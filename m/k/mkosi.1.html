DESCRIPCIÓN

mkosi es una herramienta para construir fácilmente imágenes de SO personalizadas. Es un envoltorio elegante para dnf, apt, pacman y zypper que puede generar imágenes de disco con una serie de extras.

Verbos de línea de comandos

Se conocen los siguientes verbos de línea de comandos:

resumen
Muestra un resumen legible por humanos de todas las opciones utilizadas para construir las imágenes. Esto analizará la línea de comandos y los archivos de configuración, pero solo imprimirá lo que está configurado y no construirá ni ejecutará nada realmente.
mostrar-config
Muestra los nombres y contenidos de todos los archivos de configuración cargados. mkosi carga un montón de archivos de diferentes ubicaciones y este comando facilita averiguar qué está configurado dónde.
construir
Construye la imagen basándose en la configuración pasada en la línea de comandos y en los archivos de configuración. Este comando es el predeterminado si no se especifica ningún verbo. Cualquier argumento de línea de comandos especificado después del verbo se pasará directamente al script de construcción, si se define uno.
shell
Esto construye la imagen si aún no está construida, y luego invoca systemd-nspawn para ejecutar un shell interactivo en la imagen. Esto no requiere arrancar el sistema, es como un chroot mejorado. Se puede especificar una línea de comandos opcional después del verbo shell, que se invocará en lugar del shell en el contenedor. Usa -f para reconstruir la imagen incondicionalmente antes de obtener el shell, ver más abajo. Este comando debe ejecutarse como root.
boot
Similar a shell, pero en lugar de iniciar un shell, arranca systemd en la imagen usando systemd-nspawn. Se puede especificar una línea de comandos opcional después del verbo boot, que puede contener opciones adicionales de nspawn, así como argumentos que se pasan como la línea de comandos del kernel al sistema init en la imagen.
vm
Similar a boot, pero utiliza el monitor de máquina virtual configurado (por defecto qemu) para arrancar la imagen, es decir, en lugar de virtualización de contenedores, se utiliza virtualización de máquinas virtuales. Cómo se interpretan los argumentos adicionales de la línea de comandos depende del monitor de máquina virtual configurado. Ver VirtualMachineMonitor= para más información.
ssh
Cuando la imagen se construye con la opción Ssh=yes, este comando se conecta a una máquina virtual arrancada a través de SSH. Asegúrate de ejecutar mkosi ssh con la misma configuración que mkosi build para que tenga la información necesaria disponible para conectarse a la máquina virtual en ejecución a través de SSH. Específicamente, la clave privada SSH de la configuración SshKey= se utiliza para conectarse a la máquina virtual. Usa mkosi genkey para generar automáticamente una clave y un certificado que serán recogidos por mkosi. Cualquier argumento pasado después del verbo ssh se pasa como argumentos a la invocación de ssh. Para conectarse a un contenedor, usa machinectl login o machinectl shell.

La opción Machine= se puede usar para dar un nombre de host personalizado a la máquina al arrancarla, que luego se puede usar para conectarse por ssh a la imagen (por ejemplo, mkosi --machine=mi-maquina vm seguido de mkosi --machine=mi-maquina ssh).

journalctl
Utiliza journalctl para inspeccionar el diario dentro de la imagen. Cualquier argumento especificado después del verbo journalctl se añade a la invocación de journalctl.
coredumpctl
Utiliza coredumpctl para buscar volcados de memoria dentro de la imagen. Cualquier argumento especificado después del verbo coredumpctl se añade a la invocación de coredumpctl.
sysupdate
Invoca systemd-sysupdate con la opción --transfer-source= establecida al directorio de salida y la opción --definitions= establecida al directorio configurado con SysupdateDirectory=. Cualquier argumento especificado después del verbo sysupdate se pasa directamente a la invocación de systemd-sysupdate.
sandbox
Ejecuta comandos arbitrarios dentro del mismo sandbox utilizado para ejecutar otros verbos como boot, shell, vm y más. Esto significa que /usr será reemplazado por /usr del árbol de herramientas si se utiliza uno, mientras que todo lo demás permanecerá en su lugar. Si no se proporciona ningún comando, se ejecutará $SHELL o bash si $SHELL no está establecido.
limpiar
Elimina los artefactos de construcción generados en una compilación anterior. Si se combina con -f, también elimina las imágenes de caché de compilación incremental. Si se especifica -f dos veces, también elimina cualquier caché de paquetes.
servir
Esto construye la imagen si aún no está construida, y luego sirve el directorio de salida (es decir, normalmente mkosi.output/, ver más abajo) a través de un pequeño servidor HTTP incrustado, escuchando en el puerto 8081. Combina con -f para reconstruir la imagen incondicionalmente antes de servirla. Este comando es útil para probar la adquisición basada en red de imágenes de SO, por ejemplo, a través de machinectl pull-raw ... y machinectl pull-tar ....
grabar <dispositivo>
Esto construye la imagen si aún no está construida, y luego la escribe en el dispositivo de bloque especificado. El contenido de la partición se escribe tal cual, pero la tabla de particiones GPT se corrige para que coincida con el tamaño del sector y del disco del medio especificado.

Verbs

bump
Bump the version string in mkosi.version. This is useful for implementing a simple versioning scheme: each time this verb is called the version is bumped in preparation for the subsequent build. Note that --auto-bump/-B may be used to automatically bump the version after each successful build.
genkey
Generate a pair of SecureBoot keys for usage with the SecureBootKey=/--secure-boot-key= and SecureBootCertificate=/--secure-boot-certificate= options.
documentation
Show mkosi’s documentation. If no argument is given, the mkosi man page is shown, but the arguments mkosi, mkosi-initrd, initrd, mkosi-sandbox, sandbox, mkosi.news and news are supported and respectively show the man pages for mkosi, mkosi-initrd, mkosi-sandbox and mkosi’s NEWS file.

By default this verb will try several ways to output the documentation, but a specific option can be chosen with the --doc-format option. Distro packagers are encouraged to add a file mkosi.1 into the mkosi/resources directory of the Python package, if it is missing, as well as to install it in the appropriate search path for man pages. The man page can be generated from the markdown file mkosi/resources/man/mkosi.1.md e.g via pandoc -t man -s -o mkosi.1 mkosi.1.md.

completion
Generate shell completion for the shell given as argument and print it to stdout. The arguments bash, fish, and zsh are understood.
dependencies
Output the list of packages required by mkosi to build and boot images.

This list can be piped directly to a package manager to install the packages. For example, if the host system uses the dnf package manager, the packages could be installed as follows:

mkosi dependencies | xargs -d '\n' dnf install
help
This verb is equivalent to the --help switch documented below: it shows a brief usage explanation.

Commandline-only Options

Those settings cannot be configured in the configuration files.

--force, -f
Replace the output file if it already exists, when building an image. By default when building an image and an output artifact already exists mkosi will refuse operation. Specify this option once to delete all build artifacts from a previous run before re-building the image. If incremental builds are enabled, specifying this option twice will ensure the intermediary cache files are removed, too, before the re-build is initiated. If a package cache is used (also see the Files section below), specifying this option thrice will ensure the package cache is removed too, before the re-build is initiated. For the clean operation this option has a slightly different effect: by default the verb will only remove build artifacts from a previous run, when specified once the incremental cache files are deleted too, and when specified twice the package cache is also removed.
--directory=, -C
Takes a path to a directory. mkosi switches to this directory before doing anything. Note that the various configuration files are searched for in this directory, hence using this option is an effective way to build a project located in a specific directory.
--debug
Enable additional debugging output.
--debug-shell
When executing a command in the image fails, mkosi will start an interactive shell in the image allowing further debugging.
--debug-workspace
When specified, the workspace directory will not be deleted and its location will be logged when mkosi exits.
--debug-sandbox
Run mkosi-sandbox with strace.
--version
Show package version.
--help, -h
Show brief usage information.
--genkey-common-name=
Common name to be used when generating keys via mkosi’s genkey command. Defaults to mkosi of %u, where %u expands to the username of the user invoking mkosi.
--genkey-valid-days=
Number of days that the keys should remain valid when generating keys via mkosi’s genkey command. Defaults to two years (730 days).
--auto-bump=, -B
If specified, after each successful build the version is bumped in a fashion equivalent to the bump verb, in preparation for the next build. This is useful for simple, linear version management: each build in a series will have a version number one higher then the previous one.
--doc-format
The format to show the documentation in. Supports the values markdown, man, pandoc, system and auto. In the case of markdown the documentation is shown in the original Markdown format. man shows the documentation in man page format, if it is available. pandoc will generate the man page format on the fly, if pandoc is available. system will show the system-wide man page for mkosi, which may or may not correspond to the version you are using, depending on how you installed mkosi. auto, which is the default, will try all methods in the order man, pandoc, markdown, system.
--json
Show the summary output as JSON-SEQ.
--wipe-build-dir, -w
Wipe the build directory if one is configured before building the image.

Supported output formats

The following output formats are supported:

•
Raw GPT disk image, created using systemd-repart (disk)
•
Plain directory, containing the OS tree (directory)
•
Tar archive (tar)
•
CPIO archive (cpio)

The output format may also be set to none to have mkosi produce no image at all. This can be useful if you only want to use the image to produce another output in the build scripts (e.g. build an RPM).

When a GPT disk image is created, repart partition definition files may be placed in mkosi.repart/ to configure the generated disk image.

It is highly recommended to run mkosi on a file system that supports reflinks such as XFS and btrfs and to keep all related directories on the same file system. This allows mkosi to create images very quickly by using reflinks to perform copying via copy-on-write operations.

Configuration Settings

The following settings can be set through configuration files (the syntax with SomeSetting=value) and on the command line (the syntax with --some-setting=value). For some command line parameters, a single-letter shortcut is also allowed. In the configuration files, the setting must be in the appropriate section, so the settings are grouped by section below.

Configuration is parsed in the following order:

•
The command line arguments are parsed.
•
mkosi.local.conf or mkosi.local is parsed if it exists. This file or directory should be in .gitignore (or equivalent) and is intended for local configuration.
•
Any default paths (depending on the option) are configured if the corresponding path exists.
•
mkosi.conf is parsed if it exists in the directory configured with --directory= or the current working directory if --directory= is not used.
•
mkosi.conf.d/ is parsed in the same directory if it exists. Each directory and each file with the .conf extension in mkosi.conf.d/ is parsed. Any directory in mkosi.conf.d is parsed as if it were a regular top level dir

Sintaxis del Archivo de Configuración

Los archivos de configuración son archivos de texto plano que contienen pares de asignación de variables, organizados en secciones. Las secciones se indican mediante un encabezado de sección entre corchetes, p. ej., [Config]. Los comentarios comienzan con un símbolo de almohadilla (#) y continúan hasta el final de la línea. Los valores de las variables se pueden asignar de forma literal, como una cadena entre comillas, o como una ruta de archivo. La asignación vacía se puede utilizar para restablecer un valor de variable a su valor predeterminado.

Los valores de configuración se leen de los siguientes archivos, en orden: mkosi.conf, mkosi.conf.d/*, mkosi.local.conf, mkosi.local. Los archivos de la primera ubicación se analizan en orden lexicográfico. Todos los archivos en las ubicaciones siguientes se analizan en orden lexicográfico.

Para la mayoría de las opciones, un valor vacío restaura el valor predeterminado, y el establecimiento de un valor vacío en la línea de comandos restaura el valor predeterminado, incluso si se estableció un valor en un archivo de configuración.

Los archivos de configuración y los directorios se buscan en las siguientes ubicaciones, en orden:

•
El directorio del sistema de archivos raíz.
•
Si hay algún perfil configurado, su configuración se analiza desde el directorio mkosi.profiles/.
•
Las subimágenes se analizan desde el directorio mkosi.images si existe.

Tenga en cuenta que la configuración establecida en la línea de comandos siempre tiene prioridad sobre la configuración de los archivos de configuración. Si la misma configuración se establece más de una vez en archivos de configuración, las asignaciones posteriores anulan las anteriores, excepto para la configuración que toma una colección de valores. Además, la configuración leída de mkosi.local o mkosi.local.conf anulará la configuración de los archivos que se analizan posteriormente, pero no la configuración especificada en la CLI.

Para la configuración que toma un único valor, la asignación vacía (SomeSetting= o --some-setting=) se puede usar para anular una configuración previa y restablecerla al valor predeterminado.

La configuración que toma una colección de valores se fusiona añadiendo los nuevos valores a los valores configurados previamente. Asignar una cadena vacía a dicha configuración elimina todos los valores asignados previamente y anula también cualquier valor predeterminado configurado. Los valores especificados en la CLI se añaden después de todos los valores de los archivos de configuración.

Para incluir condicionalmente archivos de configuración, se puede usar la sección [Match]. Una sección [Match] consta de condiciones individuales. Las condiciones pueden usar un símbolo de barra vertical (|) después del signo igual (...=|...), lo que hace que la condición sea una condición de activación. El archivo de configuración se incluirá si se satisface el AND lógico de todas las condiciones de no activación y el OR lógico de todas las condiciones de activación. Para negar el resultado de una condición, prefije el argumento con un signo de exclamación. Si un argumento está prefijado con el símbolo de barra vertical y un signo de exclamación, el símbolo de barra vertical debe pasarse primero y el signo de exclamación después.

Tenga en cuenta que las condiciones de [Match] se comparan con los valores actuales de configuraciones específicas y no tienen en cuenta los cambios realizados en la configuración en archivos que aún no se han analizado (los valores especificados en la CLI se tienen en cuenta). Tenga en cuenta también que coincidir con una configuración y luego cambiar su valor posteriormente en un archivo de configuración diferente puede conducir a resultados inesperados.

La sección [Match] de un archivo mkosi.conf en un directorio se aplica a todo el directorio. Si no se satisfacen las condiciones, se omite todo el directorio. Las secciones [Match] de los archivos en mkosi.conf.d/ y mkosi.local.conf solo se aplican al propio archivo.

Si hay varias secciones [Match] en el mismo archivo de configuración, cada una de ellas debe satisfacerse para que se incluya el archivo de configuración. Específicamente, las condiciones de activación solo se aplican a la sección [Match] actual y se restablecen entre varias secciones [Match]. Por ejemplo, lo siguiente solo coincidirá si el formato de salida es uno de disk o directory y la arquitectura es una de x86-64 o arm64:

[Match]
Format=|disk
Format=|directory
[Match]
Architecture=|x86-64
Architecture=|arm64

La sección [TriggerMatch] se puede utilizar para indicar secciones de coincidencia de activación. Estas son idénticas a las condiciones de activación, excepto que se aplican a toda la sección de coincidencia en lugar de solo a una única condición. Por ejemplo, lo siguiente coincidirá si la distribución es debian y la versión es bookworm o si la distribución es ubuntu y la versión es noble.

[TriggerMatch]
Distribution=debian
Release=bookworm
[TriggerMatch]
Distribution=ubuntu
Release=noble

La semántica de las condiciones en las secciones [TriggerMatch] es la misma que en [Match], es decir, todas las condiciones normales se unen mediante un AND lógico y todas las condiciones de activación se unen mediante un OR lógico. Al mezclar secciones [Match] y [TriggerMatch], se logra una coincidencia cuando todas las secciones [Match] coinciden y al menos una sección [TriggerMatch] coincide. La ausencia de secciones de coincidencia se valora como verdadera. Lógicamente, esto significa:

(⋀ᵢ Matchᵢ) ∧ (⋁ᵢ TriggerMatchᵢ)

Las opciones de línea de comandos que no toman argumentos se muestran sin = en su versión larga. En los archivos de configuración, deben especificarse con un argumento booleano: ya sea 1, yes, o true para habilitar, o 0, no, false para deshabilitar.

Sección [Distribution]

Distribution=, --distribution=, -d
La distribución a instalar en la imagen. Acepta uno de los siguientes argumentos: fedora, debian, kali, ubuntu, arch, opensuse, mageia, centos, rhel, rhel-ubi, openmandriva, rocky, alma, azure o custom. Si no se especifica, se utiliza por defecto la distribución del host o custom si la distribución del host no es una distribución compatible.
Release=, --release=, -r
La versión de la distribución a instalar en la imagen. La sintaxis precisa del argumento que toma depende de la distribución utilizada, y es ya sea una cadena numérica (en el caso de Fedora Linux, CentOS, ..., por ejemplo, 29), o un nombre de versión de distribución (en el caso de Debian, Kali, Ubuntu, ..., por ejemplo, artful). Por defecto, se utiliza una versión reciente de la distribución elegida, o la versión de la distribución que se ejecuta en el host si coincide con la distribución configurada.
Architecture=, --architecture=
La arquitectura para la que se construirá la imagen. Las arquitecturas que realmente se admiten dependen de la distribución utilizada y de si se solicita una imagen de arranque o no. Al compilar para una arquitectura externa, también deberá instalar y registrar un emulador en modo de usuario para esa arquitectura.

Se puede especificar una de las siguientes arquitecturas por imagen creada: alpha, arc, arm, arm64, ia64, loongarch64, mips64-le, mips-le, parisc, ppc, ppc64, ppc64-le, riscv32, riscv64, s390, s390x, tilegx, x86, x86-64.

LocalMirror=, --local-mirror=
El espejo se usará como un espejo local, simple y directo en lugar de usarlo como prefijo para el conjunto completo de repositorios normalmente soportados por las distribuciones. Útil para compilaciones completamente sin conexión con un único repositorio. Soportado en distribuciones basadas en deb, rpm y pacman. Anula --mirror= pero solo para la compilación local de mkosi, no se configurará dentro de la imagen final; en su lugar, se configurará --mirror= (o el repositorio predeterminado) dentro de la imagen final.
RepositoryKeyCheck=, --repository-key-check=
Controla las comprobaciones de firma/clave al usar repositorios, habilitado por defecto. Útil para deshabilitar comprobaciones cuando se combina con --local-mirror= y se usa solo un repositorio desde un sistema de archivos local.
RepositoryKeyFetch=, --repository-key-fetch=
Controla si mkosi obtendrá las claves GPG de la distribución de forma remota. Habilitado por defecto en Ubuntu cuando no se usa un árbol de herramientas o cuando se usa árboles de herramientas de Ubuntu para construir distribuciones basadas en Arch Linux o RPM. Deshabilitado por defecto en todas las demás distribuciones. Cuando se deshabilita, las claves GPG de la distribución para la distribución de destino deben instalarse localmente en el sistema anfitrión junto con el gestor de paquetes para esa distribución.

Esta configuración solo se implementa para distribuciones que usan dnf, pacman o zypper como su gestor de paquetes. Para otras distribuciones, las claves GPG de la distribución siempre se buscan localmente independientemente del valor de esta configuración. Para que las claves GPG de la distribución estén disponibles sin habilitar esta configuración, el paquete correspondiente debe ser instalado en el anfitrión. Normalmente es uno de archlinux-keyring, debian-keyring, kali-archive-keyring, ubuntu-keyring o distribution-gpg-keys (para distribuciones basadas en RPM).

Repositories=, --repositories=
Habilita repositorios de paquetes que están deshabilitados por defecto. Esto se puede usar para habilitar los repositorios EPEL para CentOS o diferentes componentes de los repositorios de Debian/Kali/Ubuntu.

Sección [Salida]

Format=, --format=, -t
El tipo de formato de imagen a generar. Uno de directory (para generar una imagen del sistema operativo directamente en un directorio local), tar (similar, pero se genera un tarball de la imagen del sistema operativo), cpio (similar, pero se genera un archivo cpio), disk (una imagen del sistema operativo en un dispositivo de bloque con una tabla de particiones GPT), uki (una imagen de kernel unificada con la imagen del sistema operativo en la sección PE de .initrd), esp (uki pero envuelta en una imagen de disco con solo una partición ESP), oci (un directorio compatible con la especificación de imagen OCI), sysext, confext, portable, addon o none (la imagen del sistema operativo está destinada únicamente como una imagen de compilación para producir otro artefacto).

Si se usa el formato de salida disk, la imagen de disco se genera utilizando systemd-repart. Los archivos de definición de particiones de `repart` a usar se pueden configurar usando la configuración RepartDirectories= o a través de mkosi.repart/. Cuando se configuran particiones verity usando la configuración Verity= de systemd-repart, mkosi analizará automáticamente el roothash de la partición hash de verity desde la salida JSON de systemd-repart y lo incluirá en la línea de comandos del kernel de cualquier imagen de kernel unificada generada por mkosi.

Si se usa el formato de salida none, los resultados de una compilación anterior no se eliminan, pero los scripts de limpieza (ver CleanScripts=) aún se ejecutan. Esto permite volver a ejecutar un script de compilación (ver BuildScripts=) sin eliminar los resultados de una compilación anterior.

ManifestFormat=, --manifest-format=
El tipo o tipos de formato de manifiesto a generar. Una lista separada por comas que consta de json (el formato de salida JSON estándar que describe los paquetes instalados), changelog (un formato de texto legible diseñado para diff). Por defecto, no se genera ningún manifiesto.
Output=, --output=, -o
Nombre a usar para el archivo o directorio de imagen de salida generado. Por defecto es image o, si se especifica ImageId=, se usa como el nombre de salida predeterminado, opcionalmente con el sufijo de la versión establecida con ImageVersion= o si una imagen específica se genera desde mkosi.images, se prefiere el nombre de la imagen sobre ImageId. Tenga en cuenta que esta opción no permite configurar el directorio de salida, use OutputDirectory= para eso.

Tenga en cuenta que esto solo especifica el prefijo de salida; dependiendo del formato de salida específico, la compresión y la versión de imagen utilizadas, el nombre de salida completo podría ser image_7.8.raw.xz.

CompressOutput=, --compress-output=
Configura la compresión para la imagen o archivo resultante. El argumento puede ser un booleano o un algoritmo de compresión (xz, zstd). La compresión zstd se usa por defecto, excepto en CentOS y sus derivados hasta la versión 8, que usan xz por defecto, y las imágenes OCI, que usan gzip por defecto. Tenga en cuenta que cuando se aplica a tipos de imagen de dispositivo de bloque, la compresión significa que la imagen no se puede iniciar directamente y necesita ser descomprimida primero. Esto también significa que los verbos shell, boot, vm no están disponibles cuando se usa esta opción. Implícito para tar, cpio, uki, esp, oci y addon.
CompressLevel=, --compress-level=
Configura el nivel de compresión a usar. Toma un entero. Los valores posibles dependen de la compresión que se esté utilizando.
OutputDirectory=, --output-directory=, -O

Bootable=, --bootable=
Toma un booleano o auto. Habilita o deshabilita la generación de una imagen arrancable. Si está habilitado, mkosi instalará un cargador de arranque EFI y agregará una partición ESP cuando se utilice la salida de imagen de disco. Si el cargador de arranque EFI seleccionado (ver Bootloader=) no está instalado o no se pueden encontrar imágenes de kernel, la compilación fallará. auto se comporta como si la opción estuviera habilitada, pero la compilación no fallará si no se pueden encontrar imágenes de kernel o el cargador de arranque EFI seleccionado. Si está deshabilitado, no se instalará ningún cargador de arranque, incluso si se encuentra dentro de la imagen, no se generarán imágenes de kernel unificadas y no se agregará ninguna partición ESP a la imagen si se utiliza el formato de salida de disco.
Bootloader=, --bootloader=
Toma uno de none, systemd-boot, uki, grub, systemd-boot-signed, uki-signed o grub-signed. El valor predeterminado es systemd-boot. Si se establece en none, no se instalará ningún cargador de arranque EFI en la imagen. Si se establece en systemd-boot, se instalará systemd-boot y para cada kernel instalado, se generará una UKI y se almacenará en EFI/Linux en la ESP. Si se establece en uki, se generará una única UKI para el último kernel instalado (el de mayor versión) que se instalará en EFI/BOOT/BOOTX64.EFI en la ESP. Si se establece en grub, para cada kernel instalado, se generará una UKI y se almacenará en EFI/Linux en la ESP. Para cada UKI generada, se agregará una entrada de menú a la configuración de grub en grub/grub.cfg en la ESP que encadena la UKI. También se escribirá un shim grub.cfg en EFI/<distribución>/grub.cfg en la ESP que carga grub/grub.cfg en la ESP para compatibilidad con versiones firmadas de grub que cargan la configuración de grub desde esta ubicación.

Las variantes signed solo instalarán binarios EFI pre-firmados enviados por la distribución.

Los kernels deben colocarse en el sistema de archivos raíz (por ejemplo, usando ExtraTrees=) en /usr/lib/modules/$version, nombrados vmlinux o vmlinuz. El $version es el producido por el objetivo make kernelversion de Kbuild.

BiosBootloader=, --bios-bootloader=
Toma uno de none o grub. El valor predeterminado es none. Si se establece en none, no se instalará ningún cargador de arranque BIOS. Si se establece en grub, grub se instalará como el cargador de arranque BIOS si se solicita una imagen arrancable con la opción Bootable=. Si no se configuran archivos de definición de particiones de re-particionamiento, mkosi agregará una partición de arranque BIOS de grub y una partición de sistema EFI a los archivos de definición de partición predeterminados.

Tenga en cuenta que esta opción no es mutuamente excluyente con Bootloader=. Es posible tener una imagen que sea arrancable tanto en UEFI como en BIOS configurando tanto Bootloader= como BiosBootloader=.

La partición de arranque BIOS de grub debe tener el UUID 21686148-6449-6e6f-744e-656564454649 y debe tener al menos 1MB.

Incluso si no se instala ningún cargador de arranque EFI, todavía necesitamos una ESP para el arranque BIOS, ya que ahí es donde almacenamos el kernel, initrd y los módulos de grub.

ShimBootloader=, --shim-bootloader=
Toma uno de none, unsigned, o signed. El valor predeterminado es none. Si se establece en none, shim y MokManager no se instalarán en la ESP. Si se establece en unsigned, mkosi buscará binarios EFI de shim y MokManager sin firmar y los instalará. Si SecureBoot= está habilitado, mkosi firmará los binarios EFI sin firmar antes de instalarlos. Si se establece en signed, mkosi buscará binarios EFI firmados y los instalará. Incluso si SecureBoot= está habilitado, mkosi no volverá a firmar estos binarios.

Tenga en cuenta que esta opción solo surte efecto cuando se solicita una imagen que se puede arrancar en firmware UEFI utilizando otras opciones (Bootable=, Bootloader=).

Tenga en cuenta que cuando esta opción está habilitada, mkosi solo instalará binarios de cargador de arranque, archivos de imagen de kernel e imágenes de kernel unificadas ya firmados, ya que la versión firmada de shim no aceptaría binarios autofirmados.

mkosi-make.conf(5)

mkosi can be configured using a system-wide configuration file /etc/mkosi/mkosi.conf, a user-specific configuration file ~/.config/mkosi/mkosi.conf, and a local configuration file ./mkosi.conf in the build directory. The latter overrides all other files. This file defines default values for the options understood by the mkosi command. See also mkosi.spec(5).

The configuration file is divided into sections, enclosed in square brackets [ ]. The first section is the [General] section, followed by the [Build] and [Host] sections. The [Build] section contains options relating to the build process itself, while the [Host] section contains options relating to how the image is run. The names of the options are case-insensitive.

Specifies whether to build disk images using loopback devices. Enabled by default. When enabled, systemd-repart will not use loopback devices to build disk images. When disabled, systemd-repart will always use loopback devices to build disk images.

Note that when using RepartOffline=nomkosi cannot run unprivileged and the image build has to be done as the root user outside of any containers and with loopback devices available on the host system.

There are currently two known scenarios where RepartOffline=no has to be used. The second is when creating a system with SELinux and an XFS root partition. Drives=, --drive=
Agrega una unidad. Toma una cadena delimitada por dos puntos con el formato <id>:<tamaño>[:<directorio>[:<opciones>[:<id-archivo>]]]. id especifica el ID asignado a la unidad. Esto se puede usar como la propiedad drive= en varios dispositivos qemu. tamaño especifica el tamaño de la unidad. Esto toma un tamaño en bytes. Además, los sufijos K, M y G se pueden usar para especificar un tamaño en kilobytes, megabytes y gigabytes respectivamente. directorio especifica opcionalmente el directorio en el que crear el archivo de respaldo de la unidad. opciones especifica opcionalmente propiedades adicionales delimitadas por comas que se pasan literalmente a la opción -drive de qemu. id-archivo especifica el ID del archivo que respalda la unidad. Las unidades con el mismo ID de archivo compartirán el archivo de respaldo. El directorio y el tamaño del archivo se determinarán a partir de la primera unidad con un ID de archivo dado.

Si existe mkosi.build (BuildScripts=), se ejecuta con la superposición de compilación montada sobre el directorio raíz de la imagen. Al ejecutar el script de compilación, $DESTDIR apunta a un directorio donde el script debe colocar cualquier archivo generado que desee que termine en la imagen. Tenga en cuenta que los sistemas de compilación basados en make, automake y meson generalmente respetan $DESTDIR, lo que hace que sea muy natural compilar árboles de *fuentes* desde el script de compilación. Después de ejecutar el script de compilación, el contenido de $DESTDIR se copia en la imagen.
•
Si existe mkosi.postinst (PostInstallationScripts=), se ejecuta después de que se instalan los árboles de compilación (opcionales) y los árboles adicionales. Este script puede usarse para modificar las imágenes sin restricciones, después de que se hayan instalado todos los paquetes de software y las fuentes compiladas.
•
Si existe mkosi.finalize (FinalizeScripts=), se ejecuta como último paso de preparación de una imagen.
•
Si existe mkosi.postoutput (PostOutputScripts=), se ejecuta justo después de que se generan todos los archivos de salida, antes de que se muevan finalmente al directorio de salida. Esto se puede usar para generar salidas adicionales o alternativas, por ejemplo, SHA256FILES o manifiestos SBOM.
•
Si existe mkosi.clean (CleanScripts=), se ejecuta justo después de que se limpian las salidas de una compilación anterior. Un script de limpieza puede limpiar cualquier salida que mkosi no conozca (por ejemplo, artefactos de SplitArtifacts=partitions o RPM compilados en un script de compilación). Tenga en cuenta que este script no utiliza el árbol de herramientas, incluso si hay uno configurado.
•
Si existe mkosi.version y es ejecutable, se ejecuta durante el análisis de la configuración y rellena ImageVersion= con la salida en stdout. Esto se puede usar para el seguimiento de versiones externo, por ejemplo, con git describe o date '+%Y-%m-%d'. Tenga en cuenta que este script se ejecuta en el sistema anfitrión sin ningún tipo de aislamiento.
•
Si existe mkosi.rootpw y es ejecutable, se ejecuta durante el análisis de la configuración y rellena RootPassword= con la salida en stdout. Esto se puede usar para generar aleatoriamente una contraseña y se puede recordar imprimiéndola en stderr o leyendo $MKOSI_CONFIG en otro script (por ejemplo, mkosi.postoutput). Tenga en cuenta que este script se ejecuta en el sistema anfitrión sin ningún tipo de aislamiento.

Si un script utiliza la extensión .chroot, mkosi hará un chroot en la imagen usando mkosi-chroot (ver más abajo) antes de ejecutar el script. Por ejemplo, si existe mkosi.postinst.chroot, mkosi hará un chroot en la imagen y lo ejecutará como script de postinstalación.

En lugar de un solo archivo de script, mkosi también leerá todos los archivos en orden lexicográfico de directorios .d con nombres apropiados, por ejemplo, todos los archivos en un mkosi.build.d se usarían como scripts de compilación. Esto está soportado por

•
mkosi.sync.d,
•
mkosi.prepare.d,
•
mkosi.build.d,
•
mkosi.postinst.d,
•
mkosi.finalize.d,
•
mkosi.postoutput.d, y
•
mkosi.clean.d.

Esto se puede combinar con la extensión .chroot, por ejemplo, mkosi.build.d/01-foo.sh se ejecutará sin hacer chroot en la imagen y mkosi.build.d/02-bar.sh.chroot se ejecutará después de hacer chroot en la imagen primero.

Los scripts ejecutados por mkosi reciben las siguientes variables de entorno:

•
$ARCHITECTURE contiene la arquitectura de la configuración Architecture=. Si Architecture= no está configurada, contendrá la arquitectura nativa de la máquina anfitriona. Consulte la documentación de Architecture= para ver los valores posibles de esta variable.
•
$QEMU_ARCHITECTURE contiene la arquitectura de $ARCHITECTURE en el formato utilizado por qemu. Útil para encontrar el binario de qemu ( qemu-system-$QEMU_ARCHITECTURE).
•
$DISTRIBUTION contiene la distribución de la configuración Distribution=.
•
$RELEASE contiene la versión de la configuración Release=.
•
$DISTRIBUTION_ARCHITECTURE contiene la arquitectura de $ARCHITECTURE en el formato utilizado por la distribución configurada.
•
$PROFILES contiene los perfiles de la configuración Profiles= como una cadena delimitada por comas.
•
$CACHED= se establece en 1 si hay una imagen en caché disponible, 0 en caso contrario.
•
$CHROOT_SCRIPT contiene la ruta del script en ejecución relativa al directorio raíz de la imagen. El caso de uso principal de esta variable es en combinación con el script mkosi-chroot. Consulte la descripción de mkosi-chroot más adelante para obtener más información.
•
$SRCDIR contiene la ruta al directorio desde donde se invocó mkosi, con las fuentes de compilación configuradas montadas encima. $CHROOT_SRCDIR contiene el valor que tendrá $SRCDIR después de invocar mkosi-chroot.
•
$BUILDDIR solo se define si existe mkosi.builddir y apunta al directorio de compilación a utilizar. Esto es útil para todos los sistemas de compilación que admiten compilaciones fuera del árbol para reutilizar artefactos ya compilados de ejecuciones anteriores. $CHROOT_BUILDDIR contiene el valor que tendrá $BUILDDIR después de invocar mkosi-chroot.
•
$DESTDIR es un directorio donde se puede colocar cualquier software instalado generado por un script de compilación. Esta variable solo se establece al ejecutar un script de compilación. $CHROOT_DESTDIR contiene el valor que tendrá $DESTDIR después de invocar mkosi-chroot.
•
$OUTPUTDIR apunta al directorio provisional utilizado para almacenar los artefactos de compilación generados durante la compilación. $CHROOT_OUTPUTDIR contiene el valor que tendrá $OUTPUTDIR después de invocar mkosi-chroot.
•
$PACKAGEDIR apunta al directorio que contiene el repositorio de paquetes local. Los scripts de compilación pueden agregar más paquetes al repositorio local escribiendo los paquetes en $PACKAGEDIR.
•
$ARTIFACTDIR apunta al directorio que se utiliza para pasar artefactos de compilación generados durante la compilación y hacerlos disponibles para su uso por mkosi. Esto es similar a PACKAGEDIR, pero está destinado a artefactos que podrían no ser paquetes entendidos por el administrador de paquetes, por ejemplo, initrds creados por generadores de initrd distintos de mkosi. Los scripts de compilación pueden agregar más artefactos al directorio colocándolos en $ARTIFACTDIR. Los archivos en este directorio solo están disponibles para la compilación actual y no se copian hacia afuera como el contenido de $OUTPUTDIR.

mkosi también utilizará ciertos subdirectorios de un directorio de artefactos para usar automáticamente su contenido en ciertos pasos. Actualmente, los siguientes dos subdirectorios en el directorio de artefactos son utilizados por mkosi:

•
io.mkosi.microcode: Todos los archivos en este directorio se utilizan como archivos de microcódigo, es decir, se anteponen a los initrds en orden lexicográfico.
•
io.mkosi.initrd: Todos los archivos en este directorio se utilizan como initrds y se unen en orden lexicográfico.

Se recomienda que los usuarios de $ARTIFACTDIR coloquen cosas para su propio uso en un directorio con nombres similares, por ejemplo, local.my.namespace.

•
$BUILDROOT es el directorio raíz de la imagen que se está compilando, opcionalmente con la superposición de compilación montada encima dependiendo del script que se esté ejecutando.
•
$WITH_DOCS es 0 o 1 dependiendo de si se solicitó una compilación sin o con documentación instalada (WithDocs=yes). Un script de compilación debería suprimir la instalación de cualquier documentación de paquetes en $DESTDIR en caso de $WITH_DOCS se establece en 0.
•
$WITH_TESTS es 0 o 1 dependiendo de si se solicitó una compilación sin o con la ejecución de la suite de pruebas (WithTests=no). Un script de compilación debe evitar ejecutar pruebas unitarias o de integración en caso de que $WITH_TESTS sea 0.
•
$WITH_NETWORK es 0 o 1 dependiendo de si se está ejecutando una compilación sin o con redes (WithNetwork=no). Un script de compilación debe evitar cualquier comunicación de red en caso de que $WITH_NETWORK sea 0.
•
$SOURCE_DATE_EPOCH se define si se solicita (SourceDateEpoch=TIMESTAMP, Environment=SOURCE_DATE_EPOCH=TIMESTAMP o la variable de entorno del host $SOURCE_DATE_EPOCH). Esto es útil para hacer que las compilaciones sean reproducibles. Consulte SOURCE_DATE_EPOCH para más información.
•
$MKOSI_UID y $MKOSI_GID respectivamente son el uid, gid del usuario que invocó mkosi.
•
$MKOSI_CONFIG es un archivo que contiene un resumen JSON de la configuración de la imagen actual. Este archivo puede ser analizado dentro de scripts para acceder a todas las configuraciones de la imagen actual.
•
$IMAGE_ID contiene el identificador de la configuración ImageId= o --image-id=.
•
$IMAGE_VERSION contiene la versión de la configuración ImageVersion= o --image-version=.

Adicionalmente, cuando se ejecuta un script, algunos scripts se ponen a disposición a través de $PATH para simplificar casos de uso comunes.

•
mkosi-chroot: Este script entrará en el entorno chroot de la imagen y ejecutará el comando dado. Además de entrar en el entorno chroot de la imagen, también montará varios archivos y directorios ($SRCDIR, $DESTDIR, $BUILDDIR, $OUTPUTDIR, $CHROOT_SCRIPT) dentro de la imagen y modificará las variables de entorno correspondientes para que apunten a las ubicaciones dentro de la imagen. También montará sistemas de archivos APIVFS (/proc, /dev, ...) para asegurarse de que los scripts y herramientas ejecutados dentro del chroot funcionen correctamente. También propaga /etc/resolv.conf desde el host al chroot si se solicita, de modo que la resolución DNS funcione dentro del chroot. Después de que el comando mkosi-chroot salga, varios puntos de montaje se limpiarán.

Por ejemplo, para invocar ls dentro de la imagen, usa lo siguiente:

mkosi-chroot ls ...

Para ejecutar el script completo dentro de la imagen, añade un sufijo .chroot al nombre ( mkosi.build.chroot en lugar de mkosi.build, etc.).

•
Para todos los gestores de paquetes compatibles (dnf, rpm, apt, dpkg, pacman, zypper), se colocan scripts con el mismo nombre en $PATH que aseguran que estos comandos operen sobre el directorio raíz de la imagen con la configuración proporcionada por el usuario en lugar de sobre el sistema host. Esto significa que desde un script, puedes hacer, por ejemplo, dnf install vim para instalar vim en la imagen.

Adicionalmente, mkosi-install, mkosi-reinstall, mkosi-upgrade y mkosi-remove invocarán la operación correspondiente del gestor de paquetes que se esté utilizando para construir la imagen.

•
git se invoca automáticamente con safe.directory=* para evitar errores de permisos cuando se ejecuta como usuario root en un espacio de nombres de usuario.
•
useradd y groupadd se invocan automáticamente con --root=$BUILDROOT cuando se ejecutan fuera de la imagen.

Cuando se ejecutan scripts, los directorios que aún son escribibles también se vuelven de solo lectura (/home, /var, /root, ...) y solo se permite escribir en el conjunto mínimo de directorios que necesitan ser escribibles. Esto es para asegurar que los scripts no puedan interferir con el sistema host cuando mkosi se ejecuta como root.

Tenga en cuenta que al ejecutar scripts, todos los directorios fuente se vuelven efímeros, lo que significa que todos los cambios realizados en los directorios fuente mientras se ejecutan los scripts se descartan después de que los scripts terminan de ejecutarse. Utilice los directorios de salida, de compilación o de caché si necesita persistir datos entre compilaciones.

Archivos

Para facilitar la creación de imágenes para versiones de desarrollo de sus proyectos, mkosi puede leer datos de configuración del directorio local, asumiendo que se invoca desde un árbol de *fuente*. Específicamente, se utilizan los siguientes archivos si existen en el directorio local:

•
El directorio mkosi.skeleton/ o el archivo comprimido mkosi.skeleton.tar pueden usarse para insertar archivos en la imagen. Los archivos se copian *antes* de que los paquetes de la distribución se instalen en la imagen. Esto permite la creación de archivos que necesitan ser proporcionados temprano, por ejemplo, para configurar el gestor de paquetes o establecer los presets de systemd.

Al usar el directorio, la propiedad de los archivos no se conserva: todos los archivos copiados serán propiedad de root. Para conservar la propiedad, use un archivo tar.

•
El directorio mkosi.extra/ o el archivo comprimido mkosi.extra.tar pueden usarse para insertar archivos adicionales en la imagen, además de lo que la distribución incluye en sus paquetes. Son similares a mkosi.skeleton/ y mkosi.skeleton.tar, pero los archivos se copian en el árbol de directorios de la imagen *después* de que el sistema operativo fue instalado.

Al usar el directorio, la propiedad de los archivos no se conserva: todos los archivos copiados serán propiedad de root. Para conservar la propiedad, use un archivo tar.

•
El directorio mkosi.sandbox/ o el archivo comprimido mkosi.sandbox.tar pueden usarse para configurar el gestor de paquetes sin que los archivos se inserten en la imagen. Si los archivos deben incluirse en la imagen, se debería usar mkosi.skeleton/ y mkosi.skeleton.tar en su lugar.

Al usar el directorio, la propiedad de los archivos no se conserva: todos los archivos copiados serán propiedad de root. Para conservar la propiedad, use un archivo tar.

•
El archivo de configuración nspawn mkosi.nspawn se copiará en el mismo lugar que el archivo de imagen de salida, si existe. Esto es útil ya que nspawn busca archivos de configuración junto a los archivos de imagen que arranca, para configuraciones adicionales del entorno de ejecución del contenedor.
•
El directorio mkosi.cache/, si existe, se utiliza automáticamente como caché de descarga de paquetes, para acelerar las ejecuciones repetidas de la herramienta.
•
El directorio mkosi.builddir/, si existe, se utiliza automáticamente como directorio de compilación fuera del árbol, si los comandos de compilación en los scripts mkosi.build lo admiten. Específicamente, este directorio se montará en el contenedor de compilación, y la variable de entorno $BUILDDIR se establecerá a este valor cuando se invoquen los scripts de compilación. Un script de compilación puede entonces usar este directorio como directorio de compilación, para compilaciones fuera del árbol al estilo automake o ninja. Esto acelera considerablemente las compilaciones, en particular cuando mkosi se utiliza en modo incremental (-i): no solo la imagen y la superposición de compilación, sino también el árbol de compilación se reutilizan entre invocaciones subsiguientes. Tenga en cuenta que si este directorio no existe, la variable de entorno $BUILDDIR no se establece, y depende de los scripts de compilación decidir si realizar una compilación dentro o fuera del árbol, y qué directorio de compilación utilizar.
•
El archivo mkosi.rootpw se puede utilizar para proporcionar la contraseña del usuario root de la imagen. Si la contraseña va precedida de hashed:, se trata como una contraseña root ya hasheada. La contraseña opcionalmente puede ir seguida de un carácter de nueva línea que se elimina implícitamente. El archivo debe tener un modo de acceso de 0600 o inferior. Si este archivo no existe, se establece la contraseña root por defecto de la distribución (lo que generalmente significa que el acceso al usuario root está bloqueado).
•
El archivo mkosi.passphrase proporciona la frase de contraseña a utilizar cuando se selecciona el cifrado LUKS. Debe contener la frase de contraseña literalmente, y
not end in a newline character (i.e. en el mismo formato que cryptsetup y /etc/crypttab esperan los archivos de frase de contraseña). El archivo debe tener un modo de acceso de 0600 o menos.
•
Los archivos mkosi.crt y mkosi.key contienen un certificado X.509 y una clave privada PEM para usar cuando se requiere firma (UEFI SecureBoot, verity, ...).
•
El directorio mkosi.output/ se utiliza para almacenar todos los artefactos de compilación.
•
El directorio mkosi.credentials/ se utiliza como fuente de credenciales adicionales similar a la opción Credentials=. Para cada archivo en el directorio, el nombre del archivo se usará como el nombre de la credencial y el contenido del archivo se convertirá en el valor de la credencial, o, si el archivo es ejecutable, mkosi ejecutará el archivo y la salida del comando a stdout se utilizará como el valor de la credencial. La salida a stderr se ignorará. Las credenciales configuradas con Credentials= tienen prioridad sobre los archivos en mkosi.credentials.
•
El directorio mkosi.repart/ se utiliza como fuente para los archivos de definición de particiones de systemd-repart, que se pasan a systemd-repart al compilar una imagen de disco. Si no existe y la configuración RepartDirectories= no está configurada, mkosi usará por defecto los siguientes archivos de definición de particiones:

00-esp.conf (si estamos compilando una imagen arrancable):

[Partition]
Type=esp
Format=vfat
CopyFiles=/boot:/
CopyFiles=/efi:/
SizeMinBytes=512M
SizeMaxBytes=512M

05-bios.conf (si estamos compilando una imagen arrancable para BIOS):

[Partition]
# UUID de la partición de arranque BIOS de grub que grub necesita en GPT para
# embeberse.
Type=21686148-6449-6e6f-744e-656564454649
SizeMinBytes=1M
SizeMaxBytes=1M

10-root.conf

[Partition]
Type=root
Format=<distribution-default-filesystem>
CopyFiles=/
Minimize=guess

Tenga en cuenta que si se encuentra mkosi.repart/ o se utiliza RepartDirectories=, no utilizaremos ninguna de las definiciones de partición predeterminadas.

Todos estos archivos son opcionales.

Tenga en cuenta que la ubicación de todos estos archivos también puede configurarse durante la invocación a través de opciones de línea de comandos y como configuraciones en mkosi.conf, en caso de que la configuración predeterminada no sea aceptable para un proyecto.

CACHÉ

mkosi admite tres cachés diferentes para acelerar la reconstrucción repetitiva de imágenes. Específicamente:

1.
La caché de paquetes del gestor de paquetes de la distribución puede almacenarse en caché entre compilaciones. Esto se configura con la opción --cache-directory= o el directorio mkosi.cache/. Esta forma de caché depende del gestor de paquetes de la distribución y almacena en caché los paquetes de la distribución (RPM, deb, ...) después de que se descargan, pero antes de que se desempaquetan.
2.
Si el modo de compilación incremental se habilita con --incremental, se crean copias en caché de la imagen final y del overlay de compilación inmediatamente antes de que se copien las fuentes de compilación (para el overlay de compilación) o los artefactos generados por mkosi.build se copien (en el caso de la imagen final). Esta forma de caché permite omitir el paso de desempaquetado de paquetes que consume mucho tiempo de los gestores de paquetes de la distribución, pero solo es efectiva si la lista de paquetes a utilizar permanece estable, pero las fuentes de compilación y sus scripts cambian regularmente. Tenga en cuenta que esta caché requiere un vaciado manual: siempre que se modifique la lista de paquetes, las imágenes en caché deben eliminarse explícitamente antes de la próxima reconstrucción, utilizando el interruptor -f.
3.
Finalmente, entre compilaciones múltiples, el directorio de artefactos de compilación puede compartirse, utilizando el directorio mkosi.builddir/. Este directorio permite que los sistemas de compilación como Meson reutilicen fuentes ya compiladas de una compilación anterior, acelerando así el proceso de compilación de un script de compilación de mkosi.build.

La caché de paquetes y el modo incremental son útiles incondicionalmente. La caché final solo se aplica a los usos de mkosi con un árbol de fuentes y un script de compilación. Cuando los tres están habilitados juntos, los tiempos de respuesta para compilaciones de imágenes completas son mínimos, ya que solo los archivos fuente modificados deben recompilarse.

VARIABLES DE ENTORNO

•
$MKOSI_LESS anula las opciones de less cuando es invocado por mkosi para paginar la salida.
•
$MKOSI_DNF puede ser utilizado para anular el ejecutable utilizado como dnf. Esto es particularmente útil para seleccionar entre dnf y dnf5.
•
$EPEL_MIRROR puede ser utilizado para anular la ubicación del espejo predeterminado utilizada para los repositorios de epel cuando se utiliza Mirror=. Por defecto, mkosi busca los repositorios de epel en el subdirectorio fedora del directorio padre del espejo especificado en Mirror=. Por ejemplo, si el espejo está configurado en https://mirror.net/centos-stream, mkosi buscará los repositorios de epel en https://mirror.net/fedora/epel.
•
SYSEXT_SCOPE y CONFEXT_SCOPE pueden ser utilizados para anular el valor predeterminado del archivo extension-release correspondiente al crear un sysext o confext. Por defecto, el valor se establece en initrd system portable.

EJEMPLOS

Crea y ejecuta una imagen GPT en formato crudo con ext4, como image.raw:

# mkosi -p systemd --incremental boot

Crea y ejecuta una imagen GPT arrancable, como foobar.raw:

$ mkosi -d fedora -p kernel-core -p systemd -p systemd-boot -p udev -o foobar.raw
# mkosi --output foobar.raw boot
$ mkosi --output foobar.raw vm

Crea y ejecuta una imagen de Fedora Linux en un directorio simple:

# mkosi --distribution fedora --format directory boot

Crea una imagen comprimida image.raw.xz con SSH instalado y agrega un archivo de suma de verificación:

$ mkosi --distribution fedora --format disk --checksum --compress-output --package=openssh-clients

Dentro del directorio fuente de un proyecto basado en automake, configura mkosi para que simplemente invocando mkosi sin parámetros se cree una imagen del sistema operativo que contenga una versión compilada del proyecto en su estado actual:

$ cat >mkosi.conf <<EOF
[Distribution]
Distribution=fedora
[Output]
Format=disk
[Content]
Packages=kernel,systemd,systemd-udev,openssh-clients,httpd
BuildPackages=make,gcc,libcurl-devel
EOF
$ cat >mkosi.build <<EOF
#!/bin/sh
if [ "$container" != "mkosi" ]; then
    exec mkosi-chroot "$CHROOT_SCRIPT" "$@"
fi
cd $SRCDIR
./autogen.sh
./configure --prefix=/usr
make -j `nproc`
make install
EOF
$ chmod +x mkosi.build
# mkosi --incremental boot
# systemd-nspawn -bi image.raw

Diferentes formas de arrancar con vm

La forma más sencilla de arrancar una máquina virtual es crear una imagen con los componentes necesarios y dejar que mkosi llame a qemu con todas las opciones correctas:

$ mkosi -d fedora \
    --autologin \
    -p systemd-udev,systemd-boot,kernel-core \
    build
$ mkosi -d fedora vm
...
fedora login: root (automatic login)
[root@fedora ~]#

Por defecto, el arranque es solo con consola de texto. En este modo, los mensajes del cargador de arranque, el kernel y systemd, y más tarde el prompt de inicio de sesión de getty y el shell, utilizan todos la misma terminal. Es posible cambiar entre la consola de qemu y el monitor presionando Ctrl-a c. El monitor de qemu puede ser, por ejemplo, utilizado para inyectar teclas especiales o apagar la máquina rápidamente. Alternativamente, la máquina puede ser apagada usando Ctrl-a x.

Para arrancar con una ventana gráfica, agrega --console=gui:

$ mkosi -d fedora --console=gui qemu

Se puede arrancar un kernel directamente con mkosi vm -kernel ... -initrd ... -append '...'. Esto es un poco más rápido porque no se utiliza un cargador de arranque, y también es más fácil experimentar con diferentes kernels y líneas de comandos del kernel. Ten en cuenta que, a pesar de su nombre, la opción -append de qemu reemplaza la línea de comandos del kernel incrustada por defecto en el kernel y cualquier especificación anterior de -append.

El UKI también se copia en el directorio de salida y puede ser arrancado directamente:

$ mkosi vm -kernel mkosi.output/fedora~38/image.efi

Al arrancar usando un kernel externo, no necesitamos el kernel *dentro* de la imagen, pero todavía querríamos que los módulos del kernel estuvieran instalados.

También es posible realizar un *arranque directo del kernel* a un cargador de arranque, aprovechando el hecho de que systemd-boot(7) es un binario UEFI válido:

$ mkosi vm -kernel /usr/lib/systemd/boot/efi/systemd-bootx64.efi

En este escenario, el kernel es cargado desde el ESP en la imagen por systemd-boot.

REQUISITOS

mkosi está empaquetado para varias distribuciones: Debian, Kali, Ubuntu, Arch Linux, Fedora Linux, OpenMandriva, Gentoo. Ten en cuenta que ha pasado tiempo desde el último lanzamiento y los paquetes distribuidos por los sistemas operativos están muy desactualizados. Actualmente recomendamos ejecutar mkosi desde git hasta que ocurra un nuevo lanzamiento.

mkosi requiere un kernel de Linux que proporcione mount_setattr(), introducido en la versión 5.12.

mkosi actualmente requiere systemd 254 para construir imágenes de disco arrancables.

Cuando no se utilizan los paquetes de distribución, asegúrate de instalar las dependencias necesarias. Por ejemplo, en Fedora Linux necesitas:

# dnf install btrfs-progs apt dosfstools mtools edk2-ovmf e2fsprogs squashfs-tools gnupg python3 tar xfsprogs xz zypper sbsigntools

En Debian/Kali/Ubuntu podría ser necesario instalar explícitamente los paquetes ubuntu-keyring, ubuntu-archive-keyring, kali-archive-keyring y/o debian-archive-keyring, además de apt, dependiendo de qué tipo de imágenes de distribución quieras construir.

Ten en cuenta que la versión mínima de Python requerida es la 3.9.

mkosi necesita habilidades sin restricciones para crear y actuar dentro de namespaces. Algunas distribuciones restringen la creación de, o las capacidades dentro de, namespaces de usuario, lo que rompe mkosi.

Para obtener información sobre Ubuntu, que implementa tales restricciones utilizando AppArmor, consulta https://ubuntu.com/blog/ubuntu-23-10-restricted-unprivileged-user-namespaces. Para otros sistemas, intenta investigar los sysctls kernel.unprivileged_userns_clone o user.max.user_namespace.

Para sistemas Ubuntu, puedes eliminar las restricciones para mkosi adaptando este fragmento para que apunte a tu binario de mkosi, copiándolo a /etc/apparmor.d/path.to.mkosi y luego ejecutando systemctl reload apparmor:

abi <abi/4.0>,
include <tunables/global>
/path/to/mkosi flags=(default_allow) {
  userns,
}

Preguntas Frecuentes (FAQ)

•
¿Por qué mkosi vm con KVM no funciona en Debian/Kali/Ubuntu?

Mientras que otras distribuciones permiten el acceso a /dev/kvm sin problemas, en Debian/Kali/Ubuntu esto solo está permitido para usuarios del grupo kvm. Debido a que mkosi se desvincula de un namespace de usuario al ejecutarse sin privilegios, incluso si el usuario que llama estaba en el grupo kvm, cuando mkosi se desvincula del namespace de usuario para ejecutarse sin privilegios, pierde el acceso al grupo kvm y para cuando iniciamos qemu ya no tenemos acceso a /dev/kvm. Como solución alternativa, puedes cambiar los permisos de los nodos de dispositivo a 0666, lo que es suficiente para que KVM funcione sin privilegios. Para que esta configuración persista después de los reinicios, copia /usr/lib/tmpfiles.d/static-nodes-permissions.conf a /etc/tmpfiles.d/static-nodes-permissions.conf y cambia el modo de /dev/kvm de 0660 a 0666.

•
¿Cómo agrego un usuario regular a una imagen?

Puedes usar el siguiente fragmento en un script de postinstalación:

useradd --create-home --user-group $USER --password "$(openssl passwd -stdin -6 <$USER_PASSWORD_FILE)"

Ten en cuenta que a partir de systemd v256, si está habilitado, systemd-homed-firstboot.service solicitará la creación de un usuario regular en el primer arranque si no existen usuarios regulares.

•
¿Por qué veo errores al cambiar la propiedad de archivos al construir imágenes?

Cuando no se ejecuta como root, tu usuario no puede cambiar la propiedad de los archivos a propietarios arbitrarios. Varias distribuciones todavía distribuyen archivos en sus paquetes que no son propiedad del usuario root. Cuando no se ejecuta como root, mkosi mapea el usuario actual a root al invocar los gestores de paquetes, lo que significa que cambiar la propiedad a root funcionará, pero cambiar la propiedad a cualquier otro usuario o grupo fallará.

Ten en cuenta que las llamadas chown solo se suprimen al ejecutar gestores de paquetes, pero no al ejecutar scripts. Si esto es necesario, por ejemplo, para un script de compilación, puedes establecer la variable MKOSI_CHROOT_SUPPRESS_CHOWN a un valor verdadero (verdadero significa que se suprimirán las llamadas chown).

Preguntas frecuentes (FAQ)

•
¿Por qué portablectl inspect <imagen>/systemd-dissect <imagen> dice que mi servicio portátil no lo es?

systemd-dissect y portablectl inspect buscan PORTABLE_PREFIXES= en os-release y si la clave falta, no reconocerán un servicio portátil como tal, mostrando ✗ bajo Usar como para el caso de systemd-dissect o n/a bajo Servicio portátil para portablectl.

Dado que no hay un buen valor predeterminado para esta clave y las imágenes de servicio portátil generadas se adjuntarán correctamente, incluso cuando la clave no esté establecida, mkosi no establece uno.

Puede establecer PORTABLE_PREFIXES= en el archivo os-release usted mismo en un script postinst.
