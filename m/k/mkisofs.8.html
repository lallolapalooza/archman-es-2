MKISOFS(8) Manual del Administrador del Sistema MKISOFS(8)

NOMBRE

mkisofs - crear una imagen de sistema de archivos híbrida ISO-9660/JOLIET/HFS/UDF con atributos Rock Ridge opcionales.

SINOPSIS

mkisofs [ opciones ] [ -o archivo ] ruta [ruta ...]
mkisofs [ opciones ] [ -o archivo ] -find [expresión find]

DESCRIPCIÓN

mkisofs es efectivamente un programa de pre-masterización para generar un sistema de archivos híbrido ISO-9660/JOLIET/HFS/UDF.

Los sistemas de archivos ISO-9660/JOLIET/UDF tienen un tamaño máximo de 8 TB. El tamaño máximo de un archivo individual es de 8 TB (los archivos individuales en UDF están actualmente limitados a aprox. 200 GB). Si desea tener archivos de más de 2 GB, necesita especificar -iso-level 3 o superior. Si se crea una híbrida HFS, el tamaño máximo de archivo para los archivos en la híbrida HFS es de 2 GB en cualquier caso.

Soporte de sistemas de archivos híbridos

mkisofs es capaz de generar los registros del Protocolo de Compartición de Uso del Sistema (SUSP) especificados por el Protocolo de Intercambio Rock Ridge. Esto se utiliza para describir más detalladamente los archivos en el sistema de archivos ISO-9660 para un host UNIX, y proporciona información como nombres de archivo más largos, uid/gid, permisos posix, enlaces simbólicos, enlaces duros, dispositivos de bloques y de caracteres.

Si se especifican las opciones de línea de comandos para híbridos Joliet, HFS o UDF, mkisofs creará metadatos de sistema de archivos adicionales y separados para Joliet, HFS o UDF. El contenido del archivo en este caso se refiere a los mismos bloques de datos en los medios. Generará un sistema de archivos ISO-9660 puro a menos que se proporcionen las opciones de línea de comandos para híbridos Joliet, HFS o UDF.

mkisofs puede generar un sistema de archivos híbrido HFS *verdadero* (o *compartido*). Los mismos archivos se ven como archivos HFS cuando se accede desde un Macintosh y como archivos ISO-9660 cuando se accede desde otras máquinas. HFS significa *Hierarchical File System* (Sistema de Archivos Jerárquico) y es el sistema de archivos nativo utilizado en las computadoras Macintosh hasta Mac OS 9.

Como alternativa, mkisofs puede generar las *Extensiones de Apple para ISO-9660* o *UDF* para cada archivo. Estas extensiones proporcionan a cada archivo el CREATOR, TYPE y ciertos Flags del Finder cuando se accede desde un Macintosh. Consulte la sección FORMATOS DE ARCHIVO DE MACINTOSH HFS a continuación.

Descripción funcional

mkisofs toma una instantánea de un árbol de directorios dado y genera una imagen binaria que corresponderá a un sistema de archivos ISO-9660 o Joliet/HFS/UDF cuando se escriba en un dispositivo de bloques.

Cada archivo escrito en el sistema de archivos ISO-9660 debe tener un nombre de archivo en formato 8.3 (8 caracteres, punto, 3 caracteres, todo en mayúsculas), incluso si se utilizan atributos Rock Ridge. Este nombre de archivo se utiliza en sistemas que no son capaces de utilizar las extensiones Rock Ridge (como MS-DOS), y cada nombre de archivo en cada directorio debe ser diferente de los otros nombres de archivo en el mismo directorio. mkisofs generalmente intenta formar nombres correctos forzando el nombre de archivo UNIX a mayúsculas y truncando según sea necesario, pero a menudo esto produce resultados insatisfactorios cuando hay casos en los que los nombres truncados no son todos únicos. mkisofs asigna ponderaciones a cada nombre de archivo, y si se encuentran dos nombres que son idénticos de otra manera, el nombre con menor prioridad se renombra para tener un número de 3 dígitos como extensión (donde el número está garantizado que sea único). Un ejemplo de esto serían los archivos foo.bar y foo.bar.~1~: el archivo foo.bar.~1~ se escribiría como FOO000.BAR;1 y el archivo foo.bar se escribiría como FOO.BAR;1.

Cuando se utiliza con varias opciones HFS o UDF, mkisofs intentará reconocer archivos almacenados en varios formatos de archivo Apple/Unix y copiará los datos y las bifurcaciones de recursos, así como cualquier información relevante del Finder. Consulte la sección FORMATOS DE ARCHIVO DE MACINTOSH HFS a continuación para obtener más información sobre los formatos que admite mkisofs.

Tenga en cuenta que mkisofs no está diseñado para comunicarse directamente con grabadoras de medios ópticos. La mayoría de las grabadoras tienen conjuntos de comandos propietarios que varían de un fabricante a otro, y necesita una herramienta especializada como cdrecord para grabar el disco.

La utilidad cdrecord es una utilidad capaz de grabar un disco real. La última versión de cdrecord está disponible en https://sourceforge.net/projects/cdrtools/files/ o https://sourceforge.net/projects/cdrtools/files/alpha/

También debe saber que la mayoría de las grabadoras de CD son muy particulares con el tiempo. Una vez que comience a grabar un disco, no puede permitir que su búfer se vacíe antes de terminar, o terminará con un disco corrupto. Por lo tanto, es fundamental que pueda mantener un flujo de datos ininterrumpido a la grabadora durante todo el tiempo que se esté grabando el disco.

Tratamiento de nombres de ruta

ruta es la ruta del árbol de directorios que se copiará en el sistema de archivos ISO-9660. Se pueden especificar varias rutas, y mkisofs fusionará los archivos encontrados en todos los componentes de ruta especificados para formar la imagen del cdrom.

Si se ha especificado la opción -graft-points, es posible "injertar" las rutas en puntos distintos del directorio raíz, y es posible injertar archivos o directorios en la imagen del cdrom con nombres diferentes a los que tienen en el sistema de archivos de origen. Esto es más fácil de ilustrar con un par de ejemplos. Empecemos asumiendo que existe un archivo local ../old.lis y desea incluirlo en la imagen del cdrom.

foo/bar/=../old.lis

incluirá el archivo old.lis en la imagen del cdrom en /foo/bar/old.lis, mientras que

foo/bar/xxx=../old.lis

incluirá el archivo old.lis en la imagen del cdrom en /foo/bar/xxx. El mismo tipo de sintaxis se puede utilizar también con directorios. mkisofs creará cualquier directorio necesario para que los puntos de injerto existan en la imagen del cdrom; los directorios no necesitan aparecer en una de las rutas. Por defecto, cualquier directorio que se cree sobre la marcha de esta manera tendrá permisos 0555 y parecerá ser propiedad de la persona que ejecuta mkisofs. Si desea otros permisos o propietarios para los directorios intermedios, consulte -uid, -gid, -dir-mode, -file-mode y -new-dir-mode.

mkisofs también se ejecutará en máquinas Win9x/NTx cuando se compile con cygwin de Cygnus (disponible en http://sourceware.cygnus.com/cygwin/). Por lo tanto, la mayoría de las referencias en esta página del manual a *Unix* también se aplican a *Win32* o *Win64*.

Este parámetro también se puede configurar en el archivo .mkisofsrc con ABST=nombrearchivo. Si se especifica en ambos lugares, se utiliza la versión de la línea de comandos.

Depende del usuario de mkisofs incluir un archivo con el nombre apropiado en el árbol del sistema de archivos creado.

Especifica una cadena de texto que se escribirá en la cabecera del volumen. Debería describir la aplicación que estará en el disco. Hay espacio en el disco para 128 caracteres de información. La entrada Joliet relacionada está limitada a 64 caracteres. Este parámetro también se puede configurar en el archivo .mkisofsrc con APPI=id. Si se especifica en ambos lugares, se utiliza la versión de la línea de comandos.
-allow-leading-dots
-ldots

Esto viola el estándar ISO-9660, pero funciona en muchos sistemas. Úselo con precaución.
-allow-lowercase
Esta opción permite que aparezcan caracteres en minúscula en los nombres de archivo ISO-9660.
Esto viola el estándar ISO-9660, pero funciona en algunos sistemas. Úselo con precaución.
-no-allow-lowercase
Esto restablece el efecto de -allow-lowercase e incluso funciona cuando se han utilizado -U, -untranslated-filenames o -iso-level 4 para permitir nombres de archivo en minúsculas.
-allow-multidot
Esta opción permite que aparezca más de un punto en los nombres de archivo ISO-9660. Un punto inicial no se ve afectado por esta opción; puede permitirse por separado usando la opción -allow-leading-dots.
Esto viola el estándar ISO-9660, pero funciona en muchos sistemas. Úselo con precaución.

Especifica el nombre del archivo bibliográfico en el descriptor de volumen primario. Hay espacio en el disco para 37 caracteres de información. La entrada Joliet relacionada está limitada a 18 caracteres. Este parámetro también se puede establecer en el archivo .mkisofsrc con BIBLO=nombrearchivo. Si se especifica en ambos lugares, se utiliza la versión de la línea de comandos.

Corresponde al usuario de mkisofs incluir un archivo con el nombre apropiado en el árbol de sistemas de archivos creado.

-cache-inodes
Almacena en caché los números de inodo y dispositivo para encontrar enlaces duros a archivos. Si mkisofs encuentra un enlace duro (un archivo con varios nombres), el archivo aparecerá solo una vez en el CD. Esto ayuda a ahorrar espacio en el CD. La opción -cache-inodes es la predeterminada en sistemas operativos tipo UNIX. Tenga cuidado al usar esta opción en un sistema de archivos sin números de inodo únicos, ya que puede dar lugar a que los archivos contengan contenido incorrecto en el CD.

Consulte la opción -duplicates-once para conocer un método que funciona en sistemas de archivos sin números de inodo únicos.

Si los inodos no se almacenan en caché, mkisofs volverá a la antigua versión Rrip 1.10 (ver -rrip110) y mkisofs no podrá crear números de inodo correctos para archivos de tamaño cero.

-no-cache-inodes
No almacene en caché los números de inodo y dispositivo. Esta opción es necesaria siempre que un sistema de archivos no tenga números de inodo únicos. Es la predeterminada en versiones antiguas de Cygwin. Dado que el sistema operativo de Microsoft que se ejecuta debajo de Cygwin utiliza números de inodo de 64 bits para NTFS, no tiene números de inodo únicos en el rango de 32 bits. Las versiones antiguas de Cygwin crean números de inodo falsos de 32 bits a partir de un algoritmo hash y, por lo tanto, crean números no únicos. Si mkisofs almacenara en caché inodos en versiones antiguas de Cygwin, creería que algunos archivos son idénticos aunque no lo sean. El resultado en este caso son archivos que contienen el contenido incorrecto si una cantidad significativa de archivos diferentes (> ~5000) se encuentra dentro del árbol que se va a archivar. Esto no sucede cuando se utiliza -no-cache-inodes, pero la desventaja es que mkisofs ya no puede detectar enlaces duros y la imagen del CD resultante puede ser más grande de lo esperado.

Si los inodos no se almacenan en caché, mkisofs volverá a la antigua versión Rrip 1.10 (ver -rrip110) y mkisofs no podrá crear números de inodo correctos para archivos de tamaño cero.

-duplicates-once
Indica a mkisofs que utilice una suma de verificación de resumen de mensajes para identificar archivos idénticos como archivos aparentemente enlazados de forma dura. Esto permite a mkisofs archivar números de inodo y enlaces duros incluso cuando se ejecuta en plataformas no POSIX como DOS.
-b imagen_arranque_eltorito
-eltorito-boot imagen_arranque_eltorito
Especifica la ruta y el nombre del archivo de imagen de arranque que se utilizará al crear un CD de arranque "El Torito". La ruta debe ser relativa a la ruta de origen y estar dentro del árbol de origen especificado para mkisofs. Esta opción es necesaria para crear un CD de arranque "El Torito". La imagen de arranque debe tener exactamente el tamaño de un disquete de 1200, 1440 o 2880 kB, y mkisofs utilizará este tamaño al crear el sistema de archivos ISO-9660 de salida. Se asume que el primer sector de 512 bytes se leerá de la imagen de arranque (básicamente, emula una unidad de disquete normal). Esto funcionará, por ejemplo, si la imagen de arranque es un disquete de arranque.

Si la imagen de arranque no es una imagen de un disquete, debe agregar una de las opciones: -hard-disk-boot o -no-emul-boot. Si el sistema no debe arrancar desde el disco emulado, use -no-boot.

Se pueden especificar varias entradas de arranque; consulte -eltorito-platform y -eltorito-alt-boot para ver cómo especificar más entradas de arranque. La primera entrada de arranque es la entrada de arranque predeterminada. Las entradas de arranque adicionales son miembros para una configuración de arranque múltiple.

Si no se ha especificado la opción -sort, las imágenes de arranque se ordenan con baja prioridad (+2) al principio del medio. Si no le gusta esto, debe especificar un peso de ordenación de 0 para las imágenes de arranque.

-eltorito-alt-boot
Comience con un nuevo conjunto de parámetros de arranque "El Torito". Esto permite tener más de una entrada de arranque El Torito en un CD. Se pueden incluir un máximo de 63 entradas de arranque El Torito en un solo CD.

La opción -eltorito-alt-boot inicia una nueva entrada de arranque con el mismo id de plataforma pero sin una nueva sección de arranque, excepto cuando aparece después de la primera entrada de arranque, que es la entrada de arranque predeterminada.

-eltorito-platform id
Establece el id de plataforma "El Torito" para un registro de arranque o una sección de registros de arranque. El parámetro id puede ser:
x86
Este es el valor predeterminado del id de plataforma y especifica entradas para la plataforma PC. Si no aparece ninguna opción -eltorito-platform antes de la primera opción -eltorito-boot, la entrada de arranque predeterminada se convierte en una entrada para la plataforma PC x86.
PPC
Entradas de arranque para la plataforma Power PC.
Mac
Entradas de arranque para la plataforma Apple Mac.

Entradas de arranque para PCs basadas en EFI.

Un valor numérico que especifica cualquier id de plataforma.

Si la opción -eltorito-platform aparece antes de la primera opción -eltorito-boot, establece el id de plataforma para la entrada de arranque predeterminada.

Si la opción -eltorito-platform aparece después de una opción -eltorito-boot y establece el id de plataforma a un valor diferente del valor anterior, inicia un nuevo conjunto de entradas de arranque.

La segunda entrada de arranque y cualquier nuevo id de plataforma crean un nuevo encabezado de sección y reducen el número de entradas de arranque por CD en uno.

errctl= nombre
errctl= especificación_control_errores
Agrega el contenido del archivo nombre a las definiciones de control de errores o agrega especificación_control_errores a las definiciones de control de errores. Es posible tener varios archivos de control de errores y varias especificación_control_errores, así como una mezcla de ambas formas.

La razón para usar el control de errores es hacer que mkisofs sea silencioso sobre las condiciones de error que se sabe que son irrelevantes para la calidad del sistema de archivos creado o para indicar a mkisofs que aborte en ciertas condiciones de error en lugar de intentar continuar con el sistema de archivos.

Una razón típica para usar el control de errores es suprimir advertencias sobre el crecimiento de los archivos de registro mientras se realiza una copia de seguridad en un sistema de archivos activo. Otra razón típica para usar el control de errores es indicar a mkisofs que aborte si, por ejemplo, no se puede archivar un archivo en lugar de continuar archivando otros archivos de una lista.

El archivo de control de errores contiene un conjunto de líneas, cada una comenzando con una lista de condiciones de error a ignorar seguida de un espacio en blanco seguido de un patrón de nombre de archivo (ver match(1) o patmatch(3) para más información). La especificación_control_errores utiliza la misma sintaxis que una sola línea del archivo de control de errores. Si el patrón del nombre del archivo necesita comenzar con un espacio en blanco, use una barra invertida para escapar el inicio del nombre del archivo. No es posible tener caracteres de nueva línea en el patrón del nombre del archivo. Siempre que se encuentra una situación de error, mkisofs verifica las líneas en el archivo de control de errores comenzando desde la parte superior. Si la condición de error actual está listada en una línea del archivo de control de errores, entonces mkisofs verifica si el patrón en el resto de la línea coincide con el nombre del archivo actual. Si este es el caso, mkisofs utiliza la especificación de control de errores actual para controlar la condición de error actual.

La lista de condiciones de error a manejar puede usar uno o más (en este caso separados por un carácter '|') identificadores de la lista a continuación:

ABORT
Si esta meta-condición se incluye en una condición de error, mkisofs abortará (saldrá) tan pronto como sea posible después de haber visto esta condición de error en lugar de hacer que mkisofs sea silencioso sobre la condición. Este indicador de condición de error solo se puede usar junto con otra condición de error o una lista de condiciones de error (separadas por un carácter '|').
WARN
Si esta meta-condición se incluye en una condición de error, mkisofs imprimirá la advertencia sobre la condición de error, pero la condición de error no afectará al código de salida de mkisofs y las estadísticas de error (que se imprimen al final) no incluirán los errores relacionados. Este indicador de condición de error solo se puede usar junto con otra condición de error o una lista de condiciones de error (separadas por un carácter '|'). El meta-indicador WARN tiene una precedencia menor que ABORT.
ALL
Este es un atajo para todas las condiciones de error a continuación.
STAT
Suprimir las advertencias de que mkisofs no pudo stat(2) un archivo.

-acl-compat
Activa la compatibilidad con ACL para los sistemas de archivos de Unix. Con esta opción activada, mkisofs intentará obtener y archivar la información ACL para cada archivo en el sistema de archivos de origen.

Esto puede tener dos efectos secundarios. Primero, la información ACL añadirá datos adicionales a cada archivo, lo que aumentará el tamaño total del sistema de archivos de CD. Segundo, la información ACL puede ser difícil de gestionar en un CD-ROM, ya que los atributos ACL se asocian con la información del sistema de archivos de origen.

Si mkisofs no puede obtener la información ACL de un archivo, imprimirá un mensaje de advertencia y continuará. El archivo se archivará sin información ACL. Si no desea ver estos mensajes, puede utilizar la opción de control de errores BADACL.

-B img_sun4,img_sun4c,img_sun4m,img_sun4d,img_sun4e
-sparc-boot img_sun4,img_sun4c,img_sun4m,img_sun4d,img_sun4e
Especifica una lista separada por comas de imágenes de arranque que son necesarias para crear un CD de arranque para sistemas sparc. El número máximo de particiones posibles es 8, por lo que es imposible especificar más de 7 imágenes de partición. Esta opción es necesaria para crear un CD de arranque para sistemas Sun sparc. Si se ha especificado la opción -B o -sparc-boot, el primer sector de la imagen resultante contendrá una etiqueta de disco Sun. Esta etiqueta de disco especifica la partición 0 para la imagen ISO-9660 y las particiones 1 ... 7 para las imágenes de arranque especificadas con esta opción. El resto de cada una de las imágenes suele contener un sistema de archivos ufs que se utiliza como etapa primaria de arranque del kernel.

El método de arranque implementado es el método de arranque que se encuentra con SunOS 4.x y SunOS 5.x. Sin embargo, no depende de los internos de SunOS, sino solo de las propiedades del prom de arranque abierto. Por esta razón, debería ser utilizable para cualquier SO que arranque desde un sistema sparc.

Para más información, véase también la sección NOTAS más abajo.

-C última_sesión_inicio,siguiente_sesión_inicio
-cdrecord-params última_sesión_inicio,siguiente_sesión_inicio
Esta opción es necesaria cuando se utiliza mkisofs para crear una imagen de CDextra o de una segunda sesión o una sesión de nivel superior para un disco multisesión. La opción -C toma un par de dos números separados por una coma. El primer número es el número de sector del primer sector de la última sesión del disco al que se debe adjuntar. El segundo número es el número de sector de inicio de la nueva sesión. El par de números esperado puede obtenerse llamando a cdrecord -msinfo ... Si la opción -C se utiliza junto con la opción -M, mkisofs creará una imagen de sistema de archivos destinada a ser una continuación de la sesión anterior. Si la opción -C se utiliza sin la opción -M, mkisofs creará una imagen de sistema de archivos destinada a ser utilizada para una segunda sesión en un CDextra. Esto es un CD multisesión que contiene datos de audio en la primera sesión y un sistema de archivos ISO-9660 en la segunda sesión.

La expresión de find actúa como un filtro entre la fuente de los nombres de archivo y el consumidor, que es el motor de archivado. Si la expresión de find se evalúa como VERDADERA, el archivo relacionado se selecciona para su procesamiento; de lo contrario, se omite.

Para que la evaluación de la expresión de find sea más conveniente, mkisofs implementa primitivas de find adicionales que tienen efectos secundarios en los metadatos del archivo. Mkisofs implementa las siguientes primitivas de find adicionales:

-help

-chgrp nombregrupo

-chmod modo
La primitiva siempre se evalúa como verdadera; establece los permisos del archivo a modo. Se aceptan permisos octales y simbólicos para modo, como con chmod(1).
-chown nombreusuario
La primitiva siempre se evalúa como verdadera; establece el propietario del archivo a nombreusuario.
-false
La primitiva siempre se evalúa como falsa; permite que el resultado de la expresión completa sea diferente del resultado de una parte de la expresión.
-true
La primitiva siempre se evalúa como verdadera; permite que el resultado de la expresión completa sea diferente del resultado de una parte de la expresión.

La línea de comandos:

mkisofs -o o.iso -find . ( -type d -ls -o false ) -o ! -type d

enumera todos los directorios y pone todos los no directorios en la imagen o.iso.

La línea de comandos:

mkisofs -o o.iso -find . ( -type d -chown root -o true )

archiva todos los directorios para que parezcan pertenecer a root en el archivo; todos los no directorios se archivan como están en el sistema de archivos.

Establece la fecha de modificación en el descriptor de volumen primario (PVD) a un valor diferente a la hora actual. Esto permite, por ejemplo, configurar un UUID intencional para grub.

El formato de espec-fecha es:

yyyy[mm[dd[hh[mm[ss]]]]][.hh][+-ghgm]

Los campos son año, mes, día del mes, hora, minuto, segundo, centésimas de segundo, desplazamiento GMT en horas y minutos. La hora se interpreta como hora local.

El año y el desplazamiento GMT son campos de cuatro dígitos, todos los demás campos toman dos dígitos. El desplazamiento GMT puede estar entre -12 y +13 horas en pasos de 15 minutos. Las ubicaciones al este de Greenwich tienen valores positivos. El valor es la suma del desplazamiento de la zona horaria y los efectos del horario de verano. Los valores omitidos se reemplazan por los valores mínimos posibles. Si se omite el desplazamiento GMT, se calcula a partir del valor de hora local que se ha proporcionado.

Entre el año y el mes, así como entre

mes y días mes, puede aparecer un separador elegido entre '/' y '-'. En este caso, el año puede ser un número de dos dígitos con valores 69..99 que representan 1969..1999 y valores 00..68 que representan 2000..2068. date "+%Y-%m-%d %H:%M:%S %z"

CONJUNTOS DE CARACTERES

mkisofs procesa los nombres de archivo de manera compatible con POSIX como cadenas de caracteres de 8 bits. Para representar todas las codificaciones para todos los idiomas, los caracteres de 8 bits no son suficientes. Unicode o ISO-10646 definen codificaciones de caracteres que necesitan al menos 21 bits para representar todos los idiomas conocidos. Pueden representarse con codificación UTF-32, UTF-16 o UTF-8. UTF-32 utiliza una codificación simple de 32 bits, pero parece ser poco común. UCS-2 es utilizado por Microsoft con Win32. Esta codificación es similar a UTF-16 con la desventaja de que solo admite un subconjunto de 16 bits (excepto cuando se utilizan sustitutos) de todos los códigos y que los caracteres de 16 bits no son compatibles con la interfaz de nombres de archivo POSIX.

Los sistemas operativos UNIX modernos pueden utilizar la codificación UTF-8 para los nombres de archivo. Esta codificación permite utilizar el conjunto completo de códigos Unicode. Cada carácter de 32 bits se representa mediante uno o más caracteres de 8 bits. Si un carácter está codificado en ISO-8859-1 (utilizado en Europa Central y América del Norte), se mapea 1:1 a un carácter Unicode codificado en UTF-32 o UTF-16. Si un carácter está codificado en ASCII de 7 bits (utilizado en EE. UU. y otros países con un conjunto de caracteres limitado), se mapea 1:1 a un carácter Unicode codificado en UTF-32, UTF-16 o UTF-8. Los códigos de caracteres que no se pueden representar como un solo byte en UTF-8 (típicamente si el valor es > 0x7F) utilizan secuencias de escape que se mapean a más de un carácter de 8 bits.

Si todos los sistemas operativos utilizaran la codificación UTF-8, mkisofs no necesitaría recodificar los caracteres en los nombres de archivo. Desafortunadamente, Apple utiliza codificaciones completamente no estándar y Microsoft utiliza una codificación Unicode que no es compatible con la interfaz de nombres de archivo POSIX.

Para todos los sistemas operativos que no utilizan codificación UTF-8, el carácter real que representa cada byte depende del *conjunto de caracteres* o *página de códigos* (que es el nombre utilizado por Microsoft) del sistema operativo local en uso: los caracteres de un conjunto de caracteres reflejarán la región o el idioma natural utilizado por el usuario.

Normalmente, los códigos de caracteres 0x00-0x1f son caracteres de control, los códigos 0x20-0x7f son los caracteres ASCII de 7 bits y (en PC y Mac) 0x80-0xff se utilizan para otros caracteres. Desafortunadamente, ni siquiera esto sigue los estándares ISO, que reservan el rango 0x80-0x9f para caracteres de control y solo permiten 0xa0-0xff para otros caracteres.

Dado que hay muchos más de 256 caracteres/símbolos en uso, solo un pequeño subconjunto se representa en un conjunto de caracteres. Por lo tanto, el mismo código de carácter puede representar un carácter diferente en diferentes conjuntos de caracteres. Así, un nombre de archivo generado, digamos en Europa Central, puede no mostrar el mismo carácter cuando se ve en una máquina en, digamos, Europa del Este.

Para complicar las cosas, diferentes sistemas operativos utilizan diferentes conjuntos de caracteres para la región o el idioma. Por ejemplo, el código de carácter para "e pequeña con acento agudo" puede ser el código de carácter 0x82 en una PC, el código 0x8e en un Macintosh y el código 0xe9 en un sistema UNIX. Tenga en cuenta que, aunque las codificaciones utilizadas en una PC o Mac no son estándar, Unicode codifica este carácter como 0x00000000e9, que es básicamente el mismo valor que el valor utilizado por la mayoría de los sistemas UNIX.

Mientras no todos los sistemas operativos y aplicaciones utilicen el conjunto de caracteres Unicode como base para los nombres de archivo de manera única, puede ser necesario especificar qué conjunto de caracteres utilizan sus nombres de archivo y en qué conjunto de caracteres deben aparecer los nombres de archivo en el CD.

Hay cuatro opciones para especificar los conjuntos de caracteres que desea utilizar:

-input-charset
Define el conjunto de caracteres local que está utilizando en su máquina host. CREADOR/TIPO HFS

Un archivo de Macintosh tiene dos propiedades asociadas que definen qué aplicación creó el archivo, el CREADOR y qué datos contiene el archivo, el TIPO. Ambos son cadenas de exactamente 4 letras. Generalmente, esto permite a un usuario de Macintosh hacer doble clic en un archivo y lanzar la aplicación correcta, etc. El CREADOR y TIPO de un archivo particular se pueden encontrar usando algo como ResEdit (o similar) en un Macintosh.

La información de CREADOR y TIPO se almacena en todos los diversos archivos codificados en Apple/Unix. Para otros archivos, es posible basar el CREADOR y el TIPO en la extensión del nombre de archivo usando un archivo de mapeo (la opción -map) y/o usando el número mágico (generalmente una firma en los primeros bytes) de un archivo (la opción -magic). Si se dan ambas opciones, entonces su orden en la línea de comandos es importante. Si la opción -map se da primero, entonces se intenta una coincidencia de extensión de nombre de archivo antes de una coincidencia de número mágico. Sin embargo, si la opción -magic se da primero, entonces se intenta una coincidencia de número mágico antes de una coincidencia de extensión de nombre de archivo.

Si no se utiliza un archivo de mapeo o mágico, o no se encuentra ninguna coincidencia, el CREADOR y TIPO predeterminados para todos los archivos regulares se pueden establecer utilizando entradas en el archivo .mkisofsrc o utilizando las opciones -hfs-creator y/o -hfs-type; de lo contrario, el CREADOR y TIPO predeterminados son 'unix' y 'TEXT'.

El formato del archivo de mapeo es el mismo formato afpfile que utiliza aufs. Este archivo tiene cinco columnas para la extensión, la traducción del archivo, el CREADOR, el TIPO y el Comentario. Las líneas que comienzan con el carácter '#' son líneas de comentarios y se ignoran. Un archivo de ejemplo sería así:

# Ejemplo de archivo de mapeo de nombres de archivo
#
# EXT Xlate CREATOR TYPE Comentario
.tif Raw '8BIM' 'TIFF' "Imagen TIFF de Photoshop"
.hqx Ascii 'BnHq' 'TEXT' "Archivo BinHex"
.doc Raw 'MSWD' 'WDBN' "Archivo de Word"
.mov Raw 'TVOD' 'MooV' "Película QuickTime"
* Ascii 'ttxt' 'TEXT' "Archivo de texto"

Donde:

La primera columna EXT define la extensión del nombre de archivo de Unix a mapear. La correspondencia predeterminada para cualquier extensión de nombre de archivo que no coincida se define con el carácter '"*"'.
La columna Xlate define el tipo de traducción de texto entre Unix y Macintosh; mkisofs la ignora, pero se mantiene para ser compatible con aufs(1). Aunque mkisofs no modifica el contenido de un archivo, si un archivo binario tiene su TIPO establecido como 'TEXT', puede ser leído incorrectamente en un Macintosh. Por lo tanto, una mejor opción para el TIPO predeterminado puede ser '????'
Las palabras clave CREATOR y TYPE deben tener 4 caracteres de longitud y estar entre comillas simples.
El campo de comentario está entre comillas dobles; mkisofs lo ignora, pero se mantiene para ser compatible con aufs.

El formato del archivo magic es casi idéntico al archivo magic(4) utilizado por el comando file(1) de Linux; las rutinas para leer y decodificar el archivo magic se basan en el comando file(1) de Linux.

Este archivo tiene cuatro columnas separadas por tabulaciones para el desplazamiento de bytes, el tipo, la prueba y el mensaje. Las líneas que comienzan con el carácter '#' son líneas de comentarios y se ignoran. Un archivo de ejemplo sería así:

# Ejemplo de archivo mágico
#
# off tipo prueba mensaje
0 string GIF8 8BIM GIFf Imagen GIF
0 beshort 0xffd8 8BIM Datos de imagen JPEG
0 string SIT! SIT! SIT! Archivo StuffIt
0 string \037\235 Compresión estándar de Unix LZIV ZIVU
0 string \037\213 Datos comprimidos gzip GNuz ZIVU
0 string %! ASPS TEXT Postscript
0 string \004%! ASPS TEXT Postscript PC con un ^D para empezar
4 string moov txtt MooV Archivo de película QuickTime (moov)
4 string mdat txtt MooV Archivo de película QuickTime (mdat)

El formato del archivo se describe en la página del manual magic(4). La única diferencia aquí es que para cada entrada en el archivo mágico, el mensaje para el desplazamiento inicial debe ser de 4 caracteres para el CREADOR seguido de 4 caracteres para el TIPO; el espacio en blanco es opcional entre ellos. Cualquier otro carácter en esta línea se ignora. Las líneas de continuación (comenzando con un '>') también se ignoran, es decir, solo se utilizan las líneas de desplazamiento inicial.

Usar la opción -magic puede aumentar significativamente el tiempo de procesamiento ya que cada archivo debe ser abierto y leído para encontrar su número mágico.

En resumen, para todos los archivos, el CREADOR predeterminado es 'unix' y el TIPO predeterminado es 'TEXT'. Estos pueden cambiarse usando entradas en el archivo .mkisofsrc o usando las opciones -hfs-creator y/o -hfs-type.

Si un archivo está en uno de los formatos Apple/Unix conocidos (y el formato ha sido seleccionado), entonces el CREADOR y TIPO se toman de los valores almacenados en el archivo Apple/Unix.

Otros archivos pueden tener su CREADOR y TIPO establecidos a partir de su extensión de nombre de archivo (la opción -map), o su número mágico (la opción -magic). Si se usa la coincidencia predeterminada en el archivo de mapeo, entonces estos valores anulan el CREADOR y TIPO predeterminados.

Una base de datos completa de CREADOR/TIPO se puede encontrar en http://www.angelfire.com/il/szekely/index.html

FORMATOS DE ARCHIVO MACINTOSH HFS

Los archivos de Macintosh tienen dos partes llamadas el fork de Datos y el de Recursos. Cualquiera de ellos puede estar vacío. Unix (y muchos otros sistemas operativos) solo pueden manejar archivos con una parte (o fork). Para añadir a esto, los archivos de Macintosh tienen una serie de atributos asociados a ellos; probablemente los más importantes son el TIPO y el CREADOR. De nuevo, Unix no tiene concepto de este tipo de atributos.

Por ejemplo, un archivo de Macintosh puede ser una imagen JPEG donde la imagen se almacena en el fork de Datos y una miniatura de escritorio se almacena en el fork de Recursos. Generalmente es la información en el fork de datos la que es útil entre plataformas.

Por lo tanto, para almacenar un archivo de Macintosh en un sistema de archivos Unix, se debe encontrar una manera de manejar los dos forks y los atributos adicionales (que se denominan información del Finder). Desafortunadamente, parece que cada paquete de software que almacena archivos de Macintosh en Unix ha elegido un método de almacenamiento completamente diferente.

However, the Apple extensions do give the advantage that the files are packed on the disk more efficiently and it may be possible to fit more files on a CD - important when the total size of the source files is approaching 650MB.

HFS MACINTOSH FILE NAMES

Where possible, the HFS filename that is stored with an Apple/Unix file is used for the HFS part of the CD. However, not all the Apple/Unix encodings store the HFS filename with the finderinfo. In these cases, the Unix filename is used - with escaped special characters. Special characters include '/' and characters with codes over 127.

Aufs escapes these characters by using ":" followed by the character code as two hex digits. Netatalk and EtherShare have a similar scheme, but uses "%" instead of a ":".

If mkisofs can't find an HFS filename, then it uses the Unix name, with any %xx or :xx characters (xx == two hex digits) converted to a single character code. If "xx" are not hex digits ([0-9a-fA-F]), then they are left alone - although any remaining ":" is converted to "%" as colon is the HFS directory separator. Care must be taken, as an ordinary Unix file with %xx or :xx will also be converted. e.g.

This:2fFile converted to This/File
This:File converted to This%File
This:t7File converted to This%t7File

Although HFS filenames appear to support upper and lower case letters, the filesystem is case insensitive. i.e. the filenames "aBc" and "AbC" are the same. If a file is found in a directory with the same HFS name, then mkisofs will attempt, where possible, to make a unique name by adding '_' characters to one of the filenames.

If an HFS filename exists for a file, then mkisofs can use this name as the starting point for the ISO-9660, Joliet and Rock Ridge filenames using the -mac-name option. Normal Unix files without an HFS name will still use their Unix name. e.g.

However, as mkisofs uses the Unix name as the starting point for the other names, then the ISO-9660 name generated will probably be SOMEIMAG.BIN and the Joliet/Rock Ridge would be someimage.gif.bin. Using the -mac-name option will not currently work with the -T option - the Unix name will be used in the TRANS.TBL file, not the Macintosh name.

The character set used to convert any HFS file name to a Joliet/Rock Ridge file name defaults to cp10000 (Mac Roman). The character set used can be specified using the -input-hfs-charset option. Other built in HFS character sets are: cp10006 (MacGreek), cp10007 (MacCyrillic), cp10029 (MacLatin2), cp10079 (MacIcelandic) and cp10081 (MacTurkish).

Note: the character codes used by HFS file names taken from the various Apple/Unix formats will not be converted as they are assumed to be in the correct Apple character set. Only the Joliet/Rock Ridge names derived from the HFS file names will be converted.

The existing mkisofs code will filter out any illegal characters for the ISO-9660 and Joliet filenames, but as mkisofs expects to be dealing directly with Unix names, it leaves the Rock Ridge names as is. EJEMPLOS

Crear una imagen de CD de 300 MB de los archivos en el directorio actual (que se llama .):

% mkisofs -o cd.iso -size-limit 300m .

Crear una imagen de CD con una estructura híbrida de HFS y ISO-9660 (es decir, una imagen de CD que se puede leer en sistemas Unix y Macintosh) de los archivos en el directorio actual.

% mkisofs -o cd.iso -hfs -r .

Crear una imagen de CD con una estructura híbrida de HFS, ISO-9660 y Joliet (es decir, una imagen de CD que se puede leer en sistemas Unix, Macintosh y Windows)

% mkisofs -o cd.iso -hfs -joliet -r .

Crear una imagen de CD híbrida con mkisofs(8) que contiene los archivos del directorio actual y que tiene los directorios del sistema de archivos HFS ocultos para el acceso directo a ISO-9660:

% mkisofs -o cd.iso -hfs -hide-hfs mac_hidden_dir -hide-joliet win_hidden_dir .

Crear una imagen de CD híbrida con mkisofs(8) que contiene los archivos del directorio actual y que tiene los directorios del sistema de archivos ISO-9660 ocultos para el acceso directo a HFS.

% mkisofs -o cd.iso -hfs -hide-iso README.unix cd_dir

es decir, el archivo README.hfs será visto como README en el CD HFS y los otros dos archivos README serán ocultos. De manera similar para el CD Joliet e ISO-9660/RockRidge.

Probablemente es posible obtener todo tipo de resultados extraños con combinaciones de las opciones hide...

Para crear un DVD-Audio a partir del directorio fuente que cumple con DVD-Audio DVD:

% mkisofs -o dvda.iso -dvd-audio DVD

NOTAS

Mkisofs puede ser instalado de forma segura como suid root. Esto puede ser necesario para permitir que mkisofs lea la sesión anterior al crear una imagen de múltiples sesiones.

mkisofs no se basa en las herramientas mk*fs estándar para unix, ya que debemos generar una copia completa de un sistema de archivos existente en un disco en el sistema de archivos ISO-9660. El nombre mkisofs es probablemente un poco un nombre inapropiado, ya que no solo crea el sistema de archivos, sino que también lo puebla. Sin embargo, el nombre apropiado de la herramienta para una herramienta de UNIX que crea sistemas de archivos poblados - mkproto - no es muy conocido.

Si mkisofs está creando una imagen de sistema de archivos con atributos Rock Ridge y el nivel de anidamiento de directorios del árbol de directorios fuente es demasiado grande para ISO-9660, mkisofs realizará una reubicación de directorios profundos. Esto da como resultado un directorio llamado RR_MOVED en el directorio raíz del CD. No puede evitar este directorio en el árbol de directorios que es visible con ISO-9660, pero se oculta automáticamente en el árbol de Rock Ridge.

El soporte de arranque sparc que se implementa con las opciones -sparc-boot sigue completamente los requisitos oficiales de arranque de CD Sparc del prom de arranque en sistemas Sun Sparc. Algunas distribuciones de Linux para sistemas Sparc utilizan un cargador de arranque llamado SILO que desafortunadamente no cumple con el estándar de arranque de CD Sparc. Es molesto ver que los autores de SILO no arreglan SILO sino que proporcionan un "parche" completamente innecesario a mkisofs que incorpora mucho más código fuente del que necesitaría la corrección para SILO.

ERRORES

•
No lee correctamente los directorios reubicados en modo multisesión al agregar datos.

Cualquier directorio profundo reubicado se pierde si la nueva sesión no incluye el directorio profundo.

Repetir mediante: crear la primera sesión con reubicación de directorios profundos y luego agregar una nueva sesión con un solo directorio que difiere de la antigua ruta profunda.

•
No reutiliza RR_MOVED al hacer multisesión desde TRANS.TBL

Puede haber otros. Por favor, repórtelos al autor.

PROBLEMAS/LIMITACIONES HFS

He tenido que hacer varias suposiciones sobre cómo espero que funcionen las rutinas libhfs modificadas, sin embargo, puede haber situaciones que o bien no he considerado, o que surgen cuando estas suposiciones fallan. Por lo tanto, no puedo garantizar que mkisofs funcione como se espera (aunque todavía no he tenido un problema importante). La mayoría de las funciones HFS funcionan bien, sin embargo, algunas no han sido probadas completamente. Estas están marcadas como Alpha arriba.

Aunque los nombres de archivo HFS parecen admitir letras mayúsculas y minúsculas, el sistema de archivos no distingue entre mayúsculas y minúsculas. Es decir, los nombres de archivo "aBc" y "AbC" son los mismos. Si se encuentra un archivo en un directorio con el mismo nombre HFS, entonces mkisofs intentará, siempre que sea posible, crear un nombre único agregando caracteres '_' a uno de los nombres de archivo.

Los nombres de archivo/directorio HFS que comparten los primeros 31 caracteres tienen _N' (N == número decimal) sustituido por los últimos caracteres para generar nombres únicos.

Se debe tener cuidado al "injertar" archivos o directorios Apple/Unix (ver arriba para el método y la sintaxis involucrada). No es posible usar un nombre nuevo para un archivo/directorio codificado en Apple/Unix. Por ejemplo, si un archivo codificado en Apple/Unix llamado "nombreantiguo" se va a agregar al CD, entonces no puede usar la línea de comandos:

mkisofs -o output.raw -hfs -graft-points nombrenuevo=nombreantiguo cd_dir

mkisofs no podrá decodificar "nombreantiguo". Sin embargo, puede injertar archivos o directorios codificados en Apple/Unix siempre que no intente darles nombres nuevos como los anteriores.

Al crear un volumen HFS con las opciones de multisesión, -M y -C, solo los archivos de la última sesión estarán en el volumen HFS. Es decir, mkisofs no puede agregar archivos existentes de sesiones anteriores al volumen HFS.

Sin embargo, si cada sesión se crea con la opción -part, entonces cada sesión aparecerá como volúmenes separados cuando se monte en una Mac. En este caso, vale la pena usar la opción -V o -hfs-volid para dar a cada sesión un nombre de volumen único, de lo contrario, cada "volumen" aparecerá en el escritorio con el mismo nombre.

Los enlaces simbólicos (al igual que todos los demás archivos no regulares) no se agregan al directorio HFS.

Los volúmenes híbridos pueden ser más grandes que los volúmenes ISO-9660 puros que contienen los mismos datos. En algunos casos (por ejemplo, volúmenes de tamaño DVD), el volumen híbrido puede ser significativamente más grande. A medida que un volumen HFS se hace más grande, también lo hace el tamaño del bloque de asignación (la cantidad más pequeña de espacio que puede ocupar un archivo). Para un CD de 650 MB, el bloque de asignación es de 10 KB, para un DVD de 4.7 GB será de aproximadamente 70 KB.

El número máximo de archivos en un volumen HFS es de aproximadamente 65500, aunque el límite real será algo menor.

El volumen híbrido resultante se puede acceder en una máquina Unix utilizando las rutinas de hfsutils. Sin embargo, no se pueden realizar cambios en el volumen, ya que está configurado como bloqueado. La opción -hfs-unlock creará una imagen de salida que no está bloqueada, sin embargo, no se deben realizar cambios en el contenido del volumen (a menos que realmente sepa lo que está haciendo), ya que no es un volumen HFS "real".

Usar la opción -mac-name actualmente no funcionará con la opción -T; el nombre Unix se usará en el archivo TRANS.TBL, no el nombre de Macintosh.

Aunque mkisofs no altera el contenido de un archivo, si un archivo binario tiene su TYPE configurado como 'TEXT', puede ser leído incorrectamente en una Macintosh. Por lo tanto, una mejor opción para el TYPE predeterminado puede ser '????'

La opción -mac-boot-file puede no funcionar en absoluto...

Puede no funcionar con archivos PC Exchange v2.2 o superior (disponibles con MacOS 8.1). Los medios DOS que contienen archivos PC Exchange deben montarse como tipo msdos (no vfat) al usar Linux.

El formato SFM solo se admite parcialmente; consulte la sección FORMATOS DE ARCHIVO HFS MACINTOSH anterior.

No es posible usar las opciones -sparc-boot o -generic-boot con las opciones -boot-hfs-file, -prep-boot o -chrp-boot.

mkisofs debería poder crear imágenes híbridas HFS de más de 4 GB, aunque esto no ha sido probado completamente.
