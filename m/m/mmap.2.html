mmap(2) Manual de Llamadas al Sistema mmap(2)

NOMBRE

mmap, munmap - mapear o desmapear archivos o dispositivos en memoria

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

SINOPSIS

#include <sys/mman.h>
void *mmap(size_t length;
           void addr[length], size_t length, int prot, int flags,
           int fd, off_t offset);
int munmap(size_t length;
           void addr[length], size_t length);

Ver VERSIONS para información sobre los requisitos de las macros de prueba de características.

DESCRIPCION

mmap() crea un nuevo mapeo en el espacio de direcciones virtuales del proceso llamante. La dirección de inicio para el nuevo mapeo se especifica en addr. El argumento length especifica la longitud del mapeo (que debe ser mayor que 0).

Si addr es NULL, el kernel elige la dirección (alineada a página) donde crear el mapeo; este es el método más portable para crear un nuevo mapeo. Si addr no es NULL, el kernel lo toma como una pista de dónde colocar el mapeo; en Linux, el kernel elegirá un límite de página cercano (pero siempre mayor o igual al valor especificado por /proc/sys/vm/mmap_min_addr) e intentará crear el mapeo allí. Si ya existe otro mapeo, el kernel elige una nueva dirección que puede o no depender de la pista. La dirección del nuevo mapeo se devuelve como resultado de la llamada.

El contenido de un mapeo de archivo (a diferencia de un mapeo anónimo; ver MAP_ANONYMOUS más adelante), se inicializa usando length bytes comenzando en el desplazamiento offset en el archivo (u otro objeto) al que se refiere el descriptor de archivo fd. offset debe ser un múltiplo del tamaño de página devuelto por sysconf(_SC_PAGE_SIZE).

Después de que la llamada mmap() haya retornado, el descriptor de archivo, fd, puede cerrarse inmediatamente sin invalidar el mapeo.

El argumento prot describe la protección de memoria deseada del mapeo (y no debe entrar en conflicto con el modo de apertura del archivo). Es PROT_NONE o el OR a nivel de bits de uno o más de las siguientes banderas:

PROT_EXEC
Las páginas pueden ser ejecutadas.
PROT_READ
Las páginas pueden ser leídas.
PROT_WRITE
Las páginas pueden ser escritas.
PROT_NONE
Las páginas no pueden ser accedidas.

El argumento flags

El argumento flags determina si las actualizaciones al mapeo son visibles para otros procesos que mapean la misma región, y si las actualizaciones se propagan al archivo subyacente. Este comportamiento se determina incluyendo exactamente uno de los siguientes valores en flags:

MAP_SHARED
Compartir este mapeo. Las actualizaciones al mapeo son visibles para otros procesos que mapean la misma región y (en el caso de mapeos con respaldo de archivo) se propagan al archivo subyacente. (Para controlar precisamente cuándo las actualizaciones se propagan al archivo subyacente se requiere el uso de msync(2).)
MAP_SHARED_VALIDATE (desde Linux 4.15)
Esta bandera proporciona el mismo comportamiento que MAP_SHARED, excepto que los mapeos MAP_SHARED ignoran las banderas desconocidas en flags. Por el contrario, al crear un mapeo usando MAP_SHARED_VALIDATE, el kernel verifica que todas las banderas pasadas sean conocidas y falla el mapeo con el error EOPNOTSUPP para banderas desconocidas. Este tipo de mapeo también se requiere para poder utilizar algunas banderas de mapeo (por ejemplo, MAP_SYNC).
MAP_PRIVATE
Crear un mapeo privado de copia en escritura. Las actualizaciones al mapeo no son visibles para otros procesos que mapean el mismo archivo, y no se propagan al archivo subyacente. No está especificado si los cambios hechos al archivo después de la llamada mmap() son visibles en la región mapeada.

Tanto MAP_SHARED como MAP_PRIVATE se describen en POSIX.1-2001 y POSIX.1-2008. MAP_SHARED_VALIDATE es una extensión de Linux.

Además, cero o más de los siguientes valores pueden ser OR-eados en flags:

MAP_32BIT (desde Linux 2.4.20, 2.6)
Colocar el mapeo en los primeros 2 Gigabytes del espacio de direcciones del proceso. Esta bandera solo es compatible con x86-64, para programas de 64 bits. Fue agregada para permitir que las pilas de hilos se asignen en algún lugar dentro de los primeros 2 GB de memoria, para mejorar el rendimiento del cambio de contexto en algunos procesadores de 64 bits tempranos. Los procesadores x86-64 modernos ya no tienen este problema de rendimiento, por lo que el uso de esta bandera no es necesario en esos sistemas. La bandera MAP_32BIT se ignora cuando se establece MAP_FIXED.
MAP_ANON
Sinónimo de MAP_ANONYMOUS; proporcionado para compatibilidad con otras implementaciones.
MAP_ANONYMOUS
El mapeo no está respaldado por ningún archivo; sus contenidos se inicializan a cero. El argumento fd se ignora; sin embargo, algunas implementaciones requieren que fd sea -1 si se especifica MAP_ANONYMOUS (o MAP_ANON), y las aplicaciones portables deben asegurarse de esto. El argumento offset debe ser cero. El soporte para MAP_ANONYMOUS en conjunción con MAP_SHARED se agregó en Linux 2.4.
MAP_DENYWRITE
Esta bandera se ignora. (Hace mucho tiempo —Linux 2.0 y anteriores— indicaba que los intentos de escribir en el archivo subyacente debían fallar con ETXTBSY. Pero esto era una fuente de ataques de denegación de servicio.)
MAP_EXECUTABLE
Esta bandera se ignora.
MAP_FILE
Bandera de compatibilidad. Ignorada.
MAP_FIXED
No interpretes addr como una pista: coloca el mapeo exactamente en esa dirección. addr debe estar debidamente alineado: para la mayoría de las arquitecturas, un múltiplo del tamaño de página es suficiente; sin embargo, algunas arquitecturas pueden imponer restricciones adicionales. Si la región de memoria especificada por addr y length se cruza con páginas de cualquier mapeo existente, la parte superpuesta de los mapeos existentes se descartará. Si la dirección especificada no se puede usar, mmap() fallará.
El software que aspira a ser portable debe usar la bandera MAP_FIXED con cuidado, teniendo en cuenta que la disposición exacta de los mapeos de memoria de un proceso puede cambiar significativamente entre versiones de Linux, versiones de la biblioteca C y lanzamientos del sistema operativo. ¡Lea atentamente la discusión de esta bandera en NOTAS!
MAP_FIXED_NOREPLACE (desde Linux 4.17)
Esta bandera proporciona un comportamiento similar a MAP_FIXED con respecto a la aplicación de addr, pero difiere en que MAP_FIXED_NOREPLACE nunca sobrescribe un rango mapeado preexistente. Si el rango solicitado colisiona con un mapeo existente, esta llamada falla con el error EEXIST. Por lo tanto, esta bandera se puede usar como una forma de intentar mapear un rango de direcciones atómicamente (con respecto a otros hilos): un hilo tendrá éxito; todos los demás informarán un fallo.

ERRORS

The mmap() function may fail for any of the reasons listed in mmap(2).

EINVAL
The specified values of length and offset are not valid.
ENOMEM
Not enough memory available.
EOVERFLOW
The number of pages used for length plus number of pages used for offset would overflow unsigned long (32 bits).
EPERM
The prot argument asks for PROT_EXEC but the mapped area belongs to a file on a filesystem that was mounted no-exec.
EPERM
The operation was prevented by a file seal; see fcntl(2).
EPERM
The MAP_HUGETLB flag was specified, but the caller was not privileged (did not have the CAP_IPC_LOCK capability) and is not a member of the hugetlb_shm_group group; see the description of /proc/sys/vm/hugetlb_shm_group in proc_sys_vm(5).
ETXTBSY
MAP_DENYWRITE was set but the object specified by fd is open for writing.

Use of a mapped region can result in these signals:

SIGSEGV
Attempted write into a region mapped as read-only.
SIGBUS
Attempted access to a page of the buffer that lies beyond the end of the mapped file. For an explanation of the treatment of the bytes in the page that corresponds to the end of a mapped file that is not a multiple of the page size, see NOTES.

VERSIONS

On some hardware architectures (e.g., i386), PROT_WRITE implies PROT_READ. It is architecture dependent whether PROT_READ implies PROT_EXEC or not. Portable programs should always set PROT_EXEC if they intend to execute code in the new mapping.

The portable way to create a mapping is to specify addr as 0 (NULL), and omit MAP_FIXED from flags. In this case, the system chooses the address for the mapping; the address is chosen so as not to conflict with any existing mapping, and will not be 0. If the MAP_FIXED flag is specified, and addr is 0 (NULL), then the mapped address will be 0 (NULL).

Certain flags constants are defined only if suitable feature test macros are defined (possibly by default): _DEFAULT_SOURCE with glibc 2.19 or later; or _BSD_SOURCE or _SVID_SOURCE in glibc 2.19 and earlier. (Employing _GNU_SOURCE also suffices, and requiring that macro specifically would have been more logical, since these flags are all Linux-specific.) The relevant flags are: MAP_32BIT, MAP_ANONYMOUS (and the synonym MAP_ANON), MAP_DENYWRITE, MAP_EXECUTABLE, MAP_FILE, MAP_GROWSDOWN, MAP_HUGETLB, MAP_LOCKED, MAP_NONBLOCK, MAP_NORESERVE, MAP_POPULATE, and MAP_STACK.

C library/kernel differences

This page describes the interface provided by the glibc mmap() wrapper function. Originally, this function invoked a system call of the same name. Since Linux 2.4, that system call has been superseded by mmap2(2), and nowadays the glibc mmap() wrapper function invokes mmap2(2) with a suitably adjusted value for offset.

NOTES

Memory mapped by mmap() is preserved across fork(2), with the same attributes.

A file is mapped in multiples of the page size. For a file that is not a multiple of the page size, the remaining bytes in the partial page at the end of the mapping are zeroed when mapped, and modifications to that region are not written out to the file. The effect of changing the size of the underlying file of a mapping on the pages that correspond to added or removed regions of the file is unspecified.

An application can determine which pages of a mapping are currently resident in the buffer/page cache using mincore(2).

Using MAP_FIXED safely

The only safe use for MAP_FIXED is where the address range specified by addr and length was previously reserved using another mapping; otherwise, the use of MAP_FIXED is hazardous because it forcibly removes preexisting mappings, making it easy for a multithreaded process to corrupt its own address space.

For example, suppose that thread A looks through /proc/pid/maps in order to locate an unused address range that it can map using MAP_FIXED, while thread B simultaneously acquires part or all of that same address range. When thread A subsequently employs mmap(MAP_FIXED), it will effectively clobber the mapping that thread B created. In this scenario, thread B need not create a mapping directly; simply making a library call that, internally, uses dlopen(3) to load some other shared library, will suffice. The dlopen(3) call will map the library into the process's address space. Furthermore, almost any library call may be implemented in a way that adds memory mappings to the address space, either with this technique, or by simply allocating memory. Examples include brk(2), malloc(3), pthread_create(3), and the PAM libraries http://www.linux-pam.org.

Since Linux 4.17, a multithreaded program can use the MAP_FIXED_NOREPLACE flag to avoid the hazard described above when attempting to create a mapping at a fixed address that has not been reserved by a preexisting mapping.

Timestamps changes for file-backed mappings

For file-backed mappings, the st_atime field for the mapped file may be updated at any time between the mmap() and the corresponding unmapping; the first reference to a mapped page will update the field if it has not been already.

The st_ctime and st_mtime field for a file mapped with PROT_WRITE and MAP_SHARED will be updated after a write to the mapped region, and before a subsequent msync(2) with the MS_SYNC or MS_ASYNC flag, if one occurs.

Huge page (Huge TLB) mappings

For mappings that employ huge pages, the requirements for the arguments of mmap() and munmap() differ somewhat from the requirements for mappings that use the native system page size.

For mmap(), offset must be a multiple of the underlying huge page size. The system automatically aligns length to be a multiple of the underlying huge page size.

For munmap(), addr, and length must both be a multiple of the underlying huge page size.

CAVEATS

Unlike typical malloc(3) implementations, mmap() does not prevent creating objects larger than PTRDIFF_MAX. Objects that are larger than PTRDIFF_MAX only work in limited ways in C (in particular, pointer subtraction results in undefined behavior if the result would be bigger than PTRDIFF_MAX). On top of that, GCC also assumes that no object is bigger than PTRDIFF_MAX. PTRDIFF_MAX is usually half of the address space size; so for 32-bit processes, it is usually 0x7fffffff (almost 2 GiB).

BUGS

On Linux, there are no guarantees like those suggested above under MAP_NORESERVE. By default, any process can be killed at any moment when the system runs out of memory.

Before Linux 2.6.7, the MAP_POPULATE flag has effect only if prot is specified as PROT_NONE.

SUSv3 specifies that mmap() should fail if length is 0. However, before Linux 2.6.12, mmap() succeeded in this case: no mapping was created and the call returned addr. Since Linux 2.6.12, mmap() fails with the error EINVAL for this case.

POSIX specifies that the system shall always zero fill any partial page at the end of the object and that system will never write any modification of the object beyond its end. On Linux, when you write data to such partial page after the end of the object, the data stays in the page cache even after the file is closed and unmapped and even though the data is never written to the file itself, subsequent mappings may see the modified content. In some cases, this could be fixed by calling msync(2) before the unmap takes place; however, this doesn't work on tmpfs(5) (for example, when using the POSIX shared memory interface documented in shm_overview(7)).

The following program prints part of the file specified in its first command-line argument to standard output. The range of bytes to be printed is specified via offset and length

mmap(2) — Arch Linux

NAME

mmap — map files or devices into memory

LIBRARY

Standard C library (libc, -lc)

SYNOPSIS

#include <sys/mman.h>
void *mmap(void *addr, size_t length, int prot, int flags,
            int fd, off_t offset);
int munmap(void *addr, size_t length);

DESCRIPTION

The mmap() function establishes a new mapping with other processes specified by fd into the virtual address space of the calling process. The file specified by fd must be open and accessible. An offset into the file is specified by offset. The length argument specifies the length of the mapping (which can be greater than or equal to zero). The value of offset must be a multiple of the system page size.

The addr argument specifies a preferred starting address for the new mapping. If addr is NULL, then the kernel chooses the address at which to create the mapping. The kernel places the mapping at an address that is suitable for the mapping.

The prot argument is a bitmask that describes the memory protection. It must be non-negative, and must be the bitwise OR of zero or more of the following symbolic constants:

PROT_READ
Pages may be read.
PROT_WRITE
Pages may be written.
PROT_EXEC
Pages may be executed.
PROT_NONE
Pages may not be accessed.

The flags argument determines the nature of the mapping. It must be a bitwise OR of zero or more of the following symbolic constants:

MAP_SHARED
Update visible to all processes mapping the same region when writing to the memory region. This mapping does not allow memory to be shared between processes running on different machines.
MAP_PRIVATE
Changes are private to the process. Modifications to the mapped area are not written back to the underlying file.
MAP_ANONYMOUS
The mapping is not backed by any file. The file descriptor fd must be -1. The mapping is initialized to zeros.
MAP_FIXED
Don't use a separate physically-based backing store. This is the default. If MAP_FIXED is specified, the address range specified by addr and length must be available. If that range is already mapped, the existing mapping is overlaid. If MAP_FIXED is not specified, the kernel may return an address different from the requested addr.
MAP_POPULATE
Populate the page tables for the mapping. This is useful for performance, since it avoids the need for page faults the first time. This flag is only valid for anonymous mappings, not for mappings of files.
MAP_NONBLOCK
Do not populate the page tables for the mapping. This is the default. If MAP_NONBLOCK is specified, the page tables are not populated for the mapping. This means that the page tables are not written back to the underlying file. This flag is only valid for anonymous mappings, not for mappings of files.

The munmap() function deletes the mapping denoted by addr and of length length. The memory region specified by addr and length must be a range that was previously mapped using mmap(). The memory region is deallocated and the address range becomes invalid for use by the calling process.

RETURN VALUE

On success, mmap() returns a pointer to the mapped area. On failure, mmap() returns MAP_FAILED (which is void*)(-1) and sets errno to indicate the error.

On success, munmap() returns 0. On failure, munmap() returns -1 and sets errno to indicate the error.

ERRORS

The mmap() function may fail for any of the following reasons:

EACCES
fd was not open for read access when PROT_READ was specified, or fd was not open for write access when PROT_WRITE was specified.
EBADF
fd is not a valid file descriptor.
EINVAL
flags is not valid. length is zero. offset is not a multiple of the system page size. The specified address range is not available. The mapping length plus the offset exceeds the maximum size of a process.
ENFILE
The system-wide limit on the total number of open files has been reached.
ENODEV
fd refers to a file that is not a regular file.
ENOMEM
Insufficient kernel memory was available to carry out the mapping.
EOVERFLOW
offset or length is too large to be represented in a size_t.
SIGSEGV
The calling process tried to access an unmapped page. This happens when the memory is not mapped.

The munmap() function may fail for any of the following reasons:

EINVAL
addr is not a multiple of the system page size. The specified address range is not available. The mapping length plus the offset exceeds the maximum size of a process.
ENOMEM
Insufficient kernel memory was available to carry out the unmapping.

NOTES

The mmap() function is used to map files or devices into memory. It can be used to read and write files, or to share memory between processes.

The mmap() function is a powerful tool that can be used to implement a variety of features, such as shared memory, memory-mapped files, and memory-mapped devices. It is important to use mmap() carefully, as incorrect usage can lead to data corruption or other problems.

The mmap() function can be used to map files or devices into memory. The fd argument is a file descriptor that refers to the file or device to be mapped. The offset argument specifies the offset into the file or device at which to start the mapping. The length argument specifies the length of the mapping.

The prot argument specifies the protection for the mapping. It can be PROT_READ, PROT_WRITE, PROT_EXEC, or PROT_NONE. The flags argument specifies the type of mapping. It can be MAP_SHARED or MAP_PRIVATE.

The munmap() function is used to unmap memory regions that have been mapped using mmap(). The addr argument specifies the starting address of the mapping to be unmapped, and the length argument specifies the length of the mapping.

It is important to unmap memory regions when they are no longer needed, as this will free up system resources. Failure to unmap memory regions can lead to memory leaks and other problems.

The following example shows how to use mmap() to map a file into memory and then write to it:

The program below uses mmap() to create a memory mapping of the file specified in the first command-line argument. It uses the offset and length specified in the second and third command-line arguments. The program creates a memory mapping of the required pages of the file and then uses write(2) to output the desired bytes.

Program source

#include <err.h>
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/mman.h>
#include <sys/stat.h>
#include <sys/types.h>
#include <unistd.h>
int
main(int argc, char *argv[])
{
    int          fd;
    char         *addr;
    off_t        offset, pa_offset;
    size_t       length;
    ssize_t      s;
    struct stat  sb;
    if (argc < 3 || argc > 4) {
        fprintf(stderr, "%s file offset [length]\n", argv[0]);
        exit(EXIT_FAILURE);
    }
    fd = open(argv[1], O_RDONLY);
    if (fd == -1)
        err(EXIT_FAILURE, "open");
    if (fstat(fd, &sb) == -1)           /* To obtain file size */
        err(EXIT_FAILURE, "fstat");
    offset = atoi(argv[2]);
    pa_offset = offset & ~(sysconf(_SC_PAGE_SIZE) - 1);
        /* offset for mmap() must be page aligned */
    if (offset >= sb.st_size) {
        fprintf(stderr, "offset is past end of file\n");
        exit(EXIT_FAILURE);
    }
    if (argc == 4) {
        length = atoi(argv[3]);
        if (offset + length > sb.st_size)
            length = sb.st_size - offset;
                /* Can't display bytes past end of file */
    } else {    /* No length arg ==> display to end of file */
        length = sb.st_size - offset;
    }
    addr = mmap(NULL, length + offset - pa_offset, PROT_READ,
                MAP_PRIVATE, fd, pa_offset);
    if (addr == MAP_FAILED)
        err(EXIT_FAILURE, "mmap");
    s = write(STDOUT_FILENO, addr + offset - pa_offset, length);
    if (s != length) {
        if (s == -1)
            err(EXIT_FAILURE, "write");
        fprintf(stderr, "partial write");
        exit(EXIT_FAILURE);
    }
    munmap(addr, length + offset - pa_offset);
    close(fd);
    exit(EXIT_SUCCESS);
}
