mmap(2) Manual de Llamadas al Sistema mmap(2)

NOMBRE

mmap, munmap - mapear o desmapear archivos o dispositivos en memoria

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

SINOPSIS

#include <sys/mman.h>
void *mmap(void *addr, size_t length, int prot, int flags,
           int fd, off_t offset);
int munmap(void *addr, size_t length);

Ver VERSIONS para información sobre los requisitos de la macro de prueba de características.

DESCRIPCIÓN

mmap() crea un nuevo mapeo en el espacio de direcciones virtuales del proceso que llama. La dirección de inicio del nuevo mapeo se especifica en addr. El argumento length especifica la longitud del mapeo (que debe ser mayor que 0).

Si addr es NULL, entonces el kernel elige la dirección (alineada a página) donde crear el mapeo; este es el método más portable de crear un nuevo mapeo. Si addr no es NULL, entonces el kernel lo toma como una pista sobre dónde colocar el mapeo; en Linux, el kernel elegirá un límite de página cercano (pero siempre mayor o igual al valor especificado por /proc/sys/vm/mmap_min_addr) e intentará crear el mapeo allí. Si ya existe otro mapeo allí, el kernel elige una nueva dirección que puede o no depender de la pista. La dirección del nuevo mapeo se devuelve como resultado de la llamada.

El contenido de un mapeo de archivo (en contraposición a un mapeo anónimo; ver MAP_ANONYMOUS más abajo), se inicializa usando length bytes comenzando en el desplazamiento offset en el archivo (u otro objeto) al que se refiere el descriptor de archivo fd. offset debe ser un múltiplo del tamaño de página devuelto por sysconf(_SC_PAGE_SIZE).

Después de que la llamada mmap() regrese, el descriptor de archivo, fd, puede cerrarse inmediatamente sin invalidar el mapeo.

El argumento prot describe la protección de memoria deseada del mapeo (y no debe entrar en conflicto con el modo de apertura del archivo). Es PROT_NONE o el OR bit a bit de una o más de las siguientes banderas:

PROT_EXEC
Las páginas pueden ser ejecutadas.
PROT_READ
Las páginas pueden ser leídas.
PROT_WRITE
Las páginas pueden ser escritas.
PROT_NONE
Las páginas no pueden ser accedidas.

El argumento flags

El argumento flags determina si las actualizaciones al mapeo son visibles para otros procesos que mapean la misma región, y si las actualizaciones se reflejan en el archivo subyacente. Este comportamiento se determina incluyendo exactamente uno de los siguientes valores en flags:

MAP_SHARED
Compartir este mapeo. Las actualizaciones al mapeo son visibles para otros procesos que mapean la misma región y (en el caso de mapeos respaldados por archivos) se reflejan en el archivo subyacente. (Para controlar con precisión cuándo se reflejan las actualizaciones en el archivo subyacente se requiere el uso de msync(2)).
MAP_SHARED_VALIDATE (desde Linux 4.15)
Esta bandera proporciona el mismo comportamiento que MAP_SHARED excepto que los mapeos MAP_SHARED ignoran las banderas desconocidas en flags. Por el contrario, al crear un mapeo usando MAP_SHARED_VALIDATE, el kernel verifica que todas las banderas pasadas sean conocidas y falla el mapeo con el error EOPNOTSUPP para banderas desconocidas. Este tipo de mapeo también se requiere para poder usar algunas banderas de mapeo (por ejemplo, MAP_SYNC).
MAP_PRIVATE
Crear un mapeo privado de copia en escritura. Las actualizaciones al mapeo no son visibles para otros procesos que mapean el mismo archivo, y no se reflejan en el archivo subyacente. No se especifica si los cambios realizados en el archivo después de la llamada mmap() son visibles en la región mapeada.

Tanto MAP_SHARED como MAP_PRIVATE se describen en POSIX.1-2001 y POSIX.1-2008. MAP_SHARED_VALIDATE es una extensión de Linux.

Además, cero o más de los siguientes valores pueden ser combinados con OR en flags:

MAP_32BIT (desde Linux 2.4.20, 2.6)
Colocar el mapeo en los primeros 2 Gigabytes del espacio de direcciones del proceso. Esta bandera solo es compatible en x86-64, para programas de 64 bits. Se añadió para permitir que las pilas de hilos se asignaran en algún lugar dentro de los primeros 2 GB de memoria, para mejorar el rendimiento del cambio de contexto en algunos procesadores de 64 bits tempranos. Los procesadores x86-64 modernos ya no tienen este problema de rendimiento, por lo que el uso de esta bandera no es necesario en esos sistemas. La bandera MAP_32BIT se ignora cuando se establece MAP_FIXED.
MAP_ANON
Sinónimo de MAP_ANONYMOUS; proporcionado para compatibilidad con otras implementaciones.
MAP_ANONYMOUS
El mapeo no está respaldado por ningún archivo; sus contenidos se inicializan a cero. El argumento fd se ignora; sin embargo, algunas implementaciones requieren que fd sea -1 si se especifica MAP_ANONYMOUS (o MAP_ANON), y las aplicaciones portables deben asegurarse de esto. El argumento offset debe ser cero. La compatibilidad con MAP_ANONYMOUS en conjunción con MAP_SHARED se añadió en Linux 2.4.
MAP_DENYWRITE
Esta bandera se ignora. (Hace mucho tiempo — Linux 2.0 y anteriores — indicaba que los intentos de escribir en el archivo subyacente debían fallar con ETXTBSY. Pero esta fue una fuente de ataques de denegación de servicio).
MAP_EXECUTABLE
Esta bandera se ignora.
MAP_FILE
Bandera de compatibilidad. Ignorada.
MAP_FIXED
No interpretes addr como una pista: coloca el mapeo exactamente en esa dirección. addr debe estar adecuadamente alineado: para la mayoría de las arquitecturas, un múltiplo del tamaño de página es suficiente; sin embargo, algunas arquitecturas pueden imponer restricciones adicionales. Si la región de memoria especificada por addr y length se solapa con páginas de algún mapeo existente, entonces la parte solapada de los mapeos existentes se descartará. Si la dirección especificada no puede ser utilizada, mmap() fallará.
El software que aspira a ser portable debe usar la bandera MAP_FIXED con cuidado, teniendo en cuenta que el diseño exacto de los mapeos de memoria de un proceso puede cambiar significativamente entre versiones de Linux, versiones de la biblioteca C y lanzamientos del sistema operativo. ¡Lea cuidadosamente la discusión de esta bandera en NOTAS!
MAP_FIXED_NOREPLACE (desde Linux 4.17)
Esta bandera proporciona un comportamiento similar a MAP_FIXED con respecto a la aplicación de addr, pero difiere en que MAP_FIXED_NOREPLACE nunca sobrescribe un rango mapeado preexistente. Si el rango solicitado colisionara con un mapeo existente, entonces esta llamada falla con el error EEXIST. Esta bandera puede ser utilizada por lo tanto como una forma de intentar mapear un rango de direcciones de manera atómica (con respecto a otros hilos): un hilo tendrá éxito; todos los demás reportarán fallo.
Tenga en cuenta que los kernels más antiguos que no reconocen la bandera MAP_FIXED_NOREPLACE típicamente (al detectar una colisión con un mapeo preexistente) recurrirán a un comportamiento de tipo “no-MAP_FIXED”: devolverán una dirección diferente de la dirección solicitada. Por lo tanto, el software compatible con versiones anteriores debe verificar la dirección devuelta con la dirección solicitada.
MAP_GR

mmap()

The mmap() system call creates a new mapping in the virtual address space of the calling process. The starting address of the new mapping is stored in the location pointed to by addr. The function is used to map files or devices into memory.

The length argument specifies the length, in bytes, of the memory region to be mapped. The offset argument specifies the offset within the file or device that is to be mapped. The offset must be a multiple of the page size.

The prot argument specifies the desired memory protection for the mapping. It is a bitmask that can be either PROT_NONE (the memory cannot be accessed) or PROT_READ (memory can be read), PROT_WRITE (memory can be written), or PROT_EXEC (memory can be executed). Write protection, if requested, must be set in the object and is required for MAP_SHARED.

The flags argument determines the nature of the mapping. The most important flags are:

MAP_ANONYMOUS
The mapping is not backed by any file. The contents of the mapping are initialized to zero. This flag is used to create anonymous memory mappings, for example, for the stack and the heap. This flag can be used with either MAP_SHARED or MAP_PRIVATE.
MAP_ANON
Synonym for MAP_ANONYMOUS.
MAP_FIXED
Do not use a free page, use the supplied address range. This is dangerous! It is used for exact address mapping. If the specified address range (addr, length) is already mapped, the existing mapping is unmapped. The caller must be sure that the address is valid.
MAP_FIXED_NOREPLACE
(Since Linux 4.14) Similar to MAP_FIXED, but if the specified address range (addr, length) clashes with an existing mapping, the call fails with the error EEXIST. This flag prevents accidentally overwriting an existing mapping.
MAP_GROWSDOWN
This flag is used for stacks. It indicates to the kernel virtual memory system that the mapping should extend downward in memory. The return address is one page lower than the memory area that is actually created in the process's virtual address space. Touching an address in the "guard" page below the mapping will cause the mapping to grow by a page. This growth can be repeated until the mapping grows to within a page of the high end of the next lower mapping, at which point touching the "guard" page will result in a SIGSEGV signal.
MAP_HUGETLB (since Linux 2.6.32)
Allocate the mapping using "huge" pages. See the Linux kernel source file Documentation/admin-guide/mm/hugetlbpage.rst for further information, as well as NOTES, below.
MAP_HUGE_2MB
MAP_HUGE_1GB (since Linux 3.8)
Used in conjunction with MAP_HUGETLB to select alternative hugetlb page sizes (respectively, 2 MB and 1 GB) on systems that support multiple hugetlb page sizes.
More generally, the desired huge page size can be configured by encoding the base-2 logarithm of the desired page size in the six bits at the offset MAP_HUGE_SHIFT. (A value of zero in this bit field provides the default huge page size; the default huge page size can be discovered via the Hugepagesize field exposed by /proc/meminfo.) Thus, the above two constants are defined as:

#define MAP_HUGE_2MB    (21 << MAP_HUGE_SHIFT)
#define MAP_HUGE_1GB    (30 << MAP_HUGE_SHIFT)

The range of huge page sizes that are supported by the system can be discovered by listing the subdirectories in /sys/kernel/mm/hugepages.
MAP_LOCKED (since Linux 2.5.37)
Mark the mapped region to be locked in the same way as mlock(2). This implementation will try to populate (prefault) the whole range but the mmap() call doesn't fail with ENOMEM if this fails. Therefore major faults might happen later on. So the semantic is not as strong as mlock(2). One should use mmap() plus mlock(2) when major faults are not acceptable after the initialization of the mapping. The MAP_LOCKED flag is ignored in older kernels.
MAP_NONBLOCK (since Linux 2.5.46)
This flag is meaningful only in conjunction with MAP_POPULATE. Don't perform read-ahead: create page tables entries only for pages that are already present in RAM. Since Linux 2.6.23, this flag causes MAP_POPULATE to do nothing. One day, the combination of MAP_POPULATE and MAP_NONBLOCK may be reimplemented.
MAP_NORESERVE
Do not reserve swap space for this mapping. When swap space is reserved, one has the guarantee that it is possible to modify the mapping. When swap space is not reserved one might get SIGSEGV upon a write if no physical memory is available. See also the discussion of the file /proc/sys/vm/overcommit_memory in proc_sys_vm(5). Before Linux 2.6, this flag had effect only for private writable mappings.
MAP_POPULATE (since Linux 2.5.46)
Populate (prefault) page tables for a mapping. For a file mapping, this causes read-ahead on the file. This will help to reduce blocking on page faults later. The mmap() call doesn't fail if the mapping cannot be populated (for example, due to limitations on the number of mapped huge pages when using MAP_HUGETLB). Support for MAP_POPULATE in conjunction with private mappings was added in Linux 2.6.23.
MAP_STACK (since Linux 2.6.27)
Allocate the mapping at an address suitable for a process or thread stack.
This flag is currently a no-op on Linux. However, by employing this flag, applications can ensure that they transparently obtain support if the flag is implemented in the future. Thus, it is used in the glibc threading implementation to allow for the fact that some architectures may (later) require special treatment for stack allocations. A further reason to employ this flag is portability: MAP_STACK exists (and has an effect) on some other systems (e.g., some of the BSDs).
MAP_SHARED
Share this mapping. Changes to the mapped memory are visible to other processes mapping the same region, and are carried through to the underlying file. On success, mmap() returns a pointer to the mapped area, which is suitable for reading and writing. The return value is MAP_FAILED (that is, (void *) -1) and should be checked for errors.
MAP_SHARED_VALIDATE
(Since Linux 4.15) This flag is similar to MAP_SHARED, but it causes the kernel to validate the mapping for specific guarantees, particularly regarding persistence to storage. See the description of MAP_SYNC below.
MAP_PRIVATE
Create a private copy-on-write mapping. Updates to the mapped memory are not visible to other processes mapping the same file or device, and are not carried through to the underlying file. If a process writes to a page in a private mapping, the kernel creates a copy of the page for that process. If the mapping is backed by a file, the file itself is not modified.
MAP_SYNC (since Linux 4.15)
This flag is available only with the MAP_SHARED_VALIDATE mapping type; mappings of type MAP_SHARED will silently ignore this flag. This flag is supported only for files supporting DAX (direct mapping of persistent memory). For other files, creating a mapping with this flag results in an EOPNOTSUPP error.
Shared file mappings with this flag provide the guarantee that while some memory is mapped writable in the address space of the process, it will be visible in the same file at the same offset even after the system crashes or is rebooted. In conjunction with the use of appropriate CPU instructions, this provides users of such mappings with a more efficient way of making data modifications persistent.
MAP_UNINITIALIZED (since Linux 2.6.33)
Don't clear anonymous pages. This flag is intended to improve performance on embedded devices. This flag is honored only if the kernel was configured with the CONFIG_MMAP_ALLOW_UNINITIALIZED option. Because of the security implications, that option is normally enabled only on embedded devices (i.e., devices where one has complete control of the contents of user memory).

Of the above flags, only MAP_FIXED is specified in POSIX.1-2001 and POSIX.1-2008. However, most systems also support MAP_ANONYMOUS (or its synonym MAP_ANON).

munmap()

The munmap() system call deletes the mappings for the specified address range, and causes further references to addresses within the range to generate invalid memory references. The region is also automatically unmapped when the process is terminated. On the other hand, closing the file descriptor does not unmap the region.

The address addr must be a multiple of the page size (but length need not be). All pages containing a part of the indicated range are unmapped, and subsequent references to these pages will generate SIGSEGV. It is not an error if the indicated range does not contain any mapped pages.

RETURN VALUE

On success, mmap() returns a pointer to the mapped area. On error, the value MAP_FAILED (that is, (void *) -1) is returned, and errno is set to indicate the error.

On success, munmap() returns 0. On failure, it returns -1, and errno is set to indicate the error (probably to EINVAL).

ERRORS

EACCES
A file descriptor refers to a non-regular file. Or a file mapping was requested, but fd is not open for reading. Or MAP_SHARED was requested and PROT_WRITE is set, but fd is not open in read/write (O_RDWR) mode. Or PROT_WRITE is set, but the file is append-only.
EAGAIN
The file has been locked, or too much memory has been locked (see setrlimit(2)).
EBADF
fd is not a valid file descriptor (and MAP_ANONYMOUS was not set).
EEXIST
MAP_FIXED_NOREPLACE was specified in flags, and the range covered by addr and length clashes with an existing mapping.
EINVAL
We don't like addr, length, or offset (e.g., they are too large, or not aligned on a page boundary).
EINVAL
(since Linux 2.6.12) length was 0.
EINVAL
flags contained none of MAP_PRIVATE, MAP_SHARED, or MAP_SHARED_VALIDATE.
ENFILE
The system-wide limit on the total number of open files has been reached.
ENODEV
The underlying filesystem of the specified file does not support memory mapping.
ENOMEM
No memory is available.
ENOMEM
The process's maximum number of mappings would have been exceeded. This error can also occur for munmap(), when unmapping a region in the middle of an existing mapping, since this results in two smaller mappings on either side of the region being unmapped.
ENOMEM
(since Linux 4.7) The process's RLIMIT_DATA limit, described in getrlimit(2), would have been exceeded.
ENOMEM
We don't like addr, because it exceeds the virtual address space of the CPU.
EOVERFLOW
On 32-bit architecture together with the large file extension (i.e., using 64-bit off_t): the number of pages used for length plus number of pages used for offset would overflow unsigned long (32 bits).
EPERM

EPERM
La operación fue impedida por un sello de archivo; ver fcntl(2).
EPERM
Se especificó la bandera MAP_HUGETLB, pero el llamador no tenía privilegios (no tenía la capacidad CAP_IPC_LOCK) y no es miembro del grupo hugetlb_shm_group; ver la descripción de /proc/sys/vm/hugetlb_shm_group en proc_sys_vm(5).
ETXTBSY
Se estableció MAP_DENYWRITE pero el objeto especificado por fd está abierto para escritura.

El uso de una región mapeada puede resultar en estas señales:

SIGSEGV
Intento de escritura en una región mapeada como solo lectura.
SIGBUS
Intento de acceso a una página del búfer que se encuentra más allá del final del archivo mapeado. Para una explicación del tratamiento de los bytes en la página que corresponde al final de un archivo mapeado que no es un múltiplo del tamaño de página, ver NOTAS.

VERSIONES

En algunas arquitecturas de hardware (por ejemplo, i386), PROT_WRITE implica PROT_READ. Si PROT_READ implica PROT_EXEC o no depende de la arquitectura. Los programas portátiles siempre deben establecer PROT_EXEC si pretenden ejecutar código en el nuevo mapeo.

La forma portátil de crear un mapeo es especificar addr como 0 (NULL), y omitir MAP_FIXED de flags. En este caso, el sistema elige la dirección para el mapeo; la dirección se elige para no entrar en conflicto con ningún mapeo existente, y no será 0. Si se especifica la bandera MAP_FIXED, y addr es 0 (NULL), entonces la dirección mapeada será 0 (NULL).

Ciertas constantes de flags se definen solo si se definen macros de prueba de características adecuadas (posiblemente por defecto): _DEFAULT_SOURCE con glibc 2.19 o posterior; o _BSD_SOURCE o _SVID_SOURCE en glibc 2.19 y anteriores. (Emplear _GNU_SOURCE también es suficiente, y requerir esa macro específicamente habría sido más lógico, ya que todas estas banderas son específicas de Linux). Las banderas relevantes son: MAP_32BIT, MAP_ANONYMOUS (y el sinónimo MAP_ANON), MAP_DENYWRITE, MAP_EXECUTABLE, MAP_FILE, MAP_GROWSDOWN, MAP_HUGETLB, MAP_LOCKED, MAP_NONBLOCK, MAP_NORESERVE, MAP_POPULATE y MAP_STACK.

Diferencias entre la biblioteca C y el kernel

Esta página describe la interfaz proporcionada por la función de envoltura mmap() de glibc. Originalmente, esta función invocaba una llamada al sistema del mismo nombre. Desde Linux 2.4, esa llamada al sistema ha sido reemplazada por mmap2(2), y hoy en día la función de envoltura mmap() de glibc invoca mmap2(2) con un valor ajustado adecuadamente para offset.

NOTAS

La memoria mapeada por mmap() se conserva a través de fork(2), con los mismos atributos.

Un archivo se mapea en múltiplos del tamaño de página. Para un archivo que no es un múltiplo del tamaño de página, los bytes restantes en la página parcial al final del mapeo se ponen a cero cuando se mapean, y las modificaciones en esa región no se escriben en el archivo. El efecto de cambiar el tamaño del archivo subyacente de un mapeo en las páginas que corresponden a regiones añadidas o eliminadas del archivo no está especificado.

Una aplicación puede determinar qué páginas de un mapeo están actualmente residentes en la caché de búferes/páginas usando mincore(2).

Usando MAP_FIXED de forma segura

El único uso seguro para MAP_FIXED es cuando el rango de direcciones especificado por addr y length fue reservado previamente usando otro mapeo; de lo contrario, el uso de MAP_FIXED es peligroso porque elimina forzosamente mapeos preexistentes, lo que facilita que un proceso multihilo corrompa su propio espacio de direcciones.

Por ejemplo, supongamos que el hilo A busca en /proc/pid/maps para localizar un rango de direcciones no utilizado que pueda mapear usando MAP_FIXED, mientras que el hilo B adquiere simultáneamente parte o la totalidad de ese mismo rango de direcciones. Cuando el hilo A posteriormente emplea mmap(MAP_FIXED), efectivamente sobrescribirá el mapeo que el hilo B creó. En este escenario, el hilo B no necesita crear un mapeo directamente; simplemente realizar una llamada a una biblioteca que, internamente, utiliza dlopen(3) para cargar alguna otra biblioteca compartida, será suficiente. La llamada a dlopen(3) mapeará la biblioteca en el espacio de direcciones del proceso. Además, casi cualquier llamada a una biblioteca puede implementarse de manera que agregue mapeos de memoria al espacio de direcciones, ya sea con esta técnica o simplemente asignando memoria. Ejemplos incluyen brk(2), malloc(3), pthread_create(3), y las bibliotecas PAM http://www.linux-pam.org.

Desde Linux 4.17, un programa multihilo puede usar la bandera MAP_FIXED_NOREPLACE para evitar el peligro descrito anteriormente al intentar crear un mapeo en una dirección fija que no ha sido reservada por un mapeo preexistente.

Cambios de marcas de tiempo para mapeos respaldados por archivos

Para mapeos respaldados por archivos, el campo st_atime del archivo mapeado puede actualizarse en cualquier momento entre mmap() y el desmapeo correspondiente; la primera referencia a una página mapeada actualizará el campo si aún no se ha hecho.

Los campos st_ctime y st_mtime para un archivo mapeado con PROT_WRITE y MAP_SHARED se actualizarán después de una escritura en la región mapeada, y antes de un msync(2) posterior con la bandera MS_SYNC o MS_ASYNC, si ocurre.

Mapeos de páginas grandes (Huge TLB)

Para mapeos que emplean páginas grandes, los requisitos para los argumentos de mmap() y munmap() difieren ligeramente de los requisitos para mapeos que utilizan el tamaño de página nativo del sistema.

Para mmap(), offset debe ser un múltiplo del tamaño de página grande subyacente. El sistema alinea automáticamente length para que sea un múltiplo del tamaño de página grande subyacente.

Para munmap(), addr y length deben ser ambos un múltiplo del tamaño de página grande subyacente.

ADVERTENCIAS

A diferencia de las implementaciones típicas de malloc(3), mmap() no impide la creación de objetos de tamaño superior a PTRDIFF_MAX. Los objetos que son más grandes que PTRDIFF_MAX solo funcionan de maneras limitadas en C (en particular, la resta de punteros produce un comportamiento indefinido si el resultado es mayor que PTRDIFF_MAX). Además, GCC también asume que ningún objeto es más grande que PTRDIFF_MAX. PTRDIFF_MAX suele ser la mitad del tamaño del espacio de direcciones; por lo tanto, para procesos de 32 bits, suele ser 0x7fffffff (casi 2 GiB).

ERRORES

En Linux, no hay garantías como las sugeridas anteriormente bajo MAP_NORESERVE. Por defecto, cualquier proceso puede ser eliminado en cualquier momento cuando el sistema se queda sin memoria.

Antes de Linux 2.6.7, la bandera MAP_POPULATE solo tenía efecto si prot se especificaba como PROT_NONE.

SUSv3 especifica que mmap() debería fallar si length es 0. Sin embargo, antes de Linux 2.6.12, mmap() tuvo éxito en este caso: no se creó ningún mapeo y la llamada devolvió addr. Desde Linux 2.6.12, mmap() falla con el error EINVAL para este caso.

POSIX especifica que el sistema debe llenar con ceros cualquier página parcial al final del objeto y que el sistema nunca escribirá ninguna modificación del objeto más allá de su final. En Linux, cuando se escriben datos en una página parcial de este tipo después del final del objeto, los datos permanecen en la caché de páginas incluso después de que el archivo se cierre y se desmapee, y aunque los datos nunca se escriban en el propio archivo, los mapeos posteriores pueden ver el contenido modificado. En algunos casos, esto podría solucionarse llamando a msync(2) antes de que ocurra el desmapeo; sin embargo, esto no funciona en tmpfs(5) (por ejemplo, al usar la interfaz de memoria compartida POSIX documentada en shm_overview(7)).

e <err.h> #include <fcntl.h> #include <stdio.h> #include <stdlib.h> #include <sys/mman.h> #include <sys/stat.h> #include <sys/types.h> #include <unistd.h> int main(int argc, char *argv[]) { int fd; char *addr; off_t offset, pa_offset; size_t length; ssize_t s; struct stat sb; if (argc < 3 || argc > 4) { fprintf(stderr, "%s file offset [length]\n", argv[0]); exit(EXIT_FAILURE); } fd = open(argv[1], O_RDONLY); if (fd == -1) err(EXIT_FAILURE, "open"); if (fstat(fd, &sb) == -1) /* Para obtener el tamaño del archivo */ err(EXIT_FAILURE, "fstat"); offset = atoi(argv[2]); pa_offset = offset & ~(sysconf(_SC_PAGE_SIZE) - 1); /* el offset para mmap() debe estar alineado a página */ if (offset >= sb.st_size) { fprintf(stderr, "el offset está más allá del final del archivo\n"); exit(EXIT_FAILURE); } if (argc == 4) { length = atoi(argv[3]); if (offset + length > sb.st_size) length = sb.st_size - offset; /* No se pueden mostrar bytes más allá del final del archivo */ } else { /* Sin argumento length ==> mostrar hasta el final del archivo */ length = sb.st_size - offset; } addr = mmap(NULL, length + offset - pa_offset, PROT_READ, MAP_PRIVATE, fd, pa_offset); if (addr == MAP_FAILED) err(EXIT_FAILURE, "mmap"); s = write(STDOUT_FILENO, addr + offset - pa_offset, length); if (s != length) { if (s == -1) err(EXIT_FAILURE, "write"); fprintf(stderr, "escritura parcial"); exit(EXIT_FAILURE); } munmap(addr, length + offset - pa_offset); close(fd); exit(EXIT_SUCCESS); }
