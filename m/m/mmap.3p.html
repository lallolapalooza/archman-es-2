PROLOGO

Esta página del manual forma parte del Manual del Programador POSIX. La implementación de Linux de esta interfaz puede diferir (consulte la página del manual de Linux correspondiente para conocer los detalles del comportamiento de Linux), o la interfaz puede no estar implementada en Linux.

NOMBRE

mmap — mapear páginas de memoria

SINOPSIS

#include <sys/mman.h>
void *mmap(void *addr, size_t len, int prot, int flags,
    int fildes, off_t off);

DESCRIPCION

La función mmap() establece un mapeo entre un espacio de direcciones de un proceso y un objeto de memoria.

La función mmap() deberá ser compatible con los siguientes objetos de memoria:

*
Archivos regulares
*
Objetos de memoria compartida
*
Objetos de memoria tipificados

La compatibilidad con cualquier otro tipo de archivo no está especificada.

El formato de la llamada es el siguiente:

pa=mmap(addr, len, prot, flags, fildes, off);

La función mmap() establecerá un mapeo entre el espacio de direcciones del proceso en una dirección pa durante len bytes hacia el objeto de memoria representado por el descriptor de archivo fildes en el desplazamiento off durante len bytes. El valor de pa es una función definida por la implementación del parámetro addr y los valores de flags, descritos más adelante. Una llamada exitosa a mmap() devolverá pa como su resultado. El rango de direcciones que comienza en pa y continúa durante len bytes será legítimo para el espacio de direcciones posible (no necesariamente actual) del proceso. El rango de bytes que comienza en off y continúa durante len bytes será legítimo para los desplazamientos posibles (no necesariamente actuales) en el objeto de memoria representado por fildes.

Si fildes representa un objeto de memoria tipificado abierto con la bandera POSIX_TYPED_MEM_ALLOCATE o POSIX_TYPED_MEM_ALLOCATE_CONTIG, el objeto de memoria a mapear será esa porción del objeto de memoria tipificado asignado por la implementación como se especifica a continuación. En este caso, si off no es cero, el comportamiento de mmap() no está definido. Si fildes se refiere a un objeto de memoria tipificado válido que no es accesible desde el proceso que llama, mmap() fallará.

El mapeo establecido por mmap() reemplazará cualquier mapeo previo para esas páginas completas que contengan alguna parte del espacio de direcciones del proceso que comienza en pa y continúa durante len bytes.

Si el tamaño del archivo mapeado cambia después de la llamada a mmap() como resultado de alguna otra operación en el archivo mapeado, el efecto de las referencias a porciones de la región mapeada que corresponden a porciones añadidas o eliminadas del archivo no está especificado.

Si len es cero, mmap() fallará y no se establecerá ningún mapeo.

El parámetro prot determina si se permiten accesos de lectura, escritura, ejecución o alguna combinación de ellos a los datos que se mapean. prot será PROT_NONE o el OR a nivel de bits de una o más de las otras banderas en la siguiente tabla, definidas en la cabecera <sys/mman.h>.

Constante Simbólica Descripción
PROT_READ Los datos se pueden leer.
PROT_WRITE Los datos se pueden escribir.
PROT_EXEC Los datos se pueden ejecutar.
PROT_NONE Los datos no se pueden acceder.

Si una implementación no puede soportar la combinación de tipos de acceso especificados por prot, la llamada a mmap() fallará.

Una implementación puede permitir accesos distintos a los especificados por prot; sin embargo, la implementación no permitirá que una escritura tenga éxito donde no se haya establecido PROT_WRITE y no permitirá ningún acceso donde se haya establecido únicamente PROT_NONE. La implementación deberá soportar al menos los siguientes valores de prot: PROT_NONE, PROT_READ, PROT_WRITE y el OR a nivel de bits de PROT_READ y PROT_WRITE. El descriptor de archivo fildes deberá haber sido abierto con permiso de lectura, independientemente de las opciones de protección especificadas. Si se especifica PROT_WRITE, la aplicación deberá asegurarse de haber abierto el descriptor de archivo fildes con permiso de escritura, a menos que se especifique MAP_PRIVATE en el parámetro flags como se describe a continuación.

El parámetro flags proporciona información adicional sobre el manejo de los datos mapeados. El valor de flags es el OR a nivel de bits de estas opciones, definidas en la cabecera <sys/mman.h>:

Constante Simbólica Descripción
MAP_SHARED Los cambios se comparten.
MAP_PRIVATE Los cambios son privados.
MAP_FIXED Interpretar addr exactamente.

Depende de la implementación si se debe soportar MAP_FIXED. MAP_FIXED se soportará en sistemas compatibles con XSI.

MAP_SHARED y MAP_PRIVATE describen la disposición de las referencias de escritura al objeto de memoria. Si se especifica MAP_SHARED, las referencias de escritura modificarán el objeto subyacente. Si se especifica MAP_PRIVATE, las modificaciones a los datos mapeados por el proceso que llama solo serán visibles para el proceso que llama y no modificarán el objeto subyacente. No se especifica si las modificaciones al objeto subyacente realizadas después de que se establezca el mapeo MAP_PRIVATE son visibles a través del mapeo MAP_PRIVATE. Se puede especificar MAP_SHARED o MAP_PRIVATE, pero no ambos. El tipo de mapeo se mantiene a través de fork().

El estado de los objetos de sincronización como mutex, semáforos, barreras y variables condicionales colocados en memoria compartida mapeada con MAP_SHARED se vuelve indefinido cuando la última región en cualquier proceso que contenga el objeto de sincronización se desmapea.

Cuando fildes representa un objeto de memoria tipificado abierto con la bandera POSIX_TYPED_MEM_ALLOCATE o POSIX_TYPED_MEM_ALLOCATE_CONTIG, mmap(), si hay suficientes recursos disponibles, mapeará len bytes asignados del objeto de memoria tipificado correspondiente que no fueron previamente asignados a ningún proceso en ningún procesador que pueda acceder a ese objeto de memoria tipificado. Si no hay suficientes recursos disponibles, la función fallará. Si fildes representa un objeto de memoria tipificado abierto con la bandera POSIX_TYPED_MEM_ALLOCATE_CONTIG, estos bytes asignados serán contiguos dentro del objeto de memoria tipificado. Si fildes representa un objeto de memoria tipificado abierto con la bandera POSIX_TYPED_MEM_ALLOCATE, estos bytes asignados pueden consistir en fragmentos no contiguos dentro del objeto de memoria tipificado. Si fildes representa un objeto de memoria tipificado abierto sin la bandera POSIX_TYPED_MEM_ALLOCATE_CONTIG ni la bandera POSIX_TYPED_MEM_ALLOCATE, se mapearán len bytes comenzando en el desplazamiento off dentro del objeto de memoria tipificado, exactamente como al mapear un archivo u objeto de memoria compartida. En este caso, si dos procesos mapean un área de memoria tipificada usando los mismos valores off y len y usando descriptores de archivo que se refieren al mismo grupo de memoria (ya sea del mismo puerto o de un puerto diferente), ambos procesos mapearán la misma región de almacenamiento.

Cuando MAP_FIXED se establece en el argumento flags, se informa a la implementación que el valor de pa será addr, exactamente. Si se establece MAP_FIXED, mmap() puede devolver MAP_FAILED y establecer errno en [EINVAL]. Si una solicitud MAP_FIXED es exitosa, entonces cualquier mapeo previo o bloqueo de memoria para esas páginas completas que contengan alguna parte del rango de direcciones [pa,pa+len) se eliminará, como si fuera por una llamada apropiada a munmap(), antes de que se establezca el nuevo mapeo.

Cuando MAP_FIXED no se establece, la implementación utiliza addr de una manera definida por la implementación para llegar a pa. El pa elegido.

DESCRIPCIÓN

La función mmap() crea una nueva asignación en el espacio de direcciones virtual del proceso llamante. El objeto especificado por el descriptor de archivo fildes se mapea en la ubicación devuelta por la función. El descriptor de archivo fildes debe ser un descriptor de archivo abierto válido. El parámetro fildes se refiere a un archivo abierto para lectura, independientemente del valor del argumento prot. Si se especifica PROT_WRITE en el argumento prot, el descriptor de archivo también debe abrirse para escritura.

El rango de direcciones virtuales y la longitud que se van a mapear se especifican por los argumentos addr y len. El argumento addr se interpreta como una dirección deseada (o sugerida) de inicio del mapeo. El argumento off especifica el desplazamiento dentro del objeto que se va a mapear, y debe ser un múltiplo del tamaño de página. El sistema mapea el archivo en unidades de páginas completas.

El argumento flags controla el tipo de mapeo y otras propiedades. Debe ser una o ambas de las siguientes opciones, o cero:

MAP_FIXED
La dirección de la asignación es exactamente addr. Si esa dirección ya está en uso, se liberará antes de que se realice la nueva asignación. Esto es peligroso, ya que puede interferir con otras asignaciones. Si addr no es un múltiplo del tamaño de página, o si no hay suficiente espacio en el espacio de direcciones del proceso para satisfacer la solicitud, la llamada fallará.
MAP_PRIVATE
Se crea una asignación privada y copiable. Las escrituras en la región mapeada no se reflejarán en el archivo subyacente y las escrituras no serán visibles para otros procesos que mapeen el mismo archivo. Si se escribe en una región mapeada con MAP_PRIVATE, el sistema operativo creará una copia privada de la página que contiene la dirección escrita. Las escrituras subsiguientes en esa página operarán en la copia.
MAP_SHARED
Se crea una asignación compartida. Las escrituras en la región mapeada se reflejarán en el archivo subyacente y serán visibles para otros procesos que mapeen el mismo archivo. El sistema operativo puede posponer la escritura de las modificaciones al archivo subyacente.

El argumento prot especifica las protecciones de acceso para la región mapeada. Debe ser una o más de las siguientes opciones, o cero:

PROT_READ
Las páginas se pueden leer.
PROT_WRITE
Las páginas se pueden escribir.
PROT_EXEC
Las páginas se pueden ejecutar.
PROT_NONE
Las páginas no se pueden acceder.

Si addr es 0, la implementación selecciona una dirección adecuada para la asignación. Si flags incluye MAP_FIXED y addr es distinto de cero, debe tener el mismo resto que el parámetro off, módulo el tamaño de página.

El sistema realiza operaciones de mapeo sobre páginas completas. Por lo tanto, si bien el parámetro len no necesita cumplir con una restricción de tamaño o alineación, el sistema incluirá, en cualquier operación de mapeo, cualquier página parcial especificada por el rango de direcciones que comienza en pa y continúa durante len bytes.

El sistema siempre pondrá a cero cualquier página parcial al final de un objeto. Además, el sistema nunca escribirá partes modificadas de la última página de un objeto que estén más allá de su final. Las referencias dentro del rango de direcciones que comienza en pa y continúa durante len bytes a páginas completas que siguen al final de un objeto darán lugar a la entrega de una señal SIGBUS.

Una implementación puede generar señales SIGBUS cuando una referencia causaría un error en el objeto mapeado, como una condición de falta de espacio.

La función mmap() agregará una referencia adicional al archivo asociado con el descriptor de archivo fildes que no se eliminará con un close() posterior en ese descriptor de archivo. Esta referencia se eliminará cuando no queden más mapeos para el archivo.

La última marca de tiempo de acceso a datos del archivo mapeado puede marcarse para actualización en cualquier momento entre la llamada a mmap() y la llamada correspondiente a munmap(). La referencia inicial de lectura o escritura a una región mapeada provocará que la última marca de tiempo de acceso a datos del archivo se marque para actualización si aún no se ha marcado.

Las últimas marcas de tiempo de modificación de datos y cambio de estado de archivo de un archivo que se mapea con MAP_SHARED y PROT_WRITE se marcarán para actualización en algún momento en el intervalo entre una referencia de escritura a la región mapeada y la próxima llamada a msync() con MS_ASYNC o MS_SYNC para esa porción del archivo por parte de cualquier proceso. Si no hay tal llamada y si el archivo subyacente se modifica como resultado de una referencia de escritura, entonces estas marcas de tiempo se marcarán para actualización en algún momento después de la referencia de escritura.

Puede haber límites definidos por la implementación en el número de regiones de memoria que se pueden mapear (por proceso o por sistema).

Si se impone tal límite, si el número de regiones de memoria que pueden ser mapeadas por un proceso se reduce por el uso de shmat() es definido por la implementación.

Si mmap() falla por razones distintas de [EBADF], [EINVAL] o [ENOTSUP], algunas de las asignaciones en el rango de direcciones que comienza en addr y continúa durante len bytes pueden haber sido desmapeadas.

VALOR DE RETORNO

Al completarse con éxito, la función mmap() devolverá la dirección en la que se colocó el mapeo (pa); de lo contrario, devolverá un valor de MAP_FAILED y establecerá errno para indicar el error. El símbolo MAP_FAILED se define en el encabezado <sys/mman.h>. Ningún retorno exitoso de mmap() devolverá el valor MAP_FAILED.

ERRORES

La función mmap() fallará si:

EACCES
El argumento fildes no está abierto para lectura, independientemente de la protección especificada, o fildes no está abierto para escritura y se especificó PROT_WRITE para un mapeo de tipo MAP_SHARED.
EAGAIN
La asignación no pudo ser bloqueada en memoria, si así lo requiere mlockall(), debido a la falta de recursos.
EBADF
El argumento fildes no es un descriptor de archivo abierto válido.
EINVAL
El valor de len es cero.
EINVAL
El valor de flags es inválido (no se estableció ni MAP_PRIVATE ni MAP_SHARED).
EMFILE
El número de regiones mapeadas excedería un límite definido por la implementación (por proceso o por sistema).
ENODEV
El argumento fildes se refiere a un tipo de archivo no compatible con mmap().
ENOMEM
Se especificó MAP_FIXED, y el rango [addr,addr+len) excede lo permitido para el espacio de direcciones de un proceso; o, si no se especificó MAP_FIXED y no hay suficiente espacio en el espacio de direcciones para realizar el mapeo.
ENOMEM
La asignación no pudo ser bloqueada en memoria, si así lo requiere mlockall(), porque requeriría más espacio del que el sistema puede suministrar.
ENOMEM
No quedan suficientes recursos de memoria no asignados en el objeto de memoria tipificada designado por fildes para asignar len bytes.
ENOTSUP
Se especificó MAP_FIXED o MAP_PRIVATE en el argumento flags y la implementación no admite esta funcionalidad.

La implementación no admite la combinación de accesos solicitados en el argumento prot.

ENXIO
Las direcciones en el rango [off,off+len) no son válidas para el objeto especificado por fildes.
ENXIO
Se especificó MAP_FIXED en flags y la combinación de addr, len y off no es válida para el objeto especificado por fildes.
ENXIO
El argumento fildes se refiere a un objeto de memoria tipificada al que no puede acceder el proceso llamante.
EOVERFLOW
El archivo es un archivo regular y el valor de off más len excede el máximo de desplazamiento establecido en la descripción del archivo abierto asociado con fildes.

La función mmap() puede fallar si:

EINVAL
El argumento addr (si se especificó MAP_FIXED) o off no es un múltiplo del tamaño de página devuelto por sysconf(), o se considera inválido por la implementación.

Las siguientes secciones son informativas.

EJEMPLOS

Ninguno.

USO DE LA APLICACIÓN

El uso de mmap() puede reducir la cantidad de memoria disponible para otras funciones de asignación de memoria.

El uso de MAP_FIXED puede dar lugar a un comportamiento no especificado en el uso posterior de malloc() y shmat(). Se desaconseja el uso de MAP_FIXED, ya que puede impedir que una implementación haga el uso más efectivo de los recursos. La mayoría de las implementaciones requieren que off y addr sean múltiplos del tamaño de página devuelto por sysconf().

La aplicación debe garantizar la sincronización correcta al usar mmap() junto con cualquier otro método de acceso a archivos, como read() y write(), entrada/salida estándar y shmat().

La función mmap() permite el acceso a recursos a través de manipulaciones del espacio de direcciones, en lugar de read()/write(). Una vez que un archivo se mapea, todo lo que un proceso tiene que hacer para acceder a él es usar los datos en la dirección a la que se mapeó el archivo. Por lo tanto, utilizando pseudo-código para ilustrar la forma en que un programa existente podría modificarse para usar mmap(), lo siguiente:

fildes = open(...)
lseek(fildes, some_offset)
read(fildes, buf, len)
/* Usar datos en buf. */

se convierte en:

fildes = open(...)
address = mmap(0, len, PROT_READ, MAP_PRIVATE, fildes, some_offset)
/* Usar datos en address. */

JUSTIFICACIÓN

Después de considerar varias otras alternativas, se decidió adoptar la definición mmap() que se encuentra en SVR4 para mapear objetos de memoria en los espacios de direcciones de los procesos. La definición de SVR4 es mínima, en el sentido de que solo describe lo que se ha construido y lo que parece necesario para una instalación de mapeo general y portátil.

Tenga en cuenta que, si bien mmap() se diseñó originalmente para mapear archivos, en realidad es una instalación de mapeo de propósito general. Se puede utilizar para mapear cualquier objeto apropiado, como memoria, archivos, dispositivos, etc., en el espacio de direcciones de un proceso.

Cuando se establece un mapeo, es posible que la implementación deba mapear más de lo solicitado en el espacio de direcciones del proceso debido a requisitos de hardware. Sin embargo, una aplicación no puede contar con este comportamiento. Las implementaciones que no utilizan una arquitectura paginada pueden simplemente asignar una región de memoria común y devolver su dirección; tales implementaciones probablemente no asignan nada más de lo necesario. Las referencias más allá del final del área solicitada no se especifican.

Si una aplicación solicita un mapeo que se superpone con mapeos existentes en el proceso, podría ser deseable que una implementación detecte esto y lo informe a la aplicación. Sin embargo, si el programa especifica un mapeo de dirección fija (que requiere cierto conocimiento de la implementación para determinar una dirección adecuada, si la función es compatible en absoluto), entonces se presume que el programa está gestionando con éxito su propio espacio de direcciones y se debe confiar en él cuando solicita mapear sobre estructuras de datos existentes. Además, también es deseable realizar la menor cantidad de llamadas al sistema posible.

PROLOG

This volume of POSIX.1-2017 specifies extensions to the base operating system that support memory management and process synchronization.

NAME

mmap

memory map

SYNOPSIS

#include <sys/mman.h>

void *mmap(void *addr, size_t len, int prot, int flags, int fildes, off_t offset);
int munmap(void *addr, size_t len);

DESCRIPTION

The mmap() function shall establish a new mapping for the calling process. The location and size of the region of the address space to be mapped are specified by the addr and len arguments, respectively. The prot argument specifies the desired memory protection for the mapped memory.

The addr argument is a hint to the implementation as to where the application would like the mapping to be placed. It is intended for use with protocols that transfer data directly between the address space of one process and the address space of another process. If addr is NULL, an address shall be chosen by the system. The length argument, len, is the number of bytes that will be mapped. The fildes argument specifies a file description referring to an object that can be memory-mapped. The offset argument is the offset in the object indicated by fildes at which to start the mapping. The value of offset shall be a multiple of the page size.

The flags argument specifies the nature of the mapping. Values for flags are constructed by a bitwise OR of the following flags:

MAP_FIXED

          Place the mapping at the exact address specified by addr.
          The addr must be a multiple of the page size. If the
          specified address range is already mapped, the existing mapping
          shall be replaced.

MAP_SHARED

          Share the mapping. Writes to the mapped memory may be written back
          to the object.

MAP_PRIVATE

          Create a private copy-on-write mapping. Writes to the mapped memory
          shall create a private copy of the page and the write is performed
          on that copy. The original object is not changed.

The prot argument specifies the memory protection for the mapped memory. The prot argument, if not zero, shall be the bitwise OR of the following flags:

PROT_READ

          Read access is permitted.

PROT_WRITE

          Write access is permitted.

PROT_EXEC

          Execute access is permitted.

PROT_NONE

          Access is not permitted.

The munmap() function shall remove any mappings for the address range starting at addr and of length len. The value of addr shall be a multiple of the page size. If the specified address range is not mapped, or if it is mapped but not entirely contained within a single mapping, the behavior is unspecified.

The mapping of memory regions is intended to support the sharing of memory between processes. The mmap() function may also be used to map files or devices into memory. It may also be used to create anonymous memory mappings that are not backed by any file or device.

RETURN VALUE

Upon successful completion, mmap() shall return a pointer to the mapped area. Otherwise, it shall return MAP_FAILED. The memory range starting at the returned address and of length len shall be valid for access at the time of return.

Upon successful completion, munmap() shall return 0. Otherwise, it shall return -1.

ERRORS

The mmap() and munmap() functions may fail if:

[EACCES]
The prot argument requires write access, but the file description fildes is not open for write access, or the mapped object is not writable.
[EBADF]
The file description fildes is not a valid file description open for reading.
[EINVAL]
The values specified by addr and len are not page size and page offset multiple.
[EINVAL]
MAP_FIXED was specified in flags and the addr specified is not available.
[EMFILE]
The maximum length to be mapped is less than len, or the system imposed limit on the total number of pages that may be mapped by a process would be exceeded.
[ENFILE]
The system imposed limit on the total number of open files has been reached.
[ENOMEM]
Insufficient system memory is available to perform the mapping.
[ENXIO]
The indicated object is an invalid object.
[EPERM]
MAP_SHARED is set in flags and the effective user ID is not the owner of the object, and the object is not mapped and does not have write permission.
[ETXTBSY]
The file is a regular file that is currently open for text editing. This error is optional.

The munmap() function may fail if:

[EINVAL]
The addr argument is not a multiple of the page size.
[ENOMEM]
The specified address range starting at addr and of length len is not mapped, or it is mapped but not entirely contained within a single mapping.

EXAMPLES

None.

APPLICATION USAGE

The mmap() function can be used to map a region of memory that is larger than the current size of the object. Memory access within the mapping but beyond the current end of the underlying objects may result in SIGBUS signals being sent to the process. The reason for this is that the size of the object can be manipulated by other processes and can change at any moment. The implementation should tell the application that a memory reference is outside the object where this can be detected; otherwise, written data may be lost and read data may not reflect actual data in the object.

Note that references beyond the end of the object do not extend the object as the new end cannot be determined precisely by most virtual memory hardware. Instead, the size can be directly manipulated by ftruncate().

Process memory locking does apply to shared memory regions, and the MCL_FUTURE argument to mlockall() can be relied upon to cause new shared memory regions to be automatically locked.

Existing implementations of mmap() return the value -1 when unsuccessful. Since the casting of this value to type void * cannot be guaranteed by the ISO C standard to be distinct from a successful value, this volume of POSIX.1‐2017 defines the symbol MAP_FAILED, which a conforming implementation does not return as the result of a successful call.

RATIONALE

The primary purpose of the mmap() function is to map files or devices into memory. This allows processes to use memory access instructions to read from and write to the file or device instead of using the read() and write() I/O system calls.

The mmap() function also provides a mechanism for creating anonymous memory mappings. These are mappings that are not backed by any file or device. Anonymous memory mappings can be either shared or private. Shared anonymous mappings are typically used for interprocess communication. Private anonymous mappings are typically used for allocating memory that is private to a process.

The MAP_FIXED flag is provided to allow applications to specify the exact address at which a mapping should be placed. This can be useful for certain types of applications, such as those that need to map a file into memory at a specific address for interprocess communication. However, the use of MAP_FIXED is generally discouraged, as it can lead to portability problems. Applications that use MAP_FIXED should be prepared to handle failures, as the requested address may not be available.

The MAP_SHARED flag indicates that writes to the mapped memory should be shared with other processes that have mapped the same object. The MAP_PRIVATE flag indicates that writes to the mapped memory should be private to the process. Private mappings are typically implemented using copy-on-write semantics.

The prot argument specifies the desired memory protection for the mapped region. The implementation is free to change the protection of the mapped region to be more restrictive than requested. For example, if the application requests PROT_WRITE, the implementation may also allow PROT_READ. However, the implementation must not allow access that is more permissive than requested. For example, if the application requests PROT_READ, the implementation must not allow write access.

The mmap() function is designed to be a general-purpose memory mapping facility. It can be used to map files, devices, or anonymous memory regions into the address space of a process. The MAP_FIXED flag allows applications to specify the exact address at which a mapping should be placed. This can be useful for certain types of applications, such as those that need to map a file into memory at a specific address for interprocess communication. However, the use of MAP_FIXED is generally discouraged, as it can lead to portability problems. Applications that use MAP_FIXED should be prepared to handle failures, as the requested address may not be available.

The POSIX.1-2017 standard specifies that the new mapping replaces any existing mappings. This implies an automatic munmap() on the address range, following existing practice in this regard. The standard developers also considered whether there should be a way for new mappings to overlay existing mappings, but found no existing practice for this.

It is not expected that all hardware implementations are able to support all combinations of permissions at all addresses. Implementations are required to disallow write access to mappings without write permission and to disallow access to mappings without any access permission. Other than these restrictions, implementations may allow access types other than those requested by the application. For example, if the application requests only PROT_WRITE, the implementation may also allow read access. A call to mmap() fails if the implementation cannot support allowing all the access requested by the application. For example, some implementations cannot support a request for both write access and execute access simultaneously. All implementations must support requests for no access, read access, write access, and both read and write access. Strictly conforming code must only rely on the required checks. These restrictions allow for portability across a wide range of hardware.

The MAP_FIXED address treatment is likely to fail for non-page-aligned values and for certain architecture-dependent address ranges. Conforming implementations cannot count on being able to choose address values for MAP_FIXED without utilizing non-portable, implementation-defined knowledge. Nonetheless, MAP_FIXED is provided as a standard interface conforming to existing practice for utilizing such knowledge when it is available.

Similarly, in order to allow implementations that do not support virtual addresses, support for directly specifying any mapping addresses via MAP_FIXED is not required and thus a conforming application may not count on it.

The MAP_PRIVATE function can be implemented efficiently when memory protection hardware is available. When such hardware is not available, implementations can implement such ``mappings'' by simply making a real copy of the relevant data into process private memory, though this tends to behave similarly to read().

The function has been defined to allow for many different models of using shared memory. However, all uses are not equally portable across all machine architectures. In particular, the mmap() function allows the system as well as the application to specify the address at which to map a specific region of a memory object. The most portable way to use the function is always to let the system choose the address, specifying NULL as the value for the argument addr and not to specify MAP_FIXED.

If it is intended that a particular region of a memory object be mapped at the same address in a group of processes (on machines where this is even possible), then MAP_FIXED can be used to pass in the desired mapping address. The system can still be used to choose the desired address if the first such mapping is made without specifying MAP_FIXED, and then the resulting mapping address can be passed to subsequent processes for them to pass in via MAP_FIXED. The availability of a specific address range cannot be guaranteed, in general.

The mmap() function can be used to map a region of memory that is larger than the current size of the object. Memory access within the mapping but beyond the current end of the underlying objects may result in SIGBUS signals being sent to the process. The reason for this is that the size of the object can be manipulated by other processes and can change at any moment. The implementation should tell the application that a memory reference is outside the object where this can be detected; otherwise, written data may be lost and read data may not reflect actual data in the object.

Note that references beyond the end of the object do not extend the object as the new end cannot be determined precisely by most virtual memory hardware. Instead, the size can be directly manipulated by ftruncate().

Process memory locking does apply to shared memory regions, and the MCL_FUTURE argument to mlockall() can be relied upon to cause new shared memory regions to be automatically locked.

Existing implementations of mmap() return the value -1 when unsuccessful. Since the casting of this value to type void * cannot be guaranteed by the ISO C standard to be distinct from a successful value, this volume of POSIX.1‐2017 defines the symbol MAP_FAILED, which a conforming implementation does not return as the result of a successful call.
