mremap(2) Manual de Llamadas al Sistema mremap(2)

NOMBRE

mremap - remapear una dirección de memoria virtual

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

SINOPSIS

#define _GNU_SOURCE         /* Ver feature_test_macros(7) */
#include <sys/mman.h>
void *mremap(size_t old_size;
             void old_address[old_size], size_t old_size,
             size_t new_size, int flags, ...  /* void *new_address */);

DESCRIPCIÓN

mremap() expande (o reduce) un mapeo de memoria existente, posiblemente moviéndolo al mismo tiempo (controlado por el argumento flags y el espacio de direcciones virtuales disponible).

Los mapeos también pueden simplemente moverse (sin ningún cambio de tamaño) especificando old_size y new_size iguales y usando la bandera MREMAP_FIXED (ver abajo). Desde Linux 6.17, mientras que old_address debe ser mapeado, old_size puede abarcar múltiples mapeos incluyendo áreas no mapeadas entre ellos al realizar un simple movimiento. La bandera MREMAP_DONTUNMAP también puede ser especificada.

De manera similar, si la operación realiza una reducción, es decir, si old_size es mayor que new_size, entonces old_size también puede abarcar múltiples mapeos, que no tienen que ser adyacentes entre sí. Si esta reducción se realiza en el lugar, es decir, ni MREMAP_FIXED ni MREMAP_DONTUNMAP se especifican, new_size también puede abarcar múltiples VMAs. Sin embargo, si el rango se mueve, entonces new_size debe abarcar solo un único mapeo.

Si la operación no es un movimiento MREMAP_FIXED ni una reducción, entonces old_size debe abarcar solo un único mapeo.

old_address es la vieja dirección del primer bloque de memoria virtual que deseas expandir, reducir y/o mover. Ten en cuenta que old_address debe estar alineado a página. old_size es el tamaño del rango que contiene los bloques de memoria virtual a manipular. new_size es el tamaño solicitado de los bloques de memoria virtual después del redimensionamiento. Un quinto argumento opcional, new_address, puede ser proporcionado; ver la descripción de MREMAP_FIXED abajo.

Si el valor de old_size es cero, y old_address hace referencia a un mapeo compartible (ver la descripción de MAP_SHARED en mmap(2)), entonces mremap() creará un nuevo mapeo de las mismas páginas. new_size será el tamaño del nuevo mapeo y la ubicación del nuevo mapeo puede ser especificada con new_address; ver la descripción de MREMAP_FIXED abajo. Si se solicita un nuevo mapeo a través de este método, entonces la bandera MREMAP_MAYMOVE también debe ser especificada.

La máscara de bits de argumento flags puede ser 0, o incluir las siguientes banderas:

MREMAP_MAYMOVE
Por defecto, si no hay suficiente espacio para expandir un mapeo en su ubicación actual, entonces mremap() falla. Si esta bandera se especifica, entonces el kernel tiene permiso para reubicar el mapeo a una nueva dirección virtual, si es necesario. Si el mapeo se reubica, entonces los punteros absolutos a la ubicación del viejo mapeo se vuelven inválidos (se deben emplear desplazamientos relativos a la dirección de inicio del mapeo).
MREMAP_FIXED (desde Linux 2.3.31)
Esta bandera tiene un propósito similar a la bandera MAP_FIXED de mmap(2). Si esta bandera se especifica, entonces mremap() acepta un quinto argumento, void *new_address, que especifica una dirección alineada a página a la que el mapeo debe ser movido. Cualquier mapeo previo en el rango de direcciones especificado por new_address y new_size se desmapea.
Si se especifica MREMAP_FIXED, entonces también se debe especificar MREMAP_MAYMOVE.
Desde Linux 6.17, si old_size es igual a new_size y se especifica MREMAP_FIXED, entonces old_size puede extenderse más allá del mapeo en el que reside old_address. En este caso, los huecos entre mapeos en el rango original se mantienen en el rango nuevo. Toda la operación se realiza de forma atómica, a menos que surja un error, en cuyo caso la operación puede completarse parcialmente, es decir, algunos mapeos pueden moverse y otros no.
Mover múltiples mapeos no está permitido si alguno de esos mapeos ha sido registrado con userfaultfd(2), o mapea controladores que especifican su propia lógica de mapeo de direcciones.
MREMAP_DONTUNMAP (desde Linux 5.7)
Esta bandera, que debe usarse junto con MREMAP_MAYMOVE, remapea mapeos a una nueva dirección pero no los desmapea de su dirección original.
La bandera MREMAP_DONTUNMAP solo puede usarse con mapeos que no sean VM_DONTEXPAND o VM_MIXEDMAP. Antes de Linux 5.13, la bandera MREMAP_DONTUNMAP solo podía usarse con mapeos anónimos privados (ver la descripción de MAP_PRIVATE y MAP_ANONYMOUS en mmap(2)).
Después de la finalización, cualquier acceso al rango especificado por old_address y old_size resultará en una falla de página. La falla de página será manejada por un controlador de userfaultfd(2) si la dirección está en un rango previamente registrado con userfaultfd(2). De lo contrario, el kernel asignará una página llena de ceros para manejar la falla.
La bandera MREMAP_DONTUNMAP puede usarse para mover un mapeo atmicamente mientras se deja la fuente mapeada. Ver NOTAS para algunas posibles aplicaciones de MREMAP_DONTUNMAP.

Si los segmentos de memoria especificados por old_address y old_size están bloqueados (usando mlock(2) o similar), entonces este bloqueo se mantiene cuando los segmentos se redimensionan y/o reubican. Como consecuencia, la cantidad de memoria bloqueada por el proceso puede cambiar.

VALOR DE RETORNO

En caso de éxito, mremap() devuelve un puntero al nuevo área de memoria virtual. En caso de error, se devuelve el valor MAP_FAILED (es decir, (void *) -1), y se establece errno para indicar el error.

ERRORES

EAGAIN
El llamador intentó expandir un segmento de memoria que está bloqueado, pero esto no fue posible sin exceder el límite de recursos RLIMIT_MEMLOCK.
EFAULT
Alguna dirección en el rango old_address a old_address+old_size es una dirección de memoria virtual inválida para este proceso. También puedes obtener EFAULT incluso si existen mapeos que cubren todo el espacio de direcciones solicitado, pero esos mapeos son de diferentes tipos, y la operación mremap() que se está realizando no lo soporta.
EINVAL
Se proporcionó un argumento inválido. Posibles causas son:
•
old_address no estaba alineado a página;
•
se especificó un valor distinto de MREMAP_MAYMOVE o MREMAP_FIXED o MREMAP_DONTUNMAP en flags;
•
new_size era cero;
•
new_size o new_address eran inválidos;
•
el nuevo rango de direcciones especificado por new_address y new_size se solapaba con el viejo rango de direcciones especificado por old_address y old_size;
•
se especificó MREMAP_FIXED o MREMAP_DONTUNMAP sin también especificar MREMAP_MAYMOVE;
•
se especificó MREMAP_DONTUNMAP, pero una o más páginas en el rango especificado por old_address y old_size no eran anónimas privadas;
•
se especificó MREMAP_DONTUNMAP y old_size no era igual a new_size;
•
old_size era cero y old_address

> no se refiere a un mapeo compartible (pero ver BUGS);
•
old_size era cero y el flag MREMAP_MAYMOVE no fue especificado.
ENOMEM
No había suficiente memoria disponible para completar la operación. Las causas posibles son:
•
El área de memoria no puede ser expandida en la dirección virtual actual, y el flag MREMAP_MAYMOVE no está establecido en flags. O, no hay suficiente memoria (virtual) disponible.
•
Se utilizó MREMAP_DONTUNMAP provocando que se creara un nuevo mapeo que excedería la memoria (virtual) disponible. O, excedería el número máximo de mapeos permitidos.

ESTÁNDARES

Linux.

HISTORIA

Antes de glibc 2.4, glibc no exponía la definición de MREMAP_FIXED, y el prototipo para mremap() no permitía el argumento new_address.

NOTAS

mremap() cambia el mapeo entre direcciones virtuales y páginas de memoria. Esto se puede usar para implementar un realloc(3) muy eficiente.

En Linux, la memoria se divide en páginas. Un proceso tiene (uno o) varios segmentos de memoria virtual lineal. Cada segmento de memoria virtual tiene uno o más mapeos a páginas de memoria real (en la tabla de páginas). Cada segmento de memoria virtual tiene su propia protección (derechos de acceso), que puede causar una violación de segmentación (SIGSEGV) si la memoria se accede incorrectamente (por ejemplo, escribiendo en un segmento de solo lectura). Acceder a memoria virtual fuera de los segmentos también causará una violación de segmentación.

Si mremap() se utiliza para mover o expandir un área bloqueada con mlock(2) o equivalente, la llamada mremap() hará un esfuerzo para poblar el nuevo área pero no fallará con ENOMEM si el área no puede ser poblada.

Casos de uso de MREMAP_DONTUNMAP

Las posibles aplicaciones para MREMAP_DONTUNMAP incluyen:

•
userfaultfd(2) no cooperativo: una aplicación puede extraer un rango de direcciones virtuales usando MREMAP_DONTUNMAP y luego emplear un manejador de userfaultfd(2) para manejar las fallas de página que ocurren posteriormente a medida que otros hilos en el proceso acceden a páginas en el rango extraído.
•
Recolección de basura: MREMAP_DONTUNMAP se puede usar en conjunto con userfaultfd(2) para implementar algoritmos de recolección de basura (por ejemplo, en una máquina virtual Java). Dicha implementación puede ser más barata (y más simple) que las técnicas convencionales de recolección de basura que implican marcar páginas con protección PROT_NONE junto con el uso de un manejador de SIGSEGV para capturar accesos a esas páginas.

BUGS

Antes de Linux 4.14, si old_size era cero y el mapeo referido por old_address era un mapeo privado (ver la descripción de MAP_PRIVATE en mmap(2)), mremap() creaba un nuevo mapeo privado no relacionado con el mapeo original. Este comportamiento no era intencional y probablemente inesperado en aplicaciones de espacio de usuario (ya que la intención de mremap() es crear un nuevo mapeo basado en el mapeo original). Desde Linux 4.14, mremap() falla con el error EINVAL en este escenario.
