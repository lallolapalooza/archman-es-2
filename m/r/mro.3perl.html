mro(3perl) Guía de referencia para programadores de Perl mro(3perl)

NOMBRE

mro - Orden de resolución de métodos

SINOPSIS

use mro; # habilita next::method y similares globalmente
use mro 'dfs'; # habilita MRO DFS para esta clase (por defecto de Perl)
use mro 'c3'; # habilita MRO C3 para esta clase

DESCRIPCIÓN

El espacio de nombres "mro" proporciona varias utilidades para tratar con el orden de resolución de métodos y el almacenamiento en caché de métodos en general.

Estas interfaces solo están disponibles en Perl 5.9.5 y superior. Consulta MRO::Compat en CPAN para una implementación mayormente compatible con versiones anteriores para Perls más antiguas.

VISIÓN GENERAL

Es posible cambiar el MRO de una clase dada ya sea usando "use mro" como se muestra en la sinopsis, o usando la función "mro::set_mro" a continuación.

Los métodos especiales "next::method", "next::can", y "maybe::next::method" no están disponibles hasta que este módulo "mro" haya sido cargado a través de "use" o "require".

El MRO C3

Además del MRO por defecto tradicional de Perl (búsqueda en profundidad, llamado "DFS" aquí), Perl ahora también ofrece el MRO C3. El soporte de Perl para C3 se basa en el trabajo realizado en el módulo Class::C3 de Stevan Little, y la mayor parte de la documentación relacionada con C3 aquí se extrae directamente de allí.

¿Qué es C3?

C3 es el nombre de un algoritmo que tiene como objetivo proporcionar un orden de resolución de métodos sensato bajo herencia múltiple. Fue introducido por primera vez en el lenguaje Dylan (ver enlaces en la sección "VER TAMBIÉN"), y luego adoptado como el MRO (Orden de Resolución de Métodos) preferido para las clases de nuevo estilo en Python 2.3. Más recientemente, ha sido adoptado como el MRO "canónico" para las clases Raku.

¿Cómo funciona C3?

C3 funciona preservando siempre el orden de precedencia local. Esto esencialmente significa que ninguna clase aparecerá antes que ninguna de sus subclases. Tomemos, por ejemplo, el patrón clásico de herencia en diamante:

   <A>
  /   \
<B>   <C>
  \   /
   <D>

El MRO estándar de Perl 5 sería (D, B, A, C). El resultado es que A aparece antes que C, aunque C es la subclase de A. El algoritmo MRO C3, sin embargo, produce el siguiente orden: (D, B, C, A), que no tiene este problema.

Este ejemplo es bastante trivial; para casos más complejos y una explicación más profunda, consulta los enlaces en la sección "VER TAMBIÉN".

Funciones

mro::get_linear_isa($classname[, $type])

Devuelve una referencia de array que es el MRO linealizado de la clase dada. Utiliza el MRO que esté actualmente en vigor para esa clase por defecto, o el MRO dado (ya sea "c3" o "dfs" si se especifica como $type).

El MRO linealizado de una clase es un array ordenado de todas las clases que se buscarían al resolver un método en esa clase, comenzando por la clase misma.

Si la clase solicitada aún no existe, esta función aún tendrá éxito y devolverá "[ $classname ]"

Ten en cuenta que "UNIVERSAL" (y cualquier miembro del MRO de "UNIVERSAL") no forman parte del MRO de una clase, aunque todas las clases hereden implícitamente métodos de "UNIVERSAL" y sus padres.

mro::set_mro($classname, $type)

Establece el MRO de la clase dada al argumento $type (ya sea "c3" o "dfs").

mro::get_mro($classname)

Devuelve el MRO de la clase dada (ya sea "c3" o "dfs").

mro::get_isarev($classname)

Obtiene el "mro_isarev" para esta clase, devuelto como una referencia de array de nombres de clase. Estas son todas las clases que "isa" el nombre de clase dado, incluso si la relación isa es indirecta. Esto se usa internamente en el código MRO para realizar un seguimiento de las invalidaciones de caché de métodos/MRO.

Al igual que con "mro::get_linear_isa" arriba, "UNIVERSAL" es especial. Las listas isarev de "UNIVERSAL" (y de sus padres) no incluyen todas las clases existentes, aunque todas las clases son efectivamente descendientes a efectos de herencia de métodos.

mro::is_universal($classname)

Devuelve un estado booleano que indica si el nombre de clase dado es "UNIVERSAL" en sí mismo, o uno de los padres de "UNIVERSAL" por herencia @ISA.

Cualquier clase para la que esta función devuelva verdadero es "universal" en el sentido de que todas las clases potencialmente heredan métodos de ella.

mro::invalidate_all_method_caches()

Incrementa "PL_sub_generation", lo que invalida el almacenamiento en caché de métodos en todos los paquetes.

mro::method_changed_in($classname)

Invalida la caché de métodos de cualquier clase dependiente de la clase dada. Esto no es normalmente necesario. El único caso conocido en el que el código perl puro puede confundir la caché de métodos es cuando se instala manualmente un nuevo subrutina constante usando un valor escalar de solo lectura, como los internos de constant. Si encuentras otro caso, por favor repórtalo para que podamos solucionarlo o documentar la excepción aquí.

mro::get_pkg_gen($classname)

Devuelve un entero que se incrementa cada vez que cambia un método local real en el paquete $classname, o se modifica el @ISA local de $classname.

Esto está pensado para autores de módulos que realizan mucha introspección de clases, ya que les permite comprobar muy rápidamente si algo importante sobre las propiedades locales de una clase dada ha cambiado desde la última vez que miraron. No se incrementa en cambios de método/@ISA en superclases.

Todavía depende de ti buscar los cambios reales, y puede que no haya ninguno. Quizás todos los cambios desde la última vez que comprobaste se cancelaron mutuamente y dejaron el paquete en el estado en que estaba antes.

Este entero normalmente comienza con un valor de 1 cuando se instancia un stash de paquete. Llamarlo en paquetes cuyos stashes no existen en absoluto devolverá 0. Si un stash de paquete se elimina por completo (lo cual no es una ocurrencia normal, pero puede suceder si alguien hace algo como "undef %PkgName::"), el número se restablecerá a 0 o 1, dependiendo de cuán completamente se haya borrado el paquete.

next::method

Esto es algo parecido a "SUPER", pero utiliza el orden de resolución de métodos C3 para obtener una mejor consistencia en situaciones de herencia múltiple. Nota

mro.3perl man page

NAME

MRO::Method - Provide next::method functionality

SYNOPSIS

    use MRO::Method;
                    # or
                    use base 'MRO::Method';

DESCRIPTION

This module provides the next::method and next::can functions that are commonly used in object-oriented Perl for accessing superclass methods. This module implements the C3 linearization algorithm for method resolution.

OVERVIEW

This module is intended to be used in one of two ways:

  • As a base class: 
        package MyClass;
                            use base 'MRO::Method';
                            sub foo {
                                my $self = shift;
                                $self->next::method(@_);
                            }
  • By importing the functions: 
        package MyClass;
                            use MRO::Method 'next::method', 'next::can';
                            sub foo {
                                my $self = shift;
                                $self->next::method(@_);
                            }

In either case, the behavior is the same. The "next::method" call will invoke the method that comes next in the Method Resolution Order (MRO) after the current method.

The C3 MRO

The C3 MRO algorithm is a method resolution order that guarantees linearization for multiple inheritance, regardless of the order of base classes. It is widely used in object-oriented languages like Python and Dylan.

While inheritance in general follows whichever MRO is in effect for the given class, "next::method" only uses the C3 MRO.

One generally uses it like so:

    sub some_method {
                        my $self = shift;
                        my $superclass_answer = $self->next::method(@_);
                        return $superclass_answer + 1;
                    }

Note that you don't (re-)specify the method name. It forces you to always use the same method name as the method you started in.

It can be called on an object or a class, of course.

The way it resolves which actual method to call is:

1.
First, it determines the linearized C3 MRO of the object or class it is being called on.
2.
Then, it determines the class and method name of the context it was invoked from.
3.
Finally, it searches down the C3 MRO list until it reaches the contextually enclosing class, then searches further down the MRO list for the next method with the same name as the contextually enclosing method.

Failure to find a next method will result in an exception being thrown (see below for alternatives).

This is substantially different than the behavior of "SUPER" under complex multiple inheritance. (This becomes obvious when one realizes that the common superclasses in the C3 linearizations of a given class and one of its parents will not always be ordered the same for both.)

Caveat: Calling "next::method" from methods defined outside the class:

There is an edge case when using "next::method" from within a subroutine which was created in a different module than the one it is called from. It sounds complicated, but it really isn't. Here is an example which will not work correctly:

*Foo::foo = sub { (shift)->next::method(@_) };

The problem exists because the anonymous subroutine being assigned to the *Foo::foo glob will show up in the call stack as being called "__ANON__" and not "foo" as you might expect. Since "next::method" uses "caller" to find the name of the method it was called in, it will fail in this case.

But fear not, there's a simple solution. The module "Sub::Name" will reach into the perl internals and assign a name to an anonymous subroutine for you. Simply do this:

    use Sub::Name 'subname';
                    *Foo::foo = subname 'Foo::foo' => sub { (shift)->next::method(@_) };

and things will Just Work.

next::can

This is similar to "next::method", but just returns either a code reference or "undef" to indicate that no further methods of this name exist.

maybe::next::method

In simple cases, it is equivalent to:

    $self->next::method(@_) if $self->next::can;

But there are some cases where only this solution works (like "goto &maybe::next::method");
