MISE(1) Manual de comandos generales MISE(1)

NOMBRE

mise - El frontend para tu entorno de desarrollo

SINOPSIS

mise [OPCIONES] [<TAREA>] [<ARGS_TAREA>] ... [<ARGS_TAREA_ULTIMA>] ... [COMANDO]

DESCRIPCIÓN

mise gestiona herramientas de desarrollo, variables de entorno y ejecuta tareas. https://github.com/jdx/mise

OPCIONES

MISE ACTIVATE

Inicializa mise en la sesión de shell actual

Esto debe ir en el archivo rc de tu shell o en el shell de inicio de sesión. De lo contrario, solo tendrá efecto en la sesión actual. (por ejemplo, ~/.zshrc, ~/.zprofile, ~/.zshenv, ~/.bashrc, ~/.bash_profile, ~/.profile, ~/.config/fish/config.fish, o $PROFILE para powershell)

Típicamente, esto se puede añadir con algo como lo siguiente:


echo 'eval "$(mise activate zsh)"' >> ~/.zshrc

Sin embargo, esto requiere que "mise" esté en tu PATH. Si no lo está, necesitas especificar la ruta completa así:


echo 'eval "$(/path/to/mise activate zsh)"' >> ~/.zshrc

Personaliza la salida de estado con la configuración `status`.

Uso: mise activate [OPCIONES] [<TIPO_SHELL>]

Opciones:

-q, --quiet
Suprime mensajes que no sean de error
-s, --shell <SHELL>
Tipo de shell para el que generar el script
--no-hook-env
No llama automáticamente a hook-env

Esto puede ser útil para depurar mise. Si ejecutas `eval "$(mise activate --no-hook-env)"`, entonces puedes llamar a `mise hook-env` manualmente, lo que mostrará las variables de entorno en la salida estándar sin modificar realmente el entorno. De esa manera puedes hacer cosas como `mise hook-env --trace` para obtener más información o simplemente ver los valores que hook-env está mostrando.

--shims
Usa shims en lugar de modificar PATH. Efectivamente lo mismo que:


PATH="$HOME/.local/share/mise/shims:$PATH"

`mise activate --shims` no soporta todas las características de `mise activate`. Ver https://mise.jdx.dev/dev-tools/shims.html#shims-vs-path para más información

--status
Muestra el mensaje "mise: <PLUGIN>@<VERSION>" al cambiar de
ng directories Argumentos:
<TIPO_DE_SHELL>
Tipo de shell para el que generar el script

MISE COMPLETION

Uso: mise completion [OPCIONES] [<SHELL>]

Opciones:

-s, --shell <TIPO_DE_SHELL>
Tipo de shell para el que generar completados
--include-bash-completion-lib
Incluir la biblioteca de completado de bash en el script de completado de bash.

Esto es necesario para que los completados funcionen en bash, pero no está incluido por defecto. Puedes cargarlo por separado o habilitar esta opción para habilitarlo en el script.

--usage
Usar siempre `usage` para los completados. Actualmente, `usage` es el valor predeterminado para fish y bash, pero no para zsh, ya que tiene algunas peculiaridades que resolver primero.

Esto requiere que la CLI `usage` esté instalada. https://usage.jdx.dev Argumentos:

<SHELL>

Esta es una alternativa a `mise activate` que te permite iniciar explícitamente una sesión de mise. Tendrá las herramientas y variables de entorno de las configuraciones cargadas. Ten en cuenta que cambiar de directorio no actualizará el entorno de mise.

Uso: mise en [OPCIONES] [<DIR>]

Opciones:

-s, --shell <SHELL>
Shell a iniciar.

Por defecto es $SHELL Argumentos:

<DIR>
Directorio en el que iniciar el shell
Por defecto: .

MISE TOOL-STUB

A tool stub is a simple file that runs a specific tool version. These are typically used for one-off commands that need a specific tool version. For example, running `node@20` without needing to modify your `mise.toml`.

Mise has built-in support for creating and executing tool stubs. They are implemented as TOML files with a special shebang line that automatically manages tool installation and execution.

A tool stub consists of: - A shebang line: #!/usr/bin/env -S mise tool-stub - TOML configuration specifying the tool, version, and options - Optional comments describing the tool's purpose

tool = "node" version = "20.0.0" bin = "node"

The stub will automatically install the specified tool version if missing and execute it with any arguments passed to the stub.

For more information, see: https://mise.jdx.dev/dev-tools/tool-stubs.html

Usage: mise tool-stub <FILE> [<ARGS>] ...

Arguments:

<FILE>
Path to the TOML tool stub file to execute

The stub file must contain TOML configuration specifying the tool and version to run. At minimum, it should specify a 'version' field. Other common fields include 'tool', 'bin', and backend-specific options.

<ARGS>
Arguments to pass to the tool

All arguments after the stub file path will be forwarded to the underlying tool. Use '--' to separate mise arguments from tool arguments if needed.

-o, --on-busy-update <MODE>
What to do when receiving events while the command is running

Default is to 'do-nothing', which ignores events while the command is running, so that changes that occur due to the command are ignored, like compilation outputs. You can also use 'queue' which will run the command once again when the current run has finished if any events occur while it's running, or 'restart', which terminates the running command and starts a new one. Finally, there's 'signal', which only sends a signal; this can be useful with programs that can reload their configuration without a full restart.

The signal can be specified with the '--signal' option.

-r, --restart
Restart the process if it's still running

This is a shorthand for '--on-busy-update=restart'.

Specify a signal to send to the process when it's still running. This implies '--on-busy-update=signal'; otherwise the signal used when that mode is 'restart' is controlled by '--stop-signal'.

See the long documentation for '--stop-signal' for syntax.

Signals are not supported on Windows at the moment, and will always be overridden to 'kill'. See '--stop-signal' for more on Windows "signals".

--stop-signal <SIGNAL>
Signal to send to stop the command

This is used by 'restart' and 'signal' modes of '--on-busy-update' (unless '--signal' is provided). The restart behaviour is to send the signal, wait for the command to exit, and if it hasn't exited after some time (see '--timeout-stop'), forcefully terminate it.

The default on unix is "SIGTERM".

Input is parsed as a full signal name (like "SIGTERM"), a short signal name (like "TERM"), or a signal number (like "15"). All input is case-insensitive.

On Windows this option is technically supported but only supports the "KILL" event, as Watchexec cannot yet deliver other events. Windows doesn't have signals as such; instead it has termination (here called "KILL" or "STOP") and "CTRL+C", "CTRL+BREAK", and "CTRL+CLOSE" events. For portability the unix signals "SIGKILL", "SIGINT", "SIGTERM", and "SIGHUP" are respectively mapped to these.

--stop-timeout <TIMEOUT>
Time to wait for the command to exit gracefully

This is used by the 'restart' mode of '--on-busy-update'. After the graceful stop signal is sent, Watchexec will wait for the command to exit. If it hasn't exited after this time, it is forcefully terminated.

Takes a unit-less value in seconds, or a time span value such as "5min 20s". Providing a unit-less value is deprecated and will warn; it will be an error in the future.

The default is 10 seconds. Set to 0 to immediately force-kill the command.

This has no practical effect on Windows as the command is always forcefully terminated; see '--stop-signal' for why.

--map-signal <SIGNAL:SIGNAL>
Translate signals from the OS to signals to send to the command

Takes a pair of signal names, separated by a colon, such as "TERM:INT" to map SIGTERM to SIGINT. The first signal is the one received by watchexec, and the second is the one sent to the command. The second can be omitted to discard the first signal, such as "TERM:" to not do anything on SIGTERM.

If SIGINT or SIGTERM are mapped, then they no longer quit Watchexec. Besides making it hard to quit Watchexec itself, this is useful to send pass a Ctrl-C to the command without also terminating Watchexec and the underlying program with it, e.g. with "INT:INT".

This option can be specified multiple times to map multiple signals.

Signal syntax is case-insensitive for short names (like "TERM", "USR2") and long names (like "SIGKILL", "SIGHUP"). Signal numbers are also supported (like "15", "31"). On Windows, the forms "STOP", "CTRL+C", and "CTRL+BREAK" are also supported to receive, but Watchexec cannot yet deliver other "signals" than a STOP.

-d, --debounce <TIMEOUT>
Time to wait for new events before taking action

When an event is received, Watchexec will wait for up to this amount of time before handling it (such as running the command). This is essential as what you might perceive as a single change may actually emit many events, and without this behaviour, Watchexec would run much too often. Additionally, it's not infrequent that file writes are not atomic, and each write may emit an event, so this is a good way to avoid running a command while a file is partially written.

An alternative use is to set a high value (like "30min" or longer), to save power or bandwidth on intensive tasks, like an ad-hoc backup script. In those use cases, note that every accumulated event will build up in memory.

Takes a unit-less value in milliseconds, or a time span value such as "5sec 20ms". Providing a unit-less value is deprecated and will warn; it will be an error in the future.

The default is 50 milliseconds. Setting to 0 is highly discouraged.

--stdin-quit
Exit when stdin closes

This watches the stdin file descriptor for EOF, and exits Watchexec gracefully when it is closed. This is used by some process managers to avoid leaving zombie processes around.

--no-vcs-ignore
Don't load gitignores

Among other VCS exclude files, like for Mercurial, Subversion, Bazaar, DARCS, Fossil. Note that Watchexec will detect which of these is in use, if any, and only load the relevant files. Both global (like '~/.gitignore') and local (like '.gitignore') files are considered.

This option is useful if you want to watch files that are ignored by Git.

--no-project-ignore

This disables loading of project-local ignore files, like '.gitignore' or '.ignore' in the watched project. This is contrasted with '--no-vcs-ignore', which disables loading of Git and other VCS ignore files, and with '--no-global-ignore', which disables loading of global or user ignore files, like '~/.gitignore' or '~/.config/watchexec/ignore'.

El valor especial 'none' se puede usar para deshabilitar el uso del shell por completo. Usar con CMD.exe:

$ watchexec --shell=cmd -- dir

Usar con un shell unix diferente:

$ watchexec --shell=bash -- 'echo $BASH_VERSION'

Usar con un shell unix y opciones:

$ watchexec --shell='zsh -x -o shwordsplit' -- scr

--emit-events-to <MODE>
Configurar emisión de eventos

Watchexec puede emitir información de eventos al ejecutar un comando, lo que puede ser utilizado por el proceso hijo para dirigirse a archivos modificados específicos.

Una cosa a tener en cuenta es asumir un comportamiento inherente donde solo hay una posibilidad. En particular, podría parecer que la variable `RENAMED` contiene tanto la ruta original como la nueva ruta renombrada. En versiones anteriores, incluso parecía en algunas plataformas que la original siempre venía antes que la nueva. Sin embargo, nada de esto era cierto. Es imposible saber de manera confiable y portable cuál de las rutas cambiadas es la antigua o la nueva, pueden aparecer "renombrados a medias" (solo el original, solo el nuevo), renombrados "desconocidos" (el cambio fue un renombrado, pero no se sabe si fue el antiguo o el nuevo), los eventos de renombrado pueden dividirse en dos límites de agrupamiento, y así sucesivamente.

Esta opción controla dónde se emite esa información. Por defecto es 'none', que no emite información de eventos en absoluto. Las otras opciones son 'environment' (obsoleto), 'stdio', 'file', 'json-stdio' y 'json-file'.

Los modos 'stdio' y 'file' son basados en texto: 'stdio' escribe rutas absolutas en la entrada estándar del comando, una por línea, cada una prefijada con `create:`, `remove:`, `rename:`, `modify:`, o `other:`, luego cierra el manejador; 'file' escribe lo mismo en un archivo temporal, y su ruta se proporciona con la variable de entorno $WATCHEXEC_EVENTS_FILE.

También hay dos modos JSON, que se basan en objetos JSON y pueden representar el conjunto completo de eventos que Watchexec maneja. Aquí tienes un ejemplo de una carpeta que se crea en Linux:

```json
{
"tags": [
{
"kind": "path",
"absolute": "/home/user/your/new-folder",
"filetype": "dir"
},
{
"kind": "fs",
"simple": "create",
"full": "Create(Folder)"
},
{
"kind": "source",
"source": "filesystem"
}
],
"metadata": {
"notify-backend": "inotify"
}
} ```

Los campos son los siguientes:


- `tags`, datos de eventos estructurados.
- `tags[].kind`, que puede ser:
* 'path', junto con:
+ `absolute`, una ruta absoluta.
+ `filetype`, un tipo de archivo si se conoce ('dir', 'file', 'symlink', 'other').
* 'fs':
+ `simple`, el tipo de evento "simple" ('access', 'create', 'modify', 'remove' u 'other').
+ `full`, el tipo de evento "completo", que es demasiado complejo para describirlo completamente aquí, pero se ve como 'General(Precise(Specific))'.
* 'source', junto con:
+ `source`, la fuente del evento ('filesystem', 'keyboard', 'mouse', 'os', 'time', 'internal').
* 'keyboard', junto con:
+ `keycode`. Actualmente solo se admite el valor 'eof'.
* 'process', para eventos causados por procesos:
+ `pid`, el ID del proceso.
* 'signal', para señales enviadas a Watchexec:
+ `signal`, el nombre de señal normalizado ('hangup', 'interrupt', 'quit', 'terminate', 'user1', 'user2').
* 'completion', cuando un comando termina:
+ `disposition`, la disposición de salida ('success', 'error', 'signal', 'stop', 'exception', 'continued').
+ `code`, el código de salida, señal, parada o excepción.
- `metadata`, información adicional sobre el evento.

El modo 'json-stdio' emitirá eventos JSON a la entrada estándar del comando, uno por línea, y luego cerrará la entrada estándar. El modo 'json-file' creará un archivo temporal, escribirá los eventos en él y proporcionará la ruta del archivo con $WATC

--environment

This mode is the legacy default until version 2.0. It sets environment variables with the paths of the affected files for filesystem events:

$WATCHEXEC_COMMON_PATH se establece en la ruta común más larga de todas las variables siguientes, y por lo tanto, debe anteponerse a cada ruta para obtener la ruta completa/real. Luego:


- $WATCHEXEC_CREATED_PATH se establece cuando se crean archivos/carpetas
- $WATCHEXEC_REMOVED_PATH se establece cuando se eliminan archivos/carpetas
- $WATCHEXEC_RENAMED_PATH se establece cuando se renombran archivos/carpetas
- $WATCHEXEC_WRITTEN_PATH se establece cuando se modifican archivos/carpetas
- $WATCHEXEC_META_CHANGED_PATH se establece cuando se modifica la metainformación de archivos/carpetas
- $WATCHEXEC_OTHERWISE_CHANGED_PATH se establece para cualquier otro tipo de evento de ruta

Las rutas múltiples se separan por el separador de rutas del sistema, ';' en Windows y ':' en Unix. Dentro de cada variable, las rutas se desduplican y se ordenan en orden binario (es decir, no son conscientes ni de Unicode ni de la configuración regional).

Este es el modo heredado, está obsoleto y se eliminará en el futuro. El entorno es un espacio muy restringido, al tiempo que limita lo que puede representar útilmente. Un gran número de archivos provocará el truncamiento del entorno, o puede generar errores o bloquear el proceso por completo. La variable $WATCHEXEC_COMMON_PATH también es poco intuitiva, como lo demuestran las múltiples consultas confusas que han llegado a mi bandeja de entrada a lo largo de los años.

-J, --filter-prog <EXPRESION>
[experimental] Programas de filtro.

/!\ Esta opción es EXPERIMENTAL y puede cambiar y/o desaparecer sin previo aviso.

Proporcione sus propios programas de filtro personalizados en sintaxis jaq (similar a jq). A los programas se les da un evento en el mismo formato que se describe en '--emit-events-to' y deben devolver un booleano. Los programas inválidos harán que watchexec falle al iniciar; use '-v' para ver los errores de tiempo de ejecución del programa.

Además de la biblioteca estándar de jaq, watchexec agrega algunas definiciones de filtro personalizadas:

- 'path | file_meta' devuelve la metainformación del archivo o null si el archivo no existe.

- 'path | file_size' devuelve el tamaño del archivo en la ruta, o null si no existe.

- 'path | file_read(bytes)' devuelve una cadena con los primeros n bytes del archivo en la ruta. Si el archivo es menor que n bytes, se devuelve el archivo completo. No hay un filtro para leer el archivo completo a la vez para fomentar la limitación de la cantidad de datos leídos y procesados.

- 'string | hash', y 'path | file_hash' devuelven el hash de la cadena o el archivo en la ruta. No se garantiza el algoritmo utilizado: trátelo como un valor opaco.

- 'any | kv_store(key)', 'kv_fetch(key)', y 'kv_clear' proporcionan un simple almacén de clave-valor. Los datos se mantienen solo en memoria, no hay persistencia. La consistencia no está garantizada.

- 'any | printout', 'any | printerr', y 'any | log(level)' imprimirán o registrarán cualquier valor dado en stdout, stderr o el registro (niveles = error, advertencia, info, depuración, rastreo), y pasarán el valor (así '[1] | log("debug") | .[]' producirá un '1' y registrará '[1]').

Todo el filtrado realizado con dichos programas, y especialmente aquellos que usan acceso kv o al sistema de archivos, es mucho más lento que los otros métodos de filtrado. Si el filtrado es demasiado lento, los eventos se acumularán y detendrán watchexec. Tenga cuidado al diseñar sus filtros.

Si el argumento de esta opción comienza con '@', el resto del argumento se toma como la ruta a un archivo que contiene un programa jaq.

Los programas Jaq se ejecutan en orden, después de todos los demás filtros, y se cortocircuitan: si un filtro (jaq o no) rechaza un evento, la ejecución se detiene allí, y no se ejecutan otros filtros. Además, se detienen después de emitir el primer valor, por lo que querrá usar 'any' o 'all' al iterar, de lo contrario, solo se procesará el primer elemento, ¡lo que puede ser bastante confuso!

Encuentre programas contribuidos por usuarios o envíe los suyos propios útiles en https://github.com/watchexec/watchexec/discussions/592.
