DESCRIPCIÓN

Este es un conjunto de herramientas para administrar clases de almacenamiento de MooseFS. Las clases de almacenamiento se utilizan para definir la política de redundancia dentro del clúster. Posteriormente, se aplicarán a objetos particulares de MooseFS (archivos o carpetas) con las herramientas mfssclass (ver mfssclass(1)). Una clase de almacenamiento es un conjunto con nombre de expresiones de etiquetas y algunas otras opciones. La expresión de etiquetas indica el formato de redundancia, el nivel de redundancia deseado y la política de almacenamiento deseada. El formato de redundancia puede ser copias o codificación de borrado (EC). El nivel de redundancia es el número de copias (de 1 a 9) o el número de partes de datos más paridad (4+n u 8+n), dependiendo del formato de redundancia indicado. La política de almacenamiento especifica, mediante el uso de etiquetas, qué servidores de fragmentos se utilizarán para el almacenamiento físico de los datos asignados a la clase de almacenamiento particular.

mfscreatesclass crea una nueva clase de almacenamiento con las opciones dadas, descritas a continuación, y la nombra NOMBRE_CLASE_ALMACENAMIENTO; se pueden proporcionar varios nombres, en cuyo caso se crearán varias clases de almacenamiento con la misma definición.

mfsmodifysclass cambia las opciones dadas en una clase o clases indicadas por los parámetros NOMBRE_CLASE_ALMACENAMIENTO.

mfsdeletesclass elimina la clase o clases indicadas por los parámetros NOMBRE_CLASE_ALMACENAMIENTO; si alguna de las clases no está vacía (es decir, todavía está siendo utilizada por algunos objetos de MooseFS), no se eliminará y la herramienta devolverá un error y se imprimirá un mensaje de error; las clases vacías se eliminarán en cualquier caso.

mfsclonesclass copia la clase indicada por NOMBRE_CLASE_ALMACENAMIENTO_ORIGEN bajo un nuevo nombre proporcionado con NOMBRE_CLASE_ALMACENAMIENTO_DESTINO.

mfsrenamesclass cambia el nombre de una clase de NOMBRE_CLASE_ALMACENAMIENTO_ORIGEN a NOMBRE_CLASE_ALMACENAMIENTO_DESTINO.

mfslistsclass lista todas las clases.

mfsimportsclass importa definiciones de clases de almacenamiento desde stdin o un archivo y las crea; el formato de entrada debe ser idéntico a la salida de mfslistsclass -l.

OPCIONES

-C parámetro opcional, que indica al sistema a qué servidores de fragmentos, definidos por la expresión CREATE_LABELS, se debe escribir primero el fragmento justo después de su creación; si no se proporciona este parámetro para una clase, se utilizarán los servidores de fragmentos KEEP_LABELS.

-K parámetro obligatorio, que indica al sistema en qué servidores de fragmentos, definidos por la expresión KEEP_LABELS, se deben mantener siempre los fragmentos, excepto en condiciones especiales como la creación, el archivado y la eliminación (movimiento a la Papelera), si están definidas.

-A parámetro opcional, que indica al sistema en qué servidores de fragmentos, definidos por la expresión ARCH_LABELS, se deben mantener los fragmentos para fines de archivado; el sistema comienza a tratar un fragmento como archivo cuando el atime/mtime/ctime (según lo establecido por -o) del archivo al que pertenece es anterior al número de horas especificado con la opción -d; ver también la sección COMPORTAMIENTO DE ARCHIVO a continuación.

-d parámetro opcional que define después de cuánto tiempo desde atime/mtime/ctime (según lo establecido por -o) un archivo (y sus fragmentos) se trata como archivo; la unidad mínima es horas, el valor predeterminado es 24, para el formato de valor vea TIEMPO.

-o parámetro opcional que define las banderas de archivo. C - ctime, M - mtime, A - atime, R - reversible, F - modo rápido, P - por fragmento; el valor predeterminado es C; ver la sección COMPORTAMIENTO DE ARCHIVO para más detalles.

-s parámetro opcional que define la longitud mínima del archivo en bytes que se puede archivar; el valor predeterminado es 0.

-T parámetro opcional, que indica al sistema en qué servidores de fragmentos, definidos por la expresión TRASH_LABELS, se deben mantener los fragmentos de los archivos en la Papelera; ver también -t.

-t parámetro opcional, que define cuánto tiempo en la Papelera debe transcurrir para que el sistema utilice realmente el esquema definido en -T para un fragmento; la unidad mínima es horas, el valor predeterminado es 0, para el formato de valor vea TIEMPO.

-c parámetro opcional, que define una descripción de la clase, para conveniencia del usuario (una cadena, longitud máxima 255 bytes).

-p parámetro opcional, que define la prioridad de una clase; el valor predeterminado es 0, ver la sección PRIORIDAD DE CLASES DE ALMACENAMIENTO.

-g parámetro opcional, que define un grupo de exportación de clase; los valores posibles son de 0 a 15, el valor predeterminado es 0; ver mfsexport.cfg(5) para una explicación.

-a puede ser 1 o 0 e indica si la clase de almacenamiento está disponible para todos (0) o solo para administradores (1).

-m modo de etiquetas utilizado; los valores posibles son l (o L, loose, Loose, LOOSE) para el modo LOOSE, d (o D, std, Std, STD) para el modo STANDARD y s (o S, strict, Strict, STRICT) para el modo STRICT; si no se define ningún modo, se asume el modo STANDARD; el comportamiento de los modos de etiquetas se describe a continuación en la sección MODOS DE ETIQUETAS.

-l lista también las definiciones, no solo los nombres de las clases de almacenamiento existentes.

-i coincidencia de nombres de clases de almacenamiento insensible a mayúsculas y minúsculas.

-r reemplaza (sobrescribe) las clases existentes al importar clases de almacenamiento.

-n utiliza el nombre de archivo proporcionado como fuente de definiciones de clases de almacenamiento para importar, en lugar de stdin.

-M punto de montaje de MooseFS, no es necesario especificarlo si una herramienta se ejecuta dentro de un directorio montado en MooseFS o si MooseFS está montado en /mnt/mfs/.

-? muestra un mensaje de uso corto.

NOTAS

EXPRESIONES DE ETIQUETAS

Las etiquetas son letras (A-Z - 26 letras) que se pueden asignar a los servidores de fragmentos. Cada servidor de fragmentos puede tener múltiples (hasta 26) etiquetas. Las etiquetas se definen en el archivo mfschunkserver.cfg, para más información consulte la página del manual correspondiente.

Una expresión de etiquetas es un conjunto de subexpresiones separadas por comas. Para copias completas, cada subexpresión especifica el esquema de almacenamiento de una copia de un archivo. La subexpresión puede ser: un asterisco o un esquema de etiquetas. Un esquema de etiquetas puede ser una etiqueta o una expresión con sumas, multiplicaciones, negaciones y paréntesis. La suma significa que un archivo puede almacenarse en cualquier servidor de fragmentos que coincida con cualquier elemento de la suma (o lógico). La multiplicación significa que un archivo solo puede almacenarse en un servidor de fragmentos que coincida con todos los elementos (y lógico). Un asterisco significa cualquier servidor de fragmentos. La negación significa cualquier servidor de fragmentos excepto el que coincide con la subexpresión negada. Las subexpresiones idénticas se pueden acortar añadiendo un número delante de una en lugar de repetirla varias veces.

Para EC, la expresión de etiquetas comienza con el signo @, seguido del número de partes de datos, luego el signo + y un número que indica cuántas partes de paridad debe tener el fragmento. Números posibles

La expresión de etiquetas EC solo se puede utilizar en lugar de ARCHIVE_LABELS o TRASH_LABELS en la definición de la clase de almacenamiento, la expresión regular de etiquetas se puede usar en cualquier lugar.

Al final de cada expresión de etiquetas se puede agregar una o dos informaciones adicionales, divididas por un separador especial. La extensión de distinción puede ser una lista de etiquetas o una de las siguientes cadenas especiales:

[IP] o [I] - distinguir por número IP

Si está presente, la parte de distinción informa al sistema que debe intentar distribuir copias completas de manera que cada copia esté en una etiqueta diferente de la lista o en un servidor de fragmentos con una dirección IP diferente o de un rack diferente. Para EC, la parte de distinción se ignora actualmente.

¡AVISO! Si CHUNKS_UNIQUE_MODE se define en mfsmaster.cfg con un valor distinto de 0, anulará cualquier configuración de distinción en las clases de almacenamiento. Para obtener más información sobre este parámetro, consulte el manual mfsmaster.cfg (5).

La extensión de anulación del modo de etiquetas puede ser uno de los tres caracteres: d (alternativamente D o en forma de cadena std o Std o STD), s (alternativamente S o en forma de cadena strict o Strict o STRICT) o l (alternativamente L o en forma de cadena loose o Loose o LOOSE) y significan que el modo de etiquetas STANDARD, STRICT o LOOSE, respectivamente, se aplicará solo a esta expresión de etiquetas. Para obtener una explicación sobre los modos de etiquetas, consulte la sección MODO DE ETIQUETAS.

Se pueden presentar una o ambas extensiones para cada expresión de etiquetas, cada una debe comenzar con su separador y si ambas están presentes, se debe mantener el orden, es decir, la extensión de distinción debe ser la primera y la extensión del modo de etiquetas debe ser la segunda.

La expresión 2 es equivalente a la expresión 2* es equivalente a la expresión *,*

S,H,H/[RACK] - los archivos tendrán 3 copias, una en un servidor con la etiqueta S, dos en servidores con la etiqueta H, pero cada copia estará en un servidor con una etiqueta diferente del conjunto de A, B, X, Y, Z

@8+3 - los archivos se mantendrán en formato EC, 8 partes de datos y 3 partes de paridad

MODO DE ETIQUETAS

Es importante especificar qué hacer cuando no es posible cumplir con los requisitos de etiquetas de una clase de almacenamiento, es decir: no hay espacio disponible en todos los servidores con las etiquetas necesarias, no hay suficientes servidores con las etiquetas necesarias o los servidores con las etiquetas necesarias están ocupados. La pregunta es si el sistema debe crear fragmentos en otros servidores (con etiquetas que no coinciden) o no. Esta decisión debe ser tomada por el usuario.

Hay 3 modos de operación: STANDARD, LOOSE y STRICT. Los modos funcionan de manera un poco diferente dependiendo de si un fragmento se almacena en formato de copias o EC, debido a la diferente naturaleza y algoritmos que cada uno de esos formatos utiliza.

Para el formato de copias, los 3 modos se comportan de la siguiente manera:

En modo STANDARD, en caso de servidores sobrecargados, el sistema esperará, pero en caso de falta de espacio utilizará otros servidores y replicará los datos a los servidores correctos cuando sea posible. Esto significa que si algunos servidores están en estado de ocupado durante mucho tiempo, puede que no sea posible crear nuevos fragmentos con ciertas clases de almacenamiento y los fragmentos en peligro (por debajo del objetivo) de esas clases corren un mayor riesgo de perderse por completo debido a las replicaciones retrasadas.

En modo STRICT, durante la escritura de un nuevo archivo, el sistema devolverá un error (ENOSPC) en caso de falta de espacio en los servidores marcados con las etiquetas especificadas para la creación de fragmentos. Todavía esperará a los servidores sobrecargados. Las replicaciones por debajo del objetivo no se realizarán si no hay espacio en los servidores con etiquetas que coincidan con la clase de almacenamiento. ¡Esto significa un alto riesgo de pérdida de datos si los servidores con algunas etiquetas se llenan permanentemente de datos!

En modo LOOSE, el sistema utilizará inmediatamente otros servidores en caso de servidores sobrecargados o falta de espacio en los servidores y replicará los datos a los servidores correctos cuando sea posible. No hay retrasos ni errores en la creación de archivos y las replicaciones por debajo del objetivo siempre se realizan lo antes posible.

Esta tabla resume el comportamiento de los modos para los fragmentos almacenados en formato de copia:

STANDARD STRICT LOOSE
CREAR - SOBRECARGADO ESPERAR ESPERAR ESCRIBIR CUALQUIERA
CREAR - SIN ESPACIO ESCRIBIR CUALQUIERA ENOSPC ESCRIBIR CUALQUIERA
REPLICAR - SOBRECARGADO ESPERAR ESPERAR ESCRIBIR CUALQUIERA
REPLICAR - SIN ESPACIO ESCRIBIR CUALQUIERA SIN COPIA ESCRIBIR CUALQUIERA

Para los fragmentos almacenados en formato EC, los 3 modos se comportan de la siguiente manera:

En general, los fragmentos solo se convertirán del formato de copia al formato EC si hay suficientes servidores en el sistema para almacenar de forma segura todas las partes del formato EC. Para el formato EC @N+X, donde N es el número de partes de datos y puede ser 4 u 8, y X es el número de partes de paridad/checksum y puede ser igual a 1 (versión CE) o cualquier número de 1 a 9 (versión PRO), los requisitos generales son:

- al menos N+2X servidores de fragmentos para convertir nuevos fragmentos del formato de copia al formato EC

- al menos N+X servidores de fragmentos para mantener los fragmentos que ya están en formato EC en ese formato

- si hay menos de N+X servidores, todos los fragmentos volverán al formato de copia (definición KEEP).

En modo LOOSE, el sistema utilizará primero los servidores que coincidan con la expresión de etiquetas definida en la clase de almacenamiento utilizada, pero si no hay suficientes servidores con etiquetas "correctas" disponibles (porque están ocupados, no tienen espacio o simplemente no están definidos), utilizará cualquier servidor de fragmentos disponible independientemente de la etiqueta; por lo tanto, N+2X y N+X se calculan a partir de todos los servidores de fragmentos disponibles cuando el sistema decide qué formato utilizar para mantener un fragmento. Además, cuando una parte de un fragmento en formato EC se vuelve no disponible o corrupta, la restauración de dicha parte también se realizará en cualquier servidor disponible, si no se puede utilizar un servidor con etiquetas "correctas" en ese momento.

Es importante recordar que si no hay suficientes servidores con etiquetas "correctas" disponibles para un fragmento en modo LOOSE, el sistema puede utilizar tantos servidores "adicionales" como desee, no solo la cantidad mínima que falta del número "correcto" de servidores.

En modo STRICT, el sistema solo utilizará los servidores que coincidan con la expresión de etiquetas definida en la clase de almacenamiento utilizada, por lo que solo los servidores disponibles o ocupados a corto plazo

en las expresiones de etiqueta definidas se utilizarán para el cálculo de N+2X y N+X cuando el sistema decida qué formato utilizar para guardar un fragmento. Cuando una parte de un fragmento en formato EC deja de estar disponible o se corrompe, la restauración de dicha parte solo se puede realizar en un servidor con etiqueta "correcta"; si dicho servidor no está disponible a largo plazo (es decir, no está disponible directamente o solo está temporalmente ocupado), esto significará automáticamente que el fragmento debe revertirse al formato de guardado de todos modos (si la parte faltante es una parte de paridad/suma de comprobación, el fragmento simplemente revertirá al formato de copia utilizando todas las partes de datos disponibles; si falta una parte de datos, se restaurará a un servidor de fragmentos que aloje otra parte del mismo fragmento, lo que no está permitido en circunstancias normales y luego seguirá inmediatamente la conversión al formato de copia).

En modo STANDARD, el sistema se comportará como en modo STRICT cuando necesite decidir si convertirá un nuevo fragmento del formato de copia al formato EC, es decir, N+2X en este paso se calcula solo a partir de servidores "correctamente" etiquetados. Pero para decidir si los fragmentos existentes deben convertirse del formato EC al formato de copia, examinará todos los servidores disponibles, independientemente de las etiquetas, por lo que N+X en este paso se calcula a partir de todos los servidores disponibles, como en el modo LOOSE. X. En caso de partes faltantes, si no es posible restaurarlas a servidores de fragmentos con etiquetas "correctas", el sistema también adaptará el comportamiento del modo LOOSE e intentará utilizar cualquier servidor disponible.

¡Aviso! Cuando un fragmento se convierte del formato de copia al formato EC, el sistema primero realiza una operación de "división local", es decir, selecciona una copia del fragmento y calcula todas las partes EC necesarias en el servidor ocupado por esta copia seleccionada. Luego, estas partes se mueven a servidores de fragmentos separados, que coinciden con las etiquetas en la definición de la clase de almacenamiento para el modo EC utilizado. Pero temporalmente, entre la división y la "salida" de las partes, pueden registrarse en un servidor de fragmentos "incorrecto" incluso en modo STRICT. Esto se debe a la mecánica de la operación de "división local".

HORA

Para las variables de tiempo, su valor puede definirse como un número de segundos u horas (entero), dependiendo de la unidad mínima de la variable, o como un período de tiempo en uno de los dos formatos posibles:

primer formato: #.#T donde T es uno de: s-segundos, m-minutos, h-horas, d-días o w-semanas; las fracciones de la unidad mínima se redondearán al valor entero

segundo formato: #s#d#h#m#s, se pueden omitir cualquier número de definiciones, pero las definiciones restantes deben estar en orden (por lo que #d#m sigue siendo una definición válida, pero #m#d no lo es); rangos: s,m: 0 a 59, h: 0 a 23, d: 0 a 6, w es ilimitado y la primera definición también es siempre ilimitada (es decir, para #d#h#m, d será ilimitado)

Si la unidad mínima de una variable es mayor que segundos, las unidades inferiores a la unidad mínima no serán aceptadas. Por ejemplo, una variable que tiene horas como unidad mínima no aceptará unidades s y m.

Ejemplos:

1.5d es lo mismo que 1d12h, es lo mismo que 36h

2.5w es lo mismo que 2w3d12h, es lo mismo que 420h; 2w84h no es un período de tiempo válido (h no es la primera definición, por lo que está limitado por el rango de 0 a 23)

COMPORTAMIENTO ARCHIVOS

Los fragmentos tienen la bandera de archivo establecida durante el bucle de mantenimiento de archivos, lo que significa que el tiempo para archivar definido por la opción -d es el tiempo mínimo que debe transcurrir antes de que se establezca la bandera, no el tiempo exacto.

El comportamiento predeterminado del sistema es que una vez que un fragmento tiene la bandera de archivo activada, NO se desactiva incluso si atime/ctime/mtime cambian, a menos que la bandera R se establezca con la opción -o. Escribir en un fragmento siempre desactivará su bandera de archivo.

Banderas de archivo:

C - usa ctime del archivo para determinar si la bandera de archivo debe activarse. Este es el valor predeterminado.

M - usa mtime del archivo para determinar si la bandera de archivo debe activarse.

A - usa atime del archivo para determinar si la bandera de archivo debe activarse.

R - reversible, si atime/mtime/ctime cambian para un archivo, el sistema verifica si la bandera de archivo debe desactivarse para sus fragmentos.

F - modo rápido, el fragmento tiene la bandera de archivo activada tan pronto como sea posible, se ignora cualquier cosa definida con la opción -d.

P - modo "por fragmento", usa mtime del fragmento para determinar si la bandera de archivo debe activarse.

La bandera de archivo se puede modificar manualmente. Consulte mfsarchive (1)

Nota: el estado ARCHIVE no significa que los fragmentos o archivos no estén disponibles, bloqueados para escritura, etc. La designación ARCHIVE solo se utiliza para indicar que dichos datos ya están destinados al almacenamiento a largo plazo. En contraste con el estado KEEP, que significa que los datos están "calientes" y se pueden cambiar con frecuencia. La distinción entre los estados KEEP y ARCHIVE es, por lo tanto, solo para permitir una definición apropiada de la forma física de almacenar estos datos. Desde el punto de vista del usuario, el archivo es igualmente accesible: tiene permisos idénticos, nombre y se encuentra en el mismo directorio. Por ejemplo, debido a que la escritura en modo EC puede ser más lenta, sugerimos almacenar datos "calientes" (KEEP) utilizando una copia y cambiarlos al formato EC (asignando el modo ARCHIVE) después de algún tiempo. Otro ejemplo es la transferencia automática de datos "fríos" a discos y servidores de fragmentos más antiguos/lentos/más baratos, utilizando diferentes etiquetas.

PRIORIDAD CLASES ALMACENAMIENTO

Las clases de almacenamiento se asignan a los archivos, pero un fragmento (una parte de un archivo) puede pertenecer a muchos archivos, gracias al mecanismo de instantáneas (consulte mfssnapshots (1)). Si un fragmento pertenece a muchos archivos con diferentes clases de almacenamiento, se debe elegir una clase de almacenamiento para especificar cómo se deben mantener las copias de este fragmento en el sistema. Hasta la versión 4.56.0 de MooseFS, se asignaba artificialmente una clase predefinida a dicho fragmento. Actualmente, se utilizará una de las clases de archivos, de acuerdo con las prioridades asignadas por el usuario, para ser exactos: el sistema elegirá la clase con la prioridad más alta de entre todas las clases de los archivos.

Ejemplo 1: hay 3 clases definidas:
ClassA, con prioridad 100,
ClassB, con prioridad 206,
ClassC, con prioridad 1001.

Un fragmento, que pertenece a 2 archivos, uno en ClassA y el otro en ClassB, se almacenará de acuerdo con la definición proporcionada por classB (mayor prioridad que ClassA).
Un fragmento, que pertenece a 3 archivos, uno en ClassA, uno en ClassB y uno en ClassC, se almacenará de acuerdo con la definición proporcionada por classC (mayor prioridad que ClassA y ClassB).

Si dos o más clases tienen la misma prioridad, entonces se considerarán los siguientes factores, en orden de importancia, para determinar cuál clase se elegirá:
- se elegirá una clase con mayor nivel de redundancia (RL) (se considerará el máximo de los niveles de redundancia KEEP y ARCHIVE de cada clase como el nivel de redundancia de esta clase),
- se elegirá una clase que tenga formato EC en estado ARCHIVE frente a una clase sin EC,
- se elegirá una clase que utilice etiquetas para el estado KEEP o ARCHIVE frente a una clase sin etiquetas,
- se elegirá una clase que tenga formato EC en estado TRASH frente a una clase sin EC,
- se elegirá una clase que utilice etiquetas para el estado TRASH frente a una clase sin etiquetas,
- si ninguna de las condiciones anteriores se utiliza, se utilizará una clase con un ID de clase mayor.

Ejemplo 2: hay 5 clases definidas, todas con la misma prioridad (por ejemplo, la prioridad predeterminada 0):
ClassA (id=1) tiene 3 copias en estado KEEP (RL=2),
ClassB (id=2) tiene 2 copias en estado KEEP y EC4+1 en estado ARCHIVE (RL=1, tiene EC en ARCHIVE),
ClassC (id=3) tiene 2 copias en estado KEEP, almacenadas en etiquetas X (RL=1, sin EC en ARCHIVE, tiene etiquetas en KEEP),
ClassD (id=4) tiene 2 copias en estado KEEP, almacenadas en etiquetas Y (RL=1, sin EC en ARCHIVE, tiene etiquetas en KEEP),
ClassE (id=5) tiene 2 copias en estado KEEP (RL=1).
También hay una clase ClassF definida, que tiene una prioridad de 77 y 2 copias en estado KEEP (RL=1).

Un fragmento, que pertenece a archivos en las clases: ClassA, ClassC y ClassE se almacenará de acuerdo con la definición de ClassA (RL más alto).
Un fragmento, que pertenece a archivos en las clases: ClassB, ClassC se almacenará de acuerdo con la definición de ClassB (RL igual, pero ClassB tiene EC).
Un fragmento, que pertenece a archivos en las clases: ClassC y ClassE se almacenará de acuerdo con la definición de ClassC (RL igual, pero ClassC tiene etiquetas).
Un fragmento, que pertenece a archivos en las clases: ClassC y ClassD se almacenará de acuerdo con la definición de ClassD (RL igual, sin EC, ambos tienen etiquetas, por lo que se elige el ID de clase mayor).
Un fragmento, que pertenece a archivos en 6 clases, de ClassA a ClassF, se almacenará de acuerdo con la definición de ClassF, porque esta tiene una prioridad mayor que todas las demás clases (77>0).
En un sistema con estas 6 clases de almacenamiento, classE nunca se utilizará para un fragmento que pertenezca a varios archivos; tiene la prioridad más baja posible (0) y ninguna condición adicional para justificar su elección (RL más bajo existente, sin EC ni etiquetas).

CLASES ALMACENAMIENTO PREDEFINIDAS

Una nueva instancia de MooseFS tendrá las siguientes clases predefinidas:

2CP - solo se define el estado KEEP, se mantienen 2 copias en cualquier etiqueta (clase predeterminada para el directorio /)

3CP - solo se define el estado KEEP, se mantienen 3 copias en cualquier etiqueta

EC4+1 - en estado KEEP, se mantienen 2 copias en cualquier etiqueta, en estado ARCHIVE, se mantienen fragmentos en formato EC4+1 en cualquier etiqueta, el retraso de archivo es de 1 día y se calcula utilizando ctime del archivo, los archivos de menos de 512kiB no se convertirán a formato EC

EC4+2 - (solo pro) en estado KEEP, se mantienen 3 copias en cualquier etiqueta, en estado ARCHIVE, se mantienen fragmentos en formato EC4+2 en cualquier etiqueta, el retraso de archivo es de 1 día y se calcula utilizando ctime del archivo, los archivos de menos de 512kiB no se convertirán a formato EC

EC8+1 - en estado KEEP, se mantienen 2 copias en cualquier etiqueta, en estado ARCHIVE, se mantienen fragmentos en formato EC8+1 en cualquier etiqueta, el retraso de archivo es de 1 día y se calcula utilizando ctime del archivo, los archivos de menos de 512kiB no se convertirán a formato EC

EC8+2 - (solo pro) en estado KEEP, se mantienen 3 copias en cualquier etiqueta, en estado ARCHIVE, se mantienen fragmentos en formato EC8+2 en cualquier etiqueta, el retraso de archivo es de 1 día y se calcula utilizando ctime del archivo, los archivos de menos de 512kiB no se convertirán a formato EC

Estas clases son totalmente modificables y eliminables, y pueden ser reemplazadas por las clases elegidas por el usuario.

Hasta la versión 4.56.0 de MooseFS, las clases predefinidas eran diferentes. La siguiente información se refiere al comportamiento antiguo de MooseFS. En versiones más recientes de MooseFS, las clases mencionadas a continuación pueden existir como

NOMBRE

mfscreatesclass - crea una nueva clase de almacenamiento

SINOPSIS

mfscreatesclass [-h] [-s] [-f] [-a] [-d días] [-m modo] [-C definición] [-K definición] [-A definición] [-l archivo_de_topología] nombre_clase

DESCRIPCIÓN

La utilidad mfscreatesclass se utiliza para crear una nueva clase de almacenamiento con las especificaciones dadas.

La clase de almacenamiento define una política de almacenamiento para los metadatos de los archivos, indicando dónde se deben almacenar las copias de los fragmentos de datos y cuántas copias deben existir.

Hay varias opciones para definir el comportamiento de la clase de almacenamiento:

-s: Crea la clase de almacenamiento sólo en el servidor maestro.

-f: Permite crear o modificar las clases de almacenamiento predefinidas (1-9). Por defecto, sólo se pueden crear o modificar clases definidas por el usuario.

-a: Crea la clase de almacenamiento para el archivo de topología especificado (por defecto es mfstopology.cfg).

-d días: Define el período de tiempo después del cual se archivarán los fragmentos (con el formato especificado por la opción -A). El valor puede ser un número entero seguido de 'd' para días, 'h' para horas o 'm' para minutos. Por ejemplo, 2d para 2 días, 12h para 12 horas, 30m para 30 minutos.

-m modo: Define el modo de almacenamiento. Los modos disponibles son:

  • p: Prefiere las copias en los servidores especificados en la definición -K. Si los servidores preferidos están sobrecargados o no disponibles, los fragmentos se colocarán en cualquier otro servidor disponible. (Modo Predeterminado)
  • l: Modo flexible. Si los servidores preferidos están sobrecargados o no disponibles, los fragmentos se colocarán en cualquier otro servidor disponible. Si los servidores preferidos están ocupados, los fragmentos se almacenan en cualquier otro servidor que no esté sobrecargado.
  • e: Modo estricto. Los fragmentos sólo se almacenarán en los servidores especificados en la definición -K. Si no hay suficientes servidores disponibles, la creación de fragmentos fallará.

-C definición: Define la política de creación de fragmentos. La definición puede ser:

  • Un número entero seguido de '*' (por ejemplo, 2*): indica el número de copias que se crearán.
  • Una lista de etiquetas de servidores separadas por comas (por ejemplo, A,B): indica que las copias deben crearse en servidores con esas etiquetas.
  • Una combinación de ambas (por ejemplo, 2*A,B): indica que se crearán 2 copias, la primera en un servidor con etiqueta 'A' y la segunda en un servidor con etiqueta 'B'.
  • Un asterisco (*): las copias se crearán en cualquier servidor disponible.

-K definición: Define la política de mantenimiento de fragmentos. Similar a la opción -C.

-A definición: Define la política de archivo de fragmentos. Similar a la opción -C, pero también soporta formatos de codificación de borrado como EC4+1 (4 datos + 1 paridad) o EC8+2 (8 datos + 2 paridad).

-l archivo_de_topología: Especifica un archivo de topología alternativo para utilizar en lugar del predeterminado mfstopology.cfg.

nombre_clase: El nombre de la nueva clase de almacenamiento.

OPCIONES

-h
Muestra un mensaje de ayuda y sale.
-s

NOTAS

Las clases de almacenamiento predefinidas (1-9) se crean como parte de una actualización, pero se comportarán exactamente como cualquier clase definida por el usuario.

Esta información se deja aquí puramente con fines informativos y se eliminará de esta página del manual en algún momento:

(Comportamiento hasta la versión 4.56.0) "Por razones de compatibilidad, cada instancia nueva o recién actualizada de MooseFS tiene 9 clases de almacenamiento predefinidas. Sus nombres son dígitos únicos, del 1 al 9, y sus definiciones son * a 9*. Son equivalentes a los objetivos numéricos simples de versiones anteriores del sistema. En caso de una actualización, todos los archivos que tenían el objetivo N antes de la actualización, ahora tendrán la clase de almacenamiento N. Estas clases sólo se pueden modificar cuando se especifica la opción -f. Se recomienda crear nuevas clases de almacenamiento en un sistema actualizado y migrar los archivos con la herramienta mfsxchgsclass, en lugar de modificar las clases predefinidas. Las clases predefinidas NO se pueden eliminar."

EJEMPLOS

Crear una nueva clase de almacenamiento llamada "Class2Copies" con 2 copias. La primera copia en un servidor de fragmentos con la etiqueta "A" y la segunda copia en un servidor de fragmentos con la etiqueta "B":

mfscreatesclass -K A,B Class2Copies

Crear una nueva clase de almacenamiento llamada "Class3Copies". Los fragmentos recién creados (-C) se mantendrán en cualquier lugar con 2 copias (2*). Poco después de la creación se mantendrán (-K) en 3 copias: la primera copia en un servidor de fragmentos con etiqueta "A", la segunda copia en un servidor de fragmentos con etiqueta "B" y la tercera en cualquier servidor de fragmentos:

mfscreatesclass -C '2*' -K 'A,B,*' Class3Copies

Crear una nueva clase de almacenamiento llamada "ClassEC4_1". Los fragmentos se crearán y mantendrán (-K) en cualquier lugar en 2 copias (2*) durante 24 horas desde la creación del archivo. Más tarde se archiarán (-A) en formato EC4+1 en cualquier servidor de fragmentos:

mfscreatesclass -K '2*' -A '@4+1' ClassEC4_1

Modificar la clase de almacenamiento "ClassEC4_1" para archivar fragmentos después de 48 horas de la modificación del archivo (no de la creación):

mfsmodifysclass -d 2d -o m ClassEC4_1

Modificar la clase de almacenamiento "Class3Copies" para mantener fragmentos en otros servidores de fragmentos (modo LOOSE) si los servidores con etiquetas "A" y "B" están demasiado ocupados (sobrecargados):

mfsmodifysclass -m l Class3Copies
