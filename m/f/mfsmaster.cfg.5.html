NOMBRE

mfsmaster.cfg - archivo de configuración principal para mfsmaster

DESCRIPCIÓN

El archivo mfsmaster.cfg contiene la configuración del proceso maestro de MooseFS.

SINTAXIS

La sintaxis es:

OPCIÓN = VALOR

Las líneas que comienzan con el carácter # se ignoran como comentarios.

OPCIONES DE INICIO

Los cambios en esta sección requieren reiniciar el proceso.

USUARIO_TRABAJO
usuario con el que se ejecutará el demonio
GRUPO_TRABAJO
grupo con el que se ejecutará el demonio; valor opcional - si está vacío, se usará el grupo predeterminado del usuario
IDENTIFICADOR_SYSLOG
nombre del proceso a incluir en los mensajes de syslog; el valor predeterminado es mfsmaster
BLOQUEAR_MEMORIA
si se debe realizar mlockall() para evitar el intercambio de memoria del proceso mfsmaster; el valor predeterminado es 0, es decir, no
DESHABILITAR_OOM_KILLER
deshabilita el "out of memory killer" (solo Linux, el valor predeterminado es 1)
NIVEL_NICE
nivel nice con el que se ejecutará el demonio; el valor predeterminado es -19; nota: el proceso debe iniciarse como root para aumentar la prioridad; si la configuración de la prioridad falla, el proceso conserva el nivel nice con el que se inició
UMASK_ARCHIVO
establece la umask predeterminada para grupos y otros (el usuario siempre tiene 0); el valor predeterminado es 027 - bloquea la escritura para el grupo y bloquea todo para los demás
RUTA_DATOS
dónde almacenar los archivos de metadatos y el archivo de bloqueo

TIEMPO_ELECCION_DELEGADO
(solo pro) cuántos segundos pasarán hasta que un maestro electo se convierta en maestro-delegado (también conocido como maestro-solo lectura) si no hay suficientes servidores de fragmentos conectados para convertirse en maestro-líder (el valor predeterminado es 0, lo que significa nunca)
MANTENER_LIDERAZGO
(solo pro) si esta opción se establece en 1, este maestro intentará asumir el liderazgo después de haberlo perdido debido a un reinicio o desconexión; no lo intentará si un usuario ha cambiado el liderazgo a propósito; para una explicación detallada, consulte NOTAS (el valor predeterminado es 0 - no intente asumir el liderazgo)
MANTENER_META_ANTERIOR
número de archivos de metadatos anteriores a conservar (el valor predeterminado es 1)
SEGUNDOS_CONSERVACION_REGISTRO_CAMBIOS
cuántos segundos de registros de cambios deben conservarse en memoria (el valor predeterminado es 5000; esto establece el mínimo, el número real puede ser un poco mayor debido a que los registros se conservan en bloques de 5k; cero deshabilita el almacenamiento adicional de registros)
MB_CONSERVACION_REGISTRO_CAMBIOS
cuánta RAM se puede utilizar para conservar registros de cambios en memoria en megabytes (el valor predeterminado es 500; esto establece el mínimo, el número real puede ser un poco mayor debido a que los registros se conservan en bloques de 5k; cero deshabilita el almacenamiento adicional de registros); el maestro siempre conservará el número menor de bloques de 5k definido por SEGUNDOS_CONSERVACION_REGISTRO_CAMBIOS y MB_CONSERVACION_REGISTRO_CAMBIOS, así que asegúrese de configurar ambos adecuadamente
MODO_GUARDADO_REGISTRO_CAMBIOS
Modo de guardado del registro de cambios (el valor predeterminado es 0)
0 - escribir en segundo plano por un proceso diferente (menos seguro, pero no hace que el maestro se detenga en caso de carga pesada del disco duro)
1 - escribir en primer plano sin sincronizar datos (el maestro espera a que cada registro de cambios se guarde en el disco duro, pero sin sincronizar; un poco más seguro que la opción en segundo plano, pero puede hacer que el maestro se detenga y espere a vaciar los búferes del disco duro)
2 - escribir en primer plano con fsync después de cada escritura (muy seguro, pero puede hacer que su maestro sea muy lento a menos que tenga hardware muy sofisticado)
CAPACIDAD_REGISTRO_FALTANTE
cuántos fragmentos faltantes se almacenarán en el maestro (se asignarán hasta 100 * CAPACIDAD_REGISTRO_FALTANTE bytes de memoria; el valor predeterminado es 100000)
PERIODO_PRUEBA_CONFIGURACION
(solo pro) con qué frecuencia (en horas) el líder del maestro debe ejecutar una prueba que verifique si las opciones de configuración son consistentes entre los módulos (el valor predeterminado es 24, el valor máximo posible es 168, 0 significa que no se realizan pruebas)
NIVEL_MINIMO_SYSLOG
nivel mínimo de mensajes que serán reportados por el maestro; niveles en orden de importancia: ERROR, WARNING, NOTICE, INFO, DEBUG (el valor predeterminado es INFO)
ELEVAR_SYSLOG_A
los mensajes reportados de nivel inferior al establecido por esta opción se elevarán a este nivel (es decir, si NIVEL_MINIMO_SYSLOG se establece en DEBUG y ELEVAR_SYSLOG_A se establece en NOTICE, todos los mensajes INFO y DEBUG se enviarán a syslog como NOTICE; el valor predeterminado es NOTICE)

NOTAS

TIEMPO

Para las variables de configuración que definen el tiempo sin requerir una unidad única y específica, el tiempo se puede definir como un número de segundos (entero) o un período de tiempo en uno de los dos formatos posibles:

primer formato: #.#T donde T es una de: s-segundos, m-minutos, h-horas, d-días o w-semanas; las fracciones de segundos se redondearán a segundos completos

segundo formato: #w#d#h#m#s, se puede omitir cualquier número de definiciones, pero las definiciones restantes deben estar en orden (por lo que #d#m sigue siendo una definición válida, pero #m#d no lo es); rangos: s,m: 0 a 59, h: 0 a 23, d: 0 a 6, w es ilimitado y la primera definición también es siempre ilimitada (es decir, para #d#h#m, d será ilimitado)

Ejemplos:

1.5h es lo mismo que 1h30m, es lo mismo que 90m, es lo mismo que 5400s, es lo mismo que 5400

2.5d es lo mismo que 2d12h, es lo mismo que 60h; 1d36h no es un período de tiempo válido (h no es la primera definición, por lo que está limitado por el rango 0 a 23)

1.03m es lo mismo que 62s (61.8 segundos se redondearán a 62)

NOTAS GENERALES

Los fragmentos (chunks) en el maestro se prueban en un bucle. La velocidad (o frecuencia) se regula mediante dos opciones: CHUNKS_LOOP_MIN_TIME y CHUNKS_LOOP_MAX_CPS. La primera define el tiempo mínimo entre iteraciones del bucle y la segunda define el número máximo de pruebas de fragmentos por segundo. Típicamente al principio, cuando el número de fragmentos es pequeño, el tiempo es constante, regulado por CHUNK_LOOP_MIN_TIME, pero cuando el número de fragmentos se vuelve mayor, el tiempo del bucle puede aumentar según CHUNKS_LOOP_MAX_CPS.

Ejemplo: CHUNKS_LOOP_MIN_TIME se establece en 300, CHUNKS_LOOP_MAX_CPS se establece en 100000 y hay 1000000 (un millón) de fragmentos en el sistema. 1000000/100000 = 10, que es menor que 300, por lo que una iteración del bucle tomará 300 segundos. Con 1000000000 (mil millones) de fragmentos, el sistema necesita 10000 segundos para una iteración del bucle.

Los límites de eliminación se definen como un límite 'blando' y uno 'duro'. Cuando el número de fragmentos a eliminar aumenta de un bucle a otro, el límite actual puede aumentarse temporalmente por encima del límite blando, pero nunca por encima del límite duro.

Los límites de replicación se dividen en cinco casos:

•
el primer límite es para fragmentos en peligro (fragmentos con una sola copia)
•
el segundo límite es para fragmentos por debajo del objetivo (fragmentos con un número de copias inferior al objetivo especificado)
•
el tercer límite es para reequilibrar entre servidores con uso de espacio cercano a la media aritmética
•
el cuarto límite es para reequilibrar entre otros servidores (uso de espacio muy bajo o muy alto)
•
el quinto límite es para replicaciones de recuperación causadas por operaciones de E/S (lectura/escritura)

Generalmente, el primer número debe ser mayor o igual que el segundo, el segundo mayor o igual que el tercero, y el cuarto mayor o igual que el tercero (1º >= 2º >= 3º <= 4º). El quinto límite debe ser igual o mayor que cualquiera de los otros límites. Si se proporciona un número, todos los límites se establecen en ese número (para compatibilidad retroactiva). Si solo se proporcionan cuatro números, el quinto se establecerá como el máximo de los cuatro (también para compatibilidad retroactiva).

Siempre que la carga del servidor de fragmentos sea superior a CS_HEAVY_LOAD_THRESHOLD y CS_HEAVY_LOAD_RATIO_THRESHOLD veces superior a la carga media, el servidor de fragmentos se cambiará al modo 'gracia'. El servidor de fragmentos permanecerá en modo gracia durante CS_HEAVY_LOAD_GRACE_PERIOD segundos.

Hay cinco valores posibles para ATIME_MODE (todos los demás valores se tratan como 0):

•
0 = Modificar siempre atime para archivos, carpetas y enlaces simbólicos.
•
1 = Modificar siempre atime pero solo en el caso de archivos (no modificar atime en el caso de carpetas y enlaces simbólicos).
•
2 = Modificar atime solo cuando sea inferior a ctime o mtime y cuando la hora actual sea superior a ctime o mtime respectivamente, también modificar atime cuando el atime actual sea anterior a 24h. Hacerlo para todos los objetos durante el acceso (como la opción "relatime" en Linux).
•
3 = Igual que lo anterior pero solo en el caso de archivos. En el caso de carpetas y enlaces simbólicos, no modificar atime.
•
4 = Nunca modificar atime durante el acceso (como la opción "noatime").

Puede reservar espacio para el superusuario usando la opción RESERVE_SPACE. Puede definirlo como número de bytes, porcentaje del espacio total, capacidad del servidor de fragmentos más grande, etc.

•
# o #B = número de bytes reservados para el superusuario. Se pueden utilizar prefijos métricos estándar - SI e IEC (k,K,M,Mi,G,Gi etc.)
•
#% o #.#% = porcentaje de la capacidad total de la instancia de MooseFS
•
#U o #.#U = múltiplos de el valor "U"; U se define como el número máximo de bytes utilizados actualmente por un solo servidor de fragmentos
•
#C o #.#C = múltiplos de el valor "C"; C se define como la capacidad total máxima de un solo servidor de fragmentos

Cuando su red tiene dos (o más) clases de IP, es posible que desee utilizar una red para la comunicación estándar entre los módulos MFS y una red separada solo para E/S. Esto se puede hacer configurando REMAP_BITS, REMAP_SOURCE_IP_CLASS y REMAP_DESTINATION_IP_CLASS. Cuando configure estas opciones, el maestro cambiará internamente las direcciones IP de los servidores de fragmentos y las enviará como ubicaciones de fragmentos, por lo que los clientes establecerán conexiones con los servidores de fragmentos utilizando la nueva IP (de destino) para todas las E/S, pero seguirán comunicándose con el maestro utilizando la IP original (de origen). También los servidores de fragmentos utilizarán la IP original para comunicarse con el maestro, pero utilizarán las nuevas IP para comunicarse entre ellos durante la replicación. Tenga en cuenta que todos los clientes y servidores de fragmentos deben tener acceso a ambas redes, pero los maestros, los metaloggers, etc. solo necesitarán acceso a la red de origen.

Cuando sus clientes están separados en dos o más redes LAN o VLAN, es posible que desee que se conecten a maestros y servidores de fragmentos utilizando IPs de su red. Esto se puede hacer configurando MULTILAN_BITS y MULTILAN_CLASSES. Cada vez que un cliente se conecta, el maestro verificará si la conexión provino de una de las clases LAN definidas y, si es así, remapeará los primeros MULTILAN_BITS de cualquier IP de servidor de fragmentos antes de enviar la IP del servidor de fragmentos al cliente. Las conexiones que provengan de otras direcciones IP se tratarán como de costumbre (es decir, se enviarán las IP originales del servidor de fragmentos en la respuesta). Todos los maestros y servidores de fragmentos deben tener una IP de cada una de las MULTILAN_CLASSES definidas y un módulo (servidor de fragmentos o maestro) debe tener el mismo sufijo IP en cada clase. También se requiere una configuración DNS adecuada: los clientes en cada LAN deben obtener una IP diferente al consultar el DNS sobre el host maestro o deben usar nombres de host maestros diferentes que se resuelvan a IPs en su clase. Consulte mfsmount(8), mfsbdev(8) para más información sobre el nombre del host maestro.

Los dos conjuntos de opciones anteriores se pueden usar juntos. Un propósito sería crear una red separada para la replicación de datos entre servidores de fragmentos, manteniendo al mismo tiempo varias redes separadas (LAN) para conjuntos de clientes separados. REMAP_BITS = 24

REMAP_DESTINATION_IP_CLASS = 10.0.1.0

MULTILAN_CLASSES = 192.168.1.0, 192.168.2.0, 192.168.3.0, 10.0.1.0

Las réplicas de chunk (o sea, las réplicas de chunks) se gestionarán en la red con el prefijo 10.0.1. Tenga en cuenta que cualquier cliente que no pertenezca a las clases de LAN definidas se conectará a los chunkservers a través de las IPs definidas por REMAP_DESTINATION_IP_CLASS. Esto también implica una configuración DNS adecuada, es decir, si el servidor maestro utiliza el sufijo de IP 1, un cliente con la IP 192.168.1.17 debería resolver el nombre del host maestro como 192.168.1.1 y un cliente con la IP 192.168.2.13 debería resolver el nombre del host maestro como 192.168.2.1. Un cliente externo a las clases de LAN definidas puede utilizar cualquiera de las IPs del servidor maestro, aunque se prefiere la 10.0.0.1.

Los maestros guardan los metadatos en un archivo en un disco local. Los momentos exactos de estas operaciones están regulados por cuatro variables: METADATA_SAVE_OFFSET, METADATA_SAVE_FREQ, (solo pro) METADATA_DOWNLOAD_FREQ, (solo pro) METADATA_CRCCHECK_FREQ.

Un solo maestro guardará los metadatos cada METADATA_SAVE_FREQ horas. El primer guardado del día ocurre a medianoche, y cada uno posterior se realiza después de METADATA_SAVE_FREQ desde el anterior. Esto se puede modificar con METADATA_SAVE_OFFSET. Si METADATA_SAVE_OFFSET se establece en un solo valor, se interpretará como minutos. Por lo tanto, una configuración como esta:

METADATA_SAVE_FREQ = 2
METADATA_SAVE_OFFSET = 15

significará guardar a las 00:15, 02:15, 04:15, etc., hasta las 22:15. Si se proporciona la hora, también se tiene en cuenta, pero solo como módulo, así que:

METADATA_SAVE_FREQ = 2
METADATA_SAVE_OFFSET = 1:15

se comportará exactamente igual que:

METADATA_SAVE_FREQ = 2
METADATA_SAVE_OFFSET = 5:15

y guardará los metadatos a las 01:15, 03:15, 05:15, etc.

Todas las horas mencionadas anteriormente se calculan en UTC, a menos que se utilice el sufijo "L". Por lo tanto, si sus servidores están en la zona horaria CET (UTC-1), esta configuración:

METADATA_SAVE_FREQ = 2
METADATA_SAVE_OFFSET = 1:15

significará que el maestro guardará los metadatos a las 01:15, 3:15, etc. UTC, lo que equivale a las 0:15, 2:15, etc. en hora local (CET). Para guardar a las 01:15 (y cada 2 horas a partir de entonces) en hora local, debe escribir:

METADATA_SAVE_FREQ = 2
METADATA_SAVE_OFFSET = 1:15L

(solo pro) Con múltiples maestros, el líder guardará los metadatos según la configuración de METADATA_CRCCHECK_FREQ, pero también teniendo en cuenta el desplazamiento. Por lo tanto, una configuración como:

METADATA_CRCCHECK_FREQ = 12
METADATA_SAVE_FREQ = 2
METADATA_SAVE_OFFSET = 1:15

significará que el líder guarda (y compara con los seguidores) los metadatos a las 01:15 y 13:15, mientras que los seguidores guardan a las 01:15, 03:15, 05:15, etc.

METADATA_DOWNLOAD_FREQ significa que el líder descargará metadatos de un seguidor y esto también tendrá en cuenta METADATA_SAVE_OFFSET de manera idéntica a como lo hace METADATA_CRCCHECK_FREQ.

Las horas mencionadas anteriormente se calculan en UTC. Por lo tanto, si sus servidores están en la zona horaria PST (UTC-8), esta configuración:

METADATA_CRCCHECK_FREQ = 12
METADATA_SAVE_FREQ = 2
METADATA_SAVE_OFFSET = 1:15

significará que el líder guardará los metadatos a las 01:15 y 13:15 UTC, lo que equivale a las 17:15 y 5:15 (5:15 PM y 5:15 AM) en hora local (PST). Para guardar a las 01:15 y 13:15 (1:15 AM y 1:15 PM) en hora local, necesita escribir:

METADATA_CRCCHECK_FREQ = 12
METADATA_SAVE_FREQ = 2
METADATA_SAVE_OFFSET = 1:15L

Configurar:

METADATA_SAVE_OFFSET = 0L

puede usarse para ajustar los tiempos de guardado a la zona horaria local sin cambiar la programación predeterminada de guardado de metadatos.

La opción KEEP_LEADERSHIP se puede utilizar para seleccionar un maestro en una instalación Pro, que asumirá el rol de LÍDER siempre que sea posible. Si este maestro pierde el liderazgo por motivos relacionados con algún mal funcionamiento (desconexión de demasiados chunkservers del clúster, desconexión de este maestro del clúster - debido a tiempos de espera u otros problemas de hardware) o debido a un reinicio del proceso (intencional o no), intentará asumir nuevamente el rol de LÍDER tan pronto como sea posible (tan pronto como alcance un estado de SEGUIDOR sincronizado). Si un usuario cambia el liderazgo utilizando la herramienta mfssupervisor, este maestro no intentará recuperar el liderazgo hasta que, una vez que se convierta nuevamente en LÍDER (esto puede ocurrir por una de estas dos razones: cambio deliberado de liderazgo por parte de un usuario o cuando el LÍDER actual falla y este servidor resulta ser elegido como el nuevo LÍDER) o sea reiniciado.

Establecer la opción KEEP_LEADERSHIP en 1 para más de un servidor maestro en un clúster NO se recomienda y puede provocar comportamientos inesperados.
