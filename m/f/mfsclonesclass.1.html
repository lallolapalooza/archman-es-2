DESCRIPCIÓN

Este es un conjunto de herramientas para administrar las clases de almacenamiento de MooseFS. Las clases de almacenamiento se utilizan para definir la política de redundancia dentro del clúster. Posteriormente, deben aplicarse a objetos (archivos o carpetas) específicos de MooseFS con las herramientas mfssclass (consulte mfssclass(1)). Una clase de almacenamiento es un conjunto con nombre de expresiones de etiquetas y otras opciones. La expresión de etiquetas indica el formato de redundancia, el nivel de redundancia deseado y la política de almacenamiento deseada. El formato de redundancia puede ser copias o codificación de borrado (EC). El nivel de redundancia es el número de copias (de 1 a 9) o el número de partes de datos más paridad (4+n u 8+n), dependiendo del formato de redundancia indicado. La política de almacenamiento especifica, mediante el uso de etiquetas, qué servidores de fragmentos (chunkservers) se utilizarán para el almacenamiento físico de los datos asignados a la clase de almacenamiento particular.

mfscreatesclass crea una nueva clase de almacenamiento con las opciones dadas, descritas a continuación, y la nombra NOMBRE_CLASE_ALMACENAMIENTO; se pueden proporcionar varios nombres, en cuyo caso se crearán varias clases de almacenamiento con la misma definición.

mfsmodifysclass cambia las opciones dadas en una o más clases indicadas por el(los) parámetro(s) NOMBRE_CLASE_ALMACENAMIENTO

mfsdeletesclass elimina la(s) clase(s) indicada(s) por el(los) parámetro(s) NOMBRE_CLASE_ALMACENAMIENTO; si alguna de las clases no está vacía (es decir, todavía es utilizada por algunos objetos de MooseFS), no se eliminará y la herramienta devolverá un error y se imprimirá un mensaje de error; las clases vacías se eliminarán en cualquier caso.

mfsclonesclass copia la clase indicada por NOMBRE_CLASE_ALMAC_ORIG con un nuevo nombre proporcionado en NOMBRE_CLASE_ALMAC_DEST.

mfsrenamesclass cambia el nombre de una clase de NOMBRE_CLASE_ALMAC_ORIG a NOMBRE_CLASE_ALMAC_DEST.

mfslistsclass lista todas las clases.

mfsimportsclass importa definiciones de clases de almacenamiento desde stdin o un archivo y las crea; el formato de entrada debe ser idéntico a la salida de mfslistsclass -l.

OPCIONES

-C parámetro opcional, que le indica al sistema a qué servidores de fragmentos, definidos por la expresión CREATE_LABELS, se debe escribir primero el fragmento justo después de su creación; si este parámetro no se proporciona para una clase, se utilizarán los servidores de fragmentos de KEEP_LABELS.

-K parámetro obligatorio, que le indica al sistema en qué servidores de fragmentos, definidos por la expresión KEEP_LABELS, los fragmentos deben mantenerse siempre, excepto para condiciones especiales como la creación, el archivado y la eliminación (movimiento a la Papelera), si están definidos.

-A parámetro opcional, que le indica al sistema en qué servidores de fragmentos, definidos por la expresión ARCH_LABELS, los fragmentos deben mantenerse con fines de archivado; el sistema comienza a tratar un fragmento como archivo cuando el atime/mtime/ctime (según se establece con -o) del archivo al que pertenece es anterior al número de horas especificado con la opción -d; consulte también la sección COMPORTAMIENTO DE ARCHIVO a continuación.

-d parámetro opcional que define después de cuánto tiempo desde atime/mtime/ctime (según se establece con -o) un archivo (y sus fragmentos) se tratan como archivo; la unidad mínima son horas, el valor predeterminado es 24, para el formato de valor consulte TIEMPO.

-o parámetro opcional que define las banderas de archivo. C - ctime, M - mtime, A - atime, R - reversible, F - modo rápido, P - por fragmento; el valor predeterminado es C; consulte la sección COMPORTAMIENTO DE ARCHIVO a continuación para obtener más detalles.

-s parámetro opcional que define la longitud mínima del archivo en bytes que se puede archivar; el valor predeterminado es 0.

-T parámetro opcional, que le indica al sistema en qué servidores de fragmentos, definidos por la expresión TRASH_LABELS, se deben mantener los fragmentos de los archivos en la Papelera; consulte también -t.

-t parámetro opcional, que define cuánto tiempo en la Papelera debe dejarse para que el sistema utilice el esquema definido en -T para un fragmento; la unidad mínima son horas, el valor predeterminado es 0, para el formato de valor consulte TIEMPO.

-c parámetro opcional, que define una descripción de clase, para conveniencia del usuario (una cadena, longitud máxima 255 bytes).

-p parámetro opcional, que define una prioridad de clase; el valor predeterminado es 0, consulte la sección PRIORIDAD DE CLASES DE ALMACENAMIENTO.

-g parámetro opcional, que define un grupo de exportación de clase; los valores posibles son de 0 a 15, el valor predeterminado es 0; consulte mfsexport.cfg(5) para obtener una explicación.

-a puede ser 1 o 0 e indica si la clase de almacenamiento está disponible para todos (0) o solo para administradores (1).

-m modo de etiqueta utilizado; los valores posibles son l (o L, loose, Loose, LOOSE) para el modo FLOJO (LOOSE), d (o D, std, Std, STD) para el modo ESTÁNDAR (STANDARD) y s (o S, strict, Strict, STRICT) para el modo ESTRICTO (STRICT); si no se define ningún modo, se asume el modo ESTÁNDAR; el comportamiento de los modos de etiqueta se describe a continuación en la sección MODOS DE ETIQUETA.

-l lista también las definiciones, no solo los nombres de las clases de almacenamiento existentes.

-i coincidencia de nombres de clases de almacenamiento insensible a mayúsculas y minúsculas.

-r reemplaza (sobrescribe) las clases existentes al importar clases de almacenamiento.

-n utiliza el nombre de archivo proporcionado como fuente de definiciones de clases de almacenamiento para importar, en lugar de stdin.

-M punto de montaje de MooseFS, no es necesario especificarlo si una herramienta se ejecuta dentro de un directorio montado por MooseFS o si MooseFS está montado en /mnt/mfs/.

-? muestra un mensaje de uso corto.

EXPRESIONES DE ETIQUETAS

Las etiquetas son letras (A-Z - 26 letras) que se pueden asignar a los servidores de fragmentos. Cada servidor de fragmentos puede tener varias (hasta 26) etiquetas. Las etiquetas se definen en el archivo mfschunkserver.cfg, para más información consulte la página del manual correspondiente.

La expresión de etiquetas es un conjunto de subexpresiones separadas por comas. Para copias completas, cada subexpresión especifica el esquema de almacenamiento de una copia de un archivo. La subexpresión puede ser: un asterisco o un esquema de etiquetas. Un esquema de etiquetas puede ser una etiqueta o una expresión con sumas, multiplicaciones, negaciones y paréntesis. Suma significa que un archivo puede almacenarse en cualquier servidor de fragmentos que coincida con cualquier elemento de la suma (lógico O). Multiplicación significa que un archivo solo puede almacenarse en un servidor de fragmentos que coincida con todos los elementos (lógico Y). Asterisco significa cualquier servidor de fragmentos. Negación significa cualquier servidor de fragmentos excepto el que coincide con la subexpresión negada. Las subexpresiones idénticas se pueden acortar añadiendo un número delante de una en lugar de repetirla varias veces.

Para EC, la expresión de etiquetas comienza con el signo @, seguido de un número de partes de datos y luego el signo + y un número que indica cuántas partes de paridad debe tener el fragmento. Números posibles

de partes de datos son 4 u 8. El número posible de partes de paridad es 1 (versión CE) o 1 a 9 (versión PRO). Así, por ejemplo, @4+1 significa EC con 4 partes de datos y 1 parte de paridad, @8+3 significa EC con 8 partes de datos y 3 partes de paridad. Si se omite el número de partes de datos, el master usa el valor predeterminado definido por DEFAULT_EC_DATA_PARTS (ver mfsmaster.cfg (5)). En este caso, @2 significa @8+2 o @4+2. Luego, pueden seguir como máximo dos subexpresiones, separadas por comas. Si solo hay una, define dónde se mantendrán todas las partes. Si hay dos, la primera subexpresión define dónde se mantendrán las partes de datos, y la segunda subexpresión define dónde se mantendrán las partes de paridad.

La expresión de etiquetas puede ser una expresión regular de etiquetas o una expresión de etiquetas EC (es decir, una expresión de etiquetas EC no puede ser una subexpresión). La expresión de etiquetas EC solo se puede usar en lugar de ARCHIVE_LABELS o TRASH_LABELS en la definición de la clase de almacenamiento; la expresión regular de etiquetas se puede usar en cualquier lugar.

Al final de cada expresión de etiquetas se puede añadir una o dos informaciones extendidas, separadas por un separador especial. La primera extensión posible es la extensión de distinción y el separador es una barra ( / ). La segunda es la anulación del modo de etiquetas y esta extensión está separada por dos puntos ( : ).

La extensión de distinción puede ser una lista de etiquetas o una de las siguientes cadenas especiales:

[IP] o [I] - distinguir por número de IP

[RACK] o [R] - distinguir por RACK, según se define en la topología, ver mfstopology.cfg (5)

Si está presente, la parte de distinción informa al sistema que debe intentar distribuir las copias completas de manera que cada copia esté en una etiqueta diferente de la lista, o en un chunkserver con una dirección IP diferente, o en un rack diferente. Para EC, la parte de distinción se ignora actualmente.

¡AVISO! Si CHUNKS_UNIQUE_MODE está definido en mfsmaster.cfg con un valor distinto de 0, anulará cualquier ajuste de distinción en las clases de almacenamiento. Para más información sobre este parámetro, consulte el manual de mfsmaster.cfg (5).

La extensión de anulación del modo de etiquetas puede ser uno de los tres caracteres: d (alternativamente D o en forma de cadena std, Std o STD), s (alternativamente S o en forma de cadena strict, Strict o STRICT) o l (alternativamente L o en forma de cadena loose, Loose o LOOSE), y significan que el modo de etiquetas ESTÁNDAR, ESTRICTO o FLEXIBLE, respectivamente, se aplicará solo a esta expresión de etiquetas. Para obtener una explicación sobre los modos de etiquetas, consulte la sección MODOS DE ETIQUETAS.

Se pueden presentar una o ambas extensiones para cada expresión de etiquetas; cada una debe comenzar con su separador y, si ambas están presentes, se debe mantener el orden, es decir, la extensión de distinción debe ser la primera y la extensión del modo de etiquetas debe ser la segunda.

Ejemplos de expresiones de etiquetas:

A,B - los archivos tendrán dos copias, una copia se almacenará en chunkserver(s) con etiqueta A, la otra en chunkserver(s) con etiqueta B

A,* - los archivos tendrán dos copias, una copia se almacenará en chunkserver(s) con etiqueta A, la otra en cualquier chunkserver(s)

A,!A - los archivos tendrán dos copias, una copia se almacenará en chunkserver(s) con etiqueta A, la otra en cualquier chunkserver(s) que no tenga la etiqueta A

*,* - los archivos tendrán dos copias, almacenadas en cualquier chunkserver(s) (diferente para cada copia)

AB,C+D+E - los archivos tendrán dos copias, una copia se almacenará en cualquier chunkserver(s) que tenga ambas etiquetas A y B (multiplicación de etiquetas), la otra en cualquier chunkserver(s) que tenga la etiqueta C o la etiqueta D o la etiqueta E (suma de etiquetas)

A,B[X+Y],C[X+Y] - los archivos tendrán tres copias, una copia se almacenará en cualquier chunkserver(s) con etiqueta A, la segunda en cualquier chunserver(s) que tenga la etiqueta B y la etiqueta X o Y, la tercera en cualquier chunkserver(s) que tenga la etiqueta C y la etiqueta X o Y

La expresión 2A es equivalente a la expresión A,A

La expresión A,3BC es equivalente a la expresión A,BC,BC,BC

La expresión 2 es equivalente a la expresión 2* es equivalente a la expresión *,*

3*/[IP] - los archivos tendrán 3 copias, cada copia se mantendrá en un chunkserver con una dirección IP diferente

A,B/[RACK] - los archivos tendrán dos copias, una copia se almacenará en chunkserver(s) con etiqueta A, la otra en chunkserver(s) con etiqueta B en un rack diferente al de la otra copia

S,H,H/[RACK] - los archivos tendrán 3 copias, una en un servidor con etiqueta S, dos en servidores con etiqueta H, pero cada copia estará en un servidor con una etiqueta diferente del conjunto de A, B, X, Y, Z

@4+1 - los archivos se mantendrán en formato EC, 4 partes de datos y 1 parte de paridad

@8+3 - los archivos se mantendrán en formato EC, 8 partes de datos y 3 partes de paridad

@2 - los archivos se mantendrán en formato EC, número por defecto de partes de datos, 2 partes de paridad

@4+3,Z - los archivos se mantendrán en formato EC, 4 partes de datos y 3 partes de paridad; todas en chunkservers con etiqueta Z.

@2,A(X+Y) - los archivos se mantendrán en formato EC, número por defecto de partes de datos, 2 partes de paridad; todas las partes se mantendrán en chunsevers con etiqueta A y etiqueta X o Y

@3,S,H - los archivos se mantendrán en formato EC, el número por defecto de partes de datos se mantendrá en chunkservers con etiqueta S, 3 partes de paridad se mantendrán en chunkservers con etiqueta H

AB,AC:l - los archivos se mantendrán en formato de copias, una copia en un servidor con etiquetas A y B, la segunda en un servidor con etiquetas A y C, y el comportamiento de esto será LOOSE (flexible)

@4+2,X,Y:s - los archivos se mantendrán en formato EC, 4 partes de datos se mantendrán en servidores con etiqueta X, 2 partes de paridad (checksum) se mantendrán en servidores con etiqueta Y, y el comportamiento de esto será STRICT (estricto)

2A/[IP]:s - los archivos se mantendrán en 2 copias, ambas copias en servidores con etiqueta A, pero cada servidor tendrá una IP diferente, el comportamiento de esto al tener en cuenta las etiquetas será STRICT (estricto)

MODOS DE ETIQUETAS

Es importante especificar qué hacer cuando no es posible cumplir los requisitos de etiquetas de una clase de almacenamiento, es decir: no hay espacio disponible en todos los servidores con las etiquetas necesarias, no hay suficientes servidores con las etiquetas necesarias o los servidores con las etiquetas necesarias están ocupados. La pregunta es si el sistema debe crear chunks en otros servidores (con etiquetas que no coinciden) o no. Esta decisión debe ser tomada por el usuario.

Hay 3 modos de operación: ESTÁNDAR, FLEXIBLE y ESTRICTO. Los modos funcionan de manera un poco diferente dependiendo de si un chunk se almacena en formato de copias o en formato EC, debido a la diferente naturaleza y algoritmos que utiliza cada uno de esos formatos.

Para el formato de copias, los 3 modos se comportan de la siguiente manera:

En modo ESTÁNDAR, en caso de servidores sobrecargados, el sistema esperará, pero en caso de falta de espacio utilizará otros servidores y replicará los datos a los servidores correctos cuando sea posible. Esto significa que si algunos servidores están en estado de ocupado durante mucho tiempo, puede que no sea posible crear nuevos chunks con ciertas clases de almacenamiento y los chunks en peligro (por debajo del objetivo) de esas clases corren un mayor riesgo de perderse por completo debido a retrasos en las replicaciones.

En modo ESTRICTO, durante la escritura de un nuevo archivo, el sistema devolverá un error (ENOSPC) en caso de falta de espacio en los servidores marcados con las etiquetas especificadas para la creación de chunks. Todavía esperará por los servidores sobrecargados. Las replicaciones por debajo del objetivo no se realizarán si no hay espacio en los servidores con etiquetas que coincidan con la clase de almacenamiento. ¡Esto significa un alto riesgo de perder datos si los servidores con algunas etiquetas están permanentemente llenos de datos!

En modo FLEXIBLE, el sistema utilizará inmediatamente otros servidores en caso de servidores sobrecargados o falta de espacio en los servidores y replicará los datos a los servidores correctos cuando sea posible. No hay retraso ni error en la creación de archivos y las replicaciones por debajo del objetivo siempre se realizan lo antes posible.

Esta tabla resume el comportamiento de los modos para los chunks almacenados en formato de copia:

ESTÁNDAR ESTRICTO FLEXIBLE
CREAR - SOBRECARGADO ESPERAR ESPERAR ESCRIBIR CUALQUIERA
CREAR - SIN ESPACIO ESCRIBIR CUALQUIERA ENOSPC ESCRIBIR CUALQUIERA
REPLICAR - SOBRECARGADO ESPERAR ESPERAR ESCRIBIR CUALQUIERA
REPLICAR - SIN ESPACIO ESCRIBIR CUALQUIERA SIN COPIA ESCRIBIR CUALQUIERA

Para los chunks almacenados en formato EC, los 3 modos se comportan de la siguiente manera:

En general, los chunks solo se convertirán de formato de copia a formato EC si hay suficientes servidores en el sistema para almacenar de forma segura todas las partes del formato EC. Para el formato EC @N+X, donde N es el número de partes de datos y puede ser 4 u 8, y X es el número de partes de paridad/checksum y puede ser igual a 1 (versión CE) o cualquier número de 1 a 9 (versión PRO), los requisitos generales son:
- al menos N+2X chunk servers para convertir nuevos chunks de formato de copia a formato EC
- al menos N+X chunk servers para mantener los chunks que ya están en formato EC en ese formato
- si hay menos de N+X servidores, todos los chunks volverán al formato de copia (definición KEEP).

En modo FLEXIBLE, el sistema intentará usar primero los servidores que coinciden con la expresión de etiquetas definida en la clase de almacenamiento utilizada, pero si no hay suficientes servidores con etiquetas "correctas" disponibles (porque están ocupados, no tienen espacio o simplemente no están definidos), utilizará cualquier chunk server disponible sin importar la etiqueta; por lo tanto, N+2X y N+X se calculan a partir de todos los chunk servers disponibles cuando el sistema decide qué formato utilizar para mantener un chunk. Además, cuando una parte de un chunk en formato EC se vuelve inaccesible o corrupta, la restauración de dicha parte también se hará en cualquier servidor disponible, si un servidor con etiquetas "correctas" no puede ser utilizado actualmente.

Es importante recordar que si no hay suficientes servidores con etiquetas "correctas" disponibles para un chunk en modo FLEXIBLE, el sistema puede utilizar tantos servidores "otros" como quiera, no solo la cantidad mínima que falta del número "correcto" de servidores.

En modo ESTRICTO, el sistema solo utilizará los servidores que coincidan con la expresión de etiquetas definida en la clase de almacenamiento utilizada, por lo que solo los servidores disponibles o ocupados a corto plazo

MODES

En el modo STRICT, el sistema solo considerará los servidores con etiquetas que coincidan con la definición de clase de almacenamiento para la creación de nuevos trozos en formato EC. Los trozos existentes en formato EC se mantendrán en dicho formato siempre que el servidor que aloja la parte de paridad/suma de comprobación sea accesible. Las etiquetas coincidentes definidas para la expresión de etiqueta se utilizarán para calcular N+2X y N+X al decidir el sistema qué formato utilizar para conservar un trozo. Cuando una parte de un trozo en formato EC se vuelve inaccesible o se corrompe, la restauración de dicha parte solo se puede realizar en un servidor con la etiqueta "correcta"; si dicho servidor está inaccesible a largo plazo (es decir, no está disponible directamente o solo está temporalmente ocupado), esto significará automáticamente que el trozo debe revertirse al formato de conservación de todos modos (si la parte faltante es una parte de paridad/suma de comprobación, el trozo simplemente revertirá al formato de copia utilizando todas las partes de datos disponibles; si falta una parte de datos, se restaurará en un servidor de trozos que aloja otra parte del mismo trozo, lo cual no está permitido en circunstancias normales, y luego la conversión al formato de copia seguirá inmediatamente).

En modo STANDARD, el sistema se comportará como en modo STRICT cuando necesite decidir si convertirá un nuevo trozo del formato de copia al formato EC, es decir, N+2X en este paso se calcula solo a partir de servidores "correctamente" etiquetados. Pero para decidir si los trozos existentes necesitan ser convertidos de formato EC a formato de copia, examinará todos los servidores disponibles, independientemente de las etiquetas, por lo que N+X en este paso se calcula a partir de todos los servidores disponibles, como en el modo LOOSE. X. En caso de partes faltantes, si no es posible restaurarlas en servidores de trozos con etiquetas "correctas", el sistema también adaptará el comportamiento del modo LOOSE e intentará utilizar cualquier servidor disponible.

¡Atención! Cuando un trozo se convierte del formato de copia al formato EC, el sistema primero realiza una operación de "división local", es decir, selecciona una copia del trozo y calcula todas las partes EC necesarias en el servidor ocupado por esta copia seleccionada. Luego, estas partes se mueven a servidores de trozos separados, coincidiendo con las etiquetas en la definición de la clase de almacenamiento para el modo EC utilizado. Pero temporalmente, entre la división y la "salida" de las partes, pueden registrarse en un servidor de trozos "incorrecto" incluso en modo STRICT. Esto se debe a la mecánica de la operación de "división local".

TIEMPO

Para las variables de tiempo, su valor puede definirse como un número de segundos o horas (entero), dependiendo de la unidad mínima de la variable, o como un período de tiempo en uno de dos formatos posibles:

primer formato: #.#T donde T es uno de: s-segundos, m-minutos, h-horas, d-días o w-semanas; las fracciones de la unidad mínima se redondearán al valor entero

segundo formato: #w#d#h#m#s, se puede omitir cualquier número de definiciones, pero las definiciones restantes deben estar en orden (así que #d#m sigue siendo una definición válida, pero #m#d no lo es); rangos: s,m: 0 a 59, h: 0 a 23, d: 0 a 6, w es ilimitado y la primera definición también es siempre ilimitada (es decir, para #d#h#m, d será ilimitado)

Si la unidad mínima de una variable es mayor que segundos, las unidades por debajo de la unidad mínima no serán aceptadas. Por ejemplo, una variable que tiene horas como unidad mínima no aceptará unidades s y m.

Ejemplos:

1.5d es lo mismo que 1d12h, es lo mismo que 36h

2.5w es lo mismo que 2w3d12h, es lo mismo que 420h; 2w84h no es un período de tiempo válido (h no es la primera definición, por lo que está limitado por el rango de 0 a 23)

COMPORTAMIENTO_DE_ARCHIVO

Las marcas de archivo se establecen en los trozos durante el bucle de mantenimiento de archivos, lo que significa que el tiempo para archivar definido por la opción -d es el tiempo mínimo que debe transcurrir antes de que se establezca la marca, no el tiempo exacto.

El comportamiento predeterminado del sistema es que una vez que un trozo tiene la marca de archivo activada, NO se desactiva incluso si atime/ctime/mtime cambian, a menos que la bandera R sea establecida por la opción -o. Escribir en un trozo siempre desactivará su marca de archivo.

Marcas de archivo:

C - utiliza el ctime del archivo para determinar si la marca de archivo debe activarse - esta es la marca predeterminada

M - utiliza el mtime del archivo para determinar si la marca de archivo debe activarse

A - utiliza el atime del archivo para determinar si la marca de archivo debe activarse

R - reversible, si atime/mtime/ctime cambian para un archivo, el sistema verifica si la marca de archivo debe desactivarse para sus trozos

F - modo rápido (fastmode), la marca de archivo del trozo se establece como activada tan pronto como sea posible, se ignora lo que se defina con la opción -d

P - modo "por trozo" (per chunk), utiliza el mtime del trozo para determinar si la marca de archivo debe activarse

La marca de archivo se puede modificar manualmente. Consulte mfsarchive (1)

Nota: el estado ARCHIVE no significa que los trozos o archivos no estén disponibles, bloqueados para escritura, etc. La designación ARCHIVE solo se utiliza para indicar que dichos datos ya están destinados al almacenamiento a largo plazo. En contraste con el estado KEEP, que significa que los datos están "en caliente" y se pueden modificar con frecuencia. La distinción entre los estados KEEP y ARCHIVE es, por lo tanto, solo para permitir una definición apropiada de la forma física de almacenar estos datos. Desde el punto de vista del usuario, el archivo es igualmente accesible: tiene permisos idénticos, nombre y está en el mismo directorio. Por ejemplo, debido a que la escritura en modo EC puede ser más lenta, sugerimos almacenar datos "en caliente" (KEEP) utilizando una copia y cambiándola al formato EC (asignando el modo ARCHIVE) después de algún tiempo. Otro ejemplo es la transferencia automática de datos "fríos" a discos y servidores de trozos más antiguos/más lentos/más baratos, utilizando diferentes etiquetas.

PRIORIDAD_DE_CLASES_DE_ALMACENAMIENTO

Las clases de almacenamiento se asignan a los archivos, pero un trozo (una parte de un archivo) puede pertenecer a muchos archivos, gracias al mecanismo de instantáneas (snapshot) (consulte mfssnapshots (1)). Si un trozo pertenece a muchos archivos con diferentes clases de almacenamiento, se debe elegir una clase de almacenamiento para especificar cómo se deben mantener las copias de este trozo en el sistema. Hasta la versión 4.56.0 de MooseFS, se asignaba artificialmente una clase predefinida a dicho trozo. Actualmente, se utilizará una de las clases de los archivos, según las prioridades asignadas por el usuario; para ser exactos: el sistema elegirá la clase con la prioridad más alta de todas las clases de los archivos.

Ejemplo 1: hay 3 clases definidas:
ClassA, con prioridad 100,
ClassB, con prioridad 206,
ClassC, con prioridad 1001.

Un trozo, que pertenece a 2 archivos, uno en ClassA, el otro en ClassB, se almacenará de acuerdo con la definición proporcionada por classB (mayor prioridad que ClassA).
Un trozo, que pertenece a 3 archivos, uno en ClassA, uno en ClassB, uno en ClassC, se almacenará de acuerdo con la definición proporcionada por classC (mayor prioridad que ClassA y ClassB).

Si dos o más clases tienen la misma prioridad, entonces se considerarán los siguientes factores, en orden de importancia, para determinar cuál clase se elegirá:
- se elegirá una clase con un nivel de redundancia (RL) más alto (se considerará el máximo de los niveles de redundancia KEEP y ARCHIVE de cada clase como el nivel de redundancia de esta clase),
- se elegirá una clase que tenga formato EC en estado ARCHIVE sobre una clase sin EC,
- se elegirá una clase que utilice etiquetas para el estado KEEP o ARCHIVE sobre una clase sin etiquetas,
- se elegirá una clase que tenga formato EC en estado TRASH sobre una clase sin EC,
- se elegirá una clase que utilice etiquetas para el estado TRASH sobre una clase sin etiquetas,
- si ninguna de las condiciones anteriores se utiliza, se utilizará una clase con un id de clase más alto.

Ejemplo 2: hay 5 clases definidas, todas con la misma prioridad (por ejemplo, la prioridad predeterminada 0):
ClassA (id=1) tiene 3 copias en estado KEEP (RL=2),
ClassB (id=2) tiene 2 copias en estado KEEP y EC4+1 en estado ARCHIVE (RL=1, tiene EC en ARCHIVE),
ClassC (id=3) tiene 2 copias en estado KEEP, almacenadas en etiquetas X (RL=1, sin EC en ARCHIVE, tiene etiquetas en KEEP),
ClassD (id=4) tiene 2 copias en estado KEEP, almacenadas en etiquetas Y (RL=1, sin EC en ARCHIVE, tiene etiquetas en KEEP),
ClassE (id=5) tiene 2 copias en estado KEEP (RL=1).
También hay una clase ClassF definida, que tiene una prioridad de 77 y 2 copias en estado KEEP (RL=1).

Un trozo, que pertenece a archivos en las clases: ClassA, ClassC y ClassE se almacenará de acuerdo con la definición de ClassA (RL más alto).
Un trozo, que pertenece a archivos en las clases: ClassB, ClassC se almacenará de acuerdo con la definición de ClassB (RL igual, pero ClassB tiene EC).
Un trozo, que pertenece a archivos en las clases: ClassC y ClassE se almacenará de acuerdo con la definición de ClassC (RL igual, pero ClassC tiene etiquetas).
Un trozo, que pertenece a archivos en las clases: ClassC y ClassD se almacenará de acuerdo con la definición de ClassD (RL igual, sin EC, ambos tienen etiquetas, por lo que se elige un ID de clase más alto).
Un trozo, que pertenece a archivos en 6 clases, de ClassA a ClassF, se almacenará de acuerdo con la definición de ClassF, porque esta tiene una prioridad más alta que todas las demás clases (77>0).
En un sistema con estas 6 clases de almacenamiento, classE nunca se usará para un trozo que pertenezca a múltiples archivos, tiene la prioridad más baja posible (0) y ninguna condición adicional para justificar su elección (RL existente más bajo, sin EC y sin etiquetas).

CLASES_DE_ALMACENAMIENTO_PREDEFINIDAS

Una nueva instancia de MooseFS tendrá las siguientes clases predefinidas:

2CP - solo se define el estado KEEP, se mantienen 2 copias en cualquier etiqueta (clase predeterminada para el directorio /)

3CP - solo se define el estado KEEP, se mantienen 3 copias en cualquier etiqueta

EC4+1 - en estado KEEP, se mantienen 2 copias en cualquier etiqueta, en estado ARCHIVE, se mantienen los trozos en formato EC4+1 en cualquier etiqueta, el retraso de archivo es de 1 día y se calcula utilizando el ctime del archivo, los archivos de menos de 512KiB no se convertirán a formato EC

EC4+2 - (solo pro) en estado KEEP, se mantienen 3 copias en cualquier etiqueta, en estado ARCHIVE, se mantienen los trozos en formato EC4+2 en cualquier etiqueta, el retraso de archivo es de 1 día y se calcula utilizando el ctime del archivo, los archivos de menos de 512KiB no se convertirán a formato EC

EC8+1 - en estado KEEP, se mantienen 2 copias en cualquier etiqueta, en estado ARCHIVE, se mantienen los trozos en formato EC8+1 en cualquier etiqueta, el retraso de archivo es de 1 día y se calcula utilizando el ctime del archivo, los archivos de menos de 512KiB no se convertirán a formato EC

EC8+2 - (solo pro) en estado KEEP, se mantienen 3 copias en cualquier etiqueta, en estado ARCHIVE, se mantienen los trozos en formato EC8+2 en cualquier etiqueta, el retraso de archivo es de 1 día y se calcula utilizando el ctime del archivo, los archivos de menos de 512KiB no se convertirán a formato EC

Estas clases son completamente modificables y eliminables, y pueden ser reemplazadas por la elección de clases del usuario.

Hasta la versión 4.56.0 de MooseFS, las clases predefinidas eran diferentes. La siguiente información se refiere al comportamiento antiguo de MooseFS. En versiones más recientes de MooseFS, las clases mencionadas a continuación pueden existir

mfscreatesclass(1) — MooseFS

NAME

mfscreatesclass — create a new storage class

SYNOPSIS

mfscreatesclass [OPTION...]

DESCRIPTION

The mfscreatesclass command creates a new storage class. Storage classes are used to define metadata, that is then used by MooseFS to decide where to store file chunks. Storage classes are used to specify goals for chunk storage, like:

  • Replication level (e.g. 2* means 2 copies, 3* means 3 copies). An asterisk (*) means that the copies can be anywhere.
  • Specific chunk servers (e.g. A, B means that at least one copy must be on a chunkserver with label A, and another copy must be on a chunkserver with label B).
  • Archival format (e.g. @4+1 means EC4+1 archival format).

Storage classes can be defined by specifying any combination of the parameters listed below.

A storage class is defined by a name and a set of rules. For more information on storage class rules, please see mfssclass(1).

OPTIONS

-C CLASSDEF
Sets the default chunk creation class. This class is used for newly created chunks. This definition is compatible with definitions described in mfssclass(1).
-K CLASSDEF
Sets the default chunk keep class. This class is used for existing chunks. This definition is compatible with definitions described in mfssclass(1).
-A CLASSDEF
Sets the default chunk archive class. This class is used for chunks that are archived. This definition is compatible with definitions described in mfssclass(1).
-d TIME
Sets the default chunk deletion delay. Chunks will be deleted only after this delay. The delay can be specified in minutes (m), hours (h), or days (d). For example, -d 2h means that chunks will be deleted after 2 hours.
-o CLASSDEF
Sets the default chunk overlive class. This class defines rules for chunks that are past their expiration date but are still kept for a certain period. This definition is compatible with definitions described in mfssclass(1).
-m MODE
Sets the default chunk management mode. Possible modes are:
  • m (minimal): At least one copy is kept on a specific server or in a specific class.
  • s (strict): All copies are kept on specific servers or in specific classes.
  • l (loose): Copies are kept on specific servers or in specific classes as long as possible. If it's not possible, then the copies are placed anywhere.
-f
Forces creation of storage class even if it already exists. Existing class will be replaced. Be careful using this option.
-v
Verbose mode. Prints detailed information about the operation.

NOTES

The predefined storage classes (1-9) are automatically created by MooseFS and cannot be deleted. They are equivalents of simple numeric goals from previous versions of the system. It is advised to create new storage classes and migrate files using the mfsxchgsclass(8) tool, rather than modifying the predefined classes.

The following section describes the behaviour of predefined classes up to version 4.56.0. This information is provided for historical context and may be removed in future versions.

(Behaviour up to version 4.56.0) "For compatibility reasons, every fresh or freshly upgraded instance of MooseFS has 9 predefined storage classes. Their names are single digits, from 1 to 9, and their definitions are * to 9*. They are equivalents of simple numeric goals from previous versions of the system. In case of an upgrade, all files that had goal N before upgrade, will now have N storage class. These classes can be modified only when option -f is specified. It is advised to create new storage classes in an upgraded system and migrate files with mfsxchgsclass tool, rather than modify the predefined classes. The predefined classes CANNOT be deleted."

EXAMPLES

Create a new storage class named "Class2Copies" with 2 copies. The first copy on one of chunkservers with label "A" and the second copy on one of chunkservers with label "B":

mfscreatesclass -K A,B Class2Copies

Create a new storage class named "Class3Copies". Freshly created chunks (-C) will be kept anywhere with 2 copies (2*). Soon after creation they will be kept (-K) in 3 copies: the first copy on one of chunkservers with label "A", the second copy on one of chunkservers with label "B" and the third on any chunkserver:

mfscreatesclass -C '2*' -K 'A,B,*' Class3Copies

Create a new storage class named "ClassEC4_1". Chunks will be created and kept (-K) anywhere in 2 copies (2*) for 24 hours from the file creation. Later they will be archived (-A) in EC4+1 format on any chunkserver:

mfscreatesclass -K '2*' -A '@4+1' ClassEC4_1

Modify the "ClassEC4_1" storage class to archive chunks after 48 hours from the file modification (not creation):

mfsmodifysclass -d 2d -o m ClassEC4_1

Modify the "Class3Copies" storage class to keep chunks on other chunkservers (LOOSE mode) if the ones with labels "A" and "B" are too busy (overloaded):

mfsmodifysclass -m l Class3Copies
