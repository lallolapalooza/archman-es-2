DESCRIPCIÓN

Este es un conjunto de herramientas para administrar las clases de almacenamiento de MooseFS. Las clases de almacenamiento se utilizan para definir la política de redundancia dentro del clúster. Posteriormente, deben aplicarse a objetos particulares de MooseFS (archivos o carpetas) con las herramientas mfssclass (ver mfssclass(1)). Una clase de almacenamiento es un conjunto con nombre de expresiones de etiquetas y otras opciones. La expresión de etiquetas indica el formato de redundancia, el nivel de redundancia deseado y la política de almacenamiento deseada. El formato de redundancia puede ser copias o codificación de borrado (EC). El nivel de redundancia es el número de copias (de 1 a 9) o el número de partes de datos más paridad (4+n u 8+n), dependiendo del formato de redundancia indicado. La política de almacenamiento especifica, mediante el uso de etiquetas, qué servidores de fragmentos se utilizarán para el almacenamiento físico de los datos asignados a la clase de almacenamiento particular.

mfscreatesclass crea una nueva clase de almacenamiento con las opciones dadas, descritas a continuación, y la nombra NOMBRE_CLASE_ALMACENAMIENTO; se pueden proporcionar varios nombres, y se crearán varias clases de almacenamiento con la misma definición.

mfsmodifysclass cambia las opciones dadas en una o varias clases indicadas por el(los) parámetro(s) NOMBRE_CLASE_ALMACENAMIENTO.

mfsdeletesclass elimina la(s) clase(s) indicada(s) por el(los) parámetro(s) NOMBRE_CLASE_ALMACENAMIENTO; si alguna de las clases no está vacía (es decir, todavía es utilizada por algunos objetos de MooseFS), no se eliminará y la herramienta devolverá un error y se imprimirá un mensaje de error; las clases vacías se eliminarán en cualquier caso.

mfsclonesclass copia la clase indicada por NOMBRE_CLASE_ALMACENAMIENTO_ORIGINAL bajo un nuevo nombre proporcionado con NOMBRE_CLASE_ALMACENAMIENTO_DESTINO.

mfsrenamesclass cambia el nombre de una clase de NOMBRE_CLASE_ALMACENAMIENTO_ORIGINAL a NOMBRE_CLASE_ALMACENAMIENTO_DESTINO.

mfslistsclass lista todas las clases.

mfsimportsclass importa definiciones de clases de almacenamiento desde stdin o un archivo y las crea; el formato de entrada debe ser idéntico a la salida de mfslistsclass -l.

OPCIONES

-C parámetro opcional, que indica al sistema a qué servidores de fragmentos, definidos por la expresión CREATE_LABELS, se escribirá primero el fragmento justo después de su creación; si este parámetro no se proporciona para una clase, se utilizarán los servidores de fragmentos KEEP_LABELS.

-K parámetro obligatorio, que indica al sistema en qué servidores de fragmentos, definidos por la expresión KEEP_LABELS, se mantendrán siempre los fragmentos, excepto para condiciones especiales como la creación, el archivo y la eliminación (movimiento a la Papelera), si están definidas.

-A parámetro opcional, que indica al sistema en qué servidores de fragmentos, definidos por la expresión ARCH_LABELS, se mantendrán los fragmentos para fines de archivo; el sistema comienza a tratar un fragmento como archivo cuando el atime/mtime/ctime (según lo establecido por -o) del archivo al que pertenece es anterior al número de horas especificado con la opción -d; ver también la sección COMPORTAMIENTO DE ARCHIVO a continuación.

-d parámetro opcional que define después de cuánto tiempo desde atime/mtime/ctime (según lo establecido por -o) un archivo (y sus fragmentos) se trata como archivo; la unidad mínima son horas, el valor predeterminado es 24; para el formato del valor, consulte TIEMPO.

-o parámetro opcional que define las banderas de archivo. C - ctime, M - mtime, A - atime, R - reversible, F - modo rápido, P - por fragmento; el valor predeterminado es C; ver la sección COMPORTAMIENTO DE ARCHIVO a continuación para más detalles.

-s parámetro opcional que define la longitud mínima del archivo en bytes que puede ser archivada; el valor predeterminado es 0.

-T parámetro opcional, que indica al sistema en qué servidores de fragmentos, definidos por la expresión TRASH_LABELS, se mantendrán los fragmentos de los archivos en la Papelera; ver también -t.

-t parámetro opcional, que define cuánto tiempo debe permanecer en la Papelera para que el sistema utilice realmente el esquema definido en -T para un fragmento; la unidad mínima son horas, el valor predeterminado es 0; para el formato del valor, consulte TIEMPO.

-c parámetro opcional, que define una descripción de clase, para conveniencia del usuario (una cadena, longitud máxima 255 bytes).

-p parámetro opcional, que define una prioridad de clase; el valor predeterminado es 0; ver la sección PRIORIDAD DE CLASES DE ALMACENAMIENTO.

-g parámetro opcional, que define un grupo de exportación de clase; los valores posibles son de 0 a 15, el valor predeterminado es 0; ver mfsexport.cfg(5) para una explicación.

-a puede ser 1 o 0 e indica si la clase de almacenamiento está disponible para todos (0) o solo para administradores (1).

-m modo de etiqueta utilizado; los valores posibles son l (o L, loose, Loose, LOOSE) para el modo LOOSE, d (o D, std, Std, STD) para el modo STANDARD y s (o S, strict, Strict, STRICT) para el modo STRICT; si no se define ningún modo, se asume el modo STANDARD; el comportamiento de los modos de etiqueta se describe a continuación en la sección MODOS DE ETIQUETA.

-l lista también las definiciones, no solo los nombres de las clases de almacenamiento existentes.

-i coincidencia insensible a mayúsculas y minúsculas de nombres de clases de almacenamiento.

-r reemplaza (sobrescribe) las clases existentes al importar clases de almacenamiento.

-n utiliza el nombre de archivo proporcionado como fuente de definiciones de clases de almacenamiento para importar, en lugar de stdin.

-M punto de montaje de MooseFS; no es necesario especificarlo si la herramienta se ejecuta dentro de un directorio montado de MooseFS o si MooseFS está montado en /mnt/mfs/.

-? muestra un mensaje de uso corto.

NOTAS

EXPRESIONES DE ETIQUETAS

Las etiquetas son letras (A-Z - 26 letras) que se pueden asignar a los servidores de fragmentos. Cada servidor de fragmentos puede tener múltiples etiquetas (hasta 26). Las etiquetas se definen en el archivo mfschunkserver.cfg; para más información, consulte la página del manual correspondiente.

Una expresión de etiquetas es un conjunto de subexpresiones separadas por comas. Para copias completas, cada subexpresión especifica el esquema de almacenamiento de una copia de un archivo. Una subexpresión puede ser: un asterisco o un esquema de etiqueta. Un esquema de etiqueta puede ser una etiqueta o una expresión con sumas, multiplicaciones, negaciones y corchetes. La suma significa que un archivo puede almacenarse en cualquier servidor de fragmentos que coincida con cualquier elemento de la suma (lógica o). La multiplicación significa que un archivo solo puede almacenarse en un servidor de fragmentos que coincida con todos los elementos (lógica y). El asterisco significa cualquier servidor de fragmentos. La negación significa cualquier servidor de fragmentos excepto el que coincide con la subexpresión negada. Las subexpresiones idénticas se pueden acortar añadiendo un número delante de una en lugar de repetirla varias veces.

Para EC, la expresión de etiquetas comienza con el signo @, seguido del número de partes de datos, luego el signo + y un número que indica cuántas partes de paridad debe tener el fragmento. Número posible

Los números de partes de datos son 4 u 8. Los números posibles de partes de paridad son 1 (versión CE ) o 1 a 9 (versión PRO). Por lo tanto, por ejemplo, @4+1 significa EC con 4 partes de datos y 1 parte de paridad, @8+3 significa EC con 8 partes de datos y 3 partes de paridad. Si se omite el número de partes de datos, el maestro utiliza el valor predeterminado definido por DEFAULT_EC_DATA_PARTS; consulte mfsmaster.cfg (5). En este caso, @2 significa @8+2 o @4+2. Luego, pueden seguir como máximo dos subexpresiones, separadas por comas. Si solo está presente una, define dónde se deben mantener todas las partes. Si ambas están presentes, la primera subexpresión define dónde se deben mantener las partes de datos, la segunda subexpresión define dónde se deben mantener las partes de paridad.

La expresión de etiquetas puede ser una expresión de etiquetas regular o una expresión de etiquetas EC (es decir, una expresión de etiquetas EC no puede ser una subexpresión). La expresión de etiquetas EC solo se puede usar en lugar de ARCHIVE_LABELS o TRASH_LABELS en la definición de la clase de almacenamiento; la expresión de etiquetas regular se puede usar en cualquier lugar.

Al final de cada expresión de etiquetas, se puede agregar una o dos informaciones adicionales, divididas por un separador especial. La primera extensión posible es la extensión de distinción y el separador es el signo de barra inclinada (/); la segunda es la anulación del modo de etiquetas y esta extensión está separada por el signo de dos puntos (:).

La extensión de distinción puede ser una lista de etiquetas o una de las siguientes cadenas especiales:

[IP] o [I] - distinguir por número IP

[RACK] o [R] - distinguir por RACK, según se define en la topología, consulte mfstopology.cfg (5)

Si está presente, la parte de distinción informa al sistema que debe intentar distribuir copias completas de manera que cada copia esté en una etiqueta diferente de la lista o en un chunkserver con una dirección IP diferente o de un rack diferente. Para EC, la parte de distinción se ignora actualmente.

¡AVISO! Si CHUNKS_UNIQUE_MODE está definido en mfsmaster.cfg con un valor distinto de 0, anulará cualquier configuración de distinción en las clases de almacenamiento. Para obtener más información sobre este parámetro, consulte el manual de mfsmaster.cfg (5).

La extensión de anulación del modo de etiquetas puede ser uno de tres caracteres: d (alternativamente D o en forma de cadena std o Std o STD), s (alternativamente S o en forma de cadena strict o Strict o STRICT) o l (alternativamente L o en forma de cadena loose o Loose o LOOSE) y significan que el modo de etiquetas ESTÁNDAR, ESTRICTO o FLOJO, respectivamente, se aplicará solo a esta expresión de etiquetas. Para obtener una explicación sobre los modos de etiquetas, consulte la sección MODOS DE ETIQUETAS.

Se puede presentar una o ambas extensiones para cada expresión de etiquetas; cada una debe comenzar con su separador y, si ambas están presentes, se debe mantener el orden, es decir, la extensión de distinción debe ser la primera y la extensión del modo de etiquetas debe ser la segunda.

Ejemplos de expresiones de etiquetas:

A,B - los archivos tendrán dos copias, una copia se almacenará en chunkserver(s) con la etiqueta A, la otra en chunkserver(s) con la etiqueta B

A,* - los archivos tendrán dos copias, una copia se almacenará en chunkserver(s) con la etiqueta A, la otra en cualquier chunkserver(s)

A,!A - los archivos tendrán dos copias, una copia se almacenará en chunkserver(s) con la etiqueta A, la otra en cualquier chunkserver(s) que no tenga la etiqueta A

*,* - los archivos tendrán dos copias, almacenadas en cualquier chunkserver(s) (diferente para cada copia)

AB,C+D+E - los archivos tendrán dos copias, una copia se almacenará en cualquier chunkserver(s) que tenga ambas etiquetas A y B (multiplicación de etiquetas), la otra en cualquier chunkserver(s) que tenga la etiqueta C o la etiqueta D o la etiqueta E (suma de etiquetas)

A,B[X+Y],C[X+Y] - los archivos tendrán tres copias, una copia se almacenará en cualquier chunkserver(s) con la etiqueta B y ya sea la etiqueta X o Y, la segunda en cualquier chunkserver(s) que tenga la etiqueta A, la tercera en cualquier chunkserver(s) que tenga la etiqueta C y ya sea la etiqueta X o Y

La expresión 2A es equivalente a la expresión A,A

La expresión A,3BC es equivalente a la expresión A,BC,BC,BC

La expresión 2 es equivalente a la expresión 2* es equivalente a la expresión *,*

3*/[IP] - los archivos tendrán 3 copias, cada copia se mantendrá en un chunkserver con una dirección IP diferente

A,B/[RACK] - los archivos tendrán dos copias, una copia se almacenará en chunkserver(s) con la etiqueta A, la otra en chunkserver(s) con la etiqueta B en un rack diferente al de la otra copia

S,H,H/[RACK] - los archivos tendrán 3 copias, una en un servidor con etiqueta S, dos en servidores con etiqueta H, pero cada copia estará en un servidor con una etiqueta diferente del conjunto de A, B, X, Y, Z

@4+1 - los archivos se mantendrán en formato EC, 4 partes de datos y 1 parte de paridad

@8+3 - los archivos se mantendrán en formato EC, 8 partes de datos y 3 partes de paridad

@2 - los archivos se mantendrán en formato EC, número predeterminado de partes de datos, 2 partes de paridad

@4+3,Z - los archivos se mantendrán en formato EC, 4 partes de datos y 3 partes de paridad; todas se mantendrán en chunkservers con la etiqueta Z.

@2,A(X+Y) - los archivos se mantendrán en formato EC, número predeterminado de partes de datos, 2 partes de paridad; todas las partes se mantendrán en chunkservers con la etiqueta A y ya sea X o Y

@3,S,H - los archivos se mantendrán en formato EC, el número predeterminado de partes de datos se mantendrá en chunkservers con la etiqueta S, 3 partes de paridad se mantendrán en chunkservers con la etiqueta H

AB,AC:l - los archivos se mantendrán en formato de copias, una copia en un servidor con las etiquetas A y B, la segunda en un servidor con las etiquetas A y C, y el comportamiento de esto debería ser FLOJO

@4+2,X,Y:s - los archivos se mantendrán en formato EC, 4 partes de datos se mantendrán en servidores con la etiqueta X, 2 partes de paridad (checksum) se mantendrán en servidores con la etiqueta Y y el comportamiento de esto debería ser ESTRICTO

2A/[IP]:s - los archivos se mantendrán en 2 copias, ambas copias en servidores con la etiqueta A, pero cada servidor debe tener una IP diferente, el comportamiento de esto al contabilizar las etiquetas debe ser ESTRICTO

MODOS DE ETIQUETAS

Es importante especificar qué hacer cuando no es posible cumplir los requisitos de etiquetas de una clase de almacenamiento, es decir: no hay espacio disponible en todos los servidores con las etiquetas necesarias, no hay suficientes servidores con las etiquetas necesarias o los servidores con las etiquetas necesarias están todos ocupados. La pregunta es si el sistema debe crear chunks en otros servidores (con etiquetas que no coinciden) o no. Esta decisión debe ser tomada por el usuario.

Hay 3 modos de operación: ESTÁNDAR, FLOJO y ESTRICTO. Los modos funcionan un poco diferente dependiendo de si un chunk se almacena en formato de copias o EC, debido a la diferente naturaleza y algoritmos que utiliza cada uno de esos formatos.

Para el formato de copias, los 3 modos se comportan de la siguiente manera:

En modo ESTÁNDAR, en caso de servidores sobrecargados, el sistema esperará, pero en caso de falta de espacio utilizará otros servidores y replicará los datos a los servidores correctos cuando sea posible. Esto significa que si algunos servidores están en estado ocupado durante mucho tiempo, podría no ser posible crear nuevos chunks con ciertas clases de almacenamiento y los chunks en peligro (por debajo del objetivo) de esas clases corren un mayor riesgo de perderse por completo debido a replicaciones retrasadas.

En modo ESTRICTO, durante la escritura de un nuevo archivo, el sistema devolverá un error (ENOSPC) en caso de falta de espacio en los servidores marcados con las etiquetas especificadas para la creación de chunks. Todavía esperará a los servidores sobrecargados. Las replicaciones por debajo del objetivo no se realizarán si no hay espacio en los servidores con etiquetas que coincidan con la clase de almacenamiento. ¡Esto significa un alto riesgo de pérdida de datos si los servidores con algunas etiquetas se llenan permanentemente de datos!

En modo FLOJO, el sistema utilizará inmediatamente otros servidores en caso de servidores sobrecargados o falta de espacio en los servidores y replicará los datos a los servidores correctos cuando sea posible. No hay retrasos ni errores en la creación de archivos y las replicaciones por debajo del objetivo siempre se realizan tan pronto como sea posible.

Esta tabla resume el comportamiento de los modos para los chunks almacenados en formato de copia:

ESTÁNDAR ESTRICTO FLOJO
CREAR - SOBRECARGADO ESPERAR ESPERAR ESCRIBIR CUALQUIERA
CREAR - SIN ESPACIO ESCRIBIR CUALQUIERA ENOSPC ESCRIBIR CUALQUIERA
REPLICAR - SOBRECARGADO ESPERAR ESPERAR ESCRIBIR CUALQUIERA
REPLICAR - SIN ESPACIO ESCRIBIR CUALQUIERA SIN COPIA ESCRIBIR CUALQUIERA

Para los chunks almacenados en formato EC, los 3 modos se comportan de la siguiente manera:

En general, los chunks solo se convertirán del formato de copia a formato EC si hay suficientes servidores en el sistema para almacenar de forma segura todas las partes del formato EC. Para el formato EC @N+X, donde N es el número de partes de datos y puede ser 4 u 8, y X es el número de partes de paridad/checksum y puede ser igual a 1 (versión CE) o cualquier número de 1 a 9 (versión PRO), los requisitos generales son:
- al menos N+2X chunkservers para convertir nuevos chunks del formato de copia a formato EC
- al menos N+X chunkservers para mantener los chunks que ya están en formato EC en ese formato
- si hay menos de N+X servidores, todos los chunks volverán al formato de copia (definición KEEP).

En modo FLOJO, el sistema intentará usar primero los servidores que coincidan con la expresión de etiquetas definida en la clase de almacenamiento utilizada, pero si no hay suficientes servidores con etiquetas "correctas" disponibles (porque están ocupados, no tienen espacio o simplemente no están definidos), utilizará cualquier chunkserver disponible independientemente de la etiqueta; por lo tanto, N+2X y N+X se calculan a partir de todos los chunkservers disponibles cuando el sistema decide qué formato usar para mantener un chunk. Además, cuando una parte de un chunk en formato EC se vuelve inaccesible o corrupta, la restauración de dicha parte también se realizará en cualquier servidor disponible, si un servidor con etiquetas "correctas" no puede utilizarse actualmente.

Es importante recordar que si no hay suficientes servidores con etiquetas "correctas" disponibles para un chunk en modo FLOJO, el sistema puede utilizar cualquier cantidad de servidores "otros" que desee, no solo la cantidad mínima que falta del número "correcto" de servidores.

En modo ESTRICTO, el sistema solo utilizará los servidores que coincidan con la expresión de etiquetas definida en la clase de almacenamiento utilizada, por lo que solo los servidores disponibles o temporalmente ocupados

Example 1: there are 3 classes defined: .br ClassA, with priority 100, .br ClassB, with priority 206, .br ClassC, with priority 1001. .P A chunk, that belongs to 2 files, one in ClassA, the other in ClassB, will be stored according to the definition provided by classB (higher priority than ClassA). .br A chunk, that belongs to 3 files, one in ClassA, one in ClassB, one in ClassC, will be stored class without labels, .br \- if none of the above conditions are used, a class with higher class id will be used. .P Example 2: there are 5 classes defined, all with the same priority (e.g. the .br ClassE (id=5) has 2 copies in KEEP state (RL=1). .br There is also a class ClassF defined, which has a priority of 77 and 2 copies in KEEP state (RL=1). .P A chunk, that belongs to files in classes: ClassA, ClassC and ClassE will be stored according to definition of ClassA (highest RL). .br A chunk, that belongs to files in classes: ClassB, ClassC will be stored according to definition of ClassB (same RL, but ClassB has EC). .br A chunk, that belongs to files in classes: ClassC and ClassE will be stored according to definition of ClassC (same RL, but ClassC has labels). .br A chunk, that belongs to files in classes: ClassC and ClassD will be stored according to definition of ClassD (same RL, no EC, both have labels, so higher class ID is picked). .br A chunk, that belongs to files in 6 classes, from ClassA to ClassF, will be stored according to definition of ClassF, because this one has higher priority than all the other classes (77>0). .br In a system with these 6 storage classes classE will never be used for a chunk belonging to multiple files, it has the lowest possible priority (0) and no extra conditions to justify its choice (lowest existing RL, no EC and When one part of a chunk in EC format becomes unavailable or corrupted, restoration of such part can only be done to a server with "correct" label; if such a server is unavailable long term (i.e. is not available outright or only temporarily busy), this will automatically mean that the chunk needs to be reverted to keep format anyway (if the missing part is a parity/checksum part, the chunk will just revert to copy format using all available data parts, if a data part is missing, it will be restored to a chunk server hosting another part of the same chunk - which is not allowed under normal circumstances - and then the conversion to copy format will follow immediately). .SS "STANDARD" .P In STANDARD mode the system will behave like in STRICT mode when it needs to make a decision whether it will convert a new chunk from copy format to EC format, that is the N+2X in this step is calculated only from "correctly" labeled servers. But to make a decision whether existing chunks need to be converted back from EC format to copy format it will look at all available servers, regardless of labels, so the N+X in this step is calculated from all available servers, like in LOOSE mode. X. In case of missing parts, if it's not possible to restore them to chunk servers with "correct" labels, the system will also adapt the LOOSE mode behaviour and try to use any available servers. .P .B Notice! When a chunk is converted from copy format to EC format, the system first performs a "local split" operation, that is it picks one copy of the chunk and calculates all EC parts necessary on the server occupied by this selected copy. Then these parts are moved to separate chunkservers, matching the labels in the storage class definition for used EC mode. But temporarily, between the split and the "moving out" of the parts, they can be recorded on a "wrong" chunk server even in STRICT mode. This is because of the mechanics of the "local split" operation. .SH "TIME" .P For time variables their value can be defined as a number of seconds or hours (integer), depending on minimum unit of the variable, or as a time period in one of two possible formats: .P first format: #.#T where T is one of: s-seconds, m-minutes, h-hours, d-days or w-weeks; fractions of minimum unit will be rounded to integer value .P second format: #w#d#h#m#s, any number of definitions can be omitted, but the remaining definitions must be in order (so #d#m is still a valid definition, but #m#d is not); ranges: s,m: 0 to 59, h: 0 to 23, d: 0 t o 6, w is unlimited and the first definition is also always unlimited (i.e. for #d#h#m d will be unlimited) .P If a minimum unit of a variable is larger than seconds, units below the minimum one will not be accepted. For example, a variable that has hours as a minimum unit will not accept s and m units. .P Examples: .P 1.5d is the same as 1d12h, is the same as 36h .P 2.5w is the same as 2w3d12h, is the same as 420h; 2w84h is not a valid time period (h is not the first definition, so it is bound by range 0 to 23) .SH "ARCHIVE BEHAVIOUR" .P Chunks have archive flag set during file maintenance loop, which means that the time to archiving defined by .B \-d option is the minimum time that has to pass before the flag is set, not the exact time. .P Default behaviour of the system is that once a chunk has the archive bit set on, it IS NOT switched off even if atime/ctime/mtime changes, unless R flag is set by option .B \-o . Writing to a chunk will always switch its archive flag off. .P Archive flags: .P C - use file's ctime to determine if archive flag should be set on - this is the default flag .P M - use file's mtime to determine if archive flag should be set on .P A - use file's atime to determine if archive flag should be set on .P R - reversible, if atime/mtime/ctime changes for a file, system verifies if archive flag should be turned off for its chunks .P F - fastmode, chunk has archive flag set to on as soon as possible, whatever is defined with .B \-d option is disregarded .P P - "per chunk" mode, use chunk's mtime to determine if archive flag should be set on .P Archive flag can be modified manually. See .B mfsarchive (1) .P Note: the ARCHIVE state does not mean that chunks or files are somehow unavailable, blocked for writing, etc. The ARCHIVE designation is only used to indicate that such data is already intended for long-term storage. In contrast to the KEEP state, which means that the data is 'hot' and can be changed frequently. The distinction between the KEEP and ARCHIVE states is therefore only to allow for an appropriate definition of the physical way of storing this data. From the user's point of view, the file is equally accessible: it has identical permissions, name, and is in the same directory. For example, due to the fact that writing in EC mode may be slower, we suggest storing 'hot' data (KEEP) using a copy and changing it to EC format (by assigning ARCHIVE mode) after some time. (Behaviour up to version 4.56.0) "For compatibility reasons, every fresh or freshly upgraded instance of MooseFS has 9 predefined storage classes. Their names are single digits, from 1 to 9, and their definitions are * to 9*. They are equivalents of simple numeric goals from previous versions of the system. In case of an upgrade, all files that had goal N before upgrade, will now have N storage class. These classes can be modified only when option -f is specified. It is advised to create new storage classes in an upgraded system and migrate files with mfsxchgsclass tool, rather than modify the predefined classes. The predefined classes CANNOT be deleted."

EJEMPLOS

Create a new storage class named "Class2Copies" with 2 copies. The first copy on one of chunkservers with label "A" and the second copy on one of chunkservers with label "B":

mfscreatesclass -K A,B Class2Copies

Create a new storage class named "Class3Copies". Freshly created chunks (-C) will be kept anywhere with 2 copies (2*). Soon after creation they will be kept (-K) in 3 copies: the first copy on one of chunkservers with label "A", the second copy on one of chunkservers with label "B" and the third on any chunkserver:

mfscreatesclass -C '2*' -K 'A,B,*' Class3Copies

Create a new storage class named "ClassEC4_1". Chunks will be created and kept (-K) anywhere in 2 copies (2*) for 24 hours from the file creation. Later they will be archived (-A) in EC4+1 format on any chunkserver:

mfscreatesclass -K '2*' -A '@4+1' ClassEC4_1

Modify the "ClassEC4_1" storage class to archive chunks after 48 hours from the file modification (not creation):

mfsmodifysclass -d 2d -o m ClassEC4_1

Modify the "Class3Copies" storage class to keep chunks on other chunkservers (LOOSE mode) if the ones with labels "A" and "B" are too busy (overloaded):

mfsmodifysclass -m l Class3Copies
