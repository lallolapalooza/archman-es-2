DESCRIPCIÓN

Este es un conjunto de herramientas para administrar las clases de almacenamiento de MooseFS. Las clases de almacenamiento se utilizan para definir la política de redundancia dentro del clúster. Posteriormente, deben aplicarse a objetos específicos de MooseFS (archivos o carpetas) con las herramientas mfssclass (ver mfssclass(1)). Una clase de almacenamiento es un conjunto con nombre de expresiones de etiquetas y algunas otras opciones. La expresión de etiquetas indica el formato de redundancia, el nivel de redundancia deseado y la política de almacenamiento deseada. El formato de redundancia puede ser copias o codificación de borrado (EC). El nivel de redundancia es el número de copias (de 1 a 9) o el número de partes de datos más paridad (4+n u 8+n), dependiendo del formato de redundancia indicado. La política de almacenamiento especifica, mediante el uso de etiquetas, qué servidores de fragmentos se utilizarán para el almacenamiento físico de los datos asignados a la clase de almacenamiento en particular.

mfscreatesclass crea una nueva clase de almacenamiento con las opciones dadas, descritas a continuación, y la nombra NOMBRE_CLASE_ALMACENAMIENTO; se puede proporcionar más de un nombre, y se crearán varias clases de almacenamiento con la misma definición.

mfsmodifysclass cambia las opciones dadas en una clase o clases indicadas por los parámetros NOMBRE_CLASE_ALMACENAMIENTO.

mfsdeletesclass elimina la(s) clase(s) indicada(s) por los parámetros NOMBRE_CLASE_ALMACENAMIENTO; si alguna de las clases no está vacía (es decir, todavía es utilizada por algunos objetos de MooseFS), no se eliminará y la herramienta devolverá un error y se imprimirá un mensaje de error; las clases vacías se eliminarán en cualquier caso.

mfsclonesclass copia la clase indicada por NOMBRE_CLASE_ORIGEN bajo un nuevo nombre proporcionado con NOMBRE_CLASE_DESTINO.

mfsrenamesclass cambia el nombre de una clase de NOMBRE_CLASE_ORIGEN a NOMBRE_CLASE_DESTINO.

mfslistsclass lista todas las clases.

mfsimportsclass importa definiciones de clases de almacenamiento desde stdin o un archivo y las crea; el formato de entrada debe ser idéntico a la salida de mfslistsclass -l.

OPCIONES

-C parámetro opcional, que indica al sistema a qué servidores de fragmentos, definidos por la expresión ETIQUETAS_CREAR, se escribirán los fragmentos por primera vez justo después de su creación; si este parámetro no se proporciona para una clase, se utilizarán los servidores de fragmentos de ETIQUETAS_MANTENER.

-K parámetro obligatorio, que indica al sistema en qué servidores de fragmentos, definidos por la expresión ETIQUETAS_MANTENER, se deben mantener siempre los fragmentos, excepto en condiciones especiales como la creación, el archivado y la eliminación (movimiento a la Papelera), si se definen.

-A parámetro opcional, que indica al sistema en qué servidores de fragmentos, definidos por la expresión ETIQUETAS_ARCH, se deben mantener los fragmentos para fines de archivo; el sistema comienza a tratar un fragmento como archivo cuando el atime/mtime/ctime (según lo establecido por -o) del archivo al que pertenece es anterior al número de horas especificado con la opción -d; ver también la sección COMPORTAMIENTO DE ARCHIVO a continuación.

-d parámetro opcional que define después de cuánto tiempo desde atime/mtime/ctime (según lo establecido por -o) un archivo (y sus fragmentos) se tratan como archivo; la unidad mínima son horas, el valor predeterminado es 24; para el formato de valor, consulte TIEMPO.

-o parámetro opcional que define las banderas de archivo. C - ctime, M - mtime, A - atime, R - reversible, F - modo rápido, P - por fragmento; el valor predeterminado es C; ver la sección COMPORTAMIENTO DE ARCHIVO a continuación para más detalles.

-s parámetro opcional que define la longitud mínima del archivo en bytes que se puede archivar; el valor predeterminado es 0.

-T parámetro opcional, que indica al sistema en qué servidores de fragmentos, definidos por la expresión ETIQUETAS_PAPELERAS, se deben mantener los fragmentos de los archivos en la Papelera; ver también -t.

-t parámetro opcional, que define cuánto tiempo debe permanecer un fragmento en la Papelera para que el sistema utilice realmente el esquema definido en -T para un fragmento; la unidad mínima son horas, el valor predeterminado es 0; para el formato de valor, consulte TIEMPO.

-c parámetro opcional, que define una descripción de clase, para conveniencia del usuario (una cadena, longitud máxima 255 bytes).

-p parámetro opcional, que define una prioridad de clase; el valor predeterminado es 0; ver la sección PRIORIDAD DE CLASES DE ALMACENAMIENTO.

-g parámetro opcional, que define un grupo de exportación de clase; los valores posibles son de 0 a 15, el valor predeterminado es 0; ver mfsexport.cfg(5) para una explicación.

-a puede ser 1 o 0 e indica si la clase de almacenamiento está disponible para todos (0) o solo para administradores (1).

-m modo de etiquetas utilizado; los valores posibles son l (o L, loose, Loose, LOOSE) para el modo SUELTO, d (o D, std, Std, STD) para el modo ESTÁNDAR y s (o S, strict, Strict, STRICT) para el modo ESTRICTO; si no se define ningún modo, se asume el modo ESTÁNDAR; el comportamiento de los modos de etiquetas se describe a continuación en la sección MODOS DE ETIQUETAS.

-l lista también las definiciones, no solo los nombres de las clases de almacenamiento existentes.

-i coincidencia de nombres de clases de almacenamiento sin distinción entre mayúsculas y minúsculas.

-r reemplaza (sobrescribe) las clases existentes al importar clases de almacenamiento.

-n utiliza el nombre de archivo proporcionado como fuente de definiciones de clases de almacenamiento para importar, en lugar de stdin.

-M punto de montaje de MooseFS, no necesita especificarse si una herramienta se ejecuta dentro de un directorio montado con MooseFS o si MooseFS está montado en /mnt/mfs/.

-? muestra un mensaje de uso corto.

NOTAS

EXPRESIONES DE ETIQUETAS

Las etiquetas son letras (A-Z - 26 letras) que se pueden asignar a los servidores de fragmentos. Cada servidor de fragmentos puede tener varias etiquetas (hasta 26). Las etiquetas se definen en el archivo mfschunkserver.cfg; para más información, consulte la página del manual correspondiente.

Una expresión de etiquetas es un conjunto de subexpresiones separadas por comas. Para copias completas, cada subexpresión especifica el esquema de almacenamiento de una copia de un archivo. Una subexpresión puede ser: un asterisco o un esquema de etiquetas. Un esquema de etiquetas puede ser una etiqueta o una expresión con sumas, multiplicaciones, negaciones y corchetes. La suma significa que un archivo se puede almacenar en cualquier servidor de fragmentos que coincida con cualquier elemento de la suma (OR lógico). La multiplicación significa que un archivo solo se puede almacenar en un servidor de fragmentos que coincida con todos los elementos (AND lógico). El asterisco significa cualquier servidor de fragmentos. La negación significa cualquier servidor de fragmentos excepto el que coincide con la subexpresión negada. Las subexpresiones idénticas se pueden acortar añadiendo un número delante de una en lugar de repetirla varias veces.

Para EC, la expresión de etiquetas comienza con el signo @, seguido del número de partes de datos y luego el signo + y un número que indica cuántas partes de paridad debe tener el fragmento. Número posible

Este sitio no está asociado de ninguna forma con Arch Linux ni afiliado a este proyecto. El contenido es únicamente una traducción de las páginas del manual de Arch publicadas en man.archlinux.org.

Las partes de los datos son 4 u 8. El número posible de partes de paridad es 1 (versión CE ) o 1 a 9 (versión PRO). Por lo tanto, por ejemplo, @4+1 significa CE con 4 partes de datos y 1 parte de paridad, @8+3 significa CE con 8 partes de datos y 3 partes de paridad. Si se omite el número de partes de datos, el maestro utilizará el valor predeterminado definido por DEFAULT_EC_DATA_PARTS; consulte mfsmaster.cfg (5). En este caso, @2 significa @8+2 o @4+2. Luego, pueden seguir como máximo dos subexpresiones, separadas por comas. Si solo hay una presente, define dónde se mantendrán todas las partes. Si ambas están presentes, la primera subexpresión define dónde se mantendrán las partes de datos y la segunda subexpresión define dónde se mantendrán las partes de paridad.

La expresión de etiquetas puede ser una expresión de etiquetas regular o una expresión de etiquetas CE (es decir, una expresión de etiquetas CE no puede ser una subexpresión). La expresión de etiquetas CE solo se puede usar en lugar de ARCHIVE_LABELS o TRASH_LABELS en la definición de la clase de almacenamiento; la expresión de etiquetas regular se puede usar en cualquier lugar.

Al final de cada expresión de etiquetas se puede agregar una o dos informaciones adicionales, divididas por un separador especial. La primera extensión posible es la extensión de distinción y el separador es una barra (/) . La segunda es la anulación del modo de etiquetas y esta extensión está separada por dos puntos (: ).

La extensión de distinción puede ser una lista de etiquetas o una de las siguientes cadenas especiales:

[IP] o [I] - distinguir por número IP

[RACK] o [R] - distinguir por RACK, como se define en la topología; consulte mfstopology.cfg (5)

Si está presente, la parte de distinción informa al sistema que debe intentar distribuir copias completas de manera que cada copia esté en una etiqueta diferente de la lista o en un chunkserver con una dirección IP diferente o de un rack diferente. Para CE, la parte de distinción se ignora actualmente.

¡AVISO! Si CHUNKS_UNIQUE_MODE se define en mfsmaster.cfg con un valor distinto de 0, anulará cualquier configuración de distinción en las clases de almacenamiento. Para obtener más información sobre este parámetro, consulte el manual mfsmaster.cfg (5).

La extensión de anulación del modo de etiquetas puede ser uno de los tres caracteres: d (alternativamente D o en forma de cadena std o Std o STD), s (alternativamente S o en forma de cadena strict o Strict o STRICT) o l (alternativamente L o en forma de cadena loose o Loose o LOOSE) y significan que el modo de etiquetas ESTÁNDAR, ESTRICTO o FLOJO, respectivamente, debe aplicarse solo a esta expresión de etiquetas. Para obtener una explicación sobre los modos de etiquetas, consulte la sección MODOS DE ETIQUETAS.

Se pueden presentar una o ambas extensiones para cada expresión de etiquetas; cada una debe comenzar con su separador y, si ambas están presentes, se debe mantener el orden, es decir, la extensión de distinción debe ser la primera y la extensión del modo de etiquetas debe ser la segunda.

Ejemplos de expresiones de etiquetas:

A,B: los archivos tendrán dos copias; una copia se almacenará en chunkservers con la etiqueta A y la otra en chunkservers con la etiqueta B

A,*: los archivos tendrán dos copias; una copia se almacenará en chunkservers con la etiqueta A y la otra en cualquier chunkserver

A,!A: los archivos tendrán dos copias; una copia se almacenará en chunkservers con la etiqueta A y la otra en cualquier chunkserver que no tenga la etiqueta A

*,*: los archivos tendrán dos copias, almacenadas en cualquier chunkserver (diferente para cada copia)

AB,C+D+E: los archivos tendrán dos copias; una copia se almacenará en cualquier chunkserver que tenga ambas etiquetas A y B (multiplicación de etiquetas), la otra en cualquier chunkserver que tenga la etiqueta C o la etiqueta D o la etiqueta E (suma de etiquetas)

A,B[X+Y],C[X+Y]: los archivos tendrán tres copias; una copia se almacenará en cualquier chunkserver con la etiqueta A, la segunda en cualquier chunkserver que tenga la etiqueta B y la etiqueta X o Y, la tercera en cualquier chunkserver que tenga la etiqueta C y la etiqueta X o Y

La expresión 2A es equivalente a la expresión A,A

La expresión A,3BC es equivalente a la expresión A,BC,BC,BC

La expresión 2 es equivalente a la expresión 2* es equivalente a la expresión *,*

3*/[IP]: los archivos tendrán 3 copias; cada copia se mantendrá en un chunkserver con una dirección IP diferente

A,B/[RACK]: los archivos tendrán dos copias; una copia se almacenará en chunkservers con la etiqueta A, la otra en chunkservers con la etiqueta B en un rack diferente al de la otra copia

S,H,H/[RACK]: los archivos tendrán 3 copias; una en un servidor con etiqueta S, dos en servidores con etiqueta H, pero cada copia estará en un servidor con una etiqueta diferente del conjunto de A, B, X, Y, Z

@4+1: los archivos se mantendrán en formato CE; 4 partes de datos y 1 parte de paridad

@8+3: los archivos se mantendrán en formato CE; 8 partes de datos y 3 partes de paridad

@2: los archivos se mantendrán en formato CE; número predeterminado de partes de datos, 2 partes de paridad

@4+3,Z: los archivos se mantendrán en formato CE; 4 partes de datos y 3 partes de paridad; todas se mantendrán en chunkservers con la etiqueta Z.

@2,A(X+Y): los archivos se mantendrán en formato CE; número predeterminado de partes de datos, 2 partes de paridad; todas las partes se mantendrán en chunkservers con las etiquetas A y X o Y

@3,S,H: los archivos se mantendrán en formato CE; el número predeterminado de partes de datos se mantendrá en chunkservers con la etiqueta S; 3 partes de paridad se mantendrán en chunkservers con la etiqueta H

AB,AC:l: los archivos se mantendrán en formato de copias; una copia en un servidor con las etiquetas A y B, la segunda en un servidor con las etiquetas A y C, y el comportamiento de esto será FLOJO

@4+2,X,Y:s: los archivos se mantendrán en formato CE; 4 partes de datos se mantendrán en servidores con la etiqueta X, 2 partes de paridad (suma de verificación) se mantendrán en servidores con la etiqueta Y, y el comportamiento de esto será ESTRICTO

2A/[IP]:s: los archivos se mantendrán en 2 copias; ambas copias en servidores con etiqueta A, pero cada servidor debe tener una IP diferente; el comportamiento de esto al tener en cuenta las etiquetas será ESTRICTO

MODOS DE ETIQUETAS

Es importante especificar qué hacer cuando no es posible cumplir los requisitos de etiquetas de una clase de almacenamiento, es decir: no hay espacio disponible en todos los servidores con las etiquetas necesarias, no hay suficientes servidores con las etiquetas necesarias o los servidores con las etiquetas necesarias están todos ocupados. La pregunta es si el sistema debe crear chunks en otros servidores (con etiquetas que no coinciden) o no. Esta decisión debe ser tomada por el usuario.

Hay 3 modos de operación: ESTÁNDAR, FLOJO y ESTRICTO. Los modos funcionan de manera un poco diferente dependiendo de si un chunk se almacena en formato de copias o CE, debido a la diferente naturaleza y algoritmos que utiliza cada uno de esos formatos.

Para el formato de copias, los 3 modos se comportan de la siguiente manera:

En modo ESTÁNDAR, en caso de servidores sobrecargados, el sistema esperará, pero en caso de falta de espacio utilizará otros servidores y replicará los datos a los servidores correctos cuando sea posible. Esto significa que si algunos servidores están en estado ocupado durante mucho tiempo, puede que no sea posible crear nuevos chunks con ciertas clases de almacenamiento y los chunks en peligro (por debajo del objetivo) de esas clases corren un mayor riesgo de perderse por completo debido a replicaciones retrasadas.

En modo ESTRICTO, durante la escritura de un nuevo archivo, el sistema devolverá un error (ENOSPC) en caso de falta de espacio en los servidores marcados con las etiquetas especificadas para la creación de chunks. Aún esperará a los servidores sobrecargados. Las replicaciones por debajo del objetivo no se realizarán si no hay espacio en los servidores con etiquetas que coincidan con la clase de almacenamiento. ¡Esto significa un alto riesgo de pérdida de datos si los servidores con algunas etiquetas están permanentemente llenos de datos!

En modo FLOJO, el sistema utilizará inmediatamente otros servidores en caso de servidores sobrecargados o falta de espacio en los servidores y replicará los datos a los servidores correctos cuando sea posible. No hay demora ni error en la creación de archivos y las replicaciones por debajo del objetivo siempre se realizan lo antes posible.

Esta tabla resume el comportamiento de los modos para chunks almacenados en formato de copia:

ESTÁNDAR ESTRICTO FLOJO
CREAR - SOBRECARGADO ESPERAR ESPERAR ESCRIBIR CUALQUIERA
CREAR - SIN ESPACIO ESCRIBIR CUALQUIERA ENOSPC ESCRIBIR CUALQUIERA
REPLICAR - SOBRECARGADO ESPERAR ESPERAR ESCRIBIR CUALQUIERA
REPLICAR - SIN ESPACIO ESCRIBIR CUALQUIERA SIN COPIA ESCRIBIR CUALQUIERA

Para chunks almacenados en formato CE, los 3 modos se comportan de la siguiente manera:

En general, los chunks solo se convertirán del formato de copia al formato CE si hay suficientes servidores en el sistema para almacenar de forma segura todas las partes del formato CE. Para el formato CE @N+X, donde N es el número de partes de datos y puede ser 4 u 8, y X es el número de partes de paridad/suma de verificación y puede ser igual a 1 (versión CE) o cualquier número de 1 a 9 (versión PRO), los requisitos generales son:
- al menos 2X+N servidores de chunk para convertir nuevos chunks del formato de copia a formato CE
- al menos N+X servidores para mantener los chunks que ya están en formato CE en este formato
- si hay menos de N+X servidores, todos los chunks volverán al formato de copia (definición KEEP).

En modo FLOJO, el sistema utilizará primero los servidores que coincidan con la expresión de etiquetas definida en la clase de almacenamiento utilizada, pero si no hay suficientes servidores con etiquetas "correctas" disponibles (porque están ocupados, no tienen espacio o simplemente no están definidos), utilizará cualquier servidor de chunk disponible independientemente de la etiqueta; por lo tanto, N+2X y N+X se calculan a partir de todos los servidores de chunk disponibles cuando el sistema decide qué formato utilizar para mantener un chunk. Además, cuando una parte de un chunk en formato CE se vuelve no disponible o corrupta, la restauración de dicha parte también se realizará en cualquier servidor disponible, si un servidor con etiquetas "correctas" no puede utilizarse actualmente.

Es importante recordar que si no hay suficientes servidores con etiquetas "correctas" disponibles para un chunk en modo FLOJO, el sistema puede utilizar cualquier cantidad de los servidores de chunk "otros", no solo la cantidad mínima que falta del número "correcto" de servidores.

En modo ESTRICTO, el sistema solo utilizará los servidores que coincidan con la expresión de etiquetas definida en la clase de almacenamiento utilizada, por lo que solo los servidores disponibles o ocupados a corto plazo

ETALONAGE

Los servidores que coincidan con la expresión de etiquetas definida se utilizarán para el cálculo de N+2X y N+X cuando el sistema decida el formato que se utilizará para conservar un fragmento. Cuando una parte de un fragmento en formato EC se vuelve inaccesible o corrupta, la restauración de dicha parte solo se puede hacer en un servidor con etiqueta "correcta"; si dicho servidor está inaccesible a largo plazo (es decir, no está disponible directamente o solo está temporalmente ocupado), esto significará automáticamente que el fragmento deberá revertirse de todos modos al formato de conservación (si la parte faltante es una parte de paridad/suma de verificación, el fragmento simplemente revertirá al formato de copia utilizando todas las partes de datos disponibles, si falta una parte de datos, se restaurará en un servidor de fragmentos que aloje otra parte del mismo fragmento, lo cual no está permitido en circunstancias normales, y luego la conversión al formato de copia seguirá inmediatamente).

En el modo STANDARD, el sistema se comportará como en el modo STRICT cuando necesite tomar una decisión sobre si convertirá un nuevo fragmento del formato de copia al formato EC, es decir, N+2X en este paso se calcula solo a partir de servidores etiquetados "correctamente". Pero para decidir si los fragmentos existentes necesitan ser convertidos de nuevo de formato EC a formato de copia, examinará todos los servidores disponibles, independientemente de las etiquetas, por lo que N+X en este paso se calcula a partir de todos los servidores disponibles, como en el modo LOOSE. X. En caso de partes faltantes, si no es posible restaurarlas en servidores de fragmentos con etiquetas "correctas", el sistema también adaptará el comportamiento del modo LOOSE e intentará utilizar cualquier servidor disponible.

¡Aviso! Cuando un fragmento se convierte del formato de copia al formato EC, el sistema primero realiza una operación de "división local", es decir, selecciona una copia del fragmento y calcula todas las partes EC necesarias en el servidor ocupado por esta copia seleccionada. Luego, estas partes se mueven a servidores de fragmentos separados, coincidiendo con las etiquetas en la definición de la clase de almacenamiento para el modo EC utilizado. Pero temporalmente, entre la división y la "salida" de las partes, pueden registrarse en un servidor de fragmentos "incorrecto" incluso en el modo STRICT. Esto se debe a la mecánica de la operación de "división local".

TIEMPO

Para las variables de tiempo, su valor se puede definir como un número de segundos u horas (entero), dependiendo de la unidad mínima de la variable, o como un período de tiempo en uno de los dos formatos posibles:

primer formato: #.#T donde T es uno de: s-segundos, m-minutos, h-horas, d-días o w-semanas; las fracciones de la unidad mínima se redondearán al valor entero

segundo formato: #w#d#h#m#s, se puede omitir cualquier número de definiciones, pero las definiciones restantes deben estar en orden (por lo que #d#m sigue siendo una definición válida, pero #m#d no lo es); rangos: s,m: 0 a 59, h: 0 a 23, d: 0 a 6, w es ilimitado y la primera definición también es siempre ilimitada (es decir, para #d#h#m d será ilimitado)

Si la unidad mínima de una variable es mayor que segundos, las unidades por debajo de la unidad mínima no serán aceptadas. Por ejemplo, una variable que tiene horas como unidad mínima no aceptará unidades s y m.

Ejemplos:

1.5d es lo mismo que 1d12h, es lo mismo que 36h

2.5w es lo mismo que 2w3d12h, es lo mismo que 420h; 2w84h no es un período de tiempo válido (h no es la primera definición, por lo que está limitado por el rango 0 a 23)

COMPORTAMIENTO DE ARCHIVO

Los fragmentos tienen la bandera de archivo establecida durante el bucle de mantenimiento de archivos, lo que significa que el tiempo para archivar definido por la opción -d es el tiempo mínimo que debe transcurrir antes de que se establezca la bandera, no el tiempo exacto.

El comportamiento predeterminado del sistema es que una vez que un fragmento tiene la bandera de archivo activada, NO se desactiva incluso si atime/ctime/mtime cambian, a menos que la bandera R sea establecida por la opción -o. Escribir en un fragmento siempre desactivará su bandera de archivo.

Banderas de archivo:

C - utiliza ctime del archivo para determinar si la bandera de archivo debe activarse; esta es la bandera predeterminada

M - utiliza mtime del archivo para determinar si la bandera de archivo debe activarse

A - utiliza atime del archivo para determinar si la bandera de archivo debe activarse

R - reversible, si atime/mtime/ctime cambian para un archivo, el sistema verifica si la bandera de archivo debe desactivarse para sus fragmentos

F - modo rápido, la bandera de archivo del fragmento se establece en activado tan pronto como sea posible, se ignora lo que se defina con la opción -d

P - modo "por fragmento", utiliza mtime del fragmento para determinar si la bandera de archivo debe activarse

La bandera de archivo se puede modificar manualmente. Ver mfsarchive (1)

Nota: el estado ARCHIVO no significa que los fragmentos o archivos no estén disponibles, bloqueados para escritura, etc. La designación ARCHIVO solo se utiliza para indicar que dichos datos ya están destinados al almacenamiento a largo plazo. A diferencia del estado KEEP, que significa que los datos están 'calientes' y pueden cambiarse con frecuencia. La distinción entre los estados KEEP y ARCHIVO es, por lo tanto, solo para permitir una definición apropiada de la forma física de almacenar estos datos. Desde el punto de vista del usuario, el archivo es igualmente accesible: tiene permisos idénticos, nombre y se encuentra en el mismo directorio. Por ejemplo, debido a que la escritura en modo EC puede ser más lenta, sugerimos almacenar datos 'calientes' (KEEP) utilizando una copia y cambiarlos al formato EC (asignando el modo ARCHIVE) después de algún tiempo. Otro ejemplo es la transferencia automática de datos 'fríos' a discos y servidores de fragmentos más antiguos/lentos/más baratos, utilizando diferentes etiquetas.

PRIORIDAD DE CLASES DE ALMACENAMIENTO

Las clases de almacenamiento se asignan a los archivos, pero un fragmento (una parte de un archivo) puede pertenecer a muchos archivos, gracias al mecanismo de instantáneas (ver mfssnapshots (1)). Si un fragmento pertenece a muchos archivos con diferentes clases de almacenamiento, se debe elegir una clase de almacenamiento para especificar cómo se deben mantener las copias de este fragmento en el sistema. Hasta la versión 4.56.0 de MooseFS, se asignaba artificialmente una clase predefinida a dicho fragmento. Actualmente se utilizará una de las clases de los archivos, según las prioridades asignadas por el usuario, para ser exactos: el sistema elegirá la clase con mayor prioridad de entre todas las clases de los archivos.

Ejemplo 1: Hay 3 clases definidas:
ClassA, con prioridad 100,
ClassB, con prioridad 206,
ClassC, con prioridad 1001.

Un fragmento, que pertenece a 2 archivos, uno en ClassA y otro en ClassB, se almacenará según la definición proporcionada por classB (mayor prioridad que ClassA).
Un fragmento, que pertenece a 3 archivos, uno en ClassA, uno en ClassB, uno en ClassC, se almacenará según la definición proporcionada por classC (mayor prioridad que ClassA y ClassB).

Si dos o más clases tienen la misma prioridad, entonces se considerarán los siguientes factores, en orden de importancia, para determinar cuál clase se elegirá:
- se elegirá una clase con mayor nivel de redundancia (RL) (se considerará el máximo de los niveles de redundancia KEEP y ARCHIVE de cada clase como el nivel de redundancia de esta clase),
- se elegirá una clase que tenga formato EC en estado ARCHIVE sobre una clase sin EC,
- se elegirá una clase que utilice etiquetas para el estado KEEP o ARCHIVE sobre una clase sin etiquetas,
- se elegirá una clase que tenga formato EC en estado TRASH sobre una clase sin EC,
- se elegirá una clase que utilice etiquetas para el estado TRASH sobre una clase sin etiquetas,
- si ninguna de las condiciones anteriores se utiliza, se utilizará una clase con un ID de clase mayor.

Ejemplo 2: Hay 5 clases definidas, todas con la misma prioridad (por ejemplo, la prioridad predeterminada 0):
ClassA (id=1) tiene 3 copias en estado KEEP (RL=2),
ClassB (id=2) tiene 2 copias en estado KEEP y EC4+1 en estado ARCHIVE (RL=1, tiene EC en ARCHIVE),
ClassC (id=3) tiene 2 copias en estado KEEP, almacenadas en etiquetas X (RL=1, sin EC en ARCHIVE, tiene etiquetas en KEEP),
ClassD (id=4) tiene 2 copias en estado KEEP, almacenadas en etiquetas Y (RL=1, sin EC en ARCHIVE, tiene etiquetas en KEEP),
ClassE (id=5) tiene 2 copias en estado KEEP (RL=1).
También hay una clase ClassF definida, que tiene una prioridad de 77 y 2 copias en estado KEEP (RL=1).

Un fragmento, que pertenece a archivos en las clases: ClassA, ClassC y ClassE se almacenará según la definición de ClassA (RL más alto).
Un fragmento, que pertenece a archivos en las clases: ClassB, ClassC se almacenará según la definición de ClassB (RL igual, pero ClassB tiene EC).
Un fragmento, que pertenece a archivos en las clases: ClassC y ClassE se almacenará según la definición de ClassC (RL igual, pero ClassC tiene etiquetas).
Un fragmento, que pertenece a archivos en las clases: ClassC y ClassD se almacenará según la definición de ClassD (RL igual, sin EC, ambos tienen etiquetas, por lo que se elige un ID de clase mayor).
Un fragmento, que pertenece a archivos en 6 clases, desde ClassA hasta ClassF, se almacenará según la definición de ClassF, porque esta tiene una prioridad mayor que todas las demás clases (77>0).
En un sistema con estas 6 clases de almacenamiento, classE nunca se utilizará para un fragmento que pertenezca a varios archivos, tiene la prioridad más baja posible (0) y ninguna condición adicional para justificar su elección (RL existente más bajo, sin EC y sin etiquetas).

CLASES DE ALMACENAMIENTO PREDETERMINADAS

Una nueva instancia de MooseFS tendrá las siguientes clases predeterminadas:

2CP - solo se define el estado KEEP, mantenga 2 copias en cualquier etiqueta (clase predeterminada para el directorio /)

3CP - solo se define el estado KEEP, mantenga 3 copias en cualquier etiqueta

EC4+1 - en estado KEEP, mantenga 2 copias en cualquier etiqueta, en estado ARCHIVE, mantenga fragmentos en formato EC4+1 en cualquier etiqueta, el retraso de archivo es de 1 día y se calcula utilizando ctime del archivo, los archivos más pequeños que 512kiB no se convertirán a formato EC

EC4+2 - (solo pro) en estado KEEP, mantenga 3 copias en cualquier etiqueta, en estado ARCHIVE, mantenga fragmentos en formato EC4+2 en cualquier etiqueta, el retraso de archivo es de 1 día y se calcula utilizando ctime del archivo, los archivos más pequeños que 512kiB no se convertirán a formato EC

EC8+1 - en estado KEEP, mantenga 2 copias en cualquier etiqueta, en estado ARCHIVE, mantenga fragmentos en formato EC8+1 en cualquier etiqueta, el retraso de archivo es de 1 día y se calcula utilizando ctime del archivo, los archivos más pequeños que 512kiB no se convertirán a formato EC

EC8+2 - (solo pro) en estado KEEP, mantenga 3 copias en cualquier etiqueta, en estado ARCHIVE, mantenga fragmentos en formato EC8+2 en cualquier etiqueta, el retraso de archivo es de 1 día y se calcula utilizando ctime del archivo, los archivos más pequeños que 512kiB no se convertirán a formato EC

Estas clases son totalmente modificables y eliminables, y pueden ser reemplazadas por las clases elegidas por el usuario.

Hasta la versión 4.56.0 de MooseFS, las clases predeterminadas eran diferentes. La siguiente información se refiere al comportamiento anterior de MooseFS. En versiones más recientes de MooseFS, las clases mencionadas a continuación pueden existir

mfscreatesclass(1) — MooseFS — Arch Linux

NAME

mfscreatesclass — creates a new storage class

SYNOPSIS

mfscreatesclass [-f] [-C <chunk creation>] [-K <chunk keep>] [-A <chunk archive>] [-d <deletion delay>] [-o <deletion mode>] <class name>

DESCRIPTION

The mfscreatesclass command creates a new storage class. A storage class defines a set of rules for storing file chunks. These rules specify where and how many copies of a chunk should be kept, and when and how they should be archived or deleted.

Storage classes are used to implement different data redundancy and archiving policies within the MooseFS distributed file system. By assigning files or directories to specific storage classes, administrators can control the data storage behaviour according to their needs, for example, ensuring high availability for critical data or archiving older data to save space.

OPTIONS

The following options are available:

-f
Force the creation of a storage class even if a class with the same name already exists. This will overwrite the existing class definition.
-C <chunk creation>
Specifies the storage policy for newly created chunks. This policy is active immediately after a chunk is created. The format follows the syntax used by the mfssclass(1) command, for example, 2* means 2 copies on any available chunkservers.
-K <chunk keep>
Specifies the storage policy for chunks that need to be kept for a longer period. This policy typically applies after the initial creation phase or after a certain time has passed. The format is the same as for the -C option.
-A <chunk archive>
Specifies the storage policy for archiving chunks. This is typically used for long-term storage or when data is no longer actively accessed. The format allows specifying erasure coding profiles, e.g., @4+1 for a 4 data + 1 parity erasure coding scheme.
-d <deletion delay>
Sets a delay before chunks are considered for deletion based on the storage class policy. The delay can be specified in days (e.g., 2d), hours (e.g., 48h), or minutes (e.g., 120m).
-o <deletion mode>
Defines the mode for chunk deletion. Common modes include:
m
Deletion based on metadata change time.
c
Deletion based on chunk creation time.
This option is often used in conjunction with the -d option.

NOTES

Predefined storage classes are created automatically by MooseFS for compatibility reasons, but will behave exactly like any user-defined classes. This information is left here purely for informative reasons and will be removed from this manual page at some point:

(Behaviour up to version 4.56.0) "For compatibility reasons, every fresh or freshly upgraded instance of MooseFS has 9 predefined storage classes. Their names are single digits, from 1 to 9, and their definitions are * to 9*. They are equivalents of simple numeric goals from previous versions of the system. In case of an upgrade, all files that had goal N before upgrade, will now have N storage class. These classes can be modified only when option -f is specified. It is advised to create new storage classes in an upgraded system and migrate files with mfsxchgsclass tool, rather than modify the predefined classes. The predefined classes CANNOT be deleted."

EXAMPLES

Create a new storage class named "Class2Copies" with 2 copies. The first copy on one of chunkservers with label "A" and the second copy on one of chunkservers with label "B":

mfscreatesclass -K A,B Class2Copies

Create a new storage class named "Class3Copies". Freshly created chunks (-C) will be kept anywhere with 2 copies (2*). Soon after creation they will be kept (-K) in 3 copies: the first copy on one of chunkservers with label "A", the second copy on one of chunkservers with label "B" and the third on any chunkserver:

mfscreatesclass -C '2*' -K 'A,B,*' Class3Copies

Create a new storage class named "ClassEC4_1". Chunks will be created and kept (-K) anywhere in 2 copies (2*) for 24 hours from the file creation. Later they will be archived (-A) in EC4+1 format on any chunkserver:

mfscreatesclass -K '2*' -A '@4+1' ClassEC4_1

Modify the "ClassEC4_1" storage class to archive chunks after 48 hours from the file modification (not creation):

mfsmodifysclass -d 2d -o m ClassEC4_1

Modify the "Class3Copies" storage class to keep chunks on other chunkservers (LOOSE mode) if the ones with labels "A" and "B" are too busy (overloaded):

mfsmodifysclass -m l Class3Copies
