DESCRIPCIÓN

Este es un conjunto de herramientas para administrar las clases de almacenamiento de MooseFS. Las clases de almacenamiento se utilizan para definir la política de redundancia dentro del clúster. Posteriormente deben aplicarse a objetos particulares de MooseFS (archivos o carpetas) con las herramientas mfssclass (ver mfssclass(1)). Una clase de almacenamiento es un conjunto con nombre de expresiones de etiquetas y otras opciones. La expresión de etiquetas indica el formato de redundancia, el nivel de redundancia deseado y la política de almacenamiento deseada. El formato de redundancia puede ser copias o codificación de eliminación (EC). El nivel de redundancia es el número de copias (de 1 a 9) o el número de partes de datos más paridad (4+n u 8+n), dependiendo del formato de redundancia indicado. La política de almacenamiento especifica, mediante el uso de etiquetas, qué servidores de fragmentos (chunkservers) se utilizarán para el almacenamiento físico de los datos asignados a la clase de almacenamiento particular.

mfscreatesclass crea una nueva clase de almacenamiento con las opciones dadas, descritas a continuación, y la nombra NOMBRE_CLASE_ALMACENAMIENTO; se pueden proporcionar varios nombres, creando entonces múltiples clases de almacenamiento con la misma definición.

mfsmodifysclass cambia las opciones dadas en una clase o clases indicadas por los parámetros NOMBRE_CLASE_ALMACENAMIENTO.

mfsdeletesclass elimina la(s) clase(s) indicada(s) por los parámetros NOMBRE_CLASE_ALMACENAMIENTO; si alguna de las clases no está vacía (es decir, todavía es utilizada por algún objeto de MooseFS), no se eliminará y la herramienta devolverá un error y se imprimirá un mensaje de error; las clases vacías se eliminarán en cualquier caso.

mfsclonesclass copia la clase indicada por NOMBRE_CLASE_ORIGEN con un nuevo nombre proporcionado en NUEVO_NOMBRE_CLASE_DESTINO.

mfsrenamesclass cambia el nombre de una clase de NOMBRE_CLASE_ORIGEN a NUEVO_NOMBRE_CLASE_DESTINO.

mfslistsclass lista todas las clases.

mfsimportsclass importa definiciones de clases de almacenamiento desde stdin o un archivo y las crea; el formato de entrada debe ser idéntico a la salida de mfslistsclass -l.

OPCIONES

-C parámetro opcional, que indica al sistema a qué servidores de fragmentos, definidos por la expresión CREATE_LABELS, se escribirá primero el fragmento justo después de su creación; si este parámetro no se proporciona para una clase, se utilizarán los servidores de fragmentos de KEEP_LABELS.

-K parámetro obligatorio, que indica al sistema en qué servidores de fragmentos, definidos por la expresión KEEP_LABELS, se mantendrán siempre los fragmentos, excepto en condiciones especiales como creación, archivo y eliminación (movimiento a la Papelera), si están definidas.

-A parámetro opcional, que indica al sistema en qué servidores de fragmentos, definidos por la expresión ARCH_LABELS, se mantendrán los fragmentos con fines de archivo; el sistema comienza a tratar un fragmento como archivo cuando atime/mtime/ctime (según lo establecido por -o) del archivo al que pertenece es anterior al número de horas especificado con la opción -d; ver también la sección COMPORTAMIENTO DE ARCHIVO a continuación.

-d parámetro opcional que define después de cuánto tiempo desde atime/mtime/ctime (según lo establecido por -o) un archivo (y sus fragmentos) se tratan como archivo; la unidad mínima es horas, el valor predeterminado es 24, para el formato del valor ver TIEMPO.

-o parámetro opcional que define las banderas de archivo. C - ctime, M - mtime, A - atime, R - reversible, F - modo rápido, P - por fragmento; el valor predeterminado es C; ver la sección COMPORTAMIENTO DE ARCHIVO para más detalles.

-s parámetro opcional que define la longitud mínima del archivo en bytes que puede ser archivada; el valor predeterminado es 0.

-T parámetro opcional, que indica al sistema en qué servidores de fragmentos, definidos por la expresión TRASH_LABELS, se mantendrán los fragmentos de archivos en la Papelera; ver también -t.

-t parámetro opcional, que define cuánto tiempo en la Papelera debe dejarse para que el sistema utilice realmente el esquema definido en -T para un fragmento; la unidad mínima es horas, el valor predeterminado es 0, para el formato del valor ver TIEMPO.

-c parámetro opcional, que define una descripción de clase, para conveniencia del usuario (una cadena, longitud máxima es 255 bytes).

-p parámetro opcional, que define una prioridad de clase; el valor predeterminado es 0, ver la sección PRIORIDAD DE CLASES DE ALMACENAMIENTO.

-g parámetro opcional, que define un grupo de exportación de clase; los valores posibles son de 0 a 15, el valor predeterminado es 0; ver mfsexport.cfg(5) para una explicación.

-a puede ser 1 o 0 e indica si la clase de almacenamiento está disponible para todos (0) o solo para administradores (1).

-m modo de etiqueta utilizado; los valores posibles son l (o L, loose, Loose, LOOSE) para el modo LOOSE, d (o D, std, Std, STD) para el modo STANDARD y s (o S, strict, Strict, STRICT) para el modo STRICT; si no se define ningún modo, se asume el modo STANDARD; el comportamiento de los modos de etiqueta se describe a continuación en la sección MODOS DE ETIQUETA.

-l lista también las definiciones, no solo los nombres de las clases de almacenamiento existentes.

-i coincidencia de nombres de clases de almacenamiento insensible a mayúsculas y minúsculas.

-r reemplaza (sobrescribe) las clases existentes al importar clases de almacenamiento.

-n usa el nombre de archivo proporcionado como fuente de definiciones de clases de almacenamiento para importar, en lugar de stdin.

-M punto de montaje de MooseFS, no es necesario especificarlo si la herramienta se ejecuta dentro de un directorio montado con MooseFS o si MooseFS está montado en /mnt/mfs/.

-? muestra un mensaje de uso corto.

NOTAS

EXPRESIONES DE ETIQUETAS

Las etiquetas son letras (A-Z - 26 letras) que se pueden asignar a los servidores de fragmentos. Cada servidor de fragmentos puede tener múltiples (hasta 26) etiquetas. Las etiquetas se definen en el archivo mfschunkserver.cfg, para más información consulte la página de manual correspondiente.

La expresión de etiquetas es un conjunto de subexpresiones separadas por comas. Para copias completas, cada subexpresión especifica el esquema de almacenamiento de una copia de un archivo. La subexpresión puede ser: un asterisco o un esquema de etiquetas. El esquema de etiquetas puede ser una etiqueta o una expresión con sumas, multiplicaciones, negaciones y paréntesis. La suma significa que un archivo puede almacenarse en cualquier servidor de fragmentos que coincida con cualquier elemento de la suma (lógico o). La multiplicación significa que un archivo solo puede almacenarse en un servidor de fragmentos que coincida con todos los elementos (lógico y). El asterisco significa cualquier servidor de fragmentos. La negación significa cualquier servidor de fragmentos excepto el que coincide con la subexpresión negada. Las subexpresiones idénticas se pueden acortar añadiendo un número delante de una en lugar de repetirla varias veces.

Para EC, la expresión de etiquetas comienza con el signo @, seguido del número de partes de datos y luego el signo + y un número que indica cuántas partes de paridad debe tener el fragmento. Número posible

Este sitio no está asociado de ninguna forma con Arch Linux ni afiliado a este proyecto. El contenido es únicamente una traducción de las páginas del manual de Arch publicadas en man.archlinux.org.

Los números de partes de datos son 4 u 8. El número posible de partes de paridad es 1 (versión CE) o de 1 a 9 (versión PRO). Así, por ejemplo, @4+1 significa EC con 4 partes de datos y 1 parte de paridad, @8+3 significa EC con 8 partes de datos y 3 partes de paridad. Si se omite el número de partes de datos, el maestro utiliza el valor predeterminado definido en DEFAULT_EC_DATA_PARTS; consulte mfsmaster.cfg (5). En este caso, @2 significa @8+2 o @4+2. Luego, pueden seguir un máximo de dos subexpresiones, separadas por comas. Si solo hay una, define dónde se mantendrán todas las partes. Si ambas están presentes, la primera subexpresión define dónde se mantendrán las partes de datos y la segunda subexpresión define dónde se mantendrán las partes de paridad.

La expresión de etiquetas puede ser una expresión de etiquetas regular o una expresión de etiquetas EC (es decir, una expresión de etiquetas EC no puede ser una subexpresión). La expresión de etiquetas EC solo se puede utilizar en lugar de ARCHIVE_LABELS o TRASH_LABELS en la definición de la clase de almacenamiento; la expresión de etiquetas regular se puede usar en cualquier lugar.

Al final de cada expresión de etiquetas, se puede agregar una o dos informaciones adicionales, divididas por un separador especial. La primera extensión posible es la extensión de distinción y el separador es la barra (/). La segunda es la anulación del modo de etiquetas y esta extensión está separada por dos puntos (:).

La extensión de distinción puede ser una lista de etiquetas o una de las siguientes cadenas especiales:

[IP] o [I] - distinguir por número IP

[RACK] o [R] - distinguir por RACK, según se define en la topología; consulte mfstopology.cfg (5)

Si está presente, la parte de distinción informa al sistema que debe intentar distribuir copias completas de manera que cada copia esté en una etiqueta diferente de la lista, o en un chunkserver con una dirección IP diferente, o en un rack diferente. Para EC, la parte de distinción se ignora actualmente.

¡AVISO! Si CHUNKS_UNIQUE_MODE está definido en mfsmaster.cfg con un valor distinto de 0, anulará cualquier configuración de distinción en las clases de almacenamiento. Para obtener más información sobre este parámetro, consulte el manual de mfsmaster.cfg (5).

La extensión de anulación del modo de etiquetas puede ser uno de tres caracteres: d (alternativamente D o en forma de cadena std o Std o STD), s (alternativamente S o en forma de cadena strict o Strict o STRICT) o l (alternativamente L o en forma de cadena loose o Loose o LOOSE) y significan que el modo de etiquetas ESTÁNDAR, ESTRICTO o SUELTO, respectivamente, debe aplicarse solo a esta expresión de etiquetas. Para obtener una explicación sobre los modos de etiquetas, consulte la sección MODOS DE ETIQUETAS.

Se pueden presentar una o ambas extensiones para cada expresión de etiquetas; cada una debe comenzar con su separador y, si ambas están presentes, se debe mantener el orden, es decir, la extensión de distinción debe ser la primera y la extensión del modo de etiquetas debe ser la segunda.

Ejemplos de expresiones de etiquetas:

A,B - los archivos tendrán dos copias, una copia se almacenará en chunkservers con la etiqueta A y la otra en chunkservers con la etiqueta B

A,* - los archivos tendrán dos copias, una copia se almacenará en chunkservers con la etiqueta A y la otra en cualquier chunkserver

A,!A - los archivos tendrán dos copias, una copia se almacenará en chunkservers con la etiqueta A y la otra en cualquier chunkserver que no tenga la etiqueta A

*,* - los archivos tendrán dos copias, almacenadas en cualquier chunkserver (diferente para cada copia)

AB,C+D+E - los archivos tendrán dos copias, una copia se almacenará en cualquier chunkserver que tenga ambas etiquetas A y B (multiplicación de etiquetas), la otra en cualquier chunkserver que tenga la etiqueta C o la etiqueta D o la etiqueta E (suma de etiquetas)

A,B[X+Y],C[X+Y] - los archivos tendrán tres copias, una copia se almacenará en cualquier chunkserver con la etiqueta B y ya sea la etiqueta X o la Y, la segunda en cualquier chunkserver que tenga la etiqueta A, la tercera en cualquier chunkserver que tenga la etiqueta C y ya sea la etiqueta X o la Y

La expresión 2A es equivalente a la expresión A,A

La expresión A,3BC es equivalente a la expresión A,BC,BC,BC

La expresión 2 es equivalente a la expresión 2* es equivalente a la expresión *,*

3*/[IP] - los archivos tendrán 3 copias, cada copia se mantendrá en un chunkserver con una dirección IP diferente

A,B/[RACK] - los archivos tendrán dos copias, una copia se almacenará en chunkservers con la etiqueta A, la otra en chunkservers con la etiqueta B en un rack diferente al de la otra copia

S,H,H/[RACK] - los archivos tendrán 3 copias, una en un servidor con etiqueta S, dos en servidores con etiqueta H, pero cada copia estará en un servidor con una etiqueta diferente del conjunto de etiquetas A, B, X, Y, Z

@4+1 - los archivos se mantendrán en formato EC, 4 partes de datos y 1 parte de paridad

@8+3 - los archivos se mantendrán en formato EC, 8 partes de datos y 3 partes de paridad

@2 - los archivos se mantendrán en formato EC, número predeterminado de partes de datos, 2 partes de paridad

@4+3,Z - los archivos se mantendrán en formato EC, 4 partes de datos y 3 partes de paridad; todas se mantendrán en chunkservers con la etiqueta Z.

@2,A(X+Y) - los archivos se mantendrán en formato EC, número predeterminado de partes de datos, 2 partes de paridad; todas las partes se mantendrán en chunkservers con la etiqueta A y ya sea X o Y

@3,S,H - los archivos se mantendrán en formato EC, el número predeterminado de partes de datos se mantendrá en chunkservers con la etiqueta S, 3 partes de paridad se mantendrán en chunkservers con la etiqueta H

AB,AC:l - los archivos se mantendrán en formato de copias, una copia en un servidor con las etiquetas A y B, la segunda en un servidor con las etiquetas A y C y el comportamiento de esto será LOOSE

@4+2,X,Y:s - los archivos se mantendrán en formato EC, 4 partes de datos se mantendrán en servidores con la etiqueta X, 2 partes de paridad (checksum) se mantendrán en servidores con la etiqueta Y y el comportamiento de esto será STRICT

2A/[IP]:s - los archivos se mantendrán en 2 copias, ambas copias en servidores con etiqueta A, pero cada servidor tendrá una IP diferente, el comportamiento de esto al tener en cuenta las etiquetas será STRICT

MODOS DE ETIQUETAS

Es importante especificar qué hacer cuando no es posible cumplir los requisitos de etiquetas de una clase de almacenamiento, es decir: no hay espacio disponible en todos los servidores con las etiquetas necesarias, no hay suficientes servidores con las etiquetas necesarias o los servidores con las etiquetas necesarias están todos ocupados. La pregunta es si el sistema debe crear chunks en otros servidores (con etiquetas no coincidentes) o no. Esta decisión debe ser tomada por el usuario.

Hay 3 modos de operación: ESTÁNDAR, SUELTO y ESTRICTO. Los modos funcionan de manera un poco diferente dependiendo de si un chunk se almacena en formato de copias o EC, debido a la diferente naturaleza y algoritmos que cada uno de esos formatos utiliza.

Para el formato de copias, los 3 modos se comportan de la siguiente manera:

En modo ESTÁNDAR, en caso de servidores sobrecargados, el sistema esperará, pero en caso de falta de espacio, utilizará otros servidores y replicará los datos a los servidores correctos cuando sea posible. Esto significa que si algunos servidores están en estado de ocupado durante mucho tiempo, puede que no sea posible crear nuevos chunks con ciertas clases de almacenamiento y los chunks en peligro (por debajo del objetivo) de esas clases corren un mayor riesgo de perderse por completo debido a las replicaciones retrasadas.

En modo ESTRICTO, durante la escritura de un nuevo archivo, el sistema devolverá un error (ENOSPC) en caso de falta de espacio en los servidores marcados con las etiquetas especificadas para la creación de chunks. Aún así, esperará a los servidores sobrecargados. Las replicaciones por debajo del objetivo no se realizarán si no hay espacio en los servidores con etiquetas que coincidan con la clase de almacenamiento. Esto significa un alto riesgo de pérdida de datos si los servidores con algunas etiquetas se llenan permanentemente de datos.

En modo SUELTO, el sistema utilizará inmediatamente otros servidores en caso de servidores sobrecargados o falta de espacio en los servidores y replicará los datos a los servidores correctos cuando sea posible. No hay retrasos ni errores en la creación de archivos y las replicaciones por debajo del objetivo siempre se realizan lo antes posible.

Esta tabla resume el comportamiento de los modos para los chunks almacenados en formato de copia:

ESTÁNDAR ESTRICTO SUELTO
CREAR - SOBRECARGADO ESPERAR ESPERAR ESCRIBIR CUALQUIERA
CREAR - SIN ESPACIO ESCRIBIR CUALQUIERA ENOSPC ESCRIBIR CUALQUIERA
REPLICAR - SOBRECARGADO ESPERAR ESPERAR ESCRIBIR CUALQUIERA
REPLICAR - SIN ESPACIO ESCRIBIR CUALQUIERA SIN COPIA ESCRIBIR CUALQUIERA

Para los chunks almacenados en formato EC, los 3 modos se comportan de la siguiente manera:

En general, los chunks solo se convertirán de formato de copia a formato EC si hay suficientes servidores en el sistema para almacenar de forma segura todas las partes del formato EC. Para el formato EC @N+X, donde N es el número de partes de datos y puede ser 4 u 8, y X es el número de partes de paridad/checksum y puede ser 1 (versión CE) o cualquier número de 1 a 9 (versión PRO), los requisitos generales son:
- al menos N+2X chunkservers para convertir nuevos chunks de formato de copia a formato EC
- al menos N+X chunkservers para mantener los chunks que ya están en formato EC en ese formato
- si hay menos de N+X servidores, todos los chunks volverán al formato de copia (definición KEEP).

En modo SUELTO, el sistema utilizará primero los servidores que coincidan con la expresión de etiquetas definida en la clase de almacenamiento utilizada, pero si no hay suficientes servidores con etiquetas "correctas" disponibles (porque están ocupados, no tienen espacio o simplemente no están definidos), utilizará cualquier chunkserver disponible independientemente de la etiqueta; por lo tanto, N+2X y N+X se calculan a partir de todos los chunkservers disponibles cuando el sistema decide qué formato utilizar para mantener un chunk. Además, cuando una parte de un chunk en formato EC no está disponible o está corrupta, la restauración de dicha parte también se realizará en cualquier servidor disponible, si un servidor con etiquetas "correctas" no puede ser utilizado actualmente.

Es importante recordar que si no hay suficientes servidores con etiquetas "correctas" disponibles para un chunk en modo SUELTO, el sistema puede utilizar tantos servidores "otros" como desee, no solo la cantidad mínima que falta del número "correcto" de servidores.

En caso de partes faltantes, si no es posible restaurarlas en servidores de fragmentos con etiquetas "correctas", el sistema también adaptará el comportamiento del modo LOOSE e intentará utilizar cualquier servidor disponible.

¡Atención! Cuando un fragmento se convierte de formato de copia a formato EC, el sistema primero realiza una operación de "división local", es decir, selecciona una copia del fragmento y calcula todas las partes EC necesarias en el servidor ocupado por esta copia seleccionada. Luego, estas partes se mueven a servidores de fragmentos separados, que coinciden con las etiquetas en la definición de la clase de almacenamiento para el modo EC utilizado. Pero temporalmente, entre la división y la "salida" de las partes, se pueden registrar en un servidor de fragmentos "incorrecto" incluso en modo STRICT. Esto se debe a la mecánica de la operación de "división local".

TIEMPO

Para las variables de tiempo, su valor puede definirse como un número de segundos u horas (entero), dependiendo de la unidad mínima de la variable, o como un período de tiempo en uno de dos formatos posibles:

primer formato: #.#T donde T es una de: s-segundos, m-minutos, h-horas, d-días o w-semanas; las fracciones de la unidad mínima se redondearán al valor entero

segundo formato: #w#d#h#m#s, se puede omitir cualquier número de definiciones, pero las definiciones restantes deben estar en orden (por lo que #d#m sigue siendo una definición válida, pero #m#d no lo es); rangos: s,m: 0 a 59, h: 0 a 23, d: 0 a 6, w es ilimitado y la primera definición también es siempre ilimitada (es decir, para #d#h#m d será ilimitado)

Si la unidad mínima de una variable es mayor que los segundos, no se aceptarán las unidades inferiores a la unidad mínima. Por ejemplo, una variable que tenga horas como unidad mínima no aceptará unidades s y m.

Ejemplos:

1.5d es lo mismo que 1d12h, es lo mismo que 36h

2.5w es lo mismo que 2w3d12h, es lo mismo que 420h; 2w84h no es un período de tiempo válido (h no es la primera definición, por lo que está limitado por el rango de 0 a 23)

COMPORTAMIENTO DE ARCHIVO

Las etiquetas de archivo se establecen en los fragmentos durante el bucle de mantenimiento de archivos, lo que significa que el tiempo para el archivo definido por la opción -d es el tiempo mínimo que debe transcurrir antes de que se establezca la etiqueta, no el tiempo exacto.

El comportamiento predeterminado del sistema es que una vez que un fragmento tiene la etiqueta de archivo activada, NO se desactiva incluso si atime/ctime/mtime cambian, a menos que la bandera R se establezca mediante la opción -o. Escribir en un fragmento siempre desactivará su etiqueta de archivo.

Etiquetas de archivo:

C - utiliza ctime del archivo para determinar si la etiqueta de archivo debe activarse; esta es la etiqueta predeterminada

M - utiliza mtime del archivo para determinar si la etiqueta de archivo debe activarse

A - utiliza atime del archivo para determinar si la etiqueta de archivo debe activarse

R - reversible, si atime/mtime/ctime cambian para un archivo, el sistema verifica si la etiqueta de archivo debe desactivarse para sus fragmentos

F - modo rápido, la etiqueta de archivo del fragmento se activa lo antes posible, se ignora cualquier cosa definida con la opción -d

P - modo "por fragmento", utiliza mtime del fragmento para determinar si la etiqueta de archivo debe activarse

La etiqueta de archivo se puede modificar manualmente. Consulte mfsarchive (1)

Nota: el estado ARCHIVE no significa que los fragmentos o archivos sean de alguna manera inaccesibles, bloqueados para escritura, etc. La designación ARCHIVE solo se utiliza para indicar que dichos datos ya están destinados al almacenamiento a largo plazo. En contraste con el estado KEEP, que significa que los datos están 'calientes' y pueden cambiarse con frecuencia. Por lo tanto, la distinción entre los estados KEEP y ARCHIVE es solo para permitir una definición apropiada de la forma física de almacenar estos datos. Desde el punto de vista del usuario, el archivo es igualmente accesible: tiene permisos, nombre idénticos y está en el mismo directorio. Por ejemplo, debido al hecho de que escribir en modo EC puede ser más lento, sugerimos almacenar datos 'calientes' (KEEP) usando una copia y cambiarlos a formato EC (asignando el modo ARCHIVE) después de algún tiempo. Otro ejemplo es la transferencia automática de datos 'fríos' a discos y servidores de fragmentos más antiguos/más lentos/más baratos, utilizando etiquetas diferentes.

PRIORIDAD DE CLASES DE ALMACENAMIENTO

Las clases de almacenamiento se asignan a los archivos, pero un fragmento (una parte de un archivo) puede pertenecer a muchos archivos, gracias al mecanismo de instantáneas (ver mfssnapshots (1)). Si un fragmento pertenece a muchos archivos con diferentes clases de almacenamiento, se debe elegir una clase de almacenamiento para especificar cómo se deben conservar las copias de este fragmento en el sistema. Hasta la versión 4.56.0 de MooseFS, se asignaba artificialmente una clase predefinida a dicho fragmento. Actualmente, se utilizará una de las clases de los archivos, de acuerdo con las prioridades asignadas por el usuario, para ser exactos: el sistema seleccionará la clase con la prioridad más alta de entre todas las clases de los archivos.

Ejemplo 1: hay 3 clases definidas:
ClassA, con prioridad 100,
ClassB, con prioridad 206,
ClassC, con prioridad 1001.

Un fragmento, que pertenece a 2 archivos, uno en ClassA y el otro en ClassB, se almacenará de acuerdo con la definición proporcionada por classB (mayor prioridad que ClassA).
Un fragmento, que pertenece a 3 archivos, uno en ClassA, uno en ClassB y uno en ClassC, se almacenará de acuerdo con la definición proporcionada por classC (mayor prioridad que ambas ClassA y ClassB).

Si dos o más clases tienen la misma prioridad, entonces se considerarán los siguientes factores, en orden de importancia, para determinar cuál clase se elegirá:
- se elegirá una clase con un nivel de redundancia (RL) más alto (se considerará el máximo de los niveles de redundancia KEEP y ARCHIVE de cada clase como el nivel de redundancia de esta clase),
- se elegirá una clase que tenga formato EC en estado ARCHIVE sobre una clase sin EC,
- se elegirá una clase que utilice etiquetas para el estado KEEP o ARCHIVE sobre una clase sin etiquetas,
- se elegirá una clase que tenga formato EC en estado TRASH sobre una clase sin EC,
- se elegirá una clase que utilice etiquetas para el estado TRASH sobre una clase sin etiquetas,
- si ninguna de las condiciones anteriores se utiliza, se utilizará una clase con un ID de clase más alto.

Ejemplo 2: hay 5 clases definidas, todas con la misma prioridad (por ejemplo, la prioridad predeterminada 0):
ClassA (id=1) tiene 3 copias en estado KEEP (RL=2),
ClassB (id=2) tiene 2 copias en estado KEEP y EC4+1 en estado ARCHIVE (RL=1, tiene EC en ARCHIVE),
ClassC (id=3) tiene 2 copias en estado KEEP, almacenadas en etiquetas X (RL=1, sin EC en ARCHIVE, tiene etiquetas en KEEP),
ClassD (id=4) tiene 2 copias en estado KEEP, almacenadas en etiquetas Y (RL=1, sin EC en ARCHIVE, tiene etiquetas en KEEP),
ClassE (id=5) tiene 2 copias en estado KEEP (RL=1).
También hay una clase ClassF definida, que tiene una prioridad de 77 y 2 copias en estado KEEP (RL=1).

Un fragmento, que pertenece a archivos en las clases: ClassA, ClassC y ClassE, se almacenará de acuerdo con la definición de ClassA (RL más alto).
Un fragmento, que pertenece a archivos en las clases: ClassB, ClassC, se almacenará de acuerdo con la definición de ClassB (mismo RL, pero ClassB tiene EC).
Un fragmento, que pertenece a archivos en las clases: ClassC y ClassE, se almacenará de acuerdo con la definición de ClassC (mismo RL, pero ClassC tiene etiquetas).
Un fragmento, que pertenece a archivos en las clases: ClassC y ClassD, se almacenará de acuerdo con la definición de ClassD (mismo RL, sin EC, ambos tienen etiquetas, por lo que se elige el ID de clase más alto).
Un fragmento, que pertenece a archivos en 6 clases, de ClassA a ClassF, se almacenará de acuerdo con la definición de ClassF, porque esta tiene una prioridad más alta que todas las demás clases (77>0).
En un sistema con estas 6 clases de almacenamiento, classE nunca se utilizará para un fragmento que pertenezca a múltiples archivos, tiene la prioridad más baja posible (0) y ninguna condición adicional para justificar su elección (RL existente más bajo, sin EC y sin etiquetas).

CLASES DE ALMACENAMIENTO PREDETERMINADAS

Una nueva instancia de MooseFS tendrá las siguientes clases predeterminadas:

2CP - solo se define el estado KEEP, se conservan 2 copias en cualquier etiqueta (clase predeterminada para el directorio /)

3CP - solo se define el estado KEEP, se conservan 3 copias en cualquier etiqueta

EC4+1 - en estado KEEP, se conservan 2 copias en cualquier etiqueta, en estado ARCHIVE, se conservan fragmentos en formato EC4+1 en cualquier etiqueta, el retraso del archivo es de 1 día y se calcula utilizando el ctime del archivo, los archivos más pequeños que 512kiB no se convertirán a formato EC

EC4+2 - (solo pro) en estado KEEP, se conservan 3 copias en cualquier etiqueta, en estado ARCHIVE, se conservan fragmentos en formato EC4+2 en cualquier etiqueta, el retraso del archivo es de 1 día y se calcula utilizando el ctime del archivo, los archivos más pequeños que 512kiB no se convertirán a formato EC

EC8+1 - en estado KEEP, se conservan 2 copias en cualquier etiqueta, en estado ARCHIVE, se conservan fragmentos en formato EC8+1 en cualquier etiqueta, el retraso del archivo es de 1 día y se calcula utilizando el ctime del archivo, los archivos más pequeños que 512kiB no se convertirán a formato EC

EC8+2 - (solo pro) en estado KEEP, se conservan 3 copias en cualquier etiqueta, en estado ARCHIVE, se conservan fragmentos en formato EC8+2 en cualquier etiqueta, el retraso del archivo es de 1 día y se calcula utilizando el ctime del archivo, los archivos más pequeños que 512kiB no se convertirán a formato EC

Estas clases son totalmente modificables y eliminables y pueden ser reemplazadas por la elección de clases del usuario.

Hasta la versión 4.56.0 de MooseFS, las clases predeterminadas eran diferentes. La siguiente información se refiere al comportamiento antiguo de MooseFS. En versiones más recientes de MooseFS, las clases mencionadas a continuación podrían existir

como resultado de una actualización, pero se comportarán exactamente como cualquier clase definida por el usuario. Esta información se deja aquí puramente con fines informativos y se eliminará de esta página del manual en algún momento:

(Comportamiento hasta la versión 4.56.0) "Por motivos de compatibilidad, cada instancia nueva o recién actualizada de MooseFS tiene 9 clases de almacenamiento predefinidas. Sus nombres son dígitos individuales, del 1 al 9, y sus definiciones son * a 9*. Son equivalentes a los objetivos numéricos simples de versiones anteriores del sistema. En caso de una actualización, todos los archivos que tenían el objetivo N antes de la actualización, ahora tendrán la clase de almacenamiento N. Estas clases solo se pueden modificar cuando se especifica la opción -f. Se recomienda crear nuevas clases de almacenamiento en un sistema actualizado y migrar archivos con la herramienta mfsxchgsclass, en lugar de modificar las clases predefinidas. Las clases predefinidas NO SE PUEDEN eliminar."

EJEMPLOS

Crear una nueva clase de almacenamiento llamada "Class2Copies" con 2 copias. La primera copia en un servidor de fragmentos con la etiqueta "A" y la segunda copia en un servidor de fragmentos con la etiqueta "B":

mfscreatesclass -K A,B Class2Copies

Crear una nueva clase de almacenamiento llamada "Class3Copies". Los fragmentos recién creados (-C) se mantendrán en cualquier lugar con 2 copias (2*). Poco después de su creación, se mantendrán (-K) en 3 copias: la primera copia en un servidor de fragmentos con la etiqueta "A", la segunda copia en un servidor de fragmentos con la etiqueta "B" y la tercera en cualquier servidor de fragmentos:

mfscreatesclass -C '2*' -K 'A,B,*' Class3Copies

Crear una nueva clase de almacenamiento llamada "ClassEC4_1". Los fragmentos se crearán y mantendrán (-K) en cualquier lugar en 2 copias (2*) durante 24 horas desde la creación del archivo. Más tarde se archivarán (-A) en formato EC4+1 en cualquier servidor de fragmentos:

mfscreatesclass -K '2*' -A '@4+1' ClassEC4_1

Modificar la clase de almacenamiento "ClassEC4_1" para archivar los fragmentos después de 48 horas desde la modificación (no creación) del archivo:

mfsmodifysclass -d 2d -o m ClassEC4_1

Modificar la clase de almacenamiento "Class3Copies" para mantener los fragmentos en otros servidores de fragmentos (modo LOOSE) si los que tienen las etiquetas "A" y "B" están demasiado ocupados (sobrecargados):

mfsmodifysclass -m l Class3Copies
