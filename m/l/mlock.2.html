mlock(2) Manual de Llamadas al Sistema mlock(2)

NOMBRE

mlock, mlock2, munlock, mlockall, munlockall - bloquear y desbloquear memoria

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

SINOPSIS

#include <sys/mman.h>
int mlock(const void addr[size], size_t size);
int mlock2(const void addr[size], size_t size, unsigned int flags);
int munlock(const void addr[size], size_t size);
int mlockall(int flags);
int munlockall(void);

DESCRIPCIÓN

mlock(), mlock2() y mlockall() bloquean parte o la totalidad del espacio de direcciones virtual del proceso que llama en la RAM, evitando que esa memoria sea paginada al área de intercambio.

munlock() y munlockall() realizan la operación inversa, desbloqueando parte o la totalidad del espacio de direcciones virtual del proceso que llama, de modo que las páginas en el rango de direcciones virtuales especificado puedan ser intercambiadas de nuevo si es necesario por el gestor de memoria del kernel.

El bloqueo y desbloqueo de memoria se realizan en unidades de páginas enteras.

mlock(), mlock2(), y munlock()

mlock() bloquea las páginas en el rango de direcciones que comienza en addr y continúa durante size bytes. Se garantiza que todas las páginas que contienen una parte del rango de direcciones especificado están residentes en RAM cuando la llamada retorna con éxito; se garantiza que las páginas permanecerán en RAM hasta que se desbloqueen posteriormente.

mlock2() también bloquea las páginas en el rango especificado que comienza en addr y continúa durante size bytes. Sin embargo, el estado de las páginas contenidas en ese rango después de que la llamada retorne con éxito dependerá del valor del argumento flags.

El argumento flags puede ser 0 o la siguiente constante:

MLOCK_ONFAULT
Bloquea las páginas que actualmente están residentes y marca todo el rango para que las páginas no residentes restantes se bloqueen cuando se pueblen mediante una falla de página.

Si flags es 0, mlock2() se comporta exactamente igual que mlock().

munlock() desbloquea las páginas en el rango de direcciones que comienza en addr y continúa durante size bytes. Después de esta llamada, todas las páginas que contienen una parte del rango de memoria especificado pueden ser movidas al espacio de intercambio externo nuevamente por el kernel.

mlockall() y munlockall()

mlockall() bloquea todas las páginas mapeadas en el espacio de direcciones del proceso que llama. Esto incluye las páginas del código, datos y segmento de pila, así como bibliotecas compartidas, datos del kernel en espacio de usuario, memoria compartida y archivos mapeados en memoria. Se garantiza que todas las páginas mapeadas están residentes en RAM cuando la llamada retorna con éxito; se garantiza que las páginas permanecerán en RAM hasta que se desbloqueen posteriormente.

El argumento flags se construye como el OR bit a bit de una o más de las siguientes constantes:

MCL_CURRENT
Bloquea todas las páginas que actualmente están mapeadas en el espacio de direcciones del proceso.
MCL_FUTURE
Bloquea todas las páginas que se mapearán en el espacio de direcciones del proceso en el futuro. Estas podrían ser, por ejemplo, nuevas páginas requeridas por un heap y una pila en crecimiento, así como nuevos archivos mapeados en memoria o regiones de memoria compartida.
MCL_ONFAULT (desde Linux 4.4)
Se utiliza junto con MCL_CURRENT, MCL_FUTURE, o ambos. Marca todas las páginas actuales (con MCL_CURRENT) o futuras (con MCL_FUTURE) para bloquearlas cuando se produzca una falla de página. Cuando se usa con MCL_CURRENT, todas las páginas presentes se bloquean, pero mlockall() no provocará fallos de página no presentes. Cuando se usa con MCL_FUTURE, todos los mapeos futuros se marcarán para bloquear páginas cuando ocurra una falla de página, pero no se poblarán con el bloqueo cuando se cree el mapeo. MCL_ONFAULT debe usarse con MCL_CURRENT o MCL_FUTURE o ambos.

Si se ha especificado MCL_FUTURE, entonces una llamada al sistema posterior (por ejemplo, mmap(2), sbrk(2), malloc(3)), puede fallar si resultara en que el número de bytes bloqueados excediera el máximo permitido (ver más abajo). En las mismas circunstancias, el crecimiento de la pila puede fallar de manera similar: el kernel denegará la expansión de la pila y entregará una señal SIGSEGV al proceso.

munlockall() desbloquea todas las páginas mapeadas en el espacio de direcciones del proceso que llama.

VALOR DE RETORNO

En caso de éxito, estas llamadas al sistema devuelven 0. En caso de error, se devuelve -1, se establece errno para indicar el error, y no se realizan cambios en ningún bloqueo en el espacio de direcciones del proceso.

ERRORES

EAGAIN
(mlock(), mlock2(), y munlock()) No se pudo bloquear todo o parte del rango de direcciones especificado.
EINVAL
(mlock(), mlock2(), y munlock()) El resultado de la suma addr+size fue menor que addr (por ejemplo, la suma pudo haber resultado en un desbordamiento).
EINVAL
(mlock2()) Se especificaron flags desconocidos.
EINVAL
(mlockall()) Se especificaron flags desconocidos o se especificó MCL_ONFAULT sin MCL_FUTURE o MCL_CURRENT.
EINVAL
(No en Linux) addr no era un múltiplo del tamaño de página.
ENOMEM
(mlock(), mlock2(), y munlock()) Parte del rango de direcciones especificado no corresponde a páginas mapeadas en el espacio de direcciones del proceso.
ENOMEM
(mlock(), mlock2(), y munlock()) Bloquear o desbloquear una región resultaría en que el número total de mapeos con atributos distintos (por ejemplo, bloqueados frente a desbloqueados) excediera el máximo permitido. (Por ejemplo, desbloquear un rango en el medio de un mapeo actualmente bloqueado resultaría en tres mapeos: dos mapeos bloqueados en cada extremo y un mapeo desbloqueado en el medio).
ENOMEM
(Linux 2.6.9 y posteriores) el llamador tenía un límite de recursos blando RLIMIT_MEMLOCK distinto de cero, pero intentó bloquear más memoria de la permitida por el límite. Este límite no se aplica si el proceso tiene privilegios (CAP_IPC_LOCK).
ENOMEM
(Linux 2.4 y anteriores) el proceso que llama intentó bloquear más de la mitad de la RAM.
EPERM
El llamador no tiene privilegios, pero necesita privilegios (CAP_IPC_LOCK) para realizar la operación solicitada.
EPERM
(munlockall()) (Linux 2.6.8 y anteriores) El llamador no tenía privilegios (CAP_IPC_LOCK).

NAME

mlock, munlock, mlockall, munlockall - lock memory pages in RAM

LIBRARY

Standard C library (libc, -lc)

SYNOPSIS

       int munlock(const void *addr, size_t len);

DESCRIPTION

Memory locking is a mechanism that allows a process to lock its own virtual memory pages into physical RAM, preventing them from being swapped out to secondary storage (disk).

The mlock() function locks the pages of memory indicated by the address range [addr, addr + len - 1]. All pages that contain any part of this range are locked. The range must be suitably aligned and should not exceed available memory.

The munlock() function unlocks the pages of memory indicated by the address range [addr, addr + len - 1].

The mlockall() function locks all pages of the calling process's virtual address space in RAM. The behavior is controlled by flags, which is a bitmask composed of one or more of the following values:

MCL_CURRENT
Lock all pages that are currently mapped for the process. This includes memory that has already been allocated and referenced.
MCL_FUTURE
Lock pages that will be mapped in the future. This affects future calls to mmap(2), brk(2), and other memory mapping and allocation functions. Memory mapped with this flag will be locked when it is mapped.
MCL_ONFAULT
(Since Linux 2.6.5) Lock pages in the future, but only when they are first accessed (i.e., on a page fault). This is useful for applications that deal with large mappings where only a small portion of the pages in the mapping are actually touched. In such cases, locking all of the pages in the mapping would incur a significant penalty.

The munlockall() function unlocks all pages that were locked by mlockall().

The mlock2() function is an extension that allows locking specified memory ranges with the MLOCK_ONFAULT flag.

MLOCK_ONFAULT
(Since Linux 4.4) Lock pages in the future, but only when they are first accessed. This is equivalent to using mlockall(MCL_ONFAULT) but applies to a specific memory range.

The flags MCL_FUTURE and MCL_ONFAULT are intended for real-time applications where deterministic execution is required. By locking memory pages, these applications can prevent unexpected delays caused by page swapping.

The effect of MCL_FUTURE is to automatically lock any pages that are subsequently mapped into the process's address space. This means that future calls to mmap(2), brk(2), and shared memory mapping functions will result in locked pages.

The effect of MCL_ONFAULT (either with mlockall() or mlock2()) is to lock pages only when they are accessed for the first time, triggering a page fault. This can be more efficient than locking all pages upfront if only a subset of the mapped memory is expected to be used.

The system enforces limits on the total amount of memory that can be locked by a process. These limits are controlled by resource limits (see setrlimit(2)) and capabilities.

On Linux, memory locks are not inherited by a child process created by fork(2). They are automatically removed (unlocked) when a process calls execve(2) or when the process terminates. The MCL_FUTURE and MCL_ONFAULT settings are also cleared by execve(2).

Pages that are locked remain locked until explicitly unlocked by munlock(2), munlockall(2), or until the process terminates. Locked pages are automatically unlocked when they are unmapped by munmap(2).

Memory locks do not stack. If a page is locked multiple times through different calls, a single unlock operation on that page will remove all locks on it. However, pages mapped into multiple locations or by multiple processes will remain locked as long as at least one lock is active.

The VmLck field of the Linux-specific /proc/pid/status file shows how many kilobytes of memory the process with ID PID has locked using mlock(), mlock2(), mlockall(), and mmap(2) MAP_LOCKED.

NOTES

Memory locking has two main applications: real-time algorithms and high-security data processing. Real-time applications require deterministic timing, and, like scheduling, paging is one major cause of unexpected program execution delays. Real-time applications will usually also switch to a real-time scheduler with sched_setscheduler(2). Cryptographic security software often handles critical bytes like passwords or secret keys as data structures. As a result of paging, these secrets could be transferred onto a persistent swap store medium, where they might be accessible to the enemy long after the security software has erased the secrets in RAM and terminated. (But be aware that the suspend mode on laptops and some desktop computers will save a copy of the system's RAM to disk, regardless of memory locks.)

Real-time processes that are using mlockall() to prevent delays on page faults should reserve enough locked stack pages before entering the time-critical section, so that no page fault can be caused by function calls. This can be achieved by calling a function that allocates a sufficiently large automatic variable (an array) and writes to the memory occupied by this array in order to touch these stack pages. This way, enough pages will be mapped for the stack and can be locked into RAM. The dummy writes ensure that not even copy-on-write page faults can occur in the critical section.

Memory locks are not inherited by a child created via fork(2) and are automatically removed (unlocked) during an execve(2) or when the process terminates. The mlockall() MCL_FUTURE and MCL_FUTURE | MCL_ONFAULT settings are not inherited by a child created via fork(2) and are cleared during an execve(2).

Note that fork(2) will prepare the address space for a copy-on-write operation. The consequence is that any write access that follows will cause a page fault that in turn may cause high latencies for a real-time process. Therefore, it is crucial not to invoke fork(2) after an mlockall() or mlock() operation—not even from a thread which runs at a low priority within a process which also has a thread running at elevated priority.

The memory lock on an address range is automatically removed if the address range is unmapped via munmap(2).

Memory locks do not stack, that is, pages which have been locked several times by calls to mlock(), mlock2(), or mlockall() will be unlocked by a single call to munlock() for the corresponding range or by munlockall(). Pages which are mapped to several locations or by several processes stay locked into RAM as long as they are locked at least at one location or by at least one process.

If a call to mlockall() which uses the MCL_FUTURE flag is followed by another call that does not specify this flag, the changes made by the MCL_FUTURE call will be lost.

The mlock2() MLOCK_ONFAULT flag and the mlockall() MCL_ONFAULT flag allow efficient memory locking for applications that deal with large mappings where only a (small) portion of pages in the mapping are touched. In such cases, locking all of the pages in a mapping would incur a significant penalty for memory locking.

Limits and permissions

In Linux 2.6.8 and earlier, a process must be privileged (CAP_IPC_LOCK) in order to lock memory and the RLIMIT_MEMLOCK soft resource limit defines a limit on how much memory the process may lock.

Since Linux 2.6.9, no limits are placed on the amount of memory that a privileged process can lock and the RLIMIT_MEMLOCK soft resource limit instead defines a limit on how much memory an unprivileged process may lock.

BUGS

In Linux 4.8 and earlier, a bug in the kernel's accounting of locked memory for unprivileged processes (i.e., without CAP_IPC_LOCK) meant that if the region specified by addr and size overlapped an existing lock, then the already locked bytes in the overlapping region were counted twice when checking against the limit. Such double accounting could incorrectly calculate a "total locked memory" value for the process that exceeded the RLIMIT_MEMLOCK limit, with the result that mlock() and mlock2() would fail on requests that should have succeeded. This bug was fixed in Linux 4.9.

In Linux 2.4 series of kernels up to and including Linux 2.4.17, a bug caused the mlockall() MCL_FUTURE flag to be inherited across a fork(2). This was rectified in Linux 2.4.18.

Since Linux 2.6.9, if a privileged process calls mlockall(MCL_FUTURE) and later drops privileges (loses the CAP_IPC_LOCK capability by, for example, setting its effective UID to a nonzero value), then subsequent memory allocations (e.g., mmap(2), brk(2)) will fail if the RLIMIT_MEMLOCK resource limit is encountered.
