mlock(2) Manual de llamadas al sistema mlock(2)

NOMBRE

mlock, mlock2, munlock, mlockall, munlockall - bloquear y desbloquear memoria

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

SINOPSIS

#include <sys/mman.h>
int mlock(const void addr[size], size_t size);
int mlock2(const void addr[size], size_t size, unsigned int flags);
int munlock(const void addr[size], size_t size);
int mlockall(int flags);
int munlockall(void);

DESCRIPCIÓN

mlock(), mlock2() y mlockall() bloquean parte o la totalidad del espacio de direcciones virtual del proceso que llama en la RAM, impidiendo que esa memoria sea paginada al área de intercambio.

munlock() y munlockall() realizan la operación inversa, desbloqueando parte o la totalidad del espacio de direcciones virtual del proceso que llama, de modo que las páginas en el rango de direcciones virtuales especificado puedan ser intercambiadas de nuevo si el gestor de memoria del kernel lo requiere.

El bloqueo y desbloqueo de memoria se realiza en unidades de páginas completas.

mlock(), mlock2(), y munlock()

mlock() bloquea páginas en el rango de direcciones que comienza en addr y continúa durante size bytes. Todas las páginas que contienen una parte del rango de direcciones especificado están garantizadas de estar residentes en RAM cuando la llamada retorna exitosamente; las páginas están garantizadas de permanecer en RAM hasta que sean desbloqueadas más tarde.

mlock2() también bloquea páginas en el rango especificado que comienza en addr y continúa durante size bytes. Sin embargo, el estado de las páginas contenidas en ese rango después de que la llamada retorne exitosamente dependerá del valor del argumento flags.

El argumento flags puede ser 0 o la siguiente constante:

MLOCK_ONFAULT
Bloquea las páginas que actualmente están residentes y marca todo el rango para que las páginas restantes no residentes se bloqueen cuando sean pobladas por una falla de página.

Si flags es 0, mlock2() se comporta exactamente igual que mlock().

munlock() desbloquea páginas en el rango de direcciones que comienza en addr y continúa durante size bytes. Después de esta llamada, todas las páginas que contienen una parte del rango de memoria especificado pueden ser movidas al espacio de intercambio externo de nuevo por el kernel.

mlockall() y munlockall()

mlockall() bloquea todas las páginas mapeadas en el espacio de direcciones del proceso que llama. Esto incluye las páginas de los segmentos de código, datos y pila, así como bibliotecas compartidas, datos del kernel en el espacio de usuario, memoria compartida y archivos mapeados en memoria. Todas las páginas mapeadas están garantizadas de estar residentes en RAM cuando la llamada retorna exitosamente; las páginas están garantizadas de permanecer en RAM hasta que sean desbloqueadas más tarde.

El argumento flags se construye como el OR a nivel de bits de una o más de las siguientes constantes:

MCL_CURRENT
Bloquea todas las páginas que actualmente están mapeadas en el espacio de direcciones del proceso.
MCL_FUTURE
Bloquea todas las páginas que se mapearán en el espacio de direcciones del proceso en el futuro. Estas podrían ser, por ejemplo, nuevas páginas requeridas por un heap y stack en crecimiento, así como nuevos archivos mapeados en memoria o regiones de memoria compartida.
MCL_ONFAULT (desde Linux 4.4)
Usado junto con MCL_CURRENT, MCL_FUTURE, o ambos. Marca todas las páginas actuales (con MCL_CURRENT) o futuras (con MCL_FUTURE) para bloquear páginas cuando se activan por un fault. Cuando se usa con MCL_CURRENT, todas las páginas presentes se bloquean, pero mlockall() no activará páginas no presentes. Cuando se usa con MCL_FUTURE, todos los mapeos futuros se marcarán para bloquear páginas cuando se activen por un fault, pero no serán poblados por el bloqueo cuando se cree el mapeo. MCL_ONFAULT debe usarse con ya sea MCL_CURRENT o MCL_FUTURE o ambos.

Si se ha especificado MCL_FUTURE, entonces una llamada al sistema posterior (por ejemplo, mmap(2), sbrk(2), malloc(3)), puede fallar si causa que el número de bytes bloqueados exceda el máximo permitido (ver abajo). En las mismas circunstancias, el crecimiento de la pila puede fallar de manera similar: el kernel negará la expansión de la pila y entregará una señal SIGSEGV al proceso.

munlockall() desbloquea todas las páginas mapeadas en el espacio de direcciones del proceso que llama.

VALOR DE RETORNO

En caso de éxito, estas llamadas al sistema devuelven 0. En caso de error, devuelven -1, se establece errno para indicar el error, y no se realiza ningún cambio en los bloqueos del espacio de direcciones del proceso.

ERRORES

EAGAIN
(mlock(), mlock2(), y munlock()) Algunas o todas las páginas del rango de direcciones especificado no pudieron ser bloqueadas.
EINVAL
(mlock(), mlock2(), y munlock()) El resultado de la suma addr+size fue menor que addr (por ejemplo, la suma pudo haber resultado en un desbordamiento).
EINVAL
(mlock2()) Se especificaron flags desconocidos.
EINVAL
(mlockall()) Se especificaron flags desconocidos o se especificó MCL_ONFAULT sin MCL_FUTURE ni MCL_CURRENT.
EINVAL
(No en Linux) addr no era un múltiplo del tamaño de página.
ENOMEM
(mlock(), mlock2(), y munlock()) Algunas partes del rango de direcciones especificado no corresponden a páginas mapeadas en el espacio de direcciones del proceso.
ENOMEM
(mlock(), mlock2(), y munlock()) El bloqueo o desbloqueo de una región resultaría en que el número total de mapeos con atributos distintos (por ejemplo, bloqueados versus desbloqueados) excediera el máximo permitido. (Por ejemplo, desbloquear un rango en el medio de un mapeo actualmente bloqueado resultaría en tres mapeos: dos mapeos bloqueados en cada extremo y un mapeo desbloqueado en el medio).
ENOMEM
(Linux 2.6.9 y posteriores) el llamador tenía un límite de recurso blando RLIMIT_MEMLOCK distinto de cero, pero intentó bloquear más memoria de la permitida por el límite. Este límite no se aplica si el proceso está privilegiado (CAP_IPC_LOCK).
ENOMEM
(Linux 2.4 y anteriores) el proceso que llama intentó bloquear más de la mitad de la RAM.
EPERM
El llamador no está privilegiado, pero necesita privilegios (CAP_IPC_LOCK) para realizar la operación solicitada.
EPERM
(munlockall()) (Linux 2.6.8 y anteriores) El llamador no estaba privilegiado (CAP_IPC_LOCK).

VERSIONES

Linux

Bajo Linux, mlock(), mlock2(), y munlock() redondean automáticamente addr hacia abajo al límite de página más cercano. Sin embargo, la especificación POSIX.1 de mlock() y munlock() permite que una implementación requiera que addr esté alineado en página, por lo que las aplicaciones portátiles deben asegurarse de ello.

mlockall(2) - Linux man-pages

NAME

mlockall, munlockall - lock or unlock all pages of the calling process

LIBRARY

Libc, with the following caveat for mlock2(2):

All the functions described here are provided by glibc, but mlock2(2) is a Linux-specific extension. Use feature test macros (see feature_test_macros(7)) to check for the availability of this function.

SYNOPSIS

#include <sys/mman.h>

int mlockall(int flags);
int munlockall(void);

DESCRIPTION

The mlockall() function locks all of the currently mapped pages of the calling process in RAM, and prevents the pages from being swapped out to disk. This includes the pages mapped for the process's text, data, stack, and shared libraries. Memory mappings created later using mmap(2) with the MAP_POPULATE flag (or that are automatically populated by the kernel, for example, when accessing them) will also be locked if the MCL_FUTURE flag is specified in flags.

The flags argument specifies which pages to lock. It is the bitwise OR of one or more of the following constants:

MCL_CURRENT
Lock all pages that are mapped into the address space of the calling process at the time of the call. This includes the text, data, stack, and shared memory segments (including those mapped by mmap(2)).
MCL_FUTURE
Lock pages that will be mapped in the future. This affects memory mappings created subsequently by mmap(2), and also anonymous memory mappings created by mlock(2), mlock2(2), or by the kernel for the stack and heap. Note that the text segment is not affected by this flag; it is handled by MCL_CURRENT.
MCL_ONFAULT
Lock pages specified by MCL_CURRENT and MCL_FUTURE only when they are accessed (that is, on a page fault). Pages that are locked using this flag are automatically unlocked when they are swapped out. This flag is useful for applications that deal with large mappings where only a small portion of pages in the mapping are actually touched. Locking all pages in such a mapping would incur a significant penalty.

If MCL_CURRENT and MCL_FUTURE are both set, all current and future pages are locked. If neither flag is specified, an error is returned.

The munlockall() function unlocks all pages that were locked by the calling process using mlockall().

The amount of memory that can be locked is limited by the RLIMIT_MEMLOCK resource limit (see setrlimit(2)). This limit is specified in bytes.

RETURN VALUE

On success, mlockall() and munlockall() return 0. On failure, they return -1, and errno is set to indicate the error.

ERRORS

EAGAIN
Not enough memory available to perform the lock (e.g., exceeded RLIMIT_MEMLOCK).
EINVAL
Invalid value in flags (e.g., neither MCL_CURRENT nor MCL_FUTURE was specified).
EPERM
The calling process does not have the CAP_IPC_LOCK capability, and it has insufficient locked memory remaining within its RLIMIT_MEMLOCK resource limit.

VERSIONS

The MCL_ONFAULT flag was added in Linux 2.6.22. It is also supported by the mlock2() system call since Linux 4.4.

The check for proc(5) shows how many kilobytes of memory the process with ID PID has locked using mlock(), mlock2(), mlockall(), and mmap(2) MAP_LOCKED.

STANDARDS

On POSIX systems on which mlock() and munlock() are available, _POSIX_MEMLOCK_RANGE is defined in <unistd.h> and the number of bytes in a page can be determined from the constant PAGESIZE (if defined) in <limits.h> or by calling sysconf(_SC_PAGESIZE).

On POSIX systems on which mlockall() and munlockall() are available, _POSIX_MEMLOCK is defined in <unistd.h> to a value greater than 0. (See also sysconf(3).)

NOTES

Memory locking has two main applications: real-time algorithms and high-security data processing. Real-time applications require deterministic timing, and, like scheduling, paging is one major cause of unexpected program execution delays. Real-time applications will usually also switch to a real-time scheduler with sched_setscheduler(2). Cryptographic security software often handles critical bytes like passwords or secret keys as data structures. As a result of paging, these secrets could be transferred onto a persistent swap store medium, where they might be accessible to the enemy long after the security software has erased the secrets in RAM and terminated. (But be aware that the suspend mode on laptops and some desktop computers will save a copy of the system's RAM to disk, regardless of memory locks.)

Real-time processes that are using mlockall() to prevent delays on page faults should reserve enough locked stack pages before entering the time-critical section, so that no page fault can be caused by function calls. This can be achieved by calling a function that allocates a sufficiently large automatic variable (an array) and writes to the memory occupied by this array in order to touch these stack pages. This way, enough pages will be mapped for the stack and can be locked into RAM. The dummy writes ensure that not even copy-on-write page faults can occur in the critical section.

Memory locks are not inherited by a child created via fork(2) and are automatically removed (unlocked) during an execve(2) or when the process terminates. The mlockall() MCL_FUTURE and MCL_FUTURE | MCL_ONFAULT settings are not inherited by a child created via fork(2) and are cleared during an execve(2).

Note that fork(2) will prepare the address space for a copy-on-write operation. The consequence is that any write access that follows will cause a page fault that in turn may cause high latencies for a real-time process. Therefore, it is crucial not to invoke fork(2) after an mlockall() or mlock() operation—not even from a thread which runs at a low priority within a process which also has a thread running at elevated priority.

The memory lock on an address range is automatically removed if the address range is unmapped via munmap(2).

Memory locks do not stack, that is, pages which have been locked several times by calls to mlock(), mlock2(), or mlockall() will be unlocked by a single call to munlock() for the corresponding range or by munlockall(). Pages which are mapped to several locations or by several processes stay locked into RAM as long as they are locked at least at one location or by at least one process.

If a call to mlockall() which uses the MCL_FUTURE flag is followed by another call that does not specify this flag, the changes made by the MCL_FUTURE call will be lost.

The mlock2() MLOCK_ONFAULT flag and the mlockall() MCL_ONFAULT flag allow efficient memory locking for applications that deal with large mappings where only a (small) portion of pages in the mapping are touched. In such cases, locking all of the pages in a mapping would incur a significant penalty for memory locking.

Limits and permissions

In Linux 2.6.8 and earlier, a process must be privileged (CAP_IPC_LOCK) in order to lock memory and the RLIMIT_MEMLOCK soft resource limit defines a limit on how much memory the process may lock.

Since Linux 2.6.9, no limits are placed on the amount of memory that a privileged process can lock and the RLIMIT_MEMLOCK soft resource limit instead defines a limit on how much memory an unprivileged process may lock.

BUGS

In Linux 4.8 and earlier, a bug in the kernel's accounting of locked memory for unprivileged processes (i.e., without CAP_IPC_LOCK) meant that if the region specified by addr and size overlapped an existing lock, then the already locked bytes in the overlapping region were counted twice when checking against the limit. Such double accounting could incorrectly calculate a "total locked memory" value for the process that exceeded the RLIMIT_MEMLOCK limit, with the result that mlock() and mlock2() would fail on requests that should have succeeded. This bug was fixed in Linux 4.9.

In Linux 2.4 series of kernels up to and including Linux 2.4.17, a bug caused the mlockall() MCL_FUTURE flag to be inherited across a fork(2). This was rectified in Linux 2.4.18.

Since Linux 2.6.9, if a privileged process calls mlockall(MCL_FUTURE) and later drops privileges (loses the CAP_IPC_LOCK capability by, for example, setting its effective UID to a nonzero value), then subsequent memory allocations (e.g., mmap(2), brk(2)) will fail if the RLIMIT_MEMLOCK resource limit is encountered.
