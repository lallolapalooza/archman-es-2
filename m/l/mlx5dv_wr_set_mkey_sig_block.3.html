NOMBRE

mlx5dv_wr_set_mkey_sig_block - Configurar una MKEY para operación de firma de bloque (integridad de datos).

SINOPSIS

#include <infiniband/mlx5dv.h>
static inline void mlx5dv_wr_set_mkey_sig_block(struct mlx5dv_qp_ex *mqp,
                                                const struct mlx5dv_sig_block_attr *attr)

DESCRIPCIÓN

Configura una MKEY con propiedades de protección de datos a nivel de bloque. Con esto, el dispositivo puede añadir/modificar/eliminar/validar campos de integridad por bloque al transmitir datos de memoria a red y al recibir datos de red a memoria.

Este setter se puede llamar opcionalmente después de que se haya iniciado la publicación de una solicitud de trabajo de configuración de MKEY utilizando mlx5dv_wr_mkey_configure(3). La configuración de las propiedades de firma de bloque para una MKEY se realiza describiendo qué tipo de firma se requiere (o se espera) en dos dominios: el dominio de cable y el dominio de memoria.

La MKEY representa una memoria virtualmente contigua, configurando un diseño para ella. El dominio de firma de memoria describe si los datos en esta memoria virtualmente contigua incluyen campos de integridad y, si es así, qué tipo (enum mlx5dv_sig_type) y qué tamaño de bloque (enum mlx5dv_block_size).

El dominio de firma de cable describe las mismas propiedades para los datos tal como se ven en el cable. Ahora, dependiendo de la operación real que ocurra (TX o RX), el dispositivo hará lo "correcto" basándose en las configuraciones de firma de los dos dominios.

Ejemplo 1:

El dominio de firma de memoria está configurado para CRC32 cada bloque de 512B.

El dominio de firma de cable está configurado para no tener firma.

Se emite un SEND utilizando la MKEY como clave local.

Resultado: el dispositivo recopilará los datos con los campos CRC32 de la MKEY (utilizando cualquier diseño configurado en la MKEY para localizar la memoria real), validará cada CRC32 contra los 512 bytes de datos anteriores, eliminará el campo CRC32 y transmitirá solo 512 bytes de datos al cable.

Ejemplo 1.1:

Igual que el anterior, pero se emite un RECV con la misma clave y ocurre la recepción.

Resultado: el dispositivo recibirá los datos del cable, los dispersará en la MKEY (utilizando cualquier diseño configurado en la MKEY para localizar la memoria real), generando y dispersando un campo CRC32 adicional después de cada 512 bytes que se dispersan.

Ejemplo 2:

El dominio de firma de memoria está configurado para no tener firma.

El dominio de firma de cable está configurado para T10DIF cada bloque de 4K.

La MKEY se envía a un nodo remoto que emite una RDMA_READ a esta MKEY.

Resultado: el dispositivo recopilará los datos de la MKEY (utilizando cualquier diseño configurado en la MKEY para localizar la memoria real), los transmitirá al cable mientras genera un campo T10DIF adicional cada 4K de datos.

Ejemplo 2.1:

Igual que el anterior, pero el nodo remoto emite una RDMA_WRITE a esta MKEY.

Resultado: el dispositivo recibirá los datos del cable, validará cada campo T10DIF contra los 4K de datos anteriores, eliminará el campo T10DIF y dispersará los datos solos en la MKEY (utilizando cualquier diseño configurado en la MKEY para localizar la memoria real).

ARGUMENTOS

mqp
El QP donde se creó una solicitud de trabajo de configuración de MKEY por

mlx5dv_wr_mkey_configure().

attr
Atributos de firma de bloque para establecer para la MKEY.

Atributos de firma de bloque

Los atributos de firma de bloque describen las estructuras de datos de entrada y salida en los dominios de memoria y cable.

struct mlx5dv_sig_block_attr {
    const struct mlx5dv_sig_block_domain *mem;
    const struct mlx5dv_sig_block_domain *wire;
    uint32_t flags;
    uint8_t check_mask;
    uint8_t copy_mask;
    uint64_t comp_mask;
};
mem
Un puntero a la configuración de firma para el dominio de memoria o NULL si el dominio no tiene firma.
wire
Un puntero a la configuración de firma para el dominio de cable o NULL si el dominio no tiene firma.
flags
Un OR a nivel de bits de los diversos valores descritos a continuación.
MLX5DV_SIG_BLOCK_ATTR_FLAG_COPY_MASK
Si el bit no está establecido, entonces copy_mask se ignora. Ver detalles en la descripción de copy_mask.
check_mask
Cada bit de check_mask corresponde a un byte del campo de firma en el dominio de entrada. El byte de la firma de entrada se comprueba si el bit correspondiente en check_mask está establecido. Los bits no relevantes para el tipo de firma se ignoran.

Diseño de check_mask.

check_mask (bits) 7 6 5 4 3 2 1 0
T10-DIF (bytes) GUARD[1] GUARD[0] APP[1] APP[0] REF[3] REF[2] REF[1] REF[0]
CRC32C/CRC32 (bytes) 3 2 1 0
CRC64_XP10 (bytes) 7 6 5 4 3 2 1 0

Las máscaras de uso común se definen en enum mlx5dv_sig_mask. También se admiten otras máscaras. Siga la tabla anterior para definir una máscara personalizada. Por ejemplo, esto puede ser útil para el campo de etiqueta de aplicación de la firma T10DIF. El uso de la etiqueta de aplicación está fuera del alcance de la especificación T10DIF y depende de la implementación. check_mask permite validar una parte de la etiqueta de aplicación si es necesario.

copy_mask
Una máscara para especificar qué parte de la firma se copia del dominio de origen al dominio de destino. La máscara de copia generalmente se calcula automáticamente. La firma se copia si el mismo tipo de firma está configurado en ambos dominios. Las partes de T10-DIF se comparan y manejan de forma independiente.

Si se establece MLX5DV_SIG_BLOCK_ATTR_FLAG_COPY_MASK, el atributo copy_mask anula el valor calculado de la máscara de copia. De lo contrario, copy_mask se ignora.

Cada bit de copy_mask corresponde a un byte del campo de firma. Si el bit correspondiente en copy_mask está establecido, el byte del campo de firma se copia del dominio de entrada al dominio de salida. El cálculo según la configuración del dominio de salida no se realiza en este caso. Los bits no relevantes para el tipo de firma se ignoran. copy_mask solo se puede usar si los dominios de entrada y salida tienen la misma estructura, es decir, el mismo tamaño de bloque y tipo de firma. La configuración de la MKEY fallará si se establece MLX5DV_SIG_BLOCK_ATTR_FLAG_COPY_MASK pero los dominios tienen diferentes estructuras de firma.

Las máscaras predefinidas están disponibles en enum mlx5dv_sig_mask. También se admite la especificación de una máscara definida por el usuario. Siga la tabla en la descripción de check_mask para definir una máscara personalizada.

copy_mask puede ser útil cuando algunos bytes de la firma no se conocen de antemano, por lo que pueden

```c struct mlx5dv_sig_block_domain sig_mem = { .type = MLX5DV_SIG_TYPE_CRC32C, .block_size = MLX5DV_BLOCK_SIZE_512 }; struct mlx5dv_sig_block_domain sig_wire = { .type = MLX5DV_SIG_TYPE_NONE, .block_size = MLX5DV_BLOCK_SIZE_NONE }; struct mlx5dv_sig_block_attr attr = { .mem = &sig_mem, .wire = &sig_wire, .check_mask = 0xFF, .flags = 0 }; mlx5dv_wr_set_mkey_sig_block(mqp, &attr);

NAME

mlx5dv_wr_set_mkey_sig_block - configure memory key with block signature attributes

SYNOPSIS

#include <mlx5/mlx5dv.h>

void
mlx5dv_wr_set_mkey_sig_block(
    struct ibv_mw *mw,
    uint64_t rkey,
    const struct mlx5dv_sig_block_domain *sig_domains,
    size_t num_domains
);

DESCRIPTION

The mlx5dv_wr_set_mkey_sig_block function configures a memory key (MKEY) with block signature attributes. The attributes are defined in sig_domains and apply to the memory region represented by the MKEY. The function is intended to be used in conjunction with mlx5dv_wr_mkey_configure(3). The specified signature domains are configured on the memory key that is created or updated by the mlx5dv_wr_mkey_configure() call.

Signature attributes are used for data integrity and protection against data corruption. The adapter calculates and/or verifies signature data for each block within the memory region according to the specified configuration.

Important: The memory key must be created or updated with the MLX5DV_MKEY_INIT_ATTR_FLAGS_BLOCK_SIGNATURE flag in the init_attr.flags field of mlx5dv_create_mkey_init_attr or mlx5dv_update_mkey_init_attr structure passed to mlx5dv_create_mkey(3) or mlx5dv_wr_mkey_configure(3), respectively.

The rkey parameter is the remote key associated with the memory region. It is used for signature verification during remote access operations.

The sig_domains parameter is an array of struct mlx5dv_sig_block_domain structures, each defining a signature domain with its own type, configuration, and block size. The num_domains parameter specifies the number of elements in the sig_domains array.

A memory region can have multiple signature domains, each operating on blocks of a specific size and using a particular signature type. The adapter processes these domains in the order they appear in the array.

The fields within the mlx5dv_sig_block_domain structure determine how the signature is generated or verified for each domain:

check_mask
A bitmask indicating which signature domains should be checked. If a bit corresponding to a specific domain is set, the adapter will verify the signature for that domain. If a bit is cleared, the signature will not be checked.
copy_mask
A bitmask indicating which signature domains should be copied. If a bit corresponding to a specific domain is set, the signature data for that domain will be copied along with the data. If a bit is cleared, the signature data will not be copied. This is useful for scenarios where the signature data does not need to be checked, but shall be preserved. In this case corresponding bits should be cleared in check_mask and set in copy_mask.

Block signature domain

struct mlx5dv_sig_block_domain {
    enum mlx5dv_sig_type sig_type;
    union {
        const struct mlx5dv_sig_t10dif *dif;
        const struct mlx5dv_sig_crc *crc;
    } sig;
    enum mlx5dv_block_size block_size;
    uint64_t comp_mask;
};
sig_type
The signature type for this domain, one of the following
MLX5DV_SIG_TYPE_T10DIF
The block-level data protection defined in the T10 specifications (T10 SBC-3).
MLX5DV_SIG_TYPE_CRC
The block-level data protection based on cyclic redundancy check (CRC). The specific type of CRC is defined in sig.
sig
Depending on sig_type, this is the per signature type specific configuration.
block_size
The block size for this domain, one of enum mlx5dv_block_size.
comp_mask
Reserved for future extension, must be 0 now.

CRC signature

struct mlx5dv_sig_crc {
    enum mlx5dv_sig_crc_type type;
    uint64_t seed;
};
type
The specific CRC type, one of the following.
MLX5DV_SIG_CRC_TYPE_CRC32
CRC32 signature is created by calculating a 32-bit CRC defined in Fibre Channel Physical and Signaling Interface (FC-PH), ANSI X3.230:1994.
MLX5DV_SIG_CRC_TYPE_CRC32C
CRC32C signature is created by calculating a 32-bit CRC called the Castagnoli CRC, defined in the Internet Small Computer Systems Interface (iSCSI) rfc3720.
MLX5DV_SIG_CRC_TYPE_CRC64_XP10
CRC64_XP10 signature is created by calculating a 64-bit CRC defined in Microsoft XP10 compression standard.
seed
A seed for the CRC calculation per block. Bits not relevant to the CRC type are ignored. For example, all bits are used for CRC64_XP10, but only the 32 least significant bits are used for CRC32/CRC32C.

Only the following values are supported as a seed: CRC32/CRC32C - 0, 0xFFFFFFFF(UINT32_MAX); CRC64_XP10 - 0, 0xFFFFFFFFFFFFFFFF(UINT64_MAX).

T10DIF signature

T10DIF signature is defined in the T10 specifications (T10 SBC-3) for block-level data protection. The size of data block protected by T10DIF must be modulo 8bytes as required in the T10DIF specifications. Note that when setting the initial LBA value to ref_tag, it should be the value of the first block to be transmitted.

struct mlx5dv_sig_t10dif {
    enum mlx5dv_sig_t10dif_bg_type bg_type;
    uint16_t bg;
    uint16_t app_tag;
    uint32_t ref_tag;
    uint16_t flags;
};
bg_type
The block guard type to be used, one of the following.
MLX5DV_SIG_T10DIF_CRC
Use CRC in the block guard field as required in the T10DIF specifications.
MLX5DV_SIG_T10DIF_CSUM
Use IP checksum instead of CRC in the block guard field.
bg
A seed for the block guard calculation per block.

The following values are supported as a seed: 0, 0xFFFF(UINT16_MAX).

app_tag
An application tag to generate or validate.
ref_tag
A reference tag to generate or validate.
flags
Flags for the T10DIF attributes, one of the following.
MLX5DV_SIG_T10DIF_FLAG_REF_REMAP
Increment reference tag per block.
MLX5DV_SIG_T10DIF_FLAG_APP_ESCAPE
Do not check block guard if application tag is 0xFFFF.
MLX5DV_SIG_T10DIF_FLAG_APP_REF_ESCAPE
Do not check block guard if application tag is 0xFFFF and reference tag is 0xFFFFFFFF.

RETURN VALUE

This function does not return a value.

In case of error, user will be notified later when completing the DV WRs chain.

Notes

A DEVX context should be opened by using mlx5dv_open_device(3).

MKEY must be created with MLX5DV_MKEY_INIT_ATTR_FLAGS_BLOCK_SIGNATURE flag.

The last operation posted on the supplied QP should be mlx5dv_wr_mkey_configure(3), or one of its related setters, and the operation must still be open (no doorbell issued).

In case of ibv_wr_complete() failure or calling to ibv_wr_abort(), the MKey may be left in an unknown state. The next configuration of it should not assume any previous state of the MKey, i.e. signature/crypto should be re-configured or reset, as required. For example, assuming mlx5dv_wr_set_mkey_sig_block() and then ibv_wr_abort() were called, then on the next configuration of the MKey, if signature is not needed, it should be reset using MLX5DV_MKEY_CONF_FLAG_RESET_SIG_ATTR.
