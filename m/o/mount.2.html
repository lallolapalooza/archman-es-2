mount(2) Manual de llamadas al sistema mount(2)

NOMBRE

mount - montar un sistema de archivos

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

SINOPSIS

#include <sys/mount.h>
int mount(const char *source, const char *target,
          const char *filesystemtype, unsigned long mountflags,
          const void *_Nullable data);

DESCRIPCIÓN

mount() adjunta el sistema de archivos especificado por source (que a menudo es una ruta de acceso que hace referencia a un dispositivo, pero también puede ser la ruta de acceso de un directorio o archivo, o una cadena ficticia) a la ubicación (un directorio o archivo) especificada por la ruta de acceso en target.

Se requiere el privilegio apropiado (Linux: la capacidad CAP_SYS_ADMIN) para montar sistemas de archivos.

Los valores para el argumento filesystemtype admitidos por el kernel se enumeran en /proc/filesystems (por ejemplo, "btrfs", "ext4", "jfs", "xfs", "vfat", "fuse", "tmpfs", "cgroup", "proc", "mqueue", "nfs", "cifs", "iso9660"). Pueden estar disponibles otros tipos cuando se carguen los módulos apropiados.

El argumento data es interpretado por los diferentes sistemas de archivos. Típicamente es una cadena de opciones separadas por comas entendidas por este sistema de archivos. Consulte mount(8) para obtener detalles sobre las opciones disponibles para cada tipo de sistema de archivos. Este argumento puede especificarse como NULL, si no hay opciones.

Una llamada a mount() realiza uno de varios tipos generales de operación, dependiendo de los bits especificados en mountflags. La elección de qué operación realizar se determina probando los bits establecidos en mountflags, con las pruebas realizadas en el orden listado aquí:

•
Remontar un montaje existente: mountflags incluye MS_REMOUNT.
•
Crear un montaje bind: mountflags incluye MS_BIND.
•
Cambiar el tipo de propagación de un montaje existente: mountflags incluye uno de MS_SHARED, MS_PRIVATE, MS_SLAVE, o MS_UNBINDABLE.
•
Mover un montaje existente a una nueva ubicación: mountflags incluye MS_MOVE.
•
Crear un nuevo montaje: mountflags no incluye ninguna de las banderas anteriores.

Cada una de estas operaciones se detalla más adelante en esta página. Se pueden especificar banderas adicionales en mountflags para modificar el comportamiento de mount(), como se describe a continuación.

Banderas adicionales de montaje

La lista a continuación describe las banderas adicionales que se pueden especificar en mountflags. Tenga en cuenta que algunos tipos de operación ignoran algunas o todas estas banderas, como se describe más adelante en esta página.

MS_DIRSYNC (desde Linux 2.5.19)
Realiza cambios de directorio en este sistema de archivos de forma síncrona. (Esta propiedad se puede obtener para directorios individuales o subárboles usando chattr(1).)
MS_LAZYTIME (desde Linux 4.0)
Reduce las actualizaciones en disco de las marcas de tiempo de los inodos (atime, mtime, ctime) manteniendo estos cambios solo en memoria. Las marcas de tiempo en disco se actualizan solo cuando:
•
el inodo necesita ser actualizado por algún cambio no relacionado con las marcas de tiempo del archivo;
•
la aplicación emplea fsync(2), syncfs(2), o sync(2);
•
un inodo no eliminado es desalojado de la memoria; o
•
han pasado más de 24 horas desde que el inodo se escribió en disco.
Esta opción de montaje reduce significativamente las escrituras necesarias para actualizar las marcas de tiempo del inodo, especialmente mtime y atime. Sin embargo, en caso de un bloqueo del sistema, los campos atime y mtime en el disco pueden estar desactualizados hasta por 24 horas.
Ejemplos de cargas de trabajo donde esta opción podría ser de beneficio significativo incluyen escrituras aleatorias frecuentes a archivos preasignados, así como casos donde la opción de montaje MS_STRICTATIME también está habilitada. (La ventaja de combinar MS_STRICTATIME y MS_LAZYTIME es que stat(2) devolverá el atime actualizado correctamente, pero las actualizaciones de atime se flushed al disco solo en los casos enumerados anteriormente).
MS_MANDLOCK
Permite bloqueos obligatorios en archivos de este sistema de archivos. (El bloqueo obligatorio aún debe habilitarse por archivo, como se describe en fcntl(2).) Desde Linux 4.5, esta opción de montaje requiere la capacidad CAP_SYS_ADMIN y un kernel configurado con la opción CONFIG_MANDATORY_FILE_LOCKING. El bloqueo obligatorio ha sido completamente obsoleto en Linux 5.15, por lo que esta bandera debe considerarse obsoleta.
MS_NOATIME
No actualizar las horas de acceso para archivos (de cualquier tipo) en este sistema de archivos.
MS_NODEV
No permitir el acceso a dispositivos (archivos especiales) en este sistema de archivos.
MS_NODIRATIME
No actualizar las horas de acceso para directorios en este sistema de archivos. Esta bandera proporciona un subconjunto de la funcionalidad proporcionada por MS_NOATIME; es decir, MS_NOATIME implica MS_NODIRATIME.
MS_NOEXEC
No permitir la ejecución de programas desde este sistema de archivos.
MS_NOSUID
No honrar las bits set-user-ID y set-group-ID ni las capacidades de archivo al ejecutar programas desde este sistema de archivos. Además, las transiciones de dominio de SELinux requieren el permiso nosuid_transition, que a su vez necesita también la capacidad de política nnp_nosuid_transition.
MS_RDONLY
Montar el sistema de archivos como solo lectura.
MS_REC (desde Linux 2.4.11)
Se utiliza junto con MS_BIND para crear un montaje bind recursivo, y junto con las banderas de tipo de propagación para cambiar recursivamente el tipo de propagación de todos los montajes en un subárbol. Consulte más adelante para obtener más detalles.
MS_RELATIME (desde Linux 2.6.20)
Cuando se accede a un archivo en este sistema de archivos, actualizar la última hora de acceso del archivo (atime) solo si el valor actual de atime es menor o igual a la última hora de modificación del archivo (mtime) o la última hora de cambio de estado (ctime). Esta opción es útil para programas, como mutt(1), que necesitan saber cuándo se ha leído un archivo desde que se modificó por última vez. Desde Linux 2.6.30, el kernel utiliza por defecto el comportamiento proporcionado por esta bandera (a menos que se especificara MS_NOATIME), y la bandera MS_STRICTATIME es necesaria para obtener la semántica tradicional. Además, desde Linux 2.6.30, la hora de último acceso del archivo siempre se actualiza si es mayor de 1 día.
MS_SILENT (desde Linux 2.6.17)
Suprime la visualización de ciertos mensajes de advertencia (printk()) en el registro del kernel. Esta bandera anula la bandera obsoleta y mal nombrada MS_VERBOSE (disponible desde Linux 2.4.12), que tiene el mismo significado.
MS_STRICTATIME (desde Linux 2.6.30)
Actualizar siempre la hora de último acceso (atime) cuando se accede a archivos en este sistema de archivos. (Este era el comportamiento predeterminado antes de Linux 2.6.30). Especificar esta bandera anula el ef

MS_SYNCHRONOUS
Hace que las escrituras en este sistema de archivos sean síncronas (como si se hubiera especificado la bandera O_SYNC en open(2) para todas las aperturas de archivos en este sistema de archivos).
MS_NOSYMFOLLOW (desde Linux 5.10)
No seguir enlaces simbólicos al resolver rutas. Los enlaces simbólicos aún se pueden crear, y readlink(1), readlink(2), realpath(1) y realpath(3) siguen funcionando correctamente.

A partir de Linux 2.4, algunas de las banderas anteriores se pueden configurar por montaje, mientras que otras se aplican a los superbloques del sistema de archivos montado, lo que significa que todos los montajes del mismo sistema de archivos comparten esas banderas. (Anteriormente, todas las banderas eran por superbloque).

Las banderas por punto de montaje son las siguientes:

•
Desde Linux 2.4: las banderas MS_NODEV, MS_NOEXEC y MS_NOSUID se pueden configurar por punto de montaje.
•
Adicionalmente, desde Linux 2.6.16: MS_NOATIME y MS_NODIRATIME.
•
Adicionalmente, desde Linux 2.6.20: MS_RELATIME.

Las siguientes banderas son por superbloque: MS_DIRSYNC, MS_LAZYTIME, MS_MANDLOCK, MS_SILENT y MS_SYNCHRONOUS. La configuración inicial de estas banderas se determina en el primer montaje del sistema de archivos y será compartida por todos los montajes posteriores del mismo sistema de archivos. Posteriormente, la configuración de las banderas se puede cambiar mediante una operación de remonte (ver abajo). Dichos cambios serán visibles a través de todos los montajes asociados con el sistema de archivos.

Desde Linux 2.6.16, MS_RDONLY se puede configurar o borrar por punto de montaje, así como en el superbloque subyacente del sistema de archivos. El sistema de archivos montado solo será grabable si ni el sistema de archivos ni el punto de montaje están marcados como de solo lectura.

Remontar un montaje existente

Se puede remontar un montaje existente especificando MS_REMOUNT en mountflags. Esto permite cambiar los mountflags y data de un montaje existente sin tener que desmontar y volver a montar el sistema de archivos. target debe ser el mismo valor especificado en la llamada inicial de mount().

Los argumentos source y filesystemtype se ignoran.

Los argumentos mountflags y data deben coincidir con los valores utilizados en la llamada mount() original, excepto aquellos parámetros que se estén modificando deliberadamente.

Los siguientes mountflags se pueden cambiar: MS_LAZYTIME, MS_MANDLOCK, MS_NOATIME, MS_NODEV, MS_NODIRATIME, MS_NOEXEC, MS_NOSUID, MS_RELATIME, MS_RDONLY, MS_STRICTATIME (cuyo efecto es borrar las banderas MS_NOATIME y MS_RELATIME), y MS_SYNCHRONOUS. Los intentos de cambiar la configuración de las banderas MS_DIRSYNC y MS_SILENT durante un remonte se ignoran silenciosamente. Tenga en cuenta que los cambios en las banderas por superbloque son visibles a través de todos los montajes del sistema de archivos asociado (porque las banderas por superbloque son compartidas por todos los montajes).

Desde Linux 3.17, si no se especifica ninguna de las banderas MS_NOATIME, MS_NODIRATIME, MS_RELATIME o MS_STRICTATIME en mountflags, la operación de remonte conserva los valores existentes de estas banderas (en lugar de usar por defecto MS_RELATIME).

Desde Linux 2.6.26, la bandera MS_REMOUNT se puede usar con MS_BIND para modificar solo las banderas por punto de montaje. Esto es particularmente útil para establecer o borrar la bandera "solo lectura" en un montaje sin cambiar los parámetros del sistema de archivos del sistema de archivos subyacente. El argumento data se ignora. Las banderas por punto de montaje existentes del punto de montaje se borran y se reemplazan por las de mountflags. Esto significa que si desea conservar alguna bandera de punto de montaje existente, debe incluirla en mountflags, junto con las banderas de punto de montaje que desea establecer (o con las banderas que desea eliminar). Especificar mountflags como:


MS_REMOUNT | MS_BIND | MS_RDONLY

hará que el acceso a través de este punto de montaje sea de solo lectura (borrando todas las demás banderas de punto de montaje), sin afectar a otros montajes de este sistema de archivos.

Crear un montaje bind

Si mountflags incluye MS_BIND (disponible desde Linux 2.4), entonces realiza un montaje bind. Un montaje bind hace que un archivo o un subárbol de directorios sea visible en otro punto dentro de la única jerarquía de directorios. Los montajes bind pueden cruzar límites de sistemas de archivos y abarcar chroot(2) jails.

Los argumentos filesystemtype y data se ignoran.

Los bits restantes (aparte de MS_REC, descrito a continuación) en el argumento mountflags también se ignoran. (El montaje bind tiene las mismas opciones de montaje que el montaje subyacente). Sin embargo, consulte la discusión sobre remontes anteriores para conocer un método para hacer que un montaje bind existente sea de solo lectura.

Por defecto, cuando se monta un directorio mediante bind, solo se monta ese directorio; si hay submontajes dentro del árbol de directorios, no se montan mediante bind. Si también se especifica la bandera MS_REC, se realiza una operación de montaje bind recursivo: todos los submontajes dentro del subárbol source (excepto los montajes no enlazables) también se montan mediante bind en la ubicación correspondiente en el subárbol target.

Cambiar el tipo de propagación de un montaje existente

Si mountflags incluye una de las banderas MS_SHARED, MS_PRIVATE, MS_SLAVE o MS_UNBINDABLE (todas disponibles desde Linux 2.6.15), entonces se cambia el tipo de propagación de un montaje existente. Si se especifican más de una de estas banderas, se produce un error.

Las únicas otras banderas que se pueden especificar al cambiar el tipo de propagación son MS_REC (descrito a continuación) y MS_SILENT (que se ignora).

Los argumentos source, filesystemtype y data se ignoran.

Los significados de las banderas de tipo de propagación son los siguientes:

MS_SHARED
Hacer que este montaje sea compartido. Los eventos de montaje y desmontaje inmediatamente debajo de este montaje se propagarán a los otros montajes que son miembros del grupo de pares de este montaje. La propagación aquí significa que el mismo montaje o desmontaje ocurrirá automáticamente debajo de los otros montajes del grupo de pares. A la inversa, los eventos de montaje y desmontaje que ocurren debajo de los montajes pares se propagarán a este montaje.
MS_PRIVATE
Hacer que este montaje sea privado. Los eventos de montaje y desmontaje no se propagan hacia o desde este montaje.
MS_SLAVE
Si este es un montaje compartido que es miembro de un grupo de pares que contiene otros miembros, conviértelo en un montaje esclavo. Si este es un montaje compartido que es miembro de un grupo de pares que no contiene otros miembros, conviértelo en un montaje privado. De lo contrario, el tipo de propagación del montaje no se modifica.
Cuando un montaje es esclavo, los eventos de montaje y desmontaje se propagan a este montaje desde el grupo de pares compartido (maestro) del cual era miembro anteriormente. Los eventos de montaje y desmontaje debajo de este montaje no se propagan a ningún par.
Un montaje puede ser esclavo de otro grupo de pares mientras al mismo tiempo comparte eventos de montaje y desmontaje con un grupo de pares del cual es miembro.
MS_UNBINDABLE
Hacer que este montaje no sea enlazable. Esto es como un montaje privado, y además este montaje no se puede montar mediante bind. Cuando se realiza un montaje bind recursivo (mount() con las banderas MS_BIND y MS_REC) en un subárbol de directorios, los montajes no enlazables dentro del subárbol se podan automáticamente (es decir, no se replican) al replicar ese subárbol para producir el subárbol de destino.

Por defecto, cambiar el tipo de propagación afecta solo al montaje target. Si la bandera MS_REC también se especifica en mountflags, entonces el tipo de propagación de todos los montajes debajo de target también se cambia.

Para más detalles sobre los tipos de propagación de montajes (incluido el tipo de propagación por defecto asignado a nuevos montajes), ver mount_namespaces(7).

Mover un montaje

Si mountflags contiene la bandera MS_MOVE (disponible desde Linux 2.4.18), entonces mueve un subárbol: source especifica un montaje existente y target especifica la nueva ubicación a la que se va a reubicar ese montaje. El movimiento es atómico: en ningún momento se desmonta el subárbol.

Los bits restantes en el argumento mountflags se ignoran, al igual que los argumentos filesystemtype y data.

Crear un nuevo montaje

Si ninguna de las banderas MS_REMOUNT, MS_BIND, MS_MOVE, MS_SHARED, MS_PRIVATE, MS_SLAVE o MS_UNBINDABLE se especifica en mountflags, entonces mount() realiza su acción por defecto: crear un nuevo montaje. source especifica la fuente para el nuevo montaje y target especifica el directorio en el que crear el punto de montaje.

Los argumentos filesystemtype y data se utilizan, y se pueden especificar bits adicionales en mountflags para modificar el comportamiento de la llamada.

VALOR DE RETORNO

En caso de éxito, se devuelve cero. En caso de error, se devuelve -1 y se establece errno para indicar el error.

ERRORES

Los valores de error dados a continuación resultan de errores independientes del tipo de sistema de archivos. Cada tipo de sistema de archivos puede tener sus propios errores especiales y su propio comportamiento especial. Consulte el código fuente del kernel de Linux para obtener detalles.

ERRORS

EACCES
Un componente de una ruta no se podía buscar. (Véase también path_resolution(7)).
EACCES
Se intentó montar un sistema de archivos de solo lectura sin proporcionar el indicador MS_RDONLY.
El sistema de archivos puede ser de solo lectura por varias razones, incluyendo: reside en un disco óptico de solo lectura; reside en un dispositivo con un interruptor físico que se ha configurado para marcar el dispositivo como de solo lectura; la implementación del sistema de archivos se compiló con soporte de solo lectura; o se detectaron errores al montar inicialmente el sistema de archivos, por lo que se marcó como de solo lectura y no se puede volver a montar como lectura-escritura (hasta que se corrijan los errores).
Algunos sistemas de archivos en su lugar devuelven el error EROFS ante un intento de montar un sistema de archivos de solo lectura.
EACCES
El dispositivo de bloques source se encuentra en un sistema de archivos montado con la opción MS_NODEV.
EBUSY
Se intentó apilar un nuevo montaje directamente encima de un punto de montaje existente que se creó en este espacio de nombres de montaje con el mismo source y target.
EBUSY
source no se puede volver a montar como de solo lectura, porque aún tiene archivos abiertos para escritura.
EFAULT

EINVAL

EINVAL

EINVAL

EINVAL

EINVAL
Se intentó una operación de movimiento (MS_MOVE), pero source no era un montaje, o era '/'.
EINVAL

EINVAL

EINVAL

EINVAL
En un espacio de nombres de montaje no privilegiado (es decir, un espacio de nombres de montaje propiedad de un espacio de nombres de usuario creado por un usuario no privilegiado), se intentó una operación de montaje de enlace (MS_BIND) sin especificar (MS_REC), lo que habría revelado el árbol del sistema de archivos debajo de uno de los submontajes del directorio que se está enlazando.

ENOTBLK

ENOTDIR

ENXIO

HISTORIA

Las definiciones de MS_DIRSYNC, MS_MOVE, MS_PRIVATE, MS_REC, MS_RELATIME, MS_SHARED, MS_SLAVE, MS_STRICTATIME y MS_UNBINDABLE se agregaron a las cabeceras de glibc en glibc 2.12.

Desde Linux 2.4, un solo sistema de archivos puede montarse en múltiples puntos de montaje, y múltiples montajes pueden apilarse en el mismo punto de montaje.

El argumento mountflags puede tener el número mágico 0xC0ED (MS_MGC_VAL) en los 16 bits superiores. (Todos los demás indicadores discutidos en DESCRIPCIÓN ocupan los 16 bits inferiores de mountflags.) Especificar MS_MGC_VAL era requerido antes de Linux 2.4, pero desde Linux 2.4 ya no es necesario y se ignora si se especifica.

El indicador original MS_SYNC se renombró a MS_SYNCHRONOUS en 1.1.69 cuando se agregó un MS_SYNC diferente a <mman.h>.

Antes de Linux 2.4, un intento de ejecutar un programa con SUID o SGID en un sistema de archivos montado con MS_NOSUID fallaba con EPERM. Desde Linux 2.4, los bits de SUID y SGID simplemente se ignoran silenciosamente en este caso.

NOTAS

Espacios de nombres de montaje

A partir de Linux 2.4.19, Linux proporciona espacios de nombres de montaje. Un espacio de nombres de montaje es el conjunto de montajes del sistema de archivos que son visibles para un proceso. Los espacios de nombres de montaje pueden (y usualmente lo son) compartirse entre múltiples procesos, y los cambios en el espacio de nombres (es decir, montajes y desmontajes) por un proceso son visibles para todos los demás procesos que comparten el mismo espacio de nombres. (La situación de Linux anterior a 2.4.19 puede considerarse como una en la que un solo espacio de nombres era compartido por todos los procesos del sistema.)

Un proceso hijo creado por fork(2) comparte el espacio de nombres de montaje de su padre; el espacio de nombres de montaje se conserva a través de un execve(2).

Un proceso puede obtener un espacio de nombres de montaje privado si: fue creado usando el indicador CLONE_NEWNS de clone(2), en cuyo caso su nuevo espacio de nombres se inicializa como una copia del espacio de nombres del proceso que llamó a clone(2); o llama a unshare(2) con el indicador CLONE_NEWNS, lo que hace que el espacio de nombres de montaje del llamante obtenga una copia privada del espacio de nombres que estaba compartiendo previamente con otros procesos, de modo que los montajes y desmontajes futuros del llamante sean invisibles para otros procesos (excepto los procesos hijos que el llamante cree posteriormente) y viceversa.

Para más detalles sobre los espacios de nombres de montaje, véase mount_namespaces(7).

Relación parental entre montajes

Cada montaje tiene un montaje padre. La relación parental general de todos los montajes define la única jerarquía de directorios vista por los procesos dentro de un espacio de nombres de montaje.

El padre de un nuevo montaje se define cuando se crea el montaje. En el caso habitual, el padre de un nuevo montaje es el montaje del sistema de archivos que contiene el directorio o archivo en el que se adjunta el nuevo montaje. En el caso en que un nuevo montaje se apila sobre un montaje existente, el padre del nuevo montaje es el montaje anterior que se apiló en esa ubicación.

La relación parental entre montajes se puede descubrir a través del archivo /proc/pid/mountinfo (ver más abajo).

/proc/pid/mounts y /proc/pid/mountinfo

El archivo específico de Linux /proc/pid/mounts expone la lista de montajes en el espacio de nombres de montaje del proceso con el ID especificado. El archivo /proc/pid/mountinfo expone aún más información sobre los montajes, incluida la información sobre el tipo de propagación y el ID de montaje que permite descubrir la relación parental entre montajes. Véase proc(5) y mount_namespaces(7) para detalles de este archivo.
