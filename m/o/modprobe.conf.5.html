MODPROBE.D(5) modprobe.d MODPROBE.D(5)

NOMBRE

modprobe.d - Directorio de configuración para modprobe

SINOPSIS

/etc/modprobe.d/*.conf

/run/modprobe.d/*.conf

/usr/local/lib/modprobe.d/*.conf

/usr/lib/modprobe.d/*.conf

/lib/modprobe.d/*.conf

DESCRIPCIÓN

Dado que el comando modprobe puede añadir o eliminar más de un módulo, debido a que los módulos tienen dependencias, necesitamos un método para especificar qué opciones se usarán con esos módulos. Uno también puede usarlos para crear alias convenientes: nombres alternativos para un módulo, o pueden anular el comportamiento normal de modprobe por completo para aquellos con requisitos especiales (como la inserción de más de un módulo).

Tenga en cuenta que los nombres de módulos y alias (como otros nombres de módulos) pueden tener - o _ en ellos: ambos son intercambiables en todos los comandos de módulo, ya que la conversión de guiones bajos ocurre automáticamente.

FORMATO DE CONFIGURACIÓN

Los archivos de configuración contienen un comando por línea, y se ignoran las líneas en blanco y las líneas que comienzan con '#' (útil para añadir comentarios). Una '\' al final de una línea hace que continúe en la siguiente línea, lo que hace que los archivos sean un poco más limpios.

Consulte la sección COMANDOS más abajo para más detalles.

DIRECTORIOS DE CONFIGURACIÓN Y PRECEDENCIA

Los archivos de configuración se leen de los directorios listados en la SINOPSIS en ese orden de precedencia. Una vez que se carga un archivo con un nombre de archivo determinado, se ignora cualquier archivo con el mismo nombre en directorios subsiguientes.

Todos los archivos de configuración se ordenan lexicográficamente, independientemente del directorio en el que residan. Los archivos de configuración pueden ser reemplazados completamente (al tener un nuevo archivo de configuración con el mismo nombre en un directorio de mayor prioridad) o reemplazados parcialmente (al tener un archivo de configuración que se ordena más tarde).

NOTA: Los directorios de configuración pueden ser alterados a través de la variable de entorno MODPROBE_OPTIONS. Consulte la sección ENTORNO en modprobe(8).

COMANDOS

alias patrón nombre_módulo

Esto te permite dar nombres alternativos a un módulo. Por ejemplo: "alias mi-módulo nombre_módulo_muy_largo" significa que puedes usar "modprobe mi-módulo" en lugar de "modprobe nombre_módulo_muy_largo". También puedes usar comodines de estilo shell, así que "alias mi-módulo* nombre_módulo_muy_largo" significa que "modprobe mi-módulo-algo" tiene el mismo efecto. No puedes tener alias de otros alias (eso lleva a la locura), pero los alias pueden tener opciones, que se añadirán a cualquier otra opción.

Tenga en cuenta que los módulos también pueden contener sus propios alias, que puede ver usando modinfo. Estos alias se usan como último recurso (es decir, si no hay un módulo real, comando install, remove o alias en la configuración).

blacklist nombre_módulo

Los módulos pueden contener sus propios alias: generalmente son alias que describen los dispositivos que soportan, como "pci:123...". Estos alias "internos" pueden ser anulados por palabras clave normales de "alias", pero hay casos en los que dos o más módulos soportan los mismos dispositivos, o un módulo reclama inválidamente soportar un dispositivo que no tiene: la palabra clave blacklist indica que todos los alias internos de ese módulo en particular deben ser ignorados.

install nombre_módulo comando...

Este comando instruye a modprobe a ejecutar tu comando en lugar de insertar el módulo en el kernel como es normal. El comando puede ser cualquier comando de shell: esto te permite hacer cualquier tipo de procesamiento complejo que desees. Por ejemplo, si el módulo "fred" funciona mejor con el módulo "barney" ya instalado (pero no depende de él, por lo que modprobe no lo cargará automáticamente), podrías decir "install fred /sbin/modprobe barney; /sbin/modprobe --ignore-install fred", lo que haría lo que quisieras. Tenga en cuenta el --ignore-install, que evita que el segundo modprobe ejecute el mismo comando install de nuevo. Ver también remove más abajo.

El futuro a largo plazo de este comando como solución al problema de proporcionar dependencias de módulos adicionales no está garantizado y se pretende reemplazar este comando con una advertencia sobre su eventual eliminación o desaprobación en algún momento en una versión futura. Su uso complica la determinación automática de las dependencias de los módulos por parte de las utilidades de distribución, como mkinitrd (porque estas ahora necesitan interpretar de alguna manera lo que los comandos de install podrían estar haciendo. En un mundo perfecto, los módulos proporcionarían toda la información de dependencias sin usar este comando y se está trabajando para implementar soporte de dependencias blandas dentro del kernel de Linux.

Si usas la cadena "$CMDLINE_OPTS" en el comando, será reemplazada por cualquier opción especificada en la línea de comandos de modprobe. Esto puede ser útil porque los usuarios esperan que "modprobe fred opt=1" pase el argumento "opt=1" al módulo, incluso si hay un comando install en el archivo de configuración. Así que nuestro ejemplo anterior se convierte en "install fred /sbin/modprobe barney; /sbin/modprobe --ignore-install fred $CMDLINE_OPTS"

options nombre_módulo opción...

Este comando te permite añadir opciones al módulo nombre_módulo (que podría ser un alias) cada vez que se inserta en el kernel: ya sea directamente (usando modprobe nombre_módulo) o porque el módulo que se inserta depende de este módulo.

Todas las opciones se suman: pueden provenir de una option para el propio módulo, para un alias, y en la línea de comandos.

remove nombre_módulo comando...

Esto es similar al comando install de arriba, excepto que se invoca cuando se ejecuta "modprobe -r".

softdep nombre_módulo pre: módulos... post: módulos...

El comando softdep te permite especificar dependencias de módulos blandas u opcionales. nombre_módulo puede usarse sin los módulos opcionales instalados, pero generalmente con algunas características faltantes. Por ejemplo, un controlador para un HBA de almacenamiento podría requerir que se cargue otro módulo para usar las características de gestión.

Los módulos pre-dependencias y post-dependencias son listas de nombres y/o alias de otros módulos que modprobe intentará instalar (o eliminar) en orden antes y después del módulo principal dado en el argumento nombre_módulo.

Ejemplo: Supongamos que "softdep c pre: a b post: d e" se proporciona en la configuración. Ejecutar "modprobe c" ahora es equivalente a "modprobe a b c d e" sin el softdep. Los indicadores como --use-blacklist se aplican a todos los módulos especificados, mientras que los parámetros del módulo solo se aplican al módulo c.

Nota: si hay comandos install o remove con el mismo argumento nombre_módulo, softdep tiene precedencia.

weakdep nombre_módulo módulos...

El comando weakdep te permite especificar dependencias de módulos débiles. Estas son similares a las pre-softdep, con la diferencia de que el espacio de usuario no intenta cargar esa dependencia antes del módulo especificado. En su lugar, el kernel puede solicitar uno o varios de ellos durante la detección del módulo, dependiendo del hardware al que se esté vinculando. El propósito de los módulos débiles es permitir que un controlador especifique que puede ser necesaria una cierta dependencia, por lo que debe estar presente en el sistema de archivos (por ejemplo, en initramfs) cuando se detecte ese módulo.

Ejemplo: Supongamos "weakdep c a b". Un programa que crea un initramfs sabe que debe agregar a, b y c al sistema de archivos, ya que a y b pueden ser necesarios/deseados en tiempo de ejecución. Cuando se carga c y se está detectando, puede emitir llamadas a request_module() haciendo que a o b también se carguen.

COMPATIBILIDAD

Una versión futura de kmod vendrá con una fuerte advertencia para evitar el uso de install como se explicó anteriormente. Esto sucederá una vez que el soporte para dependencias blandas en el kernel esté completo. Ese soporte complementará el soporte softdep existente dentro de esta utilidad al proporcionar dichas dependencias directamente dentro de los módulos.
