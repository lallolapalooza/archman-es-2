MOUNT.CIFS, MOUNT.SMB3(8) Manual del Administrador del Sistema MOUNT.CIFS, MOUNT.SMB3(8)

NOMBRE

mount.cifs, mount.smb3 - montar usando el Sistema de Archivos de Internet Común (CIFS)

SINOPSIS

mount.cifs {servicio} {punto-de-montaje} [-o opciones]

Esta herramienta forma parte del conjunto cifs-utils.

mount.cifs monta un sistema de archivos CIFS o SMB3 desde Linux. Generalmente es invocado indirectamente por el comando mount(8) cuando se usa la opción "-t cifs". Este comando solo funciona en Linux y el kernel debe soportar el sistema de archivos cifs. El protocolo SMB3 es el sucesor del protocolo CIFS (SMB) y es soportado por la mayoría de los servidores de Windows, Azure (almacenamiento en la nube), Macs y muchos otros servidores comerciales y dispositivos de almacenamiento conectado en red (NAS), así como por el popular servidor de Código Abierto Samba.

mount.smb3 monta solo sistemas de archivos SMB3. Generalmente es invocado indirectamente por el comando mount(8) cuando se usa la opción "-t smb3". El tipo de sistema de archivos smb3 se añadió en el kernel 4.18 y versiones posteriores. Funciona de manera similar a mount.cifs excepto que pasa el tipo de sistema de archivos como smb3.

La utilidad mount.cifs adjunta el nombre UNC (recurso de red exportado) especificado como servicio (usando la sintaxis //servidor/recurso_compartido, donde "servidor" es el nombre del servidor o la dirección IP y "recurso_compartido" es el nombre del recurso compartido) al directorio local punto-de-montaje.

Las opciones para mount.cifs se especifican como una lista separada por comas de pares clave=valor. Es posible enviar opciones distintas a las listadas aquí, asumiendo que el módulo del kernel del sistema de archivos cifs (cifs.ko) las soporta. Las opciones de montaje cifs no reconocidas pasadas al código del kernel vfs cifs se registrarán en el log del kernel.

mount.cifs hace que el vfs cifs lance un hilo llamado cifsd. Después de montar, sigue ejecutándose hasta que el recurso montado se desmonta (generalmente a través de la utilidad umount).

El comando mount.cifs -V muestra la versión del programa de montaje cifs.

El comando modinfo cifs muestra la versión del módulo cifs.

OPCIONES

username=arg|user=arg
especifica el nombre de usuario con el que conectarse. Si no se proporciona, se utiliza la variable de entorno USER.

Versiones anteriores de mount.cifs también permitían especificar el nombre de usuario como user%contraseña o grupo_trabajo/usuario o grupo_trabajo/usuario%contraseña para permitir especificar la contraseña y el grupo de trabajo como parte del nombre de usuario. El soporte para esos formatos alternativos de nombre de usuario está ahora obsoleto y no debe usarse. Los usuarios deben usar las opciones discretas password= y domain= para especificar esos valores. Aunque algunas versiones del módulo del kernel cifs aceptan user= como abreviatura de esta opción, su uso puede confundir al programa de montaje estándar haciéndole pensar que es un montaje no superusuario. Por lo tanto, se recomienda usar el nombre completo de la opción username=.

password=arg|pass=arg
especifica la contraseña CIFS. Si no se proporciona esta opción, se utiliza la variable de entorno PASSWD. Si la contraseña no se especifica directa o indirectamente a través de un argumento, mount.cifs solicitará la contraseña, a menos que se especifique la opción guest.

Tenga en cuenta que una contraseña que contenga el carácter delimitador (es decir, una coma ',') fallará al analizarse correctamente en la línea de comandos. Sin embargo, la misma contraseña definida en la variable de entorno PASSWD o a través de un archivo de credenciales o introducida en el aviso de contraseña se leerá correctamente.

password2=arg|pass2=arg
especifica una contraseña alternativa para ayudar con la rotación de contraseñas. Si no se proporciona esta opción, se utiliza la variable de entorno PASSWD2. Si password2 no se especifica directa o indirectamente a través de un argumento, mount.cifs NO solicitará password2.

Tenga en cuenta que una contraseña2 que contenga el carácter delimitador (es decir, una coma ',') fallará al analizarse correctamente en la línea de comandos. Sin embargo, la misma contraseña2 definida en la variable de entorno PASSWD2 o a través de un archivo de credenciales (ver más abajo) se leerá correctamente.

credentials=filename|cred=filename
especifica un archivo que contiene un nombre de usuario y/o contraseña y opcionalmente una contraseña alternativa y/o el nombre del grupo de trabajo. El formato del archivo es:
username=valor
password=valor
password2=valor
domain=valor

Esto es preferible a tener contraseñas en texto plano en un archivo compartido, como /etc/fstab. Asegúrese de proteger adecuadamente cualquier archivo de credenciales.

uid=arg
establece el uid que será propietario de todos los archivos o directorios en el sistema de archivos montado cuando el servidor no proporcione información de propiedad. Puede especificarse como un nombre de usuario o un uid numérico. Cuando no se especifica, el valor predeterminado es uid 0. El programa de montaje mount.cifs debe tener la versión 1.10 o superior para soportar la especificación del uid en formato no numérico. Consulte la sección sobre PROPIEDAD Y PERMISOS DE ARCHIVOS Y DIRECTORIOS a continuación para obtener más información.
forceuid
instruye al cliente para que ignore cualquier uid proporcionado por el servidor para archivos y directorios y que siempre asigne el propietario al valor de la opción uid=. Consulte la sección sobre PROPIEDAD Y PERMISOS DE ARCHIVOS Y DIRECTORIOS a continuación para obtener más información.
cruid=arg
establece el uid del propietario de la caché de credenciales. Esto es principalmente útil con sec=krb5. El valor predeterminado es el uid real del proceso que realiza el montaje. Establecer este parámetro dirige la llamada ascendente a buscar una caché de credenciales propiedad de ese usuario.
gid=arg
establece el gid que será propietario de todos los archivos o directorios en el sistema de archivos montado cuando el servidor no proporcione información de propiedad. Puede especificarse como un nombre de grupo o un gid numérico. Cuando no se especifica, el valor predeterminado es gid 0. El programa de montaje mount.cifs debe tener la versión 1.10 o superior para soportar la especificación del gid en formato no numérico. Consulte la sección sobre PROPIEDAD Y PERMISOS DE ARCHIVOS Y DIRECTORIOS a continuación para obtener más información.
forcegid
instruye al cliente para que ignore cualquier gid proporcionado por el servidor para archivos y directorios y que siempre asigne el propietario al valor de la opción gid=. Consulte la sección sobre PROPIEDAD Y PERMISOS DE ARCHIVOS Y DIRECTORIOS a continuación para obtener más información.
idsfromsid
Extrae uid/gid de un SID especial en lugar de mapearlo. Consulte la sección sobre PROPIEDAD Y PERMISOS DE ARCHIVOS Y DIRECTORIOS a continuación para obtener más información.
port=arg
establece el número de puerto en el que el cliente intentará contactar con el servidor CIFS. Si se especifica este valor, busca una conexión existente con este puerto y la utiliza si existe. Si no existe, intenta crear una nueva conexión en ese puerto. Si esa conexión falla, devuelve un error. Si no se especifica este valor, busca una conexión existente en el puerto 445 o 139. Si no existe tal conexión, intenta conectarse primero en el puerto 445 y luego en el puerto 139 si falla. Devuelve un error si ambos fallan.
netbiosname=arg
Al montar en servidores a través del puerto 139, especifica el nombre de origen RFC1001 a utilizar para representar la máquina netbios del cliente durante la inicialización de la sesión netbios.
servern=arg
Similar a netbiosname, excepto que especifica el nombre netbios del servidor en lugar del cliente. Aunque rara vez es necesario para montar en servidores más nuevos, esta opción es necesaria para montar en algunos servidores más antiguos (como OS/2 o Windows 98 y Windows ME) ya que al conectarse a través del puerto 139, a diferencia de la mayoría de los servidores más nuevos, no soportan un nombre de servidor predeterminado. Un nombre de servidor puede tener hasta 15 caracteres y generalmente se escribe en mayúsculas.
file_mode=arg
Si el servidor no soporta
file_mode=arg
Si las extensiones Unix de CIFS están activadas, esto establece el modo predeterminado para los archivos. Si las extensiones Unix de CIFS no están activadas, este valor se ignora.
dir_mode=arg
Si el servidor no admite las extensiones Unix de CIFS, esto anula el modo predeterminado para los directorios.
ip=arg|addr=arg
establece la dirección IP de destino. Esta opción se establece automáticamente si el nombre del servidor de la parte del nombre UNC solicitado se puede resolver, por lo que rara vez necesita ser especificada por el usuario.
domain=arg|dom=arg|workgroup=arg
Establece el dominio (grupo de trabajo) del usuario. Si no se proporcionan dominios, se utilizará el dominio vacío. Utilice domainauto para adivinar automáticamente el dominio del servidor al que se está conectando.
domainauto
Al utilizar la autenticación NTLM y no proporcionar un dominio a través de domain, adivina el dominio a partir del desafío NTLM del servidor. Este comportamiento solía ser el predeterminado en kernels anteriores a 2.6.36.
guest
no solicite una contraseña.
iocharset
Juego de caracteres utilizado para convertir nombres de ruta locales desde y hacia Unicode. Unicode se utiliza de forma predeterminada para los nombres de ruta de red si el servidor lo admite. Si no se especifica iocharset, se utilizará el nls_default especificado durante la compilación del kernel del cliente local. Si el servidor no admite Unicode, este parámetro no se utiliza.
ro
montaje de solo lectura.
rw
montaje de lectura-escritura.
setuids
Si las extensiones Unix de CIFS se negocian con el servidor, el cliente intentará establecer el uid y gid efectivos del proceso local en los archivos, directorios y dispositivos recién creados (crear, mkdir, mknod). Si las extensiones Unix de CIFS no se negocian, en lugar de utilizar el uid y gid predeterminados especificados en el montaje, se almacenará en caché el uid y gid del nuevo archivo localmente, lo que significa que el uid del archivo puede cambiar cuando se recarga el inodo (o el usuario vuelve a montar el recurso compartido).
nosetuids
El cliente no intentará establecer el uid y gid en los archivos, directorios y dispositivos recién creados (crear, mkdir, mknod), lo que hará que el servidor establezca el uid y gid en el valor predeterminado (generalmente el uid del servidor del usuario que montó el recurso compartido). Dejar que el servidor (en lugar del cliente) establezca el uid y gid es el valor predeterminado. Si las extensiones Unix de CIFS no se negocian, el uid y gid para los nuevos archivos parecerán ser el uid (gid) del montador o el uid (gid) especificado en el montaje.
perm
El cliente realiza comprobaciones de permisos (comprobación vfs_permission del uid y gid del archivo frente al modo y la operación deseada). Tenga en cuenta que esto es además de la comprobación normal de ACL en la máquina de destino realizada por el software del servidor. La comprobación de permisos del cliente está habilitada de forma predeterminada.
noperm
El cliente no realiza comprobaciones de permisos. Esto puede exponer los archivos en este montaje al acceso de otros usuarios en el sistema cliente local. Normalmente, solo es necesario cuando el servidor admite las extensiones Unix de CIFS pero los UID/GID en el sistema cliente y servidor no coinciden lo suficiente como para permitir el acceso al usuario que realiza el montaje. Tenga en cuenta que esto no afecta la comprobación normal de ACL en la máquina de destino realizada por el software del servidor (de la ACL del servidor frente al nombre de usuario proporcionado en el momento del montaje).
dynperm
Instruye al servidor para que mantenga la propiedad y los permisos en memoria que no se pueden almacenar en el servidor. Esta información puede desaparecer en cualquier momento (cada vez que el inodo se vacía de la caché), por lo que, si bien esto puede ayudar a que algunas aplicaciones funcionen, su comportamiento es algo poco fiable. Consulte la sección a continuación sobre PROPIEDAD Y PERMISOS DE ARCHIVOS Y DIRECTORIOS para obtener más información.
cache=arg
Modo de caché. Consulte la sección a continuación sobre COHERENCIA DE CACHÉ para obtener detalles. Los valores permitidos son:
  • none - no almacenar en caché los datos del archivo en absoluto
  • strict - seguir el protocolo CIFS/SMB2 estrictamente
  • loose - permitir semánticas de caché laxas

El valor predeterminado en kernels anteriores a 3.7 era loose. A partir del kernel 3.7, el valor predeterminado es strict.

nostrictsync
No solicite al servidor que vacíe en fsync(). Algunos servidores realizan escrituras no cacheadas de forma predeterminada, en cuyo caso el vaciado es redundante. En cargas de trabajo donde un cliente realiza muchas combinaciones de escritura + fsync pequeñas y donde la latencia de red es mucho mayor que la latencia del servidor, esto mejora el rendimiento en 2x. Esta opción también es una buena candidata en escenarios donde queremos rendimiento sobre consistencia.
handlecache
(predeterminado) En SMB2 y superior, el cliente a menudo tiene que abrir la raíz del recurso compartido (ruta vacía) en varios lugares durante el montaje, la revalidación de ruta y la llamada al sistema statfs(2). Esta opción reduce el tráfico redundante de ida y vuelta (aperturas y cierres) simplemente manteniendo el manejador del directorio para la raíz una vez abierto.
nohandlecache
Deshabilita el almacenamiento en caché del manejador del directorio raíz del recurso compartido.
max_cached_dirs=arg
El número máximo de directorios cacheados por recurso compartido. Los directorios se almacenan en caché localmente cuando el servidor otorga un permiso, lo que mejora el rendimiento al reducir el tráfico de red.

Por defecto, max_cached_dirs se establece en 16 y puede contener valores entre 0 y un valor máximo de 2^32 - 1.

handletimeout=arg
El tiempo (en milisegundos) durante el cual el servidor debe reservar el manejador después de una conmutación por error esperando a que el cliente se reconecte. Al montar con la opción de montaje resilienthandles o persistenthandles, o cuando el servidor solicita su uso (recursos compartidos de disponibilidad continua), este parámetro anula el tiempo de espera del manejador predeterminado del servidor (que para la mayoría de los servidores es de 120 segundos).
rwpidforward
Reenvía el pid de un proceso que abrió un archivo a cualquier operación de lectura o escritura en ese archivo. Esto evita que aplicaciones como wine(1) fallen en la lectura y escritura si utilizamos el estilo de bloqueo obligatorio.
mapchars
Traduce seis de los siete caracteres reservados (no la barra invertida, pero incluyendo los caracteres dos puntos, signo de interrogación, barra vertical, asterisco, mayor que y menor que) al rango de remapeo (por encima de 0xF000), lo que también permite al cliente CIFS reconocer archivos creados con dichos caracteres por los Servicios para Mac de Windows. Esto también puede ser útil al montar en la mayoría de las versiones de Samba (que también prohíben la creación y apertura de archivos cuyos nombres contienen cualquiera de estos siete caracteres). Esto no tiene ningún efecto si el servidor no admite Unicode en la red. Tenga en cuenta que los archivos creados con la opción de montaje mapchars pueden no ser accesibles si el recurso compartido se monta sin esa opción.
nomapchars
(predeterminado) No traduce ninguno de estos siete caracteres.
mapposix
Traduce los caracteres reservados de manera similar a mapchars, pero utiliza el mapeo de Microsoft "Services For Unix".
intr
actualmente no implementado.
nointr
(predeterminado) actualmente no implementado.
hard
El programa que accede a un archivo en el sistema de archivos montado cifs se colgará cuando el servidor falle.
soft
(predeterminado) El programa que accede a un archivo en el sistema de archivos montado cifs no se colgará cuando el servidor falle y devolverá errores a la aplicación de usuario.
noacl
No permitir operaciones POSIX ACL, incluso si el servidor las admitiera.

El cliente CIFS puede obtener y establecer ACL POSIX (getfacl, setfacl) en servidores Samba versión 3.0.10 y posteriores. Establecer ACL POSIX requiere habilitar tanto CONFIG_CIFS_XATTR como luego CONFIG_CIFS_POSIX en las opciones de configuración de CIFS al compilar el módulo cifs. El soporte de ACL POSIX se puede deshabilitar por montaje especificando noacl en el montaje.

cifsacl
Esta opción se utiliza para mapear ACL CIFS/NTFS hacia/desde bits de permiso de Linux, mapear SIDs hacia/desde UID y GID, y obtener y establecer Descriptores de Seguridad.

Consulte la sección sobre ACL CIFS/NTFS, Mapeo SID/UID/GID, DESCRIPTORES DE SEGURIDAD para obtener más información.

backupuid=arg
El acceso a archivos por parte de este usuario se realizará con la marca de intención de copia de seguridad establecida. Se debe proporcionar un nombre o un ID como argumento, no hay valores predeterminados.

Consulte la sección ACCESO A ARCHIVOS CON INTENCIÓN DE COPIA DE SEGURIDAD para obtener más detalles.

backupgid=arg
El acceso a archivos por parte de usuarios que son miembros de este grupo se realizará con la marca de intención de copia de seguridad establecida. Se debe proporcionar un nombre o un ID como argumento, no hay valores predeterminados.

Consulte la sección ACCESO A ARCHIVOS CON INTENCIÓN DE COPIA DE SEGURIDAD para obtener más detalles.

nocase
Solicita la coincidencia de nombres de ruta sin distinción entre mayúsculas y minúsculas (la distinción entre mayúsculas y minúsculas es el valor predeterminado si el servidor lo admite).
ignorecase
Sinónimo de nocase.
sec=arg
Modo de seguridad. Los valores permitidos son:
  • none - intenta conectarse como un usuario nulo (sin nombre)
  • krb5 - Utiliza autenticación Kerberos versión 5
  • krb5i - Usa autenticación Kerberos y habilita forzosamente la firma de paquetes
  • ntlm - Usa hash de contraseña NTLM
  • ntlmi - Usa hash de contraseña NTLM y fuerza la firma de paquetes
  • ntlmv2 - Usa hash de contraseña NTLMv2
  • ntlmv2i - Usa hash de contraseña NTLMv2 y fuerza la firma de paquetes
  • ntlmssp - Usa hash de contraseña NTLMv2 encapsulado en un mensaje Raw NTLMSSP
  • ntlmsspi - Usa hash de contraseña NTLMv2 encapsulado en un mensaje Raw NTLMSSP y fuerza la firma de paquetes

El valor predeterminado en las versiones principales del kernel anteriores a la v3.8 era sec=ntlm. En la v3.8, el valor predeterminado se cambió a sec=ntlmssp.

Si el servidor requiere firma durante la negociación del protocolo, puede habilitarse automáticamente. La firma de paquetes también puede habilitarse automáticamente si está habilitada en /proc/fs/cifs/SecurityFlags.

seal
Solicita cifrado a nivel de SMB. El algoritmo de cifrado utilizado es AES-128-CCM. Requiere SMB3 o superior (ver vers).
esize=arg
El tamaño mínimo (en bytes) de una respuesta de lectura cifrada en la que el cliente descargará la descifrado a un hilo de trabajo separado. Esto funcionará cuando el número de solicitudes en vuelo sea mayor que 1.

El descifrado de respuestas de lectura cifradas grandes puede ser computacionalmente costoso y, cuando hay varias lecturas en vuelo, descargar el trabajo puede mejorar el rendimiento.

El valor predeterminado es esize=0, lo que significa que todas las respuestas de lectura cifradas se descifran sin descarga y se pueden configurar hasta el tamaño máximo del búfer, que puede variar de 8192 a 130048 bytes, y tiene un valor predeterminado de 16384 bytes.

rdma
Conéctese directamente al servidor utilizando SMB Direct a través de un adaptador RDMA. Requiere SMB3 o superior (ver vers).
resilienthandles
Habilita identificadores resilientes. Si el servidor lo admite, mantén los archivos abiertos en caso de reconexión. Requiere SMB2.1 (ver vers).
noresilienthandles
(predeterminado) Deshabilita identificadores resilientes.
persistenthandles
Habilita identificadores persistentes. Si el servidor lo admite, mantén los archivos abiertos en caso de reconexión. Los identificadores persistentes también son válidos entre servidores de un clúster y tienen garantías más sólidas que los identificadores resilientes. Requiere SMB3 o superior (ver vers).
nopersistenthandles
(predeterminado) Deshabilita identificadores persistentes.
snapshot=time
Monta una instantánea específica del recurso compartido remoto. time debe ser un entero positivo que identifique la instantánea solicitada (en unidades de 100 nanosegundos transcurridas desde el 1 de enero de 1601, o alternativamente se puede especificar en formato GMT, por ejemplo, @GMT-2019.03.27-20.52.19). Soportado en el kernel de Linux a partir de la v4.19.
nobrl
No envíe solicitudes de bloqueo de rango de bytes al servidor. Esto es necesario para ciertas aplicaciones que no funcionan con bloqueos obligatorios de rango de bytes de estilo cifs (y la mayoría de los servidores cifs aún no admiten la solicitud de bloqueos consultivos de rango de bytes).
forcemandatorylock
No utilice bloqueos POSIX incluso cuando estén disponibles a través de extensiones Unix. Utilice siempre bloqueos obligatorios de estilo cifs.
locallease
Comprueba las concesiones locales en caché en lugar de consultar al servidor.
nolease
No solicite concesiones/oplocks al abrir un archivo en el servidor. Esto desactiva el almacenamiento en caché local de E/S, el bloqueo de rango de bytes y las operaciones de metadatos de lectura (ver actimeo para más detalles sobre el almacenamiento en caché de metadatos). Requiere SMB2 o superior (ver vers).
sfu
Cuando las Extensiones Unix CIFS o SMB3 no se negocian, intente crear archivos de dispositivo y fifos en un formato compatible con Services for Unix (SFU). Además, recupere los bits 10-12 del modo a través del atributo extendido SETFILEBITS (como hace SFU). En el futuro, los 9 bits inferiores del modo también se emularán mediante consultas del descriptor de seguridad (ACL). [NB: requiere la versión 1.39 o posterior del VFS CIFS. Reconocer enlaces simbólicos y poder crear enlaces simbólicos en un formato compatible con SFU requiere la versión 1.40 o posterior del módulo del kernel VFS CIFS.
mfsymlinks
Habilita el soporte para enlaces simbólicos Minshall+French (ver
http://wiki.samba.org/index.php/UNIX_Extensions#Minshall.2BFrench_symlinks ). Esta opción se ignora cuando se especifica junto con la opción sfu. Los enlaces simbólicos Minshall+French se utilizan incluso si el servidor admite las Extensiones Unix CIFS.
echo_interval=n
establece el intervalo en el que se envían solicitudes de eco al servidor en una conexión inactiva. Esta configuración también afecta el tiempo requerido para que una conexión a un servidor que no responde se cierre. Aquí n es el intervalo de eco en segundos. La reconexión ocurre al doble del valor del echo_interval establecido para un servidor que no responde. Si no se proporciona esta opción, se utiliza el valor predeterminado de 60 segundos. El valor sintonizable mínimo es de 1 segundo y el máximo puede llegar hasta 600 segundos.
serverino
Utiliza los números de inodo (identificadores de archivo persistentes únicos) devueltos por el servidor en lugar de generar automáticamente números de inodo temporales en el cliente. Aunque los números de inodo del servidor facilitan la detección de archivos enlazados físicamente (ya que tendrán los mismos números de inodo) y los números de inodo pueden ser persistentes (lo cual es útil para algunos programas), el servidor no garantiza que los números de inodo sean únicos si se exportan varios montajes del lado del servidor bajo una sola compartición (ya que los números de inodo en los servidores podrían no ser únicos si se montan varios sistemas de archivos bajo el mismo directorio superior compartido). Tenga en cuenta que no todos los servidores admiten la devolución de números de inodo del servidor, aunque aquellos que admiten las Extensiones Unix CIFS y los servidores Windows 2000 y posteriores suelen admitir esto (aunque no necesariamente en todos los sistemas de archivos locales del servidor). El parámetro no tiene efecto si el servidor no admite la devolución de números de inodo o equivalentes. Este comportamiento está habilitado por defecto.
noserverino
El cliente genera los números de inodo en lugar de utilizar los reales del servidor.

Ver sección NÚMEROS DE INODO para más información.

posix|unix|linux
(predeterminado) Habilita las Extensiones Unix para este montaje. Requiere CIFS (vers=1.0) o SMB3.1.1 (vers=3.1.1) y un servidor que las admita.
noposix|nounix|nolinux
Deshabilita las Extensiones Unix para este montaje. Esto puede ser útil para desactivar varias configuraciones a la vez. Esto incluye ACL POSIX, bloqueos POSIX, rutas POSIX, soporte de enlaces simbólicos y la recuperación de uid/gid/modo del servidor. Esto también puede ser útil para solucionar errores en un servidor que admite Extensiones Unix.

Ver sección NÚMEROS DE INODO para más información.

nouser_xattr
No permite que getfattr/setfattr obtengan/establezcan xattrs, incluso si el servidor lo admitiera de otra manera. El valor predeterminado es que el soporte de xattr esté habilitado.
nodfs
No seguir referencias de Distributed FileSystem. Las E/S en un archivo que no está almacenado en el servidor fallarán en lugar de conectarse al servidor de destino de forma transparente.
noautotune
Utiliza tamaño fijo para los búferes de socket de recepción/envío del kernel.
nosharesock
No intente reutilizar sockets si el sistema ya está conectado al servidor a través de un punto de montaje existente. Esto hará que el cliente siempre establezca una nueva conexión al servidor, sin importar si ya está conectado. Esto puede ser útil para simular múltiples clientes conectándose al mismo servidor, ya que cada punto de montaje utilizará un socket TCP diferente.
noblocksend
Envía datos en el socket utilizando operaciones no bloqueantes (bandera MSG_DONTWAIT).
rsize=bytes
Cantidad máxima de datos que el kernel solicitará en una solicitud de lectura en bytes. El tamaño máximo que los servidores aceptarán suele ser de 8 MB para dialectos SMB3 o posteriores. El valor predeterminado solicitado durante el montaje es de 4 MB. Antes del kernel 4.20, el valor predeterminado solicitado era de 1 MB. Antes del dialecto SMB2.1, el máximo solía ser de 64 K.
wsize=bytes
Cantidad máxima de datos que el kernel enviará en una solicitud de escritura en bytes. El tamaño máximo que los servidores aceptarán suele ser de 8 MB para dialectos SMB3 o posteriores. El valor predeterminado solicitado durante el montaje es de 4 MB. Antes del kernel 4.20, el valor predeterminado solicitado era de 1 MB. Antes del dialecto SMB2.1, el máximo solía ser de 64 K.
bsize=bytes
Anula el tamaño de bloque predeterminado (1 MB) informado en los archivos SMB3 (requiere una versión del kernel de 5.1 o posterior). Antes de la versión 5.1 del kernel, el tamaño de bloque siempre se informaba como 16 K en lugar de 1 MB (y no era configurable), lo que puede perjudicar el rendimiento de herramientas como cp y scp (especialmente para E/S sin caché), que deciden el tamaño de lectura y escritura a utilizar para las copias de archivos basándose en el tamaño de bloque del inodo. bsize no puede ser inferior a 16 K ni superior a 16 M.
max_credits=n
Créditos máximos que puede tener el cliente SMB2. El valor predeterminado es 32000. Debe establecerse en un número entre 20 y 60000.
fsc
Habilita el almacenamiento en caché local en disco utilizando FS-Cache para CIFS. Esta opción podría ser útil para mejorar el rendimiento en un enlace lento, un servidor muy cargado y/o una red donde leer del disco es más rápido que leer del servidor (a través de la red). Esto co
uld also impact the scalability positively as the number of calls to the server are reduced. But, be warned that local caching is not suitable for all workloads, for e.g., read-once type workloads. So, you need to consider carefully the situation/workload before using this option. Currently, local disk caching is enabled for CIFS files opened as read-only.

NOTA: Esta característica solo está disponible en los kernels más recientes que se han compilado con la opción de configuración del kernel CONFIG_CIFS_FSCACHE. También necesitas tener el demonio cachefilesd instalado y en ejecución para que la caché sea operativa.

multiuser
Mapea los accesos de usuario a credenciales individuales al acceder al servidor. Por defecto, los montajes CIFS solo utilizan un conjunto de credenciales de usuario (las credenciales de montaje) al acceder a un recurso compartido. Con esta opción, el cliente crea en su lugar una nueva sesión con el servidor utilizando las credenciales del usuario cada vez que un nuevo usuario accede al montaje. Futuros accesos de ese usuario también utilizarán esas credenciales. Dado que el kernel no puede solicitar contraseñas, los montajes multiusuario se limitan a montajes que utilizan opciones sec= que no requieren contraseñas.

Con este cambio, es factible que el servidor maneje la aplicación de permisos, por lo que esta opción también implica noperm. Además, cuando las extensiones Unix no están en uso y el administrador no ha anulado la propiedad utilizando las opciones uid= o gid=, la propiedad de los archivos se presenta como el usuario actual que accede al recurso compartido.

actimeo=arg
El tiempo (en segundos) que el cliente CIFS almacena en caché los atributos de un archivo o directorio antes de solicitar información de atributos a un servidor. Durante este período, los cambios que ocurren en el servidor permanecen sin detectarse hasta que el cliente vuelve a comprobar el servidor.

Por defecto, el tiempo de espera de la caché de atributos se establece en 1 segundo. Esto significa llamadas más frecuentes a través de la red al servidor para comprobar si los atributos han cambiado, lo que podría afectar al rendimiento. Con esta opción, los usuarios pueden realizar un compromiso entre el rendimiento y la corrección de los metadatos de la caché, dependiendo de las necesidades de la carga de trabajo. Tiempos de espera más cortos significan una mejor coherencia de la caché, pero un número elevado y frecuente de llamadas al servidor. Tiempos de espera más largos significan un número reducido de llamadas al servidor pero una menor coherencia de la caché. El valor de actimeo es un entero positivo que puede contener valores entre 0 y un valor máximo de 2^30 * HZ (frecuencia de la interrupción del temporizador). Establecerlo en 0 deshabilita el almacenamiento en caché.

acregmax=arg
El tiempo máximo (en segundos) que el cliente CIFS almacena en caché los atributos de un archivo regular antes de solicitar información de atributos actualizada a un servidor. Si esta opción no se especifica, el valor de acregmax se establecerá en el valor de actimeo, véase actimeo para más detalles.
acdirmax=arg
El tiempo máximo (en segundos) que el cliente CIFS almacena en caché los atributos de un directorio antes de solicitar información de atributos actualizada a un servidor. Si esta opción no se especifica, el valor de acdirmax se establecerá en el valor de actimeo, véase actimeo para más detalles.
upcall_target=arg
Determina el espacio de nombres en el que se deben manejar las llamadas superiores del sistema de archivos SMB. Los valores permitidos son: - mount - Resuelve las llamadas superiores al espacio de nombres del host. - app - Resuelve las llamadas superiores en el espacio de nombres del hilo que realiza la llamada (aplicación). El valor por defecto es app. Esta opción es útil en entornos como Kubernetes, donde el montaje puede ser realizado por un pod de controlador en nombre de una aplicación que se ejecuta en un contenedor separado. Asegura que las credenciales Kerberos y otros datos específicos del usuario se accedan en el espacio de nombres correcto. Al especificar app, las llamadas superiores se pueden resolver en el espacio de nombres de la aplicación, asegurando que se utilizan las credenciales correctas. mount permite la resolución en el espacio de nombres del host, lo que puede ser necesario cuando las credenciales o las configuraciones se gestionan fuera del contenedor.
multichannel
Esta opción habilita la función multichannel. Multichannel es una función del protocolo SMB3 que permite al cliente establecer múltiples conexiones de transporte a un servidor SMB y unirlas en una única sesión SMB autenticada. Esta función mejora la tolerancia a fallos y aumenta el rendimiento al distribuir el tráfico a través de varias conexiones. Con esta opción de montaje, el valor predeterminado es utilizar dos canales si el servidor soporta multichannel. El parámetro max_channels puede especificarse si se desea utilizar más de dos canales.
max_channels=arg
Esta opción es aplicable al usar la función multichannel. La opción max_channels permite al usuario especificar el número de conexiones de transporte que se deben establecer entre el cliente y el servidor hasta un límite de 16. El uso de esta opción habilita implícitamente la función multichannel. Si la opción max_channels no se especifica, la función multichannel usa por defecto 2 conexiones.
closetimeo=arg
El tiempo máximo (en segundos) que el cliente CIFS pospone el envío del cierre SMB3 final cuando el cliente tiene un contrato de arrendamiento (lease) del archivo.

Por defecto, closetimeo se establece en 1 segundo y puede contener valores entre 0 y un valor máximo de 2^30 * HZ.

noposixpaths
Si las extensiones Unix están habilitadas en un recurso compartido, el cliente generalmente permitirá que los nombres de archivo incluyan cualquier carácter excepto '/' en un componente de ruta, y utilizará barras inclinadas como delimitador de ruta. Esta opción evita que el cliente intente negociar el uso de rutas de estilo POSIX con el servidor.
posixpaths
Inverso de noposixpaths.
compress
CARACTERÍSTICA EXPERIMENTAL Habilita la compresión de mensajes en la red para montajes SMB 3.1.1 o superior. El montaje falla cuando compress está activado y vers se establece en una versión inferior a 3.1.1.
vers=arg
Versión del protocolo SMB. Los valores permitidos son:
  • 1.0 - El protocolo clásico CIFS/SMBv1.
  • 2.0 - El protocolo SMBv2.002. Se introdujo inicialmente en Windows Vista Service Pack 1 y Windows Server 2008. Tenga en cuenta que la versión de lanzamiento inicial de Windows Vista utilizaba un dialecto ligeramente diferente (2.000) que no es compatible.
  • 2.1 - El protocolo SMBv2.1 que se introdujo en Microsoft Windows 7 y Windows Server 2008R2.
  • 3.0 - El protocolo SMBv3.0 que se introdujo en Microsoft Windows 8 y Windows Server 2012.
  • 3.02 o 3.0.2 - El protocolo SMBv3.0.2 que se introdujo en Microsoft Windows 8.1 y Windows Server 2012R2.
  • 3.1.1 o 3.11 - El protocolo SMBv3.1.1 que se introdujo en Microsoft Windows 10 y Windows Server 2016.
  • 3 - La versión del protocolo SMBv3.0 y superior.
  • default - Intenta negociar la versión SMB2+ más alta soportada tanto por el cliente como por el servidor.

Si no se especifica ningún dialecto en el montaje, se utiliza vers=default. Para comprobar el Dialecto, consulte /proc/fs/cifs/DebugData

Tenga en cuenta también que, si bien esta opción rige la versión del protocolo utilizada, no todas las características de cada versión están disponibles.

El valor predeterminado desde la v4.13.5 es que el cliente y el servidor negocien la versión más alta posible mayor o igual a 2.1. En kernels anteriores a la v4.13, el valor predeterminado era 1.0. Para kernels entre la v4.13 y la v4.13.5, el valor predeterminado es 3.0.

sloppy
Permite al sistema ignorar cualquier opción de montaje no reconocida que siga a esta opción en lugar de fallar el montaje por completo.
--verbose
Imprime información de depuración adicional para el montaje. Tenga en cuenta que este parámetro debe especificarse antes de -o. Por ejemplo:
mount -t cifs //servidor/recurso /mnt --verbose -o usuario=nombreusuario

FORMATO DE SERVICIO Y DELIMITADORES

Generalmente se prefieren las barras inclinadas (/) como delimitador en los nombres de servicio. Se consideran el "delimitador universal" ya que generalmente no se permiten incrustados en componentes de ruta en máquinas Windows y el cliente puede convertirlos incondicionalmente a barras invertidas (\). Por el contrario, los caracteres de barra invertida están permitidos por POSIX como parte de un componente de ruta, y no pueden convertirse automáticamente de la misma manera.

mount.cifs intentará convertir barras invertidas a barras inclinadas donde pueda hacerlo, pero no puede hacerlo en ningún componente de ruta que siga al nombre del recurso compartido.

NÚMEROS DE INODO

Cuando las extensiones Unix están habilitadas, usamos el número de inodo real proporcionado por el servidor en respuesta a las llamadas POSIX como número de inodo.

Cuando las extensiones Unix están deshabilitadas y la opción de montaje serverino está habilitada, no hay forma de obtener el número de inodo del servidor. El cliente normalmente mapea el UniqueID asignado por el servidor a un número de inodo.

Tenga en cuenta que el UniqueID es un valor diferente del número de inodo del servidor. El valor UniqueID es único en el alcance de todo el servidor y a menudo es mayor que 2 elevado a 32. Este valor a menudo hace que los programas que no están compilados con LFS (Soporte para Archivos Grandes) generen un error EOVERFLOW de glibc, ya que no cabrá en el campo de estructura de destino. Se recomienda encarecidamente compilar sus programas con soporte LFS (es decir, con -D_FILE_OFFSET_BITS=64) para evitar este problema. También puede usar la opción de montaje noserverino para generar números de inodo menores que 2 elevado a 32 en el cliente. Pero es posible que no pueda detectar los enlaces duros correctamente.

COHERENCIA DE LA CACHÉ

Con un sistema de archivos de red como CIFS o NFS, el cliente debe lidiar con el hecho de que la actividad en otros clientes o en el servidor podría cambiar el contenido o los atributos de un archivo en

COMPORTAMIENTO DE CACHÉ

Cuando el cliente CIFS accede a un archivo que está siendo modificado por otro cliente, existe la posibilidad de que el cliente local obtenga datos desactualizados del caché sin que el cliente sea consciente de ello. Una forma de lidiar con tal problema es exigir que todos los accesos a archivos vayan directamente al servidor. Sin embargo, esto es prohibitivo en cuanto a rendimiento, por lo que la mayoría de los protocolos tienen algún mecanismo para permitir que el cliente almacene datos en caché localmente.

El protocolo CIFS exige (en efecto) que el cliente no almacene en caché los datos de archivos a menos que posea un bloqueo oportunista (también conocido como oplock) o un arrendamiento (lease). Ambas entidades permiten al cliente garantizar ciertos tipos de acceso exclusivo a un archivo para que pueda acceder a su contenido sin necesidad de interactuar continuamente con el servidor. El servidor llamará de vuelta al cliente cuando necesite revocar uno de ellos y permitirá al cliente una cierta cantidad de tiempo para vaciar cualquier dato en caché.

El cliente cifs utiliza la página de caché del kernel para almacenar en caché los datos de archivos. Cualquier E/S que se realice a través de la página de caché generalmente está alineada por páginas. Esto puede ser problemático cuando se combina con bloqueos de rango de bytes, ya que el bloqueo de Windows es obligatorio y puede impedir que se realicen lecturas y escrituras.

cache=none significa que el cliente nunca utiliza la caché para lecturas y escrituras normales. Siempre accede al servidor directamente para satisfacer una solicitud de lectura o escritura.

cache=strict significa que el cliente intentará seguir estrictamente el protocolo CIFS/SMB2. Es decir, la caché solo se confía cuando el cliente posee un oplock. Cuando el cliente no posee un oplock, entonces el cliente omite la caché y accede directamente al servidor para satisfacer una solicitud de lectura o escritura. Al hacer esto, el cliente evita problemas con los bloqueos de rango de bytes. Además, los bloqueos de rango de bytes se almacenan en caché en el cliente cuando posee un oplock y se "empujan" al servidor cuando se recupera ese oplock.

cache=loose permite al cliente utilizar semánticas de protocolo más flexibles, lo que a veces puede proporcionar un mejor rendimiento a expensas de la coherencia de la caché. El acceso a los archivos siempre involucra la página de caché. Cuando no se posee un oplock o un arrendamiento, el cliente intentará vaciar la caché poco después de escribir en un archivo. Tenga en cuenta que ese vaciado no se produce necesariamente antes de que se devuelva una llamada al sistema de escritura.

En el caso de una lectura sin poseer un oplock, el cliente intentará comprobar periódicamente los atributos del archivo para determinar si ha cambiado y si la caché podría ya no ser válida. Este mecanismo es muy similar al que utilizan NFSv2/3 para la coherencia de la caché, pero es particularmente problemático con CIFS. Windows es bastante "perezoso" con respecto a la actualización del campo LastWriteTime que el cliente utiliza para verificar esto. El efecto es que cache=loose puede causar corrupción de datos cuando varios lectores y escritores trabajan en los mismos archivos.

Debido a esto, cuando varios clientes acceden al mismo conjunto de archivos, se recomienda cache=strict. Esto ayuda a eliminar problemas de coherencia de caché al seguir los protocolos CIFS/SMB2 de manera más estricta.

Tenga en cuenta también que, independientemente del modelo de caché utilizado, el cliente siempre utilizará la página de caché para manejar los archivos mmap'ed. Las escrituras en archivos mmap'ed solo se garantizan que se vaciarán al servidor cuando se llame a msync(), o al cerrar().

El valor predeterminado en los kernels anteriores a 3.7 era loose. A partir de 3.7, el valor predeterminado es strict.

ACL CIFS/NTFS, ASIGNACIÓN SID/UID/GID, DESCRIPTORES DE SEGURIDAD

Esta opción se utiliza para trabajar con objetos de archivo que poseen Descriptores de Seguridad y ACL CIFS/NTFS en lugar de UID, GID, bits de permiso de archivo y ACL POSIX como modelo de autenticación de usuario. Este es el modelo de autenticación más común para servidores CIFS y es el que utiliza Windows.

El soporte para esto requiere que el módulo del kernel cifs esté compilado con las opciones CONFIG_CIFS_XATTR y CONFIG_CIFS_ACL habilitadas. Desde Linux 5.3, la opción CONFIG_CIFS_ACL ya no existe, ya que el soporte para ACL CIFS/NTFS siempre está integrado en el módulo del kernel cifs.

La mayoría de los kernels de distribución ya tendrán estas opciones habilitadas por defecto, pero aún puede verificar si están habilitadas con:

cat /lib/modules/$(uname -r)/build/.config

Alternativamente, si el kernel está configurado con CONFIG_IKCONFIG_PROC:

zcat /proc/config.gz

Una ACL CIFS/NTFS se asigna a los bits de permiso de archivo utilizando un algoritmo especificado en el siguiente documento de Microsoft TechNet:


http://technet.microsoft.com/en-us/library/bb463216.aspx

Para asignar SIDs a/desde UIDs y GIDs, se requiere lo siguiente:

  • una llamada al sistema del kernel a la utilidad cifs.idmap configurada a través de request-key.conf(5)
  • soporte de winbind o sssd configurado a través de nsswitch.conf(5)

Consulte las páginas de manual respectivas de cifs.idmap(8), winbindd(8) y sssd(8) para obtener más información.

Los descriptores de seguridad para un objeto de archivo se pueden recuperar y establecer directamente utilizando el atributo extendido llamado system.cifs_acl. Los descriptores de seguridad presentados a través de esta interfaz son "blobs" de datos "crudos" y necesitan una utilidad de espacio de usuario para analizarlos y formatearlos o ensamblarlos, como getcifsacl(1) y setcifsacl(1) respectivamente.

Algunas de las cosas a considerar al usar esta opción de montaje son:

  • Puede haber una latencia aumentada al manejar metadatos debido a solicitudes adicionales para obtener y establecer descriptores de seguridad.
  • La asignación entre una ACL CIFS/NTFS y los bits de permiso de archivo POSIX es imperfecta y parte de la información de la ACL puede perderse en la traducción.
  • Si la llamada al sistema a cifs.idmap no está configurada correctamente o winbind o sssd no están configurados y en ejecución, la asignación de ID fallará. En ese caso, uid y gid se establecerán por defecto a los valores del recurso compartido o a los valores de las opciones de montaje uid y/o gid si se especifican.

ACCEDER A ARCHIVOS CON INTENCIÓN DE COPIA DE SEGURIDAD

Para un usuario en el servidor, el acceso deseado a un archivo se determina por los permisos y derechos asociados con ese archivo. Esto se logra típicamente utilizando la propiedad y las ACL. Para un usuario que no tiene derechos de acceso a un archivo, todavía es posible acceder a ese archivo para un propósito específico o dirigido al otorgarle derechos especiales. Uno de los propósitos específicos es acceder a un archivo con la intención de realizar una copia de seguridad o restaurarla, es decir, intención de copia de seguridad. El derecho a acceder a un archivo con la intención de copia de seguridad típicamente se puede otorgar al hacer que ese usuario sea parte del grupo incorporado Operadores de copia de seguridad. Por lo tanto, cuando este usuario intenta abrir un archivo con la intención de copia de seguridad, la solicitud de apertura se envía estableciendo el bit FILE_OPEN_FOR_BACKUP_INTENT como una de las CreateOptions.

Como ejemplo, en un servidor de Windows, un usuario llamado testuser, no puede abrir este archivo con el siguiente descriptor de seguridad:

REVISION:0x1
CONTROL:0x9404
OWNER:Administrator
GROUP:Domain Users
ACL:Administrator:ALLOWED/0x0/FULL

Pero el usuario testuser, si se convierte en parte del grupo Operadores de copia de seguridad, puede abrir el archivo con la intención de copia de seguridad.

Cualquier usuario en el lado del cliente que pueda autenticarse como dicho usuario en el servidor, puede acceder a los archivos con la intención de copia de seguridad. Pero es deseable y preferible por razones de seguridad, entre otras, restringir este derecho especial.

La opción de montaje backupuid se utiliza para restringir este derecho especial a un usuario especificado por nombre o ID. La opción de montaje backupgid se utiliza para restringir este derecho especial a los usuarios de un grupo especificado por nombre o ID. Solo los usuarios que coincidan con backupuid o backupgid intentarán acceder a los archivos con intención de copia de seguridad. Estas dos opciones de montaje se pueden usar juntas.

PROPIEDAD Y PERMISOS DE ARCHIVOS Y DIRECTORIOS

El protocolo CIFS central no proporciona información de propiedad de Unix ni modo para archivos y directorios. Debido a esto, los archivos y directorios generalmente parecerán ser propiedad de los valores que se establezcan en las opciones uid= o gid=, y tendrán permisos establecidos en los valores predeterminados file_mode y dir_mode para el montaje. Intentar cambiar estos valores a través de chmod/chown devolverá éxito pero no tendrá ningún efecto.

Cuando el cliente y el servidor negocian extensiones de Unix, los archivos y directorios se asignarán el uid, gid y modo proporcionados por el servidor. Debido a que los montajes CIFS son generalmente de un solo usuario y se utilizan las mismas credenciales independientemente de qué usuario acceda al montaje, los archivos y directorios recién creados generalmente recibirán propiedad correspondiente a las credenciales utilizadas para montar el recurso compartido.

Si los uid y gid que se utilizan no coinciden en el cliente y el servidor, las opciones forceuid y forcegid pueden ser útiles. Sin embargo, tenga en cuenta que no existe una opción correspondiente para anular el modo. Los permisos asignados a un archivo cuando forceuid o forcegid están en efecto pueden no reflejar los permisos reales.

Cuando no se negocian las extensiones de Unix, también es posible emularlas localmente en el servidor utilizando la opción de montaje dynperm. Cuando esta opción de montaje está en efecto, los archivos y directorios recién creados recibirán lo que parecen ser permisos adecuados. Sin embargo, estos permisos no se almacenan en el servidor y pueden desaparecer en cualquier momento en el futuro (sujetos a los caprichos del kernel al vaciar la caché de inodos). En general, esta opción de montaje no se recomienda.

También es posible anular por completo la verificación de permisos en el cliente a través de la opción noperm. Las verificaciones de permisos del lado del servidor no se pueden anular. Las verificaciones de permisos realizadas por el servidor siempre corresponderán a las credenciales utilizadas para montar el recurso compartido, y no necesariamente al usuario que accede al recurso compartido.

CONFIGURACIÓN

El mecanismo principal para realizar cambios de configuración y leer información de depuración para el vfs cifs es a través del sistema de archivos /proc de Linux. En el directorio /proc/fs/cifs se encuentran varios archivos de configuración y pseudo-archivos que pueden mostrar información de depuración y estadísticas de rendimiento. Existen opciones adicionales de inicio, como el tamaño máximo del búfer y el número de búferes, que solo se pueden establecer cuando se carga el vfs cifs del kernel (módulo cifs.ko). Estas se pueden ver ejecutando la utilidad modinfo sobre el archivo cifs.ko, que listará las opciones que se pueden pasar a cifs durante la instalación del módulo (carga del controlador de dispositivo). Para más información, consulte el archivo del kernel fs/cifs/README. Al configurar el trazado dinámico (trace-cmd), tenga en cuenta que la lista de eventos SMB3 que se pueden habilitar se puede ver en: /sys/kernel/debug/tracing/events/cifs/.

SEGURIDAD

Se recomienda el uso de SMB2.1 o posterior (incluido el último dialecto SMB3.1.1) para una mayor seguridad y SMB1 ya no se solicita por defecto en el momento del montaje. Los dialectos antiguos como CIFS (SMB1, es decir, vers=1.0) tienen una seguridad mucho menor. El uso de CIFS (SMB1) se puede deshabilitar mediante modprobe cifs disable_legacy_dialects=y.

ERRORES

El montaje utilizando la especificación de URL CIFS no está soportado actualmente.

El archivo de credenciales no maneja nombres de usuario o contraseñas con espacios al principio.

Tenga en cuenta que la respuesta típica a un informe de error es una sugerencia para intentar primero la última versión. Por lo tanto, intente primero eso, y siempre incluya qué versiones utiliza del software relevante al informar errores (mínimo: mount.cifs (intente mount.cifs -V), kernel (vea /proc/version) y el tipo de servidor al que intenta conectarse.
