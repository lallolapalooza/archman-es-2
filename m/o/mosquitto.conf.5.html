MOSQUITTO.CONF(5) Formatos de archivo y convenciones MOSQUITTO.CONF(5)

NOMBRE

mosquitto.conf - el archivo de configuración de mosquitto

SINOPSIS

mosquitto.conf

DESCRIPCIÓN

mosquitto.conf es el archivo de configuración de mosquitto. Este archivo puede residir en cualquier lugar siempre que mosquitto pueda leerlo. Por defecto, mosquitto no necesita un archivo de configuración y utilizará los valores predeterminados que se enumeran a continuación. Consulte mosquitto(8) para obtener información sobre cómo cargar un archivo de configuración.

Mosquitto puede ser instruido para recargar el archivo de configuración enviando una señal SIGHUP como se describe en la sección Señales de mosquitto(8). No todas las opciones de configuración se pueden recargar, como se detalla en las opciones a continuación.

FORMATO DEL ARCHIVO

Todas las líneas que comienzan con # como el primer carácter se tratan como comentarios.

Las líneas de configuración comienzan con un nombre de variable. El valor de la variable se separa del nombre por un solo espacio.

AUTENTICACIÓN

Las opciones de autenticación descritas a continuación permiten una amplia gama de posibilidades en conjunto con las opciones de listener. Esta sección tiene como objetivo aclarar las posibilidades. También hay disponible una descripción general en https://mosquitto.org/documentation/authentication-methods/

La opción más simple es no tener ninguna autenticación. Este es el valor predeterminado si no se especifican otras opciones. El soporte encriptado no autenticado se proporciona utilizando las opciones de SSL/TLS basadas en certificados certfile y keyfile.

MQTT proporciona autenticación de nombre de usuario/contraseña como parte del protocolo. Utilice la opción password_file para definir los nombres de usuario y contraseñas válidos. Asegúrese de utilizar cifrado de red si está utilizando esta opción, de lo contrario, el nombre de usuario y la contraseña serán vulnerables a la interceptación. Utilice per_listener_settings para controlar si se requieren contraseñas globalmente o por listener.

Mosquitto proporciona el plugin Dynamic Security que maneja la autenticación de nombre de usuario/contraseña y el control de acceso de una manera mucho más flexible que un archivo de contraseñas. Consulte https://mosquitto.org/documentation/dynamic-security/

Al utilizar el cifrado basado en certificados, hay tres opciones que afectan la autenticación. La primera es require_certificate, que puede establecerse en true o false. Si es false, el componente SSL/TLS del cliente verificará el servidor, pero no hay requisito de que el cliente proporcione nada para el servidor: la autenticación se limita al nombre de usuario/contraseña incorporado de MQTT. Si require_certificate es true, el cliente debe proporcionar un certificado válido para conectarse correctamente. En este caso, las segunda y tercera opciones, use_identity_as_username y use_subject_as_username, cobran relevancia. Si se establece en true, use_identity_as_username hace que el Nombre Común (CN) del certificado del cliente se utilice en lugar del nombre de usuario de MQTT para fines de control de acceso. La contraseña no se utiliza porque se asume que solo los clientes autenticados tienen certificados válidos. Esto significa que cualquier certificado de CA que incluya en cafile o capath podrá emitir certificados de cliente que sean válidos para conectarse a su broker. Si use_identity_as_username es false, el cliente debe autenticarse como de costumbre (si es requerido por password_file) a través de las opciones de MQTT. El mismo principio se aplica para la opción use_subject_as_username, pero se utiliza todo el asunto del certificado como nombre de usuario en lugar de solo el CN.

Al utilizar el cifrado basado en clave precompartida a través de las opciones psk_hint y psk_file, el cliente debe proporcionar una identidad y clave válidas para conectarse al broker antes de que tenga lugar cualquier comunicación MQTT. Si use_identity_as_username es true, la identidad PSK se utiliza en lugar del nombre de usuario de MQTT para fines de control de acceso. Si use_identity_as_username es false, el cliente aún puede autenticarse utilizando el nombre de usuario/contraseña de MQTT si se utiliza la opción password_file.

Tanto el cifrado basado en certificados como en PSK se configuran por listener.

Se pueden crear plugins de autenticación para aumentar las opciones password_file, acl_file y psk_file con, por ejemplo, búsquedas basadas en SQL.

Es posible admitir varios esquemas de autenticación a la vez. Se podría crear una configuración que tuviera un listener para todas las diferentes opciones de cifrado descritas anteriormente y, por lo tanto, una gran cantidad de formas de autenticarse.

OPCIONES GENERALES

acl_file ruta del archivo

Establece la ruta a un archivo de lista de control de acceso. Si se define, los contenidos del archivo se utilizan para controlar el acceso de los clientes a los temas en el broker.

Si se define este parámetro, solo los temas enumerados tendrán acceso. El acceso a los temas se agrega con líneas del formato:

topic [read|write|readwrite|deny] <topic>

El tipo de acceso se controla utilizando "read", "write", "readwrite" o "deny". Este parámetro es opcional (a menos que <topic> contenga un espacio) - si no se proporciona, el acceso es de lectura/escritura. <topic> puede contener los comodines + o # como en las suscripciones. La opción "deny" se puede utilizar para denegar explícitamente el acceso a un tema que de lo contrario se concedería mediante una declaración más amplia de read/write/readwrite. Todos los temas "deny" se manejan antes que los temas que otorgan acceso de lectura/escritura.

El primer conjunto de temas se aplica a los clientes anónimos, suponiendo que allow_anonymous es true. Los ACL de temas específicos del usuario se agregan después de una línea de usuario de la siguiente manera:

user <username>

El nombre de usuario al que se hace referencia aquí es el mismo que en password_file. No es el clientid.

También es posible definir ACLs basadas en la sustitución de patrones dentro del tema. La forma es la misma que para la palabra clave topic, pero usando pattern como palabra clave.

pattern [read|write|readwrite|deny] <topic>

Los patrones disponibles para sustitución son:

•%c para coincidir con el client id del cliente
•%u para coincidir con el nombre de usuario del cliente

El patrón de sustitución debe ser el único texto para ese nivel de jerarquía. Las ACL de patrones se aplican a todos los usuarios, incluso si la palabra clave "user" se ha dado previamente.

Ejemplo:

pattern write sensor/%u/data

Permitir el acceso a los mensajes de conexión del puente:

pattern write $SYS/broker/connection/%c/state

Si el primer carácter de una línea del archivo ACL es #, se trata como un comentario.

Si per_listener_settings es true, esta opción se aplica solo al listener actual que se está configurando. Si per_listener_settings es false, esta opción se aplica a todos los listeners.

Se recarga con la señal de recarga. Los ACL actualmente cargados se liberarán y se recargarán. Las suscripciones existentes se verán afectadas después de la recarga.

Ver también https://mosquitto.org/documentation/dynamic-security/

allow_anonymous [ true | false ]

Valor booleano que determina si se permite la conexión a clientes que se conectan sin proporcionar un nombre de usuario. Si se establece en false, se debe crear otro medio de conexión para controlar el acceso de los clientes autenticados.

Por defecto es false, a menos que no se definan listeners en el archivo de configuración, en cuyo caso se establece en true, pero solo se permiten conexiones desde la máquina local.

Si per_listener_settings es true, esta opción se aplica solo al listener actual que se está configurando. Si per_listener_settings es false, esta opción se aplica a todos los listeners.


Importante
En la versión 1.6.x y anteriores, esta opción tenía como valor predeterminado true a menos que se estableciera otra opción de seguridad.
Se recarga con la señal de recarga.

allow_duplicate_messages [ true | false ]

Esta opción está obsoleta y se eliminará en una versión futura. El comportamiento será predeterminado como true.

Si un cliente está suscrito a varias suscripciones que se superponen, por ejemplo, foo/# y foo/+/baz, entonces MQTT espera que cuando el broker reciba un mensaje en un tema que coincida con ambas suscripciones, como foo/bar/baz, entonces el cliente solo reciba el mensaje una vez.


Si la opción está establecida en false, entonces los mensajes duplicados se enviarán a los clientes.

Esta opción solo afecta a los clientes que se conectan con la opción de protocolo MQTT 5. No tiene ningún efecto en los clientes que se conectan con versiones anteriores del protocolo.

Reloaded on reload signal. The currently loaded settings will be applied.

Este sitio no está asociado de ninguna forma con Arch Linux ni afiliado a este proyecto. El contenido es únicamente una traducción de las páginas del manual de Arch publicadas en man.archlinux.org.

Mosquitto realiza un seguimiento de a qué clientes se ha enviado un mensaje para cumplir con este requisito. Esta opción permite deshabilitar este comportamiento, lo que puede ser útil si tiene un gran número de clientes suscritos al mismo conjunto de temas y desea minimizar el uso de memoria.

Se puede establecer de forma segura en true si sabe de antemano que sus clientes nunca tendrán suscripciones superpuestas; de lo contrario, sus clientes deben poder manejar correctamente mensajes duplicados incluso cuando tengan QoS=2.

Por defecto es true.

Esta opción se aplica globalmente.

Recargado con la señal de recarga.

allow_zero_length_clientid [ true | false ]

MQTT 3.1.1 y MQTT 5 permiten a los clientes conectarse con un ID de cliente de longitud cero y que el broker genere un ID de cliente para ellos. Utilice esta opción para permitir/denegar este comportamiento. Por defecto es true.

Vea también la opción auto_id_prefix.

Si per_listener_settings es true, esta opción se aplica solo al oyente que se está configurando actualmente. Si per_listener_settings es false, esta opción se aplica a todos los oyentes.

Recargado con la señal de recarga.

auth_plugin_deny_special_chars [ true | false ]

Si es true, antes de que se realice una verificación de ACL, se buscará en el nombre de usuario/ID de cliente del cliente que necesita la verificación la presencia de un carácter '+' o '#'. Si se encuentra alguno de estos caracteres en el nombre de usuario o en el ID de cliente, la verificación de ACL se denegará antes de enviarla al complemento.

Esta verificación evita el caso en que un usuario malintencionado podría eludir una verificación de ACL utilizando uno de estos caracteres como su nombre de usuario o ID de cliente. Este es el mismo problema que se informó con el propio mosquitto como CVE-2017-7650.

Si está completamente seguro de que el complemento que está utilizando no es vulnerable a este ataque (es decir, si nunca usa nombres de usuario o ID de cliente en temas), puede deshabilitar esta verificación adicional y, por lo tanto, hacer que todas las verificaciones de ACL se entreguen a su complemento estableciendo esta opción en false.

Por defecto es true.

Se aplica al complemento de autenticación actual que se está configurando.

Actualmente no se recarga con la señal de recarga.

auto_id_prefix prefijo

Si allow_zero_length_clientid es true, esta opción le permite establecer una cadena que se antepondrá a los ID de cliente generados automáticamente para facilitar su visibilidad en los registros. Por defecto es auto-.

Si per_listener_settings es true, esta opción se aplica solo al oyente que se está configurando actualmente. Si per_listener_settings es false, esta opción se aplica a todos los oyentes.

Recargado con la señal de recarga.

autosave_interval segundos

El número de segundos que mosquitto esperará entre cada guardado de la base de datos en memoria en el disco. Si se establece en 0, la base de datos en memoria solo se guardará cuando mosquitto se cierre o al recibir la señal SIGUSR1. Tenga en cuenta que esta configuración solo tiene efecto si la persistencia está habilitada. Por defecto son 1800 segundos (30 minutos).

Esta opción se aplica globalmente.

Recargado con la señal de recarga.

autosave_on_changes [ true | false ]

Si es true, mosquitto contará el número de cambios de suscripción, mensajes retenidos recibidos y mensajes en cola, y si el total supera autosave_interval, la base de datos en memoria se guardará en el disco. Si es false, mosquitto guardará la base de datos en memoria tratando autosave_interval como un tiempo en segundos.

Esta opción se aplica globalmente.

Recargado con la señal de recarga.

check_retain_source [ true | false ]

Esta opción afecta al escenario en el que un cliente se suscribe a un tema que tiene mensajes retenidos. Es posible que el cliente que publicó el mensaje retenido en el tema tuviera acceso en el momento de la publicación, pero ese acceso se haya eliminado posteriormente. Si check_retain_source se establece en true, por defecto, se verificarán los derechos de acceso de la fuente de un mensaje retenido antes de que se vuelva a publicar. Cuando se establece en false, no se realizará ninguna verificación y el mensaje retenido se publicará siempre.

Esta opción se aplica globalmente, independientemente de la opción per_listener_settings.

clientid_prefixes prefijo

Esta opción está obsoleta y se eliminará en una versión futura.

Si se define, solo se permitirá conectar al broker a los clientes que tengan un clientid con un prefijo que coincida con clientid_prefixes. Por ejemplo, establecer "secure-" aquí significaría que un cliente "secure-client" podría conectarse, pero otro con clientid "mqtt" no podría. Por defecto, todos los clientids son válidos.

Esta opción se aplica globalmente.

Recargado con la señal de recarga. Tenga en cuenta que los clientes actualmente conectados no se verán afectados por ningún cambio.

connection_messages [ true | false ]

Si se establece en true, el registro incluirá entradas cuando los clientes se conecten y desconecten. Si se establece en false, estas entradas no aparecerán.

Esta opción se aplica globalmente.

Recargado con la señal de recarga.

include_dir directorio

Se pueden incluir archivos de configuración externos utilizando la opción include_dir. Esto define un directorio en el que se buscarán archivos de configuración. Todos los archivos que terminen en '.conf' se cargarán como archivo de configuración. Es mejor que esta sea la última opción en el archivo principal. Esta opción solo se procesará desde el archivo de configuración principal. El directorio especificado no debe contener el archivo de configuración principal.

Los archivos de configuración en include_dir se cargan en orden alfabético sensible a mayúsculas y minúsculas, con la mayúscula de cada letra ordenada antes que la minúscula de la misma letra.

Ejemplo de orden de carga para include_dir. Dados los archivos b.conf, A.conf, 01.conf, a.conf, B.conf y 00.conf dentro de include_dir, los archivos de configuración se cargarían en este orden:

00.conf
01.conf
A.conf
a.conf
B.conf
b.conf

Si esta opción se utiliza varias veces, cada opción include_dir se procesará completamente en el orden en que estén escritas en el archivo de configuración principal.

Ejemplo de orden de carga para Múltiples include_dir. Suponiendo un directorio one.d que contiene los archivos B.conf y C.conf, y un segundo directorio two.d que contiene los archivos A.conf y D.conf, y una configuración:

include_dir one.d
include_dir two.d

Entonces, los archivos de configuración se cargarían en este orden:

# archivos de one.d
B.conf
C.conf
# archivos de two.d
A.conf
D.conf

log_dest destinos

Envía mensajes de registro a un destino particular. Los destinos posibles son: stdout stderr syslog topic file dlt.

stdout y stderr registran en la consola en la salida nombrada.

syslog utiliza la instalación syslog del espacio de usuario que normalmente termina en /var/log/messages o similar.

topic registra en el tema del broker '$SYS/broker/log/<severity>', donde severity es uno de E, W, N, I, M que son error, advertencia, aviso, información y mensaje. La severidad del tipo de mensaje se utiliza para las opciones de registro subscribe y unsubscribe y publica mensajes de registro en $SYS/broker/log/M/subscribe y $SYS/broker/log/M/unsubscribe. Los mensajes de depuración nunca se registran en temas.

El destino file requiere un parámetro adicional que es el archivo en el que se registrará, por ejemplo, "log_dest file /var/log/mosquitto.log". El archivo se cerrará y reabrirá cuando el broker reciba una señal HUP. Solo se puede configurar un destino de archivo.

El destino dlt es para la herramienta automotriz `Diagnostic Log and Trace`. Esto requiere que Mosquitto se haya compilado con soporte DLT.

Utilice "log_dest none" si desea deshabilitar el registro. Por defecto es stderr. Esta opción se puede especificar varias veces.

Tenga en cuenta que si el broker se ejecuta como un servicio de Windows, por defecto será "log_dest none" y no habrá registro de stdout ni stderr disponible.

Recargado con la señal de recarga.

log_facility instalación local

Si se utiliza el registro syslog (no en Windows), los mensajes se registrarán en la instalación "daemon" por defecto. Utilice la opción log_facility para elegir en cuál de local0 a local7 registrar en su lugar. El valor de la opción debe ser un valor entero, por ejemplo, "log_facility 5" para usar local5.

log_timestamp [ true | false ]

Valor booleano, si se establece en true, se agregará una marca de tiempo a cada entrada de registro. El valor predeterminado es true.

Recargado con la señal de recarga.

log_timestamp_format formato

Establece el formato de la marca de tiempo del registro. Si no se establece, es el número de segundos desde la época Unix. Esta opción es una cadena de texto libre que se pasará a la función strftime como especificador de formato. Para obtener una fecha y hora ISO 8601, por ejemplo: 
log_timestamp_format %Y-%m-%dT%H:%M:%S

Recargado con la señal de recarga.

log_type tipos

Elige los tipos de mensajes a registrar. Los tipos posibles son: debug, error, warning, notice, information, subscribe, unsubscribe, websockets, none, all.

Por defecto son error, warning, notice e information. Esta opción se puede especificar varias veces. Tenga en cuenta que el tipo debug (utilizado para decodificar paquetes de red entrantes/salientes) nunca se registra en temas.

Recargado con la señal de recarga.

max_inflight_bytes contador

Se permitirán mensajes salientes de QoS 1 y 2 en tránsito hasta alcanzar este límite de bytes. Esto permite controlar la velocidad de los mensajes salientes en función del tamaño del mensaje en lugar del número de mensajes. Si el límite se establece en 100, todavía se permiten mensajes de más de 100 bytes, pero solo un mensaje puede estar en tránsito a la vez. Por defecto es 0. (Sin límite).

Vea también la opción max_inflight_messages.

Esta opción se aplica globalmente.

Recargado con la señal de recarga.

max_inflight_messages contador

El número máximo de mensajes salientes de QoS 1 o 2 que pueden estar en proceso de transmisión simultáneamente. Esto incluye los mensajes que actualmente están en el proceso de acuerdos y los mensajes que se están reintentando. Por defecto es 20. Establecido en 0

para ningún máximo. Si se establece en 1, esto garantizará la entrega de mensajes en orden.

Esta opción se aplica globalmente.

Recargada con la señal de recarga.

max_keepalive valor

Para los clientes MQTT v5, es posible que el servidor envíe un valor de "keepalive del servidor" que anule el valor de keepalive establecido por el cliente. Esto está destinado a ser utilizado como un mecanismo para indicar que el servidor desconectará al cliente antes de lo previsto, y que el cliente debe usar el nuevo valor de keepalive. La opción max_keepalive permite especificar que los clientes solo pueden conectarse con un keepalive menor o igual a este valor, de lo contrario se les enviará un keepalive del servidor indicándoles que usen max_keepalive. Esto solo se aplica a los clientes MQTT v5. El valor máximo admisible, y el valor por defecto, es 65535.

Establezca en 0 para permitir que los clientes establezcan keepalive = 0, lo que significa que no se realizan comprobaciones de keepalive y el broker nunca desconectará al cliente si no se reciben mensajes. Debe estar muy seguro de que este es el comportamiento que desea.

Para los clientes MQTT v3.1.1 y v3.1, no existe un mecanismo para indicar al cliente qué valor de keepalive deben usar. Si un cliente MQTT v3.1.1 o v3.1 especifica un tiempo de keepalive mayor que max_keepalive, se le enviará un mensaje CONNACK con el código de razón "identificador rechazado" y se le desconectará.

Esta opción se aplica globalmente.

Recargada con la señal de recarga.

max_packet_size valor

Para los clientes MQTT v5, es posible que el servidor envíe un valor de "tamaño máximo de paquete" que indicará al cliente que no aceptará paquetes MQTT de tamaño superior a valor bytes. Esto se aplica al paquete MQTT completo, no solo a la carga útil. Establecer esta opción en un valor positivo establecerá el tamaño máximo del paquete en esa cantidad de bytes. Si un cliente envía un paquete más grande que este valor, será desconectado. Esto se aplica a todos los clientes, independientemente de la versión del protocolo que utilicen, pero los clientes v3.1.1 y anteriores, por supuesto, no habrán recibido la información del tamaño máximo del paquete. Por defecto, no hay límite.

Esta opción se aplica a todos los clientes, no solo a los que utilizan MQTT v5, pero no es posible notificar a los clientes que utilizan MQTT v3.1.1 o MQTT v3.1 sobre el límite.

Establecer un valor inferior a 20 bytes está prohibido porque es probable que interfiera con el funcionamiento normal del cliente, incluso con cargas útiles pequeñas.

Esta opción se aplica globalmente.

Recargada con la señal de recarga.

max_queued_bytes contador

El número de mensajes salientes de QoS 1 y 2, además de los que están actualmente en tránsito, serán encolados (por cliente) por el broker. Una vez alcanzado este límite, los mensajes posteriores se descartarán silenciosamente. Esta es una opción importante si está enviando mensajes a alta velocidad y/o tiene clientes que responden lentamente o pueden estar desconectados durante períodos de tiempo prolongados. Por defecto es 0 (sin máximo).

Consulte también la opción max_queued_messages. Si se especifican tanto max_queued_messages como max_queued_bytes, los paquetes se encolarán hasta que se alcance el primer límite.

Esta opción se aplica globalmente.

Recargada con la señal de recarga.

max_queued_messages contador

El número máximo de mensajes de QoS 1 o 2 a mantener en la cola (por cliente) además de los mensajes que están actualmente en tránsito. Por defecto es 1000. Establezca en 0 para ningún máximo (no recomendado). Consulte también las opciones queue_qos0_messages y max_queued_bytes.

Esta opción se aplica globalmente.

Recargada con la señal de recarga.

memory_limit límite

Esta opción establece el número máximo de bytes de memoria del heap que el broker asignará, estableciendo así un límite estricto en el uso de memoria por parte del broker. Las solicitudes de memoria que excedan este valor serán denegadas. El efecto variará dependiendo de lo que se haya denegado. Si se está procesando un mensaje entrante, el mensaje se descartará y el cliente publicador será desconectado. Si se está enviando un mensaje saliente, el mensaje individual se descartará y el cliente receptor será desconectado. Por defecto, no hay límite.

Esta opción solo está disponible si la compatibilidad con el seguimiento de memoria está compilada.

Recargada con la señal de recarga. Establecer un valor inferior y recargar no provocará la liberación de memoria.

message_size_limit límite

Esta opción establece el tamaño máximo de la carga útil de publicación que el broker permitirá. Los mensajes recibidos que excedan este tamaño no serán aceptados por el broker. Esto significa que el mensaje no se reenviará a los clientes suscritos, pero el flujo de QoS se completará para mensajes de QoS 1 o QoS 2. Los clientes MQTT v5 que utilicen QoS 1 o QoS 2 recibirán un PUBACK o PUBREC con el código de razón "error específico de implementación".

El valor por defecto es 0, lo que significa que se aceptan todos los mensajes MQTT válidos. MQTT impone un tamaño máximo de carga útil de 268435455 bytes.

Esta opción se aplica globalmente.

Recargada con la señal de recarga.

password_file ruta del archivo

Establezca la ruta a un archivo de contraseñas. Si se define, el contenido del archivo se utilizará para controlar el acceso de los clientes al broker. El archivo puede crearse utilizando la utilidad mosquitto_passwd(1). Si mosquitto se compila sin soporte TLS (se recomienda incluir el soporte TLS), el archivo de contraseñas debe ser un archivo de texto con cada línea en el formato "nombredeusuario:contraseña", donde los dos puntos y la contraseña son opcionales pero recomendados. Si allow_anonymous se establece en false, solo los usuarios definidos en este archivo podrán conectarse. Establecer allow_anonymous en true cuando se define password_file es válido y podría usarse con acl_file para tener, por ejemplo, cuentas de invitado/anónimas de solo lectura y usuarios definidos que pueden publicar.

Si per_listener_settings es true, esta opción se aplica solo al oyente actual que se está configurando. Si per_listener_settings es false, esta opción se aplica a todos los oyentes.

Recargada con la señal de recarga. Los datos de nombre de usuario y contraseña cargados actualmente se liberarán y se volverán a cargar. Los clientes que ya estén conectados no se verán afectados.

Si es true, la configuración de autenticación y control de acceso se controlará por oyente. Las siguientes opciones se ven afectadas:

El comportamiento por defecto es que esto se establezca en false, lo que mantiene el comportamiento de configuración de versiones anteriores de mosquitto.

Recargada con la señal de recarga.

persistence [ true | false ]

Si es true, los datos de conexión, suscripción y mensajes se escribirán en disco en mosquitto.db en la ubicación dictada por persistence_location. Cuando mosquitto se reinicie, recargará la información almacenada en mosquitto.db. Los datos se escribirán en disco cuando mosquitto se cierre y también a intervalos periódicos según lo definido por autosave_interval. La escritura de la base de datos de persistencia también puede forzarse enviando la señal SIGUSR1 a mosquitto. Si es false, los datos se almacenarán solo en memoria. Por defecto es false.

El archivo de persistencia puede cambiar su formato en una nueva versión. El broker actualmente puede leer todos los formatos antiguos, pero solo guardará en el último formato. Siempre debería ser seguro actualizar, pero los usuarios cautelosos pueden desear hacer una copia del archivo de persistencia antes de instalar una nueva versión para poder retroceder a una versión anterior si es necesario.

Esta opción se aplica globalmente.

Recargada con la señal de recarga.

Esta opción se aplica globalmente.

Esta opción se aplica globalmente.

socket_domain [ ipv4 | ipv6 ]

Por defecto, un listener intentará escuchar en todas las versiones del protocolo IP compatibles. Si no tiene una interfaz IPv4 o IPv6, es posible que desee deshabilitar la compatibilidad con alguna de esas versiones de protocolo. En particular, tenga en cuenta que debido a las limitaciones de la biblioteca websockets, solo intentará abrir sockets IPv6 si la compatibilidad con IPv6 está compilada, y por lo tanto fallará si IPv6 no está disponible.

Establezca en ipv4 para forzar que el listener solo utilice IPv4, o establezca en ipv6 para forzar que el listener solo utilice IPv6. Si desea compatibilidad tanto con IPv4 como con IPv6, no utilice la opción socket_domain.

use_username_as_clientid [ true | false ]

Establezca use_username_as_clientid en true para reemplazar el clientid con el que un cliente se conectó con su nombre de usuario. Esto permite que la autenticación esté ligada al clientid, lo que significa que es posible evitar que un cliente desconecte a otro utilizando el mismo clientid. Por defecto es false.

Si un cliente se conecta sin nombre de usuario, será desconectado por no estar autorizado cuando esta opción esté configurada como true. No usar en conjunción con clientid_prefixes.

Esto no se aplica globalmente, sino por listener.

Soporte SSL/TLS basado en certificados

Las siguientes opciones están disponibles para que todos los listeners configuren el soporte SSL basado en certificados. Ver también "Soporte SSL/TLS basado en claves precompartidas".

cafile ruta_del_archivo

cafile se utiliza para definir la ruta a un archivo que contiene los certificados CA codificados en PEM que son de confianza al verificar los certificados de cliente entrantes.

capath ruta_del_directorio

capath se utiliza para definir un directorio que contiene certificados CA codificados en PEM que son de confianza al verificar los certificados de cliente entrantes. Para que capath funcione correctamente, los archivos de certificado deben tener ".pem" como extensión y debe ejecutar "openssl rehash <ruta_a_capath>" cada vez que agregue/elimine un certificado.

capath no es compatible con websockets.

certfile ruta_del_archivo

Ruta al certificado de servidor codificado en PEM. Esta opción y keyfile deben estar presentes para habilitar el cifrado TLS basado en certificados.

El certificado al que apunta esta opción se recargará cuando Mosquitto reciba una señal SIGHUP. Esto se puede utilizar para cargar nuevos certificados antes de que los existentes expiren.

ciphers lista_de_cifrados

La lista de cifrados permitidos para este listener, solo para TLS v1.2 y anteriores, cada uno separado por dos puntos. Los cifrados disponibles se pueden obtener utilizando el comando "openssl ciphers".

ciphers_tls1.3 lista_de_cifrados

La lista de suites de cifrado permitidas para este listener, para TLS v1.3, cada una separada por dos puntos.

crlfile ruta_del_archivo

Si tiene require_certificate establecido en true, puede crear un archivo de lista de revocación de certificados para revocar el acceso a certificados de cliente particulares. Si lo ha hecho, utilice crlfile para apuntar al archivo de revocación codificado en PEM.

dhparamfile ruta_del_archivo

Para permitir el uso del intercambio de claves DH efímero, que proporciona seguridad de reenvío, el listener debe cargar parámetros DH. Esto se puede especificar con la opción dhparamfile. El dhparamfile se puede generar con el comando, por ejemplo: 
openssl dhparam -out dhparam.pem 2048

keyfile ruta_del_archivo

Si tls_keyform es igual a "pem", esta es la ruta a la clave de servidor codificada en PEM. Esta opción y certfile deben estar presentes para habilitar el cifrado TLS basado en certificados. Si tls_keyform es "engine", representa el manejador del motor de la clave privada.

La clave privada a la que apunta esta opción se recargará cuando Mosquitto reciba una señal SIGHUP. Esto se puede utilizar para cargar nuevas claves antes de que las existentes expiren.

require_certificate [ true | false ]

Por defecto, un listener habilitado para SSL/TLS funcionará de manera similar a un servidor web habilitado para https, en el que el servidor tiene un certificado firmado por una CA y el cliente verificará que es un certificado de confianza. El objetivo general es cifrar el tráfico de red. Al establecer require_certificate en true, un cliente que se conecte a este listener debe proporcionar un certificado válido para que la conexión de red continúe. Esto permite controlar el acceso al broker fuera de los mecanismos proporcionados por MQTT.

tls_engine motor

Un ID de motor openssl válido. Estos se pueden listar con el comando openssl engine.

tls_engine_kpass_sha1 sha1_contraseña_motor

SHA1 de la contraseña de la clave privada cuando se utiliza un motor TLS. Algunos motores TLS, como el motor TPM, pueden requerir el uso de una contraseña para ser accedidos. Esta opción permite que un hash SHA1 codificado en hexadecimal de la contraseña se proporcione directamente al motor, en lugar de que se solicite la contraseña al usuario.

tls_keyform [ pem | engine ]

Especifica el tipo de clave privada en uso al realizar conexiones TLS. Puede ser "pem" o "engine". Este parámetro es útil cuando se utiliza un módulo TPM y la clave privada se ha creado con él. Por defecto es "pem", lo que significa que se utilizan archivos de clave privada normales.

tls_version versión

Configura la versión mínima del protocolo TLS que se utilizará para este listener. Los valores posibles son tlsv1.3, tlsv1.2 y tlsv1.1. Si se deja sin configurar, el valor predeterminado permite TLS v1.3 y v1.2.

En Mosquitto versión 1.6.x y anteriores, esta opción establecía la única versión del protocolo TLS que estaba permitida, en lugar de la mínima.

use_identity_as_username [ true | false ]

Si require_certificate es true, puede establecer use_identity_as_username en true para utilizar el valor CN del certificado del cliente como nombre de usuario. Si esto es true, la opción password_file no se utilizará para este listener.

Esto tiene prioridad sobre use_subject_as_username si ambos están configurados como true.

Ver también use_subject_as_username

use_subject_as_username [ true | false ]

Si require_certificate es true, puede establecer use_subject_as_username en true para utilizar el valor completo del sujeto del certificado del cliente como nombre de usuario. Si esto es true, la opción password_file no se utilizará para este listener.

El sujeto se generará en un formato similar a CN=test client,OU=Production,O=Server,L=Nottingham,ST=Nottinghamshire,C=GB.

Ver también use_identity_as_username

Soporte SSL/TLS basado en claves precompartidas

Las siguientes opciones están disponibles para que todos los listeners configuren el soporte SSL basado en claves precompartidas. Ver también "Soporte SSL/TLS basado en certificados".

Al usar PSK, los cifrados de encriptación utilizados se elegirán de la lista de cifrados PSK disponibles. Si desea controlar qué cifrados están disponibles, utilice esta opción. La pista se envía a los clientes y puede usarse localmente para ayudar en la autenticación. La pista es una cadena de formato libre que no tiene mucho significado en sí misma, así que siéntase libre de ser creativo.

Si se proporciona esta opción, consulte psk_file para definir las claves precompartidas que se utilizarán o cree un plugin de seguridad para manejarlas.

tls_version versión

Configura la versión mínima del protocolo TLS que se utilizará para este listener. Los valores posibles son tlsv1.3, tlsv1.2 y tlsv1.1. Si se deja sin configurar, el valor predeterminado permite TLS v1.3 y v1.2.

En Mosquitto versión 1.6.x y anteriores, esta opción establecía la única versión del protocolo TLS que estaba permitida, en lugar de la mínima.

use_identity_as_username [ true | false ]

Establezca use_identity_as_username para que la identidad PSK enviada por el cliente se utilice como su nombre de usuario. El nombre de usuario se verificará como de costumbre, por lo que se debe utilizar password_file u otro medio de verificación de autenticación. No se utilizará ninguna contraseña.

bridge_attempt_unsubscribe [ true | false ]

Si un puente tiene temas con dirección "out", el comportamiento predeterminado es enviar una solicitud de cancelación de suscripción al broker remoto en ese tema. Esto significa que cambiar la dirección de un tema de "in" a "out" no permitirá seguir recibiendo mensajes entrantes. Enviar estas solicitudes de cancelación de suscripción no siempre es deseable; establecer bridge_attempt_unsubscribe en false deshabilitará el envío de la solicitud de cancelación de suscripción. El valor predeterminado es true.

bridge_bind_address dirección ip

Si necesita que el puente se conecte a través de una interfaz de red particular, use bridge_bind_address para indicar al puente a qué dirección IP local debe vincular el socket, por ejemplo, bridge_bind_address 192.168.1.10.

bridge_max_packet_size valor

Si desea restringir el tamaño de los mensajes enviados a un puente remoto, use esta opción. Esto establece el número máximo de bytes para el mensaje total, incluidos los encabezados y la carga útil. Tenga en cuenta que los brokers MQTT v5 pueden proporcionar su propia propiedad de tamaño máximo de paquete. En este caso, se utilizará el menor de los dos límites. Establezca en 0 para "ilimitado".

bridge_outgoing_retain [ true | false ]

Algunos brokers MQTT no permiten mensajes retenidos. MQTT v5 proporciona un mecanismo para que los brokers indiquen a los clientes que no admiten mensajes retenidos, pero esto no es posible para MQTT v3.1.1 o v3.1. Si necesita enlazar a un broker v3.1.1 o v3.1 que no admita mensajes retenidos, establezca la opción bridge_outgoing_retain en false. Esto eliminará el bit de retención de todos los mensajes salientes a ese puente, independientemente de cualquier otra configuración. El valor predeterminado es true.

bridge_protocol_version versión

Establezca la versión del protocolo MQTT a utilizar para este puente. Puede ser mqttv50, mqttv311 o mqttv31. El valor predeterminado es mqttv311.

cleansession [ true | false ]

Establezca la opción de sesión limpia para este puente. Si se establece en false (el valor predeterminado), significa que todas las suscripciones en el broker remoto se conservan en caso de que la conexión de red se caiga. Si se establece en true, todas las suscripciones y mensajes en el broker remoto se limpiarán si la conexión se cae. Tenga en cuenta que establecerlo en true puede causar que se envíe una gran cantidad de mensajes retenidos cada vez que el puente se reconecta.

Si está utilizando puentes con cleansession establecido en false (el valor predeterminado), puede obtener un comportamiento inesperado de los temas entrantes si cambia los temas a los que se está suscribiendo. Esto se debe a que el broker remoto conserva la suscripción para el tema anterior. Si tiene este problema, conecte su puente con cleansession establecido en true, luego vuelva a conectar con cleansession establecido en false como normal.

local_cleansession [ true | false]

La opción regular cleansession cubre tanto las suscripciones locales como las remotas. local_cleansession permite dividir esto. Si se establece en false, la conexión local conservará las suscripciones, independientemente de la conexión remota.

El valor predeterminado es el valor de bridge.cleansession a menos que se especifique explícitamente.

connection nombre

Esta variable marca el inicio de una nueva conexión de puente. También se utiliza para dar un nombre al puente que se utiliza como ID de cliente en el broker remoto.

keepalive_interval segundos

Establezca el número de segundos después del cual el puente debe enviar un ping si no ha habido otro tráfico. El valor predeterminado es 60. Se permite un valor mínimo de 5 segundos.

idle_timeout segundos

Establezca el tiempo que un puente que utiliza el tipo de inicio perezoso debe estar inactivo antes de que se detenga. El valor predeterminado es 60 segundos.

local_clientid id

Establezca el clientid a utilizar en el broker local. Si no se define, el valor predeterminado es local.<remote_clientid>. Si está enlazando un broker consigo mismo, es importante que local_clientid y remote_clientid no coincidan.

local_password contraseña

Configure la contraseña a utilizar al conectar este puente al broker local. Esto puede ser importante cuando se utilizan autenticación y ACL.

local_username nombre de usuario

Configure el nombre de usuario a utilizar al conectar este puente al broker local. Esto puede ser importante cuando se utilizan autenticación y ACL.

notifications [ true | false ]

Si se establece en true, publique mensajes de notificación en los brokers local y remoto que proporcionen información sobre el estado de la conexión del puente. Los mensajes retenidos se publican en el tema $SYS/broker/connection/<remote_clientid>/state a menos que se establezca de otra manera con notification_topics. Si el mensaje es 1, la conexión está activa; si es 0, la conexión ha fallado. El valor predeterminado es true.

Esto utiliza la función de Última Voluntad y Testamento (LWT).

notifications_local_only [ true | false ]

Si se establece en true, publique solo mensajes de notificación en el broker local que proporcionen información sobre el estado de la conexión del puente. El valor predeterminado es false.

notification_topic tema

Elija el tema en el que se publicarán las notificaciones para este puente. Si no se establece, los mensajes se enviarán en el tema $SYS/broker/connection/<remote_clientid>/state.

remote_clientid id

Establezca el ID de cliente para esta conexión de puente. Si no se define, el valor predeterminado es 'name.hostname', donde 'name' es el nombre de la conexión y 'hostname' es el nombre de host de este equipo.

Esto reemplaza la antigua opción "clientid" para evitar confusiones con los lados local/remoto del puente. "clientid" sigue siendo válido por el momento.

remote_password valor

Configure una contraseña para el puente. Esto se utiliza para fines de autenticación al conectarse a un broker que admite MQTT v3.1 y superior y requiere un nombre de usuario y/o contraseña para conectarse. Esta opción solo es válida si también se proporciona un remote_username.

Esto reemplaza la antigua opción "password" para evitar confusiones con los lados local/remoto del puente. "password" sigue siendo válido por el momento.

remote_username nombre

Configure un nombre de usuario para el puente. Esto se utiliza para fines de autenticación al conectarse a un broker que admite MQTT v3.1 y superior y requiere un nombre de usuario y/o contraseña para conectarse. Consulte también la opción remote_password.

Esto reemplaza la antigua opción "username" para evitar confusiones con los lados local/remoto del puente. "username" sigue siendo válido por el momento.

restart_timeout base límite, restart_timeout constante

Establezca el tiempo que un puente que utiliza el tipo de inicio automático esperará antes de intentar reconectarse.

Esta opción se puede configurar para utilizar un tiempo de retardo constante en segundos, o para utilizar un mecanismo de retroceso basado en "Jitter Descorrelacionado", que agrega un grado de aleatoriedad a cuándo ocurre el reinicio, comenzando en la base y aumentando hasta el límite. Establezca un tiempo de espera constante de 20 segundos:

restart_timeout 20

Establezca el retroceso con una base (valor inicial) de 10 segundos y un límite (valor superior) de 60 segundos:

restart_timeout 10 30

El valor predeterminado es jitter con una base de 5 segundos y un límite de 30 segundos.

round_robin [ true | false ]

Si el puente tiene más de una dirección especificada en la configuración de dirección/direcciones, la opción round_robin define el comportamiento del puente en caso de fallo de la conexión del puente. Si round_robin es false, el valor predeterminado, entonces la primera dirección se trata como la conexión principal del puente. Si la conexión falla, se intentarán las otras direcciones secundarias por turno. Mientras esté conectado a un puente secundario, el puente intentará periódicamente reconectarse al puente principal hasta que tenga éxito.

Si round_robin es true, entonces todas las direcciones se tratan por igual. Si una conexión falla, se intentará la siguiente dirección y, si tiene éxito, permanecerá conectada hasta que falle.

start_type [ automatic | lazy | once ]

Establezca el tipo de inicio del puente. Esto controla cómo se inicia el puente y puede ser de uno de los tres tipos: automatic, lazy y once. Tenga en cuenta que RSMB proporciona un cuarto tipo de inicio "manual" que actualmente no es compatible con mosquitto.

automatic es el tipo de inicio predeterminado y significa que la conexión del puente se iniciará automáticamente cuando se inicie el broker y también se reiniciará después de un breve retraso (30 segundos) si la conexión falla.

Los puentes que utilizan el tipo de inicio lazy se iniciarán automáticamente cuando el número de mensajes en cola supere el número establecido con la opción threshold. Se detendrá automáticamente después del tiempo establecido por el parámetro idle_timeout. Utilice este tipo de inicio si desea que la conexión solo esté activa cuando sea necesaria.

Un puente que utiliza el tipo de inicio once se iniciará automáticamente cuando se inicie el broker, pero no se reiniciará si la conexión falla.

threshold conteo

Establezca el número de mensajes que deben estar en cola para que un puente con tipo de inicio perezoso se reinicie. El valor predeterminado es 10 mensajes.

topic patrón [[[ out | in | both ] nivel-qos] prefijo-local prefijo-remoto]

Defina un patrón de tema para compartir entre los dos brokers. Se comparten todos los temas que coinciden con el patrón (que puede incluir comodines). El segundo parámetro define la dirección en la que se compartirán los mensajes, por lo que es posible importar mensajes de un broker remoto utilizando in, exportar mensajes a un broker remoto utilizando out o compartir mensajes en ambas direcciones. Si este parámetro no se define, se utiliza el valor predeterminado de out. El nivel de QoS define el nivel de QoS de publicación/suscripción utilizado para este tema y, de forma predeterminada, es 0.

Las opciones prefijo-local y prefijo-remoto permiten reasignar temas al publicar y recibir de brokers remotos. Esto permite insertar un árbol de temas del broker local en el árbol de temas del broker remoto en un lugar apropiado.

Para temas entrantes, el puente antepondrá el patrón con el prefijo remoto y se suscribirá al tema resultante en el broker remoto. Cuando se reciba un mensaje entrante que coincida, se eliminará el prefijo remoto del tema y luego se agregará el prefijo local.

Para temas salientes

, el puente antepondrá el prefijo local al patrón y se suscribirá al tema resultante en el broker local. Cuando se procesa un mensaje saliente, se eliminará el prefijo local del tema y luego se añadirá el prefijo remoto.

Al utilizar el mapeo de temas, se puede definir un prefijo vacío usando el marcador "". Usar el marcador vacío para el propio tema también es válido. La siguiente tabla define qué combinación de vacío o valor es válida. El Tema Local Completo y el Tema Remoto Completo muestran los temas resultantes que se usarían en los extremos local y remoto del puente. Por ejemplo, para la primera fila de la tabla, si publicas en L/topic en el broker local, entonces el broker remoto recibirá un mensaje en el tema R/topic.

Patrón Prefijo Local Prefijo Remoto Validez Tema Local Completo Tema Remoto Completo
pattern L/ R/ válido L/pattern R/pattern
pattern L/ "" válido L/pattern pattern
pattern "" R/ válido pattern R/pattern
pattern "" "" válido (sin remapeo) pattern pattern
"" local remoto válido (remapear un solo tema local a remoto) local remoto
"" local "" inválido    
"" "" remoto inválido    
"" "" "" inválido    

Para remapear un árbol de temas completo, usa, por ejemplo:

topic # ambos 2 local/topic/ remote/topic/

Esta opción se puede especificar varias veces por puente.

Se debe tener cuidado para asegurar que no se creen bucles con esta opción. Si experimentas una alta carga de CPU en un broker, es posible que tengas un bucle en el que cada broker se reenvíe continuamente los mismos mensajes.

Consulta también la opción cleansession si recibes mensajes en temas inesperados al usar temas entrantes.

Ejemplo de Remapado de Temas de Puente.  La configuración siguiente conecta un puente al broker en test.mosquitto.org. Se suscribe al tema remoto $SYS/broker/clients/total y reenvía los mensajes recibidos al tema local test/mosquitto/org/clients/total

connection test-mosquitto-org
address test.mosquitto.org
cleansession true
topic clients/total in 0 test/mosquitto/org/ $SYS/broker/

try_private [ true | false ]

Si try_private se establece en true, el puente intentará indicar al broker remoto que es un puente y no un cliente ordinario. Si tiene éxito, esto significa que la detección de bucles será más efectiva y que los mensajes retenidos se propagarán correctamente. No todos los brokers admiten esta función, por lo que puede ser necesario establecer try_private en false si tu puente no se conecta correctamente.

El valor predeterminado es true.

Soporte SSL/TLS

Las siguientes opciones están disponibles para todos los puentes para configurar el soporte SSL/TLS.

bridge_alpn alpn

Configura la opción de negociación del protocolo de capa de aplicación para la sesión TLS. Útil para brokers que admiten tanto websockets como MQTT en el mismo puerto.

bridge_cafile ruta del archivo

Se debe proporcionar bridge_cafile o bridge_capath para permitir el soporte SSL/TLS.

bridge_cafile se utiliza para definir la ruta a un archivo que contiene los certificados CA codificados en PEM que han firmado el certificado del broker remoto.

bridge_capath ruta del archivo

Se debe proporcionar bridge_capath o bridge_cafile para permitir el soporte SSL/TLS.

bridge_capath se utiliza para definir la ruta a un directorio que contiene los certificados CA codificados en PEM que han firmado el certificado del broker remoto. Para que bridge_capath funcione correctamente, los archivos de certificado deben tener la extensión ".crt" y debes ejecutar "openssl rehash <ruta a bridge_capath>" cada vez que añadas/elimines un certificado.

bridge_certfile ruta del archivo

Ruta al certificado de cliente codificado en PEM para este puente, si es requerido por el broker remoto.

bridge_identity identidad

El cifrado de clave precompartida proporciona una alternativa al cifrado basado en certificados. Un puente se puede configurar para usar PSK con las opciones bridge_identity y bridge_psk. Esta es la identidad del cliente utilizada con el cifrado PSK. Solo uno de los cifrados, basado en certificado o PSK, puede usarse en un puente a la vez.

bridge_insecure [ true | false ]

Al usar TLS basado en certificados, el puente intentará verificar que el nombre de host proporcionado en el certificado remoto coincida con el host/dirección al que se está conectando. Esto puede causar problemas en escenarios de prueba, por lo que bridge_insecure puede establecerse en true para deshabilitar la verificación del nombre de host.

Establecer esta opción en true significa que un tercero malintencionado podría potencialmente suplantar tu servidor, por lo que siempre debe establecerse en false en entornos de producción.

bridge_keyfile ruta del archivo

Ruta a la clave privada codificada en PEM para este puente, si es requerida por el broker remoto.

bridge_psk clave

El cifrado de clave precompartida proporciona una alternativa al cifrado basado en certificados. Un puente se puede configurar para usar PSK con las opciones bridge_identity y bridge_psk. Esta es la clave precompartida en formato hexadecimal sin "0x". Solo uno de los cifrados, basado en certificado o PSK, puede usarse en un puente a la vez.

bridge_require_ocsp [ true | false ]

Cuando se establece en true, el puente requiere OCSP en la conexión TLS que abre como cliente.

bridge_tls_version versión

Configura la versión del protocolo TLS a utilizar para este puente. Los valores posibles son tlsv1.3, tlsv1.2 y tlsv1.1. El valor predeterminado es tlsv1.2. El broker remoto debe admitir la misma versión de TLS para que la conexión tenga éxito.
