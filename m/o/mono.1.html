NOMBRE

mono - Generador de código nativo de Mono para ECMA-CLI (Just-in-Time y Ahead-of-Time)

SINOPSIS

mono [opciones] archivo [argumentos...]

mono-sgen [opciones] archivo [argumentos...]

DESCRIPCIÓN

mono es una implementación en tiempo de ejecución de la Infraestructura Común de Lenguaje (Common Language Infrastructure) de ECMA. Esto puede usarse para ejecutar aplicaciones ECMA y .NET.

El tiempo de ejecución carga el archivo especificado y opcionalmente pasa los argumentos a este. El archivo es un ensamblado ECMA. Típicamente tienen una extensión .exe o .dll.

Estos ejecutables pueden referenciar funcionalidad adicional en forma de referencias de ensamblado. Por defecto, esas referencias de ensamblado se resuelven de la siguiente manera: mscorlib.dll se resuelve desde el perfil del sistema configurado por Mono, y otros ensamblados se cargan desde la Caché Global de Ensamblados (GAC).

El tiempo de ejecución contiene un generador de código nativo que transforma el Lenguaje Intermedio Común (Common Intermediate Language) en código nativo.

El generador de código puede operar en dos modos: compilación Just-in-Time (JIT) o compilación Ahead-of-Time (AOT). Dado que el código puede cargarse dinámicamente, el entorno de tiempo de ejecución y el JIT siempre están presentes, incluso si el código se compila ahead-of-time.

El tiempo de ejecución proporciona una serie de opciones de configuración para ejecutar aplicaciones, para desarrollo y depuración, y para probar y depurar el propio tiempo de ejecución.

El comando mono utiliza el recolector de basura SGen móvil y generacional, mientras que el comando mono-boehm utiliza el recolector de basura conservador de Boehm.

PORTABILIDAD

En sistemas basados en Unix, Mono proporciona un mecanismo para emular el acceso a archivos al estilo de Windows, esto incluye proporcionar una vista insensible a mayúsculas y minúsculas del sistema de archivos, mapeo de separadores de directorio (de \ a /) y eliminación de las letras de unidad.

Esta funcionalidad se habilita estableciendo la variable de entorno MONO_IOMAP a uno de los valores all, drive o case.

Consulte la descripción de MONO_IOMAP en la sección de variables de entorno para más detalles.

DESCRIPCIONES DE MÉTODOS

Una serie de opciones de línea de comandos de diagnóstico toman como argumento una descripción de método. Una descripción de método es una representación textual que puede usarse para identificar de forma única un método. La sintaxis es la siguiente:

[espacio_de_nombres]nombre_clase:nombre_método[(argumentos)]

Los valores entre corchetes son opcionales, como el espacio de nombres y los argumentos. Los argumentos en sí mismos están vacíos o son una lista separada por comas de argumentos. Tanto nombre_clase como nombre_método pueden establecerse al valor especial '*' para coincidir con cualquier valor (los usuarios de shells Unix deben escapar el argumento para evitar que el shell lo interprete).

Los argumentos, si están presentes, deben ser una lista separada por comas de tipos, ya sea un nombre de tipo completo, o para tipos integrados, deben usar los nombres de tipos de bajo nivel de ILAsm para los tipos integrados, como 'void', 'char', 'bool', 'byte', 'sbyte', 'uint16', 'int16', 'uint',

Los tipos de puntero deben ser el nombre del tipo, seguido de un '*', los arreglos deben ser el nombre del tipo seguido de '[' una o más comas (para indicar el rango del arreglo), y ']'.

Los valores genéricos deben usar '<', uno o más nombres de tipos, separados por una coma y un espacio, y '>'.

Los argumentos por referencia deben incluir un "&" después del nombre del tipo.

Ejemplos:

*:ctor(int)		// Todos los constructores que toman un int como argumento
*:Main			// Métodos llamados Main en cualquier clase
*:Main(string[])	// Métodos llamados Main que toman un array de string en cualquier clase

OPCIONES DE TIEMPO DE EJECUCIÓN

Las siguientes opciones están disponibles:

--aot, --aot[=opciones]
Esta opción se utiliza para precompilar el código CIL en el ensamblado especificado a código nativo. El código generado se almacena en un archivo con la extensión .so. Este archivo será recogido automáticamente por el tiempo de ejecución cuando se ejecute el ensamblado. La compilación Ahead-of-Time es más útil si se usa en combinación con el flag -O=all,-shared que habilita todas las optimizaciones en el generador de código. Algunas de estas optimizaciones no son prácticas para la compilación Just-in-Time, ya que pueden consumir mucho tiempo. A diferencia del .NET Framework, la compilación Ahead-of-Time no generará código independiente de dominio: genera el mismo código que produciría el compilador Just-in-Time. Dado que la mayoría de las aplicaciones utilizan un solo dominio, esto está bien. Si desea optimizar el código generado para su uso en aplicaciones multidominio, considere usar el flag -O=shared. Esto precompila los métodos, pero el ensamblado original todavía es necesario para ejecutarlo, ya que este contiene los metadatos y la información de excepciones que no están disponibles en el archivo generado. Al precompilar código, es posible que desee compilar con todas las optimizaciones (-O=all). El código precompilado es código independiente de la posición. La precompilación es solo un mecanismo para reducir el tiempo de inicio, aumentar el uso compartido de código entre múltiples procesos mono y evitar los costos de inicio del programa de compilación just-in-time. El ensamblado original aún debe estar presente, ya que los metadatos están contenidos allí. El código AOT típicamente no puede moverse de un ordenador a otro (optimizaciones específicas de la CPU detectadas en tiempo de ejecución), por lo que no debe intentar mover los ensamblados pregenerados ni empaquetar los ensamblados pregenerados para su implementación. Hay algunas opciones disponibles como parámetro de la opción de línea de comandos --aot. Las opciones se separan por comas, y se puede especificar más de una:
asmonly
Instruye al compilador AOT para que genere código de ensamblado en lugar de un archivo objeto.
bind-to-runtime-version
Si se especifica, fuerza que los archivos AOT generados se enlacen a la versión de tiempo de ejecución de Mono que los compila. Esto evitará que los archivos AOT sean consumidos por un tiempo de ejecución de Mono diferente.
data-outfile=FILE.dll.aotdata
Esto instruye al generador de código AOT para que genere ciertas construcciones de datos en un archivo separado. Esto puede reducir las imágenes ejecutables entre un cinco y un veinte por ciento. Los desarrolladores deben luego distribuir el aotdata resultante como un recurso y registrar un gancho para cargar los datos bajo demanda utilizando el método mono_install_load_aot_data_hook.
direct-icalls
Cuando se especifica esta opción, las llamadas internas (icalls, llamadas internas realizadas desde la biblioteca estándar al código del tiempo de ejecución de mono) se invocan directamente en lugar de pasar por la operación de búsqueda de símbolos del sistema operativo. Esto requiere el uso de la opción static.
direct-pinvoke
Cuando se especifica esta opción, los métodos P/Invoke se invocan directamente en lugar de pasar por la operación de búsqueda de símbolos del sistema operativo. Esto requiere el uso de la opción static.
dwarfdebug
Instruye al compilador AOT para que emita información de depuración DWARF. Cuando se usa junto con la opción nodebug, solo se emite información de depuración DWARF, pero no la información que se puede usar en tiempo de ejecución.
full
Esto crea binarios que pueden usarse con la opción --full-aot.
hybrid
Esto crea binarios que pueden usarse con la opción --hybrid-aot.
llvm
El AOT se realizará con el backend LLVM en lugar del backend Mono donde sea posible. Esto será más lento de compilar pero probablemente resultará en una mejora del rendimiento.
llvmonly
El AOT se realizará exclusivamente con el backend LLVM y no se utilizará el backend Mono. La única salida en este modo será el archivo bitcode que normalmente se especifica con la opción llvm-outfile. El uso de llvmonly habilita automáticamente las opciones full y llvm. Esta característica es experimental.
llvmopts=_opciones_

readonly-value=namespace.typename.fieldname=type/value
Anula el valor de un campo estático de solo lectura. Normalmente, durante la compilación JIT, el constructor estático se ejecuta de forma anticipada, por lo que el valor de un campo estático de solo lectura se conoce en el momento de la compilación y el compilador puede realizar una serie de optimizaciones basadas en él. Durante AOT, en cambio, el constructor estático no se puede ejecutar, por lo que esta opción se puede utilizar para establecer el valor de dicho campo y habilitar el mismo conjunto de optimizaciones. El tipo puede ser i1, i2, i4 para enteros de los tamaños respectivos (en bytes). Tenga en cuenta que los números con signo/sin signo no importan aquí, solo el tamaño del almacenamiento. Esta opción se puede especificar varias veces y no evita que el constructor estático del tipo que define el campo se ejecute con las reglas habituales en tiempo de ejecución (por lo tanto, potencialmente calculando un valor diferente para el campo).

Aplica los enlaces de ensamblado del archivo de configuración especificado al ejecutar el compilador AOT. --assembly-loader= MODO
Si el modo es estricto, Mono comprobará que el token de clave pública, la cultura y la versión de un ensamblado candidato coincidan con el nombre fuerte solicitado. Si el modo es legado, siempre que el nombre coincida, se permitirá el candidato. Estricto es el comportamiento coherente con .NET Framework, pero puede romper algunas aplicaciones existentes basadas en mono. El valor predeterminado es legado.

--full-aot
Esta bandera indica al tiempo de ejecución de Mono que no genere ningún código en tiempo de ejecución y dependa exclusivamente del código generado previamente con mono --aot=full. Esto es útil para plataformas que no permiten la generación de código dinámico, o si necesita ejecutar ensamblados a los que se les ha eliminado el IL (por ejemplo, usando mono-cil-strip). Tenga en cuenta que esta función abortará la ejecución en tiempo de ejecución si una ruta de código en su programa, o las bibliotecas de clases de Mono, intentan generar código dinámicamente. Debería probar su software de antemano y asegurarse de no utilizar ninguna característica dinámica.

--help, -h

--interpreter
El tiempo de ejecución de Mono utilizará su intérprete para ejecutar un ensamblado dado. El intérprete suele ser más lento que el JIT, pero puede ser útil en plataformas donde la generación de código en tiempo de ejecución no está permitida.
--hybrid-aot
Esta bandera permite que el tiempo de ejecución de Mono ejecute ensamblados a los que se les ha eliminado el IL, por ejemplo, usando mono-cil-strip. Para que esto funcione, el ensamblado debe haber sido compilado AOT con --aot=hybrid.

Esta bandera es similar a --full-aot, pero no deshabilita el JIT. Esto significa que puede usar características dinámicas como System.Reflection.Emit.

--llvm
Si el tiempo de ejecución de Mono se ha compilado con soporte LLVM (no disponible en todas las configuraciones), Mono utilizará el motor de optimización y generación de código de LLVM para compilar JIT o AOT. Para más información, consulte: http://www.mono-project.com/docs/advanced/mono-llvm/
--ffast-math
Esta bandera permite a Mono y LLVM aplicar optimizaciones agresivas de punto flotante. Puede romper el cumplimiento de IEEE754.
--nollvm
Al usar un Mono que se ha compilado con soporte LLVM, fuerza a Mono a volver a su motor JIT y no usar el backend LLVM.

DEPURACIÓN REMOTA

Es posible adjuntar un depurador a un proceso de Mono en ejecución. Esto se hace enviando un carácter especial a Mono. El carácter se envía mediante el envío de una señal especial al proceso Mono.

En la mayoría de los sistemas Unix, esto se puede hacer usando el comando `gcore` y enviando el archivo generado a Mono. El archivo se llama `core.`. Luego, el programa adjunto debe crear sus propios hilos y retornar después de la invocación.

Este soporte permite, por ejemplo, depurar aplicaciones haciendo que el shell de csharp se adjunte a procesos en ejecución.

PERFILADO

El runtime de Mono incluye una API de perfilador que los módulos de perfilador cargados dinámicamente y los integradores pueden usar para recopilar datos relacionados con el rendimiento de una aplicación. Los módulos de perfilador se cargan pasando el argumento de línea de comandos --profile al runtime de Mono.

Mono viene con algunos módulos de perfilador, de los cuales el perfilador log es el más completo. También es el perfilador predeterminado si no se proporciona el argumento profiler, o si se proporciona default. Es posible escribir sus propios módulos de perfilador; vea la subsección Perfiladores personalizados.

Perfilador de registros

El perfilador de registros se puede utilizar para recopilar mucha información sobre un programa que se ejecuta en el runtime de Mono. Estos datos se pueden usar (tanto mientras el proceso se está ejecutando como después) para realizar análisis del comportamiento del programa, determinar el uso de recursos, problemas de rendimiento o incluso buscar patrones de ejecución particulares.

Esto se logra registrando los eventos proporcionados por el runtime de Mono a través de la API del perfilador y escribiéndolos periódicamente en un archivo que luego puede ser inspeccionado con la herramienta mprof-report(1).

Se puede encontrar más información sobre cómo usar el perfilador de registros en la página mono-profilers(1), bajo la sección PERFILADOR DE REGISTROS, así como en la página mprof-report(1).

Perfilador de cobertura

El perfilador de cobertura de código puede instrumentar un programa para ayudar a determinar qué clases, métodos, rutas de código, etc., se ejecutan realmente. Esto es más útil cuando se ejecuta un conjunto de pruebas para determinar si las pruebas realmente cubren el código que se espera que cubran.

Se puede encontrar más información sobre cómo usar el perfilador de cobertura en la página mono-profilers(1), bajo la sección PERFILADOR DE COBERTURA.

Perfilador AOT

El perfilador AOT puede ayudar a mejorar el rendimiento de inicio registrando qué instanciaciones genéricas utiliza un programa, que el compilador AOT puede usar para compilar esas instanciaciones con anticipación para que no tengan que ser compiladas JIT al inicio.

Se puede encontrar más información sobre cómo usar el perfilador AOT en la página mono-profilers(1), bajo la sección PERFILADOR AOT.

Perfiladores personalizados

Los módulos de perfilador personalizados se pueden cargar de la misma manera que los módulos estándar que se distribuyen con Mono. También pueden acceder a la misma API de perfilador para recopilar todo tipo de información sobre el código que se está ejecutando.

Por ejemplo, para usar un perfilador de terceros llamado custom, lo cargaría de la siguiente manera:

mono --profile=custom program.exe

También podría pasarle argumentos:

mono --profile=custom:arg1,arg2=arg3 program.exe

En el ejemplo anterior, Mono cargará el perfilador de la biblioteca compartida llamada libmono-profiler-custom.so (el nombre varía según la plataforma, por ejemplo, libmono-profiler-custom.dylib en OS X). Este módulo de perfilador debe estar en la ruta de bibliotecas del enlazador dinámico (LD_LIBRARY_PATH en la mayoría de los sistemas, DYLD_LIBRARY_PATH en OS X).

Para obtener un ejemplo de cómo escribir su propio perfilador personalizado, consulte el archivo samples/profiler/sample.c en el árbol de fuentes de Mono.

AYUDAS DE DEPURACIÓN

Para depurar aplicaciones administradas, puede usar el comando mdb, un depurador de línea de comandos.

Es posible obtener un volcado de la pila de todos los hilos activos en Mono enviando la señal QUIT a Mono; puede hacerlo desde la línea de comandos, de la siguiente manera:

kill -QUIT pid
Donde pid es el ID del proceso de Mono que desea examinar. El proceso continuará ejecutándose después, pero su estado no está garantizado.

Importante: este es un mecanismo de último recurso para depurar aplicaciones y no debe usarse para monitorear o sondear una aplicación en producción. La integridad del runtime después de enviar esta señal no está garantizada y la aplicación podría fallar o terminar en cualquier momento posterior.

La opción --debug=casts se puede utilizar para obtener información más detallada para operaciones de Cast Inválido, proporcionará información sobre los tipos involucrados.

Puede usar las variables de entorno MONO_LOG_LEVEL y MONO_LOG_MASK para obtener una salida de depuración detallada sobre la ejecución de su aplicación dentro de Mono.

La variable de entorno MONO_LOG_LEVEL, si se establece, cambiará el nivel de registro al valor establecido. Los valores posibles son "error", "critical", "warning", "message", "info", "debug". El valor predeterminado es "error". Los mensajes con un nivel de registro mayor o igual al nivel de registro se imprimirán en stdout/stderr.

Use "info" para rastrear la carga dinámica de ensamblados.

Use la variable de entorno MONO_LOG_MASK para limitar el alcance de los mensajes que recibe: Si se establece, la máscara de registro cambiará al valor establecido. Los valores posibles son "asm" (cargador de ensamblados), "type", "dll" (cargador de bibliotecas nativas), "gc" (recolector de basura), "cfg" (cargador de archivos de configuración), "aot" (precompilador), "security" (por ejemplo, soporte de Moonlight CoreCLR), "threadpool" (pool de hilos genérico), "io-selector" (operaciones de socket asíncronas), "io-layer" (capa de E/S - procesos, archivos, sockets, eventos, semáforos, mutexes y manejadores), "io-layer-process", "io-layer-file", "io-layer-socket", "io-layer-event", "io-layer-semaphore", "io-layer-mutex", "io-layer-handle" y "all". El valor predeterminado es "all". Cambiar el valor de la máscara le permite mostrar solo mensajes para un componente específico. Puede usar múltiples máscaras separándolas con comas. Por ejemplo, para ver mensajes del archivo de configuración y mensajes del cargador de ensamblados, establezca su máscara en "asm,cfg".

El siguiente es un uso común para rastrear problemas con P/Invoke:

$ MONO_LOG_LEVEL="debug" MONO_LOG_MASK="dll" mono glue.exe

SERIALIZACIÓN

El motor de serialización XML de Mono por defecto utilizará un enfoque basado en reflexión para serializar, lo que podría ser lento para el procesamiento continuo (aplicaciones de servicios web). El motor de serialización determinará cuándo una clase debe usar un serializador hecho a mano basándose en algunos parámetros y, si es necesario, generará un serializador C# personalizado para sus tipos en tiempo de ejecución. Este serializador personalizado se carga dinámicamente en su aplicación.

Puede controlar esto con la variable de entorno MONO_XMLSERIALIZER_THS.

Los valores posibles son `no' para deshabilitar el uso de un serializador personalizado C#, o un entero que es el número mínimo de usos antes de que el runtime genere un serializador personalizado (0 generará un serializador personalizado en el primer acceso, 50 generará un serializador en el 50º uso). Mono recurrirá a un serializador interpretado si la generación del serializador falla de alguna manera. Este comportamiento se puede deshabilitar estableciendo la opción `nofallback' (por ejemplo: MONO_XMLSERIALIZER_THS=0,nofallback).

Tuning the GC

The GC can be tuned by passing command line arguments to the mono(1) executable. These arguments are passed using the environment variable MONO_GC_PARAMS.

For example, to set the default nursery size to 8MB and enable concurrent sweeping, you would use: 

MONO_GC_PARAMS=nursery-size=8m,concurrent-sweep mono myapp
nursery-size=size
Sets the size of the nursery. The default nursery size is 4 MB.
major=collector
Specifies which major collector to use. Options are `marksweep' for the Mark&Sweep collector, `marksweep-conc' for concurrent Mark&Sweep and `marksweep-conc-par' for parallel and concurrent Mark&Sweep. The concurrent Mark&Sweep collector is the default.
mode=balanced|throughput|pause[:max-pause]
Specifies what should be the garbage collector's target. The `throughput' mode aims to reduce time spent in the garbage collector and improve application speed, the `pause' mode aims to keep pause times to a minimum and it receives the argument max-pause which specifies the maximum pause time in milliseconds that is acceptable and the `balanced' mode which is a general purpose optimal mode.
soft-heap-limit=size
Once the heap size gets larger than this size, ignore what the default major collection trigger metric says and only allow four nursery size's of major heap growth between major collections.
evacuation-threshold=threshold
Sets the evacuation threshold in percent. This option is only available on the Mark&Sweep major collectors. The value must be an integer in the range 0 to 100. The default is 66. If the sweep phase of the collection finds that the occupancy of a specific heap block type is less than this percentage, it will do a copying collection for that block type in the next major collection, thereby restoring occupancy to close to 100 percent. A value of 0 turns evacuation off.
(no-)lazy-sweep
Enables or disables lazy sweep for the Mark&Sweep collector. If enabled, the sweeping of individual major heap blocks is done piecemeal whenever the need arises, typically during nursery collections. Lazy sweeping is enabled by default.
(no-)concurrent-sweep
Enables or disables concurrent sweep for the Mark&Sweep collector. If enabled, the iteration of all major blocks to determine which ones can be freed and which ones have to be kept and swept, is done concurrently with the running program. Concurrent sweeping is enabled by default.
stack-mark=mark-mode
Specifies how application threads should be scanned. Options are `precise` and `conservative`. Precise marking allow the collector to know what values on stack are references and what are not. Conservative marking threats all values as potentially references and leave them untouched. Precise marking reduces floating garbage and can speed up nursery collection and allocation rate, it has the downside of requiring a significant extra memory per compiled method. The right option, unfortunately, requires experimentation.
save-target-ratio=ratio
Specifies the target save ratio for the major collector. The collector lets a given amount of memory to be promoted from the nursery due to minor collections before it triggers a major collection. This amount is based on how much memory it expects to free. It is represented as a ratio of the size of the heap after a major collection. Valid values are between 0.1 and 2.0. The default is 0.5. Smaller values will keep the major heap size smaller but will trigger more major collections. Likewise, bigger values will use more memory and result in less frequent major collections. This option is EXPERIMENTAL, so it might disappear in later versions of mono.
default-allowance-ratio=ratio
Specifies the default allocation allowance when the calculated size is too small. The allocation allowance is how much memory the collector let be promoted before triggered a major collection. It is a ratio of the nursery size. Valid values are between 1.0 and 10.0. The default is 4.0. Smaller values lead to smaller heaps and more frequent major collections. Likewise, bigger values will allow the heap to grow faster but use more memory when it reaches a stable size. This option is EXPERIMENTAL, so it might disappear in later versions of mono.
minor=minor-collector
Specifies which minor collector to use. Options are `simple' which promotes all objects from the nursery directly to the old generation, `simple-par' which has same promotion behavior as `simple' but using multiple workers and `split' which lets objects stay longer on the nursery before promoting.
alloc-ratio=ratio
Specifies the ratio of memory from the nursery to be use by the alloc space. This only can only be used with the split minor collector. Valid values are integers between 1 and 100. Default is 60.
promotion-age=age
Specifies the required age of an object must reach inside the nursery before been promoted to the old generation. This only can only be used with the split minor collector. Valid values are integers between 1 and 14. Default is 2.
(no-)cementing
Enables or disables cementing. This can dramatically shorten nursery collection times on some benchmarks where pinned objects are referred to from the major heap.
allow-synchronous-major
This forbids the major collector from performing synchronous major collections. The major collector might want to do a synchronous collection due to excessive fragmentation. Disabling this might trigger OutOfMemory error in situations that would otherwise not happen.
MONO_GC_DEBUG
When using Mono with the SGen garbage collector this environment variable can be used to turn on various debugging features of the collector. The value of this variable is a comma separated list of words. Do not use these options in production.
number
Sets the debug level to the specified number.
print-allowance
After each major collection prints memory consumption for before and after the collection and the allowance for the minor collector, i.e. how much the heap is allowed to grow from minor collections before the next major collection is triggered.
print-pinning
Gathers statistics on the classes whose objects are pinned in the nursery and for which global remset entries are added. Prints those statistics when shutting down.
collect-before-allocs
check-remset-consistency
This performs a remset consistency check at various opportunities, and also clears the nursery at collection time, instead of the default, when buffers are allocated (clear-at-gc). The consistency check ensures that there are no major to minor references that are not on the remembered sets.
mod-union-consistency-check
Checks that the mod-union cardtable is consistent before each finishing major collection pause. This check is only applicable to concurrent major collectors.
check-mark-bits
Checks that mark bits in the major heap are consistent at the end of each major collection. Consistent mark bits mean that if an object is marked, all objects that it had references to must also be marked.
check-nursery-untag
After garbage collections, check whether all vtable pointers are no longer tagged.
xdomain-checks
Performs a check to make sure that no references are left to an unloaded AppDomain.
clear-at-tlab-creation
Clears the nursery incrementally when the thread local allocation buffers (TLAB) are created. The default setting clears the whole nursery at GC time.
debug-clear-at-tlab-creation
Clears the nursery incrementally when the thread local allocation buffers (TLAB) are created, but at GC time fills it with the byte `0xff`, which should result in a crash more quickly if `clear-at-tlab-creation` doesn't work properly.
clear-at-gc
This clears the nursery at GC time instead of doing it when the thread local allocation buffer (TLAB) is created. The default is to clear the nursery at TLAB creation time.
disable-minor
Don't do minor collections. If the nursery is full, a major collection is triggered instead, unless it, too, is disabled.
disable-major
Don't do major collections.
conservative-stack-mark
Forces the GC to scan the stack conservatively, even if precise scanning is available.
no-managed-allocator
Disables the managed allocator.
managed-allocator
Enables the managed allocator.
check-scan-starts
If set, does a plausibility check on the scan_starts before and after each collection
verify-nursery-at-minor-gc
If set, does a complete object walk of the nursery at the start of each minor collection.

Instruye al runtime para que inicialice la pila con algunos valores conocidos (0x2a en x86-64) al inicio de un método para ayudar a depurar el motor JIT.
keep-delegates
Esta opción filtrará trampolines de delegados que ya no se referencian para presentar al usuario más información sobre el uso incorrecto de delegados. Básicamente, se puede crear una instancia de delegado, pasarla a código no administrado y no mantener referencias en código administrado, lo que hará que el recolector de basura la elimine. Con esta opción, es posible rastrear el origen de los problemas.
no-gdb-backtrace
Esta opción deshabilitará el rastreo de pila de GDB emitido por el runtime después de un SIGSEGV o SIGABRT en código no administrado.
partial-sharing
Cuando esta opción está configurada, el runtime puede compartir código generado entre tipos genéricos, reduciendo efectivamente la cantidad de código generado.
reverse-pinvoke-exceptions
Esta opción hará que mono aborte con un mensaje descriptivo cuando, durante el desenrollado de la pila después de una excepción, llegue a un marco de pila nativo. Esto ocurre cuando se pasa un delegado administrado a código nativo y el delegado administrado lanza una excepción. Mono normalmente intentará desenrollar la pila hasta el primer manejador de excepciones (administrado) y omitirá los marcos de pila nativos en el proceso. Esto conduce a un comportamiento indefinido (ya que mono no sabe cómo procesar marcos nativos), fugas y posiblemente fallos también.
single-imm-size
Esto garantiza que cada vez que se compila código administrado, se utilizan las mismas instrucciones y registros, independientemente del tamaño de los valores utilizados.
soft-breakpoints
Esta opción permite usar pasos únicos y puntos de interrupción en hardware donde no podemos hacerlo con señales.
suspend-on-native-crash
Esta opción suspenderá el programa cuando ocurra un fallo nativo (SIGSEGV, SIGILL, ...). Esto es útil para depurar fallos que no ocurren bajo gdb, ya que un proceso en vivo contiene más información que un archivo core.
suspend-on-sigsegv
Igual que suspend-on-native-crash.
suspend-on-exception
Esta opción suspenderá el programa cuando ocurra una excepción.
suspend-on-unhandled
Esta opción suspenderá el programa cuando ocurra una excepción no controlada.
thread-dump-dir=DIR
Usa DIR para almacenar los volcadillos de hilos creados por SIGQUIT.
weak-memory-model
No impone el modelo de memoria CLR en plataformas con modelos de memoria débiles. Esto puede introducir fallos aleatorios en algunos casos raros, para entornos multihilo. Esto se puede usar para un aumento de rendimiento en aplicaciones de un solo hilo.
verbose-gdb
Hace que la salida de gdb en fallos nativos sea más detallada.
MONO_LOG_LEVEL
El nivel de registro, los valores posibles son `error', `critical', `warning', `message', `info' y `debug'. Consulta la sección DEBUGGING para más detalles.
MONO_LOG_MASK
Controla el dominio del runtime de Mono al que se aplicará el registro. Si se establece, la máscara de registro se cambiará al valor establecido. Los valores posibles son "asm" (cargador de ensamblados), "type", "dll" (cargador de bibliotecas nativas), "gc" (recolector de basura), "cfg" (cargador de archivos de configuración), "aot" (precompilador), "security" (por ejemplo, soporte CoreCLR de Moonlight) y "all". El valor predeterminado es "all". Cambiar el valor de la máscara te permite mostrar solo mensajes para un componente específico. Puedes usar varias máscaras separándolas con comas. Por ejemplo, para ver mensajes del archivo de configuración y del cargador de ensamblados, establece tu máscara a "asm,cfg".
MONO_LOG_DEST
Controla dónde se escriben los mensajes de registro de trazas. Si no se establece, los mensajes van a stdout. Si se establece, la cadena especifica una ruta a un archivo al que se agregarán los mensajes, o la cadena "syslog", en cuyo caso los mensajes se escribirán en el registro del sistema. En Windows, esto se simula escribiendo en un archivo llamado "mono.log". MONO_LOG_HEADER Controla si los mensajes de registro de trazas que no se dirigen a syslog tienen el id, la marca de tiempo y el pid como prefijo del mensaje de registro. Para habilitar un encabezado, esta variable de entorno debe ser simplemente no nula.
MONO_TRACE
Se utiliza para el seguimiento en tiempo de ejecución de llamadas a métodos. El formato de las opciones de traza separadas por comas es: 
[-]M:nombre del método
[-]N:espacio de nombres
[-]T:nombre de clase
[-]all
[-]program
disabled		Salida de traza desactivada al inicio.
Puedes activar/desactivar la salida de traza enviando una señal SIGUSR2 al programa.
MONO_TRACE_LISTENER
Si se establece, habilita System.Diagnostics.DefaultTraceListener, que imprimirá la salida de las clases System.Diagnostics Trace y Debug. Se puede establecer en un nombre de archivo, y en Console.Out o Console.Error para mostrar la salida en la salida estándar o en el error estándar, respectivamente. Si se establece en Console.Out o Console.Error, puedes agregar un prefijo opcional que se utilizará al escribir mensajes de esta manera: Console.Error:MiNombrePrograma. Consulta la documentación de System.Diagnostics.DefaultTraceListener para obtener más información.
MONO_WCF_TRACE
Esto facilita la funcionalidad de diagnóstico de WCF al simplemente producir todos los mensajes de registro del motor WCF en "stdout", "stderr" o cualquier archivo pa
ssed a esta variable de entorno. El formato del registro es el mismo que la salida de diagnóstico habitual.
MONO_XEXCEPTIONS
Esto lanza una excepción cuando se encuentra un error X11; por defecto se muestra un mensaje pero la ejecución continúa.
MONO_XMLSERIALIZER_DEBUG
Establezca este valor en 1 para evitar que el serializador elimine los archivos temporales que se crean para una serialización rápida; esto puede ser útil al depurar.
MONO_XSYNC
Esto se utiliza en la implementación de System.Windows.Forms al ejecutarse con el backend X11. Se utiliza para depurar problemas en Windows.Forms, ya que fuerza a que todos los comandos enviados al servidor X11 se realicen de forma síncrona. El modo de operación por defecto es asíncrono, lo que dificulta aislar la raíz de ciertos problemas.
MONO_XDEBUG
Cuando la variable de entorno MONO_XDEBUG está establecida, la información de depuración para el código JITted se emite en una biblioteca compartida, cargable en gdb. Esto permite, por ejemplo, ver nombres de marcos administrados en los backtraces de gdb.
MONO_VERBOSE_METHOD
Habilita la máxima verbosidad JIT para el método especificado. Esto es muy útil para diagnosticar problemas de compilación errónea de un método específico. Puede ser una lista de nombres de métodos separados por punto y coma para hacer coincidir. Si el nombre es simple, se aplica a cualquier método con ese nombre, de lo contrario, puede usar una descripción de método de mono (consulte la sección DESCRIPCIONES DE MÉTODOS).
MONO_JIT_DUMP_METHOD
Habilita el envío de la representación intermedia del JIT para un método especificado a la herramienta IdealGraphVisualizer.
MONO_VERBOSE_HWCAP
Si está establecido, hace que el JIT emita información sobre las características detectadas de la CPU (como SSE, CMOV, FCMOV, etc.) a la salida estándar.
MONO_CONSERVATIVE_HWCAP
Si está establecido, el JIT no realizará ninguna detección de capacidades de hardware. Esto puede ser útil para identificar la causa de los problemas del JIT. Este es el valor predeterminado cuando Mono se compila como un compilador cruzado AOT, de modo que el código generado se ejecutará en la mayoría del hardware.

VALGRIND

Si desea utilizar Valgrind, encontrará útil el archivo `mono.supp', que contiene las supresiones para la recolección de basura que activan advertencias incorrectas. Úselo de la siguiente manera:

    valgrind --suppressions=mono.supp mono ...

DTRACE

En algunas plataformas, Mono puede exponer un conjunto de sondas DTrace (también conocidas como sondas definidas estáticamente en el espacio de usuario, USDT).

Se definen en el archivo `mono.d'.
ves-init-begin, ves-init-end
Inicio y fin de la inicialización del tiempo de ejecución.
method-compile-begin, method-compile-end
Inicio y fin de la compilación de métodos. Los argumentos de la sonda son el nombre de la clase, el nombre del método y la firma, y en caso de method-compile-end, el éxito o fracaso de la compilación.
gc-begin, gc-end
Inicio y fin de la Recolección de Basura.
Para verificar la disponibilidad de las sondas, ejecute:
    dtrace -P mono'$target' -l -c mono

PERMISOS

La implementación de Ping de Mono para detectar la alcanzabilidad de la red puede crear paquetes ICMP sin necesidad de que el comando ping del sistema realice el trabajo. Si desea habilitar esto en Linux para usuarios no root, necesita otorgar permisos especiales al binario de Mono.

Como root, ejecute este comando:

   # setcap cap_net_raw=+ep /usr/bin/mono

ARCHIVOS

En Unix, los ensamblados se cargan desde el directorio lib de instalación. Si establece `prefix' en /usr, los ensamblados se ubicarán en /usr/lib. En Windows, los ensamblados se cargan desde el directorio donde residen mono y mint.

~/.mono/aot-cache
El directorio para los ensamblados de creación bajo demanda del compilador ahead-of-time.
/etc/mono/config, ~/.mono/config
Archivo de configuración del tiempo de ejecución de Mono. Consulte la página del manual mono-config(5) para obtener más información.
~/.config/.mono/certs, /usr/share/.mono/certs
Contiene almacenes de certificados de Mono para usuarios / máquina. Consulte la página del manual certmgr(1) para obtener más información sobre la gestión de almacenes de certificados y la página mozroots(1) para obtener información sobre cómo importar los certificados raíz de Mozilla en el almacén de certificados de Mono.
~/.mono/assemblies/ASSEMBLY/ASSEMBLY.config
Los archivos en este directorio permiten a un usuario personalizar la configuración para un ensamblado de sistema dado, el formato es el descrito en la página mono-config(5).
~/.config/.mono/keypairs, /usr/share/.mono/keypairs
Contiene pares de claves criptográficas de Mono para usuarios / máquina. Se puede acceder a ellos utilizando un objeto CspParameters con las clases DSACryptoServiceProvider y RSACryptoServiceProvider.
~/.config/.isolatedstorage, ~/.local/share/.isolatedstorage, /usr/share/.isolatedstorage
Contiene el almacenamiento aislado de Mono para usuarios no itinerantes, usuarios itinerantes y la máquina local. Se puede acceder al almacenamiento aislado utilizando las clases del espacio de nombres System.IO.IsolatedStorage.
<assembly>.config
El tiempo de ejecución carga la información de configuración para ensamblados individuales desde archivos adyacentes con los archivos .config, consulte la página http://www.mono-project.com/Config para más información.
Web.config, web.config
Las aplicaciones ASP.NET se configuran a través de estos archivos, la configuración se realiza por directorio. Para obtener más información sobre este tema, consulte la página http://www.mono-project.com/Config_system.web.
