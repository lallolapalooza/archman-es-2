NOMBRE

Monit - utilidad para monitorizar servicios en un sistema Unix

SINOPSIS

monit [opciones] <argumentos>

DESCRIPCIÓN

Monit es una utilidad para gestionar y monitorizar procesos, programas, archivos, directorios y sistemas de archivos en un sistema Unix. Monit realiza mantenimiento y reparaciones automáticas y puede ejecutar acciones causales significativas en situaciones de error. Por ejemplo, Monit puede iniciar un proceso si no está en ejecución, reiniciar un proceso si no responde y detener un proceso si utiliza demasiados recursos. Puede usar Monit para monitorizar archivos, directorios y sistemas de archivos en busca de cambios, como cambios en las marcas de tiempo, cambios en la suma de verificación o cambios de tamaño.

Monit se controla mediante un archivo de control fácil de configurar basado en una sintaxis de formato libre y orientada a tokens. Monit registra en syslog o en su propio archivo de registro y le notifica sobre condiciones de error a través de mensajes de alerta personalizables. Monit puede realizar varias comprobaciones de red TCP/IP, comprobaciones de protocolo y puede utilizar SSL para dichas comprobaciones. Monit proporciona una interfaz HTTP(S) y puede utilizar un navegador para acceder al programa Monit.

¿QUÉ MONITORIZAR?

Puede utilizar Monit para monitorizar procesos o programas similares que se ejecutan en localhost. Monit es particularmente útil para monitorizar procesos demonio, como los iniciados al arrancar el sistema. Por ejemplo, sendmail, sshd, apache y mysql. A diferencia de muchos otros sistemas de monitorización, Monit puede actuar si ocurre una situación de error; por ejemplo, si sendmail no está en ejecución, monit puede iniciar sendmail de nuevo automáticamente o si apache está utilizando demasiados recursos (por ejemplo, si hay un ataque DoS en curso), Monit puede detener o reiniciar apache y enviarle un mensaje de alerta. Monit también puede monitorizar características del proceso, como la cantidad de memoria o ciclos de CPU que utiliza un proceso.

También puede utilizar Monit para monitorizar archivos, directorios y sistemas de archivos en localhost. Monit puede monitorizar estos elementos en busca de cambios, como cambios en las marcas de tiempo, cambios en la suma de verificación o cambios de tamaño. Esto también es útil por razones de seguridad: puede monitorizar la suma de verificación md5 o sha1 de archivos que no deberían cambiar y recibir una alerta o realizar una acción si cambian.

Monit puede monitorizar conexiones de red a varios servidores, ya sea en localhost o en hosts remotos. Se admiten sockets TCP, UDP y de dominio Unix. Las pruebas de red se pueden realizar a nivel de protocolo; Monit tiene pruebas integradas para los principales protocolos de Internet, como HTTP, SMTP, etc. Incluso si un protocolo no es compatible, aún puede probar el servidor porque puede configurar Monit para enviar cualquier dato y probar la respuesta del servidor.

Monit se puede utilizar para probar programas o scripts en momentos específicos, de forma similar a cron, pero además, puede probar el valor de salida de un programa y realizar una acción o enviar una alerta si el valor de salida indica un error. Esto significa que puede utilizar Monit para realizar cualquier tipo de comprobación para la que pueda escribir un script.

Finalmente, Monit se puede utilizar para monitorizar recursos generales del sistema en localhost, como el uso general de CPU, Memoria y Carga del Sistema.

OPERACIÓN GENERAL

El comportamiento de Monit se controla mediante opciones de línea de comandos y un archivo de control de ejecución, monitrc, cuya sintaxis describimos en una sección posterior. Las opciones de línea de comandos anulan las declaraciones de .monitrc.

La ubicación predeterminada para monitrc es ~/.monitrc. Si este archivo no existe, Monit intentará en /etc/monitrc y en algunos otros lugares. Consulte ARCHIVOS para obtener más detalles. También puede especificar el archivo de control directamente utilizando el modificador de línea de comandos -c para monit. Por ejemplo,

$ monit -c /var/monit/monitrc

Antes de que Monit se inicie por primera vez, puede probar el archivo de control para ver si hay errores de sintaxis:

$ monit -t
$ Control file syntax OK

Si hubo un error, Monit imprimirá un mensaje de error en la consola, incluido el número de línea en el archivo de control donde se encontró el error.

Una vez que tenga un archivo de control Monit que funcione, simplemente inicie Monit desde la consola, de la siguiente manera:

$ monit

Puede cambiar algunas directivas de configuración a través de modificadores de línea de comandos, pero por simplicidad, se recomienda que las coloque en el archivo de control.

Monit se desconectará de la terminal y se ejecutará como un proceso en segundo plano, es decir, como un proceso demonio. Como demonio, Monit se ejecuta en ciclos; monitoriza servicios, luego duerme durante un período configurado, luego se despierta y comienza a monitorizar nuevamente en un bucle infinito.

Opciones

Las siguientes opciones son reconocidas por Monit. Sin embargo, se recomienda establecer las opciones (cuando sea aplicable) directamente en el archivo de control .monitrc.

-c archivo
Utilice este archivo de control

-d n
Ejecute Monit como un demonio una vez cada n segundos. O use "set
daemon" en monitrc.

-g nombre
Establezca el nombre del grupo para la acción de inicio, parada, reinicio, monitorización, desmonitorización,
estado y resumen.

-l archivo
Imprima la información del registro en este archivo. O use "set log"
en monitrc.

-p pidfile
Utilice este archivo de bloqueo en modo demonio. O use "set pidfile"
en monitrc.

-s statefile
Escriba la información de estado en este archivo. O use "set
statefile" en monitrc.

-B
Modo de línea de comandos por lotes (sin salida tabular ni colores). O
use "set terminal batch" en monitrc.

-I
No ejecute en modo de segundo plano (necesario para ejecutar desde init). O use
"set init" en monitrc.

-i
Imprima el ID único de Monit

-r
Restablezca el ID único de Monit. Úselo con precaución

-t
Realice una comprobación de sintaxis del archivo de control

-v
Modo detallado, funcione ruidosamente (salida de diagnóstico)

-vv
Modo muy detallado, igual que -v más registro de seguimiento de pila en caso de error

-H [nombre_archivo]
Imprima los hashes MD5 y SHA1 del archivo o de la entrada estándar si se omite el
nombre del archivo; Monit saldrá después

-V
Imprima el número de versión y el nivel de parche

-h
Imprima un texto de ayuda

Argumentos

Una vez que tenga Monit ejecutándose como un proceso demonio, puede llamar a Monit con uno de los siguientes argumentos. Monit se conectará entonces al demonio Monit (en el puerto TCP 127.0.0.1:2812 por defecto) y pedirá al demonio Monit que realice la acción solicitada. SALIDA DE TERMINAL

Monit utiliza secuencias de escape ANSI para colorear partes importantes de la salida de la línea de comandos, si la terminal admite colores, y caracteres de caja UTF-8 para la salida tabular.

Si desea procesar la salida de la CLI de Monit en un script, puede utilizar la opción -B o la siguiente declaración en el archivo de configuración de Monit para deshabilitar la salida tabular y los colores por completo:

SET TERMINAL BATCH

MODO DEMONIO

Use

SET DAEMON <segundos>
    [[WITH] START DELAY <segundos>]

para especificar la longitud del ciclo de sondeo de Monit y ejecutar Monit en modo demonio. Debe especificar un argumento numérico que sea un intervalo de sondeo en segundos.

En modo demonio, Monit se desconecta de la consola, se pone en segundo plano y se ejecuta continuamente, monitorizando cada servicio especificado y luego se duerme durante el intervalo de sondeo dado, se despierta y comienza a monitorizar de nuevo en un ciclo interminable.

Alternativamente, puede usar el modificador de línea de comandos "-d" para establecer el intervalo de sondeo, pero se recomienda encarecidamente establecer el intervalo de sondeo en su archivo ~/.monitrc, usando set daemon.

Monit siempre se iniciará en modo demonio. Si no utiliza esta declaración y no inicia Monit con la opción -d, Monit solo ejecutará una vez las comprobaciones de servicios y luego saldrá. Esto puede ser útil en algunas situaciones, pero Monit está diseñado principalmente para ejecutarse como un proceso demonio.

Llamar a "monit" con un demonio Monit en ejecución en segundo plano envía una señal de despertar al demonio, obligándolo a comprobar los servicios inmediatamente. Llamar a "monit" con el argumento quit terminará un proceso demonio Monit en ejecución en lugar de despertarlo.

La opción de retraso de inicio se puede utilizar para esperar (una vez) antes de que Monit comience a comprobar los servicios después del reinicio del sistema. Por defecto, Monit comenzará a comprobar los servicios inmediatamente al inicio.

SOPORTE INIT

La declaración "set init" evita que Monit se transforme en un proceso demonio. En su lugar, Monit se ejecutará como un proceso en primer plano. (Aún debe usar "set daemon" para especificar el ciclo de sondeo).

Esto es necesario para ejecutar Monit desde init. Ejecutar Monit desde init es probablemente la mejor manera de ejecutar Monit si desea asegurarse de que siempre tiene un demonio Monit en ejecución en su sistema. Otra opción es ejecutar Monit desde crontab. En cualquier caso, debe asegurarse de que el archivo de control no tenga errores de sintaxis antes de iniciar Monit desde init o crontab (use "monit -t" para comprobar).

Para configurar Monit para que se ejecute desde init, puede usar la declaración "set init" en el archivo de control de Monit o usar la opción "-I" desde la línea de comandos. Aquí tiene lo que debe añadir a "/etc/inittab":

# Ejecutar Monit en niveles de ejecución estándar
mo:2345:respawn:/usr/local/bin/monit -Ic /etc/monitrc

Después de modificar el archivo de configuración de init, puede ejecutar el siguiente comando para reexaminar /etc/inittab e iniciar Monit:

telinit q

Para sistemas sin telinit:

kill -1 1

Si Monit se utiliza para monitorizar servicios que también se inician al arrancar (por ejemplo, servicios iniciados a través de scripts rc de SYSV init o a través de inittab), en algunos casos, podría producirse una condición de carrera. Es decir, si un servicio tarda en iniciarse, Monit puede asumir que el servicio no se está ejecutando y posiblemente intentar iniciarlo y generar una alerta, cuando, de hecho, el servicio está a punto de iniciarse o ya está en su secuencia de inicio. Consulte las preguntas frecuentes para obtener una solución a este problema. La versión corta es iniciar Monit en un nivel de ejecución superior después de los procesos del sistema.

ARCHIVOS INCLUIDOS

El archivo de control de Monit, "monitrc", puede incluir archivos de configuración adicionales. Esta función ayuda a organizar la configuración en archivos separados en lugar de tener todo en un solo archivo, si le gusta este tipo de cosas. Las declaraciones de inclusión se pueden colocar en prácticamente cualquier lugar de "monitrc", aunque la convención es al final. La sintaxis es la siguiente:

INCLUDE <cadena_glob>

La cadena glob es cualquier tipo de cadena según se define en glob(7). Por lo tanto, puede hacer referencia a un solo archivo o cargar varios archivos a la vez. Si desea utilizar espacios en blanco en su cadena, la cadena glob debe estar incrustada entre comillas simples (') o dobles ("). Si la cadena glob coincide con un directorio en lugar de un archivo, se ignora silenciosamente.

Cualquier declaración de include en un archivo incluido se analiza como en el archivo de control principal.

Si la cadena glob coincide con varios resultados, los archivos se incluyen de forma no ordenada. Si necesita confiar en un orden determinado, debe evitar las globbing comodín y especificar en su lugar la ruta completa de los archivos incluidos.

Un ejemplo,

include /etc/monit.d/*.cfg

Esto cargará cualquier archivo que coincida con la cadena glob. Es decir, todos los archivos en /etc/monit.d que terminen con el prefijo .cfg.

Se admiten hasta 1024 archivos de inclusión. Si se supera este límite, Monit informará de un error.

OPCIONES SSL

Las opciones comunes de SSL/TLS se pueden establecer utilizando la siguiente declaración y se aplicarán a todas las conexiones SSL realizadas a través de Monit:

SET <SSL | TLS> [OPCIONES] {
    VERSION: <AUTO | [-]SSLV2 | [-]SSLV3 | [-]TLSV1 | [-]TLSV11 | [-]TLSV12 | [-]TLSV13>, ...
    VERIFY: <ENABLE | DISABLE>
    SELFSIGNED: <ALLOW | REJECT>
    CIPHERS: <cadena>
    PEMFILE: <ruta>
    PEMCHAIN: <ruta>
    PEMKEY: <ruta>
    CLIENTPEMFILE: <ruta>
    CACERTIFICATEFILE: <ruta>
    CACERTIFICATEPATH: <ruta>
}

VERSION establece la versión específica de SSL/TLS a usar. Por defecto, Monit usa AUTO. En modo AUTO, solo se permiten TLS 1.2 y 1.3, todos los demás protocolos se consideran obsoletos. Si desea usar el protocolo obsoleto, debe establecer explícitamente la versión. Puede excluir el protocolo usando el prefijo "-". Ejemplo de lista de exclusión:
set ssl {
version: auto -sslv2 -sslv3 -tlsv1 -tlsv11
} Ejemplo de lista de protocolos permitidos:
set ssl {
version: tlsv12 tlsv13
}

VERIFY habilita la verificación del certificado del servidor SSL. Esto verificará e informará de un error si el certificado del servidor no es de confianza, no es válido o ha caducado. Por defecto, la verificación del certificado está deshabilitada, aunque recomendamos habilitarla, de lo contrario, no hay garantía de que Monit esté hablando con el servidor con el que usted cree que está hablando.

SELFSIGNED los certificados autofirmados son rechazados por defecto. Use esta opción para permitir certificados autofirmados. Advertencia: no recomendado en producción por razones de seguridad, ya que en tal caso el cliente no puede verificar que habla con el servidor correcto y son posibles tipos de ataques como man-in-the-middle o secuestro de DNS).

CIPHERS anula las cifras SSL/TLS predeterminadas.

PEMFILE establece la ruta al archivo "base de datos" del certificado del servidor SSL en formato PEM. Esta opción solo tiene efecto para la interfaz HTTP de Monit.

Como alternativa a la configuración de PEMFILE con un archivo combinado de cadena y clave, PEMCHAIN y PEMKEY establecen la ruta a la cadena de certificados SSL respectivamente al archivo de clave privada del servidor en formato PEM. Esta opción solo tiene efecto para la interfaz HTTP de Monit.

CLIENTPEMFILE establece la ruta al archivo de base de datos de certificados de cliente SSL codificado en PEM. Si se establece, se habilita la autenticación de certificado de cliente.

CACERTIFICATEFILE establece la ruta al archivo codificado en PEM que contiene certificados de Autoridad de Certificación (CA). Monit utiliza los certificados CA predeterminados de OpenSSL si esta opción no se utiliza (openssl version -d se puede usar para obtener los certificados CA predeterminados). Muchas distribuciones vienen con SSL y certificados CA ya configurados y el uso de esta opción normalmente no es necesario.

CACERTIFICATEPATH establece la ruta al directorio que contiene certificados de Autoridad de Certificación (CA). Monit utiliza los certificados CA predeterminados de OpenSSL si esta opción no se utiliza. Muchas distribuciones vienen con SSL y certificados CA ya configurados y el uso de esta opción normalmente no es necesario.

La declaración de opciones SSL se aplicará globalmente a todas las conexiones SSL/TLS realizadas a través de Monit. Las opciones SSL también se pueden establecer en una comprobación local, en la configuración de mailserver o en la declaración de mmonit, y luego anularán o ampliarán la configuración global.

Para establecer opciones SSL globales, coloque esta declaración cerca de la parte superior de su archivo .monitrc:

set ssl options {...}

Aquí hay un ejemplo de cómo establecer opciones SSL tanto globales como locales:

# Habilitar la verificación de certificados para todas las conexiones SSL
# Los certificados autofirmados no están permitidos por defecto
set ssl options {
        verify: enable
}
# Verificar certificado (a través de la configuración global)
# Permitir certificado autofirmado para esta comprobación
check host example with address example.com
        if failed
                port 443
                protocol https
                with ssl options {selfsigned: allow}
        then alert
# No verificar el certificado de example2.com (anular configuración global)
check host example2 with address example2.com
        if failed
                port 443
                protocol https
                with ssl options {verify: disable}
        then alert

MODO FIPS

Para habilitar el modo FIPS (siempre que su biblioteca OpenSSL lo admita), agregue esta declaración al archivo de control de Monit:

SET FIPS

MONIT HTTPD

Si se especifica en el archivo de control, Monit se iniciará con soporte HTTP. Luego puede usar la CLI de Monit para iniciar y detener servicios, deshabilitar o habilitar la monitorización de servicios, así como ver el estado de cada servicio.

Si el soporte HTTP está habilitado a través de TCP en lugar de un socket Unix, también puede ver el panel informativo de Monit en su navegador web.

wser.

Tenga en cuenta que si el soporte HTTP está deshabilitado, la interfaz CLI de Monit tendrá una funcionalidad reducida, ya que la mayoría de los comandos CLI (como "monit status") necesitan comunicarse con el proceso en segundo plano de Monit a través de la interfaz HTTP. Recomendamos encarecidamente tener el soporte HTTP habilitado. Si la seguridad es una preocupación, vincule la interfaz HTTP solo al host local o use un Socket Unix para que Monit no sea accesible desde el exterior.

SOCKET UNIX

Sintaxis para Socket Unix:

SET HTTPD UNIXSOCKET <ruta>
    [UID <uid | nombre de usuario>]
    [GID <gid | nombre de grupo>]
    [PERMISO <número octal>]
    ALLOW <usuario:contraseña>+

Ejemplo:

set httpd unixsocket /var/run/monit.sock
    allow nombredeusuario:contraseña

UNIXSOCKET establece la ruta al Socket Unix al que Monit debe vincularse y escuchar.

UID Propietario del socket (opcional, por defecto es el usuario que ejecuta Monit)

GID Grupo del socket (opcional, por defecto es el grupo primario del usuario que ejecuta Monit)

PERMISSION Permisos del socket - modo octal absoluto (opcional, la UMASK del proceso se aplica por defecto)

PUERTO TCP

Sintaxis para puerto TCP:

SET HTTPD PORT <número>
    [ADDRESS <nombre de host | dirección IP>]
    [[with] SSL {pemfile: <ruta>}]
    ALLOW <usuario:contraseña | dirección IP | rango IP>+

PORT establece el puerto al que Monit debe vincularse y escuchar. Monit suele configurarse en el puerto 2812. Ejemplo:

set httpd port 2812
    allow nombredeusuario:contraseña

Ahora puede usar http://localhost:2812/ para acceder a la interfaz web de Monit desde un navegador, después de haber introducido el nombre de usuario y la contraseña como credenciales. Es posible que necesite usar comillas dobles alrededor de la contraseña si contiene caracteres especiales como "p@ssw:r#".

ADDRESS hace que Monit escuche solo en una interfaz específica. Por ejemplo, si *no* desea exponer la interfaz web de Monit a la red, vincúlela solo a localhost. Monit aceptará conexiones en cualquier dirección si no se usa la opción ADDRESS:

set httpd
    port 2812
    use address 127.0.0.1
    allow nombredeusuario:contraseña

Monit HTTP sobre TCP admite tanto la versión IP 4 como la 6. El soporte es transparente y no requiere ninguna configuración especial. Si la dirección de vinculación *no* se especifica como en este ejemplo:

set httpd
  port 2812
  allow ...

Monit se vinculará y escuchará en el puerto 2812 en todas las interfaces, tanto IPv4 como IPv6 si están disponibles. Para forzar que Monit HTTP solo escuche y acepte conexiones a través de IP versión 6, especifique una dirección IPv6:

set httpd
  port 2812
  use address "fe80::222:19ff:fe53:6c59"
  allow ...

De manera similar, para forzar que Monit HTTP solo escuche y acepte conexiones a través de IP versión 4, especifique una dirección IPv4:

set httpd
  port 2812
  use address 62.109.39.247
  allow ...

Configuración SSL

SSL habilita SSL/TLS para la interfaz web de Monit. Vea las opciones para la lista completa de opciones SSL.

PEMFILE establece la ruta al archivo codificado en PEM, que contiene la clave privada y el certificado del servidor. Este archivo debe almacenarse en un lugar seguro en el sistema de archivos y debe tener permisos estrictos, no más de 0700.

Alternativamente, PEMCHAIN y PEMKEY establecen la ruta a archivos separados de cadena de certificados codificados en PEM y clave privada. El archivo de clave debe almacenarse en un lugar seguro en el sistema de archivos y debe tener permisos estrictos, no más de 0700.

Ejemplo de uso de pemfile:

set httpd
    port 2812
    with ssl {
       pemfile: /etc/ssl/certs/monit.pem
    }
    allow usuario:contraseña

Ejemplo de uso de cadena de certificados y clave separadas:

set httpd
    port 2812
    with ssl {
       pemchain: /etc/ssl/certs/monit.chain.pem
       pemkey: /etc/ssl/certs/monit.key.pem
    }
    allow usuario:contraseña

Ahora puede usar https://localhost:2812/ para acceder al servidor web Monit a través de una conexión cifrada TLS.

Nota sobre certificados de servidor autofirmados: La CLI de Monit funciona en una base cliente-servidor y utiliza la GUI HTTP de Monit para recopilar el estado del demonio de Monit y pasarle comandos como iniciar/detener. Como los certificados autofirmados se rechazan por defecto por motivos de seguridad, la CLI no funcionará a menos que lo permita explícitamente usando la opción SELFSIGNED: ALLOW:

set httpd
   port 2812
   with ssl {
      pemfile: /etc/ssl/certs/monit.pem
      selfsigned: allow
   }
   allow usuario:contraseña

CLIENTPEMFILE habilita una autenticación basada en certificados de cliente y establece la ruta a un archivo de base de datos codificado en PEM, que contiene una lista de certificados de cliente permitidos. Un cliente que se conecta debe proporcionar un certificado conocido por Monit (listado en clientpemfile), de lo contrario, se rechaza. Este archivo también debe incluir todos los certificados CA necesarios. Por defecto, los certificados de cliente autofirmados se rechazan por motivos de seguridad; si desea permitir certificados de cliente autofirmados (recomendado solo para pruebas), debe permitirlos explícitamente usando la opción SELFSIGNED: ALLOW (vea el ejemplo anterior). Consulte la documentación de su navegador sobre cómo importar certificados de cliente.

Ejemplo:

set httpd
    port 2812
    with SSL {
        pemfile:       /etc/ssl/certs/monit.pem
        clientpemfile: /etc/ssl/certs/monit-client.pem
    }

Firma de la versión de Monit

SIGNATURE se puede usar para ocultar la versión de Monit de la cabecera de respuesta HTTP y de las páginas de error. Por ejemplo:

set httpd
  port 2812
  signature disable
  allow usuario:contraseña

Autenticación

El acceso a la interfaz web de Monit se controla principalmente a través de la opción ALLOW, que se utiliza para especificar la autenticación y autorizar solo a clientes específicos para que se conecten.

Si se está utilizando la interfaz de línea de comandos de Monit, es necesario al menos una contraseña en texto plano (ver más abajo), de lo contrario, la interfaz de línea de comandos de Monit no podrá conectarse a la interfaz web de Monit.

Los clientes que intentan conectarse a Monit, pero envían un nombre de usuario y/o contraseña incorrectos, se registran con su dirección IP.

Certificados de cliente

Este método de autenticación es un mecanismo de autenticación seguro y emplea certificados de cliente HTTPS para verificar la autenticidad de un cliente que se conecta. Los clientes deben poseer un Certificado de Clave Pública conocido por Monit. El cliente debe conectarse a Monit a través de SSL y Monit le pedirá al cliente que envíe su certificado. Al recibir el certificado, Monit lo compara con los certificados ubicados en el archivo CLIENTPEMFILE. Se concede acceso si el certificado del cliente está en este archivo. Consulte la configuración SSL para obtener más detalles.

Autenticación Básica

Monit admite la Autenticación Básica según se describe en la RFC 2617.

En resumen; un servidor desafía a un cliente (por ejemplo, un Navegador) a enviar información de autenticación (nombre de usuario y contraseña) y si se acepta, el servidor permitirá al cliente acceder al documento solicitado.

La mayor debilidad de la Autenticación Básica es que el nombre de usuario y la contraseña se envían en texto plano a través de la red (es decir, codificados en base64). Por lo tanto, se recomienda no utilizar este método de autenticación a menos que ejecute Monit con soporte ssl. Con ssl, es seguro usar la Autenticación Básica ya que *todos* los datos HTTP, incluidas las cabeceras de Autenticación Básica, se cifrarán.

Usuario y contraseña en texto plano

Monit utilizará la Autenticación Básica si una declaración allow contiene un nombre de usuario y una contraseña separados por un solo carácter de dos puntos (:).

Nota: Se pueden usar caracteres especiales, pero para los no alfanuméricos la contraseña debe ir entre comillas.

Sintaxis:

ALLOW <nombre de usuario>:<contraseña>

Lista de hosts y redes permitidos

Monit mantiene una lista de control de acceso de hosts y redes permitidos para conectarse. Puede agregar tantos hosts como desee, pero solo se permiten hosts con un nombre de dominio válido o su dirección IP.

Monit consultará un servidor de nombres para verificar cualquier host que intente conectarse. Si un host (cliente) intenta conectarse, pero no se encuentra en la lista de acceso o no se puede resolver, Monit cerrará la conexión con el cliente de inmediato.

Ejemplo de archivo de control:

set httpd port 2812
    allow localhost
    allow mi.otra.maquina.de.trabajo.com
    allow 10.1.1.1
    allow 192.168.1.0/255.255.255.0
    allow 10.0.0.0/8

A los clientes, que no se mencionan en la lista de permitidos e intentan conectarse a Monit, se les denegará el acceso y se registrarán con su dirección IP.

PAM

PAM es compatible en plataformas que proporcionan PAM (como Linux, macOS, FreeBSD, NetBSD).

Sintaxis:

ALLOW @<grupo>

donde "grupo" es el nombre del grupo al que se le permite acceder a la interfaz web de Monit. Monit utiliza un servicio PAM llamado monit para la autenticación PAM; consulte la página del manual de PAM para obtener instrucciones detalladas sobre cómo configurar el servicio PAM y los complementos de autenticación PAM.

Servicio PAM de ejemplo para Monit en macOS (guardar como archivo "/etc/pam.d/monit"):

# monit: auth account password session
#auth       sufficient     pam_securityserver.so
#auth       sufficient     pam_unix.so
auth       sufficient     pam_opendirectory.so
auth       required       pam_deny.so
account    required       pam_permit.so
password   required       pam_deny.so
session    required       pam_permit.so

Y un servicio PAM similar para Monit en Linux (guardar como archivo "/etc/pam.d/monit"):

# monit: auth account password session
auth       sufficient   pam_unix2.so
auth       required     pam_deny.so
account    required     pam_permit.so
password   required     pam_deny.so
session    required     pam_permit.so

Una configuración "monitrc" que solo permite que el grupo "admin" y "staff" autenticados a través de PAM accedan a la interfaz web:

set httpd
    port 2812
    allow @admin
    allow @staff readonly

Archivo htpasswd

Alternativamente, puede almacenar credenciales en un archivo con formato "htpasswd" (una entrada usuario:contraseña por línea), así: allow [cleartext|crypt|md5] /ruta [usuarios]. El valor por defecto son contraseñas en texto plano. En caso de que las contraseñas estén cifradas, es necesario especificar el método criptográfico. Si no desea que todos los usuarios del archivo de contraseñas tengan acceso a Monit, puede especificar solo los usuarios que deberían tener acceso en la declaración allow. De lo contrario, se agregan todos los usuarios.

Ejemplo1:

HTTPD

Monit includes a small HTTP server that can be used to monitor your system status via your web browser and to control services. The HTTP server is disabled by default and must be explicitly enabled by the "set httpd" configuration directive.

Enabling the HTTP server

To enable the Monit HTTP server, you must specify a port number on which Monit should listen. Use the "port" parameter for this.

set httpd port 2812

This will enable the Monit HTTP server and make it listen on port 2812. It is possible to specify an IP address as well, to bind the server to a specific network interface.

set httpd host.example.com port 2812
set httpd 127.0.0.1 port 2812

You can also configure the Monit HTTP server to use SSL, to protect sensitive information. Use the "sslenabled" parameter, and specify the paths to your SSL certificate and key files.

set httpd port 2812
    ssl=yes
    cert=/etc/monit/certs/monit.pem
    key=/etc/monit/certs/monit.key

To enable HTTPS, Monit must be compiled with OpenSSL support. Check the output of monit -V to verify this.

Additional options include:

  • allow user:password:

    Allow access to the Monit HTTPD server using username and password authentication. The password can also be specified as an MD5 hash.

  • allow /path/to/htpasswd:

    Allow access to the Monit HTTPD server using Apache compatible password files.

  • allow host:

    Allow access from the specified host. Wildcards can be used in hostnames, e.g. allow *.example.com.

  • allow ip/netmask:

    Allow access from the specified network.

  • allow @group:

    Allow access for all users in the specified group.

  • deny host:

    Deny access from the specified host.

  • deny ip/netmask:

    Deny access from the specified network.

  • max-connections number:

    Limit the number of simultaneous HTTP connections.

  • signature:

    Enable or disable the Monit HTTP server signature.

Authentication

Monit's HTTP server supports Basic Authentication. It can be configured to use either a plain text password or an MD5-hashed password. You can also use Apache compatible password files.

set httpd port 2812
    allow john:password

To use an MD5 password, you need to generate it first. For example, using Perl:

perl -e 'print crypt("password", "salt") . "\n"'

This will print a salted hash of the password. You can then use this hash in your Monit configuration:

set httpd port 2812
    allow john:$1$salt$h30fC7y0Qe7F.j1x3QyB1/

Alternatively, you can use Apache's htpasswd utility to create a password file:

htpasswd -cm /etc/httpd/htpasswd john
htpasswd -m /etc/httpd/htpasswd paul

And then reference this file in your Monit configuration:

set httpd port 2812
    allow /etc/httpd/htpasswd john paul ringo george

If you use this method together with a host list, then only clients from the listed hosts will be allowed to connect to the Monit HTTP server and each client will be asked to provide a username and a password.

Example2:

set httpd port 2812
    allow localhost
    allow 10.1.1.1
    allow hauk:"passw@rd"

If you only want to use Basic Authentication, then just provide allow entries with username and password or password files as in example 1 above.

Read-only users

Further it is possible to define some users as read-only. A read-only user can read the Monit web pages but will not get access to push-buttons and cannot change a service from the web interface.

set httpd port 2812
    allow admin:password
    allow hauk:password read-only
    allow @admins
    allow @users read-only

A user is set to read-only by using the read-only keyword after username:password. In the above example the user hauk is defined as a read-only user, while the admin user has all access rights.

Read-only http server

Finally is is possible to restrict the entire web interface as read-only. All users, regardless if defined with or without the read-only keyword, have only the permissions described above. When using this setting it is recommend to set up a UNIXSOCKET as well, otherwise the monit CLI will not work.

set httpd
    port 2812
        read-only
    unixsocket /run/monit.socket
    allow @users

ALERT MESSAGES

Monit will raise an alert in the following situations:

o A service does not exist (e.g. process is not running)
o Cannot read service data (e.g. cannot get filesystem usage)
o Execution of a service related script failed (e.g. start failed)
o Invalid service type (e.g. if path points to directory instead of file)
o Custom test script returned error
o Ping test failed
o TCP/UDP connection and/or port test failed
o Resource usage test failed (e.g. cpu usage too high)
o Checksum mismatch or change (e.g. file changed)
o File size test failed (e.g. file too large)
o Timestamp test failed (e.g. file is older then expected)
o Permission test failed (e.g. file mode doesn't match)
o An UID test failed (e.g. file owned by different user)
o A GID test failed (e.g. file owned by different group)
o A process's PID changed out of Monit's control
o A process's PPID changed out of Monit control
o Too many service recovery attempts failed
o A file content test found a match
o Filesystem flags changed
o A service action was performed by administrator
o A network link down or up
o A network link capacity changed
o A network link saturation failed
o A network link upload/download rate failed
o Monit was started, stopped or reloaded

To get an alert via e-mail, set the alert target using the global "set alert" statement (for all services) or the "alert" statement in the context of a service entry (for a single service).

Setting an alert recipient

If an event occurs, Monit will send an alert. There are two kinds of alert statement: global and local.

Global syntax:

SET ALERT mail-address [[NOT] {event, ...}] [REMINDER cycles]

Example:

set alert foo@bar

will send a default email to the address foo@bar whenever any event occurs on any service.

If you want to send alert messages to more email addresses, add a "set alert 'email'" statement for each address.

It is also possible to use the local alert statement in the context of a service check to enable alert for the given service only:

ALERT mail-address [[NOT] {event, ...}] [REMINDER cycles]

Local alert example:

check host myhost with address 1.2.3.4
    if failed port 3306 protocol mysql then alert
    if failed port 80 protocol http then alert
    alert foo@baz # Local service alert

You can combine global and local alert statements. If there is a conflict, the local alert has precedence and overrides the global statement.

Setting an event filter

If you only want an alert message sent for certain events, list them in an "{event, ...}" block, e.g.:

set alert foo@bar only on { timeout, nonexist }

The event list can also be negated to send alerts for all events except those which are listed, by prepending the list with the word "not". For example, to receive all alerts except notification about Monit program start and stop:

set alert foo@bar but not on { instance }

Setting an error reminder

Monit by default sends just one notification if a service failed and another when/if it recovers. If you want to be notified that the service is still in a failed state, you can use the reminder option in the alert statement:

SET ALERT mail-address [WITH] REMINDER [ON] number [CYCLES]

For example if you want to be notified each tenth cycle if a service remains in a failed state, you can use:

alert foo@bar with reminder on 10 cycles

Likewise if you want to be notified on each failed cycle, you can use:

alert foo@bar with reminder on 1 cycle

Disabling alerts for some service

To suppress alerts for some user and service, add the "noalert" statement in the context of a service check.

NOALERT mail-address

Example (send all alerts to foo@bar except for service p3):

set alert foo@bar
check process p1 with pidfile /var/run/p1.pid
check process p2 with pidfile /var/run/p2.pid
check process p3 with pidfile /var/run/p3.pid
    noalert foo@bar

SET MAIL-FORMAT {mail-format}

set mail-format {
     from: Monit Support <monit@foo.bar>
 reply-to: support@domain.com
  subject: $SERVICE $EVENT at $DATE
  message: Monit $ACTION $SERVICE at $DATE on $HOST: $DESCRIPTION.
           Yours sincerely,
           monit
}

The subject: option sets the message subject and must be on only one line.

You need not use all options, only the option which you want to override. For example to globally change the sender address only:

set mail-format { from: bofh@foo.bar }

LÍMITE DE REINICIO DEL SERVICIO

Monit proporciona un mecanismo de límite de reinicio para situaciones en las que un servicio simplemente se niega a iniciarse o responder durante un período prolongado.

El mecanismo de límite de reinicio se basa en el número de reinicios del servicio y el número de ciclos de sondeo. Por ejemplo, si un servicio tuvo x reinicios dentro de y ciclos de sondeo (donde x <= y), Monit realizará una acción (por ejemplo, dejar de monitorear el servicio). Si ocurre un tiempo de espera, Monit enviará un mensaje de alerta si ha registrado interés para este evento.

La sintaxis para la declaración de tiempo de espera es la siguiente (las palabras clave están en mayúsculas):

IF <número> RESTART <número> CYCLE(S) THEN <acción>

El valor acción es una de las acciones comunes o TIMEOUT (para compatibilidad con versiones anteriores, equivale a la acción UNMONITOR).

Aquí hay un ejemplo donde Monit dejará de monitorear el servicio si se reinició 2 veces dentro de 3 ciclos:

if 2 restarts within 3 cycles then unmonitor

Para que Monit verifique el servicio nuevamente después de que se deshabilitó el monitoreo, ejecute "monit monitor servicename" desde la línea de comandos.

Ejemplo para establecer una ejecución personalizada en caso de tiempo de espera:

if 5 restarts within 5 cycles then exec "/foo/bar"

Ejemplo para detener el servicio:

if 7 restarts within 10 cycles then stop

DEPENDENCIAS DEL SERVICIO

Si se especifica en el archivo de control, Monit puede realizar comprobaciones de dependencias antes de iniciar, detener, monitorear o dejar de monitorear servicios. La declaración de dependencia puede usarse dentro de cualquier entrada de servicio en el archivo de control de Monit.

La sintaxis para la declaración depend es simplemente:

DEPENDS on servicio[, servicio [,...]]

Donde servicio es un nombre de entrada de servicio de verificación utilizado en su archivo ".monitrc", por ejemplo apache o datafs.

Puede agregar más de un nombre de servicio de cualquier tipo o usar más de una declaración depend en una entrada.

Los servicios especificados en una declaración depend se verificarán durante las operaciones de detención/inicio/monitoreo/dejar de monitorear.

Si un servicio se detiene o deja de ser monitoreado, detendrá/dejará de monitorear cualquier servicio que dependa de sí mismo.

Si el servicio se inicia, todos los servicios de los que este servicio depende se iniciarán antes de iniciar este servicio. Si el inicio de algún servicio falló, el servicio con prerrequisitos NO se iniciará, pero recordará que debe iniciarse y lo intentará en el próximo ciclo.

Si se reinicia un servicio, primero detendrá todos los servicios activos que dependan de él y, después de iniciarse, iniciará nuevamente todos los servicios dependientes que estaban activos antes del reinicio.

Aquí hay un ejemplo donde configuramos una entrada de servicio apache para que dependa del binario apache subyacente. Si el binario cambia, se envía una alerta y apache ya no es monitoreado. La razón es la seguridad y que Monit no debe ejecutar un binario apache posiblemente pirateado.

(1) check process apache with pidfile "/var/run/httpd.pid"
(2)    depends on httpd
(3)    ...
(4)
(5) check file httpd with path /usr/bin/httpd
(6)    if failed checksum then stop

La primera entrada es la entrada del proceso para apache. La segunda línea establece una dependencia entre esta entrada y la entrada del servicio llamada httpd en la línea 5. Un árbol de dependencias funciona de la siguiente manera, si se realiza una acción en una rama inferior, se propagará hacia arriba en el árbol y para cada entrada dependiente ejecutará la misma acción. En este caso, si la suma de verificación falla en la línea 6, se ejecuta una acción de detención y el binario de apache ya no se verifica. Pero como la entrada del proceso apache depende de la entrada httpd, esta entrada también ejecutará la acción de detención. En resumen, si la prueba de suma de verificación para el archivo binario httpd falla, se detienen tanto la entrada check file httpd como la entrada check process apache.

Un árbol de dependencias es una construcción general y puede usarse entre todo tipos de entradas de servicio y abarcar muchos niveles y propagar cualquier acción soportada (excepto la acción exec que no se propagará hacia arriba en un árbol de dependencias por razones obvias).

Aquí hay otro ejemplo diferente. Considere la siguiente configuración común de servidor:

WEB-SERVER -> APPLICATION-SERVER -> DATABASE -> FILESYSTEM
    (a)               (b)             (c)          (d)

Puede configurar dependencias para que el servidor web dependa de que el servidor de aplicaciones se ejecute antes de que se inicie el servidor web, y que el servidor de aplicaciones dependa del servidor de base de datos, y la base de datos dependa del sistema de archivos montado antes de iniciarse. Consulte también la sección de ejemplos a continuación para ver ejemplos que utilizan la declaración depend.

Aquí describimos cómo funcionará Monit con las dependencias anteriores:

Si ningún servicio está en ejecución
Monit iniciará los servidores en el siguiente orden: d, c, b, a
Si todos los servidores están en ejecución
Cuando ejecute 'monit stop all', este es el orden de detención: a, b, c, d. Si ejecuta 'Monit stop d', entonces a, b y c también se detienen porque dependen de d y finalmente d se detiene.
Si a no está en ejecución
Monit iniciará a
Si b no está en ejecución
Monit primero detendrá a, luego iniciará b y finalmente iniciará a si b vuelve a estar en funcionamiento.
Si c no está en ejecución
Monit primero detendrá a y b, luego iniciará c y finalmente iniciará b y luego a.
Si d no está en ejecución
Monit primero detendrá a, b y c, luego iniciará d y finalmente iniciará c, b y luego a.
Si el archivo de control contiene un bucle de dependencias.
Un bucle de dependencias es, por ejemplo; a->b y b->a o a->b->c->a.

Cuando Monit se inicia, comprobará si existen dichos bucles y se quejará y saldrá si se encuentra un bucle. También saldrá con una queja si se utilizó una declaración depend que no apunta a un servicio en el archivo de control.

SINTAXIS GENERAL

Monit ofrece varias pruebas 'if' que puede utilizar en una declaración 'check' para probar diversos aspectos de un servicio.

Puede probar tanto un valor predefinido como un rango y tomar acciones si el valor cambia.

Sintaxis general para probar un valor específico o un rango:

IF <prueba> THEN <acción> [ELSE <acción>]

La acción se evalúa cada vez que la condición <PRUEBA> es verdadera. La acción de éxito es opcional y se ejecuta solo cuando el estado cambia de fallo a éxito. Si la acción de éxito no está configurada, Monit enviará una alerta de recuperación por defecto.

Sintaxis general para una prueba de cambio de valor:

IF CHANGED <prueba> THEN <acción>

La acción se ejecuta cada vez que el valor cambia. Monit recordará el nuevo valor y disparará un evento si el valor cambia nuevamente.

ACCIÓN

Cada prueba puede tener métodos asociados de alerta, inicio, detención, reinicio, dejar de monitorear o ejecutar que Monit puede usar para ejecutar acciones o programas en el servicio. La acción de éxito también soporta el método ignorar.

Sintaxis:

ALERT | IGNORE | START | STOP | R

ACCIONES

Puede seleccionar una de las siguientes acciones para cada prueba:

ALERT
RESTART
START
STOP
EXEC "programa" [[AS] UID <número | cadena>] [[AS] GID <número | cadena>] [[WITH] TIMEOUT <número> SEGUNDO(S)] [REPEAT EVERY [<número>] CICLO(S)]
UNMONITOR

En cada prueba, debe seleccionar la acción a ejecutar de esta lista:

  • ALERT envía al usuario un evento de alerta en cada cambio de estado.
  • RESTART reinicia el servicio y envía una alerta. El reinicio se realiza llamando al método de reinicio registrado del servicio o llamando primero al método de parada seguido del método de inicio si el reinicio no está configurado.
  • START inicia el servicio llamando al método de inicio registrado del servicio y envía una alerta.
  • STOP detiene el servicio llamando al método de parada registrado del servicio y envía una alerta. Si Monit detiene un servicio, Monit ya no lo verificará ni lo reiniciará más tarde. Para reactivar el monitoreo del servicio, debe habilitar explícitamente el monitoreo desde la interfaz web o desde la consola.
  • EXEC se puede usar para ejecutar un programa arbitrario y enviar una alerta. Si elige esta acción, debe indicar el programa a ejecutar y, si el programa requiere argumentos, debe encerrar el programa y sus argumentos en una cadena entre comillas. Opcionalmente, puede especificar el uid y gid a los que debe cambiar el programa ejecutado al iniciarse. El programa se ejecuta solo una vez si la prueba falla. Puede habilitar la repetición de ejecución si el error persiste durante un número dado de ciclos. Por ejemplo: 
    if failed <prueba> then exec "/usr/local/bin/sms.sh"
     as uid "nobody" and gid "nobody"
     repeat every 5 cycles

    Recuerde, si Monit se ejecuta como root, todos los programas ejecutados por Monit se iniciarán con privilegios de superusuario a menos que se utilice la extensión uid y gid.

  • UNMONITOR deshabilitará el monitoreo del servicio y enviará una alerta. El servicio ya no será verificado por Monit ni reiniciado más tarde. Para reactivar el monitoreo del servicio, debe habilitar explícitamente el monitoreo desde la interfaz web o desde la consola.
  • IGNORE se puede usar en la acción para no generar una alerta una vez que la verificación vuelve al estado anterior.

TOLERANCIA A FALLOS

Por defecto, se ejecuta una acción si coincide y el servicio correspondiente se establece en un estado de error. Sin embargo, puede requerir que una prueba falle más de una vez antes de que se active el evento de error y el estado del servicio cambie a fallido. Esto es útil para evitar recibir alertas sobre errores transitorios, que pueden ocurrir, especialmente con pruebas de red.

Sintaxis:

FOR <X> CICLOS ...

o:

<X> [VECES DENTRO] <Y> CICLOS ...

La condición puede usarse tanto para acciones de falla como de éxito.

El primer formato, más simple y recomendado, requiere "X" eventos consecutivos antes de cambiar el estado:

if failed
   port 80
   for 3 cycles
then alert

El segundo formato es más avanzado y permite tolerar problemas intermitentes, pero aún así detectar problemas excesivos, donde el servicio oscila frecuentemente entre estados de error y éxito.

Por ejemplo, si falla cada segundo ciclo (1-0-1-0-1-0-...), la condición "for 2 cycles" nunca coincidirá, a pesar de que el servicio tenga problemas. La siguiente declaración capturará dicho estado:

if failed
   port 80
   for 3 times within 5 cycles
then alert

Ejemplo que establece múltiples niveles de error y acciones:

check filesystem rootfs with path /dev/hda1
 if space usage > 80% for 5 times within 15 cycles then alert
 if space usage > 90% for 5 cycles then exec '/try/to/free/the/space'

Nota: el valor máximo para ciclos es 64.

PRUEBAS DE EXISTENCIA

Esta prueba permite activar una acción basada en la existencia del objeto monitoreado. Es compatible con servicios de tipo proceso, archivo, directorio, sistema de archivos y fifo.

Si no se define ninguna prueba de existencia, se activa la prueba implícita de no existencia con acción de reinicio, por lo que, por ejemplo, si el proceso se detiene, Monit lo reiniciará.

Hay dos tipos de pruebas de existencia:

NO EXISTE

Esta prueba activará una acción si el objeto no existe. Se puede utilizar, por ejemplo, para asegurarse de que Apache esté en ejecución, de que el sistema de archivos de datos esté montado, etc.

IF [DOES] NOT EXIST THEN <acción>

acción es una opción entre "ALERT", "RESTART", "START", "STOP", "EXEC" o "UNMONITOR".

Ejemplo: Ejecutar un script si un sistema de archivos NO existe:

check filesystem disk1 with path /dev/sda1
     if does not exist then exec "/sbin/mount..."

EXISTE

Esta prueba es la inversa de la prueba de no existencia: activará una acción si el objeto EXISTE. Se puede utilizar, por ejemplo, para matar un proceso que no debería estar en ejecución.

IF [DOES] EXIST THEN <acción>

acción es una opción entre "ALERT", "RESTART", "START", "STOP", "EXEC" o "UNMONITOR".

Ejemplo: Matar un proceso que no debería ejecutarse:

check process vmware matching "vmware"
      if exist then exec "/usr/bin/pkill -9 vmware"

Ejemplo: Alerta si existe un archivo que no debería:

check file x with path /some/path/x
      if exist then alert

PRUEBAS DE RECURSOS

Monit puede examinar cuántos recursos está utilizando un servicio. Esta prueba solo se puede utilizar dentro de una entrada de servicio de sistema o proceso en el archivo de control de Monit.

Dependiendo de las características del sistema o del proceso, los servicios se pueden detener o reiniciar y se pueden generar alertas. Por lo tanto, es posible utilizar sistemas que están inactivos y preservar el sistema bajo carga alta.

Sintaxis:

IF <recurso> <operador> <valor> THEN <acción>

operador es una opción entre "<", ">", "!=", "==" en notación C, "gt", "lt", "eq", "ne" en notación shell sh y "greater", "less", "equal", "notequal" en forma legible para humanos (si no se especifica, el valor predeterminado es EQUAL).

valor es un entero o un número real.

acción es una opción entre "ALERT", "RESTART", "START", "STOP", "EXEC" o "UNMONITOR".

recurso depende del tipo de servicio:

Pruebas de recursos del sistema

LOADAVG([1min|5min|15min]) [PER CORE] se refiere a la carga promedio del sistema. La carga promedio es el número de procesos en la cola de ejecución del sistema por núcleo de CPU, promediado durante el período de tiempo especificado. Ejemplo:

if loadavg (1min) per core > 2 for 15 cycles then alert
if loadavg (5min) per core > 1.5 for 10 cycles then alert
if loadavg (15min) per core > 1 for 8 cycles then alert

Si omite la opción per core, la prueba verificará la carga promedio total independientemente del número de núcleos de CPU.

CPU([user|system|wait|nice|hardirq|softirq|steal|guest|guestnice]) es el porcentaje de tiempo que el sistema dedica al tipo de tarea indicado:

user
La CPU está ejecutando código en modo de espacio de usuario, lo que incluye cualquier proceso que no pertenezca al kernel, como servidores web, bases de datos, shells y programas relacionados con el escritorio.
system
La CPU está ejecutando el kernel, lo que incluye controladores y otros módulos del kernel. El kernel también maneja solicitudes de procesos de espacio de usuario como asignación de memoria, E/S de disco y red, y creación de procesos hijos.
wait
La espera de E/S ocurre cuando la CPU estaba inactiva mientras esperaba que una operación de E/S de disco o red se completara.
nice
Las estadísticas "nice" contabilizan los procesos en espacio de usuario que se ejecutan con prioridad alterada (más alta o más baja de lo normal).
hardirq
El kernel está atendiendo solicitudes de interrupción de hardware. Las interrupciones de hardware provienen de periféricos como el teclado, las interfaces de red, los discos, el reloj del sistema, etc.
softirq
El kernel está atendiendo solicitudes de interrupción de software. Las interrupciones de software provienen de procesos que se ejecutan en el sistema.
steal
Esto se aplica solo a máquinas virtuales en un hipervisor. El tiempo de robo muestra el porcentaje de tiempo que una máquina virtual tuvo que esperar la CPU real mientras el hipervisor estaba atendiendo a otra máquina virtual. Si este número sigue siendo alto, el sistema anfitrión está demasiado ocupado y puede necesitar más CPU físicas o descargar algunas máquinas virtuales a otro host.
guest
Esto se aplica solo a las máquinas anfitrionas que ejecutan un hipervisor. Muestra el tiempo dedicado a ejecutar una CPU virtual para sistemas operativos invitados bajo el control del kernel de Linux. Este valor ya está incluido en las estadísticas de "user".
guestnice
Esto se aplica solo a las máquinas anfitrionas que ejecutan un hipervisor. Muestra el tiempo dedicado a ejecutar una CPU virtual para sistemas operativos invitados bajo el control del kernel de Linux, con prioridad alterada. Este valor ya está incluido en las estadísticas de "nice".

Si tiene 2 hilos, se informa un 100% de uso de CPU cuando utiliza 2 núcleos de CPU al 100%, etc. Si el proceso tiene más hilos que los núcleos de CPU disponibles en la máquina, entonces el 100% de uso de CPU corresponde a la utilización de todos los núcleos de CPU disponibles. Ejemplo:

si cpu > 10% durante 5 ciclos entonces reinicia

CPU TOTAL es el uso total de CPU del proceso y sus hijos en (porcentaje). Querrás usar CPU TOTAL típicamente para servicios como el servidor web Apache, donde un proceso maestro genera procesos hijos como trabajadores. Ejemplo:

HILOS es el número de hilos del proceso. Ejemplo:

si hilos > 3 entonces alerta

HIJOS es el número de procesos hijos del proceso. Ejemplo:

si hijos > 10 entonces alerta

MEMORIA es el uso de memoria del propio proceso, [%] o valor absoluto [B, kB, MB, GB]. Ejemplo:

si uso memoria > 8 MB entonces alerta

MEMORIA TOTAL es el uso de memoria del proceso y sus procesos hijos, ya sea en porcentaje o como una cantidad [B, kB, MB, GB]. Ejemplo:

si uso memoria total > 1% durante 10 ciclos entonces alerta

PRUEBA DE CHECKSUM DE ARCHIVO

La declaración checksum solo puede usarse en una entrada de servicio de archivo y puede usarse para verificar el checksum MD5 o SHA1 del archivo.

Verificar checksum específico:

SI FALLÓ [MD5|SHA1] CHECKSUM [ESPERAR checksum] ENTONCES acción

Verificar cualquier cambio en el archivo:

SI CAMBIÓ [MD5|SHA1] CHECKSUM ENTONCES acción

La elección de MD5 o SHA1 es opcional. MD5 presenta un checksum de 128 bits (cadena codificada en hexadecimal de 32 bytes) y SHA1 un checksum de 160 bits (cadena codificada en hexadecimal de 40 bytes). Si se omite esta opción, Monit intentará adivinar el método a partir de la cadena EXPECT o usará MD5 como checksum predeterminado.

"expect" es opcional y si se usa, especifica la cadena md5 o sha1 que Monit debería esperar al probar el checksum de un archivo. Monit entonces no calculará un checksum inicial para el archivo, sino que utilizará la cadena que proporciones. Por ejemplo:

si falló
   checksum espera 8f7f419955cefa0b33a2ba316cba3659
entonces alerta

Puedes, por ejemplo, usar la utilidad GNU md5sum(1) o sha1sum(1) para crear una cadena de checksum para un archivo y usar esta cadena en la declaración expect.

Recargar un servidor si su archivo de configuración fue modificado:

comprueba archivo apache_conf con ruta /etc/apache/httpd.conf
    si checksum cambiado entonces exec "/usr/bin/apachectl graceful"

acción es una opción de "ALERT", "RESTART", "START", "STOP", "EXEC" o "UNMONITOR".

PRUEBA DE MARCA DE TIEMPO

La declaración timestamp solo puede usarse en una entrada de servicio de archivo, fifo o directorio.

Sintaxis de marca de tiempo relativa:

SI <TIEMPO DE ACCESO | ATIME | TIEMPO DE MODIFICACIÓN | MTIME | TIEMPO DE CAMBIO | CTIME | TIEMPO[STAMP]> <operador> <valor> [unidad] ENTONCES <acción>

Sintaxis de cambio de marca de tiempo:

SI CAMBIÓ <TIEMPO DE ACCESO | ATIME | TIEMPO DE MODIFICACIÓN | MTIME | TIEMPO DE CAMBIO | CTIME | TIEMPO[STAMP]> ENTONCES acción

PRUEBA DE MARCA DE TIEMPO

Hay cuatro tipos de prueba de marca de tiempo:

ACCESO (ATIME)
Prueba la marca de tiempo que se actualiza cada vez que se accede al objeto, por ejemplo, cuando se lee el archivo. El sistema de archivos generalmente permite deshabilitar las actualizaciones de atime mediante opciones de montaje, por lo que esta prueba solo funcionará si el sistema de archivos realiza actualizaciones de atime.
CAMBIO (CTIME)
Prueba la marca de tiempo que se actualiza cada vez que se modifican los metadatos del objeto, como el propietario, el grupo, los permisos o el número de enlaces duros.
MODIFICACIÓN (MTIME)
Prueba la marca de tiempo que se actualiza cada vez que se modifica el contenido del objeto. La marca de tiempo de modificación del archivo se actualiza cada vez que el archivo se trunca o se escribe en él. La marca de tiempo de modificación del directorio se actualiza cada vez que se añaden o eliminan archivos/subdirectorios de ese directorio.
PREDETERMINADO (ÚLTIMA DE TIEMPO DE CAMBIO Y MODIFICACIÓN)
Si no se establece ningún tipo de marca de tiempo específico, se comprueba la última de las marcas de tiempo de cambio y modificación. Esta prueba permite una comprobación sencilla de cualquier modificación de objeto (datos y metadatos).

operador es una opción de "<", ">", "!=" , "==" en notación C, "GT", "LT", "EQ", "NE" en notación sh de shell y "NEWER", "OLDER", "GREATER", "LESS", "EQUAL", "NOTEQUAL" en forma legible por humanos (si no se especifica, el valor predeterminado es EQUAL).

valor es una marca de tiempo.

unidad es "SECOND(S)", "MINUTE(S)", "HOUR(S)" o "DAY(S)".

acción es una opción de "ALERT", "RESTART", "START", "STOP", "EXEC" o "UNMONITOR".

Por ejemplo, para recargar apache si el archivo de configuración cambió:

check file apache_conf with path /etc/apache/httpd.conf
  if changed timestamp then exec "/usr/bin/apachectl graceful"

Por ejemplo, para probar un directorio en busca de adición o eliminación de archivos:

check directory bar path /foo/bar
  if changed timestamp then alert

Ejemplo para enviar una alerta si un archivo de registro no se actualiza durante más de 1 hora:

if timestamp is older than 1 hour then alert

valor es una marca de agua de tamaño.

unidad es una opción de "B", "KB", "MB", "GB" o alternativas largas "byte", "kilobyte", "megabyte", "gigabyte". Si no se especifica, la unidad "byte" se asume por defecto.

PRUEBA DE CONTENIDO DE ARCHIVO

La declaración de contenido se puede usar para probar incrementalmente el contenido de un archivo de texto utilizando expresiones regulares.

Sintaxis:

IF CONTENT <operador> <regex|ruta> THEN action

operador es "=" para coincidencia o "!=" para no coincidencia.

regex es una cadena que contiene la expresión regular extendida. Ver también regex(7).

ruta es una ruta absoluta a un archivo que contiene una expresión regular extendida en cada línea. Ver también regex(7).

acción es una opción de "ALERT", "RESTART", "START", "STOP", "EXEC" o "UNMONITOR".

Al inicio, la posición de lectura se establece al final del archivo y Monit continúa escaneando hasta el final del archivo en cada ciclo.

Si el tamaño del archivo disminuye o el inodo cambia, la posición de lectura se establece al principio del archivo.

Solo se inspeccionan las líneas que terminan con un carácter de nueva línea.

Por defecto, solo se inspeccionan los primeros 511 caracteres de una línea. Puede aumentar el límite usando la declaración set limits.

IGNORE CONTENT <operador> <regex|ruta>

Las líneas que coinciden con una IGNORAR no se inspeccionan durante las evaluaciones posteriores. IGNORE CONTENT siempre tiene precedencia sobre IF CONTENT.

Todas las declaraciones de IGNORE CONTENT se evalúan primero, en el orden de su aparición. Después, se evalúan todas las declaraciones de IF CONTENT.

Por ejemplo:

check file syslog with path /var/log/syslog
      ignore content = "monit"
      if content = "^mrcoffee" then alert

TEST DE ESTADO DEL PROGRAMA

Puede comprobar el estado de salida de un programa o script. Esta prueba solo puede utilizarse dentro de una entrada de servicio de programa en el archivo de control de Monit.

Sintaxis para probar un valor de salida específico:

IF STATUS operator value THEN action

Sintaxis para probar cualquier cambio en el valor de salida:

IF CHANGED STATUS THEN action

operador es una opción de "<",">","!=","==" en notación C, "gt","lt","eq", "ne" en notación shell sh y "greater","less","equal", "notequal" en forma legible para humanos (si no se especifica, el valor predeterminado es EQUAL).

acción es una opción de "ALERT", "RESTART","START", "STOP", "EXEC" o "UNMONITOR".

Ejemplo:

check program myscript with path /usr/local/bin/myscript.sh
      if status != 0 then alert

Script de ejemplo para el ejemplo anterior (/usr/local/bin/myscript.sh):

#!/bin/sh
echo test
exit $?

También puede enviar parámetros con el programa:

check program list-files with path "/bin/ls -lrt /tmp/"
      if status != 0 then alert

Los argumentos para el programa o script son una secuencia de cadenas separadas por espacios en blanco. En el ejemplo anterior, las cadenas '-lrt' y '/tmp/' son argumentos para el programa '/bin/ls'. Si se utilizan argumentos, se recomienda utilizar comillas " para incluir la cadena, de lo contrario, si no se utilizan argumentos, las comillas no son necesarias.

Notas: Si el programa es un script, el intérprete se requiere en la primera línea. El programa o script también debe ser ejecutable.

Si Monit se ejecuta como superusuario, puede ejecutar opcionalmente el programa como un usuario y/o grupo diferente. En este ejemplo, ejecutamos el programa ls como usuario www y como grupo staff:

check program ls with path "/bin/ls /tmp"
         as uid "www"
         and gid "staff"
      if status != 0 then alert

Monit ejecutará el programa periódicamente y si el estado de salida del programa no coincide con el resultado esperado, Monit puede realizar una acción. En el ejemplo anterior, Monit generará una alerta si el valor de salida es diferente de 0. Por convención, 0 significa que el programa finalizó normalmente.

Las comprobaciones de programas son asíncronas. Esto significa que Monit no esperará a que el programa finalice, sino que Monit iniciará el programa en segundo plano y continuará inmediatamente comprobando la siguiente entrada de servicio en monitrc. En el siguiente ciclo, Monit comprobará si el programa ha finalizado y, en ese caso, recopilará el estado de salida del programa. Si el estado indica un fallo, Monit generará un mensaje de alerta que contendrá la salida de error (stderr) del programa, si la hay. Si el programa no ha finalizado después del primer ciclo, Monit esperará otro ciclo y así sucesivamente. Si el programa sigue en ejecución después de 5 minutos, Monit lo finalizará y generará un evento de tiempo de espera del programa. Es posible anular el tiempo de espera predeterminado (consulte la sintaxis a continuación).

Se pueden utilizar varias pruebas de estado, por ejemplo:

check program hwtest with path /usr/local/bin/hwtest.sh
      with timeout 500 seconds
      if status = 1 then alert
      if status = 3 for 5 cycles then exec "/usr/local/bin/emergency.sh"

NETWORK PING TEST

Monit can perform a network ping test by sending ICMP echo request datagram packets to a host and wait for the reply. This test can only be used within a check host statement. Monit must also run as the root user in order to be able to perform the ping test (because the ping test must use raw sockets which usually only the super user is allowed to).

Syntax:

IF <FAILED|SUCCEEDED> PING[4|6]
   [COUNT number]
   [SIZE number]
   [RESPONSETIME operator number <MILLISECONDS|SECONDS>]
   [TIMEOUT number SECONDS]
   [ADDRESS string]
THEN action

If a DNS host name was used in the check host statement and the host name resolve to several addresses (either IPv4 or IPv6), Monit will ping the first available address and continue with the next address until one connection succeed or until there are no more addresses left to try. You can force Monit to only ping IPv4 or IPv6 addresses by using the PING4 or the PING6 keyword instead of PING.

The COUNT parameter specifies how many consecutive ping requests will be sent to the host in one cycle at maximum. The default value is 3.

The SIZE parameter specifies the ping request payload size. Default is 64 bytes, minimum is 8 bytes, maximum 1492 bytes.

The RESPONSETIME parameter sets the response time limit. operator is a choice of "<",">","!=","==" in c notation, "gt", "lt", "eq", "ne" in shell sh notation and "greater", "less", "equal", "notequal" in human readable form (if not specified, default is EQUAL).

If no reply arrive within TIMEOUT seconds, Monit reports an error. If at least one reply was received, the ping test is considered a success.

The ADDRESS parameter specifies source IP address.

Monit will, by default, send up to three ping request packets in one cycle to prevent false alarm (i.e. up to 66% packet loss is tolerated). You can set the COUNT option to a value between 1 and 20 to send more or fewer packets. If you require 100% ping success, set the count to 1 (i.e. just one request will be sent, and if the packet was lost an error will be reported).

Note that many ISPs have started to filter out ping or ICMP packets now, in which case there will be no reply from the host.

If a ping test is used in a check host entry, this test is run first and if the test should fail, we assume that the connection to the host is down and Monit will not continue with any subsequent port tests.

Example:

check host mmonit.com with address mmonit.com
      if failed ping then alert  # IPv4 or IPv6
check host mmonit.com with address 62.109.39.247
      if failed ping then alert # Address is IPv4 so IPv4 is preferred

or test that the system is explicit accessible via IPv4 and IPv6:

check host mmonit.com with address mmonit.com
      if failed ping4 then alert  # IPv4 only
      if failed ping6 then alert  # IPv6 only

or with all parameters; Send five 128 byte pings to mmonit.com and wait for up to 10 seconds for a reply

check host mmonit.com with address mmonit.com
      if failed ping count 5 size 128 with timeout 10 seconds then alert

You can also watch host, that is supposed to be offline:

check host offlinehost with address 192.168.100.50
      if succeeded ping then alert

CONNECTION TESTS

Monit can perform connection testing via network ports or via Unix sockets. A connection test may only be used within a process or host service type context.

If a service listens on one or more sockets, Monit can connect to the port (using TCP or UDP) and verify that the service will accept a connection and that it is possible to write and read from the socket. If a connection is not accepted or if there is a problem with socket I/O, Monit will execute a specified action.

For TCP/UDP ports monit can alert on successful connection, e.g. when a service like mysql should not be publicly available.

TCP/UDP port test syntax:

IF <FAILED|SUCCEEDED>
   [HOST string]
   <PORT number>
   [ADDRESS string]
   [IPV4 | IPV6]
   [TYPE <TCP|UDP>]
   [<SSL|TLS> [with options {...}]
   [CERTIFICATE CHECKSUM [MD5|SHA1] string]
   [CERTIFICATE VALID for number DAYS]
   [PROTOCOL protocol | <SEND|EXPECT> "string",...]
   [RESPONSETIME operator number <MILLISECONDS|SECONDS>]
   [TIMEOUT number SECONDS]
   [RETRY number]
THEN action

Unix socket test syntax:

IF <FAILED|SUCCEEDED>
   <UNIX SOCKET path>
   [TYPE <TCP|UDP>]
   [PROTOCOL protocol | <SEND|EXPECT> "string",...]
   [RESPONSETIME operator number <MILLISECONDS|SECONDS>]
   [TIMEOUT number SECONDS]
   [RETRY number]
THEN action

Examples:

if failed port 80 then alert
if failed port 53 type udp protocol dns then alert
if succeeded host example.org port 3306 type tcp protocol mysql then alert
if failed unixsocket /var/run/sophie then alert

Options:

HOST hostname. Optionally specify the host to connect to. If the host is not given then localhost is assumed if this test is used inside a process entry. If this test is used inside a remote host entry then the entry's remote host is assumed.

PORT number. The port number to connect to

UNIX SOCKET path. Specifies the path to a Unix socket (local machine only).

ADDRESS string. The source IP address to use.

IPV4 | IPV6 . Optionally specify the IP version Monit should use when trying to connect to the port. If not used, Monit will try to connect to the first available address (IPv4 or IPv6). If multiple addresses are available and connection to one address failed, Monit will try the next address and so on until a connection succeed or until there are no more addresses left to try.

TYPE [TCP | UDP]. Optionally specify the socket type Monit should use when trying to connect to the port. The different socket types are: TCP or UDP, where TCP is a regular stream based socket, UDP, a datagram socket. The default socket type is TCP.

[SSL | TLS] [with options {...}]. Set SSL/TLS options and override global/default SSL options. You can set the SSL/TLS version to use, whether to verify certificates, trust self-signed certificates or set the SSL client certificates database-file for client certificate authentication.

CERTIFICATE CHECKSUM [MD5|SHA1] hash. Verify the SSL server certificate by checking its checksum. You can use either MD5 or SHA1 checksum (if you don't specify the type, Monit will determine the digest based on the hash length). You can use the openssl command line tool to get the checksum value for your certificate, which you can then use in Monit's control file:

openssl x509 -fingerprint -sha1 -in server.crt | head -1 | cut -f2 -d'='

then alert

Opciones específicas de prueba de protocolo

GENERICO (SEND/EXPECT)

Si Monit no soporta el protocolo que habla el servidor, puedes escribir tu propia prueba de protocolo usando cadenas *send* y *expect*. La instrucción *SEND* envía una cadena al puerto del servidor y la instrucción *EXPECT* compara una cadena leída del servidor con la cadena dada en la instrucción expect.

Sintaxis:

[<SEND|EXPECT> "cadena"]+

Monit enviará una cadena tal cual, y debes recordar incluir CR y LF en la cadena enviada al servidor si el protocolo espera tales caracteres para terminar una cadena (la mayoría de los protocolos basados en texto usados en Internet lo hacen).

Monit leerá por defecto hasta 255 bytes del servidor y usará esta cadena al comparar la cadena EXPECT. Puedes anular el valor predeterminado usando la instrucción set limits.

Puedes usar caracteres no imprimibles en una cadena SEND si es necesario. Usa la notación hexadecimal, \0xHEXHEX para enviar cualquier carácter en el rango \0x00-\0xFF, es decir, de 0 a 255 en decimal. Por ejemplo, para probar un servidor Quake 3:

send "\0xFF\0xFF\0xFF\0xFFgetstatus"
expect "sv_floodProtect|sv_maxPing"

Si tu sistema soporta expresiones regulares POSIX, puedes usar expresiones regulares en la cadena EXPECT, ver regex(7) para aprender más sobre los tipos de expresiones regulares que puedes usar en una cadena expect.

Dado que tanto la comparación de expresiones regulares como la de cadenas operan sobre una cadena terminada en cero, no puedes probar '\0' en un buffer EXPECT ya que este carácter marca el final del buffer. Sin embargo, escapamos '\0' en el buffer expect como "\0" que puedes probar. Es decir, '\' seguido del valor ascii para 0. Por ejemplo, así es como se prueba una cadena expect que comienza con cero seguido de cualquier número de caracteres.

expect "^[\\]0.*"

Aquí tienes un ejemplo simple del protocolo SMTP:

if failed
   port 25 and
   expect "^220.*"
   send   "HELO localhost.localdomain\r\n"
   expect "^250.*"
   send   "QUIT\r\n"
then alert

SEND/EXPECT se puede usar con cualquier tipo de socket, como sockets TCP, sockets UNIX y sockets UDP.

HTTP

Sintaxis:

PROTO(COL) HTTP
    [USERNAME "cadena"]
    [PASSWORD "cadena"]
    [REQUEST "cadena"]
    [METHOD <GET|HEAD>]
    [STATUS operador número]
    [CHECKSUM checksum]
    [HTTP HEADERS lista de cabeceras]
    [CONTENT < "=" | "!=" > CADENA]

USERNAME es un nombre de usuario opcional para autenticación Básica

PASSWORD es una contraseña opcional para autenticación Básica

La opción *REQUEST* puede establecer una cadena URL especificando un documento en el servidor HTTP. Si la instrucción request no se especifica, se solicitará la página por defecto "/"

Por ejemplo:

if failed
   port 80
   protocol http
   request "/data/show?a=b&c=d"
then restart

METHOD establece el método de solicitud HTTP. Si no se especifica, Monit prefiere el método de solicitud HTTP GET, que es más común que el método HEAD. Uno puede querer establecer explícitamente el método a HEAD para ahorrar ancho de banda de red.

La opción *STATUS* se puede usar para probar explícitamente el código de estado HTTP devuelto por el servidor HTTP. Si no se usa, la prueba de protocolo HTTP fallará si el código de estado devuelto es mayor o igual a 400. Puedes anular este comportamiento usando el calificador *status*.

Por ejemplo, para probar que una página no existe (el servidor HTTP debería devolver 404 en este caso):

if failed
   port 80
   protocol http
   request "/non/existent.php"
   status = 404
then alert

CHECKSUM Puedes probar la suma de verificación de los documentos devueltos por un servidor HTTP. Se puede usar el hash MD5 o SHA1. Monit no probará la suma de verificación de un documento si el servidor no establece la cabecera HTTP *Content-Length*. Un servidor HTTP debería establecer esta cabecera cuando sirve un documento estático (es decir, un archivo). No hay limitaciones en el tamaño del documento, pero ten en cuenta que Monit usará tiempo para descargar el documento a través de la red para calcular la suma de verificación.

Ejemplo:

if failed
   port 80
   protocol http
   request "/page.html"
   checksum 8f7f419955cefa0b33a2ba316cba3659
then alert

HTTP HEADERS se puede usar para enviar una lista de cabeceras HTTP al usar la prueba de protocolo HTTP. Por ejemplo, la cabecera host. Si la cabecera host no se establece, Monit usará el nombre de host o la dirección IP del host tal como se especifica en la instrucción check host. Especificar una cabecera host es útil si deseas conectarte y probar un host virtual basado en nombre. La sintaxis para establecer cabeceras HTTP es

http headers [nombre:valor, nombre:valor,..]

donde cada par nombre:valor está separado por ','. Si necesitas usar ':' en la cadena de valor, por ejemplo, para establecer el número de puerto para una cabecera host, debes encerrar el valor entre comillas. Por ejemplo,

http headers [Host: "mmonit.com:443"]

En un contexto de check host, usar esta instrucción podría verse así:

check host mmonit.com with address mmonit.com
  if failed
     port 80 protocol http
     with http headers [Host: mmonit.com, Cache-Control: no-cache,
       Cookie: csrftoken=nj1bI3CnMCaiNv4beqo8ZaCfAQQvpgLH]
     and request /monit/ with content = "Monit [0-9.]+"
  then alert

El establecimiento de cabeceras HTTP está asociado con la prueba de protocolo HTTP y debe venir antes de *request* como en el ejemplo anterior.

La opción *CONTENT* establece el patrón que se espera en los datos devueltos por el servidor. Si el patrón no coincide, la prueba falla. En el ejemplo anterior, si el servidor no devuelve una página con el nombre Monit seguido de un número de versión, la prueba fallará.

Por defecto, se inspecciona como máximo 1MB de contenido. Puedes aumentar este límite usando la instrucción set limits.

Por ejemplo:

if failed
   port 80
   protocol http
   content = "foobar [0-9.]+"
then alert

APACHE-STATUS

La prueba *APACHE-STATUS* permite comprobar el rendimiento del servidor examinando la página de estado generada por mod_status de Apache, que se espera que esté en su dirección predeterminada http://www.example.com/server-status.

Sintaxis:

PROTOCOL APACHE-STATUS [PATH <path>] [USERNAME <string>] [PASSWORD <string>] [<propiedad> <operador> <número>]+

PATH es una ruta opcional al estado de apache ("/server-status" por defecto)

USERNAME es un nombre de usuario opcional para autenticación Básica

PASSWORD es una contraseña opcional para autenticación Básica

propiedad es el acrónimo del estado del hijo:

(1) logging (loglimit)
(2) closing connections (closelimit)
(3) performing DNS lookups (dnslimit)
(4) in keepalive with a client (keepalivelimit)
(5) replying to a client (replylimit)
(6) receiving a request (requestlimit)
(7) initialising (startlimit)
(8) waiting for incoming connections (waitlimit)
(9) gracefully closing down (gracefullimit)
(10) performing cleanup procedures (cleanuplimit)

operador es uno de "<", "=", ">".

número es un límite numérico en porcentaje.

Cada uno de estos límites se puede comparar con un valor relativo al número total de procesos hijos activos de Apache.

Puedes combinar todas estas pruebas en una sola expresión o puedes optar por probar solo un cierto límite. Si combinas los límites debes conectarlos usando la palabra clave OR.

Ejemplo:

if failed port 80 protocol apache-status
       loglimit > 10% or
       dnslimit > 50% or
       waitlimit < 20%
then alert

SIGNALS

If a Monit daemon is running, SIGUSR1 wakes it up from its sleep phase and forces a poll of all services. SIGTERM and SIGINT will gracefully terminate a Monit daemon. The SIGTERM signal is sent to a Monit daemon if Monit is started with the quit action argument.

Sending a SIGHUP signal to a running Monit daemon will force the daemon to reinitialise itself, specifically it will reread configuration, close and reopen log files.

Running Monit in foreground while a background Monit daemon is running will wake up the daemon.

NOTES

This is a very silent program. Use the -v switch if you want to see what Monit is doing, and tail -f the log file. Optionally for testing purposes; you can start Monit with the -Iv switch. Monit will then print debug information to the console, to stop monit in this mode, simply press CTRL^C (i.e. SIGINT) in the same console.
