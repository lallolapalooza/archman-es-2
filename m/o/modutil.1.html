MODUTIL(1) Herramientas de Seguridad NSS MODUTIL(1)

NOMBRE

modutil - Gestiona la información de módulos PKCS #11 dentro de la base de datos de módulos de seguridad.

SINOPSIS

modutil [opciones] [[argumentos]]

ESTADO

Esta documentación todavía está en proceso. Por favor, contribuya a la revisión inicial en el error 836477 de Mozilla NSS[1]

DESCRIPCIÓN

La Herramienta de Base de Datos de Módulos de Seguridad, modutil, es una utilidad de línea de comandos para gestionar la información de módulos PKCS #11 tanto dentro de archivos secmod.db como dentro de tokens de hardware. modutil puede añadir y eliminar módulos PKCS #11, cambiar contraseñas en bases de datos de seguridad, establecer valores predeterminados, listar el contenido de módulos, habilitar o deshabilitar ranuras (slots), habilitar o deshabilitar el cumplimiento de FIPS 140-2, y asignar proveedores predeterminados para operaciones criptográficas. Esta herramienta también puede crear archivos de bases de datos de seguridad de certificados, claves y módulos.

Las tareas asociadas con la gestión de la base de datos de módulos de seguridad forman parte de un proceso que típicamente también implica la gestión de bases de datos de claves y bases de datos de certificados.

OPCIONES

Ejecutar modutil siempre requiere una (y solo una) opción para especificar el tipo de operación del módulo. Cada opción puede tomar argumentos, desde ninguno hasta múltiples argumentos.

Opciones

-add nombre_modulo

Añade el módulo PKCS #11 con el nombre dado a la base de datos. Usa esta opción con los argumentos -libfile, -ciphers, y -mechanisms.

-changepw nombre_token

Cambia la contraseña del token con el nombre dado. Si el token no ha sido inicializado, esta opción inicializa la contraseña. Usa esta opción con los argumentos -pwfile y -newpwfile. Una contraseña es equivalente a un número de identificación personal (PIN).

-chkfips

Verifica si el módulo está en el modo FIPS dado. true significa verificar que el módulo está en modo FIPS, mientras que false significa verificar que el módulo no está en modo FIPS.

-create

Crea nuevas bases de datos de certificados, claves y módulos. Usa el argumento de directorio -dbdir para especificar un directorio. Si alguna de estas bases de datos ya existe en un directorio especificado, modutil devuelve un mensaje de error.

-default nombre_modulo

Especifica los mecanismos de seguridad para los cuales el módulo con el nombre dado será un proveedor predeterminado. Los mecanismos de seguridad se especifican con el argumento -mechanisms.

-delete nombre_modulo

Elimina el módulo con el nombre dado. El módulo PKCS #11 predeterminado de NSS no puede ser eliminado.

-disable nombre_modulo

Deshabilita todas las ranuras (slots) en el módulo con el nombre dado. Usa el argumento -slot para deshabilitar una ranura específica.

El módulo PKCS #11 interno de NSS no puede ser deshabilitado.

-enable nombre_modulo

Habilita todas las ranuras (slots) en el módulo con el nombre dado. Usa el argumento -slot para habilitar una ranura específica.

-fips [true | false]

Habilita (true) o deshabilita (false) el cumplimiento de FIPS 140-2 para el módulo NSS predeterminado.

-force

Deshabilita las indicaciones interactivas de modutil para que pueda ser ejecutado desde un script. Usa esta opción solo después de probar manualmente cada operación planeada para verificar advertencias y para asegurar que omitir las indicaciones no cause fallos de seguridad ni pérdida de integridad de la base de datos.

-jar archivo_JAR

Añade un nuevo módulo PKCS #11 a la base de datos usando el archivo JAR con el nombre dado. Usa este comando con los argumentos -installdir y -tempdir. El archivo JAR utiliza el formato de archivo JAR PKCS #11 de NSS para identificar todos los archivos a instalar, el nombre del módulo, las banderas de mecanismos y las banderas de cifrado, así como cualquier archivo a instalar en la máquina de destino, incluyendo el archivo de biblioteca del módulo PKCS #11 y otros archivos como documentación. Esto se cubre en la sección del archivo de instalación JAR de la página del manual, que detalla el script especial necesario para realizar una instalación a través de un servidor o con modutil.

-list [nombre_modulo]

Muestra información básica sobre el contenido del archivo secmod.db. Especificar un nombre_modulo muestra información detallada sobre un módulo en particular y sus ranuras (slots) y tokens.

-rawadd

Añade la cadena de especificación del módulo a la base de datos secmod.db.

-rawlist

Muestra las especificaciones de módulo para un módulo especificado o para todos los módulos cargables.

-undefault nombre_modulo

Especifica los mecanismos de seguridad para los cuales el módulo con el nombre dado no será un proveedor predeterminado. Los mecanismos de seguridad se especifican con el argumento -mechanisms.

Argumentos

MODULO

Indica el módulo de seguridad a acceder.

ESPEC_MODULO

Indica la especificación del módulo de seguridad a cargar en la base de datos de seguridad.

-ciphers lista_habilitar_cifrados

Habilita cifrados específicos en un módulo que se está añadiendo a la base de datos. La lista_habilitar_cifrados es una lista delimitada por dos puntos de nombres de cifrados. Encierra esta lista entre comillas si contiene espacios.

-dbdir directorio

Especifica el directorio de la base de datos en el cual acceder o crear archivos de base de datos de módulos de seguridad.

modutil soporta dos tipos de bases de datos: las bases de datos de seguridad heredadas (cert8.db, key3.db, y secmod.db) y bases de datos SQLite (cert9.db, key4.db, y pkcs11.txt). Si el prefijo dbm: no se usa, entonces la herramienta asume que las bases de datos dadas están en formato SQLite.

--dbprefix prefijo

Especifica el prefijo utilizado en los archivos de base de datos, como my_ para my_cert9.db. Esta opción se proporciona como un caso especial. No se recomienda cambiar los nombres de las bases de datos de certificados y claves.

-installdir directorio_instalacion_raiz

Especifica el directorio de instalación raíz relativo al cual se instalarán los archivos por la opción -jar. Este directorio debería ser uno debajo del cual es apropiado almacenar archivos de biblioteca dinámica, como el directorio raíz de un servidor.

-libfile archivo_biblioteca

Especifica una ruta a un archivo de biblioteca que contiene la implementación del módulo de interfaz PKCS #11 que se está añadiendo a la base de datos.

-mechanisms lista_mecanismos

Especifica los mecanismos de seguridad para los cuales un módulo en particular será marcado como proveedor predeterminado. La lista_mecanismos es una lista delimitada por dos puntos de nombres de mecanismos. Encierra esta lista entre comillas si contiene espacios.

El módulo se convierte en un proveedor predeterminado para los mecanismos listados cuando esos mecanismos están habilitados. Si más de un módulo reclama ser el proveedor predeterminado de un mecanismo en particular, el proveedor predeterminado de ese mecanismo no está definido.

modutil soporta varios mecanismos: RSA, DSA, RC2, RC4, RC5, AES, DES, DH, SHA1, SHA256, SHA512, SSL, TLS, MD5, MD2, RANDOM (para generación de números aleatorios), y FRIENDLY (que significa que los certificados son legibles públicamente).

-newpwfile archivo_nueva_contraseña

Especifica un archivo de texto que contiene la nueva contraseña del token o la contraseña de reemplazo para que una contraseña pueda ser introducida automáticamente con la opción -changepw.

-nocertdb

No abrir las bases de datos de certificados o claves. Esto tiene varios efectos:
•Con el comando -create, solo se crea un archivo de módulo de seguridad; las bases de datos de certificados y claves no se crean.
•Con el comando -jar, no se comprueban las firmas en el archivo JAR.
•Con el comando -changepw, la contraseña en el módulo interno de NSS no puede ser establecida ni cambiada, ya que esta contraseña se almacena en la base de datos de claves.

-pwfile archivo_contraseña_antigua

Especifica un archivo de texto que contiene la contraseña existente de un token para que una contraseña pueda ser introducida automáticamente cuando se usa la opción -changepw para cambiar contraseñas.

-secmod nombre_secmod

Indica el nombre de la base de datos del módulo de seguridad (como secmod.db) a cargar.

-slot nombre_ranura

Especifica una ranura (slot) en particular para ser habilitada o deshabilitada con las opciones -enable o -disable.

-string CADENA_CONFIGURACIÓN

Pasa una cadena de configuración para el módulo que se está añadiendo a la base de datos.

-tempdir directorio_temporal

Indica la ubicación de un directorio donde los archivos temporales
are creados durante la instalación con la opción -jar. Si no se especifica un directorio temporal, se utiliza el directorio actual.

USO Y EJEMPLOS

Creación de Archivos de Base de Datos

Antes de que se puedan realizar operaciones, debe haber un conjunto de bases de datos de seguridad disponibles. modutil se puede usar para crear estos archivos. El único argumento requerido es el directorio de la base de datos donde se ubicarán las bases de datos.

modutil -create -dbdir directorio

Adición de un Módulo Criptográfico

Agregar un módulo PKCS #11 significa enviar un archivo de biblioteca de soporte, habilitar sus cifradores y establecer el estado del proveedor predeterminado para varios mecanismos de seguridad. Esto se puede hacer proporcionando toda la información directamente a través de modutil o ejecutando un archivo JAR y un script de instalación. Para el caso más básico, simplemente cargue la biblioteca:

modutil -add nombre_modulo -libfile archivo_biblioteca [-ciphers lista_activacion_cifradores] [-mechanisms lista_mecanismos]

Por ejemplo:

modutil -dbdir /home/mi/sharednssdb -add "Módulo PKCS #11 de Ejemplo" -libfile "/tmp/crypto.so" -mechanisms RSA:DSA:RC2:RANDOM 
Usando el directorio de base de datos ... 
Módulo "Módulo PKCS #11 de Ejemplo" añadido a la base de datos.

Instalación de un Módulo Criptográfico desde un Archivo JAR

Los módulos PKCS #11 también se pueden cargar usando un archivo JAR, que contiene todas las bibliotecas requeridas y un script de instalación que describe cómo instalar el módulo. El script de instalación JAR se describe con más detalle en la sección llamada "FORMATO DEL ARCHIVO DE INSTALACIÓN JAR".

El script de instalación JAR define la información de configuración para cada plataforma en la que el módulo puede ser instalado. Por ejemplo:

Platforms { 
   Linux:5.4.08:x86 { 
      ModuleName { "Módulo PKCS #11 de Ejemplo" } 
      ModuleFile { crypto.so } 
      DefaultMechanismFlags{0x0000} 
      CipherEnableFlags{0x0000} 
      Files { 
         crypto.so { 
            Path{ /tmp/crypto.so } 
         } 
         setup.sh { 
            Executable 
            Path{ /tmp/setup.sh } 
         } 
      } 
   } 
   Linux:6.0.0:x86 { 
      EquivalentPlatform { Linux:5.4.08:x86 } 
   } 
}

Tanto el script de instalación como las bibliotecas requeridas deben estar empaquetados en un archivo JAR, que se especifica con el argumento -jar.

modutil -dbdir /home/mt"archivo-instalacion-jar/sharednssdb -jar install.jar -installdir /home/mi/sharednssdb

Adición de Especificación de Módulo

Cada módulo tiene información almacenada en la base de datos de seguridad sobre su configuración y parámetros. Estos se pueden agregar o editar usando el comando -rawadd. Para ver la configuración actual o el formato de la especificación del módulo en la base de datos, use la opción -rawlist.

modutil -rawadd especificacion_modulo

Eliminación de un Módulo

Se puede eliminar un módulo PKCS #11 específico de la base de datos secmod.db:

modutil -delete nombre_modulo -dbdir directorio

Visualización de Información del Módulo

La base de datos secmod.db contiene información sobre los módulos PKCS #11 que una aplicación o servidor puede utilizar. Se pueden ver la lista de todos los módulos, información sobre módulos específicos y especificaciones de configuración de la base de datos para los módulos.

Para simplemente obtener una lista de módulos en la base de datos, use el comando -list.

modutil -list [nombre_modulo] -dbdir directorio

Listar los módulos muestra el nombre del módulo, su estado y otras bases de datos de seguridad asociadas para certificados y claves. Por ejemplo:

Establecer un Proveedor Predeterminado para Mecanismos de Seguridad

Múltiples módulos de seguridad pueden proporcionar soporte para los mismos mecanismos de seguridad. Es posible establecer un módulo de seguridad específico como proveedor predeterminado para un mecanismo de seguridad específico (o, por el contrario, prohibir que un proveedor proporcione esos mecanismos).

modutil -default nombre_modulo -mechanisms lista_mecanismos

Para establecer un módulo como proveedor predeterminado para mecanismos, use el comando -default con una lista de mecanismos separados por dos puntos. Los mecanismos disponibles dependen del módulo; NSS proporciona casi todos los mecanismos comunes. Por ejemplo:

modutil -default "Módulo PKCS #11 Interno de NSS" -dbdir -mechanisms RSA:DSA:RC2 
Usando el directorio de base de datos c:\databases...
Predeterminados cambiados con éxito.

Borrar el proveedor predeterminado tiene el mismo formato:

modutil -undefault "Módulo PKCS #11 Interno de NSS" -dbdir -mechanisms MD2:MD5

Habilitar y Deshabilitar Módulos y Slots

Los módulos y slots específicos en los módulos se pueden habilitar o deshabilitar selectivamente usando modutil. Ambos comandos tienen el mismo formato:

modutil -enable|-disable nombre_modulo [-slot nombre_slot]

Por ejemplo:

modutil -enable "Módulo PKCS #11 Interno de NSS" -slot "Servicios Criptográficos Internos de NSS                            " -dbdir .
Slot "Servicios Criptográficos Internos de NSS                            " habilitado.

Asegúrese de que la cantidad adecuada de espacios en blanco al final esté después del nombre del slot. Algunos nombres de slot tienen una cantidad significativa de espacios en blanco que deben incluirse, o la operación fallará.

Habilitar y Verificar Cumplimiento de FIPS

Los módulos NSS pueden tener el cumplimiento FIPS 140-2 habilitado o deshabilitado usando modutil con la opción -fips. Por ejemplo:

modutil -fips true -dbdir /home/mi/sharednssdb/
Modo FIPS habilitado.

Para verificar el estado del modo FIPS, ejecute el comando -chkfips con un indicador verdadero o falso (no importa cuál). La herramienta devuelve la configuración FIPS actual.

modutil -chkfips false -dbdir /home/mi/sharednssdb/
Modo FIPS habilitado.

Cambiar la Contraseña de un Token

Inicializar o cambiar la contraseña de un token:

modutil -changepw nombre_token [-pwfile archivo_contraseña_anterior] [-newpwfile archivo_nueva_contraseña] 
modutil -dbdir /home/mi/sharednssdb -changepw "Base de Datos de Certificados de NSS"

FORMATO DEL ARCHIVO DE INSTALACIÓN JAR

Cuando un archivo JAR es ejecutado por un servidor, por modutil, o por cualquier programa que no interprete JavaScript, se debe incluir un archivo de información especial para instalar las bibliotecas. Hay varias cosas a tener en cuenta con este archivo:

•Debe declararse en el archivo de manifiesto del archivo JAR.
•El script puede tener cualquier nombre.
•La etiqueta de metadatos para esto es Pkcs11_install_script. Para declarar metadatos en el archivo de manifiesto, colóquelos en un archivo que se pase a signtool.

Ejemplo de Script

Por ejemplo, el script instalador de PKCS #11 podría estar en el archivo pk11install. Si es así, el archivo de metadatos para signtool incluye una línea como esta:

+ Pkcs11_install_script: pk11install

El script debe definir la plataforma y el número de versión, el nombre y archivo del módulo, y cualquier información opcional como cifradores y mecanismos compatibles. Se pueden definir múltiples plataformas en un solo archivo de instalación.

ForwardCompatible { IRIX:6.2:mips SUNOS:5.5.1:sparc }
Platforms {
   WINNT::x86 {
      ModuleName { "Módulo de Ejemplo" }
      ModuleFile { win32/fort32.dll }
      DefaultMechanismFlags{0x0001}
      DefaultCipherFlags{0x0001}
      Files {
         win32/setup.exe {
            Executable
            RelativePath { %temp%/setup.exe }
         }
         win32/setup.hlp {
            RelativePath { %temp%/setup.hlp }
         }
         win32/setup.cab {
            RelativePath { %temp%/setup.cab }
         }
      }
   }
   SUNOS:5.5.1:sparc {
      ModuleName { "Módulo UNIX de Ejemplo" }
      ModuleFile { unix/fort.so }
      DefaultMechanismFlags{0x0001}
      CipherEnableFlags{0x0001}
      Files {
         unix/fort.so {
            RelativePath{%root%/lib/fort.so}
            AbsolutePath{/usr/local/netscape/lib/fort.so}
            FilePermissions{555}
         }
         xplat/instr.html {
            RelativePath{%root%/docs/inst.html}
            AbsolutePath{/usr/local/netscape/docs/inst.html}
            FilePermissions{555}
         }
      }
   }
   IRIX:6.2:mips {
      EquivalentPlatform { SUNOS:5.5.1:sparc }
   }
}

Gramática del Script

El script es Java básico, permitiendo listas, pares clave-valor, cadenas y combinaciones de todos ellos.

--> valuelist
valuelist --> value valuelist
               <null>
value ---> key_value_pair
            string
key_value_pair --> key { valuelist }
key --> string
string --> simple_string
            "complex_string"
simple_string --> [^ \t\n\""{""}"]+
complex_string --> ([^\"\\\r\n]|(\\\")|(\\\\))+

Las comillas y las barras invertidas deben escaparse con una barra invertida. Una cadena compleja no debe incluir saltos de línea ni retornos de carro. Fuera de las cadenas complejas, todo el espacio en blanco (por ejemplo, espacios, tabulaciones y retornos de carro) se considera igual y se utiliza solo para delimitar tokens.

Claves

El archivo de instalación de Java utiliza claves para definir la plataforma y la información del módulo.

ForwardCompatible proporciona una lista de plataformas que son compatibles con versiones futuras. Si la plataforma actual no se encuentra en la lista de plataformas admitidas, se consulta la lista ForwardCompatible para ver si hay plataformas que tengan el mismo sistema operativo y arquitectura en una versión anterior. Si se encuentra una, sus atributos se utilizan para la plataforma actual.

Platforms (obligatorio) Proporciona una lista de plataformas. Cada entrada en la lista es a su vez un par clave-valor: la clave es el nombre de la plataforma y la lista de valores contiene varios atributos de la plataforma. La cadena de plataforma tiene el formato *nombre del sistema:versión del SO:arquitectura*. El instalador obtiene estos valores de NSPR. La versión del SO es una cadena vacía en sistemas operativos no Unix. NSPR admite estas plataformas:

•AIX (rs6000)
•BSDI (x86)
•FREEBSD (x86)
•HPUX (hppa1.1)
•IRIX (mips)
•LINUX (ppc, alpha, x86)
•MacOS (PowerPC)
•NCR (x86)
•NEC (mips)
•OS2 (x86)
•OSF (alpha)
•ReliantUNIX (mips)

Por ejemplo:

IRIX:6.2:mips
SUNOS:5.5.1:sparc
Linux:2.0.32:x86
WIN95::x86

La información del módulo se define independientemente para cada plataforma en los atributos ModuleName, ModuleFile y Files. Estos atributos deben proporcionarse a menos que se especifique un atributo EquivalentPlatform.

Claves por Plataforma

Las claves por plataforma solo tienen significado dentro de la lista de valores de una entrada en la lista Platforms.

ModuleName (obligatorio) proporciona el nombre común para el módulo. Este nombre se utiliza para referenciar el módulo por los servidores y por la herramienta modutil.

ModuleFile (obligatorio) nombra el archivo del módulo PKCS #11 para esta plataforma. El nombre se proporciona como la ruta relativa del archivo dentro del archivo JAR.

Files (obligatorio) enumera los archivos que deben instalarse para este módulo. Cada entrada en la lista de archivos es un par clave-valor. La clave es la ruta del archivo en el archivo JAR, y la lista de valores contiene los atributos del archivo. Se debe especificar al menos RelativePath o AbsolutePath para cada archivo.

DefaultMechanismFlags especifica los mecanismos para los que este módulo es el proveedor predeterminado; esto es equivalente a la opción -mechanism con el comando -add. Este par clave-valor es una cadena de bits especificada en formato hexadecimal (0x). Se construye como una operación OR a nivel de bits. Si se omite la entrada DefaultMechanismFlags, el valor predeterminado es 0x0.

RSA:                   0x00000001
DSA:                   0x00000002
RC2:                   0x00000004
RC4:                   0x00000008
DES:                   0x00000010
DH:                    0x00000020
FORTEZZA:              0x00000040
RC5:                   0x00000080
SHA1:                  0x00000100
MD5:                   0x00000200
MD2:                   0x00000400
RANDOM:                0x08000000
FRIENDLY:              0x10000000
OWN_PW_DEFAULTS:       0x20000000
DISABLE:               0x40000000

CipherEnableFlags especifica los cifrados que proporciona este módulo que NSS no proporciona (para que el módulo habilite esos cifradores para NSS). Esto es equivalente al argumento -cipher con el comando -add. Esta clave es una cadena de bits especificada en formato hexadecimal (0x). Se construye como una operación OR a nivel de bits. Si se omite la entrada CipherEnableFlags, el valor predeterminado es 0x0.

EquivalentPlatform especifica que los atributos de la plataforma nombrada también deben usarse para la plataforma actual. Esto facilita las cosas cuando más de una plataforma utiliza la misma configuración.

Claves por Archivo

Algunas claves solo tienen significado dentro de la lista de valores de una entrada en una lista Files.

Cada archivo requiere una clave de ruta que identifique dónde está el archivo. Se debe especificar RelativePath o AbsolutePath. Si se especifican ambos, la ruta relativa se intenta primero, y la ruta absoluta solo se utiliza si el programa instalador no proporciona un directorio raíz relativo.

RelativePath especifica el directorio de destino del archivo, relativo a algún directorio decidido en el momento de la instalación. Se pueden usar dos variables en la ruta relativa: %root% y %temp%. %root% se reemplaza en tiempo de ejecución con el directorio relativo al cual se deben instalar los archivos; por ejemplo, puede ser el directorio raíz del servidor. El directorio %temp% se crea al comienzo de la instalación y se destruye al final. El propósito de %temp% es contener archivos ejecutables (como programas de configuración) o archivos que son utilizados por estos programas. Se garantiza que los archivos destinados al directorio temporal estarán en su lugar antes de que se ejecute cualquier archivo ejecutable; no se eliminan hasta que todos los archivos ejecutables hayan terminado.

AbsolutePath especifica el directorio de destino del archivo como una ruta absoluta.

Executable especifica que el archivo se ejecutará durante el curso de la instalación. Típicamente, esta cadena se utiliza para un programa de configuración proporcionado por un proveedor de módulos, como un ejecutable de configuración autoextraíble. Se pueden especificar más de un archivo como ejecutable, en cuyo caso los archivos se ejecutan en el orden en que se especifican en el archivo de script.

FilePermissions establece los permisos en cualquier archivo referenciado en una cadena de dígitos octales, de acuerdo con el formato estándar de Unix. Esta cadena es una operación OR a nivel de bits.

lectura de usuario:                0400
escritura de usuario:               0200
ejecución de usuario:             0100
lectura de grupo:               0040
escritura de grupo:              0020
ejecución de grupo:            0010
lectura de otros:               0004
escritura de otros:              0002
ejecución de otros:            0001

Es posible que algunas plataformas no comprendan estos permisos. Solo se aplican en la medida en que tengan sentido para la plataforma actual. Si se omite este atributo, se asume un valor predeterminado de 777.

TIPOS DE BASE DE DATOS NSS

NSS originalmente utilizaba bases de datos BerkeleyDB para almacenar información de seguridad. Las últimas versiones de estas bases de datos *legadas* son:

•cert8.db para certificados
•key3.db para claves
•secmod.db para información del módulo PKCS #11

Sin embargo, BerkeleyDB tiene limitaciones de rendimiento, lo que impide que sea utilizado fácilmente por múltiples aplicaciones simultáneamente. NSS tiene cierta flexibilidad que permite a las aplicaciones utilizar su propio motor de base de datos independiente, manteniendo una base de datos compartida y evitando problemas de acceso. Aun así, NSS requiere más flexibilidad para proporcionar una base de datos de seguridad verdaderamente compartida.

En 2009, NSS introdujo un nuevo conjunto de bases de datos que son bases de datos SQLite en lugar de BerkleyDB. Estas nuevas bases de datos proporcionan mayor accesibilidad y rendimiento:

•cert9.db para certificados
•key4.db para claves
•pkcs11.txt, que es una lista de todos los módulos PKCS #11 contenidos en un nuevo subdirectorio en el directorio de bases de datos de seguridad.

Dado que las bases de datos SQLite están diseñadas para ser compartidas, estos son el tipo de base de datos *compartido*. Se prefiere el tipo de base de datos compartido; el formato heredado se incluye para compatibilidad con versiones anteriores.

Por defecto, las herramientas (certutil, pk12util, modutil) asumen que las bases de datos de seguridad dadas utilizan el tipo SQLite. El uso de las bases de datos heredadas debe especificarse manualmente utilizando el prefijo dbm: con el directorio de seguridad dado. Por ejemplo:

modutil -create -dbdir dbm:/home/my/sharednssdb

Para establecer el tipo de base de datos heredado como el tipo predeterminado para las herramientas, establezca la variable de entorno NSS_DEFAULT_DB_TYPE en dbm:

export NSS_DEFAULT_DB_TYPE="dbm"

Esta línea se puede añadir al archivo ~/.bashrc para que el cambio sea permanente para el usuario.

•https://wiki.mozilla.org/NSS_Shared_DB_Howto

Para un borrador técnico sobre los cambios en las bases de datos compartidas de NSS, consulte la wiki del proyecto NSS:

•https://wiki.mozilla.org/NSS_Shared_DB
