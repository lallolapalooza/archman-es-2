monodocer(1)

monodocer(1) Manual de comandos generales monodocer(1)

NOMBRE

monodocer - Soporte para el formato de documentación ECMA

SINOPSIS

monodocer [OPCIONES]*

OPCIONES

-ensamblado:ENSAMBLADO
ENSAMBLADO es un ensamblado .NET para el cual generar plantillas de documentación.

Especifique una ruta de archivo o el nombre de un ensamblado GAC'd.

-eliminar
Permite a monodocer eliminar miembros de los archivos de documentación. Los únicos miembros eliminados son aquellos que ya no están presentes dentro del ensamblado.

Si un tipo ya no está presente, el archivo de documentación *no* se elimina, sino que se *renombra* para tener una extensión .remove.

-?, -ayuda
Mostrar información sobre los argumentos del programa.
-ignorar-miembros
No actualizar miembros.

Esto agregará plantillas de documentación para tipos agregados, pero *no* agregará ni eliminará documentación para ningún miembro de ningún tipo (incluidos los tipos agregados).

-importar-doc-barra-inclinada:ARCHIVO
ARCHIVO es un archivo XML generado con la opción /doc:ARCHIVO del compilador C# (por ejemplo, mcs -doc:foo.xml foo.cs). Importe la documentación de miembros contenida dentro de ARCHIVO al formato de documentación utilizado por monodoc.
-nombre:NOMBRE
NOMBRE es el nombre del proyecto para el cual se genera esta documentación.

Esto establece el elemento /Overview/Title dentro del archivo index.xml creado en el directorio especificado por -path . Esto es utilizado por algunos programas para información de título (por ejemplo, monodocs2html).

-espacio-de-nombres:ESPACIO-DE-NOMBRES
Solo actualizar los tipos dentro del espacio de nombres ESPACIO-DE-NOMBRES.
-sobrescrituras
Incluir métodos sobrescritos en la documentación.

Esto normalmente no es necesario, ya que el Navegador de Documentación de Mono proporcionará un enlace a los miembros del tipo base de todos modos, al igual que monodocs2html si el tipo base está dentro del mismo ensamblado.

-ruta:DIR_SALIDA
DIR_SALIDA es el directorio que contendrá las plantillas de documentación nuevas/actualizadas.
-bonito
Indentificar los archivos XML de forma legible.
-desde:DESDE
Crear un elemento <since/> para tipos y miembros agregados con el valor DESDE.

Por ejemplo, al recibir -desde:"Gtk# 2.4" se insertará un elemento en el elemento Docs para todos los tipos y miembros de tipo agregados:

<since version="Gtk# 2.4" />
El Navegador de Documentación de Mono y monodocs2html usarán este elemento para especificar en qué versión se agregó un miembro.
-tipo:TIPO
Solo crear/actualizar documentación para el tipo TIPO.
-actualizar-a:RUTA
Al actualizar la documentación, escribir los archivos de documentación actualizados en el directorio RUTA.
-V, -version
Mostrar información de versión y licencia.

DESCRIPCIÓN

monodocer ha sido obsoleto por mdoc(1). Consulte la página del manual mdoc-update(1).

monodocer es un programa que crea plantillas de documentación XML en el Formato de Documentación ECMA. No se basa en la documentación encontrada dentro del código fuente.

Las ventajas son:

*
Legibilidad del código. Una buena documentación es frecuentemente (a) verbosa y (b) llena de ejemplos. (A modo de comparación, compare la documentación del Framework .NET de Microsoft, que a menudo es una página o más de documentación para cada miembro, con la documentación de JavaDoc, que a menudo puede ser una oración por cada miembro).

Insertar buena documentación en el código fuente puede inflar frecuentemente el archivo fuente, ya que la documentación puede ser más larga que el método real que se está documentando.

*
Localización. Los formatos de documentación en el código fuente (como /doc) no tienen soporte para múltiples idiomas humanos. Si necesita soportar más de un idioma humano con fines de documentación, monodocer es útil ya que permite que cada idioma obtenga su propio directorio, y monodocer puede agregar tipos/miembros para cada directorio de documentación separado.
*
Administración. No es inusual tener equipos de documentación y desarrollo separados. También es posible que el equipo de documentación tenga una experiencia mínima con el lenguaje de programación utilizado. En tales circunstancias, la documentación en línea no es deseable ya que el equipo de documentación podría insertar inadvertidamente un error en el código fuente mientras actualiza la documentación. Alternativamente, es posible que no desee que el equipo de documentación tenga acceso al código fuente por razones de seguridad. monodocer permite que la documentación se mantenga *completamente* separada y distinta del código fuente utilizado para crear el ensamblado.

Para convertir la documentación de monodocer en algo que pueda ser consumido por el Navegador de Documentación de Mono (el navegador de ayuda de escritorio, o la interfaz web para él) es necesario compilar la documentación en un formato empaquetado. Esto se hace con la herramienta mdassembler, por ejemplo, podría usar esta cadena de herramientas de esta manera:

$ monodocer -ensamblado:MyWidgets -ruta:generated_docs
$ mdassembler --ecma generated_docs -out:MyWidgets
Lo anterior generaría un MyWidgets.zip y un MyWidgets.tree que luego podrían instalarse en el sistema. Además de los dos archivos (.zip y .tree) debe proporcionar un archivo .sources que describe dónde se debe vincular la documentación en el sistema de ayuda, es un archivo XML muy simple, como este: 
<?xml version="1.0"?>
<monodoc>
  <source provider="ecma" basefile="MyWidgets" path="classlib-gnome"/>
</monodoc>
El archivo de configuración anterior describe que la documentación está en formato ECMA (la versión compilada) que el nombre base del archivo es MyWidgets y que se vinculará en la parte "classlib-gnome" del árbol. Si desea ver los diversos nodos definidos en la documentación, puede mirar el archivo monodoc.xml que generalmente se instala en /usr/lib/monodoc/monodoc.xml.

Una vez que tenga todos sus archivos (.zip, .tree y .sources), puede instalarlos en el sistema con el siguiente comando:

        $ cp MyWidgets.tree MyWidgets.zip MyWidgets.source `pkg-config monodoc --variable sourcesdir`
Lo anterior copiará los archivos al directorio que Monodoc ha registrado (es posible que necesite permisos de root para hacerlo). El directorio real es devuelto por la invocación de pkg-config.

FORMATO ID CADENA

Los ID de cadena se utilizan para referirse a un tipo o miembro de un tipo. Los ID de cadena se documentan en ECMA-334 3ª Edición, Anexo E.3.1. Consisten en un prefijo de tipo de miembro, el nombre completo del tipo (espacio de nombres + nombre, separados por '.'), posiblemente seguido por el nombre del miembro y otra información.

Prefijos de tipo de miembro:

E:
El ID de cadena se refiere a un evento. El nombre del evento sigue al nombre del tipo: E:System.AppDomain.AssemblyLoad
F:
El ID de cadena se refiere a un campo. El nombre del campo sigue al nombre del tipo: F:System.Runtime.InteropServices.DllImportAttribute.SetLastError
M:
Se refiere a un constructor o método. Los constructores agregan .ctor al nombre del tipo, mientras que los métodos agregan el nombre del método (con un recuento opcional del número de parámetros genéricos).

Si el constructor o método toman argumentos, estos se enumeran entre paréntesis después del nombre del constructor/método:

DOCUMENTATION FORMAT

The monodocer utility supports the XML documentation format used by the C# compiler and widely adopted by the .NET community.

The following tags are supported:

<code>TEXT</code>
Used to mark up text as code. This is usually rendered in a fixed-width font.
<example>EXAMPLE</example>
Contains example code for a member. Usually rendered in a fixed-width font, and often includes <para/> tags.
<exception cref="EXEPTION_TYPE">DESCRIPTION</exception>
Used to document an exception thrown by a method. EXEPTION_TYPE should be the name of the exception class (e.g. System.ArgumentNullException). DESCRIPTION is a short description of the condition that causes the exception to be thrown.
<list type="TYPE"><listheader>...</listheader><item>...</item></list>
Allows the creation of lists. The supported types are:
bullet
A bulleted list.
number
A numbered list.
table
A table, with each item being a row.
<listheader>
Contains the header row for a table list.
<item>
An item in a list.
<para>TEXT</para>
Used to create paragraphs within documentation tags. Usually rendered with a blank line before and after the text.
<param name="NAME">DESCRIPTION</param>

Used to describe a method parameter. NAME is the name of the parameter, and DESCRIPTION is a description of the parameter.

<param name="count">The number of items to add</param>
<paramref name="NAME"/>
Used to indicate that a word is a parameter name, for use within other text blocks (e.g. within <para/> ). 
<para>The value of <paramref name="count" /> must be positive.</para>
<permission cref="PERMISSION_TYPE">DESCRIPTION</permission>
Used to document code access security permissions for a type or member. PERMISSION_TYPE should be the name of the permission class.
<remarks>DESCRIPTION</remarks>

Provides additional information about a type or member, beyond the <summary/>. This usually contains more detailed explanations, discussions of usage, or other relevant notes.

<remarks>
  This method is thread-safe.
</remarks>
<returns>DESCRIPTION</returns>

Used to describe the return value of a method.

<returns>A <see cref="T:System.String" /> representing the formatted
string.</returns>
<see cref="MEMBER_NAME"/>

Used to generate an inline reference to another type or member. MEMBER_NAME should be the fully qualified name of the type or member. This tag is often nested within other tags, such as <para/>, <summary/>, etc. Use <seealso/> to specify a link from within text.

<seealso cref="P:System.Exception.Message" />
<since version="VERSION" />

<since/> is a top-level element, and should be nested directly under the <Docs/> element.

Permits specification of which version introduced the specified type or member.

<since version="Gtk# 2.4" />
<summary>DESCRIPTION</summary>

<summary/> is a top-level element, and should be nested directly under the <Docs/> element.

Provides a (brief!) overview about a type or type member.

This is usually displayed as part of a class declaration, and should be a reasonably short description of the type/member. Use <remarks/> for more detailed information.

<typeparam name="NAME">DESCRPITION</typeparam>
<typeparam/> is a top-level element, and should be nested directly under the <Docs/> element.

This is used to describe type parameter for a generic type or generic method.

NAME is the name of the type parameter, while DESCRIPTION contains a description of the parameter (what it's used for, what restrictions it must meet, etc.).

<typeparam name="T">The type of the underlying collection</typeparam>
<typeparamref>
Used to indicate that a word is a type parameter, for use within other text blocks (e.g. within <para/> ). 
<para>If <typeparamref name="T" /> is a struct, then...</para>
<value>DESCRIPTION</value>
<value/> is a top-level element, and should be nested directly under the <Docs/> element.

Allows a property to be described.

<value>
  A <see cref="T:System.String" /> containing a widget name.
</value>
