mlock(2) Manual de Llamadas al Sistema mlock(2)

NOMBRE

mlock, mlock2, munlock, mlockall, munlockall - bloquear y desbloquear memoria

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

SINOPSIS

#include <sys/mman.h>
int mlock(const void *addr, size_t len);
int mlock2(const void *addr, size_t len, unsigned int flags);
int munlock(const void *addr, size_t len);
int mlockall(int flags);
int munlockall(void);

DESCRIPCIÓN

mlock(), mlock2() y mlockall() bloquean parte o todo el espacio de direcciones virtual del proceso que llama en la RAM, impidiendo que esa memoria se paginada al área de intercambio. mlock ha sido deprecado y en su lugar se recomienda usar mlock2().

munlock() y munlockall() realizan la operación inversa, desbloqueando parte o todo el espacio de direcciones virtual del proceso que llama, de modo que las páginas en el rango de direcciones virtual especificado puedan ser intercambiadas nuevamente si es requerido por el gestor de memoria del kernel.

El bloqueo y desbloqueo de memoria se realizan en unidades de páginas completas.

mlock(), mlock2(), y munlock()

mlock() bloquea las páginas en el rango de direcciones que comienza en addr y continúa durante len bytes. Todas las páginas que contienen una parte del rango de direcciones especificado se garantizan que estarán residentes en RAM cuando la llamada retorne exitosamente; las páginas se garantizan que permanecerán en RAM hasta que se desbloqueen posteriormente.

mlock2() también bloquea las páginas en el rango especificado que comienza en addr y continúa durante len bytes. Sin embargo, el estado de las páginas contenidas en ese rango después de que la llamada retorne exitosamente dependerá del valor en el argumento flags.

El argumento flags puede ser 0 o la siguiente constante:

MLOCK_ONFAULT
Bloquea las páginas que están actualmente residentes y marca todo el rango para que las páginas restantes no residentes se bloqueen cuando se pueblen por una falla de página.

Si flags es 0, mlock2() se comporta exactamente igual que mlock().

munlock() desbloquea las páginas en el rango de direcciones que comienza en addr y continúa durante len bytes. Después de esta llamada, todas las páginas que contienen una parte del rango de memoria especificado pueden ser movidas nuevamente al espacio de intercambio externo por el kernel.

mlockall() y munlockall()

mlockall() bloquea todas las páginas mapeadas en el espacio de direcciones del proceso que llama. Esto incluye las páginas del código, datos y segmento de pila, así como bibliotecas compartidas, datos del kernel en espacio de usuario, memoria compartida y archivos mapeados en memoria. Se garantiza que todas las páginas mapeadas estarán residentes en RAM cuando la llamada retorne exitosamente; se garantiza que las páginas permanecerán en RAM hasta que se desbloqueen posteriormente.

El argumento flags se construye como el OR bit a bit de una o más de las siguientes constantes:

MCL_CURRENT
Bloquea todas las páginas que están actualmente mapeadas en el espacio de direcciones del proceso.
MCL_FUTURE
Bloquea todas las páginas que se mapearán en el espacio de direcciones del proceso en el futuro. Estas podrían ser, por ejemplo, nuevas páginas requeridas por un heap y stack en crecimiento, así como nuevos archivos mapeados en memoria o regiones de memoria compartida.
MCL_ONFAULT (desde Linux 4.4)
Usado junto con MCL_CURRENT, MCL_FUTURE, o ambos. Marca todas las páginas actuales (con MCL_CURRENT) o futuras (con MCL_FUTURE) para bloquear las páginas cuando se cargan por falla de página. Cuando se usa con MCL_CURRENT, todas las páginas presentes se bloquean, pero mlockall() no cargará páginas no presentes. Cuando se usa con MCL_FUTURE, todos los mapeos futuros se marcarán para bloquear las páginas cuando se carguen, pero no se poblarán al crear el mapeo. MCL_ONFAULT debe usarse con MCL_CURRENT o MCL_FUTURE o ambos.

Si se ha especificado MCL_FUTURE, entonces una llamada al sistema posterior (por ejemplo, mmap(2), sbrk(2), malloc(3)), puede fallar si causa que el número de bytes bloqueados exceda el máximo permitido (ver abajo). En las mismas circunstancias, el crecimiento del stack también puede fallar: el kernel denegará la expansión del stack y enviará una señal SIGSEGV al proceso.

munlockall() desbloquea todas las páginas mapeadas en el espacio de direcciones del proceso que llama.

VALOR DE RETORNO

Al éxito, estas llamadas al sistema devuelven 0. En caso de error, devuelven -1, se establece errno para indicar el error, y no se realizan cambios en ningún bloqueo en el espacio de direcciones del proceso.

ERRORES

EAGAIN
(mlock(), mlock2(), y munlock()) Parte o todo el rango de direcciones especificado no pudo ser bloqueado.
EINVAL
(mlock(), mlock2(), y munlock()) El resultado de la suma addr+len fue menor que addr (por ejemplo, la suma pudo haber resultado en un desbordamiento).
EINVAL
(mlock2()) Se especificaron flags desconocidos.
EINVAL
(mlockall()) Se especificaron flags desconocidos o se especificó MCL_ONFAULT sin MCL_FUTURE ni MCL_CURRENT.
EINVAL
(No en Linux) addr no era un múltiplo del tamaño de página.
ENOMEM
(mlock(), mlock2(), y munlock()) Parte del rango de direcciones especificado no corresponde a páginas mapeadas en el espacio de direcciones del proceso.
ENOMEM
(mlock(), mlock2(), y munlock()) Bloquear o desbloquear una región resultaría en que el número total de mapeos con atributos distintos (por ejemplo, bloqueados vs. desbloqueados) exceda el máximo permitido (Por ejemplo, desbloquear un rango en el medio de un mapeo actualmente bloqueado resultaría en tres mapeos: dos bloqueados en cada extremo y un mapeo desbloqueado en el medio).
ENOMEM
(Linux 2.6.9 y posterior) el llamador tenía un límite de recursos blando RLIMIT_MEMLOCK distinto de cero, pero intentó bloquear más memoria de la que permitía el límite. Este límite no se aplica si el proceso está privilegiado (CAP_IPC_LOCK).
ENOMEM
(Linux 2.4 y anterior) el proceso que llama intentó bloquear más de la mitad de la RAM.
EPERM
El llamador no tiene privilegios, pero necesita privilegios (CAP_IPC_LOCK) para realizar la operación solicitada.
EPERM
(munlockall()) (Linux 2.6.8 y anterior) El llamador no tenía privilegios (CAP_IPC_LOCK).

VERSIONES

Linux

En Linux, mlock(), mlock2(), y munlock() redondean automáticamente addr hacia abajo al límite de página más cercano. Sin embargo, la especificación POSIX.1 de mlock() y munlock() permite que una implementación requiera que addr esté alineado a página, por lo que las aplicaciones portables deben asegurarse de esto.

munlockall(2) — Arch Linux man pages

NAME

munlockall, mlockall, mlock, munlock, mlock2 — lock or unlock memory

LIBRARY

Real-time extensions (libc, -lrt)

SYNOPSIS

#include <sys/mman.h>

int mlockall(int flags);
int munlockall(void);
int mlock(const void *addr, size_t len);
int munlock(const void *addr, size_t len);
int mlock2(const void *addr, size_t len, int flags);

DESCRIPTION

The functions mlockall() and munlockall() lock or unlock all of the calling process's accessible pages. The behavior of these functions is determined by the flags argument to mlockall():

MCL_CURRENT
Lock all pages that are currently mapped for the calling process. This includes memory that is mapped via mmap(2), anonymous memory mappings, and the stack and heap. Pages that are mapped with the MAP_SHARED flag will be locked, and pages that are mapped with the MAP_PRIVATE flag will also be locked.
MCL_FUTURE
Lock pages that will be mapped in the future for the calling process. This applies to anonymous memory mappings, stack, and heap. Memory mappings created using mmap(2) with this flag set will also be locked.
MCL_ONFAULT
Lock pages only when they are accessed (i.e., when a page fault occurs). This flag can be combined with MCL_CURRENT and MCL_FUTURE. If MCL_ONFAULT is specified, then memory is locked only when it is accessed. If MCL_ONFAULT is not specified, then all pages that are currently mapped or will be mapped in the future (depending on whether MCL_CURRENT and MCL_FUTURE are specified) are locked immediately.

The mlockall() function locks all pages that are currently mapped for the calling process (using MCL_CURRENT) and that will be mapped in the future (using MCL_FUTURE). The flags argument is the bitwise OR of one or more of these flags. If the flags argument is 0, it is treated as MCL_CURRENT.

The munlockall() function unlocks all pages that were locked by mlockall().

The functions mlock() and munlock() lock and unlock, respectively, the pages in the range [addr, addr+len-1]. The range must be page-aligned, and the length must be a multiple of the system page size. mlock() locks the specified pages in RAM, preventing them from being swapped out to disk. munlock() unlocks the specified pages.

The mlock2() function is similar to mlock(), but supports an additional flags argument. Currently, the only flag supported is MLOCK_ONFAULT, which behaves like the MCL_ONFAULT flag for mlockall().

RETURN VALUE

On success, mlockall(), munlockall(), mlock(), munlock(), and mlock2() return 0. On failure, they return -1, and errno is set to indicate the error.

ERRORS

EAGAIN
Not enough memory is available to perform the requested operation.
EFAULT
addr is not a valid address for this process.
EINVAL
mlock(), munlock(), or mlock2() was called with arguments that are not page-aligned or whose length is not a multiple of the page size. Or, an unknown flag was specified in flags.
EPERM
The calling process does not have the CAP_IPC_LOCK capability, and the operation would require privilege.
ENOMEM
Not enough memory is available to perform the requested operation. (This is a synonym for EAGAIN on Linux.)

VERSIONS

The proc(5) file /proc/PID/smaps shows how many kilobytes of memory the process with ID PID has locked using mlock(), mlock2(), mlockall(), and mmap(2) MAP_LOCKED.

STANDARDS

On POSIX systems on which mlock() and munlock() are available, _POSIX_MEMLOCK_RANGE is defined in <unistd.h> and the number of bytes in a page can be determined from the constant PAGESIZE (if defined) in <limits.h> or by calling sysconf(_SC_PAGESIZE).

On POSIX systems on which mlockall() and munlockall() are available, _POSIX_MEMLOCK is defined in <unistd.h> to a value greater than 0. (See also sysconf(3).)

NOTES

Memory locking has two main applications: real-time algorithms and high-security data processing. Real-time applications require deterministic timing, and, like scheduling, paging is one major cause of unexpected program execution delays. Real-time applications will usually also switch to a real-time scheduler with sched_setscheduler(2). Cryptographic security software often handles critical bytes like passwords or secret keys as data structures. As a result of paging, these secrets could be transferred onto a persistent swap store medium, where they might be accessible to the enemy long after the security software has erased the secrets in RAM and terminated. (But be aware that the suspend mode on laptops and some desktop computers will save a copy of the system's RAM to disk, regardless of memory locks.)

Real-time processes that are using mlockall() to prevent delays on page faults should reserve enough locked stack pages before entering the time-critical section, so that no page fault can be caused by function calls. This can be achieved by calling a function that allocates a sufficiently large automatic variable (an array) and writes to the memory occupied by this array in order to touch these stack pages. This way, enough pages will be mapped for the stack and can be locked into RAM. The dummy writes ensure that not even copy-on-write page faults can occur in the critical section.

Memory locks are not inherited by a child created via fork(2) and are automatically removed (unlocked) during an execve(2) or when the process terminates. The mlockall() MCL_FUTURE and MCL_FUTURE | MCL_ONFAULT settings are not inherited by a child created via fork(2) and are cleared during an execve(2).

Note that fork(2) will prepare the address space for a copy-on-write operation. The consequence is that any write access that follows will cause a page fault that in turn may cause high latencies for a real-time process. Therefore, it is crucial not to invoke fork(2) after an mlockall() or mlock() operation—not even from a thread which runs at a low priority within a process which also has a thread running at elevated priority.

The memory lock on an address range is automatically removed if the address range is unmapped via munmap(2).

Memory locks do not stack, that is, pages which have been locked several times by calls to mlock(), mlock2(), or mlockall() will be unlocked by a single call to munlock() for the corresponding range or by munlockall(). Pages which are mapped to several locations or by several processes stay locked into RAM as long as they are locked at least at one location or by at least one process.

If a call to mlockall() which uses the MCL_FUTURE flag is followed by another call that does not specify this flag, the changes made by the MCL_FUTURE call will be lost.

The mlock2() MLOCK_ONFAULT flag and the mlockall() MCL_ONFAULT flag allow efficient memory locking for applications that deal with large mappings where only a (small) portion of pages in the mapping are touched. In such cases, locking all of the pages in a mapping would incur a significant penalty for memory locking.

Limits and permissions

In Linux 2.6.8 and earlier, a process must be privileged (CAP_IPC_LOCK) in order to lock memory and the RLIMIT_MEMLOCK soft resource limit defines a limit on how much memory the process may lock.

Since Linux 2.6.9, no limits are placed on the amount of memory that a privileged process can lock and the RLIMIT_MEMLOCK soft resource limit instead defines a limit on how much memory an unprivileged process may lock.

BUGS

In Linux 4.8 and earlier, a bug in the kernel's accounting of locked memory for unprivileged processes (i.e., without CAP_IPC_LOCK) meant that if the region specified by addr and size overlapped an existing lock, then the already locked bytes in the overlapping region were counted twice when checking against the limit. Such double accounting could incorrectly calculate a "total locked memory" value for the process that exceeded the RLIMIT_MEMLOCK limit, with the result that mlock() and mlock2() would fail on requests that should have succeeded. This bug was fixed in Linux 4.9.

In Linux 2.4 series of kernels up to and including Linux 2.4.17, a bug caused the mlockall() MCL_FUTURE flag to be inherited across a fork(2). This was rectified in Linux 2.4.18.

Since Linux 2.6.9, if a privileged process calls mlockall(MCL_FUTURE) and later drops privileges (loses the CAP_IPC_LOCK capability by, for example, setting its effective UID to a nonzero value), then subsequent memory allocations (e.g., mmap(2), brk(2)) will fail if the RLIMIT_MEMLOCK resource limit is encountered.
