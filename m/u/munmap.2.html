mmap(2) Manual de llamadas al sistema mmap(2)

NOMBRE

mmap, munmap - mapear o desmapear archivos o dispositivos en memoria

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

SINOPSIS

#include <sys/mman.h>
void *mmap(size_t length;
           void addr[length], size_t length, int prot, int flags,
           int fd, off_t offset);
int munmap(size_t length;
           void addr[length], size_t length);

Ver VERSIONS para información sobre los requisitos de las macros de prueba de características.

DESCRIPCIÓN

mmap() crea un nuevo mapeo en el espacio de direcciones virtual del proceso que llama. La dirección de inicio del nuevo mapeo se especifica en addr. El argumento length especifica la longitud del mapeo (que debe ser mayor que 0).

Si addr es NULL, entonces el kernel elige la dirección (alineada en página) en la que crear el mapeo; este es el método más portable de crear un nuevo mapeo. Si addr no es NULL, entonces el kernel lo toma como una sugerencia sobre dónde colocar el mapeo; en Linux, el kernel elegirá un límite de página cercano (pero siempre mayor o igual al valor especificado por /proc/sys/vm/mmap_min_addr) e intentará crear el mapeo allí. Si ya existe otro mapeo allí, el kernel elegirá una nueva dirección que puede o no depender de la sugerencia. La dirección del nuevo mapeo se devuelve como resultado de la llamada.

El contenido de un mapeo de archivo (en contraposición a un mapeo anónimo; ver MAP_ANONYMOUS abajo), se inicializa usando length bytes comenzando en el desplazamiento offset en el archivo (u otro objeto) referido por el descriptor de archivo fd. offset debe ser un múltiplo del tamaño de página devuelto por sysconf(_SC_PAGE_SIZE).

Después de que la llamada mmap() haya devuelto, el descriptor de archivo, fd, puede cerrarse inmediatamente sin invalidar el mapeo.

El argumento prot describe la protección de memoria deseada del mapeo (y no debe entrar en conflicto con el modo de apertura del archivo). Es PROT_NONE o el OR bit a bit de una o más de las siguientes banderas:

PROT_EXEC
Las páginas pueden ser ejecutadas.
PROT_READ
Las páginas pueden ser leídas.
PROT_WRITE
Las páginas pueden ser escritas.
PROT_NONE
Las páginas no pueden ser accedidas.

El argumento flags

El argumento flags determina si las actualizaciones al mapeo son visibles para otros procesos que mapean la misma región, y si las actualizaciones se propagan al archivo subyacente. Este comportamiento se determina incluyendo exactamente uno de los siguientes valores en flags:

MAP_SHARED
Compartir este mapeo. Las actualizaciones al mapeo son visibles para otros procesos que mapean la misma región y (en el caso de mapeos respaldados por archivos) se propagan al archivo subyacente. (Para controlar precisamente cuándo se propagan las actualizaciones al archivo subyacente se requiere el uso de msync(2)).
MAP_SHARED_VALIDATE (desde Linux 4.15)
Esta bandera proporciona el mismo comportamiento que MAP_SHARED, excepto que los mapeos MAP_SHARED ignoran las banderas desconocidas en flags. Por el contrario, al crear un mapeo usando MAP_SHARED_VALIDATE, el kernel verifica que todas las banderas pasadas sean conocidas y falla el mapeo con el error EOPNOTSUPP para banderas desconocidas. Este tipo de mapeo también es requerido para poder usar algunas banderas de mapeo (por ejemplo, MAP_SYNC).
MAP_PRIVATE
Crear un mapeo privado de copia en escritura. Las actualizaciones al mapeo no son visibles para otros procesos que mapean el mismo archivo, y no se propagan al archivo subyacente. No se especifica si los cambios realizados en el archivo después de la llamada mmap() son visibles en la región mapeada.

Tanto MAP_SHARED como MAP_PRIVATE se describen en POSIX.1-2001 y POSIX.1-2008. MAP_SHARED_VALIDATE es una extensión de Linux.

Además, cero o más de los siguientes valores pueden ser combinados (OR) en flags:

MAP_32BIT (desde Linux 2.4.20, 2.6)
Colocar el mapeo en los primeros 2 Gigabytes del espacio de direcciones del proceso. Esta bandera solo es compatible en x86-64, para programas de 64 bits. Se añadió para permitir que las pilas de hilos se asignen en algún lugar dentro de los primeros 2 GB de memoria, para mejorar el rendimiento del cambio de contexto en algunos procesadores de 64 bits tempranos. Los procesadores x86-64 modernos ya no tienen este problema de rendimiento, por lo que el uso de esta bandera no es necesario en esos sistemas. La bandera MAP_32BIT se ignora cuando se establece MAP_FIXED.
MAP_ANON
Sinónimo de MAP_ANONYMOUS; proporcionado para compatibilidad con otras implementaciones.
MAP_ANONYMOUS
El mapeo no está respaldado por ningún archivo; su contenido se inicializa a cero. El argumento fd se ignora; sin embargo, algunas implementaciones requieren que fd sea -1 si se especifica MAP_ANONYMOUS (o MAP_ANON), y las aplicaciones portables deben asegurarse de ello. El argumento offset debe ser cero. El soporte para MAP_ANONYMOUS en conjunción con MAP_SHARED se añadió en Linux 2.4.
MAP_DENYWRITE
Esta bandera se ignora. (Hace mucho tiempo —Linux 2.0 y anteriores— indicaba que los intentos de escribir en el archivo subyacente debían fallar con ETXTBSY. Pero esto era una fuente de ataques de denegación de servicio).
MAP_EXECUTABLE
Esta bandera se ignora.
MAP_FILE
Bandera de compatibilidad. Ignorada.
MAP_FIXED
No interpretar addr como una sugerencia: colocar el mapeo en exactamente esa dirección. addr debe estar debidamente alineado: para la mayoría de las arquitecturas, un múltiplo del tamaño de página es suficiente; sin embargo, algunas arquitecturas pueden imponer restricciones adicionales. Si la región de memoria especificada por addr y length se superpone con páginas de cualquier mapeo existente, entonces la parte superpuesta de los mapeos existentes será descartada. Si la dirección especificada no se puede usar, mmap() fallará.
El software que aspira a ser portable debe usar la bandera MAP_FIXED con cuidado, teniendo en cuenta que la disposición exacta de los mapeos de memoria de un proceso puede cambiar significativamente entre versiones de Linux, versiones de la biblioteca C y versiones del sistema operativo. ¡Lea atentamente la discusión de esta bandera en NOTAS!
MAP_FIXED_NOREPLACE (desde Linux 4.17)
Esta bandera proporciona un comportamiento similar a MAP_FIXED con respecto a la aplicación de addr, pero difiere en que MAP_FIXED_NOREPLACE nunca sobrescribe un rango mapeado preexistente. Si el rango solicitado colisionara con un mapeo existente, entonces esta llamada falla con el error EEXIST. Por lo tanto, esta bandera puede utilizarse como una forma de intentar mapear un rango de direcciones de forma atómica (con respecto a otros hilos): un hilo tendrá éxito; todos los demás informarán de un fallo.
Tenga en cuenta que los kernels más antiguos que no reconocen la bandera MAP_FIXED_NOREPLACE típicamente (al detectar una colisión con un mapeo preexistente) recurrirán a un tipo de comportamiento "no MAP_FIXED": devolverán una dirección diferente a la solicitada. Por lo tanto, el software compatible con versiones anteriores debe verificar la dirección devuelta contra la dirección solicitada.
MAP_GR

MAP_BELOW

This flag is used for stacks. It indicates to the kernel virtual memory system that the mapping should extend downward in memory. The return address is one page lower than the memory area that is actually created in the process's virtual address space. Touching an address in the "guard" page below the mapping will cause the mapping to grow by a page. This growth can be repeated until the mapping grows to within a page of the high end of the next lower mapping, at which point touching the "guard" page will result in a SIGSEGV signal.

MAP_HUGETLB (since Linux 2.6.32)

Allocate the mapping using "huge" pages. See the Linux kernel source file Documentation/admin-guide/mm/hugetlbpage.rst for further information, as well as NOTES, below.

MAP_HUGE_2MB

MAP_HUGE_1GB (since Linux 3.8)

Used in conjunction with MAP_HUGETLB to select alternative hugetlb page sizes (respectively, 2 MB and 1 GB) on systems that support multiple hugetlb page sizes.

More generally, the desired huge page size can be configured by encoding the base-2 logarithm of the desired page size in the six bits at the offset MAP_HUGE_SHIFT. (A value of zero in this bit field provides the default huge page size; the default huge page size can be discovered via the Hugepagesize field exposed by /proc/meminfo.) Thus, the above two constants are defined as:

#define MAP_HUGE_2MB    (21 << MAP_HUGE_SHIFT)
#define MAP_HUGE_1GB    (30 << MAP_HUGE_SHIFT)

The range of huge page sizes that are supported by the system can be discovered by listing the subdirectories in /sys/kernel/mm/hugepages.

MAP_LOCKED (since Linux 2.5.37)

Mark the mapped region to be locked in the same way as mlock(2). This implementation will try to populate (prefault) the whole range but the mmap() call doesn't fail with ENOMEM if this fails. Therefore major faults might happen later on. So the semantic is not as strong as mlock(2). One should use mmap() plus mlock(2) when major faults are not acceptable after the initialization of the mapping. The MAP_LOCKED flag is ignored in older kernels.

MAP_NONBLOCK (since Linux 2.5.46)

This flag is meaningful only in conjunction with MAP_POPULATE. Don't perform read-ahead: create page tables entries only for pages that are already present in RAM. Since Linux 2.6.23, this flag causes MAP_POPULATE to do nothing. One day, the combination of MAP_POPULATE and MAP_NONBLOCK may be reimplemented.

MAP_NORESERVE

Do not reserve swap space for this mapping. When swap space is reserved, one has the guarantee that it is possible to modify the mapping. When swap space is not reserved one might get SIGSEGV upon a write if no physical memory is available. See also the discussion of the file /proc/sys/vm/overcommit_memory in proc_sys_vm(5). Before Linux 2.6, this flag had effect only for private writable mappings.

MAP_POPULATE (since Linux 2.5.46)

Populate (prefault) page tables for a mapping. For a file mapping, this causes read-ahead on the file. This will help to reduce blocking on page faults later. The mmap() call doesn't fail if the mapping cannot be populated (for example, due to limitations on the number of mapped huge pages when using MAP_HUGETLB). Support for MAP_POPULATE in conjunction with private mappings was added in Linux 2.6.23.

MAP_STACK (since Linux 2.6.27)

Allocate the mapping at an address suitable for a process or thread stack.

This flag is currently a no-op on Linux. However, by employing this flag, applications can ensure that they transparently obtain support if the flag is implemented in the future. Thus, it is used in the glibc threading implementation to allow for the fact that some architectures may (later) require special treatment for stack allocations. A further reason to employ this flag is portability: MAP_STACK exists (and has an effect) on some other systems (e.g., some of the BSDs).

MAP_SYNC (since Linux 4.15)

This flag is available only with the MAP_SHARED_VALIDATE mapping type; mappings of type MAP_SHARED will silently ignore this flag. This flag is supported only for files supporting DAX (direct mapping of persistent memory). For other files, creating a mapping with this flag results in an EOPNOTSUPP error.

Shared file mappings with this flag provide the guarantee that while some memory is mapped writable in the address space of the process, it will be visible in the same file at the same offset even after the system crashes or is rebooted. In conjunction with the use of appropriate CPU instructions, this provides users of such mappings with a more efficient way of making data modifications persistent.

MAP_UNINITIALIZED (since Linux 2.6.33)

Don't clear anonymous pages. This flag is intended to improve performance on embedded devices. This flag is honored only if the kernel was configured with the CONFIG_MMAP_ALLOW_UNINITIALIZED option. Because of the security implications, that option is normally enabled only on embedded devices (i.e., devices where one has complete control of the contents of user memory).

Of the above flags, only MAP_FIXED is specified in POSIX.1-2001 and POSIX.1-2008. However, most systems also support MAP_ANONYMOUS (or its synonym MAP_ANON).

munmap()

The munmap() system call deletes the mappings for the specified address range, and causes further references to addresses within the range to generate invalid memory references. The region is also automatically unmapped when the process is terminated. On the other hand, closing the file descriptor does not unmap the region.

The address addr must be a multiple of the page size (but length need not be). All pages containing a part of the indicated range are unmapped, and subsequent references to these pages will generate SIGSEGV. It is not an error if the indicated range does not contain any mapped pages.

RETURN VALUE

On success, mmap() returns a pointer to the mapped area. On error, the value MAP_FAILED (that is, (void *) -1) is returned, and errno is set to indicate the error.

On success, munmap() returns 0. On failure, it returns -1, and errno is set to indicate the error (probably to EINVAL).

SYNOPSIS

#include <sys/mman.h>

void *mmap(void *addr, size_t length, int prot, int flags,
              int fd, off_t offset);
int munmap(void *addr, size_t length);

DESCRIPTION

The mmap() function establishes a new mapping in the virtual address space of the calling process. The to-be-mapped bytes are described by the range [addr, addr + length). When all of the following conditions are true, the mapped region takes the file represented by the file descriptor fd as its backing store:

  • addr is NULL (or 0).
  • flags contains MAP_ANONYMOUS (or MAP_ANON).

The addr argument is a hint concerning the suggested memory address for the new mapping; that is, the kernel is free to choose the actual address anywhere in the process's address space. The actual address of the mapping is returned as the result of the call.

A null pointer (NULL) passed as the addr argument indicates that the system should choose the address at which to create the mapping.

The length argument specifies the length, in bytes, of the mapping.

The prot argument (for "protection") describes the desired memory protection of the mapping. It is either the sum of the following bitwise ORed values, or PROT_NONE (indicating that the memory cannot be accessed at all).

  • PROT_EXEC: Executable pages.
  • PROT_LOGICAL_ADDRESS_TRANSLATION: Address translation is not performed for pages in this mapping.
  • PROT_NONE: Pages cannot be accessed.
  • PROT_READ: Pages can be read.
  • PROT_WRITE: Pages can be written.

The flags argument determines which of the following (or other) values are set for the mapping. The value is the bitwise OR of several options:

  • MAP_32BIT: (Since Linux) Map the mapping using 32-bit addresses, so that the address is restricted to the lower 2 GiB of the address space. This is useful only on 64-bit systems for the performance benefits of 32-bit pointers.
  • MAP_ANON: The mapping is not backed by any object. The file descriptor must be -1. Anonymous mappings are initialized to zero. This flag is required for a shared anonymous mapping to be preserved across calls to fork(2).
  • MAP_ANONYMOUS: Synonym for MAP_ANON.
  • MAP_COPY: Deprecated.
  • MAP_DENYWRITE: Do not permit data modification to the object directly via another file descriptor that refers to the same file.
  • MAP_EXECUTABLE: Indicate that the pages in the mapping may be executed.
  • MAP_FILE: The mapping is backed by a regular file (as opposed to an anonymous mapping). This flag is the default if neither MAP_ANONYMOUS nor MAP_FILE is specified.
  • MAP_FIXED: Do not allow the system to choose the address. Addr must be a valid, non-NULL address, and the mapping is created at exactly that address. The previous mapping at that address is unmapped. MAP_FIXED is dangerous, and its use is discouraged. See NOTES.
  • MAP_FIXED_NOREPLACE: (Since Linux 4.17) Do not allow the system to choose the address. Addr must be a valid, non-NULL address. If the address range specified by addr and length is already mapped, the call fails with the error EEXIST and the existing mapping is left unchanged. If the address range is not already mapped, the mapping is created at exactly addr. This flag is intended to provide a safe way to create a mapping at a fixed address in a multithreaded program.
  • MAP_FORCE: (Since Linux) Deprecated.
  • MAP_GROWSDOWN: Indicate that the mapping may grow downwards. This is used for stack growth.
  • MAP_HUGETLB: (Since Linux) Allocate pages of a huge page size (if supported and configured). The size of huge pages is architecture-dependent. See the Linux kernel documentation for details.
  • MAP_INHERIT: (Since Linux) Mark the mapping as inheritable across fork(2). This is the default behavior for shared anonymous mappings.
  • MAP_LOCKED: Lock the mapping in memory. See mlock(2).
  • MAP_NONBLOCK: (Since Linux) Do not populate the mapping page by page. Instead, the system may initialize the mapping lazily.
  • MAP_NORESERVE: Do not reserve disk space for the mapping.
  • MAP_POPULATE: (Since Linux 2.6.23) Populate the page table entries for a mapping. As a side effect of this flag, the pages are also initialized, causing disk I/O to be performed.
  • MAP_SHARED: Share the mapping. Writes to the mapping are visible to other processes mapping the same region, and are carried through to the underlying file.
  • MAP_SHARED_VALIDATE: (Since Linux 4.17) Similar to MAP_SHARED, but requires that the caller validates that the mapping is safe. This is intended for use with shared memory object mappings and provides some protection against certain kinds of race conditions.
  • MAP_PRIVATE: Create a private copy-on-write mapping. Writes to the mapping are not visible to other processes mapping the same region, and are not carried through to the underlying file.
  • MAP_STACK: (Since Linux) Allocate the mapping on the stack.

The mapping is created in the range specified by addr and length. The value of addr is usually 0, so the kernel chooses the address. The actual address of the mapping is returned. If addr is not 0, then MAP_FIXED must be set in flags, and the mapping will be created at exactly the address specified by addr.

The fd argument is the file descriptor of the object to be mapped. If flags includes MAP_ANONYMOUS, then fd must be -1.

The offset argument is the offset in the file or shared memory object at which to start the mapping. It must be a multiple of the page size.

The munmap() function deletes the mapping specified by the range [addr, addr + length). Addr must previously have been obtained via a successful call to mmap(). Unmapping memory that has been previously unmapped results in the behavior specified by the system.

After a successful munmap() call, the calling process cannot access the memory range specified by [addr, addr + length). However, the memory range is not guaranteed to be unmapped by the kernel immediately. The memory region is not guaranteed to be freed until the process terminates.

Address space layout for mmap

The mmap() call maps the object specified by fd into the virtual address space of the calling process.

The addr argument is a hint concerning the suggested memory address for the new mapping. The actual address is returned. If addr is NULL, the system chooses the address. The system chooses the address so as not to conflict with any existing mapping. The address chosen is never 0.

The length argument specifies the length of the mapping. It is typically a multiple of the page size.

The prot argument specifies the desired memory protection for the mapping. It can be PROT_NONE, or the bitwise OR of PROT_READ, PROT_WRITE, and PROT_EXEC.

The flags argument specifies the type of mapping. It is the bitwise OR of zero or more of the following options:

MAP_32BIT
Map the mapping using 32-bit addresses. This is useful only on 64-bit systems for the performance benefits of 32-bit pointers.
MAP_ANON
The mapping is not backed by any object. The file descriptor must be -1. Anonymous mappings are initialized to zero.
MAP_ANONYMOUS
Synonym for MAP_ANON.
MAP_DENYWRITE
Do not permit data modification to the object directly via another file descriptor that refers to the same file.
MAP_EXECUTABLE
Indicate that the pages in the mapping may be executed.
MAP_FILE
The mapping is backed by a regular file (as opposed to an anonymous mapping). This flag is the default if neither MAP_ANONYMOUS nor MAP_FILE is specified.
MAP_FIXED
Do not allow the system to choose the address. Addr must be a valid, non-NULL address, and the mapping is created at exactly that address. The previous mapping at that address is unmapped.
MAP_FIXED_NOREPLACE
(Since Linux 4.17) Do not allow the system to choose the address. Addr must be a valid, non-NULL address. If the address range specified by addr and length is already mapped, the call fails with the error EEXIST and the existing mapping is left unchanged. If the address range is not already mapped, the mapping is created at exactly addr. This flag is intended to provide a safe way to create a mapping at a fixed address in a multithreaded program.
MAP_HUGETLB
(Since Linux) Allocate pages of a huge page size (if supported and configured). The size of huge pages is architecture-dependent.
MAP_INHERIT
(Since Linux) Mark the mapping as inheritable across fork(2). This is the default behavior for shared anonymous mappings.
MAP_LOCKED
Lock the mapping in memory. See mlock(2).
MAP_NONBLOCK
(Since Linux) Do not populate the mapping page by page. Instead, the system may initialize the mapping lazily.
MAP_NORESERVE
Do not reserve disk space for the mapping.
MAP_POPULATE
(Since Linux 2.6.23) Populate the page table entries for a mapping. As a side effect of this flag, the pages are also initialized, causing disk I/O to be performed.
MAP_SHARED
Share the mapping. Writes to the mapping are visible to other processes mapping the same region, and are carried through to the underlying file.
MAP_SHARED_VALIDATE
(Since Linux 4.17) Similar to MAP_SHARED, but requires that the caller validates that the mapping is safe. This is intended for use with shared memory object mappings and provides some protection against certain kinds of race conditions.
MAP_PRIVATE
Create a private copy-on-write mapping. Writes to the mapping are not visible to other processes mapping the same region, and are not carried through to the underlying file.
MAP_STACK
(Since Linux) Allocate the mapping on the stack.

The fd argument is the file descriptor of the object to be mapped. If flags includes MAP_ANONYMOUS, then fd must be -1.

The offset argument is the offset in the file or shared memory object at which to start the mapping. It must be a multiple of the page size.

The munmap() function deletes the mapping specified by the range [addr, addr + length). Addr must previously have been obtained via a successful call to mmap(). Unmapping memory that has been previously unmapped results in the behavior specified by the system.

After a successful munmap() call, the calling process cannot access the memory range specified by [addr, addr + length). However, the memory region is not guaranteed to be unmapped by the kernel immediately. The memory region is not guaranteed to be freed until the process terminates.

RETURN VALUE

On success, mmap() returns a pointer to the mapped area. On failure, mmap() returns MAP_FAILED (which is (void *) -1), and errno is set to indicate the error.

On success, munmap() returns 0. On failure, munmap() returns -1, and errno is set to indicate the error.

ERRORS

The mmap() and munmap() functions may fail for any of the following reasons:

EACCES
The file descriptor fd is not open for read access, and prot contains PROT_READ.
The file descriptor fd is not open for write access, and prot contains PROT_WRITE.
EBADF
Fd is not a valid file descriptor.
EINVAL
Invalid value for length, or offset is not page-aligned, or addr and length do not make a valid range, or MAP_FIXED was specified and addr is not page-aligned.
(Since Linux 2.6.12) length is 0.
The specified mapping is not supported.
EMFILE
Too many file descriptors are in use by the process.
ENFILE
The system limit on the total number of open files has been reached.
ENODEV
The file pointed to by fd does not support mapping.
ENOMEM
Insufficient available memory (for instance, if the kernel's memory management is unable to find sufficient free memory).
EOVERFLOW
The file is too large to be mapped.
EPERM
The operation was prevented by a file seal; see fcntl(2).
EPERM
The MAP_HUGETLB flag was specified, but the caller was not privileged (did not have the CAP_IPC_LOCK capability) and is not a member of the hugetlb_shm_group group; see the description of /proc/sys/vm/hugetlb_shm_group in proc_sys_vm(5).
ETXTBSY
MAP_DENYWRITE was set but the object specified by fd is open for writing.

Use of a mapped region can result in these signals:

SIGSEGV
Attempted write into a region mapped as read-only.
SIGBUS
Attempted access to a page of the buffer that lies beyond the end of the mapped file. For an explanation of the treatment of the bytes in the page that corresponds to the end of a mapped file that is not a multiple of the page size, see NOTES.

VERSIONS

On some hardware architectures (e.g., i386), PROT_WRITE implies PROT_READ. It is architecture dependent whether PROT_READ implies PROT_EXEC or not. Portable programs should always set PROT_EXEC if they intend to execute code in the new mapping.

The portable way to create a mapping is to specify addr as 0 (NULL), and omit MAP_FIXED from flags. In this case, the system chooses the address for the mapping; the address is chosen so as not to conflict with any existing mapping, and will not be 0. If the MAP_FIXED flag is specified, and addr is 0 (NULL), then the mapped address will be 0 (NULL).

Certain flags constants are defined only if suitable feature test macros are defined (possibly by default): _DEFAULT_SOURCE with glibc 2.19 or later; or _BSD_SOURCE or _SVID_SOURCE in glibc 2.19 and earlier. (Employing _GNU_SOURCE also suffices, and requiring that macro specifically would have been more logical, since these flags are all Linux-specific.) The relevant flags are: MAP_32BIT, MAP_ANONYMOUS (and the synonym MAP_ANON), MAP_DENYWRITE, MAP_EXECUTABLE, MAP_FILE, MAP_GROWSDOWN, MAP_HUGETLB, MAP_LOCKED, MAP_NONBLOCK, MAP_NORESERVE, MAP_POPULATE, and MAP_STACK.

C library/kernel differences

This page describes the interface provided by the glibc mmap() wrapper function. Originally, this function invoked a system call of the same name. Since Linux 2.4, that system call has been superseded by mmap2(2), and nowadays the glibc mmap() wrapper function invokes mmap2(2) with a suitably adjusted value for offset.

STANDARDS

POSIX.1-2024.

HISTORY

POSIX.1-2001, SVr4, 4.4BSD.

On POSIX systems on which mmap(), msync(2), and munmap() are available, _POSIX_MAPPED_FILES is defined in <unistd.h> to a value greater than 0. (See also sysconf(3).)

NOTES

Memory mapped by mmap() is preserved across fork(2), with the same attributes.

A file is mapped in multiples of the page size. For a file that is not a multiple of the page size, the remaining bytes in the partial page at the end of the mapping are zeroed when mapped, and modifications to that region are not written out to the file. The effect of changing the size of the underlying file of a mapping on the pages that correspond to added or removed regions of the file is unspecified.

An application can determine which pages of a mapping are currently resident in the buffer/page cache using mincore(2).

Using MAP_FIXED safely

The only safe use for MAP_FIXED is where the address range specified by addr and length was previously reserved using another mapping; otherwise, the use of MAP_FIXED is hazardous because it forcibly removes preexisting mappings, making it easy for a multithreaded process to corrupt its own address space.

For example, suppose that thread A looks through /proc/pid/maps in order to locate an unused address range that it can map using MAP_FIXED, while thread B simultaneously acquires part or all of that same address range. When thread A subsequently employs mmap(MAP_FIXED), it will effectively clobber the mapping that thread B created. In this scenario, thread B need not create a mapping directly; simply making a library call that, internally, uses dlopen(3) to load some other shared library, will suffice. The dlopen(3) call will map the library into the process's address space. Furthermore, almost any library call may be implemented in a way that adds memory mappings to the address space, either with this technique, or by simply allocating memory. Examples include brk(2), malloc(3), pthread_create(3), and the PAM libraries http://www.linux-pam.org.

Since Linux 4.17, a multithreaded program can use the MAP_FIXED_NOREPLACE flag to avoid the hazard described above when attempting to create a mapping at a fixed address that has not been reserved by a preexisting mapping.

Timestamps changes for file-backed mappings

For file-backed mappings, the st_atime field for the mapped file may be updated at any time between the mmap() and the corresponding unmapping; the first reference to a mapped page will update the field if it has not been already.

The st_ctime and st_mtime field for a file mapped with PROT_WRITE and MAP_SHARED will be updated after a write to the mapped region, and before a subsequent msync(2) with the MS_SYNC or MS_ASYNC flag, if one occurs.

Huge page (Huge TLB) mappings

For mappings that employ huge pages, the requirements for the arguments of mmap() and munmap() differ somewhat from the requirements for mappings that use the native system page size.

For mmap(), offset must be a multiple of the underlying huge page size. The system automatically aligns length to be a multiple of the underlying huge page size.

For munmap(), addr, and length must both be a multiple of the underlying huge page size.

CAVEATS

Unlike typical malloc(3) implementations, mmap() does not prevent creating objects larger than PTRDIFF_MAX. Objects that are larger than PTRDIFF_MAX only work in limited ways in C (in particular, pointer subtraction results in undefined behavior if the result would be bigger than PTRDIFF_MAX). On top of that, GCC also assumes that no object is bigger than PTRDIFF_MAX. PTRDIFF_MAX is usually half of the address space size; so for 32-bit processes, it is usually 0x7fffffff (almost 2 GiB).

BUGS

On Linux, there are no guarantees like those suggested above under MAP_NORESERVE. By default, any process can be killed at any moment when the system runs out of memory.

Before Linux 2.6.7, the MAP_POPULATE flag has effect only if prot is specified as PROT_NONE.

SUSv3 specifies that mmap() should fail if length is 0. However, before Linux 2.6.12, mmap() succeeded in this case: no mapping was created and the call returned addr. Since Linux 2.6.12, mmap() fails with the error EINVAL for this case.

POSIX specifies that the system shall always zero fill any partial page at the end of the object and that system will never write any modification of the object beyond its end. On Linux, when you write data to such partial page after the end of the object, the data stays in the page cache even after the file is closed and unmapped and even though the data is never written to the file itself, subsequent mappings may see the modified content. In some cases, this could be fixed by calling msync(2) before the unmap takes place; however, this doesn't work on tmpfs(5) (for example, when using the POSIX shared memory interface documented in shm_overview(7)).

EXAMPLES

The following program prints part of the file specified in its first command-line argument to standard output. The range of bytes to be printed is specified via offset and length values in the second and third command-line arguments. The program creates a memory mapping of the required pages of the file and then uses write(2) to output the desired bytes.

Program source

#include <sys/mman.h>
#include <sys/stat.h>
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

int
main(int argc, char *argv[])
{
    int fd;
    void *addr;
    struct stat sb;
    off_t offset;
    size_t length;

    if (argc != 4) {
        fprintf(stderr, "usage: %s file offset length\n", argv[0]);
        exit(EXIT_FAILURE);
    }

    offset = atoll(argv[2]);
    length = atoll(argv[3]);

    fd = open(argv[1], O_RDONLY);
    if (fd == -1) {
        perror("open");
        exit(EXIT_FAILURE);
    }

    if (fstat(fd, &sb) == -1) {
        perror("fstat");
        close(fd);
        exit(EXIT_FAILURE);
    }

    if (length > sb.st_size - offset) {
        fprintf(stderr, "length exceeds file size\n");
        close(fd);
        exit(EXIT_FAILURE);
    }

    addr = mmap(NULL, length, PROT_READ, MAP_PRIVATE, fd, offset);
    if (addr == MAP_FAILED) {
        perror("mmap");
        close(fd);
        exit(EXIT_FAILURE);
    }

    if (write(STDOUT_FILENO, addr, length) != length) {
        perror("write");
        munmap(addr, length);
        close(fd);
        exit(EXIT_FAILURE);
    }

    if (munmap(addr, length) == -1) {
        perror("munmap");
        close(fd);
        exit(EXIT_FAILURE);
    }

    close(fd);
    exit(EXIT_SUCCESS);
}
