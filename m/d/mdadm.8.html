MDADM(8) Manual del Administrador del Sistema MDADM(8)

NOMBRE

mdadm - administrar dispositivos MD, también conocidos como Linux Software RAID

SINOPSIS

mdadm [modo] <dispositivo_raid> [opciones] <dispositivos_componente>

DESCRIPCIÓN

Los dispositivos RAID son dispositivos virtuales creados a partir de dos o más dispositivos de bloque reales. Esto permite combinar múltiples dispositivos (típicamente unidades de disco o particiones de las mismas) en un solo dispositivo para alojar (por ejemplo) un único sistema de archivos. Algunos niveles de RAID incluyen redundancia y, por lo tanto, pueden sobrevivir a cierto grado de fallo de dispositivo.

El RAID por Software de Linux se implementa a través del controlador de dispositivos md (Múltiples Dispositivos).

Actualmente, Linux soporta dispositivos md LINEAR, RAID0 (striping), RAID1 (mirroring), RAID4, RAID5, RAID6, RAID10, MULTIPATH, FAULTY y CONTAINER.

MULTIPATH no es un mecanismo de RAID por Software, pero involucra múltiples dispositivos: cada dispositivo es una ruta hacia un dispositivo de almacenamiento físico común. Las nuevas instalaciones no deben usar md/multipath ya que no está bien soportado y no tiene desarrollo continuo. En su lugar, use las herramientas multipath-tools basadas en Device Mapper. Está obsoleto y su soporte será eliminado en el futuro.

FAULTY tampoco es un RAID real, y solo involucra un dispositivo. Proporciona una capa sobre un dispositivo real que puede ser utilizada para inyectar fallos. Está obsoleto y su soporte será eliminado en el futuro.

CONTAINER es diferente de nuevo. Un CONTAINER es una colección de dispositivos que se administran como un conjunto. Esto es similar al conjunto de dispositivos conectados a un controlador RAID de hardware. El conjunto de dispositivos puede contener una serie de diferentes matrices RAID, cada una utilizando algunos (o todos) los bloques de varios de los dispositivos en el conjunto. Por ejemplo, dos dispositivos en un conjunto de 5 dispositivos podrían formar un RAID1 usando los dispositivos completos. Los tres restantes podrían tener un RAID5 sobre la primera mitad de cada dispositivo, y un RAID0 sobre la segunda mitad.

Con un CONTAINER, hay un conjunto de metadatos que describe todas las matrices dentro del contenedor. Por lo tanto, cuando mdadm crea un dispositivo CONTAINER, el dispositivo solo representa los metadatos. Se pueden crear otras matrices normales (RAID1, etc.) dentro del contenedor.

MODOS

mdadm tiene varios modos de operación principales:

Ensamblar
Ensamblar los componentes de una matriz previamente creada en una matriz activa. Los componentes pueden especificarse explícitamente o se puede buscar. mdadm verifica que los componentes forman una matriz legítima y, bajo petición, puede manipular la información de la superbloque para ensamblar una matriz defectuosa.
Construir
Construir una matriz que no tenga metadatos por dispositivo (superbloques). Para este tipo de matrices, mdadm no puede diferenciar entre la creación inicial y el ensamblaje posterior de una matriz. Tampoco puede realizar ninguna verificación de que se han solicitado los componentes apropiados. Debido a esto, el modo Construir solo debe usarse junto con una comprensión completa de lo que se está haciendo.
Crear
Crear una nueva matriz con metadatos por dispositivo (superbloques). Se escriben metadatos apropiados en cada dispositivo, y luego se activa la matriz que comprende esos dispositivos. Se inicia un proceso de 'resincronización' para asegurar que la matriz sea consistente (por ejemplo, ambos lados de un espejo contienen los mismos datos), pero el contenido del dispositivo se deja sin tocar de otra manera. La matriz se puede utilizar tan pronto como se haya creado. No es necesario esperar a que finalice la resincronización inicial.
Seguir o Monitorizar
Monitorizar uno o más dispositivos md y actuar sobre cualquier cambio de estado. Esto solo tiene sentido para matrices RAID1, 4, 5, 6, 10 o multipath, ya que solo estas tienen un estado interesante. RAID0 o Linear nunca tienen unidades faltantes, de repuesto o fallidas, por lo que no hay nada que monitorizar.
Crecer
Crecer (o reducir) una matriz, o de lo contrario remodelarla de alguna manera. Las opciones de crecimiento admitidas actualmente incluyen cambiar el tamaño activo de los dispositivos componentes y cambiar el número de dispositivos activos en los niveles Lineal y RAID 0/1/4/5/6, cambiar el nivel RAID entre 0, 1, 5 y 6, y entre 0 y 10, cambiar el tamaño del bloque y la disposición para RAID 0,4,5,6,10, así como agregar o eliminar un bitmap de intención de escritura y cambiar la política de consistencia de la matriz.
Ensamblado Incremental
Añadir un solo dispositivo a una matriz apropiada. Si la adición del dispositivo hace que la matriz sea ejecutable, la matriz se iniciará. Esto proporciona una interfaz conveniente para un sistema de hot-plug. A medida que se detecta cada dispositivo, mdadm tiene la oportunidad de incluirlo en alguna matriz según corresponda. Opcionalmente, cuando se pasa el flag --fail, eliminaremos el dispositivo de cualquier matriz activa en lugar de agregarlo.

Si se pasa un CONTAINER a mdadm en este modo, se ensamblarán y se iniciarán todas las matrices dentro de ese contenedor.

Gestionar
Esto es para hacer cosas a componentes específicos de una matriz, como añadir nuevas unidades de repuesto y eliminar dispositivos defectuosos.
Varios
Este es un modo de 'todo lo demás' que soporta operaciones en matrices activas, operaciones en dispositivos componentes como borrar superbloques antiguos y operaciones de recopilación de información.
Auto-detectar
Este modo no actúa sobre un dispositivo o matriz específica, sino que solicita al Kernel de Linux que active cualquier matriz auto-detectada. Esto solo puede funcionar si md está compilado en el kernel — no si es un módulo. Las matrices pueden ser auto-detectadas por el kernel si todos los componentes están en particiones primarias MS-DOS con el tipo de partición FD, y todas usan metadatos v0.90. La auto-detección dentro del kernel no se recomienda para nuevas instalaciones. Usar mdadm para detectar y ensamblar matrices — posiblemente en un initrd — es sustancialmente más flexible y debería preferirse.

OPCIONES

Opciones para seleccionar un modo son:

-A, --assemble
Ensamblar una matriz preexistente.
-B, --build
Construir una matriz heredada sin superbloques.
-C, --create
Crear una nueva matriz.
-F, --follow, --monitor
Seleccionar el modo Monitorizar.
-G, --grow
Cambiar el tamaño o la forma de una matriz activa.
-I, --incremental
Añadir/eliminar un dispositivo a/desde una matriz apropiada, y posiblemente iniciar la matriz.
--auto-detect
Solicitar que el kernel inicie cualquier matriz auto-detectada. Esto solo puede funcionar si md está compilado en el kernel — no si es un módulo. Las matrices pueden ser auto-detectadas por el kernel si todos los componentes están en particiones primarias MS-DOS con el tipo de partición FD, y todas usan metadatos v0.90. La auto-detección dentro del kernel no se recomienda para nuevas instalaciones. Usar mdadm para detectar y ensamblar matrices — posiblemente en un initrd — es sustancialmente más flexible y debería preferirse.

Si se proporciona un dispositivo antes de cualquier opción, o si la primera opción es --add, --re-add, --add-spare, --fail, --remove, o --replace, se asume el modo MANAGE. Cualquier otra cosa provocará que se asuma el modo Varios.

Opciones que no son específicas del modo son:

-h, --help
Mostrar un mensaje de ayuda general o, después de una de las opciones anteriores, un mensaje de ayuda específico del modo.
--help-options
Mostrar ayuda más detallada sobre el análisis de línea de comandos y algunas opciones de uso común.
-V, --version
Imprimir información de versión para mdadm.
-v, --verbose
Sea más verboso sobre lo que está sucediendo. Esto se puede usar dos veces para ser extra-verboso. La verbosidad extra actualmente solo afecta a --detail --scan y --examine --scan.
-q, --quiet
Evite imprimir mensajes puramente informativos. Con esto, mdadm estará silencioso a menos que haya algo realmente importante que informar.
-f, --force
Sea más contundente con ciertas operaciones. Consulte los diversos modos para el significado exacto de esta opción en diferentes contextos.
-c, --config=
Especifique el archivo o directorio de configuración. Si no se especifica, se utilizará el archivo de configuración predeterminado y el directorio conf.d predeterminado. Consulte mdadm.conf(5) para más detalles.

Si el archivo de configuración proporcionado es partitions, no se leerá nada, pero mdadm actuará como si el archivo de configuración contuviera exactamente
DEVICE partitions containers
y leerá /proc/partitions para encontrar una lista de dispositivos para escanear, y /proc/mdstat para encontrar una lista de contenedores para examinar. Si la palabra none se proporciona para el archivo de configuración, entonces mdadm actuará como si el archivo de configuración estuviera vacío.

Si el nombre proporcionado es el de un directorio, entonces mdadm recopilará todos los archivos contenidos en el directorio con un nombre que termine en .conf, los ordenará léxicamente y procesará todos esos archivos como archivos de configuración.

-s, --scan
Escanear el archivo de configuración o /proc/mdstat para obtener información faltante. En general, esta opción otorga a mdadm permiso para obtener cualquier información faltante (como dispositivos componentes, dispositivos de matriz, identidades de matriz y destino de alerta) del archivo de configuración (ver opción anterior); una excepción es el modo MISC cuando se usa --detail o --stop, en cuyo caso --scan indica obtener una lista de dispositivos de matriz de /proc/mdstat.
-e, --metadata=
Declare el estilo de metadatos (superblock) RAID que se utilizará. El valor predeterminado es 1.2 para --create y adivinar para otras operaciones. El valor predeterminado se puede anular estableciendo el valor metadata para la palabra clave CREATE en mdadm.conf.

Las opciones son:

0, 0.90
Use el superblock del formato original 0.90. Este formato limita las matrices a 28 dispositivos componentes y limita los dispositivos componentes de los niveles 1 y superiores a 2 terabytes. También es posible que haya confusión sobre si el superblock se aplica a un dispositivo completo o solo a la última partición, si esa partición comienza en un límite de 64K.
1, 1.0, 1.1, 1.2 default
Use el nuevo superblock en formato versión 1. Esto tiene menos restricciones. Se puede mover fácilmente entre hosts con diferente endianness, y una operación de recuperación se puede puntos de control y reiniciar. Las diferentes subversiones almacenan el superblock en diferentes ubicaciones en el dispositivo, ya sea al final (para 1.0), al principio (para 1.1) o a 4K del principio (para 1.2). "1" es equivalente a "1.2" (el formato 1.x comúnmente preferido). "default" es equivalente a "1.2".
ddf
Use el formato DDF (Disk Data Format) "Estándar de la Industria" definido por SNIA. DDF está obsoleto y no hay desarrollo activo a su alrededor. Al crear una matriz DDF, se creará un CONTAINER y se pueden crear matrices normales en ese contenedor.
imsm
Use el formato de metadatos Intel(R) Matrix Storage Manager. Esto crea un CONTAINER que se gestiona de manera similar a DDF, y está respaldado por una ROM de opciones en algunas plataformas:
https://www.intel.com/content/www/us/en/support/products/122484
--homehost=
Esto anulará cualquier configuración de HOMEHOST en el archivo de configuración y proporcionará la identidad del host que debe considerarse el hogar para cualquier matriz.

Al crear una matriz, el homehost se registrará en los metadatos. Para superblocks de versión 1, se antepondrá al nombre de la matriz. Para superblocks de versión 0.90, parte del hash SHA1 del nombre del host se almacenará en la mitad posterior del UUID.

Al informar sobre una matriz, cualquier matriz que esté etiquetada para el homehost dado se informará como tal.

Al usar Auto-Assembly, solo las matrices etiquetadas para el homehost dado podrán usar nombres 'locales' (es decir, que no terminen en '_' seguido de una cadena de dígitos). Ver más abajo bajo Auto-Assembly.

El nombre especial "any" se puede usar como comodín. Si una matriz se crea con --homehost=any, entonces el nombre "any" se almacenará en la matriz y puede ser ensamblada de la misma manera en cualquier host. Si una matriz se ensambla con esta opción, entonces el homehost registrado en la matriz se ignorará.

--prefer=
Cuando mdadm necesita imprimir el nombre de un dispositivo, normalmente encuentra el nombre en /dev que se refiere al dispositivo y es el más corto. Cuando se proporciona un componente de ruta con --prefer, mdadm preferirá un nombre más largo si contiene ese componente. Por ejemplo, --prefer=by-uuid preferirá un nombre en un subdirectorio de /dev llamado by-uuid.

Esta funcionalidad actualmente solo es proporcionada por --detail y --monitor.

--home-cluster=
especifica el nombre del clúster para el dispositivo md. El dispositivo md solo puede ensamblarse en el clúster que coincida con el nombre especificado. Si no se proporciona esta opción, mdadm intentará detectar el nombre del clúster automáticamente.

Para crear, construir o expandir:

-n, --raid-devices=
Especifique el número de dispositivos activos en la matriz. Este número, más el número de dispositivos de repuesto (ver más abajo), debe ser igual al número de dispositivos componentes (incluyendo dispositivos "missing") que se enumeran en la línea de comandos para --create. Establecer un valor de 1 es probablemente un error y, por lo tanto, requiere que se especifique --force primero. Entonces se permitirá un valor de 1 para lineal, multipath, RAID0 y RAID1. Nunca se permite para RAID4, RAID5 o RAID6.
Este número solo se puede cambiar usando --grow para matrices RAID1, RAID4, RAID5 y RAID6.
-x, --spare-devices=
Especifique el número de dispositivos de repuesto (eXtra) en la matriz inicial. Los repuestos también se pueden agregar y eliminar más tarde. El número de dispositivos componentes enumerados en la línea de comandos debe ser igual al número de dispositivos RAID más el número de dispositivos de repuesto.
-z, --size=
Cantidad (en Kilobytes) de espacio a usar de cada unidad en los niveles RAID 1/4/5/6/10 y para RAID 0 en metadatos externos. Debe ser un múltiplo del tamaño del fragmento (chunk size) y debe dejar aproximadamente 128 Kb de espacio al final de la unidad para el superblock RAID. Si no se especifica (como normalmente no se hace), la unidad (o partición) más pequeña establece el tamaño, aunque si hay una variación entre las unidades superior al 1%, se emitirá una advertencia.

Se puede dar un sufijo de 'K', 'M', 'G' o 'T' para indicar Kilobytes, Megabytes, Gigabytes o Terabytes respectivamente.

A veces, una unidad de reemplazo puede ser un poco más pequeña que las unidades originales, aunque esto debería minimizarse según los estándares IDEMA. Dicha unidad de reemplazo será rechazada por md. Para protegerse contra esto, puede ser útil establecer el tamaño inicial ligeramente más pequeño que el dispositivo más pequeño con el objetivo de que siga siendo más grande que cualquier reemplazo.

Esta opción se puede usar con --create para determinar el tamaño inicial de una matriz. Para metadatos externos, se puede usar en un volumen, pero no en un contenedor en sí. Establecer el tamaño inicial de una matriz RAID 0 solo es válido para metadatos externos.

Este valor se puede establecer con --grow para los niveles de RAID 1/4/5/6/10, aunque las matrices DDF pueden no admitir esto. El tamaño de la matriz RAID 0 no se puede cambiar. Si la matriz se creó con un tamaño inferior a las unidades activas actuales, se puede acceder al espacio adicional usando --grow. El tamaño se puede dar como max, lo que significa elegir el tamaño más grande que encaje en todas las unidades actuales.

Antes de reducir el tamaño de la matriz (con --grow --size=), debe asegurarse de que no se necesita espacio. Si el dispositivo contiene un sistema de archivos, necesitaría redimensionar el sistema de archivos para usar menos espacio.

Después de reducir el tamaño de la matriz, debe verificar que los datos almacenados en el dispositivo sigan estando disponibles. Si el dispositivo contiene un sistema de archivos, entonces un 'fsck' del sistema de archivos es un requisito mínimo. Si hay problemas, la matriz se puede hacer más grande nuevamente sin pérdidas con otro comando --grow --size=.

-Z, --array-size=
Esto solo tiene sentido con --grow y su efecto no es persistente: cuando la matriz se detiene y se reinicia, se restaurará el tamaño predeterminado de la matriz.

Establecer el tamaño de la matriz hace que la matriz parezca más pequeña para los programas que acceden a los datos. Esto es particularmente necesario antes de remodelar una matriz para que sea más pequeña. Como la remodelación no es reversible, pero establecer el tamaño con --array-size sí lo es, se requiere que el tamaño de la matriz se reduzca según corresponda antes de que se reduzca el número de dispositivos en la matriz.

Antes de reducir el tamaño de la matriz, debe asegurarse de que no se necesita espacio. Si el dispositivo contiene un sistema de archivos, necesitaría redimensionar el sistema de archivos para usar menos espacio.

Después de reducir el tamaño de la matriz, debe verificar que los datos almacenados en el dispositivo sigan estando disponibles. Si el dispositivo contiene un sistema de archivos, entonces un 'fsck' del sistema de archivos es un requisito mínimo. Si hay problemas, la matriz se puede hacer más grande nuevamente sin pérdidas con otro comando --grow --array-size=.

Un sufijo

x de 'K', 'M', 'G' o 'T' se pueden dar para indicar Kilobytes, Megabytes, Gigabytes o Terabytes respectivamente. Un valor de max restaura el tamaño aparente del array para que sea igual a la cantidad real de espacio disponible.

Los arrays agrupados no admiten este parámetro todavía.

-c, --chunk=
Especifica el tamaño del bloque en kilobytes. El valor por defecto al crear un array es 512KB. Para asegurar la compatibilidad con versiones anteriores, el valor por defecto al construir un array sin metadatos persistentes es 64KB. Esto solo es significativo para RAID0, RAID4, RAID5, RAID6 y RAID10.

RAID4, RAID5, RAID6 y RAID10 requieren que el tamaño del bloque sea una potencia de 2, con un tamaño mínimo de bloque de 4KB.

Se puede añadir un sufijo 'K', 'M', 'G' o 'T' para indicar Kilobytes, Megabytes, Gigabytes o Terabytes respectivamente.

--rounding=
Especifica el factor de redondeo para un array Lineal. El tamaño de cada componente se redondeará hacia abajo a un múltiplo de este tamaño. Esto es un sinónimo de --chunk pero destaca el diferente significado para Lineal en comparación con otros niveles RAID. El valor por defecto es 0K (es decir, sin redondeo).
-l, --level=
Establece el nivel RAID. Cuando se usa con --create, las opciones son: linear, raid0, 0, stripe, raid1, 1, mirror, raid4, 4, raid5, 5, raid6, 6, raid10, 10, multipath, mp, faulty, container. Obviamente, algunos de estos son sinónimos.

Cuando se solicita un tipo de metadatos CONTAINER, solo se permite el nivel container, y no es necesario especificarlo explícitamente.

Cuando se usa con --build, solo son válidos linear, stripe, raid0, 0, raid1, multipath, mp y faulty.

Se puede usar con --grow para cambiar el nivel RAID en algunos casos. Ver CAMBIOS DE NIVEL más abajo.

-p, --layout=
Esta opción configura los detalles finos de la disposición de los datos para los arrays RAID5, RAID6 y RAID10, y controla los modos de fallo para faulty. También se puede usar para solucionar un error del kernel con RAID0, pero generalmente no es necesario usarla explícitamente.

La disposición del bloque de paridad RAID5 puede ser left-asymmetric, left-symmetric, right-asymmetric, right-symmetric, la, ra, ls, rs. El valor por defecto es left-symmetric.

También es posible hacer que RAID5 use una disposición similar a RAID4 eligiendo parity-first o parity-last.

Finalmente, para RAID5, existen disposiciones compatibles con DDF: ddf-zero-restart, ddf-N-restart y ddf-N-continue.

Las mismas disposiciones están disponibles para RAID6. También hay 4 disposiciones que proporcionarán una etapa intermedia para convertir entre RAID5 y RAID6. Estas proporcionan una disposición que es idéntica a la disposición RAID5 correspondiente en los N-1 dispositivos primeros, y tiene el síndrome 'Q' (el segundo bloque de 'paridad' utilizado por RAID6) en el último dispositivo. Estas disposiciones son: left-symmetric-6, right-symmetric-6, left-asymmetric-6, right-asymmetric-6 y parity-first-6.

Al establecer el modo de fallo para el nivel faulty, las opciones son: write-transient, wt, read-transient, rt, write-persistent, wp, read-persistent, rp, write-all, read-fixable, rf, clear, flush, none.

Cada modo de fallo puede ir seguido de un número, que se utiliza como período entre la generación de fallos. Sin un número, el fallo se genera una vez en la primera solicitud relevante. Con un número, el fallo se generará después de ese número de solicitudes, y continuará generándose cada vez que transcurra el período.

Se pueden tener varios modos de fallo activos simultáneamente utilizando la opción --grow para establecer modos de fallo subsiguientes.

"clear" o "none" eliminarán cualquier modo de fallo pendiente o periódico, y "flush" borrará cualquier fallo persistente.

Las opciones de disposición para RAID10 son 'n', 'o' o 'f' seguido de un número pequeño que indica el número de copias de cada bloque de datos. El valor por defecto es 'n2'. Las opciones soportadas son:

'n' indica copias 'cercanas' (near). Múltiples copias de un bloque de datos están en desplazamientos similares en diferentes dispositivos.

'o' indica copias 'desplazadas' (offset). En lugar de duplicar los bloques dentro de un stripe, se duplican stripes completos pero se rotan por un dispositivo, de modo que los bloques duplicados estén en dispositivos diferentes. Por lo tanto, las copias subsiguientes de un bloque están en la siguiente unidad y un bloque más abajo.

'f' indica copias 'lejanas' (far) (múltiples copias tienen desplazamientos muy diferentes). Ver md(4) para más detalles sobre 'near', 'offset' y 'far'.

En cuanto al número de copias de cada bloque de datos, 2 es lo normal, 3 puede ser útil. Este número puede ser como máximo igual al número de dispositivos en el array. No es necesario que divida exactamente ese número (por ejemplo, es perfectamente legal tener una disposición 'n2' para un array con un número impar de dispositivos).

Un error introducido en Linux 3.14 significa que los arrays RAID0 con dispositivos de tamaños diferentes comenzaron a usar una disposición diferente. Esto podría llevar a la corrupción de datos. Desde Linux 5.4 (y varias versiones estables que recibieron backports), el kernel no aceptará un array así a menos que se establezca explícitamente una disposición. Se puede establecer a 'original' o 'alternate'. Al crear un nuevo array, mdadm seleccionará 'original' por defecto, por lo que la disposición normalmente no necesita ser establecida. Un array creado para 'original' o 'alternate' no será reconocido por un kernel (sin parches) anterior a 5.4. Para crear un array RAID0 con dispositivos de tamaños diferentes que pueda ser utilizado en un kernel más antiguo, puede establecer la disposición a 'dangerous'. Esto usará la disposición que el kernel en ejecución soporte, por lo que los datos en el array pueden corromperse al cambiar de un kernel pre-3.14 a uno posterior.

Cuando un array se convierte de RAID5 a RAID6, se utiliza una disposición RAID6 intermedia en la que el segundo bloque de paridad (Q) siempre está en el último dispositivo. Para convertir un RAID5 a RAID6 y dejarlo en esta nueva disposición (que no requiere re-striping), use --layout=preserve. Esto intentará evitar cualquier re-striping.

Lo opuesto a esto es --layout=normalise, que cambiará una disposición RAID6 no estándar a una disposición más estándar.

--parity=
igual que --layout (explicando así la 'p' de -p).
-b, --bitmap=
Especifica cómo almacenar un mapa de bits de intención de escritura. Los siguientes valores son compatibles:

internal - el mapa de bits se almacena con los metadatos en el array y, por lo tanto, se replica en todos los dispositivos.

clustered - el array se crea para un entorno agrupado. Se crea un mapa de bits por cada nodo definido por el parámetro --nodes y se almacenan internamente.

none - crea el array sin mapa de bits o elimina cualquier mapa de bits presente (modo grow).

Establecer el mapa de bits para un archivo está obsoleto y no debería usarse. El archivo no debería existir a menos que también se proporcione --force. Se debe proporcionar el mismo archivo al ensamblar el array. El nombre del archivo debe contener al menos una barra ('/'). Los mapas de bits de archivo solo se sabe que funcionan en ext2 y ext3. Almacenar mapas de bits de archivo en otros sistemas de archivos puede resultar en problemas graves.

Al crear un array en dispositivos de 100G o más, mdadm añade automáticamente un mapa de bits interno, ya que generalmente será beneficioso. Esto se puede suprimir con --bitmap=none o seleccionando una política de consistencia diferente con --consistency-policy.

--bitmap-chunk=
Establece el tamaño del bloque del mapa de bits. Cada bit corresponde a esa cantidad de Kilobytes de almacenamiento. Al usar un mapa de bits basado en archivo, el valor por defecto es usar el tamaño más pequeño que sea al menos 4 y que requiera no más de 2^21 bloques. Al usar un mapa de bits internal, el tamaño del bloque por defecto es 64Meg, o mayor si es necesario para que el mapa de bits quepa en el espacio disponible.

Se puede añadir un sufijo 'K', 'M', 'G' o 'T' para indicar Kilobytes, Megabytes, Gigabytes o Terabytes respectivamente.

-W, --write-mostly
los dispositivos subsiguientes listados en un comando --build, --create o --add se marcarán como 'write-mostly' (escritura principalmente). Esto es válido solo para RAID1 y significa que el driver 'md' evitará leer de estos dispositivos en la medida de lo posible. Esto puede ser útil si se está reflejando sobre un enlace lento.
--write-behind=
Especifica que el modo write-behind (escritura diferida) debe estar habilitado (válido solo para RAID1). Si se especifica un argumento, establecerá el número máximo de escrituras pendientes permitidas. El valor por defecto es 256. Se requiere un mapa de bits de intención de escritura para usar el modo write-behind, y el write-behind solo se intenta en unidades marcadas como write-mostly.
--failfast
los dispositivos subsiguientes listados en un comando --create o --add se marcarán como 'failfast'. Esto es válido solo para RAID1 y RAID10. Las solicitudes de E/S a estos dispositivos intentarán fallar rápidamente en lugar de causar largos retrasos debido al manejo de errores. Tampoco se intentará reparar un error de lectura en estos dispositivos.

Si un array se degrada de tal manera que el dispositivo 'failfast' es el único dispositivo utilizable, la bandera 'failfast' se ignorará y se preferirán los retrasos extendidos para completar el fallo.

La bandera 'failfast' es apropiada para arrays de almacenamiento que tienen una baja probabilidad de fallo real, pero que a veces pueden causar retrasos inaceptables debido a funciones de mantenimiento internas.

--assume-clean
Indica a mdadm que el array preexistía y se sabe que está limpio. Puede ser útil al intentar recuperarse de un fallo importante, ya que puede estar seguro de que no se verán afectados datos a menos que realmente escriba en el array. También se puede usar al crear un RAID1 o RAID10 si desea evitar la resincronización inicial, sin embargo, esta práctica —aunque normalmente segura— no se recomienda. Úselo solo si realmente sabe lo que está haciendo.
--assume-clean
Cuando los dispositivos que formarán parte de un nuevo array fueron rellenados con ceros antes de la creación, el operador sabe que el array está realmente limpio. Si ese es el caso, como después de ejecutar badblocks, este argumento puede usarse para informar a mdadm de los hechos que el operador conoce.
Cuando un array se redimensiona a un tamaño mayor con --grow --size=, el nuevo espacio normalmente se resincroniza de la misma manera que todo el array se resincroniza en la creación. --assume-clean puede usarse con ese comando para evitar la resincronización automática.
--write-zeroes
Al crear un array, envía solicitudes de escritura de ceros a todos los dispositivos de bloque. Esto debería poner a cero el área de datos en todos los discos de tal manera que la sincronización inicial no sea necesaria y, si tiene éxito, se comportará como si se hubiera especificado --assume-clean.
Esto está pensado para usarse con dispositivos que tienen descarga de hardware para poner a cero, pero a pesar de esto, poner a cero puede llevar varios minutos para discos grandes. Por lo tanto, se imprime un mensaje antes y después de poner a cero y cada disco se pone a cero en paralelo con los demás.
Esto solo tiene sentido con --create.
--backup-file=
Esto es necesario cuando se usa --grow para aumentar el número de dispositivos raid en un RAID5 o RAID6 si no hay dispositivos de repuesto disponibles, o para reducir, cambiar el nivel de RAID o el diseño. Consulte la sección MODO GROW abajo sobre CAMBIOS EN DISPOSITIVOS RAID. El archivo debe almacenarse en un dispositivo separado, no en el array RAID que se está remodelando.
--data-offset=
Los arrays con metadatos 1.x pueden dejar un espacio entre el inicio del dispositivo y el inicio de los datos del array. Este espacio se puede usar para varios metadatos. El inicio de los datos se conoce como el desplazamiento de datos. Normalmente se calcula automáticamente un desplazamiento de datos apropiado. Sin embargo, puede ser útil establecerlo explícitamente, como al recrear un array que se creó originalmente usando una versión diferente de mdadm que calculó un desplazamiento diferente.

Establecer el desplazamiento explícitamente anula el valor predeterminado. El valor dado está en Kilobytes a menos que se use un sufijo de 'K', 'M', 'G' o 'T' para indicar explícitamente Kilobytes, Megabytes, Gigabytes o Terabytes respectivamente.

--data-offset también se puede usar con --grow para algunos niveles de RAID (inicialmente en RAID10). Esto permite cambiar el desplazamiento de datos como parte del proceso de remodelación. Cuando se cambia el desplazamiento de datos, no se requiere ningún archivo de copia de seguridad, ya que la diferencia en los desplazamientos se usa para proporcionar la misma funcionalidad.

Cuando el nuevo desplazamiento es anterior al antiguo, el número de dispositivos en el array no puede reducirse. Cuando es posterior al antiguo, el número de dispositivos en el array no puede aumentar.

Al crear un array, --data-offset se puede especificar como variable. En ese caso, se espera que cada dispositivo miembro tenga un desplazamiento añadido al nombre, separado por dos puntos. Esto hace posible recrear exactamente un array que tiene desplazamientos de datos variables (como puede ocurrir cuando se utilizan diferentes versiones de mdadm para agregar diferentes dispositivos).

--continue
Esta opción es complementaria a la opción --freeze-reshape para el ensamblaje. Es necesaria cuando la operación --grow se interrumpe y no se reinicia automáticamente debido al uso de --freeze-reshape durante el ensamblaje del array. Esta opción se usa junto con el comando -G, (--grow) y el dispositivo para que una remodelación pendiente continúe. Todos los parámetros necesarios para la continuación de la remodelación se leerán de los metadatos del array. Si el comando --grow inicial requería la opción --backup-file=, la opción de continuación requerirá el mismo archivo de copia de seguridad.
Cualquier otro parámetro pasado junto con la opción --continue será ignorado.
-N, --name=
Establece un nombre para el array. Debe ser compatible con NOMBRE PORTABLE POSIX y no puede tener más de 32 caracteres. Esto es efectivo al crear un array con metadatos v1, o un array externo.

Si se necesita un nombre pero no se especifica, se toma del nombre base del dispositivo que se está creando. Consulte NOMBRES DE DISPOSITIVOS

-R, --run
Insiste en que mdadm ejecute el array, incluso si algunos de los componentes parecen estar activos en otro array o sistema de archivos. Normalmente mdadm pedirá confirmación antes de incluir tales componentes en un array. Esta opción suprime esa pregunta.
-f, --force
Insiste en que mdadm acepte la geometría y el diseño especificados sin preguntar. Normalmente mdadm no permitirá la creación de un array con un solo dispositivo, e intentará crear un array RAID5 con una unidad faltante (ya que esto acelera la resincronización inicial). Con --force, mdadm no intentará ser tan inteligente.
-o, --readonly
Inicia el array en modo de solo lectura en lugar de lectura-escritura como es normal. No se permitirán escrituras en el array, ni se iniciará ninguna resincronización, recuperación o remodelación. Funciona con los modos Create, Assemble, Manage y Misc.
-a, --add
Esta opción se puede usar en el modo Grow en dos casos.

Si el array de destino es un array Lineal, entonces --add se puede usar para agregar uno o más dispositivos al array. Simplemente se concatenan al final del array. Una vez agregados, los dispositivos no se pueden eliminar.

Si se está utilizando la opción --raid-disks para aumentar el número de dispositivos en un array, entonces --add se puede usar para agregar dispositivos adicionales que se incluirán en el array. En la mayoría de los casos, esto no es necesario ya que los dispositivos adicionales se pueden agregar primero como repuestos, y luego se puede cambiar el número de discos RAID. Sin embargo, para RAID0 no es posible agregar repuestos. Por lo tanto, para aumentar el número de dispositivos en un RAID0, es necesario establecer el nuevo número de dispositivos y agregar los nuevos dispositivos en el mismo comando.

--nodes
Solo funciona cuando el array se crea para un entorno de clúster. Especifica el número máximo de nodos en el clúster que usarán este dispositivo simultáneamente. Si no se especifica, el valor predeterminado es 4.
--write-journal
Especifica el dispositivo de registro (journal) para el array RAID-4/5/6. El dispositivo de registro debe ser un SSD con una vida útil razonable.
-k, --consistency-policy=
Especifica cómo el array mantiene la consistencia en caso de un apagado inesperado. Solo relevante para niveles de RAID con redundancia. Las opciones admitidas actualmente son:
resync
Se realiza una resincronización completa y se regenera toda la redundancia cuando el array se inicia después de un apagado incorrecto.
bitmap
Resincronización asistida por un mapa de bits de intención de escritura. Seleccionado implícitamente al usar --bitmap.
journal
Para los niveles de RAID 4/5/6, el dispositivo de registro se utiliza para registrar transacciones y reproducirlas después de un apagado incorrecto. Seleccionado implícitamente al usar --write-journal.
ppl
Solo para RAID5, se utiliza el Registro de Paridad Parcial (Partial Parity Log) para cerrar el agujero de escritura y eliminar la resincronización. PPL se almacena en la región de metadatos de las unidades miembro de RAID, no se necesita una unidad de registro adicional.

Se puede usar con --grow para cambiar la política de consistencia de un array activo en algunos casos. Consulte CAMBIOS DE POLÍTICA DE CONSISTENCIA abajo.

Para ensamblar:

-u, --uuid=
uuid del array a ensamblar. Los dispositivos que no tengan este uuid se excluirán.
-m, --super-minor=
Número menor del dispositivo para el que se creó el array. Los dispositivos que no tengan este número menor se excluirán. Si crea un array como /dev/md1, entonces todas las superbloques contendrán el número menor 1, incluso si el array se ensambla posteriormente como /dev/md2.

Dar la palabra literal "dev" para --super-minor hará que mdadm use el número menor del dispositivo md que se está ensamblando. Por ejemplo, al ensamblar /dev/md0, --super-minor=dev buscará superbloques con un número menor de 0.

--super-minor solo es relevante para metadatos v0.90, y normalmente no debe usarse. Usar --uuid es mucho más seguro.

-N, --name=
Especifica el nombre del array a ensamblar. Debe ser compatible con NOMBRE PORTABLE POSIX y no puede tener más de 32 caracteres. Este debe ser el nombre que se especificó al crear el array. Debe coincidir exactamente con el nombre almacenado en la superbloque, o debe coincidir con el homehost actual prefijado al inicio del nombre dado.
-f, --force
Ensambla el array incluso si los metadatos de algunos dispositivos parecen estar desactualizados. Si mdadm no puede encontrar suficientes dispositivos que funcionen para iniciar el array, pero puede encontrar algunos dispositivos que están registrados como fallidos, entonces marcará esos dispositivos como que funcionan para que el array pueda iniciarse. Esto solo funciona para nativos. Para metadatos externos, permite iniciar RAID 4, 5, 6 degradado y sucio. Un array que requiere --force para iniciarse puede contener corrupción de datos. Úselo con cuidado.
-R, --run
Intenta iniciar el array incluso si se proporcionaron menos unidades de las que estaban presentes la última vez que el array estuvo activo. Normalmente, si no se encuentran todas las unidades esperadas y no se usa --scan, entonces el array se ensamblará pero no se iniciará. Con --run se intentará iniciarlo de todos modos.

Para la gestión activa de arrays:

-a, --add
Añadir dispositivos listados al array. Si se quiere que un dispositivo que parece ser un miembro reciente del array se añada como repuesto, primero hay que añadirlo con --spare. El dispositivo se añadirá como repuesto aunque parezca ser un miembro reciente del array.
-r, --remove
Eliminar los dispositivos listados. No deben estar activos, es decir, deben ser dispositivos fallidos o de repuesto.

Además del nombre de un archivo de dispositivo (por ejemplo, /dev/sda1), se pueden dar las palabras failed, detached y nombres como set-A a --remove. La primera elimina todos los dispositivos fallidos. La segunda elimina cualquier dispositivo que ya no esté conectado al sistema (es decir, una llamada a 'open' devuelve ENXIO). La tercera elimina un conjunto como se describe a continuación en --fail.

-f, --fail
Marcar los dispositivos listados como defectuosos. Además del nombre de un archivo de dispositivo, se puede dar la palabra detached o un nombre de conjunto como set-A. La primera hará que se marquen como fallidos todos los dispositivos que se hayan desconectado del sistema. Luego se podrán eliminar.

Para arrays RAID10 donde el número de copias divide uniformemente el número de dispositivos, los dispositivos pueden dividirse conceptualmente en conjuntos donde cada conjunto contiene una única copia completa de los datos en el array. A veces, un array RAID10 se configura de tal manera que estos conjuntos están en controladores separados. En este caso, todos los dispositivos de un conjunto pueden marcarse como fallidos dando un nombre como set-A o set-B a --fail. Los nombres de conjunto apropiados se informan con --detail.

--set-faulty
igual que --fail.
--replace
Marcar los dispositivos listados como que requieren reemplazo. Tan pronto como haya un repuesto disponible, se reconstruirá y reemplazará el dispositivo marcado. Esto es similar a marcar un dispositivo como defectuoso, pero el dispositivo permanece en servicio durante el proceso de recuperación para aumentar la resiliencia contra fallos múltiples. Cuando el proceso de reemplazo finalice, el dispositivo reemplazado se marcará como defectuoso.
--with
Esto puede seguir a una lista de dispositivos de --replace. Los dispositivos listados después de --with se utilizarán preferentemente para reemplazar los dispositivos listados después de --replace. Estos dispositivos ya deben ser dispositivos de repuesto en el array.
--write-mostly
Los dispositivos subsiguientes que se añadan o se vuelvan a añadir tendrán el indicador 'write-mostly' activado. Esto solo es válido para RAID1 y significa que el controlador 'md' evitará leer de estos dispositivos si es posible.
--readwrite
Los dispositivos subsiguientes que se añadan o se vuelvan a añadir tendrán el indicador 'write-mostly' desactivado.
--cluster-confirm
Confirmar la existencia del dispositivo. Esto se emite en respuesta a una solicitud de --add por parte de un nodo en un clúster. Cuando un nodo añade un dispositivo, envía un mensaje a todos los nodos del clúster para que busquen un dispositivo con un UUID. Esto se traduce en una notificación de udev con el UUID del dispositivo a añadir y el número de ranura. El nodo receptor debe acusar recibo de este mensaje con --cluster-confirm. Los argumentos válidos son <ranura>:<nombre_dispositivo> en caso de que se encuentre el dispositivo, o <ranura>:missing en caso de que no se encuentre el dispositivo.
--add-journal
Añadir un journal a un array existente, o recrear el journal para un array RAID-4/5/6 que haya perdido un dispositivo journal. Para evitar interrumpir las operaciones de escritura en curso, --add-journal solo funciona para arrays en estado de solo lectura.
--failfast
Los dispositivos subsiguientes que se añadan o se vuelvan a añadir tendrán el indicador 'failfast' activado. Esto solo es válido para RAID1 y RAID10 y significa que el controlador 'md' evitará tiempos de espera largos en el manejo de errores siempre que sea posible.
--nofailfast
Los dispositivos subsiguientes que se vuelvan a añadir se añadirán sin el indicador 'failfast' activado.

Cada una de estas opciones requiere que el primer dispositivo listado sea el array sobre el que se va a actuar, y los restantes sean los dispositivos componentes que se van a añadir, eliminar, marcar como defectuosos, etc. Se pueden especificar varias operaciones diferentes para distintos dispositivos, por ejemplo:
mdadm /dev/md0 --add /dev/sda1 --fail /dev/sdb1 --remove /dev/sdb1
Cada operación se aplica a todos los dispositivos listados hasta la siguiente operación.

Si un array está utilizando un bitmap de intento de escritura, los dispositivos que se han eliminado se pueden volver a añadir de forma que se evite una reconstrucción completa, actualizando en su lugar solo los bloques que han cambiado desde que se eliminó el dispositivo. Para arrays con metadatos persistentes (superbloques), esto se hace automáticamente. Para arrays creados con --build, mdadm necesita que se le indique que este dispositivo se eliminó recientemente con --re-add.

Los dispositivos solo pueden eliminarse de un array si no están en uso activo, es decir, deben ser repuestos o dispositivos fallidos. Para eliminar un dispositivo activo, primero debe marcarse como faulty.

Para el modo Misc:

-Q, --query
Examinar un dispositivo para ver (1) si es un dispositivo md y (2) si es un componente de un array md. Se presenta información sobre lo que se descubre.
-D, --detail
Mostrar detalles de uno o más dispositivos md.
--detail-platform
Mostrar detalles de las capacidades RAID de la plataforma (firmware / topología de hardware) para un formato de metadatos dado. Si se utiliza sin argumento, mdadm escaneará todos los controladores buscando sus capacidades. De lo contrario, mdadm solo examinará el controlador especificado por el argumento en forma de ruta de archivo absoluta o enlace, por ejemplo, /sys/devices/pci0000:00/0000:00:1f.2.
-Y, --export
Cuando se usa con --detail, --detail-platform, --examine o --incremental, la salida se formateará como pares clave=valor para una fácil importación en el entorno.

Con --incremental, el valor MD_STARTED indica si un array se inició (yes) o no, lo que puede incluir una razón (unsafe, nothing, no). También el valor MD_FOREIGN indica si el array se espera en este host (no), o si parece ser de otro lugar (yes).

-E, --examine
Mostrar el contenido de los metadatos almacenados en el(los) dispositivo(s) nombrado(s). Nótese el contraste entre --examine y --detail. --examine se aplica a los dispositivos que son componentes de un array, mientras que --detail se aplica a un array completo que está actualmente activo.
-X, --examine-bitmap
Informar sobre un archivo de bitmap. El argumento es un archivo de bitmap externo o un componente de array en caso de un bitmap interno. Tenga en cuenta que ejecutar esto en un dispositivo de array (por ejemplo, /dev/md0) no informa el bitmap de ese array.
--examine-badblocks
Listar los bloques defectuosos registrados para el dispositivo, si se ha configurado una lista de bloques defectuosos. Actualmente, solo los metadatos de 1.x e IMSM admiten listas de bloques defectuosos.
--dump=directorio
--restore=directorio
Guardar metadatos de los dispositivos listados, o restaurar metadatos a los dispositivos listados.
-R, --run
iniciar un array parcialmente ensamblado. Si --assemble no encontró suficientes dispositivos para iniciar completamente el array, puede dejarlo parcialmente ensamblado. Si lo desea, puede usar --run para iniciar el array en modo degradado.
-S, --stop
desactivar el array, liberando todos los recursos.
-o, --readonly
marcar el array como solo lectura.
-w, --readwrite
marcar el array como lectura/escritura.
--zero-superblock
Si el dispositivo contiene un superbloque md válido, el bloque se sobrescribe con ceros. Con --force, el bloque donde estaría el superbloque se sobrescribe incluso si no parece ser válido.

Nota: Tenga cuidado al llamar a --zero-superblock con RAID en clúster. Asegúrese de que el array no se está utilizando ni ensamblando en otro nodo del clúster antes de ejecutarlo.

--kill-subarray=
Si el dispositivo es un contenedor y el argumento de --kill-subarray especifica un subarray inactivo en el contenedor, entonces el subarray se elimina. Eliminar todos los subarrays dejará un 'contenedor vacío' o un superbloque de repuesto en las unidades. Consulte --zero-superblock para eliminar completamente un superbloque. Tenga en cuenta que algunos formatos dependen del índice del subarray para generar un UUID; este comando fallará si cambia el UUID de un subarray activo.
--update-subarray=
Si el dispositivo es un contenedor y el argumento de --update-subarray especifica un subarray en el contenedor, entonces se intenta actualizar el campo especificado del superbloque en el subarray. Consulte más abajo en MODO MISC para obtener detalles.
-t, --test
Cuando se usa con --detail, el estado de salida de mdadm se establece para reflejar el estado del dispositivo. Consulte más abajo en MODO MISC para obtener detalles.
-W, --wait
Para cada dispositivo md proporcionado, espere a que finalice cualquier actividad de resincronización, recuperación o remodelación antes de devolver el control. mdadm devolverá éxito si realmente esperó a cada dispositivo listado, de lo contrario devolverá fallo.
--wait-clean
Para cada dispositivo md proporcionado, o cada dispositivo en /proc/mdstat si se proporciona --scan, haga que el array se marque como limpio lo antes posible. mdadm devolverá éxito si el array usa metadatos externos y hemos esperado correctamente. Para arrays nativos, esto devuelve el control inmediatamente ya que el kernel maneja la limpieza de suciedad.

MODO CREATE

Uso: mdadm --create md-device --chunk=X --level=Y --raid-devices=Z dispositivos

Este uso inicializará una nueva matriz md, asociará algunos dispositivos con ella y activará la matriz.

md-device es un nuevo dispositivo. Podría ser un nombre estándar o un nombre elegido. Para más detalles, ver: DEVICE NAMES

El dispositivo nombrado normalmente no existirá cuando se ejecute mdadm --create, sino que será creado por udev una vez que la matriz se active.

La longitud máxima del nombre de md-device está limitada a 32 caracteres. Diferentes tipos de metadatos tienen limitaciones más estrictas (como IMSM, donde solo se permiten 16 caracteres). Por esa razón, un nombre largo podría ser truncado o rechazado, depende de la política de metadatos.

A medida que se agregan los dispositivos, se verifica si contienen superbloques RAID o sistemas de archivos. También se verifica si la varianza en el tamaño de los dispositivos excede el 1%.

Si se encuentra alguna discrepancia, la matriz no se ejecutará automáticamente, aunque la presencia de --run puede anular esta precaución.

Para crear una matriz "degradada" en la que faltan algunos dispositivos, simplemente introduzca la palabra "missing" en lugar de un nombre de dispositivo. Esto hará que mdadm deje vacía la ranura correspondiente en la matriz. Para una matriz RAID4 o RAID5, como máximo una ranura puede estar "missing"; para una matriz RAID6, como máximo dos ranuras. Para una matriz RAID1, solo se necesita un dispositivo real. Todos los demás pueden ser "missing".

Al crear una matriz RAID5, mdadm creará automáticamente una matriz degradada con una unidad de repuesto adicional. Esto se debe a que construir la unidad de repuesto en una matriz degradada es, en general, más rápido que resincronizar la paridad en una matriz no degradada pero no limpia. Esta característica se puede anular con la opción --force.

Al crear una matriz basada en particiones, usando mdadm con metadatos de la versión 1.x, el tipo de partición debe establecerse en 0xDA (datos no fs). Este tipo de selección permite una mayor precisión ya que el uso de cualquier otro (detección automática de RAID (0xFD) o una partición GNU/Linux (0x83)) podría crear problemas en caso de recuperación de la matriz a través de un live CD.

Una nueva matriz normalmente obtendrá un UUID de 128 bits asignado aleatoriamente que es muy probable que sea único. Si tiene una necesidad específica, puede elegir un UUID para la matriz dando la opción --uuid=. Tenga en cuenta que crear dos matrices con el mismo UUID es una receta para el desastre. Además, usar --uuid= al crear una matriz v0.90 anulará silenciosamente cualquier configuración de --homehost=.

Si el tipo de matriz admite un bitmap de intención de escritura, y si los dispositivos en la matriz superan los 100 GB de tamaño, se agregará automáticamente un bitmap de intención de escritura interno, a menos que se solicite explícitamente alguna otra opción con la opción --bitmap o se seleccione una política de consistencia diferente con la opción --consistency-policy. En cualquier caso, se reservará espacio para un bitmap para que se pueda agregar más tarde con --grow --bitmap=internal.

Si el tipo de metadatos lo admite (actualmente solo metadatos 1.x e IMSM), se asignará espacio para almacenar una lista de bloques defectuosos. Esto permite registrar un número moderado de bloques defectuosos, permitiendo que la unidad permanezca en servicio mientras solo está parcialmente funcional.

Al crear una matriz dentro de un CONTAINER, a mdadm se le puede dar la lista de dispositivos a usar, o simplemente el nombre del contenedor. El primer caso da control sobre qué dispositivos en el contenedor se usarán para la matriz. El segundo caso permite que mdadm elija automáticamente qué dispositivos usar basándose en la cantidad de espacio libre disponible.

Las opciones de Gestión General que son válidas con --create son:

--run
insiste en ejecutar la matriz incluso si algunos dispositivos parecen estar en uso.
--readonly
inicia la matriz en modo de solo lectura.

MODO MANAGE

Uso: mdadm dispositivo opciones... dispositivos...

Este uso permitirá fallar, eliminar o agregar dispositivos individuales en una matriz. Es posible realizar múltiples operaciones con un solo comando. Por ejemplo:
mdadm /dev/md0 -f /dev/hda1 -r /dev/hda1 -a /dev/hda1
primero marcará /dev/hda1 como defectuoso en /dev/md0 y luego lo eliminará de la matriz y finalmente lo agregará como repuesto. Sin embargo, solo una matriz md puede ser afectada por un solo comando.

Cuando se agrega un dispositivo a una matriz activa, mdadm verifica si tiene metadatos en él que sugieren que fue miembro de la matriz recientemente. Si es así, intenta "volver a agregar" el dispositivo. Si no ha habido cambios desde que se eliminó el dispositivo, o si la matriz tiene un bitmap de intención de escritura que ha registrado los cambios que hubo, el dispositivo se convertirá inmediatamente en un miembro completo de la matriz y las diferencias registradas en el bitmap se resolverán.

MODO MISC

Uso: mdadm opciones ... dispositivos ...

El modo MISC incluye una serie de operaciones distintas que operan en dispositivos distintos. Las operaciones son:

--query
Se examina el dispositivo para ver si es (1) una matriz md activa, o (2) un componente de una matriz md. Se informa la información descubierta.
--detail
El dispositivo debe ser un dispositivo md activo. mdadm mostrará una descripción detallada de la matriz. --brief o --scan hará que la salida sea menos detallada y el formato sea adecuado para su inclusión en mdadm.conf. El estado de salida de mdadm normalmente será 0, a menos que mdadm no haya podido obtener información útil sobre los dispositivos; sin embargo, si se proporciona la opción --test, el estado de salida será:
0
La matriz funciona normalmente.
1
La matriz tiene al menos un dispositivo defectuoso.
2
La matriz tiene múltiples dispositivos defectuosos que la hacen inutilizable.
4
Hubo un error al intentar obtener información sobre el dispositivo.
--detail-platform
Imprime detalles de las capacidades RAID de la plataforma (firmware / topología de hardware). Si se especifican metadatos con -e o --metadata=, el estado de retorno será:
0
los metadatos enumeraron con éxito sus componentes de plataforma en este sistema
1
los metadatos son independientes de la plataforma
2
los metadatos no pudieron encontrar sus componentes de plataforma en este sistema
--update-subarray=
Si el dispositivo es un contenedor y el argumento de --update-subarray especifica una submatriz en el contenedor, intente actualizar el campo especificado de la superbloque en la submatriz. Similar a actualizar una matriz en modo "assemble", el campo a actualizar se selecciona mediante la opción -U o --update=. Las opciones soportadas son name, ppl, no-ppl, bitmap y no-bitmap.

La opción name actualiza el nombre de la submatriz en los metadatos. Debe ser compatible con el NOMBRE PORTÁTIL POSIX y no puede tener más de 32 caracteres. Si tiene éxito, el nuevo valor se respetará después del próximo ensamblaje.

Las opciones ppl y no-ppl habilitan y deshabilitan PPL en los metadatos. Actualmente solo se soporta para submatrices IMSM.

Las opciones bitmap y no-bitmap habilitan y deshabilitan el bitmap de intención de escritura en los metadatos. Actualmente solo se soporta para submatrices IMSM.

--examine
El dispositivo debe ser un componente de una matriz md. mdadm leerá la superbloque md del dispositivo y mostrará su contenido. Si se proporciona --brief o --scan, múltiples dispositivos que son componentes de la misma matriz se agruparán y se informarán en una sola entrada adecuada para su inclusión en mdadm.conf.

Tener --scan sin listar ningún dispositivo hará que se examinen todos los dispositivos listados en el archivo de configuración.

--dump=directorio
Si el dispositivo contiene metadatos RAID, se creará un archivo en el directorio y se escribirán los metadatos en él. El archivo tendrá el mismo tamaño que el dispositivo y contendrá los metadatos en la misma ubicación en la que existen en el dispositivo. Sin embargo, el archivo será "disperso" (sparse) para que solo se asignen los bloques que contienen metadatos. El espacio total utilizado será pequeño.

El nombre de archivo utilizado en el directorio será el nombre base del dispositivo. Además, si aparecen enlaces en /dev/disk/by-id que apuntan al dispositivo, se crearán enlaces duros al archivo en el directorio basándose en estos nombres de by-id.

Se pueden listar múltiples dispositivos y sus metadatos se almacenarán todos en el mismo directorio.

--restore=directorio
Este es el inverso de --dump. mdadm localizará un archivo en el directorio que tenga un nombre apropiado para el dispositivo dado y restaurará los metadatos desde él. Se prefieren los nombres que coinciden con los nombres de /dev/disk/by-id, sin embargo, si dos de ellos se refieren a archivos diferentes, mdadm no elegirá entre ellos sino que abortará la operación.

Si se proporciona un nombre de archivo en lugar de un directorio, entonces mdadm restaurará desde ese archivo a un único dispositivo, siempre y cuando el tamaño del archivo coincida

Estas operaciones se aplican a md arrays especificados en la línea de comandos, o a todos los md arrays si se especifica --scan.

--assemble, -a
Ensambla un md array. Esto es necesario si el array está configurado, pero no está activo. Si se proporciona un nombre de dispositivo (por ejemplo, /dev/md0), se intentará ensamblar ese dispositivo. Si no se proporciona ningún nombre de dispositivo, se intentará ensamblar todos los dispositivos md que puedan ser ensamblados. --assemble, -a

--stop
Los dispositivos deben ser arrays md activos que se desactivarán, siempre que no estén actualmente en uso.
--run
Esto activará completamente un array md parcialmente ensamblado.
--readonly
Esto marcará un array activo como de solo lectura, siempre que no se esté utilizando actualmente.
--readwrite
Esto cambiará un array readonly para que vuelva a ser de lectura/escritura.
--scan

-b, --brief
Ser menos verboso. Esto se utiliza con --detail y --examine. Usar --brief con --verbose proporciona un nivel intermedio de verbosidad.

MODO MONITOR

Uso: mdadm --monitor opciones... dispositivos...

La opción de monitorización puede funcionar en dos modos:

  • modo a nivel de sistema, seguir todos los dispositivos md basados en /proc/mdstat,
  • seguir solo los dispositivos MD especificados en la línea de comandos.

--scan - indica el modo a nivel de sistema. La opción hace que el monitor rastree todos los dispositivos md que aparecen en /proc/mdstat. Si no está configurada, entonces se debe especificar al menos un dispositivo.

El uso del monitor hace que mdadm consulte periódicamente un número de arrays md y que informe sobre cualquier evento detectado.

En ambos modos, el monitor funcionará siempre que haya un array activo con redundancia y esté configurado para ser seguido (para --scan se sigue todos los arrays).

Además de informar sobre eventos, mdadm puede mover una unidad de repuesto de un array a otro si están en el mismo spare-group o domain y si el array de destino tiene una unidad fallida pero ninguna unidad de repuesto.

El resultado de la monitorización de los arrays es la generación de eventos. Estos eventos se pasan a un programa separado (si se especifica) y pueden ser enviados por correo a una dirección de correo electrónico dada.

Al pasar eventos a un programa, el programa se ejecuta una vez por cada evento y recibe 2 o 3 argumentos de línea de comandos: el primero es el nombre del evento (ver abajo), el segundo es el nombre del dispositivo md afectado y el tercero es el nombre de un dispositivo relacionado si es relevante (como un dispositivo componente que ha fallado).

Si se proporciona --scan, entonces se debe especificar un programa o una dirección de correo electrónico en la línea de comandos o en el archivo de configuración. Si no hay ninguno disponible, entonces mdadm no monitorizará nada. Para los dispositivos proporcionados directamente en la línea de comandos, sin especificar programa o correo electrónico, cada evento se informa a stdout.

Nota: En sistemas donde la monitorización de mdadm se gestiona a través de systemd, el servicio mdmonitor.service debe estar presente. Este servicio está diseñado para ser la solución principal para la monitorización de arrays. Está configurado para operar en modo de sistema completo. Se inicia mediante udev cuando se cumplen los criterios de inicio, por ejemplo, existe mdadm.conf y se establecen los parámetros de configuración necesarios. Se mantiene activo mientras un array RAID redundante esté activo; se detiene de lo contrario. El usuario debe personalizar MAILADDR en mdadm.conf para recibir notificaciones por correo. MONITORDELAY, MAILFROM y PROGRAM son opcionales. Consulte mdadm.conf(5) para una descripción detallada de estas opciones. Utilice systemctl status mdmonitor.service para verificar el estado o determinar si se necesita configuración adicional.

Los diferentes eventos son:

DeviceDisappeared
Un array md que anteriormente estaba configurado parece ya no estar configurado. (prioridad syslog: Crítica)

Si a mdadm se le indicó que monitorizara un array que es RAID0 o Lineal, entonces informará DeviceDisappeared con la información adicional Wrong-Level. Esto se debe a que RAID0 y Lineal no admiten las operaciones de fallo de dispositivo, hot-spare y resincronización que se monitorizan.

RebuildStarted
Un array md comenzó la reconstrucción (por ejemplo, recuperación, sincronización, remodelación, comprobación, reparación). (prioridad syslog: Advertencia)
RebuildNN
Donde NN es un número de dos dígitos (por ejemplo, 05, 48). Esto indica que la reconstrucción ha alcanzado ese porcentaje del total. Los eventos se generan a un incremento fijo a partir de 0. El tamaño del incremento puede especificarse con una opción de línea de comandos (el valor predeterminado es 20). (prioridad syslog: Advertencia)
RebuildFinished
Un array md que se estaba reconstruyendo, ya no lo está, ya sea porque terminó normalmente o fue abortado. (prioridad syslog: Advertencia)
Fail
Un dispositivo componente activo de un array ha sido marcado como defectuoso. (prioridad syslog: Crítica)
FailSpare
Un dispositivo componente de repuesto que se estaba reconstruyendo para reemplazar un dispositivo defectuoso ha fallado. (prioridad syslog: Crítica)
SpareActive
Un dispositivo componente de repuesto que se estaba reconstruyendo para reemplazar un dispositivo defectuoso se ha reconstruido correctamente y se ha activado. (prioridad syslog: Info)
NewArray
Se ha detectado un nuevo array md en el archivo /proc/mdstat. (prioridad syslog: Info)
DegradedArray
Un array recién detectado parece estar degradado. Este mensaje no se genera cuando mdadm detecta un fallo de unidad que causa degradación, sino solo cuando mdadm detecta que un array está degradado cuando lo ve por primera vez. (prioridad syslog: Crítica)
MoveSpare
Una unidad de repuesto se ha movido de un array en un spare-group o domain a otro para permitir el reemplazo de una unidad fallida. (prioridad syslog: Info)
SparesMissing
Si a mdadm se le ha indicado, a través del archivo de configuración, que un array debe tener un cierto número de dispositivos de repuesto, y mdadm detecta que tiene menos que ese número cuando lo ve por primera vez, informará un mensaje SparesMissing. (prioridad syslog: Advertencia)
TestMessage
Se encontró un array al iniciar y se proporcionó la bandera --test. (prioridad syslog: Info)

Solo Fail, FailSpare, DegradedArray, SparesMissing y TestMessage causan el envío de correo electrónico. Todos los eventos hacen que el programa se ejecute. El programa se ejecuta con dos o tres argumentos: el nombre del evento, el dispositivo del array y posiblemente un segundo dispositivo.

Cada evento tiene un dispositivo de array asociado (por ejemplo, /dev/md1) y posiblemente un segundo dispositivo. Para Fail, FailSpare y SpareActive el segundo dispositivo es el dispositivo componente relevante. Para MoveSpare el segundo dispositivo es el array del que se movió la unidad de repuesto.

Para que mdadm mueva unidades de repuesto de un array a otro, los diferentes arrays deben ser etiquetados con el mismo spare-group o las unidades de repuesto deben poder migrar a través de dominios POLICY coincidentes en el archivo de configuración. El nombre de spare-group puede ser cualquier cadena; solo es necesario que diferentes grupos de repuesto utilicen nombres diferentes.

Cuando mdadm detecta que un array en un grupo de repuesto tiene menos dispositivos activos de los necesarios para el array completo, y no tiene dispositivos de repuesto, buscará otro array en el mismo grupo de repuesto que tenga un conjunto completo de unidades de trabajo y una unidad de repuesto. Luego intentará eliminar la unidad de repuesto del segundo array y agregarla al primero. Si la eliminación tiene éxito pero la adición falla, entonces se vuelve a agregar al array original.

Si el grupo de repuesto para un array degradado no está definido, mdadm examinará las reglas de migración de repuestos especificadas por las líneas POLICY en mdadm.conf y luego seguirá pasos similares a los anteriores si se encuentra una unidad de repuesto coincidente.

MODO GROW

El modo GROW se utiliza para cambiar el tamaño o la forma de un array activo.

Se admiten los siguientes cambios:

  • cambiar el atributo "size" para RAID1, RAID4, RAID5 y RAID6.
  • aumentar o disminuir el atributo "raid-devices" de RAID0, RAID1, RAID4, RAID5 y RAID6.
  • cambiar el tamaño del bloque (chunk-size) y el diseño (layout) de RAID0, RAID4, RAID5, RAID6 y RAID10.
  • convertir entre RAID1 y RAID5, entre RAID5 y RAID6, entre RAID0, RAID4 y RAID5, y entre RAID0 y RAID10 (en el modo near-2).
  • agregar un bitmap de escritura (write-intent bitmap) a cualquier array que soporte estos bitmaps, o eliminar un bitmap de escritura de dicho array.
  • cambiar la política de consistencia del array.

El uso de GROW en contenedores solo se admite actualmente para el formato de metadatos de contenedor IMSM de Intel. Se puede aumentar el número de dispositivos en un contenedor, lo que afecta a todos los arrays del contenedor, o se puede convertir un array en un contenedor entre niveles donde esos niveles sean compatibles con el contenedor, y la conversión sea una de las mencionadas anteriormente.

Notas:

  • El punto de control nativo de Intel no utiliza la opción --backup-file y es transparente para la función de ensamblaje.
  • La itinerancia entre sistemas Windows(R) y Linux para metadatos IMSM no se admite durante el proceso de crecimiento.
  • Al crecer un dispositivo raid0, el nuevo tamaño del disco componente (o el tamaño de respaldo externo) debe ser mayor que LCM(antiguo, nuevo) * chunk-size * 2, donde LCM() es el mínimo común múltiplo del número antiguo y nuevo de discos componentes, y "* 2" proviene del hecho de que mdadm se niega a usar más de la mitad de un dispositivo de repuesto para espacio de respaldo.

CAMBIOS DE TAMAÑO

Para cambiar el tamaño de un array activo (RAID1, RAID4, RAID5, RAID6), se deben utilizar las opciones --grow --size= o --grow --size=. El nuevo tamaño se especifica en el número de sectores.

CAMBIOS DE TAMAÑO

Normalmente, cuando se crea una matriz, el "tamaño" se toma del más pequeño de las unidades. Si todas las unidades pequeñas de una matriz se eliminan con el tiempo y se reemplazan por unidades más grandes, entonces podrías tener una matriz de unidades grandes con solo una pequeña parte utilizada. En esta situación, cambiar el "tamaño" con el modo "GROW" permitirá que el espacio adicional comience a utilizarse. Si el tamaño se incrementa de esta manera, se iniciará un proceso de "resincronización" para asegurar que las nuevas partes de la matriz estén sincronizadas.

Tenga en cuenta que cuando una matriz cambia de tamaño, cualquier sistema de archivos que pueda estar almacenado en la matriz no crecerá ni se reducirá automáticamente para usar o liberar el espacio. El sistema de archivos deberá indicarse explícitamente que utilice el espacio adicional después de crecer, o que reduzca su tamaño **antes** de reducir la matriz.

Además, el tamaño de una matriz no se puede cambiar mientras tenga un mapa de bits activo. Si una matriz tiene un mapa de bits, debe eliminarse antes de que se pueda cambiar el tamaño. Una vez completado el cambio, se puede crear un nuevo mapa de bits.

Nota: **--grow --size** aún no es compatible con mapas de bits de archivos externos.

CAMBIOS DE DISPOSITIVOS RAID

Una matriz RAID1 puede funcionar con cualquier número de dispositivos desde 1 hacia arriba (aunque 1 no es muy útil). Puede haber momentos en los que desee aumentar o disminuir el número de dispositivos activos. Tenga en cuenta que esto es diferente de hot-add o hot-remove, que cambian el número de dispositivos inactivos.

Al reducir el número de dispositivos en una matriz RAID1, las ranuras que se van a eliminar de la matriz deben estar vacías. Es decir, los dispositivos que estaban en esas ranuras deben haber fallado y sido eliminados.

Cuando se aumenta el número de dispositivos, las unidades de respaldo activas que estén presentes se activarán de inmediato.

Cambiar el número de dispositivos activos en RAID5 o RAID6 es mucho más laborioso. Cada bloque de la matriz deberá leerse y reescribirse en una nueva ubicación. El kernel de Linux puede aumentar o disminuir de forma segura el número de dispositivos en RAID5 y RAID6, incluso reiniciando un "reshape" interrumpido.

El kernel de Linux puede convertir un RAID0 en un RAID4 o RAID5. *mdadm* utiliza esta funcionalidad y la capacidad de agregar dispositivos a un RAID4 para permitir que se agreguen dispositivos a un RAID0. Cuando se le solicita hacer esto, *mdadm* convertirá el RAID0 a un RAID4, agregará los discos necesarios y realizará el reshape, y luego convertirá el RAID4 de nuevo a RAID0.

Al disminuir el número de dispositivos, el tamaño de la matriz también disminuirá. Si había datos en la matriz, podrían destruirse y esto no es reversible, por lo que primero debe reducir el sistema de archivos en la matriz para que se ajuste al nuevo tamaño. Para ayudar a prevenir accidentes, *mdadm* requiere que el tamaño de la matriz se reduzca primero con **mdadm --grow --array-size**. Este es un cambio reversible que simplemente hace que el final de la matriz sea inaccesible. La integridad de cualquier dato se puede verificar antes de solicitar la reducción no reversible del número de dispositivos.

Al reubicar las primeras franjas en un RAID5 o RAID6, no es posible mantener los datos en el disco completamente consistentes y a prueba de fallos. Para proporcionar la seguridad requerida, mdadm deshabilita las escrituras en la matriz mientras se reforma esta "sección crítica" y toma una copia de seguridad de los datos que se encuentran en esa sección. Para los aumentos, esta copia de seguridad puede almacenarse en unidades de repuesto que tenga la matriz, sin embargo, también puede almacenarse en un archivo separado especificado con la opción **--backup-file**, y se requiere que se especifique para reducciones, cambios de nivel RAID y cambios de diseño. Si se utiliza esta opción, y el sistema falla durante el período crítico, se debe pasar el mismo archivo a **--assemble** para restaurar la copia de seguridad y volver a montar la matriz. Al reducir en lugar de aumentar la matriz, el reshape se realiza desde el final hacia el principio, por lo que la "sección crítica" se encuentra al final del reshape.

CAMBIOS DE NIVEL

El cambio del nivel RAID de cualquier matriz ocurre instantáneamente. Sin embargo, en el caso de RAID5 a RAID6, esto requiere un diseño no estándar de los datos RAID6, y en el caso de RAID6 a RAID5, ese diseño no estándar es requerido antes de que el cambio pueda completarse. Por lo tanto, aunque el cambio de nivel es instantáneo, el cambio de diseño que lo acompaña puede llevar mucho tiempo. Se requiere un **--backup-file**. Si la matriz no se está expandiendo o contrayendo simultáneamente, de modo que el tamaño de la matriz permanecerá igual - por ejemplo, reformando un RAID5 de 3 unidades en un RAID6 de 4 unidades - el archivo de copia de seguridad se utilizará no solo para una "sección crítica" sino durante toda la operación de reshape, como se describe a continuación en CAMBIOS DE DISEÑO.

CAMBIOS DE TAMAÑO DE CHUNK Y DISEÑO

Cambiar el tamaño del chunk o el diseño sin cambiar el número de dispositivos al mismo tiempo implicará reescribir todos los bloques en su lugar. Para garantizar la protección contra la pérdida de datos en caso de fallo, se debe proporcionar un **--backup-file** para estos cambios. Pequeñas secciones de la matriz se copiarán al archivo de copia de seguridad mientras se reorganizan. Esto significa que todos los datos se copian dos veces, una al archivo de copia de seguridad y otra al nuevo diseño en la matriz, por lo que este tipo de reshape será muy lento.

Si el reshape se interrumpe por cualquier motivo, este archivo de copia de seguridad debe estar disponible para **mdadm --assemble** para que la matriz pueda ser reensamblada. En consecuencia, el archivo no puede almacenarse en el dispositivo que se está reformando.

CAMBIOS DE BITMAP

Se puede agregar o eliminar un mapa de bits de intención de escritura de una matriz activa. Se pueden agregar mapas de bits internos o mapas de bits almacenados en un archivo separado. Tenga en cuenta que si agrega un mapa de bits almacenado en un archivo que se encuentra en un sistema de archivos en la matriz RAID que se está afectando, el sistema se bloqueará. El mapa de bits debe estar en un sistema de archivos separado.

CAMBIOS DE POLÍTICA DE CONSISTENCIA

La política de consistencia de una matriz activa se puede cambiar utilizando la opción **--consistency-policy** en el modo Grow. Actualmente, esto solo funciona para las políticas **ppl** y **resync** y permite habilitar o deshabilitar el Registro Parcial de Paridad RAID5 (PPL).

MODO INCREMENTAL

Uso: **mdadm --incremental** [**--run**] [**--quiet**] *dispositivo_componente* [*alias_opcionales_para_dispositivo*]

Uso: **mdadm --incremental --fail** *dispositivo_componente*

Uso: **mdadm --incremental --rebuild-map**

Uso: **mdadm --incremental --run --scan**

Este modo está diseñado para usarse junto con un sistema de descubrimiento de dispositivos. A medida que se encuentran dispositivos en un sistema, se pueden pasar a **mdadm --incremental** para agregarlos condicionalmente a una matriz apropiada.

Por el contrario, también se puede usar con el indicador **--fail** para hacer exactamente lo contrario y encontrar la matriz de la que forma parte un dispositivo en particular y eliminar el dispositivo de esa matriz.

Si el dispositivo pasado es un dispositivo **CONTAINER** creado por una llamada anterior a *mdadm*, en lugar de intentar agregar ese dispositivo a una matriz, se iniciarán todas las matrices descritas por los metadatos del contenedor.

*mdadm* realiza una serie de pruebas para determinar si el dispositivo forma parte de una matriz y de qué matriz debería formar parte. Si se encuentra una matriz apropiada, o se puede crear una, *mdadm* agrega el dispositivo a la matriz y la inicia condicionalmente.

Tenga en cuenta que *mdadm* normalmente solo agregará dispositivos a una matriz que anteriormente fueron partes activas (o de repuesto) de esa matriz. El soporte para la inclusión automática de una nueva unidad como repuesto en alguna matriz requiere una configuración a través de POLICY en el archivo de configuración.

Las pruebas que realiza *mdadm* son las siguientes:

+
¿El dispositivo está permitido por **mdadm.conf**? Es decir, ¿está listado en una línea **DEVICES** en ese archivo? Si **DEVICES** está ausente, el valor predeterminado es permitir cualquier dispositivo. De manera similar, si **DEVICES** contiene la palabra especial **partitions**, se permite cualquier dispositivo. De lo contrario, el nombre del dispositivo proporcionado a *mdadm*, o uno de los alias proporcionados, o un alias encontrado en el sistema de archivos, debe coincidir con uno de los nombres o patrones en una línea **DEVICES**.

Este es el único contexto donde se utilizan los alias. Normalmente son proporcionados por reglas *udev* que mencionan **$env{DEVLINKS}**.

+
¿El dispositivo tiene una superbloque md válida? Si se solicita una versión de metadatos específica con **--metadata** o **-e**, solo se acepta ese estilo de metadatos, de lo contrario *mdadm* encuentra cualquier versión conocida de metadatos. Si no se encuentran metadatos *md*, el dispositivo aún puede agregarse a una matriz como repuesto si POLICY lo permite.

*mdadm* mantiene una lista de matrices que ha ensamblado parcialmente en **/run/mdadm/map**. Si no existe ninguna matriz que coincida con los metadatos del nuevo dispositivo, *mdadm* debe elegir un nombre de dispositivo y un número de unidad. Lo hace basándose en cualquier nombre proporcionado en **mdadm.conf** o en cualquier información de nombre almacenada en los metadatos. Si este nombre sugiere un número de unidad, se utilizará ese número; de lo contrario, se elegirá un número de unidad libre. Normalmente *mdadm* preferirá crear una matriz particionable, sin embargo, si la línea **CREATE** en **mdadm.conf** sugiere que se prefiere una matriz no particionable, se respetará.

Si la matriz no se encuentra en el archivo de configuración y sus metadatos no la identifican como perteneciente a "homehost", entonces *mdadm* elegirá un nombre para la matriz que se sabe que no entrará en conflicto con ninguna matriz que pertenezca a este host. Lo hace agregando un guion bajo y un número pequeño al nombre preferido por los metadatos.

Una vez que se encuentra o se crea una matriz apropiada y se agrega el dispositivo, *mdadm* debe decidir si la matriz está lista para iniciarse. Normalmente comparará el número de dispositivos disponibles (no de repuesto) con el número de dispositivos que los metadatos sugieren que necesitan estar activos. Si hay al menos esa cantidad, la matriz se iniciará. Esto significa que si faltan dispositivos, la matriz no se reiniciará.

Como alternativa, se puede pasar **--run** a *mdadm*, en cuyo caso la matriz se ejecutará tan pronto como haya suficientes dispositivos presentes para que los datos sean accesibles. Para un RAID1, eso significa que un dispositivo iniciará la matriz. Para un RAID5 limpio, la matriz se iniciará tan pronto como todos

pero un disco está presente.

Tenga en cuenta que ninguno de estos enfoques es realmente ideal. Si se puede saber que todo el descubrimiento de dispositivos ha completado, entonces
mdadm -IRs
se puede ejecutar, lo que intentará iniciar todas las matrices que se están ensamblando incrementalmente. Se inician en modo "read-auto" en el que son de solo lectura hasta la primera solicitud de escritura. Esto significa que no se realizan actualizaciones de metadatos y no se intenta resincronizar ni recuperar. Los dispositivos adicionales que se encuentran antes de la primera escritura aún se pueden agregar de forma segura.

ENTORNO

Esta sección describe las variables de entorno que afectan cómo funciona mdadm.

MDADM_NO_MDMON
Establecer este valor a 1 evitará que mdadm inicie mdmon automáticamente. Esta variable está destinada principalmente a la depuración de mdadm/mdmon.
MDADM_NO_UDEV
Normalmente, mdadm no crea ningún nodo de dispositivo en /dev, sino que deja esa tarea a udev. Si udev parece no estar configurado, o si esta variable de entorno se establece en '1', mdadm creará los dispositivos necesarios.
MDADM_NO_SYSTEMCTL
Si mdadm detecta que se está utilizando systemd, normalmente solicitará a systemd que inicie varias tareas en segundo plano (en particular mdmon) en lugar de bifurcarlas y ejecutarlas en segundo plano. Esto se puede suprimir estableciendo MDADM_NO_SYSTEMCTL=1.
IMSM_NO_PLATFORM
Un valor clave de los metadatos IMSM es que permite la interoperabilidad con ROMs de arranque en plataformas Intel y con otros sistemas operativos importantes.

En consecuencia, mdadm solo permitirá la creación o modificación de una matriz IMSM si detecta que se está ejecutando en una plataforma Intel que admite IMSM y admite la configuración particular de IMSM que se solicita (algunas funcionalidades requieren soporte OROM más reciente).

Estas comprobaciones se pueden suprimir estableciendo IMSM_NO_PLATFORM=1 en el entorno. Esto puede ser útil para pruebas o recuperación ante desastres. Debe tener en cuenta que la interoperabilidad puede verse comprometida al establecer este valor.

Estos cambios también se pueden suprimir agregando mdadm.imsm.test=1 a la línea de comandos del kernel. Esto facilita la prueba del código IMSM en una máquina virtual que no tiene hardware virtual IMSM.

MDADM_GROW_ALLOW_OLD
Si una matriz se detiene mientras realiza un redimensionamiento y ese redimensionamiento utilizaba un archivo de respaldo, entonces cuando la matriz se vuelve a ensamblar, mdadm a veces se quejará de que el archivo de respaldo es demasiado antiguo. Si esto sucede y está seguro de que es el archivo de respaldo correcto, puede anular esta verificación estableciendo MDADM_GROW_ALLOW_OLD=1 en el entorno.
MDADM_CONF_AUTO
Cualquier cadena dada en esta variable se agrega al principio de la línea AUTO en el archivo de configuración, o se trata como la línea AUTO completa si no se proporciona ninguna. Se puede usar para deshabilitar ciertos tipos de metadatos cuando mdadm es llamado desde un script de arranque. Por ejemplo
export MDADM_CONF_AUTO='-ddf -imsm'
asegurará que mdadm no ensamblará automáticamente ninguna matriz DDF o IMSM que se encuentre. Esto puede ser útil en sistemas configurados para administrar dichas matrices con dmraid.

EJEMPLOS

mdadm --query /dev/nombre-del-dispositivo
Esto averiguará si un dispositivo dado es una matriz RAID, o es parte de una, y proporcionará información breve sobre el dispositivo.

mdadm --assemble --scan
Esto ensamblará e iniciará todas las matrices listadas en el archivo de configuración estándar. Este comando normalmente iría en un archivo de inicio del sistema.

mdadm --stop --scan
Esto detendrá todas las matrices que se puedan detener (es decir, que no estén actualmente en uso). Esto normalmente iría en un script de apagado del sistema.

mdadm --follow --scan --delay=120
Si (y solo si) hay una dirección de correo electrónico o un programa dado en el archivo de configuración estándar, monitoreará el estado de todas las matrices listadas en ese archivo, consultándolas cada 2 minutos.

mdadm --create /dev/md0 --level=1 --raid-devices=2 /dev/hd[ac]1
Crea /dev/md0 como una matriz RAID1 que consta de /dev/hda1 y /dev/hdc1.

echo 'DEVICE /dev/hd*[0-9] /dev/sd*[0-9]' > mdadm.conf
mdadm --detail --scan >> mdadm.conf
Esto creará un archivo de configuración de prototipo que describe las matrices activas actualmente que se sabe que están hechas de particiones de unidades IDE o SCSI. Este archivo debe revisarse antes de usarse, ya que puede contener detalles no deseados.

echo 'DEVICE /dev/hd[a-z] /dev/sd*[a-z]' > mdadm.conf
mdadm --examine --scan --config=mdadm.conf >> mdadm.conf
Esto encontrará matrices que podrían ensamblarse a partir de unidades IDE y SCSI completas existentes (no particiones), y almacenará la información en el formato de un archivo de configuración. Es muy probable que este archivo contenga detalles no deseados, particularmente las entradas devices=. Debe revisarse y editarse antes de usarse como archivo de configuración real.

mdadm --examine --brief --scan --config=partitions
mdadm -Ebsc partitions
Crea una lista de dispositivos leyendo /proc/partitions, escanea estos en busca de superbloques RAID e imprime una lista breve de todos los que se encontraron.

mdadm -Ac partitions -m 0 /dev/md0
Escanea todas las particiones y dispositivos listados en /proc/partitions y ensambla /dev/md0 a partir de todos esos dispositivos con un superbloque RAID con un número menor de 0.

mdadm --monitor --scan --daemonise > /run/mdadm/mon.pid
Si el archivo de configuración contiene una dirección de correo electrónico o un programa de alerta, ejecuta mdadm en segundo plano en modo de monitoreo, monitoreando todos los dispositivos md. También escribe el pid del demonio mdadm en /run/mdadm/mon.pid.

mdadm -Iq /dev/algundispositivo
Intenta incorporar el dispositivo recién descubierto en alguna matriz según corresponda.

mdadm --incremental --rebuild-map --run --scan
Reconstruye el mapa de la matriz a partir de las matrices actuales y luego inicia las que se puedan iniciar.

mdadm /dev/md4 --fail detached --remove detached
Cualquier dispositivo que sea componente de /dev/md4 se marcará como defectuoso y luego se eliminará de la matriz.

mdadm --grow /dev/md4 --level=6 --backup-file=/root/backup-md4
La matriz /dev/md4, que actualmente es una matriz RAID5, se convertirá a RAID6. Normalmente, ya debería haber una unidad de repuesto conectada a la matriz, ya que RAID6 necesita una unidad más que un RAID5 correspondiente.

mdadm --create /dev/md/ddf --metadata=ddf --raid-disks 6 /dev/sd[a-f]
Crea una matriz DDF sobre 6 dispositivos.

mdadm --create /dev/md/home -n3 -l5 -z 30000000 /dev/md/ddf
Crea una matriz RAID5 sobre 3 dispositivos cualesquiera del conjunto DDF dado. Usa solo 30 gigabytes de cada dispositivo.

mdadm -A /dev/md/ddf1 /dev/sd[a-f]
Ensambla una matriz ddf preexistente.

mdadm -I /dev/md/ddf1
Ensambla todas las matrices contenidas en la matriz ddf, asignando nombres según corresponda.

NOMBRE PORTABLE POSIX

Un nombre válido solo puede consistir en los caracteres "A-Za-z0-9.-_". El nombre no puede empezar con un "-" inicial y no puede exceder los 255 caracteres.

NOMBRES DE DISPOSITIVO

mdadm entiende dos tipos de nombres para los dispositivos de matriz.

El primero es el llamado formato 'estándar', que coincide con los nombres utilizados por el kernel y que aparecen en /proc/mdstat.

El segundo tipo se puede elegir libremente, pero debe residir en /dev/md/. Al proporcionar un nombre de dispositivo a mdadm para crear o ensamblar una matriz, se puede dar el nombre de ruta completo, como /dev/md0 o /dev/md/home, o solo el sufijo del segundo tipo de nombre, como home.

En cada estilo, el nombre sin procesar debe ser compatible con NOMBRE PORTABLE POSIX y no debe tener más de 32 caracteres.

Cuando mdadm elige nombres de dispositivo durante el ensamblaje automático o el ensamblaje incremental, a veces agrega un pequeño número de secuencia al final del nombre para evitar conflictos entre múltiples matrices que tienen el mismo nombre. Si mdadm puede determinar razonablemente que la matriz es realmente para este host, ya sea por un nombre de host en los metadatos o por la presencia de la matriz en mdadm.conf, entonces omitirá el sufijo si es posible. También si el homehost se especifica como <ignore> mdadm solo usará un sufijo si un ar diferente

NOMBRES DE DISPOSITIVO

El nombre del dispositivo para un array de software se especifica mediante la opción -n o la opción -N. Si no se proporciona un nombre de dispositivo con la opción -N, se asignará uno genérico, y el nombre real del dispositivo se registrará en el archivo mdadm.conf.

Se admiten nombres de dispositivo de la forma:

/dev/mdNN

donde NN es un número. Esto es compatible con todas las versiones de mdadm.

Los nombres pueden ser no numéricos, con la forma:

/dev/md_XXX

donde XXX es cualquier cadena. Estos nombres son compatibles con mdadm desde la versión 3.3, siempre que estén habilitados en mdadm.conf.

Si se intenta usar un nombre que ya existe o está listado en el archivo de configuración, se generará un error.

ENTENDIENDO LA SALIDA

EXAMINE
punto_de_control
El valor del punto de control se informa cuando el array está realizando alguna acción, incluyendo resincronización, recuperación o remodelación. Los puntos de control permiten reanudar la acción desde un cierto punto si se interrumpió.

El punto de control se informa como una combinación de dos valores: la unidad de migración actual y el número de bloques por unidad. Multiplicando estos valores y dividiendo por el tamaño del array, se puede obtener el porcentaje de progreso del punto de control en relación con el progreso actual informado en /proc/mdstat. El punto de control también está relacionado (y a veces se basa en) la entrada sysfs sync_completed, pero dependiendo de la acción, las unidades pueden diferir. Incluso si las unidades son las mismas, no se debe esperar que el punto de control y sync_completed coincidan exactamente ni que se actualicen simultáneamente.
