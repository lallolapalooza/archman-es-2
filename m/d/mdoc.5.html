mdoc(5) Manual de Formatos de Archivo mdoc(5)

NOMBRE

mdoc - Formato XML de Documentación Mono

DESCRIPCIÓN

Los diversos programas de documentación de Mono generan o manipulan archivos XML siguiendo el esquema de documentación mono:

mdoc update
Crea o actualiza la documentación XML de mono para un conjunto de ensamblados.
mdoc validate
Valida la documentación XML de mono contra el esquema XML de documentación mono.
mdoc assemble
Convierte la documentación XML de mono dentro de una estructura de directorios en un conjunto de archivos para usar con monodoc(1).
mdoc export-html
Convierte la documentación XML de mono dentro de una estructura de directorios en un conjunto de archivos HTML que se pueden ver con un navegador web.

Todas estas herramientas (y más) utilizan el esquema XML común descrito en esta página del manual.

ESTRUCTURA DE ARCHIVOS Y DIRECTORIOS

Hay tres conjuntos de archivos XML de documentación de Mono:

*
index.xml: contiene una lista de todos los ensamblados dentro del directorio contenedor, y todos los tipos y espacios de nombres dentro de esos ensamblados.
*
ns-*.xml: Hay un archivo ns-*.xml por cada espacio de nombres dentro del ensamblado; estos archivos son hermanos de index.xml.

Ejemplos de archivos ns-*.xml incluyen: ns-System.xml, ns-System.Collections.xml, y ns-.xml (para el espacio de nombres raíz, aunque se recomienda NO colocar tipos en el espacio de nombres raíz, ya que monodoc(1) no los muestra).

Los archivos ns-*.xml contienen documentación por espacio de nombres.

*
NombreEspacio/Tipo.xml: Estos archivos están dentro de un directorio con el nombre NombreEspacio con puntos, y Tipo es el nombre del tipo.

Ejemplos incluyen: TipoRaíz.xml (si el tipo no tiene espacio de nombres), System/String.xml, System.Collections/IEnumerable.xml, y System.Collections.Generic/List`1+Enumerator.xml (el `1 es el número de parámetros de tipo genérico que acepta el tipo, y todo lo que sigue al + es un tipo anidado).

Por lo tanto, el contenido típico del directorio se parecería a:

    index.xml
    ns-System.xml
    ns-System.Collections.Generic.xml
    System/String.xml
    System.Collections.Generic/List`1.xml

FORMATO DE DOCUMENTACIÓN

Formato del archivo index.xml

El archivo index.xml contiene una lista de los ensamblados anidados bajo el directorio que contiene index.xml y todos los espacios de nombres y tipos dentro de esos ensamblados. Se ve algo como esto:

    <Overview>
      <Assemblies>
        <Assembly Name="mscorlib" Version="2.0.0.0" />
        <!-- otros elementos <Assembly/>... -->
      </Assemblies>
      <Remarks>Por agregar.</Remarks>
      <Copyright>Por agregar.</Copyright>
      <Types>
        <Namespace Name="System">
          <Type Name="String" />
          <!-- Otros elementos <Type/> -->
        </Namespace>
        <Namespace Name="System.Collections.Generic">
          <Type Name="List`1" DisplayName="List&lt;T&gt;" />
          <!-- Otros elementos <Type/> -->
        </Namespace>
        <!-- otros elementos <Namespace/> -->
      </Types>
      <Title>DocTest</Title>
    </Overview>

La mayor parte de esto se mantiene automáticamente, en particular los elementos /Overview/Assemblies y /Overview/Types.

El atributo //Namespace/@Name corresponde a un directorio que contiene archivos llamados //Type/@Name.xml, mientras que el atributo //Type/@DisplayName contiene un nombre de tipo C# (si no se encuentra //Type/@DisplayName, entonces se usa //Type/@Name como nombre de visualización). También debería haber un archivo ns-[//Namespace/@Name].xml.

Hay tres elementos de interés para los autores: /Overview/Remarks, /Overview/Copyright y /Overview/Title, que contienen documentación a nivel de ensamblado. Estos elementos pueden contener cualquiera de los siguientes elementos XML (documentados en la sección Elementos XML de Documentación): block, code, example, list, para, paramref, typeparamref, see y ul.

Formato del archivo ns-*.xml

Los archivos ns-*.xml contienen documentación de espacios de nombres:

    <Namespace Name="System">
      <Docs>
        <summary>Por agregar.</summary>
        <remarks>Por agregar.</remarks>
      </Docs>
    </Namespace>

Los elementos /Namespace/Docs/summary y /Namespace/Docs/remarks deben contener documentación de espacio de nombres.

Los elementos remarks y summary se documentan en la sección Elementos XML de Documentación.

Formato del archivo NombreEspacio/Tipo.xml

El formato de documentación mono es similar al formato de documentación Ecma, tal como se describe en ECMA-335 3ª Edición, Partición IV, Capítulo 7. La principal diferencia con el formato ECMA es que cada tipo obtiene su propio archivo, dentro de un directorio idéntico al espacio de nombres del tipo. Hay mucha información que es mantenida automáticamente por mdoc(1); la mayor parte de la información dentro de la documentación no debe ser editada. Esto incluye el nombre del tipo (/Type/@FullName), las interfaces implementadas (/Type/Interfaces), la información de miembros (/Type/Members/Member/@MemberName, /Type/Members/Member/MemberSignature, /Type/Members/Member/MemberType, /Type/Members/Member/Parameters, etc.).

    <Type Name="DocAttribute" FullName="Mono.DocTest.DocAttribute">
      <TypeSignature Language="C#" Value="public class DocAttribute : Attribute" />
      <AssemblyInfo>
        <AssemblyName>DocTest</AssemblyName>
        <AssemblyVersion>0.0.0.0</AssemblyVersion>
      </AssemblyInfo>
      <Base>
        <BaseTypeName>System.Attribute</BaseTypeName>
      </Base>
      <Interfaces />
      <Attributes>
        <Attribute>
          <AttributeName>System.AttributeUsage(System.AttributeTargets.All)</AttributeName>
        </Attribute>
      </Attributes>
      <Docs>
        <summary>Por agregar.</summary>
        <remarks>Por agregar.</remarks>
      </Docs>
      <Members>
        <Member MemberName=".ctor">
          <MemberSignature Language="C#" Value="public DocAttribute (string docs);" />
          <MemberType>Constructor</MemberType>
          <AssemblyInfo>
            <AssemblyVersion>0.0.0.0</AssemblyVersion>
          </AssemblyInfo>
          <Parameters>
            <Parameter Name="docs" Type="System.String" />
          </Parameters>
          <Docs>
            <param name="docs">Por agregar.</param>
            <summary>Por agregar.</summary>
            <remarks>Por agregar.</remarks>
          </Docs>
        </Member>
      </Members>
    </Type>

Los únicos elementos que normalmente necesitan ser editados son los hijos de los elementos //Docs, que usualmente contienen el texto Por agregar. El elemento /Type/Docs contiene documentación a nivel de tipo, mientras que el elemento /Type/Members/Member/Docs contiene documentación por miembro.

Los elementos //Docs pueden contener los siguientes elementos: altcompliant, altmember, example, exception, param, permission, remarks, returns, since, summary, threadsafe, typeparam y value.

Los tipos anidados no son miembros; son tipos y se documentan en su propio archivo. Consecuentemente, los archivos NombreEspacio/Tipo.xml no son recursivos; no almacenas un elemento <Type/> dentro de un elemento <Type/>.

Elementos XML de Documentación

El contenido de

el elemento Docs es idéntico en semántica y estructura al formato de documentación C# en línea, y consta de estos elementos (listados en ECMA-334 3ª Edición, Anexo E, Sección 2). Se utilizan los siguientes elementos dentro de las descripciones de elementos:

CREF
Se refiere a una referencia de clase (o miembro), y es una cadena en el formato descrito a continuación en la sección FORMATO CREF.
TEXT
Texto no XML, y no se debe anidar XML.
XML
Solo se deben anidar elementos XML (que indirectamente pueden contener texto), pero el texto no espaciado no debe ser un nodo hijo inmediato.
XML_TEXT
Texto y XML de formato libre, de modo que se puedan anidar otros elementos XML.

Se utilizan los siguientes elementos en la documentación:

<altmember cref="CREF" />
<altmember/> es un elemento de nivel superior y debe anidarse directamente debajo del elemento <Docs/>.

Permite generar una entrada para la sección Ver también. Utilice <see/> para especificar un enlace desde dentro del texto.

    <altmember cref="P:System.Exception.Message" />
<block subset="SUBSET" type="TYPE">XML_TEXT</block>
Crea un bloque de texto, similar en concepto a un párrafo, pero se utiliza para crear divisiones dentro del texto. Hasta cierto punto, un <block/> es equivalente a la etiqueta HTML <h2/>.

SUBSET debe ser siempre el valor "none".

TYPE especifica el encabezado y el formato a utilizar. Los tipos reconocidos son:

behaviors Crea una sección con el encabezado Operación.

note Crea una sección con el encabezado Nota:.

overrides Crea una sección con el encabezado Nota para heredadores.

usage Crea una sección con el encabezado Uso.

El elemento block puede contener los siguientes elementos: block, c, code, list, para, paramref, see, subscript, sup y typeparamref.

<c>XML_TEXT</c>
Establece el texto en una fuente similar a código (similar al elemento HTML <tt/>).

El elemento c puede contener los siguientes elementos: code, para, paramref, see y typeparamref.

<code lang="LANGUAGE" src="SOURCE">TEXT</code>
Muestra varias líneas de texto en una fuente similar a código (similar al elemento HTML <pre/>).

LANGUAGE es el idioma para este bloque de código. Por ejemplo, si LANGUAGE es C#, entonces TEXT obtendrá resaltado de sintaxis para el lenguaje C# dentro del Navegador de Documentación de Mono.

SOURCE solo es interpretado por mdoc-update(1). Si el atributo src está presente cuando se ejecuta mdoc-update(1), entonces SOURCE es un archivo (relativo al directorio --out de mdoc-update(1)) que debe insertarse como valor para TEXT. El contenido de TEXT será ignorado por mdoc-update(1) y reemplazado en cada invocación. SOURCE también puede contener un "ancla", por ejemplo, src="path/to/file.cs#RegionMarker". Si hay un ancla presente, *y* LANGUAGE es C#, entonces se buscará #region RegionMarker, y el contenido entre el #region y el siguiente #endregion se insertará como valor para el elemento TEXT.

<example>XML_TEXT</example>
Indica un ejemplo que debe mostrarse de forma especial. Por ejemplo: 
    <example>
      <para>Un párrafo introductorio.</para>
      <code lang="C#">
        class Example {
          public static void Main ()
          {
            System.Console.WriteLine ("Hola, Mundo!");
          }
        }
      </code>
    </example>

El elemento example puede contener los siguientes elementos: c, code, list, para y see.

<exception cref="CREF">XML_TEXT</exception>
Identifica una excepción que puede ser lanzada por el miembro documentado.

<exception/> es un elemento de nivel superior y debe anidarse directamente debajo del elemento <Docs/>.

CREF es el tipo de excepción que se lanza, mientras que XML_TEXT contiene las circunstancias que harían que se lanzara CREF.

    <exception cref="T:System.ArgumentNullException">
      <paramref name="foo" /> era <see langword="null" />.
    </exception>

El elemento exception puede contener los siguientes elementos: block, para, paramref, see y typeparamref.

<format type="TYPE">XML_TEXT</format>
El elemento <format/> es una "puerta de escape", para incluir (posiblemente XML) contenido que no es contenido válido de mdoc(5). Es el equivalente moral de los bloques =begin format de perlpod(1).

TYPE es el tipo mime de XML_TEXT. Los procesadores de mdoc(5) pueden omitir los bloques format/> si utilizan un tipo que no es compatible.

Por ejemplo:

    <format type="text/html">
      <table width="100%">
        <tr><td style="color:red">Hola, mundo!</td></tr>
      </table>
    </format>

causaría que el elemento <table/> HTML incrustado se inserte en línea en el documento HTML resultante cuando mdoc-export-html(1) procese el archivo. (Asimismo, puede ser omitido si es procesado por otro programa).

format/> está destinado a simplificar la importación de documentación de fuentes de documentación existentes. No se debe confiar en él, si es posible.

<list>XML</list>
Crea una lista o tabla de elementos. <list/> utiliza los elementos anidados <item>XML</item>, <listheader>XML</listheader>, <term>XML_TEXT</term> y <description>XML_TEXT</description>.

Las listas tienen la sintaxis:

    <list type="bullet"> <!-- o type="number" -->
      <item><term>Elemento 1</term></item>
      <item><term>Elemento 2</term></item>
      <item><term>Elemento 3</term></item>
    </list>

Las tablas tienen la sintaxis:

    <list type="table">
      <listheader> <!-- listheader pone en negrita esta fila -->
        <term>Columna 1</term>
        <description>Columna 2</description>
        <description>Columna 3</description>
      </listheader>
      <item>
        <term>Elemento 1-A</term>
        <description>Elemento 1-B</description>
        <description>Elemento 1-C</description>
      </item>
      <item>
        <term>Elemento 2-A</term>
        <description>Elemento 2-B</description>
        <description>Elemento 2-C</description>
      </item>
    </list>

Los elementos item y description pueden contener cada uno texto y los siguientes elementos: block, c, para, paramref, see, sup y typeparamref.

<para>XML_TEXT</para>
Inserta un párrafo de XML_TEXT. Por ejemplo, 
    <para>
      Este es un párrafo de texto.
    </para>

El elemento para puede contener los siguientes elementos: block, c, example, link, list, onequarter, paramref, see, sub, sup, typeparamref y ul.

<param name="NAME">XML_TEXT</param>
<param/> es un elemento de nivel superior y debe anidarse directamente debajo del elemento <Docs/>.

Describe el parámetro NAME del constructor, método o propiedad actual:

    <param name="count">
      Un <see cref="T:System.Int32" /> que contiene el número
      de widgets a procesar.
    </param>

El elemento param puede contener los siguientes elementos: block, c, example, para, paramref, see y typeparamref.

<paramref name="NAME" />
Indica que NAME es un parámetro.

Normalmente, esto muestra NAME en texto itálico, por lo que se utiliza frecuentemente (y abusivamente) como equivalente a la etiqueta HTML <i/>. Ver la documentación de <exception/> (arriba) para un ejemplo.

<permission cref="CREF">XML_TEXT</permission>
Documenta los requisitos de accesibilidad de seguridad del miembro actual.

<permission/> es un elemento de nivel superior y debe anidarse directamente debajo del elemento <Docs/>.

CREF es una referencia de tipo al permiso de seguridad requerido, mientras que XML_TEXT es una descripción de por qué se requiere el permiso.

    <permission cref="T:System.Security.Permissions.FileIOPermission">
      Requiere permiso para leer y escribir archivos. Ver
      <see cref="F:System.Security.Permissions.FileIOPermissionAccess.Read" />,
      <see cref="F:System.Security.Permissions.FileIOPermissionAccess.Write" />.
    </permission>

El elemento permission puede contener los siguientes elementos: block, para, paramref, see y typeparamref.

<remarks>XML_TEXT</remarks>
Contiene información detallada sobre un miembro.

<remarks/> es un elemento de nivel superior y debe anidarse directamente debajo del elemento <Docs/>.

    <remarks>
      Insertar información detallada aquí.
    </remarks>

FORMATO DE DOCUMENTACIÓN

Los elementos XML utilizados para documentar los tipos y miembros de .NET se especifican en el estándar ECMA-335, Sección 15.3. Este comando mdoc genera y lee el formato de documento .NET.

Los siguientes elementos se utilizan para documentar el código:

<altmember cref="CREF" member="MEMBER" name="NAME" />
Este elemento se utiliza para agregar una referencia a otro miembro existente. Puede especificar un enlace mediante la referencia CREF, el nombre del miembro o una cadena de nombre. Esto es útil para agrupar miembros relacionados lógicamente, como métodos sobrecargados.
<code lang="LANG" />
Este elemento se utiliza para insertar bloques de código en la documentación. El atributo opcional lang puede especificar el lenguaje del código para su resaltado.
<Docs>XML_TEXT</Docs>
Este es el elemento raíz para la documentación de un tipo o miembro. Cualquier otro elemento de documentación debe anidarse directamente dentro de este.
<example>XML_TEXT</example>

<example/> es un elemento de nivel superior y debe anidarse directamente bajo el elemento <Docs/>.

Proporciona un ejemplo de uso de un tipo o miembro. El ejemplo puede contener código, texto y otros elementos de marcado.

El elemento example puede contener los siguientes elementos: block, c, code, list, para, paramref, see y typeparamref.

<exception cref="CREF" />

<exception/> es un elemento de nivel superior y debe anidarse directamente bajo el elemento <Docs/>.

Describe una excepción que puede ser generada por un tipo o miembro. El atributo cref debe hacer referencia al tipo de excepción.

    <exception cref="T:System.ArgumentNullException">
      Thrown when 
      <paramref name="input" /> is null.
    </exception>

El elemento exception puede contener los siguientes elementos: block, c, code, example, list, para, paramref, see y typeparamref.

<list type="BULLETED|NUMBERED">XML_TEXT</list>

<list/> es un elemento de nivel superior y debe anidarse directamente bajo el elemento <Docs/>.

Crea una lista con viñetas o numerada. Cada elemento de la lista se especifica dentro de un elemento <item>.

    <list type="bullet">
      <listheader>
        <term>Term</term>
        <description>
          <para>Description</para>
        </description>
      </listheader>
      <item>
        <term>Item 1</term>
        <description>
          <para>Description 1</para>
        </description>
      </item>
    </list>

El elemento list puede contener los siguientes elementos: item y listheader.

<listheader>XML_TEXT</listheader>
Contiene un encabezado para una lista. Solo puede contener los elementos term y description.
<para>XML_TEXT</para>
Define un párrafo dentro de un bloque de documentación. Los elementos de texto se pueden anidar dentro de este elemento.
<param name="NAME" />

<param/> es un elemento de nivel superior y debe anidarse directamente bajo el elemento <Docs/>.

Describe un parámetro de un método. El atributo name especifica el nombre del parámetro.

    <param name="input">
      The input string to be processed.
    </param>

El elemento param puede contener los siguientes elementos: block, c, code, example, list, para, paramref, see y typeparamref.

<paramref name="NAME" />
Utilizado para indicar que NAME es un parámetro de método.
<permission cref="CREF" />

<permission/> es un elemento de nivel superior y debe anidarse directamente bajo el elemento <Docs/>.

Describe el uso de un ensamblado de seguridad para un tipo o miembro. El atributo cref debe hacer referencia al tipo de permiso.

    <permission cref="F:System.Security.Permissions.FileIOPermissionAttribute.AllLocalFiles">
      To read from and write to the file system.
    </permission>

El elemento permission puede contener los siguientes elementos: block, c, code, example, list, para, paramref, see y typeparamref.

<remarks>XML_TEXT</remarks>

<remarks/> es un elemento de nivel superior y debe anidarse directamente bajo el elemento <Docs/>.

Contiene información adicional sobre un tipo o miembro, que no se ajusta a la descripción de un resumen. Puede incluir detalles técnicos, notas de uso o información de diseño.

El elemento remarks puede contener los siguientes elementos: block, c, code, example, list, para, paramref, see y typeparamref.

<returns>XML_TEXT</returns>

<returns/> es un elemento de nivel superior y debe anidarse directamente bajo el elemento <Docs/>.

Describe el valor de retorno de un método:

    <returns>
      A <see cref="T:System.Boolean" /> specifying whether
      or not the process can access
      <see cref="P:Mono.Unix.UnixFileSystemInfo.FullName" />.
    </returns>

El elemento returns puede contener los siguientes elementos: c, format, list, para, paramref, see y typeparamref.

<see cref="CREF" />, <see langword="LANGWORD" />
Crea un enlace al miembro especificado dentro del texto actual: 
    <see cref="M:Some.Namespace.With.Type.Method" />

o especifica que LANGWORD es una palabra clave del lenguaje:

    <see langword="null" />
<seealso cref="CREF" />
No use seealso, use altmember.
<since version="VERSION" />

<since/> es un elemento de nivel superior y debe anidarse directamente bajo el elemento <Docs/>.

Permite la especificación de qué versión introdujo el tipo o miembro especificado.

    <since version="Gtk# 2.4" />

Esto generalmente no es necesario, ya que los elementos //AssemblyInfo/AssemblyVersion rastrean qué versiones de ensamblado contienen el tipo o miembro.

<summary>XML_TEXT</summary>

<summary/> es un elemento de nivel superior y debe anidarse directamente bajo el elemento <Docs/>.

Proporciona una visión general (¡breve!) de un tipo o miembro de tipo.

Esto generalmente se muestra como parte de una declaración de clase y debe ser una descripción razonablemente corta del tipo/miembro. Use <remarks/> para obtener información más detallada.

El elemento summary puede contener los siguientes elementos: block, list, para, paramref, see y typeparamref.

<typeparam name="NAME">XML_TEXT</typeparam>
<typeparam/> es un elemento de nivel superior y debe anidarse directamente bajo el elemento <Docs/>.

Esto se utiliza para documentar un parámetro de tipo para un tipo genérico o un método genérico.

NAME es el nombre del parámetro de tipo, mientras que XML_TEXT contiene una descripción del parámetro (para qué se usa, qué restricciones debe cumplir, etc.).

    <typeparam name="T">
      The type of the underlying collection
    </typeparam>

El elemento typeparam puede contener los siguientes elementos: block, c, para, paramref, see y typeparamref.

<typeparamref name="NAME">
Se utiliza para indicar que NAME es un parámetro de tipo.
<value>XML_TEXT</value>
<value/> es un elemento de nivel superior y debe anidarse directamente bajo el elemento <Docs/>.

Permite describir una propiedad.

    <value>
      A <see cref="T:System.String" /> containing a widget name.
    </value>

El elemento value puede contener los siguientes elementos: block, c, example, list, para, paramref, see y typeparamref.

FORMATO DE CREF

Los identificadores de cadena (CREFs) se utilizan para hacer referencia a un tipo o miembro de un tipo. Los identificadores de cadena se documentan en la especificación ECMA-334, 3ª Edición, Anexo E.3.1. Consisten en un prefijo de tipo de miembro, el nombre completo del tipo (espacio de nombres + nombre, separados por .), posiblemente seguido por el nombre del miembro y otra información.

Prefijos de tipo de miembro:

C:
El CREF se refiere a un constructor. La lista de parámetros (opcional) se incluye entre paréntesis y sigue al nombre del tipo: C:System.String(System.Char,System.Int32).
E:
El CREF se refiere a un evento. El nombre del evento sigue al nombre del tipo: E:System.AppDomain.AssemblyLoad.
F:
El CREF se refiere a un campo. El nombre del campo sigue al nombre del tipo: F:System.Runtime.InteropServices.DllImportAttribute.SetLastError.
M:
Se refiere a un constructor o método. Los constructores pueden añadir .ctor al nombre del tipo (en lugar de usar el formato de constructor C: anterior), mientras que los métodos añaden el nombre del método y un recuento (opcional) del número de parámetros genéricos. Tanto los constructores como los métodos pueden añadir la lista de parámetros del método entre paréntesis.

Ejemplos: M:System.Object..ctor, M:System.String..ctor(System.Char[]), M:System.String.Concat(System.Object), M:System.Array.Sort``1(``0[]), M:System.Collections.Generic.List`1..ctor, M:System.Collections.Generic.List`1.Add(`0).

N:
Se refiere a un espacio de nombres, por ejemplo, N:System.
P:
Se refiere a una propiedad. Si la propiedad es un indexador o toma parámetros, los tipos de los parámetros se añaden al nombre de la propiedad y se incluyen entre paréntesis: P:System.String.Length, P:System.String.Chars(System.Int32).
T:
El CREF se refiere a un tipo, con el número de tipos genéricos añadidos: T:System.String, T:System.Collections.Generic.List`1, T:System.Collections.Generic.List`1.Enumerator.

Para hacerlo más interesante, los tipos y miembros genéricos tienen dos representaciones: la representación "no enlazada" (mostrada en los ejemplos anteriores), en la que los nombres de las clases tienen el recuento de parámetros genéricos añadidos a su nombre. También existe una representación "enlazada", en la que el enlace de los parámetros genéricos se enumera dentro de '{' y '}' o '<' y '>'. (El uso de '<' y '>' es menos común, ya que dentro de un documento XML deben usarse sus entidades de caracteres escapadas, lo que lleva a '&lt;' y '&gt;'.)

No enlazado:

*
T:System.Collections.Generic.List`1
*
T:System.Collections.Generic.Dictionary`2

Enlazado:

*
T:System.Collections.Generic.List{System.Int32}
*
T:System.Collections.Generic.List<System.Int32>
*
T:System.Collections.Generic.List&lt;System.Int32&gt;
*
T:System.Predicate{System.Action{System.String}}

Como se puede ver, las variantes enlazadas pueden ser arbitrariamente complejas (al igual que los genéricos).

Además, si un parámetro genérico está enlazado al parámetro genérico de un tipo o método, se utiliza el "índice" del parámetro genérico del tipo/método como enlace, de modo que, dado

    class FooType {
      public static void Foo<T> (System.Predicate<T> predicate)
      {
      }
    }

El CREF para este método es M:FooType.Foo``1(System.Predicate{``0}), ``0 es el índice del parámetro genérico número 0 que está enlazado a System.Predicate<T>.
