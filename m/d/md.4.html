MD(4) Manual de Controladores de Dispositivos MD(4)

NOMBRE

md - Controlador de Dispositivos Múltiples, también conocido como RAID de Software de Linux

SINOPSIS

/dev/mdn
/dev/md/n
/dev/md/nombre

DESCRIPCIÓN

El controlador md proporciona dispositivos virtuales que se crean a partir de uno o más dispositivos subyacentes independientes. Esta matriz de dispositivos a menudo contiene redundancia y los dispositivos suelen ser unidades de disco, de ahí el acrónimo RAID, que significa Redundant Array of Independent Disks (Matriz Redundante de Discos Independientes).

md admite los niveles RAID 1 (duplicación), 4 (matriz distribuida con dispositivo de paridad), 5 (matriz distribuida con información de paridad distribuida), 6 (matriz distribuida con información de doble redundancia distribuida) y 10 (distribuida y duplicada). Si falla un cierto número de dispositivos subyacentes mientras se utiliza uno de estos niveles, la matriz seguirá funcionando; este número es uno para los niveles RAID 4 y 5, dos para el nivel RAID 6, y todos menos uno (N-1) para el nivel RAID 1, y depende de la configuración para el nivel 10.

md también admite una serie de configuraciones de pseudo RAID (no redundantes) que incluyen RAID0 (matriz distribuida), LINEAR (matriz concatenada), MULTIPATH (un conjunto de interfaces diferentes para el mismo dispositivo) y FAULTY (una capa sobre un solo dispositivo en la que se pueden inyectar errores).

METADATOS MD

Cada dispositivo de una matriz puede tener algunos metadatos almacenados en el dispositivo. Estos metadatos a veces se llaman superbloque. Los metadatos registran información sobre la estructura y el estado de la matriz. Esto permite que la matriz se reensamble de manera confiable después de un apagado.

md proporciona soporte para dos formatos diferentes de metadatos, y se pueden agregar otros formatos.

El formato común — conocido como versión 0.90 — tiene un superbloque de 4K de longitud y se escribe en un bloque alineado de 64K que comienza a no menos de 64K ni a más de 128K desde el final del dispositivo (es decir, para obtener la dirección del superbloque, redondea el tamaño del dispositivo hacia abajo a un múltiplo de 64K y luego resta 64K). El tamaño disponible de cada dispositivo es la cantidad de espacio antes del superbloque, por lo que se pierden entre 64K y 128K cuando un dispositivo se incorpora a una matriz MD. Este superbloque almacena campos multibyte de manera dependiente del procesador, por lo que las matrices no se pueden mover fácilmente entre computadoras con diferentes procesadores.

El nuevo formato — conocido como versión 1 — tiene un superbloque que normalmente es de 1K de longitud, pero puede ser más largo. Normalmente se almacena entre 8K y 12K desde el final del dispositivo, en un límite de 4K, aunque se pueden almacenar variaciones al principio del dispositivo (versión 1.1) o 4K desde el principio del dispositivo (versión 1.2). Este formato de metadatos almacena datos multibyte en un formato independiente del procesador y admite hasta cientos de dispositivos componentes (la versión 0.90 solo admite 28).

Los metadatos contienen, entre otras cosas:

NIVEL
La forma en que los dispositivos se organizan en la matriz (LINEAR, RAID0, RAID1, RAID4, RAID5, RAID10, MULTIPATH).
UUID
un identificador universalmente único de 128 bits que identifica la matriz que contiene este dispositivo.

Cuando una matriz versión 0.90 está siendo remodelada (por ejemplo, agregando dispositivos adicionales a un RAID5), el número de versión se establece temporalmente en 0.91. Esto garantiza que si el proceso de remodelación se detiene a mitad de camino (por ejemplo, debido a un fallo del sistema) y la máquina arranca con un kernel más antiguo que no admite la remodelación, la matriz no se ensamblará (lo que causaría corrupción de datos), sino que se dejará intacta hasta que se utilice un kernel que pueda completar el proceso de remodelación.

MATRICES SIN METADATOS

Aunque generalmente es mejor crear matrices con superbloques para que puedan ensamblarse de manera confiable, existen algunas circunstancias en las que se prefiere una matriz sin superbloques. Estas incluyen:

MATRICES LEGADO
Las versiones anteriores del controlador md solo admitían configuraciones LINEAR y RAID0 y no utilizaban un superbloque (lo que es menos crítico con estas configuraciones). Aunque dichas matrices deben reconstruirse con superbloques si es posible, md continúa admitiéndolas.
FAULTY
Al ser una capa en gran medida transparente sobre un dispositivo diferente, la personalidad FAULTY no obtiene ningún beneficio de tener un superbloque.
MULTIPATH
A menudo es posible detectar dispositivos que son diferentes rutas al mismo almacenamiento directamente en lugar de tener un superbloque distintivo escrito en el dispositivo y buscado en todas las rutas. En este caso, una matriz MULTIPATH sin superbloque tiene sentido.
RAID1
En algunas configuraciones, podría desearse crear una configuración RAID1 que no utilice un superbloque y mantener el estado de la matriz en otro lugar. Aunque no se recomienda para uso general, tiene usos especiales y es compatible.

MATRICES CON METADATOS EXTERNOS

El controlador md admite matrices con metadatos gestionados externamente. Es decir, los metadatos no son gestionados por el kernel, sino por un programa de espacio de usuario que es externo al kernel. Esto permite el soporte para una variedad de formatos de metadatos sin saturar el kernel con muchos detalles.

md es capaz de comunicarse con el programa de espacio de usuario a través de varios atributos de sysfs para que pueda realizar los cambios apropiados en los metadatos, por ejemplo, para marcar un dispositivo como defectuoso. Cuando sea necesario, md esperará a que el programa reconozca el evento escribiendo en un atributo de sysfs. La página del manual de mdmon(8) contiene más detalles sobre esta interacción.

CONTENEDORES

Muchos formatos de metadatos utilizan un único bloque de metadatos para describir varias matrices que utilizan el mismo conjunto de dispositivos. En este caso, es útil que el kernel conozca el conjunto completo de dispositivos como un todo. Este conjunto es conocido por md como un contenedor. Un contenedor es una matriz md con metadatos gestionados externamente y con un desplazamiento y tamaño de dispositivo tales que solo cubre la parte de metadatos de los dispositivos. El resto de cada dispositivo está disponible para ser incorporado en varias matrices.

LINEAR

Una matriz LINEAR simplemente concatena el espacio disponible en cada disco para formar una unidad virtual grande.

Una ventaja de esta disposición sobre la disposición RAID0 más común es que la matriz puede reconfigurarse en un momento posterior con un disco adicional, de modo que la matriz se haga más grande sin perturbar los datos que están en la matriz. Esto incluso se puede hacer en una matriz en vivo.

Si se proporciona un tamaño de fragmento con una matriz LINEAR, el espacio utilizable en cada dispositivo se redondea hacia abajo a un múltiplo de este tamaño de fragmento.

RAID0

Una matriz RAID0 (que tiene cero redundancia) también se conoce como matriz distribuida. Una matriz RAID0 se configura en la creación con un Tamaño de Fragmento que debe ser de al menos 4 kibibytes.

El controlador RAID0 asigna el primer fragmento de la matriz al primer dispositivo, el segundo fragmento al segundo dispositivo, y así sucesivamente hasta que todos los discos hayan sido asignados a un fragmento. Esta colección de fragmentos forma una franja. Fragmentos adicionales se agrupan en franjas de la misma manera y se asignan al espacio restante en los discos.

Si los dispositivos de la matriz no son todos del mismo tamaño, entonces una vez que el dispositivo más pequeño se ha agotado, el controlador RAID0 comienza a recolectar fragmentos en franjas más pequeñas que solo abarcan los discos que aún tienen espacio restante.

RAID1

Una matriz RAID1 también se conoce como un conjunto espejo (aunque los espejos tienden a proporcionar imágenes reflejadas, lo que RAID1 no hace) o un plex.

Una vez inicializado, cada dispositivo en una matriz RAID1 contiene exactamente los mismos datos. Los cambios se escriben en todos los dispositivos en paralelo. Los datos se leen de cualquiera de los dispositivos. El controlador intenta distribuir las solicitudes de lectura entre todos los dispositivos para maximizar el rendimiento.

Todos los dispositivos en una matriz RAID1 deben ser del mismo tamaño. Si no lo son, solo se utiliza la cantidad de espacio disponible en el dispositivo más pequeño (cualquier espacio adicional en otros dispositivos se desperdicia).

Tenga en cuenta que el equilibrio de lectura realizado por el controlador no hace que el perfil de rendimiento de RAID1 sea el mismo que el de RAID0; una sola secuencia de entrada secuencial no se acelerará (por ejemplo, un único dd), pero múltiples secuencias secuenciales o una carga de trabajo aleatoria utilizarán más de un disco. En teoría, tener un RAID1 de N discos permitirá que N hilos secuenciales lean de todos los discos.

Los dispositivos individuales en una matriz RAID1 se pueden marcar como "principalmente de escritura". Estas unidades se excluyen del equilibrio de lectura normal y solo se leerán cuando no haya otra opción. Esto puede ser útil para dispositivos conectados a través de un enlace lento.

RAID4

Una matriz RAID4 es como una matriz RAID0 con un dispositivo adicional para almacenar la paridad. Este dispositivo es el último de los dispositivos activos en la matriz. A diferencia de RAID0, RAID4 también requiere que todas las franjas abarquen todas las unidades, por lo que se desperdicia espacio adicional en dispositivos más grandes que el más pequeño.

Cuando se modifica cualquier bloque en una matriz RAID4, el bloque de paridad de esa franja (es decir, el bloque en el dispositivo de paridad con el mismo desplazamiento de dispositivo que la franja) también se modifica para que el bloque de paridad siempre contenga la "paridad" de toda la franja. Es decir, su contenido es equivalente al resultado de realizar una operación de exclusión lógica entre todos los bloques de datos de la franja.

Esto permite que la matriz continúe funcionando si falla un dispositivo. Los datos que estaban en ese dispositivo se pueden calcular según sea necesario a partir del bloque de paridad y los otros bloques de datos.

RAID5

RAID5 es muy similar a RAID4. La diferencia es que los bloques de paridad de cada franja, en lugar de estar en un solo dispositivo, se distribuyen entre todos los dispositivos. Esto permite más paralelismo al escribir, ya que dos actualizaciones de bloque diferentes muy probablemente afectarán a los bloques de paridad en diferentes dispositivos, por lo que hay menos contención.

Esto también permite más paralelismo al leer, ya que las solicitudes de lectura se distribuyen entre todos los dispositivos de la matriz en lugar de todos menos uno.

RAID6

RAID6 es similar a RAID5, pero puede manejar la pérdida de cualesquiera dos dispositivos sin pérdida de datos. En consecuencia, requiere N+2 unidades para almacenar N unidades de datos.

El rendimiento de RAID6 es ligeramente inferior pero comparable a RAID5 en modo normal y en modo de fallo de un solo disco. Sin embargo, es muy lento en modo de fallo de dos discos.

RAID10

RAID10 proporciona una combinación de RAID1 y RAID0, y a veces se conoce como RAID1+0. Cada bloque de datos se duplica un número de veces, y la colección resultante de bloques de datos se distribuye entre múltiples unidades.

Al configurar una matriz RAID10, es necesario especificar el número de réplicas de cada bloque de datos que se requieren (esto suele ser 2) y si su disposición debe ser "cercana", "lejana" u "offset".

Disposición "offset"
La disposición "offset" es un compromiso entre las disposiciones "near" y "far". En esta disposición, las copias de un fragmento dado se distribuyen entre los dispositivos, pero de forma más agrupada que en "far".

Específicamente, las réplicas de un fragmento se colocan en dispositivos adyacentes, pero se desplazan un dispositivo para la siguiente franja. Esto reduce la probabilidad de que las escrituras en el mismo bloque pero en franjas diferentes terminen en el mismo dispositivo físico, lo que puede ocurrir con la disposición "near" en ciertos escenarios.
La disposición "offset" se utiliza a menudo para mejorar el rendimiento de escritura en matrices con un gran número de dispositivos.

"far" Layout
When "far" replicas are chosen, copies of the same chunk are spread out as much as possible across the devices.

In detail, for each chunk, the first copy is placed on device #0, the second copy on device #1, and so on, wrapping around the devices as necessary. This ensures that consecutive chunks are placed on different devices.

Example with 2 copies per chunk and an even number (4) of devices:

Device #1 Device #2 Device #3 Device #4
0x00 0 1 2 3 ) AA
0x01 4 5 6 7 ) AB
: : : : : :
0x79 312 313 314 315 ) EX

Example with 2 copies per chunk and an odd number (5) of devices:

Dev #1 Dev #2 Dev #3 Dev #4 Dev #5
0x00 0 1 2 3 4 ) AA
0x01 5 6 7 8 9 ) AB
: : : : : : :
0x79 314 315 316 317 318 ) EX

With [#] being the complete sequence of chunks and [#]~ the cyclic permutation with offset 1 thereof (in the case of more than 2 copies per chunk there would be ([#]~)~, (([#]~)~)~, ...).

The advantage of this layout is that MD can easily spread sequential reads over the devices, making them similar to RAID0 in terms of speed.
The cost is more seeking for writes, making them substantially slower.

"offset" Layout
When "offset" replicas are chosen, all the copies of a given chunk are striped consecutively ("offset by the stripe length after each other") over the devices.

Explained in detail, <number of devices> consecutive chunks are striped over the devices, immediately followed by a "shifted" copy of these chunks (and by further such "shifted" copies in the case of more than 2 copies per chunk).
This pattern repeats for all further consecutive chunks of the exported RAID10 device (in other words: all further data blocks).

The "shift" needed to prevent placing copies of the same chunks on the same devices is actually a cyclic permutation with offset 1 of each of the striped copies of <number of devices> consecutive chunks.
The offset 1 is relative to the previous striped copy of <number of devices> consecutive chunks, so in case of more than 2 copies per chunk one gets the following offsets:
1. <number of devices> consecutive chunks: offset = 0
2. <number of devices> consecutive chunks: offset = 1
3. <number of devices> consecutive chunks: offset = 2
:
n. <number of devices> consecutive chunks: offset = n-1

Example with 2 copies per chunk and an even number (4) of devices:

This should give similar read characteristics to "far" if a suitably large chunk size is used, but without as much seeking for writes.

LISTA DE BLOQUES DEFECTUOSOS

Cada dispositivo en una matriz md puede almacenar una lista de bloques defectuosos conocidos. Esta lista tiene un tamaño de 4K y generalmente se ubica al final del espacio entre el superbloque y los datos.

Cuando un bloque no se puede leer y no se puede reparar escribiendo datos recuperados de otros dispositivos, la dirección del bloque se almacena en la lista de bloques defectuosos. De manera similar, si un intento de escribir en un bloque falla, la dirección se registrará como un bloque defectuoso. Si el intento de registrar el bloque defectuoso falla, todo el dispositivo se marcará como defectuoso.

Intentar leer desde un bloque defectuoso conocido provocará un error de lectura. Intentar escribir en un bloque defectuoso conocido se ignorará si se han notificado errores de escritura por parte del dispositivo. Si no ha habido errores de escritura, los datos se escribirán en el bloque defectuoso conocido y, si eso tiene éxito, la dirección se eliminará de la lista.

Esto permite que una matriz falle de manera más agradable: unos pocos bloques en diferentes dispositivos pueden ser defectuosos sin sacar toda la matriz de acción.

La lista es particularmente útil al recuperarse en una unidad de reserva. Si unos pocos bloques no se pueden leer de los otros dispositivos, la mayor parte de la recuperación puede completarse y esos pocos bloques defectuosos se registrarán en la lista de bloques defectuosos.

AGUJERO DE ESCRITURA RAID

Debido a la naturaleza no atómica de las operaciones de escritura RAID, la interrupción de las operaciones de escritura (cierre del sistema, etc.) en una matriz RAID456 puede provocar una paridad inconsistente y pérdida de datos (el llamado agujero de escritura RAID-5). Para tapar el agujero de escritura, md admite dos mecanismos descritos a continuación.

DIARIO DE FRACCIONES MODIFICADAS
Desde Linux 4.4, md admite un diario de escritura anticipada para RAID456. Cuando se crea la matriz, se puede añadir un dispositivo de diario adicional a la matriz a través de la opción write-journal. El diario de escritura RAID funciona de manera similar a los diarios del sistema de archivos. Antes de escribir en los discos de datos, md persiste los datos Y la paridad de la fracción en el dispositivo del diario. Después de los bloqueos, md busca en el dispositivo del diario las operaciones de escritura incompletas y las reproduce en los discos de datos.

Cuando falla el dispositivo del diario, la matriz RAID se ve obligada a ejecutarse en modo de solo lectura.

REGISTRO DE PARIDAD PARCIAL
Desde Linux 4.12, md admite el Registro de Paridad Parcial (PPL) solo para matrices RAID5. La paridad parcial para una operación de escritura es el XOR de los fragmentos de datos que no han sido modificados por la escritura. PPL se almacena en la región de metadatos de los discos miembros de RAID, no se necesita un disco de diario adicional. Después de los bloqueos, si falta uno de los discos de datos de la fracción que no se modificaron, esta paridad actualizada se puede utilizar para recuperar sus datos.

Consulte Documentation/driver-api/md/raid5-ppl.rst para obtener detalles de implementación.

ESCRITURA ATRASADA

Esto permite que ciertos dispositivos de la matriz se marquen como *principalmente para escritura*. MD solo leerá de dichos dispositivos si no hay otra opción.

Si también se proporciona un mapa de bits de intenciones de escritura, las solicitudes de escritura a dispositivos principalmente para escritura se tratarán como solicitudes de escritura atrasada y md no esperará a que las escrituras de esas solicitudes se completen antes de informar la escritura como completa al sistema de archivos.

Esto permite que un RAID1 con ESCRITURA ATRASADA se utilice para duplicar datos a través de un enlace lento a un ordenador remoto (siempre que el enlace no sea demasiado lento). La latencia adicional del enlace remoto no ralentizará las operaciones normales, pero el sistema remoto seguirá teniendo una copia razonablemente actualizada de todos los datos.

FAILFAST

Desde Linux 4.10, md admite FAILFAST para matrices RAID1 y RAID10. Esta es una bandera que se puede establecer en discos individuales, aunque generalmente se establece en todos los discos o en ninguno.

Cuando md envía una solicitud de E/S a un disco que está marcado como FAILFAST, y cuando la matriz podría sobrevivir a la pérdida de ese disco sin perder datos, md solicitará que el dispositivo subyacente no realice ningún reintento. Esto significa que una falla se informará a md de inmediato, y este puede marcar el dispositivo como defectuoso y continuar usando el(los) otro(s) dispositivo(s). md no puede controlar el tiempo de espera que los dispositivos subyacentes utilizan para determinar la falla. Cualquier cambio deseado en ese tiempo de espera debe configurarse explícitamente en el dispositivo subyacente, por separado del uso de mdadm.

Si falla una solicitud FAILFAST, y si todavía es seguro marcar el dispositivo como defectuoso sin pérdida de datos, se hará y la matriz continuará funcionando con un número reducido de dispositivos. Si no es posible marcar de forma segura el dispositivo como defectuoso, md reintentará la solicitud sin deshabilitar los reintentos en el dispositivo subyacente. En cualquier caso, md no intentará reparar errores de lectura en un dispositivo marcado como FAILFAST escribiendo la información correcta. Simplemente marcará el dispositivo como defectuoso.

FAILFAST es apropiado para matrices de almacenamiento que tienen una baja probabilidad de falla real, pero que a veces introducirán retrasos inaceptables en las solicitudes de E/S mientras realizan mantenimiento interno. El valor de establecer FAILFAST implica un compromiso. La ganancia es que la posibilidad de retrasos inaceptables se reduce sustancialmente. El coste es que el evento poco probable de pérdida de datos en un dispositivo tiene una probabilidad ligeramente mayor de resultar en pérdida de datos para la matriz.

Cuando un dispositivo en una matriz que utiliza FAILFAST se marca como defectuoso, generalmente volverá a ser utilizable en poco tiempo. mdadm no intenta detectar esa posibilidad. Se debe crear algún mecanismo separado, ajustado a los detalles específicos de los modos de falla esperados, para monitorear los dispositivos y ver cuándo regresan a la funcionalidad completa, y luego volver a añadirlos a la matriz. Para que la funcionalidad de "volver a añadir" sea efectiva, una matriz que utiliza FAILFAST siempre debe tener un mapa de bits de intenciones de escritura.

REORGANIZACIÓN DE FRACCIONES

La *reorganización de fracciones*, también conocida como *remodelación*, es el proceso de reorganizar los datos almacenados en cada fracción en un nuevo diseño. Esto puede implicar cambiar el número de dispositivos en la matriz (para que las fracciones sean más anchas), cambiar el tamaño del bloque (para que las fracciones sean más profundas o más superficiales), o cambiar la disposición de los datos y la paridad (posiblemente cambiando el nivel de RAID, por ejemplo, de 1 a 5 o de 5 a 6).

md puede remodelar una matriz RAID4, RAID5 o RAID6 para tener un número diferente de dispositivos (más o menos) y para tener un diseño o tamaño de bloque diferente. También puede convertir entre estos diferentes niveles de RAID. También puede convertir entre RAID0 y RAID10, y entre RAID0 y RAID4 o RAID5. Otras posibilidades pueden seguir en futuros kernels.

Durante cualquier proceso de fracción, hay una 'sección crítica' durante la cual los datos activos se sobrescriben en el disco. Para la operación de aumentar el número de unidades en un RAID5, esta sección crítica cubre las primeras fracciones (el número siendo el producto del número antiguo y nuevo de unidades). Después de pasar esta sección crítica, los datos solo se escriben en áreas de la matriz que ya no contienen datos activos — los datos activos ya se han movido.

Para una remodelación que reduce el número de dispositivos, la 'sección crítica' está al final del proceso de remodelación.

md no puede garantizar la preservación de datos si hay un bloqueo (por ejemplo, un corte de energía) durante la sección crítica. Si se le pide a md que inicie una matriz que falló durante una sección crítica de reorganización de fracciones, fallará al iniciar la matriz.

Para hacer frente a esta posibilidad, un programa de espacio de usuario debe

  • Deshabilitar las escrituras en esa sección de la matriz (usando la interfaz sysfs),
  • tomar una copia de los datos en algún lugar (es decir, hacer una copia de seguridad),
  • permitir que el proceso continúe e invalide la copia de seguridad y restaure el acceso de escritura una vez que se haya pasado la sección crítica, y
  • proporcionar para restaurar los datos críticos antes de reiniciar la matriz después de un bloqueo del sistema.

mdadm hace esto para crecer una matriz RAID5.

Para operaciones que no cambian el tamaño de la matriz, como simplemente aumentar el tamaño del bloque o convertir RAID5 a RAID6 con un dispositivo adicional, todo el proceso es la sección crítica. En este caso, la reorganización de fracciones deberá progresar en etapas, ya que una sección se suspende, se respalda, se reorganiza y se libera.

NOMBRE

md - Dispositivos de matrices de disco de Linux

DESCRIPCIÓN

Este archivo se utiliza para controlar varios aspectos del controlador md (matriz de discos) de Linux. Las variables son de solo lectura, excepto aquellas para las cuales se indica explícitamente que son escribibles.

Todos estos archivos se encuentran en el directorio /proc/sys/dev/raid/.

md/sync_action
Este archivo controla la acción que se está ejecutando actualmente en una matriz md. Solo es aplicable si el archivo MD_REPLACE_DATA está presente para la matriz.

Se pueden escribir los siguientes valores:

resync
Inicia una resincronización completa de la matriz.
resync_force
Inicia una resincronización completa, ignorando si un disco está marcado como defectuoso.
check
Inicia una comprobación de paridad completa.
repair
Inicia una reparación completa (reconstrucción). Esto es equivalente a una resincronización con corrección de errores.
repair_force
Inicia una reparación completa, ignorando si un disco está marcado como defectuoso.
recovery
Esta acción es equivalente a resync_force.
idle
Detiene cualquier operación en curso.

También se puede escribir un valor en el archivo /proc/sys/dev/raid/n/check, donde n es el número de dispositivo md. Esto causará que se realice la misma comprobación, pero los errores se corregirán.

Finalmente, se puede escribir idle para detener el proceso de comprobación/reparación.

md/stripe_cache_size
Esto solo está disponible en RAID5 y RAID6. Registra el tamaño (en páginas por dispositivo) de la caché de bandas, que se utiliza para sincronizar todas las operaciones de escritura en la matriz y todas las operaciones de lectura si la matriz está degradada. El valor predeterminado es 256. Los valores válidos son de 17 a 32768. Aumentar este número puede mejorar el rendimiento en algunas situaciones, a costa de memoria del sistema. Tenga en cuenta que establecer este valor demasiado alto puede provocar una condición de "falta de memoria" en el sistema.

memory_consumed = system_page_size * nr_disks * stripe_cache_size

md/preread_bypass_threshold
Esto solo está disponible en RAID5 y RAID6. Esta variable establece el número de veces que MD atenderá una escritura de banda completa antes de atender una banda que requiere alguna "prelectura". Para garantizar la equidad, el valor predeterminado es 1. Los valores válidos son de 0 a stripe_cache_size. Establecer esto en 0 maximiza el rendimiento de escritura secuencial a costa de la equidad para los hilos que realizan escrituras pequeñas o aleatorias.
md/bitmap/backlog
El valor almacenado en el archivo solo tiene efecto en RAID1 cuando los dispositivos de escritura principal están activos y las solicitudes de escritura a esos dispositivos se procesan en segundo plano.

Esta variable establece un límite en el número de escrituras en segundo plano concurrentes, los valores válidos son de 0 a 16383, 0 significa que la escritura diferida no está permitida, mientras que cualquier otro número significa que puede ocurrir. Si hay más solicitudes de escritura que el número especificado, las nuevas escrituras serán síncronas.

md/bitmap/can_clear
Esto es para mapas de bits gestionados externamente, donde el kernel escribe el mapa de bits en sí, pero los metadatos que describen el mapa de bits son gestionados por mdmon o similar.

Cuando la matriz está degradada, los bits no deben borrarse. Cuando la matriz vuelve a ser óptima, los bits pueden borrarse, pero primero los metadatos deben registrar el recuento de eventos actual. Por lo tanto, md establece esto en 'false' y notifica a mdmon, luego mdmon actualiza los metadatos y escribe 'true'.

No hay código en mdmon para hacer esto realmente, así que tal vez ni siquiera funcione.

md/bitmap/chunksize
El tamaño de bloque del mapa de bits solo se puede cambiar cuando no hay ningún mapa de bits activo, y el valor debe ser una potencia de 2 y al menos 512.
md/bitmap/location
Esto indica dónde se almacena el mapa de bits de intención de escritura para la matriz. Puede ser "none" o "file" o un desplazamiento firmado desde los metadatos de la matriz, medido en sectores. No puede establecer un archivo escribiendo aquí; eso solo se puede hacer con la ioctl SET_BITMAP_FILE.

Escribir 'none' en 'bitmap/location' borrará el mapa de bits, y el valor de la ubicación anterior debe escribirse en él para restaurar el mapa de bits.

md/bitmap/max_backlog_used
Esto rastrea el número máximo de solicitudes concurrentes de escritura en segundo plano para una matriz md, escribir cualquier valor en este archivo lo borrará.
md/bitmap/metadata
Esto puede ser 'internal', 'clustered' o 'external'. 'internal' se establece por defecto, lo que significa que los metadatos del mapa de bits se almacenan en los primeros 256 bytes del espacio del mapa de bits. 'clustered' significa que se utilizan metadatos de mapa de bits separados para cada nodo del clúster. 'external' significa que los metadatos del mapa de bits son gestionados externamente al kernel.
md/bitmap/space
Esto muestra el espacio (en sectores) que está disponible en md/bitmap/location, y permite al kernel saber cuándo es seguro cambiar el tamaño del mapa de bits para que coincida con una matriz redimensionada. Debería ser suficientemente grande para contener los bytes totales del mapa de bits.

Para metadatos 1.0, supongamos que podemos usar hasta la superbloque si está antes, de lo contrario hasta 4K más allá de la superbloque. Para otras versiones de metadatos, suponga que no es posible ningún cambio.

md/bitmap/time_base
Esto muestra el tiempo (en segundos) entre volcados de disco, y se utiliza para buscar bits en el mapa de bits para ser borrados.

El valor predeterminado es 5 segundos, y debe ser un valor de entero largo sin signo.

PARÁMETROS DEL KERNEL

El controlador md reconoció varios parámetros de kernel diferentes.

raid=noautodetect
Esto deshabilitará la detección normal de matrices md que ocurre al arrancar. Si una unidad está particionada con particiones estilo MS-DOS, entonces si alguna de las 4 particiones principales tiene un tipo de partición de 0xFD, esa partición normalmente se inspeccionará para ver si es parte de una matriz MD, y si se encuentran matrices completas, se iniciarán. Este parámetro del kernel deshabilita este comportamiento.
md_mod.start_ro=1
/sys/module/md_mod/parameters/start_ro
Esto indica a md que inicie todas las matrices en modo de solo lectura. Esto es un modo de solo lectura suave que cambiará automáticamente a lectura/escritura en la primera solicitud de escritura. Sin embargo, hasta esa solicitud de escritura, md no escribe nada en ningún dispositivo y, en particular, no se inicia ninguna operación de resincronización o recuperación.
md_mod.start_dirty_degraded=1
/sys/module/md_mod/parameters/start_dirty_degraded
Como se mencionó anteriormente, md normalmente no iniciará un RAID4, RAID5 o RAID6 que esté sucio y degradado, ya que esta situación puede implicar una pérdida de datos oculta. Esto puede ser inconveniente si el sistema de archivos raíz se ve afectado. El uso de este parámetro de módulo permite que dichas matrices se inicien al arrancar. Debe entenderse que existe un riesgo real (aunque pequeño) de corrupción de datos en esta situación.
md=n,dev,dev,...
md=dn,dev,dev,...
Esto indica al controlador md que ensamble /dev/md n a partir de los dispositivos listados. Solo es necesario iniciar el dispositivo que contiene el sistema de archivos raíz de esta manera. Es mejor iniciar otras matrices una vez que el sistema haya arrancado.
md=n,l,c,i,dev...
Esto indica al controlador md que ensamble una matriz RAID0 o LINEAR heredada sin superbloque. n da el número de dispositivo md, l da el nivel, 0 para RAID0 o -1 para LINEAR, c da el tamaño de bloque como un logaritmo en base 2 desplazado en doce, por lo que 0 significa 4K, 1 significa 8K. i se ignora (soporte heredado).
