MDMON(8) Manual del Administrador del Sistema MDMON(8)

NOMBRE

mdmon - monitorizar arrays de metadatos MD externos

SINOPSIS

mdmon [--all] [--takeover] [--foreground] CONTENEDOR

DESCRIPCIÓN GENERAL

El kernel 2.6.27 introduce la capacidad de soportar arrays de metadatos externos. Los metadatos externos implican que el espacio de usuario maneja todas las actualizaciones de los metadatos. La responsabilidad del kernel es notificar al espacio de usuario cuando ocurre un "evento de metadatos", como fallos de disco y transiciones de limpio a sucio. El kernel, en casos importantes, espera a que el espacio de usuario tome medidas sobre estas notificaciones.

DESCRIPCIÓN

Actualizaciones de metadatos:

Para atender las solicitudes de actualización de metadatos, se introduce un demonio, mdmon. Mdmon tiene la tarea de buscar cambios en los atributos array_state, sync_action y state por disco en el espacio de nombres sysfs. Cuando se detecta un cambio, llama a un manejador por tipo de metadatos para realizar modificaciones en los metadatos. Se toman las siguientes acciones:

estado_del_array - inactivo
Borra el bit sucio para el volumen y permite que el array se detenga
estado_del_array - escritura pendiente
Establece el bit sucio para el array y luego establece estado_del_array a activo. Las escrituras se bloquean hasta que el espacio de usuario escriba activo.
estado_del_array - activo-inactivo
El temporizador de modo seguro ha expirado, así que se establece el estado del array a limpio para bloquear escrituras en el array
estado_del_array - limpio
Borra el bit sucio para el volumen
estado_del_array - solo lectura
Este es el estado inicial con el que comienzan todos los arrays. mdmon toma una de las tres acciones:
1/
Transiciona el array a lectura-automática manteniendo el bit sucio borrado si el manejador de metadatos determina que el array no necesita resincronización ni otra modificación.
2/
Transiciona el array a activo si el manejador de metadatos determina que se necesita una resincronización o alguna otra manipulación.
3/
Deja el array en modo de solo lectura si el volumen está marcado para no ser monitorizado; por ejemplo, la versión de metadatos se ha establecido a "externo:-/dev/md127" en lugar de "externo:/dev/md127"
accion_de_sincronizacion - resincronizar-a-inactivo
Notifica al manejador de metadatos que una resincronización puede haber completado. Si un proceso de resincronización se pone en pausa antes de completarse, este evento permite al manejador de metadatos verificar la resincronización.
accion_de_sincronizacion - recuperar-a-inactivo
Un repuesto puede haber completado la reconstrucción, así que informa al manejador de metadatos sobre el estado de cada disco. Esta es la oportunidad del manejador de metadatos para borrar cualquier bit "fuera de sincronización" y el estado degradado del volumen. Si un proceso de recuperación se pone en pausa antes de completarse, este evento permite al manejador de metadatos verificar la recuperación.
<disco>/estado - defectuoso
Un fallo de disco desencadena una serie de eventos. Primero, notifica al manejador de metadatos que un disco ha fallado, y luego notifica al kernel que puede desbloquear escrituras que dependían de este disco. Después de desbloquear el kernel, este disco se marca para ser eliminado+ de el array miembro. Finalmente, el disco se marca como fallido en todos los demás arrays miembro del contenedor.
+ Nota: Este comportamiento difiere ligeramente de los arrays MD nativos donde la eliminación está reservada para un evento de mdadm --remove. En el caso de metadatos externos, el contenedor mantiene la referencia final sobre un dispositivo de bloque y todavía se requiere una llamada mdadm --remove <contenedor> <víctima>.

Contenedores:

Los formatos de metadatos externos, como DDF, difieren de los formatos de metadatos MD nativos en que definen un conjunto de discos y una serie de sub-arrays dentro de esos discos. Los metadatos MD en comparación definen una relación 1:1 entre un conjunto de dispositivos de bloque y un array RAID. Por ejemplo, para crear 2 arrays en diferentes niveles RAID en un solo conjunto de discos, los metadatos MD requieren que los discos se particionen y luego cada array se puede crear con un subconjunto de esas particiones. Los formatos externos compatibles realizan esta segmentación de disco internamente.

Los dispositivos contenedores simplemente mantienen referencias a todos los discos miembro y permiten que herramientas como mdmon determinen qué arrays activos pertenecen a qué contenedor. Algunos comandos de gestión de arrays como la eliminación de discos y la adición de discos ahora solo son válidos a nivel de contenedor. Los intentos de realizar estas acciones en arrays miembro se bloquean con mensajes de error como:

"mdadm: No se pueden eliminar discos de un array 'miembro', realice esta operación en el contenedor padre"

Los contenedores se identifican en /proc/mdstat con una cadena de versión de metadatos "external:<nombre_metadatos>". Los dispositivos miembro se identifican mediante "external:/<dispositivo_contenedor>/<índice_miembro>", o "external:-/<dispositivo_contenedor>/<índice_miembro>" si el array debe permanecer de solo lectura.

OPCIONES

CONTENEDOR
El dispositivo contenedor a monitorizar. Puede ser una ruta completa como /dev/md/contenedor, o un simple nombre de dispositivo md como md127.
--foreground
Normalmente, mdmon se bifurcará y continuará en segundo plano. Añadir esta opción omitirá ese paso y ejecutará mdmon en primer plano.
--takeover
Esto indica a mdmon que reemplace cualquier mdmon activo que esté actualmente monitorizando el array. Esto se usa principalmente al final del proceso de arranque para reemplazar cualquier mdmon que se haya iniciado desde un initramfs antes de que se montara el sistema de archivos raíz. Esto evita mantener una referencia en ese initramfs indefinidamente y asegura que los archivos pid y sock utilizados para comunicarse con mdmon estén en un lugar estándar.
--all
Esto indica a mdmon que encuentre cualquier contenedor activo y comience a monitorizar cada uno de ellos si es apropiado. Esto se usa normalmente con --takeover al final de la secuencia de arranque. Se inicia un proceso mdmon separado para cada contenedor, ya que el argumento --all se sobrescribe con el nombre del contenedor. Para permitir contenedores con nombres más largos de 5 caracteres, este argumento puede extenderse arbitrariamente, por ejemplo a --todos-arrays-activos.

Tenga en cuenta que mdmon es iniciado automáticamente por mdadm cuando es necesario y por lo tanto no necesita ser considerado al trabajar con arrays RAID. Las únicas veces que se ejecuta aparte de por mdadm es cuando los scripts de arranque necesitan reiniciarlo después de montar el nuevo sistema de archivos raíz.

ARRANQUE Y APAGADO

Como mdmon necesita estar en ejecución cada vez que se monta cualquier sistema de archivos en el dispositivo monitorizado, hay consideraciones especiales cuando el sistema de archivos raíz se monta desde un dispositivo monitorizado por mdmon. Tenga en cuenta que, en general, mdmon es necesario incluso si el sistema de archivos se monta en modo de solo lectura, ya que algunos sistemas de archivos aún pueden escribir en el dispositivo en esas circunstancias, por ejemplo, para reproducir un diario después de un apagado inesperado.

Cuando el array es ensamblado por el código initramfs, mdadm iniciará automáticamente mdmon según sea necesario. Esto significa que mdmon debe estar instalado en el initramfs y debe haber un sistema de archivos escribible (típicamente tmpfs) en el que mdmon pueda crear un archivo .pid y un archivo .sock. El sistema de archivos particular a usar se proporciona a mdmon en tiempo de compilación y por defecto es /run/mdadm.

Este sistema de archivos debe persistir hasta el momento del apagado.

mdmon(8)

NAME

mdmon - monitors all MD devices

SYNOPSIS

mdmon --all [--takeover] [--foreground] [--check-interval seconds]

mdmon [--export-resume device] [--daemonize]

mdmon [--stop]

mdmon [--scan]

mdmon [--version]

mdmon [-h | --help]

OVERVIEW

The mdmon daemon monitors the status of all MD devices. It can notify the user of changes, take ownership of devices from an existing mdmon instance, or perform actions at shutdown time.

DESCRIPTION

The mdmon daemon is responsible for monitoring the status of all MD (Multiple Device) devices, which are typically RAID arrays managed by the Linux kernel's MD driver. It can perform various tasks, including reporting status changes, taking over monitoring from another instance, and managing devices during system startup and shutdown.

When run with --all, mdmon monitors all active MD devices. If the --takeover option is also specified, it attempts to replace any existing mdmon process that is monitoring these devices. This is particularly useful during the boot process when an initramfs might be running its own instance of mdmon. By using --takeover, the primary system's mdmon can assume control, allowing the memory used by the initramfs instance to be freed.

At system shutdown, mdmon should not be terminated abruptly like other processes. If it holds a file descriptor open (typically a socket in /dev by default), it can prevent the /dev filesystem from being unmounted, especially if /dev resides on a separate filesystem.

OPTIONS

--all
Monitor all active MD devices.
--takeover
Attempt to replace an existing mdmon instance.
--foreground
Run mdmon in the foreground (do not daemonize).
--check-interval seconds
Set the interval (in seconds) for checking the status of MD devices. Defaults to 15 seconds.
--export-resume device
Export the resume information for the specified MD device. This is typically used during shutdown.
--daemonize
Run mdmon as a background daemon.
--stop
Stop the running mdmon daemon.
--scan
Scan for MD devices and print information about them. This is typically used by other scripts.
--version
Display the version of mdmon.
-h, --help
Display a help message and exit.

START UP AND SHUTDOWN

During system startup, if an initramfs was used, mdmon should be run with --all --takeover so that the mdmon running from the initramfs can be replaced with one running in the main root, and so the memory used by the initramfs can be released.

At shutdown time, mdmon should not be killed along with other processes. Also as it holds a file (socket actually) open in /dev (by default) it will not be possible to unmount /dev if it is a separate filesystem.

EXAMPLES

mdmon --all-active-arrays --takeover
Any mdmon which is currently running is killed and a new instance is started. This should be run during in the boot sequence if an initramfs was used, so that any mdmon running from the initramfs will not hold the initramfs active.
