MARIADB-BINLOG(1) Sistema de base de datos MariaDB MARIADB-BINLOG(1)

NOMBRE

mariadb-binlog - utilidad para procesar archivos de registro binario (mariadb-binlog es ahora un enlace simbólico a mariadb-binlog)

SINOPSIS

mariadb-binlog [opciones] archivo_log ...

DESCRIPCIÓN

El registro binario del servidor consta de archivos que contienen “eventos” que describen modificaciones al contenido de la base de datos. El servidor escribe estos archivos en formato binario. Para mostrar su contenido en formato de texto, utiliza la utilidad mariadb-binlog. También puedes usar mariadb-binlog para mostrar el contenido de los archivos de registro de retransmisión (relay log) escritos por un servidor esclavo en una configuración de replicación, ya que los registros de retransmisión tienen el mismo formato que los registros binarios.

Invoca mariadb-binlog de esta manera:

shell> mariadb-binlog [opciones] archivo_log ...

Por ejemplo, para mostrar el contenido del archivo de registro binario llamado binlog.000003, utiliza este comando:

shell> mariadb-binlog binlog.0000003

La salida incluye los eventos contenidos en binlog.000003. Para el registro basado en sentencias, la información del evento incluye la sentencia SQL, el ID del servidor en el que se ejecutó, la marca de tiempo cuando se ejecutó la sentencia, cuánto tiempo tomó, etc. Para el registro basado en filas, el evento indica un cambio de fila en lugar de una sentencia SQL.

Los eventos van precedidos de comentarios de encabezado que proporcionan información adicional. Por ejemplo:

# at 141
#100309  9:28:36 server id 123  end_log_pos 245
  Query thread_id=3350  exec_time=11  error_code=0

En la primera línea, el número que sigue a `at` indica la posición de inicio del evento en el archivo de registro binario.

La segunda línea comienza con una fecha y hora que indica cuándo se inició la sentencia en el servidor donde se originó el evento. Para la replicación, esta marca de tiempo se propaga a los servidores esclavos. `server id` es el valor `server_id` del servidor donde se originó el evento. `end_log_pos` indica dónde comienza el siguiente evento (es decir, es la posición final del evento actual + 1). `thread_id` indica qué hilo ejecutó el evento. `exec_time` es el tiempo dedicado a ejecutar el evento, en un servidor maestro. En un esclavo, es la diferencia entre la hora de finalización de la ejecución en el esclavo menos la hora de inicio de la ejecución en el maestro. La diferencia sirve como un indicador de cuánto rezago tiene la replicación con respecto al maestro. `error_code` indica el resultado de ejecutar el evento. Cero significa que no ocurrió ningún error.

La salida de mariadb-binlog puede ser re-ejecutada (por ejemplo, usándola como entrada para mariadb) para rehacer las sentencias en el registro. Esto es útil para operaciones de recuperación después de un fallo del servidor. Para otros ejemplos de uso, consulta la discusión más adelante en esta sección.

Normalmente, usas mariadb-binlog para leer directamente los archivos de registro binario y aplicarlos al servidor MariaDB local. También es posible leer registros binarios de un servidor remoto utilizando la opción --read-from-remote-server. Para leer registros binarios remotos, se pueden proporcionar las opciones de parámetros de conexión para indicar cómo conectarse al servidor. Estas opciones son --host, --password, --port, --protocol, --socket y --user; se ignoran excepto cuando también se usa la opción --read-from-remote-server.

mariadb-binlog admite las siguientes opciones, que se pueden especificar en la línea de comandos o en los grupos de archivos de opciones [mariadb-binlog] y [client].

•--help, -?

Muestra un mensaje de ayuda y sale.

•--base64-output=valor

Esta opción determina cuándo se deben mostrar los eventos codificados como cadenas base64 utilizando sentencias BINLOG. La opción tiene estos valores permitidos (no distingue entre mayúsculas y minúsculas):

•AUTO ("automático") o UNSPEC ("no especificado") muestra sentencias BINLOG automáticamente cuando es necesario (es decir, para eventos de descripción de formato y eventos de fila). Este es el valor predeterminado si no se proporciona ninguna opción --base64-output.

Nota
La visualización automática de BINLOG es el único comportamiento seguro si tienes la intención de usar la salida de mariadb-binlog para volver a ejecutar el contenido de los archivos de registro binario. Los otros valores de opción están destinados solo a fines de depuración o prueba, ya que pueden producir una salida que no incluya todos los eventos en formato ejecutable.
•NEVER hace que no se muestren las sentencias BINLOG. mariadb-binlog sale con un error si se encuentra un evento de fila que debe mostrarse usando BINLOG.
•DECODE-ROWS especifica a mariadb-binlog que tienes la intención de que los eventos de fila se decodifiquen y se muestren como sentencias SQL comentadas, especificando también la opción --verbose. Al igual que NEVER, DECODE-ROWS suprime la visualización de sentencias BINLOG, pero a diferencia de NEVER, no sale con un error si se encuentra un evento de fila.
Se puede proporcionar --base64-output como --base64-output o --skip-base64-output (con el sentido de AUTO o NEVER).

Para ver ejemplos que muestran el efecto de --base64-output y --verbose en la salida de eventos de fila, consulta la sección llamada “VISUALIZACIÓN DE EVENTOS DE FILA DE MARIADB-BINLOG”.

•--binlog-row-event-max-size=ruta

El directorio donde están instalados los conjuntos de caracteres.

•--character-sets-dir=ruta

El directorio donde están instalados los conjuntos de caracteres.

•--database=nombre_bd, -d nombre_bd

Esta opción hace que mariadb-binlog muestre entradas del registro binario (solo registro local) que ocurren mientras nombre_bd ha sido seleccionada como base de datos predeterminada mediante USE.

La opción --database para mariadb-binlog es similar a la opción --binlog-do-db para mariadbd, pero se puede usar para especificar solo una base de datos. Si --database se proporciona varias veces, solo se utiliza la última instancia.

Los efectos de esta opción dependen de si se está utilizando el formato de registro basado en sentencias o en filas, de la misma manera que los efectos de --binlog-do-db dependen de si se está utilizando el formato de registro basado en sentencias o en filas.

Registro basado en sentencias. La opción --database funciona de la siguiente manera:

•Mientras nombre_bd sea la base de datos predeterminada, se mostrarán las sentencias, ya sea que modifiquen tablas en nombre_bd o en una base de datos diferente.
•A menos que nombre_bd se seleccione como la base de datos predeterminada, no se mostrarán las sentencias, incluso si modifican tablas en nombre_bd.
•Hay una excepción para CREATE DATABASE, ALTER DATABASE y DROP DATABASE. La base de datos que se está *creando, alterando o eliminando* se considera la base de datos predeterminada al determinar si se muestra la sentencia.
Supongamos que el registro binario se creó ejecutando estas sentencias usando registro basado en sentencias: 
INSERT INTO test.t1 (i) VALUES(100);
INSERT INTO db2.t2 (j)  VALUES(200);
USE test;
INSERT INTO test.t1 (i) VALUES(101);
INSERT INTO t1 (i)      VALUES(102);
INSERT INTO db2.t2 (j)  VALUES(201);
USE db2;
INSERT INTO test.t1 (i) VALUES(103);
INSERT INTO db2.t2 (j)  VALUES(202);
INSERT INTO t2 (j)      VALUES(203);

mariadb-binlog --database=test no muestra las dos primeras sentencias INSERT porque no hay una base de datos predeterminada. Muestra las tres sentencias INSERT que siguen a USE test, pero no las tres sentencias INSERT que siguen a USE db2.

mariadb-binlog --database=db2 no muestra las dos primeras sentencias INSERT porque no hay una base de datos predeterminada. No muestra las tres sentencias INSERT que siguen a USE test, pero sí muestra las tres sentencias INSERT que siguen a USE db2.

Registro basado en filas. mariadb-binlog solo muestra entradas que modifican tablas pertenecientes a nombre_bd. La base de datos predeterminada no tiene ningún efecto en esto. Supongamos que el registro binario descrito anteriormente se creó utilizando registro basado en filas en lugar de registro basado en sentencias. mariadb-binlog --database=test solo muestra aquellas entradas que modifican t1 en la base de datos test, independientemente de si se emitió USE o cuál es la base de datos predeterminada. Si un servidor se está ejecutando con binlog_format establecido en MIXED y deseas que sea posible usar mariadb-binlog con la opción --database, debes asegurarte de que las tablas que se modifican estén en la base de datos seleccionada.

•--debug[=debug_options], -# [debug_options]

Escribe un registro de depuración. Una cadena de debug_options típica es 'd:t:o,nombre_archivo'. El valor por defecto es 'd:t:o,/tmp/mariadb-binlog.trace'.

•--debug-check

Imprime información de depuración cuando el programa sale.

•--debug-info

Imprime información de depuración y estadísticas de uso de memoria y CPU cuando el programa sale.

•--defaults-extra-file=nombre

Lee este archivo después de que se lean los archivos globales.

•--defaults-file=nombre

Solo lee las opciones por defecto del archivo dado.

•--default-auth=nombre

Plugin de autenticación del lado del cliente por defecto a usar.

•--disable-log-bin, -D

Deshabilita el registro binario. Esto es útil para evitar un bucle infinito si usas la opción --to-last-log y estás enviando la salida al mismo servidor MariaDB. Esta opción también es útil al restaurar después de un fallo para evitar la duplicación de las sentencias que has registrado.

Esta opción requiere que tengas el privilegio SUPER. Hace que mariadb-binlog incluya una sentencia SET sql_log_bin = 0 en su salida para deshabilitar el registro binario de la salida restante. La sentencia SET es ineficaz a menos que tengas el privilegio SUPER.

•--flashback, -B

Soporta el modo flashback.

•--force-if-open

Fuerza si el binlog no se cerró correctamente. Por defecto está activado; usa --skip-force-if-open para deshabilitarlo.

•--force-read, -f

Con esta opción, si mariadb-binlog lee un evento de registro binario que no reconoce, imprime una advertencia, ignora el evento y continúa. Sin esta opción, mariadb-binlog se detiene si lee dicho evento.

•--hexdump, -H

Muestra un volcado hexadecimal del registro en comentarios, como se describe en la sección llamada “FORMATO DE VOLCADO HEXADECIMAL DE MARIADB-BINLOG”. La salida hexadecimal puede ser útil para depurar la replicación.

•--host=nombre_host, -h nombre_host

Obtiene el registro binario del servidor MariaDB en el host dado.

•--local-load=ruta, -l ruta

Prepara archivos temporales locales para LOAD DATA INFILE en el directorio especificado.

•--no-defaults

No leer opciones por defecto de ningún archivo de opciones.

•--offset=N, -o N

Omite las primeras N entradas del registro.

•--open-files-limit=NUM

Establece la variable open_files_limit, que se utiliza para reservar descriptores de archivo para mariadb-binlog.

•--password[=contraseña], -p[contraseña]

La contraseña a usar al conectarse al servidor. Si usas la forma corta de la opción (-p), *no* puedes dejar un espacio entre la opción y la contraseña. Si omites el valor de la contraseña siguiendo la opción --password o -p en la línea de comandos, mariadb-binlog te pedirá una.

Especificar una contraseña en la línea de comandos debe considerarse inseguro. Puedes usar un archivo de opciones para evitar dar la contraseña en la línea de comandos.

•--plugin-dir=nombre_dir

Directorio para plugins del lado del cliente.

•--print-defaults

Imprime la lista de argumentos del programa de todos los archivos de opciones y sale.

•--port=num_puerto, -P num_puerto

El número de puerto TCP/IP a usar para conectarse a un servidor remoto, o 0 para usar por defecto, en orden de preferencia, my.cnf, $MYSQL_TCP_PORT, /etc/services, valor por defecto incorporado (3306). Fuerza --protocol=tcp cuando se especifica en la línea de comandos sin otras propiedades de conexión.

•--protocol={TCP|SOCKET|PIPE|MEMORY}

El protocolo de conexión a usar para conectarse al servidor. Es útil cuando los otros parámetros de conexión normalmente harían que se usara un protocolo diferente al que deseas.

•--raw

Requiere -R. Muestra datos binarios crudos en lugar de sentencias SQL. Los archivos de salida se nombran según los registros del servidor.

•--read-from-remote-server, -R

Lee el registro binario de un servidor MariaDB en lugar de leer un archivo de registro local. Cualquier opción de parámetro de conexión se ignora a menos que también se proporcione esta opción. Estas opciones son --host, --password, --port, --protocol, --socket y --user.

Esta opción requiere que el servidor remoto esté en ejecución. Solo funciona para archivos de registro binario en el servidor remoto, no para archivos de registro de retransmisión.

•--result-file=nombre, -r nombre

Dirige la salida al archivo dado. Con --raw esto es un prefijo para los nombres de archivo.

•--rewrite-db=nombre, -r nombre

Actualiza a una base de datos con un nombre diferente al original. Ejemplo: rewrite-db='de->a'. Para eventos que se registran en binario como sentencias, reescribir la base de datos constituye cambiar la base de datos por defecto de una sentencia de db1 a db2. No hay análisis de sentencias ni reescritura de ningún tipo, es decir, si se especifica "db1.tbl" explícitamente en la sentencia, esa aparición no se cambiará a "db2.tbl". Los eventos basados en filas se reescriben correctamente para usar el nuevo nombre de base de datos. El filtrado (por ejemplo, con --database=nombre) ocurre después de que se hayan realizado las reescrituras de la base de datos. Si usas esta opción en la línea de comandos y ">" tiene un significado especial para tu intérprete de comandos, entrecomilla el valor (por ejemplo, --rewrite-db="nombreantiguo->nombrenuevo".

•--server-id=id

Muestra solo los eventos creados por el servidor con el ID de servidor dado.

•--set-charset=nombre_juego_caracteres

Añade una sentencia SET NAMES nombre_juego_caracteres a la salida para especificar el juego de caracteres a usar para procesar los archivos de registro.

•--short-form, -s

Muestra solo las sentencias contenidas en el registro, sin información adicional ni eventos basados en filas. Esto es solo para pruebas y no debe usarse en sistemas de producción. Si deseas suprimir la salida base64, considera usar --base64-output=never en su lugar.

•--socket=ruta, -S ruta

Para conexiones a localhost, el archivo de socket Unix a usar, o, en Windows, el nombre del named pipe a usar. Fuerza --protocol=socket cuando se especifica en la línea de comandos sin otras propiedades de conexión; en Windows, fuerza --protocol=pipe.

•--start-datetime=fecha_hora

Comienza a leer el registro binario en el primer evento que tenga una marca de tiempo igual o posterior al argumento fecha_hora. El valor fecha_hora es relativo a la zona horaria local de la máquina donde ejecutas mariadb-binlog. El valor debe estar en un formato aceptado para los tipos de datos DATETIME o TIMESTAMP. Por ejemplo:

shell> mariadb-binlog --start-datetime="2014-12-25 11:25:56" binlog.000003

Esta opción es útil para la recuperación a un punto en el tiempo.

•--start-position=N, -j N

Comienza a leer el registro binario en la posición N. El tipo puede ser un entero positivo o una lista de GTID. Cuando se usa un entero positivo, el valor solo se aplica al primer binlog pasado en la línea de comandos, y se imprime el primer evento que tenga una posición igual o mayor que N. En modo GTID, se pueden pasar múltiples GTID como una lista separada por comas, donde cada una debe tener un ID de dominio único. La lista representa el estado del binlog gtid que el cliente (otro servidor "réplica") conoce. Por lo tanto, cada GTID es exclusivo; solo se imprimirán eventos después de un número de secuencia dado para permitir a los usuarios recibir eventos después de su estado actual.

Esta opción es útil para la recuperación a un punto en el tiempo.

•--gtid-strict-mode

Procesa el binlog de acuerdo con la especificación gtid-strict-mode. Las posiciones de inicio y fin se verifican para que cumplan la condición de comparación start < stop. Los números de secuencia de cualquier dominio gtid deben formar una secuencia monotónicamente creciente.

•--stop-datetime=fecha_hora

Detiene la lectura del registro binario en el primer evento que tenga una marca de tiempo igual o posterior al argumento fecha_hora. Esta opción es útil para la recuperación a un punto en el tiempo. Consulta la descripción de la opción --start-datetime para obtener información sobre el valor fecha_hora.

Esta opción es útil para la recuperación a un punto en el tiempo.

•--stop-never

Espera más datos del servidor en lugar de detenerse al final del último registro. Implica --to-last-log.

•--stop-never-slave-server-id

El server_id del esclavo utilizado para --read-from-remote-server --stop-never.

•--stop-position=N

Detiene la lectura del registro binario en el primer evento que tenga una posición igual o mayor que N. El tipo puede ser un entero positivo o una lista de GTID. Cuando se usa un entero positivo, el valor solo se aplica al último archivo de registro nombrado en la línea de comandos. Cuando está en modo GTID, se pueden pasar múltiples GTID como una lista separada por comas, donde cada una debe tener un ID de dominio único. Cada GTID es inclusiva; solo se imprimen los eventos hasta los números de secuencia dados.

Esta opción es útil para la recuperación a un punto en el tiempo.

•--table, -T

Enumera entradas solo para esta tabla (solo registro local).

• --to-last-log, -t

No se detenga al final del registro binario solicitado de un servidor MariaDB, sino que continúe imprimiendo hasta el final del último registro binario. Si envía la salida al mismo servidor MariaDB, esto puede generar un bucle infinito, por lo que esta opción requiere --read-from-remote-server.

•--user=nombre_usuario, -u nombre_usuario

El nombre de usuario de MariaDB a usar al conectarse a un servidor remoto.

•--verbose, -v

Reconstruye eventos de fila y los muestra como sentencias SQL comentadas. Si se proporciona esta opción dos veces, la salida incluye comentarios para indicar los tipos de datos de columna y algunos metadatos. Si se proporciona esta opción tres veces, la salida incluye advertencias de diagnóstico sobre la integridad del evento antes de la salida del programa.

Para ver ejemplos que muestran el efecto de --base64-output y --verbose en la visualización de eventos de fila, consulte la sección llamada "MARIADB-BINLOG ROW EVENT DISPLAY".

•--version, -V

Muestra la información de la versión y sale.

También puede establecer la siguiente variable utilizando la sintaxis --nombre_var=valor:

•open_files_limit

Especifique el número de descriptores de archivo abiertos a reservar.

Puede canalizar la salida de mariadb-binlog al cliente mariadb para ejecutar los eventos contenidos en el registro binario. Esta técnica se utiliza para recuperarse de un bloqueo cuando se tiene una copia de seguridad antigua. Por ejemplo:

shell> mariadb-binlog binlog.000001 | mariadb -u root -p

O:

shell> mariadb-binlog binlog.[0-9]* | mariadb -u root -p

También puede redirigir la salida de mariadb-binlog a un archivo de texto, si necesita modificar el registro de sentencias primero (por ejemplo, para eliminar sentencias que no desea ejecutar por alguna razón). Después de editar el archivo, ejecute las sentencias que contiene utilizándolo como entrada para el programa mariadb:

shell> mariadb-binlog binlog.000001 > tmpfile
shell> ... editar tmpfile ...
shell> mariadb -u root -p < tmpfile

Cuando mariadb-binlog se invoca con la opción --start-position, muestra solo aquellos eventos con un desplazamiento en el registro binario mayor o igual a una posición dada (la posición dada debe coincidir con el inicio de un evento). También tiene opciones para detenerse y comenzar cuando ve un evento con una fecha y hora dadas. Esto le permite realizar una recuperación hasta un punto en el tiempo utilizando la opción --stop-datetime (para poder decir, por ejemplo, "restaura mis bases de datos a cómo estaban hoy a las 10:30 a.m.").

Si tiene más de un registro binario para ejecutar en el servidor MariaDB, el método seguro es procesarlos todos utilizando una única conexión al servidor. Aquí hay un ejemplo que demuestra lo que puede ser inseguro:

shell> mariadb-binlog binlog.000001 | mariadb -u root -p # PELIGRO!!
shell> mariadb-binlog binlog.000002 | mariadb -u root -p # PELIGRO!!

Procesar registros binarios de esta manera utilizando diferentes conexiones al servidor causa problemas si el primer archivo de registro contiene una sentencia CREATE TEMPORARY TABLE y el segundo registro contiene una sentencia que utiliza la tabla temporal. Cuando el primer proceso mariadb termina, el servidor elimina la tabla temporal. Cuando el segundo proceso mariadb intenta utilizar la tabla, el servidor informa "tabla desconocida".

Para evitar problemas como este, utilice un único proceso mariadb para ejecutar el contenido de todos los registros binarios que desee procesar. Aquí hay una forma de hacerlo:

shell> mariadb-binlog binlog.000001 binlog.000002 | mariadb -u root -p

Otro enfoque es escribir todos los registros en un solo archivo y luego procesar el archivo:

shell> mariadb-binlog binlog.000001 > /tmp/statements.sql
shell> mariadb-binlog binlog.000002 >> /tmp/statements.sql
shell> mariadb -u root -p -e "source /tmp/statements.sql"

mariadb-binlog puede producir una salida que reproduce una operación LOAD DATA INFILE sin el archivo de datos original. mariadb-binlog copia los datos a un archivo temporal y escribe una sentencia LOAD DATA LOCAL INFILE que hace referencia al archivo. La ubicación predeterminada del directorio donde se escriben estos archivos es específica del sistema. Para especificar un directorio explícitamente, utilice la opción --local-load.

Debido a que mariadb-binlog convierte las sentencias LOAD DATA INFILE en sentencias LOAD DATA LOCAL INFILE (es decir, agrega LOCAL), tanto el cliente como el servidor que se utilizan para procesar las sentencias deben estar configurados con la capacidad LOCAL habilitada.


Advertencia

Los archivos temporales creados para las sentencias LOAD DATA LOCAL no se eliminan automáticamente porque son necesarios hasta que realmente se ejecutan esas sentencias. Debe eliminar los archivos temporales usted mismo después de que ya no necesite el registro de sentencias. Los archivos se pueden encontrar en el directorio de archivos temporales y tienen nombres como nombre_archivo_original-#-#.

FORMATO DE VOLCADO HEXADECIMAL DE MARIADB-BINLOG

La opción --hexdump hace que mariadb-binlog produzca un volcado hexadecimal del contenido del registro binario:

shell> mariadb-binlog --hexdump master-bin.000001

La salida hexadecimal consta de líneas de comentarios que comienzan con #, por lo que la salida podría verse así para el comando anterior:

/*!40019 SET @@session.max_delayed_threads=0*/;
/*!50003 SET @OLD_COMPLETION_TYPE=@@COMPLETION_TYPE,COMPLETION_TYPE=0*/;
# at 4
#051024 17:24:13 server id 1  end_log_pos 98
# Position  Timestamp   Type   Master ID        Size      Master Pos    Flags
# 00000004 9d fc 5c 43   0f   01 00 00 00   5e 00 00 00   62 00 00 00   00 00
# 00000017 04 00 35 2e 30 2e 31 35  2d 64 65 62 75 67 2d 6c |..5.0.15.debug.l|
# 00000027 6f 67 00 00 00 00 00 00  00 00 00 00 00 00 00 00 |og..............|
# 00000037 00 00 00 00 00 00 00 00  00 00 00 00 00 00 00 00 |................|
# 00000047 00 00 00 00 9d fc 5c 43  13 38 0d 00 08 00 12 00 |.......C.8......|
# 00000057 04 04 04 04 12 00 00 4b  00 04 1a                |.......K...|
#       Start: binlog v 4, server v 5.0.15-debug-log created 051024 17:24:13
#       at startup
ROLLBACK;

La salida del volcado hexadecimal contiene actualmente los elementos de la siguiente lista. Este formato está sujeto a cambios. (Para obtener más información sobre el formato del registro binario, consulte http://forge.mysql.com/wiki/MySQL_Internals_Binary_Log.)

•Posición: La posición en bytes dentro del archivo de registro.

mariadb-binlog

mariadb-binlog

Extracts and displays contents from MariaDB binary log files.

SYNOPSIS

mariadb-binlog [options] [log_file ...]

DESCRIPTION

The mariadb-binlog utility is used to read binary log files generated by a MariaDB server. It can be used to display the contents of the binary log in a human-readable format, or to replay the binary log on another server. This utility is often used for recovery purposes or for replication.

Binary log files contain information about data changes and statements executed on the server. The format of the binary log depends on the server's binlog_format setting (statement-based, row-based, or mixed).

mariadb-binlog can display the events found in the binary log in various formats, including:

•
Raw event data
•
SQL statements that correspond to the events
•
Row-based event data in a decoded format

The utility provides options to filter events, control the output format, and specify the source server ID.

OPTIONS

The following options are supported by mariadb-binlog:

--base64-output[={ NEV ER | DECODE-ROWS | ALL }]
Controls base64 encoding of row events.
NEVER
Do not use base64 encoding. If a row event is encountered, mariadb-binlog exits with an error.
DECODE-ROWS
Do not use base64 encoding for row events. This option is similar to NEVER, but it does not exit with an error if a row event is found. This is useful when combined with --verbose to display row events as SQL statements.
ALL
Use base64 encoding for all row events. This is the default behavior. Row events are displayed within BINLOG statements.
--database=db_name
Restrict output to events related to the specified database. If this option is used multiple times, events from any of the specified databases are included.
--disable-log-bin
Disable binary logging. This option is generally not applicable when using mariadb-binlog to read existing logs, but might be relevant in specific scenarios.
--enable-cleartext-plugin
Enable the cleartext authentication plugin. This is relevant if the binary log contains authentication events that use this plugin.
--force-check-interval=N
Force interval checks for log rotation.
--hexdump
Display raw event data in hexadecimal format. Useful for debugging.
--host=host_name, -h host_name
Connect to the MariaDB server with the specified hostname.
--local-infile[={0|1|ON|OFF}]
Control loading local files. Default is 1 (ON).
--log-slave-updates
Log events that are received from a master server.
--master-data
Write a CHANGE MASTER TO statement into the output. This is useful when using the output to set up a replica.
--master-server-id=N
Consider events only from the specified master server ID.
--max-read-size=N
Set the maximum size of data read from the log.
--no-defaults
Do not read default options from option files.
--old-protocol
Use the older binary log protocol.
--one-event-per-log
Process only one event per log file.
--open-files-in-advance
Open files in advance.
--password[=password], -p[password]
Password to use when connecting to the server.
--port=port_num, -P port_num
TCP/IP port number to use for connection.
--print-table-id
Print table IDs.
--protocol=[TCP|SOCKET|PIPE|MEMORY]
Transport protocol to use for connection.
--query-log
Display query log.
--raw
Display raw event data.
--read-from-remote-server
Read binary logs from a remote server.
--skip-gtids
Skip GTID (Global Transaction Identifier) events.
--slave-info
Output information about the slave's master.
--skip-numbering
Do not use event numbering.
--socket=path
Path to the Unix socket file to use for connection.
--stop-never
Never stop processing events.
--stop-position=N
Stop processing events at the specified position.
--user=user_name, -u user_name
User name to use when connecting to the server.
--verbose, -v

--verify-binlog-checksum
Verify binary log checksums.
--wait-unsafe-for-binlog-rotation
Wait unsafely for binary log rotation.
--width=N
Set the output width.

The following examples illustrate how mariadb-binlog displays row events that specify data modifications. These correspond to events with the WRITE_ROWS_EVENT, UPDATE_ROWS_EVENT, and DELETE_ROWS_EVENT type codes. The --base64-output=DECODE-ROWS and --verbose options may be used to affect row event output.

Suppose that the server is using row-based binary logging and that you execute the following sequence of statements:

(
  id   INT NOT NULL,
  name VARCHAR(20) NOT NULL,

) ENGINE = InnoDB;
START TRANSACTION;
INSERT INTO t VALUES(1, 'apple', NULL);

Note

You should not suppress BINLOG statements if you intend to re-execute mariadb-binlog output.

The SQL statements produced by --verbose for row events are much more readable than the corresponding BINLOG statements. However, they do not correspond exactly to the original SQL statements that generated the events. The following limitations apply:

•The original column names are lost and replaced by @N, where N is a column number.
•Character set information is not available in the binary log, which affects string column display:
•There is no distinction made between corresponding binary and nonbinary string types (BINARY and CHAR, VARBINARY and VARCHAR, BLOB and TEXT). The output uses a data type of STRING for fixed-length strings and VARSTRING for variable-length strings.
•For multi-byte character sets, the maximum number of bytes per character is not present in the binary log, so the length for string types is displayed in bytes rather than in characters. For example, STRING(4) will be used as the data type for values from either of these column types: 
CHAR(4) CHARACTER SET latin1
CHAR(2) CHARACTER SET ucs2
•Due to the storage format for events of type UPDATE_ROWS_EVENT, UPDATE statements are displayed with the WHERE clause preceding the SET clause.

Proper interpretation of row events requires the information from the format description event at the beginning of the binary log. Because mariadb-binlog does not know in advance whether the rest of the log contains row events, by default it displays the format description event using a BINLOG statement in the initial part of the output.

If the binary log is known not to contain any events requiring a BINLOG statement (that is, no row events), the --base64-output=NEVER option can be used to prevent this header from being written.
