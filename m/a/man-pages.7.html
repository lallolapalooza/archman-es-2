NOMBRE

man-pages - convenciones para escribir páginas del manual de Linux

SINOPSIS

man [sección] título

DESCRIPCIÓN

Esta página describe las convenciones que deben emplearse al escribir páginas del manual para el proyecto man-pages de Linux, que documenta la API del espacio de usuario proporcionada por el kernel de Linux y la biblioteca C de GNU. Por lo tanto, el proyecto proporciona la mayoría de las páginas de la Sección 2, muchas de las páginas que aparecen en las Secciones 3, 4 y 7, y unas pocas páginas que aparecen en las Secciones 1, 5 y 8 de las páginas del manual en un sistema Linux. Las convenciones descritas en esta página también pueden ser útiles para los autores que escriben páginas del manual para otros proyectos.

Secciones de las páginas del manual

Las secciones del manual se definen tradicionalmente de la siguiente manera:

1 Comandos de usuario (Programas)
Comandos que pueden ser ejecutados por el usuario desde dentro de un shell.
2 Llamadas al sistema
Funciones que envuelven operaciones realizadas por el kernel.
3 Llamadas de biblioteca
Todas las funciones de biblioteca excluyendo los envoltorios de llamadas al sistema (la mayoría de las funciones de libc).
4 Archivos especiales (dispositivos)
Archivos encontrados en /dev que permiten acceder a los dispositivos a través del kernel.
5 Formatos de archivo y archivos de configuración
Describe varios formatos de archivo legibles por humanos y archivos de configuración.
6 Juegos
Juegos y pequeños programas divertidos disponibles en el sistema.
7 Resumen, convenciones y misceláneos
Resúmenes o descripciones de varios temas, convenciones y protocolos, estándares de conjuntos de caracteres, la disposición estándar del sistema de archivos y varias otras cosas.
8 Comandos de administración del sistema
Comandos como mount(8), muchos de los cuales solo root puede ejecutar.

Paquete de macros

Las nuevas páginas del manual deben estar marcadas usando el paquete groff an.tmac descrito en man(7). Esta elección se debe principalmente a la consistencia: la gran mayoría de las páginas del manual de Linux existentes están marcadas usando estas macros.

Convenciones para la disposición de archivos fuente

Por favor, limite la longitud de las líneas del código fuente a no más de unos 75 caracteres siempre que sea posible. Esto ayuda a evitar el salto de línea en algunos clientes de correo cuando se envían parches en línea.

Línea de título

El primer comando en una página del manual debe ser un comando TH:

.TH título sección fecha fuente sección-manual

Los argumentos del comando son los siguientes:

título
El título de la página del manual.
sección
El número de sección en el que debe colocarse la página del manual (p. ej., 7).
fecha
La fecha del último cambio no trivial que se realizó en la página del manual. (Dentro del proyecto man-pages, las actualizaciones necesarias de estas marcas de tiempo se manejan automáticamente mediante scripts, por lo que no es necesario actualizarlas manualmente como parte de un parche). Las fechas deben escribirse en formato YYYY-MM-DD.
fuente
El nombre y la versión del proyecto que proporciona la página del manual (no necesariamente el paquete que proporciona la funcionalidad).
sección-manual
Normalmente, esto debe estar vacío, ya que el valor predeterminado será adecuado.

Donde un encabezado tradicional sea aplicable, por favor úsalo; este tipo de consistencia puede hacer que la información sea más fácil de entender. Si es absolutamente necesario, puedes crear tus propios encabezados si facilitan la comprensión (esto puede ser especialmente útil para páginas en las Secciones 4 y 5). Sin embargo, antes de hacerlo, considera si podrías usar los encabezados tradicionales, con algunas subsecciones (.SS) dentro de esas secciones.

La siguiente lista detalla el contenido de cada una de las secciones anteriores.

NOMBRE
El nombre de esta página del manual.
Consulta man(7) para obtener detalles importantes de las líneas que deben seguir al comando .SH NAME. Todas las palabras de esta línea (incluida la palabra inmediatamente después del "\-") deben estar en minúsculas, excepto donde la convención terminológica inglesa o técnica lo exija.
BIBLIOTECA
La biblioteca que proporciona un símbolo.
Muestra el nombre común de la biblioteca y, entre paréntesis, el nombre del archivo de la biblioteca y, si es necesario, el indicador del enlazador necesario para enlazar un programa contra ella: (libfoo[, -lfoo]).
SINOPSIS
Un breve resumen de la interfaz del comando o función.
Para comandos, muestra la sintaxis del comando y sus argumentos (incluidas las opciones); el texto en negrita se utiliza para el texto tal cual y las cursivas se utilizan para indicar argumentos reemplazables. Los corchetes ([]) rodean los argumentos opcionales, las barras verticales (|) separan las opciones y las elipses (...) pueden repetirse. Para las funciones, muestra las declaraciones de datos requeridas o las directivas #include, seguidas de la declaración de la función.
Cuando se debe definir una macro de prueba de características para obtener la declaración de una función (o variable) de un archivo de encabezado, la SINOPSIS debe indicarlo, como se describe en feature_test_macros(7).
CONFIGURACIÓN
Detalles de configuración para un dispositivo.
Esta sección normalmente aparece solo en páginas de la Sección 4.
DESCRIPCIÓN
Una explicación de lo que hace el programa, función
, o el formato lo hace.
Discute cómo interactúa con archivos y la entrada estándar, y qué produce en la salida estándar o el error estándar. Omite detalles internos y de implementación a menos que sean críticos para entender la interfaz. Describe el caso usual; para información sobre opciones de línea de comandos de un programa, usa la sección OPCIONES.
Al describir un nuevo comportamiento o nuevas banderas para una llamada al sistema o función de biblioteca, ten cuidado de anotar la versión del kernel o de la biblioteca C que introdujo el cambio. El método preferido para anotar esta información para banderas es como parte de una lista .TP, en la siguiente forma (aquí, para una nueva bandera de llamada al sistema):
XYZ_FLAG (desde Linux 3.7)
Descripción de la bandera...
Incluir información de versión es especialmente útil para usuarios que están restringidos a usar versiones más antiguas del kernel o de la biblioteca C (lo cual es típico en sistemas embebidos, por ejemplo).
OPCIONES
Una descripción de las opciones de línea de comandos aceptadas por un programa y cómo cambian su comportamiento.
Esta sección solo debe aparecer para las páginas del manual de las secciones 1 y 8.
ESTADO DE SALIDA
Una lista de los posibles valores de estado de salida de un programa y las condiciones que causan que estos valores sean devueltos.
Esta sección solo debe aparecer para las páginas del manual de las secciones 1 y 8.
VALOR DE RETORNO
Para las páginas de las secciones 2 y 3, esta sección proporciona una lista de los valores que la rutina de biblioteca devolverá al llamador y las condiciones que causan que estos valores sean devueltos.
ERRORES
Para las páginas del manual de las secciones 2 y 3, esta es una lista de los valores que pueden ser colocados en errno en caso de error, junto con información sobre la causa de los errores.
Donde varias condiciones diferentes producen el mismo error, el enfoque preferido es crear entradas de lista separadas (con nombres de error duplicados) para cada una de las condiciones. Esto aclara las condiciones separadas, puede hacer la lista más fácil de leer y permite que la metainformación (por ejemplo, el número de versión del kernel donde la condición se volvió aplicable por primera vez) se marque más fácilmente para cada condición.
La lista de errores debe estar en orden alfabético.
ENTORNO
Una lista de todas las variables de entorno que afectan al programa o función y cómo lo afectan.
ARCHIVOS
Una lista de los archivos que el programa o función utiliza, como archivos de configuración, archivos de inicio y archivos sobre los que el programa opera directamente.
Proporciona la ruta completa de estos archivos, y utiliza el proceso de instalación para modificar la parte del directorio y que coincida con las preferencias del usuario. Para muchos programas, la ubicación de instalación predeterminada está en /usr/local, por lo que tu página de manual base debe usar /usr/local como base.
ATRIBUTOS
Un resumen de varios atributos de la(s) función(es) documentada(s) en esta página. Ver attributes(7) para más detalles.
VERSIONES
Un resumen de los sistemas donde la API se comporta de manera diferente, o donde existe una API similar.
ESTANDARES
Una descripción de cualquier estándar o convención que se relacione con la función o comando descrito por la página del manual.
Los términos preferidos para usar en los diversos estándares se enumeran como encabezados en standards(7).
Esta sección debe indicar los estándares actuales a los que se ajusta la API.
Si la API no está regida por ningún estándar pero comúnmente existe en otros sistemas, anótalo. Si la llamada es específica de Linux o de GNU, anótalo. Si está disponible en los BSD, anótalo.
Si esta sección consiste únicamente en una lista de estándares (lo cual es común), finaliza la lista con un punto ('.').
HISTORIA
Un breve resumen de las versiones del kernel de Linux o glibc donde apareció una llamada al sistema o función de biblioteca, o cambió significativamente en su operación.
Como regla general, cada nueva interfaz debe incluir una sección HISTORY en su página de manual. Desafortunadamente, muchas páginas de manual existentes no incluyen esta información (ya que no había una política para hacerlo cuando fueron escritas). Los parches para remediar esto son bienvenidos, pero, desde la perspectiva de los programadores que escriben código nuevo, esta información probablemente solo es relevante en el caso de interfaces del kernel que se han agregado en Linux 2.4 o posterior (es decir, cambios desde Linux 2.2), y funciones de biblioteca que se han agregado a glibc desde glibc 2.1 (es decir, cambios desde glibc 2.0).
La página del manual syscalls(2) también proporciona información sobre las versiones del kernel en las que aparecieron varias llamadas al sistema.

Las versiones antiguas de los estándares deben mencionarse aquí, en lugar de en ESTANDARES, por ejemplo, SUS, SUSv2 y XPG, o los estándares de implementación SVr4 y 4.xBSD.

NOTAS
Notas misceláneas.
Para las páginas del manual de las secciones 2 y 3, puede ser útil incluir subsecciones (SS) llamadas Notas de Linux y Notas de glibc.
En la sección 2, use el encabezado Diferencias entre la biblioteca C/kernel para separar notas que describan las diferencias (si las hay) entre la función de envoltura de la biblioteca C para una llamada al sistema y la interfaz de llamada al sistema bruta proporcionada por el kernel.
ADVERTENCIAS
Advertencias sobre el mal uso típico de una API por parte del usuario, que no constituyen un error de la API o un defecto de diseño.
ERRORES
Una lista de limitaciones, defectos conocidos o inconvenientes, y otras actividades cuestionables.
EJEMPLOS
Uno o más ejemplos que demuestran cómo se usa esta función, archivo o comando.
Para obtener detalles sobre cómo escribir programas de ejemplo, consulte Programas de ejemplo más abajo.
AUTORES
Una lista de autores de la documentación o del programa.
Se desaconseja encarecidamente el uso de una sección AUTHORS. Generalmente, es mejor no abarrotar cada página con una lista de autores (potencialmente numerosos con el tiempo); si escribes o modificas significativamente una página, añade un aviso de copyright como comentario en el archivo fuente. Si eres el autor de un controlador de dispositivo y quieres incluir una dirección para reportar errores, colócala en la sección BUGS.
REPORTE DE ERRORES
El proyecto man-pages no utiliza una sección REPORTING BUGS en las páginas del manual. La información sobre cómo reportar errores se proporciona en la sección COLOPHON generada por el script. Sin embargo, varios proyectos sí utilizan una sección REPORTING BUGS. Se recomienda colocarla cerca del pie de la página.
COPYRIGHT
El proyecto man-pages no utiliza una sección COPYRIGHT en las páginas del manual. La información de copyright se mantiene en el código fuente de la página. En las páginas donde esta sección está presente, se recomienda colocarla cerca del pie de la página, justo encima de SEE ALSO.
VER TAMBIÉN
Una lista separada por comas de páginas de manual relacionadas, posiblemente seguida de otras páginas o documentos relacionados.
La lista debe ordenarse por número de sección y luego alfabéticamente por nombre. No termines esta lista con un punto.
Donde la lista SEE ALSO contiene muchos nombres largos de páginas de manual, para mejorar el resultado visual de la salida, puede ser útil emplear las directivas .ad l (no justificar a la derecha) y .nh (no hiphenar). La hiphenación de nombres de páginas individuales puede evitarse precediendo las palabras con la cadena "%".
Dada la naturaleza distribuida y autónoma de los proyectos FOSS y su documentación, a veces es necesario —y en muchos casos deseable— que la sección SEE ALSO incluya referencias a páginas de manual proporcionadas por otros proyectos.

CONVENCIONES DE FORMATO Y REDACCIÓN

Las siguientes subsecciones anotan algunos detalles para las convenciones preferidas de formato y redacción en varias secciones de las páginas del proyecto man-pages.

SINOPSIS

Envuelve el(los) prototipo(s) de función en un par .nf/.fi para prevenir el relleno.

Las declaraciones adelantadas de parámetros en funciones no deben usar negrita ni cursiva; esto ayuda a distinguirlas visualmente de los parámetros reales. Por ejemplo:


int snprintf(size_t size;
             char str[restrict size], size_t size,
             const char *restrict format, ...);

En general, donde se muestra más de un prototipo de función en la SINOPSIS, los prototipos no deben separarse con líneas en blanco. Sin embargo, se pueden añadir líneas en blanco (logradas usando .P) en los siguientes casos:

•
para separar largas listas de prototipos de función en grupos relacionados (ver por ejemplo list(3));
•
en otros casos que puedan mejorar la legibilidad.

En la SINOPSIS, un prototipo de función largo puede necesitar continuar en la siguiente línea. La línea de continuación se indenta de acuerdo con las siguientes reglas:

(1)
Si hay un solo prototipo de este tipo que necesita continuación, alinee la línea de continuación de manera que, cuando la página se represente en una fuente de ancho fijo (por ejemplo, en un xterm), la línea de continuación comience justo debajo del inicio de la lista de argumentos en la línea anterior. (Excepción: la sangría puede ajustarse si es necesario para evitar una línea de continuación muy larga o una continuación adicional donde el prototipo de la función es muy largo). Por ejemplo:

int tcsetattr(int fd, int optional_actions,
              const struct termios *termios_p);

(2)
Pero, cuando múltiples funciones en el RESUMEN requieren líneas de continuación y los nombres de las funciones tienen diferentes longitudes, alinee todas las líneas de continuación para que comiencen en la misma columna. Esto proporciona una mejor representación en la salida PDF (ya que el RESUMEN utiliza una fuente de ancho variable donde los espacios se representan más estrechos que la mayoría de los caracteres). Por ejemplo:

int getopt(int argc, char * const argv[],
           const char *optstring);
int getopt_long(int argc, char * const argv[],
           const char *optstring,
           const struct option *longopts, int *longindex);

VALOR DE RETORNO

La redacción preferida para describir cómo se establece errno es "errno se establece para indicar el error" o similar. Esta redacción es consistente con la utilizada tanto en POSIX.1 como en FreeBSD.

ATRIBUTOS

Tenga en cuenta lo siguiente:

•
Envuelva la tabla en esta sección en un par .ad l/.ad para deshabilitar el relleno de texto y un par .nh/.hy para deshabilitar la guionización.
•
Asegúrese de que la tabla ocupe el ancho completo de la página mediante el uso de una descripción lbx para una de las columnas (generalmente la primera columna, aunque en algunos casos la última si contiene mucho texto).
•
Utilice libremente pares de macros T{/T} para permitir que las celdas de la tabla se dividan en varias líneas (teniendo también en cuenta que las páginas a veces pueden renderizarse a un ancho de menos de 80 columnas).

Para ver ejemplos de todo lo anterior, consulte el código fuente de varias páginas.

GUIA DE ESTILO

Las siguientes subsecciones describen el estilo preferido para el proyecto man-pages. Para obtener detalles no cubiertos a continuación, el Chicago Manual of Style suele ser una buena fuente; intente también buscar el uso preexistente en el árbol de fuentes del proyecto.

UNIX for Beginners [2ª ed., Brian W. Kernighan] también contiene una sección notable, "Hints for Preparing Documents".

Uso de lenguaje neutro en cuanto al género

En la medida de lo posible, utilice un lenguaje neutro en cuanto al género en el texto de las páginas man. El uso de "they" ("them", "themself", "their") como pronombre singular neutro en cuanto al género es aceptable.

Convenciones de formato para páginas manual que describen comandos

Para las páginas manual que describen un comando (típicamente en las Secciones 1 y 8), los argumentos siempre se especifican en cursiva, incluso en la sección RESUMEN.

El nombre del comando y sus opciones, siempre deben formatearse en negrita.

Convenciones de formato para páginas manual que describen funciones

Para las páginas manual que describen funciones (típicamente en las Secciones 2 y 3), los argumentos siempre se especifican en cursiva, incluso en la sección RESUMEN, donde el resto de la función se especifica en negrita:

int myfunction(int argc, char **argv);

Los nombres de las variables, al igual que los nombres de los argumentos, deben especificarse en cursiva.

Cualquier referencia al sujeto de la página manual actual debe escribirse con el nombre en negrita seguido de un par de paréntesis en fuente romana (normal). Por ejemplo, en la página man de fcntl(2), las referencias al sujeto de la página se escribirían como: fcntl(). La forma preferida de escribir esto en el archivo fuente es:

    .BR fcntl ()

(Usar este formato, en lugar de "\fB...\fP()", facilita la escritura de herramientas que analizan archivos fuente de páginas man.)

Uso de saltos de línea semánticos

En el código fuente de una página manual, las nuevas frases deben comenzarse en nuevas líneas, las frases largas deben dividirse en líneas en los límites de las cláusulas (comas, punto y coma, dos puntos, etc.), y las cláusulas largas deben dividirse en los límites de las frases. Esta convención, a veces conocida como "saltos de línea semánticos", facilita ver el efecto de los parches, que a menudo operan a nivel de frases, cláusulas o frases individuales.

Listas

Hay diferentes tipos de listas:

Párrafos etiquetados
Estos se utilizan para una lista de etiquetas y sus descripciones. Cuando las etiquetas son constantes (macros o números) están en negrita. Use la macro .TP.
Un ejemplo es esta subsección de "Párrafos etiquetados".
Listas ordenadas
Los elementos van precedidos por un número entre paréntesis (1), (2). Estos representan un conjunto de pasos que tienen un orden.
Cuando hay subpasos, se numerarán como (4.2).
Listas posicionales
Los elementos van precedidos por un número (índice) entre corchetes [4], [5]. Estos representan campos en un conjunto. El primer índice será:
0
Cuando representa campos de una estructura de datos C, para ser consistente con los arrays.
1
Cuando representa campos de un archivo, para ser consistente con herramientas como cut(1).
Lista de alternativas
Los elementos van precedidos por una letra entre paréntesis (a), (b). Estos representan un conjunto de alternativas (normalmente) exclusivas.
Listas de viñetas
Los elementos van precedidos por símbolos de viñeta (\[bu]). Cualquier cosa que no encaje en otro lugar suele cubrirse con este tipo de lista.
Notas numeradas
En realidad no es una lista, pero la sintaxis es idéntica a las "listas posicionales".

Siempre debe haber exactamente 2 espacios entre el símbolo de la lista y los elementos. Esto no se aplica a los "párrafos etiquetados", que usan las reglas de sangría predeterminadas.

Convenciones de formato (general)

Los párrafos deben separarse mediante marcadores adecuados (generalmente .P o .IP). No separe los párrafos con líneas en blanco, ya que esto da como resultado una mala representación en algunos formatos de salida (como PostScript y PDF).

Los nombres de archivo (ya sean rutas o referencias a archivos de encabezado) siempre están en cursiva (por ejemplo, <stdio.h>), excepto en la sección RESUMEN, donde los archivos incluidos están en negrita (por ejemplo, #include <stdio.h>). Al hacer referencia a una inclusión de archivo de encabezado estándar, especifique el archivo de encabezado rodeado por corchetes angulares, de la forma C habitual (por ejemplo, <stdio.h>).

Las macros especiales, que suelen estar en mayúsculas, están en negrita (por ejemplo, MAXINT). Excepción: no ponga NULL en negrita.

Al enumerar una lista de códigos de error, los códigos están en negrita (esta lista suele utilizar la macro .TP).

Los comandos completos, si son largos, deben escribirse como una línea con sangría propia, con una línea en blanco antes y después del comando, por ejemplo


man 7 man-pages

Si el comando es corto, puede incluirse en línea en el texto, en formato cursiva, por ejemplo, man 7 man-pages. En este caso, puede valer la pena usar espacios de no separación (\~) en lugares adecuados del comando. Las opciones del comando deben escribirse en cursiva (por ejemplo, -l).

Las expresiones, si no se escriben en una línea con sangría separada, deben especificarse en cursiva. De nuevo, el uso de espacios de no separación puede ser apropiado si la expresión está en línea con texto normal.

Al mostrar sesiones de shell de ejemplo, la entrada del usuario debe formatearse en negrita, por ejemplo


$ date;
Thu Jul  7 13:01:27 CEST 2016

Cualquier referencia a otra página man debe escribirse con el nombre en negrita, siempre seguido del número de sección, formateado en fuente romana (normal), sin espacios separadores (por ejemplo, intro(2)). La forma preferida de escribir esto en el archivo fuente es:

    .BR intro (2)

(Incluir el número de sección en las referencias cruzadas permite que herramientas como man2html(1) creen páginas correctamente hipervinculadas.)

Los caracteres de control deben escribirse en negrita, sin comillas; por ejemplo, ^X.

Ortografía

A partir de la versión 2.59, man-pages sigue las convenciones de ortografía estadounidense (anteriormente, había una mezcla aleatoria de ortografía británica y estadounidense); por favor, escriba todas las páginas nuevas y los parches de acuerdo con estas convenciones.

Además de las diferencias de ortografía bien conocidas, hay algunas sutilezas adicionales a tener en cuenta:


022;
El inglés americano tiende a usar las formas "backward", "upward", "toward", etc., en lugar de las formas británicas "backwards", "upwards", "towards", etc.
•
Las opiniones están divididas sobre "acknowledgement" vs "acknowledgment". El último es el uso predominante, pero no universal, en el inglés americano. POSIX y la licencia BSD usan la primera ortografía. En el proyecto de páginas man de Linux, usamos "acknowledgement".

Números de versión BSD

El esquema clásico para escribir números de versión BSD es x.yBSD, donde x.y es el número de versión (por ejemplo, 4.2BSD). Evita formas como BSD 4.3.

Uso de mayúsculas

En los encabezados de las subsecciones ("SS"), usa mayúscula en la primera palabra del encabezado, pero por lo demás usa minúsculas, excepto donde el uso del inglés (por ejemplo, nombres propios) o los requisitos del lenguaje de programación (por ejemplo, nombres de identificadores) dicten lo contrario. Por ejemplo:


.SS Unicode en Linux

NULL, NUL, puntero nulo y byte nulo

Un puntero nulo es un puntero que no apunta a nada, y normalmente se indica mediante la constante NULL. Por otro lado, NUL es el byte nulo, un byte con valor 0, representado en C a través de la constante de carácter '\0'.

El término preferido para el puntero es "puntero nulo" o simplemente "NULL"; evite escribir "NULL pointer".

El término preferido para el byte es "byte nulo". Evite escribir "NUL", ya que se confunde fácilmente con "NULL". Evite también los términos "byte cero" y "carácter nulo". El byte que termina una cadena C debe describirse como "el byte nulo terminador"; las cadenas pueden describirse como "terminadas en nulo", pero evite el uso de "NUL-terminated".

Enlaces

Para los hipervínculos, use el par de macros .UR/.UE (ver groff_man(7)). Esto produce hipervínculos adecuados que se pueden usar en un navegador web, al renderizar una página con, por ejemplo:


BROWSER=firefox man -H pagename

Uso de e.g., i.e., etc., a.k.a., y similares

En general, se debe evitar el uso de abreviaturas como "e.g.", "i.e.", "etc.", "cf.", y "a.k.a.", en favor de formulaciones completas adecuadas ("por ejemplo", "es decir", "y así sucesivamente", "comparar con", "también conocido como").

El único lugar donde tales abreviaturas pueden ser aceptables es en cortas acotaciones parentéticas (por ejemplo, como esta).

Incluya siempre puntos en tales abreviaturas, como se muestra aquí. Además, "e.g." y "i.e." siempre deben ir seguidos de una coma.

Generación de glifos óptimos

Donde se requiera un carácter de signo menos real (por ejemplo, para números como -1, para referencias cruzadas de páginas man como utf-8(7), o al escribir opciones que tienen un guion inicial, como en ls -l), use la siguiente forma en el código fuente de la página man:


\-

Esta directriz se aplica también a los ejemplos de código.

El uso de signos menos reales sirve a los siguientes propósitos:

•
Para proporcionar mejores representaciones en varios destinos que no sean terminales ASCII, especialmente en PDF y en terminales capaces de Unicode/UTF-8.
•
Para generar glifos que, al copiarse de las páginas representadas, produzcan signos menos reales al pegarse en un terminal.

Para producir comillas simples no inclinadas que se representen bien en ASCII, UTF-8 y PDF, use "&amp;\[aq]&amp;" ("comilla de apóstrofo"); por ejemplo


\[aq]C\[aq]

donde C es el carácter entre comillas. Esta directriz se aplica también a las constantes de caracteres utilizadas en los ejemplos de código.

Donde se requiera un carácter circunflejo (^) adecuado que se represente bien tanto en un terminal como en PDF, use "&amp;\[ha]&amp;". Esto es especialmente necesario en muestras de código, para obtener un circunflejo bien representado al renderizar a PDF.

El uso de un carácter "~" solo da como resultado una representación deficiente en PDF. En su lugar, use "&amp;\[ti]&amp;". Esto es especialmente necesario en muestras de código, para obtener una tilde bien representada al renderizar a PDF.

Programas de ejemplo y sesiones de shell

Las páginas manuales pueden incluir programas de ejemplo que demuestran cómo usar una llamada al sistema o una función de biblioteca. Sin embargo, tenga en cuenta lo siguiente:

•
Los programas de ejemplo deben estar escritos en C.
•
Un programa de ejemplo es necesario y útil solo si demuestra algo más allá de lo que se puede proporcionar fácilmente en una descripción textual de la interfaz. Un programa de ejemplo que no hace nada más que llamar a una interfaz generalmente sirve de poco propósito.
•
Los programas de ejemplo deben ser idealmente cortos (por ejemplo, un buen ejemplo a menudo se puede proporcionar en menos de 100 líneas de código), aunque en algunos casos pueden ser necesarios programas más largos para ilustrar adecuadamente el uso de una API.
•
Se agradece el código expresivo.
•
Se deben incluir comentarios cuando sean útiles. Las oraciones completas en comentarios independientes deben terminar con un punto. Los puntos generalmente deben omitirse en comentarios de "etiqueta" (es decir, comentarios que se colocan en la misma línea de código); dichos comentarios son en cualquier caso típicamente frases breves en lugar de oraciones completas.
•
Los programas de ejemplo deben realizar comprobaciones de errores después de las llamadas al sistema y las llamadas a funciones de biblioteca.
•
Los programas de ejemplo deben ser completos y compilar sin advertencias cuando se compilan con cc -Wall.
•
Siempre que sea posible y apropiado, los programas de ejemplo deben permitir la experimentación, variando su comportamiento según las entradas (idealmente desde argumentos de línea de comandos, o alternativamente, mediante entrada leída por el programa).
•
Los programas de ejemplo deben presentarse de acuerdo con el estilo de Kernighan y Ritchie, con sangría de 4 espacios. (¡Evite el uso de caracteres TAB en el código fuente!) El siguiente comando se puede utilizar para formatear su código fuente a algo parecido al estilo preferido:

indent -npro -kr -i4 -ts4 -sob -l72 -ss -nut -psl prog.c

•
Para mantener la coherencia, todos los programas de ejemplo deben terminar utilizando una de las siguientes opciones:

exit(EXIT_SUCCESS);
exit(EXIT_FAILURE);

Evite usar las siguientes formas para terminar un programa:

exit(0);
exit(1);
return n;

•
Si hay un texto explicativo extenso antes del código fuente del programa, marque el código fuente con un encabezado de subsección Código fuente del programa, como en:

.SS Código fuente del programa

Haga esto siempre si el texto explicativo incluye un registro de sesión de shell.

Si incluye un registro de sesión de shell que demuestra el uso de un programa u otra característica del sistema:

•
Coloque el registro de la sesión antes de la lista del código fuente.
•
Sangre el registro de la sesión con cuatro espacios.
•
Ponga en negrita el texto de entrada del usuario, para distinguirlo de la salida producida por el sistema.

Para algunos ejemplos de cómo deben ser los programas de ejemplo, vea wait(2) y pipe(2).
