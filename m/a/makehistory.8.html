MAKEHISTORY(8) Documentación de InterNetNews MAKEHISTORY(8)

NOMBRE

makehistory - Inicializa o reconstruye la base de datos de historial de INN

SINOPSIS

makehistory [-abFIOSx] [-f nombrearchivo] [-l conteo] [-L promedio-carga] [-s tamaño] [-T dirtemp]

DESCRIPCIÓN

makehistory reconstruye el archivo de texto de history(5), que contiene una lista de message-IDs de artículos ya vistos por el servidor. También puede ser usado para reconstruir la base de datos de vistas previas. Nótese que aunque los índices dbz para el archivo history también son reconstruidos por makehistory, es útil ejecutar makedbz(8) después de makehistory(8) para mejorar la eficiencia de los índices (makehistory no sabe qué tamaño de tabla hash usar en la primera ejecución, a menos que el tamaño se proporcione con la opción -s).

La ubicación predeterminada del archivo de texto history es pathdb/history; para especificar una ubicación alternativa, use la opción -f.

Por defecto, makehistory escaneá todo el spool, usando el gestor de almacenamiento, y escribe una línea de historial por cada artículo. Para también generar información de vista previa, use la opción -O.

Si se encuentra un artículo malformado en el spool de noticias, de una manera que impide su integración en los datos de historial o vista previa, se generará una línea de registro y el artículo malformado simplemente será omitido.

RECONSTRUCCIÓN DE VISTA PREVIA

ADVERTENCIA: Si está intentando reconstruir la base de datos de vista previa, asegúrese de detener innd(8) y eliminar o poner a cero la base de datos existente antes de comenzar para obtener los mejores resultados. La reconstrucción de vista previa no debe hacerse mientras el servidor está en ejecución. A menos que se elimine la vista previa existente, podría terminar con problemas como entradas de vista previa desordenadas, búferes de vista previa excesivamente grandes y similares.

Si ovmethod en inn.conf es "ovdb", debe tener los procesos ovdb en ejecución mientras reconstruye la vista previa. ovdb los necesita disponibles mientras escribe las entradas de vista previa. Puede iniciarlos manualmente aparte del resto del servidor ejecutando ovdb_init; consulte ovdb_init(8) para más detalles.

De manera similar, si ovmethod en inn.conf es "ovsqlite", debe tener el proceso ovsqlite-server en ejecución mientras reconstruye la vista previa. Consulte ovsqlite-server(8) para más detalles y cómo iniciarlo manualmente.

Reconstruir los datos de vista previa es tan simple como:

1.
Verificar que el archivo de configuración del nuevo método de almacenamiento de vista previa esté presente en pathetc y se ajuste a sus necesidades (buffindexed.conf, ovdb.conf o ovsqlite.conf). Tenga en cuenta que el método de almacenamiento de vista previa tradindexed no tiene un archivo de configuración dedicado.
2.
Asegurarse de que INN esté detenido ("rc.news stop" como usuario de noticias, o el comando que esté usando).
3.
Establecer el nuevo método de almacenamiento de vista previa en el parámetro ovmethod en inn.conf.
4.
Asegurarse de que el directorio especificado por el parámetro pathoverview en inn.conf exista y esté vacío (o contenga búferes buffindexed recién creados, si usa ese método de almacenamiento de vista previa). De lo contrario, renombre el directorio actual (para respaldar los datos de vista previa existentes) y recree pathoverview como el usuario de noticias.
5.
Iniciar ovdb_init o ovsqlite-server como usuario de noticias si el nuevo método de almacenamiento de vista previa es respectivamente ovdb u ovsqlite.
6.
Ejecutar "makehistory -O -x -F" y esperar a que el comando termine. (Puede notar algunos registros sobre artículos para los cuales los datos de vista previa no se pueden insertar en el nuevo método de almacenamiento de vista previa. Mientras no sean muchísimos, es normal, notablemente porque hay un límite interno en la longitud de los datos de vista previa generados por makehistory, a diferencia de innd. Desafortunadamente, estos raros artículos no estarán presentes en la nueva vista previa.)
7.
Detener los programas auxiliares ovdb u ovsqlite si los inició durante los pasos anteriores (ejecutar "rc.news stop" como usuario de noticias los detendrá; no se preocupe por los mensajes relacionados con el hecho de que el servidor de noticias no estuviera en ejecución).
8.
Iniciar INN y verificar los registros para asegurarse de que todo esté bien. Normalmente notará que el archivo active se renumeró (rc.news se encarga de eso cuando se ejecuta después de una reconstrucción de vista previa; de lo contrario, ejecute manualmente "ctlinnd renumber ''").

OPCIONES

-a
Añadir al final del archivo history en lugar de generar uno nuevo. Si añade al archivo history principal, asegúrese de que innd(8) esté limitado o no se esté ejecutando, o podría corromper el historial.
-b
Eliminar cualquier mensaje encontrado en el spool que no tenga campos de cabecera Message-ID válidos.
-F
Crear un proceso separado para volcar los datos de vista previa al disco en lugar de hacerlo directamente. La ventaja de esto es que permite a makehistory continuar recolectando más datos del spool mientras el primer lote de datos se escribe en la base de datos de vista previa. La desventaja es que se utilizará hasta el doble de espacio en disco temporal para los datos de vista previa generados. Esta opción solo tiene sentido en combinación con -O. Con buffindexed, se invoca al programa overchan para escribir la vista previa.
-f nombrearchivo
En lugar de escribir directamente en pathdb/history, escribir en nombrearchivo, también en pathdb.
-I
No almacenar datos de vista previa para artículos con números inferiores al número de artículo más bajo en active. Esto es útil si por alguna razón hay artículos antiguos en el disco que no deberían estar disponibles para los lectores o incluidos en la base de datos de vista previa.
-l conteo
Esta opción especifica cuántos artículos procesar antes de escribir la información de vista previa acumulada en la base de datos de vista previa. El valor predeterminado es 10000. Dado que el rendimiento de escritura de vista previa es más rápido con datos ordenados, cada "lote" se ordena. Incrementar el tamaño del lote con esta opción puede mejorar aún más el rendimiento de escritura, a costa de tiempos de ordenación más largos. Además, se necesitará espacio temporal para almacenar los lotes de vista previa. A una estimación aproximada, se requerirán alrededor de 300 * conteo bytes de espacio temporal (sin contar los archivos temporales creados por sort(1)). Consulte la descripción de la opción -T para saber cómo especificar la ubicación del almacenamiento temporal. Esta opción no tiene ningún efecto con buffindexed, ya que buffindexed no necesita vista previa ordenada y no se realiza ninguna agrupación.
-L promedio-carga
Pausar temporalmente las actividades si el promedio de carga del sistema excede el nivel especificado promedio-carga. Esto permite que makehistory se ejecute en un sistema que se utiliza para otros propósitos sin monopolizar los recursos del sistema y, por lo tanto, hacer que el tiempo de respuesta de otras aplicaciones sea inaceptablemente lento. Usar nice(1) no ayuda mucho para eso, ya que el problema proviene del uso de E/S de disco, y ionice(1) no siempre está disponible o es eficiente.
-O
Crear la base de datos de vista previa además del archivo history. La información de vista previa solo es necesaria si el servidor admite lectores; no es necesaria para un servidor solo de tránsito (ver enableoverview en inn.conf(5)). Si está utilizando el método de almacenamiento de vista previa buffindexed, borre todos sus búferes de vista previa antes de ejecutar makehistory con -O.
-S
En lugar de almacenar los datos de vista previa en la base de datos de vista previa, simplemente escríbalos en la salida estándar en un formato adecuado para alimentar a overchan más tarde si se desea. Cuando se utiliza esta opción, -F,
-x
Borrar todos los artículos del spool que no tengan la línea de cabecera de mensaje-ID. Esto es útil para limpiar el spool de artículos malformados antes de ejecutar makehistory(8).

makehistory(8) — Arch manual pages

NAME

makehistory — build or rebuild the history database and overview files

SYNOPSIS

makehistory [-b -f histfile] [-I -l size] [-O [-x] [-T tmpdir]] [-F]

DESCRIPTION

The makehistory utility rebuilds the history database and overview files from the news spool. It scans the news spool, identifies articles that are not in the history database, and adds them, along with their associated overview entries, to the new history database and overview files.

This can be used to build the history database for the first time, to rebuild it after corruption, or to add missing entries due to server failures or manual spool manipulation.

It is strongly recommended to stop the news server (or at least throttle it via the ctlinnd(8) command) before running makehistory.

OVERVIEW REBUILD

The overview database is built from scratch whenever the -O option is used. Any existing overview data will be lost. If you are using the buffindexed overview format, you will need to erase the overview buffers before running makehistory. This is typically done by removing the files matching "overview.*" in <pathdb>.

OPTIONS

-F
This option causes makehistory to do nothing but build the overview database. This is useful when you only want to update the overview database, for example, if you have just added a new newsfeed and want to create overview entries for older articles.
-f histfile
Specifies the name of the history file to be created. If this option is not given, the default name "history" in the directory specified by pathdb in inn.conf(5) will be used.
-b
Builds a new history file from scratch. All existing history entries will be discarded. This option is only useful when the -f option is also specified.
-I

Causes makehistory to build the history database. This is the default behavior if neither -O nor -x is specified.

It is recommended to specify the approximate size of the history database using the -l option when using -I. This will create a more efficient database.

The options -I, -l, and -T are ignored. This option only makes sense in combination with -O.

-l size
Sizes the history database for approximately size key-value pairs (i.e. lines in history). Accurately specifying the size is an optimization that will create a more efficient database. (The size should be the estimated eventual number of articles, typically the size of the old history file, in lines.)

By default, makehistory will create a database optimized for handling about 6,000,000 articles (or 500,000 if the slower tagged hash format is used). This size does not limit the number of articles the news server can store in its history file. It will just get slower when that optimal size is exceeded, until the next run of news.daily which will appropriately resize it.

-T tmpdir
If -O is given, makehistory needs a location to write temporary overview data. By default, it uses pathtmp, set in inn.conf, but if this option is given, the provided tmpdir is used instead. This is also used for temporary files created by sort(1) (which is invoked in the process of writing overview information since sorted overview information writes faster). By default, sort usually uses your system temporary directory; see the sort(1) man page on your system to be sure.
-x
If this option is given, makehistory won't write out history file entries. This is useful mostly for building overview without generating a new history file.

EXAMPLES

Here's a typical example of rebuilding the entire history and overview database, removing broken articles in the news spool. This uses the default temporary file locations and should be done while innd isn't running (or is throttled).

makehistory -b -f history.n -O -l 30000 -I

This will rebuild the overview (if using buffindexed, erase the existing overview buffers before running this command) and leave a new history file as "history.n" in pathdb. To preserve all of the history entries from the old history file that correspond to rejected articles or expired articles, follow the above command with:

cd <pathdb>
awk 'NF == 2 { print }' < history >> history.n

(replacing the path with your pathdb, if it isn't the default). Then look over the new history file for problems and run:

makedbz -s `wc -l < history.n` -f history.n

Then rename all of the files matching "history.n.*" to "history.*", replacing the current history database and indices. After that, it's safe to unthrottle innd.

For a simpler example:

makehistory -b -f history.n -I -O

will scan the spool, removing broken articles and generating history and overview entries for articles missing from history.

To pre-size the history file for 100,000,000 articles, and generate overview data at the same time, you may directly use the following command:

makehistory -O -s 100000000

You then do not need running makedbz as the history file has already been generated and optimized for the expected number of articles.

To just rebuild overview:

makehistory -O -x -F

FILES

pathdb/history
This is the default output file for makehistory.
pathtmp
Where temporary files are written unless -T is given.
