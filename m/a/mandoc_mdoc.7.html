MDOC(7) Manual de Información Miscelánea MDOC(7)

NOMBRE

mdoc — lenguaje de marcado semántico para formatear páginas del manual

DESCRIPCIÓN

El lenguaje mdoc soporta la autoría de páginas del manual para la utilidad man(1) permitiendo anotaciones semánticas de palabras, frases, secciones de página y páginas completas del manual. Dichas anotaciones son utilizadas por las herramientas de formato para lograr una presentación uniforme en todos los manuales escritos en mdoc, y para soportar hipervínculos si son soportados por el medio de salida.

Este documento de referencia describe la estructura de las páginas del manual y la sintaxis y uso del lenguaje mdoc. La implementación de referencia de una herramienta de análisis y formato es mandoc(1); la sección COMPATIBILIDAD describe la compatibilidad con otras implementaciones.

En un documento mdoc, las líneas que comienzan con el carácter de control ‘.’ se llaman “líneas de macro”. La primera palabra es el nombre de la macro. Consiste en dos o tres letras. La mayoría de los nombres de macro comienzan con una letra mayúscula. Para una lista de macros disponibles, consulte RESUMEN DE MACROS. Las palabras que siguen al nombre de la macro son argumentos para la macro, incluyendo opcionalmente los nombres de otras macros invocables; consulte SINTAXIS DE MACROS para más detalles.

Las líneas que no comienzan con el carácter de control se llaman “líneas de texto”. Proporcionan texto de formato libre para ser impreso; el formato del texto depende del contexto de procesamiento respectivo:

.Sh Las líneas de macro cambian el estado de control.
Las líneas de texto se interpretan dentro del estado actual.

Muchos aspectos de la sintaxis básica del lenguaje mdoc se basan en el lenguaje roff(7); consulte las secciones SINTAXIS DEL LENGUAJE y SINTAXIS DE MACROS en el manual de roff(7) para más detalles, en particular sobre comentarios, secuencias de escape, espacios en blanco y comillas. Sin embargo, se desaconseja el uso de peticiones de roff(7) en documentos mdoc; mandoc(1) soporta algunas de ellas meramente por compatibilidad hacia atrás.

ESTRUCTURA DEL MANUAL

Un documento mdoc bien formado consiste en un prólogo de documento seguido de una o más secciones.

El prólogo, que consiste en las macros Dd, Dt y Os en ese orden, es requerido para cada documento.

La primera sección (las secciones se denotan por Sh) debe ser la sección NAME, que consiste en al menos un Nm seguido de Nd.

Después de eso, la convención dicta especificar al menos las secciones SYNOPSIS y DESCRIPTION, aunque esto varía entre las secciones del manual.

Las secciones en un documento mdoc se ordenan convencionalmente como aparecen arriba. Las secciones deben componerse de la siguiente manera:

NOMBRE
El(los) nombre(s) y una descripción de una línea del material documentado. La sintaxis para esto es la siguiente: 
.Nm nombre0 ,
.Nm nombre1 ,
.Nm nombre2
.Nd una descripción de una línea

Múltiples nombres ‘Nm’ deben separarse por comas.

La(s) macro(s) Nm deben preceder a la macro Nd.

Consulte Nm y Nd.

BIBLIOTECA
El nombre de la biblioteca que contiene el material documentado, que se asume que es una función en un manual de sección 2, 3 o 9. La sintaxis para esto es la siguiente: 
.Lb libarm

Consulte Lb.

SINOSIS
Documenta la sintaxis de invocación de la utilidad, la sintaxis de llamada a función o la configuración del dispositivo.

Para lo primero, utilidades (secciones 1, 6 y 8), esto generalmente se estructura de la siguiente manera:

.Nm bar
.Op Fl v
.Op Fl o Ar archivo
.Op Ar
.Nm foo
.Op Fl v
.Op Fl o Ar archivo
.Op Ar

Los comandos deben ordenarse alfabéticamente.

Para lo segundo, llamadas a función (secciones 2, 3, 9):

.In cabecera.h
.Vt extern const char *global;
.Ft "char *"
.Fn foo "const char *src"
.Ft "char *"
.Fn bar "const char *src"

El orden de las macros In, Vt, Fn y Fo debe seguir las convenciones de los archivos de cabecera C.

Y para lo tercero, configuraciones (sección 4):

.Cd "it* en isa? port 0x2e"
.Cd "it* en isa? port 0x4e"

Los manuales que no están en estas secciones generalmente no necesitan una SINOSIS.

Algunas macros se muestran de manera diferente en la sección SINOSIS, particularmente Nm, Cd, Fd, Fn, Fo, In, Vt y Ft. Todas estas macros se imprimen en su propia línea. Si dos macros disímiles de este tipo se invocan por pares (excepto por Ft antes de Fo o Fn), están separadas por un espacio vertical, a menos que sea en el caso de Fo, Fn y Ft, que siempre están separadas por espacio vertical.

Cuando el texto y las macros que siguen a una macro Nm que inicia una línea de entrada abarcan múltiples líneas de salida, todas las líneas de salida excepto la primera se indentarán para alinearse con el texto inmediatamente posterior a la macro Nm, hasta la siguiente macro Nm, Sh o Ss o el final de un bloque envolvente, lo que ocurra primero.

DESCRIPTION

Manual pages are structured as a series of sections, each preceded by a section header. The sections are traditionally named NAME, SYNOPSIS, DESCRIPTION, ENVIRONMENT, FILES, EXIT STATUS, ERRORS, EXAMPLES, DIAGNOSTICS, SECURITY CONSIDERATIONS, AUTHORS, BUGS, HISTORY, SEE ALSO, STANDARDS, and NOTES. The NOTES section is commonly used for IMPLEMENTATION NOTES, AVAILABILITY, and other miscellaneous information.

Some sections are not appropriate for all manual pages. For example, EXIT STATUS is not appropriate for library function manual pages, and FILES is not appropriate for most command manual pages.

The following sections are defined by the mdoc macro package.

NAME
This section must be the first section in the manual page. It contains the name of the command or function, followed by a short, one-line description of its purpose.

See Nm and Nd.

SYNOPSIS
This section describes the command syntax, function prototype, or configuration file syntax. It typically uses a simplified notation to describe arguments, options, and other elements.

See Nm, Fl, Cm, Ar, Op, Oo, and Oc.

DESCRIPTION
This section describes the functionality of the command or function in detail. It explains what the command or function does, its purpose, and how it works. It may also describe configuration files, protocols, or other related concepts.
DEPRECATED
This section can be used to describe features that are no longer recommended for use.
CONTEXT
This section lists the contexts in which functions can be called in section 9. The contexts are autoconf, process, or interrupt.
IMPLEMENTATION NOTES
Implementation-specific notes should be kept here. This is useful when implementing standard functions that may have side effects or notable algorithmic implications.
RETURN VALUES
This section documents the return values of functions in sections 2, 3, and 9.

See Rv.

ENVIRONMENT
Lists the environment variables used by the utility, and explains the syntax and semantics of their values. The environ(7) manual provides examples of typical content and formatting.

See Ev.

FILES
Documents files used. It's helpful to document both the file name and a short description of how the file is used (created, modified, etc.).

See Pa.

EXIT STATUS
This section documents the command exit status for section 1, 6, and 8 utilities. Historically, this information was described in DIAGNOSTICS, a practise that is now discouraged.

See Ex.

EXAMPLES
Example usages. This often contains snippets of well-formed, well-tested invocations. Make sure that examples work properly!
DIAGNOSTICS
Documents error messages. In section 4 and 9 manuals, these are usually messages printed by the kernel to the console and to the kernel log. In section 1, 6, 7, and 8, these are usually messages printed by userland programs to the standard error output.

Historically, this section was used in place of EXIT STATUS for manuals in sections 1, 6, and 8; however, this practise is discouraged.

See Bl -diag.

ERRORS
Documents errno(2) settings in sections 2, 3, 4, and 9.

See Er.

SEE ALSO
References other manuals with related topics. This section should exist for most manuals. Cross-references should conventionally be ordered first by section, then alphabetically (ignoring case).

References to other documentation concerning the topic of the manual page, for example authoritative books or journal articles, may also be provided in this section.

See Rs and Xr.

STANDARDS
References any standards implemented or used. If not adhering to any standards, the HISTORY section should be used instead.

See St.

HISTORY
A brief history of the subject, including where it was first implemented, and when it was ported to or reimplemented for the operating system at hand.
AUTHORS
Credits to the person or persons who wrote the code and/or documentation. Authors should generally be noted by both name and email address.

See An.

CAVEATS
Common misuses and misunderstandings should be explained in this section.
BUGS
Known bugs, limitations, and work-arounds should be described in this section.
SECURITY CONSIDERATIONS
Documents any security precautions that operators should consider.

%I nombre
Nombre de la editorial o emisor de un bloque Rs.
%J nombre
Nombre de la revista de un bloque Rs.
%N número
Número de edición (generalmente para revistas) de un bloque Rs.
%O línea
Información opcional de un bloque Rs.
%P número
Número de página de libro o revista de un bloque Rs. Convencionalmente, el argumento comienza con ‘p.’ para una sola página o ‘pp.’ para un rango de páginas, por ejemplo:

Autor institucional (escuela, gobierno, etc.) de un bloque Rs. Se debe asignar una línea %Q separada a cada autor institucional.
%R nombre

%T título
Título del artículo de un bloque Rs. Esta macro también puede usarse en un contexto no bibliográfico al referirse a títulos de artículos.

%V número

Ac

Dt TÍTULO sección [arch]
Título del documento para mostrar en la cabecera de la página. Este es el segundo macro obligatorio de cualquier archivo mdoc.

Sus argumentos son los siguientes:

TÍTULO
El título (nombre) del documento, por defecto “SIN TÍTULO” si no se especifica. Para lograr una apariencia uniforme de las líneas de cabecera de página, por convención debe estar en mayúsculas.
sección
La sección del manual. Puede ser una de 1 (Comandos Generales), 2 (Llamadas del Sistema), 3 (Funciones de Librería), 3p (Librería Perl), 4 (Controladores de Dispositivos), 5 (Formatos de Archivo), 6 (Juegos), 7 (Información Miscelánea), 8 (Manual del Administrador del Sistema), o 9 (Manual del Desarrollador del Kernel). Debe corresponder al sufijo del nombre de archivo del manual y por defecto es una cadena vacía si no se especifica.
arch
Esto especifica la arquitectura de máquina a la que se aplica una página de manual, cuando sea relevante, por ejemplo alpha, amd64, i386 o sparc64. La lista de arquitecturas válidas varía según el sistema operativo.

Ejemplos:

.Dt FOO 1
.Dt FOO 9 i386

It [encabezado]
Un elemento de lista. La sintaxis de esta macro depende del tipo de lista.

Las listas de tipo -hang, -ohang, -inset, y -diag tienen la siguiente sintaxis:

.It args

Las listas de tipo -bullet, -dash, -enum, -hyphen y -item tienen la siguiente sintaxis:

.It

con las líneas subsiguientes interpretadas dentro del alcance de It hasta que se encuentre un El de cierre o otro It.

La lista -tag tiene la siguiente sintaxis:

.It [args]

Las líneas subsiguientes se interpretan como con -bullet y familia. Los argumentos de línea corresponden al lado izquierdo de la lista; los argumentos del cuerpo corresponden al contenido de la lista.

La lista -column es la más complicada. Su sintaxis es la siguiente:

.It celda [Ta celda ...]
.It celda [<TAB> celda ...]

Los argumentos consisten en una o más líneas de texto y macros que representan una línea de tabla completa. Las celdas dentro de la línea están delimitadas por la macro de bloque especial Ta o por caracteres de tabulación literales.

Se desaconseja encarecidamente el uso de tabulaciones literales porque son muy difíciles de usar correctamente y el código mdoc que las utiliza es muy difícil de leer. En particular, un carácter en blanco es sintácticamente significativo antes y después del carácter de tabulación literal. Si una palabra precede o sigue a la tabulación sin un espacio intermedio, esa palabra nunca se interpreta como una llamada a macro, sino que siempre se imprime literalmente.

El delimitador de celda de tabulación solo puede usarse dentro de la línea It; en las líneas siguientes, solo la macro Ta puede usarse para delimitar celdas, y la portabilidad requiere que Ta sea llamada por otras macros: algunos analizadores no la reconocen cuando aparece como la primera macro en una línea.

Tenga en cuenta que las cadenas entre comillas pueden abarcar celdas delimitadas por tabulaciones en una línea It. Por ejemplo,

.It "col1 , <TAB> col2 ," ;

preservará el espacio en blanco antes de ambas comas, pero no el espacio en blanco antes del punto y coma.

SINTAXIS DE MACROS

La sintaxis de una macro depende de su clasificación. En esta sección, '-arg' se refiere a los argumentos de la macro, que pueden ir seguidos de cero o más parámetros 'parm'; 'Yo' abre el ámbito de una macro; y si se especifica, 'Yc' lo cierra.

La columna Llamable indica que la macro también puede ser llamada pasando su nombre como argumento a otra macro. Por ejemplo, '.Op Fl O Ar file' produce '[-O archivo]'. Para evitar una llamada a macro y renderizar el nombre de la macro literalmente, escápala anteponiendo un espacio de ancho cero, '\&'. Por ejemplo, '.Op \&Fl O' produce '[Fl O]'. Si una macro no es llamable pero su nombre aparece como argumento de otra macro, se interpreta como texto opaco. Por ejemplo, '.Fl Sh' produce '-Sh'.

La columna Analizada indica si la macro puede llamar a otras macros recibiendo sus nombres como argumentos. Si una macro no se analiza pero el nombre de otra macro aparece como argumento, se interpreta como texto opaco.

La columna Ámbito, si es aplicable, describe las reglas de cierre.

Delimitadores

Cuando un argumento de macro consiste en un solo carácter de entrada considerado como delimitador, el argumento recibe un tratamiento especial. Esto no se aplica cuando los delimitadores aparecen en argumentos que contienen más de un carácter. MACRO SYNTAX

A macro call consists of a two-character macro name, followed by arguments. Arguments are separated by spaces. Macros are terminated by a newline, unless the newline is escaped with a backslash character ('‘\\’').

Macro arguments are generally scanned for nested macro calls, text decorations, and other inline markup. Some macros consume arguments and do not process them further. For example, the It macro consumes its arguments and prints them literally, with special characters escaped.

Many macros require specific argument counts. If too few arguments are supplied, they might use default values or fail gracefully. If too many arguments are supplied, they might be ignored or cause errors. The documentation for each macro specifies the expected arguments.

Special characters such as periods ('.'), colons (':'), and commas (',') are often used as delimiters for arguments or to mark the end of macro arguments. For example, the period is used to terminate macro names when they are not followed by whitespace, such as in ItLi, which is equivalent to It followed by line. A period preceded by a backslash ('‘\\’') gets this special handling; use '‘\\&.’' to prevent that.

Many in-line macros interrupt their scope when they encounter delimiters, and resume their scope when more arguments follow that are not delimiters. For example,

.Fl a ( b | c \*(Ba d ) e

renders as:

-a (-b | -c | -d) -e

This applies to both opening and closing delimiters, and also to the middle delimiter, which does not suppress spacing:

|
vertical bar

As a special case, the predefined string \*(Ba is handled and rendered in the same way as a plain '‘|’' character. Using this predefined string is not recommended in new manuals.

Appending a zero-width space ('‘\\&’') to the end of an input line is also useful to prevent the interpretation of a trailing period, exclamation or question mark as the end of a sentence, for example when an abbreviation happens to occur at the end of a text or macro input line.

Font handling

In mdoc documents, usage of semantic markup is recommended in order to have proper fonts automatically selected; only when no fitting semantic markup is available, consider falling back to Physical markup macros. Whenever any mdoc macro switches the roff(7) font mode, it will automatically restore the previous font when exiting its scope. Manually switching the font using the roff(7) '‘\f' font escape sequences is never required.

COMPATIBILITY

This section provides an incomplete list of compatibility issues between mandoc and GNU troff ("groff").

The following problematic behaviour is found in groff:

  • Pa does not format its arguments when used in the FILES section under certain list types.
  • Ta can only be called by other macros, but not at the beginning of a line.
  • '‘\f' (font face) and '‘\F' (font family face) Text Decoration escapes behave irregularly when specified within line-macro scopes.
  • Negative scaling units return to prior lines. Instead, mandoc truncates them to zero.

The following features are unimplemented in mandoc:

  • Bd -file file is unsupported for security reasons.
  • Bd -filled does not adjust the right margin, but is an alias for Bd -ragged.
  • Bd -literal does not use a literal font, but is an alias for Bd -unfilled.
  • Bd -offset center and -offset right don't work. Groff does not implement centered and flush-right rendering either, but produces large indentations.
