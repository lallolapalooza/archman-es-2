MAILX(1P) Manual de Programador POSIX MAILX(1P)

PROLOGO

Esta página del manual forma parte del Manual de Programador POSIX. La implementación de esta interfaz en Linux puede diferir (consulte la página del manual de Linux correspondiente para conocer los detalles del comportamiento de Linux), o la interfaz puede no estar implementada en Linux.

NOMBRE

mailx — procesar mensajes

SINOPSIS

Modo de Envío

mailx [-s asunto] dirección...

Modo de Recepción

mailx -e
mailx [-HiNn] [-F] [-u usuario]
mailx -f [-HiNn] [-F] [archivo]

DESCRIPCIÓN

La utilidad mailx proporciona una facilidad de envío y recepción de mensajes. Tiene dos modos principales, seleccionados por las opciones utilizadas: Modo de Envío y Modo de Recepción.

En sistemas que no soportan la opción Utilerías de Portabilidad del Usuario, una aplicación que use mailx tendrá la capacidad de enviar mensajes de manera no especificada (Modo de Envío). A menos que el primer carácter de una o más líneas sea <tilde> ('~'), todos los caracteres en el mensaje de entrada aparecerán en el mensaje entregado, pero caracteres adicionales pueden ser insertados en el mensaje antes de que sea recuperado.

En sistemas que soportan la opción Utilerías de Portabilidad del Usuario, las capacidades de recepción de correo y otras características interactivas, Modo de Recepción, descrito a continuación, también estarán habilitadas.

Modo de Envío

El Modo de Envío puede ser utilizado por aplicaciones o usuarios para enviar mensajes a partir del texto en la entrada estándar.

Modo de Recepción

El Modo de Recepción está más orientado a usuarios interactivos. El correo puede ser leído y enviado en este modo interactivo.

Al leer correo, mailx proporciona comandos para facilitar el guardado, eliminación y respuesta a los mensajes. Al enviar correo, mailx permite editar, revisar y modificar el mensaje mientras se introduce.

El correo entrante se almacenará en una o más ubicaciones no especificadas para cada usuario, colectivamente llamadas el buzón del sistema para ese usuario. Cuando mailx se invoca en Modo de Recepción, el buzón del sistema será el lugar predeterminado para encontrar correo nuevo. A medida que se leen los mensajes, se marcarán para ser movidos a un archivo secundario para su almacenamiento, a menos que se tome una acción específica. Este archivo secundario se llama mbox y normalmente se encuentra en el directorio al que se refiere la variable de entorno HOME (ver MBOX en la sección VARIABLES DE ENTORNO para una descripción de este archivo). Los mensajes permanecerán en este archivo hasta que se eliminen explícitamente. Cuando se utiliza la opción -f para leer mensajes de correo de archivos secundarios, los mensajes se conservarán en esos archivos a menos que se eliminen específicamente. Las tres ubicaciones — buzón del sistema, mbox y archivo secundario — se denominan en esta sección simplemente ``buzones'', a menos que se requiera una identificación más específica.

OPCIONES

La utilidad mailx se ajustará al volumen de Definiciones Base de POSIX.1‐2017, Sección 12.2, Guías de Sintaxis de Utilidad.

Se soportarán las siguientes opciones. (Solo la opción -s asunto será requerida en todos los sistemas. Las otras opciones solo son requeridas en sistemas que soportan la opción Utilerías de Portabilidad del Usuario.)

-e
Prueba la presencia de correo en el buzón del sistema. La utilidad mailx no escribirá nada y saldrá con un código de retorno exitoso si hay correo para leer.
-f
Lee mensajes del archivo nombrado por el operando archivo en lugar del buzón del sistema. (Ver también folder.) Si no se especifica un operando archivo, lee mensajes de mbox en lugar del buzón del sistema.
-F
Registra el mensaje en un archivo nombrado con el primer destinatario. El nombre es la porción de nombre de inicio de sesión de la dirección encontrada primero en la línea To: en la cabecera del correo. Anula la variable record, si está establecida (ver Variables Internas en mailx).
-H
Escribe solo un resumen de cabecera.
-i
Ignora interrupciones. (Ver también ignore.)
-n
No inicializa desde el archivo de inicio del sistema por defecto. Ver la sección DESCRIPCIÓN EXTENDIDA.
-N
No escribe un resumen de cabecera inicial.
-s asunto
Establece el campo de cabecera Subject a asunto. Todos los caracteres en la cadena asunto aparecerán en el mensaje entregado. Los resultados no están especificados si asunto es más largo que {LINE_MAX} - 10 bytes o contiene un <nueva línea>.
-u usuario
Lee el buzón del sistema del nombre de inicio de sesión usuario. Esto solo tendrá éxito si el usuario que invoca tiene los privilegios apropiados para leer el buzón del sistema de dicho usuario.

OPERANDOS

Se soportarán los siguientes operandos:

dirección
Destinatario del mensaje. Cuando se especifica -n y no se accede a archivos de inicio de usuario (ver la sección DESCRIPCIÓN EXTENDIDA), el usuario o aplicación deberá asegurarse de que esta es una dirección para pasar al sistema de entrega de correo. Cualquier archivo de inicio del sistema o de usuario puede habilitar alias (ver alias en Comandos en mailx) que pueden modificar la forma de dirección antes de que se pase al sistema de entrega de correo.
archivo
Una ruta de un archivo que se leerá en lugar del buzón del sistema cuando se especifique -f. El significado del argumento de opción archivo se verá afectado por el contenido de la variable interna folder; ver Variables Internas en mailx.

ENTRADA ESTÁNDAR

Cuando mailx se invoca en Modo de Envío (la primera línea de la sinopsis), la entrada estándar será el mensaje a entregar a las direcciones especificadas. Cuando está en Modo de Recepción, los comandos del usuario se aceptarán desde stdin. Si la opción Utilerías de Portabilidad del Usuario no se soporta, las líneas de entrada estándar que comienzan con un carácter de <tilde> ('~') producen resultados no especificados.

Si la opción Utilerías de Portabilidad del Usuario se soporta, entonces tanto en Modo de Envío como en Modo de Recepción, las líneas de entrada estándar que comienzan con el carácter de escape (generalmente <tilde> ('~')) afectarán el procesamiento como se describe en Escapes de Comando en mailx.

ARCHIVOS DE ENTRADA

Cuando mailx se utiliza como se describe en este volumen de POSIX.1‐2017, el argumento de opción archivo (ver la opción -f) y mbox serán archivos de texto que contienen mensajes de correo, formateados como se describe en la sección ARCHIVOS DE SALIDA. La naturaleza del buzón del sistema no está especificada; no tiene por qué ser un archivo.

VARIABLES DE ENTORNO

Parte de la funcionalidad descrita en esta sección se proporcionará en implementaciones que soporten la opción Utilerías de Portabilidad del Usuario como se describe en el texto, y no se sombrea más para esta opción.

Las siguientes variables de entorno afectarán la ejecución de mailx:

DEAD
Determina la ruta del archivo en el que se guardarán los mensajes parciales en caso de interrupciones o errores de entrega. El valor por defecto será dead.letter en el directorio nombrado por la variable HOME. El comportamiento de mailx al guardar mensajes parciales no está especificado si la opción Utilerías de Portabilidad del Usuario no se soporta y DEAD no se define con el valor /dev/null.
EDITOR
Determina el nombre del editor de texto a utilizar para la edición de mensajes. Si no se define, se utilizará un editor de texto por defecto (generalmente vi). Los comandos de edición en mailx se formatearán según lo esperado por el editor especificado. Si el valor de EDITOR es una cadena vacía, el editor se saltará. Los comandos de edición, sin embargo, no se saltarán.
HOME
Determine el directorio de inicio del usuario. Este directorio se utiliza para ubicar el archivo mbox y el archivo dead.letter por defecto.
MAIL
Determine la ruta del buzón del sistema por defecto. El valor por defecto es el archivo /var/mail/nombre_inicio_sesion o /var/spool/mail/nombre_inicio_sesion.
MBOX
Determine la ruta del archivo donde se moverán los mensajes después de ser leídos. El valor por defecto es mbox en el directorio nombrado por la variable HOME. Si esta variable está definida y la opción -f se utiliza sin un operando archivo, mailx leerá los mensajes de este archivo en lugar del buzón del sistema.
NLSPATH
Determine la ubicación de los archivos de mensajes de soporte de idioma. Consultar i18n.
SHELL
Determine el nombre del shell por defecto a utilizar para los comandos externos. Si no se define, se utilizará un shell por defecto (generalmente el shell de Bourne).

EVENTOS ASÍNCRONOS

Se debe tener cuidado al usar mailx en modo interactivo mientras se reciben señales asíncronas. La siguiente información es para ayudar a los implementadores de sistemas a proporcionar un comportamiento consistente.

En el modo interactivo, la recepción de una señal que no sea SIGKILL o SIGTRAP detendrá temporalmente la operación actual y mostrará un prompt de comando.

Si se está redactando un mensaje y se recibe una señal, el mensaje se guardará en el archivo especificado por la variable DEAD (o dead.letter en el directorio HOME) si la variable ignoreeof no está establecida. El mensaje guardado incluirá cualquier texto de cabecera introducido hasta ese momento y el texto del mensaje hasta el punto de la interrupción.

Se permite a los usuarios interrumpir la salida de mensajes del listado de cabeceras de la pantalla pulsando la tecla INTERRUPCIÓN (consulte la sección Terminación de Entrada de las Definiciones Base de POSIX.1‐2017). Si se recibe una señal mientras se está procesando un comando, la operación actual se cancelará y se volverá al prompt de comando interactivo.

Si la opción Utilerías de Portabilidad del Usuario no se soporta, la mayoría de estas capacidades de manejo de señales no están disponibles.

ESTADO DE SALIDA

Se aplicarán los valores de retorno estándar.

Los siguientes valores de retorno se aplicarán además:

0
Se ejecutó sin error.
1
Ocurrió un error.
2
Hubo un error de sintaxis en la línea de comandos, una opción o argumento inválido, o un error fatal de lectura/escritura en un archivo de correo. (Esto es aplicable solo a la implementación).
Mayor que 2
Ocurrió un error de envío de correo.

EJEMPLOS

Para enviar un correo electrónico simple:
$ mailx -s "Reunión de hoy" jdoe@ejemplo.com < mi_mensaje.txt
Este comando envía el contenido del archivo `mi_mensaje.txt` como un correo electrónico con el asunto "Reunión de hoy" a la dirección `jdoe@ejemplo.com`.
Para leer el correo en modo interactivo:
$ mailx
Este comando inicia `mailx` en modo interactivo, mostrando la lista de correos recibidos.
Para leer el correo de otro usuario (requiere privilegios):
$ mailx -u root
Este comando intenta leer el buzón del usuario `root`.

COEFICIENTES Y ESPERADOS

Nada.

ENVIRONMENT

EDITOR
Un nombre de utilidad para invocar cuando se utiliza el comando edit (consulte Comandos en mailx) o ~e (consulte Escapes de comandos en mailx). El editor predeterminado no está especificado. En sistemas conformes a XSI, es ed. Los efectos de esta variable no están especificados si la opción Utilidades de portabilidad del usuario no es compatible.
HOME
Determina la ruta del directorio de inicio del usuario.
LANG
Proporciona un valor predeterminado para las variables de internacionalización que no están establecidas o están nulas. (Consulte el volumen Definiciones básicas de POSIX.1-2017, Sección 8.2, Variables de internacionalización para conocer la precedencia de las variables de internacionalización utilizadas para determinar los valores de las categorías de localización).
LC_ALL
Si se establece en un valor de cadena no vacío, anula los valores de todas las demás variables de internacionalización.
LC_CTYPE
Determina la localización para la interpretación de secuencias de bytes de datos de texto como caracteres (por ejemplo, caracteres de un solo byte en lugar de multiocteto en argumentos y archivos de entrada) y el manejo de comparaciones de direcciones y campos de encabezado sin distinción entre mayúsculas y minúsculas.
LC_TIME
Esta variable puede determinar el formato y el contenido de las cadenas de fecha y hora escritas por mailx. Este volumen de POSIX.1-2017 especifica los efectos de esta variable solo para los sistemas que admiten la opción Utilidades de portabilidad del usuario.
LC_MESSAGES

Determina la localización que debe utilizarse para afectar el formato y el contenido de los mensajes de diagnóstico escritos en la salida de error estándar y los mensajes informativos escritos en la salida estándar.
LISTER
Determina una cadena que representa el comando para escribir el contenido del directorio folder en la salida estándar cuando se recibe el comando folders (consulte folders en Comandos en mailx). Cualquier cadena aceptable como operando command_string para el comando sh -c será válida. Si esta variable está vacía o no está establecida, el comando de salida será ls. Los efectos de esta variable no están especificados si la opción Utilidades de portabilidad del usuario no es compatible.
MAILRC
Determina la ruta del archivo de inicio del usuario. El valor predeterminado será .mailrc en el directorio al que se refiere la variable de entorno HOME. El comportamiento de mailx no está especificado si la opción Utilidades de portabilidad del usuario no es compatible y MAILRC no está definida con el valor /dev/null.
MBOX
Determina la ruta del archivo para guardar los mensajes de la bandeja de entrada del sistema que se han leído. El comando exit anulará esta función, al igual que guardar el mensaje explícitamente en otro archivo. El valor predeterminado será mbox en el directorio nombrado por la variable HOME. Los efectos de esta variable no están especificados si la opción Utilidades de portabilidad del usuario no es compatible.
NLSPATH
Determina la ubicación de los catálogos de mensajes para el procesamiento de LC_MESSAGES.
PAGER
Determina una cadena que representa un comando de paginación o filtrado de salida para escribir la salida en la terminal. Cualquier cadena aceptable como operando command_string para el comando sh -c será válida. Cuando la salida estándar es un dispositivo de terminal, la salida del mensaje se canalizará a través del comando si la variable interna mailx crt se establece en un valor menor que el número de líneas del mensaje; consulte Variables internas en mailx. Si la variable PAGER está vacía o no está establecida, el paginador será more u otra utilidad de paginación documentada en la documentación del sistema. Los efectos de esta variable no están especificados si la opción Utilidades de portabilidad del usuario no es compatible.
SHELL
Determina el nombre de un intérprete de comandos preferido. El valor predeterminado será sh. Los efectos de esta variable no están especificados si la opción Utilidades de portabilidad del usuario no es compatible.
TERM
Si la variable interna screen no está especificada, determina el nombre del tipo de terminal para indicar de manera no especificada el número de líneas en una pantalla de encabezados. Si TERM no está establecida o está establecida en nulo, se utilizará un tipo de terminal predeterminado no especificado y el valor de una pantalla no está especificado. Los efectos de esta variable no están especificados si la opción Utilidades de portabilidad del usuario no es compatible.
TZ
Esta variable puede determinar la zona horaria utilizada para calcular las cadenas de fecha y hora escritas por mailx. Si TZ no está establecida o está vacía, se utilizará una zona horaria predeterminada no especificada.
VISUAL
Determina la ruta de una utilidad para invocar cuando se utiliza el comando visual (consulte Comandos en mailx) o el escape de comando ~v (consulte Escapes de comandos en mailx). Si esta variable está vacía o no está establecida, el editor de pantalla completa será vi. Los efectos de esta variable no están especificados si la opción Utilidades de portabilidad del usuario no es compatible.

EVENTOS ASÍNCRONOS

Cuando mailx está en Modo de envío y la entrada estándar no es una terminal, tomará la acción estándar para todas las señales.

En Modo de recepción, o en Modo de envío cuando la entrada estándar es una terminal, si se recibe una señal SIGINT:

1.
Si está en modo de comando, el comando actual, si lo hay, se abortará y se mostrará un indicador de modo de comando.
2.
Si está en modo de entrada:
a.
Si ignore está establecido, mailx mostrará "@\n", descartará la línea de entrada actual y continuará procesando, omitiendo el mecanismo de aborto de mensajes descrito en el punto 2b.
b.
Si la interrupción se recibió mientras se enviaba correo, ya sea en Modo de recepción o en Modo de envío, se mostrará un mensaje y se requerirá otra interrupción posterior, sin otros caracteres intermedios escritos, para abortar el mensaje de correo. Si está en Modo de recepción y se recibe otra interrupción, se mostrará un indicador de modo de comando. Si está en Modo de envío y se recibe otra interrupción, mailx terminará con un estado distinto de cero.

En ambos casos enumerados en el punto b, si el mensaje no está vacío:

i.
Si save está habilitado y el archivo nombrado por DEAD puede crearse, el mensaje se escribirá en el archivo nombrado por DEAD. Si el archivo existe, el mensaje se escribirá para reemplazar el contenido del archivo.
ii.
Si save no está habilitado, o el archivo nombrado por DEAD no puede crearse, el mensaje no se guardará.

El utilidad mailx tomará la acción estándar para todas las demás señales.

SALIDA ESTÁNDAR

En los modos de comando y de entrada, toda la salida, incluidos los indicadores y los mensajes, se escribirá en la salida estándar.

SALIDA DE ERROR ESTÁNDAR

La salida de error estándar se utilizará únicamente para mensajes de diagnóstico.

ARCHIVOS DE SALIDA

Varios comandos y escapes de comandos de mailx pueden crear o agregar a archivos, incluida la mbox, el archivo de buzón de borradores y los buzones secundarios. Cuando mailx se utiliza como se describe en este volumen de POSIX.1-2017, estos archivos serán archivos de texto, formateados de la siguiente manera:

línea que comienza con From<espacio>
[una o más líneas de encabezado; consulte Comandos en mailx]
línea vacía
[cero o más líneas de cuerpo
línea vacía]
[línea que comienza con From<espacio>...

donde cada mensaje comienza con la línea From <espacio> mostrada, precedida por el inicio del archivo o una línea vacía. (La línea From <espacio> se considera parte del encabezado del mensaje, pero no una de las líneas de encabezado a las que se hace referencia en Comandos en mailx; por lo tanto, no se verá afectada por los comandos discard, ignore o retain.) Los formatos del resto de la línea From <espacio> y cualquier otra línea de encabezado no están especificados, excepto que ninguna deberá estar vacía. El formato de una línea de cuerpo de mensaje tampoco está especificado, excepto que ninguna línea posterior a una línea vacía comenzará con From <espacio>; mailx modificará cualquier línea de cuerpo de mensaje ingresada por el usuario (posterior a una línea vacía y comenzando con From <espacio>) agregando uno o más caracteres para preceder a la 'F'; puede agregar estos caracteres a las líneas de From <espacio> que no están precedidas por una línea vacía.

Cuando un mensaje de la bandeja de entrada del sistema o ingresado por el usuario no es un archivo de texto, se define por la implementación cómo se almacena dicho mensaje en los archivos escritos por mailx.

DESCRIPCIÓN EXTENDIDA

La funcionalidad en toda la sección DESCRIPCIÓN EXTENDIDA se proporcionará en implementaciones que admitan la opción Utilidades de portabilidad del usuario. La funcionalidad descrita en esta sección se proporcionará en implementaciones que admitan la opción Utilidades de portabilidad del usuario (y el resto de esta sección no se sombrea más para esta opción).

La utilidad mailx no tiene que admitir todas las codificaciones de caracteres en todas las circunstancias. Por ejemplo, el correo entre sistemas puede restringirse a datos de 7 bits por la red subyacente, los datos de 8 bits no necesitan ser portátiles a sistemas no internacionalizados, etc. En estas circunstancias, se recomienda utilizar solo caracteres definidos en el rango de 7 bits del estándar ISO/IEC 646:1991 Versión de referencia internacional (equivalente a ASCII).

>

Cuando se invoca mailx utilizando una de las formas de sinopsis del modo de recepción, escribirá una página de líneas de resumen de encabezado (si no se especificó -N y hay mensajes, véase más adelante), seguida de un indicador que indica que mailx puede aceptar comandos regulares (véase Comandos en mailx); esto se denomina modo de comando. La página de líneas de resumen de encabezado contendrá el primer mensaje nuevo si hay mensajes nuevos, o el primer mensaje no leído si hay mensajes no leídos, o el primer mensaje. Cuando se invoca mailx utilizando la sinopsis del modo de envío y la entrada estándar es una terminal, si no se especifica ningún asunto en la línea de comandos y la variable asksub está establecida, se mostrará un indicador para el asunto. En este punto, mailx estará en modo de entrada. Este modo de entrada también se activará al utilizar una de las formas de sinopsis del modo de recepción y se componga una respuesta o un nuevo mensaje utilizando los comandos reply, Reply, followup, Followup o mail y la entrada estándar sea una terminal. Cuando se teclea el mensaje y se encuentra el final del mensaje, este se pasará al software de entrega de correo. Los comandos se pueden introducir comenzando una línea con el carácter de escape (por defecto, <tilde> ('~')) seguido de una sola letra de comando y argumentos opcionales. Véase Comandos en mailx para un resumen de estos comandos. No está especificado qué efecto tendrán estos comandos si la entrada estándar no es una terminal cuando se introduce un mensaje usando la sinopsis del modo de envío, o los comandos del modo de lectura reply, Reply, followup, Followup o mail.

Nota:
Para conveniencia de notación, esta sección utiliza el carácter de escape predeterminado, <tilde>, en todas las referencias y ejemplos.

En cualquier momento, el comportamiento de mailx se regirá por un conjunto de variables ambientales e internas. Estas son banderas y parámetros con valor que se pueden establecer y borrar mediante los comandos set y unset de mailx.

Los comandos regulares tienen la siguiente forma:

[comando] [lista de mensajes] [argumento ...]

Si no se especifica ningún comando en el modo de comando, se asumirá next. En modo de entrada, los comandos se reconocerán por el carácter de escape, y las líneas que no se traten como comandos se considerarán entrada para el mensaje.

En modo de comando, a cada mensaje se le asignará un número secuencial, comenzando por 1.

Todos los mensajes tienen un estado que afectará cómo se muestran en el resumen de encabezado y cómo se conservan o eliminan al finalizar mailx. Existe en cualquier momento la noción de un mensaje actual, que se marcará con un '>' al principio de una línea en el resumen de encabezado. Cuando se invoca mailx utilizando una de las formas de sinopsis del modo de recepción, el mensaje actual será el primer mensaje nuevo, si hay un mensaje nuevo, o el primer mensaje no leído si hay un mensaje no leído, o el primer mensaje si hay algún mensaje, o no estará especificado si no hay mensajes en el buzón. Cada comando que acepte una lista opcional de mensajes (lista de mensajes) o un mensaje opcional único (mensaje) sobre el cual operar dejará el mensaje actual establecido en el mensaje con el número más alto de los mensajes especificados, a menos que el comando elimine mensajes, en cuyo caso el mensaje actual se establecerá en el primer mensaje no eliminado (es decir, un mensaje que no está en estado de eliminado) después del mensaje con el número más alto eliminado por el comando, si existe, o el primer mensaje no eliminado antes del mensaje con el número más alto eliminado por el comando, si existe, o a un valor no especificado si no quedan mensajes no eliminados. Todos los mensajes estarán en uno de los siguientes estados:

nuevo
El mensaje está presente en el buzón del sistema y no ha sido visto por el usuario ni movido a ningún otro estado. Los mensajes en estado nuevo cuando mailx sale se conservarán en el buzón del sistema.
no leído
El mensaje ha estado presente en el buzón del sistema durante más de una invocación de mailx y no ha sido visto por el usuario ni movido a ningún otro estado. Los mensajes en estado no leído cuando mailx sale se conservarán en el buzón del sistema.
leído
El mensaje ha sido procesado por uno de los siguientes comandos: ~f, ~m, ~F, ~M, copy, mbox, next, pipe, print, Print, top, type, Type, undelete. Los comandos delete, dp y dt también pueden hacer que el siguiente mensaje se marque como leído, dependiendo del valor de la variable autoprint. Los mensajes que están en el buzón del sistema y en estado leído cuando mailx sale se guardarán en el archivo mbox, a menos que la variable interna hold estuviera establecida. Los mensajes que están en el mbox o en un buzón secundario y en estado leído cuando mailx sale se conservarán en su ubicación actual.
eliminado
El mensaje ha sido procesado por uno de los siguientes comandos: delete, dp, dt. Los mensajes en estado eliminado cuando mailx sale se eliminarán. Los mensajes eliminados se ignorarán hasta que mailx salga o cambie de buzón o se especifiquen para el comando undelete; por ejemplo, la especificación de mensaje /cadena solo buscará en las líneas de asunto de los mensajes que aún no han sido eliminados, a menos que el comando que opera sobre la lista de mensajes sea undelete. Ningún mensaje eliminado o encabezado de mensaje eliminado será mostrado por ningún comando de mailx excepto undelete.
preservado
El mensaje ha sido procesado por un comando preserve. Cuando mailx sale, el mensaje se conservará en su ubicación actual.
guardado
El mensaje ha sido procesado por uno de los siguientes comandos: save o write. Si el buzón actual es el buzón del sistema, y la variable interna keepsave está establecida, los mensajes en el estado guardado se guardarán en el archivo designado por la variable MBOX (véase la sección VARIABLES DE ENTORNO). Si el buzón actual es el buzón del sistema, los mensajes en el estado guardado se eliminarán del buzón actual, cuando se utilice el comando quit o file para salir del buzón actual.

La línea de resumen de encabezado para cada mensaje indicará el estado del mensaje.

Muchos comandos aceptan una lista opcional de mensajes (lista de mensajes) sobre la cual operar, que por defecto es el mensaje actual. Una lista de mensajes es una lista de especificaciones de mensajes separadas por caracteres de <espacio>, que pueden incluir:

n
Mensaje número n.
+
El siguiente mensaje no eliminado, o el siguiente mensaje eliminado para el comando undelete.
-
El mensaje no eliminado anterior, o el mensaje eliminado anterior para el comando undelete.
.
El mensaje actual.
^
El primer mensaje no eliminado, o el primer mensaje eliminado para el comando undelete.
$
El último mensaje.
*
Todos los mensajes.
n‐m
Un rango inclusivo de números de mensaje.
dirección
Todos los mensajes de dirección; cualquier dirección tal como se muestra en un resumen de encabezado será coincidente en esta forma.
/cadena
Todos los mensajes con cadena en la línea de asunto (ignora mayúsculas).
:c
Todos los mensajes del tipo c, donde c será uno de:
d
Mensajes eliminados.
n
Mensajes nuevos.
o
Mensajes antiguos (cualquiera que no esté en estado leído o nuevo).
r
Mensajes leídos.
u
Mensajes no leídos.

Otros comandos toman un mensaje opcional (mensaje) sobre el cual operar, que por defecto es el mensaje actual. Todas las formas permitidas para lista de mensajes también son permitidas para mensaje, pero si se especifica más de un mensaje, solo se operará sobre el primero.

Otros argumentos son generalmente cadenas arbitrarias cuyo uso depende del comando involucrado.

Inicio en mailx

En el momento del inicio, mailx realizará los siguientes pasos en secuencia:

1.
Establecer todas las variables a sus valores predeterminados indicados.
2.
Procesar las opciones de la línea de comandos, anulando los valores predeterminados correspondientes.
3.
Importar cualquiera de las variables DEAD, EDITOR, MBOX, LISTER, PAGER, SHELL o VISUAL que estén presentes en el entorno, anulando los valores predeterminados correspondientes.
4.
Leer los comandos de mailx de un archivo de inicio del sistema no especificado, a menos que se proporcione la opción -n, para inicializar cualquier variable interna de mailx y alias.
5.
Procesar el archivo de inicio del usuario con comandos de mailx nombrado en la variable MAILRC del usuario.

La mayoría de los comandos regulares de mailx son válidos dentro de los archivos de inicio, siendo el uso más común la configuración de opciones de visualización iniciales y listas de alias. Los siguientes comandos no serán válidos en un archivo de inicio: !, edit, hold, mail, preserve, reply, Reply, shell, visual, Copy, followup y Followup. Cualquier error en un archivo de inicio provocará que mailx termine con un mensaje de diagnóstico y un estado distinto de cero, o que continúe después de mostrar un mensaje de diagnóstico, ignorando el resto de las líneas del archivo.

Una línea en blanco en un archivo de inicio será ignorada.

Variables Internas en mailx

Las siguientes variables son variables internas de mailx. Cada variable interna se puede establecer mediante el comando set de mailx en cualquier momento. Los comandos unset y set no nombre c

Variables

The following variables can be used to set or unset options for mailx and can be used to erase variables.

In the following list, variables shown as:

variable

represent Boolean values. Variables shown as:

variable=value

shall be assigned string or numeric values. For string values, the rules in Commands in mailx concerning filenames and quoting shall also apply.

The defaults specified here may be changed by the unspecified system start-up file unless the user specifies the -n option.

allnet
All network names whose login name components match shall be treated as identical. This shall cause the msglist message specifications to behave similarly. The default shall be noallnet. See also the alternates command and the metoo variable.
append
Append messages to the end of the mbox file upon termination instead of placing them at the beginning. The default shall be noappend. This variable shall not affect the save command when saving to mbox.
ask, asksub
Prompt for a subject line on outgoing mail if one is not specified on the command line with the -s option. The ask and asksub forms are synonyms; the system shall refer to asksub and noasksub in its messages, but shall accept ask and noask as user input to mean asksub and noasksub. It shall not be possible to set both ask and noasksub, or noask and asksub. The default shall be asksub, but no prompting shall be done if standard input is not a terminal.
askbcc
Prompt for the blind copy list. The default shall be noaskbcc.
askcc
Prompt for the copy list. The default shall be noaskcc.
autoprint
Enable automatic writing of messages after delete and undelete commands. The default shall be noautoprint.
bang
Enable the special-case treatment of <exclamation-mark> characters ('!') in escape command lines; see the escape command and Command Escapes in mailx. The default shall be nobang, disabling the expansion of '!' in the command argument to the ~! command and the ~<!command escape.
cmd=command

Set the default command to be invoked by the pipe command. The default shall be nocmd.
crt=number
Pipe messages having more than number lines through the command specified by the value of the PAGER variable. The default shall be nocrt. If it is set to null, the value used is implementation-defined.
debug
Enable verbose diagnostics for debugging. Messages are not delivered. The default shall be nodebug.
dot
When dot is set, a <period> on a line by itself during message input from a terminal shall also signify end-of-file (in addition to normal end-of-file). The default shall be nodot. If ignoreeof is set (see below), a setting of nodot shall be ignored and the <period> is the only method to terminate input mode.
escape=c
Set the command escape character to be the character 'c'. By default, the command escape character shall be <tilde>. If escape is unset, <tilde> shall be used; if it is set to null, command escaping shall be disabled.
flipr
Reverse the meanings of the R and r commands. The default shall be noflipr.
folder=directory

The default directory for saving mail files. User-specified filenames beginning with a <plus-sign> ('+') shall be expanded by preceding the filename with this directory name to obtain the real pathname. If directory does not start with a <slash> ('/'), the contents of HOME shall be prefixed to it. The default shall be nofolder. If folder is unset or set to null, user-specified filenames beginning with '+' shall refer to files in the current directory that begin with the literal '+' character. See also outfolder below. The folder value need not affect the processing of the files named in MBOX and DEAD.
header
Enable writing of the header summary when entering mailx in Receive Mode. The default shall be header.
hold
Preserve all messages that are read in the system mailbox instead of putting them in the mbox save file. The default shall be nohold.
ignore
Ignore interrupts while entering messages. The default shall be noignore.
ignoreeof
Ignore normal end-of-file during message input. Input can be terminated only by entering a <period> ('.') on a line by itself or by the ~. command escape. The default shall be noignoreeof. See also dot above.
indentprefix=string

A string that shall be added as a prefix to each line that is inserted into the message by the ~m command escape. This variable shall default to one <tab>.
keep
When a system mailbox, secondary mailbox, or mbox is empty, truncate it to zero length instead of removing it. The default shall be nokeep.
keepsave
Keep the messages that have been saved from the system mailbox into other files in the file designated by the variable MBOX, instead of deleting them. The default shall be nokeepsave.
metoo
Suppress the deletion of the login name of the user from the recipient list when replying to a message or sending to a group. The default shall be nometoo.
onehop
When responding to a message that was originally sent to several recipients, the other recipient addresses are normally forced to be relative to the originating author's machine for the response. This flag disables alteration of the recipients' addresses, improving efficiency in a network where all machines can send directly to all other machines (that is, one hop away). The default shall be noonehop.
outfolder
Cause the files used to record outgoing messages to be located in the directory specified by the folder variable unless the pathname is absolute. The default shall be nooutfolder. See the record variable.
page
Insert a <form-feed> after each message sent through the pipe created by the pipe command. The default shall be nopage.
prompt=string

Set the command-mode prompt to string. If string is null or if noprompt is set, no prompting shall occur. The default shall be to prompt with the string "? ".
quiet
Refrain from writing the opening message and version when entering mailx. The default shall be noquiet.
record=file
Record all outgoing mail in the file with the pathname file. The default shall be norecord. See also outfolder above.
save
Enable saving of messages in the dead-letter file on interrupt or delivery error. See the variable DEAD for the location of the dead-letter file. The default shall be save.
screen=number

Set the number of lines in a screenful of headers for the headers and z commands. If screen is not specified, a value based on the terminal type identified by the TERM environment variable, the window size, the baud rate, or some combination of these shall be used.
sendwait
Wait for the background mailer to finish before returning. The default shall be nosendwait.
showto
When the sender of the message was the user who is invoking mailx, write the information from the To: line instead of the From: line in the header summary. The default shall be noshowto.
sign=string
Set the variable inserted into the text of a message when the ~a command escape is given. The default shall be nosign. The character sequences '\t' and '\n' shall be recognized in the variable as <tab> and <newline> characters, respectively. (See also ~i in Command Escapes in mailx.)
Sign=string
Set the variable inserted into the text of a message when the ~A command escape is given. The default shall be noSign. The character sequences '\t' and '\n' shall be recognized in the variable as <tab> and <newline> characters, respectively.
toplines=number

Set the number of lines of the message to write with the top command. The default shall be 5.

Commands in mailx

Comandos en mailx

Se proporcionarán los siguientes comandos de mailx. En la siguiente lista, encabezado se refiere a líneas del encabezado del mensaje, como se muestra en la sección ARCHIVOS DE SALIDA. Línea de encabezado se refiere a líneas dentro del encabezado que comienzan con uno o más caracteres que no son espacios en blanco, seguidos inmediatamente por un : y espacios en blanco y que continúan hasta la siguiente línea que comienza con un carácter que no es un espacio en blanco o una línea vacía. Campo de encabezado se refiere a la porción de una línea de encabezado anterior al primer : en esa línea.

Para cada uno de los comandos que se enumeran a continuación, el comando se puede introducir como la abreviatura (esos caracteres en la palabra del comando de Sinopsis que preceden a [), el comando completo (todos los caracteres que se muestran para la palabra del comando, omitiendo [ y ]), o cualquier truncamiento del comando completo hasta la abreviatura. Por ejemplo, el comando exit (que se muestra como ex[it] en la Sinopsis) se puede introducir como ex, exi o exit.

Los argumentos de los comandos se pueden citar, utilizando los siguientes métodos:

*
Un argumento puede encerrarse entre comillas dobles dobles ("") o comillas simples (''); cualquier espacio en blanco, expansión de palabras del shell o caracteres de \ dentro de las comillas se tratarán literalmente como parte del argumento. Una comilla doble se tratará literalmente dentro de comillas simples y viceversa. Estas propiedades especiales de los caracteres de comilla ocurrirán solo cuando estén emparejadas al principio y al final del argumento.
*
Un \ fuera de las comillas de cierre se descartará y el siguiente carácter se tratará literalmente como parte del argumento.
*
Un \ no citado al final de una línea de comando se descartará y la siguiente línea continuará el comando.

Los nombres de archivo, cuando se esperan, se someterán a las siguientes transformaciones, en secuencia:

*
Si el nombre de archivo comienza con un + no citado, y la variable folder está definida (ver la variable folder), el + se reemplazará por el valor de la variable folder seguido de una barra inclinada. Si la variable folder no está establecida o está establecida a nulo, el nombre del archivo no cambiará.
*
Las expansiones de palabras del shell se aplicarán al nombre del archivo (ver Sección 2.6, Expansiones de Palabras). Si más de una ruta de acceso resulta de esta expansión y el comando espera un solo archivo, los efectos no se especifican.

El mensaje se pondrá en el estado saved (guardado) y se comportará como se especifica en la descripción del estado saved cuando se salga del buzón actual con el comando quit o file.

En la forma capitalizada, guarda los mensajes especificados en un archivo cuyo nombre se deriva del autor del primer mensaje. Se tomará el nombre del archivo como el nombre del autor con toda la dirección de red eliminada. Vea también los comandos Copy, followup, y Followup y la variable outfolder.

Establecer variables

Sinopsis:
se[t] [name[=[string]] ...] [name=number ...] [noname ...]

Define una o más variables llamadas name. La variable puede recibir un valor nulo, de cadena o numérico. El entrecomillado y los caracteres de escape (<barra invertida>) pueden aparecer en cualquier parte de string, como se describió anteriormente, como si la porción de string del argumento fuera el argumento completo. Las formas name y name= serán equivalentes a name="" para variables que toman valores de cadena. El comando set sin argumentos escribirá una lista de todas las variables definidas y sus valores. La forma no name será equivalente a unset name.

Invoca un intérprete de comandos interactivo (ver también SHELL).

COMMAND ESCAPES

The following commands can be entered only from input mode, by beginning a line with the escape character (by default, <tilde> ('~')). See the escape variable description for changing this special character. The format for the commands shall be:

<escape-character><command-char><separator>[<arguments>]

where the <separator> can be zero or more <blank> characters.

In the following descriptions, the application shall ensure that the argument command is a shell command string. Any string acceptable to the command interpreter specified by the SHELL variable when it is invoked as SHELL -c command_string shall be valid. The command can be presented as multiple arguments (that is, quoting is not required).

Command escapes that are listed with msglist or mailx-command arguments are invalid in Send Mode and produce unspecified results.

Synopsis:
!command

Invoke the command interpreter specified by SHELL with two arguments: -c and command. (See also sh -c.) If the bang variable is set, each unescaped occurrence of '!' in command shall be replaced with the command executed by the previous ! command or ~! command escape.

Command Escapes in mailx

The following commands can be entered only from input mode, by beginning a line with the escape character (by default, <tilde> ('~')). See the escape variable description for changing this special character. The format for the commands shall be:

<escape-character><command-char><separator>[<arguments>]

where the <separator> can be zero or more <blank> characters.

In the following descriptions, the application shall ensure that the argument command (but not mailx-command) is a shell command string. Any string acceptable to the command interpreter specified by the SHELL variable when it is invoked as SHELL -c command_string shall be valid. The command can be presented as multiple arguments (that is, quoting is not required).

Command escapes that are listed with msglist or mailx-command arguments are invalid in Send Mode and produce unspecified results.

~! command
Invoke the command interpreter specified by SHELL with two arguments: -c and command; and then return to input mode. If the bang variable is set, each unescaped occurrence of '!' in command shall be replaced with the command executed by the previous ! command or ~! command escape.
~.
Simulate end-of-file (terminate message input).
~: mailx-command, ~_ mailx-command

Perform the command-level request.
~?
Write a summary of command escapes.
~A
This shall be equivalent to ~i Sign.
~a
This shall be equivalent to ~i sign.
~b name...
Add the names to the blind carbon copy (Bcc) list.
~c name...
Add the names to the carbon copy (Cc) list.
~d
Read in the dead-letter file. See DEAD for a description of this file.
~e
Invoke the editor, as specified by the EDITOR environment variable, on the partial message.
~f [msglist]
Forward the specified messages. The specified messages shall be inserted into the current message without alteration. This command escape also shall insert message headers into the message with field selection affected by the discard, ignore, and retain commands.
~F [msglist]
This shall be the equivalent of the ~f command escape, except that all headers shall be included in the message, regardless of previous discard, ignore, and retain commands.
~h
If standard input is a terminal, prompt for a Subject line and the To, Cc, and Bcc lists. Other implementation-defined headers may also be presented for editing. If the field is written with an initial value, it can be edited as if it had just been typed.
~i string
Insert the value of the named variable, followed by a <newline>, into the text of the message. If the string is unset or null, the message shall not be changed.
~m [msglist]
Insert the specified messages into the message, prefixing non-empty lines with the string in the indentprefix variable. This command escape also shall insert message headers into the message, with field selection affected by the discard, ignore, and retain commands.
~M [msglist]
This shall be the equivalent of the ~m command escape, except that all headers shall be included in the message, regardless of previous discard, ignore, and retain commands.
~p
Write the message being entered. If the message is longer than crt lines (see Internal Variables in mailx), the output shall be paginated as described for the PAGER variable.
~q
Quit (see the quit command) from input mode by simulating an interrupt. If the body of the message is not empty, the partial message shall be saved in the dead-letter file. See DEAD for a description of this file.
~r file, ~< file, ~r !command, ~< !command

Read in the file specified by the pathname file. If the argument begins with an <exclamation-mark> ('!'), the rest of the string shall be taken as an arbitrary system command; the command interpreter specified by SHELL shall be invoked with two arguments: -c and command. The standard output of command shall be inserted into the message.
~s string
Set the subject line to string.
~t name...
Add the given names to the To list.
~v
Invoke the full-screen editor, as specified by the VISUAL environment variable, on the partial message.
~w file
Write the partial message, without the header, onto the file named by the pathname file. The file shall be created or the message shall be appended to it if the file exists.
~x
Exit as with ~q, except the message shall not be saved in the dead-letter file.
~| command
Pipe the body of the message through the given command by invoking the command interpreter specified by SHELL with two arguments: -c and command. If the command returns a successful exit status, the standard output of the command shall replace the message. Otherwise, the message shall remain unchanged. If the command fails, an error message giving the exit status shall be written.

When the -e option is specified, the following exit values are returned:

 0

>0
Mail was not found or an error occurred.

Otherwise, the following exit values are returned:

 0

>0

APPLICATION USAGE

Delivery of messages to remote systems requires the existence of communication paths to such systems. These need not exist.

Input lines are limited to {LINE_MAX} bytes, but mailers between systems may impose more severe line-length restrictions. This volume of POSIX.1‐2017 does not place any restrictions on the length of messages handled by mailx, and for delivery of local messages the only limitations should be the normal problems of available disk space for the target mail file. When sending messages to external machines, applications are advised to limit messages to less than 100000 bytes because some mail gateways impose message-length restrictions.

The format of the system mailbox is intentionally unspecified. Not all systems implement system mailboxes as flat files, particularly with the advent of multimedia mail messages. Some system mailboxes may be multiple files, others records in a database. The internal format of the messages themselves is specified with the historical format from Version 7, but only after the messages have been saved in some file other than the system mailbox. This was done so that many historical applications expecting text-file mailboxes are not broken.

Some new formats for messages can be expected in the future, probably including binary data, bit maps, and various multimedia objects. As described here, mailx is not prohibited from handling such messages, but it must store them as text files in secondary mailboxes (unless some extension, such as a variable or command line option, is used to change the stored format). Its method of doing so is implementation-defined and might include translating the data into text file-compatible or readable form or omitting certain portions of the message

DESCRIPCIÓN

El comando retain conserva todos los campos de cabecera excepto aquellos explícitamente listados.

Los comandos discard e ignore no son inversos del comando retain. El comando retain descarta todos los campos de cabecera excepto aquellos explícitamente retenidos. El comando discard mantiene todos los campos de cabecera excepto aquellos explícitamente descartados. Si existen cabeceras en la lista de cabeceras retenidas, los comandos discard e ignore son ignorados.

RACIOCINIO

Los desarrolladores del estándar sintieron firmemente que era necesario un método para que las aplicaciones enviaran mensajes a usuarios específicos. El ejemplo obvio es una utilidad por lotes, ejecutándose de forma no interactiva, que desea comunicar errores o resultados a un usuario. Sin embargo, el formato real, el mecanismo de entrega y el método de lectura del mensaje están claramente fuera del alcance de este volumen de POSIX.1‐2017.

La intención de este comando es proporcionar una interfaz simple y portable para enviar mensajes de forma no interactiva. Simplemente define un ``front-end'' al sistema de correo histórico. Se sugiere que las implementaciones denoten explícitamente el remitente y el destinatario en el cuerpo del mensaje entregado. Deliberadamente no se hicieron especificaciones adicionales de formatos para el sobre del mensaje o el mensaje en sí, ya que la industria está en medio de un cambio de los estándares actuales a un estándar más internacionalizado y probablemente sea incorrecto, en este momento, requerir uno de ellos.

Se alienta a las implementaciones a que cumplan con los diversos mecanismos de entrega descritos en los estándares CCITT X.400 o con los estándares equivalentes de Internet, descritos en las Solicitudes de Comentarios (RFC) de Internet RFC 819, RFC 920, RFC 921, RFC 1123 y RFC 5322 (que sucedió a RFC 822).

Muchos sistemas históricos modificaron cada línea del cuerpo que comenzaba con From  prefijando la 'F' con '>'. Es innecesario, pero permitido, hacer eso cuando la cadena no sigue una línea en blanco porque no se puede confundir con la siguiente cabecera.

Los comandos edit y visual simplemente editan los mensajes especificados en un archivo temporal. No modifican el contenido de esos mensajes en el buzón; tal capacidad podría agregarse como una extensión, como por ejemplo usando nombres de comando diferentes.

La restricción de que una línea de asunto tenga como máximo {LINE_MAX}-10 bytes se basa en el formato histórico que consume 10 bytes para Subject:  y el salto de línea final. Muchos sistemas de correo históricos que un mensaje puede encontrar en otros sistemas no pueden manejar líneas tan largas, sin embargo.

Al igual que las utilidades logger y lp, mailx admitidamente es difícil de probar. Esto no se consideró justificación suficiente para excluir esta utilidad de este volumen de POSIX.1‐2017. También se puede argumentar que, de hecho, es testeable, pero que las pruebas en sí no son portables.

Cuando una aplicación que desea recibir los resultados como si no se soportaran las características de la opción de Utilidades de Portabilidad del Usuario está utilizando mailx, la variable de entorno DEAD debe establecerse en /dev/null. De lo contrario, puede estar sujeta a las creaciones de archivos descritas en EVENTOS ASÍNCRONOS de mailx. De manera similar, si la variable de entorno MAILRC no se establece en /dev/null, las versiones históricas de mailx y Mail leen comandos de inicialización de un archivo antes de que comience el procesamiento. Dado que la inicialización que un usuario especifica podría alterar el contenido de los mensajes que una aplicación está intentando enviar, dichas aplicaciones deben establecer MAILRC en /dev/null.

La descripción de LC_TIME usa "puede afectar" porque muchas implementaciones históricas no pueden o no pueden manipular las cadenas de fecha y hora en las cabeceras de correo entrante. Algunas cabeceras que se encuentran en el correo entrante no tienen suficiente información para determinar la zona horaria en la que se originó el correo, y, por lo tanto, mailx no puede convertir las cadenas de fecha y hora a la forma interna que luego es analizada por rutinas como strftime() que pueden tener en cuenta la configuración de LC_TIME. Cambiar todas estas horas a un formato especificado por el usuario está permitido, pero no es obligatorio.

El paginador seleccionado cuando PAGER es nulo o no está establecido está parcialmente no especificado para permitir la práctica histórica de System V de usar pg como predeterminado. Omitir la función de paginación, por ejemplo, declarando que cat es el paginador, no cumpliría con el significado previsto de esta descripción. Sin embargo, cualquier "usuario portable" tendría que establecer PAGER explícitamente para obtener su paginador preferido en todos los sistemas. La elección del paginador se hizo parcialmente no especificada, a diferencia de la elección del editor VISUAL (que se exige que sea vi) porque la mayoría de los paginadores históricos siguen un tema común de entrada del usuario, mientras que los editores difieren drásticamente.

Se consideraron como detalles de formato las opciones para especificar direcciones como cc (copia carbón) o bcc (copia carbón oculta) y fueron omitidas.

Un estado de salida cero implica que todos los mensajes fueron *enviados*, pero no garantiza que alguno de ellos fuera realmente *entregado*. La fiabilidad del mecanismo de entrega no está especificada y es una distinción de marketing apropiada entre sistemas.

Para cumplir con las Directrices de Sintaxis de Utilidad, se requirió una solución para el argumento de opción opcional file de -f. Al hacer de file un operando, se satisfacen las directrices y los usuarios permanecen portables. Sin embargo, obliga a las implementaciones a admitir el uso como:

mailx -fin mymail.box

El método no nombre para desestablecer variables no está presente en todos los sistemas históricos, pero sí en System V y proporciona un conjunto lógico de comandos correspondientes al formato de la visualización de opciones del comando set de mailx sin argumentos.

Las variables ask y asksub son los nombres seleccionados por BSD y System V, respectivamente, para la misma función. Son sinónimos en este volumen de POSIX.1‐2017.

El comando echo de mailx no fue documentado en la versión BSD y se ha omitido aquí porque no es obviamente útil para usuarios interactivos.

El prompt predeterminado en mailx de System V es un <signo de interrogación>, en Mail de BSD un <ampersand>. Dado que este volumen de POSIX.1‐2017 eligió el nombre mailx, mantuvo el predeterminado de System V, asumiendo que los usuarios de BSD no tendrían dificultades con esta pequeña incompatibilidad (que pueden anular).

Los significados de r y R están invertidos entre mailx de System V y Mail de SunOS. Una vez más, dado que este volumen de POSIX.1‐2017 eligió el nombre mailx, mantuvo el predeterminado de System V, pero permite al usuario de SunOS lograr los resultados deseados utilizando flipr, una variable interna en mailx de System V, aunque no ha sido documentada en el SVID.

La variable indentprefix, los comandos retain y unalias, y los escapes de comando ~F y ~M fueron adoptados de Mail 4.3 BSD.

El comando version no se incluyó porque no se pudo idear una especificación suficientemente general de la información de la versión que aún fuera útil para un usuario portable. Este nombre de comando debe ser utilizado por los proveedores que deseen proporcionar información de versión sobre el comando mailx.

El "archivo de inicio del sistema específico de la implementación (no especificado)" históricamente se ha llamado /etc/mailx.rc, pero este nombre y ubicación específicos no son requeridos.

La intención de la redacción del comando next es que si algún comando ya ha mostrado el mensaje actual, debe mostrar un mensaje siguiente, pero, de lo contrario, debe mostrar el mensaje actual. Considere la secuencia de comandos:

next 3
delete 3
next

donde la opción autoprint no estaba establecida. El texto normativo especifica que el segundo comando next debería mostrar un mensaje posterior al tercer mensaje, porque a pesar de que el mensaje actual no se ha mostrado desde que fue establecido por el comando delete, se ha mostrado desde que el mensaje actual fue cualquier cosa diferente del mensaje número 3. Esto no siempre coincide con la práctica histórica en algunas implementaciones, donde la dirección del archivo de comandos seguida de next (o el comando predeterminado) omitiría el mensaje para el que el usuario había buscado.
