MAILCAP(5) Manual de Formatos de Archivo MAILCAP(5)

NOMBRE

mailcap - archivo de capacidades de metamail

DESCRIPCIÓN

El archivo mailcap es leído por el programa metamail para determinar cómo mostrar contenido no textual en el sitio local.

La sintaxis de un archivo mailcap es bastante simple, al menos comparada con los archivos termcap. Cualquier línea que comience con "#" es un comentario. Las líneas en blanco se ignoran. De lo contrario, cada línea define una única entrada mailcap para un único tipo de contenido. Las líneas largas pueden continuarse terminándolas con un carácter de barra invertida, \.

Cada entrada individual de mailcap consiste en una especificación de tipo de contenido, un comando a ejecutar y (posiblemente) un conjunto de valores de "bandera" opcionales. Por ejemplo, una entrada de mailcap muy simple (que es en realidad un comportamiento predeterminado incorporado para metamail) se vería así:

text/plain; cat %s

Las banderas opcionales se pueden usar para especificar información adicional sobre el comando de manejo de correo. Por ejemplo:

text/plain; cat %s; copiousoutput

se puede usar para indicar que la salida del comando 'cat' puede ser voluminosa, requiriendo una ventana de desplazamiento, un paginador o algún otro mecanismo de adaptación apropiado.

El campo "tipo" (text/plain, en el ejemplo anterior) es simplemente cualquier nombre de tipo de contenido legal, según lo definido por RFC 822. En la práctica, es casi cualquier cadena. Es la cadena que se comparará con la cabecera "Content-type" (o el valor pasado con -c) para decidir si esta es la entrada de mailcap que coincide con el mensaje actual. Además, el campo tipo puede especificar un subtipo (por ejemplo, "text/ISO-8859-1") o un comodín para coincidir con todos los subtipos (por ejemplo, "image/*").

El campo "comando" es cualquier comando de UNIX ("cat %s" en el ejemplo anterior), y se usa para especificar el intérprete para el tipo de mensaje dado. Se pasará al shell a través de la facilidad system(3). Los puntos y comas y las barras invertidas dentro del comando deben escaparse con barras invertidas. Si el comando contiene "%s", esos dos caracteres se reemplazarán por el nombre de un archivo que contiene el cuerpo del mensaje. Si contiene "%t', esos dos caracteres se reemplazarán por el campo de tipo de contenido, incluido el subtipo, si lo hay. (Es decir, si el tipo de contenido fuera "image/pbm; opt1=something-else", entonces "%t" se reemplazaría por "image/pbm".) Si el campo comando contiene "%{" seguido de un nombre de parámetro y un cierre "}", entonces todos esos caracteres se reemplazarán por el valor del parámetro nombrado, si lo hay, de la cabecera Content-type. Por lo tanto, en el ejemplo anterior, "%{opt1}" se reemplazaría por "something-else". Finalmente, si el comando contiene "\%", esos dos caracteres se reemplazarán por un solo carácter %. (De hecho, la barra invertida se puede usar para escapar cualquier carácter, incluido ella misma.)

Si no aparece ningún "%s" en el campo comando, en lugar de colocar el cuerpo del mensaje en un archivo temporal, metamail pasará el cuerpo al comando a través de la entrada estándar. Esto es útil para ahorrar espacio en archivos /tmp, pero puede ser problemático para aplicaciones orientadas a ventanas en algunos sistemas de ventanas como MGR.

Dos códigos especiales pueden aparecer en el comando de visualización para objetos de tipo multipart (cualquier subtipo). Estos son "%n" y "%F". %n se reemplazará por el número de partes dentro del objeto multipart. %F se reemplazará por una serie de argumentos, dos por cada parte, que dan primero el tipo de contenido y luego el nombre del archivo temporal donde se ha almacenado la parte decodificada. Además, por cada archivo creado por %F, se crea un segundo archivo, con el mismo nombre seguido de "H", que contiene la información de cabecera para esa parte del cuerpo. Esto no será necesario para la mayoría de los manejadores multipart, pero está ahí si alguna vez lo necesita.

El campo "notes=xxx" es una cadena no interpretada que se utiliza para especificar el nombre de la persona que instaló esta entrada en el archivo mailcap. (El "xxx" puede ser reemplazado por cualquier cadena de texto.)

El campo "test=xxx" es un comando que se ejecuta para determinar si la línea mailcap se aplica o no. Es decir, si el campo de tipo de contenido coincide con el tipo de contenido del mensaje, pero hay un campo "test=", entonces la prueba debe tener éxito antes de que la línea mailcap se considere "coincidente" con el mensaje que se está viendo. El comando puede ser cualquier comando de UNIX, utilizando la misma sintaxis y los mismos escapes % que para el comando de visualización, como se describe anteriormente. Un comando se considera exitoso si sale con un estado de salida cero, y falla de lo contrario.

El campo "print=xxx" es un comando que se ejecuta para imprimir los datos en lugar de mostrarlos interactivamente. Este comportamiento es generalmente una consecuencia de invocar metamail con el modificador "-h".

El campo "textualnewlines" se puede usar en el caso algo oscuro en que las reglas predeterminadas de metamail para tratar las nuevas líneas en datos codificados en base64 no son satisfactorias. Por defecto, metamail traducirá CRLF al carácter de nueva línea local en la salida decodificada en base64 si el tipo de contenido es "text" (cualquier subtipo), pero no lo hará de lo contrario. Una entrada mailcap con un campo de "textualnewlines=1" forzará dicha traducción para el tipo de contenido especificado, mientras que "textualnewlines=0" garantizará que la traducción no tenga lugar incluso para los tipos de contenido textuales.

El campo "compose" se puede utilizar para especificar un programa que se puede usar para componer un nuevo cuerpo o parte del cuerpo en el formato dado. Su uso previsto es soportar agentes de composición de correo que soportan la composición de múltiples tipos de correo utilizando agentes de composición externos. Al igual que con el comando de visualización, el comando de composición se ejecutará después de reemplazar ciertas secuencias de escape que comienzan con "%". En particular, %s debe ser reemplazado por el nombre de un archivo al que se escribirán los datos compuestos por el programa de composición especificado, lo que permite al programa que llama (por ejemplo, metamail) decirle al programa llamado dónde almacenar los datos compuestos. Si %s no aparece, se asumirá que los datos compuestos serán escritos por los programas de composición a la salida estándar. El resultado del programa de composición puede ser datos que NO son adecuados para el transporte de correo, es decir, es posible que aún necesite aplicarse un Content-Transfer-Encoding a los datos.

El campo "composetyped" es similar al campo "compose", pero se usará cuando el programa de composición necesite especificar el campo de cabecera Content-type que se aplicará a los datos compuestos. El campo "compose" es más simple y se prefiere para su uso con programas existentes (no orientados al correo) para componer datos en un formato dado. El campo "composetyped" es necesario cuando la información de Content-type debe incluir parámetros auxiliares, y el programa de composición debe saber lo suficiente sobre los formatos de correo para producir una salida que incluya la información del tipo de correo, y para aplicar cualquier Content-Transfer-Encoding necesario. Conceptualmente, "compose" especifica un programa que simplemente genera datos del tipo especificado en su forma bruta, mientras que "composetyped" especifica un programa que genera los datos como un objeto MIME, con todas las cabeceras Content-* necesarias ya en su lugar.

needsterminal
Si se da esta bandera, el intérprete nombrado necesita interactuar con el usuario en una terminal. En algunos entornos (por ejemplo, un lector de correo orientado a ventanas bajo X11) esto requerirá la creación de una nueva ventana de emulación de terminal, mientras que en la mayoría de los entornos no lo hará. Si la entrada mailcap especifica "needsterminal" y metamail no se está ejecutando en una terminal (según lo determinado por isatty(3), la opción -x y la variable de entorno MM_NOTTTY) entonces metamail intentará ejecutar el comando en una nueva ventana de emulación de terminal. Actualmente, metamail sabe cómo crear nuevas ventanas bajo los sistemas de ventanas X11, SunTools y WM.
copiousoutput
Esta bandera debe darse siempre que el intérprete sea capaz de producir más de unas pocas líneas de salida en stdout, y no interactúe con el usuario. Si la entrada mailcap especifica copiousoutput, y se ha solicitado la paginación a través del comando "-p", entonces la salida del comando que se está ejecutando se canalizará a través de un programa de paginación ("more" por defecto, pero esto se puede anular con la variable de entorno METAMAIL_PAGER).

mailcap(5) File Formats Manual

NAME

mailcap - conventions for handling mailcap files

DESCRIPTION

The mailcap file is a database used by many mail reading programs (and other programs which deal with internet messages) to determine how to display or process various types of content found in internet messages. This is done using the MIME type. A MIME type consists of a type and a subtype, for example, text/plain or image/gif.

The mailcap file is a text file, and is searched for in a standard list of directories. The format of the file is line-oriented. Each line has the following format:

    type/subtype; command; [parameter=value]...

The type/subtype field is the MIME type of the data. This may also be a wildcard of the form */* or type/*.

The command field is a shell command to be executed to display or process the data. The command may contain shell metacharacters, and will be executed by sh. The command is given the mailcap entry and the body of the message as arguments. If the command requires the content type, it is passed as the environment variable MAILCAP_CONTENT_TYPE. Similarly, MAILCAP_FILENAME is set to the name of the temporary file containing the message body.

The optional parameter=value fields are used to specify additional information about the command. Common parameters include:

  • view= : a command to display the data. This is the default if no other parameter is specified.
  • compose= : a command to compose new data of this type.
  • edit= : a command to edit existing data of this type.
  • decompose= : a command to decompose (e.g. unpack) existing data into simpler forms.
  • handle= : a command to handle data of this type (e.g. a mailcap entry for a program that handles a specific file type).
  • flags= : a comma-separated list of flags. Common flags include:
    view=
    This is the default if no other parameter is specified.
    compose=
    A command to compose new data of this type.
    edit=
    A command to edit existing data of this type.
    decompose=
    A command to decompose (e.g. unpack) existing data into simpler forms.
    handle=
    A command to handle data of this type (e.g. a mailcap entry for a program that handles a specific file type).
    text
    Indicates that the content type is primarily text-based, and can be displayed directly by the user.
    x-auto-accept
    Indicates that the content should be automatically accepted and displayed without user intervention.
    x-auto-view
    Indicates that the content should be automatically displayed without user intervention.

Entries starting with a # are comments and are ignored.

A mailcap entry may be split across multiple lines by ending each line except the last with a backslash (\).

BUILT-IN CONTENT-TYPE SUPPORT

Metamail has a set of built-in content-type handlers for common types like text, image, and audio. This support is incomplete for many subtypes -- for example, it only supports US-ASCII text in general. This kind of built-in support can be OVERRIDDEN by an entry in any mailcap file on the user's search path. Metamail also has rudimentary built-in support for types that are totally unrecognized -- i.e. for which no mailcap entry or built-in handler exists. For such unrecognized types, metamail will write a file with a "clean" copy of the data -- i.e. a copy in which all mail headers have been removed, and in which any 7-bit transport encoding has been decoded.

FILES

$HOME/.mailcap:/etc/mailcap:/usr/etc/mailcap:/usr/local/etc/mailcap -- default path for mailcap files.
