MASTER(5) Manual de formatos de archivo MASTER(5)

NOMBRE

master - formato del archivo de configuración del proceso maestro de Postfix

DESCRIPCIÓN


El sistema de correo Postfix está implementado por un pequeño número de comandos (en su mayoría) clientes que son invocados por los usuarios, y por un mayor número de servicios que se ejecutan en segundo plano.

Los servicios de Postfix están implementados por procesos demonio. Estos se ejecutan en segundo plano, iniciados bajo demanda por el proceso master(8). El archivo de configuración master.cf define cómo un programa cliente se conecta a un servicio y qué programa demonio se ejecuta cuando se solicita un servicio. La mayoría de los procesos demonio son de corta duración y terminan voluntariamente después de servir a max_use clientes, o después de inactividad durante max_idle o más unidades de tiempo.

Todos los demonios especificados aquí deben hablar un protocolo interno de Postfix. Para ejecutar software que no sea de Postfix, use los servicios local(8), pipe(8) o spawn(8), o ejecute el software con inetd(8) o equivalente.

Después de cambiar master.cf, debe ejecutar "postfix reload" para recargar la configuración.

SINTAXIS

El formato general del archivo master.cf es el siguiente:

  • Las líneas vacías y las líneas que solo contienen espacios en blanco se ignoran, al igual que las líneas cuyo primer carácter que no sea espacio en blanco es un `#'.
  • Una línea lógica comienza con texto que no son espacios en blanco. Una línea que comienza con un espacio en blanco continúa una línea lógica.
  • Cada línea lógica define un solo servicio de Postfix. Cada servicio se identifica por su nombre y tipo, como se describe a continuación. Cuando varias líneas especifican el mismo nombre y tipo de servicio, solo se recuerda la última. De lo contrario, el orden de las definiciones de servicio de master.cf no importa.

Cada línea lógica consta de ocho campos separados por espacios en blanco. Estos se describen a continuación en el orden en que aparecen en el archivo master.cf.

Donde sea aplicable, un campo de "-" solicita que se utilice el valor predeterminado incorporado. Para campos booleanos, especifique "y" o "n" para anular el valor predeterminado.

Nombre del servicio
La sintaxis del nombre del servicio depende del tipo de servicio, como se describe a continuación.
Tipo de servicio
Especifique uno de los siguientes tipos de servicio:
inet
El servicio escucha en un socket TCP/IP y es accesible a través de la red.

El nombre del servicio se especifica como host:puerto, lo que denota el host y el puerto en los que se deben aceptar nuevas conexiones. La parte del host (y los dos puntos) pueden omitirse. Tanto el host como el puerto pueden proporcionarse en forma simbólica (ver hosts(5) o services(5)) o en forma numérica (dirección IP o número de puerto). La información del host puede incluirse entre corchetes "[]"; esta forma solo es necesaria con direcciones IPv6.

Ejemplos: un servicio llamado 127.0.0.1:smtp o ::1:smtp recibe correo solo a través de la interfaz de loopback; y un servicio llamado 10025 acepta conexiones en el puerto TCP 10025 a través de todas las interfaces configuradas con el parámetro inet_interfaces.

Nota: con Postfix versión 2.2 y posteriores, especifique "inet_interfaces = loopback-only" en main.cf, en lugar de codificar información de dirección IP de loopback en master.cf o en main.cf.

unix
El servicio escucha en un socket de flujo de dominio UNIX y solo es accesible para clientes locales.

El nombre del servicio es una ruta de archivo relativa al directorio de cola de Postfix (la ruta de archivo se controla con el parámetro de configuración queue_directory en main.cf).

En sistemas Solaris 8 y anteriores, el tipo unix se implementa con sockets de flujo.

unix-dgram
El servicio escucha en un socket de datagrama de dominio UNIX y solo es accesible para clientes locales.

El nombre del servicio es una ruta de archivo relativa al directorio de cola de Postfix (la ruta de archivo se controla con el parámetro de configuración queue_directory en main.cf).

fifo (obsoleto)
El servicio escucha en una FIFO (tubería con nombre) y solo es accesible para clientes locales.

El nombre del servicio es una ruta de archivo relativa al directorio de cola de Postfix (la ruta de archivo se controla con el parámetro de configuración queue_directory en main.cf).

pass
El servicio escucha en un socket de flujo de dominio UNIX y solo es accesible para clientes locales. Recibe una conexión abierta (paso de descriptor de archivo) por solicitud de conexión.

El nombre del servicio es una ruta de archivo relativa al directorio de cola de Postfix (la ruta de archivo se controla con el parámetro de configuración queue_directory en main.cf).

En sistemas Solaris 8 y anteriores, el tipo pass se implementa con sockets de flujo.

Esta característica está disponible a partir de la versión 2.5 de Postfix.

Privado (predeterminado: sí)
Si un servicio es interno a Postfix (la ruta de archivo comienza con private/), o está expuesto a través de las herramientas de línea de comandos de Postfix (la ruta de archivo comienza con public/). Los servicios de Internet (tipo inet) no pueden ser privados.
Sin privilegios (predeterminado: sí)
Si el servicio se ejecuta con privilegios de root o como el propietario del sistema Postfix (el nombre del propietario se controla mediante la variable de configuración mail_owner en el archivo main.cf).

Los demonios local(8), pipe(8), spawn(8) y virtual(8) requieren privilegios.

Chroot (predeterminado: Postfix >= 3.0: no, Postfix < 3.0: sí)
Si el servicio se ejecuta o no en un entorno chroot al directorio de cola de correo (la ruta de archivo se controla con la variable de configuración queue_directory en el archivo main.cf).

Chroot no debe usarse con los demonios local(8), pipe(8), spawn(8) y virtual(8). Aunque el servidor proxymap(8) puede ejecutarse en chroot, hacerlo anula la mayor parte del propósito de tener ese servicio en primer lugar.

Los archivos en el subdirectorio examples/chroot-setup del código fuente de Postfix muestran cómo configurar un entorno chroot de Postfix en una variedad de sistemas. Ver también BASIC_CONFIGURATION_README para problemas relacionados con la ejecución de demonios en chroot.

Tiempo de despertar (predeterminado: 0)
Despierta automáticamente el servicio nombrado después del número especificado de segundos. El despertar se implementa conectándose al servicio y enviando una solicitud de despertar. Un ? al final del campo de tiempo de despertar solicita que no se envíen eventos de despertar antes de la primera vez que se utiliza un servicio. Especifique 0 para no despertar automáticamente.

Los demonios pickup(8), qmgr(8) y flush(8) requieren un temporizador de despertar.

Límite de procesos (predeterminado: $default_process_limit)
El número máximo de procesos que pueden ejecutar este servicio simultáneamente. Especifique 0 para no tener límite en el recuento de procesos.

NOTA: Algunos servicios de Postfix deben configurarse como un servicio de un solo proceso (por ejemplo, qmgr(8)) y algunos servicios deben configurarse sin límite de procesos (por ejemplo, cleanup(8)). Estos límites no deben cambiarse.

Nombre del comando + argumentos
El comando que se ejecutará. Los caracteres que son especiales para el shell, como ">" o "|", no tienen ningún significado especial aquí, y las comillas no se pueden usar para proteger argumentos que contienen espacios en blanco. Para proteger los espacios en blanco, use "{" y "}", como se describe a continuación.

master.5.en - manual page

NAME

master.cf - Postfix master process multiplexor configuration

DESCRIPTION

The master.cf file specifies the available Postfix listener processes (daemons) and the commands needed to start them. It is the primary interface for controlling Postfix daemon processes.

The master.cf file is processed by the master(8) process. Each line in the file specifies a service that master(8) can manage.

The master.cf file format is described in master(5).

The syntax for commands executed by specific daemons is specified in the respective daemon manual page.

The following command-line options have the same effect for all daemon programs:

-D
Run the daemon under control by the command specified with the debugger_command variable in the main.cf configuration file. See DEBUG_README for hints and tips.
-o { name = value } (long form, Postfix >= 3.0)
Override the named main.cf configuration parameter. The parameter value can refer to other parameters as $name etc., just like in main.cf. See postconf(5) for syntax.

The "long form" supports whitespace in parameter values. Whitespace after the outer "{", around "=", and before the outer "}" is ignored. Example:

/etc/postfix/master.cf:
    submission inet .... smtpd
        -o { smtpd_xxx_yyy = text with whitespace... }

NOTE: Over-zealous use of parameter overrides makes the Postfix configuration hard to understand and maintain. At a certain point, it might be easier to configure multiple instances of Postfix, instead of configuring multiple personalities via master.cf.

-o name=value (short form)
Override the named main.cf configuration parameter. The parameter value can refer to other parameters as $name etc., just like in main.cf. See postconf(5) for syntax.

The "short form" does not support whitespace around the "=" or in parameter values. To specify a parameter value that contains whitespace, use the long form described above, or use commas instead of spaces if the parameter supports that, or specify the value in main.cf. Example:

/etc/postfix/master.cf:
    submission inet .... smtpd
        -o smtpd_xxx_yyy=$submission_xxx_yyy

/etc/postfix/main.cf
    submission_xxx_yyy = text with whitespace...

NOTE: Over-zealous use of parameter overrides makes the Postfix configuration hard to understand and maintain. At a certain point, it might be easier to configure multiple instances of Postfix, instead of configuring multiple personalities via master.cf.

-v
Increase the verbose logging level. Specify multiple -v options to make a Postfix daemon process increasingly verbose.
Command-line arguments that start with {
Command-line arguments that contain whitespace
Command-line arguments that must be empty
Specify "{" and "}" around such arguments (Postfix 3.0 and later). The outer "{" and "}" will be removed, together with any leading or trailing whitespace in the remaining text.
