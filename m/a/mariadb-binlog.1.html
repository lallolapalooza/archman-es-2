MARIADB-BINLOG(1) Sistema de Base de Datos MariaDB MARIADB-BINLOG(1)

NOMBRE

mariadb-binlog - utilidad para procesar archivos de registro binario (mariadb-binlog es ahora un enlace simbólico a mariadb-binlog)

SINOPSIS

mariadb-binlog [opciones] archivo_de_registro ...

DESCRIPCIÓN

El registro binario del servidor consta de archivos que contienen "eventos" que describen modificaciones al contenido de la base de datos. El servidor escribe estos archivos en formato binario. Para mostrar su contenido en formato de texto, utiliza la utilidad mariadb-binlog. También puedes utilizar mariadb-binlog para mostrar el contenido de los archivos de registro de retransmisión (relay log) escritos por un servidor esclavo en una configuración de replicación, ya que los registros de retransmisión tienen el mismo formato que los registros binarios.

Invoca mariadb-binlog de la siguiente manera:

shell> mariadb-binlog [opciones] archivo_de_registro ...

Por ejemplo, para mostrar el contenido del archivo de registro binario llamado binlog.000003, utiliza este comando:

shell> mariadb-binlog binlog.0000003

La salida incluye los eventos contenidos en binlog.000003. Para el registro basado en sentencias, la información del evento incluye la sentencia SQL, el ID del servidor en el que se ejecutó, la marca de tiempo cuando se ejecutó la sentencia, cuánto tiempo tomó, y así sucesivamente. Para el registro basado en filas, el evento indica un cambio de fila en lugar de una sentencia SQL.

Los eventos van precedidos por comentarios de encabezado que proporcionan información adicional. Por ejemplo:

# at 141
#100309  9:28:36 server id 123  end_log_pos 245
  Query thread_id=3350  exec_time=11  error_code=0

En la primera línea, el número que sigue a at indica la posición de inicio del evento en el archivo de registro binario.

La segunda línea comienza con una fecha y hora que indican cuándo comenzó la sentencia en el servidor donde se originó el evento. Para la replicación, esta marca de tiempo se propaga a los servidores esclavos. server id es el valor server_id del servidor donde se originó el evento. end_log_pos indica dónde comienza el siguiente evento (es decir, es la posición final del evento actual + 1). thread_id indica qué hilo ejecutó el evento. exec_time es el tiempo empleado en ejecutar el evento, en un servidor maestro. En un esclavo, es la diferencia entre el tiempo de finalización de la ejecución en el esclavo menos el tiempo de inicio de la ejecución en el maestro. La diferencia sirve como un indicador de cuánto está rezagado el esclavo respecto al maestro. error_code indica el resultado de ejecutar el evento. Cero significa que no ocurrió ningún error.

La salida de mariadb-binlog se puede volver a ejecutar (por ejemplo, utilizándola como entrada para mariadb) para rehacer las sentencias en el registro. Esto es útil para operaciones de recuperación después de un fallo del servidor. Para otros ejemplos de uso, consulta la discusión más adelante en esta sección.

Normalmente, utilizas mariadb-binlog para leer archivos de registro binario directamente y aplicarlos al servidor MariaDB local. También es posible leer registros binarios de un servidor remoto utilizando la opción --read-from-remote-server. Para leer registros binarios remotos, se pueden proporcionar las opciones de parámetros de conexión para indicar cómo conectarse al servidor. Estas opciones son --host, --password, --port, --protocol, --socket y --user; se ignoran excepto cuando también utilizas la opción --read-from-remote-server.

mariadb-binlog soporta las siguientes opciones, que se pueden especificar en la línea de comandos o en los grupos de archivos de opciones [mariadb-binlog] y [client].

•--help, -?

Muestra un mensaje de ayuda y sale.

•--base64-output=valor

Esta opción determina cuándo se deben mostrar los eventos codificados como cadenas base-64 utilizando sentencias BINLOG. La opción tiene estos valores permitidos (no distingue mayúsculas de minúsculas):

•AUTO ("automático") o UNSPEC ("no especificado") muestra sentencias BINLOG automáticamente cuando es necesario (es decir, para eventos de descripción de formato y eventos de fila). Este es el valor por defecto si no se proporciona ninguna opción --base64-output.

Nota
La visualización automática de BINLOG es el único comportamiento seguro si pretendes usar la salida de mariadb-binlog para volver a ejecutar el contenido del archivo de registro binario. Los otros valores de opción solo están destinados a fines de depuración o prueba, ya que pueden producir salidas que no incluyen todos los eventos en formato ejecutable.
•NEVER hace que las sentencias BINLOG no se muestren. mariadb-binlog sale con un error si se encuentra un evento de fila que debe mostrarse usando BINLOG.
•DECODE-ROWS especifica a mariadb-binlog que pretendes que los eventos de fila se decodifiquen y se muestren como sentencias SQL comentadas al especificar también la opción --verbose. Al igual que NEVER, DECODE-ROWS suprime la visualización de sentencias BINLOG, pero a diferencia de NEVER, no sale con un error si se encuentra un evento de fila.
--base64-output se puede dar como --base64-output o --skip-base64-output (con el sentido de AUTO o NEVER).

Para ver ejemplos que muestran el efecto de --base64-output y --verbose en la salida de eventos de fila, consulta la sección llamada “VISUALIZACIÓN DE EVENTOS DE FILA DE MARIADB-BINLOG”.

•--binlog-row-event-max-size=ruta

El directorio donde están instalados los conjuntos de caracteres.

•--character-sets-dir=ruta

El directorio donde están instalados los conjuntos de caracteres.

•--database=nombre_bd, -d nombre_bd

Esta opción hace que mariadb-binlog emita entradas del registro binario (solo registro local) que ocurren mientras nombre_bd ha sido seleccionado como base de datos por defecto mediante USE.

La opción --database para mariadb-binlog es similar a la opción --binlog-do-db para mariadbd, pero puede usarse para especificar solo una base de datos. Si se proporciona --database varias veces, solo se utiliza la última instancia.

Los efectos de esta opción dependen de si se utiliza el formato de registro basado en sentencias o en filas, de la misma manera que los efectos de --binlog-do-db dependen de si se utiliza el registro basado en sentencias o en filas.

Registro basado en sentencias. La opción --database funciona de la siguiente manera:

•Mientras nombre_bd es la base de datos por defecto, las sentencias se emiten ya sea que modifiquen tablas en nombre_bd o en una base de datos diferente.
•A menos que nombre_bd sea seleccionada como la base de datos por defecto, las sentencias no se emiten, incluso si modifican tablas en nombre_bd.
•Hay una excepción para CREATE DATABASE, ALTER DATABASE y DROP DATABASE. La base de datos que se está *creando, modificando o eliminando* se considera la base de datos por defecto al determinar si se debe emitir la sentencia.
Supongamos que el registro binario se creó ejecutando estas sentencias utilizando registro basado en sentencias: 
INSERT INTO test.t1 (i) VALUES(100);
INSERT INTO db2.t2 (j)  VALUES(200);
USE test;
INSERT INTO test.t1 (i) VALUES(101);
INSERT INTO t1 (i)      VALUES(102);
INSERT INTO db2.t2 (j)  VALUES(201);
USE db2;
INSERT INTO test.t1 (i) VALUES(103);
INSERT INTO db2.t2 (j)  VALUES(202);
INSERT INTO t2 (j)      VALUES(203);

mariadb-binlog --database=test no emite las dos primeras sentencias INSERT porque no hay una base de datos por defecto. Emite las tres sentencias INSERT después de USE test, pero no las tres sentencias INSERT después de USE db2.

mariadb-binlog --database=db2 no emite las dos primeras sentencias INSERT porque no hay una base de datos por defecto. No emite las tres sentencias INSERT después de USE test, pero sí emite las tres sentencias INSERT después de USE db2.

Registro basado en filas. mariadb-binlog emite solo las entradas que modifican tablas pertenecientes a nombre_bd. La base de datos por defecto no tiene ningún efecto en esto. Supongamos que el registro binario recién descrito se creó utilizando registro basado en filas en lugar de basado en sentencias. mariadb-binlog --database=test solo emite aquellas entradas que modifican t1 en la base de datos test, independientemente de si se emitió USE o cuál es la base de datos por defecto. Si un servidor se está ejecutando con binlog_format establecido en MIXED y deseas que sea posible utilizar mariadb-binlog con la opción --database, debes asegurarte de que las tablas que se modifican estén en la base de datos selec

•--debug[=debug_options], -# [debug_options]

Escribir un registro de depuración. Una cadena típica de debug_options es 'd:t:o,nombre_archivo'. El valor predeterminado es 'd:t:o,/tmp/mariadb-binlog.trace'.

•--debug-check

Imprimir información de depuración al salir del programa.

•--debug-info

Imprimir información de depuración y estadísticas de uso de memoria y CPU al salir del programa.

•--defaults-extra-file=nombre

Leer este archivo después de leer los archivos globales.

•--defaults-file=nombre

Leer solo las opciones predeterminadas del archivo dado.

•--default-auth=nombre

Plugin de cliente de autenticación predeterminado a utilizar.

•--disable-log-bin, -D

Desactivar el registro binario. Esto es útil para evitar un bucle infinito si utiliza la opción --to-last-log y está enviando la salida al mismo servidor MariaDB. Esta opción también es útil al restaurar después de una caída para evitar la duplicación de las sentencias registradas.

Esta opción requiere que tenga el privilegio SUPER. Hace que mariadb-binlog incluya una sentencia SET sql_log_bin = 0 en su salida para deshabilitar el registro binario de la salida restante. La sentencia SET es ineficaz a menos que tenga el privilegio SUPER.

•--flashback, -B

Soporte para el modo flashback.

•--force-if-open

Forzar si el binlog no se cerró correctamente. Predeterminado a activado; use --skip-force-if-open para desactivar.

•--force-read, -f

Con esta opción, si mariadb-binlog lee un evento de registro binario que no reconoce, imprime una advertencia, ignora el evento y continúa. Sin esta opción, mariadb-binlog se detiene si lee dicho evento.

•--hexdump, -H

Mostrar un volcado hexadecimal del registro en comentarios, como se describe en la sección llamada “FORMATO DEL VOLCADO HEXADECIMAL DE MARIADB-BINLOG”. La salida hexadecimal puede ser útil para depurar la replicación.

•--host=nombre_host, -h nombre_host

Obtener el registro binario del servidor MariaDB en el host dado.

•--local-load=ruta, -l ruta

Preparar archivos temporales locales para LOAD DATA INFILE en el directorio especificado.

•--no-defaults

No leer opciones predeterminadas de ningún archivo de opciones.

•--offset=N, -o N

Omitir las primeras N entradas del registro.

•--open-files-limit=NUM

Establece la variable open_files_limit, que se utiliza para reservar descriptores de archivo para mariadb-binlog.

•--password[=contraseña], -p[contraseña]

La contraseña a utilizar al conectarse al servidor. Si utiliza la forma corta de la opción (-p), *no puede* haber un espacio entre la opción y la contraseña. Si omite el valor de la contraseña después de la opción --password o -p en la línea de comandos, mariadb-binlog le pedirá una.

Especificar una contraseña en la línea de comandos debe considerarse inseguro. Puede usar un archivo de opciones para evitar proporcionar la contraseña en la línea de comandos.

•--plugin-dir=nombre_dir

Directorio para plugins del lado del cliente.

•--print-defaults

Imprimir la lista de argumentos del programa de todos los archivos de opciones y salir.

•--port=num_puerto, -P num_puerto

El número de puerto TCP/IP a usar para conectarse a un servidor remoto, o 0 para usar el valor predeterminado, en orden de preferencia, my.cnf, $MYSQL_TCP_PORT, /etc/services, valor predeterminado integrado (3306). Fuerza --protocol=tcp cuando se especifica en la línea de comandos sin otras propiedades de conexión.

•--protocol={TCP|SOCKET|PIPE|MEMORY}

El protocolo de conexión a utilizar para conectarse al servidor. Es útil cuando los demás parámetros de conexión normalmente causarían que se utilice un protocolo diferente al que desea.

•--raw

Requiere -R. Salida de datos binarios brutos en lugar de sentencias SQL. Archivos de salida con nombre de logs del servidor.

•--read-from-remote-server, -R

Leer el registro binario de un servidor MariaDB en lugar de leer un archivo de registro local. Cualquier opción de parámetro de conexión se ignora a menos que también se proporcione esta opción. Estas opciones son --host, --password, --port, --protocol, --socket y --user.

Esta opción requiere que el servidor remoto esté en ejecución. Solo funciona para archivos de registro binarios en el servidor remoto, no para archivos de registro de retransmisión.

•--result-file=nombre, -r nombre

Dirigir la salida al archivo dado. Con --raw, este es un prefijo para los nombres de archivo.

•--rewrite-db=nombre, -r nombre

Actualiza a una base de datos con un nombre diferente al original. Ejemplo: rewrite-db='de->a'. Para eventos que se registran como sentencias, reescribir la base de datos constituye cambiar la base de datos predeterminada de una sentencia de db1 a db2. No hay análisis de sentencias ni reescritura de ningún tipo, es decir, si se especifica "db1.tbl" explícitamente en la sentencia, esa ocurrencia no se cambiará a "db2.tbl". Los eventos basados en filas se reescriben correctamente para usar el nuevo nombre de base de datos. El filtrado (por ejemplo, con --database=nombre) ocurre después de que se hayan realizado las reescrituras de la base de datos. Si usa esta opción en la línea de comandos y ">" tiene un significado especial para su intérprete de comandos, cite el valor (por ejemplo, --rewrite-db="nombreantiguo->nombrenuevo".

•--server-id=id

Mostrar solo los eventos creados por el servidor con el ID de servidor dado.

•--set-charset=nombre_juego_caracteres

Agrega una sentencia SET NAMES nombre_juego_caracteres a la salida para especificar el juego de caracteres que se utilizará para procesar los archivos de registro.

•--short-form, -s

Mostrar solo las sentencias contenidas en el registro, sin información adicional ni eventos basados en filas. Esto es solo para pruebas y no debe usarse en sistemas de producción. Si desea suprimir la salida base64, considere usar --base64-output=never en su lugar.

•--socket=ruta, -S ruta

Para conexiones a localhost, el archivo de socket Unix a usar, o, en Windows, el nombre de la tubería con nombre a usar. Fuerza --protocol=socket cuando se especifica en la línea de comandos sin otras propiedades de conexión; en Windows, fuerza --protocol=pipe.

•--start-datetime=fecha_hora

Comenzar a leer el registro binario en el primer evento con una marca de tiempo igual o posterior al argumento fecha_hora. El valor fecha_hora es relativo a la zona horaria local en la máquina donde se ejecuta mariadb-binlog. El valor debe estar en un formato aceptado para los tipos de datos DATETIME o TIMESTAMP. Por ejemplo:

shell> mariadb-binlog --start-datetime="2014-12-25 11:25:56" binlog.000003

Esta opción es útil para la recuperación punto a punto.

•--start-position=N, -j N

Comenzar a leer el registro binario en la posición N. El tipo puede ser un entero positivo o una lista de GTID. Al usar un entero positivo, el valor solo se aplica al primer archivo binlog pasado en la línea de comandos, y se imprime el primer evento cuya posición sea igual o mayor que N. En modo GTID, se pueden pasar varios GTID como una lista separada por comas, donde cada uno debe tener un ID de dominio único. La lista representa el estado del binlog gtid que conoce el cliente (otro servidor de "réplica"). Por lo tanto, cada GTID es exclusivo; solo se imprimirán los eventos posteriores a un número de secuencia dado para permitir a los usuarios recibir eventos después de su estado actual.

Esta opción es útil para la recuperación punto a punto.

•--gtid-strict-mode

Procesar el binlog según la especificación gtid-strict-mode. Las posiciones de inicio y fin se verifican para cumplir la condición de comparación start < stop. Los números de secuencia de cualquier dominio gtid deben formar una secuencia monotónicamente creciente.

•--stop-datetime=fecha_hora

Dejar de leer el registro binario en el primer evento con una marca de tiempo igual o posterior al argumento fecha_hora. Esta opción es útil para la recuperación punto a punto. Consulte la descripción de la opción --start-datetime para obtener información sobre el valor fecha_hora.

Esta opción es útil para la recuperación punto a punto.

•--stop-never

Esperar más datos del servidor en lugar de detenerse al final del último registro. Implica --to-last-log.

•--stop-never-slave-server-id

El server_id del esclavo utilizado para --read-from-remote-server --stop-never.

•--stop-position=N

Dejar de leer el registro binario en el primer evento con una posición igual o mayor que N. El tipo puede ser un entero positivo o una lista de GTID. Al usar un entero positivo, el valor solo se aplica al último archivo de registro nombrado en la línea de comandos. Al estar en modo GTID, se pueden pasar varios GTID como una lista separada por comas, donde cada uno debe tener un ID de dominio único. Cada GTID es inclusivo; solo se imprimen los eventos hasta los números de secuencia dados.

Esta opción es útil para la recuperación punto a punto.

•--table, -T

Listar entradas solo para esta tabla (solo registro local).

• --to-last-log, -t

No se detenga al final del log binario solicitado de un servidor MariaDB, sino que continúe imprimiendo hasta el final del último log binario. Si envía la salida al mismo servidor MariaDB, esto puede provocar un bucle interminable, por lo que esta opción requiere --read-from-remote-server.

•--user=nombre_usuario, -u nombre_usuario

El nombre de usuario de MariaDB que se utilizará al conectarse a un servidor remoto.

•--verbose, -v

Reconstruye eventos de fila y los muestra como sentencias SQL comentadas. Si esta opción se proporciona dos veces, la salida incluye comentarios para indicar los tipos de datos de las columnas y algunos metadatos. Si esta opción se proporciona tres veces, la salida incluye advertencias de diagnóstico sobre la integridad del evento antes de la salida del programa.

Para ver ejemplos que muestran el efecto de --base64-output y --verbose en la salida de eventos de fila, consulte la sección llamada “MARIADB-BINLOG VISUALIZACIÓN DE EVENTOS DE FILA”.

•--version, -V

Muestra información de la versión y sale.

También puede establecer la siguiente variable utilizando la sintaxis --nombre_variable=valor:

•open_files_limit

Especifica el número de descriptores de archivo abiertos que se reservarán.

Puede canalizar la salida de mariadb-binlog al cliente mariadb para ejecutar los eventos contenidos en el log binario. Esta técnica se utiliza para recuperarse de un fallo cuando se tiene una copia de seguridad antigua. Por ejemplo:

shell> mariadb-binlog binlog.000001 | mariadb -u root -p

O:

shell> mariadb-binlog binlog.[0-9]* | mariadb -u root -p

También puede redirigir la salida de mariadb-binlog a un archivo de texto, si necesita modificar el log de sentencias primero (por ejemplo, para eliminar sentencias que no desea ejecutar por algún motivo). Después de editar el archivo, ejecute las sentencias que contiene utilizándolo como entrada para el programa mariadb:

shell> mariadb-binlog binlog.000001 > tmpfile
shell> ... edite tmpfile ...
shell> mariadb -u root -p < tmpfile

Cuando mariadb-binlog se invoca con la opción --start-position, muestra solo aquellos eventos con un desplazamiento en el log binario mayor o igual a una posición dada (la posición dada debe coincidir con el inicio de un evento). También tiene opciones para detenerse y comenzar cuando ve un evento con una fecha y hora dadas. Esto le permite realizar una recuperación puntual utilizando la opción --stop-datetime (para poder decir, por ejemplo, "restaurar mis bases de datos a cómo estaban hoy a las 10:30 a.m.").

Si tiene más de un log binario para ejecutar en el servidor MariaDB, el método seguro es procesarlos todos utilizando una única conexión al servidor. Aquí hay un ejemplo que demuestra lo que puede ser inseguro:

shell> mariadb-binlog binlog.000001 | mariadb -u root -p # ¡PELIGRO!
shell> mariadb-binlog binlog.000002 | mariadb -u root -p # ¡PELIGRO!

Procesar logs binarios de esta manera utilizando diferentes conexiones al servidor causa problemas si el primer archivo de log contiene una sentencia CREATE TEMPORARY TABLE y el segundo log contiene una sentencia que utiliza la tabla temporal. Cuando el primer proceso mariadb termina, el servidor elimina la tabla temporal. Cuando el segundo proceso mariadb intenta utilizar la tabla, el servidor informa "tabla desconocida".

Para evitar problemas como este, use un único proceso mariadb para ejecutar el contenido de todos los logs binarios que desee procesar. Aquí hay una forma de hacerlo:

shell> mariadb-binlog binlog.000001 binlog.000002 | mariadb -u root -p

Otro enfoque es escribir todos los logs en un solo archivo y luego procesar el archivo:

shell> mariadb-binlog binlog.000001 >  /tmp/statements.sql
shell> mariadb-binlog binlog.000002 >> /tmp/statements.sql
shell> mariadb -u root -p -e "source /tmp/statements.sql"

mariadb-binlog puede producir una salida que reproduce una operación LOAD DATA INFILE sin el archivo de datos original. mariadb-binlog copia los datos a un archivo temporal y escribe una sentencia LOAD DATA LOCAL INFILE que hace referencia al archivo. La ubicación predeterminada del directorio donde se escriben estos archivos depende del sistema. Para especificar un directorio explícitamente, use la opción --local-load.

Debido a que mariadb-binlog convierte las sentencias LOAD DATA INFILE en sentencias LOAD DATA LOCAL INFILE (es decir, agrega LOCAL), tanto el cliente como el servidor que se utilizan para procesar las sentencias deben estar configurados con la capacidad LOCAL habilitada.


Advertencia

Los archivos temporales creados para las sentencias LOAD DATA LOCAL *no* se eliminan automáticamente porque son necesarios hasta que realmente ejecute esas sentencias. Debe eliminar los archivos temporales usted mismo después de que ya no necesite el log de sentencias. Los archivos se pueden encontrar en el directorio de archivos temporales y tienen nombres como nombre_archivo_original-#-#.

MARIADB-BINLOG FORMATO DE VOLCADO HEXADECIMAL

La opción --hexdump hace que mariadb-binlog produzca un volcado hexadecimal del contenido del log binario:

shell> mariadb-binlog --hexdump master-bin.000001

La salida hexadecimal consiste en líneas de comentarios que comienzan con #, por lo que la salida podría verse así para el comando anterior:

/*!40019 SET @@session.max_delayed_threads=0*/;
/*!50003 SET @OLD_COMPLETION_TYPE=@@COMPLETION_TYPE,COMPLETION_TYPE=0*/;
# at 4
#051024 17:24:13 server id 1  end_log_pos 98
# Position  Timestamp   Type   Master ID        Size      Master Pos    Flags
# 00000004 9d fc 5c 43   0f   01 00 00 00   5e 00 00 00   62 00 00 00   00 00
# 00000017 04 00 35 2e 30 2e 31 35  2d 64 65 62 75 67 2d 6c |..5.0.15.debug.l|
# 00000027 6f 67 00 00 00 00 00 00  00 00 00 00 00 00 00 00 |og..............|
# 00000037 00 00 00 00 00 00 00 00  00 00 00 00 00 00 00 00 |................|
# 00000047 00 00 00 00 9d fc 5c 43  13 38 0d 00 08 00 12 00 |.......C.8......|
# 00000057 04 04 04 04 12 00 00 4b  00 04 1a                |.......K...|
#       Start: binlog v 4, server v 5.0.15-debug-log created 051024 17:24:13
#       at startup
ROLLBACK;

La salida del volcado hexadecimal contiene actualmente los elementos de la siguiente lista. Este formato está sujeto a cambios. (Para obtener más información sobre el formato del log binario, consulte http://forge.mysql.com/wiki/MySQL_Internals_Binary_Log.)

•Posición: La posición en bytes dentro del archivo de log.
•Timestamp: La marca de tiempo del evento. En el ejemplo mostrado, '9d fc 5c 43' es la representación de '051024 17:24:13' en hexadecimal.
•Tipo: El código del tipo de evento. En el ejemplo mostrado, '0f' indica un FORMAT_DESCRIPTION_EVENT. La siguiente tabla enumera los posibles códigos de tipo.
Tipo Nombre Significado
00 UNKNOWN_EVENT Este evento nunca debería estar presente en el log.
01 START_EVENT_V3 Esto indica el inicio de un archivo de log escrito por MySQL 4 o anterior.

MARIADB-BINLOG MOSTRAR EVENTOS DE FILA

Los siguientes ejemplos ilustran cómo mariadb-binlog muestra los eventos de fila que especifican modificaciones de datos. Estos corresponden a eventos con los códigos de tipo WRITE_ROWS_EVENT, UPDATE_ROWS_EVENT y DELETE_ROWS_EVENT. Las opciones --base64-output=DECODE-ROWS y --verbose pueden usarse para afectar la salida de eventos de fila.

Supongamos que el servidor está utilizando el registro binario basado en filas y que ejecuta la siguiente secuencia de sentencias:

CREATE TABLE t
(
  id   INT NOT NULL,
  name VARCHAR(20) NOT NULL,
  date DATE NULL
) ENGINE = InnoDB;
START TRANSACTION;
INSERT INTO t VALUES(1, 'apple', NULL);
UPDATE t SET name = 'pear', date = '2009-01-01' WHERE id = 1;
DELETE FROM t WHERE id = 1;
COMMIT;

Por defecto, mariadb-binlog muestra los eventos de fila codificados como cadenas base64 utilizando sentencias BINLOG. Omitiendo líneas superfluas, la salida para los eventos de fila producidos por la secuencia de sentencias anterior se ve así:

Puede indicar a mariadb-binlog que suprima las sentencias BINLOG para los eventos de fila utilizando la opción --base64-output=DECODE-ROWS. Esto es similar a --base64-output=NEVER pero no finaliza con un error si se encuentra un evento de fila. shell> mariadb-binlog -v --base64-output=DECODE-ROWS archivo_registro

Nota

No debe suprimir las sentencias BINLOG si tiene la intención de volver a ejecutar la salida de mariadb-binlog.

Las sentencias SQL producidas por --verbose para los eventos de fila son mucho más legibles que las sentencias BINLOG correspondientes. Sin embargo, no corresponden exactamente a las sentencias SQL originales que generaron los eventos. Se aplican las siguientes limitaciones:

•Los nombres de columna originales se pierden y se reemplazan por @N, donde N es un número de columna.
•La información del conjunto de caracteres no está disponible en el registro binario, lo que afecta la visualización de columnas de cadena:
•No se hace distinción entre los tipos de cadena binaria y no binaria correspondientes (BINARY y CHAR, VARBINARY y VARCHAR, BLOB y TEXT). La salida utiliza un tipo de datos STRING para cadenas de longitud fija y VARSTRING para cadenas de longitud variable.
•Para conjuntos de caracteres multibyte, el número máximo de bytes por carácter no está presente en el registro binario, por lo que la longitud de los tipos de cadena se muestra en bytes en lugar de caracteres. Por ejemplo, STRING(4) se utilizará como tipo de datos para valores de cualquiera de estos tipos de columna: 
CHAR(4) CHARACTER SET latin1
CHAR(2) CHARACTER SET ucs2
•Debido al formato de almacenamiento para eventos de tipo UPDATE_ROWS_EVENT, las sentencias UPDATE se muestran con la cláusula WHERE precediendo a la cláusula SET.

La interpretación correcta de los eventos de fila requiere la información del evento de descripción del formato al principio del registro binario. Dado que mariadb-binlog no sabe de antemano si el resto del registro contiene eventos de fila, por defecto muestra el evento de descripción del formato utilizando una sentencia BINLOG en la parte inicial de la salida.

Si se sabe que el registro binario no contiene ningún evento que requiera una sentencia BINLOG (es decir, ningún evento de fila), la opción --base64-output=NEVER se puede utilizar para evitar que se escriba esta cabecera.
