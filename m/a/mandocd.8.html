MANDOCD(8) Manual del Administrador del Sistema MANDOCD(8)

NOMBRE

mandocd — proceso servidor para formatear páginas del manual en modo por lotes

SINOPSIS

mandocd [-I os=nombre] [-T salida] socket_fd

DESCRIPCIÓN

La utilidad mandocd formatea muchas páginas del manual sin requerir la sobrecarga de fork(2) y exec(3) entre cada formato. No requiere listar todos los manuales a formatear en la línea de comandos, y soporta escribir cada manual formateado en su propio descriptor de archivo.

Este servidor requiere que un socket(2) de dominio UNIX conectado ya esté presente en el momento de exec(3). Consecuentemente, no puede ser iniciado desde la línea de comandos de sh(1) porque el shell no puede proporcionar tal socket. Típicamente, el proceso padre crea el socket usando socketpair(2) antes de llamar a fork(2) y exec(3) en mandocd. El proceso padre pasará el número del descriptor de archivo como argumento a exec(3), formateado como un entero codificado en ASCII decimal. Vea catman(8) para una implementación típica de un proceso padre.

mandocd itera leyendo mensajes de un byte con recvmsg(2) desde el descriptor de archivo número socket_fd. Ignora el byte leído y solo usa los datos de control auxiliares de banda (struct cmsghdr), típicamente proporcionados por el proceso que llama usando CMSG_FIRSTHDR(3). Se espera que el proceso padre pase tres descriptores de archivo con cada byte ficticio. El primero se usa para la entrada mdoc(7) o man(7), el segundo para la salida formateada y el tercero para la salida de error.

Las opciones son las siguientes:

-I os=nombre
Anula el nombre del sistema operativo predeterminado nombre para el Os de mdoc(7) y para la macro TH de man(7).
-T salida
Formato de salida. El argumento salida puede ser ascii, utf8 o html; vea mandoc(1). En el modo de salida html, la opción de salida fragment se implica. Otras opciones de salida no son compatibles.

Después de agotar un descriptor de archivo de entrada, los tres descriptores de archivo se cierran antes de leer el siguiente byte ficticio y el mensaje de control.

Cuando se lee un mensaje de cero bytes, cuando el proceso padre cierra el socket_fd o cuando ocurre un error, mandocd sale.

ESTADO DE SALIDA

La utilidad mandocd sale con 0 en caso de éxito y  >0 si ocurre un error.

Un mensaje de cero bytes o un socket_fd cerrado se considera éxito. Los errores posibles incluyen:

  • argumentos de exec(3) faltantes, inválidos o excesivos
  • falla de recvmsg(2), por ejemplo, debido a EMSGSIZE
  • datos de control faltantes o inesperados, en particular un cmsg_level en el struct cmsghdr diferente de SOL_SOCKET, un cmsg_type diferente de SCM_RIGHTS, o un cmsg_len que no es tres veces el tamaño de un int
  • descriptores de archivo inválidos pasados en el CMSG_DATA(3)
  • agotamiento de recursos, en particular falla de dup(2) o malloc(3)

Excepto por el agotamiento de memoria y fallos similares a nivel de sistema, los errores de análisis y formato no provocan que mandocd devuelva un estado de salida de error. Incluso después de errores graves de análisis, mandocd simplemente aceptará y procesará el siguiente descriptor de archivo de entrada.

VER TAMBIÉN

mandoc(1), mandoc(3), catman(8)

HISTORIAL

La utilidad mandocd apareció en la versión 1.14.1 o en el mandoc toolkit.

AUTORES

El concepto fue diseñado e implementado por Michael Stapelberg <stapelberg@debian.org>. La unión de mandoc(3) necesaria para convertirlo en un proceso independiente fue añadida por Ingo Schwarze <schwarze@openbsd.org>.

ADVERTENCIAS

Si las páginas del manual analizadas contienen solicitudes .so de roff(7), mandocd necesita ser iniciado con el directorio de trabajo actual establecido en la raíz del árbol de páginas del manual. Evite iniciarlo en directorios que contengan archivos secretos en cualquier subdirectorio, en particular en los que el usuario que lo inicia tenga acceso de lectura a estos archivos secretos.
