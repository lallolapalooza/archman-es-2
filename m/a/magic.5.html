MAGIC(5) Manual de formatos de archivo MAGIC(5)

NOMBRE

magic — archivo de patrones mágicos del comando file

DESCRIPCIÓN

Esta página del manual documenta el formato de los archivos mágicos tal como los utiliza el comando file(1), versión 5.46. El comando file(1) identifica el tipo de un archivo utilizando, entre otras pruebas, una prueba para determinar si el archivo contiene ciertos "patrones mágicos". La base de datos de estos "patrones mágicos" suele estar ubicada en un archivo binario en /usr/share/file/misc/magic.mgc o en un directorio de archivos fragmentados de patrones mágicos de texto fuente en /usr/share/file/misc/magic. La base de datos especifica qué patrones se deben probar, qué mensaje o tipo MIME imprimir si se encuentra un patrón particular, e información adicional a extraer del archivo.

El formato de los archivos fragmentados fuente que se utilizan para construir esta base de datos es el siguiente: Cada línea de un archivo fragmentado especifica una prueba a realizar. Una prueba compara los datos que comienzan en un desplazamiento particular en el archivo con un valor de byte, una cadena o un valor numérico. Si la prueba tiene éxito, se imprime un mensaje. La línea consta de los siguientes campos:

offset
Un número que especifica el desplazamiento (en bytes) dentro del archivo de los datos que se van a probar. Este desplazamiento puede ser un número negativo si es:
  • El primer desplazamiento directo de la entrada mágica (en el nivel de continuación 0), en cuyo caso se interpreta como un desplazamiento desde el final del archivo hacia atrás. Esto solo funciona cuando se dispone de un descriptor de archivo para el archivo y es un archivo regular.
  • Un desplazamiento de continuación relativo al final del último campo de nivel superior (&).
Si el desplazamiento comienza con el símbolo “+”, entonces todos los desplazamientos se interpretan desde el principio del archivo (el predeterminado).
type
El tipo de datos a probar. Los valores posibles son:
byte
Un valor de un byte.
short
Un valor de dos bytes en el orden de bytes nativo de esta máquina.
long
Un valor de cuatro bytes en el orden de bytes nativo de esta máquina.
quad
Un valor de ocho bytes en el orden de bytes nativo de esta máquina.
float
Un número de punto flotante IEEE de precisión simple de 32 bits en el orden de bytes nativo de esta máquina.
double
Un número de punto flotante IEEE de precisión doble de 64 bits en el orden de bytes nativo de esta máquina.
string
Una cadena de bytes. La especificación del tipo de cadena puede ir seguida opcionalmente por una opción /<ancho> y opcionalmente seguida por un conjunto de banderas /[bCcftTtWw]*. El ancho limita el número de caracteres a copiar. Cero significa todos los caracteres. Se admiten las siguientes banderas:
b
Forzar prueba de archivo binario.
C
Usar coincidencia insensible a mayúsculas: los caracteres en mayúsculas en el patrón mágico coinciden tanto con mayúsculas como con minúsculas en el objetivo, mientras que los caracteres en minúsculas en el patrón mágico solo coinciden con caracteres en mayúsculas en el objetivo.
c
Usar coincidencia insensible a minúsculas: los caracteres en minúsculas en el patrón mágico coinciden tanto con mayúsculas como con minúsculas en el objetivo, mientras que los caracteres en mayúsculas en el patrón mágico solo coinciden con caracteres en minúsculas en el objetivo. Para hacer una coincidencia completa insensible a mayúsculas, especifique tanto “c” como “C”.
f
Requerir que la cadena coincidente sea una palabra completa, no una coincidencia parcial de palabra.
T
Recortar la cadena, es decir, espacios en blanco al principio y al final.
t
Forzar prueba de archivo de texto.
W
Comprimir espacios en blanco en el objetivo, que debe contener al menos un carácter de espacio en blanco. Si el patrón mágico tiene n espacios en blanco consecutivos, el objetivo necesita al menos n espacios en blanco consecutivos para coincidir.
w
Tratar cada espacio en blanco en el patrón mágico como un espacio en blanco opcional. se elimina antes de imprimir la cadena.
pstring
Una cadena estilo Pascal donde el primer byte/short/int se interpreta como la longitud sin signo. La longitud predeterminada es byte y se puede especificar como un modificador. Se admiten los siguientes modificadores:
B
Una longitud de byte (predeterminado).
H
Una longitud de 2 bytes big-endian.
h
Una longitud de 2 bytes little-endian.
L
Una longitud de 4 bytes big-endian.
l
Una longitud de 4 bytes little-endian.
J
La longitud se incluye a sí misma en su conteo.
La cadena no está terminada en NUL. Se utiliza “J” en lugar de el más valioso “I” porque este tipo de longitud es una característica del formato JPEG.
date
Un valor de cuatro bytes interpretado como una fecha de UNIX.
qdate
Un valor de ocho bytes interpretado como una fecha de UNIX.
ldate
Un valor de cuatro bytes interpretado como una fecha estilo UNIX, pero interpretado como hora local en lugar de UTC.
qldate
Un valor de ocho bytes interpretado como una fecha estilo UNIX, pero interpretado como hora local en lugar de UTC.
qwdate
Un valor de ocho bytes interpretado como una fecha estilo Windows.
msdosdate
Un valor de dos bytes interpretado como fecha estilo FAT/DOS.
msdostime
Un valor de dos bytes interpretado como hora estilo FAT/DOS.
beid3
Una longitud ID3 de 32 bits en orden de bytes big-endian.
beshort
Un valor de dos bytes en orden de bytes big-endian.
belong
Un valor de cuatro bytes en orden de bytes big-endian.
bequad
Un valor de ocho bytes en orden de bytes big-endian.
befloat
Un número de punto flotante IEEE de precisión simple de 32 bits en orden de bytes big-endian.
bedouble
Un número de punto flotante IEEE de precisión doble de 64 bits en orden de bytes big-endian.
bedate
Un valor de cuatro bytes en orden de bytes big-endian, interpretado como una fecha de Unix.
beqdate
Un valor de ocho bytes en orden de bytes big-endian, interpretado como una fecha de Unix.
beldate
Un valor de cuatro bytes en orden de bytes big-endian, interpretado como una fecha estilo UNIX, pero interpretado como hora local en lugar de UTC.

indirect
A partir del offset dado, se consulta nuevamente la base de datos mágica. El offset de la magia indirect es, por defecto, absoluto en el archivo, pero se puede especificar /r para indicar que el offset es relativo desde el principio de la entrada.
name
Define una instancia mágica "con nombre" que puede ser llamada desde otra entrada mágica use, como una llamada a subrutina. Los offsets mágicos directos de instancias con nombre son relativos al offset de la entrada previamente emparejada, pero los offsets indirectos son relativos al principio del archivo como de costumbre. Las entradas mágicas con nombre siempre coinciden.
use
Llama recursivamente a la magia con nombre a partir del offset actual. Si el nombre de la referencia comienza con ^, entonces la endianness de la magia se invierte; si la magia mencionaba leshort, por ejemplo, se trata como beshort y viceversa. Esto es útil para evitar duplicar las reglas para diferentes endianness.
regex
Una coincidencia de expresión regular en sintaxis de expresiones regulares extendidas POSIX (como egrep). Las expresiones regulares pueden requerir tiempo exponencial para procesarse, y su rendimiento es difícil de predecir, por lo que se desaconseja su uso. Cuando se utilizan en entornos de producción, su rendimiento debe comprobarse cuidadosamente. El tamaño de la cadena a buscar también debe limitarse especificando /<length>, para evitar problemas de rendimiento al escanear archivos largos. La especificación del tipo también puede ir seguida opcionalmente por /[c][s][l]. El indicador "c" hace que la coincidencia no distinga entre mayúsculas y minúsculas, mientras que el indicador "s" actualiza el offset al offset de inicio de la coincidencia, en lugar del final. El modificador "l" cambia el límite de longitud para que signifique número de líneas en lugar de un recuento de bytes. Las líneas se delimitan por el delimitador de línea nativo de la plataforma. Cuando se especifica un recuento de líneas, también se calcula un recuento de bytes implícito asumiendo que cada línea tiene 80 caracteres. Si no se especifica un recuento de bytes ni de líneas, la búsqueda se limita automáticamente a 8KiB. ^ y $ coinciden con el principio y el final de las líneas individuales, respectivamente, no con el principio y el final del archivo.
search
Una búsqueda de cadena literal comenzando en el offset dado. Se pueden usar los mismos modificadores que para los patrones de cadena. La expresión de búsqueda debe contener el rango en la forma /número,, es decir, el número de posiciones en las que se intentará la coincidencia, comenzando desde el offset de inicio. Esto es adecuado para buscar expresiones binarias más grandes con offsets variables, utilizando escapes \ para caracteres especiales. El orden del modificador y el número no es relevante.
default
Esto está destinado a ser utilizado con la prueba x (que siempre es verdadera) y no tiene tipo. Coincide cuando ninguna otra prueba en ese nivel de continuación ha coincidido antes. Borrar esas pruebas emparejadas para un nivel de continuación se puede hacer usando la prueba clear.
clear
Esta prueba es siempre verdadera y borra la bandera de coincidencia para ese nivel de continuación. Está destinada a ser utilizada con la prueba default.
der
Analiza el archivo como un archivo de Certificado DER. El campo de prueba se utiliza como un tipo DER que necesita ser emparejado. Los tipos DER son: eoc, bool, int, bit_str, octet_str, null, obj_id, obj_desc, ext, real, enum, embed, utf8_str, rel_oid, time, res2, seq, set, num_str, prt_str, t61_str, vid_str, ia5_str, utc_time, gen_time, gr_str, vis_str, gen_str, univ_str, char_str, bmp_str, date, tod, datetime, duration, oid-iri, rel-oid-iri. Estos tipos pueden ir seguidos de un tamaño numérico opcional, que indica el ancho del campo en bytes.
guid
Un Identificador Global Único, analizado e impreso como XXXXXXXX-XXXX-XXXX-XXXX-XXXXXXXXXXXX. Su formato es una cadena.
offset
Este es un valor cuádruple que indica el offset actual del archivo. Puede utilizarse para determinar el tamaño del archivo o del búfer mágico. Por ejemplo, las entradas mágicas: 
-0	offset	x	this file is %lld bytes
-0	offset	<=100	must be more than 100 \
    bytes and is only %lld
octal
Una cadena que representa un número octal.

type
The type of the data to be compared. The following types are recognized:
“char”
A single character.
“uchar”
A single unsigned character.
“short”
A short integer.
“ushort”
A short unsigned integer.
“long”
A long integer.
“ulong”
A long unsigned integer.
“quad”
A 64-bit integer.
“uquad”
A 64-bit unsigned integer.
“float”
A single-precision floating-point number.
“double”
A double-precision floating-point number.
“date”
A date.
“regex”
A regular expression.
“search”
A string to search for.
“string”
A string.
Type specifiers may be abbreviated. The type specifiers c and C are equivalent to char, the type specifiers s and S are equivalent to short, the type specifiers d and i are equivalent to long, the type specifiers u, f, g, and a are equivalent to ulong, the type specifiers o and O are equivalent to quad, and the type specifiers e and E are equivalent to double. The type specifiers l and L are equivalent to long, the type specifiers w and W are equivalent to ushort, the type specifiers dI, dL, and d4 are equivalent to long, the type specifiers uI, uL, and u4 are equivalent to ulong, the type specifier d8 is equivalent to quad, the type specifier u8 is equivalent to uquad, and the type specifier s is equivalent to string. In addition, the type specifier dQ is equivalent to quad and the type specifier uQ is equivalent to uquad.

Each top-level magic pattern (see below for an explanation of levels) is classified as text or binary according to the types used. Types “regex” and “search” are classified as text tests, unless non-printable characters are used in the pattern. All other tests are classified as binary. A top-level pattern is considered to be a test text when all its patterns are text patterns; otherwise, it is considered to be a binary pattern. When matching a file, binary patterns are tried first; if no match is found, and the file looks like text, then its encoding is determined and the text patterns are tried.

The numeric types may optionally be followed by & and a numeric value, to specify that the value is to be AND'ed with the numeric value before any comparisons are done. Prepending a u to the type indicates that ordered comparisons should be unsigned.

test
The value to be compared with the value from the file. If the type is numeric, this value is specified in C form; if it is a string, it is specified as a C string with the usual escapes permitted (e.g. \n for new-line).

Numeric values may be preceded by a character indicating the operation to be performed. It may be =, to specify that the value from the file must equal the specified value, <, to specify that the value from the file must be less than the specified value, >, to specify that the value from the file must be greater than the specified value, &, to specify that the value from the file must have set all of the bits that are set in the specified value, ^, to specify that the value from the file must have clear any of the bits that are set in the specified value, or ~, the value specified after is negated before tested. x, to specify that any value will match. If the character is omitted, it is assumed to be =. Operators &, ^, and ~ don't work with floats and doubles. The operator ! specifies that the line matches if the test does not succeed.

Numeric values are specified in C form; e.g. 13 is decimal, 013 is octal, and 0x13 is hexadecimal.

Numeric operations are not performed on date types, instead the numeric value is interpreted as an offset.

For string values, the string from the file must match the specified string. The operators =, < and > (but not &) can be applied to strings. The length used for matching is that of the string argument in the magic file. This means that a line can match any non-empty string (usually used to then print the string), with >\0 (because all non-empty strings are greater than the empty string).

Dates are treated as numerical values in the respective internal representation.

The special test x always evaluates to true.

message
The message to be printed if the comparison succeeds. If the string contains a printf(3) format specification, the value from the file (with any specified masking performed) is printed using the message as the format string. If the string begins with “\b”, the message printed is the remainder of the string with no whitespace added before it: multiple matches are normally separated by a single space.

An APPLE 4+4 character APPLE creator and type can be specified as:

!:apple	CREATYPE

A slash-separated list of commonly found filename extensions can be specified as:

!:ext	ext[/ext...]

i.e. the literal string “!:ext” followed by a slash-separated list of commonly found extensions; for example for JPEG images:

!:ext jpeg/jpg/jpe/jfif

A MIME type is given on a separate line, which must be the next non-blank or comment line after the magic line that identifies the file type, and has the following format:

!:mime	MIMETYPE

i.e. the literal string “!:mime” followed by the MIME type.

An optional strength can be supplied on a separate line which refers to the current magic description using the following format:

!:strength OP VALUE

The operand OP can be: +, -, *, or / and VALUE is a constant between 0 and 255. This constant is applied using the specified operand to the currently computed default magic strength.

Some file formats contain additional information which is to be printed along with the file type or need additional tests to determine the true file type. These additional tests are introduced by one or more > characters preceding the offset. The number of > on the line indicates the level of the test; a line with no > at the beginning is considered to be at level 0. Tests are arranged in a tree-like hierarchy: if the test on a line at level n succeeds, all following tests at level n+1 are performed, and the messages printed if the tests succeed, until a line with level n (or less) appears. For more complex files, one can use empty messages to get just the "if/then" effect, in the following way:

0      string    MZ
>0x18  uleshort  <0x40   MS-DOS executable
>0x18  uleshort  >0x3f   extended PC executable (e.g., MS Windows)

Offsets do not need to be constant, but can also be read from the file being examined. If the first character following the last > is a ( then the string after the parenthesis is interpreted as an indirect offset. That means that the number after the parenthesis is used as an offset in the file. The value at that offset is read, and is used again as an offset in the file. Indirect offsets are of the form: (x [[.,][bBcCeEfFgGhHiIlmosSqQ]][+-][ y ]). The value of x is used as an offset in the file. A byte, id3 length, short or long is read at that offset depending on the [bBcCeEfFgGhHiIlLmsSqQ] type specifier. The value is treated as signed if “,” is specified or unsigned if “.” is specified. The capitalized types interpret the number as a big endian value, whereas the small letter versions interpret the number as a little endian value; the m type interprets the number as a middle endian (PDP-11) value. To that number the value of y is added and the result is used as an offset in the file. The default type if one is not specified is long. The following types are recognized:

Type Sy Mnemonic Sy Endian Sy Size
bcBC Byte/Char N/A 1
efg Double Little 8
EFG Double Big 8
hs Half/Short Little 2
HS Half/Short Big 2
i ID3 Little 4
I ID3 Big 4
l Long Little 4
L Long Big 4
m Middle Middle 4
o Octal Textual Variable
q Quad Little 8
Q Quad Big 8

That way variable length structures can be examined:

# MS Windows executables are also valid MS-DOS executables
0           string   MZ
>0x18       uleshort <0x40  MZ executable (MS-DOS)
# skip the whole block below if it is not an extended executable
>0x18       uleshort >0x3f
>>(0x3c.l)  string   PE\0\0 PE executable (MS-Windows)
>>(0x3c.l)  string   LX\0\0 LX executable (OS/2)

This strategy of examining has a drawback: you must make sure that you eventually print something, or users may get empty output (such as when there is neither PE\0\0 nor LE\0\0 in the above example).

If this indirect offset cannot be used directly, simple calculations are possible: appending [+-*/%&|^]number to the indirect offset will cause the result of the indirect offset calculation to be modified by the given number before it is used as an offset.

DESCRIPCIÓN

Los corchetes dentro de los paréntesis permiten modificar el valor leído del archivo antes de que se utilice como desplazamiento:

# Los ejecutables de MS Windows también son ejecutables válidos de MS-DOS
0           cadena   MZ
# a veces, el valor en 0x18 es menor que 0x40 pero todavía hay un
# ejecutable extendido, simplemente se añade al archivo
>0x18       uleshort <0x40
>>(4.s*512) leshort  0x014c  ejecutable COFF (MS-DOS, DJGPP)
>>(4.s*512) leshort  !0x014c ejecutable MZ (MS-DOS)

A veces no se conoce el desplazamiento exacto, ya que esto depende de la longitud o posición (cuando se utilizó la indirección antes) de los campos precedentes. Se puede especificar un desplazamiento relativo al final del último campo de nivel superior usando el carácter «&» como prefijo del desplazamiento:

0           cadena   MZ
>0x18       uleshort >0x3f
>>(0x3c.l)  cadena   PE\0\0    ejecutable PE (MS-Windows)
# inmediatamente después de la firma PE se encuentra el tipo de CPU
>>>&0       leshort  0x14c     para Intel 80386
>>>&0       leshort  0x8664    para x86-64
>>>&0       leshort  0x184     para DEC Alpha

Los desplazamientos indirectos y relativos se pueden combinar:

0             cadena   MZ
>0x18         uleshort <0x40
>>(4.s*512)   leshort  !0x014c ejecutable MZ (MS-DOS)
# si no es COFF, retrocede 512 bytes y suma el desplazamiento tomado
# de los bytes 2/3, que es otra forma de encontrar el inicio
# del ejecutable extendido
>>>&(2.s-514) cadena   LE      ejecutable LE (controlador VxD de MS Windows)

O al revés:

0                 cadena   MZ
>0x18             uleshort >0x3f
>>(0x3c.l)        cadena   LE\0\0  ejecutable LE (MS-Windows)
# en el desplazamiento 0x80 (-4, ya que los desplazamientos relativos comienzan al final
# de la coincidencia del nivel superior) dentro de la cabecera LE, encontramos el desplazamiento
# absoluto al área de código, donde buscamos una firma específica
>>>(&0x7c.l+0x26) cadena   UPX     \b, comprimido con UPX

¡O incluso ambos!

0                cadena   MZ
>0x18            uleshort >0x3f
>>(0x3c.l)       cadena   LE\0\0 LE ejecutable (MS-Windows)
# en el desplazamiento 0x58 dentro de la cabecera LE, encontramos el desplazamiento relativo
# a un área de datos donde buscamos una firma específica
>>>&(&0x54.l-3)  cadena   UNACE  \b, archivo autorreparable ACE

Si tiene que tratar con pares de desplazamiento/longitud en su archivo, incluso el segundo valor en una expresión entre paréntesis se puede tomar del archivo en sí, utilizando otro conjunto de paréntesis. Tenga en cuenta que este desplazamiento indirecto adicional siempre es relativo al inicio del desplazamiento indirecto principal.

0                 cadena       MZ
>0x18             uleshort     >0x3f
>>(0x3c.l)        cadena       PE\0\0 PE ejecutable (MS-Windows)
# busca la sección PE llamada ".idata"...
>>>&0xf4          buscar/0x140 .idata
# ...y ve al final de ella, calculado desde inicio+longitud;
# estos se encuentran a 14 y 10 bytes después del nombre de la sección
>>>>(&0xe.l+(-4)) cadena       PK\3\4 \b, archivo autorreparable ZIP

Si tiene una lista de valores conocidos en un nivel de continuación particular y desea proporcionar un caso predeterminado tipo switch:

# limpia la coincidencia de ese nivel de continuación
>18	limpiar	x
>18	lelong	1	uno
>18	lelong	2	dos
>18	predeterminado	x
# imprime la coincidencia predeterminada
>>18	lelong	x	no coincidente 0x%x

ERRORES

Los formatos long, belong, lelong, melong, short, beshort y leshort no dependen de la longitud de los tipos de datos C short y long en la plataforma, aunque la especificación Single UNIX implica que sí lo hacen. Sin embargo, dado que OS X Mountain Lion ha pasado el conjunto de validación de la especificación Single UNIX y proporciona una versión de file(1) en la que no dependen de los tamaños de los tipos de datos C y que está compilado para un entorno de 64 bits en el que long tiene 8 bytes en lugar de 4, es de suponer que el conjunto de validación no comprueba si, por ejemplo, long se refiere a un elemento del mismo tamaño que el tipo de dato C long. Probablemente debería haber nombres de tipo int8, uint8, int16, uint16, int32, uint32, int64 y uint64, y variantes de orden de bytes especificado de ellos, para que quede más claro que esos tipos tienen anchos especificados.
