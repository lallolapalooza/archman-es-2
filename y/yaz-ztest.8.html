YAZ-ZTEST(8) Comandos de gestión del sistema YAZ-ZTEST(8)

NOMBRE

yaz-ztest - Servidor de prueba Z39.50/SRU

SINOPSIS

aplicacion [-install] [-installa] [-remove] [-a archivo] [-v nivel] [-l archivo] [-u uid] [-c config] [-f vconfig] [-C fname] [-t minutos] [-k kilobytes] [-K] [-d daemon] [-w dir] [-p pidfile] [-r kilobytes] [-ziDSTV1] [especificador-listener...]

DESCRIPCIÓN

yaz-ztest es un servidor de prueba Z39.50/SRU que utiliza la API de YAZ generic front-end server (GFS). El servidor actúa como un servidor Z39.50/SRU real pero no utiliza una base de datos. Devuelve un recuento aleatorio de resultados y devuelve un subconjunto de algunos registros integrados.

El especificador-listener consta de un modo de transporte seguido de dos puntos, seguido de una dirección de escucha. El modo de transporte es tcp, unix o ssl.

Para TCP y SSL, una dirección tiene el formato:

    hostname | número-IP [ : numeropuerto ]

Para el socket local UNIX, la dirección es el nombre del archivo del socket local.

OPCIONES

-a archivo

Especifica un archivo para volcar PDUs (con fines de diagnóstico). El nombre especial - (guión) envía la salida a stderr.

-S

No bifurcar ni crear hilos para las solicitudes de conexión. Esto es bueno para la depuración, pero no se recomienda para operaciones reales: aunque el servidor es asíncrono y no bloqueante, puede ser útil evitar que un mal funcionamiento del software (bueno, una caída) afecte a todos los usuarios actuales.

-1

Como -S pero después de una sesión el servidor sale. Este modo es *solo* para depuración.

-T

Ejecuta el servidor en modo multihilo. El servidor crea un hilo para cada conexión en lugar de bifurcar un proceso. Solo disponible en sistemas UNIX que ofrecen hilos POSIX.

-s

Utiliza el protocolo SR (obsoleto).

-z

Utiliza el protocolo Z39.50 (por defecto). Esta opción y -s se complementan. Puedes usar ambas varias veces en la misma línea de comandos, entre los especificadores de listener (ver más abajo). De esta manera, puedes configurar el servidor para escuchar conexiones en ambos protocolos simultáneamente, en diferentes puertos locales.

-l archivo

El archivo de registro.

-c config

Una opción de usuario que sirve como especificador para algún tipo de configuración, generalmente un nombre de archivo. El argumento de esta opción se transfiere al miembro configname del bloque statserv_options_block.

-f vconfig

Especifica un archivo XML que describe uno o más servidores virtuales front-end de YAZ.

-C fname

Establece el nombre del archivo de certificado SSL para el servidor (PEM).

-v nivel

El nivel de registro. Usa una lista separada por comas de los miembros del conjunto {fatal,debug,warn,log,malloc,all,none}.

-u uid

Establece el ID de usuario. Establece el UID real del proceso servidor al del usuario dado. Es útil si no te sientes cómodo con que el servidor se ejecute como root, pero necesitas iniciarlo como tal para vincular un puerto privilegiado.

-w dir

El servidor cambia a este directorio antes de escuchar las conexiones entrantes. Esta opción es útil cuando el servidor opera desde el demonio inetd (ver -i).

-p pidfile

Especifica que el servidor debe escribir su ID de Proceso en el archivo dado por pidfile. Una ubicación típica sería /var/run/yaz-ztest.pid.

-i

Utiliza esto para que el servidor se ejecute desde el servidor inetd (solo UNIX).

-D

Utiliza esto para que el servidor se ponga en segundo plano y se ejecute como un demonio. Si no se da ni -i ni -D, el servidor se inicia en primer plano.

-install

Utiliza esto para instalar el servidor como un servicio NT (solo Windows NT/2000/XP). Controla el servidor yendo a Servicios en el Panel de Control.

-installa

Utiliza esto para instalar el servidor como un servicio NT y marcarlo como "inicio automático". Controla el servidor yendo a Servicios en el Panel de Control.

-remove

Utiliza esto para eliminar el servidor de los servicios NT (solo Windows NT/2000/XP).

-t minutos

Tiempo de espera de sesión inactiva, en minutos.

-k tamaño

Tamaño máximo de registro/mensaje, en kilobytes.

-K

Fuerza no-keepalive para sesiones HTTP. Por defecto, GFS mantendrá las sesiones activas para sesiones HTTP 1.1 (según lo definido por el estándar). Usar esta opción forzará a GFS a cerrar la conexión para cada operación.

-r tamaño

Tamaño máximo del archivo de registro antes de que ocurra una rotación, en kilobytes. El tamaño por defecto es 1048576 k (=1 GB).

-d daemon

Establece el nombre del demonio a usar en el archivo de acceso a hosts. Ver hosts_access(5) y tcpd(8).

-m formato-hora

Establece el formato de las marcas de tiempo en el archivo de registro. Especifica una cadena en el formato de entrada para strftime().

-V

Muestra la versión de YAZ y sale.

PRUEBAS

yaz-ztest normalmente devuelve un recuento aleatorio de resultados entre 0 y 24. Sin embargo, si un término de consulta incluye dígitos iniciales, el valor entero de ese término se utiliza como recuento de resultados. Esto permite a los probadores devolver cualquier número de resultados. yaz-ztest incluye 24 registros MARC para pruebas. Los recuentos de resultados que excedan 24 harán que yaz-ztest devuelva el mismo lote de registros una y otra vez. Por lo tanto, el registro en la posición 1, 25, 49, etc., son equivalentes.

Para XML, si no se proporciona un conjunto de elementos o el conjunto de elementos tiene el valor "marcxml", se devuelve MARCXML (cada uno de los 24 registros ficticios convertidos de ISO2709 a XML). Para el conjunto de elementos OP, se devuelve OPAC XML.

yaz-ztest también puede devolver registros XML predefinidos (para pruebas). Esto se habilita si la variable de entorno YAZ_ZTEST_XML_FETCH está definida. Se recupera un registro de un archivo (un registro por archivo). La ruta para el nombre del archivo es FE.d.xml donde F es el valor de YAZ_ZTEST_XML_FETCH (posiblemente vacío), E es el conjunto de elementos, d es la posición del registro (comenzando desde 1).

Las siguientes bases de datos son honradas por yaz-ztest: Default, slow y db.* (todas las bases de datos con prefijo "db"). Cualquier otra base de datos hará que yaz-ztest devuelva el diagnóstico 109: "Base de datos no disponible".

Las opciones de búsqueda pueden incluirse en los argumentos GET de la forma o URL incluidos como parte del nombre de la base de datos Z39.50. Las siguientes opciones de base de datos están presentes: search-delay, present-delay, fetch-delay y seed.

Las opciones anteriores, tipos de retardo, especifican un retardo falso (sleep) que yaz-ztest realizará al buscar, presentar y recuperar registros respectivamente. El valor del retardo puede ser un valor flotante fijo que especifica el retardo en segundos. Alternativamente, el valor puede darse como dos números flotantes separados por dos puntos, lo que hará que yaz-ztest realice un sueño aleatorio entre el primer y el segundo número.

El parámetro de base de datos seed toma un entero como valor. Esto llamará a srand con este entero para asegurar que el comportamiento aleatorio pueda ser reproducido.

Supongamos que queremos que las búsquedas tarden entre 0.1 y 0.5 segundos y una recuperación tarde 0.2 segundos. Para acceder a la base de datos de prueba Default, usaríamos: Default?search-delay=0.1:0.5&fetch-delay=0.2.

CONFIGURACIÓN GFS Y HOSTS VIRTUALES

El mecanismo de hosts virtuales permite que un servidor front-end YAZ soporte múltiples back-ends. Un back-end se selecciona basándose en la vinculación TCP/IP (puerto+dirección de escucha) y/o el host virtual.

Un back-end puede configurarse para ejecutarse en un directorio de trabajo particular. O el front-end YAZ puede realizar la conversión de CQL a RPN, permitiendo así que las bases de datos Z39.50 tradicionales

GFS CONFIGURATION AND VIRTUAL HOSTS

The YAZ GFS (Generic Frontend Server) is used to proxy requests to one or more backend servers. This is done by configuring the GFS using an XML configuration file. The configuration specifies how the GFS listens for incoming connections and which backend servers it routes requests to.

The GFS can act as an SRW/SRU server. In this context, it can receive requests targeted at a specific virtual host and route them to the appropriate backend server. The virtual host can be specified in several ways:

  • For the HTTP protocol, the virtual host is specified in the Host header.
  • For the Z39.50 protocol, the virtual host is specified in the Initialize Request within the OtherInfo element, using OID 1.2.840.10003.10.1000.81.1.

Information for a particular back-end, when offered as an SRW/SRU service, may also be specified.


Note

Not all Z39.50 clients allow the VHOST information to be set. For those, the selection of the back-end must rely on the TCP/IP information alone (port and address).

The YAZ front-end server uses XML to describe the back-end configurations. Command-line option -f specifies the filename of the XML configuration.

The configuration uses the root element yazgfs. This element includes a list of listen elements, followed by one or more server elements.

The listen element describes a listener (transport endpoint), such as TCP/IP, Unix file socket, or SSL server. Content for a listener:

CDATA (required)

The CDATA for the listen element holds the listener string, such as tcp:@:210, tcp:server1:2100, etc.

attribute id (optional)

Identifier for this listener. This may be referred to from server sections.

Note

We expect more information to be added for the listen section in a future version, such as CERT file for SSL servers.

The server element describes a server and the parameters for this server type. Content for a server:

attribute id (optional)

Identifier for this server. Currently not used for anything, but it might be for logging purposes.

attribute listenref (optional)

Specifies one or more listeners for this server. Each listener ID is separated by a comma. If this attribute is not given, the server is accessible from all listeners. In order for the server to be used for real, however, the virtual host must match if specified in the configuration.

element config (optional)

Specifies the server configuration. This is equivalent to the configuration specified using command line option -c.

element directory (optional)

Specifies a working directory for this backend server. If specified, the YAZ frontend changes the current working directory to this directory whenever a backend of this type is started (backend handler bend_start), stopped (backend handler hand_stop), and initialized (bend_init).

element host (optional)

Specifies the virtual host for this server. If this is specified, a client *must* specify this host string in order to use this backend.

element cql2rpn (optional)

Specifies a filename that includes CQL to RPN conversion for this backend server. See ???. If given, the backend server will only "see" a Type-1/RPN query.

element ccl2rpn (optional)

Specifies a filename that includes CCL to RPN conversion for this backend server. See ???. If given, the backend server will only "see" a Type-1/RPN query.

element stylesheet (optional)

Specifies the stylesheet reference to be part of SRU HTTP responses when the client does not specify one. If none is given, then if the client does not specify one, then no stylesheet reference is part of the SRU HTTP response.

element client_query_charset (optional)

If specified, a conversion from the character set given to UTF-8 is performed by the generic frontend server. It is only executed for Z39.50 search requests (SRU/Solr are assumed to be UTF-8 encoded already).

element docpath (optional)

Specifies a path for local file access using HTTP. All URLs with a leading prefix (/ excluded) that matches the value of docpath are used for file access. For example, if the server is to offer access in directory xsl, the docpath would be xsl and all URLs of the form http://host/xsl will result in a local file access.

element explain (optional)

Specifies SRW/SRU ZeeRex content for this server. Copied verbatim to the client. As things are now, some of the Explain content seem redundant because host information, etc. is also stored elsewhere.

element maximumrecordsize (optional)

Specifies maximum record size/message size, in bytes. This value also serves as the maximum size of *incoming* packages (for Record Updates etc). It's the same value as that given by the -k option.

element retrievalinfo (optional)

Enables the retrieval facility to support conversions and specifications of record formats/types. See ??? for more information.

The XML below configures a server that accepts connections from two ports, TCP/IP port 9900 and a local UNIX file socket. We name the TCP/IP server public and the other server internal.

 <yazgfs>
  <listen id="public">tcp:@:9900</listen>
  <listen id="internal">unix:/var/tmp/socket</listen>
  <server id="server1">
    <host>server1.mydomain</host>
    <directory>/var/www/s1</directory>
    <config>config.cfg</config>
  </server>
  <server id="server2" listenref="public,internal">
    <host>server2.mydomain</host>
    <directory>/var/www/s2</directory>
    <config>config.cfg</config>
    <cql2rpn>../etc/pqf.properties</cql2rpn>
    <explain xmlns="http://explain.z3950.org/dtd/2.0/">
      <serverInfo>
        <host>server2.mydomain</host>
        <port>9900</port>
        <database>a</database>
      </serverInfo>
    </explain>
  </server>
  <server id="server3" listenref="internal">
    <directory>/var/www/s3</directory>
    <config>config.cfg</config>
  </server>
 </yazgfs>

There are three configured backend servers. The first two servers, "server1" and "server2", can be reached by both listener addresses. "server1" is reached by all (two) since no listenref attribute is specified. "server2" is reached by the two listeners specified. In order to distinguish between the two, a virtual host has been specified for each server in the host elements.

For "server2", elements for CQL to RPN conversion is supported and explain information has been added (a short one here to keep the example small).

The third server, "server3", can only be reached via listener "internal".
