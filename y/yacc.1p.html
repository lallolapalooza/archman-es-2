YACC(1P) Manual del programador POSIX YACC(1P)

PROLOG

Esta página del manual forma parte del Manual del programador POSIX. La implementación de esta interfaz en Linux puede diferir (consulte la página del manual de Linux correspondiente para obtener detalles sobre el comportamiento en Linux), o la interfaz puede no estar implementada en Linux.

NOMBRE

yacc — otro compilador de compiladores (DESARROLLO)

SINÓPSIS

yacc [-dltv] [-b prefijo_archivo] [-p prefijo_sym] gramática

DESCRIPCIÓN

La utilidad yacc leerá una descripción de una gramática libre de contexto en gramática y escribirá código fuente C, que cumpla con el estándar ISO C, en un archivo de código y, opcionalmente, información de cabecera en un archivo de cabecera, en el directorio actual. El código fuente generado no dependerá de ningún comportamiento indefinido, no especificado o definido por la implementación, excepto en los casos en que se copie directamente de la gramática proporcionada, o en casos que estén documentados por la implementación. El código C definirá una función y rutinas y macros relacionadas para un autómata que ejecuta un algoritmo de análisis sintáctico que cumple con los requisitos de Algoritmos.

La forma y el significado de la gramática se describen en la sección EXTENDED DESCRIPTION.

El código fuente C y el archivo de cabecera se producirán en un formato adecuado como entrada para el compilador C (consulte c99).

OPCIONES

La utilidad yacc cumplirá con el volumen de Definiciones Base de POSIX.1‐2017, Sección 12.2, Directrices de Sintaxis de Utilidades, excepto por la Directriz 9.

Las siguientes opciones serán compatibles:

-b prefijo_archivo
Utilice prefijo_archivo en lugar de y como prefijo para todos los nombres de archivo de salida. El archivo de código y.tab.c, el archivo de cabecera y.tab.h (creado cuando se especifica -d) y el archivo de descripción y.output (creado cuando se especifica -v), se cambiarán a prefijo_archivo.tab.c, prefijo_archivo.tab.h y prefijo_archivo.output, respectivamente.
-d
Escribir el archivo de cabecera; por defecto, solo se escribe el archivo de código. Consulte la sección ARCHIVOS DE SALIDA.
-l
Producir un archivo de código que no contenga construcciones #line. Si esta opción no está presente, no se especifica si el archivo de código o el archivo de cabecera contienen directivas #line. Esto solo debe usarse después de que la gramática y las acciones asociadas se hayan depurado completamente.
-p prefijo_sym

Utilice prefijo_sym en lugar de yy como prefijo para todos los nombres externos producidos por yacc. Los nombres afectados incluirán las funciones yyparse(), yylex() y yyerror(), y las variables yylval, yychar y yydebug. (En el resto de esta sección, los seis símbolos citados se referencian solo con sus nombres predeterminados como conveniencia notacional.) Los nombres locales también pueden verse afectados por la opción -p; sin embargo, la opción -p no afectará a los símbolos #define generados por yacc.
-t
Modificar las directivas de compilación condicional para permitir la compilación de código de depuración en el archivo de código. Las declaraciones de depuración en tiempo de ejecución siempre estarán contenidas en el archivo de código, pero por defecto, las directivas de compilación condicional impiden su compilación.
-v
Escribir un archivo que contenga una descripción del analizador y un informe de conflictos generados por ambigüedades en la gramática.

OPERANDOS

Se requiere el siguiente operando:

gramática
Un nombre de ruta de un archivo que contiene instrucciones, en adelante llamadas gramática, para las cuales se creará un analizador. El formato de la gramática se describe en la sección EXTENDED DESCRIPTION.

STDIN

No se utiliza.

ARCHIVOS DE ENTRADA

El archivo gramática será un archivo de texto formateado según lo especificado en la sección EXTENDED DESCRIPTION.

VARIABLES DE ENTORNO

Las siguientes variables de entorno afectarán la ejecución de yacc:

LANG
Proporcionar un valor predeterminado para las variables de internacionalización que no están establecidas o están vacías. (Consulte el volumen de Definiciones Base de POSIX.1‐2017, Sección 8.2, Variables de Internacionalización para conocer la precedencia de las variables de internacionalización utilizadas para determinar los valores de las categorías de localización).
LC_ALL
Si se establece en un valor de cadena no vacío, anulará los valores de todas las demás variables de internacionalización.
LC_CTYPE
Determinar la localización para la interpretación de secuencias de bytes de datos de texto como caracteres (por ejemplo, caracteres de un solo byte en comparación con caracteres multibyte en argumentos y archivos de entrada).
LC_MESSAGES

Determinar la localización que debe utilizarse para afectar el formato y el contenido de los mensajes de diagnóstico escritos en el error estándar.
NLSPATH
Determinar la ubicación de los catálogos de mensajes para el procesamiento de LC_MESSAGES.

Las variables LANG y LC_* afectan la ejecución de la utilidad yacc según lo indicado. La función main() definida en la Biblioteca Yacc llamará:

setlocale(LC_ALL, "")

y por lo tanto, el programa generado por yacc también se verá afectado por el contenido de estas variables en tiempo de ejecución.

EVENTOS ASÍNCRONOS

Predeterminado.

STDOUT

No se utiliza.

STDERR

Si se detectan conflictos de desplazamiento/reducción o reducción/reducción en gramática, yacc escribirá un informe de esos conflictos en el error estándar en un formato no especificado.

El error estándar también se utilizará para mensajes de diagnóstico.

ARCHIVOS DE SALIDA

El archivo de código, el archivo de cabecera y el archivo de descripción serán archivos de texto. Todos se describen en las siguientes secciones.

Archivo de Código

Este archivo contendrá el código fuente C para la función yyparse(). Contendrá código para las diversas acciones semánticas con la sustitución de macros realizada sobre ellas como se describe en la sección EXTENDED DESCRIPTION. También contendrá una copia de las declaraciones #define en el archivo de cabecera. Si se utiliza una declaración %union, la declaración para YYSTYPE también se incluirá en este archivo.

Archivo de Cabecera

El archivo de cabecera contendrá declaraciones #define que asociarán los números de token con los nombres de token. Esto permite que los archivos fuente distintos del archivo de código accedan a los códigos de token. Si se utiliza una declaración %union, la declaración para YYSTYPE y una declaración extern YYSTYPE yylval también se incluirán en este archivo.

Archivo de Descripción

El archivo de descripción será un archivo de texto que contenga una descripción de la máquina de estados correspondiente al analizador, utilizando un formato no especificado.

Este sitio no está asociado de ninguna forma con Arch Linux ni afiliado a este proyecto. El contenido es únicamente una traducción de las páginas del manual de Arch publicadas en man.archlinux.org.

LIMITS

Los límites para las tablas internas (ver Limits) también deberán ser informados, de manera definida por la implementación. (Algunas implementaciones pueden usar técnicas de asignación dinámica y no tener valores límite específicos para informar.)

DESCRIPCIÓN EXTENDIDA

El comando yacc acepta un lenguaje que se utiliza para definir una gramática para un lenguaje de destino que será analizado por las tablas y el código generado por yacc. El lenguaje aceptado por yacc como gramática para el lenguaje de destino se describe a continuación utilizando el propio lenguaje de entrada de yacc.

La gramática de entrada incluye reglas que describen la estructura de entrada del lenguaje de destino y el código que se invocará cuando se reconozcan estas reglas para proporcionar la acción semántica asociada. El código que se ejecutará aparecerá como cuerpos de texto que se pretende que sean código en lenguaje C. Estos cuerpos de texto no contendrán trigrafos en lenguaje C. Se presume que las inclusiones en lenguaje C forman una función correcta cuando yacc las procesa en sus archivos de salida. El código incluido de esta manera se ejecutará durante el reconocimiento del lenguaje de destino.

Dada una gramática, la utilidad yacc genera los archivos descritos en la sección ARCHIVOS DE SALIDA. El archivo de código puede compilarse y enlazarse utilizando c99. Si las secciones de declaración y programas del archivo de gramática no incluyeron definiciones de main(), yylex() y yyerror(), la salida compilada requiere enlazarse con versiones suministradas externamente de esas funciones. Versiones predeterminadas de main() y yyerror() se suministran en la biblioteca yacc y pueden enlazarse utilizando el operando -l y para c99. Las interfaces de la biblioteca yacc no necesitan admitir interfaces con prefijos de símbolo yy distintos de los predeterminados. La aplicación proporciona la función analizador léxico, yylex(); la utilidad lex está diseñada específicamente para generar dicha rutina.

Lenguaje de Entrada

La aplicación garantizará que cada archivo de especificación conste de tres secciones en orden: declaraciones, reglas de gramática y programas, separadas por caracteres de doble signo de porcentaje ("%%"). Las secciones de declaraciones y programas pueden estar vacías. Si esta última está vacía, la marca "%%" precedente que la separa de la sección de reglas puede omitirse.

La entrada es texto de formato libre que sigue la estructura de la gramática definida a continuación.

Estructura Léxica de la Gramática

El carácter de espacio en blanco (<blank>), nueva línea (<newline>) y salto de página (<form-feed>) se ignorarán, excepto que la aplicación garantizará que no aparezcan en nombres o símbolos reservados de varios caracteres. Los comentarios se encerrarán entre "/* ... */" y pueden aparecer donde sea válido un nombre.

Los nombres son de longitud arbitraria, compuestos por letras, puntos ('.'), guiones bajos ('_') y dígitos no iniciales. Las letras mayúsculas y minúsculas son distintas. Las aplicaciones conformes no deben usar nombres que comiencen con yy o YY ya que el analizador yacc utiliza dichos nombres. Muchos de los nombres aparecen en la salida final de yacc y, por lo tanto, deben elegirse para cumplir con cualquier regla adicional creada por el compilador C que se vaya a utilizar. En particular, aparecen en las declaraciones #define.

Un literal consistirá en un solo carácter encerrado entre caracteres de comilla simple. Todas las secuencias de escape admitidas para constantes de caracteres por el estándar ISO C serán admitidas por yacc.

La relación con el analizador léxico se discute en detalle a continuación.

La aplicación garantizará que el carácter NUL no se utilice en reglas de gramática o literales.

Sección de Declaraciones

La sección de declaraciones se utiliza para definir los símbolos utilizados para definir el lenguaje de destino y su relación entre sí. En particular, aquí se proporciona mucha de la información adicional necesaria para resolver ambigüedades en la gramática libre de contexto para el lenguaje de destino.

Por lo general, yacc asigna la relación entre los nombres simbólicos que genera y sus valores numéricos subyacentes. La sección de declaraciones permite controlar la asignación de estos valores.

También es posible mantener información semántica asociada con los tokens actualmente en la pila de análisis en una union de lenguaje C definida por el usuario, si los miembros de la unión están asociados con los diversos nombres en la gramática. La sección de declaraciones también lo permite.

Los primeros declaradores a continuación toman todos una lista de nombres como argumentos. Esa lista puede ir precedida opcionalmente por el nombre de un miembro de unión C (llamado una etiqueta o tag a continuación) que aparece entre '<' y '>'. (Como excepción a las convenciones tipográficas del resto de este volumen de POSIX.1‐2017, en este caso <tag> no representa una metavariable, sino los caracteres de corchete literal que rodean un símbolo.) El uso de la etiqueta tag especifica que los tokens nombrados en esta línea serán del mismo tipo C que el miembro de unión al que hace referencia la etiqueta tag. Esto se discute con más detalle a continuación.

Para las listas utilizadas para definir tokens, la primera aparición de un token dado puede ir seguida de un entero positivo (como una cadena de dígitos decimales). Si se hace esto, el valor subyacente asignado a él con fines léxicos se tomará como ese número.

Lo siguiente declara name como un token:

%token [<tag>] name [number] [name [number]]...

Si la etiqueta tag está presente, el tipo C para todos los tokens en esta línea se declarará como el tipo al que hace referencia la etiqueta tag. Si es un entero positivo, number, el valor se asignará al token.

Lo siguiente declara name como un token y le asigna precedencia:

%left [<tag>] name [number] [name [number]]...
%right [<tag>] name [number] [name [number]]...

Puede aparecer una o más líneas en esta sección, cada una comenzando con uno de estos símbolos. Todos los tokens en la misma línea tienen el mismo nivel de precedencia y asociatividad; las líneas están en orden de precedencia creciente o fuerza de enlace. %left denota que los operadores en esa línea son asociativos por la izquierda, y %right denota de manera similar operadores asociativos por la derecha. Si la etiqueta tag está presente, declarará un tipo C para los names como se describe para %token.

Lo siguiente declara name como un token e indica que no se puede usar asociativamente:

%nonassoc [<tag>] name [number] [name [number]]...

Si el analizador encuentra un uso asociativo de este token, informa un error. Si la etiqueta tag está presente, declarará un tipo C para los names como se describe para %token.

Lo siguiente declara que los miembros de la unión names son no terminales, y por lo tanto se requiere que tengan un campo de etiqueta tag al principio:

%type <tag> name...

Debido a que trata solo con no terminales, la asignación de un número de token o el uso de un literal también están prohibidos. Si esta construcción está presente, yacc realizará la verificación de tipos; si esta construcción no está presente, la pila de análisis contendrá solo el tipo int.

Cada nombre utilizado en la gramática que no esté definido por una declaración %token, %left, %right o %nonassoc se asume que representa un símbolo no terminal. La utilidad yacc informará un error para cualquier símbolo no terminal que no aparezca en el lado izquierdo de al menos una regla gramatical.

Una vez que se especifica el tipo, la precedencia o el número de token de un nombre, no se puede cambiar. Si la primera declaración de un token no asigna un número de token, yacc asignará un número de token. Una vez realizada esta asignación, el número de token no se cambiará mediante asignación explícita.

Los siguientes declaradores no siguen el patrón anterior.

Lo siguiente declara el no terminal name como el símbolo de inicio, que representa la estructura más grande y general descrita por las reglas gramaticales:

%start name

Por defecto, es el lado izquierdo de la primera regla gramatical; este valor predeterminado puede ser anulado con esta declaración.

Lo siguiente declara que la pila de valores de yacc es una unión de los diversos tipos de valores deseados.

%union { cuerpo de la unión (en C) }

El cuerpo de la unión no contendrá tokens de preprocesamiento de llaves desequilibradas.

Por defecto, los valores devueltos por las acciones (ver más abajo) y el analizador léxico serán de tipo int. La utilidad yacc realiza un seguimiento de los tipos e insertará nombres de miembros de unión correspondientes para realizar una verificación estricta de tipos del analizador resultante.

Alternativamente, dado que se utiliza al menos una construcción de <tag>, la unión puede declararse en un archivo de encabezado (que debe incluirse en la sección de declaraciones utilizando una construcción #include dentro de %{ y %}), y se utiliza un typedef para definir el símbolo YYSTYPE para representar esta unión. El efecto de %union es proporcionar la declaración de YYSTYPE directamente desde la entrada de yacc.

Se pueden incluir declaraciones y definiciones en lenguaje C en la sección de declaraciones, encerradas por las siguientes marcas:

%{ ... %}

Estas sentencias se copiarán en el archivo de código y tendrán ámbito global dentro de él para que puedan utilizarse en las secciones de reglas y programas. Las sentencias no contendrán "}%" fuera de un comentario, literal de cadena o constante de varios caracteres.

La aplicación garantizará que la sección de declaraciones esté terminada por el token %%.

Reglas de Gramática en yacc

La sección de reglas define la gramática libre de contexto que será aceptada por la función que genera yacc, y asocia con esas reglas acciones en lenguaje C y información adicional.

información de precedencia de yacc. La gramática se describe a continuación, y sigue una definición formal.

La sección de reglas está compuesta por una o más reglas de gramática. Una regla de gramática tiene la forma:

A : CUERPO ;

El símbolo A representa un nombre no terminal, y CUERPO representa una secuencia de cero o más nombres, literales y acción semánticas que luego pueden ser seguidos por reglas de precedencia opcionales. Solo los nombres y los literales participan en la formación de la gramática; las acciones semánticas y las reglas de precedencia se utilizan de otras maneras. Los símbolos <dos puntos> y <punto y coma> son signos de puntuación de yacc. Si hay varias reglas de gramática sucesivas con el mismo lado izquierdo, la <barra vertical> ('|') se puede usar para evitar reescribir el lado izquierdo; en este caso, el <punto y coma> aparece solo después de la última regla. El CUERPO puede estar vacío (o vacío de nombres y literales) para indicar que el símbolo no terminal coincide con la cadena vacía.

La utilidad yacc asigna un número único a cada regla. Las reglas que usan la notación de barra vertical son reglas distintas. El número asignado a la regla aparece en el archivo de descripción.

Los elementos que componen un CUERPO son:

nombre, literal
Estos forman las reglas de la gramática: nombre es un token o un no terminal; literal representa sí mismo (menos las comillas requeridas léxicamente).
acción semántica

Con cada regla de gramática, el usuario puede asociar acciones que se realizarán cada vez que la regla sea reconocida en el proceso de entrada. (Nótese que la palabra ``acción'' también puede referirse a las acciones del analizador: desplazamiento, reducción, etc.).

Estas acciones pueden devolver valores y pueden obtener los valores devueltos por acciones anteriores. Estos valores se conservan en objetos de tipo YYSTYPE (ver %union). El valor de resultado de la acción se mantendrá en la pila de análisis con el lado izquierdo de la regla, para ser accedido por otras reducciones como parte de su lado derecho. Usando la información de <etiqueta> proporcionada en la sección de declaraciones, el código generado por yacc puede ser estrictamente verificado en tipo y contener información arbitraria. Además, el analizador léxico puede proporcionar el mismo tipo de valores para los tokens, si se desea.

Una acción es una sentencia C arbitraria y como tal puede realizar entrada o salida, llamar a subprogramas y alterar variables externas. Una acción consiste en una o más sentencias C encerradas entre llaves '{' y '}'. Las sentencias no deben contener tokens de preprocesamiento de llaves desbalanceados.

Ciertas pseudo-variables se pueden usar en la acción. Estas son macros para acceder a estructuras de datos conocidas internamente por yacc.

$$
El valor de la acción se puede establecer asignándolo a $$. Si la verificación de tipo está habilitada y el tipo del valor a asignar no se puede determinar, se puede generar un mensaje de diagnóstico.
$número
Esto se refiere al valor devuelto por el componente especificado por el token número en el lado derecho de una regla, leyendo de izquierda a derecha; número puede ser cero o negativo. Si número es cero o negativo, se refiere a los datos asociados con el nombre en la pila del analizador que precede al símbolo más a la izquierda de la regla actual. (Es decir, "$0" se refiere al nombre que precede inmediatamente al nombre más a la izquierda en la regla actual que se encuentra en la pila del analizador y "$-1" se refiere al símbolo a *su* izquierda.) Si número se refiere a un elemento posterior al punto actual de la regla, o más allá del fondo de la pila, el resultado no está definido. Si la verificación de tipo está habilitada y el tipo del valor a asignar no se puede determinar, se puede generar un mensaje de diagnóstico.
$<etiqueta>número

Estos corresponden exactamente a los símbolos correspondientes sin la inclusión de la etiqueta, pero permiten una verificación estricta de tipos (y excluyen conversiones de tipo no deseadas). El efecto es que la macro se expande para usar etiqueta para seleccionar un elemento de la unión YYSTYPE (usando nombre_dato.etiqueta). Esto es particularmente útil si número no es positivo.
$<etiqueta>$
Esto impone a la referencia el tipo del miembro de la unión al que se refiere la etiqueta. Esta construcción es aplicable cuando ocurre una referencia a un valor de contexto izquierdo en la gramática y proporciona a yacc un medio para seleccionar un tipo.

Las acciones pueden ocurrir en cualquier lugar de una regla (no solo al final); una acción puede acceder a los valores devueltos por acciones a su izquierda y, a su vez, el valor que devuelve puede ser accedido por acciones a su derecha. Una acción que aparece en medio de una regla será equivalente a reemplazar la acción con un nuevo símbolo no terminal y agregar una regla vacía con ese símbolo no terminal en el lado izquierdo. La acción semántica asociada con la nueva regla será equivalente a la acción original. El uso de acciones dentro de las reglas puede introducir conflictos que de otro modo no existirían.

Por defecto, el valor de una regla será el valor del primer elemento en ella. Si el primer elemento no tiene un tipo (particularmente en el caso de un literal) y la verificación de tipo está activada por %type, resultará un mensaje de error.

precedencia
La palabra clave %prec se puede usar para cambiar el nivel de precedencia asociado con una regla de gramática particular. Ejemplos de esto se encuentran en casos donde un operador unario y uno binario tienen la misma representación simbólica, pero necesitan tener diferentes precedencias, o donde es necesario el manejo de una construcción if-else ambigua. El símbolo reservado %prec puede aparecer inmediatamente después del cuerpo de la regla de gramática y puede ser seguido por un nombre de token o un literal. Causará que la precedencia de la regla de gramática sea la del siguiente nombre de token o literal. La acción para la regla en su conjunto puede seguir a %prec.

Si sigue una sección de programa, la aplicación deberá asegurarse de que las reglas de gramática estén terminadas por %%.

Sección de Programas

La sección de programas puede incluir la definición del analizador léxico yylex(), y cualquier otra función; por ejemplo, aquellas utilizadas en las acciones especificadas en las reglas de gramática. No se especifica si la sección de programas precede o sigue a las acciones semánticas en el archivo de salida; por lo tanto, si la aplicación contiene definiciones de macros y declaraciones destinadas a aplicarse al código en las acciones semánticas, deberá colocarlas dentro de "%{ ... %}" en la sección de declaraciones.

Gramática de Entrada

La siguiente entrada a yacc produce un analizador para la entrada a yacc. Esta sintaxis formal tiene precedencia sobre la descripción de sintaxis del texto anterior.

La estructura léxica se define de forma menos precisa; la Estructura Léxica de la Gramática define la mayoría de los términos. La correspondencia entre los términos anteriores y los tokens a continuación es la siguiente:

IDENTIFICADOR
Esto corresponde al concepto de nombre, dado previamente. También incluye literales como se definió previamente.
IDENTIFICADOR_C
Este es un nombre, y además se sabe que va seguido de dos puntos <dos puntos>. Un literal no puede producir este token.
NUMERO
Una cadena de dígitos (un entero decimal no negativo).
TIPO, IZQUIERDA, MARCA, LCURL, RCURL

Estos corresponden directamente a %type, %left, %%, %{ y %}.
{ ... }
Esto indica código fuente del lenguaje C, con la posible inclusión de macros '$' como se discutió previamente. 
/* Gramática para la entrada de yacc. */
/* Entradas básicas. */
/* Los siguientes son reconocidos por el analizador léxico. */
%token    IDENTIFICADOR      /* Incluye identificadores y literales */
%token    IDENTIFICADOR_C    /* identificador (pero no literal)
                             seguido de un :. */
%token    NUMERO          /* [0-9][0-9]* */
/* Palabras reservadas : %type=>TIPO %left=>IZQUIERDA, y así sucesivamente */
%token    IZQUIERDA DERECHA NOASOC TOKEN PREC TIPO INICIO UNION
%token    MARCA            /* La marca %%. */
%token    LCURL           /* La marca %. */
%token    RCURL           /* La marca %}. */
/* Los literales de caracteres de 8 bits se representan a sí mismos; */
/* los tokens deben definirse para caracteres multibyte. */
%start    especificacion
%%
especificacion  : definiciones MARCA reglas final
      ;
final  : MARCA
      {
        /* En esta acción, configurar el resto del archivo. */
      }
      | /* Vacío; la segunda MARCA es opcional. */

Conflictos

El analizador producido para una gramática de entrada puede contener estados en los que ocurren conflictos. Los conflictos ocurren porque la gramática no es LALR(1). Una gramática ambigua siempre contiene al menos un conflicto LALR(1). La utilidad yacc resolverá todos los conflictos, utilizando reglas predeterminadas o reglas de precedencia especificadas por el usuario.

Los conflictos son conflictos de desplazamiento/reducción o de reducción/reducción. Un conflicto de desplazamiento/reducción es cuando,

por un estado y símbolo de previsualización dados, tanto una acción de desplazamiento como una acción de reducción pueden ser posibles. Un conflicto de reducción/reducción es donde, para un estado y símbolo de previsualización dados, son posibles reducciones por dos reglas diferentes.

Las reglas a continuación describen cómo especificar qué acciones tomar cuando ocurre un conflicto. No todos los conflictos de desplazamiento/reducción pueden resolverse con éxito de esta manera porque el conflicto puede deberse a algo más que la ambigüedad, por lo que el uso imprudente de estas instalaciones puede hacer que el lenguaje aceptado por el analizador sea muy diferente de lo que se pretendía. El archivo de descripción contendrá información suficiente para comprender la causa del conflicto. Donde la ambigüedad sea la razón, las reglas predeterminadas o explícitas deberían ser adecuadas para producir un analizador funcional.

Las precedencias y asociatividades declaradas (ver Sección de Declaraciones) se utilizan para resolver conflictos de análisis de la siguiente manera:

1.
Se asocia una precedencia y asociatividad a cada regla gramatical; es la precedencia y asociatividad del último token o literal en el cuerpo de la regla. Si se utiliza la palabra clave %prec, anula este valor predeterminado. Algunas reglas gramaticales pueden no tener tanto precedencia como asociatividad.
2.
Si hay un conflicto de desplazamiento/reducción, y tanto la regla gramatical como el símbolo de entrada tienen precedencia y asociatividad asociadas con ellos, entonces el conflicto se resuelve a favor de la acción (desplazar o reducir) asociada con la mayor precedencia. Si las precedencias son las mismas, entonces se utiliza la asociatividad; asociativa a la izquierda implica reducción, asociativa a la derecha implica desplazamiento, y no asociativa implica un error en la cadena que se está analizando.
3.
Cuando hay un conflicto de desplazamiento/reducción que no puede resolverse según la regla 2, se realiza el desplazamiento. Los conflictos resueltos de esta manera se cuentan en la salida de diagnóstico descrita en Manejo de Errores.
4.
Cuando hay un conflicto de reducción/reducción, se realiza una reducción por la regla gramatical que ocurre antes en la secuencia de entrada. Los conflictos resueltos de esta manera se cuentan en la salida de diagnóstico descrita en Manejo de Errores.

Los conflictos resueltos por precedencia o asociatividad no se contarán en los conflictos de desplazamiento/reducción y reducción/reducción reportados por yacc en la salida de error estándar o en el archivo de descripción.

Manejo de Errores

El token error se reserva para el manejo de errores. El nombre error puede usarse en reglas gramaticales. Indica lugares donde el analizador puede recuperarse de un error de sintaxis. El valor predeterminado de error es 256. Su valor puede cambiarse usando una declaración %token. El analizador léxico no debe devolver el valor de error.

El analizador detectará un error de sintaxis cuando se encuentre en un estado donde la acción asociada con el símbolo de previsualización es error. Una acción semántica puede hacer que el analizador inicie el manejo de errores ejecutando la macro YYERROR. Cuando se ejecuta YYERROR, la acción semántica devuelve el control al analizador. YYERROR no se puede usar fuera de las acciones semánticas.

Cuando el analizador detecta un error de sintaxis, normalmente llama a yyerror() con la cadena de caracteres "syntax error" como argumento. La llamada no se realizará si el analizador aún se está recuperando de un error anterior cuando se detecta el error. El analizador se considera que se está recuperando de un error anterior hasta que el analizador haya desplazado al menos tres símbolos de entrada normales desde que se detectó el último error o una acción semántica haya ejecutado la macro yyerrok. El analizador no llamará a yyerror() cuando se ejecute YYERROR.

La macrofunción YYRECOVERING devolverá 1 si se ha detectado un error de sintaxis y el analizador aún no se ha recuperado completamente de él. De lo contrario, devolverá cero.

Cuando el analizador detecta un error de sintaxis, el analizador verificará si se detectó un error anterior. Si se detectó un error anterior, y si no se han desplazado símbolos de entrada normales desde que se detectó el error precedente, el analizador verifica si el símbolo de previsualización es un marcador de fin (ver Interfaz con el Analizador Léxico). Si lo es, el analizador devolverá un valor distinto de cero. De lo contrario, se descartará el símbolo de previsualización y se reanudará el análisis normal.

Cuando se ejecuta YYERROR o cuando el analizador detecta un error de sintaxis y no se ha detectado ningún error anterior, o se ha desplazado al menos un símbolo de entrada normal desde que se detectó el error anterior, el analizador retrocederá un estado a la vez hasta que la pila de análisis esté vacía o el estado actual permita un desplazamiento sobre error. Si el analizador vacía la pila de análisis, devolverá un valor distinto de cero. De lo contrario, desplazará sobre error y luego reanudará el análisis normal. Si el analizador lee un símbolo de previsualización antes de que se detectara el error, ese símbolo seguirá siendo el símbolo de previsualización cuando se reanude el análisis.

La macro yyerrok en una acción semántica hará que el analizador actúe como si se hubiera recuperado completamente de errores anteriores. La macro yyclearin hará que el analizador descarte el token de previsualización actual. Si el token de previsualización actual aún no ha sido leído, yyclearin no tendrá ningún efecto.

La macro YYACCEPT hará que el analizador devuelva con el valor cero. La macro YYABORT hará que el analizador devuelva con un valor distinto de cero.

Interfaz con el Analizador Léxico

La función yylex() es una función con valor entero que devuelve un número de token que representa el tipo de token leído. Si hay un valor asociado con el token devuelto por yylex() (ver la discusión de tag arriba), se asignará a la variable externa yylval.

Si el analizador y yylex() no están de acuerdo en estos números de token, no puede ocurrir una comunicación fiable entre ellos. Para literales (de un solo byte), el token es simplemente el valor numérico del carácter en el conjunto de caracteres actual. Los números para otros tokens pueden ser elegidos por yacc, o elegidos por el usuario. En cualquier caso, la construcción #define de C se utiliza para permitir que yylex() devuelva estos números simbólicamente. Las declaraciones #define se colocan en el archivo de código y en el archivo de cabecera si se solicita este último. El conjunto de caracteres permitidos por yacc en un identificador es más grande que el permitido por C. Los nombres de tokens que contengan dichos caracteres no se incluirán en las declaraciones #define.

Si los números de token son elegidos por yacc, los tokens distintos de los literales se les asignarán números mayores que 256, aunque no se implica ningún orden. Un token puede tener un número asignado explícitamente siguiendo su primera aparición en la sección de declaraciones con un número. Los nombres y literales no definidos de esta manera conservan su definición predeterminada. Todos los números de token asignados por yacc serán únicos y distintos de los números de token utilizados para literales y tokens asignados por el usuario. Si los números de token duplicados causan conflictos en la generación del analizador, yacc informará un error; de lo contrario, no se especifica si se acepta la asignación del token o si se informa un error.

El final de la entrada se marca con un token especial llamado marcador de fin, que tiene un número de token cero o negativo. (Estos valores no son válidos para ningún otro token.) Todos los analizadores léxicos devolverán un número de token cero o negativo al llegar al final de su entrada. Si los tokens hasta el marcador de fin, pero excluyéndolo, forman una estructura que coincide con el símbolo de inicio, el analizador aceptará la entrada. Si el marcador de fin se ve en cualquier otro contexto, se considerará un error.

Completando el Programa

Además de yyparse() y yylex(), las funciones yyerror() y main() se requieren para formar un programa completo. La aplicación puede proporcionar main() y yyerror(), o esas rutinas pueden obtenerse de la biblioteca de yacc.

Biblioteca Yacc

Las siguientes funciones solo aparecerán en la biblioteca de yacc accesible a través del operando -l y a c99; por lo tanto, pueden ser redefinidas por una aplicación conforme:

int main(void)

Esta función llamará a yyparse() y saldrá con un valor no especificado. Otras acciones dentro de esta función no están especificadas.
int yyerror(const char *s)

Esta función escribirá el argumento terminado en NUL en la salida de error estándar, seguido de un <nueva línea>.

El orden de los operandos -l y y -l l dados a c99 es significativo; la aplicación deberá proporcionar su propia función main() o asegurarse de que -l y preceda a -l l.

Depuración del Analizador

El analizador generado por yacc tendrá instalaciones de diagnóstico que se pueden habilitar opcionalmente en tiempo de compilación o en tiempo de ejecución (si se habilitan en tiempo de compilación). La compilación del código de depuración en tiempo de ejecución está bajo el control de YYDEBUG, un símbolo preprocesador. Si YYDEBUG tiene un valor distinto de cero, se incluirá el código de depuración. Si su valor es cero, el código no se incluirá.

En los analizadores donde se ha incluido el código de depuración, la variable externa int yydebug se puede usar para activar la depuración (con un valor distinto de cero) y desactivarla (valor cero) en tiempo de ejecución. El valor inicial de yydebug será cero.

Cuando se especifica -t, el archivo de código se construirá de tal manera que, si YYDEBUG no está ya definido en tiempo de compilación (usando la opción c99 -D YYDEBUG, por ejemplo), YYDEBUG se establecerá explícitamente a 1. Cuando no se especifica -t, el archivo de código se construirá de tal manera que, si YYDEBUG no está ya definido, se establecerá explícitamente a cero.

El formato de la salida de depuración no está especificado, pero incluye al menos suficiente información para determinar las acciones de desplazamiento y reducción, y los símbolos de entrada. También proporciona información sobre la recuperación de errores.

NAME

yacc - yet another compiler-compiler

SYNOPSIS

yacc [-bdGILlopqrstuvw] [-n MAXIMAL_REDUNDANCYMAXIMAL_RECURSION] [-S file] [-W level] [file]...

DESCRIPTION

The yacc utility automatically generates a table-driven bottom-up parsers from an annotated context-free grammar. The grammar description is read from the specified files (standard input if none are specified).

The parser produced by yacc is based on the LALR(1) parsing algorithm. It reports conflicts (shift/reduce and reduce/reduce) that are encountered during parsing table generation.

The output of yacc is a C program (the parser) written to standard output. yacc also generates a file named y.tab.c which contains the parser code.

OPTIONS

The yacc utility shall conform to the Base Definitions volume of POSIX.1‐2017, Section 12.2, Utility Syntax Guidelines.

The following options are supported by historical implementations:

-b prefix
Use prefix as the prefix for output files instead of y. The default output file is y.tab.c. If -b is used, the base name of the output file becomes prefix.tab.c.
-d
Generate a header file (y.tab.h) containing the token definitions. This file is created using the -b prefix if specified. The header file defines the token types used by the parser and the actions. It includes the definitions for YYSTYPE and the token codes.
-G
Generate code suitable for inclusion in a shared library. This is a non-standard option.
-I
Generate code that uses the ISO C standard's <setjmp.h> and <signal.h> headers for error recovery. This is a non-standard option.
-l
Do not prefix external symbols with an underscore. This is a non-standard option.
-o outfile
Write the parser C code to outfile instead of standard output. This is a non-standard option.
-p
Write the parser symbol tables to y.output.
-q
Suppress the generation of the y.output file. This is a non-standard option.
-r
Generate multiple output files for the parser tables. This is a non-standard option.
-s
Create a smaller parser by reporting conflicts and eliminating default reduction rules. This is a non-standard option.
-t
Generate debugging code in the parser. This adds runtime checks and information useful for debugging. This is a non-standard option.
-u
Allow multiple YYSTATE definitions. This is a non-standard option.
-v
Write a description of the parser's state machine to y.dot. This is a non-standard option.
-w
Suppress warnings about grammar ambiguities and conflicts. This is a non-standard option.
-n value
Set a limit on internal table sizes. The meaning of value is implementation-defined. This option is not widely supported.
-S file
Use file as the scanner (lexical analyzer) program. By default, yacc assumes the scanner is named lex.yy.c. This option is not widely supported.
-W level
Set the warning level. level can be no-warnings, all-warnings, or a specific warning group. This option is not widely supported.

OPERANDS

The following operand is supported:

file
A path to a file containing the grammar description. If multiple files are specified, they are concatenated in the order they appear.

STDIN

If no file operands are specified, the grammar description shall be read from standard input.

INPUT FILES

The input files contain an annotated context-free grammar. The grammar description consists of three sections, separated by the line %%:

  1. Definitions section: Contains declarations of tokens, types, and other C code.
  2. Rules section: Contains the grammar rules.
  3. Subroutines section: Contains C code that is included verbatim in the generated parser, typically used for actions or helper functions.

The grammar rules are specified in the form:

non_terminal : symbol_list { action }
             | symbol_list { action }
             ...
             ;

Tokens are typically declared in the definitions section using the %token directive. The value type of tokens and non-terminals is controlled by the %type directive and the %union declaration. The %prec directive can be used to assign precedence to grammar rules.

ENVIRONMENT VARIABLES

The behavior of yacc is not affected by any environment variables.

ASYNCHRONOUS EVENTS

Default signal handling shall be used.

STDOUT

The C source code for the parser is written to standard output, unless redirected by the -o option.

STDERR

Diagnostic messages, including parsing conflicts and errors, are written to standard error.

OUTPUT FILES

The following files may be produced:

y.tab.c
The C source code for the parser. The base name can be changed using the -b option.
y.tab.h
A header file containing token definitions (if the -d option is specified). The base name can be changed using the -b option.
y.output
A description of the parser's states, conflicts, and grammar rules (if the -p option is specified). The base name can be changed using the -b option.
y.dot
A description of the parser's state machine in DOT format (if the -v option is specified). The base name can be changed using the -b option.

EXTENDED DESCRIPTION

This section details aspects of yacc that are not covered by the basic description or options.

Error Recovery

yacc supports basic error recovery using the token error. When the parser encounters an error, it enters an error state. The error recovery mechanism attempts to discard tokens until a valid parsing state is reached. The user can define custom error handling routines within the grammar rules.

Ambiguities and Conflicts

yacc reports shift/reduce and reduce/reduce conflicts when it cannot determine the correct parsing action. These conflicts indicate ambiguities in the grammar. While yacc provides default precedence rules and associativity to resolve some conflicts, it may be necessary to explicitly resolve them using the %prec directive or by restructuring the grammar.

Precedence and Associativity

yacc assigns precedence and associativity to operators based on their order of definition in the grammar. Lower precedence rules are typically resolved before higher precedence rules. The %right, %left, and %nonassoc directives can be used to explicitly define associativity. The %prec directive can be used to override default precedence.

Token Values and Types

The type of values associated with tokens and non-terminals is defined by the YYSTYPE macro. By default, YYSTYPE is an int. The user can define a custom type using the %union declaration and specify the type for individual tokens and non-terminals using %type.

Parser Size and Performance

The size and execution speed of the generated parser can be affected by various factors, including the complexity of the grammar, the use of debugging code, and specific implementation optimizations. Historical implementations without runtime debugging code generally produced smaller and faster parsers.

**Statistics Messages**

Some historical implementations of yacc provided statistical information about the generated parser, including:

Number of terminals and non-terminals
Number of grammar rules
Number of states
Number of shift/reduce and reduce/reduce conflicts
Memory usage for states, parser tables, etc.
Number of distinct lookahead sets
Number of extra closures
Number of shift and goto entries
Entries saved by goto default
Optimizer space usage
Table entry statistics
Maximum spread and offset

The exact format and availability of these statistics are implementation-defined. Some implementations may use dynamic memory allocation and not report fixed limits.

**Output File Format (`y.output`)**

The format of the y.output file is not specified by POSIX. It is intended primarily for human understanding and debugging of the parser. Implementations may vary in their output format, but it should be human-readable text.

**Standard Error Reports**

Standard error messages are generally intended for human users and are not typically parsed by conforming applications. Implementations have considerable latitude in the format and content of these messages.

**Obsolete Features**

The construction "={" was recognized in some historical implementations as equivalent to "{". This feature has been documented as obsolete since 1978 and is omitted in this volume of POSIX.1‐2017.

**Multi-byte Characters**

Lexical analyzers should recognize multi-byte characters and return them as tokens. They should not return them as multi-byte character literals. The token value 256, often used for the error token in historical implementations, may conflict with multi-byte character values in some character sets. Therefore, token value 256 may not be available for user-defined tokens.

EXIT STATUS

The yacc utility shall exit with one of the following values:

0
Successful compilation.
1
An error occurred during compilation.
2
A warning was issued during compilation, but compilation completed successfully.

CONSEQUENCES OF ERRORS

If yacc detects an error in the grammar or during table generation, it shall produce an error message to standard error and exit with a non-zero status. The output parser file may be incomplete or corrupted.

APPLICATION USAGE

The yacc utility is typically used in conjunction with the lex utility, which generates the lexical analyzer. The parser generated by yacc and the scanner generated by lex are then compiled together to form the final parser program.

Care must be taken when defining grammar rules to avoid ambiguities and conflicts. Explicitly defining precedence and associativity using directives like %prec, %left, and %right is often necessary for complex grammars.

The YYSTYPE definition and associated actions must be consistent between the yacc grammar and the lex scanner.

EXAMPLES

To compile a grammar file named grammar.y, generating a header file with token definitions, and outputting the parser to parser.c:

yacc -d -o parser.c grammar.y

To compile a grammar from standard input and produce the parser to standard output:

yacc < grammar.y

RATIONALE

The yacc utility is a standard tool for compiler construction. Its primary function is to generate LALR(1) parsers from context-free grammars. The specification aims to cover the core functionality and common options found in historical implementations while acknowledging the existence of non-standard extensions.

The standard specifies the basic behavior and output files, leaving some implementation details (like the exact format of y.output and internal table limits) undefined to allow for flexibility. The focus is on portability and interoperability.

The handling of ambiguities and conflicts is a critical aspect of parser generation. While yacc provides mechanisms for resolving some of these issues (e.g., default precedence), the ultimate responsibility lies with the grammar writer. The standard does not mandate specific behavior for ambiguous grammars beyond reporting conflicts.

The %prec directive is included as it is a common and useful mechanism for resolving precedence conflicts. However, the standard acknowledges that there may be situations where yacc cannot interpret a grammar unambiguously even if it is not strictly in error. In such cases, providing additional information through declarations like %type or %union is often a more appropriate solution, typically resulting in smaller and more efficient parsers.

The performance benefits of excluding runtime debugging code are noted as typical of historical implementations. The inclusion of statistics messages from historical implementations serves to illustrate the kind of information that might be available, while emphasizing that these are implementation-defined.

The decision not to specify the format of the y.output file is based on the principle that this file is primarily for human use and its format should not hinder application portability. Consistency across implementations has been lacking historically, and no universally accepted format has emerged.

Similarly, standard error reports are not strictly defined because they are seldom used by conforming applications, and restricting implementations in this area was deemed unnecessary.

The obsolete construction "={" is mentioned to acknowledge its historical presence but is omitted from the standard as it was already marked obsolete in 1978. This follows the general principle of pruning obsolete features.

The requirement for lexical analyzers to recognize multi-byte characters and return them as tokens, rather than multi-byte character literals, is important for internationalization. The note about token value 256 being unavailable for user-defined tokens addresses a potential conflict with the error token in historical implementations, which could impact the use of certain character sets.

The standard does not need to support behaviors that are not commonly found or are considered obsolete.

Deciding when to use %prec illustrates the difficulty in specifying the behavior of yacc. There may be situations in which the grammar is not, strictly speaking, in error, and yet yacc cannot interpret it unambiguously. The resolution of ambiguities in the grammar can in many instances be resolved by providing additional information, such as using %type or %union declarations. It is often easier and it usually yields a smaller parser to take this alternative when it is appropriate.

The size and execution time of a program produced without the runtime debugging code is usually smaller and slightly faster in historical implementations.

Statistics messages from several historical implementations include the following types of information:

n/512 terminals, n/300 non-terminals
n/600 grammar rules, n/1500 states
n shift/reduce, n reduce/reduce conflicts reported
n/350 working sets used
Memory: states, etc. n/15000, parser n/15000
n/600 distinct lookahead sets
n extra closures
n shift entries, n exceptions
n goto entries
n entries saved by goto default
Optimizer space used: input n/15000, output n/15000
n table entries, n zero
Maximum spread: n, Maximum offset: n

The report of internal tables in the description file is left implementation-defined because all aspects of these limits are also implementation-defined. Some implementations may use dynamic allocation techniques and have no specific limit values to report.

The format of the y.output file is not given because specification of the format was not seen to enhance applications portability. The listing is primarily intended to help human users understand and debug the parser; use of y.output by a conforming application script would be unusual. Furthermore, implementations have not produced consistent output and no popular format was apparent. The format selected by the implementation should be human-readable, in addition to the requirement that it be a text file.

Standard error reports are not specifically described because they are seldom of use to conforming applications and there was no reason to restrict implementations.

Some implementations recognize "={" as equivalent to '{' because it appears in historical documentation. This construction was recognized and documented as obsolete as long ago as 1978, in the referenced Yacc: Yet Another Compiler-Compiler. This volume of POSIX.1‐2017 chose to leave it as obsolete and omit it.

Multi-byte characters should be recognized by the lexical analyzer and returned as tokens. They should not be returned as multi-byte character literals. The token error that is used for error recovery is normally assigned the value 256 in the historical implementation. Thus, the token value 256, which is used in many multi-byte character sets, is not available for use as the value of a user-defined token.
