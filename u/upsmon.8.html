UPSMON(8) Manual de NUT UPSMON(8)

NOMBRE

upsmon - Monitor y controlador de apagado de SAI

SINOPSIS

upsmon -h

upsmon -c comando [-P pid]

upsmon [-D] [-F | -B] [-K] [-p] [-u usuario]

DESCRIPCIÓN

upsmon es el proceso cliente responsable de la parte más importante del monitoreo de SAI: apagar el sistema cuando se va la luz. Puede llamar a otros programas auxiliares para propósitos de notificación durante eventos de energía.

upsmon puede monitorear múltiples sistemas utilizando un único proceso. A cada SAI definido en el archivo de configuración upsmon.conf(5) se le asigna un valor de potencia y un tipo (primary o secondary).

OPCIONES

-c comando

Envía el comando comando al proceso upsmon existente. Los comandos válidos son:

fsd

Apaga todos los SAI en modo primario (usar con precaución)

stop

detiene el monitoreo y sale

reload

vuelve a leer el archivo de configuración upsmon.conf(5). Ver "matices de recarga" más abajo si esto no funciona.

-P pid

Envía la señal de comando anterior usando el número de PID especificado, en lugar de consultar el archivo PID. Esto puede ayudar a definir unidades de servicio que inician el upsmon principal como un proceso en primer plano para que no tenga que depender de un archivo PID.

-D

Aumenta el nivel de depuración. upsmon se ejecutará en primer plano por defecto e imprimirá información en stdout sobre el proceso de monitoreo. Use esta opción varias veces para obtener más detalles.

-F

upsmon se ejecutará en primer plano, independientemente de la configuración de depuración.

-B

upsmon se ejecutará en segundo plano, independientemente de la configuración de depuración.

-K

Prueba el indicador de apagado. Si existe y contiene la cadena mágica de upsmon, entonces upsmon saldrá con EXIT_SUCCESS. Cualquier otra condición hará que upsmon salga con EXIT_FAILURE.

Puedes probar una salida exitosa de upsmon -K en tus scripts de apagado para saber cuándo llamar a upsdrvctl(8) para apagar el SAI.

-p

Ejecuta con privilegios todo el tiempo. Normalmente upsmon se dividirá en dos procesos. La mayoría del código se ejecuta como un usuario sin privilegios, y solo un pequeño fragmento se ejecuta como root para llamar eventualmente a SHUTDOWNCMD si es necesario. Este interruptor deshabilitará ese modo y ejecutará el antiguo sistema de "todo root todo el tiempo".

Este no es el modo recomendado, y no deberías usarlo a menos que tengas una muy buena razón.

-u usuario

Establece el usuario para el proceso de monitoreo sin privilegios. Esto no tiene efecto cuando se usa -p.

El usuario por defecto se establece en el momento de la configuración de compilación con configure --with-user=.... Típicamente es nobody (si no está configurado de otra manera), lo cual está lejos de ser ideal, por lo que la mayoría de las distribuciones empaquetadas probablemente tendrán un usuario nut específico para esta tarea. Si tus scripts de notificación necesitan ejecutarse como un usuario específico, establécelo aquí.

También puedes establecer esto en el archivo upsmon.conf(5) con la directiva RUN_AS_USER.

OPCIONES COMUNES

-h

Muestra el mensaje de ayuda de la línea de comandos.

-V

Muestra el banner de la versión de NUT. Pueden estar disponibles más detalles si también exportas NUT_DEBUG_LEVEL=1 o un nivel de verbosidad mayor.

-W seg

Establece el tiempo de espera para las conexiones de red iniciales (por defecto son indefinidamente no bloqueantes, o hasta que el sistema interrumpa el intento). Anula la variable de entorno opcional NUT_DEFAULT_CONNECT_TIMEOUT.

DEFINICIONES SAI

En upsmon.conf(5), debes especificar al menos un SAI que será monitoreado. Usa la directiva MONITOR de esta manera:

MONITOR 'sistema' 'valor_potencia' 'usuario' 'contraseña' 'tipo'

El sistema se refiere a un servidor upsd(8), en el formato nombre_sai[@nombre_host[:puerto]]. El nombre_host por defecto es "localhost", y el puerto por defecto es 3493. Algunos ejemplos siguen:

•"su700@mi_maquina" significa un SAI llamado "su700" en una máquina llamada "mi_maquina". Esta es la forma normal.
•"fenton@maquina_grande:5678" es un SAI llamado "fenton" en una máquina llamada "maquina_grande" que ejecuta upsd(8) en el puerto "5678".

El valor_potencia se refiere a cuántas fuentes de alimentación en este sistema cliente están siendo impulsadas por este SAI. Normalmente se establece en 1, pero consulta la sección sobre valores de potencia más abajo.

El usuario es una sección en tu archivo upsd.users(5). Cualquier contraseña que establezcas en esa sección debe coincidir con la contraseña establecida en este archivo para la instancia del servidor de datos correspondiente.

El tipo establecido en esa sección de la configuración del servidor de datos también debe coincidir con el tipo aquí: primary o secondary (considéralo un "rol de upsmon"). En general, un proceso cliente "primary" es uno que se ejecuta en el sistema con el SAI realmente conectado a un puerto serie o USB, y un "secondary" extrae energía del SAI pero no puede hablar con él directamente. Consulta la sección sobre tipos de SAI para más información.

EVENTOS DE NOTIFICACIÓN

upsmon detecta varios eventos mientras monitorea cada SAI. Se les llama "eventos de notificación", ya que se pueden usar para informar a los usuarios y administradores sobre el cambio de estado. Consulta las secciones adicionales relacionadas con NOTIFY más abajo para obtener información sobre cómo personalizar la entrega de estos mensajes.

ONLINE

El SAI ha vuelto a estar en línea.

ONBATT

El SAI está en batería.

LOWBATT

La batería del SAI está baja (según lo determinado por el controlador).

FSD

El SAI ha sido ordenado a entrar en modo de "apagado forzado".

COMMOK

Se ha establecido la comunicación con el SAI.

COMMBAD

Se acaba de perder la comunicación con el SAI.

SHUTDOWN

El sistema local se está apagando.

REPLBATT

Es necesario reemplazar la batería del SAI.

NOCOMM

No se puede contactar al SAI para monitoreo.

NOPARENT

El proceso padre de upsmon murió - apagado imposible.

CAL

Calibración del SAI en progreso.

NOTCAL

Calibración del SAI finalizada.

OFF

SAI administrativamente APAGADO o inactivo.

NOTOFF

SAI ya no está administrativamente APAGADO o inactivo.

BYPASS

SAI en bypass (alimentado, no protegiendo).

NOTBYPASS

SAI ya no está en bypass.

ECO

SAI en modo ECO o similar (según lo definido y nombrado por el fabricante); otros nombres incluyen modo de alta eficiencia y sistema de ahorro de energía.

Por ejemplo, la documentación de Eaton define el modo de alta eficiencia como una especie de bypass monitoreado por hardware con un cambio en menos de 10 ms al modo en línea en caso de problemas (que es lo que se conocía como Línea-Interactiva en los viejos tiempos), que puede ser **elegido** en lugar de ejecutarse siempre en modo de doble conversión (más seguro, pero más derrochador y con un costo en la vida útil de la batería). Dispositivos más antiguos solo implementaban uno u otro.

NOTECO

SAI ya no está en modo ECO (ver arriba).

ALARM

El SAI tiene una o más alarmas activas (mira ups.alarm para detalles).

NOTALARM

La UPS ya no se encuentra en estado de alarma (sin alarmas activas).

OVER

La UPS está sobrecargada.

NOTOVER

La UPS ya no está sobrecargada.

TRIM

La UPS está ajustando el voltaje de entrada.

NOTTRIM

La UPS ya no está ajustando el voltaje de entrada.

BOOST

La UPS está amplificando el voltaje de entrada.

NOTBOOST

La UPS ya no está amplificando el voltaje de entrada.

OTHER

La UPS tiene al menos un token de estado no clasificado.

NOTOTHER

La UPS ya no tiene tokens de estado no clasificados.

SUSPEND_STARTING

El sistema operativo está entrando en modo de suspensión/hibernación.

SUSPEND_FINISHED

El sistema operativo acaba de salir del modo de suspensión/hibernación, desactivando lecturas obsoletas de la UPS para evitar un apagado desafortunado.

COMANDO NOTIFICAR

En upsmon.conf(5), puedes configurar un programa llamado NOTIFYCMD que manejará los eventos que ocurran.

La sintaxis es: NOTIFYCMD "ruta al programa"

Ejemplo:

•NOTIFYCMD "/usr/local/bin/notifyme"

Recuerda encerrar la ruta entre "comillas dobles" si contiene espacios. Probablemente no debería depender de recibir argumentos de línea de comandos.

El programa que ejecutes como tu NOTIFYCMD puede usar las variables de entorno NOTIFYTYPE y UPSNAME para saber qué ha sucedido y en qué UPS. También recibe el mensaje de notificación (ver abajo) como el primer (y único) argumento, por lo que también puedes entregar un mensaje preformateado.

Ten en cuenta que NOTIFYCMD solo se llamará para un evento determinado cuando establezcas el flag EXEC utilizando los flags de notificación, como se detalla a continuación.

FLAGS DE NOTIFICACIÓN

Por defecto, todos los eventos de notificación (ver arriba) generan un mensaje global (wall) para todos los usuarios, además de ser registrados a través de syslog. Excepto en Windows, donde upsmon solo escribe en syslog por defecto. Puedes cambiar esto con la directiva NOTIFYFLAG en el archivo de configuración:

La sintaxis es: NOTIFYFLAG tipodenotificación flags

Ejemplos:

•NOTIFYFLAG ONLINE SYSLOG
•NOTIFYFLAG ONBATT SYSLOG+WALL
•NOTIFYFLAG LOWBATT SYSLOG+WALL+EXEC

Los flags que se pueden establecer en un evento de notificación dado son:

SYSLOG

Escribir este mensaje en el registro del sistema (syslog).

WALL

Enviar este mensaje a todos los usuarios del sistema a través de wall(1).

EXEC

Ejecutar el NOTIFYCMD.

IGNORE

No hacer nada. Si usas esto, no uses ningún otro flag.

Puedes mezclar estos flags; por ejemplo, SYSLOG+WALL+EXEC hace las tres cosas para un evento dado.

MENSAJES DE NOTIFICACIÓN

upsmon viene con mensajes predeterminados para cada uno de los eventos NOTIFY. Estos pueden cambiarse con la directiva NOTIFYMSG.

La sintaxis es: NOTIFYMSG tipo "mensaje"

Ejemplos:

•NOTIFYMSG ONLINE "La UPS %s está recibiendo energía de la red"
•NOTIFYMSG ONBATT "Alguien desconectó la %s"

La primera instancia de %s se reemplaza con el identificador de la UPS que generó el evento. Estos mensajes se utilizan al enviar mensajes de pared a los usuarios directamente desde upsmon, y también se pasan al NOTIFYCMD.


Nota

Ciertas notificaciones, como NOTIFY_ALARM y NOTIFY_OTHER, pueden aceptar una segunda instancia de %s que se reemplazaría con el texto de la alarma o el token no reconocido, respectivamente.

VALORES DE POTENCIA

El "valor de potencia general actual" es la suma de todas las UPS que actualmente pueden suministrar energía al sistema que aloja upsmon. Cualquier UPS que esté en línea o simplemente en batería contribuye a este número. Si una UPS está en estado crítico (en batería y batería baja) o ha sido puesta en modo de "apagado forzado", ya no contribuye.

La sintaxis es: MONITOR nombreups valordepotencia usuario contraseña tipo

Un "valor de potencia" en una línea MONITOR en el archivo de configuración es el número de fuentes de alimentación que la UPS alimenta en el sistema actual.

•Normalmente, solo tienes una fuente de alimentación, por lo que se establecerá en 1.

Ejemplo:

•MONITOR myups@myhost 1 username mypassword primary
•En un servidor grande con fuentes de alimentación redundantes, el valor de potencia de una UPS puede ser mayor que 1. También puedes definir más de una.

Ejemplos para un servidor con cuatro módulos de fuente de alimentación y dos UPS (cada una alimentando dos fuentes de alimentación de ese servidor):

•MONITOR ups-alpha@myhost 2 username mypassword primary
•MONITOR ups-beta@myhost 2 username mypassword primary
•También puedes establecer el valor de potencia de una UPS a 0 si no suministra ninguna energía a ese sistema. Esto se utiliza generalmente cuando quieres usar las funciones de notificación de upsmon para una UPS, aunque en realidad no esté alimentando el sistema que aloja esta instancia del cliente upsmon.

No establezcas esto en "primary" a menos que realmente quieras apagar esa UPS cuando esta instancia de upsmon necesite apagarse por sus propias razones.

Ejemplo:

•MONITOR faraway@anotherbox 0 username mypassword secondary

El "valor mínimo de potencia" es el número de fuentes de alimentación que deben estar recibiendo energía para mantener en funcionamiento el ordenador de este cliente upsmon.

La sintaxis es: MINSUPPLIES valor

•Los PC típicos solo tienen 1, por lo que la mayoría de los usuarios lo dejarán con el valor predeterminado.

Ejemplo:

•MINSUPPLIES 1
•Si tienes un servidor o un sistema similar con energía redundante, este valor generalmente se establecerá más alto. Uno que requiera tres fuentes de alimentación de 4 en funcionamiento en todo momento simplemente lo establecería en 3.

Ejemplo:

•MINSUPPLIES 3

Cuando el valor general de potencia externa protegida por UPS saludable actual cae por debajo del valor de potencia mínimo requerido, upsmon inicia la secuencia de apagado. Este diseño te permite perder algunas de tus fuentes de alimentación en un entorno de potencia redundante sin apagar todo el sistema, mientras sigue funcionando correctamente para sistemas más pequeños.

TIPOS DE UPS

upsmon y upsd(8) no siempre se ejecutan en el mismo sistema. Cuando lo hacen, cualquier UPS que esté conectada directamente al host de upsmon debe ser monitoreada en modo "primario". Esto hace que upsmon se encargue de ese equipo, y esperará a que los sistemas "secundarios" se desconecten antes de apagar el sistema local. Esto permite que los sistemas distantes (monitoreando a través de la red) se apaguen limpiamente antes de que upsdrvctl shutdown se ejecute localmente y los apague a todos.

Cuando upsmon se ejecuta como secundario, depende del sistema distante para que le informe sobre el estado de la UPS. Cuando esa UPS entra en estado crítico (en batería y batería baja), invoca inmediatamente el comando de apagado local. Esto debe suceder rápidamente. Una vez que todos los secundarios se desconectan del servidor upsd(8) distante, su upsmon en modo primario iniciará su propio proceso de apagado. Tus sistemas secundarios deben detenerse y apagarse antes de que el primario apague la fuente de alimentación compartida, o podrían producirse daños en el sistema de archivos.

upsmon maneja los secundarios que se atascan, se cuelgan o de otra manera no logran desconectarse limpiamente de upsd(8) de manera oportuna con el temporizador HOSTSYNC. Durante una situación de apagado, el upsmon primario se rendirá después de este intervalo y se apagará de todos modos. Esto evita que el primario se quede ahí para siempre (lo que pondría en peligro ese host) si un secundario se rompe de alguna manera. Esto tiene un valor predeterminado de 15 segundos.

Si tu sistema primario se apaga demasiado rápido, ajusta el intervalo FINALDELAY a algo mayor que los 15 segundos predeterminados. No lo pongas demasiado alto, o la batería de tu UPS podría agotarse antes de que el proceso upsmon primario apague ese sistema.

APAGADOS PROGRAMADOS

Para esas raras situaciones en las que el proceso de apagado no se puede completar entre el momento en que se señala la batería baja y la UPS apaga realmente la carga, usa el programa auxiliar upssched(8). Puedes usarlo junto con upsmon para programar un apagado basado en el evento "en batería". upssched puede entonces volver a upsmon para iniciar el apagado una vez que ha estado en batería demasiado tiempo.

Esto puede ser complicado y enrevesado, así que quédate con el manejo predeterminado de UPS críticas si puedes.

FUENTES DE ALIMENTACIÓN REDUNDANTES

Si tienes más de una fuente de alimentación para energía redundante, también puedes tener más de una UPS alimentando tu ordenador. upsmon puede manejar esto. Asegúrate de establecer los valores de potencia de la UPS apropiadamente y el valor de MINSUPPLIES lo suficientemente alto para que siga funcionando hasta que realmente necesite apagarse.

Por ejemplo, el HP NetServer LH4 por defecto tiene 3 fuentes de alimentación instaladas, con un compartimento vacío. Tiene dos cables de alimentación, uno por lado de la caja. Esto significa que un cable de alimentación alimenta dos compartimentos de fuente de alimentación, y que solo puedes tener dos UPS suministrando energía.

Conecta la UPS "alfa" al cable que alimenta dos fuentes de alimentación, y la UPS "beta" al cable que alimenta la tercera y el compartimento vacío. Define alfa como un valor de potencia de 2, y beta como un valor de potencia de 1. Establece MINSUPPLIES en 2.

Cuando alfa se ponga en batería, tu valor general de potencia actual se mantendrá en 3, ya que sigue suministrando energía. Sin embargo, una vez que

va crítico (con batería y batería baja), dejará de contribuir al valor general de potencia actual. Eso significa que el valor será 1 (solo beta), lo cual es menor que 2. Eso es insuficiente para ejecutar el sistema, y upsmon invocará la secuencia de apagado.

Sin embargo, si beta entra en estado crítico, restar su contribución reducirá el valor general actual de 3 a 2. Esto es justo lo suficientemente alto para satisfacer el mínimo, por lo que el sistema continuará funcionando como antes. Si beta regresa más tarde, se volverá a sumar y el valor actual volverá a ser 3. Esto le permite intercambiar UPS, cambiar una configuración de alimentación o lo que sea, siempre que mantenga el valor mínimo de potencia en todo momento.

OPERACIONES MIXTEADAS

Además de poder monitorizar múltiples UPS, upsmon también puede monitorizarlas con diferentes roles. Si tiene un sistema con múltiples fuentes de alimentación atendidas por baterías de UPS separadas, es posible ser un primario en una UPS y un secundario en otra. Esto suele ocurrir cuando se agotan los puertos serie o USB y se necesita realizar la monitorización a través de otro sistema cercano.

Esto también es complicado, especialmente a la hora de apagar una UPS que ha entrado en estado crítico pero no suministra energía al sistema local. Puede hacerlo con algo de magia de scripting en su script de comando de notificación, pero está más allá del alcance de este manual.

APAGADOS FORZADOS

Cuando upsmon se ve obligado a apagar el sistema local, establece el indicador "FSD" (apagado forzado) en las UPS que está ejecutando en modo primario. Esto se utiliza para sincronizar sistemas secundarios en caso de que un primario que está bien de otra manera necesite ser apagado debido a algún evento apremiante en el sistema de gestión de la UPS.

Puede invocar manualmente este modo en el sistema con upsmon en modo primario iniciando otra copia del programa con el argumento de línea de comandos -c fsd. Esto es útil cuando desea iniciar un apagado antes de la etapa crítica a través de algún medio externo, como upssched(8).


Advertencia

Tenga en cuenta que, por diseño, dado que requerimos el reinicio de la carga y no queremos que algunos sistemas se apaguen mientras otros permanecen en funcionamiento si la "alimentación de red" regresa en el momento equivocado, como suele suceder, el indicador "FSD" no se puede eliminar del servidor de datos a menos que se reinicie su demonio. Si tomamos el primer paso en modo crítico, normalmente pretendemos llegar hasta el final: apagar todos los servidores de forma segura y desconectar la UPS.

Tenga en cuenta que algunos dispositivos UPS y sus controladores correspondientes también pueden fijar o volver a mostrar el estado "FSD" incluso si la "alimentación de red" está disponible, pero la carga restante de la batería está por debajo de un umbral configurado como "seguro" en el dispositivo (generalmente si enciende manualmente la UPS después de un largo corte de energía). Esto es por diseño de los respectivos fabricantes de UPS, ya que en tal situación no pueden garantizar que si ocurre otro corte de energía, su UPS apagará sus sistemas de manera segura nuevamente. Por lo tanto, se considera mejor y más seguro permanecer oscuro hasta que las baterías se carguen suficientemente.

Cuando llega el momento de apagar, upsmon crea POWERDOWNFLAG para comunicar al sistema operativo que la UPS debe ser apagada tarde en la secuencia de apagado. Este archivo se elimina si está presente cuando se inicia upsmon, de modo que el próximo apagado normal no cause que la UPS se apague. (En general, el archivo no se puede eliminar durante el apagado porque el sistema de archivos podría ser de solo lectura. Si el archivo está en un sistema de archivos respaldado por RAM, no estará presente y la verificación para eliminarlo no se activará).

SIMULACIÓN DE FALLOS DE ALIMENTACIÓN

Para probar un apagado sincronizado sin desconectar su(s) UPS, solo necesita establecer el indicador de apagado forzado (FSD) en ellas. Puede hacerlo llamando a upsmon nuevamente para establecer el indicador, es decir:

:; upsmon -c fsd

Después de eso, el primario y el secundario realizarán su secuencia de apagado habitual como si la batería hubiera entrado en estado crítico, mientras que usted puede cronometrar cuánto tiempo tardan. Esto es mucho más fácil para su equipo UPS, y es mejor que arrastrarse debajo de un escritorio para encontrar el enchufe.

Tenga en cuenta que también puede usar una configuración de SHUTDOWNCMD ficticia para simplemente informar que los sistemas se apagarán en este punto, sin interrumpir realmente su trabajo.


Advertencia

Después de tales experimentos "ficticios", es posible que deba reiniciar el servidor de datos NUT upsd para borrar su indicador "FSD" para los dispositivos y clientes involucrados, y asegurarse de que no queden archivos nombrados por la opción POWERDOWNFLAG (por ejemplo, /etc/killpower) en los sistemas primarios de upsmon bajo prueba.

UPSES MUERTAS

En caso de que upsmon no pueda comunicarse con upsd(8), declara esa UPS "muerta" después de un intervalo controlado por DEADTIME en upsmon.conf(5). Si esto sucede mientras esa UPS estaba últimamente en batería, se asume que ha entrado en estado crítico y ya no contribuye al valor general de potencia.

upsmon le alertará sobre una UPS que no puede ser contactada para su monitorización con un notificador "NOCOMM" por defecto cada 300 segundos. Esto se puede cambiar con la configuración NOCOMMWARNTIME.

Además, upsmon normalmente informa los fallos de sondeo para cada dispositivo que ocurren en cada ciclo POLLFREQ (por ejemplo, "Datos obsoletos" o "Controlador no conectado") al registro del sistema según lo configurado. Si se espera que sus dispositivos estén ausentes durante un período prolongado, puede usar POLLFAIL_LOG_THROTTLE_MAX para reducir el estrés en el tráfico y almacenamiento de syslog, publicando estos mensajes solo una vez en cada ciclo, y cuando la condición de error haya cambiado o se haya resuelto. Un valor negativo significa comportamiento estándar (registrar en cada ciclo, efectivamente lo mismo que cuando max=1), y un valor cero significa nunca repetir el mensaje (registrar solo al inicio y al final/cambio del estado de fallo).

Tenga en cuenta que esta limitación solo se aplica al último estado de error activo por dispositivo monitorizado.

ALARMAS DE UPS

Los fabricantes de UPS y los controladores de UPS pueden implementar alarmas específicas del dispositivo para notificar al usuario sobre condiciones potencialmente graves de la UPS. El estado "ALARM" se establecerá en dicha UPS como un denominador común para las diferentes implementaciones en los varios controladores de UPS y generalmente cada vez que se vea una variable "ups.alarm" informada por el controlador de UPS específico.

Las alarmas pueden ser actuadas por el usuario utilizando los notificadores "ALARM" y "NOTALARM", que son informados por upsmon cuando ocurre o desaparece el estado "ALARM".

Dado que las alarmas generadas por la UPS son generalmente de naturaleza grave, upsmon vigila una UPS en dicho estado más de cerca, aumentando la frecuencia de sondeo según sea necesario.

Cuando ocurre una pérdida de conexión en un estado de alarma, upsmon considerará por defecto la UPS volátil como crítica/muerta y esto puede llevar a apagados falsos si la alarma real era de naturaleza mundana (por ejemplo, causada por un modo HE/ECO). Esto se puede cambiar utilizando la configuración ALARMCRITICAL dentro de upsmon.conf.

MATICES DE RECARGA

upsmon generalmente renuncia a los permisos de root para el proceso que realiza la mayor parte del trabajo, incluido el manejo de señales como SIGHUP para recargar el archivo de configuración. Esto significa que su archivo upsmon.conf(5) debe ser legible por la cuenta no root a la que cambia upsmon.

Si desea que las recargas funcionen, upsmon debe ejecutarse como un usuario que tenga permisos para leer el archivo de configuración. Recomendamos crear un nuevo usuario solo para este propósito, ya que hacer que el archivo sea legible por "nobody" (el usuario por defecto) sería una mala idea; los paquetes suelen venir con un usuario nut o ups para ejecutar los servicios de demonio de NUT.

Consulte la sección RUN_AS_USER en upsmon.conf(5) para más información sobre este tema.

Además, no puede cambiar las definiciones de SHUTDOWNCMD o POWERDOWNFLAG con una recarga debido al modelo de proceso dividido. Si cambia esos valores, debe detener upsmon y reiniciarlo. upsmon le advertirá en syslog si realiza cambios en cualquiera de esos valores durante una recarga.

VARIABLES DE ENTORNO

NUT_DEBUG_LEVEL establece la verbosidad de depuración por defecto si no se proporcionaron argumentos -D en la línea de comandos, pero no solicita que el demonio se ejecute en modo de primer plano.

NUT_CONFPATH es el nombre de la ruta del directorio que contiene upsmon.conf y otros archivos de configuración. Si esta variable no está establecida, upsmon utiliza un valor predeterminado incorporado, que a menudo es /usr/local/ups/etc.

NUT_QUIET_INIT_UPSNOTIFY=true se puede usar para evitar que los demonios que pueden notificar a los marcos de gestión de servicios (como systemd) sobre el paso de sus hitos de ciclo de vida emitan tales notificaciones (incluidas las sobre la falta de soporte del sistema para tales características modernas, una vez por ejecución).

NUT_QUIET_INIT_BANNER=true se puede usar para suprimir el banner con el nombre y la versión de la herramienta NUT. NO recomendado para servicios debido al impacto adverso en la solución de problemas, pero puede ser útil en perfiles de shell o scripts que procesan las salidas de las herramientas NUT.
