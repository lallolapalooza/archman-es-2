NOMBRE

unbound.conf - Archivo de configuración de Unbound 1.24.2.

SINOPSIS

unbound.conf

DESCRIPCIÓN

unbound.conf se utiliza para configurar unbound(8). El formato del archivo tiene atributos y valores. Algunos atributos tienen atributos dentro de ellos. La notación es: atributo: valor.

Los comentarios comienzan con # y duran hasta el final de la línea. Las líneas vacías se ignoran, al igual que el espacio en blanco al principio de una línea.

La utilidad unbound-checkconf(8) se puede usar para comprobar unbound.conf antes de usarla.

EJEMPLO

A continuación se muestra un archivo de configuración de ejemplo. Cópielo a /etc/unbound/unbound.conf y inicie el servidor con:

$ unbound -c /etc/unbound/unbound.conf

La mayoría de la configuración son los valores predeterminados. Detenga el servidor con:

$ kill `cat /etc/unbound/unbound.pid`

A continuación se muestra un archivo de configuración mínimo. La distribución fuente contiene un archivo example.conf extenso con todas las opciones.

# Archivo de configuración de unbound.conf(5) para unbound(8).
server:
    directory: "/etc/unbound"
    username: unbound
    # asegúrese de que unbound pueda acceder a la entropía desde dentro del chroot.
    # p. ej., en linux, utilice estos comandos (en BSD, se usa devfs(8)):
    #      mount --bind -n /dev/urandom /etc/unbound/dev/urandom
    # y  mount --bind -n /dev/log /etc/unbound/dev/log
    chroot: "/etc/unbound"
    # logfile: "/etc/unbound/unbound.log"  # descomentar para usar logfile.
    pidfile: "/etc/unbound/unbound.pid"
    # verbosity: 1      # descomentar y aumentar para obtener más registros.
    # escuchar en todas las interfaces, responder a consultas de la subred local.
    interface: 0.0.0.0
    interface: ::0
    access-control: 10.0.0.0/8 allow
    access-control: 2001:DB8::/64 allow

FORMATO DEL ARCHIVO

Debe haber espacios en blanco entre las palabras clave. Las palabras clave de los atributos terminan con dos puntos ':'. Un atributo va seguido de un valor, o de sus atributos contenedores, en cuyo caso se le denomina cláusula. Las cláusulas pueden repetirse en todo el archivo (o en los archivos incluidos) para agrupar atributos bajo la misma cláusula.

Los archivos se pueden incluir usando la directiva include:. Puede aparecer en cualquier lugar, acepta un único nombre de archivo como argumento. El procesamiento continúa como si el texto del archivo incluido se hubiera copiado en el archivo de configuración en ese punto. Si también se utiliza chroot, los nombres de ruta completos para los archivos incluidos funcionan, los nombres de ruta relativos para los nombres incluidos funcionan si el directorio donde se inicia el demonio es igual a su directorio chroot/trabajo o se especifica antes de la declaración de inclusión con directory: dir. Se pueden usar comodines para incluir varios archivos, consulte glob(7).

Para una opción de inclusión más estructural, se puede usar la directiva include-toplevel:. Esto cierra cualquier cláusula que esté actualmente activa (si la hay) y fuerza el uso de las cláusulas en los archivos incluidos y justo después de esta directiva.

Opciones del servidor

Estas opciones forman parte de la cláusula server:.

verbosity: <número>
El nivel de verbosidad.
Nivel 0
Sin verbosidad, solo errores.
Nivel 1
Proporciona información operativa.
Nivel 2
Proporciona información operativa detallada, incluida información corta por consulta.
Nivel 3
Proporciona información a nivel de consulta, salida por consulta.
Nivel 4
Proporciona información a nivel de algoritmo.
Nivel 5
Registra la identificación del cliente para las ausencias en la caché.

La verbosidad también se puede aumentar desde la línea de comandos y en tiempo de ejecución a través del control remoto. Consulte unbound(8) y unbound-control(8) respectivamente.

Predeterminado: 1

statistics-interval: <segundos>
El número de segundos entre la impresión de estadísticas en el registro para cada hilo. Deshabilitar con el valor 0 o "". Las estadísticas del histograma solo se imprimen si se enviaron respuestas durante el intervalo de estadísticas, las estadísticas de la lista de solicitudes se imprimen para cada intervalo (pero pueden ser 0). Esto se debe a que el cálculo de la mediana requiere que haya datos presentes.

Predeterminado: 0 (deshabilitado)

statistics-cumulative: <sí o no>
Si está habilitado, las estadísticas son acumulativas desde el inicio de Unbound, sin borrar los contadores de estadísticas después de registrar las estadísticas.

Predeterminado: no

extended-statistics: <sí o no>
Si está habilitado, se imprimen estadísticas extendidas desde unbound-control(8). Los contadores se enumeran en unbound-control(8). Mantener un registro de más estadísticas lleva tiempo.

Predeterminado: no

statistics-inhibit-zero: <sí o no>
Si está habilitado, se inhiben de imprimirse con unbound-control(8) las estadísticas extendidas seleccionadas con un valor de 0. Estos son tipos de consulta, clases de consulta, opcodes de consulta, rcodes de respuesta (excepto NOERROR, FORMERR, SERVFAIL, NXDOMAIN, NOTIMPL, REFUSED) y acciones PRZ.

Predeterminado: sí

num-threads: <número>
El número de hilos a crear para atender a los clientes. Use 1 para no tener hilos.

Predeterminado: 1

port: <número de puerto>
El número de puerto en el que el servidor responde a las consultas.

Predeterminado: 53

interface: <dirección IP o nombre de interfaz[@puerto]>
Interfaz a usar para conectarse a la red. Esta interfaz se escucha para consultas de clientes, y las respuestas a clientes se dan desde ella. Se puede dar varias veces para trabajar en varias interfaces. Si no se da ninguna, el valor predeterminado es escuchar en localhost.

Si se usa un nombre de interfaz en lugar de una dirección IP, se utilizan las direcciones IP de esa interfaz. Las interfaces no se cambian con una recarga (kill -HUP) sino solo con un reinicio.

Se puede especificar un número de puerto con @puerto (sin espacios entre la interfaz y el número de puerto), si no se especifica, se usa el puerto predeterminado (de port).

ip-address: <dirección IP o nombre de interfaz[@puerto]>
Igual que interface (para facilitar la compatibilidad con nsd.conf(5)).
interface-automatic: <sí o no>
Escuchar en todas las direcciones de todas las interfaces (actuales y futuras), detectar la interfaz de origen en consultas UDP y copiarlas a las respuestas. Esto es muy parecido a ip-transparent, pero esta opción atiende a todas las interfaces, mientras que con ip-transparent puedes seleccionar en qué interfaces (futuras) Unbound proporciona servicio. Por defecto: no

interface-automatic-ports: "<cadena>"
Enumera los números de puerto en los que escucha interface-automatic. Si está vacío, se escucha en el puerto por defecto. Los números de puerto están separados por espacios en la cadena.

Esto se puede usar para que interface automático maneje la interfaz y escuche en el número de puerto normal, incluyéndolo en la lista, y también los números de puerto HTTPS o DNS-over-TLS incluyéndolos en la lista también.

Por defecto: ""

outgoing-interface: <dirección IPv4/IPv6 o bloque de red IPv6>
Interfaz a usar para conectarse a la red. Esta interfaz se usa para enviar consultas a servidores autoritativos y recibir sus respuestas. Se puede especificar varias veces para trabajar en varias interfaces. Si no se especifica ninguna, se usa la predeterminada (todas). Puede especificar las mismas interfaces en las líneas interface y outgoing-interface, las interfaces se usan entonces para ambos propósitos. Las consultas salientes se envían a través de una interfaz saliente aleatoria para contrarrestar la suplantación.

Si se especifica un bloque de red IPv6 en lugar de una dirección IPv6 individual, las consultas UDP salientes usarán una dirección de origen aleatoria tomada del bloque de red para contrarrestar la suplantación. Requiere que el bloque de red IPv6 sea enrutado al host que ejecuta Unbound, y requiere soporte del SO para enlaces no locales sin privilegios (actualmente solo compatible con Linux). Se pueden especificar varios bloques de red con múltiples opciones outgoing-interface, pero no especifique una dirección IPv6 individual y un bloque de red IPv6, o la aleatorización se verá comprometida. Considere combinar con prefer-ip6: yes para aumentar la probabilidad de que se seleccionen servidores DNS IPv6 para las consultas. En Linux, necesita estos dos comandos para poder usar la opción de socket freebind para recibir tráfico para el bloque de red ip6:

ip -6 addr add mi_bloque_de_red/64 dev lo && \
ip -6 route add local mi_bloque_de_red/64 dev lo
outgoing-range: <número>
Número de puertos a abrir. Este número de descriptores de archivo se puede abrir por hilo. Debe ser al menos 1. El valor por defecto depende de las opciones de compilación. Números más grandes necesitan recursos adicionales del sistema operativo. Para un rendimiento óptimo, un valor muy alto es lo mejor, use libevent para hacerlo posible.

Por defecto: 4096 (libevent) / 960 (minievent) / 48 (windows)

outgoing-port-permit: <número de puerto o rango>
Permitir que Unbound abra este puerto o rango de puertos para enviar consultas. Un mayor número de puertos salientes permitidos aumenta la resiliencia contra intentos de suplantación. Asegúrese de que estos puertos no sean necesarios para otros demonios. Por defecto, solo se utilizan los puertos superiores a 1024 que no han sido asignados por IANA. Proporcione un número de puerto o un rango de la forma "bajo-alto", sin espacios.

Las declaraciones outgoing-port-permit y outgoing-port-avoid se procesan en el orden de línea del archivo de configuración, añadiendo los puertos permitidos y restando los puertos evitados del conjunto de puertos permitidos. El procesamiento comienza con los puertos no asignados por IANA por encima de 1024 en el conjunto de puertos permitidos.

outgoing-port-avoid: <número de puerto o rango>
No permitir que Unbound abra este puerto o rango de puertos para enviar consultas. Úselo para asegurarse de que Unbound no tome un puerto que otro demonio necesita. El puerto se evita en todas las interfaces salientes, tanto IPv4 como IPv6. Por defecto, solo se utilizan los puertos superiores a 1024 que no han sido asignados por IANA. Proporcione un número de puerto o un rango de la forma "bajo-alto", sin espacios.
outgoing-num-tcp: <número>
Número de búferes TCP salientes a asignar por hilo. Si se establece en 0, o si se establece do-tcp: no, no se realizan consultas TCP a servidores autoritativos. Para instalaciones más grandes, aumentar este valor es una buena idea.

Por defecto: 10

incoming-num-tcp: <número>
Número de búferes TCP entrantes a asignar por hilo. Si se establece en 0, o si se establece do-tcp: no, no se aceptan consultas TCP de clientes. Para instalaciones más grandes, aumentar este valor es una buena idea.

Por defecto: 10

edns-buffer-size: <número>
Número de bytes de tamaño a anunciar como el tamaño del búfer de reasamblaje EDNS. Este es el valor que se introduce en los datagramas sobre UDP hacia los pares. El tamaño real del búfer está determinado por msg-buffer-size (tanto para TCP como para UDP). No establezca un valor superior a ese. Establecerlo en 512 evita incluso los problemas de MTU de ruta más estrictos, pero se considera extremo, ya que la cantidad de fallback a TCP generada es excesiva (probablemente también para este resolutor, considere ajustar outgoing-num-tcp).

Por defecto: 1232 (recomendación del DNS Flag Day 2020)

max-udp-size: <número>
Tamaño máximo de respuesta UDP (no se aplica a la respuesta TCP). 65536 desactiva el tamaño máximo de respuesta UDP y utiliza la elección del cliente, siempre. Los valores sugeridos son de 512 a 4096.

Por defecto: 1232 (igual que edns-buffer-size)

stream-wait-size: <número>
Tamaño máximo en bytes para los búferes de flujo de espera. Un número simple está en bytes, añada 'k', 'm' o 'g' para kilobytes, megabytes o gigabytes (1024*1024 bytes en un megabyte). Como los flujos TCP y TLS acumulan múltiples resultados, la cantidad de memoria utilizada para estos búferes no excede este número, de lo contrario, las respuestas se descartan. Esto gestiona el uso total de memoria del servidor (bajo uso intensivo), el número de solicitudes que se pueden poner en cola por conexión también está limitado, con solicitudes adicionales esperando en los búferes TCP.

Por defecto: 4m

msg-buffer-size: <número>
Tamaño en bytes de los búferes de mensajes. Por defecto es 65552 bytes, suficiente para paquetes de 64 Kb, el tamaño máximo de mensaje DNS. Ningún mensaje más grande que este puede ser enviado o recibido. Se puede reducir para usar menos memoria, pero algunas solicitudes de datos DNS, como las de registros de recursos enormes, resultarán en una respuesta SERVFAIL al cliente.

Por defecto: 65552

msg-cache-size: <número>
Tamaño en bytes de la caché de mensajes. Un número simple está en bytes, añada 'k', 'm' o 'g' para kilobytes, megabytes o gigabytes (1024*1024 bytes en un megabyte).

Por defecto: 4m

msg-cache-slabs: <número>
Número de "slabs" en la caché de mensajes. Los "slabs" reducen la contención de bloqueo por parte de los hilos. Debe establecerse en una potencia de 2. Establecerlo (cerca) del número de CPUs es una configuración bastante buena. Si se deja sin configurar, se configurará automáticamente como una potencia de 2 cercana al número de hilos configurados en entornos multihilo.

Por defecto: (sin configurar)

num-queries-per-thread: <número>
El número de consultas que cada hilo atenderá simultáneamente. Si llegan más consultas que necesitan ser atendidas, y no se pueden descartar consultas existentes (ver jostle-timeout), entonces las consultas se descartan. Esto obliga al cliente a reenviar después de un tiempo de espera; dando tiempo al servidor para trabajar en las consultas existentes. El valor por defecto depende de las opciones de compilación.

Por defecto: 2048 (libevent) / 512 (minievent) / 24 (windows)

jostle-timeout: <milisegundos>
Tiempo de espera utilizado cuando el servidor está muy ocupado. Establecerlo a un valor que normalmente resulte en un viaje de ida y vuelta a los servidores de autoridad.

Si llegan demasiadas consultas, el 50% de las consultas tienen permiso para completarse, y el otro 50% se reemplaza con la nueva consulta entrante si ya han pasado más de su tiempo permitido. Esto protege contra ataques de denegación de servicio por consultas lentas o altas tasas de consulta.

El efecto es que las QPS para consultas de larga duración son aproximadamente:

(num-queries-per-thread / 2) / (tiempo promedio para dichas consultas largas) QPS

Las QPS para consultas cortas pueden ser aproximadamente:

(num-queries-per-thread / 2) / (jostle-timeout en segundos enteros) QPS por hilo

aproximadamente (2048/2)*5 = 5120 QPS por defecto.

Por defecto: 200

delay-close: <milisegundos>
Retraso adicional para puertos UDP con tiempo de espera agotado antes de que se cierren, en milisegundos. Esto evita que los paquetes de respuesta muy retrasados de los servidores ascendentes (recursivos) choquen contra puertos cerrados y activen todo tipo de contadores de cierre de puertos, con, por ejemplo, 1500 milisegundos. Cuando ocurren tiempos de espera agotados, necesita sockets adicionales, verifica la ID y la IP remota de los paquetes, y los paquetes no deseados se añaden al contador de paquetes no deseados.

Por defecto: 0 (desactivado)

udp-connect: <sí o no>
Realiza connect(2) para sockets UDP que mitiga la fuga de canales laterales ICMP.

Por defecto: sí

access-control: <bloque de red IP> <acción>
Especificar el tratamiento de las consultas entrantes de su dirección IP de origen. Las consultas pueden tener acceso permitido a este servidor que proporciona respuestas DNS, o ser rechazadas, con otras acciones posibles. El rango de direcciones IP se puede especificar como un bloque de red, es posible proporcionar la declaración varias veces para especificar el tratamiento de diferentes bloques de red. El bloque de red se proporciona como una dirección IPv4 o IPv6 con /tamaño agregado para un bloque de red sin clase. Se utiliza la coincidencia de bloque de red más específica; si ninguna coincide, se utiliza refuse. Por lo tanto, el orden de las declaraciones de control de acceso no importa. La acción puede ser deny, refuse, allow, allow_setrd, allow_snoop, allow_cookie, deny_non_local o refuse_non_local.
deny
Detiene las consultas de los hosts de ese bloque de red.
refuse
También detiene las consultas, pero envía un mensaje de error DNS rcode REFUSED.
allow
Permite el acceso a los clientes de ese bloque de red. Solo permite el acceso a los clientes de recursión (que es lo que la mayoría de los clientes necesitan). Las consultas no recursivas son rechazadas.

La acción allow permite que las consultas no recursivas accedan a los local-data configurados. La razón es que esto no involucra el algoritmo de búsqueda recursiva del servidor Unbound, y los datos estáticos se sirven en la respuesta. Esto admite operaciones normales donde se realizan consultas no recursivas para los datos autoritativos. Para consultas no recursivas, se rechazan todas las respuestas de la caché dinámica.

allow_setrd
Ignora el bit de recursión deseada (RD) y trata todas las solicitudes como si el bit de recursión deseada estuviera establecido.

Tenga en cuenta que este comportamiento viola la RFC 1034, que establece que un servidor de nombres nunca debe realizar servicio recursivo a menos que se solicite a través del bit RD, ya que esto interfiere con la solución de problemas de los servidores de nombres y sus bases de datos. Este comportamiento prohibido puede ser útil si otro servidor DNS debe reenviar solicitudes para zonas específicas a un servidor DNS de resolución, pero solo admite dominios stub y envía consultas al servidor DNS de resolución con el bit RD despejado.

allow_snoop
También permite el acceso no recursivo. Esto proporciona acceso tanto recursivo como no recursivo. El nombre allow_snoop se refiere a la inspección de caché, una técnica para usar consultas no recursivas para examinar el contenido de la caché (para actos maliciosos). Sin embargo, las consultas no recursivas también pueden ser una valiosa herramienta de depuración (cuando se desea examinar el contenido de la caché).

En ese caso, utilice allow_snoop para su host de administración.

allow_cookie
Permite el acceso solo a las consultas UDP que contienen una Cookie DNS válida según lo especificado en RFC 7873 y RFC 9018, cuando la opción answer-cookie está habilitada. Las consultas UDP que contienen solo una Cookie de Cliente DNS y ninguna Cookie de Servidor, o una Cookie DNS no válida, recibirán una respuesta BADCOOKIE que incluye una Cookie DNS generada recientemente, lo que permitirá a los clientes reintentar con esa Cookie DNS. La acción allow_cookie también aceptará solicitudes a través de transportes con estado, independientemente de la presencia de una Cookie DNS y de la configuración de answer-cookie. Las consultas UDP sin Cookie DNS reciben respuestas REFUSED con el indicador TC establecido, lo que puede activar la opción de pasar a TCP para esos clientes.
deny_non_local
La acción deny_non_local es para hosts que solo tienen permitido consultar los local-data autoritativos; no se les permite la recursión completa, sino solo los datos estáticos. Los mensajes que no están permitidos se descartan.
refuse_non_local
La acción refuse_non_local es para hosts que solo tienen permitido consultar los local-data autoritativos; no se les permite la recursión completa, sino solo los datos estáticos. Los mensajes que no están permitidos reciben el código de error REFUSED.

Por defecto, solo localhost (el bloque de red IP 127.0.0.0/8, no la interfaz de bucle invertido) tiene permiso implícitamente, el resto es rechazado. El valor por defecto es refused, porque es amigable con el protocolo. El protocolo DNS no está diseñado para manejar paquetes caídos debido a políticas, y la caída puede resultar en consultas reintentadas (posiblemente excesivas).

Permit private IP addresses to be routed, or queried. Private addresses are defined by RFC 1918 (IPv4) and RFC 4193 (IPv6). Specifically, it permits the following IP ranges:

  • 172.16.0.0/12

local-zone: <zona> <tipo>
Configura una zona local. El tipo determina la respuesta que se dará si no hay coincidencia en local-data. Los tipos son deny, refuse, static, transparent, redirect, nodefault, typetransparent, inform, inform_deny, inform_redirect, always_transparent, block_a, always_refuse, always_nxdomain, always_null, y se explican a continuación. Después de eso se enumeran las configuraciones por defecto. Utilice local-data para introducir datos en la zona local. Las respuestas para las zonas locales son respuestas DNS autorizadas. Por defecto, las zonas son de clase IN.

Si necesita datos autorizados más complicados, con referencias, comodines, soporte para CNAME/DNAME o servicio autorizado de DNSSEC, configure una stub-zone para ello como se detalla en la sección de zonas stub a continuación. Una stub-zone puede ser utilizada para que unbound envíe consultas a otro servidor, un servidor autoritativo, para obtener la información. Con una forward-zone, unbound envía consultas a un servidor que es un servidor recursivo para obtener la información. Con una auth-zone, una zona puede cargarse desde un archivo y utilizarse, puede ser utilizada como una zona local para los usuarios aguas abajo, o la información de auth-zone puede ser utilizada para obtener información al resolver como si fuera un servidor upstream. Las opciones forward-zone y auth-zone se describen en sus secciones a continuación. Si desea realizar un filtrado de la información que los usuarios pueden obtener, las sentencias local-zone y local-data lo permiten, pero también se puede utilizar la funcionalidad rpz, descrita en la sección RPZ.

deny
No envíe una respuesta, descarte la consulta. Si hay una coincidencia con datos locales, la consulta se responde.
refuse
Envíe un mensaje de error de respuesta, con rcode REFUSED. Si hay una coincidencia con datos locales, la consulta se responde.
static
Si hay una coincidencia con datos locales, la consulta se responde. De lo contrario, la consulta se responde con NODATA o NXDOMAIN. Para una respuesta negativa, se incluye un SOA si está presente como local-data para el dominio apex de la zona.
transparent
Si hay una coincidencia con local-data, la consulta se responde. De lo contrario, si la consulta tiene un nombre diferente, la consulta se resuelve normalmente. Si la consulta es para un nombre dado en local-data pero no se proporciona ese tipo de datos en localdata, entonces se devuelve una respuesta NOERROR NODATA. Si no se proporciona local-zone, local-data crea una zona transparente por defecto.
typetransparent
Si hay una coincidencia con datos locales, la consulta se responde. Si la consulta es para un nombre diferente, o para el mismo nombre pero para un tipo diferente, la consulta se resuelve normalmente. Por lo tanto, similar a transparent, pero los tipos que no están listados en los datos locales se resuelven normalmente, por lo que si un registro A está en los datos locales, eso no provoca una respuesta NODATA para las consultas AAAA.
redirect
La consulta se responde con los datos locales para el nombre de la zona. Puede que no haya datos locales debajo del nombre de la zona. Esto responde a las consultas para la zona y todos los subdominios de la zona con los datos locales para la zona. Se puede utilizar para redirigir un dominio a devolver un registro de dirección diferente al usuario final, con:
local-zone: "example.com." redirect
local-data: "example.com. A 127.0.0.1"

las consultas para www.example.com y www.foo.example.com se redirigen, de modo que los usuarios con navegadores web no puedan acceder a sitios con el sufijo example.com.

inform
La consulta se responde normalmente, igual que transparent. La dirección IP del cliente (@número de puerto) se imprime en el archivo de registro. El mensaje de registro es:
timestamp, unbound-pid, info: zonename inform IP@port queryname type class.

Esta opción se puede utilizar para la resolución normal, pero las máquinas que buscan nombres infectados se registran, por ejemplo, para ejecutar antivirus en ellas.

inform_deny
La consulta se descarta, como deny, y se registra, como inform. Es decir, se encuentran máquinas infectadas sin responder a las consultas.
inform_redirect
La consulta se redirige, como redirect, y se registra, como inform. Es decir, se responden las consultas con datos fijos y también se registran las máquinas que preguntan.
always_transparent
Similar a transparent, pero ignora los datos locales y resuelve normalmente.
block_a
Similar a transparent, pero ignora los datos locales y resuelve normalmente todos los tipos de consulta, excepto A. Para consultas A, siempre devuelve NODATA. Útil en casos en los que sea necesario forzar explícitamente que todas las aplicaciones utilicen el protocolo IPv6 y eviten cualquier consulta a IPv4.
always_refuse
Similar a refuse, pero ignora los datos locales y rechaza la consulta.
always_nxdomain
Similar a static, pero ignora los datos locales y devuelve NXDOMAIN para la consulta.
always_nodata
Similar a static, pero ignora los datos locales y devuelve NODATA para la consulta.
always_deny
Similar a deny, pero ignora los datos locales y descarta la consulta.
always_null
Siempre devuelve 0.0.0.0 o ::0 para cada nombre en la zona. Similar a redirect con datos cero para A y AAAA. Ignora los datos locales en la zona. Se utiliza para algunas listas de bloqueo.
noview
Sale de esa vista y se dirige a las zonas locales globales para la respuesta a la consulta. Si view-first es no, se resolverá normalmente. Si view-first está habilitado, se realizará ese paso y se comprobarán las respuestas globales. Para cuando la vista tenga anulaciones específicas de la vista, pero alguna zona debe ser respondida desde el contenido de la zona local global.
nodefault
Se utiliza para desactivar el contenido por defecto de las zonas AS112. Los otros tipos también desactivan el contenido por defecto.
local-zone: <zona> <tipo>
Para una zona especificada, el tipo puede ser static, redirect, refuse, deny, transparent, typetransparent, o nodefault.
static
Para la zona especificada se sirve el contenido local, y para los subdominios de la zona se responde con NXDOMAIN. Este es el comportamiento predeterminado para las zonas que no son de redirección.
redirect
Para la zona especificada se sirve el contenido local, y para los subdominios de la zona se responde con la misma respuesta que para la zona especificada.
refuse
Las consultas a esta zona se rechazan con un error REFUSED.
deny
Las consultas a esta zona se rechazan con un error SERVFAIL.
transparent
Para la zona especificada se actúa como si la zona no estuviera configurada. La consulta se reenvía a otro servidor DNS.
typetransparent
Como transparent, pero solo para tipos de registro que no sean A o AAAA.

Opciones de Zona

Las opciones de zona controlan cómo Unbound trata los datos de las zonas DNS y se pueden configurar en la sección zone:.

zonemd-permissive-mode: <sí o no>
Cuando está activado, el modo permisivo para ZONEMD solo registra la ausencia de un registro ZONEMD, pero no bloquea la zona. Si está desactivado, la ausencia de un registro ZONEMD es un error que puede bloquear la zona.
zonemd-permissive-mode: <sí o no>

Con la opción desactivada, la ausencia de un ZONEMD es solo un error cuando la zona está firmada con DNSSEC, tenemos una clave de confianza y la verificación DNSSEC de la ausencia del ZONEMD falla. Con la opción activada, la ausencia de un ZONEMD es siempre un error, incluso para zonas no firmadas con DNSSEC.

Por defecto: no

zonefile: <nombre de archivo>
El nombre del archivo donde se almacena la zona. Si no se especifica, no se utiliza ningún archivo de zona. Si el archivo no existe o está vacío, Unbound intentará obtener los datos de la zona (por ejemplo, de los servidores primarios).

Opciones de Vista

Puede haber múltiples cláusulas view:. Cada una con un nombre name y cero o más atributos local-zone y local-data. Las vistas también pueden contener los atributos view-first, response-ip, response-ip-data y local-data-ptr. Las vistas se pueden mapear a las solicitudes especificando el nombre de la vista en un atributo access-control-view. Las opciones de las vistas coincidentes anularán las opciones globales. Las opciones globales se utilizarán si no se encuentra ninguna vista coincidente, o cuando la vista coincidente no tenga especificada la opción.

name: <nombre de vista>
Nombre de la vista. Debe ser único. Este nombre se utiliza en el atributo access-control-view.
local-zone: <zona> <tipo>
Elementos de zona local específicos de la vista. Tiene los mismos tipos y comportamiento que los elementos local-zone globales. Cuando se especifica al menos un local-zone: y se establece view-first: no, las zonas locales por defecto se añadirán a esta vista. Los valores por defecto se pueden deshabilitar usando el tipo nodefault. Cuando se establece view-first: yes o cuando una vista no tiene local-zone, se utilizará el local-zone global, incluyendo sus zonas por defecto.
local-data: "<cadena de registro de recursos>"
Elementos de datos locales específicos de la vista. Tiene el mismo comportamiento que los elementos local-data globales.
local-data-ptr: "DirecciónIP nombre"
Elementos local-data-ptr específicos de la vista. Tiene el mismo comportamiento que los elementos local-data-ptr globales.
view-first: <sí o no>
Si está activado, intenta utilizar local-zone y local-data globales si no hay coincidencia en las opciones específicas de la vista.

Por defecto: no

Opciones del Módulo Biblioteca Dinámica

La cláusula dynlib: proporciona la configuración para el módulo dynlib. Este módulo es solo un envoltorio muy pequeño que permite cargar módulos dinámicos en tiempo de ejecución en lugar de compilarlos en la aplicación. Para habilitar el módulo dynlib, debe compilarse en el demonio y la palabra dynlib debe incluirse en el atributo module-config. Se admiten múltiples instancias de bibliotecas dinámicas añadiendo la palabra dynlib más de una vez.

La ruta dynlib-file debe especificarse como una ruta absoluta relativa a la nueva ruta establecida por chroot, o como una ruta relativa al directorio de trabajo.

dynlib-file: <archivo dynlib>
El archivo de biblioteca dinámica a cargar. Repita esta opción por cada instancia del módulo dynlib añadida a la opción module-config.

Opciones del Módulo DNS64

El módulo dns64 debe configurarse en la directiva module-config, por ejemplo:

module-config: "dns64 validator iterator"

y compilarse en el demonio para ser habilitado.

NOTA:

Estas configuraciones van en la sección server:.
dns64-prefix: <prefijo IPv6>
Esto establece el prefijo DNS64 a usar para sintetizar registros AAAA. Debe ser /96 o más corto.

Por defecto: 64:ff9b::/96

dns64-synthall: <sí o no>

ADVERTENCIA:

¡Característica de depuración!

Si está activado, sintetiza todos los registros AAAA a pesar de la presencia de registros AAAA reales.

Por defecto: no

dns64-ignore-aaaa: <nombre de dominio>
Lista de dominios para los cuales se ignoran los registros AAAA y se utiliza el registro A en el procesamiento DNS64 en su lugar. Se puede introducir varias veces, listar un nuevo dominio para el cual se aplica, uno por línea. Se aplica también a los nombres debajo del nombre dado.

Operación NAT64

La operación NAT64 permite utilizar un prefijo NAT64 para solicitudes salientes a servidores solo IPv4. Se controla mediante dos opciones en la sección server::

do-nat64: <sí o no>
Utiliza NAT64 para alcanzar servidores solo IPv4. Considere también habilitar prefer-ip6 para preferir conexiones IPv6 nativas a los servidores de nombres.

Por defecto: no

nat64-prefix: <prefijo IPv6>
Utiliza un prefijo NAT64 específico para alcanzar servidores solo IPv4. La longitud del prefijo debe ser /32, /40, /48, /56, /64 o /96.

Por defecto: 64:ff9b::/96 (igual que dns64-prefix)

Opciones del Módulo Cache DB

El módulo Cache DB debe configurarse en la directiva module-config, p. ej.:

module-config: "validator cachedb iterator"

y debe compilarse en el demonio con --enable-cachedb.

Si este módulo está habilitado y configurado, la base de datos de backend especificada funciona como una caché de segundo nivel; cuando Unbound no encuentra una respuesta a una consulta en su caché interna en memoria, consulta el backend especificado. Si encuentra una respuesta válida en el backend, Unbound la utiliza para responder a la consulta sin realizar una resolución DNS iterativa. Si Unbound ni siquiera puede encontrar una respuesta en el backend, resuelve la consulta como de costumbre y almacena la respuesta en el backend.

Este módulo interactúa con las opciones serve-expired-* y responderá con datos expirados si Unbound está configurado para ello.

Si Unbound se compiló con --with-libhiredis en un sistema que tiene instalada la biblioteca cliente C de Redis, hiredis, entonces se puede utilizar el backend redis. Este backend se comunica con el servidor Redis especificado a través de una conexión TCP para almacenar y recuperar datos de caché. Puede utilizarse como backend de caché persistente y/o compartido.

NOTA:

Unbound nunca elimina datos almacenados en el servidor Redis, incluso si algunos datos han expirado en términos de TTL DNS o si el servidor Redis ha almacenado en caché demasiados datos; si es necesario, el servidor Redis debe configurarse para limitar el tamaño de la caché, preferiblemente con algún tipo de política de desalojo de "menos recientemente utilizado".

Además, la opción redis-expire-records se puede utilizar para establecer el TTL DNS relativo del mensaje como tiempo de espera para los registros de Redis; tenga en cuenta que se utiliza memoria adicional por clave y que la información de expiración se almacena como marcas de tiempo Unix absolutas en Redis (el tiempo del sistema debe ser estable).

Este backend utiliza comunicación síncrona con el servidor Redis, basada en la suposición de que la comunicación es estable y lo suficientemente rápida. El hilo que espera una respuesta del servidor Redis no puede manejar otras consultas DNS. Aunque el backend tiene la capacidad de reconectarse al servidor cuando la conexión se cierra inesperadamente y hay un tiempo de espera configurable en caso de que el servidor sea demasiado lento o se cuelgue, se supone que estos casos son muy raros. Si el cierre de conexión o el tiempo de espera ocurren con demasiada frecuencia, Unbound será efectivamente inutilizable con este backend. Es responsabilidad del administrador asegurarse de que la suposición se cumpla.

Especifica el nombre de la base de datos de backend. La base de datos por defecto es el backend en memoria llamado testframe, que, como su nombre indica, no es de utilidad práctica. Opciones de Zona de Política de Respuesta

Las Zonas de Política de Respuesta (RPZ) se configuran con rpz:, y cada una debe tener un atributo name. Puede haber varias, listando múltiples cláusulas RPZ, cada una con un nombre diferente. Las cláusulas RPZ se aplican en el orden de configuración y cualquier coincidencia de una zona RPZ anterior terminará la búsqueda RPZ. Tenga en cuenta que una acción PASSTHRU todavía se considera una coincidencia. El módulo respip debe agregarse a module-config, por ejemplo:

module-config: "respip validator iterator"

Se admiten los desencadenadores QNAME, Dirección IP de Respuesta, nsdname, nsip y clientip. Las acciones admitidas son: NXDOMAIN, NODATA, PASSTHRU, DROP, Datos Locales, tcp-only y
