NOMBRE

udp - Protocolo de Datagramas de Usuario para IPv4

SINOPSIS

#include <sys/socket.h>
#include <netinet/in.h>
#include <netinet/udp.h>
udp_socket = socket(AF_INET, SOCK_DGRAM, 0);

DESCRIPCIÓN

Esta es una implementación del Protocolo de Datagramas de Usuario descrito en la RFC 768. Implementa un servicio de paquetes de datagramas no conectado y no fiable. Los paquetes pueden llegar desordenados o duplicados. UDP genera y verifica sumas de verificación para detectar errores de transmisión.

Cuando se crea un socket UDP, sus direcciones locales y remotas no están especificadas. Los datagramas se pueden enviar inmediatamente usando sendto(2) o sendmsg(2) con una dirección de destino válida como argumento. Cuando se llama a connect(2) en el socket, se establece la dirección de destino predeterminada y ahora los datagramas se pueden enviar usando send(2) o write(2) sin especificar una dirección de destino. Todavía es posible enviar a otros destinos pasando una dirección a sendto(2) o sendmsg(2). Para recibir paquetes, el socket se puede vincular primero a una dirección local usando bind(2). De lo contrario, la capa de socket asignará automáticamente un puerto local libre del rango definido por /proc/sys/net/ipv4/ip_local_port_range y vinculará el socket a INADDR_ANY.

Todas las operaciones de recepción devuelven solo un paquete. Cuando el paquete es más pequeño que el buffer proporcionado, solo se devuelve esa cantidad de datos; cuando es mayor, el paquete se trunca y se establece el flag MSG_TRUNC. MSG_WAITALL no es compatible.

Las opciones de IP se pueden enviar o recibir utilizando las opciones de socket descritas en ip(7). Son procesadas por el kernel solo cuando el parámetro /proc apropiado está habilitado (pero aún se pasan al usuario incluso cuando está desactivado). Ver ip(7).

Cuando el flag MSG_DONTROUTE se establece al enviar, la dirección de destino debe referirse a una dirección de interfaz local y el paquete solo se envía a esa interfaz.

Por defecto, Linux UDP realiza el descubrimiento de MTU (Unidad de Transmisión Máxima). Esto significa que el kernel realizará un seguimiento de la MTU a una dirección IP de destino específica y devolverá EMSGSIZE cuando un paquete UDP exceda ese límite. Cuando esto sucede, la aplicación debe disminuir el tamaño del paquete. El descubrimiento de MTU de ruta también se puede desactivar usando la opción de socket IP_MTU_DISCOVER o el archivo /proc/sys/net/ipv4/ip_no_pmtu_disc; ver ip(7) para más detalles. Cuando está desactivado, UDP fragmentará los paquetes UDP salientes que excedan la MTU de la interfaz. Sin embargo, no se recomienda desactivarlo por razones de rendimiento y confiabilidad.

Formato de dirección

UDP utiliza el formato de dirección sockaddr_in de IPv4 descrito en ip(7).

Manejo de errores

Todos los errores fatales se pasarán al usuario como un error de retorno, incluso cuando el socket no esté conectado. Esto incluye errores asíncronos recibidos de la red. Puede obtener un error para un paquete anterior que se envió en el mismo socket. Este comportamiento difiere de muchas otras implementaciones de sockets BSD que no pasan ningún error a menos que el socket esté conectado. El comportamiento de Linux está ordenado por la RFC 1122.

Para compatibilidad con código heredado, en Linux 2.0 y 2.2 era posible establecer la opción SO_BSDCOMPAT de SOL_SOCKET para recibir errores remotos solo cuando el socket había sido conectado (excepto EPROTO y EMSGSIZE). Los errores generados localmente siempre se pasan. El soporte para esta opción de socket se eliminó en kernels posteriores; ver socket(7) para más información.

Cuando la opción IP_RECVERR está habilitada, todos los errores se almacenan en la cola de errores del socket y se pueden recibir mediante recvmsg(2) con el flag MSG_ERRQUEUE establecido.

Interfaces de /proc

La configuración de parámetros UDP a nivel de sistema se puede acceder a través de archivos en el directorio /proc/sys/net/ipv4/.

udp_mem (desde Linux 2.6.25)
Este es un vector de tres enteros que rige el número de páginas permitidas para la cola de todos los sockets UDP.
min
Por debajo de este número de páginas, UDP no se preocupa por su apetito de memoria. Cuando la cantidad de memoria asignada por UDP excede este número, UDP comienza a moderar el uso de memoria.
pressure
Este valor se introdujo para seguir el formato de tcp_mem (ver tcp(7)).
max
Número de páginas permitidas para la cola de todos los sockets UDP.
Los valores predeterminados para estos tres elementos se calculan en tiempo de arranque a partir de la cantidad de memoria disponible.
udp_rmem_min (entero; valor predeterminado: PAGE_SIZE; desde Linux 2.6.25)
Tamaño mínimo, en bytes, de los buffers de recepción utilizados por los sockets UDP en moderación. Cada socket UDP puede usar este tamaño para recibir datos, incluso si las páginas totales de los sockets UDP exceden la presión de udp_mem.
udp_wmem_min (entero; valor predeterminado: PAGE_SIZE; desde Linux 2.6.25)
Tamaño mínimo, en bytes, del buffer de envío utilizado por los sockets UDP en moderación. Cada socket UDP puede usar este tamaño para enviar datos, incluso si las páginas totales de los sockets UDP exceden la presión de udp_mem.

Opciones de socket

Para establecer o obtener una opción de socket UDP, llame a getsockopt(2) para leer o a setsockopt(2) para escribir la opción con el argumento de nivel de opción establecido en IPPROTO_UDP. A menos que se indique lo contrario, optval es un puntero a un int.

A continuación se muestra una lista de opciones de socket específicas de UDP. Para obtener detalles sobre algunas otras opciones de socket que también son aplicables a los sockets UDP, consulte socket(7).

UDP_CORK (desde Linux 2.5.44)
Si esta opción está habilitada, todos los datos de salida en este socket se acumulan en un solo datagrama que se transmite cuando la opción se deshabilita. Esta opción no debe usarse en código destinado a ser portable.
UDP_SEGMENT (desde Linux 4.18)
Habilita la descarga de segmentación UDP. La descarga de segmentación reduce el costo de send(2) transfiriendo varios datagramas de datos como un solo paquete grande a través de la ruta de transmisión del kernel, incluso cuando excede la MTU. Lo más tarde posible, el paquete grande se divide por tamaño de segmento en una serie de datagramas. Este paso de descarga de segmentación se pospone al hardware si es compatible, de lo contrario se realiza en software. Esta opción toma un valor en el rango [0, USHRT_MAX] que establece el tamaño del segmento: el tamaño de la carga útil del datagrama, excluyendo la cabecera UDP. DESCRIPTION

UDP (User Datagram Protocol) is a connectionless protocol that provides a limited transport layer service on top of the Internet Protocol (IP). UDP does not guarantee that datagrams reach their destination, nor that they are delivered in the order in which they were sent. The protocol provides no mechanism for error detection or recovery.

UDP datagrams are delivered to the process(es) associated with the socket.

Socket options

These socket options are set using setsockopt(2) and retrieved using getsockopt(2). The option level is IPPROTO_UDP for all options described here, except where noted.

UDP_CORK (since Linux 2.6.24)
Enables or disables UDP segmentation offload (USO) for outgoing UDP datagrams. When enabled (value is non-zero), the kernel will try to group multiple UDP datagrams into a single IP packet. This can reduce CPU overhead on the sender. The socket option UDP_CORK should be set to 1 to enable this feature. The application must then call sendmsg(2) multiple times to send data. When the application is finished sending data for a particular group of datagrams, it should call sendmsg(2) with the MSG_MORE flag set. Finally, to send the last datagram and flush the buffer, the application calls sendmsg(2) without the MSG_MORE flag. Setting UDP_CORK to 0 disables this feature and should be done after sending the last datagram. Setting UDP_CORK to 0 flushes any pending data. This option should not be used in code intended to be portable. See also sendmmsg(2) and ip(7).
UDP_GRO (since Linux 5.0)
Enables UDP receive offload. If enabled, the socket may receive multiple datagrams worth of data as a single large buffer, together with a cmsg(3) that holds the segment size. This option is the inverse of segmentation offload. It reduces receive cost by handling multiple datagrams worth of data as a single large packet in the kernel receive path, even when that exceeds MTU. This option should not be used in code intended to be portable.

Ioctls

These ioctls can be accessed using ioctl(2). The correct syntax is:

int value;
error = ioctl(udp_socket, ioctl_type, &value);
FIONREAD (SIOCINQ)
Gets a pointer to an integer as argument. Returns the size of the next pending datagram in the integer in bytes, or 0 when no datagram is pending. Warning: Using FIONREAD, it is impossible to distinguish the case where no datagram is pending from the case where the next pending datagram contains zero bytes of data. It is safer to use select(2), poll(2), or epoll(7) to distinguish these cases.
TIOCOUTQ (SIOCOUTQ)
Returns the number of data bytes in the local send queue. Supported only with Linux 2.4 and above.

In addition, all ioctls documented in ip(7) and socket(7) are supported.

ERRORS

All errors documented for socket(7) or ip(7) may be returned by a send or receive on a UDP socket.

ECONNREFUSED
No receiver was associated with the destination address. This might be caused by a previous packet sent over the socket.

VERSIONS

IP_RECVERR is a new feature in Linux 2.2.
