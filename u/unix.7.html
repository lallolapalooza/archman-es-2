NOMBRE

unix - sockets para comunicación interproceso local

SINOPSIS

#include <sys/socket.h>
#include <sys/un.h>
unix_socket = socket(AF_UNIX, type, 0);
error = socketpair(AF_UNIX, type, 0, int *sv);

DESCRIPCIÓN

La familia de sockets AF_UNIX (también conocida como AF_LOCAL) se utiliza para comunicarse eficientemente entre procesos en la misma máquina. Tradicionalmente, los sockets de dominio UNIX pueden ser sin nombre o estar enlazados a una ruta de sistema de archivos (marcados como de tipo socket). Linux también soporta un espacio de nombres abstracto que es independiente del sistema de archivos.

Los tipos de socket válidos en el dominio UNIX son: SOCK_STREAM, para un socket orientado a flujo; SOCK_DGRAM, para un socket de datagrama que preserva los límites de los mensajes (como en la mayoría de las implementaciones UNIX, los sockets de datagrama de dominio UNIX son siempre fiables y no reordenan los datagramas); y (desde Linux 2.6.4) SOCK_SEQPACKET, para un socket de paquetes secuenciados que está orientado a la conexión, preserva los límites de los mensajes y entrega los mensajes en el orden en que se enviaron.

Los sockets de dominio UNIX soportan el paso de descriptores de archivo o credenciales de proceso a otros procesos utilizando datos auxiliares.

Formato de dirección

Una dirección de socket UNIX se representa en la siguiente estructura:


struct sockaddr_un {
    sa_family_t sun_family;               /* AF_UNIX */
    char        sun_path[108];            /* Ruta */
};

El campo sun_family siempre contiene AF_UNIX. En Linux, sun_path tiene un tamaño de 108 bytes; ver también ERRORES, abajo.

Varias llamadas al sistema (por ejemplo, bind(2), connect(2) y sendto(2)) toman un argumento sockaddr_un como entrada. Algunas otras llamadas al sistema (por ejemplo, getsockname(2), getpeername(2), recvfrom(2) y accept(2)) devuelven un argumento de este tipo.

Se distinguen tres tipos de dirección en la estructura sockaddr_un:

ruta
un socket de dominio UNIX puede enlazarse a una ruta de sistema de archivos terminada en nulo utilizando bind(2). Cuando se devuelve la dirección de un socket de ruta, su longitud es

offsetof(struct sockaddr_un, sun_path) + strlen(sun_path) + 1

y sun_path contiene la ruta terminada en nulo. (En Linux, la expresión offsetof() anterior es equivalente al mismo valor que sizeof(sa_family_t), pero algunas otras implementaciones incluyen otros campos antes de sun_path, por lo que la expresión offsetof() describe de forma más portable el tamaño de la estructura de dirección.)
Para más detalles sobre sockets de ruta, ver abajo.
sin nombre
un socket de flujo que no ha sido enlazado a una ruta usando bind(2) no tiene nombre. Igualmente, los dos sockets creados por socketpair(2) no tienen nombre. Cuando se devuelve la dirección de un socket sin nombre, su longitud es sizeof(sa_family_t), y no se debe inspeccionar sun_path.
abstracto
una dirección de socket abstracta se distingue (de un socket de ruta) por el hecho de que sun_path[0] es un byte nulo ('\0'). La dirección del socket en este espacio de nombres viene dada por los bytes adicionales en sun_path que están cubiertos por la longitud especificada de la estructura de dirección. (Los bytes nulos en el nombre no tienen significado especial.) El nombre no tiene conexión con las rutas del sistema de archivos. Cuando se devuelve la dirección de un socket abstracto, el addrlen devuelto es mayor que sizeof(sa_family_t) (es decir, mayor que 2), y el nombre del socket está contenido en los primeros (addrlen - sizeof(sa_family_t)) bytes de sun_path.

Sockets de ruta

Al enlazar un socket a una ruta, se deben observar algunas reglas para máxima portabilidad y facilidad de codificación:

•
La ruta en sun_path debe estar terminada en nulo.
•
La longitud de la ruta, incluyendo el byte nulo terminador, no debe exceder el tamaño de sun_path.
•
El argumento addrlen que describe la estructura sockaddr_un envolvente debe tener un valor de al menos:

offsetof(struct sockaddr_un, sun_path)+strlen(addr.sun_path)+1

o, más sencillamente, addrlen puede especificarse como sizeof(struct sockaddr_un).

Existe cierta variación en cómo las implementaciones manejan las direcciones de sockets de dominio UNIX que no siguen las reglas anteriores. Por ejemplo, algunas (pero no todas) implementaciones añaden un terminador nulo si no se encuentra uno en el sun_path suministrado.

Al codificar aplicaciones portables, tenga en cuenta que algunas implementaciones tienen sun_path tan corto como 92 bytes.

Varias llamadas al sistema (accept(2), recvfrom(2), getsockname(2), getpeername(2)) devuelven estructuras de dirección de socket. Cuando se aplican a sockets de dominio UNIX, el argumento addrlen de valor-resultado suministrado a la llamada debe inicializarse como se indicó. Al regresar, el argumento se establece para indicar el tamaño *real* de la estructura de dirección. El llamante debe comprobar el valor devuelto en este argumento: si el valor de salida excede el valor de entrada, entonces no hay garantía de que haya un terminador nulo en sun_path. (Ver ERRORES.)

Propiedad y permisos del socket de ruta

En la implementación de Linux, los sockets de ruta respetan los permisos del directorio en el que se encuentran. La creación de un nuevo socket falla si el proceso no tiene permiso de escritura y búsqueda (ejecución) en el directorio en el que se crea el socket.

En Linux, conectarse a un objeto de socket de flujo requiere permiso de escritura en ese socket; enviar un datagrama a un socket de datagrama requiere de manera similar permiso de escritura en ese socket. POSIX no hace ninguna declaración sobre el efecto de los permisos en un archivo de socket, y en algunos sistemas (p. ej., BSDs antiguos), los permisos del socket se ignoran. Los programas portables no deben depender de esta característica para la seguridad.

Al crear un nuevo socket, el propietario y el grupo del archivo de socket se establecen según las reglas habituales. El archivo de socket tiene todos los permisos habilitados, excepto aquellos que son desactivados por el umask(2) del proceso.

El propietario, grupo y permisos de un socket de ruta pueden cambiarse (usando chown(2) y chmod(2)).

Sockets abstractos

Los permisos de socket no tienen significado para los sockets abstractos: el umask(2) del proceso no tiene efecto al enlazar un socket abstracto, y cambiar la propiedad y los permisos del objeto (mediante fchown(2) y fchmod(2)) no tiene efecto en la accesibilidad del socket.

Los sockets abstractos desaparecen automáticamente cuando se cierran todas las referencias abiertas al socket.

El espacio de nombres de sockets abstractos es una extensión no portable de Linux.

SO_PASSCRED
Habilitar esta opción de socket provoca la recepción de las credenciales del proceso que envía en un mensaje auxiliar SCM_CREDENTIALS en cada mensaje recibido posteriormente. Las credenciales devueltas son las especificadas por el remitente usando SCM_CREDENTIALS, o un valor predeterminado que incluye el PID, el ID de usuario real y el ID de grupo real del remitente, si el remitente no especificó datos auxiliares SCM_CREDENTIALS.

Habilita la recepción de la etiqueta de seguridad SELinux del socket peer en un mensaje auxiliar de tipo SCM_SECURITY (ver más abajo).
El valor proporcionado como argumento a setsockopt(2) y devuelto como resultado de getsockopt(2) es una bandera booleana entera.
La opción SO_PASSSEC es compatible con sockets de datagramas del dominio UNIX desde Linux 2.6.18; el soporte para sockets de stream del dominio UNIX se añadió en Linux 4.2.
SO_PEEK_OFF
Ver socket(7).
SO_PEERCRED
Esta opción de socket de solo lectura devuelve las credenciales del proceso peer conectado a este socket. Las credenciales devueltas son las que estaban en vigor en el momento de la llamada a connect(2), listen(2) o socketpair(2).
El argumento para getsockopt(2) es un puntero a una estructura ucred; define la macro de prueba de características _GNU_SOURCE para obtener la definición de esa estructura desde <sys/socket.h>.
El uso de esta opción solo es posible para sockets de stream AF_UNIX conectados y para pares de sockets de stream y datagramas AF_UNIX creados usando socketpair(2).
SO_PEERSEC
Esta opción de socket de solo lectura devuelve el contexto de seguridad del socket peer conectado a este socket. Por defecto, será el mismo que el contexto de seguridad del proceso que creó el socket peer, a menos que sea anulado por la política o por un proceso con los permisos necesarios.
El argumento para getsockopt(2) es un puntero a un búfer de la longitud especificada en bytes en el que se copiará la cadena del contexto de seguridad. Si la longitud del búfer es menor que la longitud de la cadena del contexto de seguridad, entonces getsockopt(2) devuelve -1, establece errno a ERANGE y devuelve la longitud requerida a través de optlen. El llamador debe asignar al menos NAME_MAX bytes para el búfer inicialmente, aunque no se garantiza que sea suficiente. Puede ser necesario redimensionar el búfer a la longitud devuelta y reintentar.
La cadena del contexto de seguridad puede incluir un carácter nulo de terminación en la longitud devuelta, pero no se garantiza que lo haga: un contexto de seguridad "foo" podría representarse como {'f','o','o'} de longitud 3 o {'f','o','o','\0'} de longitud 4, que se consideran intercambiables. La cadena es imprimible, no contiene caracteres nulos no terminadores y está en una codificación no especificada (en particular, no se garantiza que sea ASCII o UTF-8).
El uso de esta opción para sockets en la familia de direcciones AF_UNIX es compatible desde Linux 2.6.2 para sockets de stream conectados, y desde Linux 4.18 también para pares de sockets de stream y datagramas creados usando socketpair(2).

Característica de autovinculación

Si una llamada a bind(2) especifica addrlen como sizeof(sa_family_t), o si se especificó la opción de socket SO_PASSCRED para un socket que no estaba explícitamente vinculado a una dirección, entonces el socket se auto-vincula a una dirección abstracta. La dirección consiste en un byte nulo seguido de 5 bytes en el conjunto de caracteres [0-9a-f]. Por lo tanto, hay un límite de 2^20 direcciones de auto-vinculación. (Desde Linux 2.1.15, cuando se añadió la característica de auto-vinculación, se usaron 8 bytes, y el límite era por lo tanto de 2^32 direcciones de auto-vinculación. El cambio a 5 bytes se produjo en Linux 2.3.15.)

API de sockets

Los siguientes párrafos describen detalles específicos del dominio y características no compatibles de la API de sockets para sockets del dominio UNIX en Linux.

Los sockets del dominio UNIX no admiten la transmisión de datos fuera de banda (la bandera MSG_OOB para send(2) y recv(2)).

La bandera MSG_MORE de send(2) no es compatible con los sockets del dominio UNIX.

Antes de Linux 3.4, el uso de MSG_TRUNC en el argumento flags de recv(2) no era compatible con los sockets del dominio UNIX.

La opción de socket SO_SNDBUF tiene un efecto en los sockets del dominio UNIX, pero la opción SO_RCVBUF no. Para sockets de datagramas, el valor de SO_SNDBUF impone un límite superior al tamaño de los datagramas salientes. Este límite se calcula como el valor de la opción duplicado (ver socket(7)) menos 32 bytes utilizados para la sobrecarga.

Mensajes auxiliares

Los datos auxiliares se envían y reciben usando sendmsg(2) y recvmsg(2). Por razones históricas, los tipos de mensajes auxiliares listados a continuación se especifican con un tipo SOL_SOCKET aunque son específicos de AF_UNIX. Para enviarlos, establezca el campo cmsg_level de la estructura cmsghdr a SOL_SOCKET y el campo cmsg_type al tipo. Para más información, ver cmsg(3).

SCM_RIGHTS
Enviar o recibir un conjunto de descriptores de archivo abiertos de otro proceso. La porción de datos contiene un array entero de los descriptores de archivo.
Comúnmente, esta operación se denomina "pasar un descriptor de archivo" a otro proceso. Sin embargo, más precisamente, lo que se está pasando es una referencia a una descripción de archivo abierta (ver open(2)), y en el proceso receptor es probable que se utilice un número de descriptor de archivo diferente. Semánticamente, esta operación es equivalente a duplicar (dup(2)) un descriptor de archivo en la tabla de descriptores de archivo de otro proceso.
Si el búfer utilizado para recibir los datos auxiliares que contienen descriptores de archivo es demasiado pequeño (o está ausente), los datos auxiliares se truncan (o se descartan) y los descriptores de archivo excedentes se cierran automáticamente en el proceso receptor.
Si el número de descriptores de archivo recibidos en los datos auxiliares hiciera que el proceso excediera su límite de recursos RLIMIT_NOFILE (ver getrlimit(2)), los descriptores de archivo excedentes se cierran automáticamente en el proceso receptor.
La constante del kernel SCM_MAX_FD define un límite en el número de descriptores de archivo en el array. Intentar enviar un array más grande que este límite provoca que sendmsg(2) falle con el error EINVAL. SCM_MAX_FD tiene el valor 253 (o 255 antes de Linux 2.6.38).
SCM_CREDENTIALS
Enviar o recibir credenciales de UNIX. Esto se puede usar para la autenticación. Las credenciales se pasan como un mensaje auxiliar struct ucred. Esta estructura se define en <sys/socket.h> como sigue:

struct ucred {
    pid_t pid;    /* Process ID of the sending process */
    uid_t uid;    /* User ID of the sending process */
    gid_t gid;    /* Group ID of the sending process */
};

Desde glibc 2.8, la macro de prueba de características _GNU_SOURCE debe definirse (antes de incluir cualquier archivo de cabecera) para obtener la definición de esta estructura.
Las credenciales que especifica el remitente son verificadas por el kernel. A un proceso privilegiado se le permite especificar valores que no coinciden con los suyos. El remitente debe especificar su propio ID de proceso (a menos que tenga la capacidad CAP_SYS_ADMIN, en cuyo caso se puede especificar el PID de cualquier proceso existente), su ID de usuario real, ID de usuario efectivo o ID de usuario guardado (a menos que tenga CAP_SETUID), y su ID de grupo real, ID de grupo efectivo o ID de grupo guardado (a menos que tenga CAP_SETGID).
Para recibir un mensaje struct ucred, la opción SO_PASSCRED debe estar habilitada en el socket.
SCM_SECURITY
Recibir el contexto de seguridad SELinux (la etiqueta de seguridad) del socket peer. Los datos auxiliares recibidos son una cadena terminada en nulo que contiene el contexto de seguridad. El receptor debe asignar al menos NAME_MAX bytes en la porción de datos del mensaje auxiliar para estos datos.
Para recibir el contexto de seguridad, la opción SO_PASSSEC debe estar habilitada en el socket (ver arriba).

Al enviar datos auxiliares con sendmsg(2), solo se puede incluir un elemento de cada uno de los tipos anteriores en el mensaje enviado.

Se debe enviar al menos un byte de datos reales al enviar datos auxiliares. En Linux, esto es necesario para enviar correctamente datos auxiliares a través de un socket de stream del dominio UNIX. Al enviar datos auxiliares a través de un socket de datagramas del dominio UNIX, no es necesario en Linux enviar ningún dato acompañante

ANCILLARY DATA

Ancillary data (also known as control data) is used to pass protocol-specific information or other miscellaneous data along with the normal data associated with a socket. The format of ancillary data is defined by the socket type and the protocol used. For UNIX domain sockets, ancillary data can be used to pass credentials (e.g., process ID, user ID, group ID) and file descriptors (see SCM_RIGHTS below).

When sending ancillary data using sendmsg(2), the data is specified in the msg_control member of the msghdr structure. This member points to a buffer containing one or more cmsghdr structures. Each cmsghdr structure describes an ancillary data unit:

struct cmsghdr {
    size_t  cmsg_len;    // Total length of the data unit, including
                         // the cmsghdr structure itself
    int   cmsg_level;  // Originating protocol level
    int   cmsg_type;   // Protocol-specific type
// followed by the actual data
};

The cmsg_level field is typically set to the socket level that defines the ancillary data type (e.g., SOL_SOCKET for socket options). The cmsg_type field specifies the type of ancillary data. Common types for UNIX domain sockets include:

SCM_CREDENTIALS
Passes the credentials (UID, GID, PID) of the sender. The data is a structure of type struct ucred. This requires the socket to be created with the SO_PEERCRED option enabled (see setsockopt(2)). This is only supported by UNIX domain sockets.
SCM_RIGHTS
Used to pass open file descriptors from one process to another. The data is an array of integers, where each integer is a file descriptor number. This is a powerful mechanism, but it must be used with caution. The receiving process must have the necessary permissions to use the passed file descriptors. This is supported by most socket types, including UNIX domain sockets. Portable applications should ensure that at least one byte of real data is sent along with ancillary data when using datagram sockets.

When receiving ancillary data using recvmsg(2), the msg_control buffer is used to store the received ancillary data. The msg_controllen member of the msghdr structure specifies the maximum size of the buffer, and upon return, it is updated to indicate the actual amount of ancillary data received.

Ancillary data received on stream sockets acts as a barrier. Data sent in the same sendmsg(2) call as ancillary data will be received together. If multiple sendmsg(2) calls are made with and without ancillary data, the receiver will see the data in the order it was sent, with the ancillary data being associated with the specific send operation that included it. If a stream socket receives data and its ancillary data buffer is too small, the ancillary data will be truncated, and the MSG_CTRUNC flag will be set in msg.msg_flags.

If no buffer is provided for incoming ancillary data (i.e., msg_control is NULL), the ancillary data is discarded, and MSG_CTRUNC will be set if any ancillary data was sent.

Portable applications should also include at least one byte of real data when sending ancillary data over a datagram socket.

When receiving from a stream socket, ancillary data forms a kind of barrier for the received data. For example, suppose that the sender transmits as follows:

(1)
sendmsg(2) of four bytes, with no ancillary data.
(2)
sendmsg(2) of one byte, with ancillary data.
(3)
sendmsg(2) of four bytes, with no ancillary data.

Suppose that the receiver now performs recvmsg(2) calls each with a buffer size of 20 bytes. The first call will receive five bytes of data, along with the ancillary data sent by the second sendmsg(2) call. The next call will receive the remaining four bytes of data.

If the space allocated for receiving incoming ancillary data is too small then the ancillary data is truncated to the number of headers that will fit in the supplied buffer (or, in the case of an SCM_RIGHTS file descriptor list, the list of file descriptors may be truncated). If no buffer is provided for incoming ancillary data (i.e., the msg_control field of the msghdr structure supplied to recvmsg(2) is NULL), then the incoming ancillary data is discarded. In both of these cases, the MSG_CTRUNC flag will be set in the msg.msg_flags value returned by recvmsg(2).

Ioctls

The following ioctl(2) calls return information in value. The correct syntax is:

int value;
error = ioctl(unix_socket, ioctl_type, &value);

ioctl_type can be:

SIOCINQ
For SOCK_STREAM sockets, this call returns the number of unread bytes in the receive buffer. The socket must not be in LISTEN state, otherwise an error (EINVAL) is returned. SIOCINQ is defined in <linux/sockios.h>. Alternatively, you can use the synonymous FIONREAD, defined in <sys/ioctl.h>. For SOCK_DGRAM sockets, the returned value is the same as for Internet domain datagram sockets; see udp(7).

ERRORS

EADDRINUSE
The specified local address is already in use or the filesystem socket object already exists.
EBADF
This error can occur for sendmsg(2) when sending a file descriptor as ancillary data over a UNIX domain socket (see the description of SCM_RIGHTS, above), and indicates that the file descriptor number that is being sent is not valid (e.g., it is not an open file descriptor).
ECONNREFUSED
The remote address specified by connect(2) was not a listening socket. This error can also occur if the target pathname is not a socket.
ECONNRESET
Remote socket was unexpectedly closed.
EFAULT
User memory address was not valid.
EINVAL
Invalid argument passed. A common cause is that the value AF_UNIX was not specified in the sun_type field of passed addresses, or the socket was in an invalid state for the applied operation.
EISCONN
connect(2) called on an already connected socket or a target address was specified on a connected socket.
ENFILE
The system-wide limit on the total number of open files has been reached.
ENOENT
The pathname in the remote address specified to connect(2) did not exist.
ENOMEM
Out of memory.
ENOTCONN
Socket operation needs a target address, but the socket is not connected.
EOPNOTSUPP
Stream operation called on non-stream oriented socket or tried to use the out-of-band data option.
EPERM
The sender passed invalid credentials in the struct ucred.
EPIPE
Remote socket was closed on a stream socket. If enabled, a SIGPIPE is sent as well. This can be avoided by passing the MSG_NOSIGNAL flag to send(2) or sendmsg(2).
EPROTONOSUPPORT
Passed protocol is not AF_UNIX.
EPROTOTYPE
Remote socket does not match the local socket type (SOCK_DGRAM versus SOCK_STREAM).
ESOCKTNOSUPPORT
Unknown socket type.
ESRCH
While sending an ancillary message containing credentials (SCM_CREDENTIALS), the caller specified a PID that does not match any existing process.
ETOOMANYREFS
This error can occur for sendmsg(2) when sending a file descriptor as ancillary data over a UNIX domain socket (see the description of SCM_RIGHTS, above). It occurs if the number of "in-flight" file descriptors exceeds the RLIMIT_NOFILE resource limit and the caller does not have the CAP_SYS_RESOURCE capability. An in-flight file descriptor is one that has been sent using sendmsg(2) but has not yet been accepted in the recipient process using recvmsg(2).
This error is diagnosed since mainline Linux 4.5 (and in some earlier kernel versions where the fix has been backported). In earlier kernel versions, it was possible to place an unlimited number of file descriptors in flight, by sending each file descriptor with sendmsg(2) and then closing the file descriptor so that it was not accounted against the RLIMIT_NOFILE resource limit.

Other errors can be generated by the generic socket layer or by the filesystem while generating a filesystem socket object. See the appropriate manual pages for more information.

VERSIONS

SCM_CREDENTIALS and the abstract namespace were introduced with Linux 2.2 and should not be used in portable programs. (Some BSD-derived systems also support credential passing, but the implementation details differ.)

NOTES

Binding to a socket with a filename creates a socket in the filesystem that must be deleted by the caller when it is no longer needed (using unlink(2)). The usual UNIX close-behind semantics apply; the socket can be unlinked at any time and will be finally removed from the filesystem when the last reference to it is closed.

To pass file descriptors or credentials over a SOCK_STREAM socket, you must send or receive at least one byte of nonancillary data in the same sendmsg(2) or recvmsg(2) call.

UNIX domain stream sockets do not support the notion of out-of-band data.

BUGS

When binding a socket to an address, Linux is one of the implementations that append a null terminator if none is supplied in sun_path. In most cases this is unproblematic: when the socket address is retrieved, it will be one byte longer than that supplied when the socket was bound. However, there is one case where confusing behavior can result: if 108 non-null bytes are supplied when a socket is bound, then the addition of the null terminator takes the length of the pathname beyond sizeof(sun_path). Consequently, when retrieving the socket address (for example, via accept(2)), if the input addrlen argument for the retrieving call is specified as sizeof(struct sockaddr_un), then the returned address structure won't have a null terminator in sun_path.

In addition, some implementations don't require a null terminator when binding a socket (the addrlen argument is used to determine the length of sun_path) and when the socket address is retrieved on these implementations, there is no null terminator in sun_path.

Applications that retrieve socket addresses can (portably) code to handle the possibility that there is no null terminator in sun_path by respecting the fact that the number of valid bytes in the pathname is:


strnlen(addr.sun_path, addrlen - offsetof(sockaddr_un, sun_path))

Alternatively, an application can retrieve the socket address by allocating a buffer of size sizeof(struct sockaddr_un)+1 that is zeroed out before the retrieval. The retrieving call can specify addrlen as sizeof(struct sockaddr_un), and the extra zero byte ensures that there will be a null terminator for the string returned in sun_path:


void *addrp;
addrlen = sizeof(struct sockaddr_un);
addrp = malloc(addrlen + 1);
if (addrp == NULL)
    /* Handle error */ ;
memset(addrp, 0, addrlen + 1);
if (getsockname(sfd, (struct sockaddr *) addrp, &addrlen)) == -1)
    /* handle error */ ;
printf("sun_path = %s\n", ((struct sockaddr_un *) addrp)->sun_path);

EJEMPLOS

El siguiente código demuestra el uso de sockets de paquetes secuenciados para la comunicación interproceso local. Consta de dos programas. El programa servidor espera una conexión del programa cliente. El cliente envía cada uno de sus argumentos de línea de comandos en mensajes separados. El servidor trata los mensajes entrantes como enteros y los suma. El cliente envía la cadena de comando "END". El servidor envía de vuelta un mensaje que contiene la suma de los enteros del cliente. El cliente imprime la suma y sale. El servidor espera a que se conecte el siguiente cliente. Para detener el servidor, el cliente se llama con el argumento de línea de comandos "DOWN".

La siguiente salida se registró mientras se ejecutaba el servidor en segundo plano y se ejecutaba repetidamente el cliente. La ejecución del programa servidor termina cuando recibe el comando "DOWN".

Salida de ejemplo


$ ./server &
[1] 25887
$ ./client 3 4;
Result = 7
$ ./client 11 -5;
Result = 6
$ ./client DOWN;
Result = 0
[1]+  Done                    ./server
$

Origen del programa

/*
 * Archivo connection.h
 */
#ifndef CONNECTION_H
#define CONNECTION_H
#define SOCKET_NAME "/tmp/9Lq7BNBnBycd6nxy.socket"
#define BUFFER_SIZE 12
#endif  // guarda de inclusión
/*
 * Archivo server.c
 */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/socket.h>
#include <sys/types.h>
#include <sys/un.h>
#include <unistd.h>
#include "connection.h"
int
main(void)
{
    int                 down_flag = 0;
    int                 ret;
    int                 connection_socket;
    int                 data_socket;
    int                 result;
    ssize_t             r, w;
    struct sockaddr_un  name;
    char                buffer[BUFFER_SIZE];
    /* Crear socket local.  */
    connection_socket = socket(AF_UNIX, SOCK_SEQPACKET, 0);
    if (connection_socket == -1) {
        perror("socket");
        exit(EXIT_FAILURE);
    }
    /*
     * Para portabilidad, borrar toda la estructura, ya que algunas
     * implementaciones tienen campos adicionales (no estándar) en
     * la estructura.
     */
    memset(&name, 0, sizeof(name));
    /* Enlazar socket con nombre de socket.  */
    name.sun_family = AF_UNIX;
    strncpy(name.sun_path, SOCKET_NAME, sizeof(name.sun_path) - 1);
    ret = bind(connection_socket, (const struct sockaddr *) &name,
               sizeof(name));
    if (ret == -1) {
        perror("bind");
        exit(EXIT_FAILURE);
    }
    /*
     * Preparar para aceptar conexiones.  El tamaño de la cola de espera se establece
     * en 20.  Por lo tanto, mientras una solicitud está siendo procesada, otras solicitudes
     * pueden estar esperando.
     */
    ret = listen(connection_socket, 20);
    if (ret == -1) {
        perror("listen");
        exit(EXIT_FAILURE);
    }
    /* Este es el bucle principal para manejar conexiones.  */
    for (;;) {
        /* Esperar conexión entrante.  */
        data_socket = accept(connection_socket, NULL, NULL);
        if (data_socket == -1) {
            perror("accept");
            exit(EXIT_FAILURE);
        }
        result = 0;
        for (;;) {
            /* Esperar el siguiente paquete de datos.  */
            r = read(data_socket, buffer, sizeof(buffer));
            if (r == -1) {
                perror("read");
                exit(EXIT_FAILURE);
            }
            /* Asegurar que el buffer termine en 0.  */
            buffer[sizeof(buffer) - 1] = 0;
            /* Manejar comandos.  */
            if (!strncmp(buffer, "DOWN", sizeof(buffer))) {
                down_flag = 1;
                continue;
            }
            if (!strncmp(buffer, "END", sizeof(buffer))) {
                break;
            }
            if (down_flag) {
                continue;
            }
            /* Añadir sumando recibido.  */
            result += atoi(buffer);
        }
        /* Enviar resultado.  */
        sprintf(buffer, "%d", result);
        w = write(data_socket, buffer, sizeof(buffer));
        if (w == -1) {
            perror("write");
            exit(EXIT_FAILURE);
        }
        /* Cerrar socket.  */
        close(data_socket);
        /* Salir con el comando DOWN.  */
        if (down_flag) {
            break;
        }
    }
    close(connection_socket);
    /* Desvincular el socket.  */
    unlink(SOCKET_NAME);
    exit(EXIT_SUCCESS);
}
/*
 * Archivo client.c
 */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/socket.h>
#include <sys/types.h>
#include <sys/un.h>
#include <unistd.h>
#include "connection.h"
int
main(int argc, char *argv[])
{
    int                 ret;
    int                 data_socket;
    ssize_t             r, w;
    struct sockaddr_un  addr;
    char                buffer[BUFFER_SIZE];
    /* Crear socket local.  */
    data_socket = socket(AF_UNIX, SOCK_SEQPACKET, 0);
    if (data_socket == -1) {
        perror("socket");
        exit(EXIT_FAILURE);
    }
    /*
     * Para portabilidad, borrar toda la estructura, ya que algunas
     * implementaciones tienen campos adicionales (no estándar) en
     * la estructura.
     */
    memset(&addr, 0, sizeof(addr));
    /* Conectar socket a la dirección del socket.  */
    addr.sun_family = AF_UNIX;
    strncpy(addr.sun_path, SOCKET_NAME, sizeof(addr.sun_path) - 1);
    ret = connect(data_socket, (const struct sockaddr *) &addr,
                   sizeof(addr));
    if (ret == -1) {
        fprintf(stderr, "El servidor está caído.\n");
        exit(EXIT_FAILURE);
    }
    /* Enviar argumentos.  */
    for (int i = 1; i < argc; ++i) {
        w = write(data_socket, argv[i], strlen(argv[i]) + 1);
        if (w == -1) {
            perror("write");
            break;
        }
    }
    /* Solicitar resultado.  */
    strcpy(buffer, "END");
    w = write(data_socket, buffer, strlen(buffer) + 1);
    if (w == -1) {
        perror("write");
        exit(EXIT_FAILURE);
    }
    /* Recibir resultado.  */
    r = read(data_socket, buffer, sizeof(buffer));
    if (r == -1) {
        perror("read");
        exit(EXIT_FAILURE);
    }
    /* Asegurar que el buffer termine en 0.  */
    buffer[sizeof(buffer) - 1] = 0;
    printf("Resultado = %s\n", buffer);
    /* Cerrar socket.  */
    close(data_socket);
    exit(EXIT_SUCCESS);
}
