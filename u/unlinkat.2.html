unlink(2) Manual de llamadas al sistema unlink(2)

NOMBRE

unlink, unlinkat - eliminar un nombre y posiblemente el archivo al que hace referencia

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

SINOPSIS

#include <unistd.h>
int unlink(const char *path);
#include <fcntl.h>           /* Definición de constantes AT_* */
#include <unistd.h>
int unlinkat(int dirfd, const char *path, int flags);
Requisitos de macro de prueba de características para glibc (ver feature_test_macros(7)):

unlinkat():

    Desde glibc 2.10:
        _POSIX_C_SOURCE >= 200809L
    Antes de glibc 2.10:
        _ATFILE_SOURCE

DESCRIPCIÓN

unlink() elimina un nombre del sistema de archivos. Si ese nombre era el último enlace a un archivo y ningún proceso tiene el archivo abierto, el archivo se elimina y el espacio que ocupaba se pone a disposición para su reutilización.

Si el nombre era el último enlace a un archivo pero todavía hay procesos con el archivo abierto, el archivo permanecerá en existencia hasta que se cierre el último descriptor de archivo que haga referencia a él.

Si el nombre hacía referencia a un enlace simbólico, se elimina el enlace.

Si el nombre hacía referencia a un socket, FIFO o dispositivo, se elimina el nombre para él, pero los procesos que tengan el objeto abierto pueden seguir utilizándolo.

unlinkat()

La llamada al sistema unlinkat() opera exactamente de la misma manera que unlink() o rmdir(2) (dependiendo de si flags incluye o no el indicador AT_REMOVEDIR) excepto por las diferencias descritas aquí.

Si path es relativo, entonces se interpreta en relación con el directorio al que hace referencia el descriptor de archivo dirfd (en lugar de en relación con el directorio de trabajo actual del proceso llamante, como hacen unlink() y rmdir(2) para un nombre de ruta relativo).

Si path es relativo y dirfd es el valor especial AT_FDCWD, entonces path se interpreta en relación con el directorio de trabajo actual del proceso llamante (como unlink() y rmdir(2)).

Si path es absoluto, entonces dirfd se ignora.

flags es una máscara de bits que puede especificarse como 0, o combinando valores de indicadores que controlan la operación de unlinkat(). Actualmente, solo se define un indicador:

AT_REMOVEDIR
Por defecto, unlinkat() realiza el equivalente de unlink() sobre path. Si se especifica el indicador AT_REMOVEDIR, realiza el equivalente de rmdir(2) sobre path.

Ver openat(2) para una explicación de la necesidad de unlinkat().

VALOR DE RETORNO

En caso de éxito, se devuelve cero. En caso de error, se devuelve -1 y se establece la variable errno para indicar el error.

ERRORES

EACCES
El acceso de escritura al directorio que contiene path no está permitido para el UID efectivo del proceso, o uno de los directorios en path no permitió permisos de búsqueda. (Ver también path_resolution(7)).
EBUSY
No se puede eliminar path porque está siendo utilizado por el sistema u otro proceso; por ejemplo, es un punto de montaje o el software cliente NFS lo creó para representar un inodo activo pero sin nombre ( "NFS silly renamed").
EFAULT
path apunta fuera de su espacio de direcciones accesible.
EIO
Ocurrió un error de E/S.
EISDIR
path se refiere a un directorio. (Este es el valor no POSIX devuelto desde Linux 2.1.132).
ELOOP
Se encontraron demasiados enlaces simbólicos al traducir path.
ENAMETOOLONG
path era demasiado largo.
ENOENT
Un componente en path no existe o es un enlace simbólico roto, o path está vacío.
ENOMEM
No había suficiente memoria del kernel disponible.
ENOTDIR
Un componente utilizado como directorio en path no es, de hecho, un directorio.
EPERM
El sistema no permite eliminar directorios, o la eliminación de directorios requiere privilegios que el proceso llamante no tiene. (Esta es la respuesta de error prescrita por POSIX; como se mencionó anteriormente, Linux devuelve EISDIR para este caso).
EPERM (solo Linux)
El sistema de archivos no permite la eliminación de archivos.
EPERM o EACCES
El directorio que contiene path tiene el bit pegajoso (S_ISVTX) establecido y el UID efectivo del proceso no es ni el UID del archivo que se va a eliminar ni el del directorio que lo contiene, y el proceso no tiene privilegios (Linux: no tiene la capacidad CAP_FOWNER).
EPERM
El archivo que se va a eliminar está marcado como inmutable o solo para añadir. (Ver FS_IOC_SETFLAGS(2const).)
EROFS
path se refiere a un archivo en un sistema de archivos de solo lectura.

Los mismos errores que ocurren para unlink() y rmdir(2) también pueden ocurrir para unlinkat(). Los siguientes errores adicionales pueden ocurrir para unlinkat():

EBADF
path es relativo pero dirfd no es AT_FDCWD ni un descriptor de archivo válido.
EINVAL
Se especificó un valor de indicador inválido en flags.
EISDIR
path se refiere a un directorio, y AT_REMOVEDIR no se especificó en flags.
ENOTDIR
path es relativo y dirfd es un descriptor de archivo que se refiere a un archivo distinto de un directorio.

ESTÁNDARES

POSIX.1-2024.

HISTORIA

unlink()
SVr4, 4.3BSD, POSIX.1-2001.
unlinkat()
POSIX.1-2008. Linux 2.6.16, glibc 2.4.

glibc

En kernels más antiguos donde unlinkat() no está disponible, la función envoltorio de glibc recurre al uso de unlink() o rmdir(2). Cuando path es relativo, glibc construye un nombre de ruta basado en el enlace simbólico en /proc/self/fd que corresponde al argumento dirfd.

ERRORES DE PROGRAMACIÓN QUE PUEDEN SER FATALES

Las sutilezas en el protocolo subyacente a NFS pueden causar la desaparición inesperada de archivos que todavía se están utilizando.
