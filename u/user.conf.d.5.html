NOMBRE

systemd-system.conf, system.conf.d, systemd-user.conf, user.conf.d - Archivos de configuración del gestor de servicios del sistema y de la sesión

SINOPSIS

/etc/systemd/system.conf, /run/systemd/system.conf, /usr/lib/systemd/system.conf, /etc/systemd/system.conf.d/*.conf, /run/systemd/system.conf.d/*.conf, /usr/lib/systemd/system.conf.d/*.conf

~/.config/systemd/user.conf, /etc/systemd/user.conf, /run/systemd/user.conf, /usr/lib/systemd/user.conf, /etc/systemd/user.conf.d/*.conf, /run/systemd/user.conf.d/*.conf, /usr/lib/systemd/user.conf.d/*.conf

DESCRIPCIÓN

Cuando se ejecuta como una instancia del sistema, systemd interpreta el archivo de configuración system.conf y los archivos en los directorios system.conf.d; cuando se ejecuta como una instancia de usuario, interpreta el archivo de configuración user.conf (en orden de prioridad, en el directorio de inicio del usuario y bajo /etc/systemd/, /run/systemd/, y /usr/lib/systemd/) y los archivos en los directorios user.conf.d. Estos archivos de configuración contienen unas pocas configuraciones que controlan las operaciones básicas del gestor.

Consulte systemd.syntax(7) para una descripción general de la sintaxis.

DIRECTORIOS DE CONFIGURACIÓN Y PREFERENCIA

La configuración predeterminada se establece durante la compilación, por lo que la configuración solo es necesaria cuando es necesario desviarse de los valores predeterminados. El archivo de configuración principal se carga desde uno de los directorios listados en orden de prioridad, solo se utiliza el primer archivo encontrado: /etc/systemd/, /run/systemd/, /usr/local/lib/systemd/ [1], /usr/lib/systemd/. La versión del proveedor del archivo contiene entradas comentadas que muestran los valores predeterminados como guía para el administrador. También se pueden crear sobrescrituras locales creando archivos adicionales (drop-ins), como se describe a continuación. El archivo de configuración principal también se puede editar para este propósito (o una copia en /etc/ si se distribuye bajo /usr/), sin embargo, se recomienda el uso de archivos adicionales para la configuración local en lugar de modificar el archivo de configuración principal.

Además del archivo de configuración principal, se leen fragmentos de configuración adicionales (drop-ins) de /usr/lib/systemd/*.conf.d/, /usr/local/lib/systemd/*.conf.d/, y /etc/systemd/*.conf.d/. Estos archivos adicionales tienen mayor precedencia y anulan el archivo de configuración principal. Los archivos en los subdirectorios de configuración *.conf.d/ se ordenan por su nombre de archivo en orden lexicográfico, independientemente de en cuál de los subdirectorios residan. Cuando varios archivos especifican la misma opción, para las opciones que aceptan solo un valor único, la entrada en el archivo ordenado en último lugar tiene precedencia, y para las opciones que aceptan una lista de valores, las entradas se recopilan a medida que ocurren en los archivos ordenados.

Cuando los paquetes necesitan personalizar la configuración, pueden instalar archivos adicionales bajo /usr/. Los archivos en /etc/ están reservados para el administrador local, quien puede usar esta lógica para anular los archivos de configuración instalados por los paquetes del proveedor. Se deben usar archivos adicionales para anular los archivos adicionales de los paquetes, ya que el archivo de configuración principal tiene menor precedencia. Se recomienda prefijar todos los nombres de archivo en estos subdirectorios con un número de dos dígitos y un guion, para simplificar el orden. Esto también define un concepto de prioridades de archivos adicionales para permitir que los proveedores de sistemas operativos envíen archivos adicionales dentro de un rango específico inferior al rango utilizado por los usuarios. Esto debería reducir el riesgo de que los archivos adicionales de los paquetes anulen accidentalmente los archivos adicionales definidos por los usuarios. Se recomienda utilizar el rango 10-40 para los archivos adicionales en /usr/ y el rango 60-90 para los archivos adicionales en /etc/ y /run/, para asegurarse de que los archivos adicionales locales y transitorios tengan prioridad sobre los archivos adicionales enviados por el proveedor del sistema operativo.

Para deshabilitar un archivo de configuración proporcionado por el proveedor, la forma recomendada es colocar un enlace simbólico a /dev/null en el directorio de configuración en /etc/, con el mismo nombre de archivo que el archivo de configuración del proveedor.

OPCIONES

Todas las opciones se configuran en la sección [Manager]:

LogColor=, LogLevel=, LogLocation=, LogTarget=, LogTime=, DumpCore=yes, CrashChangeVT=no, CrashShell=no, CrashAction=freeze, ShowStatus=yes, DefaultStandardOutput=journal, DefaultStandardError=inherit

Configura varios parámetros de la operación básica del gestor. Estas opciones pueden ser anuladas por los procesos respectivos y los argumentos de la línea de comandos del kernel. Consulte systemd(1) para obtener detalles.

Añadido en la versión 198.

CtrlAltDelBurstAction=

Define qué acción se realizará si el usuario presiona Ctrl-Alt-Supr más de 7 veces en 2 segundos. Puede configurarse como "reboot-force", "poweroff-force", "reboot-immediate", "poweroff-immediate" o deshabilitarse con "none". El valor predeterminado es "reboot-force".

Añadido en la versión 232.

StatusUnitFormat=

Acepta name, description o combined como valor. Si es name, el gestor del sistema usará nombres de unidad en los mensajes de estado (por ejemplo, "systemd-journald.service"), en lugar de las descripciones más largas y detalladas establecidas con Description= (por ejemplo, "Servicio de registro de Journal"). Si es combined, el gestor del sistema usará tanto los nombres de unidad como las descripciones en los mensajes de estado (por ejemplo, "systemd-journald.service - Servicio de registro de Journal").

Consulte systemd.unit(5) para obtener detalles sobre los nombres de unidad y Description=.

Añadido en la versión 243.

DefaultTimerAccuracySec=

Establece la precisión predeterminada de las unidades de temporizador. Esto controla el valor predeterminado global para la configuración AccuracySec= de las unidades de temporizador, consulte systemd.timer(5) para obtener detalles. AccuracySec= establecido en unidades individuales anula el valor predeterminado global para la unidad específica. El valor predeterminado es 1 minuto. Tenga en cuenta que la precisión de las unidades de temporizador también se ve afectada por el tiempo de espera del temporizador configurado para PID 1, consulte TimerSlackNSec= anteriormente.

GESTIÓN DE RECURSOS

TimerSlackNSec=

Establece el tiempo de espera del temporizador en nanosegundos para PID 1, que se hereda por todos los procesos ejecutados, a menos que se anule individualmente, por ejemplo, con la configuración TimerSlackNSec= en las unidades de servicio (para más detalles, consulte systemd.exec(5)). El tiempo de espera del temporizador controla la precisión de los despertares activados por los temporizadores del sistema. Consulte prctl(2) para obtener más información. Tenga en cuenta que, a diferencia de la mayoría de las otras definiciones de períodos de tiempo, este parámetro acepta un valor entero en nanosegundos si no se especifica ninguna unidad. Las unidades de tiempo habituales también se entienden.

Añadido en la versión 198.

CPUAffinity=

Configura la afinidad de CPU para el gestor de servicios, así como la afinidad de CPU predeterminada para todos los procesos generados. Acepta una lista de índices o rangos de CPU separados por espacios en blanco o comas. Los rangos de CPU se especifican mediante los índices de CPU inferior y superior separados por un guion. Esta opción puede especificarse más de una vez, en cuyo caso las máscaras de afinidad de CPU especificadas se combinan. Si se asigna la cadena vacía, la máscara se restablece, todas las asignaciones anteriores a esta no tendrán ningún efecto. Los servicios individuales pueden anular la afinidad de CPU para sus procesos con la configuración CPUAffinity= en los archivos de unidad, consulte systemd.exec(5).

Añadido en la versión 198.

Configura la política de memoria NUMA para el gestor de servicios y la política de memoria NUMA predeterminada para todos los procesos generados. Los servicios individuales pueden anular la política predeterminada con la configuración NUMAPolicy= en los archivos de unidad, consulte systemd.exec(5).

Añadido en la versión 243.

Tenga en cuenta que las políticas NUMA default y local no requieren una máscara de nodo NUMA explícita y el valor de la opción puede estar vacío. De forma similar a NUMAPolicy=, el valor puede ser anulado por servicios individuales en los archivos de unidad, consulte systemd.exec(5).

DefaultLimitCPU=, DefaultLimitFSIZE=, DefaultLimitDATA=, DefaultLimitSTACK=, DefaultLimitCORE=, DefaultLimitRSS=, DefaultLimitNOFILE=, DefaultLimitAS=, DefaultLimitNPROC=, DefaultLimitMEMLOCK=, DefaultLimitLOCKS=, DefaultLimitSIGPENDING=, DefaultLimitMSGQUEUE=, DefaultLimitNICE=, DefaultLimitRTPRIO=, DefaultLimitRTTIME=

Estos ajustes controlan varios límites de recursos por defecto para los procesos ejecutados por las unidades. Consulte setrlimit(2) para más detalles. Estos ajustes pueden ser anulados en unidades individuales usando las directivas correspondientes LimitXXX= y aceptan la misma sintaxis de parámetros, consulte systemd.exec(5) para más detalles. •DefaultLimitNOFILE= por defecto es 1024:524288.
•DefaultLimitMEMLOCK= por defecto es 8M.
•DefaultLimitCORE= no tiene un valor por defecto, pero vale la pena mencionar que RLIMIT_CORE se establece en "infinito" por el PID 1, lo que se hereda de sus hijos.

Tenga en cuenta que el gestor de servicios internamente en el PID 1 aumenta RLIMIT_NOFILE y RLIMIT_MEMLOCK a valores más altos, sin embargo, el límite se revierte a los valores por defecto mencionados para todos los procesos hijos que se bifurcan.

HARDWARE WATCHDOG

RuntimeWatchdogSec=, RebootWatchdogSec=, KExecWatchdogSec=

Configure el watchdog de hardware en tiempo de ejecución y al reiniciar. Toma un valor de tiempo de espera en segundos (o en otras unidades de tiempo si va seguido de "ms", "min", "h", "d", "w"), o las cadenas especiales "off" o "default". Si se establece en "off" (alternativamente: "0") la lógica del watchdog se deshabilita: no se abre, configura ni se hace ping a ningún dispositivo watchdog. Si se establece en la cadena especial "default" el watchdog se abre y se hace ping a intervalos regulares, pero el tiempo de espera no se cambia del valor por defecto. Si se establece en cualquier otro valor de tiempo, el tiempo de espera del watchdog se configura al valor especificado (o un valor cercano a él, dependiendo de las capacidades del hardware).

Si RuntimeWatchdogSec= se establece en un valor distinto de cero, el hardware del watchdog (/dev/watchdog0 o la ruta especificada con WatchdogDevice= o la opción del kernel systemd.watchdog_device=) se programará para reiniciar automáticamente el sistema si no se contacta dentro del intervalo de tiempo de espera especificado. El gestor del sistema se asegurará de contactarlo al menos una vez cada medio intervalo de tiempo de espera especificado. Esta característica requiere la presencia de un dispositivo watchdog de hardware, como es común en sistemas integrados y de servidores. No todos los watchdogs de hardware permiten la configuración de todos los posibles valores de tiempo de espera de reinicio, en cuyo caso se elige el tiempo de espera disponible más cercano.

RebootWatchdogSec= puede usarse para configurar el watchdog de hardware cuando se solicita reiniciar el sistema. Funciona como una red de seguridad para asegurar que el reinicio se lleva a cabo incluso si un intento de reinicio limpio excede el tiempo de espera. Tenga en cuenta que el tiempo de espera de RebootWatchdogSec= se aplica solo a la segunda fase del reinicio, es decir, después de que todos los servicios regulares ya se hayan terminado, y después de que el proceso del sistema y gestor de servicios (PID 1) haya sido reemplazado por el binario systemd-shutdown, consulte el manual bootup(7) para más detalles. Durante la primera fase de la operación de apagado, el sistema y el gestor de servicios permanecen en ejecución y, por lo tanto, RuntimeWatchdogSec= sigue siendo respetado. Para definir un tiempo de espera en esta primera fase del apagado del sistema, configure JobTimeoutSec= y JobTimeoutAction= en la sección [Unit] de la unidad shutdown.target. Por defecto, RuntimeWatchdogSec= es 0 (apagado), y RebootWatchdogSec= es 10min.

KExecWatchdogSec= puede usarse para habilitar adicionalmente el watchdog cuando se ejecuta kexec en lugar de reiniciar. Tenga en cuenta que si el kernel no reinicia el watchdog en kexec (dependiendo del hardware y/o controlador específico), en este caso el watchdog podría no deshabilitarse después de que kexec tenga éxito y, por lo tanto, el sistema podría reiniciarse, a menos que RuntimeWatchdogSec= también esté habilitado al mismo tiempo. Por esta razón se recomienda habilitar KExecWatchdogSec= solo si RuntimeWatchdogSec= también está habilitado.

Estos ajustes no tienen ningún efecto si no hay un watchdog de hardware disponible.

Añadido en la versión 198.

RuntimeWatchdogPreSec=

Configure el valor del tiempo de pre-alerta del dispositivo watchdog de hardware. Toma un valor de tiempo de espera en segundos (o en otras unidades de tiempo similares a RuntimeWatchdogSec=). Un tiempo de pre-alerta del watchdog es una notificación generada por el watchdog antes de que pueda ocurrir un reinicio del watchdog en caso de que el watchdog no haya sido atendido. Esta notificación es manejada por el kernel y se puede configurar para tomar una acción (es decir, generar un pánico del kernel) usando RuntimeWatchdogPreGovernor=. No todo el hardware o los controladores de watchdog admiten la generación de una pre-alerta y, dependiendo del estado del sistema, el kernel puede ser incapaz de tomar la acción configurada antes de que el reinicio del watchdog ocurra. El watchdog se configurará para generar el evento de pre-alerta en la cantidad de tiempo especificada por RuntimeWatchdogPreSec= antes del tiempo de espera del watchdog en tiempo de ejecución (establecido por RuntimeWatchdogSec=). Por ejemplo, si tenemos RuntimeWatchdogSec=30 y RuntimeWatchdogPreSec=10, entonces el evento de pre-alerta ocurrirá si el watchdog no ha sido pingueado durante 20 segundos (10 segundos antes de que el watchdog se active). Por defecto, RuntimeWatchdogPreSec= es 0 (apagado). El valor establecido para RuntimeWatchdogPreSec= debe ser menor que el valor de tiempo de espera para RuntimeWatchdogSec=. Esta configuración no tiene efecto si no hay un watchdog de hardware disponible o si el watchdog de hardware no admite una pre-alerta y será ignorada por el kernel si el ajuste es mayor que el tiempo de espera real del watchdog.

Añadido en la versión 251.

RuntimeWatchdogPreGovernor=

Configure la acción tomada por el dispositivo watchdog de hardware cuando expira la pre-alerta. La acción por defecto para el evento de pre-alerta depende de la configuración del kernel, pero generalmente es registrar un mensaje del kernel. Para obtener una lista de acciones válidas disponibles para un dispositivo watchdog determinado, consulte el contenido del archivo /sys/class/watchdog/watchdogX/pretimeout_available_governors. Típicamente, los tipos de gobernador disponibles son noop y panic. La disponibilidad, los nombres y la funcionalidad pueden variar según el controlador de dispositivo específico en uso. Si el archivo sysfs pretimeout_available_governors está vacío, el gobernador podría estar compilado como un módulo del kernel y podría necesitar ser cargado manualmente (por ejemplo, pretimeout_noop.ko), o el dispositivo watchdog podría no admitir pre-alertas.

Añadido en la versión 251.

WatchdogDevice=

Configure el dispositivo watchdog de hardware que los temporizadores watchdog en tiempo de ejecución y de apagado abrirán y utilizarán. Por defecto es /dev/watchdog0. Esta configuración no tiene efecto si no hay un watchdog de hardware disponible.

Añadido en la versión 236.

SEGURIDAD

CapabilityBoundingSet=

Controla qué capacidades se incluyen en el conjunto de límites de capacidades para el PID 1 y sus hijos. Consulte capabilities(7) para más detalles. Toma una lista de nombres de capacidades separadas por espacios, tal como lo lee cap_from_name(3). Las capacidades listadas se incluirán en el conjunto de límites, todas las demás se eliminarán. Si la lista de capacidades va precedida de ~,

all but the listed capabilities will be included, the effect of the assignment inverted. Note that this option also affects the respective capabilities in the effective, permitted and inheritable capability sets. The capability bounding set may also be individually configured for units using the CapabilityBoundingSet= directive for units, but note that capabilities dropped for PID 1 cannot be regained in individual units, they are lost for good.

Added in version 198.

NoNewPrivileges=

Takes a boolean argument. If true, ensures that PID 1 and all its children can never gain new privileges through execve(2) (e.g. via setuid or setgid bits, or filesystem capabilities). Defaults to false. General purpose distributions commonly rely on executables with setuid or setgid bits and will thus not function properly with this option enabled. Individual units cannot disable this option. Also see No New Privileges Flag[2].

Added in version 239.

ProtectSystem=

Takes a boolean argument or the string "auto". If set to true this will remount /usr/ read-only. If set to "auto" (the default) and running in an initrd equivalent to true, otherwise false. This implements a restricted subset of the per-unit setting of the same name, see systemd.exec(5) for details: currently, the "full" or "strict" values are not supported.

Added in version 256.

SystemCallArchitectures=

Takes a space-separated list of architecture identifiers. Selects from which architectures system calls may be invoked on this system. This may be used as an effective way to disable invocation of non-native binaries system-wide, for example to prohibit execution of 32-bit x86 binaries on 64-bit x86-64 systems. This option operates system-wide, and acts similar to the SystemCallArchitectures= setting of unit files, see systemd.exec(5) for details. This setting defaults to the empty list, in which case no filtering of system calls based on architecture is applied. Known architecture identifiers are "x86", "x86-64", "x32", "arm" and the special identifier "native". The latter implicitly maps to the native architecture of the system (or more specifically, the architecture the system manager was compiled for). Set this setting to "native" to prohibit execution of any non-native binaries. When a binary executes a system call of an architecture that is not listed in this setting, it will be immediately terminated with the SIGSYS signal.

Added in version 209.

DefaultSmackProcessLabel=

Takes a SMACK64 security label as the argument. The process executed by a unit will be started under this label if SmackProcessLabel= is not set in the unit. See systemd.exec(5) for the details.

If the value is "/", only labels specified with SmackProcessLabel= are assigned and the compile-time default is ignored.

Added in version 252.

DefaultRestrictSUIDSGID=

Takes a boolean argument. This is used as a default for units which lack an explicit definition for RestrictSUIDSGID=. See systemd.exec(5) for the details.

Added in version 258.

INTERVALOS Y LÍMITES DE TASA

DefaultTimeoutStartSec=, DefaultTimeoutStopSec=, DefaultTimeoutAbortSec=, DefaultRestartSec=

Configura los intervalos de tiempo por defecto para iniciar, detener y abortar unidades, así como el tiempo de espera por defecto entre reinicios automáticos de unidades, según se configuran por unidad en TimeoutStartSec=, TimeoutStopSec=, TimeoutAbortSec= y RestartSec= (para servicios, ver systemd.service(5) para más detalles sobre la configuración por unidad). Para unidades que no son de servicio, DefaultTimeoutStartSec= establece el valor por defecto de TimeoutSec=.

DefaultTimeoutStartSec= y DefaultTimeoutStopSec= tienen por defecto 90 s en el gestor del sistema y 90 s en el gestor de usuario. DefaultTimeoutAbortSec= no se establece por defecto, de modo que todas las unidades recurran a TimeoutStopSec=. DefaultRestartSec= tiene por defecto 100 ms.

ReloadLimitIntervalSec=, ReloadLimitBurst=

Limitación de tasa para las solicitudes daemon-reload y (desde v256) daemon-reexec. La configuración se aplica a ambas operaciones, pero los límites de tasa se rastrean por separado. Por defecto no está establecido, y se puede solicitar cualquier número de operaciones en cualquier momento. ReloadLimitIntervalSec= toma un valor en segundos para configurar la ventana del límite de tasa, y ReloadLimitBurst= toma un entero positivo para configurar el número máximo de operaciones permitidas dentro de la ventana de tiempo configurada.

Añadido en la versión 253.

ENTORNO

DefaultEnvironment=

Configura variables de entorno que se pasan a todos los procesos ejecutados. Toma una lista separada por espacios de asignaciones de variables. Ver environ(7) para más detalles sobre las variables de entorno. Este bloque de entorno es interno y los cambios no se reflejan en el /proc/PID/environ del gestor.

Se admite la expansión simple de especificadores de "%", ver más abajo una lista de especificadores admitidos.

Ejemplo:

DefaultEnvironment="VAR1=word1 word2" VAR2=word3 "VAR3=word 5 6"

Establece tres variables "VAR1", "VAR2", "VAR3".

Añadido en la versión 205.

ManagerEnvironment=

Establece variables de entorno para el propio proceso gestor. Toma una lista separada por espacios de asignaciones de variables en el mismo formato que DefaultEnvironment=, ver arriba. Estas variables se fusionan en el bloque de entorno existente del proceso gestor. En particular, en el caso del gestor del sistema, este bloque incluye variables establecidas por el kernel basándose en la línea de comandos del kernel, y en el caso del gestor de usuario, las variables pasadas por el gestor del sistema. Después de que esas variables se hayan fusionado, persistirán hasta que se invaliden, incluso si el gestor se recarga o se reejecuta. En el caso del gestor de usuario, estas variables también son heredadas por los procesos generados por el gestor. Al igual que con DefaultEnvironment=, este bloque de entorno es interno y los cambios no se reflejan en el /proc/PID/environ del gestor.

Establecer variables de entorno para el proceso gestor puede ser útil para modificar su comportamiento. Ver Variables de Entorno Conocidas[3] para una descripción de algunas variables entendidas por systemd.

Se admite la expansión simple de especificadores de "%", ver más abajo una lista de especificadores admitidos.

Añadido en la versión 248.

NAME

user.conf.d - user login configuration directory

SYNOPSIS

/etc/user.conf.d/

/run/user.conf.d/

/usr/local/etc/user.conf.d/

DESCRIPTION

The user login configuration system provides a mechanism to configure various aspects of the user login process. This includes settings related to session management, resource limits, and security policies.

The configuration is split into several files, with precedence given to files in directories that are read later.

The system reads configuration files from the following directories, in order:

  • /usr/local/etc/user.conf.d/
  • /etc/user.conf.d/
  • /run/user.conf.d/

Files are processed in alphabetical order within each directory. If a configuration option is set in multiple files, the last one read takes precedence.

Configuration files should be named using the convention *.conf. Files starting with a dot (.) or ending in a tilde (~) are ignored.

CONFIGURATION DIRECTORIES AND PRECEDENCE

The system reads configuration files from the following directories, in order of precedence, with later directories overriding earlier ones:

1.
/usr/local/etc/user.conf.d/: For local administrator overrides.
2.
/etc/user.conf.d/: For system-wide configuration.
3.
/run/user.conf.d/: For runtime-generated configuration.

Files within each directory are read in alphabetical order. This allows for fine-grained control over configuration settings.

OPTIONS

The following configuration options are available:

User= Specifies the username for the user session.
Group= Specifies the primary group for the user session.
Session= Specifies the default session to start for the user.
Environment= Sets environment variables for the user session. This option can be specified multiple times.
PermitUserLogin= Controls whether user login is permitted. Accepts yes or no.
AllowCPUGroups= Specifies whether to allow CPU accounting groups for the user. Accepts yes or no.
DefaultCPUAccounting= Enables or disables CPU accounting by default for services started by the user. Accepts yes or no.
DefaultBlockIOAccounting= Enables or disables Block I/O accounting by default for services started by the user. Accepts yes or no.

RESOURCE MANAGEMENT

The following options control resource limits for the user session:

CPUShares= Sets the CPU shares for the user session.
MemoryLimit= Sets the memory limit for the user session.
IOWeight= Sets the I/O weight for the user session.

HARDWARE WATCHDOG

The following option relates to hardware watchdog support:

WatchdogSec= Sets the interval for the hardware watchdog timer.

SECURITY

The following options relate to security settings:

NoNewPrivileges= Controls whether the NO_NEW_PRIVILEGES security feature is enabled for the user session. Accepts yes or no.
CapabilityBoundingSet= Specifies the capabilities that are allowed for the user session.

TIMEOUTS AND RATE LIMITS

The following options control timeouts and rate limiting:

DefaultTimeoutStartSec= Sets the default timeout for starting services.
DefaultTimeoutStopSec= Sets the default timeout for stopping services.
DefaultTimeoutAbortSec= Sets the default timeout for aborting service operations.
DefaultRestartSec= Sets the default delay before restarting a failed service.

ENVIRONMENT

The Environment= directive can be used to set environment variables. These variables are available to processes started by the user.

Example:

Environment="MY_VAR=my_value"
Environment="ANOTHER_VAR=/path/to/something"

The following environment variables are also recognized and may influence behavior:

$TMPDIR, $TEMP, $TMP Used to determine the directory for temporary files (see %T specifier).

SPECIFIERS

Certain options can use specifiers that are expanded at runtime:

"%H" Hostname The hostname of the running system, as set in /etc/hostname.
"%M" Machine ID The machine ID of the running system, as read from /etc/machine-id.
"%S" System name The name of the operating system, as read from the NAME= field of /etc/os-release. If not set, resolves to an empty string. See os-release(5) for more information.
"%v" Operating system version The operating system version identifier of the running system, as read from the VERSION_ID= field of /etc/os-release. If not set, resolves to an empty string. See os-release(5) for more information.
"%W" Operating system variant ID The operating system variant identifier of the running system, as read from the VARIANT_ID= field of /etc/os-release. If not set, resolves to an empty string. See os-release(5) for more information.
"%T" Directory for temporary files This is either /tmp or the path "$TMPDIR", "$TEMP" or "$TMP" are set to. (Note that the directory may be specified without a trailing slash.)
"%V" Directory for larger and persistent temporary files This is either /var/tmp or the path "$TMPDIR", "$TEMP" or "$TMP" are set to. (Note that the directory may be specified without a trailing slash.)
"%h" User home directory This is the home directory of the user running the service manager instance.
"%u" Username This is the username of the user running the service manager instance.
"%U" User id This is the user id of the user running the service manager instance.
"%g" Primary group This is the primary group of the user running the service manager instance.
"%G" Primary group id This is the primary group id of the user running the service manager instance.
"%s" User shell This is the shell of the user running the service manager instance.
"%%" Single percent sign Use "%%" in place of "%" to specify a single percent sign.

systemd 258
