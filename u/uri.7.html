NOMBRE

uri, url, urn - identificador uniforme de recursos (URI), incluyendo una URL o URN

SINOPSIS

URI = [ URIabsoluta | URIrelativa ] [ "#" fragmento ]
URIabsoluta = esquema ":" ( parte_jerarquica | parte_opaca )
URIrelativa = ( ruta_red | ruta_absoluta | ruta_relativa ) [ "?" consulta ]
esquema = "http" | "ftp" | "gopher" | "mailto" | "news" | "telnet" | "file" | "ftp" | "man" | "info" | "whatis" | "ldap" | "wais" | ...
parte_jerarquica = ( ruta_red | ruta_absoluta ) [ "?" consulta ]
ruta_red = "//" autoridad [ ruta_absoluta ]
ruta_absoluta = "/" segmentos_ruta
ruta_relativa = segmento_relativo [ ruta_absoluta ]

DESCRIPCION

Un Identificador Uniforme de Recursos (URI) es una cadena corta de caracteres que identifica un recurso abstracto o físico (por ejemplo, una página web). Un Localizador Uniforme de Recursos (URL) es un URI que identifica un recurso a través de su mecanismo de acceso principal (por ejemplo, su "ubicación" en la red), en lugar de por su nombre u otro atributo de ese recurso. Un Nombre Uniforme de Recursos (URN) es un URI que debe permanecer globalmente único y persistente incluso cuando el recurso deja de existir o se vuelve inaccesible.

Los URI son la forma estándar de nombrar destinos de enlaces de hipertexto para herramientas como los navegadores web. La cadena "http://www.kernel.org" es una URL (y, por lo tanto, también es un URI). Muchas personas usan el término URL de manera laxa como sinónimo de URI (aunque técnicamente las URLs son un subconjunto de los URI).

Los URI pueden ser absolutos o relativos. Un identificador absoluto se refiere a un recurso independientemente del contexto, mientras que un identificador relativo se refiere a un recurso describiendo la diferencia con el contexto actual. Dentro de una referencia de ruta relativa, los segmentos de ruta completos "." y ".." tienen significados especiales: "el nivel jerárquico actual" y "el nivel por encima de este nivel jerárquico", respectivamente, al igual que en los sistemas tipo UNIX. Un segmento de ruta que contiene un carácter de dos puntos no se puede usar como primer segmento de una ruta de URI relativa (por ejemplo, "this:that"), porque se confundiría con un nombre de esquema; anteponga a dichos segmentos con ./ (por ejemplo, "./this:that"). Tenga en cuenta que los descendientes de MS-DOS (por ejemplo, Microsoft Windows) reemplazan los dos puntos del nombre del dispositivo con la barra vertical ("|") en los URI, por lo que "C:" se convierte en "C|".

Un identificador de fragmento, si se incluye, se refiere a una porción (fragmento) particular con nombre de un recurso; el texto después de un '#' identifica el fragmento. Un URI que comienza con '#' se refiere a ese fragmento en el recurso actual.

Uso

Existen muchos esquemas de URI diferentes, cada uno con reglas y significados adicionales específicos, pero están diseñados intencionalmente para ser lo más similares posible. Por ejemplo, muchos esquemas de URL permiten que la autoridad tenga el siguiente formato, llamado aquí servidor_ip (los corchetes muestran lo que es opcional):

servidor_ip = [usuario [ : contraseña ] @ ] host [ : puerto]

Este formato le permite insertar opcionalmente un nombre de usuario, un usuario más contraseña, y/o un número de puerto. El host es el nombre del ordenador anfitrión, ya sea su nombre determinado por DNS o una dirección IP (números separados por puntos). Por lo tanto, el URI http://fred:fredpassword@example.com:8080/ inicia sesión en un servidor web en el host example.com como fred (usando fredpassword) usando el puerto 8080. Evite incluir una contraseña en un URI si es posible debido a los muchos riesgos de seguridad de tener una contraseña escrita. Si la URL proporciona un nombre de usuario pero no una contraseña, y el servidor remoto solicita una contraseña, el programa que interpreta la URL debe solicitar una al usuario.

Aquí hay algunos de los esquemas más comunes en uso en sistemas tipo UNIX que son entendidos por muchas herramientas. Tenga en cuenta que muchas herramientas que usan URI también tienen esquemas internos o especializados; consulte la documentación de esas herramientas para obtener información sobre esos esquemas.

http - Servidor Web (HTTP)

http://servidor_ip/ruta
http://servidor_ip/ruta?consulta

Esta es una URL que accede a un servidor web (HTTP). El puerto predeterminado es 80. Si la ruta se refiere a un directorio, el servidor web elegirá qué devolver; normalmente, si existe un archivo llamado "index.html" o "index.htm", se devuelve su contenido; de lo contrario, se genera y devuelve una lista de los archivos en el directorio actual (con los enlaces apropiados). Un ejemplo es http://lwn.net.

Se puede proporcionar una consulta en el formato arcaico "isindex", que consiste en una palabra o frase y no incluye un signo de igual (=). Una consulta también puede estar en el formato más largo "GET", que tiene una o más entradas de consulta del tipo clave=valor separadas por el ampersand (&). Tenga en cuenta que clave puede repetirse más de una vez, aunque depende del servidor web y sus programas de aplicación determinar si eso tiene algún significado. Existe una interacción desafortunada con HTML/XML/SGML y el formato de consulta GET; cuando tales URI con más de una clave se incrustan en documentos SGML/XML (incluyendo HTML), el ampersand (&) debe ser reescrito como &amp;. Tenga en cuenta que no todas las consultas usan este formato; los formularios más grandes pueden ser demasiado largos para almacenarse como un URI, por lo que utilizan un mecanismo de interacción diferente (llamado POST) que no incluye los datos en el URI. Consulte la especificación Common Gateway Interface en http://www.w3.org/CGI para obtener más información.

ftp - Protocolo de Transferencia de Archivos (FTP)

ftp://servidor_ip/ruta

Esta es una URL que accede a un archivo a través del protocolo de transferencia de archivos (FTP). El puerto predeterminado (para control) es 21. Si no se incluye ningún nombre de usuario, se proporciona el nombre de usuario "anonymous", y en ese caso muchos clientes proporcionan como contraseña la dirección de correo electrónico de Internet del solicitante. Un ejemplo es <ftp://ftp.is.co.za/rfc/rfc1808.txt>.

gopher - Servidor Gopher

gopher://servidor_ip/tipo_gopher selector
gopher://servidor_ip/tipo_gopher selector%09busqueda
gopher://servidor_ip/tipo_gopher selector%09busqueda%09cadena_gopher+

El puerto gopher predeterminado es 70. tipo_gopher es un campo de un solo carácter para denotar el tipo Gopher del recurso al que se refiere la URL. Toda la ruta también puede estar vacía, en cuyo caso el delimitador "/" también es opcional, y el tipo_gopher por defecto es "1".

selector es la cadena de selector de Gopher. En el protocolo Gopher, las cadenas de selector de Gopher son una secuencia de octetos que pueden contener cualquier octeto excepto 09 hexadecimal (HT US-ASCII o tab), 0A hexadecimal (LF US-ASCII) y 0D (CR US-ASCII).

mailto - Dirección de correo electrónico

mailto:direccion-correo

Esta es una dirección de correo electrónico, generalmente de la forma nombre@nombre_host. Consulte mailaddr(7).

news - Grupo de noticias Usenet

news:nombre_grupo

Un grupo de noticias Usenet. El nombre del grupo puede ser un grupo de noticias particular, por ejemplo, "comp.os.linux.announce", o "all" para todos los grupos de noticias.

telnet - Servicio Telnet

telnet://servidor_ip/[login]

Este es un servicio Telnet. El puerto Telnet predeterminado es 23. El campo login opcional indica un nombre de usuario para iniciar sesión. Por ejemplo, <telnet://pts.cc.monash.edu.au/> se conecta a ese host, y <telnet://guest@axp.dyndns.org/> intenta iniciar sesión como "guest".

file - Archivo local

file://host/ruta

Este es un archivo en el sistema de archivos local. Si el host es "localhost" o está vacío, se accede al archivo localmente. Si el host no está vacío, pero es diferente de "localhost", se accede al archivo en un sistema remoto a través de NFS o un protocolo similar. El sistema operativo subyacente puede tener problemas con los dos puntos en los nombres de archivo, así que la RFC 1738 especifica que los dos puntos deben ser reemplazados por un carácter de barra vertical (|) en los archivos de disco (por ejemplo, C: como C|). Por lo tanto, si se accede a un archivo local C:\file.txt, se buscaría como file://localhost/C|/file.txt.

man - Página del manual

man:nombre_seccion(seccion)

Esto se refiere a una página del manual. Por ejemplo, la URI "man:printf(3)" se refiere a la página del manual de la función `printf` en la sección 3. El esquema "whatis" se puede usar para un nombre de sección de página del manual que se correlaciona con una entrada en la base de datos whatis.

info - Documentación de GNU Info

info://host/nodename

Esto se refiere a un nodo dentro del sistema de documentación de GNU Info. Por ejemplo, "info://localhost/ejemplo" se refiere al nodo "ejemplo" en el sistema Info local.

ldap - Protocolo Ligero de Acceso a Directorios

ldap://[dominio[:puerto]]/[dn[?atributos[?scope]]]

Esto se refiere a una entrada en un directorio LDAP. Por ejemplo, "ldap://ldap.example.com/cn=foo,dc=example,dc=com" se refiere a la entrada "cn=foo,dc=example,dc=com" en el servidor LDAP "ldap.example.com".

urn - Nombre Uniforme de Recursos

urn:NID:NSS

Un URN identifica un recurso por su nombre en lugar de su ubicación. El NID es el Identificador de Namespace (por ejemplo, "isbn" o "uuid"). El NSS es el Nombre de String del Namespace. Un ejemplo es "urn:isbn:0451450523".

ESQUEMAS DE URI

Este documento describe los esquemas de URI (Localizadores Uniformes de Recursos) soportados por el navegador web de KDE. Se basa en los estándares del IETF, principalmente en RFC 2396.

http - Hypertext Transfer Protocol

http://host[:port]/path
https://host[:port]/path

Estos son los esquemas más comunes para acceder a documentos en la World Wide Web. El puerto predeterminado para HTTP es 80, y para HTTPS es 443. El path es opcional y se refiere a la ubicación del recurso en el servidor. Un ejemplo es <http://www.kde.org/>.

ftp - File Transfer Protocol

ftp://host[:port]/path

Utilizado para transferir archivos. Admite autenticación anónima o con nombre de usuario y contraseña. Un ejemplo es <ftp://ftp.kde.org/pub/kde/>.

mailto - Electronic mail address

mailto:address

Representa una dirección de correo electrónico. Cualquier carácter especial en la dirección debe ser codificado según RFC 2396. El carácter '%' debe ser reemplazado por '%25'. Un ejemplo es <mailto:dwheeler@dwheeler.com>.

news - Newsgroups o mensajes de News

news:nombre-de-newsgroupe
news:id-del-mensaje

Un nombre-de-newsgroupe es un nombre jerárquico separado por puntos, como "comp.infosystems.www.misc". Si <nombre-de-newsgroupe> es "*" (como en <news:*>), se refiere a "todos los grupos de noticias disponibles". Un ejemplo es <news:comp.lang.ada>.

Un id-del-mensaje corresponde al Message-ID de la IETF RFC 1036, sin los corchetes "<" y ">"; toma la forma único@nombre_dominio_completo. Un identificador de mensaje puede distinguirse de un nombre de grupo de noticias por la presencia del carácter "@".

telnet - Inicio de sesión Telnet

telnet://servidor-ip/

El esquema de URL Telnet se utiliza para designar servicios de texto interactivos a los que se puede acceder mediante el protocolo Telnet. El carácter final "/" puede omitirse. El puerto predeterminado es 23. Un ejemplo es <telnet://melvyl.ucop.edu/>.

file - Archivo normal

file://servidor-ip/segmentos-de-ruta
file:segmentos-de-ruta

Esto representa un archivo o directorio accesible localmente. Como caso especial, servidor-ip puede ser la cadena "localhost" o la cadena vacía; esto se interpreta como "la máquina desde la que se está interpretando la URL". Si la ruta es a un directorio, el visor debe mostrar el contenido del directorio con enlaces a cada elemento; no todos los visores lo hacen actualmente. KDE soporta archivos generados a través de la URL <file:/cgi-bin>. Si el archivo dado no se encuentra, los desarrolladores del navegador pueden intentar expandir el nombre del archivo mediante globbing de nombres de archivo (ver glob(7) y glob(3)).

El segundo formato (por ejemplo, <file:/etc/passwd>) es un formato correcto para referirse a un archivo local. Sin embargo, los estándares más antiguos no permitían este formato, y algunos programas no lo reconocen como una URI. Una sintaxis más portable es usar una cadena vacía como nombre del servidor, por ejemplo, <file:///etc/passwd>; esta forma hace lo mismo y es fácilmente reconocida como una URI por los coincidores de patrones y programas antiguos. Tenga en cuenta que si realmente quiere decir "empezar desde la ubicación actual", no especifique el esquema en absoluto; use una dirección relativa como <../test.txt>, que tiene el efecto secundario de ser independiente del esquema. Un ejemplo de este esquema es <file:///etc/passwd>.

man - Documentación de páginas man

man:nombre-del-comando
man:nombre-del-comando(sección)

Esto se refiere a las páginas de referencia del manual (man) en línea locales. El nombre del comando puede ir seguido opcionalmente de un paréntesis y un número de sección; consulte man(7) para obtener más información sobre el significado de los números de sección. Este esquema de URI es único para los sistemas tipo UNIX (como Linux) y no está registrado actualmente por el IETF. Un ejemplo es <man:ls(1)>.

info - Documentación de páginas info

info:nombre-archivo-virtual
info:nombre-archivo-virtual#nombre-nodo
info:(nombre-archivo-virtual)
info:(nombre-archivo-virtual)nombre-nodo

Este esquema se refiere a las páginas de referencia info en línea (generadas a partir de archivos texinfo), un formato de documentación utilizado por programas como las herramientas GNU. Este esquema de URI es único para los sistemas tipo UNIX (como Linux) y no está registrado actualmente por el IETF. En el momento de escribir esto, GNOME y KDE difieren en su sintaxis de URI y no aceptan la sintaxis del otro. Los dos primeros formatos son el formato GNOME; en los nombres de nodo, todos los espacios se escriben como guiones bajos. Los dos últimos formatos son el formato KDE; los espacios en los nombres de nodo deben escribirse como espacios, aunque esto está prohibido por los estándares de URI. Se espera que en el futuro la mayoría de las herramientas entiendan todos estos formatos y siempre acepten guiones bajos para los espacios en los nombres de nodo. Tanto en GNOME como en KDE, si se utiliza la forma sin el nombre de nodo, se asume que el nombre de nodo es "Top". Ejemplos del formato GNOME son <info:gcc> y <info:gcc#G++_and_GCC>. Ejemplos del formato KDE son <info:(gcc)> y <info:(gcc)G++ and GCC>.

whatis - Búsqueda de documentación

whatis:cadena

Este esquema busca en la base de datos de descripciones cortas (de una línea) de comandos y devuelve una lista de descripciones que contienen esa cadena. Solo se devuelven coincidencias de palabras completas. Ver whatis(1). Este esquema de URI es único para los sistemas tipo UNIX (como Linux) y no está registrado actualmente por el IETF.

ghelp - Documentación de ayuda de GNOME

ghelp:nombre-de-la-aplicacion

Esto carga la ayuda de GNOME para la aplicación dada. Tenga en cuenta que actualmente no existe mucha documentación en este formato.

ldap - Lightweight Directory Access Protocol

ldap://hostpuerto
ldap://hostpuerto/
ldap://hostpuerto/dn
ldap://hostpuerto/dn?atributos
ldap://hostpuerto/dn?atributos?ambito
ldap://hostpuerto/dn?atributos?ambito?filtro
ldap://hostpuerto/dn?atributos?ambito?filtro?extensiones

Este esquema soporta consultas al Lightweight Directory Access Protocol (LDAP), un protocolo para consultar un conjunto de servidores para obtener información organizada jerárquicamente (como personas y recursos informáticos). Ver RFC 2255 para más información sobre el esquema de URL LDAP. Los componentes de esta URL son:

hostpuerto
el servidor LDAP a consultar, escrito como un nombre de host seguido opcionalmente por dos puntos y el número de puerto. El puerto LDAP predeterminado es el puerto TCP 389. Si está vacío, el cliente determina qué servidor LDAP usar.
dn
el Distinguished Name (DN) de LDAP, que identifica el objeto base de la búsqueda LDAP (ver RFC 2253 sección 3).
atributos
una lista separada por comas de atributos a devolver; ver RFC 2251 sección 4.1.5. Si se omite, se deben devolver todos los atributos.
ambito
especifica el ámbito de la búsqueda, que puede ser uno de "base" (para una búsqueda de objeto base), "one" (para una búsqueda de un solo nivel), o "sub" (para una búsqueda de subárbol). Si se omite el ámbito, se asume "base".
filtro
especifica el filtro de búsqueda (subconjunto de entradas a devolver). Si se omite, se deben devolver todas las entradas. Ver RFC 2254 sección 4.
extensiones
una lista separada por comas de pares tipo=valor, donde la parte =valor puede omitirse para opciones que no la requieren. Una extensión prefijada con '!' es crítica (debe ser soportada para ser válida), de lo contrario es no crítica (opcional).

Las consultas LDAP son más fáciles de explicar con un ejemplo. Aquí hay una consulta que solicita a ldap.itd.umich.edu información sobre la Universidad de Michigan en EE. UU.:

ldap://ldap.itd.umich.edu/o=University%20of%20Michigan,c=US

Para obtener solo su atributo de dirección postal, solicite:

ldap://ldap.itd.umich.edu/o=University%20of%20Michigan,c=US?postalAddress

Para consultar a host.com en el puerto 6666 información sobre la persona con nombre común (cn) "Babs Jensen" en la Universidad de Michigan, solicite:

ldap://host.com:6666/o=University%20of%20Michigan,c=US??sub?(cn=Babs%20Jensen)

wais - Wide Area Information Servers

wais://hostpuerto/base-de-datos
wais://hostpuerto/base-de-datos?busqueda
wais://hostpuerto/base-de-datos/tipowais/rutawais

Este esquema designa una base de datos WAIS, una búsqueda o un documento (ver IETF RFC 1625 para más información sobre WAIS). Hostpuerto es el nombre del host, seguido opcionalmente por dos puntos y un número de puerto (el número de puerto predeterminado es 210).

La primera forma designa una base de datos WAIS para buscar. La segunda forma designa una búsqueda particular de la base de datos WAIS base-de-datos. La tercera forma designa un documento particular dentro de una base de datos WAIS para ser recuperado. tipowais es la designación WAIS del tipo del objeto, y rutawais es el id-del-documento WAIS.

otros esquemas

Existen muchos otros esquemas de URI. La mayoría de las herramientas que aceptan URIs soportan un conjunto de URIs internas (por ejemplo, Mozilla tiene el esquema about: para información interna, y el navegador de ayuda de GNOME tiene el esquema toc: para varios puntos de partida). Existen muchos esquemas que han sido definidos pero que no son tan utilizados actualmente (por ejemplo, prospero). El esquema nntp: está obsoleto en favor del esquema news:. Se espera que las URN sean soportadas por el esquema urn:, con un espacio de nombres jerárquico (por ejemplo, urn:ietf:... identificaría documentos del IETF); en este momento, las URN no están ampliamente implementadas. No todas las herramientas soportan todos los esquemas.

Codificación de caracteres

Las URIs utilizan un número limitado de caracteres para que puedan ser escritas y utilizadas en una variedad de situaciones.

Los siguientes caracteres están reservados, es decir, pueden aparecer en una URI pero su uso se limita a su propósito reservado (los datos en conflicto deben ser escapados antes de formar la URI):


; / ? : @ & = + $ ,

Los caracteres no reservados pueden incluirse en una URI. Los caracteres no reservados incluyen letras latinas mayúsculas y minúsculas, dígitos decimales y el siguiente conjunto limitado de signos de puntuación y símbolos:


- _ . ! ~ * ' ( )

Todos los demás caracteres deben ser escapados. Un octeto escapado se codifica como un triplete de caracteres, que consiste en el carácter de porcentaje "%" seguido de los dos dígitos hexadecimales que representan el código del octeto (puede usar letras mayúsculas o minúsculas para los dígitos hexadecimales). Por ejemplo, un espacio en blanco debe ser escapado como "%20", un carácter de tabulación como "%09", y el "&" como "%26". Debido a que el carácter de porcentaje "%" siempre

que está reservado para ser el indicador de escape, debe escaparse como `"%25"`. Es práctica común escapar los espacios como el símbolo más (+) en el texto de la consulta; esta práctica no está definida uniformemente en los RFCs relevantes (que recomiendan `%20` en su lugar) pero cualquier herramienta que acepte URIs con texto de consulta debe estar preparada para ellos. Una URI se muestra siempre en su forma "escapada".

Los caracteres no reservados pueden escaparse sin cambiar la semántica de la URI, pero esto no debe hacerse a menos que la URI se esté utilizando en un contexto que no permita que aparezca el carácter no escapado. Por ejemplo, `"%7e"` se usa a veces en lugar de `"~"` en una ruta de URL HTTP, pero ambos son equivalentes para una URL HTTP.

Para las URIs que deben manejar caracteres fuera del conjunto de caracteres US ASCII, la especificación HTML 4.01 (sección B.2) y el RFC IETF 3986 (último párrafo de la sección 2.5) recomiendan el siguiente enfoque:

(1)
traducir las secuencias de caracteres a UTF-8 (RFC IETF 3629) —véase utf-8(7)— y luego
(2)
usar el mecanismo de escape de URI, es decir, usar la codificación %HH para los octetos inseguros.

Escritura de una URI

Cuando se escriben, las URIs deben colocarse entre comillas dobles (p. ej., `"http://www.kernel.org"`), encerrarse entre corchetes angulares (p. ej., http://lwn.net), o colocarse en una línea por sí solas. Una advertencia para quienes usan comillas dobles: **nunca** muevan puntuación extralimitada (como el punto que termina una frase o la coma en una lista) dentro de una URI, ya que esto cambiará el valor de la URI. En su lugar, use corchetes angulares, o cambie a un sistema de comillas que nunca incluya caracteres extralimitados dentro de comillas. Este último sistema, llamado el sistema de comillas 'nuevo' o 'lógico' por "Hart's Rules" y el "Oxford Dictionary for Writers and Editors", es una práctica preferida en Gran Bretaña y en varios idiomas europeos. Documentos más antiguos sugerían insertar el prefijo `"URL:"` justo antes de la URI, pero esta forma nunca ha tenido éxito.

La sintaxis de las URIs se diseñó para ser inequívoca. Sin embargo, a medida que las URIs se han vuelto comunes, los medios tradicionales (televisión, radio, periódicos, vallas publicitarias, etc.) han utilizado cada vez más referencias de URI abreviadas que consisten solo en la autoridad y la parte de la ruta del recurso identificado (p. ej., ``). Dichas referencias están destinadas principalmente a la interpretación humana en lugar de la máquina, con la suposición de que los heurísticos basados en el contexto son suficientes para completar la URI (p. ej., los nombres de host que comienzan con `"www"` es probable que tengan un prefijo de URI de `"http://"` y los nombres de host que comienzan con `"ftp"` un prefijo de `"ftp://"`). Muchas implementaciones de cliente resuelven heurísticamente estas referencias. Dichos heurísticos pueden cambiar con el tiempo, particularmente cuando se introducen nuevos esquemas. Dado que una URI abreviada tiene la misma sintaxis que una ruta de URL relativa, las referencias de URI abreviadas no se pueden usar donde se permiten URIs relativas, y solo se pueden usar cuando no hay una base definida (como en cuadros de diálogo). No use URIs abreviadas como enlaces de hipertexto dentro de un documento; use el formato estándar como se describe aquí.

NOTAS

Cualquier herramienta que acepte URIs (p. ej., un navegador web) en un sistema Linux debería poder manejar (directa o indirectamente) todos los esquemas descritos aquí, incluidos los esquemas man: e info:. Manejarlos invocando algún otro programa está bien y, de hecho, es alentado.

Técnicamente, el fragmento no es parte de la URI.

Para obtener información sobre cómo incrustar URIs (incluidas las URLs) en un formato de datos, consulte la documentación de ese formato. HTML usa el formato `uri"> texto </A>`. Los archivos Texinfo usan el formato `@uref{uri}`. Man y mdoc tienen la macro UR recién agregada, o simplemente incluyen la URI en el texto (los visores deberían poder detectar `://` como parte de una URI).

Los entornos de escritorio GNOME y KDE actualmente varían en las URIs que aceptan, en particular en sus respectivos navegadores de ayuda. Para listar las páginas man, GNOME usa `` mientras que KDE usa ``, y para listar las páginas info, GNOME usa `` mientras que KDE usa `` (el autor de esta página man prefiere el enfoque de KDE aquí, aunque un formato más regular sería aún mejor). En general, KDE usa `` como prefijo a un conjunto de archivos generados. KDE prefiere la documentación en HTML, accesible a través de ``. GNOME prefiere el esquema ghelp para almacenar y encontrar documentación. Ninguno de los navegadores maneja referencias file: a directorios en el momento de escribir esto, lo que dificulta referirse a un directorio completo con una URI navegable. Como se señaló anteriormente, estos entornos difieren en cómo manejan el esquema info:, probablemente la variación más importante. Se espera que GNOME y KDE converjan a formatos de URI comunes, y una versión futura de esta página man describirá el resultado convergido. Se alientan los esfuerzos para ayudar a esta convergencia.

Seguridad

Una URI no presenta en sí misma una amenaza de seguridad. No hay garantía general de que una URL, que en un momento dado localizó un recurso dado, continúe haciéndolo. Tampoco hay garantía de que una URL no localice un recurso diferente en un momento posterior; tal garantía solo se puede obtener de la(s) persona(s) que controlan ese espacio de nombres y el recurso en cuestión.

A veces es posible construir una URL de tal manera que un intento de realizar una operación aparentemente inofensiva, como la recuperación de una entidad asociada con el recurso, cause en realidad una operación remota posiblemente dañina. La URL insegura se construye típicamente especificando un número de puerto distinto del reservado para el protocolo de red en cuestión. El cliente contacta sin saberlo a un sitio que en realidad está ejecutando un protocolo diferente. El contenido de la URL contiene instrucciones que, cuando se interpretan de acuerdo con este otro protocolo, causan una operación inesperada. Un ejemplo ha sido el uso de una URL gopher para causar el envío de un mensaje no intencionado o de suplantación a través de un servidor SMTP.

Se debe tener precaución al usar cualquier URL que especifique un número de puerto distinto del predeterminado para el protocolo; especialmente, cuando es un número dentro del espacio reservado.

Se debe tener cuidado cuando una URI contiene delimitadores escapados para un protocolo dado (por ejemplo, caracteres CR y LF para protocolos telnet) y estos no se escapan antes de la transmisión. Esto podría violar el protocolo, pero evita la posibilidad de que dichos caracteres se utilicen para simular una operación o parámetro adicional en ese protocolo, lo que podría llevar a una operación remota inesperada y posiblemente dañina.

Es claramente imprudente usar una URI que contenga una contraseña que se pretende que sea secreta. En particular, se recomienda encarecidamente no usar una contraseña dentro del componente de "userinfo" de una URI, excepto en aquellos casos raros en los que el parámetro "password" pretende ser público.

ERRORES

La documentación puede colocarse en una variedad de ubicaciones, por lo que actualmente no existe un buen esquema de URI para la documentación general en línea en formatos arbitrarios. Las referencias del tipo `` no funcionan, porque diferentes distribuciones y requisitos de instalación locales pueden colocar los archivos en diferentes directorios (puede estar en /usr/doc, o /usr/local/doc, o /usr/share, o en algún otro lugar). Además, el directorio ZZZ generalmente cambia cuando cambia una versión (aunque la expansión de nombres de archivo podría superar esto parcialmente). Finalmente, usar el esquema file: no soporta fácilmente a las personas que cargan dinámicamente documentación de Internet (en lugar de cargar los archivos en un sistema de archivos local). Se puede agregar un esquema de URI futuro (p. ej., `"userdoc:"`) para permitir que los programas incluyan referencias cruzadas a documentación más detallada sin tener que conocer la ubicación exacta de esa documentación. Alternativamente, una versión futura de la especificación del sistema de archivos puede especificar las ubicaciones de los archivos lo suficiente como para que el esquema file: pueda localizar la documentación.

Muchos programas y formatos de archivo no incluyen una forma de incorporar o implementar enlaces utilizando URIs.

Muchos programas no pueden manejar todos estos diferentes formatos de URI; debería existir un mecanismo estándar para cargar una URI arbitraria que detecte automáticamente el entorno del usuario (p. ej., texto o gráficos, entorno de escritorio, preferencias del usuario local y herramientas en ejecución actualmente) e invoque la herramienta correcta para cualquier URI.

    NAME

    uri - Uniform Resource Identifier

    SYNOPSIS

    #include <uriparser/Uri.h>

    DESCRIPTION

    La biblioteca uriparser proporciona una interfaz para analizar y manipular URIs (Identificadores Uniformes de Recursos) y URNs (Nombres Uniformes de Recursos) según las especificaciones RFC 3986 y RFC 2141.

    Componentes de una URI

    Una URI se compone de los siguientes componentes:

    • Scheme (Esquema): El esquema de la URI (ej. "http", "ftp", "mailto").
    • UserInfo (Información del usuario): Información de autenticación (ej. usuario:contraseña).
    • Host: El nombre del host o la dirección IP.
    • Port (Puerto): El número de puerto.
    • Path (Ruta): La ruta del recurso.
    • Query (Consulta): Parámetros de consulta.
    • Fragment (Fragmento): Referencia a una parte específica de un recurso.

    Funcionalidad

    uriparser permite:

    • Analizar cadenas de URI en sus componentes.
    • Construir URIs a partir de sus componentes.
    • Modificar componentes de URIs existentes.
    • Convertir URIs de vuelta a cadenas.
    • Validar la sintaxis de las URIs.

    STANDARDS

    RFC 3986: Uniform Resource Identifier (URI): Generic Syntax

    RFC 2141: URN Syntax

    NOTES

    Esta es una descripción general de la biblioteca uriparser. Para detalles completos sobre el uso de las funciones, consulte la documentación de la biblioteca.
