DESCRIPCIÓN

Un Identificador Uniforme de Recursos (URI) es una cadena corta de caracteres que identifica un recurso abstracto o físico (por ejemplo, una página web). Un Localizador Uniforme de Recursos (URL) es un URI que identifica un recurso a través de su mecanismo de acceso principal (por ejemplo, su "ubicación" de red), en lugar de por su nombre o algún otro atributo de ese recurso. Un Nombre Uniforme de Recursos (URN) es un URI que debe seguir siendo globalmente único y persistente incluso cuando el recurso deja de existir o se vuelve inaccesible.

Los URI son la forma estándar de nombrar destinos de enlaces de hipertexto para herramientas como los navegadores web. La cadena "http://www.kernel.org" es un URL (y por lo tanto, también es un URI). Mucha gente usa el término URL de forma laxa como sinónimo de URI (aunque técnicamente los URL son un subconjunto de los URI).

Los URI pueden ser absolutos o relativos. Un identificador absoluto se refiere a un recurso independientemente del contexto, mientras que un identificador relativo se refiere a un recurso describiendo la diferencia con el contexto actual. Dentro de una referencia de ruta relativa, los segmentos de ruta completos "." y ".." tienen significados especiales: "el nivel de jerarquía actual" y "el nivel por encima de este nivel de jerarquía", respectivamente, al igual que lo hacen en sistemas tipo UNIX. Un segmento de ruta que contiene un carácter de dos puntos no se puede utilizar como primer segmento de una ruta de URI relativa (por ejemplo, "this:that"), porque sería confundido con un nombre de esquema; anteponga ./ a dichos segmentos (por ejemplo, "./this:that"). Tenga en cuenta que los descendientes de MS-DOS (por ejemplo, Microsoft Windows) reemplazan los dos puntos del nombre del dispositivo con la barra vertical ("|") en los URI, por lo que "C:" se convierte en "C|".

Un identificador de fragmento, si se incluye, se refiere a una parte (fragmento) específica de un recurso; el texto después de un '#' identifica el fragmento. Un URI que comienza con '#' se refiere a ese fragmento en el recurso actual.

USO

Existen muchos esquemas de URI diferentes, cada uno con reglas y significados adicionales específicos, pero están hechos intencionalmente para ser lo más similares posible. Por ejemplo, muchos esquemas de URL permiten que la autoridad tenga el siguiente formato, aquí llamado ip_server (los corchetes muestran lo que es opcional):

ip_server = [user [ : password ] @ ] host [ : port]

Este formato le permite insertar opcionalmente un nombre de usuario, un usuario más una contraseña y/o un número de puerto. El host es el nombre del equipo anfitrión, ya sea su nombre tal como lo determina DNS o una dirección IP (números separados por puntos). Por lo tanto, el URI http://fred:fredpassword@example.com:8080/ inicia sesión en un servidor web en el host example.com como fred (usando fredpassword) usando el puerto 8080. Evite incluir una contraseña en un URI si es posible debido a los muchos riesgos de seguridad de tener una contraseña escrita. Si el URL suministra un nombre de usuario pero no una contraseña, y el servidor remoto solicita una contraseña, el programa que interpreta el URL debe solicitar una al usuario.

Aquí se encuentran algunos de los esquemas más comunes en uso en sistemas tipo UNIX que son entendidos por muchas herramientas. Tenga en cuenta que muchas herramientas que utilizan URI también tienen esquemas internos o esquemas especializados; consulte la documentación de esas herramientas para obtener información sobre esos esquemas.

http - Servidor Web (HTTP)

http://ip_server/path
http://ip_server/path?query

Este es un URL que accede a un servidor web (HTTP). El puerto por defecto es 80. Si la ruta se refiere a un directorio, el servidor web elegirá qué devolver; normalmente, si hay un archivo llamado "index.html" o "index.htm", se devuelve su contenido; de lo contrario, se genera y devuelve una lista de los archivos en el directorio actual (con los enlaces apropiados). Un ejemplo es http://lwn.net.

Se puede proporcionar una consulta en el arcaico formato "isindex", que consiste en una palabra o frase y no incluye un signo de igual (=). Una consulta también puede estar en el formato más largo "GET", que tiene una o más entradas de consulta del tipo key=value separadas por el carácter ampersand (&). Tenga en cuenta que key se puede repetir más de una vez, aunque depende del servidor web y sus programas de aplicación determinar si eso tiene algún significado. Existe una interacción desafortunada con HTML/XML/SGML y el formato de consulta GET; cuando dichos URI con más de una clave se incrustan en documentos SGML/XML (incluido HTML), el ampersand (&) debe reescribirse como &amp;. Tenga en cuenta que no todas las consultas usan este formato; formularios más grandes pueden ser demasiado largos para almacenarse como un URI, por lo que utilizan un mecanismo de interacción diferente (llamado POST) que no incluye los datos en el URI. Consulte la especificación Common Gateway Interface en http://www.w3.org/CGI para más información.

ftp - Protocolo de Transferencia de Archivos (FTP)

ftp://ip_server/path

Este es un URL que accede a un archivo a través del protocolo de transferencia de archivos (FTP). El puerto por defecto (para control) es 21. Si no se incluye ningún nombre de usuario, se proporciona el nombre de usuario "anonymous", y en ese caso muchos clientes proporcionan como contraseña la dirección de correo electrónico de Internet del solicitante. Un ejemplo es <ftp://ftp.is.co.za/rfc/rfc1808.txt>.

gopher - Servidor Gopher

gopher://ip_server/gophertype selector
gopher://ip_server/gophertype selector%09search
gopher://ip_server/gophertype selector%09search%09gopher+_string

El puerto gopher por defecto es 70. gophertype es un campo de un solo carácter para denotar el tipo Gopher del recurso al que se refiere el URL. Toda la ruta también puede estar vacía, en cuyo caso la barra delimitadora "/" también es opcional, y el gophertype por defecto es "1".

selector es la cadena de selector de Gopher. En el protocolo Gopher, las cadenas de selector de Gopher son una secuencia de octetos que pueden contener cualquier octeto excepto 09 hexadecimal (tabulador US-ASCII) , 0A hexadecimal (carácter US-ASCII LF) y 0D (carácter US-ASCII CR).

mailto - Dirección de correo electrónico

mailto:email-address

Esta es una dirección de correo electrónico, generalmente de la forma name@hostname. Consulte mailaddr(7) para obtener más información sobre el formato correcto de una dirección de correo electrónico. Tenga en cuenta que cualquier carácter % debe reescribirse como %25. Un ejemplo es <mailto:dwheeler@dwheeler.com>.

news - Grupo de noticias o mensaje de noticias

news:newsgroup-name
news:message-id

Un news

ESQUEMAS DE URI

Un URI (Localizador Uniforme de Recursos) se utiliza para designar una variedad de recursos. Los URI se componen de varios componentes, y su estructura varía según el esquema.

news - Grupos de noticias Usenet

news:nombre-grupo

El esquema news: se utiliza para hacer referencia a grupos de noticias Usenet. Un nombre-grupo es un nombre jerárquico delimitado por puntos, como "comp.infosystems.www.misc". Si el nombre-grupo es "*" (como en news:*), se utiliza para referirse a "todos los grupos de noticias disponibles". Un ejemplo es news:comp.lang.ada.

Un message-id corresponde al Message-ID de IETF RFC 1036, sin los corchetes de apertura y cierre "<" y ">"; toma la forma único@nombre-dominio-completo. Un identificador de mensaje se puede distinguir de un nombre de grupo de noticias por la presencia del carácter "@".

telnet - Inicio de sesión Telnet

telnet://servidor-ip/

El esquema de URL Telnet se utiliza para designar servicios de texto interactivos a los que se puede acceder mediante el protocolo Telnet. El carácter final "/" puede omitirse. El puerto predeterminado es 23. Un ejemplo es telnet://melvyl.ucop.edu/.

file - Archivo normal

file://servidor-ip/segmentos-ruta
file:segmentos-ruta

Esto representa un archivo o directorio accesible localmente. Como caso especial, servidor-ip puede ser la cadena "localhost" o la cadena vacía; esto se interpreta como "la máquina desde la que se está interpretando la URL". Si la ruta es a un directorio, el visor debería mostrar el contenido del directorio con enlaces a cada contenido; no todos los visores lo hacen actualmente. KDE admite archivos generados a través de la URL file:/cgi-bin. Si el archivo dado no se encuentra, los desarrolladores del navegador pueden intentar expandir el nombre del archivo mediante globbing de nombres de archivo (consulte glob(7) y glob(3)).

El segundo formato (por ejemplo, file:/etc/passwd) es un formato correcto para referirse a un archivo local. Sin embargo, los estándares anteriores no permitían este formato, y algunos programas no lo reconocen como una URI. Una sintaxis más portable es usar una cadena vacía como nombre del servidor, por ejemplo, file:///etc/passwd; esta forma hace lo mismo y es fácilmente reconocida como una URI por los comparadores de patrones y los programas antiguos. Tenga en cuenta que si realmente quiere decir "empezar desde la ubicación actual", no especifique el esquema en absoluto; use una dirección relativa como ../test.txt, que tiene el efecto secundario de ser independiente del esquema. Un ejemplo de este esquema es file:///etc/passwd.

man - Documentación de páginas man

man:nombre-comando
man:nombre-comando(sección)

Esto se refiere a las páginas de referencia del manual en línea (man) locales. El nombre del comando puede ir seguido opcionalmente de un paréntesis y un número de sección; consulte man(7) para obtener más información sobre el significado de los números de sección. Este esquema de URI es exclusivo de los sistemas tipo UNIX (como Linux) y actualmente no está registrado por la IETF. Un ejemplo es man:ls(1).

info - Documentación de páginas info

info:nombre-archivo-virtual
info:nombre-archivo-virtual#nombre-nodo
info:(nombre-archivo-virtual)
info:(nombre-archivo-virtual)nombre-nodo

Este esquema se refiere a las páginas de referencia de información en línea (generadas a partir de archivos texinfo), un formato de documentación utilizado por programas como las herramientas de GNU. Este esquema de URI es exclusivo de los sistemas tipo UNIX (como Linux) y actualmente no está registrado por la IETF. En el momento de redactar este documento, GNOME y KDE difieren en su sintaxis de URI y no aceptan la sintaxis del otro. Los dos primeros formatos son el formato GNOME; en los nombres de nodo, todos los espacios se escriben como guiones bajos. Los dos últimos formatos son el formato KDE; los espacios en los nombres de nodo deben escribirse como espacios, aunque esto está prohibido por los estándares de URI. Se espera que en el futuro la mayoría de las herramientas comprendan todos estos formatos y siempre acepten guiones bajos para los espacios en los nombres de nodo. Tanto en GNOME como en KDE, si se usa la forma sin el nombre del nodo, se asume que el nombre del nodo es "Top". Ejemplos del formato GNOME son info:gcc y info:gcc#G++_and_GCC. Ejemplos del formato KDE son info:(gcc) y info:(gcc)G++ and GCC.

whatis - Búsqueda de documentación

whatis:cadena

Este esquema busca en la base de datos de descripciones cortas (de una línea) de comandos y devuelve una lista de descripciones que contienen esa cadena. Solo se devuelven coincidencias de palabras completas. Consulte whatis(1). Este esquema de URI es exclusivo de los sistemas tipo UNIX (como Linux) y actualmente no está registrado por la IETF.

ghelp - Documentación de ayuda de GNOME

ghelp:nombre-aplicación

Esto carga la ayuda de GNOME para la aplicación dada. Tenga en cuenta que actualmente no hay mucha documentación en este formato.

ldap - Protocolo ligero de acceso a directorios

ldap://hostpuerto
ldap://hostpuerto/
ldap://hostpuerto/dn
ldap://hostpuerto/dn?atributos
ldap://hostpuerto/dn?atributos?ámbito
ldap://hostpuerto/dn?atributos?ámbito?filtro
ldap://hostpuerto/dn?atributos?ámbito?filtro?extensiones

Este esquema admite consultas al Protocolo Ligero de Acceso a Directorios (LDAP), un protocolo para consultar un conjunto de servidores para obtener información organizada jerárquicamente (como personas y recursos informáticos). Consulte RFC 2255 para obtener más información sobre el esquema de URL LDAP. Los componentes de esta URL son:

hostpuerto
el servidor LDAP a consultar, escrito como un nombre de host seguido opcionalmente por dos puntos y el número de puerto. El puerto LDAP predeterminado es el puerto TCP 389. Si está vacío, el cliente determina qué servidor LDAP usar.
dn
el Distinguished Name (DN) de LDAP, que identifica el objeto base de la búsqueda LDAP (consulte RFC 2253 sección 3).
atributos
una lista separada por comas de atributos a devolver; consulte RFC 2251 sección 4.1.5. Si se omite, se deben devolver todos los atributos.
ámbito
especifica el ámbito de la búsqueda, que puede ser uno de "base" (para una búsqueda de objeto base), "one" (para una búsqueda de un solo nivel), o "sub" (para una búsqueda de subárbol). Si se omite el ámbito, se asume "base".
filtro
especifica el filtro de búsqueda (subconjunto de entradas a devolver). Si se omite, se deben devolver todas las entradas. Consulte RFC 2254 sección 4.
extensiones
una lista separada por comas de pares tipo=valor, donde la parte =valor puede omitirse para opciones que no lo requieran. Una extensión prefijada con un '!' es crítica (debe ser compatible para ser válida), de lo contrario, es no crítica (opcional).

Las consultas LDAP son más fáciles de explicar con un ejemplo. Aquí hay una consulta que le pide a ldap.itd.umich.edu información sobre la Universidad de Michigan en EE. UU.:

ldap://ldap.itd.umich.edu/o=University%20of%20Michigan,c=US

Para obtener solo su atributo de dirección postal, solicite:

ldap://ldap.itd.umich.edu/o=University%20of%20Michigan,c=US?postalAddress

Para consultar a host.com en el puerto 6666 sobre la persona con nombre común (cn) "Babs Jensen" en la Universidad de Michigan, solicite:

ldap://host.com:6666/o=University%20of%20Michigan,c=US??sub?(cn=Babs%20Jensen)

wais - Wide Area Information Servers

wais://hostpuerto/base-datos
wais://hostpuerto/base-datos?búsqueda
wais://hostpuerto/base-datos/tipo-wais/ruta-wais

Este esquema designa una base de datos WAIS, una búsqueda o un documento (consulte IETF RFC 1625 para obtener más información sobre WAIS). Hostport es el nombre del host, seguido opcionalmente por dos puntos y el número de puerto (el número de puerto predeterminado es 210).

La primera forma designa una base de datos WAIS para buscar. La segunda forma designa una búsqueda particular de la base de datos WAIS base-datos. La tercera forma designa un documento particular dentro de una base de datos WAIS para ser recuperado. tipo-wais es la designación WAIS del tipo del objeto, y ruta-wais es el ID del documento WAIS.

otros esquemas

Hay muchos otros esquemas de URI. La mayoría de las herramientas que aceptan URIs admiten un conjunto de URIs internas (por ejemplo, Mozilla tiene el esquema about: para información interna, y el navegador de ayuda de GNOME tiene el esquema toc: para varios puntos de inicio). Hay muchos esquemas que se han definido pero que no se utilizan tan ampliamente en la actualidad (por ejemplo, prospero). El esquema nntp: está obsoleto en favor del esquema news:. Se espera que las URN sean compatibles con el esquema urn:, con un espacio de nombres jerárquico (por ejemplo, urn:ietf:... identificaría documentos de la IETF); en este momento, las URN no están ampliamente implementadas. No todas las herramientas admiten todos los esquemas.

Codificación de caracteres

Las URIs utilizan un número limitado de caracteres para que puedan escribirse y utilizarse en diversas situaciones.

Los siguientes caracteres están reservados, es decir, pueden aparecer en una URI pero su uso se limita a su propósito reservado (los datos conflictivos deben ser escapados antes de formar la URI):


; / ? : @ & = + $ ,

Los caracteres no reservados pueden incluirse en una URI. Los caracteres no reservados incluyen letras latinas mayúsculas y minúsculas, dígitos decimales y el siguiente conjunto limitado de signos de puntuación y símbolos:


- _ . ! ~ * ' ( )

Todos los demás caracteres deben ser escapados. Un octeto escapado se codifica como un triplete de caracteres, que consta del carácter de porcentaje "%" seguido de los dos dígitos hexadecimales que representan el código del octeto (puede usar letras mayúsculas o minúsculas para los dígitos hexadecimales). Por ejemplo, un espacio en blanco debe ser escapado como "%20", un carácter de tabulación como "%09", y el "&" como "%26". Dado que el carácter de porcentaje "%" siempre tiene el propósito reservado de ser el indicador de escape, debe ser escapado como "%25". Es una práctica común escapar los espacios como el símbolo más (+) en el texto de la consulta; esta práctica no está definida uniformemente en las RFC relevantes (que recomiendan %20 en su lugar), pero cualquier herramienta que acepte URIs con texto de consulta debe estar preparada para ellas. A

NAME

uri — Uniform Resource Identifiers

SYNOPSIS

#include <uri.h>

DESCRIPTION

A Uniform Resource Identifier (URI) is a compact representation of some resource on the World Wide Web. The resource can be a simple HTML document, a picture, a data file, a service (e.g. an email address), or any other thing that can be identified. URIs include URLs (Uniform Resource Locators) and URNs (Uniform Resource Names).

URIs are defined in IETF RFC 3986.

A URI consists of a number of components. The first component is the scheme, which identifies the general type of resource to which the URI refers. The rest of the URI is composed of a scheme-specific part, which usually consists of a hierarchical component, and an optional fragment identifier. The scheme and the scheme-specific part are separated by a colon (":").

The hierarchical part typically consists of a path, and an optional authority. The authority typically consists of a userinfo (username and password), a host, and an optional port number. The path consists of a sequence of segments separated by slashes ("/"). The hierarchical part and the path are separated by a slash ("/"). The optional fragment identifier is separated from the rest of the URI by a hash mark ("#").

Scheme names are case-insensitive. All other components are case-sensitive.

Within the scheme-specific part, characters that are not allowed are escaped by using the percent sign (`%`) followed by two hexadecimal digits. For example, a space character is represented as `%20`. Reserved characters (such as `/` and `?`) have special meaning within the URI syntax, and must be escaped if they are to be used as data within a component. Unreserved characters (alphanumeric characters and `-`, `_`, `.`, `~`) have no special meaning and may be escaped or unescaped without changing the semantics of the URI.

URI is always shown in its "escaped" form.

Unreserved characters can be escaped without changing the semantics of the URI, but this should not be done unless the URI is being used in a context that does not allow the unescaped character to appear. For example, "%7e" is sometimes used instead of "~" in an HTTP URL path, but the two are equivalent for an HTTP URL.

For URIs which must handle characters outside the US ASCII character set, the HTML 4.01 specification (section B.2) and IETF RFC 3986 (last paragraph of section 2.5) recommend the following approach:

(1)
translate the character sequences into UTF-8 (IETF RFC 3629) —see utf-8(7)— and then
(2)
use the URI escaping mechanism, that is, use the %HH encoding for unsafe octets.

Writing a URI

When written, URIs should be placed inside double quotes (e.g., "http://www.kernel.org"), enclosed in angle brackets (e.g., http://lwn.net), or placed on a line by themselves. A warning for those who use double-quotes: never move extraneous punctuation (such as the period ending a sentence or the comma in a list) inside a URI, since this will change the value of the URI. Instead, use angle brackets instead, or switch to a quoting system that never includes extraneous characters inside quotation marks. This latter system, called the 'new' or 'logical' quoting system by "Hart's Rules" and the "Oxford Dictionary for Writers and Editors", is preferred practice in Great Britain and in various European languages. Older documents suggested inserting the prefix "URL:" just before the URI, but this form has never caught on.

The URI syntax was designed to be unambiguous. However, as URIs have become commonplace, traditional media (television, radio, newspapers, billboards, etc.) have increasingly used abbreviated URI references consisting of only the authority and path portions of the identified resource (e.g., <www.w3.org/Addressing>). Such references are primarily intended for human interpretation rather than machine, with the assumption that context-based heuristics are sufficient to complete the URI (e.g., hostnames beginning with "www" are likely to have a URI prefix of "http://" and hostnames beginning with "ftp" likely to have a prefix of "ftp://"). Many client implementations heuristically resolve these references. Such heuristics may change over time, particularly when new schemes are introduced. Since an abbreviated URI has the same syntax as a relative URL path, abbreviated URI references cannot be used where relative URIs are permitted, and can be used only when there is no defined base (such as in dialog boxes). Don't use abbreviated URIs as hypertext links inside a document; use the standard format as described here.

NOTES

Any tool accepting URIs (e.g., a web browser) on a Linux system should be able to handle (directly or indirectly) all of the schemes described here, including the man: and info: schemes. Handling them by invoking some other program is fine and in fact encouraged.

Technically, the fragment isn't part of the URI.

For information on how to embed URIs (including URLs) in a data format, see documentation on that format. HTML uses the format <A HREF="uri"> text </A>. Texinfo files use the format @uref{uri}. Man and mdoc have the recently added UR macro, or just include the URI in the text (viewers should be able to detect :// as part of a URI).

The GNOME and KDE desktop environments currently vary in the URIs they accept, in particular in their respective help browsers. To list man pages, GNOME uses <toc:man> while KDE uses <man:(index)>, and to list info pages, GNOME uses <toc:info> while KDE uses <info:(dir)> (the author of this man page prefers the KDE approach here, though a more regular format would be even better). In general, KDE uses <file:/cgi-bin/> as a prefix to a set of generated files. KDE prefers documentation in HTML, accessed via the <file:/cgi-bin/helpindex>. GNOME prefers the ghelp scheme to store and find documentation. Neither browser handles file: references to directories at the time of this writing, making it difficult to refer to an entire directory with a browsable URI. As noted above, these environments differ in how they handle the info: scheme, probably the most important variation. It is expected that GNOME and KDE will converge to common URI formats, and a future version of this man page will describe the converged result. Efforts to aid this convergence are encouraged.

Security

A URI does not in itself pose a security threat. There is no general guarantee that a URL, which at one time located a given resource, will continue to do so. Nor is there any guarantee that a URL will not locate a different resource at some later point in time; such a guarantee can be obtained only from the person(s) controlling that namespace and the resource in question.

It is sometimes possible to construct a URL such that an attempt to perform a seemingly harmless operation, such as the retrieval of an entity associated with the resource, will in fact cause a possibly damaging remote operation to occur. The unsafe URL is typically constructed by specifying a port number other than that reserved for the network protocol in question. The client unwittingly contacts a site that is in fact running a different protocol. The content of the URL contains instructions that, when interpreted according to this other protocol, cause an unexpected operation. An example has been the use of a gopher URL to cause an unintended or impersonating message to be sent via a SMTP server.

Caution should be used when using any URL that specifies a port number other than the default for the protocol; especially, when it is a number within the reserved space.

Care should be taken when a URI contains escaped delimiters for a given protocol (for example, CR and LF characters for telnet protocols) that these are not unescaped before transmission. This might violate the protocol, but avoids the potential for such characters to be used to simulate an extra operation or parameter in that protocol, which might lead to an unexpected and possibly harmful remote operation to be performed.

It is clearly unwise to use a URI that contains a password which is intended to be secret. In particular, the use of a password within the "userinfo" component of a URI is strongly recommended against except in those rare cases where the "password" parameter is intended to be public.

BUGS

Documentation may be placed in a variety of locations, so there currently isn't a good URI scheme for general online documentation in arbitrary formats. References of the form <file:///usr/doc/ZZZ> don't work, because different distributions and local installation requirements may place the files in different directories (it may be in /usr/doc, or /usr/local/doc, or /usr/share, or somewhere else). Also, the directory ZZZ usually changes when a version changes (though filename globbing could partially overcome this). Finally, using the file: scheme doesn't easily support people who dynamically load documentation from the Internet (instead of loading the files onto a local filesystem). A future URI scheme may be added (e.g., "userdoc:") to permit programs to include cross-references to more detailed documentation without having to know the exact location of that documentation. Alternatively, a future version of the filesystem specification may specify file locations sufficiently so that the file: scheme will be able to locate documentation.

Many programs and file formats don't include a way to incorporate or implement links using URIs.

Many programs can't handle all of these different URI formats; there should be a standard mechanism to load an arbitrary URI that automatically detects the users' environment (e.g., text or graphics, desktop environment, local user preferences, and currently executing tools) and invokes the right tool for any URI.
