UPSMON.CONF(5) Manual de NUT UPSMON.CONF(5)

NOMBRE

upsmon.conf - Configuración del cliente upsmon de Network UPS Tools

DESCRIPCIÓN

El trabajo principal de este archivo es definir los sistemas que upsmon(8) monitorizará, y decirle cómo apagar el sistema cuando sea necesario. Contendrá contraseñas, así que mantenlo seguro. Idealmente, solo el proceso upsmon debería poder leerlo.

Una configuración mínima debería incluir al menos una instrucción MONITOR, MINSUPPLIES (puede ser 0 si este sistema solo está monitorizando otros servidores NUT), y un POWERDOWNFLAG si esta máquina es un sistema "primario" conectado a la UPS y que maneja su comando de apagado tardío en caso de emergencia.

Además, otros valores de configuración opcionales se pueden establecer en este archivo.

NOTAS IMPORTANTES

•El contenido de este archivo debe ser ASCII puro (los códigos de caracteres que no estén en el rango se ignorarán con un mensaje de advertencia).
•Equilibra los permisos del usuario en tiempo de ejecución para acceder al archivo (y quizás al directorio en el que se encuentra) de modo que solo upsmon pueda leerlo; el acceso de escritura no es necesario. Es común usar chown root:nut y chmod 640 para establecer permisos de archivo aceptables.
•Los paquetes (y las recetas de compilación) suelen preparar un conjunto de cuentas de usuario y grupo para NUT. Las compilaciones personalizadas con configuración mínima podrían incluso usar nobody:nogroup o similar, lo que es inherentemente inseguro.
•En sistemas con preocupaciones de seguridad adicionales, los drivers de NUT, el servidor de datos y cualquier otro cliente de monitorización, registro, etc., deben ejecutarse como cuentas de usuario separadas. Esto requeriría que algunos demonios utilicen configuraciones personalizadas de usuario, grupo, RUN_AS_USER y/o RUN_AS_GROUP para anular el único valor incorporado.
•Ten en cuenta la seguridad de las copias de seguridad de este archivo, por ejemplo, los archivos de archivo en los que podría terminar.

DIRECTIVAS DE CONFIGURACIÓN

DEADTIME segundos

upsmon permite que una UPS esté ausente durante esta cantidad de segundos antes de declararla "muerta". El valor predeterminado es 15 segundos.

upsmon requiere que una UPS proporcione información de estado cada pocos segundos (ver POLLFREQ y POLLFREQALERT) para mantener las cosas actualizadas. Si la obtención de estado falla, la UPS se marca como obsoleta. Si permanece obsoleta durante más de DEADTIME segundos, la UPS se marca como muerta.

Se asume que una UPS muerta que se sabía que estaba alimentada por batería ha pasado a una condición de batería baja. Esto puede forzar un apagado si proporciona una cantidad crítica de energía a su sistema. Esto parece disruptivo, pero la alternativa es seguir adelante hacia la nada y fallar cuando te quedas sin energía.

Nota: DEADTIME debe ser un múltiplo de POLLFREQ y POLLFREQALERT. De lo contrario, tendrá UPS "muertas" simplemente porque upsmon no las está consultando lo suficientemente rápido. Regla general: toma el mayor de los dos valores de POLLFREQ y multiplícalo por 3.

FINALDELAY segundos

Al ejecutarse en modo primario, upsmon espera esta cantidad de tiempo después de enviar NOTIFY_SHUTDOWN para advertir a los usuarios. Después de que expire el temporizador, ejecuta tu SHUTDOWNCMD. Por defecto, esto se establece en 5 segundos.

Si necesita permitir que sus usuarios hagan algo entre esos eventos, aumente este número. Recuerde, en este punto la batería de su UPS está casi agotada, así que no haga que esto sea demasiado grande.

Alternativamente, puede establecer esto muy bajo para no esperar cuando sea el momento de apagar. Algunas UPS no dan mucha advertencia de batería baja y requerirán un valor de 0 aquí para un apagado seguro.


Nota
Si FINALDELAY en el secundario es mayor que HOSTSYNC en el primario, el primario dejará de esperar a que ese upsmon secundario se desconecte.

HOSTSYNC segundos

upsmon esperará hasta esta cantidad de segundos en modo primario para que los secundarios se desconecten durante una situación de apagado. Por defecto, esto es 15 segundos.

Cuando una UPS se vuelve crítica (encendida por batería + batería baja, o "FSD": apagado forzado), se supone que los sistemas secundarios se desconectan y apagan de inmediato. El temporizador HOSTSYNC evita que el upsmon primario se quede ahí para siempre si uno de los secundarios se atasca.

Este valor también se utiliza para evitar que los sistemas secundarios se queden atascados si el primario no responde a tiempo. Después de que una UPS se vuelve crítica, el secundario esperará hasta HOSTSYNC segundos a que el primario establezca la bandera FSD. Si expira ese temporizador, el upsmon secundario asumirá que el primario (o la ruta de comunicación hacia él) está roto y se apagará de todos modos.

Esto evita que los secundarios se apaguen durante un cambio de estado de corta duración a "OB LB" y de vuelta que los secundarios ven pero el primario omite.

MINSUPPLIES num

Establezca el número de fuentes de alimentación que deben estar recibiendo energía para mantener este sistema en funcionamiento. Las computadoras normales tienen solo una fuente de alimentación, por lo que el valor predeterminado de 1 es aceptable.

Los sistemas de tipo servidor grandes/caros suelen tener más y pueden funcionar con algunos faltantes. El HP NetServer LH4 puede funcionar con 2 de 4, por ejemplo, por lo que lo establecería en 2. La idea es mantener la máquina funcionando el mayor tiempo posible, ¿verdad?

Obviamente, ¡debe poner las fuentes de alimentación redundantes en circuitos de UPS diferentes para que esto tenga sentido! Consulte big-servers.txt en el subdirectorio de documentación para obtener más información e ideas sobre cómo usar esta función.

Consulte también la sección sobre "valores de potencia" en upsmon(8).

MONITOR sistema valor_potencia usuario contraseña tipo

Cada UPS que necesite monitorizar debe tener una línea MONITOR. No todas estas necesitan suministrar energía al sistema que ejecuta upsmon. Puede monitorizar otros sistemas si desea poder enviar notificaciones sobre cambios de estado en ellos.

Debe tener al menos una directiva MONITOR en upsmon.conf.

• sistema es un identificador de UPS. Tiene esta forma:

<nombre_ups>[@<nombre_host>[:<puerto>]]

El nombre_host predeterminado es "localhost". Algunos ejemplos:

• "su700@mybox" significa una UPS llamada "su700" en un sistema llamado "mybox". Esta es la forma normal.
• "fenton@bigbox:5678" es una UPS llamada "fenton" en un sistema llamado "bigbox" que ejecuta upsd(8) en el puerto "5678".
• valor_potencia es un entero que representa el número de fuentes de alimentación que la UPS alimenta en este sistema. La mayoría de las computadoras normales tienen una fuente de alimentación, y la UPS la alimenta, por lo que este valor será 1. Necesita un sistema muy grande o especial para tener algo más alto aquí.

Puede establecer el valor_potencia en 0 si desea monitorizar una UPS que en realidad no suministra energía a este sistema. Esto es útil cuando desea que upsmon envíe notificaciones sobre cambios de estado en una UPS sin apagarla cuando se vuelve crítica.

• El usuario y la contraseña en esta línea deben coincidir con una entrada en el archivo upsd.users(5) del sistema servidor upsd.

Si su nombre de usuario es "observer" y su contraseña es "abcd", la línea MONITOR podría verse así (probablemente en un sistema secundario remoto):

MONITOR myups@bigserver 1 observer abcd secondary

Mientras tanto, upsd.users en bigserver se vería así:

[observer]
        password = abcd
        upsmon secondary
[upswired]
        password = blah
        upsmon primary

Y la copia de upsmon en ese bigserver se ejecutaría con la configuración primaria:

MONITOR myups@bigserver 1 upswired blah primary
• El tipo se refiere a la relación con upsd(8). Puede ser "primary" o "secondary". Consulte upsmon(8) para obtener más información sobre el significado de estos modos. El modo que elija aquí también va en el archivo upsd.users, como se ve en el ejemplo anterior.

NOCOMMWARNTIME segundos

upsmon activará un NOTIFY_NOCOMM después de esta cantidad de segundos si no puede alcanzar ninguna de las entradas de UPS en este archivo de configuración. Le seguirá avisando hasta que la situación se resuelva. Por defecto, es
s es 300 segundos.

POLLFAIL_LOG_THROTTLE_MAX conteo

upsmon normalmente informa los fallos de sondeo de cada dispositivo que existen durante cada ciclo POLLFREQ (por ejemplo, "Datos obsoletos" o "Controlador no conectado") al registro del sistema según lo configurado. Si se espera que sus dispositivos estén ausentes durante un período prolongado, puede usar este acelerador para reducir el estrés en el tráfico de syslog y el almacenamiento, publicando estos mensajes solo una vez cada varios ciclos de bucle, y cuando la condición de error haya cambiado o se haya resuelto.

Un valor negativo significa comportamiento estándar (registrar en cada bucle, efectivamente igual que cuando max=1), y un valor cero significa no repetir nunca el mensaje (registrar solo al inicio y al final/cambio del estado de fallo).

Tenga en cuenta que este acelerador solo se aplica a un estado de error activo más reciente por dispositivo monitoreado.

NOTIFYCMD comando

upsmon llama a esto para enviar mensajes cuando ocurren cosas.

Este comando se llama con el texto completo del mensaje como un argumento. La cadena de entorno NOTIFYTYPE contendrá la cadena de tipo de lo que sea que haya causado que este evento ocurra.

Si necesita usar upssched(8), entonces debe hacerlo su NOTIFYCMD listándolo aquí.

Tenga en cuenta que esto solo se llama para eventos NOTIFY que tienen EXEC establecido con NOTIFYFLAG. Consulte NOTIFYFLAG a continuación para obtener más detalles.

Hacer que esto sea algún tipo de script de shell podría no ser una mala idea. Para más información e ideas, consulte docs/scheduling.txt

Recuerde que este comando también debe ser un elemento en el archivo de configuración, por lo que si su comando tiene espacios, envuélvalo en comillas.

NOTIFYCMD "/ruta/a/script --foo --bar"

Este script se ejecuta en segundo plano; es decir, upsmon se bifurca antes de llamar para iniciarlo. Esto significa que su NOTIFYCMD puede tener múltiples instancias ejecutándose simultáneamente si ocurren muchas cosas a la vez. Tenga esto en cuenta al diseñar notificadores complicados.

NOTIFYMSG tipo mensaje

upsmon viene con un conjunto de mensajes predeterminados para varios eventos. Puede cambiarlos si lo desea. 
NOTIFYMSG ONLINE "La SAU %s está recuperando energía de la red"
NOTIFYMSG ONBATT "Alguien desconectó la SAU %s"

Tenga en cuenta que %s se reemplaza con el identificador de la SAU en cuestión.

El mensaje debe ser un elemento en el archivo de configuración, por lo que si contiene espacios, debe envolverlo en comillas.

NOTIFYMSG NOCOMM "Alguien se robó la SAU %s"

Valores posibles para tipo:

ONLINE

La SAU vuelve a estar en línea

ONBATT

La SAU está funcionando con batería

LOWBATT

La SAU está funcionando con batería y tiene batería baja (es crítica)

FSD

La SAU está siendo apagada por la principal (FSD = "Apagado Forzado")

COMMOK

Se estableció comunicación con la SAU

COMMBAD

Se perdió la comunicación con la SAU

SHUTDOWN

El sistema está siendo apagado

REPLBATT

La batería de la SAU está defectuosa y necesita ser reemplazada

NOCOMM

Una SAU no está disponible (no se puede contactar para monitoreo)

NOPARENT

El proceso padre de upsmon murió - apagado imposible

CAL

Calibración de la SAU en progreso

NOTCAL

Calibración de la SAU finalizada

OFF

SAU administrativamente APAGADA o inactiva

NOTOFF

La SAU ya no está administrativamente APAGADA o inactiva

BYPASS

La SAU está en bypass (alimentada, no protegiendo)

NOTBYPASS

La SAU ya no está en bypass

ECO

La SAU está en modo ECO o similar (según lo define y nombra el fabricante); para más detalles, consulte upsmon(8).

NOTECO

La SAU ya no está en modo ECO (ver arriba)

ALARM

La SAU tiene una o más alarmas activas (verifique ups.alarm); para esta notificación, el mensaje puede contener un segundo marcador de posición %s para sustituir el valor actual de ups.alarm.

NOTALARM

La SAU ya no está en estado de alarma (sin alarmas activas)

OVER

La SAU está sobrecargada

NOTOVER

La SAU ya no está sobrecargada

TRIM

La SAU está ajustando el voltaje de entrada

NOTTRIM

La SAU ya no está ajustando el voltaje de entrada

BOOST

La SAU está aumentando el voltaje de entrada

NOTBOOST

La SAU ya no está aumentando el voltaje de entrada

OTHER

La SAU tiene al menos un token de ups.status no clasificado; para esta notificación, el mensaje puede contener un segundo marcador de posición %s para sustituir la colección actual de dichos tokens.

NOTOTHER

La SAU ya no tiene tokens de estado no clasificados

SUSPEND_STARTING

El sistema operativo está entrando en modo de suspensión/hibernación

SUSPEND_FINISHED

El sistema operativo acaba de finalizar el modo de suspensión/hibernación, desactivando las lecturas obsoletas de la SAU para evitar un apagado desafortunado

NOTIFYFLAG tipo bandera[+bandera]...

Por defecto, upsmon envía paredes (mensajes globales a todos los usuarios conectados) a través de /bin/wall y escribe en el syslog cuando ocurren cosas. Excepto en Windows, donde upsmon solo escribe en el Registro de Eventos por defecto. Puede cambiar esto.

Ejemplos:

NOTIFYFLAG ONLINE SYSLOG
NOTIFYFLAG ONBATT SYSLOG+WALL+EXEC

Valores posibles para las banderas:

SYSLOG

Escribe el mensaje en el syslog

WALL

Escribe el mensaje a todos los usuarios con /bin/wall

EXEC

Ejecuta NOTIFYCMD (ver arriba) con el mensaje

IGNORE

No hacer nada.

Si usa IGNORE, no use ninguna otra bandera en la misma línea.

POLLFREQ segundos

Normalmente, upsmon sondea el servidor upsd(8) cada 5 segundos. Si esto inunda su red con actividad, puede aumentarlo. También puede reducirlo para obtener actualizaciones más rápidas en algunos casos.

Hay algunas advertencias. Primero, si establece POLLFREQ demasiado alto, puede perder eventos de energía de corta duración por completo. También corre el riesgo de activar DEADTIME (ver arriba) si usa un número muy grande.

Segundo, hay un punto de rendimiento decreciente si lo establece demasiado bajo. Si bien upsd normalmente tiene todos los datos disponibles instantáneamente, la mayoría de los controladores solo actualizan el estado de la SAU una vez cada 2 segundos. Sonear más que eso generalmente no le proporciona la información más rápido.


Nota
Esta configuración es diferente de la frecuencia de sondeo soportada por algunos de los programas controladores de NUT, como usbhid-ups(8) (sobre la frecuencia con la que el controlador sondea un dispositivo en particular).

POLLFREQALERT segundos

Este es el intervalo que upsmon espera entre sondeos si alguna de sus SAU está funcionando con batería. Puede usar esto junto con POLLFREQ anterior para reducir la velocidad de los sondeos durante el comportamiento normal, pero obtener actualizaciones más rápidas cuando ocurre algo malo.

Siempre debe ser igual o inferior al valor de POLLFREQ. Por defecto, también se establece en 5 segundos.

Las advertencias de la entrada POLLFREQ sobre valores demasiado altos y demasiado bajos también se aplican aquí.

POWERDOWNFLAG nombre_archivo

upsmon crea este archivo cuando se ejecuta en modo primario cuando la SAU necesita ser apagada. Debe verificar la existencia de este archivo en sus scripts de apagado tardío y llamar a upsdrvctl shutdown si existe; tenga en cuenta que upsmon -K puede ser llamado para este efecto, si los archivos de configuración de NUT siguen siendo legibles en ese punto (sistemas de archivos mayormente desmontados o cambiados a solo lectura).

Históricamente, a menudo era /etc/killpower, pero hoy en día es posible que lo desee en un sistema de archivos temporal (por ejemplo, en /run o /run/nut).

Tenga en cuenta que se deben usar barras invertidas dobles para las rutas de Windows, por ejemplo, C:\\Temp\\killpower (Windows moderno también puede aceptar barras inclinadas como C:/Temp/killpower, pero su experiencia puede variar).

Esto se hace para restablecer forzadamente los sistemas secundarios, de modo que no se queden atascados en la etapa de "detenido" incluso si la energía regresa durante el proceso de apagado. Esto generalmente no funciona bien en SAU de contacto-closure que usan el controlador genericups.


Advertencia
El programa binario upsmon no tiene un valor predeterminado incorporado, por lo que esta configuración DEBE especificarse en la configuración, para que la integración de apagado tardío funcione en el sistema de modo primario particular.
Consulte el archivo config-notes.txt en el subdirectorio docs para obtener más información. Consulte la sección:

"Configuración de apagados automáticos para eventos de batería baja", o consulte la versión en línea.

OFFDURATION segundos

NUT soporta un "APAGADO administrativo" para dispositivos de energía que puede ser gestionado para apagar su carga de trabajo de aplicación, mientras que la SAU o ePDU permanece accesible para monitoreo y gestión. Este interruptor permite retrasar la propagación de dicho estado a una pérdida conocida de alimentación (posiblemente activando FSD en clientes upsmon que MONITOREAN el dispositivo y que de hecho aún están activos, por ejemplo, con múltiples fuentes de alimentación o porque ellos como carga no están realmente apagados), ya que cuando algunos dispositivos comienzan la calibración de la batería, informan "OFF" durante unos segundos y solo entonces podrían informar "CAL" después de cambiar todos los relés de potencia; causando así falsos positivos para el disparador FSD de upsmon.

Un valor negativo significa deshabilitar la disminución del contador de fuentes de alimentación en funcionamiento en tales casos, y un cero hace que el efecto del estado "OFF" detectado sea inmediato. El valor predeterminado incorporado es 30 (segundos), para poner en efecto un estado "OFF" (disminuir el número de fuentes de alimentación conocidas) si persiste durante esta cantidad de segundos.


Nota
hasta ahora, admitimos que el dispositivo informe un estado "OFF" que generalmente significa apagar completamente la carga; se registró un problema en el rastreador de errores para diseñar un soporte similar solo para algunas tomas o grupos de tomas manejables.

OVERDURATION segundos

Esta configuración maneja cómo una SAU sobrecargada debe se debe tratar en situaciones en las que no se comunica completamente. Dado que dicha SAI puede encontrarse en un estado potencialmente grave, algunos usuarios pueden desear que sus sistemas se apaguen inmediatamente o después de que haya transcurrido un tiempo de espera establecido. La configuración OVERDURATION define este tiempo de espera (en segundos), después del cual una SAI sobrecargada que no se comunica se considerará crítica.

Un valor negativo significa que una SAI sobrecargada nunca se considerará crítica (al menos no por la propia sobrecarga). Un valor de cero significa que la SAI se considerará crítica instantáneamente cuando esté sobrecargada y no se comunique. El valor predeterminado incorporado es -1 (segundos).


Nota
Esta configuración solo afecta el comportamiento cuando una SAI está tanto sobrecargada como no se comunica. Cuando la SAI se comunica normalmente, una condición de sobrecarga puede generar notificaciones pero no activará un apagado del sistema por sí sola.

OBLBDURATION segundos

NUT normalmente genera alarmas para apagado inmediato (FSD) para los consumidores de una SAI que se sabe que está en batería ("OB") y que alcanza el estado de batería baja ("LB"), si esa es su última fuente de energía restante para cumplir con su configuración MINSUPPLIES. En algunos casos especiales, los usuarios pueden desear retrasar la generación de la alarma (usando la opción OBLBDURATION) a su discreción y riesgo de un apagado abrupto.

Un valor positivo pone el estado "OB LB" en efecto solo si persiste durante esta cantidad de segundos. Un valor no positivo hace que el efecto FSD del estado "OB LB" detectado sea inmediato. El valor predeterminado incorporado es 0 (segundos).


Nota
Si tanto las opciones OBLBDURATION como HOSTSYNC están configuradas en el mismo sistema cliente upsmon (secundario), y HOSTSYNC es más corto, se ignorará efectivamente: upsmon esperará hasta OBLBDURATION segundos para que el estado "OB LB" se despeje, y luego la lógica del cliente secundario pasará a un apagado inmediato. Si el sistema principal emite un FSD en esta SAI, eso tendría un efecto de prioridad aún mayor tan pronto como se vea.

RBWARNTIME segundos

Cuando una SAI indica que necesita que se reemplace su batería, upsmon generará un evento NOTIFY_REPLBATT. Por defecto, esto ocurre cada 43200 segundos (12 horas).

Si necesita otro valor, establézcalo aquí.

ALARMCRITICAL 0 | 1

NUT normalmente considera las SAI con alarmas activas como volátiles, lo que significa que se observan más de cerca y pueden considerarse críticas/muertas antes que en otros estados normales de SAI. Esto es especialmente cierto en situaciones de falta de comunicación, donde una SAI en estado de ALARMA se considerará perdida y se pueden activar apagados del sistema como producto.

Dado que no existe un estándar común para lo que constituye una alarma, dichos estados de alarma pueden ser en realidad de naturaleza mundana y el comportamiento anterior no deseado debido a posibles apagados del sistema injustificados.

Cuando esta configuración está deshabilitada, upsmon considerará una SAI en estado de alarma como no volátil y la tratará como cualquier otro estado.

RUN_AS_USER nombredeusuario

upsmon normalmente se divide en dos procesos, manteniendo una pequeña parte que permanece propiedad de root para iniciar el apagado del sistema llamando a SHUTDOWNCMD cuando/si llega el momento, y ejecuta la mayor parte de las tareas de monitoreo bajo otro ID de usuario después de soltar los privilegios de root. En la mayoría de los sistemas personalizados, esto significa que se ejecuta como "nobody", ya que ese es el valor predeterminado de tiempo de compilación; los paquetes a menudo entregan un usuario "nut" o "ups" para ejecutar los demonios de servicio de NUT.

El problema es que el "nobody" predeterminado del sistema no puede leer el archivo upsmon.conf, ya que por defecto está instalado de tal manera que solo root puede abrirlo (porque este archivo puede contener datos confidenciales como credenciales del servidor de datos NUT remoto). Esto significa que no podrá recargar el archivo de configuración, ya que no estará disponible para la parte no privilegiada del demonio upsmon.

La solución es crear un nuevo usuario solo para upsmon y luego hacer que se ejecute como ese usuario. Puede ser la misma cuenta que se utiliza para los controladores NUT o el servidor de datos, pero no tiene por qué serlo. En sistemas con mayores preocupaciones sobre seguridad y separación de privilegios, sugerimos "nutmon", pero puede usar cualquier cosa que no esté ya ocupada en su sistema. Simplemente cree un usuario normal sin privilegios especiales y con una contraseña imposible.

Luego, indique a upsmon que se ejecute como ese usuario y haga que upsmon.conf sea legible para él. Sus recargas funcionarán y su archivo de configuración se mantendrá seguro.

Este archivo no debe ser escribible por el usuario upsmon, ya que sería posible explotar una vulnerabilidad, cambiar SHUTDOWNCMD por algo malicioso y luego esperar a que se reinicie upsmon. Por lo tanto, normalmente también crearía un grupo para los demonios NUT (del cual el usuario sería miembro) y otorgaría a ese grupo acceso de solo lectura a los archivos de configuración propiedad de root.

Dicho esto, pueden ser posibles otras variantes; por ejemplo, ejecutar todo upsmon como un solo proceso iniciado y propiedad inicialmente por nut y llamar a un script de apagado prefijado por sudo, pfexec u otras herramientas RBAC. Sin embargo, esto agrega más "partes móviles" y fragilidad (por ejemplo, la configuración de sudoers puede vivir en LDAP, y ese servidor podría no estar disponible durante el apagado cuando el rack está medio apagado, justo cuando lo necesita aquí), y no está disponible en todas las plataformas; por lo tanto, tales configuraciones son algo que los usuarios exploran por su cuenta hasta ahora (daríamos la bienvenida a publicaciones en NUT Wiki o enlaces a blogs).

SHUTDOWNCMD comando

upsmon ejecuta este comando cuando el sistema necesita ser apagado. Si es un sistema secundario, lo hará inmediatamente siempre que el valor general de potencia actual caiga por debajo del valor MINSUPPLIES anterior.

Cuando upsmon es un sistema primario, permitirá que los sistemas secundarios se desconecten antes de iniciar el procedimiento de apagado local.

Tenga en cuenta que el comando debe ser un elemento en el archivo de configuración. Si su comando de apagado incluye espacios, póngalo entre comillas para mantenerlo unido, es decir:

SHUTDOWNCMD "/sbin/shutdown -h +0"

SHUTDOWNEXIT booleano|número

Después de iniciar el apagado, ¿debe salir este demonio upsmon? Al hacerlo, los sistemas secundarios de NUT pueden indicar al primario de NUT que puede proceder con su propio apagado y, finalmente, indicar a la SAI que corte la energía para la carga. ("Sí" por defecto)

Algunos sistemas "secundarios" con cargas de trabajo que tardan considerable tiempo en detenerse (por ejemplo, máquinas virtuales o bases de datos grandes) pueden beneficiarse de informar (mediante la desconexión del servidor de datos) que están listos para que el sistema "primario" comience su propio apagado y, finalmente, para indicar a la SAI que corte la energía; no tan pronto como hayan iniciado su propio apagado, sino en un momento posterior (por ejemplo, cuando el servicio upsmon se detiene DESPUÉS de las cargas de trabajo más pesadas).

Tenga en cuenta que la capacidad real de completar dicho apagado depende del tiempo de ejecución restante de la batería en el momento en que el estado de energía de la SAI se considera crítico y comienzan los apagados. Es posible que también deba ajustar HOSTSYNC en el primario de NUT para que sea lo suficientemente largo para que esos secundarios detengan sus servicios. En la práctica, puede valer la pena investigar formas de activar apagados antes en estos sistemas, por ejemplo, configurando la integración de upssched o un controlador ups-dummy con anulaciones para disparadores de batería.carga o tiempo de ejecución de la batería más estrictos que los utilizados por el resto de sus servidores.

Esta opción admite cadenas de estilo booleano (sí/encendido/verdadero o no/apagado/falso) o números para definir un retraso (en segundos) entre la llamada a SHUTDOWNCMD y la salida del demonio. Cero significa salida inmediata (predeterminado), valores negativos significan nunca salir por iniciativa propia.

CERTPATH archivo de certificado o base de datos

Cuando se compila con soporte SSL, puede ingresar la ruta del certificado aquí.

Con NSS:

Los certificados se almacenan en una base de datos dedicada (datos divididos en 3 archivos). Especifique la ruta del directorio de la base de datos.

Con OpenSSL:

Directorio que contiene certificados de CA en formato PEM, utilizado para verificar el certificado del servidor presentado por el servidor upsd. Los archivos contienen cada uno un certificado de CA. Los archivos se buscan por el valor hash del nombre del sujeto de la CA, que por lo tanto debe estar disponible.

CERTIDENT nombredelcertificado contraseñadelabasededatos

Cuando se compila con soporte SSL con NSS, puede especificar el nombre del certificado a recuperar de la base de datos para autenticarse y la contraseña requerida para acceder a la clave privada relacionada con el certificado.

Nota
Asegúrese de encerrar "nombre del certificado" entre comillas dobles si está utilizando un valor con espacios.

CERTHOST nombredehost nombredelcertificado certverify forcessl

Cuando se compila con soporte SSL con NSS, puede especificar directivas de seguridad para cada servidor con el que pueda contactar.

Cada entrada mapea el nombre del servidor con el nombre del certificado esperado y las banderas que indican si el certificado del servidor se verifica y si la conexión debe ser segura.


Nota
Asegúrese de encerrar "nombre del certificado" entre comillas dobles si está utilizando un valor con espacios.

CERTVERIFY 0 | 1

Cuando se compila con soporte SSL, haga que upsmon verifique todas las conexiones con certificados.

Sin esto, no hay garantía de que el upsd sea el host correcto. Habilitar esto reduce en gran medida el riesgo de ataques de intermediario. Esto fuerza efectivamente el uso de SSL, así que no use esto a menos que todos sus hosts upsd estén listos para SSL y tengan sus certificados en orden.

Cuando se compila con soporte NSS de SSL, puede ser anulado para hosts especificados con una directiva CERTHOST.

FORCESSL 0 | 1

Cuando se compila con SSL, especifique que se debe usar una conexión segura para comunicarse con upsd.

Si no usa *CERTVERIFY* *1*, esto al menos garantizará que nadie pueda espiar sus sesiones sin un gran esfuerzo. Configurar esto hará que upsmon descarte las conexiones si el upsd remoto no admite SSL, así que no lo use a menos que todos lo tengan en funcionamiento.

Cuando se compila con soporte NSS de SSL, puede ser anulado para hosts especificados con una directiva CERTHOST.

DEBUG_MIN ENTERO

Opcionalmente, especifique un nivel mínimo de depuración para el demonio upsmon, por ejemplo, para solucionar problemas de implementación, sin afectar directamente el modo de ejecución en primer plano o en segundo plano. La opción de línea de comandos -D solo puede aumentar este nivel de verbosidad.

Nota
si el demonio en ejecución recibe un comando de recarga, la presencia del valor DEBUG_MIN NUMBER en el archivo de configuración se puede usar para ajustar la verbosidad de la depuración en el demonio de servicio en ejecución.n (se recomienda comentarlo o establecer el mínimo a cero explícito cuando se haya terminado, para evitar diarios enormes y abuso del sistema de E/S). Tenga en cuenta que para esta sintonización en tiempo de ejecución, el valor DEBUG_MIN **presente** en los archivos de configuración **recargados** se aplica instantáneamente y anula cualquier valor previamente establecido, desde el archivo o las opciones de la CLI, independientemente de si el nivel de registro anterior era mayor o menor que el número recién encontrado; un valor faltante (o comentado) sin embargo no cambia la verbosidad del registro previamente activa.
