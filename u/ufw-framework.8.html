NOMBRE

ufw-framework - usar el framework de ufw

DESCRIPCIÓN

ufw proporciona tanto una interfaz de línea de comandos como un framework para gestionar un firewall netfilter. Mientras que el comando ufw proporciona una interfaz fácil de usar para gestionar un firewall, el framework ufw proporciona al administrador métodos para personalizar el comportamiento por defecto y añadir reglas no soportadas por la herramienta de línea de comandos. De esta manera, ufw puede aprovechar al máximo la potencia y flexibilidad de netfilter de Linux.

VISIÓN GENERAL

El framework proporciona inicialización al arrancar, archivos de reglas para añadir reglas personalizadas, un método para cargar módulos netfilter, configuración de parámetros del kernel y configuración de IPv6. El framework consta de los siguientes archivos:

/usr/lib/ufw/ufw-init
script de inicialización
/etc/ufw/before.init
script de personalización de inicialización ejecutado antes de que se inicialice ufw
/etc/ufw/after.init
script de personalización de inicialización ejecutado después de que se inicialice ufw
/etc/ufw/before[6].rules
archivo de reglas que contiene reglas evaluadas antes que las reglas añadidas por la UI
/etc/ufw/user[6].rules
archivo de reglas que contiene reglas añadidas por la UI (gestionado con el comando ufw)
/etc/ufw/after[6].rules
archivo de reglas que contiene reglas evaluadas después de las reglas añadidas por la UI
/etc/default/ufw
configuración de alto nivel
/etc/ufw/sysctl.conf
ajustes finos de red del kernel
/etc/ufw/ufw.conf
configuración adicional de alto nivel

INICIALIZACIÓN AL ARRANQUE

ufw se inicia al arrancar con /usr/lib/ufw/ufw-init. Este script es un script de inicialización estándar estilo SysV utilizado por el comando ufw y no debe ser modificado. Los scripts /etc/before.init y /etc/after.init pueden ser utilizados para realizar cualquier configuración adicional del firewall que aún no sea soportada por ufw y, si existen y son ejecutables, ufw-init ejecutará estos scripts. ufw-init saldrá con error si alguno de estos scripts sale con error. ufw-init soporta los siguientes argumentos:

start:
carga el firewall
stop:
descarga el firewall
restart:
recarga el firewall
force-reload:
igual que restart
status:
estado básico del firewall
force-stop:
igual que stop, excepto que no comprueba si el firewall ya está cargado
flush-all:
vacía las cadenas incorporadas, elimina todas las cadenas no incorporadas y restablece la política a ACCEPT

ufw-init llamará a before.init y after.init con start, stop, status y flush-all, pero típicamente, si se usan, estos scripts sólo necesitan implementar start y stop.

ufw utiliza muchas cadenas definidas por el usuario además de las cadenas incorporadas de iptables. Si MANAGE_BUILTINS en /etc/default/ufw está configurado como 'yes', al detener y recargar se vacían las cadenas incorporadas. Si está configurado como 'no', al detener y recargar se eliminan las cadenas secundarias de ufw y se vacían las cadenas primarias de ufw. Además de vaciar las cadenas específicas de ufw, mantiene las cadenas primarias en el mismo orden con respecto a cualquier otra cadena definida por el usuario que pueda haber sido añadida. Esto permite que ufw interoperar con otro software que pueda gestionar sus propias reglas de firewall.

Para asegurar que su firewall se carga al arrancar, debe integrar este script en el proceso de arranque. Consulte la documentación de su distribución para conocer la forma correcta de modificar su proceso de arranque si ufw no está ya integrado.

ARCHIVOS DE REGLAS

ufw es en parte un front-end para iptables-restore, con sus reglas guardadas en /etc/ufw/before.rules, /etc/ufw/after.rules y /etc/ufw/user.rules. Los administradores pueden personalizar before.rules y after.rules según deseen utilizando la sintaxis estándar de iptables-restore. Las reglas se evalúan de la siguiente manera: primero before.rules, luego user.rules y finalmente after.rules. Las reglas IPv6 se evalúan de la misma manera, con los archivos de reglas llamados before6.rules, user6.rules y after6.rules. Tenga en cuenta que ufw status solo muestra las reglas añadidas con ufw y no las reglas encontradas en los archivos de reglas de /etc/ufw.

Importante: ufw solo utiliza la tabla *filter por defecto. Puede añadir cualquier otra tabla como *nat, *raw y *mangle según desee. Para cada tabla se requiere una sentencia COMMIT correspondiente.

Después de modificar cualquiera de estos archivos, debe recargar ufw para que las reglas surtan efecto. Consulte la sección EJEMPLOS para ver usos comunes de estos archivos de reglas.

MÓDULOS

Netfilter tiene muchos módulos diferentes de seguimiento de conexiones. Estos módulos son conscientes del protocolo subyacente y permiten al administrador simplificar sus conjuntos de reglas. Puede ajustar qué módulos netfilter cargar ajustando IPT_MODULES en /etc/default/ufw. Algunos módulos populares para cargar son:


nf_conntrack_ftp
nf_nat_ftp
nf_conntrack_irc
nf_nat_irc
nf_conntrack_netbios_ns
nf_conntrack_pptp
nf_conntrack_tftp
nf_nat_tftp
nf_conntrack_sane

La carga incondicional de módulos de seguimiento de conexiones (nf_conntrack_*) de esta manera está obsoleta. ufw continúa soportando la funcionalidad, pero la nueva configuración solo debe contener los módulos específicos requeridos para el sitio. Para más información, vea AYUDAS DE CONEXIÓN.

PARÁMETROS DEL KERNEL

ufw leerá /etc/ufw/sysctl.conf al arrancar cuando esté habilitado. Tenga en cuenta que /etc/ufw/sysctl.conf anula los valores en el systcl.conf del sistema (generalmente /etc/sysctl.conf). Los administradores pueden cambiar el archivo utilizado modificando /etc/default/ufw.

IPV6

IPv6 está habilitado por defecto. Cuando está deshabilitado, todos los paquetes entrantes, salientes y reenviados son descartados, con la excepción del tráfico en la interfaz de loopback. Para ajustar este comportamiento, establezca IPV6 a 'yes' en /etc/default/ufw. Consulte la página del manual de ufw para más detalles.

EJEMPLOS

Como se mencionó, ufw carga sus archivos de reglas en el kernel utilizando los comandos iptables-restore y ip6tables-restore. Los usuarios que deseen añadir reglas a los archivos de reglas de ufw manualmente deben estar familiarizados con estos comandos, así como con los comandos iptables e ip6tables. A continuación se presentan algunos ejemplos comunes de uso de los archivos de reglas de ufw. Todos los ejemplos asumen solo IPv4 y que DEFAULT_FORWARD_POLICY en /etc/default/ufw está configurado como DROP.

Masquerading IP

Para permitir el masquerading IP para que las computadoras de la red 10.0.0.0/8 en eth1 compartan la única dirección IP en eth0:

Editar /etc/ufw/sysctl.conf para que tenga:

net.ipv4.ip_forward=1
Añadir al final de /etc/ufw/before.rules, después de la sección *filter:

*nat
:POSTROUTING ACCEPT [0:0]
-A POSTROUTING -s 10.0.0.0/8 -o eth0 -j MASQUERADE
COMMIT
Si su firewall está utilizando túneles IPv6 o 6to4 y también está haciendo NAT, entonces no debería normalmente hacer masquerading de paquetes de protocolo '41' (ipv6). Por ejemplo, en lugar de lo anterior, /etc/ufw/before.rules puede ser ajustado para tener:

*nat
:POSTROUTING ACCEPT [0:0]
-A POSTROUTING -s 10.0.0.0/8 ! --protocol 41 -o eth0 -j MASQUERADE
COMMIT
Añadir la ufw route para permitir el tráfico:

ufw route allow in on eth1 out on eth0 from 10.0.0.0/8

Redirecciones de puertos

Para redirigir el tráfico entrante en el puerto 80 de eth0 a un servidor en la dirección IP 10.0.0.2 en el puerto 8080:

Editar /etc/ufw/before.rules para tener:

*nat
:PREROUTING ACCEPT [0:0]
-A PREROUTING -i eth0 -p tcp --dport 80 -j DNAT --to-destination 10.0.0.2:8080
COMMIT
Añadir la ufw route para permitir el tráfico:

ufw route redirect to 10.0.0.2 port 8080 from any port 80 proto tcp

EJEMPLOS

Redirecciones de puertos

Para reenviar el puerto tcp 80 en eth0 al servidor web en 10.0.0.2:

Editar /etc/ufw/sysctl.conf para que contenga:

net.ipv4.ip_forward=1
Añadir al final de /etc/ufw/before.rules, después de la sección *filter:

*nat
:PREROUTING ACCEPT [0:0]
-A PREROUTING -p tcp -i eth0 --dport 80 -j DNAT \
--to-destination 10.0.0.2:80
COMMIT
Añadir la regla ufw route para permitir el tráfico:

ufw route allow in on eth0 to 10.0.0.2 port 80 proto tcp

Filtrado de salida

Para bloquear direcciones RFC1918 que salgan por eth0:

Añadir las reglas ufw route para rechazar el tráfico:

ufw route reject out on eth0 to 10.0.0.0/8
ufw route reject out on eth0 to 172.16.0.0/12
ufw route reject out on eth0 to 192.168.0.0/16

Ejemplo completo

Este ejemplo combina los otros ejemplos y demuestra un simple cortafuegos de enrutamiento. Advertencia: esta configuración es solo un ejemplo para demostrar la funcionalidad del framework ufw de manera concisa y simple, y no debe usarse en producción sin comprender qué hace cada parte y qué no hace. Su cortafuegos sin duda querrá estar menos abierto.

Este enrutador/cortafuegos tiene dos interfaces: eth0 (orientada a Internet) y eth1 (LAN interna). Los clientes internos tienen direcciones en la red 10.0.0.0/8 y deberían poder conectarse a cualquier lugar de Internet. Las conexiones al puerto 80 desde Internet deben ser reenviadas a 10.0.0.2. Se debe permitir el acceso al puerto ssh 22 desde la estación de trabajo administrativa (10.0.0.100) a esta máquina. Asegúrese también de que ningún tráfico interno vaya a Internet.

Editar /etc/ufw/sysctl.conf para que contenga:

net.ipv4.ip_forward=1
Añadir al final de /etc/ufw/before.rules, después de la sección *filter:

*nat
:PREROUTING ACCEPT [0:0]
:POSTROUTING ACCEPT [0:0]
-A PREROUTING -p tcp -i eth0 --dport 80 -j DNAT \
--to-destination 10.0.0.2:80
-A POSTROUTING -s 10.0.0.0/8 -o eth0 -j MASQUERADE
COMMIT
Añadir las reglas ufw necesarias:

ufw route reject out on eth0 to 10.0.0.0/8
ufw route reject out on eth0 to 172.16.0.0/12
ufw route reject out on eth0 to 192.168.0.0/16
ufw route allow in on eth1 out on eth0 from 10.0.0.0/8
ufw route allow in on eth0 to 10.0.0.2 port 80 proto tcp
ufw allow in on eth1 from 10.0.0.100 to any port 22 proto tcp

AYUDAS DE CONEXIÓN

Varios protocolos requieren el uso de ayudas de seguimiento de conexiones de netfilter para agrupar paquetes relacionados en flujos RELACIONADOS para hacer que los conjuntos de reglas sean más claros y precisos. Por ejemplo, con un par de módulos del kernel y un par de reglas, un conjunto de reglas podría simplemente permitir una conexión al puerto FTP 21, luego el kernel examinaría el tráfico y marcaría los otros paquetes de datos FTP como RELACIONADOS con la conexión inicial.

Cuando se introdujeron por primera vez las ayudas, solo se podían configurar los módulos como parte de la carga del módulo (por ejemplo, si su servidor FTP escuchaba en un puerto diferente al 21, tendría que cargar el módulo nf_conntrack_ftp especificando el puerto correcto). Con el tiempo, se entendió que el uso incondicional de ayudas de conexión podría conducir a abusos, en parte porque algunos protocolos permiten datos especificados por el usuario que permitirían atravesar el cortafuegos de maneras no deseadas. A partir del kernel 4.7, la asignación automática de ayudas de conntrack (es decir, el manejo de paquetes para un puerto determinado y todas las direcciones IP) está deshabilitada (el comportamiento anterior se puede restaurar estableciendo net/netfilter/nf_conntrack_helper=1 en /etc/ufw/sysctl.conf). Ahora, los cortafuegos deberían utilizar el objetivo CT para asociar el tráfico con una ayuda particular y luego establecer reglas RELACIONADAS para usar la ayuda. Esto permite a los sitios adaptar el uso de las ayudas y ayudar a evitar abusos.

En general, para usar ayudas de forma segura, debe suceder lo siguiente:

1.
net/netfilter/nf_conntrack_helper debe establecerse en 0 (por defecto)
2.
crear una regla para el inicio de una conexión (por ejemplo, para FTP, puerto 21)
3.
crear una regla de ayuda para asociar la ayuda con esta conexión
4.
crear una regla de ayuda para asociar un flujo RELACIONADO con esta conexión
5.
si es necesario, añadir el módulo nf_conntrack_* correspondiente a IPT_MODULES
6.
opcionalmente, añadir el módulo nf_nat_* correspondiente a IPT_MODULES

En general, es deseable hacer que las reglas de ayuda de conexión sean lo más específicas posible y asegurarse de que la protección anti-spoofing esté configurada correctamente para su sitio para evitar problemas de seguridad en su conjunto de reglas. Para obtener más información, consulte ANTI-SPOOFING, arriba, y https://home.regit.org/netfilter-en/secure-use-of-helpers/.

Actualmente, las reglas de ayuda deben gestionarse a través de los ARCHIVOS DE REGLAS. Una versión futura de ufw introducirá sintaxis para trabajar con reglas de ayuda.

NOTAS

Al usar ufw con libvirt y puentes, los paquetes pueden ser bloqueados. El equipo de libvirt recomienda que los siguientes sysctl se configuren para deshabilitar netfilter en el puente:


net.bridge.bridge-nf-call-ip6tables = 0
net.bridge.bridge-nf-call-iptables = 0
net.bridge.bridge-nf-call-arptables = 0

Tenga en cuenta que el módulo bridge debe cargarse en el kernel antes de que se establezcan estos valores. Una forma de asegurar que esto funcione correctamente con ufw es añadir 'bridge' a IPT_MODULES en /etc/default/ufw, y luego añadir las reglas anteriores a /etc/ufw/sysctl.conf.

Alternativamente, en lugar de deshabilitar netfilter en el puente, puede configurar iptables para permitir que todo el tráfico se reenvíe a través del puente. Por ejemplo, añadir a /etc/ufw/before.rules dentro de la sección *filter:


-I FORWARD -m physdev --physdev-is-bridged -j ACCEPT
