userfaultfd(2) System Calls Manual userfaultfd(2)

NOMBRE

userfaultfd - crea un descriptor de archivo para manejar fallos de página en el espacio de usuario

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

SINOPSIS

#include <fcntl.h>             /* Definición de las constantes O_* */
#include <sys/syscall.h>       /* Definición de las constantes SYS_* */
#include <linux/userfaultfd.h> /* Definición de las constantes UFFD_* */
#include <unistd.h>
int syscall(SYS_userfaultfd, int flags);

Nota: glibc no proporciona un envoltorio para userfaultfd(), necesitando el uso de syscall(2).

DESCRIPCIÓN

userfaultfd() crea un nuevo objeto userfaultfd que puede ser utilizado para la delegación del manejo de fallos de página a una aplicación del espacio de usuario, y devuelve un descriptor de archivo que se refiere al nuevo objeto. El nuevo objeto userfaultfd se configura utilizando ioctl(2).

Una vez que el objeto userfaultfd está configurado, la aplicación puede usar read(2) para recibir notificaciones de userfaultfd. Las lecturas desde userfaultfd pueden ser bloqueantes o no bloqueantes, dependiendo del valor de flags utilizado para la creación del userfaultfd o llamadas posteriores a fcntl(2).

Los siguientes valores pueden ser combinados mediante OR bit a bit en flags para cambiar el comportamiento de userfaultfd():

O_CLOEXEC
Habilita el flag close-on-exec para el nuevo descriptor de archivo userfaultfd. Ver la descripción del flag O_CLOEXEC en open(2).
O_NONBLOCK
Habilita la operación no bloqueante para el objeto userfaultfd. Ver la descripción del flag O_NONBLOCK en open(2).
UFFD_USER_MODE_ONLY
Este es un flag específico de userfaultfd que fue introducido en Linux 5.11. Cuando está configurado, el objeto userfaultfd solo podrá manejar fallos de página originados desde el espacio de usuario en las regiones registradas. Cuando se activa un fallo originado por el kernel en el rango registrado con este userfaultfd, se entregará una señal SIGBUS.

Cuando el último descriptor de archivo que se refiere a un objeto userfaultfd se cierra, todos los rangos de memoria que fueron registrados con el objeto se desregistran y los eventos pendientes se vacían.

Userfaultfd soporta tres modos de registro:

UFFDIO_REGISTER_MODE_MISSING (desde Linux 4.10)
Cuando se registra con el modo UFFDIO_REGISTER_MODE_MISSING, el espacio de usuario recibirá una notificación de fallo de página cuando se acceda a una página faltante. El hilo que falló se detendrá hasta que el fallo de página sea resuelto desde el espacio de usuario mediante una llamada `ioctl` UFFDIO_COPY o UFFDIO_ZEROPAGE.
UFFDIO_REGISTER_MODE_MINOR (desde Linux 5.13)
Cuando se registra con el modo UFFDIO_REGISTER_MODE_MINOR, el espacio de usuario recibirá una notificación de fallo de página cuando ocurra un fallo de página menor. Es decir, cuando una página de respaldo está en la caché de páginas, pero las entradas de la tabla de páginas aún no existen. El hilo que falló se detendrá hasta que el fallo de página sea resuelto desde el espacio de usuario mediante una llamada `ioctl` UFFDIO_CONTINUE.
UFFDIO_REGISTER_MODE_WP (desde Linux 5.7)
Cuando se registra con el modo UFFDIO_REGISTER_MODE_WP, el espacio de usuario recibirá una notificación de fallo de página cuando se escriba en una página protegida contra escritura. El hilo que falló se detendrá hasta que el espacio de usuario retire la protección de escritura de la página mediante una llamada `ioctl` UFFDIO_WRITEPROTECT.

Se pueden habilitar múltiples modos al mismo tiempo para el mismo rango de memoria.

Desde Linux 4.14, una notificación de fallo de página de userfaultfd puede incrustar selectivamente información del ID del hilo que falló en la notificación. Es necesario habilitar explícitamente esta funcionalidad usando el bit de característica UFFD_FEATURE_THREAD_ID al inicializar el contexto de userfaultfd. Por defecto, la notificación del ID del hilo está deshabilitada.

Uso

El mecanismo userfaultfd está diseñado para permitir que un hilo en un programa multihilo realice paginación en el espacio de usuario para los otros hilos del proceso. Cuando ocurre un fallo de página para una de las regiones registradas en el objeto userfaultfd, el hilo que falló se pone en espera y se genera un evento que puede ser leído a través del descriptor de archivo userfaultfd. El hilo manejador de fallos lee eventos de este descriptor de archivo y los atiende utilizando las operaciones descritas en ioctl_userfaultfd(2). Al atender los eventos de fallo de página, el hilo manejador puede activar el despertar del hilo que está en espera.

Es posible que los hilos que fallan y los hilos que manejan los fallos se ejecuten en el contexto de diferentes procesos. En este caso, estos hilos pueden pertenecer a programas diferentes, y el programa que ejecuta los hilos que fallan no necesariamente cooperará con el programa que maneja los fallos de página. En tal modo no cooperativo, el proceso que monitoriza userfaultfd y maneja los fallos de página necesita ser consciente de los cambios en la disposición de la memoria virtual del proceso que falla para evitar la corrupción de memoria.

Desde Linux 4.11, userfaultfd también puede notificar a los hilos manejadores de fallos sobre cambios en la disposición de la memoria virtual del proceso que falla. Además, si el proceso que falla invoca fork(2), los objetos userfaultfd asociados con el padre pueden ser duplicados en el proceso hijo y el monitor userfaultfd será notificado (a través de UFFD_EVENT_FORK descrito a continuación) sobre el descriptor de archivo asociado con los objetos userfault creados para el proceso hijo, lo que permite al monitor userfaultfd realizar paginación en el espacio de usuario para el proceso hijo. A diferencia de los fallos de página que deben ser síncronos y requieren un despertar explícito o implícito, todos los demás eventos se entregan de forma asíncrona y el proceso no cooperativo reanuda la ejecución tan pronto como el gestor de userfaultfd ejecuta read(2). El gestor de userfaultfd debe sincronizar cuidadosamente las llamadas a UFFDIO_COPY con el procesamiento de eventos.

El modelo actual asíncrono de entrega de eventos es óptimo para implementaciones de gestores userfaultfd no cooperativos y monohilo.

Desde Linux 5.7, userfaultfd puede realizar seguimiento de páginas sucias de forma síncrona utilizando el nuevo modo de registro de protección contra escritura. Se debe verificar la característica UFFD_FEATURE_PAGEFAULT_FLAG_WP antes de usar esta funcionalidad. Similar al modo original de userfaultfd para páginas faltantes, el modo de protección contra escritura generará una notificación de userfaultfd cuando se escriba en la página protegida. El usuario necesita resolver el fallo de página desprotegiendo la página que falló y solicitando al hilo que falló que continúe. Para más información, por favor consulte la sección "Userfaultfd write-protect mode".

Operación de Userfaultfd

Después de que el objeto userfaultfd es creado con userfaultfd(), la aplicación debe habilitarlo usando la operación UFFDIO_API de ioctl(2). Esta operación permite un apretón de manos de dos pasos entre el kernel y el espacio de usuario para determinar qué versión de API y qué características soporta el kernel, y luego habilitar aquellas características que el espacio de usuario desea. Esta operación debe ser realizada antes que cualquiera de las otras operaciones de ioctl(2) descritas a continuación (o esas operaciones fallarán con el error EINVAL).

Después de una operación exitosa de UFFDIO_API, la aplicación registra rangos de direcciones de memoria usando la operación UFFDIO_REGISTER de ioctl(2). Después de la finalización exitosa de una operación UFFDIO_REGISTER, un fallo de página que ocurra en el rango de memoria solicitado, y que satisfaga el modo definido en el momento del registro, será reenviado por el kernel a la aplicación del espacio de usuario. La aplicación puede entonces usar varias operaciones (por ejemplo, UFFDIO_COPY, UFFDIO_ZEROPAGE, o UFFDIO_CONTINUE) de ioctl(2) para resolver el fallo de página.

Desde Linux 4.14, si la aplicación establece el bit de característica UFFD_FEATURE_SIGBUS usando la operación ioctl(2) UFFDIO_API, no se enviará ninguna notificación de error de página al espacio de usuario. En su lugar, se entregará una señal SIGBUS al proceso que generó el error. Con esta característica, userfaultfd se puede utilizar con fines de robustez para simplemente capturar cualquier acceso a áreas dentro del rango de direcciones registrado que no tengan páginas asignadas, sin tener que escuchar eventos de userfaultfd. No se requerirá ningún monitor de userfaultfd para manejar dichos accesos a memoria. Por ejemplo, esta característica puede ser útil para aplicaciones que desean evitar que el kernel asigne páginas automáticamente y rellene huecos en archivos dispersos cuando se accede al hueco a través de un mapeo de memoria.

La característica UFFD_FEATURE_SIGBUS se hereda implícitamente a través de fork(2) si se utiliza en combinación con UFFD_FEATURE_FORK.

Los detalles de las diversas operaciones de ioctl(2) se pueden encontrar en ioctl_userfaultfd(2).

Desde Linux 4.11, se pueden habilitar eventos distintos de los errores de página durante la operación UFFDIO_API.

Hasta Linux 4.11, userfaultfd solo se podía utilizar con mapeos de memoria privados anónimos. Desde Linux 4.11, userfaultfd también se puede utilizar con mapeos de memoria hugetlbfs y de memoria compartida.

Userfaultfd modo de protección contra escritura (desde Linux 5.7)

Desde Linux 5.7, userfaultfd admite el modo de protección contra escritura para memoria anónima. El usuario debe primero verificar la disponibilidad de esta característica utilizando la operación ioctl(2) UFFDIO_API contra el bit de característica UFFD_FEATURE_PAGEFAULT_FLAG_WP antes de usar esta característica.

Desde Linux 5.19, el modo de protección contra escritura también se admitió en los tipos de memoria shmem y hugetlbfs. Se puede detectar con el bit de característica UFFD_FEATURE_WP_HUGETLBFS_SHMEM.

Para registrarse en el modo de protección contra escritura de userfaultfd, el usuario debe iniciar la operación ioctl(2) UFFDIO_REGISTER con el modo UFFDIO_REGISTER_MODE_WP establecido. Tenga en cuenta que es legal monitorear el mismo rango de memoria con varios modos. Por ejemplo, el usuario puede realizar UFFDIO_REGISTER con el modo establecido en UFFDIO_REGISTER_MODE_MISSING | UFFDIO_REGISTER_MODE_WP. Cuando solo se registra UFFDIO_REGISTER_MODE_WP, el espacio de usuario *no* recibirá ninguna notificación cuando se escriba en una página faltante. En su lugar, el espacio de usuario recibirá una notificación de error de protección contra escritura solo cuando se escriba en una página existente pero protegida contra escritura.

Después de que la operación ioctl(2) UFFDIO_REGISTER se complete con el modo UFFDIO_REGISTER_MODE_WP establecido, el usuario puede proteger contra escritura cualquier memoria existente dentro del rango utilizando la operación ioctl(2) UFFDIO_WRITEPROTECT donde uffdio_writeprotect.mode debe establecerse en UFFDIO_WRITEPROTECT_MODE_WP.

Cuando ocurre un evento de protección contra escritura, el espacio de usuario recibirá una notificación de error de página cuyo uffd_msg.pagefault.flags tendrá el bit UFFD_PAGEFAULT_FLAG_WP establecido. Nota: dado que solo las escrituras pueden desencadenar este tipo de error, las notificaciones de protección contra escritura siempre tendrán el bit UFFD_PAGEFAULT_FLAG_WRITE establecido junto con el bit UFFD_PAGEFAULT_FLAG_WP.

Para resolver un error de página de protección contra escritura, el usuario debe iniciar otra operación ioctl(2) UFFDIO_WRITEPROTECT, cuyo uffd_msg.pagefault.flags debe tener el modo UFFDIO_WRITEPROTECT_MODE_WP desestablecido en la página o rango con error.

Userfaultfd modo de error menor (desde Linux 5.13)

Desde Linux 5.13, userfaultfd admite el modo de error menor. En este modo, los mensajes de error se generan no para errores mayores (donde faltaba la página), sino para errores menores, donde una página existe en la caché de páginas, pero las entradas de la tabla de páginas aún no están presentes. El usuario debe primero verificar la disponibilidad de esta característica utilizando la operación ioctl(2) UFFDIO_API con los bits de característica apropiados establecidos antes de usar esta característica: UFFD_FEATURE_MINOR_HUGETLBFS desde Linux 5.13, o UFFD_FEATURE_MINOR_SHMEM desde Linux 5.14.

Para registrarse en el modo de error menor de userfaultfd, el usuario debe iniciar la operación ioctl(2) UFFDIO_REGISTER con el modo UFFD_REGISTER_MODE_MINOR establecido.

Cuando ocurre un error menor, el espacio de usuario recibirá una notificación de error de página cuyo uffd_msg.pagefault.flags tendrá el bit UFFD_PAGEFAULT_FLAG_MINOR establecido.

Para resolver un error de página menor, el manejador debe decidir si el contenido de la página existente necesita ser modificado primero. Si es así, esto debe hacerse en el lugar a través de un segundo mapeo, no registrado por userfaultfd, a la misma página de respaldo (por ejemplo, mapeando el archivo shmem o hugetlbfs dos veces). Una vez que la página se considera "actualizada", el error puede resolverse iniciando una operación ioctl(2) UFFDIO_CONTINUE, que instala las entradas de la tabla de páginas y (por defecto) despierta al(los) hilo(s) que generó(aron) el error.

El modo de error menor solo admite memoria respaldada por hugetlbfs (desde Linux 5.13) y memoria respaldada por shmem (desde Linux 5.14).

Lectura desde la estructura userfaultfd

Cada read(2) desde el descriptor de archivo userfaultfd devuelve una o más estructuras uffd_msg, cada una de las cuales describe un evento de error de página o un evento requerido para el uso no cooperativo de userfaultfd:


struct uffd_msg {
    __u8  event;            /* Tipo de evento */
    ...
    union {
        struct {
            __u64 flags;    /* Banderas que describen el error */
            __u64 address;  /* Dirección del error */
            union {
                __u32 ptid; /* ID del hilo del error */
            } feat;
        } pagefault;
        struct {            /* Desde Linux 4.11 */
            __u32 ufd;      /* Descriptor de archivo de userfault
                               del proceso hijo */
        } fork;
        struct {            /* Desde Linux 4.11 */
            __u64 from;     /* Dirección antigua del área remapeada */
            __u64 to;       /* Nueva dirección del área remapeada */
            __u64 len;      /* Tamaño original del mapeo */
        } remap;
        struct {            /* Desde Linux 4.11 */
            __u64 start;    /* Dirección de inicio del área eliminada */
            __u64 end;      /* Dirección de fin del área eliminada */
        } remove;
        ...
    } arg;
    /* Campos de relleno omitidos */
} __packed;

Si hay varios eventos disponibles y el búfer proporcionado es lo suficientemente grande, read(2) devuelve tantos eventos como quepan en el búfer proporcionado. Si el búfer proporcionado a read(2) es más pequeño que el tamaño de la estructura uffd_msg, la operación read(2) falla con el error EINVAL.

Los campos establecidos en la estructura uffd_msg son los siguientes:

event
El tipo de evento. Dependiendo del tipo de evento, diferentes campos de la unión arg representan los detalles requeridos para el procesamiento del evento. Los eventos que no son de error de página se generan solo cuando la característica apropiada está habilitada durante el apretón de manos de la API con la operación ioctl(2) UFFDIO_API.
Los siguientes valores pueden aparecer en el campo event:
UFFD_EVENT_PAGEFAULT (desde Linux 4.3)
Un evento de error de página. Los detalles del error de página están disponibles en el campo pagefault.
UFFD_EVENT_FORK (desde Linux 4.11)
Generado cuando el proceso que genera el error invoca fork(2) (o clone(2) sin el flag CLONE_VM). Los detalles del evento están disponibles en el campo fork.
UFFD_EVENT_REMAP (desde Linux 4.11)
Generado cuando el proceso que genera el error invoca mremap(2). Los detalles del evento están disponibles en el campo remap.
UFFD_EVENT_REMOVE (desde Linux 4.11)
Generado cuando el proceso que genera el error invoca madvise(2) con consejo MADV_DONTNEED o MADV_REMOVE. Los detalles del evento están disponibles en el campo remove.
UFFD_EVENT_UNMAP (desde Linux 4.11)
Generado cuando el proceso que genera el error anula el mapeo de un rango de memoria, ya sea explícitamente usando munmap(2) o implícitamente durante mmap(2) o mremap(2). Los detalles del evento están disponibles en el campo remove.
pagefault.address
La dirección que activó el error de página.
pagefault.flags
Una máscara de bits de flags que describen el evento. Para UFFD_EVENT_PAGEFAULT, puede aparecer el siguiente flag:
UFFD_PAGEFAULT_FLAG_WP
Si este flag está establecido, entonces el error fue un error de protección contra escritura.
UFFD_PAGEFAULT_FLAG_MINOR
Si este flag está establecido, entonces el error fue un error menor.
UFFD_PAGEFAULT_FLAG_WRITE
Si este flag está establecido, entonces el error fue un error de escritura.

Si no están establecidos ni UFFD_PAGEFAULT_FLAG_WP ni UFFD_PAGEFAULT_FLAG_MINOR, entonces el error fue un error de página faltante.

pagefault.feat.pid
El ID del hilo que activó el error de página.
fork.ufd
El descriptor de archivo asociado con el objeto userfault creado para el hijo creado por fork(2).
remap.from
La dirección original del rango de memoria que fue remapeado usando mremap(2).
>
remap.to
La nueva dirección del rango de memoria que fue reasignado usando mremap(2).
remap.len
El tamaño original del rango de memoria que fue reasignado usando mremap(2).
remove.start
La dirección de inicio del rango de memoria que fue liberado usando madvise(2) o desmapeado
remove.end
La dirección de fin del rango de memoria que fue liberado usando madvise(2) o desmapeado

Una lectura(2) en un descriptor de archivo userfaultfd puede fallar con los siguientes errores:

EINVAL
El objeto userfaultfd aún no ha sido habilitado usando la operación UFFDIO_API de ioctl(2)

Si la bandera O_NONBLOCK está habilitada en la descripción de archivo asociada, el descriptor de archivo userfaultfd puede ser monitoreado con poll(2), select(2), y epoll(7). Cuando hay eventos disponibles, el descriptor de archivo se indica como legible. Si la bandera O_NONBLOCK no está habilitada, entonces poll(2) (siempre) indica el archivo como si tuviera una condición POLLERR, y select(2) indica el descriptor de archivo como legible y escribible.

VALOR DE RETORNO

En caso de éxito, userfaultfd() devuelve un nuevo descriptor de archivo que se refiere al objeto userfaultfd. En caso de error, se devuelve -1 y errno se establece para indicar el error.

ERRORES

EINVAL
Se especificó un valor no admitido en flags.
EMFILE
Se alcanzó el límite por proceso en la cantidad de descriptores de archivo abiertos.
ENFILE
Se alcanzó el límite a nivel de sistema de la cantidad total de archivos abiertos.
ENOMEM
No había suficiente memoria del kernel disponible.
EPERM (desde Linux 5.2)
El llamador no tiene privilegios (no tiene la capacidad CAP_SYS_PTRACE en el espacio de nombres de usuario inicial), y /proc/sys/vm/unprivileged_userfaultfd tiene el valor 0.

ESTANDARES

Linux.

HISTORIA

Linux 4.3.

El soporte para hugetlbfs y áreas de memoria compartida y eventos que no son de fallos de página se agregó en Linux 4.11.

NOTAS

El mecanismo userfaultfd puede usarse como una alternativa a las técnicas tradicionales de paginación en el espacio de usuario basadas en el uso de la señal SIGSEGV y mmap(2). También puede usarse para implementar la restauración perezosa para mecanismos de punto de control/restauración, así como la migración post-copia para permitir la ejecución (casi) ininterrumpida al transferir máquinas virtuales y contenedores de Linux de un host a otro.

ERRORES DE PROGRAMACIÓN

Si UFFD_FEATURE_EVENT_FORK está habilitado y una llamada al sistema de la familia fork(2) se interrumpe por una señal o falla, se puede crear un descriptor userfaultfd obsoleto. En este caso, se entregará un evento espurio UFFD_EVENT_FORK al monitor userfaultfd.

EJEMPLOS

El siguiente programa demuestra el uso del mecanismo userfaultfd. El programa crea dos hilos, uno de los cuales actúa como manejador de fallos de página para el proceso, para las páginas en una región de demanda de páginas cero creada usando mmap(2).

El programa toma un argumento de línea de comandos, que es el número de páginas que se crearán en un mapeo cuyos fallos de página se manejarán a través de userfaultfd. Después de crear un objeto userfaultfd, el programa crea un mapeo anónimo privado del tamaño especificado y registra el rango de direcciones de ese mapeo usando la operación UFFDIO_REGISTER de ioctl(2). Luego, el programa crea un segundo hilo que realizará la tarea de manejar los fallos de página.

El hilo principal recorre las páginas del mapeo, obteniendo bytes de páginas sucesivas. Dado que las páginas aún no se han accedido, el primer acceso a un byte en cada página activará un evento de fallo de página en el descriptor de archivo userfaultfd.

Cada uno de los eventos de fallo de página es manejado por el segundo hilo, que se queda en un bucle procesando la entrada del descriptor de archivo userfaultfd. En cada iteración del bucle, el segundo hilo primero llama a poll(2) para verificar el estado del descriptor de archivo y luego lee un evento del descriptor de archivo. Todos estos eventos deberían ser eventos UFFD_EVENT_PAGEFAULT, que el hilo maneja copiando una página de datos en la región de fallo usando la operación UFFDIO_COPY de ioctl(2).

#include <sys/mman.h>

#include <unistd.h>
static int page_size;
static void *
fault_handler_thread(void *arg)
{
    int                 nready;
    long                uffd;   /* descriptor de archivo userfaultfd */
    ssize_t             nread;
    struct pollfd       pollfd;
    struct uffdio_copy  uffdio_copy;
    static int      fault_cnt = 0; /* Número de fallos manejados hasta ahora */
    static char     *page = NULL;
    static struct uffd_msg  msg;  /* Datos leídos de userfaultfd */
    uffd = (long) arg;
    /* Crear una página que se copiará en la región de fallo.  */
    if (page == NULL) {
        page = mmap(NULL, page_size, PROT_READ | PROT_WRITE,
                    MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
        if (page == MAP_FAILED)
            err(EXIT_FAILURE, "mmap");
    }
    /* Bucle, manejando eventos entrantes en el descriptor de archivo userfaultfd.  */
    for (;;) {
        /* Ver qué nos dice poll() sobre el userfaultfd.  */
        pollfd.fd = uffd;
        pollfd.events = POLLIN;
        nready = poll(&pollfd, 1, -1);
        if (nready == -1)
            err(EXIT_FAILURE, "poll");
        printf("\nfault_handler_thread():\n");
        printf("    poll() devuelve: nready = %d; "
               "POLLIN = %d; POLLERR = %d\n", nready,
               (pollfd.revents & POLLIN) != 0,
               (pollfd.revents & POLLERR) != 0);
        /* Leer un evento del userfaultfd.  */
        nread = read(uffd, &msg, sizeof(msg));
        if (nread == 0) {
            printf("¡EOF en userfaultfd!\n");
            exit(EXIT_FAILURE);
        }
        if (nread == -1)
            err(EXIT_FAILURE, "read");
        /* Esperamos solo un tipo de evento; verificar esa suposición.  */
        if (msg.event != UFFD_EVENT_PAGEFAULT) {
            fprintf(stderr, "Evento inesperado en userfaultfd\n");
            exit(EXIT_FAILURE);
        }
        /* Mostrar información sobre el evento de fallo de página.  */
        printf("    Evento UFFD_EVENT_PAGEFAULT: ");
        printf("flags = %"PRIx64"; ", msg.arg.pagefault.flags);
        printf("dirección = %"PRIx64"\n", msg.arg.pagefault.address);
        /* Copiar la página apuntada por 'page' en la región de fallo.
           Variar el contenido que se copia, para que sea más obvio que cada fallo se maneja por separado.  */
        memset(page, 'A' + fault_cnt % 20, page_size);
        fault_cnt++;
        uffdio_copy.src = (unsigned long) page;
        /* ¡Necesitamos manejar los fallos de página en unidades de páginas!
           Por lo tanto, redondear la dirección del fallo hacia abajo al límite de página.  */
        uffdio_copy.dst = (unsigned long) msg.arg.pagefault.address &
                                           ~(page_size - 1);
        uffdio_copy.len = page_size;
        uffdio_copy.mode = 0;
        uffdio_copy.copy = 0;
        if (ioctl(uffd, UFFDIO_COPY, &uffdio_copy) == -1)
            err(EXIT_FAILURE, "ioctl-UFFDIO_COPY");
        printf("        (uffdio_copy.copy devolvió %"PRId64")\n",
               uffdio_copy.copy);
    }
}
int
main(int argc, char *argv[])
{
    int        s;
    char       c;
    char       *addr;   /* Inicio de la región manejada por userfaultfd */
    long       uffd;    /* descriptor de archivo userfaultfd */
    size_t     size, i;  /* Tamaño de la región manejada por userfaultfd */
    pthread_t  thr;     /* ID del hilo que maneja los fallos de página */
    struct uffdio_api       uffdio_api;
    struct uffdio_register  uffdio_register;
    if (argc != 2) {
        fprintf(stderr, "Uso: %s num-páginas\n", argv[0]);
        exit(EX
IT_FAILURE); } page_size = sysconf(_SC_PAGE_SIZE); size = strtoull(argv[1], NULL, 0) * page_size; /* Crea y habilita el objeto userfaultfd. */ uffd = syscall(SYS_userfaultfd, O_CLOEXEC | O_NONBLOCK); if (uffd == -1) err(EXIT_FAILURE, "userfaultfd"); /* NOTA: No se necesita handshake de características de dos pasos aquí, ya que este ejemplo no requiere ninguna característica específica. Los programas que *sí* lo hagan deben llamar a UFFDIO_API dos veces: una vez con `features = 0` para detectar las características admitidas por este kernel, y otra vez con el subconjunto de características que el programa realmente quiere habilitar. */ uffdio_api.api = UFFD_API; uffdio_api.features = 0; if (ioctl(uffd, UFFDIO_API, &uffdio_api) == -1) err(EXIT_FAILURE, "ioctl-UFFDIO_API"); /* Crea un mapeo anónimo privado. La memoria será mapeada bajo demanda con ceros; es decir, aún no se ha asignado. Cuando realmente toquemos la memoria, se asignará a través de userfaultfd. */ addr = mmap(NULL, size, PROT_READ | PROT_WRITE, MAP_PRIVATE | MAP_ANONYMOUS, -1, 0); if (addr == MAP_FAILED) err(EXIT_FAILURE, "mmap"); printf("Dirección devuelta por mmap() = %p\n", addr); /* Registra el rango de memoria del mapeo que acabamos de crear para su gestión por el objeto userfaultfd. En el modo, solicitamos rastrear las páginas faltantes (es decir, las páginas que aún no se han cargado). */ uffdio_register.range.start = (unsigned long) addr; uffdio_register.range.len = size; uffdio_register.mode = UFFDIO_REGISTER_MODE_MISSING; if (ioctl(uffd, UFFDIO_REGISTER, &uffdio_register) == -1) err(EXIT_FAILURE, "ioctl-UFFDIO_REGISTER"); /* Crea un hilo que procesará los eventos de userfaultfd. */ s = pthread_create(&thr, NULL, fault_handler_thread, (void *) uffd); if (s != 0) { errc(EXIT_FAILURE, s, "pthread_create"); } /* El hilo principal ahora toca la memoria en el mapeo, tocando ubicaciones separadas por 1024 bytes. Esto activará eventos de userfaultfd para todas las páginas de la región. */ i = 0xf; /* Asegúrate de que la dirección de fallo no esté en un límite de página, para probar que la manejamos correctamente en fault_handling_thread(). */ while (i < size) { c = addr[i]; printf("Leyendo la dirección %p en %s(): ", addr + i, __func__); printf("%c\n", c); i += 1024; usleep(100000); /* Ralentizamos un poco */ } exit(EXIT_SUCCESS); }
