NOMBRE

upsd.users - Definiciones de usuarios administrativos para el servidor de datos upsd de NUT

DESCRIPCIÓN

Comandos administrativos como el establecimiento de variables y los comandos instantáneos son potentes, y el acceso a ellos debe ser restringido. Este archivo define quién puede acceder a ellos y qué está disponible.

NOTAS IMPORTANTES

•El contenido de este archivo debe ser ASCII puro (los códigos de caracteres que no estén en el rango se ignorarán con un mensaje de advertencia).
•Equilibre los permisos del usuario en tiempo de ejecución para acceder al archivo (y quizás al directorio en el que se encuentra) para que solo upsd pueda leerlo; no se necesita acceso de escritura. Es común usar chown root:nut y chmod 640 para establecer permisos de archivo aceptables.
•Los paquetes (y las recetas de compilación) suelen preparar un conjunto de cuentas de usuario y grupo para NUT. Las compilaciones personalizadas con una configuración mínima podrían incluso usar nobody:nogroup o similar, lo que es inherentemente inseguro.
•En sistemas con preocupaciones de seguridad adicionales, los controladores NUT y el servidor de datos deben ejecutarse como cuentas de usuario separadas que serían miembros de un mismo grupo para el acceso compartido a los archivos de socket Unix locales y al directorio en el que se encuentran, pero de diferentes grupos para el acceso a los archivos de configuración. Esto requeriría que algunos demonios utilicen configuraciones personalizadas de usuario, grupo, RUN_AS_USER y/o RUN_AS_GROUP para anular el único valor integrado.
•Tenga en cuenta que los clientes de monitoreo, registro, etc. son solo de red. No necesitan acceso a estos archivos y directorios, y pueden ejecutarse como un usuario y grupo independientes en general.
•Tenga en cuenta la seguridad de las copias de seguridad de este archivo, por ejemplo, los archivos de archivo en los que pueda terminar.

SECCIONES

Cada usuario recibe su propia sección. Los campos de esa sección establecen los parámetros asociados con los privilegios de ese usuario. La sección comienza con el nombre del usuario entre corchetes y continúa hasta el siguiente nombre de usuario entre corchetes o el final del archivo (EOF). Estos usuarios son independientes de /etc/passwd u otras bases de datos de cuentas del sistema operativo.

Aquí hay algunos ejemplos para empezar:

[admin]
        password = mipass
        actions = set
        actions = fsd
        instcmds = all
[pfy]
        password = duh
        instcmds = test.panel.start
        instcmds = test.panel.stop
[upswired]
        password = blah
        upsmon primary
[observer]
        password = abcd
        upsmon secondary

CAMPOS

password

Establece la contraseña para este usuario.

actions

Permite al usuario realizar ciertas acciones con upsd. Para especificar varias acciones, use varias instancias del campo actions. Las acciones válidas son:

SET

cambiar el valor de ciertas variables en el UPS

FSD

establecer la bandera de apagado forzado en el UPS. Esto es equivalente a una situación de "en batería + batería baja" a efectos de monitoreo.

Se espera que la lista de acciones crezca en el futuro.

instcmds

Permite a un usuario iniciar comandos instantáneos específicos. Use "ALL" para otorgar todos los comandos automáticamente. Para especificar varios comandos, use varias instancias del campo instcmds. Para obtener la lista completa de lo que su UPS admite, use upscmd -l.

El archivo cmdvartab suministrado con la distribución NUT contiene una lista de la mayoría de los nombres de comandos generalmente conocidos.

upsmon

Agrega las acciones necesarias para un proceso upsmon y puede ser visto como un rol de una instancia de cliente particular para trabajar con esta instancia de servidor de datos. Esto se establece en primary (puede solicitar FSD) o secondary (sigue situaciones críticas para apagar cuando sea necesario).

No intente asignar acciones a upsmon manualmente, ya que podría omitir algo importante. Este método de designación de un "usuario upsmon" se creó para que las capacidades internas pudieran cambiarse en el futuro sin romper las instalaciones existentes (utilizando potencialmente acciones que no están expuestas para asignación directa).
