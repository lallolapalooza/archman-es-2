getrlimit(2) Manual de llamadas al sistema getrlimit(2)

NOMBRE

getrlimit, setrlimit, prlimit - obtener/establecer límites de recursos

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

SINOPSIS

#include <sys/resource.h>
int getrlimit(int resource, struct rlimit *rlim);
int setrlimit(int resource, const struct rlimit *rlim);
int prlimit(pid_t pid, int resource,
            const struct rlimit *_Nullable new_limit,
            struct rlimit *_Nullable old_limit);
struct rlimit {
    rlim_t  rlim_cur;  /* Límite blando */
    rlim_t  rlim_max;  /* Límite duro (techo para rlim_cur) */
};
typedef /* ... */  rlim_t;  /* Tipo entero sin signo */

DESCRIPCIÓN

Las llamadas al sistema getrlimit() y setrlimit() obtienen y establecen límites de recursos. Cada recurso tiene un límite blando y uno duro asociado, según se define en la estructura rlimit.

El límite blando es el valor que el kernel aplica para el recurso correspondiente. El límite duro actúa como un techo para el límite blando: un proceso no privilegiado solo puede establecer su límite blando a un valor en el rango de 0 hasta el límite duro y (de forma irreversible) disminuir su límite duro. Un proceso privilegiado (en Linux: uno con la capacidad CAP_SYS_RESOURCE en el espacio de nombres de usuario inicial) puede realizar cambios arbitrarios en cualquiera de los valores límite.

El valor RLIM_INFINITY denota que no hay límite en un recurso (tanto en la estructura devuelta por getrlimit() como en la estructura pasada a setrlimit()).

El argumento resource debe ser uno de:

RLIMIT_AS
Este es el tamaño máximo de la memoria virtual del proceso (espacio de direcciones). El límite se especifica en bytes y se redondea hacia abajo al tamaño de página del sistema. Este límite afecta a las llamadas a brk(2), mmap(2) y mremap(2), que fallan con el error ENOMEM al superar este límite. Además, la expansión automática de la pila falla (y genera una señal SIGSEGV que mata al proceso si no se ha proporcionado una pila alternativa mediante sigaltstack(2)). Dado que el valor es un long, en máquinas con un long de 32 bits, este límite es como máximo de 2 GiB, o este recurso es ilimitado.
RLIMIT_CORE
Este es el tamaño máximo de un archivo de core (ver core(5)) en bytes que el proceso puede volcar. Cuando es 0, no se crean archivos de volcado de núcleo. Cuando es distinto de cero, los volcados más grandes se truncan a este tamaño.
RLIMIT_CPU
Este es un límite, en segundos, de la cantidad de tiempo de CPU que el proceso puede consumir. Cuando el proceso alcanza el límite blando, se le envía una señal SIGXCPU. La acción predeterminada para esta señal es terminar el proceso. Sin embargo, la señal puede ser capturada y el manejador puede devolver el control al programa principal. Si el proceso continúa consumiendo tiempo de CPU, se le enviará SIGXCPU una vez por segundo hasta que se alcance el límite duro, momento en el cual se le enviará SIGKILL. (Este último punto describe el comportamiento de Linux. Las implementaciones varían en cómo tratan a los procesos que continúan consumiendo tiempo de CPU después de alcanzar el límite blando. Las aplicaciones portátiles que necesitan capturar esta señal deben realizar una terminación ordenada al recibir SIGXCPU por primera vez).
RLIMIT_DATA
Este es el tamaño máximo del segmento de datos del proceso (datos inicializados, datos no inicializados y heap). El límite se especifica en bytes y se redondea hacia abajo al tamaño de página del sistema. Este límite afecta a las llamadas a brk(2), sbrk(2) y (desde Linux 4.7) mmap(2), que fallan con el error ENOMEM al encontrar el límite blando de este recurso.
RLIMIT_FSIZE
Este es el tamaño máximo en bytes de los archivos que el proceso puede crear. Los intentos de extender un archivo más allá de este límite dan como resultado la entrega de una señal SIGXFSZ. Por defecto, esta señal termina un proceso, pero un proceso puede capturar esta señal en su lugar, en cuyo caso la llamada al sistema relevante (por ejemplo, write(2), truncate(2)) falla con el error EFBIG.
RLIMIT_LOCKS (Linux 2.4.0 a Linux 2.4.24)
Este es un límite en la cantidad combinada de bloqueos de flock(2) y arrendamientos de fcntl(2) que este proceso puede establecer.
RLIMIT_MEMLOCK
Este es el número máximo de bytes de memoria que pueden fijarse en la RAM. Este límite se redondea hacia abajo al múltiplo más cercano del tamaño de página del sistema. Este límite afecta a mlock(2), mlockall(2) y a la operación MAP_LOCKED de mmap(2). Desde Linux 2.6.9, también afecta a la operación SHM_LOCK de shmctl(2), donde establece un máximo de bytes totales en segmentos de memoria compartida (ver shmget(2)) que pueden ser bloqueados por el ID de usuario real del proceso que llama. Los bloqueos de shmctl(2) SHM_LOCK se contabilizan por separado de los bloqueos de memoria por proceso establecidos por mlock(2), mlockall(2) y mmap(2) MAP_LOCKED; un proceso puede bloquear bytes hasta este límite en cada una de estas dos categorías.
Antes de Linux 2.6.9, este límite controlaba la cantidad de memoria que podía ser bloqueada por un proceso privilegiado. Desde Linux 2.6.9, no se imponen límites a la cantidad de memoria que un proceso privilegiado puede bloquear, y este límite rige en su lugar la cantidad de memoria que un proceso no privilegiado puede bloquear.
RLIMIT_MSGQUEUE (desde Linux 2.6.8)
Este es un límite en el número de bytes que se pueden asignar para colas de mensajes POSIX para el ID de usuario real del proceso que llama. Este límite se aplica a mq_open(3). Cada cola de mensajes que el usuario crea cuenta (hasta que se elimina) contra este límite según la fórmula:
Desde Linux 3.5:

bytes = attr.mq_maxmsg * sizeof(struct msg_msg) +
        MIN(attr.mq_maxmsg, MQ_PRIO_MAX) *
              sizeof(struct posix_msg_tree_node)+
                        /* Para sobrecarga */
        attr.mq_maxmsg * attr.mq_msgsize;
                        /* Para datos del mensaje */

Linux 3.4 y anteriores:

bytes = attr.mq_maxmsg * sizeof(struct msg_msg *) +
                        /* Para sobrecarga */
        attr.mq_maxmsg * attr.mq_msgsize;
                        /* Para datos del mensaje */

donde attr es la estructura mq_attr especificada como cuarto argumento a mq_open(3), y las estructuras msg_msg y posix_msg_tree_node son estructuras internas del kernel.
El sumando de "sobrecarga" en la fórmula tiene en cuenta los bytes de sobrecarga requeridos por la implementación y asegura que el usuario no pueda crear un número ilimitado de mensajes de longitud cero (tales mensajes, sin embargo, consumen algo de memoria del sistema para la sobrecarga de gestión).

RLIMIT_DATA

This is the maximum size of the process's data segment (the process heap), in bytes. This limit affects the expansion of the heap done by calls like brk(2) or sbrk(2).
RLIMIT_FSIZE
This is the maximum size to which a file may be written by the process. Attempts to extend a file beyond this limit result in a SIGXFSZ signal being sent to the process. If the process catches or ignores this signal, the write operation that would have exceeded the limit returns -1 with errno set to EFBIG.
RLIMIT_LOCKS (since Linux 2.4)
This is a limit on the number of file locks (see fcntl(2)) that the calling process may hold. The value is a count of lock structures. When the limit is reached, fcntl(2) calls to place new locks fail with the error ENFILE.
RLIMIT_MEMLOCK (since Linux 2.4)
This specifies the maximum number of bytes of memory that may be locked into RAM by the process. This limit applies to the use of the mlock(2) and mlockall(2) system calls. The limit is expressed in units of pages. The effective limit is approximately this value multiplied by the system's page size (see getpagesize(2)).
RLIMIT_MSGQUEUE (since Linux 2.6.8)
This specifies the limit on the number of bytes that can be allocated for any real-time message queue (see mq_overview(7)). The value is expressed in bytes.
RLIMIT_NICE (since Linux 2.6.22)
This specifies a ceiling on the value that the process may set for its own nice level using nice(2) or setpriority(2). Only the superuser can raise the nice level (lower the nice value). The limit is applied to the nice value specified in the call, so if the current nice level is 10, and the limit is 20, the process can only set its nice level to values between 10 and 20 inclusive. The range for this limit is thus from 1 (corresponding to a nice value of 19) to 40 (corresponding to a nice value of -20). This unusual choice of range was necessary because negative numbers cannot be specified as resource limit values, since they typically have special meanings. For example, RLIM_INFINITY typically is the same as -1. For more detail on the nice value, see sched(7).
RLIMIT_NOFILE
This specifies a value one greater than the maximum file descriptor number that can be opened by this process. Attempts (open(2), pipe(2), dup(2), etc.) to exceed this limit yield the error EMFILE. (Historically, this limit was named RLIMIT_OFILE on BSD.)
Since Linux 4.5, this limit also defines the maximum number of file descriptors that an unprivileged process (one without the CAP_SYS_RESOURCE capability) may have "in flight" to other processes, by being passed across UNIX domain sockets. This limit applies to the sendmsg(2) system call. For further details, see unix(7).
RLIMIT_NPROC
This is a limit on the number of extant process (or, more precisely on Linux, threads) for the real user ID of the calling process. So long as the current number of processes belonging to this process's real user ID is greater than or equal to this limit, fork(2) fails with the error EAGAIN.
The RLIMIT_NPROC limit is not enforced for processes that have either the CAP_SYS_ADMIN or the CAP_SYS_RESOURCE capability, or run with real user ID 0.
RLIMIT_RSS
This is a limit (in bytes) on the process's resident set (the number of virtual pages resident in RAM). This limit has effect only in Linux 2.4.x, x < 30, and there affects only calls to madvise(2) specifying MADV_WILLNEED.
RLIMIT_RTPRIO (since Linux 2.6.12, but see BUGS)
This specifies a ceiling on the real-time priority that may be set for this process using sched_setscheduler(2) and sched_setparam(2).
For further details on real-time scheduling policies, see sched(7)
RLIMIT_RTTIME (since Linux 2.6.25)
This is a limit (in microseconds) on the amount of CPU time that a process scheduled under a real-time scheduling policy may consume without making a blocking system call. For the purpose of this limit, each time a process makes a blocking system call, the count of its consumed CPU time is reset to zero. The CPU time count is not reset if the process continues trying to use the CPU but is preempted, its time slice expires, or it calls sched_yield(2).
Upon reaching the soft limit, the process is sent a SIGXCPU signal. If the process catches or ignores this signal and continues consuming CPU time, then SIGXCPU will be generated once each second until the hard limit is reached, at which point the process is sent a SIGKILL signal.
The intended use of this limit is to stop a runaway real-time process from locking up the system.
For further details on real-time scheduling policies, see sched(7)
RLIMIT_SIGPENDING (since Linux 2.6.8)
This is a limit on the number of signals that may be queued for the real user ID of the calling process. Both standard and real-time signals are counted for the purpose of checking this limit. However, the limit is enforced only for sigqueue(3); it is always possible to use kill(2) to queue one instance of any of the signals that are not already queued to the process.
RLIMIT_STACK
This is the maximum size of the process stack, in bytes. Upon reaching this limit, a SIGSEGV signal is generated. To handle this signal, a process must employ an alternate signal stack (sigaltstack(2)).
Since Linux 2.6.23, this limit also determines the amount of space used for the process's command-line arguments and environment variables; for details, see execve(2).

prlimit()

The Linux-specific prlimit() system call combines and extends the functionality of setrlimit() and getrlimit(). It can be used to both set and get the resource limits of an arbitrary process.

The resource argument has the same meaning as for setrlimit() and getrlimit().

If the new_limit argument is not NULL, then the rlimit structure to which it points is used to set new values for the soft and hard limits for resource. If the old_limit argument is not NULL, then a successful call to prlimit() places the previous soft and hard limits for resource in the rlimit structure pointed to by old_limit.

The pid argument specifies the ID of the process on which the call is to operate. If pid is 0, then the call applies to the calling process. To set or get the resources of a process other than itself, the caller must have the CAP_SYS_RESOURCE capability in the user namespace of the process whose resource limits are being changed, or the real, effective, and saved user IDs of the target process must match the real user ID of the caller and the real, effective, and saved set group IDs of the target process must match the real group ID of the caller.

RETURN VALUE

On success, these system calls return 0. On error, -1 is returned, and errno is set to indicate the error.

ERRORS

EFAULT
A pointer argument points to a location outside the accessible address space.
EINVAL
The value specified in resource is not valid; or, for setrlimit() or prlimit(): rlim->rlim_cur was greater than rlim->rlim_max.
EPERM
An unprivileged process tried to raise the hard limit; the CAP_SYS_RESOURCE capability is required to do this.
EPERM
The caller tried to increase the hard RLIMIT_NOFILE limit above the maximum defined by /proc/sys/fs/nr_open (see proc(5))
EPERM
(prlimit()) The calling process did not have permission to set limits for the process specified by pid.
ESRCH
Could not find a process with the ID specified in pid.

NOTES

A child process created via fork(2) inherits its parent's resource limits. Resource limits are preserved across execve(2).

Resource limits are per-process attributes that are shared by all of the threads in a process.

Lowering the soft limit for a resource below the process's current consumption of that resource will succeed (but will prevent the process from further increasing its consumption of the resource).

One can set the resource limits of the shell using the built-in ulimit command (limit in csh(1)). The shell's resource limits are inherited by the processes that it creates to execute commands.

Since Linux 2.6.24, the resource limits of any process can be inspected via /proc/pid/limits; see proc(5).

Ancient systems provided a vlimit() function with a similar purpose to setrlimit(). For backward compatibility, glib

c también proporciona vlimit(). Todas las aplicaciones nuevas deben escribirse utilizando setrlimit().

Diferencias entre la biblioteca C y la ABI del kernel

Desde glibc 2.13, las funciones de envoltura de glibc getrlimit() y setrlimit() ya no invocan las llamadas al sistema correspondientes, sino que emplean prlimit(), por las razones descritas en BUGS.

El nombre de la función de envoltura de glibc es prlimit(); la llamada al sistema subyacente es prlimit64().

BUGS

En los kernels de Linux más antiguos, las señales SIGXCPU y SIGKILL enviadas cuando un proceso encontraba los límites blandos y duros de RLIMIT_CPU se enviaban un segundo (de CPU) más tarde de lo que debían. Esto se corrigió en Linux 2.6.8.

En los kernels de Linux 2.6.x anteriores a Linux 2.6.17, un límite de RLIMIT_CPU de 0 se trata erróneamente como "sin límite" (como RLIM_INFINITY). Desde Linux 2.6.17, establecer un límite de 0 tiene efecto, pero se trata como un límite de 1 segundo.

Un error del kernel significa que RLIMIT_RTPRIO no funciona en Linux 2.6.12; el problema está corregido en Linux 2.6.13.

En Linux 2.6.12, hubo una desalineación de un dígito entre los rangos de prioridad devueltos por getpriority(2) y RLIMIT_NICE. Esto tuvo el efecto de que el límite real para el valor nice se calculaba como 19 - rlim_cur. Esto se corrigió en Linux 2.6.13.

Desde Linux 2.6.12, si un proceso alcanza su límite blando de RLIMIT_CPU y tiene un manejador instalado para SIGXCPU, entonces, además de invocar al manejador de señales, el kernel aumenta el límite blando en un segundo. Este comportamiento se repite si el proceso continúa consumiendo tiempo de CPU, hasta que se alcanza el límite duro, momento en el cual el proceso es terminado. Otras implementaciones no cambian el límite blando de RLIMIT_CPU de esta manera, y el comportamiento de Linux probablemente no sea conforme a los estándares; las aplicaciones portátiles deben evitar depender de este comportamiento específico de Linux. El límite específico de Linux RLIMIT_RTTIME exhibe el mismo comportamiento cuando se encuentra el límite blando.

Los kernels anteriores a Linux 2.4.22 no diagnosticaban el error EINVAL para setrlimit() cuando rlim->rlim_cur era mayor que rlim->rlim_max.

Linux no devuelve un error cuando un intento de establecer RLIMIT_CPU ha fallado, por razones de compatibilidad.

Representación de valores de límites de recursos "grandes" en plataformas de 32 bits

Las funciones de envoltura de glibc getrlimit() y setrlimit() utilizan un tipo de datos rlim_t de 64 bits, incluso en plataformas de 32 bits. Sin embargo, el tipo de datos rlim_t utilizado en las llamadas al sistema getrlimit() y setrlimit() es un unsigned long (de 32 bits). Además, en Linux, el kernel representa los límites de recursos en plataformas de 32 bits como unsigned long. Sin embargo, un tipo de datos de 32 bits no es lo suficientemente amplio. El límite más relevante aquí es RLIMIT_FSIZE, que especifica el tamaño máximo al que puede crecer un archivo: para ser útil, este límite debe representarse utilizando un tipo tan amplio como el tipo utilizado para representar los desplazamientos de archivo, es decir, tan amplio como un off_t de 64 bits (suponiendo un programa compilado con _FILE_OFFSET_BITS=64).

Para solucionar esta limitación del kernel, si un programa intentaba establecer un límite de recursos a un valor mayor que el que se podía representar en un unsigned long de 32 bits, la función de envoltura setrlimit() de glibc convertía silenciosamente el valor del límite a RLIM_INFINITY. En otras palabras, la configuración solicitada del límite de recursos se ignoraba silenciosamente.

Desde glibc 2.13, glibc soluciona las limitaciones de las llamadas al sistema getrlimit() y setrlimit() implementando setrlimit() y getrlimit() como funciones de envoltura que llaman a prlimit().

EJEMPLOS

El siguiente programa demuestra el uso de prlimit().

#define _GNU_SOURCE
#define _FILE_OFFSET_BITS 64
#include <err.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/resource.h>
#include <time.h>
int
main(int argc, char *argv[])
{
    pid_t          pid;
    struct rlimit  old, new;
    struct rlimit  *newp;
    if (!(argc == 2 || argc == 4)) {
        fprintf(stderr, "Uso: %s <pid> [<límite-blando-nuevo> "
                "<límite-duro-nuevo>]\n", argv[0]);
        exit(EXIT_FAILURE);
    }
    pid = atoi(argv[1]);        /* PID del proceso objetivo */
    newp = NULL;
    if (argc == 4) {
        new.rlim_cur = atoi(argv[2]);
        new.rlim_max = atoi(argv[3]);
        newp = &new;
    }
    /* Establecer el límite de tiempo de CPU del proceso objetivo; recuperar y mostrar
       el límite anterior */
    if (prlimit(pid, RLIMIT_CPU, newp, &old) == -1)
        err(EXIT_FAILURE, "prlimit-1");
    printf("Límites anteriores: blando=%jd; duro=%jd\n",
           (intmax_t) old.rlim_cur, (intmax_t) old.rlim_max);
    /* Recuperar y mostrar el nuevo límite de tiempo de CPU */
    if (prlimit(pid, RLIMIT_CPU, NULL, &old) == -1)
        err(EXIT_FAILURE, "prlimit-2");
    printf("Nuevos límites: blando=%jd; duro=%jd\n",
           (intmax_t) old.rlim_cur, (intmax_t) old.rlim_max);
    exit(EXIT_SUCCESS);
}
