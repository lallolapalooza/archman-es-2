NOMBRE

usbguard-rules.conf - Archivo de conjunto de reglas de USBGuard.

DESCRIPCIÓN

El archivo usbguard-rules.conf es cargado por el demonio USBGuard después de analizar el archivo de configuración principal, usbguard-daemon.conf(5). El demonio espera que el archivo contenga reglas escritas en un lenguaje que se describe en la sección Lenguaje de Reglas a continuación.

LENGUAJE DE REGLAS

El demonio USBGuard decide qué dispositivo USB autorizar basándose en una política definida por un conjunto de reglas. Cuando se inserta un dispositivo USB en el sistema, el demonio escanea las reglas existentes secuencialmente. Si se encuentra una regla coincidente, esta autoriza (allow), bloquea (block) o rechaza (reject) el dispositivo, en base al objetivo de la regla. Si no se encuentra ninguna regla coincidente, la decisión se basa en un objetivo predeterminado implícito. Este predeterminado implícito es bloquear el dispositivo hasta que el usuario tome una decisión. La gramática del lenguaje de reglas, expresada en una sintaxis similar a BNF, es la siguiente:

    rule ::= target attributes.
    target ::= "allow" | "block" | "reject".
    attributes ::= attributes | attribute.
    attributes ::= .

Los atributos de la regla especifican qué dispositivos coincidir o qué condición debe cumplirse para que la regla sea aplicable. Consulte la sección Especificación de Dispositivos para ver la lista de atributos disponibles y Condiciones para la lista de condiciones de regla soportadas.

Objetivos

El objetivo de una regla especifica si el dispositivo será autorizado para su uso o no. Se reconocen tres tipos de objetivos:

•allow - Autoriza el dispositivo. El dispositivo y sus interfaces podrán comunicarse con el sistema.
•block - Desautoriza el dispositivo. El dispositivo permanecerá en estado bloqueado hasta que sea autorizado.
•reject - Desautoriza y elimina el dispositivo del sistema. El dispositivo tendrá que ser reinsertado para volver a ser visible por el sistema.

Especificación de Dispositivo

Excepto el objetivo, todos los demás campos de una regla son opcionales. Una regla donde solo se especifica el objetivo coincidirá con cualquier dispositivo. Eso permite al administrador de políticas escribir un objetivo predeterminado explícito. Si ninguna regla de la política es aplicable al dispositivo, se utilizará un objetivo implícito configurado en usbguard-daemon.conf(5). Sin embargo, si se desea acotar la aplicabilidad de una regla a un conjunto de dispositivos o a un solo dispositivo, es posible hacerlo con atributos de dispositivo y condiciones de regla.

Atributos de Dispositivo

Los atributos de dispositivo son valores específicos leídos del dispositivo USB después de que se inserta en el sistema. Qué atributos están disponibles se define a continuación. Algunos de los atributos son derivados y otros se basan en atributos leídos directamente del dispositivo. Todos los atributos soportan dos formas:

•un valor con la sintaxis: 
    nombre valor
•múltiples valores con la sintaxis: 
    nombre [operador] { valor1 valor2 ... }

donde el operador opcional es uno de:

all-of

El conjunto de atributos del dispositivo debe contener todos los valores especificados para que la regla coincida.

one-of

El conjunto de atributos del dispositivo debe contener al menos uno de los valores especificados para que la regla coincida.

none-of

El conjunto de atributos del dispositivo no debe contener ninguno de los valores especificados para que la regla coincida.

equals

El conjunto de atributos del dispositivo debe contener exactamente el mismo conjunto de valores para que la regla coincida.

equals-ordered

El conjunto de atributos del dispositivo debe contener exactamente el mismo conjunto de valores en el mismo orden para que la regla coincida.

match-all

El conjunto de atributos del dispositivo debe ser un subconjunto de los valores especificados para que la regla coincida.

Si no se especifica el operador, se establece en equals.

Lista de atributos:

id usb-device-id

Coincide con un ID de dispositivo USB.

id [operador] { usb-device-id ... }

Coincide con un conjunto de IDs de dispositivo USB.

hash "valor"

Coincide con un hash calculado a partir de los valores de atributos del dispositivo y los datos del descriptor USB. USBGuard calcula el hash para cada dispositivo.

hash [operador] { "valor" ... }

Coincide con un conjunto de hashes de dispositivo.

parent-hash "valor"

Coincide con un hash del dispositivo padre.

parent-hash [operador] { "valor" ... }

Coincide con un conjunto de hashes de dispositivo padre.

name "nombre-dispositivo"

Coincide con el atributo de nombre del dispositivo USB.

name [operador] { "nombre-dispositivo" ... }

Coincide con un conjunto de nombres de dispositivos USB.

serial "numero-de-serie"

Coincide con el atributo iSerial del dispositivo USB.

serial [operador] { "numero-de-serie" ... }

Coincide con un conjunto de atributos iSerial de dispositivos USB.

via-port "id-puerto"

Coincide con el puerto USB a través del cual está conectado el dispositivo. Tenga en cuenta que algunos sistemas tienen una numeración de puertos inestable. El puerto puede cambiar después de que el sistema se reinicie o cuando se recargan ciertos módulos del kernel. Utilice el atributo parent-hash si desea asegurarse de que un dispositivo esté conectado a través de un dispositivo padre específico.

via-port [operador] { "id-puerto" ... }

Coincide con un conjunto de puertos USB.

with-interface tipo-interfaz

Coincide con un tipo de interfaz que proporciona el dispositivo USB.

with-interface [operador] { tipo-interfaz ... }

Coincide con un conjunto de tipos de interfaz contra el conjunto de interfaces que proporciona el dispositivo USB.

with-connect-type "tipo-conexión"

Coincide con el atributo de dispositivo de puerto USB/tipo_conexión.

with-connect-type [operador] { "tipo-conexión" ... }

Coincide con un conjunto de atributos de puerto USB/tipo_conexión.

label "etiqueta"

Asocia una cadena arbitraria con una regla. La etiqueta es útil para almacenar información contextual sobre la regla o para filtrar reglas por etiqueta. Este atributo no se utiliza al probar si una regla se aplica a un dispositivo.

El usb-device-id es un par delimitado por dos puntos en forma de vendor_id:product_id. Todos los dispositivos USB tienen este ID asignado por el fabricante y debe identificar de forma única un tipo de producto USB. Tanto vendor_id como product_id son números de 16 bits representados en base hexadecimal. Es posible utilizar un asterisco para hacer coincidir cualquier ID de dispositivo *:* o cualquier ID de producto de un proveedor específico, por ejemplo, 1234:*.

El valor del id-puerto es una identificación del puerto USB específica de la plataforma. En Linux tiene la forma de "usbN" en caso de un controlador USB (más precisamente un "hub raíz") o "bus-puerto[.puerto[.puerto ...]]" (por ejemplo, 1-2, 1-2.1, ...) en caso de un dispositivo USB.

El tipo-interfaz representa una interfaz USB y debe tener el formato de tres números de 8 bits en base hexadecimal delimitados por un carácter de dos puntos, es decir, cc:ss:pp. Los números representan la clase (cc), subclase (ss) y protocolo (pp) de la interfaz asignados por la USB-IF. Consulte la lista de clases, subclases y protocolos asignados para obtener más detalles. En lugar del número de subclase y protocolo, puede escribir un asterisco (*) para hacer coincidir todas las subclases o protocolos. No se permite la coincidencia de una clase específica y un protocolo específico, es decir, si utiliza un asterisco como número de subclase, también debe utilizar un asterisco para el protocolo.

NAME

usbguard-rules.conf — USBGuard rule set

DESCRIPTION

The file usbguard-rules.conf is the main configuration file for the usbguard-daemon. It contains a list of rules that define the USB device policy for the system. Rules are evaluated in the order they appear in the file. The first rule that matches a device determines the action (allow or reject) for that device. If no rule matches, the device is rejected by default.

A rule consists of an action (allow or reject) and an optional condition. If no condition is specified, the rule matches all devices.

The general syntax for a rule is:

     <action> [rule condition]

Where <action> is either allow or reject. A rule condition is a boolean expression that evaluates to true or false.

The usbguard-daemon evaluates the rules in order and applies the action of the first rule that matches the device. If a device does not match any rule, it is rejected by default.

Rule conditions

A rule condition is evaluated for a given device and can be composed of multiple simple conditions combined with logical operators. A rule condition evaluates to true if the device matches the condition, and false otherwise.

If a rule condition evaluates to true, the action of the rule is applied. Otherwise, the rule evaluation continues with the next rule. A rule conditions has the following syntax:

     if [!]condition
     if [operator] { [!]conditionA [!]conditionB ... }

Optionally, an exclamation mark (!) can be used to negate the result of a condition.

Interpretation of the set operator:

all-of

Evaluate to true if all of the specified conditions evaluated to true.

one-of

Evaluate to true if one of the specified conditions evaluated to true.

none-of

Evaluate to true if none of the specified conditions evaluated to true.

equals

Same as all-of.

equals-ordered

Same as all-of.

List of conditions:

localtime(time_range)

Evaluates to true if the local time is in the specified time range. time_range can be written either as HH:MM[:SS] or HH:MM[:SS]-HH:MM[:SS].

allowed-matches(query)

Evaluates to true if an allowed device matches the specified query. The query uses the rule syntax. Conditions in the query are not evaluated.

rule-applied

Evaluates to true if the rule currently being evaluated ever matched a device.

rule-applied(past_duration)

Evaluates to true if the rule currently being evaluated matched a device in the past duration of time specified by the parameter. past_duration can be written as HH:MM:SS, HH:MM, or SS.

rule-evaluated

Evaluates to true if the rule currently being evaluated was ever evaluated before.

rule-evaluated(past_duration)

Evaluates to true if the rule currently being evaluated was evaluated in the pas duration of time specified by the parameter. past_duration can be written as HH:MM:SS, HH:MM, or SS.

random

Evaluates to true/false with a probability of p(true)=0.5.

random(p_true)

Evaluates to true with the specified probability p(true)=p_true.

true

Evaluates always to true.

false

Evaluates always to false.

Partial rule

Partial rule is a rule without a rule target. Partial rules may by used by some commands of usbguard CLI tool.

Comments

In order to easily understand the meaning of each rule, comments can be used. Everything after the "#" character is ignored by the rule parser.

INITIAL POLICY

Using the usbguard CLI tool and its generate-policy subcommand, you can generate an initial policy for your system instead of writing one from scratch. The tool generates an allow policy for all devices connected to the system at the time of execution. It has several options to tweak the resulting policy, see usbguard(1) for further details.

The policy will be printed out on the standard output. It’s a good idea to review the generated rules before using them on a system. The typical workflow for generating an initial policy could look like this:

    $ sudo usbguard generate-policy > rules.conf
    $ vi rules.conf
    (review/modify the rule set)
    $ sudo install -m 0600 -o root -g root rules.conf /etc/usbguard/rules.conf
    $ sudo systemctl restart usbguard

EXAMPLE POLICIES

The following examples show what to put into the rules.conf file in order to implement the given policy.

1.Allow USB mass storage devices (USB flash disks) and block everything else

This policy will block any device that isn’t just a mass storage device. Devices with a hidden keyboard interface in a USB flash disk will be blocked. Only devices with a single mass storage interface will be allowed to interact with the operating system. The policy consists of a single rule:

    allow with-interface equals { 08:*:* }

The blocking is implicit in this case because we didn’t write a block rule. Implicit blocking is useful to desktop users. A desktop applet listening to USBGuard events can ask the user for a decision if an implicit target was applied.

2.Allow a specific Yubikey device to be connected via a specific port (and reject everything else on that port) 
    allow 1050:0011 name "Yubico Yubikey II" serial "0001234567" via-port "1-2" hash "044b5e168d40ee0245478416caf3d998"
    reject via-port "1-2"

We could use just the hash to match the device. However, using the name and serial attributes provide an useful hint for later inspection of the policy. On the other hand, the hash is the most specific value we can use to identify a device. It’s the best attribute to use if you want a rule to match just one device.

3.Reject devices with suspicious combination of interfaces

A USB flash disk which implements a keyboard or a network interface is very suspicious. The following set of rules forms a policy that allows USB flash disks and explicitly rejects devices with an additional and suspicious (as defined before) interface.

    allow with-interface equals { 08:*:* }
    reject with-interface all-of { 08:*:* 03:00:* }
    reject with-interface all-of { 08:*:* 03:01:* }
    reject with-interface all-of { 08:*:* e0:*:* }
    reject with-interface all-of { 08:*:* 02:*:* }

The policy rejects all USB flash disk devices with an interface from the HID/Keyboard, Communications and Wireless classes. Note that default allow is the wrong approach and you shouldn’t just reject a set of devices and allow the rest. The policy above assumes that blocking is the default. Rejecting a set of devices considered as "bad" is a good approach how to limit the exposure of the OS to such devices as much as possible.

4.Allow a keyboard-only USB device only if there isn’t already a USB device with a keyboard interface allowed 
    allow with-interface one-of { 03:00:01 03:01:01 } if !allowed-matches(with-interface one-of { 03:00:01 03:01:01 })
5.Play "Russian roulette" with USB devices 
    allow if random(0.1666)
    reject
