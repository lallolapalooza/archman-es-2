UPSDRVCTL(8) Manual NUT UPSDRVCTL(8)

NOMBRE

upsdrvctl - controlador de drivers de UPS de Network UPS Tools

SINOPSIS

upsdrvctl -h

upsdrvctl [OPCIONES] {start | stop | shutdown | status} [ups]

upsdrvctl [OPCIONES] {list | -l} [ups]

upsdrvctl [OPCIONES] -c COMANDO [ups]

DESCRIPCIÓN

upsdrvctl proporciona una interfaz uniforme para controlar los drivers de tu UPS. Deberías usar el comando upsdrvctl en lugar de llamadas directas a los drivers siempre que sea posible.

Cuando se utiliza correctamente, upsdrvctl te permite mantener scripts de inicio idénticos en múltiples sistemas con diferentes configuraciones de UPS.


Advertencia

Para sistemas operativos con frameworks de gestión de servicios, como Solaris/illumos SMF o systemd de Linux, upsdrvsvcctl(8) podría ser una mejor opción.

De hecho, las instancias de servicio preparadas por nut-driver-enumerator(8) basadas en el contenido de tu archivo ups.conf(5) y mantenidas automáticamente por el framework respectivo pueden entrar en conflicto con la ejecución manual de drivers. En este caso, upsdrvctl emitiría una advertencia en las compilaciones de NUT con esa capacidad (se puede silenciar exportando la variable de entorno NUT_QUIET_INIT_NDE_WARNING con cualquier valor).

Es posible que necesites detener las unidades de servicio (si se usan) y ejecutar los programas drivers directamente en lugar de a través de upsdrvctl para solucionar problemas, por ejemplo, para facilitar la recopilación de registros de depuración o probar compilaciones personalizadas de drivers sin conflicto con una instancia empaquetada que se esté ejecutando normalmente.

OPCIONES

-h

Muestra el texto de ayuda.

-r directorio

Si se inicia un driver, este valor dirigirá al driver a realizar un chroot(2) en directorio. Esto puede ser útil al asegurar sistemas.

Esto se puede configurar en ups.conf(5) con la directiva chroot en la sección global.

-t

Habilita el modo de prueba. Esto también habilita el modo de depuración. El modo de prueba hace que upsdrvctl muestre las acciones que ejecutaría sin hacerlas realmente. Usa esto para probar tu configuración sin afectar realmente a tus drivers de UPS.

Esto puede ser útil al definir la directiva sdorder en tu sección ups.conf(5) para el dispositivo.

-u nombreusuario

Si se inicia un driver, este valor dirigirá al driver a realizar un setuid(2) al id de usuario asociado con nombreusuario.

Si el driver se inicia como root sin especificar este valor, utilizará el nombre de usuario que se compiló en el binario. Esto por defecto es nobody (si no se configura de otra manera), lo cual está lejos de ser ideal.

Esto se puede configurar en ups.conf(5) con la directiva user en la sección global.

-D

Aumenta el nivel de depuración. Úsalo varias veces para obtener detalles adicionales.

Ten en cuenta que esto no impide que la herramienta upsdrvctl salga después de completar su trabajo (sin embargo, una opción explícita -F sí lo hace).

También ten en cuenta que esta opción por sí sola modifica la verbosidad de depuración de la herramienta, pero no la de los drivers que lanza. Consulta la opción adicional -d para eso.

-d

Pasa el nivel de depuración seleccionado de upsdrvctl a los drivers lanzados.

Ten en cuenta que, por defecto para los demonios NUT, la depuración habilitada significa ejecutarse en modo de primer plano; puedes especificar además -B para evitarlo.

-F

El driver se ejecutará en primer plano (no se separará del proceso upsdrvctl), independientemente de la configuración de depuración. También mantendrá la herramienta en primer plano con los demonios de driver ejecutándose como sus hijos (en caso de inicio de un solo driver, ni siquiera se separará).

Tampoco esperará a que los drivers completen la inicialización, por lo que upsdrvctl advertirá sobre tales situaciones.

Especifícalo dos veces (-FF o -F -F) para guardar el archivo PID del driver incluso en este modo (no se guarda por defecto al permanecer en primer plano).

-B

Los drivers se ejecutarán en segundo plano, independientemente de la configuración de depuración, según lo establecido por las opciones -D y transmitido por las opciones -d.

-l

Alias del comando list.

COMANDOS

upsdrvctl admite tres comandos activos: start, stop y shutdown. También admite el paso de solicitudes a drivers en ejecución usando la sintaxis -c COMANDO, similar a la de otros demonios. También hay un par de comandos auxiliares disponibles: list y status.

Todos ellos pueden tomar un argumento opcional que es un nombre de UPS de ups.conf(5). Sin ese argumento, operan sobre cada UPS que está configurada actualmente.


Nota

upsdrvctl no puede administrar dispositivos que no estén listados en ups.conf (como drivers de prueba iniciados con la opción -s TMP).

start

Inicia los drivers de UPS. En caso de que el inicio falle dentro del marco de tiempo de maxstartdelay, se pueden realizar intentos adicionales utilizando los valores de maxretry y retrydelay. Por el contrario, la opción global nowait se puede utilizar, especialmente para acelerar el inicio paralelo de muchos drivers.

Consulta ups.conf(5) sobre estas opciones. Los valores predeterminados integrados son: maxstartdelay=75 (segundos), maxretry=1 (significa un intento de inicio), retrydelay=5 (segundos).

stop

Detiene los drivers de UPS. Esto no envía comandos a la UPS.

shutdown

Ordena a los drivers de UPS que ejecuten su secuencia de apagado. Esto asume que el driver ya no se está ejecutando y inicia una nueva instancia a través de drivername -k. Está destinado a usarse como el último paso en el apagado del sistema, después de que los sistemas de archivos ya no estén montados rw. Los drivers se detienen según su valor sdorder, consulta ups.conf(5).

Advertencia

Esto probablemente apagará tus ordenadores, así que no juegues con esta opción. Úsala solo cuando tus sistemas estén preparados para perder energía.


Nota

Consulta ups.conf(5) para usar el parámetro nowait. Puede ser anulado por la variable de entorno NUT_IGNORE_NOWAIT (por ejemplo, utilizada para solucionar problemas con systemd de lo contrario).

list

Sin un argumento adicional, informa todos los nombres de configuración de dispositivos conocidos actualmente en la salida estándar, uno por línea. Con un argumento, también intenta informar ese nombre, pero sale con un código de error si ese nombre no es conocido.

Nota

La herramienta saldrá con un error si el archivo ups.conf no se encuentra, no es legible o no define ninguna sección de dispositivo (cuyos nombres se informan aquí y se administran en otros comandos).


Nota

El nombre de la herramienta y la línea de banner de la versión NUT también se imprimen en la salida estándar antes de cualquier otro procesamiento. Esto se puede suprimir mediante la variable de entorno NUT_QUIET_INIT_BANNER (exportada por el llamador y vacía o "true"):

:; NUT_QUIET_INIT_BANNER=true upsdrvctl list
dummy
UPS1
UPS2

status

Similar a list, pero informa más información: también el nombre del driver, el PID si se está ejecutando, y el resultado de una sonda de señal para verificar que está respondiendo. La supresión de NUT_QUIET_INIT_BANNER puede ser útil para el análisis de scripts. Si hay algo que imprimir (se conoce al menos un dispositivo), la primera línea del informe de estado sería el encabezado con los nombres de las columnas: 
:; NUT_QUIET_INIT_BANNER=true upsdrvctl status
UPSNAME              UPSDRV  RUNNING PF_PID  S_RESPONSIVE    S_PID   S_STATUS
dummy             dummy-ups  N/A     -3      NOT_RESPONSIVE  N/A
eco650           usbhid-ups  RUNNING 3559207 RESPONSIVE      3559207 "OL"
UPS2              dummy-ups  RUNNING 31455   RESPONSIVE      31455   "OL BOOST"

Los valores están separados por TAB, pero UPSNAME y UPSDRV pueden estar acolchados con espacios a la derecha y a la izquierda respectivamente. Cualquier valor de cadena complejo estaría entrecomillado.

Si el estado de un driver es desconocido, esto se indicará como N/A.

La columna RUNNING muestra el PID si el driver se está ejecutando y actúa como un indicador de su estado. Sin embargo, una respuesta de señal (S_RESPONSIVE) es la prueba definitiva de que el driver está funcionando correctamente y está comunicándose con la UPS.

Si se detectan problemas de comunicación o si el driver no responde, se registrará una entrada apropiada en el archivo de registro del sistema (consulte la directiva syslog en ups.conf(5)). Con el nivel de depuración aumentado, se proporcionará información más detallada sobre la naturaleza de los problemas.

-c COMANDO

Envía el comando especificado a un driver de UPS en ejecución. El comando se pasa directamente al driver y su procesamiento depende del driver específico. Los comandos comunes que se envían a los drivers pueden incluir acciones relacionadas con la gestión de la UPS o la recuperación de información específica del dispositivo. Consulta la documentación de tu driver de UPS específico para ver una lista de comandos compatibles.

Por ejemplo, el driver `dummy-ups` admite el comando `GET-STATUS`.

EJEMPLOS

Para iniciar todos los drivers de UPS configurados en segundo plano con un nivel de depuración aumentado:

$ upsdrvctl -DD start

Para verificar el estado de un driver de UPS específico llamado `myups`:

$ upsdrvctl status myups

Para detener todos los drivers de UPS:

$ upsdrvctl stop

Para enviar el comando `GET-STATUS` al driver `myups`:

$ upsdrvctl -c GET-STATUS myups

Para obtener una lista de todos los drivers de UPS configurados:

$ upsdrvctl list

ARCHIVOS

/etc/ups/ups.conf
Configuración principal de Network UPS Tools, incluyendo la definición de drivers de UPS y sus parámetros.

/var/run/nut/
Directorio predeterminado para archivos PID de drivers de UPS.

upsdrvctl(8) — Network UPS Tools 2.8.4

NAME

upsdrvctl — Monitor and control NUT UPS drivers

SYNOPSIS

upsdrvctl -[uvh]

upsdrvctl -d drivername -[uvh]

upsdrvctl -[Dlv] -[c command] [-p pidfile] [-s socketpath] [-u upsname]

DESCRIPTION

The upsdrvctl utility is a control program for the Network UPS Tools (NUT) drivers. It can be used to monitor the status of running drivers, send commands to them, or start/stop them.

Monitoring Drivers

If run without any arguments, upsdrvctl displays a table of known NUT drivers. The information is gathered by querying the drivers via the NUT control socket protocol (if available and configured) and by inspecting PID files.

Fields reported (PF_* = according to PID file, if any; S_* = via socket protocol):

UPSNAME

driver section configuration name

UPSDRV

driver program name per ups.conf

RUNNING

RUNNING if PF_PID or S_PID is valid, STOPPED if at least one PID value was parsed but none was found running with a correct program name; N/A if no PID file/socket reply or failed to parse. First the PID file is consulted, but it may be absent either due to command-line parameters of daemons, or due to platform (WIN32). If no PID value was found and confirmed this way, we fall back to checking the PID reported via protocol (if available and different).

PF_PID

PID of driver according to PID file (if any), or some negative values upon errors (as defined in common.c) including an absent PID file, invalid contents, or unsupported platform for this mechanism (e.g. WIN32)

S_RESPONSIVE

RESPONSIVE if PING/PONG during socket protocol session setup succeeded; NOT_RESPONSIVE otherwise

S_PID

PID of driver according to GETPID active query, or N/A if the query failed

S_STATUS

Quoted value of ups.status variable

This mode does not discover drivers that are not in ups.conf (e.g. started manually for experiments with many -x CLI options).

Sending Commands

Use the -c command option to send a command to all running drivers managed by upsdrvctl.

-c command

Send command to the background process as a signal. Valid commands are:

dump

tell the driver(s) to dump currently known state information to their stdout (if attached anywhere)

reload

reread configuration files, ignoring modified settings which can not be applied "on the fly"

reload-or-error

reread configuration files, ignoring but counting changed values which require a driver restart (can not be changed on the fly), and return a success/fail code based on that count, so the caller can decide the fate of the currently running driver instance

reload-or-exit

reread configuration files, exiting the old driver process if it encounters modified settings which can not be applied "on the fly" (so caller like systemd can launch another copy of the driver)

exit

tell the currently running driver instance to just exit (so an external caller like the new driver instance, or the systemd or SMF frameworks would start another copy)

If the upsdrvctl was launched to remain in memory and manage NUT driver processes, it can receive supported signals and pass them to those drivers.

Options

The following options are available:

-c, --command command

Send the specified command to the driver(s). See the COMMANDS section for a list of valid commands.

-d, --driver drivername

Operate only on the specified driver. This option can be specified multiple times.

-D, --debug level

Set the debug level for upsdrvctl itself. Does not affect the drivers it controls.

-h, --help

Display a help message and exit.

-l, --list

List known drivers and their status. This is the default behavior if no other options are given.

-p, --pidfile pidfile

Specify the path to the PID file. By default, upsdrvctl looks in the standard state path.

-s, --socketpath socketpath

Specify the path to the NUT control socket. By default, upsdrvctl uses the path defined in upsd.conf.

-u, --upsname upsname

Specify the UPS name to query or send commands to. This option can be specified multiple times.

-v, --version

Display program version and exit.

COMMANDS

The following commands can be sent to drivers using the -c option:

dump

Tell the driver(s) to dump their current internal state information to their standard output. This is mainly useful for debugging.

reload

Tell the driver(s) to reread their configuration files. Settings that cannot be changed while the driver is running will be ignored until the driver is restarted.

reload-or-error

Reread configuration files. If any settings that require a driver restart are encountered, they are ignored, and a count of such settings is returned. The calling process can then decide whether to restart the driver based on this count.

reload-or-exit

Reread configuration files. If any settings that require a driver restart are encountered, the old driver process is terminated, allowing the calling process (e.g., systemd) to start a new instance with the updated configuration.

exit

Tell the driver instance to exit gracefully. This is useful when an external process (like systemd or a new driver instance) needs to replace the current driver.

ENVIRONMENT VARIABLES

NUT_DEBUG_LEVEL sets default debug verbosity if no -D arguments were provided on command line, but does not request that the daemon runs in foreground mode.

NUT_CONFPATH is the path name of the directory that contains ups.conf and other configuration files. If this variable is not set, upsdrvctl (and the drivers) use a built-in default, which is often /usr/local/ups/etc.

NUT_ALTPIDPATH is the path name of the directory in which upsd and drivers store .pid files. If this variable is not set, upsd and drivers use either NUT_STATEPATH if set, or ALTPIDPATH if set, or otherwise the built-in default STATEPATH.

DIAGNOSTICS

upsdrvctl will return a nonzero exit code if it encounters an error while performing the desired operation. This will also happen if a driver takes longer than the maxstartdelay period to enter the background.
