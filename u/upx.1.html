NOMBRE

upx - comprimir o descomprimir archivos ejecutables

SINOPSIS

upx [ comando ] [ opciones ] nombre_archivo...

RESUMEN

                 El Compresor Definitivo para Ejecutables
Copyright (c) 1996-2025 Markus Oberhumer, Laszlo Molnar & John Reiser
                        https://upx.github.io

UPX es un compresor de ejecutables portátil, extensible y de alto rendimiento para varios formatos ejecutables diferentes. Logra una excelente relación de compresión y ofrece una descompresión *muy* rápida. Sus ejecutables no sufren sobrecarga de memoria ni otros inconvenientes para la mayoría de los formatos soportados, debido a la descompresión en el lugar.

DESCARGO DE RESPONSABILIDAD

UPX no ofrece GARANTÍA ABSOLUTA; para más detalles, consulte el archivo COPYING.

Por favor, informe de todos los problemas o sugerencias a los autores. Gracias.

CONTEXTO DE SEGURIDAD

NOTA IMPORTANTE: UPX hereda el contexto de seguridad de cualquier archivo que maneje.

Esto significa que comprimir, descomprimir o incluso probar o listar un archivo requiere las mismas consideraciones de seguridad que ejecutar realmente el archivo.

¡Utilice UPX solo en archivos de confianza!

DESCRIPCIÓN

UPX es un compresor de ejecutables versátil con las siguientes características:

- seguro: como UPX es de código abierto documentado desde hace muchos años,
    cualquier software de seguridad/antivirus relevante puede examinar las
    aplicaciones comprimidas con UPX para verificarlas.
- excelente relación de compresión: típicamente comprime mejor que Zip.
    ¡Use UPX para disminuir el tamaño de su distribución!
- descompresión muy rápida: más de 500 MB/segundo en cualquier máquina
    razonablemente moderna.
- sin sobrecarga de memoria para sus ejecutables comprimidos en la mayoría de
    los formatos soportados debido a la descompresión en el lugar.
- seguro: puede listar, probar y descomprimir sus ejecutables.
    Además, se mantiene internamente una suma de verificación tanto del archivo
    comprimido como del descomprimido.
- universal: UPX puede comprimir varios formatos ejecutables, incluyendo
    programas y DLLs de Windows, aplicaciones de macOS y ejecutables de Linux.
- portátil: UPX está escrito en C++ portátil e independiente de la
    endianness.
- extensible: debido a la estructura de clases, es muy fácil soportar nuevos
    formatos ejecutables o añadir nuevos algoritmos de compresión.
- gratuito: UPX se distribuye con el código fuente completo bajo la Licencia
    Pública General de GNU v2+, con excepciones especiales que otorgan el uso
    gratuito para programas comerciales.

Probablemente ahora entienda por qué llamamos a UPX el compresor de ejecutables "definitivo".

COMANDOS

Comprimir

Esta es la operación por defecto, por ejemplo, upx tuarchivo.exe comprimirá el archivo especificado en la línea de comandos.

Descomprimir

Todos los formatos de archivo soportados por UPX pueden ser descomprimidos usando la opción -d, por ejemplo, upx -d tuarchivo.exe descomprimirá el archivo que acaba de comprimir.

Probar

El comando -t prueba la integridad de los datos comprimidos y descomprimidos. Por ejemplo, upx -t tuarchivo.exe comprueba si su archivo puede descomprimirse de forma segura. Tenga en cuenta que este comando no comprueba todo el archivo, solo la parte que se descomprimirá durante la ejecución del programa. Esto significa que no debe usar este comando como sustituto de un antivirus.

Listar

El comando -l imprime información sobre los archivos comprimidos especificados en la línea de comandos como parámetros. Por ejemplo, upx -l tuarchivo.exe muestra el tamaño comprimido/descomprimido y la relación de compresión de tuarchivo.exe.

OPCIONES

-q: silencioso, suprime advertencias

-q -q (o -qq): muy silencioso, suprime errores

-q -q -q (o -qqq): no produce ninguna salida

--help: imprime la ayuda

--version: imprime la versión de UPX

--exact: al comprimir, requiere poder obtener un archivo byte a byte idéntico después de descomprimir con la opción -d. [NOTA: esto está en desarrollo y aún no es compatible con todos los formatos. Si le importa, como solución alternativa, puede comprimir y luego descomprimir su programa una primera vez; cualquier paso adicional de compresión-descompresión debería producir resultados byte a byte idénticos en comparación con la primera versión descomprimida.]

-k: conservar archivos de copia de seguridad

-o archivo: escribir la salida en el archivo

NIVELES DE COMPRESIÓN Y AJUSTE

UPX ofrece diez niveles de compresión diferentes, de -1 a -9, y --best. El nivel de compresión por defecto es -8 para archivos menores de 512 KiB, y -7 en caso contrario.

  • Los niveles de compresión 1, 2 y 3 son bastante rápidos.
  • Los niveles de compresión 4, 5 y 6 logran un buen rendimiento tiempo/ratio.
  • Los niveles de compresión 7, 8 y 9 favorecen la relación de compresión sobre la velocidad.
  • El nivel de compresión --best puede tardar mucho tiempo.

Tenga en cuenta que el nivel de compresión --best puede ser algo lento para archivos grandes, pero definitivamente debería usarlo al lanzar una versión final de su programa.

Información rápida para lograr la mejor relación de compresión:

  • Pruebe upx --brute --no-lzma miarchivo.exe o incluso upx --ultra-brute --no-lzma miarchivo.exe.
  • La opción --lzma activa la compresión LZMA, que comprime mejor pero es *significativamente más lenta* al descomprimir. Probablemente no querrá usarla para archivos grandes.

    (Tenga en cuenta que --lzma se activa automáticamente con --all-methods y --brute; use --no-lzma para anularlo.)

  • Pruebe si --overlay=strip funciona.
  • Para programas win32/pe existe --strip-relocs=0. Ver notas abajo.

OPCIONES DE MANEJO DE SUPERPOSICIONES

Info: Una "superposición" (overlay) significa datos auxiliares adjuntos después del final lógico de un ejecutable, y a menudo contiene datos específicos de la aplicación (esta es una práctica común para evitar un archivo de datos adicional, aunque sería mejor usar secciones de recursos).

UPX maneja las superposiciones como muchos otros compresores de ejecutables: simplemente copia la superposición después de la imagen comprimida. Esto funciona con algunos archivos, pero no con otros, dependiendo de cómo una aplicación acceda realmente a estos datos superpuestos.

--overlay=copy    Copia cualquier dato adicional adjunto al archivo. [POR DEFECTO]
--overlay=strip   Elimina cualquier superposición del programa en lugar de
                  copiarla. Tenga cuidado, esto puede hacer que el programa
                  comprimido se bloquee o no sea utilizable.
--overlay=skip    Rechaza comprimir cualquier programa que tenga una superposición.

VARIABLE DE ENTORNO

La variable de entorno UPX puede contener un conjunto de opciones por defecto para UPX. Estas opciones se interpretan primero y pueden ser anuladas por parámetros explícitos en la línea de comandos. Por ejemplo:

para DOS/Windows:   set UPX=-9 --compress-icons#0
para sh/ksh/zsh:    UPX="-9 --compress-icons=0"; export UPX
para csh/tcsh:      setenv UPX "-9 --compress-icons=0"

En DOS/Windows, debe usar '#' en lugar de '=' al establecer la variable de entorno debido a una limitación de COMMAND.COM.

No todas las opciones son válidas en la variable de entorno; UPX se lo indicará.

Puede usar explícitamente la opción --no-env para ignorar la variable de entorno.

NOTAS PARA LINUX [general]

Introducción

El soporte de Linux/386 en UPX consta de 3 formatos ejecutables diferentes,
uno optimizado para ejecutables ELF ("linux/elf386"), uno optimizado
para scripts de shell ("linux/sh386"), y un formato genérico
("linux/386").
Comenzaremos con una discusión general primero, pero por favor
también lea la documentación relevante para cada uno de los formatos individuales.
Además, hay soporte especial para kernels arrancables - ver la
descripción del formato vmlinuz/386.

Resumen general para el usuario

Ejecutar un programa ejecutable comprimido intercambia menos espacio en un
medio de almacenamiento "permanente" (como un disco duro, disquete,
CD-ROM, memoria flash, EPROM, etc.) por más espacio en uno o más
medios de almacenamiento "temporales" (como RAM, espacio de intercambio, /tmp, etc.).
Ejecutar un ejecutable comprimido también requiere algunos ciclos de CPU adicionales
para generar el ejecutable comprimido en primer lugar, y para descomprimirlo en cada invocación.
¿Cuánto espacio se intercambia? Depende del ejecutable, pero muchos
programas ahorran entre un 30% y un 50% del espacio en disco permanente. ¿Cuánto tiempo de CPU se consume? Nuevamente, depende del ejecutable, pero la
velocidad de descompresión generalmente es de al menos muchos megabytes por segundo,
y frecuentemente está limitada por la velocidad de E/S del disco
o red subyacente.
Dependiendo de las estadísticas de uso y acceso, y de las velocidades relativas
de la CPU, RAM, espacio de intercambio, /tmp y almacenamiento del sistema de archivos,
invocar y ejecutar un ejecutable comprimido puede ser más rápido que
ejecutar directamente el programa sin comprimir correspondiente.
El sistema operativo podría realizar menos operaciones de E/S costosas
para invocar el programa comprimido. La paginación hacia o desde el espacio de intercambio
o /tmp podría ser más rápida que la paginación desde el sistema de archivos general.
Los programas de "tamaño mediano" que acceden a aproximadamente 1/3 a 1/2 de sus
bytes de programa almacenados pueden beneficiarse especialmente de la compresión.
Los programas pequeños tienden a no beneficiarse tanto porque el ahorro absoluto
es menor. Los programas grandes tienden a no beneficiarse proporcionalmente porque cada invocación puede usar solo una pequeña fracción del programa, y sin embargo UPX descomprime el programa completo antes de invocarlo.
Pero en entornos donde el almacenamiento en disco o memoria flash es limitado,
entonces la compresión puede ganar de todos modos.
Actualmente, los ejecutables comprimidos por UPX no comparten RAM en tiempo de ejecución
de la manera en que lo hacen los ejecutables mapeados desde un sistema de archivos. Como resultado, si el mismo programa es ejecutado simultáneamente por más de un proceso, entonces usar la versión comprimida requerirá más RAM y/o espacio de intercambio. Por lo tanto, los programas de shell (bash, csh, etc.) y "make"
podrían no ser buenos candidatos para la compresión.
UPX reconoce tres formatos ejecutables para Linux: Linux/elf386,
Linux/sh386 y Linux/386. Linux/386 es el formato más genérico;
alberga cualquier archivo que pueda ser ejecutado. En tiempo de ejecución, el stub de descompresión de UPX recrea en /tmp una copia del archivo original, y luego la copia es (re)ejecutada con los mismos argumentos.
Los ejecutables binarios ELF prefieren el formato Linux/elf386 por defecto,
porque UPX los descomprime directamente en RAM, usa solo un exec, no usa espacio en /tmp, y no usa /proc.
Los scripts de shell donde el shell subyacente acepta un argumento "-c" pueden usar el formato Linux/sh386. UPX descomprime el script de shell en memoria baja, luego mapea el shell y pasa el texto completo del script como un argumento con un "-c" inicial.

Beneficios generales:

- UPX puede comprimir todos los ejecutables, ya sean scripts AOUT, ELF, libc4, libc5,
  libc6, Shell/Perl/Python/..., binarios Java .class independientes, o lo que sea...
  Todos los scripts y programas funcionarán igual que antes.
- Los programas comprimidos son completamente autónomos. No necesitan
  ningún programa externo.
- UPX mantiene tu programa original intacto. Esto significa que
  después de la descompresión tendrás una versión byte a byte idéntica,
  y puedes usar UPX como un compresor de archivos como gzip.
  [ Nota que UPX mantiene una suma de verificación del archivo internamente,
    así que es realmente una alternativa fiable. ]
- Como el stub solo usa llamadas al sistema y no está enlazado contra libc,
  debería ejecutarse bajo cualquier configuración de Linux que pueda ejecutar
  binarios ELF.
- Por la misma razón, los ejecutables comprimidos deberían ejecutarse bajo
  FreeBSD y otros sistemas que puedan ejecutar binarios de Linux.
  [ Por favor, envía comentarios sobre este tema ]

Inconvenientes generales:

- No es aconsejable comprimir programas que normalmente tienen muchas
  instancias en ejecución (como `sh' o `make') porque los segmentos comunes de
  los programas comprimidos ya no se compartirán entre diferentes
  procesos.
- `ldd' y `size' no mostrarán nada útil porque todo lo que
  ven es el stub enlazado estáticamente. Desde la versión 0.82, las cabeceras
  de sección se han eliminado del stub de UPX y `size' ni siquiera
  reconoce el formato del archivo. El parche `patch-elfcode.h' contiene
  un parche para corregir este error en `size' y otros programas que usan GNU BFD.

Notas generales:

- Como UPX deja tu programa original intacto, es ventajoso
  eliminar la información de depuración (strip) antes de la compresión.
- Si comprimes un script, perderás la independencia de plataforma -
  esto podría ser un problema si estás usando discos montados por NFS.
- La compresión de programas suid, guid y sticky-bit se rechaza
  debido a posibles implicaciones de seguridad.
- Por la misma razón, no tiene sentido hacer que ningún programa comprimido
  sea suid.
- Obviamente, UPX no funcionará con ejecutables que quieran leer datos
  de sí mismos. Por ejemplo, esto podría ser un problema para scripts de Perl
  que acceden a sus líneas __DATA__.

NOTES FOR LINUX/PE

The PE support in UPX is quite stable now, but probably there are still some incompatibilities with some files.

Because of the way UPX (and other packers for this format) works, you can see increased memory usage of your compressed files because the whole program is loaded into memory at startup. If you start several instances of huge compressed programs you're wasting memory because the common segments of the program won't get shared across the instances. On the other hand if you're compressing only smaller programs, or running only one instance of larger programs, then this penalty is smaller, but it's still there.

If you're running executables from network, then compressed programs will load faster, and require less bandwidth during execution.

DLLs are supported. But UPX compressed DLLs can not share common data and code when they got used by multiple applications. So compressing msvcrt.dll is a waste of memory, but compressing the dll plugins of a particular application may be a better idea.

Screensavers are supported, with the restriction that the filename must end with ".scr" (as screensavers are handled slightly different than normal exe files).

UPX compressed PE files have some minor memory overhead (usually in the 10 - 30 KiB range) which can be seen by specifying the "-i" command line switch during compression.

Extra options available for this executable format:

--compress-exports=0  Don't compress the export section.
                      Use this if you plan to run the compressed
                      program under Wine.
--compress-exports=1  Compress the export section. [DEFAULT]
                      Compression of the export section can improve the
                      compression ratio quite a bit but may not work
                      with all programs (like winword.exe).
                      UPX never compresses the export section of a DLL
                      regardless of this option.
 --compress-icons=0   Don't compress any icons.
 --compress-icons=1   Compress all but the first icon.
 --compress-icons=2   Compress all icons which are not in the
                      first icon directory. [DEFAULT]
 --compress-icons=3   Compress all icons.
 --compress-resources=0  Don't compress any resources at all.
 --keep-resource=list Don't compress resources specified by the list.
                      The members of the list are separated by commas.
                      A list member has the following format: I<type[/name]>.
                      I<Type> is the type of the resource. Standard types
                      must be specified as decimal numbers, user types can be
                      specified by decimal IDs or strings. I<Name> is the
                      identifier of the resource. It can be a decimal number
                      or a string. For example:
                      --keep-resource=2/MYBITMAP,5,6/12345
                      UPX won't compress the named bitmap resource "MYBITMAP",
                      it leaves every dialog (5) resource uncompressed, and
                      it won't touch the string table resource with identifier
                      12345.
 --force              Force compression even when there is an
                      unexpected value in a header field.
                      Use with care.
 --strip-relocs=0     Don't strip relocation records.
 --strip-relocs=1     Strip relocation records. [DEFAULT]
                      This option only works on executables with base
                      address greater or equal to 0x400000. Usually the
                      compressed files becomes smaller, but some files
                      may become larger. Note that the resulting file will
                      not work under Windows 3.x (Win32s).
                      UPX never strips relocations from a DLL
                      regardless of this option.
 --all-methods        Compress the program several times, using all
                      available compression methods. This may improve
                      the compression ratio in some cases, but usually
                      the default method gives the best results anyway.
 --all-filters        Compress the program several times, using all
                      available preprocessing filters. This may improve
                      the compression ratio in some cases, but usually
                      the default filter gives the best results anyway.

NOTES FOR LINUX/SELF-EXTRACTING ARCHIVES

This is a specialized format, which contains an archive and a small Linux executable. The executable unpacks the archive into the current directory and then executes the unpacked binary.

The main disadvantage of UPX on this format is that the packed executable itself is not runnable on some systems (e.g. it's not possible to run executables from CD-ROMs).

The --self-executing option (enabled by default) tries to embed the decompression stub and the archive into a single executable.

The --lzma, --bzip2, --zlib, --lzo, --lzop and --ubc options control the compression method. See also the general options.

UPX has been successfully tested with the following executable formats:

ELF 32-bit (Intel, ARM, PowerPC, MIPS, SPARC)
ELF 64-bit (x86-64, ARM, PowerPC, MIPS, SPARC)
                                          [original]
ELF 32-bit (Intel, ARM, PowerPC, MIPS, SPARC)
ELF 64-bit (x86-64, ARM, PowerPC, MIPS, SPARC)
                                          [compressed by "upx -9"]

The compression ratio achieved is quite high, and the startup time of the compressed executables is only slightly slower than the original ones. The decompression speed is very fast.

Drawbacks:

(none)

                    the default method gives the best results anyway.
--all-filters       Compress the program several times, using all
                    available preprocessing filters. This may improve
                    the compression ratio in some cases, but usually
                    the default filter gives the best results anyway.

NOTES FOR LINUX/KERNEL MODULES

The compression of Linux kernel modules requires root privileges.

The format of kernel modules is not standardized, so UPX might not work with all of them. However, it has been successfully tested with the following kernel versions:

Linux kernel 2.2.16, 2.4.x, 2.6.x, 3.x, 4.x, 5.x

For example, this is what I get for my 2.2.16 kernel:

   1589708  vmlinux
    641073  bzImage        [original]
    560755  bzImage.upx    [compressed by "upx -9"]

- Much faster decompression at kernel boot time (but kernel decompression speed is not really an issue these days).
