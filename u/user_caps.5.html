user_caps(5) Formatos de archivo user_caps(5)

NOMBRE

user_caps - formato de capacidades terminfo definido por el usuario

SINOPSIS

infocmp -x

tic -x

DESCRIPCIÓN

Antecedentes

Antes de ncurses 5.0, las bases de datos terminfo utilizaban un repertorio fijo de capacidades de terminal diseñadas para la base de datos de terminales SVr2 en 1984, y extendido en etapas hasta SVr4 (1989), y estandarizado en la Especificación Única de Unix a partir de 1995.

La mayoría de las extensiones de este repertorio fijo fueron adiciones a las tablas de capacidades booleanas, numéricas y de cadena. En lugar de cambiar el significado de una capacidad existente, se añadió un nuevo nombre. La base de datos terminfo utiliza un formato binario; la compatibilidad binaria se garantizó utilizando una cabecera que indicaba el número de elementos en las tablas para cada tipo de capacidad. La estandarización fue incompleta:

•
El formato binario en sí no se describe en la documentación de X/Open Curses. Solo se describe el formato fuente.
Los desarrolladores de bibliotecas se basan en la documentación SVr4 y en la ingeniería inversa de los archivos terminfo compilados para que coincidan con el formato binario.
•
Al carecer de un estándar para el formato binario, la mayoría de las implementaciones copian el formato binario SVr2, que utiliza enteros con signo de 16 bits y está limitado a entradas de 4096 bytes.
El formato no puede representar capacidades numéricas muy grandes, ni puede representar un gran número de definiciones de teclado especiales.
•
Las tablas de nombres de capacidades difieren entre implementaciones.
Aunque pueden proporcionar todos los nombres de capacidades estándar, la posición en las tablas difiere porque algunas características se añadieron según fuera necesario, mientras que otras se añadieron (fuera de orden) para cumplir con X/Open Curses.
Si bien el repertorio de capacidades predefinidas de ncurses es el más cercano a Solaris, la base de datos terminfo de Solaris tiene algunas diferencias con la lista publicada por X/Open Curses. Por ejemplo, ncurses puede configurarse con tablas que coinciden con las bases de datos de terminales de AIX, HP-UX u OSF/1, en lugar de la configuración predeterminada similar a Solaris.
•
En SVr4 curses y ncurses, la base de datos de terminales se define en tiempo de compilación utilizando un archivo de texto que enumera las diferentes capacidades de terminal.
En principio, el archivo de texto puede extenderse, pero hacerlo requiere recompilar y reinstalar la biblioteca. El archivo de texto utilizado en ncurses para las capacidades de terminal incluye detalles para varios sistemas posteriores a las características documentadas de X/Open Curses. Por ejemplo, ncurses soporta estas capacidades en cada configuración:
memory_lock
(meml) bloquear memoria encima del cursor
memory_unlock
(memu) desbloquear memoria
box_chars_1
(box1) caracteres de borde conjunto primario
Las capacidades de bloqueo/desbloqueo de memoria se incluyeron porque se utilizaron en la descripción de terminal para xterm(1) en X11R6. La capacidad box1 es utilizada por tic para ayudar con las descripciones de terminal escritas para AIX.

Durante la década de 1990, algunos usuarios se mostraron reacios a utilizar terminfo a pesar de sus ventajas de rendimiento sobre termcap:

  • El repertorio fijo impidió a los usuarios añadir características para mejoras de terminal no previstas (o les obligó a reutilizar capacidades existentes como solución alternativa).
  • También se mencionó la limitación a enteros con signo de 16 bits. Como termcap almacena todo como una cadena, podía representar números más grandes.

Aunque la extensibilidad de termcap se utilizó rara vez (nunca fue el hablante quien realmente había utilizado la característica), la crítica tenía un punto. ncurses 5.0 proporcionó una forma de detectar capacidades no estándar, determinar su tipo y opcionalmente almacenarlas y recuperarlas de una manera que no interfiriera con otras aplicaciones. Estas se denominan capacidades definidas por el usuario porque no se necesitan modificaciones en los nombres de capacidades predefinidos del conjunto de herramientas.

Las utilidades de ncurses tic e infocmp tienen una opción de línea de comandos “-x” para controlar si las capacidades no estándar se almacenan o recuperan. Se proporciona una función de biblioteca use_extended_names para el mismo propósito.

Al compilar una base de datos de terminal, si se establece “-x”, tic almacenará una capacidad definida por el usuario si el nombre de la capacidad no es uno de los nombres predefinidos.

Dado que ncurses proporciona una interfaz de biblioteca termcap, estas capacidades definidas por el usuario pueden ser visibles para las aplicaciones termcap:

•
La interfaz termcap (como todas las implementaciones de termcap) requiere que los nombres de las capacidades tengan 2 caracteres.
Cuando la capacidad es lo suficientemente simple para su uso en una aplicación termcap, se proporciona como un nombre de 2 caracteres.
  • Existen otras capacidades definidas por el usuario que se refieren a características no utilizables en termcap, por ejemplo, cadenas parametrizadas que utilizan más de dos parámetros o que utilizan más que el soporte trivial de expresiones proporcionado por termcap. Para estas, la base de datos terminfo solo debe tener nombres de capacidades de 3 o más caracteres.
  • Algunos terminales pueden enviar cadenas distintas para teclas especiales (teclas de cursor, teclado o función) dependiendo de las teclas modificadoras (shift, control, etc.). Si bien terminfo y termcap tienen un conjunto de 60 nombres de teclas de función predefinidos, a los que se puede asignar una serie de teclas, eso es insuficiente para más de una docena de teclas multiplicadas por más de un par de combinaciones modificadoras. La base de datos ncurses utiliza una convención basada en xterm(1) para proporcionar nombres de teclas especiales extendidos.
Adaptar eso a la limitación de nombres de 2 caracteres de termcap sería inútil. Estas teclas extendidas solo están disponibles con terminfo.

Capacidades Reconocidas

La biblioteca ncurses utiliza las capacidades definibles por el usuario. Aunque la base de datos terminfo puede tener otras extensiones, ncurses realiza comprobaciones explícitas de las siguientes:

AX
Booleano, afirma que el terminal interpreta SGR 39 y SGR 49 restableciendo el color de primer plano y de fondo, respectivamente, a los valores predeterminados.
Esta es una característica reconocida también por el programa screen.
E3
cadena, indica cómo borrar el búfer de desplazamiento del terminal. Cuando está presente, el programa clear(1) envía esto antes de borrar el terminal.
El comando “tput clear” hace lo mismo.
NQ
Booleano, se utiliza para suprimir una comprobación de consistencia en tic para las capacidades ncurses en user6 a user9 (u6, u7, u8 y u9) que indican cómo consultar la posición del cursor del terminal y sus atributos de dispositivo.
RGB
Booleano, número o cadena, se utiliza para afirmar que las capacidades set_a_foreground y set_a_background corresponden a colores directos, utilizando una convención RGB (rojo/verde/azul). Esta capacidad permite que la función color_content devuelva valores apropiados sin necesidad de que la aplicación inicialice los colores utilizando init_color.
El tipo de capacidad determina los valores que ve ncurses:
Booleano
implica que el número de bits para rojo, verde y azul son los mismos. Utilizando el número máximo de colores, ncurses añade dos, divide esa suma por tres y asigna el resultado a rojo, verde y

blue
the red, green, blue, and white components of the corresponding color, in that order.
Si el número de bits necesarios para el número de colores no es múltiplo de tres, los componentes azul (y verde) pierden en comparación con el rojo.
number
le dice a ncurses qué resultado agregar a rojo, verde y azul. Si ncurses se queda sin bits, el azul (y el verde) pierden igual que en el caso booleano.
string
enumera explícitamente el número de bits utilizados para los componentes rojo, verde y azul como una lista separada por barras de enteros decimales.
Dado que existen varias codificaciones RGB en uso, las aplicaciones que asumen el número de bits por color probablemente no funcionarán de manera confiable. Como caso trivial, por ejemplo, se podría definir RGB#1 para representar los ocho colores ANSI estándar, es decir, un bit por color.
U8
number, afirma que ncurses debe usar valores Unicode para los caracteres de dibujo de líneas y que debe ignorar las capacidades del conjunto de caracteres alternativo cuando la configuración regional utiliza la codificación UTF-8. Para obtener más información, consulte la discusión sobre NCURSES_NO_UTF8_ACS en ncurses(3X).
Establezca esta capacidad a un valor distinto de cero para habilitarla.
XM
string, anula la cadena incorporada de ncurses que habilita/deshabilita el modo de ratón de xterm(1).
ncurses envía una secuencia de caracteres a la terminal para inicializar el modo de ratón y, cuando el usuario hace clic en los botones del ratón o (en ciertos modos) mueve el ratón, maneja los caracteres que la terminal devuelve para informarle qué se hizo con el ratón.
El protocolo del ratón se habilita cuando la máscara pasada en la función mousemask no es cero. Por defecto, ncurses maneja las respuestas para el protocolo de ratón xterm de X11. También conoce el protocolo de ratón xterm SGR 1006, pero debe indicársele que lo busque específicamente. No podrá adivinar qué modo se utiliza, ya que las respuestas son lo suficientemente similares como para que solo cause confusión.
La capacidad XM tiene un único parámetro. Si no es cero, el protocolo del ratón debe habilitarse. Si es cero, el protocolo del ratón debe deshabilitarse. ncurses inspecciona esta capacidad si está presente, para ver si se utiliza el protocolo 1006. En ese caso, espera que las respuestas utilicen el protocolo de ratón xterm SGR 1006.
El protocolo de ratón xterm es utilizado por otros emuladores de terminal. La base de datos de terminales utiliza bloques de construcción para los diversos protocolos de ratón xterm que se pueden utilizar en descripciones de terminal personalizadas.
Los bloques de construcción de la base de datos de terminal para esta característica del ratón también tienen una capacidad experimental xm. La capacidad "xm" describe la respuesta del ratón. Actualmente no hay un intérprete que utilice esta información para hacer que el soporte del ratón sea completamente impulsado por datos.
xm muestra el formato de las respuestas del ratón. En esta capacidad experimental, los parámetros son
p1
ordenada y
p2
abscisa
p3
botón
p4
estado, por ejemplo, presionado o liberado
p5
región de inicio de la ordenada
p6
región de inicio de la abscisa
p7
región de fin de la ordenada
p8
región de fin de la abscisa

Definiciones de Teclas Extendidas

Varios terminales proporcionan la capacidad de enviar cadenas distintas para combinaciones de teclas especiales modificadas. No existe un estándar sobre lo que esas teclas pueden enviar.

Desde 1999, xterm(1) ha soportado modificadores shift, control, alt y meta que producen cadenas de teclas especiales distintas. En una descripción de terminal, ncurses no tiene conocimiento especial de los modificadores utilizados. Las aplicaciones pueden utilizar la convención de nomenclatura establecida para xterm para encontrar estas teclas especiales en la descripción de la terminal.

Comenzando con la convención de curses de que los códigos de capacidad que describen la entrada generada por las teclas de un terminal comienzan con "k" y que las teclas especiales con mayúsculas usan letras mayúsculas en sus nombres, la base de datos de terminales de ncurses define los siguientes nombres y códigos a los que se les agrega un sufijo.

Código Descripción
kDC kdch1 con mayúsculas (borrar carácter)
kDN kcud1 con mayúsculas (cursor abajo)
kEND kend con mayúsculas (fin)
kHOM khome con mayúsculas (inicio)
kLFT kcub1 con mayúsculas (cursor atrás)
kNXT kgetNext con mayúsculas (siguiente)
kPRV kprev con mayúsculas (anterior)
kRIT kcuf1 con mayúsculas (cursor adelante)
kUP kcuu1 con mayúsculas (cursor arriba)

La nomenclatura de las teclas en los sistemas Unix para los que se desarrolló curses difiere de los omnipresentes descendientes actuales del diseño del teclado IBM PC/AT. En lo anterior, interprete "atrás" como "izquierda", "adelante" como "derecha", "siguiente" como "página abajo" y "anterior" como "página arriba".

Estos son los sufijos utilizados para denotar los modificadores:

Valor Descripción
2 Shift
3 Alt
4 Shift + Alt
5 Control
6 Shift + Control
7 Alt + Control
8 Shift + Alt + Control
9 Meta
10 Meta + Shift
11 Meta + Alt
12 Meta + Alt + Shift
13 Meta + Ctrl
14 Meta + Ctrl + Shift
15 Meta + Ctrl + Alt
16 Meta + Ctrl + Alt + Shift

Ninguno de estos está predefinido; las descripciones de terminal pueden referirse a nombres que ncurses asignará en tiempo de ejecución a códigos de tecla. Para usar estas teclas en un programa ncurses, una aplicación podría hacer lo siguiente:

  • utilizando una lista de nombres de teclas extendidas, solicitar a tigetstr(3X) sus valores, y
  • dada la lista de valores, solicitar a key_defined(3X) el código de tecla que devolvería wgetch(3X) para esas teclas.

PORTABILIDAD

La extensión "-x" de tic y infocmp ha sido adoptada en NetBSD curses. Esa implementación almacena capacidades definidas por el usuario, pero no hace uso de ellas misma.

user_caps - Archivos de configuración de capacidades de usuario.

DESCRIPCIÓN

El archivo user_caps es un archivo de configuración utilizado por el sistema pam_cap para gestionar las capacidades de los usuarios.

Cada línea del archivo representa una entrada de configuración y sigue el siguiente formato:

usuario:capacidad1,capacidad2,...
  • usuario: El nombre del usuario al que se le aplicarán las capacidades. Se puede usar el carácter comodín '*' para aplicar la línea a todos los usuarios no especificados explícitamente.
  • capacidad1,capacidad2,...: Una lista separada por comas de las capacidades que se asignarán al usuario. Si la lista está vacía, significa que se eliminarán todas las capacidades previamente asignadas al usuario.

Las capacidades válidas son las definidas por el sistema POSIX. Por ejemplo, cap_net_raw, cap_sys_ptrace, etc.

El archivo user_caps se lee al iniciar sesión del usuario. Si el archivo no existe o está vacío, no se aplicarán capacidades adicionales a los usuarios.

PORTABILIDAD

Este archivo es específico del sistema Linux y de la implementación de pam_cap. No es portable a otros sistemas operativos Unix-like.

AUTORES

Este archivo de configuración es parte del sistema pam_cap.

VER TAMBIÉN
