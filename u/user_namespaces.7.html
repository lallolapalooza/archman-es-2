NOMBRE

user_namespaces - resumen de los espacios de nombres de usuario de Linux

DESCRIPCIÓN

Para un resumen de los espacios de nombres, vea namespaces(7).

Los espacios de nombres de usuario aíslan identificadores y atributos relacionados con la seguridad, en particular, IDs de usuario y grupo (ver credentials(7)), el directorio raíz, claves (ver keyrings(7)) y capacidades (ver capabilities(7)). Los IDs de usuario y grupo de un proceso pueden ser diferentes dentro y fuera de un espacio de nombres de usuario. En particular, un proceso puede tener un ID de usuario normal sin privilegios fuera de un espacio de nombres de usuario mientras que al mismo tiempo tiene un ID de usuario de 0 dentro del espacio de nombres; en otras palabras, el proceso tiene privilegios completos para operaciones dentro del espacio de nombres de usuario, pero carece de privilegios para operaciones fuera del espacio de nombres.

Espacios de nombres anidados, pertenencia al espacio de nombres

Los espacios de nombres de usuario pueden anidarse; es decir, cada espacio de nombres de usuario —excepto el espacio de nombres inicial ("raíz")— tiene un espacio de nombres de usuario padre, y puede tener cero o más espacios de nombres de usuario hijos. El espacio de nombres de usuario padre es el espacio de nombres de usuario del proceso que crea el espacio de nombres de usuario a través de una llamada a unshare(2) o clone(2) con la bandera CLONE_NEWUSER.

El kernel impone (desde Linux 3.11) un límite de 32 niveles anidados de espacios de nombres de usuario. Las llamadas a unshare(2) o clone(2) que excederían este límite fallan con el error EUSERS.

Cada proceso es miembro de exactamente un espacio de nombres de usuario. Un proceso creado a través de fork(2) o clone(2) sin la bandera CLONE_NEWUSER es miembro del mismo espacio de nombres de usuario que su padre. Un proceso de un solo hilo puede unirse a otro espacio de nombres de usuario con setns(2) si tiene CAP_SYS_ADMIN en ese espacio de nombres; al hacerlo, obtiene un conjunto completo de capacidades en ese espacio de nombres.

Una llamada a clone(2) o unshare(2) con la bandera CLONE_NEWUSER hace que el nuevo proceso hijo (para clone(2)) o el llamante (para unshare(2)) sea miembro del nuevo espacio de nombres de usuario creado por la llamada.

La operación ioctl(2) NS_GET_PARENT puede usarse para descubrir la relación parental entre espacios de nombres de usuario; ver ioctl_nsfs(2).

Una tarea que cambia uno de sus IDs efectivos tendrá su volcado restablecido al valor en /proc/sys/fs/suid_dumpable. Esto puede afectar la propiedad de los archivos proc de los procesos hijos y, por lo tanto, puede hacer que el padre carezca de los permisos para escribir en los archivos de mapeo de los procesos hijos que se ejecutan en un nuevo espacio de nombres de usuario. En tales casos, hacer que el proceso padre sea "dumpable", usando PR_SET_DUMPABLE en una llamada a prctl(2), antes de crear un proceso hijo en un nuevo espacio de nombres de usuario puede resolver este problema. Ver prctl(2) y proc(5) para detalles sobre cómo se ve afectada la propiedad.

Capacidades

El proceso hijo creado por clone(2) con la bandera CLONE_NEWUSER comienza con un conjunto completo de capacidades en el nuevo espacio de nombres de usuario. De manera similar, un proceso que crea un nuevo espacio de nombres de usuario usando unshare(2) o se une a un espacio de nombres de usuario existente usando setns(2) obtiene un conjunto completo de capacidades en ese espacio de nombres. Por otro lado, ese proceso no tiene capacidades en el espacio de nombres de usuario padre (en el caso de clone(2)) o anterior (en el caso de unshare(2) y setns(2)), incluso si el nuevo espacio de nombres es creado o unido por el usuario root (es decir, un proceso con ID de usuario 0 en el espacio de nombres raíz).

Tenga en cuenta que una llamada a execve(2) hará que las capacidades de un proceso se recalculen de la manera habitual (ver capabilities(7)). En consecuencia, a menos que el proceso tenga un ID de usuario 0 dentro del espacio de nombres, o que el archivo ejecutable tenga una máscara de capacidades heredables no vacía, el proceso perderá todas las capacidades. Ver la discusión de los mapeos de ID de usuario y grupo, abajo.

Una llamada a clone(2) o unshare(2) usando la bandera CLONE_NEWUSER o una llamada a setns(2) que mueve al llamante a otro espacio de nombres de usuario establece las banderas "securebits" (ver capabilities(7)) a sus valores predeterminados (todas las banderas deshabilitadas) en el hijo (para clone(2)) o llamante (para unshare(2) o setns(2)). Tenga en cuenta que dado que el llamante ya no tiene capacidades en su espacio de nombres de usuario original después de una llamada a setns(2), no es posible que un proceso restablezca sus banderas "securebits" mientras retiene su pertenencia al espacio de nombres de usuario utilizando un par de llamadas a setns(2) para moverse a otro espacio de nombres de usuario y luego regresar a su espacio de nombres de usuario original.

Las reglas para determinar si un proceso tiene o no una capacidad en un espacio de nombres de usuario particular son las siguientes:

•
Un proceso tiene una capacidad dentro de un espacio de nombres de usuario si es miembro de ese espacio de nombres y tiene la capacidad en su conjunto de capacidades efectivas. Un proceso puede obtener capacidades en su conjunto de capacidades efectivas de varias maneras. Por ejemplo, puede ejecutar un programa set-user-ID o un ejecutable con capacidades de archivo asociadas. Además, un proceso puede obtener capacidades a través del efecto de clone(2), unshare(2) o setns(2), como ya se describió.
•
Si un proceso tiene una capacidad en un espacio de nombres de usuario, entonces tiene esa capacidad en todos los espacios de nombres hijos (y descendientes más lejanos) también.
•
Cuando se crea un espacio de nombres de usuario, el kernel registra el ID de usuario efectivo del proceso creador como el "propietario" del espacio de nombres. Un proceso que reside en el padre del espacio de nombres de usuario y cuyo ID de usuario efectivo coincide con el propietario del espacio de nombres tiene todas las capacidades en el espacio de nombres. En virtud de la regla anterior, esto significa que el proceso tiene todas las capacidades en todos los espacios de nombres de usuario descendientes más lejanos también. La operación ioctl(2) NS_GET_OWNER_UID puede usarse para descubrir el ID de usuario del propietario del espacio de nombres; ver ioctl_nsfs(2).

Efecto de las capacidades dentro de un espacio de nombres de usuario

Tener una capacidad dentro de un espacio de nombres de usuario permite a un proceso realizar operaciones (que requieren privilegio) solo sobre recursos gobernados por ese espacio de nombres. En otras palabras, tener una capacidad en un espacio de nombres de usuario permite a un proceso realizar operaciones privilegiadas sobre recursos que están gobernados por espacios de nombres (no de usuario) propiedad de (asociados con) el espacio de nombres de usuario (ver la siguiente subsección).

Por otro lado, hay muchas operaciones privilegiadas que afectan a recursos que no están asociados con ningún tipo de espacio de nombres, por ejemplo, cambiar la hora del sistema (calendario) (gobernada por CAP_SYS_TIME), cargar un módulo del kernel (gobernada por CAP_SYS_MODULE) y crear un dispositivo (gobernado por CAP_MKNOD). Solo un proceso con privilegios en el espacio de nombres de usuario *inicial* puede realizar tales operaciones.

Tener CAP_SYS_ADMIN dentro del espacio de nombres de usuario que posee el espacio de nombres de montaje de un proceso permite a ese proceso crear montajes bind y montar los siguientes tipos de sistemas de archivos:

•
/proc (desde Linux 3.8)
•
/sys (desde Linux 3.8)
•
devpts (desde Linux 3.9)
•
tmpfs(5) (desde Linux 3.9)
•
ramfs (desde Linux 3.9)
•
mqueue (desde Linux 3.9)
•
bpf (desde Linux 4.4)
•
overlayfs (desde Linux 5.11)

Poseer CAP_SYS_ADMIN dentro del espacio de nombres de usuario que posee el espacio de nombres cgroup de un proceso permite (desde Linux 4.6) que ese proceso monte el sistema de archivos cgroup versión 2 y jerarquías nombradas de cgroup versión 1 (es decir, sistemas de archivos cgroup montados con la opción "none,name=").

Poseer CAP_SYS_ADMIN dentro del espacio de nombres de usuario que posee el espacio de nombres PID de un proceso permite (desde Linux 3.8) que ese proceso monte sistemas de archivos /proc.

Sin embargo, montar sistemas de archivos basados en bloques solo puede ser realizado por un proceso que posea CAP_SYS_ADMIN en el espacio de nombres de usuario inicial.

Interacción de los espacios de nombres de usuario y otros tipos de espacios de nombres

Desde Linux 3.8, los procesos no privilegiados pueden crear espacios de nombres de usuario, y los otros tipos de espacios de nombres se pueden crear con solo la capacidad CAP_SYS_ADMIN en el espacio de nombres de usuario del llamante.

Cuando se crea un espacio de nombres no de usuario, es propiedad del espacio de nombres de usuario en el que el proceso creador era miembro en el momento de la creación del espacio de nombres. Las operaciones privilegiadas sobre recursos gobernados por el espacio de nombres no de usuario requieren que el proceso tenga las capacidades necesarias en el espacio de nombres de usuario que posee el espacio de nombres no de usuario.

Si se especifica CLONE_NEWUSER junto con otras banderas CLONE_NEW* en una única llamada a clone(2) o unshare(2), se garantiza que el espacio de nombres de usuario se creará primero, otorgando al hijo (clone(2)) o al llamante (unshare(2)) privilegios sobre los espacios de nombres restantes creados por la llamada. Por lo tanto, es posible que un llamante no privilegiado especifique esta combinación de banderas.

Cuando se crea un nuevo espacio de nombres (que no sea un espacio de nombres de usuario) a través de clone(2) o unshare(2), el kernel registra el espacio de nombres de usuario del proceso creador como el propietario del nuevo espacio de nombres. (Esta asociación no se puede cambiar). Cuando un proceso en el nuevo espacio de nombres realiza posteriormente operaciones privilegiadas que operan sobre recursos globales aislados por el espacio de nombres, las comprobaciones de permisos se realizan de acuerdo con las capacidades del proceso en el espacio de nombres de usuario que el kernel asoció con el nuevo espacio de nombres. Por ejemplo, supongamos que un proceso intenta cambiar el nombre de host (sethostname(2)), un recurso gobernado por el espacio de nombres UTS. En este caso, el kernel determinará qué espacio de nombres de usuario posee el espacio de nombres UTS del proceso y verificará si el proceso tiene la capacidad requerida (CAP_SYS_ADMIN) en ese espacio de nombres de usuario.

La operación ioctl(2) NS_GET_USERNS se puede utilizar para descubrir el espacio de nombres de usuario que posee un espacio de nombres no de usuario; consulte ioctl_nsfs(2).

Mapeos de IDs de usuario y grupo: uid_map y gid_map

Cuando se crea un espacio de nombres de usuario, comienza sin un mapeo de IDs de usuario (IDs de grupo) al espacio de nombres de usuario padre. Los archivos /proc/pid/uid_map y /proc/pid/gid_map (disponibles desde Linux 3.5) exponen los mapeos de IDs de usuario y grupo dentro del espacio de nombres de usuario para el proceso pid. Estos archivos se pueden leer para ver los mapeos en un espacio de nombres de usuario y escribir en ellos (una vez) para definir los mapeos.

La descripción en los siguientes párrafos explica los detalles para uid_map; gid_map es exactamente lo mismo, pero cada instancia de "ID de usuario" se reemplaza por "ID de grupo".

El archivo uid_map expone el mapeo de IDs de usuario desde el espacio de nombres de usuario del proceso pid al espacio de nombres de usuario del proceso que abrió uid_map (pero consulte una calificación a este punto a continuación). En otras palabras, los procesos que se encuentran en diferentes espacios de nombres de usuario verán potencialmente diferentes valores al leer de un archivo uid_map particular, dependiendo de los mapeos de IDs de usuario para los espacios de nombres de usuario de los procesos lectores.

Cada línea en el archivo uid_map especifica un mapeo de 1 a 1 de un rango de IDs de usuario contiguos entre dos espacios de nombres de usuario. (Cuando se crea un espacio de nombres de usuario por primera vez, este archivo está vacío). La especificación en cada línea toma la forma de tres números delimitados por espacios en blanco. Los dos primeros números especifican el ID de usuario inicial en cada uno de los dos espacios de nombres de usuario. El tercer número especifica el tamaño del rango mapeado. En detalle, los campos se interpretan de la siguiente manera:

(1)
El inicio del rango de IDs de usuario en el espacio de nombres de usuario del proceso pid.
(2)
El inicio del rango de IDs de usuario al que se mapean los IDs de usuario especificados por el campo uno. Cómo se interpreta el campo dos depende de si el proceso que abrió uid_map y el proceso pid están en el mismo espacio de nombres de usuario, como sigue:
(a)
Si los dos procesos están en diferentes espacios de nombres de usuario: el campo dos es el inicio de un rango de IDs de usuario en el espacio de nombres de usuario del proceso que abrió uid_map.
(b)
Si los dos procesos están en el mismo espacio de nombres de usuario: el campo dos es el inicio del rango de IDs de usuario en el espacio de nombres de usuario padre del proceso pid. Este caso permite al abridor de uid_map (el caso común aquí es abrir /proc/self/uid_map) ver el mapeo de IDs de usuario en el espacio de nombres de usuario del proceso que creó este espacio de nombres de usuario.
(3)
El tamaño del rango de IDs de usuario que se mapea entre los dos espacios de nombres de usuario.

Las llamadas al sistema que devuelven IDs de usuario (IDs de grupo) —por ejemplo, getuid(2), getgid(2), y los campos de credenciales en la estructura devuelta por stat(2)— devuelven el ID de usuario (ID de grupo) mapeado al espacio de nombres de usuario del llamante.

Cuando un proceso accede a un archivo, sus IDs de usuario y grupo se mapean al espacio de nombres de usuario inicial para fines de verificación de permisos y asignación de IDs al crear un archivo. Cuando un proceso recupera los IDs de usuario y grupo del archivo a través de stat(2), los IDs se mapean en la dirección opuesta, para producir valores relativos a los mapeos de IDs de usuario y grupo del proceso.

El espacio de nombres de usuario inicial no tiene espacio de nombres padre, pero, por coherencia, el kernel proporciona archivos de mapeo de IDs de usuario y grupo ficticios para este espacio de nombres. Al observar el archivo uid_map (gid_map es lo mismo) desde un shell en el espacio de nombres inicial se muestra:


$ cat /proc/$$/uid_map;
         0          0 4294967295

Este mapeo nos dice que el rango que comienza en el ID de usuario 0 en este espacio de nombres se mapea a un rango que comienza en 0 en el (inexistente) espacio de nombres padre, y el tamaño del rango es el entero sin signo de 32 bits más grande. Esto deja 4294967295 (el valor -1 de 32 bits con signo) sin mapear. Esto es deliberado: (uid_t) -1 se usa en varias interfaces (por ejemplo, setreuid(2)) como una forma de especificar "ningún ID de usuario". Dejar (uid_t) -1 sin mapear e inutilizable garantiza que no habrá confusión al usar estas interfaces.

Definición de mapeos de IDs de usuario y grupo: escribir en uid_map y gid_map

Después de la creación de un nuevo espacio de nombres de usuario, el archivo uid_map de un proceso en el espacio de nombres se puede escribir una vez para definir el mapeo de IDs de usuario en el nuevo espacio de nombres de usuario. Un intento de escribir más de una vez en un archivo uid_map en un espacio de nombres de usuario falla con el error EPERM. Reglas similares se aplican a los archivos gid_map.

Las líneas escritas en uid_map (gid_map) deben cumplir con las siguientes reglas de validez:

•
Los tres campos deben ser números válidos, y el último campo debe ser mayor que 0.
•
Las líneas terminan con caracteres de nueva línea.
•
Hay un límite en el número de líneas en el archivo. Hasta Linux 4.14, este límite se fijó (arbitrariamente) en 5 líneas. Desde Linux 4.16, el límite es de 340 líneas. Además, el número de bytes escritos en el archivo debe ser menor que el tamaño de página del sistema, y la escritura debe realizarse al principio del archivo (es decir, no se pueden usar lseek(2) y pwrite(2) para escribir en desplazamientos distintos de cero en el archivo).
•
Los rangos de IDs de usuario (IDs de grupo) especificados en cada línea no pueden superponerse con los rangos en ninguna otra línea. En la implementación inicial (Linux 3.8), este requisito se cumplió mediante una implementación simplista que impuso el requisito adicional de que los valores tanto en el campo 1 como en el campo 2 de las líneas sucesivas debían estar en orden numérico ascendente, lo que impedía la creación de algunos mapas que de otro modo serían válidos. Desde Linux 3.9, esta limitación se ha eliminado, lo que permite cualquier conjunto válido de mapeos no superpuestos.
•
Se debe escribir al menos una línea en el archivo.

Las escrituras que violan las reglas anteriores fallan con el error EINVAL.

Para que un proceso pueda escribir en el archivo /proc/pid/uid_map (/proc/pid/gid_map), se deben cumplir todos los siguientes requisitos de permiso:

•
El proceso que escribe debe tener la capacidad CAP_SETUID (CAP_SETGID) en el espacio de nombres de usuario del proceso pid.
•
El proceso que escribe debe estar en el espacio de nombres de usuario del proceso pid o estar en el espacio de nombres de usuario padre del proceso pid.
•
Los IDs de usuario (IDs de grupo) mapeados deben tener a su vez un mapeo en el espacio de nombres de usuario padre.
•
Si se actualiza /proc/pid/uid_map para crear un mapeo que mapee el UID 0 en el espacio de nombres padre, entonces una de las siguientes opciones debe ser verdadera:
(a)
si el proceso que escribe está en el espacio de nombres de usuario padre, entonces debe tener la capacidad CAP_SETFCAP en ese espacio de nombres de usuario; o
(b)
si el proceso que escribe está en el espacio de nombres de usuario hijo

Reglas para escribir en uid_map y gid_map

•
En un nuevo espacio de nombres de usuario, para poder escribir en uid_map o gid_map, el proceso debe tener la capacidad CAP_GID (CAP_SETUID) en el espacio de nombres de usuario padre.
•
Si el proceso está escribiendo en uid_map o gid_map dentro del mismo espacio de nombres de usuario en el que se creó, o en un espacio de nombres hijo de este, entonces el proceso que creó el espacio de nombres de usuario debe haber tenido la capacidad CAP_SETFCAP cuando se creó el espacio de nombres.

Esta regla ha estado vigente desde Linux 5.12. Elimina un error de seguridad anterior por el cual un proceso UID 0 que carece de la capacidad CAP_SETFCAP, que es necesaria para crear un binario con capacidades de archivo con nombres de espacio (como se describe en capabilities(7)), podría, no obstante, crear dicho binario, mediante los siguientes pasos:

(1)
Crear un nuevo espacio de nombres de usuario con el mapeo de identidad (es decir, UID 0 en el nuevo espacio de nombres de usuario se mapea a UID 0 en el espacio de nombres padre), de modo que UID 0 en ambos espacios de nombres sea equivalente al mismo ID de usuario raíz.
(2)
Dado que el proceso hijo tiene la capacidad CAP_SETFCAP, podría crear un binario con capacidades de archivo con nombres de espacio que luego serían efectivas en el espacio de nombres de usuario padre (porque los IDs de usuario raíz son los mismos en los dos espacios de nombres).
•
Se aplica uno de los dos casos siguientes:
(a)
O bien el proceso de escritura tiene la capacidad CAP_SETUID (CAP_SETGID) en el espacio de nombres de usuario padre.
•
No se aplican restricciones adicionales: el proceso puede realizar mapeos a IDs de usuario (IDs de grupo) arbitrarios en el espacio de nombres de usuario padre.
(b)
O bien, en caso contrario, se aplican todas las siguientes restricciones:
•
Los datos escritos en uid_map (gid_map) deben consistir en una sola línea que mapee el ID de usuario efectivo del proceso de escritura (ID de grupo) en el espacio de nombres de usuario padre a un ID de usuario (ID de grupo) en el espacio de nombres de usuario.
•
El proceso de escritura debe tener el mismo ID de usuario efectivo que el proceso que creó el espacio de nombres de usuario.
•
En el caso de gid_map, el uso de la llamada al sistema setgroups(2) debe ser denegado primero escribiendo "deny" en el archivo /proc/pid/setgroups (ver más abajo) antes de escribir en gid_map.

Las escrituras que violen las reglas anteriores fallarán con el error EPERM.

Mapeos de ID de proyecto: projid_map

De manera similar a los mapeos de IDs de usuario y grupo, es posible crear mapeos de IDs de proyecto para un espacio de nombres de usuario. (Los IDs de proyecto se utilizan para cuotas de disco; ver setquota(8) y quotactl(2)).

Los mapeos de IDs de proyecto se definen escribiendo en el archivo /proc/pid/projid_map (presente desde Linux 3.7).

Las reglas de validez para escribir en el archivo /proc/pid/projid_map son las mismas que para escribir en el archivo uid_map; la violación de estas reglas hace que write(2) falle con el error EINVAL.

Las reglas de permisos para escribir en el archivo /proc/pid/projid_map son las siguientes:

•
El proceso de escritura debe estar en el espacio de nombres de usuario del proceso pid o en el espacio de nombres de usuario padre del proceso pid.
•
Los IDs de proyecto mapeados deben tener a su vez un mapeo en el espacio de nombres de usuario padre.

La violación de estas reglas hace que write(2) falle con el error EPERM.

Interacción con llamadas al sistema que cambian los UIDs o GIDs del proceso

En un espacio de nombres de usuario donde no se ha escrito en el archivo uid_map, las llamadas al sistema que cambian los IDs de usuario fallarán. De manera similar, si no se ha escrito en el archivo gid_map, las llamadas al sistema que cambian los IDs de grupo fallarán. Después de que se hayan escrito los archivos uid_map y gid_map, solo los valores mapeados pueden usarse en llamadas al sistema que cambian los IDs de usuario y grupo.

Para los IDs de usuario, las llamadas al sistema relevantes incluyen setuid(2), setfsuid(2), setreuid(2) y setresuid(2). Para los IDs de grupo, las llamadas al sistema relevantes incluyen setgid(2), setfsgid(2), setregid(2), setresgid(2) y setgroups(2).

Escribir "deny" en el archivo /proc/pid/setgroups antes de escribir en /proc/pid/gid_map deshabilitará permanentemente setgroups(2) en un espacio de nombres de usuario y permitirá escribir en /proc/pid/gid_map sin tener la capacidad CAP_SETGID en el espacio de nombres de usuario padre.

El archivo /proc/pid/setgroups

El archivo /proc/pid/setgroups muestra la cadena "allow" si a los procesos en el espacio de nombres de usuario que contiene el proceso pid se les permite emplear la llamada al sistema setgroups(2); muestra "deny" si setgroups(2) no está permitido en ese espacio de nombres de usuario. Tenga en cuenta que, independientemente del valor en el archivo /proc/pid/setgroups (y independientemente de las capacidades del proceso), las llamadas a setgroups(2) tampoco están permitidas si /proc/pid/gid_map aún no se ha establecido.

Un proceso privilegiado (uno con la capacidad CAP_SYS_ADMIN en el espacio de nombres) puede escribir cualquiera de las cadenas "allow" o "deny" en este archivo *antes* de escribir un mapeo de ID de grupo para este espacio de nombres de usuario en el archivo /proc/pid/gid_map. Escribir la cadena "deny" impide que cualquier proceso en el espacio de nombres de usuario emplee setgroups(2).

La esencia de las restricciones descritas en el párrafo anterior es que solo se permite escribir en /proc/pid/setgroups mientras se deniega la llamada a setgroups(2) porque /proc/pid/gid_map no se ha establecido. Esto asegura que un proceso no pueda pasar de un estado donde setgroups(2) está permitido a un estado donde setgroups(2) está denegado; un proceso solo puede pasar de que setgroups(2) esté deshabilitado a que setgroups(2) esté permitido.

El valor predeterminado de este archivo en el espacio de nombres de usuario inicial es "allow".

Una vez que se ha escrito en /proc/pid/gid_map (lo que tiene el efecto de habilitar setgroups(2) en el espacio de nombres de usuario), ya no es posible denegar setgroups(2) escribiendo "deny" en /proc/pid/setgroups (la escritura falla con el error EPERM).

Un espacio de nombres de usuario hijo hereda la configuración de /proc/pid/setgroups de su padre.

Si el archivo setgroups tiene el valor "deny", entonces la llamada al sistema setgroups(2) no puede ser rehabilitada posteriormente (escribiendo "allow" en el archivo) en este espacio de nombres de usuario. (Los intentos de hacerlo fallan con el error EPERM.) Esta restricción también se propaga a todos los espacios de nombres de usuario hijos de este espacio de nombres de usuario.

El archivo /proc/pid/setgroups se agregó en Linux 3.19, pero se incluyó en versiones anteriores de la serie de kernels estables, ya que aborda un problema de seguridad. El problema se refería a archivos con permisos como "rwx---rwx". Dichos archivos otorgan menos permisos a "grupo" de los que otorgan a "otro". Esto significa que descartar grupos usando setgroups(2) podría permitir que un proceso tenga acceso a archivos que antes no tenía. Antes de la existencia de los espacios de nombres de usuario, esto no era una preocupación, ya que solo un proceso privilegiado (uno con la capacidad CAP_SETGID) podía llamar a setgroups(2). Sin embargo, con la introducción de los espacios de nombres de usuario, se hizo posible que un proceso no privilegiado creara un nuevo espacio de nombres en el que el usuario tuviera todos los privilegios. Esto luego permitió que los usuarios anteriormente no privilegiados descartaran grupos y, por lo tanto, obtuvieran acceso a archivos que antes no tenían. El archivo /proc/pid/setgroups se agregó para abordar este problema de seguridad, al denegar cualquier vía para que un proceso no privilegiado descarte grupos con setgroups(2).

IDs de usuario y grupo no mapeados

Hay varios lugares donde un ID de usuario (ID de grupo) no mapeado puede ser expuesto al espacio de usuario. Por ejemplo, el primer proceso en un nuevo espacio de nombres de usuario puede llamar a getuid(2) antes de que se haya definido un mapeo de ID de usuario para el espacio de nombres. En la mayoría de estos casos, un ID de usuario no mapeado se convierte al ID de usuario (ID de grupo) de desbordamiento; el valor predeterminado para el ID de usuario (ID de grupo) de desbordamiento es 65534. Ver las descripciones de /proc/sys/kernel/overflowuid y /proc/sys/kernel/overflowgid en proc(5).

Los casos en los que los IDs no mapeados se mapean de esta manera incluyen llamadas al sistema que devuelven IDs de usuario (getuid(2), getgid(2) y similares), credenciales pasadas a través de un socket de dominio UNIX, credenciales devueltas por stat(2), waitid(2) y las operaciones de control IPC_STAT de IPC de System V, credenciales expuestas por /proc/pid/status y los archivos en /proc/sysvipc/*, credenciales devueltas a través del campo si_uid en el siginfo_t recibido con una señal (ver sigaction(2)), credenciales escritas en el archivo de contabilidad de procesos (ver acct(5)), y credenciales devueltas con notificaciones de cola de mensajes POSIX (ver mq_notify(3)).

Acceso a archivos

Para determinar los permisos cuando un proceso no privilegiado accede a un archivo, las credenciales del proceso (UID, GID) y las credenciales del archivo se mapean retroactivamente a lo que serían en el espacio de nombres de usuario inicial y luego se comparan para determinar los permisos que el proceso tiene sobre el archivo. Lo mismo ocurre con otros objetos que emplean el modelo de accesibilidad de credenciales más máscara de permisos, como los objetos IPC de System V.

Funcionamiento de capacidades relacionadas con archivos

Ciertas capacidades permiten a un proceso eludir varias restricciones impuestas por el kernel al realizar operaciones en archivos propiedad de otros usuarios o grupos. Estas capacidades son: CAP_CHOWN, CAP_DAC_OVERRIDE, CAP_DAC_READ_SEARCH, CAP_FOWNER y CAP_FSETID.

Dentro de un espacio de nombres de usuario, estas capacidades permiten a un proceso eludir las reglas si el proceso tiene la capacidad relevante sobre el archivo, lo que significa que:

•
el proceso tiene la capacidad efectiva relevante en su espacio de nombres de usuario; y
•
el ID de usuario y el ID de grupo del archivo tienen mapeos válidos en el espacio de nombres de usuario.

La capacidad CAP_FOWNER se trata de forma algo excepcional: permite a un proceso eludir las reglas correspondientes siempre que al menos el ID de usuario del archivo tenga un mapeo en el espacio de nombres de usuario (es decir, no es necesario que el ID de grupo del archivo tenga un mapeo válido).

Programas Set-user-ID y set-group-ID

Cuando un proceso dentro de un espacio de nombres de usuario ejecuta un programa set-user-ID (set-group-ID), el ID de usuario (grupo) efectivo del proceso dentro del espacio de nombres se cambia al valor que se mapea para el ID de usuario (grupo) del archivo. Sin embargo, si el ID de usuario *o* el ID de grupo del archivo no tiene ningún mapeo dentro del espacio de nombres, el bit set-user-ID (set-group-ID) se ignora silenciosamente: el nuevo programa se ejecuta, pero el ID de usuario (grupo) efectivo del proceso permanece sin cambios. (Esto refleja la semántica de ejecutar un programa set-user-ID o set-group-ID que reside en un sistema de archivos montado con la bandera MS_NOSUID, como se describe en mount(2).)

Misceláneo

Cuando los IDs de usuario y grupo de un proceso se pasan a través de un socket de dominio UNIX a un proceso en un espacio de nombres de usuario diferente (ver la descripción de SCM_CREDENTIALS en unix(7)), se traducen a los valores correspondientes según los mapeos de ID de usuario y grupo del proceso receptor.

Disponibilidad

El uso de espacios de nombres de usuario requiere un kernel que esté configurado con la opción CONFIG_USER_NS. Los espacios de nombres de usuario requieren soporte en una variedad de subsistemas en todo el kernel. A partir de Linux 3.8, la mayoría de los subsistemas relevantes soportaban espacios de nombres de usuario, pero una serie de sistemas de archivos no tenían la infraestructura necesaria para mapear IDs de usuario y grupo entre espacios de nombres de usuario. Linux 3.12 añadió soporte para el último de los principales sistemas de archivos no soportados, XFS.

NOMBRE


user_namespaces - namespaces de usuarios de Linux






DESCRIPCIÓN


Un namespace de usuario es un namespace de Linux que aísla los
    identificadores de usuario y grupo. Cuando un proceso crea un nuevo namespace
    de usuario (usando clone(2) o unshare(2)
    con la bandera CLONE_NEWUSER), el proceso se convierte en
    el administrador del nuevo namespace. Dentro de este namespace, el proceso puede
    tener un ID de usuario (UID) y un ID de grupo (GID) de nivel superior (normalmente
    0, que corresponde a root), mientras que fuera del namespace, el proceso tiene
    un UID y GID no privilegiado.


Un namespace de usuario afecta a los siguientes identificadores y
    operaciones:


    
    
  • Los IDs de usuario y grupo que ve un proceso dentro del namespace.
    • 
    
  • La capacidad de poseer la mayoría de los recursos (como sockets de red
        y volúmenes de almacenamiento).
    • 
    
  • La capacidad de modificar ciertos archivos en el directorio /proc/sys/net.
    • 
    
  • La capacidad de instalar la mayoría de las capacidades de Linux.
    • 
    
  • La capacidad de adjuntarse a otros procesos usando ptrace(2).
    • 
    
  • La capacidad de realizar ciertas operaciones de depuración y auditoría.
    • 
    
  • La capacidad de instalar nuevas opciones de montaje y sistemas de
        archivos.
    • 
    
  • La capacidad de montar y desmontar sistemas de archivos.
    • 
    
  • La capacidad de modificar el nombre de host y el dominio de red (UTS
        namespace).
    • 



El propósito principal de un namespace de usuario es permitir que un
    usuario no privilegiado ejecute un proceso con privilegios de root dentro de
    un entorno aislado, sin otorgarle realmente privilegios de root en el sistema
    host.


El mapeo de IDs de usuario y grupo entre el namespace padre y el
    hijo se gestiona a través de los archivos especiales:



    
/proc/PID/uid_map

    
Mapea los IDs de usuario en el namespace del proceso PID a los IDs de usuario
        en el namespace padre.

    
/proc/PID/gid_map

    
Mapea los IDs de grupo en el namespace del proceso PID a los IDs de grupo
        en el namespace padre.




Estos archivos solo se pueden escribir una vez por proceso. Para
    actualizar los mapeos, el proceso padre debe escribir en el archivo
    correspondiente. El formato de cada línea es:


        ID_en_namespace_hijo  ID_en_namespace_padre  longitud



Por ejemplo, si un proceso tiene UID 0 en el namespace hijo y UID
    1000 en el namespace padre, y la longitud es 1, esto significa que el UID 0
    en el hijo se mapea al UID 1000 en el padre.


La creación de un nuevo namespace de usuario a menudo se combina con
    la creación de otros namespaces (como el namespace de montaje, el namespace
    de red, el namespace PID, etc.) para proporcionar un aislamiento más completo.






ESTÁNDARES


El namespace de usuario es una característica del kernel de Linux y
    no está estandarizado por ninguna organización externa.






NOTAS


El archivo /proc/PID/setgroups controla si
    el proceso con PID puede llamar a la llamada al sistema setgroups(2).
    Por defecto, este archivo contiene "allow". Si se escribe "deny" en este
    archivo, el proceso ya no podrá llamar a setgroups(2).
    Esto es importante porque setgroups(2) se utiliza
    para eliminar grupos de la lista de grupos efectivos de un proceso.


Para que los mapeos de UID y GID funcionen correctamente, el archivo
    /proc/PID/setgroups debe establecerse en "deny" antes
    de que se actualicen los mapeos de GID. Esto se debe a que la llamada a
    setgroups(2) puede fallar si el UID del proceso
    no se ha mapeado a un UID privilegiado en el namespace padre.


Las herramientas como newuidmap(1)
    y newgidmap(1) se utilizan para configurar
    los mapeos de UID y GID en los namespaces de usuario.


Los archivos /etc/subuid y /etc/subgid
    definen rangos de UIDs y GIDs que un usuario puede asignar a los namespaces de
    usuario que crea.


La llamada al sistema clone(2) con la
    bandera CLONE_NEWUSER puede usarse para crear un nuevo
    namespace de usuario. La llamada al sistema unshare(2)
    con la bandera CLONE_NEWUSER puede usarse para mover
    el proceso actual a un nuevo namespace de usuario.

El siguiente ejemplo muestra cómo crear un nuevo namespace de usuario

    namespace, pero será un usuario no privilegiado fuera del namespace.


#include <err.h>
#include <errno.h>
#include <fcntl.h>
#include <sched.h>
#include <stdio.h>
#include <string.h>
#include <sys/wait.h>
#include <unistd.h>

#define STACK_SIZE (1024 * 1024)
static char child_stack[STACK_SIZE];

struct child_args {
    int pipe_fd[2];
    char **argv;
};

static int
childFunc(void *arg)
{
    struct child_args *args = arg;
    char ch;

    /* Wait until the parent has updated the UID and GID mappings.  */
    close(args->pipe_fd[1]); /* Close our descriptor for the write end of the pipe */
    if (read(args->pipe_fd[0], &ch, 1) != 0) {
        fprintf(stderr, "Failure in child: read from pipe returned != 0\n");
        exit(EXIT_FAILURE);
    }
    close(args->pipe_fd[0]);

    /* Execute a shell command.  */
    printf("About to exec %s\n", args->argv[0]);
    execvp(args->argv[0], args->argv);
    err(EXIT_FAILURE, "execvp");
}

static void
update_map(const char *map_file, const char *map_data)
{
    int fd, len;
    char buf[100];

    fd = open(map_file, O_RDWR);
    if (fd == -1) {
        fprintf(stderr, "ERROR: open %s: %s\n", map_file, strerror(errno));
        return;
    }
    len = snprintf(buf, sizeof(buf), "%s", map_data);
    if (write(fd, buf, len) == -1)
        fprintf(stderr, "ERROR: write %s: %s\n", map_file, strerror(errno));
    close(fd);
}

static void
proc_setgroups_write(int child_pid, const char *str)
{
    char setgroups_path[PATH_MAX];
    int fd;

    snprintf(setgroups_path, PATH_MAX, "/proc/%jd/setgroups",
            (intmax_t) child_pid);
    fd = open(setgroups_path, O_RDWR);
    if (fd == -1) {
        /* May not exist on systems that don't support /proc/PID/setgroups */
        if (errno != ENOENT)
            fprintf(stderr, "ERROR: open %s: %s\n", setgroups_path,
                strerror(errno));
        return;
    }
    if (write(fd, str, strlen(str)) == -1)
        fprintf(stderr, "ERROR: write %s: %s\n", setgroups_path,
            strerror(errno));
    close(fd);
}

        case 'z': map_zero = 1;                 break;
        case 'M': uid_map = optarg;             break;
        case 'G': gid_map = optarg;             break;
        case 'U': flags |= CLONE_NEWUSER;       break;
        default:  usage(argv[0]);

    if (pipe(args.pipe_fd) == -1)

                    (intmax_t) getuid());

    }

    if (gid_map != NULL || map_zero) {
        proc_setgroups_write(child_pid, "deny");
        snprintf(map_path, PATH_MAX, "/proc/%jd/gid_map",
                (intmax_t) child_pid);
        if (map_zero) {
            snprintf(map_buf, MAP_BUF_SIZE, "0 %ld 1",
                    (intmax_t) getgid());
            gid_map = map_buf;
        }
        update_map(map_path, gid_map);
    }

    /* Close the write end of the pipe, to signal to the child. */
    close(args.pipe_fd[1]);

    if (waitpid(child_pid, NULL, 0) == -1)      /* Wait for child */
        err(EXIT_FAILURE, "waitpid");

    if (verbose)
        printf("%s: terminating\n", argv[0]);

    exit(EXIT_SUCCESS);
}

// Placeholder for usage function
void usage(const char *prog_name) {
    fprintf(stderr, "Usage: %s [-imnpuUv] [-M uid_map] [-G gid_map] command [args...]\n", prog_name);
    exit(EXIT_FAILURE);
}
