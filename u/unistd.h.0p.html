PRÓLOGO

Esta página del manual es parte del Manual del programador POSIX. La implementación de Linux de esta interfaz puede diferir (consulte la página del manual de Linux correspondiente para conocer los detalles del comportamiento de Linux), o la interfaz puede no estar implementada en Linux.

NOMBRE

unistd.h — constantes y tipos simbólicos estándar

SINOPSIS

#include <unistd.h>

DESCRIPCIÓN

El archivo de cabecera <unistd.h> define varias constantes simbólicas y tipos, y declara varias funciones. Los valores reales de las constantes no se especifican, excepto como se muestra. El contenido de este archivo de cabecera se muestra a continuación.

Macros de prueba de versión

El archivo de cabecera <unistd.h> definirá las siguientes constantes simbólicas. Los valores serán adecuados para su uso en directivas de preprocesamiento #if.

_POSIX_VERSION

Valor entero que indica la versión del estándar (enlace de lenguaje C) con la que cumple la implementación. Para implementaciones que cumplen con POSIX.1‐2008, el valor será 200809L.
_POSIX2_VERSION

Valor entero que indica la versión del Volumen de Shell y Utilidades de POSIX.1 con la que cumple la implementación. Para implementaciones que cumplen con POSIX.1‐2008, el valor será 200809L. Para implementaciones de perfiles que definen _POSIX_SUBPROFILE (ver Sección 2.1.5.1, Consideraciones sobre subperfiles) en <unistd.h>, _POSIX2_VERSION puede quedar indefinido o definirse con el valor -1 para indicar que el Volumen de Shell y Utilidades de POSIX.1 no se admite. En este caso, una llamada a sysconf(_SC_2_VERSION) devolverá 200809L o -1, indicando si el Volumen de Shell y Utilidades de POSIX.1 se admite o no, respectivamente, en tiempo de ejecución.

El archivo de cabecera <unistd.h> definirá la siguiente constante simbólica solo si la implementación admite la opción XSI; ver Sección 2.1.4, Cumplimiento de XSI. Si se define, su valor será adecuado para su uso en directivas de preprocesamiento #if.

_XOPEN_VERSION

Valor entero que indica la versión de la Guía de Portabilidad X/Open con la que cumple la implementación. El valor será 700.

Constantes para Opciones y Grupos de Opciones

Las siguientes constantes simbólicas, si se definen en <unistd.h>, tendrán un valor de -1, 0 o mayor, a menos que se especifique lo contrario a continuación. Para implementaciones de perfiles que definen _POSIX_SUBPROFILE (ver Sección 2.1.5.1, Consideraciones sobre subperfiles) en <unistd.h>, las constantes descritas a continuación como que siempre tienen un valor mayor que cero no necesitan definirse y, si se definen, pueden tener un valor de -1, 0 o mayor. Los valores serán adecuados para su uso en directivas de preprocesamiento #if.

Si una constante simbólica no está definida o está definida con el valor -1, la opción no se admite para la compilación. Si está definida con un valor mayor que cero, la opción siempre se admitirá cuando la aplicación se ejecute. Si está definida con el valor cero, la opción se admitirá para la compilación y es posible que se admita o no en tiempo de ejecución. Ver Sección 2.1.6, Opciones para obtener más información sobre los requisitos de cumplimiento de estas tres categorías de soporte.

Constantes Simbólicas de Configuración del Sistema

Los siguientes símbolos, definidos en <unistd.h>, se utilizan para indicar la presencia o ausencia de ciertas características del sistema o para indicar el nivel de conformidad con los estándares POSIX. Si estos símbolos se definen con un valor de -1, indica que la característica no está soportada. Si se definen con un valor distinto de -1 (incluido 0 en algunos casos), indica que la característica está soportada. APPLICATION USAGE

POSIX.1‐2008 only describes the behavior of systems that claim conformance to it. However, application developers who want to write applications that adapt to other versions of this standard (or to systems that do not conform to any POSIX standard) may find it useful t

o codifíquelos para que compilen condicionalmente código diferente dependiendo del valor de _POSIX_VERSION, por ejemplo:

#if _POSIX_VERSION >= 200112L
/* Usa la función más nueva que maneja archivos grandes. */
off_t pos=ftello(fp);
#else
/* O esta es una versión antigua de POSIX, o _POSIX_VERSION
   ni siquiera está definida, así que usa la función tradicional. */
long pos=ftell(fp);
#endif

Las versiones anteriores de POSIX.1‐2008 y de la Single UNIX Specification se pueden identificar mediante las siguientes macros:

Estándar POSIX.1‐1988

_POSIX_VERSION==198808L
Estándar POSIX.1‐1990

_POSIX_VERSION==199009L
Estándar ISO POSIX‐1:1996

_POSIX_VERSION==199506L
Single UNIX Specification, Version 1

_XOPEN_UNIX y _XOPEN_VERSION==4
Single UNIX Specification, Version 2

_XOPEN_UNIX y _XOPEN_VERSION==500
ISO POSIX‐1:2001 y Single UNIX Specification, Version 3

_POSIX_VERSION==200112L, además (si se soporta la opción XSI) _XOPEN_UNIX y _XOPEN_VERSION==600

POSIX.1‐2008 no hace ningún intento de definir la interacción binaria de aplicaciones con el sistema operativo subyacente. Sin embargo, a los desarrolladores de aplicaciones les puede resultar útil consultar _SC_VERSION en tiempo de ejecución a través de sysconf() para determinar si la versión actual del sistema operativo soporta la funcionalidad necesaria, como en el siguiente fragmento de programa:

if (sysconf(_SC_VERSION) < 200809L) {
    fprintf(stderr, "Se requiere sistema POSIX.1-2008, terminando \n");
    exit(1);
}

Las nuevas aplicaciones no deben usar _XOPEN_SHM ni _XOPEN_ENH_I18N.

FUNDAMENTO

A medida que evolucionó POSIX.1‐2008, ciertas opciones se estandarizaron lo suficiente como para concluir que simplemente requerir una de las opciones era más simple que retener la opción. Sin embargo, por motivos de retrocompatibilidad, se conservan las banderas de opción (con valores constantes requeridos).

Macros de prueba de versión

Los desarrolladores del estándar consideraron alterar la definición de _POSIX_VERSION y eliminar _SC_VERSION de la especificación de sysconf(), ya que la utilidad para una aplicación se consideraba mínima por algunos, y ya que la implementación de la funcionalidad es potencialmente problemática. Sin embargo, reconocieron que el soporte para binarios de aplicaciones existentes es una preocupación para los fabricantes, los desarrolladores de aplicaciones y los usuarios de implementaciones que cumplen con POSIX.1‐2008.

Si bien el ejemplo que utiliza _SC_VERSION en la sección USAGE DE APLICACIÓN no proporciona el mayor grado de utilidad imaginable para el desarrollador o usuario de la aplicación, es discutiblemente mejor que un archivo core o algún otro resultado igualmente oscuro. (También es posible que las implementaciones codifiquen y reconozcan binarios de aplicaciones compilados en varios entornos compatibles con POSIX.1 y modifiquen la semántica del sistema subyacente para cumplir con las expectativas de la aplicación). Por las razones descritas en los párrafos anteriores y en la sección USAGE DE APLICACIÓN, los desarrolladores del estándar optaron por conservar la funcionalidad _POSIX_VERSION y _SC_VERSION.

Constantes simbólicas en tiempo de compilación para opciones de todo el sistema

POSIX.1‐2008 incluye soporte en ciertas áreas para la política recién adoptada que rige las opciones y los stubs.

Esta política proporciona flexibilidad a las implementaciones en cuanto a cómo soportan las opciones. También especifica cómo las aplicaciones que cumplen pueden adaptarse a diferentes implementaciones que soportan diferentes conjuntos de opciones. Permite lo siguiente:

1.
Si una implementación no tiene interés en soportar una opción, no tiene que proporcionar nada asociado con esa opción más allá del anuncio de que no la soporta.
2.
Una implementación puede soportar una versión parcial o incompatible de una opción (como una extensión no estándar) siempre que no afirme soportar la opción.
3.
Una aplicación puede determinar si la opción es compatible. Una aplicación estrictamente compatible debe comprobar este mecanismo de anuncio antes de utilizar cualquier cosa asociada con la opción.

Hay una implicación importante de esta política. POSIX.1‐2008 no puede dictar el comportamiento de las interfaces asociadas con una opción cuando la implementación no afirma soportarla. En particular, no puede exigir que una función asociada con una opción no soportada falle si no se comporta según lo especificado. Sin embargo, esta política no impide que un estándar exija que ciertas funciones estén siempre presentes, pero que siempre fallen en algunas implementaciones. La función setpgid() en el estándar POSIX.1‐1990, por ejemplo, se considera apropiada.

Los estándares POSIX incluyen varias opciones, y el soporte en lenguaje C para una opción implica que la implementación debe proporcionar tipos de datos e interfaces de funciones. Una aplicación debe poder descubrir si la implementación soporta cada opción.

Cualquier aplicación debe considerar los siguientes tres casos para cada opción:

1.
Opción nunca soportada.

La implementación anuncia en tiempo de compilación que la opción nunca será soportada. En este caso, no es necesario que la implementación proporcione ninguno de los tipos de datos o interfaces de funciones que se proporcionan solo como parte de la opción. La implementación puede proporcionar tipos de datos y funciones similares a los definidos por POSIX.1‐2008, pero no hay garantía de un comportamiento particular.

2.
Opción siempre soportada.

La implementación anuncia en tiempo de compilación que la opción siempre será soportada. En este caso, todos los tipos de datos e interfaces de funciones estarán disponibles y operarán según lo especificado.

3.
Opción puede o no ser soportada.

Algunas implementaciones pueden no proporcionar un mecanismo para especificar el soporte de opciones en tiempo de compilación. Además, la implementación puede no ser capaz o no estar dispuesta a especificar el soporte o la no compatibilidad en tiempo de compilación. En cualquier caso, cualquier aplicación que pueda usar la opción en tiempo de ejecución debe poder compilar y ejecutar. La implementación debe proporcionar, en tiempo de compilación, todos los tipos de datos e interfaces de funciones necesarios para permitir esto. En esta situación, debe existir un mecanismo que permita a la aplicación consultar, en tiempo de ejecución, si la opción es compatible. Si la aplicación intenta utilizar la opción cuando no es compatible, el resultado no está especificado a menos que se especifique explícitamente lo contrario en POSIX.1‐2008.
