NOMBRE

unlang - Lenguaje unlang de procesamiento de FreeRADIUS

DESCRIPCIÓN

FreeRADIUS soporta un lenguaje de procesamiento simple en sus archivos de configuración. Lo llamamos un "lenguaje unlang" porque la intención NO es crear otro lenguaje de programación. Si necesita algo más complicado de lo que se describe aquí, sugerimos usar los módulos Perl o Python rlm_perl o rlm_python.

El objetivo del lenguaje es permitir la escritura de políticas simples con un mínimo esfuerzo. Dichas políticas se aplican cuando se está procesando una solicitud. Las solicitudes se procesan a través de servidores virtuales (incluido el predeterminado), en las secciones tituladas "authorize", "authenticate", "post-auth", "preacct", "accounting", "pre-proxy", "post-proxy" y "session".

Estas políticas no se pueden utilizar en ninguna otra parte de los archivos de configuración, como la configuración de módulos o clientes.

PALABRAS CLAVE

Las palabras clave del lenguaje son una combinación de palabras clave predefinidas y referencias a nombres de módulos cargables. Aquí solo documentamos las palabras clave predefinidas.

Sujeto a algunas limitaciones descritas a continuación, cualquier palabra clave puede aparecer en cualquier contexto. El lenguaje consiste en una serie de entradas, cada una en una línea. Cada entrada comienza con una palabra clave. Las entradas se organizan en listas. El procesamiento del lenguaje es línea por línea, desde el principio de la lista hasta el final. Las acciones se ejecutan por palabra clave.

nombre-módulo[.nombre-sección]
Una referencia al módulo con nombre. Cuando el procesamiento llega a este punto, se llama al módulo precompilado. El módulo puede tener éxito o fallar, y devolverá un estado a "unlang" si es así. Este estado se puede probar en una condición. Consulte el texto "Condiciones simples" en la sección CONDICIONES y CÓDIGOS DE RETORNO DE MÓDULOS, más abajo. Si se proporciona un nombre de sección, provocará que el módulo se ejecute como si estuviera listado en la sección con nombre. 
	chap  # llama al módulo CHAP
	sql   # llama al módulo SQL
	...
if

Comprueba una condición particular. Si es verdadera, se procesa el bloque después de la condición. De lo contrario, el bloque se ignora. Consulte CONDICIONES, más abajo, para obtener documentación sobre el formato de las condiciones. 
	if (condición) {
		...
	}
else

Define un bloque que se ejecutará solo si la condición "if" anterior devolvió falso. 
	else {
		...
	}
elsif

Define un bloque que se ejecutará solo si la condición "if" anterior devolvió falso, y si la condición especificada se evalúa como verdadera. 
	elsif (condición) {
		...
	}
foreach

Itera sobre los valores de un atributo, ejecutando el bloque para cada valor. El valor de retorno del bloque es el valor de retorno de la última sentencia ejecutada. El bucle se puede salir anticipadamente usando la palabra clave "break". A diferencia de otros lenguajes, "break" aquí significa "salir del bucle en la próxima iteración", no "salir del bucle ahora". El resultado es que cualquier sentencia después de la palabra clave "break" seguirá siendo ejecutada. Recomendamos usar "break" solo cuando sea la última sentencia en un bloque "foreach".

Dentro del bloque "foreach", el atributo sobre el que se itera se puede referenciar como "Foreach-Variable-#". Donde "#" es la profundidad del bucle, comenzando en "0". Por ejemplo, "Foreach-Variable-0". Los bucles se pueden anidar hasta ocho (8) niveles de profundidad, aunque no se recomienda.

	foreach &Referencia-Atributo {
		...
	}
switch

Una sentencia "switch" toma un argumento y contiene una serie de sentencias "case". Cuando se encuentra una sentencia "switch", el argumento de la "switch" se evalúa en turno contra el argumento de cada sentencia "case". Se ejecuta la primera sentencia "case" que coincide. Todas las demás sentencias "case" se ignoran. Se puede definir una sentencia "case" predeterminada, omitiendo su argumento.

Si el argumento es una cadena entre comillas dobles (por ejemplo, "%{exec:1 + 2}"), se expande como se describe en la sección TIPOS DE DATOS, más abajo. Luego, la coincidencia se realiza sobre la cadena devuelta por la expansión. Si el argumento es una referencia a un atributo (por ejemplo, &User-Name), entonces la coincidencia se realiza sobre el valor de ese atributo. De lo contrario, el argumento se toma como una cadena literal y la coincidencia se realiza mediante una comparación simple.

No puede aparecer ninguna sentencia que no sea "case" dentro de un bloque "switch".

	switch <argumento> {
		...
	}
case

Proporciona un marcador de posición que coincide con el argumento de una sentencia "switch" principal.

Una sentencia "case" no puede aparecer fuera de un bloque "switch".

Si el argumento es una cadena entre comillas dobles (por ejemplo, "%{exec:1 + 2}"), se expande como se describe en la sección TIPOS DE DATOS, más abajo. Luego, la coincidencia se realiza sobre la cadena devuelta por la expansión. Si el argumento es una referencia a un atributo (por ejemplo, &User-Name), entonces la coincidencia se realiza sobre el valor de ese atributo. De lo contrario, el argumento se toma como una cadena literal y la coincidencia se realiza mediante una comparación simple.

	case <argumento> {
		...
	}

Se puede definir una entrada predeterminada omitiendo el argumento, como se muestra a continuación. Esta entrada se utilizará si ninguna otra entrada "case" coincide. Solo puede existir una entrada predeterminada en una sección "switch".

	case {
		...
	}
update

Actualiza una lista de atributos particular, basándose en los atributos dados en el bloque actual. 
	update <lista> {
		&Referencia-Atributo = valor
		...
	}

La <lista> puede ser "request", "reply", "proxy-request", "proxy-reply", "coa", "disconnect", "session-state" o "control". A partir de la Versión 3, se puede omitir la <lista>, en cuyo caso se asume "request".

La lista "control" es la lista de atributos mantenidos internamente por el servidor que controla cómo el servidor procesa la solicitud. Cualquier atributo que no vaya en un paquete de red se colocará generalmente en la lista "control".

Para los métodos EAP con sesiones de autenticación tunelizadas (es decir, PEAP y EAP-TTLS), la sesión del túnel interno también puede referenciar "outer.request", "outer.reply" y "outer.control". Dichas referencias le permiten acceder a la lista relevante en la sesión del túnel exterior.

Las secciones "coa" y "disconnect" solo se pueden usar cuando el servidor recibe una Access-Request o Accounting-Request. Use "request" y "reply" en lugar de "coa" cuando el servidor reciba un paquete CoA-Request o Disconnect-Request.

Agregar uno o más atributos a la lista "coa" o "disconnect" hace que el servidor origine un paquete CoA-Request o Disconnect-Request. Ese paquete se envía cuando la Access-Request o Accounting-Request actual ha finalizado, y se ha enviado una respuesta al NAS. Vea raddb/sites-available/originate-coa para obtener información adicional.

La lista "session-state" se usa principalmente para EAP. Los atributos colocados en la lista "session-state" se guardan para el siguiente paquete en la sesión. Se recuperan automáticamente cuando se recibe el siguiente paquete.

CONDITIONS

Conditions are used to control the flow of policy statements. They evaluate to either true or false. Conditions can be nested, and can be combined using logical operators.

The simplest form of a condition is a comparison. Comparisons involve two operands and a comparison operator.

(operand1 operator operand2)

The operators are:

=
Equal to. Case-sensitive.
!=
Not equal to. Case-sensitive.
<
Less than. Case-sensitive.
<=
Less than or equal to. Case-sensitive.
>
Greater than. Case-sensitive.
>=
Greater than or equal to. Case-sensitive.
=~
Regular expression match. The right-hand operand must be a regular expression enclosed in slashes (e.g. /regex/).
!~
Not a regular expression match. The right-hand operand must be a regular expression enclosed in slashes (e.g. /regex/).

The operands can be attribute references, strings, or numbers. Attribute references are faster and more efficient.

(User-Name == "%{Filter-Id}")

The conditions will check only the first occurrence of an attribute. If there is more than one instance of an attribute, the following syntax should be used:

(&Attribute-Name[*] == "foo")

Using the "[*]" syntax means that it checks all of the instances of the named attribute. If one attribute matches, the condition succeeds. If none match, the condition fails.

Casts
(<type>foo == bar)

The left-hand-side of a condition can be "cast" to a specific data type. The data type must be one which is valid for the dictionaries. e.g. "integer", "ipaddr", etc.

The comparison is performed in a type-safe way, as with "Inter-Attribute Comparisons", above. Both sides of the condition are parsed into temporary attributes, and the attributes compared via type-specific methods. The temporary attributes have no other effect, and are not saved anywhere.

Casting allows conditions to perform type-specific comparisons. In previous versions of the server, the data would have to be manually placed into an intermediate attribute (or attributes), and then the attribute (or attributes) compared. The use of a cast allows for simpler policies.

Casts are allowed only on the left-hand side argument of a condition.

Conditions may be nested to any depth, subject only to line length limitations (8192 bytes).

DATA TYPES

There are only a few data types supported in the language. Reference to attributes, numbers, and strings. Any data type can appear in stand-alone condition, in which case they are evaluated as described in "Simple conditions", above. They can also appear (with some exceptions noted below) on the left-hand or on the right-hand side of a comparison.

numbers
Numbers are composed of decimal digits. Floating point, hex, and octal numbers are not supported. The maximum value for a number is machine-dependent, but is usually 32-bits, including one bit for a sign value.

word

Text that is not enclosed in quotes is interpreted differently depending on where it occurs in a condition. On the left hand side of a condition, it is interpreted as a reference to an attribute. On the right hand side, it is interpreted as a simple string, in the same manner as a single-quoted string.

Using attribute references permits limited type-specific comparisons, as seen in the examples below.

	if (&User-Name == "bob") {
		...
	if (&Framed-IP-Address > 127.0.0.1) {
		...
	if (&Service-Type == Login-User) {
"strings"
Double-quoted strings are expanded by inserting the value of any attributes (see ATTRIBUTE REFERENCES, below) before being evaluated. If the result is a number it is evaluated in a numerical context.

String length is limited by line-length, usually about 8000 characters. A double quote character can be used in a string via the normal back-slash escaping method. ("like \"this\" !")

'strings'
Single-quoted strings are evaluated as-is. Their values are not expanded as with double-quoted strings above, and they are not interpreted as attribute references.
`strings`
Back-quoted strings are evaluated by expanding the contents of the string, as described above for double-quoted strings. The resulting command given inside of the string in a sub-shell, and taking the output as a string. This behavior is much the same as that of Unix shells.

Note that for security reasons, the input string is split into command and arguments before string expansion is done.

For performance reasons, we suggest that the use of back-quoted strings be kept to a minimum. Executing external programs is relatively expensive, and executing a large number of programs for every request can quickly use all of the CPU time in a server. If you believe that you need to execute many programs, we suggest finding alternative ways to achieve the same result. In some cases, using a real language may be sufficient.

/regex/im
These strings are valid only on the right-hand side of a comparison, and then only when the comparison operator is "=~" or "!~". They are regular expressions, as implemented by the local regular expression library on the system. This is usually Posix regular expressions.

The trailing 'i' is optional, and indicates that the regular expression match should be done in a case-insensitive fashion.

The trailing 'm' is also optional, and indicates that carrot '^' and dollar '$' anchors should match on new lines as well as at the start and end of the subject string.

If the comparison operator is "=~", then parentheses in the regular expression will define variables containing the matching text, as described below in the ATTRIBUTE REFERENCES section.

EXPANSIONS

Attributes are expanded using the ATTRIBUTE REFERENCE syntax described above, and surrounding the reference with "%{...}"

%{Attribute-Reference}

The result will be a string which contains the value of the attribute which was referenced, as a printable string. If the attribute does not exist, the result will be an empty string.

Results of regular expression matches

If a regular expression match has previously been performed, then the special variable %{0} will contain a copy of the matched portion of the input string. The variables %{1} through %{32} will contain the substring matches, starting from the left-most capture group, onwards. If there are more than 32 capture groups, the additional results will not be accessible. If the server is built with libpcre, the results of named capture groups are available using the "%{regex:capture group}" expansion. They will also be accessible using the variables described above. Every time a regular expression is evaluated, whether it matches or not, the capture group values will be cleared.

Obtaining results from databases

It is useful to query a database for some information, and to use the result in a condition. The following syntax will call a module, pass it the given string, and replace the string expansion with the resulting string returned from the module. 
%{module: string ...}

The syntax of the string is module-specific. Please read the module documentation for additional details.

Conditional Syntax

Conditional syntax similar to that used in Unix shells may also be used.
%{%{Foo}:-bar}
If %{Foo} has a value, returns that value.
Otherwise, returns literal string "bar".
%{%{Foo}:-%{Bar}}
If %{Foo} has a value, returns that value.
Otherwise, returns the expansion of %{Bar}.

These conditional expansions can be nested to almost any depth, such as with %{%{One}:-%{%{Two}:-%{Three}}}

String lengths and arrays

Similar to a Unix shell, there are ways to reference string lengths, and the second or more instance of an attribute in a list. If you need more than this functionality, we suggest using a real language.
%{strlen:string}
The number of characters in "string". If "string" does not exist, then the length also does not exist, instead of being zero.

The "string" is expanded before the length is taken.

%{integer:Attribute-Name}
The integer value of the Attribute-Name, instead of the enumerated name.

e.g. If a request contains "Service-Type = Login-User", the expansion of %{integer:Service-Type} will yield "1".

%{hex:Attribute-Name}
The hex value of the Attribute-Name, as a series of hex digits.

e.g. If a request contains "Framed-IP-Address = 127.0.0.1", the expansion of %{hex:Framed-IP-Address} will yield "0x7f000001".

%{Attribute-Name[#]}
The number of instances of Attribute-Name.

e.g. If a request contains "User-Name = bob", the expansion of %{User-Name[#]} will yield "1".

%{Attribute-Name[*]}
All values of Attribute-Name, concatenated together with ',' as the separator.
%{List-Name:[#]}
The number of attributes in the named list.
%{List-Name:[*]}
All values of attributes in the named-list, concatenated together with ',' as the separator. Use the %{pairs:} xlat to get a list of attributes and values.

e.g. If a response contains "Reply-Message = 'Hello', Reply-Message = 'bob' the expansion of "%{reply:Reply-Message[*]} will yield "Hello\nbob"

ATTRIBUTE ASSIGNMENTS

The attribute lists described above may be edited by listing one or more attributes in an "update" section. Once the attributes have been defined, they may be referenced as described above in the ATTRIBUTE REFERENCES section.

The following syntax defines attributes in an "update" section. Each attribute and value has to be all on one line in the configuration file. There is no need for commas or semi-colons after the value.

Attribute-Reference = value

Attribute Reference

The Attribute-Reference must be a reference (see above), using a name previously defined in a dictionary. If an undefined name is used, the server will return an error, and will not start.
Operators
The operator used to assign the value of the attribute may be one of the following, with the given meaning.
=
Add the attribute to the list, if and only if an attribute of the same name is not already present in that list.

ATTRIBUTE ASSIGNMENTS

The following operators may be used to add attributes to a list, or to update existing attributes. These are used in the form:

   Attribute-Name Operator Value
:=
Agrega el atributo a la lista. Si ya existe algún atributo con el mismo nombre en esa lista, su valor se reemplaza por el valor del atributo actual.
+=
Agrega el atributo al final de la lista, incluso si ya existen atributos con el mismo nombre en la lista. Cuando el lado derecho de la expresión se resuelve en múltiples valores, significa que se agregan todos los valores al final de la lista.
^=
Agrega el atributo al principio de la lista, incluso si ya existen atributos con el mismo nombre en la lista. Cuando el lado derecho de la expresión se resuelve en múltiples valores, significa que se anteponen todos los valores al principio de la lista.

Operadores de Aplicación y Filtrado

Los siguientes operadores también pueden usarse además de los mencionados anteriormente. Su función es realizar la aplicación o el filtrado de atributos en una lista.
-=
Elimina todos los atributos coincidentes de la lista. Tanto el nombre del atributo como el valor deben coincidir para que el atributo sea eliminado de la lista.
==
Mantiene todos los atributos coincidentes. Tanto el nombre del atributo como el valor deben coincidir para que el atributo permanezca en la lista.

¡Tenga en cuenta que este operador es muy diferente del operador '=' mencionado anteriormente!

!=
Mantiene todos los atributos con nombre coincidente, y el valor no es igual al dado.
<
Mantiene todos los atributos que tienen valores menores que el valor dado aquí. Cualquier valor mayor se reemplaza por el valor dado aquí. Si no existe ningún atributo, se agrega con el valor dado aquí, como con "+=".
<=
Mantiene todos los atributos que tienen valores menores o iguales al valor dado aquí. Cualquier valor mayor se reemplaza por el valor dado aquí. Si no existe ningún atributo, se agrega con el valor dado aquí, como con "+=".
>
Mantiene todos los atributos que tienen valores mayores que el valor dado aquí. Cualquier valor menor se reemplaza por el valor dado aquí. Si no existe ningún atributo, se agrega con el valor dado aquí, como con "+=".
>=
Mantiene todos los atributos que tienen valores mayores o iguales al valor dado aquí. Cualquier valor menor se reemplaza por el valor dado aquí. Si no existe ningún atributo, se agrega con el valor dado aquí, como con "+=".
!*
Elimina todas las ocurrencias del atributo nombrado, sin importar el valor.
=~
Mantiene todos los atributos que tienen valores que coinciden con la expresión regular dada. Si no coincide ningún atributo, no se hace nada más.
!~
Mantiene todos los atributos que tienen valores que no coinciden con la expresión regular dada. Si no coincide ningún atributo, no se hace nada más.
Valores

El valor puede ser una referencia de atributo o una cadena específica del atributo.

Cuando el valor es una referencia de atributo, debe tener el formato "&Nombre-Atributo". El símbolo "&" inicial indica que el valor es una referencia. "Nombre-Atributo" es el nombre de un atributo, como "User-Name" o "request:User-Name". Cuando se utiliza una referencia de atributo, ambos atributos deben tener el mismo tipo de datos. Por ejemplo, "User-Name := &NAS-Port" es inválido, porque "User-Name" es una cadena y "NAS-Port" es un entero.

Recomendamos usar el formato "Atributo-1 = &Atributo-2" para las actualizaciones, en lugar de "Atributo-1 = "%{Atributo-2}"". La primera versión copiará los datos del atributo, sin importar su formato. La segunda versión imprimirá el Atributo-2 en una cadena y luego la analizará para crear el valor del Atributo-1. Esta segunda versión es más lenta y frágil que la primera.

Cuando el valor es una cadena específica del atributo, puede ser una cadena, un entero, una dirección IP, etc. El valor puede expandirse como se describe anteriormente en la sección TIPOS DE DATOS. Por ejemplo, especificar "Framed-IP-Address = 127.0.0.1" hará que el atributo "Framed-IP-Address" se establezca en la dirección IP "127.0.0.1". Sin embargo, usar "Framed-IP-Address := módulo a ejecutar con una cadena "127.0.0.1"". La salida del módulo "echo" se analizará como una dirección IP y se colocará en el atributo Framed-IP-Address.

Esta flexibilidad significa que puede asignar una dirección IP especificándola directamente, o haciendo que la dirección se devuelva de una consulta a la base de datos, o haciendo que la dirección se devuelva como salida de un programa que se ejecuta.

Cuando los valores de cadena se asignan finalmente a un atributo, pueden tener una longitud máxima de 253 caracteres. Este límite se debe en parte a los requisitos del protocolo y del servidor interno. Es decir, las cadenas en el lenguaje pueden tener casi 8k de longitud, por ejemplo, para una consulta SQL larga. Sin embargo, la salida de esa consulta SQL no debe superar los 253 caracteres de longitud.

OTRAS PALABRAS CLAVE

Otras palabras clave del lenguaje provienen de los nombres de los módulos cargados por el servidor. Estas palabras clave dependen tanto de los módulos como de la configuración local.

Algunas palabras clave utilizadas que se definen en el archivo de configuración predeterminado son:

fail
Hace que la solicitud se trate como si hubiera ocurrido un fallo en la base de datos.
noop
No hacer nada. Esto también sirve como una instrucción para el seguimiento configurable de conmutación por error de que no se hizo nada en la sección actual.
ok
Indica al servidor que la solicitud se procesó correctamente. Esta palabra clave puede usarse para anular fallos anteriores, si el administrador local determina que los fallos no son catastróficos.
reject
Hace que la solicitud sea rechazada inmediatamente.

CÓDIGOS DE RETORNO DE MÓDULOS

Cuando se llama a un módulo, devuelve uno de los siguientes códigos a "unlang", con el siguiente significado.

	notfound        no se encontró información
	noop            el módulo no hizo nada
	ok              el módulo tuvo éxito
	updated         el módulo actualizó la solicitud
	fail            el módulo falló
	reject          el módulo rechazó la solicitud
	userlock        el usuario fue bloqueado
	invalid         la configuración no era válida
	handled         el módulo ha manejado la solicitud por sí mismo

Estos códigos de retorno se pueden probar en una condición, como se describe anteriormente en la sección CONDICIONES.

Consulte también el archivo doc/configurable_failover para ver métodos adicionales de captura y modificación de los códigos de retorno de los módulos.
