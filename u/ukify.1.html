NOMBRE

ukify - Combina componentes en una Imagen de Kernel Unificada firmada para sistemas UEFI

SINOPSIS

ukify [OPCIONES...] build

ukify [OPCIONES...] genkey

ukify [OPCIONES...] inspect ARCHIVO...

DESCRIPCIÓN

ukify es una herramienta cuyo propósito principal es combinar componentes (generalmente un kernel, un initrd y un stub de arranque UEFI) para crear una Imagen de Kernel Unificada (UKI)[1] — un binario PE que puede ser ejecutado por el firmware para iniciar el kernel de Linux incrustado. Vea systemd-stub(7) para detalles sobre el stub.

COMANDOS

Se entienden los siguientes comandos:

build

Este comando crea una Imagen de Kernel Unificada. Las dos opciones principales que deben especificarse para el verbo build son Linux=/--linux=, y Initrd=/--initrd=. Initrd= acepta múltiples rutas separadas por espacios y --initrd= puede especificarse varias veces.

Se insertarán secciones adicionales en la UKI, ya sea automáticamente o solo si se proporciona una opción específica. Vea las discusiones de Microcode=/--microcode=, Cmdline=/--cmdline=, OSRelease=/--os-release=, DeviceTree=/--devicetree=, DeviceTreeAuto=/--devicetree-auto=, HWIDs=/--hwids=, Splash=/--splash=, PCRPKey=/--pcrpkey=, Uname=/--uname=, SBAT=/--sbat=, y --section= abajo.

ukify también puede usarse para ensamblar un binario PE que no sea ejecutable pero que contenga datos auxiliares, por ejemplo, entradas adicionales de línea de comandos del kernel.

Si se proporcionan claves de firma de PCR a través de las opciones PCRPrivateKey=/--pcr-private-key= y PCRPublicKey=/--pcr-public-key= o PCRCertificate=/--pcr-certificate=, se calcularán, firmarán e incrustarán en la UKI los valores de PCR que se verán después de arrancar con el kernel, initrd y otras secciones dadas. Se utiliza systemd-measure(1) para realizar este cálculo y firma.

El cálculo de los valores de PCR se realiza para rutas de fases de arranque específicas. Estas pueden especificarse con la opción Phases=/--phases=. Si no se especifica, se utiliza el valor predeterminado proporcionado por systemd-measure. También es posible especificar los argumentos PCRPrivateKey=/--pcr-private-key=, PCRPublicKey=/--pcr-public-key= o PCRCertificate=/--pcr-certificate=, y Phases=/--phases= más de una vez. Las firmas se realizarán entonces con cada uno de los conjuntos de claves especificados. En la línea de comandos, cuando se utilizan tanto --phases= como --pcr-private-key=, deben especificarse el mismo número de veces, y luego el n-ésimo conjunto de rutas de fase de arranque será firmado por la n-ésima clave. Esto puede usarse para construir diferentes políticas de confianza para diferentes fases del arranque. En el archivo de configuración, PCRPrivateKey=, PCRPublicKey=, y Phases= se agrupan en secciones separadas, describiendo fases de arranque separadas. Si se especifica uno de SigningEngine=/--signing-engine= o SigningProvider=/--signing-provider=, entonces los argumentos de la clave privada se pasarán textualmente a openssl(1) como URIs, y los argumentos de la clave pública se cargarán como certificados X.509, para que la firma pueda realizarse con un motor o proveedor de OpenSSL respectivamente.

Si se proporciona una clave de firma SecureBoot a través de la opción SecureBootPrivateKey=/--secureboot-private-key=, el binario PE resultante se firmará en su totalidad, permitiendo que la UKI resultante sea confiable por SecureBoot. Vea también la discusión sobre la inscripción automática en systemd-boot(7).

Si el stub y/o el kernel contienen secciones ".sbat", se fusionarán en la UKI para que las actualizaciones de revocación que afecten a uno u otro se consideren cuando la UKI sea cargada por Shim. Para más información sobre SBAT, vea la documentación de Shim[2].

genkey

Este comando crea las claves para la firma de PCR y la clave y el certificado utilizados para la firma SecureBoot. Las mismas opciones de configuración que determinan qué claves y en qué rutas se necesitarán para firmar cuando se utiliza build, aquí determinan qué claves se crearán. Vea la discusión de PCRPrivateKey=/--pcr-private-key=, PCRPublicKey=/--pcr-public-key=, y SecureBootPrivateKey=/--secureboot-private-key= abajo.

Los archivos de salida no deben existir.

inspect

Muestra información sobre las secciones en un binario o binarios dados. Si se proporciona --all, se muestran todas las secciones. De lo contrario, si se especifica la opción --section= al menos una vez, solo se muestran esas secciones. De lo contrario, se muestran las secciones conocidas que se incluyen típicamente en una UKI. Para cada sección, se imprimen su nombre, tamaño y resumen sha256. Para las secciones de texto, se imprime el contenido.

Vea también la descripción de -j/--json= y --section=.

Otras herramientas que pueden ser útiles para inspeccionar UKIs: llvm-objdump(1) -p y pe-inspect.

AJUSTES DE CONFIGURACIÓN

Los ajustes pueden aparecer en archivos de configuración (la sintaxis con AlgúnAjuste=valor) y en la línea de comandos (la sintaxis con --algún-ajuste=valor). Para algunos parámetros de línea de comandos, también se permite un atajo de una sola letra. En los archivos de configuración, el ajuste debe estar en la sección apropiada, por lo que las descripciones se agrupan por sección a continuación. Cuando el mismo ajuste aparece en el archivo de configuración y en la línea de comandos, generalmente el ajuste de la línea de comandos tiene mayor prioridad y sobrescribe completamente el ajuste del archivo de configuración. Si algún ajuste se comporta de manera diferente, se describe abajo.

Si no se proporciona ningún archivo de configuración a través de la opción --config=RUTA, ukify intentará buscar un archivo de configuración predeterminado en las siguientes rutas en este orden: /etc/systemd/ukify.conf, /run/systemd/ukify.conf, /usr/local/lib/systemd/ukify.conf, y /usr/lib/systemd/ukify.conf, y luego cargará el primero que encuentre. ukify procederá normalmente si no se especifica ningún archivo de configuración y no se encuentra ninguno por defecto.

Los argumentos posicionales LINUX e INITRD, o los ajustes equivalentes Linux= y Initrd=, son opcionales. Si se especifica más de un initrd, todos se combinarán en una única sección PE. Esto es útil para, por ejemplo, anteponer microcódigo antes del initrd real.

Se entienden las siguientes opciones y ajustes:

Opciones solo en línea de comandos

--config=RUTA

Carga la configuración del archivo de configuración dado. En general, los ajustes especificados en el archivo de configuración tienen menor precedencia que los ajustes especificados a través de opciones. En los casos en que la opción de la línea de comandos no anula completamente el ajuste del archivo de configuración, se mencionan explícitamente en las descripciones de las opciones individuales.

--join-profile=PATH

Toma una ruta a un archivo PE existente que contiene un perfil adicional para agregar a la imagen del kernel unificada. El perfil puede generarse previamente con ukify. El perfil no necesita estar firmado ni contener mediciones de PCR. Todas las secciones PE de UKI del archivo PE especificado se copian a la UKI generada. Esto es útil para generar UKIs de múltiples perfiles. Tenga en cuenta que esto solo copia secciones PE definidas por la especificación UKI, e ignora cualquier otra, por ejemplo ".text" o similar.

Añadido en la versión 257.

--sign-profile=ID

Toma un ID de perfil para el cual ukify generará mediciones de PCR firmadas. Esta opción se puede usar junto con --join-profile= al construir la imagen final del kernel unificada. Si no se especifica, se agregarán mediciones de PCR firmadas para todos los perfiles.

Añadido en la versión 258.

--join-pcrsig=PATH, --pcrsig=TEXT|@PATH

--join-pcrsig= toma una ruta a un archivo PE existente que contiene una UKI construida previamente. --pcrsig= toma una ruta a un blob JSON pcrsig existente, o un blob en línea literal. Deben usarse juntos y sin especificar ningún otro parámetro de sección de UKI. ukify adjuntará el blob JSON pcrsig a la UKI. Esto es útil en combinación con --policy-digest para crear una UKI y luego firmar los resúmenes de la política TPM2 sin conexión.

Añadido en la versión 258.

--tools=DIRS

Especifique uno o más directorios con herramientas auxiliares. ukify buscará herramientas auxiliares en esos directorios primero y, si no las encuentra, intentará cargarlas desde $PATH de la forma habitual.

Añadido en la versión 253.

--output=FILENAME

El nombre del archivo de salida. Si no se especifica, se utilizará el nombre del argumento LINUX, con el sufijo ".unsigned.efi" o ".signed.efi", dependiendo de si se realizó la firma para SecureBoot.

Sección [UKI]

Linux=LINUX, --linux=LINUX

Una ruta al binario del kernel.

Añadido en la versión 254.

OSRelease=TEXT|@PATH, --os-release=TEXT|@PATH

La descripción de os-release (la sección ".osrel"). El argumento puede ser una cadena literal o "@" seguido de un nombre de ruta. Si no se especifica, el archivo os-release(5) se tomará del sistema host.

Añadido en la versión 253.

Cmdline=TEXT|@PATH, --cmdline=TEXT|@PATH

La línea de comandos del kernel (la sección ".cmdline"). El argumento puede ser una cadena literal o "@" seguido de un nombre de ruta. Si no se especifica, no se incrustará ninguna línea de comandos.

Añadido en la versión 253.

Initrd=INITRD..., --initrd=LINUX

Cero o más rutas de initrd. En el archivo de configuración, los elementos se separan por espacios en blanco. Los initrds se combinan en el orden de especificación, con los initrds especificados en el archivo de configuración primero.

Añadido en la versión 254.

Microcode=UCODE, --microcode=UCODE

Ruta a un initrd que contiene actualizaciones de microcódigo. Si no se especifica, la sección no estará presente.

Añadido en la versión 256.

Splash=PATH, --splash=PATH

Una imagen para mostrar durante el arranque (la sección ".splash"). El argumento es una ruta a un archivo BMP. Si no se especifica, la sección no estará presente.

Añadido en la versión 253.

DeviceTree=PATH, --devicetree=PATH

La descripción del árbol de dispositivos (la sección ".dtb"). El argumento es una ruta a un archivo binario compilado de árbol de dispositivos. Si no se especifica, la sección no estará presente.

Añadido en la versión 253.

DeviceTreeAuto=PATH..., --devicetree-auto=PATH

Cero o más archivos de árbol de dispositivos seleccionables automáticamente. En el archivo de configuración, los elementos se separan por espacios en blanco. Cada árbol de dispositivos estará en una sección ".dtbauto" separada.

Añadido en la versión 257.

HWIDs=PATH, --hwids=PATH

La tabla de dispositivos de ID de hardware (la sección ".hwids"). El argumento es una ruta a un directorio con archivos de descripción de dispositivos HWID en formato JSON. Cada archivo debe contener un único objeto JSON con las claves "name", "compatible" y "hwids". Las claves "name" y "compatible" deben tener valores de cadena y la clave "hwids" debe tener una lista de cadenas como valor, donde las cadenas deben ser UUIDs válidos que representen CHIDs/HWIDs. Ejemplo: 
{
    "type": "devicetree",
    "name": "Example Laptop 16 Gen 7",
    "compatible": "example,laptop-16-g7",
    "hwids": [
        "5dc05bf4-01f6-4089-b464-a08c47ea9295",
        "3e3f8f3c-2003-46f2-811c-85554f7d5952"
    ]
}

Aquí "Example Laptop 16 Gen 7" es el "name" del dispositivo (según lo define el fabricante), "example,laptop-16-g7" es el "compatible" (según lo define el kernel) y "hwids" es una matriz de CHIDs/HWIDs (extraída, por ejemplo, de la salida de fwupdtool hwids). Si no se especifica, la sección no estará presente. Se recomienda especificar este parámetro si se van a utilizar árboles de dispositivos seleccionables automáticamente.

Añadido en la versión 257.

Uname=VERSION, --uname=VERSION

Especifique la versión del kernel (como en uname -r, la sección ".uname"). Si no se especifica, se intentará extraer la cadena de versión de la imagen del kernel. Se recomienda pasar esto explícitamente si se conoce, ya que la extracción se basa en heurísticas y no es muy fiable. Si no se especifica y la extracción falla, la sección no estará presente.

Añadido en la versión 253.

SBAT=TEXT|@PATH, --sbat=TEXT|@PATH

Metadatos SBAT asociados con la UKI o el complemento. Las políticas SBAT son útiles para revocar grupos completos de UKIs o complementos con una única política estática que no ocupa espacio en DBX/MOKX. Si no se especifica manualmente, se utilizará una entrada de metadatos predeterminada que consiste en 
uki,1,UKI,uki,1,https://uapi-group.org/specifications/specs/unified_kernel_image/

para las UKIs y

uki-addon,1,UKI Addon,addon,1,https://www.freedesktop.org/software/systemd/man/latest/systemd-stub.html

para los complementos, para garantizar que siempre sea posible revocarlos. Para obtener más información sobre SBAT, consulte la Documentación de Shim[2].

Añadido en la versión 254.

PCRPKey=PATH, --pcrpkey=PATH

Una ruta a una clave pública para incrustar en la sección ".pcrpkey". Si no se especifica, y hay exactamente un argumento PCRPublicKey=/--pcr-public-key= o PCRCertificate=/--pcr-certificate=, se utilizará esa clave. De lo contrario, la sección no estará presente.

Añadido en la versión 253.

Profile=PATH, --profile=PATH

Una ruta a un perfil UKI para colocar en una sección ".profile". Esta opción es útil para crear UKIs de múltiples perfiles y generalmente se usa en combinación con --join-profile=, para extender la UKI especificada con un perfil adicional.

Añadido en la versión 257.

PCRBanks=PATH, --pcr-banks=PATH

Una lista de bancos de PCR separados por comas o espacios para firmar una política. Si no está presente, se utilizarán todos los bancos conocidos ("sha1", "sha256", "sha384", "sha512"), lo que fallará si el sistema no los admite.

Añadido en la versión 253.

SecureBootSigningTool=SIGNER, --signtool=SIGNER

Si se debe usar "sbsign", "pesign" o "systemd-sbsign". Dependiendo de esta elección, se requerirán diferentes parámetros para firmar una imagen. Predeterminado a "sbsign".

Añadido en la versión 254.

SecureBootPrivateKey=SB_KEY, --secureboot-private-key=SB_KEY

Una ruta a una clave privada para usar en la firma del binario resultante. Si se utiliza la opción SigningEngine=/--signing-engine= o SigningProvider=/--signing-provider=, esto también puede ser una designación específica del motor o proveedor. Esta opción es requerida por SecureBootSigningTool=sbsign/--signtool=sbsign y SecureBootSigningTool=systemd-sbsign/--signtool=systemd-sbsign.

Añadido en la versión 253.

SecureBootCertificate=SB_CERT, --secureboot-certificate=SB_CERT

Una ruta a un certificado para usar en la firma del binario resultante. Si se utiliza la opción SigningEngine=/--signing-engine= o SigningProvider=/--signing-provider=, esta también puede ser una designación específica del motor o proveedor. Esta opción es requerida por SecureBootSigningTool=sbsign/--signtool=sbsign y SecureBootSigningTool=systemd-sbsign/--signtool=systemd-sbsign.

Añadido en la versión 253.

SecureBootCertificateDir=SB_PATH, --secureboot-certificate-dir=SB_PATH

Una ruta a un directorio de base de datos de certificados nss para usar en la firma del binario resultante. Tiene efecto cuando se utiliza SecureBootSigningTool=pesign/--signtool=pesign. Por defecto es /etc/pki/pesign.

Añadido en la versión 254.

SecureBootCertificateName=SB_CERTNAME, --secureboot-certificate-name=SB_CERTNAME

El nombre de la entrada de la base de datos de certificados nss para usar en la firma del binario resultante. Esta opción es requerida por SecureBootSigningTool=pesign/--signtool=pesign.

Añadido en la versión 254.

SecureBootCertificateValidity=DAYS, --secureboot-certificate-validity=DAYS

Período de validez (en días) para un certificado creado por genkey. Por defecto es 3650, es decir, 10 años.

Añadido en la versión 254.

SigningEngine=ENGINE, --signing-engine=ENGINE

Un motor OpenSSL que se utilizará para firmar el binario resultante y las mediciones de PCR, véase openssl-engine(1).

Añadido en la versión 253.

SigningProvider=PROVIDER, --signing-provider=PROVIDER

Un proveedor OpenSSL que se utilizará para firmar el binario resultante y las mediciones de PCR, véase provider(7). Esta opción solo se puede utilizar cuando se usa systemd-sbsign como herramienta de firma.

Añadido en la versión 257.

CertificateProvider=PROVIDER, --certificate-provider=PROVIDER

Un proveedor OpenSSL que se utilizará para cargar el certificado utilizado para firmar el binario resultante y las mediciones de PCR, véase provider(7). Esta opción solo se puede utilizar cuando se usa systemd-sbsign como herramienta de firma.

Añadido en la versión 257.

SignKernel=BOOL, --sign-kernel, --no-sign-kernel

Anula la detección de si se debe firmar el binario Linux en sí antes de que se incorpore a la imagen combinada. Si no se especifica, se firmará si se proporciona una clave de firma de Arranque Seguro a través de la opción SecureBootPrivateKey=/--secureboot-private-key= y el binario no ha sido firmado previamente. Si SignKernel=/--sign-kernel es verdadero, y el binario ya ha sido firmado, la firma se adjuntará de todos modos.

Añadido en la versión 253.

[PCRSignature:NAME] sección

En el archivo de configuración, estas opciones se agrupan por sección. En la línea de comandos, deben especificarse en el mismo orden. Las secciones especificadas en ambos orígenes se combinan.

PCRPrivateKey=PATH, --pcr-private-key=PATH

Una clave privada para usar en la firma de políticas de PCR. En la línea de comandos, esta opción se puede especificar más de una vez, en cuyo caso se realizarán múltiples firmas.

Añadido en la versión 253.

PCRPublicKey=PATH, --pcr-public-key=PATH

Una clave pública para usar en la firma de políticas de PCR.

En la línea de comandos, esta opción se puede especificar más de una vez, de forma similar a la opción --pcr-private-key=. Si no está presente, las claves públicas se extraerán de las claves privadas. En la línea de comandos, si está presente, esta opción debe especificarse el mismo número de veces que la opción --pcr-private-key=. No se puede especificar si se usa --pcr-certificate=.

Añadido en la versión 253.

PCRCertificate=PATH, --pcr-certificate=PATH

Un certificado X.509 para usar en la firma de políticas de PCR.

En la línea de comandos, esta opción se puede especificar más de una vez, de forma similar a la opción --pcr-private-key=. Si no está presente, las claves públicas se extraerán de las claves privadas. En la línea de comandos, si está presente, esta opción debe especificarse el mismo número de veces que la opción --pcr-private-key=. No se puede especificar si se usa --pcr-public-key=.

Añadido en la versión 258.

Phases=LIST, --phases=LIST

Una lista separada por comas o espacios de rutas de fases separadas por dos puntos para firmar una política. Cada conjunto de rutas de fase de arranque se firmará con la clave privada correspondiente. Si no está presente, se utilizará el valor por defecto de systemd-measure(1).

En la línea de comandos, cuando este argumento está presente, debe aparecer el mismo número de veces que la opción --pcr-private-key=.

Añadido en la versión 253.

EJEMPLOS

Ejemplo 1. Invocación mínima

$ ukify build \
      --linux=/lib/modules/6.0.9-300.fc37.x86_64/vmlinuz \
      --initrd=/some/path/initramfs-6.0.9-300.fc37.x86_64.img \
      --cmdline='quiet rw'

Esto crea un UKI sin firmar ./vmlinuz.unsigned.efi.

Ejemplo 2. Todo lujo de detalles

$ ukify build \
      --linux=/lib/modules/6.0.9-300.fc37.x86_64/vmlinuz \
      --initrd=early_cpio \
      --initrd=/some/path/initramfs-6.0.9-300.fc37.x86_64.img \
      --sbat='sbat,1,SBAT Version,sbat,1,https://github.com/rhboot/shim/blob/main/SBAT.md
      uki.author.myimage,1,UKI for System,uki.author.myimage,1,https://uapi-group.org/specifications/specs/unified_kernel_image/' \
      --pcr-private-key=tpm2-pcr-initrd-private-key.pem \
      --pcr-public-key=tpm2-pcr-initrd-public-key.pem \
      --phases='enter-initrd' \
      --pcr-private-key=tpm2-pcr-private-key-system.pem \
      --pcr-public-key=tpm2-pcr-public-key-system.pem \
      --phases='enter-initrd:leave-initrd enter-initrd:leave-initrd:sysinit \
                enter-initrd:leave-initrd:sysinit:ready' \
      --pcr-banks=sha384,sha512 \
      --secureboot-private-key=secureboot-private-key.pem \
      --secureboot-certificate=secureboot-certificate.pem \
      --sign-kernel \
      --cmdline='quiet rw rhgb'

Esto crea un UKI firmado ./vmlinuz.signed.efi. La sección initrd contiene dos partes concatenadas, early_cpio y initramfs-6.0.9-300.fc37.x86_64.img. La política incrustada en la sección ".pcrsig" se firmará para el initrd (la fase enter-initrd) con la clave tpm2-pcr-initrd-private-key.pem, y para el sistema principal (fases leave-initrd, sysinit, ready) con la clave tpm2-pcr-private-key-system.pem. El binario Linux y la imagen combinada resultante se firmarán con la clave de Arranque Seguro secureboot-private-key.pem.

Ejemplo 3. Todo lujo de detalles, a través de un archivo de configuración

Este es el mismo que el ejemplo anterior, pero esta vez la configuración se almacena en un archivo:

$ cat ukify.conf
[UKI]
Initrd=early_cpio
Cmdline=quiet rw rhgb
SecureBootPrivateKey=secureboot-private-key.pem
SecureBootCertificate=secureboot-certificate.pem
SignKernel=yes
PCRBanks=sha384,sha512
[PCRSignature:initrd]
PCRPrivateKey=tpm2-pcr-initrd-private-key.pem
PCRPublicKey=tpm2-pcr-initrd-public-key.pem
Phases=enter-initrd
[PCRSignature:system]
PCRPrivateKey=tpm2-pcr-private-key-system.pem
PCRPublicKey=tpm2-pcr-public-key-system.pem
Phases=enter-initrd:leave-initrd
       enter-initrd:leave-initrd:sysinit
       enter-initrd:leave-initrd:sysinit:ready
$ ukify -c ukify.conf build \
        --linux=/lib/modules/6.0.9-300.fc37.x86_64/vmlinuz \
        --initrd=/some/path/initramfs-6.0.9-300.fc37.x86_64.img

Se especifica un "initrd" (early_cpio) en el archivo de configuración, y el otro initrd (initramfs-6.0.9-300.fc37.x86_64.img) se especifica en la línea de comandos. Esto puede ser útil, por ejemplo, cuando el primer initrd contiene microcódigo para la CPU y no necesita ser actualizado cuando cambia la versión del kernel, a diferencia del initrd real.

Ejemplo 4. Complemento PE de línea de comandos del kernel

ukify build \
      --secureboot-private-key=secureboot-private-key.pem \
      --secureboot-certificate=secureboot-certificate.pem \
      --cmdline='debug' \
      --sbat='sbat,1,SBAT Version,sbat,1,https://github.com/rhboot/shim/blob/main/SBAT.md
      uki-addon.author,1,UKI Addon for System,uki-addon.author,1,https://www.freedesktop.org/software/systemd/man/systemd-stub.html'
      --output=debug.addon.efi

Esto crea un binario PE firmado que contiene el parámetro adicional de línea de comandos del kernel "debug" con metadatos SBAT que hacen referencia al propietario del complemento.

Ejemplo 5. Decidir la política de firma y crear el certificado y las claves

Primero, creemos un archivo de configuración que especifique qué firmas se realizarán:

# cat >/etc/kernel/uki.conf <<EOF
[UKI]
SecureBootPrivateKey=/etc/kernel/secureboot-private-key.pem
SecureBootCertificate=/etc/kernel/secureboot-certificate.pem
[PCRSignature:initrd]
Phases=enter-initrd
PCRPrivateKey=/etc/systemd/tpm2-pcr-initrd-private-key.pem
PCRPublicKey=/etc/systemd/tpm2-pcr-initrd-public-key.pem
[PCRSignature:system]
Phases=enter-initrd:leave-initrd enter-initrd:leave-initrd:sysinit
       enter-initrd:leave-initrd:sysinit:ready
PCRPrivateKey=/etc/systemd/tpm2-pcr-private-key-system.pem
PCRPublicKey=/etc/systemd/tpm2-pcr-public-key-system.pem
EOF

A continuación, podemos generar el certificado y las claves:

# ukify genkey --config=/etc/kernel/uki.conf
Writing SecureBoot private key to /etc/kernel/secureboot-private-key.pem
Writing SecureBoot certificate to /etc/kernel/secureboot-certificate.pem
Writing private key for PCR signing to /etc/systemd/tpm2-pcr-initrd-private-key.pem
Writing public key for PCR signing to /etc/systemd/tpm2-pcr-initrd-public-key.pem
Writing private key for PCR signing to /etc/systemd/tpm2-pcr-private-key-system.pem
Writing public key for PCR signing to /etc/systemd/tpm2-pcr-public-key-system.pem

(Ambas operaciones deben realizarse como root para permitir el acceso de escritura a /etc/kernel/.)

NAME

ukify

build Unified Kernel Images

SYNOPSIS

ukify build [OPTIONS...]

DESCRIPTION

ukify is a tool to build Unified Kernel Images (UKI).

A UKI is a single EFI executable file that contains the kernel, initial RAM disk, kernel command line, and auxiliary data (like signed PCR values or boot configuration). UKIs are designed to simplify the boot process and improve security by allowing signed verification of all components before execution.

The primary use case is to create a self-contained kernel image that can be booted directly by a UEFI firmware or a bootloader like systemd-boot. UKIs can be signed, providing a mechanism to ensure the integrity and authenticity of the boot process.

COMMANDS

The following commands are available:

build
Build a Unified Kernel Image.

CONFIGURATION SETTINGS

The following configuration settings are available when running the build command:

--linux=PATH
Path to the kernel image (e.g., /boot/vmlinuz-linux). This is a required argument for building a UKI.
--initrd=PATH
Path to the initial RAM disk image (e.g., /boot/initramfs-linux.img). This is a required argument for building a UKI.
--cmdline=STRING
Kernel command line arguments. If not specified, a default command line is used. This option can be used multiple times to append arguments.
--cmdline-from-file=PATH
Read kernel command line arguments from the specified file.
--profile=STRING
Embed a boot profile into the UKI. The string should be in the format KEY=VALUE, where KEY is the profile identifier (e.g., TITLE, ID) and VALUE is its corresponding value. This option can be used multiple times.
--join-profile=PATH
Embed an existing EFI executable file as a profile into the UKI. This is useful for combining multiple UKIs or boot entries.
--output=PATH
Path where the generated UKI will be saved. If not specified, the UKI will be named based on the kernel and initrd filenames and saved in the current directory.
--pcr-public-key=PATH
Path to a public key file (PEM format) for signing PCR values. This is used to enable measurement of boot components into TPM PCRs.
--policy-digest
Generate a policy digest for the PCR values. This option requires --pcr-public-key.
--json=short|full
Specifies the format for the PCR JSON blob. short includes only the policy digest, while full includes the policy digest and other relevant information.
--json-extra=PATH
Path to a JSON file containing extra data to be embedded in the PCR JSON blob.
--pcrsig=PATH
Path to a signed PCR JSON blob file. This option is used to embed pre-signed PCR values into the UKI.
--join-pcrsig=PATH
Embed an existing EFI executable file as a PCR signature section into the UKI. This is typically used to combine a UKI with a signed PCR section.
--sign-key=PATH
Path to a private key file (PEM format) for signing the UKI. Requires --sign-cert.
--sign-cert=PATH
Path to a certificate file (PEM format) for signing the UKI. Requires --sign-key.
--sign-id=STRING
An identifier for the signature. This is embedded in the signature metadata.
--unlock-key=PATH
Path to a private key file (PEM format) for unlocking the UKI. This is used for certain advanced signing scenarios.
--unlock-cert=PATH
Path to a certificate file (PEM format) for unlocking the UKI. Requires --unlock-key.

EXAMPLES

Example 1. Basic UKI build

$ ukify build \
      --linux=/lib/modules/6.0.9-300.fc37.x86_64/vmlinuz \
      --initrd=/some/path/initramfs-6.0.9-300.fc37.x86_64.img \
      --cmdline='quiet rw' \
      --output=my-uki.efi

This command builds a UKI named my-uki.efi containing the specified kernel, initrd, and kernel command line.

Example 2. UKI build with signing

$ ukify build \
      --linux=/lib/modules/6.0.9-300.fc37.x86_64/vmlinuz \
      --initrd=/some/path/initramfs-6.0.9-300.fc37.x86_64.img \
      --cmdline='quiet rw' \
      --sign-key=my-private.key \
      --sign-cert=my-certificate.crt \
      --output=my-signed-uki.efi

This command builds a UKI and signs it using the provided private key and certificate. The signature is embedded within the UKI.

Example 3. UKI build with PCR signing

First, create a UKI and extract the PCR policy digest:

$ ukify build \
      --linux=/lib/modules/6.0.9-300.fc37.x86_64/vmlinuz \
      --initrd=/some/path/initramfs-6.0.9-300.fc37.x86_64.img \
      --cmdline='quiet rw' \
      --pcr-public-key=tpm2-pcr-initrd-public-key.pem \
      --policy-digest \
      --json=short \
      --output=base.efi >base.pcrs

Then, sign the PCR policy digest offline using a private key (e.g., using openssl) and update the base.pcrs file with the signature. The format of the PCR policy digest is JSON.

Finally, rebuild the UKI and embed the signed PCR policy:

$ ukify build \
      --join-pcrsig=base.efi \
      --pcrsig=@base.pcrs \
      --output=base-signed.efi

The resulting UKI base-signed.efi will contain the signed PCR policy, allowing for secure boot verification against measured PCR values.

Example 4. Signing kernel-install configurations

To have kernel-install automatically sign UKIs created with ukify, you can configure the signing keys and certificates in /etc/kernel/uki.conf.

# /etc/kernel/uki.conf
[Sign]
KeyFile=/etc/kernel/my-signing.key
CertFile=/etc/kernel/my-signing.crt

When kernel-install is used to install a kernel that generates a UKI, the 60-ukify.install script will look for this configuration file. If found, it will use the specified certificate and key files to sign the generated UKI.

Note that the kernel-install(8) plugin 60-ukify.install uses /etc/kernel/uki.conf by default, so after this file has been created, installations of kernels that create a UKI on the local machine using kernel-install will perform signing using this configuration.

Example 5. Multi-Profile UKI

First, create a few profiles:

$ ukify build \
      --profile='TITLE=Base' \
      --output=profile0.efi

Add a second profile (@1):

$ ukify build \
      --profile='TITLE=Boot into Storage Target Mode
ID=storagetm' \
      --cmdline='quiet rw rd.systemd.unit=storage-target-mode.target' \
      --output=profile1.efi

Add a third profile (@2):

$ ukify build \
      --profile='TITLE=Factory Reset
ID=factory-reset' \
      --cmdline='quiet rw systemd.unit=factory-reset.target' \
      --output=profile2.efi

Then, create a UKI and include all the generated profiles:

$ ukify build \
      --linux=/lib/modules/6.0.9-300.fc37.x86_64/vmlinuz \
      --initrd=/some/path/initramfs-6.0.9-300.fc37.x86_64.img \
      --cmdline='quiet rw' \
      --join-profile=profile0.efi \
      --join-profile=profile1.efi \
      --join-profile=profile2.efi \
      --output=base.efi

The resulting UKI base-with-profile-0-1-2.efi will now contain three profiles.

Example 6. Offline signing of pcrsig section

First, create a UKI and save the PCR JSON blob:

$ ukify build \
      --linux=/lib/modules/6.0.9-300.fc37.x86_64/vmlinuz \
      --initrd=/some/path/initramfs-6.0.9-300.fc37.x86_64.img \
      --cmdline='quiet rw' \
      --pcr-public-key=tpm2-pcr-initrd-public-key.pem \
      --policy-digest \
      --json=short \
      --output=base.efi >base.pcrs

Then, sign the PCR digests offline and insert them in the JSON blob:

#!/usr/bin/python3
import base64, json, subprocess
priv_key = '/home/zbyszek/src/systemd/tpm2-pcr-private.pem'
base_file = 'base.pcrs'
base = json.load(open(base_file))
for bank,policies in base.items():
    for policy in policies:
        pol = base64.b16decode(policy['pol'].upper())
        call = subprocess.run(['openssl', 'dgst', f'-{bank}', '-sign', priv_key],
                              input=pol,
                              check=True,
                              capture_output=True)
        sig = base64.b64encode(call.stdout).decode()
        policy['sig'] = sig
print(json.dumps(base))

Finally, attach the updated JSON blob to the UKI:

$ ukify build \
      --join-pcrsig=base.efi \
      --pcrsig=@base.pcrs \
      --json=short \
      --output=base-signed.efi

The resulting UKI base-signed.efi will now contain the signed PCR digests.
