NOMBRE

varnishncsa - Muestra los registros de Varnish en el formato de registro combinado de Apache / NCSA

SINOPSIS

varnishncsa [-a] [-b] [-c] [-C] [-d] [-D] [-E] [-F <formato>] [-f <archivoformato>] [-g <solicitud|vxid>] [-h] [-j] [-k <num>] [-L <limite>] [-n <directoriotrabajo>] [-P <archivo>] [-Q <archivo>] [-q <consulta>] [-r <nombrearchivo>] [-R <limite[/duracion]>] [-t <segundos|off>] [-V] [-w <nombrearchivo>]

DESCRIPCIÓN

La utilidad varnishncsa lee los registros de memoria compartida de varnishd(1) y los presenta en el formato de registro "combinado" de Apache / NCSA.

Cada línea de registro generada se basa en una sola transacción de tipo Solicitud recopilada del registro de memoria compartida. Luego, la transacción de Solicitud se escanea en busca de las partes relevantes para generar una línea de registro. Para filtrar las líneas de registro generadas, use el lenguaje de consulta para seleccionar las transacciones aplicables. Las transacciones que no son de solicitud se ignoran.

Las siguientes opciones están disponibles:

-a
Al escribir la salida en un archivo, anéxela en lugar de sobrescribirla. Esta opción no tiene efecto sin la opción -w.
-b
Registrar solicitudes de backend. Si no se especifica -c, solo las solicitudes de backend activarán líneas de registro.
-c
Registrar solicitudes del cliente. Este es el valor predeterminado. Si se especifica -b, se necesita -c para registrar también las solicitudes del cliente.
-C
Realizar todas las coincidencias de expresiones regulares y cadenas sin distinguir entre mayúsculas y minúsculas.
-d
Procesar registros del registro al principio del registro y salir.
-D
Daemonizar.
-E
Mostrar solicitudes ESI, implica modo cliente.
-F <formato>
Establecer la cadena de formato del registro de salida.
-f <archivoformato>
Leer el formato de salida de un archivo. Leerá una sola línea del archivo especificado y usará esa línea como formato.
-g <solicitud|vxid>
La agrupación de los registros. El valor predeterminado es agrupar por vxid.
-h
Imprimir el uso del programa y salir.
-j
Hacer que los reemplazos de especificadores de formato sean compatibles con JSON. Al escapar caracteres, usar secuencias de escape \uXXXX de estilo JSON en lugar de secuencias \xXX de estilo C. Las cadenas vacías se reemplazarán con "" en lugar de "-", y los enteros vacíos se reemplazarán con null. Usar -F o -f en combinación con -j para escribir registros JSON.
-k <num>
Procesar este número de transacciones de registro coincidentes antes de salir.
-L <limite>
Establece el límite superior de transacciones incompletas retenidas antes de que la transacción más antigua se complete forzosamente. Se sintetiza un registro de advertencia cuando esto ocurre. Esta configuración mantiene un límite superior en el uso de memoria de las consultas en ejecución. El valor predeterminado es 1000 transacciones.
-n <directoriotrabajo>
Especificar el directorio de trabajo de varnish de la instancia a la que conectarse. Consulte la documentación de la opción -n de varnishd(1) para obtener información adicional y valores predeterminados.
-P <archivo>
Escribir el PID del proceso en el archivo especificado.
-Q <archivo>
Especifica el archivo que contiene la consulta VSL a utilizar. Cuando se especifican múltiples opciones -Q o -q, todas las consultas se consideran como si se usara el operador 'or' para combinarlas.
-q <consulta>
Especifica la consulta VSL a utilizar. Cuando se especifican múltiples opciones -q o -Q, todas las consultas se consideran como si se usara el operador 'or' para combinarlas.
-r <nombrearchivo>
Leer el registro en formato de archivo binario de este archivo. El archivo puede crearse con varnishlog -w nombrearchivo. Si el nombre del archivo es -, los registros se leen de la entrada estándar y no puede funcionar como demonio.
-R <limite[/duracion]>
Restringe la salida al límite especificado. Se suprimirán las transacciones que excedan el límite. El límite se especifica como el número máximo de transacciones (con respecto al método de agrupación elegido) y un período de tiempo opcional. Si no se especifica duración, se usa un valor predeterminado de s. El campo de duración se puede formatear como en VCL (por ejemplo, -R 10/2m) o como un período de tiempo simple sin el prefijo (por ejemplo, -R 5/m). Cuando está en modo de agrupación -g raw, esta configuración no se puede usar junto con -i, -I, -x o -X, y recomendamos usar -q en su lugar.
-t <segundos|off>
Tiempo de espera antes de devolver un error en la conexión VSM inicial. Si se establece, la conexión VSM se reintentará cada 0.5 segundos durante esta cantidad de segundos. Si es cero, la conexión se intentará solo una vez y fallará inmediatamente si no tiene éxito. Si se establece en "off", la conexión no fallará, lo que permitirá que la utilidad se inicie y espere indefinidamente a que aparezca la instancia de Varnish. El valor predeterminado es 5 segundos.
-V
Imprimir información de la versión y salir.
-w <nombrearchivo>
Redirigir la salida al archivo. El archivo se sobrescribirá a menos que se haya especificado la opción -a. Si la aplicación recibe un SIGHUP en modo demonio, el archivo se reabrirá, lo que permitirá rotar el archivo antiguo. Esta opción es necesaria cuando se ejecuta en modo demonio. Si el nombre del archivo es -, varnishncsa escribe en la salida estándar y no puede funcionar como demonio.
--optstring
Imprime el parámetro optstring de getopt(3) para ayudar a escribir scripts de envoltura.

MODOS

El modo predeterminado de varnishncsa es el "modo cliente". En este modo, el registro será similar a lo que un servidor web produciría en ausencia de varnish. El modo cliente se puede seleccionar explícitamente usando -c.

Si se especifica el interruptor -b, varnishncsa operará en "modo backend". En este modo, se registrarán las solicitudes generadas por varnish a los backends. A menos que también se especifique -c, se ignorarán las solicitudes del cliente recibidas por varnish.

Al ejecutar varnishncsa tanto en modo backend como cliente, se aconseja encarecidamente incluir el especificador de formato %{Varnish:side}x para distinguir entre solicitudes de backend y cliente.

Las solicitudes de cliente que resultan en una tubería (es decir, return(pipe) en vcl) no generarán registros en modo backend. Esto se debe a que varnish no está generando solicitudes, sino que simplemente pasa bytes en ambas direcciones. Sin embargo, una instancia de varnishncsa que se ejecuta en modo normal puede ver este caso usando el formateador %{Varnish:handling}x, que será 'pipe'.

En modo backend, algunos de los campos en la cadena de formato adquieren diferentes significados. En particular, los formateadores de conteo de bytes (%b, %I, %O) consideran a varnish como el cliente.

Es posible mantener dos instancias de varnishncsa en ejecución, una en modo backend y otra en modo cliente, registrando en archivos diferentes.

FORMATO

Especifica el formato de registro a usar. Si no se especifica ningún formato, se utiliza el formato de registro predeterminado:

%h %l %u %t "%r" %s %b "%{Referer}i" "%{User-agent}i"

Se admiten las secuencias de escape \n y \t.

Los formateadores admitidos son:

%b
En modo cliente, tamaño de la respuesta en bytes, excluyendo las cabeceras HTTP. En modo backend, el número de bytes recibidos del backend, excluyendo las cabeceras HTTP. En formato CLF, es decir, un '-' en lugar de un 0 cuando no se envían bytes.

NAME

varnishncsa(1) ― Varnish log file reporter

SYNOPSIS

varnishncsa [-a] [-b] [-F format] [-f logfile] [-?] [-h hash] [-i ip] [-j] [-L] [-l logfile] [-n vclname] [-P pidfile] [-q query] [-r logfile] [-s backend] [-T timeout] [-V] [-w logfile]

DESCRIPTION

The varnishncsa utility connects to a Varnish shared memory log and reports log entries in the Apache combined log format, or other user-defined formats. It can be used to log client requests, backend requests, or both.

The utility can be run in two primary modes: client mode and backend mode.

client mode
Logs requests from clients to Varnish. This is the default mode if no options are specified.
backend mode
Logs requests from Varnish to backends. This mode is enabled with the -b option.

The following options are available:

-a
Append to the log file instead of overwriting it.
-b
Log backend requests. By default, client requests are logged.
-F format
Specify the log format. The default format is the Apache Common Log Format. See the FORMAT SPECIFIERS section below for details.
-f logfile
Read log entries from the specified file instead of shared memory. This option is useful for replaying log files for testing or analysis.
-?
Print a help message and exit.
-h hash
Specify the hash algorithm to use for the VSL lookup. Possible values are mkhash and win32.
-i ip
Include only log entries from the specified IP address. This option can be specified multiple times.
-j
Output log entries in JSON format. This option is mutually exclusive with the -F option.
-L
List all available log format specifiers and exit.
-l logfile
Write log entries to the specified file. If this option is not specified, log entries are written to standard output.
-n vclname
Specify the Varnish instance name to connect to. If not specified, the default instance name (usually "varnish") is used.
-P pidfile
Write the process ID to the specified file. This is useful for managing the daemon process.
-q query
Filter log entries using a VSL query. See vsl-query(7) for details.
-r logfile
Read log entries from the specified file in reverse order. This option is useful for analyzing log files from the most recent entries.
-s backend
Specify the backend name or IP address to filter log entries. This option can be specified multiple times.
-T timeout
Specify the timeout for VSL connections in seconds. The default is 300 seconds.
-V
Print version information and exit.
-w logfile
Write log entries to the specified file and rotate the file when it reaches a certain size or age. This option is mutually exclusive with the -l option.

FORMAT SPECIFIERS

The following format specifiers can be used with the -F option:

%a
Remote host name. Defaults to '-' if not known.
%b
Size of the response in bytes. In client mode, this is the size of the response sent to the client. In backend mode, this is the size of the response received from the backend. This is equivalent to %O for client mode and %I for backend mode.
%c
Connection status. See the VSL documentation for details.
%C
The name of the Varnish child process handling the request.
%d
Number of bytes sent to the client. In backend mode, number of bytes received from the backend. This is equivalent to %O.
%D
In client mode, time taken to serve the request, in microseconds. In backend mode, time from the request was sent to the entire body had been received. This is equivalent to %{us}T.
%e
Number of bytes received from the client. In backend mode, number of bytes sent to the backend. This is equivalent to %I.
%f
The VCL subroutine called.
%H
The request protocol. Defaults to HTTP/1.0 if not known.
%h
Remote host. Defaults to '-' if not known. In backend mode this is the IP of the backend server.
%I
In client mode, total bytes received from client. In backend mode, total bytes sent to the backend.
%{X[:first|last]}i
The contents of request header X before any VCL processing for client side, and before vcl_backend_response for backend side. If the header appears multiple times in a single transaction, the last occurrence is used in backend mode and the first one in client mode.

If an optional :first or :last is used, VCL processing will be taken into account and the matching rule will be first match or last match respectively. When using :last, unset headers will still be captured.

%l
Remote logname. Always '-'.
%m
Request method. Defaults to '-' if not known.
%{X[:first|last]}o
The contents of response header X, as it was delivered for client mode, and before VCL processing for backend mode. If the header appears multiple times in a single transaction, the last occurrence is used in client mode and the first one in backend mode.

If an optional :first or :last is used, VCL processing will be taken into account and the matching rule will be first match or last match respectively. When using :last, unset headers will still be captured.

%O
In client mode, total bytes sent to client. In backend mode, total bytes received from the backend.
%q
The query string. Defaults to an empty string if not present.
%r
The first line of the request. Synthesized from other fields, so it may not be the request verbatim. See the NOTES section.
%s
Status sent to the client. In backend mode, status received from the backend.
%t
In client mode, time when the request was received, in HTTP date/time format. In backend mode, time when the request was sent.
%{X}t
In client mode, time when the request was received, in the format specified by X. In backend mode, time when the request was sent. The time specification format is the same as for strftime(3) with these extensions:
  • %{sec}: number of seconds since the Epoch
  • %{msec}: number of milliseconds since the Epoch
  • %{usec}: number of milliseconds since the Epoch
  • %{msec_frac}: millisecond fraction
  • %{usec_frac}: microsecond fraction

The extensions cannot be combined with each other or strftime(3) in the same specification. Use multiple %{X}t specifications instead.

%T
In client mode, time taken to serve the request, in seconds. In backend mode, time from the request was sent to the entire body had been received. This is equivalent to %{s}T.
%{X}T
In client mode, time taken to serve the request, in the format specified by X. In backend mode, time from the request was sent to the entire body had been received. The time specification format can be one of the following: s (same as %T), ms or us (same as %D).
%U
The request URL without the query string. Defaults to '-' if not known.
%u
Remote user from auth.
%{X}x
Extended variables. Supported variables are:
Varnish:default_format
The log format used when neither -f nor -F options are specified. Useful for appending/prepending with other formatters.
Varnish:time_firstbyte
Time from when the request processing starts until the first byte is sent to the client, in seconds. For backend mode: Time from the request was sent to the backend to the entire header had been received.
Varnish:hitmiss
In client mode, one of the 'hit' or 'miss' strings, depending on whether the request was a cache hit or miss. Pipe, pass and synth are considered misses. In backend mode, this field is blank.
Varnish:handling
In client mode, one of the 'hit', 'hitmiss', 'hitpass', 'miss', 'pass', 'pipe' or 'synth' strings indicating how the request was handled. In backend mode, this field is blank.
Varnish:side
Backend or client side. One of two values, 'b' or 'c', depending on where the request was made. In pure backend or client mode, this field will be constant.
Varnish:vxid
The VXID of the varnish transaction.
VCL_Log:key
The value set by std.log("key:value") in VCL.
VSL:tag:record-prefix[field]
The value of the VSL entry for the given tag-record prefix-field combination. Tag is mandatory, the other components are optional.

The record prefix will limit the matches to those records that have this prefix as the first part of the record content followed by a colon.

The field will, if present, treat the log record as a white space separated list of fields, and only the nth part of the record will be matched against. Fields start counting at 1 and run up to 255.

Defaults to '-' when the tag is not seen, the record prefix does not match or the field is out of bounds. If a tag appears multiple times in a single transaction, the first occurrence is used.

SIGNALS

  • SIGHUP

    Rotate the log file (see -w option) in daemon mode, abort the loop and die gracefully when running in the foreground.

  • SIGUSR1

    Flush any outstanding transactions.

NOTES

The %r formatter is equivalent to %m http://%{Host}i%U%q %H. This differs from the Apache HTTP Server %r behavior, equivalent to %m %U%q %H.

Note that request fields are collected on a first match basis in client mode and last match basis in backend mode. Similarly, response fields are collected on a first match basis in backend mode and last match basis in client mode.

In other words, request headers are logged as they were received from the client and as they were sent to the backend, while response headers are logged as they were sent to the client and as they were received from the backend.

Furthermore, these rules also apply to items that appear multiple times in a transaction. For example, if a header appears multiple times in a client request, the first occurrence is logged in client mode, while in backend mode the last occurrence is logged.

Prior to 7.7, formats %{X}i and %{X}o used to include header fields populated from VCL. Consider %{VCL_Log:key}x instead to capture data from VCL transactions.

EXAMPLE

Log the second field of the Begin record, corresponding to the VXID of the parent transaction:

varnishncsa -F "%{VSL:Begin[2]}x"

Log the entire Timestamp record associated with the processing length:

varnishncsa -F "%{VSL:Timestamp:Process}x"

Log in JSON, using the -j flag to ensure that the output is valid JSON for all inputs:

varnishncsa -j -F '{"size": %b, "time": "%t", "ua": "%{User-Agent}i"}'

Log the first and last values of a request header that is modified multiple times in VCL:

varnishncsa -F "%{x-custom-header:first}i %{x-custom-header:last}i"

NOMBRE

varnishncsa - registrador de acceso de Varnish en formato NCSA

SINOPSIS

varnishncsa [-a] [-F formato] [-P pidfile] [-w archivo]

DESCRIPCION

varnishncsa es un registrador de acceso que genera registros en el formato del servidor web NCSA Common Log Format (CLF) o su formato extendido (ELF). lee los registros de acceso de Varnish de la entrada estándar por defecto.

Varnish utiliza el formato CLF para registrar solicitudes de acceso web. El formato CLF es un formato estándar utilizado por muchos servidores web. varnishncsa es la herramienta para generar dichos registros.

varnishncsa puede ser útil si necesita integrar los registros de Varnish con herramientas que esperan registros en formato NCSA.

MODOS

-a

Permite que varnishncsa se ejecute en modo de solo lectura, asumiendo que se registrará en un archivo y que el archivo se rotará automáticamente.

-F formato

Especifica el formato de registro de salida. Las opciones disponibles son:

  • %a: Dirección IP del cliente remoto.
  • %A: Dirección IP del servidor local.
  • %b: Bytes transferidos (sin las cabeceras HTTP).
  • %B: Bytes transferidos (incluidas las cabeceras HTTP).
  • %c: Estado de la conexión.
  • %C: Tiempo total de la solicitud en microsegundos.
  • %d: Indica si la solicitud fue servida desde la caché o desde el backend.
  • %D: Tiempo total de la solicitud en microsegundos.
  • %h: Host remoto.
  • %H: Protocolo de la solicitud.
  • %i: Cabecera de solicitud de entrada.
  • %l: Identidad del cliente remoto (normalmente inexistente).
  • %m: Método de la solicitud.
  • %N: Nombre del hilo del trabajador.
  • %o: Cabecera de respuesta de salida.
  • %p: Puerto del servidor local.
  • %r: Línea de solicitud (método, URL, protocolo).
  • %R: Referente.
  • %s: Código de estado HTTP.
  • %t: Marca de tiempo.
  • %T: Tiempo total de la solicitud en segundos.
  • %u: Usuario autenticado remoto.
  • %U: URL solicitada.
  • %v: Nombre del servidor (nombre de host del servidor).
  • %X: Estado de la conexión después de que se completa la solicitud.

Si no se especifica un formato, se utiliza el formato NCSA CLF por defecto.

-P pidfile

Escribe el ID del proceso (PID) del proceso varnishncsa en el archivo especificado por pidfile. Esto es útil para detener el proceso más tarde.

-w archivo

Escribe los registros en el archivo especificado en lugar de la salida estándar. Si se utiliza la opción -a, el archivo se abrirá en modo de añadir (append).

FORMATO

El formato por defecto es el NCSA Common Log Format (CLF):

%h %l %u %t "%r" %s %b "%R"

El formato extendido (ELF) es:

%h %l %u %t "%r" %s %b "%R" "%{User-agent}i" "%{Referer}i"

Puede definir su propio formato usando los especificadores de formato mencionados en la opción -F.

SEÑALES

varnishncsa responde a las siguientes señales:

SIGHUP

Vuelve a abrir el archivo de registro (si se especifica -w).

SIGUSR1

Cambia el nivel de depuración.

SIGUSR2

Cambia el modo de registro de salida (por ejemplo, de archivo a stdout o viceversa).

NOTAS

varnishncsa lee de la entrada estándar. Esto significa que puede ser utilizado en una tubería con varnishlog.

Por ejemplo, para generar un registro en formato NCSA CLF y guardarlo en un archivo:

varnishlog | varnishncsa -w /var/log/varnish/access.log

Para generar un registro en formato extendido y guardarlo en un archivo:

varnishlog -F '%h %l %u %t "%r" %s %b "%{User-agent}i" "%{Referer}i"' -w /var/log/varnish/access.log

EJEMPLO

Para ejecutar varnishncsa y registrar en un archivo llamado access.log en el directorio actual, con el formato por defecto:

varnishlog | varnishncsa -w access.log

Para ejecutar varnishncsa en modo de solo lectura y registrar en un archivo llamado access.log, rotando el archivo automáticamente:

varnishncsa -a -w /var/log/varnish/access.log
