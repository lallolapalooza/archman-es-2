NOMBRE

VCL-probe - Configuración de sondas de salud de backend

SONDAS DE SALUD DE BACKEND

Varnish puede configurarse para enviar periódicamente una solicitud para probar si un backend está respondiendo y, por lo tanto, está "saludable".

Las sondas se pueden configurar por backend:

backend foo {
    [...]
    .probe = {
        [...]
    }
}

Se les puede asignar nombres y compartirlas entre backends:

probe light {
    [...]
}
backend foo {
    .probe = light;
}
backend bar {
    .probe = light;
}

O se puede definir una sonda predeterminada, que se aplica a todos los backends sin un .probe específico configurado:

probe default {
    [...]
}

La sintaxis básica es la misma que para los backends:

probe nombre {
    .atributo1 = valor;
    .atributo2 = "valor";
    [...]
}

No hay atributos obligatorios, todos tienen valores predeterminados.

ATRIBUTO .URL

La URL a consultar. Por defecto es /:

.url = "/salud-sonda";

ATRIBUTO .REQUEST

Se puede utilizar para especificar una solicitud HTTP/1.1 completa que se enviará:

.request = "GET / HTTP/1.1"
    "Host: ejemplo.com"
    "X-Magic: Estamos bien con esto."
    "Connection: close";

A cada una de las cadenas se le añadirá CRLF y se añadirá un bloque de encabezado HTTP final que termine en CRLF.

Debido a que el cierre de la conexión es parte de la verificación de salud, Connection: close es obligatorio.

ATRIBUTO .EXPECTED_RESPONSE

El estado HTTP esperado, por defecto es 200:

.expected_response = 418;

ATRIBUTO .EXPECT_CLOSE

Si se espera o no que el backend cierre la conexión subyacente.

Acepta true o false, por defecto es true:

.expect_close = false;

Advertencia: cuando el backend no cierra la conexión, establecer expect_close en false hace que las tareas de sonda esperen hasta que expiren antes de inspeccionar la respuesta.

ATRIBUTO .TIMEOUT

Qué tan rápido debe tener éxito la sonda, por defecto son dos segundos:

.timeout = 10s;

ATRIBUTO .INTERVAL

Tiempo entre sondas, por defecto son cinco segundos:

.interval = 1m;

EL REGISTRO DE DESPLAZAMIENTO DE SALUD DE BACKEND

Las sondas de salud de backend utilizan un registro de desplazamiento de 64 etapas para recordar las sondas de salud más recientes y para evaluar la salud total del backend.

En la CLI, un buen estado de salud del backend se ve así:

varnish> backend.list -p boot.backend
Nombre de backend  Admin    Sonda     Salud      Último cambio
boot.backend    probe    5/5      saludable  Mié, 13 Ene 2021 10:31:50 GMT
 Estados actuales  buenos:  5 umbral:  4 ventana:  5
  Tiempo de respuesta promedio de sondas buenas: 0.000793
  Más antiguo ================================================== Más nuevo
  4444444444444444444444444444444444444444444444444444444444444444 IPv4 bueno
  XXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX Transmisión buena
  RRRRRRRRRRRRRRRRRRRRRRR----RRRRRRRRRRRRRRRRRRRRRRRRRRRRRRRRRRRRR Recepción buena
  HHHHHHHHHHHHHHHHHHHHHHH--------HHHHHHHHHHHHHHHHHHHHHHHHHHHHHHHHH Feliz

Comenzando desde abajo, la última línea muestra que este backend ha sido declarado "Feliz" para la mayoría de las 64 sondas de salud, pero hubo algunos problemas hace tiempo.

Sin embargo, en este caso, el .window está configurado en cinco y el .threshold está establecido en cuatro, por lo que en este momento, el backend se considera completamente saludable.

Un .initial adicional llena tantas entradas "felices" en el registro de desplazamiento cuando se carga el VCL, para que los backends puedan volverse saludables rápidamente, incluso si su salud normalmente se considera a lo largo de muchas muestras:

.interval = 1s;
.window = 60;
.threshold = 45;
.initial = 43;

Este backend se considerará saludable si tres de cada cuatro sondas de salud en el último minuto fueron buenas, pero se vuelve saludable tan pronto como ocurran dos sondas buenas después de que se cargue el VCL.

Los valores predeterminados son:

  • .window = 8
  • .threshold = 3
  • .initial = uno menos que .threshold

Tenga en cuenta que el .initial predeterminado significa que el backend se marcará como no saludable hasta que la primera respuesta de sonda sea exitosa. Esto significa que para los backends creados sobre la marcha (por vmods), no se puede usar el valor predeterminado para .initial, ya que el backend recién creado probablemente aún no estaría saludable cuando ocurra la solicitud del backend.

vcl-probe(7)

NAME

vmod_probe - Probe backend servers for health

SYNOPSIS

vcl_probe(backend_expression, probe_expression)

DESCRIPTION

The vcl_probe VMOD allows for programmatic health probing of backend servers.

This function should be called within a VCL subroutine, such as vcl_recv or vcl_backend_fetch. It takes two arguments:

  • backend_expression: An expression that evaluates to a backend or a list of backends.
  • probe_expression: An expression that evaluates to a probe definition.

The function attempts to probe the specified backend(s) using the given probe definition. The result of the probe (whether the backend is considered healthy or unhealthy) is stored and can be used in subsequent VCL logic.

PROBES

A probe definition is used to specify how a backend server should be checked for health. It consists of several components:

THE BACKEND SPECIFICATION

This refers to the backend(s) that the probe will be applied to. It can be a single backend name or a list of backends.

THE PROBE SPECIFICATION

This defines the actual probing mechanism. Common probe types include:

  • tcp(port): Probes by attempting to establish a TCP connection to the specified port.
  • http(url): Probes by sending an HTTP request to the specified URL and checking the response code.
  • send(data): Probes by sending arbitrary data and expecting a specific response.

Each probe type can have additional options, such as timeouts and expected response content.

THE INTERVAL ATTRIBUTE

The .interval attribute specifies how often the probe should be executed. It is typically defined in seconds.

Example: set my_probe.interval = 10s;

THE BACKEND HEALTH SHIFT REGISTER

The health status of a backend is maintained using a shift register. This allows for a certain number of consecutive failures before a backend is marked as unhealthy, and a certain number of consecutive successes before it is marked as healthy again. This helps to prevent flapping (rapidly changing health status) due to transient network issues.
