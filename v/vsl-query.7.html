NOMBRE

vsl-query - Expresiones de consulta VSL de Varnish

DESCRIPCIÓN GENERAL

Las Expresiones de Consulta VSL de Varnish extraen transacciones del registro de memoria compartida de Varnish, y realizan consultas sobre las transacciones antes de informar sobre las coincidencias.

Una transacción es un conjunto de líneas de registro que pertenecen juntas, por ejemplo, una solicitud del cliente o una solicitud del backend. La API monitoriza el registro y recopila todos los registros que componen una transacción antes de informar sobre esa transacción. Las transacciones también pueden agruparse, lo que significa que las transacciones del backend se informan junto con la transacción del cliente que las inició.

Se ejecuta una consulta sobre un grupo de transacciones. Una expresión de consulta es verdadera si hay un registro en el grupo que satisface la condición. Es falsa solo si ninguno de los registros satisface la condición. Las expresiones de consulta se pueden combinar utilizando funciones booleanas. Además de los registros, es posible consultar los identificadores de transacción (vxid) en la consulta.

AGRUPACIÓN

Al agrupar transacciones, existe una estructura jerárquica que muestra qué transacción inició qué. El nivel aumenta en uno en una relación 'iniciado por', por lo que, por ejemplo, una transacción de backend tendrá un nivel uno más alto que la transacción del cliente que la inició en una equivocación de caché. Las transacciones de reinicio de solicitud no incrementan su nivel para hacerlo predecible.

Los niveles comienzan a contarse desde 1, excepto cuando se usa crudo, donde siempre será 0.

Los modos de agrupación son:

  • session

    Se informan juntas todas las transacciones iniciadas por una conexión de cliente. Las conexiones de cliente son abiertas cuando se usan conexiones persistentes HTTP, por lo que es indefinido cuándo se informará la sesión. Si se excede el período de tiempo de espera de la transacción, se informará una sesión incompleta. Los datos no transaccionales (vxid == 0) no se informan.

  • request

    Las transacciones se agrupan por solicitud, donde el conjunto incluirá la solicitud en sí, así como cualquier solicitud de backend o subsolicitud ESI. Los datos de sesión y los datos no transaccionales (vxid == 0) no se informan.

  • vxid

    Las transacciones no se agrupan, por lo que cada vxid se informa en su totalidad. Se informan individualmente sesiones, solicitudes, subsolicitudes ESI y solicitudes de backend. Los datos no transaccionales no se informan (vxid == 0). Este es el valor predeterminado.

  • raw

    Cada registro de registro constituirá su propia transacción. Se informarán todos los datos, incluidos los datos no transaccionales.

Jerarquía de Transacciones

Ejemplo de jerarquía de transacciones utilizando el modo de agrupación de solicitudes

Nivel 1: Solicitud del cliente (equivocación de caché)
  Nivel 2: Solicitud de backend
  Nivel 2: Subsolicitud ESI (equivocación de caché)
    Nivel 3: Solicitud de backend
    Nivel 3: Solicitud de backend (reinicio VCL)
    Nivel 3: Subsolicitud ESI (equivocación de caché)
      Nivel 4: Solicitud de backend
  Nivel 2: Subsolicitud ESI (acierto de caché)

USO DE MEMORIA

La API utilizará punteros a datos del registro de memoria compartida tanto como sea posible para mantener el uso de memoria al mínimo. Pero como el registro de memoria compartida es un búfer circular, los datos se sobrescribirán eventualmente, por lo que la API crea copias locales de los datos de registro referenciados cuando varnishd se acerca a sobrescribir contenido aún no informado.

Este proceso evita la pérdida de datos de registro en muchos escenarios, pero no es infalible: todavía pueden ocurrir desbordamientos donde varnishd "adelanta" al proceso lector de registros en el búfer circular cuando los clientes de la API no pueden seguir leyendo y/o copiando, por ejemplo, debido a bloqueos de salida.

Aunque no está relacionado con la agrupación en principio, la copia de datos de registro es particularmente relevante para la agrupación de sesiones junto con conexiones de cliente de larga duración; para esta agrupación, es probable que el proceso cliente de la API consuma cantidades relevantes de memoria. Dado que la agrupación vxid también registra sesiones (potencialmente de larga duración), también es probable que requiera memoria para copias de entradas de registro, pero mucha menos que la agrupación de sesiones.

LENGUAJE DE CONSULTA

Una expresión de consulta consta de criterios de selección de registros, y opcionalmente un operador y un valor para comparar con los registros seleccionados.

<criterios de selección de registro> <operador> <operando>

Adicionalmente, una expresión de consulta puede ocurrir en la transacción misma en lugar de en los registros pertenecientes a la transacción.

vxid <operador numérico> <entero>

Una consulta vxid le permite apuntar directamente a una transacción específica, cuyo ID se puede obtener de una cabecera HTTP X-Varnish, la página de error predeterminada "guru meditation", o los registros Begin y Link.

Una consulta debe caber en una sola línea, pero es posible pasar varias consultas a la vez, una consulta por línea. Las líneas vacías se ignoran y la lista de consultas se trata como si se hubiera utilizado el operador 'or' para combinarlas.

Por ejemplo, esta lista de consultas:

# capturar errores de varnish
*Error
# capturar errores de backend
BerespStatus >= 500

es idéntica a esta consulta:

(*Error) o (BerespStatus >= 500)

Se pueden usar comentarios y serán ignorados, comienzan con el carácter '#', lo que puede ser más útil cuando la consulta se lee de un archivo.

Para consultas muy largas que no se puedan dividir fácilmente en múltiples consultas, es posible dividirlas en varias líneas con una barra invertida precediendo al final de la línea.

Por ejemplo, esta consulta:

BerespStatus >= 500

es idéntica a esta consulta:

BerespStatus \
>= \
500

Una secuencia de barra invertida-nueva línea no continúa un comentario en la siguiente línea y no está permitida en una cadena entre comillas.

Criterios de selección de registro

Los criterios de selección de registro determinan a qué tipo de registros del grupo de transacciones se aplica la expresión. Sintaxis:

{nivel}lista_etiquetas:prefijo_registro[campo]

La lista_etiquetas es obligatoria, los otros componentes son opcionales.

El nivel limita la expresión a una transacción en ese nivel. Si se deja sin especificar, la expresión se aplica a transacciones en todos los niveles. El nivel es un entero positivo o cero. Si el nivel va seguido de un carácter '+', expresa mayor o igual. Si el nivel va seguido de un '-', expresa menor o igual.

La lista_etiquetas es una lista separada por comas de etiquetas de registro VSL contra las cuales se verificará esta expresión. Cada elemento de la lista puede ser un nombre de etiqueta o un comodín de etiqueta. Los comodines permiten un '*' al principio o al final del nombre, y seleccionarán todas las etiquetas que coincidan con el prefijo o sufijo. Un solo '*' seleccionará todas las etiquetas.

El prefijo_registro limitará aún más las coincidencias a aquellos registros que tengan este prefijo como primera parte del contenido del registro seguido de dos puntos. La parte del registro de registro que se comparará se limitará a lo que sigue al prefijo y los dos puntos. Esto es útil al comparar con encabezados HTTP específicos. La coincidencia del prefijo del registro no distingue entre mayúsculas y minúsculas.

El campo, si está presente, tratará el registro de registro como una lista de campos separada por espacios en blanco, y solo se comparará la n-ésima parte del registro. Los campos comienzan a contarse desde 1.

Una expresión que utiliza solo un criterio de selección de registro será verdadera si hay algún registro en el grupo de transacciones que sea seleccionado por el criterio.

Operadores

Los siguientes operadores de comparación están disponibles:

  • == != < <= > >=

    Comparación numérica. El contenido del registro se convertirá a entero o flotante antes de la comparación, dependiendo del tipo del operando.

  • eq ne

    Comparación de cadenas. 'eq' prueba la igualdad de cadenas, 'ne' prueba la desigualdad.

  • ~ !~

    Coincidencia de expresiones regulares. '~' es una coincidencia positiva, '!~' es una no coincidencia.

Operando

El operando es el valor contra el cual se compararán los registros seleccionados.

Un operando puede ser citado o no citado. Las comillas pueden ser simples o dobles, y para operandos citados se puede usar una barra invertida para escapar las comillas.

Los operandos no citados solo pueden consistir en los siguientes caracteres:

a-z A-Z 0-9 + - _ . *

Los siguientes tipos de operandos están disponibles:

  • Entero

    Un número sin parte fraccionaria, válido para los operadores de comparación numérica. El tipo entero se utiliza cuando el operando no contiene ningún punto (.) ni caracteres de exponente (e). Sin embargo, si el registro se evalúa como un flotante, solo se utiliza su parte entera para la comparación.

  • Flotante

    Un número con una parte fraccionaria, válido para los operadores de comparación numérica. El tipo flotante se utiliza cuando el operando contiene un punto (.) o un carácter de exponente (e).

  • Cadena

    Una secuencia de caracteres, válida para los operadores de igualdad de cadenas.

  • Expresión regular

    Una expresión regular PCRE2. Válida para los operadores de expresiones regulares.

Funciones booleanas

Las expresiones de consulta se pueden enlazar utilizando funciones booleanas. Las siguientes están disponibles, en orden decreciente de precedencia:

  • not <expr>

    Invierte el resultado de <expr>

  • <expr1> and <expr2>

    Verdadero solo si ambos expr1 y expr2 son verdaderos

  • <expr1> or <expr2>

    Verdadero si alguno de expr1 o expr2 es verdadero

Las expresiones se pueden agrupar utilizando paréntesis.

EJEMPLOS DE EXPRESIONES DE CONSULTA

•
El grupo de transacciones contiene una URL de solicitud que es igual a "/foo"
ReqURL eq "/foo"
•
El grupo de transacciones contiene una cabecera de cookie de solicitud
ReqHeader:cookie
•
El grupo de transacciones no contiene una cabecera de cookie de solicitud
not ReqHeader:cookie
•
Solicitud del cliente donde el manejo interno tardó más de 800 ms.:
Timestamp:Process[2] > 0.8
•
El grupo de transacciones contiene una cabecera user-agent de solicitud que contiene "iPod" y el tiempo de entrega de la solicitud excede 1 segundo
ReqHeader:user-agent ~ "iPod" and Timestamp:Resp[2] > 1.
•
El grupo de transacciones contiene un estado de respuesta de backend mayor o igual a 500
BerespStatus >= 500
•
El grupo de transacciones contiene un estado de respuesta de 304, pero donde la solicitud no contenía una cabecera if-modified-since
RespStatus == 304 and not ReqHeader:if-modified-since
•
Transacciones que han tenido fallos de backend o tiempos de entrega largos en sus subsolicitudes ESI. (Asume el modo de agrupación de solicitudes).
BerespStatus >= 500 or {2+}Timestamp:Process[2] > 1.
•
Registra errores no transaccionales. (Asume el modo de agrupación directa).
vxid == 0 and Error
