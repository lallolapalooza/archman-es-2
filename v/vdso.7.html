vDSO(7) Manual de Información Miscelánea vDSO(7)

NOMBRE

vdso — descripción general del objeto compartido dinámico ELF virtual

SINOPSIS

#include <sys/auxv.h>
void *vdso = (uintptr_t) getauxval(AT_SYSINFO_EHDR);

DESCRIPCIÓN

El "vDSO" (virtual dynamic shared object - objeto compartido dinámico virtual) es una pequeña biblioteca compartida que el kernel mapea automáticamente en el espacio de direcciones de todas las aplicaciones de espacio de usuario. Las aplicaciones normalmente no necesitan preocuparse por estos detalles, ya que el vDSO es llamado más comúnmente por la biblioteca C. De esta manera, puedes codificar de forma normal utilizando funciones estándar y la biblioteca C se encargará de utilizar cualquier funcionalidad que esté disponible a través del vDSO.

¿Por qué existe el vDSO en primer lugar? Hay algunas llamadas al sistema que el kernel proporciona y que el código del espacio de usuario termina usando con frecuencia, hasta el punto en que tales llamadas pueden dominar el rendimiento general. Esto se debe tanto a la frecuencia de la llamada como a la sobrecarga de cambio de contexto que resulta al salir del espacio de usuario y entrar en el kernel.

El resto de esta documentación está dirigida a los curiosos y/o a los escritores de bibliotecas C, en lugar de a los desarrolladores en general. Si estás intentando llamar al vDSO en tu propia aplicación en lugar de usar la biblioteca C, lo más probable es que lo estés haciendo mal.

Ejemplo de antecedentes

Realizar llamadas al sistema puede ser lento. En sistemas de 32 bits x86, puedes activar una interrupción de software (int $0x80) para indicar al kernel que deseas realizar una llamada al sistema. Sin embargo, esta instrucción es costosa: pasa por las rutas completas de manejo de interrupciones en el microcódigo del procesador, así como en el kernel. Los procesadores más nuevos tienen instrucciones más rápidas (pero incompatibles hacia atrás) para iniciar llamadas al sistema. En lugar de requerir que la biblioteca C descubra si esta funcionalidad está disponible en tiempo de ejecución, la biblioteca C puede usar funciones proporcionadas por el kernel en el vDSO.

Ten en cuenta que la terminología puede ser confusa. En sistemas x86, la función vDSO utilizada para determinar el método preferido para realizar una llamada al sistema se llama "__kernel_vsyscall", pero en x86-64, el término "vsyscall" también se refiere a una forma obsoleta de preguntar al kernel qué hora es o en qué CPU se encuentra el llamador.

Una llamada al sistema utilizada con frecuencia es gettimeofday(2). Esta llamada al sistema es invocada tanto directamente por aplicaciones de espacio de usuario como indirectamente por la biblioteca C. Piensa en marcas de tiempo o bucles de temporización o sondeos — todos estos necesitan saber con frecuencia qué hora es ahora mismo. Esta información tampoco es secreta — cualquier aplicación en cualquier modo de privilegio (root o cualquier usuario no privilegiado) obtendrá la misma respuesta. Por lo tanto, el kernel se encarga de colocar la información necesaria para responder a esta pregunta en la memoria a la que el proceso puede acceder. Ahora una llamada a gettimeofday(2) cambia de una llamada al sistema a una llamada de función normal y unos pocos accesos a memoria.

Encontrar el vDSO

La dirección base del vDSO (si existe) es pasada por el kernel a cada programa en el vector auxiliar inicial (ver getauxval(3)), a través de la etiqueta AT_SYSINFO_EHDR.

No debes asumir que el vDSO está mapeado en ninguna ubicación particular en el mapa de memoria del usuario. La dirección base generalmente se aleatorizará en tiempo de ejecución cada vez que se cree una nueva imagen de proceso (en tiempo de execve(2)). Esto se hace por razones de seguridad, para prevenir ataques de "retorno a libc".

Para algunas arquitecturas, también existe una etiqueta AT_SYSINFO. Esta se usa solo para localizar el punto de entrada de vsyscall y frecuentemente se omite o se establece en 0 (lo que significa que no está disponible). Esta etiqueta es un vestigio del trabajo inicial de vDSO (ver *Historia* a continuación) y su uso debe evitarse.

Formato del archivo

Dado que el vDSO es una imagen ELF completamente formada, puedes realizar búsquedas de símbolos en ella. Esto permite agregar nuevos símbolos con versiones más nuevas del kernel y permite a la biblioteca C detectar la funcionalidad disponible en tiempo de ejecución cuando se ejecuta bajo diferentes versiones del kernel. A menudo, la biblioteca C realizará la detección con la primera llamada y luego almacenará en caché el resultado para llamadas posteriores.

Todos los símbolos también están versionados (utilizando el formato de versión GNU). Esto permite al kernel actualizar la firma de la función sin romper la compatibilidad hacia atrás. Esto significa cambiar los argumentos que acepta la función, así como el valor de retorno. Por lo tanto, al buscar un símbolo en el vDSO, siempre debes incluir la versión para que coincida con la ABI que esperas.

Típicamente, el vDSO sigue la convención de nombres de prefijar todos los símbolos con "__vdso_" o "__kernel_" para distinguirlos de otros símbolos estándar. Por ejemplo, la función "gettimeofday" se llama "__vdso_gettimeofday".

Utilizas las convenciones de llamada estándar de C al llamar a cualquiera de estas funciones. No necesitas preocuparte por un comportamiento extraño de registro o pila.

NOTAS

Fuente

Cuando compilas el kernel, compilará y enlazará automáticamente el código vDSO por ti. Frecuentemente lo encontrarás en el directorio específico de la arquitectura:


find arch/$ARCH/ -name '*vdso*.so*' -o -name '*gate*.so*'

Al rastrear llamadas al sistema con strace(1), los símbolos (llamadas al sistema) que son exportados por el vDSO no aparecerán en la salida del rastreo. Dichas llamadas al sistema tampoco serán visibles para los filtros de seccomp(2).

NOTAS ESPECÍFICAS DE ARQUITECTURA

Las subsecciones a continuación proporcionan notas específicas de la arquitectura sobre el vDSO.

Ten en cuenta que el vDSO que se utiliza se basa en la ABI de tu código de espacio de usuario y no en la ABI del kernel. Por lo tanto, por ejemplo, cuando ejecutas un binario ELF i386 de 32 bits, obtendrás el mismo vDSO independientemente de si lo ejecutas bajo un kernel i386 de 32 bits o bajo un kernel x86-64 de 64 bits. En consecuencia, el nombre de la ABI del espacio de usuario debe utilizarse para determinar qué sección a continuación es relevante.

Funciones parisc (hppa)

El puerto parisc tiene una página de código con funciones de utilidad llamada página de puerta de enlace. En lugar de usar el enfoque normal del vector auxiliar ELF, pasa la dirección de la página al proceso a través del registro SR2. Los permisos en la página son tales que la simple ejecución de esas direcciones se ejecuta automáticamente con privilegios de kernel y no en el espacio de usuario. Esto se hace para que coincida con la forma en que funciona HP-UX.

Dado que es solo una página de código cruda, no hay información ELF para realizar búsquedas de símbolos o versionado. Simplemente llame al desplazamiento apropiado a través de la instrucción de salto, por ejemplo:


ble <offset>(%sr2, %r0)
desplazamiento función
00b0 lws_entry (operaciones CAS)
00e0 set_thread_pointer (utilizado por glibc)
0100 linux_gateway_entry (syscall)

NAME

vdso - virtual dynamically linked shared object

SYNOPSIS

The Linux kernel exports a small amount of functionality to user space via a mechanism called the vDSO (virtual dynamically linked shared object). This functionality is implemented in kernel space, but it is mapped into the address space of every process, and it is callable from user space without requiring a system call context switch.

DESCRIPTION

The vDSO provides implementations for a small number of frequently used system calls that are safe to execute in user space. The primary advantage of the vDSO is performance, as it avoids the overhead of a kernel context switch.

The exact set of functions exported by the vDSO varies depending on the kernel version and the architecture. However, common functions include:

clock_gettime
Retrieves the time from a specified clock.
getcpu
Returns the current CPU number and NUMA node number.
gettimeofday
Retrieves the system's wall-clock time.
time
Retrieves the system's calendar time.

The vDSO is implemented as a shared library that is automatically mapped into the address space of each process. The dynamic linker resolves calls to these functions to the vDSO implementations when possible.

NOTES

The vDSO is designed to provide performance improvements for specific system calls. It is not intended to replace the regular system call interface.

The vDSO is architecture-specific and kernel version-specific. Applications should not rely on the presence or specific implementation of any vDSO functionality. If a vDSO function is not available, the system call will fall back to the traditional kernel implementation.

To determine if the vDSO is being used for a particular system call, you can use tools like `strace`. If the system call is executed without entering kernel mode, it is likely being handled by the vDSO.

The symbols exported by the vDSO are typically prefixed with `__vdso_`. For example, the vDSO implementation of `clock_gettime` is exported as `__vdso_clock_gettime`.

The table below lists the symbols exported by the vDSO. All of these symbols are also available without the `__vdso_` prefix, but you should ignore those and stick to the names below.

symbol version
__vdso_clock_gettime LINUX_2.6
__vdso_getcpu LINUX_2.6
__vdso_gettimeofday LINUX_2.6

History

The vDSO was originally just a single function—the vsyscall. In older kernels, you might see that name in a process's memory map rather than "vdso". Over time, people realized that this mechanism was a great way to pass more functionality to user space, so it was reconceived as a vDSO in the current format.
