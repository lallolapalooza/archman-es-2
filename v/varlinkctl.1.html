NOMBRE

varlinkctl - Introspección e invocación de servicios Varlink

SINOPSIS

varlinkctl [OPCIONES...] info DIRECCIÓN

varlinkctl [OPCIONES...] list-interfaces DIRECCIÓN

varlinkctl [OPCIONES...] list-methods DIRECCIÓN [INTERFAZ...]

varlinkctl [OPCIONES...] introspect DIRECCIÓN [INTERFAZ...]

varlinkctl [OPCIONES...] call DIRECCIÓN MÉTODO [ARGUMENTOS]

varlinkctl [OPCIONES...] --exec call call DIRECCIÓN MÉTODO ARGUMENTOS -- COMANDOS

varlinkctl [OPCIONES...] validate-idl [ARCHIVO]

DESCRIPCIÓN

varlinkctl se puede utilizar para la introspección e invocación de servicios Varlink[1].

Los servicios se referencian mediante una de las siguientes opciones:

•Una referencia de servicio Varlink que comienza con la cadena "unix:", seguida de una ruta absoluta del socket AF_UNIX, o por "@" y una cadena arbitraria (esta última para referenciar sockets en el espacio de nombres abstracto). En este caso, se establece una conexión de socket de flujo al socket especificado.
•Una referencia de servicio Varlink que comienza con la cadena "exec:", seguida de una ruta absoluta de un binario para ejecutar. En este caso, el proceso especificado se bifurca localmente, pasando un socket de flujo conectado.
•Una referencia de servicio Varlink que comienza con la cadena "ssh-unix:", seguida de una especificación de host SSH, seguida de ":", seguida de una ruta absoluta de socket AF_UNIX. (Esto requiere OpenSSH 9.4 o posterior en el lado del servidor, y los sockets del espacio de nombres abstracto no son compatibles).
•Una referencia de servicio Varlink que comienza con la cadena "ssh-exec:", seguida de una especificación de host SSH, seguida de ":", seguida de una línea de comandos. En este caso, se invoca el comando y el protocolo Varlink se habla en la entrada y salida estándar del comando invocado.

Para mayor comodidad, también se admiten las siguientes sintaxis de dirección de servicio más simples (redundantes):

•Una ruta del sistema de archivos a un socket AF_UNIX, ya sea absoluta (es decir, comienza con "/") o relativa (en cuyo caso debe comenzar con "./").
•Una ruta del sistema de archivos a un ejecutable, ya sea absoluta o relativa (como se indicó anteriormente, debe comenzar respectivamente con "/" o "./").

COMANDOS

Se entienden los siguientes comandos:

info DIRECCIÓN

Muestra información breve sobre el servicio especificado, incluyendo el nombre del proveedor y la lista de interfaces implementadas. Espera una dirección de servicio en uno de los formatos descritos anteriormente.

Añadido en la versión 255.

list-interfaces DIRECCIÓN

Muestra una lista de las interfaces implementadas por el servicio especificado. Espera una dirección de servicio en uno de los formatos descritos anteriormente.

Añadido en la versión 255.

list-methods DIRECCIÓN [INTERFAZ...]

Muestra una lista de los métodos implementados por el servicio especificado. Espera una dirección de servicio en uno de los formatos descritos anteriormente, así como uno o más nombres de interfaz. Si no se especifica ningún nombre de interfaz, lista todos los métodos de todas las interfaces implementadas por el servicio; de lo contrario, solo los métodos de las interfaces especificadas.

Añadido en la versión 257.

introspect DIRECCIÓN [INTERFAZ...]

Muestra las definiciones de interfaz de las interfaces especificadas proporcionadas por el servicio especificado. Espera una dirección de servicio en uno de los formatos descritos anteriormente y, opcionalmente, uno o más nombres de interfaz Varlink. Si no se especifican nombres de interfaz, muestra todas las interfaces proporcionadas por el servicio.

Añadido en la versión 255.

call DIRECCIÓN MÉTODO [ARGUMENTOS]

Invoc a el método especificado del servicio especificado. Espera una dirección de servicio en el formato descrito anteriormente, un nombre de método Varlink completamente calificado y un objeto de argumentos JSON. Si no se especifica el objeto de argumentos, se lee de STDOUT en su lugar. Para pasar una lista vacía de parámetros, especifique el objeto vacío "{}".

Los parámetros de respuesta se escriben como objetos JSON en STDOUT.

Añadido en la versión 255.

validate-idl [ARCHIVO]

Lee un archivo de definición de interfaz Varlink, lo analiza y valida, y luego lo muestra con resaltado de sintaxis. Esto verifica la sintaxis y la consistencia interna de la interfaz. Espera un nombre de archivo para leer la definición de la interfaz. Si se omite, lee la definición de la interfaz de STDIN.

Añadido en la versión 255.

help

Muestra ayuda de sintaxis de comandos.

Añadido en la versión 255.

OPCIONES

Se entienden las siguientes opciones:

--more

Cuando se usa con call: espera múltiples respuestas de método. Si se establece esta bandera, la llamada al método se envía con la bandera more establecida, lo que indica al servicio que genere varias respuestas, si es necesario. El comando permanece en ejecución hasta que el servicio envía un mensaje de respuesta que indica que es el último de la serie (o si se alcanza el tiempo de espera configurado, consulte a continuación). Esta bandera solo debe establecerse para llamadas a métodos que admitan este mecanismo.

Si se habilita este modo, la salida se cambia automáticamente al modo JSON-SEQ, de modo que los objetos de respuesta individuales se puedan distinguir fácilmente.

Este interruptor no tiene efecto en el tiempo de espera de la llamada al método aplicado por defecto. Independientemente de si se especifica --more o no, el tiempo de espera predeterminado será de 45 s. Use --timeout= (ver a continuación) para cambiar o deshabilitar el tiempo de espera. Al invocar una llamada a método que devuelve continuamente actualizaciones, generalmente es deseable deshabilitar el tiempo de espera con --timeout=infinity. Por otro lado, al invocar una llamada a método --more con el propósito de enumerar objetos (que probablemente se completará rápidamente), generalmente es beneficioso dejar habilitada la lógica de tiempo de espera, por razones de robustez.

Añadido en la versión 255.

-E

Un atajo para --more --timeout=infinity. Este interruptor es útil para llamadas a métodos que implementan suscripción a un flujo continuo de actualizaciones.

Añadido en la versión 257.

--collect

Esto es similar a --more, pero recopila todas las respuestas en una matriz JSON y la imprime, en lugar de en modo JSON-SEQ.

Añadido en la versión 256.

--oneway

Cuando se usa con call: no espere una respuesta de método. Si se establece esta bandera, la llamada al método se envía con la bandera oneway establecida (el comando sale inmediatamente después), lo que indica al servicio que no genere una respuesta.

Añadido en la versión 255.

--json=MODO

Selecciona el formato de salida JSON, ya sea "pretty" para una salida bien indentada y coloreada, o "short" para una salida concisa con un espacio mínimo y sin saltos de línea. El valor predeterminado es "short".

Añadido en la versión 255.

-j

Equivalente a --json=pretty cuando se invoca interactivamente desde una terminal. De lo contrario, es equivalente a --json=short, en particular cuando la salida se canaliza a otro programa.

Añadido en la versión 255.

--quiet, -q

Suprime la salida de las respuestas de las llamadas a métodos.

Añadido en la versión 257.

--graceful=

Toma un nombre de error Varlink calificado, es decir, un nombre de interfaz, con el sufijo de un nombre de error, separados por un punto, por ejemplo, "org.varlink.service.InvalidParameter". Asegura que, si una llamada a método falla con el error especificado, esto se tratará como un éxito, es decir, hará que la invocación de varlinkctl salga con un estado de salida cero. Esta opción se puede usar más de una vez para tratar varios errores diferentes como éxitos.

Añadido en la versión 257.

--timeout=

Espera un tiempo de espera en segundos como parámetro. Por defecto, se aplica un tiempo de espera de 45 s. Para desactivar el tiempo de espera, especifique "infinity" o una cadena vacía.

Añadido en la versión 257.

NAME

varlinkctl - A command line tool to invoke Varlink methods

SYNOPSIS

varlinkctl [-h] [--help] [--version] [--no-pager] [--verbose] [--verbose-exit] [--exec=command] [--push-fd=fd]   address call interface.method [parameters]

varlinkctl [-h] [--help] [--version] [--no-pager] [--verbose] [--verbose-exit] [--exec=command] [--push-fd=fd]   address info

varlinkctl [-h] [--help] [--version] [--no-pager] [--verbose] [--verbose-exit] [--exec=command] [--push-fd=fd]   address list-interfaces

varlinkctl [-h] [--help] [--version] [--no-pager] [--verbose] [--verbose-exit] [--exec=command] [--push-fd=fd]   address introspect [interface]

DESCRIPTION

varlinkctl is a command line tool to invoke Varlink methods on services reachable via Varlink. It can be used to query service information, list available interfaces and invoke methods.

The address is the address of the Varlink service. It typically looks like a path to a UNIX domain socket, e.g. /run/systemd/resolve/io.systemd.Resolve.

Common Varlink service addresses are:

/run/systemd/io.systemd.service
The systemd process itself.
/run/systemd/resolve/io.systemd.Resolve
The systemd-resolved.service(8) service.
/run/systemd/hostnamed/io.systemd.Hostname
The systemd-hostnamed.service(8) service.
/run/udevmon/io.systemd.udevmon
The udevmon.service(5) service.

Additionally, Varlink may be invoked over SSH. Addresses may take the form:

ssh:host:path/to/socket
Connect via SSH to host and use the UNIX domain socket at path/to/socket.
ssh-exec:host:service
Connect via SSH to host and execute the Varlink service named service. The service must be available in the $PATH of the remote user.

COMMANDS

The following commands are understood:

call interface.method [parameters]
Invoke the specified method of the specified interface. The parameters are specified as a JSON string. If not specified, an empty JSON object is used. The output of the method call is printed as a JSON string to standard output. If the method call fails, an error message is printed to standard error and varlinkctl exits with a non-zero exit code.
info
Print general information about the service.
list-interfaces
List all interfaces provided by the service.
introspect [interface]
Print the introspection information for the specified interface. If no interface is specified, all interfaces are introspected.

OPTIONS

The following options are understood:

--verbose, --verbose-exit

Enable verbose logging. --verbose-exit causes varlinkctl to exit with a non-zero exit code if verbose logging is enabled and the Varlink call fails.

--exec=command

Once the method call issued via call completed successfully, chainload the specified command line, with the method call output parameters serialized to JSON passed into standard input (and standard output and standard error inherited from the invoking process). Moreover any file descriptors passed back on the underlying communication socket are passed to the invoked process via the usual $LISTEN_FDS protocol. This functionality may be used to consume replies that come with associated file descriptors in a reasonable way.

Now that if --exec is specified the the third parameter to call is not optional (i.e. the method call parameters).

Added in version 258.

--push-fd=fd

Takes a numeric file descriptor number as parameter. May be used to pass a file descriptor along with the method call, if the underlying transport supports this. May be used multiple times to pass multiple file descriptors, retaining the order in which they are specified. The specified file descriptors must be passed to the varlinkctl invocation. Optionally, in place of a numeric file descriptor number an absolute or relative file system path (the latter must be prefixed with "./") may be specified, which is opened in read-only mode.

Added in version 258.

--no-pager

Do not pipe output into a pager.

-h, --help

Print a short help text and exit.

--version

Print a short version string and exit.

EXAMPLES

Example 1. Investigating a Service

The following three commands inspect the "io.systemd.Resolve" service implemented by systemd-resolved.service(8), listing general service information and implemented interfaces, and then displaying the interface definition of its primary interface:

$ varlinkctl info /run/systemd/resolve/io.systemd.Resolve
    Vendor: The systemd Project
   Product: systemd (systemd-resolved)
   Version: 254 (254-1522-g4790521^)
       URL: https://systemd.io/
Interfaces: io.systemd
            io.systemd.Resolve
            org.varlink.service
$ varlinkctl list-interfaces /run/systemd/resolve/io.systemd.Resolve
io.systemd
io.systemd.Resolve
org.varlink.service
$ varlinkctl introspect /run/systemd/resolve/io.systemd.Resolve io.systemd.Resolve
interface io.systemd.Resolve
type ResolvedAddress(
        ifindex: ?int,
        ...

(Interface definition has been truncated in the example above, in the interest of brevity.)

Example 2. Invoking a Method

The following command resolves a hostname via systemd-resolved.service(8)'s ResolveHostname method call.

$ varlinkctl call /run/systemd/resolve/io.systemd.Resolve io.systemd.Resolve.ResolveHostname '{"name":"systemd.io","family":2}' -j
{
        "addresses" : [
                {
                        "ifindex" : 2,
                        "family" : 2,
                        "address" : [
                                185,
                                199,
                                111,
                                153
                        ]
                }
        ],
        "name" : "systemd.io",
        "flags" : 1048577
}

Example 3. Investigating a Service Executable

The following command inspects the /usr/lib/systemd/systemd-pcrextend executable and the IPC APIs it provides. It then invokes a method on it:

# varlinkctl info /usr/lib/systemd/systemd-pcrextend
    Vendor: The systemd Project
   Product: systemd (systemd-pcrextend)
   Version: 254 (254-1536-g97734fb)
       URL: https://systemd.io/
Interfaces: io.systemd
            io.systemd.PCRExtend
            org.varlink.service
# varlinkctl introspect /usr/lib/systemd/systemd-pcrextend io.systemd.PCRExtend
interface io.systemd.PCRExtend
method Extend(
        pcr: int,
        text: ?string,
        data: ?string
) -> ()
# varlinkctl call /usr/lib/systemd/systemd-pcrextend io.systemd.PCRExtend.Extend '{"pcr":15,"text":"foobar"}'
{}

Example 4. Invoking a method remotely via SSH

The following command acquires a report about the identity of a remote host "somehost" from systemd-hostnamed.service(8) by connecting via SSH to the AF_UNIX socket the service listens on:

# varlinkctl call ssh-unix:somehost:/run/systemd/io.systemd.Hostname io.systemd.Hostname.Describe '{}'

To invoke a Varlink service binary directly on the remote host, rather than talking to a service via AF_UNIX can be done like this:

# varlinkctl call ssh-exec:somehost:systemd-creds org.varlink.service.GetInfo '{}'
