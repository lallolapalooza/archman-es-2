NOMBRE

VTC - Sintaxis de Casos de Prueba de Varnish

DESCRIPCIÓN GENERAL

Este documento describe la sintaxis utilizada por los archivos de Casos de Prueba de Varnish (.vtc). Un archivo vtc describe un escenario con diferentes entidades que hablan HTTP y, en general, una o más instancias de Varnish para probar.

ANÁLISIS SINTÁCTICO

Un archivo vtc se leerá palabra por palabra, con muy poca tokenización, lo que significa que un error de sintaxis no se detectará hasta que la prueba alcance la acción relevante en el test.

Un error de análisis sintáctico resultará en la mayoría de los casos en un assert activado. Si esto sucede, por favor, consulte el archivo fuente y el número de línea relacionados. Sin embargo, esta guía debería ayudarle a evitar los errores más comunes.

Palabras y cadenas

El analizador divide las palabras detectando caracteres de espacio en blanco y una cadena es una palabra, o una serie de palabras en la misma línea encerradas entre comillas dobles ("..."), o, para cadenas multilínea, encerradas entre llaves ({...}).

Comentarios

Se ignoran los espacios en blanco iniciales de las líneas. Las líneas vacías (o las que solo consisten en espacios en blanco) también se ignoran, al igual que las líneas que comienzan con "#", que son comentarios.

Líneas y comandos

Los archivos de prueba toman como máximo un comando por línea, siendo la primera palabra de la línea el comando y las siguientes sus argumentos. Para continuar en una nueva línea sin romper la cadena de argumentos, puede escapar el carácter de nueva línea (\n) con una barra invertida (\).

MACROS

Cuando se procesa una cadena, se realiza la expansión de macros. Las macros tienen el formato ${<nombre>[,<args>...]}, tienen un nombre seguido de una lista opcional de argumentos separados por comas o espacios. Se ignoran los espacios iniciales y finales.

Las macros ${foo,bar,baz} y ${ foo bar baz } son equivalentes. Si un argumento contiene un espacio o una coma, los argumentos pueden entrecomillarse. Por ejemplo, la macro ${foo,"bar,baz"} pasa un argumento bar,baz a la macro llamada foo.

A menos que se documente lo contrario, todas las macros son macros simples que no aceptan argumentos.

Macros incorporadas

${bad_backend}
Una dirección de socket que de forma fiable nunca aceptará conexiones.
${bad_ip}
Una dirección IPv4 improbable.
${date}
La fecha y hora actuales formateadas para HTTP.
${listen_addr}
La dirección de escucha por defecto que utilizan varios componentes, por defecto un puerto aleatorio en localhost.
${localhost}
La primera dirección IP que se resuelve a "localhost".
${pwd}
El directorio de trabajo desde el cual se ejecutó varnishtest.
${string,<accion>[,<args>...]}
La macro string es el punto de entrada para la generación de texto, toma una acción especializada con cada uno de sus propios conjuntos de argumentos.
${string,repeat,<uint>,<str>}
Repite uint veces la cadena str.
${testdir}
El directorio que contiene el script VTC de la ejecución del caso de prueba en curso.
${tmpdir}
El directorio de trabajo dedicado para la ejecución del caso de prueba en curso, que resulta ser también el directorio de trabajo actual. Útil cuando se necesita una ruta absoluta al directorio de trabajo.
${topbuild}
Solo está presente cuando se utiliza la opción -i, para trabajar en Varnish mismo en lugar de una instalación normal.

SINTAXIS

barrera

NOTA: Este comando está disponible en cualquier lugar donde se den comandos.

Las barreras permiten sincronizar diferentes hilos para asegurarse de que los eventos ocurran en el orden correcto. Incluso es posible utilizarlas en VCL.

Primero, es necesario declarar la barrera:

barrier bNOMBRE TIPO NUMERO [-cyclic]

Con los argumentos siendo:

bNOMBRE
este es el nombre de la barrera, usado para identificarla cuando se crearán puntos de sincronización. Debe comenzar con 'b'.
TIPO
puede ser "cond" (mutex) o "sock" (socket) y establece el comportamiento interno. Si no necesita sincronización VCL, use cond.
NUMERO
número de puntos de sincronización necesarios para pasar la barrera.
-cyclic
si está presente, la barrera se reiniciará y estará lista para otra ronda una vez que se haya pasado.

Luego, para añadir un punto de sincronización:

barrier bNOMBRE sync

Esto bloqueará el hilo padre hasta que el número de puntos de sincronización para bNOMBRE alcance el NUMERO dado en la declaración de la barrera.

Si desea sincronizar la VCL, necesita declarar una barrera "sock". Esto emitirá una definición de macro llamada "bNOMBRE_sock" que puede usar en VCL (después de importar el vmod vtc):

vtc.barrier_sync("${bNOMBRE_sock}");

Esta función devuelve 0 si todo salió bien y es el equivalente a barrier b NOMBRE sync en el nivel superior de VTC.

cliente/servidor

Los hilos cliente y servidor son entidades HTTP falsas utilizadas para probar su Varnish y VCL. Aceptan cualquier número de argumentos, y aquellos que no se reconocen, asumiendo que no comienzan con '-', se tratan como especificaciones, detallando las acciones a realizar:

client cNOMBRE [...]
server s NOMBRE [...]

Los clientes y servidores se identifican por una cadena que es el primer argumento, los nombres de los clientes comienzan con 'c' y los nombres de los servidores con 's'.

Dado que los comandos cliente y servidor comparten una buena parte de argumentos y acciones de especificación, se agrupan en esta única sección, y los elementos específicos se marcarán explícitamente como tales.

Argumentos

-start
Inicia el hilo en segundo plano, procesando la última especificación dada.
-wait
Bloquea hasta que el hilo termine.
-run (solo cliente)
Equivalente a "-start -wait".
-repeat NUMERO
En lugar de procesar la especificación solo una vez, hágalo NUMERO veces.
-keepalive
Para repeat, no abra nuevas conexiones, sino ejecute todas las iteraciones en la misma conexión.
-break (solo servidor
Detiene el servidor.
-listen CADENA (solo servidor
Dicta el socket de escucha para el servidor. CADENA es de la forma "IP PUERTO", o "/RUTA/AL/SOCKET" para un socket de dominio Unix. En este último caso, la ruta debe comenzar con '/', y el servidor debe ser capaz de crearla.
-connect CADENA (solo cliente)
Indica al servidor al que conectarse. CADENA también es de la forma "IP PUERTO", o "/RUTA/AL/SOCKET". Al igual que con "server -listen", se reconoce un socket de dominio Unix cuando CADENA comienza con '/'.
-dispatch (solo servidor , solo s0)
Normalmente, para mantener las cosas simples, los hilos del servidor solo manejan una conexión a la vez, pero el modificador -dispatch permite aceptar cualquier número de conexiones a

VARNISH_TEST

A regression test framework for Varnish

Synopsis

varnishtest [-all | -connect HOST:PORT] [-debug] [-help] [-log FILE] [-n NAME] [-N NAME] [-P PIDFILE] [-vcl VCLFILE] [-vcl+backend] [-?] [TESTSPEC ...]

Description

varnishtest is a framework for writing regression tests for Varnish HTTP accelerator.

A test specification is a simple domain-specific language. The language is specified in a string, either double-quoted "like this", but most of the time enclosed in curly brackets, allowing multilining. Write a command per line in it, empty lines are ignored, and long lines can be wrapped by using a backslash.

When no TESTSPEC is given, varnishtest will read from standard input.

varnishtest can simulate clients and servers. This is done by opening network sockets and communicating over them.

Each test block can be run with a specific VCL program, and this program can be specified inline with the -vcl flag or passed as a file. Alternatively, all declared servers are added as backends when -vcl+backend is used.

The varnishtest command may be followed by any number of options and TESTSPEC. The options are processed in the order they are given.

Options

-all
Run all tests. This is the default unless TESTSPEC is given.
-connect HOST:PORT
Connect to the Varnish server listening on HOST:PORT. This is the default unless the test explicitly opens a server socket.
-debug
Turn on debug output. This is verbose.
-help
Print a short help message and exit.
-log FILE
Write the test log to FILE.
-n NAME
This is a shorthand for varnishd's -n flag, and specifies which Varnish instance to use.
-N NAME
This is a shorthand for varnishd's -N flag, and specifies which Varnish instance to use.
-P PIDFILE
This is a shorthand for varnishd's -P flag, and specifies where to write the PID file.
-vcl VCLFILE
Load VCL from VCLFILE.
-vcl+backend
Load VCL from file, and all declared servers are added as backends.
Same as -help.

The following options are used to control the server side of the tests:

-listen IP:PORT
Listen on IP:PORT for incoming connections. Default is 127.0.0.1:8080.
-dispatch HOST:PORT
Listen on IP:PORT for incoming connections, and dispatch them to the specified Varnish server.

However, -dispatch is only allowed for the server name "s0".

-proxy1 STRING (client only)
Use the PROXY protocol version 1 for this connection. STRING is of the form "CLIENTIP:PORT SERVERIP:PORT".
-proxy2 STRING (client only)
Use the PROXY protocol version 2 for this connection. STRING is of the form "CLIENTIP:PORT SERVERIP:PORT [TLV [TLV ... ]]".

TLV is in the form name=val

name: 0xID or alpn, authority, crc32c, noop, unique_id, netns val: 0x... or string

ssl is currently not implemented (can be sent as hex)

Macros and automatic behaviour

To make things easier in the general case, clients will connect by default to a Varnish server called v1. To connect to a different Varnish server, use '-connect ${vNAME_sock}'.

The -vcl+backend switch of the varnish command will add all the declared servers as backends. Be careful though, servers will by default listen to the 127.0.0.1 IP and will pick a random port, and publish 3 macros: sNAME_addr, sNAME_port and sNAME_sock, but only once they are started. For 'varnish -vcl+backend' to create the vcl with the correct values, the server must be started first.

logexpect

La directiva logexpect procesará registros intentando hacer coincidir el primer patrón, y cuando termine, continuará procesando, intentando hacer coincidir el siguiente patrón. Si no se encuentra una coincidencia para un patrón, la prueba fallará.

Los hilos de logexpect se declaran de esta manera:

logexpect lNOMBRE -v <id> [-g <agrupacion>] [-d 0|1] [-q consulta] \
        [argumentos vsl] {
                expect <omitir> <vxid> <etiqueta> <regex>
                expect <omitir> <vxid> <etiqueta> <regex>
                fail add <vxid> <etiqueta> <regex>
                fail clear
                abortar
                ...
        } [-start|-wait|-run]

Y una vez declarados, puedes iniciarlos o esperar por ellos:

logexpect lNOMBRE <-start|-wait>

Con:

lNOMBRE
Nombre del hilo de logexpect, debe empezar con 'l'.
-v id
Especificar la instancia de varnish a utilizar (la mayoría de las veces, id=v1).
-g <sesion|solicitud|vxid|crudo
Decide cómo se agrupan los registros, ver -g en man varnishlog para más información.
-d <0|1>
Iniciar el procesamiento de los registros de log desde el principio del log en lugar del final.
-q consulta
Filtrar registros usando una expresión de consulta, ver man vsl-query para más información. No se admiten múltiples opciones -q.
-m
Emitir también registros de log para las fallas (solo para depuración)
-err
Invertir el significado del éxito. Normalmente se llama una vez para esperar que logexpect falle.
-start
Iniciar el hilo de logexpect en segundo plano.
-wait
Esperar a que el hilo de logexpect termine.
-run
Equivalente a "-start -wait".

Argumentos VSL (similares a las opciones de varnishlog):

-C
Usar expresiones regulares sin distinguir mayúsculas y minúsculas.
-i <lista de etiquetas>
Incluir etiquetas.
-I <[lista de etiquetas:]regex>
Incluir por regex.
-T <segundos>
Tiempo de espera para el fin de transacción.

Especificación de expect:

omitir: [entero sin signo|*|?]
Número máximo de registros a omitir.
vxid: [entero sin signo|*|=]
vxid a hacer coincidir.
etiqueta: [nombre de etiqueta|*|=]
Etiqueta a hacer coincidir.
regex:
expresión regular a hacer coincidir (opcional).

Para omitir, vxid y etiqueta, '*' coincide con cualquier cosa, '=' espera el valor del registro previamente coincidente. El marcador '?' es equivalente a cero, esperando una coincidencia en el siguiente registro. La diferencia es que '?' se puede usar cuando el orden de los registros individuales consecutivos no es determinista. En otras palabras, las líneas de un bloque de alternativas marcadas con '?' pueden coincidir en cualquier orden, pero todas deben coincidir eventualmente.

Especificación de fail:

add: Añadir a la lista de fallos

Los argumentos son equivalentes a expect, excepto por la omisión de omitir.

clear: Limpiar la lista de fallos

Cualquier número de especificaciones de fallos puede estar activo durante la ejecución de un logexpect. Todas las especificaciones de fallos activas se comparan con cada línea de log y, si alguna coincide, el logexpect falla inmediatamente.

Para que un logexpect termine con éxito, no debe haber especificaciones en la lista de fallos, por lo que los logexpects siempre deben terminar con

expect <omitir> <vxid> <etiqueta> <condición de terminación> fail clear

Especificación de abortar:

process

Ejecuta un proceso con stdin+stdout en una pseudo-terminal y stderr en una tubería.

La salida de la pseudo-terminal se copia literalmente a ${pNOMBRE_out}, y las banderas -log/-dump/-hexdump también la pondrán en el vtc-log.

stream

(nota: esta sección está en el nivel superior para facilitar la navegación, pero es parte de la especificación cliente/servidor)

Los streams se corresponden aproximadamente con una solicitud en HTTP/2, se envía una solicitud en el stream N, la respuesta también, luego el stream se descarta. La excepción principal es el primer stream, 0, que sirve como coordinador.

La sintaxis de stream sigue la del cliente/servidor:

stream ID [SPEC] [ACTION]

ID es el número de stream HTTP/2, mientras que SPEC describe lo que se hará en ese stream. Si ID tiene el valor next, el número de stream real se calcula basándose en el último.

Tenga en cuenta que, al analizar una acción de stream, si la entidad no está operando en modo HTTP/2, se ejecutan primero estas especificaciones:

txpri/rxpri # cliente/servidor
stream 0 {
    txsettings
    rxsettings
    txsettings -ack
    rxsettings
    expect settings.ack == true
} -run

Y luego se activa el modo HTTP/2 antes de analizar la especificación.

Acciones

-start
Ejecuta la especificación en un hilo, devolviendo el control inmediatamente.
-wait
Espera a que el hilo iniciado termine de ejecutar la especificación.
-run
equivalente a llamar -start luego -wait.

Especificación

La especificación de un stream sigue las mismas reglas exactas que las de un cliente o un servidor.

txreq, txresp, txcont, txpush

Estos cuatro comandos se refieren al envío de cabeceras. txreq y txresp enviarán tramas HEADER; txcont enviará tramas CONTINUATION; txpush tramas PUSH. La única diferencia entre txreq y txresp son las cabeceras predeterminadas establecidas por cada uno de ellos.

-noadd
No añadir cabeceras predeterminadas. Útil para evitar duplicados al enviar cabeceras predeterminadas usando -hdr, -idxHdr y -litIdxHdr.
-status INT (txresp)
Establecer la pseudo-cabecera :status.
-url STRING (txreq, txpush)
Establecer la pseudo-cabecera :path.
-method STRING (txreq, txpush)
Establecer la pseudo-cabecera :method.
-req STRING (txreq, txpush)
Alias de -method.
-scheme STRING (txreq, txpush)
Establecer la pseudo-cabecera :scheme.
-hdr STRING1 STRING2
Insertar una cabecera, siendo STRING1 el nombre y STRING2 el valor.
-idxHdr INT
Insertar una cabecera indexada, usando INT como índice.
-litIdxHdr inc|not|never INT huf|plain STRING
Insertar una cabecera literal indexada. El primer argumento especifica si la cabecera debe añadirse a la tabla, no, o no debe comprimirse si/cuando se retransmite.

INT es el índice del nombre de la cabecera a usar.

El tercer argumento informa sobre la codificación Huffman: sí (huf) o no (plain).

El último término es el valor literal de la cabecera.

-litHdr inc|not|never huf|plain STRING1 huf|plain STRING2
Insertar una cabecera literal, con el mismo primer argumento que -litIdxHdr.

Los términos segundo y tercero indican cuál es el nombre de la cabecera y si debe codificarse en Huffman, mientras que los dos últimos hacen lo mismo con respecto al valor.

-body STRING (txreq, txresp)
Especificar un cuerpo, insertando efectivamente STRING en una trama DATA después de enviar la trama de CABECERA.
-bodyfrom FILE (txreq, txresp)
Igual que -body pero el contenido se lee desde FILE.
-bodylen INT (txreq, txresp)
Hace lo mismo que -body pero genera una cadena de longitud INT para ti.
-gzipbody STRING (txreq, txresp)
Comprime STRING con gzip y lo envía como cuerpo.
-gziplen NUMBER (txreq, txresp)
Combina -bodylen y -gzipbody: genera una cadena de longitud NUMBER, la comprime con gzip y la envía como cuerpo.
-nostrend (txreq, txresp)
No establecer automáticamente el flag END_STREAM, haciendo que el par espere un cuerpo después de las cabeceras.
-nohdrend
No establecer automáticamente el flag END_HEADERS, haciendo que el par espere más tramas HEADER.
-dep INT (txreq, txresp)
Indica al par que este contenido depende del stream con el ID INT.
-ex (txreq, txresp)
Hace que la dependencia sea exclusiva (todavía se necesita -dep).
-weight (txreq, txresp)
Establece el peso para la dependencia.
-promised INT (txpush)
El ID del stream prometido.
-pad STRING / -padlen INT (txreq, txresp, txpush)
Añade la cadena como relleno a la trama, ya sea la que proporcionaste con -pad, o una que se genera para ti, de longitud INT en el caso de -padlen.

txdata

Por defecto, las tramas de datos están vacías. El receptor sabrá que se ha entregado todo el cuerpo gracias al flag END_STREAM establecido en la última trama DATA, y txdata lo establece automáticamente.

-data STRING
Datos a incrustar en la trama.
-datalen INT
Genera una cadena de longitud INT bytes para ser enviada en la trama.
-pad STRING / -padlen INT
Añade la cadena como relleno a la trama, ya sea la que proporcionaste con -pad, o una que se genera para ti, de longitud INT en el caso de -padlen.
-nostrend
No establecer el flag END_STREAM, permitiendo enviar más datos en este stream.

Estas son dos funciones de conveniencia para recibir las cabeceras y el cuerpo de una solicitud o respuesta entrante. La única diferencia es que rxreq solo puede ser utilizada por un servidor y rxresp por un cliente.

NAME

vtc - Varnish Test Controller

OVERVIEW

This manual page describes the Varnish Test Controller (VTC) commands. VTC is a tool for testing Varnish, but it is also a useful tool for anybody who want to automate Varnish.

The VTC command line syntax is:

vtc [-hv] [-D] [-l LEVEL] [-f FILE] [-N MASTER]

Arguments:

-h
Print usage.
-v
Print version.
-D
Daemonize.
-l LEVEL
Set the logging level. Supported levels are:
error
warning
info
debug
-f FILE
Use FILE as the test script.
-N MASTER
Use MASTER as the master Varnish instance. If not specified, it defaults to the vcl_name value of the first varnish command.

The VTC commands are executed in a VTC script file. VTC commands are used to control Varnish instances, both real and simulated.

A VTC script is a sequence of commands, executed in order. Commands are separated by newlines. Some commands may take arguments, and these are separated by spaces. Quoting rules are standard shell quoting rules.

Here is a list of the available commands:

varnish
Start a Varnish instance.

The syntax is:

varnish vNAME [-options]
    [-vcl file]
    [-vcl add file]
    [-vcl.conf file]
    [-vcl.reload]
    [-vcl.label file]
    [-vcl.commit]
    [-vcl.use LABEL]
    [-cliok file]
    [-prelude file]
    [-connect_timeout NUMBER]
    [-listen_port NUMBER]
    [-listen_address ADDRESS]
    [-admin_listen_port NUMBER]
    [-admin_listen_address ADDRESS]
    [-uui BOOLEAN]
    [-n WORKING_DIR]
    [-g CONFIG]
    [-S SHARED_SECRET]
    [-P PIDFILE]
    [-T ADDRESS]
    [-d]
    [-S file]
    [-M address]
    [-log-level LEVEL]
    [-log-facility FACILITY]
    [-log-format FORMAT]
    [-log-tag TAG]
    [-unix_socket PERMISSIONS]
    [-unix_socket_dir DIRECTORY]
    [-unix_socket_group GROUP]
    [-unix_socket_user USER]
    [-daemon]
    [-excutor EXECUTOR]
    [-exit CODE]
    [-shutdown]
    [-stop]
    [-wait]
    [-wait-running]
    [-wait-stopped]
    [-cleanup]
    [-expectexit NUMBER]

Where vNAME is the name of the varnish instance. This name is used to refer to the instance in other commands. The name must start with 'v'.

The options are:

-vcl file
Load the VCL configuration from file. This can be specified multiple times. The last one will be used.
-vcl.add file
Add the VCL configuration from file to the current VCL configuration. The new VCL code is appended to the existing code.
-vcl.conf file
Load the VCL configuration from file. This option is deprecated, use -vcl instead.

Reload the VCL configuration. The new configuration is loaded and compiled, but not yet activated. The active configuration remains the old one.

Once Varnish is started, you can control it with these additional switches:

-cli STRING
Send STRING to the CLI.
-cliok STRING
Send STRING to the CLI and expect a 200 OK response.
-clierr STATUS STRING
Send STRING to the CLI and expect a response with the given STATUS code.
-cliexpect REGEXP STRING
Send STRING to the CLI and expect a response that matches the given REGEXP.
-clijson STRING
Send STRING to the CLI, expect success (CLIS_OK/200) and check that the response is parsable JSON.

It is also possible to interact with its shared memory (as you would through tools like varnishstat) with additional switches:

-expect !PATTERN|PATTERN OP NUMBER|PATTERN OP PATTERN
Look into the VSM and make sure the first VSC counter identified by PATTERN has a correct value. OP can be ==, >, >=, <, <=. For example:
varnish v1 -expect SM?.s1.g_space > 1000000
varnish v1 -expect cache_hit >= cache_hit_grace

In the ! form the test fails if a counter matches PATTERN.

The MAIN. namespace can be omitted from PATTERN.

The test takes up to 5 seconds before timing out.

-vsc PATTERN
Dump VSC counters matching PATTERN.
-vsl_catchup
Wait until the logging thread has idled to make sure that all the generated log is flushed

You can refer to the different Varnish instances by their name. For example, if you have defined two Varnish instances, v1 and v2, you can specify which one you want to interact with using the -i option. For example:

varnish -i v1 -cli "status"
varnish -i v2 -expect cache_hit > 0

If no instance is specified, the command applies to the first Varnish instance defined in the script.

It is also possible to specify a Varnish instance by its address. For example:

varnish -i 127.0.0.1:6081 -cli "status"

You can also refer to the address of a Varnish instance using the VTC variable expansion. For example, if you have defined a Varnish instance named v1, you can refer to its listening address using the variable ${v1_addr} and its listening port using the variable ${v1_port}.

For example:

varnish -i ${v1_addr}:${v1_port} -cli "status"

This allows you to specify the hostname or IP address and port for each address vNAME listens to, like for example: ${vNAME_a0_addr}.

varnishtest

Alternate name for 'vtest', see above.

vsm

Interact with the shared memory of a varnish instance.

To define a VSM consumer, use this syntax:

vsm mNAME [-n STRING]

Arguments:

mNAME
Identify the VSM consumer, it must starts with 'm'.
-n STRING
Choose the working directory of the varnish instance. By default a VSM consumer connects to ${v1_name}.
-attach
Attach to a new varnish instance. Implicitly detach from the current varnish instance if applicable.
-detach
Detach from the current varnish instance.
-expect-status STRING
Check that the status of VSM matches the list of status flags from STRING. The expected status is represented as a comma-separated list of flags. The list of flags in STRING is not sensitive to the order of flags.

The available flags are:

  • mgt-running
  • mgt-changed
  • mgt-restarted
  • wrk-running
  • wrk-changed
  • wrk-restarted

Expecting a status automatically attaches to the varnish instance if that was not already the case.

vtest

This should be the first command in your vtc as it will identify the test case with a short yet descriptive sentence. It takes exactly one argument, a string, eg:

vtest "Check that vtest is actually a valid command"

It will also print that string in the log.
