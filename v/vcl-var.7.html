NOMBRE

VCL-VARIABLES - El álbum completo

DESCRIPCIÓN

Esta es una lista de todas las variables en el lenguaje VCL.

Los nombres de las variables toman la forma ámbito.variable[.índice], por ejemplo:

req.url
beresp.http.date
client.ip

Qué operaciones son posibles en cada variable se describe a continuación, a menudo con el atajo "backend" que cubre las subrutinas vcl_backend_* {} y "client" que cubre el resto, excepto vcl_init {} y vcl_fini {}.

local, server, remote y client

Estas variables describen la conexión de red entre el cliente y varnishd.

Sin PROXY protocol:

     client    server
     remote    local
       v          v
CLIENT ------------ VARNISHD

Con PROXY protocol:

     client    server   remote     local
       v          v       v          v
CLIENT ------------ PROXY ------------ VARNISHD

client.identity

Tipo: STRING

Legible desde: client, backend

Escribible desde: client

Identificación del cliente, utilizada para balanceo de carga en el director del cliente. Por defecto es client.ip

Esta variable puede ser sobrescrita con información más precisa, por ejemplo, extraída de una cabecera Cookie:.

client.ip

Tipo: IP

Legible desde: client, backend

La dirección IP del cliente, ya sea la misma que remote.ip o lo que nos dijo el PROXY protocol.

server.hostname

Tipo: STRING

Legible desde: todos

El nombre del host del servidor, tal como lo devuelve la función del sistema gethostname(3).

server.identity

Tipo: STRING

Legible desde: todos

La identidad del servidor, tal como se establece con el parámetro -i.

Si no se pasa un parámetro -i a varnishd, se utilizará el valor de retorno de la función del sistema gethostname(3).

server.ip

Tipo: IP

Legible desde: client, backend

La dirección IP del socket en el que se recibió la conexión del cliente, ya sea la misma que local.ip o lo que nos dijo el PROXY protocol.

remote.ip

Tipo: IP

Legible desde: client, backend

La dirección IP del otro extremo de la conexión TCP. Puede ser la IP del cliente o la IP de salida de un servidor proxy.

Si la conexión es un socket de dominio UNIX, el valor será 0.0.0.0:0

local.endpoint VCL >= 4.1

Tipo: STRING

Legible desde: client, backend

La dirección del socket '-a' sobre el que se aceptó la sesión.

Si el argumento fuera -a foo=:81 esto sería ":81"

local.ip

Tipo: IP

Legible desde: client, backend

La dirección IP (y el número de puerto) del extremo local de la conexión TCP, por ejemplo 192.168.1.1:81

Si la conexión es un socket de dominio UNIX, el valor será 0.0.0.0:0

local.socket VCL >= 4.1

Tipo: STRING

Legible desde: client, backend

El nombre del socket '-a' sobre el que se aceptó la sesión.

Si el argumento fuera -a foo=:81 esto sería "foo".

Tenga en cuenta que todos los '-a' reciben un nombre por defecto en la forma a%d si no se proporciona ningún nombre.

req y req_top

Estas variables describen la solicitud actual, y cuando se procesan solicitudes ESI:include, req_top apunta a la solicitud recibida del cliente.

req

Tipo: HTTP

Legible desde: client

La estructura de datos HTTP completa de la solicitud. Principalmente útil para pasar a VMODs.

req.backend_hint

Tipo: BACKEND

Legible desde: client

Escribible desde: client

Se establece bereq.backend en esto si intentamos obtener. Cuando se establece en un director, leer esta variable devuelve un backend real si el director se ha resuelto inmediatamente, o el director en caso contrario. Cuando se usa en contexto de cadena, devuelve el nombre del director o backend, respectivamente.

req.can_gzip

Tipo: BOOL

Legible desde: client

Verdadero si el cliente proporcionó gzip o x-gzip en la cabecera Accept-Encoding.

req.esi VCL <= 4.0

Tipo: BOOL

Legible desde: client

Escribible desde: client

Establecido en false para deshabilitar el procesamiento ESI independientemente de cualquier valor en beresp.do_esi. Por defecto es true. Esta variable es reemplazada por resp.do_esi en VCL 4.1.

req.esi_level

Tipo: INT

Legible desde: client

Un contador de cuántos niveles de solicitudes ESI estamos actualmente en.

req.filters

Tipo: STRING

Legible desde: vcl_recv

Escribible desde: vcl_recv

Lista de filtros del Procesador de Cuerpo de Varnish (VFP) por los que se pasará el cuerpo de la solicitud (req.body). El orden de izquierda a derecha significa el procesamiento de cliente a caché, es decir, el filtro más a la izquierda se ejecuta primero en el cuerpo tal como se recibe del cliente después de la decodificación de cualquier codificación de transferencia.

Los filtros VFP cambian el cuerpo antes de ser potencialmente almacenado en caché (por ejemplo, usando std.cache_req.body()) y/o ser manejado por el lado del backend, donde puede ser procesado nuevamente por bereq.filters.

Intentar establecer req.filters después de procesar el cuerpo de la solicitud (nuevamente, por ejemplo con std.cache_req.body()) desencadena un error de VCL.

req.grace

Tipo: DURATION

Legible desde: client

Escribible desde: client

No se puede establecer desde: client

Límite superior para la gracia del objeto.

Durante la búsqueda, se utilizará el mínimo de req.grace y la gracia almacenada del objeto como la gracia del objeto.

Al leer el valor no establecido, se devuelve como -1.

req.hash

Tipo: BLOB

Legible desde: vcl_hit, vcl_miss, vcl_pass, vcl_purge, vcl_deliver, vcl_synth, vcl_pipe

La clave hash de esta solicitud. Principalmente útil para pasar a VMODs, pero también puede ser útil para depurar el estado de acierto/fallo.

req.hash_always_miss

Tipo: BOOL

Legible desde: client

Escribible desde: client

Por defecto: false.

Forzar un fallo de caché para esta solicitud, incluso si hay objetos coincidentes perfectamente válidos en la caché.

Esto es útil para forzar la actualización de la caché sin invalidar las entradas existentes en caso de que la obtención falle.

req.hash_ignore_busy

Tipo: BOOL

Legible desde: client

Escribible desde: client

Por defecto: false.

Ignorar cualquier objeto ocupado durante la búsqueda en caché.

Solo querrá hacer esto cuando tenga dos servidores buscando contenido uno al lado del otro para evitar interbloqueos.

req.hash_ignore_vary

Tipo: BOOL

Legible desde: client

Escribible desde: client

Por defecto: false.

Ignorar las cabeceras vary de los objetos durante la búsqueda en caché.

req.http.*

Tipo: HEADER

Legible desde: cliente

Escribible desde: cliente

No se puede eliminar desde: cliente

Las cabeceras de la solicitud, cosas como req.http.date.

Las RFC permiten múltiples cabeceras con el mismo nombre, y tanto set como unset eliminarán todas las cabeceras con el nombre dado.

El nombre de cabecera * es un símbolo de VCL y como tal no puede, por ejemplo, empezar con un número. Para trabajar con cabeceras válidas que no se pueden representar como símbolos de VCL, es posible citar el nombre, como req.http."grammatically.valid". Ninguna de las cabeceras HTTP presentes en los registros IANA necesita ser citada, por lo que la sintaxis citada se desaconseja pero está disponible para interoperabilidad.

Algunas cabeceras que no se pueden manipular para la obtención o entrega correcta de HTTP están en modo de solo lectura.

beresp.filters

Type: STRING

Readable from: vcl_backend_response

Writable from: vcl_backend_response

List of Varnish Fetch Processor (VFP) filters the beresp.body will be pulled through. The order left to right signifies processing from backend to cache, iow the leftmost filter is run first on the body as received from the backend after decoding of any transfer encodings.

VFP Filters change the body before going into the cache and/or being handed to the client side, where it may get processed again by resp.filters.

The following VFP filters exist in varnish-cache:

  • gzip: compress a body using gzip
  • testgunzip: Test if a body is valid gzip and refuse it otherwise
  • gunzip: Uncompress gzip content
  • esi: ESI-process plain text content
  • esi_gzip: Save gzipped snippets for efficient ESI-processing

    This filter enables stitching together ESI from individually gzipped fragments, saving processing power for re-compression on the client side at the expense of some compression efficiency.

Additional VFP filters are available from VMODs.

By default, beresp.filters is constructed as follows:

  • gunzip gets added for gzipped content if beresp.do_gunzip or beresp.do_esi are true.
  • esi_gzip gets added if beresp.do_esi is true together with beresp.do_gzip or content is already compressed.
  • esi gets added if beresp.do_esi is true
  • gzip gets added for uncompressed content if beresp.do_gzip is true
  • testgunzip gets added for compressed content if beresp.do_gunzip is false.

After beresp.filters is set, using any of the beforementioned beresp.do_* switches is a VCL error.

resp.status 200 se cambiará a 304 por el código principal después de un return(deliver) desde vcl_deliver para solicitudes condicionales a contenido almacenado en caché si la validación tiene éxito.

Para la validación, primero se compara req.http.If-None-Match con resp.http.Etag. Si se comparan como iguales según las reglas de validación débil (ver RFC7232), se enviará un 304.

En segundo lugar, se compara req.http.If-Modified-Since con resp.http.Last-Modified o, si no está establecido o es débil, con el punto en el tiempo en que el objeto fue modificado por última vez basándose en las cabeceras Date y Age recibidas con la respuesta del backend que creó el objeto. Si el objeto no ha sido modificado basándose en esa comparación, se enviará un 304.

Variables especiales

now

Tipo: TIME

Legible desde: all

La hora actual, en segundos desde la época UNIX.

Cuando se convierte a STRING en expresiones, devuelve una marca de tiempo formateada como Tue, 20 Feb 2018 09:30:31 GMT

now permanece estable durante la duración de cualquier subrutina VCL integrada para hacer que los cálculos basados en el tiempo sean predecibles y evitar casos límite.

En otras palabras, incluso si se invierte una cantidad considerable de tiempo en VCL, now siempre representará el punto en el tiempo en que se ingresó la subrutina VCL incorporada respectiva. Por lo tanto, now no es adecuado para ningún tipo de medición de tiempo. Ver std.timestamp(), std.now() y std.timed_call() en vmod_std(3).
