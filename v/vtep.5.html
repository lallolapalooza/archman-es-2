NOMBRE

vtep - esquema de la base de datos hardware_vtep

Este esquema especifica las relaciones que un VTEP puede usar para integrar puertos físicos en switches lógicos mantenidos por un controlador de virtualización de red, como NSX.

Glosario:

VTEP
VXLAN Tunnel End Point (Punto final de túnel VXLAN), una entidad que origina y/o termina túneles VXLAN.
HSC
Hardware Switch Controller (Controlador de switch de hardware).
NVC
Network Virtualization Controller (Controlador de virtualización de red), por ejemplo, NSX.
VRF
Virtual Routing and Forwarding instance (Instancia de enrutamiento y reenvío virtual).

Columna Común

Algunas tablas contienen una columna llamada other_config. Esta columna tiene la misma forma y propósito dondequiera que aparezca, por lo que la describimos aquí para ahorrar espacio más adelante.

other_config: mapa de pares string-string
Pares clave-valor para configurar características raramente usadas o propietarias.
Algunas tablas no tienen la columna other_config porque aún no se han definido pares clave-valor para ellas.

Detalles:

switches: conjunto de Physical_Switchs
El switch físico o switches gestionados por el VTEP.
Cuando un switch físico integra soporte para este esquema VTEP, que se espera sea el caso más común, esta columna debería apuntar a un registro Physical_Switch que representa el switch en sí. En otra implementación posible, un servidor o una VM presenta una interfaz de esquema VTEP a uno o más switches físicos, comunicándose presumiblemente con esos switches físicos a través de un protocolo propietario. En ese caso, esta columna apuntaría a un Physical_Switch por cada switch físico, y el conjunto podría cambiar con el tiempo a medida que el servidor front-end represente un conjunto diferente de switches.

Características Principales:
target: cadena (debe ser único dentro de la tabla)
Método de conexión para los gestores.
Los siguientes métodos de conexión son compatibles actualmente:
ssl:host[:port]
El puerto SSL/TLS especificado (por defecto: 6640) en el host dado, que puede ser un nombre DNS (si se compila con la biblioteca unbound) o una dirección IP.
La configuración de la clave y el certificado SSL/TLS se realiza fuera de la base de datos.
tcp:host[:port]
El puerto TCP especificado (por defecto: 6640) en el host dado, que puede ser un nombre DNS (si se compila con la biblioteca unbound) o una dirección IP.
pssl:[port][:host]
Escucha conexiones SSL/TLS en el puerto TCP especificado (por defecto: 6640). Si se especifica un host, que puede ser un nombre DNS (si se compila con la biblioteca unbound) o una dirección IP, entonces las conexiones se restringen a la dirección IP local resuelta o especificada.
ptcp:[port][:host]
Escucha conexiones en el puerto TCP especificado (por defecto: 6640). Si se especifica un host, que puede ser un nombre DNS (si se compila con la biblioteca unbound) o una dirección IP, entonces las conexiones se restringen a la dirección IP local resuelta o especificada.
Detección y Manejo de Fallos del Cliente:
max_backoff: entero opcional, al menos 1.000
Número máximo de milisegundos a esperar entre intentos de conexión. El valor predeterminado depende de la implementación.
inactivity_probe: entero opcional
Número máximo de milisegundos de tiempo inactivo en la conexión con el cliente antes de enviar un mensaje de sondeo de inactividad. Si la base de datos Open vSwitch no se comunica con el cliente durante el número especificado de segundos, enviará un sondeo. Si no se recibe respuesta durante la misma cantidad adicional de tiempo, el servidor de base de datos asume que la conexión se ha roto e intenta reconectar. El valor predeterminado depende de la implementación. Un valor de 0 deshabilita los sondeos de inactividad.
Estado:
is_connected: booleano
verdadero si está actualmente conectado a este gestor, falso en caso contrario.
status : last_error: cadena opcional
Una descripción legible por humanos del último error en la conexión con el gestor; es decir, strerror(errno). Esta clave existirá solo si ha ocurrido un error.
status : state: cadena opcional, uno de ACTIVO, RETRASO, CONECTANDO, INACTIVO o VACÍO
El estado de la conexión con el gestor:
VACÍO
La conexión está deshabilitada.
RETRASO
Intentando reconectar con un período creciente.
CONECTANDO
Intentando conectar.
ACTIVO
Conectado, host remoto responde.
INACTIVO
La conexión está inactiva. Esperando respuesta de keep-alive.
Estos valores pueden cambiar en el futuro. Se proporcionan solo para consumo humano.
status : sec_since_connect: cadena opcional, que contiene un entero, al menos 0
El tiempo transcurrido desde que este gestor se conectó con éxito por última vez a la base de datos (en segundos). El valor está vacío si el gestor nunca se ha conectado con éxito.
status : sec_since_disconnect: cadena opcional, que contiene un entero, al menos 0
El tiempo transcurrido desde que este gestor se desconectó por última vez de la base de datos (en segundos). El valor está vacío si el gestor nunca se ha desconectado.
status : locks_held: cadena opcional
Lista separada por espacios de los nombres de los bloqueos OVSDB que la conexión mantiene. Omitido si la conexión no mantiene ningún bloqueo.
status : locks_waiting: cadena opcional
Lista separada por espacios de los nombres de los bloqueos OVSDB que la conexión está esperando adquirir actualmente. Omitido si la conexión no está esperando ningún bloqueo.
status : locks_lost: cadena opcional
Lista separada por espacios de los nombres de los bloqueos OVSDB que han sido robados a la conexión por otro cliente OVSDB. Omitido si no se han robado bloqueos a esta conexión.
status : n_connections: cadena opcional, que contiene un entero, al menos 2
Cuando target especifica un método de conexión que escucha conexiones entrantes (por ejemplo, ptcp: o pssl:) y hay más de una conexión activa, el valor es el número de conexiones activas. De lo contrario, este par clave-valor se omite.
Cuando hay varias conexiones activas, las columnas de estado y los pares clave-valor (aparte de este) informan el estado de una conexión elegida arbitrariamente.
Parámetros de Conexión:

Configuración adicional para una conexión entre el gestor y el servidor de base de datos.

other_config : dscp: cadena opcional, que contiene un entero
El Punto de Código de Servicio Diferenciado (DSCP) se especifica usando 6 bits en el campo Tipo de Servicio (TOS) en la cabecera IP. DSCP proporciona un mecanismo para clasificar el tráfico de red y proporcionar Calidad de Servicio (QoS) en redes IP. El valor DSCP especificado aquí se utiliza al establecer la conexión entre el gestor y el servidor de base de datos. Si no se especifica ningún valor, se elige un valor predeterminado de 48. Los valores DSCP válidos deben estar en el rango de 0 a 63.

Un extremo que no reciba mensajes de control de BFD durante un período de tres veces la tasa de recepción esperada, señalará una falla de conectividad. En el caso de un problema de conectividad unidireccional, el sistema que no recibe mensajes de control de BFD se lo comunicará a su par en los mensajes que transmita.

Se espera que un VTEP de hardware utilice BFD para determinar la alcanzabilidad de los dispositivos al final de los túneles con los que intercambia datos. Esto puede permitir que el VTEP elija un nodo de servicio que funcione entre un conjunto de nodos de servicio que brindan alta disponibilidad. También permite que la NVC informe el estado de salud de los túneles.

En muchos casos, el par BFD de un VTEP de hardware será una instancia de Open vSwitch. La implementación de BFD de Open vSwitch tiene como objetivo cumplir fielmente con los requisitos establecidos en la RFC 5880. Open vSwitch no implementa las funciones opcionales de autenticación ni de "modo de eco".

Configuración Local de BFD:

El HSC escribe los pares clave-valor en la columna bfd_config_local para especificar las configuraciones locales que se utilizarán para las sesiones BFD en este túnel.

bfd_config_local : bfd_dst_mac: cadena opcional
Se establece en una dirección Ethernet en el formato xx:xx:xx:xx:xx:xx para establecer la MAC esperada como destino para los paquetes BFD recibidos. El valor predeterminado es 00:23:20:00:00:01.
bfd_config_local : bfd_dst_ip: cadena opcional
Se establece en una dirección IPv4 para establecer la dirección IP que se espera como destino para los paquetes BFD recibidos. El valor predeterminado es 169.254.1.0.
Configuración Remota de BFD:

La columna bfd_config_remote es la contraparte remota de la columna bfd_config_local. La NVC escribe los pares clave-valor en esta columna.

bfd_config_remote : bfd_dst_mac: cadena opcional
Se establece en una dirección Ethernet en el formato xx:xx:xx:xx:xx:xx para establecer la MAC de destino que se utilizará para los paquetes BFD transmitidos. El valor predeterminado es 00:23:20:00:00:01.
bfd_config_remote : bfd_dst_ip: cadena opcional
Se establece en una dirección IPv4 para establecer la dirección IP que se utiliza como destino para los paquetes BFD transmitidos. El valor predeterminado es 169.254.1.1.
Parámetros de BFD:

La NVC configura pares clave-valor en la columna bfd_params para habilitar y configurar BFD.

bfd_params : enable: cadena opcional, ya sea true o false
Verdadero para habilitar BFD en este Tunnel. Si no se especifica, BFD no se habilitará por defecto.
bfd_params : min_rx: cadena opcional, que contiene un entero, como mínimo 1
El intervalo más corto, en milisegundos, en el que esta sesión BFD ofrece recibir mensajes de control BFD. El extremo remoto puede optar por enviar mensajes a una velocidad más lenta. El valor predeterminado es 1000.
bfd_params : min_tx: cadena opcional, que contiene un entero, como mínimo 1
El intervalo más corto, en milisegundos, en el que esta sesión BFD está dispuesta a transmitir mensajes de control BFD. Los mensajes se transmitirán realmente a una velocidad más lenta si el extremo remoto no está dispuesto a recibir tan rápido como se especifica. El valor predeterminado es 100.
bfd_params : decay_min_rx: cadena opcional, que contiene un entero
Un intervalo de recepción alternativo, en milisegundos, que debe ser mayor o igual a bfd_params:min_rx. La implementación debe cambiar de bfd_params:min_rx a bfd_params:decay_min_rx cuando no hay tráfico de datos entrante obvio en el túnel, para reducir el costo de CPU y ancho de banda de monitorear un túnel inactivo. Esta función puede ser deshabilitada estableciendo un valor de 0. Esta función se restablece cada vez que cambian bfd_params:decay_min_rx o bfd_params:min_rx.
bfd_params : forwarding_if_rx: cadena opcional, ya sea true o false
Cuando es true, el tráfico recibido en el Tunnel se utiliza para indicar la capacidad de E/S de paquetes. Los paquetes de control BFD aún se transmiten y reciben. Se debe recibir al menos un paquete de control BFD cada 100 * bfd_params:min_rx de tiempo. De lo contrario, incluso si se recibe tráfico, bfd_params:forwarding será false.
bfd_params : cpath_down: cadena opcional, ya sea true o false
Se establece en true para notificar al extremo remoto que el tráfico no debe ser reenviado a este sistema por alguna razón distinta a una falla de conectividad en la interfaz monitoreada. La razón subyacente típica es "concatenated path down", es decir, que la conectividad más allá del sistema local está caída. El valor predeterminado es false.
bfd_params : check_tnl_key: cadena opcional, ya sea true o false
Se establece en true para que BFD acepte solo mensajes de control con una clave de túnel cero. Por defecto, BFD acepta mensajes de control con cualquier clave de túnel.
Estado de BFD:

El VTEP establece pares clave-valor en la columna bfd_status para informar el estado de BFD en este túnel. Cuando BFD no está habilitado, con bfd_params:enable, el HSC borra todos los pares clave-valor de bfd_status.

bfd_status : enabled: cadena opcional, ya sea true o false
Se establece en true si la sesión BFD se ha habilitado correctamente. Se establece en false si el VTEP no puede admitir BFD o tiene recursos insuficientes para habilitar BFD en este túnel. La NVC deshabilitará el monitoreo BFD en el otro extremo del túnel una vez que este valor se establezca en false.
bfd_status : state: cadena opcional, uno de admin_down, down, init, o up
Informa el estado de la sesión BFD. La sesión BFD está completamente saludable y negociada si está UP.
bfd_status : forwarding: cadena opcional, ya sea true o false
Informa si la sesión BFD cree que este Tunnel puede ser utilizado para reenviar tráfico. Típicamente esto significa que la sesión local está señalando UP, y el sistema remoto no está señalando un problema como "concatenated path down".
bfd_status : diagnostic: cadena opcional
Un código de diagnóstico que especifica la razón del último cambio en el estado de la sesión por parte del sistema local. Los mensajes de error se definen en la sección 4.1 de [RFC 5880].
bfd_status : remote_state: cadena opcional, uno de admin_down, down, init, o up
Informa el estado de la sesión BFD del extremo remoto.
bfd_status : remote_diagnostic: cadena opcional
Un código de diagnóstico que especifica la razón del último cambio en el estado de la sesión por parte del sistema remoto. Los mensajes de error se definen en la sección 4.1 de [RFC 5880].
bfd_status : info: cadena opcional
Un mensaje corto que proporciona información adicional sobre el estado de BFD (posiblemente incluyendo las razones por las cuales BFD no pudo ser habilitado).

Details:

Port Configuration:
peer: optional string (references a Physical_Switch)
If the Physical_Switch manages more than one switch, this column identifies the switch to which this port belongs. If the Physical_Switch manages only one switch, then this column may be omitted.
vlan_bindings: map of integer-integer pairs, key in range 0 to 4,095
Maps VLAN IDs to logical switch identifiers. A key of 0 means that untagged traffic on the physical port is mapped to the specified logical switch. A non-zero key means that traffic tagged with that VLAN ID is mapped to the specified logical switch. A value of 0 in the VLAN field means that untagged traffic on the physical port is mapped to the logical switch.
acl_bindings: map of integer-ACL pairs, key in range 0 to 4,095
Attach Access Control Lists (ACLs) to the physical port. The column consists of a map of VLAN tags to ACLs. If the value of the VLAN tag in the map is 0, this means that the ACL is associated with the entire physical port. Non-zero values mean that the ACL is to be applied only on packets carrying that VLAN tag value. Switches will not necessarily support matching on the VLAN tag for all ACLs, and unsupported ACL bindings will cause errors to be reported. The binding of an ACL to a specific VLAN and the binding of an ACL to the entire physical port should not be combined on a single physical port. That is, a mix of zero and non-zero keys in the map is not recommended.
vlan_stats: map of integer-Logical_Binding_Stats pairs, key in range 0 to 4,095
Statistics for VLANs bound to logical switches on the physical port. An implementation that fully supports such statistics would populate this column with a mapping for every VLAN that is bound in vlan_bindings. An implementation that does not support such statistics or only partially supports them would not populate this column or partially populate it, respectively. A value of zero in the VLAN field refers to untagged traffic on the physical port.
Identification:
name: string
Symbolic name for the port. The name ought to be unique within a given Physical_Switch, but the database is not capable of enforcing this.
description: string
An extended description for the port.
Error Notification:

An entry in this column indicates to the NVC that the physical port has encountered a fault. The switch must clear this column when the error has been cleared.

port_fault_status : invalid_vlan_map: none
Indicates that a VLAN-to-logical-switch mapping requested by the controller could not be instantiated by the switch because of a conflict with local configuration.
port_fault_status : invalid_ACL_binding: none
Indicates that an error has occurred in associating an ACL with a port.
port_fault_status : unspecified_fault: none
Indicates that an error has occurred on the port but that no more specific information is available.
Common Column:

The overall purpose of this column is described under Common Column at the beginning of this document.

Per Logical-Switch Tunnel Key:

Tunnel protocols tend to have a field that allows the tunnel to be partitioned into sub-tunnels: VXLAN has a VNI, GRE and STT have a key, CAPWAP has a WSI, and so on. We call these generically ``tunnel keys.’’ Given that one needs to use a tunnel key at all, there are at least two reasonable ways to assign their values:

•
Per Logical_Switch+Physical_Locator pair. That is, each logical switch may be assigned a different tunnel key on every Physical_Locator. This model is especially flexible.
In this model, Physical_Locator carries the tunnel key. Therefore, one Physical_Locator record will exist for each logical switch carried at a given IP destination.
•
Per Logical_Switch. That is, every tunnel associated with a particular logical switch carries the same tunnel key, regardless of the Physical_Locator to which the tunnel is addressed. This model may ease switch implementation because it imposes fewer requirements on the hardware datapath.
In this model, Logical_Switch carries the tunnel key. Therefore, one Physical_Locator record will exist for each IP destination.
tunnel_key: optional integer
This column is used only in the tunnel key per Logical_Switch model (see above), because only in that model is there a tunnel key associated with a logical switch.
For vxlan_over_ipv4 encapsulation, when the tunnel key per Logical_Switch model is in use, this column is the VXLAN VNI that identifies a logical switch. It must be in the range 0 to 16,777,215.
Replication Mode:

For handling L2 broadcast, multicast and unknown unicast traffic, packets can be sent to all members of a logical switch referenced by a physical switch. There are different modes to replicate the packets. The default mode of replication is to send the traffic to a service node, which can be a hypervisor, server or appliance, and let the service node handle replication to other transport nodes (hypervisors or other VTEP physical switches). This mode is called service node replication. An alternate mode of replication, called source node replication involves the source node sending to all other transport nodes. Hypervisors are always responsible for doing their own replication for locally attached VMs in both modes. Service node replication mode is the default and considered a basic requirement because it only requires sending the packet to a single transport node.

replication_mode: optional string, either service_node or source_node
This optional column defines the replication mode per Logical_Switch. There are 2 valid values, service_node and source_node. If the column is not set, the replication mode defaults to service_node.
