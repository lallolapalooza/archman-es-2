VDE_CRYPTCAB(1) Manual de Comandos Generales VDE_CRYPTCAB(1)

NOMBRE

vde_cryptcab - gestor de cables cifrados de Ethernet Distribuida Virtual

SINOPSIS

vde_cryptcab [ -p núm_puerto ] [ -s ruta_socket ] [ -c [usuario_remoto@]host[:núm_puerto_remoto] ] [ -P clave_precompartida.key ]| [ -x ] [ -v [v][v][v] ] [ -k ] [ -d ]

DESCRIPCIÓN

Un vde_cryptcab es un gestor de cables distribuido para switches VDE. Permite que dos switches VDE en dos máquinas se comuniquen utilizando un canal cifrado ChaCha.

Cuando se utiliza en modo cliente (es decir, con la opción -c), genera una clave ChaCha aleatoria y utiliza scp(1) para transferir la clave al servidor remoto.

En el lado del cliente, la variable de entorno SCP_EXTRA_OPTIONS puede establecerse para añadir opciones a la línea de comandos de scp (esto es útil, por ejemplo, cuando se utiliza dropbear u otro cliente ssh no estándar para transferir la clave ChaCha).

Después de una fase de handshake de 4 vías para verificar las credenciales del cliente, el servidor y el cliente intercambiarán datagramas VDE encapsulándolos en criptogramas que se envían a través de udp a cada host remoto.

En el lado del servidor, se podría ejecutar:


vde_cryptcab -s /tmp/vde2.ctl -p 2100
Para iniciar un cryptcab servidor multi-peer, aceptando datagramas udp en el puerto 2100, que conecta cada cliente remoto autenticado a un puerto diferente del switch. De hecho, se inicia una nueva instancia de vde_plug(1) y se conecta al switch a través de un socket unix local.

El comando


vde_cryptcab -s /tmp/vde2.ctl -c foo@remote.machine.org:2100
conectará un cliente al servidor remoto, ejecutándose en el puerto udp 2100. En este punto, en el lado del servidor se requiere una verificación de las credenciales del usuario "foo", típicamente podría ser: autenticación basada en host, desafío de contraseña o autenticación de clave pública. Ver ssh(1) para más detalles.

Si los dos vde_switches se ejecutan como demonios y están conectados a interfaces tap, se establece un túnel cifrado de nivel 2.

OPCIONES

-p núm_puerto
Es posible decidir qué puerto udp local usar. Cuando esta opción no se especifica, cryptcab usará el número de puerto udp predeterminado, 7667.
-c [usuario_remoto@]host[:núm_puerto_remoto]
ejecuta vde_cryptcab en modo cliente, intentando conectarse a host. Tanto el parámetro usuario_remoto como núm_puerto_remoto no son requeridos. Si no se especifican, se usa el mismo usuario que ejecuta vde_cryptcab para la autenticación en el servidor, y se usa el puerto udp predeterminado 7667.
-s ruta_socket
especifica el socket UNIX que será usado por programas locales para unirse a VDE. El valor predeterminado es "/tmp/vde.ctl".
-P ruta_clave_precompartida.key
si se especifica, vde_cryptcab se ejecutará en modo de clave precompartida, en lugar de generar una clave aleatoria para transmitir con ssh. La opción dada es la ruta al archivo de clave simétrica precompartida a usar para el cifrado de datos. La misma clave debe ser usada tanto en el cliente como en el servidor.
-x
Desactiva el cifrado de clave simétrica.
-k
Envía paquetes periódicos de "keepalive" para evitar tiempos de espera del servidor. Útil cuando se desea mantener disponible un enlace de bajo tráfico.
-d
Ejecutar como demonio.
-v
Verborrea. (Usa -vv -vvv o -vvvv para más verbosidad)

PROBLEMAS CONOCIDOS

Encapsular paquetes IP en una capa de sesión+udp resulta en datagramas reales más grandes que la mtu del dispositivo tap. Dado que vde_cryptcab se confunde con la fragmentación de paquetes, la mtu del dispositivo tap debe establecerse a un valor menor que la mtu de la interfaz real. Usa ip(8) o ifconfig(8) para configurar la mtu de tu dispositivo tap.

Desactivar explícitamente el cifrado conduce a obvios problemas de seguridad. Se recomienda evitar el modo sin cifrar (-x) en redes no controladas.
