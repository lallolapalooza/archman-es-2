NOMBRE

varnishd - demonio acelerador HTTP

SINOPSIS

varnishd
[-a [nombre=][direccion_escucha[,PROTO|,opcion=valor,...]] [-b [host[:puerto]|ruta]] [-C] [-d] [-F] [-f config] [-h tipo[,opciones]] [-I archivo_cliente] [-i identidad] [-j carcel[,opciones_carcel]] [-l vsl] [-M direccion:puerto] [-n directorio_trabajo] [-P archivo] [-p parametro=valor] [-r parametro[,parametro...]] [-S archivo_secreto] [-s [nombre=]tipo[,opciones]] [-T direccion[:puerto]] [-t TTL] [-V] [-W waiter]

varnishd [-x parametro|vsl|cli|builtin|cadena_opciones]

varnishd [-?]

DESCRIPCIÓN

El demonio varnishd acepta peticiones HTTP de clientes, las pasa a un servidor backend y almacena en caché los documentos devueltos para satisfacer mejor las futuras peticiones del mismo documento.

OPCIONES

Opciones básicas

-a <[nombre=][direccion_escucha[,PROTO|,opcion=valor,...]]>
Sintaxis genérica para aceptar peticiones de clientes en una direccion_escucha. Ver más abajo para detalles.

El nombre se referencia en los logs y está disponible para vcl como local.socket. Si no se especifica el nombre, se usa a con una secuencia numérica ("a0", "a1", etc.).

Cualquier argumento después de la direccion_escucha separado por coma se toma como un par opcion=valor si contiene un =, o como una selección de PROTO(colo) de lo contrario.

Las opciones válidas dependen del tipo de aceptador, ver más abajo.

PROTO puede ser "HTTP" (el predeterminado) o "PROXY". Se pueden usar ambas versiones, 1 y 2, del protocolo proxy.

Se permiten múltiples argumentos -a.

Si no se proporciona ningún argumento -a, el valor predeterminado -a :80 escuchará en todas las interfaces IPv4 e IPv6.

-a <[nombre=][direccion_ip][:puerto][,PROTO]>
La direccion_ip puede ser un nombre de host ("localhost"), un cuádruple de puntos IPv4 ("127.0.0.1") o una dirección IPv6 encerrada entre corchetes ("[::1]")

El puerto puede ser un número de puerto (80), un nombre de servicio (http) o un rango de puertos (80-81). Los rangos de puertos son inclusivos y no pueden solaparse. Si no se especifica el puerto, se usa el puerto 80 (http).

Se requiere al menos una de las direcciones IP o puerto.

-a <[nombre=][ruta][,PROTO][,usuario=nombre][,grupo=nombre][,modo=octal]>
(VCL4.1 y superior)

Acepta conexiones en un socket de dominio Unix. La ruta debe ser absoluta ("/ruta/al/socket.sock") o "@" seguido del nombre de un socket abstracto ("@mivarnishd").

Los subargumentos usuario, grupo y modo pueden usarse para especificar los permisos del archivo de socket -- usa nombres para usuario y grupo, y un valor octal de 3 dígitos para modo. Estos subargumentos no se aplican a los sockets abstractos.

-b <[host[:puerto]|ruta]>
Usa el host especificado como servidor backend. Si no se especifica el puerto, el valor predeterminado es 8080.

Si el valor de -b comienza con /, se interpreta como la ruta absoluta de un socket de dominio Unix al que se conecta Varnish. En ese caso, el valor de -b debe cumplir las condiciones requeridas para el campo .path de una declaración de backend, ver vcl(7). Los backends con direcciones de socket Unix solo se pueden usar con versiones de VCL >= 4.1.

-b solo se puede usar una vez, y no junto con f.

-f config
Usa el archivo de configuración VCL especificado en lugar del predeterminado incorporado. Ver vcl(7) para detalles sobre la sintaxis VCL.

Si se usa una única opción -f, la instancia VCL cargada del archivo se llama "boot" y se activa inmediatamente. Si se usa más de una opción -f, las instancias VCL se llaman "boot0", "boot1" y así sucesivamente, en el orden correspondiente a los argumentos -f, y la última se llama "boot", que se activa.

O se debe especificar -b o una o más opciones -f, pero no ambas, y no se pueden dejar ambas sin especificar, a menos que se use -d para iniciar varnishd en modo de depuración. Si se especifica la cadena vacía como la única opción -f, entonces varnishd comienza sin iniciar el proceso de trabajo, y el proceso de gestión aceptará comandos CLI. También puedes combinar una opción -f vacía con un script de inicialización (opción -I) y el proceso hijo se iniciará si hay una VCL activa al final de la inicialización.

Cuando se usa con un nombre de archivo relativo, config se busca en vcl_path. Es posible establecer esta ruta antes de usar opciones -f con una opción -p. Durante el inicio, varnishd no se queja de rutas VCL inseguras: a diferencia de la interfaz varnish-cli(7) a la que se podría acceder más tarde de forma remota, iniciar varnishd requiere privilegios locales.

-n directorio_trabajo
Directorio de tiempo de ejecución para memoria compartida, VCLs compilados, etc.

En aplicaciones con requisitos de rendimiento críticos, este directorio debe estar en un sistema de archivos respaldado por RAM.

Al ejecutar múltiples instancias de varnishd, se necesitan directorios separados.

El valor predeterminado se toma de la variable de entorno VARNISH_DEFAULT_N.

Las rutas relativas se añadirán a /var/lib/varnish.

Si no están presentes ni VARNISH_DEFAULT_N ni -n, el valor es /var/lib/varnish/varnishd.

Nota: Estos valores predeterminados pueden ser específicos de la distribución.

Opciones de operaciones

-F
No bifurcar, ejecutar en primer plano. Solo se puede especificar -F o -d, y -F no se puede usar junto con -C.
-T <direccion[:puerto]>
Ofrece una interfaz de administración en la dirección y puerto especificados. Ver varnish-cli(7) para la documentación de los comandos de administración. Para deshabilitar la interfaz de administración, usa none.
-M <direccion:puerto>
Conéctate a este puerto y ofrece la interfaz de línea de comandos. Piensa en ello como un shell inverso. Al ejecutar con -M y no haber ningún backend definido, el proceso hijo (la caché) no se iniciará inicialmente.
-P archivo
>Escribir el PID del proceso en el archivo especificado.
-i identidad
Especificar la identidad del servidor Varnish. Esto se puede acceder usando server.identity desde VCL.

La identidad del servidor se utiliza para el campo received-by de las cabeceras Via generadas por Varnish. Por esta razón, debe ser un token válido tal como lo define la gramática HTTP.

Si no se especifica, se utiliza la salida de gethostname(3), en cuyo caso se asume que la sintaxis es correcta.

-I archivo_cli
Ejecutar los comandos de administración en el archivo dado como archivo_cli antes de que comience el proceso de trabajo, ver Archivo de Comandos CLI.

Opciones de ajuste

-t TTL
Especifica el tiempo de vida (TTL) por defecto para los objetos cacheados. Esto es un atajo para especificar el parámetro de tiempo de ejecución default_ttl.
-p <param=valor>
Establece el parámetro especificado por param al valor especificado, ver Lista de Parámetros para más detalles. Esta opción se puede usar múltiples veces para especificar múltiples parámetros.
-s <[nombre=]tipo[,opciones]>
Utiliza el backend de almacenamiento especificado. Ver la sección Backend de Almacenamiento.

Esta opción se puede usar múltiples veces para especificar múltiples archivos de almacenamiento. El nombre se referencia en logs, VCL, estadísticas, etc. Si no se especifica el nombre, se utilizan "s0", "s1" y así sucesivamente.

-l <vsl>
Especifica el tamaño del espacio para los registros VSL, atajo para -p vsl_space=<vsl>. Se pueden usar sufijos de escala como 'K' y 'M' hasta (G)igabytes. Ver vsl_space para más información.

Opciones de seguridad

-r <param[,param...]>
Hace que los parámetros listados sean de solo lectura. Esto da al administrador del sistema una forma de limitar lo que puede hacer la CLI de Varnish. Considere hacer que parámetros como cc_command, vcc_allow_inline_c y vmod_path sean de solo lectura, ya que estos pueden ser utilizados potencialmente para escalar privilegios desde la CLI.
-S archivo_secreto
Ruta a un archivo que contiene un secreto utilizado para autorizar el acceso al puerto de administración. Para deshabilitar la autenticación usar none.

Si no se proporciona este argumento, se escribirá un secreto obtenido del PRNG del sistema en un archivo llamado _.secret en el directorio de trabajo (ver opt_n) con la propiedad y permisos por defecto del usuario que inició varnish.

Por lo tanto, los usuarios que deseen delegar el control sobre varnish probablemente querrán crear un archivo secreto personalizado con los permisos apropiados (es decir, legible por un grupo de unix para delegar control).

-j <jail[,opciones_jail]>
Especifica el mecanismo de jail a utilizar. Ver la sección Jail.

Opciones avanzadas, de desarrollo y depuración

-d
Habilita el modo de depuración: El proceso padre se ejecuta en primer plano con una conexión CLI en stdin/stdout, y el proceso hijo debe iniciarse explícitamente con un comando CLI. Terminar el proceso padre también terminará el hijo.

Solo se puede especificar uno entre -d o -F, y -d no se puede usar junto con -C.

-C
Imprime el código VCL compilado a lenguaje C y sale. Especifica el archivo VCL a compilar con la opción -f. Se debe usar -f o -b con -C, y -C no se puede usar con -F o -d.
-V
Muestra el número de versión y sale. Esta debe ser la única opción.
-h <tipo[,opciones]>
Especifica el algoritmo de hash. Ver la sección Algoritmo de Hash para una lista de algoritmos soportados.
-W esperador
Especifica el tipo de esperador a utilizar.

Algoritmo de Hash

Los siguientes algoritmos de hash están disponibles:

-h critbit
Estructura de árbol autoescalable. El algoritmo de hash por defecto en Varnish Cache 2.1 y posteriores. En comparación con un árbol B más tradicional, el árbol critbit es casi completamente sin bloqueos. No cambies esto a menos que estés seguro de lo que estás haciendo.
-h simple_list
Una lista doblemente enlazada simple. No se recomienda para uso en producción.
-h <classic[,buckets]>
Una tabla hash estándar. La clave hash es el CRC32 de la URL del objeto módulo el tamaño de la tabla hash. Cada entrada de la tabla apunta a una lista de elementos que comparten la misma clave hash. El parámetro buckets especifica el número de entradas en la tabla hash. El valor por defecto es 16383.

Backend de Almacenamiento

Se pueden definir múltiples backends de almacenamiento (donde se mantienen los objetos cacheados y en tránsito), y VCL puede dirigir qué almacenamiento se utiliza estableciendo la variable beresp.storage (ver man vcl-var para más información).

El formato del argumento para definir los backends de almacenamiento es:

-s <[nombre]=tipo[,opciones]>
Si se omite nombre, Varnish nombrará los almacenes como sN, comenzando con s0 e incrementando N por cada nuevo almacén.

Para tipo y opciones ver los detalles a continuación.

Los almacenes se pueden usar en vcl como storage.nombre, así, por ejemplo, si myStorage se definió con -s myStorage=malloc,5G, se podría usar en VCL así:

set beresp.storage = storage.myStorage;

Un nombre especial es Transient, que es el almacenamiento por defecto para objetos no cacheados resultantes de un pass, hit-for-miss o hit-for-pass.

Si no se proporcionan opciones -s, el valor por defecto es:

-s default,100m

Si no se define ningún almacenamiento Transient, el valor por defecto es un almacenamiento default no limitado, como si se definiera como:

-s Transient=default

Los siguientes tipos de almacenamiento y opciones están disponibles:

-s <default[,tamaño]>
El tipo de almacenamiento por defecto se resuelve a umem cuando está disponible y a malloc en caso contrario.
-s <malloc[,tamaño]>
malloc es un backend basado en memoria.
-s <umem[,tamaño]>
umem es un backend de almacenamiento que es más eficiente que malloc en plataformas donde está disponible.

Ver la sección sobre umem en el capítulo Storage backends del The Varnish Users Guide para más detalles.

-s <file,ruta[,tamaño[,granularidad[,consejo]]]>
El backend de archivo almacena datos en un archivo en disco. El archivo se accederá usando mmap. Tenga en cuenta que este almacenamiento no proporciona persistencia de caché.

La ruta es obligatoria. Si la ruta apunta a un directorio, se creará un archivo temporal en ese directorio y se desvinculará inmediatamente. Si la ruta apunta a un archivo no existente, se creará el archivo.

Si se omite el tamaño y la ruta apunta a un archivo existente con un tamaño mayor que cero, se utilizará el tamaño de ese archivo. Si no, se informará de un error.

La granularidad establece el tamaño del bloque de asignación. Por defecto es el tamaño de página del sistema o el tamaño de bloque del sistema de archivos, el que sea mayor.

El consejo le dice al kernel cómo varnishd espera usar esta región mapeada para que el kernel pueda elegir las técnicas de lectura anticipada y caché apropiadas. Los valores posibles son normal, random y sequential, correspondientes al argumento de consejo de madvise() MADV_NORMAL, MADV_RANDOM y MADV_SEQUENTIAL, respectivamente. Por defecto es random.

-s <persistent,ruta,tamaño>
Almacenamiento persistente. Varnish almacenará objetos en un archivo de manera que asegurará la supervivencia de la mayoría de los objetos en caso de un apagado planificado o no planificado de Varnish. El backend de almacenamiento persistente tiene múltiples problemas y probablemente será eliminado de una futura versión de Varnish.

Jail

Los jails de Varnish son una generalización de varios métodos específicos de plataforma para reducir los privilegios de los procesos de varnish. Pueden tener opciones específicas. Los jails disponibles son:

-j <solaris[,worker=`privspec`]>
Reduce los privileges(5) para varnishd y los subprocesos al conjunto mínimo requerido. Solo disponible en plataformas que tienen la llamada setppriv(2).

El argumento opcional worker se puede usar para pasar una especificación de privilegios (ver ppriv(1)) por la cual extender el conjunto efectivo del proceso trabajador de varnish. Aunque los privilegios extendidos pueden ser requeridos por vmods personalizados, *no* usar la opción worker siempre es más seguro.

Ejemplo para otorgar privilegios básicos al proceso trabajador:

-j solaris,worker=basic
-j <linux[,transparent_hugepage=`thp_setting`][,`unixjailoption`...]>
Por defecto en plataformas Linux, extiende la cárcel UNIX con mecanismos específicos de Linux:
  • Advierte cuando workdir no está en un tmpfs.
  • Intenta mantener el volcado del proceso como volcable después de soltar privilegios.
  • Añade control sobre la configuración de la página grande transparente (THP).

thp_setting puede tomar estos valores:

  • ignore: No hacer nada
  • enable: Habilitar THP (ver Nota abajo)
  • disable: Deshabilitar THP
  • try-disable (por defecto): Intentar deshabilitar, ignorar fallo (pero emitir una advertencia)

Nota: Técnicamente, enable es "deshabilitar la deshabilitación", por lo que no necesariamente habilita THP. Los nombres de configuración se han elegido para evitar una doble negación confusa.

-j <unix[,user=`user`][,ccgroup=`group`][,workuser=`user`]>
Por defecto en todas las demás plataformas cuando varnishd se inicia con un UID efectivo de 0 ("como root").

Con el mecanismo de cárcel unix activado, varnish cambiará a un usuario alternativo para los subprocesos y cambiará el UID efectivo del proceso maestro siempre que sea posible.

El argumento opcional user especifica qué usuario alternativo utilizar. Por defecto es varnish.

El argumento opcional ccgroup especifica un grupo al que añadir los subprocesos de varnish que requieran acceso a un compilador c. No hay valor por defecto.

El argumento opcional workuser especifica un usuario alternativo para el proceso de trabajo. Por defecto es vcache.

Los usuarios dados para los argumentos user y workuser necesitan tener el mismo grupo principal ("de inicio de sesión").

Para configurar un sistema para los usuarios por defecto con un nombre de grupo varnish, se pueden utilizar comandos de shell similares a estos:

groupadd varnish
useradd -g varnish -d /nonexistent -s /bin/false \
  -c "Varnish-Cache Daemon User" varnish
useradd -g varnish -d /nonexistent -s /bin/false \
  -c "Varnish-Cache Worker User" vcache
-j none
Opción de cárcel de último recurso: Con el mecanismo de cárcel none, varnish ejecutará todos los procesos con los privilegios con los que se inició.

Interfaz de Gestión

Si se especificó la opción -T, varnishd ofrecerá una interfaz de gestión de línea de comandos en la dirección y puerto especificados. La forma recomendada de conectarse a la interfaz de gestión de línea de comandos es a través de varnishadm(1).

Los comandos disponibles se documentan en varnish-cli(7).

Archivo de Comandos CLI

La opción -I permite ejecutar comandos de gestión arbitrarios al lanzar varnishd, antes de que se inicie el proceso de trabajo. En particular, esta es la forma de cargar configuraciones, aplicarles etiquetas y hacer que una instancia de VCL que utilice esas etiquetas esté activa al inicio:

vcl.load panic /etc/varnish_panic.vcl
vcl.load siteA0 /etc/varnish_siteA.vcl
vcl.load siteB0 /etc/varnish_siteB.vcl
vcl.load siteC0 /etc/varnish_siteC.vcl
vcl.label siteA siteA0
vcl.label siteB siteB0
vcl.label siteC siteC0
vcl.load main /etc/varnish_main.vcl
vcl.use main

Cada línea del archivo, incluida la última, debe ir seguida de un salto de línea o retorno de carro, o de lo contrario se considerará truncada, lo que supone un error fatal.

Si un comando en el archivo va precedido de '-', el fallo no abortará el inicio.

Tenga en cuenta que es necesario incluir un comando explícito de vcl.use para seleccionar qué VCL debe ser la VCL activa al depender del Archivo de Comandos CLI para cargar las configuraciones al inicio.

PARÁMETROS DE TIEMPO DE EJECUCIÓN

Los parámetros de tiempo de ejecución se pueden establecer durante el inicio con la opción de línea de comandos -p para varnishd(1) o a través de la CLI usando los comandos param.set o param.reset. Se pueden bloquear durante el inicio con la opción de línea de comandos -r.

Unidades de Parámetros de Tiempo de Ejecución

Hay diferentes tipos de parámetros que pueden aceptar una lista de valores específicos, u opcionalmente tomar un sufijo de unidad.

bool

Un parámetro booleano acepta los valores on y off.

También reconocerá los siguientes valores:

  • yes y no
  • true y false
  • enable y disable

bytes

Un parámetro de bytes requiere uno de los siguientes sufijos de unidad:

  • b (bytes)
  • k (kibibytes, 1024 bytes)
  • m (mebibytes, 1024 kibibytes)
  • g (gibibytes, 1024 mebibytes)
  • t (tebibytes, 1024 gibibytes)
  • p (pebibytes, 1024 tebibytes)

Las unidades multiplicadoras pueden ir seguidas de una b adicional. Por ejemplo, 32k es equivalente a 32kb. Las unidades de bytes no distinguen entre mayúsculas y minúsculas.

segundos

Un parámetro de duración puede aceptar los siguientes sufijos de unidad:

  • ms (milisegundos)
  • s (segundos)
  • m (minutos)
  • h (horas)
  • d (días)
  • w (semanas)
  • y (años)

Si el parámetro es un tiempo de espera o un plazo límite, un valor de "never" (cuando esté permitido) desactiva el efecto del parámetro.

Indicadores de Parámetros de Tiempo de Ejecución

Los parámetros de tiempo de ejecución están marcados con indicadores abreviados para evitar repetir el mismo texto una y otra vez en la tabla siguiente. El significado de los indicadores es:

  • experimental

    No tenemos información sólida sobre valores buenos/malos/óptimos para este parámetro. Se agradecen comentarios con experiencias y observaciones.

  • delayed

    Este parámetro se puede cambiar sobre la marcha, pero no tendrá efecto inmediato.

  • restart

    El proceso de trabajo debe detenerse y reiniciarse antes de que este parámetro tenga efecto.

  • reload

    Los programas VCL deben recargarse para que este parámetro tenga efecto.

  • wizard

    No tocar a menos que sepas realmente lo que estás haciendo.

  • only_root

    Solo funciona si varnishd se ejecuta como root.

Excepciones de Valores Predeterminados en Sistemas de 32 bits

Tenga en cuenta que en sistemas de 32 bits, ciertos valores predeterminados o máximos se reducen en comparación con los valores que se enumeran a continuación, para conservar el espacio de VM:

  • workspace_client: 24k
  • workspace_backend: 20k
  • http_resp_size: 8k
  • http_req_size: 12k
  • gzip_buffer: 4k
  • vsl_buffer: 4k
  • vsl_space: 1G (máximo)
  • thread_pool_stack: 64k

Lista de Parámetros

Este texto se produce a partir del mismo texto que encontrará en la CLI si utiliza el comando param.show:

accept_filter

NB: Este parámetro depende de una característica que no está disponible en todas las plataformas.

  • Unidades: bool
  • Por defecto: on (si su plataforma soporta filtros de aceptación)

Habilita los filtros de aceptación del kernel. Esto puede requerir la carga de un módulo del kernel para tener efecto cuando está habilitado.

Habilitar accept_filter puede evitar que algunas solicitudes lleguen a Varnish en primer lugar. Las solicitudes mal formadas pueden pasar desapercibidas y no aumentar el contador client_req_400. Las solicitudes GET o HEAD con cuerpo pueden ser bloqueadas por completo.

acceptor_sleep_decay

  • Por defecto: 0.9
  • Mínimo: 0
  • Máximo: 1
  • Indicadores: experimental

Si nos quedamos sin recursos, como descriptores de archivo o hilos de trabajo, el aceptador dormirá entre aceptaciones. Este parámetro reduce (multiplicativamente) la duración del sueño por cada aceptación exitosa. (es decir, 0.9 = reducir en un 10%)

acceptor_sleep_incr

  • Unidades: segundos
  • Por defecto: 0.000
  • Mínimo: 0.000
  • Máximo: 1.000
  • Indicadores: experimental

Si nos quedamos sin recursos, como descriptores de archivo o hilos de trabajo, el aceptador dormirá entre aceptaciones. Este parámetro controla cuánto más tiempo dormimos, cada vez que fallamos en aceptar una nueva conexión.

acceptor_sleep_max

  • Unidades: segundos
  • Predeterminado: 0.050
  • Mínimo: 0.000
  • Máximo: 10.000
  • Flags: experimental

Si nos quedamos sin recursos, como descriptores de archivos o hilos de trabajo, el aceptor dormirá entre aceptaciones. Este parámetro limita cuánto tiempo puede dormir entre intentos de aceptar nuevas conexiones.

auto_restart

  • Unidades: bool
  • Predeterminado: on

Reinicia automáticamente el proceso hijo/trabajador si muere.

backend_idle_timeout

  • Unidades: segundos
  • Predeterminado: 60.000
  • Mínimo: 1.000

Tiempo de espera antes de cerrar conexiones de backend no utilizadas.

backend_local_error_holddown

  • Unidades: segundos
  • Predeterminado: 10.000
  • Mínimo: 0.000
  • Flags: experimental

Al conectarse a backends, ciertos códigos de error (EADDRNOTAVAIL, EACCESS, EPERM) señalan una escasez de recursos locales o un problema de configuración para el cual reintentar los intentos de conexión puede empeorar la situación debido a la complejidad de las operaciones involucradas en el kernel. Este parámetro evita intentos de conexión repetidos durante la duración configurada.

ban_cutoff

  • Unidades: bans
  • Predeterminado: 0
  • Mínimo: 0
  • Flags: experimental

Expulsa el contenido de "long tail" de la caché para mantener el número de prohibiciones por debajo de este valor. 0 deshabilita.

Cuando este parámetro se establece en un valor distinto de cero, el "ban lurker" continúa trabajando en la lista de prohibiciones de arriba a abajo como de costumbre, pero cuando llega a la prohibición ban_cutoff-ésima, trata todos los objetos como si coincidieran con una prohibición y los expulsa de la caché. Como los objetos activamente utilizados se prueban contra la lista de prohibiciones en el momento de la solicitud y, por lo tanto, es probable que estén asociados con prohibiciones cerca de la parte superior de la lista, con ban_cutoff, se eliminan los objetos accedidos con menos frecuencia (la "long tail").

Este parámetro es una red de seguridad para evitar tiempos de respuesta deficientes debido a que las prohibiciones se prueban en el momento de la búsqueda. Establecer un corte intercambia el tiempo de respuesta por la eficiencia de la caché. El valor recomendado es proporcional a rate(bans_lurker_tests_tested) / n_objects mientras el "ban lurker" está trabajando, que es el número de prohibiciones que el sistema puede mantener. La latencia adicional debido a la prueba de prohibiciones en la solicitud está en el orden de ban_cutoff / rate(bans_lurker_tests_tested). Por ejemplo, para rate(bans_lurker_tests_tested) = 2M/s y una latencia tolerable de 100 ms, un buen valor para ban_cutoff puede ser 200K.

  • Unidades: segundos
  • Por defecto: 0.000
  • Mínimo: 0.000
  • Indicadores: experimental

Algunos sistemas (con errores) pueden necesitar un retraso corto (subsegundo) entre

een creando hilos. Establece esto a unos pocos milisegundos si ves que el contador 'threads_failed' crece demasiado.

  • Unidades: segundos
  • Predeterminado: 1.000
  • Mínimo: 0.010
  • Banderas: retrasado, experimental

Espera este tiempo después de destruir un hilo.

Esto controla la decadencia de los pools de hilos cuando están inactivos (o casi).

thread_pool_fail_delay

  • Unidades: segundos
  • Predeterminado: 0.200
  • Mínimo: 0.010
  • Banderas: experimental

Espera al menos este tiempo después de un fallo en la creación de un hilo antes de intentar crear otro hilo.

El fallo al crear un hilo de trabajo a menudo es una señal de que el final está cerca, porque el proceso se está quedando sin algún recurso. Este retraso intenta no precipitar el final innecesariamente.

Si los fallos en la creación de hilos son un problema, verifica que thread_pool_max no sea demasiado alto.

También puede ser útil aumentar thread_pool_timeout y thread_pool_min, para reducir la tasa a la que los hilos se destruyen y luego se recrean.

thread_pool_max

  • Unidades: hilos
  • Predeterminado: 5000
  • Mínimo: thread_pool_min
  • Banderas: retrasado

El número máximo de hilos de trabajo en cada pool.

No establezcas esto más alto de lo necesario, ya que los hilos de trabajo en exceso consumen RAM y CPU y generalmente solo obstaculizan la realización del trabajo.

thread_pool_min

  • Unidades: hilos
  • Predeterminado: 100
  • Mínimo: 5
  • Máximo: thread_pool_max
  • Banderas: retrasado

El número mínimo de hilos de trabajo en cada pool.

Aumentar esto puede ayudar a escalar más rápido desde situaciones de baja carga o cuando los hilos han expirado.

El mínimo técnico es de 5 hilos, pero se recomienda encarecidamente que este parámetro sea de al menos 10.

thread_pool_reserve

  • Unidades: hilos
  • Predeterminado: 0 (autoajuste: 5% de thread_pool_min)
  • Máximo: 95% de thread_pool_min
  • Banderas: retrasado

El número de hilos de trabajo reservados para tareas vitales en cada pool.

Las tareas pueden requerir que otras tareas se completen (por ejemplo, las solicitudes de clientes pueden requerir solicitudes de backend, las sesiones http2 requieren flujos, que requieren solicitudes). Esta reserva es para garantizar que las tareas de menor prioridad no impidan que las tareas de mayor prioridad se ejecuten incluso bajo alta carga.

El valor efectivo es de al menos 5 (el número de clases de prioridad internas), independientemente de este parámetro.

thread_pool_stack

  • Unidades: bytes
  • Predeterminado: 80k
  • Mínimo: sysconf(_SC_THREAD_STACK_MIN)
  • Banderas: retrasado

Tamaño de la pila de los hilos de trabajo. Es probable que el kernel redondee esto al múltiplo de 4k (o lo que sea que pueda ser page_size).

El tamaño de pila requerido está determinado principalmente por la profundidad del árbol de llamadas. Los factores determinantes más comunes relevantes en el código central de varnish son la (des)compresión GZIP, el procesamiento ESI y las coincidencias de expresiones regulares. Los VMODs también pueden requerir una cantidad significativa de pila adicional. La profundidad de anidamiento de los subs de VCL es otro factor, aunque típicamente no es predominante.

El tamaño de pila es por hilo, por lo que la memoria total máxima requerida para las pilas de hilos de trabajo está en el orden de tamaño = thread_pools x thread_pool_max x thread_pool_stack.

Por lo tanto, en particular para configuraciones con muchos hilos, mantener el tamaño de pila al mínimo ayuda a reducir la cantidad de memoria requerida por Varnish.

Por otro lado, thread_pool_stack debe ser lo suficientemente grande en todas las circunstancias, de lo contrario, varnish fallará debido a un desbordamiento de pila. Generalmente, un desbordamiento de pila se manifiesta como un error de segmentación (también conocido como segfault / SIGSEGV) con la dirección de fallo cerca del puntero de pila (sp).

A menos que el uso de la pila pueda reducirse, thread_pool_stack debe aumentarse cuando ocurra un desbordamiento de pila. Se recomienda establecerlo en incrementos del 150% al 200% hasta que cesen los desbordamientos de pila.

thread_pool_timeout

  • Unidades: segundos
  • Predeterminado: 300.000
  • Mínimo: 10.000
  • Banderas: retrasado, experimental

Umbral de inactividad de hilos.

Los hilos en exceso de thread_pool_min, que han estado inactivos durante al menos este tiempo, serán destruidos.

thread_pool_watchdog

  • Unidades: segundos
  • Predeterminado: 60.000
  • Mínimo: 0.100
  • Banderas: experimental

Vigilancia de cola de hilos atascada.

Si no se han liberado trabajos en cola durante este tiempo, el proceso trabajador se autocorrige.

thread_pools

  • Unidades: pools
  • Predeterminado: 2
  • Mínimo: 1
  • Máximo: 32
  • Banderas: retrasado, experimental

Número de pools de hilos de trabajo.

Aumentar el número de pools de trabajo disminuye la contención de bloqueos. Cada pool de trabajo también tiene un hilo aceptando nuevas conexiones, por lo que para tasas muy altas de nuevas conexiones entrantes en sistemas con muchos núcleos, puede ser necesario aumentar los pools de trabajo.

Demasiados pools desperdician recursos de CPU y RAM, y más de un pool por cada CPU es muy probable que sea perjudicial para el rendimiento.

Se puede aumentar sobre la marcha, pero las disminuciones requieren un reinicio para que surtan efecto, a menos que se establezca la bandera de depuración experimental drop_pools.

thread_queue_limit

  • Unidades: solicitudes
  • Predeterminado: 20
  • Mínimo: 0
  • Banderas: experimental

Longitud permitida de la cola de solicitudes por pool de hilos.

Esto establece el número de solicitudes que pondremos en cola, esperando un hilo disponible. Por encima de este límite, las sesiones se descartarán en lugar de ponerse en cola.

thread_stats_rate

  • Unidades: solicitudes
  • Predeterminado: 10
  • Mínimo: 0
  • Banderas: experimental

Los hilos de trabajo acumulan estadísticas y las vuelcan en los contadores de estadísticas globales si el bloqueo está libre cuando terminan un trabajo (solicitud/fetch, etc.). Este parámetro define el número máximo de trabajos que un hilo de trabajo puede manejar antes de que se vea obligado a volcar sus estadísticas acumuladas en los contadores globales.

timeout_idle

  • Unidades: segundos
  • Predeterminado: 5.000
  • Mínimo: 0.000
  • Máximo: 3600.000

Tiempo de espera de inactividad para las conexiones de cliente.

Una conexión se considera inactiva hasta que hemos recibido las cabeceras completas de la solicitud.

Este parámetro es particularmente relevante para las conexiones HTTP1 keepalive que se cierran a menos que se reciba la siguiente solicitud antes de que se alcance este tiempo de espera.

timeout_linger

  • Unidades: segundos
  • Predeterminado: 0.050
  • Mínimo: 0.000
  • Banderas: experimental

Cuánto tiempo permanece un hilo de trabajo en una sesión inactiva antes de entregarla al 'waiter'. Cuando las sesiones se reutilizan, hasta la mitad de todas las reutilizaciones ocurren dentro de los primeros 100 ms después de que la solicitud anterior se completa. Establecer esto demasiado alto resulta en que los hilos de trabajo no hacen nada por su sustento, establecerlo demasiado bajo solo significa que más sesiones dan un rodeo alrededor del 'waiter'.

transit_buffer

  • Unidades: bytes
  • Predeterminado: 0b
  • Mínimo: 0b

El número de bytes que Varnish almacena en búfer para fetch de backend en streaming no cacheados; en otras palabras, cuántos bytes lee Varnish del backend antes de lo que se ha enviado al cliente. Un valor cero significa que no hay límite, el objeto se obtiene lo más rápido posible.

Al tratar con clientes lentos, establecer este parámetro en un valor distinto de cero puede evitar que objetos grandes no cacheados se almacenen por completo cuando la intención es simplemente transmitirlos al cliente. Como resultado, una transacción de cliente lenta retiene una conexión de backend hasta el final de la entrega.

Este parámetro es el valor predeterminado para la variable VCL beresp.transit_buffer, que se puede usar para controlar el búfer de tránsito por solicitud de backend.
