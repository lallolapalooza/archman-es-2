NOMBRE

vdirsyncer - Documentación de vdirsyncer

  • Documentación
  • Código fuente

Vdirsyncer es una herramienta de línea de comandos para sincronizar calendarios y libretas de direcciones entre una variedad de servidores y el sistema de archivos local. El caso de uso más popular es sincronizar un servidor con una carpeta local y utilizar un conjunto de otros programas para modificar los eventos y contactos locales. Vdirsyncer puede entonces sincronizar esos cambios de vuelta al servidor.

Sin embargo, vdirsyncer no se limita a la sincronización entre clientes y servidores. También puede ser utilizado para sincronizar calendarios y/o libretas de direcciones directamente entre dos servidores.

¿CUÁNDO NECESITO VDIRSYNCER?

¿Por qué no Dropbox + todo.txt?

¿Qué hace el software de sincronización de archivos si ambos archivos han cambiado desde la última sincronización? La respuesta es ignorar la pregunta, sincronizar tan a menudo como sea posible y esperar lo mejor. Porque si se trata de un conflicto de sincronización, la mayoría de los servicios de sincronización no se atreven a fusionar archivos y crean dos copias en cada computadora. La fusión de las dos listas de tareas queda para el usuario.

Una mejor idea habría sido usar git para sincronizar el archivo todo.txt, que al menos es capaz de resolver algunos conflictos básicos.

¿Por qué no sincronización de archivos (Dropbox, git, ...) + vdir?

Dado que los vdirs son solo un montón de archivos, es obvio intentar la sincronización de archivos para sincronizar tus datos entre múltiples computadoras, como:

  • Syncthing
  • Dropbox o uno de los miles de servicios como este
  • unison
  • Simplemente git con un sshd.

Las desventajas de esas soluciones dependen en gran medida del programa de sincronización de archivos exacto elegido:

  • Al igual que con todo.txt, Dropbox y compañía son obviamente agnósticos/inconscientes del contenido de los archivos. Si un archivo ha cambiado en ambos lados, Dropbox simplemente copia ambas versiones a ambos lados.

    Esto es una buena idea si el usuario interactúa directamente con el sistema de archivos y es capaz de resolver conflictos por sí mismo. Aquí podría llevar a un comportamiento erróneo con, por ejemplo, khal, ya que ahora hay dos eventos con el mismo UID.

    Este punto no se aplica a git: tiene capacidades de fusión muy buenas, mejores que las que tiene vdirsyncer actualmente.

  • Dicha configuración no funciona en absoluto con teléfonos inteligentes. Vdirsyncer, por otro lado, se sincroniza con servidores CardDAV/CalDAV, a los que se puede acceder con, por ejemplo, DAVx⁵ u otras aplicaciones incluidas con los teléfonos inteligentes.

Instalación manual

Si su distribución no proporciona un paquete para vdirsyncer, aún puede usar el gestor de paquetes de Python, "pip". Primero, deberá asegurarse de que las siguientes cosas estén instaladas:

  • Python 3.8 a 3.13 y pip.
  • libxml y libxslt
  • zlib
  • Linux o macOS. Windows no es compatible, consulte la incidencia #535.

En sistemas Linux, usar el gestor de paquetes de la distribución es la mejor manera de hacerlo, por ejemplo, usando Ubuntu:

sudo apt-get install libxml2 libxslt1.1 zlib1g python3

pipx instalará vdirsyncer en ~/.local/pipx/venvs/vdirsyncer

pipx install vdirsyncer

La forma limpia y dura

~/vdirsyncer_env/bin/pip install vdirsyncer

Tendrás que poner la última línea en tu .bashrc o .bash_profile.

Configuración

NOTA:

  • El config.example del repositorio contiene una versión muy concisa de esto.
  • En este ejemplo configuramos la sincronización de contactos, pero la sincronización de calendarios funciona casi igual. Simplemente cambia type = "carddav" por type = "caldav" y fileext = ".vcf" por fileext = ".ics".
  • Echa un vistazo a la página de Problemas conocidos si algo no funciona como se planeó.

Por defecto, vdirsyncer busca su archivo de configuración en las siguientes ubicaciones:

  • El archivo apuntado por la variable de entorno VDIRSYNCER_CONFIG.
  • ~/.vdirsyncer/config.
  • $XDG_CONFIG_HOME/vdirsyncer/config, que normalmente es ~/.config/vdirsyncer/config. Ver la especificación XDG-Basedir.

El archivo de configuración debe comenzar con una sección general, donde el único parámetro requerido es status_path. El siguiente es un ejemplo mínimo:

[general]
status_path = "~/.vdirsyncer/status/"

Después de la sección general, puede haber una cantidad arbitraria de secciones de par y almacenamiento.

En vdirsyncer, la sincronización siempre se realiza entre dos almacenamientos. Dichos almacenamientos se definen en secciones de almacenamiento, y qué pares de almacenamientos deben sincronizarse realmente se define en la sección de par. Este formato se copia de OfflineIMAP, donde los almacenamientos se llaman repositorios y los pares se llaman cuentas.

El siguiente ejemplo sincroniza las agendas de ownCloud con ~/.contacts/:

[pair my_contacts]
a = "my_contacts_local"
b = "my_contacts_remote"
collections = ["from a", "from b"]
[storage my_contacts_local]
type = "filesystem"
path = "~/.contacts/"
fileext = ".vcf"
[storage my_contacts_remote]
type = "carddav"
# También podemos simplificar esta URL aquí. En teoría no debería importar.
url = "https://owncloud.example.com/remote.php/carddav/"
username = "bob"
password = "asdf"

NOTA:

La configuración para otros servidores se puede encontrar en Servidores.

Después de ejecutar vdirsyncer discover y vdirsyncer sync, ~/.contacts/ contendrá subcarpetas para cada agenda, que a su vez contendrán una serie de archivos .vcf que cada uno contiene un contacto en formato VCARD. Puedes modificar su contenido, añadir nuevos y eliminar algunos [1], y tus cambios se sincronizarán con el servidor CalDAV después de ejecutar vdirsyncer sync de nuevo. Como referencia adicional, utiliza los almacenamientos filesystem y carddav.

Sin embargo, si se crean nuevas colecciones en el servidor, no comenzará a sincronizarlas automáticamente [2]. Necesitas ejecutar vdirsyncer discover de nuevo para volver a obtener esta lista.

Más Configuración

Resolución de conflictos

¿Qué pasa si el mismo elemento se cambia en ambos lados? ¿Qué debe hacer vdirsyncer? Actualmente se ofrecen tres opciones:

1.
vdirsyncer muestra un mensaje de error (el predeterminado);
2.
vdirsyncer elige una versión alternativa sobre la otra;
3.
vdirsyncer ejecuta un comando de tu elección que se supone que fusionará las dos versiones alternativas.

Las opciones 2 y 3 requieren añadir un parámetro "conflict_resolution" a la sección de par. La opción 2 requiere dar "a wins" o "b wins" como valor al parámetro:

[pair my_contacts]
...
conflict_resolution = "b wins"

Anteriormente escribimos que b = "my_contacts_remote", así que cuando vdirsyncer encuentre la situación en la que un elemento se cambió en ambos lados, simplemente sobrescribirá el elemento local con el del servidor.

La opción 3 requiere especificar como valor de "conflict_resolution" un array que comience con "command" y que contenga las rutas y argumentos de un comando. Por ejemplo:

[pair my_contacts]
...
conflict_resolution = ["command", "vimdiff"]

En este ejemplo, se llamará a vimdiff <a> <b> con <a> y <b> siendo dos archivos temporales que contienen los archivos en conflicto. Los archivos deben ser exactamente iguales cuando el comando retorne. Se pueden pasar más argumentos al comando añadiendo más elementos al array.

Ver Sección de Par para la documentación de referencia.

Sincronización de metadatos

Además de los elementos, vdirsyncer también puede sincronizar metadatos como el nombre "amigable" de la agenda o calendario (llamado internamente "displayname") o el color asociado a un calendario. Para explicar esta característica, cambiemos a un ejemplo base diferente. Esta vez sincronizaremos calendarios:

[pair my_calendars]
a = "my_calendars_local"
b = "my_calendars_remote"
collections = ["from a", "from b"]
metadata = ["color"]
[storage my_calendars_local]
type = "filesystem"
path = "~/.calendars/"
fileext = ".ics"
[storage my_calendars_remote]
type = "caldav"
url = "https://owncloud.example.com/remote.php/caldav/"
username = "bob"
password = "asdf"

Ejecuta vdirsyncer discover para el descubrimiento. Luego puedes usar vdirsyncer metasync para sincronizar la propiedad color entre tus calendarios locales en ~/.calendars/ y tu ownCloud. Localmente el color se representa simplemente como un archivo llamado color dentro de la carpeta del calendario.

Más información sobre colecciones

"Colección" es un término colectivo para agendas y calendarios. Un servidor Carddav o Caldav puede contener varias "colecciones" que corresponden a varias agendas o calendarios.

Cada colección de un almacenamiento tiene un "nombre de colección", un identificador único para cada colección. En el caso del almacenamiento filesystem, es el nombre del directorio que representa la colección, en el caso de los almacenamientos DAV es el último segmento de la URL. Usamos este identificador en el parámetro collections en la sección pair.

Este identificador no cambia incluso si renombras tu calendario en la interfaz que sea, porque eso solo cambia la llamada propiedad "displayname" [3]. En algunos servidores (iCloud, Google) este identificador se genera aleatoriamente y no tiene correlación con el displayname que elegiste.

[3]
Que también puedes sincronizar con metasync usando metadata = ["displayname"].

Hay tres nombres de colección que tienen un significado especial:

  • "from a", "from b": Un marcador de posición para todas las colecciones que se pueden encontrar en el lado A/B al ejecutar vdirsyncer discover.
  • null: Los parámetros dados al almacenamiento son exactos y no requieren descubrimiento.

Este último requiere un poco más de explicación. Asumamos esta configuración que sincroniza dos directorios de agendas:

b = "bar"
collections = ["from a", "from b"]
[storage foo]
type = "filesystem"
fileext = ".vcf"
path = "./contacts_foo/"
[storage bar]
type = "filesystem"
fileext = ".vcf"
path = "./contacts_bar/"

COLLECTIONS

A storage can contain multiple collections. For example, a CalDAV server might host multiple calendars and a CardDAV server might host multiple addressbooks.

When you configure a storage, you can specify which collections should be synchronized. The following configuration synchronizes the calendar with the URL https://example.com/remote.php/dav/calendars/user/work/ to the local directory ~/.local/share/caldav/work/.

[storage mycaldav]
type = "caldav"
url = "https://example.com/remote.php/dav/calendars/user/work/"
filesystem_folder = "~/.local/share/caldav/work/"

This works fine as long as there is exactly one collection per storage. If there are multiple collections, they need to be given unique names. These names are then used to pair collections up when synchronizing two storages.

Collection names can be inferred automatically from the DAV server. If you set the parameter collections to null, it tells vdirsyncer that the storage consists of exactly one collection, and that this collection is to be found at the URL specified in the url parameter.

For example, if your server hosts multiple calendars and you want to sync the calendar at https://example.com/remote.php/dav/calendars/user/work/ to the local folder ~/.local/share/caldav/work/, you can configure it like this:

[storage mycaldav]
type = "caldav"
url = "https://example.com/remote.php/dav/calendars/user/work/"
filesystem_folder = "~/.local/share/caldav/work/"
collections = null

If you omit filesystem_folder (or path for other storages), vdirsyncer will try to automatically discover the correct path. If you omit collections, it's assumed to be the default collection, which is whatever is at the given URL. This means that collections = null is effectively the default behaviour.

The following config also synchronizes the same calendar:

[storage mycaldav]
type = "caldav"
url = "https://example.com/remote.php/dav/calendars/user/work/"

However, if you sync two folders, e.g. ./contacts_foo/ and ./contacts_bar/, vdirsyncer will try to find a common collection name for them. If it can't find one, it will ask you whether to create that folder on the other side.

If we set collections = null, ./contacts_foo/ and ./contacts_bar/ are no longer treated as folders with collections, but as collections themselves. This means that ./contacts_foo/ and ./contacts_bar/ will contain .vcf-files, not subfolders that contain .vcf-files.

This is useful in situations where listing all collections fails because your DAV-server doesn't support it, for example. In this case, you can set url of your carddav- or caldav-storage to a URL that points to your CalDAV/CardDAV collection directly.

Note that not all storages support the null-collection, for example google_contacts and google_calendar don't.

Configuración avanzada de colecciones (sincronización de servidor a servidor)

Los ejemplos anteriores son suficientes si deseas sincronizar un servidor remoto con un disco previamente vacío. Sin embargo, se requieren aún más trucos cuando tienes dos servidores con colecciones ya existentes que deseas sincronizar.

El problema principal en esta situación es que vdirsyncer empareja las colecciones por nombre de colección por defecto (ver definición en la sección anterior, básicamente un nombre de carpeta o un UUID remoto). Cuando tienes dos servidores, esos nombres de colección pueden no alinearse tan bien. Supongamos que creaste dos calendarios "Test", uno en un servidor NextCloud y otro en iCloud, usando sus respectivas interfaces web. Las URLs se ven algo así:

NextCloud: https://ejemplo.com/remote.php/dav/calendars/usuario/test/
iCloud:    https://p-XX.caldav.icloud.com/YYY/calendars/3b4c9995-5c67-4021-9fa0-be4633623e1c

Esas son dos colecciones de calendario DAV. Sus nombres de colección serán test y 3b4c9995-5c67-4021-9fa0-be4633623e1c respectivamente, por lo que no tienes un solo nombre con el que puedas direccionarlas ambas. Necesitarás "emparejar" (sin juegos de palabras) manualmente esas colecciones de la siguiente manera:

[pair doblecloud]
a = "my_nextcloud"
b = "my_icloud"
collections = [["mytest", "test", "3b4c9995-5c67-4021-9fa0-be4633623e1c"]]

mytest le da a esa combinación de calendarios un nombre agradable que puedes usar al referirte a ella, así que usarías vdirsyncer sync doblecloud/mytest para decir: "Solo sincroniza estos dos almacenamientos, nada más que pueda estar configurado".

NOTA:

¿Por qué no usar displaynames?

Quizás te preguntes por qué vdirsyncer simplemente no pudo averiguarlo por sí mismo. Después de todo, nombraste ambas colecciones "Test" (que se llama "el displayname"), ¿entonces por qué no emparejar colecciones por ese valor?

Hay varios problemas con esta idea:

  • Dos calendarios pueden tener exactamente el mismo displayname.
  • Un calendario puede no tener un displayname (no vacío).
  • El displayname podría cambiar. Ya sea que renombres el calendario, o que el calendario se renombre a sí mismo porque cambias una configuración de idioma.

Al final, esa propiedad nunca fue diseñada para ser analizada por máquinas.

ALMACENAMIENTO DE CONTRASEÑAS

Cambiado en la versión 0.7.0: La configuración de contraseñas fue completamente revisada.

Vdirsyncer puede obtener contraseñas de varias fuentes además del archivo de configuración.

Comando

Supongamos que tienes la siguiente configuración:

[storage foo]
type = "caldav"
url = ...
username = "foo"
password = "bar"

Pero te molesta que la contraseña esté almacenada en texto plano en el archivo de configuración. Puedes hacer esto:

[storage foo]
type = "caldav"
url = ...
username = "foo"
password.fetch = ["command", "~/get-password.sh", "more", "args"]

Puedes obtener el nombre de usuario también:

[storage foo]
type = "caldav"
url = ...
username.fetch = ["command", "~/get-username.sh"]
password.fetch = ["command", "~/get-password.sh"]

O realmente cualquier tipo de parámetro en una sección de almacenamiento.

También puedes pasar el comando como una cadena a ser ejecutada en una shell:

password.fetch = ["command", "pass", "caldav"]

Accediendo al keyring del sistema

Como se mostró anteriormente, puedes usar la estrategia command para obtener tus credenciales de fuentes arbitrarias. Un caso de uso muy común es obtener tu contraseña del keyring del sistema.

pip install keyring

Uso básico:

password.fetch = ["command", "keyring", "get", "example.com", "foouser"]

Solicitud de contraseña

También puedes simplemente solicitar la contraseña:

[storage foo]
type = "caldav"
username = "myusername"
password.fetch = ["prompt", "Contraseña para CalDAV"]

Variable de entorno

Para leer la contraseña de una variable de entorno:

[storage foo]
type = "caldav"
username = "myusername"
password.fetch = ["command", "printenv", "DAV_PW"]

Paso 1: Crear el calendario de destino

Primero necesitas crear el calendario con el que deseas sincronizar el calendario WebCAL. La mayoría de los servidores ofrecen una interfaz web para esto. Luego, debes anotar la URL CalDAV de tu calendario. Ten en cuenta que esta URL debe apuntar directamente al calendario que acabas de crear, lo que significa que tendrás una URL de este tipo para cada calendario que tengas.

Paso 2: Crear la configuración

Pega esto en tu configuración de vdirsyncer:

[pair holidays]
a = "holidays_public"
b = "holidays_private"
collections = null
[storage holidays_public]
type = "http"
# La URL de tu archivo iCalendar.
url = "..."
[storage holidays_private]
type = "caldav"
# La URL directa a tu calendario.
url = "..."
# Las credenciales de tu servidor CalDAV
username = "..."
password = "..."

Luego ejecuta vdirsyncer discover holidays y vdirsyncer sync holidays, y tu calendario creado previamente debería llenarse de eventos.

Paso 3: El parámetro partial_sync

Añadido en la versión 0.14.

Puede que te encuentres en una situación en la que quieras ocultar o modificar algunos eventos de tu calendario holidays. Si intentas hacer eso en este punto, notarás que vdirsyncer revertirá cualquier cambio que hayas hecho después de ejecutar sync varias veces. Esto se debe a que vdirsyncer quiere mantener todo sincronizado, y no puede sincronizar cambios en el calendario público de festivos porque no tiene los derechos para hacerlo.

Para tales propósitos, puedes establecer el parámetro partial_sync a ignore:

[pair holidays]
a = "holidays_public"
b = "holidays_private"
collections = null
partial_sync = ignore

Consulta la documentación de configuración para más información.

MANUAL COMPLETO DE CONFIGURACIÓN

Vdirsyncer utiliza un formato similar a ini para almacenar su configuración. Todos los valores son JSON, el JSON inválido se interpretará como una cadena:

x = "foo"  # Cadena

Sección General

[general]
status_path = ...
•
status_path: Un directorio donde vdirsyncer almacenará algunos datos adicionales para la próxima sincronización.

Los datos son necesarios para determinar si un nuevo elemento significa que se añadió en un lado o se eliminó en el otro. Las rutas relativas se interpretarán como relativas al directorio del archivo de configuración.

Sección Pair

[pair pair_name]
a = ...
b = ...
#collections = null
#conflict_resolution = null
  • Los nombres de los pares pueden consistir en cualquier carácter alfanumérico y el guion bajo.
  • a y b hacen referencia a los almacenamientos a sincronizar por sus nombres.
  • collections: Una lista de colecciones a sincronizar cuando se ejecuta vdirsyncer sync. Consulta también Más información sobre colecciones.

    Los valores especiales "from a" y "from b", indican a vdirsyncer que intente la Autodescubrimiento en un almacenamiento específico. Significa todas las colecciones del lado A / lado B.

    Si la colección que deseas sincronizar no tiene el mismo nombre en cada lado, también puedes usar un valor de la forma ["config_name", "name_a", "name_b"]. Esto sincronizará la colección name_a en el lado A con la colección name_b en el lado B. El config_name se utilizará para la representación en argumentos de la CLI y en los registros.

    Ejemplos:

  • collections = ["from b", "foo", "bar"] hace que vdirsyncer sincronice todas las colecciones del lado B, y también las colecciones llamadas "foo" y "bar".
  • collections = ["from b", "from a"] hace que vdirsyncer sincronice todas las colecciones existentes en cualquiera de los lados.
  • collections = [["bar", "bar_a", "bar_b"], "foo"] hace que vdirsyncer sincronice bar_a del lado A con bar_b del lado B, y también sincronice foo en ambos lados entre sí.
•
conflict_resolution: Opcional, define cómo se deben manejar los conflictos. Un conflicto ocurre cuando un elemento (evento, tarea) ha cambiado en ambos lados desde la última sincronización. Consulta también Resolución de conflictos.

Los valores válidos son:

  • null, donde se muestra un error y no se realizan cambios.
  • "a wins" y "b wins", donde el elemento completo se toma de un lado.
  • ["command", "vimdiff"]: Se llamará a vimdiff <a> <b> donde <a> y <b> son archivos temporales que contienen el elemento de cada lado respectivamente. Los archivos deben ser exactamente iguales cuando el comando regrese.
  • vimdiff puede ser reemplazado por cualquier otro comando. Por ejemplo, en POSIX ["command", "cp"] es equivalente a "a wins".
  • Los elementos de lista adicionales se reenviarán como argumentos. Por ejemplo, ["command", "vimdiff", "--noplugin"] ejecuta vimdiff --noplugin.

Vdirsyncer nunca intenta "fusionar automáticamente" los dos elementos.

•
partial_sync: Asume que A es de solo lectura, B no. Si cambias elementos en B, vdirsyncer no puede sincronizar los cambios a A. ¿Qué debería pasar en su lugar?
  • error: Se muestra un error.
  • ignore: El cambio se ignora. Sin embargo: Los eventos eliminados en B aún reaparecen si se actualizan en A.
  • revert (por defecto): El cambio se revierte en la próxima sincronización.

Consulta también Sincronización con almacenamientos de solo lectura.

•
metadata: Claves de metadatos que deben sincronizarse cuando se ejecuta vdirsyncer metasync. Ejemplo:
metadata = ["color", "displayname", "description", "order"]

Esto sincroniza las siguientes propiedades:

  • color: http://apple.com/ns/ical/:calendar-color
  • displayname: DAV:displayname
  • description: CalDAV:calendar-description y CardDAV:addressbook-description
  • order: http://apple.com/ns/ical/:calendar-order

El parámetro conflict_resolution también se aplica a estas propiedades.

Deben especificarse ambos o ninguno. Por defecto, se sincroniza todo.

Los parámetros principales de autenticación (username y password) se pueden omitir si se encuentran en la URL. De lo contrario, se puede omitir la autenticación por completo para acceder a calendarios públicos.

Los item_types son cadenas de caracteres que representan clases de objetos de calendario, como "VEVENT", "VTODO", "VJOURNAL". Si no se especifica, se sincronizarán todos.

La configuración para sincronizar eventos pasados (históricos) se puede hacer usando los parámetros start_date y end_date. Los valores predeterminados son el infinito negativo y el infinito positivo, respectivamente. El formato esperado para las fechas es YYYY-MM-DD.

start_date = "2023-01-01"
end_date = "+30d"
item_types = ["VEVENT"]

Puede usar un rango de fechas relativo con un sufijo 'd' para días o 'y' para años. Por ejemplo, "+30d" significa "los próximos 30 días" y "-2y" significa "los últimos 2 años". Si no se especifica un signo, se asumirá '+'.

Demasiados proveedores de WebCAL generan UIDs de todos los componentes VEVENT sobre la marcha, es decir, todos los UIDs cambian cada vez que se descarga el calendario. Esto lleva a muchos programas de sincronización a creer que todos los eventos han sido eliminados y que se han creado nuevos, y en consecuencia causa muchas cargas y eliminaciones innecesarias en el otro lado. Vdirsyncer ignora completamente los UIDs provenientes de http y los reemplazará con un hash del contenido normalizado del elemento.

  • usuario -- Nombre de usuario para la autenticación.

  • verify_fingerprint -- Opcional. Huella SHA256 del certificado esperado del servidor. Consulta Validación SSL y de certificados para más información.

  • auth_cert -- Opcional. Puede ser una ruta a un certificado con un certificado de cliente y la clave, o una lista de rutas a los archivos con ellos.
  • useragent -- Por defecto vdirsyncer.
  • filter_hook -- Opcional. Un comando de filtro para llamar para cada elemento obtenido, pasado en formato crudo a stdin y devuelto a través de stdout. Vdirsyncer con Claws Mail

Antes que nada, Claws-Mail solo admite funciones de solo lectura para vCards. Solo puede leer contactos, pero no hay editor.

Preparación

Necesitamos instalar vdirsyncer, para ello consulta aquí. Luego necesitamos crear algunas carpetas:

mkdir ~/.vdirsyncer
mkdir ~/.contactos

Configuración

Ahora creamos la configuración para vdirsyncer. Abre ~/.vdirsyncer/config con un editor de texto. La configuración debería verse así:

[general]
status_path = "~/.vdirsyncer/status/"
[almacenamiento local]
type = "singlefile"
path = "~/.contactos/%s.vcf"
[almacenamiento online]
type = "carddav"
url = "ENLACE_CARDDAV"
usuario = "USUARIO"
contraseña = "CONTRASEÑA"
read_only = true
[par contactos]
a = "local"
b = "online"
collections = ["desde a", "desde b"]
conflict_resolution = "b gana"
  • En la sección general, definimos la ruta de la carpeta de estado, para colecciones descubiertas y, en general, cosas que necesitan persistir entre sincronizaciones.
  • En la sección local, definimos que todos los contactos se sincronizarán en un solo archivo y la ruta para los contactos.
  • En la sección online, debes cambiar la url, el usuario y la contraseña a tu configuración. También establecemos el almacenamiento a solo lectura para que no se sincronicen cambios de vuelta. Claws-Mail no debería poder hacer ningún cambio de todos modos, pero este es un paso de seguridad adicional en caso de que los archivos se corrompan o vdirsyncer se comporte de manera errática. Puedes omitir esa parte si quieres poder editar esos archivos localmente.
  • En la última sección, configuramos que los contactos en línea ganen en una situación de conflicto. Configura esta parte como prefieras. Un valor correcto depende de qué lado es más probable que esté actualizado.

Sincronizar

Ahora descubrimos y sincronizamos nuestros contactos:

Ejecución como systemd.timer

vdirsyncer incluye archivos de unidad para ejecutarse a intervalos (por defecto cada 15±5 minutos).

NOTA:

Estos no se instalan al instalar mediante pip, solo a través de paquetes de distribución. Si instalaste mediante pip, o tu distribución no incluye archivos de unidad systemd, necesitarás descargar vdirsyncer.service y vdirsyncer.timer en /etc/systemd/user/ o en ~/.local/share/systemd/user.

Activación

Para activar el temporizador, simplemente ejecuta systemctl --user enable vdirsyncer.timer. Para ver los registros de ejecuciones anteriores, usa journalctl --user -u vdirsyncer.

Configuración

Es muy posible que el intervalo predeterminado de "cada quince minutos" no sea de tu agrado. Ninguna configuración predeterminada servirá a todos, pero esto es configurable simplemente ejecutando:

systemctl --user edit vdirsyncer.timer

Esto abrirá un editor en blanco, donde puedes anular el temporizador incluyendo:

OnBootSec=5m  # Esto es cuánto tiempo después del arranque se realiza la primera ejecución.
OnUnitActiveSec=15m  # Esto es con qué frecuencia se realizan las ejecuciones posteriores.

EL FORMATO DE ALMACENAMIENTO VDIR

Este documento describe un estándar para almacenar calendarios y contactos en un sistema de archivos, con el objetivo principal de ser fácil de implementar.

Vdirsyncer se sincroniza a vdirs a través del sistema de archivos. Cada vdir (básicamente solo un directorio con algunos archivos dentro) representa un calendario o una agenda.

Estructura Básica

La carpeta principal (raíz) contiene un número arbitrario de subcarpetas (colecciones), que contienen solo archivos (elementos). Los sinónimos de "colección" pueden ser "agenda" o "calendario".

Un elemento es:

  • Un archivo vCard, en cuyo caso la extensión del archivo debe ser .vcf, o
  • Un archivo iCalendar, en cuyo caso la extensión del archivo debe ser .ics.

Un elemento debe contener una propiedad UID como se describe en los estándares vCard e iCalendar. Si contiene más de una propiedad UID, los valores de estas no deben diferir.

El archivo debe contener exactamente un evento, tarea o contacto. En la mayoría de los casos, esto también implica solo

FORMAT

Un componente VEVENT/VTODO/VCARD por archivo, pero por ejemplo las excepciones de recurrencia requerirían múltiples componentes VEVENT por evento.

El nombre del archivo debe tener propiedades similares al UID del contenido del archivo. Sin embargo, no hay ningún requisito para que estos dos sean iguales. Los programas pueden optar por almacenar metadatos adicionales en ese nombre de archivo; sin embargo, al mismo tiempo *no deben* asumir que los metadatos que incluyeron serán preservados por otros programas.

Metadatos

Cualquiera de los siguientes archivos de metadatos puede estar ausente. Ninguno de los archivos listados a continuación tiene extensiones de archivo.

  • Un archivo llamado color dentro del vdir indica el color del vdir, una propiedad que solo es relevante en el diseño de la interfaz de usuario.

    Su contenido es un valor hexadecimal RGB codificado en ASCII de la forma #RRGGBB. Por ejemplo, un contenido de archivo de #FF0000 indica que el vdir tiene un color rojo (visible para el usuario). No se permiten formas cortas o valores informales como red (como se conoce en CSS, por ejemplo). El prefijo # debe estar presente.

  • Los archivos llamados displayname y description contienen una etiqueta/descripción codificada en UTF-8, que puede usarse para representar el vdir en las interfaces de usuario.
  • Un archivo llamado order dentro del vdir incluye el orden relativo del calendario, una propiedad que solo es relevante en el diseño de la interfaz de usuario.

Escritura en vdirs

Escribir en un archivo temporal en el mismo dispositivo físico y luego moverlo a la ubicación apropiada suele ser una solución muy efectiva. Para este propósito, se pueden crear archivos con la extensión .tmp dentro de las colecciones.

Al cambiar un elemento, *debe* usarse el nombre de archivo original.

Lectura de vdirs

  • No se debe tratar como elemento ningún archivo que termine en .tmp o sin extensión de archivo.
  • La parte ident del nombre de archivo *no debe* ser analizada para mejorar la velocidad de búsqueda de elementos.

Consideraciones

Rendimiento

Actualmente, los vdirs sufren de un problema de rendimiento bastante importante, que las implementaciones actuales intentan mitigar creando índices de las colecciones para una búsqueda y consulta más rápidas.

La razón por la que los nombres de archivo de los elementos no contienen información adicional es simple: las soluciones presentadas indujeron duplicación de datos, donde un duplicado podría quedar desactualizado debido a implementaciones deficientes. Tal como está ahora, un formato de índice podría formalizarse por separado.

vdirsyncer no tiene que preocuparse realmente por la búsqueda eficiente de elementos, porque su algoritmo de sincronización necesita obtener la lista completa de elementos de todos modos. Detectar cambios se implementa fácilmente comprobando la hora de modificación de los archivos.

GUÍAS DE EMPAQUETADO

¡Muchas gracias por empaquetar vdirsyncer! Las siguientes guías deberían ayudarlo a evitar algunas trampas comunes.

Si necesita parchear algo, o va en una dirección diferente, por favor, abra un issue para que también podamos abordarlo de una manera que funcione para todos. De lo contrario, recibiremos informes de errores para código o escenarios que no existen en el vdirsycner original.

Obtención del código fuente

Las etiquetas serán firmadas por el mantenedor que realiza el lanzamiento (a partir de la versión 0.16.8), y la generación del archivo tar y wheel se realiza mediante CI. Por lo tanto, solo la etiqueta en sí está firmada.

Versiones de dependencias

Como con la mayoría de los paquetes de Python, setup.py indica las dependencias de vdirsyncer. También contiene las versiones inferiores de cada dependencia. Las versiones anteriores serán rechazadas por el conjunto de pruebas.

Pruebas

Todo lo relacionado con las pruebas pasa por el Makefile en la raíz del repositorio o paquete PyPI. Intentar, por ejemplo, ejecutar pytest directamente requerirá muchas variables de entorno para ser configuradas y probablemente no querrá lidiar con eso.

Puede instalar todas las dependencias de desarrollo con:

make install-dev

Probablemente no quiera esto, ya que usará pip para descargar las dependencias. Alternativamente, las dependencias de prueba se enumeran como dependencias opcionales de test en pyproject.toml, nuevamente con requisitos de versión inferior.

También debe tener vdirsyncer completamente instalado en este punto. Simplemente cd-ear en el archivo tar no será suficiente.

La ejecución de las pruebas se realiza con:

pytest

Hypothesis generará aleatoriamente entradas de prueba. Si le importan las pruebas deterministas, establezca la variable DETERMINISTIC_TESTS en "true":

make DETERMINISTIC_TESTS=true test

Hay muchas variables adicionales que le permiten probar vdirsyncer contra un servidor particular. Esas variables no son "estables" y pueden cambiar drásticamente entre versiones menores. Simplemente no las use, es poco probable que encuentre errores que la CI de vdirsyncer no haya encontrado.

Documentación

Usando Sphinx puede generar la documentación que está leyendo ahora en una variedad de formatos, como HTML, PDF o incluso como una página de manual. Dicho esto, solo me encargo del formato de los documentos HTML.

Puede encontrar una lista de dependencias en docs-requirements.txt. Nuevamente, puede instalarlas usando pip con:

pip install -r docs-requirements.txt

Luego, cámbiese al directorio docs/ y compile el formato que desee utilizando el Makefile que se encuentra allí (ejecute make para los formatos que pueda compilar).

Archivos Contrib

Se proporcionan archivos de unidad de referencia systemd.service y systemd.timer. Se recomienda instalar esto si su distribución se basa en systemd.
