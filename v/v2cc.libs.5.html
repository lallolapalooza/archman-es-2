V2CC.LIBS(5) Formatos de Archivo V2CC.LIBS(5)

NOMBRE

v2cc.libs - Archivo de mapeo de bibliotecas VHDL para el compilador/simulador FreeHDL.

DESCRIPCIÓN

FreeHDL es un conjunto de compilador/simulador para el lenguaje de descripción de hardware VHDL. Se soportan los estándares VHDL'93 y VHDL'87.

FreeHDL traduce los archivos fuente VHDL originales a C++. Luego, el código fuente C++ puede compilarse y enlazarse al kernel para construir el programa de simulación. Al ejecutar el ejecutable generado, se simulará el modelo VHDL correspondiente. El proceso de construcción real para generar el simulador a partir del código fuente VHDL es un proceso complejo que es manejado por el script gvhdl.

FreeHDL no tiene una noción opaca de bibliotecas de diseño. Los archivos VHDL no se pre-analizan y se guardan en una base de datos de bibliotecas como en otros sistemas de compiladores/simuladores VHDL. En cambio, cada vez que se necesita hacer una referencia a una unidad de diseño, FreeHDL analiza el código VHDL de esa unidad de diseño desde cero. Por lo tanto, necesita poder encontrar el archivo fuente de una unidad de diseño dado el nombre VHDL de esa unidad.

Así, en lo que respecta a FreeHDL, una biblioteca de diseño es un mapeo de identificadores VHDL a nombres de archivo. También existe un mapeo para obtener nombres de bibliotecas a partir de archivos de mapeo.

Dicho mapeo se especifica a través de un "archivo de mapeo". Contiene una lista de reglas de patrones que transforman cada clase de identificadores en nombres de archivo.

La sintaxis de un archivo de mapeo es:


Lexical:


litchar: 'a'..'z' | 'A'..'Z' | '0'..'9' | '_' | '/' | '-' | '.' escchar


escchar: '\' char


whitespace: ' ' | '\n' | '\v' | '\t' | comment


comment: '#' any_character* '\n'


opchar: ':' | ',' | '(' | ')'


specchar: every printable char except litchar, whitespace and opchar


symchar: litchar | specchar


symbol: symchar+


Gramática:


mapping: version patternrule*


version: "v2cc_mapfile" "0"


patternrule: symbol [ ':' symbol ]

Se ignoran los comentarios.

Un archivo de mapeo especifica una secuencia de reglas de patrones. Al transformar un identificador, cada regla se prueba por turno y se elige la primera que coincida.

Una regla se ve así:


pattern: filename

Cuando la parte ": filename" se omite, por defecto es "patternEXT" donde "EXT" es determinado por el usuario del archivo de mapeo.

El "pattern" puede contener el carácter especial "<" que introduce un `comodín'. El "<" debe ir seguido de un ">", con caracteres arbitrarios entre ellos. Estos caracteres forman el nombre del comodín. Un comodín coincide con cualquier secuencia de caracteres. Puede haber cualquier número de comodines en el patrón, pero cada uno debe tener un nombre único.

El "filename" también puede contener el carácter "<", seguido de un nombre, seguido de ">". Allí, introduce una `sustitución de comodín'. Se reemplazará con los caracteres que coincidieron con el comodín con el mismo nombre en "pattern". Cuando no hay comodín en "pattern" con el nombre correcto, se reemplazará con nada. Al hacer esta sustitución, los caracteres "#" y "/" se reemplazan como "##" y "#-" respectivamente. No se realizan otras traducciones de caracteres, por lo que si tiene caracteres extraños en sus identificadores VHDL, tendrá caracteres extraños en sus nombres de archivo.

Antes de realizar la comparación con los patrones, el identificador VHDL se convierte a una forma canónica: cuando no es un identificador abstracto, todos sus caracteres se convierten a minúsculas.

Cuando el nombre de archivo resultante es relativo (no comienza con "/"), se le antepone el directorio del archivo de mapeo.

Un archivo de mapeo inexistente es equivalente a la regla única


<>

Un archivo de mapeo vacío es simplemente eso: un mapeo vacío.

El mapeo no necesita ser reversible. Está bien que múltiples identificadores se mapeen a un único nombre de archivo.

Ningún carácter especial además de "<" y ">" es válido en "pattern" o "filename". Están reservados para extensiones futuras.

Los archivos de mapeo para ir de nombres de unidades de diseño a nombres de archivo se encuentran buscando en directorios especificados por la `ruta de bibliotecas v2cc'. Puede usar la variable de entorno V2CC_LIBRARY_PATH y las opciones de línea de comandos para definir la ruta. Cuando la variable de entorno no está establecida, por defecto tiene un valor que hace que las bibliotecas estándar distribuidas e instaladas con v2cc estén disponibles. Cuando está establecida, reemplaza completamente este valor predeterminado.

La variable V2CC_LIBRARY_PATH consiste en nombres de archivo separados por ":". El nombre de archivo "*" se reemplaza con el valor predeterminado mencionado anteriormente.

Además de la variable de entorno, puede usar la opción de línea de comandos "-L libdir" con v2cc. Los directorios especificados con "-L" se agregan antes que los especificados por V2CC_LIBRARY_PATH. En la ruta de bibliotecas final, aparecen en el mismo orden que en la línea de comandos.

La búsqueda de una unidad de diseño llamada UNIT en una biblioteca llamada LIB se realiza de la siguiente manera:


para cada componente de la ruta de bibliotecas, L
si L es un archivo regular
establecer LMAP a L
o si L es un directorio
establecer LMAP a L/v2cc.libs
o si no
continuar con el siguiente componente
traducir LIB a FLIB usando LMAP con EXT=""
si FLIB.vhdl existe
terminar con FLIB.vhdl como resultado
si FLIB.v2cc existe
establecer UMAP a FLIB.v2cc
o si FLIB es un directorio
establecer UMAP a FLIB/v2cc.units
o si no
continuar con el siguiente componente
traducir UNIT a FUNIT usando UMAP con EXT=".vhdl"
terminar con FUNIT como resultado
terminar sin éxito

Este mecanismo se utiliza para todas las unidades de diseño que se referencian desde dentro del código VHDL (o por otros medios). Sin embargo, hay una complicación con las arquitecturas y los cuerpos de paquete, ya que no se identifican de forma única por un solo identificador. Para ellos, se construye un identificador artificial. Las arquitecturas reciben nombres de la forma


<entity>(<architecture>)

mientras que los cuerpos de paquete se convierten en


<package>(body)

Por ejemplo, "architecture struct of model" se convierte en "model(struct)" y "package body misc" se convierte en "misc(body)".

Cuando un archivo de diseño contiene múltiples unidades de diseño, todas se analizan, se comprueba su corrección y se recuerdan, pero solo la unidad necesaria se utilizará para la generación de código. Es decir, cuando un archivo de diseño contiene tanto una cabecera de paquete como un cuerpo de paquete y la cabecera del paquete se referencia desde otra unidad de diseño, no se generará código para el cuerpo del paquete. Cuando una de las unidades ignoradas se referencie más tarde en la misma invocación de v2cc, el archivo de diseño no se leerá de nuevo porque todas las unidades de diseño se conservan en memoria.

EJEMPLOS

La situación más simple es cuando no tiene ningún archivo de mapeo. Una biblioteca de diseño es entonces un directorio en su ruta de bibliotecas. El nombre de ese directorio es el de la biblioteca en VHDL. Cada archivo en ese directorio con extensión ".vhdl" se utiliza para una unidad de diseño con el mismo nombre que el archivo sin la extensión.

Supongamos que tiene esta estructura de directorios


somedir/
std/
standard.vhdl
textio.vhdl
ieee/
numeric_bit.vhdl
std_logic_1164.vhdl

Al colocar "somedir" en su ruta de bibliotecas, tiene acceso a las unidades de diseño


STD.STANDARD
STD.TEXTIO
IEEE.NUMERIC_BIT
IEEE.STD_LOGIC_1164

En esta situación, tiene un archivo por unidad de diseño. Cuando tiene un archivo por biblioteca de diseño, se vería así


somedir/
fmf.vhdl

Todas las referencias a unidades de diseño en la biblioteca de diseño FMF se dirigirían a "fmf.vhdl".

NOMBRE

v2cc.libs - control file for the v2cc VHDL compiler

DESCRIPCIÓN

This file is intended to control v2cc, the VHDL compiler of FreeHDL. It is placed in the library root directory and provides a map from VHDL library names to directory names. The library root directory and the subdirectories are assumed to contain the VHDL files for the corresponding VHDL libraries.

The file is free format. The first line must be "v2cc_mapfile 0". Following this, you can specify as many VHDL library names as you want. Each entry consists of the VHDL library name, a colon, and the path to the directory where the VHDL files are stored. The path can be absolute or relative to the library root directory.

Let's assume we have two VHDL libraries, lib1 and lib2. We want to map these to subdir "/foo/lib1_dir" and "/foo/lib2_dir". Hence, the file/directory structure is as follows:

/foo <- root directory de la librería /foo/v2cc.libs <- archivo de control de mapeo /foo/lib1_dir <- directorio de librería para la librería VHDL lib1 /foo/lib1_dir/comp1.vhdl <- archivo que contiene el modelo VHDL comp1 /foo/lib2_dir <- directorio de librería para la librería VHDL lib2 /foo/lib2_dir/comp2.vhdl <- archivo que contiene el modelo VHDL comp2

Then, the file "/foo/v2cc.libs" should contain:

v2cc_mapfile 0 lib1 : lib1_dir lib2 : lib2_dir

In order to compile a design named comp1 (stored in file comp1.vhdl) into VHDL library lib1, go to the subdirectory "/foo/lib1_dir" and execute:


gvhdl -c -L .. -l lib1 comp1.vhdl

Note that the option "-l lib1" forces the compiler to associate the model stored in "comp1.vhdl" with VHDL library lib1. Note further, that the compiler switch "-L .." specifies the path to the directory where "v2cc.libs" is stored. You may also specify an absolute path:


gvhdl -c -L /foo -l lib1 comp1.vhdl

Note that comp1 should reside in a file named "comp1.vhdl".

If lib2 contains a design comp2 that makes use of comp1 from lib1, then go to "/foo/lib2_dir" and run the following command to create an executable for model comp2:


gvhdl -L .. -l lib2 comp2.vhdl ../lib1_dir/comp1.o
