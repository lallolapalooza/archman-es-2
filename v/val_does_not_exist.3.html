DESCRIPCIÓN

La función val_resolve_and_check() consulta un conjunto de servidores de nombres para la tupla <nombre_dominio, tipo, clase> y verifica y valida la respuesta. La verificación implica comprobar los RRSIGs, y la validación es la verificación de una cadena de autenticación desde un ancla de confianza configurada.

El parámetro flags puede usarse para controlar los resultados de la validación. Los siguientes valores, que pueden combinarse con OR, están definidos actualmente para este campo:

VAL_QUERY_DONT_VALIDATE
Este flag hace que el validador deshabilite la validación para esta consulta.
VAL_QUERY_IGNORE_SKEW
Este flag hace que el validador deshabilite la comprobación de los tiempos de inicio y expiración de las firmas en los RRSIGs.
VAL_QUERY_AC_DETAIL
Este flag hace que el validador copie los detalles de la cadena de autenticación en el miembro val_rc_answer dentro de la estructura val_result_chain devuelta.
VAL_QUERY_ASYNC
Este flag habilita la resolución de consultas asíncronas para esa búsqueda.
VAL_QUERY_NO_DLV
Este flag hace que el validador deshabilite el procesamiento de DLV para esta consulta. Esto solo está disponible si la biblioteca libval(3) ha sido compilada con soporte DLV.
VAL_QUERY_NO_EDNS0_FALLBACK
Al consultar varios servidores de nombres, libsres(3) también intentará varios tamaños EDNS0, terminando con una consulta que tiene EDNS0 deshabilitado (es decir, sin el bit CD establecido). Este flag hace que libval deshabilite la recuperación automática de EDNS0 para la consulta.
VAL_QUERY_ITERATE
Este flag fuerza a libval a buscar iterativamente la consulta consultando varios servidores de nombres en la jerarquía de delegación, en lugar de solicitar esta información a cualquier servidor de nombres en caché que pueda estar configurado en dnsval.conf.
VAL_QUERY_SKIP_RESOLVER
Este flag fuerza a libval a mirar solo su caché mientras intenta resolver un nombre.
VAL_QUERY_SKIP_CACHE
Hay dos niveles de caché que ocurren dentro de libval: a nivel de afirmación y a nivel de respuesta. Este flag fuerza a libval a ignorar los datos en ambas cachés mientras intenta resolver un nombre.
VAL_QUERY_SKIP_ANS_CACHE
Hay dos niveles de caché que ocurren dentro de libval: a nivel de afirmación y a nivel de respuesta. Este flag fuerza a libval a ignorar los datos en la caché de respuestas mientras intenta resolver un nombre. Si ya existe una afirmación para el nombre, clase y tipo dados, esa afirmación se reutiliza hasta que expira. Una vez que expira, el nombre se busca a través de una consulta, incluso si un registro más nuevo (obtenido por otra afirmación en el mismo o diferente contexto) está disponible en su caché de respuestas.

El primer parámetro de val_resolve_and_check() es el contexto del validador. Las aplicaciones pueden crear un nuevo contexto de validador usando la función val_create_context(). Esta función analiza los archivos de configuración del resolvedor y del validador y crea el manejador newcontext para esta información analizada. La información almacenada como parte del contexto del validador incluye la política de validación y la política del resolvedor.

Las políticas del validador y del resolvedor se leen de los archivos /etc/dnsval.conf y /etc/resolv.conf por defecto. /etc/root.hints proporciona información de arranque para el validador cuando funciona como un resolvedor completo (ver dnsval.conf(3)). Estos valores por defecto pueden ser diferentes si se especificó algún otro valor en el momento de la configuración de la biblioteca. Si el archivo de configuración del resolvedor por defecto no se encuentra en la ubicación especificada, libval también intentará recurrir a /etc/resolv.conf como último recurso.

Las aplicaciones también pueden crear un contexto de validador con una política personalizada usando la función val_create_context_ex().

El argumento opt en val_create_context_ex() apunta a la siguiente estructura:

typedef struct val_context_opt {
    unsigned int vc_qflags;
    unsigned int vc_polflags;
    char *vc_valpol;
    char *vc_nslist;
    char *vc_val_conf;
    char *vc_res_conf;
    char *vc_root_conf;
    val_global_opt_t *gopt, 
} val_context_opt_t;

vc_qflags especifica los flags de consulta por defecto para las consultas asociadas con el contexto. Este campo es idéntico al argumento flags en la función val_resolve_and_check().

Los campos vc_val_conf, vc_res_conf y vc_root_conf pueden usarse para especificar archivos de configuración alternativos en lugar de los archivos por defecto utilizados para la información de configuración del validador, el resolvedor y las pistas raíz.

El campo vc_valpol puede usarse para proporcionar un "fragmento" de configuración personalizada del validador al validador. El validador analiza esta información y la aplica a la configuración por defecto del validador, ya sea como una extensión o como una anulación, según lo especificado por el campo vc_polflags. El campo vc_nslist, de manera similar, puede usarse para proporcionar una lista personalizada de servidores de nombres recursivos a los que enviar consultas, además (o en lugar) de la lista de servidores de nombres especificada en el archivo resolv.conf. La lista de servidores de nombres en vc_res_conf debe especificarse como una lista separada por espacios en blanco de direcciones IP o IPv6.

Se puede crear una asignación personalizada entre una zona y un servidor de nombres utilizando la función val_context_store_ns_for_zone().

vc_polflags puede configurarse con los siguientes valores:

CTX_DYN_POL_VAL_OVR
Cuando este flag está establecido, solo se utiliza la configuración del validador especificada en el campo vc_valpol para la configuración del validador. Las opciones especificadas en el archivo dnsval.conf se ignoran.
La función val_context_setqflags() se usa para anular los flags de consulta por defecto para un contexto de validador. El parámetro action puede ser 0 (establecer flags), 1 (anular flags) o 2 (borrar flags). El parámetro flags es una máscara de bits de los flags de consulta.

La función val_free_context() libera el contexto del validador creado por val_create_context() o val_create_context_ex().

La función val_free_result_chain() libera la cadena de resultados de una consulta devuelta por val_resolve_and_check().

La función val_istrusted() devuelve verdadero si el valor de estado dado corresponde a una respuesta que se considera confiable. Actualmente, esto incluye respuestas que se han verificado con éxito y que encadenan hasta un ancla de confianza configurada.

La función val_isvalidated() devuelve verdadero si el valor de estado dado corresponde a una respuesta que se ha validado con éxito, es decir, que encadena criptográficamente hasta un ancla de confianza configurada.

La función val_does_not_exist() devuelve verdadero si el valor de estado dado indica que el nombre de dominio o el tipo solicitado no existe. Esto incluye los códigos de error DNS NXDOMAIN y NODATA.

Las funciones p_val_status(), p_ac_status() y p_val_error() se utilizan para obtener cadenas legibles por humanos que describen un estado de validación, un estado de cadena de autenticación o un código de error de la biblioteca, respectivamente.

La función val_log_add_optarg() agrega opciones de línea de comandos para el sistema de registro interno de libval. Actualmente, el único argumento admitido es el nivel de verbosidad de los mensajes de registro (es decir, -v, -vv, -vvv).

VALORES DE RETORNO

Las funciones de creación de contexto y resolución devuelven 0 con éxito, o un código de error negativo en caso de fallo.

Las funciones val_istrusted(), val_isvalidated() y val_does_not_exist() devuelven 1 si la condición es verdadera, y 0 en caso contrario.

Las funciones p_val_status(), p_ac_status() y p_val_error() devuelven un puntero a una cadena terminada en nulo. La memoria utilizada por esta cadena es gestionada por la biblioteca y no debe ser liberada por el llamante.

DIAGNÓSTICOS

El código de retorno de las funciones de creación y resolución es un entero negativo que representa un código de error. Los códigos de error disponibles se enumeran en validator.h y se pueden mostrar usando la función p_val_error().

EJEMPLOS

La siguiente es una ilustración simple de cómo consultar el registro A para www.example.com y comprobar si la respuesta está validada:

    val_context_t *context;
    struct val_result_chain *results;
    int res;

    res = val_create_context(NULL, &context);
    if (res != 0) {
        fprintf(stderr, "Failed to create validator context: %s\n", p_val_error(res));
        exit(1);
    }

    res = val_resolve_and_check(context, "www.example.com",
                                DNS_CLASS_IN, DNS_TYPE_A, 0, &results);
    if (res != 0) {
        fprintf(stderr, "Failed to resolve and check www.example.com: %s\n", p_val_error(res));
    } else if (results != NULL) {
        if (val_isvalidated(results->val_status)) {
            printf("www.example.com A record is validated.\n");
        } else if (val_istrusted(results->val_status)) {
            printf("www.example.com A record is trusted but not validated.\n");
        } else {
            printf("www.example.com A record is not trusted or validated.\n");
        }
        val_free_result_chain(results);
    } else {
        printf("No results found for www.example.com A record.\n");
    }

    val_free_context(context);

libval - DNSSEC validator library

SYNOPSIS

int val_istrusted(val_status_t status);

int val_does_not_exist(val_status_t status);

DESCRIPTION

The DNSSEC validator library provides a means for applications to perform DNSSEC validation of DNS data. It can be used to determine if data received from a name server has been cryptographically verified and is trusted.

A validation context is created by calling val_context_create(). The policy argument may be set to VAL_POLICY_GLOBAL to use the default system policy, or VAL_POLICY_LOCAL to use the policy specified by the application.

The context object may be destroyed by calling val_context_destroy().

The context policy may be modified after creation by calling val_context_set_policy() and may be queried using val_context_get_policy().

The context policy structure val_policy_t contains flags that override the default policy configuration file, dnsval.conf. These flags are defined as:

CTX_DYN_POL_RES_OVR
When this flag is set only the name servers specified in the vc_nslist field is used for the resolver configuration. Options specified in the resolv.conf file are ignored.
CTX_DYN_POL_GLO_OVR
When this flag is set only the global options set in gopt field are used. Global options specified in the dnsval.conf file are ignored.
CTX_DYN_POL_RES_NRD
When this flag is set outgoing queries have the Recursion Desired (RD) bit set to 0. This is useful if queries need to be sent to an authoritative-only name server.

The gopt field points to the following structure:

typedef struct val_global_opt {
    int local_is_trusted;
    long edns0_size;
    int env_policy;
    int app_policy;
    char *log_target;
    int closest_ta_only;
    int rec_fallback;
    long max_refresh;
    int proto;
} val_global_opt_t;

Setting a value of 1 for local_is_trusted is equivalent to specifying the trust-oob-answers option in the dnsval.conf file to yes. Similarly, setting the closest_ta_only and rec_fallback members to 1 is equivalent to setting the closest-ta-only and rec-fallback options to yes in the dnsval.conf file. A value of 0 is equivalent to the no setting for these option.

Setting the edns0_size member to a particular value has the same effect setting the edns0-size option in the dnsval.conf file.

Setting the max_refresh member to a particular value has the same effect setting the max-refresh option in the dnsval.conf file.

Setting the proto member to a particular value has the same effect setting the proto option in the dnsval.conf file.

env_policy and app_policy can be set to one of VAL_POL_GOPT_DISABLE, VAL_POL_GOPT_ENABLE, or VAL_POL_GOPT_OVERRIDE. These values correspond directly to the disable, enable and override options for the env-policy and app-policy settings in the dnsval.conf file.

Values of -1 for the above fields are treated as "ignore" conditions in that the validator will not include dynamically supplied global options with a value of -1 when creating its context. This allows an application to overriding a subset of global options while using the global options supplied in the dnsval.conf file by default.

The log_target field enables the application to supply log targets in addition to the ones configured in the configuration file.

See dnsval.conf(5) for more details on specifying validator policy.

Default query flags can be set and unset for a given context using val_context_setqflags(). This allows an application to alter the DNSSEC validator processing, while still having most of the more granular default configuration specified in its configuration file. The action parameter can be set to one of the following.

VAL_CTX_FLAG_SET
This option causes the validator to set the given flag as one of the default query flags.
VAL_CTX_FLAG_RESET
This option causes the validator to reset the given flag if it was set as one of the default query flags for the context.

Answers returned by val_resolve_and_check() are made available in the *results linked list. Each answer corresponds to a distinct RRset; multiple RRs within the RRset are part of the same answer. Multiple answers are possible when type is ns_t_any or ns_t_rrsig.

Individual elements in *results point to val_authentication_chain linked lists. The authentication chain elements in val_authentication_chain contain the actual RRsets returned by the name server in response to the query.

Validation result values returned in val_result_chain can be can be converted into ASCII format using the p_val_status(). Authentication chain status values returned in each element of the val_authentication_chain linked list can be can be converted into ASCII format using the p_ac_status() functions.

While some applications such as DNSSEC troubleshooting utilities and packet inspection tools may look at individual authentication chain elements to identify the actual reasons for validation error, most applications will only be interested in a single error code for determining the authenticity of data.

val_isvalidated() identifies if a given validation result status value corresponds to an answer that was cryptographically verified and validated using a locally configured trust anchor.

val_istrusted() identifies if a given validator status value is trusted. An answer may be locally trusted without being validated.

val_does_not_exist() identifies if a given validator status value corresponds to one of the non-existence types.

The libval library internally allocates memory for *results and this must be freed by the invoking application using the free_result_chain() interface.

NAME

val_status - validation status codes

SYNOPSIS

#include <val.h>

DESCRIPTION

The validator maintains a status code for the validation of a DNS response. The status codes are defined in val_status_t. The following are the possible values for val_status_t:

VAL_SUCCESS
The validation completed successfully.
VAL_FAILURE
The validation failed.
VAL_UNKNOWN
The validation status could not be determined.
VAL_SERVFAIL
The DNS response indicated SERVFAIL.
VAL_NXDOMAIN
The DNS response indicated NXDOMAIN.
VAL_NODATA
The DNS response indicated NOERROR but with no records.
VAL_NOTFOUND
No RRset was found for the query.
VAL_INSECURE
The DNSSEC validation chain could not be established.
VAL_BOGUS
The DNSSEC validation chain failed.
VAL_UNBOUND
The authentication chain is not fully validated.
VAL_PARTIAL
The validation is incomplete.
VAL_NEEDS_RETRY
The validation needs to be retried.
VAL_NO_AUTHCHKSUM
No authoritative checksums were found.
VAL_ATTR_MISMATCH
Attribute mismatch.
VAL_NO_TRUST_ANCHOR
No trust anchor was found.
VAL_NOTRUST
All available components in the authentication chain verified properly, but there was no trust anchor available.

Status values in val_status_t returned by the validator can be displayed in ASCII format using p_val_status().

VAL_AC_RRSIG_ALGORITHM_MISMATCH
    The keytag referenced in the RRSIG matched a
    DNSKEY but the algorithms were different.
VAL_AC_DNSKEY_NOMATCH
    An RRSIG was created by a DNSKEY that did not
    exist in the apex keyset.

For each val_rr_rec member of type DNSKEY (or DS, where relevant) within the authentication chain val_ac_rrset, the validation status is stored in the variable rr_status and can return one of the following values:

VAL_AC_TRUST_POINT
    The given DNSKEY or a DS record was configured
    as a DNSSEC trust anchor.
VAL_AC_SIGNING_KEY
    This DNSKEY was used to create an RRSIG for
    the resource record set.
VAL_AC_VERIFIED_LINK
    This DNSKEY provided the link in the authentication
    chain from the trust anchor to the signed record.
VAL_AC_UNKNOWN_ALGORITHM_LINK
    This DNSKEY provided the link in the authentication
    chain from the trust anchor to the signed record,
    but the DNSKEY algorithm was unknown.
VAL_AC_UNKNOWN_DNSKEY_PROTOCOL
    The DNSKEY protocol number was unrecognized.
VAL_AC_ALGORITHM_NOT_SUPPORTED
    The DNSKEY or DS algorithm was not supported.

VAL_AC_DS_NOMATCH
    An RRSIG was created with a key that did not
    exist in the parent DS record set.
VAL_AC_INVALID_KEY
    The key used to verify the RRSIG was not a valid DNSKEY.
VAL_AC_INVALID_DS
    The DS used to validate the DNSKEY could not be parsed.
rr_next
Points to the next resource record in the RRset.

LOGGING

libval provides the val_log_add_optarg() function for controlling the verbosity and location of log message output.

The val_log_add_optarg() function takes two arguments: the first argument args is a character-string value that specifies the location and verbosity. The second argument, use_stderr, if set to a value greater than 0 allows libval to send log messages to stderr.

The character string that specifies log target location and verbosity has a specific format:

<debug-level>:<dest-type>[:<dest-options>]

where
<debug-level> is 1-7, for increasing levels of verbosity
<dest-type> is one of file, net, syslog, stderr, stdout
<dest-options> depends on <dest-type>
file:<file-name> (opened in append mode)
net[:<host-name>:<host-port>] (127.0.0.1:1053)
syslog[:facility] (0-23 (default 1 USER))

The log levels can be roughly translated into different types of log messages as follows (the messages returned for each level in this list subsumes the messages returned for the level above it):

3 : Error   : error encountered
4 : Warning : recovering from error
5 : Notice  : gives final validation results for a query
              and details on policy files and labels used
6 : Info    : general informational messages
7 : Debug   : detailed debug messages
val_does_not_exist.3

NAME

val_does_not_exist, val_set_log_level, val_log - validator functions

SYNOPSIS

#include <dnssec_validator/dnssec_validator.h>

val_does_not_exist(...);

void
val_set_log_level(int level);

void
val_log(int level, const char *format, ...);

DESCRIPTION

The validator library supports several functions for interacting with the DNSSEC validator. The functions are designed to be called by other programs that wish to make use of the validator library. val_does_not_exist is a placeholder for a function that does not currently exist. It is included to represent a function that would return a specific error value. The function prototypes and return values are provided to give a sense of the types of operations that are available.

val_set_log_level() allows the caller to set the logging level for the validator library. The valid levels are defined in the LOGGING section.

val_log() is the logging function used by the validator library. Callers can use this function to log messages at a specified level.

DATA STRUCTURES

No data structures are defined in this interface.

LOGGING

The validator library supports the following logging levels:

0 : None  : No logging will be performed.
1 : Error : Only errors will be logged.
2 : Warn  : Errors and warnings will be logged.
3 : Info  : Errors, warnings, and informational messages will be logged.
4 : Parse : Gives information on parsing various files and chains.
5 : Crypto: Gives details on crypto operations.
6 : Auth  : gives details on authentication chains
7 : Debug : gives debug level information

RETURN VALUES

Return values for various functions are given below. These values can be displayed in ASCII format using the p_val_error() function.

VAL_NO_ERROR
No error was encountered.
VAL_NOT_IMPLEMENTED
Functionality not yet implemented.
VAL_RESOURCE_UNAVAILABLE
Some resource (crypto possibly) was unavailable. Currently not implemented.
VAL_BAD_ARGUMENT
Bad arguments passed as parameters.
VAL_INTERNAL_ERROR
Encountered some internal error.
VAL_NO_PERMISSION
No permission to perform operation. Currently not implemented.
VAL_CONF_PARSE_ERROR
Error in parsing some configuration file.
VAL_CONF_NOT_FOUND
A configuration file was not available.
VAL_NO_POLICY
The policy identifier being referenced was invalid.

FILES

The validator library reads configuration information from two files, resolv.conf and dnsval.conf.

See dnsval.conf(5) for a description of the syntax for these files.
