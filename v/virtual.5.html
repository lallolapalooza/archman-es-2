VIRTUAL(5) Manual de formatos de archivo VIRTUAL(5)

NOMBRE

virtual - formato de tabla de alias virtuales de Postfix

SINOPSIS

postmap /etc/postfix/virtual
postmap -q "cadena" /etc/postfix/virtual
postmap -q - /etc/postfix/virtual <archivo_entrada

DESCRIPCIÓN


La tabla opcional de alias virtuales virtual(5) (virtual_alias_maps) se aplica a todos los destinatarios: locales(8), virtuales y remotos. Esta característica se implementa en el demonio cleanup(8) de Postfix antes de que el correo sea puesto en cola. Estas tablas a menudo se consultan con una dirección de correo electrónico completa (incluido el dominio).

Esto es diferente de la tabla aliases(5) (alias_maps) que se aplica solo a destinatarios local(8). Esa tabla solo se consulta con la parte local de la dirección de correo electrónico (sin dominio).

El aliasing virtual es recursivo; para terminar la recursión para una dirección específica, aliásela a sí misma.

Las principales aplicaciones del aliasing virtual son:

  • Redirigir el correo de una dirección a una o más direcciones.
  • Implementar dominios de alias virtuales donde todas las direcciones se aliásan a direcciones en otros dominios.

    Los dominios de alias virtuales no deben confundirse con los dominios de buzones virtuales que se implementan con el agente de entrega de correo virtual(8) de Postfix. Con los dominios de buzones virtuales, cada dirección de destinatario puede tener su propio buzón.

El aliasing virtual se aplica solo a las direcciones de sobre del destinatario, y no afecta a las cabeceras del mensaje. Utilice el mapeo canonical(5) para reescribir las cabeceras y las direcciones de sobre en general.

Normalmente, la tabla de alias virtual(5) se especifica como un archivo de texto que sirve como entrada para el comando postmap(1). El resultado, un archivo indexado en formato dbm o db, se utiliza para búsquedas rápidas por el sistema de correo. Ejecute el comando "postmap /etc/postfix/virtual" para reconstruir un archivo indexado después de cambiar el archivo de texto correspondiente.

Cuando la tabla se proporciona a través de otros medios como NIS, LDAP o SQL, se realizan las mismas búsquedas que para los archivos indexados ordinarios.

Alternativamente, la tabla puede proporcionarse como un mapa de expresiones regulares donde los patrones se dan como expresiones regulares, o las búsquedas pueden dirigirse a un servidor basado en TCP. En esos casos, las búsquedas se realizan de una manera ligeramente diferente, como se describe a continuación en "TABLAS DE EXPRESIONES REGULARES" o "TABLAS BASADAS EN TCP".

PLEGAR MAYÚSCULAS Y MINÚSCULAS

La cadena de búsqueda se pliega a minúsculas antes de la búsqueda en la base de datos. A partir de Postfix 2.3, la cadena de búsqueda no se pliega con tipos de base de datos como regexp: o pcre: cuyos campos de búsqueda pueden coincidir tanto con mayúsculas como con minúsculas.

FORMATO DE TABLA

El formato de entrada para el comando postmap(1) es el siguiente:

patrón dirección, dirección, ...
Cuando patrón coincide con una dirección de correo, reemplázala por la dirección correspondiente.
líneas en blanco y comentarios
Las líneas vacías y las líneas que solo contienen espacios en blanco se ignoran, al igual que las líneas cuyo primer carácter que no sea espacio en blanco es un `#'.
texto de múltiples líneas
Una línea lógica comienza con texto que no sean espacios en blanco. Una línea que comienza con espacios en blanco continúa una línea lógica.

ORDEN DE BÚSQUEDA DE TABLA

Con búsquedas de archivos indexados como DB o DBM, o de tablas de red como NIS, LDAP o SQL, cada consulta de usuario@dominio produce una secuencia de patrones de consulta como se describe a continuación.

Cada patrón de consulta se envía a cada tabla de búsqueda especificada antes de intentar el siguiente patrón de consulta, hasta que se encuentra una coincidencia.

usuario@dominio dirección, dirección, ...
Redirige el correo para usuario@dominio a dirección. Esta forma tiene la precedencia más alta.
usuario dirección, dirección, ...
Redirige el correo para usuario@sitio a dirección cuando sitio es igual a $myorigin, cuando sitio está listado en $mydestination, o cuando está listado en $inet_interfaces o $proxy_interfaces.

Esta funcionalidad se solapa con la funcionalidad de la base de datos aliases(5) local. La diferencia es que el mapeo virtual(5) se puede aplicar a direcciones no locales.

@dominio dirección, dirección, ...
Redirige el correo para otros usuarios en dominio a dirección. Esta forma tiene la precedencia más baja.

Nota: @dominio es un comodín. Con esta forma, el servidor SMTP de Postfix acepta correo para cualquier destinatario en dominio, independientemente de si ese destinatario existe. Esto puede convertir su sistema de correo en una fuente de retrodispersión: Postfix primero acepta correo para destinatarios inexistentes y luego intenta devolver ese correo como "no entregable" a la dirección del remitente, a menudo falsificada.

Para evitar la retrodispersión con correo para un dominio comodín, reemplace el mapeo comodín con mapeos explícitos 1:1, o agregue una restricción reject_unverified_recipient para ese dominio:

    smtpd_recipient_restrictions =
        ...
        reject_unauth_destination
        check_recipient_access
            inline:{example.com=reject_unverified_recipient}
    unverified_recipient_reject_code = 550

En el ejemplo anterior, Postfix puede contactar con un servidor remoto si el destinatario está aliásado a una dirección remota.

REESCRITURA DE DIRECCIÓN DE RESULTADO

El resultado de la búsqueda está sujeto a reescritura de direcciones:

  • Cuando el resultado tiene la forma @otrodominio, el resultado se convierte en el mismo usuario en otrodominio. Esto solo funciona para la primera dirección en un resultado de búsqueda de múltiples direcciones.
  • Cuando "append_at_myorigin=yes", agregue "@$myorigin" a las direcciones sin "@dominio".
  • Cuando "append_dot_mydomain=yes", agregue ".$mydomain" a las direcciones sin ".dominio".

EXTENSIÓN DE DIRECCIÓN

Cuando la parte local de una dirección de correo contiene el delimitador de destinatario opcional (por ejemplo, usuario+foo@dominio), el orden de búsqueda se convierte en: usuario+foo@dominio, usuario@dominio, usuario+foo, usuario, y @dominio.

El parámetro propagate_unmatched_extensions controla si una extensión de dirección no coincidente (+foo) se propaga al resultado de una búsqueda de tabla.

DOMINIOS DE ALIAS VIRTUALES

Además de los alias virtuales, la tabla de alias virtuales también puede usarse para implementar dominios de alias virtuales. Con un dominio de alias virtual, todas las direcciones de destinatario se aliásan a direcciones en otros dominios.

Los dominios de alias virtuales no deben confundirse con los dominios de buzones virtuales que se implementan con el agente de entrega de correo virtual(8) de Postfix. Con los dominios de buzones virtuales, cada dirección de destinatario puede tener su propio buzón.

Con un dominio de alias virtual, el dominio virtual tiene su propio espacio de nombres de usuario. Los nombres de usuario locales (es decir, no virtuales) no son visibles en un dominio de alias virtual. En particular, los aliases(5) locales y las listas de correo locales no son visibles como nombrelocal@dominio-de-alias-virtual.

El soporte para un dominio de alias virtual se ve así:

/etc/postfix/main.cf:
    virtual_alias_maps = hash:/etc/postfix/virtual

Nota: algunos sistemas usan bases de datos dbm en lugar de hash. Consulte la salida de "postconf -m" para ver los tipos de base de datos disponibles.

/etc/postfix/virtual:
    dominio-alias-virtual    cualquiercosa (el contenido del lado derecho no importa)
    postmaster@dominio-alias-virtual pos
virtual(5) — Postfix virtual alias lookup tables

NAME

virtual — Postfix virtual alias lookup tables

SYNOPSIS

virtual(5)

Table format for virtual alias mappings

DESCRIPTION

The Postfix SMTP server can rewrite recipient addresses for virtual domains. A virtual domain is a domain that is not necessarily owned by the mail server, but for which the mail server accepts mail.

The mapping is controlled by lookup tables, specified by the virtual_alias_maps parameter in main.cf.

When the Postfix SMTP server receives mail for a domain listed in virtual_alias_domains (or implicitly defined by virtual_alias_maps), it searches the virtual_alias_maps tables for the recipient address.

The lookup tables are searched using the full recipient address, e.g. user@example.com.

If a lookup key matches the recipient address, the lookup result is a new address or a list of addresses (one per line, separated by whitespace). The original recipient address is then replaced by the result address(es).

If the lookup key does not match the recipient address, the search continues with the next table, if any.

If no match is found in any table, the original recipient address is used. If the domain part of the address is one of the domains listed in mydestination or virtual_alias_domains, the address is delivered locally. Otherwise, the address is forwarded to the destination domain.

This lookup is performed by the local(8) delivery agent, after the address has been expanded (see aliases(5)).

CASE FOLDING

For the `virtual` lookup table type, domain names are case-folded before lookup. User names are not case-folded.

TABLE FORMAT

The lookup tables are indexed text files. Each line in the file consists of a lookup key, followed by whitespace, followed by a substitution value. The lookup key is typically an email address. The substitution value is one or more email addresses.

Empty lines and lines starting with '#' or '%' are ignored.

    # comment
    
    key whitespace value

Example:

    # Mail for info@example.com is delivered to sales@example.com
    info@example.com        sales@example.com
    
    # Mail for sales@example.com is delivered to multiple recipients
    sales@example.com       "Alice <alice@example.com>" "Bob <bob@example.com>"
    
    # Mail for unknown users in example.com is delivered to a catch-all address
    @example.com            catchall@example.com

The lookup key can be a full email address (e.g. user@domain.com) or a domain name (e.g. domain.com) or just the wildcard @domain.com for matching any user in that domain. For details, see postmap(1).

The substitution value can be a single address, a comma-separated list of addresses, or multiple addresses separated by whitespace. Enclose addresses in double quotes if they contain special characters or whitespace.

TABLE SEARCH ORDER

The tables are searched in the order they are listed in the virtual_alias_maps parameter. The first match found determines the result.

If a lookup key is a full email address (e.g. user@domain.com), it is looked up first.

If no full email address match is found, and the address includes a domain part (e.g. domain.com), then that domain part is looked up (e.g. domain.com, @domain.com). This allows for catch-all addresses.

The search order is:

  1. Full email address lookup: user@domain.com
  2. Domain wildcard lookup: @domain.com
  3. Domain lookup: domain.com

Example:

    # main.cf
    virtual_alias_maps = hash:/etc/postfix/virtual
    
    # /etc/postfix/virtual
    # Match specific user
    user@example.com     realuser@example.com
    
    # Match all users in example.com (catch-all)
    @example.com         catchall@example.com
    
    # Match a specific domain (less specific than @example.com)
    example.com          domain_catchall@example.com

In this example, mail for user@example.com will be delivered to realuser@example.com because the full email address match takes precedence. Mail for any other user in example.com (e.g. test@example.com) will be delivered to catchall@example.com because the @domain.com entry is checked before the domain.com entry.

RESULT ADDRESS REWRITING

The result of a lookup can be rewritten further by other mapping tables. For example, if the result is user@otherdomain.com, and canonical_maps is configured, Postfix will perform another lookup in the canonical_maps table.

The order of rewriting is:

  1. virtual_alias_maps
  2. spatial_maps (if configured)
  3. canonical_maps
  4. alias_maps

This means that a virtual alias can point to a canonical alias, which in turn can point to a regular alias.

ADDRESS EXTENSION

By default, address extensions (e.g., the part after the '+' in user+tag@example.com) are ignored by virtual alias lookups. If you want to preserve address extensions, you can use the propagate_unmatched_extensions parameter.

When propagate_unmatched_extensions is set to virtual, any address extension that is not matched by a lookup rule will be appended to the result address.

Example:

    # main.cf
    virtual_alias_maps = hash:/etc/postfix/virtual
    propagate_unmatched_extensions = virtual
    
    # /etc/postfix/virtual
    user@example.com     realuser@example.com

With this configuration, mail sent to user+tag@example.com will be delivered to realuser+tag@example.com.

VIRTUAL ALIAS DOMAINS

The virtual_alias_domains parameter in main.cf specifies a list of domains for which Postfix should accept mail and perform virtual alias lookups. This parameter uses the same format as the mydestination parameter.

    # main.cf
    virtual_alias_domains = example.com, virtual.example.com

If you specify a domain in virtual_alias_domains, you must also specify it (or a wildcard mapping) in virtual_alias_maps. Otherwise, mail to that domain will be rejected.

    # main.cf
    virtual_alias_domains = example.com
    virtual_alias_maps = hash:/etc/postfix/virtual
    
    # /etc/postfix/virtual
    # This entry is required, even if it's just a catch-all
    @example.com     catchall@example.com

Alternatively, you can omit virtual_alias_domains and rely solely on virtual_alias_maps to define the virtual domains. In this case, any domain mentioned as a lookup key in virtual_alias_maps is implicitly considered a virtual domain.

    # main.cf
    virtual_alias_maps = hash:/etc/postfix/virtual
    
    # /etc/postfix/virtual
    # example.com is implicitly a virtual domain because it's a key here
    info@example.com        sales@example.com
    user@virtual.example.com address@example.com

It is recommended to explicitly list virtual domains in virtual_alias_domains to avoid potential conflicts or misconfigurations.

Do not specify virtual alias domains in the main.cf mydestination or relay_domains configuration parameters.

With a virtual alias domain, the Postfix SMTP server accepts mail for known-user@virtual-alias.domain, and rejects mail for unknown-user@virtual-alias.domain as undeliverable, unless a catch-all rule is defined.

REGULAR EXPRESSION TABLES

This section describes how the table lookups change when the table is given in the form of regular expressions. For a description of regular expression lookup table syntax, see regexp_table(5) or pcre_table(5).

Each pattern is a regular expression that is applied to the entire address being looked up. Thus, user@domain mail addresses are not broken up into their user and @domain constituent parts, nor is user+foo broken up into user and foo.

Patterns are applied in the order as specified in the table, until a pattern is found that matches the search string.

Results are the same as with indexed file lookups, with the additional feature that parenthesized substrings from the pattern can be interpolated as $1, $2 and so on.

TCP-BASED TABLES

This section describes how the table lookups change when lookups are directed to a TCP-based server. For a description of the TCP client/server lookup protocol, see tcp_table(5). This feature is available in Postfix 2.5 and later.

Each lookup operation uses the entire address once. Thus, user@domain mail addresses are not broken up into their user and @domain constituent parts, nor is user+foo broken up into user and foo.

Results are the same as with indexed file lookups.

BUGS


The table format does not understand quoting conventions.

CONFIGURATION PARAMETERS

The following main.cf parameters are especially relevant to this topic. See the Postfix main.cf file for syntax details and for default values. Use the "postfix reload" command after a configuration change.

virtual_alias_maps ($virtual_maps)
Optional lookup tables that are often searched with a full email address (including domain) and that apply to all recipients: local(8), virtual, and remote; this is unlike alias_maps that are only searched with an email address localpart (no domain) and that apply only to local(8) recipients.
virtual_alias_domains ($virtual_alias_maps)
Postfix is the final destination for the specified list of virtual alias domains, that is, domains for which all addresses are aliased to addresses in other local or remote domains.
propagate_unmatched_extensions (canonical, virtual)
What address lookup tables copy an address extension from the lookup key to the lookup result.

Other parameters of interest:

inet_interfaces (all)
The local network interface addresses that this mail system receives mail on.
mydestination ($myhostname, localhost.$mydomain, localhost)
The list of domains that are delivered via the $local_transport mail delivery transport.
myorigin ($myhostname)
The domain name that locally-posted mail appears to come from, and that locally posted mail is delivered to.
owner_request_special (yes)
Enable special treatment for owner-listname entries in the aliases(5) file, and don't split owner-listname and listname-request address localparts when the recipient_delimiter is set to "-".
proxy_interfaces (empty)
The remote network interface addresses that this mail system receives mail on by way of a proxy or network address translation unit.
