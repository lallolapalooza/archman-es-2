getrlimit(2) Manual de Llamadas al Sistema getrlimit(2)

NOMBRE

getrlimit, setrlimit, prlimit - obtener/establecer límites de recursos

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

SINOPSIS

#include <sys/resource.h>
int getrlimit(int resource, struct rlimit *rlim);
int setrlimit(int resource, const struct rlimit *rlim);
int prlimit(pid_t pid, int resource,
            const struct rlimit *_Nullable new_limit,
            struct rlimit *_Nullable old_limit);
struct rlimit {
    rlim_t  rlim_cur;  /* Límite blando */
    rlim_t  rlim_max;  /* Límite duro (techo para rlim_cur) */
};
typedef /* ... */  rlim_t;  /* Tipo entero sin signo */

DESCRIPCIÓN

Las llamadas al sistema getrlimit() y setrlimit() obtienen y establecen límites de recursos. Cada recurso tiene un límite blando y uno duro asociado, según se define en la estructura rlimit.

El límite blando es el valor que el kernel aplica para el recurso correspondiente. El límite duro actúa como un techo para el límite blando: un proceso no privilegiado puede establecer solo su límite blando a un valor en el rango de 0 hasta el límite duro y (de forma irreversible) reducir su límite duro. Un proceso privilegiado (en Linux: uno con la capacidad CAP_SYS_RESOURCE en el espacio de nombres de usuario inicial) puede realizar cambios arbitrarios en cualquiera de los valores límite.

El valor RLIM_INFINITY denota ningún límite en un recurso (tanto en la estructura devuelta por getrlimit() como en la estructura pasada a setrlimit()).

El argumento resource debe ser uno de:

RLIMIT_AS
Este es el tamaño máximo de la memoria virtual (espacio de direcciones) del proceso. El límite se especifica en bytes y se redondea hacia abajo al tamaño de página del sistema. Este límite afecta a las llamadas a brk(2), mmap(2) y mremap(2), que fallan con el error ENOMEM al superar este límite. Además, la expansión automática de la pila falla (y genera una señal SIGSEGV que mata al proceso si no se ha puesto a disposición una pila alternativa mediante sigaltstack(2)). Dado que el valor es un long, en máquinas con un long de 32 bits, o este límite es como máximo de 2 GiB, o este recurso es ilimitado.
RLIMIT_CORE
Este es el tamaño máximo de un archivo core (ver core(5)) en bytes que el proceso puede volcar. Cuando es 0, no se crean archivos de volcado core. Cuando es distinto de cero, los volcados más grandes se truncan a este tamaño.
RLIMIT_CPU
Este es un límite, en segundos, sobre la cantidad de tiempo de CPU que el proceso puede consumir. Cuando el proceso alcanza el límite blando, se le envía una señal SIGXCPU. La acción predeterminada para esta señal es terminar el proceso. Sin embargo, la señal puede ser capturada y el manejador puede devolver el control al programa principal. Si el proceso continúa consumiendo tiempo de CPU, se le enviará SIGXCPU una vez por segundo hasta que se alcance el límite duro, momento en el cual se le envía SIGKILL. (Este último punto describe el comportamiento de Linux. Las implementaciones varían en cómo tratan los procesos que continúan consumiendo tiempo de CPU después de alcanzar el límite blando. Las aplicaciones portátiles que necesitan capturar esta señal deben realizar una terminación ordenada al recibir SIGXCPU por primera vez.)
RLIMIT_DATA
Este es el tamaño máximo del segmento de datos del proceso (datos inicializados, datos no inicializados y heap). El límite se especifica en bytes y se redondea hacia abajo al tamaño de página del sistema. Este límite afecta a las llamadas a brk(2), sbrk(2) y (desde Linux 4.7) mmap(2), que fallan con el error ENOMEM al encontrar el límite blando de este recurso.
RLIMIT_FSIZE
Este es el tamaño máximo en bytes de los archivos que el proceso puede crear. Los intentos de extender un archivo más allá de este límite resultan en la entrega de una señal SIGXFSZ. Por defecto, esta señal termina un proceso, pero un proceso puede capturar esta señal en su lugar, en cuyo caso la llamada al sistema relevante (por ejemplo, write(2), truncate(2)) falla con el error EFBIG.
RLIMIT_LOCKS (Linux 2.4.0 a Linux 2.4.24)
Este es un límite en el número combinado de bloqueos flock(2) y arrendamientos fcntl(2) que este proceso puede establecer.
RLIMIT_MEMLOCK
Este es el número máximo de bytes de memoria que pueden bloquearse en RAM. Este límite se redondea hacia abajo al múltiplo más cercano del tamaño de página del sistema. Este límite afecta a mlock(2), mlockall(2) y la operación MAP_LOCKED de mmap(2). Desde Linux 2.6.9, también afecta a la operación SHM_LOCK de shmctl(2), donde establece un máximo para los bytes totales en segmentos de memoria compartida (ver shmget(2)) que pueden ser bloqueados por el ID de usuario real del proceso que llama. Los bloqueos SHM_LOCK de shmctl(2) se contabilizan por separado de los bloqueos de memoria por proceso establecidos por mlock(2), mlockall(2) y mmap(2) con MAP_LOCKED; un proceso puede bloquear bytes hasta este límite en cada una de estas dos categorías.
Antes de Linux 2.6.9, este límite controlaba la cantidad de memoria que podía ser bloqueada por un proceso privilegiado. Desde Linux 2.6.9, no hay límites sobre la cantidad de memoria que un proceso privilegiado puede bloquear, y este límite rige en su lugar la cantidad de memoria que un proceso no privilegiado puede bloquear.
RLIMIT_MSGQUEUE (desde Linux 2.6.8)
Este es un límite en el número de bytes que se pueden asignar para colas de mensajes POSIX para el ID de usuario real del proceso que llama. Este límite se aplica para mq_open(3). Cada cola de mensajes que el usuario crea cuenta (hasta que se elimina) contra este límite según la fórmula:
Desde Linux 3.5:

bytes = attr.mq_maxmsg * sizeof(struct msg_msg) +
        MIN(attr.mq_maxmsg, MQ_PRIO_MAX) *
              sizeof(struct posix_msg_tree_node)+
                        /* Por sobrecarga */
        attr.mq_maxmsg * attr.mq_msgsize;
                        /* Por datos del mensaje */

Linux 3.4 y anteriores:

bytes = attr.mq_maxmsg * sizeof(struct msg_msg *) +
                        /* Por sobrecarga */
        attr.mq_maxmsg * attr.mq_msgsize;
                        /* Por datos del mensaje */

donde attr es la estructura mq_attr especificada como el cuarto argumento a mq_open(3), y las estructuras msg_msg y posix_msg_tree_node son estructuras internas del kernel.
La adición de "sobrecarga" en la fórmula tiene en cuenta los bytes de sobrecarga requeridos por la implementación y asegura que el usuario no pueda crear un número ilimitado de mensajes de longitud cero (dichos mensajes consumen de todos modos algo de memoria del sistema para la sobrecarga de contabilidad).
RLIMIT_NICE (desde Linux 2.6.12, pero ver BUGS abajo)
Esto especifica un techo al cual el valor de nice del proceso puede ser elevado usando setpriority(2) o nice(2). El techo real para el valor de nice se calcula como 20 - rlim_cur. El rango útil
for this limit is thus from 1 (corresponding to a nice value of 19) to 40 (corresponding to a nice value of -20). This unusual choice of range was necessary because negative numbers cannot be specified as resource limit values, since they typically have special meanings. For example, RLIM_INFINITY typically is the same as -1. For more detail on the nice value, see sched(7).
RLIMIT_NOFILE
This specifies a value one greater than the maximum file descriptor number that can be opened by this process. Attempts (open(2), pipe(2), dup(2), etc.) to exceed this limit yield the error EMFILE. (Historically, this limit was named RLIMIT_OFILE on BSD.)
Since Linux 4.5, this limit also defines the maximum number of file descriptors that an unprivileged process (one without the CAP_SYS_RESOURCE capability) may have "in flight" to other processes, by being passed across UNIX domain sockets. This limit applies to the sendmsg(2) system call. For further details, see unix(7).
RLIMIT_NPROC
This is a limit on the number of extant process (or, more precisely on Linux, threads) for the real user ID of the calling process. So long as the current number of processes belonging to this process's real user ID is greater than or equal to this limit, fork(2) fails with the error EAGAIN.
The RLIMIT_NPROC limit is not enforced for processes that have either the CAP_SYS_ADMIN or the CAP_SYS_RESOURCE capability, or run with real user ID 0.
RLIMIT_RSS
This is a limit (in bytes) on the process's resident set (the number of virtual pages resident in RAM). This limit has effect only in Linux 2.4.x, x < 30, and there affects only calls to madvise(2) specifying MADV_WILLNEED.
RLIMIT_RTPRIO (since Linux 2.6.12, but see BUGS)
This specifies a ceiling on the real-time priority that may be set for this process using sched_setscheduler(2) and sched_setparam(2).
For further details on real-time scheduling policies, see sched(7)
RLIMIT_RTTIME (since Linux 2.6.25)
This is a limit (in microseconds) on the amount of CPU time that a process scheduled under a real-time scheduling policy may consume without making a blocking system call. For the purpose of this limit, each time a process makes a blocking system call, the count of its consumed CPU time is reset to zero. The CPU time count is not reset if the process continues trying to use the CPU but is preempted, its time slice expires, or it calls sched_yield(2).
Upon reaching the soft limit, the process is sent a SIGXCPU signal. If the process catches or ignores this signal and continues consuming CPU time, then SIGXCPU will be generated once each second until the hard limit is reached, at which point the process is sent a SIGKILL signal.
The intended use of this limit is to stop a runaway real-time process from locking up the system.
For further details on real-time scheduling policies, see sched(7)
RLIMIT_SIGPENDING (since Linux 2.6.8)
This is a limit on the number of signals that may be queued for the real user ID of the calling process. Both standard and real-time signals are counted for the purpose of checking this limit. However, the limit is enforced only for sigqueue(3); it is always possible to use kill(2) to queue one instance of any of the signals that are not already queued to the process.
RLIMIT_STACK
This is the maximum size of the process stack, in bytes. Upon reaching this limit, a SIGSEGV signal is generated. To handle this signal, a process must employ an alternate signal stack (sigaltstack(2)).
Since Linux 2.6.23, this limit also determines the amount of space used for the process's command-line arguments and environment variables; for details, see execve(2).

prlimit()

The Linux-specific prlimit() system call combines and extends the functionality of setrlimit() and getrlimit(). It can be used to both set and get the resource limits of an arbitrary process.

The resource argument has the same meaning as for setrlimit() and getrlimit().

If the new_limit argument is not NULL, then the rlimit structure to which it points is used to set new values for the soft and hard limits for resource. If the old_limit argument is not NULL, then a successful call to prlimit() places the previous soft and hard limits for resource in the rlimit structure pointed to by old_limit.

The pid argument specifies the ID of the process on which the call is to operate. If pid is 0, then the call applies to the calling process. To set or get the resources of a process other than itself, the caller must have the CAP_SYS_RESOURCE capability in the user namespace of the process whose resource limits are being changed, or the real, effective, and saved user IDs of the target process must match the real user ID of the caller and the real, effective, and saved set group IDs of the target process must match the real group ID of the caller.

VALOR DE RETORNO

En caso de éxito, estas llamadas al sistema devuelven 0. En caso de error, se devuelve -1 y errno se establece para indicar el error.

ERRORES

EFAULT
Un argumento de puntero apunta a una ubicación fuera del espacio de direcciones accesible.
EINVAL
El valor especificado en resource no es válido; o, para setrlimit() o prlimit(): rlim->rlim_cur era mayor que rlim->rlim_max.
EPERM
Un proceso no privilegiado intentó aumentar el límite duro; la capacidad CAP_SYS_RESOURCE es necesaria para hacer esto.
EPERM
El llamador intentó aumentar el límite duro RLIMIT_NOFILE por encima del máximo definido por /proc/sys/fs/nr_open (ver proc(5))
EPERM
(prlimit()) El proceso llamador no tenía permiso para establecer los límites del proceso especificado por pid.
ESRCH
No se pudo encontrar un proceso con el ID especificado en pid.

NOTAS

Un proceso hijo creado a través de fork(2) hereda los límites de recursos de su padre. Los límites de recursos se conservan a través de execve(2).

Los límites de recursos son atributos por proceso que son compartidos por todos los hilos de un proceso.

Reducir el límite blando para un recurso por debajo del consumo actual de ese recurso por parte del proceso tendrá éxito (pero evitará que el proceso aumente aún más su consumo del recurso).

Se pueden establecer los límites de recursos del shell utilizando el comando integrado ulimit (limit en csh(1)). Los límites de recursos del shell son heredados por los procesos que crea para ejecutar comandos.

Desde Linux 2.6.24, los límites de recursos de cualquier proceso pueden ser inspeccionados a través de /proc/pid/limits; ver proc(5).

Sistemas antiguos proporcionaban una función vlimit() con un propósito similar a setrlimit(). Para compatibilidad con versiones anteriores, glibc al

so proporciona vlimit(). Todas las aplicaciones nuevas deben escribirse utilizando setrlimit().

Diferencias entre la librería C y la ABI del kernel

Desde glibc 2.13, las funciones de envoltura getrlimit() y setrlimit() de glibc ya no invocan las llamadas al sistema correspondientes, sino que utilizan prlimit(), por las razones descritas en BUGS.

El nombre de la función de envoltura de glibc es prlimit(); la llamada al sistema subyacente es prlimit64().

BUGS

En kernels de Linux más antiguos, las señales SIGXCPU y SIGKILL enviadas cuando un proceso encontraba los límites blandos y duros de RLIMIT_CPU se entregaban un segundo (de CPU) más tarde de lo debido. Esto se corrigió en Linux 2.6.8.

En los kernels de Linux 2.6.x anteriores a Linux 2.6.17, un límite de RLIMIT_CPU de 0 se trata erróneamente como "sin límite" (como RLIM_INFINITY). Desde Linux 2.6.17, establecer un límite de 0 sí tiene efecto, pero se trata como un límite de 1 segundo.

Un error del kernel provoca que RLIMIT_RTPRIO no funcione en Linux 2.6.12; el problema se corrigió en Linux 2.6.13.

En Linux 2.6.12, hubo un error de un elemento en el rango de prioridades devuelto por getpriority(2) y RLIMIT_NICE. Esto tuvo el efecto de que el techo real para el valor nice se calculaba como 19 - rlim_cur. Esto se corrigió en Linux 2.6.13.

Desde Linux 2.6.12, si un proceso alcanza su límite blando de RLIMIT_CPU y tiene un manejador instalado para SIGXCPU, entonces, además de invocar el manejador de señales, el kernel incrementa el límite blando en un segundo. Este comportamiento se repite si el proceso continúa consumiendo tiempo de CPU, hasta que se alcanza el límite duro, momento en el que el proceso es terminado. Otras implementaciones no modifican el límite blando de RLIMIT_CPU de esta manera, y el comportamiento de Linux probablemente no sea conforme a los estándares; las aplicaciones portátiles deben evitar depender de este comportamiento específico de Linux. El límite específico de Linux RLIMIT_RTTIME presenta el mismo comportamiento cuando se encuentra el límite blando.

Los kernels anteriores a Linux 2.4.22 no diagnosticaban el error EINVAL para setrlimit() cuando rlim->rlim_cur era mayor que rlim->rlim_max.

Linux no devuelve un error cuando un intento de establecer RLIMIT_CPU ha fallado, por razones de compatibilidad.

Representación de valores de límite de recursos "grandes" en plataformas de 32 bits

Las funciones de envoltura getrlimit() y setrlimit() de glibc utilizan un tipo de datos rlim_t de 64 bits, incluso en plataformas de 32 bits. Sin embargo, el tipo de datos rlim_t utilizado en las llamadas al sistema getrlimit() y setrlimit() es un unsigned long (de 32 bits). Además, en Linux, el kernel representa los límites de recursos en plataformas de 32 bits como unsigned long. Sin embargo, un tipo de datos de 32 bits no es lo suficientemente amplio. El límite más relevante aquí es RLIMIT_FSIZE, que especifica el tamaño máximo al que un archivo puede crecer: para ser útil, este límite debe representarse utilizando un tipo tan amplio como el tipo utilizado para representar los desplazamientos de archivo, es decir, tan amplio como un off_t de 64 bits (asumiendo un programa compilado con _FILE_OFFSET_BITS=64).

Para solucionar esta limitación del kernel, si un programa intentaba establecer un límite de recursos a un valor mayor que el que se puede representar en un unsigned long de 32 bits, la función de envoltura setrlimit() de glibc convertía silenciosamente el valor del límite a RLIM_INFINITY. En otras palabras, la configuración solicitada del límite de recursos se ignoraba silenciosamente.

Desde glibc 2.13, glibc soluciona las limitaciones de las llamadas al sistema getrlimit() y setrlimit() implementando setrlimit() y getrlimit() como funciones de envoltura que llaman a prlimit().

EJEMPLOS

El programa siguiente demuestra el uso de prlimit().

#define _GNU_SOURCE
#define _FILE_OFFSET_BITS 64
#include <err.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/resource.h>
#include <time.h>
int
main(int argc, char *argv[])
{
    pid_t          pid;
    struct rlimit  old, new;
    struct rlimit  *newp;
    if (!(argc == 2 || argc == 4)) {
        fprintf(stderr, "Uso: %s <pid> [<límite-blando-nuevo> "
                "<límite-duro-nuevo>]\n", argv[0]);
        exit(EXIT_FAILURE);
    }
    pid = atoi(argv[1]);        /* PID del proceso objetivo */
    newp = NULL;
    if (argc == 4) {
        new.rlim_cur = atoi(argv[2]);
        new.rlim_max = atoi(argv[3]);
        newp = &new;
    }
    /* Establecer el límite de tiempo de CPU del proceso objetivo; recuperar y mostrar
       el límite anterior */
    if (prlimit(pid, RLIMIT_CPU, newp, &old) == -1)
        err(EXIT_FAILURE, "prlimit-1");
    printf("Límites anteriores: blando=%jd; duro=%jd\n",
           (intmax_t) old.rlim_cur, (intmax_t) old.rlim_max);
    /* Recuperar y mostrar el nuevo límite de tiempo de CPU */
    if (prlimit(pid, RLIMIT_CPU, NULL, &old) == -1)
        err(EXIT_FAILURE, "prlimit-2");
    printf("Nuevos límites: blando=%jd; duro=%jd\n",
           (intmax_t) old.rlim_cur, (intmax_t) old.rlim_max);
    exit(EXIT_SUCCESS);
}
