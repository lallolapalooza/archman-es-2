NOMBRE

VCL-steps - subrutinas incorporadas

DESCRIPCIÓN

Varias subrutinas incorporadas son llamadas durante el procesamiento de las solicitudes del cliente y del backend, así como tras vcl.load y vcl.discard.

Ver reference-states para una descripción gráfica detallada de los estados y cómo se relacionan con las funciones del código principal y las subrutinas VCL.

Las subrutinas incorporadas siempre terminan con un return(<acción>), donde <acción> determina cómo continúa el procesamiento en la máquina de estados de procesamiento de solicitudes.

El comportamiento de las acciones es idéntico o al menos similar entre las subrutinas, por lo que las diferencias solo se documentan cuando son relevantes.

Las acciones comunes se documentan en vcl_actions en la siguiente sección. Las acciones específicas de una o solo algunas subrutinas se documentan en vcl_steps.

Se proporciona un comportamiento predeterminado para todos los reference-states en el código vcl-built-in-code.

ACCIONES VCL

Las acciones se utilizan con la palabra clave return(<acción>), que devuelve el control de las subrutinas a varnish. La acción determina cómo continúa el procesamiento en varnish, como se muestra en reference-states.

Las acciones comunes se documentan aquí, mientras que las acciones adicionales específicas de una o solo algunas subrutinas se documentan en la siguiente sección vcl_steps, así como qué acción se puede usar desde qué subrutina incorporada.

Acciones comunes para el lado del cliente y el backend

fail(err)

Transición a vcl_synth en el lado del cliente como para return(synth(503, "VCL Fallida")), pero con cualquier cambio de estado de la solicitud deshecho como si se hubiera llamado a std.rollback() y forzando el cierre de la conexión. El argumento de cadena opcional err se registra en VSL bajo una etiqueta VCL_Error.

Devolver fail desde vcl_synth envía una respuesta mínima con un estado 500.

Destinado a errores fatales, para los cuales solo es posible un manejo mínimo de errores.

Acciones comunes para el lado del cliente

synth(estado código, razón)

Transición a vcl_synth con resp.status y resp.reason preestablecidos a los argumentos de synth().

pass

Cambiar al modo pass, haciendo que la solicitud actual no utilice la caché ni ponga su respuesta en ella. El control eventualmente pasará a vcl_pass.

pipe

Cambiar al modo pipe. El control eventualmente pasará a vcl_pipe.

restart

Reiniciar la transacción. Incrementa el contador req.restarts.

Si el número de reinicios es mayor que el parámetro max_restarts, el control pasa a vcl_synth como para return(synth(503, "Demasiados reinicios"))

Para un reinicio, todas las modificaciones a los atributos de req se conservan excepto para req.restarts y req.xid, que deben cambiar por diseño.

Acciones comunes para el lado del backend

abandon

Abandonar la solicitud del backend. A menos que la solicitud del backend fuera una obtención en segundo plano, el control pasa a vcl_synth en el lado del cliente con resp.status preestablecido a 503.

PASOS VCL

Lado del cliente

vcl_recv

Se llama al principio de una solicitud, después de que la solicitud completa ha sido recibida y analizada, después de un restart o como resultado de una inclusión ESI.

Su propósito es decidir si servir o no la solicitud, modificarla posiblemente y decidir cómo procesarla más a fondo. Se puede establecer una pista de backend como predeterminada para el lado del procesamiento del backend.

La subrutina vcl_recv puede terminar llamando a return() en una de las siguientes palabras clave:

fail(err)
ver sección fail arriba
synth(código de estado, razón)
ver sección synth arriba
restart
ver sección restart arriba
pass
ver sección pass arriba
pipe
ver sección pipe arriba
hash
Continuar procesando el objeto como un candidato potencial para el
almacenamiento en caché. Pasa el control a vcl_hash.
purge
Purgar el objeto y sus variantes. El control pasa a través de
vcl_hash a vcl_purge.
vcl(etiqueta)
Cambiar a vcl etiquetado con etiqueta.
Esto revertirá la solicitud como si se hubiera llamado a
std.rollback(req) y continuará el procesamiento vcl en
vcl_recv del vcl etiquetado con etiqueta como si fuera
el vcl activo.
El retorno vcl(etiqueta) solo es válido mientras el contador
req.restarts sea cero y si se usa desde el vcl activo.
Ver el comando ref_cli_vcl_label en varnish-cli(7).

vcl_pipe

Se llama al entrar en modo pipe. En este modo, la solicitud se pasa al backend, y cualquier dato adicional tanto del cliente como del backend se pasa sin cambios hasta que alguno de los extremos cierre la conexión. Básicamente, Varnish se degrada a un simple proxy TCP, mezclando bytes de aquí para allá. Para una conexión en modo pipe, ninguna otra subrutina VCL será llamada después de vcl_pipe.

La subrutina vcl_pipe puede terminar llamando a return() con una de las siguientes palabras clave:

fail(err)
ver sección fail arriba
synth(código de estado, razón)
ver sección synth arriba
pipe
Continuar con el modo pipe.

vcl_pass

Se llama al entrar en modo pass. En este modo, la solicitud se pasa al backend, y la respuesta del backend se pasa al cliente, pero no se introduce en la caché. Las solicitudes posteriores enviadas a través de la misma conexión de cliente se manejan normalmente.

La subrutina vcl_pass puede terminar llamando a return() con una de las siguientes palabras clave:

fail(err)
ver sección fail arriba
synth(código de estado, razón)
ver sección synth arriba
restart
ver sección restart arriba
fetch
Continuar con el modo pass - iniciar una solicitud de backend.

vcl_hash

Se llama después de vcl_recv para crear un valor hash para la solicitud. Esto se utiliza como clave para buscar el objeto en Varnish.

La subrutina vcl_hash puede terminar llamando a return() con una de las siguientes palabras clave:

fail(err)
ver sección fail arriba
lookup
Buscar el objeto en la caché.
El control pasa a vcl_purge cuando proviene de un retorno
purge en vcl_recv.
De lo contrario, el control pasa a la siguiente subrutina según el
resultado de la búsqueda en caché:
* un acierto: pasar a vcl_hit
* un fallo o un acierto en un objeto "hit-for-miss" (un objeto con
obj.uncacheable == true): pasar a vcl_miss
* un acierto en un objeto "hit-for-pass" (para el cual se había
devuelto previamente pass(DURACIÓN) desde
vcl_backend_response): pasar a
vcl_pass

vcl_purge

fail(err)
ver sección fail arriba

vcl_miss

Se llama después de una búsqueda en caché si el documento solicitado no se encontró en la caché o si vcl_hit devolvió fetch.

Su propósito es decidir si intentar o no recuperar el documento del backend. Se puede establecer una pista del backend como predeterminada para el lado del procesamiento del backend.

La subrutina vcl_miss puede terminar llamando return() con una de las siguientes palabras clave:

fail(err)
ver sección fail arriba
synth(status code, reason)
ver sección synth arriba
restart
ver sección restart arriba
pass
ver sección pass arriba
fetch
Recuperar el objeto solicitado del backend. El control finalmente pasará
a vcl_backend_fetch.

vcl_hit

Se llama cuando una búsqueda en caché es exitosa. El objeto impactado puede estar obsoleto: puede tener un ttl cero o negativo con solo tiempo de grace o keep restante.

La subrutina vcl_hit puede terminar llamando return() con una de las siguientes palabras clave:

fail(err)
ver sección fail arriba
synth(status code, reason)
ver sección synth arriba
restart
ver sección restart arriba
pass
ver sección pass arriba
deliver
Entregar el objeto. Si está obsoleto, se activa una búsqueda en segundo
plano para actualizarlo.

vcl_deliver

Se llama antes de que se entregue al cliente cualquier objeto, excepto un resultado de vcl_synth.

La subrutina vcl_deliver puede terminar llamando return() con una de las siguientes palabras clave:

fail(err)
ver sección fail arriba
synth(status code, reason)
ver sección synth arriba
restart
ver sección restart arriba
deliver
Entregar el objeto al cliente.

vcl_synth

Se llama para entregar un objeto sintético. Un objeto sintético se genera en VCL, no se recupera del backend. Su cuerpo se puede construir usando la función synthetic().

Un objeto definido por vcl_synth nunca entra en la caché, a diferencia de un objeto definido por vcl_backend_error, que puede terminar en la caché.

La subrutina puede terminar llamando return() con una de las siguientes palabras clave:

fail(err)
ver sección fail arriba
restart
ver sección restart arriba
deliver
Entregar directamente el objeto definido por vcl_synth al cliente
sin llamar a vcl_deliver.

Lado del Backend

vcl_backend_fetch

Se llama antes de enviar la solicitud al backend. En esta subrutina, típicamente se modifica la solicitud antes de que llegue al backend.

La subrutina vcl_backend_fetch puede terminar llamando return() con una de las siguientes palabras clave:

fail(err)
ver sección fail arriba
abandon
ver sección abandon arriba
fetch
Recuperar el objeto del backend.
error(status code, reason)
Transición a vcl_backend_error con beresp.status y
beresp.reason preestablecidos a los argumentos de error() si
se proporcionan argumentos.

Antes de llamar a vcl_backend_fetch, el núcleo de Varnish prepara la solicitud del backend bereq de la siguiente manera:

•
A menos que la solicitud sea un pass,
  • establecer bereq.method a GET y bereq.proto a HTTP/1.1 y
  • establecer bereq.http.Accept_Encoding a gzip si ref_param_http_gzip_support está habilitado.
  • Si hay un objeto de caché existente que debe ser revalidado, establecer bereq.http.If-Modified-Since a partir de su encabezado Last-Modified y/o establecer bereq.http.If-None-Match a partir de su encabezado Etag
  • Establecer bereq.http.X-Varnish al ID de transacción actual (vxid)

Estos cambios se pueden deshacer o modificar en vcl_backend_fetch antes de que se emita la solicitud al backend.

En particular, para almacenar en caché solicitudes que no sean GET, req.method debe guardarse en un encabezado o variable en vcl_recv y restaurarse a bereq.method. Tenga en cuenta que almacenar en caché solicitudes que no sean GET generalmente también requiere cambiar la clave de caché en vcl_hash, por ejemplo, hasheando también el método de solicitud y/o el cuerpo de la solicitud.

Las solicitudes HEAD se pueden satisfacer a partir de respuestas GET en caché.

vcl_backend_refresh

Esta subrutina se llama después de recibir una respuesta 304 legítima del backend para que pueda elegir cómo manejar la revalidación del objeto.

El valor predeterminado es aplicar la lógica RFC, que consiste en fusionar los nuevos encabezados con los obsoletos.

El valor devuelto solo afecta a los encabezados de respuesta; el cuerpo que se entrega es siempre el del objeto obsoleto.

merge
Fusionar los encabezados que obtuvimos de la respuesta del backend con
los que teníamos en el objeto en caché.
obj_stale
Devolver los encabezados del objeto obsoleto sin realizar la lógica de
fusión RFC.
beresp
Devolver los encabezados de beresp tal como estaban al final de esta
subrutina sin ejecutar la lógica de fusión RFC. Los encabezados
content-length y content-encoding presentes en el beresp 304 se
eliminarán y se reemplazarán por los del objeto obsoleto si están
disponibles. Los encabezados Etag y Last-Modified también se copian
del objeto obsoleto para permitir futuras revalidaciones.
fail
ver sección fail arriba
abandon
ver sección abandon arriba
retry
Reintentar la transacción del backend. Incrementa el contador
retries. Si el número de reintentos es mayor que
max_retries, el control se pasará a
vcl_backend_error.
error(status code, reason)
Transición a vcl_backend_error con beresp.status y
beresp.reason preestablecidos a los argumentos de error() si
se proporcionan argumentos.

vcl_backend_response

Se llama después de que se hayan recuperado con éxito los encabezados de respuesta del backend.

La subrutina vcl_backend_response puede terminar llamando return() con una de las siguientes palabras clave:

fail(err)
ver sección fail arriba
abandon
ver sección abandon arriba
deliver
Para una respuesta 304, crear un objeto de caché actualizado.
De lo contrario, recuperar el cuerpo del objeto del backend e iniciar
la entrega a las solicitudes de cliente en espera, posiblemente en
paralelo (streaming).
retry
Reintentar la transacción del backend. Incrementa el contador
retries. Si el número de reintentos es mayor que
max_retries, el control se pasará a
vcl_backend_error.
pass(duration)
Marcar el objeto como hit-for-pass durante la duración dada. Las
búsquedas subsiguientes que impacten este objeto se convertirán en
transacciones pasadas, como si vcl_recv hubiera devuelto
pass.
error(status code, reason)
Transición a vcl_backend_error con beresp.status y
beresp.reason preestablecidos a los argumentos de error() si
se proporcionan argumentos.

vcl_backend_error

Esta subrutina se llama si falla la recuperación del backend o si se exceden las max_retries.

Devolver con abandon no deja un objeto en caché.

Si se devuelve con deliver y beresp.uncacheable == false, se genera un objeto de caché sintético en VCL, cuyo cuerpo se puede construir usando la función synthetic().

Dado que estos objetos sintéticos se almacenan en caché en estas circunstancias especiales, tenga cuidado al colocar información privada allí. Si realmente debe hacerlo, debe establecer explícitamente beresp.uncacheable a true en vcl_backend_error.

La subrutina vcl_backend_error puede terminar llamando return() con una de las siguientes palabras clave:

fail(err)
ver sección fail arriba
abandon
ver sección abandon arriba
deliver
Entregar y posiblemente almacenar en caché el objeto definido en
vcl_backend_error como si se hubiera recuperado del backend,
también conocido como "backend synth".
retry
Reintentar la transacción del backend. Incrementa el contador
retries. Si el número de reintentos es mayor que
max_retries, se llama a vcl_synth en el lado del cliente
con resp.status preestablecido a 503.

Durante vcl.load / vcl.discard

vcl_init

Se llama cuando se carga VCL, antes de que pasen solicitudes a través de ella. Típicamente se usa para inicializar VMODs.

La subrutina vcl_init puede terminar llamando return() con una de las siguientes palabras clave:

ok
Retorno normal, VCL continúa cargándose.
fail(err)
Abortar la carga de esta VCL.

vcl_fini

Se llama cuando se descarta VCL solo después de que todas las solicitudes hayan salido de VCL. Típicamente se usa para limpiar VMODs.

La subrutina vcl_fini puede terminar llamando return() con una de las siguientes palabras clave:

ok
Retorno normal, VCL se descartará.
