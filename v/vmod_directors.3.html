DESCRIPCIÓN

vmod_directors habilita el balanceo de carga de backend en Varnish.

El módulo implementa técnicas de balanceo de carga, y también sirve como un ejemplo de cómo se podrían extender las capacidades de balanceo de carga de Varnish.

Para habilitar el balanceo de carga, debes importar este vmod (directors).

Luego defines tus backends. Una vez que tienes los backends declarados, puedes agregarlos a un director. Esto ocurre en el código VCL ejecutado. Si quieres emular el comportamiento anterior de Varnish 3.0, puedes simplemente inicializar los directores en vcl_init{}, así:

sub vcl_init {
    new vdir = directors.round_robin();
    vdir.add_backend(backend1);
    vdir.add_backend(backend2);
}

Como puedes ver, no hay nada que te impida manipular los directores en otras partes de VCL. Por lo tanto, podrías tener código VCL que agregue más backends a un director cuando se llame a una URL específica.

Ten en cuenta que los directores pueden usar otros directores como backends.

new xround_robin = directors.round_robin()

Crea un director de ronda robin.

Este director seleccionará backends en un orden de ronda robin.

Ejemplo:

new vdir = directors.round_robin();

VOID xround_robin.add_backend(BACKEND)

Agrega un backend al director de ronda robin.

Ejemplo:

vdir.add_backend(backend1);

VOID xround_robin.remove_backend(BACKEND)

Elimina un backend del director de ronda robin.

Ejemplo:

vdir.remove_backend(backend1);

BACKEND xround_robin.backend()

Selecciona un backend del director.

Ejemplo:

set req.backend_hint = vdir.backend();

new xfallback = directors.fallback(BOOL sticky=0)

Crea un director de fallback.

Un director de fallback probará cada uno de los backends agregados en orden, y devolverá el primero que esté sano.

Si sticky se establece en true, el director seguirá utilizando el backend sano, incluso si un backend de mayor prioridad queda disponible. Una vez que se agota toda la lista de backends, volverá a empezar desde el principio.

Ejemplo:

new vdir = directors.fallback();

VOID xfallback.add_backend(BACKEND)

Agrega un backend al director.

Ten en cuenta que el orden en que se hace esto es importante para el director de fallback.

Ejemplo:

vdir.add_backend(backend1);

VOID xfallback.remove_backend(BACKEND)

Elimina un backend del director.

Ejemplo:

vdir.remove_backend(backend1);

BACKEND xfallback.backend()

Selecciona un backend del director.

Ejemplo:

set req.backend_hint = vdir.backend();

new xrandom = directors.random()

Crea un director de backend aleatorio.

El director aleatorio distribuye la carga entre los backends utilizando una distribución de probabilidad aleatoria ponderada.

Se utiliza el generador aleatorio "testeable" en varnishd, que permite ejecutar pruebas deterministas (Ver: d00004.vtc).

Ejemplo:

new vdir = directors.random();

VOID xrandom.add_backend(BACKEND, REAL)

Agrega un backend al director con un peso dado.

Cada backend recibirá aproximadamente el 100 * (peso / (suma(todos_los_pesos_agregados))) por ciento del tráfico enviado a este director.

Ejemplo:

# 2/3 a backend1, 1/3 a backend2.
vdir.add_backend(backend1, 10.0);
vdir.add_backend(backend2, 5.0);

VOID xrandom.remove_backend(BACKEND)

Elimina un backend del director.

Ejemplo:

vdir.remove_backend(backend1);

BACKEND xrandom.backend()

Selecciona un backend del director.

Ejemplo:

set req.backend_hint = vdir.backend();

new xhash = directors.hash()

Crea un director de backend de hash.

El director elige el servidor de backend calculando un hash/digest de la cadena dada a xhash.backend().

Comúnmente utilizado con client.ip o una cookie de sesión para obtener sesiones fijas (sticky sessions).

Ejemplo:

new vdir = directors.hash();

VOID xhash.add_backend(BACKEND, REAL weight=1.0)

Add a backend to the director with a certain weight.

Weight is used as in the random director. Recommended and default value is 1.0 unless you have special needs.

Example:

vdir.add_backend(normal_backend);
vdir.add_backend(larger_backend, 1.5);

VOID xhash.remove_backend(BACKEND)

Remove a backend from the director.

Example::
vdir.remove_backend(larger_backend);

BACKEND xhash.backend(STRING)

Pick a backend from the hash director.

Use the string or list of strings provided to pick the backend.

Example::
# pick a backend based on the cookie header from the client set req.backend_hint = vdir.backend(req.http.cookie);

DIRECTORS.XSHARD

new xshard = directors.shard()

Create a shard director.

Introduction

The shard director selects backends by a key, which can be provided directly or derived from strings. For the same key, the shard director will always return the same backend, unless the backend configuration or health state changes. Conversely, for differing keys, the shard director will likely choose different backends. In the default configuration, unhealthy backends are not selected.

The shard director resembles the hash director, but its main advantage is that, when the backend configuration or health states change, the association of keys to backends remains as stable as possible.

In addition, the rampup and warmup features can help to further improve user-perceived response times.

Sharding

This basic technique allows for numerous applications like optimizing backend server cache efficiency, Varnish clustering or persisting sessions to servers without keeping any state, and, in particular, without the need to synchronize state between nodes of a cluster of Varnish servers:

  • Many applications use caches for data objects, so, in a cluster of application servers, requesting similar objects from the same server may help to optimize efficiency of such caches.

    For example, sharding by URL or some id component of the url has been shown to drastically improve the efficiency of many content management systems.

  • As special case of the previous example, in clusters of Varnish servers without additional request distribution logic, each cache will need store all hot objects, so the effective cache size is approximately the smallest cache size of any server in the cluster.

    Sharding allows to segregate objects within the cluster such that each object is only cached on one of the servers (or on one primary and one backup, on a primary for long and others for short etc...). Effectively, this will lead to a cache size in the order of the sum of all individual caches, with the potential to drastically increase efficiency (scales by the number of servers).

  • Another application is to implement persistence of backend requests, such that all requests sharing a certain criterion (such as an IP address or session ID) get forwarded to the same backend server.

When used with clusters of varnish servers, the shard director will, if otherwise configured equally, make the same decision on all servers. In other words, requests sharing a common criterion used as the shard key will be balanced onto the same backend server(s) no matter which Varnish server handles the request.

The drawbacks are:

  • the distribution of requests depends on the number of requests per key and the uniformity of the distribution of key values. In short, while this technique may lead to much better efficiency overall, it may also lead to less good load balancing for specific cases.
  • When a backend server becomes unavailable, every persistence technique has to reselect a new backend server, but this technique will also switch back to the preferred server once it becomes healthy again, so when used for persistence, it is generally less stable compared to stateful techniques (which would continue to use a selected server for as long as possible (or dictated by a TTL)).

Method

When xshard.reconfigure() is called explicitly (or implicitly at the end of any task containing reconfigurations like xshard.add_backend()), a consistent hashing circular data structure gets built from the last 32 bits of SHA256 hash values of <ident><n> (default ident being the backend name) for each backend and for a running number n from 1 to the replicas argument to xshard.reconfigure(). Hashing creates the seemingly random order for placement of backends on the consistent hashing ring. When xshard.add_backend() was called with a weight argument, replicas is scaled by that weight to add proportionally more copies of the that backend on the ring.

When xshard.backend() is called, a load balancing key gets generated unless provided. The smallest hash value in the circle is looked up that is larger than the key (searching clockwise and wrapping around as necessary). The backend for this hash value is the preferred backend for the given key.

If a healthy backend is requested, the search is continued linearly on the ring as long as backends found are unhealthy or all backends have been checked. The order of these "alternative backends" on the ring is likely to differ for different keys. Alternative backends can also be selected explicitly.

On consistent hashing see:


  • http://www8.org/w8-papers/2a-webserver/caching/paper2.html

  • http://www.audioscrobbler.net/development/ketama/
  • svn://svn.audioscrobbler.net/misc/ketama

  • http://en.wikipedia.org/wiki/Consistent_hashing

Error Reporting

Failing methods should report errors to VSL with the Error tag, so when configuring the shard director, you are advised to check:

varnishlog -I Error:^vmod_directors.shard

Additional information may be provided as Notices, which can be checked using

varnishlog -I Notice:^vmod_directors.shard

VOID xshard.set_warmup(REAL probability=0.0)

Set the default warmup probability. See the warmup parameter of xshard.backend(). If probability is 0.0 (default), warmup is disabled.

VOID xshard.set_rampup(DURATION duration=0)

Set the default rampup duration. See rampup parameter of xshard.backend(). If duration is 0 (default), rampup is disabled.

VOID xshard.associate(BLOB param=0)

Associate a default directors.shard_param() object or clear an association.

The value of the param argument must be a call to the xshard_param.use() method. No argument clears the association.

The association can be changed per backend request using the param argument of xshard.backend().

BOOL xshard.add_backend(BACKEND backend, [STRING ident], [DURATION rampup], [REAL weight])

BOOL xshard.add_backend(
      BACKEND backend,
      [STRING ident],
      [DURATION rampup],
      [REAL weight]
)

Add a backend backend to the director.

ident: Optionally specify an identification string for this backend, which will be hashed by xshard.reconfigure() to construct the consistent hashing ring. The identification string defaults to the backend name.

ident allows to add multiple instances of the same backend.

rampup: Optionally specify a specific rampup time for this backend. Otherwise, the per-director rampup time is used (see xshard.set_rampup()).

weight: Optionally specify a weight to scale the xshard.reconfigure() replicas parameter. weight is limited to at least 1. Values above 10 probably do not make much sense. The effect of weight is also capped such that the total number of replicas does not exceed UINT32_MAX.

BOOL xshard.remove_backend([BACKEND backend], [STRING ident])

BOOL xshard.remove_backend(
      [BACKEND backend=0],
      [STRING ident=0]
)

Remove backend(s) from the director. Either backend or ident must be specified. ident removes a specific instance. If backend is given without ident, all instances of this backend are removed.

BOOL xshard.clear()

Remove all backends from the director.

BACKEND xshard.backend(STRING key=NULL, [STRING param])

Pick a backend from the shard director.

key: The key to use for sharding. If NULL, a key is generated from the request.

param: An optional shard parameter object created by directors.shard_param().

Example:

# Pick a backend based on the client's IP address
set req.backend_hint = xshard.backend(client.ip);

# Pick a backend based on the client's IP address and a specific shard parameter
set req.backend_hint = xshard.backend(client.ip, my_shard_param);

BOOL xshard.clear()

Elimina todos los backends del director.

BOOL xshard.reconfigure(INT replicas=67)

Reconfigura explícitamente el anillo de hash consistente para que los cambios en los backends surtan efecto inmediatamente.

Si este método no se llama explícitamente, la reconfiguración ocurre al final de la tarea actual (después de vcl_init {} o cuando la tarea del cliente o backend actual finaliza).

BACKEND xshard.backend([ENUM by], [INT key], [BLOB key_blob], [INT alt], [REAL warmup], [BOOL rampup], [ENUM healthy], [BLOB param], [ENUM resolve])

BACKEND xshard.backend(
      [ENUM {HASH, URL, KEY, BLOB} by=HASH],
      [INT key],
      [BLOB key_blob],
      [INT alt=0],
      [REAL warmup=-1],
      [BOOL rampup=1],
      [ENUM {CHOSEN, IGNORE, ALL} healthy=CHOSEN],
      [BLOB param],
      [ENUM {NOW, LAZY} resolve]
)

Busca un backend en el anillo de hash consistente.

Esta documentación utiliza la noción de un orden de backends para una clave de partición particular. Este orden es determinista pero aparentemente aleatorio, determinado por el algoritmo de hash consistente, y es probable que difiera para diferentes claves, dependiendo del número de backends y el número de réplicas. En particular, el orden de backends al que se hace referencia aquí _no_ es el orden dado cuando se agregan los backends.

•
by cómo determinar la clave de partición
•
HASH:
  • cuando se llama en contexto de backend y en vcl_pipe {}: Usa el valor de hash de varnish como lo establece vcl_hash{}
  • cuando se llama en contexto de cliente que no sea vcl_pipe {}: hashea req.url
  • URL: hashea req.url / bereq.url
  • KEY: usa el argumento key
  • BLOB: usa el argumento key_blob
  • key clave de búsqueda con by=KEY

    el método xshard.key() puede ser útil para generar una clave de partición a partir de cadenas personalizadas.

  • key_blob clave de búsqueda con by=BLOB

    Actualmente, esto usa los primeros 4 bytes del blob dado en orden de bytes de red (endian big), rellenado con ceros a la izquierda para blobs de menos de 4 bytes.

  • alt selección de backend alternativa

    Selecciona el alt-ésimo backend alternativo para la key dada.

    Esto es particularmente útil para reintentos / reinicios debido a errores de backend: Al establecer alt=req.restarts o alt=bereq.retries con healthy=ALL, se selecciona otro servidor.

    Las funciones rampup y warmup solo están activas para alt==0

  • rampup inicio lento para servidores que acaban de estar sanos

    Si alt==0 y el backend elegido está en su período de rampup, con una probabilidad proporcional a la fracción de tiempo desde que la copia de seguridad se volvió sana hasta el período de rampup, devuelve el siguiente backend alternativo, a menos que este también esté en su período de rampup.

    El intervalo de rampup predeterminado se puede establecer por directorio usando el método xshard.set_rampup() o específicamente por backend con el método xshard.add_backend().

  • warmup selección probabilística de servidor alternativo

    valores posibles: -1, 0..1

    -1: usa la probabilidad de warmup de la definición del director

    Solo se usa para alt==0: Establece la proporción de solicitudes (0.0 a 1.0) que van al siguiente backend alternativo para calentarlo cuando el backend preferido está sano. No está activo si cualquiera de los backends preferidos o alternativos está en rampup.

    warmup=0.5 es una forma conveniente de distribuir la carga para cada clave sobre dos backends en condiciones normales de operación.

  • healthy
  • CHOSEN: Devuelve un backend sano si es posible.

    Para alt==0, devuelve el primer backend sano o ninguno.

    Para alt > 0, ignora el estado de salud de los backends saltados para la selección de backend alternativa, luego devuelve el siguiente backend sano. Si este no existe, devuelve el último backend sano de los saltados o ninguno.

  • IGNORE: Ignora completamente el estado de salud del backend

    Simplemente devuelve el primer o el alt-ésimo backend alternativo, ignorando el estado de salud, rampup y warmup.

  • ALL: Comprueba el estado de salud también para la selección de backend alternativa

    Para alt > 0, devuelve el alt-ésimo backend alternativo de todos los sanos, el último backend sano encontrado o ninguno.

•
resolve

predeterminado: LAZY en vcl_init{}, NOW en caso contrario

  • NOW: busca un backend y lo devuelve.

    No se puede usar en vcl_init{}.

  • LAZY: devuelve una instancia de este director para una resolución posterior de backend.

    El modo LAZY es necesario para referenciar instancias de director de partición, por ejemplo, como backends para otros directores (capa de directores).

    En vcl_init{} y en el lado del cliente, el modo LAZY no se puede usar con ningún otro argumento.

    En el lado del backend y en vcl_pipe {}, los parámetros de los argumentos o un conjunto de parámetros asociado afectan la instancia del director de partición para la solicitud de backend independientemente de dónde se refiera.

•
param

Usa o asocia un conjunto de parámetros. El valor del argumento param debe ser una llamada al método xshard_param.use().

predeterminado: como se establece mediante xshard.associate() o no establecido.

  • para resolve=NOW toma los valores predeterminados de los parámetros del conjunto de parámetros directors.shard_param()
  • para resolve=LAZY asocia el conjunto de parámetros directors.shard_param() para esta solicitud de backend

    Notas de implementación para el uso de conjuntos de parámetros con resolve=LAZY:

  • Un argumento param permanece asociado y cualquier cambio en el conjunto de parámetros asociado afecta la decisión de partición una vez que el director se resuelve en un backend real.
  • Si también se proporcionan otros argumentos de parámetros, tienen preferencia y se mantienen incluso si el conjunto de parámetros dado por el argumento param se cambia posteriormente dentro de la misma solicitud de backend.
  • Cada llamada a xshard.backend() anula cualquier llamada anterior.

VOID xshard.debug(INT)

intencionalmente indocumentado

new xshard_param = directors.shard_param()

Crea un conjunto de parámetros de partición.

Un conjunto de parámetros permite la reutilización de argumentos de xshard.backend() en muchas instancias de director de partición y simplifica casos de uso avanzados (por ejemplo, director de partición con parámetros personalizados en capas debajo de otros directores).

Los conjuntos de parámetros tienen dos ámbitos:

  • ámbito por-VCL definido en vcl_init{}
  • ámbito por solicitud de backend

El ámbito por-VCL define los valores predeterminados para el ámbito por backend. Cualquier cambio en un conjunto de parámetros en contexto de backend y en vcl_pipe {} solo afecta la solicitud de backend respectiva.

Los conjuntos de parámetros no se pueden usar en el contexto del cliente, excepto para vcl_pipe {}.

El siguiente ejemplo es un caso de uso típico: Un conjunto de parámetros se asocia con varios directores. La elección del director ocurre en el lado del cliente y los parámetros se cambian en el lado del backend para implementar reintentos en backends alternativos:

sub vcl_init {
  new shard_param = directors.shard_param();
  new dir_A = directors.shard();
  dir_A.add_backend(...);
  dir_A.reconfigure();
  dir_A.associate(shard_param.use()); # <-- !
  new dir_B = directors.shard();
  dir_B.add_backend(...);
  dir_B.reconfigure();
  dir_B.associate(shard_param.use()); # <-- !
}
sub vcl_recv {
  if (...) {
    set req.backend_hint = dir_A.backend(resolve=LAZY);
  } else {
    set req.backend_hint = dir_B.backend(resolve=LAZY);
  }
}
sub vcl_backend_fetch {
  # cambia el comportamiento de dir_A y dir_B
  shard_param.set(alt=bereq.retries, by=URL);
}

VOID xshard_param.clear()

Restablece el conjunto de parámetros a los valores predeterminados como se documenta para xshard.backend().

  • en vcl_init{}, restablece el valor predeterminado del conjunto de parámetros para este VCL
  • en contexto de backend y en vcl_pipe {}, restablece el conjunto de parámetros para esta solicitud de backend a los valores predeterminados del VCL

Restringido a: vcl_pipe, backend, housekeeping.

      [ENUM {HASH, URL, KEY, BLOB} by],
      [INT key],
      [BLOB key_blob],
      [INT alt],
      [REAL warmup],
      [BOOL rampup],
      [ENUM {CHOSEN, IGNORE, ALL} healthy]

Establece un parámetro de partición en el conjunto de parámetros. Ver xshard.backend() para una descripción de los parámetros.

Los parámetros se aplican al conjunto de parámetros del director actual y solo son efectivos para la solicitud de backend actual (o para VCL de inicialización si se llama en ese contexto).

Restringido a: vcl_pipe, backend, housekeeping.

Los siguientes ejemplos muestran el uso de set():

sub vcl_init {
  new sp = directors.shard_param();
  # Usar una clave personalizada y un backend alternativo para reintentos
  sp.set(key=12345, alt=req.restarts, by=KEY);
  # Usa esta configuración para un backend específico
  new dir = directors.shard();
  dir.add_backend(...);
  dir.associate(sp.use());
}
sub vcl_recv {
  # Usa el backend configurado anteriormente
  set req.backend_hint = dir.backend(resolve=LAZY);
}

Los siguientes ejemplos muestran cómo establecer parámetros de salud:

sub vcl_backend_fetch {
  # ignora la salud para la selección de backend alternativa
  # esta configuración es solo para esta solicitud de backend
  shard_param.set(healthy=IGNORE, alt=bereq.retries);
  # Lo mismo, pero también cambia la forma en que se calcula la clave
  shard_param.set(healthy=IGNORE, alt=bereq.retries, by=URL);
}

INT xshard_param.use()

Devuelve un valor que puede ser pasado a xshard.backend() como el argumento param. Vea xshard.backend() para más detalles.

new sp = directors.shard_param();
new dir = directors.shard();
dir.associate(sp.use());

# En vcl_backend_fetch:

•
name nombre del backend para añadir
  • replicas número de réplicas de este backend en el anillo de hash. Mayor número de réplicas significa que este backend es más probable que sea seleccionado.

  • param conjunto de parámetros para usar con este backend.

REAL xshard.get_backend(INT key)

Devuelve la probabilidad (0.0-1.0) de que el backend dado sea seleccionado para la clave dada.

Este método solo se puede usar en el contexto de backend.

VOID xshard.set_rampup(REAL interval)

Establece el intervalo de rampup predeterminado para todos los backends de este director.

El intervalo se especifica en segundos.

Si se establece en 0, la rampa de inicio se desactiva.

Por defecto, el intervalo de rampup es de 10 segundos.

Restringido a: vcl_init.

VOID xshard.set_warmup(REAL ratio)

Establece la proporción de warmup predeterminada para todos los backends de este director.

La proporción se especifica como un valor entre 0.0 y 1.0.

Si se establece en 0, el warmup se desactiva.

Por defecto, la proporción de warmup es 0.0.

Restringido a: vcl_init.

Asocia un conjunto de parámetros con este director. Ver xshard_param.use() para más detalles.

Restringido a: vcl_init.
