virtualenv es una herramienta para crear entornos aislados de Python.

VIRTUALENV VS VENV

Desde Python 3.3, una parte de él ha sido integrada en la biblioteca estándar bajo el módulo venv https://docs.python.org/3/library/venv.html. El módulo venv no ofrece todas las características de esta biblioteca, por nombrar solo algunas más prominentes:

  • es más lento (al no tener el método de semilla app-data),
  • no es tan extensible,
  • no puede crear entornos virtuales para versiones de Python instaladas arbitrariamente (y descubrirlas automáticamente),
  • no es actualizable a través de pip https://pip.pypa.io/en/stable/installing/,
  • no tiene una API programática tan rica (describir entornos virtuales sin crearlos).

CONCEPTO Y PROPÓSITO DE VIRTUALENV

El problema básico que se aborda es el de las dependencias y versiones, e indirectamente los permisos. Imagina que tienes una aplicación que necesita la versión 1 de LibFoo, pero otra aplicación requiere la versión 2. ¿Cómo puedes usar ambas bibliotecas? Si instalas todo en tu Python principal (por ejemplo, python3.8), es fácil terminar en una situación en la que dos paquetes tienen requisitos conflictivos.

O, más generalmente, ¿qué pasa si quieres instalar una aplicación y dejarla así? Si una aplicación funciona, cualquier cambio en sus bibliotecas o en las versiones de esas bibliotecas puede romper la aplicación. Además, ¿qué pasa si no puedes instalar paquetes en el directorio global de site-packages, debido a que no tienes permisos para cambiar el entorno de Python principal?

En todos estos casos, virtualenv puede ayudarte. Crea un entorno que tiene sus propios directorios de instalación, que no comparte bibliotecas con otros entornos de virtualenv (y opcionalmente tampoco accede a las bibliotecas instaladas globalmente).

Instalación

vía pipx

virtualenv https://pypi.org/project/virtualenv es una herramienta CLI que necesita un intérprete de Python para ejecutarse. Si ya tienes un intérprete de Python 3.7+, lo mejor es usar pipx https://pypi.org/project/pipx para instalar virtualenv en un entorno aislado. Esto tiene el beneficio adicional de que más tarde podrás actualizar virtualenv sin afectar otras partes del sistema.

pipx install virtualenv
virtualenv --help

vía pip

Alternativamente, puedes instalarlo dentro del propio intérprete global de Python (quizás como un paquete de usuario a través de la opción --user). Ten cuidado si estás usando una instalación de Python que es gestionada por tu sistema operativo u otro gestor de paquetes. pip podría no coordinarse con esas herramientas y podría dejar tu sistema en un estado inconsistente. Nota: si eliges este camino, debes asegurarte de que pip sea lo suficientemente nuevo según las subsecciones siguientes:

python -m pip install --user virtualenv
python -m virtualenv --help

wheel

Instalar virtualenv a través de un wheel (por defecto con pip) requiere un instalador que pueda entender la etiqueta python-requires (ver PEP-503 https://www.python.org/dev/peps/pep-0503/), con pip esto es la versión 9.0.0 (lanzada en noviembre de 2016). Además, en caso de que no lo estés instalando a través de PyPi necesitas usar un espejo que reenvíe correctamente la etiqueta python-requires (notablemente los espejos de OpenStack no hacen esto, o versiones antiguas de devpi https://github.com/devpi/devpi - añadida con la versión 4.7.0).

Compatibilidad de Python y SO

virtualenv funciona con las siguientes implementaciones de intérprete de Python:

  • CPython https://www.python.org/: 3.13 >= python_version >= 3.7
  • PyPy https://pypy.org/: 3.10 >= python_version >= 3.7

Esto significa que virtualenv funciona en la última versión de parche de cada una de estas versiones menores. Las versiones de parche anteriores se soportan en la medida de lo posible.

CPython se distribuye en varias formas, y cada SO lo empaqueta de nuevo, a menudo aplicando alguna personalización en el camino. Por lo tanto, no podemos decir universalmente que soportamos todas las plataformas, sino que especificamos algunas contra las que probamos. En caso de las no especificadas aquí, el soporte es desconocido, aunque probablemente funcionarán. Si encuentras algún caso, por favor abre una solicitud de características en nuestro rastreador de incidencias.

Introducción

Virtualenv tiene un comando básico:

virtualenv venv

Nota:

Al crear un entorno virtual, se recomienda utilizar una versión específica de Python, por ejemplo, invocando virtualenv con python3.10 -m virtualenv venv. Si usas un comando genérico como python3 -m virtualenv venv, el entorno creado se vinculará a /usr/bin/python3. Esto puede ser problemático porque cuando se instala una nueva versión de Python en el sistema, el enlace simbólico /usr/bin/python3 probablemente se actualizará para apuntar a la nueva versión. Esto hará que el entorno virtual utilice inadvertidamente la nueva versión de Python, lo que a menudo no es el comportamiento deseado. Usar una versión específica asegura que el entorno virtual esté vinculado a esa versión exacta, proporcionando estabilidad y previsibilidad.

Esto creará un entorno virtual de Python de la misma versión que virtualenv, instalado en el subdirectorio venv. La herramienta de línea de comandos tiene bastantes indicadores que modifican su comportamiento; para una lista completa, consulta los indicadores CLI <#cli-flags>.

La herramienta funciona en dos fases:

  • Fase 1 descubre un intérprete de Python para crear un entorno virtual a partir de él (por defecto, es el mismo Python desde el que se está ejecutando virtualenv, sin embargo, podemos cambiar esto a través de la opción p <#p>).
  • Fase 2 crea un entorno virtual en el destino especificado (dest <#dest>), que puede dividirse en cuatro subpasos adicionales:
  • crea un Python que coincida con el intérprete de Python de destino de la fase 1,
  • instala (arranca) paquetes semilla (uno o más de pip https://pypi.org/project/pip, setuptools https://pypi.org/project/setuptools, wheel https://pypi.org/project/wheel) en el entorno virtual creado,
  • instala scripts de activación en el directorio binario del entorno virtual (estos permitirán a los usuarios finales *activar* el entorno virtual desde varios shells).
  • crea archivos que marcan el entorno virtual para ser ignorado por los sistemas de control de versiones (actualmente solo admitimos Git, ya que Mercurial, Bazaar o SVN no admiten archivos de ignore en subdirectorios). Este paso se puede omitir con la opción no-vcs-ignore <#no-vcs-ignore>.

El Python en tu nuevo virtualenv está efectivamente aislado del Python que se utilizó para crearlo.

Descubrimiento de Python

Lo primero que necesitamos para poder crear un entorno virtual es un intérprete de Python. Esto describirá a la herramienta qué tipo de entorno virtual te gustaría crear, piénsalo como: versión, arquitectura, implementación.

virtualenv, al ser una aplicación de Python, siempre tiene al menos una disponible, la que virtualenv está utilizando, y como tal, este es el elemento descubierto por defecto. Esto significa que si instalas virtualenv en Python 3.8, virtualenv creará por defecto entornos virtuales que también serán de la versión 3.8.

Los entornos virtuales de Python creados generalmente no son autocontenidos. Una instalación completa de Python suele componerse de miles de archivos, por lo que no es eficiente instalar todo Python de nuevo en una nueva carpeta. En su lugar, los entornos virtuales son meras carcasas, que contienen poco en sí mismos y toman prestado la mayor parte del Python del sistema (esto es lo que instalaste, cuando instalaste Python mismo). Esto significa que si actualizas tu Python del sistema, tus entornos virtuales *podrían* romperse, así que ten cuidado. La ventaja de esto, refiriéndonos al Python del sistema, es que la creación de entornos virtuales puede ser rápida.

Activadores

Estos son scripts de activación que modificarán la configuración de su shell para garantizar que los comandos dentro del entorno virtual de Python tengan prioridad sobre sus rutas del sistema. Por ejemplo, si invocar pip desde su shell devolvía el pip del Python del sistema antes de la activación, una vez que realice la activación, esto debería referirse al pip del entorno virtual. Tenga en cuenta que todo lo que hacemos es cambiar la prioridad; por lo tanto, si la carpeta bin/Scripts de su entorno virtual no contiene algún ejecutable, este seguirá resolviéndose al mismo ejecutable que se habría resuelto antes de la activación.

Para ver una lista de los shells para los que proporcionamos activadores, consulte activators <#activators>. La ubicación de estos está justo al lado de los ejecutables de Python: generalmente la carpeta Scripts en Windows, bin en POSIX. Se llaman activate, más una extensión específica para cada activador, sin extensión para Bash. Puede invocarlos, generalmente haciendo un source de ellos. El comando source puede variar según el shell; por ejemplo, en Bash es source (o .):

source venv/bin/activate

El script activate antepone la carpeta binaria del entorno virtual a la variable de entorno PATH. Es realmente solo una conveniencia para hacerlo, ya que usted mismo podría hacer lo mismo.

Tenga en cuenta que no tiene que activar un entorno virtual para usarlo. En su lugar, puede usar las rutas completas a sus ejecutables, en lugar de depender de su shell para resolverlos a su entorno virtual.

Los scripts activadores también modifican el prompt de su shell para indicar qué entorno está activo actualmente, anteponiendo el nombre del entorno (o el nombre especificado por --prompt al crear inicialmente el entorno) entre corchetes, como (venv). Puede deshabilitar este comportamiento estableciendo la variable de entorno VIRTUAL_ENV_DISABLE_PROMPT a cualquier valor. También puede obtener el nombre del entorno a través de la variable de entorno VIRTUAL_ENV_PROMPT si desea personalizar su prompt, por ejemplo.

Los scripts también proporcionan un comando deactivate que le permitirá deshacer la operación:

deactivate

Nota:

Si usa Powershell, el script activate está sujeto a las políticas de ejecución http://technet.microsoft.com/en-us/library/dd347641.aspx en el sistema. Por defecto, Windows 7 y posteriores, la política de ejecución del sistema se establece en Restricted, lo que significa que no se permite la ejecución de scripts como el script activate.

Sin embargo, eso no puede impedirnos cambiarlo ligeramente para permitir su ejecución. Puede relajar la política de ejecución del sistema para permitir la ejecución de scripts locales sin verificar la firma del código utilizando lo siguiente:

Set-ExecutionPolicy RemoteSigned

Dado que el script activate.ps1 se genera localmente para cada virtualenv, no se considera un script remoto y, por lo tanto, se puede ejecutar.

Una explicación más detallada de esto se puede encontrar en la publicación del blog de Allison Kaptur de 2013: There's no magic: virtualenv edition https://www.recurse.com/blog/14-there-is-no-magic-virtualenv-edition explica cómo virtualenv utiliza bash y Python, y PATH y PYTHONHOME para aislar las rutas de los entornos virtuales.

Opciones de descubrimiento

Entendiendo el descubrimiento de intérpretes: --python vs. --try-first-with

Puedes controlar qué intérprete de Python selecciona virtualenv utilizando las banderas --python y --try-first-with. Para evitar confusiones, es mejor pensar en ellas como la "regla" y la "pista".

``--python <especificación>``: La Regla

Esta bandera establece los requisitos obligatorios para el intérprete. La <especificación> puede ser:

  • Una cadena de versión (por ejemplo, python3.8, pypy3). virtualenv buscará cualquier intérprete que coincida con esta versión.
  • Una ruta absoluta (por ejemplo, /usr/bin/python3.8). Este es un requisito *estricto*. Solo se utilizará el intérprete en esta ruta exacta. Si no existe o no es un intérprete válido, la creación fallará.

``--try-first-with <ruta>``: La Pista

Esta bandera proporciona una ruta a un ejecutable de Python para verificar *antes* de que virtualenv realice su búsqueda estándar. Esto puede acelerar el descubrimiento o ayudar a seleccionar un intérprete específico cuando existen múltiples versiones en tu sistema.

Cómo funcionan juntas

virtualenv solo usará un intérprete de --try-first-with si satisface la regla de la bandera --python. La regla --python siempre tiene prioridad.

Ejemplos:

1.
La pista no coincide con la regla:
virtualenv --python python3.8 --try-first-with /usr/bin/python3.10 mi-entorno
•
Resultado: virtualenv inspecciona primero /usr/bin/python3.10. Ve que no coincide con la regla python3.8 y la rechaza. Luego procede con su búsqueda normal para encontrar un intérprete python3.8 en otro lugar.
2.
La pista no coincide con una regla de ruta estricta:
virtualenv --python /usr/bin/python3.8 --try-first-with /usr/bin/python3.10 mi-entorno
•
Resultado: La regla es estrictamente /usr/bin/python3.8. virtualenv comprueba la pista /usr/bin/python3.10, ve que la ruta no coincide y la rechaza. Luego pasa a probar /usr/bin/python3.8 y crea el entorno con éxito.

Este enfoque garantiza que el comportamiento sea predecible y que --python siga siendo la fuente definitiva de verdad para la intención del usuario.

Valores predeterminados

Archivo de configuración

A menos que se establezca VIRTUALENV_CONFIG_FILE, virtualenv busca un archivo de configuración estándar virtualenv.ini. La ubicación exacta depende del sistema operativo que esté utilizando, según lo determinado por la definición de configuración de aplicaciones de platformdirs https://pypi.org/project/platformdirs. Se puede anular estableciendo la variable de entorno VIRTUALENV_CONFIG_FILE. La ubicación del archivo de configuración se imprime al final de la salida cuando se pasa --help.

Las claves de los ajustes se derivan de la opción de la línea de comandos (eliminando los caracteres - iniciales y reemplazando - por _). Cuando hay varias banderas disponibles, la primera que se encuentra es la que vale (el orden es como aparece en --help).

Por ejemplo, --python se especificaría como:

[virtualenv]
python = /opt/python-3.8/bin/python

Las opciones que aceptan varios valores, como extra-search-dir, se pueden especificar como:

[virtualenv]
extra_search_dir =
    /path/to/dists
    /path/to/other/dists

Variables de entorno

Los valores predeterminados también se pueden especificar a través de variables de entorno. Las claves de los ajustes se derivan de la opción de la línea de comandos (eliminando los caracteres - iniciales y reemplazando - por _, finalmente, capitalizando el nombre). Cuando hay varias banderas disponibles, la primera que se encuentra es la que vale (el orden es como aparece en --help).

Por ejemplo, para utilizar un binario de Python personalizado, en lugar del que se ejecuta virtualenv, puede establecer la variable de entorno VIRTUALENV_PYTHON así:

env VIRTUALENV_PYTHON=/opt/python-3.8/bin/python virtualenv

Donde la opción acepta varios valores, por ejemplo para python o extra-search-dir, los valores pueden separarse mediante saltos de línea literales o comas. Los saltos de línea y las comas no se pueden mezclar y si ambos están presentes solo se utiliza el salto de línea para separar los valores. Ejemplos para valores múltiples:

env VIRTUALENV_PYTHON=/opt/python-3.8/bin/python,python3.8 virtualenv
env VIRTUALENV_EXTRA_SEARCH_DIR=/path/to/dists\n/path/to/other/dists virtualenv

La invocación equivalente basada en banderas CLI para los ejemplos anteriores sería:

virtualenv --python=/opt/python-3.8/bin/python --python=python3.8
virtualenv --extra-search-dir=/path/to/dists --extra-search-dir=/path/to/other/dists

Extender funcionalidad

virtualenv permite extender la funcionalidad incorporada a través de un sistema de complementos. Para añadir un complemento necesita:

  • escribir un archivo de python que contenga el código del complemento que siga nuestra interfaz esperada,
  • empaquetarlo como una biblioteca de python,
  • instalarlo junto con el entorno virtual.

Descubrimiento de Python

El mecanismo de descubrimiento de Python es un componente que debe responder a la siguiente pregunta: basándose en algún tipo de entrada del usuario, dame un intérprete de Python en la máquina que coincida. El intérprete incorporado intenta descubrir un intérprete de Python instalado (basado en PEP-515 y descubrimiento de PATH) en la máquina del usuario, donde la entrada del usuario es una especificación de python. Un mecanismo de descubrimiento alternativo, por ejemplo, sería utilizar el popular proyecto pyenv https://github.com/pyenv/pyenv para descubrir, y si no está presente, instalar el intérprete de Python solicitado. Desarrollo

Primeros pasos

virtualenv es un proyecto de código abierto mantenido por voluntarios y damos la bienvenida a contribuciones de todo tipo. Las secciones siguientes te ayudarán a empezar con el desarrollo, las pruebas y la documentación. Nos complace que estés interesado en trabajar en virtualenv. Este documento está diseñado para que te configures para trabajar en virtualenv y para que sirva como guía y referencia de la configuración de desarrollo. Si encuentras algún problema durante este proceso, por favor abre un ticket https://github.com/pypa/virtualenv/issues/new?title=Trouble+with+development+environment en el rastreador de incidencias.

Configuración

virtualenv es una aplicación de línea de comandos escrita en Python. Para trabajar en ella, necesitarás:

•
Código fuente: disponible en GitHub <https://github.com/pypa/virtualenv>. Puedes usar git para clonar el
repositorio:
git clone https://github.com/pypa/virtualenv
cd virtualenv
  • Intérprete de Python: Recomendamos usar CPython. Puedes usar esta guía https://realpython.com/installing-python/ para configurarlo.
  • tox https://pypi.org/project/tox: para obtener automáticamente las dependencias de desarrollo del proyecto y ejecutar la suite de pruebas. Recomendamos instalarlo usando pipx https://pipxproject.github.io/pipx/.

Ejecución desde el árbol de fuentes

La forma más fácil de hacerlo es generar el entorno de tox de desarrollo y luego invocar virtualenv desde la carpeta .tox/dev.

tox -e dev
.tox/dev/bin/virtualenv  # en Linux
.tox/dev/Scripts/virtualenv  # en Windows

Ejecución de pruebas

Las pruebas de virtualenv están escritas usando el framework de pruebas pytest https://pypi.org/project/pytest. tox https://pypi.org/project/tox se utiliza para automatizar la configuración y ejecución de las pruebas de virtualenv.

Para ejecutar las pruebas localmente, ejecuta:

tox -e py

Esto ejecutará la suite de pruebas para la misma versión de Python en la que está instalado tox. Alternativamente, puedes especificar una versión específica de Python usando el formato pyNN, como: py38, pypy3, etc.

tox ha sido configurado para reenviar cualquier argumento adicional que reciba a pytest. Esto permite el uso de la rica CLI de pytest https://docs.pytest.org/en/latest/usage.html#specifying-tests-selecting-tests. Como ejemplo, puedes seleccionar pruebas usando las diversas formas que pytest proporciona:

# Usando marcadores
tox -e py -- -m "not slow"
# Usando palabras clave
tox -e py -- -k "test_extra"

Algunas pruebas requieren dependencias adicionales para ejecutarse, como los diversos activadores de shell (bash, fish, powershell, etc.). Estas pruebas se omitirán automáticamente si no están presentes; ten en cuenta, sin embargo, que en CI se ejecutan todas las pruebas; por lo tanto, incluso si todas las pruebas tienen éxito localmente para ti, aún pueden fallar en CI.

Ejecución de linters

virtualenv utiliza pre-commit https://pypi.org/project/pre-commit para gestionar el linting de la base de código. pre-commit realiza varias comprobaciones en todos los archivos de virtualenv y utiliza herramientas que ayudan a seguir un estilo de código coherente dentro de la base de código. Para usar linters localmente, ejecuta:

tox -e fix

Nota:

Evita usar comentarios # noqa para suprimir advertencias del linter; siempre que sea posible, se deben solucionar las advertencias en su lugar. Los comentarios # noqa están reservados para casos raros en los que el estilo recomendado causa graves problemas de legibilidad.

Construcción de documentación

La documentación de virtualenv se construye usando Sphinx https://pypi.org/project/Sphinx. La documentación está escrita en reStructuredText. Para construirla localmente, ejecuta:

tox -e docs

La documentación construida se encontrará en la carpeta .tox/docs_out y puede verse abriendo index.html dentro de esa carpeta.

Lanzamiento

El calendario de lanzamientos de virtualenv está ligado a pip y setuptools. Incluimos la última versión de estas bibliotecas, por lo que cada vez que hay una nueva versión de cualquiera de ellas, habrá un nuevo lanzamiento de virtualenv poco después (normalmente esperamos solo unos pocos días para evitar incorporar lanzamientos rotos).

Contribución

Envío de pull requests

Envía pull requests contra la rama main, proporcionando una buena descripción de lo que estás haciendo y por qué. Debes tener permiso legal para distribuir cualquier código que contribuyas a virtualenv y debe estar disponible bajo la Licencia MIT. Cualquier pull request debe considerar y funcionar en todas estas plataformas.

Los Pull Requests deben ser pequeños para facilitar la revisión. Mantenlos autónomos y de alcance limitado. Los estudios han demostrado https://www.kessler.de/.

Todas las solicitudes de extracción y fusiones a la rama 'main' se prueban utilizando Azure Pipelines https://azure.microsoft.com/en-gb/services/devops/pipelines/ (configurado por el archivo azure-pipelines.yml en la raíz del repositorio). Puede encontrar el estado y los resultados de las ejecuciones de CI para su PR en la interfaz web de GitHub para la solicitud de extracción. También puede encontrar enlaces a las páginas de los servicios de CI para las compilaciones específicas en forma de enlaces "Detalles", en caso de que la ejecución de CI falle y desee ver la salida.

Para activar la ejecución de CI nuevamente para una solicitud de extracción, puede cerrar y abrir la solicitud de extracción o enviar otro cambio a la solicitud de extracción. Si es necesario, los mantenedores del proyecto pueden activar manualmente un reinicio de un trabajo/compilación.

Entradas de NOTICIAS

El archivo changelog.rst se gestiona utilizando towncrier https://pypi.org/project/towncrier y todos los cambios no triviales deben ir acompañados de una entrada de noticias. Para agregar una entrada al archivo de noticias, primero debe haber creado un problema que describa el cambio que desea realizar. Una solicitud de extracción en sí misma *puede* funcionar como tal, pero se prefiere tener un problema dedicado (por ejemplo, en caso de que el PR sea rechazado debido a razones de calidad del código).

Una vez que tenga un problema o PR, toma el número y crea un archivo dentro del directorio docs/changelog con el nombre de ese número de problema y una extensión de:

  • feature.rst,
  • bugfix.rst,
  • doc.rst,
  • removal.rst,
  • misc.rst.

Por lo tanto, si su número de problema o PR es 1234 y este cambio soluciona un error, crearía un archivo docs/changelog/1234.bugfix.rst. Los PR pueden abarcar varias categorías creando varios archivos (por ejemplo, si agregó una función y desaprobó/eliminó la función anterior al mismo tiempo, crearía docs/changelog/1234.bugfix.rst y docs/changelog/1234.remove.rst). Del mismo modo, si un PR toca varios problemas/PR, puede crear un archivo para cada uno de ellos con el mismo contenido y towncrier https://pypi.org/project/towncrier los eliminará duplicados.

Contenido de una entrada de NOTICIAS

El contenido de este archivo es texto formateado en reStructuredText que se utilizará como contenido de la entrada del archivo de noticias. No es necesario que haga referencia a los números de problema o PR aquí, ya que towncrier agregará automáticamente una referencia a todos los problemas afectados al renderizar el archivo de noticias.

Para mantener un estilo coherente en el archivo changelog.rst, se prefiere que la entrada de noticias sea concisa, en mayúsculas y minúsculas, más corta que 120 caracteres y en tono imperativo: una entrada debe completar la oración Este cambio.... En casos raros, donde una línea no es suficiente, use una línea de resumen en tono imperativo seguida de una línea en blanco que la separe de la descripción de la función/cambio en uno o más párrafos, cada uno envuelto a 120 caracteres. Recuerde que una entrada de noticias está destinada a los usuarios finales y solo debe contener detalles relevantes para un usuario final.

Elegir el tipo de entrada de NOTICIAS

Un cambio trivial es cualquier cosa que no justifique una entrada en el archivo de noticias. Algunos ejemplos son: refactorizaciones de código que no cambian nada en lo que respecta al público, correcciones de errores tipográficos, modificación de espacios en blanco, etc. Para marcar un PR como trivial, un contribuyente simplemente necesita agregar un archivo vacío con un nombre aleatorio en el directorio news/ con la extensión .trivial.

Convertirse en mantenedor

Si desea convertirse en un mantenedor oficial, comience por ayudar. Como primer paso, le damos la bienvenida a clasificar problemas en el rastreador de problemas de virtualenv. Los mantenedores de virtualenv brindan capacidades de clasificación a los contribuyentes una vez que han estado por aquí por un tiempo y han contribuido positivamente al proyecto. Esto es opcional y muy recomendado para convertirse en un mantenedor de virtualenv. Más tarde, cuando crea que está listo, póngase en contacto con uno de los mantenedores y ellos iniciarán una votación entre los mantenedores existentes.

Nota:

Al convertirse en mantenedor, se le debe dar acceso a varias herramientas relacionadas con virtualenv en múltiples plataformas. Estos se anotan aquí para referencia futura por parte de los mantenedores:
  • Acceso de inserción a GitHub
  • Acceso de publicación en PyPI
  • Capacidades de administración de CI
  • Capacidades de administración de ReadTheDocs
