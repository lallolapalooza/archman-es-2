NOMBRE

vtep-ctl - utilidad para consultar y configurar una base de datos VTEP

SINOPSIS

vtep-ctl [opciones] -- [opciones] comando [argumentos] [-- [opciones] comando [argumentos]]...

DESCRIPCIÓN

vtep-ctl configura una base de datos VTEP. Consulte vtep(5) para obtener documentación completa sobre el esquema de la base de datos.

vtep-ctl se conecta a un proceso ovsdb-server que mantiene una base de datos de configuración VTEP. Utilizando esta conexión, consulta y posiblemente aplica cambios a la base de datos, dependiendo de los comandos proporcionados.

vtep-ctl puede ejecutar cualquier número de comandos en una única ejecución, implementados como una única transacción atómica contra la base de datos.

La línea de comandos de vtep-ctl comienza con opciones globales (consulte OPCIONES a continuación para obtener detalles). Las opciones globales van seguidas de uno o más comandos. Cada comando debe comenzar con -- por sí solo como argumento de línea de comandos, para separarlo de los comandos siguientes. (El -- antes del primer comando es opcional). El comando en sí comienza con opciones específicas del comando, si las hay, seguido del nombre del comando y cualquier argumento. Consulte EJEMPLOS a continuación para ver ejemplos de sintaxis.

OPCIONES

Las siguientes opciones afectan el comportamiento de vtep-ctl en su conjunto. Algunos comandos individuales también aceptan sus propias opciones, que se proporcionan justo antes del nombre del comando. Si el primer comando en la línea de comandos tiene opciones, esas opciones deben separarse de las opciones globales mediante --.

--db=servidor
Establece servidor como el servidor de base de datos al que se conecta vtep-ctl para consultar o modificar la configuración. servidor puede ser un método de conexión activo o pasivo de OVSDB, como se describe en ovsdb(7). El valor predeterminado es unix:/run/openvswitch/db.sock.
--no-syslog
Por defecto, vtep-ctl registra sus argumentos y los detalles de cualquier cambio que realice en el registro del sistema. Esta opción deshabilita este registro.
Esta opción es equivalente a --verbose=vtep_ctl:syslog:warn.
--oneline
Modifica el formato de salida de modo que la salida de cada comando se imprima en una sola línea. Los caracteres de nueva línea que de otro modo separarían las líneas se imprimen como \n, y cualquier instancia de \ que de otro modo aparecería en la salida se duplica. Imprime una línea en blanco por cada comando que no tenga salida. Esta opción no afecta el formato de la salida de los comandos list o find; consulte Opciones de formato de tabla a continuación.
--dry-run
Evita que vtep-ctl modifique realmente la base de datos.
-t seg

--timeout=seg
Por defecto, o con un valor de seg de 0, vtep-ctl espera eternamente una respuesta de la base de datos. Esta opción limita el tiempo de ejecución a aproximadamente seg segundos. Si el tiempo de espera expira, vtep-ctl saldrá con una señal SIGALRM. (Un tiempo de espera normalmente ocurriría solo si la base de datos no se puede contactar, o si el sistema está sobrecargado).

Opciones de formato de tabla

Estas opciones controlan el formato de la salida de los comandos list y find.

-f formato

--format=formato
Establece el tipo de formato de tabla. Los siguientes tipos de formato están disponibles:
table
Tablas de texto 2D con columnas alineadas.
list (predeterminado)
Una lista con una columna por línea y filas separadas por una línea en blanco.
html
Tablas HTML.
csv
Valores separados por comas según se define en RFC 4180.
json
Formato JSON según se define en RFC 4627. La salida es una secuencia de objetos JSON, cada uno de los cuales corresponde a una tabla. Cada objeto JSON tiene los siguientes miembros con los valores indicados:
caption
El título de la tabla. Este miembro se omite si la tabla no tiene título.
headings
Un arreglo con un elemento por columna de tabla. Cada elemento del arreglo es una cadena que da el encabezado de la columna correspondiente.
data
Un arreglo con un elemento por fila de tabla. Cada elemento es también un arreglo con un elemento por columna de tabla. Los elementos de este arreglo de segundo nivel son las celdas que constituyen la tabla. Las celdas que representan datos u otros tipos de datos de OVSDB se expresan en el formato descrito en la especificación OVSDB; otras celdas simplemente se expresan como cadenas de texto.
-d formato

--data=formato
Establece el formato para las celdas dentro de las tablas de salida, a menos que el formato de tabla se establezca en json, en cuyo caso el formato json siempre se utiliza al formatear celdas. Los siguientes tipos de formato están disponibles:
string (predeterminado)
El formato simple descrito en la sección Valores de la base de datos de ovs-vsctl(8).
bare
El formato simple con la puntuación eliminada: [] y {} se omiten alrededor de conjuntos, mapas y columnas vacías, los elementos dentro de conjuntos y mapas se separan por espacios y las cadenas nunca se citan. Este formato puede ser más fácil de analizar para scripts.
json
El formato JSON RFC 4627 como se describe anteriormente.
--no-headings
Esta opción suprime la fila de encabezado que de otro modo aparece en la primera fila de la salida de la tabla.
--pretty
Por defecto, el JSON en la salida se imprime de la forma más compacta posible. Esta opción hace que el JSON en la salida se imprima de una manera más legible. Los miembros de los objetos y los elementos de los arreglos se imprimen uno por línea, con sangría.
Esta opción no afecta al JSON en las tablas, que siempre se imprime de forma compacta.
--bare
Equivalente a --format=list --data=bare --no-headings.
--max-column-width=n
Solo para salida de tabla, limita el ancho de cualquier columna en la salida a n columnas. Los datos de celda más largos se truncan para que quepan, según sea necesario. Las columnas siempre son lo suficientemente anchas para mostrar los nombres de las columnas, si se imprime la fila de encabezado.

OPTIONS

-c certificate.pem

--certificate=certificate.pem
Specifies the certificate file in PEM format that vtep-ctl should use to authenticate itself to SSL/TLS peers. The certificate must be signed by the certificate authority (CA) that the peer in SSL/TLS connections will use to verify it.
-C cacert.pem

--ca-cert=cacert.pem
Especifica un archivo PEM que contiene el certificado de la CA que vtep-ctl debe usar para verificar los certificados presentados por los pares SSL/TLS. (Este puede ser el mismo certificado que los pares SSL/TLS usan para verificar el certificado especificado en -c o --certificate, o puede ser uno diferente, dependiendo del diseño de PKI en uso).
-C none

--ca-cert=none
Deshabilita la verificación de los certificados presentados por los pares SSL/TLS. Esto introduce un riesgo de seguridad, ya que significa que los certificados no pueden verificarse como los de hosts conocidos y confiables.
--bootstrap-ca-cert=cacert.pem
Cuando cacert.pem existe, esta opción tiene el mismo efecto que -C o --ca-cert. Si no existe, entonces vtep-ctl intentará obtener el certificado de la CA del par SSL/TLS en su primera conexión SSL/TLS y lo guardará en el archivo PEM especificado. Si tiene éxito, cerrará inmediatamente la conexión y se volverá a conectar, y a partir de entonces todas las conexiones SSL/TLS deberán ser autenticadas por un certificado firmado por la CA obtenida de esa manera.
Esta opción expone la conexión SSL/TLS a un ataque de intermediario al obtener el certificado de CA inicial, pero puede ser útil para el arranque.
Esta opción solo es útil si el par SSL/TLS envía su certificado de CA como parte de la cadena de certificados SSL/TLS. Los protocolos SSL/TLS no requieren que el servidor envíe el certificado de CA.
Esta opción es mutuamente excluyente con -C y --ca-cert.
--peer-ca-cert=peer-cacert.pem
Especifica un archivo PEM que contiene uno o más certificados adicionales para enviar a los pares SSL/TLS. peer-cacert.pem debe ser el certificado de la CA utilizado para firmar el propio certificado de vtep-ctl, es decir, el certificado especificado en -c o --certificate. Si el certificado de vtep-ctl se firma a sí mismo, entonces --certificate y --peer-ca-cert deben especificar el mismo archivo.
Esta opción no es útil en operación normal, ya que el par SSL/TLS ya debe tener el certificado de la CA para que el par tenga alguna confianza en la identidad de vtep-ctl. Sin embargo, esto ofrece una forma para que una nueva instalación arranque el certificado de la CA en su primera conexión SSL/TLS.
-v[spec]

--verbose=[spec]
Establece los niveles de registro. Sin ningún spec, establece el nivel de registro para cada módulo y destino a dbg. De lo contrario, spec es una lista de palabras separadas por espacios, comas o dos puntos, hasta una de cada categoría a continuación:
  • Un nombre de módulo válido, tal como se muestra en el comando vlog/list en ovs-appctl(8), limita el cambio de nivel de registro al módulo especificado.
  • syslog, console o file, para limitar el cambio de nivel de registro solo al registro del sistema, a la consola o a un archivo, respectivamente. (Si se especifica --detach, vtep-ctl cierra sus descriptores de archivo estándar, por lo que el registro en la consola no tendrá ningún efecto).
En la plataforma Windows, syslog se acepta como una palabra y solo es útil junto con la opción --syslog-target (la palabra no tiene efecto de lo contrario).
•
off, emer, err, warn, info o dbg, para controlar el nivel de registro. Se registrarán los mensajes de la gravedad dada o superior, y se filtrarán los mensajes de menor gravedad. off filtra todos los mensajes. Consulte ovs-appctl(8) para obtener una definición de cada nivel de registro.
Las mayúsculas no distinguen entre sí dentro de spec.
Independientemente de los niveles de registro establecidos para file, el registro en un archivo no se llevará a cabo a menos que también se especifique --log-file (ver más abajo).
Por compatibilidad con versiones anteriores de OVS, any se acepta como una palabra pero no tiene efecto.
-v

--verbose
Establece el nivel de verbosidad de registro máximo, equivalente a --verbose=dbg.
-vPATTERN:destination:pattern

--verbose=PATTERN:destination:pattern
Establece el patrón de registro para destination a pattern. Consulte ovs-appctl(8) para una descripción de la sintaxis válida para pattern.
-vFACILITY:facility

--verbose=FACILITY:facility
Establece la instalación RFC5424 del mensaje de registro. facility puede ser uno de kern, user, mail, daemon, auth, syslog, lpr, news, uucp, clock, ftp, ntp, audit, alert, clock2, local0, local1, local2, local3, local4, local5, local6 o local7. Si esta opción no se especifica, se usa daemon como predeterminado para el syslog del sistema local y se usa local0 al enviar un mensaje al destino proporcionado a través de la opción --syslog-target.
--log-file[=file]
Habilita el registro en un archivo. Si se especifica file, se usa como el nombre exacto para el archivo de registro. El nombre de archivo de registro predeterminado que se usa si se omite file es /var/log/openvswitch/vtep-ctl.log.
--syslog-target=host:port
Envía mensajes de syslog al port UDP en host, además del syslog del sistema. El host debe ser una dirección IP numérica, no un nombre de host.
--syslog-method=method
Especifica method cómo se deben enviar los mensajes de syslog al demonio de syslog. Se admiten las siguientes formas:
  • libc, usa la función syslog() de libc. La desventaja de usar esta opción es que libc agrega un prefijo fijo a cada mensaje antes de que se envíe al demonio de syslog a través del socket de dominio UNIX /dev/log.
  • unix:file, usa directamente un socket de dominio UNIX. Es posible especificar un formato de mensaje arbitrario con esta opción. Sin embargo, rsyslogd 8.9 y versiones anteriores utilizan de todos modos una función de análisis codificada que limita el uso del socket de dominio UNIX. Si desea utilizar un formato de mensaje arbitrario con versiones anteriores de rsyslogd, utilice en su lugar un socket UDP a la dirección IP de localhost.
  • udp:ip:port, usa un socket UDP. Con este método es posible utilizar un formato de mensaje arbitrario también con versiones anteriores de rsyslogd. Al enviar mensajes de syslog a través de un socket UDP, se deben tener en cuenta precauciones adicionales, por ejemplo, el demonio de syslog debe configurarse para escuchar en el puerto UDP especificado, las reglas de iptables accidentales podrían interferir con el tráfico de syslog local y existen algunas consideraciones de seguridad que se aplican a los sockets UDP, pero no a los sockets de dominio UNIX.
  • null, descarta todos los mensajes registrados en syslog.
El valor predeterminado se toma de la variable de entorno OVS_SYSLOG_METHOD; si no está establecida, el valor predeterminado es libc.
-h

--help
Imprime un breve mensaje de ayuda en la consola.
-V

--version
Imprime la información de la versión en la consola.

COMANDOS

Los comandos implementados por vtep-ctl se describen en las secciones siguientes.

Comandos de Switches Físicos

Estos comandos examinan y manipulan switches físicos.

[--may-exist] add-ps pswitch
Crea un nuevo switch físico llamado pswitch. Inicialmente el switch no tendrá puertos.
Sin --may-exist, intentar crear un switch que existe es un error. Con --may-exist, este comando no hace nada si pswitch ya existe.
[--if-exists] del-ps pswitch
Elimina pswitch y todos sus puertos.
Sin --if-exists, intentar eliminar un switch que no existe es un error. Con --if-exists, intentar eliminar un switch que no existe no tiene ningún efecto.
list-ps
Lista todos los switches físicos existentes en la salida estándar, uno por línea.
ps-exists pswitch
Verifica si pswitch existe. Si es así, vtep-ctl sale exitosamente con código de salida 0. Si no, vtep-ctl sale sin éxito con código de salida 2.

Estos comandos consultan y modifican el contenido de las tablas de ovsdb. Son una ligera abstracción de la interfaz de ovsdb y, como tales, operan a un nivel inferior que otros comandos de vtep-ctl.

Identificación de Tablas, Registros y Columnas

Cada uno de estos comandos tiene un parámetro table para identificar una tabla dentro de la base de datos. Muchos de ellos también toman un parámetro record que identifica un registro particular dentro de una tabla. El parámetro record puede ser el UUID de un registro, y muchas tablas ofrecen formas adicionales de identificar registros. Algunos comandos también toman parámetros column que identifican un campo particular dentro de los registros de una tabla.

Las siguientes tablas están definidas actualmente:

Global
Configuración de nivel superior para un VTEP de hardware. Esta tabla contiene exactamente un registro, identificado especificando . como nombre del registro.
Manager
Configuración de una conexión OVSDB. Los registros pueden identificarse por el objetivo (por ejemplo, tcp:1.2.3.4).
Physical_Switch
Un switch físico que implementa un VTEP. Los registros pueden identificarse por el nombre del switch físico.
Physical_Port
Un puerto dentro de un switch físico.
Logical_Binding_Stats
Informa estadísticas para el switch lógico con el que se asocia una VLAN en un puerto físico.
Logical_Switch
Un switch Ethernet lógico. Los registros pueden identificarse por el nombre del switch lógico.
Ucast_Macs_Local
Mapeo de direcciones MAC unicast descubiertas localmente a túneles.
Ucast_Macs_Remote
Mapeo de direcciones MAC unicast programadas remotamente a túneles.
Mcast_Macs_Local
Mapeo de direcciones MAC multicast descubiertas localmente a túneles.
Mcast_Macs_Remote
Mapeo de direcciones MAC multicast programadas remotamente a túneles.
Physical_Locator_Set
Un conjunto de uno o más localizadores físicos.
Physical_Locator
Identifica un punto final al que el tráfico del switch lógico puede ser encapsulado y reenviado. Los registros pueden identificarse por el nombre del localizador físico.

Los nombres de los registros deben especificarse completos y con la capitalización correcta, excepto que los UUID pueden abreviarse a sus primeros 4 (o más) dígitos hexadecimales, siempre que sea único dentro de la tabla. Los nombres de tablas y columnas no distinguen entre mayúsculas y minúsculas, y - y _ se tratan indistintamente. Son aceptables abreviaturas únicas de nombres de tablas y columnas, por ejemplo, man o m es suficiente para identificar la tabla Manager.

Valores de Base de Datos

Cada columna en la base de datos acepta un tipo fijo de datos. Los tipos básicos actualmente definidos, y sus representaciones, son:

integer
Un entero decimal en el rango de -2**63 a 2**63-1, inclusive.
real
Un número de punto flotante.
Boolean
Verdadero o falso, escrito true o false, respectivamente.
string
Una cadena Unicode arbitraria, excepto que los bytes nulos no están permitidos. Las comillas son opcionales para la mayoría de las cadenas que comienzan con una letra inglesa o un guión bajo y consisten únicamente en letras, guiones bajos, guiones y puntos. Sin embargo, true y false y las cadenas que coinciden con la sintaxis de los UUID (ver abajo) deben ir entre comillas dobles para distinguirlas de otros tipos básicos. Cuando se usan comillas dobles, la sintaxis es la de las cadenas en JSON, por ejemplo, las barras invertidas pueden usarse para escapar caracteres especiales. La cadena vacía debe representarse como un par de comillas dobles ("").
UUID
Ya sea un identificador universalmente único al estilo de RFC 4122, por ejemplo, f81d4fae-7dec-11d0-a765-00a0c91e6bf6, o un @nombre definido por un comando get o create dentro de la misma invocación de vtep-ctl.

Múltiples valores en una sola columna pueden separarse por espacios o una sola coma. Cuando hay múltiples valores, los duplicados no están permitidos y el orden no es importante. Por el contrario, algunas columnas de base de datos pueden tener un conjunto vacío de valores, representado como [], y los corchetes pueden opcionalmente encerrar otros conjuntos no vacíos o valores únicos. Para una columna que acepta un conjunto de enteros, los comandos de base de datos aceptan un rango. Un rango se representa por dos enteros separados por -. Un rango es inclusivo. Un rango tiene un tamaño máximo de 4096 elementos. Si se necesitan más elementos, se pueden especificar en rangos separados.

Algunas columnas de base de datos son "mapas" de pares clave-valor, donde la clave y el valor son cada uno de un tipo de base de datos fijo. Estos se especifican en el formato key=value, donde key y value siguen la sintaxis del tipo de clave y tipo de valor de la columna, respectivamente. Cuando hay múltiples pares (separados por espacios o una coma), las claves duplicadas no están permitidas y, de nuevo, el orden no es importante. Los valores duplicados están permitidos. Un mapa vacío se representa como {}. Los corchetes pueden opcionalmente encerrar mapas no vacíos también (pero use comillas para evitar que el shell expanda other-config={0=x,1=y} en other-config=0=x other-config=1=y, lo que puede no tener el efecto deseado).

Sintaxis de Comandos de Base de Datos
[--if-exists] [--columns=columna[,columna]...] list tabla [registro]...
Lista los datos en cada registro especificado. Si no se especifican registros, lista todos los registros en tabla.
Si se especifica --columns, solo se listan las columnas solicitadas, en el orden especificado. De lo contrario, se listan todas las columnas, en orden alfabético por nombre de columna.
Sin --if-exists, es un error si algún registro especificado no existe. Con --if-exists, el comando ignora cualquier registro que no exista, sin producir ninguna salida.
[--columns=columna[,columna]...] find tabla [columna[:clave]=valor]...
Lista los datos en cada registro en tabla cuya columna sea igual a valor o, si se especifica clave, cuya columna contenga una clave con el valor especificado. Los siguientes operadores pueden usarse donde se escribe = en el resumen de sintaxis:
= != < > <= >=
Selecciona registros en los que columna[:clave] es igual, no es igual, es menor que, es mayor que, es menor o igual que, o es mayor o igual que valor, respectivamente.
Considere columna[:clave] y valor como conjuntos de elementos. Los conjuntos idénticos se consideran iguales. De lo contrario, si los conjuntos tienen un número diferente de elementos, el conjunto con más elementos se considera más grande. De lo contrario, considere un elemento de cada conjunto en pares, en orden creciente dentro de cada conjunto. El primer par que difiere determina el resultado. (Para una columna que contiene pares clave-valor, primero se comparan todas las claves y los valores solo se consideran si los dos conjuntos contienen claves idénticas).
{=} {!=}
Prueba de igualdad o desigualdad de conjuntos, respectivamente.
{<=}
Selecciona registros en los que columna[:clave] es un subconjunto de valor. Por ejemplo, flood-vlans{<=}1,2 selecciona registros en los que la columna flood-vlans es el conjunto vacío o contiene 1 o 2 o ambos.
{<}
Selecciona registros en los que columna[:clave] es un subconjunto propio de valor. Por ejemplo, flood-vlans{<}1,2 selecciona registros en los que la columna flood-vlans es el conjunto vacío o contiene 1 o 2 pero no ambos.
{>=} {>}
Igual que {<=} y {<}, respectivamente, excepto que la relación se invierte. Por ejemplo, flood-vlans{>=}1,2 selecciona registros en los que la columna flood-vlans contiene tanto 1 como 2.

Los siguientes operadores solo están disponibles en Open vSwitch 2.16 y posteriores:

{in}
Selecciona registros en los que cada elemento en columna[:clave] también está en valor. (Esto es lo mismo que {<=}).
{not-in}
Selecciona registros en los que cada elemento en columna[:clave] no está en valor.
Para operadores aritméticos (= != < > <= >=), cuando se especifica clave pero la columna de un registro en particular no contiene clave, el registro se omite siempre de los resultados. Por lo tanto, la condición other-config:mtu!=1500 coincide con registros que tienen una clave mtu cuyo valor no es 1500, pero no con aquellos que carecen de una clave mtu.
Para los operadores de conjuntos, cuando se especifica clave pero la columna de un registro en particular no contiene clave, la comparación se realiza contra un conjunto vacío. Por lo tanto, la condición other-config:mtu{!=}1500 coincide con registros que tienen una clave mtu cuyo valor no es 1500 y aquellos que carecen de una clave mtu.
No olvide escapar < o > de la interpretación por el shell.
Si se especifica --columns, solo se listan las columnas solicitadas, en el orden especificado. De lo contrario, se listan todas las columnas, en orden alfabético por nombre de columna.
Los UUID que se muestran para las filas creadas en la misma invocación de vtep-ctl serán incorrectos.
[--if-exists] [--id=@nombre] get tabla registro [columna[:clave]]...
Imprime el valor de cada columna especificada en el registro dado en tabla. Para columnas de tipo mapa, una cla
y pueden especificarse opcionalmente, en cuyo caso se imprime el valor asociado a key en la columna, en lugar del mapa completo.
Sin --if-exists, es un error si record no existe o si se especifica key, si key no existe en record. Con --if-exists, un record faltante no produce ninguna salida y una key faltante imprime una línea en blanco.
Si se especifica @name, entonces el UUID de record puede ser referido por ese nombre más adelante en la misma invocación de vtep-ctl en contextos donde se espera un UUID.
Tanto --id como los argumentos de column son opcionales, pero generalmente se debe especificar al menos uno de ellos. Si ambos se omiten, entonces get no tiene ningún efecto aparte de verificar que record existe en table.
--id y --if-exists no se pueden usar juntos.
[--if-exists] set table record column[:key]=value...
Establece el valor de cada column especificada en el record dado en table a value. Para columnas de tipo mapa, se puede especificar opcionalmente una key, en cuyo caso se cambia el valor asociado a key en esa columna (o se añade, si no existe), en lugar del mapa completo.
Sin --if-exists, es un error si record no existe. Con --if-exists, este comando no hace nada si record no existe.
[--if-exists] add table record column [key=]value...
Añade el valor especificado o el par clave-valor a column en record en table. Si column es un mapa, entonces se requiere key, de lo contrario está prohibido. Si key ya existe en una columna de tipo mapa, entonces el value actual no se reemplaza (use el comando set para reemplazar un valor existente).
Sin --if-exists, es un error si record no existe. Con --if-exists, este comando no hace nada si record no existe.
[--if-exists] remove table record column value...

[--if-exists] remove table record column key...

[--if-exists] remove table record column key=value...
Elimina los valores o pares clave-valor especificados de column en record en table. La primera forma se aplica a columnas que no son mapas: cada value especificado se elimina de la columna. Las formas segunda y tercera se aplican a columnas de tipo mapa: si solo se especifica una key, entonces se elimina cualquier par clave-valor con la key dada, independientemente de su valor; si se da un value entonces se elimina un par solo si coinciden tanto la clave como el valor.
No es un error si la columna no contiene la clave o el valor o el par especificado.
Sin --if-exists, es un error si record no existe. Con --if-exists, este comando no hace nada si record no existe.
[--if-exists] clear table record column...
Establece cada column en record en table al conjunto vacío o al mapa vacío, según corresponda. Este comando se aplica solo a columnas que se permiten estar vacías.
Sin --if-exists, es un error si record no existe. Con --if-exists, este comando no hace nada si record no existe.
[--id=(@name | uuid] create table column[:key]=value...
Crea un nuevo registro en table y establece los valores iniciales de cada column. Las columnas que no se establecen explícitamente recibirán sus valores predeterminados. Muestra el UUID de la nueva fila.
Si se especifica @name, entonces el UUID de la nueva fila puede ser referido por ese nombre en otra parte de la misma invocación de vtep-ctl en contextos donde se espera un UUID. Dichas referencias pueden preceder o seguir al comando create.
Si se especifica un uuid válido, entonces se usa como el UUID de la nueva fila.
Precaución (ovs-vsctl como ejemplo)
Los registros en la base de datos Open vSwitch solo son significativos cuando son alcanzables directa o indirectamente desde la tabla Open_vSwitch. Excepto para los registros en las tablas QoS o Queue, los registros que no son alcanzables desde la tabla Open_vSwitch se eliminan automáticamente de la base de datos. Esta eliminación ocurre inmediatamente, sin esperar comandos adicionales de ovs-vsctl u otra actividad de la base de datos. Por lo tanto, un comando create generalmente debe ir acompañado de comandos adicionales dentro de la misma invocación de ovs-vsctl para añadir una cadena de referencias al registro recién creado desde el registro de nivel superior Open_vSwitch. La sección EJEMPLOS muestra cómo hacer esto.
[--if-exists] destroy table record...
Elimina cada record especificado de table. A menos que se especifique --if-exists, cada record debe existir.
--all destroy table
Elimina todos los registros de la table.
Precaución (ovs-vsctl como ejemplo)
El comando destroy solo es útil para registros en las tablas QoS o Queue. Los registros en otras tablas se eliminan automáticamente de la base de datos cuando dejan de ser alcanzables desde la tabla Open_vSwitch. Esto significa que eliminar la última referencia a un registro es suficiente para eliminar el registro en sí. Para los registros en estas tablas, destroy se ignora silenciosamente. Consulte la sección EJEMPLOS más abajo para obtener más información.
wait-until table record [column[:key]=value]...
Espera hasta que table contenga un registro llamado record cuyo column sea igual a value o, si se especifica key, cuyo column contenga una key con el value especificado. Este comando admite los mismos operadores y semántica descritos para el comando find anterior.
Si no se proporcionan argumentos column[:key]=value, este comando espera solo hasta que record exista. Si se proporcionan más de un argumento de este tipo, el comando espera hasta que todos se cumplan.
Precaución (ovs-vsctl como ejemplo)
Generalmente, wait-until debe colocarse al principio de un conjunto de comandos ovs-vsctl. Por ejemplo, wait-until bridge br0 -- get bridge br0 datapath_id espera hasta que se cree un puente llamado br0, luego imprime su columna datapath_id, mientras que get bridge br0 datapath_id -- wait-until bridge br0 abortará si no existe ningún puente llamado br0 cuando ovs-vsctl se conecte inicialmente a la base de datos.
Considere especificar --timeout=0 junto con --wait-until, para evitar que vtep-ctl termine después de esperar un máximo de 5 segundos.
comment [arg]...
Este comando no tiene ningún efecto en el comportamiento, pero cualquier registro de registro de base de datos creado por el comando incluirá el comando y sus argumentos.
