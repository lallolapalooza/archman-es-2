val_add_valpolicy(3)

Paquete: dnssec-tools

Licencias: BSD

dnsval.conf(3) Manual del programador dnsval.conf(3)

NOMBRE

dnsval.conf, resolv.conf, root.hints - Política de configuración para la biblioteca validadora DNSSEC libval(3)

val_add_valpolicy - Añadir dinámicamente una nueva política al contexto del validador

val_remove_valpolicy - Eliminar una política añadida dinámicamente del contexto del validador

SINOPSIS

int val_add_valpolicy(val_context_t *context, 
                void *policy_definition,
                val_policy_entry_t **pol);
int val_remove_valpolicy(val_context_t *context,
                val_policy_entry_t *pol);
typedef struct {
    char *keyword;
    char *zone;
    char *value;
    long ttl;
} libval_policy_definition_t;

DESCRIPCIÓN

Las aplicaciones pueden usar políticas locales para influir en el resultado de la validación. Ejemplos de elementos de política local incluyen anclas de confianza para diferentes zonas y algoritmos no confiables para claves criptográficas y hashes. La política local puede variar según la aplicación y el escenario operativo.

La función val_add_valpolicy() puede usarse para añadir dinámicamente una nueva política para un contexto dado (las políticas no se añaden de forma persistente a la configuración del sistema). El campo policy_definition contiene una definición específica de la implementación de la política del validador a añadir. Para la biblioteca libval, esto está representado por la estructura libval_policy_definition_t, que contiene cuatro campos: los argumentos keyword, zone y value son idénticos a keyword, zone y additional-data definidos a continuación para dnsval.conf. ttl especifica la duración en segundos durante la cual la política se mantiene en vigor. Un valor ttl de -1 añade la política al contexto de forma indefinida. Se devuelve un identificador de la política recién añadida en *pol. Esta estructura es opaca para las aplicaciones; las aplicaciones no deben modificar el contenido de la memoria devuelta en *pol.

Las aplicaciones también pueden revocar los efectos de una política recién añadida, pol, antes de que expire su intervalo de tiempo de espera utilizando la política val_remove_valpolicy().

La biblioteca del validador lee información de configuración de tres archivos separados: resolv.conf, root.hints y dnsval.conf.

resolv.conf
Las opciones nameserver y search son compatibles en el archivo resolv.conf.

La opción nameserver se utiliza para especificar la dirección IP del servidor de nombres al que se deben enviar las consultas por defecto. Por ejemplo,

nameserver 10.0.0.1

Se pueden especificar varios campos adicionales para calificar el servidor de nombres. Por ejemplo, en la siguiente línea:

nameserver [10.0.0.1][example.tsigkey:hmac-md5.sig-alg.reg.int:300:0jnu3SdsMvzzlmTDPYRceA==]:8053

example.tsigkey se refiere al nombre de la clave TSIG; hmac-md5.sig-alg.reg.int se refiere al algoritmo TSIG, 300 es el factor de fudge TSIG y la clave se especifica como un valor codificado en base64. El valor 8053 se refiere al número de puerto.

Los valores para el algoritmo TSIG y el factor de fudge en el ejemplo anterior son los predeterminados. Pueden omitirse de la siguiente manera:

nameserver [10.0.0.1][example.tsigkey:::0jnu3SdsMvzzlmTDPYRceA==]:8053

La parte TSIG también puede omitirse por completo, en cuyo caso la representación es la siguiente:

nameserver [10.0.0.1]:8053

La opción search se utiliza para especificar la ruta de búsqueda para emitir consultas. Por ejemplo,

search test.dnssec-tools.org dnssec-tools.org

La opción forward se utiliza para redirigir las consultas de nombres que coinciden con un nombre de zona dado a los servidores de nombres proporcionados. Por ejemplo,

forward 76.216.12.217 test.dnssec-tools.org

Si el archivo resolv.conf no contiene servidores de nombres, el validador intenta responder recursivamente a la consulta utilizando la información presente en root.hints.

root.hints
El archivo root.hints contiene información de arranque para el resolvedor mientras intenta responder recursivamente a las consultas. El contenido de este archivo puede ser generado por el siguiente comando: 
dig @e.root-servers.net . ns > root.hints
dnsval.conf
El archivo dnsval.conf contiene la política del validador. Consiste en una secuencia de los siguientes "fragmentos de política": 
<etiqueta> <palabra_clave> <datos_adicionales>;

Las políticas se identifican mediante simples cadenas de texto llamadas etiquetas, que deben ser únicas dentro del sistema de configuración. Por ejemplo, "browser" podría usarse como la etiqueta que define la política del validador para todos los navegadores web en un sistema. Un valor de etiqueta de ": " identifica la política predeterminada, la política que se utiliza cuando se especifica un contexto NULL como parámetro ctx para las interfaces listadas en libval(3), val_getaddrinfo(3), y val_gethostbyname(3). La política predeterminada debe ser única dentro del sistema de configuración.

keyword especifica el componente de la política dentro del fragmento de política. El formato de additional-data depende de la palabra_clave especificada.

Si se definen múltiples fragmentos de política para la misma combinación de etiqueta y palabra_clave, se utiliza la primera definición en el archivo.

Las siguientes palabras_clave están definidas para dnsval.conf:

trust-anchor
Para el atributo "trust-anchor", los datos_adicionales son una secuencia de pares ordenados, cada uno que consiste en el nombre de la zona y la parte RDATA para el ancla de confianza con un prefijo opcional. Las anclas de confianza pueden ser registros DNSKEY o DS, el prefijo en el RDATA se utiliza para indicar qué tipo de registro es. Se asume DNSKEY si no se especifica ningún prefijo.

A continuación se presenta un ejemplo.

browser trust-anchor
    .   DS  19036  8  2  \
        49AAC11D7B6F6446702E54A1607371607A1A41855200FD2CE\
        1CDDE32F24E8FB5
    example.com   257 3 5 AQO8XS4y9r77X 9SHBmrx MoJf1Pf9\
        AT9Mr/L5BBGtO9/e9f/zl4FFgM2l B6M2 XEm6mp6 mit4tzp\
        B/sAEQw1McYz6bJdKkTiqtuWTCfDmgQhI6 /Ha0 Ef GPNSqn\
        Y 99FmbSeWNIRaa4fgSCVFhvbrYq1nXkNVy QPeEVHk oDNCA\
        lr qOA3lw==
;
zone-security-expectation
Para el atributo "zone-security-expectation", los datos_adicionales son una secuencia de tuplas <nombre de dominio,valor> que representan la expectativa de seguridad para los nombres en ese dominio, donde el valor puede ser uno de los siguientes:
ignore
Ignorar la validación DNSSEC para nombres bajo este dominio.
validate
Realizar la validación DNSSEC de las respuestas recibidas para nombres bajo este dominio.
untrusted
Rechazar todas las respuestas recibidas para nombres bajo este dominio.

Esta construcción de política del validador DNSSEC zone-security-expectation hace posible definir varias islas de confianza para zonas habilitadas para DNSSEC y para ignorar o validar datos de zonas seleccionadas. La expectativa de seguridad DNSSEC predeterminada para un dominio es "validate". En el siguiente ejemplo, para contextos de validador DNSSEC creados con una etiqueta de política de validador DNSSEC de "browser", la validación DNSSEC solo se realiza para nombres bajo el dominio example.com; los nombres bajo el dominio somebogus.org se consideran siempre no confiables y se ignora la validación DNSSEC para todos los demás nombres de dominio.

browser zone-security-expectation   
    example.com  validate      
    somebogusname.org untrusted
    . ignore
;
provably-insecure-status
Para el atributo "provably-insecure-status", los datos_adicionales son una secuencia de tuplas <nombre de dominio,valor> que representan la validez de la condición provably insecure, donde el valor es uno de los siguientes:
trusted
Tratar la condición provably insecure como válida.
untrusted
Tratar la condición provably insecure como inválida.

La siguiente configuración proporciona un ejemplo de cómo se puede configurar la política del validador para los dominios de prueba. Tenga en cuenta que el dominio '.' es especial, ya que se refiere a la raíz del DNS.

browser provably-insecure-status
    .   trusted
    example.com untrusted
;
untrusted
Tratar la condición de inseguridad demostrable como inválida.

El valor predeterminado para el estado de inseguridad demostrable de un dominio es "trusted". En el siguiente ejemplo, para los contextos del validador DNSSEC creados con la etiqueta predeterminada, la condición de inseguridad demostrable se trata como válida para todos los dominios excepto el dominio net, donde esta condición se trata como inválida.

: provably-insecure-status
    . trusted
    net untrusted
;
clock-skew
Para el atributo "clock-skew", los datos adicionales son una secuencia del nombre de dominio y el número de segundos de desfase de reloj aceptables para las firmas en nombres de ese dominio. Un valor de desfase de reloj de -1 tiene el efecto de desactivar las comprobaciones de tiempo de inicio y expiración en las firmas de ese dominio. El desfase de reloj predeterminado es 0. En el siguiente ejemplo, para los contextos del validador DNSSEC creados con la etiqueta "mta", las comprobaciones de inicio y expiración de firmas se deshabilitan para todos los nombres del dominio example.com. 
mta clock-skew
    example.com -1
;
nsec3-max-iter [solo si LIBVAL_NSEC3 está habilitado]
Especifica el número máximo de iteraciones permitidas al calcular el hash NSEC3 para una zona. Un valor de -1 no establece un límite máximo en el número de iteraciones. Esta es también la configuración predeterminada para una zona.
dlv-trust-points [solo si LIBVAL_DLV está habilitado]
Especifica el árbol DLV para la zona de destino. En el siguiente ejemplo, libval utilizará el registro DLV definido en dlv.isc.org. para todas las consultas bajo la raíz que no nos den una respuesta confiable utilizando el mecanismo DNSSEC normal y tengan una expectativa de seguridad de zona de validate. 
dlv dlv-trust-points
    .   dlv.isc.org.
;

Para que DLV se utilice en el ejemplo anterior, también debe haber una política de ancla de confianza definida para el registro dlv, con la política de expectativa de seguridad de zona para el registro establecida en validate.

dlv trust-anchor
    dlv.isc.org DS  19297  5  2  \
                A11D16F6733983E159EDF8053B2FB57B479D81A309A5\
                0EAA79A81AF48A47C617
;

Además de las opciones de configuración específicas de la zona, también es posible configurar opciones globales para la validación en dnsval.conf. Las opciones globales se pueden especificar utilizando la siguiente construcción.

global-options
    keyowrd1 value1
    keyword2 value2
    ...
;

Solo puede haber una construcción global-options definida para dnsval.conf. Si se definen múltiples construcciones, solo se utiliza la primera.

Las siguientes palabras clave están definidas para global-options en dnsval.conf

trust-local-answers
Esta opción ha sido obsoleta. Use trust-oob-answers en su lugar.
trust-oob-answers
Si el valor asociado a esta opción es yes, entonces, para todas las respuestas devueltas utilizando algún mecanismo fuera de banda (por ejemplo, un almacén de archivos como /etc/hosts), el valor devuelto por la función val_istrusted() (ver libval(3)) es mayor que uno.
edns0-size
Al consultar varios servidores de nombres, libsres también intentará varios tamaños EDNS0, terminando con una consulta en la que EDNS0 está deshabilitado (es decir, sin el bit CD establecido). Los siguientes tamaños EDNS0 se intentan por defecto: 4096, 1492, 512. El control de política "edns0-size" se puede utilizar para cambiar el tamaño EDNS0 más grande que se intenta.
env-policy
Esta opción permite al administrador de dnsval.conf controlar si libval utiliza valores especificados por el usuario en variables de entorno al determinar la política de libval y los destinos de registro. Consulte la sección a continuación sobre la anulación de las políticas de dnsval.conf para obtener detalles adicionales sobre esta opción.
app-policy
Esta opción permite al administrador del archivo dnsval.conf controlar si libval buscará automáticamente una política de validación con una etiqueta igual al nombre de la aplicación en dnsval.conf. Consulte la sección a continuación sobre la anulación de las políticas de dnsval.conf para obtener detalles adicionales sobre esta opción.
closest-ta-only
El comportamiento de validación predeterminado es buscar cualquier cadena de autenticación que valide correctamente. Por lo tanto, si existen anclas de confianza para example.com y test.example.com, el validador devolverá éxito si la cadena de autenticación se puede anclar a la ancla de confianza de example.com, incluso si el ancla de confianza de test.example.com no coincide. En casos donde esto no es deseable, se puede usar la opción closest-ta-only.

Si esta opción se establece en yes, el algoritmo de validación termina en la TA coincidente más cercana.

rec-fallback
Esta opción se utiliza para controlar si libval intentará recurrir a una búsqueda recursiva del nombre si la respuesta del servidor de nombres en caché devolvió un error. Por defecto, esta opción se establece en yes; se puede desactivar estableciendo esta opción en no.
max-refresh
Esta opción se utiliza en conjunto con la marca de consulta VAL_QUERY_SKIP_CACHE. Cuando las consultas tienen esta marca habilitada, normalmente omitirán las entradas en caché. Sin embargo, max-refresh puede limitar la frecuencia con la que se envían realmente las consultas en el cable. Cuando esta opción se establece en un valor positivo, solo se envía una nueva consulta si el valor en caché se almacenó hace más de (el valor especificado por) max-refresh segundos. Si max-refresh es 0, la caché siempre se omite. Si el valor es -1, la caché nunca se omite. El valor predeterminado para max-refresh es 60 segundos. Esto significa que dos consultas enviadas con la marca VAL_QUERY_SKIP_CACHE establecida con menos de un minuto de diferencia solo resultarán en una consulta vista en el cable.
proto
Esta opción se utiliza para controlar el protocolo de red que libval utiliza para enviar consultas a varios servidores de nombres. Si el valor se establece en ipv6, libval usa solo IPv6; si se establece en ipv4, libval usa solo IPv4. El valor predeterminado es any, lo que hace que libval envíe a través de cualquiera de los protocolos disponibles para el servidor de nombres dado.
timeout
Esta opción reemplaza el valor predeterminado del tiempo de espera del resolutor con el valor proporcionado.
retry
Esta opción reemplaza el valor predeterminado de reintentos del resolutor con el valor proporcionado.
log
Esta opción controla el nivel de registro y el destino del registro para libval. El valor esperado para esta opción es el mismo que el especificado para val_add_log_optarg (ver libval(3)).

A continuación, se muestra un ejemplo de construcción global-options:

global-options
    trust-oob-answers yes
    edns0-size 4096
    env-policy enable
    app-policy enable
    log 5:stderr
;

ANULACIÓN DE POLÍTICAS DE resolv.conf

libval primero examina las opciones del resolutor presentes en el archivo resolv.conf especificado en el momento de ejecutar configure. Si este archivo no está presente, libval busca en el archivo /etc/resolv.conf las opciones del resolutor.

Esto permite a los usuarios anular las políticas del resolutor de una manera sencilla. El resolv.conf específico del sistema puede permanecer sin cambios, mientras que cualquier política adicional que pueda ser necesaria para libval se puede usar en el archivo resolv.conf proporcionado por configure.

ANULACIÓN DE POLÍTICAS DE dnsval.conf

libval proporciona tres formas de adaptar las políticas de dnsval.conf a un entorno determinado.

Múltiplos archivos de inclusión
libval permite incluir archivos dnsval.conf adicionales en un archivo dnsval.conf dado. La opción se especifica de la siguiente manera: 
include /ruta/al/archivo/de/anulación/dnsval.conf

Los archivos se leen en amplitud. Las políticas se evalúan de manera que la última política definida tenga mayor precedencia que las anteriores. Por lo tanto, un administrador puede proporcionar un dnsval.conf con políticas predeterminadas que incluyan otro archivo del directorio principal del usuario. El archivo incluido puede usarse para anular las políticas especificadas en el archivo dnsval.conf base.

Políticas de nombre de aplicación
Si la opción global app-policy no está deshabilitada, libval busca automáticamente una política en dnsval.conf con un valor de etiqueta construido a partir del nombre de la aplicación. Por ejemplo, dnsval.conf puede definirse con políticas de validador para la etiqueta foo. La aplicación foo, cuando se ejecuta, utilizará la política definida contra la etiqueta foo durante su operación de validación.
Políticas a través del entorno
Si la opción global env-policy no está deshabilitada, libval examina las variables de entorno VAL_CONTEXT_LABEL y VAL_LOG_TARGET para determinar la etiqueta de la política del validador y el destino del registro.
Precedencia de etiquetas de validador
Efectivamente, existen cuatro tipos diferentes de etiquetas de política que pueden ser aplicadas por libval: políticas de nombre de aplicación, políticas a través de VAL_CONTEXT_LABEL y etiquetas especificadas por la aplicación (ya sea NULL o no NULL). La precedencia de la aplicación de estas etiquetas se define con las siguientes reglas:

1. Si env-policy es "override", use la etiqueta especificada en la variable de entorno VAL_CONTEXT_LABEL (si está definida).

2. Si env-policy es "enable" y la política especificada por la aplicación es NULL, use la etiqueta especificada en la variable de entorno VAL_CONTEXT_LABEL (si está definida).

3. Si app-policy es "override", use la etiqueta generada a partir del nombre de la aplicación. Si esta etiqueta de política no existe en el sistema de configuración, use la política predeterminada.

4. Si app-policy es "enable" y la política especificada por la aplicación es NULL, use la etiqueta generada a partir del nombre de la aplicación.

val_add_valpolicy(3)

NAME

SYNOPSIS

#include <libval/libval.h>

val_set_policy_file_from_buffer(const char *policy_buffer);

int
val_get_policy_list(char ***policy_list);

DESCRIPTION

The libval library provides a mechanism for loading and managing DNSSEC validation policies. These policies are used to guide the validation process. The following functions are available for managing and manipulating these policies:

val_add_valpolicy
Adds a new validation policy. policy_name is the name of the policy and policy_data is a string containing the policy definition. The format of policy_data is described in dnsval.conf(5).
val_get_valpolicy
Retrieves the data for a given policy. policy_name is the name of the policy to retrieve. If found, the policy data is returned in policy_data, which is a pointer to a dynamically allocated string. The caller is responsible for freeing this memory.
val_set_policy
Sets the current validation policy to the one specified by policy_name. If the policy name is NULL, the system default policy is used.
val_set_policy_file
Sets the current validation policy by reading from the specified policy_file. The file should be in the same format as dnsval.conf(5).
val_set_policy_file_from_buffer
Sets the current validation policy by reading from the provided policy_buffer. The buffer should contain policy definitions in the format described in dnsval.conf(5).
val_get_policy_name
Retrieves the name of the currently active validation policy. The policy name is returned in policy_name, which is a pointer to a dynamically allocated string. The caller is responsible for freeing this memory.
val_get_policy_list
Retrieves a list of all available validation policy names. The list is returned in policy_list, which is a pointer to a dynamically allocated array of strings. The caller is responsible for freeing the memory for the array and each string within it.
val_get_policy
Retrieves the data for a given policy. policy_name is the name of the policy to retrieve. If found, the policy data is returned in policy_data, which is a pointer to a dynamically allocated string. The caller is responsible for freeing this memory.
val_set_policy_override
Sets the global policy option env-policy to override. This allows environment variables and application-specified policies to influence the validation policy. See the "OVERRIDING DNSVAL.CONF POLICIES" section for details.
val_set_policy_disable
Sets the global policy option env-policy to disable. This disables the influence of environment variables and application-specified policies on the validation policy, forcing the use of the system default policy.
val_set_policy_enable
Sets the global policy option env-policy to enable. This allows environment variables and application-specified policies to be used under certain conditions. See the "OVERRIDING DNSVAL.CONF POLICIES" section for details.

OVERRIDING resolv.conf POLICIES

The global options env-policy and app-policy control how libval interacts with policies specified in resolv.conf and other configuration files.

disable
Ignores any policy specified by the application or environment. The system default policy is always used.
enable
If the application specifies a policy, that policy is used. Otherwise, the policy specified by the environment (e.g., VAL_CONTEXT_LABEL) is used. If neither is specified, the system default policy is used.
override
The policy specified by the environment (e.g., VAL_CONTEXT_LABEL) is always used if it is specified. Otherwise, the policy specified by the application is used. If neither is specified, the system default policy is used.

The app-policy global option controls whether policies specified by the application are used.

disable
Ignores any policy specified by the application. The policy is determined by the env-policy setting and the environment.
enable
If the application specifies a policy and it is not NULL, use this label.

6. Use default policy

The following use-cases can therefore be defined

locked-down system with single policy
An administrator that wants to (and is able to) lock down a system to a particular validator policy, must set the env-policy and app-policy global options to disable. This also requires that administrators are able to lock down the system to specific applications and that these applications are not written in a way that would allow them to specify non-NULL policy labels during context creation. (see val_create_context in libval(3)).
locked-down system with app-specific policies
An administrator that wants to (and is able to) lock down a system to a particular dnsval.conf file, but wishes to use different policies for different applications must set the app-policy to override and the env-policy to disable. The administrator must also define policies for various application names in dnval.conf; for applications that don't have a policy with a label corresponding to its name, the default policy is used.

The administrator may set the app-policy to enable if non-NULL policies specified by the application during validator context creation is deemed acceptable.

User controlled
An administrator can set env-policy to override to give the user complete control over which policy label is used during validation. The validation policy is read through the VAL_CONTEXT_LABEL environment variable.

If VAL_CONTEXT_LABEL is specified globally for the system, the administrator may instead choose the env-policy global option to be enable instead of override. In this case, the label given in VAL_CONTEXT_LABEL is used only when the policy specified by the application is non-NULL.

The label in VAL_CONTEXT_LABEL is used only if it is defined. If this value is NULL, libval will read other policy labels as guided by the precedence rules listed above.
