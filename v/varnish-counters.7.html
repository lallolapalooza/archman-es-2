NOMBRE

varnish-counters - Definiciones de campos de contador de Varnish

LCK – CONTADORES DE BLOQUEO

Contadores que rastrean la actividad en las diferentes clases de bloqueos mutex.

Los recuentos pueden ser ligeramente incorrectos si hay más de un bloqueo instanciado en cada clase (es decir, .creat > 1)

creat – contador - debug

Bloqueos creados

destroy – contador - debug

Bloqueos destruidos

locks – contador - debug

Operaciones de bloqueo

dbg_busy – contador - debug

Operaciones de bloqueo disputadas

Si el bit de depuración lck está activado: Operaciones de bloqueo que devolvieron EBUSY en el primer intento de bloqueo.

Si el bit de depuración lck está desactivado, este contador nunca se incrementará, incluso si las operaciones de bloqueo son disputadas.

dbg_try_fail – contador - debug

Operaciones de intento de bloqueo fallidas y disputadas

Si el bit de depuración lck está activado: Operaciones de intento de bloqueo que devolvieron EBUSY.

Si el bit de depuración lck está desactivado, este contador nunca se incrementará, incluso si las operaciones de bloqueo son disputadas.

MAIN – CONTADORES PRINCIPALES

summs – contador - debug

operaciones de resumen de estadísticas

Número de veces que las estadísticas por hilo se sumaron a los contadores globales.

uptime – contador - info

Tiempo de actividad del proceso hijo

Cuánto tiempo ha estado funcionando el proceso hijo.

sess_conn – contador - info

Sesiones aceptadas

Número de sesiones aceptadas con éxito

sess_fail – contador - info

Fallos al aceptar sesiones

Número de fallos al aceptar la conexión TCP.

Este contador es la suma de los contadores sess_fail_*, que proporcionan información más detallada.

sess_fail_econnaborted – contador - info

Fallos al aceptar sesiones: conexión abortada

Razón detallada para sess_fail: Conexión abortada por el cliente, generalmente inofensiva.

sess_fail_eintr – contador - info

Fallos al aceptar sesiones: llamada al sistema interrumpida

Razón detallada para sess_fail: La llamada accept() fue interrumpida, generalmente inofensiva.

sess_fail_emfile – contador - info

Fallos al aceptar sesiones: demasiados archivos abiertos

Razón detallada para sess_fail: No había descriptor de archivo disponible. Considere aumentar RLIMIT_NOFILE (ver ulimit -n).

sess_fail_ebadf – contador - info

Fallos al aceptar sesiones: descriptor de archivo incorrecto

Razón detallada para sess_fail: El descriptor de archivo del socket de escucha no era válido. Nunca debería suceder.

sess_fail_enomem – contador - info

Fallos al aceptar sesiones: no hay suficiente memoria

Razón detallada para sess_fail: Lo más probable es que sea insuficiente memoria en el buffer del socket. Nunca debería suceder.

sess_fail_other – contador - info

Fallos al aceptar sesiones: otros

Razón detallada para sess_fail: ninguno de los anteriores, ver registro SessError (varnishlog -g raw -i SessError).

client_req_400 – contador - info

Solicitudes de cliente recibidas, sujetas a errores 400

400 significa que no pudimos entender la solicitud, estaba drásticamente mal formada.

client_req_417 – contador - info

Solicitudes de cliente recibidas, sujetas a errores 417

417 significa que algo salió mal con un encabezado Expect:.

client_req – contador - info

Solicitudes de cliente válidas recibidas

El número de solicitudes de cliente analizables vistas.

esi_req – contador - info

Subsolicitudes ESI

Número de subsolicitudes ESI realizadas.

cache_hit – contador - info

Acertadas en caché

Número de aciertos en caché. Un acierto en caché indica que un objeto ha sido entregado a un cliente sin tener que obtenerlo de un servidor backend.

cache_hit_grace – contador - info

Acertadas en caché con gracia

Número de aciertos en caché con gracia. Un acierto en caché con gracia es un acierto en caché donde el objeto está expirado. Tenga en cuenta que dichos aciertos también están incluidos en el contador cache_hit.

cache_hitpass – contador - info

Acertadas en caché para pasar.

Número de aciertos para pasar. Un acierto en caché para pasar indica que Varnish va a pasar la solicitud al backend y esta decisión se ha almacenado en caché en sí misma. Esto cuenta cuántas veces se utiliza la decisión en caché.

cache_hitmiss – contador - info

Acertadas en caché para fallo.

Número de aciertos para fallo. Un acierto en caché para fallo indica que Varnish va a proceder como para un fallo de caché sin agrupación de solicitudes, y esta decisión ha sido almacenada en caché. Esto cuenta cuántas veces se utiliza la decisión en caché.

cache_miss – contador - info

Fallos en caché

Número de fallos. Un fallo en caché indica que el objeto se obtuvo del backend antes de entregarlo al cliente.

beresp_uncacheable – contador - info

Respuestas del backend no cacheadas

Número de respuestas del backend consideradas no cacheadas.

beresp_shortlived – contador - info

Objetos efímeros

Número de objetos creados con ttl+grace+keep menor que el parámetro de tiempo de ejecución 'shortlived'.

backend_conn – contador - info

Conexiones al backend exitosas

Cuántas conexiones al backend se han establecido con éxito.

backend_unhealthy – contador - info

Conexiones al backend no intentadas

backend_busy – contador - info

Conexiones al backend demasiadas

backend_fail – contador - info

Fallos de conexión al backend

backend_reuse – contador - info

Reutilizaciones de conexión al backend

Número de reutilizaciones de conexión al backend. Este contador se incrementa cada vez que reutilizamos una conexión reciclada.

backend_recycle – contador - info

Reciclajes de conexión al backend

Número de reciclajes de conexión al backend. Este contador se incrementa cada vez que tenemos una conexión de mantenimiento (keep-alive) que se devuelve al pool de conexiones. Aún no se ha utilizado, pero podría serlo, a menos que el backend la cierre.

backend_retry – contador - info

Reintentos de conexión al backend

backend_wait – contador - info

Esperó en cola una conexión al backend

Número de conexiones al backend que tuvieron que esperar en cola para obtener una conexión disponible.

ESTADÍSTICAS AVANZADAS

These statistics are available via CLI command `varnishstat -a` or via the Varnish Cache Admin interface.

Estas estadísticas están disponibles a través del comando de CLI `varnishstat -a` o a través de la interfaz de administración de Varnish Cache.

backend_conn – counter - info

Backend connections

Number of backend connections successfully established.

backend_fail – counter - info

Backend connect failures

Number of backend connections that failed. This includes all connection attempts that did not result in a successful connection within the `backend_connect_timeout` limit.

backend_unreachable – counter - info

Backend unreachable

Number of backends that were unreachable. This is counted if a backend connection fails after the first attempt.

backend_busy – counter - info

Backend busy

Number of times a backend connection attempt failed because the backend was busy. This is typically when the backend has reached its maximum connection limit.

backend_retry – counter - info

Backend retries

Number of times a backend connection attempt was retried. This happens if a backend is temporarily unavailable.

backend_reset – counter - info

Backend reset

Number of times a backend connection was reset by the backend server.

backend_reuse – counter - info

Backend reuse

Number of times an existing backend connection was reused.

backend_toolate – counter - info

Backend too late

Number of times a backend connection attempt timed out.

backend_linger – counter - info

Backend connection linger

Number of backend connections that were kept open longer than necessary.

backend_wait – counter - info

Backend conn. waited in queue

Count of backend requests that waited in a backend_wait queue for a connection to become available. The size of a backend wait queue is defined by the backend wait_limit property. The wait queue is only used when max_connections to the backend are in use.

backend_wait_fail – counter - info

Backend conn. waited in queue and did not get a connection

Count of backend requests that waited in a backend_wait queue for a connection to become available and did not get one (timed out). The maximum time to wait in the queue is defined by the backend wait_timeout property.

beresp.body empty

fail – counter - info

Connections failed

Counter of failed opens. Detailed reasons are given in the fail_* counters (DIAG level) and in the log under the FetchError tag.

This counter is the sum of all detailed fail_* counters.

All fail_* counters may be slightly inaccurate for efficiency.
