VSL(7) Manual de Información Miscelánea VSL(7)

NOMBRE

VSL - Varnish Shared Memory Logging

DESCRIPCIÓN

Este documento describe el formato y contenido de todas las etiquetas de registro de memoria compartida de Varnish. Estas etiquetas son utilizadas por las herramientas de registro varnishlog(1), varnishtop(1), etc. que vienen con Varnish.

Etiquetas VSL

BackendClose - Conexión de backend cerrada
Registrado cuando se cierra una conexión de backend.

El formato es:

%d %s %s [ %s ]
|  |  |    |
|  |  |    +- Razón opcional, ver SessClose para explicación
|  |  +------ "close" o "recycle"
|  +--------- Nombre de visualización del backend
+------------ Descriptor de archivo de conexión
BackendOpen - Conexión de backend abierta
Registrado cuando se abre una nueva conexión de backend.

El formato es:

%d %s %s %s %s %s %s
|  |  |  |  |  |  |
|  |  |  |  |  |  +- "connect" o "reuse"
|  |  |  |  |  +---- Puerto local
|  |  |  |  +------- Dirección local
|  |  |  +---------- Puerto remoto
|  |  +------------- Dirección remota
|  +---------------- Nombre de visualización del backend
+------------------- Descriptor de archivo de conexión
Backend_health - Verificación de salud del backend
El resultado de una sonda de salud del backend.

El formato es:

%s %s %s %s %u %u %u %f %f %s
|  |  |  |  |  |  |  |  |  |
|  |  |  |  |  |  |  |  |  +- Información de respuesta/error HTTP de la sonda
|  |  |  |  |  |  |  |  +---- Tiempo medio de respuesta
|  |  |  |  |  |  |  +------- Tiempo de respuesta
|  |  |  |  |  |  +---------- Tamaño de la ventana de la sonda
|  |  |  |  |  +------------- Nivel umbral de la sonda
|  |  |  |  +---------------- Número de sondeos buenos en la ventana
|  |  |  +------------------- Bits de la ventana de la sonda
|  |  +---------------------- "healthy" o "sick"
|  +------------------------- "Back", "Still" o "Went"
+---------------------------- Nombre del backend

Los bits de la ventana de la sonda son:

'-': No se pudo conectar
'4': IPv4 bueno
'6': IPv6 bueno
'U': UNIX bueno
'x': Error Xmit (Transmisión)
'X': Xmit bueno
'r': Error Recv (Recepción)
'R': Recv bueno
'H': Happy (Feliz)

Cuando el backend se crea por primera vez, los bits de la ventana para las ranuras de verificación de salud que aún no se han ejecutado aparecen como fallos de conexión ('-').

ExpBan - Objeto desalojado debido a prohibición
Registra el VXID cuando un objeto está prohibido.
ExpKill - Evento de expiración de objeto
Registra eventos relacionados con la expiración de objetos. Los eventos son:
EXP_Rearm
Registrado cuando cambia la hora de expiración de un objeto.
EXP_Inbox
Registrado cuando el hilo de expiración recoge un objeto de la bandeja de entrada para su procesamiento.
EXP_Kill
Registrado cuando el hilo de expiración elimina un objeto de la bandeja de entrada.
EXP_When
Registrado cuando el hilo de expiración mueve un objeto en el binheap.
EXP_Inspect
Registrado cuando el hilo de expiración inspecciona el próximo objeto programado para expirar.
EXP_Expired
Registrado cuando el hilo de expiración expira un objeto.
EXP_Removed
Registrado cuando el hilo de expiración elimina un objeto antes de la expiración.
VBF_Superseded
Registrado cuando un objeto reemplaza a otro.
LRU_Cand
Registrado cuando un objeto es evaluado para expiración forzada LRU.
LRU
Registrado cuando un objeto es expirado forzosamente debido a LRU.
LRU_Fail
Registrado cuando no se encuentra un objeto candidato adecuado para la expiración forzada LRU.

El formato es:

EXP_Rearm p=%p E=%f e=%f f=0x%x
EXP_Inbox p=%p e=%f f=0x%x
EXP_Kill p=%p e=%f f=0x%x
EXP_When p=%p e=%f f=0x%x
EXP_Inspect p=%p e=%f f=0x%x
EXP_Expired x=%u t=%f h=%u
EXP_Removed x=%u t=%f h=%u
VBF_Superseded x=%u n=%u
LRU_Cand p=%p f=0x%x r=%d
LRU x=%u
LRU_Fail
Leyenda:
p=%p         Puntero Objcore
t=%f         TTL restante (s)
e=%f         Tiempo de expiración (época unix)
E=%f         Tiempo de expiración antiguo (época unix)
f=0x%x       Banderas Objcore
r=%d         Contador de referencias Objcore
x=%u         VXID del objeto
n=%u         Nuevo VXID del objeto
h=%u         Accesos Objcore

Gzip - G(un)zip realizado en el objeto
Se emite un registro Gzip por cada instancia de trabajo de gzip o gunzip realizada. En el peor de los casos, una transacción ESI almacenada en objetos comprimidos pero entregados descomprimidos, se encontrará con muchos de estos.

El formato es:

%c %c %c %d %d %d %d %d
|  |  |  |  |  |  |  |
|  |  |  |  |  |  |  +- Longitud en bits de los datos comprimidos
|  |  |  |  |  |  +---- Ubicación en bits del último bit
|  |  |  |  |  +------- Ubicación en bits del primer bloque deflate
|  |  |  |  +---------- Bytes de salida
|  |  |  +------------- Bytes de entrada
|  |  +---------------- 'E': ESI, '-': Objeto normal
|  +------------------- 'F': Fetch, 'D': Deliver
+---------------------- 'G': Gzip, 'U': Gunzip, 'u': Gunzip-test

Ejemplos:

U F E 182 159 80 80 1392
G F E 159 173 80 1304 1314

SessClose - Conexión del cliente cerrada
SessClose es el último registro para cualquier conexión de cliente.

El formato es:

%s %f
|  |
|  +- Cuánto tiempo estuvo abierta la sesión
+---- Por qué se cerró la conexión
Explicación de las razones (primera columna):
  • REM_CLOSE: Cliente cerrado
  • REQ_CLOSE: El cliente solicitó el cierre
  • REQ_HTTP10: Proto < HTTP/1.1
  • RX_BAD: Solicitud/respuesta recibida incorrecta
  • RX_BODY: Fallo al recibir el cuerpo
  • RX_JUNK: Datos basura recibidos
  • RX_OVERFLOW: Desbordamiento del búfer recibido
  • RX_TIMEOUT: Tiempo de espera de recepción
  • RX_CLOSE_IDLE: Se alcanzó el tiempo de espera inactivo
  • TX_PIPE: Transacción en tubería
  • TX_ERROR: Transacción de error
  • TX_EOF: Transmisión de fin de archivo
  • RESP_CLOSE: Cierre solicitado por el backend/VCL
  • OVERLOAD: Falta de algún recurso
  • PIPE_OVERFLOW: Desbordamiento de la tubería de sesión
  • RANGE_SHORT: Datos insuficientes para el rango
  • REQ_HTTP20: HTTP2 no aceptado
  • VCL_FAILURE: Fallo de VCL
  • RAPID_RESET: Restablecimiento rápido de HTTP2

TTL - TTL establecido en el objeto
Se emite un registro TTL cada vez que se establecen los valores ttl, grace o keep para un objeto, así como si el objeto es almacenable en caché o no.

El formato es:

%s %d %d %d %d [ %d %d %u %u ] %s
|  |  |  |  |    |  |  |  |    |
|  |  |  |  |    |  |  |  |    +- "cacheable" o "uncacheable"
|  |  |  |  |    |  |  |  +------ Max-Age del encabezado Cache-Control
|  |  |  |  |    |  |  +--------- Encabezado Expires
|  |  |  |  |    |  +------------ Encabezado Date
|  |  |  |  |    +--------------- Age (incluye el valor del encabezado Age:)
|  |  |  |  +-------------------- Tiempo de referencia para TTL
|  |  |  +----------------------- Keep
|  |  +-------------------------- Grace
|  +----------------------------- TTL
+-------------------------------- "RFC", "VCL" o "HFP"

Los cuatro campos opcionales solo están presentes en los encabezados "RFC".

Ejemplos:

VCL 120 10 0 1312966111 uncacheable
HFP 2 0 0 1312966113 uncacheable
Timestamp - Información de tiempo
Contiene información de tiempo para los hilos de trabajo de Varnish.

Varnish emite marcas de tiempo en ciertos eventos y muestra la hora absoluta del evento, el tiempo transcurrido desde el inicio de la unidad de trabajo y el tiempo transcurrido desde que se registró la última marca de tiempo. Consulte la sección TIMESTAMPS a continuación para obtener información sobre las marcas de tiempo individuales.

El formato es:

%s: %f %f %f
|   |  |  |
|   |  |  +- Tiempo desde la última marca de tiempo
|   |  +---- Tiempo desde el inicio de la unidad de trabajo
|   +------- Tiempo absoluto del evento
+----------- Etiqueta del evento

VCL_acl - Resultados de la comprobación de ACL de VCL
Las ACL con la bandera +log emiten este registro con el resultado.

El formato es:

%s [%s [%s [fixed: %s]]]
|   |   |          |
|   |   |          +- Información fija (ver más abajo)
|   |   +------------ Entrada coincidente (solo para MATCH)
|   +---------------- Nombre de la ACL para MATCH o NO_MATCH
+-------------------- MATCH, NO_MATCH o NO_FAM
  • Información fija: contiene la red/máscara para entradas no canónicas (ver la bandera pedantic de acl) o plegada para entradas que fueron el resultado de una operación de plegado (ver la bandera fold de acl).
  • MATCH denota una coincidencia de ACL
  • NO_MATCH denota que una ACL comprobada no ha coincidido
  • NO_FAM denota una familia de direcciones faltante y no debería ocurrir.

El formato es:

FILTERS

Filters are used to specify which log records to show. Filters are specified on the command line, and there can be multiple filters. A log record is shown if it matches any of the filters.

The filters are specified as a comma-separated list of filter expressions. A filter expression is composed of zero or more conditions, separated by commas.

A condition is either a tag name, or a tag name followed by a condition operator and a value. The condition operators are:

=
Match the value exactly.
~
Match the value using a POSIX regular expression.
!
Negate the result of the condition.

A filter expression matches a log record if all of its conditions match.

The default filter is -everything, which matches all log records.

The following tags are available:

%s %d %d
|  |  |
|  |  +- Total bytes produced
|  +---- Number of calls made
+------- Name of filter

NB: This log record is masked by default.

Witness - Lock order witness records
Diagnostic recording of locking order.
WorkThread - Logs thread start/stop events
Logs worker thread creation and termination events.

The format is:

%p %s
|  |
|  +- [start|end]
+---- Worker struct pointer

NB: This log record is masked by default.

TIMESTAMPS

Los timestamps se insertan en el log al completar ciertos eventos durante el manejo de tareas del hilo de trabajo. Los timestamps tienen una etiqueta que muestra qué evento se completó. Los campos reportados muestran el tiempo absoluto del evento, el tiempo transcurrido desde el inicio de la tarea y el tiempo transcurrido desde que se registró el último timestamp.

Los timestamps registrados automáticamente por Varnish se insertan después de completar eventos que se espera que tengan retrasos (por ejemplo, E/S de red o tiempo de espera en una cola). Los timestamps también se pueden insertar desde VCL usando la función std.timestamp(). Si se realizan tareas que consumen tiempo en la configuración de VCL, es una buena idea registrar un timestamp después de completar esa tarea. Esto evita que la información de tiempo en timestamps posteriores incluya el tiempo dedicado al evento VCL.

MENSAJES DE NOTIFICACIÓN

Los mensajes de notificación contienen información sobre el manejo de una solicitud. Estas pueden ser circunstancias excepcionales encontradas que causan una desviación del manejo normal. Los mensajes están precedidos por vsl: para los mensajes generados por el núcleo de Varnish, y se alienta a los autores de VMOD a usar vmod_<nombre>: para sus propios mensajes de notificación. Esto coincide con el nombre de la página del manual donde se esperan descripciones detalladas de los mensajes de notificación.

Los mensajes principales se describen a continuación.

Obtención condicional esperando objeto de streaming

El backend respondió 304 Not Modified a una obtención condicional utilizando un objeto que aún no se ha obtenido completamente como objeto desactualizado. Esto solo puede suceder cuando el TTL del objeto es menor que el tiempo que toma obtenerlo. La obtención se detiene hasta que el objeto desactualizado se obtiene por completo, momento en el cual el nuevo objeto se crea normalmente. Mientras se espera, cualquier tiempo de gracia en el objeto desactualizado estará en efecto.

Alto número de variantes

Los objetos se buscan principalmente en un índice utilizando la clave hash calculada a partir de la función VCL hash_data(). Cuando hay variantes involucradas, es decir, cuando una respuesta del backend se almacenó con una cabecera Vary, se realiza una búsqueda secundaria pero no está indexada. A medida que aumenta el número de variantes para una clave dada, esto puede ralentizar las búsquedas en caché, y dado que esto sucede bajo un bloqueo, puede aumentar significativamente la contención de bloqueo, aún más para objetos solicitados con frecuencia. Por lo tanto, las variantes deben usarse con moderación en respuestas cacheadas, pero dado que pueden originarse tanto en VCL como en servidores de origen, esta notificación debería ayudar a identificar recursos problemáticos.
