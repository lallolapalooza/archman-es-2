N

malloc(

)

La función malloc() asigna size bytes y devuelve un puntero a la memoria asignada. La memoria no está inicializada. Si size es 0, entonces malloc() devuelve un valor de puntero único que más tarde puede ser pasado con éxito a free(). (Véase "Comportamiento no po

rtable" para problem
as de portabilidad.)

free(

)

La función free() libera el espacio de memoria apuntado por p, que debe haber sido devuelto por una llamada anterior a malloc() o funciones relacionadas. De lo contrario, o si p ya ha sido liberado, ocurre un comportamiento indefinido. Si p es NULL, no se realiza

ningun
a operación.

calloc(

)

La función calloc() asigna memoria para un array de n elementos de size bytes cada uno y devuelve un puntero a la memoria asignada. La memoria se establece en cero. Si n o size es 0, entonces calloc() devuelve un valor de puntero único que más tarde puede ser pasado con éxito a free(

).

Si la multiplicación de n y size resultara en un desbordamiento entero, entonces calloc() devuelve un error. Por el contrario, un desbordamiento entero no sería detectado en la siguiente llamada a malloc(), con el resultado de que se asignaría un bloque de memoria de tamaño

incorrecto: 


malloc
(n *
size);

realloc(

)

La función realloc() cambia el tamaño del bloque de memoria apuntado por p a size bytes. El contenido de la memoria permanecerá sin cambios en el rango desde el inicio de la región hasta el mínimo entre los tamaños antiguos y nuevos. Si el nuevo tamaño es mayor que el antiguo, la memoria añadida no será

inicializada.

Si p es NULL, entonces la llamada es equivalente a malloc(size), para todos los valores de size

.

Si size es igual a cero, y p no es NULL, entonces la llamada es equivalente a free(p) (pero véase "Comportamiento no portable" para problemas de portabilidad)

.

A menos que p sea NULL, debe haber sido devuelto por una llamada anterior a malloc o funciones relacionadas. Si el área apuntada fue movida, se realiza un free

(p
).

reallocarray(

)

La función reallocarray() cambia el tamaño de (y posiblemente mueve) el bloque de memoria apuntado por p para que sea lo suficientemente grande para un array de n elementos, cada uno de size bytes. Es equivalente a la

llamada 


realloc(p, n * size)
;

Sin embargo, a diferencia de esa llamada a realloc(), reallocarray() falla de forma segura en el caso en que la multiplicación desborde. Si ocurre dicho desbordamiento, reallocarray(

) devue
lve un
error.

VALOR DE

RETORNO

Las funciones malloc(), calloc(), realloc() y reallocarray() devuelven un puntero a la memoria asignada, que está adecuadamente alineada para cualquier tipo que quepa en el tamaño solicitado o menos. En caso de error, estas funciones devuelven NULL y establecen errno. Intentar asignar más de PTRDIFF_MAX bytes se considera un error, ya que un objeto de ese tamaño podría causar que una resta posterior de punteros

desborde.

La función free() no devuelve ningún valor y preserva errno

.

Las funciones realloc() y reallocarray() devuelven NULL si p no es NULL y el tamaño solicitado es cero; esto no se considera un error. (Véase "Comportamiento no portable" para problemas de portabilidad.) De lo contrario, el puntero devuelto puede ser el mismo que p si la asignación no fue movida (p. ej., había espacio para expandir la asignación in situ), o diferente de p si la asignación fue movida a una nueva dirección. Si estas funcione

s fallan, el bloque original queda i
ntacto; no es liberado ni movido.

NOTA

S

Por defecto, Linux sigue una estrategia de asignación de memoria optimista. Esto significa que cuando malloc() devuelve non-NULL no hay garantía de que la memoria realmente esté disponible. En caso de que resulte que el sistema se ha quedado sin memoria, uno o más procesos serán asesinados por el OOM killer. Para más información, consulta la descripción de /proc/sys/vm/overcommit_memory y /proc/sys/vm/oom_adj en proc(5), y el archivo del código fuente del kernel de Linux Documentation/vm/overcommit-a

ccounting.rst.

Normalmente, malloc() asigna memoria del heap, y ajusta el tamaño del heap según sea necesario, usando sbrk(2). Cuando se asignan bloques de memoria mayores que MMAP_THRESHOLD bytes, la implementación de malloc() en glibc asigna la memoria como un mapeo anónimo privado usando mmap(2). MMAP_THRESHOLD es 128 kB por defecto, pero es ajustable usando mallopt(3). Antes de Linux 4.7, las asignaciones realizadas usando mmap(2) no se veían afectadas por el límite de recursos RLIMIT_DATA; desde Linux 4.7, este límite también se aplica a las asignaciones realizadas usando mmap(

2).

Para evitar la corrupción en aplicaciones multihilo, se usan mutexes internamente para proteger las estructuras de datos de gestión de memoria empleadas por estas funciones. En una aplicación multihilo en la que los hilos asignan y liberan memoria simultáneamente, podría haber contención por estos mutexes. Para manejar de forma escalable la asignación de memoria en aplicaciones multihilo, glibc crea arenas adicionales de asignación de memoria si se detecta contención de mutexes. Cada arena es una gran región de memoria que es internamente asignada por el sistema (usando brk(2) o mmap(2)), y gestionada con sus propios

mutexes.

Si tu programa usa un asignador de memoria privado, debería hacerlo reemplazando malloc(), free(), calloc(), y realloc(). Las funciones de reemplazo deben implementar los comportamientos documentados de glibc, incluyendo el manejo de errno, las asignaciones de tamaño cero y la comprobación de desbordamiento; de lo contrario, otras rutinas de la biblioteca podrían fallar o funcionar incorrectamente. Por ejemplo, si el free() de reemplazo no preserva errno, entonces rutinas de la biblioteca aparentemente no relacionadas podrían fallar sin tener una razón válida en errno. Los asignadores de memoria privados también podrían necesitar reemplazar otras funciones de glibc; consulta "Replacing malloc" en el manual de glibc para más

detalles.

Los fallos en los asignadores de memoria casi siempre están relacionados con la corrupción del heap, como desbordar un trozo asignado o liberar el mismo puntero dos

veces.

La implementación de malloc() es ajustable a través de variables de entorno; consulta mallopt(3) para más

detalles.

Comportamiento no

portable

El comportamiento de estas funciones cuando el tamaño solicitado es cero es específico de glibc; otras implementaciones podrían devolver NULL sin establecer errno, y los programas POSIX portables deberían tolerar tal comportamiento. Consulta realloc(

3p).

POSIX requiere que los asignadores de memoria establezcan errno en caso de fallo. Sin embargo, el estándar C no requiere esto, y las aplicaciones portables a plataformas no POSIX no deberían asumir

esto.

Los programas portables no deberían usar asignadores de memoria privados, ya que POSIX y el estándar C no permiten el reemplazo de malloc(), free(), calloc(), y real

lo
c(
).

ERRORE

S

Los programadores esperarían naturalmente por inducción que realloc(p, size) es consistente con free(p) y malloc(size), ya que ese es el comportamiento en el caso general. Esto no es explícitamente requerido por POSIX.1-2024 o C11, pero todas las implementaciones conformes son consistentes con

eso.

La implementación de realloc() en glibc no es consistente con eso, y como consecuencia, es peligroso llamar a realloc(p, 0) en

glibc.

Una solución trivial para glibc es llamarlo como realloc(p, size?size:1)

.

La solución para reallocarray() en glibc —que comparte el mismo error— sería reallocarray(p, n?

n:1, size
?size:1).
