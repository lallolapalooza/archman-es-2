DESCRIPCIÓ

N

La función freeaddrinfo() liberará una o más estructuras addrinfo devueltas por getaddrinfo(), junto con cualquier almacenamiento adicional asociado con esas estructuras. Si el campo ai_next de la estructura no es nulo, se liberará toda la lista de estructuras. La función freeaddrinfo() deberá soportar la liberación de sublistas arbitrarias de una lista addrinfo devuelta originalmente por getaddrin

fo().

La función getaddrinfo() traducirá el nombre de una ubicación de servicio (por ejemplo, un nombre de host) y/o un nombre de servicio y devolverá un conjunto de direcciones de socket e información asociada para ser usada en la creación de un socket con el que abordar el servicio

especificado.
Not
a:
En muchos casos, está implementada por el S
istema de Nombres de Dominio, como se
documenta en RFC 1034, RFC 1035 y RFC 1886.

Las funciones freeaddrinfo() y getaddrinfo() deberán ser seguras en entornos con hilos (thread-safe)

.

Los argumentos nodename y servname son punteros nulos o punteros a cadenas terminadas por nulo. Uno o ambos de estos dos argumentos deberán ser proporcionados por la aplicación como un puntero no

nulo.

El formato de un nombre válido depende de la familia o familias de dirección. Si no se especifica una familia concreta y el nombre podría interpretarse como válido en múltiples familias soportadas, la implementación intentará resolver el nombre en todas las familias soportadas y, en ausencia de errores, se devolverá uno o más

resultados.

Si el argumento nodename no es nulo, puede ser un nombre descriptivo o una cadena de dirección. Si la familia de dirección especificada es AF_INET, AF_INET6 o AF_UNSPEC, los nombres descriptivos válidos incluyen los nombres de host. Si la familia de dirección especificada es AF_INET o AF_UNSPEC, las cadenas de dirección que usan la notación estándar de Internet especificada en inet_addr() son vá

lidas.

Si la familia de dirección especificada es AF_INET6 o AF_UNSPEC, son válidas las formas de texto estándar de IPv6 descritas en inet_ntop

().

Si nodename no es nulo, la ubicación de servicio solicitada está nombrada por nodename; de lo contrario, la ubicación de servicio solicitada es local al

llamante.

Si servname es nulo, la llamada devolverá direcciones de nivel de red para el nodename especificado. Si servname no es nulo, es una cadena de caracteres terminada por nulo que identifica el servicio solicitado. Este puede ser un nombre descriptivo o una representación numérica adecuada para su uso con la familia o familias de dirección. Si la familia de dirección especificada es AF_INET, AF_INET6 o AF_UNSPEC, el servicio puede especificarse como una cadena que especifique un número de puerto

decimal.

Si el argumento hints no es nulo, se refiere a una estructura que contiene valores de entrada que dirigen la operación proporcionando opciones y limitando la información devuelta a un tipo de socket, familia de dirección y/o protocolo concretos, como se describe a continuación. La aplicación deberá asegurarse de que cada uno de los miembros ai_addrlen, ai_addr, ai_canonname y ai_next, así como cada uno de los miembros adicionales no estándar, si los hay, de esta estructura hints estén inicializados. Si alguno de estos miembros tiene un valor distinto del que resultaría de la inicialización predeterminada, el comportamiento es definido por la implementación. Un valor de AF_UNSPEC para ai_family significa que el llamante aceptará cualquier familia de dirección. Un valor de cero para ai_socktype significa que el llamante aceptará cualquier tipo de socket. Un valor de cero para ai_protocol significa que el llamante aceptará cualquier protocolo. Si hints es un puntero nulo, el comportamiento será como si se refiriera a una estructura que contiene el valor cero para los campos ai_flags, ai_socktype y ai_protocol, y AF_UNSPEC para el campo ai_fa

mily.

El campo ai_flags al que apunta el parámetro hints deberá establecerse en cero o ser el OR inclusivo a nivel de bits de uno o más de los valores AI_PASSIVE, AI_CANONNAME, AI_NUMERICHOST, AI_NUMERICSERV, AI_V4MAPPED, AI_ALL y

AI_ADDRCONFIG.

Si se especifica la bandera AI_PASSIVE, la información de dirección devuelta deberá ser adecuada para su uso en el enlace de un socket para aceptar conexiones entrantes para el servicio especificado. En este caso, si el argumento nodename es nulo, la parte de la dirección IP de la estructura de dirección del socket se establecerá en INADDR_ANY para una dirección IPv4 o en IN6ADDR_ANY_INIT para una dirección IPv6. Si no se especifica la bandera AI_PASSIVE, la información de dirección devuelta deberá ser adecuada para una llamada a connect() (para un protocolo orientado a conexión) o para una llamada a connect(), sendto() o sendmsg() (para un protocolo sin conexión). En este caso, si el argumento nodename es nulo, la parte de la dirección IP de la estructura de dirección del socket se establecerá en la dirección de bucle (loopback). La bandera AI_PASSIVE se ignorará si el argumento nodename no es

nulo.

Si se especifica la bandera AI_CANONNAME y el argumento nodename no es nulo, la función intentará determinar el nombre canónico correspondiente a nodename (por ejemplo, si nodename es un alias o una notación abreviada para un nombre completo)

.
Not
a:
Dado que las diferentes implementaciones usan diferentes modelos conceptuales, los términos «nombre can
ónico» y «alias» no pueden definirse con precisión para el caso general. Sin embargo, se espera q
ue las implementaciones del Sistema de Nombres de Dominio los interpreten tal como se usan en RFC 1034.

Una cadena de dirección de host numérica no es un «nombre» y, por tanto, no tiene una f

orma de «nombre canónico»; no se realiza ninguna traducción de dirección a nombre de hos
t. Véase más abajo el manejo del caso en el que no se puede obtener un nombre canónico.

Si se especifica la bandera AI_NUMERICHOST, entonces la cadena nodename no nula proporcionada deberá ser una cadena de dirección de host numérica. De lo contrario, se devolverá un error [EAI_NONAME]. Esta bandera evitará que se invoque cualquier tipo de servicio de resolución de nombres (por ejemplo, el DNS)

.

Si se especifica la bandera AI_NUMERICSERV, entonces la cadena servname no nula proporcionada deberá ser una cadena de puerto numérica. De lo contrario, se devolverá un error [EAI_NONAME]. Esta bandera evitará que se invoque cualquier tipo de servicio de resolución de nombres (por ejemplo, NIS+)

.

Por defecto, con un ai_family de AF_INET6, getaddrinfo() devolverá solo direcciones IPv6. Si se especifica la bandera AI_V4MAPPED junto con un ai_family de AF_INET6, entonces getaddrinfo() devolverá direcciones IPv6 mapeadas desde IPv4 si no se encuentran direcciones IPv6 coincidentes. La bandera AI_V4MAPPED se ignorará a menos que ai_family sea igual a AF_INET6. Si se usa la bandera AI_ALL con la bandera AI_V4MAPPED, entonces getaddrinfo() devolverá todas las direcciones IPv6 e IPv4 coincidentes. La bandera AI_ALL sin la bandera AI_V4MAPPED se

ignorará.

Si se especifica la bandera AI_ADDRCONFIG, las direcciones IPv4 se devolverán solo si hay una dirección IPv4 configurada en el sistema local, y las direcciones IPv6 se devolverán solo si hay una dirección IPv6 configurada en el sistema

local.

El campo ai_socktype al que apunta el argumento hints especifica el tipo de socket para el servicio, como se define en socket(). Si no se especifica un tipo de socket concreto (por ejemplo, un valor de cero) y el nombre de servicio podría interpretarse como válido con múltiples tipos de socket soportados, la implementación intentará resolver el nombre de servicio para todos los tipos de socket soportados y, en ausencia de errores, se devolverán todos los resultados posibles. Un valor de tipo de socket distinto de cero limitará la información devuelta a valores con el tipo de socket

especificado.

Si el campo ai_family al que apunta hints tiene el valor AF_UNSPEC, se devolverán direcciones para su uso con cualquier familia de dirección que pueda usarse con elespecificado nombre de nodo y/o nombre de servicio. De lo contrario, las direcciones se devolverán para su uso solo con la familia de direcciones especificada. Si ai_family no es AF_UNSPEC y ai_protocol no es cero, entonces las direcciones se devolverán para su uso solo con la familia de direcciones y el protocolo especificados; el valor de ai_protocol se interpretará como en una llamada a la función socket() con los valores correspondientes de ai_family y ai_protoco

l
.

VALOR DE

RETORNO

Un valor de retorno cero para getaddrinfo() indica una finalización exitosa; un valor de retorno distinto de cero indica un fallo. Los valores posibles para los fallos se enumeran en la sección

ERRORES.

Tras el retorno exitoso de getaddrinfo(), la ubicación a la que res apunta hará referencia a una lista enlazada de estructuras addrinfo, cada una de las cuales especificará una dirección de socket y la información para usar al crear un socket con el cual usar esa dirección de socket. La lista incluirá al menos una estructura addrinfo. El campo ai_next de cada estructura contiene un puntero a la siguiente estructura de la lista, o un puntero nulo si es la última estructura de la lista. Cada estructura de la lista incluirá valores para usar con una llamada a la función socket(), y una dirección de socket para usar con la función connect() o, si se especificó la bandera AI_PASSIVE, para usar con la función bind(). Los campos ai_family, ai_socktype y ai_protocol deberán ser utilizables como los argumentos para la función socket() para crear un socket adecuado para usar con la dirección devuelta. Los campos ai_addr y ai_addrlen son utilizables como los argumentos para las funciones connect() o bind() con dicho socket, según la bandera

AI_PASSIVE.

Si nodename no es nulo, y si lo solicita la bandera AI_CANONNAME, el campo ai_canonname de la primera estructura addrinfo devuelta apuntará a una cadena terminada por nulo que contiene el nombre canónico correspondiente al nodename de entrada; si el nombre canónico no está disponible, entonces ai_canonname hará referencia al argumento nodename o a una cadena con el mismo contenido. El contenido del campo ai_flags de las estructuras devueltas es

indefinido.

Todos los campos en las estructuras de dirección de socket devueltas por getaddrinfo() que no se rellenan a través de un argumento explícito (por ejemplo, sin6_flowinfo) se establecerán en

cero.

APLICACIONES

Si el llamador maneja solo TCP y no UDP, por ejemplo, entonces el miembro ai_protocol de la estructura hints debe establecerse en IPPROTO_TCP cuando se llame a getaddrin

fo().

Si el llamador maneja solo IPv4 y no IPv6, entonces el miembro ai_family de la estructura hints debe establecerse en AF_INET cuando se llame a getaddrin

fo().

Aunque es una práctica común inicializar la estructura hints

usando: 
struct addrinfo hi
nts; memset(&hints,
0, sizeof hints);

este método no es portable según este estándar, porque la estructura puede contener miembros de puntero o de punto flotante que no están obligados a tener una representación de todos los bits en cero después de la inicialización predeterminada. Los métodos portables utilizan la inicialización predeterminada; por

ejemplo: 
struct addrinfo hints = { 0
}
;

o

: 
static struct addrinfo
hints_init; struct addri
nfo hints = hints_init;

Una versión futura de este estándar puede requerir que un objeto puntero con una representación de todos los bits en cero sea un puntero nulo, y que addrinfo no tenga ningún miembro de punto flotante si un objeto de punto flotante con una representación de todos los bits en cero no tiene el valor 0.

0.

El término ``nombre canónico'' es engañoso; proviene del Sistema de Nombres de Dominio (RFC 2181). Debe tenerse en cuenta que e

l nombre canónico es el resultado del procesamiento de alias, y no necesariamente un atributo único de un host, una direcci
ón o un conjunto de direcciones. Véase la RFC 2181 para más discusión de esto en el contexto del Sistema de Nombres de Dominio.
