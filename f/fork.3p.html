FORK(3P) Manual del Programador POSIX FORK(3P)

PRÓLOGO

Esta página manual forma parte del Manual del Programador POSIX. La implementación de Linux de esta interfaz puede diferir (consulte la página manual de Linux correspondiente para detalles del comportamiento de Linux), o la interfaz puede no estar implementada en Linux.

NOMBRE

fork — crea un nuevo proceso

SINOPSIS

#include <unistd.h>
pid_t fork(void);

DESCRIPCIÓN

La fork() función creará un nuevo proceso. El nuevo proceso (proceso hijo) será una copia exacta del proceso que la invoca (proceso padre) excepto como se detalla a continuación:

*
El proceso hijo tendrá un ID de proceso único.
*
El ID del proceso hijo tampoco coincidirá con ningún ID de grupo de procesos activo.
*
El proceso hijo tendrá un ID de proceso padre diferente, que será el ID de proceso del proceso que lo invoca.
*
El proceso hijo tendrá su propia copia de los descriptores de archivo del padre. Cada descriptor de archivo del hijo se referirá a la misma descripción de archivo abierto que el descriptor de archivo correspondiente del padre.
*
El proceso hijo tendrá su propia copia de los flujos de directorio abiertos del padre. Cada flujo de directorio abierto en el proceso hijo puede compartir el posicionamiento del flujo de directorio con el flujo de directorio correspondiente del padre.
*
El proceso hijo tendrá su propia copia de los descriptores de catálogo de mensajes del padre.
*
Los valores del proceso hijo de tms_utime, tms_stime, tms_cutime, y tms_cstime se establecerán en 0.
*
El tiempo restante hasta una señal de alarma se restablecerá a cero, y la alarma, si la hay, será cancelada; véase alarm().
*
Todos los valores semadj serán borrados.
*
Los bloqueos de archivo establecidos por el proceso padre no serán heredados por el proceso hijo.
*
El conjunto de señales pendientes para el proceso hijo se inicializará al conjunto vacío.
*
Los temporizadores de intervalo serán restablecidos en el proceso hijo.
*
Cualquier semáforo que esté abierto en el proceso padre también estará abierto en el proceso hijo.
*
El proceso hijo no heredará ningún bloqueo de memoria del espacio de direcciones establecido por el proceso padre mediante llamadas a mlockall() o mlock().
*
Los mapeos de memoria creados en el padre se conservarán en el proceso hijo. Los mapeos MAP_PRIVATE heredados del padre también serán mapeos MAP_PRIVATE en el hijo, y cualquier modificación a los datos en estos mapeos realizada por el padre antes de llamar a fork() será visible para el hijo. Cualquier modificación a los datos en mapeos MAP_PRIVATE realizada por el padre después de que fork() retorne será visible solo para el padre. Las modificaciones a los datos en mapeos MAP_PRIVATE realizadas por el hijo serán visibles solo para el hijo.
*
Para las políticas de planificación SCHED_FIFO y SCHED_RR, el proceso hijo heredará la política y los ajustes de prioridad del proceso padre durante una fork() función. Para otras políticas de planificación, la política y los ajustes de prioridad en fork() están definidos por la implementación.
*
Los temporizadores por proceso creados por el padre no serán heredados por el proceso hijo.
*
El proceso hijo tendrá su propia copia de los descriptores de cola de mensajes del padre. Cada uno de los descriptores de mensaje del hijo se referirá a la misma descripción de cola de mensajes abierta que el descriptor de mensaje correspondiente del padre.
*
Ninguna operación de entrada asíncrona o salida asíncrona será heredada por el proceso hijo. Cualquier uso de bloques de control asíncronos creados por el padre produce un comportamiento indefinido.
*
Se creará un proceso con un solo hilo. Si un proceso multihilo llama a fork(), el nuevo proceso contendrá una réplica del hilo que lo invoca y todo su espacio de direcciones, posiblemente incluyendo los estados de mutexes y otros recursos. En consecuencia, para evitar errores, el proceso hijo solo puede ejecutar operaciones seguras para señales asíncronas hasta que se llame a una de las funciones exec .

Cuando la aplicación llama a fork() desde un manejador de señales y cualquiera de los manejadores de fork registrados por pthread_atfork() llama a una función que no es segura para señales asíncronas, el comportamiento es indefinido.

*
Si tanto la opción Trace como la opción Trace Inherit son soportadas:

Si el proceso que la invoca estaba siendo trazado en un flujo de traza que tenía su política de herencia establecida a POSIX_TRACE_INHERITED, el proceso hijo será trazado en ese flujo de traza, y el proceso hijo heredará el mapeo del padre de nombres de eventos de traza a identificadores de tipo de evento de traza. Si el flujo de traza en el que el proceso que la invoca estaba siendo trazado tenía su política de herencia establecida a POSIX_TRACE_CLOSE_FOR_CHILD, el proceso hijo no será trazado en ese flujo de traza. La política de herencia se establece mediante una llamada a la posix_trace_attr_setinherited() función.

*
Si la opción Trace es soportada, pero la opción Trace Inherit no lo es:

El proceso hijo no será trazado en ninguno de los flujos de traza de su proceso padre.

*
Si la opción Trace es soportada, el proceso hijo de un proceso controlador de traza no controlará los flujos de traza controlados por su proceso padre.
*
El valor inicial del reloj de tiempo de CPU del proceso hijo se establecerá en cero.
*
El valor inicial del reloj de tiempo de CPU del único hilo del proceso hijo se establecerá en cero.

Todas las demás características del proceso definidas por POSIX.1‐2008 serán las mismas en los procesos padre e hijo. La herencia de características del proceso no definidas por POSIX.1‐2008 no está especificada por POSIX.1‐2008.

Después de fork(), tanto el proceso padre como el proceso hijo serán capaces de ejecutarse independientemente antes de que cualquiera de ellos termine.

VALOR DE RETORNO

Tras la finalización exitosa, fork() retornará 0 al proceso hijo y retornará el ID de proceso del hijo al proceso padre. Ambos procesos continuarán ejecutándose desde la fork() función. De lo contrario, se retornará -1 al proceso padre, no se creará ningún proceso hijo, y errno se establecerá para indicar el error.

ERRORES

La fork() función fallará si:

EAGAIN
El sistema carecía de los recursos necesarios para crear otro proceso, o se excedería el límite impuesto por el sistema sobre el número total de procesos en ejecución en todo el sistema o por un solo usuario {CHILD_MAX}.

La fork() función puede fallar si:

ENOMEM
No hay suficiente espacio de almacenamiento disponible.

JUSTIFICACIÓN

Muchas implementaciones históricas tienen ventanas de tiempo donde una señal enviada a un grupo de procesos (por ejemplo, un SIGINT interactivo) justo antes o durante la ejecución de fork() se entrega al padre después de la fork() pero no al hijo porque el fork() código borra el conjunto de señales pendientes del hijo. Este volumen de POSIX.1‐2017 no requiere, ni siquiera permite, este comportamiento. Sin embargo, es pragmático esperar que problemas de esta naturaleza puedan continuar existiendo en implementaciones que parecen conformarse a este volumen de POSIX.1‐2017 y pasar las suites de verificación disponibles. Este comportamiento es solo una consecuencia de la implementación al no hacer que el intervalo entre la generación de la señal y su entrega sea totalmente invisible. Desde el punto de vista de la aplicaciónn's perspective, a fork () call should appear atomic. A signal that is generated prior to the fork () should be delivered prior to the fork (). A signal sent to the process group after the fork () should be delivered to both parent and child. The implementation may actually initialize internal data structures corresponding to the child's set of pending signals to include signals sent to the process group during the fork (). Since the fork () call can be considered as atomic from the application's perspective, the set would be initialized as empty and such signals would have arrived after the for

Although it is not recommended for this purpose, such an error would be an allowable extension for an implementation. The [ENOMEM] error value is reserved for those implementations that detect and distinguish such a condition. The only objection anticipated to the phrase ``executing independently'' is testability, but this assertion should be testable. Such tests require that both the parent and child can block on a detectable action of the other, such as a write to a pipe or a signal. An interactive exchange of such actions should be possible for the system to conform to the intent of this volume of POSIX.1‐2017. The [EAGAIN

Whether it occurs or not is not in any practical sense under the control of the application because the condition is usually a consequence of the user's use of the system, not of the application's code. Thus, no application can or should rely upon its occurrence under any circumstances, nor should the exact semantics of what concept of ``user'' is used be of concern to the application developer. Validation writers should be cognizant of this limitation. There are two reasons why POSIX programmers call fork (). One reason is to create a new thread of control within the same program (which was originally only possible in POSIX by creating a new process); the other is to create a new process running a different program. In the latter case, the call to fork () is soon followed by a call to one of the exe

c

functions. The general problem with making fork () work in a multi-threaded world is what to do with all of the threads. There are two alternatives. One is to copy all of the threads into the new process. This causes the programmer or implementation to deal with threads that are suspended on system calls or that might be about to execute system calls that should not be executed in the new process. The other alternative is to copy only the thread that calls fork (). This creates the difficulty that the state of process-local resources is usually held in process memory. If a thread that is not calling fork () holds a resource, that resource is never released in the child process because the thread whose job it is to release the resource does not exist in the child process. When a programmer is writing a multi-threaded program, the first described

use of

fork (), creating new threads in the same program, is provided by the pthread_create () function. The

fork

() function is thus used only to run new programs, and the effects of calling functions that require certain resources between the call to fork () and the call to an exec function are undefined. The addition of the forkall () function to the standard was considered and rejected. The forkall () function lets all the threads in the parent be duplicated in the child. This essentially duplicates the state of the parent in the child. This allows threads in the child to continue processing and allows locks and the state to be preserved without explicit pthread_atfork () code. The calling process has to ensure that the threads processing state that is shared between the parent and child (that is, file descriptors or

If this is not desired behavior, the parent process has to synchronize with such threads before calling forkall (). While the fork () function is async-signal-safe, there is no way for an implementation to determine whether the fork handlers established by pthread_atfork () are async-signal-safe. The fork handlers may attempt to execute portions of the implementation that are not async-signal-safe, such as those that are protected by mutexes, leading to a deadlock condition.
