DESCRIPCIÓ

N

La llamada al sistema futex() proporciona un método para esperar hasta que una cierta condición se cumpla. Se utiliza típicamente como una construcción bloqueante en el contexto de la sincronización de memoria compartida. Al usar futexes, la mayoría de las operaciones de sincronización se realizan en el espacio de usuario. Un programa en espacio de usuario emplea la llamada al sistema futex() solo cuando es probable que el programa tenga que bloquearse durante un tiempo prolongado hasta que la condición se cumpla. Otras operaciones de futex() se pueden usar para despertar a cualquier proceso o hilo que esté esperando una condición

particular.

Un futex es un valor de 32 bits—referido a continuación como una palabra futex—cuya dirección se proporciona a la llamada al sistema futex(). (Los futexes tienen un tamaño de 32 bits en todas las plataformas, incluidos los sistemas de 64 bits.) Todas las operaciones de futex están gobernadas por este valor. Para compartir un futex entre procesos, el futex se coloca en una región de memoria compartida, creada usando (por ejemplo) mmap(2) o shmat(2). (Por lo tanto, la palabra futex puede tener diferentes direcciones virtuales en diferentes procesos, pero estas direcciones se refieren todas a la misma ubicación en la memoria física.) En un programa multihilo, es suficiente colocar la palabra futex en una variable global compartida por todos los

hilos.

Al ejecutar una operación de futex que solicita bloquear un hilo, el núcleo solo se bloqueará si la palabra futex tiene el valor que el hilo llamador proporcionó (como uno de los argumentos de la llamada futex()) como el valor esperado de la palabra futex. La carga del valor de la palabra futex, la comparación de ese valor con el valor esperado y el bloqueo real ocurrirán de forma atómica y estarán totalmente ordenados con respecto a las operaciones concurrentes realizadas por otros hilos en la misma palabra futex. Por lo tanto, la palabra futex se usa para conectar la sincronización en el espacio de usuario con la implementación del bloqueo por parte del núcleo. De manera análoga a una operación atómica de comparación e intercambio que potencialmente cambia la memoria compartida, el bloqueo a través de un futex es una operación atómica de comparación y

bloqueo.

Un uso de los futexes es para implementar bloqueos. El estado del bloqueo (es decir, adquirido o no adquirido) se puede representar como un indicador de acceso atómico en la memoria compartida. En el caso sin contención, un hilo puede acceder o modificar el estado del bloqueo con instrucciones atómicas, por ejemplo, cambiándolo atómicamente de no adquirido a adquirido usando una instrucción atómica de comparación e intercambio. (Tales instrucciones se realizan completamente en modo usuario, y el núcleo no mantiene información sobre el estado del bloqueo.) Por otro lado, un hilo puede no poder adquirir un bloqueo porque ya está adquirido por otro hilo. Luego puede pasar el indicador del bloqueo como una palabra futex y el valor que representa el estado adquirido como el valor esperado a una operación de espera de futex(). Esta operación de futex() se bloqueará si y solo si el bloqueo sigue adquirido (es decir, el valor en la palabra futex todavía coincide con el "estado adquirido"). Al liberar el bloqueo, un hilo tiene que primero restablecer el estado del bloqueo a no adquirido y luego ejecutar una operación de futex que despierte a los hilos bloqueados en el indicador del bloqueo usado como palabra futex (esto se puede optimizar aún más para evitar despertares innecesarios). Vea futex(7) para más detalles sobre cómo usar

futexes.

Además de la funcionalidad básica de futex de espera y despertar, existen más operaciones de futex destinadas a soportar casos de uso más

complejos.

Tenga en cuenta que no es necesaria ninguna inicialización o destrucción explícita para usar futexes; el núcleo mantiene un futex (es decir, el artefacto de implementación interno del núcleo) solo mientras se realizan operaciones como FUTEX_WAIT(2const) en una palabra futex

particular.

Futexes de herencia de

prioridad

Linux soporta futexes de herencia de prioridad (PI) para manejar problemas de inversión de prioridad que pueden encontrarse con bloqueos de futex normales. La inversión de prioridad es el problema que ocurre cuando una tarea de alta prioridad está bloqueada esperando adquirir un bloqueo mantenido por una tarea de baja prioridad, mientras que las tareas de prioridad intermedia preemption continuamente a la tarea de baja prioridad de la CPU. En consecuencia, la tarea de baja prioridad no avanza hacia la liberación del bloqueo, y la tarea de alta prioridad permanece

bloqueada.

La herencia de prioridad es un mecanismo para lidiar con el problema de la inversión de prioridad. Con este mecanismo, cuando una tarea de alta prioridad se bloquea por un bloqueo mantenido por una tarea de baja prioridad, la prioridad de la tarea de baja prioridad se eleva temporalmente a la de la tarea de alta prioridad, de modo que no sea preemptionada por ninguna tarea de nivel intermedio, y así pueda avanzar hacia la liberación del bloqueo. Para ser efectiva, la herencia de prioridad debe ser transitiva, lo que significa que si una tarea de alta prioridad se bloquea en un bloqueo mantenido por una tarea de prioridad más baja que a su vez está bloqueada por un bloqueo mantenido por otra tarea de prioridad intermedia (y así sucesivamente, para cadenas de longitud arbitraria), entonces ambas de esas tareas (o más generalmente, todas las tareas en una cadena de bloqueos) tienen su priori futex(2)

NAME

futex - fast userspace mutex

SYNOPSIS

#include <linux/futex.h>
#include <sys/syscall.h>
#include <unistd.h>
#include <stdatomic.h>
#include <stdint.h>
#include <sys/time.h>

long futex(uint32_t *uaddr, int op, uint32_t val,
           const struct timespec *timeout, uint32_t *uaddr2, uint32_t val3);

long syscall(SYS_futex, uint32_t *uaddr, int op, uint32_t val,
             const struct timespec *timeout, uint32_t *uaddr2, uint32_t val3);

DESCRIPTION

A futex (Fast Userspace MuTex) is a Linux-specific mechanism for interprocess communication. It allows user-space programs to implement synchronization primitives (like mutexes and semaphores) efficiently. The kernel is involved only when a thread needs to wait for a condition to be met (e.g., a mutex to be unlocked). Otherwise, the synchronization is performed entirely in user space using atomic operations.

The primary goal of futexes is to avoid the overhead of system calls for uncontended operations. When a synchronization primitive is not contended (i.e., the resource being protected is available), operations on it complete entirely in user space using atomic instructions (like compare-and-swap). A system call is only made when a thread tries to acquire a resource that is already held, or tries to access a resource that has already been released and potentially signaled.

The futex(2) system call is a low-level interface. It takes an address uaddr pointing to a 32-bit integer (the "futex word") in user space, an operation op, and various arguments depending on the operation.

The values in the futex word are interpreted as follows:

•
A value of 0 typically means the lock/mutex is available.
•
A non-zero value typically indicates that the lock/mutex is held. The value itself often encodes the ID of the owner thread.

The system call is used for the following basic operations:

•
FUTEX_WAIT: If the value at uaddr is equal to val, then the calling thread blocks (sleeps) until the futex word changes its value or the optional timeout expires. The kernel maintains a list of threads waiting on a specific futex address. If the value at uaddr is not equal to val, the call returns immediately with the error EAGAIN.
•
FUTEX_WAKE: Wake up at most val threads that are currently waiting on the futex word at uaddr. The kernel checks the value at uaddr, and if it matches the value provided in the (unused, historically) val3 argument (which is 0 for FUTEX_WAKE), it wakes up the threads. If the value does not match, no threads are woken. The FUTEX_WAKE operation returns the number of threads that were woken.
•
FUTEX_FD: Associates a file descriptor with the futex word. This is used for implementing timers and other event-driven mechanisms. Not typically used directly by application developers.
•
FUTEX_REQUEUE: A more complex operation that allows waking some threads from one futex and requeuing the rest onto another futex. This is used for implementing more sophisticated synchronization primitives.

In addition to these basic operations, Linux provides support for priority-inheritance (PI) futexes. PI futexes are designed to work with real-time threads and ensure that high-priority threads do not suffer from priority inversion when waiting for locks held by low-priority threads.

A PI-aware futex requires cooperation between user space and the kernel. The kernel manages a real-time mutex (RT-mutex) internally when a PI futex is used and threads are blocked. The futex word itself encodes information about the lock's state, including whether it's locked, who the owner is, and whether there are waiters.

From a user-space perspective, what makes a futex PI-aware is a policy agreement (described below) between user space and the kernel about the value of the futex word, coupled with the use of the PI-futex operations described below. (Unlike the other futex operations described above, the PI-futex operations are designed for the implementation of very specific IPC mechanisms.)

The PI-futex operations described below differ from the other futex operations in that they impose policy on the use of the value of the futex word:

•
If the lock is not acquired, the futex word's value shall be 0.
•
If the lock is acquired, the futex word's value shall be the thread ID (TID; see gettid(2)) of the owning thread.
•
If the lock is owned and there are threads contending for the lock, then the FUTEX_WAITERS bit shall be set in the futex word's value; in other words, this value is:

FUTEX_WAITERS | TID

(Note that is invalid for a PI futex word to have no owner and FUTEX_WAITERS set.)

With this policy in place, a user-space application can acquire an unacquired lock or release a lock using atomic instructions executed in user mode (e.g., a compare-and-swap operation such as cmpxchg on the x86 architecture). Acquiring a lock simply consists of using compare-and-swap to atomically set the futex word's value to the caller's TID if its previous value was 0. Releasing a lock requires using compare-and-swap to set the futex word's value to 0 if the previous value was the expected TID.

If a futex is already acquired (i.e., has a nonzero value), waiters must employ the FUTEX_LOCK_PI(2const) or FUTEX_LOCK_PI2(2const) operations to acquire the lock. If other threads are waiting for the lock, then the FUTEX_WAITERS bit is set in the futex value; in this case, the lock owner must employ the FUTEX_UNLOCK_PI(2const) operation to release the lock.

In the cases where callers are forced into the kernel (i.e., required to perform a futex() call), they then deal directly with a so-called RT-mutex, a kernel locking mechanism which implements the required priority-inheritance semantics. After the RT-mutex is acquired, the futex value is updated accordingly, before the calling thread returns to user space.

It is important to note that the kernel will update the futex word's value prior to returning to user space. (This prevents the possibility of the futex word's value ending up in an invalid state, such as having an owner but the value being 0, or having waiters but not having the FUTEX_WAITERS bit set.)

If a futex has an associated RT-mutex in the kernel (i.e., there are blocked waiters) and the owner of the futex/RT-mutex dies unexpectedly, then the kernel cleans up the RT-mutex and hands it over to the next waiter. This in turn requires that the user-space value is updated accordingly. To indicate that this is required, the kernel sets the FUTEX_OWNER_DIED bit in the futex word along with the thread ID of the new owner. User space can detect this situation via the presence of the FUTEX_OWNER_DIED bit and is then responsible for cleaning up the stale state left over by the dead owner.

PI futexes are operated on by specifying one of the values listed below in op. Note that the PI futex operations must be used as paired operations and are subject to some additional requirements:

•
FUTEX_LOCK_PI(2const), FUTEX_LOCK_PI2(2const), and FUTEX_TRYLOCK_PI(2const) pair with FUTEX_UNLOCK_PI(2const). FUTEX_UNLOCK_PI(2const) must be called only on a futex owned by the calling thread, as defined by the value policy, otherwise the error EPERM results.
•
FUTEX_WAIT_REQUEUE_PI(2const) pairs with FUTEX_CMP_REQUEUE_PI(2const). This must be performed from a non-PI futex to a distinct PI futex (or the error EINVAL results). Additionally, the number of waiters to be woken must be 1 (or the error EINVAL results).

The PI futex operations are as follows:

FUTEX_LOCK_PI(2const)
FUTEX_LOCK_PI2(2const)
FUTEX_TRYLOCK_PI(2const)
FUTEX_UNLOCK_PI(2const)
FUTEX_CMP_REQUEUE_PI(2const)
FUTEX_WAIT_REQUEUE_PI(2const)

The FUTEX_WAIT_REQUEUE_PI(2const) and FUTEX_CMP_REQUEUE_PI(2const) were added to support a fairly specific use case: support for priority-inheritance-aware POSIX threads condition variables. The idea is that these operations should always be paired, in order to ensure that user space and the kernel remain in sync. Thus, in the FUTEX_WAIT_REQUEUE_PI(2const) operation, the user-space application pre-specifies the target of the requeue that takes place in the FUTEX_CMP_REQUEUE_PI(2const) operation.

RETURN VALUE

On error, -1 is returned, and errno is set to indicate the error.

The return value on success depends on the operation.

ERRORS

EACCES
No read access to the memory of a futex word.
EFAULT
uaddr did not point to a valid user-space address.
EINVAL
uaddr does not point to a valid object—that is, the address is not four-byte-aligned.
EINVAL
Invalid argument.
ENOSYS
Invalid operation specified in op.
ENOSYS
The FUTEX_CLOCK_REALTIME option was specified in op, but the accompanying operation was neither FUTEX_WAIT_BITSET(2const), FUTEX_WAIT_REQUEUE_PI(2const), nor FUTEX_LOCK_PI2(2const).

Program source

/* futex_demo.c
   Usage: futex_demo [nloops]
                    (Default: 5)
   Demonstrate the use of futexes in a program where parent and child
   use a pair of futexes located inside a shared anonymous mapping to
   synchronize access to a shared resource: the terminal.  The two
   processes each write 'num-loops' messages to the terminal and employ
   a synchronization protocol that ensures that they alternate in
   writing messages.
*/
#define _GNU_SOURCE
#include <err.h>
#include <errno.h>
#include <linux/futex.h>
#include <stdatomic.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/mman.h>
#include <sys/syscall.h>
#include <sys/wait.h>
#include <unistd.h>
static uint32_t *futex1, *futex2, *iaddr;
static int
futex(uint32_t *uaddr, int op, uint32_t val,
      const struct timespec *timeout, uint32_t *uaddr2, uint32_t val3)
{
    return syscall(SYS_futex, uaddr, op, val,
                   timeout, uaddr2, val3);
}
/* Acquire the futex pointed to by 'futexp': wait for its value to
   become 1, and then set the value to 0.  */
static void
fwait(uint32_t *futexp)
{
    long            s;
    const uint32_t  one = 1;
    /* atomic_compare_exchange_strong(ptr, oldval, newval)
       atomically performs the equivalent of:
           if (*ptr == *oldval)
               *ptr = newval;
       It returns true if the test yielded true and *ptr was updated.  */
    while (1) {
        /* Is the futex available? */
        if (atomic_compare_exchange_strong(futexp, &one, 0))
            break;      /* Yes */
        /* Futex is not available; wait.  */
        s = futex(futexp, FUTEX_WAIT, 0, NULL, NULL, 0);
        if (s == -1 && errno != EAGAIN)
            err(EXIT_FAILURE, "futex-FUTEX_WAIT");
    }
}
/* Release the futex pointed to by 'futexp': if the futex currently
   has the value 0, set its value to 1 and then wake any futex waiters,
   so that if the peer is blocked in fwait(), it can proceed.  */
static void
fpost(uint32_t *futexp)
{
    long            s;
    const uint32_t  zero = 0;
    /* atomic_compare_exchange_strong() was described
       in comments above.  */
    if (atomic_compare_exchange_strong(futexp, &zero, 1)) {
        s = futex(futexp, FUTEX_WAKE, 1, NULL, NULL, 0);
        if (s  == -1)
            err(EXIT_FAILURE, "futex-FUTEX_WAKE");
    }
}
int
main(int argc, char *argv[])
{
    pid_t         childPid;
    unsigned int  nloops;
    setbuf(stdout, NULL);
    nloops = (argc > 1) ? atoi(argv[1]) : 5;
    /* Create a shared anonymous mapping that will hold the futexes.
       Since the futexes are being shared between processes, */
    /* the mapping must be created with the MAP_SHARED flag. */
    /* We allocate space for two futexes (futex1, futex2) and */
    /* one integer (iaddr) to act as a counter. */
    struct {
        uint32_t futex1;
        uint32_t futex2;
        uint32_t counter;
    } *shared;
    shared = mmap(NULL, sizeof(*shared), PROT_READ | PROT_WRITE,
                  MAP_SHARED | MAP_ANONYMOUS, -1, 0);
    if (shared == MAP_FAILED)
        err(EXIT_FAILURE, "mmap");
    /* Initialize the futexes and counter. */
    shared->futex1 = 0;
    shared->futex2 = 1; /* Start with futex2 available (value 1) */
    shared->counter = 0;
    futex1 = &(shared->futex1);
    futex2 = &(shared->futex2);
    iaddr = &(shared->counter);
    /* Create a child process. */
    childPid = fork();
    if (childPid == -1)
        err(EXIT_FAILURE, "fork");
    if (childPid == 0) { /* Child process */
        for (unsigned int j = 0; j < nloops; j++) {
            /* Wait for futex1 to become available (value 1), */
            /* then acquire it (set to 0). */
            fwait(futex1);
            /* Increment the shared counter and print message. */
            printf("Child  (%5d) %u\n", gettid(), *iaddr);
            (*iaddr)++;
            /* Release futex2 (set to 1) and wake one waiter. */
            fpost(futex2);
        }
        exit(EXIT_SUCCESS);
    } else { /* Parent process */
        for (unsigned int j = 0; j < nloops; j++) {
            /* Wait for futex2 to become available (value 1), */
            /* then acquire it (set to 0). */
            fwait(futex2);
            /* Increment the shared counter and print message. */
            printf("Parent (%5d) %u\n", gettid(), *iaddr);
            (*iaddr)++;
            /* Release futex1 (set to 1) and wake one waiter. */
            fpost(futex1);
        }
        /* Wait for the child process to terminate. */
        if (waitpid(childPid, NULL, 0) == -1)
            err(EXIT_FAILURE, "waitpid");
    }
    /* Unmap the shared memory region. */
    if (munmap(shared, sizeof(*shared)) == -1)
        err(EXIT_FAILURE, "munmap");
    exit(EXIT_SUCCESS);
}

futex(2) — Linux manual page

NAME

futex, futex_wait, futex_wake, futex_wait_robust, futex_wake_robust — Fast Userspace Mutexes

LIBRARY

libpthread, and in Linux kernel versions before 5.17, also available directly from the kernel via syscalls.

SYNOPSIS

#include <linux/futex.h>
int futex(int *uaddr, int op, int val, const struct timespec *timeout, int *uaddr2, int val3);
int futex_wait(int *uaddr, int val, const struct timespec *timeout);
int futex_wake(int *uaddr, int num_wakeup);
int futex_wait_robust(int *uaddr, int val, const struct timespec *timeout);
int futex_wake_robust(int *uaddr, int num_wakeup);

DESCRIPTION

The futex() system call provides a generic interface for implementing various synchronization primitives. The core idea is to allow user-space programs to perform atomic operations and, if the operation fails, to put the calling thread to sleep efficiently without involving the kernel more than necessary. The term "futex" stands for "Fast Userspace Mutex".

The futex() system call takes six arguments:

uaddr
A pointer to an integer in user space. This integer represents the state of the synchronization primitive. The exact meaning of the integer values depends on the op argument.
op
The operation to perform. This is a bitmask that specifies the operation and can include flags. Key operations include:
  • FUTEX_WAIT: If the value at uaddr is equal to val, the calling thread sleeps until the futex is woken up by a FUTEX_WAKE operation. If the value at uaddr is not equal to val, the call returns immediately.
  • FUTEX_WAKE: Wakes up at least one thread sleeping on the futex specified by uaddr. The number of threads to wake up is specified by val3 (or val in older interfaces).
  • FUTEX_PRIVATE_WAIT and FUTEX_PRIVATE_WAKE: These operations work on futexes that are private to the process (i.e., not shared between processes).
  • FUTEX_WAIT_BITSET: Similar to FUTEX_WAIT, but uses a bitmask to determine when to wake up.
  • FUTEX_WAKE_BITSET: Similar to FUTEX_WAKE, but wakes up threads based on a bitmask.
val
The value to compare against the integer at uaddr for FUTEX_WAIT operations. For FUTEX_WAKE operations, it specifies the maximum number of threads to wake up (in older interfaces).
timeout
A pointer to a struct timespec specifying the maximum time to wait. If timeout is NULL, the wait is indefinite. If timeout->tv_sec and timeout->tv_nsec are both zero, the call returns immediately if the futex is not yet available.
uaddr2
Used for operations like FUTEX_REQUEUE, which allows transferring waiters from one futex to another.
val3
Used for operations like FUTEX_WAKE to specify the number of waiters to wake up. Also used for FUTEX_WAIT_BITSET and FUTEX_WAKE_BITSET.

The functions futex_wait() and futex_wake() are simplified wrappers around the futex() system call. They are typically provided by the C library (libpthread) to implement synchronization primitives like mutexes and condition variables.

FUTEX_WAIT and FUTEX_WAKE are the "shared" futex operations, meaning they can be used to synchronize between different processes. FUTEX_PRIVATE_WAIT and FUTEX_PRIVATE_WAKE are designed for synchronization within a single process and may have different semantics or performance characteristics.

The _ROBUST variants (futex_wait_robust, futex_wake_robust) are related to robust futex handling, which ensures that locks are properly released even if a process terminates abnormally.

RETURN VALUE

On success, futex(), futex_wait(), and futex_wake() return the number of threads woken up. For FUTEX_WAIT operations, a return value of 0 indicates that the timeout expired or the futex value did not match.

On error, these calls return -1, and errno is set to indicate the error.

ERRORS

The specific errors depend on the operation performed. Common errors include:

EAGAIN
The futex value did not match the expected value (for FUTEX_WAIT).
EINTR
The wait was interrupted by a signal.
EINVAL
Invalid arguments were provided.
ENOMEM
Out of memory.
EWOULDBLOCK
Similar to EAGAIN, indicating the operation would block.

STANDARDS

These system calls are Linux-specific.

HISTORY

The futex system call was introduced in Linux kernel 2.5.7.

EXAMPLES

The following example demonstrates a simple producer-consumer scenario using futexes to synchronize two processes.

/*
 * This program demonstrates the use of futexes for inter-process synchronization.
 * It creates a shared memory region containing two futexes: one for the parent
 * (futex1) and one for the child (futex2). The parent acts as a producer and
 * the child as a consumer. They take turns accessing a shared resource (simulated
 * by printing a message and a counter).
 *
 * Compile with: gcc -o futex_example futex_example.c -lrt -pthread
 */
#include <err.h>
#include <errno.h>
#include <fcntl.h>
#include <inttypes.h>
#include <linux/futex.h>
#include <poll.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/mman.h>
#include <sys/syscall.h>
#include <sys/types.h>
#include <sys/wait.h>
#include <time.h>
#include <unistd.h>

/*
 * Helper function to wait on a futex.
 * Equivalent to: futex(futex_addr, FUTEX_WAIT, expected_value, NULL, NULL, 0);
 */
static inline int
fwait(int *futex_addr)
{
    return syscall(SYS_futex, futex_addr, FUTEX_WAIT, 0, NULL, NULL, 0);
}

/*
 * Helper function to wake up a futex waiter.
 * Equivalent to: futex(futex_addr, FUTEX_WAKE, 1, NULL, NULL, 0);
 */
static inline int
fpost(int *futex_addr)
{
    return syscall(SYS_futex, futex_addr, FUTEX_WAKE, 1, NULL, NULL, 0);
}

int
main(int argc, char *argv[])
{
    unsigned int nloops;
    int *futex1, *futex2;
    int *iaddr;
    pid_t childPid;

    if (argc != 2) {
        fprintf(stderr, "Usage: %s <num-loops>\n", argv[0]);
        exit(EXIT_FAILURE);
    }

    nloops = atoi(argv[1]);

    /* Create a shared anonymous memory mapping. This mapping will be inherited
       by the child process. We use it to store two futex variables.
       We use the "shared" futex operations (i.e., not the ones suffixed
       "_PRIVATE").  */
    iaddr = mmap(NULL, sizeof(*iaddr) * 2, PROT_READ | PROT_WRITE,
                 MAP_ANONYMOUS | MAP_SHARED, -1, 0);
    if (iaddr == MAP_FAILED)
        err(EXIT_FAILURE, "mmap");
    futex1 = &iaddr[0];
    futex2 = &iaddr[1];
    *futex1 = 0;        /* State: unavailable */
    *futex2 = 1;        /* State: available */
    /* Create a child process that inherits the shared anonymous
       mapping.  */
    childPid = fork();
    if (childPid == -1)
        err(EXIT_FAILURE, "fork");
    if (childPid == 0) {        /* Child */
        for (unsigned int j = 0; j < nloops; j++) {
            fwait(futex1);
            printf("Child  (%jd) %u\n", (intmax_t) getpid(), j);
            fpost(futex2);
        }
        exit(EXIT_SUCCESS);
    }
    /* Parent falls through to here.  */
    for (unsigned int j = 0; j < nloops; j++) {
        fwait(futex2);
        printf("Parent (%jd) %u\n", (intmax_t) getpid(), j);
        fpost(futex1);
    }
    wait(NULL);
    exit(EXIT_SUCCESS);
}
