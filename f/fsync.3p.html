DESCRIPCIÓ

N

La función fsync() debe solicitar que todos los datos del descriptor de archivo abierto indicado por fildes se transfieran al dispositivo de almacenamiento asociado con el archivo descrito por fildes. La naturaleza de la transferencia está definida por la implementación. La función fsync() no debe retornar hasta que el sistema haya completado esa acción o hasta que se detecte un

error.

Si _POSIX_SYNCHRONIZED_IO está definido, la función fsync() debe forzar que todas las operaciones de E/S actualmente en cola asociadas con el archivo indicado por el descriptor de archivo fildes pasen al estado de finalización de E/S sincronizada. Todas las operaciones de E/S deben

completarse según lo definido para la finalización
de integridad de archivos de E/S sincronizada.

APLICACIONES

La función fsync() debe ser usada por programas que requieren que las modificaciones a un archivo se completen antes de continuar; por ejemplo, un programa que contiene un

a funcionalidad simple de transacciones podría usarla para asegurar que todas las m
odificaciones a un archivo o archivos causadas por una transacción sean registradas.

JUSTIFICACIÓ

N

La función fsync() está destinada a forzar una escritura física de datos desde la caché de búfer, y a asegurar que después de un fallo del sistema u otro fallo, todos los datos hasta el momento de la llamada a fsync() estén registrados en el disco. Dado que los conceptos de ``caché de búfer'', ``fallo del sistema'', ``escritura física'' y ``almacenamiento no volátil'' no están definidos aquí, la redacción debe ser más

abstracta.

Si _POSIX_SYNCHRONIZED_IO no está definido, la redacción depende en gran medida del documento de conformidad para decirle al usuario qué se puede esperar del sistema. Está explícitamente previsto que se permita una implementación nula. Esto podría ser válido en el caso donde el sistema no puede asegurar almacenamiento no volátil bajo ninguna circunstancia, o cuando el sistema es altamente tolerante a fallos y la funcionalidad no es requerida. En el punto medio entre estos extremos, fsync() podría o no causar realmente que los datos se escriban donde estén a salvo de un fallo de energía. El documento de conformidad debe identificar al menos que existe una configuración (y cómo obtener esa configuración) donde esto puede asegurarse para al menos algunos archivos que el usuario puede seleccionar para usar para datos críticos. No se pretende que se requiera una lista exhaustiva, sino que se proporcione información suficiente para que, si se necesitan guardar datos críticos, el usuario pueda determinar cómo debe configurarse el sistema para permitir que los datos se escriban en almacenamiento no

volátil.

Es razonable afirmar que los aspectos clave de fsync() son irrazonables de probar en una suite de pruebas. Eso no hace que la función sea menos valiosa, solo más difícil de probar. Una prueba formal de conformidad probablemente debería forzar un fallo del sistema (apagado de energía) durante la prueba para esta condición, pero debe hacerse de tal manera que las pruebas automatizadas no requieran hacer esto excepto cuando se esté haciendo un registro formal de los resultados. Tampoco sería irrazonable omitir las pruebas para fsync(), permitiendo que se trate como un

problema de calid
ad de implementación.
