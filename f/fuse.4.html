DESCRIPCIÓ

N

Este dispositivo es la interfaz principal entre el controlador del sistema de archivos FUSE y un proceso en espacio de usuario que desea proporcionar el sistema de archivos (referido en el resto de esta página man como el demonio del sistema de archivos). Esta página man está destinada a aquellos interesados en comprender la interfaz del propio kernel. Quienes implementan un sistema de archivos FUSE pueden desear hacer uso de una biblioteca en espacio de usuario como libfuse que abstrae la interfaz de bajo

nivel.

En su núcleo, FUSE es un protocolo simple cliente-servidor, en el que el kernel de Linux es el cliente y el demonio es el servidor. Después de obtener un descriptor de archivo para este dispositivo, el demonio puede leer(2) solicitudes de ese descriptor de archivo y se espera que escriba(2) sus respuestas. Es importante señalar que un descriptor de archivo está asociado con un sistema de archivos FUSE único. En particular, abrir una segunda copia de este dispositivo no permitirá acceder a los recursos creados a través del primer descriptor de archivo (y viceversa)

.

El protocolo

básico

Cada mensaje que es leído por el demonio comienza con una cabecera descrita por la siguiente

estructura: 


struct fuse_in_header {
    uint32_t len;       /* Tamaño total de los datos,
                           incluyendo esta cabecera */
    uint32_t opcode;    /* El tipo de operación (ver más abajo) */
    uint64_t unique;    /* Un identificador único para esta solicitud */
    uint64_t nodeid;    /* ID del objeto del sistema de archivos
                           sobre el que se está operando */
    uint32_t uid;       /* UID del proceso solicitante */
    uint32_t gid;       /* GID del proceso solicitante */
    uint32_t pid;       /* PID del proceso solicitante */
    uint32_t padding;
}
;

La cabecera es seguida por una porción de datos de tamaño variable (que puede estar vacía) específica de la operación solicitada (la operación solicitada es indicada por opcod

e).

El demonio debería entonces procesar la solicitud y —si aplica— enviar una respuesta (casi todas las operaciones requieren una respuesta; si no lo hacen, esto está documentado más abajo), realizando una escritura(2) al descriptor de archivo. Todas las respuestas deben comenzar con la siguiente

cabecera: 


struct fuse_out_header {
    uint32_t len;       /* Tamaño total de los datos escritos al
                           descriptor de archivo */
    int32_t  error;     /* Cualquier error que haya ocurrido (0 si no hay ninguno) */
    uint64_t unique;    /* El valor de la
                           solicitud correspondiente */
}
;

Esta cabecera también es seguida por datos de tamaño variable (potencialmente vacíos) dependiendo de la solicitud ejecutada. Sin embargo, si la respuesta es una respuesta de error (es decir, error está establecido), entonces no se debe enviar más

datos de carga útil, indepen
dientemente de la solicitud.

intercambiados

Esta sección debería contener la documentación para cada uno de los mensajes en el protocolo. Esta página man está actualmente incompleta, por lo que no todos los mensajes están documentados. Para cada mensaje, primero se da la struct enviada por el kernel, seguida de una descripción de la semántica del

FUSE_IN

struct fuse_init_in {
    uint32_t major;
    uint32_t minor;
    uint32_t max_readahead; /* Desde protocolo v7.6 */
    uint32_t flags;         /* Desde protocolo v7.6
*/ };
Esta es la primera solicitud enviada por el kernel al demonio. Se utiliza para negociar la versión del protocolo y otros parámetros del sistema de archivos. Tenga en cuenta que la versión del protocolo puede afectar la disposición de cualquier estructura en el protocolo (incluyendo esta estructura). El demonio debe por tanto recordar la versión y los flags negociados para cada sesión. A la fecha de escritura de esta página man, la versión de protocolo de kernel más alta soportada es 7.2
6.
Los usuarios deben ser conscientes de que las descripciones en esta página man pueden estar incompletas o ser incorrectas para versiones de protocolo más antiguas o más
recientes.
La respuesta para esta solicitud tiene el siguiente
formato: 

struct fuse_init_out {
    uint32_t major;
    uint32_t minor;
    uint32_t max_readahead;   /* Desde v7.6 */
    uint32_t flags;           /* Desde v7.6; algunos bits de flags
                                 se introdujeron más tarde */
    uint16_t max_background;  /* Desde v7.13 */
    uint16_t congestion_threshold;  /* Desde v7.13 */
    uint32_t max_write;       /* Desde v7.5 */
    uint32_t time_gran;       /* Desde v7.6 */
    uint32_t unused[9]
; };
Si la versión mayor soportada por el kernel es mayor que la soportada por el demonio, la respuesta consistirá únicamente en uint32_t major (siguiendo la cabecera habitual), indicando la versión mayor más alta soportada por el demonio. El kernel emitirá entonces una nueva solicitud FUSE_INIT que se ajuste a la versión más antigua. En el caso inverso, el demonio debería retroceder silenciosamente a la versión mayor del
kernel.
La versión menor negociada se considera que es el mínimo de las vers
iones menores proporcionadas por el demonio y el kernel, y ambas part
es deberían usar el protocolo correspondiente a dicha versión menor.

struct fuse_getattr_in {
    uint32_t getattr_flags;
    uint32_t dummy;

                         (getattr_flags & FUSE_GETATTR_FH)

La operación solicitada es calcular los atributos a ser devueltos por stat(2) y operaciones similares para el objeto de sistema de archivos dado. El objeto para el cual los atributos deberían ser calculados es indicado ya sea por header->nodeid o, si el flag FUSE_GETATTR_FH está establecido, por el manejador de archivo fh. El último caso de operación es análogo a fstat(
2).
Por razones de rendimiento, estos atributos pueden ser almacenados en caché en el kernel durante una duración de tiempo especificada. Mientras el tiempo de expiración de la caché no haya sido excedido, los atributos serán servidos desde la caché y no causarán solicitudes adicionales de FUSE_GETATT
R.
Los atributos calculados y el tiempo de expiración de la caché solicitado deberían entonces ser devueltos en la siguiente
estructura: 

struct fuse_attr_out {
    /* Duración de la caché de atributos (segundos + nanosegundos) */
    uint64_t attr_valid;
    uint32_t attr_valid_nsec;
    uint32_t dummy;
    struct fuse_attr {
        uint64_t ino;
        uint64_t size;
        uint64_t blocks;
        uint64_t atime;
        uint64_t mtime;
        uint64_t ctime;
        uint32_t atimensec;
        uint32_t mtimensec;
        uint32_t ctimensec;
        uint32_t mode;
        uint32_t nlink;
        uint32_t uid;
        uint32_t gid;
        uint32_t rdev;
        uint32_t blksize;
        uint32_t padding;
    } attr;
};

La operación solicitada es abrir el nodo indicado por header->nodeid. La semántica exacta de lo que esto significa dependerá del sistema de archivos siendo implementendido. Sin embargo, como mínimo, el sistema de archivos debe validar que las banderas solicitadas sean válidas para el recurso indicado y luego enviar una respuesta con el siguiente

struct fuse_open_out {
    uint64_t fh;
    uint32_t open_flags;
    uint32_t padding;
};
El campo fh es un identificador opaco que el núcleo utilizará para referirse a este recurso. El campo open_flags es una máscara de bits de cualquier número de las
banderas que indican al núcleo propi

struct fuse_interrupt_in {
    uint64_t unique;
};
La acción solicitada es cancelar la operación pendiente indicada por unique. Esta solicitud no requiere respuesta. Sin embargo, la recepción de este mensaje no cancela por sí misma la operación indicada. El núcleo seguirá esperando una respuesta a dicha operación (por ejemplo, un error EINTR o una lectura corta). Se emitirá como máximo una solicitud FUSE_INTERRUPT para una operación determinada. Tras emitir dicha operación,
el núcleo esperará de forma ininterrump
ible la finalización de la solicitud indicada.

struct fuse_entry_out {
    uint64_t nodeid;            /* ID del inodo */
    uint64_t generation;        /* Generación del inodo */
    uint64_t entry_valid;

    uint32_t entry_valid_nsec;
    uint32_t attr_valid_nsec;
