DESCRIPCIÓ

N

El archivo /etc/freeipmi//freeipmi_interpret_sensor.conf define cómo deben interpretarse los sensores IPMI. Los sensores basados en IPMI especifican una serie de estados/umbrales cuando se leen. Basándose en esos estados/umbrales, bibliotecas y herramientas como libfreeipmi(3), libipmimonitoring(3) y ipmi-sensors(8) pueden informar si una lectura de un sensor es "buena" o "mala" mediante un informe de un estado NOMINAL, WARNING o

CRITICAL.

Cada uno de los estados listados a continuación es (con suerte) lo suficientemente descriptivo como para describir las condiciones de estado que pueden activarse/desactivarse para cada tipo de sensor. Para obtener información más detallada sobre cada uno de los estados individuales listados a continuación, consulte las "Tablas de códigos de sensores y eventos" de la Especificación IPMI. Ipmi-sensors(8) se puede utilizar para determinar los tipos de sensores y los estados/umbrales que existen en un sistema, generando una salida muy detallada y observando qué tipos de eventos de aserción o desaserción son

posibles.

Los valores posibles para todos los estados/umbrales a continuación

son:

Nominal - Señalar lectura Nominal si se activa el

estado/umbral

Warning - Señalar lectura Warning si se activa el

estado/umbral

Critical - Señalar lectura Critical si se activa el

estado/umbral

Actualmente no se admiten todos los tipos de sensores IPMI y tipos de eventos. Si desea que se admitan más, envíe un correo electrónico a la lista de correo de

FreeIPMI.

Los valores predeterminados seleccionados para la activación de estados/umbrales individuales se basan en suposiciones y en el análisis de placas base. Si cree que deberían cambiarse, envíe un correo electrónico a la lista de correo de FreeIPMI para discutir cuáles deberían ser los valores predeterminados

.

La mayoría de las interpretaciones predeterminadas se pueden determinar con bastante facilidad y pueden satisfacer las necesidades de la mayoría de los usuarios. Por ejemplo, una lectura de "Performance_Met" normalmente es mejor que "Performance_Lags". Sin embargo, algunos sensores pueden ser ambiguos y depender completamente del fabricante. Por ejemplo, "State_Asserted" frente a "State_Deasserted" dependen completamente de la interpretación del proveedor. Se recomienda a los usuarios que ajusten las interpretaciones a continuación según las necesidades de sus

máquinas.

Cada grupo de condiciones de estado a continuación incluye una configuración para "No_Event". Esta es la condición bajo la cual no han ocurrido o no se han activado estados/eventos del sens

or. En la mayoría de los casos, se prefiere una asignación a "Nominal". Sin embargo, en algunas circunstancias, puede ser útil informar algo diferente. Por ejemplo, si un sensor en una
placa base en particular está obligado a informar un estado/evento, una condición de estado sin sensor podría indicar un sensor defectuoso. Esto depende en gran medida de la placa base.

FORMAT

O

Las opciones de configuración que se pueden especificar en el archivo de configuración se enumeran a continuación. Cada opción de configuración debe figurar en un

a línea separada. Los argumentos de una opción se separan por cualquier cantidad de espacios en blanco. Los múltiples argumentos también se separan por espacios e
n blanco. Los comentarios se pueden marcar usando el signo de número ("#"), y las líneas se pueden continuar en la siguiente usando la barra invertida ("\\").

IPMI_O
EM
Las siguientes opciones de configuración se pueden utilizar para configurar interpretaciones específicas de OEM. Los usuarios deben tener en cuenta que tanto IPMI_OEM_Bitmask como IPMI_OEM_Value se pueden configurar para una combinación idéntica de Manufacturer-ID, Product-ID, Event-Reading-Type-Code y Sensor-Type. Se iteran todas las reglas de interpretación para una combinación específica y se devuelve el estado de sensor resultante peor (es decir, Advertencia < Nominal, Crítico < Advertencia). Si no se encuentra ninguna coincidencia, no se devuelve ningún estado de sensor para la lectura del sensor OEM. Para cada una de las opciones de configuración siguientes, <Manufacturer-ID> es el ID numérico de fabricante IANA para el fabricante en cuestión. El <Product-ID> es uno o más IDs numéricos que representan el producto del fabricante. El <Product-ID> se puede listar como un número numérico único (por ejemplo, 1234), un rango de IDs separado por un guion (por ejemplo, 12-20), o una lista de IDs de producto específicos separados por un signo más (por ejemplo, 12+19+22). Tanto el Manufacturer-ID como el Product-ID se pueden encontrar utilizando bmc-info(8). Se pueden introducir múltiples pares de <Manufacturer-ID> y <Product-ID> separados por comas. El Event-Reading-Type-Code y el Sensor-Type no necesitan ser tipos OEM. Pueden ser tipos no OEM y utilizarse para proporcionar reglas
de interpretación para sensores que pueden comport
arse fuera del estándar de la especificación IPMI.
IPMI_OEM_Bitmask <Manufacturer-ID>:<Product-ID>,... Event-Reading-Type-Code Sensor-Type Sensor-Event-Bitmask Sta
te
IPMI_OEM_Bitmask se puede utilizar para configurar una interpretación de estado para una combinación específica de Manufacturer-ID, Product-ID, Event-Reading-Type-Code y Sensor-Type y una máscara de bits específica del Sensor-Event. El estado se aceptará como la interpretación del sensor si la máscara de bits introducida Y (AND) con la lectura real de la máscara de bits del evento del sensor es verdadera. Como caso especial, el estado se aceptará si la máscara de bits introducida y la máscara de bits real del evento del sensor son ambas 0. En otras palabras, si no ocurrieron eventos, se puede configurar una interpretación OEM para este caso introduciendo una máscara de bits de
0x0000.
