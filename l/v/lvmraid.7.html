NOMBRE

lvmraid — RAID de LVM

DESCRIPCIÓN

El RAID de lvm(8) es una forma de crear un Volumen Lógico (LV) que utiliza múltiples dispositivos físicos para mejorar el rendimiento o tolerar fallos de dispositivos. En LVM, los dispositivos físicos son Volúmenes Físicos (PV) dentro de un único Grupo de Volúmenes (VG).

Cómo se colocan los bloques de datos del LV en los PV viene determinado por el nivel de RAID. Los niveles de RAID se conocen comúnmente como 'raid' seguido de un número, p.ej., raid1, raid5 o raid6. La selección de un nivel de RAID implica hacer concesiones entre: requisitos de dispositivos físicos, tolerancia a fallos y rendimiento. Una descripción de los niveles de RAID se puede encontrar en: Technical_Position.pdf

El RAID de LVM utiliza tanto el mapeador de dispositivos (DM) como los controladores de dispositivos múltiples (MD) del kernel de Linux. DM se utiliza para crear y gestionar dispositivos LVM visibles, y MD se utiliza para colocar datos en los dispositivos físicos.

LVM crea LVs ocultos (dispositivos dm) en capas entre el LV visible y los dispositivos físicos. Los LVs en las capas intermedias se llaman LVs secundarios. Para el RAID de LVM, se crea un par de LVs secundarios para almacenar datos y metadatos (superbloque RAID y mapa de bits de intención de escritura) por cada imagen/rama RAID (ver ejemplos del comando lvs(8) a continuación).

USO

Para crear un LV RAID, utiliza `lvcreate` y especifica un tipo de LV. El tipo de LV corresponde a un nivel de RAID. Los niveles de RAID básicos que se pueden utilizar son: raid0, raid1, raid4, raid5, raid6, raid10.

lvcreate --type NivelRAID [OPCIONES] --name Nombre --size Tamaño VG [PVs]

Para mostrar el tipo de LV de un LV existente, ejecuta:

# lvs -o name,segtype LV

(El tipo de LV también se conoce como "tipo de segmento" o "segtype".)

Los LVs se pueden crear con los siguientes tipos:

raid0

También llamado striping, raid0 distribuye los datos del LV entre múltiples dispositivos en unidades de tamaño de stripe. Se utiliza para aumentar el rendimiento. Los datos del LV se perderán si alguno de los dispositivos falla.

lvcreate --type raid0 [--stripes Número --stripesize Tamaño] VG [PVs]

--stripes Número
especifica el Número de dispositivos entre los cuales se distribuirá el LV.
--stripesize Tamaño
especifica el Tamaño de cada stripe en kilobytes. Esta es la cantidad de datos que se escribe en un dispositivo antes de pasar al siguiente.
PVs
especifica los dispositivos a utilizar. Si no se especifica, lvm elegirá Número dispositivos, uno por cada stripe, basándose en el número de PVs disponibles o proporcionados.

raid1

También llamado mirroring, raid1 utiliza múltiples dispositivos para duplicar los datos del LV. Los datos del LV permanecen disponibles si todos los dispositivos fallan excepto uno. El número mínimo de dispositivos (es decir, pares de LVs secundarios) requeridos es 2.

lvcreate --type raid1 [--mirrors Número] VG [PVs]

--mirrors Número
especifica el Número de imágenes de espejo además de la imagen del LV original, p.ej., `--mirrors 1` significa que hay dos imágenes de los datos, la original y una imagen de espejo.
PVs
especifica los dispositivos a utilizar. Si no se especifica, lvm elegirá Número dispositivos, uno por cada imagen.

raid4

raid4 es una forma de striping que utiliza un dispositivo adicional, el primer dispositivo, dedicado al almacenamiento de bloques de paridad. Los datos del LV permanecen disponibles si falla un dispositivo. La paridad se utiliza para recalcular los datos que se han perdido de un solo dispositivo. El número mínimo de dispositivos requeridos es 3.

lvcreate --type raid4 [--stripes Número --stripesize Tamaño] VG [PVs]

--stripes Número
especifica el Número de dispositivos a utilizar para los datos del LV. Esto no incluye el dispositivo adicional que lvm añade para almacenar los bloques de paridad. Un LV raid4 con Número stripes requiere Número+1 dispositivos. Número debe ser 2 o más.
--stripesize Tamaño
especifica el Tamaño de cada stripe en kilobytes. Esta es la cantidad de datos que se escribe en un dispositivo antes de pasar al siguiente.
PVs
especifica los dispositivos a utilizar. Si no se especifica, lvm elegirá Número+1 dispositivos separados.

raid4 se llama paridad no rotatoria porque los bloques de paridad siempre se almacenan en el mismo dispositivo.

raid5

raid5 es una forma de striping que utiliza un dispositivo adicional para almacenar bloques de paridad. Los datos del LV y los bloques de paridad se almacenan en cada dispositivo, típicamente en un patrón rotatorio para razones de rendimiento. Los datos del LV permanecen disponibles si falla un dispositivo. La paridad se utiliza para recalcular los datos que se han perdido de un solo dispositivo. El número mínimo de dispositivos requeridos es 3 (a menos que se convierta de raid1 de 2 ramas a reestructurar a más stripes; ver reestructuración).

lvcreate --type raid5 [--stripes Número --stripesize Tamaño] VG [PVs]

--stripes Número
especifica el Número de dispositivos a utilizar para los datos del LV. Esto no incluye el dispositivo adicional que lvm añade para almacenar los bloques de paridad. Un LV raid5 con Número stripes requiere Número+1 dispositivos. Número debe ser 2 o más.
--stripesize Tamaño
especifica el Tamaño de cada stripe en kilobytes. Esta es la cantidad de datos que se escribe en un dispositivo antes de pasar al siguiente.
PVs
especifica los dispositivos a utilizar. Si no se especifica, lvm elegirá Número+1 dispositivos separados.

raid5 se llama paridad rotatoria porque los bloques de paridad se colocan en diferentes dispositivos en una secuencia de ciclo. Hay variaciones de raid5 con diferentes algoritmos para colocar los bloques de paridad. La variante predeterminada es raid5_ls (raid5 left symmetric, que es una paridad rotatoria 0 con reinicio de datos).
Ver VARIACIONES DE RAID5 a continuación.

raid6

raid6 es una forma de striping como raid5, pero utiliza dos dispositivos adicionales para bloques de paridad. Los datos del LV y los bloques de paridad se almacenan en cada dispositivo, típicamente en un patrón rotatorio para razones de rendimiento. Los datos del LV permanecen disponibles si fallan hasta dos dispositivos. La paridad se utiliza para recalcular los datos que se han perdido de uno o dos dispositivos. El número mínimo de dispositivos requeridos es 5.

lvcreate --type raid6 [--stripes Número --stripesize Tamaño] VG [PVs]

--stripes Número
especifica el Número de dispositivos a utilizar para los datos del LV. Esto no incluye los dos dispositivos adicionales que lvm añade para almacenar los bloques de paridad. Un LV raid6 con Número stripes requiere Número+2 dispositivos. Número debe ser 3 o más.
--stripesize Tamaño
especifica el Tamaño de cada stripe en kilobytes. Esta es la cantidad de datos que se escribe en un dispositivo antes de pasar al siguiente.
PVs
especifica los dispositivos a utilizar. Si no se especifica, lvm elegirá Número+2 dispositivos separados.

Al igual que raid5, existen variaciones de raid6 con diferentes algoritmos para colocar los bloques de paridad. La variante predeterminada es raid6_zr (raid6 zero restart, también conocido como left symmetric, que es una paridad rotatoria 0 con reinicio de datos

rt).
Ver VARIANTES DE RAID6 abajo.

raid10

raid10 es una combinación de raid1 y raid0, distribuyendo datos entre dispositivos duplicados. Los datos del LV permanecen disponibles si uno o más dispositivos permanecen en cada conjunto de duplicados. El número mínimo de dispositivos requeridos es 4.

lvcreate --type raid10 [--mirrors NúmeroDeEspejos] [--stripes NúmeroDeFranjas --stripesize Tamaño] VG [PVs]

--mirrors NúmeroDeEspejos
especifica el número de imágenes de espejo dentro de cada franja. por ejemplo, --mirrors 1 significa que hay dos imágenes de los datos, el original y una imagen de espejo.
--stripes NúmeroDeFranjas
especifica el número total de dispositivos a usar en todas las imágenes raid1 (no el número de dispositivos raid1 sobre los cuales distribuir el LV, aunque ese es el resultado efectivo). El número de dispositivos en cada espejo raid1 será NúmeroDeFranjas/(NúmeroDeEspejos+1), por ejemplo, espejos 1 y franjas 4 distribuirán los datos entre dos espejos raid1, donde cada espejo contiene dos dispositivos.
--stripesize Tamaño
especifica el Tamaño de cada franja en kilobytes. Esta es la cantidad de datos que se escribe en un dispositivo antes de pasar al siguiente.
PVs
especifica los dispositivos a utilizar. Si no se especifica, lvm elegirá los dispositivos necesarios. Los dispositivos se utilizan para crear espejos en el orden en que se enumeran, por ejemplo, para espejos 1, franjas 2, enumerar PV1 PV2 PV3 PV4 da como resultado los espejos PV1/PV2 y PV3/PV4.

RAID10 no está duplicando encima de franjas, lo que sería RAID01, que es menos tolerante a fallos de dispositivos.

Monitorización

Cuando se activa un LV RAID, se inicia el proceso dmeventd(8) para monitorizar el estado del LV. Varios eventos detectados en el kernel pueden hacer que se envíe una notificación desde el mapeador de dispositivos al proceso de monitorización, incluyendo fallos de dispositivos y finalización de la sincronización (por ejemplo, para inicialización o limpieza).

El archivo de configuración de LVM contiene opciones que afectan cómo responderá el proceso de monitorización a los eventos de fallo (por ejemplo, raid_fault_policy). Es posible activar y desactivar la monitorización con lvchange, pero no se recomienda desactivarla a menos que tenga un conocimiento profundo de las consecuencias.

Sincronización

La sincronización es el proceso que hace que todos los dispositivos en un LV RAID sean consistentes entre sí.

En un LV RAID1, todas las imágenes de espejo deben tener los mismos datos. Cuando se añade una nueva imagen de espejo, o una imagen de espejo carece de datos, las imágenes necesitan ser sincronizadas. Se copian bloques de datos de una imagen existente a una nueva o desactualizada para que coincidan.

En un LV RAID 4/5/6, los bloques de paridad y los bloques de datos deben coincidir según el cálculo de paridad. Cuando cambian los dispositivos en un LV RAID, los bloques de datos y paridad pueden volverse inconsistentes y necesitan ser sincronizados. Se leen bloques correctos, se calcula la paridad y se escriben los bloques recalculados.

La implementación RAID rastrea qué partes de un LV RAID están sincronizadas. Cuando se crea y activa un LV RAID por primera vez, la primera sincronización se llama inicialización. Un puntero almacenado en los metadatos RAID rastrea el proceso de inicialización, lo que permite reiniciarlo después de una desactivación del RaidLV o un fallo. Cualquier escritura en el RaidLV ensucia la región respectiva del mapa de bits de intención de escritura, lo que permite una recuperación rápida de las regiones después de un fallo. Sin esto, todo el LV tendría que ser sincronizado cada vez que se activara.

La sincronización automática ocurre cuando se activa un LV RAID, pero generalmente es parcial porque los mapas de bits reducen las áreas que se revisan. Una sincronización completa se vuelve necesaria cuando se reemplazan los dispositivos en el LV RAID.

El estado de sincronización de un LV RAID se informa mediante el siguiente comando, donde "Cpy%Sync" = "100%" significa que la sincronización está completa:

# lvs -a -o name,sync_percent

Limpieza

La limpieza es un escaneo completo del LV RAID solicitado por un usuario. La limpieza puede encontrar problemas que pasan desapercibidos en la sincronización parcial.

La limpieza asume que los metadatos RAID y los mapas de bits pueden ser inexactos, por lo que verifica todos los metadatos RAID, los datos del LV y los bloques de paridad. La limpieza puede encontrar inconsistencias causadas por errores de hardware o degradación. Estos tipos de problemas pueden no ser detectados por la sincronización automática que excluye las áreas fuera del mapa de bits de intención de escritura de RAID.

El comando para limpiar un LV RAID puede operar en dos modos diferentes:

lvchange --syncaction check|repair LV

check
El modo de verificación es de solo lectura y solo detecta áreas inconsistentes en el LV RAID, no las corrige.
repair
El modo de reparación verifica y escribe bloques corregidos para sincronizar cualquier área inconsistente.

La limpieza puede consumir mucho ancho de banda y ralentizar la E/S de la aplicación en el LV RAID. Para controlar la tasa de E/S utilizada para la limpieza, use:

--maxrecoveryrate Tamaño[k|UNIT]
Establece la tasa máxima de recuperación para un LV RAID. El Tamaño se especifica como una cantidad por segundo para cada dispositivo en el array. Si no se proporciona sufijo, se utiliza KiB/segundo/dispositivo. Establecer la tasa de recuperación a 0 significa que no tendrá límites.
--minrecoveryrate Tamaño[k|UNIT]
Establece la tasa mínima de recuperación para un LV RAID. El Tamaño se especifica como una cantidad por segundo para cada dispositivo en el array. Si no se proporciona sufijo, se utiliza KiB/segundo/dispositivo. Establecer la tasa de recuperación a 0 significa que no tendrá límites.

Para mostrar la limpieza actual en progreso en un LV, incluyendo el modo syncaction y el porcentaje completado, ejecute:

# lvs -a -o name,raid_sync_action,sync_percent

Después de que la limpieza se complete, para mostrar el número de bloques inconsistentes encontrados, ejecute:

# lvs -o name,raid_mismatch_count

Además, si se encontraron discrepancias, el campo de atributos de lvs(8) mostrará la letra "m" (mismatch) en la novena posición, por ejemplo:

# lvs -o name,vgname,segtype,attr vg/lv
  LV VG   Type  Attr
  lv vg   raid1 Rwi-a-r-m-

Limitaciones de Limpieza

El modo check solo puede informar el número de bloques inconsistentes, no puede informar qué bloques son inconsistentes. Esto hace imposible saber qué dispositivo tiene errores, o si los errores afectan a los datos del sistema de archivos, metadatos o nada en absoluto.

El modo repair puede hacer que los datos del LV RAID sean consistentes, pero no sabe qué datos son correctos. El resultado puede ser datos consistentes pero incorrectos. Cuando dos bloques de datos diferentes deben hacerse consistentes, elige el bloque del dispositivo que se usaría durante la inicialización RAID. Sin embargo, si se conoce el PV que contiene datos corruptos, se puede usar lvchange --rebuild en lugar de la limpieza para reconstruir los datos en el dispositivo defectuoso.

Los desarrollos futuros podrían incluir:

Permitir a un usuario elegir la versión correcta de los datos durante la reparación.

Usar una mayoría de dispositivos para determinar la versión correcta de los datos a utilizar en un RAID1 de 3 vías o un LV RAID6.

Usar un dispositivo de suma de verificación para identificar cuándo y dónde ocurre un error, permitiendo que se reescriba.

SubLVs

Un LV es a menudo una combinación de otros LVs ocultos llamados SubLVs. Los SubLVs utilizan dispositivos físicos o se construyen a partir de otros SubLVs. Los SubLVs almacenan bloques de datos de LV, bloques de paridad RAID y metadatos RAID. Los SubLVs generalmente están ocultos, por lo que se requiere la opción lvs -a para mostrarlos:

# lvs -a -o name,segtype,devices

Los nombres de SubLV comienzan con el nombre del LV visible y tienen un sufijo automático que indica su función:

 •
Los SubLVs que contienen bloques de datos o paridad de LV tienen el sufijo _rimage_#.
Estos SubLVs a veces se denominan DataLVs.
 •
Los SubLVs que contienen metadatos RAID tienen el sufijo _rmeta_#. Los metadatos RAID incluyen información de superbloque, tipo de RAID, mapa de bits e información de estado del dispositivo.
Estos SubLVs a veces se denominan MetaLVs.

Los SubLVs son un detalle de implementación interna de LVM. La forma en que se utilizan, construyen y nombran puede cambiar.

Los siguientes ejemplos muestran la disposición de SubLV para cada uno de los tipos básicos de LV RAID, utilizando el menor número de dispositivos permitidos para cada uno.

Ejemplos

raid0

Cada SubLV rimage contiene una porción de los datos del LV. No se usa paridad. No se usan metadatos RAID.

# lvs -a -o name,segtype,devices

  [lvr0_rimage_0] linear /dev/sda(...)
  [lvr0_rimage_1] linear /dev/sdb(...)

Cuando un array RAID pierde un número crítico de dispositivos, lo que provoca que pierda su capacidad de funcionar de manera confiable, el array se detendrá y requerirá reparación.

Inicie el proceso de reparación con este comando:

lvconvert --repair LV

Si los dispositivos previamente no disponibles vuelven a ser accesibles, este proceso de reparación actualizará sus metadatos y el array RAID podrá ser reactivado.

INTEGRIDAD DE DATOS

El destino de integridad del mapeador de dispositivos se puede usar en combinación con los niveles RAID 1, 4, 5, 6, 10 para detectar y corregir la corrupción de datos en las imágenes RAID. Se coloca una capa dm-integrity encima de cada imagen RAID y se crea un sub-LV adicional para almacenar metadatos de integridad (sumas de verificación de datos) para cada imagen RAID. Cuando se leen datos de una imagen, se utilizan sumas de verificación de integridad para detectar corrupción. Si se detecta, dm-raid lee los datos de otra imagen (correcta) para devolverlos al llamador. dm-raid también escribirá automáticamente los datos correctos de vuelta a la imagen con datos incorrectos para corregir la corrupción.

Al crear un LV RAID con integridad, o al agregar integridad, se requiere espacio para los metadatos de integridad. Cada 500 MB de datos de LV requiere una asignación adicional de 4 MB para metadatos de integridad, para cada imagen RAID.

Crear un LV RAID con integridad:
lvcreate --type raidN --raidintegrity y

Agregar integridad a un LV RAID existente:
lvconvert --raidintegrity y LV

Eliminar integridad de un LV RAID:
lvconvert --raidintegrity n LV

Opciones de integridad

--raidintegritymode journal|bitmap
Utiliza un journal (por defecto) o un mapa de bits para mantener las sumas de verificación de integridad consistentes en caso de un fallo. Las áreas del mapa de bits se recalculan después de un fallo, por lo que la corrupción en esas áreas no se detectaría. Un journal no tiene este problema. El modo journal duplica las escrituras al almacenamiento, pero puede mejorar el rendimiento de escrituras dispersas empaquetadas en una sola escritura de journal. En teoría, el modo de mapa de bits puede lograr el rendimiento completo de escritura del dispositivo, pero no se beneficiaría de la posible optimización de escrituras dispersas.
--raidintegrityblocksize 512|1024|2048|4096
El tamaño del bloque a utilizar para dm-integrity en imágenes RAID. El tamaño del bloque de integridad generalmente debería coincidir con el tamaño del bloque lógico del dispositivo, o los tamaños de sector/bloque del sistema de archivos. Puede ser menor que el tamaño del sector/bloque del sistema de archivos, pero no menor que el tamaño del bloque lógico del dispositivo. Valores posibles: 512, 1024, 2048, 4096.
--integritysettings key=val
Las opciones de ajuste del kernel de dm-integrity se pueden especificar aquí. La configuración se puede incluir con lvcreate o lvconvert cuando se habilita la integridad por primera vez, o cambiar con lvchange en un LV inactivo existente. Consulte la documentación del kernel para obtener descripciones de las opciones ajustables. Repita la opción para establecer múltiples valores. Use lvs -a -o integritysettings VG/LV_rimage_N para mostrar los valores configurados. Use lvchange --integritysettings "" para borrar todos los valores configurados (dm-integrity usará sus valores predeterminados).

Inicialización de la integridad

Cuando se agrega integridad a un LV, el kernel necesita inicializar los metadatos de integridad (sumas de verificación crc32) para todos los bloques del LV. La verificación de corrupción de datos realizada por dm-integrity solo operará en áreas del LV que ya estén inicializadas. El progreso de la inicialización de la integridad se informa mediante el campo de informe de LV "syncpercent" (y bajo la columna Cpy%Sync de lvs(8)).

Limitaciones de la integridad

Para solucionar algunas limitaciones, es posible eliminar la integridad del LV, realizar el cambio y luego agregar la integridad nuevamente. (Los metadatos de integridad necesitarían ser inicializados al agregarse de nuevo.)

LVM debe poder asignar el sub-LV de metadatos de integridad en un solo PV que ya está en uso por la imagen RAID asociada. Esto puede causar un problema durante lvextend si el PV original que contiene la imagen y los metadatos de integridad está lleno. Para solucionar esta limitación, elimine la integridad, extienda el LV y vuelva a agregar la integridad.

Se pueden agregar imágenes RAID adicionales a los LVs raid1, pero no a otros niveles RAID.

Un LV raid1 con integridad no puede convertirse a lineal (elimine la integridad para hacer esto).

Los LVs RAID con integridad aún no se pueden usar como sub-LVs con otros tipos de LV.

Lo siguiente aún no está permitido en LVs RAID con integridad: lvreduce, pvmove, lvconvert --splitmirrors, lvchange --rebuild.

AJUSTE DE RAID1

Un LV RAID1 se puede ajustar para que se eviten ciertos dispositivos para la lectura mientras se escriben en todos los dispositivos.

lvchange --[raid]writemostly PV[:y|n|t] LV

El dispositivo especificado se marcará como "write mostly" (principalmente escritura), lo que significa que se evitará la lectura de este dispositivo y se preferirán otros dispositivos para la lectura (a menos que no haya otros dispositivos disponibles). Esto minimiza las E/S al dispositivo especificado.

Si el nombre del PV no tiene sufijo, se establece el atributo "write mostly". Si el nombre del PV tiene el sufijo :n, se borra el atributo "write mostly", y el sufijo :t alterna la configuración actual.

La opción "write mostly" se puede repetir en la línea de comandos para cambiar múltiples dispositivos a la vez.

Para informar la configuración actual de "write mostly", el campo de atributos de lvs(8) mostrará la letra "w" en la novena posición cuando se establece "write mostly":

lvs -a -o name,attr

Cuando un dispositivo se marca como "write mostly", se puede configurar el número máximo de escrituras pendientes a ese dispositivo. Una vez alcanzado el máximo, las escrituras posteriores se vuelven síncronas. Cuando es síncrono, una escritura al LV no se completará hasta que las escrituras a todas las imágenes espejo se completen.

lvchange --[raid]writebehind Número LV

Para informar la configuración actual de "write behind", ejecute:

lvs -o name,raid_write_behind

Cuando "write behind" no está configurado, o está establecido en 0, todas las escrituras del LV son síncronas.

TRANSICIÓN DE RAID

La transición de RAID consiste en convertir un LV RAID de un nivel RAID a otro, por ejemplo, de raid5 a raid6. Cambiar el nivel RAID generalmente se hace para aumentar o disminuir la resiliencia a fallos de dispositivos o para reorganizar los LVs. Esto se hace usando lvconvert y especificando el nuevo nivel RAID como el tipo de LV:

lvconvert --type NivelRaid LV [PVs]

Las conversiones de transición de RAID más comunes y recomendadas son:

lineal a raid1
Lineal es una única imagen de datos de LV, y convertirla a raid1 agrega una imagen espejo que es una copia directa de la imagen lineal original.
striped/raid0 a raid4/5/6
Agregar dispositivos de paridad a un volumen rayado resulta en raid4/5/6.

Las conversiones antinaturales que no se recomiendan incluyen la conversión entre tipos rayados y no rayados. Esto se debe a que los sistemas de archivos a menudo optimizan los patrones de E/S basándose en los valores de rayado del dispositivo. Si esos valores cambian, puede disminuir el rendimiento.

Convertir a un nivel RAID superior requiere asignar nuevos SubLVs para almacenar metadatos RAID, y nuevos SubLVs para almacenar bloques de paridad para los datos del LV. Convertir a un nivel RAID inferior elimina los SubLVs que ya no son necesarios.

La conversión a menudo requiere una sincronización completa del LV RAID (Ver Sincronización). Convertir a RAID1 requiere copiar todos los bloques de datos del LV a N nuevas imágenes en nuevos dispositivos. Convertir a un nivel RAID de paridad requiere leer todos los bloques de datos del LV, calcular la paridad y escribir los nuevos bloques de paridad. La sincronización puede llevar mucho tiempo dependiendo del rendimiento de los dispositivos utilizados y del tamaño del RaidLV. Puede degradar el rendimiento. Los controles de tasa también se aplican a la conversión; ver --minrecoveryrate y --maxrecoveryrate.

Advertencia: aunque es posible crear LVs striped con hasta 128 rayas, se pueden convertir un máximo de 64 rayas a raid0, 63 a raid4/5 y 62 a raid6 debido a los SubLVs de paridad adicionales. Un LV striped con un máximo de 32 rayas se puede convertir a raid10.

Conversiones indirectas

Convertir de un nivel RAID a otro puede requerir múltiples pasos, convirtiendo primero a niveles RAID intermedios.

linear a raid6

Para convertir un LV de lineal a raid6:
1. convertir a raid1 con dos imágenes
2. convertir a raid5 (internamente raid5_ls) con dos imágenes
3. convertir a raid5 con tres o más rayas

(redimensionar)
4. convertir a raid6 (internamente raid6_ls_6)
5. convertir a raid6 (internamente raid6_zr, redimensionar)

Los comandos para realizar los pasos anteriores son:
1. lvconvert --type raid1 --mirrors 1 LV
2. lvconvert --type raid5 LV
3. lvconvert --stripes 3 LV
4. lvconvert --type raid6 LV
5. lvconvert --type raid6 LV

La conversión final de raid6_ls_6 a raid6_zr se realiza para evitar la posible reducción del rendimiento de escritura/recuperación en raid6_ls_6 debido al dispositivo de paridad dedicado. raid6_zr rota los bloques de datos y paridad para evitar esto.

lineal a con bandas

Para convertir un LV de lineal a con bandas:
1. convertir a raid1 con dos imágenes
2. convertir a raid5_n
3. convertir a raid5_n con cinco bandas de 128k (redimensionar)
4. convertir raid5_n a con bandas

Los comandos para realizar los pasos anteriores son:
1. lvconvert --type raid1 --mirrors 1 LV
2. lvconvert --type raid5_n LV
3. lvconvert --stripes 5 --stripesize 128k LV
4. lvconvert --type striped LV

El tipo raid5_n en el paso 2 se usa porque tiene SubLVs de paridad dedicados al final y se puede convertir directamente a con bandas. El tamaño de la banda se incrementa en el paso 3 para agregar espacio adicional para el proceso de conversión. Este paso aumenta el tamaño del LV en un factor de cinco. Después de la conversión, este espacio adicional se puede reducir (o usar para aumentar el sistema de archivos usando el LV).

Invertir estos pasos convertirá un LV con bandas a lineal.

raid6 a con bandas

Para convertir un LV de raid6_nr a con bandas:
1. convertir a raid6_n_6
2. convertir a con bandas

Los comandos para realizar los pasos anteriores son:
1. lvconvert --type raid6_n_6 LV
2. lvconvert --type striped LV

REDIMENSIONAMIENTO RAID

El redimensionamiento RAID consiste en cambiar atributos de un LV RAID manteniendo el mismo nivel RAID. Esto incluye cambiar el diseño RAID, el tamaño de la banda o el número de bandas.

Al cambiar el diseño RAID o el tamaño de la banda, no se necesitan asignar nuevos SubLVs (MetaLVs o DataLVs), pero los DataLVs se extienden por una pequeña cantidad (típicamente 1 extent). El espacio adicional permite que los bloques en una banda se actualicen de forma segura y no se corrompan en caso de un fallo. Si ocurre un fallo, el redimensionamiento puede reiniciarse.

(Si los bloques en una banda se actualizaron en el lugar, un fallo podría dejarlos parcialmente actualizados y corruptos. En su lugar, una banda existente se pone en pausa, se lee, se cambia su diseño y la nueva banda se escribe en espacio libre. Una vez hecho esto, la nueva banda se despausa y se usa.)

Also, converting a mirrored logical volume to RAID1 will require at least two devices, and converting a RAID1 logical volume to a mirrored one will require at least two devices.

DEVICE FAILURE

When a device fails in a RAID1 or RAID10 configuration, the logical volume is marked as inactive and all I/O operations fail. This is to prevent data corruption. The user must then take action to replace the failed device and repair the logical volume.

In RAID5/6 configurations, device failures are handled differently. If a device fails, the logical volume is marked as degraded, but I/O operations continue to succeed. The system will attempt to reconstruct the missing data from the parity information. However, performance may be degraded, and the logical volume is more vulnerable to further device failures.

If multiple devices fail in a RAID5/6 configuration, the logical volume may become unusable. The user must replace the failed devices and recreate the logical volume. The lvconvert command can be used to convert a degraded RAID logical volume to a linear logical volume, allowing data recovery. This is a last resort option, as it will result in data loss.

DATA INTEGRITY

RAID5 and RAID6 provide data redundancy and integrity through the use of parity information. This allows the system to detect and correct data errors, and to reconstruct data in case of device failure.

The lvconvert command can be used to convert a logical volume to or from a RAID type. This can be used to improve data integrity by converting a linear logical volume to a RAID type, or to recover data from a degraded RAID logical volume by converting it to a linear logical volume.

When converting a RAID logical volume to a linear logical volume, the parity information is discarded. This means that the data integrity guarantees of the RAID type are lost. The resulting linear logical volume will be more vulnerable to data corruption and device failures.

The RAID1 type in LVM provides a number of tuning options that can be used to optimize its performance. These options are available through the lvconvert command.

The default RAID1 type uses a copy-on-write mechanism to maintain data consistency. This can be inefficient for write-heavy workloads. The lvconvert command allows you to change the RAID1 type to a more performance-oriented one, such as RAID10.

The lvconvert command can also be used to adjust the number of mirrors and the stripe size of a RAID1 logical volume. These parameters can be tuned to match the specific workload and hardware configuration.

The RAID takeover functionality allows LVM to take over management of an existing software RAID array. This is useful when you want to integrate a software RAID array into an LVM setup, or when you want to migrate data from a software RAID array to LVM.

To perform a RAID takeover, you first need to create a new logical volume of the same size as the RAID array. SINOPSIS

/dev/lvmraid/raidN

DESCRIPCIÓN

lvmraid es un destino de LVM que implementa un conjunto de dispositivos RAID por software. Permite a LVM gestionar dispositivos RAID con múltiples discos subyacentes. Actualmente, el soporte de LVM para dispositivos RAID se implementa utilizando la infraestructura de MD (RAID por software) del kernel de Linux.

NOMBRADO DE DISPOSITIVOS

Los dispositivos lvmraid se crean en el grupo de volúmenes lvmraid (si no se especifica un nombre de grupo de volúmenes diferente) con el prefijo raid y un número secuencial (por ejemplo, raid0, raid1, raid2, etc.).

NIVELES RAID

Los siguientes niveles RAID son compatibles:

raid0 (stripe)
No proporciona redundancia. Los datos se dividen en bloques y se distribuyen en todos los discos físicos. Útil para aumentar el rendimiento.
raid1 (mirror)
Proporciona redundancia duplicando todos los datos en todos los discos. Si un disco falla, el sistema puede seguir funcionando con los discos restantes.
raid4 (striped with parity)
Similar a RAID0, pero el último disco se reserva para información de paridad. Este diseño puede ser un cuello de botella de rendimiento ya que todas las operaciones de escritura deben pasar por el disco de paridad.
raid5 (distributed parity)
Similar a RAID4, pero la información de paridad se distribuye en todos los discos. Esto reduce el cuello de botella de rendimiento de RAID4 y proporciona un buen equilibrio entre rendimiento y redundancia.
raid6 (dual distributed parity)
Similar a RAID5, pero utiliza dos bloques independientes de información de paridad distribuidos en todos los discos. Esto permite que el sistema soporte el fallo de dos discos simultáneamente sin pérdida de datos.
raid10 (striped mirrors)
Combina RAID0 y RAID1. Los discos se agrupan en pares de espejos (RAID1), y luego estos espejos se dividen en franjas (RAID0). Proporciona tanto redundancia como rendimiento.

El soporte de RAID por software en LVM se introdujo por primera vez en LVM2. La implementación se basa en la infraestructura MD existente en el kernel de Linux.
