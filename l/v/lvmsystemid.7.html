NOMBRE

lvmsystemid — ID de sistema de LVM

DESCRIPCIÓN

El ID de sistema de LVM (lvm(8)) restringe el acceso al Grupo de Volúmenes (VG) a un solo host. Esto es útil cuando un VG se coloca en dispositivos de almacenamiento compartido, o cuando los dispositivos locales son visibles tanto para el sistema operativo anfitrión como para el invitado. En casos como estos, un VG puede ser visible para múltiples hosts a la vez, y se necesita algún mecanismo para evitar que sea utilizado por más de un host a la vez.

El ID de sistema de un VG identifica a un host como propietario del VG. El host con un ID de sistema coincidente puede usar el VG y sus LV, mientras que LVM en otros hosts lo ignorará. Esto protege al VG de ser utilizado accidentalmente desde otros hosts.

El ID de sistema es una cadena que identifica de forma única a un host. Puede configurarse como un valor personalizado, o puede ser asignado automáticamente por LVM utilizando algún identificador único ya disponible en el host, por ejemplo, machine-id o uname.

Cuando se crea un nuevo VG, el ID de sistema del host local se registra en los metadatos del VG. El host creador entonces posee el nuevo VG, y LVM en otros hosts lo ignorará. Cuando se importa un VG existente exportado (vgimport), el ID de sistema del host local se guarda en los metadatos del VG, y el host importador posee el VG.

Un VG sin ID de sistema puede ser utilizado por LVM en cualquier host donde los dispositivos del VG sean visibles. Cuando no se utilizan ID de sistema, los filtros de dispositivos deben configurarse en todos los hosts para excluir los dispositivos del VG de todos menos de uno de los hosts.

Un VG extranjero es un VG visto por un host con un ID de sistema no coincidente, es decir, el ID de sistema en los metadatos del VG no coincide con el ID de sistema configurado en el host. Si el host no tiene ID de sistema, y el VG sí lo tiene, el VG es extranjero y LVM lo ignorará. Si el VG no tiene ID de sistema, el acceso no está restringido, y LVM puede acceder a él desde cualquier host, tenga o no el host un ID de sistema.

Los cambios en el ID de sistema de un host y en el ID de sistema de un VG se pueden realizar en circunstancias limitadas (ver vgexport y vgimport). Cambios inadecuados pueden resultar en que un host pierda el acceso a su VG, o que un VG sea dañado accidentalmente por el acceso de un host no deseado. Incluso cambios limitados en el ID de sistema del VG pueden no reflejarse perfectamente entre hosts. Una visión más coherente del almacenamiento compartido requiere un sistema de bloqueo entre hosts para coordinar el acceso.

Los caracteres válidos del ID de sistema son los mismos que los caracteres válidos del nombre del VG. Si un ID de sistema contiene caracteres inválidos, esos caracteres se omiten y se utilizan los caracteres restantes. Si un ID de sistema es más largo que la longitud máxima del nombre, se utilizan los caracteres hasta la longitud máxima. La longitud máxima de un ID de sistema es de 128 caracteres.

Imprimir el ID de sistema de un VG para verificar si está establecido:

vgs -o systemid VG

Imprimir el ID de sistema del host local para verificar si está configurado:

lvm systemid

Limitaciones y advertencias

Para beneficiarse completamente del ID de sistema, todos los hosts deben tener configurado un ID de sistema, y todos los VGs deben tener un ID de sistema establecido. Sin ningún método para restringir el acceso, como ID de sistema o filtros de dispositivos, un VG que es visible para múltiples hosts puede ser dañado o destruido accidentalmente.

•
Un VG sin ID de sistema puede ser utilizado sin restricciones desde cualquier host donde sea visible, incluso desde hosts que tienen un ID de sistema.
•
Muchos VGs no tendrán un ID de sistema configurado porque LVM no lo ha habilitado por defecto, e incluso cuando está habilitado, muchos VGs fueron creados antes de que la característica se añadiera a LVM o se habilitara. Se puede asignar un ID de sistema a estos VGs usando vgchange --systemid (ver abajo).
•
Dos hosts no deben tener asignado el mismo ID de sistema. Hacerlo anula el propósito de distinguir diferentes hosts con este valor.
•
Los PV huérfanos (o dispositivos no utilizados) en almacenamiento compartido no están protegidos por la característica de ID de sistema. Comandos que utilizan estos PV, como vgcreate o vgextend, no se les impide realizar operaciones conflictivas y dañar los PV. Ver la sección orphans para más información.
•
El ID de sistema no protege los dispositivos en un VG de programas distintos a LVM.
•
Un host que usa una versión antigua de LVM (sin la característica de ID de sistema) no reconocerá un ID de sistema establecido en los VGs. El LVM antiguo puede leer un VG con un ID de sistema, pero se le impide escribir en el VG (o sus LV). La característica de ID de sistema cambia el modo de escritura de un VG, haciéndolo parecer de solo lectura a versiones anteriores de LVM.

Esto también significa que si un host retrocede a una versión anterior de LVM, perdería el acceso a cualquier VG que hubiera creado con un ID de sistema. Para evitar esto, el ID de sistema debe eliminarse de los VGs locales antes de degradar LVM a una versión sin la característica de ID de sistema.

Tipos de acceso a VG

Un VG local está destinado a ser utilizado por un solo host.

Un VG compartido o en clúster está destinado a ser utilizado por múltiples hosts.

Estos pueden distinguirse además como:

Sin restricciones:
Un VG local que no tiene ID de sistema. Este tipo de VG no está protegido y es accesible para cualquier host.
Propiedad:
Un VG local que tiene un ID de sistema establecido, visto desde el host con un ID de sistema coincidente (el propietario). Este tipo de VG es accesible para el host.
Extranjero:
Un VG local que tiene un ID de sistema establecido, visto desde cualquier host con un ID de sistema no coincidente (o sin ID de sistema). Es propiedad de otro host. Este tipo de VG no es accesible para el host.
Exportado:
Un VG local que ha sido exportado con vgexport y no tiene ID de sistema. Este tipo de VG solo puede ser accedido por vgimport, que lo cambiará a propiedad.
Compartido:
Un VG compartido o "lockd" tiene el tipo de bloqueo (lock_type) establecido y no tiene ID de sistema. Un VG compartido está destinado a ser utilizado en almacenamiento compartido desde múltiples hosts, y solo es accesible para hosts que usan lvmlockd. Aplicable solo si LVM está compilado con soporte para lvmlockd.
En clúster:
Un VG en clúster o "clvm" tiene la bandera "clustered" establecida y no tiene ID de sistema. Un VG en clúster está destinado a ser utilizado en almacenamiento compartido desde múltiples hosts, y solo es accesible para hosts que usan clvmd. Aplicable solo si LVM está compilado con soporte para clvm.

Configuración del ID de sistema del host

El propio ID de sistema de un host puede definirse de varias maneras. `global/system_id_source` en lvm.conf define el método que LVM utilizará para encontrar el ID de sistema local:

none
LVM no utilizará un ID de sistema. Se permite que LVM acceda a VGs sin ID de sistema, y creará nuevos VGs sin ID de sistema. Una `system_id_source` indefinida es equivalente a `none`.

lvm.conf

global {
    system_id_source = "none"
}
appmachineid
Se utiliza una derivación específica de LVM de `/etc/machine-id` como ID de sistema. Consulte machine-id(5) para verificar si machine-id está disponible en el host.

lvm.conf

global {
    system_id_source = "appmachineid"
}
machineid
El contenido de `/etc/machine-id` se utiliza como ID de sistema si está disponible. (Se recomienda `appmachineid` para evitar exponer el `machine-id` confidencial).

lvm.conf

global {
    system_id_source = "machineid"
}
uname
La cadena `utsname.nodename` de uname(2) se utiliza como ID de sistema. Un uname que comienza con "localhost" se ignora y es equivalente a `none`.

lvm.conf

global {
    system_id_source = "uname"
}

NAME

lvmsystemid

LVM system ID concepts

DESCRIPTION

LVM can use a system ID string to identify the host system that owns a Volume Group (VG). This is a security feature that prevents a host from accessing VGs that belong to another host.

The system ID is usually derived from the host's machine-id(5), but can be configured in lvm.conf(5). When a VG is created, its system ID is set to the system ID of the host running the command. When a host scans for VGs, it will only see VGs whose system IDs match its own, or VGs with no system ID.

system_id_source

The system ID for the host is determined by the global/system_id_source setting in lvm.conf. The default value is "auto".

auto
Tries to find a system ID in the following order:
  • If /etc/lvm/lvmlocal.conf contains a local/system_id setting, that is used.
  • If /etc/lvm/lvm.conf contains a global/system_id_file setting, the system ID is read from that file.
  • If /etc/machine-id exists and is not empty, that is used.
  • If /var/lib/dbus/machine-id exists and is not empty, that is used.
  • If /etc/hostname exists and is not empty, that is used.
  • The system's uname(2) nodename is used.
none
No system ID is generated. The host will only be able to see VGs that have no system ID. This is equivalent to turning off system ID filtering.
file
The system ID is read from the file specified by global/system_id_file in lvm.conf. If the file does not exist or is empty, it's equivalent to none.
local
The system ID is read from the local/system_id setting in /etc/lvm/lvmlocal.conf. If this setting does not exist, it's equivalent to none.
uname
The system ID is set to the host's nodename from uname(2). This is equivalent to the 'auto' setting when no other options are found.

If the system ID cannot be determined, or if system_id_source is set to "none", the host is treated as having no system ID. This means it can access VGs with no system ID, but cannot access VGs with a system ID set.

Overriding system ID

In some cases, it may be necessary for a host to access VGs with different system IDs, e.g. if a host's system ID changes, and it wants to use VGs that it created with its old system ID. To allow a host to access VGs with other system IDs, those other system IDs can be listed in lvmlocal.conf local/extra_system_ids.

lvmlocal.conf

local {
    extra_system_ids = [ "my_other_name" ]
}

A safer option may be configuring the extra values as needed on the command line as:
--config 'local/extra_system_ids=["id"]'

vgcreate

In vgcreate, the host running the command assigns its own system ID to the new VG. To override this and set another system ID:

vgcreate --systemid SystemID VG PVs

Overriding the host's system ID makes it possible for a host to create a VG that it may not be able to use. Another host with a system ID matching the one specified may not recognize the new VG without manually rescanning devices.

If the --systemid argument is an empty string (""), the VG is created with no system ID, making it accessible to other hosts (see warnings above.)

report/display

The system ID of a VG is displayed with the "systemid" reporting option.

Report/display commands ignore foreign VGs by default. To report foreign VGs, the --foreign option can be used. This causes the VGs to be read from disk.

vgs --foreign -o +systemid

When a host with no system ID sees foreign VGs, it warns about them as they are skipped. The host should be assigned a system ID, after which standard reporting commands will silently ignore foreign VGs.

vgexport/vgimport

vgexport clears the VG system ID when exporting the VG.

vgimport sets the VG system ID to the system ID of the host doing the import.

vgchange

A host can change the system ID of its own VGs, but the command requires confirmation because the host may lose access to the VG being changed:

vgchange --systemid SystemID VG

The system ID can be removed from a VG by specifying an empty string ("") as the new system ID. This makes the VG accessible to other hosts (see warnings above.)

A host cannot directly change the system ID of a foreign VG.

To move a VG from one host to another, vgexport and vgimport should be used.

To forcibly gain ownership of a foreign VG, a host can temporarily add the foreign system ID to its extra_system_ids list, and change the system ID of the foreign VG to its own. See Overriding system ID above.

shared VGs

A shared VG has no system ID set, allowing multiple hosts to use it via lvmlockd. Changing a VG to shared will clear the existing system ID. Applicable only if LVM is compiled with lvmlockd support.

clustered VGs

A clustered/clvm VG has no system ID set, allowing multiple hosts to use it via clvmd. Changing a VG to clustered will clear the existing system ID. Changing a VG to not clustered will set the system ID to the host running the vgchange command.

creation_host

In vgcreate, the VG metadata field creation_host is set by default to the host's uname. The creation_host cannot be changed, and is not used to control access. When system_id_source is "uname", the system_id and creation_host fields will be the same.

orphans

Orphan PVs are unused devices; they are not currently used in any VG. Because of this, they are not protected by a system ID, and any host can use them. Coordination of changes to orphan PVs is beyond the scope of system ID. The same is true of any block device that is not a PV.
