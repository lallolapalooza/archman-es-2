NOMBRE

lvmthin — Aprovisionamiento ligero (thin provisioning) de LVM

DESCRIPCIÓN

Los bloques en un Volumen Lógico (LV) de lvm(8) estándar se asignan cuando se crea el LV, pero los bloques en un LV con aprovisionamiento ligero se asignan a medida que se escriben. Debido a esto, un LV con aprovisionamiento ligero tiene un tamaño virtual que puede ser mucho mayor que el almacenamiento físico disponible. La cantidad de almacenamiento físico proporcionada para los LVs con aprovisionamiento ligero se puede incrementar más tarde según sea necesario.

Los bloques en un LV estándar se asignan (durante la creación) desde el Grupo de Volúmenes (VG), pero los bloques en un LV ligero se asignan (durante el uso) desde un "pool ligero" (thin pool). El pool ligero contiene bloques de almacenamiento físico, y los bloques del LV ligero hacen referencia a bloques en el pool ligero.

Se debe crear un "LV de pool ligero" especial antes de que se puedan crear LVs ligeros dentro de él. Un LV de pool ligero se crea combinando dos LVs estándar: un LV de datos que contendrá los bloques para los LVs ligeros, y un LV de metadatos que contendrá los metadatos. Los metadatos del pool ligero son creados y utilizados por el módulo del kernel "dm_thin_pool" para rastrear los bloques de datos utilizados por los LVs ligeros.

Las instantáneas (snapshots) de LVs ligeros son eficientes porque los bloques de datos comunes a un LV ligero y cualquiera de sus instantáneas se comparten. Se pueden tomar instantáneas de LVs ligeros o de otras instantáneas ligeras. Los bloques comunes a instantáneas recursivas también se comparten en el pool ligero. No hay límite ni degradación por secuencias de instantáneas.

A medida que los LVs ligeros o los LVs de instantánea se escriben, consumen bloques de datos en el pool ligero. A medida que disminuyen los bloques de datos libres en el pool, puede ser necesario añadir más espacio físico al pool. Esto se hace extendiendo el pool ligero con espacio físico adicional del VG. Eliminar LVs ligeros o instantáneas del pool ligero también puede liberar más espacio. Sin embargo, eliminar LVs ligeros no siempre es una forma efectiva de liberar espacio en un pool ligero porque los bloques pueden ser compartidos por instantáneas, y los bloques libres pueden estar demasiado fragmentados para ser liberados.

La asignación de bloques bajo demanda puede hacer que los bloques del LV ligero se fragmenten en el pool ligero, lo que puede resultar en un rendimiento reducido en comparación con un LV estándar completamente aprovisionado.

DEFINICIONES

LV Ligero
Un LV ligero es un volumen lógico de LVM para el cual se asigna almacenamiento bajo demanda. A medida que se escribe en un LV ligero, se asignan bloques de un pool ligero para contener los datos. Un LV ligero tiene un tamaño virtual que puede ser mayor que el espacio físico en el pool ligero.
Pool Ligero
Un pool ligero es un LV especial que contiene extensiones físicas desde las cuales se asignan LVs ligeros. El LV de pool ligero no se utiliza como un dispositivo de bloques, sino que el nombre del pool ligero se referencia al crear LVs ligeros. El LV de pool ligero debe extenderse con extensiones físicas adicionales antes de que se agote el espacio. Un pool ligero tiene dos LVs componentes ocultos: uno para contener datos ligeros y otro para contener metadatos ligeros.
LV de Datos de Pool Ligero
Un componente de un pool ligero que contiene datos de LVs ligeros. El LV de datos es un LV oculto con un sufijo _tdata, y no se utiliza directamente. El tamaño físico del LV de datos se muestra como el tamaño del pool ligero.
LV de Metadatos de Pool Ligero
Un componente de un pool ligero que contiene metadatos para el módulo del kernel "dm_thin_pool". "dm_thin_pool" genera y utiliza estos metadatos para rastrear los bloques de datos utilizados por los LVs ligeros. El LV de metadatos es un LV oculto con un sufijo _tmeta, y no se utiliza directamente.
Instantánea Ligera
Una instantánea ligera es un LV ligero que se crea haciendo referencia a un LV ligero existente u otra instantánea ligera. La instantánea ligera inicialmente hace referencia a los mismos bloques que el LV ligero existente. Actúa como una copia puntual del LV ligero al que hacía referencia.
Origen Externo
Un LV de solo lectura que se utiliza como origen de instantánea para LVs ligeros. Las porciones no escritas de los LVs ligeros se leen del origen externo.

USO

Creación de Pool Ligero

Se puede crear un pool ligero con el comando lvcreate. Los LVs de componentes de datos y metadatos se asignan desde el VG y se combinan en un pool ligero. El lvcreate -L|--size será el tamaño del LV de datos del pool ligero, y el tamaño del LV de metadatos se calculará automáticamente (o, opcionalmente, se puede especificar con --poolmetadatasize.)

# lvcreate --type thin-pool -n ThinPool -L Size VG

Conversión de Pool Ligero

Para una disposición de pool ligero personalizada, los LVs de datos y metadatos se pueden crear por separado y luego combinarlos en un pool ligero con lvconvert. Esto permite usar tipos de LV específicos, o dispositivos específicos, para los LVs de datos/metadatos. La combinación de los LVs de datos y metadatos en un pool ligero borra el contenido de ambos LVs. El pool ligero resultante toma el nombre y el tamaño del LV de datos. (Si no se especifica un LV de metadatos, lvconvert creará automáticamente uno para usar en el pool ligero.)

# lvcreate -n DataLV -L Size VG DataDevices
# lvcreate -n MetadataLV -L MetadataSize VG MetadataDevices
# lvconvert --type thin-pool --poolmetadata MetadataLV VG/DataLV

(DataLV ahora se referirá como ThinPool, y se puede usar para crear LVs ligeros.)

Creación de LV Ligero

Los LVs ligeros se crean en un pool ligero, y se crean con un tamaño virtual usando la opción -V|--virtualsize. El tamaño virtual puede ser mayor que el espacio físico disponible en el pool ligero.

# lvcreate --type thin -n ThinLV -V VirtualSize --thinpool ThinPool VG

Creación de Instantánea Ligera

Las instantáneas de LVs ligeros son LVs ligeros en sí mismas, pero la instantánea LV inicialmente hace referencia a los mismos bloques que el LV ligero de origen. El LV ligero de origen y sus LVs ligeros de instantánea divergirán a medida que se escriban en ellos. El LV ligero de origen se puede eliminar sin afectar a las instantáneas que lo referencian. Se pueden tomar instantáneas de LVs ligeros que a su vez fueron creados como instantáneas. (No se debe usar una opción de tamaño al crear una instantánea ligera, de lo contrario se creará una instantánea COW.)

# lvcreate --snapshot -n SnapLV VG/ThinLV

Porcentaje de Datos de Pool Ligero y Porcentaje de Metadatos

Para los LVs de pool ligero activos, el comando 'lvs' muestra "Data%" (-o data_percent) y "Meta%" (-o metadata_percent). El porcentaje de datos es el porcentaje del espacio en el LV de datos que está actualmente utilizado por los LVs ligeros. El porcentaje de metadatos es el porcentaje del espacio en el LV de metadatos que está actualmente utilizado por el módulo "dm_thin_pool". El pool ligero debe extenderse antes de que cualquiera de estos valores alcance el 100%.

# lvs -o data_percent VG/ThinPool
# lvs -o metadata_percent VG/ThinPool

Extensión de Pool Ligero

Cuando se ejecuta lvextend en un pool ligero, extenderá el LV de datos interno por la cantidad especificada, y el LV de metadatos interno también se extenderá, si es necesario, en relación con el nuevo tamaño de datos.

# lvextend --size Size VG/ThinPool

Se puede solicitar un nuevo tamaño de metadatos al extender los datos del pool ligero.

# lvextend --size Size --poolmetadatasize MetadataSize VG/ThinPool

El tamaño de metadatos se puede extender sin extender el tamaño de datos.

# lvextend --poolmetadatasize MetadataSize VG/ThinPool

El LV de datos o metadatos interno se puede extender por nombre.

# lvextend -L Size VG/ThinPool_tdata
# lvextend -L MetadataSize VG/ThinPool_tmeta

Extensión Automática de Pool Ligero

Es importante extender un pool ligero antes de que se agote el espacio, de lo contrario podría dañarse, y ser difícil o imposible de reparar. LVM se puede configurar para que dmeventd(8) extienda automáticamente los pools ligeros cuando les queda poco espacio. Deben estar disponibles extensiones libres en el VG para usarlas en la extensión de los pools ligeros.

dmeventd(8) generalmente es iniciado por el servicio lvm2-monitor. dmeventd recibe notificaciones del kernel indicando cuándo los datos o metadatos del pool ligero se están llenando. En respuesta, dmeventd ejecuta el comando "lvextend --use-policies V

Thin Pool Autoextend

Thin pools can be automatically extended when their usage exceeds a configured threshold. This feature requires the dmeventd(8) daemon to be running and monitoring the thin pool LV. The daemon watches the LV's usage and compares it with thresholds defined in lvm.conf(5) under the activation/ section. When the usage exceeds the threshold, the thin pool is extended by the configured percentage. System messages will indicate when these extensions occur.

To enable thin pool automatic extension, set the following in lvm.conf(5):

activation/thin_pool_autoextend_threshold
Extend the thin pool when the current usage reaches this percentage. The chosen value should depend on the rate at which new data may be written. If space is consumed more quickly, then a lower threshold will provide dmeventd and lvextend more time to react and extend the pool. The minimum is 50. Setting to 100 disables autoextend.
activation/thin_pool_autoextend_percent
A thin pool is extended by this percent of its current size.

The thin pool itself must be monitored by dmeventd to be automatically extended. When activating a thin pool, lvm normally requests monitoring by dmeventd. To verify this, run:

# lvs -o+seg_monitor VG/ThinPool

To begin monitoring a thin pool in dmeventd:

# lvchange --monitor y VG/ThinPool

Activación de LV Delgado (Thin LV)

Un LV delgado que se crea como instantánea (snapshot) recibe la propiedad "omitir activación" (skip activation). Esto se informa con `lvs -o skip_activation`, o con la letra 'k' en el décimo atributo del LV. Esta propiedad hace que los comandos `vgchange -ay` y `lvchange -ay` omitan la activación del LV delgado a menos que la opción `-K|--ignoreactivationskip` también se establezca.

# lvchange -ay -K VG/SnapLV

La propiedad "omitir activación" en un LV delgado puede ser eliminada, de modo que no se requiera `-K` para activarlo (o habilitada para que `-K` sea requerida).

# lvchange --setactivationskip y VG/SnapLV
# lvchange --setactivationskip n VG/SnapLV

Para configurar la opción "omitir activación" que `lvcreate` aplica a las nuevas instantáneas, establezca lvm.conf(5) activation/auto_set_activation_skip.

Conversión de LV Grueso (Thick LV) a LV Delgado (Thin LV)

Un LV grueso (por ejemplo, lineal, rayado) puede convertirse a un LV delgado en un nuevo pool delgado. El nuevo pool delgado se crea utilizando el LV grueso existente como datos del pool delgado. Se generan nuevos metadatos del pool delgado y se escriben en un nuevo LV de metadatos. El nuevo LV delgado referencia los datos gruesos originales ahora ubicados en el LV de datos del pool delgado. Nota: Esta conversión no se puede revertir; el volumen delgado no puede volver a ser el LV grueso.

# lvconvert --type thin VG/ThickLV

(ThickLV ahora se referiría como ThinLV, y existirá un nuevo pool delgado llamado ThinLV_tpool0.)

Después de la conversión, el LV delgado y el pool delgado resultantes se verán algo diferentes de los LVs/pools delgados ordinarios: el nuevo LV delgado estará completamente aprovisionado en el pool delgado, y el uso de datos del pool delgado será del 100%. El pool delgado requerirá extensión antes de que se utilicen nuevos LVs delgados o instantáneas.

Pool Delgado sobre LVM RAID

Los LVs de componentes de datos o metadatos de un pool delgado pueden usar LVM RAID creando primero LVs RAID para los componentes de datos y/o metadatos, y luego convirtiendo estos LVs RAID en un pool delgado.

# lvcreate --type raidN -n DataLV -L Size VG DataDevices
# lvcreate --type raidN -n MetadataLV -L MetadataSize VG MetadataDevices
# lvconvert --type thin-pool --poolmetadata MetadataLV VG/DataLV

(DataLV ahora se referiría como ThinPool, y puede ser utilizado para crear LVs delgados.)

Para usar MD RAID en lugar de LVM RAID, cree LVs lineales de datos/metadatos en dispositivos MD y refiérase a los dispositivos MD para DataDevices/MetadataDevices.

Pool Delgado en LVM VDO

Los datos del pool delgado pueden ser comprimidos y deduplicados usando VDO. Los datos de todos los LVs delgados en el pool delgado serán comprimidos y deduplicados usando el módulo dm-vdo.

# lvcreate --type thin-pool -n ThinPool -L Size --pooldatavdo y VG

O, convierta un LV existente (por ejemplo, lineal, rayado) en un pool delgado que usa compresión/deduplicación VDO para datos delgados. El contenido existente en el LV será borrado.

# lvconvert --type thin-pool --pooldatavdo y VG/LV

(LV ahora se referiría como ThinPool, y puede ser utilizado para crear LVs delgados.)

Creación Combinada de Pool Delgado y LV Delgado

Se puede usar un solo comando para crear un nuevo pool delgado con un nuevo LV delgado.

# lvcreate --type thin -n ThinLV -V VirtualSize \
        --thinpool ThinPool -L ThinPoolSize VG

Primero, se crea un nuevo pool delgado:
El nombre del Pool Delgado se toma de --thinpool ThinPool
El tamaño del Pool Delgado se toma de -L|--size ThinPoolSize

Segundo, se crea un nuevo LV delgado:
El nombre del LV Delgado se toma de -n|--name ThinLV
El tamaño del LV Delgado se toma de -V|--virtualsize VirtualSize

Otros LVs delgados pueden ser creados en el pool delgado usando los comandos `lvcreate` estándar para LVs delgados.

Creación de Instantánea Delgada de un Origen Externo

Las instantáneas delgadas típicamente se toman de otros LVs delgados dentro del mismo pool delgado. Pero, también es posible crear una instantánea delgada de un LV externo (por ejemplo, lineal, rayado, LV delgado en otro pool delgado). El LV externo debe estar en modo de solo lectura (lvchange --permission r) e inactivo para ser utilizado como origen externo delgado. Las escrituras en el LV de instantánea delgada se almacenan en su pool delgado, y las partes no escritas se leen del origen externo. Un LV de origen externo puede ser utilizado para múltiples instantáneas delgadas.

# lvcreate --snapshot -n SnapLV --thinpool ThinPool VG/ExternalOrigin

Conversión de Instantánea Delgada y Origen Externo

En este caso, un LV existente, no delgado, se convierte en un origen externo de solo lectura, y se crea un nuevo LV delgado como instantánea de ese origen externo. Al nuevo LV delgado se le da el nombre del LV existente, y al LV existente se le da un nuevo nombre de --originname.

Las porciones no escritas del nuevo LV delgado se leen del origen externo. Si el LV delgado se elimina, el LV de origen externo puede ser usado nuevamente en modo de lectura/escritura. Por lo tanto, el LV delgado puede ser visto como una instantánea del volumen original.

# lvconvert --type thin --thinpool ThinPool --originname ExtOrigin VG/LV

El argumento del LV existente se renombra a ExtOrigin, y el nuevo LV delgado tiene el nombre del LV existente.

Fusión de Instantánea Delgada

Una instantánea delgada puede ser fusionada en su LV delgado de origen. El resultado de una fusión de instantánea es que el LV delgado de origen toma el contenido del LV de instantánea, y el LV de instantánea se elimina. Cualquier contenido que era exclusivo del LV delgado de origen se pierde después de la fusión.

Debido a que una fusión cambia el contenido de un LV, no se puede realizar mientras los LVs estén abiertos, por ejemplo, montados. Si se inicia una fusión mientras los LVs están abiertos, el efecto de la fusión se retrasa hasta la próxima activación del LV delgado de origen.

# lvconvert --merge VG/SnapLV

TEMAS ESPECIALES

Dispositivos Físicos para Datos y Metadatos de Pools Delgados

Colocar el LV de datos del pool delgado y el LV de metadatos en dispositivos físicos separados mejorará el rendimiento. También se recomiendan dispositivos más rápidos y redundantes para los metadatos. Para personalizar mejor los LVs de datos y metadatos, créelos por separado y luego combínelos en un pool delgado con `lvconvert`.

Para configurar el comportamiento de `lvcreate` para colocar los datos y metadatos del pool delgado en dispositivos separados, establezca `allocación/thin_pool_metadata_require_separate_pvs` en lvm.conf(5).

LV de Metadatos de Reserva

La primera vez que se crea un LV de pool delgado, lvm creará un LV de metadatos de reserva en el VG. Este comportamiento se puede controlar con la opción --poolmetadataspare y|n. Para crear el LV pmspare ("pool metadata spare"), lvm primero crea un LV con un nombre predeterminado, por ejemplo, lvol0, y luego convierte este LV en un LV oculto con el sufijo _pmspare, por ejemplo, lvol0_pmspare.

Se mantiene un LV pmspare en un VG para ser utilizado por cualquier pool delgado.

El LV pmspare no se puede crear explícitamente, pero se puede eliminar explícitamente.

La sección "Comprobación y reparación de metadatos del pool delgado" describe el uso del LV pmspare.

Comprobación y Reparación de Metadatos del Pool Delgado

Si los metadatos del pool delgado están dañados, es posible que se puedan reparar. La comprobación y reparación de metadatos del pool delgado es análoga a ejecutar `fsck`/reparación en un sistema de archivos. Los metadatos del pool delgado son compactos, por lo que incluso pequeñas áreas de daño o corrupción pueden resultar en una pérdida de datos significativa. El almacenamiento resiliente para los metadatos del pool delgado puede tener un valor adicional.

Cuando se activa un LV de pool delgado, lvm ejecuta el comando thin_check(8) para comprobar la corrección de los metadatos en el LV de metadatos del pool. Para configurar el uso de `thin_check`, la ubicación o las opciones utilizadas por lvm, establezca `global/thin_check_executable` en lvm.conf(5)
La ubicación del programa. Establecerlo en una cadena vacía ("") deshabilita la ejecución de `thin_check` por parte de lvm. Esto no se recomienda.

lvm.conf(5) `global/thin_check_options`
Controla las opciones de comando que lvm utilizará al ejecutar `thin_check`.

Si `thin_check` encuentra un problema con los metadatos, el LV de pool delgado no se activa y los metadatos del pool delgado deben ser reparados.

Los comandos de reparación simples no siempre tienen éxito. La reparación avanzada puede requerir la edición de los metadatos del pool delgado y los metadatos de lvm. Las versiones más nuevas del kernel y las herramientas de lvm pueden tener más éxito en la reparación. Informe los detalles de los metadatos delgados dañados para obtener el mejor asesoramiento sobre la recuperación.

Comando para reparar un pool delgado:

# lvconvert --repair VG/ThinPool

La reparación realiza los siguientes pasos:

1.
Crea una copia nueva y reparada de los metadatos.
`lvconvert` ejecuta el comando thin_repair(8) para leer los metadatos dañados del LV de metadatos del pool existente y escribe una nueva copia reparada en el LV pmspare del VG.
2.
Reemplaza el LV de metadatos del pool delgado.
Si el paso 1 es exitoso, el LV de metadatos del pool delgado es reemplazado por el LV pmspare que contiene los metadatos corregidos. El LV de metadatos del pool delgado anterior, que contiene los metadatos dañados, se vuelve visible con el nuevo nombre `ThinPool_metaN` (donde N es 0, 1,...).

Si la reparación funciona, el LV de pool delgado y sus LVs delgados pueden activarse. El usuario debe verificar que cada LV delgado en el pool delgado se pueda activar correctamente, y luego verificar la integridad del sistema de archivos en cada LV delgado (por ejemplo, usando `fsck` u otras herramientas). Una vez que se considera que el pool delgado se ha recuperado por completo, el LV `ThinPool_metaN` que contiene los metadatos originales y dañados se puede eliminar manualmente para recuperar el espacio.

Si la reparación falla, el LV `ThinPool_metaN` original y sin modificar que contiene los metadatos dañados...

que preservarse para soporte o métodos de recuperación más avanzados. Los datos de los LV delgados pueden, en última instancia, no ser recuperables.

Si los metadatos se restauran manualmente directamente con thin_repair, el LV de metadatos del pool puede ser intercambiado manualmente con otro LV que contenga metadatos nuevos:

# lvconvert --thinpool VG/ThinPool --poolmetadata VG/NewMetadataLV

Eliminar LVs de thin pool, LVs delgados y instantáneas

Eliminar un LV delgado y sus instantáneas relacionadas devuelve los bloques que utilizaban al thin pool. Estos bloques se reutilizarán para otros LVs delgados e instantáneas.

Eliminar un LV de thin pool elimina tanto el LV de datos como el LV de metadatos y devuelve el espacio al VG.

La eliminación de LVs de thin pool, LVs delgados e instantáneas con lvremove no se puede revertir con vgcfgrestore.

vgcfgbackup no realiza copias de seguridad de los metadatos del thin pool.

Usar fstrim para aumentar el espacio libre en un thin pool

Eliminar archivos en un sistema de archivos en un LV delgado generalmente no devuelve espacio libre al thin pool, ya que los sistemas de archivos normalmente no se montan con la opción de montaje discard (debido a la penalización de rendimiento).

Ejecutar manualmente el comando fstrim puede devolver al thin pool el espacio de un LV delgado que había sido utilizado por archivos eliminados. Esto solo es efectivo para bloques completos del thin pool que se han vuelto no utilizados (las áreas no utilizadas del sistema de archivos pueden no cubrir un bloque completo). Las instantáneas delgadas también evitan que se liberen bloques del thin pool. fstrim utiliza descartes y no tendrá ningún efecto si el thin pool está configurado para ignorar descartes.

Ejemplo

Un thin pool tiene 10G de espacio de datos físicos y un LV delgado tiene un tamaño virtual de 100G. Escribir un archivo de 1G en el sistema de archivos reduce el espacio libre en el thin pool en un 10% y aumenta el uso virtual del sistema de archivos en un 1%. Eliminar el archivo de 1G restaura el 1% virtual al sistema de archivos, pero no restaura el 10% físico al thin pool. El comando fstrim restaura el espacio físico al thin pool.

Agotamiento de datos del Thin Pool

Cuando se gestiona correctamente, el espacio de datos del thin pool debe extenderse antes de que se agote por completo (ver secciones sobre extensión de un thin pool automática y manualmente).

Sin embargo, si un thin pool se queda sin espacio, el comportamiento del thin pool completo se puede configurar con la propiedad "when full" (cuándo está lleno), informada con lvs -o whenfull. La propiedad "when full" se puede establecer en "error" o "queue". Cuando se establece en "error", un thin pool completo generará inmediatamente errores para las escrituras. Cuando se establece en "queue", las escrituras se ponen en cola durante un período de tiempo.

Mostrar la configuración actual de "when full":

# lvs -o whenfull VG/ThinPool

Establecer la propiedad "when full" a "error":

# lvchange --errorwhenfull y VG/ThinPool

Establecer la propiedad "when full" a "queue":

# lvchange --errorwhenfull n VG/ThinPool

Para configurar el valor que se asignará a los nuevos thin pools, establezca lvm.conf(5) activation/error_when_full

La configuración de whenfull no afecta a la configuración de monitorización y auto-extensión, y la configuración de monitorización/auto-extensión no afecta a la configuración de whenfull. Solo cuando la monitorización/auto-extensión no son efectivas es cuando el thin pool se llena y se aplica la configuración de whenfull.

— cola cuando está lleno —

Por defecto, las escrituras se ponen en cola durante un período de tiempo cuando el thin pool se llena. Se aceptan y ponen en cola las escrituras a LVs delgados, con la expectativa de que el espacio de datos del pool se extienda pronto. Una vez que el espacio de datos se extiende, las escrituras en cola se procesarán y el thin pool volverá a su funcionamiento normal.

Mientras espera a ser extendido, el thin pool pondrá en cola las escrituras hasta por 60 segundos (el valor por defecto). Si el espacio de datos no se ha extendido después de este tiempo, las escrituras en cola devolverán un error al llamador, por ejemplo, al sistema de archivos. Esto puede provocar daños en el sistema de archivos que requieren reparación. Cuando un thin pool devuelve errores para escrituras a un LV delgado, cualquier sistema de archivos está sujeto a la pérdida de datos de usuario no sincronizados.

El tiempo de espera de 60 segundos se puede cambiar o deshabilitar con la opción del módulo del kernel "dm_thin_pool" no_space_timeout. Esta opción establece el número de segundos que los thin pools pondrán en cola las escrituras. Si se establece en 0, las escrituras no caducarán. Deshabilitar los tiempos de espera puede provocar que el sistema se quede sin recursos, agotamiento de memoria, tareas bloqueadas y bloqueos. (El tiempo de espera se aplica a todos los thin pools del sistema.)

— error cuando está lleno —

Las escrituras a LVs delgados devuelven inmediatamente un error, y no se ponen en cola escrituras. Esto puede provocar daños en el sistema de archivos que requieren reparación.

— porcentaje de datos —

Cuando el espacio de datos se agota, el comando lvs muestra 100 bajo Data% y la letra D en la novena columna para el LV del thin pool:

# lvs -o name,data_percent,attr  vg/pool0
  LV     Data%  Attr
  pool0  100.00 twi-aot-D-

— causas —

Un thin pool puede quedarse sin espacio de datos por cualquiera de las siguientes razones:

•
La extensión automática del thin pool está deshabilitada y el thin pool no se extiende manualmente.
(No se recomienda deshabilitar la extensión automática.)
•
El demonio dmeventd(8) no se está ejecutando y el thin pool no se extiende manualmente.
(No se recomienda deshabilitar dmeventd.)
•
La extensión automática del thin pool es demasiado lenta dada la tasa de escrituras a los LVs delgados en el pool. (Esto se puede abordar ajustando activation/thin_pool_autoextend_threshold y activation/thin_pool_autoextend_percent.)
•
El VG no tiene suficientes bloques libres para extender el thin pool.

Agotamiento de metadatos del Thin Pool

Si el espacio de metadatos del thin pool se agota (o falla una operación de metadatos del thin pool), se devolverán errores para las operaciones de E/S en los LVs delgados.

Cuando el espacio de metadatos se agota, el comando lvs muestra 100 bajo Meta% para el LV del thin pool:

# lvs -o name,metadata_percent vg/pool0
  LV    Meta%
  pool0 100.00

Las mismas razones de agotamiento del espacio de datos del thin pool se aplican al espacio de metadatos del thin pool.

El agotamiento del espacio de metadatos puede provocar metadatos inconsistentes del thin pool y sistemas de archivos inconsistentes, por lo que la respuesta requiere una comprobación y reparación fuera de línea.

1.
Desactiva el LV del thin pool, o reinicia el sistema si no es posible.
2.
Repara el thin pool con lvconvert --repair.
Ver "Comprobación y reparación de metadatos del Thin Pool".
3.
Extiende el espacio de metadatos del pool con lvextend --poolmetadatasize.
Ver "Extensión del Thin Pool".
4.
Comprueba y repara el sistema de archivos.

Configuración personalizada del Thin Pool

Puede ser útil que diferentes thin pools tengan diferentes ajustes de thin pool, como umbrales de auto-extensión y porcentajes. Para cambiar los valores de lvm.conf(5) en una base por VG o por LV, adjunta un "perfil" al VG o LV. Un perfil es una colección de ajustes de configuración, guardada en un archivo de texto local (usando el formato de lvm.conf(5)). lvm busca perfiles en el directorio profile_dir, por ejemplo, /etc/lvm/profile/. Una vez adjuntado a un VG o LV, lvm procesará el VG o LV utilizando los ajustes del perfil adjuntado. Un perfil se nombra y se hace referencia por su nombre de archivo.

Para usar un perfil para personalizar los ajustes de lvextend para un LV:

•
Crea un archivo que contenga los ajustes, guardado en profile_dir.
Para la ubicación de profile_dir, ejecuta: 
# lvmconfig config/profile_dir
•
Adjunta el perfil a un LV, usando el comando: 
# lvchange --metadataprofile ProfileName VG/ThinPool
•
Extiende el LV utilizando los ajustes del perfil: 
# lvextend --use-policies VG/ThinPool

Ejemplo

# lvmconfig config/profile_dir
profile_dir="/etc/lvm/profile"
# cat /etc/lvm/profile/pool0extend.profile
activation {
        thin_pool_autoextend_threshold=50
        thin_pool_autoextend_percent=10
}
# lvchange --metadataprofile pool0extend vg/pool0
# lvextend --use-policies vg/pool0

Notas

•
Un perfil se adjunta a un VG o LV por nombre, donde el nombre hace referencia a un archivo local en profile_dir. Si el VG se mueve a otra máquina, el archivo con el perfil también debe moverse.
•
Solo ciertos ajustes se pueden usar en un perfil de VG o LV, ver: 
# lvmconfig --type profilable-metadata
•
Un LV sin su propio perfil heredará el perfil del VG.
•
Elimina un perfil de un LV usando el comando: 
# lvchange --detachprofile VG/ThinPool
•
Los comandos también pueden tener perfiles aplicados a ellos. Los ajustes que se pueden aplicar a un comando son diferentes
--commandprofile ProfileName
Aplicar el perfil especificado a este comando. Los perfiles se pueden definir en el directorio de perfiles (normalmente /etc/lvm/profile/) o en un directorio especificado en lvm.conf(5). La sintaxis de los perfiles es similar a la de la línea de comandos de LVM, pero tiene más flexibilidad. Por ejemplo, se pueden especificar rangos de tamaños de LVM, números de LVs, o usar comodines. Esto se hace para aplicar configuraciones predefinidas a los comandos de LVM, en lugar de tener que especificarlas cada vez. Un comando con un perfil aplicado tendrá el mismo efecto que si se hubieran especificado los parámetros del perfil directamente en la línea de comandos. Esto puede ser útil para simplificar comandos complejos o para asegurar que se aplican ciertas configuraciones de forma consistente. Consultar lvmconfig(8) para obtener más información sobre los perfiles y cómo crearlos. Para aplicar un perfil a un comando, escribe el perfil, guárdalo en el directorio de perfiles y ejecuta el comando usando la opción: --commandprofile NombreDelPerfil.

Cero

La propiedad "cero" de un pool delgado determina si los bloques se sobrescriben con ceros cuando se aprovisionan para un LV delgado. La configuración actual se informa con lvs -o cero (mostrando "cero" o "1" cuando el cero está habilitado), o 'z' en el octavo lv_attr. La opción -Z|--zero se utiliza para especificar el modo de cero.

Crear un pool delgado con modo de cero:

# lvcreate --type thin-pool -n ThinPool -L Size -Z y VG

Deshabilitar el modo de cero de un pool delgado existente:

# lvchange -Z n VG/ThinPool

Si el modo de cero se cambia de "n" a "y", los bloques aprovisionados previamente no se ponen a cero.

El aprovisionamiento de grandes bloques puestos a cero reduce el rendimiento.

Para configurar el modo de cero utilizado para los nuevos pools delgados cuando no se especifica en la línea de comandos, establezca lvm.conf(5) allocation/thin_pool_zero

Descarta

La propiedad "descartes" de un pool delgado determina cómo se gestionan las solicitudes de descarte. La configuración actual se informa con lvs -o descartes. La opción --discards se utiliza para especificar el modo de descarte.

Modos de descarte posibles:

ignorar
Ignorar cualquier descarte que se reciba.
nopassdown
Procesar cualquier descarte en el propio pool delgado, y permitir que los bloques recién inutilizados se utilicen para nuevos datos.
passdown
Procesar descartes en el pool delgado (como con nopassdown), y pasar los descartes al dispositivo subyacente. Este es el modo predeterminado.

Crear un pool delgado con un modo de descarte específico:

# lvcreate --type thin-pool -n ThinPool -L Size \
	--discards nopassdown VG

Cambiar el modo de descarte de un pool delgado existente:

# lvchange --discards nopassdown VG/ThinPool

Para configurar el modo de descarte utilizado para los nuevos pools delgados cuando no se especifica en la línea de comandos, establezca lvm.conf(5) allocation/thin_pool_discards

Los descartes pueden tener un impacto adverso en el rendimiento, véase la sección fstrim para más información.

Tamaño de bloque

Un pool delgado asigna almacenamiento físico para LVs delgados en unidades de "bloques". El tamaño de bloque actual de un pool delgado se informa con lvs -o chunksize. La opción --chunksize se utiliza para especificar el valor para un nuevo pool delgado (las unidades predeterminadas son KiB.) El valor debe ser un múltiplo de 64 KiB, entre 64 KiB y 1 GiB.

Cuando un pool delgado se utiliza principalmente para la característica de aprovisionamiento delgado, un valor mayor es óptimo. Para optimizar para muchas instantáneas, un valor menor reduce el tiempo de copia y consume menos espacio.

Para configurar el tamaño de bloque utilizado para los nuevos pools delgados cuando no se especifica en la línea de comandos, establezca lvm.conf(5) allocation/thin_pool_chunk_size

El valor predeterminado se muestra con:

# lvmconfig --type default allocation/thin_pool_chunk_size

Tamaño de metadatos del pool delgado

La cantidad de metadatos del pool delgado depende de cuántos bloques se comparten entre LVs delgados (es decir, a través de instantáneas). Un pool delgado con muchas instantáneas puede necesitar un LV de metadatos más grande. Los tamaños de los LV de metadatos de los pools delgados pueden variar de 2 MiB a aproximadamente 16 GiB.

Cuando un comando LVM crea automáticamente un LV de metadatos de pool delgado, el tamaño se especifica con la opción --poolmetadatasize. Cuando esta opción no se proporciona, LVM elige automáticamente un tamaño basado en el tamaño de los datos y el tamaño del bloque.

Puede ser difícil predecir la cantidad de espacio de metadatos que se necesitará, por lo que se recomienda empezar con un tamaño de 1 GiB, que debería ser suficiente para todos los propósitos prácticos. Un LV de metadatos de pool delgado puede ser ampliado posteriormente manual o automáticamente si es necesario.

(A efectos de compatibilidad con versiones anteriores, lvm.conf(5) allocation/thin_pool_crop_metadata controla el recorte del tamaño del LV de metadatos a 15.81 GiB para ser compatible con versiones anteriores de lvm. Con el recorte, puede haber problemas con volúmenes por encima de este tamaño cuando se utilizan con herramientas delgadas, es decir, thin_repair. El recorte solo debe habilitarse cuando la compatibilidad sea necesaria.)

XFS en instantáneas

Montar un sistema de archivos XFS en un nuevo LV de instantánea requiere atención al estado del registro y al UUID del sistema de archivos. En el LV de instantánea, el registro de xfs contendrá una transacción ficticia, y el UUID de xfs coincidirá con el UUID del sistema de archivos en el LV de origen.

Si el LV de instantánea es escribible, el montaje recuperará el registro para borrar la transacción ficticia, pero requerirá omitir la comprobación del UUID:

# mount /dev/VG/SnapLV /mnt -o nouuid

Después del primer montaje con el enfoque anterior, el UUID puede ser cambiado posteriormente usando:

# xfs_admin -U generate /dev/VG/SnapLV
# mount /dev/VG/SnapLV /mnt

Una vez que el UUID ha sido cambiado, el comando de montaje ya no requerirá la opción nouuid.
Si el LV de instantánea es de solo lectura, la recuperación del registro y la comprobación del UUID deben omitirse mientras se monta en modo de solo lectura:
