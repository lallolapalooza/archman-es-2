NOMBRE

lvmcache — Caché de LVM

DESCRIPCIÓN

lvm(8) incluye dos tipos de caché que se pueden usar para mejorar el rendimiento de un Volumen Lógico (LV). Al usar caché, subconjuntos variables de los datos de un LV se almacenan temporalmente en un dispositivo más pequeño y rápido (por ejemplo, un SSD) para mejorar el rendimiento del LV.

Para hacer esto con lvm, primero se crea un nuevo LV especial a partir del dispositivo más rápido. Este LV contendrá la caché. Luego, el nuevo LV rápido se adjunta al LV principal mediante un comando lvconvert. lvconvert inserta uno de los destinos del mapeador de dispositivos en la ruta de I/O del LV principal. El destino del mapeador de dispositivos combina el LV principal y el LV rápido en un dispositivo híbrido que se parece al LV principal, pero tiene mejor rendimiento. Mientras se utiliza el LV principal, partes de sus datos se almacenarán temporal y transparentemente en el LV rápido especial.

Los dos tipos de caché son:

•
Una caché de puntos calientes de lectura y escritura, utilizando el módulo del kernel dm-cache. Esta caché rastrea los patrones de acceso y ajusta su contenido deliberadamente para que las partes comúnmente utilizadas del LV principal se encuentren probablemente en el almacenamiento rápido. LVM se refiere a esto utilizando el tipo de LV cache.
•
Una caché de escritura, utilizando el módulo del kernel dm-writecache. Esta caché se puede usar con dispositivos SSD o PMEM para acelerar todas las escrituras en el LV principal. Los datos leídos del LV principal no se almacenan en la caché, solo los datos recién escritos. LVM se refiere a esto utilizando el tipo de LV writecache.

USO

1. Identificar el LV principal que necesita caché

El LV principal puede existir ya, y se encuentra en dispositivos más grandes y lentos. Un LV principal se crearía con un comando como:

# lvcreate -n principal -L Tamaño vg /dev/disco_duro_lento

2. Identificar el LV rápido a utilizar como caché

Un LV rápido se crea utilizando uno o más dispositivos rápidos, como un SSD. Este LV especial se usará para contener la caché:

# lvcreate -n rapido -L Tamaño vg /dev/ssd_rapido
# lvs -a
  LV   Attr       Type   Devices
  rapido -wi------- linear /dev/ssd_rapido
  principal -wi------- linear /dev/disco_duro_lento

3. Iniciar la caché del LV principal

Para iniciar la caché del LV principal, convierta el LV principal al tipo de caché deseado, y especifique el LV rápido a usar como caché:

usando dm-cache (con cachepool):

# lvconvert --type cache --cachepool rapido vg/principal

usando dm-cache (con cachevol):

# lvconvert --type cache --cachevol rapido vg/principal

usando dm-writecache (con cachevol):

# lvconvert --type writecache --cachevol rapido vg/principal

Para más alternativas, ver:
atajo de comando dm-cache
dm-cache con LVs de datos y metadatos separados

4. Mostrar LVs

Una vez que el LV rápido ha sido adjuntado al LV principal, lvm reporta el tipo del LV principal como cache o writecache dependiendo del tipo utilizado. Mientras está adjunto, el LV rápido está oculto y se renombra con un sufijo _cvol o _cpool. Es mostrado por lvs -a. El LV _corig o _wcorig representa el LV original sin la caché.

usando dm-cache (con cachepool):

# lvs -ao+devices
  LV                 Pool         Type       Devices
  principal               [rapido_cpool] cache      principal_corig(0)
  [rapido_cpool]                    cache-pool rapido_pool_cdata(0)
  [rapido_cpool_cdata]              linear     /dev/ssd_rapido
  [rapido_cpool_cmeta]              linear     /dev/ssd_rapido
  [principal_corig]                 linear     /dev/disco_duro_lento

usando dm-cache (con cachevol):

# lvs -ao+devices
  LV           Pool        Type   Devices
  principal       [rapido_cvol] cache  principal_corig(0)
  [rapido_cvol]              linear /dev/ssd_rapido
  [principal_corig]             linear /dev/disco_duro_lento

usando dm-writecache (con cachevol):

# lvs -ao+devices
  LV            Pool        Type       Devices
  principal       [rapido_cvol] writecache principal_wcorig(0)
  [rapido_cvol]               linear     /dev/ssd_rapido
  [principal_wcorig]          linear     /dev/disco_duro_lento

5. Usar el LV principal

Utilice el LV hasta que la caché ya no sea deseada, o necesite ser cambiada.

6. Detener la caché

Para detener la caché del LV principal y también eliminar el pool de caché innecesario, use --uncache:

# lvconvert --uncache vg/principal
# lvs -a
  LV   VG Attr       Type   Devices
  principal vg -wi------- linear /dev/disco_duro_lento

Para detener la caché del LV principal, separe el LV rápido del LV principal. Esto cambia el tipo del LV principal de vuelta a lo que era antes de que se adjuntara la caché.

# lvconvert --splitcache vg/principal
# lvs -a
  LV   VG Attr       Type   Devices
  rapido vg -wi------- linear /dev/ssd_rapido
  principal vg -wi------- linear /dev/disco_duro_lento

7. Crear un nuevo LV con caché

Se puede crear un nuevo LV con caché adjunta en el momento de la creación usando el siguiente comando:

# lvcreate --type cache|writecache -n Nombre -L Tamaño
	--cachedevice /dev/ssd_rapido vg /dev/disco_duro_lento

El LV principal se crea con el Nombre y Tamaño especificados a partir del disco_duro_lento. Se crea un LV rápido oculto en el ssd_rapido y luego se adjunta al nuevo LV principal. Si el ssd_rapido no está en uso, se utilizará todo el disco como caché a menos que se use la opción --cachesize para especificar un tamaño para el LV rápido. La opción --cachedevice se puede repetir para usar múltiples discos para el LV rápido.

OPCIONES

opción argumentos

--cachepool LV_Pool_Caché|LV
Pase esta opción a un LV de pool de caché o a un LV estándar. Al usar un pool de caché, lvm coloca los datos de caché y los metadatos de caché en diferentes LVs. Los dos LVs juntos se llaman pool de caché. Esto tiene un rendimiento ligeramente mejor para dm-cache y permite la colocación específica y la selección del tipo de segmento para los volúmenes de datos y metadatos. Un pool de caché se representa como un tipo especial de LV que no se puede usar directamente. Si se pasa un LV estándar con esta opción, lvm lo convertirá primero en un pool de caché combinándolo con otro LV para usarlo como metadatos. Esta opción se puede usar con dm-cache.
--cachevol LV
Pase esta opción a un LV rápido que debe usarse para contener la caché. Con un cachevol, los datos de caché y los metadatos se almacenan en diferentes partes del mismo LV rápido. Esta opción se puede usar con dm-writecache o dm-cache.
--cachedevice PV
Esta opción se puede usar en lugar de --cachevol, en cuyo caso se creará un LV de cachevol utilizando el dispositivo especificado. Esta opción se puede repetir para crear un cachevol utilizando múltiples dispositivos, o se puede especificar un nombre de etiqueta en cuyo caso el cachevol se creará utilizando cualquiera de los dispositivos con la etiqueta dada. Si un dispositivo de caché nombrado no está en uso, se utilizará todo el dispositivo para crear el cachevol. Para crear un cachevol de un tamaño específico a partir de los dispositivos de caché, incluya la opción --cachesize.

dm-cache tamaño de bloque

Un pool de caché tendrá un tamaño de bloque lógico de 4096 bytes si se crea en un dispositivo con un tamaño de bloque lógico de 4096 bytes.

Si un LV principal tiene un tamaño de bloque lógico de 512 (con un sistema de archivos xfs existente que usa ese tamaño), entonces no puede usar un pool de caché con un tamaño de bloque lógico de 4096. Si se adjunta el pool de caché, el LV principal probablemente fallará al montar.

Para evitar este problema, use una opción de mkfs para especificar un tamaño de bloque de 4096 para el sistema de archivos,

or attach the cache pool before running mkfs.

dm-writecache tamaño de bloque

El tamaño de bloque de dm-writecache puede ser de 4096 bytes (el valor predeterminado) o de 512 bytes. El valor predeterminado de 4096 tiene un mejor rendimiento y debe usarse, excepto cuando 512 es necesario por motivos de compatibilidad. El tamaño de bloque de dm-writecache se especifica con --cachesettings block_size=4096|512 al iniciar el caché.

Cuando un sistema de archivos como xfs ya existe en el LV principal antes de la puesta en caché y el sistema de archivos utiliza un tamaño de bloque de 512, el tamaño de bloque de writecache debe establecerse en 512. (Es probable que el sistema de archivos no se monte si se utiliza un tamaño de bloque de writecache de 4096 en este caso.)

Comprueba el tamaño del sector xfs mientras el sistema de archivos está montado:

# xfs_info /dev/vg/main
Busca sectsz=512 o sectsz=4096

El tamaño de bloque de writecache debe elegirse para que coincida con el valor de sectsz de xfs.

También es posible especificar un tamaño de sector de 4096 a mkfs.xfs al crear el sistema de archivos. En este caso, se puede utilizar el tamaño de bloque de writecache de 4096.

El tamaño de bloque de writecache se muestra con el comando:

# lvs -o writecacheblocksize VG/LV

dm-writecache uso de memoria

La cantidad de memoria del sistema principal utilizada por dm-writecache puede ser un factor al seleccionar el tamaño del caché cachevol y el tamaño de bloque de writecache.

•
tamaño de bloque de writecache 4096: cada 100 GiB de cachevol de writecache utiliza un poco más de 2 GiB de memoria del sistema.
•
tamaño de bloque de writecache 512: cada 100 GiB de cachevol de writecache utiliza un poco más de 16 GiB de memoria del sistema.

dm-writecache configuración

Para especificar la configuración de dm-writecache modificable en la línea de comandos, usa:
--cachesettings 'opción=N' o
--cachesettings 'opción1=N opción2=N ...'

Por ejemplo, --cachesettings 'high_watermark=90 writeback_jobs=4'.

Para incluir la configuración al iniciar el caché, ejecuta:

# lvconvert --type writecache --cachevol fast \
	--cachesettings 'opción=N' vg/main

Para cambiar la configuración de un LV de writecache existente, ejecuta:

# lvchange --cachesettings 'opción=N' vg/main

Para borrar toda la configuración que se haya aplicado, ejecuta:

# lvchange --cachesettings '' vg/main

Para ver la configuración que se ha aplicado a un LV de writecache, ejecuta:

# lvs -o cachesettings vg/main

La configuración modificable es:

high_watermark = <porcentaje>
Inicia la escritura de vuelta cuando el uso del caché de escritura alcanza este porcentaje (0-100).
low_watermark = <porcentaje>
Detiene la escritura de vuelta cuando el uso del caché de escritura alcanza este porcentaje (0-100).
writeback_jobs = <conteo>
Limita el número de bloques que están en tránsito durante la escritura de vuelta. Establecer este valor reduce el rendimiento de la escritura de vuelta, pero puede mejorar la latencia de las solicitudes de lectura.
autocommit_blocks = <conteo>
Cuando la aplicación escribe esta cantidad de bloques sin emitir la solicitud FLUSH, los bloques se confirman automáticamente.
autocommit_time = <milisegundos>
Los datos se confirman automáticamente si pasa este tiempo y no se recibe ninguna solicitud FLUSH.
fua = 0|1
Utiliza la bandera FUA al escribir datos de la memoria persistente en el dispositivo subyacente. Solo aplicable a la memoria persistente.
nofua = 0|1
No utilices la bandera FUA al escribir datos y envía la solicitud FLUSH después. Algunos dispositivos subyacentes funcionan mejor con fua, otros con nofua. Es necesario realizar pruebas para determinar cuál. Solo aplicable a la memoria persistente.
cleaner = 0|1
Establecer cleaner=1 activa el modo limpiador de caché de escritura en el que los datos se descargan gradualmente del caché. Si esto se hace antes de separar el caché de escritura, el comando splitcache tendrá poca o ninguna descarga que realizar. Si no se hace de antemano, el comando splitcache activa el modo limpiador y espera a que la descarga se complete antes de separar el caché de escritura. Agregar cleaner=0 al comando splitcache omitirá el modo limpiador, y cualquier descarga requerida se realiza en la suspensión del dispositivo.
max_age = <milisegundos>
Especifica la edad máxima de un bloque en milisegundos. Si un bloque se almacena en el caché durante demasiado tiempo, se escribirá en el dispositivo subyacente y se limpiará.
metadata_only = 0|1
Solo se promociona metadatos al caché. Esta opción mejora el rendimiento para cargas de trabajo REQ_META más pesadas.
pause_writeback = <milisegundos>
Pausa la escritura de vuelta si hubo alguna E/S de escritura redirigida al volumen de origen en los últimos milisegundos.

dm-writecache usando perfiles de metadatos

Además de especificar la configuración de writecache en la línea de comandos, también se puede configurar en lvm.conf(5), o en un archivo de perfil, utilizando la estructura de configuración allocation/cache_settings/writecache que se muestra a continuación.

Es posible preparar varios archivos de perfil diferentes en el directorio /etc/lvm/profile y especificar el nombre del archivo del perfil al iniciar writecache.

Ejemplo

# cat <<EOF > /etc/lvm/profile/cache_writecache.profile
allocation {
cache_settings {
writecache {
high_watermark=60
writeback_jobs=1024
}
}
}
EOF
# lvcreate -an -L10G --name fast vg /dev/fast_ssd
# lvcreate --type writecache -L10G --name main  --cachevol fast \
   --metadataprofile cache_writecache vg /dev/slow_hdd

dm-cache con LVs de datos y metadatos separados

La forma preferida de usar dm-cache es colocar los metadatos de caché y los datos de caché en LVs separados. Para hacer esto, se crea un "pool de caché", que es un LV especial que hace referencia a dos LVs secundarios, uno para datos y otro para metadatos.

Para crear un pool de caché de un tamaño de datos determinado y dejar que lvm2 calcule el tamaño de metadatos apropiado:

# lvcreate --type cache-pool -L DataSize -n fast vg /dev/fast_ssd1

Para crear un pool de caché a partir de un LV separado y dejar que lvm2 calcule el tamaño apropiado de metadatos de caché:

# lvcreate -n fast -L DataSize vg /dev/fast_ssd1
# lvconvert --type cache-pool vg/fast /dev/fast_ssd1

Para crear un pool de caché a partir de dos LVs separados:

# lvcreate -n fast -L DataSize vg /dev/fast_ssd1
# lvcreate -n fastmeta -L MetadataSize vg /dev/fast_ssd2
# lvconvert --type cache-pool --poolmetadata fastmeta vg/fast

Luego, usa el LV del pool de caché para iniciar la puesta en caché del LV principal:

# lvconvert --type cache --cachepool fast vg/main

Una variación del mismo procedimiento crea automáticamente un pool de caché al iniciar la puesta en caché. Para hacer esto, usa un LV estándar como --cachepool (este contendrá los datos de caché) y otro LV estándar como --poolmetadata (este contendrá los metadatos de caché). LVM creará un LV de pool de caché a partir de los dos LVs especificados y utilizará el pool de caché para iniciar la puesta en caché del LV principal.

# lvcreate -n fast -L DataSize vg /dev/fast_ssd1
# lvcreate -n fastmeta -L MetadataSize vg /dev/fast_ssd2
# lvconvert --type cache --cachepool fast \
        --poolmetadata fastmeta vg/main

dm-cache modos de caché

El modo de caché dm-cache predeterminado es "writethrough" (escritura directa). Writethrough asegura que cualquier dato escrito se almacenará tanto en el caché como en el LV de origen. La pérdida de un dispositivo asociado con el caché en este caso no significaría la pérdida de datos.

Un segundo modo de caché es "writeback" (escritura diferida). Writeback retrasa la escritura de bloques de datos del caché al LV de origen. Este modo aumentará el rendimiento, pero la pérdida de un dispositivo de caché puede resultar en pérdida de datos.

Con la opción --cachemode, el modo de caché se puede establecer al iniciar la puesta en caché, o cambiar en un LV que ya está en caché. El modo de caché actual se puede mostrar con la opción de reporte cache_mode:

# lvs -o+cache_mode VG/LV

lvm.conf(5) allocation/cache_mode – define el modo de caché predeterminado.

# lvconvert --type cache --cachemode writethrough \
        --cachepool fast vg/main
# lvconvert --type cache --cachemode writethrough \
        --cachevol fast vg/main

dm-cache tamaño de fragmento

El tamaño de los bloques de datos gestionados por dm-cache se puede especificar con la opción --chunksize al iniciar la puesta en caché. La unidad predeterminada es KiB. El valor debe ser un múltiplo de 32 KiB entre 32 KiB y 1 GiB. Los fragmentos de caché mayores de 512 KiB solo deben usarse cuando sea necesario.

Usar un tamaño de fragmento demasiado grande puede resultar en un uso ineficiente del caché, en el que lecturas y escrituras pequeñas hacen que grandes secciones de un LV se almacenen en el caché. También puede requerir aumentar el umbral de migración, que por defecto es de 2048 sectores (1 MiB). Lvm2 asegura que el umbral de migración tenga al menos 8 fragmentos de tamaño. Esto puede, en algunos casos, resultar en una carga de ancho de banda muy alta de transferencia de datos entre el LV de caché y su LV de origen de caché. Sin embargo, elegir un tamaño de fragmento demasiado pequeño puede resultar en más sobrecarga al intentar gestionar los numerosos fragmentos que se mapean en el caché. La sobrecarga puede incluir tanto un tiempo de CPU excesivo buscando fragmentos, como memoria excesiva rastreando fragmentos.

Comando para mostrar el tamaño del fragmento:

# lvs -o+chunksize VG/LV

NOMBRE

lvmcache - LVM caching

DESCRIPCIÓN

El subsistema dm-cache es un dispositivo de mapeo de destino implementado en el subsistema de destino de dispositivos (Device Mapper) del kernel de Linux. Permite que un dispositivo de almacenamiento rápido (llamado dispositivo de caché) sea utilizado para almacenar datos de un dispositivo de almacenamiento más lento (llamado dispositivo de origen) para mejorar el rendimiento de acceso.

lvmcache utiliza el subsistema dm-cache para proporcionar una interfaz de alto nivel para la creación y gestión de dispositivos de caché.

Un dispositivo de caché se compone de un dispositivo de origen, un dispositivo de caché y un dispositivo de metadatos de caché. Estos se agrupan en un pool de caché y luego se adjuntan a un dispositivo de origen para formar un dispositivo de caché.

El dispositivo de origen es el dispositivo de almacenamiento principal. El dispositivo de caché se utiliza para almacenar copias de los datos del dispositivo de origen. El dispositivo de metadatos de caché almacena información sobre qué bloques de datos se almacenan en el dispositivo de caché, por ejemplo, si están sucios o limpios.

El dispositivo de caché puede ser un solo dispositivo de bloque (por ejemplo, un SSD). El dispositivo de metadatos de caché debe ser un dispositivo de bloque más pequeño. Puede ser un dispositivo separado o un pequeño LV separado dentro del mismo dispositivo de origen o en un dispositivo diferente.

Se pueden usar políticas de caché para controlar cómo se gestionan los datos en el dispositivo de caché. La política predeterminada es smq (simple timed queue merge), que intenta optimizar el rendimiento de lectura y escritura.

El dispositivo de origen y el dispositivo de caché pueden tener diferentes tamaños. El tamaño del dispositivo de caché determina la cantidad de datos que se pueden almacenar en caché. El tamaño del dispositivo de metadatos de caché depende del tamaño del dispositivo de caché y del formato de metadatos utilizado.

Se puede configurar un dispositivo de metadatos de caché separado dentro del mismo pool de caché para la redundancia. Esto se conoce como metadatos de pool de caché "redundantes" o "spare".

El subsistema dm-cache también admite la creación de pools de caché con un dispositivo de metadatos que requiere su propio PV independiente.

El modo de caché se puede establecer en writethrough o writeback. En modo writethrough, las escrituras se envían tanto al dispositivo de caché como al dispositivo de origen, lo que garantiza la durabilidad de los datos pero puede ser más lento. En modo writeback, las escrituras solo se envían al dispositivo de caché inicialmente y se copian al dispositivo de origen más tarde, lo que puede mejorar el rendimiento pero requiere que el caché se vacíe correctamente antes de desmontarlo o apagar el sistema.

Los pools de caché se pueden crear como LVs con un tipo especial cache-pool.

Los pools de caché pueden ser convertidos a LVs de metadatos thin (delgado).

Se puede configurar un dispositivo de metadatos de caché de "tamaño cero" para usar un dispositivo de metadatos de caché dedicado y separado.

Los pools de caché pueden ser creados con un segundo dispositivo de metadatos para redundancia.

El tamaño de los metadatos del pool de caché se puede ajustar.

Las instalaciones de clúster pueden crear pools de caché de forma redundante.

Los pools de caché se pueden convertir a LVs delgados.

Se puede añadir un disco de metadatos spare a un pool de caché existente.

Los pools de caché pueden ser creados con un dispositivo de metadatos que está en un PV separado y dedicado.

Se pueden obtener las opciones de configuración del pool de caché de LVM mediante el comando lvmconfig.

El tamaño del fragmento del pool de caché se puede controlar para optimizar el rendimiento. El valor predeterminado se puede ver usando lvmconfig.

Se puede verificar el umbral de migración de un LV en caché en ejecución con el comando lvs.

OPCIONES

Las opciones se pasan a lvcreate y lvchange para configurar el caché. Consulte lvcreate(8) y lvchange(8) para obtener una descripción completa de las opciones.

dm-cache cache mode
Controla si las escrituras se envían tanto al dispositivo de caché como al dispositivo de origen (writethrough, el valor predeterminado) o si solo se envían al dispositivo de caché inicialmente y se copian al dispositivo de origen más tarde (writeback). Las escrituras en modo writeback pueden mejorar el rendimiento, pero requieren que el caché se vacíe correctamente antes de desmontarlo o apagar el sistema.
dm-cache cache pool chunk size
Controla el tamaño del fragmento del pool de caché. Los fragmentos son las unidades de datos más pequeñas que dm-cache gestiona. Un tamaño de fragmento más pequeño puede reducir la sobrecarga en LVs pequeños, mientras que un tamaño de fragmento más grande puede mejorar el rendimiento en LVs grandes. El valor predeterminado es 64KiB. El valor se puede establecer usando lvm.conf(5) o la opción --cachesettings en lvcreate o lvchange.

dm-cache cache settings

Para establecer la configuración de caché de dm-cache use:

--cachesettings 'option1=N option2=N ...'

Para anular/eliminar la configuración de caché y restaurar su valor predeterminado del kernel use la palabra clave especial 'default' como parámetro de opción:

--cachesettings 'option1=default option2=default ...'

dm-cache migration threshold cache setting

La migración de datos entre el origen y el LV de caché utiliza ancho de banda. El usuario puede establecer un límite para evitar que ocurra más de una cierta cantidad de migración en un momento dado. Actualmente, dm-cache no tiene en cuenta el tráfico de E/S normal que va a los dispositivos.

El usuario puede establecer el umbral de migración a través de la configuración de la política de caché como "migration_threshold=<#sectores>" para establecer el número máximo de sectores que se migran, siendo el valor predeterminado 2048 sectores (1 MiB) o 8 fragmentos de caché, el que sea mayor de esos dos valores.

Comando para establecer el umbral de migración a 2 MiB (4096 sectores):

# lvcreate --cachesettings 'migration_threshold=4096' VG/LV

Comando para mostrar el umbral de migración:

# lvs -o+kernel_cache_settings,cache_settings VG/LV
# lvs -o+chunksize VG/LV

Comando para restaurar/revertir al valor predeterminado:

# lvchange --cachesettings 'migration_threshold=default' VG/LV

dm-cache cache policy

El subsistema dm-cache tiene parámetros adicionales por LV: la política de caché a utilizar y, posiblemente, parámetros ajustables para la política de caché. Actualmente hay tres políticas disponibles: "smq" es la política predeterminada, "mq" es una implementación anterior y "cleaner" se utiliza para forzar al caché a escribir de vuelta (vaciar) todas las escrituras en caché en el LV de origen.

La política "mq" anterior tiene varios parámetros ajustables. Los valores predeterminados se eligen para que sean adecuados para la mayoría de los sistemas, pero en circunstancias especiales, cambiar la configuración puede mejorar el rendimiento. Sin embargo, los kernels más nuevos alias esta política con la política "smq". Por lo tanto, la configuración de caché utilizada para configurar la política "mq" [random_threshold, sequential_threshold, discard_promote_adjustment, read_promote_adjustment, write_promote_adjustment] se ignora silenciosamente y el rendimiento coincide con "smq".

Con las opciones --cachepolicy y --cachesettings, la política de caché y la configuración se pueden establecer cuando se inicia el caché, o cambiar en un LV en caché existente (ambas opciones se pueden usar juntas). La política de caché actual y la configuración se pueden mostrar con las opciones de informe cache_policy y cache_settings:

# lvs -o+cache_policy,cache_settings VG/LV

Cambiar la política de caché y la configuración de un LV existente.

# lvchange --cachepolicy mq --cachesettings \
	'migration_threshold=2048 random_threshold=4' vg/main

lvm.conf(5) allocation/cache_policy – define la política de caché predeterminada.

lvm.conf(5) allocation/cache_settings – define la configuración de caché predeterminada.

dm-cache using metadata profiles

Los pools de caché permiten establecer una variedad de opciones. Muchas de estas configuraciones se pueden especificar en lvm.conf o en la configuración de perfiles. Puede preparar una serie de perfiles diferentes en el directorio /etc/lvm/profile y simplemente especificar el nombre del archivo de perfil de metadatos al almacenar en caché un LV o crear un pool de caché. Consulte la salida de:

# lvmconfig --type default --withcomments

para una descripción detallada de todas las configuraciones de caché individuales.

Ejemplo

# cat <<EOF > /etc/lvm/profile/cache_big_chunk.profile
allocation {
cache_pool_metadata_require_separate_pvs=0
cache_pool_chunk_size=512
cache_metadata_format=2
cache_mode="writethrough"
cache_policy="smq"
cache_settings {
smq {
migration_threshold=8192
}
}
}
EOF
# lvcreate --cache -L10G --metadataprofile cache_big_chunk vg/main \
        /dev/fast_ssd
# lvcreate --cache -L10G vg/main --config \
        'allocation/cache_pool_chunk_size=512' /dev/fast_ssd

dm-cache spare metadata LV

Consulte lvmthin(7) para obtener una descripción del LV "pool metadata spare". El mismo concepto se utiliza para los pools de caché.

dm-cache metadata formats

Hay dos formatos de disco para los metadatos de dm-cache. El formato de metadatos se puede especificar con --cachemetadataformat cuando se inicia el caché, y no se puede cambiar. El formato 2 tiene un mejor rendimiento; es más compacto y almacena bits sucios en un árbol b separado, lo que mejora la velocidad de apagado del caché. Con auto, lvm selecciona la mejor opción proporcionada por el módulo del kernel dm-cache actual.

RAID1 cache device

RAID1 se puede usar para crear el LV rápido que contiene el caché, de modo que pueda tolerar fallos de dispositivos. (Al usar dm-cache con LVs de datos y metadatos separados, cada uno de los sub-LVs puede usar RAID1).

# lvcreate -n main -L Size vg /dev/slow
# lvcreate --type raid1 -m 1 -n fast -L Size vg /dev/ssd1 /dev/ssd2
# lvconvert --type cache --cachevol fast vg/main

dm-cache command shortcut

Se puede usar un solo comando para almacenar en caché el LV principal con la creación automática de un pool de caché:

# lvcreate --cache --size CacheDataSize VG/LV [FastPVs]

o la variante más larga

# lvcreate --type cache --size CacheDataSize \
        --name NameCachePool VG/LV [FastPVs]

En este comando, el LV especificado ya existe y es el LV principal que se va a almacenar en caché. El comando crea un nuevo pool de caché con el tamaño y el nombre dados, o el nombre se selecciona automáticamente de una secuencia lvolX_cpool, utilizando los PV rápidos opcionalmente especificados (típicamente un ssd). Luego, adjunta el nuevo pool de caché al LV principal existente para comenzar el almacenamiento en caché.

(Nota: asegúrese de que el LV principal especificado sea un LV estándar. Si se especifica erróneamente un LV de pool de caché, el comando hace algo diferente).

(Nota: la opción type se interpreta de manera diferente por este comando que por los comandos lvcreate normales en los que --type especifica el tipo del LV recién creado. En este caso, se está creando un LV con el tipo cache-pool, y el LV principal existente se está convirtiendo al tipo cache.)
