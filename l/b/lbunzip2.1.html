LBZIP2(1) Comandos de usuario LBZIP2(1)

NOMBRE

lbzip2 - utilidad bzip2 paralela

SINOPSIS

lbzip2|bzip2 [-n WTHRS] [-k|-c|-t] [-d] [-1 .. -9] [-f] [-s] [-u] [-v] [-S] [ ARCHIVO ... ]

lbunzip2|bunzip2 [-n WTHRS] [-k|-c|-t] [-z] [-f] [-s] [-u] [-v] [-S] [ ARCHIVO ... ]

lbzcat|bzcat [-n WTHRS] [-z] [-f] [-s] [-u] [-v] [-S] [ ARCHIVO ... ]

lbzip2|bzip2|lbunzip2|bunzip2|lbzcat|bzcat -h

DESCRIPCIÓN

Comprime o descomprime los operandos ARCHIVO o la entrada estándar a archivos normales o la salida estándar usando el algoritmo de compresión de texto de ordenamiento por bloques de Burrows-Wheeler. La utilidad lbzip2 emplea múltiples hilos y un divisor limitado por entrada incluso al descomprimir archivos .bz2 creados por el bzip2 estándar.

La compresión es generalmente considerablemente mejor que la lograda por compresores más convencionales basados en LZ77/LZ78, y competitiva con todos menos los mejores de la familia de compresores estadísticos PPM.

La compresión se realiza siempre, incluso si el archivo comprimido es ligeramente más grande que el original. La expansión en el peor de los casos es para archivos de longitud cero, que se expanden a catorce bytes. Los datos aleatorios (incluida la salida de la mayoría de los compresores de archivos) se codifican con una expansión asintótica de alrededor del 0.5%.

Las opciones de línea de comandos son deliberadamente muy similares a las de bzip2 y gzip, pero no son idénticas.

INVOCACIÓN

El modo de operación predeterminado es la compresión. Si la utilidad se invoca como lbunzip2 o bunzip2, el modo se cambia a descompresión. Llamar a la utilidad como lbzcat o bzcat selecciona la descompresión, con el flujo de bytes descomprimido escrito en la salida estándar.

OPCIONES

-n WTHRS
Establece el número de hilos de (des)compresión a WTHRS. Si no se especifica esta opción, lbzip2 intenta consultar al sistema el número de procesadores en línea (si tanto el entorno de compilación como el entorno de ejecución lo soportan), o sale con un error (si no puede determinar el número de procesadores en línea).
-k, --keep
No eliminar los operandos ARCHIVO después de una (des)compresión exitosa. Abrir archivos de entrada regulares con más de un enlace.
-c, --stdout
Escribir la salida a la salida estándar, incluso cuando hay operandos ARCHIVO presentes. Implica -k y excluye -t.
-t, --test
Probar la descompresión; descartar la salida en lugar de escribirla en archivos o en la salida estándar. Implica -k y excluye -c. Aproximadamente equivalente a pasar -c y redirigir la salida estándar al sumidero de bits.
-d, --decompress
Forzar la descompresión sobre el modo de operación seleccionado por el nombre de invocación.
-z, --compress
Forzar la compresión sobre el modo de operación seleccionado por el nombre de invocación.
-1 .. -9
Establecer el tamaño del bloque de compresión a 100K .. 900K, en incrementos de 100K. Ignorado durante la descompresión. Ver también la sección TAMAÑO DE BLOQUE más abajo.
--fast
Alias para -1.
--best
Alias para -9. Este es el valor predeterminado.
-f, --force
Abrir archivos de entrada no regulares. Abrir archivos de entrada con más de un enlace, rompiendo enlaces cuando -k no se especifica además. Intentar eliminar cada archivo de salida antes de abrirlo. Por defecto, lbzip2 no sobrescribirá los archivos existentes; si desea que esto suceda, debe especificar -f. Si también se dan -c y -d, no rechazar archivos que no estén en formato bzip2, simplemente cópielos sin cambios; sin -f, lbzip2 se detendría después de encontrar un archivo que no esté en formato bzip2.
-s, --small
Reducir el uso de memoria a costa del rendimiento.
-u, --sequential
Realizar la división de bloques de entrada secuencialmente. Esto puede mejorar la relación de compresión y disminuir el uso de CPU, pero degradará la escalabilidad.
-v, --verbose
Ser más verboso. Imprimir información más detallada sobre el progreso de (des)compresión en la salida estándar: antes de procesar cada archivo, imprimir un mensaje indicando los nombres de los archivos de entrada y salida; durante la (des)compresión, imprimir un porcentaje aproximado de completitud y tiempo estimado de llegada (solo si la salida estándar está conectada a una terminal); después de procesar cada archivo, imprimir un mensaje que muestre la relación de compresión, el ahorro de espacio, el tiempo total de compresión (tiempo real) y la velocidad promedio de (des)compresión (bytes de datos planos procesados por segundo).
-S
Imprimir estadísticas de variables de condición en la salida estándar para cada operación de (des)compresión completada. Útil en perfilado.
-q, --quiet, --repetitive-fast, --repetitive-best, --exponential
Aceptado por compatibilidad con bzip2, de lo contrario se ignora.
-h, --help
Imprimir ayuda sobre el uso de la línea de comandos en la salida estándar y salir exitosamente.
-L, --license, -V, --version
Imprimir información de licencia y versión en la salida estándar y salir exitosamente.

AMBIENTE

LBZIP2, BZIP2, BZIP
Antes de analizar la línea de comandos, lbzip2 inserta el contenido de estas variables, en el orden especificado, entre el nombre de invocación y el resto de la línea de comandos. Los tokens se separan por espacios y tabulaciones, que no se pueden escapar.

OPERANDOS

ARCHIVO
Especificar archivos para comprimir o descomprimir.

Los ARCHIVOs con sufijos de nombre .bz2, .tbz, .tbz2 y .tz2 se omitirán al comprimir. Al descomprimir, los sufijos .bz2 se eliminarán de los nombres de archivo de salida; los sufijos .tbz, .tbz2 y .tz2 se reemplazarán por .tar; otros nombres de archivo se añadirán con .out. Si se entrega una señal INT o TERM a lbzip2, entonces elimina el archivo de salida regular actualmente abierto antes de salir.

Si no se proporciona ARCHIVO, lbzip2 funciona como un filtro, procesando la entrada estándar a la salida estándar. En este caso, lbzip2 se negará a escribir salida comprimida en una terminal (o leer entrada comprimida de una terminal), ya que esto sería completamente incomprensible y, por lo tanto, inútil.

ESTADO DE SALIDA

0
si lbzip2 finaliza exitosamente. Esto presupone que siempre que lo intenta, lbzip2 nunca falla al escribir en la salida estándar.
1
si lbzip2 encuentra un error fatal.
4
si lbzip2 emite advertencias sin encontrar un error fatal. Esto presupone que siempre que lo intenta, lbzip2 nunca falla al escribir en la salida estándar.
SIGPIPE, SIGXFSZ
si lbzip2 tiene la intención de salir con el estado 1 debido a cualquier error fatal, pero cualquier señal de este tipo con la acción SIG_DFL heredada fue

EXIT STATUS

lbzip2 exits with a non-zero status if an error occurs, otherwise zero.

Non-zero exit codes are:

1
for a critical error (e.g. running out of memory, failing to allocate a thread, etc.).
2
for a non-critical error (e.g. an input file doesn't exist or cannot be read).
3
if a runtime assertion fails (i.e. lbzip2 detects a bug in itself).
4
if the command line is erroneous.
5
if the compressed data is corrupt.

In case of error, the file currently being processed (if any) is deleted. If the error is a signal received by lbzip2, then the output file is deleted, and then lbzip2 exits by re-raising (one of) the received signal(s).

The signals received by lbzip2 are:

SIGABRT
if a runtime assertion fails (i.e. lbzip2 detects a bug in itself). Hopefully whoever compiled your binary wasn't bold enough to #define NDEBUG.
SIGINT, SIGTERM
lbzip2 catches these signals so that it can remove an interrupted output file. In such cases, lbzip2 exits by re-raising (one of) the received signal(s).

BLOCK SIZE

lbzip2 compresses large files in blocks. It can operate at various block sizes, ranging from 100k to 900k in 100k steps, and it allocates only as much memory as it needs to. The block size affects both the compression ratio achieved, and the amount of memory needed both for compression and decompression. Compression and decompression speed is virtually unaffected by block size, provided that the file being processed is large enough to be split among all worker threads.

The flags -1 through -9 specify the block size to be 100,000 bytes through 900,000 bytes (the default) respectively. At decompression-time, the block size used for compression is read from the compressed file -- the flags -1 to -9 are irrelevant to and so ignored during decompression.

Larger block sizes give rapidly diminishing marginal returns; most of the compression comes from the first two or three hundred k of block size, a fact worth bearing in mind when using lbzip2 on small machines. It is also important to appreciate that the decompression memory requirement is set at compression-time by the choice of block size. In general you should try and use the largest block size memory constraints allow.

Another significant point applies to small files. By design, only one of lbzip2's worker threads can work on a single block. This means that if the number of blocks in the compressed file is less than the number of processors online, then some of worker threads will remain idle for the entire time. Compressing small files with smaller block sizes can therefore significantly increase both compression and decompression speed. The speed difference is more noticeable as the number of CPU cores grows.

ERROR HANDLING

Dealing with error conditions is the least satisfactory aspect of lbzip2. The policy is to try and leave the filesystem in a consistent state, then quit, even if it means not processing some of the files mentioned in the command line.

`A consistent state' means that a file exists either in its compressed or uncompressed form, but not both. This boils down to the rule `delete the output file if an error condition occurs, leaving the input intact'. Input files are only deleted when we can be pretty sure the output file has been written and closed successfully.

RESOURCE ALLOCATION

lbzip2 needs various kinds of system resources to operate. Those include memory, threads, mutexes and condition variables. The policy is to simply give up if a resource allocation failure occurs.

Resource consumption grows linearly with number of worker threads. If lbzip2 fails because of lack of some resources, decreasing number of worker threads may help. It would be possible for lbzip2 to try to reduce number of worker threads (and hence the resource consumption), or to move on to subsequent files in the hope that some might need less resources, but the complications for doing this seem more trouble than they are worth.

DAMAGED FILES

lbzip2 attempts to compress data by performing several non-trivial transformations on it. Every compression of a file implies an assumption that the compressed file can be decompressed to reproduce the original. Great efforts in design, coding and testing have been made to ensure that this program works correctly. However, the complexity of the algorithms, and, in particular, the presence of various special cases in the code which occur with very low but non-zero probability make it very difficult to rule out the possibility of bugs remaining in the program. That is not to say this program is inherently unreliable. Indeed, I very much hope the opposite is true -- lbzip2 has been carefully constructed and extensively tested.

As a self-check for your protection, lbzip2 uses 32-bit CRCs to make sure that the decompressed version of a file is identical to the original. This guards against corruption of the compressed data, and against undiscovered bugs in lbzip2 (hopefully unlikely). The chances of data corruption going undetected is microscopic, about one chance in four billion for each file processed. Be aware, though, that the check occurs upon decompression, so it can only tell you that that something is wrong.

CRCs can only detect corrupted files, they can't help you recover the original, uncompressed data. However, because of the block nature of the compression algorithm, it may be possible to recover some parts of the damaged file, even if some blocks are destroyed.

BUGS

Separate input files don't share worker threads; at most one input file is worked on at any moment.
