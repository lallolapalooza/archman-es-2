NOMBRE

lxc.container.conf - archivo de configuración de contenedores LXC

DESCRIPCIÓN

LXC es el runtime de contenedores Linux de bajo nivel, bien conocido y ampliamente probado. Ha estado en desarrollo activo desde 2008 y se ha demostrado en entornos de producción críticos en todo el mundo. Algunos de sus contribuyentes principales son las mismas personas que ayudaron a implementar varias características de contenedorización conocidas dentro del kernel de Linux.

El enfoque principal de LXC son los contenedores de sistema. Es decir, contenedores que ofrecen un entorno lo más cercano posible al que obtendrías de una VM, pero sin la sobrecarga que implica ejecutar un kernel separado y simular todo el hardware.

Esto se logra a través de una combinación de características de seguridad del kernel como namespaces, control de acceso obligatorio y cgroups.

LXC tiene soporte para contenedores no privilegiados. Los contenedores no privilegiados son contenedores que se ejecutan sin ningún privilegio. Esto requiere soporte para namespaces de usuario en el kernel en el que se ejecuta el contenedor. LXC fue el primer runtime en soportar contenedores no privilegiados después de que los namespaces de usuario se fusionaran en el kernel principal.

En esencia, los namespaces de usuario aíslan conjuntos dados de UID y GID. Esto se logra estableciendo un mapeo entre un rango de UID y GID en el host a un rango diferente (no privilegiado) de UID y GID en el contenedor. El kernel traducirá este mapeo de tal manera que dentro del contenedor todos los UID y GID aparezcan como esperarías del host, mientras que en el host estos UID y GID son de hecho no privilegiados. Por ejemplo, un proceso que se ejecuta como UID y GID 0 dentro del contenedor podría aparecer como UID y GID 100000 en el host. La implementación y los detalles de funcionamiento se pueden obtener de la página del manual correspondiente de namespaces de usuario. Los mapeos de UID y GID se pueden definir con la clave lxc.idmap.

Las claves de configuración de namespaces de Linux utilizan puntos simples. Esto significa que las claves de configuración complejas como lxc.net.0 exponen varias subclaves como lxc.net.0.type, lxc.net.0.link, lxc.net.0.ipv6.address, y otras para una configuración aún más detallada.

CONFIGURACIÓN

Para facilitar la administración de múltiples contenedores relacionados, es posible que un archivo de configuración de contenedor cause la carga de otro archivo. Por ejemplo, la configuración de red se puede definir en un archivo común que sea incluido por múltiples contenedores. Luego, si los contenedores se mueven a otro host, solo un archivo puede necesitar ser actualizado.

lxc.include
Especifica el archivo a incluir. El archivo incluido debe tener el mismo formato de archivo de configuración lxc válido.

ARQUITECTURA

Permite establecer la arquitectura para el contenedor. Por ejemplo, establecer una arquitectura de 32 bits para un contenedor que ejecuta binarios de 32 bits en un host de 64 bits. Esto corrige los scripts del contenedor que dependen de la arquitectura para realizar algunas tareas, como descargar paquetes.

lxc.arch
Especifica la arquitectura para el contenedor.

Algunas opciones válidas son x86, i686, x86_64, amd64

NOMBRE DE HOST

La sección utsname define el nombre de host a establecer para el contenedor. Esto significa que el contenedor puede establecer su propio nombre de host sin cambiar el del sistema. Esto hace que el nombre de host sea privado para el contenedor.

lxc.uts.name
especifica el nombre de host para el contenedor

SEÑAL DE DETENCIÓN

Permite especificar el nombre o número de señal que se envía al proceso init del contenedor para apagar limpiamente el contenedor. Diferentes sistemas init podrían usar diferentes señales para realizar una secuencia de apagado limpia. Esta opción permite especificar la señal en el estilo de kill(1), por ejemplo, SIGPWR, SIGRTMIN+14, SIGRTMAX-10 o un número simple. La señal por defecto es SIGPWR.

lxc.signal.halt
especifica la señal utilizada para detener el contenedor

SEÑAL DE REINICIO

Permite especificar el nombre o número de señal para reiniciar el contenedor. Esta opción permite especificar la señal en el estilo de kill(1), por ejemplo, SIGTERM, SIGRTMIN+14, SIGRTMAX-10 o un número simple. La señal por defecto es SIGINT.

lxc.signal.reboot
especifica la señal utilizada para reiniciar el contenedor

SEÑAL DE PARADA

Permite especificar el nombre o número de señal para apagar forzosamente el contenedor. Esta opción permite especificar la señal en el estilo de kill(1), por ejemplo, SIGKILL, SIGRTMIN+14, SIGRTMAX-10 o un número simple. La señal por defecto es SIGKILL.

lxc.signal.stop
especifica la señal utilizada para detener el contenedor

COMANDO INIT

Establece el comando a usar como sistema init para los contenedores.

lxc.execute.cmd
Ruta absoluta desde el rootfs del contenedor al binario a ejecutar por defecto. Esto tiene más sentido para lxc-execute.
lxc.init.cmd
Ruta absoluta desde el rootfs del contenedor al binario a usar como init. Esto tiene más sentido para lxc-start. Por defecto es /sbin/init.

DIRECTORIO DE TRABAJO INIT

Establece la ruta absoluta dentro del contenedor como directorio de trabajo para los contenedores. LXC cambiará a este directorio antes de ejecutar init.

lxc.init.cwd
Ruta absoluta dentro del contenedor a usar como directorio de trabajo.

ID INIT

Establece el UID/GID a usar para el sistema init y comandos subsiguientes. Tenga en cuenta que usar un UID no root al iniciar un contenedor de sistema probablemente no funcionará debido a la falta de privilegios. Establecer el UID/GID es útil principalmente al ejecutar contenedores de aplicaciones. Por defecto: UID(0), GID(0)

lxc.init.uid
UID a usar para init.
lxc.init.gid
GID a usar para init.

PLANIFICACIÓN DE NÚCLEOS

La planificación de núcleos define si la carga útil del contenedor está marcada como programable en el mismo núcleo. Hacer esto hará que el planificador del kernel asegure que las tareas que no están en el mismo grupo nunca se ejecuten simultáneamente en un núcleo. Esto puede servir como una medida de seguridad adicional para evitar que la carga útil del contenedor use ataques de hyper-threading cruzado.

lxc.sched.core
Los únicos valores permitidos son 0 y 1. Establezca esto en 1 para crear un dominio de planificación de núcleos para el contenedor o 0 para no crearlo. Si no se establece explícitamente, no se creará ningún dominio de planificación de núcleos para el contenedor.

PROC

Con

proc filesystem for the container.

lxc.proc.[nombre_del_archivo_proc]
Especifica el nombre del archivo proc a establecer. Los nombres de archivo disponibles son los que aparecen en /proc/PID/. Ejemplo: 
              lxc.proc.oom_score_adj = 10

EFÍMERO

Permite especificar si un contenedor será destruido al apagarse.

lxc.ephemeral
Los únicos valores permitidos son 0 y 1. Establezca esto en 1 para destruir un contenedor al apagar.

RED

La sección de red define cómo se virtualiza la red en el contenedor. La virtualización de red actúa en la capa dos. Para utilizar la virtualización de red, se deben especificar parámetros para definir las interfaces de red del contenedor. Se pueden asignar y utilizar varias interfaces virtuales en un contenedor, incluso si el sistema tiene solo una interfaz de red física.

lxc.net
puede usarse sin valor para borrar todas las opciones de red previas.
lxc.net.[i].type
especifica qué tipo de virtualización de red se utilizará para el contenedor. Debe especificarse antes que cualquier otra opción en el dispositivo de red. Se pueden especificar varias redes usando un índice adicional i después de todas las claves lxc.net.*. Por ejemplo, lxc.net.0.type = veth y lxc.net.1.type = veth especifican dos redes diferentes del mismo tipo. Todas las claves que compartan el mismo índice i se tratarán como pertenecientes a la misma red. Por ejemplo, lxc.net.0.link = br0 pertenecerá a lxc.net.0.type. Actualmente, los diferentes tipos de virtualización pueden ser:

empty: creará solo la interfaz de loopback.

veth: se crea un dispositivo de par ethernet virtual con un lado asignado al contenedor y el otro lado al host. lxc.net.[i].veth.mode especifica el modo que utilizará el padre veth en el host. Los modos aceptados son bridge y router. El modo por defecto es bridge si no se especifica. En modo bridge, el lado del host se conecta a un bridge especificado por la opción lxc.net.[i].link. Si no se especifica el enlace del bridge, se creará el dispositivo de par veth pero no se conectará a ningún bridge. De lo contrario, el bridge debe crearse en el sistema antes de iniciar el contenedor. lxc no gestionará ninguna configuración fuera del contenedor. En modo router, se crean rutas estáticas en el host para las direcciones IP del contenedor que apuntan a la interfaz veth del lado del host. Además, se añaden entradas de ARP proxy y NDP proxy en la interfaz veth del lado del host para las IPs de gateway definidas en el contenedor, para permitir al contenedor alcanzar el host. Por defecto, lxc elige un nombre para el dispositivo de red que pertenece al exterior del contenedor, pero si desea gestionar este nombre usted mismo, puede indicarle a lxc que establezca un nombre específico con la opción lxc.net.[i].veth.pair (excepto para contenedores no privilegiados donde esta opción se ignora por razones de seguridad). Se pueden añadir rutas estáticas en el host que apunten al contenedor usando las opciones lxc.net.[i].veth.ipv4.route y lxc.net.[i].veth.ipv6.route. Varias líneas especifican varias rutas. La ruta tiene el formato x.y.z.t/m, ej. 192.168.1.0/24. En modo bridge, la membresía VLAN sin etiquetar se puede establecer con la opción lxc.net.[i].veth.vlan.id. Acepta un valor especial de 'none' que indica que el puerto del contenedor debe eliminarse de la VLAN sin etiquetar por defecto del bridge. La opción lxc.net.[i].veth.vlan.tagged.id se puede especificar varias veces para establecer la membresía del puerto del bridge del contenedor a una o más VLANs etiquetadas.

vlan: se vincula una interfaz vlan con la interfaz especificada por lxc.net.[i].link y se asigna al contenedor. El identificador vlan se especifica con la opción lxc.net.[i].vlan.id.

macvlan: se vincula una interfaz macvlan con la interfaz especificada por lxc.net.[i].link y se asigna al contenedor. lxc.net.[i].macvlan.mode especifica el modo que utilizará la macvlan para comunicarse entre diferentes macvlan en el mismo dispositivo superior. Los modos aceptados son private, vepa, bridge y passthru. En modo private, el dispositivo nunca se comunica con ningún otro dispositivo en el mismo upper_dev (por defecto). En modo vepa, el nuevo modo Virtual Ethernet Port Aggregator (VEPA), asume que el bridge adyacente devuelve todos los frames donde tanto el origen como el destino son locales al puerto macvlan, es decir, el bridge está configurado como un relé reflectante. Los frames de broadcast que llegan desde el upper_dev se inundan a todas las interfaces macvlan en modo VEPA, los frames locales no se entregan localmente. En modo bridge, proporciona el comportamiento de un bridge simple entre diferentes interfaces macvlan en el mismo puerto. Los frames de una interfaz a otra se entregan directamente y no se envían externamente. Los frames de broadcast se inundan a todos los demás puertos del bridge y a la interfaz externa, pero cuando regresan de un relé reflectante, no los entregamos de nuevo. Dado que conocemos todas las direcciones MAC, el modo bridge de macvlan no requiere aprendizaje ni STP como lo hace el módulo de bridge. En modo passthru, todos los frames recibidos por la interfaz física se reenvían a la interfaz macvlan. Solo es posible una interfaz macvlan en modo passthru para una interfaz física.

ipvlan: se vincula una interfaz ipvlan con la interfaz especificada por lxc.net.[i].link y se asigna al contenedor. lxc.net.[i].ipvlan.mode especifica el modo que utilizará la ipvlan para comunicarse entre diferentes ipvlan en el mismo dispositivo superior. Los modos aceptados son l3, l3s y l2. El valor por defecto es el modo l3. En modo l3, el procesamiento TX hasta L3 ocurre en la instancia de pila adjunta al dispositivo dependiente y los paquetes se cambian a la instancia de pila del dispositivo padre para el procesamiento L2 y el enrutamiento desde esa instancia se utilizará antes de que los paquetes se pongan en cola en el dispositivo de salida. En este modo, los dispositivos dependientes no recibirán ni podrán enviar tráfico multicast/broadcast. En modo l3s, el procesamiento TX es muy similar al modo L3, excepto que iptables (seguimiento de conexión) funciona en este modo y, por lo tanto, es L3-simétrico (L3s). Esto tendrá un rendimiento ligeramente menor, pero eso no debería importar ya que usted está eligiendo este modo en lugar del modo L3 simple para que funcione el seguimiento de conexión. En modo l2, el procesamiento TX ocurre en la instancia de pila adjunta al dispositivo dependiente y los paquetes se cambian y ponen en cola en el dispositivo padre para enviarlos. En este modo, los dispositivos dependientes recibirán/enviarán multicast y broadcast (si corresponde) también. lxc.net.[i].ipvlan.isolation especifica el modo de aislamiento. Los valores de aislamiento aceptados son bridge, private y vepa. El valor por defecto es bridge. En modo de aislamiento bridge, los dispositivos dependientes pueden cruzar entre sí además de comunicarse a través del dispositivo padre. En modo de aislamiento private, el puerto se establece en modo privado. Es decir, el puerto no permitirá la comunicación cruzada entre dispositivos dependientes. En modo de aislamiento vepa, el puerto se establece en modo VEPA. Es decir, el puerto descargará la funcionalidad de conmutación a la entidad externa como se describe en 802.1Qbg.

phys: se asigna una interfaz ya existente especificada por lxc.net.[i].link al contenedor.

lxc.net.[i].flags
Especifica una acción a realizar para la red.

up: activa la interfaz.

lxc.net.[i].link
Especifica la interfaz a utilizar para el tráfico de red real.
lxc.net.[i].l2proxy
Controla si se agregarán entradas de vecino IP de capa 2 a la interfaz lxc.net.[i].link para las direcciones IP del contenedor. Se puede establecer en 0 o 1. Por defecto es 0. Cuando se usa con direcciones IPv4, se deben establecer los siguientes valores de sysctl: net.ipv4.conf.[link].forwarding=1 Cuando se usa con direcciones IPv6, se deben establecer los siguientes valores de sysctl: net.ipv6.conf.[link].proxy_ndp=1 net.ipv6.conf.[link].forwarding=1
lxc.net.[i].mtu
Especifica la unidad de transferencia máxima para esta interfaz.
lxc.net.[i].name
El nombre de la interfaz se asigna dinámicamente, pero si se necesita otro nombre porque los archivos de configuración utilizados por el contenedor usan un nombre genérico, por ejemplo, eth0, esta opción renombrará la interfaz en el contenedor.
lxc.net.[i].hwaddr
La dirección MAC de la interfaz se asigna dinámicamente por defecto a la interfaz virtual, pero en algunos casos, esto es necesario para resolver un conflicto de dirección MAC o para tener siempre la misma dirección IPv6 de enlace local. Cualquier "x" en la dirección se reemplazará por un valor aleatorio, lo que permite establecer plantillas de hwaddr.
lxc.net.[i].ipv4.address
Especifica la dirección IPv4 a asignar a la interfaz virtualizada. Varias líneas especifican varias direcciones IPv4. La dirección tiene el formato x.y.z.t/m, ej. 192.168.1.123/24. Opcionalmente, puede especificar la dirección de broadcast después de la dirección IP, por ejemplo, 192.168.1.123/24 255.255.255.255. De lo contrario, se calcula automáticamente a partir de la dirección IP.
lxc.net.[i].ipv4.gateway
Especifica la dirección IPv4 a utilizar como gateway dentro del contenedor. La dirección tiene el formato x.y.z.t, ej. 192.168.1.123. También puede tener el valor especial auto, que significa tomar la dirección principal de la interfaz del bridge (según lo especificado por la opción lxc.net.[i].link) y usarla como gateway. auto solo está disponible cuando se utilizan los tipos de red veth, macvlan e ipvlan. También puede tener el valor especial dev, que significa establecer el gateway por defecto como una ruta de dispositivo. Esto es principalmente para usarlo con n de capa 3

MODES DE RÉSEAU

Par défaut, LXC utilise des interfaces réseau de type veth. Cependant, d'autres types peuvent être utilisés pour le mode de réseau.

lxc.net.[i].type
Spécifie le type d'interface réseau à utiliser pour lai-ème interface réseau du conteneur. Les valeurs acceptées sont : veth, macvlan, ipvlan, loopback, phys, vlan, tap et none. Le type par défaut est veth.
lxc.net.[i].link
Définit le périphérique de liaison sur l'hôte auquel l'interface réseau du conteneur sera attachée. Cette option est utilisée pour les types de réseau macvlan, veth, phys et vlan. Par exemple, pour attacher une interface macvlan au périphérique eth0 de l'hôte, vous définiriez lxc.net.[i].link sur eth0.
lxc.net.[i].ipv4.address
Spécifie l'adresse IPv4 à attribuer à l'interface virtualisée. Plusieurs lignes spécifient plusieurs adresses IPv4. L'adresse est au format A.B.C.D/M, par exemple, 10.0.3.4/24.
lxc.net.[i].ipv4.gateway
Spécifie l'adresse IPv4 à utiliser comme passerelle à l'intérieur du conteneur. L'adresse est au format A.B.C.D, par exemple, 10.0.3.1. Peut également avoir la valeur spéciale auto, ce qui signifie qu'il prendra l'adresse principale du périphérique de pont (telle que spécifiée par l'option lxc.net.[i].link) et l'utilisera comme passerelle. auto n'est disponible que lors de l'utilisation des types de réseau veth, macvlan et ipvlan. Peut également avoir la valeur spéciale dev, ce qui signifie que la passerelle par défaut sera définie comme une route de périphérique. Ceci est principalement destiné à être utilisé avec des modes réseau de couche 3, tels que IPVLAN.
lxc.net.[i].ipv6.address
Spécifie l'adresse IPv6 à attribuer à l'interface virtualisée. Plusieurs lignes spécifient plusieurs adresses IPv6. L'adresse est au format x::y/m, par exemple, 2003:db8:1:0:214:1234:fe0b:3596/64.
lxc.net.[i].ipv6.gateway
Spécifie l'adresse IPv6 à utiliser comme passerelle à l'intérieur du conteneur. L'adresse est au format x::y, par exemple, 2003:db8:1:0::1. Peut également avoir la valeur spéciale auto, ce qui signifie qu'il prendra l'adresse principale du périphérique de pont (telle que spécifiée par l'option lxc.net.[i].link) et l'utilisera comme passerelle. auto n'est disponible que lors de l'utilisation des types de réseau veth, macvlan et ipvlan. Peut également avoir la valeur spéciale dev, ce qui signifie que la passerelle par défaut sera définie comme une route de périphérique. Ceci est principalement destiné à être utilisé avec des modes réseau de couche 3, tels que IPVLAN.
lxc.net.[i].script.up
Ajoute une option de configuration pour spécifier un script à exécuter après la création et la configuration du réseau utilisé du côté hôte.

En plus des informations disponibles pour tous les hooks. Les informations suivantes sont fournies au script :

•
LXC_HOOK_TYPE : le type de hook. Il s'agit de 'up' ou 'down'.
•
LXC_HOOK_SECTION : le type de section 'net'.
•
LXC_NET_TYPE : le type de réseau. Il s'agit de l'un des types de réseau valides répertoriés ici (par exemple, 'vlan', 'macvlan', 'ipvlan', 'veth').
•
LXC_NET_PARENT : le périphérique parent sur l'hôte. Ceci n'est défini que pour les types de réseau 'macvlan', 'veth', 'phys'.
•
LXC_NET_PEER : le nom du périphérique pair sur l'hôte. Ceci n'est défini que pour les types de réseau 'veth'. Notez que ces informations ne sont disponibles que lorsque lxc.hook.version est défini sur 1.

Le fait que ces informations soient fournies sous forme de variables d'environnement ou d'arguments au script dépend de la valeur de lxc.hook.version. Si elle est définie sur 1, les informations sont fournies sous forme de variables d'environnement. Si elle est définie sur 0, les informations sont fournies en tant qu'arguments au script.

La sortie standard du script est enregistrée au niveau de débogage. La sortie d'erreur standard n'est pas enregistrée, mais peut être capturée par le hook redirigeant sa sortie d'erreur standard vers la sortie standard.

•
LXC_NET_PARENT : le périphérique parent sur l'hôte. Ceci n'est défini que pour les types de réseau 'macvlan', 'veth', 'phys'.

Le fait que ces informations soient fournies sous forme de variables d'environnement ou d'arguments au script dépend de la valeur de lxc.hook.version. NOUVELLE INSTANCE PSEUDO TTY (DEVPTS)

Pour une isolation plus stricte, le conteneur peut avoir sa propre instance privée du pseudo tty.

lxc.pty.max
Si défini, le conteneur aura une nouvelle instance de pseudo tty, le rendant privé pour lui. La valeur spécifie le nombre maximum de pseudo ttys autorisés pour une instance pty (cette limitation n'est pas encore implémentée).

CONSOLE SYSTÈME DU CONTENEUR

Si le conteneur est configuré avec un système de fichiers racine et que le fichier inittab est configuré pour utiliser la console, vous voudrez peut-être spécifier où va la sortie de cette console.

lxc.console.buffer.size
La définition de cette option demande à liblxc d'allouer un tampon circulaire en mémoire. La sortie de la console du conteneur sera écrite dans le tampon circulaire. Notez que le tampon circulaire doit être au moins aussi grand qu'une taille de page standard. Lorsqu'une valeur inférieure à une seule taille de page est transmise, liblxc alloue un tampon circulaire d'une seule taille de page. Une taille de page est généralement de 4 Ko. Le mot-clé 'auto' amènera liblxc à allouer un tampon circulaire de 128 Ko. Lors de la spécification manuelle d'une taille pour le tampon circulaire, la valeur doit être une puissance de 2 une fois convertie en octets. Les préfixes de taille valides sont 'KB', 'MB', 'GB'. (Notez que toutes les conversions sont basées sur des multiples de 1024. Cela signifie que 'KB' == 'KiB', 'MB' == 'MiB', 'GB' == 'GiB'. De plus, la casse du suffixe est ignorée, c'est-à-dire que 'kB', 'KB' et 'Kb' sont traités de manière égale.)
lxc.console.size
La définition de cette option demande à liblxc de limiter la taille du fichier journal de la console spécifié dans lxc.console.logfile. Notez que la taille du fichier journal doit être au moins aussi grande qu'une taille de page standard. Lorsqu'une valeur inférieure à une seule taille de page est transmise, liblxc définit la taille du fichier journal à une seule taille de page. Une taille de page est généralement de 4 Ko. Le mot-clé 'auto' amènera liblxc à imposer une limite de 128 Ko au fichier journal. Lors de la spécification manuelle d'une taille pour le fichier journal, la valeur doit être une puissance de 2 une fois convertie en octets. Les préfixes de taille valides sont 'KB', 'MB', 'GB'. (Notez que toutes les conversions sont basées sur des multiples de 1024. Cela signifie que 'KB' == 'KiB', 'MB' == 'MiB', 'GB' == 'GiB'. De plus, la casse du suffixe est ignorée, c'est-à-dire que 'kB', 'KB' et 'Kb' sont traités de manière égale.) Si les utilisateurs souhaitent refléter le tampon circulaire de la console sur le disque, ils doivent définir lxc.console.size égal à lxc.console.buffer.size.
lxc.console.logfile
Spécifie un chemin vers un fichier où la sortie de la console sera écrite. Notez qu'à la différence du fichier journal du tampon circulaire sur disque, ce fichier continuera de croître, remplissant potentiellement les disques de l'utilisateur s'il n'est pas roté et supprimé. Ce problème peut également être évité en utilisant les options de tampon circulaire en mémoire lxc.console.buffer.size et lxc.console.buffer.logfile.
lxc.console.rotate
Indique s'il faut faire pivoter le fichier journal de la console spécifié dans lxc.console.logfile. Les utilisateurs peuvent envoyer une requête API pour faire pivoter le fichier journal. Notez que l'ancien fichier journal aura le même nom que l'original avec le suffixe ".1" ajouté. Les utilisateurs qui souhaitent empêcher le fichier journal de la console de remplir le disque doivent faire pivoter le fichier journal et le supprimer s'il n'est pas nécessaire. Ce problème peut également être évité en utilisant les options de tampon circulaire en mémoire lxc.console.buffer.size et lxc.console.buffer.logfile.
lxc.console.path
Spécifie un chemin vers un périphérique auquel la console sera attachée. Le mot-clé 'none' désactivera simplement la console. Notez que lorsque vous spécifiez 'none' et créez un nœud de périphérique pour la console dans le conteneur à /dev/console ou que vous montez en amont le /dev/console de l'hôte dans le conteneur à /dev/console, le conteneur aura un accès direct au /dev/console de l'hôte. Ceci est dangereux lorsque le conteneur a un accès en écriture au périphérique et doit donc être utilisé avec prudence.

EMPLACEMENT DES PÉRIPHÉRIQUES CONSOLE

Les consoles LXC sont fournies via des PTYs Unix98 créés sur l'hôte et montés par liaison sur les périphériques attendus dans le conteneur. Par défaut, ils sont montés par liaison sur /dev/console et /dev/ttyN. Cela peut empêcher les mises à niveau de packages dans l'invité. Par conséquent, vous pouvez spécifier un emplacement de répertoire (sous /dev) sous lequel LXC créera les fichiers et les montera par liaison. Ceux-ci seront ensuite liés symboliquement à /dev/console et /dev/ttyN. Une mise à niveau de package pourra alors réussir car elle pourra supprimer et remplacer les liens symboliques.

lxc.tty.dir
Spécifie un répertoire sous /dev sous lequel créer les périphériques de console du conteneur. Notez que LXC déplacera tous les montages par liaison ou les nœuds de périphérique pour /dev/console dans ce répertoire.

PUNTOS DE MONTAJE

La sección de puntos de montaje especifica los diferentes lugares a montar. Estos puntos de montaje serán privados para el contenedor y no serán visibles para los procesos que se ejecutan fuera del contenedor. Esto es útil para montar /etc, /var o /home, por ejemplo.

NOTA - LXC generalmente se asegurará de que los destinos de montaje y las fuentes de bind-mount relativas estén adecuadamente confinados bajo la raíz del contenedor, para evitar ataques que impliquen montar por encima de directorios y archivos del host. (Se ignoran los enlaces simbólicos en las fuentes de montaje absolutas). Sin embargo, si la configuración del contenedor monta primero un directorio que está bajo el control del usuario del contenedor, como /home/joe, en el contenedor en alguna *ruta*, y luego monta bajo *ruta*, entonces sería posible un ataque TOCTTOU donde el usuario del contenedor modifica un enlace simbólico en su directorio de inicio en el momento justo.

lxc.mount.fstab
especifica una ubicación de archivo en formato *fstab*, que contiene la información de montaje. La ubicación del destino de montaje puede y en la mayoría de los casos debe ser una ruta relativa, que será relativa a la raíz del contenedor montada. Por ejemplo, 
             proc proc proc nodev,noexec,nosuid 0 0

Montará un sistema de archivos proc bajo el /proc del contenedor, independientemente de dónde provenga el sistema de archivos raíz. Esto es resistente a sistemas de archivos respaldados por dispositivos de bloque, así como a la clonación de contenedores.

Tenga en cuenta que al montar un sistema de archivos desde un archivo de imagen o un dispositivo de bloque, el tercer campo (fs_vfstype) no puede ser auto como con mount(8) sino que debe ser especificado explícitamente.

lxc.mount.entry
Especifica un punto de montaje correspondiente a una línea en formato fstab. Además, lxc soporta propagación de montaje, como rshared o rprivate, y añade tres opciones de montaje adicionales. optional no falla si el montaje no funciona. create=dir o create=file para crear un directorio (o archivo) cuando el punto sea montado. relative la ruta de origen se toma como relativa a la raíz del contenedor montado. Por ejemplo, 
             dev/null proc/kcore none bind,relative 0 0

Expandirá dev/null a ${LXC_ROOTFS_MOUNT}/dev/null y lo montará en proc/kcore dentro del contenedor.

lxc.mount.auto
especifica qué sistemas de archivos del kernel estándar deben ser montados automáticamente. Esto puede simplificar drásticamente la configuración. Los sistemas de archivos son:
•
proc:mixed (o proc): monta /proc como lectura-escritura, pero remonta /proc/sys y /proc/sysrq-trigger como solo lectura con fines de seguridad / aislamiento del contenedor.
•
proc:rw: monta /proc como lectura-escritura
•
sys:mixed (o sys): monta /sys como solo lectura pero con /sys/devices/virtual/net escribible.
•
sys:ro: monta /sys como solo lectura con fines de seguridad / aislamiento del contenedor.
•
sys:rw: monta /sys como lectura-escritura
•
cgroup:mixed: Monta un tmpfs en /sys/fs/cgroup, crea directorios para todas las jerarquías a las que se añade el contenedor, crea subdirectorios en esas jerarquías con el nombre del cgroup, y bind-monta el propio cgroup del contenedor en ese directorio. El contenedor podrá escribir en su propio directorio cgroup, pero no en los padres, ya que se remontarán como solo lectura.
•
cgroup:mixed:force: La opción force hará que LXC realice los montajes de cgroup para el contenedor bajo todas las circunstancias. De lo contrario, es similar a cgroup:mixed. Esto es principalmente útil cuando los namespaces de cgroup están habilitados, donde LXC normalmente dejará el montaje de cgroups al binario init del contenedor ya que es perfectamente seguro hacerlo.
•
cgroup:ro: similar a cgroup:mixed, pero todo se montará como solo lectura.
•
cgroup:ro:force: La opción force hará que LXC realice los montajes de cgroup para el contenedor bajo todas las circunstancias. De lo contrario, es similar a cgroup:ro. Esto es principalmente útil cuando los namespaces de cgroup están habilitados, donde LXC normalmente dejará el montaje de cgroups al binario init del contenedor ya que es perfectamente seguro hacerlo.
•
cgroup:rw: similar a cgroup:mixed, pero todo se montará como lectura-escritura. Tenga en cuenta que las rutas que conducen al propio cgroup del contenedor serán escribibles, pero no serán un sistema de archivos cgroup sino simplemente parte del tmpfs de /sys/fs/cgroup
•
cgroup:rw:force: La opción force hará que LXC realice los montajes de cgroup para el contenedor bajo todas las circunstancias. De lo contrario, es similar a cgroup:rw. Esto es principalmente útil cuando los namespaces de cgroup están habilitados, donde LXC normalmente dejará el montaje de cgroups al binario init del contenedor ya que es perfectamente seguro hacerlo.
•
cgroup (sin especificador): por defecto es cgroup:rw si el contenedor conserva la capacidad CAP_SYS_ADMIN, cgroup:mixed en caso contrario.

Tenga en cuenta que en comparación con cgroup, donde todos los caminos que conducen al propio cgroup del contenedor son simplemente directorios en el tmpfs subyacente, aquí /sys/fs/cgroup/$hierarchy contendrá la jerarquía completa de cgroup del host, aunque sea de solo lectura fuera del propio cgroup del contenedor. •
cgroup-full:mixed:force: La opción force hará que LXC realice los montajes de cgroup para el contenedor bajo todas las circunstancias. De lo contrario, es similar a cgroup-full:mixed. Esto es principalmente útil cuando los namespaces de cgroup están habilitados, donde LXC normalmente dejará el montaje de cgroups al binario init del contenedor ya que es perfectamente seguro hacerlo.

cgroup-full:ro: similar a cgroup-full:mixed, pero todo se montará como solo lectura.

Si los namespaces de cgroup están habilitados, cualquier solicitud de montaje automático de cgroup será ignorada, ya que el contenedor puede montar los sistemas de archivos por sí mismo, y el montaje automático puede confundir al init del contenedor.

Tenga en cuenta que si el montaje automático del sistema de archivos cgroup está habilitado, el tmpfs bajo /sys/fs/cgroup siempre se montará como lectura-escritura (pero para los casos :mixed y :ro, las jerarquías individuales, /sys/fs/cgroup/$hierarchy, serán de solo lectura). Esto es para solucionar una peculiaridad en el comando mountall(8) de Ubuntu que hará que los contenedores esperen entrada del usuario al arrancar si /sys/fs/cgroup se monta como solo lectura y el contenedor no puede remontarlo como lectura-escritura debido a la falta de CAP_SYS_ADMIN.

Ejemplos:

              lxc.mount.auto = proc sys cgroup
              lxc.mount.auto = proc:rw sys:rw cgroup-full:rw

SISTEMA DE ARCHIVOS RAÍZ

El sistema de archivos raíz del contenedor puede ser diferente al del sistema host.

lxc.rootfs.path
especifica el sistema de archivos raíz para el contenedor. Puede ser un archivo de imagen, un directorio o un dispositivo de bloque. Si no se especifica, el contenedor comparte su sistema de archivos raíz con el host.

Para contenedores respaldados por directorios o dispositivos de bloque simples, se puede usar un nombre de ruta. Si el rootfs está respaldado por un dispositivo nbd, entonces nbd:file:1 especifica que file debe ser adjuntado a un dispositivo nbd, y la partición 1 debe ser montada como rootfs. nbd:file especifica que el propio dispositivo nbd debe ser montado. overlayfs:/lower:/upper especifica que el rootfs debe ser un overlay con /upper montado como lectura-escritura sobre un montaje de solo lectura de /lower. Para overlay se pueden especificar múltiples directorios /lower. loop:/file le dice a lxc que adjunte /file a un dispositivo loop y monte el dispositivo loop.

Esto es útil cuando el usuario no quiere hacer un chown recursivo del rootfs del contenedor para que coincida con el idmapping del espacio de nombres de usuario que va a utilizar el contenedor. En su lugar, se puede utilizar un montaje idmapped para manejar esto. El argumento para idmap= puede ser una ruta que apunte a un archivo de espacio de nombres de usuario que LXC abrirá y utilizará para idmapear el rootfs o el valor especial "container" que instruirá a LXC a utilizar el espacio de nombres de usuario del contenedor para idmapear el rootfs.
lxc.rootfs.managed

CONTROL GROUPS ("CGROUPS")

La sección de grupos de control contiene la configuración para los diferentes subsistemas. lxc no verifica la corrección del nombre del subsistema. Esto tiene la desventaja de no detectar errores de configuración hasta que el contenedor se inicia, pero tiene la ventaja de permitir cualquier subsistema futuro.

La implementación del kernel de cgroups ha cambiado significativamente a lo largo de los años. Con Linux 4.5 se añadió soporte para un nuevo sistema de archivos de cgroup, usualmente referido como "cgroup2" o "jerarquía unificada". Desde entonces, el antiguo sistema de archivos de cgroup es usualmente referido como "cgroup1" o las "jerarquías heredadas". Por favor, consulte la página del manual de cgroups para una explicación detallada de las diferencias entre las dos versiones.

LXC distingue entre la configuración para la jerarquía heredada y la unificada utilizando diferentes prefijos de clave de configuración. Para alterar la configuración de los controladores en una jerarquía heredada se debe usar el prefijo de clave lxc.cgroup. y para alterar la configuración de un controlador en la jerarquía unificada se debe usar la clave lxc.cgroup2.. Tenga en cuenta que LXC ignorará la configuración lxc.cgroup. en sistemas que solo usan la jerarquía unificada. A la inversa, ignorará las opciones lxc.cgroup2. en sistemas que solo usan jerarquías heredadas.

En su núcleo, una jerarquía de cgroup es una forma de organizar procesos jerárquicamente. Usualmente, una jerarquía de cgroup tendrá uno o más "controladores" habilitados. Un "controlador" en una jerarquía de cgroup es usualmente responsable de distribuir un tipo específico de recurso del sistema a lo largo de la jerarquía. Los controladores incluyen el controlador "pids", el controlador "cpu", el controlador "memory" y otros. Sin embargo, algunos controladores no entran en la categoría de distribución de un recurso del sistema, sino que a menudo se les denomina controladores de "utilidad". Un controlador de utilidad es el controlador de dispositivos. En lugar de distribuir un recurso del sistema, permite gestionar el acceso a dispositivos.

En la jerarquía heredada, el controlador de dispositivos se implementó como la mayoría de los otros controladores, como un conjunto de archivos a los que se podía escribir. Estos archivos se denominaban "devices.allow" y "devices.deny". El controlador de dispositivos heredado permitía la implementación de "listas de permitidos" y "listas de denegados".

Una lista de permitidos es un programa de dispositivos que por defecto bloquea el acceso a todos los dispositivos. Para acceder a dispositivos específicos, se deben especificar "reglas de permiso" para dispositivos o clases de dispositivos particulares. En contraste, una lista de denegados es un programa de dispositivos que por defecto permite el acceso a todos los dispositivos. Para restringir el acceso a dispositivos específicos, se deben especificar "reglas de denegación" para dispositivos o clases de dispositivos particulares.

En la jerarquía unificada de cgroup, la implementación del controlador de dispositivos ha cambiado completamente. En lugar de archivos para leer y escribir, se puede adjuntar un programa eBPF de BPF_PROG_TYPE_CGROUP_DEVICE a un cgroup. A pesar de que la implementación del kernel ha cambiado completamente, LXC intenta permitir que se sigan las mismas semánticas tanto en el cgroup de dispositivos heredado como en el controlador de dispositivos unificado basado en eBPF. Los siguientes párrafos explican las semánticas para el controlador de dispositivos unificado basado en eBPF.

Como se mencionó, el formato para especificar reglas de dispositivos para el controlador de dispositivos unificado basado en eBPF es el mismo que para el controlador de dispositivos cgroup heredado; solo ha cambiado el prefijo de la clave de configuración. Específicamente, las reglas de dispositivos para el controlador de dispositivos cgroup heredado se especifican a través de lxc.cgroup.devices.allow y lxc.cgroup.devices.deny, mientras que para el controlador de dispositivos cgroup2 basado en eBPF se deben usar lxc.cgroup2.devices.allow y lxc.cgroup2.devices.deny.

•
Una regla de dispositivo de lista de denegados 
	        lxc.cgroup2.devices.deny = a

hará que LXC instruya al kernel para bloquear el acceso a todos los dispositivos por defecto. Para conceder acceso a dispositivos, se deben añadir reglas de permiso a través de la clave lxc.cgroup2.devices.allow. Esto se denomina un programa de dispositivos de "lista de permitidos".

•
Una regla de dispositivo de lista de permitidos 
	        lxc.cgroup2.devices.allow = a

hará que LXC instruya al kernel para permitir el acceso a todos los dispositivos por defecto. Para denegar el acceso a dispositivos, se deben añadir reglas de denegación a través de la clave lxc.cgroup2.devices.deny. Esto se denomina un programa de dispositivos de "lista de denegados".

•
Especificar cualquiera de las dos reglas mencionadas anteriormente provocará que se borren todas las reglas anteriores, es decir, la lista de dispositivos se restablecerá.
•
Cuando se solicita un programa de lista de permitidos, es decir, el acceso a todos los dispositivos está bloqueado por defecto, se ignoran las reglas de denegación específicas para dispositivos individuales o clases de dispositivos.
•
Cuando se solicita un programa de lista de denegados, es decir, el acceso a todos los dispositivos está permitido por defecto, se ignoran las reglas de permiso específicas para dispositivos individuales o clases de dispositivos.

Por ejemplo, el conjunto de reglas:

          lxc.cgroup2.devices.deny = a
          lxc.cgroup2.devices.allow = c *:* m
          lxc.cgroup2.devices.allow = b *:* m
          lxc.cgroup2.devices.allow = c 1:3 rwm

implementa un programa de dispositivos de lista de permitidos, es decir, el kernel bloqueará el acceso a todos los dispositivos no permitidos específicamente en esta lista. Este programa en particular indica que se pueden crear todos los dispositivos de caracteres y bloques, pero solo /dev/null se puede leer o escribir.

Si en cambio cambiamos a el siguiente conjunto de reglas:

          lxc.cgroup2.devices.allow = a
          lxc.cgroup2.devices.deny = c *:* m
          lxc.cgroup2.devices.deny = b *:* m
          lxc.cgroup2.devices.deny = c 1:3 rwm

entonces LXC instruirá al kernel para implementar una lista de denegados, es decir, el kernel permitirá el acceso a todos los dispositivos no denegados específicamente en esta lista. Este programa en particular indica que no se pueden crear dispositivos de caracteres o bloques y que a /dev/null no se le permite leer, escribir o crear.

Ahora consideremos el mismo programa pero seguido de una "regla global" que determina el tipo de programa de dispositivo (lista de permitidos o lista de denegados) como se explicó anteriormente:

          lxc.cgroup2.devices.allow = a
          lxc.cgroup2.devices.deny = c *:* m
          lxc.cgroup2.devices.deny = b *:* m
          lxc.cgroup2.devices.deny = c 1:3 rwm
          lxc.cgroup2.devices.allow = a

La última línea hará que LXC restablezca la lista de dispositivos sin cambiar el tipo de programa de dispositivo.

Si especificamos:

          lxc.cgroup2.devices.allow = a
          lxc.cgroup2.devices.deny = c *:* m
          lxc.cgroup2.devices.deny = b *:* m
          lxc.cgroup2.devices.deny = c 1:3 rwm
          lxc.cgroup2.devices.deny = a

en su lugar, la última línea hará que LXC restablezca la lista de dispositivos y cambie de un programa de lista de permitidos a un programa de lista de denegados.

lxc.cgroup.[nombre del controlador].[archivo del controlador]
Especifica el valor del grupo de control que se establecerá en una jerarquía de cgroup heredada. El nombre del controlador es el nombre literal del grupo de control. Los nombres permitidos y la sintaxis de sus valores no son dictados por LXC, sino que dependen de las características del kernel de Linux en ejecución en el momento en que se inicia el contenedor, por ejemplo, lxc.cgroup.cpuset.cpus

Los nombres permitidos y la sintaxis de sus valores no son dictados por LXC, sino que dependen de las características del kernel de Linux en ejecución en el momento en que se inicia el contenedor, por ejemplo, lxc.cgroup2.memory.high
lxc.cgroup.dir
especifica un directorio o ruta en el que se creará el cgroup del contenedor. Por ejemplo, establecer lxc.cgroup.dir = my-cgroup/first para un contenedor llamado "c1" creará el cgroup del contenedor como un sub-cgroup de "my-cgroup". Por ejemplo, si el cgroup actual del usuario "my-user" se encuentra en el cgroup raíz del controlador cpuset en una jerarquía cgroup v1, esto crearía el cgroup "/sys/fs/cgroup/cpuset/my-user/my-cgroup/first/c1" para el contenedor. LXC creará cualquier cgroup faltante. Esto presupone que el usuario tiene acceso de escritura a su cgroup actual.

CONFIGURACIÓN SECCOMP

Un contenedor puede iniciarse con un conjunto reducido de llamadas al sistema disponibles cargando un perfil seccomp al inicio. El archivo de configuración seccomp debe comenzar con un número de versión en la primera línea, un tipo de política en la segunda línea, seguido de la configuración.

Actualmente se admiten las versiones 1 y 2. En la versión 1, la política es una simple lista de permitidos. Por lo tanto, la segunda línea debe decir "allowlist", con el resto del archivo conteniendo un (numérico) número de llamada al sistema por línea. Cada número de llamada al sistema se incluye en la lista de permitidos, mientras que cada número no listado se incluye en la lista de denegados para su uso en el contenedor.

En la versión 2, la política puede ser una lista de denegados o de permitidos, admite acciones predeterminadas por regla y por política, y admite la resolución de llamadas al sistema por arquitectura a partir de nombres textuales.

Un ejemplo de política de lista de denegados, en la que se permiten todas las llamadas al sistema excepto mknod, que simplemente no hará nada y devolverá 0 (éxito), se ve así:

      2
      denylist
      mknod errno 0
      ioctl notify

Especificar "errno" como acción hará que LXC registre un filtro seccomp que provocará que se devuelva un errno específico al llamador. El valor de errno se puede especificar después de la palabra de acción "errno".

Especificar "notify" como acción hará que LXC registre un escuchador de seccomp y obtenga un descriptor de archivo de escucha del kernel. Cuando se realiza una llamada al sistema registrada como "notify", el kernel generará un evento de sondeo y enviará un mensaje a través del descriptor de archivo. El llamador puede leer este mensaje, inspeccionar las llamadas al sistema, incluidos sus argumentos. Basándose en esta información, se espera que el llamador envíe un mensaje informando al kernel qué acción tomar. Hasta que se envíe ese mensaje, el kernel bloqueará el proceso llamador. El formato de los mensajes a leer y enviar está documentado en seccomp.

PR_SET_NO_NEW_PRIVS

Con PR_SET_NO_NEW_PRIVS activo, execve() promete no otorgar privilegios para hacer nada que no se pudiera haber hecho sin la llamada a execve() (por ejemplo, hacer que las marcas de bits de modo set-user-ID y set-group-ID, y las capacidades de archivo no funcionen). Una vez establecido, este bit no se puede desestablecer. El establecimiento de este bit se hereda por los hijos creados por fork() y clone(), y se conserva en execve(). Tenga en cuenta que PR_SET_NO_NEW_PRIVS se aplica después de que el contenedor haya cambiado a su perfil AppArmor o contexto SELinux previsto.

El usuario root en el contenedor tendrá privilegios dentro del contenedor, pero sin privilegios en el host. Normalmente, un contenedor de sistema querrá un rango de IDs, por lo que mapearía, por ejemplo, los IDs de usuario y grupo 0 a 20,000 en el contenedor a los IDs 200,000 a 220,000.

lxc.idmap
Se deben proporcionar cuatro valores. Primero un carácter, 'u' o 'g', para especificar si se están mapeando IDs de usuario o de grupo. Finalmente, un rango que indica el número de IDs consecutivos a mapear.

CONTAINER HOOKS

The hooks provide a mechanism to run arbitrary commands at various points in the container lifecycle. The hooks are defined using configuration keys starting with lxc.hook..

For hooks that run inside the container's namespaces, the hooks are run as the root user inside the container. For hooks that run on the host, they are run as the same user that is running the lxc tool.

The following hooks are supported:

lxc.hook.pre-mount
A hook to be run in the container's fs namespace but before the rootfs has been set up. This allows for manipulation of the rootfs, i.e. to mount an encrypted filesystem. Mounts done in this hook will not be reflected on the host (apart from mounts propagation), so they will be automatically cleaned up when the container shuts down.
lxc.hook.mount
A hook to be run in the container's namespace after mounting has been done, but before the pivot_root.
lxc.hook.autodev
A hook to be run in the container's namespace after mounting has been done and after any mount hooks have run, but before the pivot_root, if lxc.autodev == 1. The purpose of this hook is to assist in populating the /dev directory of the container when using the autodev option for systemd based containers. The container's /dev directory is relative to the ${LXC_ROOTFS_MOUNT} environment variable available when the hook is run.
lxc.hook.start-host
A hook to be run in the host's namespace after the container has been setup, and immediately before starting the container init.
lxc.hook.start
A hook to be run in the container's namespace immediately before executing the container's init. This requires the program to be available in the container.
lxc.hook.stop
A hook to be run in the host's namespace with references to the container's namespaces after the container has been shut down. For each namespace an extra argument is passed to the hook containing the namespace's type and a filename that can be used to obtain a file descriptor to the corresponding namespace, separated by a colon. The type is the name as it would appear in the /proc/PID/ns directory. For instance for the mount namespace the argument usually looks like mnt:/proc/PID/fd/12.
lxc.hook.post-stop
A hook to be run in the host's namespace after the container has been shut down.
lxc.hook.clone
A hook to be run when the container is cloned to a new one. See lxc-clone(1) for more information.
lxc.hook.destroy
A hook to be run when the container is destroyed.

REGISTRO

El registro se puede configurar por contenedor. Por defecto, dependiendo de cómo se compiló el paquete lxc, el inicio del contenedor se registra solo en el nivel ERROR, y se registra en un archivo con el nombre del contenedor (con '.log' añadido) ya sea bajo la ruta del contenedor, o bajo /var/log/lxc.

Tanto el nivel de registro predeterminado como el archivo de registro se pueden especificar en el archivo de configuración del contenedor, anulando el comportamiento predeterminado. Tenga en cuenta que las entradas del archivo de configuración se pueden anular a su vez por las opciones de línea de comandos de lxc-start.

lxc.log.level
El nivel al que se registrará. El nivel de registro es un entero en el rango de 0 a 8 inclusive, donde un número más bajo significa una depuración más detallada. En particular, 0 = trace, 1 = debug, 2 = info, 3 = notice, 4 = warn, 5 = error, 6 = critical, 7 = alert, y 8 = fatal. Si no se especifica, el nivel predeterminado es 5 (error), por lo que solo se registran los errores y superiores.

Tenga en cuenta que cuando se llama a un script (como un script de hook o un script de interfaz de red de subida o bajada), la salida estándar del script se registra en el nivel 1, debug.

lxc.log.file
El archivo al que se debe escribir la información de registro.
lxc.log.syslog
Enviar información de registro a syslog. Respeta el nivel de registro definido en lxc.log.level. El argumento debe ser la instalación de syslog a utilizar, las válidas son: daemon, local0, local1, local2, local3, local4, local5, local5, local6, local7.

ARRANQUE AUTOMÁTICO

Las opciones de arranque automático admiten la marca de qué contenedores deben iniciarse automáticamente y en qué orden. Estas opciones pueden ser utilizadas directamente por las herramientas LXC o por herramientas externas proporcionadas por las distribuciones.

lxc.start.auto
Si el contenedor debe iniciarse automáticamente. Los valores válidos son 0 (apagado) y 1 (encendido).
lxc.start.delay
Cuánto tiempo esperar (en segundos) después de iniciar el contenedor antes de iniciar el siguiente.
lxc.start.order
Un entero utilizado para ordenar los contenedores al iniciar automáticamente una serie de contenedores a la vez. Un valor más bajo significa un inicio más temprano.
lxc.monitor.unshare
Si no es cero, el espacio de nombres de montaje se separará del host antes de inicializar el contenedor (antes de ejecutar cualquier hook pre-inicio). Esto requiere la capacidad CAP_SYS_ADMIN al inicio. Por defecto es 0.
lxc.monitor.signal.pdeath
Establecer la señal que se enviará al init del contenedor cuando el monitor lxc salga. Por defecto, se establece en SIGKILL, lo que hará que todos los procesos del contenedor se eliminen cuando el proceso monitor lxc muera. Para asegurar que los contenedores permanezcan en funcionamiento incluso si el monitor lxc muere, establezca esto en 0.
lxc.group
Una clave de valor múltiple (se puede usar varias veces) para poner el contenedor en un grupo de contenedores. Estos grupos se pueden utilizar (entre otras cosas) para iniciar una serie de contenedores relacionados.

ARranque AUTOMÁTICO Y ARRANQUE DEL SISTEMA

Cada contenedor puede formar parte de cualquier número de grupos o de ningún grupo. Dos grupos son especiales. Uno es el grupo NULL, es decir, el contenedor no pertenece a ningún grupo. El otro grupo es el grupo "onboot".

Cuando el sistema arranca con el servicio LXC habilitado, primero intentará arrancar cualquier contenedor con lxc.start.auto == 1 que sea miembro del grupo "onboot". El inicio se realizará en el orden de lxc.start.order. Si se ha especificado un lxc.start.delay, se respetará ese retraso antes de intentar iniciar el siguiente contenedor para dar tiempo al contenedor actual a comenzar la inicialización y reducir la sobrecarga del sistema host. Después de iniciar los miembros del grupo "onboot", el sistema LXC procederá a iniciar los contenedores con lxc.start.auto == 1 que no sean miembros de ningún grupo (el grupo NULL) y procederá como con el grupo onboot.

ENTORNO DEL CONTENEDOR

Si desea pasar variables de entorno al contenedor (es decir, variables de entorno que estarán disponibles para init y todos sus descendientes), puede utilizar los parámetros lxc.environment para hacerlo. Tenga cuidado de no pasar nada sensible; cualquier proceso en el contenedor que no tenga su entorno depurado tendrá estas variables disponibles, y las variables de entorno siempre están disponibles a través de /proc/PID/environ.

Este parámetro de configuración se puede especificar varias veces; una vez por cada variable de entorno que desee configurar.
