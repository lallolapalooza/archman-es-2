NOMBRE

lxc - contenedores linux

DESCRIPCIÓN GENERAL

La tecnología de contenedores está siendo activamente impulsada hacia el mainstream del kernel de Linux. Proporciona gestión de recursos a través de cgroups (control groups) y aislamiento de recursos mediante namespaces.

lxc, tiene como objetivo utilizar estas nuevas funcionalidades para proporcionar un objeto de contenedor de espacio de usuario que ofrece aislamiento de recursos completo y control de recursos para una aplicación o un sistema completo.

lxc es lo suficientemente pequeño como para gestionar fácilmente un contenedor con comandos simples y lo suficientemente completo como para ser utilizado para otros propósitos.

REQUISITOS

La versión del kernel >= 3.10 incluida en las distribuciones, funcionará con lxc, esta tendrá menos funcionalidades pero suficientes para ser interesante.

lxc se basa en un conjunto de funcionalidades proporcionadas por el kernel. El script auxiliar lxc-checkconfig te proporcionará información sobre la configuración de tu kernel, las características requeridas y las que faltan.

ESPECIFICACIÓN FUNCIONAL

Un contenedor es un objeto que aísla algunos recursos del host, para la aplicación o el sistema que se ejecuta en él.

La aplicación / sistema se lanzará dentro de un contenedor especificado por una configuración que se crea inicialmente o se pasa como parámetro de los comandos.

Cómo ejecutar una aplicación en un contenedor

Antes de ejecutar una aplicación, debes saber qué recursos deseas aislar. La configuración predeterminada es aislar PIDs, la IPC sysv y los puntos de montaje. Si deseas ejecutar un shell simple dentro de un contenedor, se necesita una configuración básica, especialmente si deseas compartir el rootfs. Si deseas ejecutar una aplicación como sshd, deberías proporcionar una nueva pila de red y un nuevo nombre de host. Si deseas evitar conflictos con algunos archivos, por ejemplo /var/run/httpd.pid, deberías volver a montar /var/run con un directorio vacío. Si deseas evitar los conflictos en todos los casos, puedes especificar un rootfs para el contenedor. El rootfs puede ser un árbol de directorios, previamente montado con bind con el rootfs inicial, por lo que aún puedes usar tu distribución pero con tus propios /etc y /home

Aquí tienes un ejemplo de árbol de directorios para sshd:

[root@lxc sshd]$ tree -d rootfs

rootfs	
|-- bin	
|-- dev	
|   |-- pts
|   `-- shm
|       `-- network
|-- etc	
|   `-- ssh
|-- lib	
|-- proc
|-- root
|-- sbin
|-- sys	
|-- usr	
`-- var	
    |-- empty
    |   `-- sshd
    |-- lib
    |   `-- empty
    |       `-- sshd
    `-- run
        `-- sshd

y los puntos de montaje asociados a él:

	[root@lxc sshd]$ cat fstab
	/lib /home/root/sshd/rootfs/lib none ro,bind 0 0
	/bin /home/root/sshd/rootfs/bin none ro,bind 0 0
	/usr /home/root/sshd/rootfs/usr none ro,bind 0 0
	/sbin /home/root/sshd/rootfs/sbin none ro,bind 0 0

Cómo ejecutar un sistema en un contenedor

Ejecutar un sistema dentro de un contenedor es, paradójicamente, más fácil que ejecutar una aplicación. ¿Por qué? Porque no tienes que preocuparte por los recursos a aislar, todo necesita ser aislado; los otros recursos se especifican como aislados pero sin configuración porque el contenedor los configurará. Por ejemplo, la dirección ipv4 será configurada por los scripts de inicio del contenedor del sistema. Aquí tienes un ejemplo del archivo de puntos de montaje:

	[root@lxc debian]$ cat fstab
	/dev	/home/root/debian/rootfs/dev none bind 0 0
	/dev/pts /home/root/debian/rootfs/dev/pts  none bind 0 0

CICLO DE VIDA DEL CONTENEDOR

Cuando se crea el contenedor, contiene la información de configuración. Cuando se lanza un proceso, el contenedor se estará iniciando y ejecutando. Cuando el último proceso que se ejecuta dentro del contenedor finaliza, el contenedor se detiene.

En caso de fallo durante la inicialización del contenedor, pasará por el estado de aborto.

CONFIGURACIÓN

El contenedor se configura a través de un archivo de configuración, el formato del archivo de configuración se describe en lxc.conf(5)

CREAR / DESTRUIR CONTENEDORES

Se puede crear un objeto de contenedor persistente a través del comando lxc-create. Toma un nombre de contenedor como parámetro y un archivo de configuración y plantilla opcionales. El nombre es utilizado por los diferentes comandos para referirse a este contenedor. El comando lxc-destroy destruirá el objeto del contenedor.

lxc-create -n foo
lxc-destroy -n foo

CONTENEDOR VOLÁTIL

No es obligatorio crear un objeto de contenedor antes de iniciarlo. El contenedor se puede iniciar directamente con un archivo de configuración como parámetro.

INICIAR / DETENER CONTENEDOR

Cuando el contenedor ha sido creado, está listo para ejecutar una aplicación / sistema. Este es el propósito de los comandos lxc-execute y lxc-start. Si el contenedor no fue creado antes de iniciar la aplicación, el contenedor utilizará el archivo de configuración pasado como parámetro al comando y, si no hay tal parámetro, utilizará un aislamiento predeterminado. Si la aplicación finalizó, el contenedor se detendrá, pero si es necesario, se puede usar el comando lxc-stop para detener el contenedor.

Ejecutar una aplicación dentro de un contenedor no es exactamente lo mismo que ejecutar un sistema. Por esta razón, hay dos comandos diferentes para ejecutar una aplicación en un contenedor:

lxc-execute -n foo [-f config] /bin/bash
lxc-start -n foo [-f config] [/bin/bash]

El comando lxc-execute ejecutará el comando especificado dentro de un contenedor a través de un proceso intermedio, lxc-init. Este lxc-init, después de lanzar el comando especificado, esperará su fin y todos los demás procesos reparentados. (para soportar daemons en el contenedor). En otras palabras, en el contenedor, lxc-init tiene PID 1 y el primer proceso de la aplicación tiene PID 2.

El comando lxc-start ejecutará directamente el comando especificado en el contenedor. El PID del primer proceso es 1. Si no se especifica ningún comando, lxc-start ejecutará el comando definido en lxc.init.cmd o, si no está establecido, /sbin/init.

Para resumir, lxc-execute es para ejecutar una aplicación y lxc-start es más adecuado para ejecutar un sistema.

Si la aplicación ya no responde, es inaccesible o no puede finalizar por sí misma, un comando lxc-stop salvaje matará todos los procesos en el contenedor sin piedad.

lxc-stop -n foo -k

CONECTARSE A UN TTY DISPONIBLE

Si el contenedor está configurado con ttys, es posible acceder a él a través de ellos. Corresponde al contenedor proporcionar un conjunto de ttys disponibles para ser utilizados por el siguiente comando. Cuando el tty se pierde, es posible reconectarse a él sin volver a iniciar sesión.

lxc-console -n foo -t 3

CONGELAR / DESCONGELAR CONTENEDOR

A veces, es útil detener todos los procesos que pertenecen a un contenedor, por ejemplo, para la planificación de trabajos. Los comandos:

lxc-freeze -n foo

pondrán todos los procesos en un estado no interrumpible y

lxc-unfreeze -n foo

los reanudarán.

lxc - documentation

NAME

lxc - LXC container interfaces

OVERVIEW

This document briefly describes the main commands of LXC.

REQUIREMENTS

This document applies to LXC version 2.0.0. This document does not describe the usage of the commands. For detailed description of each command, please consult the man page of the command itself.

FUNCTIONAL SPECIFICATION

FREEZING AND UNFREEZING CONTAINERS

The container freezing is implemented using the freezer cgroup controller. This is why this feature is enabled if the freezer cgroup v1 controller is enabled in the kernel.

OBTENER INFORMACIÓN SOBRE UN CONTENEDOR

Cuando hay muchos contenedores, es difícil seguir qué se ha creado o destruido, qué está en ejecución o cuáles son los PID que se ejecutan en un contenedor específico. Por esta razón, los siguientes comandos pueden ser útiles:

lxc-ls -f
lxc-info -n foo

lxc-ls lista los contenedores.

lxc-info proporciona información para un contenedor específico.

Aquí tienes un ejemplo de cómo la combinación de estos comandos permite listar todos los contenedores y recuperar su estado.

for i in $(lxc-ls -1); do
  lxc-info -n $i
done

MONITORIZAR CONTENEDOR

A veces es útil hacer un seguimiento de los estados de un contenedor, por ejemplo, para monitorizarlo o simplemente para esperar un estado específico en un script.

El comando lxc-monitor monitorizará uno o varios contenedores. El parámetro de este comando acepta una expresión regular, por ejemplo:

lxc-monitor -n "foo|bar"

monitorizará los estados de los contenedores llamados 'foo' y 'bar', y:

lxc-monitor -n ".*"

monitorizará todos los contenedores.

Para un contenedor 'foo' que se inicia, realiza algo de trabajo y sale, la salida tendrá el formato:

'foo' changed state to [STARTING]
'foo' changed state to [RUNNING]
'foo' changed state to [STOPPING]
'foo' changed state to [STOPPED]

El comando lxc-wait esperará un cambio de estado específico y saldrá. Esto es útil para scripts para sincronizar el lanzamiento de un contenedor o el final. El parámetro es una combinación OR de diferentes estados. El siguiente ejemplo muestra cómo esperar a que un contenedor se inicie correctamente como un demonio.

# lanzar lxc-wait en segundo plano
lxc-wait -n foo -s STOPPED &
LXC_WAIT_PID=$!
# este comando pasa a segundo plano
lxc-execute -n foo mydaemon &
# bloquear hasta que lxc-wait salga
# y lxc-wait sale cuando el contenedor
# está STOPPED
wait $LXC_WAIT_PID
echo "'foo' is finished"

CONFIGURACIÓN DE CGROUP PARA CONTENEDORES

El contenedor está asociado a los grupos de control, cuando se inicia un contenedor se crea un grupo de control y se asocia con él. Las propiedades del grupo de control se pueden leer y modificar cuando el contenedor se está ejecutando utilizando el comando lxc-cgroup.

El comando lxc-cgroup se utiliza para establecer o obtener un subsistema de grupo de control que está asociado con un contenedor. El nombre del subsistema es manejado por el usuario, el comando no realizará ninguna verificación de sintaxis en el nombre del subsistema, si el nombre del subsistema no existe, el comando fallará.

lxc-cgroup -n foo cpuset.cpus

mostrará el contenido de este subsistema.

lxc-cgroup -n foo cpu.shares 512

establecerá el subsistema al valor especificado.
