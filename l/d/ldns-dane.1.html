NOMBRE

ldns-dane - verificar o crear autenticación TLS con DANE (RFC6698)

SINOPSIS

ldns-dane [OPCIONES] verificar nombre puerto

ldns-dane [OPCIONES] -t archivoTLSA verificar

ldns-dane [OPCIONES] crear nombre puerto


[ UsoCertificado [ Selector [ TipoCoincidencia ] ] ]

ldns-dane -h

ldns-dane -v

DESCRIPCIÓN

En la primera forma: Se establece una conexión TLS a nombre:puerto. Los registros de recursos TLSA para nombre se utilizan para autenticar la conexión.

En la segunda forma: Los registros TLSA se leen de archivoTLSA y se utilizan para autenticar el servicio TLS que referencian.

En la tercera forma: Se establece una conexión TLS a nombre:puerto y se utiliza para crear los registros de recursos TLSA que autenticarían la conexión. Los parámetros para la creación de registros TLSA son:

UsoCertificado:

0 | PKIX-TA
Restricción de CA
1 | PKIX-EE
Restricción de certificado de servicio
2 | DANE-TA
Afirmación de ancla de confianza
3 | DANE-EE
Certificado emitido por dominio (por defecto)

Selector:

0 | Cert
Certificado completo
1 | SPKI
SubjectPublicKeyInfo (por defecto)

TipoCoincidencia:

0 | Full
No se utiliza hash
1 | SHA2-256
SHA-256 (por defecto)
2 | SHA2-512
SHA-512

OPCIONES

-4
Conexión TLS solo IPv4
-6
Conexión TLS solo IPv6
-a dirección
No intentes resolver nombre, sino conéctate a dirección en su lugar.

Esta opción se puede dar varias veces.

-b
imprimir en formato "nombre. TYPE52 \# tamaño datoshexadecimales" en lugar del formato de presentación TLSA.
-c archivocert
No conectes TLS a nombre:puerto, sino autentica (o crea registros TLSA) para el certificado (cadena) en archivocert en su lugar.
-d
Asume validez DNSSEC incluso cuando los registros TLSA se obtuvieron de forma insegura o eran falsos.
-f archivoCA
Usa archivoCA para validar.
-h
Imprimir ayuda de uso breve
-i
Interactuar después de conectarse.
-k archivollave
Especifica un archivo que contenga un registro DNSKEY o DS de confianza. Las claves se utilizan al seguir firmas (es decir, si se da -S).

Esta opción se puede dar varias veces.

Alternativamente, si -k no se especifica, y existe un ancla de confianza predeterminada (/etc/trusted-key.key) y contiene un registro DNSKEY o DS válido, se utilizará como ancla de confianza.

-n
No verifiques el nombre del servidor en el certificado.
-o desplazamiento
Al crear un registro de recurso TLSA de "Afirmación de ancla de confianza", selecciona el desplazamiento-ésimo desplazamiento de certificado desde el final de la cadena de validación. 0 significa el último certificado, 1 el penúltimo, 2 el antepenúltimo, etc.

Cuando desplazamiento es -1 (el valor por defecto), se usa el último certificado (como con 0) que DEBE ser autofirmado. Esto puede ayudar a asegurar que el ancla de confianza prevista (autofirmada) esté realmente presente en la cadena de certificados del servidor (lo cual es un requisito de DANE).

-p rutacA
Usar certificados en el directorio rutacA para validar.
-s
Al crear registros de recursos TLSA con el uso de certificado "Restricción de CA" y "Restricción de certificado de servicio", no validará y asumirá que PKIX es válido.

Para "Restricción de CA", esto significa que la verificación debe terminar con un certificado autofirmado.

-S
Seguir la(s) firma(s) hasta una clave conocida.

Sin esta opción, se confía en la red local para proporcionar un resolutor DNSSEC (es decir, se comprueba el bit AD).

-t archivoTLSA
Leer registro(s) TLSA de archivoTLSA. Cuando también se dan nombre y puerto, solo se utilizan los registros TLSA que coinciden con nombre, puerto y transporte. De lo contrario, el nombre propietario del(los) registro(s) TLSA se utilizará para determinar nombre, puerto y transporte.
-T
Devolver el estado de salida 2 para conexiones validadas PKIX sin registros TLSA (seguros).
-u
Usar transporte UDP en lugar de TCP.
-v
Mostrar versión y salir.

ARCHIVOS

/etc/trusted-key.key
El archivo del cual se cargan las claves de confianza para seguir firmas, cuando no se proporciona la opción -k.
