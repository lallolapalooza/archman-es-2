ld.so(8) System Manager's Manual ld.so(8)

NOMBRE

ld.so, ld-linux.so - enlazador/cargador dinámico

SINOPSIS

El enlazador dinámico puede ejecutarse indirectamente ejecutando algún programa o objeto compartido enlazado dinámicamente (en cuyo caso no se pueden pasar opciones de línea de comandos al enlazador dinámico y, en el caso de ELF, se ejecuta el enlazador dinámico que está almacenado en la sección .interp del programa) o directamente ejecutando:

/lib/ld-linux.so.* [OPCIONES] [PROGRAMA [ARGUMENTOS]]

DESCRIPCIÓN

Los programas ld.so y ld-linux.so* encuentran y cargan los objetos compartidos (bibliotecas compartidas) necesarios para un programa, preparan el programa para su ejecución y luego lo ejecutan.

Los binarios de Linux requieren enlazado dinámico (enlazado en tiempo de ejecución) a menos que se haya dado la opción -static a ld(1) durante la compilación.

El programa ld.so maneja binarios a.out, un formato binario utilizado hace mucho tiempo. El programa ld-linux.so* (/lib/ld-linux.so.1 para libc5, /lib/ld-linux.so.2 para glibc2) maneja binarios que están en el formato ELF más moderno. Ambos programas tienen el mismo comportamiento y utilizan los mismos archivos y programas de soporte (ldd(1), ldconfig(8), y /etc/ld.so.conf).

Al resolver dependencias de objetos compartidos, el enlazador dinámico primero inspecciona cada cadena de dependencia para ver si contiene una barra (esto puede ocurrir si se especificó una ruta de acceso de objeto compartido que contiene barras en tiempo de enlace). Si se encuentra una barra, la cadena de dependencia se interpreta como una ruta (relativa o absoluta) y el objeto compartido se carga usando esa ruta.

Si una dependencia de objeto compartido no contiene una barra, se busca en el siguiente orden:

(1)
Usando los directorios especificados en el atributo de la sección dinámica DT_RPATH del binario si está presente y el atributo DT_RUNPATH no existe.
(2)
Usando la variable de entorno LD_LIBRARY_PATH, a menos que el ejecutable se esté ejecutando en modo de ejecución segura (ver abajo), en cuyo caso esta variable se ignora.
(3)
Usando los directorios especificados en el atributo de la sección dinámica DT_RUNPATH del binario si está presente. Dichos directorios solo se buscan para encontrar los objetos requeridos por las entradas DT_NEEDED (dependencias directas) y no se aplican a los hijos de esos objetos, que deben tener sus propias entradas DT_RUNPATH. Esto es diferente de DT_RPATH, que se aplica a las búsquedas de todos los hijos en el árbol de dependencias.
(4)
Desde el archivo de caché /etc/ld.so.cache, que contiene una lista compilada de objetos compartidos candidatos encontrados previamente en la ruta de bibliotecas aumentada. Si, sin embargo, el binario se enlazó con la opción del enlazador -z nodefaultlib, se omiten los objetos compartidos en las rutas predeterminadas. Los objetos compartidos instalados en directorios de capacidades de hardware (ver abajo) tienen prioridad sobre otros objetos compartidos.
(5)
En la ruta predeterminada /lib, y luego /usr/lib. (En algunas arquitecturas de 64 bits, las rutas predeterminadas para objetos compartidos de 64 bits son /lib64, y luego /usr/lib64.) Si el binario se enlazó con la opción del enlazador -z nodefaultlib, se omite este paso.

Tokens de cadena dinámica

En varios lugares, el enlazador dinámico expande tokens de cadena dinámica:

•
En las variables de entorno LD_LIBRARY_PATH, LD_PRELOAD, y LD_AUDIT,
•
dentro de los valores de las etiquetas de sección dinámica DT_NEEDED, DT_RPATH, DT_RUNPATH, DT_AUDIT, y DT_DEPAUDIT de binarios ELF,
•
en los argumentos de las opciones de línea de comandos de ld.so --audit, --library-path, y --preload (ver abajo), y
•
en los argumentos de nombre de archivo de las funciones dlopen(3) y dlmopen(3).

Los tokens sustituidos son los siguientes:

$ORIGIN (o equivalentemente ${ORIGIN})
Esto se expande al directorio que contiene el programa o el objeto compartido. Por lo tanto, una aplicación ubicada en somedir/app podría compilarse con

gcc -Wl,-rpath,'$ORIGIN/../lib'

para que encuentre un objeto compartido asociado en somedir/lib sin importar dónde se ubique somedir en la jerarquía de directorios. Esto facilita la creación de aplicaciones "llave en mano" que no necesitan instalase en directorios especiales, sino que pueden descomprimirse en cualquier directorio y aun así encontrar sus propios objetos compartidos.
$LIB (o equivalentemente ${LIB})
Esto se expande a lib o lib64 según la arquitectura (por ejemplo, en x86-64, se expande a lib64 y en x86-32, se expande a lib).
$PLATFORM (o equivalentemente ${PLATFORM})
Esto se expande a una cadena correspondiente al tipo de procesador del sistema host (por ejemplo, "x86_64"). En algunas arquitecturas, el kernel de Linux no proporciona una cadena de plataforma al enlazador dinámico. El valor de esta cadena se toma del valor AT_PLATFORM en el vector auxiliar (ver getauxval(3)).

Tenga en cuenta que los tokens de cadena dinámica deben citarse correctamente cuando se establecen desde un shell, para evitar su expansión como variables de shell o de entorno.

OPCIONES

--argv0 cadena (desde glibc 2.33)
Establece argv[0] al valor cadena antes de ejecutar el programa.
--audit lista
Usa los objetos nombrados en lista como auditores. Los objetos en lista están delimitados por dos puntos.
--glibc-hwcaps-mask lista
solo busca subdirectorios incorporados si están en lista.
--glibc-hwcaps-prepend lista
Busca subdirectorios glibc-hwcaps en lista.
--inhibit-cache
No usar /etc/ld.so.cache.
--library-path ruta
Usa ruta en lugar de la configuración de la variable de entorno LD_LIBRARY_PATH (ver abajo). Los nombres ORIGIN, LIB, y PLATFORM se interpretan como para la variable de entorno LD_LIBRARY_PATH.
--inhibit-rpath lista
Ignora la información RPATH y RUNPATH en los nombres de objetos de lista. Esta opción se ignora al ejecutarse en modo de ejecución segura (ver abajo). Los objetos en lista están delimitados por dos puntos o espacios.
--list
Lista todas las dependencias y cómo se resuelven.
--list-diagnostics (desde glibc 2.33)
Imprime información de diagnóstico del sistema en un formato legible por máquina, como algunas variables internas del cargador, el vector auxiliar (ver getauxval(3)) y las variables de entorno. En algunas arquitecturas, el comando puede imprimir información adicional (como las características de la CPU utilizadas en la selección de funciones indirectas de GNU en x86). --list-tunables (desde glibc 2.33) Imprime los nombres y valores de todos los tunables, junto con los valores mínimos y máximos permitidos.
--preload lista (desde glibc 2.30)
Precarga los objetos especificados en lista. Los objetos en lista están delimitados por dos puntos o espacios. Los objetos se precargan como se explica en la descripción de la variable de entorno LD_PRELOAD abajo.
En contraste con LD_PRELOAD, la opción --preload proporciona una forma de realizar la precarga para un solo ejecutable sin afectar la precarga realizada en ningún proceso hijo que ejecute un nuevo programa.
--verify
Verifica que el programa está enlazado dinámicamente y que este enlazador dinámico puede manejarlo.
AMBIENTE

Varias variables de entorno influyen en el funcionamiento del enlazador dinámico.

Modo de ejecución seguro

Por razones de seguridad, si el enlazador dinámico determina que un binario debe ejecutarse en modo de ejecución segura, los efectos de algunas variables de entorno se anulan o modifican, y además esas variables de entorno se eliminan del entorno, de modo que el programa ni siquiera ve las definiciones. Algunas de estas variables de entorno afectan al propio funcionamiento del enlazador dinámico y se describen a continuación. Otras variables de entorno tratadas de esta manera incluyen: GCONV_PATH, GETCONF_DIR, HOSTALIASES, LD_AUDIT, LD_DEBUG, LD_DEBUG_OUTPUT, LD_DYNAMIC_WEAK, LD_HWCAP_MASK, LD_LIBRARY_PATH, LD_ORIGIN_PATH, LD_PRELOAD, LD_PROFILE, LD_SHOW_AUXV, LOCALDOMAIN, LOCPATH, MALLOC_TRACE, NIS_PATH, NLSPATH, RESOLV_HOST_CONF, RES_OPTIONS, TMPDIR y TZDIR.

Un binario se ejecuta en modo de ejecución segura si la entrada AT_SECURE en el vector auxiliar (ver getauxval(3)) tiene un valor distinto de cero. Esta entrada puede tener un valor distinto de cero por varias razones, entre ellas:

•
Las identidades de usuario real y efectiva del proceso difieren, o las identidades de grupo real y efectiva difieren. Esto suele ocurrir como resultado de la ejecución de un programa set-user-ID o set-group-ID.
•
Un proceso con una ID de usuario que no es root ejecutó un binario que confería capacidades al proceso.
•
Un módulo de seguridad de Linux puede haber establecido un valor distinto de cero.

Variables de entorno

Entre las variables de entorno más importantes se encuentran las siguientes:

LD_ASSUME_KERNEL (desde glibc 2.2.3 hasta glibc 2.36)
Cada objeto compartido puede informar al enlazador dinámico de la versión mínima de ABI del kernel que requiere. (Este requisito está codificado en una sección de nota ELF que se puede ver a través de readelf -n como una sección etiquetada como NT_GNU_ABI_TAG). En tiempo de ejecución, el enlazador dinámico determina la versión de ABI del kernel en ejecución y rechazará la carga de objetos compartidos que especifiquen versiones de ABI mínimas que excedan esa versión de ABI.
LD_ASSUME_KERNEL se puede utilizar para hacer que el enlazador dinámico asuma que se está ejecutando en un sistema con una versión de ABI del kernel diferente. Por ejemplo, la siguiente línea de comandos hace que el enlazador dinámico asuma que se está ejecutando en Linux 2.2.5 al cargar los objetos compartidos requeridos por myprog:

$ LD_ASSUME_KERNEL=2.2.5 ./myprog

En sistemas que proporcionan varias versiones de un objeto compartido (en diferentes directorios en la ruta de búsqueda) que tienen diferentes requisitos de versión mínima de ABI del kernel, LD_ASSUME_KERNEL se puede utilizar para seleccionar la versión del objeto que se utiliza (dependiendo del orden de búsqueda de directorios).
Históricamente, el uso más común de la característica LD_ASSUME_KERNEL era seleccionar manualmente la implementación anterior de hilos POSIX LinuxThreads en sistemas que proporcionaban tanto LinuxThreads como NPTL (esta última era típicamente la predeterminada en tales sistemas); ver pthreads(7).
LD_BIND_NOW (desde glibc 2.1.1)
Si se establece en una cadena no vacía, hace que el enlazador dinámico resuelva todos los símbolos al inicio del programa en lugar de diferir la resolución de llamadas a funciones hasta el momento en que se referencian por primera vez. Esto es útil cuando se utiliza un depurador.
LD_LIBRARY_PATH
Una lista de directorios en los que buscar bibliotecas ELF en tiempo de ejecución. Los elementos de la lista están separados por dos puntos o punto y coma, y no hay soporte para escapar ninguno de los separadores. Un nombre de directorio de longitud cero indica el directorio de trabajo actual.
Esta variable se ignora en el modo de ejecución segura.
Dentro de las rutas especificadas en LD_LIBRARY_PATH, el enlazador dinámico expande los tokens $ORIGIN, $LIB y $PLATFORM (o las versiones que usan llaves alrededor de los nombres) como se describe anteriormente en Tokens de cadena dinámicos. Por lo tanto, por ejemplo, lo siguiente haría que se buscara una biblioteca en el subdirectorio lib o lib64 debajo del directorio que contiene el programa que se va a ejecutar:

$ LD_LIBRARY_PATH='$ORIGIN/$LIB' prog

(¡Tenga en cuenta el uso de comillas simples, que evitan la expansión de $ORIGIN y $LIB como variables del shell!)
LD_PRELOAD
Una lista de objetos compartidos ELF adicionales especificados por el usuario para ser cargados antes que todos los demás. Esta característica se puede utilizar para anular selectivamente funciones en otros objetos compartidos.
Los elementos de la lista pueden separarse por espacios o dos puntos, y no hay soporte para escapar ninguno de los separadores. Los objetos se buscan utilizando las reglas dadas en DESCRIPCIÓN. Los objetos se buscan y se añaden al mapa de enlaces en el orden de izquierda a derecha especificado en la lista.
En el modo de ejecución segura, las rutas de precarga que contienen barras se ignoran. Además, los objetos compartidos solo se precargan de los directorios de búsqueda estándar y solo si tienen activado el bit de modo set-user-ID (lo cual no es típico).
Dentro de los nombres especificados en la lista LD_PRELOAD, el enlazador dinámico comprende los tokens $ORIGIN, $LIB y $PLATFORM (o las versiones que usan llaves alrededor de los nombres) como se describe anteriormente en Tokens de cadena dinámicos. (Ver también la discusión sobre el uso de comillas bajo la descripción de LD_LIBRARY_PATH).
Existen varios métodos para especificar bibliotecas que se precargarán, y estos se manejan en el siguiente orden:
(1)
La variable de entorno LD_PRELOAD.
(2)
La opción de línea de comandos --preload al invocar el enlazador dinámico directamente.
(3)
El archivo /etc/ld.so.preload (descrito a continuación).
LD_TRACE_LOADED_OBJECTS
Si se establece (a cualquier valor), hace que el programa liste sus dependencias dinámicas, como si se ejecutara con ldd(1), en lugar de ejecutarse normalmente.

Luego hay muchas variables más o menos oscuras, muchas obsoletas o solo para uso interno.

LD_AUDIT (desde glibc 2.4)
Una lista de objetos compartidos ELF especificados por el usuario para ser cargados antes que todos los demás en un espacio de nombres de enlazador separado (es decir, uno que no interfiere con los enlaces de símbolos normales que ocurrirían en el proceso). Estos objetos se pueden utilizar para auditar el funcionamiento del enlazador dinámico. Los elementos de la lista están separados por dos puntos, y no hay soporte para escapar el separador.
LD_AUDIT se ignora en el modo de ejecución segura.
El enlazador dinámico notificará a los objetos compartidos de auditoría en los llamados puntos de control de auditoría —por ejemplo, al cargar un nuevo objeto compartido, resolver un símbolo o llamar a un símbolo de otro objeto compartido— llamando a una función apropiada dentro del objeto compartido de auditoría. Para más detalles, ver rtld-audit(7). La interfaz de auditoría es en gran medida compatible con la proporcionada en Solaris, como se describe en su Guía de enlazador y bibliotecas, en el capítulo Interfaz de auditoría del enlazador en tiempo de ejecución.
Dentro de los nombres especificados en la lista LD_AUDIT, el enlazador dinámico comprende los tokens $ORIGIN, $LIB y $PLATFORM (o las versiones que usan llaves alrededor de los nombres) como se describe anteriormente en Tokens de cadena dinámicos. (Ver también la discusión sobre el uso de comillas bajo la descripción de LD_LIBRARY_PATH).
Desde glibc 2.13, en modo de ejecución segura, los nombres en la lista de auditoría que contienen barras se ignoran, y solo se cargan los objetos compartidos en los directorios de búsqueda estándar que tienen activado el bit de modo set-user-ID.
LD_BIND_NOT (desde glibc 2.1.95)
Si esta variable de entorno se establece en una cadena no vacía, no actualice la GOT (tabla de desplazamiento global) y la PLT (tabla de enlace de procedimientos) después de resolver un símbolo de función. Al combinar el uso de esta variable con LD_DEBUG (con las categorías bindings y symbols), se pueden observar todos los enlaces de funciones en tiempo de ejecución.
LD_DEBUG (desde glibc 2.1)
Produce información de depuración detallada sobre el funcionamiento del enlazador dinámico. El contenido de esta variable son una o más de las siguientes categorías, separadas por dos puntos, comas o (si el valor está entre comillas) espacios:
help
Especificar help en el valor de esta variable no ejecuta el programa especificado y muestra un mensaje de ayuda sobre qué categorías se pueden especificar en esta variable de entorno.
all
Imprime toda la información de depuración (excepto statistics y unused; ver abajo).
bindings
Muestra información sobre a qué definición se vincula cada símbolo.
files
Muestra el progreso del archivo de entrada.
libs
Muestra las rutas de búsqueda de bibliotecas.
reloc
Muestra el procesamiento de reubicación.
scopes
Muestra información de ámbito.
statistics
Muestra estadísticas de reubicación.

ENVIRONMENT

LD_DEBUG
Display debugging information to standard error. A colon-separated list of keywords can be specified. The following keywords are known:
libs
Display search paths for shared object binary libraries.
reloc
Display relocation information.
symbols
Display search paths for each symbol look-up.
unused
Determine unused DSOs.
versions
Display version dependencies.
Since glibc 2.3.4, LD_DEBUG is ignored in secure-execution mode, unless the file /etc/suid-debug exists (the content of the file is irrelevant).
LD_DEBUG_OUTPUT (since glibc 2.1)
By default, LD_DEBUG output is written to standard error. If LD_DEBUG_OUTPUT is defined, then output is written to the pathname specified by its value, with the suffix "." (dot) followed by the process ID appended to the pathname.
LD_DEBUG_OUTPUT is ignored in secure-execution mode.
LD_DYNAMIC_WEAK (since glibc 2.1.91)
By default, when searching shared libraries to resolve a symbol reference, the dynamic linker will resolve to the first definition it finds.
Old glibc versions (before glibc 2.2), provided a different behavior: if the linker found a symbol that was weak, it would remember that symbol and keep searching in the remaining shared libraries. If it subsequently found a strong definition of the same symbol, then it would instead use that definition. (If no further symbol was found, then the dynamic linker would use the weak symbol that it initially found.)
The old glibc behavior was nonstandard. (Standard practice is that the distinction between weak and strong symbols should have effect only at static link time.) In glibc 2.2, the dynamic linker was modified to provide the current behavior (which was the behavior that was provided by most other implementations at that time).
Defining the LD_DYNAMIC_WEAK environment variable (with any value) provides the old (nonstandard) glibc behavior, whereby a weak symbol in one shared library may be overridden by a strong symbol subsequently discovered in another shared library. (Note that even when this variable is set, a strong symbol in a shared library will not override a weak definition of the same symbol in the main program.)
Since glibc 2.3.4, LD_DYNAMIC_WEAK is ignored in secure-execution mode.
LD_HWCAP_MASK (from glibc 2.1 to glibc 2.38)
Mask for hardware capabilities. Since glibc 2.26, the option might be ignored if glibc does not support tunables.
LD_ORIGIN_PATH (since glibc 2.1)
Path where the binary is found.
Since glibc 2.4, LD_ORIGIN_PATH is ignored in secure-execution mode.
LD_POINTER_GUARD (from glibc 2.4 to glibc 2.22)
Set to 0 to disable pointer guarding. Any other value enables pointer guarding, which is also the default. Pointer guarding is a security mechanism whereby some pointers to code stored in writable program memory (return addresses saved by setjmp(3) or function pointers used by various glibc internals) are mangled semi-randomly to make it more difficult for an attacker to hijack the pointers for use in the event of a buffer overrun or stack-smashing attack. Since glibc 2.23, LD_POINTER_GUARD can no longer be used to disable pointer guarding, which is now always enabled.
LD_PROFILE (since glibc 2.1)
The name of a (single) shared object to be profiled, specified either as a pathname or a soname. Profiling output is appended to the file whose name is: $LD_PROFILE_OUTPUT/$LD_PROFILE.profile.
Since glibc 2.2.5, LD_PROFILE uses a different default path in secure-execution mode.
LD_PROFILE_OUTPUT (since glibc 2.1)
Directory where LD_PROFILE output should be written. If this variable is not defined, or is defined as an empty string, then the default is /var/tmp.
LD_PROFILE_OUTPUT is ignored in secure-execution mode; instead /var/profile is always used.
LD_SHOW_AUXV (since glibc 2.1)
If this environment variable is defined (with any value), show the auxiliary array passed up from the kernel (see also getauxval(3)).
Since glibc 2.3.4, LD_SHOW_AUXV is ignored in secure-execution mode.
LD_TRACE_LOADED_OBJECTS
If this environment variable is set (to any value), then instead of executing the program, the dynamic linker will print the names of the shared objects that would be loaded and the search paths that would be followed, and then exit. This can be used to debug problems with shared library linking. If LD_WARN is also set, then warnings about unresolved symbols are also displayed.
Since glibc 2.2.5, LD_TRACE_LOADED_OBJECTS is ignored in secure-execution mode.
LD_TRACE_PRELINKING (from glibc 2.4 to glibc 2.35)
If this environment variable is defined, trace prelinking of the object whose name is assigned to this environment variable. (Use ldd(1) to get a list of the objects that might be traced.) If the object name is not recognized, then all prelinking activity is traced.
LD_USE_LOAD_BIAS (from glibc 2.3.3 to glibc 2.35)
By default (i.e., if this variable is not defined), executables and prelinked shared objects will honor base addresses of their dependent shared objects and (nonprelinked) position-independent executables (PIEs) and other shared objects will not honor them. If LD_USE_LOAD_BIAS is defined with the value 1, both executables and PIEs will honor the base addresses. If LD_USE_LOAD_BIAS is defined with the value 0, neither executables nor PIEs will honor the base addresses.
Since glibc 2.3.3, this variable is ignored in secure-execution mode.
LD_VERBOSE (since glibc 2.1)
If set to a nonempty string, output symbol versioning information about the program if the LD_TRACE_LOADED_OBJECTS environment variable has been set.
LD_WARN (since glibc 2.1.3)
If set to a nonempty string, warn about unresolved symbols.
LD_PREFER_MAP_32BIT_EXEC (x86-64 only; since glibc 2.23)
According to the Intel Silvermont software optimization guide, for 64-bit applications, branch prediction performance can be negatively impacted when the target of a branch is more than 4 GB away from the branch. If this environment variable is set (to any value), the dynamic linker will first try to map executable pages using the mmap(2) MAP_32BIT flag, and fall back to mapping without that flag if that attempt fails. NB: MAP_32BIT will map to the low 2 GB (not 4 GB) of the address space.
Because MAP_32BIT reduces the address range available for address space layout randomization (ASLR), LD_PREFER_MAP_32BIT_EXEC is always disabled in secure-execution mode.

Legacy Hardware capabilities (from glibc 2.5 to glibc 2.37)

Some shared objects are compiled using hardware-specific instructions which do not exist on every CPU. Such objects should be installed in directories whose names define the required hardware capabilities, such as /usr/lib/sse2/. The dynamic linker checks these directories against the hardware of the machine and selects the most suitable version of a given shared object. Hardware capability directories can be cascaded to combine CPU features. The list of supported hardware capability names depends on the CPU. The following names are currently recognized:

Alpha
ev4, ev5, ev56, ev6, ev67
MIPS
loongson2e, loongson2f, octeon, octeon2
PowerPC
4xxmac, altivec, arch_2_05, arch_2_06, booke, cellbe, dfp, efpdouble, efpsingle, fpu, ic_snoop, mmu, notb, pa6t, power4, power5, power5+, power6x, ppc32, ppc601, ppc64, smt, spe, ucache, vsx
SPARC
flush, muldiv, stbar, swap, ultra3, v9, v9v, v9v2
s390

The legacy hard

NOTES

The glibc library uses hardware capabilities to provide optimized code for specific CPU architectures and instruction sets. This mechanism allows the dynamic linker to select the most appropriate version of a shared library at runtime, based on the capabilities of the executing hardware. This can lead to significant performance improvements for applications that utilize these capabilities.

The older, non-glibc hardware capabilities support has the drawback that each new feature added grows the search path exponentially, because it has to be added to every combination of the other existing features.

For instance, on x86 32-bit, if the hardware supports i686 and sse2, the resulting search path will be i686/sse2:i686:sse2:.. A new capability newcap will set the search path to newcap/i686/sse2:newcap/i686:newcap/sse2:newcap:i686/sse2:i686:sse2:.

glibc Hardware capabilities (from glibc 2.33)

glibc 2.33 added a new hardware capability scheme,
where under each CPU architecture, certain levels can be defined, grouping support for certain features or special instructions. Each architecture level has a fixed set of paths that it adds to the dynamic linker search list, depending on the hardware of the machine. Since each new architecture level is not combined with previously existing ones, the new scheme does not have the drawback of growing the dynamic linker search list uncontrollably.

For instance, on x86 64-bit, if the hardware supports x86_64-v3 (for instance Intel Haswell or AMD Excavator), the resulting search path will be glibc-hwcaps/x86-64-v3:glibc-hwcaps/x86-64-v2:. The following paths are currently supported, in priority order.

PowerPC (64-bit little-endian only)
power10, power9
s390 (64-bit only)
z16, z15, z14, z13
x86 (64-bit only)
x86-64-v4, x86-64-v3, x86-64-v2

glibc 2.37 removed support for the legacy hardware capabilities.
