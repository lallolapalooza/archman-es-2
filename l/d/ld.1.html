LD(1) Herramientas de desarrollo GNU LD(1)

NOMBRE

ld - El enlazador GNU

SINOPSIS

ld [opciones] archivos-objeto ...

DESCRIPCIÓN

ld combina un número de archivos objeto y de archivo, relocaliza sus datos y resuelve las referencias de símbolos. Usualmente, el último paso en la compilación de un programa es ejecutar ld.

ld acepta archivos de lenguaje de comandos de enlazado escritos en un superconjunto de la sintaxis del Lenguaje de Comandos del Editor de Enlace de AT&T, para proporcionar control explícito y total sobre el proceso de enlazado.

Esta página del manual no describe el lenguaje de comandos; ver la entrada de ld en "info" para detalles completos sobre el lenguaje de comandos y sobre otros aspectos del enlazador GNU.

Esta versión de ld utiliza las bibliotecas BFD de propósito general para operar sobre archivos objeto. Esto permite a ld leer, combinar y escribir archivos objeto en muchos formatos diferentes; por ejemplo, COFF o "a.out". Diferentes formatos pueden ser enlazados juntos para producir cualquier tipo de archivo objeto disponible.

Además de su flexibilidad, el enlazador GNU es más útil que otros enlazadores al proporcionar información diagnóstica. Muchos enlazadores abandonan la ejecución inmediatamente al encontrar un error; siempre que sea posible, ld continúa ejecutándose, permitiéndole identificar otros errores (o, en algunos casos, obtener un archivo de salida a pesar del error).

El enlazador GNU ld está pensado para cubrir una amplia gama de situaciones y para ser lo más compatible posible con otros enlazadores. Como resultado, usted tiene muchas opciones para controlar su comportamiento.

OPCIONES

El enlazador soporta una gran cantidad de opciones de línea de comandos, pero en la práctica pocas de ellas se utilizan en un contexto particular. Por ejemplo, un uso frecuente de ld es enlazar archivos objeto estándar de Unix en un sistema Unix estándar y soportado. En tal sistema, para enlazar un archivo "hello.o":

ld -o <salida> /lib/crt0.o hello.o -lc

Esto le dice a ld que produzca un archivo llamado salida como resultado de enlazar el archivo "/lib/crt0.o" con "hello.o" y la biblioteca "libc.a", que vendrá de los directorios de búsqueda estándar. (Ver la discusión de la opción -l abajo).

Algunas de las opciones de línea de comandos para ld pueden ser especificadas en cualquier punto de la línea de comandos. Sin embargo, las opciones que se refieren a archivos, como -l o -T, causan que el archivo sea leído en el punto en el que la opción aparece en la línea de comandos, en relación con los archivos objeto y otras opciones de archivo. Repetir opciones no relacionadas con archivos con un argumento diferente no tendrá ningún efecto adicional, o anulará ocurrencias previas (las más a la izquierda en la línea de comandos) de esa opción. Las opciones que pueden ser significativamente especificadas más de una vez se anotan en las descripciones a continuación.

Los argumentos que no son opciones son archivos objeto o archivos que serán enlazados juntos. Pueden seguir, preceder o mezclarse con las opciones de la línea de comandos, excepto que un argumento de archivo objeto no puede colocarse entre una opción y su argumento.

Usualmente el enlazador se invoca con al menos un archivo objeto, pero usted puede especificar otras formas de archivos de entrada binarios usando -l, -R, y el lenguaje de comandos de script. Si no se especifican archivos de entrada binarios en absoluto, el enlazador no produce ninguna salida y emite el mensaje No input files.

Si el enlazador no puede reconocer el formato de un archivo objeto, asumirá que es un script de enlazador. Un script especificado de esta manera complementa el script de enlazador principal utilizado para el enlace (ya sea el script de enlazador por defecto o el especificado usando -T). Esta característica permite al enlazador enlazar contra un archivo que parece ser un objeto o un archivo, pero que en realidad solo define algunos valores de símbolo, o utiliza "INPUT" o "GROUP" para cargar otros objetos. Especificar un script de esta manera solo complementa el script de enlazador principal, con los comandos adicionales colocados después del script principal; use la opción -T para reemplazar completamente el script de enlazador por defecto, pero tenga en cuenta el efecto del comando "INSERT".

Para opciones cuyos nombres son una sola letra, los argumentos de opción deben seguir la letra de opción sin espacios intermedios, o darse como argumentos separados inmediatamente después de la opción que los requiere.

Para opciones cuyos nombres son múltiples letras, un guión o dos pueden preceder al nombre de la opción; por ejemplo, -trace-symbol y --trace-symbol son equivalentes. Tenga en cuenta: hay una excepción a esta regla. Las opciones de múltiples letras que comienzan con una 'o' minúscula solo pueden ir precedidas por dos guiones. Esto es para reducir la confusión con la opción -o. Así, por ejemplo, -omagic establece el nombre del archivo de salida a magic, mientras que --omagic establece la bandera NMAGIC en la salida.

Los argumentos para las opciones de múltiples letras deben estar separados del nombre de la opción por un signo igual, o darse como argumentos separados inmediatamente después de la opción que los requiere. Por ejemplo, --trace-symbol foo y --trace-symbol=foo son equivalentes. Se aceptan abreviaturas únicas de los nombres de las opciones de múltiples letras.

Tenga en cuenta: si el enlazador se invoca indirectamente, a través de un controlador de compilación (por ejemplo, gcc), entonces todas las opciones de línea de comandos del enlazador deben ir precedidas por -Wl, (o lo que sea apropiado para el controlador de compilación particular) de esta manera:

gcc -Wl,--start-group foo.o bar.o -Wl,--end-group

Esto es importante, porque de lo contrario el programa controlador de compilación podría descartar silenciosamente las opciones del enlazador, resultando en un enlace incorrecto. La confusión también puede surgir al pasar opciones que requieren valores a través de un controlador, ya que el uso de un espacio entre la opción y el argumento actúa como un separador, y hace que el controlador pase solo la opción al enlazador y el argumento al compilador. En este caso, lo más sencillo es utilizar las formas unidas tanto de las opciones de una sola letra como de múltiples letras, tales como:

gcc foo.o bar.o -Wl,-eENTRY -Wl,-Map=a.map

Cualquier carácter (incluido una barra invertida) puede incluirse anteponiendo el carácter a incluir con una barra invertida. Si se especifica varias veces, "DT_DEPAUDIT" contendrá una lista de interfaces de auditoría separadas por dos puntos para usar. --enable-linker-version
Habilita la directiva de script del enlazador "LINKER_VERSION", descrita en Output Section Data. Si se utiliza esta directiva en un script de enlazador y se ha habilitado esta opción, se insertará una cadena que contiene la versión del enlazador en el punto actual.

Nota: la ubicación de esta opción en la línea de comandos del enlazador es significativa. Solo afectará a los scripts de enlazador que vengan después en la línea de comandos, o que estén integrados en el enlazador.

--disable-linker-version
Deshabilita la directiva de script del enlazador "LINKER_VERSION", para que no inserte una cadena de versión. Este es el comportamiento predeterminado.
--enable-non-contiguous-regions
Esta opción evita generar un error si una sección de entrada no encaja en una sección de salida coincidente. El enlazador intenta asignar la sección de entrada a secciones de salida coincidentes posteriores y solo genera un error si ninguna sección de salida es lo suficientemente grande. Esto es útil cuando hay varias regiones de memoria no contiguas disponibles y la sección de entrada no requiere una en particular. El orden en que se evalúan las secciones de entrada no cambia, por ejemplo: 
MEMORY {
  MEM1 (rwx) : ORIGIN = 0x1000, LENGTH = 0x14
  MEM2 (rwx) : ORIGIN = 0x1000, LENGTH = 0x40
  MEM3 (rwx) : ORIGIN = 0x2000, LENGTH = 0x40
}
SECTIONS {
  mem1 : { *(.data.*); } > MEM1
  mem2 : { *(.data.*); } > MEM2
  mem3 : { *(.data.*); } > MEM3
}

con secciones de entrada:
.data.1: tamaño 8
.data.2: tamaño 0x10
.data.3: tamaño 4

resulta en .data.1 asignada a mem1, y .data.2 y .data.3
asignadas a mem2, aunque .data.3 cabría en mem3.

Esta opción es incompatible con las sentencias INSERT porque cambia la forma en que las secciones de entrada se asignan a las secciones de salida.

--enable-non-contiguous-regions-warnings
Esta opción habilita advertencias cuando "--enable-non-contiguous-regions" permite coincidencias posiblemente inesperadas en la asignación de secciones, lo que podría llevar a descartar silenciosamente una sección en lugar de fallar porque no encaja en ninguna región de salida.
-e entry
--entry=entry
Use entry como el símbolo explícito para comenzar la ejecución de su programa, en lugar del punto de entrada predeterminado. Si no hay ningún símbolo llamado entry, el enlazador intentará analizar entry como un número y lo usará como la dirección de entrada (el número se interpretará en base 10; puede usar un prefijo 0x para base 16, o un prefijo 0 para base 8). Para i386 PE, entry también puede ser el nombre de la función original (sin el guion bajo inicial y/o el sufijo stdcall @number cuando sea aplicable).
--exclude-libs lib,lib,...
Especifica una lista de bibliotecas de archivo de las cuales los símbolos no deben ser exportados automáticamente. Los nombres de las bibliotecas pueden estar delimitados por comas o dos puntos. Especificar "--exclude-libs ALL" excluye los símbolos de todas las bibliotecas de archivo de la exportación automática. Esta opción solo está disponible para el puerto i386 PE del enlazador y para los puertos ELF. Para i386 PE, los símbolos listados explícitamente en un archivo .def todavía se exportan, independientemente de esta opción. Para los puertos ELF, los símbolos afectados por esta opción se tratarán como ocultos.
--exclude-modules-for-implib module,module,...
Especifica una lista de archivos objeto o miembros de archivo, de los cuales los símbolos no deben exportarse automáticamente, pero que deben copiarse íntegramente a la biblioteca de importación que se genera durante el enlace. Los nombres de los módulos pueden estar delimitados por comas o dos puntos, y deben coincidir exactamente con los nombres de archivo utilizados por ld para abrir los archivos; para miembros de archivo, este es simplemente el nombre del miembro, pero para archivos objeto, el nombre listado debe incluir y coincidir exactamente con cualquier ruta utilizada para especificar el archivo de entrada en la línea de comandos del enlazador. Esta opción solo está disponible para el puerto i386 PE del enlazador. Los símbolos listados explícitamente en un archivo .def todavía se exportan, independientemente de esta opción.
-E
--export-dynamic
--no-export-dynamic
Al crear un ejecutable enlazado dinámicamente, usar la opción -E o la opción --export-dynamic hace que el enlazador agregue todos los símbolos a la tabla de símbolos dinámicos. La tabla de símbolos dinámicos es el conjunto de símbolos que son visibles desde objetos dinámicos en tiempo de ejecución.

Si no usa ninguna de estas opciones (o usa la opción --no-export-dynamic para restaurar el comportamiento predeterminado), la tabla de símbolos dinámicos normalmente contendrá solo aquellos símbolos que son referenciados por algún objeto dinámico mencionado en el enlace.

Si usa "dlopen" para cargar un objeto dinámico que necesita referirse a los símbolos definidos por el programa, en lugar de algún otro objeto dinámico, entonces probablemente necesitará usar esta opción al enlazar el programa en sí.

También puede usar la lista dinámica para controlar qué símbolos deben agregarse a la tabla de símbolos dinámicos si el formato de salida lo admite. Consulte la descripción de --dynamic-list.

Tenga en cuenta que esta opción es específica para los puertos ELF. Los destinos PE admiten una función similar para exportar todos los símbolos de una DLL o EXE; consulte la descripción de --export-all-symbols a continuación.

Al crear una biblioteca compartida, las referencias a símbolos que coincidan con glob no se vincularán a las definiciones dentro de la biblioteca compartida. Esta opción no tiene efecto al crear una biblioteca compartida y no se especifican -Bsymbolic o --dynamic-list. Esta opción solo es significativa en plataformas ELF que admiten bibliotecas compartidas.

-aux name
When creating an ELF shared object, create a DT_AUXILIARY entry pointing to the shared object name. This option may be specified more than once. The DT_AUXILIARY entries will be created in the order in which they appear on the command line.
-F name
--filter=name
When creating an ELF shared object, set the internal DT_FILTER field to the specified name. This tells the dynamic linker that the symbol table of the shared object which is being created should be used as a filter on the symbol table of the shared object name.

If you later link a program against this filter object, then, when you run the program, the dynamic linker will see the DT_FILTER field. The dynamic linker will resolve symbols according to the symbol table of the filter object as usual, but it will actually link to the definitions found in the shared object name. Thus the filter object can be used to select a subset of the symbols provided by the object name.

Some older linkers used the -F option throughout a compilation toolchain for specifying object-file format for both input and output object files. The GNU linker uses other mechanisms for this purpose: the -b, --format, --oformat options, the "TARGET" command in linker scripts, and the "GNUTARGET" environment variable. The GNU linker will ignore the -F option when not creating an ELF shared object.

When creating an ELF executable or shared object, call NAME when the executable or shared object is unloaded, by setting DT_FINI to the address of the function. By default, the linker uses "_fini" as the function to call.

-l namespec
--library=namespec
Add the archive or object file specified by namespec to the list of files to link. This option may be used any number of times. If namespec is of the form :filename, ld will search the library path for a file called filename, otherwise it will search the library path for a file called libnamespec.a.

On systems which support shared libraries, ld may also search for files other than libnamespec.a. Specifically, on ELF and SunOS systems, ld will search a directory for a library called libnamespec.so before searching for one called libnamespec.a. (By convention, a ".so" extension indicates a shared library.) Note that this behavior does not apply to :filename, which always specifies a file called filename.

The linker will search an archive only once, at the location where it is specified on the command line. If the archive defines a symbol which was undefined in some object which appeared before the archive on the command line, the linker will include the appropriate file(s) from the archive. However, an undefined symbol in an object appearing later on the command line will not cause the linker to search the archive again.

See the -( option for a way to force the linker to search archives multiple times.

You may list the same archive multiple times on the command line.

This type of archive searching is standard for Unix linkers. However, if you are using ld on AIX, note that it is different from the behaviour of the AIX linker.

-L searchdir
--library-path=searchdir
Add path searchdir to the list of paths that ld will search for archive libraries and ld control scripts. You may use this option any number of times. The directories are searched in the order in which they are specified on the command line. Directories specified on the command line are searched before the default directories. All -L options apply to all -l options, regardless of the order in which the options appear. -L options do not affect how ld searches for a linker script unless -T option is specified.

If searchdir begins with "=" or $SYSROOT, then this prefix will be replaced by the sysroot prefix, controlled by the --sysroot option, or specified when the linker is configured.

The default set of paths searched (without being specified with -L) depends on which emulation mode ld is using, and in some cases also on how it was configured.

The paths can also be specified in a link script with the "SEARCH_DIR" command. Directories specified this way are searched at the point in which the linker script appears in the command line.

-m emulation
Emulate the emulation linker. You can list the available emulations with the --verbose or -V options.

If the -m option is not used, the emulation is taken from the "LDEMULATION" environment variable, if that is defined.

Otherwise, the default emulation depends upon how the linker was configured.

--remap-inputs=pattern=filename
--remap-inputs-file=file
These options allow the names of input files to be changed before the linker attempts to open them. The option --remap-inputs=foo.o=bar.o will cause any attempt to load a file called foo.o to instead try to load a file called bar.o. Wildcard patterns are permitted in the first filename, so --remap-inputs=foo*.o=bar.o will rename any input file that matches foo*.o to bar.o.

An alternative form of the option --remap-inputs-file=filename allows the remappings to be read from a file. Each line in the file can contain a single remapping. Blank lines are ignored. Anything from a hash character (#) to the end of a line is considered to be a comment and is also ignored. The mapping pattern can be separated from the filename by whitespace or an equals (=) character.

The options can be specified multiple times. Their contents accumulate. The remappings will be processed in the order in which they occur on the command line, and if they come from a file, in the order in which they occur in the file. If a match is made, no further checking for that filename will be performed.

If the replacement filename is /dev/null or just NUL then the remapping will actually cause the input file to be ignored. This can be a convenient way to experiment with removing input files from a complicated build environment.

Note that this option is position dependent and only affects filenames that come after it on the command line. Thus:

ld foo.o --remap-inputs=foo.o=bar.o

Will have no effect, whereas:

ld --remap-inputs=foo.o=bar.o foo.o

Will rename the input file foo.o to bar.o.

Note - these options also affect files referenced by INPUT statements in linker scripts. But since linker scripts are processed after the entire command line is read, the position of the remap options on the command line is not significant.

If the verbose option is enabled then any mappings that match will be reported, although again the verbose option needs to be enabled on the command line before the remaped filenames appear.

If the -Map or --print-map options are enabled then the remapping list will be included in the map output.

-M
--print-map
Print a link map to the standard output. A link map provides information about the link, including the following:
  • Where object files are mapped into memory.
  • How common symbols are allocated.
  • All archive members included in the link, with a mention of the symbol which caused the archive member to be brought in.
  • The values assigned to symbols.

    Note - symbols whose values are computed by an expression which involves a reference to a previous value of the same symbol may not have correct result displayed in the link map. This is because the linker discards intermediate results and only retains the final value of an expression. Under such circumstances the linker will display the final value enclosed by square brackets. Thus for example a linker script containing:

    foo = 1
fo
o = foo * 4 foo = foo + 8

producirá la siguiente salida en el mapa de enlace si se utiliza la opción -M:

0x00000001                foo = 0x1
[0x0000000c]                foo = (foo * 0x4)
[0x0000000c]                foo = (foo + 0x8)

Consulte Expressions para obtener más información sobre expresiones en scripts de enlazador.

  • Cómo se fusionan las propiedades de GNU.

    Cuando el enlazador fusiona las secciones .note.gnu.property de entrada en una única sección .note.gnu.property de salida, algunas propiedades se eliminan o se actualizan. Estas acciones se informan en el mapa de enlace. Por ejemplo:

    Removed property 0xc0000002 to merge foo.o (0x1) and bar.o (not found)

    Esto indica que la propiedad 0xc0000002 se elimina de la salida al fusionar las propiedades en foo.o, cuyo valor de la propiedad 0xc0000002 es 0x1, y bar.o, que no tiene la propiedad 0xc0000002.

    Esto indica que el valor de la propiedad 0xc0010001 se actualiza a 0x1 en la salida al fusionar las propiedades en foo.o, cuya propiedad 0xc0010001 tiene el valor 0x1, y bar.o, cuya propiedad 0xc0010001 tiene el valor 0x1.

    -n
    --nmagic
    Desactiva la alineación de página de secciones y deshabilita el enlace contra bibliotecas compartidas. Si el formato de salida admite números mágicos de estilo Unix, marca la salida como "NMAGIC".

    Establece las secciones de texto y datos para que sean legibles y modificables. Además, no alinea por página el segmento de datos y deshabilita el enlace contra bibliotecas compartidas.     -o salida
    --output=salida
    Utiliza salida como el nombre para el programa producido por ld; si no se especifica esta opción, se utiliza por defecto el nombre a.out. El comando de script "OUTPUT" también puede especificar el nombre del archivo de salida.

    Nota: el enlazador eliminará el archivo de salida antes de empezar a escribir en él. Hará esto incluso si resulta que el enlace no se puede completar debido a errores.

    Nota: el enlazador verificará que el nombre del archivo de salida no coincida con el nombre de ninguno de los archivos de entrada, pero eso es todo. En particular, no se quejará si el archivo de salida puede sobrescribir un archivo fuente u otro archivo importante. Por lo tanto, en los sistemas de compilación, se recomienda usar la opción -o como la última opción en la línea de comandos del enlazador. Por ejemplo, considere:

    ld -o $(EXE) $(OBJS)
ld $(OBJS) -o $(EXE)

    Si la variable EXE no está definida por alguna razón, la primera versión del comando del enlazador podría terminar borrando uno de los archivos objeto (el primero en la lista OBJS), mientras que la segunda versión del comando del enlazador generará un mensaje de error y no borrará nada.

    --dependency-file=depfile
    Escribe un archivo de dependencia en depfile. Este archivo contiene una regla adecuada para "make" que describe el archivo de salida y todos los archivos de entrada que se leyeron para producirlo. La salida es similar a la salida del compilador con -M -MP. Tenga en cuenta que no hay una opción como el -MM del compilador, para excluir "archivos del sistema" (que no es un concepto bien especificado en el enlazador, a diferencia de los "archivos de encabezado del sistema" en el compilador). Por lo tanto, la salida de --dependency-file siempre es específica para el estado exacto de la instalación donde se produjo, y no debe copiarse en makefiles distribuidos sin una edición cuidadosa.
    -O nivel
    Si nivel es un valor numérico mayor que cero, ld optimiza la salida. Esto puede llevar significativamente más tiempo y, por lo tanto, probablemente solo debería habilitarse para el binario final. Por el momento, esta opción solo afecta la generación de bibliotecas compartidas ELF. Las versiones futuras del enlazador pueden hacer un mayor uso de esta opción. Además, actualmente no hay diferencia en el comportamiento del enlazador para diferentes valores distintos de cero de esta opción. Nuevamente, esto puede cambiar con las versiones futuras.
    -plugin nombre
    Involucra un plugin en el proceso de enlace. El parámetro nombre es el nombre de archivo absoluto del plugin. Generalmente, este parámetro es agregado automáticamente por el compilador, cuando se usa la optimización en tiempo de enlace, pero los usuarios también pueden agregar sus propios plugins si lo desean.

    Tenga en cuenta que la ubicación de los plugins originados por el compilador es diferente del lugar donde los programas ar, nm y ranlib buscan sus plugins. Para que esos comandos utilicen un plugin basado en el compilador, primero debe copiarse en el directorio ${libdir}/bfd-plugins. Todos los plugins de enlazador basados en gcc son retrocompatibles, por lo que es suficiente con copiar el más nuevo.

    --push-state
    --push-state permite preservar el estado actual de las banderas que gobiernan el manejo de archivos de entrada para que puedan ser restauradas con una opción --pop-state correspondiente.

    Las opciones cubiertas son: -Bdynamic, -Bstatic, -dn, -dy, -call_shared, -non_shared, -static, -N, -n, --whole-archive, --no-whole-archive, -r, -Ur, --copy-dt-needed-entries, --no-copy-dt-needed-entries, --as-needed, --no-as-needed, y -a.

    Un objetivo para esta opción son las especificaciones para pkg-config. Cuando se usa con la opción --libs, se listan todas las bibliotecas posiblemente necesarias y luego se enlazan con todas ellas todo el tiempo. Es mejor devolver algo como lo siguiente:

    -Wl,--push-state,--as-needed -libone -libtwo -Wl,--pop-state
    --pop-state
    Anula el efecto de --push-state, restaura los valores anteriores de las banderas que rigen el manejo de archivos de entrada.
    -q
    --emit-relocs
    Deja las secciones de reubicación y su contenido en ejecutables completamente enlazados. Las herramientas de análisis y optimización post-enlace pueden necesitar esta información para realizar modificaciones correctas de los ejecutables. Esto resulta en ejecutables más grandes.

    Esta opción actualmente solo es compatible con plataformas ELF.

    --force-dynamic
    Forza que el archivo de salida tenga secciones dinámicas. Esta opción es específica para destinos VxWorks.
    -r
    --relocatable
    Genera salida reubicable, es decir, genera un archivo de salida que a su vez puede servir como entrada para ld. Esto a menudo se llama *enlazado parcial*. Como efecto secundario, en entornos que admiten números mágicos estándar de Unix, esta opción también establece el número mágico del archivo de salida en "OMAGIC". Si esta opción no se especifica, se produce un archivo absoluto. Al enlazar programas C++, esta opción *no* resolverá las referencias a los constructores; para hacerlo, use -Ur.

    Cuando un archivo de entrada no tiene el mismo formato que el archivo de salida, el enlazado parcial solo se admite si ese archivo de entrada no contiene ninguna reubicación. Diferentes formatos de salida pueden tener restricciones adicionales; por ejemplo, algunos formatos basados en "a.out" no admiten el enlazado parcial con archivos de entrada en otros formatos en absoluto.

    Cuando la salida reubicable contiene contenido que requiere optimización en tiempo de enlace (LTO) y contenido que no requiere LTO, se creará una sección .gnu_object_only para contener un archivo objeto reubicable, como si se aplicara -r a todas las entradas reubicables que no requieren LTO. Al procesar una entrada reubicable con una sección .gnu_object_only, el enlazador extraerá la sección .gnu_object_only como una entrada separada.

    Tenga en cuenta que dado que -r agrupa algunas secciones de diferentes archivos de entrada, puede haber impactos negativos en el tamaño del código y la localidad en el ejecutable final o la biblioteca compartida.

    Esta opción hace lo mismo que -i.

    -R nombrearchivo
    --just-symbols=nombrearchivo
    Lee los nombres de los símbolos y sus direcciones de nombrearchivo, pero no los reubica ni
    inclúyelo en la salida. Esto permite que tu archivo de salida haga referencia simbólicamente a ubicaciones absolutas de memoria definidas en otros programas. Puedes usar esta opción más de una vez.

    Por compatibilidad con otros enlazadores ELF, si la opción -R va seguida de un nombre de directorio, en lugar de un nombre de archivo, se trata como la opción -rpath.

    --rosegment
    --no-rosegment
    Intenta asegurar que solo se cree un único segmento de solo lectura, no de código. Solo útil cuando se usa junto con la opción -z separate-code. Los binarios resultantes deberían ser más pequeños que si se usa -z separate-code por sí sola. Sin esta opción, o si se especifica --no-rosegment, la opción -z separate-code creará dos segmentos de solo lectura, uno antes del segmento de código y otro después.

    Los nombres de las opciones son engañosos, pero se han elegido para que el enlazador sea compatible con los enlazadores LLD y GOLD.

    Estas opciones solo son compatibles con destinos ELF.

La salida de -t es útil para generar una lista de todos los archivos objeto y scripts involucrados en el enlazado, por ejemplo, al empaquetar archivos para un informe de error del enlazador.
    -T scriptfile
    --script=scriptfile
    Usa scriptfile como script del enlazador. Este script reemplaza el script del enlazador predeterminado de ld (en lugar de agregarse a él), a menos que el script contenga "INSERT", por lo que commandfile debe especificar todo lo necesario para describir el archivo de salida.

    -dT scriptfile
    --default-script=scriptfile

Esto permite que las opciones colocadas después de la opción --default-script en la línea de comandos afecten al comportamiento del script del enlazador, lo que puede ser importante cuando la línea de comandos del enlazador no puede ser controlada directamente por el usuario. (por ejemplo, porque la línea de comandos está siendo construida por otra herramienta, como gcc).

    -u symbol
    --undefined=symbol
    Fuerza que symbol se ingrese en el archivo de salida como un símbolo indefinido. Hacer esto puede, por ejemplo, activar el enlazado de módulos adicionales de las bibliotecas estándar. -u puede repetirse con diferentes argumentos de opción para ingresar símbolos indefinidos adicionales.     --require-defined=symbol
    Requiere que symbol esté definido en el archivo de salida. Esta opción es igual a la opción --undefined excepto que si symbol no está definido en el archivo de salida, el enlazador emitirá un error y saldrá. El mismo efecto se puede lograr en un script de enlazador usando "EXTERN", "ASSERT" y "DEFINED" juntos. Esta opción se puede usar varias veces para requerir símbolos adicionales.
    -Ur
    Para programas que no utilizan constructores o destructores, o para sistemas basados en ELF, esta opción es equivalente a -r: genera salida relocalizable, es decir, un archivo de salida que a su vez puede servir como entrada para ld. Sin embargo, para otros binarios, la opción -Ur es similar a -r pero también resuelve referencias a constructores y destructores.

    Para aquellos sistemas donde -r y -Ur se comportan de manera diferente, no funciona usar -Ur en archivos que fueron enlazados con -Ur; una vez que la tabla de constructores ha sido construida, no se puede agregar. Usa -Ur solo para el último enlace parcial, y -r para los otros.

    --orphan-handling=MODE
    Controla cómo se manejan las secciones huérfanas. Una sección huérfana es aquella que no se menciona específicamente en un script de enlazador.

    MODE puede tener cualquiera de los siguientes valores:

    "place"
    Las secciones huérfanas se colocan en una sección de salida adecuada siguiendo la estrategia descrita en Secciones Huérfanas. La opción --unique también afecta cómo se colocan las secciones.
    "discard"
    Todas las secciones huérfanas se descartan, colocándolas en la sección /DISCARD/.
    "warn"
    El enlazador colocará la sección huérfana como para "place" y también emitirá una advertencia.
    "error"
    El enlazador saldrá con un error si se encuentra alguna sección huérfana.

    El valor predeterminado si no se proporciona --orphan-handling es "place".

    --unique[=SECTION]
    Crea una sección de salida separada para cada sección de entrada que coincida con SECTION, o si el argumento comodín opcional SECTION falta, para cada sección de entrada huérfana. Una sección huérfana es aquella que no se menciona específicamente en un script de enlazador. Puedes usar esta opción varias veces en la línea de comandos; evita la fusión normal de secciones de entrada con el mismo nombre, anulando las asignaciones de secciones de salida en un script de enlazador.

    --version
    -V

    -X

    -z keyword
    Las palabras clave reconocidas son:

    call-nop=suffix-nop
    call-nop=prefix-byte

    -( archivos -)
    --start-group archivos --end-group
    Los archivos deben ser una lista de archivos de biblioteca. Pueden ser nombres de archivo explícitos o opciones -l.

    Las bibliotecas especificadas se buscan repetidamente hasta que no se creen nuevas referencias indefinidas. Normalmente, una biblioteca se busca solo una vez en el orden en que se especifica en la línea de comandos. Si un símbolo en esa biblioteca es necesario para resolver un símbolo indefinido al que se hace referencia desde un objeto en una biblioteca que aparece más tarde en la línea de comandos, el enlazador no podría resolver esa referencia. Agrupando las bibliotecas, todas ellas se buscarán repetidamente hasta que todas las referencias posibles se resuelvan.

    Usar esta opción tiene un coste de rendimiento significativo. Es mejor usarla solo cuando haya referencias circulares inevitables entre dos o más bibliotecas.

    --as-needed
    --no-as-needed
    Esta opción afecta a las etiquetas DT_NEEDED de ELF para bibliotecas dinámicas mencionadas en la línea de comandos después de la opción --as-needed. Normalmente el enlazador añadirá una etiqueta DT_NEEDED por cada biblioteca dinámica mencionada en la línea de comandos, sin importar si la biblioteca es realmente necesaria o no. --as-needed hace que una etiqueta DT_NEEDED solo se emita para una biblioteca que *en ese punto del enlace* satisface una referencia a un símbolo indefinido no débil de un archivo objeto regular o, si la biblioteca no se encuentra en las listas DT_NEEDED de otras bibliotecas necesarias, una referencia a un símbolo indefinido no débil de otra biblioteca dinámica necesaria. Esto es similar a las reglas para la extracción de archivos objeto de las bibliotecas. --no-as-needed restaura el comportamiento predeterminado.

    Si un archivo de salida completamente enlazado y construido con éxito no tiene el sufijo ".exe" o ".dll", esta opción fuerza al enlazador a copiar el archivo de salida a uno con el mismo nombre y el sufijo ".exe". Esta opción es útil al usar makefiles de Unix sin modificar en un host Microsoft Windows, ya que algunas versiones de Windows no ejecutarán una imagen a menos que termine con un sufijo ".exe".

    --gc-sections
    --no-gc-sections
    Habilita la recolección de basura de secciones de entrada no utilizadas. Se ignora en objetivos que no soportan esta opción. El comportamiento por defecto (de no realizar esta recolección de basura) puede ser restaurado especificando --no-gc-sections en la línea de comandos. Tenga en cuenta que la recolección de basura para objetivos de formato COFF y PE está soportada, pero la implementación se considera actualmente experimental.

    --gc-sections decide qué secciones de entrada se utilizan examinando símbolos y reubicaciones. Se conservará la sección que contiene el símbolo de entrada y todas las secciones que contienen símbolos indefinidos en la línea de comandos, así como las secciones que contienen símbolos referenciados por objetos dinámicos. Tenga en cuenta que al construir bibliotecas compartidas, el enlazador debe asumir que todo símbolo visible es referenciado. Una vez que este conjunto inicial de secciones ha sido determinado, el enlazador marca recursivamente como utilizadas cualquier sección referenciada por sus reubicaciones. Vea --entry, --undefined, y --gc-keep-exported.

    Esta opción puede configurarse al realizar un enlace parcial (habilitado con la opción -r). En este caso, la raíz de los símbolos a conservar debe especificarse explícitamente ya sea por una de las opciones --entry, --undefined, o --gc-keep-exported, o por un comando "ENTRY" en el script del enlazador.

    Como extensión de GNU, las secciones de entrada ELF marcadas con el flag "SHF_GNU_RETAIN" no serán recolectadas por la basura.

    --print-gc-sections
    --no-print-gc-sections
    Lista todas las secciones eliminadas por la recolección de basura. La lista se imprime en stderr. Esta opción solo es efectiva si la recolección de basura ha sido habilitada a través de la opción --gc-sections). El comportamiento por defecto (de no listar las secciones que se eliminan) puede ser restaurado especificando --no-print-gc-sections en la línea de comandos.
    --gc-keep-exported
    Cuando --gc-sections está habilitado, esta opción previene la recolección de basura de secciones de entrada no utilizadas que contienen símbolos globales con visibilidad por defecto o protegida. Esta opción está destinada a ser utilizada para ejecutables donde las secciones no referenciadas de otro modo serían recolectadas por la basura independientemente de la visibilidad externa de los símbolos contenidos. Tenga en cuenta que esta opción no tiene efecto al enlazar objetos compartidos, ya que es el comportamiento por defecto. Esta opción solo es compatible con objetivos de formato ELF.
    --print-output-format
    Imprime el nombre del formato de salida por defecto (quizás influenciado por otras opciones de línea de comandos). Esta es la cadena que aparecería en un comando de script del enlazador "OUTPUT_FORMAT".
    --print-memory-usage
    Imprime el tamaño usado, tamaño total y tamaño usado de las regiones de memoria creadas con el
    command **MEMORY**. Esto es útil en objetivos integrados para tener una vista rápida de la cantidad de memoria libre. El formato de la salida tiene un titular y una línea por región. Es legible por humanos y fácilmente analizable por herramientas. Aquí hay un ejemplo de una salida: 
    Región de memoria    Tamaño usado    Tamaño de región   % Usado
             ROM:        256 KB         1 MB     25.00%
             RAM:          32 B         2 GB      0.00%

    Nota: si desea obtener información sobre el uso de memoria del enlazador, la opción --stats lo hará.

    --help
    Imprime un resumen de las opciones de la línea de comandos en la salida estándar y sale.
    --target-help
    Imprime un resumen de todas las opciones específicas del objetivo en la salida estándar y sale.
    -Map=archivo-mapa
    Imprime un mapa de enlace en el archivo archivo-mapa. Consulte la descripción de la opción -M, anterior. Si archivo-mapa es solo el carácter "-", el mapa se escribirá en stdout.

    Especificar un directorio como archivo-mapa hace que el mapa del enlazador se escriba como un archivo dentro del directorio. Normalmente, el nombre del archivo dentro del directorio se calcula como el nombre base del archivo de salida con ".map" añadido. Sin embargo, si se utiliza el carácter especial "%", este será reemplazado por la ruta completa del archivo de salida. Además, si hay algún carácter después del símbolo %, entonces ".map" ya no se añadirá.

    -o foo.exe -Map=bar                  [Crea ./bar]
-o ../dir/foo.exe -Map=bar           [Crea ./bar]
-o foo.exe -Map=../dir               [Crea ../dir/foo.exe.map]
-o ../dir2/foo.exe -Map=../dir       [Crea ../dir/foo.exe.map]
-o foo.exe -Map=%                    [Crea ./foo.exe.map]
-o ../dir/foo.exe -Map=%             [Crea ../dir/foo.exe.map]
-o foo.exe -Map=%.bar                [Crea ./foo.exe.bar]
-o ../dir/foo.exe -Map=%.bar         [Crea ../dir/foo.exe.bar]
-o ../dir2/foo.exe -Map=../dir/%     [Crea ../dir/../dir2/foo.exe.map]
-o ../dir2/foo.exe -Map=../dir/%.bar [Crea ../dir/../dir2/foo.exe.bar]

    Es un error especificar más de un carácter "%".

    Si el archivo de mapa ya existe, será sobrescrito por esta operación.

    --no-keep-memory
    Normalmente, ld optimiza la velocidad en lugar del uso de memoria almacenando en caché las tablas de símbolos de los archivos de entrada en memoria. Esta opción le indica a ld que optimice en su lugar el uso de memoria, volviendo a leer las tablas de símbolos según sea necesario. Esto puede ser necesario si ld se queda sin espacio de memoria al enlazar un ejecutable grande.
    --no-undefined
    -z defs
    Informa de referencias de símbolos no resueltas de archivos objeto regulares. Esto se hace incluso si el enlazador está creando una biblioteca compartida no simbólica. El interruptor --[no-]allow-shlib-undefined controla el comportamiento para informar de referencias no resueltas encontradas en bibliotecas compartidas que se están enlazando.

    Los efectos de esta opción se pueden revertir usando "-z undefs".

    --allow-multiple-definition
    -z muldefs
    Normalmente, cuando un símbolo se define varias veces, el enlazador informará de un error fatal. Estas opciones permiten definiciones múltiples y se utilizará la primera definición.
    --allow-shlib-undefined
    --no-allow-shlib-undefined
    Permite o prohíbe símbolos indefinidos en bibliotecas compartidas. Este interruptor es similar a --no-undefined excepto que determina el comportamiento cuando los símbolos indefinidos están en una biblioteca compartida en lugar de un archivo objeto regular. No afecta a cómo se manejan los símbolos indefinidos en archivos objeto regulares.

    El comportamiento predeterminado es informar de errores para cualquier símbolo indefinido referenciado en bibliotecas compartidas si el enlazador se está utilizando para crear un ejecutable, pero permitirlos si el enlazador se está utilizando para crear una biblioteca compartida.

    Las razones para permitir referencias de símbolos indefinidos en bibliotecas compartidas especificadas en el momento del enlace son que:

    • Una biblioteca compartida especificada en el momento del enlace puede no ser la misma que la disponible en el momento de la carga, por lo que el símbolo podría ser resoluble en el momento de la carga.
    • Hay algunos sistemas operativos, por ejemplo BeOS y HPPA, donde los símbolos indefinidos en bibliotecas compartidas son normales.

      El kernel de BeOS, por ejemplo, aplica parches a las bibliotecas compartidas en el momento de la carga para seleccionar la función que sea más apropiada para la arquitectura actual. Esto se usa, por ejemplo, para seleccionar dinámicamente una función memset apropiada.

    --error-handling-script=nombre-script
    Si se proporciona esta opción, el enlazador invocará a nombre-script cada vez que se encuentre un error. Actualmente, sin embargo, solo se admiten dos tipos de error: símbolos faltantes y bibliotecas faltantes. Se pasarán dos argumentos al script: la palabra clave "undefined-symbol" o "missing-lib" y el nombre del símbolo indefinido o la biblioteca faltante. La intención es que el script proporcione sugerencias al usuario sobre dónde se pueden encontrar el símbolo o la biblioteca. Después de que el script haya terminado, se mostrará el mensaje de error normal del enlazador.

    La disponibilidad de esta opción está controlada por un interruptor de tiempo de configuración, por lo que puede que no esté presente en implementaciones específicas.

    --no-undefined-version
    Normalmente, cuando un símbolo tiene una versión indefinida, el enlazador lo ignora. Esta opción prohíbe los símbolos con versión indefinida y, en su lugar, se emitirá un error fatal.
    --default-symver
    Crea y utiliza una versión de símbolo predeterminada (el soname) para los símbolos exportados sin versión.
    --default-imported-symver
    Crea y utiliza una versión de símbolo predeterminada (el soname) para los símbolos importados sin versión.
    --no-warn-mismatch
    Normalmente, ld dará un error si se intenta enlazar archivos de entrada que no coinciden por alguna razón, tal vez porque han sido compilados para diferentes procesadores o para diferentes endianidades. Esta opción le indica a ld que permita silenciosamente tales posibles errores. Esta opción solo debe usarse con cuidado, en casos en los que haya tomado alguna acción especial que garantice que los errores del enlazador son inapropiados.
    --no-warn-search-mismatch
    Normalmente, ld advertirá si encuentra una biblioteca incompatible durante la búsqueda de una biblioteca. Esta opción silencia la advertencia.
    --no-whole-archive
    Desactiva el efecto de la opción --whole-archive para los archivos de archivo subsiguientes.
    --noinhibit-exec
    Conserva el archivo de salida ejecutable siempre que aún sea utilizable. Normalmente, el enlazador no producirá un archivo de salida si encuentra errores durante el proceso de enlace; sale sin escribir un archivo de salida cuando emite algún error.
    -nostdlib
    Solo busca en los directorios de bibliotecas especificados explícitamente en la línea de comandos. Se ignoran los directorios de bibliotecas especificados en los scripts del enlazador (incluidos los scripts del enlazador especificados en la línea de comandos).
    --oformat=formato-salida
    ld puede configurarse para admitir más de un tipo de archivo objeto. Si su ld está configurado de esta manera, puede usar la opción --oformat para especificar el formato binario para el archivo objeto de salida. Incluso cuando ld está configurado para admitir formatos de objeto alternativos, normalmente no necesita especificarlo, ya que ld debería estar configurado para producir como formato de salida predeterminado el formato más común en cada máquina. formato-salida es una cadena de texto, el nombre de un formato particular compatible con las bibliotecas BFD. (Puede listar los formatos binarios disponibles con objdump -i.) El comando de script "OUTPUT_FORMAT" también puede especificar el formato de salida, pero esta opción lo anula.
    --out-implib archivo
    Crea una biblioteca de importación en archivo correspondiente al ejecutable que el enlazador está generando (por ejemplo, una DLL o un programa ELF). Esta biblioteca de importación (que debería llamarse "*.dll.a" o "*.a" para DLLs) puede usarse para enlazar clientes contra el ejecutable generado; este comportamiento hace posible omitir un paso separado de creación de bibliotecas de importación (por ejemplo, "dlltool" para DLLs). Esta opción solo está disponible para los puertos del enlazador dirigidos a i386 PE y ELF.
    -pie
    --pic-executable
    Crea un ejecutable independiente de la posición. Esto actualmente solo se admite en plataformas ELF. Los ejecutables independientes de la posición son relocalizados por el enlazador dinámico a la dirección virtual que el SO elija para ellos, la cual puede variar entre invocaciones. Se marcan como ET_DYN en la cabecera del archivo ELF, pero difieren de las bibliotecas compartidas en varios aspectos. En particular, los símbolos definidos en un PIE, por defecto, no pueden ser anulados por otro objeto como sí pueden serlo en una biblioteca compartida.
    -no-pie
    Crea un ejecutable dependiente de la posición. Este es el valor predeterminado.
    -qmagic
    Esta opción se ignora por compatibilidad con Linux.
    -Qy
    Esta opción se ignora por compatibilidad con SVR4.
    --relax
    --no-relax
    Una opción con efectos dependientes de la máquina. Esta opción solo se admite en unas pocas
    objetivos.

    En algunas plataformas, la opción --relax realiza optimizaciones globales específicas del objetivo que se vuelven posibles cuando el enlazador resuelve la direccionamiento en el programa, como relajar modos de dirección, sintetizar nuevas instrucciones, seleccionar versiones más cortas de las instrucciones actuales y combinar valores constantes.

    En algunas plataformas, estas optimizaciones globales en tiempo de enlace pueden imposibilitar la depuración simbólica del ejecutable resultante. Se sabe que este es el caso para la familia de procesadores Matsushita MN10200 y MN10300.

    En plataformas donde la característica es compatible, la opción --no-relax la deshabilitará.

    En plataformas donde la característica no es compatible, se aceptan tanto --relax como --no-relax, pero se ignoran.

    --retain-symbols-file=nombrearchivo
    Conservar solo los símbolos listados en el archivo nombrearchivo, descartando todos los demás. nombrearchivo es simplemente un archivo plano, con un nombre de símbolo por línea. Esta opción es especialmente útil en entornos (como VxWorks) donde se acumula gradualmente una gran tabla de símbolos global, para conservar la memoria en tiempo de ejecución.

    --retain-symbols-file no descarta símbolos indefinidos ni símbolos necesarios para las reubicaciones.

    Solo puede especificar --retain-symbols-file una vez en la línea de comandos. Anula -s y -S.

    -rpath=dir
    Agrega un directorio a la ruta de búsqueda de bibliotecas en tiempo de ejecución. Esto se utiliza al enlazar un ejecutable ELF con objetos compartidos. Todos los argumentos -rpath se concatenan y se pasan al enlazador en tiempo de ejecución, que los utiliza para localizar objetos compartidos en tiempo de ejecución.

    La opción -rpath también se utiliza al localizar objetos compartidos que son requeridos por objetos compartidos incluidos explícitamente en el enlace; vea la descripción de la opción -rpath-link. La búsqueda de -rpath de esta manera solo es compatible con enlazadores nativos y enlazadores cruzados que se han configurado con la opción --with-sysroot.

    Si -rpath no se utiliza al enlazar un ejecutable ELF, se utilizará el contenido de la variable de entorno "LD_RUN_PATH" si está definido.

    La opción -rpath también se puede usar en SunOS. Por defecto, en SunOS, el enlazador formará una ruta de búsqueda en tiempo de ejecución a partir de todas las opciones -L que se le den. Si se utiliza una opción -rpath, la ruta de búsqueda en tiempo de ejecución se formará exclusivamente utilizando las opciones -rpath, ignorando las opciones -L. Esto puede ser útil al usar gcc, que agrega muchas opciones -L que pueden estar en sistemas de archivos montados NFS.

    Por compatibilidad con otros enlazadores ELF, si la opción -R va seguida de un nombre de directorio, en lugar de un nombre de archivo, se trata como la opción -rpath.

    -rpath-link=dir
    Al usar ELF o SunOS, una biblioteca compartida puede requerir otra. Esto ocurre cuando un enlace de "ld -shared" incluye una biblioteca compartida como uno de los archivos de entrada.

    Cuando el enlazador encuentra una dependencia de este tipo al realizar un enlace no compartido y no relocable, intentará automáticamente localizar la biblioteca compartida requerida e incluirla en el enlace, si no está incluida explícitamente. En tal caso, se buscan varios directorios como se describe a continuación. La opción -rpath-link especifica el primer conjunto de directorios a buscar. Esta opción puede especificar una secuencia de nombres de directorio, ya sea proporcionando una lista de nombres separados por dos puntos, o apareciendo varias veces.

    Los tokens $ORIGIN y $LIB pueden aparecer en estos directorios de búsqueda. Se reemplazarán por la ruta completa al directorio que contiene el programa u objeto compartido en el caso de $ORIGIN y ya sea lib - para binarios de 32 bits - o lib64 - para binarios de 64 bits - en el caso de $LIB.

    La forma alternativa de estos tokens - ${ORIGIN} y ${LIB} - también se puede usar. El token $PLATFORM no es compatible.

    La opción --rpath-link debe usarse con precaución, ya que anula la ruta de búsqueda que puede haber sido compilada directamente en una biblioteca compartida. En tal caso, es posible utilizar involuntariamente una ruta de búsqueda diferente a la que habría utilizado el enlazador en tiempo de ejecución.

    Cuando se requieren bibliotecas compartidas adicionales, el enlazador buscará directorios en el orden que se enumera a continuación para encontrarlas. Tenga en cuenta, sin embargo, que esto solo se aplica a bibliotecas adicionales necesarias para satisfacer bibliotecas compartidas ya incluidas. No se aplica a bibliotecas que se incluyen a través de la opción de línea de comandos -l. Las búsquedas de bibliotecas -l solo se realizan en directorios especificados por la opción -L.

    1.
    Cualquier directorio especificado por las opciones -rpath-link.
    2.
    Cualquier directorio especificado por las opciones -rpath. La diferencia entre -rpath y -rpath-link es que los directorios especificados por las opciones -rpath se incluyen en el ejecutable y se utilizan en tiempo de ejecución, mientras que la opción -rpath-link solo es efectiva en tiempo de enlace. La búsqueda de -rpath de esta manera solo es compatible con enlazadores nativos y enlazadores cruzados que se han configurado con la opción --with-sysroot.
    3.
    En un sistema ELF, para enlazadores nativos, si no se utilizaron las opciones -rpath y -rpath-link, busque el contenido de la variable de entorno "LD_RUN_PATH".
    4.
    En SunOS, si no se utilizó la opción -rpath, busque cualquier directorio especificado usando las opciones -L.
    5.
    Para un enlazador nativo, busque el contenido de la variable de entorno "LD_LIBRARY_PATH".
    6.
    Para un enlazador ELF nativo, se buscan los directorios en "DT_RUNPATH" o "DT_RPATH" de una biblioteca compartida para las bibliotecas compartidas que necesita. Las entradas "DT_RPATH" se ignoran si existen entradas "DT_RUNPATH".
    7.
    Para un enlazador de un sistema Linux, si existe el archivo /etc/ld.so.conf, la lista de directorios que se encuentran en ese archivo. Nota: la ruta a este archivo se antepone al valor "sysroot", si está definido, y luego cualquier cadena "prefix" si el enlazador se configuró con la opción --prefix=<ruta>.
    8.
    Para un enlazador nativo en un sistema FreeBSD, cualquier directorio especificado por la macro "_PATH_ELF_HINTS" definida en el archivo de encabezado elf-hints.h.
    9.
    Cualquier directorio especificado por un comando "SEARCH_DIR" en un script de enlazador dado en la línea de comandos, incluidos los scripts especificados por -T (pero no -dT).
    10.
    Los directorios predeterminados, normalmente /lib y /usr/lib.
    11.
    Cualquier directorio especificado por un plugin LDPT_SET_EXTRA_LIBRARY_PATH.
    12.
    Cualquier directorio especificado por un comando "SEARCH_DIR" en un script de enlazador predeterminado.

    Sin embargo, tenga en cuenta que en los sistemas basados en Linux existe una advertencia adicional: Si la opción --as-needed está activa y se localiza una biblioteca compartida que normalmente satisfaría la búsqueda y esta biblioteca no tiene una etiqueta DT_NEEDED para libc.so y existe una biblioteca compartida más adelante en el conjunto de directorios de búsqueda que también satisface la búsqueda y esta segunda biblioteca compartida tiene una etiqueta DT_NEEDED para libc.so entonces se seleccionará la segunda biblioteca en lugar de la primera.

    Si no se encuentra la biblioteca compartida requerida, el enlazador emitirá una advertencia y continuará con el enlace.

    --section-ordering-file=script
    Esta opción se utiliza para aumentar el script de enlazador actual con un mapeo adicional de secciones de entrada a secciones de salida. Este archivo debe usar la misma sintaxis para "SECTIONS" que se usa en los scripts de enlazador normales, pero no debe hacer nada más que colocar secciones de entrada en secciones de salida. @pxref{SECTIONS}

    Una segunda restricción en el script de ordenación de secciones es que solo puede hacer referencia a secciones de salida que ya están definidas por el script de enlazador que se está utilizando actualmente. (Es decir, el script de enlazador predeterminado o un script especificado en la línea de comandos). Sin embargo, el beneficio del script de ordenación de secciones es que las secciones de entrada se mapean al inicio de las secciones de salida, para que puedan garantizar la ordenación de las secciones dentro de la sección de salida. Por ejemplo, imagine que el script de enlazador predeterminado se ve así:

    SECTIONS {
  .text : { *(.text.hot) ; *(.text .text.*) }
  .data : { *(.data.big) ; *(.data .data.*) }
  }

    Luego, si se utiliza un archivo de ordenación de secciones como este:

    .text : { *(.text.first) ; *(.text.z*) }
.data : { foo.o(.data.first) ; *(.data.small) }

    Esto sería equivalente a un script de enlazador como este:

    SECTIONS {
  .text : { *(.text.first) ; *(.text.z*) ; *(.text.hot) ; *(.text .text.*) }
  .data : { foo.o(.data.first) ; *(.data.small) ; *(.data.big) ; *(.data .data.*) }
  }

    La ventaja del archivo de ordenación de secciones es que se puede usar para ordenar aquellas secciones que son importantes para el usuario sin tener que preocuparse por ninguna otra sección, regiones de memoria o cualquier otra cosa.

    -shared
    -Bshareable
    Crea una biblioteca compartida. Esto actualmente solo es compatible en plataformas ELF, XCOFF y SunOS. En SunOS, el enlazador creará automáticamente una biblioteca compartida si la opción -e no se utiliza y hay símbolos indefinidos en el enlace.
    --sort-common
    --sort-common=ascending
    --sort-common=descending
    Esta opción le dice a ld que ordene los elementos comunes.
    mon símbolos por alineación en orden ascendente o descendente cuando los coloca en las secciones de salida apropiadas. Las alineaciones de símbolos consideradas son de dieciséis bytes o más, ocho bytes, cuatro bytes, dos bytes y un byte. Esto es para evitar huecos entre símbolos debido a restricciones de alineación. Si no se especifica ningún orden de clasificación, se asume el orden descendente.
    --sort-section=nombre
    Esta opción aplicará "SORT_BY_NAME" a todos los patrones de sección comodín en el script del enlazador.
    --sort-section=alineación
    Esta opción aplicará "SORT_BY_ALIGNMENT" a todos los patrones de sección comodín en el script del enlazador.
    --spare-dynamic-tags=contador
    Esta opción especifica el número de ranuras vacías que se dejarán en la sección .dynamic de los objetos compartidos ELF. Las ranuras vacías pueden ser necesarias para herramientas de postprocesamiento, como el pre-enlazador. El valor predeterminado es 5.
    --split-by-file[=tamaño]
    Similar a --split-by-reloc pero crea una nueva sección de salida para cada archivo de entrada cuando se alcanza el tamaño. El tamaño por defecto es 1 si no se especifica.
    --split-by-reloc[=contador]
    Intenta crear secciones adicionales en el archivo de salida de modo que ninguna sección de salida individual en el archivo contenga más de contador reubicaciones. Esto es útil al generar archivos reubicables enormes para descargar en ciertos kernels de tiempo real con el formato de archivo objeto COFF; ya que COFF no puede representar más de 65535 reubicaciones en una sola sección. Tenga en cuenta que esto fallará con formatos de archivo objeto que no admiten secciones arbitrarias. El enlazador no dividirá las secciones de entrada individuales para su redistribución, por lo que si una sección de entrada contiene más de contador reubicaciones, una sección de salida contendrá esa cantidad de reubicaciones. El contador por defecto es 32768.
    --stats[=nombre_archivo]
    Calcula y muestra estadísticas sobre la operación del enlazador, como el tiempo de ejecución y el uso de memoria.

    Si no se proporciona el argumento opcional nombre_archivo, solo se informa información básica y se envía al flujo de salida de error estándar. Si se proporciona el argumento nombre_archivo, se escribe información extendida en el archivo con nombre. Si nombre_archivo se establece solo en el símbolo -, entonces la información extendida se envía al flujo de salida estándar. Si nombre_archivo comienza con +, el archivo se abre en modo de añadir en lugar de sobrescribir.

    Si se ha habilitado la opción -Map, la información también se registra en el archivo de mapa. Nota: si tanto la opción --stats como la opción -Map han recibido argumentos nombre_archivo y coinciden, la información solo se escribirá una vez, no dos.

    Si la variable de entorno "LD_STATS" está definida, esto se comporta como la opción --stats. Si el valor de la variable es una cadena, se utilizará como nombre de un archivo en el que se debe registrar la información. De lo contrario, la información se enviará al flujo de salida estándar. El uso de la variable de entorno permite registrar estadísticas sin tener que modificar la línea de comandos del enlazador. Nota: si se utilizan tanto la variable de entorno como la opción --stats, la opción --stats tiene prioridad.

    La información extendida informada incluye el tiempo de CPU utilizado y, si la llamada a la biblioteca del sistema getrusage() está disponible, se registra el uso de memoria. Esta información se informa para partes individuales del proceso de enlazado, que se denominan fases. Además, la información también se informa para una fase especial llamada ALL, que cubre todo el proceso de enlazado. Tenga en cuenta que las fases individuales pueden contener o superponerse con otras, por lo que no se debe asumir que los recursos generales utilizados por el enlazador son la suma de los recursos utilizados por las fases individuales.

    Además, cuando se informa información extendida, también se incluyen la versión del enlazador, los argumentos de la línea de comandos y la hora de inicio del enlazador. Esto facilita el manejo de la situación en la que un sistema de compilación invoca múltiples enlazados y la identificación exacta de los argumentos que fueron responsables de producir las estadísticas que se informan.

    --warn-common
    Advierte cuando un símbolo común se combina con otro símbolo común o con una definición de símbolo. Los enlazadores de Unix permiten esta práctica algo descuidada, pero los enlazadores de otros sistemas operativos no lo hacen. Esta opción te permite encontrar problemas potenciales al combinar símbolos globales. Desafortunadamente, algunas bibliotecas C usan esta práctica, por lo que puedes recibir algunas advertencias sobre símbolos en las bibliotecas así como en tus programas.

    Hay tres tipos de símbolos globales, ilustrados aquí con ejemplos en C:

    int i = 1;
    Una definición, que va en la sección de datos inicializados del archivo de salida.
    extern int i;
    Una referencia indefinida, que no asigna espacio. Debe haber una definición o un símbolo común para la variable en algún lugar.
    int i;
    Un símbolo común. Si solo hay (uno o más) símbolos comunes para una variable, va en el área de datos no inicializados del archivo de salida. El enlazador fusiona múltiples símbolos comunes para la misma variable en un solo símbolo. Si son de diferentes tamaños, elige el tamaño más grande. El enlazador convierte un símbolo común en una declaración, si hay una definición de la misma variable.

    La opción --warn-common puede producir cinco tipos de advertencias. Cada advertencia consiste en un par de líneas: la primera describe el símbolo recién encontrado, y la segunda describe el símbolo anterior encontrado con el mismo nombre. Uno o ambos de los dos símbolos será un símbolo común.

    1.
    Convirtiendo un símbolo común en una referencia, porque ya existe una definición para el símbolo. 
    <archivo>(<sección>): advertencia: común de `<símbolo>'
   sobrescrito por definición
<archivo>(<sección>): advertencia: definido aquí
    2.
    Convirtiendo un símbolo común en una referencia, porque se encuentra una definición posterior para el símbolo. Esto es lo mismo que el caso anterior, excepto que los símbolos se encuentran en un orden diferente. 
    <archivo>(<sección>): advertencia: definición de `<símbolo>'
   sobrescribiendo común
<archivo>(<sección>): advertencia: común está aquí
    3.
    Fusionando un símbolo común con un símbolo común anterior del mismo tamaño. 
    <archivo>(<sección>): advertencia: común múltiple
   de `<símbolo>'
<archivo>(<sección>): advertencia: común anterior está aquí
    4.
    Fusionando un símbolo común con un símbolo común anterior más grande. 
    <archivo>(<sección>): advertencia: común de `<símbolo>'
   sobrescrito por común más grande
<archivo>(<sección>): advertencia: común más grande está aquí
    5.
    Fusionando un símbolo común con un símbolo común anterior más pequeño. Esto es lo mismo que el caso anterior, excepto que los símbolos se encuentran en un orden diferente. 
    <archivo>(<sección>): advertencia: común de `<símbolo>'

    --warn-execstack
    --warn-execstack-objects
    --no-warn-execstack
    En plataformas ELF, el enlazador puede generar mensajes de advertencia si se le pide crear un archivo de salida que contenga una pila ejecutable. Hay tres estados posibles:
    1.
    No generar ninguna advertencia.
    2.
    Generar siempre advertencias, incluso si la pila ejecutable se solicita a través de la opción de línea de comandos -z execstack.
    3.
    Solo generar una advertencia si un archivo objeto solicita una pila ejecutable, pero no si se utiliza la opción -z execstack.

    El estado predeterminado depende de cómo se configuró el enlazador cuando se construyó. La opción --no-warn-execstack siempre pone al enlazador en el estado de no advertencias. La opción --warn-execstack pone al enlazador en el estado de advertir siempre. La opción --warn-execstack-objects pone al enlazador en el estado de advertir solo para archivos objeto.

    Nota: Los archivos de entrada en formato ELF pueden especificar que necesitan una pila ejecutable al tener una sección .note.GNU-stack con el bit de ejecución activado en sus flags de sección. Pueden especificar que no necesitan una pila ejecutable al tener la misma sección, pero sin el bit de flag de ejecución activado. Si un archivo de entrada no tiene una sección .note.GNU-stack, entonces el comportamiento predeterminado es específico del objetivo. Para algunos objetivos, la ausencia de dicha sección implica que se requiere una pila ejecutable. Esto suele ser un problema para archivos ensambladores hechos a mano.

    --error-execstack
    --no-error-execstack
    Si el enlazador va a generar un mensaje de advertencia sobre una pila ejecutable, entonces la opción --error-execstack cambiará esa advertencia por un error. Nota: esta opción no cambia el estado de generación de advertencias de execstack del enlazador. Usa --warn-execstack o --warn-execstack-objects para establecer un estado de advertencia específico.

    La opción --no-error-execstack restaurará el comportamiento predeterminado de generar mensajes de advertencia.

    --warn-multiple-gp
    Advierte si se requieren múltiples valores de puntero global en el archivo de salida. Esto solo tiene sentido para ciertos procesadores, como Alpha. Específicamente, algunos procesadores colocan constantes de valor grande en una sección especial. Un registro especial (el puntero global) apunta a la mitad de esta sección, para que las constantes puedan cargarse eficientemente mediante un modo de direccionamiento relativo al registro base. Dado que el desplazamiento en el modo relativo al registro base es fijo y relativamente pequeño (por ejemplo, 16 bits), esto limita el tamaño máximo del pool de constantes. Por lo tanto, en programas grandes, a menudo es necesario usar múltiples valores de puntero global para poder direccionar todas las constantes posibles. Esta opción hace que se emita una advertencia siempre que ocurra este caso.
    --warn-once
    Advierte solo una vez por cada símbolo no resuelto, en lugar de una vez por módulo que hace referencia a él.
    --warn-rwx-segments
    --no-warn-rwx-segments

Dicho segmento representa una posible vulnerabilidad de seguridad. Además, se generarán advertencias si se crea un segmento de almacenamiento de hilos (TLS) con el flag de permiso de ejecución activado, independientemente de si tiene o no los flags de lectura y/o escritura activados.

    Estas advertencias están habilitadas por defecto. Pueden ser deshabilitadas mediante la opción --no-warn-rwx-segments y rehabilitadas mediante la opción --warn-rwx-segments.

    --error-rwx-segments
    --no-error-rwx-segments

    Nota: la opción --error-rwx-segments no activa por sí sola las advertencias sobre estos segmentos. Estas advertencias están habilitadas por defecto, si el enlazador fue configurado de esa manera, o mediante la opción de línea de comandos --warn-rwx-segments.

    --warn-textrel

    --warn-alternate-em

    --warn-unresolved-symbols

    --whole-archive
    Para cada archivo de biblioteca mencionado en la línea de comandos después de la opción --whole-archive, incluye cada archivo objeto del archivo de biblioteca en el enlace, en lugar de buscar en el archivo de biblioteca los archivos objeto requeridos.     --wrap=símbolo
    Usa una función envoltorio (wrapper) para el símbolo. Cualquier referencia indefinida a símbolo se resolverá como "__wrap_símbolo". Cualquier referencia indefinida a "__real_símbolo" se resolverá como símbolo.

    Esto se puede usar para proporcionar un envoltorio para una función del sistema. La función envoltorio debe llamarse "__wrap_símbolo". Si desea llamar a la función del sistema, debe llamar a "__real_símbolo".

    Aquí hay un ejemplo trivial:

    void *
__wrap_malloc (size_t c)
{
  printf ("malloc llamado con %zu\n", c);
  return __real_malloc (c);
}

    Si enlaza otro código con este archivo usando --wrap malloc, todas las llamadas a "malloc" llamarán a la función "__wrap_malloc" en su lugar. La llamada a "__real_malloc" en "__wrap_malloc" llamará a la función real "malloc".

    Es posible que desee proporcionar también una función "__real_malloc", para que los enlaces sin la opción --wrap tengan éxito. Si lo hace, no debe colocar la definición de "__real_malloc" en el mismo archivo que "__wrap_malloc"; si lo hace, el ensamblador puede resolver la llamada antes de que el enlazador tenga la oportunidad de envolverla con "malloc".

    Solo las referencias indefinidas son reemplazadas por el enlazador. Por lo tanto, las referencias internas de la unidad de traducción a símbolo no se resuelven como "__wrap_símbolo". En el siguiente ejemplo, la llamada a "f" en "g" no se resuelve como "__wrap_f".

    int
f (void)
{
  return 123;
}

int
g (void)
{
  return f();
}

    --enable-new-dtags
    --disable-new-dtags
    Este enlazador puede crear las nuevas etiquetas dinámicas en ELF. Pero los sistemas ELF más antiguos pueden no entenderlas. Si especifica --disable-new-dtags, no se crearán nuevas etiquetas dinámicas. Por defecto, no se crean las nuevas etiquetas dinámicas.     --hash-size=número
    Establece el tamaño por defecto de las tablas hash del enlazador a un número primo cercano a número. Aumentar este valor puede reducir el tiempo que tarda el enlazador en realizar sus tareas, a expensas de aumentar los requisitos de memoria del enlazador. De manera similar, reducir este valor puede reducir los requisitos de memoria a expensas de la velocidad.
    --hash-style=estilo
    Establece el tipo de tabla(s) hash del enlazador. estilo puede ser "sysv" para la sección clásica de ELF ".hash", "gnu" para la nueva sección de estilo GNU ".gnu.hash" o "both" para ambas tablas hash, la clásica de ELF ".hash" y la nueva de estilo GNU ".gnu.hash". El valor por defecto depende de cómo se configuró el enlazador, pero para la mayoría de los sistemas basados en Linux será "both".
    --compress-debug-sections=none
    --compress-debug-sections=zlib
    --compress-debug-sections=zlib-gnu
    --compress-debug-sections=zlib-gabi
    --compress-debug-sections=zstd
    En plataformas ELF, estas opciones controlan cómo se comprimen las secciones de depuración DWARF usando zlib.

    --compress-debug-sections=none no comprime las secciones de depuración DWARF. --compress-debug-sections=zlib-gnu comprime las secciones de depuración DWARF y las renombra para que comiencen con .zdebug en lugar de .debug. --compress-debug-sections=zlib-gabi también comprime las secciones de depuración DWARF, pero en lugar de renombrarlas, establece el flag SHF_COMPRESSED en los encabezados de las secciones.

    La opción --compress-debug-sections=zlib es un alias de --compress-debug-sections=zlib-gabi.

    --compress-debug-sections=zstd comprime las secciones de depuración DWARF usando zstd.

    Tenga en cuenta que esta opción anula cualquier compresión en las secciones de depuración de entrada, por lo que si un binario se enlaza con --compress-debug-sections=none, por ejemplo, cualquier sección de depuración comprimida en los archivos de entrada se descomprimirá antes de copiarse en el binario de salida.

    El comportamiento de compresión por defecto varía según la plataforma de destino y las opciones de configuración utilizadas para compilar la cadena de herramientas. El valor por defecto puede determinarse examinando la salida de la opción --help del enlazador.

    --reduce-memory-overheads
    Esta opción reduce los requisitos de memoria en tiempo de ejecución de ld, a expensas de la velocidad de enlazado. Se introdujo para seleccionar el antiguo algoritmo O(n^2) para la generación del archivo de mapa de enlace, en lugar del nuevo algoritmo O(n) que utiliza aproximadamente un 40% más de memoria para el almacenamiento de símbolos.

    Otro efecto del cambio es establecer el tamaño por defecto de la tabla hash a 1021, lo que nuevamente ahorra memoria a costa de aumentar el tiempo de ejecución del enlazador. Sin embargo, esto no se hace si se ha utilizado el modificador --hash-size.

    El modificador --reduce-memory-overheads también se puede utilizar para habilitar otros intercambios en futuras versiones del enlazador.

    --max-cache-size=tamaño
    ld normalmente almacena en caché la información de reubicación y las tablas de símbolos de los archivos de entrada en memoria con tamaño ilimitado. Esta opción establece el tamaño máximo de caché en tamaño.
    --build-id
    --build-id=estilo
    Solicita la creación de una sección de nota ELF ".note.gnu.build-id" o una sección COFF ".buildid". El contenido de la nota son bits únicos que identifican este archivo enlazado. estilo puede ser "uuid" para usar 128 bits aleatorios; "sha1" para usar un hash SHA1 de 160 bits, "md5" para usar un hash MD5 de 128 bits, o "xx" para usar un XXHASH de 128 bits sobre las partes normativas del contenido de salida; o "0xcadena_hex" para usar una cadena de bits elegida especificada como un número par de dígitos hexadecimales (los caracteres "-" y ":" entre pares de dígitos se ignoran). Si se omite estilo, se usa "sha1".

    Los estilos "md5", "sha1" y "xx" producen un identificador que es siempre el mismo en un archivo de salida idéntico, pero que es casi seguro único entre todos los archivos de salida no idénticos. No está destinado a ser comparado como una suma de verificación del contenido del archivo. Un archivo enlazado puede ser modificado posteriormente por otras herramientas, pero la cadena de bits de ID de compilación que identifica el archivo enlazado original no cambia.

    Pasar "none" como estilo deshabilita la configuración de cualquier opción "--build-id" anterior en la línea de comandos.

    --package-metadata=JSON

    Nota: El uso de la extensión 'auto-import' hará que la sección de texto del archivo de imagen se convierta en escribible. Esto no se ajusta a la especificación del formato PE-COFF publicada por Microsoft.

    Nota - el uso de la extensión 'auto-import' también hará que los datos de solo lectura que normalmente se colocarían en la sección .rdata se coloquen en la sección .data en su lugar. Esto es para solucionar un problema con las constantes que se describe aquí: http://www.cygwin.com/ml/cygwin/2004-09/msg01101.html

    El uso de 'auto-import' generalmente "simplemente funciona", pero a veces puedes ver este mensaje:

    "la variable '<var>' no se puede auto-importar. Por favor, lee la documentación de ld para "--enable-auto-import" para obtener detalles."

    Este mensaje ocurre cuando alguna (sub)expresión accede a una dirección dada finalmente por la suma de dos constantes (las tablas de importación de Win32 solo permiten una). Instancias donde esto puede ocurrir incluyen accesos a campos miembro de variables struct importadas de un DLL, así como el uso de un índice constante en un array variable importado de un DLL. Cualquier variable de múltiples palabras (arrays, structs, long long, etc.) puede desencadenar esta condición de error. Sin embargo, independientemente del tipo de dato exacto de la variable exportada ofensiva, ld la detectará, emitirá la advertencia y saldrá.

    Hay varias formas de abordar esta dificultad, independientemente del tipo de dato de la variable exportada:

    Una forma es usar el modificador --enable-runtime-pseudo-reloc. Esto deja la tarea de ajustar las referencias en tu código cliente para el entorno de ejecución, por lo que este método solo funciona cuando el entorno de ejecución soporta esta característica.

    Una segunda solución es forzar una de las 'constantes' a ser una variable, es decir, desconocida y no optimizable en tiempo de compilación. Para arrays, hay dos posibilidades: a) hacer que el índice (la dirección del array) sea una variable, o b) hacer que el índice 'constante' sea una variable. Así:

    extern tipo extern_array[];
extern_array[1] -->
   { volatile tipo *t=extern_array; t[1] }

    o

    extern tipo extern_array[];
extern_array[1] -->
   { volatile int t=1; extern_array[t] }

    Para structs (y la mayoría de los otros tipos de datos de múltiples palabras), la única opción es hacer que la struct misma (o el long long, o el ...) sea una variable:

    extern struct s extern_struct;
extern_struct.campo -->
   { volatile struct s *t=&extern_struct; t->campo }

    o

    extern long long extern_ll;
extern_ll -->
  { volatile long long * local_ll=&extern_ll; *local_ll }

    Un tercer método para lidiar con esta dificultad es abandonar 'auto-import' para el símbolo en cuestión y marcarlo con "__declspec(dllimport)". Sin embargo, en la práctica, eso requiere usar #defines en tiempo de compilación para indicar si estás compilando un DLL, compilando código cliente que se enlazará al DLL, o simplemente compilando/enlazando a una biblioteca estática. Al elegir entre los diversos métodos para resolver el problema de 'dirección directa con desplazamiento constante', deberías considerar el uso típico en el mundo real:

    Original:

    --foo.h
extern int arr[];
--foo.c
#include "foo.h"
void main(int argc, char **argv){
  printf("%d\n",arr[1]);
}

    Solución 1:

    --foo.h
extern int arr[];
--foo.c
#include "foo.h"
void main(int argc, char **argv){
  /* Esta solución alternativa es para win32 y cygwin; no "optimizar" */
  volatile int *parr = arr;
  printf("%d\n",parr[1]);
}

    Solución 2:

    --foo.h
/* Nota: Se asume auto-export (sin __declspec(dllexport)) */
#if (defined(_WIN32) || defined(__CYGWIN__)) && \
  !(defined(FOO_BUILD_DLL) || defined(FOO_STATIC))
#define FOO_IMPORT __declspec(dllimport)
#else
#define FOO_IMPORT
#endif
extern FOO_IMPORT int arr[];
--foo.c
#include "foo.h"
void main(int argc, char **argv){
  printf("%d\n",arr[1]);
}

Si se usa --ignore-branch-isa, entonces el enlazador acepta cualquier reubicación de rama y cualquier transición de modo ISA requerida se pierde en el cálculo de la reubicación, excepto en algunos casos de instrucciones "BAL" que cumplen las condiciones de relajación y se convierten en instrucciones equivalentes "JALX" a medida que se calcula la reubicación asociada. Por defecto o si se usa --no-ignore-branch-isa, se realiza una comprobación que provoca la pérdida de una transición de modo ISA y genera un error.
    --compact-branches
    --no-compact-branches
    Estas opciones controlan la generación de instrucciones compactas por el enlazador en las entradas PLT para MIPS R6.

    Para el destino pdp11-aout, se pueden producir tres variantes del formato de salida según lo seleccionado por las siguientes opciones. La variante por defecto para pdp11-aout es la opción --omagic, mientras que para otros destinos --nmagic es el valor por defecto. La opción --imagic solo está definida para el destino pdp11-aout, mientras que las otras se describen aquí ya que se aplican al destino pdp11-aout.

    -N
    --omagic
    Marcar la salida como "OMAGIC" (0407) en la cabecera a.out para indicar que el segmento de texto no debe ser protegido contra escritura y compartido. Dado que los segmentos de texto y datos son legibles y escribibles, el segmento de datos se asigna inmediatamente contiguo después del segmento de texto. Este es el formato más antiguo para programas ejecutables PDP11 y es el valor por defecto para ld en sistemas Unix PDP11 desde el principio hasta 2.11BSD.
    -n
    --nmagic
    Marcar la salida como "NMAGIC" (0410) en la cabecera a.out para indicar que cuando el archivo de salida se ejecute, la porción de texto será de solo lectura y compartible entre todos los procesos que ejecuten el mismo archivo. Esto implica mover las áreas de datos hasta el primer límite de página de 8K bytes posible después del final del texto. Esta opción crea un formato de ejecutable puro.
    -z
    --imagic
    Marcar la salida como "IMAGIC" (0411) en la cabecera a.out para indicar que cuando el archivo de salida se ejecute, los segmentos de texto y datos del programa se cargarán en espacios de direcciones separados utilizando la característica de espacio de instrucciones y datos divididos de la unidad de gestión de memoria en modelos más grandes del PDP11. Esto duplica el espacio de direcciones disponible para el programa. El segmento de texto es nuevamente puro, protegido contra escritura y compartible. La única diferencia en el formato de salida entre esta opción y las otras, además del número mágico, es que tanto el texto como los datos

    OPTIONS

    --no-magic
    This option is obsolete. The default behaviour of ld is to use a magic number to determine the object file format. Sections start at location 0. The -z option selected this format in 2.11BSD. This option creates a separate executable format.
    --no-omagic
    Equivalent to --nmagic for pdp11-aout.

    ENVIRONMENT

    You can change the behaviour of ld with the environment variables "GNUTARGET", "LDEMULATION" and "COLLECT_NO_DEMANGLE".

    "GNUTARGET" determines the input-file object format if you don't use -b (or its synonym --format). Its value should be one of the BFD names for an input format. If there is no "GNUTARGET" in the environment, ld uses the natural format of the target. If "GNUTARGET" is set to "default" then BFD attempts to discover the input format by examining binary input files; this method often succeeds, but there are potential ambiguities, since there is no method of ensuring that the magic number used to specify object-file formats is unique. However, the configuration procedure for BFD on each system places the conventional format for that system first in the search-list, so ambiguities are resolved in favor of convention.

    "LDEMULATION" determines the default emulation if you don't use the -m option. The emulation can affect various aspects of linker behaviour, particularly the default linker script. You can list the available emulations with the --verbose or -V options. If the -m option is not used, and the "LDEMULATION" environment variable is not defined, the default emulation depends upon how the linker was configured.

    Normally, the linker will default to demangling symbols. However, if "COLLECT_NO_DEMANGLE" is set in the environment, then it will default to not demangling symbols. This environment variable is used in a similar fashion by the "gcc" linker wrapper program. The default may be overridden by the --demangle and --no-demangle options.

    If the PE/COFF specific --insert-timestamp is active and the SOURCE_DATE_EPOCH environment variable is defined, then the timestamp value in this variable will be inserted into the COFF header instead of the current time.

    If the "LD_STATS" environment variable is defined then linker resource use information will be recorded, just as if the --stats option had been used. If the "LD_STATS" variable has a string value then this will used as the name of a file into which the information should be stored. Otherwise the information will be sent to the standard output stream.
