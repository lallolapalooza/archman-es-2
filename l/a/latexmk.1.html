LATEXMK(1) Manual de Comandos Generales LATEXMK(1)

NOMBRE

latexmk - genera documentos LaTeX

SINOPSIS

latexmk [opciones] [archivo ...]

DESCRIPCIÓN

Latexmk automatiza completamente el proceso de compilación de un documento LaTeX. Esencialmente, es como un pariente especializado de la utilidad general make, pero uno que determina las dependencias automáticamente y tiene algunas otras características muy útiles. En su modo de operación básico, a latexmk se le da el nombre del archivo fuente primario de un documento, y emite la secuencia apropiada de comandos para generar una versión .dvi, .ps, .pdf y/o en papel del documento.

Por defecto, latexmk ejecutará los comandos necesarios para generar un archivo .dvi, lo que imita el comportamiento de versiones anteriores cuando solo estaba disponible latex.

Latexmk también puede configurarse para ejecutarse de forma continua con un visor adecuado. En ese caso, el programa latex (o uno de sus parientes), etc., se vuelven a ejecutar cada vez que uno de los archivos fuente se modifica, y el visor actualiza automáticamente la vista en pantalla del documento compilado.

Latexmk determina cuáles son los archivos fuente examinando el archivo de registro. (Opcionalmente, también examina la lista de archivos de entrada y salida generada por la opción -recorder de las versiones modernas de latex (y pdflatex, xelatex, lualatex). Consulte la documentación de la opción -recorder de latexmk a continuación). Cuando se ejecuta latexmk, examina las propiedades de los archivos fuente, y si alguno ha sido modificado desde la última generación del documento, latexmk ejecutará los diversos programas de procesamiento de LaTeX según sea necesario. En particular, repetirá la ejecución de latex (o un programa relacionado) con la frecuencia necesaria para resolver todas las referencias cruzadas; dependiendo de los paquetes de macros utilizados. Con algunos paquetes de macros y clases de documentos, pueden ser necesarias cuatro, o incluso más, ejecuciones. Si es necesario, latexmk también ejecutará bibtex, biber y/o makeindex. Además, latexmk puede configurarse para generar otros archivos necesarios. Por ejemplo, a partir de un archivo de figura actualizado, puede generar automáticamente un archivo en formato postscript encapsulado u otro formato adecuado para ser leído por LaTeX.

Latexmk tiene dos opciones de previsualización diferentes. Con la opción simple -pv, se ejecuta automáticamente un visor dvi, postscript o pdf después de generar la versión dvi, postscript o pdf del documento. El tipo de archivo a visualizar se selecciona según la configuración y las opciones de línea de comandos.

La segunda opción de previsualización es la potente opción -pvc (mnemotécnico: "preview continuously" - previsualizar continuamente). En este caso, latexmk se ejecuta de forma continua, monitoreando regularmente todos los archivos fuente para ver si alguno ha cambiado. Cada vez que se detecta un cambio, latexmk ejecuta todos los programas necesarios para generar una nueva versión del documento. Un buen visor actualizará automáticamente su pantalla. Por lo tanto, el usuario puede simplemente editar un archivo y, cuando los cambios se guarden en disco, latexmk automatiza completamente el ciclo de actualización del archivo .dvi (y/o .ps y .pdf) y la actualización de la pantalla del visor. No es exactamente WYSIWYG, pero se acerca bastante.

Para otros visores, el usuario puede tener que actualizar manualmente la visualización del visor, lo que puede ser (por ejemplo, con algunas versiones de xdvi y gsview) tan simple como forzar un redibujo de su pantalla.

Latexmk tiene la capacidad de imprimir una pancarta en gris diagonalmente a través de cada página al crear el archivo postscript. También puede, si es necesario, llamar a un programa externo para realizar otro postprocesamiento en los archivos dvi y postscript generados. (Consulte las opciones -dF y -pF, y la documentación de las variables de configuración $dvi_filter y $ps_filter). Estas capacidades son remanentes de versiones anteriores de latexmk, pero **actualmente no son funcionales**. Se puede obtener más flexibilidad en las versiones actuales, ya que las cadenas de comandos para ejecutar *latex ahora pueden configurarse para ejecutar múltiples comandos. Esto también amplía la posibilidad de postprocesar los archivos generados.

Latexmk es altamente configurable, tanto desde la línea de comandos como en archivos de configuración, de modo que pueda adaptarse a una amplia variedad de necesidades de los usuarios y configuraciones del sistema. Los valores predeterminados se establecen según el sistema operativo, por lo que latexmk a menudo funciona sin configuración especial en MS-Windows, cygwin, Linux, OS-X y otros sistemas UNIX. Consulte la sección "Archivos de Configuración/Inicialización (rc)", y luego las secciones posteriores "Cómo Establecer Variables en Archivos de Inicialización", "Formato de Especificaciones de Comandos", "Lista de Variables de Configuración Usables en Archivos de Inicialización", "Dependencias Personalizadas" y "Configuración Avanzada"

Una complicación muy molesta y manejada de manera muy confiable por latexmk es que LaTeX es un sistema de múltiples pasadas. En cada ejecución, LaTeX lee información generada en una ejecución anterior, para cosas como referencias cruzadas e índices. En los casos más simples, una segunda ejecución de LaTeX es suficiente, y a menudo el archivo de registro contiene un mensaje sobre la necesidad de otra pasada. Sin embargo, hay una amplia variedad de paquetes de macros adicionales para LaTeX, con diversos comportamientos. El resultado es romper las determinaciones simplistas de cuántas ejecuciones son necesarias y de qué programas. Latexmk tiene una solución muy general y eficiente a estos problemas. La solución implica conservar entre ejecuciones la información sobre los archivos fuente, y un síntoma es que latexmk genera un archivo adicional (con extensión .fdb_latexmk, por defecto) que contiene la información de los archivos fuente.

OPCIONES Y ARGUMENTOS DE LATEXMK EN LA LÍNEA DE COMANDOS

En general, la línea de comandos para invocar latexmk tiene la forma

latexmk [opciones] [archivo]

Todas las opciones pueden introducirse con uno o dos caracteres de guión, por ejemplo, "latexmk -help" o "latexmk --help".

Nota 1: En la documentación, '*latex' significa cualquiera de los motores compatibles, es decir, actualmente latex, lualatex, pdflatex, xelatex. La mención de uno específico de estos normalmente se refiere a ese motor específico. Versiones anteriores de esta documentación no eran tan consistentes. Cuál de estos se utiliza para compilar un documento, depende de la configuración y de los argumentos de la línea de comandos.

Nota 2: **Además de las opciones en la lista a continuación,** latexmk reconoce casi todas las opciones que reconocen los programas *latex en sus implementaciones actuales de TeXLive y MiKTeX. Algunas de las opciones para estos programas activan una acción o comportamiento especial por parte de latexmk, en cuyo caso tienen explicaciones específicas en este documento; en este caso, pueden o no pasarse también a *latex.

Ejecute latexmk con -showextraoptions para obtener una lista de las opciones que acepta latexmk y que se pasan directamente a *latex. Consulte también la explicación de la opción -showextraoptions para obtener más información.

Definiciones de opciones y argumentos

archivo
Se pueden especificar uno o más archivos. Si no se especifican archivos, latexmk, por defecto, se ejecutará en todos los archivos del directorio de trabajo actual con extensión ".tex". Este comportamiento se puede cambiar: consulte la descripción relativa a la variable @default_files en la sección "Lista de variables de configuración utilizables en archivos de inicialización".

Si se especifica un archivo sin extensión, la extensión ".tex" se añade automáticamente, tal como hace LaTeX. Por lo tanto, si especifica:

latexmk foo

entonces latexmk operará en el archivo "foo.tex".

Existen ciertas restricciones sobre qué caracteres pueden estar en un nombre de archivo; ciertos caracteres están prohibidos o son problemáticos para los programas latex, etc. Estos caracteres son: "$", "%", "\", "~", el carácter de comillas dobles, y los caracteres de control nulo, tabulación, salto de página, retorno de carro, avance de línea y suprimir. Además, "&" está prohibido cuando es el primer carácter de un nombre de archivo.

Latexmk genera un error fatal cuando detecta alguno de los caracteres anteriores en los nombres de archivo TeX especificados en la línea de comandos. **Sin embargo**, antes de probar los caracteres ilegales, latexmk elimina pares coincidentes de comillas dobles de un nombre de archivo. Esto coincide con la forma en que los programas TeX manejan las comillas dobles, que son ignoradas cuando están emparejadas. Esto se hace para permitir la especificación de nombres de archivo que contienen caracteres especiales en sistemas donde las comillas se usan para escapar tales caracteres, como en algunas versiones de la línea de comandos de Windows.

-auxdir=FOO o -aux-directory=FOO
Establece el directorio para los archivos de salida auxiliares de *latex (.aux, .log etc). Estos son todos los archivos generados, con la excepción de los archivos de salida finales (.dvi, .ps, .pdf, .synctex.gz, .synctex). Véase la opción -outdir/-output-directory para los directorios de los archivos de salida principales, y la opción -out2dir para los archivos de salida finales.

Si el directorio especificado para la opción -aux/-aux-directory está en blanco, entonces se utiliza el valor predeterminado, que es el mismo que el directorio de salida.

Si también utiliza la opción -cd, y el directorio de salida auxiliar especificado es una ruta relativa, entonces la ruta se interpreta en relación con el directorio del documento.

Véase la sección DIRECTORios AUXILIARES Y DE SALIDA para más detalles.

-bibtex
Cuando el archivo fuente utiliza archivos bbl para la bibliografía, ejecuta bibtex o biber según sea necesario para regenerar los archivos bbl.

Esta propiedad también se puede configurar estableciendo la variable $bibtex_use a 2 en un archivo de configuración.

-bibtex-
Nunca ejecutes bibtex o biber. Además, considera siempre los archivos .bbl como valiosos, es decir, no los elimines en una operación de limpieza.

Un uso común para esta opción es cuando un documento proviene de una fuente externa, completo con sus archivos bbl, y el usuario no tiene disponibles los archivos bib correspondientes. En esta situación, el uso de la opción -bibtex- evitará que latexmk intente ejecutar bibtex o biber, lo que resultaría en la sobrescritura de los archivos bbl.

Esta propiedad también se puede configurar estableciendo la variable $bibtex_use a 0 en un archivo de configuración.

-bibtex-cond
Cuando el archivo fuente utiliza un archivo bbl para la bibliografía y bibtex se utiliza para generar la bibliografía, ejecuta bibtex según sea necesario para regenerar los archivos bbl solo si existen los archivos bib relevantes. Por lo tanto, cuando los archivos bib no están disponibles, bibtex no se ejecuta, evitando así la sobrescritura del archivo bbl. Además, considera siempre los archivos .bbl como valiosos, es decir, no los elimines en una operación de limpieza.

Esta es la configuración predeterminada. También se puede configurar estableciendo la variable $bibtex_use a 1 en un archivo de configuración.

La razón para usar esta configuración es primero permitir el cambio automático entre el uso y no uso de bibtex dependiendo de la existencia o no de un archivo bib. Además, al enviar artículos a una revista científica, es común enviar solo los archivos .tex y .bbl (más los archivos gráficos), pero no un archivo .bib. Por lo tanto, a menudo es útil considerar los archivos .bbl como archivos fuente verdaderos, que deben conservarse en una operación de limpieza.

Esta propiedad también se puede configurar estableciendo la variable $bibtex_use a 1 en un archivo de configuración.

Nota que cuando se utiliza biber, y no existe un archivo bib, esta opción no impide que biber se ejecute, con el archivo bbl siendo incorrecto. Véase la documentación sobre $bibtex_use para más detalles. Sin embargo, un archivo bbl se considera valioso en una operación de limpieza.

-bibtex-cond1
Lo mismo que -bibtex-cond excepto que los archivos .bbl solo se consideran valiosos si uno o más archivos bib no existen.

Por lo tanto, si existen todos los archivos bib, se ejecuta bibtex para generar los archivos .bbl según sea necesario, y luego es apropiado eliminar los archivos bbl en una operación de limpieza, ya que se pueden volver a generar.

Esta propiedad también se puede configurar estableciendo la variable $bibtex_use a 1.5 en un archivo de configuración.

Nota que cuando se utiliza biber, y no existe un archivo bib, esta opción no impide que biber se ejecute, con el archivo bbl siendo incorrecto. Véase la documentación sobre $bibtex_use para más detalles. Sin embargo, un archivo bbl se considera valioso en una operación de limpieza.

-bibtexfudge o -bibfudge
Activa el ajuste de cambio de directorio para bibtex. Véase la documentación de $bibtex_fudge para más detalles.
-bibtexfudge- o -bibfudge-
Desactiva el ajuste de cambio de directorio para bibtex. Véase la documentación de $bibtex_fudge para más detalles.
-bm <mensaje>
Un mensaje de banner para imprimir en diagonal en cada página al convertir el archivo dvi a postscript. El mensaje debe ser un único argumento en la línea de comandos, así que ten cuidado con las comillas de los espacios y similares.

Nota que si se especifica la opción -bm, se asume la opción -ps.

-bi <intensidad>
Qué tan oscuro imprimir el mensaje del banner. Un número decimal entre 0 y 1. 0 es negro y 1 es blanco. El valor predeterminado es 0.95, que está bien a menos que tu cartucho de tóner se esté agotando.
-bs <escala>
Un número decimal que especifica cuán grande se imprimirá el mensaje del banner. Es necesario experimentar para obtener la escala correcta para tu mensaje, como regla general, la escala debe ser aproximadamente igual a 1100 dividido por el número de caracteres en el mensaje. El valor predeterminado es 220.0 que es justo para mensajes de 5 caracteres.
-commands
Lista los comandos utilizados por latexmk para procesar archivos, y luego sale.
-c
Limpia (elimina) todos los archivos regenerables generados por latex y bibtex o biber excepto los dvi, postscript y pdf. Estos archivos son una combinación de archivos de registro, archivos aux, el archivo de base de datos de latexmk con información de archivos fuente, y aquellos con extensiones especificadas en la variable de configuración @generated_exts. Además, se eliminan los archivos especificados por las variables de configuración $clean_ext y @generated_exts.

Esta limpieza es en lugar de un make regular. Véase la opción -gg si desea hacer una limpieza seguida de un make.

Tratamiento de archivos .bbl: Si $bibtex_use se establece a 0 o 1, los archivos bbl siempre se consideran no regenerables. Si $bibtex_use se establece a 1.5, los archivos bbl se cuentan como no regenerables condicionalmente: Si el archivo bib existe, entonces los archivos bbl son regenerables y se eliminan en una limpieza. Pero si $bibtex_use es 1.5 y no existe un archivo bib, entonces los archivos bbl se consideran no regenerables y, por lo tanto, no se eliminan.

En contraste, si $bibtex_use se establece a 2, los archivos bbl siempre se consideran regenerables y se eliminan en una limpieza.

Tratamiento de archivos generados por dependencias personalizadas: Si $cleanup_includes_cusdep_generated es distinto de cero, los archivos regenerables se consideran incluyendo aquellos generados por dependencias personalizadas y también se eliminan. De lo contrario, estos archivos no se eliminan.

-C
Limpia (elimina) todos los archivos regenerables generados por latex y bibtex o biber. Esto es lo mismo que la opción -c con la adición de archivos dvi, postscript y pdf, y aquellos especificados en la variable de configuración $clean_full_ext.

Esta limpieza es en lugar de un make regular. Véase la opción -gg si desea hacer una limpieza seguida de un make.

Véase la opción -c para la especificación de si los archivos .bbl se consideran no regenerables o regenerables.

Si $cleanup_includes_cusdep_generated es distinto de cero, los archivos regenerables se consideran incluyendo aquellos generados por dependencias personalizadas y también se eliminan. De lo contrario, estos archivos no se eliminan.

-CA
(Obsoleto). Ahora equivalente a la opción -C. Véase esa opción para más detalles.
-cd
Cambia al directorio que contiene el archivo fuente principal antes de procesarlo. Entonces todos los archivos generados (.aux, .log, .dvi, .pdf, etc.) serán relativos al archivo fuente.

Esta opción es particularmente útil cuando latexmk se invoca desde una GUI configurada para invocar latexmk con una ruta completa para el archivo fuente.

Esta opción funciona estableciendo la variable de configuración $do_cd a uno; puedes establecer esa variable si deseas configurar latexmk para que tenga el efecto de la opción -cd sin especificarla en la línea de comandos. Véase la documentación para esa variable.

-cd-
NO cambies al directorio que contiene el archivo fuente principal antes de procesarlo. Entonces todos los archivos generados (.aux, .log, .dvi, .pdf, etc.) serán relativos al directorio actual en lugar del archivo fuente.

Este es el comportamiento predeterminado y corresponde al comportamiento de los programas *latex. Sin embargo, no es un comportamiento deseable cuando latexmk es invocado por una GUI configurada para invocar latexmk con una ruta completa para el archivo fuente. Véase la opción -cd.

Esta opción funciona estableciendo la variable de configuración $do_cd a cero. Véase la documentación para esa variable para más información.

-CF
Elimina el archivo que contiene la base de datos de información de archivos fuente, antes de realizar las otras acciones solicitadas.
-d
Establece el modo borrador. Esto imprime el mensaje del banner "DRAFT" a través de tu página al convertir el archivo dvi a postscript. El tamaño y la intensidad se pueden modificar con -bs y -bi
options. La opción -bm anulará esta opción, ya que es solo una forma abreviada de especificar:

latexmk -bm DRAFT

Tenga en cuenta que si se especifica la opción -d, se asume la opción -ps.

-deps
Muestra una lista de archivos dependientes después del procesamiento. Esto tiene el formato de una lista de dependencias tal como la utiliza el programa make y, por lo tanto, es adecuada para su uso en un Makefile. Ofrece una vista general de los archivos sin listar los archivos intermedios, según latexmk pueda determinarlos.

Por defecto, la lista de archivos dependientes se envía a la salida estándar (es decir, normalmente a la pantalla a menos que haya redirigido la salida de latexmk). Pero puede establecer el nombre del archivo donde se envía la lista con la opción -deps-out=.

Consulte la sección "USO DE latexmk CON make" para ver un ejemplo de cómo utilizar una lista de dependencias con make.

Los usuarios familiarizados con GNU automake y gcc encontrarán que la opción -deps es muy similar en su propósito y resultados a la opción -M de gcc. (De hecho, latexmk también tiene las opciones -M, -MF y -MP que se comportan como las de gcc).

-dependents
Equivalente a -deps.
-deps-
No mostrar una lista de archivos dependientes después del procesamiento. (Este es el valor predeterminado).
-dependents-
Equivalente a -deps-.
-deps-escape=<string>
Establece el tipo de escape utilizado para los espacios en la lista de dependencias. Los valores posibles son "none", "unix", "nmake", correspondientemente a ningún escape, escape con un "\" adecuado para el make estándar de Unix, y escape con "^", adecuado para el nmake de Microsoft.
-deps-out=FILENAME
Establece el nombre del archivo al que se escribe la lista de archivos dependientes. Si el argumento FILENAME se omite o se establece en "-", entonces la salida se envía a stdout.

El uso de esta opción también activa la salida de la lista de archivos dependientes después del procesamiento.

-dF
Filtrado de archivos Dvi. El argumento para esta opción es un filtro que generará un archivo dvi filtrado con la extensión ".dviF". Todo el procesamiento adicional (por ejemplo, conversión a postscript, vista previa, impresión) se realizará entonces sobre este archivo dvi filtrado.

Ejemplo de uso: Para utilizar dviselect para seleccionar solo las páginas pares del archivo dvi:

latexmk -dF "dviselect even" foo.tex

-diagnostics
Imprime diagnósticos detallados durante una ejecución. Esto puede ayudar a depurar problemas o a comprender el comportamiento de latexmk en situaciones difíciles.
-dir-report
Para cada archivo .tex procesado, enumera la configuración de los directorios auxiliares y de salida, después de que se hayan normalizado a partir de la configuración especificada durante la inicialización. Consulte la descripción de la variable $aux_out_dir_report para obtener más detalles.
-dir-report-
No informar la configuración de los directorios auxiliares y de salida. (Predeterminado)
-dir-report-only
Después de completar toda la inicialización, proporcione la configuración de los directorios auxiliares y de salida, y luego deténgase. Esta opción se utiliza principalmente para depurar problemas de configuración.
-dvi
Genera la versión dvi del documento utilizando latex. (Y desactiva cualquier solicitud incompatible).
-dvilua
Genera la versión dvi del documento utilizando lualatex en lugar de latex. (Y desactiva cualquier solicitud incompatible).
-dvi-
Desactiva la generación de la versión dvi del documento. (Esto puede ser anulado si se crea algún otro archivo (por ejemplo, un archivo .ps) que se genera a partir del archivo dvi, o si no se solicita ningún archivo generado).
-dvilualatex="COMANDO"
Esto establece la cadena que especifica el comando para ejecutar dvi lualatex. Se comporta como la opción -pdflatex, pero establece la variable $dvilualatex.

Nota: Esta opción, cuando se proporciona con el argumento COMANDO, solo establece el comando para invocar dvilualatex; no activa el uso de dvilualatex. Eso se hace con otras opciones o en un archivo de inicialización.

-e <código>
Ejecuta el código de inicialización especificado antes del procesamiento. El código es código Perl de la misma forma que se utiliza en los archivos de inicialización de latexmk. Para más detalles, consulte la información sobre la opción -r y la sección sobre "Archivos de configuración/inicialización (RC)". El código suele ser una secuencia de sentencias de asignación separadas por punto y coma.

El código se ejecuta cuando se encuentra la opción -e durante el análisis de la línea de comandos de latexmk. Consulte la opción -r para ver una forma de ejecutar código de inicialización desde un archivo. Un error resulta en la detención de latexmk. Se pueden utilizar múltiples instancias de las opciones -r y -e, y se ejecutan en el orden en que aparecen en la línea de comandos.

Se necesita cierta precaución para tratar correctamente las comillas de caracteres especiales en el código de la línea de comandos. Por ejemplo, si desea establecer el comando latex para que utilice su opción -shell-escape, entonces bajo UNIX/Linux podría usar la línea

latexmk -e '$latex=q/latex %O -shell-escape %S/' file.tex

Tenga en cuenta que las comillas simples bloquean los shells de comandos normales de UNIX/Linux para que no traten los caracteres dentro de las comillas como especiales. (En este ejemplo, la construcción q/.../ es un modismo de Perl equivalente a usar comillas simples. Esto evita las complicaciones de incluir un carácter de comilla dentro de una cadena ya entrecomillada de una manera que sea independiente tanto del shell como del sistema operativo).

La línea de comandos anterior NO funcionará en MS-Windows con cmd.exe o command.com o 4nt.exe. Para MS-Windows con estos shells de comandos, podría usar

latexmk -e "$latex=q/latex %O -shell-escape %S/" file.tex

o

latexmk -e "$latex='latex %O -shell-escape %S'" file.tex

Los dos últimos ejemplos NO funcionarán con los shells de comandos de UNIX/Linux.

(Nota: los ejemplos anteriores muestran cómo usar -e para especificar código de inicialización que se ejecutará. Pero el efecto particular también se puede lograr mediante el uso de la opción -latex con menos problemas de manejo de comillas.)

-emulate-aux-dir
Emula el uso de un directorio auxiliar en lugar de dejar que los programas *latex lo hagan. (MiKTeX soporta -aux-directory, pero TeXLive no).

Consulte la sección DIRECTORIOS AUXILIARES Y DE SALIDA para más detalles.

-emulate-aux-dir-
Desactiva la emulación para implementar un directorio auxiliar y deja que el programa *latex maneje el caso en que el directorio auxiliar sea diferente del directorio de salida. Tenga en cuenta que si utiliza TeXLive, que no soporta -aux-directory, latexmk activará automáticamente la emulación de aux_dir después de la primera ejecución de *latex, ya que encontrará el archivo .log en el lugar equivocado.
-f
Fuerza a latexmk a continuar el procesamiento del documento a pesar de los errores. Normalmente, cuando latexmk detecta que LaTeX u otro programa ha encontrado un error que no se resolverá con un procesamiento adicional, no se realiza ningún procesamiento adicional.

Nota: "Procesamiento adicional" significa la ejecución de otros programas o la reejecución de latex (etc.) que se realizaría si no hubiera ocurrido ningún error. Si en su lugar, o además, desea que el programa latex (etc) no se detenga para pedir entrada al usuario después de un error, debe organizarlo mediante una opción que se pase al programa, por ejemplo, mediante la opción -interaction=nonstopmode de latexmk (que latexmk pasa a *latex).

-f-
Desactiva el procesamiento forzado más allá de los errores, como se establece con la opción -f. Esto podría usarse para anular una configuración en un archivo de configuración.
-g
Fuerza a latexmk a procesar el documento completamente, incluso en situaciones donde latexmk normalmente decidiría que no ha ocurrido ningún cambio en los archivos fuente desde la ejecución anterior. Esta opción es útil, por ejemplo, si cambia algunas opciones y desea reprocesar los archivos.
-g-

-jobname=PATTERN

Set the jobname of the TeX file. The PATTERN is interpreted as a format string, and may contain %-specifications of the kind used by printf. In addition, the following %-specifications are supported:

%A
The basename of the source file being processed, with no extension. For example, if the file is `test1.tex', then %A is `test1'. This is the default format string for the jobname.
%F
The full name of the source file being processed. For example, `test1.tex'.

The primary purpose is when multiple files are specified on the command line to latexmk, and you wish to use a jobname with a different file-dependent value for each file. For example, suppose you had .tex files test1.tex and test2.tex, and you wished to compare the results of compilation by *latex and those with xelatex. Then under a unix-type operating system you could use the command line


latexmk -pdf -jobname=%A-pdflatex *.tex
latexmk -pdfxe -jobname=%A-xelatex *.tex

Then the .aux, .log, and .pdf files from the use of pdflatex would have basenames test1-pdflatex and test2-pdflatex, while from xelatex, the basenames would be test1-xelatex and test2-xelatex.

Under MS-Windows with cmd.exe, you would need to double the percent sign, so that the percent character is passed to latexmk rather than being used to substitute an environment variable:


latexmk -pdf -jobname=%%A-pdflatex *.tex
latexmk -pdfxe -jobname=%%A-xelatex *.tex

Lo opuesto a -silent. Esta es la configuración por defecto.
-view=default, -view=dvi, -view=hnt, -view=ps, -view=pdf, -view=none
Establece el tipo de archivo utilizado cuando se solicita una vista previa (por ejemplo, mediante las opciones -pv o -pvc). Por defecto, se visualiza el tipo de archivo de mayor prioridad solicitado (en el orden de menor a mayor: .dvi, .hnt, .ps, .pdf).

Observe la posibilidad de -view=none, en cuyo caso no se abre ningún visor. Un ejemplo de su uso es en conjunción con la opción -pvc, cuando desea que latexmk realice una compilación automáticamente cada vez que cambian los archivos fuente, pero no desea que se abra un programa de vista previa.

-Werror
Esto hace que latexmk devuelva un código de estado distinto de cero si alguno de los archivos procesados genera una advertencia sobre problemas con citas o referencias (es decir, citas o referencias indefinidas o referencias multidefinidas). Esto es *después* de que latexmk haya completado todas las ejecuciones necesarias para intentar resolver las referencias y citas. Por lo tanto, -Werror hace que latexmk trate dichas advertencias como errores, pero solo cuando ocurren en la última ejecución de *latex y solo después de que se completa el procesamiento. También se puede establecer mediante la variable de configuración $warnings_as_errors.
-xdv
Genera la versión xdv del documento usando xelatex. (Y desactiva cualquier solicitud incompatible).
-xelatex
Utiliza xelatex. Es decir, utiliza xelatex para procesar el(los) archivo(s) fuente. Esto generará un pdf (pero indirectamente a través de un archivo xdv). (Y desactiva cualquier solicitud incompatible).

Esta opción es equivalente a usar la siguiente opción:


-pdfxe

[Nota: Tenga en cuenta que el método de implementación de esta opción, pero no su efecto principal previsto, difiere de algunas versiones anteriores de latexmk. Latexmk primero utiliza xelatex para crear un archivo .xdv y realiza todas las ejecuciones adicionales necesarias (incluidas las de bibtex, etc.). Solo después crea el archivo pdf a partir del archivo .xdv, utilizando xdvipdfmx. Consulte la documentación de -pdfxe para saber por qué se hace esto.]

-xelatex="COMMAND"
Esto establece la cadena que especifica el comando para ejecutar xelatex. Establece la variable $xelatex.

Advertencia: Es importante asegurarse de que se utilice -no-pdf cuando se invoque xelatex, ya que latexmk espera que xelatex produzca un archivo .xdv, no un archivo .pdf. Si proporciona %O en la especificación del comando, esto se hará automáticamente. Consulte la documentación de la opción -pdfxe para saber por qué latexmk crea un archivo .xdv en lugar de un archivo .pdf cuando se utiliza xelatex.

Un ejemplo del uso de la opción -xelatex:


latexmk -pdfxe -xelatex="xelatex --shell-escape %O %S" foo.tex

Nota: Esta opción, cuando se proporciona con el argumento COMMAND, solo establece el comando para invocar xelatex; no activa el uso de lualatex. Eso se hace mediante otras opciones o en un archivo de inicialización.

Compatibilidad entre opciones

La opción de vista previa continua -pvc solo puede funcionar con un archivo. Por lo tanto, en este caso, normalmente solo especificará un nombre de archivo en la línea de comandos.

Las opciones -p, -pv y -pvc son mutuamente excluyentes. Por lo tanto, cada una de estas opciones desactiva las otras.

MANEJO DE ERRORES, PROBLEMAS, ETC.

Algunas posibilidades:

a. Si obtiene un error extraño, revise cuidadosamente la salida que aparece en la pantalla y en los archivos de registro. Aunque hay mucha información notoriamente verbosa en la salida de latex (y que latexmk añade), la verbosidad está ahí por una razón: para permitir al usuario diagnosticar problemas. Latexmk repite algunos mensajes al final de una ejecución que cree que de otro modo pasarían desapercibidos en medio de otra salida.

b. En general, recuerde que latexmk realiza su trabajo ejecutando otros programas. Su primera prioridad al tratar con errores debe ser examinar qué salió mal con los programas individuales. Luego, necesita corregir las causas de los errores en las ejecuciones de estos programas. (A menudo provienen de errores en el documento fuente, pero también podrían ser sobre paquetes LaTeX faltantes, etc.)

c. Si latexmk no ejecuta los programas como usted desea, entonces necesita buscar en esta documentación la lista de opciones de línea de comandos y luego en las secciones sobre archivos de configuración/inicialización. Gran parte del comportamiento de latexmk es configurable para lidiar con situaciones particulares. (¡Pero hay mucha lectura!)

El resto de estas notas consiste en ideas para lidiar con situaciones más difíciles.

d. Trucos adicionales pueden implicar reemplazar los comandos estándar que latexmk ejecuta por otros comandos o scripts.

e. Para posibles ejemplos de código para usar en un archivo RC, consulte el directorio example_rcfiles en la distribución de latexmk (por ejemplo, en http://mirror.ctan.org/support/latexmk/example_rcfiles). Incluso si estos ejemplos no hacen lo que usted quiere, pueden proporcionarle inspiración adecuada.

f. Hay un truco útil que se puede usar cuando se utiliza lualatex en lugar de pdflatex (y en algunas situaciones relacionadas). El problema es que latexmk no detectará una dependencia de un archivo, digamos bar.baz, que es incluido por el código lua en su documento en lugar de por la parte LaTeX. (Por lo tanto, si cambia bar.baz y vuelve a ejecutar latexmk, entonces latexmk pensará que no han cambiado los archivos y no volverá a ejecutar lualatex, mientras que si hubiera '\input{bar.baz}' en la parte LaTeX del documento, latexmk notaría el cambio). Una solución es simplemente poner lo siguiente en algún lugar de la parte LaTeX del documento:


\typeout{(bar.baz)}

Esto inserta una línea en el archivo de registro que latexmk tratará como si implicara que el archivo bar.baz fue leído. (Por el momento, no conozco una forma de hacer esto automáticamente). Por supuesto, si el archivo tiene un nombre diferente, cambie bar.baz por el nombre de su archivo.

DIRECTORIOS AUXILIARES Y DE SALIDA

Ejecutar *latex y los programas asociados genera una serie de archivos, a menudo es conveniente organizar los archivos generados para que estén en un directorio diferente al(los) archivo(s) fuente de un documento. Para nuestros propósitos aquí, identificamos dos clases de archivos generados.

Una clase son los que se pueden denominar archivos de salida finales, por ejemplo, el archivo .pdf generado al ejecutar pdflatex, o el archivo .dvi de latex. También en esta clase se encuentran los archivos ps generados al aplicar dvips a un archivo .dvi. También hay archivos .synctec o .synctex.gz que pueden ser utilizados por programas que muestran archivos .pdf y similares para relacionar posiciones en ellos con posiciones en los archivos fuente.

La segunda clase de archivo está compuesta por todos los demás archivos generados: Estos incluyen notablemente archivos .aux que se utilizan para implementar referencias cruzadas, y que se generan en una ejecución y se leen en una ejecución posterior. Muchos paquetes generan aún más archivos intermedios de este tipo, así como programas como bibtex, makeindex, etc. También hay archivos .log de *latex y archivos correspondientes de otros programas.

Utilizaremos el término "directorio de salida" para el directorio que recibe los archivos de salida finales, y "directorio auxiliar" para el directorio de los demás archivos generados. Si no se proporcionan opciones especiales a los programas *latex, estos directorios son por defecto el directorio actual, y entonces los archivos generados no se segregan. Si los dos directorios son iguales, como es la situación más simple, entonces todos los archivos generados se escriben en el mismo directorio, y a menudo se hace referencia simplemente al directorio de salida, sin mencionar un directorio auxiliar separado.

Los programas *latex proporcionan soporte para ellos: mediante la opción única -output-directory para las implementaciones de TeXLive, y mediante las opciones -aux-directory y -output-directory para las implementaciones de MiKTeX. Se necesita un soporte especial como este por dos razones: Primero, hay muchos paquetes que escriben archivos y es necesario asegurarse de que se escriban automáticamente en el directorio apropiado sin necesidad de reescribir el código de los paquetes. Segundo, los archivos a menudo se vuelven a leer en ejecuciones posteriores de *latex, y es necesario que el programa sepa dónde encontrar los archivos.

Una complicación es que la implementación de TeXLive no permite directorios auxiliares y de salida separados. Latexmk lo maneja pudiendo emular un directorio auxiliar separado: en este método invoca *latex con solo la opción -output-directory, con el directorio no configurado al directorio de salida deseado, sino al directorio auxiliar. Después de ejecutar *latex, mueve el

directorios finales relevantes para el directorio de salida previsto. La emulación se puede activar configurando la variable de configuración $emulate_aux a uno en un archivo de configuración o utilizando la opción -emulate-aux-dir de latexmk. El método de emulación funciona igual de bien si se utiliza MiKTeX.

Latexmk también activa la emulación si se considera necesaria, de la siguiente manera. Supongamos que la emulación está desactivada inicialmente, pero los directorios aux y de salida son diferentes. Entonces latexmk invoca *latex con una opción -aux-directory y, después de la ejecución, descubre que no se ha obedecido, sobre todo porque el archivo .log está en el directorio de salida en lugar del directorio aux. Latexmk activa entonces la emulación y lo intenta de nuevo. Concebiblemente, podría mover todos los archivos generados apropiados del directorio de salida al directorio aux; pero hay una gran variedad de posibilidades para estos archivos que es difícil identificarlos todos de forma fiable, excepto en casos sencillos.

Tenga en cuenta que el problema de la emulación solo surge cuando el usuario ha dispuesto que los directorios aux y de salida sean diferentes. Cuando en cambio son iguales, por ejemplo, porque el usuario solo ha configurado la variable $out_dir, entonces latexmk invoca *latex solo con una opción -output-directory, que funciona según lo previsto tanto con TeXLive como con MiKTeX.

Además, latexmk organiza las invocaciones de programas auxiliares como bibtex y makeindex para que lean y escriban los archivos relevantes desde y hacia el directorio aux. Programas como dvips, dvipdf, ps2pdf y xdvipdfmx se invocan para que lean de los lugares apropiados y escriban su salida en el directorio de salida.

Archivos considerados como archivos de salida finales, es decir, aquellos que pertenecen al directorio de salida en lugar del directorio aux: Estos tienen las extensiones .dvi, .ps., .pdf, .synctex y .synctex.gz. Un caso especial, debido a problemas de compatibilidad, son los archivos .fls: Véase más abajo.

Tenga en cuenta que xelatex, cuando se invoca con su opción -no-pdf, como hace latexmk, genera un archivo .xdv, que parecería tener el mismo estado que un archivo .dvi generado por latex. Sin embargo, latexmk trata .xdv como un archivo intermedio que se encuentra en el directorio aux. Esto es para que coincida con el tratamiento de MiKTeX de la opción -aux-directory. Como justificación adicional, se puede decir que en condiciones modernas un archivo .xdv es (casi) siempre un archivo intermedio. Históricamente, la situación con los archivos .dvi de latex era diferente, y actualmente existen previsualizadores dvi.

Variables y opciones para directorios: Las variables para configurar los directorios aux y de salida son $aux_dir y $out_dir, con las opciones de línea de comandos correspondientes -auxdir (o -aux-directory) y -outdir (o -output-directory). Cuando un valor para estos está en blanco (que es el valor por defecto), implica el uso de un valor por defecto: Para el directorio aux, el valor por defecto es establecerlo igual al directorio de salida. Para el directorio de salida, el valor por defecto es el directorio actual.

Para activar y desactivar el modo de emulación, existe la variable de configuración $emulate_aux y las opciones -emulate-aux-dir, -emulate-aux-dir-, -noemulate-aux-dir.

Interacción con la opción -cd: Cuando se utiliza la opción -cd (o la configuración equivalente de la variable $do_cd), latexmk cambia el directorio de trabajo al directorio del documento antes de invocar *latex. Si los directorios aux y/o de salida se proporcionan mediante rutas relativas, por ejemplo, mediante -outdir=output para un directorio llamado "output", entonces los directorios son relativos al directorio del documento, en lugar de relativos al directorio de trabajo que estaba en vigor cuando se invocó latexmk. Esto coincide con el comportamiento de *latex invocado con los argumentos de directorio de línea de comandos proporcionados después del cambio de directorio de trabajo al directorio del documento.

Creación automática de directorios aux y de salida: A diferencia de *latex, si latexmk encuentra que el/los directorio/s solicitado/s no existen, lo/s crea, evitando así errores cuando se invoca *latex.

Si el documento utiliza la macro \include para leer un archivo .tex de un subdirectorio, *latex intentará escribir un archivo aux adicional en el subdirectorio correspondiente del directorio aux. Si el subdirectorio no existe, *latex se quejará de que no puede escribir el archivo aux. Después de la ejecución de *latex, latexmk detecta esta situación, crea el directorio necesario y vuelve a ejecutar *latex con la situación de error corregida.

Elección de directorios aux y de salida: A menudo, los directorios aux y de salida se proporcionan como subdirectorios del directorio del documento, por ejemplo, mediante -outdir=output. Pero es posible proporcionar, por ejemplo, una ruta absoluta o una ruta relativa a un directorio padre, por ejemplo, "/tmp/foo" o "../output". Tenga en cuenta que en general esto puede causar problemas, especialmente con makeindex o bibtex. Esto se debe a que las versiones modernas de estos programas, por defecto, se negarán a funcionar cuando descubran que se les pide escribir en un archivo en un directorio que parece no ser el directorio de trabajo actual o uno de sus subdirectorios. Esto forma parte de las medidas de seguridad de todo el sistema TeX que intentan evitar que documentos TeX maliciosos o errantes manipulen incorrectamente los archivos de un usuario.

Por defecto, latexmk evade este problema: Antes de ejecutar bibtex y makeindex, latexmk cambia el directorio de trabajo al directorio aux, con la configuración apropiada de rutas de búsqueda. El uso o no de este truco está regido por las variables $bibtex_fudge y $makeindex_fudge. Desafortunadamente, el truco a veces hace que bibtex y makeindex no puedan encontrar archivos.

Si es necesario, el truco se puede desactivar. Pero esto es incompatible con un directorio aux como, "/tmp/foo" o "../output"). Si realmente tiene que lidiar con esta situación, y solo si tiene que lidiar con ella, entonces necesita deshabilitar las medidas de seguridad (y asumir cualquier riesgo). Una forma de hacerlo es establecer temporalmente una variable de entorno del sistema operativo openout_any a "a" (como en "all"), para anular la configuración por defecto "paranoid".

Ciertos nombres de directorios aux y de salida no permitidos en Microsoft Windows: Es natural querer usar el nombre "aux" para el directorio aux, por ejemplo, usando la opción -auxdir=aux. Pero en los sistemas operativos Microsoft "aux" es uno de los nombres que no están permitidos para un archivo o directorio. Me resulta útil estandarizar un nombre como "auxdir" (por ejemplo, mediante -auxdir=auxdir); esto funciona independientemente del sistema operativo.

Ubicación del archivo .fls: Gran parte de la información de dependencias que utiliza latexmk proviene del archivo .fls generado cuando se invoca *latex con la opción -recorder, lo que latexmk hace por defecto. Puede parecer lógico que esto se escriba en el directorio aux. Pero, de hecho, las versiones de MiKTeX anteriores a octubre de 2020 lo escribían en el directorio de salida. Las versiones posteriores lo escriben en el directorio aux. Para lidiar con esto, latexmk hace dos cosas: Primero, si latexmk descubre que el archivo .fls solo se ha generado en el directorio "incorrecto", entonces latexmk lo copia al directorio esperado, después de lo cual la operación de latexmk continúa correctamente independientemente del comportamiento de *latex. Segundo, permite que su idea del directorio "correcto" (o esperado) se configure mediante la variable $fls_uses_aux_dir. Por defecto es cero, para corresponder con el comportamiento actual de MiKTeX.

PERMITIR EL CAMBIO DEL TIPO DE ARCHIVO DE SALIDA

Cuando se ejecuta uno de los motores de latex, la situación habitual es que latex produce un archivo .dvi, mientras que pdflatex y lualatex producen un archivo .pdf. Para xelatex, el valor predeterminado es producir un archivo .pdf, pero para optimizar el tiempo de procesamiento, latexmk ejecuta xelatex con su opción -no-pdf para que produzca un archivo .xdv. El procesamiento posterior por parte de latexmk toma esto como punto de partida.

Sin embargo, el archivo de salida real puede diferir de la expectativa normal; y entonces latexmk puede ajustar su procesamiento para adaptarse a esta situación. La diferencia en el tipo de archivo de salida puede ocurrir por dos razones: Una es que para latex, pdflatex y lualatex el propio documento puede anular los valores predeterminados. La otra es que puede haber una configuración, o una configuración incorrecta, tal que el programa que latexmk invoca para compilar el documento no sea el esperado, o se le pasen opciones incompatibles con lo que latexmk espera inicialmente.

En latex y pdflatex, el control del formato de salida por parte del documento se realiza estableciendo el macro \pdfoutput. En lualatex, se utiliza el macro \outputmode en su lugar.

Un ejemplo de caso de uso importante para el control del formato de salida por parte del documento es un documento que utiliza el paquete psfrag para insertar elementos gráficos en el archivo de salida. El paquete psfrag logra sus efectos insertando código postscript en la salida de la compilación del documento. Esto implica el uso de la compilación a un archivo .dvi, seguido del uso de la conversión a un archivo postscript (ya sea directamente, como por dvips o implícitamente, como paso intermedio por dvipdf). Entonces es útil forzar la salida a ser del formato .dvi insertando \pdfoutput=0 en el preámbulo del documento.

Otro ejemplo es donde el documento utiliza archivos gráficos de los tipos .pdf, .jpg y png. Con la configuración predeterminada para el paquete graphicx, estos pueden procesarse en la compilación a .pdf pero no en la compilación a .dvi. En este caso, es útil insertar \pdfoutput=1 en el preámbulo del documento para forzar la compilación al formato de salida .pdf.

En todos estos casos, es necesario que latexmk ajuste su procesamiento para tratar con una discrepancia entre el formato de salida real (de .pdf, .dvi, .xdv) y el formato inicialmente esperado, si es posible. Latexmk lo hace siempre que se cumplan las siguientes condiciones.

La primera es que la variable de configuración $allow_switch de latexmk esté establecida en un valor distinto de cero, como es por defecto. Si esta variable es cero, una discrepancia de tipos de archivo en el resultado de la compilación provocará un error.

La segunda condición para que latexmk pueda manejar un cambio de tipo de salida es que no se realicen solicitudes explícitas de archivos de salida .dvi o .ps. Las solicitudes explícitas se realizan mediante las opciones -dvi y -ps, -print=dvi, -print=ps, -view=dvi y -view=ps, y mediante la configuración correspondiente de las variables de configuración $dvi_mode, $postscript_mode, $print_type y $view. Las restricciones de tipo de impresión y tipo de vista solo se aplican cuando se solicitan explícitamente la impresión y la visualización, respectivamente. Para este propósito, el uso de las opciones -pdfdvi y -pdfps (y la configuración correspondiente de la variable $pdf_mode) no cuenta como una solicitud explícita.

Nota que al acomodar un cambio en el tipo de archivo de salida, hay un cambio sustancial involucrado en la red de reglas que latexmk usa en sus acciones. La segunda condición aplicada para acomodar un cambio es evitar situaciones donde el cambio en la red de reglas sea demasiado radical para ser manejado fácilmente de forma automática.

ARCHIVOS DE CONFIGURACIÓN/INICIALIZACIÓN (RC)

En esta sección se explica qué archivos de configuración lee latexmk. Las secciones posteriores "Cómo establecer variables en archivos de inicialización", "Formato de las especificaciones de comandos", "Lista de variables de configuración utilizables en archivos de inicialización", "Dependencias personalizadas" y "Configuración avanzada" detallan qué se puede configurar y cómo.

Latexmk se puede personalizar utilizando archivos de inicialización, que se leen al inicio en el siguiente orden:

1) El archivo RC del sistema, si existe.
En un sistema UNIX, latexmk busca en los siguientes directorios un
archivo RC del sistema, que puede llamarse "LatexMk" o "latexmkrc". Los
directorios se buscan en el siguiente orden, y latexmk utiliza
el primer archivo de este tipo que encuentra (si lo hay):
"/etc",
"/opt/local/share/latexmk",
"/usr/local/share/latexmk",
"/usr/local/lib/latexmk".
En un sistema MS-Windows solo busca en "C:\latexmk".
En un sistema cygwin (es decir, un sistema MS-Windows en el que el Perl es el de cygwin), latexmk busca en los directorios
"/cygdrive/c/latexmk",
"/etc",
"/opt/local/share/latexmk",
"/usr/local/share/latexmk",
"/usr/local/lib/latexmk".

Si la variable de entorno LATEXMKRCSYS está establecida, su valor se usa como nombre del archivo RC del sistema, en lugar de cualquiera de los anteriores.

2) El archivo RC del usuario, si existe. Este puede estar en uno de dos lugares. El tradicional es ".latexmkrc" en el directorio personal del usuario. La otra posibilidad es "latexmk/latexmkrc" en el directorio de configuración XDG del usuario. El archivo que se lee es el primero de "$XDG_CONFIG_HOME/latexmk/latexmkrc" o "$HOME/.latexmkrc" que exista. (Ver https://specifications.freedesktop.org/basedir-spec/basedir-spec-latest.html para detalles sobre la Especificación del Directorio Base XDG.)

Aquí $HOME es el directorio personal del usuario. [Latexmk determina el directorio personal del usuario de la siguiente manera: Es el valor de la variable de entorno HOME, si esta variable existe, lo cual normalmente ocurre en sistemas tipo UNIX (incluidos Linux y OS-X). De lo contrario, se usa la variable de entorno USERPROFILE, si existe, lo cual normalmente ocurre en sistemas MS-Windows. De lo contrario, se usa una cadena vacía en lugar de $HOME, en cuyo caso latexmk no busca un archivo RC en él.]

$XDG_CONFIG_HOME es el valor de la variable de entorno XDG_CONFIG_HOME si existe. Si esta variable de entorno no existe, pero $HOME no está en blanco, entonces $XDG_CONFIG_HOME se establece al valor por defecto de $HOME/.config. De lo contrario, $XDG_CONFIG_HOME está en blanco, y latexmk no busca un archivo RC bajo él.

3) El archivo RC en el directorio de trabajo actual. Este archivo puede llamarse "latexmkrc" o ".latexmkrc", y el primero de estos que se encuentre se usa, si existe alguno.

4) Cualquier archivo RC especificado en la línea de comandos con la opción -r.

Cada archivo RC es una secuencia de comandos Perl. Naturalmente, un usuario puede usar esto de forma creativa. Pero para la mayoría de los propósitos, simplemente se usa una secuencia de sentencias de asignación que anulan algunas de las configuraciones integradas de Latexmk. Los casos sencillos se pueden manejar sin conocimiento del lenguaje Perl utilizando los ejemplos de este documento como plantillas. Las líneas de comentarios se introducen con el carácter "#".

Tenga en cuenta que las opciones de línea de comandos se obedecen en el orden en que están escritas; por lo tanto, cualquier archivo RC especificado en la línea de comandos con la opción -r puede anular opciones anteriores pero puede ser anulado por sí mismo por opciones posteriores en la línea de comandos. También existe la opción -e, que permite especificar código de inicialización en la línea de comandos de latexmk.

Para posibles ejemplos de código en un archivo RC, ver el directorio example_rcfiles en la distribución de latexmk (por ejemplo, en http://mirror.ctan.org/support/latexmk/example_rcfiles).

CÓMO ESTABLECER VARIABLES EN ARCHIVOS DE INICIALIZACIÓN

Las variables importantes que se pueden configurar se describen en la sección "Lista de variables de configuración utilizables en archivos de inicialización". (Ver la sección anterior "Archivos de configuración/inicialización (rc)" para los archivos donde se realizan las configuraciones.) La sintaxis para establecer estas variables es de las siguientes formas:

$bibtex = 'bibtex %O %S';

para establecer una variable de cadena,

$preview_mode = 1;

para establecer una variable numérica, y

@default_files = ('paper', 'paper1');

para establecer un array de cadenas. Es posible añadir un elemento a una variable de array de la siguiente manera:

push @default_files, 'paper2';

Tenga en cuenta que las variables "escalares" simples tienen nombres que comienzan con un carácter $ y las variables de array tienen nombres que comienzan con un carácter @. Cada sentencia termina con un punto y coma.

Las cadenas deben ir entre comillas simples. (Podría usar comillas dobles, como en muchos lenguajes de programación. Pero entonces el lenguaje de programación Perl introduce algunas reglas especiales para interpolar variables en cadenas. Las personas no fluidas en Perl querrán evitar estas complicaciones.)

Puede hacer cosas mucho más complicadas, pero para esto necesitará consultar un manual del lenguaje de programación Perl.

FORMATO DE LAS ESPECIFICACIONES DE COMANDOS

Algunas de las variables establecen los comandos que latexmk usa para llevar a cabo su trabajo, por ejemplo, para generar un archivo .dvi a partir de un archivo .tex o para ver un archivo postscript. Esta sección describe algunas características importantes de cómo se especifican los comandos. (Tenga en cuenta que algunas de las posibilidades enumeradas aquí no se aplican a la variable $kpsewhich; ver su documentación.)

Marcadores de posición: Suponga que desea que latexmk use el comando elatex en lugar del comando latex regular, y suponga además que desea darle la opción "--shell-escape". Podría hacerlo con la siguiente configuración:


$latex = 'elatex --shell-escape %O %S';

Los dos elementos que comienzan con el carácter % son marcadores de posición. Estos se sustituyen por valores apropiados antes de que se ejecute el comando. Por lo tanto, %S será reemplazado por el archivo fuente al que se aplicará el comando elatex, y %O será reemplazado por cualquier opción que latexmk haya decidido usar para este comando. (Por ejemplo, si usó la opción -silent en la invocación de latexmk, resulta en la sustitución de %O por "-interaction=batchmode".)

Los marcadores de posición disponibles son:

%A
nombre base del archivo tex principal. A diferencia de %R, este no se ve afectado por el ajuste de un nombre de trabajo mediante la opción -jobname o el valor de configuración $jobname.
%B
nombre base del archivo para el comando actual. Por ejemplo, si se está creando un archivo postscript document.ps a partir del archivo dvi document.dvi, entonces el nombre base es document.
%D
archivo de destino (por ejemplo, el nombre del archivo postscript al convertir un archivo dvi a postscript).
%O
opciones
%P
Si la variable $pre_tex_code no está vacía, entonces %P se sustituye por el contenido de $pre_tex_code seguido de \input{SOURCE}, donde SOURCE representa el nombre del archivo fuente. Se realiza el entrecomillado apropiado. Esto permite pasar código TeX a uno de los motores *latex para que se ejecute antes de leer el archivo fuente.

Si la variable $pre_tex_code es una cadena vacía, entonces %P es equivalente a %S.

%R
nombre base del archivo raíz.

Por defecto, este es el nombre base del archivo tex principal. Sin embargo, el valor puede ser cambiado por el uso de la opción -jobname o la variable de configuración $jobname. Este es entonces el nombre base para archivos como los archivos .aux y .log producidos al ejecutar *latex, así como para los archivos principales .dvi, .pdf, .ps y/o .xdvi.

%S
archivo fuente (por ejemplo, el nombre del archivo dvi al convertir un archivo .dvi a ps).
%T
El nombre del archivo tex principal.
%U
Si la variable $pre_tex_code no está vacía, entonces su valor se sustituye por %U (entrecomillado apropiadamente). De lo contrario, se reemplaza por una cadena nula.
%Y
Nombre del directorio para archivos de salida auxiliares (ver la variable de configuración $aux_dir). Se añade un carácter separador de directorio ('/') si $aux_dir no está vacío y no termina en un carácter adecuado, siendo los caracteres adecuados aquellos apropiados para UNIX y MS-Windows, es decir, ':', '/' y '\'. Tenga en cuenta que si, tras la inicialización, $out_dir está establecido, pero $aux_dir no está establecido (es decir, está en blanco), entonces latexmk establece $aux_dir al mismo valor que $out_dir.
%Z
Nombre del directorio para archivos de salida (ver la variable de configuración $out_dir). Se añade un carácter separador de directorio ('/') si $out_dir no está vacío y no termina en un carácter adecuado, siendo los caracteres adecuados aquellos apropiados para UNIX y MS-Windows, es decir, ':', '/' y '\'.

Si por alguna razón necesita un carácter % literal en su cadena que no esté sujeto a las reglas anteriores, use "%%".

Se aplicará el entrecomillado apropiado a las sustituciones de nombres de archivo, por lo que no debe proporcionarlo usted mismo, incluso si los nombres de sus archivos tienen espacios. (Pero si sus nombres de archivo TeX tienen espacios, tenga cuidado, ya que algunas versiones antiguas del programa TeX no pueden corregir

ly maneja nombres de archivo que contienen espacios.) En caso de que el cifrado de latexmk no funcione correctamente en su sistema, puede desactivarlo; consulte la documentación de la variable $quote_filenames.

Consulte los valores predeterminados en la sección "Lista de variables de configuración utilizables en archivos de inicialización" para ver cuál es normalmente el uso más apropiado.

Si omite proporcionar algún marcador de posición en la especificación de un comando, latexmk proporcionará lo que su autor considere apropiado por defecto. Esto proporciona compatibilidad con archivos de configuración de versiones anteriores de latexmk, que no utilizaban marcadores de posición.

"Desconexión" de un comando: Normalmente, cuando latexmk ejecuta un comando, espera a que el comando se complete. Esto es apropiado para comandos como latex, por supuesto. Pero para los previsualizadores, el comando normalmente debería ejecutarse de forma desconectada, de modo que latexmk ponga en marcha el previsualizador y luego vuelva a su siguiente tarea (o salga si no hay nada más que hacer). Para lograr este efecto de desconexión de un comando, debe preceder el nombre del comando con "start ", como en


$dvi_previewer = 'start xdvi %O %S';

Esto se traducirá a lo que sea apropiado para su sistema operativo.

Notas: (1) En algunas circunstancias, latexmk ejecutará siempre un comando de forma desconectada. Este es el caso de un previsualizador en modo continuo de previsualización, ya que de lo contrario previsualizar continuamente no tiene sentido. (2) Esto excluye la posibilidad de ejecutar un comando llamado start. (3) Si la palabra start aparece más de una vez al principio de la cadena del comando, es equivalente a tener solo una. (4) En cygwin, ocurren algunas complicaciones, ya que cygwin es una fusión complicada de UNIX y MS-Windows. Consulte el código fuente para ver cómo he manejado el problema.

Nombres de comandos que contienen espacios: En MS-Windows es común que el nombre de un comando incluya espacios, ya que el software a menudo se instala en un subdirectorio de "C:\Archivos de programa". Dichos nombres de comandos deben ir entre comillas dobles, como en


$lpr_pdf = '"c:/Program Files/Ghostgum/gsview/gsview32.exe" /p %S';
$pdf_previewer = 'start "c:/Program Files/SumatraPDF/SumatraPDF.exe" %O %S';
$pdf_previewer = 'start "c:/Program Files/SumatraPDF (x86)/SumatraPDF.exe" %O %S';

(Nota sobre el ejemplo anterior: En MS-Windows, las barras inclinadas hacia adelante son equivalentes a las barras invertidas en un nombre de archivo en casi todas las circunstancias, siempre que el nombre de archivo esté entre comillas dobles. Es más fácil usar barras inclinadas hacia adelante en ejemplos como el anterior, ya que así no hay que preocuparse por las reglas para tratar las barras inclinadas hacia adelante en cadenas en el lenguaje Perl.)

Nombres de comandos en Cygwin: Si latexmk es ejecutado por el Perl de Cygwin, asegúrese particularmente de que los nombres de ruta en los comandos tengan *barras inclinadas hacia adelante* y no las barras invertidas habituales como separador de componentes de nombres de ruta. Consulte los ejemplos anteriores. Las barras invertidas a menudo son malinterpretadas por el shell de Unix que utiliza el Perl de Cygwin para ejecutar comandos externos. Las barras inclinadas hacia adelante no sufren este problema y (cuando están entre comillas, como se mencionó anteriormente) son igualmente aceptables para MS-Windows.

Uso de asociaciones de archivos de MS-Windows: Un truco útil en las versiones modernas de MS-Windows (por ejemplo, WinXP) es usar simplemente el comando 'start' solo:


$dvi_previewer = 'start %S';

En MS-Windows, esto hará que se ejecute el programa que el sistema ha asociado con los archivos dvi. (Lo mismo se aplica a un visor de postscript y a un visor de pdf.) Pero tenga en cuenta que este truco no siempre es adecuado para el previsualizador de pdf, si su sistema tiene acroread como visor de pdf predeterminado. Como se explica en otra parte, acroread en MS-Windows no funciona bien con latex y latexmk, porque acroread bloquea el archivo pdf.

No usar un comando determinado: Si no se va a ejecutar un comando, se utiliza el nombre de comando NONE, como en


$lpr = 'NONE lpr';

Esto se usa típicamente cuando no existe un comando apropiado en su sistema. La cadena después de "NONE" es efectivamente un comentario.

Opciones para comandos: Establecer el nombre de un comando no solo se puede usar para cambiar el nombre del comando llamado, sino también para agregar opciones al comando. Suponga que desea que latexmk use latex con las opciones de fuente habilitadas. Entonces podría usar la siguiente línea en un archivo de inicialización:


$latex = 'latex --src-specials %O %S';

Ejecutar una subrutina en lugar de un comando externo: Use una especificación que comience con "internal", como en


$latex = 'internal mylatex %O %S';
sub mylatex {
my @args = @_;
# Posible preprocesamiento aquí
return system 'latex', @args;
}

Para algunas de las posibilidades más exóticas que se vuelven disponibles entonces, consulte la sección "Configuración avanzada: Algunos recursos adicionales y trucos avanzados". También consulte algunos de los ejemplos en el directorio example_rcfiles en la distribución de latexmk.

Trucos avanzados: Normalmente se especifica un solo comando para los comandos invocados por latexmk. Naturalmente, si hay algún procesamiento adicional complicado que necesite hacer en su situación especial, puede escribir un script (o archivo por lotes) para hacer el procesamiento, y luego configurar latexmk para usar su script en lugar del programa estándar.

También puede usar una subrutina de Perl en lugar de un script; consulte lo anterior. Esta es generalmente la solución más flexible y portable.

También es posible configurar latexmk para ejecutar múltiples comandos. Por ejemplo, si al ejecutar pdflatex para generar un archivo pdf a partir de un archivo tex necesita ejecutar otro programa después de pdflatex para realizar algún procesamiento adicional, podría hacer algo como:


$pdflatex = 'pdflatex --shell-escape %O %S; pst2pdf_for_latexmk %B';

Esta definición asume que está utilizando un sistema similar a UNIX (que incluye Linux y OS-X), de modo que los dos comandos que se ejecutarán están separados por el punto y coma en medio de la cadena.

Si está utilizando MS-Windows, reemplazaría la línea anterior por


$pdflatex = 'cmd /c pdflatex --shell-escape %O %S'
. '&& pst2pdf_for_latexmk %B';

Aquí, el separador de comandos de UNIX ; se reemplaza por &&. Además, hay un problema de que algunas versiones de Perl en MS-Windows no obedecen el separador de comandos; este problema se supera invocando explícitamente el procesador de línea de comandos de MS-Windows cmd.exe.

LISTA DE VARIABLES DE CONFIGURACIÓN UTILIZABLES EN ARCHIVOS DE INICIALIZACIÓN

En esta sección se especifican las variables cuyos valores se pueden ajustar para configurar latexmk. (Consulte la sección anterior "Archivos de configuración/inicialización (rc)" para ver los archivos donde se realizan las configuraciones.)

Los valores predeterminados se indican entre corchetes. Tenga en cuenta que para las variables que son booleanas, relativas a si latexmk se comporta o no de cierta manera, un valor distinto de cero, normalmente 1, indica verdadero, es decir, el comportamiento ocurre, mientras que un valor cero indica falso, es decir, el comportamiento no ocurre.

$allow_subdir_creation [1]

Especifica la acción a tomar cuando los mensajes en el archivo .log indican un fallo en un intento de compilación de *latex de escribir un archivo en un subdirectorio del directorio de salida porque el subdirectorio no existía.

Si el valor de $allow_subdir_creation es 0, no se toma ninguna acción. Si es 1, se crea el subdirectorio apropiado y se activa una nueva ejecución de *latex, pero solo si el archivo que se está escribiendo es un archivo .aux. (Esto ocurre, por ejemplo, si el documento incluye un archivo de un subdirectorio del directorio del documento, mediante el comando \include. Si el valor de $allow_subdir_creation es 2, entonces la creación del subdirectorio se realiza independientemente del tipo de archivo en cuestión.

$allow_switch [1]

Esto controla qué sucede cuando la extensión de salida de latex, pdflatex, lualatex o xelatex difiere de lo esperado. (Las extensiones posibles son .dvi, .pdf, .xdv.) Esto puede ocurrir con el uso de la macro \pdfoutput en un documento compilado bajo latex o pdflatex, o con el uso de la macro \outputmode bajo lualatex. También puede ocurrir con ciertos tipos de configuración incorrecta.

En tal caso, latexmk puede ajustar apropiadamente su red de reglas. El ajuste se realiza si $allow_switch está activado y si no se ha realizado ninguna solicitud de un archivo dvi o ps.

Consulte la sección PERMITIR CAMBIO DE EXTENSIÓN DE SALIDA.

$always_view_file_via_temporary [0]
Si los archivos .ps y .pdf se crearán inicialmente en un directorio temporal y luego se moverán a la ubicación final. (Esto se aplica a las operaciones de dvips, dvipdf y ps2pdf, y a los operadores de filtrado en archivos .dvi y .ps. No se aplica a pdflatex, desafortunadamente, ya que pdflatex no proporciona ninguna forma de especificar un nombre elegido para el archivo de salida.)

Este uso de un archivo temporal resuelve un problema: la creación de estos archivos puede llevar mucho tiempo. Si un visor (notablemente gv) detecta que el archivo ha cambiado, puede leer el nuevo archivo antes de que el programa que escribe el archivo haya terminado su trabajo, lo que puede causar estragos.

Consulte la variable $pvc_view_file_via_temporary para una configuración que se aplica solo si se utiliza el modo "preview-continuous" (opción -pvc). Consulte $tmpdir para configurar el directorio donde se crea el archivo temporal.

$analyze_input_log_always [1]

Después de una ejecución de latex (etc.), analizar siempre el .log en busca de archivos de entrada en las construcciones <...> y (...). De lo contrario, el análisis solo se realiza cuando el archivo fls no existe o está desactualizado.

En circunstancias normales, los datos en el archivo fls son confiables, y la prueba del archivo de registro genera muchos falsos positivos; por lo general, es mejor establecer $analyze_input_log_always en cero. Pero la prueba del archivo de registro es necesaria al menos en la siguiente situación: Cuando un usuario necesita persuadir a latexmk de que un cierto archivo es un archivo fuente, y latexmk no lo encuentra de otra manera. Entonces el usuario puede escribir código que haga que se escriba una línea con (...) en el archivo de registro. Un caso importante es para lualatex, que no siempre genera líneas en el archivo .fls para los archivos lua de entrada. (La situación con lualatex es ALTAMENTE dependiente de la versión, por ejemplo, hubo un gran cambio entre TeXLive 2016 y TeXLive 2017.)

Para mantener la compatibilidad con versiones anteriores de latexmk, el valor predeterminado es establecer $analyze_input_log_always a 1.

$auto_rc_use [1]
Si se deben leer automáticamente los archivos de inicialización (rc) estándar, que son el archivo RC del sistema, el archivo RC del usuario y el archivo RC en el directorio actual. La opción de línea de comandos -norc puede usarse para desactivar esta configuración. Cada archivo RC también podría desactivar esta configuración, es decir, podría establecer $auto_rc_use a cero para evitar la lectura automática de los archivos RC posteriores.

Esta variable no afecta la lectura de los archivos RC especificados en la línea de comandos por la opción -r.

$aux_dir [""]
El directorio aux, es decir, el directorio en el que se escribirán los archivos auxiliares (aux, log, etc.) durante una ejecución de *latex.

Si esta variable no está establecida, pero $out_dir está establecida, entonces latexmk toma el directorio aux como igual al directorio de salida, que es el directorio en el que se escribirán los archivos de salida finales.

Si ninguna de las variables está establecida, entonces el directorio actual al invocar *latex se utiliza tanto para los directorios aux como para los de salida.

Si los directorios aux y de salida son distintos, entonces el directorio aux contiene todos los archivos generados con la excepción de los "archivos de salida finales", que se definen como archivos .dvi, .ps, .pdf, .synctex y .synctex.gz.

Ver la sección DIRECTORIOS AUXILIARES Y DE SALIDA para más detalles.

$aux_out_dir_report [0]
Si esta variable se establece en 1, entonces antes del procesamiento de cada archivo .tex principal, se listan la configuración de los directorios aux y de salida, después de haber sido normalizadas a partir de la configuración especificada durante la inicialización.

Este informe proporciona un recordatorio de dónde buscar los archivos generados.

El informe se realiza por archivo .tex principal, debido a los posibles cambios de directorio para cada archivo (cuando se usa la opción -cd). En los casos más simples, los nombres de los directorios son los mismos que los especificados originalmente. Pero en general se realiza alguna limpieza/normalización; esto ayuda al rendimiento y limpia la salida a la pantalla.

Si esta variable se establece en 2, entonces se detiene después de informar la configuración de los directorios aux y de salida, en lugar de continuar con el procesamiento de los archivos tex. Esta configuración se utiliza principalmente para depurar problemas de configuración. Ver la opción -dir-report-only.

$bad_warning_is_error [0]
Si las advertencias incorrectas reportadas por *latex en el archivo de registro se tratan como errores. Las especificaciones de los mensajes de advertencia se encuentran en @bad_warnings.
@bad_warnings
Matriz de expresiones regulares que especifican mensajes en el archivo de registro que son tratados oficialmente como advertencias en lugar de errores por *latex, pero que un usuario puede tratar como errores: Ver $bad_warning_is_error.

Actualmente, el conjunto predeterminado de estas advertencias son las relativas a \end que ocurren dentro de construcciones.

$banner [0]
Si es distinto de cero, el mensaje de banner se imprime en cada página al convertir el archivo dvi a postscript. Sin modificar la variable $banner_message, esto es equivalente a especificar la opción -d.

Tenga en cuenta que si $banner es distinto de cero, se asume el modo $postscript_mode y el archivo postscript se genera siempre, incluso si es más reciente que el archivo dvi.

$banner_intensity [0.95]
Equivalente a la opción -bi, este es un número decimal entre 0 y 1 que especifica qué tan oscuro se imprime el mensaje de banner. 0 es negro, 1 es blanco. El valor predeterminado es el correcto si su cartucho de tóner no se está agotando demasiado.
$banner_message ["DRAFT"]
El mensaje de banner que se imprimirá en cada página al convertir el archivo dvi a postscript. Esto es equivalente a la opción -bm.
$banner_scale [220.0]
Un número decimal que especifica qué tan grande se imprimirá el mensaje de banner. La experimentación es necesaria para obtener la escala correcta para su mensaje, como regla general la escala debe ser aproximadamente igual a 1100 dividido por el número de caracteres en el mensaje. El valor predeterminado es el correcto para mensajes de 5 caracteres. Esto es equivalente a la opción -bs.
@BIBINPUTS
Esta es una variable de matriz, ahora en gran parte obsoleta, que especifica los directorios donde latexmk debe buscar los archivos .bib. Por predeterminado, se establece a partir de la variable de entorno BIBINPUTS del sistema operativo. Si esa variable de entorno no está establecida, se establece una lista de un solo elemento que consiste en el directorio actual. El formato de los nombres de los directorios depende de su sistema operativo, por supuesto. Ejemplos de cómo establecer esta variable son:


@BIBINPUTS = ( ".", "C:\\bibfiles" );
@BIBINPUTS = ( ".", "\\server\bibfiles" );
@BIBINPUTS = ( ".", "C:/bibfiles" );
@BIBINPUTS = ( ".", "//server/bibfiles" );
@BIBINPUTS = ( ".", "/usr/local/texmf/bibtex/bib" );

Tenga en cuenta que en MS Windows, se puede usar una barra inclinada '/' o una barra invertida '\' para separar los componentes de la ruta, por lo que los dos primeros y los dos últimos ejemplos son equivalentes. Cada barra invertida debe duplicarse para evitar problemas con las reglas de Perl para escribir cadenas. En general, es más sencillo usar siempre barras inclinadas en lugar de barras invertidas.

Nota importante: Esta variable ahora está en gran parte obsoleta en la versión actual de latexmk, ya que ahora utiliza un método mejor para buscar archivos utilizando el comando kpsewhich. Sin embargo, si su sistema es inusual y no tiene el comando kpsewhich, es posible que necesite establecer la variable @BIBINPUTS.

$biber ["biber %O %S"]
El programa de procesamiento de biber.
$biber_silent_switch ["--onlylog"]
Interruptor(es) para el programa de procesamiento de biber cuando el modo silencioso está activado.
$bibtex ["bibtex %O %S"]
El programa de procesamiento de BibTeX.
$bibtex_fudge [1]
Al usar bibtex, si se debe cambiar de directorio a $aux_dir antes de ejecutar bibtex.

La necesidad surge de la siguiente manera:

a. Con bibtex antes de aproximadamente 2019, si el nombre de archivo que se le da contiene un componente de ruta, había un error que hacía que bibtex no encontrara archivos aux adicionales, como los generados por el comando \include en TeX.

b. Con todas las versiones moderadamente recientes de bibtex, bibtex puede negarse a escribir sus archivos bbl y blg, por razones de seguridad, para ciertos casos del componente de ruta del nombre de archivo que se le da.

Sin embargo, también hay casos raros en los que el método de cambio de directorio impide que bibtex encuentre ciertos archivos bib o bst. Entonces $bibtex_fudge necesita establecerse en 0.

$bibtex_silent_switch ["-terse"]
Interruptor(es) para el programa de procesamiento de BibTeX cuando el modo silencioso está activado.
$bibtex_use [1]
Bajo qué condiciones ejecutar bibtex o biber. Cuando latexmk descubre por el archivo de registro que se usan una o más bibliografías generadas por bibtex/biber, puede ejecutar bibtex o biber siempre que parezca necesario regenerar los archivos bbl a partir de sus archivos de base de datos bib de origen. Pero a veces, los archivos bib no están disponibles (por ejemplo, para un documento obtenido de un archivo externo), pero los archivos bbl se proporcionan. En ese caso, el uso de bibtex o biber resultará en la sobrescritura incorrecta de los preciosos archivos bbl. La variable $bibtex_use controla si esto sucede, y también controla si los archivos .bbl se eliminan o no en una operación de limpieza.

Los valores posibles de $bibtex_use son:
0: nunca usar bibtex o biber; nunca eliminar archivos .bbl en una limpieza.
1: usar bibtex o biber solo si los archivos bib existen; nunca
eliminar archivos .bbl en una limpieza.
1.5: usar bibtex o biber solo si los archivos bib existen;
eliminar condicionalmente los archivos .bbl en una limpieza (es decir, eliminarlos solo cuando
todos los archivos bib existan).
2: ejecutar bibtex o biber siempre que parezca necesario actualizar los archivos bbl, sin verificar la existencia de los archivos bib; siempre eliminar los archivos .bbl en una limpieza.

Nota: Cuando se está utilizando biber, el uso condicional de biber puede ser problemático. Desde el punto de vista de latexmk, el problema es que, debido a cómo funciona biber, solo se puede obtener un conocimiento completo de sus archivos fuente después de ejecutar biber. En contraste, para bibtex, la información completa sobre qué archivos bib se utilizan se obtiene del archivo .aux después de una ejecución de *latex. Pero para biber, la información correspondiente es algo incompleta; esta es la información obtenida en el archivo .bcf que genera el paquete biblatex durante una ejecución de *latex.

$cleanup_includes_cusdep_generated [0]
Si es distinto de cero, especifica que la limpieza también elimina los archivos que son generados por dependencias personalizadas. (Al realizar una limpieza, por ejemplo, mediante el uso de la opción -C, las dependencias personalizadas son las listadas en el archivo .fdb_latexmk de una ejecución anterior.)
$cleanup_includes_generated [0]
Si es distinto de cero, especifica que la limpieza también elimina los archivos que se detectan en el archivo fls (o en su defecto, en el archivo de registro) como generados. También incluirá archivos hechos a partir de estos archivos generados de primera generación.

Esta operación es algo peligrosa y puede tener consecuencias no deseadas, ya que los archivos a eliminar se determinan a partir de un archivo creado por *latex, que puede contener información errónea. Por lo tanto, esta variable está desactivada por defecto, y luego los archivos a eliminar se restringen a aquellos especificados explícitamente por patrones configurados en las variables clean_ext, clean_full_ext y @generated_exts. Los casos estándar (por ejemplo, archivos .log) aparecen en el valor inicial de latexmk para la matriz @generated_exts.

$clean_ext [""]
Extensiones adicionales de archivos para que latexmk elimine cuando se selecciona alguna de las opciones de limpieza (-c o -C). El valor de esta variable es una cadena que contiene las extensiones separadas por espacios.

También es posible especificar un patrón más general de archivo a eliminar, utilizando el marcador de posición %R, como en los comandos, y también es posible usar comodines. Por lo tanto, al establecer


$clean_ext = "out %R-blx.bib %R-figures*.log pythontex-files-%R/*";

La mayoría de los archivos que se van a eliminar son relativos al directorio especificado por $aux_dir. $clean_ext = "pythontex-files-%R/* pythontex-files-%R";

$compiling_cmd [""], $failure_cmd [""], $warning_cmd [""], $success_cmd [""]

Estas variables especifican comandos que se ejecutan en ciertos puntos de las compilaciones. Una motivación para su existencia es permitir indicaciones visuales convenientes y muy útiles del estado de la compilación, incluso cuando la ventana que recibe la salida de la compilación está oculta. Esto es particularmente útil en el modo continuo de vista previa.

Los comandos se ejecutan en los siguientes puntos: $compiling_cmd al inicio de la compilación, $success_cmd al final de una compilación completamente exitosa, $failure_cmd al final de una compilación no exitosa, $warning_cmd al final de una compilación por lo demás exitosa que presenta advertencias sobre citas o referencias no definidas o sobre referencias definidas múltiples veces. Si alguna de las variables anteriores no está definida o está en blanco (situación por defecto), entonces el comando correspondiente no se ejecuta.

Sin embargo, cuando $warning_cmd no está configurada, en el caso de una compilación con advertencias sobre referencias o citas, pero sin ningún otro error, se utiliza uno u otro de $success_cmd o $failure_cmd (si está configurado) según la configuración de $warnings_as_errors.

Un ejemplo de configuración sencilla de estas variables es el siguiente


$compiling_cmd = "xdotool search --name \"%D\" set_window --name \"%D compilando\"";
$success_cmd = "xdotool search --name \"%D\" set_window --name \"%D OK\"";
$warning_cmd = "xdotool search --name \"%D\" ".
"set_window --name \"%D PROBLEMA CITA/REFERENCIA\"";
$failure_cmd = "xdotool search --name \"%D\" set_window --name \"%D FALLO\"";

Estos asumen que el programa xdotool está instalado, que el visor está utilizando un sistema de ventanas X para la visualización, y que el título de la ventana contiene el nombre del archivo mostrado, como normalmente lo hace. Cuando se ejecutan los comandos, la cadena comodín %D se reemplaza por el nombre del archivo de destino, que es el archivo que se está previsualizando. Los comandos anteriores resultan en una cadena apropiada que se añade al nombre de archivo en el título de la ventana: " compilando", " OK", o " FALLO".

Otros comodines que se pueden usar son %S, %T y %R, siendo %S y %T normalmente idénticos. Estos pueden ser útiles para un comando que cambia el título de la ventana del editor. La indicación visual en el título de una ventana puede ser útil, ya que el usuario no tiene que desviar constantemente la atención a la ventana de compilación (posiblemente oculta) para conocer el estado de la compilación.

Las situaciones más complicadas se manejan mejor definiendo una subrutina Perl para invocar los comandos necesarios, y utilizando la palabra clave "internal" en las definiciones para que la subrutina sea invocada. (Ver la sección "Formato de las Especificaciones de Comandos" para saber cómo hacerlo.)

Naturalmente, las configuraciones anteriores que invocan el programa xdotool solo son aplicables cuando se utiliza el sistema de ventanas X para las ventanas relevantes. Para otros casos, tendrá que encontrar qué soluciones de software están disponibles.

$filetime_causality_threshold [5]
El uso de esta variable es el siguiente: En varios lugares, latexmk necesita determinar si un archivo particular ha sido producido durante una ejecución recién concluida de alguna regla/programa o si es un remanente de una ejecución anterior. (Un ejemplo es la producción de un archivo .bcf por el paquete biblatex durante una ejecución de *latex para proporcionar información bibliográfica al programa biber. Si no se produce un archivo .bcf durante una ejecución actual de *latex, sino que es un remanente de una ejecución anterior, entonces latexmk tiene que concluir que el documento .tex ha cambiado de tal manera que biber ya no debe usarse.)

El criterio de Latexmk para que un archivo haya sido producido durante una ejecución es que la hora de modificación del archivo sea más reciente que la hora del sistema al comienzo de la ejecución. Básicamente, si la hora de modificación es anterior a esto, entonces es un remanente de una ejecución anterior. Sin embargo, un uso ingenuo del criterio puede, entre otras cosas, chocar con la granularidad de cómo se almacenan las horas de los archivos en algunos sistemas de archivos, lo que significa que es posible que la hora informada por el sistema de archivos para un archivo sea un segundo o más anterior a la hora de modificación real, siendo la diferencia exacta bastante aleatoria.

La variable $fi letime_causality_threshold permite una apropiada laxitud en el uso de la hora de modificación de archivos por parte de latexmk. Puede ser bastante generoso; simplemente debe ser inferior a la escala de tiempo en la que un usuario humano realiza cambios en los archivos fuente de un documento (o en los archivos de configuración, etc).

Este uso de @generated_exts es normalmente irrelevante, dada la precisión habitual de las otras formas en que latexmk determina estos archivos generados.

añade la extensión "end" a la lista de extensiones generadas predefinidas. (Esta extensión es utilizada por el paquete RevTeX, por ejemplo.)

%hash_calc_ignore_pattern
!!!Esta variable es solo para expertos!!!

La regla general que latexmk utiliza para determinar cuándo se necesita una ejecución adicional de algún programa es que uno de los archivos fuente ha cambiado. Pero considere, por ejemplo, un paquete de latex que causa la creación de un archivo postscript encapsulado (un archivo "eps") que se va a leer en la siguiente ejecución. El archivo contiene una línea de comentario que indica su fecha y hora de creación. En la siguiente ejecución, la hora cambia, latex ve que el archivo eps ha cambiado y, por lo tanto, vuelve a ejecutar latex. Esto causa un bucle infinito, que solo se interrumpe porque latexmk tiene un límite en el número de ejecuciones para proteger contra situaciones patológicas.

Pero la línea cambiante no tiene ningún efecto real, ya que es un comentario. Puede instruir a latex para que ignore la línea problemática de la siguiente manera:


$hash_calc_ignore_pattern{'eps'} = '^%%CreationDate: ';

Esto crea una regla para archivos con la extensión .eps sobre las líneas a ignorar. El lado izquierdo es un modismo de Perl para establecer un elemento en un hash. Tenga en cuenta que la extensión del archivo se especifica sin un punto. El valor, en el lado derecho, es una cadena que contiene una expresión regular. (Consulte la documentación de Perl sobre cómo especificarla en general.) Esta expresión regular en particular especifica que las líneas que comienzan con "%%CreationDate: " deben ignorarse al decidir si un archivo de la extensión dada .eps ha cambiado.

Solo hay una expresión regular disponible para cada extensión. Si necesita más de un patrón para especificar las líneas a ignorar, entonces necesita combinar los patrones en una única expresión regular. El método más sencillo es separar los diferentes patrones simples mediante un carácter de barra vertical (que indica "alternancia" en la jerga de las expresiones regulares). Por ejemplo,


$hash_calc_ignore_pattern{'eps'} = '^%%CreationDate: |^%%Title: ';

hace que las líneas que comienzan con "^%%CreationDate: " o "^%%Title: " se ignoren.

Puede suceder que un patrón a ignorar se especifique en, por ejemplo, un archivo de inicialización del sistema o del usuario, y desee eliminarlo en un archivo que se lee más tarde. Para hacer esto, usa la función delete de Perl, por ejemplo,


delete $hash_calc_ignore_pattern{'eps'};

Si no está establecido, entonces si $warnings_as_errors es distinto de cero y $failure_cmd está establecido, entonces se usa $failure_cmd. De lo contrario, se usa $success_cmd, si está establecido. DEPENDENCIAS PERSONALIZADAS

En cualquier archivo RC, se puede configurar un conjunto de dependencias personalizadas para convertir un archivo con una extensión a un archivo con otra. Un ejemplo de uso sería permitir que latexmk convierta un archivo .fig a .eps para ser incluido en el archivo .tex.

Definición de una dependencia personalizada:

El método antiguo de configurar latexmk para usar una dependencia personalizada era manipular directamente el array @cus_dep_list que contiene información que define las dependencias personalizadas. (Consulte la sección "Método Antiguo de Definición de Dependencias Personalizadas" para obtener detalles.) Este método todavía funciona, pero ya no se prefiere.

Un método mejor es utilizar las subrutinas que permiten manipulaciones convenientes de la lista de dependencias personalizadas. Estas son:


add_cus_dep( fromextension, toextension, must, subroutine )
remove_cus_dep( fromextension, toextension )
show_cus_dep()

Los argumentos son los siguientes:

extensión de origen (from extension):
La extensión del archivo del que estamos convirtiendo (p. ej., "fig"). Se especifica sin el punto.
extensión de destino (to extension):
La extensión del archivo al que estamos convirtiendo (p. ej., "eps"). Se especifica sin el punto.
obligatorio (must):
Si es distinto de cero, el archivo del que estamos convirtiendo **debe** existir; si no existe, latexmk mostrará un mensaje de error y saldrá, a menos que se especifique la opción -f. Si must es cero y el archivo del que estamos convirtiendo no existe, entonces no se toma ninguna acción. Generalmente, el valor apropiado de must es cero.
función (function):
El nombre de la subrutina que latexmk debe llamar para realizar la conversión del archivo. El primer argumento para la subrutina es el nombre base del archivo a convertir sin ninguna extensión. Las subrutinas se declaran en la sintaxis de Perl. La función debe devolver 0 si tuvo éxito y un número distinto de cero si falló.

Naturalmente, add_cus_dep agrega una dependencia personalizada con las extensiones de origen y destino especificadas. Si una dependencia personalizada ya se ha definido previamente (p. ej., en un rcfile que se leyó anteriormente), entonces se reemplaza por la nueva.

La subrutina remove_cus_dep elimina la dependencia personalizada especificada. La subrutina show_cus_dep hace que se envíe una lista de las dependencias personalizadas actualmente definidas a la salida de pantalla.

Cómo se utilizan las dependencias personalizadas:

Se crea una instancia de una regla de dependencia personalizada cada vez que latexmk detecta que una ejecución de *latex necesita leer un archivo, como un archivo gráfico, cuya extensión es la extensión de destino de una dependencia personalizada. Entonces latexmk examina si existe un archivo con el mismo nombre, pero con la extensión de origen correspondiente, tal como se especifica en la dependencia personalizada. Si lo hace, entonces se crea una instancia correspondiente de la dependencia personalizada, después de lo cual la regla se invoca cada vez que el archivo de destino (el de extensión de destino) está desactualizado con respecto al archivo de origen correspondiente.

Para crear el nuevo archivo de destino, se invoca la subrutina Perl especificada en la regla, con un argumento que es el nombre base de los archivos en cuestión. Los casos simples solo implican una subrutina que invoca un programa externo; esto se puede hacer siguiendo las plantillas a continuación, incluso por aquellos sin conocimiento del lenguaje de programación Perl. Por supuesto, los expertos podrían hacer algo mucho más elaborado.

Un elemento en la especificación de cada regla de dependencia personalizada, etiquetado como "obligatorio" (must) arriba, especifica cómo se debe aplicar la regla cuando el archivo de origen no existe.

Cuando latex informa que un archivo de entrada (p. ej., un archivo gráfico) no existe, latexmk intenta encontrar un archivo de origen y una dependencia personalizada que puedan usarse para crearlo. Si tiene éxito, entonces crea una instancia de la dependencia personalizada y la invoca para crear el archivo faltante, después de lo cual la siguiente pasada de latex, etc., podrá leer el archivo recién creado.

Nota para uso avanzado: La variable de entorno del sistema operativo TEXINPUTS se puede utilizar para especificar una ruta de búsqueda para encontrar archivos por latex, etc. De manera correspondiente, cuando se informa de un archivo faltante, latexmk busca en los directorios especificados en TEXINPUTS, así como en el directorio actual, para encontrar un archivo de origen a partir del cual se pueda usar una instancia de una dependencia personalizada para crear el archivo faltante.

Función para implementar dependencia personalizada, método tradicional:

La función que implementa una dependencia personalizada obtiene la información sobre los archivos a procesar de dos maneras. La primera es a través de su único argumento; el argumento contiene el nombre base de los archivos de origen y destino. La segunda manera se describe más adelante.

Un ejemplo simple y típico de código en un archivo rc de inicialización que utiliza el primer método es:


add_cus_dep( 'fig', 'eps', 0, 'fig2eps' );
sub fig2eps {
system( "fig2dev -Leps \"$_[0].fig\" \"$_[0].eps\"" );
}

La primera línea agrega una dependencia personalizada que convierte un archivo con la extensión "fig", tal como lo crea el programa xfig, a un archivo PostScript encapsulado, con la extensión "eps". Las líneas restantes definen una subrutina que realiza la conversión. Si ya existe una regla para convertir archivos de "fig" a "eps" (p. ej., de un archivo de inicialización leído previamente), latexmk eliminará esta regla antes de crear la nueva.

Supongamos que latexmk está utilizando esta regla para convertir un archivo "figura.fig" a "figura.eps". Luego invocará la subrutina fig2eps definida en el código anterior con un solo argumento "figura", que es el nombre base de cada uno de los archivos (posiblemente con un componente de ruta). Este argumento se hace referencia como $_[0] en Perl. En el ejemplo anterior, la subrutina utiliza el comando system de Perl para invocar el programa fig2dev. Los ficheros de inicialización de latexmk pueden contener definiciones de dependencias personalizadas. Estas definen cómo crear un tipo de fichero a partir de otro tipo de fichero. Por ejemplo, podrías querer que latexmk convierta automáticamente los ficheros PostScript con extensión .ps a ficheros PDF con extensión .pdf. Esto se puede conseguir con la siguiente definición:


add_cus_dep( 'ps', 'pdf', 0, 'ps2pdf' );
sub ps2pdf {
return system( "ps2pdf $_[0].ps $_[0].pdf" );
}

La función add_cus_dep tiene cuatro argumentos:

  • El primer argumento es la extensión del fichero de origen (sin el punto). En el ejemplo, es 'ps'.
  • El segundo argumento es la extensión del fichero de destino (sin el punto). En el ejemplo, es 'pdf'.
  • El tercer argumento es un número que indica si la dependencia es "obligatoria" (must). Si es 1, entonces la dependencia se considera siempre necesaria. Si es 0, entonces la dependencia sólo se considera necesaria si el fichero de destino no existe. El valor 0 es lo normal.
  • El cuarto argumento es el nombre de la subrutina de Perl que realiza la conversión. En el ejemplo, es 'ps2pdf'.

La subrutina ps2pdf es una subrutina de Perl estándar. Se le pasa como argumento el nombre base del fichero (sin extensión) que se está procesando. Así, si latexmk necesita crear foo.pdf a partir de foo.ps, llamará a ps2pdf('foo'). La subrutina puede entonces usar el nombre base para construir los nombres de los ficheros de entrada y salida. Por ejemplo, para crear foo.pdf a partir de foo.ps, la subrutina debe ejecutar un comando del sistema como ps2pdf foo.ps foo.pdf.

En el ejemplo anterior, la subrutina ps2pdf usa la función de Perl system() para ejecutar un comando externo. La subrutina devuelve el valor devuelto por system(). Si el valor devuelto es distinto de cero, entonces latexmk asumirá que ocurrió un error durante la ejecución de la subrutina. En el ejemplo anterior, no se da un valor de retorno explícito, y en su lugar el valor de retorno es el valor devuelto por la última (y única) declaración, es decir, la invocación de system, que devuelve el valor 0 en caso de éxito.

Si usa pdflatex, lualatex o xelatex en lugar de latex, entonces probablemente preferirá convertir sus ficheros gráficos al formato pdf, en cuyo caso reemplazaría el código anterior en un fichero de inicialización por:


add_cus_dep( 'fig', 'pdf', 0, 'fig2pdf' );
sub fig2pdf {
return system( "fig2dev -Lpdf \"$_[0].fig\" \"$_[0].pdf\"" );
}

Nota 1: En las líneas de comando dadas en los comandos de sistema en los ejemplos anteriores, se han insertado comillas dobles alrededor de los nombres de fichero (implementado por '\"' en el lenguaje Perl). Estas inmunizan la ejecución del programa contra caracteres especiales en los nombres de fichero. Muy a menudo estas comillas no son necesarias, es decir, se pueden omitir. Pero normalmente es más seguro mantenerlas. A pesar de que las reglas para las comillas varían entre sistemas operativos, shells de comandos y software individual, las comillas en los ejemplos anteriores no causan problemas en los casos que he probado.

Nota 2: Un caso en el que las comillas son importantes es cuando los ficheros están en un subdirectorio y su sistema operativo es Microsoft Windows. Entonces el carácter separador de componentes de directorio puede ser una barra inclinada '/' o la barra invertida '\' más común de Microsoft. Las barras inclinadas las genera latexmk, para mantener su cordura frente a software como MiKTeX que mezcla ambos separadores de directorio; pero su uso correcto normalmente requiere nombres de fichero entre comillas. (Vea un fichero de registro de una ejecución de MiKTeX (al menos en la v. 2.9) para un ejemplo del uso de ambos separadores de directorio.)

Nota 3: Las subrutinas que implementan dependencias personalizadas en los ejemplos dados solo tienen una línea que invoca un programa externo. Esa es la situación usual. Pero dado que las subrutinas están en el lenguaje Perl, puede implementar un procesamiento mucho más complicado si lo necesita.

Eliminar dependencias personalizadas, y cuándo podría necesitar hacerlo:

Si tiene algunas dependencias personalizadas generales definidas en el fichero de inicialización del sistema o del usuario, puede encontrar que para un proyecto en particular son indeseables. Así que podría querer eliminar las innecesarias. Una situación en la que esto sería deseable es cuando hay múltiples dependencias personalizadas con la misma extensión de origen o la misma extensión de destino. En ese caso, latexmk podría elegir una diferente de la que usted quiere para un proyecto específico. Como ejemplo, para eliminar cualquier regla de "fig" a "eps" usaría:


remove_cus_dep( 'fig', 'eps' );

Si tiene conjuntos complicados de dependencias personalizadas, puede que quiera obtener una lista de las dependencias personalizadas. Esto se hace usando la línea


show_cus_dep();

en un fichero de inicialización.

Función que implementa dependencia personalizada, métodos alternativos:

Hasta ahora los ejemplos de funciones para implementar dependencias personalizadas han usado el argumento de la función para especificar el nombre base del fichero convertido. Este método ha estado disponible desde versiones muy antiguas de latexmk, y se pueden encontrar muchos ejemplos, por ejemplo, en la web.

Sin embargo en versiones posteriores de latexmk la estructura interna de la implementación de sus "reglas" para los pasos de procesamiento, incluyendo dependencias personalizadas, se volvió mucho más potente. La función que implementa una dependencia personalizada se ejecuta dentro de un contexto especial donde se definen una serie de variables y subrutinas adicionales. Las documentadas públicamente, destinadas a ser estables a largo plazo, se enumeran a continuación, bajo el encabezado "Variables y subrutinas para procesar una regla".

Ejemplos de su uso se dan en los siguientes ejemplos, que conciernen a múltiples ficheros de índice y glosarios.

La única conversión de fichero de índice incorporada en latexmk es de un fichero .idx escrito en una ejecución de *latex a un fichero .ind que se leerá en una ejecución posterior. Pero con el paquete index.sty, por ejemplo, puedes crear índices adicionales con extensiones que tú configures. Latexmk no sabe cómo deducir las extensiones a partir de la información que tiene. Pero puedes escribir fácilmente una dependencia personalizada. Por ejemplo si tu fichero latex usa el comando "\newindex{special}{ndx}{nnd}{Special index}" necesitarás que latexmk convierta ficheros con la extensión .ndx a .nnd. El método más elemental es definir una dependencia personalizada de la siguiente manera:


add_cus_dep( 'ndx', 'nnd', 0, 'ndx2nnd' );
sub ndx2nnd {
return system( "makeindex -o \"$_[0].nnd\" \"$_[0].ndx\"" );
}
push @generated_exts, 'ndx', 'nnd';

Nota el añadido de la línea comparado con ejemplos anteriores. La línea adicional añade las extensiones "ndx" y "nnd" a la lista de extensiones para los ficheros generados; entonces los ficheros de índice adicionales serán eliminados por las operaciones de limpieza.

Pero si tienes aún más índices con extensiones aún diferentes, por ejemplo, "adx" y "and", entonces necesitarás una función separada para cada par de extensiones. Esto es bastante molesto. Puedes usar la función Run_subst para simplificar las definiciones y usar una única función:


add_cus_dep( 'ndx', 'nnd', 0, 'dx2nd' );
add_cus_dep( 'adx', 'and', 0, 'dx2nd' );
sub dx2nd {
return Run_subst( "makeindex -o %D %S" );
}
push @generated_exts, 'ndx', 'nnd', 'adx', 'and';

También podrías en su lugar usar


add_cus_dep( 'ndx', 'nnd', 0, 'dx2nd' );
add_cus_dep( 'adx', 'and', 0, 'dx2nd' );
sub dx2nd {
return Run_subst( $makeindex );
}
push @generated_exts, 'ndx', 'nnd', 'adx', 'and';

Este último ejemplo usa la especificación de comando en $makeindex, y por lo tanto cualquier personalización que hayas hecho para el índice estándar también se aplica a tus índices adicionales.

Técnicas similares se pueden aplicar para los glosarios.

Aquellos de ustedes con experiencia en Makefiles, pueden preocuparse de que el fichero .ndx se escriba durante una ejecución de *latex y sea siempre posterior al .nnd leído por última vez. Por lo tanto el .nnd parece estar perpetuamente desactualizado. Esta situación, de dependencias circulares, es endémica de latex, y es uno de los problemas que latexmk está programado para superar. Examina el contenido de los ficheros (mediante un checksum), y solo rehace cuando el contenido del fichero ha cambiado realmente.

Por supuesto si eliges escribir datos aleatorios en el .nnd (o en el fichero .aux, etc.) que cambian en cada nueva ejecución, entonces tendrás un problema. Para expertos reales: Ver el patrón %hash_calc_ignore_pattern si tienes que lidiar con tales problemas.

Método antiguo de definición de dependencias personalizadas:

En versiones mucho más antiguas de latexmk, el único método para definir dependencias personalizadas era manipular directamente la tabla de dependencias personalizadas. Esta está contenida en el array @cus_dep_list. Es un array de cadenas, y cada cadena en el array tiene cuatro elementos, cada uno separado por un espacio, la extensión de origen, la extensión de destino, el elemento "obligatorio" (must), y el nombre de la subrutina para la dependencia personalizada. Todos estos se definieron anteriormente.

Un ejemplo del método antiguo de definición de dependencias personalizadas es el siguiente. Es el código en un fichero RC para asegurar la conversión automática de ficheros .fig a ficheros .eps:


push @cus_dep_list, "fig eps 0 fig2eps";
sub fig2eps {
return system( "fig2dev -Lps \"$_[0].fig\" \"$_[0].eps\"" );
}

Este método todavía funciona, y es casi equivalente al código dado anteriormente que usaba la subrutina add_cus_dep. Sin embargo, el método antiguo no elimina ninguna dependencia personalizada previa para la misma conversión. Por lo tanto, el nuevo método es preferible.

Variables y subrutinas para procesar una regla

Un paso en el procesamiento se llama una regla. Una posibilidad para implementar el procesamiento de una regla es mediante una subrutina Perl. Este es siempre el caso para las dependencias personalizadas. Además, para cualquier otra regla, puedes usar una subrutina prefijando la especificación del comando con la palabra "internal" -- ver la sección FORMATO DE LAS ESPECIFICACIONES DE COMANDOS.

Cuando usas una subrutina para procesar una regla, todas las posibilidades de la programación Perl están disponibles, por supuesto. Además, algunas de las variables y subrutinas internas de latexmk están disponibles. Las que se enumeran a continuación están destinadas a estar disponibles para usuarios (avanzados), y sus especificaciones generalmente tendrán estabilidad bajo las actualizaciones. $rule
Esta variable tiene el nombre de la regla, tal como lo conoce latexmk. Tenga en cuenta que el contenido exacto de esta variable para una regla dada puede depender de la versión de latexmk.
$$Pbase
Esto proporciona el nombre base para la regla. Generalmente, determina los nombres de los archivos generados. Por ejemplo, para una ejecución de *latex, el nombre del archivo .log es el directorio auxiliar concatenado con el nombre base y luego `.log'.

Para una regla de *latex, el nombre base no tiene componente de directorio. Para otras reglas, incluye el componente de directorio (si se utiliza alguno).

Esta (molesta) diferencia está asociada con las diferentes formas en que funcionan los comandos invocados por latexmk cuando la línea de comandos incluye un nombre de archivo fuente que incluye un componente de directorio. Para los comandos *latex, el directorio del archivo fuente es irrelevante para el componente de directorio de los archivos generados, que en cambio está determinado por los valores en las opciones -aux-directory y/o -output-directory.

En contraste, muchos otros programas (por ejemplo, biber, bibtex) colocan sus archivos generados en el mismo directorio que el archivo fuente, simplemente con una extensión cambiada.

El segundo signo de dólar desreferencia la referencia para dar el valor real. (Una referencia se utiliza de manera similar a un puntero, y la `P' (por `pointer') al principio del nombre de la variable es una convención utilizada en latexmk para indicar que la variable es una variable de referencia.)

$$Psource

Dado que la subrutina mmz_analyze se ha definido en el archivo rc.

add_hook( 'after_main_pdf', sub{ print "TEST\n"; return 0; } );

ensure_path( var, valores ...)

El primer parámetro es el nombre de una de las variables de entorno del sistema para rutas de búsqueda. Los parámetros restantes son valores que deben estar en la variable. Para cada uno de los parámetros de valor, si aún no está en la variable, se antepone a la variable; en ese caso, la variable de entorno se creará si aún no existe. Para separar valores, se utiliza el carácter apropiado para el sistema operativo; consulte la variable de configuración $search_path_separator.

Ejemplo:


ensure_path( 'TEXINPUTS', './custom_cls_sty_files//' );

(En este ejemplo, el `//' final está documentado por los sistemas TeX para significar que *latex busca archivos en el directorio especificado y en todos sus subdirectorios).

Técnicamente, ensure_path funciona estableciendo la variable de Perl $ENV{var}, donde var es el nombre de la variable de destino. El valor modificado se pasa como una variable de entorno a cualquier programa invocado.

popd()

Realizan exactamente la misma función que los comandos del mismo nombre en los shells de comandos del sistema operativo como bash en Unix y cmd.exe en Windows.

rdb_add_generated( archivo, ... )
Esta subrutina debe usarse en el contexto de una regla, es decir, desde dentro de una subrutina que está llevando a cabo el procesamiento de una regla. Tal es el caso de la subrutina que implementa una dependencia personalizada, o la subrutina invocada mediante el uso de la palabra clave "internal" en la especificación del comando, como en la variable $latex.

Sus argumentos son una secuencia de nombres de archivo que se generan durante la ejecución de la regla. Los nombres pueden surgir de un análisis de los resultados de la ejecución, por ejemplo, en un archivo de registro, o del conocimiento de las propiedades de la regla específica. Llamar a rdb_add_generated con estos nombres de archivo asegura que estos archivos se marquen como generados por la regla en las estructuras de datos internas de latexmk. Básicamente, no se toma ninguna acción si los archivos ya se han marcado como generados.

Un propósito principal de usar esta subrutina es para la situación en la que un archivo generado es también el archivo fuente para alguna regla, de modo que latexmk pueda vincular correctamente la información de dependencia en su red de reglas.

Nota: A diferencia de otras subrutinas en esta sección, no hay argumento para una regla para rdb_add_generated. En su lugar, la subrutina debe invocarse durante el procesamiento de una regla cuando latexmk ha configurado un contexto apropiado (es decir, variables apropiadas). En contraste, las subrutinas con un argumento de regla también se pueden usar fuera de un contexto de regla.

rdb_ensure_file( $regla, archivo )
Esta subrutina asegura que el archivo dado esté entre los archivos fuente para la regla especificada. Se utiliza típicamente cuando, durante el procesamiento de una regla, se sabe que un archivo adicional en particular está entre las dependencias que latexmk debería conocer, pero sus métodos predeterminados no encuentran la dependencia. Casi siempre el primer argumento es el nombre de la regla que se está procesando actualmente, por lo que es apropiado especificarlo mediante $rule.

Para ver ejemplos de su uso, consulte algunos de los archivos en el directorio example_rcfiles de la distribución de latexmk. Actualmente, los casos que utilizan esta subrutina son bib2gls-latexmkrc, exceltex_latexmkrc y texinfo-latexmkrc. Estos ilustran casos típicos en los que el procesamiento normal de latexmk no detecta ciertos archivos fuente adicionales.

Tenga en cuenta que rdb_ensure_file solo tiene un argumento de nombre de archivo, a diferencia de otras subrutinas en esta sección. Si desea aplicar su acción a varios archivos, necesitará una llamada a rdb_ensure_file por cada archivo.

rdb_ensure_files_here( archivo, ... )
Similar a la subrutina rdb_ensure_files, excepto que (a) asume que el contexto es el de una regla y los archivos se agregarán a la lista fuente para esa regla; (b) se permiten múltiples archivos.
rdb_remove_files( $regla, archivo, ... )
Esta subrutina elimina uno o más archivos de la lista de dependencias para la regla dada.
rdb_remove_generated( archivo, ... )
Esta subrutina debe usarse en el contexto de una regla, es decir, desde dentro de una subrutina que está llevando a cabo el procesamiento de una regla. Realiza la acción opuesta a rdb_add_generated. Su efecto es asegurar que los nombres de archivo dados no se listen en las estructuras de datos internas de latexmk como generados por la regla.
rdb_list_source( $regla )
Esta subrutina devuelve la lista de archivos fuente (es decir, la lista de dependencias) para la regla dada.
rdb_set_source( $regla, archivo, ... )
rdb_set_source( $regla, @archivos )
Esta subrutina establece la lista de dependencias para la regla dada a los archivos especificados. Los archivos que ya están en la lista tienen información sin cambios. Los archivos que no estaban en la lista se agregan a ella. Los archivos de la lista de dependencias anterior que no están en la lista de archivos recién especificada se eliminan de la lista de dependencias.
Run_subst( especificación_comando )
Esta subrutina ejecuta el comando especificado por especificación_comando. La especificación es una cadena en el formato que se enumera en la sección "Formato de las especificaciones de comandos". Una acción importante de Run_subst es realizar sustituciones de marcadores de posición, por ejemplo, %S y %D para archivos de origen y destino; estos se sustituyen antes de que se ejecute el comando. Además, el comando después de la sustitución se imprime en la pantalla a menos que latexmk se esté ejecutando en modo silencioso.
test_gen_file_time ( <archivo> )
Esta subrutina se utiliza en el contexto de una regla. Devuelve verdadero o falso según si un archivo con el nombre dado existe y fue generado en la última ejecución de la regla. Si la subrutina devuelve falso, pero el archivo existe, entonces el archivo es un remanente de una ejecución anterior.

La prueba para determinar si un archivo se generó en la ejecución actual es si la hora de modificación del archivo es al menos tan reciente como la hora en que

t la ejecución de la regla se inició. Se tiene en cuenta la posibilidad de la granularidad de los valores de la hora de modificación en los sistemas de archivos. Consulte la descripción de la variable $filetime_causality_threshold para más detalles.

Además, latexmk tiene en cuenta la posibilidad de que los archivos estén alojados en un ordenador diferente al que ejecuta latexmk y que las horas del reloj del sistema en los dos ordenadores no coincidan. Latexmk detecta automáticamente (e informa) cualquier discrepancia significativa y la corrige.

Configuración coordinada de comandos para *latex

Para configurar $dvilualatex, $hilatex, $latex, $pdflatex, $lualatex y $xelatex con un patrón común, puede utilizar una de las siguientes subrutinas: std_tex_cmds, alt_tex_cmds y set_tex_cmds.

Para obtener los comandos estándar, utilice


&std_tex_cmds;

Esto resulta en $latex = 'latex %O %S', y de forma similar para $dvilualatex, $hilatex, $pdflatex, $lualatex y $xelatex. Tenga en cuenta el ampersand (&) en la invocación; esto indica a Perl que se está llamando a una subrutina. (El uso de esta subrutina le permite anular redefiniciones previas de las variables $latex, etc., que podrían haber ocurrido en un archivo rc leído anteriormente).

Para poder utilizar la cadena proporcionada por la opción -pretex (si existe), puede utilizar


&alt_tex_cmds;

Esto resulta en $latex = 'latex %O %P', etc. Nuevamente, tenga en cuenta el ampersand (&) en la invocación; esto indica a Perl que se está llamando a una subrutina.

Una forma más general de especificar las variables es utilizando


set_tex_cmds( 'CMD_SPEC' );

Aquí CMD_SPEC es la línea de comandos sin el nombre del programa. Esto resulta en $latex = 'latex CMD_SPEC', y de forma similar para $pdflatex, etc. (No es necesario un ampersand (&) delante del nombre de la subrutina aquí, ya que los paréntesis indican a Perl que se está invocando una subrutina).

Un ejemplo que proporciona la opción --interaction=batchmode a los comandos *latex sería


set_tex_cmds( '--interaction=batchmode %O %S' );

Esto resulta en $latex = 'latex --interaction=batchmode %O %S ', etc. Tenga en cuenta que cuando '%O' aparece después de la opción añadida, como aquí, las opciones proporcionadas en la línea de comandos a latexmk pueden anular la proporcionada.

Se puede configurar una línea de comandos más general utilizando el marcador de posición '%C' en CMD_SPEC. El '%C' se sustituye por el nombre básico del comando, es decir, cualquiera de 'latex', 'pdflatex', etc., que sea apropiado. (Se permite más de una ocurrencia de '%C'). Por ejemplo, para utilizar las versiones de desarrollo/pre-lanzamiento de latex, etc., que tienen nombres como 'latex-dev', 'pdflatex-dev', etc., podría utilizar


set_tex_cmds( '%C-dev %O %S' );

Esto resulta en $latex = 'latex-dev %O %S', etc. (Los programas de pre-lanzamiento latex-dev, etc., se proporcionan en las distribuciones actuales de TeXLive y MiKTeX).

Ganchos (Hooks)

Latexmk proporciona una forma de organizar subrutinas definidas por el usuario para que se llamen en ciertos puntos del procesamiento. Estas pueden utilizarse para configurar un comportamiento y acciones apropiados más allá del comportamiento normal de latexmk. Para un buen ejemplo de cómo se pueden utilizar para adaptar el comportamiento de latexmk a paquetes específicos, consulte el archivo memoize_latexmkrc en el subdirectorio example_rcfiles de la distribución de latexmk. (En una instalación estándar de TeXLive, ese subdirectorio se encuentra en texmf-dist/doc/support/latexmk/)

El mecanismo de ganchos es complementario al método de redefinición de cadenas de comandos como $pdflatex, etc. Los dos métodos tienen dominios de utilidad superpuestos.

Tenga en cuenta que el mecanismo de ganchos se hace público por primera vez en la versión 4.84 de latexmk. Está sujeto a cambios y mejoras a medida que se adquiera experiencia.

Los ganchos se organizan en pilas de ganchos con nombre, y una subrutina de gancho se añade a una pila dada mediante la subrutina add_hook de latexmk (documentada anteriormente). Las pilas disponibles actualmente son las siguientes, enumeradas en el orden aproximado en que se encuentran en el procesamiento de un documento:


before_xlatex

Las subrutinas de esta pila de ganchos se llaman justo antes de que se ejecute un
programa *latex.

after_xlatex

Las subrutinas de esta pila de ganchos se llaman después de que se ejecute un programa *latex. Antes de que se llamen las subrutinas, latexmk ha realizado un postprocesamiento inmediato, por ejemplo, para mover el archivo pdf generado del directorio aux
al directorio de salida cuando $emulate_aux está configurado a 1.

after_xlatex_analysis

Las subrutinas de esta pila de ganchos se llaman después de que latexmk ha realizado su análisis de dependencias tras la ejecución de un programa *latex. Las subrutinas de esta
pila proporcionan una forma útil de añadir elementos a la información de dependencias
asociada a paquetes particulares y que latexmk no
maneja automáticamente.

after_main_pdf

Las subrutinas de esta pila de ganchos se llaman después de que una de las reglas que
crea el archivo pdf del documento. (Esto incluye pdflatex, lualatex,
dvipdf, ps2pdf, xdvipdfmx).

cleanup

Las subrutinas de esta pila de ganchos se llaman siempre que latexmk está a punto
de realizar una operación de limpieza. Pueden utilizarse, por ejemplo, para adaptar los
archivos eliminados a las peculiaridades de paquetes particulares cuando los
mecanismos generales de latexmk para especificar los archivos a eliminar son demasiado inflexibles.


Estas subrutinas se llaman antes de que latexmk realice ninguna de sus propias eliminaciones de archivos;
por lo tanto, las subrutinas de gancho tienen acceso a todos los archivos generados
que proporcionan información específica del paquete.


cleanup_extra_full

Las subrutinas de esta pila de ganchos se llaman además de las de
la pila de limpieza, siempre que se vaya a realizar una operación de limpieza completa (es decir,
una que incluya los archivos pdf, ps, etc.). Se llaman inmediatamente
después de las de la pila de limpieza, pero aún antes de que latexmk realice ninguna de
sus propias eliminaciones de archivos.

(Cualquier otra pila definida en latexmk.pl pero no listada anteriormente debe considerarse experimental y sujeta a cambios).

Cada subrutina debe devolver 0 en caso de éxito y un valor distinto de cero en caso de fallo. Esto coincide con la convención utilizada para ejecutar programas, por ejemplo, mediante la subrutina system de Perl, y la convención coincidente utilizada para subrutinas de dependencias personalizadas en latexmk.

Para la mayoría de las pilas de ganchos, las subrutinas se llaman en el contexto de una regla, con variables como $rule definidas. Sin embargo, algunas pilas de ganchos, como las de limpieza, se llaman desde fuera de cualquier regla; y latexmk ajusta las variables relevantes para que se refieran a la tarea general (es decir, al procesamiento de un archivo .tex principal particular).

Configuración avanzada: Uso de latexmk con make

Esta sección está dirigida únicamente a usuarios avanzados que utilizan el programa make para proyectos complejos, como el desarrollo de software, con las dependencias especificadas por un Makefile.

Ahora bien, la tarea básica de latexmk es ejecutar los programas apropiados para crear una versión visualizable de un documento LaTeX. Sin embargo, el programa make habitual no es adecuado para este propósito por al menos dos razones. La primera es que el uso de LaTeX implica dependencias circulares (por ejemplo, a través de archivos .aux), y estas no pueden ser manejadas por el programa make estándar. La segunda es que en un documento grande, el conjunto de archivos fuente puede cambiar con bastante frecuencia, especialmente con archivos gráficos incluidos; en esta situación, mantener un Makefile actualizado manualmente es inapropiado y propenso a errores, especialmente cuando las dependencias se pueden determinar automáticamente. Latexmk resuelve ambos problemas de forma robusta.

Por lo tanto, para muchos documentos LaTeX estándar, latexmk puede utilizarse por sí solo sin el programa make. En un proyecto complejo, simplemente necesita ser configurado adecuadamente. Una configuración estándar sería definir dependencias personalizadas para crear archivos gráficos a partir de sus archivos fuente (por ejemplo, como los creados por el programa xfig). Las dependencias personalizadas son el equivalente de latexmk a las reglas de patrones en los Makefiles.

Sin embargo, hay proyectos para los que un Makefile es apropiado, y es útil saber cómo usar latexmk desde un Makefile. Un ejemplo típico sería generar documentación para un proyecto de software. Potencialmente, la interacción con el resto de las reglas en el Makefile podría ser bastante complicada, por ejemplo, si algunos de los archivos fuente de un documento LaTeX son generados por el software del proyecto.

En esta sección, doy un par de ejemplos de cómo latexmk puede invocarse de manera útil desde un Makefile. Los ejemplos utilizan características específicas de las versiones actuales de GNU make, que es la predeterminada tanto en sistemas linux como en OS-X. Pueden requerir modificaciones para otras versiones de make.

El método más sencillo es simplemente delegar todas las tareas relevantes a latexmk, como es adecuado para un documento LaTeX sencillo. Para esto, un Makefile adecuado es como


.PHONY : FORCE_MAKE
all : try.pdf
%.pdf : %.tex FORCE_MAKE
latexmk -pdf -dvi- -ps- $<

(Nota: ¡la última línea debe ir precedida por una tabulación para que el Makefile funcione correctamente!) Naturalmente, si hacer try.pdf a partir de su archivo LaTeX asociado try.tex fuera la única tarea a realizar, un uso directo de latexmk sin un Makefile sería normalmente mejor. El beneficio de usar un Makefile para un documento LaTeX sería en un proyecto más grande, donde líneas como la anterior solo serían una pequeña parte de un Makefile más grande.

CUSTOM DEPENDENCIES

The following is an example of how to use make to manage dependencies between LaTeX files and graphics files.

As a starting point, consider a Makefile that just contains a pattern rule for making a .pdf file from a .tex file, and it is defined to use latexmk in the obvious way. There is a conventional default target named "all", with a prerequisite of try.pdf. So when make is invoked, by default it makes try.pdf. The only complication is that there may be many source files beyond try.tex, but these aren't specified in the Makefile, so changes in them will not by themselves cause latexmk to be invoked. Instead, the pattern rule is equipped with a "phony" prerequisite FORCE_MAKE; this has the effect of causing the rule to be always out-of-date, so that latexmk is always run. It is latexmk that decides whether any action is needed, e.g., a rerun of pdflatex. Effectively the Makefile delegates all decisions to latexmk, while make has no knowledge of the list of source files except for primary LaTeX file for the document. If there are, for example, graphics files to be made, these must be made by custom dependencies configured in latexmk.

But something better is needed in more complicated situations, for example, when the making of graphics files needs to be specified by rules in the Makefile. To do this, one can use a Makefile like the following:


TARGETS = document1.pdf document2.pdf
DEPS_DIR = .deps
LATEXMK = latexmk -recorder -use-make -deps \
-e 'warn qq(In Makefile, turn off custom dependencies\n);' \
-e '@cus_dep_list = ();' \
-e 'show_cus_dep();'
all : $(TARGETS)
$(foreach file,$(TARGETS),$(eval -include $(DEPS_DIR)/$(file)P))
$(DEPS_DIR) :
mkdir $@
%.pdf : %.tex
if [ ! -e $(DEPS_DIR) ]; then mkdir $(DEPS_DIR); fi
$(LATEXMK) -pdf -dvi- -ps- -deps-out=$(DEPS_DIR)/$@P $<
%.pdf : %.fig
fig2dev -Lpdf $< $@

(Again, the lines containing the commands for the rules should be started with tabs.) This example was inspired by how GNU automake handles automatic dependency tracking of C source files.

After each run of latexmk, dependency information is put in a file in the .deps subdirectory. The Makefile causes these dependency files to be read by make, which now has the full dependency information for each target .pdf file. To make things less trivial it is specificed that two files document1.pdf and document2.pdf are the targets. The dependency files are .deps/document1.pdfP and .deps/document2.pdfP.

There is now no need for the phony prerequisite for the rule to make .pdf files from .tex files. But I have added a rule to make .pdf files from .fig files produced by the xfig program; these are commonly used for graphics insertions in LaTeX documents. Latexmk is arranged to output a dependency file after each run. It is given the -recorder option, which improves its detection of files generated during a run of pdflatex; such files should not be in the dependency list. The -e options are used to turn off all custom dependencies, and to document this. Instead the -use-make is used to delegate the making of missing files to make itself.

Suppose in the LaTeX file there is a command \includegraphics{graph}, and an xfig file "graph.fig" exists. On a first run, pdflatex reports a missing file, named "graph". Latexmk succeeds in making "graph.pdf" by calling "make graph.pdf", and after completion of its work, it lists "fig.pdf" among the dependents of the file latexmk is making. Then let "fig.fig" be updated, and then let make be run. Make first remakes "fig.pdf", and only then reruns latexmk.

Thus we now have a method by which all the subsidiary processing is delegated to make.

Escaping of characters in dependency lists: There are certain special characters that need to be escaped when names of files and directories containing them appear in a dependency list used by a make program. Generally, such special characters are best avoided.

By default, latexmk does no escaping of this kind, and the user will have to arrange to deal with the issue separately, if the relevant special characters are used. Note that the rules for escaping depend on which make program is used, and on its version.

One special case is of spaces, since those are particularly prevalent, notably in standard choices of name for a user's home directory. So latexmk does provide an option to escape spaces. See the option -deps_escape=... and the variable $deps_escape for details.

NON_ASCII CHARACTERS IN FILENAMES, RC FILES, ETC

Modern operating systems and file systems allow non-ASCII characters in the names of files and directories that encompass the full Unicode range. Mostly, latexmk deals with these correctly. However, there are some situations in which there are problems, notably on Microsoft Windows. Prior to version 4.77, latexmk had problems with non-ASCII filenames on Windows, even though there were no corresponding problems on macOS and Linux. These problems are corrected in the present version.

BUGS (SELECTED)

Sometimes a viewer (gv) tries to read an updated .ps or .pdf file after its creation is started but before the file is complete. Work around: manually refresh (or reopen) display. Or use one of the other previewers and update methods.

(The following isn't really a bug, but concerns features of previewers.) Preview continuous mode only works perfectly with certain previewers: Xdvi on UNIX/Linux works for dvi files. Gv on UNIX/Linux works for both postscript and pdf. Ghostview on UNIX/Linux needs a manual update (reopen); it views postscript and pdf. Gsview under MS-Windows works for both postscript and pdf, but only reads the updated file when its screen is refreshed. Acroread under UNIX/Linux views pdf, but the file needs to be closed and reopened to view an updated version. Under MS-Windows, acroread locks its input file and so the pdf file cannot be updated. (Remedy: configure latexmk to use sumatrapdf instead.)
