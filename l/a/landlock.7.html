Landlock(7) Manual de Información Miscelánea Landlock(7)

NOMBRE

Landlock - control de acceso no privilegiado

DESCRIPCIÓN

Landlock es un sistema de control de acceso que permite a cualquier proceso restringirse a sí mismo y a sus futuros hijos de forma segura. Debido a que Landlock es un Módulo de Seguridad de Linux (LSM) apilable, hace posible crear sandboxes de seguridad seguros como nuevas capas de seguridad además de los controles de acceso existentes a nivel de sistema. Este tipo de sandbox se espera que ayude a mitigar el impacto de seguridad de los bugs y comportamientos inesperados o maliciosos en las aplicaciones.

Una política de seguridad Landlock es un conjunto de derechos de acceso (por ejemplo, abrir un archivo en solo lectura, crear un directorio, etc.) asociados a una jerarquía de archivos. Dicha política puede ser configurada y aplicada por los procesos para sí mismos usando tres llamadas al sistema:

•
landlock_create_ruleset(2) crea un nuevo conjunto de reglas;
•
landlock_add_rule(2) agrega una nueva regla a un conjunto de reglas;
•
landlock_restrict_self(2) aplica un conjunto de reglas al hilo que la llama.

Para poder usar estas llamadas al sistema, el kernel en ejecución debe ser compatible con Landlock y debe estar habilitado al arrancar.

Reglas de Landlock

Una regla de Landlock describe una acción sobre un objeto que el proceso pretende realizar. Un conjunto de reglas se agrega en un conjunto de reglas, que luego puede restringir el hilo que lo aplica, y sus futuros hijos.

Los dos tipos de reglas existentes son:

Reglas del sistema de archivos
Para estas reglas, el objeto es una jerarquía de archivos, y las acciones del sistema de archivos relacionadas se definen con derechos de acceso al sistema de archivos.
Reglas de red (desde ABI v4)
Para estas reglas, el objeto es un puerto TCP, y las acciones relacionadas se definen con derechos de acceso a la red.

Acciones del sistema de archivos

Estos indicadores permiten restringir un proceso sandbox a un conjunto de acciones sobre archivos y directorios. Los archivos o directorios abiertos antes del sandboxing no están sujetos a estas restricciones. Ver landlock_add_rule(2) y landlock_create_ruleset(2) para más contexto.

Los siguientes derechos de acceso se aplican solo a archivos:

LANDLOCK_ACCESS_FS_EXECUTE
Ejecutar un archivo.
LANDLOCK_ACCESS_FS_WRITE_FILE
Abrir un archivo con acceso de escritura.
Al abrir archivos para escritura, a menudo necesitarás adicionalmente el derecho LANDLOCK_ACCESS_FS_TRUNCATE. En muchos casos, estas llamadas al sistema truncan los archivos existentes al sobrescribirlos (por ejemplo, creat(2)).
LANDLOCK_ACCESS_FS_READ_FILE
Abrir un archivo con acceso de lectura.
LANDLOCK_ACCESS_FS_TRUNCATE
Truncar un archivo con truncate(2), ftruncate(2), creat(2), o open(2) con O_TRUNC.
Este derecho de acceso está disponible desde la tercera versión de la interfaz ABI de Landlock.

Si un archivo abierto puede ser truncado con ftruncate(2) o usado con ioctl(2) se determina durante open(2), de la misma manera que los permisos de lectura y escritura se verifican durante open(2) usando LANDLOCK_ACCESS_FS_READ_FILE y LANDLOCK_ACCESS_FS_WRITE_FILE.

Un directorio puede recibir derechos de acceso relacionados con archivos o directorios. El siguiente derecho de acceso se aplica al propio directorio y a los directorios debajo de él:

LANDLOCK_ACCESS_FS_READ_DIR
Abrir un directorio o listar su contenido.

Sin embargo, los siguientes derechos de acceso solo se aplican al contenido de un directorio, no al directorio en sí:

LANDLOCK_ACCESS_FS_REMOVE_DIR
Eliminar un directorio vacío o renombrarlo.
LANDLOCK_ACCESS_FS_REMOVE_FILE
Desvincular (o renombrar) un archivo.
LANDLOCK_ACCESS_FS_MAKE_CHAR
Crear (o renombrar o enlazar) un dispositivo de caracteres.
LANDLOCK_ACCESS_FS_MAKE_DIR
Crear (o renombrar) un directorio.
LANDLOCK_ACCESS_FS_MAKE_REG
Crear (o renombrar o enlazar) un archivo regular.
LANDLOCK_ACCESS_FS_MAKE_SOCK
Crear (o renombrar o enlazar) un socket de dominio UNIX.
LANDLOCK_ACCESS_FS_MAKE_FIFO
Crear (o renombrar o enlazar) una tubería con nombre.
LANDLOCK_ACCESS_FS_MAKE_BLOCK
Crear (o renombrar o enlazar) un dispositivo de bloque.
LANDLOCK_ACCESS_FS_MAKE_SYM
Crear (o renombrar o enlazar) un enlace simbólico.
LANDLOCK_ACCESS_FS_REFER
Enlazar o renombrar un archivo desde o hacia un directorio diferente (es decir, reparentar una jerarquía de archivos).
Este derecho de acceso está disponible desde la segunda versión de la interfaz ABI de Landlock.
Este es el único derecho de acceso que es denegado por defecto por cualquier conjunto de reglas, incluso si el derecho no se especifica como manejado en el momento de la creación del conjunto de reglas. La única forma de que un conjunto de reglas otorgue este derecho es permitirlo explícitamente para un directorio específico agregando una regla coincidente al conjunto de reglas.
En particular, al usar la primera versión de la interfaz ABI de Landlock, Landlock siempre denegará los intentos de reparentar archivos entre diferentes directorios.
Además de que los directorios de origen y destino tengan el derecho de acceso LANDLOCK_ACCESS_FS_REFER, la operación de enlace o renombramiento intentada debe cumplir las siguientes restricciones:
•
El archivo reparentado no puede obtener más derechos de acceso en el directorio de destino de los que tenía previamente en el directorio de origen. Si se intenta esto, la operación resulta en un error EXDEV.
•
Al enlazar o renombrar, el derecho LANDLOCK_ACCESS_FS_MAKE_* para el tipo de archivo respectivo debe ser otorgado para el directorio de destino. De lo contrario, la operación resulta en un error EACCES.
•
Al renombrar, el derecho LANDLOCK_ACCESS_FS_REMOVE_* para el tipo de archivo respectivo debe ser otorgado para el directorio de origen. De lo contrario, la operación resulta en un error EACCES.
Si no se cumplen múltiples requisitos, el código de error EACCES tiene precedencia sobre EXDEV.

El siguiente derecho de acceso se aplica tanto a archivos como a directorios:

LANDLOCK_ACCESS_FS_IOCTL_DEV
Invocar comandos ioctl(2) en un dispositivo de caracteres o bloque abierto.

NAME

landlock - Linux Landlock sandboxing API

SYNOPSIS

#include <linux/landlock.h>
long syscall(SYS_landlock_create_ruleset,
             const struct landlock_ruleset_attr *attr,
             size_t attr_size,
             __u32 flags);
long syscall(SYS_landlock_add_rule,
             int ruleset_fd,
             __u32 rule_type,
             const void *rule_data,
             __u32 flags);
long syscall(SYS_landlock_restrict_self,
             int ruleset_fd,
             __u32 flags);

Link with -llandlock (part of libsandbox).

DESCRIPTION

Landlock is a security module in the Linux kernel that allows unprivileged processes to restrict their own capabilities and the capabilities of their children. It operates by creating a security policy, called a ruleset, which consists of rules. A ruleset can then be applied to the calling thread using landlock_restrict_self(2). Once applied, the ruleset cannot be removed, and only additional restrictions can be added by descendant processes (although not necessarily enforced if the descendant process is in a different Landlock domain).

Landlock policies are granular and operate on file system accesses and network accesses. The policies are defined using rules.

Ruleset creation

A ruleset is created using the landlock_create_ruleset(2) system call. The system call takes a pointer to a struct landlock_ruleset_attr, which specifies the types of operations that the ruleset will handle. The available operations are defined by flags like:

LANDLOCK_ACCESS_FS_EXECUTE
Allow or deny executing files.
LANDLOCK_ACCESS_FS_WRITE_FILE
Allow or deny writing to files.
LANDLOCK_ACCESS_FS_READ_FILE
Allow or deny reading from files.
LANDLOCK_ACCESS_FS_READ_DIR
Allow or deny reading directories.
LANDLOCK_ACCESS_FS_REMOVE_DIR
Allow or deny removing directories.
LANDLOCK_ACCESS_FS_REMOVE_FILE
Allow or deny removing files.
LANDLOCK_ACCESS_FS_MAKE_CHAR
Allow or deny creating character special files.
LANDLOCK_ACCESS_FS_MAKE_DIR
Allow or deny creating directories.
LANDLOCK_ACCESS_FS_MAKE_REG
Allow or deny creating regular files.
LANDLOCK_ACCESS_FS_MAKE_SOCK
Allow or deny creating UNIX domain sockets.
LANDLOCK_ACCESS_FS_MAKE_FIFO
Allow or deny creating FIFO special files.
LANDLOCK_ACCESS_FS_MAKE_BLOCK
Allow or deny creating block special files.
LANDLOCK_ACCESS_FS_MAKE_SYM
Allow or deny creating symbolic links.
LANDLOCK_ACCESS_FS_REFER
Allow or deny referencing files (e.g. hard links, renames).
LANDLOCK_ACCESS_FS_TRUNCATE
Allow or deny truncating files.
LANDLOCK_ACCESS_NET_BIND_TCP
Allow or deny binding to TCP sockets.
LANDLOCK_ACCESS_NET_CONNECT_TCP
Allow or deny connecting to TCP sockets.
LANDLOCK_ACCESS_FS_IOCTL_DEV
Allow or deny performing ioctl() on device files.
LANDLOCK_SCOPE_ABSTRACT_UNIX_SOCKET
Restrict operations on abstract namespace UNIX domain sockets.
LANDLOCK_SCOPE_SIGNAL
Restrict the ability to send signals.

The attr.handled_access_fs field specifies which filesystem access rights the ruleset will handle. The rules added later must be a subset of these handled accesses.

The attr.handled_access_net field specifies which network access rights the ruleset will handle. The rules added later must be a subset of these handled accesses.

The attr.exempt_vpdirfd field specifies a directory file descriptor that will be exempt from Landlock restrictions. This can be used to allow access to specific parts of the filesystem, e.g. for accessing kernel file systems like procfs or sysfs. Note that this exemption applies to the entire ruleset, not just to specific rules.

Ruleset updates

Rules can be added to a ruleset using the landlock_add_rule(2) system call. This call takes a file descriptor to an existing ruleset, the type of rule to add, and a pointer to the rule data. The supported rule types are:

LANDLOCK_RULE_PATH_BENEATH
This rule restricts access to a directory and all files and directories underneath it. The rule data is a pointer to a struct landlock_path_beneath_attr. This structure contains a file descriptor to the directory (parent_fd) and a bitmask of allowed filesystem access rights (allowed_access).
LANDLOCK_RULE_LANDSizes
This rule restricts operations on files based on their size. The rule data is a pointer to a struct landlock_fs_size_attr. This structure contains a maximum size (max_size) and minimum size (min_size) for files that are allowed to be accessed.
LANDLOCK_RULE_PROG
This rule restricts the execution of programs. The rule data is a pointer to a struct landlock_prog_attr. This structure contains a file descriptor to an executable file (prog_fd) and a bitmask of allowed program execution attributes (attrs).

When a rule is added, the requested access rights must be a subset of the rights specified in attr.handled_access_fs or attr.handled_access_net when the ruleset was created. If an access right is not explicitly allowed by any rule, it is denied.

Applying the ruleset

A ruleset is applied to the calling thread using the landlock_restrict_self(2) system call. This call takes a file descriptor to the ruleset and flags. Once this system call is made, the thread and all its future children are subject to the restrictions imposed by the ruleset. Landlock domains are cumulative; if a thread is already in a Landlock domain, applying a new ruleset results in a new domain that is the intersection of the previous domain and the new ruleset.

To prevent a process from gaining more privileges than intended (e.g., via setuid binaries), it is recommended to call prctl(2) with PR_SET_NO_NEW_PRIVS before applying the Landlock ruleset.

Landlock ABI versions

Landlock is an evolving API. New features and access rights are added in new ABI versions. Programs should check the available ABI version of the running kernel to ensure compatibility. This can be done by passing LANDLOCK_CREATE_RULESET_VERSION as the flags argument to landlock_create_ruleset(2). The return value will be the highest ABI version supported by the kernel. The supported ABI versions and their associated features are:

Table 1: Landlock ABI versions and features
ABI Version Kernel Version New Features
1 5.13 Initial release. Filesystem access control (read, write, append, truncate, etc.).
2 5.19 LANDLOCK_ACCESS_FS_REFER access right. This allows restricting hard links and renaming of files across directories.
3 6.2 LANDLOCK_ACCESS_FS_TRUNCATE access right. This allows restricting file truncation.
4 6.2 Network access control (TCP bind, TCP connect).
5 6.10 LANDLOCK_ACCESS_FS_IOCTL_DEV access right. This allows restricting ioctl operations on device files.
6 6.12 LANDLOCK_SCOPE_ABSTRACT_UNIX_SOCKET and LANDLOCK_SCOPE_SIGNAL scopes. These allow restricting access to abstract namespace UNIX domain sockets and sending signals, respectively.

To query the running kernel's Landlock ABI version, programs may pass the LANDLOCK_CREATE_RULESET_VERSION flag to landlock_create_ruleset(2).

When building fallback mechanisms for compatibility with older kernels, users are advised to consider the special semantics of the LANDLOCK_ACCESS_FS_REFER access right: In ABI v1, linking and moving of files between different directories is always forbidden, so programs relying on such operations are only compatible with Landlock ABI v2 and higher.

NOTES

Landlock is enabled by CONFIG_SECURITY_LANDLOCK. The lsm=lsm1,...,lsmN command line parameter controls the sequence of the initialization of Linux Security Modules. It must contain the string landlock to enable Landlock. If the command line parameter is not specified, the initialization falls back to the value of the deprecated security= command line parameter and further to the value of CONFIG_LSM. We can check that Landlock is enabled by looking for landlock: Up and running. in kernel logs.

CAVEATS

It is currently not possible to restrict some file-related actions accessible through these system call families: chdir(2), stat(2), flock(2), chmod(2), chown(2), setxattr(2), utime(2), fcntl(2), access(2). Future Landlock evolutions will enable to restrict them.

EXAMPLES

We first need to create the ruleset that will contain our rules.

For this example, the ruleset will contain rules that only allow read actions, but write actions will be denied. The ruleset then needs to handle both of these kinds of actions. See the DESCRIPTION section for the description of filesystem actions.


struct landlock_ruleset_attr attr = {0};
int ruleset_fd;
attr.handled_access_fs =
        LANDLOCK_ACCESS_FS_EXECUTE |
        LANDLOCK_ACCESS_FS_WRITE_FILE |
        LANDLOCK_ACCESS_FS_READ_FILE |
        LANDLOCK_ACCESS_FS_READ_DIR |
        LANDLOCK_ACCESS_FS_REMOVE_DIR |
        LANDLOCK_ACCESS_FS_REMOVE_FILE |
        LANDLOCK_ACCESS_FS_MAKE_CHAR |
        LANDLOCK_ACCESS_FS_MAKE_DIR |
        LANDLOCK_ACCESS_FS_MAKE_REG |
        LANDLOCK_ACCESS_FS_MAKE_SOCK |
        LANDLOCK_ACCESS_FS_MAKE_FIFO |
        LANDLOCK_ACCESS_FS_MAKE_BLOCK |
        LANDLOCK_ACCESS_FS_MAKE_SYM |
        LANDLOCK_ACCESS_FS_REFER |
        LANDLOCK_ACCESS_FS_TRUNCATE |
        LANDLOCK_ACCESS_FS_IOCTL_DEV;

To be compatible with older Linux versions, we detect the available Landlock ABI version, and only use the available subset of access rights:


/*
 * Table of available file system access rights by ABI version,
 * numbers hardcoded to keep the example short.
 */
__u64 landlock_fs_access_rights[] = {
    (LANDLOCK_ACCESS_FS_MAKE_SYM  << 1) - 1,  /* v1                  */
    (LANDLOCK_ACCESS_FS_REFER     << 1) - 1,  /* v2: add "refer"     */
    (LANDLOCK_ACCESS_FS_TRUNCATE  << 1) - 1,  /* v3: add "truncate"  */
    (LANDLOCK_ACCESS_FS_TRUNCATE  << 1) - 1,  /* v4: TCP support     */
    (LANDLOCK_ACCESS_FS_IOCTL_DEV << 1) - 1,  /* v5: add "ioctl_dev" */
};
int abi = landlock_create_ruleset(NULL, 0,
                                  LANDLOCK_CREATE_RULESET_VERSION);
if (abi == -1) {
    /*
     * Kernel too old, not compiled with Landlock,
     * or Landlock was not enabled at boot time.
     */
    perror("Unable to use Landlock");
    return;  /* Graceful fallback: Do nothing.  */
}
abi = MIN(abi, 3);
/* Only use the available rights in the ruleset.  */
attr.handled_access_fs &= landlock_fs_access_rights[abi - 1];

The available access rights for each ABI version are listed in the VERSIONS section.

If our program needed to create hard links or rename files between different directories (LANDLOCK_ACCESS_FS_REFER), we would require the following change to the backwards compatibility logic: Directory reparenting is not possible in a process restricted with Landlock ABI version 1. Therefore, if the program needed to do file reparenting, and if only Landlock ABI version 1 was available, we could not restrict the process.

Now that the ruleset attributes are determined, we create the Landlock ruleset and acquire a file descriptor as a handle to it, using landlock_create_ruleset(2):


ruleset_fd = landlock_create_ruleset(&attr, sizeof(attr), 0);
if (ruleset_fd == -1) {
    perror("Failed to create a ruleset");
    exit(EXIT_FAILURE);
}

We can now add a new rule to the ruleset through the ruleset's file descriptor. The requested access rights must be a subset of the access rights which were specified in attr.handled_access_fs at ruleset creation time.

In this example, the rule will only allow reading the file hierarchy /usr. Without another rule, write actions would then be denied by the ruleset. To add /usr to the ruleset, we open it with the O_PATH flag and fill the struct landlock_path_beneath_attr with this file descriptor.


struct landlock_path_beneath_attr path_beneath = {0};
int err;
path_beneath.allowed_access =
        LANDLOCK_ACCESS_FS_EXECUTE |
        LANDLOCK_ACCESS_FS_READ_FILE |
        LANDLOCK_ACCESS_FS_READ_DIR;
path_beneath.parent_fd = open("/usr", O_PATH | O_CLOEXEC);
if (path_beneath.parent_fd == -1) {
    perror("Failed to open file");
    close(ruleset_fd);
    exit(EXIT_FAILURE);
}
err = landlock_add_rule(ruleset_fd, LANDLOCK_RULE_PATH_BENEATH,
                        &path_beneath, 0);
close(path_beneath.parent_fd);
if (err) {
    perror("Failed to update ruleset");
    close(ruleset_fd);
    exit(EXIT_FAILURE);
}

We now have a ruleset with one rule allowing read access to /usr while denying all other handled accesses for the filesystem. The next step is to restrict the current thread from gaining more privileges (e.g., thanks to a set-user-ID binary).


if (prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0)) {
    perror("Failed to restrict privileges");
    close(ruleset_fd);
    exit(EXIT_FAILURE);
}

The current thread is now ready to sandbox itself with the ruleset.


if (landlock_restrict_self(ruleset_fd, 0)) {
    perror("Failed to enforce ruleset");
    close(ruleset_fd);
    exit(EXIT_FAILURE);
}
close(ruleset_fd);

If the landlock_restrict_self(2) system call succeeds, the current thread is now restricted and this policy will be enforced on all its subsequently created children as well. Once a thread is landlocked, there is no way to remove its security policy; only adding more restrictions is allowed. These threads are now in a new Landlock domain, merge of their parent one (if any) with the new ruleset.

NAME

landlock — Linux API for sandboxing

DESCRIPTION

The Landlock Linux Security Module (LSM) provides a sandboxing mechanism for unprivileged processes. It allows a process to define a set of access control rules that restrict its future access to the filesystem and other resources. These rules are organized into rulesets, which are then attached to file descriptors.

Landlock operates by intercepting filesystem access system calls and checking them against the active rules. If a rule is violated, the system call is denied.

The primary interface to Landlock is through the following system calls:

landlock_create_ruleset(2)

landlock_add_rule(2)

landlock_restrict_self(2)

This man page provides an overview of the Landlock API. For detailed information on specific system calls and their parameters, refer to their respective man pages.

VERSIONS

Landlock was introduced in Linux kernel version 5.13.

NOTES

Landlock is still under active development, and new features and capabilities are being added continuously. The API may change in future kernel versions.

To use Landlock, you need to ensure that the Landlock LSM is enabled in your kernel configuration.

Example usage can be found in the Landlock documentation and source code, such as in:

ee/samples/landlock/sandboxer.c

CAVEATS

Landlock rules are applied to the process that creates them and any child processes it creates after the ruleset is activated. It does not affect already running processes or other unrelated processes.

The effectiveness of Landlock depends on the specific rules defined. Misconfigured rules could either be too restrictive, preventing necessary operations, or not restrictive enough, failing to provide adequate protection.

EXAMPLES

A simple example demonstrating the creation of a ruleset and restricting access to a specific directory:

#include <stdio.h>
#include <fcntl.h>
#include <unistd.h>
#include <sys/stat.h>
#include <linux/landlock.h>

#include "syscalls.h" // Assuming this provides landlock wrappers

int main() {
    int ruleset_fd;
    struct landlock_ruleset_attr rs_attr = {0};
    struct landlock_rule_attr rule_attr = {0};
    struct landlock_path_beneath_mkdir_rule mkdr_rule = {0};
    int dir_fd;

    // Create a new ruleset
    ruleset_fd = landlock_create_ruleset(&rs_attr, sizeof(rs_attr), 0);
    if (ruleset_fd < 0) {
        perror("landlock_create_ruleset");
        return 1;
    }

    // Open the directory to restrict access to
    dir_fd = open("./restricted_dir", O_RDONLY | O_DIRECTORY);
    if (dir_fd < 0) {
        perror("open ./restricted_dir");
        close(ruleset_fd);
        return 1;
    }

    // Configure a rule to disallow creating files within the restricted directory
    mkdr_rule.parent_ino = dir_fd; // Not strictly needed for PATH_BENEATH, but good practice
    mkdr_rule.protected_dir.flags = LANDLOCK_PATH_CONTAIN;
    // If you wanted to restrict within, you'd use LANDLOCK_PATH_BENEATH here

    // Set up the rule attributes
    rule_attr.behavior = LANDLOCK_RULE_PATH_BENEATH_MKDIR; // Example: disallow mkdir
    rule_attr.u.path_beneath_mkdir.parent_fd = dir_fd;
    rule_attr.u.path_beneath_mkdir.flags = LANDLOCK_PATH_CONTAIN; // Restrict within dir_fd

    // Add the rule to the ruleset
    if (landlock_add_rule(ruleset_fd, LANDLOCK_RULE_PATH_BENEATH_MKDIR, &rule_attr, sizeof(rule_attr), 0) < 0) {
        perror("landlock_add_rule");
        close(dir_fd);
        close(ruleset_fd);
        return 1;
    }

    // Restrict the current process to the created ruleset
    if (landlock_restrict_self(ruleset_fd, 0) < 0) {
        perror("landlock_restrict_self");
        close(dir_fd);
        close(ruleset_fd);
        return 1;
    }

    printf("Process restricted. Cannot create directories inside './restricted_dir'.\n");

    // Attempt to create a directory (this should fail if rules are applied correctly)
    if (mkdir("./restricted_dir/test_subdir", 0755) == 0) {
        printf("mkdir succeeded unexpectedly!\n");
        rmdir("./restricted_dir/test_subdir"); // Clean up if it succeeded
    } else {
        perror("mkdir ./restricted_dir/test_subdir");
    }

    // Clean up
    close(dir_fd);
    close(ruleset_fd);

    return 0;
}
