NOMBRE

libxdp - biblioteca para adjuntar programas XDP y usar sockets AF_XDP

SINOPSIS

Este directorio contiene los archivos para la biblioteca libxdp para adjuntar programas XDP a interfaces de red y usar sockets AF_XDP. La biblioteca es bastante ligera y se basa en libbpf para hacer el trabajo pesado de procesar archivos de objetos eBPF, etc.

Libxdp proporciona dos características principales sobre libbpf. La primera es la capacidad de cargar múltiples programas XDP en secuencia en un solo dispositivo de red (lo que no es compatible de forma nativa con el kernel). Esta compatibilidad se basa en la funcionalidad freplace del kernel, que hace posible adjuntar un programa eBPF como reemplazo de una función global en otro programa eBPF (ya cargado). La segunda característica principal son las funciones auxiliares para configurar sockets AF_XDP, así como para leer y escribir paquetes desde estos sockets.

Parte de la funcionalidad proporcionada por libxdp depende de características específicas del kernel; consulte la sección "Compatibilidad de características del kernel" a continuación para obtener más detalles.

Usando libxdp desde una aplicación

El uso básico de libxdp desde una aplicación es bastante sencillo. El siguiente ejemplo carga y luego descarga un programa XDP de la interfaz 'lo':

#define IFINDEX 1
struct xdp_program *prog;
int err;
prog = xdp_program__open_file("my-program.o", "section_name", NULL);
err = xdp_program__attach(prog, IFINDEX, XDP_MODE_NATIVE, 0);
if (!err)
    xdp_program__detach(prog, IFINDEX, XDP_MODE_NATIVE, 0);
xdp_program__close(prog);

La estructura xdp_program es una estructura opaca que representa un solo programa XDP. libxdp contiene funciones para crear dicha estructura, ya sea desde un archivo de objeto BPF en disco, desde un objeto BPF de libbpf, o desde un identificador de un programa que ya está cargado en el kernel:

struct xdp_program *xdp_program__from_bpf_obj(struct bpf_object *obj,
                                              const char *section_name);
struct xdp_program *xdp_program__find_file(const char *filename,
                                           const char *section_name,
                                           struct bpf_object_open_opts *opts);
struct xdp_program *xdp_program__open_file(const char *filename,
                                           const char *section_name,
                                           struct bpf_object_open_opts *opts);
struct xdp_program *xdp_program__from_fd(int fd);
struct xdp_program *xdp_program__from_id(__u32 prog_id);
struct xdp_program *xdp_program__from_pin(const char *pin_path);

Las funciones que abren un archivo u objeto BPF necesitan el nombre de la función del programa XDP, así como el nombre del archivo u objeto, ya que un archivo ELF puede contener múltiples programas XDP. La función xdp_program__find_file() toma un nombre de archivo sin ruta y buscará el objeto en LIBXDP_OBJECT_PATH, que por defecto es /usr/lib/bpf (o /usr/lib64/bpf en sistemas que usan una ruta de bibliotecas dividida). Esto es útil para aplicaciones que distribuyen archivos de objetos eBPF precompilados.

La función xdp_program__attach() adjuntará el programa a una interfaz, construyendo un programa despachador para ejecutarlo. Se pueden adjuntar múltiples programas a la vez con xdp_program__attach_multi(); se ordenarán según su prioridad de ejecución, y la ejecución de un programa a otro procederá en función de las acciones de llamada en cadena definidas para cada programa (ver la sección **Metadatos del programa** a continuación). Debido a que el proceso de carga implica modificar el tipo de adjunto del programa, las funciones de adjunto solo funcionan con objetos struct xdp_program que aún no se han cargado en el kernel.

Al usar las funciones de adjunto para adjuntar a una interfaz que ya tiene un programa XDP cargado, libxdp intentará agregar el programa a la lista de programas cargados. Sin embargo, esto puede fallar, ya sea debido a la falta de compatibilidad del kernel, o porque el programa ya adjunto no se cargó usando un despachador compatible con libxdp. Si falta la compatibilidad del kernel para el adjunto incremental (fusionado en el kernel 5.10), la única manera de ejecutar múltiples programas en una sola interfaz es adjuntarlos todos al mismo tiempo con xdp_program__attach_multi(). Si el programa existente no es un despachador XDP, ese programa tendrá que ser desadjuntado de la interfaz antes de que libxdp pueda adjuntar uno nuevo. Esto se puede hacer llamando a xdp_program__detach() con una referencia al programa cargado; pero tenga en cuenta que esto, por supuesto, romperá cualquier aplicación que dependa de ese otro programa XDP.

Metadatos del programa

Para admitir múltiples programas XDP en la misma interfaz, libxdp utiliza dos metadatos para cada programa XDP: prioridad de ejecución y acciones de llamada en cadena.

Prioridad de ejecución

Esta es la prioridad del programa y es un entero simple que se usa para ordenar los programas al cargar múltiples programas en la misma interfaz. Los programas que desean ejecutarse temprano (como un filtro de paquetes) deben establecer valores bajos para esto, mientras que los programas que desean ejecutarse más tarde (como un reenviador de paquetes o un contador) deben establecer valores más altos. Tenga en cuenta que los programas posteriores solo se ejecutan si los programas anteriores terminan con un código de retorno que forma parte de sus acciones de llamada en cadena (ver abajo). Si no se especifica, el valor de prioridad predeterminado es 50.

Acciones de llamada en cadena

Estos son los códigos de retorno del programa que el programa indica para los paquetes que deben continuar procesándose. Si el programa devuelve una de estas acciones, se ejecutarán los programas posteriores en la cadena de llamadas, mientras que si devuelve cualquier otra acción, el procesamiento se interrumpirá y el despachador XDP devolverá el veredicto inmediatamente. Si no se establece, esto se limita por defecto a XDP_PASS, que es probablemente el valor que la mayoría de los programas deberían usar.

Especificando metadatos

Los metadatos descritos anteriormente se especifican como información BTF incrustada en el archivo ELF que contiene el programa XDP. El archivo xdp_helpers.h incluido con libxdp contiene macros auxiliares para incluir esta información, que se puede usar de la siguiente manera:

#include <bpf/bpf_helpers.h>
#include <xdp/xdp_helpers.h>
struct {
        __uint(priority, 10);
        __uint(XDP_PASS, 1);
        __uint(XDP_DROP, 1);
} XDP_RUN_CONFIG(my_xdp_func);

Este ejemplo especifica que el programa XDP en my_xdp_func debe tener prioridad 10 y que sus acciones de llamada en cadena son XDP_PASS y XDP_DROP. En un archivo fuente con múltiples programas XDP en el mismo archivo, se puede incluir una definición como la anterior para cada programa (función XDP principal). Cualquier programa que no especifique información de configuración utilizará los valores predeterminados descritos anteriormente.

Inspeccionando y modificando metadatos

libxdp expone las siguientes funciones que una aplicación puede usar para inspeccionar y modificar los metadatos de un programa XDP. La modificación solo es posible antes de que un programa se adjunte a una interfaz. Estas funciones no modificarán la información BTF en sí, sino que los nuevos valores se almacenarán como parte del adjunto del programa.

unsigned int xdp_program__run_prio(const struct xdp_program *xdp_prog);
int xdp_program__set_run_prio(struct xdp_program *xdp_prog,
                              unsigned int run_prio);
bool xdp_program__chain_call_enabled(const struct xdp_program *xdp_prog,
                                     enum xdp_action action);
int xdp_program__set_chain_call_enabled(struct xdp_program *prog,
                                        unsigned int action,
                                        bool enabled);
int xdp_program__print_chain_call_actions(const struct xdp_program *prog,
                                          char *buf,
                                          size_t buf_len);

El programa despachador

Para admitir programas no descargados múltiples en la misma interfaz de red, libxdp utiliza un programa despachador, que es un pequeño programa envoltorio que llamará a cada programa componente en orden, esperará el código de retorno y luego realizará una llamada en cadena a

el siguiente programa basado en la llamada en cadena de acciones del programa anterior (ver la sección Metadatos del programa arriba).

Si bien las aplicaciones que usan libxdp no necesitan conocer los detalles del programa de distribución para simplemente cargar un programa XDP en una interfaz, libxdp expone el programa de distribución y sus programas componentes adjuntos, que se pueden usar para enumerar los programas actualmente adjuntos a una interfaz.

La estructura utilizada para esto es struct xdp_multiprog, que solo se puede construir a partir de los programas cargados en una interfaz basada en ifindex. La API para obtener una referencia a multiprog e iterar a través de los programas adjuntos se ve así:

struct xdp_multiprog *xdp_multiprog__get_from_ifindex(int ifindex);
struct xdp_program *xdp_multiprog__next_prog(const struct xdp_program *prog,
                                             const struct xdp_multiprog *mp);
void xdp_multiprog__close(struct xdp_multiprog *mp);
int xdp_multiprog__detach(struct xdp_multiprog *mp, int ifindex);
enum xdp_attach_mode xdp_multiprog__attach_mode(const struct xdp_multiprog *mp);
struct xdp_program *xdp_multiprog__main_prog(const struct xdp_multiprog *mp);
struct xdp_program *xdp_multiprog__hw_prog(const struct xdp_multiprog *mp);
bool xdp_multiprog__is_legacy(const struct xdp_multiprog *mp);

Si se adjunta un programa no descargado a la interfaz que libxdp no reconoce como programa de distribución, aún se devolverá una estructura xdp_multiprog, y xdp_multiprog__is_legacy() devolverá true para ese programa (tenga en cuenta que esto también es válido si solo se carga un programa descargado). Se puede obtener una referencia a ese programa XDP (regular) mediante xdp_multiprog__main_prog(). Si el programa adjunto a la interfaz **es** un programa de distribución, xdp_multiprog__main_prog() devolverá una referencia al propio programa de distribución, lo cual es principalmente útil para obtener otros datos sobre ese programa (como el ID del programa). Se puede adquirir una referencia a un programa descargado utilizando xdp_multiprog_hw_prog(). La función xdp_multiprog__attach_mode() devuelve el modo de adjunto del programa no descargado; se debe verificar si se adjunta un programa descargado a través de xdp_multiprog_hw_prog().

Fijación en bpffs

El kernel desvinculará automáticamente los programas componentes del distribuidor una vez que desaparezca la última referencia a ellos. Para evitar que esto suceda, libxdp fijará las referencias de los programas componentes en bpffs antes de adjuntar el distribuidor a la interfaz de red. Las rutas generadas para la fijación son las siguientes:

—
/sys/fs/bpf/xdp/dispatch-IFINDEX-DID - programa distribuidor para IFINDEX con ID de programa BPF DID
—
/sys/fs/bpf/xdp/dispatch-IFINDEX-DID/prog0-prog - programa componente 0, referencia de programa
—
/sys/fs/bpf/xdp/dispatch-IFINDEX-DID/prog0-link - programa componente 0, referencia de enlace bpf
—
/sys/fs/bpf/xdp/dispatch-IFINDEX-DID/prog1-prog - programa componente 1, referencia de programa
—
/sys/fs/bpf/xdp/dispatch-IFINDEX-DID/prog1-link - programa componente 1, referencia de enlace bpf
—
etc., hasta diez programas componentes

Si está configurada, la variable de entorno LIBXDP_BPFFS anulará la ubicación de bpffs, pero el subdirectorio xdp siempre se usa. Si no hay un bpffs montado, libxdp consultará la variable de entorno LIBXDP_BPFFS_AUTOMOUNT. Si está configurada como 1, libxdp intentará montar automáticamente un bpffs. Si no, libxdp volverá a cargar un solo programa sin distribuidor, como si el kernel no soportara las funciones necesarias para la adjunción multiprog.

Usando sockets AF_XDP

Libxdp implementa funciones auxiliares para configurar sockets AF_XDP, así como para leer y escribir paquetes desde estos sockets. Los sockets AF_XDP se pueden usar para redirigir paquetes al espacio de usuario a altas tasas desde un programa XDP. Tenga en cuenta que esta funcionalidad solía residir en libbpf, pero ahora se ha trasladado a libxdp, ya que encaja mejor en esta biblioteca. A partir de la versión 1.0 de libbpf, se eliminará el soporte para sockets AF_XDP y todo el desarrollo futuro se realizará en libxdp.

Para obtener una descripción general de los sockets AF_XDP, consulte este artículo de Linux Plumbers (http://vger.kernel.org/lpc_net2018_talks/lpc18_pres_af_xdp_perf-v3.pdf) y la documentación del kernel de Linux (Documentation/networking/af_xdp.rst o https://www.kernel.org/doc/html/latest/networking/af_xdp.html).

Como ejemplo de cómo usar la interfaz, consulte los programas AF_XDP-example y AF_XDP-forwarding en el repositorio bpf-examples: https://github.com/xdp-project/bpf-examples.

Ruta de control

Libxdp proporciona funciones auxiliares para crear y destruir umems y sockets como se muestra a continuación. Lo primero que generalmente querrá hacer un usuario es crear un área de umem. Esta es el área que contendrá todos los paquetes recibidos y los que se van a enviar. Después de eso, se pueden crear sockets AF_XDP vinculados a este umem. Estos pueden ser sockets que tienen propiedad exclusiva de ese umem a través de xsk_socket__create() o compartidos con otros sockets usando xsk_socket__create_shared. Hay una opción llamada XSK_LIBBPF_FLAGS__INHIBIT_PROG_LOAD que se puede establecer en el campo libxdp_flags (también llamado libbpf_flags por razones de compatibilidad). Esto hará que libxdp no cargue ningún programa XDP ni establezca mapas BPF, lo cual es imprescindible si los usuarios desean agregar su propio programa XDP.

Si ya existe un socket creado con socket(AF_XDP, SOCK_RAW, 0) no vinculado ni asociado a ningún umem, el descriptor de archivo de este socket se puede usar en los parámetros opts de xsk_umem__create_opts(), que es una forma recomendada de crear umem.

struct xsk_umem *xsk_umem__create_opts(void *umem_area,
                                       struct xsk_ring_prod *fill,
                                       struct xsk_ring_cons *comp,
                                       struct xsk_umem_opts *opts);
int xsk_umem__create(struct xsk_umem **umem,
                     void *umem_area, __u64 size,
                     struct xsk_ring_prod *fill,
                     struct xsk_ring_cons *comp,
                     const struct xsk_umem_config *config);
int xsk_umem__create_with_fd(struct xsk_umem **umem,
                             int fd, void *umem_area, __u64 size,
                             struct xsk_ring_prod *fill,
                             struct xsk_ring_cons *comp,
                             const struct xsk_umem_config *config);
int xsk_socket__create(struct xsk_socket **xsk,
                       const char *ifname, __u32 queue_id,
                       struct xsk_umem *umem,
                       struct xsk_ring_cons *rx,
                       struct xsk_ring_prod *tx,
                       const struct xsk_socket_config *config);
int xsk_socket__create_shared(struct xsk_socket **xsk_ptr,
                              const char *ifname,
                              __u32 queue_id, struct xsk_umem *umem,
                              struct xsk_ring_cons *rx,
                              struct xsk_ring_prod *tx,
                              struct xsk_ring_prod *fill,
                              struct xsk_ring_cons *comp,
                              const struct xsk_socket_config *config);
int xsk_umem__delete(struct xsk_umem *umem);
void xsk_socket__delete(struct xsk_socket *xsk);

También hay dos funciones auxiliares para obtener el descriptor de archivo de un umem o un socket. Estos son necesarios cuando se utilizan syscalls estándar de Linux como poll(), recvmsg(), sendto(), etc.

int xsk_umem__fd(const struct xsk_umem *umem);
int xsk_socket__fd(const struct xsk_socket *xsk);

La ruta de control también proporciona dos API para configurar sockets AF_XDP cuando el proceso que va a usar el socket AF_XDP no tiene privilegios. Estas dos funciones realizan las operaciones que requieren privilegios y se pueden ejecutar desde alguna forma de proceso de control que tenga los privilegios necesarios. El xsk_socket__create ejecutado en el proceso no privilegiado omitirá estos dos pasos. Para ver un ejemplo de cómo usarlos, consulte el programa AF_XDP-example en el repositorio bpf-examples: https://github.com/xdp-project/bpf-examples/tree/main/AF_XDP-example.

int xsk_setup_xdp_prog(int ifindex, int *xsks_map_fd);
int xsk_socket__update_xskmap(struct xsk_socket *xsk, int xsks_map_fd);

Para reducir aún más el nivel de privilegios requerido, se puede crear previamente un socket AF_XDP con socket(AF_XDP, SOCK_RAW, 0) y pasarlo a un proceso no privilegiado. Este socket se puede usar en xsk_umem__create_opts() y más tarde en xsk_socket__create() con el umem creado. xsk_socket__create_shared() aún requeriría privilegios para la creación del socket AF_XDP.

Ruta de datos

Por razones de rendimiento, todas las funciones de ruta de datos son funciones static inline que se encuentran en el archivo de encabezado xsk.h para que puedan optimizarse en el binario de la aplicación de destino para obtener el mejor rendimiento posible. Hay cuatro anillos FIFO de dos tipos principales: anillos de productor (fill y Tx) y anillos de consumidor (Rx y completion). Los anillos de productor utilizan funciones xsk_ring_prod y los anillos de consumidor utilizan funciones xsk_ring_cons. Para los anillos de productor, se comienza reservando uno o más espacios en un anillo de productor y luego, cuando se han completado, se envían para que el kernel actúe sobre ellos. Para un anillo de consumidor, se inspecciona si hay algún paquete nuevo en el anillo y, si es así, se pueden leer del anillo. Una vez que se termina de leerlos, se liberan al kernel para que pueda usarlos para paquetes nuevos. También hay una operación de cancelación para los anillos de consumidor si la aplicación no desea consumir todos los paquetes recibidos con la operación de inspección.

__u32 xsk_ring_prod__reserve(struct xsk_ring_prod *prod, __u32 nb, __u32 *idx);
void xsk_ring_prod__submit(struct xsk_ring_prod *prod, __u32 nb);
__u32 xsk_ring_cons__peek(struct xsk_ring_cons *cons, __u32 nb, __u32 *idx);
void xsk_ring_cons__cancel(struct xsk_ring_cons *cons, __u32 nb);
void xsk_ring_cons__release(struct xsk_ring_cons *cons, __u32 nb);

Las siguientes funciones se utilizan para leer y escribir los descriptores de los anillos. xsk_ring_prod__fill_addr() y xsk_ring_prod__tx_desc() **escriben** entradas en los anillos fill y Tx.

gs respectivamente, mientras que xsk_ring_cons__comp_addr y xsk_ring_cons__rx_desc leen entradas de los anillos de finalización y Rx, respectivamente. El idx es el parámetro devuelto en las llamadas a xsk_ring_prod__reserve o xsk_ring_cons__peek. Para avanzar a la siguiente entrada, simplemente haga idx++.

__u64 *xsk_ring_prod__fill_addr(struct xsk_ring_prod *fill, __u32 idx);
struct xdp_desc *xsk_ring_prod__tx_desc(struct xsk_ring_prod *tx, __u32 idx);
const __u64 *xsk_ring_cons__comp_addr(const struct xsk_ring_cons *comp, __u32 idx);
const struct xdp_desc *xsk_ring_cons__rx_desc(const struct xsk_ring_cons *rx, __u32 idx);

Las funciones xsk_umem se utilizan para obtener un puntero a los datos del paquete en sí, siempre ubicados dentro del umem. En el modo alineado por defecto, puede obtener la variable addr directamente del descriptor Rx. Pero en modo no alineado, necesita usar las tres últimas funciones a continuación, ya que el desplazamiento utilizado se transporta en los 16 bits superiores de la dirección. Por lo tanto, no puede usar la dirección directamente desde el descriptor en el caso no alineado.

void *xsk_umem__get_data(void *umem_area, __u64 addr);
__u64 xsk_umem__extract_addr(__u64 addr);
__u64 xsk_umem__extract_offset(__u64 addr);
__u64 xsk_umem__add_offset_to_addr(__u64 addr);

Hay una función más en el plano de datos que comprueba si la bandera need_wakeup está establecida. Se recomienda encarecidamente el uso de esta bandera y debe habilitarse estableciendo el bit XDP_USE_NEED_WAKEUP en el campo xdp_bind_flags que se proporciona a las llamadas a xsk_socket_create_[shared](). Si esta función devuelve verdadero, entonces necesita llamar a recvmsg(), sendto() o poll() dependiendo de la situación. recvmsg() si está **recibiendo**, o sendto() si está **enviando**. poll() se puede usar para ambos casos y también proporciona la capacidad de dormir, como con cualquier otro socket. Pero tenga en cuenta que poll es una operación más lenta que las otras dos.

int xsk_ring_prod__needs_wakeup(const struct xsk_ring_prod *r);

Para obtener un ejemplo de cómo usar todas estas API, consulte los programas AF_XDP-example y AF_XDP-forwarding en el repositorio bpf-examples: https://github.com/xdp-project/bpf-examples.

Compatibilidad de características del kernel y programas BPF

Las características expuestas por libxdp dependen de ciertas versiones del kernel y características BPF para funcionar. Para obtener el máximo beneficio de todas las características, libxdp debe usarse con el kernel 5.10 o posterior, a menos que las confirmaciones mencionadas a continuación se hayan portado. Sin embargo, libxdp sondeará el kernel y recurrirá transparentemente a procedimientos de carga heredados, por lo que es posible utilizar la biblioteca con versiones anteriores, aunque algunas características no estarán disponibles, como se detalla a continuación.

La capacidad de adjuntar múltiples programas BPF a una única interfaz depende de la característica del kernel "extensión de programa BPF" que se introdujo con el commit be8704ff07d2 ("bpf: Introduce dynamic program extensions") en el kernel principal y apareció por primera vez en la versión 5.6 del kernel. Para adjuntar **incrementalmente** múltiples programas, se necesita un refinamiento adicional agregado por el commit 4a1e7c0c63e0 ("bpf: Soporte para adjuntar programas freplace a múltiples puntos de adjunción"); esto apareció por primera vez en la versión 5.10 del kernel principal. La funcionalidad depende de la característica "trampolines BPF", que está disponible en las arquitecturas que la soportan.

La matriz de soporte es la siguiente:

—
Los kernels anteriores a 5.6 solo pueden adjuntar un único programa XDP a cada interfaz.
—
Los kernels 5.6+ pueden adjuntar múltiples programas si todos se adjuntan al mismo tiempo.
—
Los kernels 5.10+ tienen soporte completo para multiprog XDP en arquitecturas que soportan trampolines BPF.
—
En arquitecturas sin soporte de trampolines BPF, solo se puede adjuntar un único programa a cada interfaz.

Para cargar programas AF_XDP, el soporte del kernel para sockets AF_XDP debe incluirse y habilitarse en la compilación del kernel. Además, al usar sockets AF_XDP, también se carga un programa XDP en la interfaz. El programa XDP utilizado para esto por libxdp requiere la capacidad de realizar búsquedas en mapas en mapas XSK, que se introdujo con el commit fada7fdc83c0 ("bpf: Permitir bpf_map_lookup_elem() en un xskmap") en el kernel 5.3. Esto significa que la versión mínima requerida del kernel para usar AF_XDP es el kernel 5.3; sin embargo, para que el programa XDP AF_XDP coexista con otros programas, se aplican las mismas restricciones de multiprog que se describen arriba.

Tenga en cuenta que algunas distribuciones de Linux portan características a versiones anteriores del kernel, especialmente en kernels empresariales; por ejemplo, los kernels de Red Hat Enterprise Linux incluyen todo lo necesario para que libxdp funcione desde RHEL 8.5.

Finalmente, los programas XDP cargados utilizando la instalación multiprog deben incluir información de tipo (usando el Formato de Tipo BPF, BTF). Para obtener esto, compile los programas con una versión reciente de Clang/LLVM (versión 10+), y habilite la información de depuración al compilar (usando la opción -g).
