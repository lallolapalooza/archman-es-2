NOMBRE

libunwind -- una API de desenrollado (unwind) (mayormente) independiente de la plataforma

DESENROLLADO LOCAL

Libunwind es muy fácil de usar al desenrollar una pila desde dentro de un programa en ejecución. Esto se llama desenrollado local. Supongamos que desea desenrollar la pila mientras se ejecuta en alguna función F(). En esta función, llamaría a unw_getcontext() para obtener una instantánea de los registros de la CPU (estado de la máquina). Luego inicializa un cursor de desenrollado basado en esta instantánea. Esto se hace con una llamada a unw_init_local(). El cursor ahora apunta al marco actual, es decir, al marco de la pila que corresponde a la activación actual de la función F(). El cursor de desenrollado se puede mover ``hacia arriba'' (hacia marcos de pila anteriores) llamando a unw_step(). Al llamar repetidamente a esta rutina, puede descubrir toda la cadena de llamadas que condujo a la activación de la función F(). Un valor de retorno positivo de unw_step() indica que hay más marcos en la cadena, cero indica que se ha llegado al final de la cadena y cualquier valor negativo indica que ha ocurrido algún tipo de error.

Aunque no es posible mover directamente el cursor de desenrollado en la dirección ``hacia abajo'' (hacia marcos de pila más nuevos), este efecto se puede lograr haciendo copias de un cursor de desenrollado. Por ejemplo, un programa que a veces tiene que moverse ``hacia abajo'' por un marco de pila podría mantener dos variables de cursor: ``curr'' y ``prev''. El primero se utilizaría como cursor actual y prev se mantendría como el cursor del ``marco anterior'' copiando el contenido de curr a prev justo antes de llamar a unw_step(). Con este enfoque, el programa podría moverse un paso ``hacia abajo'' simplemente copiando prev de nuevo a curr siempre que sea necesario. En el caso más extremo, un programa podría mantener un cursor separado para cada marco de llamada y de esa manera podría moverse hacia arriba y hacia abajo en la cadena de marcos de llamada a voluntad.

Dado un cursor de desenrollado, es posible leer y escribir los registros de la CPU que se conservaron para el marco de pila actual (tal como lo identifica el cursor). Libunwind proporciona varias rutinas para este propósito: unw_get_reg() lee un registro entero (general), unw_get_fpreg() lee un registro de punto flotante, unw_set_reg() escribe un registro entero y unw_set_fpreg() escribe un registro de punto flotante. Tenga en cuenta que, por definición, solo se puede acceder al estado de la máquina conservado durante una operación de desenrollado. Normalmente, este estado consiste en los registros guardados por el callee ("conservados"). Sin embargo, en algunas circunstancias especiales (por ejemplo, en una trampa de manejador de señales), incluso los registros guardados por el caller ("temporales") se conservan en el marco de pila y, en esos casos, libunwind les otorgará acceso. El conjunto exacto de registros a los que se puede acceder a través del cursor depende, por supuesto, de la plataforma. Sin embargo, hay dos registros que se pueden leer en todas las plataformas: el puntero de instrucción (IP), también conocido como el "contador de programa", y el puntero de pila (SP). En libunwind, estos registros se identifican mediante las macros UNW_REG_IP y UNW_REG_SP, respectivamente.

Además de simplemente mover el cursor de desenrollado y leer/escribir registros guardados, libunwind también proporciona la capacidad de reanudar la ejecución en un marco de pila arbitrario. Como puede imaginar, esto es útil para implementar saltos no locales y el manejo de excepciones que requieren algunos lenguajes de alto nivel como Java. Reanudar la ejecución con un marco de pila particular simplemente requiere llamar a unw_resume() y pasar el cursor que identifica el marco de destino como único argumento.

Normalmente, libunwind admite tanto el desenrollado local como el remoto (este último se explicará en la siguiente sección). Sin embargo, si le dice a libunwind que su programa solo necesita desenrollado local, se puede seleccionar una implementación especial que puede ejecutarse mucho más rápido que la implementación genérica que admite ambos tipos de desenrollado. Para seleccionar esta versión optimizada, simplemente defina la macro UNW_LOCAL_ONLY antes de incluir el archivo de cabecera <libunwind.h>. Está perfectamente bien que un solo programa emplee tanto el desenrollado local solamente como el genérico. Es decir, independientemente de si UNW_LOCAL_ONLY está definido o no, cada archivo fuente (unidad de compilación) puede tomar su propia decisión. Independientemente de la configuración de UNW_LOCAL_ONLY, siempre enlazará la misma biblioteca al programa (normalmente -lunwind). Además, la parte de libunwind que administra la información de desenrollado para el código generado dinámicamente no se ve afectada por la configuración de UNW_LOCAL_ONLY.

Si juntamos todo lo anterior, así es como podríamos usar libunwind para escribir una función ``show_backtrace()'' que imprime un rastreo de pila clásico:

#define UNW_LOCAL_ONLY
#include <libunwind.h>
void show_backtrace (void) {
  unw_cursor_t cursor; unw_context_t uc;
  unw_word_t ip, sp;
  unw_getcontext(&uc);
  unw_init_local(&cursor, &uc);
  while (unw_step(&cursor) > 0) {
    unw_get_reg(&cursor, UNW_REG_IP, &ip);
    unw_get_reg(&cursor, UNW_REG_SP, &sp);
    printf ("ip = %lx, sp = %lx\n", (long) ip, (long) sp);
  }
}

DESENROLLADO REMOTO

Libunwind también se puede usar para desenrollar una pila en un proceso ``remoto''. Aquí, ``remoto'' puede significar otro proceso en la misma máquina o incluso un proceso en una máquina completamente diferente de la que está ejecutando libunwind. El desenrollado remoto se utiliza normalmente en depuradores y simuladores de conjuntos de instrucciones, por ejemplo.

Antes de poder desenrollar un proceso remoto, necesita crear un nuevo objeto de espacio de direcciones para ese proceso. Esto se logra con la rutina unw_create_addr_space(). La rutina toma dos argumentos: un puntero a un conjunto de rutinas accesorias y un entero que especifica el orden de bytes del proceso de destino. Las rutinas accesorias proporcionan a libunwind los medios para comunicarse con el proceso remoto. En particular, hay callbacks para leer y escribir la memoria del proceso, sus registros y para acceder a la información de desenrollado que puede ser necesaria para libunwind.

Con el espacio de direcciones creado, el desenrollado se puede iniciar con una llamada a unw_init_remote(). Esta rutina es muy similar a unw_init_local(), excepto que toma un objeto de espacio de direcciones y un puntero opaco como argumentos. La rutina utiliza estos argumentos para obtener el estado inicial de la máquina. Libunwind nunca utiliza el puntero opaco por sí solo, sino que simplemente lo pasa a las rutinas accesorias (callbacks). Típicamente, este puntero se utiliza para seleccionar, por ejemplo, el hilo dentro de un proceso que se va a desenrollar.

Una vez que se ha inicializado un cursor con unw_init_remote(), el desenrollado funciona exactamente como en el caso local. Es decir, puede usar unw_step() para moverse ``hacia arriba'' en la cadena de llamadas, leer y escribir registros, o reanudar la ejecución en un marco de pila particular llamando a unw_resume.

DESENROLLADO TRANSPLATAFORMA Y MULTIPLATAFORMA

Libunwind ha sido diseñado para permitir el desenrollado entre plataformas (arquitecturas). ¡De hecho, un solo programa puede usar libunwind para desenrollar un número arbitrario de plataformas de destino, ¡todas al mismo tiempo!

NAME

libunwind - exception-free stack unwinding library

SYNOPSIS

#include <libunwind.h>

DESCRIPTION

Libunwind is a library that provides a machine-independent API for determining the stack backtrace. It is designed to be used by debuggers, exception handlers, and other low-level system software.

Libunwind supports several types of unwinding:

  • local unwinding: This is the simplest case, where libunwind is used to unwind the stack of the current process.
  • remote unwinding: In this case, libunwind is used to unwind the stack of a different process (the target). This is typically done by a debugger.

The distinction between local and remote unwinding is important. Local unwinding typically has access to the state of the process (registers, stack memory, etc.), while remote unwinding must obtain this information through process-specific mechanisms (e.g., by using ptrace(2)).

Libunwind distinguishes between the host platform (where the unwinding is performed) and the target platform (the platform of the process being unwound). If the host and the target platform are the same, we call it native unwinding. If they differ, we call it cross-platform unwinding.

The principle behind supporting native, cross-platform, and multi-platform unwinding is very simple: for native unwinding, a program includes <libunwind.h> and uses the linker switch -lunwind. For cross-platform unwinding, a program includes <libunwind-PLAT.h> and uses the linker switch -lunwind-PLAT, where PLAT is the name of the target platform (e.g., ia64 for IA-64, hppa-elf for ELF-based HP PA-RISC, or x86 for 80386). Multi-platform unwinding works exactly like cross-platform unwinding, the only limitation is that a single source file (compilation unit) can include at most one libunwind header file. In other words, the platform-specific support for each supported target needs to be isolated in separate source files---a limitation that shouldn't be an issue in practice.

Note that, by definition, local unwinding is possible only for the native case. Attempting to call, e.g., unw_local_init() when targeting a cross-platform will result in a link-time error (unresolved references).

THREAD- AND SIGNAL-SAFETY

All libunwind routines are thread-safe. What this means is that multiple threads may use libunwind simultaneously. However, any given cursor may be accessed by only one thread at any given time.

To ensure thread safety, some libunwind routines may have to use locking. Such routines must not be called from signal handlers (directly or indirectly) and are therefore not signal-safe. The manual page for each libunwind routine identifies whether or not it is signal-safe, but as a general rule, any routine that may be needed for local unwinding is signal-safe (e.g., unw_step() for local unwinding is signal-safe). For remote unwinding, none of the libunwind routines are guaranteed to be signal-safe.

UNWINDING THROUGH DYNAMICALLY GENERATED CODE

Libunwind provides the routines _U_dyn_register() and _U_dyn_cancel() to register/cancel the information required to unwind through code that has been generated at runtime (e.g., by a just-in-time (JIT) compiler). It is important to register the information for all dynamically generated code because otherwise, a debugger may not be able to function properly or high-level language exception handling may not work as expected.

The interface for registering and canceling dynamic unwind info has been designed for maximum efficiency, so as to minimize the performance impact on JIT compilers. In particular, both routines are guaranteed to execute in ``constant time'' (O(1)) and the data structure encapsulating the dynamic unwind info has been designed to facilitate sharing, such that similar procedures can share much of the underlying information.

For more information on the libunwind support for dynamically generated code, see libunwind-dynamic(3libunwind).

CACHING OF UNWIND INFO

To speed up execution, libunwind may aggressively cache the information it needs to perform unwinding. If a process changes during its lifetime, this creates a risk of libunwind using stale data. For example, this would happen if libunwind were to cache information about a shared library which later on gets unloaded (e.g., via dlclose(3libunwind)).

To prevent the risk of using stale data, libunwind provides two facilities: first, it is possible to flush the cached information associated with a specific address range in the target process (or the entire address space, if desired). This functionality is provided by unw_flush_cache(). The second facility is provided by unw_set_caching_policy(), which lets a program select the exact caching policy in use for a given address space object. In particular, by selecting the policy UNW_CACHE_NONE, it is possible to turn off caching completely, therefore eliminating the risk of stale data altogether (at the cost of slower execution). By default, caching is enabled for local unwinding only. The cache size can be dynamically changed with unw_set_cache_size(), which also flushes the current cache.

FILES

libunwind.h

Headerfile to include for native (same platform) unwinding.
libunwind-PLAT.h

Headerfile to include when the unwind target runs on platform PLAT. For example, to unwind an IA-64 program, the header file libunwind-ia64.h should be included.
-lunwind

Linker switch to add when building a program that does native (same platform) unwinding.
-lunwind-PLAT

Linker switch to add when building a program that unwinds a program on platform PLAT. For example, to (cross-)unwind an IA-64 program, the linker switch -lunwind-ia64 should be added. Note: multiple such switches may need to be specified for programs that can unwind programs on multiple platforms.
