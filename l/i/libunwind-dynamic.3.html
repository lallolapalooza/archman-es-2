NOMBRE

libunwind-dynamic -- soporte de libunwind para código generado en tiempo de ejecución

INTRODUCCIÓN

Para que libunwind haga su trabajo, necesita poder reconstruir el estado del frame de cada frame en una cadena de llamadas. El estado del frame describe el subconjunto del estado de la máquina que consiste en los registros del frame (típicamente el puntero de instrucción y el puntero de pila) y todos los registros guardados por el llamador (registros preservados). El estado del frame describe cada registro ya sea proporcionando su valor actual (para los registros del frame) o proporcionando la ubicación en la que se almacena el valor actual (registros guardados por el llamador).

Para el código generado estáticamente, el compilador normalmente se encarga de emitir unwind-info que proporciona la cantidad mínima de información necesaria para reconstruir el estado del frame para cada instrucción en un procedimiento. Para el código generado dinámicamente, el generador de código en tiempo de ejecución debe utilizar la interfaz de desenrollado dinámico proporcionada por libunwind para suministrar la información equivalente. Esta página del manual describe el formato de esta información en detalle.

A efectos de esta discusión, un procedimiento se define como una pieza arbitraria de código contiguo. Normalmente, cada procedimiento corresponde directamente a una función en el lenguaje fuente, pero esto no es estrictamente necesario. Por ejemplo, un generador de código en tiempo de ejecución podría traducir una función dada en dos procedimientos separados (discontinuos): uno para el código ejecutado frecuentemente (caliente) y otro para el código ejecutado raramente (frío). Del mismo modo, las funciones simples del lenguaje fuente (generalmente funciones hoja) pueden traducirse en código para el que se aplican las convenciones de desenrollado predeterminadas y, para dicho código, no es estrictamente necesario registrar la información de desenrollado dinámico.

Un procedimiento consta lógicamente de una secuencia de regiones. Las regiones están anidadas en el sentido de que, por defecto, se asume que el estado del frame al final de una región es el estado del frame para la siguiente región. Cada región se considera dividida en un prólogo, un cuerpo y un epílogo. Cada uno de ellos puede estar vacío. Si no está vacío, el prólogo configura el estado del frame para el cuerpo. Por ejemplo, el prólogo puede necesitar asignar espacio en la pila y guardar ciertos registros guardados por el llamador. El cuerpo realiza el trabajo real del procedimiento pero no modifica el estado del frame de ninguna manera. Si no está vacío, el epílogo restaura el estado del frame anterior y, como tal, deshace o cancela el efecto del prólogo. De hecho, un único epílogo puede deshacer el efecto de los prólogos de varias regiones (anidadas).

Cabe señalar que, aunque el prólogo, el cuerpo y el epílogo son entidades lógicamente separadas, los generadores de código optimizadores generalmente intercalarán instrucciones de las tres entidades. Por esta razón, la interfaz de desenrollado dinámico de libunwind no hace ninguna distinción entre prólogo y cuerpo. Del mismo modo, el conjunto exacto de instrucciones que componen un epílogo tampoco es relevante. El único punto en el epílogo que necesita ser descrito explícitamente por la información de desenrollado dinámico es el punto en el que se restaura el puntero de pila. La razón por la que este punto necesita ser descrito es que una vez que se restaura el puntero de pila, todos los valores guardados en la porción desasignada del frame de pila se vuelven inválidos y, por lo tanto, libunwind necesita saberlo. Se asume que la porción del estado del frame que no está guardada en la pila permanece válida hasta el final de la región. Por esta razón, generalmente no hay necesidad de describir instrucciones que restauren el contenido de los registros guardados por el llamador.

Dentro de una región, cada instrucción que afecta al estado del frame de alguna manera necesita ser descrita con un descriptor de operación. Para este propósito, a cada instrucción en la región se le asigna un índice único. Exactamente cómo se deriva este índice depende de la arquitectura. Por ejemplo, en arquitecturas RISC y estilo EPIC, las instrucciones tienen un tamaño fijo, por lo que es posible numerarlas simplemente. En contraste, la mayoría de las CISC utilizan codificaciones de instrucciones de longitud variable, por lo que generalmente es necesario usar un desplazamiento de byte como índice. Dado el índice de la instrucción, el descriptor de operación especifica el efecto de la instrucción de manera abstracta. Por ejemplo, podría expresar que la instrucción almacena el registro guardado por el llamador r1 en el desplazamiento 16 del frame de pila.

PROCEDIMIENTOS

Un generador de código en tiempo de ejecución registra la información de desenrollado dinámico de un procedimiento configurando una estructura de tipo unw_dyn_info_t y llamando a _U_dyn_register(), pasando la dirección de la estructura como único argumento. Los miembros de la estructura unw_dyn_info_t se describen a continuación:

void *next

Reservado para libunwind. La aplicación no debe usarlo.
void *prev

Reservado para libunwind. La aplicación no debe usarlo.
unw_word_t start_ip

La dirección de inicio de las instrucciones del procedimiento (recuerde: los procedimientos se definen como piezas de código contiguas, por lo que basta con un solo rango de código).
unw_word_t end_ip

La dirección final de las instrucciones del procedimiento (no inclusiva, es decir, end_ip-start_ip es el tamaño del procedimiento en bytes).
unw_word_t gp

El valor del puntero global en uso para este procedimiento. El significado exacto del puntero global es específico de la arquitectura y en algunas arquitecturas no se utiliza en absoluto.
int32_t format

El formato de la información de desenrollado. Este miembro puede ser uno de UNW_INFO_FORMAT_DYNAMIC, UNW_INFO_FORMAT_TABLE o UNW_INFO_FORMAT_REMOTE_TABLE.
union u

Esta unión contiene una subestructura para cada formato de información de desenrollado posible:
unw_dyn_proc_info_t pi

Este miembro se utiliza para el formato UNW_INFO_FORMAT_DYNAMIC.
unw_dyn_table_info_t ti

Este miembro se utiliza para el formato UNW_INFO_FORMAT_TABLE.
unw_dyn_remote_table_info_t rti

Este miembro se utiliza para el formato UNW_INFO_FORMAT_REMOTE_TABLE.

El formato de estos submiembros se describe en detalle a continuación.

FORMATO PROC-INFO

Este es el formato preferido de desenrollado dinámico y, en general, es el utilizado por los generadores de código en tiempo de ejecución completos. En este formato, los detalles de un procedimiento se describen mediante una estructura de tipo unw_dyn_proc_info_t. Esta estructura contiene los siguientes miembros:

unw_word_t name_ptr

La dirección de un nombre (legible por humanos) del procedimiento o 0 si no hay dicho nombre disponible. Si no es cero, la cadena almacenada en esta dirección debe terminar en NUL ASCII. Para lenguajes fuente que utilizan decoración de nombres (como C++ o Java), la cadena almacenada en esta dirección debe ser la versión sin decorar del nombre.
unw_word_t handler

La dirección de la rutina de personalidad para este procedimiento. Las rutinas de personalidad se utilizan en conjunción con el manejo de excepciones. Consulte el borrador de la ABI de C++ (http://www.codesourcery.com/cxx-abi/) para obtener una visión general y una descripción de la rutina de personalidad. Si el procedimiento no tiene rutina de personalidad, handler debe establecerse en 0.
uint32_t flags

Una máscara de bits de banderas. Por el momento, no se han definido banderas y este miembro debe establecerse en 0.
unw_dyn_region_info_t *regions

Una lista enlazada terminada en NULL de descriptores de región. Consulte la sección "Descriptores de región" a continuación para obtener más detalles.

FORMATO TABLE-INFO

Este formato

se utiliza generalmente cuando el código generado dinámicamente se deriva de código estático y la información de desenrollado (unwind-info) para las versiones dinámica y estática son idénticas. Por ejemplo, este formato puede ser útil al cargar código generado estáticamente en un espacio de direcciones de una manera no estándar (es decir, a través de algún medio que no sea dlopen()). En este formato, los detalles de un grupo de procedimientos se describen mediante una estructura de tipo unw_dyn_table_info. Esta estructura contiene los siguientes miembros:

unw_word_t name_ptr

La dirección de un nombre (legible por humanos) del procedimiento o 0 si no hay tal nombre disponible. Si no es cero, la cadena almacenada en esta dirección debe terminar en NUL ASCII. Para lenguajes fuente que utilizan manejo de nombres (como C++ o Java), la cadena almacenada en esta dirección debe ser la versión *desenredada* del nombre.
unw_word_t segbase

El valor base del segmento que debe agregarse a los valores relativos al segmento almacenados en la información de desenrollado. El significado exacto de este valor es específico de la arquitectura.
unw_word_t table_len

La longitud de la información de desenrollado (table_data) contada en unidades de palabras (unw_word_t).
unw_word_t table_data

Un puntero a los datos reales que codifican la información de desenrollado. El formato exacto es específico de la arquitectura (ver secciones específicas de la arquitectura a continuación).

FORMATO DE INFORMACIÓN DE TABLA REMOTA (REMOTE TABLE-INFO)

El formato de información de tabla remota tiene el mismo propósito básico que el formato de información de tabla regular. La única diferencia es que cuando libunwind utiliza la información de desenrollado, mantendrá los datos de la tabla en el espacio de direcciones de destino (que puede ser remoto). En consecuencia, el tipo del miembro table_data es unw_word_t en lugar de un puntero. Esto implica que libunwind tendrá que acceder a los datos de la tabla a través de la devolución de llamada access_mem() del espacio de direcciones, en lugar de una referencia directa a la memoria.

Desde el punto de vista de un generador de código en tiempo de ejecución, el formato de información de tabla remota no ofrece ninguna ventaja y se espera que tales generadores describan sus procedimientos con el formato proc-info o el formato de tabla normal. La razón principal de la existencia del formato de información de tabla remota es permitir que la devolución de llamada find_proc_info() específica del espacio de direcciones (ver unw_create_addr_space(3libunwind)) devuelva tablas de desenrollado cuyos datos permanecen en memoria remota. Esto puede acelerar el desenrollado (por ejemplo, para un depurador) porque reduce la cantidad de datos que deben cargarse desde la memoria remota.

DESCRIPTORES DE REGIÓN

Un descriptor de región es una estructura de longitud variable que describe cómo cada instrucción en la región afecta el estado del marco. Por supuesto, la mayoría de las instrucciones en una región generalmente no cambian el estado del marco y para esas, no es necesario registrar nada en el descriptor de región. Un descriptor de región es una estructura de tipo unw_dyn_region_info_t y tiene los siguientes miembros:

unw_dyn_region_info_t *next

Un puntero a la siguiente región. Si esta es la última región, next es NULL.
int32_t insn_count

La longitud de la región en instrucciones. Se asume que cada instrucción tiene un tamaño fijo (ver secciones específicas de la arquitectura para detalles). El valor de insn_count puede ser negativo en la última región de un procedimiento (es decir, puede ser negativo solo si next es NULL). Un valor negativo indica que la región cubre las últimas *N* instrucciones del procedimiento, donde *N* es el valor absoluto de insn_count.
uint32_t op_count

La longitud (asignada) del array op_count.
unw_dyn_op_t op

Una matriz de directivas de desenrollado dinámico. Ver la Sección ``Directivas de desenrollado dinámico'' para una descripción de las directivas.

Un descriptor de región con un insn_count de cero es una *región vacía* y tales regiones son perfectamente legales. De hecho, las regiones vacías pueden ser útiles para establecer un estado de marco particular antes del inicio de otra región.

Una sola lista de regiones puede ser compartida entre múltiples procedimientos siempre que dichos procedimientos compartan una prólogo y epílogo comunes (sus cuerpos pueden diferir, por supuesto). Normalmente, dichos procedimientos consisten en una prólogo predefinida, el cuerpo y un epílogo predefinido. Esto podría describirse mediante dos regiones: una que cubre la prólogo y otra que cubre el epílogo. Dado que la longitud del cuerpo es variable, la última región tendría que especificar un valor negativo en insn_count para que libunwind sepa que la región cubre el final del procedimiento (hasta la dirección especificada por end_ip).

El descriptor de región es una estructura de longitud variable para hacer posible la asignación de toda la memoria necesaria con una sola solicitud de asignación de memoria. Para facilitar la asignación de descriptores de región, libunwind proporciona una rutina auxiliar con la siguiente sinopsis:

size_t _U_dyn_region_size(int op_count);

Esta rutina devuelve el número de bytes necesarios para mantener un descriptor de región con espacio para op_count directivas de desenrollado. Tenga en cuenta que la longitud de la matriz op no tiene que coincidir exactamente con el número de directivas en una región. En su lugar, es suficiente si la matriz op contiene al menos tantas entradas como directivas haya, ya que el final de las directivas siempre se puede indicar con la directiva UNW_DYN_STOP.

DIRECTIVAS DE DESENROLLADO DINÁMICO

Una directiva de desenrollado dinámico describe cómo cambia el estado del marco en un punto particular dentro de una región. La descripción tiene la forma de una estructura de tipo unw_dyn_op_t. Esta estructura tiene los siguientes miembros:

int8_t tag

La etiqueta de operación. Debe ser uno de los valores unw_dyn_operation_t descritos a continuación.
int8_t qp

El predicado calificador que controla si esta directiva está activa o no. Esto es útil para arquitecturas con predicados como IA-64 o ARM, donde el contenido de otro registro (guardado por el llamador) determina si una instrucción se ejecuta (tiene efecto). Si la directiva está siempre activa, este miembro debe establecerse en la constante simbólica _U_QP_TRUE (esta constante está definida para todas las arquitecturas, predichas o no).
int16_t reg

El número del registro afectado por la instrucción.
int32_t when

El número relativo a la región de la instrucción a la que se aplica esta directiva. Por ejemplo, un valor de 0 significa que el efecto descrito por esta directiva ha ocurrido una vez que se ha ejecutado la primera instrucción de la región.
unw_word_t val

El valor que se aplicará mediante la etiqueta de operación. El significado exacto de este valor varía según la etiqueta. Ver la Sección ``Etiquetas de operación'' a continuación.

Es perfectamente legítimo especificar múltiples directivas de desenrollado dinámico con el mismo valor de `when`, si una instrucción particular tiene un efecto complejo en el estado del marco.

Las regiones vacías, por definición, no contienen instrucciones reales y, como tales, las directivas no están ligadas a una instrucción particular. Por convención, el miembro `when` debe establecerse en 0, sin embargo.

No es necesario que las directivas de desenrollado dinámico aparezcan en orden de valores `when` crecientes. Si las directivas resultan estar ordenadas de esa manera, puede resultar en una ejecución ligeramente más rápida, pero un generador de código en tiempo de ejecución no debe hacer esfuerzos adicionales solo para garantizar que las directivas estén ordenadas.

NOTA DE IMPLEMENTACIÓN: si las implementaciones de libunwind para ciertas arquitecturas prefieren que la lista de directivas de desenrollado esté ordenada, se recomienda que dichas implementaciones primero verifiquen si la lista está ordenada de hecho y, si no, ordenen explícitamente las directivas antes del primer uso. Con este enfoque, la sobrecarga de la ordenación explícita solo se paga cuando hay un beneficio real y si el generador de código en tiempo de ejecución genera listas ordenadas de forma natural, la penalización de rendimiento se limita a una simple verificación O(N).

ETIQUETAS DE OPERACIÓN

Las posibles etiquetas de operación se definen mediante el tipo de enumeración unw_dyn_operation_t, que define los siguientes valores:

UNW_DYN_STOP

Marca el final de la lista de directivas de desenrollado dinámico. Todas las entradas restantes en la matriz `op` del descriptor de región se ignoran. Se garantiza que esta etiqueta tenga un valor de 0.
UNW_DYN_SAVE_REG

Marca una instrucción que guarda el registro `reg` en el registro `val`.
UNW_DYN_SPILL_FP_REL

Marca una instrucción que vierte el registro `reg` en una ubicación relativa al puntero de marco. El desplazamiento relativo al puntero de marco está dado por el valor almacenado en el miembro `val`. Ver las secciones específicas de la arquitectura para una descripción del diseño del marco de pila.
UNW_DYN_SPILL_SP_REL

Marca una instrucción que vierte el registro `reg` en una ubicación relativa al puntero de pila. El desplazamiento relativo al puntero de pila está dado por el valor almacenado en el miembro `val`. Ver las secciones específicas de la arquitectura para una descripción del diseño del marco de pila.
UNW_DYN_ADD

Marca una instrucción que suma el valor constante `val` al registro `reg`. Para sumar o restar un valor constante, almacene el complemento a dos del valor en `val`. El conjunto de registros que se pueden especificar para esta etiqueta se describe en las secciones específicas de la arquitectura a continuación.

REGIONS DESCRIPTORS

- significado del miembro segbase en el formato table-info/table-remote-info - formato de table_data en el formato table-info/table-remote-info - tamaño de instrucción: cada paquete se cuenta como 3 instrucciones, independientemente de la plantilla (MLX) - describir la disposición del marco de pila, especialmente con respecto al direccionamiento relativo a sp y relativo a fp - UNW_DYN_ADD solo puede añadir a ``sp'' (siempre un valor negativo); usar POP_FRAMES en caso contrario
