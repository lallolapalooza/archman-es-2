NOMBRE

libsolv-bindings - acceder a libsolv desde perl/python/ruby

DESCRIPCIÓN

Las vinculaciones de lenguaje de Libsolv ofrecen una interfaz abstracta y orientada a objetos a la biblioteca. Los lenguajes compatibles son actualmente perl, python, ruby y tcl. Todo el código de ejemplo (excepto en las secciones específicas, por supuesto) enumera primero la interfaz "estilo C", luego la sintaxis para perl, python y ruby (en ese orden).

ESPECIFICIDADES PERL

Las vinculaciones de perl de Libsolv se pueden cargar con la siguiente instrucción:

use solv;

Los objetos se crean llamando al método new() en una clase o se devuelven llamando a métodos en otros objetos.

my $pool = solv::Pool->new();
my $repo = $pool->add_repo("mi_primer_repo");

Swig encapsula todos los objetos como hashes enlazados, por lo que los atributos se pueden acceder tratando el objeto como una referencia de hash estándar:

$pool->{appdata} = 42;
printf "appdata es %d\n", $pool->{appdata};

Una excepción especial a esto son los objetos iteradores, que se encapsulan como arrays enlazados para que sea posible iterar con una instrucción for():

my $iter = $pool->solvables_iter();
for my $solvable (@$iter) { ... };

Como inconveniente de este enfoque, los objetos iteradores no pueden tener atributos.

Si es necesario pasar un array a un método, normalmente se hace por referencia; si un método devuelve un array, lo devuelve en la pila de perl:

my @problems = $solver->solve(\@jobs);

Debido a un error en swig, la conversión a cadena no funciona para los objetos de libsolv. En su lugar, debe llamar al método str() del objeto.

print $dep->str() . "\n";

Swig implementa todas las constantes como variables numéricas (en lugar de las subs de constantes más naturales), así que no olvide el prefijo "$" al acceder a una constante. Tampoco olvide anteponer el espacio de nombres de la constante:

$pool->set_flag($solv::Pool::POOL_FLAG_OBSOLETEUSESCOLORS, 1);

ESPECIFICIDADES PYTHON

Las vinculaciones de python se pueden cargar con:

import solv

Los objetos se crean llamando al método constructor para una clase o se devuelven llamando a métodos en otros objetos.

pool = solv.Pool()
repo = pool.add_repo("mi_primer_repo")

Los atributos se pueden acceder como de costumbre:

pool.appdata = 42
print "appdata es %d" % (pool.appdata)

Los iteradores también funcionan como se espera:

for solvable in pool.solvables_iter():

Los arrays se pasan y devuelven como objetos de lista:

jobs = []
problems = solver.solve(jobs)

Las vinculaciones definen la conversión a cadena para muchas clases, algunas también tienen un método repr para facilitar la depuración.

print dep
print repr(repo)

Las constantes son atributos de las clases correspondientes:

pool.set_flag(solv.Pool.POOL_FLAG_OBSOLETEUSESCOLORS, 1);

ESPECIFICIDADES RUBY

Las vinculaciones de ruby se pueden cargar con:

require 'solv'

Los objetos se crean llamando al método new en una clase o se devuelven llamando a métodos en otros objetos. Tenga en cuenta que todas las clases comienzan con una letra mayúscula en ruby, por lo que la clase se llama "Solv".

pool = Solv::Pool.new
repo = pool.add_repo("mi_primer_repo")

Los atributos se pueden acceder como de costumbre:

pool.appdata = 42
puts "appdata es #{pool.appdata}"

Los iteradores también funcionan como se espera:

for solvable in pool.solvables_iter() do ...

Los arrays se pasan y devuelven como objetos de array:

jobs = []
problems = solver.solve(jobs)

La mayoría de las clases definen un método to_s, por lo que los objetos se pueden convertir fácilmente a cadena. Muchos también definen un método inspect().

puts dep
puts repo.inspect

Las constantes residen en el espacio de nombres de la clase a la que pertenecen:

pool.set_flag(Solv::Pool::POOL_FLAG_OBSOLETEUSESCOLORS, 1);

Tenga en cuenta que los métodos booleanos tienen un signo de interrogación al final para ser coherentes con otros módulos de ruby:

puts "vacío" if repo.isempty?

ESPECIFICIDADES TCL

Las vinculaciones de tcl de Libsolv se pueden cargar con la siguiente instrucción:

package require solv

Los objetos se crean llamando al nombre de la clase precedido de "new_", o se devuelven llamando a métodos en otros objetos.

set pool [solv::new_Pool]
set repo [$pool add_repo "mi_primer_repo"]

Swig proporciona un método "cget" para leer atributos de objetos y un método "configure" para escribirlos:

$pool configure -appdata 42
puts "appdata es [$pool cget -appdata]"

Las vinculaciones de tcl proporcionan una pequeña utilidad para trabajar con iteradores en estilo foreach:

set iter [$pool solvables_iter]
solv::iter s $iter { ... }

Los arrays de libsolv se mapean a las listas de tcl:

set jobs [list $job1 $job2]
set problems [$solver solve $jobs]
puts "Tenemos [llength $problems] problemas..."

La conversión a cadena se realiza llamando al método "str" del objeto.

puts [$dep str]

Hay una excepción: debe usar "stringify" para los objetos Datamatch, ya que swig informa de un conflicto con el atributo "str".

Algunas clases también admiten un método "==" para pruebas de igualdad y un método "!=".

Swig implementa todas las constantes como variables numéricas; las constantes pertenecientes a una clase de libsolv van precedidas del nombre de la clase:

$pool set_flag $solv::Pool_POOL_FLAG_OBSOLETEUSESCOLORS 1
puts [$solvable lookup_str $solv::SOLVABLE_SUMMARY]

ESPECIFICIDADES LUA

Las vinculaciones de lua de Libsolv se pueden cargar con la siguiente instrucción:

require("solv")

Los objetos se crean llamando al método constructor para una clase o se devuelven llamando a métodos en otros objetos.

pool = solv.Pool()
repo = pool:add_repo("mi_primer_repo")

Observe la sintaxis ":método" que hace que lua añada el objeto como primer argumento.

Los atributos se pueden acceder como de costumbre:

pool.appdata = 42
print("appdata es "..pool.appdata)

Los iteradores también funcionan como se espera:

for solvable in pool.solvables do
...

Note that some functions return a table instead of an iterator, so you need to use “ipairs” for iteration:

for _,solvable in ipairs(job.solvables()) do ...

Arrays are passed and returned as tables:

jobs = {}
problems = solver.solve(jobs)
if #problems != 0 then ...

The bindings define a “__tostring” method for many classes:

print(dep)
print(("Package: %s"):format(solvable))

Constants live in the namespace of the class they belong to:

pool:set_flag(Solv.Pool.POOL_FLAG_OBSOLETEUSESCOLORS, 1);

EL CLASE POOL

The pool is libsolv’s central resource manager. A pool consists of Solvables, Repositories, Dependencies, each indexed by Ids.

CONSTANTES

POOL_FLAG_PROMOTEEPOCH

Promote the epoch of the providing dependency to the requesting dependency if it does not contain an epoch. Used at some time in old rpm versions, modern systems should never need this.

POOL_FLAG_FORBIDSELFCONFLICTS

Disallow the installation of packages that conflict with themselves. Debian always allows self-conflicting packages, rpm used to forbid them but switched to also allowing them since rpm-4.9.0.

POOL_FLAG_OBSOLETEUSESPROVIDES

Make obsolete type dependency match against provides instead of just the name and version of packages. Very old versions of rpm used the name/version, then it got switched to provides and later switched back again to just name/version.

POOL_FLAG_IMPLICITOBSOLETEUSESPROVIDES

An implicit obsoletes is the internal mechanism to remove the old package on an update. The default is to remove all packages with the same name, rpm-5 switched to also removing packages providing the same name.

POOL_FLAG_OBSOLETEUSESCOLORS

Rpm’s multilib implementation distinguishes between 32bit and 64bit packages (the terminology is that they have a different color). If obsoleteusescolors is set, packages with different colors will not obsolete each other.

POOL_FLAG_IMPLICITOBSOLETEUSESCOLORS

Same as POOL_FLAG_OBSOLETEUSESCOLORS, but used to find out if packages of the same name can be installed in parallel. For current Fedora systems, POOL_FLAG_OBSOLETEUSESCOLORS should be false and POOL_FLAG_IMPLICITOBSOLETEUSESCOLORS should be true (this is the default if FEDORA is defined when libsolv is compiled).

POOL_FLAG_NOINSTALLEDOBSOLETES

Since version 4.9.0 rpm considers the obsoletes of installed packages when checking for dependency conflicts, thus you may not install a package that is obsoleted by some other installed package unless you also erase the other package.

POOL_FLAG_HAVEDISTEPOCH

Mandriva added a new field called distepoch that gets checked in version comparison if the epoch/version/release of two packages are the same.

POOL_FLAG_NOOBSOLETESMULTIVERSION

If a package is installed in multiversion mode, rpm used to ignore both the implicit obsoletes and the obsolete dependency of a package. This was changed to ignoring just the implicit obsoletes, thus you may install multiple versions of the same name, but obsoleted packages still get removed.

POOL_FLAG_ADDFILEPROVIDESFILTERED

Make the addfileprovides method only add files from the standard locations (i.e. the “bin” and “etc” directories). This is useful if you have only few packages that use non-standard file dependencies, but you still want the fast speed that addfileprovides() generates.

POOL_FLAG_NOWHATPROVIDESAUX

Disable the creation of the auxiliary whatprovides index. This saves a bit of memory but also makes the whatprovides lookups a bit slower.

POOL_FLAG_WHATPROVIDESWITHDISABLED

Make the whatprovides index also contain disabled packages. This means that you do not need to recreate the index if a package is enabled/disabled, i.e. the pool→considered bitmap is changed.

Some package managers like rpm allow dependencies on files
    contained in other packages. To allow libsolv to deal with those
    dependencies in an efficient way, you need to call the addfileprovides
    method after creating and reading all repositories. This method will scan
    all dependency for file names and then scan all packages for matching files.
    If a filename has been matched, it will be added to the provides list of the
    corresponding package. The addfileprovides_queue variant works the same way
    but returns an array containing all file dependencies. This information can
    be stored in the meta section of the repositories to speed up the next time
    the repository is loaded and addfileprovides is called.

No internaliza los datos del repositorio añadidos. Esto es útil si planeas añadir más datos, ya que la internalización es una operación costosa.

REPO_LOCALPOOL

Utiliza el pool del repodata para el almacenamiento de Ids en lugar del pool global. Útil si no quieres contaminar el pool global con muchos ids innecesarios, como al almacenar la lista de archivos.

REPO_USE_LOADING

Utiliza el repodata que se está cargando actualmente en lugar de crear uno nuevo. Esto solo tiene sentido si se usa en una devolución de llamada de carga.

REPO_EXTEND_SOLVABLES

No crea nuevos solvables para los nuevos datos, sino que busca solvables existentes y les añade los datos. Antepone el rootdir del pool a la ruta al realizar operaciones de archivo.

REPO_NO_LOCATION

No añadas un elemento de ubicación a los solvables. Útil si los solvables no están en la posición final, para que puedas agregar la ubicación correcta más adelante en tu código.

SOLV_ADD_NO_STUBS

No crees stubs para las partes del repositorio que se pueden descargar bajo demanda.

Constantes de acción:

SOLVER_NOOP

No hacer nada.

SOLVER_INSTALL

Instalar un paquete del conjunto especificado de paquetes. Intenta instalar el paquete que mejor coincida (es decir, la versión más alta de los paquetes de los repositorios con la prioridad más alta).

SOLVER_ERASE

Borrar todos los paquetes del conjunto especificado. Si un paquete no está instalado, borrarlo evitará que se instale.

SOLVER_UPDATE

Actualizar los paquetes instalados coincidentes a su mejor versión. Si ninguno de los paquetes especificados está instalado, intente actualizar los paquetes instalados a las versiones especificadas. Consulte la sección sobre actualizaciones dirigidas para obtener más información.

SOLVER_WEAKENDEPS

Permite romper las dependencias de los paquetes coincidentes. Usar con cuidado.

SOLVER_MULTIVERSION

Marca los paquetes coincidentes para instalación multiversión. Si se instalan debido a algún otro job, la instalación mantendrá instalada la versión antigua del paquete (para rpm, esto se hace usando "-i" en lugar de "-U").

SOLVER_LOCK

No cambiar el estado de los paquetes coincidentes, es decir, cuando están instalados permanecen instalados, si no, no se seleccionan para su instalación.

SOLVER_DISTUPGRADE

Actualizar los paquetes instalados coincidentes a la mejor versión incluida en uno de los repositorios. Después de esta operación, todos provienen de uno de los repositorios disponibles excepto los paquetes huérfanos. Los paquetes huérfanos son paquetes que no tienen relación con los paquetes en los repositorios, es decir, ningún paquete en los repositorios tiene el mismo nombre o obsoleta el paquete huérfano. Esta acción sincroniza los paquetes instalados con los del repositorio. Por defecto, también desactiva el bloqueo de arquitectura/vendedor/versión para los paquetes afectados para simular una instalación limpia. Esto significa que distupgrade puede realmente degradar paquetes si solo hay versiones inferiores de un paquete disponibles en los repositorios. Puede ajustar este comportamiento con las banderas del solver SOLVER_FLAG_DUP_.

SOLVER_DROP_ORPHANED

Borrar todos los paquetes instalados coincidentes si son huérfanos. Esto solo tiene sentido si hay un job de "distupgrade de todos los paquetes". Por defecto, se borran los paquetes huérfanos solo si bloquean la instalación de otros paquetes.

SOLVER_VERIFY

Corregir problemas de dependencias de los paquetes instalados coincidentes. Por defecto, se ignoran los problemas de dependencias para los paquetes instalados.

SOLVER_USERINSTALLED

Los paquetes instalados coincidentes se consideran instalados por un usuario, por lo tanto, no instalados para cumplir alguna dependencia. Esta es una entrada necesaria para el cálculo de paquetes innecesarios para jobs que tienen establecida la bandera SOLVER_CLEANDEPS.

SOLVER_ALLOWUNINSTALL

Permite al solver desinstalar los paquetes instalados coincidentes si se interponen en el camino de la resolución de una dependencia. Esto es similar a la bandera SOLVER_FLAG_ALLOW_UNINSTALL, pero limitado a un conjunto específico de paquetes.

SOLVER_FAVOR

Prefiere los paquetes especificados si el solver encuentra una alternativa. Si un job contiene varios elementos de favor/desfavor que coinciden, el último tiene prioridad.

SOLVER_DISFAVOR

Evita los paquetes especificados si el solver encuentra una alternativa. Esto también se puede usar para bloquear la instalación de paquetes recomendados o suplementados.

SOLVER_EXCLUDEFROMWEAK

Evita que los paquetes especificados satisfagan dependencias recomendadas o suplementadas. A diferencia de SOLVER_DISFAVOR, no interfiere con otras reglas.

SOLVER_JOBMASK

Una máscara que contiene todos los bits de acción anteriores.

Constantes modificadoras de acción:

SOLVER_WEAK

Convierte el job en un job débil. El solver intenta cumplir los jobs débiles, pero no informa de un problema si no es posible hacerlo.

SOLVER_ESSENTIAL

SOLVER_CLEANDEPS

SOLVER_FORCEBEST

ACTUALIZACIONES DIRIGIDAS

ACTUALIZACIONES DIRIGIDAS

Libsolv tiene dos modos para actualizaciones y actualizaciones de distribución (distupgrade): dirigidas y no dirigidas. El modo no dirigido significa que los paquetes instalados del conjunto especificado se actualizarán a la mejor versión. El modo dirigido significa que los paquetes que se pueden actualizar a un paquete del conjunto especificado se actualizarán a la mejor versión dentro del conjunto.

Aquí hay un ejemplo para explicar la sutil diferencia. Suponga que tiene el paquete A instalado en la versión "1.1", "A-1.2" está disponible en uno de los repositorios y también hay un paquete "B" que anula el paquete A.

Una actualización no dirigida de "A" actualizará el "A-1.1" instalado a paquete "B", ya que esa es la versión más nueva (B anula A y, por lo tanto, es más nueva).

Una actualización dirigida de "A" actualizará "A-1.1" a "A-1.2", ya que el conjunto de paquetes contiene tanto "A-1.1" como "A-1.2", y "A-1.2" es el más nuevo.

Una actualización no dirigida de "B" no hará nada, ya que "B" no está instalado.

Una actualización dirigida de "B" actualizará "A-1.1" a "B".

Tenga en cuenta que el valor predeterminado es hacer "auto-dirigido", por lo tanto, si el conjunto de paquetes especificado no incluye un paquete instalado, el solucionador asumirá una operación dirigida, incluso si no se usa SOLVER_TARGETED.

Esto coincide en su mayor parte con la intención del usuario, con una excepción: en el ejemplo anterior, una actualización de "A-1.2" actualizará "A-1.1" a "A-1.2" (modo dirigido), pero una segunda actualización de "A-1.2" de repente se actualizará a "B", ya que se elige el modo no dirigido porque "A-1.2" ahora está instalado.

Si desea tener control total sobre cuándo se elige el modo de direccionamiento, desactive el auto-direccionamiento con la opción del solucionador SOLVER_FLAG_NO_AUTOTARGET. En ese caso, todas las actualizaciones se considerarán no dirigidas a menos que incluyan el flag SOLVER_TARGETED.

BITS ESTABLECIDOS

Los bits establecidos especifican qué partes de los paquetes especificados fueron especificadas por el usuario. Lo utiliza el solucionador al verificar si una operación está permitida o no. Por ejemplo, el solucionador normalmente no permitirá la degradación de un paquete instalado. Pero no informará un problema si se utiliza el flag SOLVER_SETEVR, ya que asume que el usuario especificó la versión exacta y, por lo tanto, sabe lo que está haciendo.

Entonces, si un paquete "screen-1-1" está instalado para la arquitectura x86_64 y la versión "2-1" solo está disponible para la arquitectura i586, la instalación del paquete "screen-2.1" pedirá confirmación al usuario debido a la diferente arquitectura. Al utilizar la clase Selection para crear trabajos, los bits establecidos se agregan automáticamente, por ejemplo, seleccionar "screen.i586" agregará automáticamente SOLVER_SETARCH, y por lo tanto no se informará ningún problema.

LA CLASE SOLVER

La resolución de dependencias es el propósito de esta biblioteca. Se necesita un objeto solucionador para la resolución para almacenar el resultado de la ejecución del solucionador. Flags para modificar el comportamiento del solucionador:

SOLVER_FLAG_ALLOW_DOWNGRADE

Permite que el solucionador degrade paquetes sin pedir confirmación (es decir, informar un problema).

SOLVER_FLAG_ALLOW_ARCHCHANGE

Permite que el solucionador cambie la arquitectura de un paquete instalado sin pedir confirmación. Tenga en cuenta que los cambios hacia/desde noarch siempre se consideran permitidos.

Permite que el solucionador cambie el nombre de un paquete instalado, es decir, instale un paquete con un nombre diferente que anule el paquete instalado. Esta opción está activada por defecto.

SOLVER_FLAG_ALLOW_UNINSTALL

Permite que el solucionador elimine paquetes instalados para cumplir los trabajos. Esta flag también incluye las flags anteriores. Hace que la opción de trabajo SOLVER_FORCEBEST considere solo los paquetes que cumplen las políticas para los paquetes instalados, es decir, sin degradaciones, sin cambios de arquitectura, sin cambios de proveedor (ver las primeras flags de esta sección). Resuelve los paquetes instalados antes de resolver los trabajos dados. Establecer esta flag significa que el solucionador preferirá elegir una versión de paquete que se ajuste a los otros paquetes instalados en lugar de actualizar los paquetes instalados.

ACTIVE/PASSIVE VIEW

Active view lists what new packages get installed, while passive view shows what happens to the installed packages. Most often there’s not much difference between the two modes, but things get interesting if multiple packages get replaced by one new package. Say you have installed packages A-1-1 and B-1-1, and now install A-2-1 which has a new dependency that obsoletes B. The transaction elements will be

updated   A-1-1 (other: A-2-1)
obsoleted B-1-1 (other: A-2-1)

in passive mode, but

update A-2-1 (other: A-1-1)
erase  B

in active mode. If the mode contains SOLVER_TRANSACTION_SHOW_ALL, the passive mode list will be unchanged but the active mode list will just contain A-2-1.
