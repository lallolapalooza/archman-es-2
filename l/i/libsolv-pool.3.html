NOMBRE

libsolv-pool - Objeto pool de Libsolv

ATRIBUTOS PÚBLICOS

void *appdata

Un puntero de propósito libre para el usuario de la biblioteca. Liberar el pool simplemente descarta el puntero.

Stringpool ss

El pool de cadenas unificadas.

Reldep *rels

El pool de dependencias de relación unificadas.

int nrels

Número de dependencias de relación asignadas.

Repo **repos

El array de punteros de repositorio, indexado por el Id del repositorio.

int nrepos

Número de elementos del array de repositorios asignados, es decir, el tamaño del array repos.

int urepos

Número de elementos del array de repositorios usados (es decir, distintos de cero).

Repo *installed

Puntero al repositorio que contiene los paquetes instalados. Puedes leer este atributo libremente, pero deberías usar pool_set_installed() si quieres cambiarlo.

Solvable *solvables

El array de objetos Solvable.

int nsolvables

Número de objetos Solvable, es decir, el tamaño del array solvables. Ten en cuenta que el array puede contener solvables liberados; en ese caso, el puntero del repositorio del solvable será cero.

int disttype

El tipo de distribución de tu sistema, por ejemplo, DISTTYPE_DEB. Puedes leer este atributo libremente, pero deberías usar pool_setdisttype() si quieres cambiarlo.

Id *whatprovidesdata

Almacenamiento de Id multipropósito que contiene arrays de Ids terminados en cero. pool_whatprovides() devuelve un desplazamiento en estos datos.

Map *considered

Mapa de bits opcional que puede hacer que la biblioteca ignore los solvables. Si se establece un mapa de bits, solo se considerarán utilizables los solvables que tengan un bit establecido en el mapa de bits en su Id.

int debugmask

Una máscara que define qué eventos de depuración deben informarse. pool_setdebuglevel() establece esta máscara.

Datapos pos

Un objeto que almacena una posición en los datos del repositorio. Funciones como dataiterator_set_pos() establecen este objeto; el acceso a datos con un Id de solvable pseudo SOLVID_POS lo utiliza.

Queue pooljobs

Una cola donde se pueden almacenar trabajos fijos del solucionador. Estos trabajos se agregan automáticamente cuando se llama a solver_solve(); son útiles para almacenar datos de configuración, como qué paquetes deben instalarse multiversión.

CREACIÓN Y DESTRUCCIÓN

Pool *pool_create();

Crea una nueva instancia de un pool.

void pool_free(Pool *pool);

Libera un pool y todos los datos que contiene, por ejemplo, los solvables, los repositorios, las cadenas.

DEPURACIÓN Y REPORTE DE ERRORES

Constantes

SOLV_FATAL

Informa el error y llama a “exit(1)” después. No puedes enmascarar este nivel. Informa a stderr en lugar de a stdout.

SOLV_ERROR

Se utiliza para informar errores. Informa a stderr en lugar de a stdout.

SOLV_WARN

Se utiliza para informar advertencias.

SOLV_DEBUG_STATS

Se utiliza para informar datos estadísticos.

SOLV_DEBUG_RULE_CREATION

Se utiliza para informar información sobre la creación de reglas por parte del solucionador.

SOLV_DEBUG_PROPAGATE

Se utiliza para informar información sobre el proceso de propagación de reglas unitarias del solucionador.

SOLV_DEBUG_ANALYZE

Se utiliza para informar información sobre el mecanismo de generación de reglas aprendidas del solucionador.

SOLV_DEBUG_UNSOLVABLE

Se utiliza para informar información sobre cómo el solucionador maneja las reglas conflictivas.

SOLV_DEBUG_SOLUTIONS

Se utiliza para informar información sobre cómo el solucionador crea soluciones para resolver problemas.

SOLV_DEBUG_POLICY

Se utiliza para informar información sobre cómo el solucionador busca una solución óptima.

SOLV_DEBUG_RESULT

Utilizado por las funciones de depuración para mostrar resultados.

SOLV_DEBUG_JOB

Se utiliza para informar información sobre el proceso de generación de reglas de trabajos.

SOLV_DEBUG_SOLVER

Se utiliza para informar información sobre lo que el solucionador está haciendo actualmente.

SOLV_DEBUG_TRANSACTION

Se utiliza para informar información sobre el proceso de generación y ordenación de transacciones.

SOLV_DEBUG_TO_STDERR

Escribe mensajes de depuración en stderr en lugar de stdout.

Funciones

void pool_debug(Pool *pool, int type, const char *format, ...);

Informa un mensaje del tipo type. Puedes filtrar mensajes de depuración estableciendo una máscara de depuración.

void pool_setdebuglevel(Pool *pool, int level);

Establece una máscara de depuración predefinida. Un nivel más alto generalmente significa que se establecen más bits en la máscara, por lo tanto, se imprimen más mensajes.

void pool_setdebugmask(Pool *pool, int mask);

Establece la máscara de depuración para filtrar mensajes de depuración.

int pool_error(Pool *pool, int ret, const char *format, ...);

Establece la cadena de error del pool. El valor ret se usa simplemente como valor de retorno de la función para que puedas escribir código como return pool_error(...);. Si la máscara de depuración contiene el bit SOLV_ERROR, también se llama a pool_debug() con el mensaje y el tipo SOLV_ERROR.

extern char *pool_errstr(Pool *pool);

Devuelve la cadena de error actual almacenada en el pool. Al igual que con el valor errno de libc, la cadena solo es significativa después de que una función devuelve un error.

void pool_setdebugcallback(Pool *pool, void (*debugcallback)(Pool *, void *data, int type, const char *str), void *debugcallbackdata);

Establece una función de callback de depuración personalizada. En lugar de escribir en stdout o stderr, se llamará a la función de callback.

CONFIGURACIÓN DEL POOL

Constantes

DISTTYPE_RPM

Para sistemas que utilizan rpm como gestor de paquetes de bajo nivel.

DISTTYPE_DEB

Para sistemas que utilizan dpkg como gestor de paquetes de bajo nivel.

DISTTYPE_ARCH

Para sistemas que utilizan el gestor de paquetes de Arch Linux.

DISTTYPE_HAIKU

Para sistemas que utilizan paquetes haiku.

POOL_FLAG_PROMOTEEPOCH

Promueve la época de la dependencia de proveedor a la dependencia solicitante si esta no contiene una época. Se usó en versiones antiguas de rpm, los sistemas modernos nunca deberían necesitar esto.

POOL_FLAG_FORBIDSELFCONFLICTS

Prohíbe la instalación de paquetes que entran en conflicto consigo mismos. Debian siempre permite paquetes que entran en conflicto consigo mismos, rpm solía prohibirlos pero recientemente cambió a permitir también.

POOL_FLAG_OBSOLETEUSESPROVIDES

Hace que la dependencia de tipo obsoleto coincida con los proveedores en lugar de solo con el nombre y la versión de los paquetes. Versiones muy antiguas de rpm usaban el nombre/versión, luego se cambió a proveedores y más tarde se volvió a usar solo nombre/versión.

POOL_FLAG_IMPLICITOBSOLETEUSESPROVIDES

Un obsoleto implícito es el mecanismo interno para eliminar el paquete antiguo en una actualización. Th

e default es eliminar todos los paquetes con el mismo nombre, rpm-5 cambió para eliminar también los paquetes que proporcionan el mismo nombre.

POOL_FLAG_OBSOLETEUSESCOLORS

La implementación multilib de Rpm (utilizada en RedHat y Fedora) distingue entre paquetes de 32 y 64 bits (la terminología es que tienen un color diferente). Si obsoleteusescolors está activado, los paquetes con diferentes colores no se anularán entre sí.

POOL_FLAG_IMPLICITOBSOLETEUSESCOLORS

Igual que POOL_FLAG_OBSOLETEUSESCOLORS, pero se utiliza para determinar si los paquetes del mismo nombre se pueden instalar en paralelo. Para los sistemas Fedora actuales, POOL_FLAG_OBSOLETEUSESCOLORS debe ser falso y POOL_FLAG_IMPLICITOBSOLETEUSESCOLORS debe ser verdadero (este es el valor predeterminado si FEDORA está definido cuando se compila libsolv).

POOL_FLAG_NOINSTALLEDOBSOLETES

Las nuevas versiones de rpm consideran los obsoletes de los paquetes instalados al verificar dependencias, por lo tanto, no puede instalar un paquete que es obsoleto por algún otro paquete instalado, a menos que también elimine el otro paquete.

POOL_FLAG_HAVEDISTEPOCH

Mandriva agregó un nuevo campo llamado distepoch que se verifica en la comparación de versiones si la época/versión/lanzamiento de dos paquetes son los mismos.

POOL_FLAG_NOOBSOLETESMULTIVERSION

Si un paquete está instalado en modo multiversión, rpm solía ignorar tanto los obsoletes implícitos como la dependencia de obsoletes de un paquete. Esto se cambió para ignorar solo los obsoletes implícitos, por lo tanto, puede instalar múltiples versiones del mismo nombre, pero los paquetes obsoletos aún se eliminan.

POOL_FLAG_ADDFILEPROVIDESFILTERED

Hacer que el método addfileprovides solo agregue archivos de las ubicaciones estándar (es decir, los directorios “bin” y “etc”). Esto es útil si tiene pocos paquetes que utilizan dependencias de archivos no estándar, pero aún desea la velocidad rápida que genera addfileprovides().

Funciones

int pool_setdisttype(Pool *pool, int disttype);

Establece el tipo de paquete de su sistema. El disttype se utiliza, por ejemplo, para definir la semántica de comparación de paquetes. El disttype predeterminado de Libsolv debe coincidir con el gestor de paquetes de su sistema, por lo que solo necesita usar esta función si desea utilizar la biblioteca para resolver problemas de empaquetado para diferentes sistemas. La función devuelve el disttype antiguo en caso de éxito y -1 si el nuevo disttype no es compatible. Tenga en cuenta que todas las llamadas a pool_setarch y pool_setarchpolicy deben venir después de la llamada a pool_setdisttype, ya que utilizan el ID de arquitectura noarch/any/all.

int pool_set_flag(Pool *pool, int flag, int value);

Establece una bandera a un nuevo valor. Devuelve el valor antiguo de la bandera.

int pool_get_flag(Pool *pool, int flag);

Obtiene el valor de una bandera del pool. Consulte la sección de constantes para conocer el significado de las banderas.

void pool_set_rootdir(Pool *pool, const char *rootdir);

Establece un directorio raíz específico. Algunas funciones de la biblioteca admiten una bandera que indica a la función que anteponga rootdir a los nombres de archivos y directorios.

const char *pool_get_rootdir(Pool *pool);

Devuelve el valor actual del directorio raíz.

char *pool_prepend_rootdir(Pool *pool, const char *dir);

Antepone el directorio raíz a la cadena del argumento dir. La cadena devuelta ha sido asignada recientemente y necesita ser liberada después de su uso.

char *pool_prepend_rootdir_tmp(Pool *pool, const char *dir);

Igual que pool_prepend_rootdir, pero utiliza el espacio temporal del pool para la asignación.

void pool_set_installed(Pool *pool, Repo *repo);

Establece qué repositorio debe tratarse como el repositorio “instalado”, es decir, el que contiene información sobre los paquetes instalados.

void pool_set_languages(Pool *pool, const char **languages, int nlanguages);

Establece el idioma de su sistema. La biblioteca proporciona funciones de búsqueda que devuelven cadenas localizadas, por ejemplo, para descripciones de paquetes. Puede establecer una matriz de idiomas para proporcionar un mecanismo de reserva si un idioma no está disponible.

void pool_setarch(Pool *pool, const char *arch);

Establece la arquitectura de su sistema. La arquitectura se utiliza para determinar qué paquetes son instalables y cuáles no. El argumento arch es normalmente el valor “machine” de la llamada al sistema “uname”.

void pool_setarchpolicy(Pool *, const char *);

Establece la política de arquitectura para su sistema. Esta es la versión general de pool_setarch (de hecho, pool_setarch llama a pool_setarchpolicy internamente). Consulte la sección sobre políticas de arquitectura para obtener más información.

void pool_addvendorclass(Pool *pool, const char **vendorclass);

Agrega una nueva clase de equivalencia de proveedor al sistema. Una clase de equivalencia de proveedor define si un paquete instalado de un proveedor puede ser reemplazado por un paquete proveniente de un proveedor diferente. El argumento vendorclass debe ser una matriz de cadenas terminada en NULL. Consulte la sección sobre políticas de proveedor para obtener más información.

void pool_setvendorclasses(Pool *pool, const char **vendorclasses);

Establece todas las equivalencias de proveedor permitidas. El argumento vendorclasses debe ser una matriz terminada en NULL que consta de todas las clases permitidas concatenadas. Cada clase en sí debe terminar en NULL, por lo que la última clase termina con dos elementos NULL, uno para finalizar la clase y otro para finalizar la lista de clases.

void pool_set_custom_vendorcheck(Pool *pool, int (*vendorcheck)(Pool *, Solvable *, Solvable *));

Define un mecanismo personalizado de verificación de proveedor. Puede usar esto si el mecanismo interno de clase de equivalencia de proveedor de libsolv no satisface sus necesidades.

void pool_setloadcallback(Pool *pool, int (*cb)(Pool *, Repodata *, void *), void *loadcbdata);

Define una función de devolución de llamada que se llamará cuando los metadatos del repositorio necesiten cargarse bajo demanda. Consulte la sección sobre carga bajo demanda en el manual de libsolv-repodata.

void pool_setnamespacecallback(Pool *pool, Id (*cb)(Pool *, void *, Id, Id), void *nscbdata);

Define una función de devolución de llamada para implementar soporte de espacio de nombres personalizado. Consulte la sección sobre dependencias de espacio de nombres.

GESTIÓN DE IDENTIFICADORES Y POOLS

Constantes

ID_EMPTY

El Id de la cadena vacía, siempre es el Id 1.

REL_LT

Representa una relación de “<”.

REL_EQ

Representa una relación de “=”.

REL_GT

Representa una relación de “>”. Puede usar combinaciones de REL_GT, REL_EQ y REL_LT combinadas con OR para crear cualquier relación que desee.

REL_AND

Una operación AND booleana, las partes “nombre” y “evr” de la relación pueden ser dos subdependencias. Los paquetes deben coincidir con ambas partes de la dependencia.

REL_OR

Una operación OR booleana, las partes “nombre” y “evr” de la relación pueden ser dos subdependencias. Los paquetes pueden coincidir con cualquier parte de la dependencia.

REL_WITH

Como REL_AND, pero los paquetes deben coincidir con ambas dependencias simultáneamente. Consulte la sección sobre dependencias booleanas para obtener más información.

REL_NAMESPACE

Una relación especial de espacio de nombres. Consulte la sección sobre dependencias de espacio de nombres para obtener más información.

REL_ARCH

Una dependencia de filtro de arquitectura. La parte “nombre” de la relación es una subdependencia, la parte “evr” es el Id de una arquitectura que deben tener los paquetes correspondientes (tenga en cuenta que esta es una coincidencia exacta que ignora las políticas de arquitectura).

REL_FILECONFLICT

Una dependencia interna de conflicto de archivos utilizada para representar conflictos de archivos. Consulte la función pool_add_fileconflicts_deps().

REL_COND

Una dependencia condicional, la subdependencia “nombre” solo se considera si se cumple la subdependencia “evr”. Consulte la sección sobre dependencias booleanas para obtener más información.

REL_UNLESS

Una dependencia condicional, la subdependencia “nombre” solo se considera si la subdependencia “evr” NO se cumple. Consulte la sección sobre dependencias booleanas para obtener más información.

REL_COMPAT

Una dependencia compat utilizada en Haiku para representar rangos de versiones. La parte “nombre” es la versión real, la parte “evr” es la versión de compatibilidad hacia atrás.

REL_KIND

Una pseudo dependencia que limita los solvables a un tipo específico. Se espera que el tipo sea un prefijo del nombre del solvable, por ejemplo, “patch:foo” sería del tipo “patch”. “REL_KIND” solo se admite en las funciones de selección.

REL_MULTIARCH

Una anotación multiarch de debian. El valor más común para la parte “evr” es “any”.

REL_ELSE

La parte else de una dependencia “REL_COND” o “REL_UNLESS”. Consulte la sección sobre dependencias booleanas.

REL_ERROR

Una dependencia ilegal. Esto es útil para codificar errores de análisis de dependencias.

Funciones

POOL FUNCTIONS

Id pool_str2id(Pool *pool, const char *str, int create);

Agrega una cadena al pool de cadenas unificadas, devolviendo el Id de la cadena. Si create es cero, no se agregarán nuevas cadenas al pool, en su lugar se devolverá el Id 0.

Id pool_strn2id(Pool *pool, const char *str, unsigned int len, int create);

Igual que pool_str2id, pero solo se utilizan len caracteres de la cadena. Esto se puede utilizar para agregar subcadenas al pool.

Id pool_rel2id(Pool *pool, Id name, Id evr, int flags, int create);

Crea una dependencia relacional a partir de otras dependencias, name y evr, y un flag. Consulte las constantes REL_ para ver los flags admitidos. Al igual que con pool_str2id, create define si se agregarán nuevas dependencias o si se devolverá el Id cero.

Id pool_id2langid(Pool *pool, Id id, const char *lang, int create);

Adjunta un sufijo de idioma a un Id de cadena. Esta función se puede utilizar para crear Ids de nombres de clave de idioma a partir de nombres de clave; es el equivalente funcional de convertir el argumento id a una cadena, agregar un carácter “:” y el argumento lang a la cadena, y luego convertir el resultado de nuevo en un Id.

const char *pool_id2str(const Pool *pool, Id id);

Convierte un Id de nuevo en una cadena. Si el Id es un Id relacional, se convertirá la parte “nombre”.

const char *pool_id2rel(const Pool *pool, Id id);

Devuelve la cadena de relación de un Id relacional. Devuelve una cadena vacía si el Id pasado no es una relación.

const char *pool_id2evr(const Pool *pool, Id id);

Devuelve la parte “evr” de un Id relacional como cadena. Devuelve una cadena vacía si el Id pasado no es una relación.

const char *pool_dep2str(Pool *pool, Id id);

Convierte un Id de nuevo en una cadena. Si el Id pasado pertenece a una relación, se devuelve una cadena que representa la relación. Tenga en cuenta que en ese caso, la cadena se asigna en el espacio temporal del pool.

void pool_freeidhashes(Pool *pool);

Libera los hashes utilizados para unificar cadenas y relaciones. Puede utilizar esta función para ahorrar memoria si sabe que ya no creará nuevas cadenas y relaciones.

FUNCIONES DE SOLVABLE

Solvable *pool_id2solvable(const Pool *pool, Id p);

Convierte un Id de solvable en un puntero a los datos del solvable. Tenga en cuenta que el puntero puede volverse inválido si se crean nuevos solvables o se eliminan solvables antiguos, ya que la matriz que almacena todos los solvables puede ser reasignada.

Id pool_solvable2id(const Pool *pool, Solvable *s);

Convierte un puntero a los datos del solvable en un Id de solvable.

const char *pool_solvid2str(Pool *pool, Id p);

Devuelve una cadena que representa el solvable con el Id p. La cadena será alguna representación canónica del solvable, generalmente una combinación del nombre, la versión y la arquitectura.

const char *pool_solvable2str(Pool *pool, Solvable *s);

Igual que pool_solvid2str, pero en lugar del Id, se pasa un puntero al solvable.

COINCIDENCIA DE DEPENDENCIAS

Constantes

EVRCMP_COMPARE

Compara todas las partes de la versión, trata las partes faltantes como cadenas vacías.

EVRCMP_MATCH_RELEASE

Un modo especial para la coincidencia de cadenas de versiones rpm. Si una versión omite la parte de lanzamiento, coincide con todos los lanzamientos. En ese caso, se devuelven los valores especiales “-2” y “2”, dependiendo de cuál de las dos versiones no tenía parte de lanzamiento.

EVRCMP_MATCH

Una coincidencia genérica, las partes faltantes siempre coinciden.

EVRCMP_COMPARE_EVONLY

Solo compara las partes de época y versión, ignora la parte de lanzamiento.

Funciones

int pool_evrcmp(const Pool *pool, Id evr1id, Id evr2id, int mode);

Compara dos Ids de versión, devuelve -1 si la primera versión es menor que la segunda versión, 0 si son idénticas, y 1 si la primera versión es mayor que la segunda.

int pool_evrcmp_str(const Pool *pool, const char *evr1, const char *evr2, int mode);

Igual que pool_evrcmp(), pero utiliza cadenas en lugar de Ids.

int pool_evrmatch(const Pool *pool, Id evrid, const char *epoch, const char *version, const char *release);

Coincide un Id de versión con una época, una versión y una cadena de lanzamiento. Pasar NULL significa que la parte debe coincidir con todo.

int pool_match_dep(Pool *pool, Id d1, Id d2);

Devuelve “1” si la dependencia d1 (el proveedor) coincide con la dependencia d2, de lo contrario devuelve “0”. Para que dos dependencias coincidan, tanto las partes de “nombre” deben coincidir como el rango de versiones descrito por las partes “evr” deben superponerse.

int pool_match_nevr(Pool *pool, Solvable *s, Id d);

Al igual que pool_match_dep, pero el proveedor es la dependencia "self-provides" del Solvable s, es decir, la dependencia “s→name = s→evr”.

int pool_satisfieddep_map(Pool *pool, const Map *map, Id dep);

Devuelve “1” si la dependencia dep es satisfecha por los paquetes especificados en map, de lo contrario devuelve “0”.

ÍNDICE WHATPROVIDES

void pool_createwhatprovides(Pool *pool);

Crea un índice que mapea Ids de dependencias a conjuntos de paquetes que proporcionan la dependencia.

void pool_freewhatprovides(Pool *pool);

Libera el índice whatprovides para ahorrar memoria.

Id pool_whatprovides(Pool *pool, Id d);

Devuelve un desplazamiento en la matriz whatprovidesdata del Pool. Los solvables con los Ids almacenados a partir de ese desplazamiento proporcionan la dependencia d. La lista de solvables está terminada en nulo.

Id *pool_whatprovides_ptr(Pool *pool, Id d);

En lugar de devolver el desplazamiento, devuelve el puntero a los Ids almacenados en ese desplazamiento. Tenga en cuenta que este puntero tiene un tiempo de validez muy limitado, ya que cualquier llamada que agregue nuevos valores al área whatprovidesdata puede reasignar la matriz.

Id pool_queuetowhatprovides(Pool *pool, Queue *q);

Agrega el contenido de la Cola q al final de la matriz whatprovidesdata, devolviendo el desplazamiento en la matriz.

void pool_addfileprovides(Pool *pool);

Algunos administradores de paquetes como rpm permiten dependencias en archivos contenidos en otros paquetes. Para permitir que libsolv trate esas dependencias de manera eficiente, necesita llamar al método addfileprovides después de crear y leer todos los repositorios. Este método escanee todas las dependencias en busca de nombres de archivo y luego escanee todos los paquetes en busca de archivos coincidentes. Si se ha emparejado un nombre de archivo, se agregará a la lista de proporciona del paquete correspondiente.

void pool_addfileprovides_queue(Pool *pool, Queue *idq, Queue *idqinst);

Igual que pool_addfileprovides, pero los Ids agregados se devuelven en dos Colas, idq para todos los repositorios excepto el que contiene los paquetes “instalados”, idqinst para este último. Esta información se puede almacenar en la sección meta de los repositorios para acelerar la próxima vez que se cargue el repositorio y se llame a addfileprovides.

void pool_set_whatprovides(pool, Id id, Id offset);

Establece manualmente una entrada en el índice whatprovides. Nunca hará esto para dependencias de paquetes, ya que esas entradas se crean llamando a la función pool_createwhatprovides(). Pero esta función es útil para proporciona de espacios de nombres si no desea utilizar una llamada de retorno de espacio de nombres para establecer perezosamente los proporciona. El argumento offset es un desplazamiento en la matriz whatprovides, por lo que puede usar “1” como valor falso y “2” como valor verdadero.

void pool_flush_namespaceproviders(Pool *pool, Id ns, Id evr);

Borra la caché de los proveedores para dependencias de espacios de nombres que coinciden con el espacio de nombres ns. Si el argumento evr no es cero, se borra la dependencia del espacio de nombres para esa dependencia específica, de lo contrario se borran todas las dependencias de espacios de nombres coincidentes. Consulte la sección sobre dependencias de espacios de nombres para obtener más información.

void pool_add_fileconflicts_deps(Pool *pool, Queue *conflicts);

Algunos administradores de paquetes como rpm informan conflictos cuando la instalación de un paquete sobrescribe un archivo de otro paquete instalado con contenido diferente. Dado que la información del contenido del archivo no se almacena en los metadatos del repositorio, esos conflictos solo se pueden detectar después de que se descargan los paquetes. Libsolv proporciona una función

para comprobar conflictos de este tipo, pool_findfileconflicts(). Si se encuentran conflictos, estos se pueden agregar como dependencias especiales REL_FILECONFLICT, de modo que el solucionador estará al tanto del conflicto cuando se vuelva a ejecutar.

FUNCIONES DE UTILIDAD

char *pool_alloctmpspace(Pool *pool, int len);

Asigna espacio en el área de espacio temporal del pool. Este espacio tiene una vida útil limitada; se liberará automáticamente después de realizar 16 (actualmente) llamadas adicionales a pool_alloctmpspace().

void pool_freetmpspace(Pool *pool, const char *space);

Devuelve al sistema el espacio asignado con pool_alloctmpspace(). No es necesario utilizar esta función, ya que el espacio se recupera automáticamente, pero puede ser útil para extender la vida útil de otros punteros al área de espacio temporal del pool.

const char *pool_bin2hex(Pool *pool, const unsigned char *buf, int len);

Convierte datos binarios a hexadecimal, devolviendo una cadena asignada en el área de espacio temporal del pool.

char *pool_tmpjoin(Pool *pool, const char *str1, const char *str2, const char *str3);

Une tres cadenas y devuelve el resultado en el área de espacio temporal del pool. Puede usar argumentos NULL si solo desea unir menos cadenas.

char *pool_tmpappend(Pool *pool, const char *str1, const char *str2, const char *str3);

Similar a pool_tmpjoin(), pero si el primer argumento es el último espacio asignado en el área de espacio temporal del pool, este será reemplazado por el resultado de la unión y no se utilizará una nueva ranura de espacio temporal. Por lo tanto, puede unir más de tres cadenas mediante una combinación de una llamada a pool_tmpjoin() y múltiples llamadas a pool_tmpappend(). Tenga en cuenta que el puntero str1 ya no es utilizable después de la llamada.

POLÍTICAS DE ARQUITECTURA

Una política de arquitectura define una lista de arquitecturas que pueden instalarse en el sistema y también la relación entre ellas (es decir, el orden). Las arquitecturas pueden delimitarse con tres caracteres diferentes:

':'

Sin relación entre las arquitecturas. Un paquete de una arquitectura no puede ser reemplazado por uno de la otra arquitectura.

'>'

La primera arquitectura es mejor que la segunda. Un paquete instalado de la segunda arquitectura puede ser reemplazado por uno de la primera arquitectura y viceversa. El solucionador seleccionará la mejor arquitectura si las versiones son las mismas.

'='

Las dos arquitecturas son libremente intercambiables. Se utiliza para definir alias para arquitecturas.

Un ejemplo sería 'x86_64:i686=athlon>i586'. Esto significa que los paquetes x86_64 solo pueden ser reemplazados por otros paquetes x86_64, los paquetes i686 pueden ser reemplazados por paquetes i686 e i586 (pero se preferirán los paquetes i686) y athlon es otro nombre para la arquitectura i686.

Puede desactivar las comprobaciones de reemplazo de arquitectura con la bandera SOLVER_FLAG_ALLOW_ARCHCHANGE del Solver.

VENDOR POLICIES

Vendor policies control how solvables with different vendors are treated. By default, solvables from different vendors are not considered equal. For example, if you have installed a package 'foo' from vendor 'vendorA' and you want to install 'foo' from vendor 'vendorB', the solver will say that 'foo' is already installed and not offer the replacement. This is because it is very likely that packages from different vendors are incompatible, even if they have the same name and version.

Vendor policies can be used to override this behavior. You can define vendor equivalence classes. Packages from a vendor belonging to a certain class may be replaced by packages from any other vendor in the same class. This feature is especially useful for vendor groups that coordinate their package building. For example, you could define a vendor equivalence class for all vendors that belong to 'vendor group X'. Then, if you have a package installed from 'vendorA' (which belongs to 'vendor group X'), you could replace it with a package from 'vendorB' (also belonging to 'vendor group X').

To define vendor equivalence classes, you use the pool_add_vendor_group function. The function takes a list of vendor strings and adds them to a new equivalence class. You can call this function multiple times to define multiple equivalence classes. The set of allowed vendor changes for an installed package is calculated by building the union of all equivalence classes the vendor of the installed package is part of.

You can turn off the vendor replacement checks with the Solver’s SOLVER_FLAG_ALLOW_VENDORCHANGE flag.

BOOLEAN DEPENDENCIES

Boolean dependencies allow building complex expressions from simple dependencies. Note that depending on the package manager only a subset of those may be useful. For example, debian currently only allows an "OR" expression.

REL_OR

The expression is true if either the first dependency or the second one is true. This is useful for package dependencies like “Requires”, where you can specify that either one of the packages need to be installed.

REL_AND

The expression is true if both dependencies are true. The packages fulfilling the dependencies may be different, i.e. “Supplements: perl REL_AND python” is true if both a package providing perl and a package providing python are installed.

REL_WITH

The expression is true if both dependencies are true and are fulfilled by the same package. Thus “Supplements: perl REL_WITH python” would only be true if a package is installed that provides both dependencies (some kind of multi-language interpreter).

REL_COND

The expression is true if the first dependency is true or the second dependency is false. “A REL_COND B” is equivalent to “A REL_OR (NOT B)” (except that libsolv does not expose “NOT”).

REL_UNLESS

The expression is true if the first dependency is true and the second dependency is false. “A REL_UNLESS B” is equivalent to “A REL_AND (NOT B)” (except that libsolv does not expose “NOT”).

REL_ELSE

The “else” part of a “REL_COND” or “REL_UNLESS” dependency. It has to be directly in the evr part of the condition, e.g. “foo REL_COND (bar REL_ELSE baz)”. For “REL_COND” this is equivalent to writing “(foo REL_COND bar) REL_AND (bar REL_OR baz)”. For “REL_UNLESS” this is equivalent to writing “(foo REL_UNLESS bar) REL_OR (bar REL_AND baz)”.

Each sub-dependency of a boolean dependency can in turn be a boolean dependency, so you can chain them to create complex dependencies.

NAMESPACE DEPENDENCIES

Namespace dependencies can be used to implement dependencies on attributes external to libsolv. An example would be a dependency on the language set by the user. This types of dependencies are usually only used for “Conflicts” or “Supplements” dependencies, as the underlying package manager does not know how to deal with them.

If the library needs to evaluate a namespace dependency, it calls the namespace callback function set in the pool. The callback function can return a set of packages that “provide” the dependency. If the dependency is provided by the system, the returned set should consist of just the system solvable (Solvable Id 1).

The returned set of packages must be returned as offset into the whatprovidesdata array. You can use the pool_queuetowhatprovides function to convert a queue into such an offset. To ease programming the callback function, the return values “0” and “1” are not interpreted as an offset. “0” means that no package is in the return set, “1” means that just the system solvable is in the set.

The returned set is cached, so that for each namespace dependency the callback is just called once. If you need to flush the cache (maybe because the user has selected a different language), use the pool_flush_namespaceproviders() function.
