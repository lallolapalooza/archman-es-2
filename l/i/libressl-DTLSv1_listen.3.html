Paquete: libressl

Licencias: ISC, custom:OpenSSL

DTLSV1_LISTEN(3) Manual de funciones de la biblioteca DTLSV1_LISTEN(3)

NOMBRE

DTLSv1_listen — escuchar conexiones DTLS entrantes

SINOPSIS

biblioteca “libssl” libcrypto
#include <openssl/ssl.h>

int
DTLSv1_listen(SSL *ssl, struct sockaddr *peer);

DESCRIPCIÓN

DTLSv1_listen() escucha nuevas conexiones DTLS entrantes. Si se recibe un ClientHello que no contiene una cookie, entonces DTLSv1_listen() responde con un HelloVerifyRequest. Si se recibe un ClientHello con una cookie verificada, entonces el control se devuelve al código del usuario para permitir que se complete el handshake (por ejemplo, usando SSL_accept(3)).

DTLSv1_listen() está implementado actualmente como una macro.

Los protocolos basados en datagramas pueden ser susceptibles a ataques de denegación de servicio. Un atacante DTLS podría, por ejemplo, enviar una serie de solicitudes de inicio de handshake que hagan que el servidor asigne estado (y posiblemente realice operaciones criptográficas), consumiendo así recursos del servidor. El atacante también podría (con UDP) simplemente falsificar la dirección IP de origen en dicho ataque.

Como contramedida a eso, DTLS incluye un mecanismo de cookie sin estado. La idea es que cuando un cliente intenta conectarse a un servidor, envía un mensaje ClientHello. El servidor responde con un HelloVerifyRequest que contiene una cookie única. El cliente luego reenvía el ClientHello, pero esta vez incluye la cookie en el mensaje, demostrando así que el cliente es capaz de recibir mensajes enviados a esa dirección. Todo esto puede ser realizado por el servidor sin asignar ningún estado y, por lo tanto, sin consumir recursos costosos.

OpenSSL implementa esta capacidad a través de la función DTLSv1_listen(). El parámetro ssl debe ser un objeto SSL recién asignado con sus BIOs de lectura y escritura establecidos, de la misma manera que se haría para una llamada a SSL_accept(3). Típicamente, el BIO de lectura estará en un estado "no conectado" y, por lo tanto, será capaz de recibir mensajes de cualquier par.

Cuando se recibe un ClientHello que contiene una cookie que ha sido verificada, entonces DTLSv1_listen() retornará con el parámetro ssl actualizado a un estado en el que el handshake puede ser continuado por una llamada a (por ejemplo) SSL_accept(3). Además, la estructura struct sockaddr apuntada por peer se llenará con los detalles del par que envió el ClientHello. Es responsabilidad del código que llama asegurarse de que la ubicación de peer sea lo suficientemente grande para acomodar el esquema de direccionamiento en uso. Por ejemplo, esto podría hacerse asignando espacio para una struct sockaddr_storage y convirtiendo el puntero a ella a una struct sockaddr * para la llamada a DTLSv1_listen(). Típicamente, se espera que el código de usuario "conecte" el socket subyacente al par y continúe el handshake en un estado conectado.

Antes de llamar a DTLSv1_listen(), el código de usuario debe asegurarse de que las devoluciones de llamada de generación y verificación de cookies se hayan configurado usando SSL_CTX_set_cookie_generate_cb() y SSL_CTX_set_cookie_verify_cb() respectivamente.

Dado que DTLSv1_listen() opera de forma completamente sin estado mientras procesa ClientHellos entrantes, no puede procesar mensajes fragmentados (ya que esto requeriría la asignación de estado). Una implicación de esto es que DTLSv1_listen() solo admite ClientHellos que caben dentro de un solo datagrama.

VALORES DE RETORNO

A partir de OpenSSL 1.1.0, un valor de retorno de >= 1 indica éxito. En este caso, el valor de peer se llenará y el objeto ssl se configurará listo para continuar el handshake.

Un valor de retorno de 0 indica un error no fatal. Esto podría ser (por ejemplo) debido a E/S sin bloqueo, o a que se ha recibido algún mensaje inválido de un par. Los errores pueden colocarse en la cola de errores de OpenSSL con información adicional si es apropiado. Típicamente, se espera que el código de usuario reintente la llamada a DTLSv1_listen() en caso de un error no fatal. Cualquier error antiguo en la cola de errores se borrará en la llamada subsiguiente.

Un valor de retorno de <0 indica un error fatal. Esto podría ser (por ejemplo) debido a un fallo al asignar suficiente memoria para la operación.

Antes de OpenSSL 1.1.0, los errores fatales y no fatales producían valores de retorno <= 0 (en implementaciones típicas, el código de usuario trata todos los errores como no fatales), mientras que los valores de retorno >0 indican éxito.
