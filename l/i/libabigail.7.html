NOMBRE

libabigail - Biblioteca para analizar y comparar ABIs de ELF

DESCRIPCIÓN GENERAL DEL FRAMEWORK ABIGAIL

ABIGAIL significa Application Binary Interface Generic Analysis and Instrumentation Library (Biblioteca Genérica de Análisis e Instrumentación de Interfaz Binaria de Aplicación).

El tipo de incompatibilidades de interfaz en las que se centra Abigail está relacionado con cambios en los símbolos de funciones y variables exportadas de ELF, así como con cambios en la disposición y tamaño de los tipos de datos de las funciones y variables exportadas por bibliotecas compartidas.

En otras palabras, si el tipo de retorno de una función exportada por una biblioteca compartida cambia de una manera incompatible de una versión a otra de una determinada biblioteca compartida, queremos que Abigail ayude a la gente a detectarlo.

Además de esta representación interna, libabigail proporciona utilidades para realizar comparaciones profundas de dos ABIs. Es decir, puede comparar los tipos de dos conjuntos de funciones o variables y representar el resultado de una manera que permite emitir informes textuales sobre las diferencias.

Esto nos permite escribir herramientas como abidiff, que pueden comparar la ABI de dos bibliotecas compartidas y representar el resultado de una manera suficientemente significativa para ayudarnos a detectar incompatibilidades de ABI. Hay varias otras herramientas que se construyen utilizando el framework de Abigail.

CONCEPTOS

Artefactos de ABI

El conjunto de artefactos de ABI para un binario se llama Corpus de ABI.

Los tipos escalares tienen un nombre, un tamaño y otras propiedades escalares.

Un tipo agregado generalmente está constituido por subtipos.

Por ejemplo, los tipos de clase o unión son un tipo de tipo agregado. Tienen un nombre, un tamaño y miembros. Cada miembro puede ser:

  • un miembro de datos con un tipo que representa un subtipo del tipo agregado, un desplazamiento y un nombre
  • o una función con un tipo que representa otro subtipo del tipo agregado y un nombre. Algunas funciones miembro (virtuales) también pueden tener un desplazamiento.

Otro ejemplo de tipo agregado es un tipo de función, que es la unión del tipo de retorno y los tipos de parámetros de la función.

Cambios de ABI

Libabigail representa y analiza cambios en tipos, funciones, variables y símbolos ELF.

Estos diferentes tipos de cambios de artefactos de ABI se categorizan según el impacto que tienen en la compatibilidad de la ABI.

Los cambios de artefactos de ABI son reportados por herramientas como abidiff y abipkgdiff en informes de diferencias textuales organizados en torno a los diferentes tipos de cambios que se enumeran a continuación.

Tenga en cuenta que los usuarios pueden instruir a las herramientas para que eviten emitir informes sobre ciertos cambios. Esto se hace a través de especificaciones de supresión.

Cambios inofensivos

Un cambio en el informe de diferencias se considera inofensivo si *no* causa ningún problema de compatibilidad de ABI. Es decir, no impide que una aplicación enlazada dinámicamente contra una versión dada de una biblioteca siga funcionando con las versiones posteriores modificadas de la misma biblioteca.

Por defecto, abidiff y abipkgdiff filtran los cambios inofensivos del informe de diferencias.

Cambios perjudiciales

Un cambio de ABI se considera perjudicial si *puede* causar problemas de compatibilidad de ABI. Es decir, puede impedir que una aplicación enlazada dinámicamente contra una versión dada de una biblioteca siga funcionando con las versiones posteriores modificadas de la misma biblioteca.

Dicho de otra manera, un cambio perjudicial es un cambio que no es inofensivo.

Un cambio perjudicial necesita ser revisado absolutamente por un ser humano para saber si realmente causa un problema de compatibilidad de ABI.

Por defecto, abidiff muestra cambios perjudiciales para funciones y variables globales.

Si la herramienta emite al menos un cambio perjudicial, entonces el bit ABIDIFF_ABI_CHANGE del campo de bits devuelto en el código de salida se establece en 1.

Cambios incompatibles

Un cambio incompatible es un cambio perjudicial que causa problemas de incompatibilidad de ABI. En el lenguaje coloquial de los programadores, se dice que tal cambio *rompe la ABI*.

Si la herramienta abidiff o abipkgdiff emite al menos un cambio incompatible, entonces los bits ABIDIFF_ABI_INCOMPATIBLE_CHANGE y ABIDIFF_ABI_CHANGE del campo de bits devuelto en el código de salida se establecen en 1.

Los cambios reconocidos como incompatibles de ABI son los siguientes:

  • cambio del SONAME de la biblioteca compartida
  • cambio de la arquitectura de un binario
  • eliminación de símbolos ELF de funciones exportadas o variables globales (no necesariamente descritos por información de depuración)
  • eliminación de funciones o variables globales exportadas que están descritas por información de depuración.
  • cualquier cambio incompatible en la disposición del tipo que se utiliza como tipo de una variable global o como tipo de retorno o parámetro de una función. Ese cambio de disposición de tipo incompatible puede ser:
  • una modificación del tamaño del tipo
  • o la eliminación de un miembro de datos
  • o una modificación del desplazamiento de un miembro de datos
  • o un cambio incompatible en un subtipo del tipo

Tenga en cuenta que si un tipo no se utiliza como tipo de una variable global ni como tipo de retorno o parámetro de una función, entonces abidiff (o abipkgdiff) no considerará un cambio incompatible de este tipo como un cambio incompatible de ABI. Ese cambio simplemente se considerará perjudicial. El bit ABIDIFF_ABI_CHANGE del campo de bits devuelto en el código de salida se establece en 1, lo que significa que el cambio requiere una revisión humana. Esta es una limitación actual del framework de análisis de libabigail que podría abordarse en futuras refinaciones.

Definición

NAME

abigail-suppression-file

suppression specification file format

DESCRIPTION

The libabigail library is meant to be used to compare Application Binary Interfaces (ABI). It can be used for various purposes, but one of its most common usages is to detect ABI changes between two different versions of a library.

When comparing two ABIs, libabigail generates a report of the differences it found. The problem is that sometimes, the differences found are not considered relevant by the developer, and they do not want them to appear in the report. It is especially the case when the changes are made inside of a private part of the ABI. And that is why the suppression specification file format has been introduced.

This document describes the suppression specification file format. It allows users to specify which changes they want to be suppressed and hence, not be reported about.

A suppression specification file is a text file composed of sections. Each section is delimited by a line containing the section name enclosed in square brackets. For example:

[section_name]
property1 = value1
property2 = value2

There can be empty lines and comments in the file. Lines starting with the '#' character are considered comments. Empty lines are ignored.

Properties are defined as name=value pairs. Leading and trailing white spaces are ignored around property names and values. Property names are case sensitive.

Properties are expected to be interpreted within the context of the section they are defined in. Some properties might be valid in one section but not in others.

A number of predefined section names are recognized by libabigail. Each section is meant to specify suppression rules about a particular kind of ABI artifacts. The list of all the known sections is presented below.

Regular expressions are used in various places in the suppression specification file format. Libabigail uses the extended POSIX regular expression syntax. Note that the regular expression engine used is the one from the GNU C Library.

When using a regular expression, make sure to escape any character that has a special meaning in the regular expression syntax. For example, to match a literal asterisk (*), you would need to write it as \\\*. The double backslash is required because the backslash character itself is also a special character in the INI file syntax used for suppression files.

The suppression mechanism can operate in two different modes: "late suppression" and "early suppression". In the default "late suppression" mode, suppressions are applied after the ABIs have been parsed and compared. In this mode, suppressed artifacts are still represented in memory, but they are omitted from the diff report. In the "early suppression" mode, suppressions are applied during the ABI parsing stage. This means that suppressed artifacts are never built in memory, potentially saving memory. However, this mode can lead to unintended consequences and must be explicitly enabled, for example, by using the drop property or specific command-line options.

The set of ABI artifacts to avoid emitting change reports about.

Introductory examples

Its syntax is based on a simplified and customized form of Ini File Syntax. For instance, to specify that change reports on a type named FooPrivateType should be suppressed, one could write this suppression specification:

[suppress_type]
  name = FooPrivateType

If we want to ensure that only change reports about structures named FooPrivateType should be suppressed, we could write:

[suppress_type]
  type_kind = struct
  name = FooPrivateType

But we could also want to suppress change reports avoid typedefs named FooPrivateType. In that case we would write:

[suppress_type]
  type_kind = typedef
  name = FooPrivateType

Or, we could want to suppress change reports about all struct which names end with the string "PrivateType":

[suppress_type]
  type_kind = struct
  name_regexp = ^.*PrivateType

Let's now look at the generic syntax of suppression specification files.

Syntax

Properties

More generally, the format of suppression lists is organized around the concept of property. Every property has a name and a value, delimited by the = sign. E.g:

name = value

Leading and trailing white spaces are ignored around property names and values.

Regular expressions

The value of some properties might be a regular expression. In that case, they must comply with the syntax of extended POSIX regular expressions. Note that Libabigail uses the regular expression engine of the GNU C Library.

Escaping a character in a regular expression

When trying to match a string that contains a * character, like in the pointer type int*, one must be careful to notice that the character * is a special character in the extended POSIX regular expression syntax. And that character must be escaped for the regular expression engine. Thus the regular expression that would match the string int* in a suppression file should be

So, in short, to escape a character in a regular expression, always prefix the character with the \\ sequence.

Modus operandi

Suppression specifications can be applied at two different points of the processing pipeline of libabigail.

In the default operating mode called "late suppression mode", suppression specifications are applied to the result of comparing the in-memory internal representations of two ABIs. In this mode, if an ABI artifact matches a suppression specification, its changes are not mentioned in the ABI change report. The internal representation of the "suppressed" changed ABI artifact is still present in memory; it is just not mentioned in the ABI change report. The change report can still mention statistics about the number of changed ABI artifacts that were suppressed.

This is the default mode of interpretation of suppression specifications for most tools including abidiff and abidw.

There is another operating mode called the "early suppression mode" where suppression specifications are applied during the construction of the in-memory internal representation of a given ABI. In that mode, if an ABI artifact matches a suppression specification, no in-memory internal representation is built for it. As a result, no change about the matched ABI artifact is going to be mentioned in the ABI change report and no statistic about the number of suppressed ABI changes is available. Also, please note that because suppressed ABI artifacts are removed from the in-memory internal representation in this mode, the amount of memory used by the internal representation is potentially smaller than the memory consumption in the late suppression mode.

Please note that this mode suppresses data from the internal representation constructed by libabigail and thus can lead to unintended and surprising consequences. Consequently this mode has to be set explicitly by users either by using the drop property in a suppression specification or by using a special tool command line option like abidw --force-early-suppression.

Sections

Properties are then grouped into arbitrarily named sections that shall not be nested. The name of the section is on a line by itself and is surrounded by square brackets, i.e:

[section_name]
property1_name = property1_value
property2_name = property2_value

A section might or might not have properties. Sections that expect to have properties and which are found nonetheless empty are just ignored. Properties that are not recognized by the reader are ignored as well.

Section names

Each different section can be thought of as being a directive to suppress ABI change reports for a particular kind of ABI artifact.

[suppress_file]

This directive prevents a given tool from loading a file (binary or abixml file) if its file name or other properties match certain properties. Thus, if the tool is meant to compare the ABIs of two files, and if the directive prevents it from loading either one of the files, then no comparison is performed.

Note that for the [suppress_file] directive to work, at least one of the following properties must be provided:

file_name_regexp, file_name_not_regexp, soname_regexp, soname_not_regexp.

If none of the above properties are provided, then the [suppress_file] directive is simply ignored.

The potential properties of this sections are listed below:

Prevents the system from loading the file which name does not match the regular expression specified as value of this property.

file_name_regexp

Usage:

file_name_regexp = <regular-expression>

Prevents the system from loading the file which name matches the regular expression specified as value of this property.

soname_regexp = <regular-expression>

This directive suppresses report messages about a type change.

Note that for the [suppress_type] directive to work, at least one of the following properties must be provided:

file_name_regexp, file_name_not_regexp, soname_regexp, soname_not_regexp, name, name_regexp, name_not_regexp, source_location_not_in, source_location_not_regexp, type_kind.

This can save memory, but it might also lead to unintended consequences. This is why this property must be set explicitly.

label

enumeradores_cambiados

Uso:

enumeradores_cambiados = <lista-de-enumeradores>

enumeradores_cambiados_regexp

Uso:

enumeradores_cambiados_regexp = <lista-de-expresiones-regulares-de-enumeradores>

Suprime informes de cambios que involucran cambios en el valor de los enumeradores de un tipo enum dado. Esta propiedad se aplica si la propiedad tipo_clase se establece en el valor enum, al menos. El valor de la propiedad enumeradores_cambiados_regexp es una lista separada por comas de expresiones regulares que deben coincidir con los nombres de los enumeradores que el usuario espera que cambien. descartar
Uso:
descartar = sí | no

Si un tipo coincide con una especificación de supresión que contiene la propiedad "descartar" establecida en "sí" (o en "verdadero"), entonces el tipo ni siquiera se representará en la representación interna del ABI que se está analizando. Esta propiedad hace que su especificación de supresión contenedora se aplique en el modo de especificación de supresión temprana. El efecto neto es que potencialmente reduce la cantidad de memoria utilizada para representar el ABI que se está analizando.

Tenga en cuenta que para los tipos struct, class o enum que coinciden con una especificación de supresión con esta propiedad establecida en "sí" (o en "verdadero"), si la especificación también tiene una propiedad etiqueta con un valor establecido en libabigail::OPAQUE_TYPE_LABEL, entonces el tipo se transforma en un tipo opaco, en lugar de simplemente descartarse. Eso también reduce la cantidad de memoria utilizada para representar el ABI que se está analizando, pero con potencialmente menos interrupción en la representación resultante del ABI.

Tenga en cuenta que para que esta propiedad sea efectiva, la especificación de supresión contenedora debe tener al menos una de las siguientes propiedades especificadas: nombre_regexp, nombre, nombre_regexp, ubicacion_fuente_no_en o ubicacion_fuente_no_regexp.

tiene_miembro_dato

tiene_miembro_dato = <lista-de-nombres-de-miembros-dato>

Suprime informes de cambios que involucran un tipo que contiene miembros dato cuyos nombres se proporcionan en la lista de valores de esta propiedad.

Un ejemplo de uso de esta propiedad sería:

tiene_miembro_dato = {miembro_dato_privado0, miembro_dato_privado1}

La propiedad anterior coincidiría con cualquier tipo que contenga al menos dos miembros dato cuyos nombres son miembro_dato_privado0 y miembro_dato_privado1.

Otro ejemplo de uso de esta propiedad sería:

tiene_miembro_dato = otro_miembro_dato_privado

La propiedad anterior coincidiría con cualquier tipo que contenga un miembro dato cuyo nombre sea otro_miembro_dato_privado0.

tiene_miembro_dato_regexp

Uso:

tiene_miembro_dato_regexp = <una-expresion-regular>

Suprime informes de cambios que involucran un tipo que contiene miembros dato cuyos nombres coinciden con la expresión regular proporcionada como valor de esta propiedad.

Un ejemplo de uso de esta propiedad sería:

tiene_miembro_dato_regexp = ^miembro_dato_privado

La propiedad anterior coincidiría con cualquier tipo que contenga miembros dato cuyos nombres coinciden con la expresión regular ^miembro_dato_privado. En otras palabras, coincidiría con cualquier tipo que contenga miembros dato cuyos nombres comienzan con la cadena "miembro_dato_privado".


•
tiene_miembro_dato_insertado_en
Uso:
tiene_miembro_dato_insertado_en = <offset-en-bits>

Suprime informes de cambios que involucran un tipo que tiene al menos un miembro dato insertado en un desplazamiento especificado por el valor de la propiedad offset-en-bits. Tenga en cuenta que si el tamaño del tipo cambió, el cambio de tipo NO será suprimido por la evaluación de esta propiedad, a menos que la propiedad tiene_cambio_tamaño esté presente y establecida en sí.

El valor offset-en-bits es:

•
un valor entero, expresado en bits, que denota el desplazamiento del punto de inserción del miembro dato, comenzando desde el principio de la estructura o clase relevante.
•
expresiones de selector de desplazamiento de miembro dato, tales como:
  • la palabra clave fin que es una constante con nombre cuyo valor es igual al desplazamiento del final de la estructura o clase.
  • la palabra clave offset_of_flexible_array_data_member que es una constante con nombre que se evalúa al desplazamiento del miembro dato de matriz flexible contenido en la estructura relevante.
  • la expresión de llamada a función offset_of(nombre-miembro-dato) donde nombre-miembro-dato es el nombre de un miembro dato dado de la estructura o clase relevante. El valor de esta expresión de llamada a función es un entero que representa el desplazamiento del miembro dato denotado por nombre-miembro-dato.
  • la expresión de llamada a función offset_after(nombre-miembro-dato) donde nombre-miembro-dato es el nombre de un miembro dato dado de la estructura o clase relevante. El valor de esta expresión de llamada a función es un entero que representa el desplazamiento del punto que viene justo después de la región ocupada por el miembro dato denotado por nombre-miembro-dato.
  • la expresión de llamada a función offset_of_first_data_member_regexp(nombre-miembro-dato-regexp) donde nombre-miembro-dato-regexp es una expresión regular que coincide con un miembro dato. El valor de esta expresión de llamada a función es un entero que representa el desplazamiento del primer miembro dato cuyo nombre coincide con el argumento de expresión regular. Si ningún miembro dato de un tipo de clase dado coincide con la expresión regular, entonces el tipo de clase no coincidirá con la directiva actual.
  • la expresión de llamada a función offset_of_last_data_member_regexp(nombre-miembro-dato-regexp) donde nombre-miembro-dato-regexp es una expresión regular que coincide con un miembro dato. El valor de esta expresión de llamada a función es un entero que representa el desplazamiento del último miembro dato cuyo nombre coincide con el argumento de expresión regular.   type_kind = struct
  has_data_member_inserted_at = end

  # al final, y si el cambio afecta los usos del tipo a través de una
  # referencia o un puntero.

Básicamente, durante la canonización de tipos, cada comparación de tipos se realiza dos veces: una vez en modo estructural (comparando cada subtipo miembro a miembro) y una vez utilizando comparación canónica. Las dos comparaciones deberían arrojar el mismo resultado. De lo contrario, se emite una señal de aborto y el proceso puede ser depurado para comprender por qué los dos tipos de comparación arrojan resultados diferentes.

Esta es una opción de depuración y verificación de integridad opcional. Para habilitarla, el paquete libabigail debe estar configurado con la opción de configuración --enable-debug-type-canonicalization.

    Valores de retorno

    El código de salida del comando abidiff es 0 si la ABI de los binarios que se comparan son iguales, o distinto de cero si difieren o si la herramienta encontró un error.

    En este último caso, el código de salida es un campo de bits de 8 bits en el que cada bit tiene un significado específico.

    El primer bit, de valor 1, llamado ABIDIFF_ERROR, significa que hubo un error.

    El segundo bit, de valor 2, llamado ABIDIFF_USAGE_ERROR, significa que hubo un error en la forma en que el usuario invocó la herramienta. Podría establecerse, por ejemplo, si el usuario invocó la herramienta con un interruptor de línea de comandos desconocido, con un número incorrecto de argumentos, etc. Si este bit está establecido, entonces el bit ABIDIFF_ERROR también debe estar establecido.

    El tercer bit, de valor 4, llamado ABIDIFF_ABI_CHANGE, significa que la ABI de los binarios que se comparan son diferentes.

    El cuarto bit, de valor 8, llamado ABIDIFF_ABI_INCOMPATIBLE_CHANGE, significa que la ABI de los binarios comparados difieren de manera incompatible. Si este bit está establecido, entonces el bit ABIDIFF_ABI_CHANGE también debe estar establecido. Si ABIDIFF_ABI_CHANGE está establecido y ABIDIFF_INCOMPATIBLE_CHANGE *NO* está establecido, entonces significa que las ABI que se comparan pueden ser compatibles o no. En ese caso, un ser humano necesita revisar los cambios de ABI para decidir si son compatibles o no.

    Tenga en cuenta que, por el momento, solo hay unos pocos tipos de cambios de ABI que resultarían en el establecimiento del indicador ABIDIFF_ABI_INCOMPATIBLE_CHANGE. Esos cambios de ABI son:

    • la eliminación del símbolo de una función o variable que ha sido definida y exportada.
    • la modificación del índice de un miembro de una tabla de funciones virtuales (para programas y bibliotecas C++).

    Con el tiempo, cuando se encuentren más patrones de cambio de ABI que siempre constituyan cambios de ABI incompatibles, adaptaremos el código para reconocer esos casos y estableceremos ABIDIFF_ABI_INCOMPATIBLE_CHANGE en consecuencia. Por lo tanto, si encuentra tales patrones, háganoslo saber.

    Los bits restantes no se utilizan por el momento.

    abipkgdiff

    La ABI de los binarios contenidos en el segundo conjunto de paquetes se compara contra la ABI de los binarios contenidos en el primer conjunto de paquetes.

    Esta herramienta utiliza la biblioteca libabigail para analizar el binario así como su información de depuración asociada. Este es su modo de operación general.

    Libabigail tiene entonces capacidades para generar representaciones textuales de Corpos de ABI, compararlos, analizar sus cambios e informar sobre ellos.

    Invocación

    abipkgdiff [opciones] <paquete1> <paquete2>

    paquete1 y paquete2 son los paquetes que contienen los binarios a comparar.

    Un estilo de invocación alternativo sería:

    abipkgdiff [opciones] --set1 <pkg1-v1> <pkg2-v1> <pkg3-v1> \
                     --set2 <pkg1-v2> <pkg2-v2> <pkg3-v2>

    donde la ABI de los binarios contenidos en el segundo conjunto de paquetes se compara contra los binarios contenidos en el primer conjunto de paquetes.

    Entorno

    abipkgdiff carga dos archivos de especificación de supresión por defecto, fusiona su contenido y lo usa para filtrar informes de cambios de ABI que puedan considerarse falsos positivos para los usuarios.

    • Archivo de especificación de supresión del sistema por defecto

      Se localiza mediante la variable de entorno opcional LIBABIGAIL_DEFAULT_SYSTEM_SUPPRESSION_FILE. Si esa variable de entorno no está establecida, entonces abipkgdiff intenta cargar el archivo de supresión $libdir/libabigail/libabigail-default.abignore. Si ese archivo no está presente, entonces no se carga ningún archivo de especificación de supresión del sistema por defecto.

    • Archivo de especificación de supresión del usuario por defecto.

      Se localiza mediante la variable de entorno opcional LIBABIGAIL_DEFAULT_USER_SUPPRESSION_FILE. Si esa variable de entorno no está establecida, entonces abipkgdiff intenta cargar el archivo de supresión $HOME/.abignore. Si ese archivo no está presente, entonces no se carga ninguna especificación de supresión de usuario por defecto.

    Además de estos archivos de especificación de supresión por defecto, abipkgdiff buscará dentro de los paquetes que se están comparando y si encuentra un archivo que termina con la extensión .abignore, entonces lo considerará como una especificación de supresión y lo combinará con la especificación de supresión por defecto que pueda estar ya cargada.

    El usuario también puede usar la opción --suppressions (que se documenta más adelante) para proporcionar una especificación de supresión.

    kmidiff

    kmidiff compara las Interfaces de Módulos del Kernel (KMI) binarias de dos árboles del Kernel de Linux. La KMI binaria es la interfaz que el Kernel de Linux expone a sus módulos. Los árboles que nos interesan aquí son el resultado de la compilación del árbol fuente del Kernel de Linux.

    Enfoque general

    Un ejemplo de cómo compilar tu kernel si quieres compararlo con otro usando kmidiff es:

    git clone -b v4.5 git://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git linux/v4.5
cd linux/v4.5
make allyesconfig all

    Luego instala los módulos en un directorio, por ejemplo, el subdirectorio build/modules de tu árbol fuente del kernel:

    mkdir build/modules
make modules_install INSTALL_MOD_DIR=build/modules

    Luego construye una lista de interfaces exportadas por el kernel, que quieras comparar:

    cat > kmi-whitelist << EOF
[kernel_4.5_kmi_whitelist]
 init_task
 schedule
 dev_queue_xmit
 __kmalloc
 printk
EOF

    Supón que has hecho algo similar para la rama v4.6 del kernel de Linux, ahora tienes estos dos directorios: linux/v4.5 y linux/v4.6. Sus módulos están presentes en los directorios linux/v4.5/build/modules y linux/v4.6/build/modules.

    Para comparar sus KMI, kmidiff necesita saber dónde encontrar los binarios vmlinux y sus módulos asociados. Así se vería la línea de comandos:

    kmidiff                                     \
  --kmi-whitelist  linux/v4.6/kmi-whitelist \
  --vmlinux1       linux/v4.5/vmlinux       \
  --vmlinux2       linux/v4.6/vmlinux       \
                   linux/v4.5/build/modules \
                   linux/v4.6/build/modules

    Esta herramienta utiliza la biblioteca libabigail para analizar el binario, así como su información de depuración asociada. Este es su modo de operación general.

    Libabigail tiene entonces capacidades para generar representaciones textuales de Corpora de ABI, compararlas, analizar sus cambios e informar sobre ellos.

    De forma más general, kmidiff se invoca de la siguiente forma:

    kmidiff [opciones] <directorio-primeros-módulos> <directorio-segundos-módulos>

    Entorno

    Por defecto, kmidiff compara todas las interfaces (funciones y variables exportadas) entre el Kernel y sus módulos. En la práctica, sin embargo, algunos usuarios podrían querer comparar un subconjunto de esas interfaces.

    Los usuarios pueden entonces definir una "lista blanca" de las interfaces a comparar. Dicha lista blanca es solo un archivo en formato "INI" que se ve así:

    [kernel_version_x86_64_whitelist]
  function1_name
  function2_name
  global_variable1_name
  ....

    Tenga en cuenta que el nombre de la sección (el nombre que está entre los dos corchetes) de ese archivo INI solo tiene que terminar con la cadena "whitelist". Por lo tanto, puede definir el nombre que desee, por ejemplo [kernel_46_x86_64_whitelist].

    Luego, cada línea de ese archivo de lista blanca es el nombre de una función o variable exportada. Solo esas interfaces, junto con los tipos accesibles desde sus firmas, serán comparadas por kmidiff recursivamente.

    NAME

    abidw

    SYNOPSIS

    abidw [OPTIONS] PATH ...

    DESCRIPTION

    The abidw program is an ABI auditor that produces an XML representation of the ABI.

    Given a list of paths to binaries, abidw will produce an XML document that describes the Application Binary Interface (ABI) of each of them. The ABI description is intended to be used by other libraries and tools that need to query and/or consume ABI information.

    The tool needs DWARF debug information to be available for the binaries it is asked to audit. This debug information can be found in the same binary files or in separate files (typically ending with .debug).

    abidw can be instructed to analyze only the listed binaries, or it can be asked to analyze them along with their dynamic dependencies.

    The output of the tool is an XML document that describes the ABI. The format of this document is called ABIXML. ABIXML is a format that is supposed to be stable across the different releases of libabigail.

    The list of paths provided on the command line can contain paths to regular binary files, archives (like tarballs, zip files, etc.) or directories. If a directory is provided, abidw will traverse it recursively and will look for binary files inside it.

    OPTIONS

    • --added-binaries <path-list>

      A comma separated list of paths to binary files that are to be added to the set of binaries that abidw is supposed to analyze. The list can also be specified multiple times.

    • --added-binaries-dir <path-list>

      A comma separated list of directory paths that abidw should search for additional binary files to analyze. These additional binaries will be added to the set of binaries described in the ABIXML output.

      This option can be provided multiple times to specify multiple directories.

      Note that this option can be used in conjunction with --follow-dependencies to specify the directories where the dependencies of the binaries listed on the command line are to be found.

    • --build-id-filter <build-id-list>

      A comma separated list of ELF build IDs. When specified, abidw will only report on binaries that have one of the build IDs in the list.

    • --compiler-info

      Include compiler information in the generated ABIXML.

    • --debug-abigail

      Enable debug logging for libabigail itself.

    • --drop-relocatable

      Do not include information about relocatable symbol definitions in the generated ABIXML.

    • --early-suppression

      Perform suppression processing as early as possible.

    • --exclude-path-filter <path-regex>

      A regular expression that specifies paths to exclude from analysis. If a path matches this regex, it will be skipped.

    • --executable-filter <executable-regex>

      A regular expression that specifies executable names to include. Only executables matching this regex will be analyzed.

    • --force-early-suppression

      Force the application of suppression rules even if they are not marked with the 'drop' property.

    • --follow-dependencies

      Analyze the dynamic dependencies of the binaries provided on the command line, in addition to the binaries themselves.

    • --help | -h

      Display a help message and exit.

    • --includedir <path-list>

      A comma-separated list of directories to search for include files. This is useful when analyzing C++ templates or other language constructs that rely on header files.

    • --input-path-filter <path-regex>

      A regular expression that specifies paths to include in the analysis. Only paths matching this regex will be considered.

    • --no-default-arctan

      Do not include default arctan information.

    • --no-emit-abiegn

      Do not emit ABIEGN information.

    • --no-emit-dictionary

      Do not emit dictionary information.

    • --no-emit-names

      Do not emit names information.

    • --no-emit-source-dir

      Do not emit source directory information.

    • --no-emit-symbol-visibility

      Do not emit symbol visibility information.

    • --no-emit-types

      Do not emit type information.

    • --no-source-date-epoch

      Do not include the SOURCE_DATE_EPOCH information.

    • --no-write-default-sizes

      In the XML ABI representation, do not write the size-in-bits for pointer type definitions, reference type definitions, function declarations and function types when they are equal to the default address size of the translation unit. Note that libabigail before 1.8 will not set the default size and will interpret types without a size-in-bits attribute as zero sized.

    • --out-file | -o <file-path>

      This option instructs abidw to emit the XML representation of path-to-elf-file into the file file-path, rather than emitting it to its standard output.

    • --stats

      Emit statistics about various internal things.

    • --suppressions | suppr <path-to-suppression-specifications-file>

      Use a suppression specification file located at path-to-suppression-specifications-file. Note that this option can appear multiple times on the command line. In that case, all of the provided suppression specification files are taken into account. ABI artifacts matched by the suppression specifications are suppressed from the output of this tool.

      Only suppression specifications that have the drop property set to 'yes' are going to be effective. All other suppression specification directives will appear as being ignored, unless the command line option --force-early-suppression is provided.

    • --type-id-style <sequence``|``hash>

      This option controls how types are idenfied in the generated XML files. The default sequence style just numbers (with type-id- as prefix) the types in the order they are encountered. The hash style uses a (stable, portable) hash of libabigail's internal type names and is intended to make the XML files easier to diff.

    • --verbose

      Emit verbose logs about the progress of miscellaneous internal things.

    • --version | -v

      Display the version of the program and exit.

    USAGE EXAMPLES

    1.
    Emitting an ABIXML representation of a binary:
    $ abidw binary > binary.abi
    2.
    Emitting an ABIXML representation of a set of binaries specified on the command line:
    $ abidw --added-binaries=bin1,bin2,bin3  \
        --added-binaries-dir /some/where \
        binary > binaries.abi

    Note that the binaries bin1, bin2 and bin3 are to be found in the directory /some/where. A representation of the ABI of the set of binaries binary, bin1, bin2 and bin3 called an ABI corpus group is serialized in the file binaries.abi.

    3.
    Emitting an ABIXML representation of a binary and its dependencies:
    $ abidw --follow-dependencies              \
        --added-binaries-dir /some/where   \
        binary > binary.abi

    Note that only the dependencies that are found in the directory /some/where are analysed. Their ABIs, along with the ABI the binary named binary are represented as an ABI corpus group and serialized in the file binary.abi, in the ABIXML format.

      Specify the preexisting git working tree for abidb to submit to or check against. The default is the current working directory. It may be used concurrently by multiple "check" operations, but only one "submit" operation.

    • --help | -h

      Display a short help about the command and exit.

    • --loglevel LOGLEVEL

      Specify the diagnostic level for messages to stderr. One of debug, info, warning, error, or critical; case-insensitive. The default is info.

    • --timeout SECONDS

      Specify a maximum limit to the execution time (in seconds) allowed for the abidw and abicompat programs that are executed. By default, no limit is set for the execution time of these programs.

    Submit Options

    • --archive | -Z .EXT[=CMD]

      Designate PATH names with a .EXT suffix to be treated as archives. If CMD is present, pipe the PATH through the given shell command, otherwise pass as if through cat. The resulting stream is then opened by libarchive, to enumerate the contents of a wide variety of possible archive file format. Process each file in the archive individually into abixml.

      For example, -Z .zip will process each file in a zip file, and -Z .deb='dpkg-deb --fsys-tarfile' will process each payload file in a Debian archive.

    • --filter REGEX

      Limit files selected for abixml extraction to those that match the given regular expression. The default is /lib.*\.so, as a heuristic to identify shared libraries.

    • --submit PATH1 PATH2 ...

      Using abidw, extract abixml for each of the listed files, generally shared libraries, subject to the filename filter and the archive decoding options. Save the output of each abidw run into the selected distrobranch of the selected git repo. If --submit and --check are both given, do submit operations first.

    • --sysroot PREFIX Specify the a prefix path that is to be removed from submitted file names.

    Check Options

    • --check PATH1 PATH2 ...

      Using abidiff, compare each of the listed file, generally executables, against abixml documents for selected versions for all shared libraries needed by the executable. These are listed by enumerating the dynamic segment tags DT_NEEDED of the executable.

    • --ld-library-path DIR1:DIR2:DIR3...

      Select the search paths for abixml documents used to locate any particular SONAME . The first given directory wins. However, all versions of the same SONAME in that directory are selected for comparison. The default is unspecified, which means to search for all matching SONAME entries in the distrobranch, regardless of specific directory.

    Exit Code

    In case of successful submission and/or checking of all paths, the exit code is 0.

    In case of error, the exit code of abidb is nonzero, and a brief listing of the binaries unable to be submitted and/or checked is printed.

    Git Repository Schema

    abidb stores abixml documents in a git repo with the following naming schema within the distrobranch:

    1.
    The directory path leading to the shared library file
    2.
    The SONAME of the shared library file, as a subdirectory name
    3.
    A file named BUILDID.xml, where BUILDID is the hexadecimal ELF build-id note of the shared library.

    elfutils

    Elfutils is a set of libraries and tools to work with ELF files. It is a new implementation of the libraries that used to be part of the GNU binutils package, but with a better API and without the restrictions imposed by the GNU license.

    Introduction

    This document describes the utilities provided by the elfutils package.

    Build IDs

    Build IDs are unique identifiers for compiled objects like shared libraries and executables. They are embedded into the ELF file by the linker. Elfutils uses Build IDs to track and manage different versions of objects.

    The filename format used by elfutils for storing objects based on their Build IDs is:

          <build-id>-<soname>.so

    For example:

          788cdd41a15985bf8e0a48d213a46e07d58822df-libc.so.6.xml
      e2ca832f1c2112aea9d7b9bc639e97e873a6b516-ld-linux.so.2.xml
      b65f3c15b129f33f44f504da1719926aec03c07d-libc.so.6.xml

    The purpose of including the Build ID in the name is to allow different versions of a shared library in a distribution to be stored nearby without conflicts. The SONAME is used in the second-to-last component of the name, following the behavior of ld.so and ldconfig, which rely on symbolic links to map references from the SONAME to an actual file.

    abicompat

    abicompat checks that an application which links against a given shared library is still ABI compatible with a subsequent version of that library. If the new version of the library introduces an ABI incompatibility, then abicompat will indicate to the user what exactly that incompatibility is.

    Invocation

    abicompat [options] [<application> <shared-library-first-version> <shared-library-second-version>]

    Options

    • --help

      Display a short help message about the command and exit.

    • --version | -v

      Display the version of the program and exit.

    • --list-undefined-symbols | -u

      Display the list of undefined symbols of the application and exit.

    • --show-base-names | -b

      In the resulting report emitted by the tool, this option makes the application and libraries be referred to by their base names only; not by a full absolute name. This can be useful for scripts that want to compare names of the application and libraries independently of their directory names.

    • --app-debug-info-dir | --appd <path-to-app-debug-info-directory>

      Set the path to the directory where the debug information of the application is expected to be laid out. This is useful for application binaries for which the debug info is in a separate set of files.

    • --lib-debug-info-dir1 | --libd1 <path-to-lib1-debug-info>

      Set the path to the directory where the debug information of the first version of the shared library is expected to be laid out. This is useful for shared library binaries for which the debug info is in a separate set of files.

    • --lib-debug-info-dir2 | --libd2 <path-to-lib1-debug-info>

      Set the path to the directory where the debug information of the second version of the shared library is expected to be laid out. This is useful for shared library binaries for which the debug info is in a separate set of files.

    • --suppressions | --suppr <path-to-suppressions>

      Use a suppression specification file located at path-to-suppressions. Note that this option can appear multiple times on the command line; all the suppression specification files are then taken into account.

    • --no-show-locs

      Do not show information about where in the second shared library the respective type was changed.

    • --btf

      When comparing binaries, extract ABI information from BTF debug information, if present.

    • --ctf

      When comparing binaries, extract ABI information from CTF debug information, if present.

    • --fail-no-debug-info

      If no debug info was found, this option causes the program to fail. Otherwise, without this option, the program will attempt to compare properties of the binaries that are not related to debug info, like pure ELF properties.

    • --ignore-soname

      Ignore differences in the SONAME when doing a comparison.

    • --weak-mode

      This triggers the weak mode of abicompat. In this mode, only one version of the library is required. That is, abicompat is invoked like this:

      abicompat --weak-mode <the-application> <the-library>

      Note that the --weak-mode option can even be omitted if only one version of the library is given, along with the application; in that case, abicompat automatically switches to operate in weak mode:

      abicompat <the-application> <the-library>

      In this weak mode, the types of functions and variables exported by the library and consumed by the application (i.e., the symbols of these functions and variables are undefined in the application and are defined and exported by the library) are compared to the version of these types as expected by the application. If these two versions of types differ, abicompat informs the user about the differences.

      In other words, in this mode, abicompat checks that the types of the functions and variables exported by the library have the same meaning as what the application expects, as far as the ABI is concerned.

      Note that in this mode, abicompat does not detect exported functions or variables (symbols) that are expected by the application but have been removed from the library. This is why it is called weak mode.

    Return values

    The exit code of the abicompat command is either 0 if the ABI of the binaries being compared are equal, or non-zero if they differ or if the tool encountered an error.

    In the latter case, the exit code is an 8-bit bit field in which each bit has a specific meaning.

    The first bit, of value 1, named ABIDIFF_ERROR, indicates that there was an error.

    The second bit, of value 2, named ABIDIFF_USAGE_ERROR, indicates that there was an error in the way the user invoked the tool. It might be set, for instance, if the user invoked the tool with an unknown command line switch, with the wrong number or type of arguments, etc. If this bit is set, then the ABIDIFF_ERROR bit must also be set.

    The third bit, of value 4, named ABIDIFF_ABI_CHANGE, indicates that the ABI of the binaries being compared are different.

    The fourth bit, of value 8, named ABIDIFF_ABI_INCOMPATIBLE_CHANGE, indicates that the ABI of the binaries compared are different in an incompatible way. If this bit is set, then the ABIDIFF_ABI_CHANGE bit must also be set. If the ABIDIFF_ABI_CHANGE is set and the ABIDIFF_INCOMPATIBLE_CHANGE is *not* set, then it means that the ABIs being compared might or might not be compatible. In that case, a human being needs to review the ABI changes to decide if they are compatible or not.

    The remaining bits are not currently used.

    abilint

    abilint analiza la representación XML nativa de una ABI tal como la emite abidw. Una vez que ha analizado la representación XML de la ABI, abilint construye un modelo en memoria a partir de ella. Luego, intenta guardarlo de nuevo en formato XML, en la salida estándar. Si esa operación de lectura-escritura tiene éxito, es probable que la representación XML de entrada de la ABI sea significativa.

    Tenga en cuenta que la intención principal de esta herramienta es ayudar a depurar problemas en la biblioteca subyacente Libabigail.

    Invocación

    abilint [options] [<abi-file1>]

    Opciones

    • --annotate

      Anota la salida ABIXML con comentarios encima de la mayoría de los elementos. Los comentarios consisten en la forma impresa de tipos, declaraciones o incluso símbolos ELF. El propósito es hacer que la salida ABIXML sea más legible para humanos con fines de depuración o documentación.

    • --ctf

      Extrae información de ABI de la información de depuración CTF, si está presente en el objeto dado.

    • --debug-info-dir <ruta>

      Tenga en cuenta que ruta debe apuntar al directorio raíz bajo el cual la información de depuración está organizada de manera arbórea. En sistemas basados en Red Hat, ese directorio suele ser <root>/usr/lib/debug.

      Tenga en cuenta también que esta opción no es obligatoria para la información de depuración dividida instalada por el gestor de paquetes de su sistema, ya que entonces abidiff sabe dónde encontrarla.

    • --diff

      Para entradas XML, realiza una comparación de texto entre la entrada y el modelo de memoria guardado de nuevo en el disco. Esto puede ayudar a detectar problemas en el manejo del formato XML por parte de la biblioteca subyacente Libabigail.

    • --header-file | --hf <ruta-del-archivo-de-cabecera>

    • --help

      Muestra un breve mensaje de ayuda y sale.

    • --noout

      No muestres nada en la salida estándar. El código de retorno del comando es la única forma de saber si el comando tuvo éxito.

    • --suppressions | suppr <ruta-al-archivo-de-especificaciones-de-supresión>

    • --version | -v

      Muestra la versión del programa y sale.

    NAME

    fedabipkgdiff - Compare ABI of two builds of an RPM package

    SYNOPSIS

    fedabipkgdiff [options] [<rpmfile1> <rpmfile2>]

    fedabipkgdiff [options] <packagename1> <packagename2>

    DESCRIPTION

    The fedabipkgdiff tool is a frontend to the abidiff tool. It allows you to compare the Application Binary Interface (ABI) of two builds of an RPM package. The two builds can be specified either as two RPM files, or as two package names. In the latter case, the tool queries the Koji build system (of Fedora) to find the latest builds of the specified packages and downloads them for the comparison.

    The following options are supported:

    • --all-subpackages

      When comparing two packages, compare also the ABI of their sub-packages.

    • --arch <arch>

      Compare the ABI of the binaries for the specified architecture only. If this option is not provided, the comparison is performed for all architectures specified by the --from and --to options.

    • --builddiff <path-to-builddiff>

      Use the specified builddiff tool instead of the one found in the system.

    • --cache <path-to-cache>

      Use the specified directory to cache downloaded RPMs.

    • --build <build_id>

      Specifies the Koji build ID to use as the baseline. This is useful when the package name is ambiguous (e.g. when there are multiple packages with the same name). This option can be used multiple times.

    • --from <distro>
    • --help

      Print a help message and exit.

    • --klimit <limit>

      Specifies the maximum number of Koji builds to consider for each package. The default value is 1.

    • --abi-group <group>

      Comparison can be performed on different ABI groups. By default, the tool compares the ABI of all symbols that are exported by the binaries. This option allows to limit the comparison to a specific ABI group. Currently supported ABI groups are:

      o all : Compare all symbols.

      o exported : Compare only exported symbols.

      o private : Compare only private symbols.

      o public : Compare only public symbols.

      This option is useful to filter symbols based on their visibility.

    • --no-cache

      Do not use cache directory for downloaded RPMs.

    • --no-klimit

      Do not limit the number of Koji builds to consider for each package.

    • --no-private-dso

      Do not compare the ABI of shared libraries that are private to the packages. If this option is not provided, shared libraries that are private to the packages being considered are compared.

    • --no-symbols

      Do not compare the ABI of functions and global variables. By default, the comparison includes functions and global variables.

    • --public-symbols

      Compare the ABI of functions and global variables that are publicly exported in the binaries being compared, even if those types are not defined in public header files available from the packages being compared.

    • --private-dso

      Compare the ABI of shared libraries that are private to the packages. If this option is not provided, shared libraries that are private to the packages being considered are not compared.

    • --server <URL>
    • --show-identical-binaries
    Show the names of the all binaries compared, including the binaries whose ABI compare equal. By default, when this option is not provided, only binaries with ABI changes are mentionned in the output.
    • --suppressions <path-to-suppresions>

      Use a suppression specification file located at path-to-suppressions.

    • --to <distro>
    • --topurl <URL>
    • --traceback

      Show traceback when an exception raised. This is useful for developers of the tool itself to know more exceptional errors.

    Return value

    The exit code of the abipkgdiff command is either 0 if the ABI of the binaries compared are equivalent, or non-zero if they differ or if the tool encountered an error.

    In the later case, the value of the exit code is the same as for the abidiff tool.

    Use cases

    Below are some usage examples currently supported by fedabipkgdiff.

    1.
    Compare the ABI of binaries in a local package against the ABI of the latest stable package in Fedora 23. 
    $ fedabipkgdiff --from fc23 ./httpd-2.4.18-2.fc24.x86_64.rpm
    2.
    Compare the ABI of binaries in two local packages.

    Suppose you have built two versions of package httpd, and you want to see what ABI differences between these two versions of RPM files. The command line invocation would be:

    $ fedabipkgdiff path/to/httpd-2.4.23-3.fc23.x86_64.rpm another/path/to/httpd-2.4.23-4.fc24.x86_64.rpm

    All what fedabipkgdiff does happens on local machine without the need of querying or downloading RPMs from Koji.

    3.
    Compare the ABI of binaries in the latest build of the httpd package in Fedora 23 against the ABI of the binaries in the latest build of the same package in 24.

    In this case, note that neither of the two packages are available locally. The tool is going to talk with the Fedora Build System, determine what the versions and releases of the latest packages are, download them and perform the comparison locally. The command line invocation would be:

    $ fedabipkgdiff httpd-2.8.14.fc23 httpd-2.8.14.fc24

    But if we want to perform the ABI comparison for a specific architecture, say, x86_64, then the command line invocation would be:

    $ fedabipkgdiff httpd-2.8.14.fc23.x86_64 httpd-2.8.14.fc24.x86_64
    5.
    If the use wants to also compare the sub-packages of a given package, she can use the --all-subpackages option. The first command of the previous example would thus look like:
    $ fedabipkgdiff --all-subpackages httpd-2.8.14.fc23 httpd-2.8.14.fc24
