NOMBRE

libcurl-tutorial - tutorial de programación de libcurl

Objetivo

Este documento intenta describir los principios generales y algunos enfoques básicos a considerar al programar con libcurl. El texto se enfoca en la interfaz C, pero debería aplicarse bastante bien a las interfaces de otros lenguajes, ya que generalmente siguen la API C con bastante cercanía.

Este documento se refiere a 'el usuario' como la persona que escribe el código fuente que utiliza libcurl. Ese serías probablemente tú o alguien en tu posición. Lo que generalmente se denomina 'el programa' es el código fuente recopilado que tú escribes y que utiliza libcurl para las transferencias. El programa está fuera de libcurl y libcurl está fuera del programa.

Para obtener más detalles sobre todas las opciones y funciones descritas aquí, consulta sus respectivas páginas man.

Compilación

Hay muchas formas diferentes de compilar programas C. Este capítulo asume un proceso de compilación estilo Unix. Si utilizas un sistema de compilación diferente, aún puedes leer esto para obtener información general que puede aplicarse también a tu entorno.

Compilar el Programa
Tu compilador necesita saber dónde se encuentran las cabeceras de libcurl. Por lo tanto, debes establecer la ruta de inclusión de tu compilador para que apunte al directorio donde las instalaste. La herramienta 'curl-config'[3] puede usarse para obtener esta información: 
  $ curl-config --cflags
Enlazar el Programa con libcurl
Una vez compilado el programa, necesitas enlazar tus archivos objeto para crear un único ejecutable. Para que esto tenga éxito, necesitas enlazar con libcurl y posiblemente también con otras bibliotecas de las que libcurl mismo depende. Como las bibliotecas de OpenSSL, pero incluso algunas bibliotecas estándar del sistema operativo pueden ser necesarias en la línea de comandos. Para averiguar qué indicadores usar, una vez más la herramienta 'curl-config' acude al rescate: 
  $ curl-config --libs
SSL o No
libcurl se puede compilar y personalizar de muchas maneras. Una de las cosas que varían entre diferentes bibliotecas y compilaciones es el soporte para transferencias basadas en SSL, como HTTPS y FTPS. Si se detectó correctamente una biblioteca SSL compatible en el momento de la compilación, libcurl se compila con soporte SSL. Para averiguar si una libcurl instalada se compiló con soporte SSL habilitado, usa curl-config de esta manera: 
  $ curl-config --feature

Si SSL es compatible, la palabra clave SSL se escribirá en la salida estándar, posiblemente junto con otras características que podrían estar activas o desactivadas para diferentes libcurls.

Consulta también la sección "Características que Proporciona libcurl" más abajo.

Macro autoconf
Cuando escribas tu script de configuración para detectar libcurl y configurar las variables correspondientemente, ofrecemos una macro que probablemente hace todo lo que necesitas en esta área. Consulta el archivo docs/libcurl/libcurl.m4, incluye documentación sobre cómo usarla.

Código Portable en un Mundo Portable

Las personas detrás de libcurl han realizado un esfuerzo considerable para hacer que libcurl funcione en una gran cantidad de sistemas operativos y entornos diferentes.

Tú programas libcurl de la misma manera en todas las plataformas en las que se ejecuta libcurl. Solo hay unos pocos detalles menores que difieren. Si simplemente te aseguras de escribir tu código lo suficientemente portable, puedes crear un programa portable. libcurl no debería impedirte eso.

Preparación Global

El programa debe inicializar parte de la funcionalidad de libcurl globalmente. Eso significa que debe hacerse exactamente una vez, sin importar cuántas veces intentes usar la biblioteca. Una vez durante toda la vida de tu programa. Esto se hace usando

 curl_global_init()

y toma un parámetro que es un patrón de bits que le dice a libcurl qué inicializar. Usar CURL_GLOBAL_ALL hace que inicialice todos los módulos internos conocidos, y puede ser una buena opción predeterminada. Los dos bits actuales que se especifican son:

CURL_GLOBAL_WIN32
que solo hace algo en máquinas Windows. Cuando se usa en una máquina Windows, hace que libcurl inicialice las utilidades de sockets Win32. Sin tener eso inicializado correctamente, tu programa no puede usar sockets correctamente. Solo debes hacer esto una vez por aplicación, así que si tu programa ya hace esto o si otra biblioteca en uso lo hace, no deberías indicarle a libcurl que haga esto también.
CURL_GLOBAL_SSL
que solo hace algo en las libcurls compiladas y habilitadas para SSL. En estos sistemas, esto hace que libcurl inicialice la biblioteca SSL correctamente para esta aplicación. Esto solo necesita hacerse una vez por aplicación, así que si tu programa u otra biblioteca ya lo hace, este bit no debería ser necesario.

libcurl tiene un mecanismo de protección predeterminado que detecta si curl_global_init(3) no ha sido llamado para cuando se llama a curl_easy_perform(3) y si ese es el caso, libcurl ejecuta la función por sí misma con un patrón de bits estimado. Tenga en cuenta que depender únicamente de esto no se considera correcto ni bueno.

Cuando el programa ya no utilice libcurl, debe llamar a curl_global_cleanup(3), que es lo opuesto a la llamada de inicialización. Realiza las operaciones inversas para limpiar los recursos que la llamada a curl_global_init(3) inicializó.

Deben evitarse llamadas repetidas a curl_global_init(3) y curl_global_cleanup(3). Solo deben llamarse una vez cada una.

Características que Proporciona libcurl

Se considera una buena práctica determinar las características de libcurl en tiempo de ejecución en lugar de en tiempo de compilación (si es posible, por supuesto). Al llamar a curl_version_info(3) y verificar los detalles de la estructura devuelta, tu programa puede averiguar exactamente qué soporta la libcurl en ejecución.

Dos Interfaces

libcurl introdujo primero la llamada interfaz easy. Todas las operaciones en la interfaz easy se prefijan con 'curl_easy'. La interfaz easy te permite realizar transferencias únicas con una llamada a función síncrona y bloqueante.

libcurl también ofrece otra interfaz que permite transferencias simultáneas múltiples en un solo hilo, la llamada interfaz multi. Más sobre esa interfaz se detalla en un capítulo separado más adelante. Aún necesitas entender primero la interfaz easy, así que por favor continúa leyendo para una mejor comprensión.

Manejar la Interfaz Easy de libcurl

Para usar la interfaz easy, primero debes crear un manejador easy. Necesitas un manejador para cada sesión easy que quieras realizar. Básicamente, debes usar un manejador por cada hilo que planees usar para transferir. Nunca debes compartir el mismo manejador en múltiples hilos.

Obtén un manejador easy con

 handle = curl_easy_init();
Devuelve un manejador easy. Usando eso, procedes al siguiente paso: configurar tus acciones preferidas. Un manejador es solo una entidad lógica para la próxima transferencia o serie de transferencias.

Estableces propiedades y opciones para este manejador usando curl_easy_setopt(3). Controlan cómo se realizarán las transferencias subsiguientes que utilicen este manejador. Las opciones permanecen establecidas en el manejador hasta que se vuelvan a establecer a algo diferente. Son persistentes. Múltiples solicitudes utilizando el mismo manejador usan las mismas opciones.

Si en algún momento deseas anular todas las opciones previamente establecidas para un solo manejador easy, puedes llamar a curl_easy_reset(3) y también puedes hacer un clon de un manejador easy (con todas sus opciones establecidas) usando curl_easy_duphandle(3).

sections: - title: Basic Usage content: | strings son "cadenas", punteros a datos terminados con un byte cero. Cuando estableces cadenas con curl_easy_setopt(3), libcurl hace su propia copia para que no necesiten ser conservadas en tu aplicación después de ser establecidas[4].

Una de las propiedades más básicas para establecer en el manejador es la URL. Estableces tu URL preferida para la transferencia con CURLOPT_URL(3) de una manera similar a:

 curl_easy_setopt(handle, CURLOPT_URL, "http://example.com/");

Supongamos por un momento que deseas recibir datos ya que la URL identifica un recurso remoto que deseas obtener aquí. Dado que estás escribiendo un tipo de aplicación que necesita esta transferencia, asumo que te gustaría que los datos te fueran pasados directamente en lugar de simplemente pasarse a stdout. Por lo tanto, escribes tu propia función que coincide con este prototipo:

 size_t write_data(void *buffer, size_t size, size_t nmemb, void *userp);
Le dices a libcurl que pase todos los datos a esta función emitiendo una función similar a esta: 
 curl_easy_setopt(handle, CURLOPT_WRITEFUNCTION, write_data);
Puedes controlar qué datos recibe tu función de devolución de llamada en el cuarto argumento estableciendo otra propiedad: 
 curl_easy_setopt(handle, CURLOPT_WRITEDATA, &internal_struct);
Usando esa propiedad, puedes pasar fácilmente datos locales entre tu aplicación y la función que es invocada por libcurl. libcurl en sí mismo no toca los datos que pasas con CURLOPT_WRITEDATA(3).

libcurl ofrece su propia devolución de llamada interna predeterminada que se encarga de los datos si no estableces la devolución de llamada con CURLOPT_WRITEFUNCTION(3). Simplemente envía los datos recibidos a stdout. Puedes hacer que la devolución de llamada predeterminada escriba los datos en un archivo diferente pasando un 'FILE *' a un archivo abierto para escritura con la opción CURLOPT_WRITEDATA(3).

Ahora, necesitamos dar un paso atrás y respirar hondo. Aquí hay uno de esos raros detalles dependientes de la plataforma. ¿Lo viste? En algunas plataformas[2], libcurl no puede operar en manejadores de archivo abiertos por el programa. Por lo tanto, si usas la devolución de llamada predeterminada y pasas un manejador de archivo abierto con CURLOPT_WRITEDATA(3), libcurl falla. Deberías evitar esto para que tu programa funcione correctamente en prácticamente todas partes.

(CURLOPT_WRITEDATA(3) se conocía anteriormente como CURLOPT_FILE. Ambos nombres todavía funcionan y hacen lo mismo).

Si estás usando libcurl como una DLL de Windows, DEBES usar CURLOPT_WRITEFUNCTION(3) si estableces CURLOPT_WRITEDATA(3) - o experimentarás fallos.

Por supuesto, hay muchas más opciones que puedes establecer, y volveremos a algunas de ellas más tarde. Continuemos en cambio con la transferencia real:

 success = curl_easy_perform(handle);

curl_easy_perform(3) se conecta al sitio remoto, realiza los comandos necesarios y realiza la transferencia. Siempre que recibe datos, llama a la función de devolución de llamada que establecimos previamente. La función puede recibir un byte a la vez, o puede recibir muchos kilobytes a la vez. libcurl entrega tanto como sea posible tan a menudo como sea posible. Tu función de devolución de llamada debe devolver el número de bytes de los que "se ocupó". Si esa no es la misma cantidad de bytes que se le pasó, libcurl aborta la operación y devuelve un código de error.

Cuando la transferencia se completa, la función devuelve un código de retorno que te informa si tuvo éxito en su misión o no. Si un código de retorno no es suficiente para ti, puedes usar el CURLOPT_ERRORBUFFER(3) para apuntar libcurl a un búfer tuyo donde almacena un mensaje de error legible por humanos también.

Si luego quieres transferir otro archivo, el manejador está listo para ser utilizado de nuevo. Incluso se prefiere y se anima a reutilizar un manejador existente si tienes la intención de realizar otra transferencia. libcurl entonces intenta reutilizar una conexión previa.

Para algunos protocolos, descargar un archivo puede implicar un proceso complicado de inicio de sesión, configuración del modo de transferencia, cambio del directorio actual y finalmente transferencia de los datos del archivo. libcurl se encarga de toda esa complicación por ti. Dada simplemente la URL de un archivo, libcurl se encarga de todos los detalles necesarios para mover el archivo de una máquina a otra.

Consulta libcurl-thread(3) para más información. - title: When It does not Work content: | Hay momentos en que la transferencia falla por alguna razón. Podrías haber establecido la opción incorrecta de libcurl o malinterpretado qué hace realmente la opción de libcurl, o el servidor remoto podría devolver respuestas no estándar que confunden a la biblioteca, lo que luego confunde a tu programa.

Hay una regla de oro cuando ocurren estas cosas: establece la opción CURLOPT_VERBOSE(3) a 1. hace que la biblioteca envíe todos los detalles del protocolo que envía, información interna y también algunos datos del protocolo recibido (especialmente al usar FTP). Si estás usando HTTP, agregar las cabeceras en la salida recibida para estudiarlas también es una forma inteligente de obtener una mejor comprensión de por qué el servidor se comporta como lo hace. Incluye las cabeceras en la salida normal del cuerpo con CURLOPT_HEADER(3) establecido en 1.

Por supuesto, todavía quedan errores. Necesitamos saber sobre ellos para poder corregirlos, por lo que dependemos en gran medida de tus informes de errores. Cuando reportes posibles errores en libcurl, por favor incluye tantos detalles como sea posible: un volcado de protocolo que produce CURLOPT_VERBOSE(3), la versión de la biblioteca, la mayor parte posible de tu código que usa libcurl, el nombre y la versión del sistema operativo, el nombre y la versión del compilador, etc.

Si CURLOPT_VERBOSE(3) no es suficiente, aumenta el nivel de datos de depuración que recibe tu aplicación usando CURLOPT_DEBUGFUNCTION(3).

Obtener un conocimiento profundo sobre los protocolos involucrados nunca está de más, y si estás intentando hacer cosas extrañas, podrías entender mejor libcurl y cómo usarlo si estudias los documentos RFC apropiados al menos brevemente.

- title: Upload Data to a Remote Site content: | libcurl intenta mantener un enfoque independiente del protocolo para la mayoría de las transferencias, por lo tanto, subir a un sitio FTP remoto es similar a subir datos a un servidor HTTP con una solicitud PUT.

Por supuesto, primero creas un manejador fácil o reutilizas uno existente. Luego estableces la URL sobre la que operar, como antes. Esta es la URL remota, que ahora subimos.

Como estamos escribiendo una aplicación, lo más probable es que queramos que libcurl obtenga los datos de carga solicitándolos nosotros. Para hacer que lo haga, establecemos la devolución de llamada de lectura y el puntero personalizado que libcurl pasa a nuestra devolución de llamada de lectura. La devolución de llamada de lectura debe tener un prototipo similar a:

 size_t function(char *bufptr, size_t size, size_t nitems, void *userp);
Donde bufptr es el puntero a un búfer que llenamos con datos para subir y nitems es el tamaño del búfer y, por lo tanto, la cantidad máxima de datos que podemos devolver a libcurl en esta llamada. El puntero userp es el puntero personalizado que establecemos para apuntar a una estructura nuestra para pasar datos privados entre la aplicación y la devolución de llamada. 
 curl_easy_setopt(handle, CURLOPT_READFUNCTION, read_function);
 curl_easy_setopt(handle, CURLOPT_READDATA, &filedata);
Le dices a libcurl que queremos subir: 
 curl_easy_setopt(handle, CURLOPT_UPLOAD, 1L);

Algunos protocolos no se comportan correctamente cuando las cargas se realizan sin ningún conocimiento previo del tamaño de archivo esperado. Por lo tanto, establece el tamaño del archivo de carga usando CURLOPT_INFILESIZE_LARGE(3) para todos los tamaños de archivo conocidos como esto[1]:

 /* en este ejemplo, file_size debe ser una variable curl_off_t */
 curl_easy_setopt(handle, CURLOPT_INFILESIZE_LARGE, file_size);

Cuando llamas a curl_easy_perform(3) esta vez, realiza todas las operaciones necesarias y cuando haya invocado la carga, llama a tu devolución de llamada proporcionada para obtener los datos a subir. El programa debe devolver tantos datos como sea posible en cada invocación, ya que es probable que eso haga que la carga se realice lo más rápido posible. La devolución de llamada debe devolver el número de bytes que escribió en el búfer. Devolver 0 señala el final de la carga.

- title: Passwords content: | Muchos protocolos usan o incluso requieren que se proporcionen nombre de usuario y contraseña para poder descargar o subir los datos de tu elección. libcurl ofrece varias formas de especificarlos.

La mayoría de los protocolos admiten que especifiques el nombre y la contraseña en la propia URL. libcurl detecta esto y los utiliza en consecuencia. Esto se escribe así:

 protocol://user:password@example.com/path/
Si necesitas algún carácter extraño en tu nombre de usuario o contraseña, debes introducirlos codificados en URL, como %XX donde XX es un número hexadecimal de dos dígitos.

libcurl también proporciona opciones para establecer varias contraseñas. El nombre de usuario y la contraseña, como se muestran incrustados en la URL, pueden configurarse en su lugar con la opción CURLOPT_USERPWD(3). El argumento pasado a libcurl debe ser un char * a una cadena en el formato "user:password". De manera similar a esto:

 curl_easy_setopt(handle, CURLOPT_USERPWD, "myname:thesecret");

Otro caso en el que pueden ser necesarios el nombre y la contraseña en ocasiones es para aquellos usuarios que necesitan autenticarse ante un proxy que utilizan. libcurl ofrece otra opción para esto, CURLOPT_PROXYUSERPWD(3). Se utiliza de forma bastante similar a la opción CURLOPT_USERPWD(3) así:

 curl_easy_setopt(handle, CURLOPT_PROXYUSERPWD, "myname:thesecret");

Hay una forma "estándar" de Unix de larga data para almacenar nombres de usuario y contraseñas FTP, a saber, en el archivo $HOME/.netrc (en Windows, libcurl también verifica la variable de entorno %USERPROFILE% si %HOME% no está configurada, y prueba "_netrc" como nombre). El archivo debe hacerse privado para que solo el usuario pueda leerlo (ver también el capítulo "Consideraciones de Seguridad"), ya que podría contener la contraseña en texto plano. libcurl tiene la capacidad de usar este archivo para averiguar qué conjunto de nombre de usuario y contraseña usar para un host particular.  curl_easy_setopt(handle, CURLOPT_PROXYTYPE, CURLPROXY_SOCKS4);

Variables de Entorno
-
libcurl comprueba y utiliza automáticamente un conjunto de variables de entorno para saber qué proxies utilizar para ciertos protocolos. Los nombres de las variables siguen una vieja tradición y se construyen como "[protocolo]_proxy" (nota las minúsculas). Esto hace que la variable 'http_proxy' se compruebe para un nombre de proxy a utilizar cuando la URL de entrada es HTTP. Siguiendo la misma regla, la variable llamada 'ftp_proxy' se comprueba para URLs FTP. De nuevo, los proxies son siempre proxies HTTP, los diferentes nombres de las variables simplemente permiten utilizar diferentes proxies HTTP. - El contenido de la variable de entorno del proxy debe estar en el formato "[protocolo://][usuario:contraseña@]máquina[:puerto]". Donde la parte de protocolo:// especifica qué tipo de proxy es, y el número de puerto opcional especifica en qué puerto opera el proxy. Si no se especifica, se utiliza el número de puerto por defecto interno, y es muy probable que no sea el que te gustaría que fuera. - Hay dos variables de entorno especiales. 'all_proxy' es lo que establece el proxy para cualquier URL en caso de que la variable específica del protocolo no se haya establecido, y 'no_proxy' define una lista de hosts que no deben usar un proxy, aunque una variable lo indique. Si 'no_proxy' es un asterisco simple ("*"), coincide con todos los hosts. - Para deshabilitar explícitamente la comprobación y el uso de variables de entorno de proxy por parte de libcurl, establece el nombre del proxy en "" - una cadena vacía - con `CURLOPT_PROXY`. -
-
SSL y Proxies
-
SSL es para conexiones seguras punto a punto. Esto implica un cifrado fuerte y cosas similares, que efectivamente hacen imposible que un proxy actúe como un "hombre en el medio", que es la tarea del proxy, como se discutió anteriormente. En su lugar, la única forma de que SSL funcione sobre un proxy HTTP es pedirle al proxy que canalice todo sin poder verificar o manipular el tráfico. - Abrir una conexión SSL sobre un proxy HTTP es, por lo tanto, una cuestión de pedirle al proxy una conexión directa al host de destino en un puerto especificado. Esto se hace con la solicitud HTTP CONNECT. ("por favor, querido proxy, conéctame a ese host remoto"). - Debido a la naturaleza de esta operación, donde el proxy no tiene idea de qué tipo de datos pasan a través de este túnel, esto rompe algunas de las pocas ventajas que provienen del uso de un proxy, como el almacenamiento en caché. Muchas organizaciones impiden este tipo de tunelización a números de puerto de destino distintos de 443 (que es el número de puerto HTTPS por defecto). -

Tunelización

Tunelización a través de Proxy

Tunneling a través de Proxy
Como se explicó anteriormente, la tunelización es necesaria para que SSL funcione y a menudo incluso está restringida a la operación destinada a SSL; HTTPS.

Sin embargo, este no es el único momento en el que la tunelización de proxy puede ofrecerle beneficios a usted o a su aplicación.

Dado que la tunelización abre una conexión directa desde su aplicación a la máquina remota, de repente reintroduce la capacidad de realizar operaciones que no sean HTTP a través de un proxy HTTP. De hecho, puede usar cosas como la carga FTP o comandos personalizados de FTP de esta manera.

Nuevamente, esto a menudo lo impiden los administradores de los proxies y rara vez se permite.

Indique a libcurl que use la tunelización de proxy de esta manera:

 curl_easy_setopt(handle, CURLOPT_HTTPPROXYTUNNEL, 1L);
De hecho, puede haber ocasiones en las que desee realizar operaciones HTTP sencillas utilizando un túnel de este tipo, ya que esto le permite operar en el servidor remoto en lugar de pedirle al proxy que lo haga. ¡libcurl tampoco se interpone en el camino de tales acciones innovadoras!
Configuración Automática de Proxy
Netscape fue el primero en proponer esto. Básicamente, es una página web (generalmente con extensión .pac) con un JavaScript que, al ser ejecutado por el navegador con la URL solicitada como entrada, devuelve información al navegador sobre cómo conectarse a la URL. La información devuelta puede ser "DIRECT" (lo que significa que no se debe usar ningún proxy), "PROXY host:port" (para indicar al navegador dónde se encuentra el proxy para esta URL en particular) o "SOCKS host:port" (para dirigir el navegador a un proxy SOCKS).

libcurl no tiene medios para interpretar o evaluar JavaScript y, por lo tanto, no lo admite. Si se encuentra en una situación en la que se enfrenta a este desagradable invento, los siguientes consejos se han mencionado y utilizado en el pasado:

- Dependiendo de la complejidad de JavaScript, escriba un script que lo traduzca a otro idioma y ejecútelo.

- Lea el código JavaScript y reescriba la misma lógica en otro idioma.

- Implemente un intérprete de JavaScript; la gente ha utilizado con éxito el motor JavaScript de Mozilla en el pasado.

- Pida a sus administradores que detengan esto, para una configuración de proxy estática o similar.

La Persistencia es el Camino hacia la Felicidad

Reciclar el mismo handle 'easy' varias veces al realizar múltiples solicitudes es el camino a seguir.

Después de cada operación individual de curl_easy_perform(3), libcurl mantiene la conexión viva y abierta. Una solicitud posterior que utilice el mismo handle 'easy' para el mismo host podría simplemente poder usar la conexión ya abierta. ¡Esto reduce mucho el impacto en la red!

Incluso si la conexión se interrumpe, todas las conexiones que involucran SSL al mismo host nuevamente se benefician de la caché de ID de sesión de libcurl, que reduce drásticamente el tiempo de reconexión.

Las conexiones FTP que se mantienen activas ahorran mucho tiempo, ya que se omiten los ciclos de ida y vuelta de comandos-respuesta, y tampoco corre el riesgo de ser bloqueado sin permiso para iniciar sesión nuevamente, como ocurre en muchos servidores FTP que solo permiten que N personas inicien sesión al mismo tiempo.

libcurl almacena en caché los resultados de la resolución de nombres DNS, para que las búsquedas de un nombre previamente buscado sean mucho más rápidas.

Otros detalles interesantes que mejoran el rendimiento para solicitudes posteriores también pueden agregarse en el futuro.

Cada handle 'easy' intenta mantener vivas las últimas conexiones durante un tiempo en caso de que se vuelvan a utilizar. Puede establecer el tamaño de esta "caché" con la opción CURLOPT_MAXCONNECTS(3). El valor predeterminado es 5. Raramente tiene sentido cambiar este valor, y si piensa en cambiarlo, a menudo es solo cuestión de volver a pensar.

Para forzar que su próxima solicitud no utilice una conexión ya existente, puede hacerlo estableciendo CURLOPT_FRESH_CONNECT(3) en 1. En un espíritu similar, también puede prohibir que la próxima solicitud "descanse" y posiblemente se reutilice después de la solicitud estableciendo CURLOPT_FORBID_REUSE(3) en 1.

Personalizando Operaciones

Actualmente hay un desarrollo en curso donde cada vez más protocolos se basan en HTTP para el transporte. Esto tiene beneficios obvios, ya que HTTP es un protocolo probado y confiable que está ampliamente implementado y tiene un excelente soporte para proxies.

Cuando utiliza uno de estos protocolos, e incluso al realizar otros tipos de programación, puede necesitar cambiar los modales tradicionales de HTTP (o FTP o...). Puede necesitar cambiar palabras, encabezados o varios datos.

libcurl también es tu amigo aquí.

CURLOPT_CUSTOMREQUEST
Si lo único que desea es cambiar la palabra clave de la solicitud HTTP real, como cuando GET, HEAD o POST no son suficientes para usted, CURLOPT_CUSTOMREQUEST(3) está ahí para usted. Es fácil de usar: 
curl_easy_setopt(handle, CURLOPT_CUSTOMREQUEST, "MYOWNREQUEST");

Al utilizar la solicitud personalizada, cambia la palabra clave de la solicitud real que está realizando. Por lo tanto, por defecto realiza una solicitud GET, pero también puede realizar una operación POST (como se describió anteriormente) y luego reemplazar la palabra clave POST si lo desea. Usted manda.

Modificar Encabezados
Los protocolos similares a HTTP pasan una serie de encabezados al servidor al realizar la solicitud, y usted es libre de pasar cualquier cantidad de encabezados adicionales que considere apropiados. Agregar encabezados es así de fácil: 
struct curl_slist *headers=NULL; /* inicializar a NULL es importante */
headers = curl_slist_append(headers, "Hey-server-hey: how are you?");
headers = curl_slist_append(headers, "X-silly-content: yes");
/* pasar nuestra lista de encabezados hechos a medida */
curl_easy_setopt(handle, CURLOPT_HTTPHEADER, headers);
curl_easy_perform(handle); /* transferir http */
curl_slist_free_all(headers); /* liberar la lista de encabezados */

... y si cree que algunos de los encabezados generados internamente, como Accept: o Host:, no contienen los datos que desea que contengan, puede reemplazarlos simplemente estableciéndolos también:

headers = curl_slist_append(headers, "Accept: Agent-007");
headers = curl_slist_append(headers, "Host: munged.host.line");
Eliminar Encabezados
Si reemplaza un encabezado existente con uno sin contenido, evita que se envíe el encabezado. Por ejemplo, si desea evitar por completo el envío del encabezado "Accept:", puede deshabilitarlo con código similar a esto:


headers = curl_slist_append(headers, "Accept:");

Tanto reemplazar como cancelar encabezados internos deben hacerse con cuidado y debe tener en cuenta que puede violar el protocolo HTTP al hacerlo.

Forzar la codificación de transferencia por fragmentos (chunked)
Al asegurarse de que una solicitud utilice el encabezado personalizado "Transfer-Encoding: chunked" al realizar una operación HTTP que no sea GET, libcurl cambia a la carga en "fragmentos", aunque el tamaño de los datos a cargar sea conocido. Por defecto, libcurl generalmente cambia a la carga en fragmentos automáticamente si el tamaño de los datos de carga es desconocido.
Versión HTTP
Todas las solicitudes HTTP incluyen el número de versión para indicar al servidor qué versión admitimos. libcurl habla HTTP 1.1 por defecto. Algunos servidores antiguos no responden bien a las solicitudes 1.1 y, al tratar con cosas antiguas y obstinadas como esas, puede indicar a libcurl que use 1.0 en su lugar haciendo algo como esto:


curl_easy_setopt(handle, CURLOPT_HTTP_VERSION, CURL_HTTP_VERSION_1_0);

Comandos Personalizados de FTP
No todos los protocolos son similares a HTTP, por lo que lo anterior puede no ayudarle cuando desee que, por ejemplo, sus transferencias FTP se comporten de manera diferente.

Enviar comandos personalizados a un servidor FTP significa que debe enviar los comandos exactamente como los espera el servidor FTP (RFC 959 es una buena guía aquí), y solo puede usar comandos que funcionen únicamente en la conexión de control. Todos los tipos de comandos que requieren intercambio de datos y, por lo tanto, necesitan una conexión de datos deben dejarse al juicio de libcurl. También tenga en cuenta que libcurl hace todo lo posible para cambiar de directorio al directorio de destino antes de realizar cualquier transferencia, por lo que si cambia de directorio (con CWD o similar) puede confundir a libcurl y luego es posible que no intente transferir el archivo al directorio remoto correcto.

Un pequeño ejemplo que elimina un archivo dado antes de una operación:

 headers = curl_slist_append(headers, "DELE file-to-remove");
 /* pasar la lista de comandos personalizados al handle */
 curl_easy_setopt(handle, CURLOPT_QUOTE, headers);
 curl_easy_perform(handle); /* ¡transferir datos ftp! */
 curl_slist_free_all(headers); /* liberar la lista de encabezados */

Si en cambio quisiera que esta operación (o cadena de operaciones) ocurra _después_ de que se haya realizado la transferencia de datos, la opción para curl_easy_setopt(3) se llamaría en cambio CURLOPT_POSTQUOTE(3) y se usaría de la misma manera.

La Interfaz multi

La interfaz easy, descrita en detalle en este documento, es una interfaz síncrona que transfiere un archivo a la vez y no retorna hasta que ha terminado.

La interfaz multi, por otro lado, permite que tu programa transfiera múltiples archivos en ambas direcciones al mismo tiempo, sin forzarte a usar múltiples hilos. El nombre podría hacer parecer que la interfaz multi es para programas multihilo, pero la verdad es casi la inversa. La interfaz multi permite a una aplicación de un solo hilo realizar el mismo tipo de transferencias múltiples y simultáneas que pueden realizar los programas multihilo. Permite muchos de los beneficios de las transferencias multihilo sin la complejidad de gestionar y sincronizar muchos hilos.

Para complicar un poco más las cosas, existen incluso dos versiones de la interfaz multi. La basada en eventos, también llamada multi_socket, y la "normal" diseñada para usarse con select(). Consulte la página man libcurl-multi.3 para obtener detalles sobre la API basada en eventos multi_socket; esta descripción es para la orientada a select().

Para usar esta interfaz, es mejor si primero comprendes los conceptos básicos de cómo usar la interfaz easy. La interfaz multi es simplemente una forma de realizar múltiples transferencias al mismo tiempo sumando múltiples handles easy a una "pila multi".

Creas los handles easy que deseas, uno por cada transferencia concurrente, y estableces todas las opciones tal como aprendiste arriba, y luego creas un handle multi con curl_multi_init(3) y añades todos esos handles easy a ese handle multi con curl_multi_add_handle(3).

Cuando hayas añadido los handles que tienes por el momento (aún puedes añadir nuevos en cualquier momento), inicias las transferencias llamando a curl_multi_perform(3).

curl_multi_perform(3) es asíncrona. Solo realiza lo que se puede hacer ahora y luego devuelve el control a tu programa. Está diseñada para no bloquear nunca. Necesitas seguir llamando a la función hasta que todas las transferencias se completen.

El mejor uso de esta interfaz es cuando haces un select() en todos los descriptores de archivo o sockets posibles para saber cuándo volver a llamar a libcurl. Esto también te facilita esperar y responder a acciones en los sockets/handles de tu propia aplicación. Descubres qué seleccionar usando curl_multi_fdset(3), que rellena un conjunto de variables fd_set por ti con los descriptores de archivo particulares que libcurl utiliza en ese momento.

Cuando luego llamas a select(), esta retorna cuando uno de los handles de archivo señala una acción y luego llamas a curl_multi_perform(3) para permitir que libcurl haga lo que necesita hacer. Ten en cuenta que libcurl también incluye algo de código de tiempo de espera, por lo que te aconsejamos que nunca uses tiempos de espera largos en select() antes de volver a llamar a curl_multi_perform(3). Se proporciona curl_multi_timeout(3) para ayudarte a obtener un período de tiempo de espera adecuado.

Otra precaución que debes tomar: llama siempre a curl_multi_fdset(3) inmediatamente antes de la llamada a select(), ya que el conjunto actual de descriptores de archivo puede cambiar en cualquier invocación de función de curl.

Si deseas detener la transferencia de uno de los handles easy en la pila, puedes usar curl_multi_remove_handle(3) para eliminar handles easy individuales. Recuerda que los handles easy deben ser limpiados con curl_easy_cleanup(3).

Cuando una transferencia dentro de la pila multi ha finalizado, el contador de transferencias en ejecución (rellenado por curl_multi_perform(3)) disminuye. Cuando el número llega a cero, todas las transferencias han terminado.

curl_multi_info_read(3) se puede usar para obtener información sobre transferencias completadas. Luego retorna el código CURLcode para cada transferencia easy, para permitirte determinar el éxito de cada transferencia individual.

Compartir Datos Entre Handles Easy

Puedes compartir algunos datos entre handles easy cuando se usa la interfaz easy, y algunos datos se comparten automáticamente cuando usas la interfaz multi.

Cuando añades handles easy a un handle multi, estos handles easy comparten automáticamente muchos de los datos que de otro modo se mantendrían en una base por handle easy cuando se usa la interfaz easy.

La caché DNS se comparte entre los handles dentro de un handle multi, haciendo que las resoluciones de nombres posteriores sean más rápidas, y el pool de conexiones que se mantiene para permitir mejores conexiones persistentes y reutilización de conexiones también se comparte. Si estás usando la interfaz easy, aún puedes compartir estos entre handles easy específicos usando la interfaz share, ver libcurl-share(3).

Algunas cosas nunca se comparten automáticamente, ni siquiera dentro de los handles multi, como por ejemplo las cookies, por lo que la única forma de compartir eso es con la interfaz share.
