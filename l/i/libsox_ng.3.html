DESCRIPCIÓN

libsox_ng es una biblioteca de lectores/escritores de formatos de archivo de muestras de sonido y procesadores de efectos de sonido. Se desarrolla principalmente para ser utilizado por SoX, pero cualquier aplicación de audio podría encontrarla útil.

Este no es realmente un manual para la API de libsox_ng; es una introducción a las operaciones básicas para leer y escribir archivos de audio y cómo usar cadenas de efectos, seguida de notas sobre cómo escribir nuevos manejadores de formatos y efectos. Para una descripción exhaustiva de la API de libsox_ng, consulte http://martinwguy.net/test/soxygen/sox_8h.html

int sox_format_init(void)
sox_format_init() realiza la inicialización requerida por todos los manejadores de formatos de archivo. Si se compila con soporte de biblioteca dinámica, esto detectará e inicializará todas las bibliotecas externas. Debería llamarse antes de realizar cualquier operación de archivo.
void sox_format_quit(void)
sox_format_quit() realiza la limpieza relacionada con todos los manejadores de formatos de archivo y debería llamarse después de que se hayan completado todas las operaciones de archivo.
sox_format_t *sox_open_read(char const *path, sox_signalinfo_t const *signal, sox_encodinginfo_t const *encoding, char const *filetype)
sox_open_read() abre un archivo para lectura. Un nombre especial de `-' lee datos de stdin. Si signal no es NULL, especifica las propiedades de la señal de audio, como la frecuencia de muestreo o el número de canales. Si encoding no es NULL, especifica la codificación de la muestra. Tanto signal como encoding normalmente solo son necesarios para archivos de audio sin encabezado donde esa información no se almacena en el archivo. Si filetype no es NULL, especifica el tipo de archivo usando las cadenas cortas enumeradas en soxformat_ng(7); de lo contrario, el tipo de archivo se adivina a partir de la extensión del nombre de archivo y/o el contenido del archivo.

Tras una finalización exitosa, sox_open_read() devuelve un puntero a un sox_format_t completado, que eventualmente debe cerrarse con sox_close(), o NULL en caso contrario. Actualmente no hay forma de determinar la razón del fallo excepto por el mensaje de error impreso en la salida de error estándar (stderr).

sox_format_t *sox_open_write(char const *filename, sox_signalinfo_t const *signal, sox_encodinginfo_t const *encoding, char const *filetype, sox_oob_t const *oob, sox_bool (*overwrite_permitted)(char const *filename))
sox_open_write() abre el archivo nombrado para escritura. Un nombre especial de `-' escribe datos en stdout. Si signal no es NULL, especifica el formato de datos del archivo de salida; la estructura signal completada por sox_open_read() se puede usar para copiar datos en el mismo formato. Si encoding no es NULL, especifica la codificación de muestra deseada. Dado que la mayoría de los formatos de archivo pueden codificar datos de diferentes maneras, esto generalmente debe especificarse; si es NULL, se utiliza un valor predeterminado. Si filetype no es NULL, especifica el tipo de archivo a escribir, utilizando las cadenas cortas enumeradas en soxformat_ng(7); de lo contrario, el tipo de archivo es el de la extensión del nombre de archivo. Si oob no es NULL y el tipo de archivo admite comentarios y otros datos fuera de banda como puntos de bucle e información de instrumentos, estos se almacenan en el encabezado del archivo. Si overwrite no es NULL y el archivo ya existe, se llama a la función con el nombre del archivo como argumento para determinar si el archivo debe ser sobrescrito. Si es NULL, los archivos existentes se sobrescriben.

sox_open_write() devuelve un puntero a un sox_format_t que debe cerrarse con sox_close(), o NULL si falla. Al igual que sox_open_read(), no hay forma de determinar la razón del fallo, excepto por el mensaje que imprime.

size_t sox_read(sox_format_t *format, sox_sample_t *buf, size_t len)
sox_read() lee len muestras en buf utilizando el manejador de formato especificado por format. Es responsabilidad del llamante proporcionar un búfer lo suficientemente grande para hasta len muestras. Todos los datos se convierten a muestras de 32 bits con signo antes de colocarse en buf. El valor de len es el número total de muestras (número de fotogramas de muestra multiplicado por el número de canales) y si su valor no es un múltiplo del número de canales, puede ocurrir cualquier cosa.

Devuelve el número de muestras leídas, que puede ser menor que el número solicitado, o cero al final del archivo o si ocurrió un error. El valor de retorno de sox_read() no distingue entre el final de un archivo y un error, pero puede inspeccionar format->sox_errno para diferenciar. Debería ser SOX_SUCCESS o SOX_EOF a menos que haya ocurrido algún otro error previamente; puede borrar format->sox_errno a 0 de antemano para estar seguro y, si es algo que no sea SOX_SUCCESS, habrá una razón más explícita en format->sox_errstr.

size_t sox_read(sox_format_t *format, sox_sample_t *buf, size_t len)
sox_read() devuelve el número de muestras leídas correctamente. Si ocurre un error o se ha llegado al final del archivo, el valor de retorno es cero o SOX_EOF, dependiendo de la función.
size_t sox_write(sox_format_t *format, sox_sample_t const *buf, size_t len)
sox_write() escribe len muestras desde buf al archivo descrito por format y los datos de 32 bits con signo en buf se convierten según el formato. El valor de len es el total de muestras y debe ser divisible por el número de canales, de lo contrario ocurrirán cosas inesperadas. Devuelve el número real de muestras codificadas, cero si ocurrió un error.
int sox_seek(sox_format_t *format, size_t offset, int whence)
sox_seek() reposiciona el desplazamiento del archivo asociado con format al offset dado. En caso de éxito, devuelve SOX_SUCCESS; SOX_EOF en caso contrario. Dado que sox_read() y sox_write() realizan transformaciones complejas de los datos de los archivos, su utilidad es cuestionable.
int sox_close(sox_format_t *format)
sox_close() desasocia un format de su archivo subyacente. Si el manejador de formato se estaba utilizando para salida, cualquier dato almacenado en búfer se escribe primero. Devuelve SOX_SUCCESS si todo salió bien; si no, SOX_EOF o, ocasionalmente, algún otro código de error. Al igual que sox_open_read() y sox_open_write(), actualmente no hay forma de determinar la razón precisa del fallo, aparte de los mensajes impresos en stderr. En cualquier caso, no se debe volver a utilizar el manejador, ni siquiera otra llamada a sox_close().

Establecer opciones solo se admite antes de que se inicie el efecto. El comportamiento no está definido si se llama cuando el efecto ya ha comenzado.

TYPES

sox_sample_t A signed 32 bit integer used internally to represent audio samples.

sox_effect_t An effects structure. It is an array of effects structures. The individual effects are referenced by index.

sox_effects_chain_t A structure that holds an effects chain with its associated effects and parameters.

sox_format_t A structure that holds information about an audio file stream. This includes signal information (rate, bits, channels, etc.), file state, and pointers to file format specific handlers.

sox_signal_t A structure holding signal information such as sample rate, number of channels, bit depth, and encoding.

sox_globals_t A structure that holds global state for the library. Initializing this structure can be done with a call to sox_init().

DESCRIPTION

The library functions provide access to SoX's audio file handling and effects processing capabilities. Applications can use these functions to read and write audio files, and to apply a chain of audio effects.

sox_open_stream opens an audio file stream identified by pathname. The type parameter specifies the desired sample type of the output stream, and type_out specifies the desired sample type of the input stream. The mode parameter specifies how the file is to be opened, and may be "r" for read, "w" for write, or "rw" for read and write.

sox_open_play opens an audio file stream identified by pathname for playback. It is equivalent to calling sox_open_stream with type set to NULL, type_out set to NULL, and mode set to "r".

sox_open_record opens an audio file stream identified by pathname for recording. It is equivalent to calling sox_open_stream with type set to NULL, type_out set to NULL, and mode set to "w".

sox_write writes audio samples from buf to the file stream sf. The number of samples to write is specified by len, which is updated on return to indicate the number of samples actually written.

sox_read reads audio samples from the file stream sf into buf. The maximum number of samples to read is specified by len.

sox_seek sets the file position in the audio file stream sf. The argument offset specifies the new position, and whence specifies how the offset is interpreted. It may be SEEK_SET, SEEK_CUR, or SEEK_END.

sox_close closes the audio file stream sf and releases any associated resources.

sox_dup_effects_chain duplicates an effects chain. This is useful if you want to modify an effects chain without affecting the original chain.

sox_effect_options sets the options for a particular effect in the effects chain. The argument ep is a pointer to the effect structure, n is the number of arguments, and argv is an array of strings representing the arguments.

sox_get_effects_chain returns a pointer to the effects chain associated with the audio file stream sf. Changes made to the returned effects chain will affect subsequent read/write operations on the stream. The effects chain is not duplicated, so modifications to it will affect the original chain. This is useful for inspection and modification of effects chains.

sox_set_globals allows you to set global variables for the library. This should normally be done using sox_init().

sox_set_comment sets the comment chunk in an audio file. This is only supported for certain audio file formats.

sox_signal_to_num_samples_const, sox_signal_to_num_samples, sox_signal_to_num_secs_const, and sox_signal_to_num_secs convert between time and sample counts given a signal structure which contains the sample rate.

EFFECTS CHAIN MANAGEMENT

int sox_add_effect(sox_effects_chain_t *ecp, const char *effect_name, sox_effect_option_t *opts, sox_signal_t *in_sig)
Adds an effect to the end of the effects chain represented by ecp. The effect to be added is identified by effect_name. The opts parameter is an array of options for the effect, and in_sig specifies the input signal characteristics. The function updates the signal characteristics in in_sig based on the effect's processing. It returns SOX_SUCCESS on success, or an error code otherwise. The effect itself determines what the output signal should be but, depending on the effect options given and on in, the effect may choose a different encoding such as changing the number of channels or the sample rate. Whatever output rate and channels the effect produces are written back to in ready to be passed to subsequent calls of sox_add_effect so that changes propagate to each new effect. It returns SOX_SUCCESS if it was successful.
void sox_delete_effects_chain(sox_effects_chain_t *ecp)
sox_delete_effects_chain() closes an effects chain down and releases any resources reserved during the creation of the chain. It also deletes all the effects in the chain.

EXAMPLES

SoX includes skeleton C files to assist you in writing new formats (skelform.c) and effects (skeleff.c). New formats can often just deal with the header and then use raw.c's routines for reading and writing.

example0.c and example1.c are a good starting point to see how to write applications using libsox_ng and sox_ng.c itself is also a good reference.

INTERNALS

SoX's formats and effects operate with an internal sample format of signed 32-bit integers. The data processing routines are called with buffers of these samples and buffer sizes which refer to the number of samples processed, not the number of bytes. File readers translate input samples to signed 32-bit integers and return the number of samples read. For example, data in linear signed byte format is left-shifted 24 bits.

Representing samples as integers can cause problems when processing audio. For example, if an effect to mix down left and right channels into one monophonic channel were to use the obvious

   *obuf++ = (*ibuf++ + *ibuf++)/2;
distortion may occur since the intermediate addition can overflow 32 bits. 
   *obuf++ = *ibuf++/2 + *ibuf++/2;
would get round the overflow but at the expense of the least significant bit.

Stereo data is stored with the left and right speaker data in successive samples and quadraphonic data is stored left front, right front, left rear, right rear.

FORMATS

A format is responsible for translating between sound sample files and an internal buffer. The internal buffer is stored in signed longs with a fixed sampling rate. The format operates from two data structures: a format structure and a private structure.

The format structure contains a list of control parameters for the audio: sampling rate, data size (8, 16 or 32 bits), encoding (unsigned, signed, floating point etc.), and the number of sound channels. It also contains other state information: whether the sample file needs to be byte-swapped, whether sox_seek() will work, its suffix, its file stream pointer, its format pointer and the format's private structure.

The private area is a preallocated data array for the format to use however it wishes. It should have a defined data structure and cast the array to that structure. See voc.c for an example of the use of a private data area. voc.c has to track the number of samples it writes and, when finishing, seek back to the beginning of the file and write it into the header. The private area is usually not very large and some effects, such as echo, lsx_malloc() larger areas for delay lines and such.

A format has 6 routines:

startread
Set up the format parameters, read in a data header and do anything else that needs to be done.
read
Given a buffer and a length, read up to that many samples, transform them into signed long integers, and copy them into the buffer. It returns the number of samples actually read.
stopread
Do what needs to be done when it has finished reading.
startwrite
Set up the format parameters, maybe write out a data header and any other preliminaries for writing the format.
write
Given a buffer and a length, copy that many samples out of the buffer, convert them from signed longs to the appropriate data and write them to the file. If it can't write out all the samples, it will return a lesser number of samples.
stopwrite
Typically, fix up the file header or whatever else needs to be done.

EFFECTS

Each effect runs with one input and one output stream. An effect's implementation comprises six functions that may be called according to the following flow diagram:

LOOP (invocations with different parameters)
  getopts
  LOOP (invocations with the same parameters)
    LOOP (channels)
      start
    LOOP (while there is input audio to process)
      LOOP (channels)
        flow
    LOOP (while there is output audio to generate)
      LOOP (channels)
        drain
    LOOP (channels)
      stop
  kill
Functions that an effect does not need can be NULL. An effect that is marked `MCHAN' does not use the LOOP (channels) lines and must perform multiple channel processing inside the affected functions. Multiple effect instances may be processed in parallel.
getopts
is called with a character string argument list for the effect.
start
is called with the signal parameters for the input and output streams.
flow
is called with input and output data buffers, and (by reference) the input and output data buffer sizes. It processes the input buffer into the output buffer, and sets the size variables to the numbers of samples actually processed. It is under no obligation to read from the input buffer or write to the output buffer during the same call. If the call returns SOX_EOF, this means that the effect will not read any more data and can be used to switch to drain mode sooner.
drain
is called when there are no more input data samples. If the effect wishes to generate more data samples, it copies the generated data into the given buffer and returns the number of samples generated. If it fills the buffer, it will be called again; The echo effect uses this to fade away.
stop
is called when there are no more input samples and no more output samples to process. It is typically used to close or free resources such as memory and temporary files that were allocated during start. See echo.c for an example.
kill
is called to allow resources allocated by getopts to be released. See pad.c for an example.

LINKING

How you link against libsox_ng depends on how SoX was built on your system. For a static build, just link against the library. For a dynamic build, use libtool to link with the correct linker flags. See the libtool manual for details; basically, you use it like this:

   libtool --mode=link gcc -o prog /path/to/libsox_ng.la

    NAME

    libsox_ng - SoX (Sound eXchange) library - the cross-platform sound processing library

    SYNOPSIS

    #include <sox.h>

int sox_init();
void sox_quit();

sox_format_t * sox_open_read(const char * filename, const sox_sample_format_t * fmt, ...);

sox_effect_chain_t * sox_create_effect_chain();
int sox_delete_effect_chain(sox_effect_chain_t * chain);
int sox_add_effect(sox_effect_chain_t * chain, const sox_effect_t * effect, const char ** args);
int sox_apply_chain(sox_effect_chain_t * chain, sox_format_t * in, sox_format_t * out);

const char * sox_strerror(int errnum);

    DESCRIPTION

    The SoX library is a cross-platform sound processing library. It provides a standard interface for reading, writing and manipulating audio files. The library supports a wide range of audio file formats and provides a powerful effects processing engine.

    The library is initialized by calling sox_init() and should be shut down by calling sox_quit() before the application exits.

    Audio files can be opened for reading or writing using sox_open_read() and sox_open_write() respectively. These functions return a sox_format_t handle which is used for subsequent operations. The format can be specified explicitly by passing a sox_sample_format_t struct, or it can be determined from the filename extension.

    Audio data is read from and written to files using sox_read() and sox_write(). These functions operate on buffers of type sox_audio_t, which represent samples. The number of samples to read or write is specified by the samples argument.

    Effects processing is handled by creating an effect chain using sox_create_effect_chain(). Effects are added to the chain using sox_add_effect(), which takes the effect name and an array of arguments. The chain can then be applied to an audio input and output using sox_apply_chain() or sox_process_chain().

    Information about available effects can be obtained using sox_get_effect_by_name(), sox_get_effect_by_num(), sox_effect_flags(), and sox_list_effects().

    Audio statistics can be retrieved for an opened audio file using sox_get_stats(). The statistics can then be converted to a human-readable string using sox_stats_string().

    The library version can be obtained using sox_version() and sox_version_string().

    Error information can be retrieved using sox_strerror().

    EXAMPLES

    // Initialize the SoX library
sox_init();

// Open an audio file for reading
sox_format_t * in_file = sox_open_read("input.wav", NULL, NULL, NULL);

// Create an effect chain
sox_effect_chain_t * chain = sox_create_effect_chain();

// Add a volume effect to the chain
const char * vol_args[] = {"-n", "0.5"};
sox_add_effect(chain, sox_get_effect_by_name("volume"), vol_args);

// Open an audio file for writing
sox_format_t * out_file = sox_open_write("output.wav", sox_get_signalinfo(in_file), NULL, NULL);

// Apply the effect chain
sox_process_chain(chain, in_file, out_file);

// Close the files and delete the chain
sox_close(in_file);
sox_close(out_file);
sox_delete_effect_chain(chain);

// Shut down the SoX library
sox_quit();

    EFFECTS

    The SoX library supports a wide range of audio effects. Some common effects include:

    • volume: Adjusts the volume of the audio.
    • trim: Trims silence from the beginning or end of the audio.
    • fade: Applies a fade-in or fade-out effect.
    • reverse: Reverses the audio.
    • rate: Resamples the audio to a different sample rate.
    • normvol: Normalizes the audio volume.
    • compand: Compresses or expands the dynamic range of the audio.

    Refer to the soxeffects(7) man page for a complete list of available effects and their arguments.

    LINKING

    To link against the SoX library, use the following flag:

    gcc your_program.c -o your_program -lsox_ng
