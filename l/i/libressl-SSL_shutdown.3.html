SSL_SHUTDOWN(3) Manual de funciones de biblioteca SSL_SHUTDOWN(3)

NOMBRE

SSL_shutdown — cerrar una conexión TLS/SSL

SINOPSIS

biblioteca “libssl” libcrypto
#include <openssl/ssl.h>

int
SSL_shutdown(SSL *ssl);

DESCRIPCIÓN

SSL_shutdown() cierra una conexión TLS/SSL activa. Envía la alerta de cierre “close notify” al par.

SSL_shutdown() intenta enviar la alerta de cierre “close notify” al par. Independientemente de si la operación tiene éxito o no, se establece el indicador SSL_SENT_SHUTDOWN y una sesión actualmente abierta se considera cerrada y válida, y se mantendrá en la caché de sesiones para su reutilización posterior.

El procedimiento de cierre consta de 2 pasos: el envío de la alerta de cierre “close notify” y la recepción de la alerta de cierre “close notify” del par. Según el estándar TLS, es aceptable que una aplicación solo envíe su alerta de cierre y luego cierre la conexión subyacente sin esperar la respuesta del par (de esta manera se pueden ahorrar recursos, ya que el proceso puede terminar o servir a otra conexión). Cuando la conexión subyacente se utilizará para más comunicaciones, se debe realizar el procedimiento de cierre completo (alertas bidireccionales “close notify”), para que los pares permanezcan sincronizados.

SSL_shutdown() admite el cierre unidireccional y bidireccional mediante su comportamiento de 2 pasos.

Cuando la aplicación es la primera en enviar la alerta de cierre “close notify”, SSL_shutdown() solo enviará la alerta y luego establecerá el indicador SSL_SENT_SHUTDOWN (para que la sesión se considere válida y se mantenga en caché). SSL_shutdown() devolverá 0. Si un cierre unidireccional es suficiente (la conexión subyacente se cerrará de todos modos), esta primera llamada a SSL_shutdown() es suficiente. Para completar el apretón de manos de cierre bidireccional, se debe volver a llamar a SSL_shutdown(). La segunda llamada hará que SSL_shutdown() espere la alerta de cierre “close notify” del par. En caso de éxito, la segunda llamada a SSL_shutdown() devolverá 1.

Si el par ya envió la alerta de cierre “close notify” y ya se procesó implícitamente dentro de otra función (SSL_read(3)), se establece el indicador SSL_RECEIVED_SHUTDOWN. SSL_shutdown() enviará la alerta de cierre “close notify”, establecerá el indicador SSL_SENT_SHUTDOWN y devolverá inmediatamente con 1. Si SSL_RECEIVED_SHUTDOWN ya está establecido, se puede comprobar utilizando la llamada SSL_get_shutdown() (ver también la llamada SSL_set_shutdown(3)).

Por lo tanto, se recomienda comprobar el valor de retorno de SSL_shutdown() y volver a llamar a SSL_shutdown() si el cierre bidireccional aún no está completo (valor de retorno de la primera llamada es 0).

El comportamiento de SSL_shutdown() depende adicionalmente del BIO subyacente.

Si el BIO subyacente es bloqueante, SSL_shutdown() solo devolverá una vez que el paso del apretón de manos haya finalizado o se haya producido un error.

Si el BIO subyacente es no bloqueante, SSL_shutdown() también devolverá cuando el BIO subyacente no pueda satisfacer las necesidades de SSL_shutdown() para continuar el apretón de manos. En este caso, una llamada a SSL_get_error(3) con el valor de retorno de SSL_shutdown() producirá SSL_ERROR_WANT_READ o SSL_ERROR_WANT_WRITE. El proceso de llamada debe repetir la llamada después de tomar las medidas apropiadas para satisfacer las necesidades de SSL_shutdown(). La acción depende del BIO subyacente. Al usar un socket no bloqueante, no hay nada que hacer, pero select(2) puede usarse para comprobar la condición requerida. Al usar un BIO de búfer, como un par de BIO, los datos deben escribirse en o recuperarse del BIO antes de poder continuar.

SSL_shutdown() puede modificarse para solo establecer la conexión en estado de “cierre” pero no para enviar realmente los mensajes de alerta de “close notify”; consulte SSL_CTX_set_quiet_shutdown(3). Cuando el cierre silencioso (“quiet shutdown”) está habilitado, SSL_shutdown() siempre tendrá éxito y devolverá 1.

VALORES DE RETORNO

Los siguientes valores de retorno pueden ocurrir:

0
El cierre aún no ha finalizado. Llame a SSL_shutdown() por segunda vez, si se va a realizar un cierre bidireccional. La salida de SSL_get_error(3) puede ser engañosa, ya que puede marcarse un SSL_ERROR_SYSCALL erróneo incluso si no ocurrió ningún error.
1
El cierre se completó con éxito. Se envió la alerta de cierre “close notify” y se recibió la alerta de cierre “close notify” del par.
−1
El cierre no fue exitoso porque ocurrió un error fatal a nivel de protocolo o un fallo de conexión. También puede ocurrir si se necesita una acción para continuar la operación para BIOs no bloqueantes. Llame a SSL_get_error(3) con el valor de retorno ret para averiguar el motivo.
