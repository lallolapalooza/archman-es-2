NOMBRE

libdnf5-actions - Plugin de Acciones

DESCRIPCIÓN

Este plugin permite definir acciones a ejecutar a través de los ganchos (hooks) de callback de libdnf5. Cada acción se engancha a un callback específico. Las acciones para los callbacks goal_resolved, pre_transaction y post_transaction pueden definir una regla de filtrado (similar a glob) sobre el NEVRA del paquete o los archivos del paquete, así como si el paquete es entrante o saliente.

CONFIGURACIÓN

El plugin no extiende la configuración estándar. Sin embargo, lee archivos de "acciones".

Los archivos de acciones se leen del directorio <libdnf5_plugins_config_dir>/actions.d/. Solo se leen los archivos con extensión ".actions".

FORMATO DEL ARCHIVO DE ACCIONES

Las líneas vacías y las líneas que comienzan con el carácter '#' (línea de comentario) se ignoran.

Cada línea no comentada define una acción y consta de cinco elementos separados por dos puntos: nombre_callback:filtro_paquete:dirección:opciones:comando.

nombre_callback

  • pre_base_setup
  • post_base_setup
  • repos_configured (añadido en la versión 1.0.0)
  • repos_loaded (añadido en la versión 1.0.0)
  • pre_add_cmdline_packages (añadido en la versión 1.0.0)
  • post_add_cmdline_packages (añadido en la versión 1.0.0)
  • goal_resolved (añadido en la versión 1.3.0)
  • pre_transaction
  • post_transaction
filtro_paquete
Una regla de filtrado (similar a glob) aplicada al NEVRA del paquete (también en sus formas abreviadas) o a los archivos del paquete.

Un filtro vacío significa ejecutar el comando una vez sin información sobre el paquete. El filtro "*" significa ejecutar el comando para cada paquete en la transacción que coincida con el filtro de dirección. El filtro solo puede estar no vacío para los callbacks goal_resolved, pre_transaction y post_transaction.

dirección
Filtra los paquetes por su dirección (entrante al sistema/saliente del sistema) en una transacción. Si está vacío, el filtro no se aplica. El filtro solo puede estar no vacío cuando se combina con un filtro_paquete no vacío.
  • in - paquetes que entran al sistema (degradación, instalación, reinstalación, actualización)
  • out - paquetes que salen del sistema (actualizados, degradados, reinstalados, eliminados, reemplazados/obsoletados)
opciones
Las opciones se separan por espacios. Un espacio dentro de una opción se puede escribir usando escape. (añadido en la versión 0.3.0)
•
enabled=<valor> - el valor especifica cuándo la acción está habilitada (añadido en la versión 0.3.0)
  • 1 - la acción siempre está habilitada
  • host-only - la acción solo está habilitada para operaciones en el host
  • installroot-only - la acción solo está habilitada para operaciones en la "installroot" alternativa
•
raise_error=<valor> - el <valor> especifica cómo se manejan los errores del proceso de acción. ¿Qué sucede si el proceso de acción no se inició o terminó con un código de salida distinto de cero o terminó de forma anormal (recibió una señal) o ocurrió un error durante la comunicación (error de sintaxis, interrupción de la comunicación, fallo al procesar la línea de salida en modo de comunicación simple). Si la opción no está presente, raise_error=0 por compatibilidad hacia atrás. (añadido en la versión 1.4.0)
  • 0 - los errores se registran
  • 1 - se lanza una excepción
comando
Cualquier archivo ejecutable con argumentos.

Los argumentos se separan por espacios. Un espacio dentro de un argumento se puede escribir usando escape. El escape también se puede usar para prevenir la sustitución y pasar caracteres especiales \a, \b, \f, \n, \r, \t, \v. El desescape de los argumentos se realiza después de la sustitución.

Las siguientes variables en el comando serán sustituidas:

  • ${pid} - ID del proceso
  • ${plugin.version} - versión del plugin de acciones (añadido en la versión 0.3.0)
  • ${conf.<nombre_opción>} - opción de la configuración base
  • ${conf.<patrón_repoid>.<nombre_opción>[=<patrón_valor>]} - lista de pares "repoid.opción=valor" (añadido en la versión 1.1.0)
  • ${var.<nombre_variable>} - variable
  • ${tmp.<nombre_variable_plugin_acciones>} - variable existe solo en el contexto del plugin de acciones
  • ${pkg.<nombre_atributo_paquete>} - valor del atributo del paquete
  • ${pkg.name} - nombre del paquete
  • ${pkg.arch} - arquitectura del paquete
  • ${pkg.version} - versión del paquete
  • ${pkg.release} - release del paquete
  • ${pkg.epoch} - epoch del paquete
  • ${pkg.na} - nombre.arquitectura del paquete
  • ${pkg.evr} - epoch-versión-release del paquete
  • ${pkg.nevra} - nevra del paquete (epoch 0 se oculta)
  • ${pkg.full_nevra} - nevra completa del paquete (epoch siempre está presente) ${name}-${epoch}:${ver}-${rel}.${arch}
  • ${pkg.repo_id} - ID del repositorio del paquete
  • ${pkg.license} - licencia del paquete
  • ${pkg.location} - la ubicación del archivo del paquete
  • ${pkg.vendor} - proveedor del paquete
  • ${pkg.action} - acción realizada sobre el paquete:
  • I - paquete recién instalado
  • U - paquete instalado como actualización
  • D - paquete instalado como degradación
  • R - paquete utilizado para reinstalación
  • E - paquete borrado (eliminado) del sistema (fue actualizado/degradado/reinstalado/eliminado)
  • O - paquete reemplazado (obsoletado)

El comando se evaluará para cada paquete que coincida con el filtro_paquete y la dirección. Sin embargo, después de la sustitución de variables, cualquier comando duplicado se eliminará y cada comando solo se ejecutará una vez por transacción. Los comandos se ejecutan en secuencia. No hay paralelismo. La sustitución de argumentos se realiza después de que el comando anterior ha completado. Esto permite que la sustitución utilice los resultados de los comandos anteriores. El orden de ejecución de los comandos sigue el orden en los archivos de acción, pero puede diferir del orden de los paquetes en la transacción. En otras palabras, cuando defines varias líneas de acción para el mismo filtro_paquete y dirección, estas líneas se ejecutarán en el orden en que se definieron en el archivo de acción cuando el filtro_paquete y la dirección coinciden con un paquete. Sin embargo, el orden en que se invoca un filtro_paquete particular depende de la posición del paquete correspondiente en la transacción.

Los pares repoid.opción=valor en la lista están separados por el carácter ','. El carácter ',' en el valor se reemplaza por la secuencia de escape "\x2C". Si se usa patrón_valor, solo se listarán los pares con el valor coincidente. El patrón_repoid y el patrón_valor pueden contener globs.

FORMATO DE SALIDA ESTÁNDAR DE ACCIÓN

La salida estándar de cada acción (comando) ejecutada se captura y procesa. Cada línea de salida puede cambiar el valor de una opción de configuración base, el valor de una opción de configuración en repositorios coincidentes o una variable. También puede establecer o anular una variable del plugin de acciones. El valor de esta variable está disponible para los siguientes comandos usando la sustitución ${tmp.<nombre_variable_plugin_acciones>}.

.

Las acciones deben modificar la configuración de los repositorios en el hook repos_configured. En este punto, la configuración de los repositorios está cargada pero aún no aplicada.

Desde la versión 1.4.0, la línea de salida puede escribir un mensaje en el logger, lanzar una excepción de parada y una excepción de error.

Formato de línea de salida

  • tmp.<nombre_variable_plugin_acciones>=<valor> - establece el valor de la variable del plugin de acciones <nombre_variable_plugin_acciones>
  • tmp.<nombre_variable_plugin_acciones> - elimina la variable del plugin de acciones si existe
  • conf.<nombre_opción>=<valor> - establece el valor de la opción <nombre_opción> en la configuración base
  • conf.<patrón_repoid>.<nombre_opción>=<valor> - establece el valor de la opción <nombre_opción> en los repositorios coincidentes (añadido en la versión 1.1.0)
  • var.<nombre_variable>=<valor> - establece el valor de la variable <nombre_variable>
  • stop=<mensaje> - lanza una excepción de parada con <mensaje> (añadido en la versión 1.4.0)
  • error=<mensaje> - el <mensaje> de error se registra o lanza una excepción de error con <mensaje> si raise_error=1 (añadido en la versión 1.4.0)
  • log.<nivel>=<mensaje> - escribe <mensaje> en el logger con prioridad <nivel> (añadido en la versión 1.4.0)
Niveles: CRITICAL, ERROR, WARNING, NOTICE, INFO, DEBUG, TRACE

UN EJEMPLO DE ARCHIVO DE ACCIONES:

# Imprime la cabecera con el ID del proceso
pre_base_setup::::/usr/bin/sh -c echo\ -------------------------------------\ >>/tmp/actions-trans.log
pre_base_setup::::/usr/bin/sh -c date\ >>/tmp/actions-trans.log
pre_base_setup::::/usr/bin/sh -c echo\ libdnf5\ pre_base_setup\ fue\ llamado.\ Process\ ID\ =\ '${pid}'.\ >>/tmp/actions-trans.log
pre_base_setup:::enabled=installroot-only:/usr/bin/sh -c echo\ run\ in\ alternative\ "installroot":\ installroot\ =\ '${conf.installroot}'\ >>/tmp/actions-trans.log
# Imprime el valor de la opción de configuración "defaultyes".
pre_base_setup::::/bin/sh -c echo\ 'pre_base_setup:\ conf.defaultyes=${{conf.defaultyes}}'\ >>\ {context.dnf.installroot}/actions.log
# Imprime un mensaje indicando que se llamó al callback "post_base_setup".
post_base_setup::::/usr/bin/sh -c echo\ libdnf5\ post_base_setup\ fue\ llamado.\ >>/tmp/actions-trans.log
# Imprime una lista de los repositorios configurados con su estado de habilitación.
repos_configured::::/usr/bin/sh -c echo\ Repositories:\ ${conf.*.enabled}\ >>/tmp/repos.log
# Imprime una lista de repositorios que utilizan el protocolo http en baseurl.
repos_configured::::/usr/bin/sh -c echo\ "${conf.*.baseurl=*http://*}"\ >>/tmp/baseurl_http.log
# Deshabilita todos los repositorios cuyos IDs comiencen con "rpmfusion".
repos_configured::::/usr/bin/sh -c echo\ conf.rpmfusion*.enabled=0
# Imprime información sobre el inicio de la transacción.
# Como package_filter está vacío, ejecuta los comandos una vez.
pre_transaction::::/usr/bin/sh -c echo\ Transaction\ start.\ Packages\ in\ transaction:\ >>/tmp/actions-trans.log
# Registra todos los paquetes (acción del paquete, nevra completo, id del repo) en la transacción en un archivo.
# Utiliza el comando de shell "echo" y la redirección a un archivo.
pre_transaction:*:::/usr/bin/sh -c echo\ '${pkg.action}'\ '${pkg.full_nevra}'\ '${pkg.repo_id}'\ >>/tmp/actions-trans.log
# Imprime la fecha y hora e información sobre el final de la transacción.
# Como package_filter está vacío, ejecuta los comandos una vez.
post_transaction::::/usr/bin/sh -c date\ >>/tmp/actions-trans.log
post_transaction::::/usr/bin/sh -c echo\ Transaction\ end.\ Repositories\ used\ in\ the\ transaction:\ >>/tmp/actions-trans.log
# Registra todos los repositorios de los cuales se usaron paquetes en la transacción para instalar en el sistema.
# Cada repositorio se listará solo una vez, incluso si se usaron múltiples paquetes del mismo repositorio.
# El mismo comando (después de la sustitución de variables) se ejecuta solo una vez por transacción.
post_transaction:*:in::/usr/bin/sh -c echo\ '${pkg.repo_id}'\ >>/tmp/actions-trans.log
# ==============================================================================================
# Las siguientes dos acciones emulan el plugin snapper de DNF4. Utiliza el programa de línea de comandos "snapper".
# Crea una instantánea previa antes de la transacción y almacena el número de instantánea en la variable "tmp.snapper_pre_number".
pre_transaction::::/usr/bin/sh -c echo\ "tmp.snapper_pre_number=$(snapper\ create\ -t\ pre\ -p)"
# Si la variable "tmp.snapper_pre_number" existe, crea una instantánea posterior después de la transacción y elimina la variable "tmp.snapper_pre_number".
post_transaction::::/usr/bin/sh -c [\ -n\ "${tmp.snapper_pre_number}"\ ]\ &&\ snapper\ create\ -t\ post\ --pre-number\ "${tmp.snapper_pre_number}"\ ;\ echo\ tmp.snapper_pre_number
