libcurl-multi(3) Manual de funciones de la biblioteca libcurl-multi(3)

NOMBRE

libcurl-multi - cómo usar la interfaz múltiple (multi interface)

DESCRIPCIÓN

Esta es una visión general sobre cómo usar la interfaz múltiple de libcurl en tus programas C. Hay páginas de manual específicas para cada función mencionada aquí. También está la página de manual de libcurl-tutorial(3) para un tutorial completo sobre programación con libcurl y la página de manual de libcurl-easy(3) para una visión general de la interfaz fácil (easy interface) de libcurl.

Todas las funciones de la interfaz múltiple comienzan con el prefijo curl_multi.

OBJETIVOS

La interfaz múltiple ofrece varias capacidades que la interfaz fácil no tiene. Son principalmente:

1. Habilitar una interfaz de "pull". La aplicación que usa libcurl decide cuándo y dónde pedir a libcurl que obtenga/envíe datos.

2. Habilitar múltiples transferencias simultáneas en el mismo hilo sin complicar la aplicación.

3. Permitir a la aplicación esperar por acciones en sus propios descriptores de archivo y los descriptores de archivo de curl simultáneamente.

4. Habilitar el manejo basado en eventos y escalar transferencias hasta miles de conexiones paralelas y más allá.

UN MANEJADOR MÚLTIPLE, MÚCHOS MANEJADORES FÁCILES

Para usar la interfaz múltiple, primero debes crear un 'manejador múltiple' (multi handle) con curl_multi_init(3). Este manejador se usa como entrada para todas las funciones curl_multi_* posteriores.

Con un manejador múltiple y la interfaz múltiple, puedes realizar varias transferencias simultáneas en paralelo. Cada transferencia individual se construye alrededor de un manejador fácil (easy handle). Creas todos los manejadores fáciles que necesites y configuras las opciones apropiadas para cada manejador fácil usando curl_easy_setopt(3).

Hay dos sabores de la interfaz múltiple: la orientada a select() y la basada en eventos que llamamos multi_socket. Te beneficiarás de leer la descripción de ambas versiones para comprender completamente cómo funcionan y se diferencian. Comenzamos con la versión orientada a select().

Cuando un manejador fácil está configurado y listo para la transferencia, en lugar de usar curl_easy_perform(3) como cuando se usa la interfaz fácil para transferencias, debes agregar el manejador fácil al manejador múltiple con curl_multi_add_handle(3). Puedes agregar más manejadores fáciles a un manejador múltiple en cualquier momento, incluso si otras transferencias ya están en curso.

Si cambias de opinión, el manejador fácil se elimina de la pila múltiple nuevamente usando curl_multi_remove_handle(3). Una vez eliminado del manejador múltiple, puedes volver a usar otras funciones de la interfaz fácil como curl_easy_perform(3) sobre el manejador o lo que consideres necesario. Puedes eliminar manejadores en cualquier momento durante las transferencias.

Agregar el manejador fácil al manejador múltiple no inicia la transferencia. Recuerda que una de las ideas principales de esta interfaz es que tu aplicación la impulse. Tú impulsas las transferencias invocando curl_multi_perform(3). libcurl entonces transfiere datos si hay algo disponible para transferir. Utiliza las devoluciones de llamada (callbacks) y todo lo demás que hayas configurado en los manejadores fáciles individuales. Transfiere datos en todas las transferencias actuales en la pila múltiple que están listas para transferir algo. Pueden ser todas, pueden ser ninguna. Cuando no hay nada más que hacer por ahora, regresa a la aplicación que llama.

Tu aplicación extrae información de libcurl sobre cuándo le gustaría ser invocada para transferir datos o realizar otro trabajo. La forma más conveniente es usar curl_multi_poll(3) que te ayuda a esperar hasta que la aplicación deba llamar a libcurl nuevamente. La API más antigua para lograr lo mismo es curl_multi_fdset(3) que extrae fd_sets de libcurl para usar en llamadas select() o poll() y así saber cuándo las transferencias en la pila múltiple pueden necesitar atención. Ambas APIs permiten que tu programa espere por entrada en tus propios descriptores de archivo privados al mismo tiempo. curl_multi_timeout(3) también te ayuda proporcionando un período de tiempo de espera (timeout) adecuado para tus llamadas select().

curl_multi_perform(3) almacena el número de transferencias aún en ejecución en uno de sus argumentos de entrada, y al leerlo puedes descubrir cuándo se completan todas las transferencias en los manejadores múltiples. 'Completado' no significa éxito. Una o más de las transferencias pueden haber fallado.

Para obtener información sobre transferencias completadas, para determinar el éxito o no, etc., se debe llamar a curl_multi_info_read(3). Puede devolver un mensaje sobre una transferencia actual o anterior. Llamadas repetidas a la función obtienen más mensajes hasta que la cola de mensajes esté vacía. La información que recibes allí incluye un puntero al manejador fácil que puedes usar para identificar a qué manejador fácil se refiere la información.

Cuando una transferencia individual se completa, el manejador fácil aún permanece agregado a la pila múltiple. Primero debes eliminar el manejador fácil con curl_multi_remove_handle(3) y luego limpiarlo con curl_easy_cleanup(3), o posiblemente establecer nuevas opciones para él y volver a agregarlo con curl_multi_add_handle(3) para iniciar otra transferencia.

Cuando todas las transferencias en la pila múltiple estén completadas, cierra el manejador múltiple con curl_multi_cleanup(3). Ten cuidado y ten en cuenta que **DEBES** invocar llamadas separadas a curl_easy_cleanup(3) para cada manejador fácil individual para limpiarlos adecuadamente.

Si deseas reutilizar un manejador fácil que se agregó al manejador múltiple para una transferencia, primero debes eliminarlo de la pila múltiple y luego volver a agregarlo (posiblemente después de haber alterado algunas opciones a tu elección).

MULTI_SOCKET

La función curl_multi_socket_action(3) ofrece una forma para que las aplicaciones no solo eviten ser forzadas a usar select(), sino que también ofrece una API de mucho mayor rendimiento que marca una diferencia significativa para las aplicaciones que utilizan un gran número de conexiones simultáneas.

curl_multi_socket_action(3) se utiliza entonces en lugar de curl_multi_perform(3).

Al usar esta API, agregas manejadores fáciles al manejador múltiple igual que con la interfaz múltiple normal. Luego, también configuras dos devoluciones de llamada con las opciones CURLMOPT_SOCKETFUNCTION(3) y CURLMOPT_TIMERFUNCTION(3) a curl_multi_setopt(3). Son dos funciones de devolución de llamada que libcurl llama con información sobre para qué sockets esperar, y para qué actividad, y cuál es el tiempo de espera actual (timeout), si este expira, libcurl debería ser notificado.

La API multi_socket está diseñada para informar a tu aplicación sobre qué sockets está utilizando actualmente libcurl y para qué actividades (lectura y/o escritura) en esos sockets tu aplicación debe esperar.

Tu aplicación debe asegurarse de recibir todos los sockets sobre los que se informa en la devolución de llamada CURLMOPT_SOCKETFUNCTION(3) y asegurarse de que reacciona a la actividad dada en ellos. Cuando un socket tiene la actividad dada, llamas a curl_multi_socket_action(3) especificando qué socket y acción hay.

La devolución de llamada CURLMOPT_TIMERFUNCTION(3) se llama para establecer un tiempo de espera. Cuando ese tiempo de espera expira, tu aplicación debe llamar a la función curl_multi_socket_action(3) indicando que fue debido a un tiempo de espera.

Esta API se utiliza típicamente con una funcionalidad subyacente basada en eventos (como libevent, libev, kqueue, epoll o similar) con la que la aplicación se "suscribe" a los cambios de socket. Esto permite que las aplicaciones y libcurl escalen mucho mejor hacia arriba y más allá de miles de transferencias simultáneas sin perder rendimiento.

curl_multi_socket.3.en: libcurl multi interface - Arch Linux

NAME

curl_multi_socket, curl_multi_socket_all - use libcurl with non-blocking sockets

SYNOPSIS

#include <curl/curl.h>
long curl_multi_socket_all(CURLM *multi_handle,
                           curl_socket_t *sockindex,
                           int *numsocks);
long curl_multi_socket(CURLM *multi_handle,
                       long timeout);

DESCRIPTION

The multi interface of libcurl allows you to perform multiple transfers concurrently using a single thread. This is often referred to as asynchronous or non-blocking I/O.

When you use the multi interface, you add one or more easy handles to a CURLM handle. Then you repeatedly call curl_multi_socket_action(3) to let libcurl perform its work.

Instead of blocking and waiting for network activity, curl_multi_socket_action(3) tells you which sockets it is currently interested in and requires you to monitor. You then use the standard socket monitoring functions like select(2), poll(2), epoll(7) or similar, to wait for activity on these sockets, or for a timeout to expire.

When activity occurs on one or more sockets, or when the timeout expires, you call curl_multi_socket_action(3) again, providing the set of sockets that have activity. libcurl then processes the network data, updates the state of the easy handles, and may complete transfers.

The functions curl_multi_socket and curl_multi_socket_all are wrappers around curl_multi_socket_action(3). They simplify the process of using the multi interface by providing a way to integrate it with standard socket monitoring functions.

curl_multi_socket_all is the most versatile function. It takes a pointer to an array of file descriptors (`sockindex`) and fills it with the file descriptors that libcurl is currently interested in. It also sets `numsocks` to the number of file descriptors in the array. You then use these file descriptors with your preferred socket monitoring function (e.g., select(2)). After the monitoring function returns, you pass the same `sockindex` and `numsocks` to curl_multi_socket_action(3), indicating which sockets have activity.

curl_multi_socket is a simpler function. You provide it with a timeout value, and it internally uses a suitable socket monitoring function to wait for activity on the sockets libcurl is interested in, or until the timeout expires. When it returns, you call curl_multi_socket_action(3) to process the events.

The return value of these functions is the return value of curl_multi_socket_action(3).

OBJECTIVES

The primary objective of the multi interface is to allow multiple transfers to be performed simultaneously without requiring multiple threads. This is achieved by using non-blocking socket operations and an event-driven model.

ONE MULTI HANDLE MANY EASY HANDLES

A single `CURLM` handle can manage multiple `CURL` easy handles. This allows you to initiate and track numerous transfers concurrently. You add easy handles to the multi handle using curl_multi_add_handle(3) and remove them with curl_multi_remove_handle(3).

MULTI_SOCKET

The core of the non-blocking operation lies in the socket callback function. When you call curl_multi_socket_action(3), if libcurl needs to perform socket operations, it will invoke the socket callback you previously registered with curl_multi_setopt(3) using the `CURLMOPT_SOCKETFUNCTION` option. This callback receives the socket descriptor, the `CURLM` handle, the socket event, and a user-defined pointer.

Your socket callback function should then register or deregister the provided socket descriptor with your preferred event notification mechanism (e.g., `epoll`, `kqueue`, `select`, `poll`). You should also keep track of which events (read/write) you have registered for each socket.

When your event notification mechanism indicates activity on a socket, you call curl_multi_socket_action(3) again, passing the file descriptor in the `sockfd` argument, and you get callbacks invoked that set you up and you then continue to call curl_multi_socket_action(3) accordingly when you get activity on the sockets you have been asked to wait on, or if the timeout timer expires.

You can poll curl_multi_info_read(3) to see if any transfer has completed, as it then has a message saying so. To know how many transfers are currently queued, running, pending or done, you can use the curl_multi_get_offt(3) function.

BLOCKING

A few areas in the code are still using blocking code, even when used from the multi interface. While we certainly want and intend for these to get fixed in the future, you should be aware of the following current restrictions:

 - Name resolves unless the c-ares or threaded-resolver backends are used
 - file:// transfers
 - TELNET transfers
