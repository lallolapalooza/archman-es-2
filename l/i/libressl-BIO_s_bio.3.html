DESCRIPCIÓN

BIO_s_bio() devuelve el método para un par BIO. Un par BIO es un par de BIO de origen/sumidero donde los datos escritos en cualquiera de las mitades del par se almacenan en búfer y se pueden leer desde la otra mitad. Ambas mitades generalmente deben ser manejadas por el mismo hilo de aplicación, ya que no se realiza ningún bloqueo en las estructuras de datos internas.

Dado que las cadenas BIO típicamente terminan en un BIO de origen/sumidero, es posible convertirlo en la mitad de un par BIO y que todos los datos sean procesados por la cadena bajo el control de la aplicación.

Un uso típico de los pares BIO es colocar la E/S TLS/SSL bajo el control de la aplicación. Esto se puede usar cuando la aplicación desea usar un transporte no estándar para TLS/SSL o las rutinas de socket normales no son apropiadas.

Las llamadas a BIO_read(3) leerán datos del búfer o solicitarán un reintento si no hay datos disponibles.

Las llamadas a BIO_write(3) colocarán datos en el búfer o solicitarán un reintento si el búfer está lleno.

Las llamadas estándar BIO_ctrl_pending(3) y BIO_ctrl_wpending(3) se pueden usar para determinar la cantidad de datos pendientes en el búfer de lectura o escritura.

BIO_reset(3) borra cualquier dato en el búfer de escritura.

BIO_make_bio_pair() une dos BIO separados en un par conectado.

BIO_destroy_bio_pair() destruye la asociación entre dos BIO conectados. La liberación de cualquiera de las mitades del par destruirá automáticamente la asociación.

BIO_shutdown_wr() se utiliza para cerrar un BIO b. Después de esta llamada, no se permitirán escrituras adicionales en el BIO b; devolverán un error. Las lecturas en la otra mitad del par devolverán cualquier dato pendiente o EOF cuando se hayan leído todos los datos pendientes.

BIO_set_write_buf_size() establece el tamaño del búfer de escritura del BIO b en size. Si el tamaño no está inicializado, se usa un valor predeterminado. Actualmente es de 17K, suficiente para un registro TLS de tamaño máximo. Cuando una cadena que contiene un par BIO se copia con BIO_dup_chain(3), el tamaño del búfer de escritura se copia automáticamente del objeto BIO original al nuevo.

BIO_get_write_buf_size() devuelve el tamaño del búfer de escritura.

BIO_new_bio_pair() combina las llamadas a BIO_new(3), BIO_make_bio_pair() y BIO_set_write_buf_size() para crear un par conectado de BIOs bio1 y bio2 con tamaños de búfer de escritura writebuf1 y writebuf2. Si alguno de los tamaños es cero, se utiliza el tamaño predeterminado. BIO_new_bio_pair() no verifica si bio1 o bio2 apuntan a algún otro BIO; los valores se sobrescriben y no se llama a BIO_free(3).

BIO_get_write_guarantee() y BIO_ctrl_get_write_guarantee() devuelven la longitud máxima de datos que se pueden escribir actualmente en el BIO. Las escrituras mayores que este valor devolverán un valor de BIO_write(3) menor que la cantidad solicitada o, si el búfer está lleno, solicitarán un reintento. BIO_ctrl_get_write_guarantee() es una función mientras que BIO_get_write_guarantee() es una macro.

BIO_get_read_request() y BIO_ctrl_get_read_request() devuelven la cantidad de datos solicitados, o el tamaño del búfer si es menor, si el último intento de lectura en la otra mitad del par BIO falló debido a un búfer vacío. Esto se puede usar para determinar cuántos datos se deben escribir en el BIO para que la próxima lectura tenga éxito: esto es más útil en aplicaciones TLS/SSL donde la cantidad de datos leídos es generalmente significativa en lugar de solo un tamaño de búfer. Después de una lectura exitosa, esta llamada devolverá cero. También devolverá cero una vez que se hayan escrito nuevos datos que satisfagan la solicitud de lectura, o parte de ella. Tenga en cuenta que BIO_get_read_request() nunca devuelve una cantidad mayor que la devuelta por BIO_get_write_guarantee().

BIO_ctrl_reset_read_request() también se puede usar para restablecer el valor devuelto por BIO_get_read_request() a cero.

Ambas mitades de un par BIO deben liberarse. Incluso si una mitad se libera implícitamente debido a una llamada a BIO_free_all(3) o SSL_free(3), la otra mitad todavía necesita ser liberada.

Cuando se utilizan en aplicaciones bidireccionales (como TLS/SSL), se debe tener cuidado de vaciar cualquier dato en el búfer de escritura. Esto se puede hacer llamando a BIO_pending(3) en la otra mitad del par y, si hay datos pendientes, leyéndolos y enviándolos al transporte subyacente. DESCRIPCIÓN

This is the BIO pair BIO. It is a virtual BIO that connects two other BIOs together. Data written to one BIO is read from the other. This can be used for testing or for implementing protocols where there is a need to separate the protocol processing from the underlying transport mechanism.

The BIO pair BIO is created using BIO_new_bio_pair(3). The arguments bio1 and bio2 are pointers to BIO pointers that will receive the newly created BIO pair. writebufsize1 and writebufsize2 specify the write buffer size for each of the BIOs. A size of 0 means that the default size will be used.

The BIO pair BIO acts as a simple buffer. Data written to one side is stored in a buffer until it is read from the other side. The read and write operations are therefore non-blocking. The write buffer size can be set using BIO_set_write_buf_size(3) or when creating the BIO pair.

The available commands for BIO_ctrl(3) are:

BIO_C_GET_READ_REQUEST
Returns the number of bytes that must be available in the read buffer before the SSL operations can be continued. This is useful when using the BIO pair with SSL.
BIO_C_RESET_READ_REQUEST
Resets the read request counter. This should be called after data has been read from the BIO.
BIO_C_GET_WRITE_BUF_SIZE
Returns the current write buffer size.
BIO_C_SET_WRITE_BUF_SIZE
Sets the write buffer size. The argument parg is a pointer to a size_t value specifying the new size.
BIO_C_GET_WRITE_GUARANTEE
Returns the write guarantee. This is the maximum number of bytes that can be written to the BIO without blocking. The argument parg is a pointer to a size_t value that will receive the guarantee.
BIO_C_MAKE_BIO_PAIR
Creates a BIO pair. The arguments bio1 and bio2 are pointers to BIO pointers that will receive the newly created BIO pair. This is equivalent to calling BIO_new_bio_pair(3) with default buffer sizes.
BIO_C_DESTROY_BIO_PAIR
Destroys a BIO pair. The arguments bio1 and bio2 are pointers to the BIOs that form the pair. After this call, the BIOs will be freed and set to NULL.
BIO_C_SHUTDOWN_WR
Shuts down the write side of the BIO. This is equivalent to calling BIO_ctrl_shutdown(3) with the argument 1.

The BIO pair BIO is typically used in conjunction with the SSL library to allow applications to perform SSL operations on non-networked BIOs. For example, you could use a BIO pair to simulate network traffic during testing.

When BIO_read(3) is called and there is no data in the buffer, it will return -1 and BIO_should_retry(3) will return true. This is because the data must be written to the other side of the BIO pair before it can be read. This is similar to the behavior of a non-blocking network socket.

If a request is made using BIO_write(3) and then a read is attempted using BIO_read(3), BIO_should_read(3) will be true. This can occur during a TLS/SSL handshake for example. BIO_write(3) will succeed and place data in the write buffer. BIO_read(3) will initially fail and BIO_should_read(3) will be true. If the application then waits for data to become available on the underlying transport before flushing the write buffer, it will never succeed because the request was never sent.

BIO_eof(3) is true if no data is in the peer BIO and the peer BIO has been shutdown.

VALORES DE RETORNO

BIO_new_bio_pair() returns 1 on success, with the new BIOs available in bio1 and bio2, or 0 on failure, with NULL pointers stored into the locations for bio1 and bio2. Check the error stack for more information.

When called on a BIO pair BIO object, BIO_method_type(3) returns the constant BIO_TYPE_BIO and BIO_method_name(3) returns a pointer to the static string "BIO pair".

EJEMPLOS

The BIO pair can be used to have full control over the network access of an application. The application can call select(2) on the socket as required without having to go through the SSL interface.

BIO *internal_bio, *network_bio;
...
BIO_new_bio_pair(&internal_bio, 0, &network_bio, 0);
SSL_set_bio(ssl, internal_bio, internal_bio);
SSL_operations();  /* e.g. SSL_read() and SSL_write() */
...

application |   TLS-engine
   |        |
   +----------> SSL_operations()
            |     /\    ||
            |     ||    \/
            |   BIO-pair (internal_bio)
            |   BIO-pair (network_bio)
            |     ||     /\
            |     \/     ||
   +-----------< BIO_operations()
   |        |
 socket     |

...
SSL_free(ssl);		/* implicitly frees internal_bio */
BIO_free(network_bio);
...

As the BIO pair will only buffer the data and never directly access the connection, it behaves non-blocking and will return as soon as the write buffer is full or the read buffer is drained. Then the application has to flush the write buffer and/or fill the read buffer.

Use BIO_ctrl_pending(3) to find out whether data is buffered in the BIO and must be transferred to the network. Use BIO_ctrl_get_read_request() to find out how many bytes must be written into the buffer before the SSL operations can successfully be continued.

ADVERTENCIAS

As the data is buffered, SSL operations may return with an ERROR_SSL_WANT_READ condition, but there is still data in the write buffer. An application must not rely on the error value of the SSL operation but must assure that the write buffer is always flushed first. Otherwise a deadlock may occur as the peer might be waiting for the data before being able to continue.
