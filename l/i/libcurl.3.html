libcurl(3) Manual de funciones de biblioteca libcurl(3)

NOMBRE

libcurl - transferencias de URL del lado del cliente

DESCRIPCIÓN

Esta es una breve descripción general de cómo usar libcurl en sus programas C. Existen páginas de manual específicas para cada función mencionada aquí. Consulte libcurl-easy(3), libcurl-multi(3), libcurl-share(3), libcurl-url(3), libcurl-ws(3) y libcurl-tutorial(3) para una comprensión profunda sobre cómo programar con libcurl.

Hay muchas integraciones disponibles que brindan acceso a libcurl en su idioma preferido. Busque en otra parte la documentación sobre ellas.

TRANSFERENCIAS

Para transferir archivos, usted crea un "manejador fácil" usando curl_easy_init(3) para una transferencia individual (en cualquier dirección). Luego, establece su conjunto deseado de opciones en ese manejador con curl_easy_setopt(3). Las opciones que establece con curl_easy_setopt(3) permanecen. Se utilizan para cada uso repetido de este manejador hasta que cambie la opción o las restablezca todas con curl_easy_reset(3).

Para transferir datos, usted tiene la opción de usar la interfaz "easy" o la interfaz "multi".

La interfaz easy es una interfaz síncrona con la que llama curl_easy_perform(3) y la deja realizar la transferencia. Cuando está completada, la función retorna y usted puede continuar. Más detalles se encuentran en la página del manual libcurl-easy(3).

La interfaz multi, por otro lado, es una interfaz asíncrona, que usted llama y que realiza solo una pequeña parte de la transferencia en cada invocación. Es perfecta si desea hacer cosas mientras la transferencia está en curso, o similar. La interfaz multi le permite hacer 'select()' en la acción de libcurl, e incluso descargar fácilmente múltiples archivos simultáneamente usando un solo hilo. Vea más detalles en la página del manual libcurl-multi(3).

INTERFACES DE SOPORTE

También hay una serie de funciones y familias de interfaces útiles adicionales para usar, incluidas estas:

curl_version_info()
obtiene información detallada de la versión de libcurl (y otras bibliotecas utilizadas). Consulte curl_version_info(3)
curl_getdate()
convierte una cadena de fecha a time_t. Consulte curl_getdate(3)
curl_easy_getinfo()
obtiene información sobre una transferencia realizada. Consulte curl_easy_getinfo(3)
curl_mime_addpart()
ayuda a construir un POST de formulario HTTP. Consulte curl_mime_addpart(3)
curl_slist_append()
construye una lista enlazada. Consulte curl_slist_append(3)
Compartir datos entre transferencias
Puede tener múltiples manejadores fáciles compartiendo ciertos datos, incluso si se usan en diferentes hilos. Esta magia se configura usando la interfaz de compartir, como se describe en la página del manual libcurl-share(3).
Análisis de URL
Análisis y manipulación de URL. Consulte libcurl-url(3)
Comunicación WebSocket
Consulte libcurl-ws(3)

ENLAZANDO CON LIBCURL

En máquinas tipo Unix, hay una herramienta llamada curl-config que se instala con el resto del material de curl cuando se realiza 'make install'.

curl-config se agrega para facilitar a las aplicaciones el enlace con libcurl y a los desarrolladores el aprendizaje sobre libcurl y cómo usarlo.

Ejecute 'curl-config --libs' para obtener las opciones de enlazador (adicionales) que necesita para enlazar con la versión particular de libcurl que tiene instalada. Consulte la página del manual de curl-config(1) para más detalles.

Los sistemas operativos tipo Unix que distribuyen libcurl como parte de sus distribuciones a menudo no proporcionan la herramienta curl-config, sino que simplemente instalan la biblioteca y las cabeceras en la ruta común para este propósito.

Muchos sistemas Linux y similares utilizan pkg-config para proporcionar opciones de compilación y enlace sobre bibliotecas, y libcurl también lo soporta.

NOMBRES DE SÍMBOLOS DE LIBCURL

Todas las funciones públicas de la interfaz de libcurl se prefijan con 'curl_' (con una 'c' minúscula). Puede encontrar otras funciones en el código fuente de la biblioteca, pero otros prefijos indican que las funciones son privadas y pueden cambiar sin previo aviso en la próxima versión.

Solo use funciones y funcionalidades documentadas.

PORTABILIDAD

libcurl funciona **exactamente** igual, en cualquiera de las plataformas en las que compila y construye.

HILOS

libcurl es seguro para hilos, pero hay algunas excepciones. Consulte libcurl-thread(3) para más información.

CONEXIONES PERSISTENTES

Conexiones persistentes significa que libcurl puede reutilizar la misma conexión para varias transferencias, si las condiciones son adecuadas.

libcurl siempre intenta usar conexiones persistentes. Siempre que use curl_easy_perform(3) o curl_multi_perform(3), etc., libcurl intenta usar una conexión existente para realizar la transferencia, y si no existe, abre una nueva que está sujeta a reutilización en una posible llamada posterior a curl_easy_perform(3) o curl_multi_perform(3).

Para permitir que libcurl aproveche al máximo las conexiones persistentes, debe realizar tantas transferencias de archivos como sea posible usando el mismo manejador.

Si usa la interfaz easy, y llama curl_easy_cleanup(3), todas las conexiones posiblemente abiertas mantenidas por libcurl se cierran y se olvidan.

Cuando ha creado un manejador multi y está usando la interfaz multi, el pool de conexiones se mantiene en el manejador multi para que cerrar y crear nuevos manejadores fáciles para realizar transferencias no los afecte. En su lugar, todos los manejadores fáciles añadidos pueden aprovechar el único pool compartido.

CONSTANTES GLOBALES

Hay una variedad de constantes que libcurl utiliza, principalmente a través de su uso interno de otras bibliotecas, que son demasiado complejas para que el cargador de bibliotecas las configure. Por lo tanto, un programa debe llamar a una función de biblioteca después de que el programa se cargue y esté en ejecución para finalizar la configuración del código de la biblioteca. Por ejemplo, cuando libcurl se compila con soporte SSL a través de la biblioteca GNU TLS, hay un árbol elaborado dentro de esa biblioteca que describe el protocolo SSL.

curl_global_init(3) es la función que debe llamar. Esto puede asignar recursos (por ejemplo, la memoria para el árbol GNU TLS mencionado anteriormente), por lo que la función compañera curl_global_cleanup(3) los libera.

Si libcurl se compiló con soporte para múltiples backends SSL, la función curl_global_sslset(3) se puede llamar antes de curl_global_init(3) para seleccionar el backend SSL activo.

Las funciones de constantes globales son seguras para hilos desde libcurl 7.84.0 si curl_version_info(3) tiene el indicador CURL_VERSION_ Asynchronous resolver. Antes de eso, solo la primera llamada a cualquiera de ellas era segura para hilos.

GLOBAL CONSTANTS

The functions that are described in this manual page have global state and are not thread safe. See libcurl-thread(3) for thread safety guidelines.

If the global constant functions are not thread safe, then you must not call them when any other thread in the program is running. It is not good enough that no other thread is using libcurl at the time, because these functions internally call similar functions of other libraries, and those functions are similarly thread-unsafe. You cannot generally know what these libraries are, or whether other threads are using them.

If the global constant functions are not thread safe, then the basic rule for constructing a program that uses libcurl is this: Call curl_global_init(3), with a CURL_GLOBAL_ALL argument, immediately after the program starts, while it is still only one thread and before it uses libcurl at all. Call curl_global_cleanup(3) immediately before the program exits, when the program is again only one thread and after its last use of libcurl.

It is not actually required that the functions be called at the beginning and end of the program -- that is just usually the easiest way to do it.

You can call both of these multiple times, as long as all calls meet these requirements and the number of calls to each is the same.

The global constant situation merits special consideration when the code you are writing to use libcurl is not the main program, but rather a modular piece of a program, e.g. another library. As a module, your code does not know about other parts of the program -- it does not know whether they use libcurl or not. Its code does not necessarily run at the start and end of the whole program.

A module like this must have global constant functions of its own, just like curl_global_init(3) and curl_global_cleanup(3). The module thus has control at the beginning and end of the program and has a place to call the libcurl functions. If multiple modules in the program use libcurl, they all separately call the libcurl functions, and that is OK because only the first curl_global_init(3) and the last curl_global_cleanup(3) in a program change anything. (libcurl uses a reference count in static memory).

In a C++ module, it is common to deal with the global constant situation by defining a special class that represents the global constant environment of the module. A program always has exactly one object of the class, in static storage. That way, the program automatically calls the constructor of the object as the program starts up and the destructor as it terminates. As the author of this libcurl-using module, you can make the constructor call curl_global_init(3) and the destructor call curl_global_cleanup(3) and satisfy libcurl's requirements without your user having to think about it. (Caveat: If you are initializing libcurl from a Windows DLL you should not initialize it from DllMain or a static initializer because Windows holds the loader lock during that time and it could cause a deadlock.)

curl_global_init(3) has an argument that tells what particular parts of the global constant environment to set up. In order to successfully use any value except CURL_GLOBAL_ALL (which says to set up the whole thing), you must have specific knowledge of internal workings of libcurl and all other parts of the program of which it is part.

A special part of the global constant environment is the identity of the memory allocator. curl_global_init(3) selects the system default memory allocator, but you can use curl_global_init_mem(3) to supply one of your own. However, there is no way to use curl_global_init_mem(3) in a modular program -- all modules in the program that might use libcurl would have to agree on one allocator.

There is a failsafe in libcurl that makes it usable in simple situations without you having to worry about the global constant environment at all: curl_easy_init(3) sets up the environment itself if it has not been done yet. The resources it acquires to do so get released by the operating system automatically when the program exits.

This failsafe feature exists mainly for backward compatibility because there was a time when the global functions did not exist. Because it is sufficient only in the simplest of programs, it is not recommended for any program to rely on it.
