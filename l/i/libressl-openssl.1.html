OPENSSL(1) Manual de comandos generales OPENSSL(1)

NOMBRE

openssl — Herramienta de línea de comandos de OpenSSL

SINOPSIS

openssl comando [opt_comando ...] [arg_comando ...]

openssl list-standard-commands | list-message-digest-commands | list-cipher-commands | list-cipher-algorithms | list-message-digest-algorithms | list-public-key-algorithms

openssl no-comando

DESCRIPCIÓN

OpenSSL es un kit de herramientas criptográficas que implementa el protocolo de red Transport Layer Security (TLS), así como estándares criptográficos relacionados.

El programa openssl es una herramienta de línea de comandos para usar las diversas funciones criptográficas de la biblioteca de criptografía de openssl desde la shell.

Los pseudocomandos list-standard-commands, list-message-digest-commands, y list-cipher-commands imprimen una lista (una entrada por línea) de los nombres de todos los comandos estándar, comandos de resumen de mensajes o comandos de cifrado, respectivamente, que están disponibles en la utilidad openssl actual.

Los pseudocomandos list-cipher-algorithms y list-message-digest-algorithms listan todos los nombres de cifrados y resúmenes de mensajes, una entrada por línea. Los alias se listan como:

de => a

El pseudocomando list-public-key-algorithms lista todos los algoritmos de clave pública compatibles.

El pseudocomando no-comando comprueba si un comando del nombre especificado está disponible. Si comando no existe, devuelve 0 e imprime no-comando; de lo contrario, devuelve 1 e imprime comando. En ambos casos, la salida va a stdout y no se imprime nada en stderr. Los argumentos adicionales de línea de comandos siempre se ignoran. Dado que para cada cifrado existe un comando del mismo nombre, esto proporciona una forma fácil para que los scripts de shell comprueben la disponibilidad de cifrados en el programa openssl.

Nota: no-comando no puede detectar pseudocomandos como quit, list-...-commands, o no-comando en sí mismo.

ASN1PARSE

openssl asn1parse
[-i] [-dlimit número] [-dump] [-genconf archivo] [-genstr cadena] [-in archivo] [-inform der | pem | txt] [-length número] [-noout] [-offset número] [-oid archivo] [-out archivo] [-strparse offset]

El comando asn1parse es una utilidad de diagnóstico que puede analizar estructuras ASN.1. También se puede usar para extraer datos de datos con formato ASN.1.

Las opciones son las siguientes:

-dlimit número
Volca los primeros número bytes de datos desconocidos en formato hexadecimal.
-dump
Volca datos desconocidos en formato hexadecimal.
-genconf archivo, -genstr cadena
Genera datos codificados basados en la cadena cadena, el archivo archivo, o ambos, utilizando el formato descrito en ASN1_generate_nconf(3). Si solo está presente archivo, la cadena se obtiene de la sección predeterminada usando el nombre “asn1”. Los datos codificados se pasan a través del analizador ASN.1 y se imprimen como si provinieran de un archivo; por lo tanto, los contenidos se pueden examinar y escribir en un archivo usando la opción -out.
-i
Indenta la salida de acuerdo con la "profundidad" de las estructuras.
-in archivo
El archivo de entrada del que leer, o la entrada estándar si no se especifica.
-inform der | pem | txt
El formato de entrada.
-length número
Número de bytes a analizar; el valor predeterminado es hasta el final del archivo.
-noout
No muestre la versión analizada del archivo de entrada.
-offset número
Desplazamiento inicial para comenzar el análisis; el valor predeterminado es el inicio del archivo.
-oid archivo
Un archivo que contiene identificadores de objetos (OIDs) adicionales. Si un OID (identificador de objeto) no forma parte de la tabla interna de openssl, se representará en forma numérica (por ejemplo, 1.2.3.4).

Cada línea consta de tres columnas: la primera columna es el OID en formato numérico y debe ir seguida de espacios en blanco. La segunda columna es el "nombre corto", que es una sola palabra seguida de espacios en blanco. La última columna es el resto de la línea y es el "nombre largo". asn1parse muestra el nombre largo.

-out archivo
El archivo de salida codificado en DER; el valor predeterminado es ninguna salida codificada (útil cuando se combina con -strparse).
-strparse offset
Analiza los octetos de contenido del objeto ASN.1 comenzando en el desplazamiento offset. Esta opción se puede usar varias veces para "profundizar" en una estructura anidada.

openssl ca
[-batch] [-cert archivo] [-config archivo] [-create_serial] [-crl_CA_compromise tiempo] [-crl_compromise tiempo] [-crl_hold instrucción] [-crl_reason razón] [-crldays días] [-crlexts sección] [-crlhours horas] [-crlsec segundos] [-days arg] [-enddate 

Este sitio no está asociado de ninguna forma con Arch Linux ni afiliado a este proyecto. El contenido es únicamente una traducción de las páginas del manual de Arch publicadas en man.archlinux.org.

-cert file
El archivo del certificado de CA.
-config file
Especificar un archivo de configuración alternativo.
-create_serial
Si la lectura del número de serie del archivo de texto especificado en la configuración falla, crea un nuevo número de serie aleatorio para ser utilizado como el próximo número de serie.
-days arg
El número de días para certificar el certificado.
-enddate date
Establecer la fecha de caducidad. El formato de la fecha es [YY]YYMMDDHHMMSSZ, con los cuatro dígitos del año requeridos para fechas a partir de 2050.
-extensions section
La sección del archivo de configuración que contiene las extensiones de certificado que se añadirán cuando se emita un certificado (por defecto es x509_extensions a menos que se utilice la opción -extfile). Si no hay ninguna sección de extensión presente, se crea un certificado V1. Si la sección de extensión está presente (incluso si está vacía), entonces se crea un certificado V3. Consulte la página del manual de x509v3.cnf(5) para obtener detalles sobre el formato de la sección de extensión.
-extfile file
Un archivo de configuración adicional file para leer las extensiones de certificado (usando la sección por defecto a menos que la opción -extensions también se use).
-in file
Un archivo de entrada file que contiene una única solicitud de certificado a ser firmada por la CA.
-infiles
Si está presente, esta debe ser la última opción; todos los argumentos subsiguientes se asumen que son los nombres de los archivos que contienen solicitudes de certificado.
-key password
La contraseña password utilizada para cifrar la clave privada. Dado que en algunos sistemas los argumentos de la línea de comandos son visibles, esta opción debe usarse con precaución.
-keyfile file
La clave privada para firmar las solicitudes.
-keyform pem | der
Formato del archivo de clave privada. El valor por defecto es pem.
-md alg
El algoritmo de resumen de mensajes a utilizar. Los valores posibles incluyen md5 y sha1. Esta opción también se aplica a las CRL.
-multivalue-rdn
Esta opción hace que el argumento -subj se interprete con soporte completo para RDNs multivalor, por ejemplo "/DC=org/DC=OpenSSL/DC=users/UID=123456+CN=John Doe". Si -multivalue-rdn no se usa, el valor de UID se establece en "123456+CN=John Doe".
-name section
Especifica la sección section del archivo de configuración a utilizar (anula default_ca en la sección ca).
-noemailDN
El DN de un certificado puede contener el campo EMAIL si está presente en el DN de la solicitud, sin embargo, es una buena política tener solo el correo electrónico establecido en la extensión altName del certificado. Cuando se establece esta opción, el campo EMAIL se elimina del sujeto del certificado y se establece solo en las extensiones, si están presentes. La palabra clave email_in_dn se puede usar en el archivo de configuración para habilitar este comportamiento.
-notext
No mostrar la forma de texto de un certificado en el archivo de salida.
-out file
El archivo de salida donde se enviarán los certificados. El valor por defecto es la salida estándar. Los detalles del certificado también se imprimirán en este archivo en formato PEM.
-outdir directory
El directorio directory donde se enviarán los certificados. El certificado se escribirá en un archivo que consiste en el número de serie en hexadecimal con ".pem" añadido.
-passin arg
La fuente de la contraseña de la clave.
-policy arg
Definir la "política" de la CA a utilizar. La sección de política en el archivo de configuración consiste en un conjunto de variables que corresponden a los campos del DN del certificado. Los valores pueden ser uno de "match" (el valor debe coincidir con el mismo campo en el certificado de la CA), "supplied" (el valor debe estar presente), o "optional" (el valor puede estar presente). Cualquier campo no mencionado en la sección de política se elimina silenciosamente, a menos que se establezca la opción -preserveDN, pero esto puede considerarse más una peculiaridad que un comportamiento intencionado.
-preserveDN
Normalmente, el orden del DN de un certificado es el mismo que el orden de los campos en la sección de política relevante. Cuando se establece esta opción, el orden es el mismo que el de la solicitud. Esto es en gran medida para la compatibilidad con el antiguo control de inscripción de IE que solo aceptaba certificados si sus DN coincidían con el orden de la solicitud. Esto no es necesario para Xenroll.
-revoke file
Revocar un certificado contenido en el archivo file.
-selfsign
Indica que los certificados emitidos deben ser firmados con la clave con la que se firmaron las solicitudes de certificado, proporcionada con -keyfile. Las solicitudes de certificado firmadas con una clave diferente son ignoradas. Si se proporcionan -gencrl o -ss_cert, -selfsign se ignora.

Una consecuencia de usar -selfsign es que el certificado autofirmado aparece entre las entradas de la base de datos de certificados (ver la opción de configuración database) y utiliza el mismo contador de números de serie que todos los demás certificados firmados con el certificado autofirmado.

-sigopt nm:v
Pasa opciones al algoritmo de firma durante las operaciones de firma o certificación. Los nombres y valores de estas opciones son específicos del algoritmo.
-ss_cert file
Un único certificado autofirmado a ser firmado por la CA.
-startdate date
Establecer la fecha de inicio. El formato de la fecha es [YY]YYMMDDHHMMSSZ, con los cuatro dígitos del año requeridos para fechas a partir de 2050.
-status serial
Actualiza el estado del certificado con el número de serie dado en formato hexadecimal a "revoked" o "good".
-subj arg
Reemplaza el nombre del sujeto dado en la solicitud. El arg debe tener el formato /type0=value0/type1=value1/type2=...; los caracteres pueden ser escapados con ‘\’ (barra invertida), no se omiten espacios.
-updatedb
Actualiza la base de datos de certificados.
-utf8
Interpretar los valores de los campos leídos de una terminal u obtenidos de un archivo de configuración como cadenas UTF-8. Por defecto, se interpretan como ASCII.
-verbose
Modo detallado.

CERTHASH

openssl certhash
[-nv] dir ...

El comando certhash calcula un valor hash de un archivo ".pem" en la lista de directorios especificada y crea enlaces simbólicos para cada archivo, donde el nombre del enlace es el valor hash. Consulte la página del manual SSL_CTX_load_verify_locations(3) para ver cómo se utilizan los enlaces hash.

Los enlaces creados tienen el formato "HHHHHHHH.D", donde cada 'H' es un carácter hexadecimal y 'D' es un solo dígito decimal. Los hashes para las CRL se ven similares, excepto que la letra 'r' aparece después del punto, así: "HHHHHHHH.rD". Al procesar un directorio, certhash primero eliminará todos los enlaces que tengan un nombre en esa sintaxis y una referencia inválida.

Múltiples objetos pueden tener el mismo hash; se indicarán incrementando el valor 'D'. Los duplicados se encuentran comparando la huella digital completa SHA256. Se mostrará una advertencia si se encuentra un duplicado.

También se mostrará una advertencia si hay archivos que no se pueden analizar como certificados o CRL.

Las opciones son las siguientes:

-n
Realizar una simulación (dry-run) y no realizar ningún cambio.
-v
Imprimir detalles adicionales sobre el procesamiento.
dir ...
Especificar los directorios a procesar.

openssl cms

El comando cms maneja correo S/MIME v3.1. Puede cifrar, descifrar, firmar y verificar, comprimir y descomprimir mensajes S/MIME.

El mensaje MIME debe enviarse sin líneas en blanco entre las cabeceras y la salida. Algunos programas de correo agregarán automáticamente una línea en blanco. Canalizar el correo directamente a sendmail es una forma de lograr el formato correcto.

El mensaje proporcionado para ser firmado o cifrado debe incluir las cabeceras MIME necesarias o muchos clientes S/MIME no lo mostrarán correctamente (si es que lo hacen). Puede usar la opción -text para agregar automáticamente cabeceras de texto plano.

Un mensaje "firmado y cifrado" es uno en el que un mensaje firmado se cifra posteriormente. Esto se puede producir cifrando un mensaje ya firmado.

Hay varias opciones de operación que establecen el tipo de operación a realizar. El significado de las otras opciones varía según el tipo de operación.

-encrypt
Cifrar correo para los certificados de destinatario proporcionados. El archivo de entrada es el mensaje a cifrar. El archivo de salida es el correo cifrado en formato MIME. El tipo CMS real es EnvelopedData. Tenga en cuenta que no se realiza ninguna verificación de revocación para el certificado del destinatario, por lo que si esa clave ha sido comprometida, otros pueden descifrar el texto.
-decrypt
Descifrar correo utilizando el certificado y la clave privada proporcionados. Espera un mensaje de correo cifrado en formato MIME en el archivo de entrada. El correo descifrado se escribe en el archivo de salida.
-sign
Firmar correo utilizando el certificado y la clave privada proporcionados.
-sign
Firmar un mensaje. El archivo de entrada es el mensaje a firmar. El mensaje firmado en formato MIME se escribe en el archivo de salida.
-verify
Verificar correo firmado. Espera un mensaje de correo firmado en la entrada y emite los datos firmados. Se admiten tanto la firma de texto claro como la opaca.
-cmsout
Tomar un mensaje de entrada y escribir una estructura CMS codificada en PEM.
-resign
Volver a firmar un mensaje. Tomar un mensaje existente y uno o más firmantes nuevos. Esta operación utiliza un resumen de mensaje existente al agregar un nuevo firmante. Esto significa que los atributos deben estar presentes en al menos un firmante existente que utilice el mismo resumen de mensaje o esta operación fallará.
-data_create
Crear un tipo de Datos CMS.
-data_out
Extraer contenido del tipo de Datos CMS de entrada.
-digest_create
Crear un tipo DigestedData CMS.
-digest_verify
Verificar un tipo DigestedData CMS y extraer el contenido.
-compress
Crear un tipo CompressedData CMS. Debe compilarse con soporte zlib para que esta opción funcione.
-uncompress
Descomprimir un tipo CompressedData CMS y extraer el contenido. Debe compilarse con soporte zlib para que esta opción funcione.
-EncryptedData_encrypt
Cifrar un contenido utilizando la clave simétrica y el algoritmo proporcionados mediante un tipo EncryptedData CMS.
-EncryptedData_decrypt
Descifrar un tipo EncryptedData CMS utilizando la clave simétrica proporcionada.
-sign_receipt
Generar y emitir un recibo firmado para el mensaje proporcionado. El mensaje de entrada debe contener una solicitud de recibo firmado. La funcionalidad es, por lo demás, similar a la operación -sign.
-verify_receipt file
Verificar un recibo firmado en un archivo. El mensaje de entrada debe contener la solicitud de recibo original. La funcionalidad es, por lo demás, similar a la operación -verify.

Las opciones restantes son las siguientes:

-CAfile file
Un archivo que contiene certificados CA de confianza, utilizado con -verify y -verify_receipt.

Un directorio que contiene certificados CA de confianza, utilizado con -verify y -verify_receipt. Este directorio debe ser un directorio de certificados estándar: es decir, un hash de cada nombre de sujeto (utilizando x509 -hash) debe estar vinculado a cada certificado.

Permite especificar listas de revocación de certificados adicionales para la verificación. Las CRL deben estar en formato PEM.

-certsout file
Un archivo en el que se escribirán los certificados contenidos en el mensaje.

-debug_decrypt

Establecer el tipo de contenido encapsulado, utilizado con -sign. Si no se proporciona, se utiliza el tipo Data. El argumento type puede ser cualquier nombre OID válido en formato de texto o numérico.

Establece el tamaño del búfer para E/S.
-d
Descifra los datos de entrada.
-debug

[-CA archivo] [-CApath directorio] [-cert archivo] [-dgst alg] [-header nombre valor] [-host nombrehost:puerto] [-ignore_err] [-index archivoíndice] [-issuer archivo] [-ndays días] [-nmin minutos] [-no_cert_checks] [-no_cert_verify] [-no_certs] [-no_chain] [-no_explicit] [-no_intern] [-no_nonce] [-no_signature_verify] [-nonce] [-noverify] [-nrequest número] [-out archivo] [-path ruta] [-port numeropuerto] [-req_text] [-reqin archivo] [-reqout archivo] [-resp_key_id] [-resp_no_certs] [-resp_text] [-respin archivo] [-respout archivo] [-rkey archivo] [-rother archivo] [-rsigner archivo] [-serial num] [-sign_other archivo] [-signer archivo] [-signkey archivo] [-status_age edad] [-text] [-timeout segundos] [-trust_other] [-url urlresponder] [-VAfile archivo] [-validity_period nsec] [-verify_other archivo]

El Protocolo de Estado de Certificado en Línea (OCSP) permite a las aplicaciones determinar el estado (de revocación) de un certificado identificado (RFC 2560).

El comando ocsp realiza muchas tareas OCSP comunes. Se puede utilizar para imprimir solicitudes y respuestas, crear solicitudes y enviar consultas a un respondedor OCSP, y comportarse como un mini servidor OCSP.

Las opciones son las siguientes:

-CAfile archivo, -CApath directorio
Un archivo o directorio que contiene certificados CA de confianza, utilizado para verificar la firma en la respuesta OCSP.
-cert archivo
Añade el certificado archivo a la solicitud. El certificado del emisor se toma de la opción -issuer anterior, o se produce un error si no se especifica ningún certificado de emisor.
-dgst alg
Utiliza el algoritmo de hash alg para la identificación del certificado en la solicitud OCSP. Por defecto se usa SHA1.
-host nombre_host:puerto, -path ruta
Envía la solicitud OCSP a nombre_host en el puerto. -path especifica el nombre de ruta HTTP a utilizar, o / por defecto.
-header nombre valor
Añade el encabezado nombre con el valor especificado a la solicitud OCSP que se envía al respondedor. Esto puede repetirse.
-issuer archivo
El certificado del emisor actual, en formato PEM. Se puede usar varias veces y debe aparecer antes de cualquier opción -cert.
-no_cert_checks
No realizar ninguna comprobación adicional sobre el certificado del firmante de la respuesta OCSP. Es decir, no realizar ninguna comprobación para ver si el certificado del firmante está autorizado a proporcionar la información de estado necesaria: como resultado, esta opción solo debe usarse con fines de prueba.
-no_cert_verify
No verificar en absoluto el certificado del firmante de la respuesta OCSP. Dado que esta opción permite que la respuesta OCSP sea firmada por cualquier certificado, solo debe usarse con fines de prueba.
-no_certs
No incluir ningún certificado en la solicitud firmada.
-no_chain
No utilizar certificados en la respuesta como certificados CA adicionales no confiables.
-no_explicit
No comprobar la confianza explícita para la firma OCSP en el certificado de la CA raíz.
-no_intern
Ignorar los certificados contenidos en la respuesta OCSP al buscar el certificado del firmante. El certificado del firmante debe especificarse con las opciones -verify_other o -VAfile.
-no_signature_verify
No comprobar la firma de la respuesta OCSP. Dado que esta opción tolera firmas inválidas en las respuestas OCSP, normalmente solo se usará con fines de prueba.
-nonce, -no_nonce
Añadir una extensión nonce OCSP a una solicitud, o deshabilitar la adición de un nonce OCSP. Normalmente, si se introduce una solicitud OCSP usando la opción -respin no se añade ningún nonce: usar la opción -nonce forzará la adición de un nonce. Si se está creando una solicitud OCSP (usando las opciones -cert y -serial), se añade automáticamente un nonce; especificar -no_nonce anula esto.
-noverify
No intentar verificar la firma de la respuesta OCSP o los valores nonce. Esto normalmente solo se usará para depuración, ya que deshabilita toda la verificación del certificado del respondedor.
-out archivo
Especifica el archivo de salida al que escribir, o la salida estándar si no se especifica.
-req_text, -resp_text, -text
Imprime la forma textual de la solicitud OCSP, respuesta, o ambas, respectivamente.
-reqin archivo, -respin archivo
Lee un archivo de solicitud o respuesta OCSP desde archivo. Estas opciones se ignoran si la creación de una solicitud o respuesta OCSP está implícita por otras opciones (por ejemplo, con las opciones -serial, -cert y -host).
-reqout archivo, -respout archivo
Escribe la solicitud o respuesta de certificado codificada en DER en archivo.
-serial num
Igual que la opción -cert, excepto que el certificado con el número de serie num se añade a la solicitud. El número de serie se interpreta como un entero decimal a menos que vaya precedido de ‘0x’. También se pueden especificar enteros negativos precediendo el valor con un signo menos.
-sign_other archivo
Certificados adicionales para incluir en la solicitud firmada.
-signer archivo, -signkey archivo
Firma la solicitud OCSP utilizando el certificado especificado en la opción -signer y la clave privada especificada por la opción -signkey. Si la opción -signkey no está presente, la clave privada se lee del mismo archivo que el certificado. Si no se especifica ninguna de las opciones, la solicitud OCSP no se firma.
-timeout segundos
Tiempo de espera de conexión al respondedor OCSP en segundos.
-trust_other
Los certificados especificados por la opción -verify_other deben ser explícitamente confiables y no se realizarán comprobaciones adicionales sobre ellos. Esto es útil cuando la cadena completa del certificado del respondedor no está disponible o confiar en una CA raíz no es apropiado.
-url url_del_respondedor
Especifica la URL del respondedor. Se pueden especificar URLs HTTP y HTTPS (SSL/TLS).
-VAfile archivo
Un archivo que contiene certificados de respondedores explícitamente confiables. Equivalente a las opciones -verify_other y -trust_other.
-validity_period nsec, -status_age antigüedad
El rango de tiempos, en segundos, que se tolerarán en una respuesta OCSP. Cada respuesta de estado de certificado incluye un tiempo notBefore y un tiempo notAfter opcional. El tiempo actual debe caer entre estos dos valores, pero el intervalo entre los dos tiempos puede ser de solo unos pocos segundos. En la práctica, los relojes del respondedor OCSP y de los clientes pueden no estar sincronizados con precisión, por lo que una comprobación de este tipo puede fallar. Para evitar esto, la opción -validity_period se puede usar para especificar un rango de error aceptable en segundos, siendo el valor por defecto de 5 minutos.

Si se omite el tiempo notAfter de una respuesta, significa que la nueva información de estado está disponible inmediatamente. En este caso, se comprueba la antigüedad del campo notBefore para ver si no es mayor que antigüedad segundos. Por defecto, esta comprobación adicional no se realiza.

-verify_other archivo
Un archivo que contiene certificados adicionales para buscar al intentar localizar el certificado de firma de la respuesta OCSP. Algunos respondedores omiten el certificado del firmante real de la respuesta, por lo que esto se puede usar para suministrar el certificado necesario.

Las opciones para el servidor OCSP son las siguientes:

-CA archivo
Certificado de la CA correspondiente a la información de revocación en archivo_índice.
-ignore_err
Ignorar la respuesta inválida.
-index archivo_índice
archivo_índice es un archivo de índice de texto en formato ca que contiene información de revocación de certificados.

Si se especifica esta opción, ocsp está en modo respondedor, de lo contrario está en modo cliente. Las solicitudes que procesa el respondedor pueden especificarse en la línea de comandos (usando las opciones -issuer y -serial), proporcionarse en un archivo (usando la opción -respin), o a través de clientes OCSP externos (si se especifica puerto o url).

Si esta opción está presente, entonces las opciones -CA y -rsigner también deben estar presentes.

-nmin minutos, -ndays días
Número de minutos o días en los que hay información de revocación fresca disponible: se usa en el campo nextUpdate. Si no se presenta ninguna de las opciones, el campo nextUpdate se omite, lo que significa que la información de revocación fresca está disponible inmediatamente.
-nrequest número
Salir después de recibir número solicitudes (el valor por defecto es ilimitado).
-port portnum
Puerto para escuchar las solicitudes OCSP. También se puede especificar utilizando la opción -url.
-resp_key_id
Identifica el certificado del firmante utilizando el ID de clave; por defecto se utiliza el nombre del sujeto.
-resp_no_certs
No incluir ningún certificado en la respuesta OCSP.
-rkey archivo
La clave privada para firmar las respuestas OCSP; si no está presente, se utiliza el archivo especificado en la opción -rsigner.
-rother archivo
Certificados adicionales a incluir en la respuesta OCSP.
-rsigner archivo
El certificado para firmar las respuestas OCSP.

Inicialmente, se localiza el certificado del respondedor OCSP y se comprueba la firma en la solicitud OCSP utilizando la clave pública del certificado del respondedor. Luego se realiza una verificación normal de certificados en el certificado del respondedor OCSP, construyendo una cadena de certificados en el proceso. Las ubicaciones de los certificados de confianza utilizados para construir la cadena se pueden especificar mediante las opciones -CAfile y -CApath o se buscarán en el directorio de certificados estándar de openssl.

Si la verificación inicial falla, el proceso de verificación OCSP se detiene con un error. De lo contrario, se compara el certificado de la CA emisora en la solicitud con el certificado del respondedor OCSP: si hay una coincidencia, la verificación OCSP tiene éxito.

De lo contrario, se comprueba la CA del certificado del respondedor OCSP con el certificado de la CA emisora en la solicitud. Si hay una coincidencia y el uso de clave extendida OCSPSigning está presente en el certificado del respondedor OCSP, la verificación OCSP tiene éxito.

De lo contrario, se comprueba la CA raíz de la CA del respondedor OCSP para ver si es de confianza para la firma OCSP. Si lo es, la verificación OCSP tiene éxito.

Si ninguna de estas comprobaciones tiene éxito, la verificación OCSP falla. Lo que esto efectivamente significa es que si el certificado del respondedor OCSP está autorizado directamente por la CA sobre la cual está emitiendo información de revocación (y está correctamente configurado), entonces la verificación tendrá éxito.

Si el respondedor OCSP es un respondedor global, que puede proporcionar detalles sobre múltiples CA y tiene su propia cadena de certificados separada, entonces su CA raíz puede ser de confianza para la firma OCSP. Alternativamente, el certificado del respondedor en sí puede ser explícitamente confiable con la opción -VAfile.

PASSWD

openssl passwd
[-1 | -apr1 | -crypt] [-in archivo] [-noverify] [-quiet] [-reverse] [-salt cadena] [-stdin] [-table] [contraseña]

El comando passwd calcula el hash de una contraseña.

Las opciones son las siguientes:

-1
Utiliza el algoritmo de contraseña BSD basado en MD5 llamado "1".
-apr1
Utiliza el algoritmo "apr1" (variante de Apache del algoritmo BSD).
-crypt
Utiliza el algoritmo "crypt" (el predeterminado).
-in archivo
Lee contraseñas del archivo archivo.
-noverify
No verifica al leer una contraseña desde la terminal.
-quiet
No emite advertencias cuando las contraseñas proporcionadas en la línea de comandos se truncan.
-reverse
Cambia las columnas de la tabla. Esto solo tiene sentido junto con la opción -table.
-salt cadena
Utiliza la sal especificada por cadena. Al leer una contraseña desde la terminal, esto implica -noverify.
-stdin
Lee contraseñas de la entrada estándar.
-table
En la lista de salida, antepone la contraseña en texto plano y un carácter TAB a cada hash de contraseña.

El comando pkcs7 procesa archivos PKCS#7 en formato DER o PEM. Las rutinas PKCS#7 solo entienden PKCS#7 v 1.5 según se especifica en RFC 2315.

Las opciones son las siguientes:

-in archivo
El archivo de entrada del que leer, o la entrada estándar si no se especifica.
-inform der | pem
El formato de entrada.
-noout
No mostrar la versión codificada de la estructura PKCS#7 (o certificados si se establece -print_certs).
-out archivo
El archivo de salida al que escribir, o la salida estándar si no se especifica.
-outform der | pem

-print

PKCS8

openssl pkcs8
[-in archivo] [-inform der | pem] [-nocrypt] [-noiter] [-out archivo] [-outform der | pem] [-passin arg] [-passout arg] [-topk8] [-v1 alg] [-v2 alg]

El comando pkcs8 procesa claves privadas (cifradas y sin cifrar) en formato PKCS#8 con una variedad de algoritmos PKCS#5 (v1.5 y v2.0) y PKCS#12.

Las opciones son las siguientes:

-in archivo
El archivo de entrada del que leer, o la entrada estándar si no se especifica. Si la clave está cifrada, se solicitará una contraseña.
-inform der | pem
El formato de entrada.
-nocrypt
Genera una estructura PrivateKeyInfo sin cifrar. Esta opción no cifra las claves privadas en absoluto y solo debe utilizarse cuando sea absolutamente necesario.
-noiter
Utiliza un recuento de iteraciones de 1. Consulte la sección PKCS12 a continuación para obtener una explicación detallada de esta opción.
-out archivo
El archivo de salida al que escribir, o la salida estándar si no se especifica. Si se establecen opciones de cifrado, se solicitará una contraseña.
-outform der | pem
El formato de salida.
-passin arg
La fuente de la contraseña de la clave.
-passout arg
La fuente de la contraseña del archivo de salida.
-topk8
Lee una clave privada de formato tradicional y escribe una clave de formato PKCS#8.
-v1 alg
Especifica un algoritmo PKCS#5 v1.5 o PKCS#12 a
use.
PBE-MD5-DES
DES de 56 bits.
PBE-SHA1-RC2-64 | PBE-MD5-RC2-64 | PBE-SHA1-DES
RC2 de 64 bits o DES de 56 bits.
PBE-SHA1-RC4-128 | PBE-SHA1-RC4-40 | PBE-SHA1-3DES
 
PBE-SHA1-2DES | PBE-SHA1-RC2-128 | PBE-SHA1-RC2-40
Algoritmo de cifrado basado en contraseña PKCS#12, que permite algoritmos de cifrado robustos como triple DES o RC2 de 128 bits.
-v2 alg
Utiliza algoritmos PKCS#5 v2.0. Estos son cifradores de bloque utilizados en modo CBC. El valor predeterminado es AES-256-CBC. Con la excepción de AES, las opciones disponibles en RFC 8018 se consideran obsoletas. Se pueden habilitar con des, des3 y rc2 (rc5 ya no es compatible).

PKCS12

openssl pkcs12
[-aes128 | -aes192 | -aes256 | -camellia128 | -camellia192 | -camellia256 | -des | -des3 | -idea] [-cacerts] [-CAfile archivo] [-caname nombre] [-CApath directorio] [-certfile archivo] [-certpbe alg] [-chain] [-clcerts] [-descert] [-export] [-in archivo] [-info] [-inkey archivo] [-keyex] [-keypbe alg] [-keysig] [-macalg alg] [-maciter] [-name nombre] [-nocerts] [-nodes] [-noiter] [-nokeys] [-nomac] [-nomaciter] [-nomacver] [-noout] [-out archivo] [-passin arg] [-passout arg] [-password arg] [-twopass]

El comando pkcs12 permite crear y analizar archivos PKCS#12 (a veces denominados archivos PFX). Por defecto, se analiza un archivo PKCS#12; un archivo PKCS#12 se puede crear utilizando la opción -export.

Las opciones para analizar un archivo PKCS12 son las siguientes:

-aes128 | -aes192 | -aes256 | -camellia128 | -camellia192 | -camellia256 | -des | -des3 | -idea
Cifra las claves privadas utilizando los cifradores AES, CAMELLIA, DES, triple DES o IDEA, respectivamente. El valor predeterminado es triple DES.
-cacerts
Solo muestra certificados de CA (no certificados de cliente).
-clcerts
Solo muestra certificados de cliente (no certificados de CA).
-in archivo
El archivo de entrada del que leer, o la entrada estándar si no se especifica.
-info
Muestra información adicional sobre la estructura del archivo PKCS#12, los algoritmos utilizados y los recuentos de iteración.
-nocerts
No mostrar certificados.
-nodes
No cifrar claves privadas.
-nokeys
No mostrar claves privadas.
-nomacver
No intentes verificar la MAC de integridad antes de leer el archivo.
-noout
No mostrar las claves y certificados en la versión del archivo de salida del archivo PKCS#12.
-out archivo
El archivo de salida al que escribir, o la salida estándar si no se especifica.
-passin arg
La fuente de la contraseña de la clave.
-passout arg
La fuente de la contraseña del archivo de salida.
-twopass
Solicita contraseñas separadas para integridad y cifrado: la mayoría del software siempre asume que son las mismas, por lo que esta opción hará que dichos archivos PKCS#12 sean ilegibles.

Las opciones para la creación de archivos PKCS12 son las siguientes:

-CAfile archivo
Almacenamiento de CA como archivo.
-CApath directorio
Almacenamiento de CA como directorio. El directorio debe ser un directorio de certificados estándar: es decir, un hash de cada nombre de sujeto (usando x509 -hash) debe estar vinculado a cada certificado.
-caname nombre
Especifica el "nombre amigable" para otros certificados. Puede usarse varias veces para especificar nombres para todos los certificados en el orden en que aparecen.
-certfile archivo
Un archivo del que leer certificados adicionales.
-certpbe alg, -keypbe alg
Especifica el algoritmo utilizado para cifrar la clave privada y los certificados a seleccionar. Se puede utilizar cualquier nombre de algoritmo PBE de PKCS#5 v1.5 o PKCS#12. Si se especifica un nombre de cifrador (como el que muestra el comando list-cipher-algorithms), se utiliza con PKCS#5 v2.0. Por razones de interoperabilidad, es aconsejable utilizar solo algoritmos PKCS#12.
-chain
Incluye toda la cadena de certificados del certificado de usuario. La tienda de CA estándar se utiliza para esta búsqueda. Si la búsqueda falla, se considera un error fatal.
-descert
Cifra el certificado utilizando triple DES; esto puede hacer que el archivo PKCS#12 no sea legible por algunos programas de "grado de exportación". Por defecto, la clave privada se cifra utilizando triple DES y el certificado utilizando RC2 de 40 bits.
-export
Crea un archivo PKCS#12 (en lugar de analizar uno).
-in archivo
El archivo de entrada del que leer, o la entrada estándar si no se especifica. El orden no importa, pero debe haber una clave privada y su certificado correspondiente. Si hay certificados adicionales, también se incluirán en el archivo PKCS#12.
-inkey archivo
Archivo del que leer una clave privada. Si no está presente, una clave privada debe estar presente en el archivo de entrada.
-keyex | -keysig
Especifica si la clave privada se utilizará para el intercambio de claves o solo para la firma. Normalmente, el software de "grado de exportación" solo permitirá claves RSA de 512 bits para fines de cifrado, pero de longitud arbitraria para la firma. La opción -keysig marca la clave solo para la firma. Las claves solo de firma se pueden utilizar para la firma S/MIME, authenticode (firma de control ActiveX) y autenticación de cliente SSL.
-macalg alg
Especifica el algoritmo de resumen MAC. El valor predeterminado es SHA1.
-maciter
Incluido solo por compatibilidad: solía ser necesario utilizar recuentos de iteraciones MAC, pero ahora se utilizan por defecto.
-name nombre
Especifica el "nombre amigable" para el certificado y la clave privada. Este nombre suele ser mostrado en listas por el software que importa el archivo.
-nomac
No intentes proporcionar la integridad MAC.
-nomaciter, -noiter
Afecta a los recuentos de iteración en los algoritmos MAC y de clave.

Para disuadir ataques mediante el uso de grandes diccionarios de contraseñas comunes, el algoritmo que deriva las claves de las contraseñas puede tener un

recuento de iteraciones aplicado a él: esto causa que una determinada parte del algoritmo se repita y lo ralentiza. El MAC se utiliza para comprobar la integridad del archivo, pero dado que normalmente tendrá la misma contraseña que las claves y certificados, también podría ser atacado. Por defecto, tanto el MAC como los recuentos de iteraciones de cifrado se establecen en 2048; utilizando estas opciones, los recuentos de iteraciones del MAC y del cifrado se pueden establecer en 1. Dado que esto reduce la seguridad del archivo, no deberías usar estas opciones a menos que realmente tengas que hacerlo. La mayoría del software admite recuentos de iteraciones tanto de MAC como de clave.

-out archivo
El archivo de salida al que escribir, o la salida estándar si no se especifica.
-passin arg
La fuente de la contraseña de la clave.
-passout arg
La fuente de la contraseña del archivo de salida.
-password arg
Con -export, -password es equivalente a -passout. De lo contrario, -password es equivalente a -passin.

PKEYUTL

openssl pkeyutl
[-asn1parse] [-certin] [-decrypt] [-derive] [-encrypt] [-hexdump] [-in archivo] [-inkey archivo] [-keyform der | pem] [-out archivo] [-passin arg] [-peerform der | pem] [-peerkey archivo] [-pkeyopt opt:valor] [-pubin] [-rev] [-sigfile archivo] [-sign] [-verify] [-verifyrecover]

-asn1parse
Analiza ASN.1 los datos de salida. Esto es útil cuando se combina con la opción -verifyrecover cuando se firma una estructura ASN.1.

La entrada es un certificado que contiene una clave pública.

Descifra los datos de entrada utilizando una clave privada.
-derive
Deriva un secreto compartido utilizando la clave del par.
-encrypt
Cifra los datos de entrada utilizando una clave pública.
-hexdump

El comando ts es una aplicación cliente y servidor básica de Autoridad de Sellado de Tiempo (TSA) según se especifica en RFC 3161 (Protocolo de Sellado de Tiempo, TSP). Una TSA puede ser parte de una implementación de PKI y su función es proporcionar una prueba a largo plazo de la existencia de datos específicos. Aquí hay una breve descripción del protocolo:

  1. El cliente TSA calcula un valor hash unidireccional para un archivo de datos y envía el hash a la TSA.
  2. La TSA adjunta la fecha y hora actuales al valor hash recibido, las firma y envía el token de sellado de tiempo de vuelta al cliente. Al crear este token, la TSA certifica la existencia del archivo de datos original en el momento de la generación de la respuesta.
  3. El cliente TSA recibe el token de sellado de tiempo y verifica la firma sobre él. También comprueba si el token contiene el mismo valor hash que había enviado a la TSA.

Hay una unidad de datos de protocolo codificada en DER definida para transportar una solicitud de sellado de tiempo a la TSA y otra para enviar la respuesta de sellado de tiempo de vuelta al cliente. El comando ts tiene tres funciones principales: crear una solicitud de sellado de tiempo basada en un archivo de datos; crear una respuesta de sellado de tiempo basada en una solicitud; y verificar si una respuesta corresponde a una solicitud particular o a un archivo de datos.

Todavía no hay soporte para enviar las solicitudes/respuestas automáticamente a través de HTTP o TCP, como se sugiere en RFC 3161. Los usuarios deben enviar las solicitudes por FTP o correo electrónico.

El programa verify utiliza las mismas funciones que la verificación interna de SSL y S/MIME, con una diferencia crucial: siempre que sea posible, se intenta continuar después de un error, mientras que normalmente la operación de verificación se detendría ante el primer error. Esto permite determinar todos los problemas con una cadena de certificados.

La operación de verificación consta de varios pasos separados. En primer lugar, se construye una cadena de certificados comenzando desde el certificado proporcionado y terminando en la CA raíz. Es un error si no se puede construir toda la cadena. La cadena se construye buscando el certificado del emisor del certificado actual. Si se encuentra un certificado que es su propio emisor, se asume que es la CA raíz.

Todos los certificados cuyo nombre de asunto coincide con el nombre del emisor del certificado actual están sujetos a pruebas adicionales. Los componentes relevantes del identificador de clave de autoridad del certificado actual (si están presentes) deben coincidir con el identificador de clave de sujeto (si está presente) y el emisor y número de serie del emisor candidato; además, la extensión keyUsage del emisor candidato (si está presente) debe permitir la firma de certificados.

La búsqueda primero busca en la lista de certificados no confiables y, si no se encuentra ninguna coincidencia, las búsquedas restantes son de los certificados confiables. La CA raíz siempre se busca en la lista de certificados confiables: si el certificado a verificar es un certificado raíz, entonces se debe encontrar una coincidencia exacta en la lista confiable.

La segunda operación es verificar las extensiones de cada certificado no confiable en busca de consistencia con el propósito proporcionado. Si la opción -purpose no está incluida, no se realizan verificaciones. El certificado proporcionado o "hoja" debe tener extensiones compatibles con el propósito proporcionado y todos los demás certificados también deben ser certificados de CA válidos. Las extensiones precisas requeridas se describen con más detalle en la sección X509 a continuación.

La tercera operación es verificar la configuración de confianza en la CA raíz. La CA raíz debe ser confiable para el propósito proporcionado. Un certificado sin configuraciones de confianza se considera válido para todos los propósitos.

La operación final es verificar la validez de la cadena de certificados. El período de validez se verifica con la hora actual del sistema y las fechas notBefore y notAfter en el certificado. Las firmas del certificado también se verifican en este punto.

Si todas las operaciones se completan con éxito, el certificado se considera válido. Si alguna operación falla, el certificado no es válido. Cuando una operación de verificación falla, los mensajes de salida pueden ser algo crípticos. La forma general del mensaje de error es:

server.pem: /C=AU/ST=Queensland/O=CryptSoft Pty Ltd/CN=Test CA (1024-bit)
error 24 at 1 depth lookup:invalid CA certificate

La primera línea contiene el nombre del certificado que se está verificando, seguido del nombre del asunto del certificado. La segunda línea contiene el número de error tal como lo definen las constantes X509_V_ERR_* en <openssl/x509_vfy.h>, el mensaje de error asociado documentado en X509_STORE_CTX_get_error(3) y la profundidad. La profundidad es el número del certificado que se está verificando cuando se detectó un problema, comenzando con cero para el propio certificado que se está verificando, luego 1 para la CA que firmó el certificado y así sucesivamente.

The basicConstraints extension CA flag is used to determine whether the certificate can be used as a CA. If the CA flag is true, it is a CA; if the CA flag is false, it is not a CA. All CAs should have the CA flag set to true.

If the basicConstraints extension is absent, then the certificate is considered to be a possible CA; other extensions are checked according to the intended use of the certificate. A warning is given in this case because the certificate should really not be regarded as a CA. However it is allowed to be a CA to work around some broken software.

If the certificate is a V1 certificate (and thus has no extensions) and it is self-signed, it is also assumed to be a CA but a warning is again given. This is to work around the problem of Verisign roots which are V1 self-signed certificates.

If the keyUsage extension is present, then additional restraints are made on the uses of the certificate. A CA certificate must have the keyCertSign bit set if the keyUsage extension is present.

The extended key usage extension places additional restrictions on the certificate uses. If this extension is present, whether critical or not, the key can only be used for the purposes specified.

A complete description of each test is given below. The comments about basicConstraints and keyUsage and V1 certificates above apply to all CA certificates.

SSL Client
The extended key usage extension must be absent or include the web client authentication OID. keyUsage must be absent or it must have the digitalSignature bit set. The Netscape certificate type must be absent or it must have the SSL client bit set.
SSL Client CA
The extended key usage extension must be absent or include the web client authentication OID. The Netscape certificate type must be absent or it must have the SSL CA bit set: this is used as a workaround if the basicConstraints extension is absent.
SSL Server
The extended key usage extension must be absent or include the web server authentication and/or one of the SGC OIDs. keyUsage must be absent or it must have the digitalSignature set, the keyEncipherment set, or both bits set. The Netscape certificate type must be absent or have the SSL server bit set.
SSL Server CA
The extended key usage extension must be absent or include the web server authentication and/or one of the SGC OIDs. The Netscape certificate type must be absent or the SSL CA bit must be set: this is used as a workaround if the basicConstraints extension is absent.
Netscape SSL Server
For Netscape SSL clients to connect to an SSL server; it must have the keyEncipherment bit set if the keyUsage extension is present. This isn't always valid because some cipher suites use the key for digital signing. Otherwise it is the same as a normal SSL server.
Common S/MIME Client Tests
The extended key usage extension must be absent or include the email protection OID. The Netscape certificate type must be absent or should have the S/MIME bit set. If the S/MIME bit is not set in Netscape certificate type, then the SSL client bit is tolerated as an alternative but a warning is shown: this is because some Verisign certificates don't set the S/MIME bit.
S/MIME Signing
In addition to the common S/MIME client tests, the digitalSignature bit must be set if the keyUsage extension is present.
S/MIME Encryption
In addition to the common S/MIME tests, the keyEncipherment bit must be set if the keyUsage extension is present.
S/MIME CA
The extended key usage extension must be absent or include the email protection OID. The Netscape certificate type must be absent or must have the S/MIME CA bit set: this is used as a workaround if the basicConstraints extension is absent.
CRL Signing
The keyUsage extension must be absent or it must have the CRL signing bit set.
CRL Signing CA
The normal CA tests apply, except the basicConstraints extension must be present.
-setalias arg
Set the alias of the certificate, allowing the certificate to be referred to usando un apodo, como "Certificado de Steve".
-trustout
Genera un certificado de confianza (por defecto si se modifican las configuraciones de confianza). Se puede introducir un certificado normal o de confianza, pero por defecto se genera un certificado normal y se desechan las configuraciones de confianza.

La utilidad x509 se puede usar para firmar certificados y solicitudes: por lo tanto, puede actuar como una mini CA. Las siguientes son opciones de firma de x509:

-CA archivo
El certificado de CA a utilizar para firmar. Cuando esta opción está presente, x509 se comporta como una mini CA. El archivo de entrada es firmado por la CA utilizando esta opción; es decir, su nombre de emisor se establece en el nombre del sujeto de la CA y se firma digitalmente utilizando la clave privada de la CA.

Esta opción normalmente se combina con la opción -req. Sin la opción -req, la entrada es un certificado que debe ser autofirmado.

-CAcreateserial
Crea el archivo de número de serie de la CA si no existe en lugar de generar un error. El archivo contendrá el número de serie ‘02’ y el certificado que se está firmando tendrá ‘1’ como su número de serie.
-CAform der | pem
El formato del archivo de certificado de CA. Por defecto es pem.
-CAkey archivo
Establece la clave privada de la CA para firmar un certificado. De lo contrario, se asume que la clave privada de la CA está presente en el archivo del certificado de CA.
-CAkeyform der | pem
El formato de la clave privada de la CA. Por defecto es pem.
-CAserial archivo
Utiliza el número de serie en archivo para firmar un certificado. El archivo debe consistir en una línea que contenga un número par de dígitos hexadecimales con el número de serie a utilizar. Después de cada uso, el número de serie se incrementa y se vuelve a escribir en el archivo.

El nombre de archivo por defecto consiste en el nombre base del archivo de certificado de CA con .srl añadido. Por ejemplo, si el archivo del certificado de CA se llama mycacert.pem, espera encontrar un archivo de número de serie llamado mycacert.srl.

-checkend arg
Verifica si el certificado expira en los próximos arg segundos. Si es así, sale con valor de retorno 1; de lo contrario, sale con valor de retorno 0.
-clrext
Elimina cualquier extensión de un certificado. Esta opción se utiliza cuando un certificado se crea a partir de otro certificado (por ejemplo, con las opciones -signkey o -CA). Normalmente, todas las extensiones se conservan.
-days arg
El número de días que el certificado será válido. Por defecto son 30 días.
-extensions sección
La sección de la que añadir las extensiones del certificado. Si esta opción no se especifica, las extensiones deben estar contenidas en la sección sin nombre (por defecto) o la sección por defecto debe contener una variable llamada "extensions" que contenga la sección a utilizar.
-extfile archivo
Archivo que contiene las extensiones del certificado a utilizar. Si no se especifica, no se añaden extensiones al certificado.
-force_pubkey clave
Establece la clave pública del certificado a la clave pública contenida en clave.
-keyform der | pem
El formato del archivo de clave utilizado en las opciones -force_pubkey y -signkey.
-new
Genera un nuevo certificado utilizando el sujeto dado por -set_subject y firmado por -signkey. Si no se proporciona una clave pública con -force_pubkey, el certificado resultante es autofirmado. Esta opción no se puede usar con -in o -req.
-req
Espera una solicitud de certificado en la entrada en lugar de un certificado. Esta opción no se puede usar con -new.
-set_issuer nombre
El nombre del emisor a utilizar. nombre debe tener el formato /tipo0=valor0/tipo1=valor1/tipo2=...; los caracteres pueden ser escapados con ‘\’ (barra invertida); no se omiten espacios.
-set_serial n
El número de serie a utilizar. Esta opción se puede usar con las opciones -signkey o -CA. Si se usa en conjunto con la opción -CA, no se utiliza el archivo de número de serie (como se especifica en las opciones -CAserial o -CAcreateserial).

El número de serie puede ser decimal o hexadecimal (si va precedido por ‘0x’). También se pueden especificar números de serie negativos, pero no se recomienda su uso.

-set_subject nombre
El nombre del sujeto a utilizar. nombre debe tener el formato /tipo0=valor0/tipo1=valor1/tipo2=...; los caracteres pueden ser escapados con ‘\’ (barra invertida); no se omiten espacios.
-signkey archivo
Autofirma archivo usando la clave privada proporcionada.

Si el archivo de entrada es un certificado, establece el nombre del emisor al nombre del sujeto (es decir, lo hace autofirmado), cambia la clave pública al valor proporcionado y cambia las fechas de inicio y fin. La fecha de inicio se establece en la hora actual y la fecha de fin se establece en un valor determinado por la opción -days. Cualquier extensión de certificado se conserva a menos que se proporcione la opción -clrext.

Si la entrada es una solicitud de certificado, se crea un certificado autofirmado utilizando la clave privada proporcionada con el nombre del sujeto en la solicitud.

-utf8
Interpreta los valores de campo leídos de un terminal o obtenidos de un archivo de configuración como cadenas UTF-8. Por defecto, se interpretan como ASCII.
-x509toreq
Convierte un certificado en una solicitud de certificado. La opción -signkey se utiliza para pasar la clave privada requerida.

NOTACIÓN COMÚN

Varios comandos comparten una sintaxis común, como se detalla a continuación.

Los argumentos de contraseña, especificados típicamente usando -passin y -passout para contraseñas de entrada y salida, permiten obtener contraseñas de una variedad de fuentes. Ambas opciones toman un único argumento, descrito a continuación. Si no se proporciona un argumento de contraseña y se requiere una contraseña, se le pedirá al usuario que introduzca una: esto normalmente se leerá de la terminal actual sin que se muestre.

pass:contraseña
La contraseña real es contraseña. Dado que la contraseña es visible para las utilidades, esta forma solo debe usarse donde la seguridad no sea importante.
env:var
Obtiene la contraseña de la variable de entorno var. Dado que el entorno de otros procesos es visible, esta opción debe usarse con precaución.
file:ruta
La primera línea de ruta es la contraseña. Si se suministra el mismo argumento ruta a -passin y -passout, entonces la primera línea se usará para la contraseña de entrada y la siguiente línea para la contraseña de salida. ruta no necesita referirse a un archivo regular: podría, por ejemplo, referirse a un dispositivo o a una tubería con nombre.
fd:número
Lee la contraseña del descriptor de archivo número. Esto se puede usar para enviar los datos a través de una tubería, por ejemplo.
stdin
Lee la contraseña de la entrada estándar.

Los formatos de entrada/salida, especificados típicamente usando -inform y -outform, indican el formato que se está leyendo o escribiendo. El argumento no distingue mayúsculas de minúsculas.

der
Distinguished Encoding Rules (DER) es un formato binario.
net
Formato heredado inseguro.
pem
