NOMBRE

libnbd - biblioteca cliente de dispositivo de bloque de red (NBD) en espacio de usuario

SINOPSIS

#include <libnbd.h>
struct nbd_handle *nbd;
char buf[512];
if ((nbd = nbd_create ()) == NULL ||
    nbd_connect_tcp (nbd, "servidor.ejemplo.com", "nbd") == -1 ||
    nbd_pread (nbd, buf, sizeof buf, 0, 0) == -1)
  fprintf (stderr, "%s\n", nbd_get_error ());
  nbd_close (nbd);
  exit (EXIT_FAILURE);
}
nbd_close (nbd);
 cc prog.c -o prog -lnbd
o:
 cc prog.c -o prog `pkg-config libnbd --cflags --libs`

DESCRIPCIÓN

Network Block Device (NBD) es un protocolo de red para acceder a dispositivos de bloque a través de la red. Los dispositivos de bloque son discos duros y cosas que se comportan como discos duros, como imágenes de disco y máquinas virtuales.

Libnbd es una biblioteca cliente para el protocolo NBD que puede acceder a la mayoría de las características de NBD, siendo a la vez sencilla de usar y potente.

Esta página del manual ofrece una visión general de libnbd, usando C como ejemplo, pero la biblioteca está disponible desde otros lenguajes de programación.

MANEJADORES

Para usar la API, primero debes abrir un manejador llamando a nbd_create(3) (o su equivalente en otros idiomas):

struct nbd_handle *nbd;
nbd = nbd_create ();

Esto crea y devuelve un manejador, que está asociado a una conexión a un servidor NBD, inicialmente no conectado.

Cada manejador es una máquina de estados compleja que puede estar en estados como creado, conectado a un servidor remoto, negociando, inactivo y listo para emitir comandos, o ocupado enviando o recibiendo comandos.

Los manejadores tienen un nombre utilizado en mensajes de depuración. El nombre se genera normalmente ("nbd1", "nbd2", etc.), pero puedes establecer un nombre amigable con nbd_set_handle_name(3). También hay un campo privado en el manejador para uso de la aplicación, ver nbd_set_private_data(3).

Cuando hayas terminado con el manejador, debes llamar a nbd_close(3), que cierra el socket subyacente (si es necesario) y libera todos los recursos asociados.

API SÍNCRONA VS ASÍNCRONA

Hay dos niveles de API disponibles. Una API síncrona simple de alto nivel te permite dar al manejador instrucciones de alto nivel como "conectar al servidor", "leer un bloque", "escribir un bloque", etc. Cada una de estas funciones se ejecutará hasta completarse, bloqueando el hilo actual antes de devolver. También hay disponible una API asíncrona no bloqueante de nivel inferior más compleja, donde puedes integrarte con poll(2) u otro bucle principal.

Puedes mezclar libremente las dos APIs en el mismo manejador. También puedes llamar a APIs en un solo manejador desde múltiples hilos. Las llamadas API individuales al manejador son atómicas: o bien toman un bloqueo en el manejador mientras se ejecutan o tienen cuidado de acceder a los campos del manejador atómicamente.

Libnbd **no** crea sus propios hilos.

USO DE LA API SÍNCRONA (“DE ALTO NIVEL”)

Esta es la forma más sencilla de usar la API, con el posible inconveniente de que cada función de libnbd se bloquea hasta que se completa.

Crea un manejador y conéctate al servidor:

struct nbd_handle *nbd;
nbd = nbd_create ();
if (!nbd) {
  fprintf (stderr, "%s\n", nbd_get_error ());
  nbd_close (nbd);
  exit (EXIT_FAILURE);
}
if (nbd_connect_tcp (nbd, "servidor.ejemplo.com", "nbd") == -1) {
  fprintf (stderr, "%s\n", nbd_get_error ());
  nbd_close (nbd);
  exit (EXIT_FAILURE);
}

Lee el primer sector (512 bytes) de la exportación NBD:

char buf[512];
if (nbd_pread (nbd, buf, sizeof buf, 0, 0) == -1) {
  fprintf (stderr, "%s\n", nbd_get_error ());
  nbd_close (nbd);
  exit (EXIT_FAILURE);
}

Cierra el manejador:

nbd_close (nbd);

Puedes llamar a la API de alto nivel desde múltiples hilos, pero cada llamada a la API de libnbd toma un bloqueo en el manejador, por lo que los comandos no se ejecutarán en paralelo.

USO DE LA API ASÍNCRONA (“DE BAJO NIVEL”)

La API de bajo nivel es útil si quieres usar libnbd en código no bloqueante; o si quieres emitir comandos en paralelo desde múltiples hilos; o si necesitas más control, especialmente sobre tener múltiples comandos en curso en una sola conexión.

Para usar la API de bajo nivel, necesitarás integrarte con poll(2) u otro "bucle principal" como el bucle de eventos principal de GLib.

Emisión de comandos asíncronos

Usa las variantes "nbd_aio_*" para emitir comandos de forma asíncrona (sin esperar a que el comando se complete antes de devolver). Por ejemplo, la variante asíncrona de nbd_pread(3) es:

int64_t cookie;
cookie = nbd_aio_pread (nbd, buf, sizeof buf,
                        NBD_NULL_COMPLETION, 0);
if (cookie == -1) {
  fprintf (stderr, "%s\n", nbd_get_error ());
  nbd_close (nbd);
  exit (EXIT_FAILURE);
}

Hay varias cosas a tener en cuenta aquí:

  • Esto solo inicia el comando. El comando todavía está (normalmente) en curso cuando la llamada devuelve éxito, donde debes depender de llamadas API posteriores para conocer el resultado final del comando y activar cualquier callback pendiente. Sin embargo, también debes poder manejar el caso en que la carga del sistema permita que la máquina de estados avance lo suficiente como para invocar callbacks antes de que la API asíncrona devuelva.
  • Se ha asignado un buffer ("buf") para recopilar el resultado de la lectura, pero no se garantiza que se rellene con datos hasta que el comando se haya completado (ver ejemplos a continuación). El buffer no debe liberarse hasta que el comando haya terminado de ejecutarse.
  • Puedes emitir múltiples comandos en el mismo manejador al mismo tiempo.
  • Se devuelve una cookie que identifica este comando en llamadas posteriores. La cookie es única (por manejador de libnbd) y >= 1.
  • Puedes registrar una función que se llamará cuando el comando se complete, ver "Callbacks de finalización" a continuación. En este caso, hemos especificado un callback de finalización nulo. Si se especifica un callback de finalización, solo se llamará si el comando asíncrono se envió correctamente (si la API asíncrona en sí misma devuelve un error, no hay nada más que completar).

Socket y dirección

Cada manejador de libnbd tiene un socket asociado (una vez que ha comenzado a conectarse). Puedes leer el descriptor de archivo del socket usando:

int fd = nbd_aio_get_fd (nbd);

El socket no es bloqueante. Entre llamadas a libnbd está en la condición de "bloquearía". Puedes saber si libnbd espera leer o escribir desde el socket a continuación llamando a:

int dir = nbd_aio_get_direction (nbd);

que devuelve uno de "LIBNBD_AIO_DIRECTION_READ", "LIBNBD_AIO_DIRECTION_WRITE" o "LIBNBD_AIO_DIRECTION_NONE".

Procesamiento del bucle principal

Para procesar eventos de red y completar comandos asíncronos, debes llamar periódicamente a:

int r = nbd_aio_progress (nbd);
if (r == -1) {
  fprintf (stderr, "%s\n", nbd_get_error ());
  nbd_close (nbd);
  exit (EXIT_FAILURE);
}

Si nbd_aio_progress devuelve 0, significa que no se hizo nada. Si devuelve 1, significa que se procesó un evento. Si devuelve 2, significa que se completó un comando.

En un bucle principal normal, usarías poll(2) para esperar hasta que el socket asociado con el manejador esté listo para leer o escribir, y luego llamarías a nbd_aio_progress.

Ejemplo con poll(2):

struct pollfd pfd;
pfd.fd = nbd_aio_get_fd (nbd);
pfd.events = nbd_aio_get_event_mask (nbd);
pfd.revents = 0;

while (1) {
  int ret = poll (&pfd, 1, -1);
  if (ret == -1) {
    perror ("poll");
    break;
  }

  if (pfd.revents & (POLLIN | POLLPRI | POLLOUT | POLLERR | POLLHUP)) {
    ret = nbd_aio_progress (nbd);
    if (ret == -1) {
      fprintf (stderr, "%s\n", nbd_get_error ());
      break;
    }
    if (ret == 0) {
      // No progress was made, need to re-evaluate poll events
      pfd.events = nbd_aio_get_event_mask (nbd);
    } else if (ret & NBD_AIO_PROGRESS_DISCONNECTED) {
      // The NBD connection was disconnected
      break;
    }
  }
}

El código de ejemplo anterior espera indefinidamente hasta que ocurra un evento en el socket NBD. Cuando ocurre un evento, se llama a nbd_aio_progress para procesarlo. Si nbd_aio_progress devuelve 0, significa que no se hizo ningún progreso (lo que puede suceder si el evento no era relevante para el estado actual de libnbd), por lo que los eventos de sondeo se actualizan y el bucle continúa.

Si nbd_aio_progress devuelve 1, significa que se hizo algún progreso (un comando de red se envió o recibió). Si devuelve 2, significa que se completó un comando (se llamó a su callback, si lo hubo).

El valor de retorno NBD_AIO_PROGRESS_DISCONNECTED indica que la conexión NBD se ha cerrado.

Callbacks de finalización

Puedes registrar un callback para que se llame cuando un comando asíncrono se complete. El tipo de callback es:

typedef void (*nbd_completion_callback) (void *user_data, int err, int size);

El parámetro user_data es un puntero que pasaste cuando llamaste a la función asíncrona. El parámetro err es 0 si el comando tuvo éxito, o un código de error (como errno) si falló. El parámetro size es el número de bytes leídos o escritos (si el comando tuvo éxito). Si el comando falló, size no está definido.

Para registrar un callback, pásalo como argumento a la función asíncrona, junto con los datos de usuario opcionales:

int64_t cookie;
char buf[1024];
// Pasa la dirección de la función de callback y los datos de usuario
cookie = nbd_aio_pread (nbd, buf, sizeof buf, my_callback, my_data);
// ...
void my_callback (void *user_data, int err, int size) {
  if (err == 0) {
    // Éxito, 'size' bytes leídos en 'buf' (accesible a través de user_data)
    char *data = user_data;
    // Hacer algo con los datos...
  } else {
    // Error
    fprintf (stderr, "Error reading from NBD: %s\n", strerror (err));
  }
}

Si llamas a una función asíncrona sin especificar un callback (es decir, pasando NBD_NULL_COMPLETION), el comando aún se ejecutará, pero no se te notificará explícitamente de su finalización mediante un callback. Aún puedes comprobar el estado de los comandos en curso utilizando nbd_aio_list_completions.

Manejo de errores

Para obtener información detallada sobre el último error ocurrido en un manejador, usa:

const char *nbd_get_error (struct nbd_handle *nbd);

Esto devuelve una cadena que describe el error. La cadena se valida hasta la próxima llamada a una función de libnbd en ese manejador.

En el caso de la API asíncrona, los errores también se pasan a los callbacks de finalización.

CONFIGURACIÓN DEL MANEJADOR

Hay varias opciones que puedes configurar en un manejador de libnbd para modificar su comportamiento. Puedes establecer opciones antes de llamar a nbd_connect_* y algunas también después.

Las opciones disponibles incluyen:

NBD_OPT_PORT
Establece el número de puerto TCP (por defecto 2100 o 10809). nbd_set_opt_port.
NBD_OPT_WRITE_CACHE
Habilita o deshabilita la caché de escritura (por defecto: deshabilitado). nbd_set_opt_write_cache.
NBD_OPT_CACHE_SIZE
Establece el tamaño de la caché de escritura en bytes (por defecto: 0).
NBD_OPT_SEND_ERRORS
Habilita o deshabilita el envío de errores NBD al servidor (por defecto: habilitado).
NBD_OPT_MAX_SEND
Establece el tamaño máximo de un paquete NBD que se enviará al servidor (por defecto: 0, lo que significa sin límite).
NBD_OPT_MAX_RECEIVE
Establece el tamaño máximo de un paquete NBD que se recibirá del servidor (por defecto: 0, lo que significa sin límite).
NBD_OPT_TIMEOUT
Establece el tiempo de espera para las operaciones de red en milisegundos (por defecto: 0, lo que significa sin tiempo de espera).
NBD_OPT_HOST
Establece el nombre de host o dirección IP del servidor NBD. Necesario si no se usa nbd_connect_tcp o nbd_connect_unix.
NBD_OPT_ABORT_TIMEOUT
Establece el tiempo de espera para la abortación de comandos en milisegundos (por defecto: 0, sin tiempo de espera).
NBD_OPT_NO_ZERO_MSG
Deshabilita el envío del mensaje "tamaño cero" para las escrituras (por defecto: deshabilitado). Útil para servidores NBD que no manejan correctamente escrituras de tamaño cero.
NBD_OPT_TLS_ENABLED
Habilita o deshabilita TLS (por defecto: deshabilitado).
NBD_OPT_TLS_CERTIFICATE
Establece la ruta al archivo de certificado TLS (formato PEM).
NBD_OPT_TLS_PRIVATE_KEY
Establece la ruta al archivo de clave privada TLS (formato PEM).
NBD_OPT_TLS_CA_CERTIFICATE
Establece la ruta al archivo del certificado CA TLS (formato PEM) para la verificación del certificado del servidor.
NBD_OPT_TLS_dh_PARAMS
Establece la ruta al archivo de parámetros DH TLS (formato PEM).
NBD_OPT_TLS_PROTOCOLS
Establece los protocolos TLS permitidos (p. ej., "TLSv1.2,TLSv1.3").
NBD_OPT_TLS_VERIFY_PEER
Habilita o deshabilita la verificación del par TLS (por defecto: habilitado).
NBD_OPT_TLS_VERIFY_DEPTH
Establece la profundidad máxima de la cadena de verificación del certificado TLS (por defecto: 9).
NBD_OPT_TLS_SESSION_CACHE
Habilita o deshabilita la caché de sesiones TLS (por defecto: habilitado).

Puedes establecer estas opciones usando la función nbd_set_opt_* correspondiente, por ejemplo:

nbd_set_opt_write_cache (nbd, 1); // Habilitar caché de escritura
nbd_set_opt_timeout (nbd, 5000); // Establecer tiempo de espera de 5 segundos

También puedes obtener el valor de una opción usando nbd_get_opt_*.

EXPORTACIONES Y DISPOSITIVOS

Un servidor NBD puede exportar múltiples "dispositivos" o "exportaciones". Cada exportación representa un dispositivo de bloque separado (por ejemplo, una imagen de disco, una partición, etc.).

Después de conectarte al servidor, puedes obtener información sobre las exportaciones disponibles:

struct nbd_export *exports;
int num_exports;
int r = nbd_get_exports (nbd, &exports, &num_exports);
if (r == 0) {
  for (int i = 0; i < num_exports; i++) {
    printf ("Exportación %d: nombre='%s', tamaño=%lu\n",
            i, exports[i].name, exports[i].size);
  }
  nbd_free_exports (exports);
}

Por defecto, libnbd selecciona la primera exportación disponible (índice 0) si no se especifica ninguna. Puedes seleccionar una exportación específica usando:

nbd_connect_tcp (nbd, "servidor.ejemplo.com", "exportacion1");

donde "exportacion1" es el nombre de la exportación.

Si el servidor NBD no proporciona nombres de exportación, o si deseas seleccionar por índice, puedes usar la opción NBD_OPT_EXPORT_ID antes de conectarte:

nbd_set_opt_export_id (nbd, 1); // Seleccionar la exportación con índice 1
nbd_connect_tcp (nbd, "servidor.ejemplo.com", NULL); // El nombre de exportación es NULL

SEGMENTACIÓN

Para optimizar el rendimiento, libnbd puede dividir las operaciones de lectura/escritura grandes en varias solicitudes más pequeñas, o fusionar múltiples operaciones pequeñas en una sola solicitud más grande. Esto se denomina "segmentación".

Puedes controlar el comportamiento de segmentación usando las siguientes opciones:

NBD_OPT_MAX_SEND
Establece el tamaño máximo de un paquete NBD enviado al servidor. Las escrituras más grandes que esto se dividirán.
NBD_OPT_MAX_RECEIVE
Establece el tamaño máximo de un paquete NBD recibido del servidor. Las lecturas más grandes que esto se dividirán.

Por defecto, estas opciones tienen un valor de 0, lo que significa que no hay límite y libnbd intentará enviar/recibir tantos datos como sea posible en una sola operación (hasta el límite del sistema operativo y el protocolo NBD).

Si estás experimentando problemas de rendimiento o compatibilidad, puedes intentar establecer estos valores a un tamaño de bloque más pequeño, como 1MB (1048576 bytes).

VIRTUAL BLOQUE I/O

Libnbd implementa el protocolo NBD, que está diseñado para el acceso a dispositivos de bloque. Sin embargo, también se puede usar para acceder a datos que no son dispositivos de bloque tradicionales, como archivos.

Esto se logra a través del subsistema "Virtual Block I/O" de libnbd. Permite que libnbd actúe como un servidor NBD para un archivo en el sistema de archivos local, permitiendo que otros clientes NBD accedan al archivo como si fuera un dispositivo de bloque.

La interfaz principal para esto es la función nbd_server_create y las funciones relacionadas. Estas funciones permiten configurar un servidor NBD que expone un archivo o un directorio como un dispositivo de bloque NBD.

Ejemplo básico:

struct nbd_server *server;
// Crear un servidor NBD que expone el archivo "mi_imagen.img"
server = nbd_server_create (NBD_SERVER_FILE, "mi_imagen.img", NULL);
if (!server) {
  // Manejar error
}
// Iniciar el servidor NBD en el puerto 10809
if (nbd_server_start (server, 10809) == -1) {
  // Manejar error
}
// Mantener el servidor en ejecución...
// Para detenerlo:
// nbd_server_stop (server);
// nbd_server_destroy (server);

INFORMACIÓN GENERAL

La biblioteca libnbd se utiliza para implementar el protocolo Network Block Device (NBD). Permite a las aplicaciones cliente conectarse a servidores NBD para acceder al almacenamiento en red como si fuera un dispositivo de bloque local.

Al igual que con otros servicios de red, la conexión a un servidor NBD implica la detección de la dirección del servidor y el puerto. Si el servidor NBD se está ejecutando como un servicio de systemd, puede configurarse para usar la activación por socket de systemd, que permite iniciar el servidor NBD solo cuando hay una conexión entrante y pasar el socket al servidor.

Detección de URIs

nbd_is_uri(3) utiliza una heurística para detectar si el parámetro podría ser una URI NBD o algo más (como un nombre de archivo). Puede ser útil para parámetros de programas que pueden ser una URI o un archivo.

CONEXIÓN A UN SERVIDOR NBD

Para conectarse a un servidor NBD, libnbd admite varios métodos:

Conexión a un host conocido

El método más básico es usar nbd_connect_uri(3) con una URI que especifique el host y el puerto, por ejemplo: "nbd://example.com/" o "nbd+ssh://root@example.com/".

Conexión a un subproceso

Algunos servidores NBD —notablemente nbdkit(1) con el parámetro -s, y nbd-server(1) con el parámetro de puerto establecido en 0— también pueden aceptar una única conexión NBD en stdin/stdout. Puede ejecutar estos servidores como un subproceso de su programa principal usando nbd_connect_command(3). Este ejemplo crea un disco RAM grabable de 1G:

char *argv[] = { "nbdkit", "-s", "--exit-with-parent",
                           "memory", "1G", NULL };
nbd_connect_command (nbd, argv);

Cuando se cierra el manejador, el subproceso nbdkit se elimina, lo que en este caso significa que el disco RAM se descarta, por lo que es útil para pruebas.

Conexión a un subproceso mediante activación por socket de systemd

Algunos servidores NBD —notablemente nbdkit(1) y qemu-nbd(1)— admiten la activación por socket de systemd, lo que permite a libnbd pasar un socket al subproceso. Esto funciona de manera muy similar a nbd_connect_command(3) descrito anteriormente, pero debe usar nbd_connect_systemd_socket_activation(3) en su lugar.

Conexión a cualquier socket

Si ninguno de los otros métodos nbd_connect* son adecuados, puede crear un socket conectado usted mismo y pasarlo a nbd_connect_socket(3).

Un uso para esto es en fuzzing, donde usamos socketpair(2) para crear el socket, luego hacemos fork, luego tenemos el entorno de prueba en el proceso hijo conectado a libnbd a través del par de sockets (ver: https://gitlab.com/nbdkit/libnbd/-/blob/master/fuzzing/libnbd-fuzz-wrapper.c).

Otro uso es conectar libnbd a una familia de direcciones que no admite de forma nativa, como XDP o IB.

CONTROL DE LA NEGOCIACIÓN

Por defecto, al iniciar una conexión, libnbd manejará toda la negociación con el servidor, utilizando solo la configuración (por ejemplo, nbd_set_export_name(3) o nbd_add_meta_context(3)) que se solicitó antes del intento de conexión; esta fase continúa hasta que nbd_aio_is_connecting(3) ya no devuelve verdadero, momento en el cual, o bien los comandos de datos están listos para usarse o la conexión ha fallado con un error.

Pero hay escenarios en los que es útil controlar también los comandos de handshake enviados durante la negociación, como solicitar al servidor una lista de exports disponibles antes de seleccionar cuál usar. Esto se hace llamando a nbd_set_opt_mode(3) antes de conectar; luego, después de solicitar una conexión, la máquina de estados se pausará en nbd_aio_is_negotiating(3) en cualquier momento en que el usuario pueda decidir qué comando de handshake enviar a continuación. Tenga en cuenta que el estado de negociación solo es accesible desde servidores "newstyle"; los servidores "oldstyle" no pueden negociar y progresarán hasta el estado listo.

Cuando se alcanza el estado de negociación, puede iniciar comandos de opción como nbd_opt_list(3) o sus equivalentes asíncronos, así como alterar la configuración, como el nombre de exportación que anteriormente debía establecerse antes de la conexión. Dado que el protocolo NBD no permite comandos de negociación paralelos, no hay cookie involucrado y puede rastrear la finalización de cada comando cuando el estado ya no es nbd_aio_is_connecting(3). Si nbd_opt_go(3) falla pero la conexión sigue activa, volverá al estado de negociación, donde puede solicitar un nombre de exportación diferente e intentarlo de nuevo. Salir del estado de negociación solo es posible con un nbd_opt_go(3) exitoso que pasa a la fase de datos, o nbd_opt_abort(3) que realiza un cierre limpio de la conexión omitiendo la fase de datos.

EXPORTS Y FLAGS

Es posible que los servidores NBD sirvan contenido diferente en diferentes "exports". Para esto, debe pasar el nombre de exportación correcto al servidor. Llame a esta API antes de conectar:

nbd_set_export_name (nbd, "export");

Tenga en cuenta que hay algunos servidores (como nbdkit(1) <= 1.14) que ignoran esto, y otros servidores (como qemu-nbd(8)) que requieren que se establezca correctamente pero no pueden servir contenido diferente.

Estas API también están disponibles después de un nbd_opt_info(3) exitoso durante la fase de negociación, si utilizó nbd_set_opt_mode(3) antes de conectar.

Llamadas a flags

Después de conectar, el servidor enviará un conjunto de flags que describen el export, como si es grabable y si puede admitir flush al almacenamiento permanente. Estos flags se pueden acceder desde libnbd utilizando API como:

int is_read_only = nbd_is_read_only (nbd);
int can_flush = nbd_can_flush (nbd);

Las llamadas a flags son: nbd_can_block_status_payload(3), nbd_can_cache(3), nbd_can_df(3), nbd_can_fast_zero(3), nbd_can_flush(3), nbd_can_fua(3), nbd_can_meta_context(3), nbd_can_multi_conn(3), nbd_can_trim(3), nbd_can_zero(3), nbd_is_read_only(3), nbd_is_rotational(3).

Tamaño del export

Para obtener el tamaño del export en bytes, use nbd_get_size(3):

int64_t size = nbd_get_size (nbd);

Restricciones de tamaño de bloque

Algunos servidores NBD no pueden manejar solicitudes en ningún límite de bytes. Podrían, por ejemplo, requerir que todas las solicitudes estén alineadas a sectores de 512 bytes.

Además, algunos servidores anuncian un tamaño de bloque preferido. Esto no es un requisito, sino el tamaño de bloque mínimo que se puede acceder eficientemente (generalmente sin activar ciclos costosos de lectura-modificación-escritura dentro del servidor).

Estos se denominan restricciones de tamaño de bloque y se pueden consultar llamando a nbd_get_block_size(3). Preste especial atención a la restricción "LIBNBD_SIZE_MINIMUM", ya que algunos servidores fallarán las solicitudes que sean más pequeñas o no estén alineadas a este tamaño de bloque con errores "EINVAL" ("Argumento inválido").

Para obtener información sobre el lado del servidor, consulte ".block_size" en nbdkit-plugin(3).

Para obtener información definitiva sobre las restricciones de tamaño de bloque, lea la especificación del protocolo NBD.

Servidores Newstyle y oldstyle

Libnbd puede conectarse tanto al protocolo NBD más simple y antiguo (antes de 2011), denominado ahora "oldstyle", como a servidores modernos "newstyle-fixed". ("newstyle" solo estuvo disponible brevemente.) Para averiguar el protocolo utilizado por el servidor, llame a nbd_get_protocol(3).

COMANDOS DE DATOS

Puede leer y escribir datos del servidor NBD utilizando nbd_pread(3) y nbd_pwrite(3) o sus equivalentes asíncronos.

Todos los comandos de datos admiten un argumento de "flags" (obligatorio en C, pero opcional en lenguajes donde puede ser 0 por defecto). Para mayor comodidad, la constante "LIBNBD_CMD_FLAG_MASK" se define con el conjunto de flags actualmente reconocidos por libnbd, donde extensiones futuras del protocolo NBD pueden resultar en flags adicionales admitidos; pero en general, los comandos de datos específicos solo aceptan un subconjunto de flags conocidos.

Libnbd, por defecto, realiza algunas verificaciones de sanidad del lado del cliente en cada uno de sus comandos de datos; por ejemplo, se rechazan los intentos de escribir en un servidor que ha anunciado una conexión de solo lectura. Es posible anular aspectos de esta verificación utilizando nbd_set_strict_mode(3).

Algunos servidores también admiten:

trim/discard
Si nbd_can_trim(3) devuelve verdadero, nbd_trim(3) se puede utilizar para "agujerear" el almacenamiento de respaldo del disco en el servidor. Normalmente (aunque no en todos los casos) los agujeros se leen como ceros pero no ocupan espacio.
zeroing
Si nbd_can_zero(3) devuelve verdadero, nbd_zero(3) se puede utilizar para poner a cero eficientemente partes del disco sin tener que enviar grandes cantidades de bytes cero a través de la red (como sería necesario si se usara nbd_pwrite(3)).

OPTIMIZATIONS

Some servers support the following optional features which can make future writes more efficient and/or less likely to fail because of out of space errors.

flushing
Some servers can commit data to permanent storage and tell you that this has happened reliably. There are two export flags associated with this: nbd_can_flush(3) and nbd_can_fua(3).

The nbd_flush(3) call (available if nbd_can_flush(3) returns true) flushes all pending writes to disk and does not complete until that operation has finished. It is similar to using sync(2) on POSIX systems.

A more efficient way to achieve this is to set the flag "LIBNBD_CMD_FLAG_FUA" on write-like calls (like write, trim and zero). This flag means the call will not complete until committed to permanent storage, but it does not involve flushing the entire disk.

prefetching
Some servers can prefetch data, making subsequent reads faster. The nbd_cache(3) call (available if nbd_can_cache(3) returns true) is used to prefetch.
block status
Some servers are able to provide information about the various extents within the image, via the notion of one or more meta contexts. The most common meta context is "base:allocation" (available in libnbd.h as "LIBNBD_CONTEXT_BASE_ALLOCATION"), which can be used to learn which portions of a file are allocated or read as zero. Other contexts may be available; for example, qemu-nbd(8) can expose a meta context "qemu:dirty-bitmap:NAME" for tracking which portions of a file are tracked by a qcow2 dirty bitmap.

In order to utilize block status, the client must call nbd_add_meta_context(3) prior to connecting, for each meta context in which it is interested, then check nbd_can_meta_context(3) after connection to see which contexts the server actually supports. If a context is supported, the client can then use nbd_block_status_64(3) with a callback function that will receive an array of structs describing consecutive extents within a context. Each struct gives the length of the extent, then a bitmask description of that extent (for the "base:allocation" context, the bitmask may include "LIBNBD_STATE_HOLE" for unallocated portions of the file, and/or "LIBNBD_STATE_ZERO" for portions of the file known to read as zero).

There is a full example of requesting meta context and using block status available at https://gitlab.com/nbdkit/libnbd/blob/master/interop/dirty-bitmap.c

PERFORMANCE

Issuing multiple in-flight requests

NBD servers which properly implement the specification can handle multiple data requests in flight over the same connection at the same time. Libnbd supports this when using the low level API.

To use it you simply issue more requests as needed (eg. using calls like nbd_aio_pread(3), nbd_aio_pwrite(3)) without waiting for previous commands to complete. You need to be careful that requests in flight do not overlap with disk offsets of other write-like commands in flight — an overlapping read may see indeterminate data, and an overlapping write may even cause disk corruption where the resulting disk contents do not match either of the two writes.

Each request is identified by a unique 64 bit cookie (assigned by libnbd), allowing libnbd and callers to match replies to requests. Replies may arrive out of order. A request that is rejected client-side for failing a sanity check (such as attempting to write to a read-only server, see nbd_set_strict_mode(3)) will fail rather than returning a cookie, although closure cleanup is still performed.

Although in theory you can have an indefinite number of requests in flight at the same time, in practice it's a good idea to limit them to some number. Libnbd will queue commands in the handle even if it cannot write them to the server, so this limit is largely to prevent a backlog of commands from consuming too much memory. It is suggested to start with a limit of 64 requests in flight (per NBD connection), and measure how adjusting the limit up and down affects performance for your local configuration.

There is a full example using multiple in-flight requests available at https://gitlab.com/nbdkit/libnbd/blob/master/examples/threaded-reads-and-writes.c

Multi-conn

Some NBD servers advertise “multi-conn” which means that it is safe to make multiple connections to the server and load-balance commands across all of the connections.

To do this you should open a single connection first and test for this feature using nbd_can_multi_conn(3). Without error handling it would look like this:

struct nbd_handle *nbd[4];
size_t i;
bool supports_multi_conn;
nbd[0] = nbd_create ();
nbd_connect_tcp (nbd[0], "server", "10809");
supports_multi_conn = nbd_can_multi_conn (nbd[0]) > 0;

If multi-conn is supported then you can open further connections:

if (supports_multi_conn) {
  for (i = 1; i <= 3; ++i) {
    nbd[i] = nbd_create ();
    nbd_connect_tcp (nbd[i], "server", "10809");
  }
}

If you are issuing multiple in-flight requests (see above) and limiting the number, then the limit should be applied to each individual NBD connection.

ENCRYPTION AND AUTHENTICATION

The NBD protocol and libnbd supports TLS (sometimes incorrectly called “SSL”) for encryption of the data stream and authentication of clients and servers. Libnbd defaults to TLS disabled for maximum interoperability. To enable it on a handle you must call nbd_set_tls(3) before connecting.

To allow TLS, but fall back to unencrypted:

nbd_set_tls (nbd, LIBNBD_TLS_ALLOW);

Use nbd_get_tls_negotiated(3) to find out if TLS negotiation was successful. Avoid "LIBNBD_TLS_ALLOW" if man-in-the-middle attacks are a concern.

The most secure mode is to require TLS and fail to connect if the server does not support it:

nbd_set_tls (nbd, LIBNBD_TLS_REQUIRE);

It may also be necessary to verify that the server’s identity is correct. For some servers it may be necessary to verify to the server that the client is permitted to connect. This can be done using either X.509 certificates, or TLS Pre-Shared Keys (PSK). Certificates are more secure. PSK is far more convenient, but you must have an existing secure channel to distribute the keys.

Setting up X.509 using system certificate authorities (CAs)

This is the default if you don’t call any other "nbd_set_tls_*" functions. In this case the server must have a public (eg. HTTPS) certificate which can be verified against the CAs registered on your system (eg. under /etc/pki).

To disable server name verification — which opens you up to a potential Man-In-The-Middle (MITM) attack — use:

nbd_set_tls_verify_peer (nbd, false);

Setting up an X.509 certificate authority (CA)

You can set up your own CA and register clients and servers with it, issuing client and server certificates which will reliably authenticate your clients and servers to each other.

Doing this is described in detail in the nbdkit-tls(1) manual. The only differences for libnbd are:

  • Non-root certificates must be placed in "$HOME/.pki/libnbd/" or "$HOME/.config/pki/libnbd/"
  • Libnbd reads client-cert.pem and client-key.pem (instead of server-cert.pem and server-key.pem).

Once you have set up the directory containing the certificates, call:

nbd_set_tls_certificates (nbd, "/path/to/directory");

Setting up Pre-Shared Keys (PSK)

TLS Pre-Shared Keys are a much more convenient method of setting up TLS, and more appropriate for NBD, but you should have an existing secure method available to distribute the keys. They are therefore ideal if you want to set up an NBD service as an adjunct to an existing secure REST API.

Use psktool(1) to create a file of "username:key" pairs:

psktool -u username -p keys.psk

and pass this path to libnbd:

nbd_set_tls_psk_file (nbd, "keys.psk");

If necessary you may need to set the client username (otherwise libnbd will use your login name):

nbd_set_tls_username (nbd, "username");

Some libnbd calls take callbacks (eg. nbd_set_debug_callback(3), nbd_aio_pread(3)). Libnbd can call these functions while processing.

In the C API these libnbd calls take a structure which contains the functi

Para callbacks opcionales, si no desea el callback, establezca ".callback" a "NULL" o utilice las macros equivalentes (como "NBD_NULL_COMPLETION") definidas en "libnbd.h":

Desde otros lenguajes, la estructura y el puntero opaco no son necesarios porque se pueden utilizar closures para lograr el mismo efecto.

Tiempos de vida del callback

Puede asociar una función de liberación opcional con los callbacks. Libnbd llamará a esta función cuando el callback ya no sea llamado por libnbd, incluso en el caso de que la API falle.

Esto puede utilizarse para liberar "user_data" asociado. Por ejemplo:

void *my_data = malloc (...);
nbd_aio_pread_structured (nbd, buf, sizeof buf, offset,
               (nbd_chunk_callback) { .callback = my_fn,
                                      .user_data = my_data,
                                      .free = free },
               NBD_NULL_COMPLETION,
               0);

llamará a free(3) una vez sobre "my_data" después del punto en que se sepa que la función "chunk.callback = my_fn" ya no se puede llamar, independientemente de cuántas veces se haya llamado realmente a "my_fn". Si se suministra tanto un callback de mitad de comando como uno de finalización, las funciones se alcanzarán en este orden: callbacks de mitad de función, callback de finalización, liberación de mitad de función y, finalmente, liberación de finalización.

La función de liberación solo es accesible en la API de C, ya que no es necesaria en lenguajes de programación con recolección de basura.

Callbacks con ".callback=NULL" y ".free!=NULL"

Es posible registrar un callback como este:

...
  (nbd_completion_callback) { .callback = NULL,
                              .user_data = my_data,
                              .free = free },
...

El significado de esto es que el callback nunca se llama, pero la función de liberación todavía se llama después de la última vez que se habría llamado al callback. Esto es útil para aplicar acciones de liberación genéricas cuando los comandos asíncronos se retiran.

Callbacks y bloqueo

Los callbacks se invocan en un punto en el que se mantiene el bloqueo de libnbd, típicamente durante una llamada a "nbd_aio_notify_read", "nbd_aio_notify_write", "nbd_aio_poll", u otra llamada que pueda avanzar la máquina de estados de libnbd. Dependiendo de la carga del sistema, incluso es posible que se alcance un callback antes de la finalización de la llamada "nbd_aio_*" que especificó el callback. Como tal, no es seguro que el callback llame a ninguna API de "nbd_*" en el mismo objeto nbd, ya que provocaría un interbloqueo.

Callbacks de finalización

Todos los comandos asíncronos tienen una función de callback de finalización opcional que se utiliza si la llamada a la API asíncrona informa éxito. El callback de finalización se invoca cuando el comando enviado se marca finalmente como completado, después de que todos los callbacks de mitad de comando hayan finalizado y antes de cualquier función de liberación. El callback de finalización no se alcanza si la propia API asíncrona falla, mientras que los callbacks de liberación se alcanzan independientemente del resultado de la API asíncrona inicial.

Cuando el callback de finalización devuelve 1, el comando se retira automáticamente (no es necesario llamar a nbd_aio_command_completed(3)); para cualquier otro valor de retorno, el comando todavía necesita ser retirado manualmente (de lo contrario, el comando ocupará recursos hasta que eventualmente se alcance nbd_close(3)).

Callbacks con parámetro "int *error"

Algunos de los comandos de alto nivel (nbd_pread_structured(3), nbd_block_status_64(3)) implican el uso de una función de callback invocada por la máquina de estados en puntos apropiados de la respuesta del servidor antes de que el comando general se complete. Estas funciones de callback, junto con todos los callbacks de finalización, incluyen un parámetro "error" que es un puntero que contiene el valor de cualquier error detectado hasta el momento. Si una función de callback falla y desea cambiar el error resultante del comando general visible más adelante en la secuencia de la API, debe asignar de nuevo a "error" y devolver -1 en la API de C. Las asignaciones a "error" se ignoran para cualquier otro valor de retorno; de manera similar, asignar 0 a "error" no tiene ningún efecto. En otros enlaces de lenguaje, la notificación de errores de callback generalmente se hace generando una excepción en lugar de mediante un valor de retorno.

Tenga en cuenta que un callback de mitad de comando podría no ser alcanzado nunca, por ejemplo, si libnbd detecta que el comando no era válido para enviar (ver nbd_set_strict_mode(3)) o si el servidor informa de un error que concluye el comando. Es seguro que un callback de mitad de comando ignore un "error" distinto de cero: todos los demás parámetros para el callback de mitad de comando seguirán siendo válidos (correspondientes a la porción actual de la respuesta del servidor), y el comando general seguirá fallando (en el callback de finalización o en nbd_aio_command_completed(3) para un comando asíncrono, o como resultado del comando síncrono general). Devolver -1 desde un callback de mitad de comando no evita que ese callback se alcance de nuevo, si el servidor envía más respuestas de mitad de comando que justifican otro uso de ese callback. Un callback de mitad de comando puede alcanzarse más veces de lo esperado si el servidor no es conforme.

Por otro lado, si se proporciona un callback de finalización (solo posible con comandos asíncronos), no se llamará si la llamada inicial a la API falla (por ejemplo, al intentar un comando asíncrono en el estado incorrecto - no hay nada que completar ya que el comando no se puso en cola), pero de lo contrario se llamará exactamente una vez, y el callback de finalización no debe ignorar el valor al que apunta "error". En particular, el contenido de un buffer pasado a nbd_aio_pread(3) o nbd_aio_pread_structured(3) no está definido si *error es distinto de cero al entrar en el callback de finalización. Se recomienda que si elige usar la retirada automática de comandos (donde el callback de finalización devuelve 1 para evitar la necesidad de llamar a nbd_aio_command_completed(3) más tarde), su función de finalización debe devolver 1 en todas las rutas de control, incluso al manejar errores (tenga en cuenta que con la retirada automática, la asignación a "error" no tiene sentido ya que no hay una API posterior para ver ese valor).

CONTADORES DE ESTADÍSTICAS

Libnbd rastrea varios contadores de estadísticas, útiles para rastrear cuánta tráfico se envió a través de la conexión. Los contadores rastrean el número de bytes en texto plano enviados y recibidos por el protocolo NBD (no necesariamente el número de bytes enviados por el socket, particularmente cuando TLS está habilitado), así como el número de trozos de protocolo (un grupo de bytes delimitado por un número mágico, y no lo mismo que el número de paquetes TCP).

printf ("bytes: sent=%" PRIu64 " received=%" PRIu64,
         nbd_stats_bytes_sent (nbd), nbd_stats_bytes_received (nbd));
printf ("chunks: sent=%" PRIu64 " received=%" PRIu64,
         nbd_stats_chunks_sent (nbd), nbd_stats_chunks_received (nbd));

SEÑALES

Libnbd no instala manejadores de señales. Intenta deshabilitar "SIGPIPE" al escribir en el socket NBD utilizando la bandera "MSG_NOSIGNAL" de send(2), o la opción de socket "SO_NOSIGPIPE", en plataformas que lo soportan.

En algunas plataformas Linux antiguas o más recientes no Linux, el programa principal puede desear registrar un manejador de señales para ignorar SIGPIPE:

signal (SIGPIPE, SIG_IGN);

COMPILACIÓN DE TU PROGRAMA

En la mayoría de los sistemas, los programas C que usan libnbd se pueden compilar así:

cc prog.c -o prog -lnbd

Para detectar si la biblioteca libnbd y el archivo de cabecera están instalados, el método preferido es usar pkg-config(1) o pkgconf(1):

pkg-config libnbd --exists || fail libnbd is required

En caso de que la biblioteca o el archivo de cabecera no estén instalados en las ubicaciones habituales del sistema, puede compilar su programa así, utilizando pkg-config para detectar la ubicación correcta de libnbd:

cc prog.c -o prog `pkg-config libnbd --cflags --libs`

Para compilar un proyecto externo contra una copia compilada del árbol de fuentes de libnbd que no se ha instalado, consulte el script ./run.

Proyectos Autoconf

Los proyectos externos que utilizan autoconf y necesitan verificar si libnbd está instalado deben usar la macro "PKG_CHECK_MODULES" en configure.ac de esta manera:

PKG_CHECK_MODULES([LIBNBD], [libnbd])

Esto definirá "@LIBNBD_CFLAGS@" y "@LIBNBD_LIBS@" que necesitarás añadir a tu Makefile.am.

Proyectos CMake

Para proyectos CMake usa:

find_package(PkgConfig REQUIRED)
pkg_check_modules(LIBNBD REQUIRED libnbd)
target_link_libraries(prog ${LIBNBD_LIBRARIES})
target_include_directories(prog PUBLIC ${LIBNBD_INCLUDE_DIRS})
target_compile_options(prog PUBLIC ${LIBNBD_CFLAGS_OTHER})

Proyectos Meson

Para proyectos meson usa:

nbd_dep = dependency('libnbd')
executable('prog', 'prog.c', dependencies : [nbd_dep])
