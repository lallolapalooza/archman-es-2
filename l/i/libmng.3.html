LIBMNG(3) Manual de Funciones de Biblioteca LIBMNG(3)

NOMBRE

libmng - Biblioteca de Referencia de Gráficos de Red Multimagen (MNG) 1.0.9

SINOPSIS

#include <libmng.h>

DESCRIPCIÓN

La biblioteca libmng soporta la decodificación, visualización, codificación y diversas otras manipulaciones de archivos de imagen del formato Multiple-image Network Graphics (MNG). Utiliza la biblioteca de compresión zlib(3) y, opcionalmente, la biblioteca JPEG del Independent JPEG Group (IJG) y/o lcms (little cms), una biblioteca de gestión de color de Marti Maria Saguer.

I. Introducción

Este archivo describe cómo usar y modificar la biblioteca de referencia MNG (conocida como libmng) para su propio uso. Hay siete secciones en este archivo: introducción, callbacks, administración, lectura, visualización, escritura y notas de modificación y configuración para varias plataformas especiales. Asumimos que libmng ya está instalado; consulte el archivo INSTALL.README para obtener instrucciones sobre cómo instalar libmng.

Libmng fue escrita para soportar y promover la especificación MNG.

La especificación MNG-1.0 está disponible en http://www.libpng.org/pub/mng/spec/.

Otra información sobre MNG se puede encontrar en la página principal de MNG, http://www.libpng.org/pub/mng/. La última versión de libmng se puede encontrar en su propia página principal en http://www.libmng.com/.

En la mayoría de los casos, la biblioteca no necesitará ser modificada. Para fines de estandarización, la biblioteca contiene tanto una DLL de Windows como un Makefile para compilar una biblioteca compartida (SO). La biblioteca está escrita en C, pero también hay disponible una interfaz para Borland Delphi.

Libmng ha sido diseñada para manejar múltiples sesiones al mismo tiempo, para ser fácilmente modificable, para ser portable a la gran mayoría de máquinas (ANSI, K&R, 32 y 64 bits) disponibles, y para ser fácil de usar.

Libmng utiliza zlib para la compresión y descompresión de archivos MNG. Para más información sobre zlib y la última versión de zlib, consulte la página principal de zlib, http://www.zlib.org/. La utilidad de compresión zlib es una utilidad de propósito general que es útil para más que archivos MNG/PNG, y puede usarse sin libmng. Consulte la documentación entregada con zlib para más detalles.

Libmng utiliza opcionalmente la biblioteca JPEG del Independent JPEG Group (IJG). Esta biblioteca se utiliza para el subformato JNG, que forma parte de la especificación MNG, y permite la inclusión de imágenes decodificadas en JPEG y, por lo tanto, altamente comprimidas (fotográficas). Para más información sobre la biblioteca JPEG de IJG y las últimas fuentes, consulte http://www.ijg.org/.

Libmng también puede utilizar opcionalmente la biblioteca lcms (little CMS) de Marti Maria Saguer. Esta biblioteca proporciona un excelente sistema de gestión de color (CMS), lo que da a libmng la capacidad de proporcionar corrección de color completa para imágenes con la información de color adecuada codificada. Para más información y las últimas fuentes, consulte http://www.littlecms.com/.

Libmng es segura para hilos, siempre que los hilos utilicen identificadores diferentes devueltos por la llamada de inicialización. Cada hilo debe tener su propio identificador y, por lo tanto, su propia imagen. Libmng no se protege contra dos hilos que utilizan la misma instancia de un identificador.

El archivo de cabecera libmng.h es la única referencia necesaria para la programación con libmng:

#include <libmng.h>

II. Callbacks

Libmng hace un uso extensivo de funciones de callback. Esto tiene como objetivo mantener la biblioteca lo más independiente de la plataforma y flexible posible. De hecho, la primera llamada que realizará a la biblioteca ya contiene tres parámetros que puede utilizar para proporcionar puntos de entrada de callback.

La mayoría de las funciones deben devolver un mng_bool (booleano). Devolver MNG_FALSE indica que la biblioteca falló en algún aspecto y la biblioteca saldrá inmediatamente de lo que estaba haciendo y volverá a la aplicación. Devolver MNG_TRUE indica que no hubo problemas y el procesamiento puede continuar.

Repasemos cada uno de los posibles callbacks. Las secciones sobre lectura, visualización y escritura también explicarán qué callbacks se necesitan, cuándo y dónde.

- mng_ptr mng_memalloc (mng_size_t iLen)

Una función muy básica que la biblioteca utiliza para asignar un bloque de memoria con el tamaño dado. Una implementación típica sería:


mng_ptr mi_alloc (mng_size_t iLen) {
return calloc (1, iLen);
}

¡¡¡Tenga en cuenta que la biblioteca requiere que ponga a cero el bloque de memoria!!!

- void mng_memfree (mng_ptr pPtr,
mng_size_t iLen)

Contrapunto de la función anterior. Típicamente:


void mi_free (mng_ptr pPtr, mng_size_t iLen) {
free (pPtr);
}

- mng_bool mng_openstream (mng_handle hHandle)

- mng_bool mng_closestream (mng_handle hHandle)

Estas son llamadas por la biblioteca justo antes de que comience a procesar (ya sea leer o escribir) un archivo y justo después de que termine el procesamiento. Este es el lugar recomendado para inicializar y finalizar E/S. Si lo hace o no, depende de usted. La biblioteca no le da ningún significado a las llamadas. Simplemente se proporcionan para su conveniencia.

- mng_bool mng_readdata (mng_handle hHandle,
mng_ptr pBuf,
mng_uint32 iBuflen,
mng_uint32p pRead)

Esta función se llama cuando la biblioteca necesita más entrada mientras lee una imagen. El proceso de lectura admite dos modos: modo de suspensión (SMOD) y modo de no suspensión (NSMOD). Consulte mng_set_suspensionmode() para obtener una descripción más detallada.

En NSMOD, la biblioteca requiere que devuelva exactamente la cantidad de bytes solicitados (= iBuflen). Cualquier cantidad menor indica que el archivo de entrada se ha agotado y la biblioteca devolverá un código de error MNG_UNEXPECTEDEOF.

En SMOD, puede devolver una cantidad menor de bytes que la solicitada. Esto le dice a la biblioteca que debe esperar temporalmente a que lleguen más datos de entrada. La biblioteca devolverá MNG_NEEDMOREDATA y esperará una llamada a mng_read_resume() o mng_display_resume() a continuación, tan pronto como lleguen más datos de entrada.

Para NSMOD, esta función podría ser tan simple como:


mng_bool mi_lectura (mng_handle hHandle,
mng_ptr pBuf,
mng_uint32 iBuflen,
mng_uint32p pRead) {
*pRead = fread (pBuf, 1, iBuflen, mi_archivo);
return MNG_TRUE;
}

- mng_bool mng_writedata (mng_handle hHandle,
mng_ptr pBuf,
mng_uint32 iBuflen,
mng_uint32p pWritten)

Esta función se llama durante la función mng_write() para generar datos reales en el archivo. No hay modo de suspensión durante la escritura, por lo que la aplicación debe devolver la cantidad exacta de bytes que la biblioteca solicita que se escriban.

Una implementación típica podría ser:


mng_bool mi_escritura (mng_handle hHandle,
mng_ptr pBuf,
mng_uint32 iBuflen,
mng_uint32p pWritten) {
*pWritten = fwrite (pBuf, 1, iBuflen, mi_archivo);
return MNG_TRUE;
}

- mng_bool mng_errorproc (mng_handle hHandle,
mng_int32 iErrorcode,
mng_int8 iSeverity,
mng_chunkid iChunkname,
mng_uint32 iChunkseq,
mng_int32 iExtra1,
mng_int32 iExtra2,
mng_pchar zErrortext)

Esta función se llama cada vez que se detecta un error dentro de la biblioteca. Esto puede ser causado por entradas inválidas, callbacks que indican fallo o por llamar incorrectamente a funciones fuera de lugar.

Si no proporciona este callback, la biblioteca aún devolverá un código de error de la función llamada, y la función mng_getlasterror() se puede utilizar para recuperar los otros parámetros.

Esta función se proporciona actualmente solo por conveniencia, pero en algún momento podría usarse para indicar que ciertos errores pueden ser aceptables y que el procesamiento debe continuar.

- mng_bool mng_traceproc (mng_handle hHandle,
mng_int32 iFuncnr,
mng_int32 iFuncseq,
mng_pchar zFuncname)

Esta función se proporciona para permitir un análisis funcional de la biblioteca. Esto puede ser útil si encuentra ciertos errores y no puede determinar cuál es el problema.

II. Callbacks

Callbacks are the hooks through which libmng interacts with your application. The library signals events to your application via callbacks, and asks for data from your application via callbacks. As an example, if libmng needs a line of pixels to display, it will ask your application for it using a callback.

The callbacks are divided into two categories:


- Those that are called by the library *to* the application.


- Those that are called by the application *to* the library.

All callbacks that are called by the library *to* the application are defined as mng_cb_ followed by the name of the function. All callbacks that are called by the application *to* the library are defined as mng_ followed by the name of the function.

A few notes on callbacks in general:

  • All callbacks must return a boolean value. If the callback was successful it must return MNG_TRUE. If the callback failed it must return MNG_FALSE.

  • The library requires a valid pointer to the callback function entry-point. A MNG_NULL pointer will result in an error.

  • If your application needs to handle multiple MNGs simultaneously, you will receive a mng_handle as the first parameter to each callback. This handle is unique to each MNG processing instance and allows you to associate the callback with the correct MNG.

  • The application is responsible for the memory management of all data passed to the library, and for all data the library is expected to return. See the section on memory management for more details.

Information callbacks

These callbacks are called by the library to inform the application about the contents of the MNG stream.

- mng_bool mng_processheader (mng_handle hHandle,
mng_uint32 iWidth,
mng_uint32 iHeight)

This function is called once the header information of an input- image has been processed. At this point the image dimensions are available and also some other properties depending on the type of the image. Eg. for a MNG the frame-/layercount, playtime & simplicity fields are known.

The primary purpose of this callback is to inform the application of the size of the image, and for the application to initialize the drawing canvas to be used by the library. This is also a good point to set the canvas-style. Eg. mng_set_canvasstyle().

- mng_bool mng_processtext (mng_handle hHandle,
mng_uint8 iType,
mng_pchar zKeyword,
mng_pchar zText,
mng_pchar zLanguage,
mng_pchar zTranslation)

This callback is activated for each textual chunk in the input- image. These are tEXt, zTXt & iTXt. It may be used to retain specific comments for presentation to the user.

- mng_bool mng_processsave (mng_handle hHandle)

- mng_bool mng_processseek (mng_handle hHandle,
mng_pchar zName)

The purpose of these callbacks is to signal the processing of the SAVE & SEEK chunks in a MNG input-file. This may be used in the future to specify some special processing. At the moment these functions are only provided as a signal.

- mng_ptr mng_getcanvasline (mng_handle hHandle,
mng_uint32 iLinenr)

- mng_ptr mng_getbkgdline (mng_handle hHandle,
mng_uint32 iLinenr)

- mng_ptr mng_getalphaline (mng_handle hHandle,
mng_uint32 iLinenr)

These callbacks are used to access the drawing canvas, background canvas and an optional separate alpha-channel canvas. The latter is used only with the MNG_CANVAS_RGB8_A8 canvas-style.

If the getbkgdline() callback is not supplied the library will composite fully or partially transparent pixels in the image against a specified background color. See mng_set_bgcolor() for more details. If a chosen canvas-style includes an alpha-channel, this callback is very likely not needed.

The application is responsible for returning a pointer to a line of pixels, which should be in the exact format as defined by the call to mng_set_canvasstyle() and mng_set_bkgdstyle(), without gaps between the representation of each pixel, unless specified by the canvas-style.

- mng_bool mng_refresh (mng_handle hHandle,
mng_uint32 iX,
mng_uint32 iY,
mng_uint32 iWidth,
mng_uint32 iHeight)

This callback is called when the library has drawn a complete frame onto the drawing canvas, and it is ready to be displayed. The application is responsible for transferring the drawing canvas from memory onto the actual output device.

- mng_uint32 mng_gettickcount (mng_handle hHandle)

This function should return the number of milliseconds on some internal clock. The entire animation timing depends heavily on this function, and the number returned should be as accurate as possible.

- mng_bool mng_settimer (mng_handle hHandle,
mng_uint32 iMsecs)

This callback is activated every time the library requires a "pause". Note that the function itself should NOT execute the wait. It should simply store the time-field and allow the library to return. Libmng will return with the MNG_NEEDTIMERWAIT code, indicating the callback was called and it is now time to execute the pause.

After the indicated number of milliseconds have elapsed, the application should call mng_display_resume(), to resume the animation as planned.

This method allows for both a real timer or a simple wait command in the application. Whichever method you select, both the gettickcount() and settimer() callbacks are crucial for proper animation timing.

- mng_bool mng_processgamma (mng_handle hHandle,
mng_uint32 iGamma)

- mng_bool mng_processchroma (mng_handle hHandle,
mng_uint32 iWhitepointx,
mng_uint32 iWhitepointy,
mng_uint32 iRedx,
mng_uint32 iRedy,
mng_uint32 iGreenx,
mng_uint32 iGreeny,
mng_uint32 iBluex,
mng_uint32 iBluey)

- mng_bool mng_processsrgb (mng_handle hHandle,
mng_uint8 iRenderingintent)

- mng_bool mng_processiccp (mng_handle hHandle,
mng_uint32 iProfilesize,
mng_ptr pProfile)

- mng_bool mng_processarow (mng_handle hHandle,
mng_uint32 iRowsamples,
mng_bool bIsRGBA16,
mng_ptr pRow)

These callbacks are only required when you selected the MNG_APP_CMS directive during compilation of the library. See the configuration section for more details.

- mng_bool mng_iteratechunk (mng_handle hHandle,
mng_handle hChunk,
mng_chunkid iChunkid,
mng_uint32 iChunkseq)

This callback is only used for the mng_iterate_chunks() function. It is called exactly once for each chunk stored.

Data provider callbacks

These callbacks are used by the library to request data from the application. At the moment, these are only used when writing MNG or PNG files.

- mng_bool mng_readbyte (mng_handle hHandle,
mng_ptr pBuffer,
mng_uint32 iBytesToRead,
mng_uint32 *pBytesRead)

This callback is used to supply the library with data from the input file. The application must fill the supplied buffer with data read from the source. iBytesToRead specifies the maximum number of bytes to read. pBytesRead is a pointer to a 32-bit unsigned integer where the actual number of bytes read must be stored. The callback must return MNG_TRUE if the read operation was successful, even if *pBytesRead is less than iBytesToRead (this typically happens at end-of-file).

The callback must return MNG_FALSE if an error occurred during the read operation, or if no data could be read and the end of the file has not been reached.

A typical implementation might read from a stdio stream, a memory buffer, or a network socket.

- mng_bool mng_writebyte (mng_handle hHandle,
mng_pchar zBuffer,
mng_uint32 iBytesToWrite,
mng_uint32 *pBytesWritten)

This callback is used to write data supplied by the library to the output file. The application must write the contents of the supplied buffer to the destination. iBytesToWrite specifies the number of bytes to write. pBytesWritten is a pointer to a 32-bit unsigned integer where the actual number of bytes written must be stored. The callback must return MNG_TRUE if the write operation was successful. It must return MNG_FALSE if an error occurred.

A typical implementation might write to a stdio stream, a memory buffer, or a network socket.

III. Housekeeping

Memory management

The library can use internal memory allocation/deallocation or use provided callbacks for its memory management. The choice is made at compilation time. See the section on customization for details.

If internal management has been selected, the memory callback functions need not be supplied. Even if you do supply them they will not be used. The actual code used is similar to the code discussed in the callback section:


pPtr = calloc (1, iLen);


free (pPtr);

If your compiler does not support these functions, or you wish to monitor the library's use of memory for certain reasons, you can choose to compile the library with external memory management. In this case the memory callback functions MUST be supplied, and should function as if the above code was used.

Initialization

The basic initialization of the library is short and swift:


myhandle = mng_initialize (myuserdata, my_alloc,
my_free, MNG_NULL);
if (myhandle == MNG_NULL)
/* process error */;

The first field is an application-only parameter. It is saved in libmng's internal structures and available at all times through the mng_get_userdata() function. This is especially handy in callback functions if your program may be handling multiple files at the same time.

The second and third field supply the library with the memory callback function entry-points. These are described in more detail in the callback section and the previous paragraph.

The fourth and last field may be used to supply the library with the entry-point of a trace callback function. For regular use you will not need this!

The function returns a handle which will be your ticket to MNG-heaven. All other functions rely on this handle. It is the single fixed unique reference-point between your application and the library.

You should call the initialization function for each image you wish to process simultaneously. If you are processing images consecutively, you can reset the internal status of the library with the mng_reset() function. This function will clear all internal state variables, free any stored chunks and/or objects, etc, etc. Your callbacks and other external parameters will be retained.

After you successfully received the handle it is time to set the required callbacks. The sections on reading, displaying & writing indicate which callbacks are required and which are optional. To set the callbacks simply do:


myretcode = mng_setcb_xxxxxx (myhandle, my_xxxxxx);
if (myretcode != MNG_NOERROR)
/* process error */;

Naturally you'd replace the x's with the name of the callback.

Cleanup

Once you've gotten hold of that precious mng_handle, you should always, and I mean always, call the cleanup function when you're done. Just do:


mng_cleanup (myhandle);

And you're done. There shouldn't be an ounce of memory spilled after that call.

Note that if you would like to process multiple files consecutively you do not need to do mng_cleanup() / mng_initialize() between each file but simply


myretcode = mng_reset (myhandle);
if (myretcode != MNG_NOERROR)
/* process error */;

will suffice. Saves some time and effort, that.

Error handling

From the examples in the previous paragraphs you may have noticed a meticulous scheme for error handling. And yes, that's exactly what it is. Practically each call simply returns an errorcode, indicating success, eg. MNG_NOERROR or failure, anything else but MNG_NEEDMOREDATA and MNG_NEEDTIMERWAIT. These latter two will be discussed in more detail in their respective fields of interest: the reading section and displaying section respectively.

It is the application's responsibility to check the returncode after each call. You can call mng_getlasterror() to receive the details of the last detected error. This even includes a discriptive error-message if you enabled that option during compilation of the library.

Note that after receiving an error it is still possible to call the library, but it's also very likely that any following call will fail. The only functions deemed to work will be mng_reset() and mng_cleanup(). Yes, if you abort your program after an error, you should still call mng_cleanup().

IV. Leer

Configuración

Asumiendo que has inicializado la biblioteca y eres el propietario de un `mng_handle`. Las siguientes devoluciones de llamada son esenciales:


mng_readdata, mng_closestream

Opcionalmente, puedes definir:


mng_errorproc, mng_traceproc
mng_processheader, mng_processtext
mng_processsave, mng_processseek

La parte de lectura también fallará si ya estás creando o mostrando un archivo. Parece un poco obvio, pero pensé que lo mencionaría, por si acaso.

¿Suspender o no suspender?

Hay una decisión que debes tomar antes de llamar a la función de lectura. ¿Necesitas el modo de suspensión o no?

Si estás leyendo desde un disco, lo más probable es que no necesites el modo de suspensión. Incluso los discos más antiguos y lentos serán lo suficientemente rápidos para la lectura directa.

Sin embargo, si tu entrada proviene de un dispositivo muy lento, como una línea de acceso telefónico o similar, puedes optar por el modo de suspensión. Esto se hace llamando a


myretcode = mng_set_suspensionmode (myhandle,
MNG_TRUE);
if (myretcode != MNG_NOERROR)
/* procesar error */;

El modo de suspensión forzará a la biblioteca a usar un búfer especial en la entrada. Esto permite a tu aplicación recibir datos de longitud arbitraria y devolverlos en la devolución de llamada `mng_readdata()`, sin perturbar las rutinas de procesamiento de fragmentos de la biblioteca.

El modo de suspensión requiere un poco de cuidado adicional en la lógica principal de la aplicación. La función de lectura puede devolver `MNG_NEEDMOREDATA` cuando la devolución de llamada `mng_readdata()` devuelve menos datos de los que necesita para procesar el siguiente fragmento. Esto indica a la aplicación que espere a que lleguen más datos y luego reanude el procesamiento llamando a `mng_read_resume()`.

La API de alto nivel de lectura

La lectura real es muy simple. Dado que todas las E/S se realizan fuera de la biblioteca a través de las devoluciones de llamada, la biblioteca puede centrarse en su tarea real: ¡entender, verificar y etiquetar los datos de entrada!

Todo lo que realmente necesitas hacer es esto:


myretcode = mng_read (myhandle);
if (myretcode != MNG_NOERROR)
/* procesar error */;

Por supuesto, si estás en modo de suspensión, el código es un poco más complicado:


myretcode = mng_read (myhandle);


while (myretcode == MNG_NEEDMOREDATA) {
/* esperar a que lleguen los datos de entrada */
myretcode = mng_read_resume (myhandle);
}


if (myretcode != MNG_NOERROR)
/* procesar error */;

Esto es bastante rudimentario y métodos de programación más sofisticados pueden dictar un enfoque diferente. Cualquiera que sea el método que decidas, debería actuar como si el código anterior estuviera en su lugar.

También existe la función `mng_readdisplay()`, pero esto se discute en la sección de visualización. Funciona de manera muy similar a la función `mng_read()`, pero también comienza a mostrar la imagen inmediatamente. `mng_read_resume()` debería reemplazarse por `mng_display_resume()` en ese caso.

¿Qué sucede internamente?

Lo que realmente sucede dentro de la biblioteca depende de las opciones de configuración establecidas durante la compilación de la biblioteca.

Básicamente, la biblioteca primero leerá la cabecera del archivo de 8 bytes, para determinar su validez y el tipo de imagen que está a punto de procesar. Luego, leerá repetidamente una longitud de fragmento de 4 bytes y luego el resto del fragmento hasta que alcance el fin de archivo (indicado por la devolución de llamada `mng_readdata()`) o decida implícitamente el fin de archivo al procesar el último fragmento lógico de la imagen.

Las aplicaciones que requieren conformidad estricta y no permiten datos superfluos después del fragmento final, deberán realizar esta verificación en su devolución de llamada `mng_closestream()`.

Cada fragmento se verifica en busca de CRC, después de lo cual se entrega a la rutina de procesamiento de fragmentos apropiada. Estas rutinas diseccionarán el fragmento, verificarán la validez de su contenido, verificarán su posición con respecto a otros fragmentos, etc., etc.

Si todo está en orden, el fragmento se procesa de la siguiente manera:

Si se seleccionó soporte de visualización durante la compilación, se realizará una inicialización previa a la visualización.

Si se seleccionó soporte de almacenamiento de fragmentos durante la compilación, los datos de los fragmentos pueden almacenarse en una estructura interna especial y guardarse para referencia futura.

Almacenamiento y acceso a fragmentos

Una de las opciones de compilación activa el soporte para el almacenamiento de fragmentos. Esta opción puede ser útil si desea examinar una imagen. La directiva es `MNG_STORE_CHUNKS`. También debes activar la directiva `MNG_ACCESS_CHUNKS`.

La instalación de almacenamiento real se puede activar o desactivar con la función `mng_set_storechunks()`. Si se establece en `MNG_TRUE`, los fragmentos se almacenarán a medida que se leen.

En cualquier momento, puedes llamar a la función `mng_iterate_chunks()` para iterar a través de la lista actual de fragmentos. Esta función requiere una devolución de llamada que se llama para cada fragmento y recibe un manejador de fragmento específico. Este manejador de fragmento se puede usar para llamar a la función `mng_getchunk_xxxx()` apropiada, para acceder a las propiedades del fragmento.

Una implementación típica podría verse así:


mng_bool my_iteratechunk (mng_handle hHandle,
mng_handle hChunk,
mng_chunkid iChunkid,
mng_uint32 iChunkseq) {
switch (iChunkid) {
case MNG_UINT_MHDR : { /* procesar MHDR */;
break; }
case MNG_UINT_FRAM : { /* procesar FRAM */;
break; }


...etc...


case MNG_UINT_HUH : { /* fragmento desconocido */;
break; }
default : { /* duh; olvidé uno */; }
}


return MNG_TRUE; /* seguir enviándolos */
}

Para acceder a los campos reales del fragmento, digamos de un fragmento SHOW, harías:


mng_bool isempty;
mng_uint16 firstid, lastid;
mng_uint8 showmode;


myretcode mng_getchunk_show (hHandle, hChunk,
isempty, firstid,
lastid, showmode);
if (myretcode != MNG_NOERROR)
/* procesar error */;

V. Visualización

Configuración

Asumiendo que has inicializado la biblioteca y eres el propietario de un `mng_handle`. Las siguientes devoluciones de llamada son esenciales:


mng_getcanvasline, mng_refresh
mng_gettickcount, mng_settimer

Si deseas usar un fondo proporcionado por la aplicación, debes suministrar:


mng_getbkgdline

Si deseas usar el estilo de lienzo `MNG_CANVAS_RGB8_A8`, debes suministrar:


mng_getalphaline

Opcionalmente, puedes definir:


mng_errorproc, mng_traceproc
mng_processheader, mng_processtext
mng_processsave, mng_processseek

¡Ten en cuenta que la devolución de llamada `mng_processheader()` es opcional, pero será bastante significativa para el correcto funcionamiento!

Mostrar una imagen fallará si estás creando un archivo o ya mostrando uno. ¡Sí, no puedes mostrarlo dos veces!

Una palabra sobre los estilos de lienzo

El estilo del lienzo describe cómo está compuesto tu lienzo de dibujo. Debes establecer esto antes de que la biblioteca comience a dibujar, por lo que la devolución de llamada `mng_processheader()` es un buen lugar para ello.

Actualmente, solo se admiten estilos de lienzo RGB de 8 bits, con o sin canal alfa.

Si deseas realizar la composición alfa tú mismo, puedes seleccionar uno de los estilos de lienzo que incluyen un canal alfa. Incluso puedes tener un lienzo alfa separado seleccionando el estilo `MNG_CANVAS_RGB8_A8`.

Todos los estilos requieren un modelo compacto. Por ejemplo, `MNG_CANVAS_BGR8` requiere que tus líneas de lienzo estén en almacenamiento bgrbgrbgr..., donde cada letra representa un valor de 8 bits del color correspondiente, y cada trío forma los valores de un (1) píxel.

La biblioteca procesa una línea a la vez, por lo que las líneas del lienzo no necesitan estar consecutivas en memoria.

Composición alfa y fondos de aplicación

Todos los Gráficos de Red pueden ser parcialmente transparentes. Esto requiere un procesamiento especial si necesitas mostrar una imagen contra algún fondo. Ten en cuenta que la cabecera MNG (fragmento MHDR) contiene un campo de simplicidad que indica si la información de transparencia en el archivo es crítica o no. Esto solo se aplica a imágenes incrustadas, lo que significa que el marco de imagen completo del MNG aún puede contener píxeles completamente transparentes.

Dependiendo de tus necesidades, puedes proporcionar un color de fondo único, un lienzo de fondo o indicarle a la biblioteca que devuelva el canal alfa y que realices la composición alfa tú mismo.

Esto es diferente del fragmento BACK en un MNG, o del fragmento bKGD en un PNG o JNG (incrustado). El fragmento BACK indica un color y/o imagen de fondo opcional o obligatorio. El fragmento bKGD solo indica un color de fondo opcional. Estos fragmentos indican las preferencias del autor. Pueden estar ausentes, en cuyo caso necesitas proporcionar algún tipo de fondo tú mismo.

Componer contra un color de fondo

Este es el método más fácil. Llama a la función `mng_set_bgcolor()` para establecer los valores del componente rojo, verde y azul de tu color de fondo preferido.

Usa uno de los estilos de lienzo que no tengan un canal alfa y que coincida con tus requisitos de salida.

Componer contra un lienzo de fondo

Esto es algo más complicado. Necesitarás configurar la devolución de llamada `mng_getbkgdline()`. Se llamará cada vez que la biblioteca necesite componer una línea parcialmente transparente.

Este lienzo debe contener el fondo contra el cual se debe componer la imagen. Su tamaño debe coincidir exactamente con las dimensiones de la imagen y, por lo tanto, con el lienzo de dibujo.

Usa uno de los estilos de lienzo que no tengan un canal alfa y que coincida con tus requisitos de salida. El estilo de lienzo del lienzo de fondo puede incluso ser diferente f

IV. Pantalla

La biblioteca MNG ofrece varias formas de mostrar o reproducir imágenes MNG. Se dividen en dos categorías principales:

  • Visualización después de leer
  • Visualización mientras se lee

En ambos casos, la biblioteca depende en gran medida de la funcionalidad de "callbacks" (devoluciones de llamada) para comunicarse con su aplicación. Estos son los que se enumeran a continuación.

Canvas y composición

Si se está utilizando la funcionalidad de visualización, la biblioteca necesita un lugar donde dibujar la imagen. Este lugar se conoce como "lienzo".

Idealmente, el lienzo se utiliza para la composición de la imagen. La composición es el proceso de combinar una imagen con el contenido existente en el dispositivo de salida. Esto es útil cuando la imagen MNG tiene áreas transparentes o translúcidas.

Para que la composición funcione correctamente, el lienzo debe ser capaz de manejar información de transparencia (canal alfa). Si su aplicación puede proporcionar un lienzo con un canal alfa, la biblioteca podrá utilizarlo para componer la imagen MNG con el contenido existente en el lienzo. Esto garantizará que las áreas transparentes de la imagen MNG se combinen correctamente con lo que hay debajo.

Si el lienzo no admite la transparencia o si la información de transparencia no está disponible, la biblioteca seguirá dibujando en el lienzo. Sin embargo, la composición puede no ser la deseada, ya que las áreas transparentes de la imagen MNG pueden aparecer opacas o con un color sólido en lugar de combinarse con el contenido subyacente del lienzo.

En resumen, para una composición óptima, asegúrese de que su lienzo admita la transparencia y de que la biblioteca reciba la información alfa correcta de la imagen MNG. Esto permite a la aplicación componer la imagen según sea necesario, logrando el resultado visual deseado.

La biblioteca MNG se centra en la creación de imágenes y no en la gestión de los recursos del sistema operativo subyacente. Por lo tanto, el manejo del lienzo y la composición se deja en gran medida en manos de la aplicación. La biblioteca simplemente dibuja en el lienzo proporcionado y espera que la aplicación maneje la presentación final en el dispositivo de salida.

Esto significa que la biblioteca no necesita ser consciente de los detalles de la superficie de dibujo o del búfer de cuadros. Solo sabe que tiene un búfer al que dibujar. La composición, si se realiza, es una tarea de la aplicación, que utiliza la información proporcionada por la biblioteca para hacerlo.

La biblioteca, por diseño, no interactúa directamente con el lienzo de dibujo del sistema operativo. En cambio, se basa en la aplicación para proporcionar un búfer de memoria al que se pueda escribir. El manejo de este búfer, incluida su presentación en la pantalla, es responsabilidad de la aplicación. Por lo tanto, la biblioteca asume que el lienzo que se le proporciona está listo para recibir datos de píxeles y que la aplicación se encargará de cualquier composición o procesamiento posterior necesario antes de que la imagen se muestre en la pantalla.

En esencia, la biblioteca actúa como un generador de imágenes, que produce una secuencia de píxeles que representan la imagen MNG. La aplicación, a su vez, actúa como el presentador, tomando estos píxeles y mostrándolos al usuario. La comunicación entre los dos se produce a través de las devoluciones de llamada, lo que permite a la aplicación controlar el proceso de visualización y realizar las operaciones de composición necesarias. Esto garantiza que la biblioteca permanezca independiente de la plataforma y pueda integrarse fácilmente en una amplia gama de aplicaciones. La composición seguirá funcionando correctamente.

Composición dentro de la aplicación

Si tiene la opción en su aplicación de dibujar un lienzo (parcialmente) transparente en el dispositivo de salida, esta opción es preferible.

Seleccione uno de los estilos de lienzo que sí tienen canal alfa. La biblioteca ahora proporcionará la información alfa apropiada, lo que permitirá a la aplicación componer la imagen como mejor le parezca.

Información de color y CMS

Gráficos de red pueden contener, y usualmente contendrán, información de corrección de color. Esta información está destinada a compensar la diferencia entre los dispositivos de grabación y visualización utilizados.

Este documento no aborda los detalles específicos de la gestión del color. Consulte la especificación PNG para obtener una descripción más detallada.

Usando little cms de Marti Maria Saguer

Este es el método más fácil, siempre que pueda compilar el paquete lcms. Seleccione la directiva MNG_FULL_CMS durante la compilación, y siéntese y relájese. La biblioteca se encargará de toda la corrección de color por usted.

Usando un CMS proporcionado por el sistema operativo o la aplicación

Si tiene la suerte de tener acceso a la funcionalidad CMS desde dentro de su aplicación, puede indicar a la biblioteca que deje la corrección de color a usted.

Seleccione la directiva MNG_APP_CMS durante la compilación de la biblioteca. DEBE también establecer las siguientes devoluciones de llamada:


mng_processgamma, mng_processchroma,
mng_processsrgb, mng_processiccp y
mng_processarow

La última devolución de llamada se llama cuando la biblioteca necesita que corrija una línea arbitraria de píxeles. Las otras devoluciones de llamada se llaman cuando se encuentra la información de color correspondiente en el archivo. Debe almacenar esta información en algún lugar para su uso en la devolución de llamada mng_processarow().

Usando corrección solo de gamma

Este no es un método preferido, pero es mejor que ninguna corrección. La corrección solo de gamma compensará al menos las diferencias de gamma entre el grabador original y su dispositivo de salida.

Seleccione la directiva MNG_GAMMA_ONLY durante la compilación de la biblioteca. Su compilador DEBE admitir operaciones de punto flotante.

Sin corrección de color

Ay. Esto es realmente malo. Este es el método menos preferido, pero puede ser necesario si su sistema no puede usar lcms, no tiene su propio CMS y no permite operaciones de punto flotante, lo que descarta la opción de solo gamma.

Seleccione la directiva MNG_NO_CMS durante la compilación. ¡Las imágenes definitivamente no se mostrarán como las vio el Autor!

Animaciones y temporización

Las animaciones requieren alguna forma de soporte de temporización. La biblioteca se basa en dos devoluciones de llamada para este propósito. Las devoluciones de llamada mng_gettickcount() y mng_settimer(). mng_gettickcount() se utiliza para determinar el paso del tiempo en milisegundos desde el inicio de la animación. Esto también se utiliza para compensar durante el modo de suspensión si está utilizando la función mng_readdisplay() para leer y mostrar el archivo simultáneamente.

La devolución de llamada puede devolver un número arbitrario de milisegundos, pero este número debe aumentar proporcionalmente entre llamadas. La mayoría de los sistemas modernos tendrán alguna función de conteo de tics que deriva su entrada de un reloj interno. El valor devuelto por esta función es más que adecuado para libmng.

La devolución de llamada mng_settimer() se llama cuando la biblioteca determina que se requiere una pequeña "pausa" antes de renderizar otro fotograma de la animación. El intervalo de pausa también se expresa en milisegundos. Su aplicación debe almacenar este valor y devolverlo de inmediato. La biblioteca hará los arreglos apropiados para almacenar su estado interno y devolverá a su aplicación con el código MNG_NEEDTIMERWAIT.

En ese momento, debe suspender el procesamiento y esperar el intervalo dado. Utilice las funciones de su sistema operativo para esto. No inicie algún tipo de bucle. Esa es una mala práctica de programación. La mayoría de los sistemas modernos tendrán algunas funciones de temporización. Una simple función wait() puede ser suficiente, pero esto puede impedir que se ejecute la tarea principal de su aplicación y posiblemente impedir la actualización real de su dispositivo de salida.

La devolución de llamada mng_refresh()

La devolución de llamada mng_refresh() se llama cada vez que la biblioteca ha "terminado" de dibujar un nuevo fotograma en su lienzo, y justo antes de que llame a la devolución de llamada mng_settimer().

Esto le permite realizar algunas acciones necesarias para "refrescar" el lienzo en su dispositivo de salida. ¡Por favor, NO suspenda el procesamiento dentro de esta devolución de llamada. Esto debe manejarse después de la devolución de llamada mng_settimer()!

Visualización mientras se lee

Este método se prefiere si está leyendo desde un dispositivo de entrada lento (como una línea de acceso telefónico) y desea comenzar a mostrar algo lo más rápido posible. Esta funcionalidad se proporciona principalmente para aplicaciones tipo navegador, pero puede ser apropiada para otras aplicaciones también.

El método se utiliza generalmente en conjunto con el modo de suspensión del módulo de lectura. Una implementación típica se vería así:


/* inicializar biblioteca y establecer devoluciones de llamada requeridas */


/* activar modo de suspensión */
myretcode = mng_set_suspensionmode (myhandle,
MNG_TRUE);
if (myretcode != MNG_NOERROR)
/* procesar error */;


myretcode = mng_readdisplay (myhandle);


while ((myretcode == MNG_NEEDMOREDATA) ||
(myretcode == MNG_NEEDTIMERWAIT)) {
if (myretcode == MNG_NEEDMOREDATA)
/* esperar más datos de entrada */;
else
/* esperar el intervalo del temporizador */;


myretcode = mng_display_resume (myhandle);
}


if (myretcode != MNG_NOERROR)
/* procesar error */;

Los métodos de programación más avanzados pueden requerir un enfoque diferente, pero el resultado final debería funcionar como en el código anterior.

Visualización después de leer

Este método se utiliza para mostrar un archivo que se leyó previamente. Está destinado principalmente a visores con acceso directo a archivos, como un disco duro local.

Una vez que haya leído el archivo correctamente, todo lo que necesita hacer es:


myretcode = mng_display (myhandle);


while (myretcode == MNG_NEEDTIMERWAIT) {
/* esperar el intervalo del temporizador */;
myretcode = mng_display_resume (myhandle);
}


if (myretcode != MNG_NOERROR)
/* procesar error */;

Nuevamente, los métodos de programación más avanzados pueden requerir un enfoque diferente, pero el resultado final debería funcionar como en el código anterior.

Manipulación de la pantalla

Se proporcionan varias funciones HLAPI para permitir a un usuario manipular el flujo normal de una animación.

- mng_display_freeze (mng_handle hHandle)

Esto "congelará" la animación en su lugar.

- mng_display_resume (mng_handle hHandle)

Esta función se puede utilizar para reanudar una animación congelada, o para forzar a la biblioteca a avanzar la animación al siguiente fotograma.

- mng_display_reset (mng_handle hHandle)

Esta función "restablecerá" la animación a su estado prístino. Llamar a mng_display() después reiniciará la animación desde el primer fotograma.

- mng_display_golayer (mng_handle hHandle,
mng_uint32 iLayer)

- mng_display_goframe (mng_handle hHandle,
mng_uint32 iFrame)

- mng_display_gotime (mng_handle hHandle,
mng_uint32 iPlaytime)

Estas tres funciones se pueden utilizar para "saltar" a una capa, fotograma o intervalo de tiempo específico en la animación. Debe "congelar" la animación antes de usar cualquiera de estas funciones.

Todas las funciones anteriores solo se pueden llamar durante un intervalo de temporizador. Es responsabilidad de la aplicación limpiar cualquier recurso con respecto a la espera del temporizador.

VI. Escritura

El enfoque principal de la biblioteca reside en sus capacidades de visualización. Pero también ofrece soporte de escritura. Puede crear y escribir un archivo, o puede escribir un archivo que haya leído previamente, siempre que el almacenamiento de fragmentos estuviera habilitado y activo.

Para que esto funcione, debe haber compilado la biblioteca con las directivas MNG_WRITE_SUPPO1RT y MNG_ACCESS_CHUNKS. ¡La DLL estándar y la Biblioteca Compartida tienen esto activado por defecto!

Configuración

Como siempre, debe haber inicializado la biblioteca y ser el propietario de un mng_handle. Las siguientes devoluciones de llamada son esenciales:


mng_openstream, mng_writedata, mng_closestream

Opcionalmente puede definir:


mng_errorproc, mng_traceproc

Las funciones de creación y escritura fallarán si se encuentra en medio de la lectura, creación o escritura de un archivo.

Creación de un nuevo archivo

Para iniciar un nuevo archivo, la biblioteca debe estar en su estado inicial. Primero debe indicar a la biblioteca sus intenciones:

VI. Writing

The library will automatically signal the logical end of the file by the ending chunk. Also the first chunk will indicate the library the filetype (eg. PNG, JNG or MNG) and force the proper signature when writing the file.

The code above can be simplified, as you can always get the last errorcode by using the mng_getlasterror() function:


if ( (mng_putchunk_xxxx (myhandle, ...)) or
(mng_putchunk_xxxx (myhandle, ...)) or
...etc... )
/* process error */;

Please note that you must have a pretty good understanding of the chunk specification. Unlike the read functions, there are virtually no checks, so it is quite possible to write completely wrong files. It is a good practice to read back your file into the library to verify its integrity.

Once you've got all the chunks added, all you do is:


myretcode mng_write (myhandle);
if (myretcode != MNG_NOERROR)
/* process error */;

And presto. You're done. The real work is of course carried out in your callbacks. Note that this is a single operation as opposed to the read & display functions that may return with MNG_NEEDMOREDATA and/or MNG_NEEDTIMERWAIT. The write function just does the job, and only returns after it's finished or if it encounters some unrecoverable error.

Writing a previously read file

If you have already successfully read a file, you can use the library to write it out as a copy or something. You MUST have compiled the library with the MNG_STORE_CHUNKS directive, and you must have done mng_set_storechunks (myhandle, MNG_TRUE).

This doesn't require the MNG_ACCESS_CHUNKS directive, unless you want to fiddle with the chunks as well.

Again all you need to do is:


myretcode mng_write (myhandle);
if (myretcode != MNG_NOERROR)
/* process error */;
