libinn_dbz(3) Documentación de InterNetNews libinn_dbz(3)

NOMBRE

dbz - Rutinas de base de datos para InterNetNews

SINOPSIS

#include <inn/dbz.h>
#define DBZMAXKEY              ...
#define DBZ_INTERNAL_HASH_SIZE ...
typedef enum
{
    DBZSTORE_OK,
    DBZSTORE_EXISTS,
    DBZSTORE_ERROR
} DBZSTORE_RESULT;
typedef enum
{
    INCORE_NO,
    INCORE_MEM,
    INCORE_MMAP
} dbz_incore_val;
typedef struct {
    bool writethrough;
    dbz_incore_val pag_incore;
    dbz_incore_val exists_incore;
    bool nonblock;
} dbzoptions;
typedef struct {
    char hash[DBZ_INTERNAL_HASH_SIZE];
} __attribute__((__packed__)) erec;
extern bool dbzinit(const char *name);
extern bool dbzclose(void);
extern bool dbzfresh(const char *name, off_t size);
extern bool dbzagain(const char *name, const char *oldname);
extern bool dbzexists(const HASH key);
extern bool dbzfetch(const HASH key, off_t *value);
extern DBZSTORE_RESULT dbzstore(const HASH key, off_t data);
extern bool dbzsync(void);
extern long dbzsize(off_t contents);
extern void dbzsetoptions(const dbzoptions options);
extern void dbzgetoptions(dbzoptions *options);

DESCRIPCIÓN

Estas funciones proporcionan un sistema de indexación para un acceso aleatorio rápido a un archivo de texto, en adelante denominado el archivo base.

dbz almacena desplazamientos dentro del archivo base para una recuperación rápida. Todas las recuperaciones se basan en un valor hash que se genera mediante la función HashMessageID en libinn(3).

dbzinit abre una base de datos, un índice del archivo base name, que consta de los archivos name.dir, name.index y name.hash, los cuales deben existir previamente. (Si la base de datos es nueva, deberían ser archivos de longitud cero). Los accesos posteriores van a esa base de datos hasta que se llama a dbzclose para cerrarla. Cuando se utiliza el formato hash etiquetado (si se proporcionó --enable-tagged-hash al configurar), se utiliza un archivo name.pag en lugar de .index y .hash.

dbzfetch busca en la base de datos la clave key especificada, asignando el desplazamiento del archivo base para la key correspondiente a value, si existe.

dbzstore almacena el par clave-datos key-data en la base de datos. Devolverá "DBZSTORE_EXISTS" para duplicados (entradas que ya existen) y "DBZSTORE_OK" para éxito. Fallará con "DBZSTORE_ERROR" si los archivos de la base de datos no son escribibles o no están abiertos, o si ocurre cualquier otro error.

dbzexists verificará si el hash dado existe o no. dbz está optimizado para esta operación y puede ser significativamente más rápido que dbzfetch.

dbzfresh es una variante de dbzinit para crear una nueva base de datos con mayor control sobre los detalles. El parámetro size especifica el tamaño de la primera tabla hash dentro de la base de datos, en número de pares clave-valor. El rendimiento será mejor si el número de pares clave-valor almacenados en la base de datos no excede aproximadamente 2/3 de size, o 1/2 de size cuando se utiliza el formato hash etiquetado. (La función dbzsize, dado el número esperado de pares clave-valor, sugerirá un tamaño de base de datos que cumpla estos criterios.) Suponiendo que un desplazamiento fseek sea de 4 bytes, el archivo .index tendrá 4 * size bytes. El archivo .hash tendrá "DBZ_INTERNAL_HASH_SIZE" * size bytes (el archivo .dir es diminuto y de tamaño aproximadamente constante) hasta que el número de pares clave-valor exceda aproximadamente el 80% de size. (Nada terrible sucederá si la base de datos crece más allá del 100% de size, pero los accesos se ralentizarán bastante y los archivos .index y .hash crecerán un poco).

dbz almacena hasta "DBZ_INTERNAL_HASH_SIZE" bytes (por defecto, 4 bytes si se usa el formato hash etiquetado, 6 en caso contrario) del hash del Message-ID en el archivo .hash para confirmar un acierto. Esto elimina la necesidad de leer el archivo base para manejar colisiones.

Un size de 0 dado a dbzfresh es sinónimo del valor predeterminado local; el valor predeterminado normal es adecuado para tablas de aproximadamente 6.000.000 pares clave-valor (o 500.000 pares clave-valor cuando se utiliza el formato hash etiquetado). Ese valor predeterminado es utilizado por dbzinit.

Cuando las bases de datos se regeneran periódicamente, como es el caso del archivo history, lo más sencillo es elegir los parámetros para una nueva base de datos basándose en la antigua. Esto también permite alguna memoria de los tamaños pasados de la base de datos antigua, de modo que se pueda elegir un nuevo tamaño de base de datos para cubrir las fluctuaciones esperadas. dbzagain es una variante de dbzinit para crear una nueva base de datos como una nueva generación de una base de datos antigua. Los archivos de la base de datos para oldname deben existir. dbzagain es equivalente a llamar a dbzfresh con un size igual al resultado de aplicar dbzsize al mayor número de entradas en la base de datos oldname y sus 10 generaciones anteriores.

Cuando se realizan muchos accesos por el mismo programa, dbz es masivamente más rápido si su primera tabla hash está en memoria. Si el flag pag_incore se establece en "INCORE_MEM", se intenta leer la tabla en memoria cuando se abre la base de datos, y dbzclose la escribe de nuevo en disco (si se leyó correctamente y se ha modificado). dbzsetoptions se puede usar para establecer los flags pag_incore y exists_incore a diferentes valores que deberían ser "INCORE_NO" (leer desde disco), "INCORE_MEM" (leer desde memoria) o "INCORE_MMAP" (leer desde un archivo mmap'ed) para los archivos .hash y .index por separado; esto no afecta al estado de una base de datos que ya se ha abierto. El valor predeterminado es "INCORE_NO" para el archivo .index y "INCORE_MMAP" para el archivo .hash. El intento de leer la tabla puede fallar debido a falta de memoria; en ese caso, dbz falla con un error. Los almacenamientos en una base de datos en memoria no se escriben (en general) en el archivo hasta dbzclose o dbzsync, por lo que si la robustez en presencia de fallos o accesos concurrentes es crucial, es probable que se deban evitar las bases de datos en memoria o que la opción writethrough se establezca a true (indicando que se escriba sistemáticamente en el sistema de archivos además de actualizar la base de datos en memoria).

Si la opción nonblock es verdadera, las escrituras en los archivos .hash y .index se realizarán utilizando E/S no bloqueante. Esto puede ser significativamente más rápido si su plataforma soporta E/S no bloqueante con archivos. Solo es aplicable si no está usando mmap para la base de datos.

dbzsync provoca que todos los búferes, etc., se vacíen a los archivos. Se suele utilizar como precaución contra fallos o accesos concurrentes cuando un proceso que utiliza dbz se ejecutará durante mucho tiempo. Es una operación algo costosa, especialmente para una base de datos en memoria.

La lectura concurrente de bases de datos es bastante segura, pero no hay bloqueo (interbloqueo), por lo que la actualización concurrente no lo es.

Una base de datos abierta ocupa tres flujos stdio y dos descriptores de archivo; el consumo de memoria es insignificante excepto para bases de datos en memoria (y búferes stdio).

DIAGNÓSTICOS

Las funciones que devuelven valores bool devuelven true para éxito, false para fallo.

dbzinit intenta tener errno establecido de manera plausible al regresar, pero por lo demás esto no está garantizado. Un errno de "EDOM" de dbzinit indica que la base de datos no parecía estar en formato dbz.

Si se define "DBZTEST" en tiempo de compilación, entonces se incluirá una función main(). Esto realizará pruebas de rendimiento y de integridad.

ERRORES

A diferencia de dbm, dbz se negará a dbzstore con una clave que ya esté en la base de datos. El usuario es responsable de evitar esto.

El mapeador de mayúsculas y minúsculas de RFC5322 implementa solo una primera aproximación a las reglas de mayúsculas y minúsculas terriblemente complejas de RFC5322.

dbz ya no intenta ser compatible en cuanto a llamadas con dbm de ninguna manera.

libinn_dbz(3) — INN 2.7.3

NAME

libinn_dbz, dbz_open, dbz_close, dbz_fetch, dbz_store, dbz_delete — INN database access

SYNOPSIS

#include <libinn.h>

DBZ *dbz_open(const char *path, const char *mode);

int dbz_close(DBZ *dbz);

char *dbz_fetch(DBZ *dbz, const char *key);

int dbz_store(DBZ *dbz, const char *key, const char *value);

int dbz_delete(DBZ *dbz, const char *key);

DESCRIPTION

The functions dbz_open, dbz_close, dbz_fetch, dbz_store, and dbz_delete are used to access the INN database files. The database files are plain text files with a specific format that is not specified here.

The dbz_open function opens a database file located at path with the specified mode. The mode can be "r" (read-only), "w" (write-only, truncating the file if it exists), or "a" (append-only, creating the file if it does not exist). It returns a pointer to a DBZ structure on success, or NULL on failure.

The dbz_close function closes the database file associated with the DBZ pointer dbz. It returns 0 on success, or -1 on failure.

The dbz_fetch function retrieves the value associated with the specified key from the database. It returns a pointer to the value on success, or NULL on failure or if the key is not found. The returned pointer points to dynamically allocated memory that must be freed by the caller using free.

The dbz_store function stores the association between key and value in the database. It returns 0 on success, or -1 on failure. If the key already exists, its value is updated.

The dbz_delete function removes the association for the specified key from the database. It returns 0 on success, or -1 on failure.

DIAGNOSTICS

Error messages are printed to standard error.

BUGS

This implementation has limitations on the size of keys and values. The underlying database format is simple and may not be suitable for large amounts of data.

HISTORY

The original database access functions were written by Spencer <henry@zoo.toronto.edu> as part of the C News project. The MD5 code was borrowed from RSA. Extensive reworking was done by Clayton O'Neill <coneill@oneill.net> to remove backwards compatibility and add hashes into dbz files. This documentation was rewritten into POD by Julien Elie.
