NOMBRE

libcurl-thread - seguridad de hilos de libcurl

Multihilo con libcurl

libcurl es seguro para hilos pero no tiene sincronización interna de hilos. Es posible que tenga que proporcionar sus propios bloqueos si se encuentra con alguna de las excepciones de seguridad de hilos a continuación.

Manéjadores

Nunca debe compartir el mismo manejador en múltiples hilos. Puede pasar los manejadores entre hilos, pero nunca debe usar un único manejador desde más de un hilo en ningún momento determinado.

Objetos compartidos

Puede compartir ciertos datos entre múltiples manejadores utilizando la interfaz de compartir, pero debe proporcionar su propio bloqueo y configurar curl_share_setopt(3) con CURLSHOPT_LOCKFUNC y CURLSHOPT_UNLOCKFUNC.

Tenga en cuenta que algunos elementos están específicamente documentados como no seguros para hilos en la API de compartir (el grupo de conexiones y la caché HSTS, por ejemplo).

TLS

Todas las bibliotecas TLS actuales que soporta libcurl son seguras para hilos.

OpenSSL
OpenSSL 1.1.0+ se puede usar de forma segura en aplicaciones multihilo siempre que el soporte para la API de subprocesos del sistema operativo subyacente esté incorporado. Para versiones anteriores de OpenSSL, el usuario debe configurar devoluciones de llamada de mutex.

Es posible que libcurl no pueda limpiar completamente después de OpenSSL multihilo, dependiendo de cómo se compiló y cargó OpenSSL como biblioteca. Es posible, en raras circunstancias, que ocurra una fuga de memoria, a menos que implemente su propia limpieza de hilos de OpenSSL.

Por ejemplo, en Windows, si tanto libcurl como OpenSSL están enlazados estáticamente a una DLL o aplicación, entonces OpenSSL puede filtrar memoria a menos que la DLL o aplicación llame a OPENSSL_thread_stop() antes de que cada hilo termine. Si OpenSSL se compila como una DLL, lo hace automáticamente y no hay fugas. Si libcurl se compila como una DLL y OpenSSL está enlazado estáticamente a ella, entonces libcurl realiza esta limpieza automáticamente y no hay fugas (añadido en libcurl 8.8.0).

Por favor, revise la documentación de OpenSSL para obtener una lista completa de circunstancias: https://docs.openssl.org/3.0/man3/OPENSSL_init_crypto/#notes

Señales

Las señales se utilizan para establecer tiempos de espera de resolución de nombres (durante la búsqueda de DNS), cuando se compila sin usar los backends c-ares o de resolución de hilos. En sistemas que tienen un concepto de señal.

Al usar múltiples hilos, debe establecer la opción CURLOPT_NOSIGNAL(3) en 1L para todos los manejadores. Todo funciona bien, excepto que los tiempos de espera no se pueden honrar durante las búsquedas de DNS, lo que puede solucionar compilando libcurl con soporte para c-ares o de resolución de hilos. c-ares es una biblioteca que proporciona resolución de nombres asíncrona. En algunas plataformas, libcurl simplemente no puede funcionar correctamente en multihilo a menos que se establezca la opción CURLOPT_NOSIGNAL(3).

Cuando CURLOPT_NOSIGNAL(3) se establece en 1L, su aplicación necesita lidiar con el riesgo de SIGPIPE (que al menos el backend de OpenSSL puede activar). Tenga en cuenta que establecer CURLOPT_NOSIGNAL(3) en 0L no funciona en una situación de hilos, ya que existe una condición de carrera en la que libcurl corre el riesgo de restaurar el controlador de señales anterior mientras otro hilo aún debería ignorarlo.

Resolución de nombres

Las llamadas del sistema gethostbyname o getaddrinfo y otras llamadas de resolución de nombres utilizadas por libcurl son proporcionadas por su sistema operativo y deben ser seguras para hilos. Es importante que libcurl pueda encontrar y utilizar versiones seguras para hilos de estas y otras llamadas del sistema, ya que de lo contrario no puede funcionar completamente seguro para hilos. Se sabe que algunos sistemas operativos tienen implementaciones de hilos defectuosas. Anteriormente hemos recibido informes de problemas en *BSD (al menos en el pasado, puede que funcionen bien hoy en día). Algunos sistemas operativos que se sabe que tienen soporte sólido y funcional para hilos son Linux, Solaris y Windows.

Funciones curl_global_*

Estas funciones son seguras para hilos desde libcurl 7.84.0 si curl_version_info(3) tiene activado el bit de característica CURL_VERSION_THREADSAFE (en la mayoría de las plataformas).

Si estas funciones no son seguras para hilos y está utilizando libcurl con múltiples hilos, es especialmente importante que antes de usarlas llame a curl_global_init(3) o curl_global_init_mem(3) para inicializar explícitamente la biblioteca y sus dependencias, en lugar de depender de la inicialización de seguridad de último recurso "perezosa" que ocurre la primera vez que se llama a curl_easy_init(3). Para una explicación detallada, consulte la sección CONSTANTES GLOBALES de libcurl(3).

Funciones de memoria

Estas funciones, proporcionadas por su sistema operativo o por sus propios reemplazos, deben ser seguras para hilos. Puede usar curl_global_init_mem(3) para configurar sus propias funciones de memoria de reemplazo.

Funciones no seguras

CURLOPT_DNS_USE_GLOBAL_CACHE(3) no es seguro para hilos.

curl_version_info(3) no es seguro para hilos antes de la inicialización de libcurl.
