DESCRIPCIÓN

systemd-stub (almacenado en archivos por arquitectura linuxx64.efi.stub, linuxia32.efi.stub, linuxaa64.efi.stub en disco) es un simple stub de arranque UEFI. Un stub de arranque UEFI se adjunta a una imagen binaria del kernel de Linux, y es una pieza de código que se ejecuta en el entorno del firmware UEFI antes de pasar al entorno del kernel de Linux. El stub de arranque UEFI asegura que un kernel de Linux sea ejecutable como un binario UEFI normal, y es capaz de realizar varias preparaciones antes de cambiar el sistema al mundo Linux.

El stub de arranque UEFI busca varios recursos para la invocación del kernel dentro del propio binario PE de UEFI. Esto permite combinar varios recursos dentro de una única imagen binaria PE ("Unified Kernel Image" o "UKI" para abreviar), que luego puede ser firmada mediante UEFI SecureBoot en su totalidad, cubriendo todos los recursos individuales a la vez. Específicamente, puede incluir las siguientes secciones PE:

•Una sección ".linux" con la imagen del kernel de Linux ELF. Esta sección es obligatoria.
•Una sección opcional ".osrel" con información de la versión del SO, es decir, el contenido del archivo os-release(5) del SO al que pertenece el kernel.
•Una sección opcional ".cmdline" con la línea de comandos del kernel que se pasará al kernel invocado.
•Una sección opcional ".initrd" con el initrd.
•Una sección opcional ".ucode" con un initrd que contiene microcódigo, para ser entregado al kernel antes que cualquier otro initrd. Este initrd no debe estar comprimido.
•Una sección opcional ".splash" con una imagen (en formato .BMP de Windows) para mostrar en pantalla antes de invocar el kernel.
•Una sección opcional ".dtb" con un Dispositivo de árbol compilado en binario.
•Cero o más secciones ".dtbauto". systemd-stub siempre usará la primera que coincida. La coincidencia se realiza tomando la primera cadena de "compatible" del Dispositivo de árbol de los "compatible" proporcionados por el firmware en las tablas de configuración y comparándola con la primera cadena de "compatible" de cada una de las secciones ".dtbauto". Si el firmware no proporciona un Dispositivo de árbol, la coincidencia se realiza utilizando la sección ".hwids" en su lugar. Después de seleccionar una sección ".hwids" (ver la descripción a continuación), la cadena "compatible" de esa sección se utilizará para realizar el mismo procedimiento de coincidencia. Si se encuentra una coincidencia, esa sección ".dtbauto" se cargará y anulará la sección ".dtb" si está presente.
•Cero o más secciones ".efifw" para la imagen del firmware. Funciona de manera similar a las secciones ".dtbauto". systemd-stub siempre usará la primera que coincida. La coincidencia se realiza seleccionando primero la entrada más apropiada en la sección ".hwids" basada en los IDs de hardware proporcionados por SMBIOS (ver abajo). Si se encuentra una entrada adecuada, la cadena "fwid" de esa entrada se utilizará para realizar el procedimiento de coincidencia para los blobs de firmware en la sección ".efifw". Se cargará el primer firmware coincidente.
•Cero o más secciones ".hwids" con los IDs de hardware de las máquinas para hacer coincidir los Dispositivos de árbol. systemd-stub utilizará los datos de SMBIOS para calcular los IDs de hardware de la máquina (según la especificación[1]), y luego intentará encontrar alguno de ellos en cada una de las secciones ".hwids". Se utilizará la primera sección coincidente.
•Una sección opcional ".uname" con información de la versión del kernel, es decir, la salida de uname -r para el kernel incluido en la sección ".linux".
•Una sección opcional ".sbat" con metadatos de revocación de SBAT[2].
•Una sección opcional ".pcrsig" con un conjunto de firmas criptográficas para los valores esperados de PCR de TPM2 después de que el kernel se haya iniciado, en formato JSON. Esto es útil para implementar políticas de TPM2 que vinculan el cifrado de disco y similares a kernels que están firmados por una clave específica.
•Una sección opcional ".pcrpkey" con una clave pública en formato PEM que coincide con los datos de firma en la sección ".pcrsig".

En una UKI básica, las secciones enumeradas anteriormente aparecen como máximo una vez, con la excepción de las secciones ".dtbauto" y ".hwids". En una UKI multiperfil, múltiples conjuntos de estas secciones están presentes en un solo archivo y forman "perfiles", uno de los cuales se puede seleccionar al arrancar. Para ello, se define la sección PE ".profile" para que se utilice como separador entre conjuntos de secciones. La sección ".profile" en sí misma puede contener metainformación sobre la sección, y sigue una estructura similar al contenido de la sección ".osrel". Para más detalles sobre UKIs multiperfil, ver abajo.

Si UEFI SecureBoot está habilitado y la sección ".cmdline" está presente en la imagen ejecutada, se ignorarán los intentos de anular la línea de comandos del kernel pasándola como parámetros de invocación al binario EFI. Por lo tanto, para permitir la anulación de la línea de comandos del kernel, deshabilite UEFI SecureBoot o no incluya una sección PE de línea de comandos del kernel en el archivo de imagen del kernel. Si se acepta una línea de comandos a través de parámetros de invocación de EFI al binario de EFI, se medirá en el TPM PCR 12 (si hay un TPM presente).

Si un Dispositivo de árbol está incrustado en la sección ".dtb", reemplaza un Dispositivo de árbol existente en la tabla de configuración de EFI correspondiente. systemd-stub solicitará al firmware a través del "EFI_DT_FIXUP_PROTOCOL" las correcciones específicas del hardware al Dispositivo de árbol.

El contenido de 11 de estas 12 secciones se mide en el TPM PCR 11. De lo contrario, no se utiliza y, por lo tanto, el resultado se puede precalcular sin demasiado esfuerzo. La sección ".pcrsig" no se incluye en esta medición de PCR, ya que se supone que contiene firmas para la salida de la operación de medición, y por lo tanto no puede ser también una entrada para ella. Si una UKI contiene múltiples perfiles, solo se miden las secciones PE del perfil seleccionado (y las del perfil base, excepto si se anulan).

Si es distinto de cero, el perfil numérico seleccionado se mide en el PCR 12.

Cuando las secciones ".pcrsig" y/o ".pcrpkey" están presentes en una imagen de kernel unificada, su contenido se pasa al kernel arrancado en un archivo de initrd cpio sintético que los coloca en los archivos /.extra/tpm2-pcr-signature.json y /.extra/tpm2-pcr-public-key.pem. Típicamente, una línea de tmpfiles.d(5) asegura entonces que se copien a /run/systemd/tpm2-pcr-signature.json y /run/systemd/tpm2-pcr-public-key.pem donde permanecen accesibles incluso después de que el sistema transicione del entorno initrd al sistema de archivos del host. Herramientas como systemd-cryptsetup@.service(8), systemd-cryptenroll(1) y systemd-creds(1) usarán automáticamente los archivos presentes en estas rutas para desbloquear recursos protegidos (almacenamiento cifrado o credenciales) o vincular el cifrado a kernels arrancados.

Para más detalles sobre el concepto de UKI, ver la especificación de UKI[3].

ARCHIVOS COMPAÑEROS

El stub de arranque UEFI systemd-stub recopila automáticamente tres tipos de archivos auxiliares compañeros colocados opcionalmente en directorios de caída en la misma partición que el binario EFI, genera dinámicamente archivos initrd de cpio a partir de ellos y los pasa al kernel.

Este sitio no está asociado de ninguna forma con Arch Linux ni afiliado a este proyecto. El contenido es únicamente una traducción de las páginas del manual de Arch publicadas en man.archlinux.org.

Específicamente:

• Para un binario de kernel llamado foo.efi, buscará archivos con la extensión .cred en un directorio llamado foo.efi.extra.d/ adyacente. Si el binario del kernel utiliza un contador para el propósito de **Evaluación Automática de Arranque**[4], este contador se ignorará. Por ejemplo, foo+3-0.efi buscará en el directorio foo.efi.extra.d/. Se genera un archivo **cpio** a partir de todos los archivos encontrados de esa manera, colocándolos en el directorio /.extra/credentials/ de la jerarquía de archivos initrd. El initrd principal podrá entonces acceder a ellos en este directorio. Esto está destinado a almacenar credenciales auxiliares, cifradas y autenticadas para su uso con LoadCredentialEncrypted en la Partición del Sistema UEFI. Consulte systemd.exec(5) y systemd-creds(1) para obtener detalles sobre credenciales cifradas. El archivo **cpio** generado se mide en el TPM PCR 12 (si hay un TPM presente).
• De manera similar, los archivos foo.efi.extra.d/*.sysext.raw se empaquetan en un archivo **cpio** y se colocan en el directorio /.extra/sysext/ en la jerarquía de archivos initrd. Esto está destinado a pasar imágenes de extensión del sistema adicionales específicas de UKI al initrd. Consulte systemd-sysext(8) para obtener detalles sobre las imágenes de extensión del sistema. El archivo **cpio** generado que contiene estas imágenes de extensión del sistema se mide en el TPM PCR 13 (si hay un TPM presente).
• De manera similar, los archivos /loader/extensions/*.sysext.raw se empaquetan en un archivo **cpio** y se colocan en el directorio /.extra/global_sysext/ en la jerarquía de archivos initrd. Esto está destinado a pasar imágenes de extensión del sistema globales adicionales al initrd. Consulte systemd-sysext(8) para obtener detalles sobre las imágenes de extensión del sistema. El archivo **cpio** generado que contiene estas imágenes de extensión del sistema se mide en el TPM PCR 13 (si hay un TPM presente).
• De manera similar, los archivos foo.efi.extra.d/*.confext.raw se empaquetan en un archivo **cpio** y se colocan en el directorio /.extra/confext/ en la jerarquía de archivos initrd. Esto está destinado a pasar imágenes de extensión de configuración adicionales específicas de UKI al initrd. Consulte systemd-confext(8) para obtener detalles sobre las imágenes de extensión de configuración. El archivo **cpio** generado que contiene estas imágenes de extensión de configuración se mide en el TPM PCR 12 (si hay un TPM presente).
• De manera similar, los archivos /loader/extensions/*.confext.raw se empaquetan en un archivo **cpio** y se colocan en el directorio /.extra/global_confext/ en la jerarquía de archivos initrd. Esto está destinado a pasar imágenes de extensión de configuración globales adicionales al initrd. Consulte systemd-confext(8) para obtener detalles sobre las imágenes de extensión de configuración. El archivo **cpio** generado que contiene estas imágenes de extensión de configuración se mide en el TPM PCR 12 (si hay un TPM presente).
• De manera similar, los archivos foo.efi.extra.d/*.addon.efi se cargan y verifican como binarios PE, y se cargan secciones específicas de ellos. Los complementos se utilizan para pasar parámetros adicionales de la línea de comandos del kernel (sección ".cmdline"), o blobs de DeviceTree (sección ".dtb"), initrds adicionales (sección ".initrd") y actualizaciones de microcódigo (sección ".ucode"). Los complementos permiten que estos recursos se pasen independientemente de la versión del kernel que se esté iniciando, permitiendo, por ejemplo, que los proveedores de plataformas envíen configuraciones específicas de la plataforma.

En caso de que Secure Boot esté habilitado, estos archivos se validarán utilizando claves en la base de datos UEFI (DB), la DB de Shim o MOK de Shim, y solo se cargarán si la verificación es exitosa. Además, si tanto el complemento como el UKI contienen una sección ".uname", el complemento será rechazado si no coinciden exactamente. Se recomienda agregar siempre una sección ".sbat" a todos los complementos firmados, para que puedan ser revocados con una actualización de la política SBAT, sin requerir inclusión en listas negras a través de DBX/MOKX. La herramienta ukify(1) agregará una política SBAT por defecto si no se proporciona ninguna al crear complementos. Para obtener más información sobre SBAT, consulte la **documentación de Shim**[2].

Los archivos de complemento se ordenan, cargan y miden en el TPM PCR 12 (si hay un TPM presente) y se agregan a la línea de comandos del kernel. Las opciones de la línea de comandos del UKI se enumeran primero, luego las opciones de los complementos en /loader/addons/*.addon.efi, y finalmente los complementos específicos del UKI. Los blobs del árbol de dispositivos se cargan y miden siguiendo el mismo algoritmo. Los complementos de microcódigo se pasan al kernel en orden inverso (complementos específicos del UKI, complementos globales, sección incrustada del UKI). Esto se debe a que el controlador de actualización de microcódigo se detiene en el primer nombre de archivo coincidente. Los complementos siempre se cargan en el mismo orden según el nombre de archivo, de modo que, dado el mismo conjunto de complementos, se puede esperar el mismo conjunto de mediciones en PCR12. Sin embargo, tenga en cuenta que el nombre de archivo no está protegido por la firma PE, y como tal, un atacante con acceso de escritura al ESP podría potencialmente renombrar estos archivos para cambiar el orden en que se cargan, de una manera que podría alterar la funcionalidad del kernel, ya que algunas opciones podrían depender del orden. Si firma dichos complementos, debe prestar atención a los valores de PCR12 y utilizar un servicio de atestación para que el uso indebido de sus complementos firmados pueda ser detectado y tratado utilizando uno de los mecanismos de revocación mencionados anteriormente.

• Los archivos /loader/credentials/*.cred se empaquetan en un archivo **cpio** y se colocan en el directorio /.extra/global_credentials/ de la jerarquía de archivos initrd. Esto está destinado a pasar credenciales adicionales al initrd, independientemente de la versión del kernel que se esté iniciando. El archivo **cpio** generado se mide en el TPM PCR 12 (si hay un TPM presente).
• Además, los archivos /loader/addons/*.addon.efi se cargan y verifican como binarios PE, y se analizan las secciones ".cmdline", ".dtb", ".initrd" y ".ucode" de ellos. Esto está destinado a pasar parámetros adicionales de la línea de comandos, blobs de DeviceTree, initrds y actualizaciones de microcódigo al kernel, independientemente de la versión del kernel que se esté iniciando.

Estos mecanismos pueden utilizarse para parametrizar y extender imágenes initrd inmutables y confiables (es decir, firmadas) de una manera razonablemente segura: todos los datos que contienen se miden en los PCR de TPM. Al acceder, deben validarse aún más: en el caso de las credenciales, cifrándolas/autenticándolas a través de TPM, como expone systemd-creds encrypt -T (consulte systemd-creds(1) para obtener detalles); en el caso de las imágenes de extensión del sistema, utilizando imágenes Verity firmadas.

UKIS MULTIPERFIL

En muchos contextos es útil permitir la invocación de un único UKI en múltiples modos diferentes (o "perfiles") sin comprometer la integridad criptográfica, las mediciones, etc. del proceso de arranque. Por ejemplo, un único UKI podría proporcionar tres perfiles distintos: uno de arranque normal, uno que invoca una operación de "restablecimiento de fábrica" y uno que arranca en un modo de destino de almacenamiento (como en systemd-storagetm.service(8)). Cada perfil utilizaría entonces las mismas secciones ".linux" y ".initrd", pero tendría una sección ".cmdline" separada. Por ejemplo, los dos últimos perfiles extenderían la línea de comandos normal del kernel con "systemd.unit=factory-reset.target" o "rd.systemd.unit=storagetm.target".

Un único UKI puede admitir múltiples perfiles mediante la sección especial PE ".profile". Esta sección actúa como separador entre las secciones PE de los perfiles individuales. Por lo tanto, las secciones PE ".profile" pueden aparecer varias veces en un único UKI, y las otras secciones PE enumeradas anteriormente también pueden aparecer varias veces, si se utilizan ".profile", pero solo una vez antes de la primera sección ".profile", una vez entre cada par subsiguiente y una vez después de la última aparición de ".profile". Las secciones listadas antes de la primera sección ".profile" se consideran el perfil "base" del UKI. Cada sección ".profile" introduce entonces un nuevo perfil, que se numera a partir de cero. Las secciones PE que siguen a cada ".profile" son específicas de ese perfil. Al arrancar en un perfil específico, los perfiles de la sección base se utilizan en combinación con las secciones del perfil específico: si la misma sección se define en ambos, la sección por perfil anula la versión del perfil base, de lo contrario se utilizan las secciones del perfil base.

Un UKI que no contiene ningún ".profile" se considera equivalente a uno que solo contiene un ".profile", ya que solo tiene un perfil " @0".

Aquí hay un ejemplo simple de las secciones de un UKI multiperfil, inspirado en la configuración sugerida anteriormente:

Tabla 1. Ejemplo de UKI multiperfil

Sección Perfil
".linux" Perfil base
".osrel"
".cmdline"
".initrd"
".profile" Perfil @0
".profile" Perfil @1
".cmdline"
".profile" Perfil @2
".cmdline"

La lista de secciones anterior definiría tres perfiles. Las cuatro primeras secciones constituyen el perfil base. Una sección ".profile" introduce entonces el perfil @0. No anula ninguna sección (ni añade ninguna) de la sección base, por lo que le sigue inmediatamente otra sección ".profile" que introduce la sección @1. Este perfil anula la línea de comandos del kernel. Finalmente, las dos últimas secciones definen la sección @2, que también anula la línea de comandos. (Tenga en cuenta que en este ejemplo, el primer ".cmdline" también podría haberse movido detrás del primer ".profile" con un efecto equivalente. Para mantener las cosas bien extensibles, probablemente sea una buena idea mantener la línea de comandos genérica en la sección base en lugar del perfil 0, en caso de que los perfiles añadidos posteriormente deseen reutilizarla).

El perfil a iniciar puede controlarse a través de la propia línea de comandos del UKI: si el primer argumento comienza con "@", seguido de un número entero positivo en decimal, selecciona el perfil en el que arrancar. Si el primer argumento no se especifica de esa manera, el UKI arrancará automáticamente en el perfil 0.

Una sección ".profile" puede contener metadatos sobre el perfil. Sigue un formato similar a ".osrel" (es decir, una lista de cadenas separadas por saltos de línea, similar a un bloque de asignación de variables de entorno). Actualmente hay dos campos definidos: "ID=" debe contener una cadena de identificación corta que identifique el perfil (es decir, un nombre corto como "reset", "storage" o "debug").

.g. "ID=factory-reset"). "TITLE=" debe contener una cadena legible por humanos que puede aparecer en la entrada del menú de arranque para este perfil (por ejemplo, "TITLE='Restablecer dispositivo de fábrica'").

NOTAS SOBRE TPM PCR

Tenga en cuenta que cuando se invoca un kernel unificado que utiliza systemd-stub, el firmware lo medirá en su totalidad en el PCR 4 del TPM, cubriendo todos los recursos integrados, como el código stub en sí, el kernel principal, el initrd integrado y la línea de comandos del kernel (ver arriba para una lista completa), incluyendo todos los perfiles de UKI.

Tenga en cuenta también que cuando systemd-stub mide una sección PE, medirá la cantidad de bytes que ocupa la sección en memoria (VirtualSize) y no la cantidad de bytes que ocupa la sección en disco (SizeOfRawData). Esto significa que si el tamaño en memoria es mayor que el tamaño en disco, systemd-stub terminará midiendo ceros adicionales. Para evitar que esto suceda, se recomienda asegurarse de que el tamaño en memoria de cada sección medida por systemd-stub sea siempre menor o igual al tamaño en disco. ukify se asegura automáticamente de que esto sea así al construir UKIs o complementos.

Tenga en cuenta también que el kernel de Linux medirá todos los initrd que reciba en el PCR 9 del TPM. Esto significa que cada tipo de initrd (del perfil de UKI seleccionado) se medirá posiblemente dos o tres veces: los initrd integrados en la imagen del kernel se medirán en los PCR 4, 9 y 11; el initrd sintetizado a partir de credenciales (y el sintetizado a partir de extensiones de configuración) se medirán tanto en el PCR 9 como en el 12; el initrd sintetizado a partir de extensiones del sistema se medirá tanto en el PCR 4 como en el 9. VARIABLES EFI

Las siguientes variables EFI son definidas, establecidas y leídas por systemd-stub, bajo el UUID del proveedor "4a67b082-0a4c-41cf-b6c7-440b29bb8c4f", para la comunicación entre el stub de arranque y el SO:

LoaderDevicePartUUID

Contiene el UUID de la partición desde la que se inició el cargador de arranque en el arranque actual (generalmente una Partición del Sistema EFI). Si ya está establecida por el cargador de arranque, systemd-stub la dejará intacta. Si aún no está establecida, se establecerá con el UUID de la partición desde la que se inicia el kernel unificado, para dar soporte a sistemas que arrancan directamente en una imagen de kernel unificada, omitiendo cualquier cargador de arranque. systemd-gpt-auto-generator(8) utiliza esta información para encontrar automáticamente el disco de arranque, con el fin de descubrir automáticamente varias otras particiones en el mismo disco.

Añadido en la versión 224.

LoaderFirmwareInfo, LoaderFirmwareType

Información breve del firmware. Utilice bootctl(1) para ver estos datos.

Añadido en la versión 250.

LoaderTpm2ActivePcrBanks

Representación de cadena hexadecimal de una máscara de bits con valores definidos por la Especificación del Protocolo TCG EFI para TPM 2.0 como EFI_TCG2_BOOT_HASH_ALG_*. Si no se detectó soporte para TPM2 o ningún banco activo, se establecerá en 0. Establecido por el cargador de arranque. Utilice systemd-analyze(1) para ver estos datos.

Añadido en la versión 258.

LoaderImageIdentifier

La ruta del sistema de archivos al ejecutable EFI del cargador de arranque para el arranque actual, relativa al directorio raíz de la partición (es decir, relativa a la partición indicada por LoaderDevicePartUUID, ver arriba). Si aún no está establecida, se establecerá con la ruta del sistema de archivos del ejecutable EFI del kernel unificado arrancado, para dar soporte a sistemas que arrancan directamente en una imagen de kernel unificada, omitiendo cualquier cargador de arranque. Utilice bootctl(1) para ver estos datos.

Añadido en la versión 237.

StubDevicePartUUID, StubImageIdentifier

Similar a LoaderDevicePartUUID y LoaderImageIdentifier, pero indica la ubicación del binario EFI de la imagen del kernel unificada en lugar de la ubicación del binario del cargador de arranque, independientemente de si se arrancó a través de un cargador de arranque o no.

Añadido en la versión 257.

StubDeviceURL

Si la imagen del kernel se invocó a través de un arranque de red, esta variable contendrá la URL de origen. Esto puede usarse para adquirir automáticamente recursos adicionales de la misma fuente.

INITRD RESOURCES

The kernel may be asked to copy specific files from the Unified Kernel Image (UKI) into the initrd, to be made available in the initrd execution environment.

This is configured via the kernel command line, specifically using the --uefi-stub-args= option of ukify(1).

The specific options are:

  • --kernel-cmdline=...: Set the kernel command line passed to the kernel.
  • --kernel-cmdline-file=...: Read the kernel command line from a file.
  • --tpm-pcr-digits=...: Set the PCRs to be used for TPM2 measurements.
  • --splash-image=...: Set the splash image to be embedded.

For details, see ukify(1).

The following files may be copied:

/.extra/tpm2-pcr-signature.json

The JSON file containing the TPM2 PCR signature, as found in the ".pcrsig" PE section of the unified kernel image, is copied into the /.extra/tpm2-pcr-signature.json file in the initrd execution environment.

Added in version 252.

/.extra/tpm2-pcr-public-key.pem

The PEM public key included in the ".pcrpkey" PE section of the unified kernel image is copied into the /.extra/tpm2-pcr-public-key.pem file in the initrd execution environment.

Added in version 252.

/.extra/profile, /.extra/os-release

The contents of the ".profile" and ".osrel" sections of the selected profile, if any.

Added in version 257.

Note that all these files are located in the "tmpfs" file system the kernel sets up for the initrd file hierarchy and are thus lost when the system transitions from the initrd execution environment into the host file system. If these resources shall be kept around over this transition they need to be copied to a place that survives the transition first, for example via a suitable tmpfiles.d(5) line. By default, this is done for the TPM2 PCR signature and public key files.

SMBIOS TYPE 11 STRINGS

systemd-stub can be configured using SMBIOS Type 11 strings. Applicable strings consist of a name, followed by "=", followed by the value. Unless systemd-stub detects it is running inside a confidential computing environment, systemd-stub will search the table for a string with a specific name, and if found, use its value. The following strings are read:

io.systemd.stub.kernel-cmdline-extra

If set, the value of this string is added to the list of kernel command line arguments that are measured in PCR12 and passed to the kernel.

Added in version 254.
