LIBEXPECT(3) Library Functions Manual LIBEXPECT(3)

NOMBRE

libexpect - biblioteca de diálogo programado con programas interactivos

DESCRIPCIÓN

Esta biblioteca contiene funciones que permiten usar Expect como una extensión de Tcl o usarla directamente desde C o C++ (sin Tcl). Añadir Expect como una extensión de Tcl es muy corto y simple, por lo que se cubrirá primero.

SINOPSIS

#include expect_tcl.h
Expect_Init(interp);
cc files... -lexpect5.20 -ltcl7.5 -lm

Nota: las versiones de la biblioteca pueden diferir en la versión real.

La función Expect_Init añade comandos de expect al intérprete nombrado. Evita sobrescribir comandos que ya existen, sin embargo, los alias que comienzan con "exp_" siempre se crean para los comandos de expect. Así, por ejemplo, "send" se puede usar como "exp_send".

Generalmente, solo debes llamar a los comandos Expect a través de Tcl_Eval. Ciertas funciones auxiliares se pueden llamar directamente. Se resumen a continuación. Pueden ser útiles para construir tu propio main. Mira el archivo exp_main_exp.c en la distribución de Expect como un prototipo de main. Otro prototipo es tclAppInit.c en la distribución fuente de Tcl. Un prototipo para trabajar con Tk está en exp_main_tk.c en la distribución de Expect.

exp_cmdlinecmds es 1 si Expect ha sido invocado con comandos en la línea de comandos del programa (usando "-c", por ejemplo). exp_interactive es 1 si Expect ha sido invocado con el flag -i o si no se está invocando ningún comando o script. exp_cmdfile es un stream del cual Expect leerá comandos. exp_cmdfilename es el nombre de un archivo que Expect abrirá y del cual leerá comandos. exp_tcl_debugger_available es 1 si el depurador ha sido armado.

exp_parse_argv lee la representación de la línea de comandos. Basado en lo que encuentra, cualquiera de las otras variables listadas aquí se inicializa apropiadamente. exp_interpreter solicita interactivamente comandos al usuario y los evalúa. exp_interpret_cmdfile lee el stream dado y evalúa cualquier comando encontrado. exp_interpret_cmdfilename abre el archivo nombrado y evalúa cualquier comando encontrado. exp_interpret_rcfiles lee y evalúa los archivos .rc. Si my_rc es cero, entonces ~/.expectrc se omite. Si sys_rc es cero, entonces el archivo expectrc a nivel de sistema se omite. exp_cook devuelve un buffer estático que contiene el argumento reproducido con saltos de línea reemplazados por secuencias de retorno de carro y avance de línea. El propósito principal de esto es permitir la producción de mensajes sin preocuparse por si la terminal está en modo crudo o cocido. Si la longitud es cero, se calcula mediante strlen. exp_error es una función similar a printf que escribe el resultado en interp->result.

DESCRIPCIÓN

exp_spawnl y exp_spawnv crean un nuevo proceso para que su entrada, salida y error estándar puedan ser escritos y leídos por el proceso actual. file es el nombre de un archivo a ejecutar. Los punteros arg son cadenas terminadas en nulo. Siguiendo el estilo de execve(), arg0 (o argv[0]) es habitualmente un duplicado del nombre del archivo.

Hay cuatro interfaces disponibles, exp_spawnl es útil cuando el número de argumentos se conoce en tiempo de compilación. exp_spawnv es útil cuando el número de argumentos no se conoce en tiempo de compilación. exp_spawnfd es útil cuando ya se dispone de un descriptor de archivo abierto como fuente. exp_popen se explica más adelante.

Si el proceso se crea con éxito, se devuelve un descriptor de archivo que corresponde a la entrada estándar, salida estándar y error estándar del proceso. Se puede asociar un stream con el descriptor de archivo usando fdopen(). (Esto casi seguramente debería ir seguido de setbuf() para dejar de almacenar en búfer la E/S).

Cerrar el descriptor de archivo normalmente será detectado por el proceso como un EOF. Una vez que dicho proceso sale, se debe esperar (mediante wait) para liberar el espacio del proceso del kernel. (Algunos sistemas te permiten evitar esto si ignoras la señal SIGCHLD).

exp_popen es otra interfaz más, al estilo de popen(). Toma una línea de comandos del shell Bourne y devuelve un stream que corresponde a la entrada estándar, salida estándar y error estándar del proceso. La implementación real de exp_popen a continuación demuestra exp_spawnl.

FILE *
exp_popen(program)
char *program;
{
	FILE *fp;
	int ec;
	if (0 > (ec = exp_spawnl("sh","sh","-c",program,(char *)0)))
		return(0);
	if (NULL == (fp = fdopen(ec,"r+")) return(0);
	setbuf(fp,(char *)0);
	return(fp);
}

Después de iniciar un proceso, la variable exp_pid se establece en el ID de proceso del nuevo proceso. La variable exp_pty_slave_name se establece en el nombre del lado esclavo del pty.

Las funciones spawn utilizan un pty para comunicarse con el proceso. Por defecto, el pty se inicializa de la misma manera que la tty del usuario (si es posible, es decir, si el entorno tiene una terminal de control). Esta inicialización se puede omitir estableciendo exp_ttycopy a 0.

El pty se inicializa aún más con algunos valores predeterminados a nivel de sistema si exp_ttyinit es distinto de cero. El valor predeterminado es generalmente comparable a "stty sane".

La configuración de la tty se puede modificar aún más estableciendo la variable exp_stty_init. Esta variable se interpreta al estilo de argumentos de stty. Por ejemplo, exp_stty_init = "sane"; repite la inicialización predeterminada.

En algunos sistemas, es posible redirigir la salida de la consola a ptys. Si esto es compatible, puedes forzar que el próximo spawn obtenga la salida de la consola estableciendo la variable exp_console a 1.

Entre el momento en que se inicia un proceso y el nuevo programa toma el control, las funciones spawn pueden limpiar el entorno cerrando descriptores de archivo. Por defecto, los únicos descriptores de archivo cerrados son los internos de Expect y cualquiera marcado como "close-on-exec".

Si es necesario, puedes cerrar descriptores de archivo adicionales creando una función apropiada y asignándola a exp_close_in_child. La función se llamará después del fork y antes del exec. (Esto también modifica el comportamiento del comando spawn en Expect).

Si también estás usando Tcl, puede ser conveniente usar la función exp_close_tcl_files que cierra todos los archivos entre los descriptores de archivo estándar predeterminados y el descriptor más alto conocido por Tcl. (Expect hace esto).

La función exp_child_exec_prelude es la última función llamada antes del exec real en el hijo. Puedes redefinirla para efectos como manipular el uid o las señales.

SI DESEA ASIGNAR SU PROPIO PTY

extern int exp_autoallocpty;
extern int exp_pty[2];

Las funciones spawn utilizan un pty para comunicarse con el proceso. Por defecto, se asigna automáticamente un pty cada vez que se inicia un proceso. Si desea asignar ptys usted mismo, antes de llamar a una de las funciones spawn, establezca exp_autoallocpty en 0, exp_pty[0] al descriptor de archivo maestro del pty y exp_pty[1] al descriptor de archivo esclavo del pty. La biblioteca expect no realizará ninguna inicialización de pty (por ejemplo, no se utilizará exp_stty_init). El descriptor de archivo esclavo del pty se cerrará automáticamente cuando se inicie el proceso. Después de que el proceso se inicie, toda la comunicación posterior se realiza con el descriptor de archivo maestro del pty.

SYNTAX

#include <expect.h>

int exp_spawnl(const char *file, const char *arg0, ...);

int exp_spawnv(const char *file, char *constargv[]);

int exp_spawnlp(const char *file, const char *arg0, ...);

int exp_spawnvp(const char *file, char *constargv[]);

DESCRIPTION

The functions exp_spawnl and exp_spawnlp execute a new process. The first argument is the name of the command to execute. The remaining arguments are the arguments to the command. The list of arguments must be terminated by a NULL pointer. The first argument, arg0, is conventionally the name of the command. The functions exp_spawnv and exp_spawnvp are equivalent, but take the arguments in an array argv. The argv array must also be terminated by a NULL pointer.

The functions ending in p (e.g. exp_spawnlp) search the user's PATH for the specified executable file if it does not contain a slash (/).

The functions exp_spawnl and exp_spawnv duplicate the shell's actions in searching for an executable file in a list of directories. The directory list is obtained from the environment.

EXPECT PROCESSING

While it is possible to use read() to read information from a process spawned by exp_spawnl or exp_spawnv, more convenient functions are provided. They are as follows:

int
exp_expectl(fd,type1,pattern1,[re1,],value1,type2,...,exp_end);
int fd;
enum exp_type type;
char *pattern1, *pattern2, ...;
regexp *re1, *re2, ...;
int value1, value2, ...;


int
exp_fexpectl(fp,type1,pattern1,[re1,]value1,type2,...,exp_end);
FILE *fp;
enum exp_type type;
char *pattern1, *pattern2, ...;
regexp *re1, *re2, ...;
int value1, value2, ...;
enum exp_type {
exp_end,
exp_glob,
exp_exact,
exp_regexp,
exp_compiled,
exp_null,
};
struct exp_case {
char *pattern;
regexp *re;
enum exp_type type;
int value;
};
int
exp_expectv(fd,cases);
int fd;
struct exp_case *cases;
int
exp_fexpectv(fp,cases);
FILE *fp;
struct exp_case *cases;
extern int exp_timeout;
extern char *exp_match;
extern char *exp_match_end;
extern char *exp_buffer;
extern char *exp_buffer_end;
extern int exp_match_max;
extern int exp_full_buffer;
extern int exp_remove_nulls;

The functions wait until the output from a process matches one of the patterns, a specified time period has passed, or an EOF is seen.

The first argument to each function is either a file descriptor or a stream. Successive sets of arguments describe patterns and associated integer values to return when the pattern matches.

The type argument is one of four values. exp_end indicates that no more patterns appear. exp_glob indicates that the pattern is a glob-style string pattern. exp_exact indicates that the pattern is an exact string. exp_regexp indicates that the pattern is a regexp-style string pattern. exp_compiled indicates that the pattern is a regexp-style string pattern, and that its compiled form is also provided. exp_null indicates that the pattern is a null (for debugging purposes, a string pattern must also follow).

If the compiled form is not provided with the functions exp_expectl and exp_fexpectl, any pattern compilation done internally is thrown away after the function returns. The functions exp_expectv and exp_fexpectv will automatically compile patterns and will not throw them away. Instead, they must be discarded by the user, by calling free on each pattern. It is only necessary to discard them, the last time the cases are used.

Regexp subpatterns matched are stored in the compiled regexp. Assuming "re" contains a compiled regexp, the matched string can be found in re->startp[0]. The match substrings (according to the parentheses) in the original pattern can be found in re->startp[1], re->startp[2], and so on, up to re->startp[9]. The corresponding strings ends are re->endp[x] where x is that same index as for the string start.

The type exp_null matches if a null appears in the input. The variable exp_remove_nulls must be set to 0 to prevent nulls from being automatically stripped. By default, exp_remove_nulls is set to 1 and nulls are automatically stripped.

exp_expectv and exp_fexpectv are useful when the number of patterns is not known in advance. In this case, the sets are provided in an array. The end of the array is denoted by a struct exp_case with type exp_end. For the rest of this discussion, these functions will be referred to generically as expect.

If a pattern matches, then the corresponding integer value is returned. Values need not be unique, however they should be positive to avoid being mistaken for EXP_EOF, EXP_TIMEOUT, or EXP_FULLBUFFER. Upon EOF or timeout, the value EXP_EOF or EXP_TIMEOUT is returned. The default timeout period is 10 seconds but may be changed by setting the variable exp_timeout. A value of -1 disables a timeout from occurring. A value of 0 causes the expect function to return immediately (i.e., poll) after one read(). However it must be preceded by a function such as select, poll, or an event manager callback to guarantee that there is data to be read.

If the variable exp_full_buffer is 1, then EXP_FULLBUFFER is returned if exp_buffer fills with no pattern having matched.

When the expect function returns, exp_buffer points to the buffer of characters that was being considered for matching. exp_buffer_end points to one past the last character in exp_buffer. If a match occurred, exp_match points into exp_buffer where the match began. exp_match_end points to one character past where the match ended.

Each time new input arrives, it is compared to each pattern in the order they are listed. Thus, you may test for absence of a match by making the last pattern something guaranteed to appear, such as a prompt. In situations where there is no prompt, you must check for EXP_TIMEOUT (just like you would if you were interacting manually). More philosophy and strategies on specifying expect patterns can be found in the documentation on the expect program itself. See SEE ALSO below.

Patterns are the usual C-shell-style regular expressions. For example, the following fragment looks for a successful login, such as from a telnet dialogue.

switch (exp_expectl(
	exp_glob,"connected",CONN,
	exp_glob,"busy",BUSY,
	exp_glob,"failed",ABORT,
	exp_glob,"invalid password",ABORT,
	exp_end)) {
case CONN:	/* logged in successfully */
	break;
case BUSY:	/* couldn't log in at the moment */
	break;
case EXP_TIMEOUT:
case ABORT:	/* can't log in at any moment! */
	break;
default: /* problem with expect */
}

Asterisks (as in the example above) are a useful shorthand for omitting line-termination characters and other detail. Patterns must match the entire output of the current process (since the previous read on the descriptor or stream). More than 2000 bytes of output can force earlier bytes to be "forgotten". This may be changed by setting the variable exp_match_max. Note that excessively large values can slow down the pattern matcher.

RUNNING IN THE BACKGROUND

extern int exp_disconnected;
int exp_disconnect();

It is possible to move a process into the background after it has begun running. A typical use for this is to read passwords and then go into the background to sleep before using the passwords to do real work.

To move a process into the background, fork, call exp_disconnect() in the child process and exit() in the parent process. This disassociates your process from the controlling terminal. If you wish to move a process into the background in a different way, you must set the variable exp_disconnected to 1. This allows processes spawned after this point to be started correctly.

MULTIPLEXING

By default, the expect functions block inside of a read on a single file descriptor. If you want to wait on patterns from multiple file descriptors, use select, poll, or an event manager. They will tell you what file descriptor is ready to read.

When a file descriptor is ready to read, you can use the expect functions to do one and only read by setting timeout to 0.

SLAVE CONTROL

void
exp_slave_control(fd,enable)
int fd;
int enable;

Pty trapping is normally done automatically by the expect functions. However, if you want to issue an ioctl, for example, directly on the slave device, you should temporary disable trapping.

Pty trapping can be controlled with exp_slave_control. The first argument is the file descriptor corresponding to the spawned process. The second argument is a 0 if trapping is to be disabled and 1 if it is to be enabled.

ERRORS

All functions indicate errors by returning -1 and setting errno.

Errors that occur after the spawn functions fork (e.g., attempting to spawn a non-existent program) are written to the process's stderr, and will be read by the first expect.

SIGNALS

extern int exp_reading;
extern jmp_buf exp_readenv;

expect uses alarm() to timeout, thus if you generate alarms during expect, it will timeout prematurely.

Internally, expect calls read() which can be interrupted by signals. If you define signal handlers, you can choose to restart or abort expect's internal read. The variable, exp_reading, is true if (and only if) expect's read has been interrupted. longjmp(exp_readenv,EXP_ABORT) will abort the read. longjmp(exp_readenv,EXP_RESTART) will restart the read.

LOGGING

extern int exp_loguser;
extern int exp_logfile_all
extern FILE *exp_logfile;

If exp_loguser is nonzero, expect sends any output from the spawned process to stdout. Since interactive programs typically echo their input, this usually suffices to show both sides of the conversation. If exp_logfile is also nonzero, this same output is written to the stream defined by exp_logfile. If exp_logfile_all is non-zero, exp_logfile is written regardless of the value of exp_loguser.

DEBUGGING

While I consider the library to be easy to use, I think that the standalone expect program is much, much, easier to use than working with the C compiler and its usual edit, compile, debug cycle. Unlike typical C programs, most of the debugging isn't getting the C compiler to accept your programs - rather, it is getting the dialogue correct. Also, translating scripts from expect to C is usually not necessary. For example, the speed of interactive dialogues is virtually never an issue. So please try the standalone 'expect' program first. I suspect it is a more appropriate solution for most people than the library.

Nonetheless, if you feel compelled to debug in C, here are some tools to help you.

extern int exp_is_debugging;
extern FILE *exp_debugfile;

    intentar codificarlos en un programa puede revelar muchas sorpresas en la
    interfaz de un programa. Por lo tanto, hay una variedad de ayudas de
    depuración disponibles. Están controladas por las variables anteriores, todas
    con valor 0 por defecto.

ADVERTENCIAS

Las versiones de flujo de las funciones de expect son mucho más lentas que las versiones de descriptores de archivo porque no hay forma portátil de leer un número desconocido de bytes sin el riesgo de tiempo de espera agotado. Por lo tanto, los caracteres se leen uno a uno. Por lo tanto, se le anima encarecidamente a utilizar las versiones de descriptor de archivo de expect (aunque, las versiones automatizadas de programas interactivos normalmente no exigen alta velocidad de todos modos).

En realidad, puede obtener lo mejor de ambos mundos, escribiendo con las funciones de flujo habituales y leyendo con las versiones de descriptor de archivo de expect, siempre y cuando no intente mezclar otras funciones de entrada de flujo (por ejemplo, fgetc). Para hacer esto, pase fileno(stream) como el descriptor de archivo cada vez. Afortunadamente, hay pocas razones para usar algo más que las funciones de expect al leer de programas interactivos.

No hay un exp_pclose correspondiente a exp_popen (a diferencia de popen y pclose). Solo se necesitan dos funciones para cerrar una conexión (fclose() seguido de la espera del pid), pero no es raro separar estas dos acciones por grandes intervalos de tiempo, por lo que la función parece de poco valor.

Si está ejecutando en un Cray con Unicos (todo lo que sé con seguridad por experiencia), debe ejecutar su programa compilado como root o setuid. El problema es que el Cray solo permite que los procesos root abran ptys. Debe observar todas las precauciones posibles: Si no necesita permisos, establezca setuid(0) solo inmediatamente antes de llamar a una de las funciones de spawn y restablézcalo inmediatamente después.

Normalmente, spawn tarda poco en ejecutarse. Si nota que spawn tarda una cantidad significativa de tiempo, probablemente esté encontrando ptys bloqueados. Se ejecutan una serie de pruebas en los ptys para evitar enredos con procesos errantes. (Estos tardan 10 segundos por pty bloqueado). Ejecutar expect con la opción -d mostrará si expect está encontrando muchos ptys en estados extraños. Si no puede matar los procesos a los que están adjuntos estos ptys, su único recurso puede ser reiniciar.

ERRORES

Las funciones exp_fexpect no funcionan en absoluto bajo HP-UX; parece ser un error en getc. Siga el consejo (anterior) sobre el uso de las funciones exp_expect (que no necesita llamar a getc). Si soluciona el problema (antes que yo, por favor revise la última versión), hágame saber.

VER TAMBIÉN

Una alternativa a esta biblioteca es el programa expect. expect interpreta scripts escritos en un lenguaje de alto nivel que dirigen el diálogo. Además, el usuario puede tomar el control e interactuar directamente cuando lo desee. Si no es absolutamente necesario escribir su propio programa C, es mucho más fácil usar expect para realizar toda la interacción. Se describe más detalladamente en las siguientes referencias:

"expect: Curing Those Uncontrollable Fits of Interactivity" por Don Libes, Proceedings of the Summer 1990 USENIX Conference, Anaheim, California, 11-15 de junio de 1990.

"Using expect to Automate System Administration Tasks" por Don Libes, Proceedings of the 1990 USENIX Large Installation Systems Administration Conference, Colorado Springs, Colorado, 17-19 de octubre de 1990.

expect(1), alarm(3), read(2), write(2), fdopen(3), execve(2), execvp(3), longjmp(3), pty(4).
