NOMBRE

nss-systemd, libnss_systemd.so.2 - Resolución de nombres de usuario y grupos de UNIX para la consulta de usuarios/grupos a través de Varlink

SINOPSIS

libnss_systemd.so.2

DESCRIPCIÓN

nss-systemd es un módulo plug-in para la funcionalidad del GNU Name Service Switch (NSS) de la Biblioteca C de GNU (glibc), que proporciona resolución de nombres de usuario y grupos de UNIX para servicios que implementan la API de consulta de registros de usuarios/grupos a través de Varlink[1], como el administrador del sistema y de servicios systemd(1) (para su característica DynamicUser=, ver systemd.exec(5) para detalles), systemd-homed.service(8), o systemd-machined.service(8).

Este módulo también garantiza que los usuarios y grupos root y nobody (es decir, los usuarios/grupos con los UID/GID 0 y 65534) sigan siendo resolubles en todo momento, incluso si no están listados en /etc/passwd o /etc/group, o si estos archivos faltan.

Este módulo utiliza preferentemente systemd-userdbd.service(8) para resolver usuarios y grupos, pero también funciona sin que el servicio esté en ejecución.

Para activar el módulo NSS, agregue "systemd" a las líneas que comienzan con "passwd:", "group:", "shadow:" y "gshadow:" en /etc/nsswitch.conf.

Se recomienda colocar "systemd" después de la entrada "files" de las líneas de /etc/nsswitch.conf para que las asignaciones basadas en /etc/passwd, /etc/group, /etc/shadow y /etc/gshadow tengan prioridad.

REGISTROS ESTÁTICOS DE USUARIO/GRUPO JSON DROP-IN

Además de los registros de usuarios/grupos adquiridos a través de las interfaces IPC de Varlink mencionadas anteriormente y las cuentas raíz y nobody sintetizadas, este módulo también pone a disposición del sistema cuentas de usuario y grupo que se definen en archivos drop-in estáticos en los directorios /etc/userdb/, /run/userdb/, /run/host/userdb/ y /usr/lib/userdb/.

Este es un mecanismo simple para proporcionar registros de usuarios y grupos estáticos a través de archivos drop-in JSON. Dichos registros de usuarios deben definirse en el formato descrito por la especificación de Registros de Usuarios JSON[2] y colocarse en uno de los directorios mencionados anteriormente bajo un nombre de archivo compuesto por el nombre de usuario con el sufijo .user, con un modo de acceso legible para todos. También se debe crear un enlace simbólico con el nombre del registro de usuario UID formateado en decimal y con el sufijo .user, apuntando al archivo de registro principal, para permitir tanto las consultas por nombre de usuario como por UID. Opcionalmente, se pueden proporcionar datos de registros de usuarios privilegiados (por ejemplo, contraseñas UNIX cifradas) en un par de archivos complementarios separados con el sufijo .user-privileged. Los datos deben almacenarse en un archivo regular con el nombre del usuario con el sufijo .user-privileged, y un enlace simbólico que apunte a él, con el nombre del UID numérico utilizado formateado en decimal con el mismo sufijo. Estos archivos complementarios no deben ser legibles para nadie que no sea root. Ejemplo:

-rw-r--r--. 1 root root  723 May 10 foobar.user
-rw-------. 1 root root  123 May 10 foobar.user-privileged
lrwxrwxrwx. 1 root root   19 May 10 4711.user -> foobar.user
lrwxrwxrwx. 1 root root   19 May 10 4711.user-privileged -> foobar.user-privileged

De manera similar, se pueden definir registros de grupos siguiendo el formato descrito en Registro de Grupos JSON[3], utilizando los sufijos de archivo .group y .group-privileged.

Los archivos de registro primarios de usuario/grupo (es decir, los que tienen los sufijos .user y .group) no deben contener la sección "privileged", tal como se describe en las especificaciones. Los archivos de registro privilegiados de usuario/grupo (es decir, los que tienen los sufijos .user-privileged y .group-privileged) deben contener esta sección, exclusivamente.

Además de los dos tipos de archivos de registro de usuarios y los dos tipos de archivos de registro de grupos, existe un quinto tipo de archivo que puede colocarse en los directorios de búsqueda: archivos que indican la membresía de usuarios en grupos. Específicamente, para cada par de usuario/grupo donde el usuario debe ser miembro de un grupo, se debe crear un archivo llamado "nombreusuario:nombredegrupo.membership", es decir, el nombre de usuario de UNIX textual, seguido de dos puntos, seguido del nombre de grupo de UNIX textual, con el sufijo ".membership". Actualmente, el contenido de estos archivos no se lee, y los archivos deben crearse vacíos. La mera existencia de estos archivos es suficiente para afectar la membresía de usuario/grupo. Si un programa proporciona archivos de registro de usuarios y/o grupos en los directorios de búsqueda, siempre debe crear también dichos archivos, tanto para membresías de grupos primarias como auxiliares.

Tenga en cuenta que los registros de usuarios/grupos estáticos generalmente no anulan los registros conflictivos en /etc/passwd o /etc/group u otras bases de datos de cuentas. De hecho, antes de incorporar estos archivos, se debe tener un nivel razonable de cuidado para evitar conflictos de nombres de usuario/grupo y UID/GID.

El servicio systemd-userdb-load-credentials.service se ejecuta automáticamente al arrancar e instala estos archivos a partir de los registros de usuarios pasados a través de credenciales del sistema. Consulte userdbctl(1) y systemd.system-credentials(7) para obtener más detalles.

CONFIGURACIÓN EN /ETC/NSSWITCH.CONF

Aquí hay un ejemplo de archivo /etc/nsswitch.conf que habilita nss-systemd correctamente:

passwd:         files systemd
group:          files [SUCCESS=merge] systemd
shadow:         files systemd
gshadow:        files systemd
hosts:          mymachines resolve [!UNAVAIL=return] files myhostname dns
networks:       files
protocols:      db files
services:       db files
ethers:         db files
rpc:            db files
netgroup:       nis

CONFIGURATION IN /ETC/NSSWITCH.CONF

To enable the systemd NSS service, you need to configure the /etc/nsswitch.conf file. Add or modify the following lines:

passwd: files systemd
group: files systemd
shadow: files systemd
gshadow: files systemd

This configuration tells the system to first look up user and group information in the local files (e.g., /etc/passwd, /etc/group) and then fall back to the systemd NSS service if the information is not found.

Note: The 'systemd' entry should be placed appropriately in the lookup order based on your needs. It is generally recommended to place it after 'files' for local definitions.

EXAMPLE: MAPPINGS PROVIDED BY SYSTEMD-MACHINED.SERVICE

When systemd-machined.service(8) is running, it can expose user and group information for managed virtual machines and containers. libnss_systemd.so.2 can be configured to query this information, allowing users and groups within those environments to be recognized by the host system.

For example, a configuration might look like:

passwd: files systemd
group: files systemd

If systemd-userdbd.service is running, it will be queried by libnss_systemd.so.2. This allows for dynamic user and group mappings to be provided.
