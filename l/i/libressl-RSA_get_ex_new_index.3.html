libressl-RSA_get_ex_new_index(3)

Paquete: libressl

Licencias: ISC, custom:OpenSSL

RSA_GET_EX_NEW_INDEX(3) Manual de Funciones de Biblioteca RSA_GET_EX_NEW_INDEX(3)

NOMBRE

RSA_get_ex_new_index, RSA_set_ex_data, RSA_get_ex_data — añadir datos específicos de la aplicación a objetos RSA

SINOPSIS

biblioteca “libcrypto”
#include <openssl/rsa.h>

int
RSA_get_ex_new_index(long argl, void *argp, CRYPTO_EX_new *new_func, CRYPTO_EX_dup *dup_func, CRYPTO_EX_free *free_func);

int
RSA_set_ex_data(RSA *rsa, int idx, void *data);

void *
RSA_get_ex_data(RSA *rsa, int idx);

DESCRIPCIÓN

Los siguientes objetos padres pueden tener datos específicos de la aplicación llamados “ex_data” adjuntos a ellos: BIO, DH, DSA, EC_KEY, RSA, SSL, SSL_CTX, SSL_SESSION, UI, X509, X509_STORE, y X509_STORE_CTX. La página de manual presente documenta las funciones de API relacionadas que toman el tipo de objeto RSA como ejemplo. Las funciones para los otros tipos de objeto funcionan de la misma manera: simplemente reemplace la cadena "RSA" con el nombre del tipo de objeto respectivo en el resto de esta página de manual.

Por defecto, cada objeto RSA individual puede almacenar un void * que apunta a datos específicos de la aplicación. Ese puntero específico se identifica mediante un argumento idx de 0.

RSA_get_ex_new_index() reserva el siguiente argumento idx consecutivo, permitiendo el almacenamiento de un void * adicional por objeto RSA. Típicamente se llama al inicio del programa. Puede ser llamado más de una vez si algunos objetos RSA necesitan almacenar más de dos punteros específicos de la aplicación. Reservar un índice adicional para un tipo de objeto padre, por ejemplo para RSA, no cambia el número de índices que pueden usarse con ningún otro tipo de objeto padre.

Se recomienda encarecidamente pasar siempre tres punteros NULL para los argumentos new_func, dup_func, y free_func. Al seguir esta recomendación, los argumentos argl y argp son ignorados; convencionalmente, se recomienda pasar 0 y NULL. Debido a que su uso no se recomienda, los tres tipos de función de devolución de llamada solo se documentan en la página de manual de bajo nivel CRYPTO_EX_new(3).

RSA_set_ex_data() almacena el puntero data como datos específicos de la aplicación en el idx dado del objeto rsa dado. El significado de los datos apuntados depende de la aplicación. El llamador conserva la propiedad de data y es responsable de liberarlo cuando ni el llamador ni el objeto rsa lo necesiten más. Cualquier otro puntero que se haya almacenado previamente en el mismo idx en el mismo objeto rsa se sobrescribe silenciosamente. Pasar un puntero NULL para el argumento data es válido e indica que actualmente no se necesitan almacenar datos específicos de la aplicación en el idx dado.

RSA_get_ex_data() recupera el último puntero que se almacenó usando RSA_set_ex_data() en el idx dado del objeto rsa dado.

VALORES DE RETORNO

RSA_get_ex_new_index() devuelve un nuevo índice igual o mayor que 1, o -1 si falla la asignación de memoria.

RSA_set_ex_data() devuelve 1 en caso de éxito o 0 si falla la asignación de memoria.

RSA_get_ex_data() devuelve los datos específicos de la aplicación o NULL si rsa no contiene datos específicos de la aplicación en el idx dado.

ERRORES

Después de un fallo de RSA_get_ex_new_index() o RSA_set_ex_data(), el siguiente diagnóstico puede recuperarse con ERR_get_error(3), ERR_GET_REASON(3), y ERR_reason_error_string(3):

ERR_R_MALLOC_FAILURE "fallo de malloc"
Falló la asignación de memoria.

En algunos casos de fallo inusuales, ERR_get_error(3) puede reportar errores diferentes causados por OPENSSL_init_crypto(3) o incluso ninguno.

RSA_get_ex_data() no distingue entre éxito y fallo. Consecuentemente, después de que RSA_get_ex_data() devuelve NULL, ERR_get_error(3) devuelve 0 a menos que todavía haya un error anterior en la cola.

VER TAMBIÉN

BIO_set_ex_data(3), CRYPTO_set_ex_data(3), DH_set_ex_data(3), DSA_set_ex_data(3), RSA_new(3), SSL_CTX_set_ex_data(3), SSL_SESSION_set_ex_data(3), SSL_set_ex_data(3), X509_STORE_CTX_set_ex_data(3), X509_STORE_set_ex_data(3)

HISTORIA

Estas funciones aparecieron por primera vez en SSLeay 0.9.0 y han estado disponibles desde OpenBSD 2.4.

ADVERTENCIAS

Una minoría relativamente pequeña de programas de aplicación intentan cambiar el contrato de la API de tal manera que RSA_set_ex_data() transfiere la propiedad de data al objeto rsa. Lo hacen proporcionando una free_func que llama free(3) o funciones *_free() de nivel superior en data y a veces también intentan trabajo adicional de limpieza como efecto secundario.

Esta práctica no se recomienda por varias razones:

  1. Debido a un error masivo de diseño en la función de API de bajo nivel CRYPTO_free_ex_data(3), esta práctica crea la posibilidad de que RSA_free(3) falle debido a un fallo de asignación de memoria, lo que provoca fugas de memoria del contenido de los datos específicos de la aplicación y omite silenciosamente cualquier trabajo de limpieza adicional que la free_func debía realizar, dejando la aplicación en un estado inconsistente indetectable. Podría decirse que filtrar memoria adicional mientras se intenta liberar algo es lo más desafortunado, especialmente cuando el programa ya tiene escasez de memoria.

CAVEATS
  1. Esta práctica introduce un riesgo de errores de uso después de liberar (use-after-free) y doble liberación (double-free) en caso de que el objeto rsa se destruya mientras un llamador de RSA_set_ex_data() o RSA_get_ex_data() todavía mantiene un puntero data. No existe tal riesgo cuando no se instala ninguna free_func.
  2. Intentar realizar trabajo de limpieza adicional en free_func es una idea aún peor porque free_func no puede informar sobre ningún problema que pueda detectar mientras realiza ese trabajo. En su lugar, si se necesita cualquier trabajo de limpieza adicional, se recomienda que el código llamador se encargue de ello antes de llamar a RSA_free(3).

Aún menos programas de aplicación instalan una new_func que asigna memoria y almacena un puntero a ella en el objeto rsa llamando a CRYPTO_set_ex_data(3). Eso es inútil porque new_func no tiene acceso a ninguna información útil que pudiera almacenar en dicha memoria y porque el valor de retorno predeterminado de NULL de RSA_get_ex_data() es suficiente para indicar que aún no se ha almacenado ningún dato específico de la aplicación. Además, asignar memoria en new_func tampoco es aconsejable porque introduce una responsabilidad adicional para los llamadores de RSA_set_ex_data() de llamar siempre primero a RSA_get_ex_data(), incluso cuando es la primera vez que la aplicación desea establecer datos específicos de la aplicación en un objeto rsa particular, y modificar lo que sea que retorne RSA_get_ex_data() o liberarlo antes de llamar a RSA_set_ex_data(). Si se olvida esto, resultará en una fuga de memoria.

En consecuencia, es mejor dejar la asignación de cualquier memoria necesaria al código de la aplicación que llama a RSA_set_ex_data().

Instalar una dup_func a menudo se ve en combinación con instalar una free_func, por razones obvias. Rara vez es útil porque para la mayoría de los tipos de objetos padre que admiten ex_data, incluido RSA, la biblioteca no proporciona una función de API de copia en primer lugar, e incluso donde existen funciones de copia, tienden a ser frágiles y propensas a errores. Cuando se necesita un nuevo objeto, generalmente es aconsejable construirlo desde cero siempre que sea posible, en lugar de intentar una operación de copia.

Además de eso, si falla dup_func, por ejemplo, debido a un fallo en la asignación de memoria, el fallo no se informa ni se detecta de ninguna manera, dejando al nuevo objeto padre con datos incompletos y potencialmente en un estado inconsistente.

BUGS

Si RSA_set_ex_data() falla, la recuperación es muy difícil. En particular, llamar a RSA_free(3) sobre el objeto padre rsa justo después es probable que también falle la asignación de memoria, filtrando toda la memoria asignada internamente por todas las llamadas anteriores de RSA_set_ex_data() sobre rsa en lugar de liberar esa memoria. Para recuperarse, el programa de aplicación tendría que liberar una cantidad suficiente de otra memoria antes de llamar a RSA_free(3), lo que rara vez será factible. En consecuencia, después de un fallo de RSA_set_ex_data(), terminar el programa es probablemente la única opción razonable.

Si se llama a RSA_set_ex_data() con un argumento idx mayor que el último devuelto previamente por RSA_get_ex_new_index(), aún puede tener éxito, y aunque la API no lo garantiza, recuperar los data de un idx falso de este tipo puede ser incluso posible con RSA_get_ex_data(), ocultando el error en el programa de aplicación que causó pasar el idx falso a RSA_set_ex_data() en primer lugar.

Si el argumento idx falso es grande, RSA_set_ex_data() puede asignar inútilmente una gran cantidad de memoria. Llamar a RSA_free(3) sobre el objeto padre rsa es la única forma de recuperar esa memoria.

Si el argumento idx falso es muy grande, es probable que RSA_set_ex_data() cause un retraso significativo antes de fallar eventualmente debido a la falta de memoria. Es probable que retorne sin liberar la memoria ya asignada, causando que cualquier intento posterior de asignar memoria para otros propósitos también falle. En esta situación, lo dicho anteriormente sobre el fallo de RSA_set_ex_data() se aplica, por lo que terminar el programa es probablemente la única opción razonable.
