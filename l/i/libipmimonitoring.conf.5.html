NOMBRE

freeipmi_interpret_sensor.conf - especificar reglas de interpretación de sensores

DESCRIPCIÓN

El archivo /etc/freeipmi//freeipmi_interpret_sensor.conf define cómo se deben interpretar los sensores IPMI. Los sensores basados en IPMI especifican un número de estados/umbrales cuando se leen. Basándose en esos estados/umbrales, bibliotecas y herramientas como libfreeipmi(3), libipmimonitoring(3) e ipmi-sensors(8) pueden informar si la lectura de un sensor es "buena" o "mala" a través de un informe de un estado NOMINAL, ADVERTENCIA o CRÍTICO.

Cada uno de los estados listados a continuación son (esperemos) lo suficientemente descriptivos para describir las condiciones de estado que pueden ser establecidas/desestablecidas para cada tipo de sensor. Para obtener información más detallada sobre cada uno de los estados individuales listados a continuación, consulte la Especificación IPMI "Tablas de códigos de sensores y eventos". Ipmi-sensors(8) se puede utilizar para determinar los tipos de sensores y los estados/umbrales que existen en un sistema al generar una salida muy detallada y ver qué tipos de eventos de Asertación o Desasertación son posibles.

Los valores posibles para todos los estados/umbrales a continuación son:

Nominal - Señalar lectura Nominal si el estado/umbral se activa

Advertencia - Señalar lectura de Advertencia si el estado/umbral se activa

Crítico - Señalar lectura Crítica si el estado/umbral se activa

No todos los tipos de sensores IPMI y tipos de eventos son compatibles actualmente. Si desea que se admita más, envíe un correo electrónico a la lista de correo de FreeIPMI.

Los valores predeterminados seleccionados para los estados/umbrales individuales que se activan se basan en las mejores suposiciones y en el análisis de las placas base. Si cree que deberían cambiarse, envíe un correo electrónico a la lista de correo de FreeIPMI para discutir cuáles deberían ser los valores predeterminados.

La mayoría de las interpretaciones predeterminadas se pueden determinar con bastante facilidad y pueden satisfacer las necesidades de la mayoría de los usuarios. Por ejemplo, una lectura de "Rendimiento_Cumplido" es normalmente mejor que "Rendimiento_Retrasado". Sin embargo, algunos sensores pueden ser ambiguos y depender completamente del fabricante. Por ejemplo, "Estado_Asertado" frente a "Estado_Desasertado" son completamente a interpretación del proveedor. Se recomienda a los usuarios que ajusten las interpretaciones a continuación según sea necesario para sus máquinas.

Cada grupo de condiciones de estado a continuación incluye una configuración para "Sin_Evento". Esta es la condición bajo la cual no se han ocurrido ni se activan estados/eventos del sensor. En la mayoría de las condiciones, se prefiere un mapeo a "Nominal". Sin embargo, bajo algunas circunstancias, puede ser útil informar algo más. Por ejemplo, si un sensor en una placa base en particular es requerido para informar un estado/evento, una condición de sin estado del sensor podría indicar un sensor roto. Esto depende en gran medida de la placa base.

FORMATO

Las opciones de configuración que se pueden especificar en el archivo de configuración se enumeran a continuación. Cada opción de configuración debe estar en una línea separada. Los argumentos de una opción se separan por cualquier cantidad de espacio en blanco. Múltiples argumentos también se separan por espacio en blanco. Los comentarios se pueden marcar usando el carácter de signo de almohadilla ("#"), y las líneas se pueden continuar en la siguiente usando la barra invertida ("\").

Aquí hay un ejemplo de cómo se vería un archivo de configuración modificado.

# se desaserta, y crítico si se aserta.
IPMI_Temperature_State_Deasserted Warning
IPMI_Temperature_State_Asserted Critical

# Interpretar el sensor de temperatura de la placa base como crítico si
# supera el umbral superior.
IPMI_Threshold_Sensor_At_Or_Above_Upper_Critical_Threshold Critical

IPMI_OEM
The following configuration options can be used to configure OEM specific interpretations. Users should be aware that both IPMI_OEM_Bitmask and IPMI_OEM_Value can be configured for an identical Manufacturer-ID, Product-ID, Event-Reading-Type-Code, and Sensor-Type combination. All interpretations rules for a specific combination are iterated through and the worst resulting sensor state is returned (i.e. Warning < Nominal, Critical < Warning). If no match is found, no sensor state is returned for the OEM sensor reading. For each of the configuration options below, <Manufacturer-ID> is the numeric IANA manufacturer ID for the manufacturer in question. The <Product-ID> is one or more numeric IDs representing the manufacturer's product. The <Product-ID> can be listed as a single numeric number (e.g. 1234), a range of IDs separated by a dash (e.g. 12-20), or a list of specific product IDs separated by a plus (e.g. 12+19+22). Both the Manufacturer-ID and Product-ID can be found using bmc-info(8). Multiple <Manufacturer-ID> and <Product-ID> pairs can be input separated by commas. The Event-Reading-Type-Code and Sensor-Type need not be OEM types. They may be non-OEM types and used to provide interpretation rules for sensors that may be behaving outside the standard of the IPMI specification.
IPMI_OEM_Bitmask <Manufacturer-ID>:<Product-ID>,... Event-Reading-Type-Code Sensor-Type Sensor-Event-Bitmask State
IPMI_OEM_Bitmask can be used to configure a state interpretation for a specific Manufacturer-ID, Product-ID, Event-Reading-Type-Code, and Sensor-Type combination and a specific bitmask of the Sensor-Event. The state will be accepted as the sensor interpretation if the inputted bitmask ANDed with the actual sensor event bitmask reading is true. As a special case, the state will be accepted if the inputted bitmask and the actual sensor event bitmask are both 0. In other words, if no events happened, an OEM interpretation can be configured for this case by inputing a bitmask of 0x0000.
IPMI_OEM_Value <Manufacturer-ID>:<Product-ID>,... Event-Reading-Type-Code Sensor-Type Sensor-Event-Bitmask-Value State
IPMI_OEM_Value can be used to configure a state interpretation for a specific Manufacturer-ID, Product-ID, Event-Reading-Type-Code, and Sensor-Type combination and a specific value for the Sensor-Event-Bitmask. The state will be accepted as the sensor interpretation if the inputted bitmask value is equal to the actual sensor event bitmask reading.
