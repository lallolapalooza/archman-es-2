NOMBRE

libcurl-security - consideraciones de seguridad al usar libcurl

Seguridad

El proyecto libcurl se toma la seguridad en serio. La biblioteca está escrita con precaución y se toman medidas para mitigar muchos tipos de riesgos que se encuentran al operar con servidores potencialmente maliciosos en Internet. Sin embargo, es una biblioteca potente que permite a los desarrolladores de aplicaciones tomar decisiones entre la facilidad de escritura y la exposición a operaciones potencialmente arriesgadas. Si se usa de la manera correcta, puedes usar libcurl para transferir datos de forma bastante segura.

Muchas aplicaciones se utilizan en redes cerradas donde los usuarios y servidores pueden ser (posiblemente) confiables, pero muchas otras se utilizan en servidores arbitrarios y se alimentan con datos de usuarios potencialmente no confiables. A continuación se presenta una discusión sobre algunos riesgos en las formas en que las aplicaciones comúnmente usan libcurl y las posibles mitigaciones de esos riesgos. No es exhaustiva, pero muestra clases de ataques que las aplicaciones robustas deberían considerar. El proyecto Common Weakness Enumeration en https://cwe.mitre.org/ es una buena referencia para muchas de estas y tipos similares de debilidades que los desarrolladores de aplicaciones deberían tener en cuenta.

Líneas de Comando

Si usas una herramienta de línea de comandos (como curl) que utiliza libcurl, y le das opciones en la línea de comandos, esas opciones pueden ser leídas por otros usuarios de tu sistema cuando usan ps u otras herramientas para listar los procesos en ejecución.

Para evitar estos problemas, nunca pases información sensible a los programas usando opciones de línea de comandos. Escríbela en un archivo protegido y usa la opción -K para evitar esto.

.netrc

El archivo .netrc es una característica bastante útil que te permite iniciar sesión rápida y automáticamente en sitios visitados frecuentemente. El archivo contiene contraseñas en texto plano y es un verdadero riesgo de seguridad. En algunos casos, tu .netrc también se almacena en un directorio de inicio que está montado en NFS o se usa en otro sistema de archivos basado en red, por lo que la contraseña en texto plano viaja por tu red cada vez que alguien lee ese archivo.

Para aplicaciones que habilitan el uso de .netrc, un usuario que logre configurar la URL correcta podría entonces pasar contraseñas.

Para evitar estos problemas, no uses archivos .netrc y nunca almacenes contraseñas en texto plano en ningún lugar.

Contraseñas en Texto Plano

Muchos de los protocolos que libcurl soporta envían nombre y contraseña sin cifrar como texto plano (autenticación HTTP Basic, FTP, TELNET, etc.). Es fácil para cualquiera en tu red o en una red cercana a la tuya simplemente lanzar una herramienta de análisis de red y espiar tus contraseñas. No te dejes engañar por el hecho de que HTTP Basic usa contraseñas codificadas en base64. Puede que no parezcan legibles a primera vista, pero son "descifradas" fácilmente por cualquiera en segundos.

Para evitar este problema, utiliza un mecanismo de autenticación u otro protocolo que no permita a los fisgones ver tu contraseña: autenticación Digest, CRAM-MD5, Kerberos, SPNEGO o NTLM. O mejor aún: usa protocolos autenticados que protejan toda la conexión y todo lo que se envía a través de ella.

Conexiones no Autenticadas

Los protocolos que no tienen ninguna forma de autenticación criptográfica no pueden saber con certeza que se están comunicando con el servidor remoto correcto.

Si tu aplicación está usando un esquema fijo o un nombre de host fijo, no es seguro mientras la conexión no esté autenticada. Podría haber un ataque de "man-in-the-middle" o, de hecho, el servidor completo podría haber sido reemplazado por un actor malintencionado.

Los protocolos no autenticados son inseguros. Los datos que regresan a curl pueden haber sido inyectados por un atacante. Los datos que curl envía pueden ser modificados antes de que lleguen al servidor previsto. Si es que llegan al servidor previsto.

Remedios:

Restringir las operaciones a transferencias autenticadas
Usa protocolos autenticados protegidos con HTTPS o SSH.
Asegurarse de que el certificado del servidor, etc. sea verificado
Nunca deshabilites la verificación de certificados.

Certificados y Conexiones de Larga Duración

La validación de certificados de conexiones cifradas se realiza inmediatamente después de establecerse una conexión. Esa conexión podría usarse para muchas transferencias posteriores, incluso si el certificado utilizado para la validación expira o se revoca, el paquete de certificados local se modifica de manera que habría causado que dicho certificado fallara la validación, el servidor cambia su certificado por uno que habría fallado la validación, o incluso si se introduce un servidor completamente diferente bajo el mismo nombre de host. Esto podría continuar durante muchas horas (o incluso años) después de que ocurra dicho cambio, lo cual puede no ser el comportamiento deseado para algunas aplicaciones.

Remedios:

Usa la opción CURLOPT_MAXLIFETIME_CONN(3) para limitar el tiempo que se utilizan las conexiones después de haber sido validadas exitosamente. Las transferencias posteriores requieren una nueva conexión con validación realizada nuevamente.

Redirecciones

La opción CURLOPT_FOLLOWLOCATION(3) sigue automáticamente las redirecciones HTTP enviadas por un servidor remoto. Estas redirecciones pueden referirse a cualquier tipo de URL, no solo HTTP. libcurl restringe los protocolos permitidos para usarse en redirecciones por razones de seguridad: solo HTTP, HTTPS, FTP y FTPS están habilitados por defecto. Las aplicaciones pueden optar por restringir ese conjunto aún más.

Una redirección a una URL de tipo archivo (file:) haría que libcurl leyera (o escribiera) archivos arbitrarios del sistema de archivos local. Si la aplicación devuelve los datos al usuario (como sucedería en algunos tipos de scripts CGI), un atacante podría aprovechar esto para leer datos prohibidos de otro modo (por ejemplo, file://localhost/etc/passwd).

Si las credenciales de autenticación se almacenan en el archivo ~/.netrc, o se está utilizando Kerberos, cualquier otro tipo de URL (no solo file:) que requiera autenticación también está en riesgo. Una redirección como ftp://some-internal-server/private-file devolvería datos incluso cuando el servidor está protegido por contraseña.

De la misma manera, si se ha configurado una clave privada SSH no cifrada para el usuario que ejecuta la aplicación libcurl, las URL SCP: o SFTP: podrían acceder a recursos protegidos por contraseña o clave privada, por ejemplo, sftp://user@some-internal-server/etc/passwd

Las opciones CURLOPT_REDIR_PROTOCOLS_STR(3) y CURLOPT_NETRC(3) se pueden usar para mitigar este tipo de ataque.

Una redirección también puede especificar una ubicación disponible solo en la máquina que ejecuta libcurl, incluidos servidores ocultos detrás de un firewall para el atacante. Por ejemplo, http://127.0.0.1/ o http://intranet/delete-stuff.cgi?delete=all o tftp://bootp-server/pc-config-data

Las aplicaciones pueden mitigar esto deshabilitando CURLOPT_FOLLOWLOCATION(3) y manejando las redirecciones ellas mismas, sanitizando las URL según sea necesario. Alternativamente, una aplicación podría dejar CURLOPT_FOLLOWLOCATION(3) habilitado pero establecer CURLOPT_REDIR_PROTOCOLS_STR(3) e instalar una función de callback CURLOPT_OPENSOCKETFUNCTION(3) o CURLOPT_PREREQFUNCTION(3) en la cual las direcciones se sanitizan antes de su uso.

CRLF en Cabeceras

Para todas las opciones en libcurl que especifican cabeceras, incluyendo pero no limitado a CURLOPT_HTTPHEADER(3), CURLOPT_PROXYHEADER(3), CURLOPT_COOKIE(3), CURLOPT_USERAGENT(3), CURLOPT_REFERER(3) y CURLOPT_RANGE(3), libcurl envía las cabeceras tal cual y no aplica ninguna

NAME

libcurl security - security considerations for libcurl

Security

libcurl is a powerful tool and with great power comes great responsibility. This document aims to highlight areas where libcurl can be misused or can be used in ways that may compromise security.

This document is not exhaustive, but covers many common areas of concern.

Command Lines

If an application passes arbitrary data to libcurl, this data may be interpreted by libcurl in unintended ways. For example, if a user can supply a URL, and the URL contains characters that are interpreted by the command-line parser itself, this could lead to security problems.

For example, passing a URL like --url "file:///etc/passwd" when expecting a network resource could potentially lead to reading sensitive files. Be sure that user-supplied data is properly sanitized and validated before being passed to libcurl functions or options.

.netrc

libcurl can be instructed to read username and password from a .netrc file (or equivalent). This file often resides in the user's home directory and may contain credentials for multiple hosts. If the application is running with elevated privileges, or if the file is readable by other users, this can be a security risk.

The application using libcurl should ensure that it does not run with unnecessary privileges when using this feature, and that the permissions on the file itself are set appropriately.

Clear Text Passwords

Many protocols supported by libcurl (like FTP, POP3, IMAP, SMTP) allow for authentication using clear text passwords. If the connection is not encrypted (e.g., using TLS/SSL), these passwords can be intercepted by network sniffers. Always prefer using encrypted connections (e.g., FTPS, SMTPS, IMAPS, POP3S) when sensitive authentication data is being transferred.

Even when using encrypted connections, some protocols might still send the username and password in clear text *before* the encryption is established. Ensure that the specific protocol and its secure variant are used correctly.

FTP uses two connections

When performing an FTP transfer, two TCP connections are used: one for setting up the transfer and one for the actual data.

FTP is not only unauthenticated, but the setting up of the second transfer is also a weak spot. The second connection to use for data, is either setup with the PORT/EPRT command that makes the server connect back to the client on the given IP+PORT, or with PASV/EPSV that makes the server setup a port to listen to and tells the client to connect to a given IP+PORT.

Again, unauthenticated means that the connection might be meddled with by a man-in-the-middle or that there is a malicious server pretending to be the right one.

A malicious FTP server can respond to PASV commands with the IP+PORT of a totally different machine. Perhaps even a third party host, and when there are many clients trying to connect to that third party, it could create a Distributed Denial-Of-Service attack out of it. If the client makes an upload operation, it can make the client send the data to another site. If the attacker can affect what data the client uploads, it can be made to work as a HTTP request and then the client could be made to issue HTTP requests to third party hosts.

An attacker that manages to control curl's command line options can tell curl to send an FTP PORT command to ask the server to connect to a third party host instead of back to curl.

The fact that FTP uses two connections makes it vulnerable in a way that is hard to avoid.

Active FTP passes on the local IP address

If you use curl/libcurl to do active FTP transfers, curl passes on the address of your local IP to the remote server - even when for example using a SOCKS or HTTP proxy in between curl and the target server.

Denial of Service

A malicious server could cause libcurl to effectively hang by sending data slowly, or even no data at all but just keeping the TCP connection open. This could effectively result in a denial-of-service attack. The CURLOPT_TIMEOUT(3) and/or CURLOPT_LOW_SPEED_LIMIT(3) options can be used to mitigate against this.

A malicious server could cause libcurl to download an infinite amount of data, potentially causing system resources to be exhausted resulting in a system or application crash. Setting the CURLOPT_MAXFILESIZE_LARGE(3) option is not sufficient to guard against this. Instead, applications should monitor the amount of data received within the write or progress callback and abort once the limit is reached.

A malicious HTTP server could cause an infinite redirection loop, causing a denial-of-service. This can be mitigated by using the CURLOPT_MAXREDIRS(3) option.

Arbitrary Headers

User-supplied data must be sanitized when used in options like CURLOPT_USERAGENT(3), CURLOPT_HTTPHEADER(3), CURLOPT_POSTFIELDS(3) and others that are used to generate structured data. Characters like embedded carriage returns or ampersands could allow the user to create additional headers or fields that could cause malicious transactions.

Server-supplied Names

A server can supply data which the application may, in some cases, use as a filename. The curl command-line tool does this with --remote-header-name, using the Content-disposition: header to generate a filename. An application could also use CURLINFO_EFFECTIVE_URL(3) to generate a filename from a server-supplied redirect URL. Special care must be taken to sanitize such names to avoid the possibility of a malicious server supplying one like "/etc/passwd", "autoexec.bat", "prn:" or even ".bashrc".

Server Certificates

A secure application should never use the CURLOPT_SSL_VERIFYPEER(3) option to disable certificate validation. There are numerous attacks that are enabled by applications that fail to properly validate server TLS/SSL certificates, thus enabling a malicious server to spoof a legitimate one. HTTPS without validated certificates is potentially as insecure as a plain HTTP connection.

Showing What You Do

Relatedly, be aware that in situations when you have problems with libcurl and ask someone for help, everything you reveal in order to get best possible help might also impose certain security related risks. Hostnames, usernames, paths, operating system specifics, etc. (not to mention passwords of course) may in fact be used by intruders to gain additional information of a potential target.

Be sure to limit access to application logs if they could hold private or security-related data. Besides the obvious candidates like usernames and passwords, things like URLs, cookies or even filenames could also hold sensitive data.

To avoid this problem, you must of course use your common sense. Often, you can just edit out the sensitive data or just search/replace your true information with faked data.

setuid applications using libcurl

libcurl-using applications that set the 'setuid' bit to run with elevated or modified rights also implicitly give that extra power to libcurl and this should only be done after careful considerations.

Giving setuid powers to the application means that libcurl can save files using those new rights (if for example the SSLKEYLOGFILE environment variable is set). Also: if the application wants these powers to read or manage secrets that the user is otherwise not able to view (like credentials for a login etc), it should be noted that libcurl still might understand proxy environment variables that allow the user to redirect libcurl operations to use a proxy controlled by the user.

File descriptors, fork and NTLM

An application that uses libcurl and invokes fork() gets all file descriptors duplicated in the child process, including the ones libcurl created.

libcurl itself uses fork() and execl() if told to use the CURLAUTH_NTLM_WB authentication method which then invokes the helper command in a child process with file descriptors duplicated. Make sure that only the trusted and reliable helper program is invoked.

This feature was removed from curl in 8.8.0.

Secrets in memory

When applications pass usernames, passwords or other sensitive data to libcurl to be used for upcoming transfers, those secrets are kept around as-is in memory. In many cases they are stored in the heap for as long as the handle itself for which the options are set.

If an attacker can access the heap, like maybe by reading swap space or via a core dump file, such data might be accessible.

Further, when eventually closing a handle and the secrets are no longer needed, libcurl does not explicitly clear memory before freeing it, so credentials may be left in freed data.

Saving files

libcurl cannot protect against attacks where an attacker has write access to the same directory where libcurl is directed to save files.

Cookies

If libcurl is built with PSL (Public Suffix List) support, it detects and discards cookies that are specified for such suffix domains that should not be allowed to have cookies.

if libcurl is not built with PSL support, it has no ability to stop super cookies.

Report Security Problems

Should you detect or just suspect a security problem in libcurl or curl, contact the project curl security team immediately. See https://curl.se/dev/secprocess.html for details.
