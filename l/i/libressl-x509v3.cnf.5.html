NOMBRE

x509v3.cnf — Formato de configuración de extensiones de certificado X.509 V3

DESCRIPCIÓN

Varias de las utilidades de OpenSSL pueden agregar extensiones a un certificado o solicitud de certificado basándose en el contenido de un archivo de configuración. El formato del archivo se basa en el formato de openssl.cnf(5).

Típicamente la aplicación contendrá una opción para apuntar a una sección de extensiones. Cada línea de la sección de extensiones tiene la forma:

nombre_extension=[critical,] opciones_extension

Si está presente critical, entonces la extensión será crítica.

El formato de opciones_extension depende del valor de nombre_extension.

Hay cuatro tipos principales de extensiones: extensiones de cadena, extensiones de múltiples valores, extensiones en bruto y extensiones arbitrarias.

Las extensiones de cadena simplemente tienen una cadena que contiene el valor en sí o cómo se obtiene. Por ejemplo:

nsComment="Este es un comentario"

Las extensiones de múltiples valores tienen una forma corta y una forma larga. La forma corta es una lista de nombres y valores:

basicConstraints=critical,CA:true,pathlen:1

La forma larga permite que los valores se coloquen en una sección separada:

basicConstraints=critical,@bs_section

[bs_section]
CA=true
pathlen=1

Ambas formas son equivalentes.

La sintaxis de las extensiones en bruto está regida por el código de extensión: puede contener, por ejemplo, datos en múltiples secciones. La sintaxis correcta a usar está definida por el propio código de extensión: consulte la extensión de políticas de certificado para ver un ejemplo.

Si un tipo de extensión no es compatible, entonces se debe usar la sintaxis de extensiones arbitrarias; consulte la sección EXTENSIONES ARBITRARIAS para más detalles.

EXTENSIONES ESTÁNDAR

Las siguientes secciones describen cada extensión soportada en detalle.

Restricciones básicas

Esta es una extensión de múltiples valores que indica si un certificado es un certificado de CA. El primer nombre (obligatorio) es CA seguido de TRUE o FALSE. Si CA es TRUE, entonces se puede incluir un nombre opcional pathlen seguido de un valor no negativo. Por ejemplo:

basicConstraints=CA:TRUE
basicConstraints=CA:FALSE
basicConstraints=critical,CA:TRUE, pathlen:0

Un certificado de CA debe incluir el valor basicConstraints con el campo CA establecido a TRUE. Un certificado de usuario final debe establecer CA a FALSE o excluir la extensión por completo. Algunos software pueden requerir la inclusión de basicConstraints con CA establecido a FALSE para certificados de entidad final.

El parámetro pathlen indica el número máximo de CAs que pueden aparecer debajo de esta en una cadena. Así que si tienes una CA con un pathlen de cero, solo puede usarse para firmar certificados de usuario final y no más CAs.

Uso de clave

El uso de clave es una extensión de múltiples valores que consta de una lista de nombres de los usos de clave permitidos.

Los nombres soportados son: digitalSignature, nonRepudiation, keyEncipherment, dataEncipherment, keyAgreement, keyCertSign, cRLSign, encipherOnly, y decipherOnly. Ejemplos:

keyUsage=digitalSignature, nonRepudiation
keyUsage=critical, keyCertSign

Uso extendido de clave

Esta extensión consta de una lista de propósitos para los cuales se puede usar la clave pública del certificado.

Estos pueden ser nombres cortos de objetos o la forma numérica punteada de OIDs. Aunque se puede usar cualquier OID, solo ciertos valores tienen sentido. En particular, los siguientes valores PKIX, NS y MS son significativos:

Identificador de clave de sujeto

Esta es realmente una extensión de cadena y puede tomar dos valores posibles. Ya sea la palabra hash que seguirá automáticamente las directrices del RFC 3280 o una cadena hexadecimal que proporciona el valor de extensión a incluir. El uso de la cadena hexadecimal se desaconseja encarecidamente. Ejemplo:

subjectKeyIdentifier=hash

Identificador de clave de autoridad

La extensión de identificador de clave de autoridad permite dos opciones, keyid e issuer: ambas pueden tomar el valor opcional always.

Si está presente la opción keyid, se intenta copiar el identificador de clave del sujeto del certificado padre. Si está presente el valor always, se devuelve un error si la opción falla.

La opción issuer copia el emisor y el número de serie del certificado emisor. Esto solo se hará si la opción keyid falla o no se incluye a menos que la bandera always incluya siempre el valor. Ejemplo:

authorityKeyIdentifier=keyid,issuer

NAME

x509v3.cnf

configuration file for X509 v3 extensions

DESCRIPTION

The x509v3.cnf file is a text file used to specify X509 v3 extensions. It uses a simple text format consisting of sections, each beginning with a name enclosed in square brackets, followed by a series of tag=value or tag=section assignments.

This file can be used to define standard extensions, deprecated extensions, and arbitrary extensions. The format is identical to that used by the OpenSSL configuration file, openssl.cnf(5).

STANDARD EXTENSIONS

The following extensions are defined by RFC 3280 and related documents. They are generally used to provide additional information about a certificate or to convey policy information.

TLS Feature (aka must staple)

This is a multi-valued extension consisting of a list of TLS extension identifiers. Each identifier may be a number in the range from 0 to 65535 or a supported name. When a TLS client sends a listed extension, the TLS server is expected to include that extension in its reply.

The supported names are: status_request and status_request_v2. Example:

tlsfeature = status_request

DEPRECATED EXTENSIONS

The following extensions are non-standard, Netscape specific and largely obsolete. Their use in new applications is discouraged.

Netscape string extensions

Netscape comment (nsComment) is a string extension containing a comment which will be displayed when the certificate is viewed in some browsers. Example:

nsComment = Some Random Comment

Other supported extensions in this category are: nsBaseUrl, nsRevocationUrl, nsCaRevocationUrl, nsRenewalUrl, nsCaPolicyUrl, and nsSslServerName.

Netscape certificate type

This is a multi-valued extensions which consists of a list of flags to be included. It was used to indicate the purposes for which a certificate could be used. The basicConstraints, keyUsage, and extended key usage extensions are now used instead.

Acceptable values for nsCertType are: client, server, email, objsign, reserved, sslCA, emailCA, objCA.

ARBITRARY EXTENSIONS

If an extension is not supported by the OpenSSL code, then it must be encoded using the arbitrary extension format. It is also possible to use the arbitrary format for supported extensions. Extreme care should be taken to ensure that the data is formatted correctly for the given extension type.

There are two ways to encode arbitrary extensions.

The first way is to use the word ASN1 followed by the extension content using the same syntax as ASN1_generate_nconf(3). For example:

1.2.3.4=critical,ASN1:UTF8String:Some random data
1.2.3.4=ASN1:SEQUENCE:seq_sect

[seq_sect]
field1 = UTF8:field1
field2 = UTF8:field2

It is also possible to use the word DER to include the raw encoded data in any extension.

1.2.3.4=critical,DER:01:02:03:04
1.2.3.4=DER:01020304

The value following DER is a hex dump of the DER encoding of the extension. Any extension can be placed in this form to override the default behaviour. For example:

basicConstraints=critical,DER:00:01:02:03

HISTORY

X509v3 extension code was first added to OpenSSL 0.9.2.

CAVEATS

There is no guarantee that a specific implementation will process a given extension. It may therefore sometimes be possible to use certificates for purposes prohibited by their extensions because a specific application does not recognize or honour the values of the relevant extensions.

The DER and ASN1 options should be used with caution. It is possible to create totally invalid extensions if they are not used carefully.

If an extension is multi-value and a field value must contain a comma, the long form must be used. Otherwise the comma would be misinterpreted as a field separator. For example,

subjectAltName=URI:ldap://somehost.com/CN=foo,OU=bar

will produce an error, but the following form is valid:

subjectAltName=@subject_alt_section

[subject_alt_section]
subjectAltName=URI:ldap://somehost.com/CN=foo,OU=bar

Due to the behaviour of the OpenSSL CONF library, the same field name can only occur once in a section. That means that

subjectAltName=@alt_section

[alt_section]
email=steve@here
email=steve@there

will only use the last value. This can be worked around by using the form:

[alt_section]
email.1=steve@here
email.2=steve@there
