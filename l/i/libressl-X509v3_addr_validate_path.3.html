X509V3_ADDR_VALIDATE_PATH(3) Manual de funciones de biblioteca X509V3_ADDR_VALIDATE_PATH(3)

NOMBRE

X509v3_addr_validate_path, X509v3_addr_validate_resource_set, X509v3_asid_validate_path, X509v3_asid_validate_resource_set — validación de ruta RFC 3779 para delegación de direcciones IP y números de AS

SINOPSIS

biblioteca “libcrypto”
#include <openssl/x509v3.h>

int
X509v3_addr_validate_path(X509_STORE_CTX *ctx);

int
X509v3_addr_validate_resource_set(STACK_OF(X509) *chain, IPAddrBlocks *addrblocks, int allow_inherit);

int
X509v3_asid_validate_path(X509_STORE_CTX *ctx);

int
X509v3_asid_validate_resource_set(STACK_OF(X509) *chain, ASIdentifiers *asid, int allow_inherit);

DESCRIPCIÓN

Ambas extensiones RFC 3779 requieren verificaciones adicionales en la validación de la ruta de certificación.

  1. El conjunto inicial de recursos de direcciones IP y números de AS permitidos se define en el ancla de confianza, donde no se permite la herencia.
  2. Un emisor solo puede delegar subconjuntos de recursos presentes en sus extensiones RFC 3779 o subconjuntos de recursos heredados de su emisor.
  3. Si una extensión RFC 3779 está presente en un certificado, el mismo tipo de extensión también debe estar presente en su emisor.
  4. Todas las extensiones RFC 3779 que aparecen en la ruta de validación deben estar en forma canónica de acuerdo con X509v3_addr_is_canonical(3) y X509v3_asid_is_canonical(3).

X509v3_addr_validate_path() y X509v3_asid_validate_path() son llamadas desde X509_verify_cert(3) como parte de la construcción de la cadena de verificación. Al encontrar un error o una infracción de las reglas anteriores, error, error_depth, y current_cert se establecen en ctx y se llama a la devolución de llamada de verificación con ok establecido en 0. X509_V_ERR_INVALID_EXTENSION indica un recurso no canónico, X509_V_ERR_UNNESTED_RESOURCE indica una infracción de las otras reglas anteriores. En raras circunstancias, el error puede ser X509_V_ERR_UNSPECIFIED y para direcciones IP los recursos X509_V_ERR_OUT_OF_MEM también son posibles.

X509v3_addr_validate_resource_set() valida los recursos en addrblocks contra un certificado específico chain. Después de verificar que addrblocks es canónico, sus direcciones IP se verifican para que estén cubiertas en el certificado en la profundidad 0, luego la cadena se recorre hasta el ancla de confianza hasta que se encuentre un error o una infracción de las reglas anteriores. addrblocks tiene permitido usar herencia de acuerdo con X509v3_addr_inherits(3) si y solo si allow_inherit es distinto de cero.

X509v3_asid_validate_resource_set() realiza verificaciones similares a X509v3_addr_validate_resource_set() para asid.

VALORES DE RETORNO

Todas estas funciones devuelven 1 en caso de validación exitosa y 0 en caso contrario.

Para X509v3_addr_validate_path() y X509v3_asid_validate_path() una no vacía chain y una verify_cb deben estar presentes en ctx, de lo contrario fallan y establecen el error en ctx a X509_V_ERR_UNSPECIFIED. La verify_cb se llama con los códigos de error descritos anteriormente en la mayoría de los errores encontrados durante la validación. Algunas extensiones malformadas pueden provocar un error que no puede ser interceptado por la devolución de llamada. Con la excepción de un error de asignación, no se establecen códigos de error en la pila de errores.

X509v3_addr_validate_resource_set() acepta un NULL addrblocks y X509v3_asid_validate_resource_set() acepta un NULL asid como válido. Fallan si chain es NULL o está vacío. Si allow_inherit es 0, addrblocks o asid se verifica para herencia con X509v3_addr_inherits(3) o X509v3_asid_inherits(3). Los casos de fallo restantes son los mismos que para X509v3_addr_validate_path() y X509v3_asid_validate_path(). No pueden ni intentan comunicar la causa del error al llamador.
