NOMBRE

libarchive_internals — descripción de las interfaces internas de libarchive

VISTA GENERAL

La biblioteca libarchive proporciona una interfaz flexible para leer y escribir archivos de archivo en streaming como tar y cpio. Internamente, sigue un diseño modular en capas que debería facilitar la adición de nuevos formatos de archivo y compresión.

ARQUITECTURA GENERAL

Externamente, libarchive expone la mayoría de las operaciones a través de una interfaz opaca, similar a objetos. Los objetos archive_entry(3) almacenan información sobre un único objeto del sistema de archivos. El resto de la biblioteca proporciona facilidades para escribir objetos archive_entry(3) en archivos de archivo, leerlos desde archivos de archivo y escribirlos en disco. (Hay planes para añadir una facilidad para leer objetos archive_entry(3) desde disco también.)

Las APIs de lectura y escritura tienen cada una cuatro capas: una capa de API pública, una capa de formato que entiende el formato del archivo de archivo, una capa de compresión y una capa de E/S. La capa de E/S está completamente expuesta a los clientes, quienes pueden reemplazarla por completo con sus propias funciones.

Para proporcionar la mayor consistencia posible para los clientes, algunas funciones públicas están virtualizadas. Eventualmente, debería ser posible para los clientes abrir un archivo o un escritor de disco, y luego usar un único conjunto de código para seleccionar y escribir entradas, independientemente del destino.

ARQUITECTURA DE LECTURA

Desde el exterior, los clientes utilizan la API de archive_read(3) para manipular un objeto archive para leer entradas y cuerpos de un flujo de archivo. Internamente, el objeto archive se convierte en un objeto archive_read, que contiene todos los datos específicos de la lectura. La API tiene cuatro capas: La capa más baja es la capa de E/S. Esta capa puede ser anulada por los clientes, pero la mayoría de los clientes utilizan las devoluciones de llamada de E/S empaquetadas proporcionadas, por ejemplo, por archive_read_open_memory(3) y archive_read_open_fd(3). La capa de compresión llama a la capa de E/S para leer bytes y los descomprime para la capa de formato. La capa de formato desempaqueta un flujo de bytes sin comprimir y crea objetos archive_entry a partir de los datos entrantes. La capa de API rastrea el estado general (por ejemplo, evita que los clientes lean datos antes de leer una cabecera) e invoca las operaciones de las capas de formato y compresión a través de punteros de función registrados. En particular, la capa de API impulsa el proceso de detección de formato: al abrir el archivo, lee un bloque de datos inicial y lo ofrece a cada manejador de compresión registrado. El que tenga la mayor oferta se inicializa con el primer bloque. Del mismo modo, se consulta a los manejadores de formato para ver cuál es el mejor para cada archivo. (Antes de la versión 2.4.0, los licitadores de formato se invocaban para cada entrada, pero este diseño dificultaba la recuperación de errores.)

Capa de E/S y Devoluciones de Llamada del Cliente

La API de lectura hace todo lo posible para ser amigable con los clientes. Como resultado, hay pocas restricciones sobre el comportamiento de las devoluciones de llamada del cliente.

Se espera que la devolución de llamada de lectura del cliente proporcione un bloque de datos en cada llamada. Un retorno de longitud cero indica fin de archivo, pero de lo contrario, los bloques pueden ser tan pequeños como un byte o tan grandes como todo el archivo. En particular, los bloques pueden ser de diferentes tamaños.

La devolución de llamada de salto del cliente devuelve el número de bytes realmente omitidos, que puede ser mucho menor que el salto solicitado. El único requisito es que el salto no sea mayor. En particular, se permite a los clientes devolver cero para cualquier salto que no quieran manejar. La devolución de llamada de salto nunca debe invocarse con un valor negativo.

Tenga en cuenta que no todos los clientes leen desde disco: los clientes que leen desde redes pueden proporcionar bloques de diferentes tamaños en cada solicitud y no pueden omitir nada; los clientes avanzados pueden usar mmap(2) para leer todo el archivo en memoria a la vez y devolver todo el archivo a libarchive como un solo bloque; otros clientes pueden iniciar operaciones de E/S asíncronas para el siguiente bloque en cada solicitud.

Capa de descompresión

La capa de descompresión no solo maneja la descompresión, sino que también almacena datos en búfer para que los manejadores de formato vean un modelo de E/S más agradable. La API de descompresión es un modelo de dos etapas de previsualización/consumo. Una solicitud de read_ahead especifica una cantidad mínima de lectura; la capa de descompresión debe proporcionar un puntero a al menos esa cantidad de datos. Si hay más datos disponibles inmediatamente, debería devolver más: la capa de formato maneja lecturas de datos en bloque solicitando un mínimo de un byte y luego copiando tantos datos como estén disponibles.

Una llamada posterior a la función consume() avanza el puntero de lectura. Tenga en cuenta que los datos devueltos por una llamada a read_ahead() garantizan que permanecerán en su lugar hasta la próxima llamada a read_ahead(). Las llamadas intermedias a consume() no deben hacer que los datos se muevan.

Las solicitudes de salto deben manejarse siempre exactamente. Los manejadores de descompresión que no pueden buscar hacia adelante no deben registrar un manejador de salto; la capa de API completa un manejador de salto genérico que lee y descarta datos.

Un manejador de descompresión tiene un ciclo de vida específico:

Registro/Configuración
Cuando el cliente invoca la función de soporte público, el manejador de descompresión invoca la función interna __archive_read_register_compression() para proporcionar funciones de licitación e inicialización. Esta función devuelve NULL en caso de error o bien un puntero a una struct decompressor_t. Esta estructura contiene una ranura void * config que puede usarse para almacenar cualquier información de personalización.
Licitación
La función de licitación se invoca con un puntero y el tamaño de un bloque de datos. El descompresor puede acceder a sus datos de configuración a través del elemento decompressor del objeto archive_read. La función de licitación es, por lo demás, sin estado. En particular, no debe realizar ninguna operación de E/S.

El valor devuelto por la función de licitación indica su idoneidad para manejar este flujo de datos. Una oferta de cero asegurará que este descompresor nunca se invoque. Devuelva cero si las comprobaciones de número mágico fallan. De lo contrario, su implementación inicial debería devolver el número de bits comprobados realmente. Por ejemplo, si verifica dos bytes completos y tres bits de otro byte, ofrezca 19. Tenga en cuenta que el bloque inicial puede ser muy corto; tenga cuidado de inspeccionar solo los datos que se le proporcionan. (Los descompresores actuales requieren dos bytes para una licitación correcta.)

Inicializar
Al ganador de la licitación se le llamará su función init. Esta función debe inicializar las ranuras restantes del objeto struct decompressor_t apuntado por el elemento decompressor del objeto archive_read. En particular, debe asignar cualquier dato de trabajo que necesite en la ranura data de esa estructura. La función init se llama con el bloque de datos que se utilizó para la prueba. En este punto, el descompresor es responsable de todas las solicitudes de E/S a las devoluciones de llamada del cliente. El descompresor es libre de leer más datos según sea necesario.
Satisfacer solicitudes de E/S
El manejador de formato invocará las funciones read_ahead, consume y skip según sea necesario.
Finalizar
El método de finalización se llama solo una vez cuando se cierra el archivo. Debe liberar todo lo almacenado en las ranuras data y config del objeto decompressor. No debe invocar la devolución de llamada de cierre del cliente.

NAME

libarchive internals — how to extend libarchive

OVERVIEW

This document describes the internal architecture of libarchive and how to add new formats or compression methods to it.

GENERAL ARCHITECTURE

libarchive supports both reading and writing archives. Both operations are structured as a pipeline of layers:

  • API Layer
  • Format Layer
  • Compression Layer
  • I/O Layer

The API layer provides the public interface. The format layer handles the specifics of a particular archive format (e.g., tar, zip). The compression layer handles compression and decompression (e.g., gzip, bzip2). The I/O layer handles the underlying character-set conversions and buffered I/O.

For reading, the layers are:

archive_read() calls a format reader, which calls a compression reader, which calls an I/O reader.

For writing, the layers are:

archive_write() calls a format writer, which calls a compression writer, which calls an I/O writer.

The archive_write_disk() function is a special case which bypasses the format and compression layers, writing directly to the disk.

READ ARCHITECTURE

The read interface has a number of features that make it challenging to implement new formats. These include support for multiple archive formats, multiple compression methods, sparse files, and an API that allows clients to look ahead in the input stream.

Initialize Data Structures
When a new archive reader is created, you need to initialize your data structures and pointers.
Bid
Formats the bid by invoking the read_ahead() decompression method but not calling the consume() method. This allows each bidder to look ahead in the input stream. Bidders should not look further ahead than necessary, as long look aheads put pressure on the decompression layer to buffer lots of data. Most formats only require a few hundred bytes of look ahead; look aheads of a few kilobytes are reasonable. (The ISO9660 reader sometimes looks ahead by 48k, which should be considered an upper limit.)
Read header
The header read is usually the most complex part of any format. There are a few strategies worth mentioning: For formats such as tar or cpio, reading and parsing the header is straightforward since headers alternate with data. For formats that store all header data at the beginning of the file, the first header read request may have to read all headers into memory and store that data, sorted by the location of the file data. Subsequent header read requests will skip forward to the beginning of the file data and return the corresponding header.
Read Data
The read data interface supports sparse files; this requires that each call return a block of data specifying the file offset and size. This may require you to carefully track the location so that you can return accurate file offsets for each read. Remember that the decompressor will return as much data as it has. Generally, you will want to request one byte, examine the return value to see how much data is available, and possibly trim that to the amount you can use. You should invoke consume for each block just before you return it.
Skip All Data
The skip data call should skip over all file data and trailing padding. This is called automatically by the API layer just before each header read. It is also called in response to the client calling the public data_skip() function.
Cleanup
On cleanup, the format should release all of its allocated memory.

WRITE_DISK ARCHITECTURE

The write_disk API is intended to look just like the write API to clients. Since it does not handle multiple formats or compression, it is not layered internally.

GENERAL SERVICES

The archive_read, archive_write, and archive_write_disk objects all contain an initial archive object which provides common support for a set of standard services. (Recall that ANSI/ISO C90 guarantees that you can cast freely between a pointer to a structure and a pointer to the first element of that structure.) The archive object has a magic value that indicates which API this object is associated with, slots for storing error information, and function pointers for virtualized API functions.

MISCELLANEOUS NOTES

Connecting existing archiving libraries into libarchive is generally quite difficult. In particular, many existing libraries strongly assume that you are reading from a file; they seek forwards and backwards as necessary to locate various pieces of information. In contrast, libarchive never seeks backwards in its input, which sometimes requires very different approaches.

For example, libarchive's ISO9660 support operates very differently from most ISO9660 readers. The libarchive support utilizes a work-queue design that keeps a list of known entries sorted by their location in the input. Whenever libarchive's ISO9660 implementation is asked for the next header, checks this list to find the next item on the disk. Directories are parsed when they are encountered and new items are added to the list. This design relies heavily on the ISO9660 image being optimized so that directories always occur earlier on the disk than the files they describe.

Depending on the specific format, such approaches may not be possible. The ZIP format specification, for example, allows archivers to store key information only at the end of the file. In theory, it is possible to create ZIP archives that cannot be read without seeking. Fortunately, such archives are very rare, and libarchive can read most ZIP archives, though it cannot always extract as much information as a dedicated ZIP program.
