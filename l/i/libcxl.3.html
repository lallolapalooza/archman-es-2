LIBCXL(3) Manual de libcxl LIBCXL(3)

NOMBRE

libcxl - Una biblioteca para interactuar con dispositivos CXL a través de las interfaces sysfs(5) e ioctl(2)

SINOPSIS

#include <cxl/libcxl.h>
cc ... -lcxl

DESCRIPCIÓN

libcxl proporciona interfaces para interactuar con dispositivos CXL en Linux, utilizando interfaces sysfs para la mayoría de las interacciones del kernel y la interfaz ioctl() para la submisión de comandos.

El punto de partida para todas las interfaces de la biblioteca es un objeto cxl_ctx, devuelto por linklibcxl:cxl_new[3]. Los dispositivos de memoria CXL Tipo 3 y otros objetos de dispositivo CXL son descendientes del objeto cxl_ctx, y pueden ser iterados a través de una API iteradora de objetos de la forma cxl_<objeto>_foreach(<objeto padre>, <iterador de objeto>).

MEMDEVS

El objeto que representa un expansor de memoria CXL (dispositivo Tipo 3) es struct cxl_memdev. Las interfaces de la biblioteca relacionadas con estos dispositivos tienen el prefijo cxl_memdev_. Estas interfaces están mayormente asociadas con interacciones sysfs (a menos que se indique lo contrario en sus respectivas secciones de documentación). Típicamente se utilizan para recuperar datos publicados por el kernel, o para enviar datos o activar operaciones del kernel para un dispositivo dado.

struct cxl_memdev *cxl_memdev_get_first(struct cxl_ctx *ctx);
struct cxl_memdev *cxl_memdev_get_next(struct cxl_memdev *memdev);

#define cxl_memdev_foreach(ctx, memdev) \
        for (memdev = cxl_memdev_get_first(ctx); \
             memdev != NULL; \
             memdev = cxl_memdev_get_next(memdev))

Las instancias de memdev CXL se enumeran desde el contexto global de la biblioteca struct cxl_ctx. Por defecto, un memdev solo ofrece un portal para enviar comandos del dispositivo de memoria, consulte las APIs de puerto, decodificador y punto final para determinar qué Recursos de Memoria CXL, si los hay, son accesibles dado un memdev específico.

El host de un memdev es el dispositivo de Punto Final PCIe que registró sus capacidades CXL con el núcleo CXL de Linux.

A un memdev se le da un nombre de dispositivo del kernel de la forma "mem%d" donde un id (cxl_memdev_get_id()) se asigna dinámicamente a medida que se descubren los dispositivos. Tenga en cuenta que no hay garantías de que los ids / nombres de dispositivos del kernel para los memdevs sean estables de un arranque a otro, los dispositivos se enumeran de forma asíncrona. Si se necesita un identificador estable, utilice cxl_memdev_get_serial() que devuelve un valor de acuerdo con la Extensión de Capacidad de Número de Serie del Dispositivo en la Especificación Base PCIe 5.0.

El nodo del dispositivo de caracteres para la submisión de comandos se puede encontrar por defecto en /dev/cxl/mem%d, o se crea con un mayor / menor devuelto por cxl_memdev_get_{major,minor}().

Los atributos pmem_size y ram_size devuelven el aprovisionamiento actual de DPA (Dirección Física del Dispositivo / capacidad local) en el dispositivo.

cxl_memdev_get_numa_node() devuelve el número de nodo de CPU afín si está disponible o -1 en caso contrario.

cxl_memdev_wait_sanitize() si una operación de sanitización está en curso cuando se llama a esta función, el programa se bloqueará hasta que la operación de sanitización se complete o la espera finalice.

MEMDEV: Control

int cxl_memdev_disable_invalidate(struct cxl_memdev *memdev);
int cxl_memdev_enable(struct cxl_memdev *memdev);

Cuando un dispositivo de memoria se deshabilita, anula el registro de sus puntos finales asociados y potencialmente los puertos de switch intervinientes si no hay otros memdevs que mantengan ese puerto activo. Esto significa que cualquier objeto de puerto existente que la biblioteca haya devuelto previamente ya no es válido y debe ser re-leído. Los llamantes deben tener cuidado de recuperar los objetos de puerto después de cxl_memdev_disable_invalidate(). Cualquier uso de un objeto de puerto obtenido previamente después de una llamada a cxl_memdev_disable_invalidate() es un error de programación de uso después de liberado. Se deduce que después de cxl_memdev_enable() pueden aparecer nuevos puertos en la topología que anteriormente no eran enumerables.


Nota

cxl_memdev_disable_invalidate() forzará la deshabilitación del memdev
independientemente de si la memoria proporcionada por el dispositivo está en uso activo por el sistema operativo. Los llamantes asumen la responsabilidad de asegurar que es seguro deshabilitar el dispositivo de memoria. De lo contrario, esta llamada puede ser tan destructiva como arrancar un DIMM de un sistema en funcionamiento. Al igual que todas las demás llamadas de libcxl que mutan el estado del sistema o divulgan información sensible de seguridad, esta llamada requiere privilegios de root / CAP_SYS_ADMIN.

Un cxl_cmd es un objeto referenciado que se utiliza para realizar comandos de Buzón (Mailbox) como se describe en la Especificación CXL. Un objeto cxl_cmd está vinculado a un cxl_memdev. Las interfaces de biblioteca asociadas tienen el prefijo cxl_cmd_. Dentro de esta subclase de interfaces, hay:

•Interfaces cxl_cmd_new_*() que asignan un nuevo objeto cxl_cmd para un tipo de comando dado dirigido a un memdev dado. Como parte del proceso de instanciación del comando, la biblioteca valida que el comando sea compatible con el dispositivo de memoria, de lo contrario, devuelve NULL para indicar sin soporte. El id del comando libcxl es traducido por el kernel a un opcode estándar CXL. Consulte los posibles ids de comando en /usr/include/linux/cxl_mem.h.
•Interfaces cxl_cmd_<nombre>_set_<campo> que establecen campos específicos en un cxl_cmd
•cxl_cmd_submit que envía el comando a través de ioctl()
•Interfaces cxl_cmd_<nombre>_get_<campo> que obtienen campos específicos de la respuesta del comando
•Interfaces cxl_cmd_get_* para obtener información general relacionada con el comando.

cxl_cmd_new_raw() soporta los llamados comandos RAW donde el id del comando es RAW y transporta una carga de comando de dispositivo de memoria CXL sin modificar asociada con el argumento opcode. Dado que el kernel realiza una validación mínima de entrada en estos comandos, típicamente los comandos raw no son soportados por el kernel fuera de los escenarios de compilación de depuración. libcxl se limita a soportar comandos que aparecen en el estándar CXL / especificaciones públicas.

cxl_memdev{read,write,zero}_label() son ayudantes para organizar múltiples comandos de acceso a etiquetas sobre una extensión arbitraria de la etiqueta del dispositivo

PARTITIONING

CXL partitioning allows a single CXL device to be partitioned into multiple virtual CXL devices. Partitioning support is exposed via the sysfs interface, and managed via the CXL library.

PARTITION: Set Mode

The cxl_cmd_partition_set_mode() admite la selección del modo NEXTBOOT o IMMEDIATE. Cuando se establece el modo CXL_SETPART_IMMEDIATE, es responsabilidad del llamador evitar cambios inmediatos en la partición cuando el dispositivo está en uso. Cuando se establece el modo CXL_SETPART_NEXTBOOT, el cambio en la partición se convertirá en la configuración "siguiente", que se activará en el próximo reinicio del dispositivo.

BUSES

El espacio de memoria CXL es coherente con la CPU y el dispositivo. Los rangos de direcciones que admiten acceso coherente son descritos por el firmware de la plataforma y comunicados al sistema operativo a través de un objeto raíz CXL, struct cxl_bus.

BUS: Enumeración

       for (bus = cxl_bus_get_first(ctx); bus != NULL;                      \
            bus = cxl_bus_get_next(bus))

Cuando un memdev está activo, ha establecido una jerarquía de puertos CXL entre él y la raíz de su topología CXL asociada. Los auxiliares cxl_{memdev,endpoint}_get_bus() recorren esa topología para recuperar el objeto de bus asociado.

BUS: Atributos

const char *cxl_bus_get_provider(struct cxl_bus *bus);
const char *cxl_bus_get_devname(struct cxl_bus *bus);
int cxl_bus_get_id(struct cxl_bus *bus);

El nombre del proveedor de un bus es un nombre persistente independiente del orden de descubrimiento. Los nombres de proveedor posibles son ACPI.CXL y cxl_test. Los atributos devname e id, como otros objetos, son solo los nombres de dispositivos del kernel que están sujetos a cambios basados en el orden de descubrimiento.

BUS: Control

int cxl_bus_disable_invalidate(struct cxl_bus *bus);

Se puede desmantelar una topología CXL completa con esta API. Como otras APIs _invalidate, los llamadores deben asumir que todos los objetos de la biblioteca han sido liberados. Esta va un paso más allá y también libera el argumento @bus. Esto puede causar fallos en el sistema y solo es útil en escenarios de desarrollo de controladores del kernel.

PUERTOS

Los puertos CXL rastrean la jerarquía PCIe entre un objeto raíz CXL del firmware de la plataforma, a través de puentes host CXL / PCIe, puertos raíz CXL / PCIe y puertos de switch CXL / PCIe.

       for (port = cxl_port_get_first(parent); port != NULL;                \
            port = cxl_port_get_next(port))
#define cxl_port_foreach_all(top, port)                                        \
       for (port = cxl_port_get_first(top); port != NULL;                     \
            port = cxl_port_get_next_all(port, top))

Un objeto de bus encapsula un objeto de puerto CXL. Utilice cxl_bus_get_port() para usar APIs de puertos genéricas en objetos raíz.

Los puertos son jerárquicos. Todos, excepto un objeto raíz, tienen otro puerto CXL como objeto padre recuperable a través de cxl_port_get_parent().

El puerto raíz de una jerarquía se puede recuperar a través de cualquier instancia de puerto en esa jerarquía a través de cxl_port_get_bus().

El host de un puerto es el nombre del dispositivo correspondiente del puerto raíz PCIe, o el puerto upstream del switch con capacidades CXL.

El auxiliar cxl_port_foreach_all() realiza una iteración en profundidad de todos los puertos debajo del argumento de puerto top.

El tipo de puerto se comunica a través de cxl_port_is_<type>(). Un puerto habilitado es aquel que ha logrado descubrir los registros de componentes CXL en el dispositivo host y ha enumerado sus puertos downstream. Para que un memdev esté habilitado para la operación de memoria CXL, todos los puertos CXL en su ascendencia también deben estar habilitados, incluido un puerto raíz, un número arbitrario de puertos de switch intermedios y un puerto de punto final terminal.

cxl_port_hosts_memdev() devuelve verdadero si el host del puerto aparece en la ascendencia de la topología del dispositivo del host del memdev.

El nodo físico de un dport solo está disponible para los puertos downstream definidos por el firmware de la plataforma y alias del objeto compañero, como un puente host PCI, en la jerarquía de dispositivos PCI.

El auxiliar cxl_dport_maps_memdev() verifica si un dport es un ancestro de un memdev dado.

PUNTOS FINALES

Los objetos de punto final CXL encapsulan el conjunto de decodificadores de memoria de dispositivo (HDM) administrados por el host en un dispositivo de memoria físico. El punto final es el último salto en una cadena de decodificadores que traducen SPA a DPA (dirección física del sistema a dirección física local del dispositivo).

DECODIFICADORES

Los objetos de decodificador están asociados con la "Capacidad del Decodificador HDM" publicada en dispositivos de Puerto y puntos finales PCIe capaces de CXL. El kernel también modela rangos de memoria CXL descritos por el firmware de la plataforma (como el ACPI CEDT.CFMWS) como objetos de decodificador estáticos. Enrutan las Direcciones Físicas del Sistema a través de una topología de puertos a un decodificador de punto final que realiza la traducción final de SPA a DPA (dirección física del sistema a dirección física local del dispositivo).

DEPRECATED

The following functions are deprecated and may be removed in future versions of libcxldev:

cxl_decoder_get_target_type()
Use cxl_decoder_get_mode() instead. The enum cxl_decoder_target_type is also deprecated.

DESCRIPTION

This API provides the ability to enumerate and modify CXL (Compute Express Link) topology components including decoders, targets, and regions.

DECODERS

A decoder is an abstract representation of a CXL port that controls the routing of System Physical Addresses (SPA) to downstream devices. The CXL topology is a hierarchy of these decoders, starting from a root decoder.

The kernel protects the enumeration of the physical address layout of the system. Without CAP_SYS_ADMIN cxl_decoder_get_resource() returns ULLONG_MAX to indicate that the address information was not retrievable. Otherwise, cxl_decoder_get_resource() returns the currently programmed value of the base of the decoder’s decode range. A zero-sized decoder indicates a disabled decoder.

Root level decoders only support limited set of memory types in their address range. The cxl_decoder_is_<memtype>_capable() helpers identify what is supported. Switch level decoders, in contrast are capable of routing any memory type, i.e. they just forward along the memory type support from their parent port. Endpoint decoders follow the capabilities of their host memory device.

The capabilities of a decoder are not to be confused with their type / mode. The type ultimately depends on the endpoint. For example an accelerator requires all decoders in its ancestry to be set to CXL_DECODER_TTYPE_ACCELERATOR, and conversely plain memory expander devices require CXL_DECODER_TTYPE_EXPANDER.

Platform firmware may setup the CXL decode hierarchy before the OS boots, and may additionally require that the OS not change the decode settings. This property is indicated by the cxl_decoder_is_locked() API.

When a decoder is associated with a region cxl_decoder_get_region() returns that region object. Note that it is only applicable to switch and endpoint decoders as root decoders have a 1:N relationship with regions. Use cxl_region_foreach() for the similar functionality for root decoders.

TARGETS

A root or switch level decoder takes an SPA (system-physical-address) as input and routes it to a downstream port. Which downstream port depends on the downstream port’s position in the interleave. A struct cxl_target object represents the properties of a given downstream port relative to its interleave configuration.

#define cxl_target_foreach(decoder, target)                                   \
       for (target = cxl_target_get_first(decoder); target != NULL;           \
            target = cxl_target_get_next(target))

Target objects can only be enumerated if the decoder has been configured, for switch decoders. For root decoders they are always available since the root decoder target mapping is static. The cxl_decoder_get_target_by_memdev() helper walks the topology to validate if the given memory device is capable of receiving cycles from this upstream decoder. It does not validate if the memory device is currently configured to participate in that decode.

The position of a decoder along with the interleave granularity dictate which address in the decoder’s resource range map to which port.

The target id is an identifier that the CXL port uses to reference this downstream port. For CXL / PCIe downstream switch ports the id is defined by the PCIe Link Capability Port Number field. For root decoders the id is specified by platform firmware specific mechanism. For ACPI.CXL defined root ports the id comes from the CEDT.CHBS / ACPI0016 _UID.

The device name of a target is the name of the host device for the downstream port. For CXL / PCIe downstream ports the devname is downstream switch port PCI device. For CXL root ports the devname is a platform firmware object for the host bridge like a ACPI0016 device instance.

The cxl_target_maps_memdev() helper is the companion of cxl_decoder_get_target_by_memdev() to determine which downstream ports / targets are capable of mapping which memdevs.

Some platform firmware implementations define an alias / companion device to represent the root of a PCI device hierarchy. The cxl_target_get_physical_node() helper returns the device name of that companion object in the PCI hierarchy.

REGIONS

A CXL region is composed of one or more slices of CXL memdevs, with configurable interleave settings - both the number of interleave ways, and the interleave granularity. In terms of hierarchy, it is the child of a CXL root decoder. A root decoder (recall that this corresponds to an ACPI CEDT.CFMWS window), may have multiple child regions, but a region is strictly tied to one root decoder.

The slices that compose a region are called mappings. A mapping is a tuple of memdev, endpoint decoder, and the position.

REGION: Enumeration

struct cxl_region *cxl_region_get_next(struct cxl_region *region);
#define cxl_region_foreach(decoder, region)                                    \
        for (region = cxl_region_get_first(decoder); region != NULL;           \
             region = cxl_region_get_next(region))
#define cxl_region_foreach_safe(decoder, region, _region)                      \
        for (region = cxl_region_get_first(decoder),                           \
             _region = region ? cxl_region_get_next(region) : NULL;            \
             region != NULL;                                                   \
             region = _region,                                                 \
             _region = _region ? cxl_region_get_next(_region) : NULL)

A region’s resource attribute is the Host Physical Address at which the region’s address space starts. The region’s address space is a subset of the parent root decoder’s address space.

The interleave ways is the number of component memdevs participating in the region.

The interleave granularity depends on the root decoder’s granularity, and must follow the interleave math rules defined in the CXL spec.

Regions have a list of targets 0..N, which are programmed with the name of an endpoint decoder under each participating memdev.

The decode_commit and decode_reset attributes reserve and free DPA space on a given memdev by allocating an endpoint decoder, and programming it based on the region’s interleave geometry.

Once a region is active it is attached to either the NVDIMM subsystem where its properties can be interrogated by ndctl, or the DAX subsystem where its properties can be interrogated by daxctl. The helper cxl_region_get_daxctl_region() returns an struct daxctl_region * that can be used with other libdaxctl APIs.
