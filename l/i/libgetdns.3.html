NAME

libgetdns -- an implementation of a modern asynchronous DNS API by and for application developers

LIBRARY

DNS Resolver library (libgetdns, -lgetdns)

SYNOPSIS

libgetdns

This man page describes the getdns library, the general concepts behind the API and some of the common elements of the public interface to the library. Each of the public entry points and more complex data types are captured in separate man pages.

DESCRIPTION

getdns is modern asynchronous DNS API intended to be useful to application developers and operating system distributors as a way of making all types of DNS information easily available in many types of programs. The major features of this new API are:


Full support for event-driven programming
Supports DNSSEC in multiple ways
Mirroring of the resolution in getaddrinfo()
Easily supports all RRtypes, even those yet to be defined

Each of the entry points is offered with both asynchronous and synchronous signatures. The asynchronous functions rely on event handling and callback via libevent. Functions are thread safe.

A context structure maintains DNS query and response data and is used to maintain state during calls to the public entry points.

The project page for this implementation is at

http://getdnsapi.net

The specification is maintained at

http://getdnsapi.net/spec

The git repository for this implementation is at

http://github.com/getdnsapi/getdns

DATA STRUCTURES

The API uses a few data structures to pass data into and return data from the public entry points.

list
an ordered list, the members of the list can be any of the four data types.
dict
a name-value pair. The name is a string literal, and the value can be any of the four data types. The order of the name-value pairs in a dict is not important.
int
an integer compatible with uint32_t.
bindata
a struct used to hold binary data defined as { size_t size; uint8_t *binary_stuff; }.

ASYNCHRONOUS USE

The getdns specification emphasizes the asynchronous nature of the API and allows implementations to define their own approach. This page documents this implementation's decisions and facilities provided to the developer.

This implementation provides asynchronous support via the following mechanisms:

File Descriptor Polling
Event Loop Integrations:
libevent
libuv
libev
Custom Event Loop Integrations

All functions and types discussed in this page are declared in getdns_extra.h

Build-in Event loop

The library has an built in event loop that can be used if none of the extensions for external event loops are used. The library will execute requests and dispatch callbacks with a call to getdns_context_run(). If an event loop extension is used, this will run the extension's eventloop.

void getdns_context_run(getdns_context *context)

Run the context's event loop until nothing more to do.

uint32_t getdns_context_get_num_pending_requests(getdns_context* context, struct timeval* next_timeout)

Get the number of outstanding asynchronous requests for a given context as well as the the amount of time until the next timeout. The next_timeout struct can be NULL. If supplied and the number of outstanding requests is > 0, then the timeout represents the relative time until the next timeout.

getdns_return_t getdns_context_process_async(getdns_context* context)

Inform the context to process its outstanding requests. Users should call this when either a timeout has occurred or the file descriptor signals that it is ready. User callbacks are fired during this call.

Included Event Loop Integrations

A number of applications achieve asynchronous behavior by leveraging event loop abstraction libraries. If the build system discovers a supported event loop, the event loop extension is built in addition to the getdns library. Extensions are built as an additional shared library. The following event loop libraries are supported:

libevent1 and libevent2

The libevent extension allows a context to attach to a event_base. The event loop is then run like any other application using libevent via event_base_dispatch or event_base_loop and expect getdns callbacks to fire.

Note that if both libevent1 and libevent2 reside on system, the extension uses libevent2.

Extension library: libgetdns_ext_event.[shared_lib_ext]
Extension header: getdns/getdns_ext_libevent.h

libuv

The libuv extension allows a context to attach to a uv_loop_s. The event loop can then be run like any other application using libuv via uv_run and expect getdns callbacks to fire.

Extension library: libgetdns_ext_uv.[shared_lib_ext]
Extension header: getdns_ext_libuv.h

libev

The libev extension allows a context to attach to a ev_loop. The event loop can then be run like any other application using libev via ev_run and expect getdns callbacks to fire.

Extension library: libgetdns_ext_ev.[shared_lib_ext]
Extension header: getdns_ext_libev.h

getdns_context event loop extension functions

The following are functions used by the extension entry point to attach to a particular context.

The application sets an event loop extension on a context. The extension_data is optional data that is passed into the extension methods. If an event loop is already set on a context then it is cleaned up. All outstanding requests are also canceled.

getdns_return_t getdns_extension_set_eventloop(struct getdns_context* context, getdns_eventloop_extension* extension, void* extension_data);

The application gets the extension data associated with a context.

void* getdns_context_get_extension_data(struct getdns_context* context);

When no more work must be done the application detaches an event loop from a context

getdns_return_t getdns_extension_detach_eventloop(struct getdns_context* context);

SYNCHRONOUS USE

There are four synchronous functions parallel to the four getdns async functions, except that there is no callback parameter. When an application calls one of these synchronous functions, the API gathers all the required information and then returns the result. The value returned is exactly the same as the response returned in the callback if you had used the async version of the function.

When you are done with the data in the response, call getdns_free_sync_request_memory so that the API can free the memory from its internal pool.

DNSSEC

Si una aplicación desea que la API realice la validación DNSSEC para una solicitud, debe establecer una o más extensiones relacionadas con DNSSEC. Tenga en cuenta que, de forma predeterminada, ninguna de estas extensiones está establecida y la API no realizará DNSSEC. Tenga en cuenta que obtener resultados DNSSEC puede llevar más tiempo en algunas circunstancias.

Para devolver el estado DNSSEC de cada registro DNS en la lista replies_tree, use la extensión dnssec_return_status. El valor de la extensión (un entero) se establece en GETDNS_EXTENSION_TRUE para que el estado devuelto tenga el nombre dnssec_status (un entero) agregado a los otros nombres en el diccionario del registro ("header", "question", etc.). Los valores para ese nombre son GETDNS_DNSSEC_SECURE, GETDNS_DNSSEC_BOGUS, GETDNS_DNSSEC_INDETERMINATE y GETDNS_DNSSEC_INSECURE. Por lo tanto, una respuesta podría verse así:

{     # Esta es la primera respuesta
      "dnssec_status": GETDNS_DNSSEC_INDETERMINATE,
      "header": { "id": 23456, "qr": 1, "opcode": 0, ... },
      . . .

Si en lugar de devolver el estado, desea ver solo resultados seguros, use la extensión dnssec_return_only_secure. El valor de la extensión (un entero) se establece en GETDNS_EXTENSION_TRUE para que solo se devuelvan en las listas replies_tree y replies_full los registros que la API pueda validar como seguros con DNSSEC. No se agregan nombres adicionales al diccionario del registro; el cambio es que algunos registros podrían no aparecer en los resultados. Cuando se establece esta opción de contexto, si la API recibe respuestas DNS pero ninguna se determina como segura, el código de error en el nivel superior del objeto de respuesta es GETDNS_RESPSTATUS_NO_SECURE_ANSWERS.

Las aplicaciones que deseen realizar su propia validación querrán tener los registros relacionados con DNSSEC para una respuesta particular. Use la extensión dnssec_return_validation_chain. El valor de la extensión (un entero) se establece en GETDNS_EXTENSION_TRUE para que se devuelva un conjunto de registros adicionales relacionados con DNSSEC necesarios para la validación en el objeto de respuesta. Este conjunto se presenta como validation_chain (una lista) en el nivel superior del objeto de respuesta. Esta lista incluye todos los diccionarios de registros de recursos para todos los registros de recursos (DS, DNSKEY y sus RRSIG) que son necesarios para realizar la validación desde la raíz hacia abajo. REGISTROS OPT DE RECURSOS

Para búsquedas que necesitan un registro de recursos OPT en la sección de Datos Adicionales, use la extensión add_opt_parameters. El valor de la extensión (un diccionario) contiene los parámetros; estos se describen con más detalle en el RFC 2671. Son:

maximum_udp_payload_size (un entero) entre 512 y 65535; si no se especifica, esto se toma de los contextos DNS

extended_rcode (un entero) entre 0 y 255; si no se especifica, esto se toma de los contextos DNS

version (un entero) entre 0 y 255; si no se especifica, esto por defecto es 0

do_bit (un entero) entre 0 y 1; si no se especifica, esto se toma de los contextos DNS

options (una lista) contiene diccionarios para cada opción que se especificará. Cada vez en la lista contiene dos nombres: option_code (un entero) y option_data (datos binarios). La API analiza todo el conjunto de opciones en datos de registro (RDATA) formateados correctamente para el registro de recursos.

Es muy importante tener en cuenta que el registro de recursos OPT especificado en la extensión add_opt_parameters podría no ser el mismo que la API envía en la consulta. Por ejemplo, si la aplicación también incluye alguna de las extensiones DNSSEC, la API se asegurará de que el registro de recursos OPT establezca el registro de recursos apropiadamente, realizando los cambios necesarios en la configuración de add_opt_parameters.

El uso de esta extensión puede entrar en conflicto con los valores del contexto DNS. Por ejemplo, el valor predeterminado para un sistema operativo podría ser un tamaño de paquete máximo de 65535, pero la extensión podría especificar 1550. En tal caso, la API respetará los valores indicados en la extensión, pero respetará los valores del contexto DNS si no se proporcionan valores en la extensión.

DATOS DE RESPUESTA

La función de devolución de llamada contiene un puntero a un objeto de respuesta. Un objeto de respuesta es siempre un diccionario. El objeto de respuesta siempre contiene al menos tres nombres: replies_full (una lista) y replies_tree (una lista), y status (un entero). replies_full es una lista de respuestas DNS (cada una son datos binarios) tal como aparecen en el cable. replies_tree es una lista de respuestas DNS (cada una es un diccionario) con las diversas partes de la respuesta analizadas. status es un código de estado para la consulta.

Debido a que la API puede extenderse en el futuro, un objeto de respuesta también podría contener nombres distintos de replies_full, replies_tree y status. De manera similar, cualquiera de los diccionarios descritos aquí podría extenderse en versiones posteriores de la API. Por lo tanto, una aplicación que utiliza la API no debe asumir que conoce todos los nombres posibles en un diccionario.

A continuación se enumeran los códigos de estado para los objetos de respuesta. Tenga en cuenta que, si el estado es que no hay respuestas para la consulta, las listas en replies_full y replies_tree tendrán cero longitud.

GETDNS_RESPSTATUS_GOOD Se devolvió al menos una respuesta

GETDNS_RESPSTATUS_NO_NAME Las consultas para el nombre produjeron todas respuestas negativas

GETDNS_RESPSTATUS_ALL_TIMEOUT Todas las consultas para el nombre expiraron

GETDNS_RESPSTATUS_NO_SECURE_ANSWERS Se especificó la configuración del contexto para obtener solo respuestas seguras, y se recibió al menos una respuesta DNS, pero ninguna respuesta DNS se determinó como segura a través de DNSSEC.

El nivel superior de replies_tree puede tener opcionalmente los siguientes nombres: canonical_name (datos binarios), intermediate_aliases (una lista), answer_ipv4_address (datos binarios), answer_ipv6_address (datos binarios) y answer_type (un entero).

El valor de canonical_name es el nombre que la API utilizó para su búsqueda. Está en formato de presentación FQDN. Los valores en la lista intermediate_aliases son nombres de dominio de cualquier CNAME o DNAME no sintetizado encontrado al resolver la consulta original. La lista podría tener cero entradas si no hubo CNAME en el camino. Estos pueden ser útiles, por ejemplo, para comparaciones de nombres al seguir las reglas en RFC 612

RESPUESTA DE DATOS

El valor de answer_ipv4_address y answer_ipv6_address son las direcciones del servidor desde el que se recibió la respuesta. El valor de answer_type es el tipo de servicio de nombres que generó la respuesta. Los valores son:


GETDNS_NAMETYPE_DNS
DNS Normal (RFC 1035)
GETDNS_NAMETYPE_WINS
El servicio de nombres WINS (se necesita alguna referencia)

Si la llamada fue getdns_address o getdns_address_sync, el nivel superior de replies_tree tiene un nombre adicional, just_address_answers (una lista). El valor de just_address_answers es una lista que contiene todos los registros A y AAAA de las secciones de respuesta de cualquiera de las respuestas, en el orden en que aparecen en las respuestas. Cada elemento de la lista es un diccionario con al menos dos nombres: address_type (cuyo valor es un bindata; actualmente es "IPv4" o "IPv6") y address_data (cuyo valor es un bindata). Tenga en cuenta que la extensión dnssec_return_only_secure afecta lo que aparecerá en la lista just_address_answers. Si el DNS devuelve otros tipos de direcciones, esos tipos también aparecerán en esta lista.

La API puede facilitar el descubrimiento de servicios a través de registros SRV. Si la llamada fue getdns_service o getdns_service_sync, el nivel superior de replies_tree tiene un nombre adicional, srv_addresses (una lista). La lista está ordenada por prioridad y peso según el algoritmo de ponderación en la RFC 2782, con el valor de prioridad más bajo primero. Cada elemento de la lista es un diccionario con al menos dos nombres: port y domain_name. Si la API pudo determinar la dirección del nombre de dominio de destino (por ejemplo, desde su caché o desde la sección Adicional de las respuestas), el diccionario para un elemento también contendrá address_type (cuyo valor es un bindata; actualmente es "IPv4" o "IPv6") y address_data (cuyo valor es un bindata). Tenga en cuenta que la extensión dnssec_return_only_secure afecta lo que aparecerá en la lista srv_addresses.

ESTRUCTURA DEL ÁRBOL DE RESPUESTAS DNS

Los nombres en cada entrada de la lista replies_tree para las respuestas DNS incluyen header (un diccionario), question (un diccionario), answer (una lista), authority (una lista) y additional (una lista), que corresponden a las secciones en el formato del mensaje DNS. Las listas answer, authority y additional contienen cero o más diccionarios cada una, y cada diccionario en cada lista representa un registro de recursos.

Los nombres en el diccionario header son todos los campos de la Sección 4.1.1 de la RFC 1035. Son: id, qr, opcode, aa, tc, rd, ra, z, rcode, qdcount, ancount, nscount y arcount. Todos son enteros.

Los nombres en el diccionario question son los tres campos de la Sección 4.1.2 de la RFC 1035: qname (un bindata), qtype (un entero) y qclass (un entero).

Los registros de recursos son un poco diferentes a las cabeceras y las secciones de preguntas, ya que la parte RDATA a menudo tiene su propia estructura. Los otros nombres en los diccionarios de registros de recursos son name (un bindata), type (un entero), class (un entero), ttl (un entero) y rdata (un diccionario); no hay un nombre equivalente al campo RDLENGTH.

El diccionario rdata tiene nombres diferentes para cada tipo de respuesta. Hay una lista completa de los tipos definidos en la API. Para los nombres que terminan en "-obsolete" o "-unknown", el bindata es todo el campo RDATA. Por ejemplo, el rdata de un registro A tiene un nombre ipv4_address (un bindata); el rdata de un registro SRV tiene los nombres priority (un entero), weight (un entero), port (un entero) y target (un bindata).

Cada diccionario rdata también tiene un campo rdata_raw (un bindata). Esto es útil para tipos no definidos en esta versión de la API. También puede ser valioso si una versión posterior de la API permite analizadores adicionales. Por lo tanto, realizar una consulta de tipos no conocidos por la API aún devolverá un resultado: un rdata solo con un rdata_raw.

Se espera que extensiones posteriores de la API den nombres diferentes a algunos tipos de DNS. También es posible que extensiones posteriores cambien los nombres de algunos de los tipos de DNS enumerados anteriormente.

FUNCIONES DE DEVOLUCIÓN DE LLAMADA

Una llamada a las funciones asíncronas de getdns generalmente devuelve antes de que ocurra cualquier E/S de red o de archivo. Después de que la API procesa toda la información necesaria, llama a la función de devolución de llamada que fue pasada por la aplicación. La función de devolución de llamada puede ser llamada en cualquier momento, incluso antes de que la función que la llamó haya regresado. La API garantiza que la devolución de llamada se llamará exactamente una vez, a menos que la función que la llamó devolviera un error, en cuyo caso la función de devolución de llamada nunca se llama.

La función de llamada getdns llama a la devolución de llamada con los parámetros definidos de la siguiente manera:

typedef void (*getdns_callback_t)(

getdns_context_t context,
uint16_t callback_type,
getdns_dict *response,
void *userarg,
getdns_transaction_t transaction_id)

context consulte getdns_context (3)

callback_type Suministra la razón de la devolución de llamada.

GETDNS_CALLBACK_COMPLETE La respuesta contiene los datos solicitados

GETDNS_CALLBACK_CANCEL El programa que llama canceló la devolución de llamada; response es NULL

GETDNS_CALLBACK_TIMEOUT La acción solicitada expiró; response es NULL

GETDNS_CALLBACK_ERROR La acción solicitada tuvo un error; response es NULL

response Un objeto de respuesta con los datos de la respuesta. Esto se describe en la sección titulada "DATOS DE RESPUESTA" en otra parte de esta página del manual. El objeto de respuesta es parte del espacio de memoria de la API y será liberado por la API cuando la devolución de llamada regrese.

userarg Idéntico al userarg pasado a la función que llama.

transaction_id El identificador de transacción asignado por la función que llama, utilizado para asociar una respuesta DNS con una solicitud DNS específica.

Para cancelar una devolución de llamada pendiente, use la siguiente función.


getdns_return_t
getdns_cancel_callback (getdns_context_t context, getdns_transaction_t transaction_id)

Esto hace que la API llame a la devolución de llamada con un callback_type de GETDNS_CALLBACK_CANCEL si la devolución de llamada para este transaction_id aún no ha sido llamada. El código de devolución de llamada para la cancelación debe limpiar cualquier memoria relacionada con la llamada identificada, como la desasignación de memoria para el userarg. getdns_cancel_callback() puede regresar inmediatamente, incluso antes de que la devolución de llamada complete su trabajo y regrese. Llamar a getdns_cancel_callback() con un transaction_id de una devolución de llamada que ya ha sido llamada o un transaction_id desconocido devuelve GETDNS_RETURN_UNKNOWN_TRANSACTION; de lo contrario, getdns_cancel_callback() devuelve GETDNS_RETURN_GOOD.
