libressl-SSL_CTX_set_verify(3)

SSL_CTX_SET_VERIFY(3) Manual de Funciones de Librería SSL_CTX_SET_VERIFY(3)

NOMBRE

SSL_CTX_set_verify, SSL_set_verify, SSL_CTX_set_verify_depth, SSL_set_verify_depth — establecer parámetros de verificación de certificado del par

SINOPSIS

librería «libssl» libcrypto
#include <openssl/ssl.h>

void
SSL_CTX_set_verify(SSL_CTX *ctx, int mode, int (*verify_callback)(int, X509_STORE_CTX *));

void
SSL_set_verify(SSL *s, int mode, int (*verify_callback)(int, X509_STORE_CTX *));

void
SSL_CTX_set_verify_depth(SSL_CTX *ctx, int depth);

void
SSL_set_verify_depth(SSL *s, int depth);

int
verify_callback(int preverify_ok, X509_STORE_CTX *x509_ctx);

DESCRIPCIÓN

SSL_CTX_set_verify() establece las banderas de verificación para ctx a mode y especifica la función verify_callback a utilizar. Si no se debe especificar ninguna función de callback, se puede usar el puntero NULL para verify_callback.

SSL_set_verify() establece las banderas de verificación para ssl a mode y especifica la función verify_callback a utilizar. Si no se debe especificar ninguna función de callback, se puede usar el puntero NULL para verify_callback. En este caso, la última verify_callback establecida específicamente para este ssl permanece. Si no se estableció previamente ningún callback especial, se utiliza el callback predeterminado para el ctx subyacente, que era válido en el momento en que ssl se creó con SSL_new(3). Dentro de la función de callback, SSL_get_ex_data_X509_STORE_CTX_idx(3) puede ser llamada para obtener el índice de datos del objeto SSL actual que está realizando la verificación.

SSL_CTX_set_verify_depth() establece la profundidad máxima para la verificación de la cadena de certificados que se permitirá para ctx. (Ver la sección ERRORES.)

SSL_set_verify_depth() establece la profundidad máxima para la verificación de la cadena de certificados que se permitirá para ssl. (Ver la sección ERRORES.)

La verificación de certificados puede controlarse mediante un conjunto de banderas de mode ORed bit a bit:

SSL_VERIFY_NONE
Modo servidor: el servidor no enviará una solicitud de certificado de cliente al cliente, por lo que el cliente no enviará un certificado.

Modo cliente: si no se utiliza un cifrado anónimo (deshabilitado por defecto), el servidor enviará un certificado que será verificado. El resultado del proceso de verificación del certificado se puede comprobar después del handshake TLS/SSL utilizando la función SSL_get_verify_result(3). El handshake continuará independientemente del resultado de la verificación.

SSL_VERIFY_PEER
Modo servidor: el servidor envía una solicitud de certificado de cliente al cliente. El certificado devuelto (si lo hay) se verifica. Si el proceso de verificación falla, el handshake TLS/SSL se termina inmediatamente con un mensaje de alerta que contiene la razón del fallo de verificación. El comportamiento puede controlarse mediante las banderas adicionales SSL_VERIFY_FAIL_IF_NO_PEER_CERT y SSL_VERIFY_CLIENT_ONCE.

Modo cliente: el certificado del servidor se verifica. Si el proceso de verificación falla, el handshake TLS/SSL se termina inmediatamente con un mensaje de alerta que contiene la razón del fallo de verificación. Si no se envía ningún certificado de servidor, porque se utiliza un cifrado anónimo, SSL_VERIFY_PEER se ignora.

SSL_VERIFY_FAIL_IF_NO_PEER_CERT
Modo servidor: si el cliente no devolvió un certificado, el handshake TLS/SSL se termina inmediatamente con una alerta de "fallo de handshake". Esta bandera debe usarse junto con SSL_VERIFY_PEER.

Modo cliente: ignorado.

SSL_VERIFY_CLIENT_ONCE
Modo servidor: solo solicite un certificado de cliente en el handshake TLS/SSL inicial. No solicite un certificado de cliente de nuevo en caso de renegociación. Esta bandera debe usarse junto con SSL_VERIFY_PEER.

Modo cliente: ignorado.

Se debe establecer exactamente una de las banderas mode SSL_VERIFY_NONE y SSL_VERIFY_PEER en cualquier momento.

El procedimiento de verificación real se realiza utilizando el procedimiento de verificación incorporado o utilizando otra función de verificación proporcionada por la aplicación establecida con SSL_CTX_set_cert_verify_callback(3). Las siguientes descripciones se aplican en el caso del procedimiento incorporado. Un procedimiento proporcionado por la aplicación también tiene acceso a la información de profundidad de verificación y a la función verify_callback(), pero la forma en que se utiliza esta información puede ser diferente.

SSL_CTX_set_verify_depth() y SSL_set_verify_depth() establecen el límite hasta el cual se utilizan los certificados en una cadena durante el procedimiento de verificación. Si la cadena de certificados es más larga de lo permitido, se ignoran los certificados por encima del límite. Se generan mensajes de error como si estos certificados no estuvieran presentes, lo más probable es que se emita un X509_V_ERR_UNABLE_TO_GET_ISSUER_CERT_LOCALLY. El recuento de profundidad es "nivel 0: certificado del par", "nivel 1: certificado de CA", "nivel 2: certificado de CA de nivel superior", y así sucesivamente. Establecer la profundidad máxima en 2 permite los niveles 0, 1 y 2. El límite de profundidad predeterminado es 100, lo que permite el certificado del par y 100 certificados de CA adicionales.

La función verify_callback se utiliza para controlar el comportamiento cuando se establece la bandera SSL_VERIFY_PEER. Debe ser proporcionada por la aplicación y recibe dos argumentos: preverify_ok indica si la verificación del certificado en cuestión ha sido superada (preverify_ok=1) o no (preverify_ok=0). x509_ctx es un puntero al contexto completo utilizado para la verificación de la cadena de certificados.

La cadena de certificados se comprueba comenzando con el nivel de anidamiento más profundo (el certificado raíz de la CA) y trabajando hacia arriba.

VALORES DE RETORNO

SSL_CTX_set_verify() y SSL_set_verify() no devuelven ningún valor.

SSL_CTX_set_verify_depth() y SSL_set_verify_depth() no devuelven ningún valor.

OPERACIONES SOPORTADAS

ERRORES

La profundidad máxima de verificación se establece de forma global para el SSL_CTX. Si varios hilos usan el mismo SSL_CTX, se requiere sincronización para evitar condiciones de carrera al cambiar la profundidad de verificación.

En el modo SSL_VERIFY_PEER, el valor de retorno de la función verify_callback solo se tiene en cuenta si el argumento preverify_ok es distinto de cero. Si se devuelve 0, el valor de retorno de la función verify_callback se ignora.

Si SSL_set_verify() se llama con NULL para verify_callback, se utiliza la función de callback predeterminada del contexto subyacente. Si el contexto tiene su propia función de callback personalizada, esta se utilizará en su lugar.

ESTÁNDARES

El comportamiento de SSL_VERIFY_PEER en modo cliente y servidor puede ser complejo. Consulte las RFC de TLS/SSL para obtener una descripción detallada.

NOMBRE

SSL_CTX_set_verify, SSL_set_verify, SSL_CTX_set_verify_depth, SSL_set_verify_depth - establecer el modo y la profundidad de verificación de certificados

SINOPSIS

#include <openssl/ssl.h>

int SSL_CTX_set_verify(SSL_CTX *ctx, int mode,
       verify_callback *callback);
int SSL_set_verify(SSL *ssl, int mode, verify_callback *callback);

void SSL_CTX_set_verify_depth(SSL_CTX *ctx, int depth);
void SSL_set_verify_depth(SSL *ssl, int depth);

typedef int (*verify_callback)(int preverify_ok, X509_STORE_CTX *ctx);

DESCRIPCIÓN

La función SSL_CTX_set_verify() establece el modo y la devolución de llamada de verificación para un SSL_CTX. El argumento mode es el bitwise OR de las siguientes banderas:

SSL_VERIFY_NONE
Nunca se solicita al par que presente un certificado. La verificación del certificado del par está deshabilitada.
SSL_VERIFY_PEER
Se solicita al par que presente un certificado. El proceso de verificación subsiguiente se realiza como se describe en la sección DESCRIPTION de verify(1).
SSL_VERIFY_FAIL_IF_NO_PEER_CERT
Si el par no presenta un certificado, la verificación falla. Esto solo tiene efecto si SSL_VERIFY_PEER también está configurado.
SSL_VERIFY_CLIENT_ONCE
Solo se solicita al par que presente un certificado durante la fase de negociación inicial. Si el par no presenta un certificado, la verificación falla. Esto solo tiene efecto si SSL_VERIFY_PEER también está configurado.

El argumento callback es un puntero a una función de devolución de llamada que se invocará durante la verificación del certificado del par. Si callback es NULL, se utilizará una devolución de llamada predeterminada. Vea la sección EXAMPLES para ver un ejemplo de una función de devolución de llamada.

La función SSL_set_verify() hace lo mismo para una conexión SSL específica.

El argumento depth en SSL_CTX_set_verify_depth() y SSL_set_verify_depth() establece el número máximo de certificados que se pueden seguir en la cadena de certificados del par. El valor predeterminado es 1, lo que significa que solo se permite el certificado del par y su emisor inmediato.

La verificación del certificado del par se realiza en cada nivel de la cadena de certificados. En cada nivel, se verifican las firmas y los atributos del emisor. Siempre que se encuentra un error de verificación, el número de error se almacena en x509_ctx y se llama a verify_callback con preverify_ok igual a 0. Al aplicar las funciones X509_CTX_store_*() verify_callback puede localizar el certificado en cuestión y realizar pasos adicionales (ver EJEMPLOS). Si no se encuentra ningún error para un certificado, se llama a verify_callback con preverify_ok igual a 1 antes de avanzar al siguiente nivel.

El valor de retorno de verify_callback controla la estrategia del proceso de verificación posterior. Si verify_callback devuelve 0, el proceso de verificación se detiene inmediatamente con el estado de “verificación fallida”. Si SSL_VERIFY_PEER está configurado, se envía una alerta de fallo de verificación al par y se termina el handshake TLS/SSL. Si verify_callback devuelve 1, el proceso de verificación continúa. Si verify_callback siempre devuelve 1, el handshake TLS/SSL no se terminará con respecto a los fallos de verificación y la conexión se establecerá. Sin embargo, el proceso de llamada puede recuperar el código de error del último error de verificación utilizando SSL_get_verify_result(3) o manteniendo su propio almacenamiento de errores administrado por verify_callback.

Si no se especifica ningún verify_callback, se utilizará la devolución de llamada predeterminada. Su valor de retorno es idéntico a preverify_ok, por lo que cualquier fallo de verificación conducirá a la terminación del handshake TLS/SSL con un mensaje de alerta, si SSL_VERIFY_PEER está configurado.

EJEMPLOS

La siguiente secuencia de código implementa una función verify_callback de ejemplo que siempre continuará el handshake TLS/SSL independientemente del fallo de verificación, si se desea. La devolución de llamada implementa un límite de profundidad de verificación con salida más informativa.

Se imprimen todos los errores de verificación; la información sobre la cadena de certificados se imprime bajo petición. El ejemplo se implementa para un servidor que permite pero no requiere certificados de cliente.

El ejemplo utiliza la técnica ex_data para almacenar/recuperar datos de aplicación de la estructura SSL (ver SSL_get_ex_new_index(3), SSL_get_ex_data_X509_STORE_CTX_idx(3)).

...

typedef struct {
	int	verbose_mode;
	int	verify_depth;
	int	always_continue;
} mydata_t;
int mydata_index;
...
static int
verify_callback(int preverify_ok, X509_STORE_CTX *ctx)
{
	char buf[256];
	X509 *err_cert;
	int err, depth;
	SSL *ssl;
	mydata_t *mydata;

	err_cert = X509_STORE_CTX_get_current_cert(ctx);
	err = X509_STORE_CTX_get_error(ctx);
	depth = X509_STORE_CTX_get_error_depth(ctx);

	/*
	 * Recuperar el puntero a la SSL de la conexión que se está tratando
	 * actualmente * y los datos específicos de la aplicación almacenados en
	 * el objeto SSL.
	 */
	ssl = X509_STORE_CTX_get_ex_data(ctx,
	    SSL_get_ex_data_X509_STORE_CTX_idx());
	mydata = SSL_get_ex_data(ssl, mydata_index);

	X509_NAME_oneline(X509_get_subject_name(err_cert), buf, 256);

	/*
	 * Capturar una cadena de certificados demasiado larga. El límite de
	 * profundidad establecido con SSL_CTX_set_verify_depth() se establece
	 * a propósito en "límite+1" para que siempre que se cumpla la
	 * condición "depth>verify_depth", hayamos violado el límite y
	 * queramos registrar esta condición de error.
	 * Debemos hacerlo aquí, porque el error CHAIN_TOO_LONG no se encontraría
	 * explícitamente; solo se registrarían los errores introducidos al
	 * cortar los certificados adicionales.
	 */
	if (depth > mydata->verify_depth) {
		preverify_ok = 0;
		err = X509_V_ERR_CERT_CHAIN_TOO_LONG;
		X509_STORE_CTX_set_error(ctx, err);
	}
	if (!preverify_ok) {
		printf("error de verificación:num=%d:%s:depth=%d:%s\n", err,
		    X509_verify_cert_error_string(err), depth, buf);
	} else if (mydata->verbose_mode) {
		printf("depth=%d:%s\n", depth, buf);
	}

	/*
	 * En este punto, err contiene el último error de verificación.
	 * Podemos usarlo para algo especial
	 */
	if (!preverify_ok && (err ==
	    X509_V_ERR_UNABLE_TO_GET_ISSUER_CERT)) {
		X509_NAME_oneline(X509_get_issuer_name(ctx->current_cert),
		    buf, 256);
		printf("emisor= %s\n", buf);
	}

	if (mydata->always_continue)
		return 1;
	else
		return preverify_ok;
}

mydata_t mydata;

mydata_index = SSL_get_ex_new_index(0, "mydata index", NULL, NULL, NULL);

SSL_CTX_set_verify(ctx, SSL_VERIFY_PEER|SSL_VERIFY_CLIENT_ONCE,

 * un error apropiado en el archivo de registro.

SSL_CTX_set_verify_depth(verify_depth + 1);

/*
 * Configurar los datos específicos de SSL en "mydata" y almacenarlos en la
 * estructura SSL.
 */
mydata.verify_depth = verify_depth; ...
SSL_set_ex_data(ssl, mydata_index, &mydata);

HISTORIA

SSL_set_verify() apareció en SSLeay 0.4 o anterior. SSL_CTX_set_verify() apareció por primera vez en SSLeay 0.6.4. Ambas funciones han estado disponibles desde OpenBSD 2.4.

SSL_CTX_set_verify_depth() y SSL_set_verify_depth() aparecieron por primera vez en OpenSSL 0.9.3 y han estado disponibles desde OpenBSD 2.6.

ERRORES

En modo cliente, no se verifica si está configurado el indicador SSL_VERIFY_PEER, sino si SSL_VERIFY_NONE no está configurado. Esto puede conducir a un comportamiento inesperado, si SSL_VERIFY_PEER y SSL_VERIFY_NONE no se utilizan según lo requerido (exactamente uno debe estar configurado en cualquier momento).

La profundidad de verificación del certificado establecida con SSL[_CTX]_verify_depth() detiene la verificación en una cierta profundidad. El mensaje de error producido será el de una cadena de certificados incompleta y no X509_V_ERR_CERT_CHAIN_TOO_LONG como se podría esperar.
