I. Introducción

Este archivo describe cómo usar y modificar la biblioteca de referencia PNG (conocida como libpng) para su propio uso. Además de este archivo, example.c es un buen punto de partida para usar la biblioteca, ya que está ampliamente comentada y debería incluir todo lo que la mayoría de la gente necesitará. Suponemos que libpng ya está instalada; consulte el archivo INSTALL para obtener instrucciones sobre cómo configurar e instalar libpng.

Para ver ejemplos de uso de libpng, consulte los archivos "example.c", "pngtest.c" y los archivos del directorio "contrib", todos los cuales se incluyen en la distribución de libpng.

Libpng fue escrita como un complemento de la especificación PNG, como una forma de reducir la cantidad de tiempo y esfuerzo que lleva admitir el formato de archivo PNG en programas de aplicación.

La especificación PNG (Tercera Edición), junio de 2025, está disponible como una Recomendación del W3C en https://www.w3.org/TR/2025/REC-png-3-20250624/.

La especificación PNG (Segunda Edición), noviembre de 2003, está disponible como una Recomendación del W3C y como un Estándar ISO (ISO/IEC 15948:2004 (E)) en https://www.w3.org/TR/2003/REC-PNG-20031110/. Los documentos del W3C y de la ISO tienen contenido técnico idéntico.

La especificación PNG-1.2 está disponible en https://www.libpng.org/pub/png/spec/1.2/. Es técnicamente equivalente a la especificación PNG (Segunda Edición), pero tiene material adicional.

La especificación PNG-1.0 está disponible como RFC 2083 en https://www.libpng.org/pub/png/spec/1.0/ y como una Recomendación del W3C en https://www.w3.org/TR/REC-png-961001.

Algunos trozos adicionales se describen en los documentos de trozos especiales de propósito público en http://www.libpng.org/pub/png/spec/register/

Se puede encontrar otra información sobre PNG y la última versión de libpng en la página principal de PNG, http://www.libpng.org/pub/png/.

La mayoría de los usuarios no tendrán que modificar la biblioteca significativamente; los usuarios avanzados pueden querer modificarla más. Se hicieron todos los intentos para que fuera lo más completa posible, al mismo tiempo que se mantenía el código fácil de entender. Actualmente, esta biblioteca solo admite C. Se está considerando el soporte para otros idiomas.

Libpng ha sido diseñada para manejar múltiples sesiones a la vez, para ser fácilmente modificable, para ser portable a la gran mayoría de máquinas (ANSI, K&R, de 16, 32 y 64 bits) disponibles y para ser fácil de usar. El objetivo final de libpng es promover la aceptación del formato de archivo PNG de cualquier manera posible. Si bien todavía queda trabajo por hacer (consulte el archivo TODO), libpng debería cubrir la mayoría de las necesidades de sus usuarios.

Libpng utiliza zlib para la compresión y descompresión de archivos PNG. Puede encontrar más información sobre zlib y la última versión de zlib en la página principal de zlib, https://zlib.net/. La utilidad de compresión zlib es una utilidad de propósito general que es útil para más que solo archivos PNG, y se puede usar sin libpng. Consulte la documentación que se entrega con zlib para obtener más detalles. Normalmente puede encontrar los archivos fuente de la utilidad zlib dondequiera que encuentre los archivos fuente de libpng.

Libpng es segura para subprocesos, siempre que los subprocesos utilicen instancias diferentes de las estructuras. Cada subproceso debe tener sus propias instancias de png_struct y png_info, y por lo tanto, su propia imagen. Libpng no se protege contra dos subprocesos que utilizan la misma instancia de una estructura.

II. Estructuras

Hay dos estructuras principales que son importantes para libpng, png_struct y png_info. Ambas son estructuras internas que ya no están expuestas en la interfaz de libpng (a partir de libpng 1.5.0).

La estructura png_info está diseñada para proporcionar información sobre el archivo PNG. En un momento dado, los campos de png_info estaban destinados a ser directamente accesibles para el usuario. Sin embargo, esto tendía a causar problemas con las aplicaciones que utilizaban bibliotecas cargadas dinámicamente, y como resultado, se desarrolló un conjunto de funciones de interfaz para png_info (las funciones png_get_*() y png_set_*()), y se desaprobó el acceso directo a los campos de png_info.

La estructura png_struct es el objeto utilizado por la biblioteca para decodificar una sola imagen. A partir de la versión 1.5.0, esta estructura tampoco está expuesta.

Casi todas las API de libpng requieren un puntero a una png_struct como primer argumento. Muchas (en particular las API png_set y png_get) también requieren un puntero a png_info como segundo argumento. Algunas macros visibles por la aplicación definidas en png.h diseñadas para acceso básico a datos (lectura y escritura de enteros en formato PNG) no toman un puntero png_info, pero casi siempre es seguro asumir que se debe pasar un (png_struct*) para llamar a una función API.

Puede tener más de una estructura png_info asociada con una imagen, como se ilustra en pngtest.c, una para información válida antes de los trozos IDAT y otra (llamada "end_info" a continuación) para cosas posteriores a ellos.

El archivo de cabecera png.h es una referencia invaluable para programar con libpng. Y ya que estoy en ello, asegúrese de incluir el archivo de cabecera de libpng:

#include <png.h>

y también (a partir de libpng-1.5.0) el archivo de cabecera de zlib, si lo necesita:

#include <zlib.h>

Tipos

El archivo de cabecera png.h define una serie de tipos integrales utilizados por las API. La mayoría de estos son bastante obvios; por ejemplo, tipos que corresponden a enteros de tamaños particulares y tipos para pasar valores de color.

Una excepción es cómo se manejan los números no integrales. Para conveniencia de la aplicación, la mayoría de las API que toman dichos números tienen argumentos C (double); sin embargo, internamente PNG y libpng utilizan enteros de 32 bits con signo y codifican el valor multiplicando por 100.000. A partir de libpng 1.5.0, se define una macro de conveniencia PNG_FP_1 en png.h junto con un tipo (png_fixed_point) que es simplemente (png_int_32).

Todas las API que toman argumentos (double) también tienen una API correspondiente que toma los argumentos de punto fijo enteros correspondientes. La API de punto fijo tiene el mismo nombre que la de punto flotante con "_fixed" añadido. El rango real de valores permitidos en las API es frecuentemente menor que el rango completo de (png_fixed_point) (-21474 a +21474). Cuando las API requieren un argumento no negativo, el tipo se registra como png_uint_32 arriba. Consulte el archivo de cabecera y el texto a continuación para obtener más información.

Se debe tener especial cuidado con el manejo del trozo sCAL porque el propio trozo utiliza valores no integrales codificados como cadenas que contienen números de punto flotante decimales. Consulte los comentarios en el archivo de cabecera.

Configuración

Las declaraciones de funciones del archivo de cabecera principal a menudo están protegidas por directivas de preprocesamiento C de la forma:


#ifdef PNG_feature_SUPPORTED
declare-function
#endif
...
#ifdef PNG_feature_SUPPORTED
use-function
#endif

La biblioteca se puede compilar sin soporte para estas API, aunque una compilación estándar tendrá todas las API implementadas. Los programas de aplicación deben verificar las macros de características antes de usar una API para obtener la máxima portabilidad. A partir de libpng 1.5.0, las macros de características establecidas durante la compilación de libpng se registran en el archivo de cabecera "pnglibconf.h" y este archivo siempre es incluido por png.h.

Si no necesita cambiar la configuración de la biblioteca de la predeterminada, salte a la siguiente sección ("Lectura").

Observe que algunos de los makefiles en el directorio 'scripts' y (en la versión 1.5.0) todos los archivos de proyecto de compilación en el directorio 'projects' simplemente copian scripts/pnglibconf.h.prebuilt a pnglibconf.h. Esto significa que estos sistemas de compilación no permiten la autoconfiguración fácil de la biblioteca; solo admiten la configuración predeterminada.

La forma más fácil de hacer cambios menores en la configuración de libpng cuando la autoconfiguración es compatible es agregar definiciones a la línea de comandos usando (típicamente) CPPFLAGS. Por ejemplo:

CPPFLAGS=-DPNG_NO_FLOATING_ARITHMETIC

cambiará la implementación matemática interna de libpng para la corrección gamma y otros cálculos aritméticos a punto fijo, evitando la necesidad de un soporte rápido de punto flotante. El resultado se puede ver en el pnglibconf.h generado; asegúrese de que contenga la configuración de la macro de características modificada.

Si necesita hacer cambios de configuración más extensos, más de uno o dos ajustes de macros de características, puede agregar -DPNG_USER_CONFIG a la línea de comandos de compilación y poner una lista de ajustes de macros de características en pngusr.h o puede establecer DFA_XTRA (una variable makefile) a un archivo que contenga la misma información en forma de ajustes de 'opción'.

A. Cambiando pnglibconf.h

Existen diversos métodos para compilar libpng. No todos admiten la reconfiguración de pnglibconf.h. Para reconfigurar pnglibconf.h, debe ser recompilado desde scripts/pnglibconf.dfa usando awk o debe ser editado a mano.

La edición manual se logra copiando scripts/pnglibconf.h.prebuilt a pnglibconf.h y cambiando las líneas que definen las características admitidas,

prestando mucha atención a la información de 'option' en scripts/pnglibconf.dfa que describe esas características y sus requisitos. Esto es fácil de hacer mal.

B. Configuración usando DFA_XTRA

Recompilar desde pnglibconf.dfa es fácil si se dispone de una versión funcional de 'awk', o una variante posterior como 'nawk' o 'gawk'. La compilación de configure encontrará automáticamente un awk apropiado y construirá pnglibconf.h. El archivo scripts/pnglibconf.mak contiene un conjunto de reglas de make para hacer lo mismo si no se utiliza configure, y muchos de los makefiles en el directorio scripts utilizan este enfoque.

Al recompilar, simplemente escriba un nuevo archivo que contenga las opciones modificadas y establezca DFA_XTRA al nombre de este archivo. Esto hace que la compilación añada el nuevo archivo al final de scripts/pnglibconf.dfa. El archivo pngusr.dfa debe contener líneas de las siguientes formas:

everything = off

Esto desactiva todas las características opcionales. Inclúyalo al principio de pngusr.dfa para facilitar la construcción de una configuración mínima. Necesitará activar al menos algunas características después para habilitar la lectura o la escritura de código, o ambas.

option feature on option feature off

Habilita o deshabilita una característica individual. Esto habilitará automáticamente otras características requeridas por una característica que se activa o deshabilitará otras características que requieran una característica que se desactiva. Las configuraciones conflictivas provocarán un mensaje de error emitido por awk.

setting feature default value

Cambia el valor por defecto de la configuración 'feature' a 'value'. Hay un pequeño número de configuraciones listadas en la parte superior de pnglibconf.h, están documentadas en el código fuente. La mayoría de estos valores tienen implicaciones de rendimiento para la biblioteca, pero la mayoría no tiene un efecto visible en la API. Algunos también pueden ser anulados desde la API.

Este método de construcción de un pnglibconf.h personalizado se ilustra en contrib/pngminim/*. Vea el destino "$(PNGCONF):" en el makefile y pngusr.dfa en estos directorios.

C. Configuración usando PNG_USER_CONFIG

Si se añade -DPNG_USER_CONFIG a CPPFLAGS al compilar pnglibconf.h, el archivo pngusr.h se incluirá automáticamente antes de procesar las opciones en scripts/pnglibconf.dfa. Su archivo pngusr.h debe contener solo definiciones de macros que activen o desactiven características o establezcan configuraciones.

Aparte de la configuración global "everything = off", todas las opciones listadas arriba se pueden establecer usando macros en pngusr.h:

#define PNG_feature_SUPPORTED

es equivalente a:

option feature on

#define PNG_NO_feature

es equivalente a:

option feature off

#define PNG_feature value

es equivalente a:

setting feature default value

Nótese que en ambos casos, pngusr.dfa y pngusr.h, el contenido del archivo pngusr que usted proporciona anula el contenido de scripts/pnglibconf.dfa

Si se producen comportamientos confusos o incomprensibles, es posible examinar el archivo intermedio pnglibconf.dfn para encontrar el conjunto completo de información de dependencia para cada configuración y opción. Simplemente localice la característica en el archivo y lea los comentarios C que la preceden.

Este método también se ilustra en los makefiles de contrib/pngminim/* y pngusr.h.

III. Lectura

Ahora recorreremos las funciones posibles a llamar al leer un archivo PNG secuencialmente, explicando brevemente la sintaxis y el propósito de cada una. Vea example.c y png.h para más detalles. Si bien la lectura progresiva se cubre en la siguiente sección, aún necesitará algunas de las funciones discutidas en esta sección para leer un archivo PNG.

Configuración

Querrá hacer la inicialización de E/S(*) antes de entrar en libpng, de modo que si no funciona, no tenga mucho que deshacer. Por supuesto, también querrá asegurarse de que está tratando, de hecho, con un archivo PNG. Libpng proporciona una comprobación simple para ver si un archivo es un archivo PNG. Para usarla, pase los primeros 1 a 8 bytes del archivo a la función png_sig_cmp(), y devolverá 0 (falso) si los bytes coinciden con los bytes correspondientes de la firma PNG, o un valor distinto de cero (verdadero) en caso contrario. Por supuesto, cuantos más bytes pase, mayor será la precisión de la predicción.

Si tiene la intención de mantener el puntero de archivo abierto para su uso en libpng, debe asegurarse de no leer más de 8 bytes desde el principio del archivo, y también debe hacer una llamada a png_set_sig_bytes() con el número de bytes que leyó desde el principio. Libpng solo verificará los bytes (si los hay) que su programa no leyó.

(*): Si no está utilizando las funciones de E/S estándar, necesitará reemplazarlas con funciones personalizadas. Vea la discusión en Personalización de libpng.


FILE *fp = fopen(file_name, "rb");
if (!fp)
{
return ERROR;
}


if (fread(header, 1, number, fp) != number)
{
return ERROR;
}


is_png = (png_sig_cmp(header, 0, number) == 0);
if (!is_png)
{
return NOT_PNG;
}

Para garantizar que el tamaño de estas estructuras sea correcto incluso con una libpng enlazada dinámicamente, existen funciones para inicializar y asignar las estructuras. También pasamos la versión de la biblioteca, punteros opcionales a funciones de manejo de errores y un puntero a una estructura de datos para uso de las funciones de error, si es necesario (el puntero y las funciones pueden ser NULL si se van a utilizar los manejadores de errores por defecto). Vea la sección sobre Cambios en Libpng más abajo con respecto a las antiguas funciones de inicialización. Las funciones de asignación de estructuras devuelven silenciosamente NULL si no logran crear la estructura, por lo que su aplicación debe comprobarlo.

(PNG_LIBPNG_VER_STRING, (png_voidp)user_error_ptr,

if (!png_ptr)
return ERROR;


png_infop info_ptr = png_create_info_struct(png_ptr);

png_structp png_ptr = png_create_read_struct_2
(PNG_LIBPNG_VER_STRING, (png_voidp)user_error_ptr,
user_error_fn, user_warning_fn, (png_voidp)

Las rutinas de manejo de errores pasadas a png_create_read_struct() y las rutinas de asignación/liberación de memoria pasadas a png_create_struct_2() solo son necesarias si no está utilizando las funciones de manejo de errores y asignación/liberación de memoria proporcionadas por libpng.

Cuando libpng encuentra un error, espera hacer un longjmp de vuelta a su rutina. Por lo tanto, necesitará llamar a setjmp y pasar su png_jmpbuf(png_ptr). Si lee el archivo desde diferentes rutinas, necesitará actualizar el búfer de longjmp cada vez que entre en una nueva rutina que llame a una función png_*().

Vea la documentación de setjmp/longjmp de su compilador para más información sobre setjmp/longjmp. Vea la discusión sobre el manejo de errores de libpng en la sección Personalización de Libpng más abajo para más información sobre el manejo de errores de libpng. Si ocurre un error y libpng hace un longjmp de vuelta a su setjmp, querrá llamar a png_destroy_read_struct() para liberar cualquier memoria.


if (setjmp(png_jmpbuf(png_ptr)))
{
png_destroy_read_struct(&png_ptr, &info_ptr, &end_info);
fclose(fp);
return ERROR;
}

Pase NULL en lugar de &end_info si no ha creado una estructura end_info.

Si prefiere evitar la complejidad de los problemas de setjmp/longjmp, puede compilar libpng con PNG_NO_SETJMP, en cuyo caso los errores resultarán en una llamada a PNG_ABORT() que por defecto llama a abort().

Puede #define PNG_ABORT() a una función que haga algo más útil que abort(), siempre que su función no retorne.

Ahora necesita configurar el código de entrada. El valor por defecto para libpng es usar la función C fread(). Si usa esta, necesitará pasar un FILE * válido en la función png_init_io(). Asegúrese de que el archivo está abierto en modo binario. Si desea manejar la lectura de datos de otra manera, no necesita llamar a la función png_init_io(), pero debe implementar los métodos de E/S de libpng discutidos en la sección Personalización de Libpng más abajo.


png_init_io(png_ptr, fp);

Si previamente abrió el archivo y leyó parte de la firma desde el principio para ver si era un archivo PNG, necesita informar a libpng de que faltan algunos bytes al principio del archivo.


png_set_sig_bytes(png_ptr, number);

Puede cambiar el tamaño del búfer de compresión zlib a utilizar al leer datos comprimidos con


png_set_compression_buffer_size(png_ptr, buffer_size);

donde el tamaño por defecto es de 8192 bytes. Tenga en cuenta que el tamaño del búfer se cambia inmediatamente y el búfer se reasigna inmediatamente, en lugar de establecer una bandera para que se actúe sobre ella más tarde.

Si desea que los errores de CRC se manejen de manera diferente a la predeterminada, use


png_set_crc_action(png_ptr, crit_action, ancil_action);

Los valores para png_set_crc_action() indican cómo libpng debe manejar los errores de CRC en fragmentos auxiliares y críticos, y si se deben utilizar los datos contenidos en ellos. A partir de libpng-1.6.26, esto también rige cómo se maneja un error de ADLER32 al leer el fragmento IDAT. Tenga en cuenta que es imposible "descartar" datos en un fragmento crítico.

Opciones para (int) crit_action son
PNG_CRC_DEFAULT 0 error/salir
PNG_CRC_ERROR_QUIT 1 error/salir
PNG_CRC_WARN_USE 3 advertir/usar datos
PNG_CRC_QUIET_USE 4 silencio/usar datos
PNG_CRC_NO_CHANGE 5 usar el valor actual

Opciones para (int) ancil_action son
PNG_CRC_DEFAULT 0 error/salir
PNG_CRC_ERROR_QUIT 1 error/salir
PNG_CRC_WARN_DISCARD 2 advertir/descartar datos
PNG_CRC_WARN_USE 3 advertir/usar datos
PNG_CRC_QUIET_USE 4 silencio/usar datos
PNG_CRC_NO_CHANGE 5 usar el valor actual

Cuando la configuración para crit_action es PNG_CRC_QUIET_USE, las sumas de verificación CRC y ADLER32 no solo se ignoran, sino que tampoco se evalúan.

Configuración de código de devolución de llamada

Puede configurar una función de devolución de llamada para manejar los fragmentos desconocidos en el flujo de entrada. Debe proporcionar la función


read_chunk_callback(png_structp png_ptr,
png_unknown_chunkp chunk)
{
/* La estructura de fragmento desconocido contiene sus
datos de fragmento, junto con datos similares para cualquier otro
fragmento desconocido: */


png_byte name[5];
png_byte *data;
size_t size;


/* Tenga en cuenta que libpng ya se ha encargado de
el manejo de CRC */


/* inserte su código aquí. Busque su fragmento en la
estructura de fragmento desconocido, procéselo y devuelva uno
de los siguientes: */


return -n; /* el fragmento tuvo un error */
return 0; /* no se reconoció */
return n; /* éxito */
}

(Puede darle a su función otro nombre que le guste en lugar de "read_chunk_callback")

Para informar a libpng sobre su función, use


png_set_read_user_chunk_fn(png_ptr, user_chunk_ptr,
read_chunk_callback);

Esto nombra no solo la función de devolución de llamada, sino también un puntero de usuario que puede recuperar con


png_get_user_chunk_ptr(png_ptr);

Si llama a la función png_set_read_user_chunk_fn(), todos los fragmentos desconocidos que la devolución de llamada no maneje se guardarán al leerlos. Puede hacer que se descarten devolviendo '1' ("manejado") en lugar de '0'. Este comportamiento cambiará en libpng 1.7 y se utilizará el manejo predeterminado establecido por la función png_set_keep_unknown_chunks(), que se describe a continuación, cuando la devolución de llamada devuelva 0. Si desea el comportamiento existente, debe establecer el valor predeterminado global en PNG_HANDLE_CHUNK_IF_SAFE ahora; esto es compatible con todas las versiones actuales de libpng y con 1.7. Libpng 1.6 emite una advertencia si mantiene el valor predeterminado, o PNG_HANDLE_CHUNK_NEVER, y la devolución de llamada devuelve 0.

En este punto, puede configurar una función de devolución de llamada que se llamará después de que se haya leído cada fila, que puede utilizar para controlar un medidor de progreso o similar. Se demuestra en pngtest.c. Debe proporcionar una función


void read_row_callback(png_structp png_ptr,
png_uint_32 row, int pass)
{
/* inserte su código aquí */
}

(Puede darle otro nombre que le guste en lugar de "read_row_callback")

Para informar a libpng sobre su función, use


png_set_read_status_fn(png_ptr, read_row_callback);

Cuando se llama a esta función, la fila ya se ha procesado por completo y 'row' y 'pass' se refieren a la siguiente fila que se manejará. Para el caso no entrelazado, la fila que se acaba de manejar es simplemente una menos que el número de fila proporcionado, y 'pass' siempre será 0. Para el caso entrelazado, se aplica lo mismo a menos que el valor de fila sea 0, en cuyo caso la fila que se acaba de manejar fue la última de uno de los pasos anteriores. Dado que el entrelazado puede omitir un paso, no puede estar seguro de que el paso anterior sea solo 'pass-1'; si realmente necesita saber cuál es el último paso, registre (row, pass) de la devolución de llamada y use el último valor registrado cada vez.

Al igual que con la transformación de usuario, puede encontrar la fila de salida utilizando la macro PNG_ROW_FROM_PASS_ROW.

Manejo de fragmentos desconocidos

Ahora puede establecer la forma en que la biblioteca procesa los fragmentos desconocidos en el flujo PNG de entrada. Se leerán tanto los fragmentos conocidos como los desconocidos. El comportamiento normal es que los fragmentos conocidos se analicen en información en varios miembros de info_ptr, mientras que los fragmentos desconocidos se descartarán. Este comportamiento puede ser ineficiente si su aplicación nunca utilizará ciertos tipos de fragmentos conocidos. Para cambiar esto, puede llamar:


png_set_keep_unknown_chunks(png_ptr, keep,
chunk_list, num_chunks);


keep - 0: manejo predeterminado de fragmentos desconocidos
1: ignorar; no mantener
2: mantener solo si es seguro copiar
3: mantener incluso si no es seguro copiar


Puede usar estas definiciones:
PNG_HANDLE_CHUNK_AS_DEFAULT 0
PNG_HANDLE_CHUNK_NEVER 1
PNG_HANDLE_CHUNK_IF_SAFE 2
PNG_HANDLE_CHUNK_ALWAYS 3


chunk_list - lista de fragmentos afectados (una cadena de bytes,
cinco bytes por fragmento, NULL o ' ' si
num_chunks es positivo; ignorado si
numchunks <= 0).


num_chunks - número de fragmentos afectados; si es 0, todos
los fragmentos desconocidos están afectados. Si es positivo,
solo los fragmentos de la lista están afectados,
y si es negativo, todos los fragmentos desconocidos y
todos los fragmentos conocidos excepto IHDR,
PLTE, tRNS, IDAT e IEND están
afectados.

Los fragmentos desconocidos declarados de esta manera se guardarán como datos en bruto en una lista de estructuras png_unknown_chunk. Si un fragmento que normalmente es conocido por libpng se nombra en la lista, se manejará como desconocido, de acuerdo con la directiva "keep". Si un fragmento se nombra en instancias sucesivas de png_set_keep_unknown_chunks(), la instancia final tendrá prioridad. Los fragmentos IHDR e IEND no deben nombrarse en chunk_list; si lo están, libpng los procesará normalmente de todos modos. Si sabe que su aplicación nunca utilizará ciertos fragmentos en particular, use PNG_HANDLE_CHUNK_NEVER (o 1) como se demuestra a continuación.

Aquí hay un ejemplo del uso de png_set_keep_unknown_chunks(), donde el fragmento privado "vpAg" será procesado posteriormente por una función de devolución de llamada de fragmento de usuario:


png_byte vpAg[5]={118, 112, 65, 103, (png_byte) ' '};


#if defined(PNG_UNKNOWN_CHUNKS_SUPPORTED)
png_byte unused_chunks[]=
{
104, 73, 83, 84, (png_byte) ' ', /* hIST */
105, 84, 88, 116, (png_byte) ' ', /* iTXt */
112, 67, 65, 76, (png_byte) ' ', /* pCAL */
115, 67, 67, 76, (png_byte) ' ', /* sCAL */
115, 80, 76, 84, (png_byte) ' ', /* sPLT */
116, 73, 77, 69, (png_byte) ' ', /* tIME */
};
#endif


...


#if defined(PNG_UNKNOWN_CHUNKS_SUPPORTED)
/* ignorar todos los fragmentos desconocidos
* (usar la configuración global "2" para libpng16 y anteriores):
*/
png_set_keep_unknown_chunks(read_ptr, 2, NULL, 0);


/* excepto por vpAg: */
png_set_keep_unknown_chunks(read_ptr, 2, vpAg, 1);


/* ignorar también los fragmentos conocidos no utilizados: */
png_set_keep_unknown_chunks(read_ptr, 1, unused_chunks,
(int)(sizeof unused_chunks)/5);
#endif

Límites del usuario

La especificación PNG permite que el ancho y la altura de una imagen sean tan grandes como 2^(31-1 (0x7fffffff), o aproximadamente 2.147 mil millones de filas y columnas. Por seguridad, libpng impone un límite predeterminado de 1 millón de filas y columnas. Las imágenes más grandes se rechazarán inmediatamente con una llamada a png_error(). Si desea cambiar estos límites, puede usar


png_set_user_limits(png_ptr, width_max, height_max);

para establecer sus propios límites (libpng puede rechazar algunas imágenes muy anchas de todos modos debido a posibles condiciones de desbordamiento de búfer).

Debe colocar esta declaración después de crear la estructura PNG y antes de llamar a png_read_info(), png_read_png() o png_process_data().

Al escribir un flujo de datos PNG, coloque esta declaración antes de llamar a png_write_info() o png_write_png().

Si necesita recuperar los límites que se están aplicando, use


width_max = png_get_user_width_max(png_ptr);
height_max = png_get_user_height_max(png_ptr);

La especificación PNG no establece límites en la cantidad de fragmentos auxiliares permitidos en un flujo de datos PNG. Por defecto, libpng impone un límite de un total de 1000 fragmentos sPLT, tEXt, iTXt, zTXt y desconocidos que se almacenarán. Si ha configurado tanto info_ptr como end_info_ptr, el límite se aplica por separado a cada uno. Puede cambiar el límite en la cantidad total de dichos fragmentos que se almacenarán, con


png_set_chunk_cache_max(png_ptr, user_chunk_cache_max);

donde 0x7fffffffL significa ilimitado. Puede recuperar este límite con


chunk_cache_max = png_get_chunk_cache_max(png_ptr);

Libpng impone un límite de 8 Megabytes (8,000,000 bytes) en la cantidad de memoria que cualquier fragmento que no sea IDAT puede ocupar, originalmente o cuando se descomprime (antes de libpng-1.6.32 el límite solo se aplicaba a los fragmentos comprimidos después de la descompresión). Puede cambiar este límite con


png_set_chunk_malloc_max(png_ptr, user_chunk_malloc_max);

y puede recuperar el límite con


chunk_malloc_max = png_get_chunk_malloc_max(png_ptr);

Se ignorarán los fragmentos que provoquen que alguno de estos límites se supere.

Información sobre su sistema

Si tiene la intención de mostrar el PNG o incorporarlo en otros datos de imagen, necesita decirle a libpng información sobre su pantalla o superficie de dibujo para que libpng pueda convertir los valores de la imagen para que coincidan con la pantalla.

Desde libpng-1.5.4 esta información se puede establecer antes de leer la cabecera del archivo PNG. En versiones anteriores existía png_set_gamma() pero se comportaba incorrectamente si se llamaba antes de que se hubiera leído la cabecera del archivo PNG y png_set_alpha_mode() no existía.

Si necesita admitir versiones anteriores a libpng-1.5.4, pruebe el número de versión como se ilustra a continuación usando "PNG_LIBPNG_VER >= 10504" y siga los procedimientos descritos en la página de manual correspondiente.

Proporciona a libpng la codificación esperada por su sistema expresada como un valor de 'gamma'. También puede especificar una codificación predeterminada para el archivo PNG en caso de que la información requerida falte en el archivo. Por defecto, libpng asume que los datos PNG coinciden con su sistema, para mantener este valor predeterminado llame:


png_set_gamma(png_ptr, screen_gamma, output_gamma);

o puede usar el equivalente de punto fijo:


png_set_gamma_fixed(png_ptr, PNG_FP_1*screen_gamma,
PNG_FP_1*output_gamma);

Si no conoce el gamma de su sistema, probablemente sea 2.2 - una buena aproximación al estándar IEC para sistemas de visualización (sRGB). Si las imágenes son demasiado contrastadas o deslavadas, ¡se equivocó con el valor! ¡Consulte la documentación de su sistema!

Muchos sistemas permiten cambiar el gamma del sistema a través de una tabla de consulta en el controlador de pantalla, algunos sistemas, incluidos los Macs antiguos, cambian la respuesta por defecto. A partir de la versión 1.5.4 hay tres valores especiales disponibles

libpng


PNG_DEFAULT_sRGB: Indica que el sistema cumple con el estándar
IEC 61966-2-1. Esto coincide con casi
todos los sistemas.
PNG_GAMMA_MAC_18: Indica que el sistema es un sistema Apple Macintosh
antiguo (anterior a Mac OS 10.6) con
la configuración predeterminada.
PNG_GAMMA_LINEAR: Solo el valor de punto fijo para 1.0 - indica
que el sistema espera datos sin codificación gamma.

Utilizaría el valor lineal (sin codificar) si necesita procesar los valores de píxeles además, ya que esto evita la necesidad de decodificar y recodificar cada valor de componente cada vez que se realiza una operación aritmética. Gran parte del software gráfico utiliza valores lineales por esta razón, a menudo con valores de componentes de mayor precisión para preservar la precisión general.

El valor output_gamma expresa cómo decodificar los valores de salida, no cómo están codificados. Los valores utilizados corresponden a los números normales utilizados para describir la gamma general de un sistema de visualización de computadora; por ejemplo, 2.2 para un sistema compatible con sRGB. Los valores se escalan por 100000 en la versión de _fixed de la API (por lo tanto, 220000 para sRGB).

La inversa del valor siempre se utiliza para proporcionar un valor predeterminado para la codificación del archivo PNG si no tiene un chunk gAMA y si no se ha llamado a png_set_gamma() para anular la información de gamma de PNG.

Cuando se selecciona el modo ALPHA_OPTIMIZED, la gamma de salida se utiliza para codificar píxeles opacos, sin embargo, los píxeles con valores alfa más bajos no se codifican, independientemente de la configuración de gamma de salida.

Cuando se solicita el manejo estándar de Porter Duff con el modo 1, la codificación de salida se establece como lineal y el valor output_gamma solo es relevante como valor predeterminado para los datos de entrada que no tienen información gamma. La codificación de salida lineal se anulará si se llama a png_set_gamma() - ¡los resultados pueden ser muy inesperados!

Los siguientes números se derivan del estándar sRGB y la investigación detrás de él. sRGB se define para ser aproximado por un valor de chunk gAMA de PNG de 0.45455 (1/2.2) para PNG. El valor incluye implícitamente cualquier corrección de visualización requerida para tener en cuenta las diferencias en el entorno de color de la escena original y el entorno de visualización previsto; el valor expresa cómo *decodificar* la imagen para su visualización, no cómo se *codificaron* los datos originales.

sRGB proporciona un punto de referencia para el estándar PNG al definir un entorno de visualización. sRGB en sí mismo, y los estándares de TV anteriores, en realidad utilizan una transformación más compleja (una porción lineal seguida de una ley de potencia gamma 2.4) de la que PNG puede expresar. (PNG se limita a leyes de potencia simples). Al decir que una imagen para visualización directa en un sistema compatible con sRGB debe almacenarse con un valor de chunk gAMA de 45455 (11.3.3.2 y 11.3.3.5 de la especificación ISO PNG), la especificación PNG permite derivar valores para otros sistemas y entornos de visualización.

El valor de Mac se deduce de sRGB basándose en la suposición de que la corrección de visualización adicional real utilizada en los primeros sistemas de visualización de Mac se implementó como una tabla de búsqueda de potencia 1.45.

Cualquier sistema donde se utilice una tabla de búsqueda programable o donde las características del dispositivo de visualización final puedan cambiarse requiere código específico del sistema para obtener la característica actual. Sin embargo, esto puede ser difícil y la mayoría de las correcciones gamma de PNG solo requieren un valor aproximado.

Por defecto, si no se llama a png_set_alpha_mode(), libpng asume que todos los valores son valores lineales sin codificar y que el dispositivo de salida también tiene una característica lineal. Esto rara vez es correcto; siempre es mejor llamar a png_set_alpha_mode() con PNG_DEFAULT_sRGB que depender del valor predeterminado si no sabe cuál es la respuesta correcta.

El valor especial PNG_GAMMA_MAC_18 indica un sistema Mac anterior (anterior a Mac OS 10.6) que utilizaba una tabla de corrección para implementar una gamma algo más baja en un sistema sRGB.

Ambos valores están reservados (no son valores gamma simples) para permitir una corrección más precisa internamente en el futuro.

NOTA: los valores se pueden pasar a las API de punto fijo o de punto flotante, pero la API de punto flotante también aceptará valores de punto flotante.

Lo segundo de lo que puede necesitar informar a libpng es cómo su sistema maneja la información del canal alfa. Algunos archivos PNG, pero no todos, contienen un canal alfa. Para mostrar estos archivos correctamente, necesita componer los datos sobre un fondo adecuado, como se describe en la especificación PNG.

Libpng solo admite la composición sobre un solo color (usando png_set_background; ver más abajo). De lo contrario, debe realizar la composición usted mismo y, en este caso, es posible que deba llamar a png_set_alpha_mode:


#if PNG_LIBPNG_VER >= 10504
png_set_alpha_mode(png_ptr, mode, screen_gamma);
#else
png_set_gamma(png_ptr, screen_gamma, 1.0/screen_gamma);
#endif

El valor screen_gamma es el mismo que el argumento de png_set_gamma; sin embargo, cómo afecta a la salida depende del modo. png_set_alpha_mode() establece el valor predeterminado de gamma de archivo a 1/screen_gamma, por lo que normalmente no necesita llamar a png_set_gamma. Si necesita valores predeterminados diferentes, llame a png_set_gamma() antes de png_set_alpha_mode() - si lo llama después, anulará la configuración realizada por png_set_alpha_mode().

El modo es el siguiente:


PNG_ALPHA_PNG: Los datos se codifican según la especificación PNG. Los componentes rojo, verde y azul, o gris, son valores de color codificados con gamma y no se multiplican previamente por el valor alfa. El valor alfa es una medida lineal de la contribución del píxel al píxel de salida final correspondiente.

Normalmente debería usar este formato si tiene la intención de realizar correcciones de color en los valores de color; la mayoría, si no todos, los programas de corrección de color no tienen manejo para el canal alfa y, de todos modos, las matemáticas para manejar valores de componentes pre-multiplicados son innecesariamente complejas.

Antes de realizar cualquier operación aritmética en los valores de los componentes, debe eliminar la codificación gamma y multiplicar el canal alfa. Consulte la especificación PNG para obtener más detalles. Es importante tener en cuenta que cuando una imagen con un canal alfa se escala, se deben utilizar valores de componentes codificados linealmente y pre-multiplicados.

Los modos restantes suponen que no necesita realizar más correcciones de color o que, si lo hace, su software de corrección de color sabe todo sobre el alfa (probablemente no lo haga). 'Asocian' el alfa con la información de color almacenando valores de canal de color que se han escalado por el alfa. La ventaja es que los canales de color se pueden remuestrear (la imagen se puede escalar) en esta forma. La desventaja es que la práctica normal es almacenar valores lineales, no codificados (gamma), y esto requiere canales de 16 bits para imágenes fijas en lugar de los canales de 8 bits que son apenas suficientes si se utiliza la codificación gamma. Además, todos los valores de píxeles no transparentes, incluidos los completamente opacos, deben codificarse con gamma para producir la imagen final. Estos son los modos 'STANDARD', 'ASSOCIATED' o 'PREMULTIPLIED' descritos a continuación (siendo los dos últimos los nombres comunes para los canales de color alfa asociados). Tenga en cuenta que los archivos PNG siempre contienen canales de color no asociados; png_set_alpha_mode() con uno de los modos hace que el decodificador convierta los píxeles a una forma asociada antes de devolverlos a su aplicación.

Dado que no es necesario realizar operaciones aritméticas en valores de color opacos siempre que no vayan a ser remuestreados y estén en el espacio de color final, es posible optimizar el manejo del alfa almacenando los píxeles opacos en formato PNG (ajustados para el espacio de color de salida) mientras se almacenan los píxeles parcialmente opacos en el formato lineal estándar. La precisión requerida para la composición alfa estándar es relativamente baja, porque los píxeles están aislados, por lo tanto, típicamente la pérdida de precisión en el almacenamiento de valores lineales de 8 bits es aceptable. (Esto no es cierto si el canal alfa se utiliza para simular transparencia en áreas grandes - ¡use 16 bits o el modo PNG en este caso!) Este es el modo 'OPTIMIZED'. Para este modo, un píxel se trata como opaco solo si el valor alfa es igual al valor máximo.


PNG_ALPHA_STANDARD: Los datos que produce libpng se codifican de la forma estándar que la mayoría del software gráfico escrito correctamente asume. libpng eliminará la codificación gamma y los valores de componentes lineales se multiplicarán previamente por el canal alfa.

Con este formato, la imagen final debe recodificarse para que coincida con la gamma de visualización antes de mostrar la imagen. Si su sistema no hace eso, y aún así parece realizar operaciones aritméticas en los píxeles sin decodificarlos, está roto; consulte los modos a continuación.

Con PNG_ALPHA_STANDARD, libpng siempre produce valores de componentes lineales, independientemente de la screen_gamma que proporcione. Sin embargo, el valor screen_gamma se utiliza como valor predeterminado para la gamma de archivo si el archivo PNG no tiene información de gamma.

Si llama a png_set_gamma() después de png_set_alpha_mode(), anulará la codificación lineal. En su lugar, los valores de píxeles pre-multiplicados se codificarán con gamma, pero el canal alfa seguirá siendo lineal. Esto puede coincidir con los requisitos de algún software defectuoso, pero es poco probable.

Si bien los datos lineales de 8 bits se utilizan a menudo, tienen una precisión insuficiente para cualquier imagen con un rango dinámico razonable. Para evitar problemas, y si su software lo admite, use png_set_expand_16() para forzar que todos los componentes sean de 16 bits.


PNG_ALPHA_OPTIMIZED: Este modo es el mismo que PNG_ALPHA_STANDARD, excepto que los píxeles completamente opacos se codifican con gamma según el valor screen_gamma. Los píxeles con alfa inferior a 1.0 seguirán teniendo componentes lineales.

Utilice este formato si tiene control sobre su software de composición y, por lo tanto, no realiza otras operaciones aritméticas (como escalar) con los datos que obtiene de libpng. Su software de composición puede simplemente copiar píxeles opacos a la salida, pero aún tiene valores lineales para los píxeles no opacos.

En la composición normal, donde el canal alfa codifica la cobertura parcial de píxeles (en contraposición a la translucidez de área amplia), las imprecisiones de la representación de 8 bits de píxeles no opacos son irrelevantes.

También puede probar este formato si su software está defectuoso; podría verse mejor.


PNG_ALPHA_BROKEN: Esto es PNG_ALPHA_STANDARD; sin embargo, todos los valores de los componentes, incluido el canal alfa, están codificados con gamma. Esto es defectuoso porque, en la práctica, ninguna implementación que utilice esta opción deshace correctamente la codificación antes de manejar la composición alfa. Utilice esta opción solo si otros errores graves en el software o hardware que utiliza lo exigen. En la mayoría de los casos de software o hardware defectuosos, el error en la visualización final se manifiesta como un halo sutil alrededor de las partes compuestas de la imagen. Es posible que ni siquiera lo perciba como un halo; la parte compuesta de la imagen puede simplemente aparecer separada del fondo, como si se hubiera recortado de papel y pegado después.

Si no tiene que lidiar con errores en software o hardware, o si puede corregirlos, hay tres formas recomendadas de usar png_set_alph

a_mode()

   png_set_alpha_mode(png_ptr, PNG_ALPHA_PNG,
   screen_gamma);

Puede realizar correcciones de color en el resultado (libpng actualmente no admite correcciones de color internamente). Cuando maneje el canal alfa, deberá deshacer la codificación gamma y multiplicar el alfa.

   png_set_alpha_mode(png_ptr, PNG_ALPHA_STANDARD,
   screen_gamma);
   png_set_expand_16(png_ptr);

Si está utilizando la interfaz de alto nivel, no llame a png_set_expand_16(); en su lugar, pase PNG_TRANSFORM_EXPAND_16 a la interfaz.

Con este modo no puede realizar correcciones de color, pero puede realizar operaciones aritméticas, incluida la composición y el escalado, en los datos sin un procesamiento adicional.

   png_set_alpha_mode(png_ptr, PNG_ALPHA_OPTIMIZED,
   screen_gamma);

Puede evitar la expansión a componentes de 16 bits con este modo, pero pierde la capacidad de escalar la imagen o realizar otras operaciones aritméticas lineales. Todo lo que puede hacer es componer el resultado en una salida coincidente. Dado que este modo es específico de libpng, también deberá escribir su propio software de composición.

Los siguientes son ejemplos de llamadas a png_set_alpha_mode para lograr la corrección gamma general requerida y, cuando sea necesario, la pre-multiplicación alfa.

   png_set_alpha_mode(pp, PNG_ALPHA_PNG, PNG_DEFAULT_sRGB);

Las opciones para alpha_mode son:

   PNG_ALPHA_PNG 0 /* según el estándar PNG */
   PNG_ALPHA_STANDARD 1 /* según Porter/Duff */
   PNG_ALPHA_ASSOCIATED 1 /* como arriba; esta es la práctica normal */
   PNG_ALPHA_PREMULTIPLIED 1 /* como arriba */
   PNG_ALPHA_OPTIMIZED 2 /* 'PNG' para píxeles opacos, de lo contrario 'STANDARD' */
   PNG_ALPHA_BROKEN 3 /* el canal alfa está codificado en gamma */

PNG_ALPHA_PNG es el manejo predeterminado de libpng del canal alfa. No está pre-multiplicado en los componentes de color. Además, la llamada indica que la salida es para un sistema sRGB y hace que todos los archivos PNG sin fragmentos gAMA se asuman codificados usando sRGB.

   png_set_alpha_mode(pp, PNG_ALPHA_PNG, PNG_GAMMA_MAC);

En este caso, se asume que la salida es algo así como una pantalla compatible con sRGB precedida por una tabla de consulta de ley de potencias de potencia 1.45. Así es como se comportaban los primeros sistemas Mac.

   png_set_alpha_mode(pp, PNG_ALPHA_STANDARD, PNG_GAMMA_LINEAR);

Este es el enfoque clásico de Jim Blinn y funcionará en entornos académicos donde todo se hace según las reglas. Tiene la desventaja de asumir que los datos PNG de entrada sin información gamma son lineales; es poco probable que esto sea correcto a menos que los archivos PNG se hayan generado localmente. La mayoría de las veces, la precisión de la salida será tan baja que mostrará una banda significativa en las áreas oscuras de la imagen.

   png_set_expand_16(pp);
   png_set_alpha_mode(pp, PNG_ALPHA_STANDARD, PNG_DEFAULT_sRGB);

Este es un enfoque inspirado en Jim Blinn algo más realista. Se asume que los archivos PNG tienen la codificación sRGB si no están marcados con un valor gamma y la salida siempre es de 16 bits por componente. Esto permite un escalado y procesamiento precisos de los datos. Si sabe que sus archivos PNG de entrada se generaron localmente, es posible que deba reemplazar PNG_DEFAULT_sRGB con el valor correcto para su sistema.

   png_set_alpha_mode(pp, PNG_ALPHA_OPTIMIZED, PNG_DEFAULT_sRGB);

Si solo necesita componer la imagen PNG sobre un fondo existente y si usted controla el código que hace esto, puede usar la configuración de optimización. En este caso, simplemente copia los píxeles completamente opacos a la salida. Para los píxeles que no son completamente transparentes (simplemente omita esos), realice las matemáticas de composición usando png_composite o png_composite_16 a continuación y luego codifique los valores resultantes de 8 bits o 16 bits para que coincidan con la codificación de salida.

   Otros casos

Si ni la codificación PNG ni la lineal estándar le funcionan debido al software o hardware que utiliza, entonces tiene un gran problema. El caso PNG probablemente resultará en halos alrededor de la imagen. La codificación lineal probablemente resultará en una imagen descolorida y demasiado brillante (en realidad, es demasiado contrastada). Pruebe el modo ALPHA_OPTIMIZED anterior; esto probablemente reducirá sustancialmente los halos. Alternativamente, intente:

   png_set_alpha_mode(pp, PNG_ALPHA_BROKEN, PNG_DEFAULT_sRGB);

Esta opción también reducirá los halos, pero habrá ligeros halos oscuros alrededor de las partes opacas de la imagen donde el fondo es claro. En el modo OPTIMIZED, los halos serán halos claros donde el fondo es oscuro. Elija: ¡los halos son inevitables a menos que pueda arreglar su hardware/software! (El enfoque OPTIMIZED es ligeramente más rápido).

Cuando el gamma predeterminado de los archivos PNG no coincide con el gamma de salida. Si tiene archivos PNG sin información gamma, png_set_alpha_mode le permite proporcionar un gamma predeterminado, pero también establece el gamma de salida en el valor coincidente. Si sabe que sus archivos PNG tienen un gamma que no coincide con la salida, puede aprovechar el hecho de que png_set_alpha_mode siempre establece el gamma de salida pero solo establece el predeterminado PNG si aún no está establecido:

   png_set_alpha_mode(pp, PNG_ALPHA_PNG, PNG_DEFAULT_sRGB);
   png_set_alpha_mode(pp, PNG_ALPHA_PNG, PNG_GAMMA_MAC);

La primera llamada establece los valores gamma predeterminado y de salida, la segunda llamada anula el gamma de salida sin cambiar el predeterminado. Esto es más fácil que lograr el mismo efecto con png_set_gamma. Debe usar PNG_ALPHA_PNG para la primera llamada; la verificación interna en png_set_alpha se activará si se realiza más de una llamada a png_set_alpha_mode y png_set_background en la misma operación de lectura; sin embargo, se ignoran múltiples llamadas con PNG_ALPHA_PNG.

Si no necesita el canal alfa o no puede manejarlo, puede llamar a png_set_background() para eliminarlo componiéndolo contra un color fijo. No llame a png_set_strip_alpha() para hacer esto; dejará valores de píxel espurios en partes transparentes de esta imagen.

   png_set_background(png_ptr, &background_color,
   PNG_BACKGROUND_GAMMA_SCREEN, 0, 1);

El color_de_fondo es un valor RGB o de escala de grises según el formato de datos que libpng le proporcionará. Debido a que aún no conoce el formato del archivo PNG, si llama a png_set_background en este momento, debe asegurarse de que el formato producido por libpng siempre tenga componentes de 8 bits o 16 bits y luego almacenar el color como un color de 8 bits o 16 bits según corresponda. El color contiene valores de componentes grises y RGB separados, por lo que puede permitir que libpng produzca salida gris o RGB según el formato de entrada, pero las imágenes de escala de grises de baja profundidad de bits siempre deben convertirse a un formato de al menos 8 bits. (¡Incluso si las imágenes de escala de grises de baja profundidad de bits no pueden tener un canal alfa, pueden tener un color transparente!).

Establecerá las transformaciones que necesite más tarde, ya sea como indicadores para la interfaz de alto nivel o llamadas a la API de libpng para la interfaz de bajo nivel. Como referencia, la configuración y las llamadas a la API requeridas son:

The read interface

Libpng expects the application to allocate space for the image data. There are two ways to do this:

  • The simple way:

    Call png_set_rows() and pass it a pointer to an array of pointers, one for each row. Libpng will allocate and free memory for the row pointers if you use png_malloc() for them.

  • The low-level way:

    Allocate one large buffer and calculate the addresses of each row within that buffer.

In either case, you are responsible for freeing the memory when you are done with it. The simplest way to do this is to use the simplified API, where libpng handles all the memory management for you.

Here is an example of the simple allocation method:


png_bytepp row_pointers = NULL;
...
/* Allocate memory for row pointers */
row_pointers = (png_bytepp)png_malloc(png_ptr, height * sizeof(png_bytep));
for (int i = 0; i < height; i++)
row_pointers[i] = NULL; /* Initialize with NULL */
/* Allocate memory for each row */
for (int i = 0; i < height; i++) {
row_pointers[i] = (png_bytep)png_malloc(png_ptr, png_get_rowbytes(png_ptr,
info_ptr));
}
/* Set the row pointers in libpng */
png_set_rows(png_ptr, info_ptr, row_pointers);
...
/* Free the memory */
for (int i = 0; i < height; i++)
png_free(png_ptr, row_pointers[i]);
png_free(png_ptr, row_pointers);

If you use png_read_png(), libpng will allocate memory for the row pointers and the image data itself, and will free it when you call png_destroy_read_struct().

Here is an example of the low-level allocation method:


png_bytepp row_pointers = NULL;
png_bytep buffer = NULL;
...
/* Allocate one large buffer for the image data */
buffer = (png_bytep)png_malloc(png_ptr, png_get_rowbytes(png_ptr,
info_ptr) * height);
/* Allocate memory for row pointers */
row_pointers = (png_bytepp)png_malloc(png_ptr, height * sizeof(png_bytep));
for (int i = 0; i < height; i++) {
row_pointers[i] = buffer + i * png_get_rowbytes(png_ptr, info_ptr);
}
/* Set the row pointers in libpng */
png_set_rows(png_ptr, info_ptr, row_pointers);
...
/* Free the memory */
png_free(png_ptr, row_pointers);
png_free(png_ptr, buffer);

If you use png_set_rows(), the application is responsible for freeing row_pointers (and row_pointers[i], if they were separately allocated).

If you don't allocate row_pointers ahead of time, png_read_png() will do it, and it'll be free'ed by libpng when you call png_destroy_*().

The low-level read interface

If you are going the low-level route, you are now ready to read all the file information up to the actual image data. You do this with a call to png_read_info().


png_read_info(png_ptr, info_ptr);

This will process all chunks up to but not including the image data.

This also copies some of the data from the PNG file into the decode structure for use in later transformations. Important information copied in is:

1) The PNG file gamma from the gAMA chunk. This overwrites the default value provided by an earlier call to png_set_gamma() or png_set_alpha_mode().

2) Prior to libpng-1.5.4 the background color from a bKGd chunk. This damages the information provided by an earlier call to png_set_background() resulting in unexpected behavior. Libpng-1.5.4 no longer does this.

3) The number of significant bits in each component value. Libpng uses this to optimize gamma handling by reducing the internal lookup table sizes.

4) The transparent color information from a tRNS chunk. This can be modified by a later call to png_set_tRNS().

Una breve palabra sobre text_ptr y num_text. PNG almacena comentarios en pares clave/texto, un par por chunk, sin límite en el número de chunks de texto y un límite de 2^31 bytes en su tamaño. Se sugiere encarecidamente que las claves y el texto sean comprensibles para los humanos (ese es el propósito), así que no use abreviaturas. No se permiten símbolos que no se impriman. Consulte la especificación PNG para más detalles. Tampoco hay requisito de tener texto después de la clave.

Sin embargo, algunos o todos los chunks de texto pueden estar después de la imagen, así que, para asegurarse de haber leído todos los chunks de texto, no manipule estos hasta después de leer la información posterior a la imagen. Esto se mencionará nuevamente más abajo en la discusión que acompaña a png_read_end().

Transformaciones de entrada

Después de haber leído la información de la cabecera, puede configurar la biblioteca para que maneje cualquier transformación especial de los datos de la imagen. Las diversas formas de transformar los datos se describirán en el orden en que deben ocurrir. Esto es importante, ya que algunos de estos cambian el tipo de color y/o la profundidad de bits de los datos, y otros solo funcionan en ciertos tipos de color y profundidades de bits.

Las transformaciones que solicita se ignoran si no tienen ningún significado para un formato de datos de entrada particular. Sin embargo, algunas transformaciones pueden tener un efecto como resultado de una transformación previa. Si especifica un conjunto contradictorio de transformaciones, por ejemplo, agregar y quitar el canal alfa, no puede predecir el resultado final.

El color utilizado para los valores de transparencia debe suministrarse en el mismo formato/profundidad que los datos actuales de la imagen. Se almacena en el mismo formato/profundidad que los datos de la imagen en un chunk tRNS, por lo que esto es lo que libpng espera para estos datos.

El color utilizado para el valor de fondo depende del argumento need_expand, como se describe a continuación.

Por ejemplo, los datos paletizados o en escala de grises de 4 bits/píxel se devolverán como 2 píxeles/byte con el píxel más a la izquierda en los bits de orden superior del byte, a menos que se llame a png_set_packing(). Los datos RGB de 8 bits se almacenarán en formato RGB RGB RGB, a menos que se llame a png_set_filler() o png_set_add_alpha() para insertar bytes de relleno, antes o después de cada triplete RGB.

Los datos RGB de 16 bits se devolverán RRGGBB RRGGBB, con el byte más significativo del valor del color primero, a menos que se llame a png_set_scale_16() para transformarlo a tripletes RGB RGB normales, o se llame a png_set_filler() o png_set_add_alpha() para insertar dos bytes de relleno, antes o después de cada triplete RRGGBB. Del mismo modo, los datos en escala de grises de 8 o 16 bits se pueden modificar con png_set_filler(), png_set_add_alpha(), png_set_strip_16() o png_set_scale_16().

png_set_filler(png_ptr, filler, PNG_FILLER_BEFORE);

Al rellenar un píxel de 8 bits, se utilizan los 8 bits menos significativos del número, si se proporciona un número de 16 bits. png_get_current_row_number(png_structp png_ptr);

No intente usarlos fuera de una devolución de llamada de transformación; en primer lugar, solo son compatibles si las transformaciones de usuario son compatibles, en segundo lugar, pueden devolver resultados inesperados a menos que la fila se esté procesando activamente en el momento en que se llaman.

Con imágenes entrelazadas, el valor devuelto es la fila en la subimagen de entrada. Utilice `PNG_ROW_FROM_PASS_ROW(row, pass)` y `PNG_COL_FROM_PASS_COL(col, pass)` para encontrar el píxel de salida (x,y) dado un píxel de subimagen entrelazada (row,col,pass).

La discusión sobre el manejo del entrelazado anterior contiene más información sobre cómo usar estos valores.

También puede configurar un puntero a una estructura de usuario para que la utilice su función de devolución de llamada, e informar a libpng de que su función de transformación cambiará el número de canales o la profundidad de bits con la función


png_set_user_transform_info(png_ptr, user_ptr,
user_depth, user_channels);

La aplicación del usuario, no libpng, es responsable de asignar y liberar cualquier memoria requerida para la estructura de usuario.

Puede recuperar el puntero a través de la función `png_get_user_transform_ptr()`. Por ejemplo:


voidp read_user_transform_ptr =
png_get_user_transform_ptr(png_ptr);

Lo último que hay que manejar es el entrelazado; esto se cubre en detalle a continuación, pero debe llamar a la función aquí si desea que libpng maneje la expansión de la imagen entrelazada.


number_of_passes = png_set_interlace_handling(png_ptr);

Después de establecer las transformaciones, libpng puede actualizar su estructura `png_info` para reflejar cualquier transformación que haya solicitado con esta llamada.


png_read_update_info(png_ptr, info_ptr);

Esto es muy útil para actualizar el campo `rowbytes` de la estructura `info` para que pueda usarlo para asignar la memoria de su imagen. Esta función también actualizará su paleta con la `screen_gamma` y el fondo correctos si se han proporcionado con las llamadas anteriores. Solo puede llamar a `png_read_update_info()` una vez con un `info_ptr` determinado.

Después de llamar a `png_read_update_info()`, puede asignar cualquier memoria que necesite para contener la imagen. Los datos de fila son simplemente datos de bytes sin procesar para todas las formas de imágenes. Dado que la asignación real varía entre las aplicaciones, no se proporcionará ningún ejemplo. Si está asignando un gran bloque de memoria, deberá crear una matriz de punteros a cada fila, ya que será necesaria para algunas de las funciones siguientes.

Asegúrese de que su plataforma pueda asignar el búfer que necesitará. libpng verifica internamente el ancho excesivo, pero deberá hacer su propia verificación para `number_of_rows*width*pixel_size` si está utilizando un búfer de varias filas:


/* Protección contra desbordamiento de enteros */
if (number_of_rows > PNG_SIZE_MAX/(width*pixel_size))
png_error(png_ptr, "el búfer image_data sería demasiado grande");

Recuerde: Antes de llamar a `png_read_update_info()`, las funciones `png_get_*()` devuelven los valores correspondientes a la imagen PNG original. Después de llamar a `png_read_update_info()`, los valores se refieren a la imagen que libpng generará. En consecuencia, debe llamar a todas las funciones `png_set_*()` antes de llamar a `png_read_update_info()`. Esto es particularmente importante para `png_set_interlace_handling()`: si va a llamar a `png_read_update_info()`, debe llamar a `png_set_interlace_handling()` antes, a menos que desee recibir una salida entrelazada.

Reading image data

After you've allocated memory, you can read the image data. The simplest way to do this is in one function call. If you are allocating enough memory to hold the whole image, you can just call png_read_image() and libpng will read in all the image data and put it in the memory area supplied. You will need to pass in an array of pointers to each row.

This function automatically handles interlacing, so you don't need to call png_set_interlace_handling() (unless you call png_read_update_info()) or call this function multiple times, or any of that other stuff necessary with png_read_rows().


png_read_image(png_ptr, row_pointers);

where row_pointers is:


png_bytep row_pointers[height];

You can point to void or char or whatever you use for pixels.

If you don't want to read in the whole image at once, you can use png_read_rows() instead. If there is no interlacing (check interlace_type == PNG_INTERLACE_NONE), this is simple:


png_read_rows(png_ptr, row_pointers, NULL,
number_of_rows);

where row_pointers is the same as in the png_read_image() call.

If you are doing this just one row at a time, you can do this with a single row_pointer instead of an array of row_pointers:


png_bytep row_pointer = row;
png_read_row(png_ptr, row_pointer, NULL);

If the file is interlaced (interlace_type != 0 in the IHDR chunk), things get somewhat harder. The only current (PNG Specification version 1.2) interlacing type for PNG is (interlace_type == PNG_INTERLACE_ADAM7); a somewhat complicated 2D interlace scheme, known as Adam7, that breaks down an image into seven smaller images of varying size, based on an 8x8 grid. This number is defined (from libpng 1.5) as PNG_INTERLACE_ADAM7_PASSES in png.h

libpng can fill out those images or it can give them to you "as is". It is almost always better to have libpng handle the interlacing for you. If you want the images filled out, there are two ways to do that. The one mentioned in the PNG specification is to expand each pixel to cover those pixels that have not been read yet (the "rectangle" method). This results in a blocky image for the first pass, which gradually smooths out as more pixels are read. The other method is the "sparkle" method, where pixels are drawn only in their final locations, with the rest of the image remaining whatever colors they were initialized to before the start of the read. The first method usually looks better, but tends to be slower, as there are more pixels to put in the rows.

If, as is likely, you want libpng to expand the images, call this before calling png_start_read_image() or png_read_update_info():


if (interlace_type == PNG_INTERLACE_ADAM7)
number_of_passes
= png_set_interlace_handling(png_ptr);

This will return the number of passes needed. Currently, this is seven, but may change if another interlace type is added. This function can be called even if the file is not interlaced, where it will return one pass. You then need to read the whole image 'number_of_passes' times. Each time will distribute the pixels from the current pass to the correct place in the output image, so you need to supply the same rows to png_read_rows in each pass.

If you are not going to display the image after each pass, but are going to wait until the entire image is read in, use the sparkle effect. This effect is faster and the end result of either method is exactly the same. If you are planning on displaying the image after each pass, the "rectangle" effect is generally considered the better looking one.

If you only want the "sparkle" effect, just call png_read_row() or png_read_rows() as normal, with the third parameter NULL. Make sure you make pass over the image number_of_passes times, and you don't change the data in the rows between calls. You can change the locations of the data, just not the data. Each pass only writes the pixels appropriate for that pass, and assumes the data from previous passes is still valid.


png_read_rows(png_ptr, row_pointers, NULL,
number_of_rows);
or
png_read_row(png_ptr, row_pointers, NULL);

If you only want the first effect (the rectangles), do the same as before except pass the row buffer in the third parameter, and leave the second parameter NULL.


png_read_rows(png_ptr, NULL, row_pointers,
number_of_rows);
or
png_read_row(png_ptr, NULL, row_pointers);

If you don't want libpng to handle the interlacing details, just call png_read_rows() PNG_INTERLACE_ADAM7_PASSES times to read in all the images. Each of the images is a valid image by itself; however, you will almost certainly need to distribute the pixels from each sub-image to the correct place. This is where everything gets very tricky.

If you want to retrieve the separate images you must pass the correct number of rows to each successive call of png_read_rows(). The calculation gets pretty complicated for small images, where some sub-images may not even exist because either their width or height ends up zero. libpng provides two macros to help you in 1.5 and later versions:


png_uint_32 width = PNG_PASS_COLS(image_width, pass_number);
png_uint_32 height = PNG_PASS_ROWS(image_height, pass_number);

Respectively these tell you the width and height of the sub-image corresponding to the numbered pass. 'pass' is in in the range 0 to 6 - this can be confusing because the specification refers to the same passes as 1 to 7! Be careful, you must check both the width and height before calling png_read_rows() and not call it for that pass if either is zero.

You can, of course, read each sub-image row by row. If you want to produce optimal code to make a pixel-by-pixel transformation of an interlaced image this is the best approach; read each row of each pass, transform it, and write it out to a new interlaced image.

If you want to de-interlace the image yourself libpng provides further macros to help that tell you where to place the pixels in the output image. Because the interlacing scheme is rectangular - sub-image pixels are always arranged on a rectangular grid - all you need to know for each pass is the starting column and row in the output image of the first pixel plus the spacing between each pixel. As of libpng 1.5 there are four macros to retrieve this information:


png_uint_32 x = PNG_PASS_START_COL(pass);
png_uint_32 y = PNG_PASS_START_ROW(pass);
png_uint_32 xStep = 1U << PNG_PASS_COL_SHIFT(pass);
png_uint_32 yStep = 1U << PNG_PASS_ROW_SHIFT(pass);

These allow you to write the obvious loop:


png_uint_32 input_y = 0;
png_uint_32 output_y = PNG_PASS_START_ROW(pass);


while (output_y < output_image_height)
{
png_uint_32 input_x = 0;
png_uint_32 output_x = PNG_PASS_START_COL(pass);


while (output_x < output_image_width)
{
image[output_y][output_x] =
subimage[pass][input_y][input_x++];


output_x += xStep;
}


++input_y;
output_y += yStep;
}

Notice that the steps between successive output rows and columns are returned as shifts. This is possible because the pixels in the subimages are always a power of 2 apart - 1, 2, 4 or 8 pixels - in the original image. In practice you may need to directly calculate the output coordinate given an input coordinate. libpng provides two further macros for this purpose:


png_uint_32 output_x = PNG_COL_FROM_PASS_COL(input_x, pass);
png_uint_32 output_y = PNG_ROW_FROM_PASS_ROW(input_y, pass);

Finally a pair of macros are provided to tell you if a particular image row or column appears in a given pass:


int col_in_pass = PNG_COL_IN_INTERLACE_PASS(output_x, pass);
int row_in_pass = PNG_ROW_IN_INTERLACE_PASS(output_y, pass);

Bear in mind that you will probably also need to check the width and height of the pass in addition to the above to be sure the pass even exists!

With any luck you are convinced by now that you don't want to do your own interlace handling. In reality normally the only good reason for doing this is if you are processing PNG files on a pixel-by-pixel basis and don't want to load the whole file into memory when it is interlaced.

libpng includes a test program, pngvalid, that illustrates reading and writing of interlaced images. If you can't get interlacing to work in your code and don't want to leave it to libpng (the recommended approach), see how pngvalid.c does it.

Finishing a sequential read

After you are finished reading the image through the low-level interface, you can finish reading the file.

If you want to use a different crc action for handling CRC errors in chunks after the image data, you can call png_set_crc_action() again at this point.

If you are interested in comments or time, which may be stored either before or after the image data, you should pass the separate png_info struct if you want to keep the comments from before and after the image separate.


png_infop end_info = png_create_info_struct(png_ptr);


if (!end_info)
{
png_destroy_read_struct(&png_ptr, &info_ptr, NULL);
return ERROR;
}


png_read_end(png_ptr, end_info);

If you are not interested, you should still call png_read_end() but you can pass NULL, avoiding the need to create an end_info structure. If you do this, libpng will not process any chunks after IDAT other than skipping over them and perhaps (depending on whether you have called png_set_crc_action) checking their CRCs while looking for the IEND chunk.


png_read_end(png_ptr, NULL);

If you don't call png_read_end(), then your file pointer will be left pointing to the first chunk after the last IDAT, which is probably not what you want if you expect to read something beyond the end of the PNG datastream.

When you are done, you can free all memory allocated by libpng like this:


png_destroy_read_struct(&png_ptr, &info_ptr, &end_info);

or, if you didn't create an end_info structure,


png_destroy_read_struct(&png_ptr, &info_ptr, NULL);

III. Lectura

En este punto, tienes un puntero a una estructura png_ptr y un puntero a una estructura png_info. Debes inicializar la estructura png_info con la información de cabecera del archivo PNG. El único modo de hacer esto es llamar a la función png_read_info(). Esta función lee y procesa todos los chunks que preceden inmediatamente al primer chunk IDAT. Devuelve un valor que indica el estado de la lectura, y si es necesario, se puede utilizar un longjmp() para manejar un error.


png_read_info(png_ptr, info_ptr);

Ahora, la estructura png_info contendrá la información de la cabecera del archivo PNG. Puedes consultar todos los campos de la estructura png_info para obtener la información que necesitas. Por ejemplo, puedes obtener el ancho y alto de la imagen llamando a png_get_image_width() y png_get_image_height().

Por ejemplo:


png_uint_32 width, height;
png_get_image_width(png_ptr, info_ptr, &width);
png_get_image_height(png_ptr, info_ptr, &height);

También puedes obtener información sobre el tipo de color, la profundidad de bits, etc. de la misma manera. Consulta la documentación de libpng para obtener una lista completa de las funciones de acceso a la información.

En este punto, también tienes la opción de transformar la imagen. libpng proporciona una serie de funciones que pueden modificar la forma en que se lee la imagen. Por ejemplo, puedes convertir una imagen de escala de grises a color RGB llamando a png_set_gray_to_rgb(). Puedes expandir una paleta a RGB llamando a png_set_palette_to_rgb(). Puedes eliminar el canal alfa llamando a png_set_strip_alpha(). Puedes eliminar la inversión de color llamando a png_set_invert_mono(). Puedes expandir la profundidad de bits a 8 bits por canal llamando a png_set_expanded().

La función png_set_interlace_handling() es útil para la lectura de imágenes entrelazadas. Esta función debe llamarse antes de leer los datos de píxeles, y establece el número de pasadas que se utilizarán para la lectura de imágenes entrelazadas. Devuelve el número de pasadas que se utilizarán.


int num_passes = png_set_interlace_handling(png_ptr);

Después de configurar las transformaciones deseadas, debes llamar a png_read_update_info(). Esta función actualiza la estructura png_info con la información de la imagen después de aplicar las transformaciones. Luego, debes asignar memoria para las filas de píxeles que vas a leer. El número de filas que necesitas asignar depende de si la imagen es entrelazada o no, y del número de pasadas que se utilizarán.


png_uint_32 **row_pointers;
row_pointers = (png_uint_32 **)png_malloc(png_ptr, height * sizeof(png_byte*));
for (int i = 0; i < height; i++)
row_pointers[i] = (png_uint_32 *)png_malloc(png_ptr, png_get_rowbytes(png_ptr, info_ptr));

Una vez que todo está configurado, puedes empezar a leer los datos de los píxeles llamando a png_read_rows() o png_read_image(). La función png_read_rows() lee un número especificado de filas de píxeles y las almacena en el búfer proporcionado. La función png_read_image() lee todas las filas de píxeles de la imagen y las almacena en el búfer proporcionado. Ambas funciones devuelven un valor que indica el estado de la lectura, y si es necesario, se puede utilizar un longjmp() para manejar un error.


png_read_rows(png_ptr, row_pointers, num_rows);
png_read_image(png_ptr, row_pointers);

Si la imagen es entrelazada, deberás llamar a png_read_rows() varias veces para leer todas las pasadas. El número de pasadas se determina por el valor devuelto por png_set_interlace_handling(). Cada llamada a png_read_rows() leerá un conjunto de filas para la pasada actual.

Hay dos funciones de retorno de llamada disponibles para la lectura de datos: png_set_read_fn() y png_set_read_status_fn().

La función png_set_read_fn() se utiliza para establecer funciones de lectura personalizadas. Esto es útil si no estás leyendo desde un archivo estándar de C, sino desde otra fuente de datos. La función toma dos argumentos: el puntero png_ptr y un puntero a la función de lectura personalizada. La función de lectura personalizada debe tener la siguiente firma:


void read_data_callback(png_structp png_ptr, png_bytep data, png_size_t length)

Esta función debe leer `length` bytes de datos y colocarlos en el búfer `data`. Si ocurre un error, debe llamar a png_error().

La función png_set_read_status_fn() se utiliza para establecer una función de retorno de llamada que se llamará después de que cada fila se haya leído. Esto es útil para controlar una barra de progreso o similar. La función toma dos argumentos: el puntero png_ptr y un puntero a la función de retorno de llamada de estado de lectura. La función de retorno de llamada de estado de lectura debe tener la siguiente firma:


void read_row_callback(png_structp png_ptr, unsigned int row, int pass)

Cuando esta función es llamada, la fila ya ha sido completamente procesada y leída. Los argumentos `row` y `pass` se refieren a la siguiente fila que se va a manejar. Para el caso no entrelazado, la fila que se acaba de manejar es simplemente `row - 1`, y `pass` siempre será 0. Para el caso entrelazado, lo mismo se aplica a menos que el valor de `row` sea 0, en cuyo caso la fila que se acaba de manejar fue la última de una de las pasadas precedentes. Debido a que el entrelazado puede saltarse una pasada, no puedes estar seguro de que la pasada anterior sea solo `pass - 1`. Si realmente necesitas saber cuál es la última pasada, graba (row, pass) desde la función de retorno de llamada y usa el último valor registrado cada vez.

Puedes usar la macro PNG_ROW_FROM_PASS_ROW para encontrar la fila de salida usando la fila de pasada.

Después de leer todos los datos de los píxeles, debes llamar a png_read_end_info(). Esta función lee y procesa todos los chunks restantes después del último chunk IDAT, hasta e incluyendo el chunk IEND. Después de llamar a esta función, la estructura png_info se actualiza con la información de los chunks finales.


png_read_end_info(png_ptr, info_ptr);

Finalmente, debes liberar la memoria asignada para las estructuras png_ptr y png_info, así como para los búferes de fila. Esto se hace llamando a png_destroy_read_struct().


png_destroy_read_struct(&png_ptr, &info_ptr, NULL);

Se pueden usar dos funciones de retorno de llamada para controlar el proceso de lectura:

start_callback
Esta función se llama antes de comenzar a leer el archivo PNG. Se puede utilizar para inicializar cualquier estructura de datos necesaria.
end_callback
Esta función se llama después de que se haya leído todo el archivo PNG, incluyendo el chunk IEND. Se puede utilizar para realizar cualquier limpieza necesaria.

Para registrar estas funciones de retorno de llamada, utiliza las siguientes funciones:

png_set_read_status_fn(png_ptr, read_status_fn);

  • user_io_ptr es un puntero a datos definidos por el usuario que se pasarán a las funciones de lectura.

  • read_status_fn es la función de retorno de llamada que se llamará después de que se haya leído cada fila.

La verificación de índices de paleta no válidos en la escritura se añadió en libpng 1.5.10. Si un píxel contiene un índice no válido (fuera de rango), libpng emite un error benigno. Esto está habilitado por defecto porque esta condición es un error según la especificación PNG, Cláusula 11.3.2, pero el error puede ser ignorado en cada png_ptr con

Si se ignora el error, o si png_benign_error() lo trata como una advertencia, los píxeles no válidos se escriben tal cual por el codificador, resultando en una transmisión de datos PNG no válida como salida. En este caso, la aplicación es responsable de asegurar que los índices de píxeles estén dentro del rango cuando escriba un chunk PLTE con menos entradas de las que la profundidad de bits permitiría.

png_write_rows(png_ptr, row_pointers,
number_of_rows);

row_pointers es el mismo que en la llamada a png_write_image().

Si solo está escribiendo una fila a la vez, puede hacerlo con un solo row_pointer en lugar de un array de row_pointers:


png_bytep row_pointer = row;


png_write_row(png_ptr, row_pointer);

Cuando el archivo está entrelazado, las cosas pueden complicarse bastante. El único esquema de entrelazado definido actualmente (según la especificación PNG versión 1.2, con fecha de julio de 1999) para archivos PNG es el esquema de entrelazado "Adam7", que divide una imagen en siete imágenes más pequeñas de tamaño variable. libpng construirá estas imágenes para usted, o puede hacerlo usted mismo. Si desea construirlas usted mismo, consulte la especificación PNG para obtener detalles sobre qué píxeles escribir cuándo.

Si no desea que libpng maneje los detalles del entrelazado, simplemente use png_set_interlace_handling() y llame a png_write_rows() el número correcto de veces para escribir todas las subimágenes (png_set_interlace_handling() devuelve el número de subimágenes).

Si desea que libpng construya las subimágenes, llame a esto antes de comenzar a escribir cualquier fila:


number_of_passes = png_set_interlace_handling(png_ptr);

Esto devolverá el número de pasadas necesarias. Actualmente, son siete, pero puede cambiar si se agrega otro tipo de entrelazado.

Luego escriba la imagen completa number_of_passes veces.


png_write_rows(png_ptr, row_pointers, number_of_rows);

Piense detenidamente antes de escribir una imagen entrelazada. Típicamente, el código que lee tales imágenes lee todos los datos de la imagen en memoria, sin comprimir, antes de realizar cualquier procesamiento. Solo el código que puede mostrar una imagen sobre la marcha puede aprovechar el entrelazado, e incluso entonces la imagen debe tener exactamente el tamaño correcto para el dispositivo de salida, porque escalar una imagen requiere píxeles adyacentes y estos no están disponibles hasta que se hayan leído todas las pasadas.

Si escribe una imagen entrelazada, rara vez necesitará manejar el entrelazado usted mismo. Llame a png_set_interlace_handling() y utilice el enfoque descrito anteriormente.

La única vez que es concebible que realmente necesite escribir una imagen entrelazada pasada por pasada es cuando ha leído una pasada por pasada y le ha hecho alguna transformación píxel por píxel, como se describe en el código de lectura anterior. En este caso, use las macros PNG_PASS_ROWS y PNG_PASS_COLS para determinar el tamaño de cada subimagen en su momento y simplemente escriba las filas que obtuvo del código de lectura.

P. Freeing Data

If you allocated data such as a palette that you passed in to libpng with png_set_*, you must not free it until just before the call to png_destroy_write_struct().

The default behavior is only to free data that was allocated internally by libpng. This can be changed, so that libpng will not free the data, or so that it will free data that was allocated by the user with png_malloc() or png_calloc() and passed in via a png_set_*() function, with


png_data_freer(png_ptr, info_ptr, freer, mask)


freer - one of
PNG_DESTROY_WILL_FREE_DATA
PNG_SET_WILL_FREE_DATA
PNG_USER_WILL_FREE_DATA


mask - which data elements are affected
same choices as in png_free_data()

For example, to transfer responsibility for some data from a read structure to a write structure, you could use


png_data_freer(read_ptr, read_info_ptr,
PNG_USER_WILL_FREE_DATA,
PNG_FREE_PLTE|PNG_FREE_tRNS|PNG_FREE_hIST)


png_data_freer(write_ptr, write_info_ptr,
PNG_DESTROY_WILL_FREE_DATA,
PNG_FREE_PLTE|PNG_FREE_tRNS|PNG_FREE_hIST)

thereby briefly reassigning responsibility for freeing to the user but immediately afterwards reassigning it once more to the write_destroy function. Having done this, it would then be safe to destroy the read structure and continue to use the PLTE, tRNS, and hIST data in the write structure.

This function only affects data that has already been allocated. You can call this function before calling after the png_set_*() functions to control whether the user or png_destroy_*() is supposed to free the data. When the user assumes responsibility for libpng-allocated data, the application must use png_free() to free it, and when the user transfers responsibility to libpng for data that the user has allocated, the user must have used png_malloc() or png_calloc() to allocate it.

If you allocated text_ptr.text, text_ptr.lang, and text_ptr.translated_keyword separately, do not transfer responsibility for freeing text_ptr to libpng, because when libpng fills a png_text structure it combines these members with the key member, and png_free_data() will free only text_ptr.key. Similarly, if you transfer responsibility for free'ing text_ptr from libpng to your application, your application must not separately free those members. V. Simplified API

The simplified API, which became available in libpng-1.6.0, hides the details of both libpng and the PNG file format itself. It allows PNG files to be read into a very limited number of in-memory bitmap formats or to be written from the same formats. If these formats do not accommodate your needs then you can, and should, use the more sophisticated APIs above - these support a wide variety of in-memory formats and a wide variety of sophisticated transformations to those formats as well as a wide variety of APIs to manipulate ancillary information.

To read a PNG file using the simplified API:


1) Declare a 'png_image' structure (see below) on the stack, set the
version field to PNG_IMAGE_VERSION and the 'opaque' pointer to NULL
(this is REQUIRED, your program may crash if you don't do it.)


2) Call the appropriate png_image_begin_read... function.


3) Set the png_image 'format' member to the required sample format.


4) Allocate a buffer for the image and, if required, the color-map.


5) Call png_image_finish_read to read the image and, if required, the
color-map into your buffers.

There are no restrictions on the format of the PNG input itself; all valid color types, bit depths, and interlace methods are acceptable, and the input image is transformed as necessary to the requested in-memory format during the png_image_finish_read() step. The only caveat is that if you request a color-mapped image from a PNG that is full-color or makes complex use of an alpha channel the transformation is extremely lossy and the result may look terrible.

To write a PNG file using the simplified API:


1) Declare a 'png_image' structure on the stack and memset()
it to all zero.


2) Initialize the members of the structure that describe the
image, setting the 'format' member to the format of the
image samples.


3) Call the appropriate png_image_write... function with a
pointer to the image and, if necessary, the color-map to write
the PNG data.

png_image is a structure that describes the in-memory format of an image when it is being read or defines the in-memory format of an image that you need to write. The "png_image" structure contains the following members:


png_controlp opaque Initialize to NULL, free with png_image_free
png_uint_32 version Set to PNG_IMAGE_VERSION
png_uint_32 width Image width in pixels (columns)
png_uint_32 height Image height in pixels (rows)
png_uint_32 format Image format as defined below
png_uint_32 flags A bit mask containing informational flags
png_uint_32 colormap_entries; Number of entries in the color-map
png_uint_32 warning_or_error;
char message[64];

In the event of an error or warning the "warning_or_error" field will be set to a non-zero value and the 'message' field will contain a ' ' terminated string with the libpng error or warning message. If both warnings and an error were encountered, only the error is recorded. If there are multiple warnings, only the first one is recorded.

The upper 30 bits of the "warning_or_error" value are reserved; the low two bits contain a two bit code such that a value more than 1 indicates a failure in the API just called:


0 - no warning or error
1 - warning
2 - error
3 - error preceded by warning

The pixels (samples) of the image have one to four channels whose components have original values in the range 0 to 1.0:


1: A single gray or luminance channel (G).
2: A gray/luminance channel and an alpha channel (GA).
3: Three red, green, blue color channels (RGB).
4: Three color channels and an alpha channel (RGBA).

The channels are encoded in one of two ways:


a) As a small integer, value 0..255, contained in a single byte. For the alpha channel the original value is simply value/255. For the color or luminance channels the value is encoded according to the sRGB specification and matches the 8-bit format expected by typical display devices.

The color/gray channels are not scaled (pre-multiplied) by the alpha channel and are suitable for passing to color management software.


b) As a value in the range 0..65535, contained in a 2-byte integer, in the native byte order of the platform on which the application is running. All channels can be converted to the original value by dividing by 65535; all channels are linear. Color channels use the RGB encoding (RGB end-points) of the sRGB specification. This encoding is identified by the PNG_FORMAT_FLAG_LINEAR flag below.

When the simplified API needs to convert between sRGB and linear colorspaces, the actual sRGB transfer curve defined in the sRGB specification (see the article at https://en.wikipedia.org/wiki/SRGB) is used, not the gamma=1/2.2 approximation used elsewhere in libpng.

When an alpha channel is present it is expected to denote pixel coverage of the color or luminance channels and is returned as an associated alpha channel: the color/gray channels are scaled (pre-multiplied) by the alpha value.

The samples are either contained directly in the image data, between 1 and 8 bytes per pixel according to the encoding, or are held in a color-map indexed by bytes in the image data. In the case of a color-map the color-map entries are individual samples, encoded as above, and the image data has one byte per pixel to select the relevant sample from the color-map.

VII. MNG support

The MNG specification (available at http://www.libpng.org/pub/mng) allows certain extensions to PNG for PNG images that are embedded in MNG datastreams. Libpng can support some of these extensions. To enable them, use the png_permit_mng_features() function: feature_set = png_permit_mng_features(png_ptr, mask) mask is a png_uint_32 containing the bitwise OR of the features you want to enable. These include PNG_FLAG_MNG_EMPTY_PLTE PNG_FLAG_MNG_FILTER_64 PNG_ALL_MNG_FEATURES feature_set is a png_uint_32 that is the bitwise AND of your mask with the set of MNG features that is supported by the version of libpng that you are using. It is an error to use this function when reading or writing a standalone PNG file with the PNG 8-byte signature. The PNG datastream must be wrapped in a MNG datastream. As a minimum, it must have the MNG 8-byte signature and the MHDR and MEND chunks. Libpng does not provide support for these or any other MNG chunks; your application must provide its own support for them. You may wish to consider using libmng (available at https://www.libmng.com/) instead.

VIII. Changes to Libpng from version 0.88

It should be noted that versions of libpng later than 0.96 are not distributed by the original libpng author, Guy Schalnat, nor by Andreas Dilger, who had taken over from Guy during 1996 and 1997, and distributed versions 0.89 through 0.96, but rather by another member of the original PNG Group, Glenn Randers-Pehrson. Guy and Andreas are still alive and well, but they have moved on to other things. The old libpng functions png_read_init(), png_write_init(), png_info_init(), png_read_destroy(), and png_write_destroy() have been moved to PNG_INTERNAL in version 0.95 to discourage their use. These functions will be removed from libpng version 1.4.0. The preferred method of creating and initializing the libpng structures is via the png_create_read_struct(), png_create_write_struct(), and png_create_info_struct() because they isolate the size of the structures from the application, allow version error checking, and also allow the use of custom error handling routines during the initialization, which the old functions do not. The functions png_read_destroy() and png_write_destroy() do not actually free the memory that libpng allocated for these structs, but just reset the data structures, so they can be used instead of png_destroy_read_struct() and png_destroy_write_struct() if you feel there is too much system overhead allocating and freeing the png_struct for each image read. Setting the error callbacks via png_set_message_fn() before png_read_init() as was suggested in libpng-0.88 is no longer supported because this caused applications that do not use custom error functions to fail if the png_ptr was not initialized to zero. It is still possible to set the error callbacks AFTER png_read_init(), or to change them with png_set_error_fn(), which is essentially the same function, but with a new name to force compilation errors with applications that try to use the old method. Support for the sCAL, iCCP, iTXt, and sPLT chunks was added at libpng-1.0.6; however, iTXt support was not enabled by default. Starting with version 1.0.7, you can find out which version of the library you are using at run-time: png_uint_32 libpng_vn = png_access_version_number(); The number libpng_vn is constructed from the major version, minor version with leading zero, and release number with leading zero, (e.g., libpng_vn for version 1.0.7 is 10007). Note that this function does not take a png_ptr, so you can call it before you've created one. You can also check which version of png.h you used when compiling your application: png_uint_32 application_vn = PNG_LIBPNG_VER;

No hay cambios sustanciales en la API entre las partes no obsoletas de la API 1.4.5 y la API 1.5.0; sin embargo, la capacidad de acceder directamente a los miembros de las estructuras de control principales de libpng, png_struct y png_info, obsoleta en versiones anteriores de libpng, se ha eliminado por completo de libpng 1.5, y se crearon nuevos archivos de cabecera privados "pngstruct.h", "pnginfo.h" y "pngdebug.h".

Ya no incluimos zlib.h en png.h. La directiva de inclusión se ha movido a pngstruct.h, donde no es accesible por las aplicaciones. Las aplicaciones que necesiten acceso a información en zlib.h necesitarán añadir la directiva '#include "zlib.h"'. No importa si esto se coloca antes o después de la directiva '#include png.h'.

Las macros png_sprintf(), png_strcpy() y png_strncpy() ya no se usan y se eliminaron.

Movimos el png_strle

macros: png_malloc(), png_free(), png_memcpy(), png_memset(), y png_memcmp() a un archivo de encabezado privado (pngpriv.h) que no es accesible para las aplicaciones.

En png_get_iCCP, el tipo de "profile" se cambió de png_charpp a png_bytepp, y en png_set_iCCP, de png_charp a png_const_bytep.

Hay cambios de forma en png.h, incluyendo macros nuevas y cambiadas para declarar partes de la API. Algunas funciones de la API con argumentos que son punteros a datos que no se modifican dentro de la función han sido corregidas para declarar estos argumentos con const.

Gran parte del uso interno de macros de C para controlar la compilación de la biblioteca también ha cambiado y parte de esto es visible en los archivos de encabezado exportados, en particular, el uso de macros para controlar los datos y los elementos de la API visibles durante la compilación de la aplicación puede requerir una revisión significativa del código de la aplicación. (Es extremadamente raro que una aplicación haga esto).

Cualquier programa que se compiló contra libpng 1.4 y no utilizó características obsoletas o accedió a estructuras internas de la biblioteca debería compilarse y funcionar contra libpng 1.5, excepto por el cambio en el prototipo de las funciones de la API png_get_iCCP() y png_set_iCCP() mencionado anteriormente.

libpng 1.5.0 agrega macros PNG_ PASS para ayudar en la lectura y escritura de imágenes entrelazadas. Las macros devuelven el número de filas y columnas en cada pasada e información que se puede usar para desentrelazar y (si es absolutamente necesario) entrelazar una imagen.

libpng 1.5.0 agrega una API png_longjmp(png_ptr, valor). Esta API llama a png_longjmp_ptr proporcionado por la aplicación en el búfer de longjmp interno, pero inicializado por la aplicación. Se proporciona como una conveniencia para evitar la necesidad de usar la macro png_jmpbuf, que tenía el efecto secundario innecesario de restablecer el valor de png_longjmp_ptr interno.

libpng 1.5.0 incluye una API completa de punto fijo. Por defecto, está presente junto con la API de punto flotante correspondiente. En general, la API de punto fijo es más rápida y pequeña que la de punto flotante porque el formato de archivo PNG utilizaba punto fijo, no punto flotante. Esto se aplica incluso si la biblioteca utiliza punto flotante en cálculos internos. Una nueva macro, PNG_FLOATING_ARITHMETIC_SUPPORTED, revela si la biblioteca utiliza aritmética de punto flotante (por defecto) o aritmética de punto fijo internamente para cálculos críticos de rendimiento como la corrección gamma. En algunos casos, los cálculos gamma pueden producir resultados ligeramente diferentes. Esto ha cambiado los resultados en png_rgb_to_gray y en la composición alfa (png_set_background, por ejemplo). Esto se aplica incluso si la imagen original ya era lineal (gamma == 1.0) y, por lo tanto, no es necesario linealizar la imagen. Esto se debe a que libpng *no* ha sido modificada para optimizar ese caso correctamente, todavía.

El soporte de punto fijo para el chunk sCAL viene con una advertencia importante; la especificación sCAL utiliza una codificación decimal de valores de punto flotante y la precisión de los valores de punto fijo de PNG es insuficiente para la representación de estos valores. En consecuencia, una API de "cadena" (png_get_sCAL_s y png_set_sCAL_s) es la única forma confiable de leer chunks sCAL arbitrarios en ausencia de la API de punto flotante o de cálculos internos de punto flotante. A partir de libpng-1.5.0, ambas funciones están presentes cuando se define PNG_sCAL_SUPPORTED. Antes de libpng-1.5.0, su presencia también dependía de que PNG_FIXED_POINT_SUPPORTED estuviera definido y PNG_FLOATING_POINT_SUPPORTED no estuviera definido.

Las aplicaciones ya no necesitan incluir el archivo de encabezado de distribución opcional pngusr.h ni definir las macros correspondientes durante la compilación de la aplicación para ver la variante correcta de la API de libpng. A partir de 1.5.0, el código de la aplicación puede verificar la macro _SUPPORTED correspondiente:

#ifdef PNG_INCH_CONVERSIONS_SUPPORTED
/* código que utiliza las API de conversión de pulgadas. */ #endif

Esta macro solo se definirá si las funciones de conversión de pulgadas se han compilado en libpng. El conjunto completo de macros, y si el soporte se ha compilado o no, están disponibles en el archivo de encabezado pnglibconf.h. Este archivo de encabezado es específico de la compilación de libpng. Tenga en cuenta que antes de 1.5.0, las macros _SUPPORTED siempre tendrían la definición predeterminada a menos que se restablecieran mediante pngusr.h o mediante configuraciones explícitas en la línea de comandos del compilador. Estas configuraciones pueden producir advertencias o errores del compilador en 1.5.0 debido a la redefinición de macros.

Las aplicaciones ahora pueden elegir si usan estas macros o llaman a la función correspondiente definiendo PNG_USE_READ_MACROS o PNG_NO_USE_READ_MACROS antes de incluir png.h. Tenga en cuenta que esto solo se admite a partir de 1.5.0; definir PNG_NO_USE_READ_MACROS antes de 1.5.0 provocará un error de enlace.

Antes de libpng-1.5.4, el compresor zlib utilizaba el mismo conjunto de parámetros al comprimir los datos IDAT y los datos textuales como zTXt e iCCP. En libpng-1.5.4, reinicializamos el flujo zlib para cada tipo de datos. Agregamos cinco funciones png_set_text_*() para establecer los parámetros a utilizar con datos textuales.

Antes de libpng-1.5.4, la opción PNG_READ_16_TO_8_ACCURATE_SCALE_SUPPORTED estaba desactivada por defecto, y ocurría un escalado ligeramente impreciso. Esta opción ya no se puede desactivar, y la elección de escalado de 16 a 8 preciso o impreciso se realiza utilizando la nueva API png_set_scale_16_to_8() para escalado preciso o la antigua API png_set_strip_16_to_8() para un simple recorte. En libpng-1.5.4, la macro PNG_READ_16_TO_8_ACCURATE_SCALE_SUPPORTED se convirtió en PNG_READ_SCALE_16_TO_8_SUPPORTED, y la macro PNG_READ_16_TO_8 se convirtió en PNG_READ_STRIP_16_TO_8_SUPPORTED, para habilitar las dos funciones png_set_*_16_to_8() por separado.

Antes de libpng-1.5.4, la función png_set_user_limits() solo se podía usar para reducir los límites de ancho y alto del valor de PNG_USER_WIDTH_MAX y PNG_USER_HEIGHT_MAX, aunque este documento decía que se podía usar para anularlos. Ahora esta función reducirá o aumentará los límites.

A partir de libpng-1.5.22, se establecieron límites de usuario predeterminados. Estos pueden ser anulados por llamadas de aplicación a png_set_user_limits(), png_set_user_chunk_cache_max() y/o png_set_user_malloc_max(). Los límites son ahora
máximo posible por defecto
png_user_width_max 0x7fffffff 1.000.000
png_user_height_max 0x7fffffff 1.000.000
png_user_chunk_cache_max 0 (ilimitado) 1000
png_user_chunk_malloc_max 0 (ilimitado) 8.000.000

La función png_set_option() (y el miembro "options" de la estructura png) se agregó a libpng-1.5.15, con la opción PNG_ARM_NEON.

La biblioteca ahora admite una implementación completa de punto fijo y, por lo tanto, se puede utilizar en sistemas que no tienen soporte de punto flotante o un soporte muy limitado o lento. Anteriormente, la corrección gamma, una parte esencial del soporte completo de PNG, requería punto flotante razonablemente rápido.

Como parte de esto, la elección de la implementación interna se ha independizado de la elección de las API de punto fijo frente a punto flotante y se han implementado todas las API de punto fijo faltantes.

El mecanismo exacto utilizado para controlar los atributos de las funciones de la API ha cambiado, como se describe en el archivo INSTALL.

Se proporciona un nuevo programa de prueba, pngvalid, además de pngtest. pngvalid valida la precisión aritmética de los cálculos de corrección gamma e incluye una serie de validaciones del formato de archivo. Un subconjunto del rango completo de pruebas se ejecuta cuando se realiza "make check" (en la compilación 'configure'). pngvalid también permite evaluar el uso total de memoria asignada y realiza validaciones adicionales de sobrescritura de memoria.

Se han realizado muchos cambios en las macros de características individuales. Los siguientes son los cambios que es más probable que noten los constructores de bibliotecas que configuran libpng:

1) Todas las macros de características ahora tienen nombres consistentes:

#define PNG_NO_feature desactiva la característica #define PNG_feature_SUPPORTED activa la característica

pnglibconf.h contiene una línea para cada macro de característica que es:

#define PNG_feature_SUPPORTED

si la característica es compatible o:

/*#undef PNG_feature_SUPPORTED*/

si no lo es. El código de la biblioteca verifica consistentemente la macro 'SUPPORTED'. No lo hace, y las aplicaciones libpng tampoco deberían hacerlo, verificar la macro 'NO', que normalmente no se definirá incluso si la característica no es compatible. Las macros 'NO' solo se utilizan internamente para establecer o no establecer las macros 'SUPPORTED' correspondientes.

La compatibilidad con los nombres antiguos se proporciona de la siguiente manera:

PNG_INCH_CONVERSIONS activa PNG_INCH_CONVERSIONS_SUPPORTED

Y las siguientes definiciones desactivan la característica correspondiente:

PNG_SETJMP_NOT_SUPPORTED desactiva SETJMP PNG_READ_TRANSFORMS_NOT_SUPPORTED desactiva READ_TRANSFORMS PNG_NO_READ_COMPOSITED_NODIV desactiva READ_COMPOSITE_NODIV PNG_WRITE_TRANSFORMS_NOT_SUPPORTED desactiva WRITE_TRANSFORMS PNG_READ_ANCILLARY_CHUNKS_NOT_SUPPORTED desactiva READ_ANCILLARY_CHUNKS PNG_WRITE_ANCILLARY_CHUNKS_NOT_SUPPORTED desactiva WRITE_ANCILLARY_CHUNKS

Los constructores de bibliotecas deben dejar de usar los nombres inconsistentes anteriores.

2) El formato de los mensajes de advertencia y error dependía previamente de la característica STDIO. La biblioteca se ha modificado para utilizar la característica CONSOLE_IO en su lugar. Esto significa que si CONSOLE_IO está deshabilitado, la biblioteca ya no utiliza las funciones printf(3), aunque las implementaciones de lectura/escritura predeterminadas utilizan funciones stdio.h de estilo (FILE).

3) Tres macros de características controlan ahora las decisiones de punto fijo/punto flotante:

PNG_FLOATING_POINT_SUPPORTED habilita las API de punto flotante

PNG_FIXED_POINT_SUPPORTED habilita las API de punto fijo; sin embargo, en la práctica, estas suelen ser necesarias internamente de todos modos (porque el formato de archivo PNG es de punto fijo), por lo tanto, en la mayoría de los casos, PNG_NO_FIXED_POINT simplemente evita que la función se exporte.

PNG_FLOATING_ARITHMETIC_SUPPORTED elige entre la implementación interna de punto flotante o la de punto fijo. Típicamente, la implementación de punto fijo es más grande y más lenta que la implementación de punto flotante en un sistema que admite punto flotante; sin embargo, puede ser más rápida en un sistema que carece de hardware de punto flotante y, por lo tanto, utiliza una emulación por software.

4) Se agregó PNG_{READ,WRITE}_INT_FUNCTIONS_SUPPORTED. Esto permite deshabilitar las funciones para leer y escribir enteros de forma independiente de PNG_USE_READ_MACROS, lo que permite compilar libpng con las funciones, aunque la opción predeterminada es usar las macros; esto permite a las aplicaciones elegir en el momento de la compilación de la aplicación si usar o no macros (anteriormente imposible porque las funciones no estaban en la compilación predeterminada).

Se ha agregado una "API simplificada" (consulte la documentación en png.h y un ejemplo simple en contrib/examples/pngtopng.c). La nueva API públicamente visible incluye lo siguiente:

Starting with libpng-1.6.0, you can configure libpng to prefix all exported symbols, using the PNG_PREFIX macro.

We no longer include string.h in png.h. The include statement has been moved to pngpriv.h, where it is not accessible by applications. Applications that need access to information in string.h must add an '#include <string.h>' directive. It does not matter whether this is placed prior to or after the '#include "png.h"' directive.

png_malloc_default()

with png_get_io_chunk_type(). The new
function returns a 32-bit integer instead of
a string.
The png_sizeof(), png_strlen(), png_memcpy(), png_memcmp(), and
png_memset() macros are no longer used in the libpng sources and
have been removed. These had already been made invisible to applications
(i.e., defined in the private pngpriv.h header file) since libpng-1.5.0.

The signatures of many exported functions were changed, such that
png_structp became png_structrp or png_const_structrp
png_infop became png_inforp or png_const_inforp where "rp" indicates a "restricted pointer".

Dropped support for 16-bit platforms. The support for FAR/far types has been eliminated and the definition of png_alloc_size_t is now controlled by a flag so that 'small size_t' systems can select it if necessary.

Error detection in some chunks has improved; in particular the iCCP chunk reader now does pretty complete validation of the basic format. Some bad profiles that were previously accepted are now accepted with a warning or rejected, depending upon the png_set_benign_errors() setting, in particular the very old broken Microsoft/HP 3144-byte sRGB profile. Starting with libpng-1.6.11, recognizing and checking sRGB profiles can be avoided by means of


#if defined(PNG_SKIP_sRGB_CHECK_PROFILE) && defined(PNG_SET_OPTION_SUPPORTED)
png_set_option(png_ptr, PNG_SKIP_sRGB_CHECK_PROFILE,
PNG_OPTION_ON);
#endif

It's not a good idea to do this if you are using the "simplified API", which needs to be able to recognize sRGB profiles conveyed via the iCCP chunk.

The PNG spec requirement that only grayscale profiles may appear in images with color type 0 or 4 and that even if the image only contains gray pixels, only RGB profiles may appear in images with color type 2, 3, or 6, is now enforced. The sRGB chunk is allowed to appear in images with any color type and is interpreted by libpng to convey a one-tracer-curve gray profile or a three-tracer-curve RGB profile as appropriate.

Libpng 1.5.x erroneously used /MD for Debug DLL builds; if you used the debug builds in your app and you changed your app to use /MD you will need to change it back to /MDd for libpng 1.6.x.

Prior to libpng-1.6.0 a warning would be issued if the iTXt chunk contained an empty language field or an empty translated keyword. Both of these are allowed by the PNG specification, so these warnings are no longer issued.

The library now issues an error if the application attempts to set a transform after it calls png_read_update_info() or if it attempts to call both png_read_update_info() and png_start_read_image() or to call either of them more than once.

The default condition for benign_errors is now to treat benign errors as warnings while reading and as errors while writing.

The library now issues a warning if both background processing and RGB to gray are used when gamma correction happens. As with previous versions of the library the results are numerically very incorrect in this case.

There are some minor arithmetic changes in some transforms such as png_set_background(), that might be detected by certain regression tests.

Unknown chunk handling has been improved internally, without any API change. This adds more correct option control of the unknown handling, corrects a pre-existing bug where the per-chunk 'keep' setting is ignored, and makes it possible to skip IDAT chunks in the sequential reader.

The machine-generated configure files are no longer included in branches libpng17 and later of the GIT repository. They continue to be included in the tarball releases, however.

Libpng-1.6.0 through 1.6.2 used the CMF bytes at the beginning of the IDAT stream to set the size of the sliding window for reading instead of using the default 32-kbyte sliding window size. It was discovered that there are hundreds of PNG files in the wild that have incorrect CMF bytes that caused zlib to issue the "invalid distance too far back" error and reject the file. Libpng-1.6.3 and later calculate their own safe CMF from the image dimensions, provide a way to revert to the libpng-1.5.x behavior (ignoring the CMF bytes and using a 32-kbyte sliding window), by using


png_set_option(png_ptr, PNG_MAXIMUM_INFLATE_WINDOW,
PNG_OPTION_ON);

and provide a tool (contrib/tools/pngfix) for rewriting a PNG file while optimizing the CMF bytes in its IDAT chunk correctly.

Libpng-1.6.0 and libpng-1.6.1 wrote uncompressed iTXt chunks with the wrong length, which resulted in PNG files that cannot be read beyond the bad iTXt chunk. This error was fixed in libpng-1.6.3, and a tool (called contrib/tools/png-fix-itxt) has been added to the libpng distribution.

Starting with libpng-1.6.17, the PNG_SAFE_LIMITS macro was eliminated and safe limits are used by default (users who need larger limits can still override them at compile time or run time, as described above).

default spec limit

png_user_height_max 1,000,000 2,147,483,647
png_user_chunk_cache_max 128 unlimited

Starting with libpng-1.6.18, a PNG_RELEASE_BUILD macro was added, which allows library builders to control compilation for an installed system (a release build). It can be set for testing debug or beta builds to ensure that they will compile when the build type is switched to RC or STABLE. In essence this overrides the PNG_LIBPNG_BUILD_BASE_TYPE definition which is not directly user controllable.

Starting with libpng-1.6.19, attempting to set an over-length PLTE chunk is an error. Previously this requirement of the PNG specification was not enforced, and the palette was always limited to 256 entries. An over-length PLTE chunk found in an input PNG is silently truncated.

Starting with libpng-1.6.31, the eXIf chunk is supported. Libpng does not attempt to decode the Exif profile; it simply returns a byte array containing the profile to the calling application which must do its own decoding.

XV. Estilo de codificación

Nuestro estilo de codificación es similar al estilo "Allman" (Ver https://en.wikipedia.org/wiki/Indent_style#Allman_style), con llaves en líneas separadas:


if (condition)
{
action;
}


else if (another condition)
{
another action;
}

Las llaves se pueden omitir de acciones simples de una sola línea:


if (condition)
return 0;

Usamos indentación de 3 espacios, excepto para declaraciones continuadas que generalmente se indentan igual que la primera línea de la declaración más cuatro espacios adicionales.

Para definiciones de macros usamos indentación de 2 espacios, dejando siempre el "#" en la primera columna.


#ifndef PNG_NO_FEATURE
# ifndef PNG_FEATURE_SUPPORTED
# define PNG_FEATURE_SUPPORTED
# endif
#endif

Los comentarios aparecen con el "/*" inicial en la misma indentación que la declaración que sigue al comentario:


/* Comentario de una sola línea */
statement;


/* Este es un comentario
* de múltiples
* líneas
*/
statement;

DESCRIPTION

This document is intended to describe the libpng library and its API, not the PNG file format itself. The PNG format specification should be consulted for details about the format.

The PNG specification is available at http://www.libpng.org/pub/png/spec/1.2/PNG-spec.html.

Libpng is a library of C functions for reading and writing PNG files. It is used by many applications that need to support the PNG file format.

The following is an excerpt from the libpng documentation file, primarily focusing on coding style and versioning.

I. Introduction

Libpng is the official PNG reference library. It is used by many PNG software packages and is considered the reference implementation of the PNG specification.

The library is distributed under the libpng license, which is compatible with the PNG specification license and the zlib license.

II. Structures

The primary structure used by libpng is png_struct, which holds information about the PNG file being read or written. Other important structures include png_info, which holds information about the PNG file's metadata (chunks), and png_color_16, png_color_rgb, etc., which represent color information.

III. Reading

The basic sequence for reading a PNG file is:

  1. Call png_create_read_struct to create a png_struct.
  2. Call png_create_info_struct to create a png_info.
  3. Initialize the input I/O functions using png_set_read_fn.
  4. Call png_read_info to read the PNG header and ancillary chunks.
  5. Process the header information obtained from png_get_IHDR and other png_get_* functions.
  6. Optionally, call png_set_* functions to modify the image data before it is read (e.g., png_set_expand, png_set_strip_16).
  7. Call png_read_image to read the image data.
  8. Call png_read_end to read the end of the file.
  9. Call png_destroy_read_struct to free allocated memory.

IV. Writing

The basic sequence for writing a PNG file is:

  1. Call png_create_write_struct to create a png_struct.
  2. Call png_create_info_struct to create a png_info.
  3. Initialize the output I/O functions using png_set_write_fn.
  4. Set the PNG header information using png_set_IHDR and other png_set_* functions.
  5. Optionally, set ancillary chunks using png_set_* functions (e.g., png_set_text, png_set_pHYs).
  6. Call png_write_info to write the header and ancillary chunks.
  7. Allocate memory for the image rows and fill it with image data.
  8. Call png_write_image to write the image data.
  9. Call png_write_end to write the end of the file.
  10. Call png_destroy_write_struct to free allocated memory.

V. Simplified API

Libpng provides a simplified API for common tasks, including reading and writing entire PNG images with default settings. These functions are typically named png_read_png, png_write_png, etc.

VI. Modifying/Customizing libpng

Libpng can be customized in several ways:

  • Error handling: You can provide custom error handling functions using png_set_error_fn.
  • Memory allocation: You can provide custom memory allocation functions using png_set_malloc_fn and png_set_free_fn (or png_set_user_chunk_malloc_fn and png_set_user_chunk_free_fn for chunks).
  • I/O functions: You can provide custom I/O functions using png_set_read_fn and png_set_write_fn.
  • Transformations: You can define custom transformations to apply to image data during reading or writing using png_set_read_user_transform_fn and png_set_write_user_transform_fn.
  • Unknown chunks: You can control how unknown chunks are handled using png_set_keep_unknown_chunks and png_set_check_for_unknown_chunks.

VII. MNG support

Libpng supports the Multiple-Network Graphics (MNG) format, an extension of PNG. Support for MNG can be enabled or disabled using png_set_allow_mng.

VIII. Changes to Libpng from version 0.88

This section details changes made to libpng prior to version 1.0.0. It is included for historical context.

The following coding style rules are applied to libpng source code:

Comments are placed on the line before the statement to which they pertain:


/* This is a comment.
*/
statement;

Very short comments can be placed after the end of the statement to which they pertain:


statement; /* comment */

We don't use C++ style ("//") comments. We have, however, used them in the past in some now-abandoned MMX assembler code.

Functions and their curly braces are not indented, and exported functions are marked with PNGAPI:


/* This is a public function that is visible to
* application programmers. It does thus-and-so.
*/
void PNGAPI
png_exported_function(png_ptr, png_info, foo)
{
body;
}

The return type and decorations are placed on a separate line ahead of the function name, as illustrated above.

The prototypes for all exported functions appear in png.h, above the comment that says


/* Maintainer: Put new public prototypes here ... */

We mark all non-exported functions with "/* PRIVATE */"":


void /* PRIVATE */
png_non_exported_function(png_ptr, png_info, foo)
{
body;
}

The prototypes for non-exported functions (except for those in pngtest) appear in pngpriv.h above the comment that says


/* Maintainer: Put new private prototypes here ^ */

To avoid polluting the global namespace, the names of all exported functions and variables begin with "png_", and all publicly visible C preprocessor macros begin with "PNG". We request that applications that use libpng *not* begin any of their own symbols with either of these strings.

We put a space after the "sizeof" operator and we omit the optional parentheses around its argument when the argument is an expression, not a type name, and we always enclose the sizeof operator, with its argument, in parentheses:


(sizeof (png_uint_32))
(sizeof array)

Prior to libpng-1.6.0 we used a "png_sizeof()" macro, formatted as though it were a function.

Control keywords if, for, while, and switch are always followed by a space to distinguish them from function calls, which have no trailing space.

We put a space after each comma and after each semicolon in "for" statements, and we put spaces before and after each C binary operator and after "for" or "while", and before "?". We don't put a space between a typecast and the expression being cast, nor do we put one between a function name and the left parenthesis that follows it:


for (i = 2; i > 0; --i)
y[i] = a(x) + (int)b;

We prefer #ifdef and #ifndef to #if defined() and #if !defined() when there is only one macro being tested. We always use parentheses with "defined".

We express integer constants that are used as bit masks in hex format, with an even number of lower-case hex digits, and to make them unsigned (e.g., 0x00U, 0xffU, 0x0100U) and long if they are greater than 0x7fff (e.g., 0xffffUL).

We prefer to use underscores rather than camelCase in names, except for a few type names that we inherit from zlib.h.

We prefer "if (something != 0)" and "if (something == 0)" over "if (something)" and if "(!something)", respectively, and for pointers we prefer "if (some_pointer != NULL)" or "if (some_pointer == NULL)".

We do not use the TAB character for indentation in the C sources.

Lines do not exceed 80 characters.

Other rules can be inferred by inspecting the libpng source.

Transformaciones

Libpng proporciona varias transformaciones para manipular los datos de la imagen, incluyendo:
  • png_set_strip_alpha: Elimina el canal alfa.
  • png_set_swap_alpha: Intercambia los canales alfa y de color.
  • png_set_gray_to_rgb: Convierte escala de grises a RGB.
  • png_set_rgb_to_gray: Convierte RGB a escala de grises.
  • png_set_expand: Expande los tipos de imagen a 8 bits por canal.
  • png_set_quantize: Cuantiza la imagen a un número especificado de colores.
  • png_set_gamma: Aplica corrección gamma.
  • png_set_shift: Desplaza los valores de bits.
  • png_set_interlace_handling: Maneja la carga entrelazada.

Manejo de errores

Libpng utiliza un sistema de manejo de errores basado en conjuntos de errores. Las funciones de creación de estructuras devuelven punteros nulos en caso de error, y las funciones posteriores establecen códigos de error en la estructura `png_structp`. Se pueden registrar funciones de manejo de errores personalizadas utilizando `png_set_error_fn`.

Funciones de E/S

Libpng permite el uso de funciones de E/S personalizadas para leer y escribir datos de archivos. Esto se hace mediante las funciones `png_set_read_fn` y `png_set_write_fn`, que toman punteros a funciones definidas por el usuario.

Cambios

Cambios en Libpng de la versión 1.2.x a la 1.4.x

  • Se mejoró el soporte para la compresión zlib.
  • Se corrigieron varios errores de seguridad.
  • Se añadieron nuevas funciones para el manejo de metadatos.

Cambios en Libpng de la versión 1.4.x a la 1.5.x

  • Se introdujo un nuevo sistema de manejo de errores.
  • Se mejoró el rendimiento en la lectura y escritura de archivos.
  • Se añadieron funciones para la creación y manipulación de chunks de metadatos.

Cambios en Libpng de la versión 1.5.x a la 1.6.x

  • Se eliminó el soporte para versiones antiguas de PNG (beta).
  • Se mejoró la seguridad contra ataques de denegación de servicio.
  • Se añadieron funciones para el manejo de la inversión de bytes.

Detección de libpng

Para detectar la versión de libpng en tiempo de compilación, se pueden usar las macros `PNG_LIBPNG_VER_MAJOR`, `PNG_LIBPNG_VER_MINOR` y `PNG_LIBPNG_VER_RELEASE`.
