lit(1)

LIT(1) LLVM LIT(1)

NOMBRE

lit - Probador Integrado de LLVM

SINOPSIS

lit [opciones] [pruebas]

DESCRIPCIÓN

lit es una herramienta portátil para ejecutar conjuntos de pruebas al estilo LLVM y Clang, resumiendo sus resultados e indicando fallos. lit está diseñado para ser una herramienta de pruebas ligera con una interfaz de usuario lo más simple posible.

lit debe ejecutarse con una o más pruebas para ejecutar especificadas en la línea de comandos. Las pruebas pueden ser archivos de prueba individuales o directorios donde buscar pruebas (ver DESCUBRIMIENTO DE PRUEBAS).

Cada prueba especificada se ejecutará (potencialmente en paralelo) y una vez que todas las pruebas se hayan ejecutado, lit imprimirá información resumida sobre el número de pruebas que pasaron o fallaron (ver RESULTADOS DEL ESTADO DE LAS PRUEBAS). El programa lit se ejecutará con un código de salida no cero si alguna prueba falla.

Por defecto, lit usará una visualización de progreso sucinta y solo imprimirá información resumida para los fallos de las pruebas. Ver OPCIONES DE SALIDA para ver las opciones que controlan la visualización de progreso y la salida de lit.

lit también incluye una serie de opciones para controlar cómo se ejecutan las pruebas (las características específicas pueden depender del formato de prueba particular). Ver OPCIONES DE EJECUCIÓN para más información.

Finalmente, lit también admite opciones adicionales para ejecutar solo un subconjunto de las opciones especificadas en la línea de comandos, ver OPCIONES DE SELECCIÓN para más información.

lit analiza las opciones de la variable de entorno LIT_OPTS después de analizar las opciones de la línea de comandos. LIT_OPTS es principalmente útil para complementar o anular las opciones de la línea de comandos proporcionadas a lit por los objetivos check definidos por el sistema de compilación de un proyecto.

lit también puede leer opciones de archivos de respuesta que se especifican como entradas utilizando la sintaxis @ruta/al/archivo.rsp. Los argumentos leídos de un archivo deben ser uno por línea y se tratan como si estuvieran en el mismo lugar que el argumento de referencia del archivo original en la línea de comandos. Un archivo de respuesta puede hacer referencia a otros archivos de respuesta.

Los usuarios interesados en la arquitectura de lit o en el diseño de una implementación de pruebas de lit deben consultar INFRAESTRUCTURA DE LIT.

OPCIONES GENERALES

-h, --help
Muestra el mensaje de ayuda de lit y sale.
--version
Muestra el número de versión de lit y sale.
-j N, --workers N
Ejecuta N pruebas en paralelo. Por defecto, esto se elige automáticamente para coincidir con el número de CPUs disponibles detectados.
--config-prefix NOMBRE
Busca NOMBRE.cfg y NOMBRE.site.cfg al buscar conjuntos de pruebas, en lugar de lit.cfg y lit.site.cfg.
-D NOMBRE[=VALOR], --param NOMBRE[=VALOR]
Agrega un parámetro definido por el usuario NOMBRE con el VALOR dado (o la cadena vacía si no se proporciona). El significado y uso de estos parámetros dependen del conjunto de pruebas.

OPCIONES DE SALIDA

-q, --quiet
Suprime cualquier salida excepto los fallos de las pruebas.
-s, --succinct
Muestra menos salida, por ejemplo, no muestra información sobre las pruebas que pasan. También muestra una barra de progreso, a menos que se especifique --no-progress-bar.
-v, --verbose
Muestra más información sobre los fallos de las pruebas, por ejemplo, la salida completa de la prueba en lugar de solo el resultado de la prueba.

Cada comando se imprime antes de ejecutarse. Esto puede ser valioso para depurar fallos de pruebas, ya que el último comando impreso es el que falló. Además, lit inserta 'RUN: en la línea N' después de cada canal de comandos en la salida para ayudarle a localizar la línea de origen del comando fallido.

-vv, --echo-all-commands
Alias obsoleto para -v.
-a, --show-all
Habilita -v, pero para todas las pruebas, no solo las fallidas.
-o RUTA, --output RUTA
Escribe los resultados de las pruebas en la ruta proporcionada.
--no-progress-bar
No usar la barra de progreso basada en curses.
--show-excluded
Mostrar pruebas excluidas.
--show-skipped
Mostrar pruebas omitidas.
--show-unsupported
Mostrar pruebas no soportadas.
--show-pass
Mostrar pruebas pasadas.
--show-flakypass
Mostrar pruebas pasadas con reintento.
--show-xfail
Mostrar pruebas esperadas de fallar.

OPCIONES DE EJECUCIÓN

--gtest-sharding
Habilitar fragmentación para el formato GoogleTest.
--no-gtest-sharding
Deshabilitar fragmentación para el formato GoogleTest.
--path RUTA
Especificar una RUTA adicional a usar al buscar ejecutables en las pruebas.
--vg
Ejecutar pruebas individuales bajo valgrind (usando la herramienta memcheck). El argumento --error-exitcode para valgrind se usa para que los fallos de valgrind hagan que el programa salga con un estado no cero.

Cuando esta opción está habilitada, lit también proporcionará automáticamente una característica de "valgrind" que se puede usar para deshabilitar condicionalmente (o esperar un fallo en) ciertas pruebas.

--vg-leak
Cuando se usa --vg, habilita las verificaciones de fugas de memoria. Cuando esta opción está habilitada, lit también proporcionará automáticamente una característica de "vg_leak" que se puede usar para deshabilitar condicionalmente (o esperar un fallo en) ciertas pruebas.
--vg-arg ARG
Cuando se usa --vg, especifica un argumento adicional para pasar a valgrind mismo.
--no-execute
No ejecutar ninguna prueba (asumir que pasan).
--xunit-xml-output XUNIT_XML_OUTPUT
Escribe informes de pruebas XML compatibles con XUnit en el archivo especificado.
--report-failures-only
Incluir solo fallos (ver RESULTADOS DEL ESTADO DE LAS PRUEBAS) en el informe.
--valgrind
Alias obsoleto para --vg.
--no-valgrind
Alias obsoleto para --no-vg.
--valgrind-leak
Alias obsoleto para --vg-leak.

OPCIONES DE SELECCIÓN

-i, --include PATTERN
Solo ejecutar pruebas que coincidan con el patrón dado. El patrón es una expresión regular que se aplica al nombre de la prueba (la ruta relativa al directorio raíz de la prueba).
-e, --exclude PATTERN
Excluir pruebas que coincidan con el patrón dado.
-a, --exclude-directory PATTERN
Excluir directorios que coincidan con el patrón dado.
--match-all
Indicar que el patrón dado en el argumento de línea de comandos debe coincidir con el nombre del archivo de prueba.

DESCUBRIMIENTO DE PRUEBAS

Los argumentos de prueba de la línea de comandos se interpretan de la siguiente manera:

Archivos
Un argumento de prueba que termina en .py se trata como un módulo de prueba Python y se ejecuta directamente.
Directorios
Cualquier otro argumento de prueba se trata como un directorio en el que buscar pruebas. lit buscará recursivamente en el directorio un archivo llamado lit.cfg. Si se encuentra uno, el directorio se considera la raíz de un conjunto de pruebas. Si se encuentra un archivo lit.site.cfg, se utilizará en lugar de lit.cfg y se considerará que tiene prioridad sobre las opciones de configuración establecidas en el archivo lit.cfg.

Para obtener más información sobre la creación de archivos de configuración, consulte LIT INFRASTRUCTURE.

RESULTADOS DEL ESTADO DE LAS PRUEBAS

Los siguientes códigos de estado se utilizan para indicar el resultado de una prueba:

PASSED
La prueba se ejecutó correctamente y los resultados esperados se cumplieron.
FAILED
La prueba produjo una salida inesperada o falló al ejecutarse.
XPASS
La prueba falló cuando se esperaba que fallara, pero en realidad pasó. Esto indica un cambio en el comportamiento de la prueba o del sistema subyacente.
XFAIL
La prueba falló como se esperaba. Esto es útil para documentar fallos conocidos que aún no se han corregido.
UNSUPPORTED
La prueba no se puede ejecutar en el sistema actual debido a requisitos faltantes o incompatibilidades.
UNRESOLVED
No se pudo determinar el estado de la prueba. Esto generalmente indica un problema con la configuración de la prueba o la ejecución de lit.
UNAVAILABLE
La prueba no está disponible (por ejemplo, falta un archivo de entrada). Esta es una categoría diferente a UNSUPPORTED.
UNEXPECTED_EXIT_CODE
La prueba salió con un código de salida inesperado. Esto es útil para detectar regresiones en el manejo de errores.

INFRAESTRUCTURA DE LIT

lit está diseñado para ser una infraestructura de pruebas extensible. Los archivos de configuración (.cfg) son scripts de Python que definen cómo se deben ejecutar las pruebas y qué herramientas están disponibles. Para obtener más detalles sobre el diseño de la infraestructura de lit, consulte el repositorio de código fuente de LLVM.

  • Opción del conjunto de pruebas config.test_retry_attempts

No rastrear el tiempo transcurrido para cada prueba.

OPCIONES DE SELECCIÓN

Por defecto, lit ejecutará primero las pruebas fallidas, luego ejecutará las pruebas en orden descendente de tiempo de ejecución para optimizar la concurrencia. El orden de ejecución se puede cambiar usando la opción --order.

Los datos de tiempo se almacenan en test_exec_root en un archivo llamado .lit_test_times.txt. Si este archivo no existe, entonces lit busca en test_source_root el archivo para acelerar opcionalmente las compilaciones limpias.

--max-tests N
Ejecuta como máximo N pruebas y luego termina.
--max-time N
Dedica como máximo N segundos (aproximadamente) a la ejecución de pruebas y luego termina. Ten en cuenta que esto no es un alias de --timeout; son dos tipos diferentes de máximos.
--order {lexical,random,smart}
Define el orden en que se ejecutan las pruebas. Los valores admitidos son:
  • lexical - las pruebas se ejecutarán en orden léxico según la ruta del archivo de prueba. Esta opción es útil cuando se desea un orden de prueba predecible.
  • random - las pruebas se ejecutarán en orden aleatorio.
  • smart - las pruebas que fallaron previamente se ejecutarán primero, luego las pruebas restantes, todas en orden descendente de tiempo de ejecución. Este es el valor predeterminado ya que optimiza la concurrencia.
--shuffle
Ejecuta las pruebas en orden aleatorio, no falladas/más lentas primero. Obsoleto, usa --order en su lugar.
-i, --incremental
Ejecuta primero las pruebas fallidas (OBSOLETO: usa --order=smart).
--filter REGEXP
Ejecuta solo aquellas pruebas cuyo nombre coincida con la expresión regular especificada en REGEXP. La variable de entorno LIT_FILTER también se puede usar en lugar de esta opción, lo cual es especialmente útil en entornos donde la llamada a lit se emite indirectamente.
--filter-out REGEXP
Filtra aquellas pruebas cuyo nombre coincida con la expresión regular especificada en REGEXP. La variable de entorno LIT_FILTER_OUT también se puede usar en lugar de esta opción, lo cual es especialmente útil en entornos donde la llamada a lit se emite indirectamente.
--xfail LIST
Trata aquellas pruebas cuyo nombre está en la lista separada por punto y coma LIST como XFAIL. Esto puede ser útil cuando uno no quiere modificar el conjunto de pruebas. La variable de entorno LIT_XFAIL también se puede usar en lugar de esta opción, lo cual es especialmente útil en entornos donde la llamada a lit se emite indirectamente.

Se puede especificar un nombre de prueba como un nombre de archivo relativo al directorio del conjunto de pruebas. Por ejemplo:

LIT_XFAIL="affinity/kmp-hw-subset.c;offloading/memory_manager.cpp"

En este caso, todas las siguientes pruebas se tratan como XFAIL:

libomp :: affinity/kmp-hw-subset.c
libomptarget :: nvptx64-nvidia-cuda :: offloading/memory_manager.cpp
libomptarget :: x86_64-pc-linux-gnu :: offloading/memory_manager.cpp

Alternativamente, se puede especificar un nombre de prueba como el nombre completo de la prueba informado en la salida de LIT. Por ejemplo, podemos ajustar el ejemplo anterior para no tratar la versión nvptx64-nvidia-cuda de offloading/memory_manager.cpp como XFAIL:

LIT_XFAIL="affinity/kmp-hw-subset.c;libomptarget :: x86_64-pc-linux-gnu :: offloading/memory_manager.cpp"
--xfail-not LIST
No trates las pruebas especificadas como XFAIL. La variable de entorno LIT_XFAIL_NOT también se puede usar en lugar de esta opción. La sintaxis es la misma que para --xfail y LIT_XFAIL. --xfail-not y LIT_XFAIL_NOT siempre anulan todas las demás especificaciones de XFAIL, incluida una opción --xfail que aparece más tarde en la línea de comandos. El propósito principal es suprimir un resultado XPASS sin modificar un caso de prueba que utiliza la directiva XFAIL.
--num-shards M
Divide el conjunto de pruebas seleccionadas en M subconjuntos de igual tamaño o "fragmentos", y ejecuta solo uno de ellos. Debe usarse con la opción --run-shard=N, que selecciona el fragmento a ejecutar. La variable de entorno LIT_NUM_SHARDS también se puede usar en lugar de esta opción. Estas dos opciones proporcionan un mecanismo general para particionar grandes conjuntos de pruebas, para la ejecución paralela en máquinas separadas (por ejemplo, en una gran granja de pruebas).
--run-shard N
Selecciona qué fragmento ejecutar, asumiendo que se proporcionó la opción --num-shards=M. Las dos opciones deben usarse juntas, y el valor de N debe estar en el rango 1..M. La variable de entorno LIT_RUN_SHARD también se puede usar en lugar de esta opción.

ESTADO DE SALIDA

lit saldrá con un código de salida de 1 si hay algún fallo (ver RESULTADOS DEL ESTADO DE PRUEBA) y no se ha pasado --ignore-fail. De lo contrario, saldrá con el estado 0. Se utilizan otros códigos de salida para fallos no relacionados con las pruebas (por ejemplo, un error del usuario o un error interno del programa).

DESCUBRIMIENTO DE PRUEBAS

Las entradas pasadas a lit pueden ser pruebas individuales, o directorios completos o jerarquías de pruebas para ejecutar. Cuando lit se inicia, lo primero que hace es convertir las entradas en una lista completa de pruebas para ejecutar como parte del *descubrimiento de pruebas*.

En el modelo lit, cada prueba

debe existir dentro de alguna suite de pruebas. lit resuelve las entradas especificadas en la línea de comandos a suites de pruebas buscando hacia arriba desde la ruta de entrada hasta que encuentra un archivo lit.cfg o lit.site.cfg. Estos archivos sirven tanto como un marcador de suites de pruebas como archivos de configuración que lit carga para entender cómo encontrar y ejecutar las pruebas dentro de la suite de pruebas.

Una vez que lit ha mapeado las entradas a suites de pruebas, recorre la lista de entradas añadiendo pruebas para archivos individuales y buscando recursivamente pruebas en directorios.

Este comportamiento facilita la especificación de un subconjunto de pruebas para ejecutar, al tiempo que permite que la configuración de la suite de pruebas controle exactamente cómo se interpretan las pruebas. Además, lit siempre identifica las pruebas por la suite de pruebas en la que se encuentran y su ruta relativa dentro de la suite de pruebas. Para proyectos configurados adecuadamente, esto permite a lit proporcionar soporte conveniente y flexible para compilaciones fuera del árbol.

ESTADO DE LA PRUEBA RESULTADOS

Cada prueba produce finalmente uno de los siguientes ocho resultados:

PASS

La prueba tuvo éxito.

FLAKYPASS

La prueba tuvo éxito después de volver a ejecutarse más de una vez. Esto solo se aplica a pruebas que contienen una anotación ALLOW_RETRIES:.

XFAIL

La prueba falló, pero se esperaba. Esto se utiliza para formatos de prueba que permiten especificar que una prueba no funciona actualmente, pero se desea dejarla en la suite de pruebas.

XPASS

La prueba tuvo éxito, pero se esperaba que fallara. Esto se utiliza para pruebas que se especificaron como esperadas a fallar, pero que ahora tienen éxito (generalmente porque la característica que prueban estaba rota y ha sido corregida).

FAIL

La prueba falló.

UNRESOLVED

No se pudo determinar el resultado de la prueba. Por ejemplo, esto ocurre cuando la prueba no se pudo ejecutar, la prueba en sí es inválida, o la prueba fue interrumpida.

UNSUPPORTED

La prueba no es compatible en este entorno. Esto es utilizado por formatos de prueba que pueden informar pruebas no compatibles.

TIMEOUT

La prueba se ejecutó, pero excedió el tiempo de espera antes de que pudiera completarse.

Las pruebas no resueltas (UNRESOLVED), con tiempo de espera excedido (TIMEOUT), fallidas (FAIL) y que pasaron inesperadamente (XPASS) se consideran fallos.

Dependiendo del formato de prueba, las pruebas pueden producir información adicional sobre su estado (generalmente solo para fallos). Consulte la sección OPCIONES DE SALIDA para obtener más información.

INFRAESTRUCTURA LIT

Esta sección describe la arquitectura de pruebas de lit para usuarios interesados en crear una nueva implementación de pruebas de lit, o extender una existente.

lit en sí es principalmente una infraestructura para descubrir y ejecutar pruebas arbitrarias, y para exponer una única interfaz conveniente a estas pruebas. lit en sí mismo no sabe cómo ejecutar pruebas, sino que esta lógica es definida por las suites de pruebas.

SUITES DE PRUEBAS

Como se describe en DESARROLLO DE PRUEBAS, las pruebas siempre se encuentran dentro de una suite de pruebas. Las suites de pruebas sirven para definir el formato de las pruebas que contienen, la lógica para encontrar esas pruebas y cualquier información adicional para ejecutar las pruebas.

lit identifica las suites de pruebas como directorios que contienen archivos lit.cfg o lit.site.cfg (ver también --config-prefix). Las suites de pruebas se descubren inicialmente buscando recursivamente en la jerarquía de directorios todos los archivos de entrada pasados en la línea de comandos. Puede usar --show-suites para mostrar las suites de pruebas descubiertas al inicio.

Una vez que se descubre una suite de pruebas, se carga su archivo de configuración. Los archivos de configuración son módulos Python que se ejecutarán. Cuando el archivo de configuración se ejecuta, se predefinen dos variables globales importantes:

lit_config

El objeto de configuración global de lit (una instancia de LitConfig), que define los formatos de prueba incorporados, los parámetros de configuración globales y otras rutinas auxiliares para implementar configuraciones de prueba.

config

Este es el objeto de configuración (una instancia de TestingConfig) para la suite de pruebas, que se espera que el archivo de configuración poble. Las siguientes variables también están disponibles en el objeto config, algunas de las cuales deben ser establecidas por la configuración y otras son opcionales o predefinidas:

name [requerido] El nombre de la suite de pruebas, para uso en informes y diagnósticos.

test_format [requerido] El objeto de formato de prueba que se utilizará para descubrir y ejecutar pruebas en la suite de pruebas. Generalmente, este será un formato de prueba incorporado disponible en el módulo lit.formats.

test_source_root La ruta del sistema de archivos a la raíz de la suite de pruebas. Para compilaciones fuera del árbol, este es el directorio que se escaneará en busca de pruebas.

test_exec_root Para compilaciones fuera del árbol, la ruta a la raíz de la suite de pruebas dentro del directorio del objeto. Aquí es donde se ejecutarán las pruebas y se colocarán los archivos de salida temporales.

environment Un diccionario que representa el entorno a utilizar al ejecutar pruebas en la suite.

standalone_tests Cuando es verdadero, marca un directorio con pruebas esperadas para ser ejecutadas de forma independiente. El descubrimiento de pruebas está deshabilitado para ese directorio. lit.suffixes y lit.excludes deben estar vacíos cuando esta variable es verdadera.

suffixes Para los formatos de prueba de lit que escanean directorios en busca de pruebas, esta variable es una lista de sufijos para identificar archivos de prueba. Utilizado por: ShTest.

substitutions Para los formatos de prueba de lit que sustituyen variables en un script de prueba, la lista de sustituciones a realizar. Utilizado por: ShTest.

unsupported Marca un directorio no compatible, todas las pruebas dentro de él se informarán como no compatibles. Utilizado por: ShTest.

parent La configuración padre, este es el objeto de configuración del directorio que contiene la suite de pruebas, o None.

root La configuración raíz. Esta es la configuración de lit más alta en el proyecto.

pipefail Normalmente, una prueba que utiliza una tubería de shell falla si alguno de los comandos de la tubería falla. Si esto no es deseado, establecer esta variable a falso hace que la prueba falle solo si el último comando de la tubería falla.

available_features Un conjunto de características que se pueden utilizar en directivas XFAIL, REQUIRES y UNSUPPORTED.

DESARROLLO DE PRUEBAS

Una vez que se localizan las suites de pruebas, lit recorre recursivamente el directorio fuente (siguiendo test_source_root) en busca de pruebas. Cuando lit entra en un subdirectorio, primero verifica si hay una suite de pruebas anidada definida en ese directorio. Si es así, carga esa suite de pruebas de forma recursiva, de lo contrario, instancia una configuración de prueba local para el directorio (ver ARCHIVOS DE CONFIGURACIÓN LOCAL).

Las pruebas se identifican por la suite de pruebas en la que están contenidas y la ruta relativa dentro de esa suite. Tenga en cuenta que la ruta relativa puede no hacer referencia a un archivo real en disco; algunos formatos de prueba (como GoogleTest) definen pruebas "virtuales" que tienen una ruta que contiene tanto la ruta al archivo de prueba real como una subruta para identificar la prueba virtual.

ARCHIVOS DE CONFIGURACIÓN LOCAL

Cuando lit carga un subdirectorio en una suite de pruebas, instancia una configuración de prueba local clonando la configuración del directorio padre --- la raíz de esta cadena de configuración siempre será una suite de pruebas. Una vez que la configuración de prueba se clona, lit busca un archivo lit.local.cfg en el subdirectorio. Si está presente, este archivo se cargará y se puede utilizar para especializar la configuración para cada directorio individual. Esta facilidad se puede utilizar para definir subdirectorios de pruebas opcionales, o para cambiar otros parámetros de configuración --- por ejemplo, para cambiar el formato de prueba, o los sufijos que identifican los archivos de prueba.

SUSTITUCIONES

lit permite sustituir patrones dentro de los comandos RUN. También proporciona el siguiente conjunto base de sustituciones, que se definen en TestRunner.py:

Macro Sustitución
%s ruta de origen (ruta al archivo que se está ejecutando actualmente)
%S directorio de origen (directorio del archivo que se está ejecutando actualmente)
%p igual que %S
%{pathsep} separador de ruta
%{fs-src-root} componente raíz de las rutas del sistema de archivos que apuntan al checkout de LLVM
%{fs-tmp-root} componente raíz de las rutas del sistema de archivos que apuntan al directorio temporal de la prueba
%{fs-sep} separador de ruta del sistema de archivos
%t nombre de archivo temporal único para la prueba
%basename_t El último componente de ruta de %t pero sin la extensión .tmp (obsoleto, use %{t:stem} en su lugar)
%T directorio padre de %t (no único, obsoleto, no usar)

NOMBRE

lit - LLVM integrado en el framework de pruebas

SINOPSIS

lit [options] [test suite options] [test-file...]

DESCRIPCIÓN

lit es un sistema de pruebas de Python diseñado para ser utilizado para probar herramientas y bibliotecas de compilación, ensamblado, enlazado y ejecución.

El sistema de pruebas de LLVM usa lit extensivamente, y este documento se centra en el uso de lit para probar LLVM. Sin embargo, lit es suficientemente genérico para ser utilizado en otras ocasiones.

El sistema de pruebas de LLVM está organizado como un árbol de directorios. Cada subdirectorio puede contener:

  • Archivos de prueba, que son scripts de Python que ejecutan una prueba y devuelven un resultado.
  • Archivos de configuración, llamados lit.cfg (o lit.site.cfg para configuraciones específicas del sitio), que configuran el comportamiento de lit para el directorio actual y todos los subdirectorios.
  • Subdirectorios que contienen más pruebas o configuraciones.

Una ejecución de lit puede ser configurada por uno o más archivos lit.cfg. Estos archivos son scripts de Python que pueden definir variables que controlan el comportamiento de lit, como los comandos a ejecutar, las características disponibles, etc. Para más detalles, consulte la sección LIT_INFRASTRUCTURE.

Una vez configurado, lit navega recursivamente el árbol de directorios, buscando archivos de prueba y ejecutándolos. Los resultados de cada prueba son reportados al usuario, y un resumen final se presenta al final de la ejecución.

OPCIONES GENERALES

-h, --help
Mostrar un resumen de las opciones de línea de comandos y salir.
-j N, --threads=N
Usar N hilos para ejecutar las pruebas en paralelo. El valor por defecto es el número de CPUs detectadas en el sistema.
-I dir
Añadir dir al camino de búsqueda de módulos Python.
-D NAME=VALUE
Definir una variable de sustitución global. Véase la sección SUBSTITUTIONS.
-d file
Generar un archivo de diagnóstico en file. Este archivo contiene información detallada sobre la ejecución de las pruebas, incluyendo los comandos ejecutados y sus salidas.
--no-progress-bar
Desactivar la barra de progreso.
--show-pass[=mode]
Mostrar todas las pruebas que pasan. El modo puede ser categories, none, o terse (por defecto).
--show-skip[=mode]
Mostrar todas las pruebas que se omiten. El modo puede ser categories, none, o terse (por defecto).
--quiet
Imprimir menos información. Sólo muestra los resultados de las pruebas que fallan o no se resuelven.
--verbose
Imprimir más información. Muestra los resultados de todas las pruebas, incluyendo las que pasan.
--config-file=file
Usar file como archivo de configuración principal.
--site-config-file=file
Usar file como archivo de configuración del sitio.

OPCIONES DE SALIDA

--summary[=file]
Escribir un resumen de la ejecución de las pruebas a file. Si file no se especifica, el resumen se escribe en la salida estándar.
--no-results-screen
No mostrar la pantalla de resultados al final de la ejecución.

OPCIONES DE EJECUCIÓN

--max-failures=N
Detener la ejecución después de N fallos. El valor por defecto es infinito.
--max-time=N
Establecer un tiempo límite de N segundos para la ejecución de todas las pruebas.
--max-individual-test-time=N
Establecer un tiempo límite de N segundos para cada prueba individual.
--debug
Habilitar la depuración de lit. Esto produce una gran cantidad de salida, que es útil para depurar problemas con lit mismo.

OPCIONES DE SELECCIÓN

-k PATTERN, --filter=PATTERN
Sólo ejecutar pruebas cuyo nombre coincida con el patrón PATTERN. El patrón puede contener comodines como * y ?. Si se proporciona varias veces, sólo se ejecutarán las pruebas que coincidan con alguno de los patrones.
-i PATTERN, --exclude=PATTERN
Excluir pruebas cuyo nombre coincida con el patrón PATTERN. Si se proporciona varias veces, se excluirán las pruebas que coincidan con alguno de los patrones.
--run-suite=NAME
Ejecutar sólo las pruebas pertenecientes al conjunto de pruebas NAME.
--run-keywords=KEYWORD,...
Ejecutar sólo las pruebas que estén marcadas con alguna de las palabras clave especificadas.
--run-features=FEATURE,...
Ejecutar sólo las pruebas que tengan habilitadas todas las características especificadas.
--run-only=test-path
Ejecutar sólo la prueba especificada en test-path.

OPCIONES ADICIONALES

--use-default-substitutions
Usar las sustituciones por defecto definidas por el framework de pruebas de LLVM.
--no-default-substitutions
No usar las sustituciones por defecto.

ESTADO DE SALIDA

El código de salida de lit es un valor de 8 bits que representa el resultado de la ejecución de las pruebas. Los bits significativos son:

0x01
Al menos una prueba falló.
0x02
Al menos una prueba no se resolvió.
0x04
Al menos una prueba fue marcada como XPASS (esperada pasar, pero falló).
0x08
Al menos una prueba fue marcada como XFAIL (esperada fallar, pero pasó).
0x10
Al menos una prueba fue marcada como UNSUPPORTED (no soportada).
0x20
Al menos una prueba fue marcada como UNRESOLVED (no resuelta).
0x40
Se produjo un error interno de lit.
0x80
Se produjo un fallo de tiempo de espera.

Si ninguna prueba falló y no se produjeron otros errores, el código de salida es 0.

RESULTADOS DE ESTADO DE PRUEBA

lit soporta los siguientes códigos de resultado para las pruebas:

PASS
La prueba pasó con éxito.
FAIL
La prueba falló.
XPASS
La prueba estaba marcada como esperada fallar, pero pasó.
XFAIL
La prueba estaba marcada como esperada fallar y falló.
UNSUPPORTED
La prueba no está soportada en este entorno.
UNRESOLVED
La prueba no pudo ser resuelta (por ejemplo, debido a una dependencia faltante).
TIMEOUT
La prueba excedió el tiempo límite de ejecución.

Adicionalmente, se pueden usar los siguientes códigos de resultado para pruebas de rendimiento:

IMPROVED
El rendimiento de la prueba mejoró en comparación con la línea base.
REGRESSED
El rendimiento de la prueba empeoró en comparación con la línea base.

INFRAESTRUCTURA LIT

Los archivos de configuración de lit (lit.cfg y lit.site.cfg) son scripts de Python que pueden definir varias variables para controlar el comportamiento de lit. Las siguientes variables son las más importantes:

config.name
El nombre del conjunto de pruebas que se está ejecutando.
config.test_format
El formato de las pruebas a usar. Por defecto es un formato simple que busca pruebas en archivos Python.
config.suffixes
Una lista de sufijos de archivo que se consideran archivos de prueba. Por defecto es [].
config.excludes
Una lista de patrones de nombres de archivo a excluir.
config.test_env
Una lista de variables de entorno que se exportarán a los procesos de prueba.
config.environment
Un diccionario que establece variables de entorno para los procesos de prueba. Por ejemplo, config.environment['PATH'] puede ser usado para añadir directorios al PATH.
config.substitutions
Una lista de diccionarios que definen sustituciones para ser usadas en los comandos de prueba. Cada diccionario puede contener las claves 'name', 'value', y 'type'. El tipo puede ser 'string' (por defecto) o 'path'.
config.available_features
Una lista de cadenas que representan las características disponibles en el entorno de prueba.
config.root
La ruta al directorio raíz del conjunto de pruebas.
config.target_triples
Una lista de triples de destino para los que se ejecutarán las pruebas. Si está vacío, las pruebas se ejecutarán para el triple de destino anfitrión.
config.imports
Una lista de módulos que se importarán en el script de prueba. Esto es útil para compartir código común entre las pruebas.

El archivo lit.site.cfg se utiliza para anular la configuración definida en lit.cfg y para proporcionar configuraciones específicas del sitio, como rutas a herramientas o dependencias.

SUSTITUCIONES

Las sustituciones permiten reemplazar nombres de archivo, directorios y otras cadenas en los comandos de prueba. Esto es útil para hacer que los scripts de prueba sean portables entre diferentes sistemas y configuraciones. Las sustituciones se definen en el archivo de configuración de lit, o se pueden especificar en la línea de comandos usando la opción -D.

Las sustituciones son de la forma %keyword o %{keyword:type}.

Las siguientes sustituciones están disponibles por defecto:

%S     El directorio del archivo de prueba actual.
%s     El nombre del archivo de prueba actual (incluyendo la extensión).
%T     El directorio temporal del archivo de prueba actual.
%t     El nombre del archivo de prueba actual sin la extensión.
%pyglib dir.pyglib
%target_triple
%arch
%vendor
%os
%target_features

Las siguientes sustituciones están disponibles para la manipulación de rutas:

%/s %s pero \ se reemplaza por /
%/S %S pero \ se reemplaza por /
%/p %p pero \ se reemplaza por /
%/t %t pero \ se reemplaza por /
%/T %T pero \ se reemplaza por /
%{s:basename} El último componente de ruta de %s
%{t:stem} El último componente de ruta de %t pero sin la extensión .tmp (alias para %basename_t)
%{s:real} %s después de expandir todos los enlaces simbólicos y unidades de sustitución
%{S:real} %S después de expandir todos los enlaces simbólicos y unidades de sustitución
%{p:real} %p después de expandir todos los enlaces simbólicos y unidades de sustitución
%{t:real} %t después de expandir todos los enlaces simbólicos y unidades de sustitución
%{T:real} %T después de expandir todos los enlaces simbólicos y unidades de sustitución
%{/s:real} %/s después de expandir todos los enlaces simbólicos y unidades de sustitución
%{/S:real} %/S después de expandir todos los enlaces simbólicos y unidades de sustitución
%{/p:real} %/p después de expandir todos los enlaces simbólicos y unidades de sustitución
%{/t:real} %/t después de expandir todos los enlaces simbólicos y unidades de sustitución
%{/T:real} %/T después de expandir todos los enlaces simbólicos y unidades de sustitución
%{/s:regex_replacement} %/s pero escapado para su uso en el reemplazo de un comando s@@@ en sed
%{/S:regex_replacement} %/S pero escapado para su uso en el reemplazo de un comando s@@@ en sed
%{/p:regex_replacement} %/p pero escapado para su uso en el reemplazo de un comando s@@@ en sed
%{/t:regex_replacement} %/t pero escapado para su uso en el reemplazo de un comando s@@@ en sed
%{/T:regex_replacement} %/T pero escapado para su uso en el reemplazo de un comando s@@@ en sed
%:s En Windows, %/s pero se elimina un : si es el segundo carácter. De lo contrario, %s pero con un único / inicial eliminado.
%:S En Windows, %/S pero se elimina un : si es el segundo carácter. De lo contrario, %S pero con un único / inicial eliminado.
%:p En Windows, %/p pero se elimina un : si es el segundo carácter. De lo contrario, %p pero con un único / inicial eliminado.
%:t En Windows, %/t pero se elimina un : si es el segundo carácter. De lo contrario, %t pero con un único / inicial eliminado.
%:T En Windows, %/T pero se elimina un : si es el segundo carácter. De lo contrario, %T pero con un único / inicial eliminado.

Se proporcionan otras sustituciones que son variaciones de este conjunto base y se pueden definir patrones de sustitución adicionales en cada módulo de prueba. Consulte la sección LOCAL CONFIGURATION FILES de los módulos.

Se puede encontrar información más detallada sobre las sustituciones en la Guía de Infraestructura de Pruebas de LLVM <>.

FORMATO DE SALIDA DE EJECUCIÓN DE PRUEBAS

La salida de lit para una ejecución de pruebas se ajusta al siguiente esquema, tanto en modo corto como en modo detallado (aunque en modo corto no se mostrarán líneas de PASS). Este esquema ha sido elegido para ser relativamente fácil de analizar de forma fiable por una máquina (por ejemplo, en la extracción de registros de buildbot), y para que otras herramientas lo generen.

Se espera que cada resultado de prueba aparezca en una línea que coincida con:

<código de resultado>: <nombre de la prueba> (<información de progreso>)

donde <código de resultado> es un resultado de prueba estándar como PASS, FAIL, XFAIL, XPASS, UNRESOLVED o UNSUPPORTED. Los códigos de resultado de rendimiento IMPROVED y REGRESSED también están permitidos.

El campo <nombre de la prueba> puede consistir en una cadena arbitraria que no contenga saltos de línea.

El campo <información de progreso> se puede utilizar para informar de información de progreso como (1/300) o puede estar vacío, pero incluso cuando está vacío, los paréntesis son obligatorios.

En caso de que una prueba permita reintentos (ver la anotación ALLOW_RETRIES:) y necesite más de un intento para tener éxito, <información de progreso> se amplía con esta información:

, <número de intentos realizados> de <máximo de intentos permitidos> intentos

Cada resultado de prueba puede incluir información de registro adicional (multilínea) en el siguiente formato:

<delimitador de registro> TEST '(<nombre de la prueba>)' <delimitador final>
... mensaje de registro ...
<delimitador de registro>

donde <nombre de la prueba> debe ser el nombre de una prueba reportada previamente, <delimitador de registro> es una cadena de caracteres "*" *al menos* cuatro caracteres de longitud (la longitud recomendada es 20), y <delimitador final> es una cadena arbitraria (sin analizar).

El siguiente es un ejemplo de una salida de ejecución de pruebas que consta de cuatro pruebas A, B, C y D, y un mensaje de registro para la prueba C que falla:

PASS: A (1 de 4)
PASS: B (2 de 4)
FAIL: C (3 de 4)
******************** TEST 'C' FAILED ********************
La prueba 'C' falló como resultado del código de salida 1.
********************
PASS: D (4 de 4)

CARACTERÍSTICAS PREDETERMINADAS

Para mayor comodidad, lit añade automáticamente available_features para algunos casos de uso comunes.

lit añade una característica basada en el sistema operativo en el que se está compilando, por ejemplo: system-darwin, system-linux, etc. lit también añade automáticamente una característica basada en la arquitectura actual, por ejemplo target-x86_64, target-aarch64, etc.

Al compilar con sanitizadores habilitados, lit añade automáticamente el nombre corto del sanitizador, por ejemplo: asan, tsan, etc.

Para ver la lista completa de características que se pueden añadir, consulte llvm/utils/lit/lit/llvm/config.py.
