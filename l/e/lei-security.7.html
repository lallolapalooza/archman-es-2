NAME

lei - security information

SYNOPSIS

lei(1) está pensado para usarse tanto con correo público archivado como con correo "privado" en buzones personales. Este documento tiene como objetivo ofrecer una visión general de las implicaciones de seguridad y gestionar las expectativas del usuario.

DESCRIPTION

lei espera ser ejecutado como un usuario normal en un sistema tipo Unix. Espera un sistema de archivos sensible a mayúsculas y minúsculas con soporte para permisos estándar de Unix.

No utiliza ACLs POSIX, atributos extendidos ni ninguna otra función relacionada con la seguridad que requiera módulos Perl no estándar.

Existe soporte preliminar para "usuarios virtuales", pero está incompleto y sin documentar.

INTERNAL FILES

lei se ejecuta con un umask de 077 para evitar que otros usuarios del sistema accedan al correo de los demás.

El almacenamiento git y las bases de datos Xapian se encuentran en "$XDG_DATA_HOME/lei/store" (normalmente "~/.local/share/lei/store"). Cualquier correo personal importado residirá aquí, por lo que esto debería estar en un sistema de archivos o dispositivo de bloque cifrado.

"$XDG_RUNTIME_DIR/lei" (normalmente "/run/user/$UID/lei" o "/tmp/lei-$UID") contiene el socket utilizado para acceder al demonio de lei. Solo debe ser accesible por el propietario (modo 0700).

"$XDG_CACHE_HOME/lei" (normalmente "~/.cache/lei") contendrá nombres de carpetas IMAP y Maildir que podrían filtrar información sensible, así como nombres de repositorios git.

"$XDG_DATA_HOME/lei/saved-searches" (normalmente "~/.local/share/lei/saved-searches") contendrá nombres de carpetas mencionados anteriormente, así como el historial de búsquedas (eliminable).

La configuración de lei reside en "$XDG_CONFIG_HOME/lei/config" (normalmente "~/.config/lei/config"). Puede contener rutas y nombres de host sensibles en la configuración si el usuario decide configurarlos.

lei en sí nunca escribirá credenciales en el sistema de archivos. Sin embargo, git-credential(1) puede estar configurado para hacerlo. lei solo leerá "~/.netrc" si se utiliza "--netrc" (y nunca escribirá en "~/.netrc").

"$XDG_CACHE_HOME/public-inbox" (normalmente "~/.cache/public-inbox") puede contener datos y módulos compilados con Inline::C que se pueden compartir con instancias de public-inbox-daemon(8) de cara al público; por lo tanto, no deben haber datos privados en las rutas de "public-inbox".

EXTERNAL FILES

Las ubicaciones establecidas por lei-add-external(1) pueden compartirse con procesos de public-inbox-daemon(8) de cara al público. Pueden residir en almacenamiento compartido y pueden hacerse legibles para otros usuarios en el sistema local.

CORE DUMPS

En caso de que algún proceso falle, un volcado de memoria (core dump) podría contener contraseñas o el contenido de mensajes sensibles. Por favor, repórtelos para que puedan ser corregidos (ver "CONTACT").

NETWORK ACCESS

lei utiliza actualmente los ejecutables curl(1) y git(1) en $PATH para el acceso a redes HTTP y HTTPS. La autenticación interactiva para HTTP y HTTPS aún no es compatible, ya que todas las fuentes HTTP/HTTPS compatibles actualmente son instancias de PublicInbox::WWW.

Se utiliza la biblioteca Mail::IMAPClient para IMAP e IMAPS. Net::NNTP (biblioteca estándar) se utiliza para NNTP y NNTPS.

Mail::IMAPClient y Net::NNTP utilizarán IO::Socket::SSL para TLS si está disponible. A su vez, IO::Socket::SSL utiliza la biblioteca OpenSSL, ampliamente instalada.

Se intentará STARTTLS si es anunciado por el servidor, a menos que se utilicen IMAPS o NNTPS. Se puede usar "-c imap.starttls=0" y "-c nntp.startls=0" para deshabilitar STARTTLS.

Se utilizará IO::Socket::Socks si "-c imap.proxy" o "-c nntp.proxy" apuntan a una dirección "socks5h://$HOST:$PORT" (común para Tor).

El modificador "--netrc" puede pasarse a curl y usarse para acceso NNTP/IMAP (a través de Net::Netrc).

CREDENTIAL DATA

lei utiliza git-credential(1) para solicitar a los usuarios nombres de usuario y contraseñas IMAP y NNTP. Estas contraseñas no están cifradas en memoria y se transfieren entre procesos a través de sockets UNIX anónimos y tuberías. Pueden ser expuestas a través de herramientas de seguimiento de llamadas al sistema (por ejemplo, strace(1)), errores/ataques del kernel y hardware.

Si bien las credenciales no se escriben en el sistema de archivos por defecto, es posible que terminen en el disco si los procesos se intercambian (swapped out). Se recomienda el uso de una partición de intercambio cifrada.

AUTHENTICATION METHODS

LOGIN (nombre de usuario + contraseña) se sabe que funciona sobre IMAP(S), al igual que AUTH=ANONYMOUS (que es utilizado por public-inbox-imapd(1) como parte de nuestro conjunto de pruebas). AUTHINFO puede funcionar para NNTP, pero no ha sido probado. Se necesitarán probadores para otros métodos de autenticación.

DENIAL-OF-SERVICE VECTORS

lei utiliza la misma biblioteca de análisis MIME que public-inbox-mda(1) con límites de tamaño de encabezado, partes, anidamiento y límites de delimitador similares a los que se encuentran en SpamAssassin y postfix.

El análisis de direcciones de correo electrónico lo maneja Email::Address::XS si está disponible, pero puede recurrir a expresiones regulares que favorecen la velocidad y tiempos de ejecución predecibles sobre la corrección.

ENCRYPTED EMAILS

Aún no es compatible, pero eventualmente debería ser posible configurar el descifrado y la indexación de mensajes y archivos adjuntos cifrados. Cuando sea compatible, los términos descifrados se almacenarán en las bases de datos Xapian bajo "$XDG_DATA_HOME/lei/store".
