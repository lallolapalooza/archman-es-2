LEX(1P) Manual del programador de POSIX LEX(1P)

PROLOG

Esta página del manual es parte del Manual del programador de POSIX. La implementación de Linux de esta interfaz puede diferir (consulte la página del manual de Linux correspondiente para conocer los detalles del comportamiento de Linux), o la interfaz puede no estar implementada en Linux.

NOMBRE

lex — genera programas para tareas léxicas (DESARROLLO)

SINOPSIS

lex [-t] [-n|-v] [archivo...]

DESCRIPCIÓN

La utilidad lex generará programas C para ser utilizados en el procesamiento léxico de la entrada de caracteres, y que puedan ser usados como interfaz para yacc. Los programas C se generarán a partir del código fuente de lex y se ajustarán al estándar ISO C, sin depender de ningún comportamiento indefinido, no especificado o dependiente de la implementación, excepto en los casos en que el código se copie directamente de la fuente suministrada, o en casos que sean documentados por la implementación. Generalmente, la utilidad lex escribirá el programa que genera en el archivo lex.yy.c; el estado de este archivo no está especificado si lex sale con un estado de salida distinto de cero. Consulte la sección DESCRIPCIÓN EXTENDIDA para una descripción completa del lenguaje de entrada de lex.

OPCIONES

La utilidad lex se ajustará al volumen de Definiciones Base de POSIX.1‐2017, Sección 12.2, Directrices de Sintaxis de Utilidad, excepto por la Directriz 9.

Se soportarán las siguientes opciones:

-n
Suprime el resumen de estadísticas que normalmente se escribe con la opción -v. Si no se especifican tamaños de tabla en el código fuente de lex y no se especifica la opción -v, entonces se implica -n.
-t
Escribe el programa resultante en la salida estándar en lugar de lex.yy.c.
-v
Escribe un resumen de las estadísticas de lex en la salida estándar. (Consulte la discusión de los tamaños de tabla de lex en Definiciones en lex.) Si se especifica la opción -t y no se especifica -n, este informe se escribirá en la salida de error estándar. Si se especifican tamaños de tabla en el código fuente de lex, y si la opción -n no se especifica, la opción -v puede habilitarse.

OPERANDOS

Se soportará el siguiente operando:

archivo
Una ruta de acceso a un archivo de entrada. Si se especifican más de un archivo de este tipo, todos los archivos se concatenarán para producir un único programa lex. Si no se especifican operandos de archivo, o si un operando de archivo es '-', se utilizará la entrada estándar.

ENTRADA ESTÁNDAR

Se utilizará la entrada estándar si no se especifican operandos de archivo, o si un operando de archivo es '-'. Véase ARCHIVOS DE ENTRADA.

ARCHIVOS DE ENTRADA

Los archivos de entrada contendrán código fuente de lex, como se describe en la sección DESCRIPCIÓN EXTENDIDA.

Las siguientes variables de entorno afectarán la ejecución de lex:

LANG
Proporciona un valor predeterminado para las variables de internacionalización que no están establecidas o están vacías. (Consulte el volumen de Definiciones Base de POSIX.1‐2017, Sección 8.2, Variables de Internacionalización para la precedencia de las variables de internacionalización utilizadas para determinar los valores de las categorías de configuración regional.)
LC_ALL
Si se establece en un valor de cadena no vacío, anula los valores de todas las demás variables de internacionalización.
LC_COLLATE

Determina la configuración regional para el comportamiento de rangos, clases de equivalencia y elementos de colación multicarácter dentro de las expresiones regulares. Si esta variable no está establecida en la configuración regional POSIX, los resultados no están especificados.
LC_CTYPE
Determina la configuración regional para la interpretación de secuencias de bytes de datos de texto como caracteres (por ejemplo, caracteres de un solo byte frente a caracteres de varios bytes en argumentos y archivos de entrada), y el comportamiento de las clases de caracteres dentro de las expresiones regulares. Si esta variable no está establecida en la configuración regional POSIX, los resultados no están especificados.

Determina la configuración regional que debe utilizarse para afectar el formato y el contenido de los mensajes de diagnóstico escritos en la salida de error estándar.
NLSPATH
Determina la ubicación de los catálogos de mensajes para el procesamiento de LC_MESSAGES.

SYNOPSIS

lex [-c | -n] [-Ca | -Cd | -Co] [-f] [-i] [-l] [-P prefix] [-r] [-s] [-t] [-v] [file...]

DESCRIPTION

The lex utility generates a lexical analyzer (also known as a scanner or tokenizer) based on the specified input files. The generated lexical analyzer is written to the file lex.yy.c by default.

The input files consist of one or more sections separated by %% delimiters. The sections are:

  • Definitions.
  • Rules.
  • User subroutines.

The first %% is required to mark the beginning of the rules section. The second %% is required only if the user subroutines section follows.

Rules Processing

When the generated lexical analyzer recognizes text that matches one or more rules, it selects the rule that matches the longest possible string of input characters. If there is a tie for the longest match, the first rule encountered in the input is selected. The action associated with the selected rule is then executed. If the selected rule has no action, nothing is done.

The actions are C program fragments that are copied verbatim into the generated source file lex.yy.c. The lexical analyzer function is named yylex().

The following variables are available to actions:

yytext
A pointer to the current token. The type of yytext can be declared as either a character array or a pointer using the %array or %pointer declarations, but the default is implementation-defined.
*
The external int yyleng shall be set to the length of the matching string.
*
The expression's corresponding program fragment, or action, shall be executed.

During pattern matching, lex shall search the set of patterns for the single longest possible match. Among rules that match the same number of characters, the rule given first shall be chosen.

The general format of lex source shall be:

Definitions %% Rules %% UserSubroutines

The first %% is required to mark the beginning of the rules (regular expressions and actions); the second %% is required only if user subroutines follow.

Any line in the Definitions section beginning with a <blank> shall be assumed to be a C program fragment and shall be copied to the external definition area of the lex.yy.c file. Similarly, anything in the Definitions section included between delimiter lines containing only "%{" and "%}" shall also be copied unchanged to the external definition area of the lex.yy.c file.

Any such input (beginning with a <blank> or within "%{" and "%}" delimiter lines) appearing at the beginning of the Rules section before any rules are specified shall be written to lex.yy.c after the declarations of variables for the yylex() function and before the first line of code in yylex(). Thus, user variables local to yylex() can be declared here, as well as application code to execute upon entry to yylex().

The action taken by lex when encountering any input beginning with a <blank> or within "%{" and "%}" delimiter lines appearing in the Rules section but coming after one or more rules is undefined. The presence of such input may result in an erroneous definition of the yylex() function.

C-language code in the input shall not contain C-language trigraphs. The C-language code within "%{" and "%}" delimiter lines shall not contain any lines consisting only of "%}", or only of "%%".

Definitions in lex

Definitions appear before the first %% delimiter. Any line in this section not contained between "%{" and "%}" lines and not beginning with a <blank> shall be assumed to define a lex substitution string. The format of these lines shall be:

name substitute

If a name does not meet the requirements for identifiers in the ISO C standard, the result is undefined. The string substitute shall replace the string {name} when it is used in a rule. The name string shall be recognized in this context only when the braces are provided and when it does not appear within a bracket expression or within double-quotes.

In the Definitions section, any line beginning with a <percent-sign> (%) character and followed by an alphanumeric word beginning with either 's' or 'S' shall define a set of start conditions. Any line beginning with a % followed by a word beginning with either 'x' or 'X' shall define a set of exclusive start conditions. When the generated scanner is in a %s state, patterns with no state specified shall be also active; in a %x state, such patterns shall not be active. The rest of the line, after the first word, shall be considered to be one or more <blank>-separated names of start conditions. Start condition names shall be constructed in the same way as definition names. Start conditions can be used to restrict the matching of regular expressions to one or more states as described in Regular Expressions in lex.

Implementations shall accept either of the following two mutually-exclusive declarations in the Definitions section:

%array
Declare the type of yytext to be a null-terminated character array.
%pointer
Declare the type of yytext to be a pointer to a null-terminated character string.

The default type of yytext is implementation-defined. If an application refers to yytext outside of the scanner source file (that is, via an extern), the application shall include the appropriate %array or %pointer declaration in the scanner source file.

Implementations shall accept declarations in the Definitions section for setting certain internal table sizes. The declarations are shown in the following table.


Table: Table Size Declarations in lex

Declaration Description Minimum Value
%p n Number of positions 2500
%n n Number of states 500
%a n Number of transitions 2000
%e n Number of parse tree nodes 1000
%k n Number of packed character classes 1000
%o n Size of the output array 3000

In the table, n represents a positive decimal integer, preceded by one or more <blank> characters. The exact meaning of these table size numbers is implementation-defined. The implementation shall document how these numbers affect the lex utility and how they are related to any output that may be generated by the implementation should limitations be encountered during the execution of lex. It shall be possible to determine from this output which of the table size values needs to be modified to permit lex to successfully generate tables for the input language. The values in the column Minimum Value represent the lowest values conforming implementations shall provide.

Rules in lex

The rules in lex source files are a table in which the left column contains regular expressions and the right column contains actions (C program fragments) to be executed when the expressions are recognized.

ERE action
ERE action
...

The extended regular expression (ERE) portion of a row shall be separated from action by one or more <blank> characters. A regular expression containing <blank> characters shall be recognized under one of the following conditions:

*
The entire expression appears within double-quotes.
*
The <blank> characters appear within double-quotes or square brackets.
*
Each <blank> is preceded by a <backslash> character.

User Subroutines in lex

Anything in the user subroutines section shall be copied to lex.yy.c following yylex().

Regular Expressions in lex

The lex utility shall support the set of extended regular expressions (see the Base Definitions volume of POSIX.1‐2017, Section 9.4, Extended Regular Expressions), with the following additions and exceptions to the syntax:

"..."
Any string enclosed in double-quotes shall represent the characters within the double-quotes as themselves, except that <backslash>-escapes (which appear in the following table) shall be recognized. Any <backslash>-escape sequence shall be terminated by the closing quote. For example, "\01""1" represents a single string: the octal value 1 followed by the character '1'.
<state>r, <state1,state2,...>r

The regular expression r shall be matched only when the program is in one of the start conditions indicated by state, state1, and so on; see Actions in lex. (As an exception to the typographical conventions of the rest of this volume of POSIX.1‐2017, in this case <state> does not represent a metavariable, but the literal angle-bracket characters surrounding a symbol.) The start condition shall be recognized as such only at the beginning of a regular expression.
r/x
The regular expression r shall be matched only if it is followed by an occurrence of regular expression x (x is the instance of trailing context, further defined below). The token returned in yytext shall only match r. If the trailing portion of r matches the beginning of x, the result is unspecified. The r expression cannot include further trailing context or the '+' (match-end-of-line) operator; x cannot include the '^' (match-beginning-of-line) operator, nor trailing context, nor the '+' operator. That is, only one occurrence of trailing context is allowed in a lex regular expression, and the '^' operator only can be used at the beginning of such an expression.
{name}
When name is one of the substitution symbols from the Definitions section, the string, including the enclosing braces, shall be replaced by the substitute val
ue. El valor de sustitución se tratará en la expresión regular extendida como si estuviera entre paréntesis. No se producirá ninguna sustitución si {nombre} aparece dentro de una expresión de corchetes o entre comillas dobles.

Dentro de una ERE, un carácter de se considerará que inicia una secuencia de escape, según se especifica en la tabla del volumen de Definiciones Base de POSIX.1-2017, Capítulo 5, Notación de formato de archivo ('\\', '\a', '\b', '\f', '\n', '\r', '\t', '\v'). Además, se reconocerán las secuencias de escape de la siguiente tabla.

Un literal no puede aparecer dentro de una ERE; la secuencia de escape '\n' se puede usar para representar un . Un no será igualado por un operador de punto.

Los operadores de anclaje de ERE '^' y '$' no aparecen en la tabla. Con las expresiones regulares de lex, estos operadores están restringidos en su uso: el operador '^' solo se puede usar al principio de una expresión regular completa, y el operador '$' solo al final. Los operadores se aplican a toda la expresión regular. Por lo tanto, por ejemplo, el patrón "(\\^abc)|(def$)" no está definido; en su lugar, se puede escribir como dos reglas separadas, una con la expresión regular "\\^abc" y otra con "def$", que comparten una acción común a través de la acción especial '|' (ver más abajo). Si el patrón se escribiera "\\^abc|def$", coincidiría con "abc" o "def" en una línea por sí sola.

A diferencia de las reglas generales de ERE, el anclaje incrustado no está permitido por la mayoría de las implementaciones históricas de lex. Un ejemplo de anclaje incrustado sería para patrones como "(\\^| )foo( |%)" para igualar "foo" cuando existe como una palabra completa. Esta funcionalidad se puede obtener usando las características existentes de lex:

^foo/[ \n]      |
" foo"/[ \n]    /* Se encontró foo como una palabra separada. */

Tenga en cuenta también que '$' es una forma de contexto de cola (es equivalente a "/\n") y como tal no se puede usar con expresiones regulares que contengan otra instancia del operador (ver la discusión anterior sobre el contexto de cola).

El operador adicional de contexto de cola de expresiones regulares '/' se puede usar como un carácter ordinario si se presenta entre comillas dobles, "/"; precedido por una , "\/"; o dentro de una expresión de corchetes, "[/]". Los operadores de condición de inicio '<' y '>' solo serán especiales en una condición de inicio al principio de una expresión regular; en cualquier otro lugar de la expresión regular se tratarán como caracteres ordinarios.

Acciones en lex

La acción a tomar cuando se iguala una ERE puede ser un fragmento de programa C o las acciones especiales descritas a continuación; el fragmento de programa puede contener una o más sentencias C, y también puede incluir acciones especiales. La sentencia C vacía ';' será una acción válida; cualquier cadena en la entrada lex.yy.c que coincida con la porción del patrón de tal regla se ignora o omite efectivamente. Sin embargo, la ausencia de una acción no será válida, y la acción que toma lex en tal condición no está definida.

La especificación de una acción, incluyendo sentencias C y acciones especiales, puede extenderse a lo largo de varias líneas si está encerrada entre llaves:

ERE <uno o más espacios> { sentencia de programa
                           sentencia de programa }

Las sentencias del programa no contendrán tokens de preprocesamiento de llaves desequilibrados.

La acción predeterminada cuando una cadena en la entrada de un programa lex.yy.c no coincide con ninguna expresión será copiar la cadena a la salida. Debido a que el comportamiento predeterminado de un programa generado por lex es leer la entrada y copiarla a la salida, un programa fuente mínimo de lex que solo tenga "%%" generará un programa C que simplemente copie la entrada a la salida sin cambios.

Cuatro acciones especiales estarán disponibles:

|   ECHO;   REJECT;   BEGIN
|
La acción '|' significa que la acción para la siguiente regla es la acción para esta regla. A diferencia de las otras tres acciones, '|' no puede encerrarse entre llaves ni terminar en punto y coma; la aplicación debe asegurarse de que se especifique sola, sin otras acciones.
ECHO;
Escribir el contenido de la cadena yytext en la salida.
REJECT;
Por lo general, solo una expresión coincide con una cadena dada en la entrada. REJECT significa "continuar con la siguiente expresión que coincide con la entrada actual", y provocará que se ejecute la regla que fue la segunda opción después de la regla actual para la misma entrada. Por lo tanto, se pueden igualar y ejecutar múltiples reglas para una cadena de entrada o cadenas de entrada superpuestas. Por ejemplo, dadas las expresiones regulares "xyz" y "xy" y la entrada "xyz", por lo general solo coincidiría la expresión regular "xyz". El siguiente intento de coincidencia comenzaría después de la z. Si la última acción en la regla "xyz" es REJECT, se ejecutarían tanto esta regla como la regla "xy". La acción REJECT puede implementarse de tal manera que el flujo de control no continúe después de ella, como si fuera equivalente a un goto a otra parte de yylex(). El uso de REJECT puede resultar en escáneres algo más grandes y lentos.
BEGIN
La acción:
BEGIN nuevostado;

cambia el estado (condición de inicio) a nuevostado. Si la cadena nuevostado no se ha declarado previamente como una condición de inicio en la sección de Definiciones, los resultados no están definidos. El estado inicial se indica con el dígito '0' o el token INITIAL.

Las funciones o macros descritas a continuación son accesibles para el código de usuario incluido en la entrada de lex. Es

is unspecified whether they appear in the C code output of lex, or are accessible only through the -l l operand to c99 (the lex library).

int yylex(void)

Realiza el análisis léxico de la entrada; esta es la función principal generada por la utilidad lex. La función debe devolver cero cuando se alcanza el final de la entrada; de lo contrario, debe devolver valores distintos de cero (tokens) determinados por las acciones que se seleccionan.
int yymore(void)

Cuando se llama, indica que cuando se reconozca la siguiente cadena de entrada, se añadirá al valor actual de yytext en lugar de reemplazarlo; el valor en yyleng se ajustará en consecuencia.
int yyless(int n)

Conserva n caracteres iniciales en yytext, terminados en NUL, y trata los caracteres restantes como si no se hubieran leído; el valor en yyleng se ajustará en consecuencia.
int input(void)

Devuelve el siguiente carácter de la entrada, o cero al final del archivo. Debe obtener la entrada del puntero de flujo yyin, aunque posiblemente a través de un búfer intermedio. Por lo tanto, una vez que ha comenzado el análisis, el efecto de alterar el valor de yyin no está definido. El carácter leído se eliminará del flujo de entrada del analizador sin ningún procesamiento por parte del analizador.
int unput(int c)

Devuelve el carácter 'c' a la entrada; yytext y yyleng no están definidos hasta que se corresponda la siguiente expresión. El resultado de usar unput() para más caracteres de los que se han introducido no está especificado.

Las siguientes funciones deben aparecer solo en la biblioteca lex accesible a través del operando -l l; por lo tanto, pueden ser redefinidas por una aplicación que cumpla con el estándar:

int yywrap(void)

Llamada por yylex() al final del archivo; la yywrap() por defecto siempre debe devolver 1. Si la aplicación requiere que yylex() continúe procesando con otra fuente de entrada, entonces la aplicación puede incluir una función yywrap(), que asocia otro archivo con la variable externa FILE * yyin y debe devolver un valor de cero.
int main(int argc, char *argv[])

Llama a yylex() para realizar el análisis léxico, luego sale. El código del usuario puede contener main() para realizar operaciones específicas de la aplicación, llamando a yylex() según corresponda.

Excepto por input(), unput() y main(), todos los nombres externos y estáticos generados por lex deben comenzar con el prefijo yy o YY.

USO DE LA APLICACIÓN

Se advierte a las aplicaciones que cumplen con el estándar que en la sección Reglas, una ERE sin acción no es aceptable, pero no es necesario que lex la detecte como errónea. Esto puede resultar en errores de compilación o de tiempo de ejecución.

El propósito de input() es tomar caracteres del flujo de entrada y descartarlos en lo que respecta al análisis léxico. Un uso común es descartar el cuerpo de un comentario una vez que se reconoce el inicio de un comentario.

La utilidad lex no está completamente internacionalizada en su tratamiento de expresiones regulares en el código fuente de lex o en el analizador léxico generado. Parecería deseable que el analizador léxico interprete las expresiones regulares dadas en el código fuente de lex según el entorno especificado cuando se ejecuta el analizador léxico, pero esto no es posible con la tecnología actual de lex. Además, la naturaleza misma de los analizadores léxicos producidos por lex debe estar estrechamente ligada a los requisitos léxicos del lenguaje de entrada que se describe, que con frecuencia es específico de la configuración regional de todos modos. (Por ejemplo, escribir un analizador que se utiliza para texto en francés no es automáticamente útil para procesar otros idiomas).

EJEMPLOS

El siguiente es un ejemplo de un programa lex que implementa un escáner rudimentario para una sintaxis similar a Pascal:

%{
/* Se necesita esto para la llamada a atof() más abajo. */
#include <math.h>
/* Se necesita esto para printf(), fopen() y stdin más abajo. */
#include <stdio.h>
%}
DIGIT    [0-9]
ID       [a-z][a-z0-9]*
%%
{DIGIT}+ {
    printf("Un entero: %s (%d)\n", yytext,
        atoi(yytext));
    }
{DIGIT}+"."{DIGIT}*        {
    printf("Un flotante: %s (%g)\n", yytext,
        atof(yytext));
    }
if|then|begin|end|procedure|function        {
    printf("Una palabra clave: %s\n", yytext);
    }
{ID}    printf("Un identificador: %s\n", yytext);
"+"|"-"|"*"|"/"        printf("Un operador: %s\n", yytext);
"{"[^}\n]*"}"    /* Ignorar comentarios de una sola línea. */
[ \t\n]+        /* Ignorar espacios en blanco. */
.  printf("Carácter no reconocido: %s\n", yytext);
%%
int main(int argc, char *argv[])
{
    ++argv, --argc;  /* Saltar el nombre del programa. */
    if (argc > 0)
        yyin = fopen(argv[0], "r");
    else
        yyin = stdin;
    yylex();
}

FUNDAMENTO

Aunque la opción -c y las referencias al lenguaje C se conservan en esta descripción, lex puede generalizarse a otros lenguajes, como se hizo en su momento para EFL, el Lenguaje FORTRAN Extendido. Dado que la especificación de entrada de lex es esencialmente independiente del lenguaje, se podrían escribir versiones de esta utilidad para producir código Ada, Modula-2 o Pascal, y existen implementaciones históricas conocidas que lo hacen.

La descripción actual de lex omite el problema de tratar las ERE internacionalizadas en el código fuente de lex o en el analizador léxico generado. Si sigue el modelo utilizado por awk (se asume que el código fuente se presenta en la configuración regional POSIX, pero la entrada y la salida están en la configuración regional especificada por las variables de entorno), entonces las tablas en el analizador léxico producido por lex interpretarían las ERE especificadas en el código fuente de lex en términos de las variables de entorno especificadas cuando se ejecutó lex. El efecto deseado sería que el analizador léxico interpretara las ERE dadas en el código fuente de lex según el entorno especificado cuando se ejecuta el analizador léxico, pero esto no es posible con la tecnología actual de lex.

La descripción de las secuencias de escape de dígitos octales y hexadecimales concuerda con el uso de secuencias de escape en el estándar ISO C.

Las versiones anteriores de este estándar permitían implementaciones con bytes distintos de ocho bits, pero esto se ha modificado en esta versión.

No hay una especificación detallada del formato de salida. El comportamiento observado de lex en cuatro implementaciones históricas diferentes fue que ninguna de estas implementaciones informaba consistentemente los números de línea para los mensajes de error y advertencia. Además, había un deseo de que se permitiera a lex emitir mensajes de diagnóstico adicionales. Dejar los formatos de mensajes sin especificar evita estas cuestiones de formato y problemas de internacionalización.

Aunque el especificador %x para las condiciones de inicio *exclusivas* no es una práctica histórica, se cree que es un cambio menor en las implementaciones históricas y mejora enormemente la usabilidad de los programas lex, ya que permite a una aplicación obtener la funcionalidad esperada con menos sentencias.

Las declaraciones %array y %pointer se agregaron como una solución intermedia entre los sistemas históricos. El lex basado en System V copia el texto coincidente a una matriz yytext. El programa flex, compatible con sistemas BSD y GNU, utiliza un puntero. En este último caso, se obtienen mejoras significativas de rendimiento para algunos analizadores. La mayoría de los programas históricos no requerirán ningún cambio al portar de un sistema a otro porque la cadena a la que se hace referencia está terminada en nulo en ambos casos. (El método utilizado por flex en su caso es terminar el token en el lugar agregando un carácter nulo, recordando el carácter que solía venir justo después del token y reemplazándolo antes de continuar con el siguiente escaneo). Los programas de múltiples archivos con referencias externas a yytext fuera del archivo fuente del analizador deberían seguir funcionando en sus sistemas históricos, pero requerirían una de las nuevas declaraciones para ser considerados estrictamente portátiles.

La descripción de las ERE evita la duplicación innecesaria de detalles de las ERE porque sus significados dentro de una ERE de lex son los mismos que los de la ERE en este volumen de POSIX.1‐2017.

La razón de la condición indefinida asociada con el texto que comienza con un <espacio en blanco> o dentro de las líneas delimitadoras "%{" y "%}" que aparecen en la sección Reglas se debe a la práctica histórica. Tanto el lex de BSD como el de System V copian la entrada con sangría (o entre delimitadores) en la sección Reglas (excepto al principio) a áreas inaccesibles de la función yylex() (el código se escribe directamente después de una instrucción break). En algunos casos, el lex de System V genera un mensaje de error o un error de sintaxis, dependiendo de la forma de la entrada con sangría.

La intención al dividir la lista de funciones en aquellas que pueden aparecer en lex.yy.c *frente a* aquellas que solo aparecen en libl.a es que solo las funciones en libl.a puedan ser redefinidas de manera confiable por una aplicación que cumpla con el estándar.

Las descripciones de la salida estándar y el error estándar son algo complicadas porque las implementaciones históricas de lex optaron por emitir mensajes de diagnóstico

RATIONALE

The description of the "yytext" variable was modified to clarify that it is not guaranteed to be null-terminated. The original text was ambiguous.

The description of the interaction between the -t option and the default output stream was modified to clarify that the output is written to standard output by default, unless the -t option is given. POSIX.1‐2008 allows this behavior, but leaves an opening for the more expected behavior of using standard error for diagnostics. Also, the System V behavior of writing the statistics when any table sizes are given is allowed, while BSD-derived systems can avoid it. The programmer can always precisely obtain the desired results by using either the -t or -n options.

The OPERANDS section does not mention the use of - as a synonym for standard input; not all historical implementations support such usage for any of the file operands.

A description of the translation table was deleted from early proposals because of its relatively low usage in historical applications.

The change to the definition of the input() function that allows buffering of input presents the opportunity for major performance gains in some applications.

The following examples clarify the differences between lex regular expressions and regular expressions appearing elsewhere in this volume of POSIX.1‐2017. For regular expressions of the form "r/x", the string matching r is always returned; confusion may arise when the beginning of x matches the trailing portion of r. For example, given the regular expression "a*b/cc" and the input "aaabcc", yytext would contain the string "aaab" on this match. But given the regular expression "x*/xy" and the input "xxxy", the token xxx, not xx, is returned by some implementations because xxx matches "x*".

In the rule "ab*/bc", the "b*" at the end of r extends r's match into the beginning of the trailing context, so the result is unspecified. If this rule were "ab/bc", however, the rule matches the text "ab" when it is followed by the text "bc". In this latter case, the matching of r cannot extend into the beginning of x, so the result is specified.
