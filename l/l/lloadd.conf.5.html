LLOADD.CONF(5) Manual de formatos de archivo LLOADD.CONF(5)

NOMBRE

lloadd.conf - archivo de configuración para lloadd, el demonio LDAP independiente

SINOPSIS

/etc/openldap/lloadd.conf

DESCRIPCIÓN

El archivo /etc/openldap/lloadd.conf contiene información de configuración para el demonio lloadd(8).

El archivo lloadd.conf consiste en una serie de opciones de configuración globales que se aplican a lloadd en su totalidad (incluyendo todos los backends), seguido de cero o más definiciones de backends que contienen información específica sobre cómo contactar una instancia de backend. Las opciones de configuración no distinguen entre mayúsculas y minúsculas; sus valores, caso por caso, pueden ser sensibles a mayúsculas y minúsculas.

El formato general de lloadd.conf es el siguiente:

    # comentario - estas opciones se aplican al servidor en su conjunto
    <opciones de configuración globales>
    # primera definición de backend
    backend-server <definición de backend 1>
    # definiciones de backend subsiguientes
    ...

Se pueden configurar tantos servidores de backend como se desee.

Si una línea comienza con espacio en blanco, se considera una continuación de la línea anterior. Ninguna línea física debe tener más de 2000 bytes de longitud.

Las líneas en blanco y las líneas de comentario que comienzan con un carácter `#` se ignoran. Nota: las líneas de continuación se desenrollan antes de aplicar el procesamiento de comentarios.

Los argumentos en las líneas de configuración están separados por espacios en blanco. Si un argumento contiene espacios en blanco, el argumento debe ir entre comillas dobles. Si un argumento contiene una comilla doble (`"') o un carácter de barra invertida (`\'), el carácter debe ir precedido por un carácter de barra invertida.

Las opciones de configuración específicas disponibles se discuten a continuación en Opciones de Configuración Global y Opciones Generales de Backend. Consulte la "Guía del Administrador de OpenLDAP" para obtener más detalles sobre el archivo de configuración de lloadd.

INTEGRACIÓN CON SLAPD

Tenga en cuenta que cuando lloadd está configurado como un módulo de slapd, cualquier opción que comparta el mismo nombre que una opción en slapd.conf(5), la interpretación de slapd prevalece y la opción lloadd mencionada no está disponible directamente a través de slapd.conf(5); en su lugar, tendría que configurarse a través de un atributo dedicado en cn=config. En particular, a menos que se establezca la opción TLSShareSlapdCTX, lloadd mantiene su propio contexto TLS que no se puede configurar excepto a través de la configuración dinámica.

Una opción adicional está disponible cuando se ejecuta como un módulo de slapd:

listen <URIs de escucha>
Las URIs en las que debe escuchar el módulo Balanceador de Carga. No deben solaparse con las que slapd utiliza para sus propios sockets de escucha. El atributo cn=config relacionado es olcBkLloadListen con cada URI proporcionada como un valor separado. Ningún cambio en este atributo realizado después de que el servidor se inicie tendrá efecto hasta que se reinicie.

OPCIONES DE CONFIGURACIÓN GLOBALES

Las opciones descritas en esta sección se aplican a todos los backends. Los argumentos que deben ser reemplazados por texto real se muestran entre corchetes <>.

argsfile <nombre_archivo>
El nombre (absoluto) de un archivo que contendrá la línea de comandos del servidor lloadd (nombre del programa y opciones).
concurrency <entero>
Especifica un nivel deseado de concurrencia. Se proporciona al sistema de hilos subyacente como una pista. El valor predeterminado es no proporcionar ninguna pista.
feature <característica> [...]
Activa características adicionales compatibles con el Balanceador de Carga LDAP. Las características compatibles son:
proxyauthz
al reenviar una operación, pasa la identidad autorizada del cliente usando el control de autorización proxy (RFC 4370). No se agrega ningún control a la operación si es iniciada por un cliente cuya identidad enlazada coincide con la identidad configurada en bindconf (no se intenta ninguna normalización del DN).

Si los enlaces SASL son emitidos por clientes y esta característica está habilitada, los servidores de backend necesitan admitir la operación extendida LDAP Who Am I? para que el Balanceador de Carga detecte la identidad de autorización correcta.

include <nombre_archivo>
Lee información de configuración adicional del archivo dado antes de continuar con la siguiente línea del archivo actual.
io-threads <entero>
Especifica el número de hilos a utilizar para el gestor de conexiones. El valor predeterminado es 1 y esto es típicamente adecuado para hasta 16 núcleos de CPU. El valor debe establecerse en una potencia de 2.

Si se modifica después de que el servidor se inicie, un cambio en esta opción no tendrá efecto hasta que el servidor se reinicie.

logfile <nombre_archivo>
Especifica un archivo para registrar mensajes de depuración de lloadd. Por defecto, estos mensajes solo van a stderr, no se registran en ningún otro lugar y no están relacionados con los mensajes expuestos por el
logfile-format debug | syslog-utc | syslog-localtime
Especifica el formato del prefijo para los mensajes escritos en el archivo de registro. El formato debug es el formato normal utilizado para los mensajes de depuración de slapd, con una marca de tiempo en hexadecimal, seguida de un ID de hilo. Las otras opciones son usar prefijos estilo syslog(3), con marcas de tiempo en UTC o en la zona horaria local. El valor predeterminado es el formato debug. Parámetro de configuración loglevel. Especificar un archivo de registro copia los mensajes a stderr y al archivo de registro.
logfile-only on | off
Especifica que los mensajes de depuración solo deben ir al archivo de registro configurado y no a stderr.
logfile-rotate <max> <Mbytes> <horas>
Especifica la rotación automática para el archivo de registro configurado como el número máximo de archivos de registro antiguos a conservar, un tamaño máximo en megabytes permitido para que un archivo de registro crezca antes de la rotación y una edad máxima en horas para que se use un archivo de registro antes de la rotación. El número máximo debe estar en el rango 1-99. Establecer Mbytes u horas a cero deshabilita la verificación de tamaño o edad, respectivamente. Al menos uno de Mbytes u horas debe ser distinto de cero. Por defecto, no se realizará ninguna rotación automática.
loglevel <entero> [...]
Especifica el nivel en el que se deben registrar los mensajes de depuración y las estadísticas de operaciones (actualmente registrados en la utilidad syslogd(8) LOG_LOCAL4). Deben considerarse subsistemas en lugar de niveles de registro cada vez más detallados. Algunos mensajes con mayor prioridad se registran independientemente del loglevel configurado tan pronto como se configura cualquier registro. Los niveles de registro son aditivos y los niveles disponibles son:
1
(0x1 trace) seguimiento de llamadas a funciones
2
(0x2 packets) depuración de manejo de paquetes
4
(0x4 args) depuración detallada (argumentos de función)
8
(0x8 conns) gestión de conexiones
16
(0x10 BER) imprimir paquetes enviados y recibidos
64
(0x40 config) procesamiento de archivo de configuración
256
(0x100 stats) conexiones, operaciones LDAP, resultados (recomendado)
512
(0x200 stats2) envío de entradas de registro de estadísticas
32768
(0x8000 none) solo mensajes que se registran independientemente del nivel de registro establecido
El nivel de registro deseado se puede introducir como un único entero que combine los niveles deseados (con OR), tanto en notación decimal como hexadecimal, como una lista de enteros (que se combinan con OR internamente), o como una lista de los nombres que se muestran entre paréntesis, de modo que 
    loglevel 5

LOGGING OPTIONS

The loglevel is controlled by the loglevel directive. The loglevel is specified as an integer value or as a keyword. Keywords are defined for convenience. The keywords are:

none
no messages are logged.
stat
statistics logging (default).
parse
message parsing.
args
operation arguments.
results
operation results.
shell
shell specific.
filter
filter specific.
access
access control.
stats
statistics logging.
conns
connection handling.
listener
listener specific.
config
configuration file parsing.
acl
acl specific.
proxy
proxy specific.
sync
replication.
parse_wrapping
argument parsing when wrapping backend operations.
trace
trace messages.
any
all messages.

The keywords can be combined using the bitwise OR operator (for example, stats|parse).

The numerical values are:

0x00000000 (0)
none
0x00000001 (1)
stats
0x00000002 (2)
parse
0x00000004 (4)
args
0x00000008 (8)
results
0x00000010 (16)
shell
0x00000020 (32)
filter
0x00000040 (64)
access
0x00000080 (128)
stats
0x00000100 (256)
conns
0x00000200 (512)
listener
0x00000400 (1024)
config
0x00000800 (2048)
acl
0x00001000 (4096)
proxy
0x00002000 (8192)
sync
0x00004000 (16384)
parse_wrapping
0x00008000 (32768)
trace
0xFFFFFFFF (-1)
any

The following examples are equivalent:

    loglevel 0x201
    loglevel 512 1
    loglevel 0x200 0x1
    loglevel stats trace

The keyword any can be used as a shortcut to enable logging at all levels (equivalent to -1). The keyword none, or the equivalent integer representation, causes those messages that are logged regardless of the configured loglevel to be logged. In fact, if loglevel is set to 0, no logging occurs, so at least the none level is required to have high priority messages logged.

The loglevel defaults to stats. This level should usually also be included when using other loglevels, to help analyze the logs.

pidfile <filename>
The (absolute) name of a file that will hold the lloadd server's process ID (see getpid(2)).
sockbuf_max_incoming_client <integer>
Specify the maximum LDAP PDU size accepted coming from clients. The default is 262143.
sockbuf_max_incoming_upstream <integer>
Specify the maximum LDAP PDU size accepted coming from upstream connections. The default is 4194303.
tcp-buffer [listener=<URL>] [{read|write}=]<size>
Specify the size of the TCP buffer. A global value for both read and write TCP buffers related to any listener is defined, unless the listener is explicitly specified, or either the read or write qualifiers are used. See tcp(7) for details. Note that some OS-es implement automatic TCP buffer tuning.
threads <integer>
Specify the maximum size of the primary thread pool. The default is 16; the minimum value is 2.
threadqueues <integer>
Specify the number of work queues to use for the primary thread pool. The default is 1 and this is typically adequate for up to 8 CPU cores. The value should not exceed the number of CPUs in the system.
max_pdus_per_cycle <integer>
If set to 0, PDUs are handled by the I/O threads directly, otherwise a task is queued to be picked up by the thread pool. This task will process PDUs from the connection until there is no more data to be read or this limit is reached when the I/O thread can pick it up again. Very high values have a potential to cause some connections to be starved in a very high-bandwidth environment. The default is 1000.
client_max_pending <integer>
Will cause the load balancer to limit the number unfinished operations for each client connection. The default is 0, unlimited.
iotimeout <integer>
Specify the number of milliseconds to wait before forcibly closing a connection with an outstanding write. This allows faster recovery from various network hang conditions. An iotimeout of 0 disables this feature. The default is 10000.
write_coherence <integer>
Specify the number of seconds after a write operation is finished that lloadd will direct operations exclusively to the last selected backend. A write operation is anything not handled internally (certain exops, abandon), except search, compare and bind operations. Bind operations also reset this restriction. The default is 0, write operations do not restrict selection. When negative, the restriction is not time limited and will persist until the next bind.
restrict_exop <OID> <action>
Tell lloadd that extended operation with a given OID should be handled in a specific way. OID 1.1 is special, setting a default (only for operations not handled internally). The meaning of the <action> argument is the same as in restrict_control below.
restrict_control <OID> <action>
Tell lloadd that a control with a given OID attached to any operation should be handled in a specific way according to the <action> argument. At the moment, only operations passed intact are inspected in this way, in particular, controls on bind and extended operations are not checked.

In order of descending priority (the control with highest priority action wins), this is the action made:

reject
operations that carry this control will be rejected.
connection
once an upstream is selected, every future operation from this client will be directed to the same connection. Useful when state is shared between client and upstream that the load balancer doesn't track.
backend
like write except this does not time out.
write
this is treated like a write operation (see write_coherence) above.
ignore
does not influence restrictions, useful when changing the global exop default. This is the default handling for exops/controls not handled by the load balancer internally.

TLS OPTIONS

If lloadd is built with support for Transport Layer Security, there are more options you can specify.

TLSShareSlapdCTX { on | off }
If set to no (the default), lloadd will use its own TLS context (needs to be configured via cn=config unless lloadd is run as a standalone daemon). If enabled, the options for slapd apply instead, since the slapd's TLS context is used then.

The following options are available only when compiled as a standalone daemon. When compiled as a slapd(8) module, the cn=config equivalents need to be used if a separate TLS context for the module is needed, otherwise use the TLSShareSlapdCTX option.

TLSCipherSuite <cipher-suite-spec>
Permits configuring what ciphers will be accepted and the preference order. <cipher-suite-spec> should be a cipher specification for the TLS library in use (OpenSSL, GnuTLS, or Mozilla NSS). Example:
OpenSSL:
TLSCipherSuite HIGH:MEDIUM:+SSLv2
GnuTLS:
TLSCiphersuite SECURE256:!AES-128-CBC

To check what ciphers a given spec selects in OpenSSL, use:

openssl ciphers -v <cipher-suite-spec>

With GnuTLS the available specs can be found in the manual page of gnutls-cli(1) (see the description of the option --priority).

In older versions of GnuTLS, where gnutls-cli does not support the option --priority, you can obtain the — more limited — list of ciphers by calling:

gnutls-cli -l

When using Mozilla NSS, the OpenSSL cipher suite specifications are used and translated into the format used internally by Mozilla NSS. There isn't an easy way to list the cipher suites from the command line. The authoritative list is in the source code for Mozilla NSS in the file sslinfo.c in the structure

        static const SSLCipherSuiteInfo suiteInfo[]
TLSCACertificateFile <filename>
Specifies the file that contains certificates for all of the Certificate Authorities that lloadd will recognize. The certificate for the CA that signed the server certificate must be included among these certificates. If the signing CA was not a top-level (root) CA, certificates for the entire sequence of CA's from the signing CA to the top-level CA should be present. Multiple certificates are simply appended to the file; the order is not significant.
TLSCACertificatePath <path>
Specifies the path of a directory that contains Certificate Authority certificates in separate individual files. Usually only one of this or the TLSCACertificateFile is used. This directive is not supported when using GnuTLS.

When using Mozilla NSS, <path> may contain a Mozilla NSS cert/key database. If <path> contains a Mozilla NSS cert/key database and CA cert files, OpenLDAP will use the cert/key database and will ignore the CA cert files.

TLSCertificateFile <filename>
Specifies the file that contains the lloadd server certificate.

When using Mozilla NSS, if using a cert/key database (specified with TLSCACertificatePath), TLSCertificateFile specifies the name of the certificate to use:

TLSCertificateFile Server-Cert
If using a token other than the internal built in token, specify the token name first, followed by a colon: 
TLSCertificateFile my hardware device:Server-Cert
Use certutil -L to list the certificates by name: 
certutil -d /path/to/certdbdir -L
TLSCertificateKeyFile <filename>
Specifies the file that contains the lloadd server private key that matches the certificate stored in the TLSCertificateFile file. Currently, the private key must not be protected with a password, so it is of critical importance that it is protected carefully.

When using Mozilla NSS, TLSCertificateKeyFile specifies the name of a file that contains the password for the key for the certificate s

especificado con TLSCertificateFile. El comando modutil se puede utilizar para desactivar la protección por contraseña de la base de datos de certificados/claves. Por ejemplo, si TLSCACertificatePath especifica /etc/openldap/certdb como la ubicación de la base de datos de certificados/claves, usa modutil para cambiar la contraseña a una cadena vacía:

modutil -dbdir /etc/openldap/certdb -changepw 'NSS Certificate DB'
Debes tener la contraseña antigua, si la hay. Ignora la ADVERTENCIA sobre el navegador en ejecución. Presiona 'Enter' para la nueva contraseña.
TLSDHParamFile <nombre archivo>
Esta directiva especifica el archivo que contiene los parámetros para el intercambio de claves efímeras Diffie-Hellman. Esto es necesario para poder utilizar un certificado DSA en el servidor, o un certificado RSA que carezca del uso de clave de "cifrado de clave". Ten en cuenta que la configuración de esta opción también puede habilitar los intercambios de claves Diffie-Hellman anónimos en ciertas suites de cifrado no predeterminadas. Generalmente se deben evitar los intercambios de claves anónimos, ya que no proporcionan autenticación real del cliente o servidor y no ofrecen protección contra ataques de tipo "man-in-the-middle". Debes añadir "&quot;!ADH&quot;" a tus suites de cifrado para asegurar que estas suites no se utilicen. Al usar Mozilla NSS, estos parámetros siempre se generan aleatoriamente, por lo que esta directiva se ignora.
TLSECName <nombre>
Especifica el nombre de una curva para usar en el intercambio de claves efímeras Diffie-Hellman de curva elíptica. Esto es necesario para habilitar los algoritmos ECDHE en OpenSSL. Esta opción no se usa con GnuTLS; las curvas pueden elegirse en la especificación de la suite de cifrado de GnuTLS. Esta opción también se ignora para Mozilla NSS.
TLSProtocolMin <mayor>[.<menor>]
Especifica la versión mínima del protocolo SSL/TLS que se negociará. Si el servidor no admite al menos esa versión, el handshake SSL fallará. Para requerir TLS 1.x o superior, establece esta opción a 3.(x+1), por ejemplo, 
TLSProtocolMin 3.2

requeriría TLS 1.1. Especificar un mínimo superior al admitido por la implementación de OpenLDAP resultará en que se requiera el nivel más alto que admite. Esta directiva se ignora con GnuTLS.

TLSRandFile <nombre archivo>
Especifica el archivo del que obtener bits aleatorios cuando /dev/[u]random no está disponible. Generalmente se establece en el nombre del socket EGD/PRNGD. La variable de entorno RANDFILE también se puede usar para especificar el nombre del archivo. Esta directiva se ignora con GnuTLS y Mozilla NSS.
TLSVerifyClient <nivel>
Especifica qué comprobaciones se realizan en los certificados del cliente en una sesión TLS entrante, si las hay. El &lt;nivel&gt; se puede especificar con una de las siguientes palabras clave:
never
Este es el valor predeterminado. lloadd no solicitará un certificado al cliente.
allow
Se solicita el certificado del cliente. Si no se proporciona ningún certificado, la sesión continúa normalmente. Si se proporciona un certificado inválido, se ignorará y la sesión continuará normalmente.
try
Se solicita el certificado del cliente. Si no se proporciona ningún certificado, la sesión continúa normalmente. Si se proporciona un certificado inválido, la sesión se termina inmediatamente.
demand | hard | true
Estas palabras clave son todas equivalentes, por motivos de compatibilidad. Se solicita el certificado del cliente. Si no se proporciona ningún certificado, o se proporciona un certificado inválido, la sesión se termina inmediatamente.
TLSCRLCheck <nivel>
Especifica si la Lista de Revocación de Certificados (CRL) de la CA debe utilizarse para verificar si los certificados de los clientes no han sido revocados. Esto requiere que el parámetro TLSCACertificatePath esté configurado. Esta directiva se ignora con GnuTLS y Mozilla NSS. El &lt;nivel&gt; se puede especificar con una de las siguientes palabras clave:
none
No se realizan comprobaciones de CRL.
peer
Comprueba la CRL del certificado del par.
all
Comprueba la CRL de toda la cadena de certificados.
TLSCRLFile <nombre archivo>
Especifica un archivo que contiene una Lista de Revocación de Certificados que se utilizará para verificar que los certificados no han sido revocados. Esta directiva solo es válida cuando se utilizan GnuTLS y Mozilla NSS.

CONFIGURACIÓN DEL BACKEND

Las opciones en esta sección describen cómo lloadd se conecta y autentica a los servidores backend. Los backends se organizan en grupos (tiers). Los backends en el primer tier se intentan primero; si ninguno de ellos es accesible, se intenta el siguiente tier de la misma manera. Si hay un backend en el tier que tiene conexiones adecuadas, pero están ocupadas, no se consulta ningún tier adicional. Esto es útil en escenarios de alta disponibilidad donde se debe contactar a un grupo de servidores (por ejemplo, el entorno local) si es posible.

Se asume que todos los servidores backend sirven los mismos datos. Al inicio, se configuran las conexiones y las que no están dedicadas a manejar solicitudes de bind se autentican con el backend utilizando la información en la opción bindconf. La configuración de autenticación se comparte entre ellas.

bindconf
[bindmethod=simple|sasl] [binddn=&lt;dn&gt;] [saslmech=&lt;mech&gt;] [authcid=&lt;identidad&gt;] [authzid=&lt;identidad&gt;] [credentials=&lt;passwd&gt;] [realm=&lt;realm&gt;] [secprops=&lt;propiedades&gt;] [timeout=&lt;segundos&gt;] [network-timeout=&lt;segundos&gt;] [keepalive=&lt;inactivo&gt;:&lt;sondeos&gt;:&lt;intervalo&gt;] [tcp-user-timeout=&lt;milisegundos&gt;] [tls_cert=&lt;archivo&gt;] [tls_key=&lt;archivo&gt;] [tls_cacert=&lt;archivo&gt;] [tls_cacertdir=&lt;ruta&gt;] [tls_reqcert=never|allow|try|demand] [tls_cipher_suite=&lt;cifrados&gt;] [tls_crlcheck=none|peer|all] [tls_protocol_min=&lt;mayor&gt;[.&lt;menor&gt;]]

Especifica las credenciales de bind que lloadd usa al establecer sus conexiones regulares a todos los backends.

Un bindmethod de simple requiere las opciones binddn y credentials y solo debe usarse cuando existan servicios de seguridad adecuados (por ejemplo, TLS o IPSEC). ¡RECUERDA: las credenciales de bind simple deben estar en texto plano! Un bindmethod de sasl requiere la opción saslmech. Dependiendo del mecanismo, se puede especificar una identidad de autenticación y/o credenciales usando authcid y credentials. El parámetro authzid se puede usar para especificar una identidad de autorización. Las propiedades de seguridad específicas (como con la palabra clave sasl-secprops anterior) para un bind SASL se pueden establecer con la opción secprops. Un reino SASL no predeterminado se puede establecer con la opción realm.

El parámetro timeout indica cuánto tiempo puede estar pendiente una operación de respuesta (resultado, entrada de búsqueda, ...) del servidor en segundos. Debido a cómo se detectan los tiempos de espera, el tiempo de espera podría no detectarse y manejarse hasta timeout segundos después de que ocurra.

El parámetro network-timeout establece cuánto tiempo esperará el consumidor para establecer una conexión de red con el proveedor. Una vez establecida la conexión, el parámetro timeout determina cuánto tiempo esperará el consumidor para que se complete la solicitud Bind inicial.

Un tiempo de espera establecido en 0 significa que no hay tiempo de espera y, de forma predeterminada, no hay tiempos de espera.

El parámetro keepalive establece los valores de idle, probes e interval utilizados para comprobar si un socket está activo; idle es el número de segundos que una conexión debe permanecer inactiva antes de que TCP comience a enviar sondas de keepalive; probes es el número máximo de sondas de keepalive que TCP debe enviar antes de descartar la conexión; interval es el intervalo en segundos entre sondas de keepalive individuales. Solo algunos sistemas admiten la personalización de estos valores; de lo contrario, el parámetro keepalive se ignora y se utilizan los ajustes a nivel de sistema.

El parámetro tcp-user-timeout, si no es cero, corresponde a TCP_USER_TIMEOUT establecido en las conexiones upstream, anulando la configuración del sistema operativo. Solo algunos sistemas admiten la personalización de este parámetro; de lo contrario, se ignora y se utilizan los ajustes a nivel de sistema.

OPCIONES DE TIER

tier
&lt;tipo de tier&gt;

Agrupa servidores que deben considerarse en el mismo intento. Si se encuentra una conexión viable, incluso si está ocupada, el balanceador de carga no procede al siguiente tier. El proceso de selección de una conexión dentro de un tier depende del tipo del tier.


Los tipos disponibles son:

roundrobin
Los servidores se intentan en orden y si uno se selecciona correctamente, la siguiente búsqueda intentará desde el siguiente en la lista.
weighted
Los servidores backend aceptan una nueva opción weight=&lt;int&gt; que indica con qué frecuencia deben seleccionarse. Si no se especifica, el peso predeterminado es 0 y dichos backends tienen una ligera posibilidad de ser seleccionados incluso cuando se configura un backend con peso distinto de cero en el tier. El proceso de selección sigue la línea de RFC2782.

lloadd.conf(5) — OpenLDAP 2.6.10

NAME

lloadd.conf — load balancer configuration file

SYNOPSIS

/etc/openldap/lloadd.conf

DESCRIPTION

The lloadd(8) load balancer uses a configuration file to determine how to proxy LDAP requests to a pool of backend LDAP servers.

The configuration file is divided into several sections, each defined by keywords. Blank lines and lines starting with '#' are ignored.

SLAPD INTEGRATION

The lloadd load balancer can be used in conjunction with slapd(8) to provide load balancing, failover, and high-availability for LDAP services. It acts as a proxy, accepting client connections and forwarding requests to one or more backend LDAP servers.

GLOBAL CONFIGURATION OPTIONS

argsfile file
Specifies the file containing command line arguments for lloadd. This is useful for managing runtime configurations.
pidfile file
Specifies the file where the process ID (PID) of the running lloadd daemon will be written. This is essential for managing the daemon process.
restrict_exop oid [accept|reject|connection|request|authenticate]
Controls the proxying of extended operations (Exops). You can specify an object identifier (OID) and an action to take when that Exop is encountered. The default is to reject all Exops.
restrict_control oid [accept|reject|connection|request|authenticate]
Controls the proxying of LDAP controls. Similar to restrict_exop, but for controls. The default is to reject all controls.
bindconf
Specifies the method for how lloadd itself binds to the backend LDAP servers. This section contains keywords such as:
bindmethod=method
The authentication method. Supported methods include simple.
binddn=binddn
The distinguished name (DN) to use for binding to the backend servers.
credentials=password
The password corresponding to the binddn.

TLS OPTIONS

Global TLS options can be set to configure secure connections between lloadd and the backend servers.

tls_cert file
Path to the server certificate file.
tls_key file
Path to the server private key file.
tls_cafile file
Path to the CA certificate file.
tls_cacertdir dir
Path to a directory containing CA certificates.
tls_reqcert demand|allow|try|never
Specifies whether a certificate is required from the server. demand (default) requires a valid certificate. allow allows anonymous connections if the server doesn't offer a certificate. try attempts to get a certificate but proceeds if none is available. never disables certificate checking.
tls_cipher cipherlist
Specifies the list of allowable TLS ciphers.

BACKEND CONFIGURATION

This section defines the backend LDAP servers that lloadd will use.

TIER OPTIONS

tier type
Defines the load balancing strategy for the subsequent backends. Supported types include:
weighted
Backends are selected based on their assigned weights. A higher weight means a higher probability of being selected. This is the default tier type.
round-robin
Backends are selected in a simple round-robin fashion, regardless of weights.
source-affinity
Attempts to direct requests from the same source IP address to the same backend server consistently. If the server becomes unavailable, another server is chosen.
least-loaded
The backend with the fewest active connections is chosen. If multiple backends have the same load, the weighted strategy is used as a tie-breaker. If weights are equal, a backend is chosen based on its position in the configuration file.
lowest-latency
The backend with the lowest measured latency is tried first. If the backend is not available (or is busy), the other backend is tried, then backends are chosen in a round-robin order.

Note that unlike weighted, the higher the weight, the higher the "effective" latency and lower the chance a backend is selected.

BACKEND OPTIONS

backend-server
uri=ldap[s]://<hostname>[:port] [retry=<retry interval in ms>] [starttls=yes|critical] [numconns=<conns>] [bindconns=<conns>] [max-pending-ops=<ops>] [conn-max-pending=<ops>]

Marks the beginning of a backend definition.

uri specifies the backend as an LDAP URI. If <port> is not given, the standard LDAP port number (389 or 636) is used.

Lloadd will attempt to maintain numconns active connections and also bindconns active connections dedicated to handling client bind requests.

If an error occurs on a working connection, a new connection attempt is made immediately, if one happens on establishing a new connection to this backend, lloadd will wait before a new reconnect attempt is made according to the retry parameter (default is 5 seconds).

Operations will be distributed across the backend's connections (upstreams).

The parameter conn-max-pending unless set to 0 (the default), will limit the number unfinished operations per upstream connection. Similarly, max-pending-ops will limit the total number or unfinished operations across all backend's connections, 0, the default, means no limit will be imposed for this backend.

The starttls parameter specifies use of the StartTLS extended operation to establish a TLS session before Binding to the provider. If the critical argument is supplied, the session will be aborted if the StartTLS request fails. Otherwise the syncrepl session continues without TLS. The tls_reqcert setting defaults to "demand" and the other TLS settings default to the same as the main slapd TLS settings.

EXAMPLES

Here is a short example of a configuration file:

argsfile  /var/lib/openldap/run/lloadd.args
pidfile   /var/lib/openldap/run/lloadd.pid
# cancel not supported yet
restrict_exop 1.3.6.1.1.8 reject
# turn not supported
restrict_exop 1.3.6.1.1.19 reject
# TXN Exop if desired, otherwise reject
restrict_exop 1.3.6.1.1.21.1 connection
# Paged results control
restrict_control 1.2.840.113556.1.4.319 connection
# VLV control
restrict_control 2.16.840.1.113730.3.4.9 connection
bindconf
    bindmethod=simple
    binddn=cn=test
    credentials=pass
tier weighted
backend-server
    uri=ldap://ldap1.example.com
    numconns=3
    bindconns=2
    retry=5000
    max-pending-ops=5
    conn-max-pending=3
    weight=5
backend-server
    uri=ldap://ldap2.example.com
    numconns=3
    bindconns=2
    retry=5000
    max-pending-ops=5
    conn-max-pending=3
    weight=10

"OpenLDAP Administrator's Guide" contains a longer annotated example of a configuration file. The original /etc/openldap/lloadd.conf is another example.

LIMITATIONS

Support for proxying SASL Binds is limited to the EXTERNAL mechanism (and only to extract the DN of a client TLS certificate if used during the last renegotiation) and mechanisms that rely neither on connection metadata (as Kerberos does) nor establish a SASL integrity/confidentialiy layer (again, some Kerberos mechanisms, DIGEST-MD5 can negotiate this).
