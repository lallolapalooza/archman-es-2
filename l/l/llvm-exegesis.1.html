NOMBRE

llvm-exegesis - Benchmark de Instrucciones de Máquina de LLVM

SINOPSIS

llvm-exegesis [opciones]

DESCRIPCIÓN

llvm-exegesis es una herramienta de benchmarking que utiliza la información disponible en LLVM para medir características de las instrucciones de la máquina host, como latencia, rendimiento o descomposición de puertos.

Dado un nombre de opcode de LLVM y un modo de benchmarking, llvm-exegesis genera un fragmento de código que hace que la ejecución sea lo más serial (o paralela) posible para que podamos medir la latencia (o el rendimiento inverso/descomposición de microoperaciones) de la instrucción. El fragmento de código se compila Just-In-Time (JIT) y, a menos que se solicite lo contrario, se ejecuta en el subtarget del host. El tiempo empleado (o el uso de recursos) se mide utilizando contadores de rendimiento del hardware. El resultado se imprime en formato YAML a la salida estándar.

El objetivo principal de esta herramienta es validar (o invalidar) automáticamente los modelos de planificación TableDef de LLVM. Para ello, también proporcionamos análisis de los resultados.

llvm-exegesis también puede evaluar fragmentos de código arbitrarios proporcionados por el usuario.

PLATAFORMAS SOPORTADAS

Actualmente, llvm-exegesis solo soporta X86 (solo 64 bits), ARM (solo AArch64, la generación de fragmentos es escasa), MIPS, PowerPC (solo PowerPC64LE) y RISC-V (RV64I/E y RV32I/E) en Linux para benchmarking. No se garantiza que toda la funcionalidad de benchmarking funcione en todas las plataformas. llvm-exegesis también tiene un modo de análisis separado que es compatible con todas las plataformas en las que está LLVM.

Para habilitar el benchmarking en llvm-exegesis, LLVM debe estar configurado y compilado con LLVM_ENABLE_LIBPFM habilitado, ya que llvm-exegesis depende de libpfm4 para acceder a los contadores de rendimiento. El benchmarking puede fallar si la CPU de destino no es compatible con libpfm. Esto se puede verificar estableciendo las variables de entorno LIBPFM_VERBOSE y LIBPFM_DEBUG para habilitar el modo detallado o de depuración para libpfm. Si libpfm está instalado en un directorio no estándar, LLVM puede configurarse para localizar los archivos de biblioteca y encabezado necesarios estableciendo las variables de entorno LIBRARY_PATH, C_INCLUDE_PATH y CPLUS_INCLUDE_PATH. Adicionalmente, LD_LIBRARY_PATH debe ser establecido para que llvm-exegesis pueda localizar la biblioteca libpfm durante la ejecución.

ANOTACIONES DE FRAGMENTOS

llvm-exegesis soporta la evaluación de fragmentos de ensamblado arbitrarios. Sin embargo, la evaluación de estos fragmentos a menudo requiere alguna configuración para que puedan ejecutarse correctamente. llvm-exegesis tiene cinco anotaciones y algunas utilidades adicionales para ayudar con la configuración, de modo que los fragmentos puedan ser evaluados correctamente.

  • LLVM-EXEGESIS-DEFREG <nombre del registro> - Añadir esta anotación al fragmento de ensamblado de texto a evaluar marca el registro como que requiere una definición. Se proporcionará automáticamente un valor a menos que se pase un segundo parámetro, un valor hexadecimal. Esto se hace con el formato LLVM-EXEGESIS-DEFREG <nombre del registro> <valor hexadecimal>. <valor hexadecimal> es un patrón de bits utilizado para llenar el registro. Si es un valor menor que el registro, se extiende con signo para que coincida con el tamaño del registro.
  • LLVM-EXEGESIS-LIVEIN <nombre del registro> - Esta anotación permite especificar registros que deben conservar su valor al iniciar el benchmark. Los valores se pueden pasar a través de registros desde la configuración del benchmark en algunos casos. Los registros y los valores asignados a ellos que se pueden utilizar en el script de benchmarking con un LLVM-EXEGESIS-LIVEIN son los siguientes:
•
Registro de memoria temporal - El registro específico en el que se coloca este valor depende de la plataforma (por ejemplo, es el registro RDI en X86 Linux). Establecer este registro como live in asegura que se coloca un puntero a un bloque de memoria (1MB) dentro de este registro que puede ser utilizado por el fragmento.
  • LLVM-EXEGESIS-MEM-DEF <nombre del valor> <tamaño> <valor> - Esta anotación permite especificar definiciones de memoria que luego pueden ser mapeadas en el proceso de ejecución de un fragmento con la anotación LLVM-EXEGESIS-MEM-MAP. Cada valor se nombra utilizando el argumento <nombre del valor> para que pueda ser referenciado posteriormente dentro de una anotación de mapa. El tamaño se especifica en un número decimal de bytes y el valor se proporciona en hexadecimal. Si el tamaño del valor es menor que el tamaño especificado, el valor se repetirá hasta llenar toda la sección de memoria. El uso de esta anotación requiere el modo de ejecución de subprocesos.
  • LLVM-EXEGESIS-MEM-MAP <nombre del valor> <dirección> - Esta anotación permite mapear definiciones de memoria previamente definidas en el contexto de ejecución de un proceso. El nombre del valor hace referencia a una definición de memoria previamente definida y la dirección es un número decimal que especifica la dirección en la que debe comenzar la definición de memoria. Tenga en cuenta que una única definición de memoria puede ser mapeada múltiples veces. El uso de esta anotación requiere el modo de ejecución de subprocesos.
  • LLVM-EXEGESIS-SNIPPET-ADDRESS <dirección> - Esta anotación permite establecer la dirección en la que se mapeará el principio del fragmento a ejecutar. La dirección se proporciona en hexadecimal. Tenga en cuenta que el fragmento también incluye código de configuración, por lo que la instrucción exactamente en la dirección especificada no será la primera instrucción del fragmento. El uso de esta anotación requiere el modo de ejecución de subprocesos. Esto es útil en casos donde la memoria accedida por el fragmento depende de la ubicación del fragmento, como el direccionamiento relativo a RIP.
  • LLVM-EXEGESIS-LOOP-REGISTER <nombre del registro> - Esta anotación especifica el registro de bucle a utilizar para llevar la cuenta de la iteración actual cuando se utiliza el modo de repetición de bucle. llvm-exegesis necesita llevar la cuenta de la iteración de bucle actual dentro del modo de repetición de bucle de manera eficiente (es decir, sin accesos a memoria), y utiliza un registro para hacer esto. Este registro tiene un valor predeterminado específico de la arquitectura (por ejemplo, R8 en X86), pero esto puede entrar en conflicto con algunos fragmentos. Esta anotación permite cambiar el registro para evitar interferencias entre el registro índice del bucle y el fragmento.

EJEMPLO 1: EVALUACIÓN DE INSTRUCCIONES

Supongamos que tiene una máquina X86-64. Para medir la latencia de una sola instrucción, ejecute:

$ llvm-exegesis --mode=latency --opcode-name=ADD64rr

Medir la descomposición de microoperaciones o el rendimiento inverso de una instrucción funciona de manera similar:

$ llvm-exegesis --mode=uops --opcode-name=ADD64rr
$ llvm-exegesis --mode=inverse_throughput --opcode-name=ADD64rr

La salida es un documento YAML (el valor predeterminado es escribir en stdout, pero puede redirigir la salida a un archivo usando --benchmarks-file):

---
key:
  opcode_name:     ADD64rr
  mode:            latency
  config:          ''
cpu_name:        haswell
llvm_triple:     x86_64-unknown-linux-gnu
num_repetitions: 10000
measurements:
  - { key: latency, value: 1.0058, debug_string: '' }
error:           ''
info:            'explicit self cycles, selecting one aliasing configuration.
Snippet:
ADD64rr R8, R8, R10
'
...

Para medir la latencia de todas las instrucciones para la arquitectura host, ejecute:

$ llvm-exegesis --mode=latency --opcode-index=-1

EJEMPLO 2: EVALUACIÓN DE UN FRAGMENTO DE CÓDIGO PERSONALIZADO

Para medir la latencia/microoperaciones de un fragmento de código personalizado, puede especificar la opción snippets-file (- lee desde la entrada estándar).

$ echo "vzeroupper" | llvm-exegesis --mode=uops --snippets-file=-

Los fragmentos de código del mundo real típicamente dependen de registros o memoria. llvm-exegesis comprueba la vivacidad de los registros (es decir, cualquier uso de registro tiene una definición correspondiente o es un "live in"). Si su código depende del valor de algunos registros, necesita usar anotaciones de fragmento para asegurar que la configuración se realice correctamente.

">Por ejemplo, el siguiente fragmento de código depende de los valores de XMM1 (que será establecido por la herramienta) y del búfer de memoria pasado en RDI (en vivo).

# LLVM-EXEGESIS-LIVEIN RDI
# LLVM-EXEGESIS-DEFREG XMM1 42
vmulps        (%rdi), %xmm1, %xmm2
vhaddps       %xmm2, %xmm2, %xmm3
addq $0x10, %rdi

EJEMPLO 3: BENCHMARKING CON ANOTACIONES DE MEMORIA

Algunos fragmentos requieren configuración de memoria en lugares específicos para ejecutarse sin fallar. La configuración de memoria se puede lograr con las anotaciones LLVM-EXEGESIS-MEM-DEF y LLVM-EXEGESIS-MEM-MAP. Para ejecutar el siguiente fragmento:

movq $8192, %rax
movq (%rax), %rdi

Necesitamos tener al menos ocho bytes de memoria asignados comenzando en 0x2000. Podemos crear el entorno de ejecución necesario con las siguientes anotaciones añadidas al fragmento:

# LLVM-EXEGESIS-MEM-DEF test1 4096 7fffffff
# LLVM-EXEGESIS-MEM-MAP test1 8192
movq $8192, %rax
movq (%rax), %rdi

EJEMPLO 4: ANÁLISIS

Suponiendo que tiene un conjunto de instrucciones benchmarkeadas (latencia o uops) en formato YAML en el archivo /tmp/benchmarks.yaml, puede analizar los resultados utilizando el siguiente comando:

  $ llvm-exegesis --mode=analysis \
--benchmarks-file=/tmp/benchmarks.yaml \
--analysis-clusters-output-file=/tmp/clusters.csv \
--analysis-inconsistencies-output-file=/tmp/inconsistencies.html

Esto agrupará las instrucciones en clusters con las mismas características de rendimiento. Los clusters se escribirán en /tmp/clusters.csv en el siguiente formato:

cluster_id,opcode_name,config,sched_class
...
2,ADD32ri8_DB,,WriteALU,1.00
2,ADD32ri_DB,,WriteALU,1.01
2,ADD32rr,,WriteALU,1.01
2,ADD32rr_DB,,WriteALU,1.00
2,ADD32rr_REV,,WriteALU,1.00
2,ADD64i32,,WriteALU,1.01
2,ADD64ri32,,WriteALU,1.01
2,MOVSX64rr32,,BSWAP32r_BSWAP64r_MOVSX64rr32,1.00
2,VPADDQYrr,,VPADDBYrr_VPADDDYrr_VPADDQYrr_VPADDWYrr_VPSUBBYrr_VPSUBDYrr_VPSUBQYrr_VPSUBWYrr,1.02
2,VPSUBQYrr,,VPADDBYrr_VPADDDYrr_VPADDQYrr_VPADDWYrr_VPSUBBYrr_VPSUBDYrr_VPSUBQYrr_VPSUBWYrr,1.01
2,ADD64ri8,,WriteALU,1.00
2,SETBr,,WriteSETCC,1.01
...

llvm-exegesis también analizará los clusters para señalar inconsistencias en la información de programación. La salida es un archivo html. Por ejemplo, /tmp/inconsistencies.html contendrá mensajes como los siguientes: [imagen]

Tenga en cuenta que los nombres de las clases de programación solo se resolverán cuando llvm-exegesis se compile en modo de depuración; de lo contrario, solo se mostrará el ID de la clase. Sin embargo, esto no invalida ninguno de los resultados del análisis.

OPCIONES

--help
Imprimir un resumen de las opciones de línea de comandos.
--opcode-index=<índice de opcode de LLVM>
Especificar el opcode a medir, por índice. Especificar -1 resultará en la medición de todos los opcodes existentes. Ver el ejemplo 1 para más detalles. Se debe establecer opcode-index, opcode-name o snippets-file.
--opcode-name=<nombre de opcode 1>,<nombre de opcode 2>,...
Especificar el opcode a medir, por nombre. Se pueden especificar varios opcodes como una lista separada por comas. Ver el ejemplo 1 para más detalles. Se debe establecer opcode-index, opcode-name o snippets-file.
--snippets-file=<nombre de archivo>
Especificar el fragmento de código personalizado a medir. Ver el ejemplo 2 para más detalles. Se debe establecer opcode-index, opcode-name o snippets-file.
--mode=[latency|uops|inverse_throughput|analysis]
Especificar el modo de ejecución. Tenga en cuenta que algunos modos tienen requisitos y opciones adicionales.

El modo latency puede utilizar RDTSC o LBR. latency[LBR] solo está disponible en X86 (al menos Skylake). Para ejecutar en modo latency, se debe especificar un valor positivo para x86-lbr-sample-period y --repetition-mode=loop.

En modo analysis, también necesita especificar al menos uno de los argumentos -analysis-clusters-output-file= y -analysis-inconsistencies-output-file=.

--benchmark-phase=[prepare-snippet|prepare-and-assemble-snippet|assemble-measured-code|measure]
Por defecto, cuando se especifica -mode=, el fragmento generado se ejecutará y medirá, y esto requiere que estemos ejecutando en el hardware para el que se generó el fragmento, y que admita mediciones de rendimiento. Sin embargo, es posible detenerse en alguna etapa antes de medir. Las opciones son: * prepare-snippet: Solo generar la secuencia de instrucciones mínima. * prepare-and-assemble-snippet: Igual que prepare-snippet, pero también vuelca una parte de la secuencia (codificada en hexadecimal). * assemble-measured-code: Igual que prepare-and-assemble-snippet, pero también crea la secuencia completa que se puede volcar a un archivo usando --dump-object-to-disk. * measure: Igual que assemble-measured-code, pero también ejecuta la medición.
--x86-lbr-sample-period=<nRamas/muestra>
Especificar el período de muestreo de LBR - cuántas ramas antes de tomar una muestra. Cuando se especifica un valor positivo para esta opción y cuando el modo es latency, utilizaremos LBR para medir. Al elegir el período de muestreo "correcto", se prefiere un valor pequeño, pero puede haber estrangulamiento si el muestreo es demasiado frecuente. Se debe utilizar un número primo para evitar omitir consistentemente ciertos bloques.
--x86-disable-upper-sse-registers
El uso de los registros xmm superiores (xmm8-xmm15) fuerza una codificación de instrucción más larga que puede ejercer una mayor presión en las etapas de fetch y decode del frontend, lo que potencialmente reduce la tasa a la que se despachan las instrucciones al backend, especialmente en hardware más antiguo. Comparar los resultados base con este modo habilitado puede ayudar a determinar los efectos del frontend y se puede utilizar para mejorar las estimaciones de latencia y rendimiento.
--repetition-mode=[duplicate|loop|min|middle-half-duplicate|middle-half-loop]
Especificar el modo de repetición. duplicate creará un bloque básico grande y lineal con min-instructions instrucciones (repitiendo el fragmento min-instructions/tamaño del fragmento veces). loop, opcionalmente, duplicará el fragmento hasta que el cuerpo del bucle contenga al menos loop-body-size instrucciones, y luego envolverá el resultado en un bucle que ejecutará min-instructions instrucciones (por lo tanto, de nuevo, repitiendo el fragmento min-instructions/tamaño del fragmento veces). El modo loop, especialmente con desenrollado de bucle, tiende a ocultar mejor los efectos del frontend de la CPU en arquitecturas que almacenan en caché las instrucciones decodificadas, pero consume un registro para contar iteraciones. Si se realiza un análisis sobre muchos opcodes, puede ser mejor utilizar en su lugar el modo min, que ejecutará cada modo, y producirá el resultado medido mínimo. Los modos de repetición de la mitad del medio duplicarán o ejecutarán el fragmento en un bucle dependiendo del modo específico. Los modos de repetición de la mitad del medio ejecutarán dos benchmarks, uno con el doble de longitud que el primero, y luego restarán la diferencia entre ellos para obtener valores sin sobrecarga.
--min-instructions=<Número de instrucciones>
Especificar el número objetivo de instrucciones ejecutadas. Tenga en cuenta que la repetición real del fragmento será min-instructions/tamaño del fragmento. Valores más altos conducen a mediciones más precisas pero alargan el benchmark.
--loop-body-size=<Tamaño preferido del cuerpo del bucle>
Solo efectivo para -repetition-mode=[loop|min]. En lugar de hacer un bucle sobre el fragmento directamente, primero duplíquelo para que el cuerpo del bucle contenga al menos esta cantidad de instrucciones. Esto potencialmente resulta en que el cuerpo del bucle se almacene en caché en la Op Cache / Loop Cache de la CPU, lo que permite un rendimiento potencialmente mayor que el de los decodificadores de la CPU.
--max-configs-per-opcode=<valor>
Especificar el número máximo de configuraciones que se pueden generar para cada opcode. Por defecto es 1, lo que significa que asumimos que una sola medición es suficiente para caracterizar un opcode. Esto podría no ser cierto para todas las instrucciones: por ejemplo, las características de rendimiento de la instrucción LEA en X86 dependen del valor de los registros y constantes asignados. Establecer un valor de -max-configs-per-opcode mayor que 1 permite a llvm-exegesis explorar más configuraciones para descubrir si algunas asignaciones de registros o constantes conducen a diferentes características de rendimiento.
--benchmarks-file=</ruta/al/archivo>
Archivo para leer (modo analysis) o escribir (modos latency/uops/inverse_throughput) resultados de benchmark. "-" usa stdin/stdout.
--analysis-clusters-output-file=</ruta/al/archivo>
Si se proporciona, escribe los clusters de análisis como CSV en este archivo. "-" imprime en stdout. Por defecto, este análisis no se ejecuta.

OPTIONS

--analysis-inconsistencies-output-file=</ruta/al/archivo>
Si no está vacío, escribe las inconsistencias encontradas durante el análisis en este archivo. - imprime en stdout. Por defecto, este análisis no se ejecuta.
--analysis-filter=[all|reg-only|mem-only]
Por defecto, se analizan todos los resultados de los benchmarks, pero a veces puede ser útil observar solo aquellos que no involucran memoria, o viceversa. Esta opción permite mantener todos los benchmarks, o filtrar (ignorar) todos los que involucran memoria (instrucciones que pueden leer o escribir en memoria), o lo contrario, mantener solo dichos benchmarks.
--analysis-clustering=[dbscan,naive]
Especifica el algoritmo de clustering a utilizar. Por defecto se usará DBSCAN. El algoritmo de clustering ingenuo es mejor para realizar trabajos adicionales en el archivo de salida de -analysis-inconsistencies-output-file=, creará un cluster por opcode y verificará que el cluster sea estable (todos los puntos son vecinos).
--analysis-numpoints=<parámetro numPoints de dbscan>
Especifica el parámetro numPoints a utilizar para el clustering DBSCAN (modo analysis, solo DBSCAN).
--analysis-clustering-epsilon=<parámetro epsilon de dbscan>
Especifica el parámetro epsilon utilizado para el clustering de los puntos del benchmark (modo analysis).
--analysis-inconsistency-epsilon=<epsilon>
Especifica el parámetro epsilon utilizado para la detección de cuándo el cluster es diferente de los valores del perfil de programación de LLVM (modo analysis).
--analysis-display-unstable-clusters
Si hay más de un benchmark para un opcode, dichos benchmarks pueden terminar sin agruparse en el mismo cluster si las características de rendimiento medidas son diferentes. Por defecto, todos esos opcodes se filtran. Esta bandera mostrará en su lugar solo dichos opcodes inestables.
--ignore-invalid-sched-class=false
Si se establece, ignora las instrucciones que no tienen una clase de programación (índice de clase = 0).
--mtriple=<nombre del triple>
Triple de destino. Consulte -version para ver los objetivos disponibles.
--mcpu=<nombre del cpu>
Si se establece, mide las características de la CPU utilizando los contadores para esta CPU. Esto es útil al crear nuevos modelos de programación (la CPU host es desconocida para LLVM). (-mcpu=help para detalles)
--analysis-override-benchmark-triple-and-cpu
Por defecto, llvm-exegesis analizará los benchmarks para el triple/CPU con los que fueron medidos, pero si desea analizarlos para alguna otra combinación (especificada a través de -mtriple/-mcpu), puede pasar esta bandera.
--dump-object-to-disk=<nombre de archivo>
Si se establece, llvm-exegesis volcará el código generado a un archivo temporal para permitir la inspección del código. Deshabilitado por defecto.
--use-dummy-perf-counters
Si se establece, llvm-exegesis no leerá ningún contador de rendimiento real y devolverá un valor ficticio en su lugar. Esto se puede usar para asegurar que un fragmento no cause un error cuando los contadores de rendimiento del hardware no están disponibles y para depurar llvm-exegesis en sí mismo.
--execution-mode=[inprocess,subprocess]
Esta opción especifica el modo de ejecución a utilizar. El modo de ejecución inprocess es el predeterminado. El modo de ejecución subprocess permite funcionalidades adicionales como anotaciones de memoria, pero actualmente está restringido a X86-64 en Linux.
--benchmark-repeat-count=<recuento-de-repetición>
Esta opción permite especificar el número de veces que se repetirá la medición al realizar mediciones de latencia. Por defecto, llvm-exegesis repetirá una medición de latencia suficientes veces para equilibrar el tiempo de ejecución y la reducción de ruido.
--validation-counter=[instructions-retired,l1d-cache-load-misses,
l1d-cache-store-misses,l1i-cache-load-misses,data-tlb-load-misses,
data-tld-store-misses,instruction-tlb-load-misses]
Esta opción permite el uso de contadores de validación, que miden eventos microarquitectónicos adicionales como fallos de caché para validar las condiciones de ejecución de fragmentos. Estos eventos se miden utilizando el subsistema perf en un grupo con el contador de rendimiento utilizado para medir el valor de interés. Esta bandera se puede especificar varias veces para medir múltiples eventos. El número máximo de contadores de validación depende de la plataforma.
--benchmark-process-cpu=<id de cpu>
Esta opción especifica el número de CPU que se debe utilizar para ejecutar el subproceso de benchmarking. Al iniciar el subproceso, llvm-exegesis establecerá la afinidad del subproceso para que solo incluya la CPU especificada. Esta opción solo funciona en el modo de ejecución de subproceso.

ESTADO DE SALIDA

llvm-exegesis devuelve 0 en caso de éxito. De lo contrario, se imprime un mensaje de error en la salida de error estándar y la herramienta devuelve un valor distinto de 0.
