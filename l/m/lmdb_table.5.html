NOMBRE

lmdb_table - Adaptador LMDB de Postfix

SINOPSIS

postmap lmdb:/etc/postfix/nombre_archivo
postmap -i lmdb:/etc/postfix/nombre_archivo <archivo_entrada
postmap -d "clave" lmdb:/etc/postfix/nombre_archivo
postmap -d - lmdb:/etc/postfix/nombre_archivo <archivo_entrada
postmap -q "clave" lmdb:/etc/postfix/nombre_archivo
postmap -q - lmdb:/etc/postfix/nombre_archivo <archivo_entrada

DESCRIPCIÓN


El adaptador LMDB de Postfix proporciona acceso a un almacén persistente, mapeado en memoria, de clave-valor. El tamaño de la base de datos está limitado solo por el tamaño del espacio de direcciones de memoria (típicamente 31 o 47 bits en CPUs de 32 o 64 bits, respectivamente) y por el espacio disponible en el sistema de archivos.

SOLICITUDES

El adaptador LMDB soporta todas las operaciones de tabla de consulta de Postfix. Esto hace que LMDB sea adecuado para la reescritura de direcciones de Postfix, enrutamiento, políticas de acceso, cachés o cualquier información que pueda almacenarse bajo una clave de consulta fija.

Cuando una transacción falla debido a una base de datos llena, Postfix redimensiona la base de datos y reintenta la transacción.

Las consultas de tabla de Postfix pueden generar claves de búsqueda parciales tales como nombres de dominio sin uno o más subdominios, direcciones de red sin uno o más octetos menos significativos, o direcciones de correo electrónico sin la parte local, extensión de dirección o porción de dominio. Este comportamiento también se encuentra con, por ejemplo, tablas btree:, hash:, o ldap:.

Los cambios en una base de datos LMDB no activan un reinicio automático del demonio, y no requieren un reinicio del demonio con "postfix reload".

FIABILIDAD

La arquitectura de copia en escritura de LMDB proporciona actualizaciones seguras, a costa de usar más espacio que algunas otras bases de datos de archivos planos. Las operaciones de lectura están mapeadas en memoria para mayor velocidad. Las operaciones de escritura no están mapeadas en memoria para evitar corrupción silenciosa debido a errores de puntero errantes.

Múltiples procesos pueden actualizar de forma segura una base de datos LMDB sin serializar las solicitudes a través del servicio proxymap(8). Esto hace que LMDB sea adecuado como caché compartida para los servicios verify(8) o postscreen(8).

SINCRONIZACIÓN

El adaptador LMDB de Postfix no utiliza el esquema de bloqueo incorporado de LMDB, ya que requeriría archivos de bloqueo escribibles por todos y violaría el modelo de seguridad de Postfix. En su lugar, Postfix utiliza bloqueos fcntl(2) con granularidad de archivo completo. Los programas que utilizan el protocolo de bloqueo incorporado de LMDB corromperán una base de datos LMDB de Postfix o leerán datos basura.

Cada transacción de lectura o escritura de la base de datos LMDB de Postfix debe protegerse de principio a fin con un bloqueo fcntl(2) compartido o exclusivo. Un escritor puede degradar atómicamente un bloqueo exclusivo a un bloqueo compartido, pero debe mantener un bloqueo exclusivo al abrir otra transacción de escritura.

Tenga en cuenta que los bloqueos fcntl(2) no protegen las transacciones dentro del mismo proceso entre sí. Si un programa no puede evitar realizar solicitudes de base de datos simultáneas, entonces debe proteger sus transacciones con bloqueos dentro del proceso, además de los bloqueos fcntl(2) por proceso.

PARÁMETROS DE CONFIGURACIÓN

Los programas de corta duración recogen automáticamente los cambios en main.cf. Con programas de demonio de larga duración, use el comando "postfix reload" después de un cambio de configuración.

El límite de tamaño inicial de la base de datos LMDB de OpenLDAP en bytes.
