DESCRIPCIÓN

gcov es un programa de cobertura de pruebas. Úselo junto con GCC para analizar sus programas y ayudar a crear código más eficiente y rápido, y para descubrir partes no probadas de su programa. Puede usar gcov como una herramienta de perfilado para ayudar a descubrir dónde sus esfuerzos de optimización afectarán mejor a su código. También puede usar gcov junto con la otra herramienta de perfilado, gprof, para evaluar qué partes de su código utilizan la mayor cantidad de tiempo de computación.

Las herramientas de perfilado le ayudan a analizar el rendimiento de su código. Usando un perfilador como gcov o gprof, puede obtener estadísticas básicas de rendimiento, tales como:

  • con qué frecuencia se ejecuta cada línea de código
  • qué líneas de código se ejecutan realmente
  • cuánto tiempo de computación utiliza cada sección de código

Una vez que sepa estas cosas sobre cómo funciona su código cuando se compila, puede mirar cada módulo para ver qué módulos deben ser optimizados. gcov le ayuda a determinar en qué trabajar para la optimización.

Los desarrolladores de software también utilizan las pruebas de cobertura junto con conjuntos de pruebas, para asegurarse de que el software es realmente lo suficientemente bueno para una versión. Los conjuntos de pruebas pueden verificar que un programa funciona como se espera; un programa de cobertura prueba para ver cuánto del programa es ejercitado por el conjunto de pruebas. Los desarrolladores pueden entonces determinar qué tipos de casos de prueba deben agregarse a los conjuntos de pruebas para crear mejores pruebas y un mejor producto final.

Debe compilar su código sin optimización si planea usar gcov porque la optimización, al combinar algunas líneas de código en una función, puede no darle tanta información como necesita para buscar "puntos calientes" donde el código utiliza una gran cantidad de tiempo de computación. Del mismo modo, dado que gcov acumula estadísticas por línea (en la resolución más baja), funciona mejor con un estilo de programación que coloca solo una declaración por línea. Si utiliza macros complicadas que se expanden a bucles o a otras estructuras de control, las estadísticas son menos útiles; solo informan sobre la línea donde aparece la llamada a la macro. Si sus macros complejas se comportan como funciones, puede reemplazarlas con funciones en línea para resolver este problema.

gcov crea un archivo de registro llamado archivo_fuente.gcov que indica cuántas veces se ha ejecutado cada línea de un archivo fuente archivo_fuente.c. Puede usar estos archivos de registro junto con gprof para ayudar a ajustar el rendimiento de sus programas. gprof proporciona información de tiempo que puede usar junto con la información que obtiene de gcov.

gcov solo funciona en código compilado con GCC. No es compatible con ningún otro mecanismo de perfilado o cobertura de pruebas.

OPCIONES

-a
--all-blocks
Escribir recuentos de ejecución individuales para cada bloque básico. Normalmente, gcov genera recuentos de ejecución solo para los bloques principales de una línea. Con esta opción, puede determinar si los bloques dentro de una sola línea no se están ejecutando.
-b
--branch-probabilities
Escribir las frecuencias de rama en el archivo de salida y las estadísticas resumidas de rama en la salida estándar. Esta opción le permite ver con qué frecuencia se tomó cada rama en su programa. Las ramas incondicionales no se mostrarán, a menos que se proporcione la opción -u.
-c
--branch-counts
Escribir las frecuencias de rama como el número de ramas tomadas, en lugar del porcentaje de ramas tomadas.
-g
--conditions
Escribir la cobertura de condiciones en el archivo de salida y las estadísticas resumidas de condiciones en la salida estándar. Esta opción le permite ver si las condiciones en su programa tuvieron al menos una vez un efecto independiente en el resultado de la expresión booleana (cobertura de decisión/condición modificada). Esto requiere que compile la fuente con -fcondition-coverage.
-d
--display-progress
Mostrar el progreso en la salida estándar.
-f
--function-summaries
Generar resúmenes para cada función además del resumen a nivel de archivo.
-h
--help
Mostrar ayuda sobre cómo usar gcov (en la salida estándar) y salir sin realizar ningún procesamiento adicional.
-j
--json-format
Generar el archivo gcov en un formato intermedio JSON fácil de analizar que no requiere código fuente para su generación. El archivo JSON se comprime con el algoritmo de compresión gzip y los archivos tienen la extensión .gcov.json.gz.

La estructura del JSON es la siguiente:

{
  "current_working_directory": "foo/bar",
  "data_file": "a.out",
  "format_version": "2",
  "gcc_version": "11.1.1 20210510"
  "files": ["$file"]
}

Los campos del elemento raíz tienen la siguiente semántica:

  • current_working_directory: directorio de trabajo donde se compiló una unidad de compilación
  • data_file: nombre del archivo de datos (GCDA)
  • format_version: versión semántica del formato

    Cambios en la versión 2:

*
calls: se añade información sobre llamadas a funciones
*
gcc_version: versión del compilador GCC

Cada file tiene la siguiente forma:

{
  "file": "a.c",
  "functions": ["$function"],
  "lines": ["$line"]
}

Los campos del elemento file tienen la siguiente semántica:

*
file_name: nombre del archivo fuente

Cada function tiene la siguiente forma:

{
  "blocks": 2,
  "blocks_executed": 2,
  "demangled_name": "foo",
  "end_column": 1,
  "end_line": 4,
  "execution_count": 1,
  "name": "foo",
  "start_column": 5,
  "start_line": 1
}

Los campos del elemento function tienen la siguiente semántica:

  • blocks: número de bloques que están en la función
  • blocks_executed: número de bloques ejecutados de la función
  • demangled_name: nombre desanidado de la función
  • end_column: columna en el archivo fuente donde termina la función
  • end_line: línea en el archivo fuente donde termina la función
  • execution_count: número de ejecuciones de la función
  • name: nombre de la función
  • start_column: columna en el archivo s

# NOMBRE gcov - contador de cobertura del programa C/C++ # RESUMEN **gcov** [*-b*] [*-c*] [*-f*] [*-h*] [*-i*] [*-j*] [*-l*] [*-m*] [*-n*] [*-o* directorio|archivo] [*-p*] [*-q*] [*-r*] [*-s* directorio] [*-t*] [*-u*] [*-v*] [*-w*] [*-x*] [archivo_entrada...] # DESCRIPCIÓN En el modo de línea de comandos, **gcov** se ejecuta en los archivos de salida generados por el compilador GCC con las opciones de instrumentación de cobertura de código. Para C++, esto significa compilar con `-fprofile-arcs -ftest-coverage`. Para Ada, esto significa compilar con `-fprofile-arcs -fbranch-probabilities -ftest-coverage`. **gcov** se ejecuta una vez por cada archivo de entrada que se compila. Por ejemplo, si tu programa consta de tres archivos fuente C, `main.c`, `foo.c` y `bar.c`, entonces debes ejecutar `gcov` una vez por cada uno de ellos. Si invocas `gcov` con varios archivos de entrada, las contribuciones de cada archivo de entrada se suman. Normalmente, lo invocarías con la misma lista de archivos que la que utilizaste para el enlace final de tu ejecutable. Por ejemplo, si tu programa consta de los archivos fuente `test.c`, `test.h`, `test.cpp` y `test.hpp`, y tu compilación es: ```bash gcc -fprofile-arcs -ftest-coverage test.c -o test ``` o ```bash g++ -fprofile-arcs -ftest-coverage test.cpp -o test ``` entonces debes ejecutar `gcov` para cada uno de los archivos de entrada utilizados: ```bash gcov test.c gcov test.cpp ``` Esto generará los archivos `test.c.gcov` y `test.cpp.gcov`. Los archivos incluidos, como `test.h` y `test.hpp`, también pueden generar archivos `.gcov` si contienen código y ese código fue instrumentado. En la mayoría de los casos, **gcov** se ejecuta con el directorio actual como el mismo que cuando se invocó el compilador. De lo contrario, no podrá localizar los archivos fuente. **gcov** produce archivos llamados *nombre_mangled.gcov* en el directorio actual. Estos contienen la información de cobertura del archivo fuente al que corresponden. Se produce un archivo *.gcov* por cada archivo fuente (o cabecera) que contiene código y que fue compilado para producir los archivos de datos. El componente *nombre_mangled* del nombre del archivo de salida suele ser simplemente el nombre del archivo fuente, pero puede ser algo más complicado si se dan las opciones `-l` o `-p`. Consulte esas opciones para obtener más detalles. Los archivos *.gcov* contienen campos separados por **:** junto con el código fuente del programa. El formato es ``` :: ``` La información adicional de bloques puede seguir a cada línea, cuando se solicita mediante una opción de línea de comandos. El *contador_ejecuciones* es **-** para las líneas que no contienen código. Las líneas no ejecutadas se marcan como **#####** o **=====**, dependiendo de si son alcanzables por caminos no excepcionales o solo por caminos excepcionales como los manejadores de excepciones de C++, respectivamente. Dada la opción `-a`, los bloques no ejecutados se marcan como **$$$$$** o **%%%%%**, dependiendo de si un bloque básico es alcanzable a través de rutas no excepcionales o excepcionales. Los bloques básicos ejecutados que tienen una sentencia con recuento de ejecución cero terminan con el carácter **\*** y se colorean con color magenta con la opción `-k`. Esta funcionalidad no se admite en Ada. Tenga en cuenta que GCC puede eliminar por completo los cuerpos de las funciones que no son necesarias, por ejemplo, si se insertan en todas partes. Dichas funciones se marcan con **-**, lo que puede ser confuso. Utilice la opción `-fkeep-inline-functions` para evitar la eliminación de estas funciones. Las líneas de salida de `gcov` pueden contener información sobre los bloques básicos y los arcos (ramas y llamadas). La información sobre bloques y arcos se genera en el formato JSON. Cada archivo de salida *.gcov* comienza con una sección de comentarios que contiene información sobre el programa para el que se genera el informe. La siguiente información está disponible:
  • archivo: nombre del archivo fuente
  • fecha: fecha en la que se generó el archivo de informe
  • GCC: versión de GCC que se utilizó para compilar el programa
  • ídem: nombre completo de la ruta del archivo ejecutable
  • función: detalles de las funciones encontradas en el código fuente
Cada entrada de *función* tiene la siguiente forma:
  • nombre: nombre de la función
  • archivos_fuente: número de archivos fuente en los que se encontró la función
  • línea_inicial: número de línea en el archivo fuente donde comienza la función
  • columna_inicial: número de columna en el archivo fuente donde comienza la función
Tenga en cuenta que los números de línea y columna se numeran a partir de 1. En la implementación actual, *línea_inicial* y *columna_inicial* no incluyen parámetros de plantilla y el tipo de retorno inicial, pero es probable que esto se corrija en el futuro. Cada *línea* tiene la siguiente forma: 
{
  "block_ids": ["$block_id"],
  "branches": ["$branch"],
  "calls": ["$call"],
  "count": 2,
  "conditions": ["$condition"],
  "line_number": 15,
  "unexecuted_block": false,
  "function_name": "foo",
}
Las ramas y las llamadas solo están presentes con la opción *-b*. Los campos del elemento *línea* tienen la siguiente semántica:
  • block_ids: IDs de los bloques básicos que pertenecen a la línea
  • count: número de ejecuciones de la línea
  • line_number: número de línea
  • unexecuted_block: indicador de si la línea contiene un bloque no ejecutado (no todas las sentencias de la línea se ejecutan)
  • function_name: nombre de una función a la que pertenece esta *línea* (puede no estar configurado para una línea con sentencias insertadas)
Cada *rama* tiene la siguiente forma: 
{
  "count": 11,
  "destination_block_id": 17,
  "fallthrough": true,
  "source_block_id": 13,
  "throw": false
}
Los campos del elemento *rama* tienen la siguiente semántica:
  • count: número de ejecuciones de la rama
  • fallthrough: verdadero cuando la rama es una rama de caída
  • throw: verdadero cuando la rama es una rama excepcional
  • source_block_id: ID del bloque básico donde ocurre esta rama
  • destination_block_id: ID del bloque básico al que salta esta rama
Cada *llamada* tiene la siguiente forma: 
{
  "destination_block_id": 1,
  "returned": 11,
  "source_block_id": 13
}
Los campos del elemento *llamada* tienen la siguiente semántica:
  • returned: número de veces que se devolvió una llamada a función (el recuento de llamadas es igual a *line::count*)
  • source_block_id: ID del bloque básico donde ocurre esta llamada
  • destination_block_id: ID del bloque básico al que continúa la llamada después de la devolución
Cada *condición* tiene la siguiente forma: 
{
  "count": 4,
  "covered": 2,
  "not_covered_false": [],
  "not_covered_true": [0, 1],
}
Los campos del elemento *condición* tienen la siguiente semántica:
  • count: número de resultados de condición en esta expresión
  • covered: número de resultados de condición cubiertos en esta expresión
  • not_covered_true: términos, por índice, no vistos como verdaderos en esta expresión
  • not_covered_false: términos, por índice, no vistos como falsos en esta expresión
# OPCIONES
  • -H
  • --human-readable: Escribe los recuentos en formato legible por humanos (como 24.6k).
  • -k
  • --use-colors: Usa colores para las líneas de código que tienen cobertura cero. Usamos color rojo para las líneas no excepcionales y cian para las excepcionales. Los mismos colores se usan para los bloques básicos con la opción `-a`.
  • -l
  • --long-file-names: Crea nombres de archivo largos para los archivos fuente incluidos. Por ejemplo, si el archivo de cabecera *x.h* contiene código y fue incluido en el archivo *a.c*, entonces ejecutar **gcov** en el archivo *a.c* generará un archivo de salida llamado *a.c##x.h.gcov* en lugar de *x.h.gcov*. Esto puede ser útil si *x.h* se incluye en varios archivos fuente y desea ver las contribuciones individuales. Si utiliza la opción `-p`, tanto el nombre del archivo incluyente como el incluido serán nombres de ruta completos.
  • -m
  • --demangled-names: Muestra los nombres de función desmangled en la salida. El valor predeterminado es mostrar los nombres de función mangled.
  • -n
  • --no-output: No cree el archivo de salida **gcov**.
  • -o directorio|archivo
  • --object-directory directorio
  • --object-file archivo: Especifique el directorio que contiene los archivos de datos de gcov, o el nombre de ruta del objeto. Los archivos de datos *.gcno* y *.gcda* se buscan utilizando esta opción. Si se especifica un directorio, los archivos de datos están en ese directorio y se nombran según el nombre del archivo de entrada, sin su extensión. Si se especifica un archivo aquí, los archivos de datos se nombrarán según ese archivo, sin su extensión.
  • -p
  • --preserve-paths: Conserva la información completa de la ruta en los nombres de los archivos *.gcov* generados. Sin esta opción, solo se utiliza el componente del nombre de archivo. Con esta opción, se utilizan todos los directorios, los caracteres **/** se traducen a caracteres **#**, los componentes de directorio **. ** se eliminan y los componentes **.. ** irremovibles se renombran a **^**. Esto es útil si los archivos fuente están en varios directorios diferentes.
  • -q
  • --use-hotness-colors: Emite una salida coloreada similar a perf para las líneas activas. La leyenda de la escala de colores se imprime al principio del archivo de salida.
  • -r
  • --relative-only: Solo muestra información sobre archivos fuente con un nombre de ruta relativo (después de la eliminación del prefijo fuente). Las rutas absolutas suelen ser archivos de cabecera del sistema y la cobertura de cualquier función insertada en ellos normalmente no es interesante.
  • -s directorio
  • --source-prefix directorio: Un prefijo para los nombres de archivo fuente que se eliminará al generar los archivos de cobertura de salida. Esta opción es útil cuando se compila en un directorio separado y no se desea la ruta al directorio fuente al determinar los nombres de archivo de salida. Tenga en cuenta que esta detección de prefijo se aplica antes de determinar si el archivo fuente es absoluto.
  • -t
  • --stdout: Salida al estándar de salida en lugar de a los archivos de salida.
  • -u
  • --unconditional-branches: Cuando se dan probabilidades de rama, incluye las de ramas incondicionales. Las ramas incondicionales normalmente no son interesantes.
  • -v
  • --version: Muestra el número de versión de **gcov** (en la salida estándar) y sale sin realizar ningún otro procesamiento.
  • -w
  • --verbose: Imprime información detallada relacionada con bloques básicos y arcos.
  • -x
  • --hash-filenames: Cuando se utiliza *--preserve-paths*, gcov utiliza la ruta completa de los archivos fuente para crear un nombre de archivo de salida. Esto puede dar lugar a nombres de archivo largos que pueden superar los límites del sistema de archivos. Esta opción crea nombres de la forma *nombre_archivo_fuente##*md5*.gcov*, donde el componente *nombre_archivo_fuente* es la parte final del nombre de archivo y el componente *md5* se calcula a partir del nombre mangled completo que se habría utilizado de otra manera. La opción es una alternativa a *--preserve-paths* en sistemas que tienen un límite en el sistema de archivos.

The \"coverage\" output consists of each word in the original source file, followed by:

1. The execution count of the instrumented line. Lines that contain no executable code are omitted.

2. An indication of whether the execution count is at least 1. If the execution count is zero, it indicates that the line was not executed. If the execution count is greater than zero, it indicates that the line was executed.

3. For C++ programs using templates, you can also get coverage per instance of a template function. This is done by using the -a or --all-blocks option. When this option is used, each basic block of the function will be shown on a separate line. The line number will be suffixed with -block <N>.

When you compile code with the `-fbranch-probabilities' option, you can also get coverage information about the branches taken. This is enabled by the `-b' option.

The options `-fkeep-static-functions' and `-fkeep-inline-functions' are useful if you want gcov to show coverage information for static or inline functions respectively.

Some lines of information at the start have line_number of zero. These preamble lines are of the form

-:0:<tag>:<value>

The ordering and number of these preamble lines will be augmented as gcov development progresses --- do not rely on them remaining unchanged. Use tag to locate a particular preamble line.

The additional block information is of the form

<tag> <information>

The information is human readable, but designed to be simple enough for machine parsing too.

When printing percentages, 0% and 100% are only printed when the values are exactly 0% and 100% respectively. Other values which would conventionally be rounded to 0% or 100% are instead printed as the nearest non-boundary value.

For each function, a line is printed showing how many times the function is called, how many times it returns and what percentage of the function's blocks were executed.

For each basic block, a line is printed after the last line of the basic block describing the branch or call that ends the basic block. There can be multiple branches and calls listed for a single source line if there are multiple basic blocks that end on that line. In this case, the branches and calls are each given a number. There is no simple way to map these branches and calls back to source constructs. In general, though, the lowest numbered branch or call will correspond to the leftmost construct on the source line.

For a branch, if it was executed at least once, then a percentage indicating the number of times the branch was taken divided by the number of times the branch was executed will be printed. Otherwise, the message "never executed" is printed.

For a call, if it was executed at least once, then a percentage indicating the number of times the call returned divided by the number of times the call was executed will be printed. This will usually be 100%, but may be less for functions that call "exit" or "longjmp", and thus may not return every time they are called.

The execution counts are cumulative. If the example program were executed again without removing the .gcda file, the count for the number of times each line in the source was executed would be added to the results of the previous run(s). This is potentially useful in several ways. For example, it could be used to accumulate data over a number of program runs as part of a test verification suite, or to provide more accurate long-term information over a large number of program runs.

The data in the .gcda files is saved immediately before the program exits. Uso de gcov con optimización de GCC

Si planeas usar gcov para ayudar a optimizar tu código, debes primero compilar tu programa con la opción especial de GCC --coverage. Aparte de eso, puedes usar cualquier otra opción de GCC; pero si quieres demostrar que cada línea de tu programa se ejecutó, no debes compilar con optimización al mismo tiempo. En algunas máquinas, el optimizador puede eliminar algunas líneas de código simples combinándolas con otras líneas. Por ejemplo, código como este:

if (a != b)
  c = 1;
else
  c = 0;

puede compilarse en una sola instrucción en algunas máquinas. En este caso, no hay forma de que gcov calcule recuentos de ejecución separados para cada línea porque no hay código separado para cada línea. Por lo tanto, la salida de gcov se ve así si compilaste el programa con optimización:

100:   12:if (a != b)
100:   13:  c = 1;
100:   14:else
100:   15:  c = 0;

La salida muestra que este bloque de código, combinado por la optimización, se ejecutó 100 veces. En cierto sentido, este resultado es correcto, porque solo hubo una instrucción que representó las cuatro líneas. Sin embargo, la salida no indica cuántas veces el resultado fue 0 y cuántas veces el resultado fue 1.

Las funciones insertables en línea pueden crear recuentos de línea inesperados. Los recuentos de línea se muestran para el código fuente de la función insertable, pero lo que se muestra depende de dónde se inserta la función en línea, o si no se inserta en absoluto.

Si la función no se inserta en línea, el compilador debe emitir una copia fuera de línea de la función, en cualquier archivo objeto que la necesite. Si fileA.o y fileB.o contienen ambos cuerpos fuera de línea de una función insertable particular, también contendrán recuentos de cobertura para esa función. Cuando fileA.o y fileB.o se enlazan juntos, el enlazador, en muchos sistemas, seleccionará uno de esos cuerpos fuera de línea para todas las llamadas a esa función y eliminará o ignorará el otro. Desafortunadamente, no eliminará los contadores de cobertura del cuerpo de la función no utilizado. Por lo tanto, cuando se instrumenta, todos los usos de esa función, excepto uno, mostrarán recuentos cero.

Si la función se inserta en línea en varios lugares, la estructura del bloque en cada ubicación podría no ser la misma. Por ejemplo, una condición podría ser calculable en tiempo de compilación en algunas instancias. Dado que la cobertura de todos los usos de la función insertable se mostrará para las mismas líneas de código, los recuentos de línea en sí mismos podrían parecer inconsistentes.

Las aplicaciones de larga duración pueden usar las utilidades "__gcov_reset" y "__gcov_dump" para restringir la recopilación de perfiles a la región de interés del programa. Llamar a "__gcov_reset(void)" borrará todos los contadores de perfil en tiempo de ejecución a cero, y llamar a "__gcov_dump(void)" hará que la información del perfil recopilada en ese momento se vuelque a los archivos de salida .gcda. Las aplicaciones instrumentadas usan un destructor estático con prioridad 99 para invocar la función "__gcov_dump". Por lo tanto, "__gcov_dump" se ejecuta después de todos los destructores estáticos definidos por el usuario, así como los manejadores registrados con "atexit".

Si un ejecutable carga un objeto compartido dinámico a través de la funcionalidad dlopen, se necesita -Wl,--dynamic-list-data para volcar todos los datos del perfil.

La biblioteca de tiempo de ejecución de perfilado informa varios errores relacionados con la manipulación y el guardado del perfil. Los errores se imprimen en la salida de error estándar o en el archivo GCOV_ERROR_FILE, si se usa la variable de entorno. Para terminar inmediatamente después de que ocurra un error, establezca la variable de entorno GCOV_EXIT_AT_ERROR. Esto puede ayudar a los usuarios a encontrar conflictos de perfil que conducen a un perfil engañoso.
