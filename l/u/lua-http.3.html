Introducción

lua-http es una biblioteca de HTTP y WebSocket eficiente y capaz para Lua 5.1, 5.2, 5.3 y LuaJIT. Algunas de las características de la biblioteca incluyen:

•
Soporte para las versiones HTTP 1, 1.1 y 2 según se especifica en RFC 7230 (https://tools.ietf.org/html/rfc7230) y RFC 7540 (https://tools.ietf.org/html/rfc7540)
•
Proporciona API tanto de cliente como de servidor
•
API completamente asíncrona que no bloquea el hilo actual al ejecutar operaciones que típicamente bloquean
•
Soporte para WebSockets según se especifica en RFC 6455 (https://tools.ietf.org/html/rfc6455) incluyendo ping/pong, transferencia de datos binarios y cifrado TLS
•
Seguridad de la capa de transporte (TLS) - lua-http soporta HTTPS y WSS a través de luaossl (https://github.com/wahern/luaossl).
•
Fácil integración en otros bucles de eventos o scripts

¿Por qué lua-http?

La biblioteca lua-http fue escrita para llenar un vacío en el ecosistema de Lua proporcionando una biblioteca de HTTP y WebSocket con los siguientes rasgos:

•
Asíncrona y eficiente
•
Puede ser utilizada sin forzar al desarrollador a seguir un patrón específico. Por el contrario, la biblioteca se puede adaptar a muchos patrones comunes.
•
Puede ser utilizada a un nivel muy alto sin necesidad de comprender el transporte de datos HTTP (aparte de las direcciones de conexión).
•
Proporciona una rica API de bajo nivel, si se desea, para crear potentes herramientas basadas en HTTP a nivel de protocolo.

Como resultado de estos objetivos de diseño, la biblioteca es simple y discreta y puede acomodar decenas de miles de conexiones en hardware común.

lua-http es una biblioteca flexible de HTTP y WebSocket que permite a los desarrolladores concentrarse en las características del negocio al construir aplicaciones habilitadas para Internet. Si está buscando una forma de optimizar el desarrollo de una aplicación habilitada para Internet, habilitar la red HTTP en su juego, crear un nuevo sistema de Internet de las Cosas (IoT), o escribir un servidor web eficiente para un caso de uso específico, lua-http tiene las herramientas que necesita.

Portabilidad

lua-http es código puro de Lua con dependencias en las siguientes bibliotecas externas:

•
cqueues (http://25thandclement.com/~william/projects/cqueues.html) - Biblioteca API de Posix para Lua
•
luaossl (http://25thandclement.com/~william/projects/luaossl.html) - Enlaces de Lua para TLS/SSL
•
lua-zlib (https://github.com/brimworks/lua-zlib) - Enlaces opcionales de Lua para zlib

lua-http puede ejecutarse en cualquier sistema operativo compatible con cqueues y openssl, lo que en el momento de escribir esto incluye GNU/Linux, FreeBSD, NetBSD, OpenBSD, OSX y Solaris.

Casos de uso comunes

Las siguientes son dos demostraciones sencillas de cómo se puede utilizar la biblioteca lua-http:

Recuperación de un documento

La interfaz de nivel más alto para clientes es http.request. Al construir un objeto de request a partir de una URI usando new_from_uri y evaluándolo inmediatamente, puede obtener fácilmente un recurso HTTP.

local http_request = require "http.request"
local headers, stream = assert(http_request.new_from_uri("http://example.com"):go())
local body = assert(stream:get_body_as_string())
if headers:get ":status" ~= "200" then
    error(body)
end
print(body)

Comunicaciones WebSocket

Para solicitar información de un servidor WebSocket, utilice el módulo websocket para crear un nuevo cliente WebSocket.

local websocket = require "http.websocket"
local ws = websocket.new_from_uri("wss://echo.websocket.org")
assert(ws:connect())
assert(ws:send("koo-eee!"))
local data = assert(ws:receive())
assert(data == "koo-eee!")
assert(ws:close())

Operación asíncrona

lua-http ha sido escrito para operar de forma asíncrona para que pueda ser utilizado en su aplicación, servidor o juego sin bloquear su bucle principal. Las operaciones asíncronas se logran utilizando cqueues, una biblioteca Lua/C que incorpora el yield de Lua y APIs a nivel de kernel para reducir el uso de CPU. Todas las operaciones de lua-http, incluyendo la resolución DNS, la negociación TLS y las operaciones de lectura/escritura no bloquearán el hilo principal de la aplicación cuando se ejecuten dentro de un cqueue o un "contenedor" habilitado para cqueues. Si bien a veces es necesario bloquear una rutina (yield) y esperar datos externos, todas las llamadas a API de bloqueo aceptan un tiempo de espera opcional para garantizar el buen comportamiento de las aplicaciones en red y evitar rutinas no responsivas o "muertas".

Las operaciones asíncronas son una de las características más potentes de lua-http y no requieren ningún esfuerzo por parte del desarrollador. Por ejemplo, un servidor HTTP puede ser instanciado dentro de cualquier bucle principal de Lua y ejecutarse junto con el código de la aplicación sin afectar negativamente al proceso principal de la aplicación. Si otros componentes habilitados para cqueues se integran dentro de un bucle de cqueues, la aplicación estará completamente impulsada por eventos a través de APIs de sondeo a nivel de kernel.

cqueues puede ser utilizado junto con lua-http para integrar otras características en su aplicación Lua y crear aplicaciones potentes, eficientes y habilitadas para la web. Algunos de los ejemplos en esta guía utilizarán cqueues para demostraciones sencillas. Para más recursos sobre cqueues, por favor consulte:

•
El sitio web de cqueues (http://25thandclement.com/~william/projects/cqueues.html) para más información sobre la biblioteca cqueues.
•
Los ejemplos de cqueues se pueden encontrar con el código fuente de cqueues disponible a través de git o archivos (http://www.25thandclement.com/~william/projects/cqueues.html#download) o acceder a ellos en línea aquí (https://github.com/wahern/cqueues/tree/master/examples).
•
Para más información sobre la integración de cqueues con otras bibliotecas de bucle de eventos, consulte la integración con otros bucles principales (https://github.com/wahern/cqueues/wiki/Integrations-with-other-main-loops).
•
Para otras bibliotecas que utilizan cqueues, como APIs asíncronas para Redis y PostgreSQL, consulte la entrada del wiki de cqueues aquí (https://github.com/wahern/cqueues/wiki/Libraries-that-use-cqueues).

Convenciones

La siguiente es una lista de convenciones de API y referencia general:

HTTP

•
Los campos de la línea de solicitud y estado HTTP 1 se pasan dentro de objetos headers bajo las claves ":authority", ":method", ":path", ":scheme" y ":status" según se define en HTTP 2. Como tal, todos se conservan en formato de cadena (importante de recordar para el campo :status).
•
Los campos de encabezado siempre deben usarse con claves en minúsculas.

Errores

•
Parámetros de función inválidos lanzarán un error de Lua (si se validan).
•
Errores de red, por ejemplo, la desconexión de un cliente, se comunicarán a través de un valor de retorno de Lua en lugar de lanzar un error. Los clientes son responsables de inspeccionar los valores de retorno para detectar y manejar dichos errores.

Tiempos de espera

Todas las operaciones que pueden bloquear el hilo actual toman un argumento de tiempo de espera. Este argumento es siempre el número de segundos que se permite antes de devolver nil, mensaje_error, ETIMEDOUT, donde mensaje_error es un mensaje de error localizado como "la conexión se agotó".

Terminología

Gran parte de la terminología de lua-http se toma prestada de HTTP 2.

Conexión: Una abstracción sobre un socket TCP/IP subyacente. lua-http tiene actualmente dos tipos de conexión: uno para HTTP 1 y otro para HTTP 2.

Stream: Una solicitud/respuesta en un objeto de conexión. lua-http tiene dos tipos de stream: uno para streams HTTP 1 y otro para streams HTTP 2. La interfaz común se describe en stream.

Interfaces

lua-http tiene módulos separados para los protocolos HTTP 1 y HTTP 2, sin embargo, las diferentes versiones comparten muchos conceptos comunes. lua-http proporciona una interfaz común para las operaciones que tienen sentido para ambas versiones de protocolo (así como para futuros desarrollos).

Las siguientes secciones describen las interfaces expuestas por la biblioteca lua-http.

conexión

Una conexión encapsula un socket y proporciona operaciones específicas del protocolo. Una conexión puede tener streams que encapsulan las solicitudes/respuestas que ocurren a través de una conexión. Alternativamente, puede ignorar los streams por completo y utilizar operaciones de bajo nivel específicas del protocolo para leer y escribir en el socket.

Todos los tipos de conexión exponen los siguientes campos:

connection.type

El modo de uso del objeto de conexión. Los valores válidos son:

•
"client": Actúa como cliente; este tipo de conexión es utilizado por entidades que desean realizar solicitudes
•
"server": Actúa como servidor; este tipo de conexión es utilizado por entidades que desean responder a solicitudes

connection.version

El número de versión HTTP de la conexión como un número.

connection:pollfd()

connection:events()

connection:timeout()

connection:connect(timeout)

Completa la conexión al servidor remoto utilizando la dirección especificada, la versión HTTP y cualquier opción especificada en el constructor de connection.new. La función connect se detendrá hasta que el intento de conexión finalice (éxito o fracaso) o hasta que se supere el tiempo de espera. La conexión puede incluir búsquedas de DNS, negociación TLS e intercambio de configuraciones HTTP2. Devuelve true en caso de éxito. En caso de error, devuelve nil, un mensaje de error y un número de error.

connection:checktls()

Comprueba el socket para una conexión TLS (Transport Layer Security) válida. Devuelve el objeto ssl de luaossl si la conexión está asegurada. Devuelve nil y un mensaje de error si no hay una sesión TLS activa. Consulte el sitio web de luaossl (http://25thandclement.com/~william/projects/luaossl.html) para obtener más información sobre el objeto ssl.

connection:localname()

Devuelve la información de la conexión para el socket local. Devuelve la familia de direcciones, la dirección IP y el puerto para un socket externo. Para sockets de dominio Unix, la función devuelve AF_UNIX y la ruta. Si el objeto de conexión no está conectado, devuelve AF_UNSPEC (0). En caso de error, devuelve nil, un mensaje de error y un número de error.

connection:peername()

Devuelve la información de la conexión para el peer del socket (es decir, el siguiente salto). Devuelve la familia de direcciones, la dirección IP y el puerto para un socket externo. Para sockets Unix, la función devuelve AF_UNIX y la ruta. Si el objeto de conexión no está conectado, devuelve AF_UNSPEC (0). En caso de error, devuelve nil, un mensaje de error y un número de error.

Nota: Si el cliente está utilizando un proxy, los valores devueltos :peername() apuntan al proxy, no al servidor remoto.

connection:flush(timeout)

Vacía los datos salientes en búfer en el socket hacia el sistema operativo. Devuelve true en caso de éxito. En caso de error, devuelve nil, un mensaje de error y un número de error.

connection:shutdown()

Realiza un cierre ordenado de la conexión cerrando todos los streams y llama a :shutdown() en el socket. La conexión no se puede volver a abrir.

connection:close()

Cierra una conexión y libera los recursos del sistema operativo. Tenga en cuenta que :close() realiza una connection:shutdown() antes de liberar los recursos.

connection:new_stream()

Crea y devuelve un nuevo stream en la conexión.

connection:get_next_incoming_stream(timeout)

Devuelve el siguiente stream iniciado por el par en la conexión. Esta función se puede usar para detenerse y "escuchar" streams HTTP entrantes.

connection:onidle(new_handler)

Proporciona una función de devolución de llamada para que se llame cuando la conexión quede inactiva, es decir, cuando no haya ninguna solicitud en curso ni streams en cola esperando. Cuando se llama, recibirá la conexión como primer argumento. Devuelve el manejador anterior.

stream

Un stream HTTP es una abstracción de una solicitud/respuesta dentro de una conexión HTTP. Dentro de un stream puede haber un número de bloques de "encabezados", así como datos conocidos como el "cuerpo".

http.headers

Una lista ordenada de campos de cabecera. Cada campo tiene un nombre, un valor y un flag never_index que indica si el campo de cabecera contiene datos potencialmente sensibles.

Cada objeto de cabeceras tiene un índice por nombre de campo para recuperar eficientemente valores por clave. Ten en cuenta que puede haber múltiples valores para un nombre de campo dado. (por ejemplo, un servidor HTTP puede enviar dos cabeceras Set-Cookie).

Como se indica en la sección Convenciones, los campos de línea de solicitud y estado de HTTP 1 se pasan dentro de objetos de cabeceras bajo las claves ":authority", ":method", ":path", ":scheme" y ":status" según se define en HTTP 2. Como tal, todos se mantienen en formato de cadena (importante recordar para el campo ":status").

Crea y devuelve un nuevo objeto de cabeceras.

Devuelve el número de cabeceras.

También disponible como #headers en Lua 5.2+.

headers:clone()

Crea y devuelve una copia del objeto de cabeceras.

headers:append(name, value, never_index)

Añade una cabecera.

name es el nombre del campo de cabecera. La convención es usar minúsculas. No se validará en este momento.
value es el valor del campo de cabecera. No se validará en este momento.
never_index es un booleano opcional que indica si el value debe considerarse secreto. Por defecto es true para los campos de cabecera: authorization, proxy-authorization, cookie y set-cookie.

headers:each()

Un iterador sobre todas las cabeceras que emite name, value, never_index.

Ejemplo

local http_headers = require "http.headers"
local myheaders = http_headers.new()
myheaders:append(":status", "200")
myheaders:append("set-cookie", "foo=bar")
myheaders:append("connection", "close")
myheaders:append("set-cookie", "baz=qux")
for name, value, never_index in myheaders:each() do
    print(name, value, never_index)
end

":status", "200", false
"set-cookie", "foo=bar", true
"connection", "close", false

]]

local deflater = zlib.deflate()
local compressed = deflater(original, true)

http.compat.prosody

Provides usage similar to prosody’s net.http (https://prosody.im/doc/developers/net/http)

request(url, ex, callback)

A few key differences to the prosody net.http.request:

•
must be called from within a running cqueue
•
The callback may be called from a different thread in the cqueue
•
The returned object will be a http.request object
•
This object is passed to the callback on errors and as the fourth argument on success
•
The default user-agent will be from lua-http (rather than "Prosody XMPP Server")
•
lua-http features (such as HTTP2) will be used where possible

Example

local prosody_http = require "http.compat.prosody"
local cqueues = require "cqueues"
local cq = cqueues.new()
cq:wrap(function()
    prosody_http.request("http://httpbin.org/ip", {}, function(b, c, r)
        print(c) --> 200
        print(b) --> {"origin": "123.123.123.123"}
    end)
end)
assert(cq:loop())

http.compat.socket

Provides compatibility with luasocket’s http.request module (http://w3.impa.br/~diego/software/luasocket/http.html).

Differences:

•
Will automatically be non-blocking when run inside a cqueues managed coroutine
•
lua-http features (such as HTTP2) will be used where possible

Example

Using the `simple' interface as part of a normal script:

local socket_http = require "http.compat.socket"
local body, code = assert(socket_http.request("http://lua.org"))
print(code, #body) --> 200, 2514
