DESCRIPCIÓN

El Linux Trace Toolkit: next generation es un paquete de software de código abierto utilizado para el trazado correlacionado del kernel de Linux, aplicaciones de usuario y bibliotecas de usuario.

LTTng-UST es el componente de trazado del espacio de usuario del proyecto LTTng. Es una adaptación al espacio de usuario de las capacidades de trazado de baja sobrecarga del trazador del kernel de Linux LTTng. La biblioteca liblttng-ust se utiliza para rastrear aplicaciones y bibliotecas de usuario.


Nota

Esta página del manual trata sobre la biblioteca liblttng-ust. El proyecto LTTng-UST también proporciona paquetes Java y Python para rastrear aplicaciones escritas en esos lenguajes. Cómo instrumentar y rastrear aplicaciones Java y Python se documenta en la documentación en línea de LTTng http://lttng.org/docs/.

Hay tres formas de usar liblttng-ust:

•Usando la API de lttng_ust_tracef(3), que es similar a printf(3).
•Usando la API de lttng_ust_tracelog(3), que es lttng_ust_tracef(3) con un parámetro de nivel de registro.
•Definiendo sus propios puntos de trazado. Consulte la sección Creación de un proveedor de puntos de trazado más abajo.

Compatibilidad con APIs anteriores

Desde LTTng-UST 2.13, la definición LTTNG_UST_COMPAT_API_VERSION controla qué APIs de LTTng-UST están disponibles (compiladas):

Indefinido

Todas las APIs están disponibles.

N (entero 0 o positivo)

La versión de API N, y todas las APIs existentes siguientes, están disponibles. Las APIs anteriores no están disponibles (no compiladas).

La siguiente tabla muestra el mapeo de las versiones de LTTng-UST (hasta LTTng-UST 2.14.0) a las versiones de API disponibles:

Versión de LTTng-UST Versiones de API disponibles
2.0 a 2.12 0
2.13 0 y 1

Esta página del manual solo documenta la versión 1 de la API.

Si desea tener acceso a la versión 0 de la API (por ejemplo, las macros tracepoint(), ctf_integer() y TRACEPOINT_EVENT()), entonces no defina LTTNG_UST_COMPAT_API_VERSION, o defínala a 0 antes de incluir cualquier encabezado de LTTng-UST.

Creación de un proveedor de puntos de trazado

La creación de un proveedor de puntos de trazado es el primer paso para usar liblttng-ust. Los siguientes pasos son:

•Instrumentar su aplicación con llamadas lttng_ust_tracepoint()
•Compilar su aplicación con soporte de LTTng-UST
ort, ya sea *estáticamente* o *dinámicamente*.

Un proveedor de tracepoint es un objeto compilado que contiene las sondas de eventos correspondientes a las definiciones de tus tracepoints personalizados. Un proveedor de tracepoint contiene el código para obtener el tamaño de un evento y serializarlo, entre otras cosas.

Para crear un proveedor de tracepoint, comienza con la siguiente plantilla de *encabezado de proveedor de tracepoint*:

#undef LTTNG_UST_TRACEPOINT_PROVIDER
#define LTTNG_UST_TRACEPOINT_PROVIDER mi_proveedor
#undef LTTNG_UST_TRACEPOINT_INCLUDE
#define LTTNG_UST_TRACEPOINT_INCLUDE "./tp.h"
#if !defined(_TP_H) || \
    defined(LTTNG_UST_TRACEPOINT_HEADER_MULTI_READ)
#define _TP_H
#include <lttng/tracepoint.h>
/*
 * LTTNG_UST_TRACEPOINT_EVENT(), LTTNG_UST_TRACEPOINT_EVENT_CLASS(),
 * LTTNG_UST_TRACEPOINT_EVENT_INSTANCE(),
 * LTTNG_UST_TRACEPOINT_LOGLEVEL(), y `LTTNG_UST_TRACEPOINT_ENUM()`
 * se utilizan aquí.
 */
#endif /* _TP_H */
#include <lttng/tracepoint-event.h>

En esta plantilla, el proveedor de tracepoint se llama mi_proveedor (definición de LTTNG_UST_TRACEPOINT_PROVIDER). El archivo debe tener el nombre de la definición de LTTNG_UST_TRACEPOINT_INCLUDE (tp.h en este caso). Entre #include <lttng/tracepoint.h> y #endif van las invocaciones de las macros *LTTNG_UST_TRACEPOINT_EVENT(), *LTTNG_UST_TRACEPOINT_EVENT_CLASS(), *LTTNG_UST_TRACEPOINT_EVENT_INSTANCE(), *LTTNG_UST_TRACEPOINT_LOGLEVEL() y *LTTNG_UST_TRACEPOINT_ENUM().


Nota

Puedes evitar escribir el código repetitivo de prólogo y epílogo en el archivo de plantilla anterior utilizando la herramienta lttng-gen-tp(1) que viene con LTTng-UST.

El archivo de encabezado del proveedor de tracepoint debe incluirse en un archivo fuente que se vea así:

#define LTTNG_UST_TRACEPOINT_CREATE_PROBES
#include "tp.h"

Juntos, esos dos archivos (llamémoslos tp.h y tp.c) forman las fuentes del proveedor de tracepoint, listos para ser compilados.

Puedes crear múltiples proveedores de tracepoint para ser usados en una sola aplicación, pero cada uno debe tener su propio archivo de encabezado.

La sección de uso de *LTTNG_UST_TRACEPOINT_EVENT() a continuación muestra cómo usar la macro LTTNG_UST_TRACEPOINT_EVENT() para definir los tracepoints reales en el archivo de encabezado del proveedor de tracepoint.

Consulta la sección *EJEMPLO* a continuación para ver un ejemplo completo.

Uso de LTTNG_UST_TRACEPOINT_EVENT()

La macro LTTNG_UST_TRACEPOINT_EVENT() se utiliza en un archivo de encabezado de proveedor de plantilla (ver la sección *Creación de un proveedor de tracepoint* arriba) para definir tracepoints de LTTng-UST.

La plantilla de uso de LTTNG_UST_TRACEPOINT_EVENT() es la siguiente:

LTTNG_UST_TRACEPOINT_EVENT(
    /* Nombre del proveedor de tracepoint */
    mi_proveedor,
    /* Nombre del tracepoint/evento */
    mi_tracepoint,
    /* Lista de argumentos del tracepoint (entrada) */
    LTTNG_UST_TP_ARGS(
        ...
    ),
    /* Lista de campos del evento eventual (salida) */
    LTTNG_UST_TP_FIELDS(
        ...
    )
)

La macro LTTNG_UST_TP_ARGS() contiene los argumentos de entrada del tracepoint. Estos argumentos pueden usarse en las expresiones de argumento de los campos de salida definidos en LTTNG_UST_TP_FIELDS().

El formato de los parámetros de LTTNG_UST_TP_ARGS() es: tipo C, seguido del nombre del argumento; repetir según sea necesario, hasta diez veces. Por ejemplo:

LTTNG_UST_TP_ARGS(
    int, mi_entero,
    const char *, mi_cadena,
    FILE *, mi_archivo,
    double, mi_flotante,
    struct mi_datos *, mis_datos
)

La macro LTTNG_UST_TP_FIELDS() contiene los campos de salida del tracepoint, es decir, los datos reales que se pueden registrar en la carga útil de un evento emitido por este tracepoint.

La macro LTTNG_UST_TP_FIELDS() contiene una lista de macros lttng_ust_field_*() NO separadas por comas. Las macros disponibles se documentan en la sección *Macros de tipo de campo lttng_ust_field_*() disponibles* a continuación.

Enumeración. El campo de enumeración debe definirse antes de usar esta macro con la macro LTTNG_UST_TRACEPOINT_ENUM(). Consulte la sección de uso de *LTTNG_UST_TRACEPOINT_ENUM() para más información.

lttng_ust_field_enum(nombre_prov, nombre_enum, tipo_int, nombre_campo,
                     expr)
lttng_ust_field_enum_nowrite(nombre_prov, nombre_enum, tipo_int,
                             nombre_campo, expr)

Los parámetros son:

count

Número de elementos en el array/secuencia. Esto debe ser conocido en tiempo de compilación.

nombre_enum

Nombre de un campo de enumeración definido previamente con la macro LTTNG_UST_TRACEPOINT_ENUM(). Consulte la sección de uso de *LTTNG_UST_TRACEPOINT_ENUM() para más información.

expr

Expresión C que resulta en el valor del campo. Esta expresión puede usar uno o más argumentos pasados al tracepoint. Los argumentos de un tracepoint dado se definen en la macro LTTNG_UST_TP_ARGS() (ver la sección *Creación de un proveedor de tracepoint* arriba).

nombre_campo

Nombre del campo del evento (sintaxis de identificador C, NO una cadena literal).

tipo_float

Tipo C de punto flotante (float o double). El tamaño de este tipo determina el tamaño del campo de número de punto flotante.

tipo_int

Tipo C entero. El tamaño de este tipo determina el tamaño del campo entero/enumeración.

len_expr

Expresión C que resulta en la longitud de la secuencia. Esta expresión puede usar uno o más argumentos pasados al tracepoint.

tipo_len

Tipo C entero sin signo de la longitud de la secuencia.

nombre_prov

Nombre del proveedor de tracepoint. Debe ser el mismo que el nombre del proveedor de tracepoint utilizado en una definición de campo previa.

Las versiones _nowrite se omiten a sí mismas del registro del trac e, pero son idénticos en lo demás. Su propósito principal es hacer que parte del contexto del evento esté disponible para los filtros de eventos sin tener que confirmar los datos en sub-buffers. Consulte lttng-enable-event(1) para obtener más información sobre el filtrado dinámico de eventos.

Uso de LTTNG_UST_TRACEPOINT_ENUM()

Un campo de enumeración es una lista de mapeos entre enteros, o un rango de enteros, y cadenas (a veces llamadas etiquetas o enumeradores). Los campos de enumeración se pueden usar para tener un rastreo más compacto cuando los valores posibles para un campo son limitados.

Un campo de enumeración se define con la macro LTTNG_UST_TRACEPOINT_ENUM():

LTTNG_UST_TRACEPOINT_ENUM(
    /* Nombre del proveedor del punto de rastreo */
    mi_proveedor,
    /* Nombre de la enumeración (único en todo el proveedor del punto de rastreo) */
    mi_enum,
    /* Mapeos de la enumeración */
    LTTNG_UST_TP_ENUM_VALUES(
        ...
    )
)

LTTNG_UST_TP_ENUM_VALUES() contiene una lista de mapeos de enumeración, NO separados por comas. Se pueden usar dos macros en LTTNG_UST_TP_ENUM_VALUES(): lttng_ust_field_enum_value() y lttng_ust_field_enum_range().

lttng_ust_field_enum_value() es un mapeo de valor único:

lttng_ust_field_enum_value(etiqueta, valor)

Esta macro mapea la cadena etiqueta dada al valor valor.

lttng_ust_field_enum_range() es un mapeo de rango:

lttng_ust_field_enum_range(etiqueta, inicio, fin)

Esta macro mapea la cadena etiqueta dada al rango de enteros desde inicio hasta fin, inclusivamente. Los mapeos de rango pueden superponerse, pero el comportamiento depende de la implementación: cada lector de rastreo maneja los rangos superpuestos como desee.

Uso de LTTNG_UST_TRACEPOINT_EVENT_CLASS()

Una clase de punto de rastreo es una clase de puntos de rastreo que comparten los mismos tipos y nombres de campo. Una instancia de punto de rastreo es una instancia de dicha clase de punto de rastreo declarada, con su propio nombre de evento.

LTTng-UST crea una función de serialización de eventos por clase de punto de rastreo. El uso de LTTNG_UST_TRACEPOINT_EVENT() crea una clase de punto de rastreo por definición de punto de rastreo, mientras que el uso de LTTNG_UST_TRACEPOINT_EVENT_CLASS() y LTTNG_UST_TRACEPOINT_EVENT_INSTANCE() crea una clase de punto de rastreo y una o más instancias de punto de rastreo de esta clase. En otras palabras, muchos puntos de rastreo pueden reutilizar el mismo código de serialización. Reutilizar el mismo código, cuando sea posible, puede reducir la contaminación de la caché, mejorando así el rendimiento.

La macro LTTNG_UST_TRACEPOINT_EVENT_CLASS() acepta los mismos parámetros que la macro LTTNG_UST_TRACEPOINT_EVENT(), excepto que en lugar de un nombre de evento, su segundo parámetro es el nombre de la clase de punto de rastreo:

#define LTTNG_UST_TRACEPOINT_PROVIDER mi_proveedor
/* ... */
LTTNG_UST_TRACEPOINT_EVENT_CLASS(
    /* Nombre del proveedor de la clase de punto de rastreo */
    mi_proveedor,
    /* Nombre de la clase de punto de rastreo */
    mi_clase_punto_rastreo,
    /* Lista de argumentos del punto de rastreo (entrada) */
    LTTNG_UST_TP_ARGS(
        ...
    ),
    /* Lista de campos del evento eventual (salida) */
    LTTNG_UST_TP_FIELDS(
        ...
    )
)

Una vez definida la clase de punto de rastreo, puede crear tantas instancias de punto de rastreo como necesite:

#define LTTNG_UST_TRACEPOINT_PROVIDER natality
/* ... */
LTTNG_UST_TRACEPOINT_EVENT_INSTANCE(
    /* Nombre del proveedor de la clase de punto de rastreo */
    mi_proveedor,
    /* Nombre de la clase de punto de rastreo */
    mi_clase_punto_rastreo,
    /* Nombre del proveedor local (de instancia) */
    natality,
    /* Nombre del punto de rastreo/evento */
    mi_punto_rastreo,
    /* Lista de argumentos del punto de rastreo (entrada) */
    LTTNG_UST_TP_ARGS(
        ...
    )
)

Como puede ver, LTTNG_UST_TRACEPOINT_EVENT_INSTANCE() no contiene la macro LTTNG_UST_TP_FIELDS(), ya que se definen a nivel de LTTNG_UST_TRACEPOINT_EVENT_CLASS().

Tenga en cuenta que la macro LTTNG_UST_TRACEPOINT_EVENT_INSTANCE() requiere dos nombres de proveedor:

•El nombre del proveedor de la clase de punto de rastreo (mi_proveedor en el ejemplo anterior).

Este es el mismo que el primer argumento de la expansión de LTTNG_UST_TRACEPOINT_EVENT_CLASS() al que se hace referencia.

•El nombre del proveedor local, o de instancia (natality en el ejemplo anterior).

Este es el nombre del proveedor que se convierte en la parte prefijo del nombre de los eventos que crea dicho punto de rastreo.

Los dos nombres de proveedor pueden ser diferentes si las macros de clase de punto de rastreo y de instancia de punto de rastreo están en dos unidades de traducción diferentes.

Uso de LTTNG_UST_TRACEPOINT_LOGLEVEL()

Opcionalmente, se puede asignar un nivel de registro a un punto de rastreo definido. Asignar diferentes niveles de severidad a los puntos de rastreo puede ser útil: al controlar las sesiones de rastreo, puede optar por habilitar solo los eventos que caen dentro de un rango específico de nivel de registro utilizando las opciones --loglevel y --loglevel-only del comando lttng-enable-event(1).

Los niveles de registro se asignan a los puntos de rastreo que ya están definidos utilizando la macro LTTNG_UST_TRACEPOINT_LOGLEVEL(). Esta última debe usarse después de haber utilizado LTTNG_UST_TRACEPOINT_EVENT() o LTTNG_UST_TRACEPOINT_EVENT_INSTANCE() para un punto de rastreo dado. La macro LTTNG_UST_TRACEPOINT_LOGLEVEL() se utiliza de la siguiente manera:

LTTNG_UST_TRACEPOINT_LOGLEVEL(
    /* Nombre del proveedor del punto de rastreo */
    mi_proveedor,
    /* Nombre del punto de rastreo/evento */
    mi_punto_rastreo,
    /* Nivel de registro */
    LTTNG_UST_TRACEPOINT_LOGLEVEL_INFO
)

Las definiciones de nivel de registro disponibles son:

LTTNG_UST_TRACEPOINT_LOGLEVEL_EMERG

El sistema no es utilizable.

LTTNG_UST_TRACEPOINT_LOGLEVEL_ALERT

Se debe tomar una acción inmediatamente.

LTTNG_UST_TRACEPOINT_LOGLEVEL_CRIT

Condiciones críticas.

LTTNG_UST_TRACEPOINT_LOGLEVEL_ERR

Condiciones de error.

LTTNG_UST_TRACEPOINT_LOGLEVEL_WARNING

Condiciones de advertencia.

LTTNG_UST_TRACEPOINT_LOGLEVEL_NOTICE

Condición normal, pero significativa.

LTTNG_UST_TRACEPOINT_LOGLEVEL_INFO

Mensaje informativo.

LTTNG_UST_TRACEPOINT_LOGLEVEL_DEBUG_SYSTEM

Información de depuración con alcance a nivel de sistema (conjunto de programas).

LTTNG_UST_TRACEPOINT_LOGLEVEL_DEBUG_PROGRAM

Información de depuración con alcance a nivel de programa (conjunto de procesos).

LTTNG_UST_TRACEPOINT_LOGLEVEL_DEBUG_PROCESS

Información de depuración con alcance a nivel de proceso (conjunto de módulos).

LTTNG_UST_TRACEPOINT_LOGLEVEL_DEBUG_MODULE

Información de depuración con alcance a nivel de módulo (ejecutable/biblioteca) (conjunto de unidades).

LTTNG_UST_TRACEPOINT_LOGLEVEL_DEBUG_UNIT

Información de depuración con alcance a nivel de unidad de compilación (conjunto de funciones).

LTTNG_UST_TRACEPOINT_LOGLEVEL_DEBUG_FUNCTION

Información de depuración con alcance a nivel de función.

LTTNG_UST_TRACEPOINT_LOGLEVEL_DEBUG_LINE

Instrumentar tu aplicación

Una vez creado el proveedor de puntos de rastreo (consulte la sección Creación de un proveedor de puntos de rastreo anterior), puede instrumentar su aplicación con los puntos de rastreo definidos gracias a la macro lttng_ust_tracepoint():

#define lttng_ust_tracepoint(nombre_prov, nombre_t, ...)

Con:

nombre_prov

Nombre del proveedor del punto de rastreo.

nombre_t

Nombre del punto de rastreo/evento.

...

Argumentos del punto de rastreo, si los hay.

Asegúrese de incluir el archivo de cabecera del proveedor del punto de rastreo en cualquier lugar donde utilice lttng_ust_tracepoint() para este proveedor.


Nota

Aunque LTTng-UST admite duplicados en el sitio de llamada de lttng_ust_tracepoint() con los mismos nombres de proveedor y punto de rastreo, se recomienda utilizar un par proveedor/punto de rastreo solo una vez dentro del código fuente de la aplicación para ayudar a mapear los eventos a sus sitios de llamada al analizar el rastreo.

A veces, los argumentos del punto de rastreo son costosos de calcular (por ejemplo, tomar la pila de llamadas). Para evitar el cálculo cuando el punto de rastreo está deshabilitado, puede usar las macros lttng_ust_tracepoint_enabled() y lttng_ust_do_tracepoint():

#define lttng_ust_tracepoint_enabled(nombre_prov, nombre_t)
#define lttng_ust_do_tracepoint(nombre_prov, nombre_t, ...)

lttng_ust_tracepoint_enabled() devuelve un valor distinto de cero si el punto de rastreo llamado nombre_t del proveedor llamado nombre_prov está habilitado en tiempo de ejecución.

lttng_ust_do_tracepoint() es como lttng_ust_tracepoint(), excepto que no verifica si el punto de rastreo está habilitado. El uso de lttng_ust_tracepoint() con lttng_ust_tracepoint_enabled() es peligroso ya que lttng_ust_tracepoint() también contiene la verificación de lttng_ust_tracepoint_enabled(), por lo tanto, es posible una condición de carrera en esta situación:

if (lttng_ust_tracepoint_enabled(mi_proveedor, mi_punto_rastreo)) {
    cosas = preparar_cosas();
}
lttng_ust_tracepoint(mi_proveedor, mi_punto_rastreo, cosas);

Si el punto de rastreo se habilita después de la condición, entonces cosas no se prepara: el evento emitido contendrá datos incorrectos, o la aplicación completa podría fallar (por ejemplo, error de segmentación).


Nota

Ni lttng_ust_tracepoint_enabled() ni lttng_ust_do_tracepoint() tienen una llamada STAP_PROBEV(), por lo que si la necesita, debe emitirla usted mismo.

_C/C++_constructors_and_destructors'>Rastreo de constructores y destructores C/C++

Si se cumple una de las siguientes condiciones:

• Compilas tu aplicación C++ con GCC ≤ 4.8.
• Compilas tu aplicación C/C++ con un compilador C++ y defines LTTNG_UST_ALLOCATE_COMPOUND_LITERAL_ON_HEAP.

Entonces LTTng no rastreará:

• Constructores y destructores C en la propia aplicación o en archivos enlazados estáticamente.
• Algunos constructores y destructores C++ en la propia aplicación o en archivos enlazados estáticamente.

En este caso, qué constructores y destructores C++ exactos no se rastrearán depende del orden de inicialización dentro de cada unidad de traducción y entre todas las unidades de traducción cuando se enlazan juntas.

Enlace estático del proveedor de puntos de traza

Con el método de enlace estático, los proveedores de puntos de traza compilados se copian en la aplicación de destino.

Define la macro LTTNG_UST_TRACEPOINT_DEFINE debajo de la definición de LTTNG_UST_TRACEPOINT_CREATE_PROBES en el código fuente del proveedor de puntos de traza:

#define LTTNG_UST_TRACEPOINT_CREATE_PROBES
#define LTTNG_UST_TRACEPOINT_DEFINE
#include "tp.h"

Crea el archivo objeto del proveedor de puntos de traza:

$ cc -c -I. tp.c

Nota

Aunque una aplicación instrumentada con puntos de traza LTTng-UST puede compilarse con un compilador C++, los puntos de traza deben compilarse con un compilador C.

En este punto, puedes archivar este archivo objeto del proveedor de puntos de traza, posiblemente con otros archivos objeto de tu aplicación o con otros archivos objeto de proveedores de puntos de traza, como una biblioteca estática:

$ ar rc tp.a tp.o

Usar una biblioteca estática tiene la ventaja de centralizar los objetos del proveedor de puntos de traza para que puedan ser compartidos entre múltiples aplicaciones. De esta manera, cuando se modifica el proveedor de puntos de traza, los cambios en el código fuente no tienen que ser parcheados en el árbol de código fuente de cada aplicación. Las aplicaciones necesitan ser enlazadas nuevamente después de cada cambio, pero no necesitan ser recompiladas de otra manera (a menos que la API del proveedor de puntos de traza cambie).

Luego, enlaza tu aplicación con este archivo objeto (o con la biblioteca estática que lo contiene) y con liblttng-ust y libdl (libc en un sistema BSD):

$ cc -o app tp.o app.o -llttng-ust -ldl

Carga dinámica del proveedor de puntos de traza

El segundo enfoque para empaquetar el proveedor de puntos de traza es utilizar el cargador dinámico: la biblioteca y sus funciones miembro se buscan explícitamente, se cargan en tiempo de ejecución.

En este escenario, el proveedor de puntos de traza se compila como un objeto compartido.

El proceso para crear el objeto compartido del proveedor de puntos de traza es prácticamente el mismo que el método de enlace estático, excepto que:

• Dado que el proveedor de puntos de traza no forma parte de la aplicación, LTTNG_UST_TRACEPOINT_DEFINE debe definirse, para cada proveedor de puntos de traza, en exactamente un archivo fuente de la aplicación.
• LTTNG_UST_TRACEPOINT_PROBE_DYNAMIC_LINKAGE debe definirse junto a LTTNG_UST_TRACEPOINT_DEFINE.

Respecto a LTTNG_UST_TRACEPOINT_DEFINE y LTTNG_UST_TRACEPOINT_PROBE_DYNAMIC_LINKAGE, la práctica recomendada es usar un archivo fuente C separado en tu aplicación para definirlos, e incluir después los archivos de cabecera del proveedor de puntos de traza. Por ejemplo, como tp-define.c:

#define LTTNG_UST_TRACEPOINT_DEFINE
#define LTTNG_UST_TRACEPOINT_PROBE_DYNAMIC_LINKAGE
#include "tp.h"

El archivo objeto del proveedor de puntos de traza utilizado para crear la biblioteca compartida se construye como se hace con el método de enlace estático, pero con la opción -fpic:

$ cc -c -fpic -I. tp.c

Luego se enlaza como biblioteca compartida de la siguiente manera:

$ cc -shared -Wl,--no-as-needed -o tp.so tp.o -llttng-ust

Este objeto compartido del proveedor de puntos de traza no se enlaza con la aplicación de usuario: debe cargarse manualmente. Es por eso que la aplicación se construye sin mención de este proveedor de puntos de traza, pero aún necesita libdl:

$ cc -o app app.o tp-define.o -ldl

Hay dos formas de cargar dinámicamente el objeto compartido del proveedor de puntos de traza:

• Cargarlo manualmente desde la aplicación usando dlopen(3).
• Hacer que el cargador dinámico lo cargue con la variable de entorno LD_PRELOAD (ver ld.so(8)).

Si la aplicación no carga dinámicamente el objeto compartido del proveedor de puntos de traza utilizando uno de los métodos anteriores, el rastreo se deshabilita para esta aplicación, y los eventos no se listan en la salida de lttng-list(1).

Tenga en cuenta que no es seguro usar dlclose(3) en un objeto compartido de proveedor de puntos de traza que se está utilizando activamente para el rastreo, debido a la falta de conteo de referencias de LTTng-UST al objeto compartido.

Por ejemplo, enlazar estáticamente un proveedor de puntos de traza a un objeto compartido que será cargado dinámicamente por una aplicación (un plugin, por ejemplo) no es seguro: el objeto compartido, que contiene el proveedor de puntos de traza, podría ser cerrado dinámicamente (dlclose(3)) en cualquier momento por la aplicación.

Para instrumentar un objeto compartido, ya sea:

• Enlazar estáticamente el proveedor de puntos de traza a la aplicación, o
• Construir el proveedor de puntos de traza como un objeto compartido (siguiendo el procedimiento que se muestra en esta sección), y precargarlo cuando se necesite el rastreo usando la variable de entorno LD_PRELOAD.

Uso de LTTng-UST con demonios

Se requiere un cuidado adicional al usar liblttng-ust con aplicaciones demonio que llaman a fork(2), clone(2), o el rfork(2) de BSD sin una llamada posterior a la familia de sistema exec(3). La biblioteca liblttng-ust-fork.so necesita ser precargada antes de iniciar la aplicación con la variable de entorno LD_PRELOAD (ver ld.so(8)).

Para usar liblttng-ust con una aplicación demonio que cierra descriptores de archivo que no fueron abiertos por ella, precarga la biblioteca liblttng-ust-fd.so antes de iniciar la aplicación. Los casos de uso típicos incluyen demonios que cierran todos los descriptores de archivo después de fork(2), y aplicaciones con errores que realizan "cierres dobles".

Detectar si LTTng-UST está cargado

Para detectar si liblttng-ust está cargado desde una aplicación:

int lttng_ust_loaded __attribute__((weak));

Este símbolo débil es establecido por el constructor de liblttng-ust.

2.Prueba lttng_ust_loaded donde sea necesario: 
/* ... */
if (lttng_ust_loaded) {
    /* LTTng-UST está cargado */
} else {
    /* LTTng-UST NO está cargado */
}
/* ... */

};
int main(int argc, char* argv[])

    FILE *stream;

    lttng_ust_tracepoint(my_provider, simple_event, argc, argv[0]);

                "Error: Cannot open /tmp/app.txt for writing\n");

    }
    if (fprintf(stream, "0123456789") != 10) {
        fclose(stream);
        fprintf(stderr, "Error: Cannot write to /tmp/app.txt\n");
        return EXIT_FAILURE;
    }
    lttng_ust_tracepoint(my_provider, big_event, 35,
                         "hello tracepoint", stream, -3.14,
                         array_of_ints);
    fclose(stream);
    app_struct.b = argc;
    app_struct.c = "[the string]";
    lttng_ust_tracepoint(my_provider, event_instance1, 23,
                         &app_struct);
    app_struct.b = argc * 5;
    app_struct.c = "[other string]";
    lttng_ust_tracepoint(my_provider, event_instance2, 17,

    app_struct.c = "nothing";
    lttng_ust_tracepoint(my_provider, event_instance3, -52,

VARIABLES DE ENTORNO

LTTNG_HOME

Directorio de inicio alternativo del usuario. Esta variable es útil cuando el usuario que ejecuta la aplicación instrumentada tiene un directorio de inicio no escribible. Esta ruta es donde se encuentran los sockets Unix para la comunicación con el demonio de sesión por usuario.

LTTNG_UST_ABORT_ON_CRITICAL

Si está configurado, aborta la aplicación instrumentada en un mensaje de error crítico.

LTTNG_UST_ALLOW_BLOCKING

Si está configurado, permite que la aplicación intente trazar eventos cuando no hay espacio para el registro del evento en el sub-búfer, bloqueando efectivamente la aplicación hasta que se libere espacio o se alcance el tiempo de espera configurado.

Para permitir que una aplicación se bloquee durante el trazado, también debes especificar un tiempo de espera de bloqueo cuando creas un canal con la opción --blocking-timeout del comando lttng-enable-channel(1).

Esta opción puede ser útil en cargas de trabajo que generan un rendimiento de datos de traza muy grande, donde bloquear la aplicación es un compromiso aceptable para evitar descartar registros de eventos.


Advertencia
Establecer esta variable de entorno puede afectar significativamente los tiempos de la aplicación.

LTTNG_UST_APP_PATH

Ruta del directorio donde se espera que el demonio de sesión LTTng coloque los siguientes archivos para recibir solicitudes de conexión de la aplicación instrumentada:
•El socket Unix de registro de la aplicación.
•Los archivos de memoria compartida "wait" para despertar aplicaciones instrumentadas que están esperando que se inicie un demonio de sesión.
•El archivo del puerto del agente.

Este archivo contiene el puerto TCP al que los agentes deben conectarse para habilitar el trazado LTTng.

Este directorio debe existir cuando inicies la aplicación para que el trazado LTTng esté habilitado.

Cuando LTTNG_UST_APP_PATH está configurado, liblttng-ust:

•Solo considera esta ruta para conectarse a un demonio de sesión.
•No se conectará a demonios de sesión raíz y/o de usuario como de costumbre.

Ver la variable de entorno correspondiente LTTNG_UST_CTL_PATH de lttng-sessiond(8).

LTTNG_UST_CLOCK_PLUGIN

Ruta al objeto compartido que actúa como plugin de reemplazo de reloj. Un ejemplo de dicho plugin se puede encontrar en la documentación de LTTng-UST bajo examples/clock-override https://github.com/lttng/lttng-ust/tree/stable-2.14/doc/examples/clock-override.

VARIABLES DE ENTORNO

LTTNG_UST_DEBUG

Si se establece, activa la salida de depuración y de errores de liblttng-ust.

LTTNG_UST_GETCPU_PLUGIN

Ruta al objeto compartido que actúa como plugin de reemplazo de getcpu(). Un ejemplo de dicho plugin se puede encontrar en la documentación de LTTng-UST bajo examples/getcpu-override https://github.com/lttng/lttng-ust/tree/stable-2.14/doc/examples/getcpu-override.

LTTNG_UST_MAP_POPULATE_POLICY

Si se establece, anula la política utilizada para poblar las páginas de memoria compartida dentro de la aplicación.

Los valores posibles son:

none (predeterminado)

No pre-poblar ninguna página: tomar fallos menores en el primer acceso mientras se rastrea.

cpu_possible

Pre-poblar páginas para todas las CPU posibles en el sistema, como se muestra en /sys/devices/system/cpu/possible.

LTTNG_UST_REGISTER_TIMEOUT

Tiempo de espera para el comando del demonio de sesión registration done antes de proceder a ejecutar el programa principal (milisegundos).

El valor 0 significa no esperar. El valor -1 significa esperar para siempre. Se recomienda establecer esta variable de entorno a 0 para aplicaciones con restricciones de tiempo en el tiempo de inicio del proceso.

Predeterminado: 3000.

LTTNG_UST_WITHOUT_BADDR_STATEDUMP

Si se establece, evita que liblttng-ust realice un volcado de estado de dirección base (ver la sección Vaciado de estado de LTTng-UST anterior).

LTTNG_UST_WITHOUT_PROCNAME_STATEDUMP

Si se establece, evita que liblttng-ust realice un volcado de estado de nombre de proceso (ver la sección Vaciado de estado de LTTng-UST anterior).
