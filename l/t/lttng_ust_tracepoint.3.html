DESCRIPCIÓN

El proyecto Linux Trace Toolkit: next generation http://lttng.org/ es un paquete de software de código abierto utilizado para el trazado correlacionado del kernel de Linux, aplicaciones de usuario y bibliotecas de usuario.

LTTng-UST es el componente de trazado en el espacio de usuario del proyecto LTTng. Es una adaptación al espacio de usuario de las capacidades de trazado de baja sobrecarga del trazador del kernel de Linux LTTng. La biblioteca liblttng-ust se utiliza para trazar aplicaciones y bibliotecas de usuario.


Nota

Esta página del manual trata sobre la biblioteca liblttng-ust. El proyecto LTTng-UST también proporciona paquetes Java y Python para trazar aplicaciones escritas en esos idiomas. Cómo instrumentar y trazar aplicaciones Java y Python se documenta en la documentación en línea de LTTng http://lttng.org/docs/.

Hay tres formas de usar liblttng-ust:

•Usando la API lttng_ust_tracef(3), que es similar a printf(3).
•Usando la API lttng_ust_tracelog(3), que es lttng_ust_tracef(3) con un parámetro de nivel de registro.
•Definiendo sus propios puntos de trazado. Consulte la sección Creación de un proveedor de puntos de trazado más abajo.

Compatibilidad con APIs anteriores

Desde LTTng-UST 2.13, la definición LTTNG_UST_COMPAT_API_VERSION controla qué APIs de LTTng-UST están disponibles (compiladas):

Indefinido

Todas las APIs están disponibles.

N (0 o entero positivo)

La versión de API N, y todas las APIs existentes siguientes, están disponibles. Las APIs anteriores no están disponibles (no compiladas).

La siguiente tabla muestra el mapeo de las versiones de LTTng-UST (hasta LTTng-UST 2.14.0) a las versiones de API disponibles:

Versión de LTTng-UST Versiones de API disponibles
2.0 a 2.12 0
2.13 0 y 1

Esta página del manual solo documenta la versión 1 de la API.

Si desea tener acceso a la versión 0 de la API (por ejemplo, las macros tracepoint(), ctf_integer() y TRACEPOINT_EVENT()), entonces no defina LTTNG_UST_COMPAT_API_VERSION, o defínela a 0 antes de incluir cualquier encabezado de LTTng-UST.

Creación de un proveedor de puntos de trazado

Crear un proveedor de puntos de trazado es el primer paso para usar liblttng-ust. Los pasos siguientes son:

•Instrumentar su aplicación con llamadas a lttng_ust_tracepoint()
•Compilar su aplicación con soporte LTTng-UST
, ya sea estáticamente o dinámicamente.

Un proveedor de tracepoint es un objeto compilado que contiene las sondas de eventos correspondientes a sus definiciones de tracepoint personalizadas. Un proveedor de tracepoint contiene el código para obtener el tamaño de un evento y para serializarlo, entre otras cosas.

Para crear un proveedor de tracepoint, comience con la siguiente plantilla de encabezado del proveedor de tracepoint:

#undef LTTNG_UST_TRACEPOINT_PROVIDER
#define LTTNG_UST_TRACEPOINT_PROVIDER mi_proveedor
#undef LTTNG_UST_TRACEPOINT_INCLUDE
#define LTTNG_UST_TRACEPOINT_INCLUDE "./tp.h"
#if !defined(_TP_H) || \
    defined(LTTNG_UST_TRACEPOINT_HEADER_MULTI_READ)
#define _TP_H
#include <lttng/tracepoint.h>
/*
 * LTTNG_UST_TRACEPOINT_EVENT(), LTTNG_UST_TRACEPOINT_EVENT_CLASS(),
 * LTTNG_UST_TRACEPOINT_EVENT_INSTANCE(),
 * LTTNG_UST_TRACEPOINT_LOGLEVEL(), y `LTTNG_UST_TRACEPOINT_ENUM()`
 * se utilizan aquí.
 */
#endif /* _TP_H */
#include <lttng/tracepoint-event.h>

En esta plantilla, el proveedor de tracepoint se llama mi_proveedor (definición de LTTNG_UST_TRACEPOINT_PROVIDER). El archivo debe tener el nombre de la definición de LTTNG_UST_TRACEPOINT_INCLUDE (tp.h en este caso). Entre #include <lttng/tracepoint.h> y #endif van las invocaciones de las macros LTTNG_UST_TRACEPOINT_EVENT(), LTTNG_UST_TRACEPOINT_EVENT_CLASS(), LTTNG_UST_TRACEPOINT_EVENT_INSTANCE(), LTTNG_UST_TRACEPOINT_LOGLEVEL() y LTTNG_UST_TRACEPOINT_ENUM().


Nota

Puede evitar escribir el código repetitivo del prólogo y epílogo en el archivo de plantilla anterior utilizando la herramienta lttng-gen-tp(1) incluida con LTTng-UST.

El archivo de encabezado del proveedor de tracepoint debe incluirse en un archivo fuente que se vea así:

#define LTTNG_UST_TRACEPOINT_CREATE_PROBES
#include "tp.h"

Juntos, esos dos archivos (llamémoslos tp.h y tp.c) forman los fuentes del proveedor de tracepoint, listos para ser compilados.

Puede crear múltiples proveedores de tracepoint para ser utilizados en una única aplicación, pero cada uno debe tener su propio archivo de encabezado.

La sección de uso de LTTNG_UST_TRACEPOINT_EVENT() a continuación muestra cómo usar la macro LTTNG_UST_TRACEPOINT_EVENT() para definir los tracepoints reales en el archivo de encabezado del proveedor de tracepoint.

Uso de LTTNG_UST_TRACEPOINT_EVENT()

La macro LTTNG_UST_TRACEPOINT_EVENT() se utiliza en un archivo de encabezado de proveedor de plantilla (ver la sección Creación de un proveedor de tracepoint anterior) para definir tracepoints LTTng-UST.

La plantilla de uso de LTTNG_UST_TRACEPOINT_EVENT() es la siguiente:

LTTNG_UST_TRACEPOINT_EVENT(
    /* Nombre del proveedor de tracepoint */
    mi_proveedor,
    /* Nombre del tracepoint/evento */
    mi_tracepoint,
    /* Lista de argumentos del tracepoint (entrada) */
    LTTNG_UST_TP_ARGS(
        ...
    ),
    /* Lista de campos del evento resultante (salida) */
    LTTNG_UST_TP_FIELDS(
        ...
    )
)

La macro LTTNG_UST_TP_ARGS() contiene los argumentos de entrada del tracepoint. Estos argumentos se pueden usar en las expresiones de los campos de salida definidos en LTTNG_UST_TP_FIELDS().

El formato de los parámetros de LTTNG_UST_TP_ARGS() es: tipo C, luego nombre del argumento; repetir según sea necesario, hasta diez veces. Por ejemplo:

LTTNG_UST_TP_ARGS(
    int, mi_entero,
    const char *, mi_cadena,
    FILE *, mi_archivo,
    double, mi_flotante,
    struct my_data *, mis_datos
)

La macro LTTNG_UST_TP_FIELDS() contiene los campos de salida del tracepoint, es decir, los datos reales que se pueden registrar en la carga útil de un evento emitido por este tracepoint.

La macro LTTNG_UST_TP_FIELDS() contiene una lista de macros lttng_ust_field_*() NO separadas por comas. Las macros disponibles se documentan en la sección Macros de tipos de campo disponibles lttng_ust_field_*() a continuación.

lttng_ust_field_sequence_text(char, nombre_campo, expr, tipo_len,

lttng_ust_field_sequence_text_nowrite(char, nombre_campo, expr,

Enumeración. El campo de enumeración debe definirse antes de usar esta macro con la macro LTTNG_UST_TRACEPOINT_ENUM(). Consulte la sección de uso de LTTNG_UST_TRACEPOINT_ENUM() para obtener más información.

lttng_ust_field_enum(nombre_prov, nombre_enum, tipo_int, nombre_campo,
                     expr)
lttng_ust_field_enum_nowrite(nombre_prov, nombre_enum, tipo_int,
                             nombre_campo, expr)

Los parámetros son:

count

Número de elementos en el array/secuencia. Esto debe conocerse en tiempo de compilación.

nombre_enum

Nombre de un campo de enumeración definido previamente con la macro LTTNG_UST_TRACEPOINT_ENUM(). Consulte la sección de uso de LTTNG_UST_TRACEPOINT_ENUM() para obtener más información.

expr

Expresión C que resulta en el valor del campo. Esta expresión puede usar uno o más argumentos pasados al tracepoint. Los argumentos de un tracepoint dado se definen en la macro LTTNG_UST_TP_ARGS() (ver la sección Creación de un proveedor de tracepoint anterior).

nombre_campo

Nombre del campo del evento (sintaxis de identificador C, NO una cadena literal).

tipo_float

Tipo C de punto flotante (float o double). El tamaño de este tipo determina el tamaño del campo del número de punto flotante.

tipo_int

Tipo C entero. El tamaño de este tipo determina el tamaño del campo entero/enumeración.

len_expr

Expresión C que resulta en la longitud de la secuencia. Esta expresión puede usar uno o más argumentos pasados al tracepoint.

tipo_len

Tipo C entero sin signo de la longitud de la secuencia.

nombre_prov

Nombre del proveedor de tracepoint. Debe ser el mismo que el nombre del proveedor de tracepoint utilizado en una definición de campo anterior.

Las versiones _nowrite se omiten a sí mismas del trazo registrado, pero son idénticos en lo demás. Su propósito principal es poner a disposición de los filtros de eventos parte del contexto del evento sin tener que confirmar los datos en sub-buffers. Consulte lttng-enable-event(1) para obtener más información sobre el filtrado dinámico de eventos.

Uso de LTTNG_UST_TRACEPOINT_ENUM()

Un campo de enumeración es una lista de mapeos entre enteros, o un rango de enteros, y cadenas de texto (a veces llamadas etiquetas o enumeradores). Los campos de enumeración se pueden usar para tener un rastro más compacto cuando los valores posibles para un campo son limitados.

Un campo de enumeración se define con la macro LTTNG_UST_TRACEPOINT_ENUM():

LTTNG_UST_TRACEPOINT_ENUM(
    /* Nombre del proveedor del punto de traza */
    mi_proveedor,
    /* Nombre de la enumeración (único en todo el proveedor de puntos de traza) */
    mi_enum,
    /* Mapeos de la enumeración */
    LTTNG_UST_TP_ENUM_VALUES(
        ...
    )
)

LTTNG_UST_TP_ENUM_VALUES() contiene una lista de mapeos de enumeración, NO separados por comas. Se pueden usar dos macros en LTTNG_UST_TP_ENUM_VALUES(): lttng_ust_field_enum_value() y lttng_ust_field_enum_range().

lttng_ust_field_enum_value() es un mapeo de valor único:

lttng_ust_field_enum_value(etiqueta, valor)

Esta macro mapea la cadena etiqueta dada al valor valor.

lttng_ust_field_enum_range() es un mapeo de rango:

lttng_ust_field_enum_range(etiqueta, inicio, fin)

Esta macro mapea la cadena etiqueta dada al rango de enteros desde inicio hasta fin, ambos inclusive. Los mapeos de rango pueden solaparse, pero el comportamiento está definido por la implementación: cada lector de trazas maneja los rangos solapados como desee.

Uso de LTTNG_UST_TRACEPOINT_EVENT_CLASS()

Una clase de punto de traza es una clase de puntos de traza que comparten los mismos tipos y nombres de campo. Una instancia de punto de traza es una instancia de dicha clase de punto de traza declarada, con su propio nombre de evento.

LTTng-UST crea una función de serialización de eventos por clase de punto de traza. El uso de LTTNG_UST_TRACEPOINT_EVENT() crea una clase de punto de traza por definición de punto de traza, mientras que el uso de LTTNG_UST_TRACEPOINT_EVENT_CLASS() y LTTNG_UST_TRACEPOINT_EVENT_INSTANCE() crea una clase de punto de traza, y una o más instancias de punto de traza de esta clase. En otras palabras, muchos puntos de traza pueden reutilizar el mismo código de serialización. Reutilizar el mismo código, cuando sea posible, puede reducir la contaminación de la caché, mejorando así el rendimiento.

La macro LTTNG_UST_TRACEPOINT_EVENT_CLASS() acepta los mismos parámetros que la macro LTTNG_UST_TRACEPOINT_EVENT(), excepto que en lugar de un nombre de evento, su segundo parámetro es el nombre de la clase de punto de traza:

#define LTTNG_UST_TRACEPOINT_PROVIDER mi_proveedor
/* ... */
LTTNG_UST_TRACEPOINT_EVENT_CLASS(
    /* Nombre del proveedor de la clase de punto de traza */
    mi_proveedor,
    /* Nombre de la clase de punto de traza */
    mi_clase_punto_traza,
    /* Lista de argumentos del punto de traza (entrada) */
    LTTNG_UST_TP_ARGS(
        ...
    ),
    /* Lista de campos del evento eventual (salida) */
    LTTNG_UST_TP_FIELDS(
        ...
    )
)

Una vez definida la clase de punto de traza, puede crear tantas instancias de punto de traza como sea necesario:

#define LTTNG_UST_TRACEPOINT_PROVIDER natalidad
/* ... */
LTTNG_UST_TRACEPOINT_EVENT_INSTANCE(
    /* Nombre del proveedor de la clase de punto de traza */
    mi_proveedor,
    /* Nombre de la clase de punto de traza */
    mi_clase_punto_traza,
    /* Nombre del proveedor local (de instancia) del punto de traza */
    natalidad,
    /* Nombre del punto de traza/evento */
    mi_punto_traza,
    /* Lista de argumentos del punto de traza (entrada) */
    LTTNG_UST_TP_ARGS(
        ...
    )
)

Como puede ver, LTTNG_UST_TRACEPOINT_EVENT_INSTANCE() no contiene la macro LTTNG_TP_FIELDS(), ya que se definen a nivel de LTTNG_UST_TRACEPOINT_EVENT_CLASS().

Tenga en cuenta que la macro LTTNG_UST_TRACEPOINT_EVENT_INSTANCE() requiere dos nombres de proveedor:

•El nombre del proveedor de la clase de punto de traza (mi_proveedor en el ejemplo anterior).

Este es el mismo que el primer argumento de la expansión de LTTNG_UST_TRACEPOINT_EVENT_CLASS() al que referirse.

•El nombre del proveedor local, o de instancia, (natalidad en el ejemplo anterior).

Este es el nombre del proveedor que se convierte en la parte prefijo del nombre de los eventos que crea dicho punto de traza.

Los dos nombres de proveedor pueden ser diferentes si las macros de la clase de punto de traza y de la instancia de punto de traza están en dos unidades de traducción distintas.

Uso de LTTNG_UST_TRACEPOINT_LOGLEVEL()

Opcionalmente, se puede asignar un nivel de registro a un punto de traza definido. Asignar diferentes niveles de severidad a los puntos de traza puede ser útil: al controlar las sesiones de traza, puede optar por habilitar solo eventos que caigan dentro de un rango de nivel de registro específico utilizando las opciones --loglevel y --loglevel-only del comando lttng-enable-event(1).

Los niveles de registro se asignan a puntos de traza que ya están definidos utilizando la macro LTTNG_UST_TRACEPOINT_LOGLEVEL(). Esta última debe usarse después de haber utilizado LTTNG_UST_TRACEPOINT_EVENT() o LTTNG_UST_TRACEPOINT_EVENT_INSTANCE() para un punto de traza dado. La macro LTTNG_UST_TRACEPOINT_LOGLEVEL() se utiliza de la siguiente manera:

LTTNG_UST_TRACEPOINT_LOGLEVEL(
    /* Nombre del proveedor del punto de traza */
    mi_proveedor,
    /* Nombre del punto de traza/evento */
    mi_punto_traza,
    /* Nivel de registro */
    LTTNG_UST_TRACEPOINT_LOGLEVEL_INFO
)

Las definiciones de nivel de registro disponibles son:

LTTNG_UST_TRACEPOINT_LOGLEVEL_EMERG

El sistema no es utilizable.

LTTNG_UST_TRACEPOINT_LOGLEVEL_ALERT

Se debe tomar acción inmediatamente.

LTTNG_UST_TRACEPOINT_LOGLEVEL_CRIT

Condiciones críticas.

LTTNG_UST_TRACEPOINT_LOGLEVEL_ERR

Condiciones de error.

LTTNG_UST_TRACEPOINT_LOGLEVEL_WARNING

Condiciones de advertencia.

LTTNG_UST_TRACEPOINT_LOGLEVEL_NOTICE

Condición normal, pero significativa.

LTTNG_UST_TRACEPOINT_LOGLEVEL_INFO

Mensaje informativo.

LTTNG_UST_TRACEPOINT_LOGLEVEL_DEBUG_SYSTEM

Información de depuración con alcance a nivel de sistema (conjunto de programas).

LTTNG_UST_TRACEPOINT_LOGLEVEL_DEBUG_PROGRAM

Información de depuración con alcance a nivel de programa (conjunto de procesos).

LTTNG_UST_TRACEPOINT_LOGLEVEL_DEBUG_PROCESS

Información de depuración con alcance a nivel de proceso (conjunto de módulos).

LTTNG_UST_TRACEPOINT_LOGLEVEL_DEBUG_MODULE

Información de depuración con alcance a nivel de módulo (ejecutable/biblioteca) (conjunto de unidades).

LTTNG_UST_TRACEPOINT_LOGLEVEL_DEBUG_UNIT

Información de depuración con alcance a nivel de unidad de compilación (conjunto de funciones).

LTTNG_UST_TRACEPOINT_LOGLEVEL_DEBUG_FUNCTION

Información de depuración con alcance a nivel de función.

LTTNG_UST_TRACEPOINT_LOGLEVEL_DEBUG_LINE

Información de depuración con alcance a nivel de línea (nivel de registro predeterminado).

Instrumentar su aplicación

Una vez creado el proveedor de puntos de traza (consulte la sección Creación de un proveedor de puntos de traza más arriba), puede instrumentar su aplicación con los puntos de traza definidos gracias a la macro lttng_ust_tracepoint():

#define lttng_ust_tracepoint(nombre_prov, nombre_t, ...)

Con:

nombre_prov

Nombre del proveedor del punto de traza.

nombre_t

Nombre del punto de traza/evento.

...

Argumentos del punto de traza, si los hay.

Asegúrese de incluir el archivo de encabezado del proveedor del punto de traza en cualquier lugar donde utilice lttng_ust_tracepoint() para este proveedor.


Nota

Aunque LTTng-UST admite duplicados en el sitio de llamada de lttng_ust_tracepoint() con los mismos nombres de proveedor y punto de traza, se recomienda utilizar un par de nombres de proveedor/punto de traza solo una vez dentro del código fuente de la aplicación para ayudar a mapear los eventos a sus sitios de llamada al analizar la traza.

A veces, los argumentos del punto de traza son costosos de calcular (toman la pila de llamadas, por ejemplo). Para evitar el cálculo cuando el punto de traza está deshabilitado, puede utilizar las macros lttng_ust_tracepoint_enabled() y lttng_ust_do_tracepoint():

#define lttng_ust_tracepoint_enabled(nombre_prov, nombre_t)
#define lttng_ust_do_tracepoint(nombre_prov, nombre_t, ...)

lttng_ust_tracepoint_enabled() devuelve un valor distinto de cero si el punto de traza llamado nombre_t del proveedor llamado nombre_prov está habilitado en tiempo de ejecución.

lttng_ust_do_tracepoint() es como lttng_ust_tracepoint(), excepto que no comprueba si el punto de traza está habilitado. El uso de lttng_ust_tracepoint() con lttng_ust_tracepoint_enabled() es peligroso, ya que lttng_ust_tracepoint() también contiene la comprobación de lttng_ust_tracepoint_enabled(), por lo que es posible una condición de carrera en esta situación:

if (lttng_ust_tracepoint_enabled(mi_proveedor, mi_punto_traza)) {
    cosas = preparar_cosas();
}
lttng_ust_tracepoint(mi_proveedor, mi_punto_traza, cosas);

Si el punto de traza está habilitado después de la condición, entonces cosas no se prepara: el evento emitido contendrá datos incorrectos, o la aplicación completa podría fallar (fallo de segmentación, por ejemplo).


Nota

Ni lttng_ust_tracepoint_enabled() ni lttng_ust_do_tracepoint() tienen una llamada STAP_PROBEV(), por lo que si la necesita, debe emitir esta llamada usted mismo.

Trazado de constructores y destructores de C/C++

Si se cumple una de las siguientes condiciones:

•Compilas tu aplicación C++ con GCC  ≤ 4.8.
•Compilas tu aplicación C/C++ con un compilador C++ y defines LTTNG_UST_ALLOCATE_COMPOUND_LITERAL_ON_HEAP.

Entonces LTTng no trazará:

•Constructores y destructores de C en la propia aplicación o en archivos enlazados estáticamente.
•Algunos constructores y destructores de C++ en la propia aplicación o en archivos enlazados estáticamente.

En este caso, qué constructores y destructores de C++ exactos no serán trazados dependerá del orden de inicialización dentro de cada unidad de traducción y entre todas las unidades de traducción cuando se enlacen juntas.

Enlazado estático del proveedor de tracepoints

Con el método de enlace estático, los proveedores de tracepoints compilados se copian en la aplicación de destino.

Define la definición LTTNG_UST_TRACEPOINT_DEFINE debajo de la definición LTTNG_UST_TRACEPOINT_CREATE_PROBES en el código fuente del proveedor de tracepoints:

#define LTTNG_UST_TRACEPOINT_CREATE_PROBES
#define LTTNG_UST_TRACEPOINT_DEFINE
#include "tp.h"

Crea el archivo objeto del proveedor de tracepoints:

$ cc -c -I. tp.c

Nota

Aunque una aplicación instrumentada con tracepoints LTTng-UST puede ser compilada con un compilador C++, las sondas de tracepoints deben ser compiladas con un compilador C.

En este punto, puedes archivar este archivo objeto del proveedor de tracepoints, posiblemente con otros archivos objeto de tu aplicación o con otros archivos objeto de proveedores de tracepoints, como una biblioteca estática:

$ ar rc tp.a tp.o

El uso de una biblioteca estática tiene la ventaja de centralizar los objetos del proveedor de tracepoints para que puedan ser compartidos entre múltiples aplicaciones. De esta manera, cuando se modifica el proveedor de tracepoints, los cambios en el código fuente no tienen que ser parcheados en el árbol de código fuente de cada aplicación. Las aplicaciones necesitan ser re-enlazadas después de cada cambio, pero no necesitan ser recompiladas de otra manera (a menos que cambie la API del proveedor de tracepoints).

Luego, enlaza tu aplicación con este archivo objeto (o con la biblioteca estática que lo contiene) y con liblttng-ust y libdl (libc en un sistema BSD):

$ cc -o app tp.o app.o -llttng-ust -ldl

Carga dinámica del proveedor de tracepoints

El segundo enfoque para empaquetar el proveedor de tracepoints es usar el cargador dinámico: la biblioteca y sus funciones miembro se buscan explícitamente, se cargan en tiempo de ejecución.

En este escenario, el proveedor de tracepoints se compila como un objeto compartido.

El proceso para crear el objeto compartido del proveedor de tracepoints es prácticamente el mismo que el del método de enlace estático, excepto que:

•Dado que el proveedor de tracepoints no forma parte de la aplicación, LTTNG_UST_TRACEPOINT_DEFINE debe definirse, para cada proveedor de tracepoints, en exactamente un archivo fuente de la aplicación.
•LTTNG_UST_TRACEPOINT_PROBE_DYNAMIC_LINKAGE debe definirse junto a LTTNG_UST_TRACEPOINT_DEFINE.

Con respecto a LTTNG_UST_TRACEPOINT_DEFINE y LTTNG_UST_TRACEPOINT_PROBE_DYNAMIC_LINKAGE, la práctica recomendada es usar un archivo fuente C separado en tu aplicación para definirlos, y luego incluir los archivos de cabecera del proveedor de tracepoints. Por ejemplo, como tp-define.c:

#define LTTNG_UST_TRACEPOINT_DEFINE
#define LTTNG_UST_TRACEPOINT_PROBE_DYNAMIC_LINKAGE
#include "tp.h"

El archivo objeto del proveedor de tracepoints utilizado para crear la biblioteca compartida se construye como se hace usando el método de enlace estático, pero con la opción -fpic:

$ cc -c -fpic -I. tp.c

Luego se enlaza como una biblioteca compartida de esta manera:

$ cc -shared -Wl,--no-as-needed -o tp.so tp.o -llttng-ust

Este objeto compartido del proveedor de tracepoints no se enlaza con la aplicación de usuario: debe ser cargado manualmente. Es por eso que la aplicación se construye sin mención de este proveedor de tracepoints, pero aún necesita libdl:

$ cc -o app app.o tp-define.o -ldl

Hay dos maneras de cargar dinámicamente el objeto compartido del proveedor de tracepoints:

•Cargarlo manualmente desde la aplicación usando dlopen(3).
•Hacer que el cargador dinámico lo cargue con la variable de entorno LD_PRELOAD (ver ld.so(8)).

Si la aplicación no carga dinámicamente el objeto compartido del proveedor de tracepoints utilizando uno de los métodos anteriores, el trazado se deshabilita para esta aplicación, y los eventos no se listan en la salida de lttng-list(1).

Ten en cuenta que no es seguro usar dlclose(3) en un objeto compartido de un proveedor de tracepoints que se está utilizando activamente para el trazado, debido a la falta de conteo de referencias de LTTng-UST al objeto compartido.

Por ejemplo, enlazar estáticamente un proveedor de tracepoints a un objeto compartido que va a ser cargado dinámicamente por una aplicación (un plugin, por ejemplo) no es seguro: el objeto compartido, que contiene el proveedor de tracepoints, podría ser cerrado dinámicamente (dlclose(3)) en cualquier momento por la aplicación.

Para instrumentar un objeto compartido, haz una de las siguientes cosas:

•Enlaza estáticamente el proveedor de tracepoints a la aplicación, o
•Construye el proveedor de tracepoints como un objeto compartido (siguiendo el procedimiento mostrado en esta sección), y precárgalo cuando se necesite trazado usando la variable de entorno LD_PRELOAD.

Uso de LTTng-UST con daemons

Se necesita un cuidado adicional al usar liblttng-ust con aplicaciones demonio que llaman a fork(2), clone(2), o el rfork(2) de BSD sin una llamada de sistema de la familia exec(3) posterior. La biblioteca liblttng-ust-fork.so necesita ser precargada antes de iniciar la aplicación con la variable de entorno LD_PRELOAD (ver ld.so(8)).

Para usar liblttng-ust con una aplicación demonio que cierra descriptores de archivo que no fueron abiertos por ella, precarga la biblioteca liblttng-ust-fd.so antes de iniciar la aplicación. Los casos de uso típicos incluyen demonios que cierran todos los descriptores de archivo después de fork(2), y aplicaciones defectuosas que realizan "dobles cierres".

NAME

lttng-ust - LTTng User Space Tracer library

SYNOPSIS

#include <lttng/tracepoint.h>

The LTTng-UST (User Space Tracer) library provides a simple API to generate tracepoints from user-space applications. Tracepoints are instrumentation points that can be enabled or disabled dynamically at run time.

LTTng-UST instrumentation consists of the following:

Tracepoint provider

A tracepoint provider is a set of tracepoints defined by the application developer. These tracepoints are declared within a header file using the macros defined by LTTng-UST, such as LTTNG_UST_TRACEPOINT_EVENT, LTTNG_UST_TRACEPOINT_LOGLEVEL, LTTNG_UST_TRACEPOINT_EVENT_CLASS, and LTTNG_UST_TRACEPOINT_EVENT_INSTANCE.

The provider is then activated by including the header file in a source file (typically named after the provider) after defining LTTNG_UST_TRACEPOINT_CREATE_PROBES and LTTNG_UST_TRACEPOINT_DEFINE.

See the tracepoint provider header file and tracepoint provider source file sections below.

Application

An application can use tracepoints defined by a provider. To do so, it needs to include the provider's header file.

The tracepoints are then called using the lttng_ust_tracepoint macro.

See the application header file and application source file sections below.

LTTng-UST can be linked either dynamically or statically to the application.

Dynamic linking

Dynamic linking is the default linking method. It means that the instrumented application depends on the liblttng-ust.so shared library.

Static linking

Static linking means that the instrumented application embeds the LTTng-UST library code within its own binary. This avoids the dependency on liblttng-ust.so and provides potentially better performance by eliminating dynamic linking overhead. This method is enabled by defining LTTNG_UST_STATIC before including <lttng/tracepoint.h>.

#define LTTNG_UST_STATIC
#include <lttng/tracepoint.h>

When static linking is used, the tracepoint provider header file needs to define LTTNG_UST_TRACEPOINT_PROVIDER and LTTNG_UST_TRACEPOINT_INCLUDE.

The tracepoint provider source file needs to define LTTNG_UST_TRACEPOINT_CREATE_PROBES, LTTNG_UST_TRACEPOINT_DEFINE, and LTTNG_UST_TRACEPOINT_STATIC.

#define LTTNG_UST_TRACEPOINT_CREATE_PROBES
#define LTTNG_UST_TRACEPOINT_DEFINE
#define LTTNG_UST_TRACEPOINT_STATIC
#include "tp.h"

Note that the tracepoint provider header file needs to be included in the source file where the main function resides, and the application needs to be linked with the provider's object file.

The debug link file name is defined as follows:

/sys/kernel/debug/tracing/trace_marker

Detect if LTTng-UST is loaded

To detect if liblttng-ust is loaded from an application:

1.Define the lttng_ust_loaded weak symbol globally: 
int lttng_ust_loaded __attribute__((weak));

This weak symbol is set by the constructor of liblttng-ust.

2.Test lttng_ust_loaded where needed: 
/* ... */
if (lttng_ust_loaded) {
    /* LTTng-UST is loaded */
} else {
    /* LTTng-UST is NOT loaded */
}
/* ... */

EXAMPLE


Note

A few examples are available in the doc/examples directory of LTTng-UST’s source tree.

This example shows all the features documented in the previous sections. The static linking method is chosen here to link the application with the tracepoint provider.

You can compile the source files and link them together statically like this:

$ cc -c -I. tp.c
$ cc -c app.c
$ cc -o app tp.o app.o -llttng-ust -ldl

Using the lttng(1) tool, create an LTTng tracing session, enable all the events of this tracepoint provider, and start tracing:

$ lttng create my-session
$ lttng enable-event --userspace 'my_provider:*'
$ lttng start

You may also enable specific events:

$ lttng enable-event --userspace my_provider:big_event
$ lttng enable-event --userspace my_provider:event_instance2

Run the application:

$ ./app some arguments

Stop the current tracing session and inspect the recorded events:

$ lttng stop
$ lttng view

#include <stdlib.h>
#include <stdio.h>

#include "app.h"
static int array_of_ints[] = {
    100, -35, 1, 23, 14, -6, 28, 1001, -3000,
};
int main(int argc, char* argv[])
{
    FILE *stream;
    struct app_struct app_struct;
    lttng_ust_tracepoint(my_provider, simple_event, argc, argv[0]);
    stream = fopen("/tmp/app.txt", "w");
    if (!stream) {
        fprintf(stderr,
                "Error: Cannot open /tmp/app.txt for writing\n");
        return EXIT_FAILURE;
    }
    if (fprintf(stream, "0123456789") != 10) {
        fclose(stream);
        fprintf(stderr, "Error: Cannot write to /tmp/app.txt\n");
        return EXIT_FAILURE;
    }
    lttng_ust_tracepoint(my_provider, big_event, 35,
                         "hello tracepoint", stream, -3.14,
                         array_of_ints);
    fclose(stream);
    app_struct.b = argc;
    app_struct.c = "[the string]";
    lttng_ust_tracepoint(my_provider, event_instance1, 23,
                         &app_struct);
    app_struct.b = argc * 5;
    app_struct.c = "[other string]";
    lttng_ust_tracepoint(my_provider, event_instance2, 17,
                         &app_struct);
    app_struct.b = 23;
    app_struct.c = "nothing";
    lttng_ust_tracepoint(my_provider, event_instance3, -52,
                         &app_struct);
    return EXIT_SUCCESS;
}

ENVIRONMENT VARIABLES

LTTNG_HOME

Alternative user’s home directory. This variable is useful when the user running the instrumented application has a non-writable home directory. This path is where Unix sockets for communication with the per-user session daemon are located.

LTTNG_UST_ABORT_ON_CRITICAL

If set, abort the instrumented application on a critical error message.

LTTNG_UST_ALLOW_BLOCKING

If set, allow the application to retry event tracing when there’s no space left for the event record in the sub-buffer, therefore effectively blocking the application until space is made available or the configured timeout is reached.

To allow an application to block during tracing, you also need to specify a blocking timeout when you create a channel with the --blocking-timeout option of the lttng-enable-channel(1) command.

This option can be useful in workloads generating very large trace data throughput, where blocking the application is an acceptable trade-off to prevent discarding event records.


Warning
Setting this environment variable may significantly affect application timings.

LTTNG_UST_APP_PATH

Path of the directory where to expect the LTTng session daemon to place the following files to receive instrumented application connection requests:
•The application registration Unix socket.
•The "wait" shared memory files to wake up instrumented applications that are waiting for a session daemon to start.
•The agent port file.

This file contains the TCP port the agents must connect to in order to enable LTTng tracing.

This directory must exist when you start the application for LTTng tracing to be enabled.

When LTTNG_UST_APP_PATH is set, liblttng-ust:

•Only considers this path to connect to a session daemon.
•Won’t connect to root and/or user session daemons as usual.

See the corresponding LTTNG_UST_CTL_PATH environment variable of lttng-sessiond(8).

LTTNG_UST_CLOCK_PLUGIN

Path to the shared object which acts as the clock override plugin. An example of such a plugin can be found in the LTTng-UST documentation under examples/clock-override https://github.com/lttng/lttng-ust/tree/stable-2.14/doc/examples/clock-override.

VARIABLES DE ENTORNO

LTTNG_UST_DEBUG

Si está configurada, habilita la salida de depuración y de errores de liblttng-ust.

LTTNG_UST_GETCPU_PLUGIN

Ruta al objeto compartido que actúa como plugin de reemplazo de getcpu(). Un ejemplo de dicho plugin se puede encontrar en la documentación de LTTng-UST bajo examples/getcpu-override https://github.com/lttng/lttng-ust/tree/stable-2.14/doc/examples/getcpu-override.

LTTNG_UST_MAP_POPULATE_POLICY

Si está configurada, anula la política utilizada para poblar las páginas de memoria compartida dentro de la aplicación.

Los valores posibles son:

none (predeterminado)

No pre-poblar ninguna página: incurrir en fallos menores en el primer acceso al trazar.

cpu_possible

Pre-poblar páginas para todas las CPU posibles en el sistema, como se muestra en /sys/devices/system/cpu/possible.

LTTNG_UST_REGISTER_TIMEOUT

Tiempo de espera para el comando del demonio de sesión registration done antes de proceder a ejecutar el programa principal (milisegundos).

El valor 0 significa no esperar. El valor -1 significa esperar para siempre. Se recomienda establecer esta variable de entorno a 0 para aplicaciones con restricciones de tiempo en el tiempo de inicio del proceso.

Predeterminado: 3000.

LTTNG_UST_WITHOUT_BADDR_STATEDUMP

Si está configurada, evita que liblttng-ust realice un volcado de estado de dirección base (ver la sección Vuelto de estado de LTTng-UST más arriba).

LTTNG_UST_WITHOUT_PROCNAME_STATEDUMP

Si está configurada, evita que liblttng-ust realice un volcado de estado de nombre de proceso (ver la sección Vuelto de estado de LTTng-UST más arriba).
