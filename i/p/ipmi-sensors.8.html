IPMI-SENSORS(8) Comandos del sistema IPMI-SENSORS(8)

NOMBRE

ipmi-sensors - mostrar información de sensores IPMI

SINOPSIS

ipmi-sensors [OPCIÓN...]

DESCRIPCIÓN

Ipmi-sensors muestra las lecturas actuales de los sensores y la información del repositorio de datos de sensores (SDR). La salida predeterminada muestra el identificador de registro, el nombre del sensor, el nombre del tipo de sensor, la lectura del sensor (si corresponde) y el evento actual del sensor. Se puede encontrar información más detallada usando las opciones verbosas especificadas más abajo. Ipmi-sensors no informa al usuario si existe un problema con un sensor en particular, porque las lecturas y eventos de los sensores no se analizan de forma predeterminada. Los usuarios pueden desear usar la opción --output-sensor-state para generar la salida del estado analizado del sensor. Algunos sensores pueden tener una lectura o evento de sensor "N/A" si la información no está disponible. Esto es típico de un sensor que no está habilitado o que no es propiedad de un BMC. Por favor, consulte la opción --bridge-sensors más abajo para tratar con sensores que no son propiedad de un BMC. Los sensores pueden generar un evento de sensor "Desconocido" si la lectura del sensor no se puede obtener. Esto es típico de un sensor ocupado o de una lectura que no se puede calcular. Si los sensores reportan "Estado no reconocido", esto indica un tipo de sensor desconocido, típicamente un sensor OEM. Si la interpretación OEM del sensor está disponible, la opción --interpret-oem-data puede ser capaz de reportar el estado apropiado del sensor. Los sensores no siempre necesitan reportar un evento de sensor. Cuando no hay un evento de sensor presente, típicamente se reporta "OK".

A continuación se enumeran las opciones IPMI generales, las opciones específicas de la herramienta, información de solución de problemas, información de soluciones alternativas, ejemplos y problemas conocidos. Para una introducción general a FreeIPMI, consulte freeipmi(7). Para realizar la configuración de sensores IPMI, consulte ipmi-config(8). Para realizar alguna gestión avanzada de SDR, consulte bmc-device(8).

OPCIONES GENERALES

Las siguientes opciones son opciones generales para configurar la comunicación IPMI y ejecutar comandos generales de la herramienta.

-D IPMIDRIVER, --driver-type=IPMIDRIVER
Especifica el tipo de driver a usar en lugar de hacer una selección automática. Los drivers fuera de banda actualmente disponibles son LAN y LAN_2_0, que realizan IPMI 1.5 e IPMI 2.0 respectivamente. Los drivers en banda actualmente disponibles son KCS, SSIF, OPENIPMI, SUNBMC e INTELDCMI.
--disable-auto-probe
No sondear los dispositivos IPMI en banda para los valores predeterminados.
--driver-address=DRIVER-ADDRESS
Especifica la dirección del driver en banda a usar en lugar del valor sondeado. DRIVER-ADDRESS debe ir precedido de "0x" para un valor hexadecimal y '0' para un valor octal.
--driver-device=DEVICE
Especifica la ruta del dispositivo del driver en banda a usar en lugar de la ruta sondeada.
--register-spacing=REGISTER-SPACING
Especifica el espaciado de registros del driver en banda en lugar del valor sondeado. El argumento está en bytes (es decir, espaciado de registro de 32 bits = 4).
--target-channel-number=CHANNEL-NUMBER
Especifica el número de canal de destino del driver en banda al que enviar las solicitudes IPMI.
--target-slave-address=SLAVE-ADDRESS
Especifica el número de esclavo de destino del driver en banda al que enviar las solicitudes IPMI.
-h IPMIHOST1,IPMIHOST2,..., --hostname=IPMIHOST1[:PUERTO],IPMIHOST2[:PUERTO],...
Especifica el(los) host(s) remoto(s) con los que comunicarse. Se pueden separar múltiples nombres de host con comas o especificarlos en un formato de rango; consulte el soporte de rangos de hosts más abajo. Se puede especificar un puerto opcional con cada host, lo que puede ser útil en situaciones de reenvío de puertos o similares. Al especificar una dirección IPv6 y un puerto, use el formato [DIRECCIÓN]:PUERTO.
-u USERNAME, --username=USERNAME
Especifica el nombre de usuario a usar al autenticarse con el host remoto. Si no se especifica, se asume un nombre de usuario nulo (es decir, anónimo). El usuario debe tener al menos privilegios de OPERADOR para que esta herramienta funcione completamente.
-p PASSWORD, --password=PASSWORD
Especifica la contraseña a usar al autenticarse con el host remoto. Si no se especifica, se asume una contraseña nula. La longitud máxima de la contraseña es 16 para IPMI 1.5 y 20 para IPMI 2.0.
-P, --password-prompt
Solicita la contraseña para evitar la posibilidad de listarla en las listas de procesos.
-k K_G, --k-g=K_G
Especifica la clave K_g del BMC a usar al autenticarse con el host remoto para IPMI 2.0. Si no se especifica, se asume una clave nula. Para introducir la clave en forma hexadecimal, preceda la cadena con '0x'. Por ejemplo, la clave 'abc' se puede introducir con la cadena 'abc' o con la cadena '0x616263'.
-K, --k-g-prompt
Solicita la clave k-g para evitar la posibilidad de listarla en las listas de procesos.
--session-timeout=MILLISECONDS
Especifica el tiempo de espera de la sesión en milisegundos. Por defecto es 20000 milisegundos (20 segundos) si no se especifica.
--retransmission-timeout=MILLISECONDS
Especifica el tiempo de espera de retransmisión de paquetes en milisegundos. Por defecto es 1000 milisegundos (1 segundo) si no se especifica. El tiempo de espera de retransmisión no puede ser mayor que el tiempo de espera de la sesión.
-a AUTHENTICATION-TYPE, --authentication-type=AUTHENTICATION-TYPE
Especifica el tipo de autenticación de IPMI 1.5 a usar. Los tipos de autenticación actualmente disponibles son NONE, STRAIGHT_PASSWORD_KEY, MD2 y MD5. Por defecto es MD5 si no se especifica.
-I CIPHER-SUITE-ID, --cipher-suite-id=CIPHER-SUITE-ID
Especifica el ID de suite de cifrado de IPMI 2.0 a usar. El ID de la suite de cifrado identifica un conjunto de algoritmos de autenticación, integridad y confidencialidad a usar para la comunicación IPMI 2.0. El algoritmo de autenticación identifica el algoritmo a usar para la configuración de la sesión, el algoritmo de integridad identifica el algoritmo a usar para las firmas de los paquetes de la sesión, y el algoritmo de confidencialidad identifica el algoritmo a usar para el cifrado de la carga útil. Por defecto es el ID de suite de cifrado 3 si no se especifica. Actualmente se admiten los siguientes IDs de suite de cifrado:

0 - Algoritmo de autenticación = Ninguno; Algoritmo de integridad = Ninguno; Algoritmo de confidencialidad = Ninguno

1 - Algoritmo de autenticación = HMAC-SHA1; Algoritmo de integridad = Ninguno; Algoritmo de confidencialidad = Ninguno

2 - Algoritmo de autenticación = HMAC-SHA1; Algoritmo de integridad = HMAC-SHA1-96; Algoritmo de confidencialidad = Ninguno

3 - Algoritmo de autenticación = HMAC-SHA1; Algoritmo de integridad = HMAC-SHA1-96; Algoritmo de confidencialidad = AES-CBC-128

6 - Algoritmo de autenticación = HMAC-MD5; Algoritmo de integridad = Ninguno; Algoritmo de confidencialidad = Ninguno

7 - Algoritmo de autenticación = HMAC-MD5; Algoritmo de integridad = HMAC-MD5-128; Algoritmo de confidencialidad = Ninguno

8 - Algoritmo de autenticación = HMAC-MD5; Algoritmo de integridad = HMAC-MD5-128; Algoritmo de confidencialidad = AES-CBC-128

11 - Algoritmo de autenticación = HMAC-MD5; Algoritmo de integridad = MD5-128; Algoritmo de confidencialidad = Ninguno

12 - Algoritmo de autenticación = HMAC-MD5; Algoritmo de integridad = MD5-128; Algoritmo de confidencialidad = AES-CBC-128

15 - Algoritmo de autenticación = HMAC-SHA256; Algoritmo de integridad = Ninguno; Algoritmo de confidencialidad = Ninguno

16 - Algoritmo de autenticación = HMAC-SHA256; Algoritmo de integridad = HMAC_SHA256_128; Algoritmo de confidencialidad = Ninguno

17 - Algoritmo de autenticación = HMAC-SHA256; Algoritmo de integridad = HMAC_SHA256_128; Algoritmo de confidencialidad = AES-CBC-128

-l PRIVILEGE-LEVEL, --privilege-level=PRIVILEGE-LNIVEL
Especifica el nivel de privilegio a utilizar. Los niveles de privilegio actualmente disponibles son USER, OPERATOR y ADMIN. Por defecto es OPERATOR si no se especifica.
--config-file=ARCHIVO
Especifica un archivo de configuración alternativo.
-W SOLUCIONES, --workaround-flags=SOLUCIONES
Especifica soluciones a problemas de cumplimiento del proveedor. Se pueden especificar múltiples soluciones separadas por comas. Un indicador especial de línea de comandos "none" indicará que no se aplicarán soluciones (puede ser útil para anular los valores predeterminados configurados). Consulte SOLUCIONES más abajo para obtener una lista de las soluciones disponibles.
--debug
Activa la depuración.
-?, --help
Muestra una lista de ayuda y sale.
--usage
Muestra un mensaje de uso y sale.
-V, --version
Muestra la versión del programa y sale.

OPCIONES DE IPMI-SENSORS

Las siguientes opciones son específicas de ipmi-sensors.

-v, --verbose
Muestra una salida de sensores detallada. Esta opción mostrará información adicional sobre los sensores, como umbrales, rangos, números y códigos de tipo de evento/lectura.
-vv
Muestra una salida de sensores muy detallada. Esta opción mostrará más información adicional que la opción detallada, como información sobre eventos, otros tipos de sensores y sensores OEM.
-i, --sdr-info
Muestra información del repositorio de datos de sensores (SDR)
-q, --quiet-readings
No muestra los valores de lectura de los sensores por defecto. Esta opción es particularmente útil si desea utilizar una salida distribuida por hosts a través de un clúster y desea consolidar la salida.
-r LISTA-DE-IDS-DE-REGISTRO, --record-ids=LISTA-DE-IDS-DE-REGISTRO
Especifica los sensores a mostrar por id de registro. Se pueden separar múltiples ids de registro con comas o espacios. Si se especifican tanto --record-ids como --sensor-types , --record-ids tiene prioridad. Un id de registro especial en la línea de comandos, "all", indicará que se deben mostrar todos los ids de registro (puede ser útil para anular los valores predeterminados configurados).
-R LISTA-DE-IDS-DE-REGISTRO, --exclude-record-ids=LISTA-DE-IDS-DE-REGISTRO
Especifica los sensores a no mostrar por id de registro. Se pueden separar múltiples ids de registro con comas o espacios. Un id de registro especial en la línea de comandos, "none", indicará que no se debe excluir ningún id de registro (puede ser útil para anular los valores predeterminados configurados).
-t LISTA-DE-TIPOS-DE-SENSOR, --sensor-types=LISTA-DE-TIPOS-DE-SENSOR
Especifica los tipos de sensores para los que mostrar salidas. Se pueden separar múltiples tipos con comas o espacios. Si se especifican tanto --record-ids como --sensor-types , --record-ids tiene prioridad. Un tipo especial en la línea de comandos, "all", indicará que se deben mostrar todos los tipos (puede ser útil para anular los valores predeterminados configurados). Los usuarios pueden especificar los tipos de sensores por cadena de texto (ver --list-sensor-types más abajo) o por número (decimal o hexadecimal).
-T LISTA-DE-TIPOS-DE-SENSOR, --exclude-sensor-types=LISTA-DE-TIPOS-DE-SENSOR
Especifica los tipos de sensores para los que no mostrar salidas. Se pueden separar múltiples tipos con comas o espacios. Un tipo especial en la línea de comandos, "none", indicará que no se debe excluir ningún tipo (puede ser útil para anular los valores predeterminados configurados). Los usuarios pueden especificar los tipos de sensores por cadena de texto (ver --list-sensor-types más abajo) o por número (decimal o hexadecimal).
-L, --list-sensor-types
Lista los tipos de sensores.
-b, --bridge-sensors
Por defecto, no se intenta obtener lecturas de sensores para sensores cuyos propietarios no son el BMC. Al establecer esta opción, las peticiones de sensores pueden ser enrutadas a propietarios que no son el BMC para obtener lecturas de sensores. El enrutamiento puede no funcionar en algunos tipos de interfaces/controladores.
--shared-sensors
Algunos sensores comparten el mismo registro de datos de sensores (SDR). Esto se utiliza típicamente para entradas del log de eventos del sistema (SEL) y no para lecturas de sensores. Sin embargo, puede haber algunas placas base en las que este formato se utilice para múltiples sensores activos, o el usuario simplemente tiene interés en ver la permutación de entradas compartidas por una entrada de SDR. Al establecer esta opción, se iterará y mostrará cada número de sensor compartido por un registro.
--interpret-oem-data
Intenta interpretar datos OEM, como datos de eventos, lecturas de sensores o información extra general, etc. Si no hay una interpretación OEM disponible, se generará la salida predeterminada. La corrección de las interpretaciones OEM no puede garantizarse debido a posibles cambios que los proveedores OEM puedan realizar en productos, firmware, etc. Consulte INTERPRETACIÓN OEM más abajo para las interpretaciones de placas base confirmadas y soportadas.
--ignore-not-available-sensors
Ignora los sensores no disponibles (es decir, N/A) en la salida.
--ignore-unrecognized-events
Ignora los eventos de sensores no reconocidos. Esto suprimirá la salida de eventos no reconocidos, que típicamente se muestran como 'Unrecognized Event = XXXXh' en la salida. Además, los eventos no reconocidos se ignorarán al calcular el estado del sensor con --output-sensor-state más abajo.
--output-event-bitmask
Muestra el valor de la máscara de bits del evento en lugar de su representación en cadena de texto.
--output-sensor-state
Muestra el estado del sensor en la salida. Esto añadirá una salida adicional que informa si un sensor está en un estado NOMINAL, WARNING o CRITICAL. El estado del sensor es un valor interpretado basado en el evento actual del sensor. Las interpretaciones del estado del sensor están determinadas por el archivo de configuración /etc/freeipmi//freeipmi_interpret_sensor.conf. Consulte freeipmi_interpret_sensor.conf(5) para más información. Esta opción produce una salida idéntica al estado del sensor que se mostraba previamente en ipmimonitoring(8).
--sensor-state-config-file=ARCHIVO
Especifica un archivo de configuración de estado de sensores alternativo. La opción se ignora si no se especifica --output-sensor-state .
--entity-sensor-names
Muestra los nombres de los sensores con el prefijo de su id de entidad y número de instancia cuando sea apropiado. Esto puede ser necesario en algunas placas base para ayudar a identificar a qué sensores se hace referencia. Por ejemplo, una placa base puede tener múltiples sensores llamados 'TEMP'. El id de entidad y el número de instancia pueden ayudar a aclarar a qué sensor se refiere "Procesador 1" frente a "Procesador 2".
--output-sensor-thresholds
Muestra los umbrales de los sensores en la salida. Esto añadirá columnas a la salida predeterminada para los umbrales no recuperable inferior, crítico inferior, no crítico inferior, no crítico superior, crítico superior y no recuperable superior.
--no-sensor-type-output
No muestra el tipo de sensor para cada entrada. En muchos sistemas, el tipo de sensor es redundante con el nombre del sensor. Esto puede ser especialmente cierto si se especifica --entity-sensor-names . Si el nombre del sensor es suficiente, o si el tipo de sensor no es de interés para el usuario, se puede especificar esta opción para condensar la salida.
--comma-separated-output
Muestra los campos en formato separado por comas.
--no-header-output
No muestra los encabezados de las columnas. Puede ser útil en scripts.
--non-abbreviated-units
Muestra las unidades sin abreviar (por ejemplo, 'Amps' en lugar de 'A'). Puede ayudar a desambiguar las unidades (por ejemplo, 'C' para Celsius o Culombios).
--legacy-output
Muestra la salida en formato heredado. Las opciones más nuevas pueden no ser aplicables a la salida heredada.
--ipmimonitoring-legacy-output
Muestra la salida en el formato heredado de la herramienta ipmimonitoring heredada. Las opciones más nuevas pueden no ser aplicables a la salida heredada.

OPCIONES DE CACHÉ DE SDR

Esta herramienta requiere acceso a la caché del repositorio de datos de sensores (SDR) para su funcionamiento general. Por defecto, los datos del SDR se descargarán y almacenarán en caché en la máquina local. Las siguientes opciones se aplican a la caché del SDR.

--flush-cache
Vacía la versión en caché de la caché del repositorio de datos de sensores (SDR). El SDR se almacena típicamente en caché para un acceso posterior más rápido. Sin embargo, puede necesitar ser vaciada y regenerada si el SDR ha sido actualizado en un sistema.
--quiet-cache
No muestra información sobre la creación/borrado de la caché. Puede ser útil en scripts.
--sdr-cache-recreate
Si la caché del SDR está desactualizada o es inválida, regenera automáticamente la caché del repositorio de datos de sensores (SDR). Esta opción puede ser útil para fines de scripting.
--sdr-cache-file=ARCHIVO
Especifica un archivo de caché del repositorio de datos de sensores (SDR) específico para ser almacenado o leído. Si se usa esta opción cuando se especifican múltiples hosts, se usará el mismo archivo de caché del SDR para todos los hosts.
--sdr-cache-directory=DIRECTORIO
Especifica un directorio alternativo para que se almacenen o se lean las cachés del repositorio de datos de sensores (SDR). Por defecto es el directorio de inicio si no se especifica.

OPCIONES DE TIEMPO

Por definición de IPMI, todas las horas y marcas de tiempo de IPMI se almacenan en hora local. Sin embargo, en muchas situacioness, las marcas de tiempo no se almacenarán en hora local. Si un sistema almacena realmente las marcas de tiempo en hora local depende de muchos factores, como el proveedor, el BIOS y el sistema operativo. Las siguientes opciones permitirán al usuario ajustar la interpretación de las marcas de tiempo almacenadas y cómo deben ser mostradas.

--utc-to-localtime
Asumir que todos los tiempos se reportan en hora UTC y convertir el tiempo a hora local antes de ser mostrado.
--localtime-to-utc
Convertir todas las marcas de tiempo en hora local a UTC antes de ser mostradas.
--utc-offset=SEGUNDOS
Especificar un desfase UTC específico en segundos a añadir a las marcas de tiempo. El valor puede oscilar entre -86400 y 86400 segundos. Por defecto es 0.

OPCIONES DE RANGO DE HOSTS

Las siguientes opciones manipulan la salida de rangos de hosts. Vea SOPORTE DE RANGO DE HOSTS más abajo para información adicional sobre rangos de hosts.

-B, --buffer-output
Almacenar en búfer la salida de rangos de hosts. Para cada nodo, almacenar en búfer la salida estándar hasta que el nodo haya completado su operación IPMI. Al especificar esta opción, los datos pueden parecer que se muestran más lentamente al usuario, ya que toda la operación IPMI debe completarse antes de que se pueda mostrar algún dato. Vea SOPORTE DE RANGO DE HOSTS más abajo para información adicional.
-C, --consolidate-output
Consolidar la salida de rangos de hosts. La salida estándar completa de cada nodo especificado será consolidada de modo que los nodos con salida idéntica no se muestren dos veces. Un encabezado listará aquellos nodos con la salida consolidada. Cuando se especifica esta opción, no se puede ver ninguna salida hasta que las operaciones IPMI a todos los nodos se hayan completado. Si el usuario interrumpe el programa antes de tiempo, toda la salida consolidada actualmente será volcada. Vea SOPORTE DE RANGO DE HOSTS más abajo para información adicional.
-F NÚM, --fanout=NÚM
Especificar el abanico de múltiples hosts. Se utiliza un algoritmo de "ventana deslizante" (o abanico) para la comunicación IPMI en paralelo, de modo que los nodos más lentos o los nodos con tiempo de espera agotado no obstaculicen la comunicación en paralelo. El número máximo de hilos disponibles al mismo tiempo está limitado por el abanico. El valor por defecto es 64.
-E, --eliminate
Eliminar los hosts determinados como no detectados por ipmidetect. Esto intenta eliminar el problema común de que la ejecución de rangos de hosts agote el tiempo de espera debido a que varios nodos hayan sido retirados del servicio en un gran clúster. El demonio ipmidetectd debe estar ejecutándose en el nodo que ejecuta el comando.
--always-prefix
Siempre anteponer el prefijo a la salida, incluso si solo se especifica un host o se comunica en banda. Esta opción es principalmente útil para propósitos de scripting. La opción será ignorada si se especifica con la opción -C.

SOPORTE DE RANGO DE HOSTS

Múltiples hosts pueden introducirse ya sea como listas explícitas de hosts separadas por comas o como un rango de nombres de host en la forma general: prefijo[n-m,l-k,...], donde n < m y l < k, etc. La última forma no debe confundirse con las clases de caracteres de expresiones regulares (también denotadas por []). Por ejemplo, foo[19] no representa foo1 o foo9, sino que representa un rango degenerado: foo19.

Esta sintaxis de rango está destinada solo como una conveniencia en clústeres con una convención de nombres prefijoNN, y la especificación de rangos no debe considerarse necesaria -- la lista foo1,foo9 podría especificarse como tal, o por el rango foo[1,9].

A continuación se muestran algunos ejemplos del uso de rangos:

    foo[01-05] en lugar de foo01,foo02,foo03,foo04,foo05
    foo[7,9-10] en lugar de foo7,foo9,foo10
    foo[0-3] en lugar de foo0,foo1,foo2,foo3

Como recordatorio para el lector, algunos intérpretes de comandos interpretarán los corchetes ([ y ]) para la coincidencia de patrones. Dependiendo de su intérprete de comandos, puede ser necesario encerrar las listas de rangos entre comillas.

Cuando el usuario especifica múltiples hosts, se ejecutará un hilo para cada host en paralelo hasta el abanico configurado (que puede ajustarse a través de la opción -F). Esto permitirá la comunicación con un gran número de nodos mucho más rápidamente que si se hiciera en serie.

Por defecto, la salida estándar de cada nodo especificado será mostrada con el nombre de host anteponiéndose a cada línea. Aunque esta salida es legible en muchas situaciones, puede ser difícil de leer en otras situaciones. Por ejemplo, la salida de múltiples nodos puede mezclarse. Las opciones -B y -C pueden usarse para cambiar este valor por defecto.

Se utilizará la comunicación IPMI en banda cuando se especifica el host "localhost". Esto permite al usuario añadir el localhost a la salida de rangos de hosts.

SOLUCIÓN DE PROBLEMAS GENERAL

La mayoría de las veces, los problemas de IPMI se deben a problemas de configuración.

Los problemas de IPMI sobre LAN implican una configuración incorrecta del BMC de la máquina remota. Verifique dos veces para asegurarse de que lo siguiente está configurado correctamente en el BMC de la máquina remota: dirección IP, dirección MAC, máscara de subred, nombre de usuario, habilitación de usuario, privilegio de usuario, contraseña, privilegio LAN, habilitación LAN y tipo(s) de autenticación permitidos. Para conexiones IPMI 2.0, verifique dos veces para asegurarse de que el(los) privilegio(s) de la suite de cifrado y la clave K_g están configurados correctamente. La herramienta ipmi-config(8) puede usarse para verificar y/o cambiar estos ajustes de configuración.

Los problemas de IPMI en banda típicamente son causados por controladores mal configurados o BMCs no estándar.

Además de los consejos de solución de problemas siguientes, por favor vea SOLUCIONES ALTERNATIVAS más abajo para ver también si hay errores específicos del proveedor que hayan sido descubiertos y solucionados.

A continuación se listan muchos de los problemas comunes para los mensajes de error. Para soporte adicional, por favor envíe un correo electrónico a la lista de correo <freeipmi-users@gnu.org>.

"username invalid" (nombre de usuario no válido) - El nombre de usuario introducido (o un nombre de usuario NULO si no se introdujo ninguno) no está disponible en la máquina remota. También puede ser que la configuración del nombre de usuario del BMC remoto sea incorrecta.

"password invalid" (contraseña no válida) - La contraseña introducida (o una contraseña NULA si no se introdujo ninguna) no es correcta. También puede ser que la contraseña del usuario no esté configurada correctamente en el BMC remoto.

"password verification timeout" (tiempo de espera de verificación de contraseña agotado) - La verificación de la contraseña ha agotado el tiempo de espera. Ocurrió un error "password invalid" (contraseña no válida) (descrito arriba) o un "session timeout" (tiempo de espera de sesión) genérico (descrito más abajo). Durante este punto del protocolo no se puede diferenciar cuál ocurrió.

"k_g invalid" (K_g no válido) - La clave K_g introducida (o una clave K_g NULA si no se introdujo ninguna) no es correcta. También puede ser que la clave K_g no esté configurada correctamente en el BMC remoto.

"privilege level insufficient" (nivel de privilegio insuficiente) - Un comando IPMI requiere un privilegio de usuario más alto que el con el que se autenticó. Por favor, intente autenticarse con un privilegio más alto. Esto puede requerir autenticarse con un usuario diferente que tenga un privilegio máximo más alto.

"privilege level cannot be obtained for this user" (no se puede obtener el nivel de privilegio para este usuario) - El nivel de privilegio con el que intenta autenticarse es más alto que el máximo permitido para este usuario. Por favor, intente de nuevo con un privilegio más bajo. También puede ser que el nivel de privilegio máximo permitido para un usuario no esté configurado correctamente en el BMC remoto.

"authentication type unavailable for attempted privilege level" (tipo de autenticación no disponible para el nivel de privilegio intentado) - El tipo de autenticación con el que desea autenticarse no está disponible para este nivel de privilegio. Por favor, intente de nuevo con un tipo de autenticación alternativo o un nivel de privilegio alternativo. También puede ser que los tipos de autenticación disponibles con los que puede autenticarse no estén configurados correctamente en el BMC remoto.

"cipher suite id unavailable" (id de suite de cifrado no disponible) - El id de suite de cifrado con el que desea autenticarse no está disponible en el BMC remoto. Por favor, intente de nuevo con un id de suite de cifrado alternativo. También puede ser que los ids de suite de cifrado disponibles no estén configurados correctamente en el BMC remoto.

"ipmi 2.0 unavailable" (IPMI 2.0 no disponible) - No se descubrió IPMI 2.0 en la máquina remota. Por favor, intente usar IPMI 1.5 en su lugar.

"connection timeout" (tiempo de espera de conexión agotado) - La comunicación IPMI inicial falló. Son posibles varios errores potenciales, incluyendo un nombre de host especificado no válido, una dirección IP de IPMI que no puede resolverse, IPMI no está habilitado en el servidor remoto, la conexión de red es deficiente, etc. Por favor, verifique la configuración y la conectividad.

"session timeout" (tiempo de espera de sesión agotado) - La sesión IPMI ha agotado el tiempo de espera. Por favor, reconéctese. Si este error ocurre con frecuencia, puede desear aumentar el tiempo de espera de retransmisión. Algunos BMCs remotos son considerablemente más lentos que otros.

"device not found" (dispositivo no encontrado) - El dispositivo especificado no pudo encontrarse. Por favor, verifique la configuración o las entradas e intente de nuevo.

"driver timeout" (tiempo de espera del controlador agotado) - La comunicación con el controlador o el dispositivo ha agotado el tiempo de espera. Por favor, intente de nuevo.

"message timeout" (tiempo de espera del mensaje agotado) - La comunicación con el controlador o el dispositivo ha agotado el tiempo de espera. Por favor, intente de nuevo.

"BMC busy" (BMC ocupado) - El BMC está actualmente ocupado. Puede estar procesando información o tener demasiadas sesiones simultáneas que gestionar. Por favor, espere e intente de nuevo.

"could not find inband device" (no se pudo encontrar el dispositivo en banda) - Un dispositivo en banda no pudo encontrarse. Por favor, verifique la configuración o especifique un dispositivo o controlador específico en la línea de comandos.

"driver timeout" (tiempo de espera del controlador agotado) - El controlador en banda ha agotado el tiempo de espera comunicándose con el BMC o el procesador de servicio local. El BMC o el procesador de servicio puede estar ocupado o (en el peor de los casos) posiblemente no funcionando.

"internal IPMI error" (error IPMI interno) - Ha ocurrido un error IPMI que FreeIPMI no sabe cómo manejar. Por favor, envíe un correo electrónico a <freeipmi-users@gnu.org> para informar del problema.

"sensor config file parse error" (error de análisis del archivo de configuración del sensor) - Se encontró un error de análisis en el archivo de configuración de interpretación de sensores. Por favor, vea freeipmi_interpret_sensor.conf(5).

SOLUCIONES ALTERNATIVAS

Con tantos proveedores diferentes implementando sus propias soluciones de IPMI, diferentes proveedores pueden implementar incorrectamente sus protocolos de IPMI. Lo siguiente describe un número de soluciones alternativas actualmente disponibles para manejar problemas de cumplimiento descubiertos. Cuando es posible, las soluciones alternativas han sido implementadas de modo que serán transparentes para el usuario. Sin embargo, algunas requerirán que el usuario especifique que se use una solución alternativa a través de la opción -W

HARDWARE ISSUES

El hardware listado a continuación puede indicar solo el hardware en el que se descubrió un problema. Las versiones más nuevas de hardware pueden solucionar los problemas indicados a continuación. Máquinas similares de diferentes fabricantes pueden o no presentar los mismos problemas. Diferentes fabricantes pueden licenciar su firmware del mismo desarrollador de firmware IPMI, por lo que puede valer la pena intentar las soluciones alternativas que se enumeran a continuación, incluso si su placa base no está listada.

Si cree que su hardware tiene un problema de cumplimiento adicional que requiere la implementación de una solución alternativa, póngase en contacto con los mantenedores de FreeIPMI en <freeipmi-users@gnu.org> o <freeipmi-devel@gnu.org>.

assumeio - Esta bandera de solución alternativa asumirá que las interfaces inband se comunican con la E/S del sistema en lugar de ser mapeadas en memoria. Esto solucionará sistemas que informan direcciones base inválidas. Aquellos que encuentren este problema pueden ver errores como "dispositivo no soportado" o "no se pudo encontrar dispositivo inband". Problema observado en HP ProLiant DL145 G1.

spinpoll - Esta bandera de solución alternativa indicará a algunos controladores inband (notablemente el controlador KCS) que giren mientras sondean en lugar de poner el proceso en espera. Esto puede mejorar significativamente el tiempo de reloj de pared de las herramientas, ya que la granularidad del programador del sistema operativo puede ser mucho mayor que el tiempo que se tarda en realizar una sola transacción de mensaje IPMI. Sin embargo, al girar, su sistema puede estar realizando menos trabajo útil al no cambiar de contexto la herramienta por una tarea más útil.

authcap - Esta bandera de solución alternativa omitirá las comprobaciones tempranas de las capacidades del nombre de usuario, las capacidades de autenticación y el soporte K_g, y permitirá que la autenticación IPMI tenga éxito. Soluciona varios problemas en los que el sistema remoto no informa correctamente las capacidades del nombre de usuario, las capacidades de autenticación o el estado K_g. Aquellos que encuentren este problema pueden ver errores como "nombre de usuario inválido", "tipo de autenticación no disponible para el nivel de privilegio intentado" o "k_g inválido". Problema observado en Asus P5M2/P5MT-R/RS162-E4/RX4, Intel SR1520ML/X38ML y Sun Fire 2200/4150/4450 con ELOM.

nochecksumcheck - Esta bandera de solución alternativa le dirá a FreeIPMI que no verifique las sumas de verificación devueltas de las respuestas a los comandos IPMI. Soluciona sistemas que devuelven sumas de verificación inválidas debido a errores de implementación, pero el paquete es válido de otra manera. Se advierte a los usuarios sobre el uso de esta opción, ya que elimina la validación de la integridad del paquete en varias circunstancias. Sin embargo, es poco probable que sea un problema en la mayoría de las situaciones. Aquellos que encuentren este problema pueden ver errores como "tiempo de espera de conexión", "tiempo de espera de sesión" o "tiempo de espera de verificación de contraseña". En conexiones IPMI 1.5, la solución alternativa "noauthcodecheck" también puede ser necesaria. Problema observado en Supermicro X9SCM-iiF, Supermicro X9DRi-F y Supermicro X9DRFR.

idzero - Esta bandera de solución alternativa permitirá que los identificadores de sesión vacíos sean aceptados por el cliente. Soluciona sesiones IPMI que informan identificadores de sesión vacíos al cliente. Aquellos que encuentren este problema pueden ver errores de "tiempo de espera de sesión". Problema observado en Tyan S2882 con BMC M3289.

unexpectedauth - Esta bandera de solución alternativa permitirá que los códigos de autenticación inesperados no nulos se comprueben como si fueran esperados. Soluciona un problema en el que los paquetes contienen datos de autenticación no nulos cuando deberían ser nulos debido a la autenticación por mensaje deshabilitada. Aquellos que encuentren este problema pueden ver errores de "tiempo de espera de sesión". Problema observado en Dell PowerEdge 2850, SC1425. Confirmado que se ha solucionado en firmware más reciente.

forcepermsg - Esta bandera de solución alternativa forzará el uso de autenticación por mensaje, independientemente de lo que anuncie el sistema remoto. Soluciona un problema en el que la autenticación por mensaje se anuncia como deshabilitada en el sistema remoto, pero en realidad es necesaria para el protocolo. Aquellos que encuentren este problema pueden ver errores de "tiempo de espera de sesión". Problema observado en IBM eServer 325.

endianseq - Esta bandera de solución alternativa invertirá el endianness de los números de secuencia de sesión para permitir que la sesión continúe correctamente. Soluciona números de secuencia de sesión IPMI 1.5 que tienen el endianness incorrecto. Aquellos que encuentren este problema pueden ver errores de "tiempo de espera de sesión". Problema observado en algunos Sun ILOM 1.0/2.0 (depende del endianness del procesador de servicio).

noauthcodecheck - Esta bandera de solución alternativa le dirá a FreeIPMI que no verifique los códigos de autenticación devueltos de las respuestas a los comandos IPMI 1.5. Soluciona sistemas que devuelven códigos de autenticación inválidos debido a errores de hash o implementación. Se advierte a los usuarios sobre el uso de esta opción, ya que elimina una verificación de autenticación que verifica la validez de un paquete. Sin embargo, en la mayoría de las organizaciones, es poco probable que sea un problema de seguridad. Aquellos que encuentren este problema pueden ver errores como "tiempo de espera de conexión", "tiempo de espera de sesión" o "tiempo de espera de verificación de contraseña". Problema observado en Xyratex FB-H8-SRAY, Intel Windmill, Quanta Winterfell y Wiwynn Windmill.

intel20 - Esta bandera de solución alternativa solucionará varios problemas de autenticación IPMI 2.0 de Intel. Los problemas cubiertos incluyen el relleno de nombres de usuario y el truncamiento de contraseñas si el algoritmo de autenticación es HMAC-MD5-128. Aquellos que encuentren este problema pueden ver errores como "nombre de usuario inválido", "contraseña inválida" o "k_g inválido". Problema observado en Intel SE7520AF2 con Intel Server Management Module (Professional Edition).

supermicro20 - Esta bandera de solución alternativa solucionará varios problemas de autenticación IPMI 2.0 de Supermicro en placas base con firmware IPMI Peppercon. Los problemas cubiertos incluyen el manejo de códigos de autenticación de longitud inválida. Aquellos que encuentren este problema pueden ver errores de "contraseña inválida". Problema observado en Supermicro H8QME con tarjeta hija SIMSO. Confirmado que se ha solucionado en firmware más reciente.

sun20 - Esta bandera de solución alternativa solucionará varios problemas de autenticación IPMI 2.0 de Sun. Los problemas cubiertos incluyen claves hash de longitud inválida, claves con hash incorrecto y registros de suites de cifrado inválidos. Aquellos que encuentren este problema pueden ver errores de "contraseña inválida" o "error de bmc". Problema observado en Sun Fire 4100/4200/4500 con ILOM. Esta solución alternativa incluye automáticamente la solución alternativa "opensesspriv".

opensesspriv - Esta bandera de solución alternativa alterará ligeramente el protocolo de conexión IPMI 2.0 de FreeIPMI para solucionar un algoritmo de hash inválido utilizado por el sistema remoto. El nivel de privilegio enviado durante la etapa de Apertura de Sesión de una conexión IPMI 2.0 se utiliza para hashear claves en lugar del nivel de privilegio enviado durante la etapa de conexión RAKP1. Aquellos que encuentren este problema pueden ver errores como "contraseña inválida", "k_g inválido", "código de estado rmcpplus erróneo" o "no se puede obtener el nivel de privilegio para este usuario". Problema observado en Sun Fire 4100/4200/4500 con ILOM, Inventec 5441/Dell Xanadu II, Supermicro X8DTH, Supermicro X8DTG, Intel S5500WBV/Penguin Relion 700, Intel S2600JF/Appro 512X, Quanta QSSC-S4R/Appro GB812X-CN, Dell C5220 y el BMC de software OpenIPMI. Esta solución alternativa se activa automáticamente con la solución alternativa "sun20".

integritycheckvalue - Esta bandera de solución alternativa solucionará un valor de verificación de integridad inválido durante el establecimiento de una sesión IPMI 2.0 cuando se utiliza la Suite de Cifrado ID 0. El valor de verificación de integridad debe ser de longitud 0, sin embargo, la placa base remota responde con un campo no vacío. Aquellos que encuentren este problema pueden ver errores de "k_g inválido". Problema observado en Supermicro X8DTG, Supermicro X8DTU e Intel S5500WBV/Penguin Relion 700, e Intel S2600JF/Appro 512X.

assumemaxsdrrecordcount - Esta solución alternativa indicará a la lectura de SDR que deje de leer después de haber leído un número máximo conocido de registros SDR. Esto solucionará sistemas que tienen funciones de lectura SDR mal implementadas. Aquellos que encuentren este problema pueden ver errores de "conteo de registros SDR inválido". Problema observado en una placa base Inspur no especificada.

discretereading - Esta opción de solución alternativa permitirá leer lecturas de sensores analógicos (es decir, rpm, grados, etc.) incluso si el código de tipo de evento/lectura para el sensor es para un sensor discreto (es decir, aserción vs. desaserción). Esta opción soluciona registros SDR mal definidos (y discutiblemente ilegales) que esperan que las lecturas de sensores analógicos se lean junto con sensores discretos. Se confirma que esta opción soluciona problemas en las placas base HP Proliant DL380 G7 y HP ProLiant ML310 G5.

ignorescanningdisabled - Esta opción de solución alternativa permitirá leer las lecturas de sensores incluso si el bit de escaneo del sensor indica que un sensor está deshabilitado. Esta opción soluciona placas base que indican incorrectamente que los sensores están deshabilitados. Este problema puede existir en su placa base si los sensores se enumeran como "N/A" aunque deberían estar disponibles. Se confirma que esta opción soluciona problemas en las placas base Dell Poweredge 2900, Dell Poweredge 2950, Dell Poweredge R410, Dell Poweredge R610 y HP Integrity rx3600.

assumebmcowner - Esta opción de solución alternativa permitirá leer las lecturas de sensores si el propietario del sensor es el BMC, pero el propietario del sensor informado no es el BMC. Normalmente, los sensores propiedad de un propietario de sensor que no es BMC deben ser puenteados (por ejemplo, con la opción --bridge-sensors), sin embargo, si el propietario del sensor que no es BMC es inválido, el puente falla. Esta opción soluciona placas base que informan incorrectamente un propietario de sensor que no es BMC asumiendo siempre que el propietario del sensor es el BMC. Este problema puede existir en su placa base si los sensores se enumeran como "N/A" aunque deberían estar disponibles. Se confirma que esta opción soluciona problemas en las placas base Fujitsu RX300 y Fujitsu RX300S2.

ignoreauthcode - Esta opción de solución alternativa permitirá leer las lecturas de sensores si la máquina remota está calculando incorrectamente los códigos de autenticación (es decir, hashes de autenticación) al comunicarse a través de LAN. Este problema puede existir en su sistema si el error "tiempo de espera de sesión" o si hay una apariencia de bloqueo. Se advierte a los usuarios sobre el uso de esta opción, ya que elimina una verificación de autenticación que verifica la validez de un paquete. Sin embargo, en la mayoría de las organizaciones, es poco probable que sea un problema de seguridad. La omisión de los paquetes de autenticación se limita solo al período en el que se realizan las lecturas de sensores, y no a ninguna parte de la autenticación de la sesión o la finalización de la sesión. Se confirma que esta opción funciona en Inventec 5441/Dell Xanadu II e Inventec 5442/Dell Xanadu III. (Nota: En los sistemas anteriores, este problema solo se ha observado cuando se utiliza --bridge-sensors).

No Soporte IPMI 1.5 - Se ha descubierto que algunas placas base que admiten IPMI 2.0 no admiten IPMI 1.5. Aquellos que encuentren este problema pueden ver errores como "ipmi 2.0 no disponible" o "tiempo de espera de conexión". Este problema se puede solucionar utilizando IPMI 2.0 en lugar de IPMI 1.5 especificando --driver-type=LAN_2_0. Problema observado en varias placas base HP y Supermicro.

EJEMPLOS

# ipmi-sensors

Muestra todos los sensores y lecturas en la máquina local.

# ipmi-sensors --verbose

Muestra sensores y lecturas detallados en la máquina local.

# ipmi-sensors --record-ids="7,11,102"

Muestra los identificadores de registro de sensor 7, 11 y 102 en la máquina local.

# ipmi-sensors --sensor-types=fan

Muestra todos los sensores de tipo ventilador en la máquina local.

# ipmi-sensors -h ahost -u myusername -p mypassword

Muestra todos los sensores en una máquina remota usando IPMI sobre LAN.

# ipmi-sensors -h mycluster[0-127] -u myusername -p mypassword

Muestra todos los sensores en un clúster usando IPMI sobre LAN.

DIAGNÓSTICOS

Tras una ejecución exitosa, el estado de salida es 0. En caso de error, el estado de salida es 1.

Si se especifican múltiples hosts para la comunicación, el estado de salida es 0 si y solo si todos los objetivos se ejecutan correctamente. De lo contrario, el estado de salida es 1.

PROBLEMAS CONOCIDOS

En sistemas operativos antiguos, si ingresa su nombre de usuario, contraseña y otra información potencialmente relevante para la seguridad en la línea de comandos, esta información puede ser descubierta por otros usuarios al usar herramientas como el ps(1) comando o al mirar en el sistema de archivos /proc. Generalmente es más seguro ingresar la información de contraseña con opciones como las opciones -P o -K. Configurar información relevante para la seguridad en el archivo de configuración de FreeIPMI también sería una forma apropiada de ocultar esta información.

Para prevenir ataques de fuerza bruta, algunos BMC se "bloquearán" temporalmente después de un número de errores de autenticación remota. Puede que necesite esperar un tiempo para que este bloqueo temporal pase antes de que pueda autenticarse de nuevo.

Algunos sensores pueden mostrarse como no disponibles (es decir, N/A) porque el propietario del sensor no es el BMC. Para intentar enlazar sensores y acceder a sensores que no están en el BMC, los usuarios pueden desear probar las -b o --bridge-sensors opciones.
