DESCRIPCIÓ

N

ipmi-config se utiliza para obtener y establecer parámetros de configuración en IPMI. Puede usarse para configurar nombres de usuario, contraseñas, información de red, seguridad, Serial-over-LAN (SOL), filtrado de eventos de plataforma (PEF), dispositivos de arranque, política de restauración de energía, umbrales de sensores, eventos de sensores y muchas más opciones de configuración. Generalmente se requiere alguna configuración antes de que la mayoría de las herramientas IPMI puedan usarse para acceder a una máquina de forma remota. Por defecto, ipmi-config le permitirá --checkout o --commit solo los valores IPMI esenciales necesarios para la configuración de IPMI. Para campos de configuración avanzada adicionales relacionados con la configuración del Chasis (incluyendo opciones de arranque), el filtrado de eventos de plataforma (PEF) o los sensores, consulte la opción --category a continuación. Para más detalles sobre la configuración IPMI esencial, consulte ipmi-config.conf(5). La mayoría de las operaciones de configuración requieren privilegios ADMIN al usar ipmi-config fuera de banda. Aunque no es necesario conectarse mediante un usuario con privilegios ADMIN para el uso fuera de banda, la gran mayoría de las opciones de configuración no se recuperarán ni se

establecerán.

A continuación se enumeran las opciones IPMI generales, las opciones específicas de la herramienta, información de solución de problemas, información sobre métodos alternativos, ejemplos y problemas conocidos. Para una introducción general a FreeIPMI, consulte freeipmi(7). Consulte USO GENERAL más abajo para una descripción del uso básico de ipmi-confi

g

USO

GENERAL

La mayoría de los usuarios de

desearán:

A) Ejecutar con --checkout para obtener una copia de la configuración actual y almacenarla en un archivo. La salida estándar puede ser redirigida a un archivo o se puede especificar un archivo con la opción --fil

ename.

B) Editar el archivo de configuración con un

editor.

C) Confirmar la configuración de vuelta usando la opción --commit y especificando el archivo de configuración con la opción --filename. La configuración puede ser confirmada a múltiples hosts en paralelo a través del soporte de rango de

Aunque no es típicamente necesario, algunas placas base no almacenan los valores de configuración en memoria no volátil. Por lo tanto, después de que el sistema se reinicie, algunos valores de configuración pueden haber cambiado. El usuario puede desear ejecutar herramientas de configuración en cada arranque para asegurarse de que los valores de configuración

permanezcan.

Los comentarios se listarán ocasionalmente en los archivos verificados con información sobre cómo configurar campos. La página del manual ipmi-config.conf(5) también proporciona información adicional sobre el significado de los diferentes

campos.

Para usuarios con grandes clústeres o conjuntos de nodos, puede desear usar el mismo archivo de configuración para todos los nodos. El único problema con esto es que la dirección IP y la dirección MAC serán diferentes en cada nodo de su clúster y por lo tanto no pueden ser configurados a través del mismo archivo de configuración. La dirección IP y la dirección MAC en su archivo de configuración pueden ser sobrescritas en la línea de comandos usando la opción --key-pair. El siguiente ejemplo podría ser usado en un script para configurar cada nodo en un clúster con el mismo archivo de configuración de BMC. El script solo necesita determinar la dirección IP y la dirección MAC correctas a

usar.

# ipmi-config --commit -k Lan_Conf:Ip

_Address=$MY_IP -k Lan_Conf:Mac_A
ddress=$MY_MAC --filename=my_bmc.conf

INFORMACIÓN DE CONFIGURACIÓN DE CASOS ESPECIALES DEL NÚCLEO

Los campos UserN:Password (donde N es un número) no se pueden extraer en algunos sistemas, por lo tanto, el valor extraído siempre estará en blanco.

El campo UserN:Enable_User (donde N es un número) no se puede extraer en sistemas IPMI más antiguos, por lo tanto, el valor extraído a veces estará en blanco.

Los campos UserN:Lan_Session_Limit y UserN:Serial_Session_Limit (donde N es un número) no se pueden extraer en algunos sistemas, por lo tanto, el valor extraído siempre estará en blanco. Si no se especifica en commits posteriores de configuraciones, el campo puede restablecerse a 0 debido a un requisito de que otros campos (configurados junto con el límite de sesión) requerirán un valor de entrada para el límite de sesión. En la mayoría de las condiciones, no es necesario configurar este campo y la mayoría de los usuarios pueden optar por ignorarlo. Este campo se considera opcional según los estándares IPMI y puede generar errores al intentar configurarlo en un valor distinto de cero. Si ocurren errores, restablecer el valor a 0 debería resolver los problemas.

Los campos Lan_Conf:IP_Address y Lan_Conf:MAC_Address no se pueden confirmar en paralelo a través de la soporte de hostrange. Cada máquina debe configurarse con una tupla única de dirección IP y dirección MAC, por lo tanto, prohibimos esta configuración en ipmi-config.

En algunas placas base, Lan_Conf:MAC_Address puede ser de solo lectura y la dirección MAC se configura automáticamente.

En algunas placas base, Lan_Conf:MAC_Address puede ser de solo lectura y la dirección MAC se configura a través de un comando OEM. Consulte ipmi-oem(8) para ver si la configuración OEM para su placa base es compatible.

En algunas placas base, una serie de campos de configuración de usuario no se pueden leer ni configurar hasta después de que se haya configurado un nombre de usuario no nulo o una contraseña no nula. En algunos de estos casos, una salida apropiada en el archivo de configuración indicará esta situación. Sin embargo, no todos los casos de esquina de las placas base pueden ser detectados. Los usuarios pueden desear jugar con el orden de los campos para solucionar estos problemas.

En algunas placas base, la autenticación OEM en Lan_Conf_Auth no se puede habilitar. Sin embargo, la configuración predeterminada de la placa base tiene estos campos habilitados. Se recomienda a los usuarios que deshabiliten toda la autenticación OEM en esta sección.

En algunas placas base, pueden existir múltiples canales para la comunicación IPMI LAN o Serial. Si existen múltiples canales, la configuración de ambos canales puede verse y configurarse finalmente ejecutando --checkout en modo detallado. Cada sección o nombre de clave se sufijará apropiadamente con la palabra Channel y el número del canal. Por ejemplo, podría ver un Lan_Conf_Channel_1 y Lan_Conf_Channel_3, donde puede configurar la configuración LAN en los canales 1 y 3 respectivamente.

En algunas placas base, los cambios de configuración no serán "absorbidos" por el sistema hasta que la placa base se reinicie completamente. Esto se puede lograr apagando y encendiendo físicamente el sistema (por ejemplo, presionando un botón), o se puede lograr a través de un reinicio en frío. Un reinicio en frío se puede ejecutar a través de bmc-device.

INFORMACIÓN DE CONFIGURACIÓN DE CASOS ESPECIALES DEL CHASIS

Los campos Chassis_Front_Panel_Buttons:Enable_Standby_Button_For_Entering_Standby, Chassis_Front_Panel_Buttons:Enable_Diagnostic_Interrupt_Button Chassis_Front_Panel_Buttons:Enable_Reset_Button, y Chassis_Front_Panel_Buttons:Enable_Power_Off_Button_For_Power_Off_Only pueden no ser capaces de ser extraídos en algunos sistemas IPMI, por lo tanto, el valor extraído puede estar en blanco. Algunos de estos campos pueden ser deshabilitables, mientras que otros no. El campo Chassis_Power_Conf:Power_Control_Interval no puede ser extraído. Por lo tanto, el valor extraído siempre estará en blanco.

INFORMACIÓN DE CONFIGURACIÓN DE CASOS ESPECIALES DE PEF

En algunas placas base, pueden existir múltiples canales para la comunicación IPMI LAN. Si existen múltiples canales, la configuración de ambos canales puede verse y configurarse finalmente ejecutando --checkout en modo detallado. Cada nombre de sección se sufijará apropiadamente con la palabra Channel y el número del canal. Por ejemplo, podría ver una Community_String_Channel_1 y una Community_String_Channel_3, donde puede configurar la Cadena de Comunidad en los Canales 1 y 3 respectivamente. INFORMACIÓN DE CONFIGURACIÓN DE CASOS ESPECIALES DE SENSORES

Dado que muchos campos configurables implican números decimales, pueden producirse imprecisiones de precisión/punto flotante al configurar nuevos umbrales. Las imprecisiones pueden no ser aparentes de inmediato. Se recomienda a los usuarios que verifiquen sus cambios después de configurar nuevos umbrales.

SOPORTE DE HOSTRANGED

Se pueden ingresar múltiples hosts ya sea como listas explícitas de hosts separadas por comas o como un rango de nombres de host en la forma general: prefijo[n-m,l-k,...], donde n < m y l < k, etc. La última forma no debe confundirse con las clases de caracteres de expresiones regulares (también denotadas por []). Por ejemplo, foo[19] no representa foo1 o foo9, sino que representa un rango degenerado: foo19.

Esta sintaxis de rango está destinada solo como una conveniencia en clústeres con una convención de nombres prefijoNN y la especificación de rangos no debe considerarse necesaria; la lista foo1,foo9 podría especificarse como tal, o mediante el rango foo[1,9].

A continuación, se muestran algunos ejemplos de uso de rangos:

    foo[01-05] en lugar de foo01,foo02,foo03,foo04,foo05
    foo[7,9-10] en lugar de foo7,foo9,foo10
    foo[0-3] en lugar de foo0,foo1,foo2,foo3

Como recordatorio al lector, algunos shells interpretarán corchetes ([ y ]) para la coincidencia de patrones. Dependiendo de su shell, puede ser necesario incluir listas de rangos entre comillas.

Cuando el usuario especifica varios hosts, se ejecutará un hilo para cada host en paralelo hasta el fanout configurado (que se puede ajustar mediante la opción -F). Esto permitirá la comunicación a un gran número de nodos mucho más rápidamente que si se hiciera en serie.

Por defecto, la salida estándar de cada nodo especificado se mostrará con el nombre del host precediendo a cada línea. Aunque esta salida es legible en muchas situaciones, puede ser difícil de leer en otras situaciones. Por ejemplo, la salida de múltiples nodos puede mezclarse. Las opciones -B y -C se pueden usar para cambiar este valor predeterminado.

La comunicación IPMI en banda se utilizará cuando se especifique el host "localhost". Esto permite al usuario agregar el localhost a la salida de hostranged.

SOLUCIÓN GENERAL DE PROBLEMAS

La mayoría de las veces, los problemas de IPMI se deben a problemas de configuración.

Los problemas de IPMI sobre LAN implican una configuración incorrecta del BMC de la máquina remota. Verifique que lo siguiente esté configurado correctamente en el BMC de la máquina remota: dirección IP, dirección MAC, máscara de subred, nombre de usuario, habilitación de usuario, privilegio de usuario, contraseña, privilegio de LAN, habilitación de LAN y tipos de autenticación permitidos. Para conexiones IPMI 2.0, verifique que los privilegios del conjunto de cifrado y la clave K_g estén configurados correctamente. La herramienta ipmi-config(8) se puede utilizar para verificar y/o cambiar estas configuraciones.

Los problemas de IPMI en banda suelen ser causados por controladores configurados incorrectamente o BMC no estándar.

Además de los consejos de solución de problemas a continuación, consulte también SOLUCIONES a continuación si existen errores específicos del proveedor que se hayan descubierto y resuelto.

A continuación, se enumeran muchos de los problemas comunes de mensajes de error. Para soporte adicional, envíe un correo electrónico a la lista de correo <freeipmi-users@gnu.org>.

"nombre de usuario inválido" - El nombre de usuario ingresado (o un nombre de usuario NULL si no se ingresó ninguno) no está disponible en la máquina remota. También es posible que la configuración del nombre de usuario del BMC remoto sea incorrecta.

"contraseña inválida" - La contraseña ingresada (o una contraseña NULL si no se ingresó ninguna) no es correcta. También es posible que la contraseña del usuario no esté configurada correctamente en el BMC remoto.

"tiempo de espera de verificación de contraseña" - La verificación de contraseña ha expirado. Ocurrió un error de "contraseña inválida" (descrito anteriormente) o un "tiempo de espera de sesión" genérico (descrito a continuación). Durante este punto del protocolo, no se puede diferenciar cuál ocurrió.

"k_g inválido" - La clave K_g ingresada (o una clave K_g NULL si no se ingresó ninguna) no es correcta. También es posible que la clave K_g no esté correctamente configurada en el BMC remoto.

"nivel de privilegio insuficiente" - Un comando IPMI requiere un privilegio de usuario superior al con el que se autenticó. Intente autenticarse con un privilegio superior. Esto puede requerir la autenticación con un usuario diferente que tenga un privilegio máximo superior.

"no se puede obtener el nivel de privilegio para este usuario" - El nivel de privilegio con el que está intentando autenticarse es superior al máximo permitido para este usuario. Intente nuevamente con un privilegio inferior. También es posible que el nivel de privilegio máximo permitido para un usuario no esté configurado correctamente en el BMC remoto.

"tipo de autenticación no disponible para el nivel de privilegio intentado" - El tipo de autenticación con el que desea autenticarse no está disponible

disponibles para este nivel de privilegio. Por favor, inténtelo de nuevo con un tipo de autenticación alternativo o un nivel de privilegio alternativo. También es posible que los tipos de autenticación disponibles con los que puede autenticarse no estén configurados correctamente en el BMC

remoto.

"cipher suite id unavailable" - El id de la suite de cifrado con el que desea autenticarse no está disponible en el BMC remoto. Por favor, inténtelo de nuevo con un id de la suite de cifrado alternativo. También es posible que los ids de la suite de cifrado disponibles no estén configurados correctamente en el BMC

remoto.

"ipmi 2.0 unavailable" - No se detectó IPMI 2.0 en la máquina remota. Por favor, intente usar IPMI 1.5 en su

lugar.

"connection timeout" - La comunicación IPMI inicial falló. Hay varios errores potenciales posibles, incluyendo un nombre de host no válido especificado, una dirección IP de IPMI que no se puede resolver, IPMI no está habilitado en el servidor remoto, la conexión de red es deficiente, etc. Por favor, verifique la configuración y la

conectividad.

"session timeout" - La sesión IPMI ha expirado. Por favor, reconéctese. Si este error ocurre a menudo, es posible que desee aumentar el tiempo de espera de retransmisión. Algunos BMC remotos son considerablemente más lentos que

otros.

"device not found" - No se pudo encontrar el dispositivo especificado. Por favor, verifique la configuración o las entradas e inténtelo de

nuevo.

"driver timeout" - La comunicación con el controlador o el dispositivo ha expirado. Por favor, inténtelo de

nuevo.

"message timeout" - La comunicación con el controlador o el dispositivo ha expirado. Por favor, inténtelo de

nuevo.

"BMC busy" - El BMC está ocupado actualmente. Puede estar procesando información o tener demasiadas sesiones simultáneas para gestionar. Por favor, espere e inténtelo de

nuevo.

"could not find inband device" - No se pudo encontrar un dispositivo inband. Por favor, verifique la configuración o especifique un dispositivo o controlador específico en la línea de

comandos.

"driver timeout" - El controlador inband ha expirado al comunicarse con el B

MC o el procesador de servicio local. El BMC o el procesador de servicio pu
eden estar ocupados o (en el peor de los casos) posiblemente no funcionando.

ALTERNATIVAS

Con tantos proveedores diferentes implementando sus propias soluciones IPMI, diferentes proveedores pueden implementar sus protocolos IPMI incorrectamente. A continuación se describen varias soluciones alternativas actualmente disponibles para manejar los problemas de cumplimiento descubiertos. Cuando sea posible, se han implementado soluciones alternativas para que sean transparentes al usuario. Sin embargo, algunas requerirán que el usuario especifique que se utilice una solución alternativa a través de la opción

-W.

El hardware listado a continuación puede indicar solo el hardware en el que se descubrió un problema. Las versiones más nuevas de hardware pueden corregir los problemas indicados a continuación. Máquinas similares de otros proveedores pueden o no exhibir los mismos problemas. Diferentes proveedores pueden licenciar su firmware del mismo desarrollador de firmware IPMI, por lo que puede valer la pena probar las soluciones alternativas listadas a continuación incluso si su placa base no está

listada.

Si cree que su hardware tiene un problema de cumplimiento adicional que necesita que se implemente una solución alternativa, por favor, contacte a los mantenedores de FreeIPMI en <freeipmi-users@gnu.org> o <freeipmi-devel@gnu.org>

.

assumeio - Esta opción de solución alternativa asumirá que las interfaces inband se comunican con la E/S del sistema en lugar de estar mapeadas en memoria. Esto solucionará sistemas que reportan direcciones base no válidas. Aquellos que encuentren este problema pueden ver errores "device not supported" o "could not find inband device". Problema observado en HP ProLiant DL145

G1.

spinpoll - Esta opción de solución alternativa informará a algunos controladores inband (notablemente el controlador KCS) que giren mientras hacen sondeos en lugar de poner el proceso a dormir. Esto puede mejorar significativamente el tiempo de ejecución de las herramientas porque la granularidad del planificador del sistema operativo puede ser mucho mayor que el tiempo que toma realizar una única transacción de mensaje IPMI. Sin embargo, al girar, su sistema puede estar realizando un trabajo menos útil al no cambiar el contexto de la herramienta para una tarea más

útil.

authcap - Esta opción de solución alternativa omitirá las verificaciones tempranas de capacidades de nombre de usuario, capacidades de autenticación y soporte de K_g, y permitirá que la autenticación IPMI tenga éxito. Soluciona múltiples problemas en los que el sistema remoto no reporta correctamente las capacidades de nombre de usuario, las capacidades de autenticación o el estado de K_g. Aquellos que encuentren este problema pueden ver errores "username invalid", "authentication type unavailable for attempted privilege level" o "k_g invalid". Problema observado en Asus P5M2/P5MT-R/RS162-E4/RX4, Intel SR1520ML/X38ML, y Sun Fire 2200/4150/4450 con

ELOM.

nochecksumcheck - Esta opción de solución alternativa le dirá a FreeIPMI que no verifique las sumas de verificación devueltas por las respuestas de los comandos IPMI. Soluciona sistemas que devuelven sumas de verificación no válidas debido a errores de implementación, pero el paquete es de otro modo válido. Se advierte a los usuarios sobre el uso de esta opción, ya que elimina la validación de la integridad del paquete en varias circunstancias. Sin embargo, es poco probable que sea un problema en la mayoría de las situaciones. Aquellos que encuentren este problema pueden ver errores "connection timeout", "session timeout" o "password verification timeout". En conexiones IPMI 1.5, la solución alternativa "noauthcodecheck" también puede ser necesaria. Problema observado en Supermicro X9SCM-iiF, Supermicro X9DRi-F, y Supermicro

X9DRFR.

idzero - Esta opción de solución alternativa permitirá que el cliente acepte IDs de sesión vacíos. Soluciona sesiones IPMI que reportan IDs de sesión vacíos al cliente. Aquellos que encuentren este problema pueden ver errores "session timeout". Problema observado en Tyan S2882 con BMC

M3289.

unexpectedauth - Esta opción de solución alternativa permitirá que se verifiquen códigos de autenticación no nulos inesperados como si se esperaran. Soluciona un problema cuando los paquetes contienen datos de autenticación no nulos cuando deberían ser nulos debido a la autenticación por mensaje deshabilitada. Aquellos que encuentren este problema pueden ver errores "session timeout". Problema observado en Dell PowerEdge 2850, SC1425. Confirmado como corregido en firmware más

nuevo.

forcepermsg - Esta opción de solución alternativa forzará el uso de la autenticación por mensaje sin importar lo que anuncie el sistema remoto. Soluciona un problema cuando la autenticación por mensaje se anuncia como deshabilitada en el sistema remoto, pero en realidad es requerida por el protocolo. Aquellos que encuentren este problema pueden ver errores "session timeout". Problema observado en IBM eServer

325.

endianseq - Esta opción de solución alternativa invertirá el orden de los bytes de los números de secuencia de sesión para permitir que la sesión continúe correctamente. Soluciona números de secuencia de sesión de IPMI 1.5 que tienen el orden de los bytes incorrecto. Aquellos que encuentren este problema pueden ver errores "session timeout". Problema observado en algunos Sun ILOM 1.0/2.0 (depende del orden de los bytes del procesador de servicio)

.

noauthcodecheck - Esta opción de solución alternativa le dirá a FreeIPMI que no verifique los códigos de autenticación devueltos por las respuestas de los comandos IPMI 1.5. Soluciona sistemas que devuelven códigos de autenticación no válidos debido a errores de hash o de implementación. Se advierte a los usuarios sobre el uso de esta opción, ya que elimina una verificación de autenticación que valida la integridad de un paquete. Sin embargo, en la mayoría de las organizaciones, es poco probable que sea un problema de seguridad. Aquellos que encuentren este problema pueden ver errores "connection timeout", "session timeout" o "password verification timeout". Problema observado en Xyratex FB-H8-SRAY, Intel Windmill, Quanta Winterfell, y Wiwynn

Windmill.

intel20 - Esta opción de solución alternativa solucionará varios problemas de autenticación IPMI 2.0 de Intel. Los problemas cubiertos incluyen el relleno de nombres de usuario y el truncamiento de contraseñas si el algoritmo de autenticación es HMAC-MD5-128. Aquellos que encuentren este problema pueden ver errores "username invalid", "password invalid" o "k_g invalid". Problema observado en Intel SE7520AF2 con Intel Server Management Module (Professional Edition)

.

supermicro20 - Esta opción de solución alternativa solucionará varios problemas de autenticación IPMI 2.0 de Supermicro en placas base con firmware IPMI de Peppercon. Los problemas cubiertos incluyen el manejo de códigos de autenticación de longitud no válida. Aquellos que encuentren este problema pueden ver errores "password invalid". Problema observado en Supermicro H8QME con tarjeta hija SIMSO. Confirmado como corregido en firmware más

nuevo.

sun20 - Esta opción de solución alternativa solucionará varios problemas de autenticación IPMI 2.0 de Sun. Los problemas cubiertos incluyen claves de hash de longitud no válida, claves con hash incorrecto y registros de suite de cifrado no válidos. Aquellos que encuentren este problema pueden ver errores "password invalid" o "bmc error". Problema observado en Sun Fire 4100/4200/4500 con ILOM. Esta solución alternativa incluye automáticamente la solución alternativa

"opensesspriv".

opensesspriv - Esta opción de solución alternativa alterará ligeramente el protocolo de conexión IPMI 2.0 de FreeIPMI para solucionar un algoritmo de hash no válido utilizado por el sistema remoto. El nivel de privilegio enviado durante la etapa de Apertura de Sesión de una conexión IPMI 2.0 se utiliza para las claves de hash en lugar del nivel de privilegio enviado durante la etapa de conexión RAKP1. Esta solución alternativa se activa automáticamente con la solución alternativa

integritycheckvalue - Esta opción de solución alternativa solucionará un valor de verificación de integridad no válido durante el establecimiento de una sesión IPMI 2.0 al usar el ID de Suite de Cifrado 0. El valor de verificación de integridad debería tener una longitud de 0, sin embargo, la placa base remota responde con un campo no vacío. Aquellos que encuentren este problema pueden ver errores "k_g invalid". Problema observado en Supermicro X8DTG, Supermicro X8DTU, y Intel S5500WBV/Penguin Relion 700, y Intel S2600JF/Appro

GENERAL USE

The ipmi-config utility is used to get, set, and diff IPMI configuration information.

The utility can be used to configure the following types of configuration information:

  • Core configuration information.
  • Chassis configuration information.
  • PEF configuration information.
  • Sensors configuration information.
  • SOL configuration information.
  • User configuration information.

The configuration information can be retrieved from the BMC, or stored to the BMC. The configuration information can be outputted to the console, or to a file. The configuration information can also be diffed against the BMC. For more information on the configuration file format, see ipmi-config.conf(5).

In order to use ipmi-config, you must first specify the interface to use for communication with the BMC. This can be done by specifying the --interface= option, or by specifying the IPMI_INTERFACE environment variable. For a complete listing of the interfaces, see freeipmi(7).

If multiple hosts are specified, then the configuration file may be specified once for all hosts. However, it is generally recommended that each host have its own configuration file.

CORE SPECIAL CASE CONFIGURATION INFORMATION

Some BMCs, such as the HP ProLiant ML110 G7, will require a delay between commits to prevent the BMC from becoming unresponsive. The option --commit-delay=DELAY can be used to add a delay between commits. The delay is specified in milliseconds. For example, setting --commit-delay=1000 will add a 1 second delay between commits.

Some motherboards have BMCs that can be overwhelmed by commits. The option --commit-throttle can be used to add a delay between commits. This is similar to --commit-delay, but instead of adding a delay after every commit, it adds a delay after every key. It works around motherboards that have BMCs that can be overwhelmed by commits. Those hitting this issue may see commit errors or commits not being written to the BMC. Issue observed on Quanta S99Q/Dell FS12-TY and Dell PowerEdge T320.

CHASSIS SPECIAL CASE CONFIGURATION INFORMATION

Some BMCs, such as the Dell PowerEdge R710, will report the chassis power status incorrectly. The option --chassis-power-status-workaround can be used to correct this. This option forces ipmi-config to assume that the chassis power is on, regardless of what the BMC reports.

PEF SPECIAL CASE CONFIGURATION INFORMATION

On some motherboards, the PEF configuration is not properly initialized. The option --pef-initialize can be used to force the PEF configuration to be initialized. This option should be used with caution, as it will reset the PEF configuration to its default values.

SENSORS SPECIAL CASE CONFIGURATION INFORMATION

Some BMCs, such as the Supermicro X8DTL, will report sensor readings incorrectly. The option --sensor-reading-workaround can be used to correct this. This option forces ipmi-config to assume that the sensor readings are correct, regardless of what the BMC reports.

HOSTRANGED SUPPORT

The ipmi-config utility can be used to configure the hostranged daemon. The hostranged daemon is used to manage the hostranged service. The hostranged service is used to monitor the hostranged sensors.

The following options can be used to configure the hostranged daemon:

--hostranged-config=FILE
Read the configuration file from FILE. If not specified, then the default configuration file "~/.hostranged/hostranged.conf" is used.
--hostranged-port=PORT
Use PORT instead of the default.
--hostranged-host=HOST
Use HOST instead of the default.
--hostranged-verbose
Enable verbose output of hostranged.
--hostranged-debug
Enable debug output of hostranged.

GENERAL TROUBLESHOOTING

If you are having trouble communicating with the BMC, try the following:

  • Ensure that the IPMI interface is correctly configured. See freeipmi(7) for more information.
  • Ensure that the BMC is powered on and accessible.
  • Try using a different IPMI interface.
  • Try using a different IP address or hostname.
  • Try using a different username and password.
  • Check the BMC logs for any errors.

WORKAROUNDS

The following workarounds are available:

--commit-throttle - Add a delay between commits. This is similar to --commit-delay, but instead of adding a delay after every commit, it adds a delay be tween the commit of every key. It works around motherboards that have BMCs that can be overwhelmed by commits. Those hitting this issue may see commit errors or commits not being written to the BMC. Issue observed on Quanta S99Q/Dell FS12-TY and Dell PowerEdge T320.

solchannelassumelanchannel - This workaround will force ipmi-config to assume that the channel used SOL is identical to the channel used for LAN. On some motherboards, the SOL channel is reported incorrectly, leading to incorrect configuration. Most notably, this problem has come up when attempting to configure multiple channels. Issue observed on Intel S5500WBV/Penguin Relion 700.

DIAGNOSTICS

Upon successful execution, exit status is 0. On non-fatal error, exit status is 1. On fatal error, exit status is 2.

If multiple hosts are specified for communication, the exit status is 0 if and only if all targets successfully execute. If any non-fatal error occurs, exit status is 1. If any fatal error occurs, exit status is 2.

KNOWN ISSUES

On older operating systems, if you input your username, password, and other potentially security relevant information on the command line, this information may be discovered by other users when using tools like the ps(1) command or looking in the /proc file system. It is generally more secure to input password information with options like the -P or -K options. Configuring security relevant information in the FreeIPMI configuration file would also be an appropriate way to hide this information.

In order to prevent brute force attacks, some BMCs will temporarily "lock up" after a number of remote authentication errors. You may need to wait awhile in order to this temporary "lock up" to pass before you may authenticate again.
