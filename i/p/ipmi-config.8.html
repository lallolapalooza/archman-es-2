DESCRIPCIÓ

N

ipmi-config se utiliza para obtener y establecer parámetros de configuración en IPMI. Puede usarse para configurar nombres de usuario, contraseñas, información de red, seguridad, Serial-over-LAN (SOL), filtrado de eventos de plataforma (PEF), dispositivos de arranque, política de restauración de energía, umbrales de sensores, eventos de sensores y muchas más opciones de configuración. Generalmente se requiere cierta configuración antes de que la mayoría de las herramientas IPMI puedan usarse para acceder a una máquina de forma remota. De forma predeterminada, ipmi-config le permitirá --checkout o --commit solo los valores IPMI esenciales necesarios para la configuración de IPMI. Para campos de configuración avanzada adicionales relacionados con la configuración del chasis (incluyendo opciones de arranque), el filtrado de eventos de plataforma (PEF) o los sensores, consulte la opción --category a continuación. Para más detalles sobre la configuración IPMI esencial, consulte ipmi-config.conf(5). La mayoría de las operaciones de configuración requieren privilegios ADMIN al usar ipmi-config fuera de banda. Aunque no es necesario conectarse mediante un usuario con privilegios ADMIN para el uso fuera de banda, la gran mayoría de las opciones de configuración no se obtendrán ni se

establecerán.

A continuación se enumeran las opciones IPMI generales, las opciones específicas de la herramienta, información de solución de problemas, información de métodos alternativos, ejemplos y problemas conocidos. Para una introducción general a FreeIPMI, consulte freeipmi(7). Consulte USO GENERAL a continuación para una descripción del uso básico de ipmi-confi

g
.

Las siguientes opciones manipulan la salida de rango de hosts. Consulte SOPORTE DE RANGO DE HOSTS más abajo para obtener información adicional sobre rangos de

-B, --buffer-out
put
Almacena en búfer la salida de rango de hosts. Para cada nodo, almacena en búfer la salida estándar hasta que el nodo haya completado su operación IPMI. Al especificar esta opción, los datos pueden parecer que se emiten más lentamente al usuario, ya que toda la operación IPMI debe completarse antes de que se pueda emitir algún dato. Consulte SOPORTE DE RANGO DE HOSTS más abajo para obtener información
adicional.
-C, --consolidate-out

Consolida la salida de rango de hosts. La salida estándar completa de cada nodo especificado se consolidará para que los nodos con salida idéntica no se emitan dos veces. Un encabezado listará aquellos nodos con la salida consolidada. Cuando se especifica esta opción, no se puede ver ninguna salida hasta que las operaciones IPMI a todos los nodos se hayan completado. Si el usuario interrumpe el programa antes de tiempo, toda la salida consolidada actual se volcará. Consulte SOPORTE DE RANGO DE HOSTS más abajo para obtener información
adicional.

M
Especifica el fanout de múltiples hosts. Se utiliza un algoritmo de "ventana deslizante" (o fanout) para la comunicación IPMI paralela, de modo que los nodos más lentos o los nodos con tiempo de espera no obstruyan la comunicación paralela. El número máximo de hilos disponibles al mismo tiempo está limitado por el fanout. El valor predeterminado es
64.

Elimina los hosts determinados como no detectados por ipmidetect. El demonio ipmidetectd debe estar ejecutándose en el nodo que ejecuta el

USO

GENERAL

La mayoría de los usuarios

querrán:

A) Ejecutar con --checkout para obtener una copia de la configuración actual y almacenarla en un archivo. La salida estándar se puede redirigir a un archivo o se puede especificar un archivo con la opción --filename

.

B) Editar el archivo de configuración con un

editor.

C) Confirmar la configuración de nuevo usando la opción --commit y especificando el archivo de configuración con la opción --filename. La configuración se puede confirmar en múltiples hosts en paralelo a través del soporte de rango de

hosts.

Aunque no es típicamente necesario, algunas placas base no almacenan los valores de configuración en memoria no volátil. Por lo tanto, después de reiniciar el sistema, algunos valores de configuración pueden haber cambiado. El usuario puede desear ejecutar herramientas de configuración en cada arranque para asegurar que los valores de configuración se

mantengan.

Se listarán comentarios ocasionalmente en los archivos verificados con información sobre cómo configurar campos. La página del manual ipmi-config.conf(5) también proporciona información adicional sobre el significado de diferentes

campos.

Para usuarios con grandes clústeres o conjuntos de nodos, es posible que desee usar el mismo archivo de configuración para todos los nodos. El único problema con esto es que la dirección IP y la dirección MAC serán diferentes en cada nodo de su clúster y por lo tanto no se pueden configurar a través del mismo archivo de configuración. La dirección IP y la dirección MAC en su archivo de configuración pueden ser sobrescritas en la línea de comandos usando la opción --key-pair. El siguiente ejemplo podría usarse en un script para configurar cada nodo en un clúster con el mismo archivo de configuración BMC. El script solo necesita determinar la dirección IP y la dirección MAC correctas para

usar.

# ipmi-config --commit -k Lan_Conf:I

p_Address=$MY_IP -k Lan_Conf:Mac_Ad
dress=$MY_MAC --filename=my_bmc.conf on class="Sh">

INFORMACIÓN DE CONFIGURACIÓN DE CASOS ESPECIALES DE

NÚCLEO

Los campos UserN:Password (donde N es un número) no pueden ser extraídos en algunos sistemas, por lo tanto el valor extraído siempre será

vacío.

Los campos UserN:Enable_User (donde N es un número) no pueden ser extraídos en sistemas IPMI antiguos, por lo tanto el valor extraído será a veces

vacío.

Los campos UserN:Lan_Session_Limit y UserN:Serial_Session_Limit (donde N es un número) no pueden ser extraídos en algunos sistemas, por lo tanto el valor extraído siempre será vacío. Si no se especifica en envíos posteriores de configuraciones, el campo puede ser restablecido a 0 debido a un requisito de que otros campos (configurados junto con el límite de sesión) requerirán un valor de entrada para el límite de sesión. Bajo la mayoría de las condiciones, no es necesario establecer este campo y la mayoría de los usuarios pueden optar por ignorarlo. Este campo es considerado opcional por los estándares de IPMI, y puede resultar en errores al intentar configurarlo a un valor distinto de cero. Si ocurren errores, establecer el valor de vuelta a 0 debería resolver los

problemas.

Los campos Lan_Conf:IP_Address y Lan_Conf:MAC_Address no pueden ser enviados en paralelo mediante soporte de rango de hosts. Cada máquina debe ser configurada con una tupla única de dirección IP y dirección MAC, por lo tanto deshabilitamos esta configuración en ipmi-config

.

En algunas placas base, Lan_Conf:MAC_Address puede ser de solo lectura y la dirección MAC es configurada automáticamente

.

En algunas placas base, Lan_Conf:MAC_Address puede ser de solo lectura y la dirección MAC es configurada mediante un comando OEM. Vea ipmi-oem(8) para ver si la configuración OEM para su placa base es

soportada.

En algunas placas base, varios campos de configuración de usuario no pueden ser leídos o configurados hasta después de que un nombre de usuario no nulo o una contraseña no nula sea configurada. En algunos de estos casos, una salida apropiada en el archivo de configuración indicará esta situación. Sin embargo, no todos los casos especiales de placas base pueden ser detectados. Los usuarios pueden desear experimentar con el orden de los campos para solucionar estos

problemas.

En algunas placas base, la Autenticación OEM en Lan_Conf_Auth no puede ser habilitada. Sin embargo, los ajustes predeterminados de la placa base tienen estos campos habilitados. Se recomienda a los usuarios deshabilitar toda la Autenticación OEM en esta

sección.

En algunas placas base, pueden existir múltiples canales para la comunicación IPMI LAN o Serial. Si existen múltiples canales, la configuración de ambos canales puede ser vista y finalmente configurada ejecutando --checkout bajo modo verboso. Cada sección o nombre de clave tendrá el sufijo apropiado con la palabra Channel y el número de canal. Por ejemplo, podría ver un Lan_Conf_Channel_1 y Lan_Conf_Channel_3, donde puede configurar la configuración LAN en los Canales 1 y 3 respectivamente

.

En algunas placas base, los cambios de configuración no serán "absorbidos" por el sistema hasta que la placa base sea reiniciada físicamente. Esto puede lograrse apagando y encendiendo físicamente el sistema (ej. presionando el botón), o puede lograrse mediante un reinicio en frío. Un reinicio en frío puede ser ejecutado mediante bmc-devic

e
.

SOPORTE DE RANGO DE

HOSTS

Múltiples hosts pueden ser ingresados ya sea como listas explícitas de hosts separadas por comas o un rango de nombres de host en la forma general: prefijo[n-m,l-k,...], donde n < m y l < k, etc. La última forma no debe confundirse con clases de caracteres de expresiones regulares (también denotadas por []). Por ejemplo, foo[19] no representa foo1 o foo9, sino que representa un rango degenerado:

foo19.

Esta sintaxis de rango está destinada solo como una conveniencia en clústeres con una convención de nombres prefijoNN y la especificación de rangos no debe considerarse necesaria -- la lista foo1,foo9 podría ser especificada como tal, o por el rango foo[1,9]

.

Algunos ejemplos de uso de rangos

siguen: 
    foo[01-05] en lugar de foo01,foo02,foo03,foo04,foo05
    foo[7,9-10] en lugar de foo7,foo9,foo10
    foo[0-3] en lugar de foo0,foo1,foo2,
foo3

Como recordatorio para el lector, algunos intérpretes de comandos interpretarán corchetes ([ y ]) para coincidencia de patrones. Dependiendo de su intérprete de comandos, puede ser necesario encerrar las listas de rangos entre

comillas.

Cuando el usuario especifica múltiples hosts, un hilo será ejecutado para cada host en paralelo hasta el abanico configurado (que puede ser ajustado mediante la opción -F). Esto permitirá la comunicación a un gran número de nodos mucho más rápido que si se hiciera en

serie.

Por defecto, la salida estándar de cada nodo especificado será emitida con el nombre de host antepuesto a cada línea. Aunque esta salida es legible en muchas situaciones, puede ser difícil de leer en otras situaciones. Por ejemplo, la salida de múltiples nodos puede mezclarse entre sí. Las opciones -B y -C pueden ser usadas para cambiar este comportamiento por

defecto.

La comunicación IPMI in-band será usada cuando se espec

ifica el host "localhost". Esto permite al usuario
agregar el localhost a la salida de rango de hosts.

SOLUCIÓN DE PROBLEMAS

GENERAL

La mayoría de las veces, los problemas de IPMI se deben a problemas de

configuración.

Los problemas de IPMI sobre LAN involucran una mala configuración del BMC de la máquina remota. Verifique dos veces para asegurarse de que lo siguiente esté configurado correctamente en el BMC de la máquina remota: dirección IP, dirección MAC, máscara de subred, nombre de usuario, habilitación de usuario, privilegio de usuario, contraseña, privilegio LAN, habilitación LAN y tipo(s) de autenticación permitido(s). Para conexiones IPMI 2.0, verifique dos veces para asegurarse de que el(los) privilegio(s) de suite de cifrado y la clave K_g estén configurados correctamente. La herramienta ipmi-config(8) puede ser usada para verificar y/o cambiar estos ajustes de

configuración.

Los problemas de IPMI in-band son típicamente causados por controladores mal configurados o BMCs no

estándar.

Además de los consejos de solución de problemas a continuación, por favor vea SOLUCIONES ALTERNATIVAS más abajo para ver también si hay errores específicos del proveedor que han sido descubiertos y

solucionados.

A continuación se enumeran muchos de los problemas comunes para mensajes de error. Para soporte adicional, por favor envíe un correo electrónico a la lista de correo <freeipmi-users@gnu.org>

.

"username invalid" - El nombre de usuario ingresado (o un nombre de usuario NULO si no se ingresó ninguno) no está disponible en la máquina remota. También es posible que la configuración del nombre de usuario del BMC remoto sea

incorrecta.

"password invalid" - La contraseña ingresada (o una contraseña NULA si no se ingresó ninguna) no es correcta. También es posible que la contraseña para el usuario no esté correctamente configurada en el BMC

remoto.

"password verification timeout" - La verificación de la contraseña ha expirado. Ocurrió un error "password invalid" (descrito arriba) o un "session timeout" genérico (descrito más abajo). Durante este punto del protocolo no se puede diferenciar cuál

ocurrió.

"k_g invalid" - La clave K_g ingresada (o una clave K_g NULA si no se ingresó ninguna) no es correcta. También es posible que la clave K_g no esté correctamente configurada en el BMC

remoto.

"privilege level insufficient" - Un comando IPMI requiere un privilegio de usuario más alto que el con el que se autenticó. Por favor intente autenticar con un privilegio más alto. Esto puede requerir autenticar a un usuario diferente que tenga un privilegio máximo más

alto.

"privilege level cannot be obtained for this user" - El nivel de privilegio con el que intenta autenticar es más alto que el máximo permitido para este usuario. Por favor intente de nuevo con un privilegio más bajo. También es posible que el nivel de privilegio máximo permitido para un usuario no esté correctamente configurado en el BMC

remoto.

"authentication type unavailable for attempted privilege level" - El tipo de autenticación con el que desea autenticar no está disponble para este nivel de privilegio. Por favor, inténtelo de nuevo con un tipo de autenticación alternativo o un nivel de privilegio alternativo. También es posible que los tipos de autenticación disponibles con los que puede autenticar no estén correctamente configurados en el BMC

remoto.

"cipher suite id unavailable" (id de suite de cifrado no disponible) - El id de suite de cifrado con el que desea autenticar no está disponible en el BMC remoto. Por favor, inténtelo de nuevo con un id de suite de cifrado alternativo. También es posible que los ids de suite de cifrado disponibles no estén correctamente configurados en el BMC

remoto.

"ipmi 2.0 unavailable" (ipmi 2.0 no disponible) - No se detectó IPMI 2.0 en la máquina remota. Por favor, intente usar IPMI 1.5 en su

lugar.

"connection timeout" (tiempo de espera de conexión agotado) - La comunicación IPMI inicial falló. Hay varios errores potenciales posibles, incluyendo un nombre de host no válido especificado, una dirección IP de IPMI que no se puede resolver, IPMI no está habilitado en el servidor remoto, la conexión de red es deficiente, etc. Por favor, verifique la configuración y la

conectividad.

"session timeout" (tiempo de espera de sesión agotado) - La sesión IPMI ha agotado su tiempo de espera. Por favor, reconéctese. Si este error ocurre con frecuencia, es posible que desee aumentar el tiempo de espera de retransmisión. Algunos BMCs remotos son considerablemente más lentos que

otros.

"device not found" (dispositivo no encontrado) - No se pudo encontrar el dispositivo especificado. Por favor, verifique la configuración o las entradas e inténtelo de

nuevo.

"driver timeout" (tiempo de espera del controlador agotado) - La comunicación con el controlador o el dispositivo ha agotado su tiempo de espera. Por favor, inténtelo de

nuevo.

"message timeout" (tiempo de espera del mensaje agotado) - La comunicación con el controlador o el dispositivo ha agotado su tiempo de espera. Por favor, inténtelo de

nuevo.

"BMC busy" (BMC ocupado) - El BMC está actualmente ocupado. Puede que esté procesando información o tener demasiadas sesiones simultáneas para gestionar. Por favor, espere e inténtelo de

nuevo.

"could not find inband device" (no se pudo encontrar el dispositivo inband) - No se pudo encontrar un dispositivo inband. Por favor, verifique la configuración o especifique un dispositivo o controlador específico en la línea de

comandos.

"driver timeout" (tiempo de espera del controlador agotado) - El controlador inband ha agotado

su tiempo de espera comunicándose con el BMC o el procesador de servicio local. El BMC o el pr
ocesador de servicio puede estar ocupado o (en el peor de los casos) posiblemente no funcionar.

SOLUCIONES

ALTERNATIVAS

Con tantos proveedores diferentes implementando sus propias soluciones IPMI, diferentes proveedores pueden implementar incorrectamente sus protocolos IPMI. Lo siguiente describe una serie de soluciones alternativas actualmente disponibles para manejar problemas de cumplimiento descubiertos. Cuando sea posible, las soluciones alternativas se han implementado para que sean transparentes para el usuario. Sin embargo, algunas requerirán que el usuario especifique que se use una solución alternativa mediante la opción

-W.

El hardware listado a continuación puede indicar solo el hardware en el que se descubrió un problema. Las versiones más nuevas de hardware pueden corregir los problemas indicados a continuación. Máquinas similares de otros proveedores pueden o no exhibir los mismos problemas. Diferentes proveedores pueden licenciar su firmware del mismo desarrollador de firmware IPMI, por lo que puede valer la pena probar las soluciones alternativas listadas a continuación incluso si su placa base no está

listada.

Si cree que su hardware tiene un problema de cumplimiento adicional que necesita que se implemente una solución alternativa, por favor, contacte a los mantenedores de FreeIPMI en <freeipmi-users@gnu.org> o <freeipmi-devel@gnu.org>

.

assumeio - Este indicador de solución alternativa asumirá que las interfaces inband se comunican con la E/S del sistema en lugar de estar mapeadas en memoria. Esto funcionará en sistemas que reportan direcciones base no válidas. Aquellos que encuentren este problema pueden ver errores "device not supported" (dispositivo no soportado) o "could not find inband device" (no se pudo encontrar el dispositivo inband). Problema observado en HP ProLiant DL145

G1.

spinpoll - Este indicador de solución alternativa informará a algunos controladores inband (el controlador KCS, notablemente) que giren mientras hacen sondeo en lugar de poner el proceso a dormir. Esto puede mejorar significativamente el tiempo de ejecución real de las herramientas porque la granularidad del planificador de un sistema operativo puede ser mucho mayor que el tiempo que lleva realizar una única transacción de mensaje IPMI. Sin embargo, al girar, su sistema puede estar realizando un trabajo menos útil al no cambiar el contexto de la herramienta para una tarea más

útil.

authcap - Este indicador de solución alternativa omitirá las comprobaciones tempranas de capacidades de nombre de usuario, capacidades de autenticación y soporte de K_g, y permitirá que la autenticación IPMI tenga éxito. Funciona en múltiples problemas en los que el sistema remoto no reporta correctamente las capacidades del nombre de usuario, las capacidades de autenticación o el estado de K_g. Aquellos que encuentren este problema pueden ver errores "username invalid" (nombre de usuario no válido), "authentication type unavailable for attempted privilege level" (tipo de autenticación no disponible para el nivel de privilegio intentado) o "k_g invalid" (k_g no válido). Problema observado en Asus P5M2/P5MT-R/RS162-E4/RX4, Intel SR1520ML/X38ML, y Sun Fire 2200/4150/4450 con

ELOM.

nochecksumcheck - Este indicador de solución alternativa le dirá a FreeIPMI que no verifique las sumas de comprobación devueltas por las respuestas de los comandos IPMI. Funciona en sistemas que devuelven sumas de comprobación no válidas debido a errores de implementación, pero el paquete es válido de otro modo. Se advierte a los usuarios sobre el uso de esta opción, ya que elimina la validación de la integridad del paquete en una serie de circunstancias. Sin embargo, es poco probable que sea un problema en la mayoría de las situaciones. Aquellos que encuentren este problema pueden ver errores "connection timeout" (tiempo de espera de conexión agotado), "session timeout" (tiempo de espera de sesión agotado) o "password verification timeout" (tiempo de espera de verificación de contraseña agotado). En conexiones IPMI 1.5, la solución alternativa "noauthcodecheck" también puede ser necesaria. Problema observado en Supermicro X9SCM-iiF, Supermicro X9DRi-F, y Supermicro

X9DRFR.

idzero - Este indicador de solución alternativa permitirá que el cliente acepte IDs de sesión vacíos. Funciona en sesiones IPMI que reportan IDs de sesión vacíos al cliente. Aquellos que encuentren este problema pueden ver errores "session timeout" (tiempo de espera de sesión agotado). Problema observado en Tyan S2882 con BMC

M3289.

unexpectedauth - Este indicador de solución alternativa permitirá que los códigos de autenticación no nulos inesperados se verifiquen como si se esperaran. Funciona en un problema cuando los paquetes contienen datos de autenticación no nulos cuando deberían ser nulos debido a la autenticación por mensaje deshabilitada. Aquellos que encuentren este problema pueden ver errores "session timeout" (tiempo de espera de sesión agotado). Problema observado en Dell PowerEdge 2850, SC1425. Confirmado como corregido en firmware más

nuevo.

forcepermsg - Este indicador de solución alternativa forzará el uso de la autenticación por mensaje sin importar lo que anuncie el sistema remoto. Funciona en un problema cuando la autenticación por mensaje se anuncia como deshabilitada en el sistema remoto, pero en realidad es requerida por el protocolo. Aquellos que encuentren este problema pueden ver errores "session timeout" (tiempo de espera de sesión agotado). Problema observado en IBM eServer

325.

endianseq - Este indicador de solución alternativa invertirá el endian de los números de secuencia de sesión para permitir que la sesión continúe correctamente. Funciona en números de secuencia de sesión IPMI 1.5 que tienen el endian incorrecto. Aquellos que encuentren este problema pueden ver errores "session timeout" (tiempo de espera de sesión agotado). Problema observado en algunos Sun ILOM 1.0/2.0 (depende del endian del procesador de servicio)

.

noauthcodecheck - Este indicador de solución alternativa le dirá a FreeIPMI que no verifique los códigos de autenticación devueltos por las respuestas de los comandos IPMI 1.5. Funciona en sistemas que devuelven códigos de autenticación no válidos debido a errores de hashing o de implementación. Se advierte a los usuarios sobre el uso de esta opción, ya que elimina una verificación de autenticación que valida la integridad de un paquete. Sin embargo, en la mayoría de las organizaciones, es poco probable que sea un problema de seguridad. Aquellos que encuentren este problema pueden ver errores "connection timeout" (tiempo de espera de conexión agotado), "session timeout" (tiempo de espera de sesión agotado) o "password verification timeout" (tiempo de espera de verificación de contraseña agotado). Problema observado en Xyratex FB-H8-SRAY, Intel Windmill, Quanta Winterfell, y Wiwynn

Windmill.

intel20 - Este indicador de solución alternativa funcionará en varios problemas de autenticación IPMI 2.0 de Intel. Los problemas cubiertos incluyen el relleno de nombres de usuario y el truncamiento de contraseñas si el algoritmo de autenticación es HMAC-MD5-128. Aquellos que encuentren este problema pueden ver errores "username invalid" (nombre de usuario no válido), "password invalid" (contraseña no válida) o "k_g invalid" (k_g no válido). Problema observado en Intel SE7520AF2 con Intel Server Management Module (Professional Edition)

.

supermicro20 - Este indicador de solución alternativa funcionará en varios problemas de autenticación IPMI 2.0 de Supermicro en placas base con firmware IPMI de Peppercon. Los problemas cubiertos incluyen el manejo de códigos de autenticación de longitud no válida. Aquellos que encuentren este problema pueden ver errores "password invalid" (contraseña no válida). Problema observado en Supermicro H8QME con tarjeta hija SIMSO. Confirmado como corregido en firmware más

nuevo.

sun20 - Este indicador de solución alternativa funcionará en varios problemas de autenticación IPMI 2.0 de Sun. Los problemas cubiertos incluyen claves hash de longitud no válida, claves hash incorrectamente calculadas y registros de suite de cifrado no válidos. Aquellos que encuentren este problema pueden ver errores "password invalid" (contraseña no válida) o "bmc error" (error de BMC). Problema observado en Sun Fire 4100/4200/4500 con ILOM. Esta solución alternativa incluye automáticamente la solución alternativa

"opensesspriv".

opensesspriv - Este indicador de solución alternativa alterará ligeramente el protocolo de conexión IPMI 2.0 de FreeIPMI para solucionar un algoritmo de hashing no válido utilizado por el sistema remoto. El nivel de privilegio enviado durante la etapa de Apertura de Sesión de una conexión IPMI 2.0 se utiliza para el hashing de claves en lugar del nivel de privilegio enviado durante la etapa de conexión RAKP1. Aquellos que encuentren este problema pueden ver errores "password invalid" (contraseña no válida), "k_g invalid" (k_g no válido), "bad rmcpplus status code" (código de estado rmcpplus incorrecto) o "privilege level cannot be obtained for this user" (no se puede obtener el nivel de privilegio para este usuario). Problema observado en Sun Fire 4100/4200/4500 con ILOM, Inventec 5441/Dell Xanadu II, Supermicro X8DTH, Supermicro X8DTG, Intel S5500WBV/Penguin Relion 700, Intel S2600JF/Appro 512X, Quanta QSSC-S4R/Appro GB812X-CN, Dell C5220, y el software BMC OpenIPMI. Esta solución alternativa se activa automáticamente con la solución alternativa

"sun20".

integritycheckvalue - Este indicador de solución alternativa funcionará en un valor de verificación de integridad no válido durante el establecimiento de una sesión IPMI 2.0 al usar el ID de Suite de Cifrado 0. El valor de verificación de integridad debería tener una longitud de 0, sin embargo, la placa base remota responde con un campo no vacío. Aquellos que encuentren este problema pueden ver errores "k_g invalid" (k_g no válido). Problema observado en Supermicro X8DTG, Supermicro X8DTU, y Intel S5500WBV/Penguin Relion 700, e Intel S2600JF/Appro

512X.

Sin Soporte para IPMI 1.5 - Se ha descubierto que algunas placas base que soportan IPMI 2.0 no soportan IPMI 1.5. Aquellos que encuentren este problema pueden ver errores "ipmi 2.0 unavailable" (ipmi 2.0 no disponible) o "connection timeout" (tiempo de espera de conexión agotado). Este problema se puede solucionar usando IPMI 2.0 en lugar de IPMI 1.5 especificando --driver-type=LAN_2.0. Problema observado en un número de placas base de HP y

Supermicro.

slowcommit - Esta solución alternativa ralentizará las confirmaciones al BMC durmiendo un segundo entre la confirmación de secciones. Funciona en placas base que tienen BMCs que pueden ser abrumados por las confirmaciones. Aquellos que encuentren este problema pueden ver errores de confirmación o confirmaciones que no se escriben en el BMC. Problema observado en Supermicro

H8QME.

NOMBRE

ipmi-config - utilidad para configurar el dispositivo BMC a través de la interfaz IPMI.

SINOPSIS

ipmi-config [-h | --help] [-V | --version]

ipmi-config [-m | --checkout] [-c | --commit] [-d | --diff]

[-f | --filename nombre_archivo] [-a | --category categoría] [-k | --key-pair par_clave]

[-C | --capabilities] [-s | --sdr-cache]

[-H | --hostranged]

[-v | --verbose]

[-I | --interface interfaz]

[-L | --local]

[-r | --remove]

[-D | --debug]

[host ...]

DESCRIPCIÓN

La utilidad ipmi-config se utiliza para obtener y establecer la configuración del dispositivo BMC (Baseboard Management Controller) a través de la interfaz IPMI.

Esta utilidad se puede usar para consultar, confirmar y comparar configuraciones de varios dispositivos BMC.

OPCIONES GENERALES

Las siguientes opciones están disponibles para todas las operaciones de ipmi-config:

-h, --help
Muestra un mensaje de ayuda y sale.
-V, --version
Muestra la información de versión y sale.
-v, --verbose
Habilita la salida detallada.
-D, --debug
Habilita la salida de depuración.
-I, --interface interfaz
Especifica la interfaz IPMI a utilizar (por ejemplo, open, lan, lanplus). El valor predeterminado es lanplus.
-L, --local
Se comunica con el BMC localmente.
-r, --remove
Elimina las entradas del archivo de configuración.
host ...
Una lista de uno o más hosts BMC con los que comunicarse.

IPMI-CONFIG OPCIONES

Las siguientes opciones se utilizan para realizar operaciones en la configuración del BMC:

-m, --checkout
Obtiene la información de configuración del BMC.
-c, --commit
Confirma la información de configuración en el BMC.
-d, --diff
Muestra las diferencias entre la configuración actual y la proporcionada.
-f, --filename nombre_archivo
Especifica el archivo de configuración a utilizar para las operaciones de checkout, commit o diff.
-a, --category categoría
Especifica la categoría de configuración a procesar (por ejemplo, pef, chassis, sensors, sol, all).
-k, --key-pair par_clave
Especifica un par clave-valor para la configuración. El formato es categoría:clave=valor.

OPCIONES DEL CACHÉ SDR

-s, --sdr-cache
Habilita el uso del caché SDR. Esto puede mejorar el rendimiento al recuperar información del SDR.

OPCIONES DE HOSTRANGED

-H, --hostranged
Habilita la funcionalidad de hostranged. Esto permite que ipmi-config se comunique con múltiples hosts utilizando la información de rango de hosts.

USO GENERAL

Para obtener toda la información de configuración del BMC:

# ipmi-config --checkout

Para confirmar toda la información de configuración desde un archivo:

# ipmi-config --commit --filename=config.conf

Para comparar la configuración actual con la de un archivo:

# ipmi-config --diff --filename=config.conf

INFORMACIÓN DE CONFIGURACIÓN ESPECIAL PARA CASOS DE USO DEL NÚCLEO

Algunas configuraciones del núcleo pueden requerir consideraciones especiales:

lan_conf_misc:broadcast_arps
Este par clave-valor controla si el BMC envía ARPs de radiodifusión. Si se establece en 0, el BMC no enviará ARPs de radiodifusión. Esto puede ser útil en redes donde los ARPs de radiodifusión pueden causar problemas.
lan_conf_misc:gratuitous_arp_interval
Este par clave-valor especifica el intervalo en segundos entre los ARPs de radiodifusión. Un valor de 0 deshabilita los ARPs de radiodifusión.

INFORMACIÓN DE CONFIGURACIÓN ESPECIAL PARA CASOS DE USO DEL CHASIS

Las siguientes opciones son específicas de la configuración del chasis:

chassis_power_control:power_state
Controla el estado de energía del chasis. Los valores posibles son on, off, reset.
chassis_power_control:cold_reset_delay
Especifica el retraso en segundos antes de realizar un reinicio en frío.
chassis_power_control:warm_reset_delay
Especifica el retraso en segundos antes de realizar un reinicio en caliente.

INFORMACIÓN DE CONFIGURACIÓN ESPECIAL PARA CASOS DE USO PEF

La siguiente opción es específica de la configuración PEF (Platform Event Filter):

pef_config:alert_immediate_power_off
Si se establece en 1, el BMC apagará inmediatamente el sistema cuando se reciba una alerta PEF.

INFORMACIÓN DE CONFIGURACIÓN ESPECIAL PARA CASOS DE USO DE SENSORES

La siguiente opción es específica de la configuración de sensores:

sensor_config:set_sensor_reading
Permite establecer manualmente la lectura de un sensor. El formato es sensor_number:value.

SOPORTE DE HOSTRANGED

Cuando se utiliza la opción --hostranged, ipmi-config puede comunicarse con múltiples hosts especificados en un archivo de rango de hosts. El formato del archivo de rango de hosts es el siguiente:

host_range_start[-host_range_end][,host_range_start[-host_range_end]]...

Por ejemplo:

192.168.1.100-192.168.1.150,192.168.2.1

SOLUCIÓN DE PROBLEMAS GENERAL

Si encuentra errores al comunicarse con el BMC, asegúrese de que la interfaz IPMI esté habilitada y configurada correctamente. Verifique que las credenciales de inicio de sesión sean correctas y que el host BMC sea accesible.

SOLUCIONES ALTERNATIVAS

Las siguientes soluciones alternativas están disponibles para problemas específicos:

commit_late_device
Este workaround retrasa el commit de todos los comandos hasta después de que el dispositivo sea contactado. Esto puede ayudar a evitar errores de commit en placas base que pueden verse abrumadas por commits.
solchannelassumelanchannel
Este workaround fuerza a ipmi-config a asumir que el canal utilizado para SOL es idéntico al canal utilizado para LAN. Esto puede ayudar con problemas de configuración en placas base donde el canal SOL se informa incorrectamente.

EJEMPLOS

# ipmi-config --checkout

Muestra toda la información de configuración principal en la consola. # ipmi-config --checkout --category=pef

Muestra toda la información de configuración de PEF en la consola. # ipmi-config --checkout --category=pef,chassis

Muestra toda la información de configuración de PEF y chasis en la consola.

# ipmi-config --checkout --filename=bmc-data1.conf

Almacena toda la información de configuración principal en bmc-data1.conf.

# ipmi-config --diff --filename=bmc-data2.conf

Muestra todas las diferencias entre la configuración actual y el archivo bmc-data2.conf.

# ipmi-config --diff --key-pair="lan_conf_misc:gratuitous_arp_interval=8"

Muestra la diferencia entre la configuración actual y el valor de 'lan_conf_misc:gratuitous_arp_interval' de '8'.

# ipmi-config --commit --filename=bmc-data1.conf

Confirma todos los valores de configuración del archivo bmc-data1.conf.

# ipmi-config --commit --key-pair="lan_conf_misc:gratuitous_arp_interval=4"

Confirma la clave 'lan_conf_misc:gratuitous_arp_interval' con el valor '4'.

# ipmi-config --commit --filename=bmc-data-updt.conf --key-pair="lan_conf_misc:gratuitous_arp_interval=4"

Confirma todos los valores de configuración del archivo bmc-data-updt.conf y la clave 'lan_conf_misc:gratuitous_arp_interval' con el valor '4'.

DIAGNÓSTICOS

Al ejecutarse correctamente, el estado de salida es 0. En caso de error no fatal, el estado de salida es 1. En caso de error fatal, el estado de salida es 2.

Si se especifican múltiples hosts para la comunicación, el estado de salida es 0 si y solo si todos los objetivos se ejecutan correctamente. Si ocurre algún error no fatal, el estado de salida es 1. Si ocurre algún error fatal, el estado de salida es 2.

PROBLEMAS CONOCIDOS

En sistemas operativos más antiguos, si introduce su nombre de usuario, contraseña y otra información potencialmente relevante para la seguridad en la línea de comandos, esta información puede ser descubierta por otros usuarios al usar herramientas como el comando ps(1) o al mirar en el sistema de archivos /proc. Generalmente es más seguro introducir la información de contraseña con opciones como las opciones -P o -K. Configurar información relevante para la seguridad en el archivo de configuración FreeIPMI también sería una forma apropiada de ocultar esta información.

Para evitar ataques de fuerza bruta, algunos BMC se "bloquearán" temporalmente después de un número de errores de autenticación remota. Es posible que deba esperar un tiempo para que este "bloqueo" temporal pase antes de poder autenticarse nuevamente.
