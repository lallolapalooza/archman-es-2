ip(7) Manual de Información Diversa ip(7)

NOMBRE

ip - Implementación del protocolo IPv4 en Linux

SINOPSIS

#include <sys/socket.h>
#include <netinet/in.h>
#include <netinet/ip.h>  /* superconjunto de los anteriores */
tcp_socket = socket(AF_INET, SOCK_STREAM, 0);
udp_socket = socket(AF_INET, SOCK_DGRAM, 0);
raw_socket = socket(AF_INET, SOCK_RAW, protocol);

DESCRIPCIÓN

Linux implementa el Protocolo de Internet, versión 4, descrito en RFC 791 y RFC 1122. ip contiene una implementación de multidifusión de nivel 2 conforme a RFC 1112. También contiene un enrutador IP incluyendo un filtro de paquetes.

La interfaz de programación es compatible con los sockets BSD. Para más información sobre sockets, véase socket(7).

Un socket IP se crea usando socket(2):


socket(AF_INET, socket_type, protocol);

Los tipos de socket válidos incluyen SOCK_STREAM para abrir un socket de flujo, SOCK_DGRAM para abrir un socket de datagrama, y SOCK_RAW para abrir un raw(7) socket para acceder al protocolo IP directamente.

protocol es el protocolo IP en la cabecera IP que se va a recibir o enviar. Los valores válidos para protocol incluyen:

•
0 y IPPROTO_TCP para tcp(7) sockets de flujo;
•
0 y IPPROTO_UDP para udp(7) sockets de datagrama;
•
IPPROTO_SCTP para sctp(7) sockets de flujo; y
•
IPPROTO_UDPLITE para udplite(7) sockets de datagrama.

Para SOCK_RAW puede especificar un protocolo IP válido de IANA definido en los números asignados del RFC 1700.

Cuando un proceso quiere recibir nuevos paquetes entrantes o conexiones, debe vincular un socket a una dirección de interfaz local usando bind(2). En este caso, solo un socket IP puede estar vinculado a cualquier par (dirección, puerto) local dado. Cuando INADDR_ANY se especifica en la llamada bind, el socket se vinculará a todas las interfaces locales. Cuando listen(2) se llama en un socket no vinculado, el socket se vincula automáticamente a un puerto libre aleatorio con la dirección local establecida a INADDR_ANY. Cuando connect(2) se llama en un socket no vinculado, el socket se vincula automáticamente a un puerto libre aleatorio o a un puerto compartido utilizable con la dirección local establecida a INADDR_ANY.

Una dirección de socket local TCP que ha sido vinculada no está disponible durante algún tiempo después de cerrarse, a menos que SO_REUSEADDR se haya establecido. Debe tenerse cuidado al usar esta bandera ya que hace que TCP sea menos fiable.

Formato de dirección

Una dirección de socket IP se define como una combinación de una dirección de interfaz IP y un número de puerto de 16 bits. El protocolo IP básico no proporciona números de puerto, estos son implementados por protocolos de nivel superior como udp(7) y tcp(7). En sockets crudos sin_port se establece en el protocolo IP.


struct sockaddr_in {
    sa_family_t    sin_family; /* familia de direcciones: AF_INET */
    in_port_t      sin_port;   /* puerto en orden de bytes de red */
    struct in_addr sin_addr;   /* dirección de internet */
};
/* Dirección de Internet */
struct in_addr {
    uint32_t       s_addr;     /* dirección en orden de bytes de red */
};

sin_family siempre se establece en AF_INET. Esto es obligatorio; en Linux 2.2 la mayoría de las funciones de red devuelven EINVAL cuando esta configuración falta. sin_port contiene el puerto en orden de bytes de red. Los números de puerto por debajo de 1024 se llaman puertos privilegiados (o a veces: puertos reservados). Solo un proceso privilegiado (en Linux: un proceso que tiene la capacidad CAP_NET_BIND_SERVICE en el espacio de nombres de usuario que gobierna su espacio de nombres de red) puede bind(2) a estos sockets. Nótese que el protocolo IPv4 crudo como tal no tiene concepto de puerto, estos son implementados solo por protocolos superiores como tcp(7) y udp(7).

sin_addr es la dirección IP del host. El miembro s_addr de struct in_addr contiene la dirección de interfaz del host en orden de bytes de red. in_addr debería ser asignado uno de los valores INADDR_* (por ejemplo, INADDR_LOOPBACK) usando htonl(3) o establecido usando las funciones de biblioteca inet_aton(3), inet_addr(3), inet_makeaddr(3) o directamente con el resolvedor de nombres (véase gethostbyname(3)).

Las direcciones IPv4 se dividen en direcciones unidifusión, difusión y multidifusión. Las direcciones unidifusión especifican una sola interfaz de un host, las direcciones de difusión especifican todos los hosts en una red, y las direcciones de multidifusión se dirigen a todos los hosts en un grupo de multidifusión. Los datagramas a direcciones de difusión pueden ser enviados o recibidos solo cuando SO_BROADCAST la bandera del socket está establecida. En la implementación actual, los sockets orientados a conexión están permitidos usar solo direcciones unidifusión.

Nótese que la dirección y el puerto siempre se almacenan en orden de bytes de red. En particular, esto significa que necesita llamar a htons(3) en el número que se asigna a un puerto. Todas las funciones de manipulación de dirección/puerto en la biblioteca estándar trabajan en orden de bytes de red.

Direcciones especiales y reservadas

Hay varias direcciones especiales:

INADDR_LOOPBACK (127.0.0.1)
siempre se refiere al host local a través del dispositivo de loopback;
INADDR_ANY (0.0.0.0)
significa cualquier dirección para la vinculación de sockets;
INADDR_BROADCAST (255.255.255.255)
tiene el mismo efecto en bind(2) que INADDR_ANY por razones históricas. Un paquete dirigido a INADDR_BROADCAST a través de un socket que tiene SO_BROADCAST establecido será difundido a todos los hosts en el segmento de red local, siempre que el enlace sea capaz de difusión.
Dirección de número más alto
Dirección de número más bajo
En cualquier subred IP local no punto a punto con un tipo de enlace que soporte difusiones, la dirección de número más alto (por ejemplo, la dirección .255 en una subred con máscara de red 255.255.255.0) se designa como una dirección de difusión. No puede ser asignada útilmente a una interfaz individual, y solo puede ser dirigida con un socket en el que SO_BROADCAST la opción haya sido establecida. Los estándares de Internet han históricamente también reservado la dirección de número más bajo (por ejemplo, la dirección .0 en una subred con máscara de red 255.255.255.0) para difusión, aunque la llaman "obsoleta" para este propósito. (Algunas fuentes también se refieren a esta como la "dirección de red.") Desde Linux 5.14, se trata como una dirección unidifusión ordinaria y puede ser asignada a una interfaz.

Los estándares de Internet han tradicionalmente también reservado varias direcciones para usos particulares, aunque Linux ya no trata algunas de estas de manera especial.

[0.0.0.1, 0.255.255.255]
[240.0.0.0, 255.255.255.254]
Las direcciones en estos rangos (0/8 y 240/4) están reservadas globalmente. Desde Linux 5.3 y Linux 2.6.25, respectivamente, las direcciones 0/8 y 240/4, distintas de INADDR_ANY y INADDR_BROADCAST, se tratan como direcciones unidifusión ordinarias. Los sistemas que siguen los comportamientos tradicionales pueden no interoperar con estas direcciones históricamente reservadas.
[127.0.0.1, 127.255.255.254]
Las direcciones en este rango (127/8) se tratan como direcciones de loopback similares a la dirección de loopback local estandarizada INADDR_LOOPBACK (127.0.0.1);
[224.0.0.0, 239.255.255.255]
Direccsses en este rango (224/4) están dedicadas a su uso en multicast.

Opciones de socket

IP admite algunas opciones de socket específicas del protocolo que pueden establecerse con setsockopt(2) y leerse con getsockopt(2). El nivel de opción de socket para IP es IPPROTO_IP. Un indicador entero booleano es cero cuando es falso, y verdadero en caso contrario.

Cuando se especifica una opción de socket no válida, getsockopt(2) y setsockopt(2) fallan con el error ENOPROTOOPT.

IP_ADD_MEMBERSHIP (desde Linux 1.2)
Únete a un grupo multicast. El argumento es una estructura ip_mreqn .

struct ip_mreqn {
    struct in_addr imr_multiaddr; /* dirección del grupo
                                     multicast IP */
    struct in_addr imr_address;   /* dirección IP de la interfaz
                                     local */
    int            imr_ifindex;   /* índice de la interfaz */
};

imr_multiaddr contiene la dirección del grupo multicast al que la aplicación desea unirse o del que desea salir. Debe ser una dirección multicast válida (o setsockopt(2) falla con el error EINVAL). imr_address es la dirección de la interfaz local con la que el sistema debe unirse al grupo multicast; si es igual a INADDR_ANY, el sistema elige una interfaz apropiada. imr_ifindex es el índice de la interfaz que debe unirse/salir del grupo imr_multiaddr , o 0 para indicar cualquier interfaz.
La estructura ip_mreqn solo está disponible desde Linux 2.2. Por compatibilidad, la antigua estructura ip_mreq (presente desde Linux 1.2) sigue siendo admitida; difiere de ip_mreqn solo en que no incluye el campo imr_ifindex . (El núcleo determina qué estructura se está pasando basándose en el tamaño pasado en optlen.)
IP_ADD_MEMBERSHIP es válido solo para setsockopt(2).
IP_ADD_SOURCE_MEMBERSHIP (desde Linux 2.4.22 / Linux 2.5.68)
Únete a un grupo multicast y permite recibir datos solo de una fuente especificada. El argumento es una estructura ip_mreq_source .

struct ip_mreq_source {
    struct in_addr imr_multiaddr;  /* dirección del grupo
                                      multicast IP */
    struct in_addr imr_interface;  /* dirección IP de la interfaz
                                      local */
    struct in_addr imr_sourceaddr; /* dirección IP de la
                                      fuente multicast */
};

La estructura ip_mreq_source es similar a ip_mreqn descrita en IP_ADD_MEMBERSHIP. El campo imr_multiaddr contiene la dirección del grupo multicast al que la aplicación desea unirse o del que desea salir. El campo imr_interface es la dirección de la interfaz local con la que el sistema debe unirse al grupo multicast. Finalmente, el campo imr_sourceaddr contiene la dirección de la fuente de la que la aplicación desea recibir datos.
Esta opción puede usarse varias veces para permitir recibir datos de más de una fuente.
IP_BIND_ADDRESS_NO_PORT (desde Linux 4.2)
Informa al núcleo que no reserve un puerto efímero al usar bind(2) con un número de puerto de 0. El puerto se elegirá más tarde automáticamente en el momento de connect(2) , de una manera que permite compartir un puerto de origen siempre que la tupla de 4 elementos sea única.
IP_BLOCK_SOURCE (desde Linux 2.4.22 / 2.5.68)
Deja de recibir datos multicast de una fuente específica en un grupo dado. Esto es válido solo después de que la aplicación se haya suscrito al grupo multicast usando IP_ADD_MEMBERSHIP o IP_ADD_SOURCE_MEMBERSHIP.
El argumento es una estructura ip_mreq_source como se describe en IP_ADD_SOURCE_MEMBERSHIP.
IP_DROP_MEMBERSHIP (desde Linux 1.2)
Sal de un grupo multicast. El argumento es una estructura ip_mreqn o ip_mreq similar a IP_ADD_MEMBERSHIP.
IP_DROP_SOURCE_MEMBERSHIP (desde Linux 2.4.22 / 2.5.68)
Sal de un grupo específico de fuente, es decir, deja de recibir datos de un grupo multicast dado que provienen de una fuente dada. Si la aplicación se ha suscrito a múltiples fuentes dentro del mismo grupo, los datos de las fuentes restantes seguirán entregándose. Para dejar de recibir datos de todas las fuentes a la vez, usa IP_DROP_MEMBERSHIP.
El argumento es una estructura ip_mreq_source como se describe en IP_ADD_SOURCE_MEMBERSHIP.
IP_FREEBIND (desde Linux 2.4)
Si está habilitada, esta opción booleana permite vincularse a una dirección IP que es no local o que no existe (aún). Esto permite escuchar en un socket, sin requerir que la interfaz de red subyacente o la dirección IP dinámica especificada estén activas en el momento en que la aplicación intenta vincularse a ella. Esta opción es el equivalente por socket de la ip_nonlocal_bind interfaz /proc descrita más abajo.
IP_HDRINCL (desde Linux 2.0)
Si está habilitada, el usuario proporciona una cabecera IP delante de los datos del usuario. Válido solo para sockets SOCK_RAW ; consulta raw(7) para más información. Cuando este indicador está habilitado, los valores establecidos por IP_OPTIONS, IP_TTLy IP_TOS se ignoran.
IP_LOCAL_PORT_RANGE (desde Linux 6.3)
Establece u obtiene el rango de puertos locales predeterminado por socket. Esta opción puede usarse para restringir el rango global de puertos locales, definido por la ip_local_port_range interfaz /proc descrita más abajo, para un socket dado.
La opción toma un valor uint32_t con los 16 bits altos establecidos en el límite superior del rango, y los 16 bits bajos establecidos en el límite inferior del rango. Los límites del rango son inclusivos. Los valores de 16 bits deben estar en orden de bytes del host.
El límite inferior debe ser menor que el límite superior cuando ambos límites no son cero. De lo contrario, establecer la opción falla con EINVAL.
Si cualquiera de los límites está fuera del rango global de puertos locales, o es cero, entonces ese límite no tiene efecto.
Para restablecer la configuración, pasa cero como límite superior y como límite inferior.
IP_MSFILTER (desde Linux 2.4.22 / 2.5.68)
Esta opción proporciona acceso a la API avanzada de filtrado de estado completo. El argumento es una estructura ip_msfilter .

struct ip_msfilter {
    struct in_addr imsf_multiaddr; /* dirección del grupo
                                      multicast IP */
    struct in_addr imsf_interface; /* dirección IP de la interfaz
                                      local */
    uint32_t       imsf_fmode;     /* modo de filtrado */
    uint32_t       imsf_numsrc;    /* número de fuentes en
                                      el siguiente array */
    struct in_addr imsf_slist[1];  /* array de direcciones
                                      de fuentes */
};

Hay dos macros, MCAST_INCLUDE y MCAST_EXCLUDE, que pueden usarse para especificar el modo de filtrado. Adicionalmente, existe la macro IP_MSFILTER_SIZE(n) para determinar cuánta memoria se necesita para almacenar una estructura ip_msfilter con n fuentes en la lista de fuentes.
Para la descripción completa del filtrado de fuentes multicast, consulta el RFC 3376.
IP_MTU (desde Linux 2.2)
Recupera el MTU de ruta conocido actualmente para el socket actual. Devuelve un entero.
IP_MTU es válido solo para getsockopt(2) y puede emplearse solo cuando el socket ha sido conectado.
IP_MTU_DISCOVER (desde Linux 2.2)
Establece u obtiene la configuración de Descubrimiento de MTU de Ruta para un socket. Cuando está habilitada, Linux realizará el Descubrimiento de MTU de Ruta según lo definido en el RFC 1191 en sockets SOCK_STREAM . Para sockets que no sonSOCK_STREAM , IP_PMTUDISC_DO fuerza que el indicador de no fragmentar se establezca en todos los paquetes salientes. Es responsabilidad del usuario empaquetizar los datos en trozos del tamaño del MTU y realizar las retransmisiones si es necesario. El núcleo rechazará (con EMSGSIZE) los datagramas que sean más grandes que el MTU de ruta conocido. IP_PMTUDISC_WANT fragmentará un datagrama si es necesario según el MTU de ruta, o establecerá el indicador de no fragmentar en caso contrario.
El valor predeterminado a nivel de sistema puede alternarse entre IP_PMTUDISC_WANT y IP_PMTUDISC_DONT escribiendo (valores cero y no cero respectivamente) en el archivo /proc/sys/net/ipv4/ip_no_pmtu_disc .
Valor de descubrimiento de MTU de ruta Significado
IP_PMTUDISC_WANT Usa la configuración por ruta.
IP_PMTUDISC_DONT Nunca haga Descubrimiento de MTU de Ruta.
IP_PMTUDISC_DO Siempre haga Descubrimiento de MTU de Ruta.
IP_PMTUDISC_PROBE Establece DF pero ignora el MTU de Ruta.
Cuando el descubrimiento de PMTU está habilitado, el núcleo mantiene automáticamente un seguimiento del MTU de ruta por host de destino. Cuando se conecta a un par específico con connect(2), el MTU de ruta conocido actualmente puede recuperarse convenientemente usando la opción de socket IP_MTU (por ejemplo, después de que ocurriera un error EMSGSIZE ). El MTU de ruta puede cambiar con el tiempo. Para sockets sin conexión con muchos destinos, el nuevo MTU para un destino dado también puede accederse usando el error cola (ver IP_RECVERR). Se encolará un nuevo error por cada actualización de MTU entrante.
Mientras se está realizando el descubrimiento de MTU, los paquetes iniciales de los sockets de datagramas pueden ser descartados. Las aplicaciones que usan UDP deben ser conscientes de esto y no tenerlo en cuenta para su estrategia de retransmisión de paquetes.
Para iniciar el proceso de descubrimiento de MTU de la ruta en sockets no conectados, es posible comenzar con un tamaño de datagrama grande (cabeceras de hasta 64 kilobytes de longitud) y dejar que se reduzca mediante actualizaciones de la MTU de la ruta.
Para obtener una estimación inicial de la MTU de la ruta, conecte un socket de datagramas a la dirección de destino usando connect(2) y recupere la MTU llamando a getsockopt(2) con la opción IP_MTU .
Es posible implementar el sondeo de MTU RFC 4821 con sockets SOCK_DGRAM o SOCK_RAW estableciendo un valor de IP_PMTUDISC_PROBE (disponible desde Linux 2.6.22). Esto es también particularmente útil para herramientas de diagnóstico como tracepath(8) que desean enviar deliberadamente paquetes de sondeo más grandes que la MTU de la ruta observada.
IP_MULTICAST_ALL (desde Linux 2.6.31)
Esta opción se puede usar para modificar la política de entrega de mensajes multidifusión. El argumento es un entero booleano (por defecto 1). Si se establece a 1, el socket recibirá mensajes de todos los grupos a los que se ha unido globalmente en todo el sistema. De lo contrario, entregará mensajes solo de los grupos a los que se ha unido explícitamente (por ejemplo, a través de la opción IP_ADD_MEMBERSHIP ) en este socket en particular.
IP_MULTICAST_IF (desde Linux 1.2)
Establece el dispositivo local para un socket multidifusión. El argumento para setsockopt(2) es una estructura ip_mreqn o (desde Linux 3.5) ip_mreq similar a IP_ADD_MEMBERSHIP, o una estructura in_addr . (El kernel determina qué estructura se está pasando basándose en el tamaño pasado en optlen.) Para getsockopt(2), el argumento es una estructura in_addr .
IP_MULTICAST_LOOP (desde Linux 1.2)
Establece o lee un argumento entero booleano que determina si los paquetes multidifusión enviados deben ser devueltos en bucle a los sockets locales.
IP_MULTICAST_TTL (desde Linux 1.2)
Establece o lee el valor de tiempo de vida (TTL) de los paquetes multidifusión salientes para este socket. Es muy importante que los paquetes multidifusión establezcan el TTL más pequeño posible. El valor por defecto es 1, lo que significa que los paquetes multidifusión no abandonan la red local a menos que el programa de usuario lo solicite explícitamente. El argumento es un entero.
IP_NODEFRAG (desde Linux 2.6.36)
Si está habilitado (el argumento es distinto de cero), se deshabilita el reensamblado de paquetes salientes en la capa netfilter. El argumento es un entero.
Esta opción es válida solo para sockets SOCK_RAW .
IP_OPTIONS (desde Linux 2.0)
Establece u obtiene las opciones IP que se enviarán con cada paquete de este socket. Los argumentos son un puntero a un búfer de memoria que contiene las opciones y la longitud de la opción. La llamada setsockopt(2) establece las opciones IP asociadas con un socket. El tamaño máximo de opción para IPv4 es 40 bytes. Ver RFC 791 para las opciones permitidas. Cuando el paquete de solicitud de conexión inicial para un socket SOCK_STREAM contiene opciones IP, las opciones IP se establecerán automáticamente a las opciones del paquete inicial con las cabeceras de enrutamiento invertidas. No se permite que los paquetes entrantes cambien las opciones después de que se ha establecido la conexión. El procesamiento de todas las opciones de enrutamiento de origen entrantes está deshabilitado por defecto y se puede habilitar usando la interfaz accept_source_route /proc . Otras opciones como las marcas de tiempo todavía se manejan. Para los sockets de datagramas, las opciones IP solo pueden ser establecidas por el usuario local. Llamar a getsockopt(2) con IP_OPTIONS pone las opciones IP actuales usadas para el envío en el búfer proporcionado.
IP_PASSSEC (desde Linux 2.6.17)
Si IPSEC etiquetado o NetLabel está configurado en los hosts de envío y recepción, esta opción habilita la recepción del contexto de seguridad del socket par en un mensaje auxiliar de tipo SCM_SECURITY recuperado usando recvmsg(2). Esta opción solo está soportada para sockets UDP; para sockets TCP o SCTP, ver la descripción de la opción SO_PEERSEC más abajo.
El valor dado como argumento a setsockopt(2) y devuelto como resultado de getsockopt(2) es un indicador booleano entero.
El contexto de seguridad devuelto en el mensaje auxiliar SCM_SECURITY tiene el mismo formato que el descrito bajo la opción SO_PEERSEC más abajo.
Nota: el reutilizar el tipo de mensaje SCM_SECURITY para la opción de socket IP_PASSSEC fue probablemente un error, ya que otros mensajes de control IP usan su propio esquema de numeración en el espacio de nombres IP y a menudo usan el valor de la opción de socket como el tipo de mensaje. Actualmente no hay conflicto, ya que la opción IP con el mismo valor que SCM_SECURITY es IP_HDRINCL y esta nunca se usa para un tipo de mensaje de control.
IP_PKTINFO (desde Linux 2.2)
Pasa un mensaje auxiliar IP_PKTINFO que contiene una estructura pktinfo que proporciona alguna información sobre el paquete entrante. Esto funciona solo para sockets orientados a datagramas. El argumento es un indicador que le dice al socket si el mensaje IP_PKTINFO debe ser pasado o no. El mensaje en sí solo puede ser enviado/recuperado como un mensaje de control con un paquete usando recvmsg(2) o sendmsg(2).

struct in_pktinfo {
    unsigned int   ipi_ifindex;  /* Índice de la interfaz */
    struct in_addr ipi_spec_dst; /* Dirección local */
    struct in_addr ipi_addr;     /* Dirección de destino
                                    de la cabecera */
};

ipi_ifindex es el índice único de la interfaz en la que se recibió el paquete. ipi_spec_dst es la dirección local del paquete y ipi_addr es la dirección de destino en la cabecera del paquete. Si IP_PKTINFO se pasa a sendmsg(2) y ipi_spec_dst no es cero, entonces se usa como la dirección de origen local para la búsqueda en la tabla de enrutamiento y para configurar las opciones de enrutamiento de origen IP. Cuando ipi_ifindex no es cero, la dirección local primaria de la interfaz especificada por el índice sobrescribe ipi_spec_dst para la búsqueda en la tabla de enrutamiento.
No soportado para sockets SOCK_STREAM .
IP_RECVERR (desde Linux 2.2)
Habilita el paso de mensajes de error extendidos y fiables. Cuando está habilitado en un socket de datagramas, todos los errores generados serán encolados en una cola de errores por socket. Cuando el usuario recibe un error de una operación de socket, los errores pueden ser recibidos llamando a recvmsg(2) con el indicador MSG_ERRQUEUE establecido. La estructura sock_extended_err que describe el error será pasada en un mensaje auxiliar con el tipo IP_RECVERR y el nivel IPPROTO_IP. Esto es útil para el manejo de errores fiables en sockets no conectados. La porción de datos recibidos de la cola de errores contiene el paquete de error.
El mensaje de control IP_RECVERR contiene una estructura sock_extended_err :

#define SO_EE_ORIGIN_NONE    0
#define SO_EE_ORIGIN_LOCAL   1
#define SO_EE_ORIGIN_ICMP    2
#define SO_EE_ORIGIN_ICMP6   3
struct sock_extended_err {
    uint32_t ee_errno;   /* número de error */
    uint8_t  ee_origin;  /* dónde se originó el error */
    uint8_t  ee_type;    /* tipo */
    uint8_t  ee_code;    /* código */
    uint8_t  ee_pad;
    uint32_t ee_info;    /* información adicional */
    uint32_t ee_data;    /* otros datos */
    /* Pueden seguir más datos */
};
struct sockaddr *SO_EE_OFFENDER(struct sock_extended_err *);

ee_errno contiene el número errno del error encolado. ee_origin es el código de origen de dónde se originó el error. Los otros campos son específicos del protocolo. La macro SO_EE_OFFENDER devuelve un puntero a la dirección del objeto de red donde se originó el error dado un puntero al mensaje auxiliar. Si esta dirección no es conocida, el miembro sa_family de sockaddr contiene AF_UNSPEC y los otros campos de sockaddr están indefinidos.
IP usa la estructura sock_extended_err de la siguiente manera: ee_origin se establece a SO_EE_ORIGIN_ICMP para errores recibidos como un paquete ICMP, o SO_EE_ORIGIN_LOCAL para errores generados localmente. Los valores desconocidos deben ser ignorados. ee_type y ee_code se establecen a partir de los campos de tipo y código de la cabecera ICMP. ee_info contiene la MTU descubierta para errores EMSGSIZE . El mensaje también contiene el sockaddr_in del nodo que causó el error, al que se puede acceder con la macro SO_EE_OFFENDER . El campo sin_family de la dirección SO_EE_OFFENDER es AF_UNSPEC cuando la fuente era desconocida. Cuando el error se originó en la red, todas las opciones IP (IP_OPTIONS, IP_TTL, etc.) habilitadas en el socket y contenidas en el paquete de error se pasan como mensajes de control. La carga útil del paquete que causó el error se devuelve como carga útil normal. Nótese que TCP no tiene cola de errores; MSG_ERRQUEUE no está permitido en sockets SOCK_STREAM . IP_RECVERR es válido para TCP, pero todos los errores son devueltos solo por el valor de retorno de la función de socket o por SO_ERROR .
Para sockets crudos, IP_RECVERR habilita el paso de todos los errores ICMP recibidos a la aplicación, de lo contrario los errores solo se reportan en sockets conectados.
Establece o recupera un indicador booleano entero. IP_RECVERR está por defecto deshabilitado.
IP_RECVOPTS (desde Linux 2.2)
Pasa todas las opciones IP entrantes al usuario en un mensaje de control IP_OPTIONS . ThEl encabezado de enrutamiento y otras opciones ya están rellenos para el host local. No es compatible con sockets SOCK_STREAM.
IP_RECVORIGDSTADDR (desde Linux 2.6.29)
Esta opción booleana habilita el mensaje auxiliar IP_ORIGDSTADDR en recvmsg(2), en el que el kernel devuelve la dirección de destino original del datagrama que se está recibiendo. El mensaje auxiliar contiene una struct sockaddr_in. No es compatible con sockets SOCK_STREAM.
IP_RECVTOS (desde Linux 2.2)
Si está habilitado, el mensaje auxiliar IP_TOS se pasa con los paquetes entrantes. Contiene un byte que especifica el campo Tipo de Servicio/Precedencia de la cabecera del paquete. Espera una bandera entera booleana. No es compatible con sockets SOCK_STREAM.
IP_RECVTTL (desde Linux 2.2)
Cuando se establece esta bandera, pasa un mensaje de control IP_TTL con el campo de tiempo de vida del paquete recibido como un entero de 32 bits. No es compatible con sockets SOCK_STREAM.
IP_RETOPTS (desde Linux 2.2)
Idéntica a IP_RECVOPTS, pero devuelve opciones crudas sin procesar con marcas de tiempo y opciones de registro de ruta no rellenas para este salto. No es compatible con sockets SOCK_STREAM.
IP_ROUTER_ALERT (desde Linux 2.2)
Pasa todos los paquetes que se van a reenviar con la opción IP Router Alert establecida en este socket. Válido solo para sockets crudos. Esto es útil, por ejemplo, para demonios RSVP en espacio de usuario. Los paquetes interceptados no son reenviados por el kernel; es responsabilidad del usuario volver a enviarlos. Se ignora la vinculación del socket; dichos paquetes solo se filtran por protocolo. Espera una bandera entera.
IP_TOS (desde Linux 1.0)
Establece o recibe el campo Tipo de Servicio (TOS) que se envía con cada paquete IP originado en este socket. Se utiliza para priorizar paquetes en la red. TOS es un byte. Hay algunas banderas TOS estándar definidas: IPTOS_LOWDELAY para minimizar los retrasos para el tráfico interactivo, IPTOS_THROUGHPUT para optimizar el rendimiento, IPTOS_RELIABILITY para optimizar la fiabilidad, IPTOS_MINCOST debe usarse para "datos de relleno" donde la transmisión lenta no importa. Como máximo se puede especificar uno de estos valores TOS. Otros bits no son válidos y deben limpiarse. Linux envía los datagramas IPTOS_LOWDELAY primero por defecto, pero el comportamiento exacto depende de la disciplina de colas configurada. Algunos niveles de alta prioridad pueden requerir privilegios de superusuario (la capacidad CAP_NET_ADMIN).
IP_TRANSPARENT (desde Linux 2.6.24)
Establecer esta opción booleana habilita el proxy transparente en este socket. Esta opción de socket permite a la aplicación llamante vincularse a una dirección IP no local y operar tanto como cliente como servidor con la dirección extranjera como punto final local. NOTA: esto requiere que el enrutamiento se configure de manera que los paquetes que van a la dirección extranjera se enruten a través del cuadro TProxy (es decir, el sistema que aloja la aplicación que utiliza la opción de socket IP_TRANSPARENT). Habilitar esta opción de socket requiere privilegios de superusuario (la capacidad CAP_NET_ADMIN o CAP_NET_RAW).
La redirección TProxy con el objetivo TPROXY de iptables también requiere que se establezca esta opción en el socket redirigido.
IP_TTL (desde Linux 1.0)
Establece o recupera el campo de tiempo de vida actual que se utiliza en cada paquete enviado desde este socket.
IP_UNBLOCK_SOURCE (desde Linux 2.4.22 / 2.5.68)
Desbloquea una fuente de multidifusión previamente bloqueada. Devuelve EADDRNOTAVAIL cuando la fuente dada no está siendo bloqueada.
El argumento es una estructura ip_mreq_source como se describe en IP_ADD_SOURCE_MEMBERSHIP.
SO_PEERSEC (desde Linux 2.6.17)
Si IPSEC o NetLabel etiquetados están configurados en los hosts de envío y recepción, esta opción de socket de solo lectura devuelve el contexto de seguridad del socket par conectado a este socket. Por defecto, este será el mismo que el contexto de seguridad del proceso que creó el socket par a menos que sea anulado por la política o por un proceso con los permisos requeridos.
El argumento para getsockopt(2) es un puntero a un búfer de la longitud especificada en bytes en el que se copiará la cadena de contexto de seguridad. Si la longitud del búfer es menor que la longitud de la cadena de contexto de seguridad, entonces getsockopt(2) devuelve -1, establece errno a ERANGE y devuelve la longitud requerida a través de optlen. El llamador debe asignar al menos NAME_MAX bytes para el búfer inicialmente, aunque esto no garantiza que sea suficiente. Puede ser necesario redimensionar el búfer a la longitud devuelta y reintentar.
La cadena de contexto de seguridad puede incluir un carácter nulo terminador en la longitud devuelta, pero no está garantizado que lo haga: un contexto de seguridad "foo" podría representarse como {'f','o','o'} de longitud 3 o {'f','o','o','\0'} de longitud 4, que se consideran intercambiables. La cadena es imprimible, no contiene caracteres nulos no terminadores y está en una codificación no especificada (en particular, no se garantiza que sea ASCII o UTF-8).
El uso de esta opción para sockets en la familia de direcciones AF_INET es compatible desde Linux 2.6.17 para sockets TCP, y desde Linux 4.17 para sockets SCTP.
Para SELinux, NetLabel solo transmite la porción MLS del contexto de seguridad del par a través del cable, estableciendo por defecto el resto del contexto de seguridad a los valores definidos en la política para el identificador de seguridad inicial de netmsg (SID). Sin embargo, NetLabel se puede configurar para pasar contextos de seguridad completos en loopback. IPSEC etiquetado siempre pasa contextos de seguridad completos como parte de establecer la asociación de seguridad (SA) y busca basándose en la asociación para cada paquete.

/proc interfaces

El protocolo IP admite un conjunto de interfaces /proc para configurar algunos parámetros globales. Los parámetros se pueden acceder leyendo o escribiendo archivos en el directorio /proc/sys/net/ipv4/. Las interfaces descritas como Booleanas aceptan un valor entero, con un valor distinto de cero ("verdadero") que significa que la opción correspondiente está habilitada, y un valor cero ("falso") que significa que la opción está deshabilitada.

ip_always_defrag (Booleano; desde Linux 2.2.13)
[Nuevo con Linux 2.2.13; en versiones anteriores del kernel esta característica estaba controlada en tiempo de compilación por la opción CONFIG_IP_ALWAYS_DEFRAG; esta opción no está presente en Linux 2.4.x y posteriores]
Cuando esta bandera booleana está habilitada (distinta de 0), los fragmentos entrantes (partes de paquetes IP que surgieron cuando algún host entre el origen y el destino decidió que los paquetes eran demasiado grandes y los cortó en pedazos) se reensamblarán (desfragmentarán) antes de ser procesados, incluso si están a punto de ser reenviados.
Habilítelo solo si ejecuta un firewall que sea el único enlace a su red o un proxy transparente; nunca lo use para un enrutador o host normal. De lo contrario, la comunicación fragmentada puede verse perturbada si los fragmentos viajan a través de diferentes enlaces. La desfragmentación también tiene un alto costo de memoria y tiempo de CPU.
Esto se activa automáticamente cuando se configura el enmascaramiento o el proxy transparente.
ip_autoconfig (desde Linux 2.2 hasta Linux 2.6.17)
No documentado.
ip_default_ttl (entero; por defecto: 64; desde Linux 2.2)
Establece el valor de tiempo de vida por defecto de los paquetes salientes. Esto se puede cambiar por socket con la opción IP_TTL.
ip_dynaddr (Booleano; por defecto: deshabilitado; desde Linux 2.0.31)
Habilita la reescritura dinámica de entradas de dirección de socket y enmascaramiento en cambios de dirección de interfaz. Esto es útil para interfaces dialup con direcciones IP cambiantes. 0 significa sin reescritura, 1 lo habilita y 2 habilita el modo detallado.
ip_forward (Booleano; por defecto: deshabilitado; desde Linux 1.2)
Habilita el reenvío IP con una bandera booleana. El reenvío IP también se puede configurar por interfaz.
ip_local_port_range (desde Linux 2.2)
Este archivo contiene dos enteros que definen el rango de puertos locales por defecto asignados a los sockets que no están explícitamente vinculados a un número de puerto —es decir, el rango utilizado para los puertos efímeros. Un puerto efímero se asigna a un socket en las siguientes circunstancias:
•
el número de puerto en una dirección de socket se especifica como 0 al llamar a bind(2);
•
listen(2) se llama en un socket de flujo que no estaba previamente vinculado;
•
connect(2) se llamó en un socket que no estaba previamente vinculado;
•
sendto(2) se llama en un socket de datagrama que no estaba previamente vinculado.
La asignación de puertos efímeros comienza con el primer número en ip_local_port_range y termina con el segundo número. Si el rango de puertos efímeros se agota, la llamada al sistema correspondiente devuelve un error (pero véase BUGS).
Tenga en cuenta que el rango de puertos en ip_local_port_range no debe entrar en conflicto con los puertos utilizados por el enmascaramiento (aunque el caso se maneja). Además, las elecciones arbitrarias pueden causar problemas con algunos filtros de paquetes de firewall que hacen suposiciones sobre los puertos locales en uso. El primer número debería ser al menos mayor que 1024, o mejor, mayor que 4096, para evitar conflictos con puertos conocidos y para minimi

IP-FIREWALL

El módulo de filtrado de paquetes de Linux (netfilter) puede ser controlado mediante sysfs.

ip_no_pmtu_disc (Boolean; por defecto: deshabilitado; desde Linux 2.2)
Si está habilitado, no realice Path MTU Discovery para sockets TCP por defecto. Path MTU discovery puede fallar si hay firewalls mal configurados (que descartan todos los paquetes ICMP) o interfaces mal configuradas (por ejemplo, un enlace punto a punto donde ambos extremos no coinciden en la MTU) en la ruta. Es mejor arreglar los routers defectuosos en la ruta que desactivar Path MTU Discovery globalmente, ya que no hacerlo incurre en un alto coste para la red.

Si está configurado, permite a los procesos usar bind(2) en direcciones IP no locales, lo cual puede ser muy útil, pero puede romper algunas aplicaciones.
ip6frag_time (entero; por defecto: 30)
Tiempo en segundos para mantener un fragmento IPv6 en memoria.
ip6frag_secret_interval (entero; por defecto: 600)
Intervalo de regeneración (en segundos) del secreto hash (o vida útil del secreto hash) para fragmentos IPv6.
ipfrag_high_thresh (entero)
ipfrag_low_thresh (entero)
Si la cantidad de fragmentos IP en cola alcanza ipfrag_high_thresh, la cola se reduce hasta ipfrag_low_thresh. Contiene un entero con el número de bytes.

ERRORES

EACCES
El usuario intentó ejecutar una operación sin los permisos necesarios. Estos incluyen: enviar un paquete a una dirección de broadcast sin tener la bandera SO_BROADCAST activada; enviar un paquete a través de una ruta prohibida; modificar la configuración del firewall sin privilegios de superusuario (la capacidad CAP_NET_ADMIN); enlazar a un puerto privilegiado sin privilegios de superusuario (la capacidad CAP_NET_BIND_SERVICE).
EADDRINUSE
Se intentó enlazar a una dirección ya en uso.
EADDRNOTAVAIL
Se solicitó una interfaz inexistente o la dirección de origen solicitada no era local.
EAGAIN
La operación en un socket no bloqueante bloquearía.
EALREADY
Una operación de conexión en un socket no bloqueante ya está en progreso.
ECONNABORTED
Una conexión se cerró durante un accept(2).
EHOSTUNREACH
No hay una entrada válida en la tabla de enrutamiento que coincida con la dirección de destino. Este error puede ser causado por un mensaje ICMP de un router remoto o por la tabla de enrutamiento local.
EINVAL
Se pasó un argumento inválido. Para operaciones de envío, esto puede ser causado por enviar a una ruta de agujero negro.
EISCONN
Se llamó a connect(2) en un socket ya conectado.
EMSGSIZE
El datagrama es más grande que una MTU en la ruta y no puede ser fragmentado.
ENOBUFS
ENOMEM
No hay suficiente memoria libre. Esto a menudo significa que la asignación de memoria está limitada por los límites del buffer del socket, no por la memoria del sistema, pero esto no es 100% consistente.
ENOENT
Se llamó a SIOCGSTAMP en un socket donde no llegó ningún paquete.
ENOPKG
Un subsistema del kernel no fue configurado.
ENOPROTOOPT
EOPNOTSUPP
Se pasó una opción de socket inválida.
ENOTCONN
La operación solo está definida en un socket conectado, pero el socket no estaba conectado.
EPERM
El usuario no tiene permiso para establecer alta prioridad, cambiar la configuración o enviar señales al proceso o grupo solicitado.
EPIPE
La conexión se cerró inesperadamente o fue terminada por el otro extremo.
ESOCKTNOSUPPORT
El socket no está configurado o se solicitó un tipo de socket desconocido.

Otros errores pueden ser generados por los protocolos superpuestos; vea tcp(7), raw(7), udp(7), y socket(7).

NOTAS

IP_FREEBIND, IP_MSFILTER, IP_MTU, IP_MTU_DISCOVER, IP_RECVORIGDSTADDR, IP_PASSSEC, IP_PKTINFO, IP_RECVERR, IP_ROUTER_ALERT, y IP_TRANSPARENT son específicos de Linux.

Tenga mucho cuidado con la opción SO_BROADCAST - no tiene privilegios en Linux. Es fácil sobrecargar la red con broadcasts descuidados. Para nuevos protocolos de aplicación, es mejor usar un grupo multicast en lugar de broadcast. Se desaconseja el broadcast. Consulte RFC 6762 para ver un ejemplo de protocolo (mDNS) que utiliza el enfoque multicast más moderno para comunicarse con un grupo abierto de hosts en la red local.

Algunas otras implementaciones de sockets BSD proporcionan las opciones de socket IP_RCVDSTADDR e IP_RECVIF para obtener la dirección de destino y la interfaz de los datagramas recibidos. Linux tiene el más general IP_PKTINFO para la misma tarea.

Algunas implementaciones de sockets BSD también proporcionan una opción IP_RECVTTL, pero se pasa un mensaje auxiliar con el tipo IP_RECVTTL junto con el paquete entrante. Esto es diferente de la opción IP_TTL utilizada en Linux.

El uso del nivel de opción de socket SOL_IP no es portátil; las pilas basadas en BSD usan el nivel IPPROTO_IP.

INADDR_ANY (0.0.0.0) y INADDR_BROADCAST (255.255.255.255) son neutros en cuanto a orden de bytes. Esto significa que htonl(3) no tiene efecto sobre ellos.

Compatibilidad

Para compatibilidad con Linux 2.0, la sintaxis obsoleta socket(AF_INET, SOCK_PACKET, protocol) todavía es soportada para abrir un socket packet(7). Esto está obsoleto y debería ser reemplazado por socket(AF_PACKET, SOCK_RAW, protocol). La principal diferencia es la nueva estructura de direcciones sockaddr_ll para información genérica de capa de enlace en lugar de la antigua sockaddr_pkt.

BUGS

Hay demasiados valores de error inconsistentes.

El error utilizado para diagnosticar el agotamiento del rango de puertos efímeros difiere entre las diversas llamadas al sistema (connect(2), bind(2), listen(2), sendto(2)) que pueden asignar puertos efímeros.

Los ioctls para configurar opciones específicas de interfaz IP y tablas ARP no están descritos.

La recepción de la dirección de destino original con MSG_ERRQUEUE en msg_name por recvmsg(2) no funciona en algunos kernels de Linux 2.2.
