freeipmi_interpret_sensor.con

f - especifica las reglas de
interpretación de sensores

DESCRIPCIÓ

N

El archivo /etc/freeipmi//freeipmi_interpret_sensor.conf define cómo deben interpretarse los sensores IPMI. Los sensores basados en IPMI especifican una serie de estados/umbrales cuando se leen. Basándose en esos estados/umbrales, bibliotecas y herramientas como libfreeipmi(3), libipmimonitoring(3) y ipmi-sensors(8) pueden informar si una lectura de sensor es "buena" o "mala" mediante un informe de un estado NOMINAL, WARNING o

CRITICAL.

Cada uno de los estados enumerados a continuación es (con suerte) lo suficientemente descriptivo como para describir las condiciones de estado que pueden establecerse/desactivarse para cada tipo de sensor. Para obtener información más detallada sobre cada uno de los estados individuales enumerados a continuación, consulte las "Tablas de códigos de sensores y eventos" de la especificación IPMI. Ipmi-sensors(8) se puede utilizar para determinar los tipos de sensores y los estados/umbrales que existen en un sistema, generando una salida muy detallada y viendo qué tipos de eventos de aserción o desaserción son

posibles.

Los valores posibles para todos los estados/umbrales a continuación

son:

Nominal - Señala una lectura Nominal si se activa el

estado/umbral

Warning - Señala una lectura Warning si se activa el

estado/umbral

Critical - Señala una lectura Critical si se activa el

estado/umbral

Actualmente no se admiten todos los tipos de sensores IPMI y tipos de eventos. Si desea que se admitan más, envíe un correo electrónico a la lista de correo de

FreeIPMI.

Los valores predeterminados seleccionados para la activación de estados/umbrales individuales se basan en conjeturas y en el análisis de placas base. Si cree que deberían cambiarse, envíe un correo electrónico a la lista de correo de FreeIPMI para discutir cuáles deberían ser los valores predeterminados

.

La mayoría de las interpretaciones predeterminadas se pueden determinar con bastante facilidad y pueden satisfacer las necesidades de la mayoría de los usuarios. Por ejemplo, una lectura de "Performance_Met" es normalmente mejor que "Performance_Lags". Sin embargo, algunos sensores pueden ser ambiguos y depender completamente del fabricante. Por ejemplo, "State_Asserted" vs. "State_Deasserted" dependen completamente de la interpretación del proveedor. Se recomienda a los usuarios que ajusten las interpretaciones a continuación según las necesidades de sus

máquinas.

Cada grupo de condiciones de estado a continuación incluye una configuración para "No_Event". Esta es la condición bajo la cual no han ocurrido ni se han activado estados/eventos de senso

r. En la mayoría de las condiciones, se prefiere una asignación a "Nominal". Sin embargo, en algunas circunstancias, puede ser útil informar otra cosa. Por ejemplo, si un sensor en u
na placa base en particular está obligado a informar un estado/evento, una condición de "sin estado de sensor" podría indicar un sensor roto. Esto depende en gran medida de la placa base.

FORMAT

O

Las opciones de configuración que se pueden especificar en el archivo de configuración se enumeran a continuación. Cada opción de configuración debe figurar en

una línea separada. Los argumentos de una opción se separan por cualquier cantidad de espacios en blanco. Los argumentos múltiples también se separan por espacio
s en blanco. Los comentarios se pueden marcar usando el signo de número ("#"), y las líneas se pueden continuar en la siguiente usando la barra invertida ("\").

Las siguientes opciones de configuración se pueden utilizar para configurar interpretaciones específicas de OEM. Los usuarios deben tener en cuenta que tanto IPMI_OEM_Bitmask como IPMI_OEM_Value se pueden configurar para una combinación idéntica de Manufacturer-ID, Product-ID, Event-Reading-Type-Code, y Sensor-Type. Se recorren todas las reglas de interpretación para una combinación específica y se devuelve el estado de sensor resultante peor (es decir, Advertencia < Nominal, Crítico < Advertencia). Si no se encuentra ninguna coincidencia, no se devuelve ningún estado de sensor para la lectura del sensor OEM. Para cada una de las opciones de configuración siguientes, <Manufacturer-ID> es el ID numérico de fabricante IANA para el fabricante en cuestión. El <Product-ID> es uno o más IDs numéricos que representan el producto del fabricante. El <Product-ID> se puede listar como un número numérico único (por ejemplo, 1234), un rango de IDs separados por un guion (por ejemplo, 12-20), o una lista de IDs de producto específicos separados por un signo más (por ejemplo, 12+19+22). Tanto el Manufacturer-ID como el Product-ID se pueden encontrar usando bmc-info(8). Se pueden introducir múltiples pares de <Manufactu

<Product-ID> separados por comas. El Event-Reading-Type-Code y elSensor-Type no necesitan ser tipos OEM.
