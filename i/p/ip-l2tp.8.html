L2TPv3 es adecuado para el túnel de capa 2. Los túneles estáticos son útiles

para

establecer enlaces de red a través de redes IP cuando los túneles son fijos. Los túneles L2TPv3 pueden transportar datos de más de una sesión. Cada sesión se identifica mediante un session_id y el tunnel_id del túnel principal. Se debe crear un túnel antes de poder crear una sesión en el túnel. Al crear un túnel L2TP, se especifica la dirección IP del par remoto,

que

puede ser una dirección IPv4 o IPv6. También se debe especificar la dirección IP local que se utilizará para alcanzar al par. Esta es la dirección en la que el sistema local escuchará y aceptará los paquetes de datos L2TP recibidos del par. L2TPv3 define dos formatos de encapsulación de paquetes: UDP o IP. La encapsulación UDP

es

la más común. La encapsulación IP utiliza un valor de protocolo IP dedicado para transportar datos L2TP sin la sobrecarga de UDP. Utilice la encapsulación IP solo cuando no haya dispositivos NAT ni cortafuegos en la ruta de red. Cuando se crea una sesión de Ethernet L2TPv3, se crea una interfaz de

red

virtual para la sesión, que debe configurarse y activarse, al igual que cualquier otra interfaz de red. Cuando se pasan datos a través de la interfaz, se transportan a través del túnel L2TP hasta el par. Al configurar las tablas de enrutamiento del sistema o añadir la interfaz a un puente, la interfaz L2TP es como un cable virtual (pseudocable) conectado al par. Establecer un pseudocable de Ethernet L2TPv3 no gestionado implica crear manualmente contextos

L2TP

en el sistema local y en el par. Los parámetros utilizados en cada sitio deben corresponder, de lo contrario no se transportarán datos. No es posible realizar comprobaciones de consistencia, ya que no se utiliza ningún protocolo de control para establecer túneles L2TP no gestionados. Una vez que la interfaz de red virtual de una sesión L2TP determinada está configurada y habilitada, se pueden transmitir datos, incluso si el par aún no está configurado. Si el par no está configurado, los paquetes de datos L2TP serán descartados por el par. Para establecer un túnel L2TP no

gestionado,

utilice l2tp add tunnel y l2tp add session descritos en este documento. Luego, configure y habilite la interfaz de red virtual del túnel, según sea necesario. Tenga en cuenta que los túneles no

gestionados

transportan solo tramas Ethernet. Si necesita transportar tráfico PPP (L2TPv2) o su par no admite túneles L2TPv3 no gestionados, necesitará un servidor L2TP que implemente el protocolo de control L2TP. Configuración como interfaces en

puente

Para transportar datos no IP, la interfaz de red L2TP se añade a un puente en lugar de asignarle su propia dirección IP, utilizando las utilidades estándar de Linux. Dado que se transportan tramas Ethernet sin encapsular dentro del túnel, el MTU de las interfaces L2TP debe establecerse para dejar espacio para esas

cabeceras. 
site-A:# ip link set l2tpeth0 up mtu 1446
site-A:# ip link add br0 type bridge
site-A:# ip link set l2tpeth0 master br0
site-A:# ip link set eth0 master br0
site-A:# ip link set br0
up

Si está utilizando VLANs, configure un puente por VLAN y ponga cada VLAN en puente sobre una sesión L2TP separada. Por ejemplo, para poner en puente el ID de VLAN 5 en eth1 sobre un pseudocircuito

L2TP: 
site-A:# ip link set l2tpeth0 up mtu 1446
site-A:# ip link add brvlan5 type bridge
site-A:# ip link set l2tpeth0.5 master brvlan5
site-A:# ip link set eth1.5 master brvlan5
site-A:# ip link set brvlan5
up

Añadir la interfaz L2TP a un puente hace que el puente reenvíe tráfico por el pseudocircuito L2TP igual que reenvía por cualquier otra interfaz. El puente aprende las direcciones MAC de los hosts conectados a cada interfaz y reenvía las tramas de forma inteligente de un puerto del puente a otro. No se asignan direcciones IP a las interfaces l2tpethN. Si el puente está correctamente configurado en ambos lados del pseudocircuito L2TP, debería ser posible alcanzar hosts en la red en puente del extremo

remoto.

Cuando se ponen en puente tramas Ethernet sin encapsular a través de un túnel L2TP, las tramas grandes pueden fragmentarse y reenviarse como fragmentos IP individuales al destinatario, dependiendo del MTU de la interfaz física utilizada por el túnel. Cuando las tramas Ethernet transportan protocolos que son reensamblados por el destinatario, como IP, esto no es un problema. Sin embargo, dicha fragmentación puede causar problemas para protocolos como PPPoE, donde el destinatario espera recibir tramas Ethernet exactamente como se transmitieron. En tales casos, es importante que las tramas que salen del túnel se reensamblen en una sola trama antes de ser reenviadas. Para ello, active el seguimiento de conexiones de netfilter (conntrack) o cargue manualmente los módulos de desfragmentación de netfilter de Linux en cada extremo del

túnel. 
site-A:# modprobe nf_defrag_ipv4
site-B:# modprobe
nf_defrag_ipv4

Si se está utilizand

o L2TP sobre IPv6,
use el módulo de de

INTEROPERABILIDA

D

Los túneles L2TPv3 no gestionados (estáticos) son soportados por algunos proveedores de equipos de red como

Cisco.

En Linux, los mensajes Hello de L2TP no están soportados en túneles no gestionados. Los mensajes Hello son utilizados por los clientes y servidores L2TP para detectar fallos de enlace con el fin de automatizar el desmantelamiento y el restablecimiento de túneles dinámicos. Si un extremo remoto no-Linux soporta los mensajes Hello en túneles no gestionados, debe desactivarse para interoperar con

Linux.

Linux usa por defecto el tipo Default Layer2SpecificHeader tal como se define en la especificación del pro

tocolo L2TPv3, RFC3931. Este ajuste debe ser consistente con el configurado en el extremo remoto. Algunas
implementaciones de proveedores (por ejemplo, Cisco) usan por defecto un tipo de Layer2SpecificHeader de None.
