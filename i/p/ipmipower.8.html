DESCRIPCIÓ

N

Ipmipower permite a los usuarios encender, apagar, reciclar, reiniciar de forma forzada, obtener una consulta de estado de energía, realizar una interrupción de diagnóstico por pulso, o iniciar un apagado suave del sistema operativo a través de ACPI mediante el protocolo IPMI sobre

LAN.

Cuando se especifica un comando de energía (--on, --off, --cycle, --reset, --stat, --pulse, o --soft) en la línea de comandos, Ipmipower intentará ejecutar el comando de energía en todos los nombres de host listados en la línea de comandos y luego

saldrá.

Si no se especifican comandos de energía en la línea de comandos, ipmipower se ejecutará en modo interactivo. El modo interactivo proporciona al usuario una interfaz de línea de comandos para introducir varios comandos. Los detalles de la interfaz de línea de comandos interactiva se pueden encontrar más abajo en COMANDOS

INTERACTIVOS.

A continuación se enumeran las opciones generales de IPMI, las opciones específicas de la herramienta, información de solución de problemas, información de soluciones alternativas, ejemplos y problemas conocidos. Para una introducción general a FreeIPMI, consulte free

ipmi
(7).

Las siguientes opciones se utilizan para cambiar el comportamiento de red de ipmipower

--retransmission-wait-timeout=MILLISECON
DS
Especifica la longitud del tiempo de espera de retransmisión en milisegundos. El tiempo de espera de retransmisión es similar al tiempo de espera de retransmisión anterior, pero se usa específicamente para la verificación de la finalización de la energía con las opciones --wait-until-on y --wait-until-off. El valor predeterminado es 500 milisegundos (0.5 segundos)

--retransmission-backoff-count=COU
NT
Especifica el recuento de retroceso de retransmisión para las retransmisiones. Después de cada COUNT retransmisiones, la longitud del tiempo de espera de retransmisión se incrementará por otro factor. El valor predeterminado
es 8.
--ping-interval=MILLISECON
DS
Especifica la longitud del intervalo de ping en milisegundos. Cuando se ejecuta en modo interactivo, los mensajes de descubrimiento de RMCP (Remote Management Control Protocol) se enviarán a todos los hosts remotos configurados cada MILLISECONDS para confirmar su soporte de IPMI. No se pueden enviar comandos de energía a un host hasta que sea descubierto (o redescubierto si se perdió previamente). El valor predeterminado es 5000 milisegundos (5 segundos). Los mensajes de descubrimiento de ping se pueden deshabilitar estableciendo este valor en 0. Los mensajes de descubrimiento de ping RMCP se deshabilitan automáticamente en modo no
interactivo.
--ping-timeout=MILLISECON
DS
Especifica la longitud del tiempo de espera de ping en milisegundos. Cuando se ejecuta en modo interactivo, los mensajes de descubrimiento de RMCP (Remote Management Control Protocol) se enviarán a todos los hosts remotos configurados para confirmar su soporte de IPMI. Un host remoto se considera no descubierto si el host no responde en el tiempo MILLISECONDS. El valor predeterminado es 30000 milisegundos (30 segundos). El tiempo de espera de ping no puede ser mayor que el intervalo de
ping.
--ping-packet-count=COU
NT
Especifica el tamaño del recuento de paquetes de ping. El valor predeterminado es 10. Consulte la opción --ping-percent a continuación para obtener más información sobre esta opció
n.
--ping-percent=PERCE
NT
Especifica el valor del porcentaje de ping. El valor predeterminado es 50. Dado que IPMI se basa en UDP, es difícil para ipmipower distinguir entre una máquina que falta y una conexión de red deficiente (o muy cargada) en modo interactivo. Por ejemplo, suponga que un enlace descarta consistentemente el 80% de los paquetes a una máquina en particular. La operación de control de energía puede tener dificultades para completarse, aunque una respuesta pong reciente de RMCP hace que ipmipower crea que la máquina está encendida y funcionando correctamente. Las opciones de recuento y porcentaje de paquetes de ping se utilizan para aliviar este problema. Ipmipower monitoreará los paquetes de ping RMCP en fragmentos de recuento de paquetes. Si ipmipower no recibe una respuesta a más del porcentaje de ping de esos paquetes, ipmipower asumirá que el enlace a este nodo es deficiente y no enviará operaciones de control de energía a ese nodo hasta que se determine que la conexión es confiable. Esta heurística se puede deshabilitar estableciendo el recuento de paquetes de ping o el porcentaje de ping en 0. Esta función no se usa si el intervalo de ping está establecido en
0.
--ping-consec-count=COU
NT
Especifica el recuento consecutivo de ping. Esta es otra heurística utilizada para determinar si un nodo debe considerarse descubierto, no de
scubierto o con una conexión deficiente. Si se recibió una respuesta pong RMCP válida para los últimos COUNT paquetes de ping, un nodo se con
siderará descubierto, independientemente de otras heurísticas enumeradas anteriormente. El valor predeterminado es 5. Esta heurística se pued
e deshabilitar estableciendo este valor en 0. Esta función no se usa si otras funciones de ping descritas anteriormente están deshabilitadas.

EXTENSIONES DE ENERGÍA

OEM

Algunas placas base incluyen extensiones OEM de IPMI para mecanismos alternativos de control de energía. Por ejemplo, estos mecanismos de control de energía pueden permitirle controlar la energía de un subdispositivo dentro del sistema en lugar del sistema

completo.

Al especificar un tipo de energía OEM mediante --oem-power-type en la línea de comandos o en el archivo freeipmi.conf(5), puede indicar a ipmipower que ejecute implementaciones alternativas de control de energía en lugar de las estándar. Dependiendo de la extensión OEM, algunos comandos de control de energía pueden dejar de estar disponibles. Por ejemplo, una extensión OEM puede permitir on pero no cycle. Algunas opciones de ipmipower pueden dejar de funcionar

también.

Algunas extensiones OEM pueden requerir argumentos adicionales para su acción de control de energía, como un identificador de subdispositivo. Los argumentos adicionales se pueden proporcionar añadiendo un signo más ('+') y la información extra al final del nombre de host. Esto se puede hacer en la línea de comandos o en el modo interactivo. Por ejemplo, el nombre de host mynode+18 indicaría que la operación de control de energía debe enviarse al host mynode, y 18 es el identificador de un posible subdispositivo a controlar. La opción --consolidate-output se desactiva comúnmente al usar un control de energía OEM que requiere argumentos

extra.

Debido a que el control de energía OEM puede involucrar subtipos, es posible que un usuario desee controlar la energía de múltiples subdispositivos en el mismo host. Por ejemplo, podría especificar los hosts mynode+1,mynode+2, indicando controlar la energía de los subdispositivos 1 y 2 en mynode. Como muchos BMC no pueden manejar múltiples sesiones IPMI, las operaciones de control de energía para el mismo host se serializarán internamente por ipmipower

.

A continuación se listan los tipos de energía OEM disponibles actualmente, junto con información sobre los sistemas con los que funcionan y las operaciones de control de energía

disponibles.
C41
0X
Este tipo de energía OEM soporta el control de energía de ranuras PCIe en sistemas Dell Poweredge C410x. Soporta on, off y stat. El número de ranura PCIe va del 1 al 16 y siempre debe especificarse al intentar controlar la energía con esta extensión. Por ejemplo, el nombre de host mynode+2 informaría a ipmipower para operar en el número de ranura 2 en mynode. Parece que el C410x tiene dificultad para manejar nuevas solicitudes de control de energía de ranura hasta que las anteriores hayan completado. Los usuarios podrían considerar seriamente usar las opciones --wait-until-on y --wait-until-off si se van a controlar múltiples ranuras en rápida
sucesión.

SOPORTE DE MÚLTIPLES

HOSTS

Se pueden introducir múltiples hosts ya sea como listas explícitas de hosts separadas por comas o como un rango de nombres de host en la forma general: prefijo[n-m,l-k,...], donde n < m y l < k, etc. La última forma no debe confundirse con las clases de caracteres de expresiones regulares (también denotadas por []). Por ejemplo, foo[19] no representa foo1 o foo9, sino que representa un rango degenerado:

foo19.

La sintaxis de rango está pensada solo como una conveniencia en clústeres con una convención de nombres prefijoNN, y la especificación de rangos no debe considerarse necesaria -- la lista foo1,foo9 podría especificarse como tal, o por el rango foo[1,9]

.

A continuación se muestran algunos ejemplos de uso de

rangos: 
    foo[01-05] en lugar de foo01,foo02,foo03,foo04,foo05
    foo[7,9-10] en lugar de foo7,foo9,foo10
    foo[0-3] en lugar de foo0,foo1,foo2,
foo3

Como recordatorio para el lector, algunos shells interpretarán los corchetes ([ y ]) para el emparejamiento de patrones. Dependiendo de su shell, puede ser necesario encerrar las listas de rangos entre

comillas.

Cuando el usuario especifica múltiples hosts, se creará un socket para cada host y se consultará, permitiendo efectivamente la comunicación con todos los hosts en paralelo. Esto permitirá la comunicación con un gran número de nodos mucho más rápidamente que si se hiciera en serie. La opción -F puede configurar el número de nodos con los que se puede comunicar en paralelo al mismo

tiempo.

Por defecto, la salida estándar de cada nodo especificado se mostrará con el nombre de host antepuesto a cada línea. Aunque esta salida es legible en muchas situaciones, puede ser difícil de leer en otras situaciones. Por ejemplo, la salida de múltiples nodos puede mezclarse. Las opciones -B y -C se pueden usar para cambiar e

ste comportamie
nto por defecto.

SOLUCIÓN DE PROBLEMAS

GENERAL

La mayoría de las veces, los problemas de IPMI se deben a problemas de

configuración.

Los problemas de IPMI sobre LAN involucran una mala configuración del BMC de la máquina remota. Verifique dos veces que lo siguiente esté configurado correctamente en el BMC de la máquina remota: dirección IP, dirección MAC, máscara de subred, nombre de usuario, habilitación de usuario, privilegio de usuario, contraseña, privilegio LAN, habilitación LAN y tipo(s) de autenticación permitido(s). Para conexiones IPMI 2.0, verifique dos veces que el(los) privilegio(s) de suite de cifrado y la clave K_g estén configurados correctamente. La herramienta ipmi-config(8) se puede usar para verificar y/o cambiar estos ajustes de

configuración.

Además de los consejos de solución de problemas a continuación, consulte SOLUCIONES ALTERNATIVAS más abajo para ver si se han descubierto y solucionado errores específicos de algún

proveedor.

A continuación se listan muchos de los problemas comunes para los mensajes de error. Para soporte adicional, por favor envíe un correo a la lista de correo <freeipmi-users@gnu.org>

.

"username invalid" - El nombre de usuario introducido (o un nombre de usuario NULL si no se introdujo ninguno) no está disponible en la máquina remota. También es posible que la configuración del nombre de usuario del BMC remoto sea

incorrecta.

"password invalid" - La contraseña introducida (o una contraseña NULL si no se introdujo ninguna) no es correcta. También es posible que la contraseña del usuario no esté configurada correctamente en el BMC

remoto.

"password verification timeout" - La verificación de la contraseña ha expirado. Ocurrió un error "password invalid" (descrito arriba) o un "session timeout" genérico (descrito más abajo). En este punto del protocolo no se puede diferenciar cuál

ocurrió.

"k_g invalid" - La clave K_g introducida (o una clave K_g NULL si no se introdujo ninguna) no es correcta. También es posible que la clave K_g no esté configurada correctamente en el BMC

remoto.

"privilege level insufficient" - Un comando IPMI requiere un privilegio de usuario más alto que el con el que se autenticó. Por favor, intente autenticar con un privilegio más alto. Esto puede requerir autenticar a un usuario diferente.er que tiene un privilegio máximo más

alto.

"privilege level cannot be obtained for this user" - El nivel de privilegio con el que intenta autenticarse es superior al máximo permitido para este usuario. Inténtelo de nuevo con un privilegio más bajo. También es posible que el nivel de privilegio máximo permitido para un usuario no esté configurado correctamente en el BMC

remoto.

"authentication type unavailable for attempted privilege level" - El tipo de autenticación con el que desea autenticarse no está disponible para este nivel de privilegio. Inténtelo de nuevo con un tipo de autenticación alternativo o un nivel de privilegio alternativo. También es posible que los tipos de autenticación disponibles con los que puede autenticarse no estén configurados correctamente en el BMC

remoto.

"cipher suite id unavailable" - El id de suite de cifrado con el que desea autenticarse no está disponible en el BMC remoto. Inténtelo de nuevo con un id de suite de cifrado alternativo. También es posible que los ids de suite de cifrado disponibles no estén configurados correctamente en el BMC

remoto.

"ipmi 2.0 unavailable" - No se detectó IPMI 2.0 en la máquina remota. Intente usar IPMI 1.5 en su

lugar.

"connection timeout" - La comunicación IPMI inicial falló. Pueden existir varios errores potenciales, incluyendo un nombre de host especificado no válido, una dirección IP de IPMI que no se puede resolver, IPMI no está habilitado en el servidor remoto, la conexión de red es deficiente, etc. Por favor, verifique la configuración y la

conectividad.

"session timeout" - La sesión IPMI ha expirado. Por favor, reconéctese. Si este error ocurre con frecuencia, es posible que desee aumentar el tiempo de espera de retransmisión. Algunos BMC remotos son considerablemente más lentos que

otros.

"internal IPMI error" - Ha ocurrido un error de IPMI que Fre

eIPMI no sabe cómo manejar. Por favor, envíe un correo electr
ónico a <freeipmi-users@gnu.org> para informar del problema.

SOLUCIÓN DE PROBLEMAS DE

IPMIPOWER

Al encender una máquina apagada, el cliente debe tener un medio para resolver la dirección MAC de la tarjeta de ethernet de la máquina remota. Aunque la mayoría de las soluciones IPMI modernas admiten la capacidad de hacer ARP y resolver direcciones cuando la máquina está apagada, algunas máquinas más antiguas no lo hacen. Esto se resuelve típicamente de una de dos

maneras:

1) Habilitar ARPs gratuitos en la máquina remota. La máquina remota enviará un ARP gratuito, que anuncia la dirección IP y MAC de la ethernet para que otras máquinas en la red almacenen esta información en su caché ARP local. Para grandes clústeres, este método no se recomienda, ya que los ARPs gratuitos pueden inundar la red con tráfico

innecesario.

2) Almacenar permanentemente la dirección MAC de la máquina remota en la caché ARP local. Este es el enfoque más común en grandes

clústeres.

Otros métodos se e

numeran en la espec
ificación de IPMI.

SOLUCIONES

ALTERNATIVAS

Con tantos proveedores diferentes implementando sus propias soluciones IPMI, diferentes proveedores pueden implementar sus protocolos IPMI incorrectamente. Lo siguiente describe una serie de soluciones alternativas actualmente disponibles para manejar problemas de cumplimiento descubiertos. Cuando es posible, las soluciones alternativas se han implementado para que sean transparentes para el usuario. Sin embargo, algunas requerirán que el usuario especifique que se use una solución alternativa mediante la opción

-W.

El hardware listado a continuación puede indicar solo el hardware en el que se descubrió un problema. Las versiones más nuevas de hardware pueden corregir los problemas indicados a continuación. Máquinas similares de otros proveedores pueden o no exhibir los mismos problemas. Diferentes proveedores pueden licenciar su firmware del mismo desarrollador de firmware IPMI, por lo que puede valer la pena probar las soluciones alternativas listadas a continuación incluso si su placa base no está

listada.

Si cree que su hardware tiene un problema de cumplimiento adicional que necesita que se implemente una solución alternativa, por favor, contacte a los mantenedores de FreeIPMI en <freeipmi-users@gnu.org> o <freeipmi-devel@gnu.org>

.

authcap - Esta opción de solución alternativa omitirá las verificaciones iniciales de capacidades de nombre de usuario, capacidades de autenticación y soporte de K_g, y permitirá que la autenticación IPMI tenga éxito. Soluciona múltiples problemas en los que el sistema remoto no informa correctamente las capacidades de nombre de usuario, las capacidades de autenticación o el estado de K_g. Aquellos que encuentren este problema pueden ver errores "username invalid", "authentication type unavailable for attempted privilege level" o "k_g invalid". Problema observado en Asus P5M2/P5MT-R/RS162-E4/RX4, Intel SR1520ML/X38ML y Sun Fire 2200/4150/4450 con

ELOM.

nochecksumcheck - Esta opción de solución alternativa le dirá a FreeIPMI que no verifique las sumas de verificación devueltas por las respuestas de los comandos IPMI. Soluciona sistemas que devuelven sumas de verificación no válidas debido a errores de implementación, pero el paquete es de otro modo válido. Se advierte a los usuarios sobre el uso de esta opción, ya que elimina la validación de la integridad del paquete en una serie de circunstancias. Sin embargo, es improbable que sea un problema en la mayoría de las situaciones. Aquellos que encuentren este problema pueden ver errores "connection timeout", "session timeout" o "password verification timeout". En conexiones IPMI 1.5, la solución alternativa "noauthcodecheck" también puede ser necesaria. Problema observado en Supermicro X9SCM-iiF, Supermicro X9DRi-F y Supermicro

X9DRFR.

idzero - Esta opción de solución alternativa permitirá que el cliente acepte IDs de sesión vacíos. Soluciona sesiones IPMI que informan IDs de sesión vacíos al cliente. Aquellos que encuentren este problema pueden ver errores "session timeout". Problema observado en Tyan S2882 con BMC

M3289.

unexpectedauth - Esta opción de solución alternativa permitirá que los códigos de autenticación no nulos inesperados se verifiquen como si se esperaran. Soluciona un problema cuando los paquetes contienen datos de autenticación no nulos cuando deberían ser nulos debido a la autenticación por mensaje deshabilitada. Aquellos que encuentren este problema pueden ver errores "session timeout". Problema observado en Dell PowerEdge 2850, SC1425. Confirmado como corregido en firmware más

nuevo.

forcepermsg - Esta opción de solución alternativa forzará el uso de la autenticación por mensaje sin importar lo que anuncie el sistema remoto. Soluciona un problema cuando la autenticación por mensaje está anunciada como deshabilitada en el sistema remoto, pero en realidad es requerida por el protocolo. Aquellos que encuentren este problema pueden ver errores "session timeout". Problema observado en IBM eServer

325.

endianseq - Esta opción de solución alternativa invertirá el orden de bytes de los números de secuencia de sesión para permitir que la sesión continúe correctamente. Soluciona números de secuencia de sesión IPMI 1.5 con el orden de bytes incorrecto. Aquellos que encuentren este problema pueden ver errores "session timeout". Problema observado en algunos Sun ILOM 1.0/2.0 (depende del orden de bytes del procesador de servicio)

.

noauthcodecheck - Esta opción de solución alternativa le dirá a FreeIPMI que no verifique los códigos de autenticación devueltos por las respuestas de los comandos IPMI 1.5. Soluciona sistemas que devuelven códigos de autenticación no válidos debido a errores de hashing o implementación. Se advierte a los usuarios sobre el uso de esta opción, ya que elimina una verificación de autenticación que valida la integridad de un paquete. Sin embargo, en la mayoría de las organizaciones, es improbable que sea un problema de seguridad. Aquellos que encuentren este problema pueden ver errores "connection timeout", "session timeout" o "password verification timeout". Problema observado en Xyratex FB-H8-SRAY, Intel Windmill, Quanta Winterfell y Wiwynn

Windmill.

intel20 - Esta opción de solución alternativa solucionará varios problemas de autenticación IPMI 2.0 de Intel. Los problemas cubiertos incluyen el relleno de nombres de usuario y el truncamiento de contraseñas si el algoritmo de autenticación es HMAC-MD5-128. Aquellos que encuentren este problema pueden ver errores "username invalid", "password invalid" o "k_g invalid". Problema observado en Intel SE7520AF2 con Intel Server Management Module (Professional Edition)

.

supermicro20 - Esta opción de solución alternativa solucionará varios problemas de autenticación IPMI 2.0 de Supermicro en placas base con firmware IPMI de Peppercon. Los problemas cubiertos incluyen el manejo de códigos de autenticación de longitud no válida. Aquellos que encuentren este problema pueden ver errores "password invalid". Problema observado en Supermicro H8QME con tarjeta hija SIMSO. Confirmado como corregido en firmware más

nuevo.

sun20 - Esta opción de solución alternativa solucionará varios problemas de autenticación IPMI 2.0 de Sun. Los problemas cubiertos incluyen claves hash de longitud no válida, claves hash incorrectamente calculadas y registros de suite de cifrado no válidos. Aquellos que encuentren este problema pueden ver errores "password invalid" o "bmc error". Problema observado en Sun Fire 4100/4200/4500 con ILOM. Esta solución alternativa incluye automáticamente la solución alternativa

"opensesspriv".

opensesspriv - Esta opción de solución alternativa alterará ligeramente el protocolo de conexión IPMI 2.0 de FreeIPMI para solucionar un algoritmo de hashing no válido utilizado por el sistema remoto. El nivel de privilegio enviado durante la etapa de Apertura de Sesión de una conexión IPMI 2.0 se utiliza para el hashing de claves en lugar del nivel de privilegio enviado durante la etapa de conexión RAKP1. Aquellos que encuentren este problema pueden ver errores "password invalid", "k_g invalid", "bad rmcpplus status code" o "privilege level cannot be obtained for this user". Problema observado en Sun Fire 4100/4200/4500 con ILOM, Inventec 5441/Dell Xanadu II, Supermicro X8DTH, Supermicro X8DTG, Intel S5500WBV/Penguin Relion 700, Intel S2600JF/Appro 512X, Quanta QSSC-S4R/Appro GB812X-CN, Dell C5220 y el software BMC OpenIPMI. Esta solución alternativa se activa automáticamente con la solución alternativa

"sun20".

integritycheckvalue - Esta opción de solución alternativa solucionará un valor de verificación de integridad no válido durante el establecimiento de una sesión IPMI 2.0 al usar Cipher Suite ID 0. El valor de verificación de integridad debería tener una longitud de 0, sin embargo, la placa base remota responde con un campo no vacío. Aquellos que encuentren este problema pueden ver errores "k_g invalid". Problema observado en Supermicro X8DTG, Supermicro X8DTU, Intel S5500WBV/Penguin Relion 700 e Intel S2600JF/Appro

512X.

ipmiping - Esta opción de solución alternativa informará a ipmipower para que use paquetes ping basados en IPMI en lugar de paquetes ping RMCP. Se ha observado que algunas placas base no implementan el soporte de ping/pong RMCP a pesar de ser requerido por la especificación IPMI. Aquellos que encuentren este problema pueden ver errores "not discovered" en el modo shell. Problema observado en Intel M50FCP, Intel Windmill, Quanta Winterfell y Wiwynn

Windmill.

Sin soporte para IPMI 1.5 - Se ha encontrado que algunas placas base que soportan IPMI 2.0 no soportan IPMI 1.5. Aquellos que encuentren este problema pueden ver errores "ipmi 2.0 unavailable" o "connection timeout". Este problema se puede solucionar usando IPMI 2.0 en lugar de IPMI 1.5 especificando --driver-type=LAN_2_0. Problema observado en un núme

PROBLEMAS

CONOCIDOS

En sistemas operativos antiguos, si ingresa su nombre de usuario, contraseña y otra información potencialmente relevante para la seguridad en la línea de comandos, esta información puede ser descubierta por otros usuarios al usar herramientas como el comando ps(1) o al mirar en el sistema de archivos /proc. Generalmente es más seguro ingresar la información de la contraseña con opciones como las opciones -P o -K. Configurar información relevante para la seguridad en el archivo de configuración de FreeIPMI también sería una forma apropiada de ocultar esta

información.

Para prevenir ataques de fuerza bruta, algunos BMC se "bloquearán" temporalmente después de un número de errores de autenticación remota. Es posible que deba esperar un tiempo para que este "bloqueo" temporal pase antes de que pueda autenticarse de

nuevo.

Las especificaciones de IPMI no requieren que los BMC realicen una operación de control de energía antes de devolver un código de finalización al llamador. Por lo tanto, es posible que ipmipower devuelva consultas de estado de energía opuestas a lo que está esperando. Por ejemplo, si se realiza una operación de "apagado", un BMC puede devolver un código de finalización exitoso a ipmipower antes de que la operación de "apagado" se realice realmente. Las consultas de estado de energía subsiguient

es pueden devolver "encendido" durante varios segundos, has
ta que el BMC realice realmente la operación de "apagado".
