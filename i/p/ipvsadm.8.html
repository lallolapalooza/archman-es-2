Ipvsadm(8)se utiliza para configurar, mantener o inspeccionar la tabla del servidor virtual en el kernel de Linux. El Servidor Virtual de Linux se puede utilizar para construir servicios de red escalables basados en un clúster de dos o más nodos. El nodo activo del clúster redirige las solicitudes de servicio a un conjunto de hosts de servidor que realmente realizarán los servicios. Las características soportadas incluyen tres protocolos (TCP, UDP y SCTP), tres métodos de reenvío de paquetes (NAT, túnel y enrutamiento directo) y ocho algoritmos de balanceo de carga (round robin, round robin ponderado, menor conexión, menor conexión ponderada, menor conexión basada en localidad, menor conexión basada en localidad con replicación, hash de destino y hash de origen).
El comando tiene dos formatos básicos de ejecución:ipvsadm
COMMAND virtual-service [ scheduling-method ] [ persistence options ] ipvsadm command
virtual-service server-address [ packet-forwarding-method
] [ weight options

]

El primer formato manipula un servicio virtual y el algoritmo para asignar solicitudes de servicio a los servidores reales. Opcionalmente, se puede especificar un tiempo de espera de persistencia y una máscara de red para la granularidad de un servicio persistente, así como un motor de persistencia. El segundo formato manipula un servidor real que está asociado con un servicio virtual existente. Al especificar un servidor real, se puede especificar el método de reenvío de paquetes y el peso del servidor real, en relación con otros servidores reales para el servicio virtual; de

lo contrario, se usarán los valores predeterminados.

PARÁMETROS

Los comandos anteriores aceptan o requieren cero o más de los siguientes parámetros.

-s, --scheduler scheduling-method
scheduling-method Algoritmo para asignar conexiones TCP y datagramas UDP a servidores reales. Los algoritmos de programación se implementan como módulos del kernel. Se incluyen diez con el Linux Virtual Server:

rr - Round Robin (Round Robin): distribuye los trabajos por igual entre los servidores reales disponibles.

wrr - Weighted Round Robin (Round Robin ponderado): asigna trabajos a los servidores reales de forma proporcional al peso de los servidores reales. Los servidores con pesos más altos reciben primero los nuevos trabajos y obtienen más trabajos que los servidores con pesos más bajos. Los servidores con pesos iguales reciben una distribución igual de los nuevos trabajos.

lc - Least-Connection (Menor conexión): asigna más trabajos a los servidores reales con menos trabajos activos.

wlc - Weighted Least-Connection (Menor conexión ponderada): asigna más trabajos a los servidores con menos trabajos y en relación con el peso de los servidores reales (Ci/Wi). Este es el predeterminado.

lblc - Locality-Based Least-Connection (Menor conexión basada en la localidad): asigna trabajos destinados a la misma dirección IP al mismo servidor si el servidor no está sobrecargado y está disponible; de lo contrario, asigna trabajos a servidores con menos trabajos, y lo conserva para futuras asignaciones.

lblcr - Locality-Based Least-Connection with Replication (Menor conexión basada en la localidad con replicación): asigna trabajos destinados a la misma dirección IP al nodo con menor conexión en el conjunto de servidores para la dirección IP. Si todos los nodos del conjunto de servidores están sobrecargados, selecciona un nodo con menos trabajos en el clúster y lo añade al conjunto de servidores de destino. Si el conjunto de servidores no se ha modificado durante el tiempo especificado, el nodo más cargado se elimina del conjunto de servidores, para evitar un alto grado de replicación.

dh - Destination Hashing (Hashing de destino): asigna trabajos a los servidores mediante la búsqueda en una tabla hash estáticamente asignada por sus direcciones IP de destino.

sh - Source Hashing (Hashing de origen): asigna trabajos a los servidores mediante la búsqueda en una tabla hash estáticamente asignada por sus direcciones IP de origen. Este programador tiene dos indicadores: sh-fallback, que habilita el cambio a un servidor diferente si el servidor seleccionado no estaba disponible, y sh-port, que añade el número de puerto de origen al cálculo del hash.

sed - Shortest Expected Delay (Retraso esperado más corto): asigna un trabajo entrante al servidor con el retraso esperado más corto. El retraso esperado que experimentará el trabajo es (Ci + 1) / Ui si se envía al i-ésimo servidor, en el cual Ci es el número de trabajos en el i-ésimo servidor y Ui es la tasa de servicio fija (peso) del i-ésimo servidor.

nq - Never Queue (Nunca en cola): asigna un trabajo entrante a un servidor inactivo si lo hay, en lugar de esperar a uno rápido; si todos los servidores están ocupados, adopta la política de retraso esperado más corto para asignar el trabajo.

fo - Weighted Failover (Conmutación por error ponderada): asigna un trabajo entrante al servidor con el peso más alto que esté actualmente disponible.

ovf - Weighted Overflow (Desbordamiento ponderado): asigna un trabajo entrante al servidor con el peso más alto que esté actualmente disponible y se desborda al siguiente cuando las conexiones activas superan el peso del nodo. Tenga en cuenta que este programador puede no ser adecuado para UDP porque solo usa conexiones activas.

mh - Maglev Hashing (Hashing Maglev): asigna trabajos entrantes basándose en el algoritmo de hashing Maglev de Google, proporcionando una participación casi igual de trabajos a cada servidor real y proporciona una interrupción mínima. Cuando el conjunto de servidores reales cambia, una conexión probablemente se enviará al mismo servidor real que antes. Este programador tiene dos indicadores: mh-fallback, que habilita el cambio a un servidor diferente si el servidor seleccionado no estaba disponible, y mh-port, que añade el número de puerto de origen al cálculo del hash.

-p, --persistent [timeout]
Especifica que un servicio virtual es persistente. Si se especifica esta opción, múltiples solicitudes de un cliente se redirigen al mismo servidor real seleccionado para la primera solicitud. Opcionalmente, el timeout de las sesiones persistentes puede especificarse dado en segundos, de lo contrario se usará el predeterminado de 300 segundos. Esta opción puede usarse en conjunto con protocolos como SSL o FTP donde es importante que los clientes se conecten consistentemente con el mismo servidor real.

Nota: Si un servicio virtual va a manejar conexiones FTP entonces la persistencia debe establecerse para el servicio virtual si el enrutamiento directo o el túnel se usan como mecanismo de reenvío. Si se usa el enmascaramiento en conjunto con un servicio FTP, la persistencia no es necesaria, pero debe usarse el módulo del kernel ip_vs_ftp. Este módulo puede insertarse manualmente en el kernel usando insmod(8).

-M, --netmask netmask
Especifica la granularidad con la que se agrupan los clientes para los servicios virtuales persistentes. La dirección de origen de la solicitud se enmascara con esta máscara de red para dirigir a todos los clientes de una red al mismo servidor real. El predeterminado es 255.255.255.255, es decir, la granularidad de persistencia es por host cliente. Se pueden usar máscaras de red menos específicas para resolver problemas con clústeres de caché no persistentes en el lado del cliente. Las máscaras de red IPv6 deben especificarse como una longitud de prefijo entre 1 y 128. La longitud de prefijo predeterminada es 128.
--pe persistence-engine
Especifica un motor de persistencia alternativo a usar. Actualmente el único motor de persistencia alternativo disponible es sip.
-b, --sched-flags sched-flags
Establece indicadores del programador para este servidor virtual. sched-flags es una lista de indicadores separados por comas. Consulte las descripciones del programador para los indicadores válidos del programador.
-r, --real-server server-address
Servidor real al que se puede asignar una solicitud asociada de servicio. La server-address es la host dirección de un servidor real, y puede más port. Host puede ser una dirección IP simple o un nombre de host. Port puede ser un número de puerto simple o el nombre de servicio del puerto. En el caso del método de enmascaramiento, la dirección del host es normalmente una dirección IP privada RFC 1918, y el puerto puede ser diferente del del servicio asociado. Con los métodos de túnel y enrutamiento directo, port debe ser igual al de la dirección del servicio. Para servicios normales, se usará el puerto especificado en la dirección del servicio si port no se especifica. Para servicios fwmark, port puede omitirse, en cuyo caso el puerto de destino en el servidor real será el puerto de destino de la solicitud enviada al servicio virtual.
[packet-forwarding-method]

-g, --gatewaying Usa enrutamiento de puerta de enlace (enrutamiento directo). Este es el predeterminado.

-i, --ipip Usa encapsulación ipip (túnel).

--tun-type tun-type tun-type es uno de ipip|gue|gre. El valor predeterminado de tun-type es ipip.

--tun-port tun-port tun-port es un entero que especifica el puerto de destino. Solo válido para tun-type gue.

--tun-nocsum Especifica que las sumas de verificación del túnel están deshabilitadas. Este es el predeterminado. Solo válido para tun-type gue y gre.

--tun-csum Especifica que las sumas de verificación del túnel están habilitadas. Solo válido para tun-type gue y gre.

--tun-remcsum Especifica que la descarga de verificación remota (Remote Checksum Offload) está habilitada. Solo válido para tun-type gue.

-m, --masquerading Usa enmascaramiento (traducción de acceso a la red, o NAT).

Nota: Independientemente del mecanismo de reenvío de paquetes especificado, los servidores reales para direcciones para las que hay interfaces en el nodo local usarán el método de reenvío local, luego los paquetes para los servidores se pasarán a la capa superior en el nodo local. Esto no puede especificarse por ipvsadm, más bien lo establece el kernel a medida que se añaden o modifican los servidores reales.

-w, --weight weight
Weight es un entero que especifica la capacidad de un servidor relativa a los demás en el grupo. Los valores válidos de weight son 0 a 65535. El predeterminado es 1. Los servidores inactivos se especifican con un peso de cero. Un servidor inactivo no recibirá nuevos trabajos pero aún servirá los trabajos existentes, para todos los algoritmos de programación distribuidos con el Linux Virtual Server. Establecer un servidor inactivo puede ser útil si el servidor está sobrecargado o necesita sacarse del servicio para mantenimiento.
-x, --u-threshold uthreshold
uthreshold es un entero que especifica el umbral de conexión superior de un servidor. Los valores válidos de uthreshold son 0 a 65535. El predeterminado es 0, lo que significa que el umbral de conexión superior no está establecido. Si uthreshold se establece con otros valores, no se enviarán nuevas conexiones al servidor cuando el número de sus conexiones supere su umbral de conexión superior.
-y, --l-threshold lthreshold
lthreshold es un entero que especifica el umbral de conexión inferior de un servidor. Los valores válidos de lthreshold son 0 a 65535. El predeterminado es 0, lo que significa que el umbral de conexión inferior no está establecido. Si lthreshold se establece con otros valores, el servidor recibirá nuevas conexiones cuando el número de sus conexiones baje por debajo de su umbral de conexión inferior. Si lthreshold no está establecido pero uthreshold lo está, el servidor recibirá nuevas conexiones cuando el número de sus conexiones baje por debajo de tres cuartos de su umbral de conexión superior.
-c, --connection
Salida de conexión. El list comando con esta opción listará las conexiones IPVS actuales.
--timeout
Salida de tiempo de espera. El list comando con esta opción mostrará los valores de tiempo de espera (en segundos) para las sesiones TCP, las sesiones TCP después de recibir un paquete FIN, y los paquetes UDP.

PARÁMETROS PARA EL DEMONIO DE SINCRONIZACIÓN

El --start-daemon requiere cero o más de los siguientes parámetros.

--syncid syncid
Especifica el syncid que el demonio maestro de sincronización rellena en el encabezado SyncID mientras envía mensajes de multidifusión, o que el demonio de respaldo de sincronización usa para filtrar los mensajes de multidifusión que no coinciden con el valor de SyncID. Los valores válidos de syncid son de 0 a 255. El valor predeterminado es 0, lo que significa que no hay filtrado en absoluto.
--sync-maxlen length
Especifica la longitud deseada de los mensajes de sincronización (tamaño de carga útil UDP). Se espera que el servidor de respaldo use un valor no menor que el valor usado en el servidor maestro. Los valores válidos de length están en el rango 1 .. (65535 - 20 - 8) pero el kernel asegura un espacio para al menos un mensaje de sincronización. Si el valor es menor que MTU, los mensajes de sincronización serán fragmentados por la capa IP. El valor predeterminado se deriva del valor de MTU cuando se inicia el demonio pero el demonio maestro no usará un valor predeterminado superior a 1500 por razones de compatibilidad.
--mcast-interface interface
Especifica la interfaz de multidifusión a través de la cual el demonio maestro de sincronización envía las multidifusiones salientes, o a la que el demonio de respaldo de sincronización escucha para las multidifusiones.
--mcast-group address
Especifica la dirección de multidifusión IPv4 o IPv6 para los mensajes de sincronización. El valor predeterminado es 224.0.0.81.
--mcast-port port
Especifica el puerto UDP para los mensajes de sincronización. El valor predeterminado es 8848.
--mcast-ttl ttl
Especifica el valor TTL para los mensajes de sincronización (1 .. 255). El valor predeterminado es 1.

EJEMPLO 1 - Servicio Virtual Simple

Los siguientes comandos configuran un Director Linux para distribuir las solicitudes entrantes dirigidas al puerto 80 en 207.175.44.110 equitativamente al puerto 80 en cinco servidores reales. El método de reenvío usado en este ejemplo es NAT, con cada uno de los servidores reales enmascarado por el Director Linux.

ipvsadm -A -t 207.175.44.110:80 -s rr
ipvsadm -a -t 207.175.44.110:80 -r 192.168.10.1:80 -m
ipvsadm -a -t 207.175.44.110:80 -r 192.168.10.2:80 -m
ipvsadm -a -t 207.175.44.110:80 -r 192.168.10.3:80 -m
ipvsadm -a -t 207.175.44.110:80 -r 192.168.10.4:80 -m
ipvsadm -a -t 207.175.44.110:80 -r 192.168.10.5:80 -m

Alternativamente, esto podría lograrse con un solo comando ipvsadm.

echo "
-A -t 207.175.44.110:80 -s rr
-a -t 207.175.44.110:80 -r 192.168.10.1:80 -m
-a -t 207.175.44.110:80 -r 192.168.10.2:80 -m
-a -t 207.175.44.110:80 -r 192.168.10.3:80 -m
-a -t 207.175.44.110:80 -r 192.168.10.4:80 -m
-a -t 207.175.44.110:80 -r 192.168.10.5:80 -m
" | ipvsadm -R

Como se usa enmascaramiento como mecanismo de reenvío en este ejemplo, la ruta predeterminada de los servidores reales debe establecerse en el director linux, el cual necesitará estar configurado para reenviar y enmascarar paquetes. Esto puede lograrse usando los siguientes comandos:

echo "1" > /proc/sys/net/ipv4/ip_forward

EJEMPLO 2 - Servicio Virtual con Marca de Cortafuegos

Los siguientes comandos configuran un Director Linux para distribuir las solicitudes entrantes dirigidas a cualquier puerto en 207.175.44.110 o 207.175.44.111 equitativamente al puerto correspondiente en cinco servidores reales. Como en el ejemplo anterior, el método de reenvío usado en este ejemplo es NAT, con cada uno de los servidores reales enmascarado por el Director Linux.

ipvsadm -A -f 1  -s rr
ipvsadm -a -f 1 -r 192.168.10.1:0 -m
ipvsadm -a -f 1 -r 192.168.10.2:0 -m
ipvsadm -a -f 1 -r 192.168.10.3:0 -m
ipvsadm -a -f 1 -r 192.168.10.4:0 -m
ipvsadm -a -f 1 -r 192.168.10.5:0 -m

Como se usa enmascaramiento como mecanismo de reenvío en este ejemplo, la ruta predeterminada de los servidores reales debe establecerse en el director linux, el cual necesitará estar configurado para reenviar y enmascarar paquetes. El servidor real también debería estar configurado para marcar los paquetes entrantes dirigidos a cualquier puerto en 207.175.44.110 y 207.175.44.111 con firewall-mark 1. Si el tráfico FTP va a ser manejado por este servicio virtual, entonces el módulo del kernel ip_vs_ftp necesita ser insertado en el kernel. Estas operaciones pueden lograrse usando los siguientes comandos:

echo "1" > /proc/sys/net/ipv4/ip_forward
modprobe ip_tables
iptables  -A PREROUTING -t mangle -d 207.175.44.110/31 -j MARK --set-mark 1
modprobe ip_vs_ftp

EJEMPLO 3 - Servicio Virtual con Túnel GUE

Los siguientes comandos configuran un Director Linux para distribuir las solicitudes entrantes dirigidas al puerto 80 en 207.175.44.110 equitativamente al puerto 80 en cinco servidores reales. El método de reenvío usado en este ejemplo es túnel con encapsulación gue.

ipvsadm -A -t 207.175.44.110:80 -s rr
ipvsadm -a -t 207.175.44.110:80 -r 192.168.10.1:80 -i --tun-type gue --tun-port 6080 --tun-nocsum
ipvsadm -a -t 207.175.44.110:80 -r 192.168.10.2:80 -i --tun-type gue --tun-port 6080 --tun-csum
ipvsadm -a -t 207.175.44.110:80 -r 192.168.10.3:80 -i --tun-type gue --tun-port 6080 --tun-remcsum
ipvsadm -a -t 207.175.44.110:80 -r 192.168.10.4:80 -i --tun-type gue --tun-port 6078
ipvsadm -a -t 207.175.44.110:80 -r 192.168.10.5:80 -i --tun-type gue --tun-port 6079

Alternativamente, esto podría lograrse con un solo comando ipvsadm.

echo "
-A -t 207.175.44.110:80 -s rr
-a -t 207.175.44.110:80 -r 192.168.10.1:80 -i --tun-type gue --tun-port 6080 --tun-nocsum
-a -t 207.175.44.110:80 -r 192.168.10.2:80 -i --tun-type gue --tun-port 6080 --tun-csum
-a -t 207.175.44.110:80 -r 192.168.10.3:80 -i --tun-type gue --tun-port 6080 --tun-remcsum
-a -t 207.175.44.110:80 -r 192.168.10.4:80 -i --tun-type gue --tun-port 6078
-a -t 207.175.44.110:80 -r 192.168.10.5:80 -i --tun-type gue --tun-port 6079
" | ipvsadm -R

EJEMPLO 4 - Servicio Virtual con Túnel GRE

Los siguientes comandos configuran un Director Linux para usar encapsulación GRE.

ipvsadm -A -t 10.0.0.1:80 -s rr
ipvsadm -a -t 10.0.0.1:80 -r 192.168.11.1:80 -i --tun-type gre --tun-csum

IPv6

Las direcciones IPv6 deberían estar rodeadas por corchetes ([ y ]).

ipvsadm -A -t [2001:db8::80]:80 -s rr
ipvsadm -a -t [2001:db8::80]:80 -r [2001:db8::a0a0]:80 -m

Los servicios fwmark IPv6 requieren la opción -6.

NOTAS

El Servidor Virtual de Linux implementa tres estrategias de defensa contra algunos tipos de ataques de denegación de servicio (DoS). El Director Linux crea una entrada para cada conexión para mantener su estado, y cada entrada ocupa 128 bytes de memoria efectiva. La vulnerabilidad de LVS a un ataque DoS radica en el potencial de aumentar el número de entradas tanto como sea posible hasta que el director linux se quede sin memoria. Las tres estrategias de defensa contra el ataque son: Descartar aleatoriamente algunas entradas en la tabla. Descartar 1/tasa paquetes antes de reenviarlos. Y usar la tabla de transición de estado tcp segura y tiempos de espera cortos. Las estrategias son controladas por variables sysctl y entradas correspondientes en el sistema de archivos /proc:

/proc/sys/net/ipv4/vs/drop_entry /proc/sys/net/ipv4/vs/drop_packet /proc/sys/net/ipv4/vs/secure_tcp

Los valores válidos para cada variable van del 0 al 3. El valor por defecto es 0, lo que desactiva la respectiva estrategia de defensa. 1 y 2 son modos automáticos: cuando no hay suficiente memoria disponible, la respectiva estrategia se habilitará y la variable se establecerá automáticamente en 2; de lo contrario, la estrategia se deshabilita y la variable se establece en 1. Un valor de 3 indica que la respectiva estrategia está siempre habilitada. El umbral de memoria disponible y los tiempos de espera de TCP seguro se pueden ajustar usando las variables sysctl y las entradas correspondientes en el sistema de archivos /proc:

/proc/sys/net/ipv4/vs/amemthresh /proc/sys/net/ipv4/vs/timeout_*
