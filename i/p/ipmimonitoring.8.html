IPMI-SENSORS(8) Comandos del Sistema IPMI-SENSORS(8)

NOMBRE

ipmi-sensors - mostrar información de sensores IPMI

SINOPSIS

ipmi-sensors [OPCIÓN...]

DESCRIPCIÓN

Ipmi-sensors muestra las lecturas actuales de los sensores e información del repositorio de datos del sensor (SDR). La visualización predeterminada muestra el ID del registro de cada sensor, el nombre del sensor, el nombre del tipo de sensor, la lectura del sensor (si corresponde) y el evento del sensor actual. Se puede encontrar información más detallada utilizando las opciones detalladas especificadas a continuación. Ipmi-sensors no informa al usuario si existe un problema con un sensor en particular porque las lecturas y los eventos de los sensores no se analizan de forma predeterminada. Los usuarios pueden desear usar la opción --output-sensor-state para mostrar el estado del sensor analizado. Algunos sensores pueden tener una lectura de sensor o un evento de sensor de "N/A" si la información no está disponible. Esto es típico de un sensor que no está habilitado o que no pertenece a un BMC. Consulte la opción --bridge-sensors a continuación para tratar con sensores que no pertenecen a un BMC. Los sensores pueden generar un evento de sensor de "Desconocido" si no se puede leer la lectura del sensor. Esto es típico de un sensor que está ocupado o de una lectura que no se puede calcular. Si los sensores informan "Estado no reconocido", es indicativo de un tipo de sensor desconocido, típicamente un sensor OEM. Si la interpretación OEM del sensor está disponible, --interpret-oem-data puede informar el estado apropiado del sensor. Los sensores no siempre necesitan informar un evento de sensor. Cuando no hay un evento de sensor, típicamente se informa "OK".

A continuación se enumeran las opciones generales de IPMI, las opciones específicas de la herramienta, la información de solución de problemas, la información de soluciones alternativas, los ejemplos y los problemas conocidos. Para una introducción general a FreeIPMI, consulte freeipmi(7). Para configurar sensores IPMI, consulte ipmi-config(8). Para realizar una gestión avanzada de SDR, consulte bmc-device(8).

OPCIONES GENERALES

Las siguientes opciones son opciones generales para configurar la comunicación IPMI y ejecutar comandos generales de la herramienta.

-D IPMIDRIVER, --driver-type=IPMIDRIVER
Especifica el tipo de controlador a usar en lugar de hacer una selección automática. Los controladores fuera de banda disponibles actualmente son LAN y LAN_2_0, que realizan IPMI 1.5 e IPMI 2.0 respectivamente. Los controladores en banda disponibles actualmente son KCS, SSIF, OPENIPMI, SUNBMC e INTELDCMI.
--disable-auto-probe
No sondear los dispositivos IPMI en banda para obtener la configuración predeterminada.
--driver-address=DIRECCION-CONTROLADOR
Especifica la dirección del controlador en banda a usar en lugar del valor sondado. DIRECCION-CONTROLADOR debe ir precedida por "0x" para un valor hexadecimal y '0' para un valor octal.
--driver-device=DISPOSITIVO
Especifica la ruta del dispositivo del controlador en banda a usar en lugar de la ruta sondada.
--register-spacing=ESPACIO-REGISTROS
Especifica el espaciado de registros del controlador en banda en lugar del valor sondado. El argumento está en bytes (es decir, espaciado de registros de 32 bits = 4)
--target-channel-number=NUMERO-CANAL
Especifica el número de canal de destino del controlador en banda al que enviar solicitudes IPMI.
--target-slave-address=DIRECCION-ESCLAVO
Especifica el número de esclavo de destino del controlador en banda al que enviar solicitudes IPMI.
-h IPMIHOST1,IPMIHOST2,..., --hostname=IPMIHOST1[:PUERTO],IPMIHOST2[:PUERTO],...
Especifica el(los) host(s) remoto(s) con el(los) que comunicarse. Se pueden separar varios nombres de host por coma o se pueden especificar en formato de rango; consulte SOPORTE DE RANGO DE HOSTS a continuación. Se puede especificar un puerto opcional con cada host, lo que puede ser útil en situaciones de reenvío de puertos o similares. Si especifica una dirección IPv6 y un puerto, use el formato [DIRECCIÓN]:PUERTO.
-u NOMBRE-USUARIO, --username=NOMBRE-USUARIO
Especifica el nombre de usuario a usar al autenticarse con el host remoto. Si no se especifica, se asume un nombre de usuario nulo (es decir, anónimo). El usuario debe tener al menos privilegios de OPERADOR para que esta herramienta funcione completamente.
-p CONTRASEÑA, --password=CONTRASEÑA
Especifica la contraseña a usar al autenticarse con el host remoto. Si no se especifica, se asume una contraseña nula. La longitud máxima de la contraseña es 16 para IPMI 1.5 y 20 para IPMI 2.0.
-P, --password-prompt
Solicita la contraseña para evitar la posibilidad de listarla en las listas de procesos.
-k K_G, --k-g=K_G
Especifica la clave K_g del BMC a usar al autenticarse con el host remoto para IPMI 2.0. Si no se especifica, se asume una clave nula. Para introducir la clave en formato hexadecimal, prefije la cadena con '0x'. Por ejemplo, la clave 'abc' se puede introducir con la cadena 'abc' o la cadena '0x616263'
-K, --k-g-prompt
Solicita k-g para evitar la posibilidad de listarla en las listas de procesos.
--session-timeout=MILISEGUNDOS
Especifica el tiempo de espera de la sesión en milisegundos. El valor predeterminado es 20000 milisegundos (20 segundos) si no se especifica.
--retransmission-timeout=MILISEGUNDOS
Especifica el tiempo de espera de retransmisión del paquete en milisegundos. El valor predeterminado es 1000 milisegundos (1 segundo) si no se especifica. El tiempo de espera de retransmisión no puede ser mayor que el tiempo de espera de la sesión.
-a TIPO-AUTENTICACION, --authentication-type=TIPO-AUTENTICACION
Especifica el tipo de autenticación IPMI 1.5 a usar. Los tipos de autenticación disponibles actualmente son NONE, STRAIGHT_PASSWORD_KEY, MD2 y MD5. El valor predeterminado es MD5 si no se especifica.
-I ID-SUITE-CIFRADO, --cipher-suite-id=ID-SUITE-CIFRADO
Especifica el ID de la suite de cifrado IPMI 2.0 a usar. El ID de la Suite de Cifrado identifica un conjunto de algoritmos de autenticación, integridad y confidencialidad a usar para la comunicación IPMI 2.0. El algoritmo de autenticación identifica el algoritmo a usar para la configuración de la sesión, el algoritmo de integridad identifica el algoritmo a usar para las firmas de paquetes de sesión, y el algoritmo de confidencialidad identifica el algoritmo a usar para el cifrado de la carga útil. El valor predeterminado es el ID de la suite de cifrado 3 si no se especifica. Las siguientes suites de cifrado los IDs son actualmente compatibles:

0 - Algoritmo de Autenticación = Ninguno; Algoritmo de Integridad = Ninguno; Algoritmo de Confidencialidad = Ninguno

1 - Algoritmo de Autenticación = HMAC-SHA1; Algoritmo de Integridad = Ninguno; Algoritmo de Confidencialidad = Ninguno

2 - Algoritmo de Autenticación = HMAC-SHA1; Algoritmo de Integridad = HMAC-SHA1-96; Algoritmo de Confidencialidad = Ninguno

3 - Algoritmo de Autenticación = HMAC-SHA1; Algoritmo de Integridad = HMAC-SHA1-96; Algoritmo de Confidencialidad = AES-CBC-128

6 - Algoritmo de Autenticación = HMAC-MD5; Algoritmo de Integridad = Ninguno; Algoritmo de Confidencialidad = Ninguno

7 - Algoritmo de Autenticación = HMAC-MD5; Algoritmo de Integridad = HMAC-MD5-128; Algoritmo de Confidencialidad = Ninguno

8 - Algoritmo de Autenticación = HMAC-MD5; Algoritmo de Integridad = HMAC-MD5-128; Algoritmo de Confidencialidad = AES-CBC-128

11 - Algoritmo de Autenticación = HMAC-MD5; Algoritmo de Integridad = MD5-128; Algoritmo de Confidencialidad = Ninguno

12 - Algoritmo de Autenticación = HMAC-MD5; Algoritmo de Integridad = MD5-128; Algoritmo de Confidencialidad = AES-CBC-128

15 - Algoritmo de Autenticación = HMAC-SHA256; Algoritmo de Integridad = Ninguno; Algoritmo de Confidencialidad = Ninguno

16 - Algoritmo de Autenticación = HMAC-SHA256; Algoritmo de Integridad = HMAC_SHA256_128; Algoritmo de Confidencialidad = Ninguno

17 - Algoritmo de Autenticación = HMAC-SHA256; Algoritmo de Integridad = HMAC_SHA256_128; Algoritmo de Confidencialidad = AES-CBC-128

-l NIVEL-PRIVILEGIO, --privilege-level=NIVEL-PRIVILEGIO
Especifica el nivel de privilegio a usar al autenticarse con el host remoto. Los niveles de privilegio disponibles son CALLBACK, USER, OPERATOR, y ADMIN. El valor predeterminado es USER si no se especifica. El usuario debe tener al menos privilegios de OPERADOR para que esta herramienta funcione completamente.

Este sitio no está asociado de ninguna forma con Arch Linux ni afiliado a este proyecto. El contenido es únicamente una traducción de las páginas del manual de Arch publicadas en man.archlinux.org.

-NIVEL
Especifica el nivel de privilegio a utilizar. Los niveles de privilegio actualmente disponibles son USER, OPERATOR y ADMIN. Por defecto es OPERATOR si no se especifica.
--config-file=ARCHIVO
Especifica un archivo de configuración alternativo.
-W SOLUCIONES, --workaround-flags=SOLUCIONES
Especifica soluciones a problemas de cumplimiento del proveedor. Se pueden especificar múltiples soluciones separadas por comas. Un indicador especial de línea de comandos "none" indicará que no hay soluciones (puede ser útil para anular los valores predeterminados configurados). Vea SOLUCIONES más abajo para obtener una lista de las soluciones disponibles.
--debug
Activa la depuración.
-?, --help
Muestra una lista de ayuda y sale.
--usage
Muestra un mensaje de uso y sale.
-V, --version
Muestra la versión del programa y sale.

IPMI-SENSORS OPCIONES

Las siguientes opciones son específicas de ipmi-sensors.

-v, --verbose
Muestra una salida detallada de los sensores. Esta opción mostrará información adicional sobre los sensores, como umbrales, rangos, números y códigos de tipo de evento/lectura.
-vv
Muestra una salida muy detallada de los sensores. Esta opción mostrará más información adicional que la opción detallada, como información sobre eventos, otros tipos de sensores y sensores OEM.
-i, --sdr-info
Muestra información del repositorio de datos de sensores (SDR)
-q, --quiet-readings
No muestra los valores de lectura de los sensores de forma predeterminada. Esta opción es particularmente útil si desea utilizar una salida distribuida entre hosts en un clúster y desea consolidar la salida.
-r LISTA-DE-IDS-DE-REGISTRO, --record-ids=LISTA-DE-IDS-DE-REGISTRO
Especifica los sensores a mostrar por id de registro. Se pueden separar múltiples ids de registro con comas o espacios. Si se especifican tanto --record-ids como --sensor-types , --record-ids tiene prioridad. Un id de registro especial de línea de comandos "all" indicará que se deben mostrar todos los ids de registro (puede ser útil para anular los valores predeterminados configurados).
-R LISTA-DE-IDS-DE-REGISTRO, --exclude-record-ids=LISTA-DE-IDS-DE-REGISTRO
Especifica los sensores a no mostrar por id de registro. Se pueden separar múltiples ids de registro con comas o espacios. Un id de registro especial de línea de comandos "none" indicará que no se debe excluir ningún id de registro (puede ser útil para anular los valores predeterminados configurados).
-t LISTA-DE-TIPOS-DE-SENSOR, --sensor-types=LISTA-DE-TIPOS-DE-SENSOR
Especifica los tipos de sensores para los que mostrar salidas. Se pueden separar múltiples tipos con comas o espacios. Si se especifican tanto --record-ids como --sensor-types , --record-ids tiene prioridad. Un tipo especial de línea de comandos "all" indicará que se deben mostrar todos los tipos (puede ser útil para anular los valores predeterminados configurados). Los usuarios pueden especificar los tipos de sensores por cadena (vea --list-sensor-types más abajo) o por número (decimal o hexadecimal).
-T LISTA-DE-TIPOS-DE-SENSOR, --exclude-sensor-types=LISTA-DE-TIPOS-DE-SENSOR
Especifica los tipos de sensores para los que no mostrar salidas. Se pueden separar múltiples tipos con comas o espacios. Un tipo especial de línea de comandos "none" indicará que no se debe excluir ningún tipo (puede ser útil para anular los valores predeterminados configurados). Los usuarios pueden especificar los tipos de sensores por cadena (vea --list-sensor-types más abajo) o por número (decimal o hexadecimal).
-L, --list-sensor-types
Lista los tipos de sensores.
-b, --bridge-sensors
De forma predeterminada, no se intenta obtener lecturas de sensores para sensores cuyos propietarios no son el BMC. Al establecer esta opción, las peticiones de sensores se pueden enlazar a propietarios que no son el BMC para obtener lecturas de sensores. El enlace puede no funcionar en algunas interfaces/tipos de controlador.
--shared-sensors
Algunos sensores comparten el mismo registro de datos de sensores (SDR). Esto se utiliza típicamente para entradas del registro de eventos del sistema (SEL) y no para lecturas de sensores. Sin embargo, puede haber algunas placas base en las que este formato se utilice para múltiples sensores activos, o el usuario simplemente tiene interés en ver la permutación de entradas compartidas por una entrada de SDR. Al establecer esta opción, se iterará y mostrará cada número de sensor compartido por un registro.
--interpret-oem-data
Intenta interpretar datos OEM, como datos de eventos, lecturas de sensores o información extra general, etc. Si no hay una interpretación OEM disponible, se generará la salida predeterminada. La corrección de las interpretaciones OEM no puede garantizarse debido a posibles cambios que los proveedores OEM puedan hacer en productos, firmware, etc. Vea INTERPRETACIÓN OEM más abajo para las interpretaciones confirmadas de placas base soportadas.
--ignore-not-available-sensors
Ignora los sensores no disponibles (es decir, N/A) en la salida.
--ignore-unrecognized-events
Ignora los eventos de sensores no reconocidos. Esto suprimirá la salida de eventos no reconocidos, típicamente mostrados como 'Unrecognized Event = XXXXh' en la salida. Además, los eventos no reconocidos se ignorarán al calcular el estado del sensor con --output-sensor-state más abajo.
--output-event-bitmask
Muestra el valor de la máscara de bits del evento en lugar de la representación de cadena.
--output-sensor-state
Muestra el estado del sensor en la salida. Esto añadirá una salida adicional que informa si un sensor está en un estado NOMINAL, WARNING o CRITICAL. El estado del sensor es un valor interpretado basado en el evento actual del sensor. Las interpretaciones del estado del sensor están determinadas por el archivo de configuración /etc/freeipmi//freeipmi_interpret_sensor.conf. Vea freeipmi_interpret_sensor.conf(5) para más información. Esta opción da una salida idéntica al estado del sensor previamente mostrado por ipmimonitoring(8).
--sensor-state-config-file=ARCHIVO
Especifica un archivo de configuración de estado del sensor alternativo. La opción se ignora si --output-sensor-state no se especifica.
--entity-sensor-names
Muestra los nombres de los sensores con el prefijo de su id de entidad y número de instancia cuando sea apropiado. Esto puede ser necesario en algunas placas base para ayudar a identificar a qué sensores se hace referencia. Por ejemplo, una placa base puede tener múltiples sensores llamados 'TEMP'. El id de entidad y el número de instancia pueden ayudar a aclarar a qué sensor se refiere "Processor 1" vs. "Processor 2".
--output-sensor-thresholds
Muestra los umbrales de los sensores en la salida. Esto añadirá columnas a la salida predeterminada para los umbrales no recuperable inferior, crítico inferior, no crítico inferior, no crítico superior, crítico superior y no recuperable superior.
--no-sensor-type-output
No muestra el tipo de sensor para cada entrada. En muchos sistemas, el tipo de sensor es redundante con el nombre del sensor. Esto puede ser especialmente cierto si --entity-sensor-names se especifica. Si el nombre del sensor es suficiente, o si el tipo de sensor no es de interés para el usuario, se puede especificar esta opción para condensar la salida.
--comma-separated-output
Muestra los campos en formato separado por comas.
--no-header-output
No muestra los encabezados de las columnas. Puede ser útil en scripts.
--non-abbreviated-units
Muestra las unidades sin abreviar (por ejemplo, 'Amps' en lugar de 'A'). Puede ayudar a desambiguar las unidades (por ejemplo, 'C' para Celsius o Coulombios).
--legacy-output
Muestra la salida en formato heredado. Las opciones más nuevas pueden no ser aplicables a la salida heredada.
--ipmimonitoring-legacy-output
Muestra el formato heredado de la herramienta heredada ipmimonitoring . Las opciones más nuevas pueden no ser aplicables a la salida heredada.

OPCIONES DE CACHÉ SDR

Esta herramienta requiere acceso a la caché del repositorio de datos de sensores (SDR) para su funcionamiento general. De forma predeterminada, los datos SDR se descargarán y almacenarán en caché en la máquina local. Las siguientes opciones se aplican a la caché SDR.

--flush-cache
Vacía la versión en caché del repositorio de datos de sensores (SDR). El SDR se almacena típicamente en caché para un acceso posterior más rápido. Sin embargo, puede necesitar ser vaciado y regenerado si el SDR ha sido actualizado en un sistema.
--quiet-cache
No muestra información sobre la creación/borrado de la caché. Puede ser útil en scripts.
--sdr-cache-recreate
Si la caché SDR está desactualizada o es inválida, regenera automáticamente la caché del repositorio de datos de sensores (SDR). Esta opción puede ser útil para fines de scripting.
--sdr-cache-file=ARCHIVO
Especifica un archivo de caché específico del repositorio de datos de sensores (SDR) para ser almacenado o leído. Si se usa esta opción cuando se especifican múltiples hosts, se usará el mismo archivo de caché SDR para todos los hosts.
--sdr-cache-directory=DIRECTORIO
Especifica un directorio alternativo para que se almacenen o se lean las cachés del repositorio de datos de sensores (SDR). Por defecto es el directorio de inicio si no se especifica.

DATE AND TIME OPTIONS

The following options allow the user to adjust the interpretation of timestamps. By default, timestamps are interpreted as local time. If your system stores timestamps in UTC, you will want to use one of the following options.

It is important to note that the system BIOS, operating system, and vendor can all affect whether timestamps are stored in local time or UTC. Due to this ambiguity, the following options have been provided to allow the user to specify how timestamps should be interpreted.

--utc-to-localtime
Assume all times are reported in UTC time and convert the time to localtime before being output.
--localtime-to-utc
Convert all localtime timestamps to UTC before being output.
--utc-offset=SECONDS
Specify a specific UTC offset in seconds to be added to timestamps. Value can range from -86400 to 86400 seconds. Defaults to 0.

HOSTRANGED OPTIONS

The following options manipulate hostranged output. See HOSTRANGED SUPPORT below for additional information on hostranges.

-B, --buffer-output
Buffer hostranged output. For each node, buffer standard output until the node has completed its IPMI operation. When specifying this option, data may appear to output slower to the user since the the entire IPMI operation must complete before any data can be output. See HOSTRANGED SUPPORT below for additional information.
-C, --consolidate-output
Consolidate hostranged output. The complete standard output from every node specified will be consolidated so that nodes with identical output are not output twice. A header will list those nodes with the consolidated output. When this option is specified, no output can be seen until the IPMI operations to all nodes has completed. If the user breaks out of the program early, all currently consolidated output will be dumped. See HOSTRANGED SUPPORT below for additional information.
-F NUM, --fanout=NUM
Specify multiple host fanout. A "sliding window" (or fanout) algorithm is used for parallel IPMI communication so that slower nodes or timed out nodes will not impede parallel communication. The maximum number of threads available at the same time is limited by the fanout. The default is 64.
-E, --eliminate
Eliminate hosts determined as undetected by ipmidetect. This attempts to remove the common issue of hostranged execution timing out due to several nodes being removed from service in a large cluster. The ipmidetectd daemon must be running on the node executing the command.
--always-prefix
Always prefix output, even if only one host is specified or communicating in-band. This option is primarily useful for scripting purposes. Option will be ignored if specified with the -C option.

HOSTRANGED SUPPORT

Multiple hosts can be input either as an explicit comma separated lists of hosts or a range of hostnames in the general form: prefix[n-m,l-k,...], where n < m and l < k, etc. The later form should not be confused with regular expression character classes (also denoted by []). For example, foo[19] does not represent foo1 or foo9, but rather represents a degenerate range: foo19.

This range syntax is meant only as a convenience on clusters with a prefixNN naming convention and specification of ranges should not be considered necessary -- the list foo1,foo9 could be specified as such, or by the range foo[1,9].

Some examples of range usage follow:

    foo[01-05] instead of foo01,foo02,foo03,foo04,foo05
    foo[7,9-10] instead of foo7,foo9,foo10
    foo[0-3] instead of foo0,foo1,foo2,foo3

As a reminder to the reader, some shells will interpret brackets ([ and ]) for pattern matching. Depending on your shell, it may be necessary to enclose ranged lists within quotes.

When multiple hosts are specified by the user, a thread will be executed for each host in parallel up to the configured fanout (which can be adjusted via the -F option). This will allow communication to large numbers of nodes far more quickly than if done in serial.

By default, standard output from each node specified will be output with the hostname prepended to each line. Although this output is readable in many situations, it may be difficult to read in other situations. For example, output from multiple nodes may be mixed together. The -B and -C options can be used to change this default.

In-band IPMI Communication will be used when the host "localhost" is specified. This allows the user to add the localhost into the hostranged output.

GENERAL TROUBLESHOOTING

Most often, IPMI problems are due to configuration problems.

IPMI over LAN problems involve a misconfiguration of the remote machine's BMC. Double check to make sure the following are configured properly in the remote machine's BMC: IP address, MAC address, subnet mask, username, user enablement, user privilege, password, LAN privilege, LAN enablement, and allowed authentication type(s). For IPMI 2.0 connections, double check to make sure the cipher suite privilege(s) and K_g key are configured properly. The ipmi-config(8) tool can be used to check and/or change these configuration settings.

Inband IPMI problems are typically caused by improperly configured drivers or non-standard BMCs.

In addition to the troubleshooting tips below, please see WORKAROUNDS below to also if there are any vendor specific bugs that have been discovered and worked around.

Listed below are many of the common issues for error messages. For additional support, please e-mail the <freeipmi-users@gnu.org> mailing list.

"username invalid" - The username entered (or a NULL username if none was entered) is not available on the remote machine. It may also be possible the remote BMC's username configuration is incorrect.

"password invalid" - The password entered (or a NULL password if none was entered) is not correct. It may also be possible the password for the user is not correctly configured on the remote BMC.

"password verification timeout" - Password verification has timed out. A "password invalid" error (described above) or a generic "session timeout" (described below) occurred. During this point in the protocol it cannot be differentiated which occurred.

"k_g invalid" - The K_g key entered (or a NULL K_g key if none was entered) is not correct. It may also be possible the K_g key is not correctly configured on the remote BMC.

"privilege level insufficient" - An IPMI command requires a higher user privilege than the one authenticated with. Please try to authenticate with a higher privilege. This may require authenticating to a different user which has a higher maximum privilege.

"privilege level cannot be obtained for this user" - The privilege level you are attempting to authenticate with is higher than the maximum allowed for this user. Please try again with a lower privilege. It may also be possible the maximum privilege level allowed for a user is not configured properly on the remote BMC.

"authentication type unavailable for attempted privilege level" - The authentication type you wish to authenticate with is not available for this privilege level. Please try again with an alternate authentication type or alternate privilege level. It may also be possible the available authentication types you can authenticate with are not correctly configured on the remote BMC.

"cipher suite id unavailable" - The cipher suite id you wish to authenticate with is not available on the remote BMC. Please try again with an alternate cipher suite id. It may also be possible the available cipher suite ids are not correctly configured on the remote BMC.

"ipmi 2.0 unavailable" - IPMI 2.0 was not discovered on the remote machine. Please try to use IPMI 1.5 instead.

"connection timeout" - Initial IPMI communication failed. A number of potential errors are possible, including an invalid hostname specified, an IPMI IP address cannot be resolved, IPMI is not enabled on the remote server, the network connection is bad, etc. Please verify configuration and connectivity.

"session timeout" - The IPMI session has timed out. Please reconnect. If this error occurs often, you may wish to increase the retransmission timeout. Some remote BMCs are considerably slower than others.

"device not found" - The specified device could not be found. Please check configuration or inputs and try again.

"driver timeout" - Communication with the driver or device has timed out. Please try again.

"message timeout" - Communication with the driver or device has timed out. Please try again.

"BMC busy" - The BMC is currently busy. It may be processing information or have too many simultaneous sessions to manage. Please wait and try again.

"could not find inband device" - An inband device could not be found. Please check configuration or specify specific device or driver on the command line.

"driver timeout" - The inband driver has timed out communicating to the local BMC or service processor. The BMC or service processor may be busy or (worst case) possibly non-functioning.

"internal IPMI error" - An IPMI error has occurred that FreeIPMI does not know how to handle. Please e-mail <freeipmi-users@gnu.org> to report the issue.

"sensor config file parse error" - A parse error was found in the sensor interpretation configuration file. Please see freeipmi_interpret_sensor.conf(5).

WORKAROUNDS

With so many different vendors implementing their own IPMI solutions, different vendors may implement their IPMI protocols incorrectly. The following describes a number of workarounds currently available to handle discovered compliance issues. When possible, workarounds have been implemented so they will be transparent to the user. However, some will require the user to specify a workaround be used via the -W o

opción

.

El hardware listado a continuación puede indicar únicamente el hardware en el que se descubrió un problema. Versiones más recientes de hardware pueden corregir los problemas indicados a continuación. Máquinas similares de distintos proveedores pueden o no exhibir los mismos problemas. Diferentes proveedores pueden licenciar su firmware del mismo desarrollador de firmware IPMI, por lo que puede ser útil probar las soluciones alternativas listadas a continuación incluso si su placa base no está listada. Si cree que su hardware tiene un problema de cumplimiento adicional que requiere la implementación de una solución alternativa, por favor contacte a los mantenedores de FreeIPMI en <freeipmi-users@gnu.org> o <freeipmi-devel@gnu.org>

assumeio - Este indicador de solución alternativa asumirá que las interfaces inband se comunican con el E/S del sistema en lugar de estar mapeadas en memoria. Esto solucionará sistemas que reportan direcciones base inválidas. Aquellos que encuentren este problema pueden ver errores "device not supported" o "could not find inband device". Problema observado en HP ProLiant DL145 G1. spinpoll - Este indicador de solución alternativa informará a algunos controladores inband (notablemente el controlador KCS) que giren (spin) mientras hacen sondeo en lugar de poner el proceso a dormir. Esto puede mejorar significativamente el tiempo de ejecución real de las herramientas porque la granularidad del planificador de un sistema operativo puede ser mucho mayor que el tiempo que toma realizar una única transacción de mensaje IPMI. Sin embargo, al girar, su sistema puede estar realizando un trabajo menos útil al no cambiar el contexto de la herramienta para una tarea más

Soluciona múltiples problemas en los que el sistema remoto no reporta correctamente las capacidades de nombre de usuario, las capacidades de autenticación o el estado de K_g. Se advierte a los usuarios sobre el uso de esta opción, ya que elimina la validación de la integridad del paquete en una serie de circunstancias.
