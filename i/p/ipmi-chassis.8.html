IPMI-CHASSIS(8) Comandos del sistema IPMI-CHASSIS(8)

NOMBRE

ipmi-chassis - Utilidad de gestión de chasis IPMI

SINOPSIS

ipmi-chassis [OPCIÓN...]

DESCRIPCIÓN

Ipmi-chassis se utiliza para gestionar/monitorizar un chasis IPMI, como la alimentación del chasis, la identificación (es decir, control del LED) y el estado. Consulte OPCIONES a continuación para ver todas las opciones de gestión de chasis disponibles.

A continuación se enumeran las opciones generales de IPMI, las opciones específicas de la herramienta, la información de resolución de problemas, la información de soluciones alternativas, ejemplos y problemas conocidos. Para una introducción general a FreeIPMI, consulte freeipmi(7). Para realizar la configuración del chasis IPMI, consulte ipmi-config(8). Para realizar una gestión avanzada del chasis, consulte bmc-device(8). Para una utilidad de control de alimentación del chasis más potente, consulte ipmipower(8).

OPCIONES GENERALES

Las siguientes opciones son opciones generales para configurar la comunicación IPMI y ejecutar comandos generales de la herramienta.

-D CONTROLADORIPMI, --driver-type=CONTROLADORIPMI
Especifica el tipo de controlador a utilizar en lugar de una selección automática. Los controladores externos disponibles actualmente son LAN y LAN_2_0, que realizan IPMI 1.5 y IPMI 2.0 respectivamente. Los controladores internos disponibles actualmente son KCS, SSIF, OPENIPMI, SUNBMC e INTELDCMI.
--disable-auto-probe
No sondear dispositivos IPMI internos en busca de configuraciones predeterminadas.
--driver-address=DIRECCION_CONTROLADOR
Especifica la dirección del controlador interno a utilizar en lugar del valor sondado. DIRECCION_CONTROLADOR debe ir prefijada con "0x" para un valor hexadecimal y '0' para un valor octal.
--driver-device=DISPOSITIVO
Especifica la ruta del dispositivo del controlador interno a utilizar en lugar de la ruta sondada.
--register-spacing=ESPACIADO_REGISTROS
Especifica el espaciado de registros del controlador interno en lugar del valor sondado. El argumento está en bytes (es decir, espaciado de registros de 32 bits = 4)
--target-channel-number=NUMERO_CANAL
Especifica el número de canal interno del controlador al que se enviarán las solicitudes IPMI.
--target-slave-address=DIRECCION_ESCLAVO
Especifica el número de esclavo del controlador interno al que se enviarán las solicitudes IPMI.
-h HOSTIPMI1,HOSTIPMI2,..., --hostname=HOSTIPMI1[:PUERTO],HOSTIPMI2[:PUERTO],...
Especifica el(los) host(s) remoto(s) con los que comunicarse. Se pueden separar varios nombres de host con comas o especificarse en formato de rango; consulte SOPORTE DE RANGO DE HOSTS a continuación. Se puede especificar un puerto opcional con cada host, lo que puede ser útil en situaciones de reenvío de puertos o similares. Si se especifica una dirección IPv6 y un puerto, utilice el formato [DIRECCIÓN]:PUERTO.
-u NOMBRE_USUARIO, --username=NOMBRE_USUARIO
Especifica el nombre de usuario a utilizar al autenticarse con el host remoto. Si no se especifica, se asume un nombre de usuario nulo (es decir, anónimo). El usuario debe tener al menos privilegios de ADMIN para que esta herramienta funcione completamente.
-p CONTRASEÑA, --password=CONTRASEÑA
Especifica la contraseña a utilizar al autenticarse con el host remoto. Si no se especifica, se asume una contraseña nula. La longitud máxima de la contraseña es 16 para IPMI 1.5 y 20 para IPMI 2.0.
-P, --password-prompt
Solicitar la contraseña para evitar la posibilidad de que aparezca en las listas de procesos.
-k K_G, --k-g=K_G
Especifica la clave K_g BMC a utilizar al autenticarse con el host remoto para IPMI 2.0. Si no se especifica, se asume una clave nula. Para introducir la clave en formato hexadecimal, prefije la cadena con '0x'. Por ejemplo, la clave 'abc' se puede introducir con la cadena 'abc' o con la cadena '0x616263'.
-K, --k-g-prompt
Solicitar k-g para evitar la posibilidad de que aparezca en las listas de procesos.
--session-timeout=MILLISEGUNDOS
Especifica el tiempo de espera de la sesión en milisegundos. El valor por defecto es 20000 milisegundos (20 segundos) si no se especifica.
--retransmission-timeout=MILLISEGUNDOS
Especifica el tiempo de espera de retransmisión de paquetes en milisegundos. El valor por defecto es 1000 milisegundos (1 segundo) si no se especifica. El tiempo de espera de retransmisión no puede ser mayor que el tiempo de espera de la sesión.
-a TIPO_AUTENTICACIÓN, --authentication-type=TIPO_AUTENTICACIÓN
Especifica el tipo de autenticación IPMI 1.5 a utilizar. Los tipos de autenticación disponibles actualmente son NONE, STRAIGHT_PASSWORD_KEY, MD2 y MD5. El valor por defecto es MD5 si no se especifica.
-I ID_SUITE_CIFRADO, --cipher-suite-id=ID_SUITE_CIFRADO
Especifica el ID de la suite de cifrado IPMI 2.0 a utilizar. El ID de la suite de cifrado identifica un conjunto de algoritmos de autenticación, integridad y confidencialidad a utilizar para la comunicación IPMI 2.0. El algoritmo de autenticación identifica el algoritmo a utilizar para la configuración de la sesión, el algoritmo de integridad identifica el algoritmo a utilizar para las firmas de paquetes de sesión y el algoritmo de confidencialidad identifica el algoritmo a utilizar para el cifrado de la carga útil. El valor por defecto es el ID de la suite de cifrado 3 si no se especifica. Los siguientes IDs de suite de cifrado son compatibles actualmente:

0 - Algoritmo de autenticación = Ninguno; Algoritmo de integridad = Ninguno; Algoritmo de confidencialidad = Ninguno

1 - Algoritmo de autenticación = HMAC-SHA1; Algoritmo de integridad = Ninguno; Algoritmo de confidencialidad = Ninguno

2 - Algoritmo de autenticación = HMAC-SHA1; Algoritmo de integridad = HMAC-SHA1-96; Algoritmo de confidencialidad = Ninguno

3 - Algoritmo de autenticación = HMAC-SHA1; Algoritmo de integridad = HMAC-SHA1-96; Algoritmo de confidencialidad = AES-CBC-128

6 - Algoritmo de autenticación = HMAC-MD5; Algoritmo de integridad = Ninguno; Algoritmo de confidencialidad = Ninguno

7 - Algoritmo de autenticación = HMAC-MD5; Algoritmo de integridad = HMAC-MD5-128; Algoritmo de confidencialidad = Ninguno

8 - Algoritmo de autenticación = HMAC-MD5; Algoritmo de integridad = HMAC-MD5-128; Algoritmo de confidencialidad = AES-CBC-128

11 - Algoritmo de autenticación = HMAC-MD5; Algoritmo de integridad = MD5-128; Algoritmo de confidencialidad = Ninguno

12 - Algoritmo de autenticación = HMAC-MD5; Algoritmo de integridad = MD5-128; Algoritmo de confidencialidad = AES-CBC-128

15 - Algoritmo de autenticación = HMAC-SHA256; Algoritmo de integridad = Ninguno; Algoritmo de confidencialidad = Ninguno

16 - Algoritmo de autenticación = HMAC-SHA256; Algoritmo de integridad = HMAC_SHA256_128; Algoritmo de confidencialidad = Ninguno

17 - Algoritmo de autenticación = HMAC-SHA256; Algoritmo de integridad = HMAC_SHA256_128; Algoritmo de confidencialidad = AES-CBC-128

-l NIVEL_PRIVILEGIO, --privilege-level=NIVEL_PRIVILEGIO
Especifica el nivel de privilegio a utilizar. Los niveles de privilegio disponibles actualmente son USER, OPERATOR y ADMIN. El valor por defecto es ADMIN si no se especifica.
--config-file=ARCHIVO
Especifica un archivo de configuración alternativo.
-W SOLUCIONES_ALTERNATIVAS, --workaround-flags=SOLUCIONES_ALTERNATIVAS
Especifica soluciones alternativas para problemas de cumplimiento de proveedores. Se pueden especificar varias soluciones alternativas separadas por comas. Un indicador especial de línea de comandos "none" indicará que no hay soluciones alternativas (puede ser útil para anular las configuraciones predeterminadas). Consulte SOLUCIONES ALTERNATIVAS a continuación para ver una lista de soluciones alternativas disponibles.
--debug
Activa la depuración.
-?, --help
Muestra una lista de ayuda y sale.
--usage
Muestra un mensaje de uso y sale.
-V, --version
Muestra la información de la versión y sale.

OPCIONES_IPMI-CHASSIS

Las siguientes opciones son específicas de ipmi-chassis.

--get-chassis-capabilities
Obtener capacidades del chasis. Este comando devuelve información sobre qué funciones principales de gestión del chasis están disponibles.
--get-chassis-status
Obtener estado del chasis. Este comando devuelve información de estado de alto nivel sobre el chasis.
--chassis-control=CONTROL
Controlar el chasis. Este comando proporciona control de encendido, apagado y reinicio. Valores admitidos: POWER-DOWN, POWER-UP, POWER-CYCLE, HARD-RESET, DIAGNOSTIC-INTERRUPT, SOFT-SHUTDOWN.
--chassis-identify=IDENTIFY
Establecer la identificación del chasis. Este comando controla la identificación física del sistema, típicamente un LED. Valores admitidos: TURN-OFF para apagar la identificación, <intervalo> para encender la identificación durante "intervalo" segundos, FORCE para encender indefinidamente.
--get-system-restart-cause
Obtener la causa de reinicio del sistema.
--get-power-on-hours-counter
Obtener el contador de horas de encendido (POH).

OPCIONES_HOSTRANGED

Las siguientes opciones manipulan la salida de hostranged. Ver SOPORTE_HOSTRANGED abajo para información adicional sobre hostranges.

-B, --buffer-output
Almacenar en búfer la salida de hostranged. Para cada nodo, almacenar en búfer la salida estándar hasta que el nodo haya completado su operación IPMI. Al especificar esta opción, los datos pueden parecer que salen más lentamente para el usuario, ya que toda la operación IPMI debe completarse antes de que se puedan emitir datos. Ver SOPORTE_HOSTRANGED abajo para información adicional.
-C, --consolidate-output
Consolidar la salida de hostranged. La salida estándar completa de cada nodo especificado se consolidará para que los nodos con salida idéntica no se emitan dos veces. Un encabezado enumerará los nodos con la salida consolidada. Cuando se especifica esta opción, no se puede ver ninguna salida hasta que las operaciones IPMI en todos los nodos se hayan completado. Si el usuario interrumpe el programa anticipadamente, se volcará toda la salida actualmente consolidada. Ver SOPORTE_HOSTRANGED abajo para información adicional.
-F NUM, --fanout=NUM
Especificar múltiples fanout de host. Se utiliza un algoritmo de "ventana deslizante" (o fanout) para la comunicación IPMI paralela, de modo que los nodos lentos o los nodos que han caducado no impidan la comunicación paralela. El número máximo de hilos disponibles al mismo tiempo está limitado por el fanout. El valor predeterminado es 64.
-E, --eliminate
Eliminar hosts determinados como no detectados por ipmidetect. Esto intenta eliminar el problema común de que la ejecución de hostranged caduque debido a que varios nodos se eliminan del servicio en un clúster grande. El demonio ipmidetectd debe estar en ejecución en el nodo que ejecuta el comando.
--always-prefix
Prefijar siempre la salida, incluso si solo se especifica un host o se comunica en banda. Esta opción es principalmente útil para fines de scripting. La opción se ignorará si se especifica con la opción -C.

SOPORTE_HOSTRANGED

Se pueden introducir varios hosts ya sea como listas explícitas de hosts separadas por comas o como un rango de nombres de host en la forma general: prefijo[n-m,l-k,...], donde n < m y l < k, etc. La forma posterior no debe confundirse con las clases de caracteres de expresiones regulares (también denotadas por []). Por ejemplo, foo[19] no representa foo1 o foo9, sino que representa un rango degenerado: foo19.

Esta sintaxis de rango está destinada únicamente como una conveniencia en clústeres con una convención de nomenclatura prefijoNN y la especificación de rangos no debe considerarse necesaria: la lista foo1,foo9 podría especificarse como tal, o mediante el rango foo[1,9].

Algunos ejemplos de uso de rangos son los siguientes:

    foo[01-05] en lugar de foo01,foo02,foo03,foo04,foo05
    foo[7,9-10] en lugar de foo7,foo9,foo10
    foo[0-3] en lugar de foo0,foo1,foo2,foo3

Como recordatorio para el lector, algunos shells interpretarán los corchetes ([ y ]) para la coincidencia de patrones. Dependiendo de tu shell, puede ser necesario encerrar las listas de rango entre comillas.

Cuando se especifican varios hosts por el usuario, se ejecutará un hilo para cada host en paralelo hasta el fanout configurado (que se puede ajustar mediante la opción -F). Esto permitirá la comunicación a un gran número de nodos mucho más rápido que si se hiciera en serie.

Por defecto, la salida estándar de cada nodo especificado se emitirá con el nombre del host antepuesto a cada línea. Aunque esta salida es legible en muchas situaciones, puede ser difícil de leer en otras. Por ejemplo, la salida de varios nodos puede mezclarse. Las opciones -B y -C se pueden usar para cambiar este comportamiento predeterminado.

La comunicación IPMI en banda se utilizará cuando se especifique el host "localhost". Esto permite al usuario agregar localhost a la salida de hostranged.

SOLUCIÓN_DE_PROBLEMAS_GENERAL

La mayoría de las veces, los problemas de IPMI se deben a problemas de configuración.

Los problemas de IPMI sobre LAN implican una configuración incorrecta del BMC de la máquina remota. Verifique nuevamente para asegurarse de que lo siguiente esté configurado correctamente en el BMC de la máquina remota: dirección IP, dirección MAC, máscara de subred, nombre de usuario, habilitación de usuario, privilegio de usuario, contraseña, privilegio de LAN, habilitación de LAN y tipo(s) de autenticación permitidos. Para conexiones IPMI 2.0, verifique nuevamente para asegurarse de que el privilegio(s) de la suite de cifrado y la clave K_g estén configurados correctamente. La herramienta ipmi-config(8) se puede usar para verificar y/o cambiar estas configuraciones.

Los problemas de IPMI en banda suelen ser causados por controladores mal configurados o BMC no estándar.

Además de los consejos de solución de problemas a continuación, consulte también SOLUCIONES MÁS ADELANTE si hay algún error específico del fabricante que se haya descubierto y para el cual se haya encontrado una solución alternativa.

A continuación, se enumeran muchos de los problemas comunes para los mensajes de error. Para obtener soporte adicional, envíe un correo electrónico a la lista de correo <freeipmi-users@gnu.org>.

"username invalid" - El nombre de usuario introducido (o un nombre de usuario NULL si no se introdujo ninguno) no está disponible en la máquina remota. También es posible que la configuración del nombre de usuario del BMC remoto sea incorrecta.

"password invalid" - La contraseña introducida (o una contraseña NULL si no se introdujo ninguna) no es correcta. También es posible que la contraseña del usuario no esté configurada correctamente en el BMC remoto.

"password verification timeout" - La verificación de la contraseña ha caducado. Se produjo un error de "password invalid" (descrito anteriormente) o un error genérico de "session timeout" (descrito a continuación). Durante este punto del protocolo, no se puede diferenciar cuál ocurrió.

"k_g invalid" - La clave K_g introducida (o una clave K_g NULL si no se introdujo ninguna) no es correcta. También es posible que la clave K_g no esté configurada correctamente en el BMC remoto.

"privilege level insufficient" - Un comando IPMI requiere un privilegio de usuario superior al con el que se autenticó. Intente autenticarse con un privilegio superior. Esto puede requerir autenticarse con un usuario diferente que tenga un privilegio máximo superior.

"privilege level cannot be obtained for this user" - El nivel de privilegio con el que intenta autenticarse es superior al máximo permitido para este usuario. Intente nuevamente con un privilegio inferior. También es posible que el nivel de privilegio máximo permitido para un usuario no esté configurado correctamente en el BMC remoto.

"authentication type unavailable for attempted privilege level" - El tipo de autenticación con el que desea autenticarse no está disponible para este nivel de privilegio. Intente nuevamente con un tipo de autenticación alternativo o un nivel de privilegio alternativo. También es posible que los tipos de autenticación disponibles con los que puede autenticarse no estén configurados correctamente en el BMC remoto.

"cipher suite id unavailable" - El ID de la suite de cifrado con el que desea autenticarse no está disponible en el BMC remoto. Intente nuevamente con un ID de suite de cifrado alternativo. También es posible que los ID de suite de cifrado disponibles no estén configurados correctamente en el BMC remoto.

"ipmi 2.0 unavailable" - IPMI 2.0 no se descubrió en la máquina remota. Intente usar IPMI 1.5 en su lugar.

"connection timeout" - Falló la comunicación IPMI inicial. Es posible una serie de errores potenciales, que incluyen un nombre de host inválido especificado, una dirección IP de IPMI no resoluble, IPMI no habilitado en el servidor remoto, una conexión de red defectuosa, etc. Verifique la configuración y la conectividad.

"session timeout" - La sesión IPMI ha caducado. Por favor, vuelva a conectarse. Si este error ocurre a menudo, es posible que desee aumentar el tiempo de espera de retransmisión. Algunos BMC remotos son considerablemente más lentos que otros.

"device not found" - No se pudo encontrar el dispositivo especificado. Verifique la configuración o las entradas e intente nuevamente.

"driver timeout" - Se ha agotado el tiempo de espera de la comunicación con el controlador o dispositivo. Intente nuevamente.

"message timeout" - Se ha agotado el tiempo de espera de la comunicación con el controlador o dispositivo. Intente nuevamente.

"BMC busy" - El BMC está ocupado actualmente. Puede estar procesando información o tener demasiadas sesiones simultáneas para gestionarlas. Espere e intente nuevamente.

"could not find inband device" - No se pudo encontrar un dispositivo en banda. Verifique la configuración o especifique un dispositivo o controlador específico en la línea de comandos.

"driver timeout" - El controlador en banda ha agotado el tiempo de espera de la comunicación con el BMC local o el procesador de servicio. El BMC o el procesador de servicio pueden estar ocupados o (en el peor de los casos) posiblemente no funcionen.

"internal IPMI error" - Se ha producido un error de IPMI que FreeIPMI no sabe cómo manejar. Envíe un correo electrónico a <freeipmi-users@gnu.org> para informar el problema.

SOLUCIONES_ALTERNATIVAS

Con tantos fabricantes implementando sus propias soluciones IPMI, diferentes fabricantes pueden implementar sus protocolos IPMI incorrectamente. Lo siguiente describe una serie de soluciones alternativas actualmente disponibles para manejar los problemas de cumplimiento descubiertos. Siempre que sea posible, las soluciones alternativas se han implementado para que sean transparentes para el usuario. Sin embargo, algunas requerirán que el usuario especifique que se use una solución alternativa a través de la opción -W.

El hardware listado a continuación puede indicar solo el hardware en el que se descubrió un problema. Las versiones más nuevas de hardware pueden corregir los problemas indicados a continuación. Máquinas similares de diferentes fabricantes pueden o no presentar los mismos problemas. Diferentes fabricantes pueden licenciar su firmware del mismo desarrollador de firmware IPMI, por lo que puede valer la pena probar las soluciones alternativas que se enumeran a continuación, incluso si su placa base no está listada.

Si cree que su hardware tiene un problema de cumplimiento adicional que requiere una solución alternativa, comuníquese con los mantenedores de FreeIPMI en <freeipmi-users@gnu.org> o <freeipmi-devel@gnu.org>.

assumeio - Esta bandera de solución alternativa asumirá que las interfaces inband se comunican con la E/S del sistema en lugar de mapearse en memoria. Esto solucionará sistemas que informan direcciones base inválidas. Aquellos que experimenten este problema pueden ver errores como "dispositivo no soportado" o "no se pudo encontrar dispositivo inband". Problema observado en HP ProLiant DL145 G1.

spinpoll - Esta bandera de solución alternativa indicará a algunos controladores inband (en particular, el controlador KCS) que giren mientras consultan en lugar de poner el proceso a dormir. Esto puede mejorar significativamente el tiempo de ejecución del reloj de pared de las herramientas, ya que la granularidad del planificador del sistema operativo puede ser mucho mayor que el tiempo necesario para realizar una única transacción de mensaje IPMI. Sin embargo, al girar, su sistema puede estar realizando menos trabajo útil al no cambiar el contexto de la herramienta para una tarea más útil.

authcap - Esta bandera de solución alternativa omitirá las comprobaciones tempranas de las capacidades del nombre de usuario, las capacidades de autenticación y el soporte K_g, y permitirá que la autenticación IPMI tenga éxito. Soluciona múltiples problemas en los que el sistema remoto no informa correctamente las capacidades del nombre de usuario, las capacidades de autenticación o el estado K_g. Aquellos que experimenten este problema pueden ver errores como "nombre de usuario inválido", "tipo de autenticación no disponible para el nivel de privilegio intentado" o "k_g inválido". Problema observado en Asus P5M2/P5MT-R/RS162-E4/RX4, Intel SR1520ML/X38ML y Sun Fire 2200/4150/4450 con ELOM.

nochecksumcheck - Esta bandera de solución alternativa indicará a FreeIPMI que no verifique las sumas de verificación devueltas por las respuestas de los comandos IPMI. Soluciona sistemas que devuelven sumas de verificación inválidas debido a errores de implementación, pero el paquete es válido de lo contrario. Se advierte a los usuarios sobre el uso de esta opción, ya que elimina la validación de la integridad del paquete en una serie de circunstancias. Sin embargo, es poco probable que sea un problema en la mayoría de las situaciones. Aquellos que experimenten este problema pueden ver errores como "tiempo de espera de conexión", "tiempo de espera de sesión" o "tiempo de espera de verificación de contraseña". En conexiones IPMI 1.5, la solución alternativa "noauthcodecheck" también puede ser necesaria. Problema observado en Supermicro X9SCM-iiF, Supermicro X9DRi-F y Supermicro X9DRFR.

idzero - Esta bandera de solución alternativa permitirá que los identificadores de sesión vacíos sean aceptados por el cliente. Soluciona sesiones IPMI que informan identificadores de sesión vacíos al cliente. Aquellos que experimenten este problema pueden ver errores de "tiempo de espera de sesión". Problema observado en Tyan S2882 con BMC M3289.

unexpectedauth - Esta bandera de solución alternativa permitirá que los códigos de autenticación no nulos inesperados se verifiquen como si fueran esperados. Soluciona un problema en el que los paquetes contienen datos de autenticación no nulos cuando deberían ser nulos debido a la desactivación de la autenticación por mensaje. Aquellos que experimenten este problema pueden ver errores de "tiempo de espera de sesión". Problema observado en Dell PowerEdge 2850, SC1425. Confirmado que se corrigió en firmware más reciente.

forcepermsg - Esta bandera de solución alternativa forzará el uso de la autenticación por mensaje, sin importar lo que anuncie el sistema remoto. Soluciona un problema en el que la autenticación por mensaje se anuncia como deshabilitada en el sistema remoto, pero en realidad es requerida por el protocolo. Aquellos que experimenten este problema pueden ver errores de "tiempo de espera de sesión". Problema observado en IBM eServer 325.

endianseq - Esta bandera de solución alternativa invertirá el endianness de los números de secuencia de sesión para permitir que la sesión continúe correctamente. Soluciona números de secuencia IPMI 1.5 que tienen el endianness incorrecto. Aquellos que experimenten este problema pueden ver errores de "tiempo de espera de sesión". Problema observado en algunos Sun ILOM 1.0/2.0 (depende del endianness del procesador de servicio).

noauthcodecheck - Esta bandera de solución alternativa indicará a FreeIPMI que no verifique los códigos de autenticación devueltos por las respuestas de los comandos IPMI 1.5. Soluciona sistemas que devuelven códigos de autenticación inválidos debido a errores de hash o implementación. Se advierte a los usuarios sobre el uso de esta opción, ya que elimina una verificación de autenticación que verifica la validez de un paquete. Sin embargo, en la mayoría de las organizaciones, es poco probable que sea un problema de seguridad. Aquellos que experimenten este problema pueden ver errores como "tiempo de espera de conexión", "tiempo de espera de sesión" o "tiempo de espera de verificación de contraseña". Problema observado en Xyratex FB-H8-SRAY, Intel Windmill, Quanta Winterfell y Wiwynn Windmill.

intel20 - Esta bandera de solución alternativa solucionará varios problemas de autenticación IPMI 2.0 de Intel. Los problemas cubiertos incluyen el relleno de nombres de usuario y la truncación de contraseñas si el algoritmo de autenticación es HMAC-MD5-128. Aquellos que experimenten este problema pueden ver errores como "nombre de usuario inválido", "contraseña inválida" o "k_g inválido". Problema observado en Intel SE7520AF2 con Intel Server Management Module (Professional Edition).

supermicro20 - Esta bandera de solución alternativa solucionará varios problemas de autenticación IPMI 2.0 de Supermicro en placas base con firmware IPMI Peppercon. Los problemas cubiertos incluyen el manejo de códigos de autenticación de longitud inválida. Aquellos que experimenten este problema pueden ver errores de "contraseña inválida". Problema observado en Supermicro H8QME con tarjeta hija SIMSO. Confirmado que se corrigió en firmware más reciente.

sun20 - Esta bandera de solución alternativa solucionará varios problemas de autenticación IPMI 2.0 de Sun. Los problemas cubiertos incluyen claves hash de longitud inválida, claves con hash incorrecto y registros de cifrado inválidos. Aquellos que experimenten este problema pueden ver errores como "contraseña inválida" o "error bmc". Problema observado en Sun Fire 4100/4200/4500 con ILOM. Esta solución alternativa incluye automáticamente la solución alternativa "opensesspriv".

opensesspriv - Esta bandera de solución alternativa alterará ligeramente el protocolo de conexión IPMI 2.0 de FreeIPMI para solucionar un algoritmo de hash inválido utilizado por el sistema remoto. El nivel de privilegio enviado durante la etapa de Apertura de Sesión de una conexión IPMI 2.0 se utiliza para hashear claves en lugar del nivel de privilegio enviado durante la etapa de conexión RAKP1. Aquellos que experimenten este problema pueden ver errores como "contraseña inválida", "k_g inválido", "código de estado rmcpplus erróneo" o "no se puede obtener el nivel de privilegio para este usuario". Problema observado en Sun Fire 4100/4200/4500 con ILOM, Inventec 5441/Dell Xanadu II, Supermicro X8DTH, Supermicro X8DTG, Intel S5500WBV/Penguin Relion 700, Intel S2600JF/Appro 512X, Quanta QSSC-S4R/Appro GB812X-CN, Dell C5220 y el BMC de software OpenIPMI. Esta solución alternativa se activa automáticamente con la solución alternativa "sun20".

integritycheckvalue - Esta bandera de solución alternativa solucionará un valor de verificación de integridad inválido durante el establecimiento de una sesión IPMI 2.0 cuando se utiliza el ID de conjunto de cifrado 0. El valor de verificación de integridad debe ser de longitud 0, sin embargo, la placa base remota responde con un campo no vacío. Aquellos que experimenten este problema pueden ver errores de "k_g inválido". Problema observado en Supermicro X8DTG, Supermicro X8DTU e Intel S5500WBV/Penguin Relion 700, e Intel S2600JF/Appro 512X.

Sin Soporte IPMI 1.5 - Se ha descubierto que algunas placas base que admiten IPMI 2.0 no admiten IPMI 1.5. Aquellos que experimenten este problema pueden ver errores como "ipmi 2.0 no disponible" o "tiempo de espera de conexión". Este problema se puede solucionar utilizando IPMI 2.0 en lugar de IPMI 1.5 especificando --driver-type=LAN_2_0. Problema observado en varias placas base HP y Supermicro.

EJEMPLOS

# ipmi-chassis --get-status

Obtener el estado del chasis de la máquina local.

# ipmi-chassis -h ahost -u miusuario -p micontraseña --get-status

Obtener el estado del chasis de una máquina remota utilizando IPMI sobre LAN.

# ipmi-chassis -h mi-cluster[0-127] -u miusuario -p micontraseña --get-status

Obtener el estado del chasis en un clúster utilizando IPMI sobre LAN.

# ipmi-chassis -h ahost -u miusuario -p micontraseña --chassis-control=POWER-UP

Encender una máquina remota utilizando IPMI sobre LAN.

DIAGNOSTICO

Tras una ejecución exitosa, el estado de salida es 0. En caso de error, el estado de salida es 1.

Si se especifican varios hosts para la comunicación, el estado de salida es 0 si y solo si todos los objetivos se ejecutan correctamente. De lo contrario, el estado de salida es 1.

PROBLEMAS_CONOCIDOS

En sistemas operativos más antiguos, si introduce su nombre de usuario, contraseña y otra información potencialmente relevante para la seguridad en la línea de comandos, esta información puede ser descubierta por otros usuarios al usar herramientas como el comando ps(1) o al mirar en el sistema de archivos /proc. Generalmente, es más seguro ingresar la información de la contraseña con opciones como -P o -K. Configurar la información relevante para la seguridad en el archivo de configuración de FreeIPMI también sería una forma apropiada de ocultar esta información.

Para prevenir ataques de fuerza bruta, algunos BMC se "bloquearán" temporalmente después de un número de errores de autenticación remota. Es posible que deba esperar un tiempo para que este "bloqueo" temporal pase antes de poder autenticarse nuevamente.
