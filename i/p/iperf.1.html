Les mesures de latence incluent à la fois le délai monodirectionnel (OWD) et les temps d'aller-retour (RTT.) Iperf peut utiliser à la fois des sockets TCP et UDP (ou protocoles.) Il prend en charge le trafic unidirectionnel, en duplex intégral (même socket) et bidirectionnel, et prend en charge plusieurs flux de trafic simultanés. Il prend en charge le trafic multicast y compris les adhésions au multicast spécifique à la source (SSM). Sa conception multi-thread permet des performances maximales. Les métriques affichées aident à caractériser les performances réseau d'hôte à hôte. Le réglage de l'option améliorée (-e) fournit toutes les métriques disponibles. Remarque : les métriques sont au niveau des lectures et écritures de socket. Elles n'incluent pas le surcoût associé aux en-têtes des couches de protocole de niveau inférieur. El **enlace** se realiza en el nivel lógico del puerto y la dirección IP (o capa 3) utilizando la opción -B y dos puntos como separador entre el puerto y la dirección IP. El enlace a nivel de dispositivo (o capa 2) requiere el signo de porcentaje (%) como delimitador (tanto para el cliente como para el servidor). Un ejemplo de puerto de origen y dirección IP es -B 192.168.1.1:6001. Para **enlazar solo el puerto de origen** y dejar que el sistema operativo elija la dirección IP de origen, use 0.0.0.0, por ejemplo, **-B 0.0.0.0:6001**. En el cliente, la opción -B afecta a la llamada del sistema bind(2), y establecerá la dirección IP de origen y el puerto de origen, por ejemplo, iperf -c <host> -B 192.168.100.2:6002. Esto controla los valores de origen del paquete, pero no el enrutamiento. Esto puede ser confuso, ya que una búsqueda de ruta o dispositivo puede no ser la del dispositivo con la IP de origen configurada. Por lo tanto, por ejemplo, si la dirección IP de eth0 se utiliza para -B y la tabla de enrutamiento para la dirección IP de destino resuelve la interfaz de salida como eth1, entonces el host enviará el paquete por el dispositivo eth1 mientras usa la dirección IP de origen de eth0 en el paquete. Para afectar la interfaz de salida física (por ejemplo, sistemas de doble conexión), use -c <host>%<dev> (requiere root), que omite la búsqueda en la tabla de enrutamiento del host, o configure el enrutamiento de políticas por cada dirección de origen -B y establezca la interfaz de salida apropiadamente en las rutas de políticas. En el servidor o en la recepción, solo se recibirán los paquetes destinados a la dirección IP -B. También es útil para multidifusión. Por ejemplo, iperf -s -B 224.0.0.1**%eth0** solo aceptará paquetes de multidifusión IP con IP de destino 224.0.0.1 que se reciban en la interfaz eth0, mientras que iperf -s -B 224.0.0.1 recibirá esos paquetes en cualquier interfaz. Finalmente, el especificador de dispositivo es necesario para la v6 link-local, por ejemplo, -c [v6addr]%<dev> -V, para seleccionar la interfaz de salida.

Inversión, dúplex completo, doble prueba (-d) y compensación (-r): Las opciones **--reverse** (-R) y **--full-duplex** pueden ser confusas en comparación con las opciones más antiguas **--dualtest (-d)** y **--tradeoff (-r)**. Las opciones más nuevas **--reverse** y **--full-duplex** solo abren un socket y leen y escriben en el **mismo descriptor de socket**, es decir, utilizan el socket en modo dúplex completo. Los antiguos -d y -r abren segundos sockets en la dirección opuesta y no utilizan un socket en modo dúplex completo. Tenga en cuenta que el dúplex completo se aplica al socket y no a los dispositivos de red, y que los sistemas operativos admiten sockets dúplex completos independientemente de si la red subyacente admite transmisión y recepción dúplex completas. Se **sugiere usar --reverse** si desea **probar a través de un firewall NAT** (o -R en sistemas que no sean Windows). Esto aplica una inversión de roles de la prueba después de abrir el socket dúplex completo. (Nota: puede ser necesario eludir el firewall para usar -d y -r si hay una puerta de enlace NAT en el camino).

Además, la configuración --reverse -b <rate> se comporta de manera diferente para TCP y UDP. Para TCP, limitará la tasa del lado de lectura, es decir, el cliente iperf (con el rol invertido para actuar como servidor) leyendo del socket dúplex completo. Esto, a su vez, controlará el flujo del tráfico inverso según el control de congestión TCP estándar. El --reverse -b <rate> se aplicará en la transmisión (es decir, el servidor con el rol invertido para actuar como cliente) para UDP, ya que no hay control de flujo con UDP. No hay opción para limitar directamente las escrituras con pruebas TCP al usar --reverse.

Rebote (Bounceback): La prueba de rebote permite medir la capacidad de respuesta de la red (que, en esta prueba, es inversamente proporcional a la latencia). Las unidades son respuestas por segundo o rps. La latencia es simplemente el retraso en unidades de tiempo. Las métricas de latencia requieren conocer el retraso de lo que se está midiendo. Para el rebote, es una escritura del cliente a una lectura del servidor seguida de una escritura del servidor y luego una lectura del cliente. La escritura original es rebotada. Iperf 2 configura el socket con TCP_NODELAY y posiblemente TCP_QUICKACK (a menos que se deshabilite). El cliente envía una escritura pequeña (que por defecto es de 100 bytes a menos que se establezca -l) y emite una lectura esperando el "rebote" del servidor. El servidor espera una lectura y luego, opcionalmente, se demora antes de enviar la carga útil. Esto se repite hasta que finaliza el tráfico. Los resultados se muestran en unidades de rps y retrasos de tiempo.

La opción de socket TCP_QUICKACK se habilitará durante las pruebas de rebote cuando el rebote-espera se establezca en un valor distinto de cero. La opción de socket se aplica después de cada read() en el servidor y antes de la llamada de retraso de espera. También se aplica en el cliente. Use --bounceback-no-quickack para que TCP se ejecute en modo predeterminado según el socket (que lo más probable es que sea TCP_QUICKACK desactivado).

Detecciones de reloj no sincronizado con --bounceback y --trip-times (a partir del 19 de marzo de 2023): Iperf 2 puede detectar cuando los relojes tienen errores de sincronización mayores que el RTT de rebote. Esto se hace a través de la marca de tiempo de envío del cliente (reloj A), la marca de tiempo de recepción del servidor (reloj B) y la marca de tiempo de recepción final del cliente (reloj A). La verificación, realizada en cada rebote, es write(A) < read(B) < read(A). Esto es compatible con las pruebas de rebote con un ligero ajuste: clock write(A) < clock read(B) < clock read(A) - (clock write(B) - clock read(B)). Todas las marcas de tiempo se muestrean en la escritura o lectura inicial (no en la finalización). El error de salida se muestra como se indica a continuación y no hay salida para un valor cero.

Tiempos de conexión TCP: El tiempo de conexión TCP (o apretón de manos de tres vías) se puede ver en el cliente iperf cuando se establece la opción -e (--enhanced). Busque ct=<valor> en el mensaje conectado, por ejemplo, en '[ 3] local 192.168.1.4 port 48736 connected with 192.168.1.1 port 5001 **(ct=1.84 ms)**' que muestra que el 3WHS tomó 1.84 milissegundos.

Rango de puertos (Port-range): Se admiten rangos de puertos utilizando la notación de guion, por ejemplo, 6001-6009. Esto provocará múltiples hilos, uno por puerto, en el oyente/servidor o en el cliente. El usuario debe asegurarse de que los puertos en el rango de puertos estén disponibles y no en uso por el sistema operativo. La opción -P es compatible en el cliente y se aplicará a cada puerto de destino dentro del rango de puertos. Finalmente, esto se puede utilizar como solución para UDP en Windows y -P > 1, ya que Windows no distribuye UDP según la conexión del servidor y el quinteto.

Cálculo de paquetes por segundo (pps): El cálculo de paquetes por segundo se realiza como una derivada, es decir, número de paquetes dividido por el tiempo. El tiempo se toma desde el último paquete anterior hasta el último paquete actual. No es el tiempo del intervalo de muestra. El último paquete puede caer en momentos diferentes dentro de un intervalo. Esto significa que los pps no tienen que coincidir con los bytes rx divididos por el intervalo de muestra. Además, con --trip-times activado, la hora del paquete al recibir se establece por la hora de escritura del remitente, por lo que los pps indican los pps de extremo a extremo con --trip-times. El cálculo de pps RX es solo del lado de recepción cuando se establece -e y no se establece --trip-times.

Ley de Little: En la teoría de colas, la ley de Little es un teorema que determina el número promedio de elementos (L) en un sistema de colas estacionario basándose en el tiempo de espera promedio (W) de un elemento dentro de un sistema y el número promedio de elementos que llegan al sistema por unidad de tiempo (lambda). Matemáticamente, L = lambda * W. Tal como se utiliza aquí, las unidades son bytes. La tasa de llegada se toma de las escrituras.

Potencia de red (Network power): La métrica de potencia de red (NetPwr) es **experimental**. Es una función de conveniencia definida como rendimiento/retraso. Para transmisiones TCP, el retraso son los tiempos de RTT muestreados. Para recepciones TCP, el retraso es la latencia de escritura a lectura. Para UDP, el retraso es la latencia de extremo a extremo. No confunda esto con la definición física de potencia (delta energía/delta tiempo), sino más bien como una medida de una propiedad deseable dividida por una propiedad indeseable. Tenga en cuenta también que debe usar -i intervalo con TCP para obtener esto, ya que eso establece la tasa de muestreo de RTT. La métrica se escala para facilitar la legibilidad humana.

Multidifusión (Multicast): Iperf 2 admite multidifusión con un par de advertencias. Primero, las transmisiones de multidifusión no pueden aprovechar la opción -P. El servidor serializará las transmisiones de multidifusión. Además, se recomienda encarecidamente utilizar -t en un servidor que se utilizará para clientes de multidifusión. Esto se debe a que el paquete único de fin de tráfico enviado desde el cliente al servidor puede perderse y no hay paquetes de fin de tráfico redundantes. Establecer -t en el servidor matará el hilo del servidor en caso de que este paquete se pierda.

TCP_QUICKACK: La opción de socket TCP_QUICKACK se aplicará después de cada read() en el servidor, de modo que los ACKs TCP se envíen inmediatamente, en lugar de poder retrasarse.

NOTAS

La opción -u está diseñada para pruebas de rendimiento UDP y no para pruebas de rendimiento TCP que utilizan UDP. La mayoría de los routers y firewalls están optimizados para el tráfico TCP. El tráfico UDP puede ser descartado o acelerado por los dispositivos de red para simular el tráfico de Internet.

El uso de -l y -b con opciones de tiempo (como -t o -n) puede dar resultados inesperados con ciertas combinaciones. Por ejemplo, establecer -l a un valor muy grande en modo UDP podría agotar la memoria del búfer del kernel y devolver un error.

El modo UDP puede utilizar más ancho de banda del que se solicita si el receptor no puede seguir el ritmo. Esto es normal y se debe a que iperf está enviando paquetes UDP a la tasa solicitada, pero los paquetes se agrupan en el búfer del receptor y se procesan juntos, lo que provoca un pico de ancho de banda.

Se recomienda utilizar la opción -y para registrar los tiempos de los informes. Útil para muestreo sub-milisegundo.
