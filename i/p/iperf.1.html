DESCRIPCIÓ

N

iperf 2 es una herramienta de pruebas que realiza mediciones de tráfico de red utilizando sockets de red. Las métricas de rendimiento soportadas incluyen rendimiento y latencia (o capacidad del enlace y capacidad de respuesta.) Las mediciones de latencia incluyen tanto el retraso de ida (OWD) como los tiempos de ida y vuelta (RTTs.) Iperf puede usar tanto sockets TCP como UDP (o protocolos.) Soporta tráfico unidireccional, dúplex completo (mismo socket) y bidireccional, y soporta múltiples flujos de tráfico simultáneos. Soporta tráfico multicast incluyendo uniones a multicast específico de fuente (SSM). Su diseño multihilo permite un rendimiento máximo. Las métricas mostradas ayudan a caracterizar el rendimiento de red de host a host. Establecer la opción mejorada (-e) proporciona todas las métricas disponibles. Nota: las métricas son a nivel de lecturas y escrituras de socket. No incluyen la sobrecarga asociada con los encabezados de capas de protocolo de nivel

inferior.

El usuario debe establecer tanto un servidor (para recibir tráfico) como un cliente (pa

ra generar y enviar tráfico) para que se produzca una prueba. El cliente y el servidor
típicamente están en diferentes hosts o computadoras pero no es necesario que lo estén.

Opciones numéricas: Algunas opciones numéricas admiten caracteres de formato según '<valor>c' (p. ej. 10M) donde los c caracteres de formato son k,m,g,K,M,G. Los caracteres de formato en minúscula se basan en 10^3 y los de mayúscula en 2^n, p. ej. 1k = 1000, 1K = 1024, 1m = 1,000,000 y 1M = 1,048,

576

Limitación de tasa: La opción -b admite la limitación de tasa de lectura y escritura a nivel de aplicación. La opción -b en el cliente también admite cargas ofrecidas variables a través del formato <media>,<desviación estándar>, p. ej. -b 100m,10m. La distribución utilizada es logarítmico-normal. Similar para la opción isócrona. La -b en el servidor limita la tasa de las lecturas. También se admite la regulación basada en socket usando la opción larga --fq-rate. Esto funcionará también con las opciones --reverse y

--full-duplex.

IP tos y dscp: Especifica el tipo de servicio o la clase DSCP para las conexiones. Los valores aceptados son af11, af12, af13, af21, af22, af23, af31, af32, af33, af41, af42, af43, cs0, cs1, cs2, cs3, cs4, cs5, cs6, cs7, ef, le, nqb, nqb2, ac_be, ac_bk, ac_vi, ac_vo, lowdelay, throughput, reliability, un valor numérico, o none para usar el valor predeterminado del sistema operativo. Los valores ac_xx son las cuatro categorías de acceso definidas en WMM para Wi-Fi, y son alias de valores DSCP que se mapearán a las ACs correspondientes bajo la suposición de que el dispositivo usa la tabla de mapeo DSCP-a-UP especificada en IETF RFC

8325.

Se puede establecer el byte tos usando:
--dscp en el cliente
--tos o -S en el cliente o el servidor, aunque la configuración del lado del servidor tiene advertencias (véase el siguiente punto)
--tos-override para el tráfico invertido del lado del servidor (el caso de uso es para blanquear la ruta de

retorno)

El valor --dscp en el cliente es simplemente una comodidad en la que el usuario puede establecer los seis bits del campo dscp en lugar de establecer el byte tos. El --tos-override permite probar la función de TOS reflejado de los puntos de acceso (AP). Esto es cuando la red blanquea la configuración tos del lado del cliente y el tráfico inverso no tendrá entonces ninguna configuración TOS. Se espera que el AP aplique el TOS del tráfico ascendente al tráfico inverso. El caso de uso es que el --tos-overide sería cero simulando el blanqueo de red del byte tos. Si no hay configuración --tos, entonces setsockopt nunca se llamarán y se usarán los valores predeterminados

.

--trip-times La opción --trip-times habilita muchas métricas de retardo de ida y vuelta (OWD). Tenga en cuenta también que usar --trip-times en un cliente TCP hará que --tcp-write-prefetch se establezca en un valor pequeño si tcp-write-prefetch no se ha establecido también. Esto se hace para reducir la latencia de hinchazón del lado de envío (que no está relacionada con la latencia inducida por la red.) Establezca --tcp-write-prefetch en cero para desactivar esto (lo que desactivará TCP_NOTSENT_LOWAT) y permitirá la hinchazón del lado de

envío.

Relojes sincronizados: La opción --trip-times indica que los relojes del cliente y del servidor están sincronizados a una referencia común. El Protocolo de Tiempo de Red (NTP) o el Protocolo de Tiempo de Precisión (PTP) se usan comúnmente para esto. El error del reloj de referencia y los protocolos de sincronización afectarán la precisión de cualquier medición de latencia de extremo a extremo. Véase la sección de NOTAS de bounceback sobre las detecciones de relojes no

sincronizados

Histogramas y estadísticas no paramétricas: La opción --histograms proporciona los datos brutos donde nada se promedia. Esto es útil para distribuciones no paramétricas, p. ej. latencia. La salida estándar sí usa el teorema del límite central para producir promedio, mínimo, máximo y variación. Esto pierde información cuando la distribución subyacente no es Gaussiana. Se admiten histogramas para que esta información esté

disponible.
