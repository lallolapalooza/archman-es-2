DESCRIPCIÓ

N

Ipmi-oem se utiliza para ejecutar comandos IPMI específicos de OEM. Está destinado a proporcionar una mejor interfaz de usuario para comandos IPMI específicos de OEM en lugar de usar ipmi-raw(8). Consulte OEM IDS Y COMANDOS SOPORTADOS más abajo para obtener una lista de comandos IPMI específicos de OEM compatibles. También se puede generar una lista de comandos específicos de OEM compatibles usando la opción --list. No hay garantías de que los comandos OEM a continuación funcionen en una placa base en particular. Las extensiones OEM pueden o no existir en revisiones de hardware y/o revisiones de firmware específicas de las placas base. Las extensiones pueden o no funcionar para otras líneas de placas base del mismo

fabricante.

A continuación se enumeran las opciones IPMI generales, las opciones específicas de la herramienta, la información de resolución de problemas, la información de soluciones alternativas, ejemplos y problemas conocidos. Para una introducción general a FreeIPMI, consulte free

ipmi
(7).

CONNECTION OPTIONS

These options control how the tool connects to the target IPMI interface.

Specify the hostname or IP address of the target system to connect to. If not specified, the tool will attempt to use 'localhost' or the system's default IPMI host.

SDR CACHE OPTIONS

This tool requires access to the sensor data repository (SDR) cache for general operation. By default, SDR data will be downloaded and cached on the local machine. The following options apply to the SDR cache.

--flush-cache
Flush a cached version of the sensor data repository (SDR) cache. The SDR is typically cached for faster subsequent access. However, it may need to be flushed and re-generated if the SDR has been updated on a system.
--quiet-cache
Do not output information about cache creation/deletion. May be useful in scripting.
--sdr-cache-recreate
If the SDR cache is out of date or invalid, automatically recreate the sensor data repository (SDR) cache. This option may be useful for scripting purposes.
--sdr-cache-file=FILE
Specify a specific sensor data repository (SDR) cache file to be stored or read from. If this option is used when multiple hosts are specified, the same SDR cache file will be used for all hosts.
--sdr-cache-directory=DIRECTORY
Specify an alternate directory for sensor data repository (SDR) caches to be stored or read from. Defaults to the home directory if not specified.

TIME OPTIONS

By IPMI definition, all IPMI times and timestamps are stored in localtime. However, in many situations, the timestamps will not be stored in localtime. Whether or not a system truly stored the timestamps in localtime varies on many factors, such as the vendor, BIOS, and operating system. The following options will allow the user to adjust the interpretation of the stored timestamps and how they should be output.

--utc-to-localtime
Assume all times are reported in UTC time and convert the time to localtime before being output.
--localtime-to-utc
Convert all localtime timestamps to UTC before being output.
--utc-offset=SECONDS
Specify a specific UTC offset in seconds to be added to timestamps. Value can range from -86400 to 86400 seconds. Defaults to 0.

HOSTRANGED OPTIONS

The following options manipulate hostranged output. See HOSTRANGED SUPPORT below for additional information on hostranges.

-B, --buffer-output
Buffer hostranged output. For each node, buffer standard output until the node has completed its IPMI operation. When specifying this option, data may appear to output slower to the user since the the entire IPMI operation must complete before any data can be output. See HOSTRANGED SUPPORT below for additional information.
-C, --consolidate-output
Consolidate hostranged output. The complete standard output from every node specified will be consolidated so that nodes with identical output are not output twice. A header will list those nodes with the consolidated output. When this option is specified, no output can be seen until the IPMI operations to all nodes has completed. If the user breaks out of the program early, all currently consolidated output will be dumped. See HOSTRANGED SUPPORT below for additional information.
-F NUM, --fanout=NUM
Specify multiple host fanout. A "sliding window" (or fanout) algorithm is used for parallel IPMI communication so that slower nodes or timed out nodes will not impede parallel communication. The maximum number of threads available at the same time is limited by the fanout. The default is 64.
-E, --eliminate
Eliminate hosts determined as undetected by ipmidetect. This attempts to remove the common issue of hostranged execution timing out due to several nodes being removed from service in a large cluster. The ipmidetectd daemon must be running on the node executing the command.
--always-prefix
Always prefix output, even if only one host is specified or communicating in-band. This option is primarily useful for scripting purposes. Option will be ignored if specified with the -C option.

SOPORTE DE

HOSTRANGED

Se pueden introducir múltiples hosts ya sea como listas explícitas de hosts separadas por comas o como un rango de nombres de host en la forma general: prefix[n-m,l-k,...], donde n < m y l < k, etc. La última forma no debe confundirse con las clases de caracteres de expresiones regulares (también denotadas por []). Por ejemplo, foo[19] no representa foo1 o foo9, sino que representa un rango degenerado:

foo19.

Esta sintaxis de rango está destinada solo como una conveniencia en clústeres con una convención de nombres prefixNN y la especificación de rangos no debe considerarse necesaria -- la lista foo1,foo9 podría especificarse como tal, o mediante el rango foo[1,9]

.

A continuación se muestran algunos ejemplos de uso de

rangos: 
    foo[01-05] en lugar de foo01,foo02,foo03,foo04,foo05
    foo[7,9-10] en lugar de foo7,foo9,foo10
    foo[0-3] en lugar de foo0,foo1,foo2,
foo3

Como recordatorio para el lector, algunos intérpretes de comandos interpretarán los corchetes ([ y ]) para la coincidencia de patrones. Dependiendo de su intérprete de comandos, puede ser necesario encerrar las listas de rangos entre

comillas.

Cuando el usuario especifica múltiples hosts, se ejecutará un hilo para cada host en paralelo hasta la dispersión configurada (que se puede ajustar a través de la opción -F). Esto permitirá la comunicación con un gran número de nodos mucho más rápidamente que si se hiciera en

serie.

De forma predeterminada, la salida estándar de cada nodo especificado se mostrará con el nombre de host antepuesto a cada línea. Aunque esta salida es legible en muchas situaciones, puede ser difícil de leer en otras situaciones. Por ejemplo, la salida de múltiples nodos puede mezclarse. Las opciones -B y -C se pueden utilizar para cambiar este comportamiento

predeterminado.

Se utilizará la comunicación IPMI in-band cuando se

especifica el host "localhost". Esto permite al usu
ario añadir el localhost a la salida de hostranged.

SOLUCIÓN DE PROBLEMAS

GENERAL

La mayoría de las veces, los problemas de IPMI se deben a problemas de

configuración.

Los problemas de IPMI sobre LAN implican una configuración incorrecta del BMC de la máquina remota. Verifique dos veces para asegurarse de que lo siguiente esté configurado correctamente en el BMC de la máquina remota: dirección IP, dirección MAC, máscara de subred, nombre de usuario, habilitación de usuario, privilegio de usuario, contraseña, privilegio LAN, habilitación LAN y tipo(s) de autenticación permitidos. Para conexiones IPMI 2.0, verifique dos veces para asegurarse de que los privilegios de la suite de cifrado y la clave K_g estén configurados correctamente. La herramienta ipmi-config(8) se puede utilizar para verificar y/o cambiar estos ajustes de

configuración.

Los problemas de IPMI in-band típicamente son causados por controladores mal configurados o BMCs no

estándar.

Además de los consejos de solución de problemas a continuación, consulte SOLUCIONES ALTERNATIVAS a continuación para ver también si se han descubierto y solucionado errores específicos del

proveedor.

A continuación se enumeran muchos de los problemas comunes para los mensajes de error. Para soporte adicional, por favor envíe un correo electrónico a la lista de correo <freeipmi-users@gnu.org>

.

"username invalid" - El nombre de usuario introducido (o un nombre de usuario NULL si no se introdujo ninguno) no está disponible en la máquina remota. También es posible que la configuración del nombre de usuario del BMC remoto sea

incorrecta.

"password invalid" - La contraseña introducida (o una contraseña NULL si no se introdujo ninguna) no es correcta. También es posible que la contraseña del usuario no esté configurada correctamente en el BMC

remoto.

"password verification timeout" - La verificación de la contraseña ha agotado el tiempo de espera. Ocurrió un error "password invalid" (descrito arriba) o un "session timeout" genérico (descrito a continuación). En este punto del protocolo no se puede diferenciar cuál

ocurrió.

"k_g invalid" - La clave K_g introducida (o una clave K_g NULL si no se introdujo ninguna) no es correcta. También es posible que la clave K_g no esté configurada correctamente en el BMC

remoto.

"privilege level insufficient" - Un comando IPMI requiere un privilegio de usuario más alto que el con el que se autenticó. Por favor, intente autenticarse con un privilegio más alto. Esto puede requerir autenticarse con un usuario diferente que tenga un privilegio máximo más

alto.

"privilege level cannot be obtained for this user" - El nivel de privilegio con el que intenta autenticarse es más alto que el máximo permitido para este usuario. Por favor, intente de nuevo con un privilegio más bajo. También es posible que el nivel de privilegio máximo permitido para un usuario no esté configurado correctamente en el BMC

remoto.

"authentication type unavailable for attempted privilege level" - El tipo de autenticación con el que desea autenticarse no estáot disponible para este nivel de privilegio. Inténtelo de nuevo con un tipo de autenticación alternativo o un nivel de privilegio alternativo. También es posible que los tipos de autenticación disponibles con los que puede autenticarse no estén configurados correctamente en el BMC remoto.

"cipher suite id unavailable" - El ID de la suite de cifrado con el que desea autenticarse no está disponible en el BMC remoto. Inténtelo de nuevo con un ID de suite de cifrado alternativo. También es posible que los IDs de suite de cifrado disponibles no estén configurados correctamente en el BMC remoto.

"ipmi 2.0 unavailable" - No se detectó IPMI 2.0 en la máquina remota. Intente usar IPMI 1.5 en su lugar.

"connection timeout" - Falló la comunicación inicial de IPMI. Es posible una serie de errores potenciales, que incluyen un nombre de host no válido especificado, una dirección IP de IPMI que no se puede resolver, IPMI no habilitado en el servidor remoto, una conexión de red mala, etc. Verifique la configuración y la conectividad.

"session timeout" - La sesión de IPMI ha expirado. Vuelva a conectarse. Si este error ocurre con frecuencia, es posible que desee aumentar el tiempo de espera de retransmisión. Algunos BMC remotos son considerablemente más lentos que otros.

"device not found" - No se pudo encontrar el dispositivo especificado. Verifique la configuración o las entradas e intente de nuevo.

"driver timeout" - Ha expirado el tiempo de espera de la comunicación con el controlador o dispositivo. Intente de nuevo.

"message timeout" - Ha expirado el tiempo de espera de la comunicación con el controlador o dispositivo. Intente de nuevo.

"BMC busy" - El BMC está ocupado actualmente. Puede estar procesando información o tener demasiadas sesiones simultáneas para gestionarlas. Espere e intente de nuevo.

"could not find inband device" - No se pudo encontrar un dispositivo inband. Verifique la configuración o especifique un dispositivo o controlador específico en la línea de comandos.

"driver timeout" - El controlador inband ha expirado comunicándose con el BMC local o el procesador de servicio. El BMC o el procesador de servicio pueden estar ocupados o (en el peor de los casos) posiblemente no funcionen.

SOLUCIONES

Con tantos proveedores diferentes implementando sus propias soluciones IPMI, diferentes proveedores pueden implementar sus protocolos IPMI incorrectamente. La siguiente descripción detalla una serie de soluciones disponibles actualmente para manejar los problemas de cumplimiento detectados. Cuando sea posible, las soluciones se han implementado para que sean transparentes para el usuario. Sin embargo, algunas requerirán que el usuario especifique el uso de una solución a través de la opción -W.

El hardware listado a continuación puede indicar solo el hardware en el que se descubrió un problema. Las versiones más nuevas de hardware pueden corregir los problemas indicados a continuación. Máquinas similares de diferentes proveedores pueden o no presentar los mismos problemas. Diferentes proveedores pueden licenciar su firmware del mismo desarrollador de firmware IPMI, por lo que puede valer la pena intentar las soluciones listadas a continuación, incluso si su placa base no está listada.

Si cree que su hardware tiene un problema de cumplimiento adicional que requiere la implementación de una solución, comuníquese con los mantenedores de FreeIPMI en <freeipmi-users@gnu.org> o <freeipmi-devel@gnu.org>.

assumeio - Esta bandera de solución asumirá que las interfaces inband se comunican con la E/S del sistema en lugar de mapearse en memoria. Esto solucionará sistemas que informan direcciones base inválidas. Aquellos que experimenten este problema pueden ver errores como "device not supported" o "could not find inband device". Problema observado en HP ProLiant DL145 G1.

spinpoll - Esta bandera de solución instruirá a algunos controladores inband (notablemente el controlador KCS) a girar mientras hacen ping en lugar de poner el proceso a dormir. Esto puede mejorar significativamente el tiempo de ejecución en reloj de pared de las herramientas, ya que la granularidad del planificador del sistema operativo puede ser mucho mayor que el tiempo necesario para realizar una sola transacción de mensaje IPMI. Sin embargo, al girar, su sistema puede estar realizando menos trabajo útil al no cambiar de contexto la herramienta para una tarea más útil.

authcap - Esta bandera de solución omitirá las comprobaciones tempranas de capacidades de nombre de usuario, capacidades de autenticación y soporte K_g, permitiendo que la autenticación IPMI tenga éxito. Soluciona múltiples problemas en los que el sistema remoto no informa correctamente las capacidades de nombre de usuario, capacidades de autenticación o el estado K_g. Aquellos que experimenten este problema pueden ver errores como "username invalid", "authentication type unavailable for attempted privilege level", o "k_g invalid". Problema observado en Asus P5M2/P5MT-R/RS162-E4/RX4, Intel SR1520ML/X38ML y Sun Fire 2200/4150/4450 con ELOM.

nochecksumcheck - Esta bandera de solución indicará a FreeIPMI que no verifique las sumas de verificación devueltas de las respuestas de comandos IPMI. Soluciona sistemas que devuelven sumas de verificación inválidas debido a errores de implementación, pero el paquete es válido en otros aspectos. Se advierte a los usuarios sobre el uso de esta opción, ya que elimina la validación de la integridad del paquete en varias circunstancias. Sin embargo, es poco probable que sea un problema en la mayoría de las situaciones. Aquellos que experimenten este problema pueden ver errores como "connection timeout", "session timeout" o "password verification timeout". En conexiones IPMI 1.5, la solución "noauthcodecheck" también puede ser necesaria. Problema observado en Supermicro X9SCM-iiF, Supermicro X9DRi-F y Supermicro X9DRFR.

idzero - Esta bandera de solución permitirá que los IDs de sesión vacíos sean aceptados por el cliente. Soluciona sesiones IPMI que informan IDs de sesión vacíos al cliente. Aquellos que experimenten este problema pueden ver errores de "session timeout". Problema observado en Tyan S2882 con BMC M3289.

unexpectedauth - Esta bandera de solución permitirá que los authcodes inesperados no nulos se verifiquen como si fueran esperados. Soluciona un problema cuando los paquetes contienen datos de autenticación no nulos cuando deberían ser nulos debido a la autenticación por mensaje deshabilitada. Aquellos que experimenten este problema pueden ver errores de "session timeout". Problema observado en Dell PowerEdge 2850,SC1425. Confirmado que se corrigió en firmware más reciente.

forcepermsg - Esta bandera de solución forzará el uso de la autenticación por mensaje sin importar lo que anuncie el sistema remoto. Soluciona un problema cuando la autenticación por mensaje se anuncia como deshabilitada en el sistema remoto, pero en realidad es requerida para el protocolo. Aquellos que experimenten este problema pueden ver errores de "session timeout". Problema observado en IBM eServer 325.

endianseq - Esta bandera de solución invertirá el endianness de los números de secuencia de sesión para permitir que la sesión continúe correctamente. Soluciona números de secuencia de sesión IPMI 1.5 que tienen el endianness incorrecto. Aquellos que experimenten este problema pueden ver errores de "session timeout". Problema observado en algunos Sun ILOM 1.0/2.0 (depende del endianness del procesador de servicio).

noauthcodecheck - Esta bandera de solución indicará a FreeIPMI que no verifique los códigos de autenticación devueltos de las respuestas de comandos IPMI 1.5. Soluciona sistemas que devuelven códigos de autenticación inválidos debido a errores de hash o implementación. Se advierte a los usuarios sobre el uso de esta opción, ya que elimina una verificación de autenticación que verifica la validez de un paquete. Sin embargo, en la mayoría de las organizaciones, es poco probable que sea un problema de seguridad. Aquellos que experimenten este problema pueden ver errores como "connection timeout", "session timeout" o "password verification timeout". Problema observado en Xyratex FB-H8-SRAY, Intel Windmill, Quanta Winterfell y Wiwynn Windmill.

Aquellos que experimenten este problema pueden ver errores como "username invalid", "password invalid" o "k_g invalid". Esta solución se activa automáticamente con la solución "sun20".

integritycheckvalue - Esta bandera de solución solucionará un valor de verificación de integridad inválido durante el establecimiento de una sesión IPMI 2.0 cuando se usa la Suite de Cifrado ID 0. El valor de verificación de integridad debería ser de longitud 0, sin embargo, la placa base remota responde con un campo no vacío. Aquellos que experimenten este problema pueden ver errores de "k_g invalid". Problema observado en Supermicro X8DTG, Supermicro X8DTU e Intel S5500WBV/Penguin Relion 700, e Intel S2600JF/Appro 512X.

assumemaxsdrrecordcount - Esta solución indicará a la lectura de SDR que deje de leer después de que se haya leído un número máximo conocido de registros SDR. Esto solucionará sistemas que han implementado incorrectamente las funciones de lectura de SDR. Aquellos que experimenten este problema pueden ver errores de "SDR record count invalid". Problema observado en una placa base Inspur no especificada.

Sin soporte IPMI 1.5 - Se ha descubierto que algunas placas base que admiten IPMI 2.0 no admiten IPMI 1.5. Aquellos que experimenten este problema pueden ver errores como "ipmi 2.0 unavailable" o "connection timeout". Este problema se puede solucionar utilizando IPMI 2.0 en lugar de IPMI 1.5 especificando --driver-type=LAN_2_0. Problema observado en varias placas base HP y Supermicro.

DIAGNOSTICS

Al ejecutarse correctamente, el estado de salida es 0. En caso de error, el estado de salida es 1.

Si se especifican múltiples hosts para la comunicación, el estado de salida es 0 si y solo si todos los objetivos se ejecutan correctamente. De lo contrario, el estado de salida es 1.

PROBLEMAS CONOCIDOS

En sistemas operativos más antiguos, si introduce su nombre de usuario, contraseña y otra información potencialmente relevante para la seguridad en la línea de comandos, esta información puede ser descubierta por otros usuarios al usar herramientas como el comando ps(1) o al mirar en el sistema de archivos /proc. Generalmente es más seguro introducir la información de contraseña con opciones como las opciones -P o -K. Configurar la información relevante para la seguridad en el archivo de configuración de FreeIPMI también sería una forma apropiada de ocultar esta información.

Para prevenir ataques de fuerza bruta, algunos BMC se "bloquearán" temporalmente después de un número de errores de autenticación remota. Puede que necesite esperar un tiempo para que este "bloqueo" temporal pase antes de poder autenticarse nuevamente.
