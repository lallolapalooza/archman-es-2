NOMBRE

freeipmi_interpret_sensor.conf - especificar reglas de interpretación de sensores

DESCRIPCIÓN

El archivo /etc/freeipmi//freeipmi_interpret_sensor.conf define cómo se deben interpretar los sensores IPMI. Los sensores basados en IPMI especifican un número de estados/umbrales al ser leídos. Basándose en estos estados/umbrales, las bibliotecas y herramientas como libfreeipmi(3), libipmimonitoring(3) y ipmi-sensors(8) pueden informar si la lectura de un sensor es "buena" o "mala" a través de un informe de estado NOMINAL, ADVERTENCIA o CRÍTICO.

Cada uno de los estados enumerados a continuación son (esperemos) lo suficientemente descriptivos para describir las condiciones de estado que pueden ser activadas/desactivadas para cada tipo de sensor. Para obtener información más detallada sobre cada uno de los estados enumerados a continuación, consulte la Especificación IPMI "Tablas de Códigos de Sensores y Eventos". Ipmi-sensors(8) se puede utilizar para determinar los tipos de sensores y los estados/umbrales que existen en un sistema, emitiendo una salida muy detallada y viendo qué tipos de eventos de Activación o Desactivación son posibles.

Los valores posibles para todos los estados/umbrales a continuación son:

Nominal - Indica lectura Nominal si el estado/umbral se activa

Advertencia - Indica lectura de Advertencia si el estado/umbral se activa

Crítico - Indica lectura Crítica si el estado/umbral se activa

No todos los tipos de sensores y tipos de eventos IPMI son actualmente compatibles. Si desea que se admitan más, envíe un correo electrónico a la lista de correo de FreeIPMI.

Los valores predeterminados seleccionados para estados/umbrales individuales que se activan se basan en las mejores suposiciones y en las placas base que se analizan. Si cree que deberían cambiarse, envíe un correo electrónico a la lista de correo de FreeIPMI para discutir cuáles deberían ser los valores predeterminados.

La mayoría de las interpretaciones predeterminadas se pueden determinar con bastante facilidad y pueden satisfacer las necesidades de la mayoría de los usuarios. Por ejemplo, una lectura de "Performance_Met" es normalmente mejor que "Performance_Lags". Sin embargo, algunos sensores pueden ser ambiguos y depender completamente del fabricante. Por ejemplo, "State_Asserted" frente a "State_Deasserted" son completamente a interpretación del proveedor. Se recomienda a los usuarios que ajusten las interpretaciones a continuación según sea necesario para sus máquinas.

Cada grupo de condiciones de estado a continuación incluye una configuración para "No_Event". Esta es la condición bajo la cual no se han producido ni se han activado estados/eventos de sensor. En la mayoría de las condiciones, se prefiere una asignación a "Nominal". Sin embargo, bajo algunas circunstancias, puede ser útil informar algo más. Por ejemplo, si se requiere que un sensor en una placa base en particular informe un estado/evento, una condición de estado de sensor nulo podría indicar un sensor roto. Esto depende en gran medida de la placa base.

FORMATO

Las opciones de configuración que se pueden especificar en el archivo de configuración se enumeran a continuación. Cada opción de configuración debe figurar en una línea separada. Los argumentos de una opción están separados por cualquier cantidad de espacio en blanco. Múltiples argumentos también están separados por espacio en blanco. Los comentarios pueden marcarse usando el carácter de almohadilla ("#"), y las líneas pueden continuarse en la siguiente usando una barra invertida ("\").

IPMI_OEM
The following configuration options can be used to configure OEM specific interpretations. Users should be aware that both IPMI_OEM_Bitmask and IPMI_OEM_Value can be configured for an identical Manufacturer-ID, Product-ID, Event-Reading-Type-Code, and Sensor-Type combination. All interpretations rules for a specific combination are iterated through and the worst resulting sensor state is returned (i.e. Warning < Nominal, Critical < Warning). If no match is found, no sensor state is returned for the OEM sensor reading. For each of the configuration options below, <Manufacturer-ID> is the numeric IANA manufacturer ID for the manufacturer in question. The <Product-ID> is one or more numeric IDs representing the manufacturer's product. The <Product-ID> can be listed as a single numeric number (e.g. 1234), a range of IDs separated by a dash (e.g. 12-20), or a list of specific product IDs separated by a plus (e.g. 12+19+22). Both the Manufacturer-ID and Product-ID can be found using bmc-info(8). Multiple <Manufacturer-ID> and <Product-ID> pairs can be input separated by commas. The Event-Reading-Type-Code and Sensor-Type need not be OEM types. They may be non-OEM types and used to provide interpretation rules for sensors that may be behaving outside the standard of the IPMI specification.
IPMI_OEM_Bitmask <Manufacturer-ID>:<Product-ID>,... Event-Reading-Type-Code Sensor-Type Sensor-Event-Bitmask State
IPMI_OEM_Bitmask can be used to configure a state interpretation for a specific Manufacturer-ID, Product-ID, Event-Reading-Type-Code, and Sensor-Type combination and a specific bitmask of the Sensor-Event. The state will be accepted as the sensor interpretation if the inputted bitmask ANDed with the actual sensor event bitmask reading is true. As a special case, the state will be accepted if the inputted bitmask and the actual sensor event bitmask are both 0. In other words, if no events happened, an OEM interpretation can be configured for this case by inputing a bitmask of 0x0000.
IPMI_OEM_Value <Manufacturer-ID>:<Product-ID>,... Event-Reading-Type-Code Sensor-Type Sensor-Event-Bitmask-Value State
IPMI_OEM_Value can be used to configure a state interpretation for a specific Manufacturer-ID, Product-ID, Event-Reading-Type-Code, and Sensor-Type combination and a specific value for the Sensor-Event-Bitmask. The state will be accepted as the sensor interpretation if the inputted bitmask value is equal to the actual sensor event bitmask reading.
