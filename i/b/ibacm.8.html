NOMBRE

ibacm - servicios de resolución de direcciones y rutas para InfiniBand.

SINOPSIS

ibacm [-D] [-P] [-A addr_file] [-O option_file]

DESCRIPCIÓN

El IB ACM implementa y proporciona un marco para servicios de resolución de nombres, direcciones y rutas (caminos) sobre InfiniBand. Está destinado a abordar los problemas de escalabilidad en la configuración de conexiones al ejecutar aplicaciones MPI en clústeres grandes. El IB ACM proporciona la información necesaria para establecer una conexión, pero no implementa el protocolo CM.

Un usuario principal del servicio ibacm es la biblioteca librdmacm. Esto permite a las aplicaciones utilizar el servicio ibacm sin cambios en el código o sin necesidad de ser conscientes de que el servicio está en uso. librdmacm versiones 1.0.12 - 1.0.15 pueden invocar servicios IB ACM cuando se compilan con la opción --with-ib_acm. La versión 1.0.16 y posteriores de librdmacm utilizarán automáticamente el IB ACM si está instalado. Los servicios IB ACM se integran con las rutinas rdma_resolve_addr, rdma_resolve_route y rdma_getaddrinfo. Para obtener el máximo beneficio, se debe utilizar la rutina rdma_getaddrinfo, sin embargo, las aplicaciones existentes aún deberían ver beneficios significativos en la escalabilidad de las conexiones utilizando las llamadas disponibles en librdmacm 1.0.11 y versiones anteriores.

El IB ACM se centra en ser escalable, eficiente y extensible. Implementa una arquitectura de complementos que permite a un proveedor suministrar su proveedor propietario además del proveedor predeterminado. La implementación actual del proveedor predeterminado ibacmp limita el tráfico de red, las interacciones de SA y los servicios centralizados. Ibacmp admite múltiples protocolos de resolución para manejar diferentes topologías de fabricación.

El paquete IB ACM consta de tres componentes: el servicio central ibacm, la biblioteca compartida del proveedor predeterminado ibacmp y una utilidad de prueba/configuración - ib_acme. Los tres son componentes de espacio de usuario y están disponibles para Linux. A continuación se proporcionan detalles adicionales.

OPCIONES

-D
ejecutar en modo demonio (predeterminado)
-P
ejecutar como proceso estándar
-A addr_file
archivo de configuración de direcciones
-O option_file
archivo de configuración de opciones
--systemd
Habilita la integración con systemd. Esto incluye la activación opcional del socket del puerto de escucha del demonio.

GUÍA DE INICIO RÁPIDO

1. Prerrequisitos: deben estar instalados libibverbs y libibumad. La pila IB debe estar en ejecución con IPoIB configurado. Estos pasos asumen que el usuario tiene privilegios administrativos.

2. Instale el paquete IB ACM. Esto instala ibacm, ibacmp, ib_acme y scripts init.d.

3. Ejecute 'ibacm' como administrador para iniciar el demonio ibacm.

4. Opcionalmente, ejecute 'ib_acme -d <ip_destino> -v' para verificar que el servicio ibacm está en ejecución.

5. Instale librdmacm, utilizando la opción de compilación --with-ib_acm si es necesario. Esta opción de compilación no es necesaria con librdmacm 1.0.17 o posterior. librdmacm utilizará automáticamente el servicio ibacm. En caso de fallos, librdmacm volverá a la resolución normal.

6. Puede usar ib_acme -P para recopilar estadísticas de rendimiento del demonio ibacm local para ver si el servicio funciona correctamente. De manera similar, el comando ib_acme -e podría usarse para enumerar todos los puntos finales creados por el servicio ibacm local.

NOTAS

ib_acme:

El programa ib_acme cumple una doble función. Actúa como una utilidad para probar el funcionamiento de ibacm y ayudar a verificar si el servicio ibacm y el protocolo seleccionado son utilizables para una configuración de clúster dada. Además, genera automáticamente archivos de configuración de ibacm para ayudar o eliminar la configuración manual.

Archivos de configuración de ibacm:

El servicio ibacm se basa en dos archivos de configuración.

El archivo ibacm_addr.cfg contiene mapeos de nombres y direcciones para cada punto final IB <dispositivo, puerto, pkey>. Aunque los nombres en el archivo ibacm_addr.cfg pueden ser cualquiera, ib_acme mapea el nombre del host a los puntos finales IB. Las direcciones IP, por otro lado, se asignan dinámicamente. Si no se encuentra el archivo de direcciones, el servicio ibacm intentará crear uno utilizando valores predeterminados.

El archivo ibacm_opts.cfg proporciona un conjunto de opciones configurables para el servicio central ibacm y el proveedor predeterminado, como tiempo de espera, número de reintentos, nivel de registro, etc. ib_acme genera el archivo ibacm_opts.cfg utilizando información estática. Si no se encuentra un archivo de opciones, ibacm utilizará los valores predeterminados.

ibacm:

El servicio ibacm es responsable de resolver nombres y direcciones a información de ruta InfiniBand y de almacenar en caché dichos datos. Debe ejecutarse con privilegios administrativos.

ibacm implementa una interfaz de cliente sobre sockets TCP, que es abstraída por la biblioteca librdmacm. Uno o más proveedores pueden ser cargados por el servicio central, dependiendo de la configuración. En el proveedor predeterminado ibacmp, uno o más protocolos de backend se utilizan para satisfacer las solicitudes del usuario. Aunque ibacmp admite consultas de registro de ruta SA estándar en el backend, también admite un protocolo de resolución basado en tráfico multicast. Este último no es utilizable en todas las topologías de fabric, específicamente en aquellas que pueden no tener rutas reversibles o fábricas que utilicen enrutamiento de torus. Los usuarios deben usar la utilidad ib_acme para verificar que el protocolo multicast sea utilizable antes de ejecutar otras aplicaciones.

Conceptualmente, el proveedor predeterminado ibacmp implementa un protocolo similar a ARP y utiliza registros multicast IB para construir datos de registro de ruta o consulta directamente al SA, dependiendo del protocolo de ruta seleccionado. Por defecto, el proveedor ibacmp utiliza y almacena en caché las consultas de registro de ruta SA.

Específicamente, todos los puntos finales IB se unen a varios grupos multicast. Los grupos multicast difieren según tasas, mtu, sl, etc., y se priorizan. Todos los puntos finales participantes deben poder comunicarse en el grupo multicast de menor prioridad. ibacmp asigna uno o más nombres/direcciones a cada punto final IB utilizando el archivo ibacm_addr.cfg. Los clientes proporcionan nombres o direcciones de origen y destino como entrada al servicio, y reciben como salida datos de registro de ruta.

El servicio mapea el nombre/dirección de origen de un cliente a un punto final IB local. Si el nombre/dirección de destino no está almacenado en caché localmente en el proveedor predeterminado, envía una solicitud multicast en el grupo multicast de menor prioridad en el punto final local. La solicitud lleva una lista de grupos multicast que el remitente puede usar. El destinatario de la solicitud selecciona el grupo multicast de mayor prioridad que también puede usar y devuelve esa información directamente al remitente. Todos los puntos finales que reciben el mensaje de solicitud multicast almacenan en caché los datos de la solicitud. El punto final de origen también almacena en caché la respuesta y utiliza el grupo multicast seleccionado para construir u obtener datos de registro de ruta, que se devuelven al cliente.

La implementación actual del proveedor ibacmp tiene varias restricciones adicionales:

- ibacmp está limitado en su manejo de cambios dinámicos. ibacm debe detenerse y reiniciarse si se reconfigura un clúster.

- No se ha verificado el soporte para IPv6.

- El número de grupos multicast que un punto final puede soportar se limita a 2.

ibacmp contiene varias cachés internas. Estas incluyen cachés para direcciones de destino GID y LID. Estas cachés se pueden precargar opcionalmente. ibacm admite el formato de registro de ruta "full" del plugin dump_pr de OpenSM que se utiliza para precargar estas cachés. El formato del archivo se especifica en el archivo ibacm_opts.cfg a través de la opción route_preload, que debe establecerse en full_opensm_v1 para este formato de archivo. El formato predeterminado es none, que no precarga estas cachés. Consulte dump_pr.notes.txt en dump_pr para obtener más información sobre el formato de archivo full_opensm_v1 y cómo configurar OpenSM para generar este archivo.

Además, las cachés de nombres, IPv4 e IPv6 se pueden precargar utilizando la opción addr_preload. El valor predeterminado es none, que no precarga estas cachés. Para precargar estas cachés, establezca esta opción en acm_hosts y configure addr_data_file adecuadamente.
