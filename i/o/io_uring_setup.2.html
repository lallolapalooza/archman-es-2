DESCRIPCIÓ

N

La llamada al sistema io_uring_setup(2) configura una cola de envío (SQ) y una cola de finalización (CQ) con al menos entries entradas, y devuelve un descriptor de archivo que se puede utilizar para realizar operaciones posteriores en la instancia de io_uring. Las colas de envío y finalización se comparten entre el espacio de usuario y el núcleo, lo que elimina la necesidad de copiar datos al iniciar y finalizar la

E/S.

params es utilizada por la aplicación para pasar opciones al núcleo, y por el núcleo para transmitir información sobre los búferes de

anillo. 


struct io_uring_params {
    __u32 sq_entries;
    __u32 cq_entries;
    __u32 flags;
    __u32 sq_thread_cpu;
    __u32 sq_thread_idle;
    __u32 features;
    __u32 wq_fd;
    __u32 resv[3];
    struct io_sqring_offsets sq_off;
    struct io_cqring_offsets cq_off;
}
;

Los campos flags, sq_thread_cpu y sq_thread_idle se utilizan para configurar la instancia de io_uring. flags es una máscara de bits de 0 o más de los siguientes valores combinados con

OR:
IORING_SETUP_IOP
OLL
Realizar una espera activa (busy-waiting) por una finalización de E/S, en lugar de recibir notificaciones a través de una IRQ (Solicitud de Interrupción) asíncrona. El sistema de archivos (si existe) y el dispositivo de bloque deben admitir el sondeo (polling) para que esto funcione. La espera activa proporciona una latencia menor, pero puede consumir más recursos de la CPU que la E/S dirigida por interrupciones. Actualmente, esta función solo es utilizable en un descriptor de archivo abierto con el indicador O_DIRECT. Cuando se envía una lectura o escritura a un contexto con sondeo, la aplicación debe sondear las finalizaciones en el anillo CQ llamando a io_uring_enter(2). Es ilegal mezclar E/S con sondeo y sin sondeo en una instancia de io_uring.

Esto solo es aplicable a dispositivos de almacenamiento por ahora, y el dispositivo de almacenamiento debe estar configurado para el sondeo. La forma de hacerlo depende del tipo de dispositivo en cuestión. Para los dispositivos NVMe, el controlador nvme debe cargarse con el parámetro poll_queues establecido en el número deseado de colas de sondeo. Las colas de sondeo se compartirán

adecuadamente entre las CPU del sistema, si el núme
ro es menor que el número de hilos de CPU en línea.
IORING_SETUP_HYBRID_IOP
OLL
Este indicador debe usarse con el indicador IORING_SETUP_IOPOLL. El sondeo de E/S híbrido es una función basada en iopoll, difiere del sondeo estricto en que se retrasará un poco antes de realizar el sondeo del lado de la finalización, para evitar desperdiciar demasiados recursos de la CPU. Al igual que IOPOLL, requiere que los dispositivos admitan el
sondeo.
IORING_SETUP_SQP
OLL
Cuando se especifica este indicador, se crea un hilo del núcleo para realizar el sondeo de la cola de envío. Una instancia de io_uring configurada de esta manera permite a una aplicación emitir E/S sin realizar nunca un cambio de contexto al núcleo. Al utilizar la cola de envío para rellenar nuevas entradas de cola de envío y observar las finalizaciones en la cola de finalización, la aplicación puede enviar y recoger E/S sin realizar una sola llamada al sistema.

Si el hilo del núcleo está inactivo durante más de sq_thread_idle milisegundos, establecerá el bit IORING_SQ_NEED_WAKEUP en el campo flags de la struct io_sq_ring. Cuando esto suceda, la aplicación debe llamar a io_uring_enter(2) para despertar al hilo del núcleo. Si la E/S se mantiene ocupada, el hilo del núcleo nunca dormirá. Una aplicación que utilice esta función deberá proteger la llamada a io_uring_enter(2) con la siguiente secuencia de

código: 


/*
 * Ensure that the wakeup flag is read after the tail pointer
 * has been written. It's important to use memory load acquire
 * semantics for the flags read, as otherwise the application
 * and the kernel might not agree on the consistency of the
 * wakeup flag.
 */
unsigned flags = atomic_load_relaxed(sq_ring->flags);
if (flags & IORING_SQ_NEED_WAKEUP)
    io_uring_enter(fd, 0, 0, IORING_ENTER_SQ_WAKEUP)
;

donde sq_ring es un anillo de cola de envío configurado utilizando la estructura struct io_sqring_offsets

descrita a c
ontinuación.
Tenga en cuenta que, al utilizar un anillo configurado con IORING_SETUP_SQPOLL, nunca llama directamente a la llamada al sistema io_uring_enter(2). Eso normalmente lo gestiona la función io_uring_submit(3) de liburing. Determina automáticamente si está utilizando el modo de sondeo o no y se ocupa de cuándo su programa necesita llamar a io_uring_enter(2) sin que usted tenga que preocuparse por
ello.
Tenga en cuenta que, aunque esto pueda parecer inmediatamente atractivo como un indicador automático de "más rápido", se deben realizar evaluaciones caso por caso para verificar si tiene sentido para la
aplicación.
Antes de la versión 5.11 del núcleo de Linux, para usar esta función con éxito, la aplicación debe registrar un conjunto de archivos para usar en la E/S a través de io_uring_register(2) utilizando el código de operación IORING_REGISTER_FILES. El no hacerlo resultará en que la E/S enviada falle con EBADF. La presencia de esta función se puede detectar por el indicador de función IORING_FEAT_SQPOLL_NONFIXED. En la versión 5.11 y posteriores, ya no es necesario registrar archivos para usar esta función. 5.11 también permite usar esto como no root, si el usuario tiene la capacidad CAP_SYS_NICE. En 5.13 este requisito también se relajó, y no se necesitan privilegios especiales para SQPOLL en núcleos más nuevos. Ciertos núcleos estables anteriores a 5.13 también pueden admitir SQPOLL sin
privilegios.

IORING_SETUP_SUBMIT_
ALL
Normalmente io_uring deja de enviar un lote de solicitudes si una de estas solicitudes resulta en un error. Esto puede causar el envío de menos de lo esperado, si una solicitud termina en error mientras se envía. Si el anillo se crea con este indicador, io_uring_enter(2) continuaráContinúe enviando solicitudes incluso si encuentra un error al enviar una solicitud. Los CQE todavía se publican para solicitudes erróneas, independientemente de si esta bandera está configurada en el momento de la creación del anillo, la única diferencia es si el la secuencia de envío se detiene o continúa cuando se observa un error. Disponible desde la versión 5.18.
IORING_SETUP_COOP_TASKRUN
Por defecto, io_uring interrumpirá una tarea que se ejecuta en el espacio de usuario cuando un evento de finalización llegue. Esto es para asegurar que las finalizaciones se ejecuten de manera oportuna. Para muchos casos de uso, esto es excesivo y puede causar una disminución del rendimiento debido a la interrupción entre procesadores utilizada para esto, la transición del kernel/usuario, la interrupción innecesaria de las actividades del espacio de usuario de la tarea, y una menor agrupación si las finalizaciones llegan a una velocidad rápida. La mayoría de las aplicaciones no necesitan la interrupción forzada, ya que los eventos se procesan en cualquier transición del kernel/usuario. La excepción son las configuraciones donde la aplicación usa múltiples hilos operando en el mismo anillo, donde la aplicación que espera finalizaciones no es la que las envió. Para la mayoría de los demás casos de uso, establecer esta bandera mejorará el rendimiento. Disponible desde la versión 5.19.
IORING_SETUP_TASKRUN_FLAG
Se utiliza junto con IORING_SETUP_COOP_TASKRUN, esto proporciona una bandera, IORING_SQ_TASKRUN, que se establece en el anillo SQ flags cada vez que hay finalizaciones pendientes que deben procesarse. liburing verificará esta bandera incluso al hacer io_uring_peek_cqe(3) y entrará en el kernel para procesarlas, y las aplicaciones pueden hacer lo mismo. Esto hace que IORING_SETUP_TASKRUN_FLAG sea seguro de usar incluso cuando las aplicaciones dependen de una operación de tipo peek en el anillo CQ para ver si hay algo pendiente que recoger. Disponible desde la versión 5.19.
IORING_SETUP_SQE128
Si se establece, io_uring utilizará SQE de 128 bytes en lugar de la variante normal de 64 bytes. Este es un requisito para usar ciertos tipos de solicitud; a partir de la versión 5.19, solo el comando de pase IORING_OP_URING_CMD para el pase NVMe requiere esto. Disponible desde la versión 5.19.
IORING_SETUP_CQE32
Si se establece, io_uring utilizará CQE de 32 bytes en lugar de la variante normal de 16 bytes. Este es un requisito para usar ciertos tipos de solicitud; a partir de la versión 5.19, solo el comando de pase IORING_OP_URING_CMD para el pase NVMe requiere esto. Disponible desde la versión 5.19.
IORING_SETUP_SINGLE_ISSUER
Una pista para el kernel de que solo una tarea (o hilo) enviará solicitudes, lo que se utiliza para optimizaciones internas. La tarea de envío es ya sea la tarea que creó el anillo, o si se especifica IORING_SETUP_R_DISABLED, entonces es la tarea que habilita el anillo a través de io_uring_register(2). El kernel impone esta regla, fallando las solicitudes con -EEXIST si se viola la restricción. Tenga en cuenta que cuando se establece IORING_SETUP_SQPOLL, se considera que la tarea de sondeo está realizando todos los envíos en nombre del espacio de usuario y, por lo tanto, siempre cumple con la regla independientemente de cuántas tareas del espacio de usuario realicen io_uring_enter(2). Disponible desde la versión 6.0.
IORING_SETUP_DEFER_TASKRUN
Por defecto, io_uring procesará todo el trabajo pendiente al final de cualquier llamada al sistema o interrupción de hilo. Esto puede retrasar el progreso de la aplicación. Establecer esta bandera indicará a io_uring que debe posponer el trabajo hasta una llamada a io_uring_enter(2) con la bandera IORING_ENTER_GETEVENTS establecida. Esto permite a la aplicación solicitar que se ejecute el trabajo justo antes de procesar las finalizaciones. Esta bandera requiere que se establezca la bandera IORING_SETUP_SINGLE_ISSUER, y también garantiza que la llamada a io_uring_enter(2) se realice desde el mismo hilo que envió las solicitudes. Tenga en cuenta que si se establece esta bandera, la responsabilidad de activar periódicamente el trabajo (por ejemplo, a través de cualquiera de las funciones de espera de CQE) recae en la aplicación, o de lo contrario es posible que las finalizaciones no se entreguen. Disponible desde la versión 6.1.
IORING_SETUP_NO_MMAP
Por defecto, io_uring asigna memoria del kernel que los llamantes deben posteriormente mapear usando mmap(2). Si se establece esta bandera, io_uring utiliza en su lugar búferes asignados por el llamante; p->cq_off.user_addr debe apuntar a la memoria para los anillos sq/cq, y p->sq_off.user_addr debe apuntar a la memoria para los sqe. Cada asignación debe ser memoria contigua. Típicamente, los llamantes deben asignar esta memoria usando mmap(2) para asignar una página grande. Si se establece esta bandera, un intento posterior de mmap(2) el descriptor de archivo io_uring fallará. Disponible desde la versión 6.5.
IORING_SETUP_REGISTERED_FD_ONLY
Si se establece esta bandera, io_uring registrará el descriptor de archivo del anillo y devolverá el índice del descriptor registrado, sin asignar nunca un descriptor de archivo no registrado. El llamante deberá usar IORING_REGISTER_USE_REGISTERED_RING al llamar a io_uring_register(2). Esta bandera solo tiene sentido cuando se usa junto con IORING_SETUP_NO_MMAP, que también debe establecerse. Disponible desde la versión 6.5.
IORING_SETUP_NO_SQARRAY
Si se establece esta bandera, las entradas en la cola de envío se enviarán en orden, volviendo a la primera entrada después de llegar al final de la cola. En otras palabras, ya no habrá una indirección a través de la matriz de entradas de envío, y la cola se indexará directamente mediante la cola de envío y el rango de índices representado por ella módulo el tamaño de la cola. Posteriormente, el usuario no debe mapear la matriz de entradas de la cola de envío, y el desplazamiento correspondiente en struct io_sqring_offsets se establecerá en cero. Disponible desde la versión 6.6.

Si no se especifican banderas, la instancia de io_uring se configura para E/S impulsada por interrupciones. La E/S se puede enviar usando io_uring_enter(2) y se puede recuperar escaneando la cola de finalización.

La matriz resv debe inicializarse a cero.

features es completado por el kernel, que especifica varias características compatibles con la versión actual del kernel.

IORING_FEAT_SINGLE_MMAP
Si se establece esta bandera, los dos anillos SQ y CQ se pueden mapear con una sola llamada a mmap(2). Los SQE aún deben asignarse por separado. Esto reduce las llamadas necesarias a mmap(2) de tres a dos. Disponible desde el kernel 5.4.
IORING_FEAT_NODROP
Si se establece esta bandera, io_uring admite no descartar eventos de finalización casi nunca. Un evento descartado solo puede ocurrir si el kernel se queda sin memoria, en cuyo caso tienes problemas peores que un evento perdido. Tu aplicación y otras probablemente serán eliminadas por falta de memoria de todos modos. Si ocurre un evento de finalización y el anillo CQ está lleno, el kernel almacena el evento internamente hasta que el anillo CQ tenga espacio para más entradas. En kernels anteriores, si se ingresa esta condición de desbordamiento, intentar enviar más E/S fallaría con el valor de error -EBUSY, si no puede vaciar los eventos desbordados en el anillo CQ. Si esto sucede, la aplicación debe recuperar eventos del anillo CQ e intentar el envío nuevamente. Si el kernel no tiene memoria libre para almacenar el evento internamente, se verá reflejado en un aumento del valor de desbordamiento en el cqring. Disponible desde el kernel 5.5. Adicionalmente io_uring_enter(2) devolverá -EBADR la próxima vez que de lo contrario dormiría esperando finalizaciones (desde el kernel 5.19).
IORING_FEAT_SUBMIT_STABLE
Si se establece esta bandera, las aplicaciones pueden tener la certeza de que cualquier dato para la descarga asíncrona ha sido consumido cuando el kernel ha consumido el SQE. Disponible desde el kernel 5.5.
IORING_FEAT_RW_CUR_POS
Si se establece esta bandera, las aplicaciones pueden especificar offset == -1 con IORING_OP_{READV,WRITEV}, IORING_OP_{READ,WRITE}_FIXED, y IORING_OP_{READ,WRITE} para significar la posición actual del archivo, que se comporta como preadv2(2) y pwritev2(2) con offset == -1. Utilizará (y actualizará) la posición actual del archivo. Esto obviamente viene con la advertencia de que si la aplicación tiene múltiples lecturas o escrituras en vuelo, el resultado final no será el esperado. Esto es similar a hilos que comparten un descriptor de archivo y realizan E/S usando la posición actual del archivo. Disponible desde el kernel 5.6.
IORING_FEAT_CUR_PERSONALITY
Si se establece esta bandera, entonces io_uring garantiza que tanto la ejecución síncrona como asíncrona de una solicitud asumen las credenciales de la tarea que llamó a io_uring_enter(2) para poner en cola las solicitudes. Si esta bandera no está establecida, entonces las solicitudes se emiten con las credenciales de la tarea que originalmente registró el io_uring. Si solo una tarea está usando un anillo, entonces esta bandera no importa ya que las credenciales siempre serán las mismas. Tenga en cuenta que este es el comportamiento predeterminado; las tareas aún pueden registrar diferentes personalidades a través de io_uring_register(2) con IORING_REGISTER_PERSONALITY y especificar la personalidad a usar en el sqe. Disponible desde el kernel 5.6.
IORING_FEAT_FAST_POLL
Si se establece esta bandera, entonces io_uring admite el uso de un mecanismo interno de sondeo para impulsar la preparación de datos/espacio. Esto significa que las solicitudes que no pueden leer o escribir datos en un archivo ya no necesitan ser derivadas a un hilo asíncrono para su manejo, sino que comenzarán la operación cuando el archivo esté listo. Esto es similar a hacer poll + read/write en el espacio de usuario, pero elimina la necesidad de hacerlo. Si se establece esta bandera, las solicitudes que esperan espacio/datos consumen un locon menos recursos al hacerlo, ya que no bloquean un hilo. Disponible desde el kernel
5.7.
