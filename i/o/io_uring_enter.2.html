DESCRIPCIÓ

N

io_uring_enter(2) se utiliza para iniciar y completar E/S usando las colas de envío y finalización compartidas configuradas por una llamada a io_uring_setup(2). Una sola llamada puede tanto enviar nueva E/S como esperar la finalización de la E/S iniciada por esta llamada o por llamadas anteriores a io_uring_ent

er(2).

fd es el descriptor de archivo devuelto por io_uring_setup(2). to_submit especifica el número de E/S a enviar desde la cola de envío. flags es una máscara de bits de los siguientes

valores:
IORING_ENTER_GETEVE
NTS
Si se establece esta bandera, la llamada al sistema esperará el número especificado de eventos en min_complete antes de retornar. Esta bandera puede establecerse junto con to_submit para enviar y completar eventos en una sola llamada al sistema. Si se establece esta bandera, la bandera IORING_SETUP_DEFER_TASKRUN no debe estar establecida o el hilo que emite la llamada al sistema debe ser el hilo que creó el io_uring asociado con fd, o ser el hilo que habilitó el anillo creado originalmente con IORING_SETUP_R_DISABLED a través de io_uring_register(2) o io_uring_enable_r
ings(3).
IORING_ENTER_SQ_WAK
EUP
Si el anillo ha sido creado con IORING_SETUP_SQPOLL, entonces esta bandera le pide al kernel despertar el hilo del kernel SQ para enviar
E/S.
IORING_ENTER_SQ_W
AIT
Si el anillo ha sido creado con IORING_SETUP_SQPOLL, entonces la aplicación no tiene una visión real de cuándo el hilo del kernel SQ ha consumido entradas del anillo SQ. Esto puede llevar a una situación donde la aplicación ya no puede obtener una entrada SQE libre para enviar, sin saber cuándo una se hará disponible a medida que el hilo del kernel SQ las consume. Si la llamada al sistema se usa con esta bandera establecida, entonces esperará hasta que al menos una entrada esté libre en el anillo
SQ.
IORING_ENTER_EXT_
ARG
Por defecto, arg es un puntero a sigset_t. Si IORING_ENTER_EXT_ARG está establecida (soportada desde el kernel 5.11), entonces arg es en su lugar un puntero a un struct io_uring_getevents_arg y argsz debe establecerse al tamaño de esta estructura. La definición es la siguiente: 
struct io_uring_getevents_arg {
        __u64   sigmask;
        __u32   sigmask_sz;
        __u32   pad;
        __u64   ts;

;

lo que permite pasar tanto una máscara de señales como un puntero a un valor de tiempo de espera struct __kernel_timespec. Si ts se establece a un puntero válido, entonces este valor de tiempo indica el tiempo de espera para esperar eventos. Si una aplicación está esperando eventos y desea

dejar de esperar después de una cantidad de tiempo especificada, entonces esto puede
lograrse directamente en la versión 5.11 y superior usando esta característica.

normal.

Si la instancia de io_uring fue configurada para sondeo, especificando IORING_SETUP_IOPOLL en la llamada a io_uring_setup(2), entonces min_complete tiene un significado ligeramente diferente. Pasar un valor de 0 instruye al kernel para devolver cualquier evento que ya esté completo, sin bloquear. Si min_complete es un valor distinto de cero, el kernel aún devolverá inmediatamente si hay eventos de finalización disponibles. Si no hay eventos de finalización disponibles, entonces la llamada sondeará hasta que una o más finalizaciones se hagan disponibles, o hasta que el proceso haya excedido su porción de tiempo del

planificador.

Tenga en cuenta que, para E/S dirigida por interrupción (donde IORING_SETUP_IOPOLL no fue especificada en la llamada a io_uring_setup(2)), una aplicación puede verificar la cola de finalización para eventos de finalización sin entrar en el kernel en

absoluto.

Cuando la llamada al sistema retorna que una cierta cantidad de SQEs han sido consumidos y enviados, es seguro reutilizar las entradas SQE en el anillo. Esto es cierto incluso si el envío real de la E/S tuvo que ser aplazado a un contexto asíncrono, lo que significa que el SQE puede de hecho no haber sido enviado aún. Si el kernel requiere el uso posterior de una entrada SQE particular, habrá hecho una copia privada de

ella.

sig es un puntero a una máscara de señales (ver sigprocmask(2)); si sig no es NULL, io_uring_enter(2) primero reemplaza la máscara de señales actual por la apuntada por sig, luego espera a que los eventos se hagan disponibles en la cola de finalización, y luego restaura la máscara de señales original. La siguiente llamada a io_uring_enter(2)

: 


ret = io_uring_enter(fd, 0, 1, IORING_ENTER_GETEVENTS, &sig)
;

es equivalente a ejecutar atómicamente las siguientes

llamadas: 


pthread_sigmask(SIG_SETMASK, &sig, &orig);
ret = io_uring_enter(fd, 0, 1, IORING_ENTER_GETEVENTS, NULL);
pthread_sigmask(SIG_SETMASK, &orig, NULL)
;

Vea la descripción de pselect(2) para una explicación de por qué el parámetro sig es

necesario.

El opcode describe la operación a realizar. Puede ser uno de:



  
IORING_OP_NOP

  
No realizar ninguna E/S. Esto es útil para probar el rendimiento de la
      implementación de io_uring en sí misma.

  
IORING_OP_READV

  

  
IORING_OP_WRITEV

  
Operaciones de lectura y escritura vectorizadas, similares a preadv2(2) y
      pwritev2(2). Si el archivo no es buscable, off debe establecerse en
      cero o -1.
      

  
IORING_OP_READ_FIXED

  

  
IORING_OP_WRITE_FIXED

  
Leer o escribir en búferes pre-asignados. Consulte io_uring_register(2)
      para obtener detalles sobre cómo configurar un contexto para lecturas y escrituras fijas.
      

  
IORING_OP_FSYNC

  
Sincronización de archivo. Consulte también fsync(2). Opcionalmente off y len
      pueden usarse para especificar un rango dentro del archivo a sincronizar en lugar de
      sincronizar todo el archivo, que es el comportamiento predeterminado. Tenga en cuenta que, aunque
      la E/S se inicia en el orden en que aparece en la cola de envío,
      las finalizaciones no tienen orden. Por ejemplo, una aplicación que coloca una
      escritura seguida de un fsync en la cola de envío no puede esperar que el
      fsync se aplique a la escritura. Las dos operaciones se ejecutan en paralelo, por lo que
      el fsync puede completarse antes de que la escritura se emita al almacenamiento. Lo mismo
      ocurre con las escrituras emitidas previamente que no se han completado antes
      del fsync. Para imponer el orden, se pueden utilizar SQE enlazados,
      IOSQE_IO_DRAIN o esperar la llegada de CQE de las solicitudes que
      tienen que ordenarse antes de una solicitud dada antes de enviar su SQE.
      

  
IORING_OP_POLL_ADD

  
Sondear el fd especificado en la entrada de la cola de envío para los eventos
      especificados en el campo poll_events. A diferencia de poll o epoll sin
      EPOLLONESHOT, por defecto esta interfaz siempre funciona en modo único. Es decir, una vez que la operación de sondeo se completa, deberá volver a enviarse.
    
Si IORING_POLL_ADD_MULTI está configurado en el campo len de la SQE,
        entonces el sondeo funcionará en modo múltiple. Esto significa que se activará repetidamente cuando el evento solicitado sea verdadero, y por lo tanto, se pueden generar múltiples CQE a partir de esta única SQE. El campo flags del CQE tendrá IORING_CQE_F_MORE configurado en la finalización si la aplicación debe esperar más entradas CQE de la solicitud original. Si esta bandera no está configurada en la finalización, entonces la solicitud de sondeo ha terminado y no se generarán más eventos. Este modo está disponible desde la versión 5.13.

    
Este comando funciona como un poll(2) asíncrono y el resultado del evento de finalización es la máscara de eventos devuelta.

    
Sin IORING_POLL_ADD_MULTI y la operación de sondeo inicial con
        IORING_POLL_ADD_MULTI, la operación está activada por nivel, es decir, si hay datos listos o eventos pendientes, etc. en el momento del envío, se publicará un CQE correspondiente. Las posibles finalizaciones posteriores a la primera causadas por un IORING_POLL_ADD_MULTI están activadas por flanco.

      

  
IORING_OP_POLL_REMOVE

  
Eliminar o actualizar una solicitud de sondeo existente. Si se encuentra, el campo res de la struct io_uring_cqe contendrá 0. Si no se encuentra, res contendrá -ENOENT, o -EALREADY si la solicitud de sondeo ya estaba en proceso de completarse.
    
Si IORING_POLL_UPDATE_EVENTS está configurado en el campo len de la SQE,
        entonces la solicitud actualizará una solicitud de sondeo existente con la máscara de eventos pasada en esta solicitud. La búsqueda se basa en el campo user_data de la SQE original enviada, y este valor se pasa en el campo addr de la SQE. Si
        IORING_POLL_UPDATE_USER_DATA está configurado en el campo len de la SQE,
        entonces la solicitud actualizará el user_data de una solicitud de sondeo existente basándose en el valor pasado en el campo off. La actualización de un sondeo existente está disponible desde la versión 5.13.

      

  
IORING_OP_EPOLL_CTL

  
Añadir, eliminar o modificar entradas en la lista de intereses de epoll(7). Consulte
      epoll_ctl(2) para obtener detalles de la llamada al sistema. fd contiene el
      descriptor de archivo que representa la instancia de epoll, off contiene el
      descriptor de archivo a añadir, eliminar o modificar, len contiene la operación (
      EPOLL_CTL_ADD, EPOLL_CTL_DEL, EPOLL_CTL_MOD) a
      realizar y, addr contiene un puntero a la estructura epoll_event. Disponible desde la versión 5.6.
      

  
IORING_OP_SYNC_FILE_RANGE

Consulte también sync_file_range(2) para la descripción general de la llamada al sistema relacionada. Disponible desde la versión 5.2.

IORING_OP_TIME
OUT
  
Este comando registrará una operación de tiempo de espera. El campo addr
      debe contener un puntero a una estructura struct __kernel_timespec, len debe
      contener 1 para indicar una estructura __kernel_timespec, timeout_flags
      puede contener IORING_TIMEOUT_ABS para un valor de tiempo de espera absoluto, o
      0 para un tiempo de espera relativo. off puede contener un recuento de eventos de finalización. Un
      tiempo de espera desencadenará un evento de despertar en el anillo de
      finalización para cualquiera que esté esperando eventos. Se cumple una
      condición de tiempo de espera cuando expira el tiempo de espera
      especificado o cuando se han completado el número especificado de
      eventos. Cualquiera de las condiciones desencadenará el evento. Si se
      establece en 0, los eventos completados no se cuentan, lo que
      efectivamente actúa como un temporizador. Los tiempos de espera de
      io_uring usan el
      CLOCK_MONOTONIC como fuente de reloj predeterminada. La solicitud se
      completará con -ETIME si el tiempo de espera se completó a través de
      la expiración del temporizador, o 0 si el tiempo de espera se completó a través de
      solicitudes que se completaron por sí mismas. Si el tiempo de espera fue
      cancelado antes de expirar, la solicitud se completará con -ECANCELED. Disponible desde
      5.4.
    
Desde la versión 5.15, este comando también admite los siguientes modificadores
        en time
out
_fl

    CLOCK_BOOTTIME en lugar de CLOCK_MONOTONIC. Esta fuente de reloj
    difiere en que incluye el tiempo transcurrido si el sistema estuvo suspendido mientras
    había una solicitud de tiempo de espera en 
curso.

IORING_TIMEOUT_REALTIME Si se establece, entonces la fuente de reloj utilizada
    es CLOCK_REALTIME en lugar de CLOCK_MONOTONIC.

Intenta cancelar una solicitud ya emitida. addr debe contener el
      campo user_data de la solicitud que debe ser cancelada. La
      solicitud de cancelación se completará con uno de los siguientes códigos
      de resultado. Si se encuentra, el campo res del cqe contendrá 0. Si no se encuentra,
      res contendrá -ENOENT. Si se encuentra y se intentó cancelar,
      el campo res contendrá -EALREADY. En este caso, la
      solicitud puede o no terminar. En general, las solicitudes que son
      interrumpibles (como la E/S de sockets) serán canceladas, mientras que
      las solicitudes de E/S de disco no pueden ser canceladas si ya han
      comenzado. Disponible desde 
5.5.

IORING_OP_PROVIDE_BUFF
ERS
  
Este comando permite a una aplicación registrar un grupo de búferes para ser
      utilizados por comandos que leen/reciben datos. El uso de búferes de esta manera puede
      eliminar la necesidad de separar el poll + read, lo que proporciona un
      punto conveniente en el tiempo para asignar un búfer para una solicitud dada. A menudo
      no es factible tener tantos búferes disponibles como lecturas o
      recepciones pendientes. Con esta función, la aplicación puede tener su conjunto de búferes
      listo en el kernel, y cuando el archivo o el socket esté listo para leer/recibir
      datos, se puede seleccionar un búfer para la operación. fd debe contener
      el número de búferes a proporcionar, addr debe contener la dirección inicial
      desde la que añadir búferes, len debe contener la longitud de cada
      búfer a añadir del rango, buf_group debe contener el ID de grupo
      de este rango de búferes, y off debe contener el ID de búfer inicial
      de este rango de búferes. Con esto establecido, el kernel añade búferes
      comenzando con la dirección de memoria en addr, cada uno con una longitud de
      len. Por lo tanto, la aplicación debe proporcionar len * fd de memoria en addr. Los búferes se agrupan por el ID de grupo, y cada
      búfer dentro de este grupo será idéntico en tamaño según los argumentos anteriores.
      Esto permite a la aplicación proporcionar diferentes grupos de
      búferes, y esto se usa a menudo para tener búferes de diferentes tamaños
      disponibles dependiendo de cuáles sean las expectativas de la solicitud
      individual. Al enviar una solicitud que debe usar un búfer proporcionado, el
      flag IOSQE_BUFFER_SELECT debe estar establecido, y buf_group debe
      establecerse en el ID de grupo de búferes deseado del que se debe seleccionar
      el búfer. Disponible desde la versión 
5.7.

IORING_OP_SEND
_ZC
  
Emite el equivalente de copia cero de una llamada al sistema send(2). Similar a
      IORING_OP_SEND, pero intenta evitar hacer copias intermedias de
      datos. La ejecución de copia cero no está garantizada y puede recurrir a la copia.
      La solicitud también puede fallar con -EOPNOTSUPP, cuando un protocolo no
      soporta copia cero, en cuyo caso se recomienda a los usuarios usar envíos con copia
      en su lugar.
    
El campo flags de la primera struct io_uring_cqe
        probablemente contendrá IORING_CQE_F_MORE, lo que significa que habrá
        un segundo evento de finalización / notificación para la solicitud, con el
        campo user_data establecido en el mismo valor. El usuario no debe modificar
        el búfer de datos hasta que se publique la notificación. El primer cqe sigue
        las reglas habituales y por lo tanto su campo res contendrá el número de
        bytes enviados o un código de error negativo. El campo res
        de la notificación se establecerá en cero y el campo flags contendrá
        IORING_CQE_F_NOTIF. El modelo de dos pasos es necesario porque el
        kernel puede retener los búferes durante mucho tiempo, p. ej. esperando un ACK
        de TCP, y tener un cqe separado para las finalizaciones de solicitudes permite al espacio de usuario
        enviar más datos sin retrasos adicionales. Tenga en cuenta, las notificaciones solo
        son responsables de controlar el tiempo de vida de los búferes, y como tales
        no significan nada sobre si los datos han sido realmente enviados o
        recibidos por el otro extremo. Incluso las solicitudes con error pueden generar una
        notificación, y el usuario debe comprobar IORING_CQE_F_MORE
        en lugar de confiar en el 
resultado.
    
fd debe establecerse en el descriptor de archivo del socket,
        addr debe contener un puntero al búfer, len denota la
        longitud del búfer a enviar, y msg_flags contiene los flags
        asociados con la llamada al sistema. Cuando addr2 no es cero, apunta
        a la dirección del destino con addr_len especificando su tamaño,
        convirtiendo la solicitud en un equivalente de la llamada al sistema 
sendto(2).
    
Disponible desde 
6.0.

Cuando se especifica esta bandera, el SQE no se iniciará antes de que se completen los SQE enviados previamente, y los nuevos SQE no se iniciarán antes de que este se complete. Disponible desde la versión

IOSQE_IO_LI
NK
  
Cuando se especifica esta bandera, el SQE forma un enlace con el siguiente SQE en el
      ring de envío. Ese siguiente SQE no se iniciará antes de que la solicitud
      anterior se complete. Esto, en efecto, forma una cadena de SQE, que puede ser
      de longitud arbitraria. El final de la cadena lo marca el primer SQE que
      no tiene esta bandera establecida. Las cadenas no se soportan a través de
      límites de envío. Incluso si el último SQE en un envío tiene esta bandera
      establecida, aún terminará la cadena actual. Esta bandera no tiene efecto sobre
      envíos de SQE anteriores, ni impacta a los SQE que están fuera del
      final de la cadena. Esto significa que múltiples cadenas pueden estar ejecutándose en
      paralelo, o cadenas y SQE individuales. Solo los miembros dentro de la cadena son
      serializados. Una cadena de SQE se romperá si cualquier solicitud en esa cadena
      termina en error. io_uring considera cualquier resultado inesperado como un error. Esto
      significa que, por ejemplo, una lectura corta también terminará el resto de la
      cadena. Si una cadena de enlaces de SQE se rompe, la parte no iniciada restante de la
      cadena será terminada y completada con -ECANCELED como el
      código de error. Disponible desde la versión 
5.3.
  
IOSQE_IO_HARDL
INK
  
Como IOSQE_IO_LINK, pero no se rompe independientemente del resultado de la
      finalización. Tenga en cuenta que el enlace aún se romperá si falla el envío de la
      solicitud principal, los enlaces duros solo son resistentes en presencia de
      resultados de finalización para solicitudes que se enviaron correctamente.
      IOSQE_IO_HARDLINK implica IOSQE_IO_LINK. Disponible desde
      la versión 
5.5.

NC
  
El funcionamiento normal de io_uring es intentar emitir un sqe como no bloqueante
      primero, y si eso falla, ejecutarlo de manera asíncrona. Para soportar una
      operación superpuesta más eficiente de solicitudes que la
      aplicación sabe/asume que siempre (o la mayoría de las veces) se bloquearán, la aplicación puede
      pedir que un sqe se emita de forma asíncrona desde el inicio. Disponible desde
      la versión 
5.6.
  
IOSQE_BUFFER_SEL
ECT
  
Se usa en conjunto con el comando IORING_OP_PROVIDE_BUFFERS,
      que registra un pool de buffers para ser usados por comandos que leen o
      reciben datos. Cuando se registran buffers para este caso de uso, y esta bandera
      está establecida en el comando, io_uring tomará un buffer de este pool cuando la
      solicitud esté lista para recibir o leer datos. Si es exitoso, el CQE resultante
      tendrá IORING_CQE_F_BUFFER establecido en la parte de flags de la
      estructura, y los bits superiores IORING_CQE_BUFFER_SHIFT contendrán el ID de
      los buffers seleccionados. Esto permite a la aplicación saber exactamente qué
      buffer fue seleccionado para la operación. Si no hay buffers disponibles y
      esta bandera está establecida, la solicitud fallará con -ENOBUFS como el
      código de error. Una vez que un buffer ha sido usado, ya no está disponible en el
      pool del kernel. La aplicación debe volver a registrar el buffer dado cuando
      esté listo para reciclarlo (por ejemplo, cuando haya terminado de usarlo). Disponible desde
      la versión 
5.7.
  
IOSQE_CQE_SKIP_SUCC
ESS
  
No generar un CQE si la solicitud se completa exitosamente. Si la solicitud
      falla, un CQE apropiado se publicará como de costumbre y si no hay
      IOSQE_IO_HARDLINK, los CQE para todas las solicitudes enlazadas serán omitidos.
      La noción de fallo/éxito es específica del opcode y es la misma que al
      romper cadenas de IOSQE_IO_LINK. Un caso especial es cuando la
      solicitud tiene un timeout enlazado, entonces la generación del CQE para el timeout
      enlazado se decide únicamente por si tiene IOSQE_CQE_SKIP_SUCCESS
      establecido, independientemente de si expiró o fue cancelado. En otras palabras, si un
      timeout enlazado tiene la bandera establecida, está garantizado que no publicará un CQE.
    
La semántica se elige para acomodar varios casos de uso.
        Primero, cuando todas las solicitudes excepto la última de un enlace normal sin timeouts
        enlazados están marcadas con la bandera, solo se publica un CQE por enlace.
        Adicionalmente, permite la supresión de CQE en casos donde los efectos
        secundarios de una operación ejecutada exitosamente son suficientes para que el espacio de usuario
        conozca el estado del sistema. Un ejemplo sería escribir en un
        archivo de 
sincronización.
    
Esta bandera es incompatible con IOSQE_IO_DRAIN. Usar
        ambos en un mismo ring es comportamiento indefinido, incluso cuando no
        se usan juntos en una misma solicitud. Actualmente, después de la primera
        solicitud con IOSQE_CQE_SKIP_SUCCESS, todas las solicitudes subsecuentes
        marcadas con drain fallarán en el momento del envío. Tenga en cuenta que el reporte de
        errores es solo el mejor esfuerzo, y las restricciones pueden cambiar en el
        
futuro.

    __u32    flags;
}
;

user_data es copiado del campo del mismo nombre en la
    entrada de la cola de envío. El caso de uso principal es almacenar datos que la
    aplicación necesitará acceder al finalizar esta E/S particular. El

    en conjunto con IOSQE_BUFFER_SELECT o IORING_OP_MSG_RING,

    a través de este campo. Se describen en la sección ERRORES DE
  CQE
.

    documentados en las páginas del manual preadv2(2) y pwritev2(2),

    el número de bytes transferidos en caso de que la operación sea exitosa. Por lo tanto,
    tanto el retorno de error como el de éxito se pueden encontrar en ese campo en el CQE.

    otros tipos de solicitudes, los valores de retorno están documentados en la página del manual
