DESCRIPCIÓ

N

iodine le permite tunelizar datos IPv4 a través de un servidor DNS. Esto puede ser útil en situaciones donde el acceso a Internet está protegido por un cortafuegos, pero se permiten las consultas DNS. Necesita un dispositivo TUN/TAP para funcionar. El ancho de banda es asimétrico, con un máximo medido de 680 kbit/s de subida y 2,3 Mbit/s de bajada en una red de prueba LAN por cable. El rendimiento sostenido realista en una red Wifi que utiliza una caché DNS de grado operador se ha medido en unos 50 kbit/s de subida y más de 200 kbit/s de bajada. iodine es la aplicación cliente, iodined es el

servidor.

Nota: se requiere que el servidor y el cliente hablen exactamente el mismo protocolo. En la ma

yoría de los casos, esto significa ejecutar la misma versión de iodine. Desafortunadamente, imp
lementar compatibilidad de protocolo hacia atrás y hacia adelante generalmente no es factible.

Opciones del

cliente:
-
r
Omitir el modo UDP crudo. Si no se usa, iodine intentará obtener la dirección IP pública del host iodined y probar si es accesible directamente. Si lo es, el tráfico se enviará al servidor en lugar del relé
DNS.
-R
rdomain
Usar el dominio de enrutamiento de OpenBSD 'rdomain' para la conexión
DNS.
-m
fragsize
Forzar el tamaño máximo del fragmento de bajada. Si no se establece, el cliente sondeará automáticamente el tamaño máximo de fragmento de bajada
aceptado.
-M
namelen
Longitud máxima de los nombres de host de subida, por defecto 255. Rango utilizable de aproximadamente 100 a 255. Use esta opción para reducir el ancho de banda de subida en favor del ancho de banda de bajada. También es útil para servidores DNS que se comportan de manera poco fiable al usar nombres de host de longitud completa, lo que se nota cuando el sondeo automático del tamaño del fragmento devuelve resultados muy diferentes cada
vez.
-T
dnstype
Anulación del tipo de solicitud DNS. Por defecto, la autodetección sondeará los tipos de solicitud DNS que funcionan y seleccionará el tipo de solicitud que se espera que proporcione el mayor ancho de banda. Sin embargo, puede resultar que un relé DNS imponga límites que distorsionen la imagen, lo que puede llevar a que un tipo de solicitud DNS "inesperado" proporcione más ancho de banda. En ese caso, use esta opción para anular la autodetección. En orden (esperado) de ancho de banda decreciente, los tipos de solicitud DNS soportados son: NULL, PRIVATE, TXT, SRV, MX, CNAME y A (devolviendo CNAME). Tenga en cuenta que SRV, MX y A pueden/causarán búsquedas adicionales por parte de servidores de nombres en caché "inteligentes" para obtener una dirección IP real, lo que puede ralentizar o fallar completamente. El tipo PRIVATE usa el valor 65399 (en el rango de 'uso privado') y requiere servidores que implementen RFC
3597.
-O
downenc
Forzar el tipo de codificación de bajada para todas las respuestas de tipo de consulta excepto NULL. Por defecto es autodetectado, pero puede no detectar todos los problemas con los códec más avanzados. Use esta opción para anular la autodetección. Base32 es el códec de menor calidad y siempre debería funcionar; esto se usa cuando la autodetección falla. Base64 proporciona más ancho de banda, pero puede no funcionar en todos los servidores de nombres. Base64u es igual a Base64 excepto en usar el guion bajo ('_') en lugar del signo más ('+'), posiblemente funcionando donde Base64 no lo hace. Base128 usa valores de byte altos (mayormente letras acentuadas en iso8859-1), lo que podría funcionar con algunos servidores de nombres. Para consultas TXT, Raw proporcionará el máximo rendimiento, pero esto solo funcionará si la ruta del servidor de nombres es completamente 8-bit-clean para respuestas que se supone son "texto
legible".
-L
0|1
Interruptor de modo perezoso (lazy). -L1 (por defecto): Usar el modo perezoso para un rendimiento mejorado y una latencia reducida. Una minoría muy pequeña de relés DNS parece ser incapaz de manejar el patrón de tráfico del modo perezoso, resultando en que no lleguen datos o muy pocos. El cliente iodine detectará esto e intentará volver al modo heredado, pero esto puede no funcionar siempre. En estas situaciones use -L0 para forzar la ejecución en modo heredado (implica
-I1).
-I
interval
Intervalo máximo entre solicitudes (pings) para que los servidores DNS intermedios no agoten el tiempo de espera. Por defecto es 4 en modo perezoso, lo que funcionará bien en la mayoría
de los casos. Cuando ocurren demasiados errores SERVFAIL, iodine reducirá esto automáticamente a 1. Para obtener el tráfico DNS mínimo absoluto, aumente bien por encima de 4, pero
no tanto que comiencen a ocurrir errores SERVFAIL. Hay algunos relés DNS con tiempos de espera muy pequeños, notablemente dnsadvantage.com (ultradns), que darán errores SERVFAIL incluso
con -I1; los datos seguirán pasando, y estos errores pueden ignorarse. El valor máximo útil es 59, ya que iodined cerrará la conexión de un cliente después de 60 segundos de inactividad.

Opciones del

servidor:
-
c
Deshabilitar la comprobación de la dirección IP del cliente en todas las solicitudes entrantes. Por defecto, las solicitudes que se originan en direcciones IP que no coinciden serán rechazadas, sin embargo esto causará problemas cuando las solicitudes se enruten a través de un clúster de servidores
DNS.
-
s
No intentar configurar la dirección IP o el MTU. Esto solo debe usarse si ya ha configurado el dispositivo que se
usará.
-
D
Aumentar el nivel de depuración. El nivel 1 imprime información sobre cada paquete RX/TX. Implica la opción -f. En el nivel 2 (-DD) o superior, las consultas DNS se imprimirán literalmente. Al usar la codificación de subida Base128, esto es mejor verlo como texto ISO Latin-1 en lugar de (ilegal) UTF-8. Esto es fácilmente hecho con : "LC_ALL=C luit iodined -DD ..." (ver luit(1)
).
-m
mtu
Establece 'mtu' como el tamaño de mtu para el dispositivo tun. Esto se enviará al cliente al iniciar sesión, y el cliente usará el mismo mtu para su dispositivo tun. Por defecto 1130. Ten en cuenta que el tráfico DNS se fragmentará automáticamente cuando sea
necesario.
-l external|listen_
ip4
Hace que el servidor escuche solo en 'listen_ip4' para solicitudes IPv4 entrantes. Por defecto, las solicitudes entrantes se aceptan desde todas las interfaces (0.0.0.0). Un nombre de dominio puede usarse como argumento - usa uno con solo un registro A. Si listen_ip4 es 'external', iodined usará el servicio DNS de opendns.com para obtener la IP externa del host y usarla como dirección de
escucha.
-L
listen_ip6
Hace que el servidor escuche solo en 'listen_ip6' para solicitudes IPv6 entrantes. Por defecto, las solicitudes entrantes se aceptan desde todas las interfaces (::). Un nombre de dominio puede usarse como argumento - usa uno con solo un registro
AAAA.
-p
port
Hace que el servidor escuche en 'port' en lugar de 53 para el tráfico. Si 'listen_ip4' no incluye localhost, este 'port' puede ser el mismo que 'dnsport'. Nota: Debes asegurarte de que las solicitudes dns se reenvíen a este puerto tú
mismo.
-n
auto|external_ip
La dirección IP a devolver en las respuestas NS. Por defecto se devuelve la dirección usada como destino en la consulta. Si external_ip es 'auto', iodined usará el servicio DNS de opendns.com para obtener la IP externa del host y usarla para las respuestas
NS.
-b
dnsport
Si se especifica este puerto, todas las solicitudes entrantes que no estén dentro del dominio del túnel se reenviarán a este puerto en localhost, para ser manejadas por un dns real. Si 'listen_ip' no incluye localhost, este 'dnsport' puede ser el mismo que 'port'. Nota: El reenvío no es totalmente transparente, y no se recomienda su uso en entornos de
producción.
-i
max_idle_time
Hace que el servidor se detenga después de max_idl
e_time segundos si no se ha recibido tráfic
o. Esto debe combinarse con systemd o upstart par
a activación bajo demanda para ser efectivo.

SEGURIDA

D

El inicio de sesión es un hash MD5 de desafío-respuesta relativamente seguro, con la contraseña nunca pasando por la línea. Sin embargo, todos los demás datos son NO cifrados de ninguna manera. El tráfico dns también es vulnerable a ataques de repetición, inyección y hombre en el medio, especialmente cuando iodined se usa con la opción -c. Se recomienda encarecidamente el uso de ssh o vpn para túneles. En tanto el servidor como el cliente, usa iptables, pf u otros cortafuegos para bloquear todo el tráfico que entra desde

las interfaces tun, excepto hacia l
os puertos ssh o vpn utilizados.
