ioctl(2) Manual de Llamadas al Sistema ioctl(2)

NOMBRE

ioctl - controlar un dispositivo

BIBLIOTECA

Biblioteca C estándar (libc,-lc)

SINOPSIS

#include <sys/ioctl.h>
int ioctl(int fd, unsigned long op, ...);  /* glibc, BSD */
int ioctl(int fd, int op, ...);            /* musl, otros UNIX */

DESCRIPCIÓN

La ioctl() La llamada al sistema manipula los parámetros subyacentes del dispositivo de archivos especiales. En particular, muchas características operativas de archivos especiales de caracteres (por ejemplo, terminales) pueden controlarse con ioctl() operaciones. El argumento fd debe ser un descriptor de archivo abierto.

El segundo argumento es un código de operación dependiente del dispositivo. El tercer argumento es un puntero sin tipo a la memoria. Tradicionalmente es char *argp (de los días anteriores a que void * fuera C válido), y se le llamará así en esta discusión.

Un ioctl() op tiene codificado en él si el argumento es un parámetro in o un parámetro out , y el tamaño del argumento argp en bytes. Las macros y definiciones utilizadas para especificar un ioctl() op se encuentran en el archivo <sys/ioctl.h>. Vea NOTAS.

VALOR DE RETORNO

Normalmente, en caso de éxito se devuelve cero. Algunas ioctl() operaciones usan el valor de retorno como un parámetro de salida y devuelven un valor no negativo en caso de éxito. En caso de error, se devuelve -1, y errno se establece para indicar el error.

ERRORES

EBADF
fd no es un descriptor de archivo válido.
EFAULT
argp referencia un área de memoria inaccesible.
EINVAL
op o argp no es válido.
ENOTTY
fd no está asociado con un dispositivo especial de caracteres.
ENOTTY
La operación especificada no se aplica al tipo de objeto que el descriptor de archivo fd referencia.

VERSIONES

Los argumentos, los retornos y la semántica de ioctl() varían según el controlador de dispositivo en cuestión (la llamada se usa como un mecanismo general para operaciones que no se ajustan limpiamente al modelo de E/S de flujo de UNIX).

ESTÁNDARES

Ninguno.

HISTORIA

La versión 7 de AT&T UNIX tiene 

ioctl(int fd, int op, struct sgttyb *argp);

(donde struct sgttyb ha sido utilizado históricamente por stty(2) y gtty(2), y es polimórfico por tipo de operación (como lo sería void * si hubiera estado disponible)).

SysIII documenta arg sin ningún tipo.

4.3BSD tiene 

ioctl(int d, unsigned long op, char *argp);

(con char * de manera similar en lugar de void *).

SysVr4 tiene 

int ioctl(int fd, int op, ...  /* arg */);

NOTAS

Para usar esta llamada, se necesita un descriptor de archivo abierto. A menudo la open(2) llamada tiene efectos secundarios no deseados, que pueden evitarse en Linux dándole el O_NONBLOCK indicador.

Estructura de ioctl

Los valores de op de ioctl son constantes de 32 bits. En principio, estas constantes son completamente arbitrarias, pero la gente ha intentado construir alguna estructura en ellas.

La situación antigua de Linux era la de constantes mayormente de 16 bits, donde el último byte es un número de serie, y el byte(s) anterior(es) dan un tipo que indica el controlador. A veces se usaba el número mayor: 0x03 para los HDIO_* ioctls, 0x06 para los LP* ioctls. Y a veces se usaban una o más letras ASCII. Por ejemplo, TCGETS tiene el valor 0x00005401, con 0x54 = 'T' que indica el controlador de terminal, y CYGETTIMEOUT tiene el valor 0x00435906, con 0x43 0x59 = 'C' 'Y' que indica el controlador cyclades.

Más tarde (0.98p5) se incorporó más información en el número. Se tienen 2 bits de dirección (00: ninguno, 01: escritura, 10: lectura, 11: lectura/escritura) seguidos de 14 bits de tamaño (dando el tamaño del argumento), seguidos de un tipo de 8 bits (recopilando los ioctls en grupos para un propósito común o un controlador común), y un número de serie de 8 bits.

Las macros que describen esta estructura se encuentran en <asm/ioctl.h> y son _IO(type,nr) y {_IOR,_IOW,_IOWR}(type,nr,size). Usan sizeof(size) de modo que size es un nombre erróneo aquí: este tercer argumento es un tipo de datos.

Tenga en cuenta que los bits de tamaño son muy poco fiables: en muchos casos son incorrectos, ya sea por macros defectuosas que usan sizeof(sizeof(struct)), o por valores heredados.

Por lo tanto, parece que la nueva estructura solo dio desventajas: no ayuda en la verificación, pero causa valores variables para las distintas arquitecturas.
