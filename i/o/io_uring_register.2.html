io_uring_register(2) Linux Programmer's Manual io_uring_register(2)

NOMBRE

io_uring_register - registrar archivos o búferes de usuario para E/S asíncrona

SINOPSIS

#include <liburing.h>
int io_uring_register(unsigned int fd, unsigned int opcode,
                      void *arg, unsigned int nr_args);

DESCRIPCIÓN

La llamada al sistema io_uring_register(2) registra recursos (p. ej., búferes de usuario, archivos, eventfd, personalidad, restricciones) para su uso en una instancia de io_uring(7) referenciada por fd. Registrar archivos o búferes de usuario permite al kernel tomar referencias a largo plazo a estructuras de datos internas o crear mapeos a largo plazo de la memoria de la aplicación, reduciendo en gran medida la sobrecarga por E/S.

fd es el descriptor de archivo devuelto por una llamada a io_uring_setup(2). Si opcode tiene el flag IORING_REGISTER_USE_REGISTERED_RING aplicado con OR, fd es en su lugar el índice de un fd de anillo registrado.

opcode puede ser uno de:

IORING_REGISTER_BUFFERS
arg apunta a un array de struct iovec de nr_args entradas. Los búferes asociados con los iovecs se bloquearán en memoria y se cargarán contra el límite de recursos RLIMIT_MEMLOCK del usuario. Consulte getrlimit(2) para más información. Además, hay un límite de tamaño de 1GiB por búfer. Actualmente, los búferes deben ser memoria anónima, no respaldada por archivo, como la devuelta por malloc(3) o mmap(2) con el flag MAP_ANONYMOUS establecido. Se espera que esta limitación se elimine en el futuro. También se admiten páginas enormes. Tenga en cuenta que la página enorme completa se fijará en el kernel, incluso si solo se usa una parte de ella.

Después de una llamada exitosa, los búferes proporcionados se mapean en el kernel y son elegibles para E/S. Para hacer uso de ellos, la aplicación debe especificar los opcodes IORING_OP_READ_FIXED o IORING_OP_WRITE_FIXED en la entrada de la cola de envío (consulte la definición de struct io_uring_sqe en io_uring_enter(2)), y establecer el campo buf_index al índice de búfer deseado. El rango de memoria descrito por los campos addr y len de la entrada de la cola de envío debe estar dentro del búfer indexado.

Es perfectamente válido configurar un búfer grande y luego solo usar parte de él para una E/S, siempre que el rango esté dentro de la región mapeada originalmente.

Una aplicación puede aumentar o disminuir el tamaño o número de búferes registrados primero anulando el registro de los búferes existentes, y luego emitiendo una nueva llamada a io_uring_register(2) con los nuevos búferes.

Tenga en cuenta que antes de 5.13 el registro de búferes esperaba a que el anillo estuviera inactivo. Si la aplicación actualmente tiene solicitudes en vuelo, el registro esperará a que terminen antes de continuar.

Una aplicación no necesita anular el registro de búferes explícitamente antes de apagar la instancia de io_uring. Tenga en cuenta, sin embargo, que el procesamiento de apagado puede ejecutarse de forma asíncrona dentro del kernel. Como resultado, no se garantiza que las páginas se desfijen inmediatamente en este caso. Disponible desde 5.1.

IORING_REGISTER_BUFFERS2
Registra búferes para E/S. Similar a IORING_REGISTER_BUFFERS pero tiene como objetivo tener una ABI más extensible.

arg apunta a una struct io_uring_rsrc_register, y nr_args debe establecerse al número de bytes en la estructura.


struct io_uring_rsrc_register {
    __u32 nr;
    __u32 flags;
    __u64 resv2;
    __aligned_u64 data;
    __aligned_u64 tags;
};

El campo data contiene un puntero a un array de struct iovec de nr entradas. El campo tags debe ser 0, entonces el etiquetado está deshabilitado, o apuntar a un array de nr "etiquetas" (enteros sin signo de 64 bits). Si una etiqueta es cero, entonces el etiquetado para este recurso particular (un búfer en este caso) está deshabilitado. De lo contrario, después de que el recurso haya sido anulado su registro y ya no se use, se publicará un CQE con user_data establecido en la etiqueta especificada y todos los demás campos puestos a cero.

El campo flags admite los siguientes flags:


IORING_RSRC_REGISTER_SPARSE Si se establece, io_uring registrará nr búferes vacíos, que deben actualizarse antes de su uso. Cuando este flag está establecido, data y tags deben ser NULL. Disponible desde 5.19.

Tenga en cuenta que las actualizaciones de recursos, p. ej. IORING_REGISTER_BUFFERS_UPDATE, no necesariamente desasignan recursos para el momento en que retorna, pero pueden mantenerse vivos hasta que todas las solicitudes que los usan se completen.

Disponible desde 5.13.

IORING_REGISTER_BUFFERS_UPDATE
Actualiza los búferes registrados con otros nuevos, ya sea convirtiendo una entrada dispersa en una real, o reemplazando una entrada existente.

arg debe contener un puntero a una struct io_uring_rsrc_update2, que contiene un desplazamiento en el que comenzar la actualización, y un array de struct iovec. tags apunta a un array de etiquetas. nr debe contener el número de descriptores en los arrays pasados. Consulte IORING_REGISTER_BUFFERS2 para la descripción del etiquetado de recursos.


struct io_uring_rsrc_update2 {
    __u32 offset;
    __u32 resv;
    __aligned_u64 data;
    __aligned_u64 tags;
    __u32 nr;
    __u32 resv2;
};


Disponible desde 5.13.

IORING_UNREGISTER_BUFFERS
Esta operación no toma argumentos, y arg debe pasarse como NULL. Todos los búferes registrados previamente asociados con la instancia de io_uring se liberarán de forma síncrona. Disponible desde 5.1.
IORING_REGISTER_FILES
Registra archivos para E/S. arg contiene un puntero a un array de nr_args descriptores de archivo (enteros con signo de 32 bits).

Para hacer uso de los archivos registrados, el flag IOSQE_FIXED_FILE debe establecerse en el miembro flags de la struct io_uring_sqe, y el miembro fd se establece al índice del archivo en el array de descriptores de archivo.

El conjunto de archivos puede ser disperso, lo que significa que el campo fd en el array puede establecerse a -1. Consulte IORING_REGISTER_FILES_UPDATE para saber cómo actualizar archivos en su lugar.

Tenga en cuenta que antes de 5.13 el registro de archivos esperaba a que el anillo estuviera inactivo. Si la aplicación actualmente tiene solicitudes en vuelo, el registro esperará a que terminen antes de continuar. Consulte IORING_REGISTER_FILES_UPDATE para saber cómo actualizar un conjunto existente sin esa limitación.

Los archivos se anulan automáticamente en su registro cuando la instancia de io_uring se desmonta. Una aplicación solo necesita anular el registro si desea registrar un nuevo conjunto de fds. Disponible desde 5.1.

IORING_REGISTER_FILES2
Registra archivos para E/S. Similar a IORING_REGISTER_FILES.

arg apunta a una struct io_uring_rsrc_register, y nr_args debe establecerse al número de bytes en la estructura.

El campo data contiene un puntero a un array de nr descriptores de archivo (enteros con signo de 32 bits). El campo tags debe ser 0 o apuntar a un array de nr "etiquetas" (enteros sin signo de 64 bits). Consulte IORING_REGISTER_BUFFERS2 para más información sobre el etiquetado de recursos.

Tenga en cuenta que las actualizaciones de recursos, p. ej. IORING_REGISTER_FILES_UPDATE, no necesariamente desasignan recursos, pueden mantenerse hasta que todas las solicitudes que usan ese recurso se completen.

Disponible desde 5.13.

IORING_REGISTER_FILES_UPDATE
Esta operación reemplaza archivos existentes en el conjunto de archivos registrados con nuevos, ya sea convirtiendo una entrada dispersa (una donde fd es igual a -1) en una real, eliminando una entrada existente (la nueva se establece en -1), o reemplazando una entrada existente con una nueva entrada existente.

arg debe contener un puntero a una struct io_uring_rsrc_update, que contiene un desplazamiento en el que comenzar la actualización, y un arreglo de descriptores de archivo a usar para la actualización. nr_args debe contener el número de descriptores en el arreglo pasado. Disponible desde 5.5.

Los descriptores de archivo pueden omitirse si se establecen en IORING_REGISTER_FILES_SKIP. Omitir un fd no tocará el archivo asociado con el fd anterior en ese índice. Disponible desde 5.12.

IORING_REGISTER_FILES_UPDATE2
Similar a IORING_REGISTER_FILES_UPDATE, reemplaza archivos existentes en el conjunto de archivos registrados con nuevos, ya sea convirtiendo una entrada dispersa (una donde fd es igual a -1) en una real, eliminando una entrada existente (la nueva se establece en -1), o reemplazando una entrada existente con una nueva entrada existente.

arg debe contener un puntero a una struct io_uring_rsrc_update2, que contiene un desplazamiento en el que comenzar la actualización, y un arreglo de descriptores de archivo a usar para la actualización almacenado en data. tags apunta a un arreglo de etiquetas. nr debe contener el número de descriptores en los arreglos pasados. Consulte IORING_REGISTER_BUFFERS2 para la descripción del etiquetado de recursos.

Disponible desde 5.13.

IORING_UNREGISTER_FILES
Esta operación no requiere argumento, y arg debe pasarse como NULL. Todos los archivos previamente registrados asociados con la instancia de io_uring serán anulados en su registro. Disponible desde 5.1.
IORING_REGISTER_EVENTFD
Es posible usar eventfd(2) para recibir notificaciones de eventos de finalización en una instancia de io_uring. Si esto se desea, se puede registrar un descriptor de archivo eventfd mediante esta operación. arg debe contener un puntero al descriptor de archivo eventfd, y nr_args debe ser 1. Tenga en cuenta que, aunque io_uring generalmente se cuida de evitar eventos espurios, estos pueden ocurrir. De manera similar, las finalizaciones por lotes de CQEs pueden solo desencadenar una única notificación eventfd incluso si se publican múltiples CQEs. La aplicación no debe hacer suposiciones sobre el número de eventos disponibles que tengan una correlación directa con las notificaciones eventfd publicadas. Una notificación eventfd debe tratarse, por lo tanto, solo como una pista para verificar el anillo CQ en busca de finalizaciones. Disponible desde 5.2.

Una aplicación puede deshabilitar temporalmente las notificaciones, que llegan a través del eventfd registrado, estableciendo el bit IORING_CQ_EVENTFD_DISABLED en el campo flags del anillo CQ. Disponible desde 5.8.

IORING_REGISTER_EVENTFD_ASYNC
Esto funciona igual que IORING_REGISTER_EVENTFD, excepto que las notificaciones solo se publican para eventos que se completan de forma asíncrona. Esto significa que los eventos que se completan en línea mientras se envían no desencadenan un evento de notificación. Los argumentos proporcionados son los mismos que para IORING_REGISTER_EVENTFD. Disponible desde 5.6.
IORING_UNREGISTER_EVENTFD
Anula el registro de un descriptor de archivo eventfd para detener las notificaciones. Dado que actualmente solo se admite un descriptor eventfd, esta operación no toma argumento, y arg debe pasarse como NULL y nr_args debe ser cero. Disponible desde 5.2.
IORING_REGISTER_PROBE
Esta operación devuelve una estructura, io_uring_probe, que contiene información sobre los códigos de operación admitidos por io_uring en el kernel en ejecución. arg debe contener un puntero a una struct io_uring_probe, y nr_args debe contener el tamaño del arreglo ops en esa struct probe. El arreglo ops es del tipo io_uring_probe_op, que contiene el valor del código de operación y un campo flags. Si el campo flags tiene IO_URING_OP_SUPPORTED establecido, entonces este código de operación es compatible con el kernel en ejecución. Disponible desde 5.6.
IORING_REGISTER_PERSONALITY
Esta operación registra las credenciales de la aplicación en ejecución con io_uring, y devuelve un id asociado con estas credenciales. Las aplicaciones que deseen compartir un anillo entre usuarios/procesos separados pueden pasar este id de credencial en el campo personality del sqe. Si se establece, ese sqe particular se emitirá con estas credenciales. Debe invocarse con arg establecido en NULL y nr_args establecido en cero. Disponible desde 5.6.
IORING_UNREGISTER_PERSONALITY
Esta operación anula el registro de una personalidad previamente registrada con io_uring. nr_args debe establecerse en el id en cuestión, y arg debe establecerse en NULL. Disponible desde 5.6.
IORING_REGISTER_ENABLE_RINGS
Esta operación habilita un anillo io_uring iniciado en un estado deshabilitado (se especificó IORING_SETUP_R_DISABLED en la llamada a io_uring_setup(2)). Mientras el anillo io_uring está deshabilitado, no se permiten envíos y los registros no están restringidos.

Después de la ejecución de esta operación, el anillo io_uring está habilitado: se permiten envíos y registros, pero se validarán siguiendo las restricciones registradas (si las hay). Esta operación no toma argumento, debe invocarse con arg establecido en NULL y nr_args establecido en cero. Disponible desde 5.10.

IORING_REGISTER_RESTRICTIONS
arg apunta a un arreglo de struct io_uring_restriction de nr_args entradas.

Con una entrada es posible permitir un opcode de io_uring_register(2), o especificar qué opcode y flags de la entrada de la cola de envío están permitidos, o requerir que se especifiquen ciertas flags (estas flags deben establecerse en cada entrada de la cola de envío).

Todas las restricciones deben enviarse con una sola llamada a io_uring_register(2) y se manejan como una lista de permitidos (los códigos de operación y flags no registrados no están permitidos).

Las restricciones solo se pueden registrar si el anillo io_uring se inició en un estado deshabilitado (se debe especificar IORING_SETUP_R_DISABLED en la llamada a io_uring_setup(2)).

Disponible desde 5.10.

IORING_REGISTER_IOWQ_AFF
Por defecto, los workers asíncronos creados por io_uring heredarán la máscara de CPU de su padre. Normalmente son todas las CPU del sistema, a menos que el padre se ejecute con un conjunto limitado. Si este no es el resultado deseado, la aplicación puede indicar explícitamente a io_uring en qué CPU pueden ejecutarse los workers asíncronos. arg debe apuntar a una máscara cpu_set_t, y nr_args al tamaño en bytes de esa máscara.

Disponible desde 5.14.

IORING_UNREGISTER_IOWQ_AFF
Deshace una máscara de CPU establecida previamente con IORING_REGISTER_IOWQ_AFF. No debe tener arg ni nr_args establecidos.

Disponible desde 5.14.

IORING_REGISTER_IOWQ_MAX_WORKERS
Por defecto, io_uring limita los workers ilimitados creados al número máximo de procesadores establecido por RLIMIT_NPROC y los workers limitados son una función del tamaño del anillo SQ y del número de CPU del sistema. A veces esto puede ser excesivo (o demasiado poco, para los limitados), y este comando proporciona una forma de cambiar el recuento por anillo (por nodo NUMA) en su lugar.

arg debe establecerse en un puntero a unsigned int a un array de dos valores, con los valores del array establecidos al recuento máximo de workers por nodo NUMA. El índice 0 contiene el recuento de workers limitados, y el índice 1 contiene el recuento de workers ilimitados. Al retornar con éxito, el array pasado contendrá los valores máximos anteriores para cada tipo. Si el recuento pasado es 0, entonces este comando devuelve los valores máximos actuales y no modifica la configuración actual. nr_args debe establecerse en 2, ya que el comando toma dos valores.

Disponible desde 5.15.

IORING_REGISTER_RING_FDS
Siempre que se llama a io_uring_enter(2) para enviar una solicitud o esperar completaciones, el kernel debe obtener una referencia al descriptor de archivo. Si la aplicación que usa io_uring es multihilo, la tabla de archivos se marca como compartida, y la obtención y liberación de la referencia del descriptor de archivo es más costosa que para una aplicación no multihilo.

De forma similar a cómo io_uring permite el registro de archivos, esto permite el registro del propio descriptor de archivo del anillo. Esto reduce la sobrecarga de la llamada al sistema io_uring_enter(2).

arg debe establecerse en un puntero a un array de tipo struct io_uring_rsrc_update de nr_args número de entradas. El campo data de esta estructura debe contener un descriptor de archivo io_uring, y el campo offset puede ser -1 o un offset explícito deseado para el valor del descriptor de archivo registrado. Si se usa -1, entonces al retornar con éxito de esta llamada al sistema, el campo contendrá el valor del descriptor de archivo registrado que se usará para futuras llamadas al sistema io_uring_enter(2).

Al completarse con éxito esta solicitud, los descriptores devueltos pueden usarse en lugar del descriptor de archivo real para io_uring_enter(2), siempre que IORING_ENTER_REGISTERED_RING esté establecido en los flags de la llamada al sistema. Este flag indica al kernel que se usa un descriptor registrado en lugar de un descriptor de archivo real.

Cada hilo o proceso que use un anillo debe registrar el descriptor de archivo directamente emitiendo esta solicitud.

El número máximo de descriptores de anillo registrados admitidos está actualmente limitado a 16.

Disponible desde 5.18.

IORING_UNREGISTER_RING_FDS
Anula el registro de descriptores registrados previamente con IORING_REGISTER_RING_FDS.

arg debe establecerse en un puntero a un array de tipo struct io_uring_rsrc_update de nr_args número de entradas. Solo el campo offset debe establecerse en la estructura, conteniendo el offset del descriptor de archivo registrado devuelto previamente por IORING_REGISTER_RING_FDS que la aplicación desea anular el registro.

Tenga en cuenta que esto no se hace automáticamente al salir del anillo, si el hilo o la tarea que registró previamente un descriptor de archivo de anillo no está saliendo. Se recomienda anular manualmente el registro de cualquier descriptor de anillo registrado previamente si el anillo se cierra y la tarea persiste. Esto liberará una ranura de registro, dejándola disponible para uso futuro.

Disponible desde 5.18.

IORING_REGISTER_PBUF_RING
Registra un anillo de búferes compartido para usarse con búferes proporcionados. Esta es una alternativa más reciente al uso de IORING_OP_PROVIDE_BUFFERS que es más eficiente, para usarse con tipos de solicitud que admiten el flag IOSQE_BUFFER_SELECT.

El argumento arg debe rellenarse con la información adecuada. Tiene el siguiente aspecto:


struct io_uring_buf_reg {
    __u64 ring_addr;
    __u32 ring_entries;
    __u16 bgid;
    __u16 flags;
    __u32 min_left;
    __u32 resv[5];
};


El campo ring_addr debe contener la dirección de la memoria asignada para alojar este anillo. La memoria debe estar alineada a página y, por tanto, asignada adecuadamente usando, por ejemplo, posix_memalign(3) o similar. El tamaño del anillo es el producto de ring_entries y el tamaño de struct io_uring_buf. ring_entries es el tamaño deseado del anillo, y debe ser una potencia de 2. El tamaño máximo permitido es 2^15 (32768). bgid es el ID del grupo de búferes asociado con este anillo. Las SQE que seleccionan un búfer tienen un grupo de búferes asociado en su campo buf_group, y las CQE asociadas tendrán IORING_CQE_F_BUFFER establecido en su miembro flags, que también contendrá el ID específico del búfer seleccionado. min_left es el valor mínimo que debe quedar en un anillo de búferes consumido incrementalmente para que el búfer se considere válido. Si no se establece, por defecto es un solo byte. Solo es válido con IOU_PBUF_RING_INC establecido en flags . El resto de los campos están reservados y deben ponerse a cero.

nr_args debe establecerse en 1.

Véase también io_uring_register_buf_ring(3) para más detalles. Disponible desde 5.19.

IORING_UNREGISTER_PBUF_RING
Anula el registro de un anillo de búferes proporcionado registrado previamente. arg debe establecerse en la dirección de una struct io_uring_buf_reg, con solo el campo bgid establecido al ID del grupo de búferes del grupo de búferes proporcionado registrado previamente. nr_args debe establecerse en 1. Véase también IORING_REGISTER_PBUF_RING.

Disponible desde 5.19.

IORING_REGISTER_SYNC_CANCEL
Realiza una solicitud de cancelación síncrona, que funciona de forma similar a IORING_OP_ASYNC_CANCEL excepto que se completa en línea. Esto puede ser útil en escenarios donde las cancelaciones deben ocurrir de forma síncrona, en lugar de necesitar emitir una SQE y esperar la finalización de esa CQE específica.

arg debe establecerse en un puntero a una estructura io_uring_sync_cancel_reg, con los detalles completados para qué solicitud(es) se deben cancelar. Consulte io_uring_register_sync_cancel(3) para obtener detalles sobre eso. Los valores de retorno son los mismos, excepto que se devuelven de forma síncrona en lugar de a través del campo res del CQE. nr_args debe establecerse en 1.

Disponible desde 6.0.

IORING_REGISTER_FILE_ALLOC_RANGE
establece el rango permitido para las asignaciones de índices de archivos fijos dentro del kernel. Cuando las solicitudes que pueden instanciar un nuevo archivo fijo se usan con IORING_FILE_INDEX_ALLOC, la aplicación está pidiendo al kernel que asigne un nuevo descriptor de archivo fijo en lugar de pasar un valor específico para uno. De forma predeterminada, el kernel elegirá cualquier descriptor de archivo fijo disponible dentro del rango disponible. Esto efectivamente permite que la aplicación reserve un rango solo para asignaciones dinámicas, con el resto utilizándose para valores específicos.

nr_args debe establecerse en 1 y arg debe establecerse en un puntero a una estructura io_uring_file_index_range:


struct io_uring_file_index_range {
    __u32 off;
    __u32 len;
    __u64 resv;
};


con off establecido en el valor inicial del rango, y len establecido en el número de descriptores. El campo reservado resv debe borrarse a cero.

La aplicación debe haber registrado primero una tabla de archivos.

Disponible desde 6.0.

IORING_REGISTER_PBUF_STATUS
Se puede usar para recuperar la cabeza actual de un ringbuffer proporcionado anteriormente mediante IORING_REGISTER_PBUF_RING. arg debe apuntar a una


struct io_uring_buf_status {
	__u32	buf_group;	/* entrada */
	__u32	head;		/* salida */
	__u32	resv[8];
};


de la cual arg->buf_group debe contener el ID del grupo de búferes para el anillo de búferes en cuestión, nr_args debe establecerse en 1 y arg->resv debe ponerse a cero. La cabeza actual del ringbuffer se devolverá en arg->head.

Disponible desde 6.8.

IORING_REGISTER_NAPI
Registra una instancia napi con la instancia io_uring de fd. arg debe apuntar a una


struct io_uring_napi {
	__u32	busy_poll_to;
	__u8	prefer_busy_poll;
	__u8	pad[3];
	__u64	resv;
};


en la cual arg->busy_poll_to debe contener el tiempo de espera de busy poll en microsegundos y arg->prefer_busy_poll debe especificar si se debe usar busy polling en lugar de IRQs. nr_args debe establecerse en 1 y arg->pad y arg->resv deben ponerse a cero. Al retornar con éxito, la estructura io_uring_napi apuntada por arg contendrá la configuración usada anteriormente.

Disponible desde 6.9.

IORING_UNREGISTER_NAPI
Anula el registro de una instancia napi registrada previamente mediante IORING_REGISTER_NAPI en la instancia io_uring de fd. arg debe apuntar a una struct io_uring_napi. Al retornar con éxito, la estructura io_uring_napi apuntada por arg contendrá la configuración usada anteriormente.

Disponible desde 6.9.

IORING_REGISTER_CLOCK
Especifica qué id de reloj usará io_uring para los temporizadores mientras espera eventos de finalización con IORING_ENTER_GETEVENTS. Solo es efectivo si se pasa el argumento timeout en struct io_uring_getevents_arg, ignorándose en caso contrario. Cuando se usa junto con IORING_ENTER_ABS_TIMER, interpreta el argumento timeout como tiempo absoluto del reloj especificado.

El reloj predeterminado es CLOCK_MONOTONIC.

Disponible desde 6.12 y admite CLOCK_MONOTONIC y CLOCK_BOOTTIME.

IORING_REGISTER_CLONE_BUFFERS
Admite la clonación de búferes desde un anillo de origen a un anillo de destino, duplicando búferes registrados previamente desde el origen al destino. arg debe establecerse en un puntero a una struct io_uring_clone_buffers y nr_args debe establecerse en 1 . struct io_uring_buf_reg tiene el siguiente aspecto:


struct io_uring_clone_buffers {
    __u32 src_fd;
    __u32 flags;
    __u32 src_off;
    __u32 dst_off;
    __u32 nr;
    __u32 pad[3];
};

donde src_fd indica el fd del anillo de origen, flags son indicadores modificadores para la operación, src_off indica el desplazamiento desde donde comenzar la clonación desde el anillo de origen, dst_off indica el desplazamiento desde donde comenzar la clonación hacia el anillo de destino, y nr indica el número de búferes a clonar en los desplazamientos dados. pad debe rellenarse con ceros. El kernel 6.12 agregó soporte para la clonación de rango completo, donde src_off, dst_off y nr deben establecerse todos en 0, lo que indica la clonación de toda la tabla del origen al destino. El kernel 6.13 agregó soporte para especificar los desplazamientos y cuántos búferes clonar. Además, agregó soporte para clonar en una tabla registrada previamente en el destino también; 6.12 haría fallar esa operación con -EBUSY si se intentara. Para reemplazar nodos existentes, o clonar en una tabla existente, IORING_REGISTER_DST_REPLACE debe establecerse en el miembro flags.

IORING_REGISTER_SEND_MSG_RING
Admite el envío del equivalente a una solicitud IORING_OP_MSG_RING, pero sin tener un anillo de origen disponible. Toma un puntero a una structio_uring_sqe que debe prepararse con io_uring_prep_msg_ring(3) antes de enviarse. Solo admite solicitudes de tipo IORING_MSG_DATA. Disponible desde el kernel 6.13.
IORING_REGISTER_RESIZE_RINGS
Admite el redimensionamiento de los anillos SQ y CQ. Toma un puntero a una structio_uring_params como argumento, donde sq_entries y cq_entries pueden establecerse en los valores deseados. Solo admite un conjunto limitado de indicadores establecidos en el argumento structio_uring_params, notablemente IORING_SETUP_CQSIZE y IORING_SETUP_CLAMP para modificar el dimensionamiento del anillo CQ. Consulte io_uring_resize_rings(3) para obtener detalles. Tenga en cuenta que, si bien liburing se encarga del desmapeo y mapeo del anillo para una operación de redimensionamiento, los usuarios manuales de esta llamada al sistema de registro deben realizar esas operaciones, de manera similar a cuando se crea un nuevo anillo. La estructura structio_uring_params obtendrá los desplazamientos necesarios copiados de vuelta tras la finalización exitosa de esta llamada al sistema, que pueden usarse para mapear en memoria el anillo tal como se habría mapeado un nuevo anillo. Disponible desde el kernel 6.13.
IORING_REGISTER_MEM_REGION
Admite el registro de regiones de memoria con múltiples propósitos, evitando la copia innecesaria de structio_uring_getevents_arg para operaciones de espera que especifican un tiempo de espera o un tiempo de espera mínimo. Toma un puntero a una estructura structio_uring_mem_region_reg, que tiene el siguiente aspecto:


struct io_uring_mem_region_reg {
    __u64 region_uptr;
    __u64 flags;
    __u64 __resv[2];
};

donde region_uptr debe establecerse en la región que se está registrando como regiones de memoria, flags especifica indicadores modificadores (actualmente debe ser IORING_MEM_REGION_REG_WAIT_ARG ). Los campos de relleno deben estar todos establecidos a 0 . Cada región de memoria tiene el siguiente aspecto:


struct io_uring_region_desc {
    __u64 user_addr;
    __u64 size;
    __u32 flags;
    __u32 id;
    __u64 mmap_offset;
    __u64 __resv[4];
};

donde user_addr apunta a las asignaciones de memoria del espacio de usuario, size es el tamaño de la memoria del espacio de usuario. Las regiones de memoria del espacio de usuario admitidas actualmente tienen el siguiente aspecto:


struct io_uring_reg_wait {
    struct __kernel_timespec ts;
    __u32                    min_wait_usec;
    __u32                    flags;
    __u64                    sigmask;
    __u32                    sigmask_sz;
    __u32                    pad[3];
    __u64                    pad2[2];
};

donde ts contiene la información de tiempo de espera para esta región, flags contiene información sobre la región de tiempo de espera, sigmask es un puntero a una máscara de señales, si se usa, y sigmask_sz es el tamaño de esa máscara de señales. Los campos de relleno deben estar todos establecidos a 0 . Actualmente el único indicador válido es IORING_REG_WAIT_TS , que, si se establece, indica que los valores en ts son válidos y deben usarse para una operación de tiempo de espera. El campo user_addr de structio_uring_region_desc debe establecerse en una dirección de miembros de structio_uring_reg_wait, se puede mapear hasta el tamaño de una página. Con el tamaño de 64 bytes por región, eso permite al menos 64 regiones individuales en un sistema con tamaño de página de 4k. Los desplazamientos de estas regiones se usan para una llamada al sistema io_uring_enter(2), siendo el primero 0, el segundo 1, y así sucesivamente. Después del registro de las regiones de espera, se puede usar io_uring_enter(2) con el indicador de entrada IORING_ENTER_EXT_ARG_REG y un argp establecido en el desplazamiento de la región de espera, en lugar de un puntero a una estructura structio_uring_getevent_arg. Si se usa con IORING_ENTER_GETEVENTS , entonces la operación de espera usará la información en la región de espera registrada en lugar de necesitar una estructura io_uring_getevent_arg copiada para cada operación. Para esperas de alta frecuencia, esto puede ahorrar una cantidad considerable de ciclos de CPU. Nota: una vez que se ha registrado una región, no se puede desregistrar. Vive durante toda la vida del anillo. El desplazamiento de una región de espera individual puede modificarse antes de cualquier llamada al sistema io_uring_enter(2). Disponible desde el kernel 6.13.

IORING_REGISTER_ZCRX_IFQ
Registra una cola de interfaz de recepción de copia cero para operaciones de recepción de red. La recepción de copia cero permite al kernel colocar los datos de red entrantes directamente en la memoria proporcionada por la aplicación sin copiarlos, reduciendo la sobrecarga de CPU para cargas de trabajo de red de alto ancho de banda. arg debe apuntar a una estructura struct io_uring_zcrx_ifq_reg, y nr_args debe establecerse en 1.


struct io_uring_zcrx_ifq_reg {
    __u32 if_idx;
    __u32 if_rxq;
    __u32 rq_entries;
    __u32 flags;
    __u64 area_ptr;
    __u64 region_ptr;
    struct io_uring_zcrx_offsets offsets;
    __u32 zcrx_id;
    __u32 __resv2;
    __u64 __resv[3];
};


donde if_idx es el índice de la interfaz de red, if_rxq es el índice de la cola de recepción, rq_entries es el número de entradas en la cola de recarga (se redondeará hacia arriba a una potencia de dos), flags contiene indicadores modificadores, area_ptr apunta a una struct io_uring_zcrx_area_reg que describe el área de memoria a usar, region_ptr apunta a una struct io_uring_region_desc que describe la región de memoria, y tras un retorno exitoso zcrx_id contendrá el ID del contexto de recepción de copia cero registrado. El campo offsets es rellenado por el kernel y contiene los desplazamientos del anillo para la cola de recarga.

El anillo de io_uring debe haberse creado con los indicadores IORING_SETUP_DEFER_TASKRUN y IORING_SETUP_CQE32 o IORING_SETUP_CQE_MIXED establecidos. El llamador debe tener la capacidad CAP_NET_ADMIN.

Disponible desde el kernel 6.15.

IORING_REGISTER_QUERY
Consulta las capacidades de io_uring y la compatibilidad de características. Esta operación no requiere un anillo de io_uring y puede llamarse con fd establecido en -1. Proporciona información sobre los códigos de operación, indicadores y capacidades específicas del subsistema admitidos. arg debe apuntar a una struct io_uring_query_hdr y nr_args debe ser 0.


struct io_uring_query_hdr {
    __u64 next_entry;
    __u64 query_data;
    __u32 query_op;
    __u32 size;
    __s32 result;
    __u32 __resv[3];
};


Se pueden encadenar múltiples consultas mediante next_entry, que apunta a la siguiente struct io_uring_query_hdr (o 0 para la última entrada). query_data apunta a una estructura de datos apropiada para el tipo de consulta. query_op especifica el tipo de consulta y puede ser uno de:

•
IO_URING_QUERY_OPCODES - Devuelve información sobre los códigos de operación e indicadores admitidos en una struct io_uring_query_opcode
•
IO_URING_QUERY_ZCRX - Devuelve información sobre la compatibilidad de recepción de copia cero en una struct io_uring_query_zcrx
•
IO_URING_QUERY_SCQ - Devuelve información sobre el diseño del anillo SQ/CQ en una struct io_uring_query_scq


size debe establecerse en el tamaño de la estructura de datos a la que apunta query_data. Al retornar, result será 0 en caso de éxito, o un código de error negativo.

Disponible desde el kernel 6.15.

IORING_REGISTER_ZCRX_CTRL
Realiza operaciones de control sobre un contexto de recepción de copia cero registrado previamente. arg debe apuntar a una struct zcrx_ctrl y nr_args debe ser 0.


struct zcrx_ctrl {
    __u32 zcrx_id;
    __u32 op;
    __u64 __resv[2];
    union {
        struct zcrx_ctrl_export     zc_export;
        struct zcrx_ctrl_flush_rq   zc_flush;
    };
};


donde zcrx_id es el ID del contexto de recepción de copia cero devuelto por IORING_REGISTER_ZCRX_IFQ, y op especifica la operación de control:

•
ZCRX_CTRL_FLUSH_RQ - Vacía los búferes pendientes de la cola de recarga
•
ZCRX_CTRL_EXPORT - Exporta el contexto de recepción de copia cero para su uso por otros anillos

Disponible desde el kernel 6.15.

VALOR DE RETORNO

En caso de éxito, io_uring_register(2) devuelve 0 o un valor positivo, dependiendo del opcode utilizado. En caso de error, se devuelve un valor de error negativo. El llamador no debe confiar en la variable errno.

ERRORES

EACCES
El campo opcode no está permitido debido a restricciones registradas.
EBADF
Uno o más descriptores de archivo en el arreglo fd no son válidos.
EBADFD
Se especificó IORING_REGISTER_ENABLE_RINGS o IORING_REGISTER_RESTRICTIONS, pero el anillo io_uring no está deshabilitado.
EBUSY
Se especificó IORING_REGISTER_BUFFERS o IORING_REGISTER_FILES o IORING_REGISTER_RESTRICTIONS, pero ya había búferes, archivos o restricciones registrados.
EEXIST
El hilo que realiza el registro no es válido.
EFAULT
el búfer está fuera del espacio de direcciones accesible del proceso, o iov_len es mayor que 1GiB.
EINVAL
Se especificó IORING_REGISTER_BUFFERS o IORING_REGISTER_FILES, pero nr_args es 0.
EINVAL
Se especificó IORING_REGISTER_BUFFERS, pero nr_args excede UIO_MAXIOV
EINVAL
Se especificó IORING_UNREGISTER_BUFFERS o IORING_UNREGISTER_FILES, y nr_args no es cero o arg no es NULL.
EINVAL
Se especificó IORING_REGISTER_RESTRICTIONS, pero nr_args excede el número máximo permitido de restricciones o el opcode de restricción no es válido.
EMFILE
Se especificó IORING_REGISTER_FILES y nr_args excede el número máximo permitido de archivos en un conjunto de archivos fijos.
EMFILE
Se especificó IORING_REGISTER_FILES y agregar nr_args referencias de archivo excedería el número máximo permitido de archivos que el usuario puede tener según el límite de recursos RLIMIT_NOFILE y el llamador no tiene la capacidad CAP_SYS_RESOURCE. Tenga en cuenta que este es un límite por usuario, no por proceso.
ENOMEM
No hay suficientes recursos del kernel disponibles, o el llamador tenía un límite de recursos flexible RLIMIT_MEMLOCK distinto de cero, pero intentó bloquear más memoria de la que el límite permitía. Este límite no se aplica si el proceso es privilegiado (CAP_IPC_LOCK).
ENXIO
Se especificó IORING_UNREGISTER_BUFFERS o IORING_UNREGISTER_FILES, pero no había búferes o archivos registrados.
ENXIO
Intento de registrar archivos o búferes en una instancia de io_uring que ya está sometida a un registro de archivos o búferes, o que está siendo desmantelada.
EOPNOTSUPP
Los búferes de usuario apuntan a memoria respaldada por archivo.
EFAULT
Los búferes de usuario apuntan a memoria respaldada por archivo (kernels más nuevos).
ENOENT
Se especificó IORING_REGISTER_PBUF_STATUS, pero buf_group no hacía referencia a un grupo de búferes actualmente válido.
EINVAL
Se especificó IORING_REGISTER_PBUF_STATUS, pero el grupo de búferes válido especificado por buf_group no hacía referencia a un grupo de búferes registrado mediante IORING_REGISTER_PBUF_RING.
EINVAL
Se especificó IORING_REGISTER_NAPI, pero el anillo asociado con fd no se ha creado con IORING_SETUP_IOPOLL.
