NOMBRE

io_uring_prep_accept - preparar una solicitud de aceptación

SINOPSIS

#include <sys/socket.h>
#include <liburing.h>
void io_uring_prep_accept(struct io_uring_sqe *sqe,
                          int sockfd,
                          struct sockaddr *addr,
                          socklen_t *addrlen,
                          int flags);
void io_uring_prep_accept_direct(struct io_uring_sqe *sqe,
                                 int sockfd,
                                 struct sockaddr *addr,
                                 socklen_t *addrlen,
                                 int flags,
                                 unsigned int file_index);
void io_uring_prep_multishot_accept(struct io_uring_sqe *sqe,
                                    int sockfd,
                                    struct sockaddr *addr,
                                    socklen_t *addrlen,
                                    int flags);
void io_uring_prep_multishot_accept_direct(struct io_uring_sqe *sqe,
                                           int sockfd,
                                           struct sockaddr *addr,
                                           socklen_t *addrlen,
                                           int flags);

DESCRIPCIÓN

La función io_uring_prep_accept(3) y sus tres variantes preparan una solicitud de aceptación similar a accept4(2). La entrada de la cola de envío sqe se configura para usar el descriptor de archivo sockfd para comenzar a aceptar una solicitud de conexión descrita por la dirección del socket en addr y de longitud de estructura addrlen, y utilizando banderas modificadoras en flags.

Las tres variantes permiten combinar la tabla de archivos directa y las características multishot.

Los descriptores directos son descriptores de archivo privados de io_uring. Evitan parte de la sobrecarga asociada con las tablas de archivos compartidas por hilos y se pueden usar en cualquier solicitud de io_uring que tome un descriptor de archivo. Las dos variantes directas aquí crean dichos descriptores directos. Después de su creación, se pueden usar configurando IOSQE_FIXED_FILE en el miembro flags de SQE, y estableciendo el campo fd de SQE al valor del descriptor directo en lugar del descriptor de archivo regular. Los descriptores directos se gestionan como archivos registrados.

Para usar una variante de aceptación directa, la aplicación primero debe haber registrado una tabla de archivos de un tamaño deseado usando io_uring_register_files(3) o io_uring_register_files_sparse(3). Una vez registrada, io_uring_prep_accept_direct(3) permite que una entrada en esa tabla sea seleccionada específicamente a través del argumento file_index. Si la entrada especificada ya contiene un archivo, el archivo se eliminará primero de la tabla y se cerrará, de acuerdo con el comportamiento de actualización de un archivo existente con io_uring_register_files_update(3). file_index también puede establecerse en IORING_FILE_INDEX_ALLOC para esta variante y se seleccionará y devolverá dinámicamente un índice de tabla no utilizado. Igualmente, io_uring_prep_multishot_accept_direct seleccionará y devolverá dinámicamente un índice de tabla no utilizado para cada conexión aceptada. Si se emplearán ambas formas de selección directa, específica y dinámica, consulte io_uring_register_file_alloc_range(3) para configurar la tabla de modo que las entradas seleccionadas dinámicamente se apunten a un rango diferente al que se dirige las solicitudes específicas.

Tenga en cuenta que los kernels antiguos no comprueban el campo file_index de SQE, lo que significa que las aplicaciones no pueden confiar en que se devuelva un CQE res de -EINVAL cuando el kernel es demasiado antiguo, ya que los kernels más antiguos pueden no reconocer que se les está pidiendo que usen una ranura de tabla directa.

Cuando una solicitud de aceptación directa pide que se seleccione dinámicamente una ranura de tabla pero no hay entradas libres, se devuelve -ENFILE como res del CQE.

Las variantes multishot permiten a una aplicación emitir una única solicitud de aceptación, que activará repetidamente un CQE cuando llegue una solicitud de conexión. Al igual que con otras solicitudes de tipo multishot, la aplicación debe observar las flags del CQE y ver si se establece IORING_CQE_F_MORE al completarse como una indicación de si la solicitud de aceptación generará más CQEs. Tenga en cuenta que para las variantes multishot, establecer addr y addrlen puede no tener mucho sentido, ya que el mismo valor se utilizaría para cada conexión aceptada. Esto significa que los datos escritos en addr pueden ser sobrescritos por una nueva conexión antes de que la aplicación haya tenido tiempo de procesar una conexión pasada. Si la aplicación sabe que no puede llegar una nueva conexión antes de que se procese una anterior, puede usarse como se espera. Las variantes multishot están disponibles desde la versión 5.19.

Consulte la página del manual accept4(2) para obtener detalles sobre la propia función de aceptación.

VALOR DE RETORNO

Ninguno

ERRORES

El campo res del CQE contendrá el resultado de la operación.

io_uring_prep_accept(3) genera el descriptor de archivo instalado como su resultado.

io_uring_prep_accept_direct(3) y file_index establecido en un descriptor directo específico genera 0 en caso de éxito. El llamador debe recordar qué descriptor directo se eligió para esta solicitud.

io_uring_prep_accept_direct(3) y file_index establecido en IORING_FILE_INDEX_ALLOC genera el descriptor directo elegido dinámicamente.

io_uring_prep_multishot_accept(3) genera el descriptor de archivo instalado en cada resultado.

io_uring_prep_multishot_accept_direct(3), genera el descriptor directo elegido dinámicamente en cada resultado.

Tenga en cuenta que donde las llamadas al sistema síncronas devolverán -1 en caso de fallo y establecerán errno al valor real del error, io_uring nunca usa errno. En su lugar, genera el errno negado directamente en el campo res del CQE.

NOTAS

Al igual que con cualquier solicitud que pasa datos en una estructura, esos datos deben permanecer válidos hasta que la solicitud se haya enviado correctamente. No es necesario que permanezcan válidos hasta la finalización. Una vez que se ha enviado una solicitud, el estado en el kernel es estable. Los kernels muy tempranos (5.4 y anteriores) requerían que el estado fuera estable hasta que ocurriera la finalización. Las aplicaciones pueden probar este comportamiento inspeccionando la bandera IORING_FEAT_SUBMIT_STABLE devuelta desde io_uring_queue_init_params(3).

Tenga en cuenta que las versiones directas de accept no aceptan SOCK_CLOEXEC, y establecer esa bandera dará como resultado un error -EINVAL en el CQE.
