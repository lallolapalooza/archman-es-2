NOMBRE

io_uring_queue_init - configurar colas de envío y finalización de io_uring

SINOPSIS

#include <liburing.h>
int io_uring_queue_init(unsigned entradas,
                        struct io_uring *anillo,
                        unsigned flags);
int io_uring_queue_init_params(unsigned entradas,
                               struct io_uring *anillo,
                               struct io_uring_params *params);
int io_uring_queue_init_mem(unsigned entradas,
                            struct io_uring *anillo,
                            struct io_uring_params *params,
                            void *buf, size_t buf_size);

DESCRIPCIÓN

La función io_uring_queue_init(3) ejecuta la llamada al sistema io_uring_setup(2) para inicializar las colas de envío y finalización en el kernel con al menos entradas en la cola de envío y luego mapea el descriptor de archivo resultante a memoria compartida entre la aplicación y el kernel.

Por defecto, el anillo CQ tendrá el doble de entradas que las especificadas por entradas para el anillo SQ. Esto es adecuado para cargas de trabajo de archivos o almacenamiento regulares, pero puede ser demasiado pequeño para cargas de trabajo de red. Las entradas del anillo SQ no imponen un límite en el número de solicitudes en curso que el anillo puede soportar, simplemente limita la cantidad que se puede enviar al kernel de una vez (lote). Si el anillo CQ se desborda, por ejemplo, se generan más entradas de las que caben en el anillo antes de que la aplicación pueda recuperarlas, entonces si el kernel soporta IORING_FEAT_NODROP, el anillo entra en un estado de desbordamiento del anillo CQ. De lo contrario, descarta los CQE e incrementa cq.koverflow en struct io_uring con el número de CQE descartados. El estado de desbordamiento se indica con IORING_SQ_CQ_OVERFLOW establecido en las banderas del anillo SQ. A menos que el kernel se quede sin memoria disponible, las entradas no se descartan, pero es una ruta de finalización mucho más lenta y ralentizará el procesamiento de solicitudes. Por esta razón, debe evitarse y el anillo CQ debe dimensionarse adecuadamente para la carga de trabajo. Establecer cq_entries en struct io_uring_params indicará al kernel que asigne esta cantidad de entradas para el anillo CQ, independientemente del tamaño del anillo SQ dado en entradas. Si el valor no es una potencia de 2, se redondeará a la potencia de 2 más cercana.

En caso de éxito, io_uring_queue_init(3) devuelve 0 y anillo apuntará a la memoria compartida que contiene las colas io_uring. En caso de fallo, se devuelve -errno.

flags se pasará a la llamada al sistema io_uring_setup (ver io_uring_setup(2)).

Las variantes io_uring_queue_init_params(3) y io_uring_queue_init_mem(3) pasarán los parámetros indicados por params directamente a la llamada al sistema io_uring_setup(2).

La variante io_uring_queue_init_mem(3) utiliza el buf proporcionado con el tamaño asociado buf_size como memoria para el anillo, utilizando la bandera IORING_SETUP_NO_MMAP en io_uring_setup(2). El buffer pasado a io_uring_queue_init_mem(3) debe estar alineado al tamaño de página en el host, y ya debe estar a cero. Típicamente, el llamador debe asignar una huge page y pasarla a io_uring_queue_init_mem(3). Las páginas asignadas por mmap ya están a cero. io_uring_queue_init_mem(3) devuelve el número de bytes utilizados del buffer proporcionado, para que la aplicación pueda reutilizar el buffer con el desplazamiento devuelto para colocar más anillos en la misma huge page.

En caso de éxito, los recursos mantenidos por anillo deben liberarse mediante una llamada correspondiente a io_uring_queue_exit(3).

VALOR DE RETORNO

io_uring_queue_init(3) y io_uring_queue_init_params(3) devuelven 0 en caso de éxito y -errno en caso de fallo.

io_uring_queue_init_mem(3) devuelve el número de bytes utilizados del buffer proporcionado en caso de éxito, y -errno en caso de fallo.

VER TAMBIÉN

io_uring_setup(2), io_uring_register_ring_fd(3), mmap(2), io_uring_queue_exit(3)
