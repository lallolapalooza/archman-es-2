NOMBRE

img2dcm - Convertir formatos de imagen estándar a formato DICOM

SINOPSIS

img2dcm [opciones] imgfile-in... dcmfile-out

DESCRIPCIÓN

La herramienta img2dcm sirve como una herramienta de conversión de un formato de imagen estándar como JPEG (incluido JPEG-LS) o BMP a DICOM. Se pueden seleccionar diferentes Clases SOP de salida. La información adicional (sobre pacientes, series, etc.) almacenada en el archivo de salida DICOM se puede extraer de otros archivos DICOM que sirven como "plantilla" para el objeto DICOM resultante. img2dcm también se puede configurar para inventar atributos DICOM de tipo 1 y tipo 2 faltantes para funcionar incluso sin ningún conjunto de datos de plantilla.

PARÁMETROS

imgfile-in   archivo de entrada de imagen
dcmfile-out  archivo de salida DICOM ("-" para stdout)

NOTAS

Fuentes de atributos

Para convertir un formato de imagen general a formato DICOM, la aplicación img2dcm puede recibir información de entrada adicional para rellenar atributos obligatorios (y opcionales) en el nuevo archivo DICOM, como información del paciente, estudio y serie. Esta información se puede recopilar utilizando diferentes enfoques, que se pueden combinar y se aplican al archivo resultante en el siguiente orden:

  • Usando la opción --dataset-from, img2dcm se ve obligado a importar atributos de un archivo DICOM existente. El archivo DICOM proporcionado se importa completamente y sirve como base para todas las operaciones de exportación posteriores. Como excepción, el UID de Instancia SOP no se copia con esta opción. Los datos relacionados con la imagen como Filas, Columnas, etc., también se intercambian durante la conversión. Tenga en cuenta que img2dcm no verifica la validez de ningún otro valor de atributo, por ejemplo, no examina secuencias para adaptar ningún atributo al nuevo objeto (imágenes referenciadas, etc.). Por lo tanto, se recomienda utilizar las plantillas en el directorio de datos para objetos SC y VLP (antiguos). Consulte también la sección "Plantillas de entrada". Como alternativa a la opción --dataset-from, se puede usar la opción mutuamente excluyente --dataset-from-xml. En este caso, sin embargo, el archivo debe contener datos XML en el formato producido por dcm2xml.
  • Las opciones --study-from y --series-from se pueden usar para importar información del paciente, estudio y serie de un archivo DICOM existente. Si se especifica --series-from, el archivo DICOM dado es abierto por img2dcm y se importa toda la información obligatoria hasta el nivel de serie. Tenga en cuenta que esto incluye información del paciente, estudio y serie. En el caso de --study-from, se excluye la información de la serie. Usar --study-from y --series-from al mismo tiempo tiene sentido. Si ambas opciones se proporcionan en la línea de comandos, la opción más a la derecha prevalece. Los siguientes atributos se transfieren:
      Nivel del Paciente:
        Nombre del Paciente
        ID del Paciente
        Sexo del Paciente
        Fecha de Nacimiento del Paciente
        Juego de Caracteres Específico
      Nivel del Estudio:
        UID de Instancia del Estudio
        Fecha del Estudio
        Hora del Estudio
        Nombre del Médico Referente
        ID del Estudio
        Número de Acceso
      Nivel de Serie (solo en caso de opción --series-from):
        UID de Instancia de Serie
        Número de Serie
        Fabricante
  • Con las opciones --insert-type2 y --invent-type1 (ambas habilitadas por defecto), los atributos faltantes (atributos de tipo 2) y/o los valores de atributos faltantes (para atributos de tipo 1) se agregan e inventan automáticamente por img2dcm. Tenga en cuenta que estas opciones solo se evalúan si la opción --do-checks está habilitada (por defecto). Si la opción --no-checks está habilitada, no se realizará ninguna inserción automática de atributos.
  • La opción --key se puede utilizar para agregar atributos adicionales al archivo de salida DICOM. También es posible especificar secuencias, elementos y atributos anidados utilizando la opción --key. En estos casos, se debe utilizar una notación especial de "ruta". Los detalles sobre esta notación de ruta se pueden encontrar en la documentación de dcmodify. La opción --key puede estar presente más de una vez. La parte del valor (después del '=') puede estar ausente, lo que hace que el atributo se establezca con longitud cero. Tenga en cuenta que la opción --key se aplica al final, justo antes de guardar el archivo DICOM, por lo que no hay
comprobación de valores en absoluto.

Es posible convertir múltiples archivos de entrada en una imagen DICOM multiframe si la clase SOP DICOM seleccionada soporta multiframe. En particular, las clases SOP de captura secundaria multiframe soportan esta característica. Se seleccionan a través de la opción de línea de c

omandos
--new-sc.

Juegos de

caracteres

Cuando se carga una plantilla de entrada usando --dataset-from o --dataset-from-xml, se usa el juego de caracteres específico de esa plantilla para el archivo DICOM generado. Si las --study-from o --series-from se usan adicionalmente, img2dcm intentará convertir el juego de caracteres de estos atributos al de la plantilla, y reportará un error si eso no es

posible.

Si las --study-from o --series-from se usan sin una plantilla, se usa el juego de caracteres específico de esta fuente para el archivo DICOM generado. Cualquier clave especificada en la línea de comandos con la opción --key se trata como bytes crudos y sobrescribe cualquier atributo que pueda ya estar presente debido a una plantilla o a un archivo de estudio/serie. Por lo tanto, se debe tener cuidado de no especificar un juego de caracteres específico en la línea de comandos si uno podrí

a cargarse desde otro archivo. También es responsabilidad del usuario asegurarse de que los valores de atributo especificados en la línea d
e comandos usen la codificación correcta, ya que no se realizará ninguna conversión antes de que los valores se almacenen en el archivo DICOM.

Plugins de

entrada

La aplicación img2dcm actualmente soporta los formato

s de imagen JPEG, JP
EG-LS y BMP como entrada.

Plugin de entrada

JPEG

Para JPEG, el JPEG original del archivo fuente no se decodifica pero se extrae y se transforma ligeramente (p. ej., se corta la cabecera JFIF) para permitir una conversión rápida incluso de archivos JPEG grandes sin la necesidad de decodificar y recodificar. El plugin JPEG elige la sintaxis de transferencia de salida necesaria automáticamente dependiendo de la codificación real de los datos dentro del archivo JPEG. Por lo tanto, las siguientes sintaxis de transferencia (y sus codificaciones JPEG correspondientes) son usadas por el plugin

JPEG:
  • Proceso de codificación JPEG 1
    Baseline, Lossy, Non-Hierarchical, Sequential, DCT, Huffman, 8 Bit
    Transfer Syntax UID = 1.2.840.10008.1.2.4.
    • 50
  • Proceso de codificación JPEG 2 (8-bit) y 4 (12-bit)
    Extended, Lossy, Non-Hierarchical, Sequential, DCT, Huffman, 8/12 Bit
    Transfer Syntax UID = 1.2.840.10008.1.2.4.
    • 51
  • Proceso de codificación JPEG 10 (8-bit) y 12 (12-bit)
    Full Progression, lossy, Non-Hierarch., Progressive, DCT, Huffman, 8/12 Bit
    Transfer Syntax
    • UID = 1.2.840
.10008.1.2.4.55

Se soportan imágenes en color y en escala de

grises.

El soporte para la sintaxis de transferencia JPEG Extended puede deshabilitarse (opción--disable-ext) así como el soporte para la sintaxis de transferencia JPEG Progressive (retirada) (--disable-p

rogr).

La codificación JPEG sin pérdida así como cualquier modo de codificación JPEG aritmética o jerárquica no son soportados por el

plugin.

La información JFIF (JPEG File Interchange Format) facilita marcadores APPn opcionales en un archivo JPEG. Muchas cámaras digitales no integran tal información JFIF en la salida JPEG que crean. Por ejemplo, JFIF contiene información sobre la relación de aspecto de píxeles de la imagen comprimida. Si quiere que la aplicación img2dcm insista en una cabecera JFIF en el flujo JPEG, puede usar la opción --insist-on-jfif, la cual abortará si no se puede encontrar información JFIF. Por defecto, la información JFIF faltante es

ignorada.

Para DICOM es una especie de "zona gris", si la integración de datos JFIF (o cualquier otro APPn) en el flujo JPEG interno del objeto DICOM está permitida o no. Sin embargo, el enfoque más fiable es cortar esos marcadores y su información del flujo JPEG. Este enfoque también es tomado por la aplicación img2dcm. Por defecto, todos los marcadores APPn son cortados del flujo JPEG original. Sin embargo, si quiere mantener otros marcadores APPn que no sean JFIF (p. ej., información EXIF) dentro del flujo DICOM, la opción --keep-appn hace el truco. También debería ser ligeramente más rápido que cortar la información APPn, porque no es necesario escanear todo el flujo JPEG por tales datos. Como se ha dicho antes, la información JFIF es siempre removida por img2dcm. Sin embargo, al usar esta opción, el marcador APP2 se retiene, pero img2dcm no crea un atributo IC

C Profile (0028,2
000) equivalente.

Plugin de entrada

JPEG-LS

El plugin JPEG-LS ha sido integrado directamente en el plugin JPEG principal. No hay necesidad de que el usuario declare explícitamente de antemano si la entrada es JPEG o

JPEG-LS.

Para JPEG-LS, el JPEG-LS original del archivo fuente no se decodifica pero se extrae y se transforma ligeramente (p. ej., se corta el marcador APP8) para permitir una conversión rápida incluso de archivos JPEG-LS grandes sin la necesidad de decodificar y

recodificar.

El plugin JPEG-LS elige la sintaxis de transferencia de salida necesaria automáticamente dependiendo de la codificación real de los datos dentro del archivo JPEG-LS. Por lo tanto, las siguientes sintaxis de transferencia (y sus codificaciones JPEG-LS correspondientes) son usadas por el plugin

JPEG-LS:
  • Compresión de imagen JPEG-LS sin pérdida
    Transfer Syntax UID = 1.2.840.10008.1.2.4.
    • 80
  • Compresión de imagen JPEG-LS con pérdida (near-lossless)
    Transfer Syntax
    • UID = 1.2.840
.10008.1.2.4.81

Se soportan imágenes en color y en escala de grises. CP-1843 establece que el valor de Planar Configuration (0028,0006) es irrelevante ya que la manera de codificar los componentes está especificada en el flujo de bits JPEG-LS como componentes, líneas o muestras entrelazadas, por lo tanto debe establecerse en 0. Dado que actualmente no está definida en DICOM ninguna transformación de color específica para JPEG-LS, se asume que el flujo JPEG-LS está codificado en el espacio de color

RGB.

Para DICOM está claro que la cabecera SPIFF no debería estar presente en el flujo JPEG-LS interno del objeto DICOM. El plugin simplemente rechaza cualquier archivo JPEG-LS de entrada que contenga una cabecera SPIFF en el marcador

APP8.

Por defecto, todos los marcadores APPn son cortados del flujo JPEG-LS original. Sin embargo, si quiere mantener marcadores APPn (p. ej., información de transformación de color APP8/HP, también conocida como 'mrfx') dentro del flujo DICOM, la opción --keep-appn hace el truco. Preste atención a que el plugin comprobará la transformación de color real especificada en el marcador APP8/HP. Dado qu

e DICOM no permite especificar ninguna transformación de color en el mar
cador APP8, solo se acepta un valor de 0 (sin transformación de color).

Plugin de entrada

BMP

img2dcm soporta BMP como formato de entrada. Sin embargo, hasta ahora solo se soportan las imágenes BMP más comunes. En particular, las imágenes BMP que usan campos de bits o codificación por longitud de ejecución serán rechazadas. Tales imágenes no son comunes. Las

imágenes de entrada serán convertidas o bien en una imagen DICOM con modelo de color RGB y una profundidad de bits de 24, o en una imag
en con modelo de color MONOCHROME2 y 8 bits por píxel. No hay opciones específicas para el ajuste fino de la conversión del formato BMP.

Plugins de

salida

La clase SOP de salida deseada puede seleccionarse en la línea de comandos. Actualmente, están disponibles plugins de exportación para la clase SOP de imagen de captura secundaria (por defecto, opción -sc), las clases SOP de imagen de captura secundaria multiframe (opción -nsc), la clase SOP de imagen fotográfica de luz visible (opción -vl), y las clases SOP de imagen de fotografía oftálmica (opción -oph). Tenga en cuenta que la primera está obsoleta de acuerdo con el estándar DICOM pero se selecciona por defecto porque es ampliamente soportada. Las versiones futuras de img2dcm podrían proporcionar más plugins de salida para otras clases

SOP.

Para las nuevas clases SOP de captura secundaria, no es posible especificar qué clase SOP específica debe usarse para la salida. Eso se debe a que estas nuevas clases SOP se diferencian entre sí por la profundidad de color (1/8/16) y el hecho de si la imagen es blanco/negro o a color. Es por eso que img2dcm decide durante la conversión qué c

lase SOP de salida es
adecuada para una imagen fuente dada.

Aquí hay algunos ejemplos que muestran cómo la aplicación img2dcm puede

usarse.

Igual que arriba, pero indica a img2dcm que lea un archivo BMP en lugar de

Igual que el primer ejemplo, pero escribe un objeto de Imagen de Fotografía de Luz Visible en "out.dcm" y establece PatientName como "Bond^James", que de otro modo quedaría

4

Igual que 1), pero importa la información de paciente/estudio/serie del archivo DICOM "template.dcm". Tenga en cuenta que el atributo PatientName contendrá "Bond^James" al final, cualquier valor de "template.dcm" será sobrescrito. Esto se debe a que la opción -k se aplica al final de la tubería de conversión (ver arriba)
.
5

Igual que 1), pero no realiza ninguna comprobación de atributos y no inserta atributos de tipo 1 y tipo 2. Así, en este caso, se generaría un objeto DICOM inválido. Esto puede ser interesante si el archivo de salida no está destinado a ser completado, sino que se someterá a transformaciones posteriores, por ejemplo, añadir atributos usando dcmodify. Utilice la opción --no-checks solo si sabe lo que está
haciendo.
6

Igual que 1), pero no inserta los atributos de tipo 1 faltantes y/o sus valores. Los atributos de tipo 2 sí se insertarán. Tenga en cuenta que en este caso se debe asegurar que todos los atributos de tipo 1 se proporcionan por otros medios, es decir, añadiéndolos con la opción --key. De lo contrario, img2dcm reportará un error y dejará de
convertir.

Igual que 1), pero transfiere la información APPn como EXIF al flujo JPEG resultante del objeto DICOM. Además, --insist-on-jfif forzará a img2dcm a abortar si no existe información JFIF en el archivo de

REGISTRO DE

EVENTOS

El nivel de registro de eventos de las diversas herramientas de línea de comandos y bibliotecas subyacentes puede ser especificado por el usuario. Por defecto, solo se escriben errores y advertencias en el flujo de error estándar. Usando la opción --verbose también se informan mensajes informativos como detalles del procesamiento. La opción --debug puede usarse para obtener más detalles sobre la actividad interna, por ejemplo, con fines de depuración. Otros niveles de registro pueden seleccionarse usando la opción --log-level. En el modo --quiet solo se reportan errores fatales. En tales eventos de error muy graves, la aplicación normalmente terminará. Para más detalles sobre los diferentes niveles de registro, vea la documentación del módulo

"oflog".

En caso de que el registro de eventos deba escribirse en un archivo (opcionalmente con rotación de archivos de registro), en syslog (Unix) o en el registro de eventos (Windows), puede usarse la opción --log-config. Este archivo de configuración también permite dirigir solo ciertos mensajes a un flujo de salida particular y filtrar ciertos mensajes basándose en el módulo o la aplicación donde se generan. Un archivo de configuración de ejemplo se proporciona en <etcdir>/l

ogger
.cfg.

LÍNEA DE

COMANDOS

Todas las herramientas de línea de comandos usan la siguiente notación para los parámetros: los corchetes encierran valores opcionales (0-1), tres puntos finales indican que se permiten múltiples valores (1-n), una combinación de ambos significa de 0 a n

valores.

Las opciones de la línea de comandos se distinguen de los parámetros por un signo inicial '+' o '-' respectivamente. Usualmente, el orden y la posición de las opciones de la línea de comandos son arbitrarios (es decir, pueden aparecer en cualquier lugar). Sin embargo, si las opciones son mutuamente excluyentes, se usa la aparición más a la derecha. Este comportamiento se ajusta a las reglas de evaluación estándar de los shells Unix

comunes.

Además, se pueden especificar uno o más archivos de comandos usando un signo '@' como prefijo del nombre de archivo (por ejemplo, @command.txt).
