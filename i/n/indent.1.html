Esta página man se genera a partir del archivo indent.texinfo. Esta es la Edición de "El Manual de indent", para la versión de Indent , última actualización

.

El programa indent se puede utilizar para hacer que el código sea más fácil de leer. También puede convertir de un estilo de escritura de C a

otro.

indent entiende una cantidad sustancial sobre la sintaxis de C, pero también intenta lidiar con sintaxis incompletas y mal

formadas.

En la versión 1.2 y versiones más

recientes, el estilo de inde
ntación GNU es el predeterminado.

INVOCACIÓN DE

INDENT

A partir de la versión 1.3, el formato del comando indent

es: 


indent [opciones] [archivos-de-entrada]
indent [opciones] [archivo-de-entrada-único] [-o archivo-de-salida]

Este formato es diferente al de versiones anteriores y otras versiones de indent

.

En la primera forma, se especifica uno o más archivos de entrada. indent crea una copia de seguridad de cada archivo, y el archivo original es reemplazado por su versión indentada. Ver ARCHIVOS DE COPIA DE SEGURIDAD, para una explicación de cómo se crean las copias de

seguridad.

En la segunda forma, solo se especifica un archivo de entrada. En este caso, o cuando se usa la entrada estándar, puede especificar un archivo de salida después de la opción

‘-o’.

Para hacer que indent escriba en la salida estándar, use la opción ‘-st’. Esto solo se permite cuando hay un solo archivo de entrada, o cuando se usa la entrada

estándar.

Si no se nombran archivos de entrada, se lee la entrada estándar. También, si se especifica un nombre de archivo ‘-’, entonces se lee la entrada

estándar.

Como ejemplo, cada uno de los siguientes comandos tomará como entrada el programa ‘slithy_toves.c’ y escribirá su texto indentado en ‘slithy_toves.

out’: 


indent slithy_toves.c -o slithy_toves.out
indent -st slithy_toves.c > slithy_toves.out
cat slithy_toves.c | indent -o slithy_toves.out

La mayoría de las otras opciones de indent controlan cómo se formatean los programas. A partir de la versión 1.2, indent también reconoce un nombre largo para cada nombre de opción. Las opciones largas se prefijan con ‘--’ o ‘+’. [ ‘+’ está siendo reemplazado por ‘--’ para mantener la consistencia con el estándar POSIX.]
En la mayor parte de este documento, se usan los nombres cortos tradicionales por brevedad. Ver RESUMEN DE OPCIONES, para una lista de opciones, incluyendo tanto nombres largos como

cortos.

Aquí hay otro

ejemplo: 


indent -br test/metabolism.c -l85

Esto indentará el programa ‘test/metabolism.c’ usando las opciones ‘-br’ y ‘-l85’, escribirá la salida de vuelta en ‘test/metabolism.c’, y escribirá el contenido original de ‘test/metabolism.c’ en un archivo de copia de seguridad en el directorio

‘test’.

Las invocaciones equivalentes usando nombres largos de opciones para este ejemplo

serían: 


indent --braces-on-if-line --line-length185 test/metabolism.c
indent +braces-on-if-line +line-length185 test/metabolism.c

Si encuentra que a menudo usa indent con las mismas opciones, puede poner esas opciones en un archivo llamado ‘.indent.pro’. indent buscará un archivo de perfil en tres lugares. Primero comprobará la variable de entorno INDENT_PROFILE. Si existe, se espera que su valor nombre el archivo que se va a usar. Si la variable de entorno no existe, indent busca ‘.indent.pro’ en el directorio actual
y lo usa si lo encuentra. Finalmente indent buscará en su directorio de inicio ‘.indent.pro’ y usará ese archivo si lo encuentra. Este comportamiento es diferente al de otras versiones de indent, que cargan ambos archivos si ambos

existen.

El formato de ‘.indent.pro’ es simplemente una lista de opciones, tal como aparecerían en la línea de comandos, separadas por espacios en blanco (tabulaciones, espacios y saltos de línea). Las opciones en ‘.indent.pro’ pueden estar rodeadas por comentarios C o C++, en cuyo caso se

ignoran.

Los interruptores de la línea de comandos se manejan después de procesar ‘ ?.indent.pro’. Las opciones especificadas posteriormente anulan los argumentos especificados anteriormente, con una excepción: las opciones especificadas explícitamente siempre anulan las opciones de fondo (Ver ESTILOS COMUNES). Puede evitar que indent lea un archivo ‘.indent.pro’

especificando
la opción ‘-npro’.

ARCHIVOS DE COPIA DE

SEGURIDAD

A partir de la versión 1.3, GNU indent crea archivos de copia de seguridad al estilo GNU, de la misma manera que lo hace GNU Emacs. Esto significa que se pueden crear nombres de archivo de copia de seguridad simples o numerados

.

Los nombres de archivo de copia de seguridad simples se generan añadiendo un sufijo al nombre del archivo original. El valor predeterminado para este sufijo es la cadena de un carácter ‘~’ (virgulilla). Así, el archivo de copia de seguridad de ‘python.c’ sería ‘python.

c~’.

En lugar del predeterminado, puede especificar cualquier cadena como sufijo configurando la variable de entorno SIMPLE_BACKUP_SUFFIX con su sufijo

preferido.

Las versiones de copia de seguridad numeradas de un archivo ‘momeraths.c’ se ven como ‘momeraths.c.~23~’, donde 23 es la versión de esta copia de seguridad en particular. Al hacer una copia de seguridad numerada del archivo ‘src/momeraths.c’, el archivo de copia de seguridad se llamará ‘src/momeraths.c.~V~’, donde V es uno más que la versión más alta que existe actualmente en el directorio ‘src’. La variable de entorno VERSION_WIDTH controla el número de dígitos, usando relleno de ceros a la izquierda cuando sea necesario. Por ejemplo, configurar esta variable en "2" hará que el archivo de copia de seguridad se llame ‘momeraths.c.

~04~’.

El tipo de archivo de copia de seguridad creado está controlado por el valor de la variable de entorno VERSION_CONTROL. Si es la cadena ‘simple’, entonces solo se crearán copias de seguridad simples. Si su valor es la cadena ‘numbered’, entonces se crearán copias de seguridad numeradas. Si su valor es ‘numbered-existing’, entonces se crearán copias de seguridad numeradas si ya existen copias de seguridad numeradas para el archivo que se está indentando; de lo contrario, se crea una copia de seguridad simple. Si VERSION_CONTROL no está configurada, entonces indent asume el comportamiento de ‘numbered-existing’

.

Otras versiones de indent usan el sufijo ‘.BAK’ al nombrar los archivos de copia de seguridad. Este comportamiento se puede emular configurando SIMPLE_BACKUP_SUFFIX a ‘.

BAK’.

Nótese también que otras versiones de indent crean copias de seguridad en el directorio actual, en lugar del directorio del archivo fuente como indent de GN

U ahora
hace.

ESTILOS

COMUNES

Hay varios estilos comunes de código C, incluyendo el estilo GNU, el estilo Kernighan & Ritchie y el estilo original de Berkeley. Un estilo puede seleccionarse con una sola opción de fondo, que especifica un conjunto de valores para todas las demás opciones. Sin embargo, las opciones especificadas explícitamente siempre anulan las opciones implícitas por una opción de

fondo.

A partir de la versión 1.2, el estilo predeterminado de indent de GNU es el estilo GNU. Por lo tanto, ya no es necesario especificar la opción ‘-gnu’ para obtener este formato, aunque hacerlo no causará un error. Los ajustes de opciones que corresponden al estilo GNU

son: 


-nbad -bap -nbc -bbo -bl -bli2 -bls -ncdb -nce -cp1 -cs -di2
-ndj -nfc1 -nfca -hnl -i2 -ip5 -lp -pcs -nprs -psl -saf -sai
-saw -nsc -nsob

El estilo de codificación GNU es el preferido por el proyecto GNU. Es el estilo que el modo C de GNU Emacs fomenta y que se usa en las partes C de GNU Emacs. (Las personas interesadas en escribir programas para el Proyecto GNU deberían conseguir una copia de "The GNU Coding Standards", que también cubre cuestiones semánticas y de portabilidad como el uso de memoria, el tamaño de los enteros, etc.

)

El estilo Kernighan & Ritchie se usa en todo su conocido libro "The C Programming Language". Se habilita con la opción ‘-kr’. El estilo Kernighan & Ritchie corresponde al siguiente conjunto de

opciones: 


-nbad -bap -bbo -nbc -br -brs -c33 -cd33 -ncdb -ce -ci4 -cli0
-cp33 -cs -d0 -di1 -nfc1 -nfca -hnl -i4 -ip0 -l75 -lp -npcs
-nprs -npsl -saf -sai -saw -nsc -nsob -nss -par

El estilo Kernighan & Ritchie no pone comentarios a la derecha del código en la misma columna en todo momento (ni usa solo un espacio a la derecha del código), así que para este estilo indent ha elegido arbitrariamente la columna

33.

El estilo del indent original de Berkeley se puede obtener especificando ‘-orig’ (o especificando ‘--original’, usando el nombre largo de la opción). Este estilo es equivalente a los siguientes

ajustes: 


-nbad -nbap -bbo -bc -br -brs -c33 -cd33 -cdb -ce -ci4 -cli0
-cp33 -di16 -fc1 -fca -hnl -i4 -ip4 -l75 -lp -npcs -nprs -psl
-saf -sai -saw -sc -nsob -nss -ts8

El estilo Linux se usa en el código del núcleo de Linux y los controladores. El código generalmente tiene que seguir el estilo de codificación de Linux para ser aceptado. Este estilo es equivalente a los siguientes

ajustes: 


-nbad -bap -nbc -bbo -hnl -br -brs -c33 -cd33 -ncdb -ce -ci4 
-cli0 -d0 -di1 -nfc1 -i8 -ip0 -l80 -lp -npcs -nprs -npsl -sai
-saf -saw -ncs -nsc -sob -nfca -cp33 -ss -ts8 -il1

BLANCO

Varios estilos de programación usan líneas en blanco en diferentes lugares. indent tiene una serie de opciones para insertar o eliminar líneas en blanco en lugares

específicos.

La opción ‘-bad’ causas indent para forzar una línea en blanco después de cada bloque de declaraciones. La opción ‘-nbad’ hace que indent no fuerce tales líneas en

blanco.

La opción ‘-bap’ fuerza una línea en blanco después de cada cuerpo de procedimiento. La opción ‘-nbap’ no fuerza tales líneas en

blanco.

La opción ‘-bbb’ fuerza una línea en blanco antes de cada comentario enmarcado (Véase COMENTARIOS.) La opción ‘-nbbb’ no fuerza tales líneas en

blanco.

La opción ‘-sob’ hace que indent trague líneas en blanco opcionales (es decir, cualquier línea en blanco opcional presente en la entrada será eliminada de l

a salida). Si se especifica ‘-nsob’, cualquier línea en blanco p
resente en el archivo de entrada será copiada al archivo de salida.

--blank-lines-after-declaration

s

Por ejemplo, dada la entrada 

char *foo;
char *bar;

COMENTARIO

S

indent formatea tanto comentarios C como C++. Los comentarios C comienzan con ‘/*’, terminan con ‘*/’ y pueden contener caracteres de salto de línea. Los comentarios C++ comienzan con el delimitador ‘//’ y terminan en el salto de

línea.

indent maneja los comentarios de manera diferente dependiendo de su contexto. indent intenta distinguir entre comentarios que siguen a sentencias, comentarios que siguen a declaraciones, comentarios que siguen a directivas de preprocesador, y comentarios que no son precedidos por código de ningún tipo, es decir, que comienzan el texto de la línea (aunque no necesariamente en la columna 1)

.

indent distingue aún más entre comentarios encontrados fuera de procedimientos y agregados, y aquellos encontrados dentro de ellos. En particular, un comentario que comienza una línea encontrada dentro de un procedimiento será sangrado a la columna en la que el código está actualmente sangrado. La excepción a esto es un comentario que comienza en la columna más a la izquierda; dicho comentario es emitido en esa

columna.

indent intenta dejar los comentarios enmarcados sin modificar. La idea general de tal comentario es que está encerrado en un rectángulo o una «caja» de asteriscos o guiones para distinguirlo visualmente. Más precisamente, los comentarios enmarcados se definen como aquellos en los que el ‘/*’ inicial es seguido inmediatamente por el carácter ‘*’, ‘=’, ‘_’, o ‘-’, o aquellos en los que el delimitador de comentario de apertura (‘/*’) está en una línea por sí solo, y la línea siguiente comienza con un ‘*’ en la misma columna que el asterisco del delimitador de

apertura.

Ejemplos de comentarios enmarcados

son: 


/**********************
 * Comment in a box!! *
 **********************/
       /*
        * A different kind of scent,
        * for a different kind of comment.
        */

indent intenta dejar los comentarios enmarcados exactamente como se encuentran en el archivo fuente. Así, la sangría del comentario no se modifica, y su longitud no se verifica de ninguna manera. La única alteración realizada es que un carácter de tabulación incrustado puede ser convertido en el número apropiado de

espacios.

Si se especifica la opción ‘-bbb’, todos estos comentarios enmarcados serán precedidos por una línea en blanco, a menos que tal comentario sea precedido por

código.

Los comentarios que no son comentarios enmarcados pueden ser formateados, lo que significa que la línea se divide para caber dentro de un margen derecho y se rellena a la izquierda con espacios en blanco. Los saltos de línea simples son equivalentes a un espacio, pero las líneas en blanco (dos o más saltos de línea seguidos) se consideran un salto de párrafo. El formateo de comentarios que comienzan después de la primera columna se habilita con la opción ‘-fca’. Para formatear aquellos que comienzan en la columna uno, especifique ‘-fc1’. Tal formateo está deshabilitado por

defecto.

El margen derecho para el formateo tiene un valor predeterminado de 78, pero puede ser cambiado con la opción ‘-lc’. Si el margen especificado no permite que el comentario sea impreso, el margen se extenderá automáticamente durante la duración de ese comentario. El margen no se respeta si el comentario no está siendo

formateado.

Si se especifica la opción ‘-fnc’, todos los comentarios con ‘/*’ incrustado tendrán esa secuencia de caracteres reemplazada por un espacio seguido del carácter ‘*’, eliminando así el

anidamiento.

Si el comentario comienza una línea (es decir, no hay texto de programa a su izquierda), será sangrado a la columna en la que se encontró, a menos que el comentario esté dentro de un bloque de código. En ese caso, tal comentario será alineado con el código sangrado de ese bloque (a menos que el comentario comenzara en la primera columna). Esta alineación puede ser afectada por la opción ‘-d’, que especifica una cantidad por la cual tales comentarios son movidos hacia la izquierda, o des-sangrados. Por ejemplo, ‘-d2’ coloca los comentarios dos espacios a la izquierda del código. Por defecto, los comentarios se alinean con el código, a menos que comiencen en la primera columna, en cuyo caso se dejan allí por defecto --- para alinearlos con el código, especifique

‘-fc1’.

Los comentarios a la derecha del código aparecerán por defecto en la columna 33. Esto puede ser cambiado con una de tres opciones. ‘-c’ especificará la columna para comentarios que siguen al código, ‘-cd’ especifica la columna para comentarios que siguen a declaraciones, y ‘-cp’ especifica la columna para comentarios que siguen a directivas de preprocesador #else y #endif. ‘-dj’ junto con ‘-cd0’ puede usarse para suprimir la alineación de comentarios a la derecha de las declaraciones, haciendo que el comentario siga a un tabulador desde el final de la declaración. Normalmente ‘-cd0’ hace que ‘-c’ se vuelva

efectivo.

Si el código a la izquierda del comentario excede la columna de inicio, la columna del comentario se extenderá a la siguiente columna de tabulación después del final del código, a menos que se especifique la opción ‘-ntac’. En el caso de las directivas de preprocesador, los comentarios se extienden a un espacio después del final de la directiva. Esta extensión dura solo durante la salida de ese comentario en

particular.

La opción ‘-cdb’ coloca los delimitadores de comentario en líneas en blanco. Así, un comentario de una sola línea como /* Loving hug */ puede ser transformado

en: 


/*
   Loving hug
 */

Se pueden colocar asteriscos al comienzo de comentarios de varias líneas con la opción ‘-sc’. Así, el comentario de una sola línea de arriba puede ser transformado (con ‘-cdb -sc’)

en: 


/*
 * Loving hug
 */

SENTENCIA

S

La opción ‘-br’ o ‘-bl’ especifica cómo formatear las

llaves.

La opción ‘-br’ formatea las llaves de sentencia

así: 


if (x > 0) {
  x--;
}

La opción ‘-bl’ las formatea

así: 


if (x > 0)
  {
    x--;
  }

Si usa la opción ‘-bl’, también puede querer especificar la opción ‘-bli’. Esta opción especifica el número de espacios por los que se sangran las llaves. ‘-bli2’, la predeterminada, da el resultado mostrado arriba. ‘-bli0’ resulta en lo

siguiente: 


if (x > 0)
{
  x--;
}

Si está usando la opción ‘-br’, probablemente quiera usar también la opción ‘-ce’. Esto hace que el else en una construcción if-then-else se pegue al ‘}’ inmediatamente anterior. Por ejemplo, con ‘-br -ce’ obtiene lo

siguiente: 


if (x > 0) {
  x--;
} else {
  fprintf (stderr, "...something wrong?\n");
}

Con ‘-br -nce’ ese código aparecería

como 


if (x > 0) {
  x--;
}
else {
  fprintf (stderr, "...something wrong?\n");
}

Se produce una excepción al comportamiento cuando hay un comentario entre la llave derecha y la sentencia else subsiguiente. Mientras que la opción ‘-br’ hará que una llave izquierda salte sobre el comentario, el else no salta sobre el comentario para pegarse porque tiene una fuerte probabilidad de cambiar el significado del

comentario.

La opción ‘-cdw’ hace que el while en un bucle do-while se pegue al ‘}’ inmediatamente anterior. Por ejemplo, con ‘-cdw’ obtiene lo

siguiente: 


do {
  x--;
} while (x);

Con ‘-ncdw’ ese código aparecería

como 


do {
  x--;
}
while (x);

La opción ‘-slc’ permite que una condición sin llaves y su sentencia interna aparezcan en la misma línea. Por

ejemplo: 


if (x) x--;
else x++;

Sin ‘-slc’ ese código aparecería

como 


if (x)
  x--;
else
  x++;

La opción ‘-cli’ especifica el número de espacios por los que las etiquetas case deben ser sangradas a la derecha del containing instrucción s

witch.

El valor por defecto genera código

como: 


switch (i)
  {
  case 0:
    break;
  case 1:
    {
      ++i;
    }
  default:
    break;
  }

Usando ‘-cli2’ esto se convertiría

en: 


switch (i)
  {
    case 0:
      break;
    case 1:
      {
        ++i;
      }
    default:
      break;
  }

La sangría de las llaves debajo de una instrucción case se puede controlar con la opción ‘-cbin’. Por ejemplo, usando ‘-cli2 -cbi0’ resulta

en: 


switch (i)
  {
    case 0:
      break;
    case 1:
    {
      ++i;
    }
    default:
      break;
  }

Si hay un punto y coma en la misma línea que una instrucción for o while la opción ‘-ss’ hará que se coloque un espacio antes del punto y coma. Esto enfatiza el punto y coma, dejando claro que el cuerpo de la instrucción for o while es una instrucción vacía. ‘-nss’ desactiva esta

característica.

La opción ‘-pcs’ hace que se coloque un espacio entre el nombre del procedimiento que se llama y el ‘(’ (por ejemplo, puts ("Hi");. La opción ‘-npcs’ daría puts("Hi");)

.

Si se especifica la opción ‘-cs’, indent pone un espacio entre un operador de conversión y el objeto a convertir. La opción ‘-ncs’ asegura que no haya espacio entre el operador de conversión y el objeto. Recuerda que indent solo conoce los tipos de datos estándar de C y por lo tanto no puede reconocer tipos definidos por el usuario en conversiones. Así (mytype)thing no se trata como una

conversión.

La opción ‘-bs’ asegura que haya un espacio entre la palabra clave sizeof y su argumento. En algunas versiones, esto se conoce como la opción

‘Bill_Shannon’.

La opción ‘-saf’ fuerza un espacio entre una for y el paréntesis siguiente. Este es el valor por

defecto.

La opción ‘-sai’ fuerza un espacio entre una if y el paréntesis siguiente. Este es el valor por

defecto.

La opción ‘-saw’ fuerza un espacio entre una while y el paréntesis siguiente. Este es el valor por

defecto.

La opción ‘-prs’ hace que todos los paréntesis estén separados con un espacio de lo que haya entre ellos. Por ejemplo, usando ‘-prs’ resulta en código

como: 


  while ( ( e_code - s_code ) < ( dec_ind - 1 ) )
    {
      set_buf_break ( bb_dec_ind );
      *e_code++ = ’ ’;
    }

DECLARACIONE

S

Por defecto indent alineará los identificadores en la columna especificada por la opción ‘-di’. Por ejemplo, ‘-di16’ hace que las cosas se vean

así: 


int             foo;
char           *bar;

Usando un valor pequeño (como uno o dos) para la opción ‘-di’ se puede hacer que los identificadores se coloquen en la primera posición disponible; por

ejemplo: 


int foo;
char *bar;

El valor dado a la opción ‘-di’ aún afectará a las variables que se ponen en líneas separadas de sus tipos, por ejemplo ‘-di2’ llevará

a: 


int
  foo;

Si se especifica la opción ‘-bc’, se fuerza un salto de línea después de cada coma en una declaración. Por

ejemplo, 


int a,
  b,
  c;

Con la opción ‘-nbc’ esto se vería

así 


int a, b, c;

La opción ‘-bfda’ hace que se fuerce un salto de línea después de la coma que separa los argumentos de una declaración de función. Los argumentos aparecerán un nivel de sangría más profundo que la declaración de la función. Esto es particularmente útil para funciones con listas de argumentos largas. La opción ‘-bfde’ hace que se fuerce un salto de línea antes del corchete de cierre de la declaración de la función. Para ambas opciones la configuración ’n’ es la por defecto: -nbfda y

-nbfde.

Por

ejemplo, 


void foo (int arg1, char arg2, int *arg3, long arg4, char arg5);
Con la opción ‘-bfda’ esto se vería así 


void foo (
    int arg1,
    char arg2,
    int *arg3,
    long arg4,
    char arg5);

Con, además, la opción ‘-bfde’ esto se vería

así 


void foo (
    int arg1,
    char arg2,
    int *arg3,
    long arg4,
    char arg5
    );

La opción ‘-psl’ hace que el tipo de un procedimiento que se está definiendo se coloque en la línea anterior al nombre del procedimiento. Este estilo es necesario para que el programa etags funcione correctamente, así como algunas de las funciones c-mode de

Emacs.

Debes usar la opción ‘-T’ para decirle a indent el nombre de todos los nombres de tipo en tu programa que están definidos por typedef. ‘-T’ se puede especificar más de una vez, y todos los nombres especificados se usan. Por ejemplo, si tu programa

contiene 


typedef unsigned long CODE_ADDR;
typedef enum {red, blue, green} COLOR;

usarías las opciones ‘-T CODE_ADDR -T

COLOR’.

La opción ‘-brs’ o ‘-bls’ especifica cómo formatear las llaves en las declaraciones de struct. La opción ‘-brs’ formatea las llaves

así: 


struct foo {
  int x;
};

La opción ‘-bls’ las formatea

así: 


struct foo
{
  int x;
};

De manera similar a las opciones de llaves de estructura ‘-brs’ y ‘-bls’,
las opciones de llaves de función ‘-brf’ o ‘-blf’ especifican cómo formatear las llaves en las definiciones de función. La opción ‘-brf’ formatea las llaves

así: 


int one(void) {
  return 1;
};

La opción ‘-blf’ las formatea

así: 


int one(void)
{
  return 1;
};

La opción ‘-sar’ afecta cómo indent representará las listas de inicialización. Sin ‘-sar’ se formatean

así: 


int a[] = {1, 2, 3, 4};
struct s {
  const char *name;
  int x;
} a[] = {
  {"name", 0},
  {"a", 1}
};

Con ‘-sar’ se formatean así, con espacios dentro de las

llaves: 


int a[] = { 1, 2, 3, 4 };
struct s {
  const char *name;
  int x;
} a[] = {
  { "name", 0 },
  { "a", 1 }
};

SANGRÍ

A

El asunto más básico y más controvertido con respecto al formateo de código es precisamente cómo debe lograrse la sangría. Afortunadamente, indent soporta varios estilos de sangría diferentes. El valor por defecto es usar tabulaciones para la sangría, lo cual está especificado por la opción ‘-ut’. Asumiendo el tamaño de tabulación por defecto de 8, el código se vería

así: 


int a(int b)
{
        return b;
|------|
 1 tabulación
}

Para aquellos que prefieren espacios en lugar de tabulaciones, ‘indent’ proporciona la opción ‘-nut’. El mismo código se vería

así: 


int a(int b)
{
        return b;
|------|
8 espacios
}

Otro asunto en el formateo de código es cuánto debe sangrarse cada línea desde el margen izquierdo. Cuando se encuentra el comienzo de una instrucción como if o for, el nivel de sangría se incrementa por el valor especificado por la opción ‘-i’. Por ejemplo, usa ‘-i8’ para especificar una sangría de ocho caracteres para cada nivel. Cuando una instrucción se divide en dos líneas, la segunda línea se sangra con un número de espacios adicionales especificado por la opción ‘-ci’. ‘-ci’ tiene un valor por defecto de 0. Sin embargo, si se especifica la opción ‘-lp’, y una línea tiene un paréntesis izquierdo que no se cierra en esa línea, entonces las líneas de continuación se alinearán para comenzar en la posición de carácter justo después del paréntesis izquierdo. Este procesamiento también se aplica a ‘[’ y se aplica a ‘{’ cuando ocurre en listas de inicialización. Por ejemplo, una pieza de código continuado podría verse así con ‘-nlp -ci3’ en

efecto: 


  p1 = first_procedure (second_procedure (p2, p3),
     third_procedure (p4, p5));

Con ‘-lp’ en efecto el código se ve algo más

claro: 


  p1 = first_procedure (second_procedure (p2, p3),
                        third_procedure (p4, p5));

Cuando una instrucción se divide entre dos o más pares de paréntesis (...), cada par extra causa que el nivel de sangría tenga sangría

extra: 


if ((((i < 2 &&
        k > 0) || p == 0) &&
    q == 1) ||
  n = 0)

La opción ‘-ipN’ se puede usar para establecer el desplazamiento extra por paréntesis. Por ejemplo, ‘-ip0’ formatearía lo anterior

como: 


if ((((i < 2 &&
  k > 0) || p == 0) &&
  q == 1) ||
  n = 0)

indent asume que las tabulaciones se colocan en intervalos regulares de tanto los flujos de caracteres de entrada como de salida. Estos intervalos tienen por defecto un ancho de 8 columnas, pero (desde la versión 1.2) pueden cambiarse con la opción ‘-ts’. Las tabulaciones se tratan como el número equivalente de

espacios.

Por defecto, indent usará tabulaciones para sangrar tanto como sea posible, y luego rellenará con espacios hasta alcanzar la posición deseada. Sin embargo, con la opción ‘-as’, se usarán espacios para la alineación más allá del nivel de sangría actual. Por defecto, asumiendo que ‘-lp’ está habilitado, el código se sangraría así (‘t’ representa tabulaciones, ‘s’ representa espacios)

:

NUEVAS OPCIONES

La siguiente es una lista de las opciones que son nuevas en esta versión de indent.

El sangrado de las declaraciones de tipos en las definiciones de funciones de estilo antiguo está controlado por el parámetro ‘-ip’. Este es un parámetro numérico que especifica cuántos espacios se sangran las declaraciones de tipos. Por ejemplo, el valor predeterminado ‘-ip5’ hace que las definiciones se vean así:

create_world (x, y, scale)
     int x;
     int y;
     float scale;
{
  . . .
}

Para compatibilidad con otras versiones de indent, se proporciona la opción ‘-nip’, que es equivalente a ‘-ip0’.

ANSI C permite que los espacios en blanco se coloquen en las líneas de comandos del preprocesador entre el carácter ‘#’ y el nombre del comando. Por defecto, indent elimina este espacio, pero especificar la opción ‘-lps’ dirige indent a dejar este espacio sin modificar. La opción ‘-ppi’ anula ‘-nlps’ y ‘-lps’.

Esta opción se puede utilizar para solicitar que las sentencias condicionales del preprocesador se sangren por el número dado de espacios, por ejemplo con la opción ‘-ppi 3’

#else
#define Z 0
#endif
#endif
se convierte en

#   if Y
#      define Z 1
#   else
#      define Z 0
#   endif
#endif

Esta opción establece el desplazamiento en el que se posicionará una etiqueta (excepto las etiquetas de caso). Si se establece en cero o un número positivo, indica cuán lejos del margen izquierdo se sangrará una etiqueta. Si se establece en un número negativo, indica cuán atrás del nivel de sangría actual se colocará la etiqueta. El valor predeterminado es -2, que coincide con el comportamiento de las versiones anteriores de indent. ROMPER LÍNEAS LARGAS

Con la opción ‘-ln’, o ‘--line-lengthn’, es posible especificar la longitud máxima de una línea de código C, sin incluir los posibles comentarios que la sigan.

Cuando las líneas se vuelven más largas que la longitud de línea especificada, GNU indent intenta romper la línea en un lugar lógico. Esto es nuevo a partir de la versión 2.1, pero aún no es muy inteligente ni flexible.

Actualmente hay tres opciones que permiten interferir con el algoritmo que determina dónde romper una línea.

La opción ‘-bbo’ hace que GNU indent prefiera romper líneas largas antes de los operadores booleanos && y ||. La opción ‘-nbbo’ hace que GNU indent no tenga esa preferencia. Por ejemplo, la opción predeterminada ‘-bbo’ (junto con ‘--line-length60’ y ‘--ignore-newlines’) hace que el código se vea así:


  if (mask
      && ((mask[0] == ’\0’)
          || (mask[1] == ’\0’
              && ((mask[0] == ’0’) || (mask[0] == ’*’)))))

Usando la opción ‘-nbbo’ se verá así:


  if (mask &&
      ((mask[0] == ’\0’) ||
       (mask[1] == ’\0’ &&
        ((mask[0] == ’0’) || (mask[0] == ’*’)))))

El valor predeterminado ‘-hnl’, sin embargo, respeta los saltos de línea en el archivo de entrada dándoles la máxima prioridad posible para romper líneas. Por ejemplo, cuando el archivo de entrada se ve así:


  if (mask
      && ((mask[0] == ’\0’)
      || (mask[1] == ’\0’ && ((mask[0] == ’0’) || (mask[0] == ’*’)))))

entonces, usando la opción ‘-hnl’, o ‘--honour-newlines’, junto con las opciones mencionadas anteriormente ‘-nbbo’ y ‘--line-length60’, hará que la salida no sea la que se muestra en el último ejemplo, sino que preferirá romper en las posiciones donde el código se rompió en el archivo de entrada:


  if (mask
      && ((mask[0] == ’\0’)
          || (mask[1] == ’\0’ &&
              ((mask[0] == ’0’) || (mask[0] == ’*’)))))

La idea detrás de esta opción es que las líneas que son demasiado largas, pero que ya están divididas, no serán modificadas por GNU indent. Sin embargo, el código realmente desordenado debería procesarse con indent al menos una vez usando la opción ‘--ignore-newlines’.

La opción ‘-gts’ afecta cómo se tratan las macros estándar de gettext _() y N_(). El comportamiento predeterminado (o el uso de ‘-ngts’) hace que indent las trate como lo hace con otras funciones, de modo que una cadena larga se rompe de manera similar al siguiente ejemplo.


  if (mask)
    {
      warning (_
               ("Esta es una cadena larga que permanece junta."));
    }

Con la opción ‘-gts’, el guion bajo se trata como parte de la cadena, manteniéndola unida a la cadena y respetando el hecho de que gettext proporciona discretamente una cadena localizada. Esto solo funciona si _(" está unido como una unidad al principio de la cadena y ") está unido como una unidad al final.


  if (mask)
    {
      warning 
        (_("Esta es una cadena larga que permanece junta."));
    }

DESACTIVAR EL FORMATO

El formato del código C se puede desactivar para partes de un programa incrustando comentarios de control especiales en el programa. Para desactivar el formato de una sección de un programa, coloque el comentario de control de desactivación /* *INDENT-OFF* */ en una línea por sí solo justo antes de esa sección. El texto del programa escaneado después de este comentario de control se emite exactamente como entrada sin modificaciones hasta que se escanea el comentario de habilitación correspondiente en una línea por sí solo. El comentario de control de habilitación es /* *INDENT-ON* */, y cualquier texto que siga al comentario en la línea también se emite sin formato. El formato comienza de nuevo con la línea de entrada que sigue al comentario de habilitación.

Más precisamente, indent no intenta verificar el delimitador de cierre (*/) para estos comentarios C, y cualquier espacio en blanco en la línea es totalmente transparente.

Estos comentarios de control también funcionan en sus formatos C++, concretamente // *INDENT-OFF* y // *INDENT-ON*.

Cabe señalar que el estado interno de indent permanece sin cambios durante la sección sin formato. Por lo tanto, por ejemplo, desactivar el formato en medio de una función y continuarla después del final de la función puede generar resultados extraños. Por lo tanto, es aconsejable ser algo modular al seleccionar el código que se dejará sin formato.

Como nota histórica, algunas versiones anteriores de indent producían mensajes de error que comenzaban con *INDENT**. Estas versiones de indent estaban escritas para ignorar cualquier línea de texto de entrada que comenzara con tales mensajes de error. He eliminado esta característica incestuosa de GNU indent.

OPCIONES VARIAS

Para saber qué versión de indent tiene, use el comando indent -version. Esto informará el número de versión de indent, sin realizar ningún procesamiento normal.

La opción ‘-v’ se puede usar para activar el modo detallado. Cuando está en modo detallado, indent informa cuándo divide una línea de entrada en dos o más líneas de salida, y proporciona algunas estadísticas de tamaño al finalizar.

La opción ‘-pmt’ hace que indent conserve los tiempos de acceso y modificación en los archivos de salida. Usar esta opción tiene la ventaja de que ejecutar indent en todos los archivos fuente y de encabezado de un proyecto no hará que make reconstruya todos los objetivos. Esta opción solo está disponible en sistemas operativos que tienen la función POSIX utime(2).

ERRORES CONOCIDOS

Por favor, informe cualquier error a bug-indent@gnu.org.

Cuando indent se ejecuta dos veces en un archivo, con el mismo perfil, *nunca* debería cambiar ese archivo la segunda vez. Con el diseño actual de indent, esto no se puede garantizar y no se ha probado exhaustivamente.

indent no entiende C. En algunos casos, esto lleva a la incapacidad de unir líneas. El resultado es que ejecutar un archivo a través de indent es *irreversible*, incluso si el archivo de entrada utilizado fue el resultado de ejecutar indent con un perfil determinado (‘.indent.pro’).

Si bien se hizo un intento para que indent funcionara para C++, no hará un buen trabajo en ningún código fuente C++ excepto en el más simple.

indent no considera la opción ‘--line-length’ dada al escribir comentarios en el archivo de salida. Esto a menudo da como resultado que los comentarios se coloquen muy a la derecha. Para prohibir que indent una una línea rota que tiene un comentario al final, asegúrese de que los comentarios comiencen en la primera línea de la rotura.
