interp(n)

Paquete: tcl

Licencias: TCL

interp(n) Tcl Built-In Commands interp(n)

NOMBRE

interp - Crear y manipular intérpretes de Tcl

SINOPSIS

interp subcomando ?arg arg ...?

DESCRIPCIÓN

Este comando permite crear uno o más intérpretes Tcl nuevos que coexisten con el intérprete creador en la misma aplicación. El intérprete creador se denomina padre y el nuevo intérprete se denomina hijo. Un padre puede crear cualquier número de hijos, y cada hijo puede a su vez crear hijos adicionales de los que es padre, lo que da como resultado una jerarquía de intérpretes.

Cada intérprete es independiente de los demás: tiene su propio espacio de nombres para comandos, procedimientos y variables globales. Un intérprete padre puede crear conexiones entre sus hijos y él mismo utilizando un mecanismo llamado alias. Un alias es un comando en un intérprete hijo que, cuando se invoca, provoca que se invoque un comando en su intérprete padre o en otro intérprete hijo. Las únicas otras conexiones entre intérpretes son a través de variables de entorno (la variable env), que normalmente se comparten entre todos los intérpretes de la aplicación, y mediante callbacks de límite de recursos excedido. Tenga en cuenta que el espacio de nombres para archivos (como los nombres devueltos por el comando open) ya no se comparte entre intérpretes. Se proporcionan comandos explícitos para compartir archivos y para transferir referencias a archivos abiertos de un intérprete a otro.

El comando interp también proporciona soporte para intérpretes seguros. Un intérprete seguro es un hijo cuyas funciones han sido muy restringidas, de modo que es seguro ejecutar scripts no confiables sin temor a que dañen otros intérpretes o el entorno de la aplicación. Por ejemplo, todos los comandos de creación de canales de E/S y los comandos de creación de subprocesos se hacen inaccesibles para los intérpretes seguros. Consulte INTÉRPRETES SEGUROS a continuación para obtener más información sobre qué características están presentes en un intérprete seguro. La funcionalidad peligrosa no se elimina del intérprete seguro; en su lugar, se oculta, de modo que solo los intérpretes de confianza pueden obtener acceso a ella. Para obtener una explicación detallada de los comandos ocultos, consulte COMANDOS OCULTOS, a continuación. El mecanismo de alias se puede utilizar para la comunicación protegida (análoga a una llamada al kernel) entre un intérprete hijo y su padre. Consulte INVOCACIÓN DE ALIAS, a continuación, para obtener más detalles sobre cómo funciona el mecanismo de alias.

Un nombre de intérprete calificado es una lista Tcl adecuada que contiene un subconjunto de sus antecesores en la jerarquía de intérpretes, terminada por la cadena que nombra al intérprete en su padre inmediato. Los nombres de intérpretes son relativos al intérprete en el que se utilizan. Por ejemplo, si “a” es un hijo del intérprete actual y tiene un hijo “a1”, que a su vez tiene un hijo “a11”, el nombre calificado de “a11” en “a” es la lista “a1 a11”.

El comando interp, descrito a continuación, acepta nombres de intérprete calificados como argumentos; el intérprete en el que se evalúa el comando siempre se puede referir como {} (la lista o cadena vacía). Tenga en cuenta que es imposible referirse a un intérprete padre (antecesor) por nombre en un intérprete hijo excepto a través de alias. Además, no existe un nombre global mediante el cual se pueda referir al primer intérprete creado en una aplicación. Ambas restricciones están motivadas por preocupaciones de seguridad.

THE INTERP COMMAND

The interp command is used to create, delete, and manipulate child interpreters, and to share or transfer channels between interpreters. It can have any of several forms, depending on the subcommand argument:

interp alias srcPath srcToken
Returns a Tcl list whose elements are the targetCmd and args associated with the alias represented by srcToken (this is the value returned when the alias was created; it is possible that the name of the source command in the child is different from srcToken).
interp alias srcPath srcToken {}
Deletes the alias for srcToken in the child interpreter identified by srcPath. srcToken refers to the value returned when the alias was created; if the source command has been renamed, the renamed command will be deleted.
interp alias srcPath srcCmd targetPath targetCmd ?arg arg ...?
This command creates an alias between one child and another (see the alias child command below for creating aliases between a child and its parent). In this command, either of the child interpreters may be anywhere in the hierarchy of interpreters under the interpreter invoking the command. SrcPath and srcCmd identify the source of the alias. SrcPath is a Tcl list whose elements select a particular interpreter. For example, “a b” identifies an interpreter “b”, which is a child of interpreter “a”, which is a child of the invoking interpreter. An empty list specifies the interpreter invoking the command. srcCmd gives the name of a new command, which will be created in the source interpreter. TargetPath and targetCmd specify a target interpreter and command, and the arg arguments, if any, specify additional arguments to targetCmd which are prepended to any arguments specified in the invocation of srcCmd. TargetCmd may be undefined at the time of this call, or it may already exist; it is not created by this command. The alias arranges for the given target command to be invoked in the target interpreter whenever the given source command is invoked in the source interpreter. See ALIAS INVOCATION below for more details. The command returns a token that uniquely identifies the command created srcCmd, even if the command is renamed afterwards. The token may but does not have to be equal to srcCmd.
interp aliases ?path?
This command returns a Tcl list of the tokens of all the source commands for aliases defined in the interpreter identified by path. The tokens correspond to the values returned when the aliases were created (which may not be the same as the current names of the commands).
interp bgerror path ?cmdPrefix?
This command either gets or sets the current background exception handler for the interpreter identified by path. If cmdPrefix is absent, the current background exception handler is returned, and if it is present, it is a list of words (of minimum length one) that describes what to set the interpreter's background exception handler to. See the BACKGROUND EXCEPTION HANDLING section for more details.
interp cancel ?-unwind? ?--? ?path? ?result?
Cancels the script being evaluated in the interpreter identified by path. Without the -unwind switch the evaluation stack for the interpreter is unwound until an enclosing catch command is found or there are no further invocations of the interpreter left on the call stack. With the -unwind switch the evaluation stack for the interpreter is unwound without regard to any intervening catch command until there are no further invocations of the interpreter left on the call stack. The -- switch can be used to mark the end of switches; it may be needed if path is an unusual value such as -safe. If result is present, it will be used as the error message string; otherwise, a default error message string will be used.
interp create ?-safe? ?--? ?path?
Creates a child interpreter identified by path and a new command, called a child command. The name of the child command is the last component of path. The new child interpreter and the child command are created in the interpreter identified by the path obtained by removing the last component from path. For example, if path is a b c then a new child interpreter and child command named c are created in the interpreter identified by the path a b. The child command may be used to manipulate the new interpreter as described below. If path is omitted, Tcl creates a unique name of the form interpx, where x is an integer, and uses it for the interpreter and the child command. If the -safe switch is specified (or if the parent interpreter is a safe interpreter), the new child interpreter will be created as a safe interpreter with limited functionality; otherwise the child will include the full set of Tcl built-in commands and variables. The -- switch can be used to mark the end of switches; it may be needed if path is an unusual value such as -safe. The result of the command is the name of the new interpreter. The name of a child interpreter must be unique among all the children for its parent; an error occurs if a child interpreter by the given name already exists in this parent. The initial recursion limit of the child interpreter is set to the current recursion limit of its parent interpreter.
interp debug path ?-frame ?bool??
Controls whether frame-level stack information is captured in the child interpreter identified by path. If no arguments are given, option and current setting are returned. If -frame is given, the debug setting is set to the given boolean if provided and the current setting is returned. This only affects the output of info frame, in that exact frame-level information for command invocation at the bytecode level is only captured with this setting on.

For example, with code like

proc mycontrol {... script} {
  ...
  uplevel 1 $script
  ...
}
proc dosomething {...} {
  ...
  mycontrol {
    somecode
  }
}

the standard setting will provide a relative line number for the command somecode and the relevant frame will be of type eval. With frame-debug active on the other hand the tracking extends so far that the system will be able to determine the file and absolute line number of this command, and return a frame of type source. This more exact information is paid for with slower execution of all commands.

Note that once it is on, this flag cannot be switched back off: such attempts are silently ignored. This is needed to maintain the consistency of the underlying interpreter's state.

interp delete ?path ...?
Deletes zero or more interpreters given by the optional path arguments, and for each interpreter, it also deletes its children. The command also deletes the child command for each interpreter deleted. For each path argument, if no interpreter by that name exists, the command raises an error.
interp eval path arg ?arg ...?
This command concatenates all of the arg arguments in the same fashion as the concat command, then evaluates the resulting string as a Tcl script in the child interpreter identified by path. The result of this evaluation (including all return options, such as -errorinfo and -errorcode information, if an error occurs) is returned to the invoking interpreter. Note that the script will be executed in the current context stack frame of the path interpreter; this is so that the implementations (in a parent interpreter) of aliases in a child interpreter can execute scripts in the child that find out information about the child's current state and stack frame.
interp exists path
Returns 1 if a child interpreter by the specified path exists in this parent, 0 otherwise. If path is omitted, the invoking interpreter is used.
interp expose path hiddenName ?exposedCmdName?
Makes the hidden command hiddenName exposed, eventually bringing it back under a new exposedCmdName name (this name is currently accepted only if it is a valid global name space name without any ::), in the interpreter denoted by path. If an exposed command with the targeted name already exists, this command fails. Hidden commands are explained in more detail in HIDDEN COMMANDS, below.
interp hide path exposedCmdName ?hiddenCmdName?
Makes the exposed command exposedCmdName hidden, renaming it to the hidden command hiddenCmdName, or keeping the same name if hiddenCmdName is not given, in the interpreter denoted by path. If a hidden command with the targeted name already exists, this command fails. Currently both exposedCmdName and hiddenCmdName can not contain namespace qualifiers, or an error is raised. Commands to be hidden by interp hide are looked up in the global namespace even if the current namespace is not the global one. This prevents children from fooling a parent interpreter into hiding the wrong command, by making the current namespace be different from the global one. Hidden commands are explained in more detail in HIDDEN COMMANDS, below.
interp hidden path
Returns a list of the names of all hidden commands in the interpreter identified by path.
interp invokehidden path ?-option ...? hiddenCmdName ?arg ...?
Invokes the hidden command hiddenCmdName with the arguments supplied in the interpreter denoted by path. No substitutions or evaluation are applied to the arguments. Three -options are supported, all of which start with -: -namespace (which takes a single argument afterwards, nsName), -global, and --. If the -namespace flag is present, the hidden command is invoked in the namespace called nsName in the target interpreter. If the -global flag is present, the hidden command is invoked at the global level in the target interpreter; otherwise it is invoked at the current call frame and can access local variables in that and outer call frames. The -- flag allows the hiddenCmdName argument to start with a “-” character, and is otherwise unnecessary. If both the -namespace and -global flags are present, the -namespace flag is ignored. Note that the hidden command will be executed (by default) in the current context stack frame of the path interpreter. Hidden commands are explained in more detail in HIDDEN COMMANDS, below.
interp issafe ?path?
Returns 1 if the interpreter identified by the specified path is safe, 0 otherwise.
interp limit path limitType ?-option? ?value ...?
Sets up, manipulates and queries the configuration of the resource limit limitType for the interpreter denoted by path. If no -option is specified, return the current configuration of the limit. If -option is the sole argument, return the value of that option. Otherwise, a list of -option/value argument pairs must supplied. See RESOURCE LIMITS below for a more detailed explanation of what limits and options are supported.
interp marktrusted path
Marks the interpreter identified by path as trusted. Does not expose the hidden commands. This command can only be invoked from a trusted interpreter. The command has no effect if the interpreter identified by path is already trusted.
interp recursionlimit path ?newlimit?
Returns the maximum allowable nesting depth for the interpreter specified by path. If newlimit is specified, the interpreter recursion limit will be set so that nesting of more than newlimit calls to Tcl_Eval and related procedures in that interpreter will return an error. The newlimit value is also returned. The newlimit value must be a positive integer between 1 and the maximum value of a non-long integer on the platform.

The command sets the maximum size of the Tcl call stack only. It cannot by itself prevent stack overflows on the C stack being used by the application. If your machine has a limit on the size of the C stack, you may get stack overflows before reaching the limit set by the command. If this happens, see if there is a mechanism in your system for increasing the maximum size of the C stack.

interp share srcPath channelId destPath
Causes the IO channel identified by channelId to become shared between the interpreter identified by srcPath and the interpreter identified by destPath. Both interpreters have the same permissions on the IO channel. Both interpreters must close it to close the underlying IO channel; IO channels accessible in an interpreter are automatically closed when an interpreter is destroyed.
interp slaves ?path?
Returns a Tcl list of the names of all the child interpreters associated with the interpreter identified by path. If path is omitted, the invoking interpreter is used.
interp children ?path?
Synonym for . interp slaves ?path?
interp target path alias
Returns a Tcl list describing the target interpreter for an alias. The alias is specified with an interpreter path and source command name, just as in interp alias above. The name of the target interpreter is returned as an interpreter path, relative to the invoking interpreter. If the target interpreter for the alias is the invoking interpreter then an empty list is returned. If the target interpreter for the alias is not the invoking interpreter or one of its descendants then an error is generated. The target command does not have to be defined at the time of this invocation.
interp transfer srcPath channelId destPath
Causes the IO channel identified by channelId to become available in the interpreter identified by destPath and unavailable in the interpreter identified by srcPath.

child COMMAND

Por cada intérprete hijo creado con el comando interp, se crea un nuevo comando Tcl en el intérprete padre con el mismo nombre que el nuevo intérprete. Este comando puede usarse para invocar varias operaciones sobre el intérprete. Tiene la siguiente forma general:

child command ?arg arg ...?

child es el nombre del intérprete, y command y los args determinan el comportamiento exacto del comando. Las formas válidas de este comando son:

child aliases
Devuelve una lista Tcl cuyos elementos son los tokens de todos los alias en child. Los tokens corresponden a los valores devueltos cuando se crearon los alias (que pueden no ser los mismos que los nombres actuales de los comandos).
child alias srcToken
Devuelve una lista Tcl cuyos elementos son el targetCmd y los args asociados con el alias representado por srcToken (este es el valor devuelto cuando se creó el alias; es posible que el comando fuente real en el hijo sea diferente de srcToken).
child alias srcToken {}
Elimina el alias de srcToken en el intérprete hijo. srcToken se refiere al valor devuelto cuando se creó el alias; si el comando fuente ha sido renombrado, el comando renombrado será eliminado.
child alias srcCmd targetCmd ?arg ..?
Crea un alias de modo que siempre que se invoque srcCmd en child, se invoque targetCmd en el padre. Los argumentos arg se pasarán a targetCmd como argumentos adicionales, antepuestos antes de cualquier argumento pasado en la invocación de srcCmd. Consulte ALIAS INVOCATION a continuación para más detalles. El comando devuelve un token que identifica de forma única el comando creado srcCmd, incluso si el comando se renombra después. El token puede, pero no tiene que ser igual a srcCmd.
child bgerror ?cmdPrefix?
Este comando obtiene o establece el manejador de excepciones en segundo plano actual para el intérprete child. Si cmdPrefix está ausente, se devuelve el manejador de excepciones en segundo plano actual, y si está presente, es una lista de palabras (de longitud mínima uno) que describe a qué establecer el manejador de excepciones en segundo plano del intérprete. Consulte la sección BACKGROUND EXCEPTION HANDLING para más detalles.
child eval arg ?arg ..?
Este comando concatena todos los argumentos arg de la misma forma que el comando concat, luego evalúa la cadena resultante como un script Tcl en child. El resultado de esta evaluación (incluyendo todas las opciones de return, como la información de -errorinfo y -errorcode, si ocurre un error) se devuelve al intérprete invocador. Tenga en cuenta que el script se ejecutará en el marco de pila de contexto actual de child; esto es para que las implementaciones (en un intérprete padre) de alias en un intérprete hijo puedan ejecutar scripts en el hijo que averigüen información sobre el estado actual y el marco de pila del hijo.
child expose hiddenName ?exposedCmdName?
Este comando expone el comando oculto hiddenName, eventualmente devolviéndolo bajo un nuevo nombre exposedCmdName (este nombre es actualmente aceptado solo si es un nombre válido del espacio de nombres global sin ningún ::), en child. Si ya existe un comando expuesto con el nombre objetivo, este comando falla. Para más detalles sobre comandos ocultos, consulte HIDDEN COMMANDS, a continuación.
child hide exposedCmdName ?hiddenCmdName?
Este comando oculta el comando expuesto exposedCmdName, renombrándolo al comando oculto hiddenCmdName, o manteniendo el mismo nombre si el argumento no se proporciona, en el intérprete child. Si ya existe un comando oculto con el nombre objetivo, este comando falla. Actualmente tanto exposedCmdName como hiddenCmdName no pueden contener calificadores de espacio de nombres, o se genera un error. Los comandos que se van a ocultar se buscan en el espacio de nombres global incluso si el espacio de nombres actual no es el global. Esto evita que los hijos engañen a un intérprete padre para que oculte el comando equivocado, haciendo que el espacio de nombres actual sea diferente del global. Para más detalles sobre comandos ocultos, consulte HIDDEN COMMANDS, a continuación.
child hidden
Devuelve una lista de los nombres de todos los comandos ocultos en child.
child invokehidden ?-option ...? hiddenName ?arg ..?
Este comando invoca el comando oculto hiddenName con los argumentos proporcionados, en child. No se aplican sustituciones ni evaluaciones a los argumentos. Se admiten tres -options, todas las cuales comienzan con -: -namespace (que toma un único argumento después, nsName), -global y --. Si se proporciona la opción -namespace, el comando oculto se invoca en el espacio de nombres especificado en el hijo. Si se proporciona la opción -global, el comando se invoca a nivel global en el hijo; de lo contrario, se invoca en el marco de llamada actual y puede acceder a variables locales en ese marco de llamada o en los externos. La opción -- permite que el argumento hiddenCmdName comience con un carácter “-”, y por lo demás es innecesaria. Si se proporcionan tanto la opción -namespace como la -global, la opción -namespace se ignora. Tenga en cuenta que el comando oculto se ejecutará (por defecto) en el marco de pila de contexto actual de child. Para más detalles sobre comandos ocultos, consulte HIDDEN COMMANDS, a continuación.
child issafe
Devuelve 1 si el intérprete hijo es seguro, 0 en caso contrario.
child limit limitType ?-option? ?value ...?
Configura, manipula y consulta la configuración del límite de recursos limitType para el intérprete hijo. Si no se especifica ninguna -option, devuelve la configuración actual del límite. Si -option es el único argumento, devuelve el valor de esa opción. De lo contrario, se debe proporcionar una lista de pares de argumentos -option/value. Consulte RESOURCE LIMITS a continuación para una explicación más detallada de qué límites y opciones se admiten.
child marktrusted
Marca el intérprete hijo como de confianza. Solo puede ser invocado por un intérprete de confianza. Este comando no expone ningún comando oculto en el intérprete hijo. El comando no tiene efecto si el hijo ya es de confianza.
child recursionlimit ?newlimit?
Devuelve la profundidad máxima de anidamiento permitida para el intérprete child. Si se especifica newlimit, el límite de recursión en child se establecerá de modo que el anidamiento de más de newlimit llamadas a Tcl_Eval() y procedimientos relacionados en child devuelva un error. También se devuelve el valor newlimit. El valor newlimit debe ser un entero positivo entre 1 y el valor máximo de un entero no long en la plataforma.

El comando establece solo el tamaño máximo de la pila de llamadas de Tcl. No puede por sí mismo evitar desbordamientos de pila en la pila de C que usa la aplicación. Si su máquina tiene un límite en el tamaño de la pila de C, puede obtener desbordamientos de pila antes de alcanzar el límite establecido por el comando. Si esto sucede, vea si hay un mecanismo en su sistema para aumentar el tamaño máximo de la pila de C.

INTÉRPRETES SEGUROS

Un intérprete seguro es aquel con funcionalidad restringida, de modo que es seguro ejecutar un script arbitrario de tu peor enemigo sin temor a que ese script dañe la aplicación contenedora o el resto de tu entorno informático. Para hacer seguro un intérprete, se eliminan ciertos comandos y variables del intérprete. Por ejemplo, se eliminan los comandos para crear archivos en disco, y se elimina el comando exec, ya que podría usarse para causar daños a través de subprocesos. Se puede proporcionar acceso limitado a estas instalaciones creando alias al intérprete padre que verifiquen cuidadosamente sus argumentos y proporcionen acceso restringido a un subconjunto seguro de instalaciones. Por ejemplo, la creación de archivos podría permitirse en un subdirectorio concreto y la invocación de subprocesos podría permitirse para un conjunto de programas cuidadosamente seleccionado y fijo.

Se crea un intérprete seguro especificando el modificador -safe al comando interp create. Además, cualquier hijo creado por un intérprete seguro también será seguro.

Un intérprete seguro se crea con exactamente el siguiente conjunto de comandos integrados:

after	append	apply	array
binary	break	catch	chan
clock	close	concat	continue
dict	eof	error	eval
expr	fblocked	fcopy	fileevent
flush	for	foreach	format
gets	global	if	incr
info	interp	join	lappend
lassign	lindex	linsert	list
llength	lrange	lrepeat	lreplace
lsearch	lset	lsort	namespace
package	pid	proc	puts
read	regexp	regsub	rename
return	scan	seek	set
split	string	subst	switch
tell	time	trace	unset
update	uplevel	upvar	variable
vwait	while
zlib

Los siguientes comandos quedan ocultos por interp create cuando crea un intérprete seguro:

cd	encoding	exec	exit
fconfigure	file	glob	load
open	pwd	socket	source
unload

Estos comandos pueden recrearse posteriormente como procedimientos o alias de Tcl, o volver a exponerse mediante interp expose.

Los siguientes comandos de la biblioteca de procedimientos de soporte de Tcl no están presentes en un intérprete seguro:

auto_exec_ok	auto_import	auto_load
auto_load_index	auto_qualify	unknown

Obsérvese en particular que los intérpretes seguros no tienen un comando unknown predeterminado, por lo que las instalaciones de autoloading predeterminadas de Tcl no están disponibles. El acceso de autoload a los comandos de Tcl que normalmente se cargan automáticamente:

auto_mkindex	auto_mkindex_old
auto_reset	history
parray	pkg_mkIndex
::pkg::create	::safe::interpAddToAccessPath
::safe::interpCreate	::safe::interpConfigure
::safe::interpDelete	::safe::interpFindInAccessPath
::safe::interpInit	::safe::setLogCmd
tcl_endOfWord	tcl_findLibrary
tcl_startOfNextWord	tcl_startOfPreviousWord
tcl_wordBreakAfter	tcl_wordBreakBefore

solo puede proporcionarse mediante la definición explícita de un comando unknown en el intérprete seguro. Esto implicará exponer el comando source. Esto se logra más fácilmente creando el intérprete seguro con el mecanismo Safe-Tcl de Tcl. Safe-Tcl proporciona versiones seguras de source, load y otros comandos de Tcl necesarios para admitir la carga automática de comandos y la carga de paquetes.

Además, la variable env no está presente en un intérprete seguro, por lo que no puede compartir variables de entorno con otros intérpretes. La variable env plantea un riesgo de seguridad, porque los usuarios pueden almacenar información sensible en una variable de entorno. Por ejemplo, el manual de PGP recomienda almacenar la contraseña de protección de la clave privada de PGP en la variable de entorno PGPPASS. Hacer que esta variable esté disponible para código no confiable que se ejecuta en un intérprete seguro conllevaría un riesgo de seguridad.

Si se cargan extensiones en un intérprete seguro, también pueden restringir su propia funcionalidad para eliminar comandos inseguros. Para una discusión sobre la gestión de extensiones por seguridad, véanse las entradas del manual para Safe-Tcl y el comando load de Tcl.

Un intérprete seguro no puede alterar el límite de recursión de ningún intérprete, incluido él mismo.

INVOCACIÓN DE ALIAS

El mecanismo de alias ha sido diseñado cuidadosamente para que pueda utilizarse de forma segura en un script no confiable que se ejecuta en un intérprete seguro, incluso si el destino del alias no es un intérprete seguro. Lo más importante para garantizar la seguridad es asegurar que la información transmitida del hijo al padre nunca sea evaluada ni sustituida en el padre; si esto ocurriera, permitiría a un script malicioso en el hijo invocar funciones arbitrarias en el padre, lo que comprometería la seguridad.

Cuando se invoca el origen de un alias en el intérprete hijo, se realizan las sustituciones habituales de Tcl al analizar ese comando. Estas sustituciones se llevan a cabo en el intérprete de origen tal como se harían para cualquier otro comando invocado en ese intérprete. El procedimiento de comando para el comando de origen toma sus argumentos y los combina con el targetCmd y los args del alias para crear un nuevo arreglo de argumentos. Si las palabras de srcCmd eran “srcCmd arg1 arg2 ... argN”, el nuevo conjunto de palabras será “targetCmd arg arg ... arg arg1 arg2 ... argN”, donde targetCmd y args son los valores proporcionados cuando se creó el alias. TargetCmd se utiliza entonces para localizar un procedimiento de comando en el intérprete destino, y ese procedimiento de comando se invoca con el nuevo conjunto de argumentos. Se produce un error si no existe ningún comando llamado targetCmd en el intérprete destino. No se realizan sustituciones adicionales sobre las palabras: el procedimiento de comando destino se invoca directamente, sin pasar por el mecanismo de evaluación normal de Tcl. Por lo tanto, las sustituciones se realizan sobre cada palabra exactamente una vez: targetCmd y args se sustituyeron al analizar el comando que creó el alias, y arg1 - argN se sustituyen cuando se analiza el comando de origen del alias en el intérprete de origen.

Al escribir los targetCmds para alias en intérpretes seguros, es muy importante que los argumentos de ese comando nunca sean evaluados ni sustituidos, ya que esto proporcionaría un mecanismo de escape mediante el cual el intérprete hijo podría ejecutar código arbitrario en el padre. Esto, a su vez, comprometería la seguridad del sistema.

COMANDOS OCULTOS

Los intérpretes seguros restringen en gran medida la funcionalidad disponible para los programas Tcl que se ejecutan dentro de ellos. Permitir que el programa Tcl no confiable tenga acceso directo a esta funcionalidad no es seguro, porque puede utilizarse para una variedad de ataques contra el entorno. Sin embargo, hay ocasiones en las que existe una necesidad legítima de utilizar la funcionalidad peligrosa en el contexto del intérprete seguro. Por ejemplo, a veces un programa debe ser cargado con source en el intérprete. Otro ejemplo es Tk, donde las ventanas están vinculadas a la jerarquía de ventanas de un intérprete específico; algunas funciones potencialmente peligrosas, por ejemplo, la gestión de ventanas, deben realizarse sobre estas ventanas dentro del contexto del intérprete.

El comando interp proporciona una solución a este problema en forma de comandos ocultos. En lugar de eliminar por completo los comandos peligrosos de un intérprete seguro, estos comandos se ocultan para que dejen de estar disponibles para los scripts Tcl que se ejecutan en el intérprete. Sin embargo, dichos comandos ocultos pueden ser invocados por cualquier ancestro confiable del intérprete seguro, en el contexto del intérprete seguro, utilizando interp invoke. Los comandos ocultos y los comandos expuestos residen en espacios de nombres separados. Es posible definir un comando oculto y un comando expuesto con el mismo nombre dentro de un mismo intérprete.

Los comandos ocultos en un intérprete hijo pueden invocarse en el cuerpo de procedimientos llamados en el padre durante la invocación de un alias. Por ejemplo, se podría crear un alias para source en un intérprete hijo. Cuando se invoca en el intérprete hijo, se llama a un procedimiento en el intérprete padre para comprobar que la operación es permitida (por ejemplo, solicita cargar con source un archivo al que el intérprete hijo tiene permitido acceder). El procedimiento entonces invoca el comando source oculto en el intérprete hijo para cargar realmente el contenido del archivo. Tenga en cuenta que existen dos comandos llamados source en el intérprete hijo: el alias y el comando oculto.

Debido a que un intérprete padre puede invocar un comando oculto como parte del manejo de la invocación de un alias, se debe tener mucho cuidado para evitar evaluar cualquier argumento pasado a través de la invocación del alias. De lo contrario, los intérpretes hijos maliciosos podrían hacer que un intérprete padre confiable ejecute comandos peligrosos en su nombre. Consulte la sección sobre INVOCACIÓN DE ALIAS para una discusión más completa de este tema. Para ayudar a evitar este problema, no se aplican sustituciones ni evaluaciones a los argumentos de interp invokehidden.

A los intérpretes seguros no se les permite invocar comandos ocultos en sí mismos ni en sus descendientes. Esto les impide obtener acceso a la funcionalidad oculta en sí mismos o en sus descendientes.

El conjunto de comandos ocultos en un intérprete puede ser manipulado por un intérprete confiable utilizando interp expose e interp hide. El comando interp expose mueve un comando oculto al conjunto de comandos expuestos en el intérprete identificado por path, posiblemente renombrando el comando en el proceso. Si ya existe un comando expuesto con el nombre objetivo, la operación falla. De manera similar, interp hide mueve un comando expuesto al conjunto de comandos ocultos en ese intérprete. A los intérpretes seguros no se les permite mover comandos entre el conjunto de comandos ocultos y expuestos, ni en sí mismos ni en sus descendientes.

Actualmente, los nombres de los comandos ocultos no pueden contener calificadores de espacio de nombres, y primero debe renombrar un comando en un espacio de nombres al espacio de nombres global antes de poder ocultarlo. Los comandos que se van a ocultar mediante interp hide se buscan en el espacio de nombres global incluso si el espacio de nombres actual no es el global. Esto evita que los hijos engañen a un intérprete padre para que oculte el comando equivocado, haciendo que el espacio de nombres actual sea diferente del global.

LÍMITES DE RECURSOS

Todo intérprete tiene dos tipos de límites de recursos que pueden ser impuestos por cualquier intérprete padre sobre sus hijos. Los límites de comandos (de tipo command) restringen el número total de comandos Tcl que puede ejecutar un intérprete (como puede inspeccionarse mediante el comando info cmdcount), y los límites de tiempo (de tipo time) establecen un límite para que la ejecución dentro del intérprete se complete. Nótese que los límites de tiempo se expresan como tiempos absolutos (como en clock seconds) y no como tiempos relativos (como en after) porque pueden modificarse después de su creación.

Cuando se excede un límite para un intérprete, primero se invocan las funciones de retorno (callbacks) de manejo definidas por los intérpretes padres. Si esas funciones de retorno aumentan o eliminan el límite, la ejecución dentro del intérprete (previamente) limitado continúa. Si el límite sigue vigente, se genera un error en ese punto y el procesamiento normal de errores dentro del intérprete (mediante el comando catch) se deshabilita, de modo que el error se propaga hacia afuera (construyendo un rastro de pila a medida que avanza) hasta el punto donde se invocó el intérprete limitado (por ejemplo, mediante interp eval), donde pasa a ser responsabilidad del código llamador capturarlo y manejarlo.

OPCIONES DE LÍMITE

Cada límite tiene una serie de opciones asociadas, algunas de las cuales son comunes a todos los tipos de límites, y otras son particulares al tipo de límite.

-command
Esta opción (común para todos los tipos de límite) especifica (si no está vacía) un script Tcl que se ejecutará en el espacio de nombres global del intérprete que lee y escribe la opción cuando se excede el límite particular en el intérprete limitado. La función de retorno puede modificar el límite en el intérprete si desea que el intérprete limitado continúe ejecutándose. Si la función de retorno genera una excepción, se informa a través del mecanismo de excepciones en segundo plano (véase MANEJO DE EXCEPCIONES EN SEGUNDO PLANO). Nótese que las funciones de retorno definidas por un intérprete están completamente aisladas de las funciones de retorno definidas por otro, y que el orden en que se llaman esas funciones de retorno no está definido.
-granularity
Esta opción (común para todos los tipos de límite) especifica con qué frecuencia (de entre los puntos en que el intérprete Tcl se encuentra en un estado consistente donde la comprobación de límites es posible) se comprueba realmente el límite. Esto permite ajustar con qué frecuencia se comprueba un límite y, por tanto, con qué frecuencia se incurre en la sobrecarga de la comprobación de límites (que puede ser sustancial en el caso de los límites de tiempo).
-milliseconds
Esta opción especifica el número de milisegundos después del momento definido en la opción -seconds en que se activará el límite de tiempo. Solo debe especificarse junto con la opción -seconds (ya sea que se haya establecido previamente o se establezca en esta invocación).
-seconds
Esta opción especifica el número de segundos después de la época (véase clock seconds) en que se activará el límite de tiempo para el intérprete. El límite se activará al inicio del segundo, a menos que se especifique a nivel de subsegundo mediante la opción -milliseconds. Esta opción puede ser la cadena vacía, lo que indica que no se establece un límite de tiempo para el intérprete.
-value
Esta opción especifica el número de comandos que el intérprete puede ejecutar antes de activar el límite de comandos. Esta opción puede ser la cadena vacía, lo que indica que no se establece un límite de comandos para el intérprete.

Cuando un intérprete con un límite de recursos establecido crea un intérprete hijo, ese intérprete hijo tendrá impuestos límites de recursos que son al menos tan restrictivos como los límites del intérprete padre creador. Si el intérprete padre del padre limitado desea relajar estas condiciones, debe ocultar el comando interp en el hijo y luego usar alias y el subcomando interp invokehidden para proporcionar dicho acceso como elija al comando interp al padre limitado según sea necesario.

MANEJO DE EXCEPCIONES EN SEGUNDO PLANO

Cuando ocurre una excepción en una situación donde no puede informarse directamente hacia arriba en la pila (por ejemplo, al procesar eventos en una llamada update o vwait), la excepción se informa en su lugar mediante el mecanismo de manejo de excepciones en segundo plano. Cada intérprete tiene un manejador de excepciones en segundo plano registrado; el manejador de excepciones predeterminado hace que se llame al comando bgerror en el espacio de nombres global del intérprete, pero se pueden instalar otros manejadores de excepciones y procesar las excepciones en segundo plano de formas sustancialmente diferentes.

Un manejador de excepciones en segundo plano consiste en una lista no vacía de palabras a la que se añadirán dos palabras más en el momento de la invocación. La primera palabra será el resultado del intérprete en el momento de la excepción, típicamente un mensaje de error, y la segunda será el diccionario de opciones de retorno en el momento de la excepción. Estos son los mismos valores que catch puede capturar cuando controla la evaluación de scripts en una situación no relacionada con el segundo plano. La lista resultante se ejecutará entonces en el espacio de nombres global del intérprete sin que se realicen más sustituciones.

CRÉDITOS

El mecanismo de intérprete seguro se basa en el prototipo Safe-Tcl implementado por Nathaniel Borenstein y Marshall Rose.

EJEMPLOS

Crear y usar un alias para un comando en el intérprete actual:

interp alias {} getIndex {} lsearch {alpha beta gamma delta}
set idx [getIndex delta]

Ejecutar un comando arbitrario en un intérprete seguro donde cada invocación de lappend se registra:

set i [interp create -safe]
interp hide $i lappend
interp alias $i lappend {} loggedLappend $i
proc loggedLappend {i args} {
    puts "invocación registrada de lappend $args"
    interp invokehidden $i lappend {*}$args
}
interp eval $i $someUntrustedScript

Establecer un límite de recursos en un intérprete para que un bucle infinito termine.

set i [interp create]
interp limit $i command -value 1000
interp eval $i {
    set x 0
    while {1} {
        puts "Contando... [incr x]"
    }
}
