Tcl qui coexistent avec l'interpréteur créateur dans la même application. L'interpréteur créateur est appelé le parent et le nouvel interpréteur est appelé un enfant. Un parent peut créer un nombre quelconque d'enfants, et chaque enfant peut lui-même créer des enfants supplémentaires dont il est le parent, résultant en une hiérarchie d'interpréteurs. Chaque interpréteur est indépendant des autres : il possède son

propre

espace de noms pour les commandes, les procédures et les variables globales. Un interpréteur parent peut créer des connexions entre ses enfants et lui-même à l'aide d'un mécanisme appelé un alias. Un alias est une commande dans un interpréteur enfant qui, lorsqu'elle est invoquée, provoque l'invocation d'une commande dans son interpréteur parent ou dans un autre interpréteur enfant. Les seules autres connexions entre interpréteurs sont via les variables d'environnement (la variable env), qui sont normalement partagées entre tous les interpréteurs de l'application, et par les rappels de dépassement de limite de ressources. Notez que l'espace de noms pour les fichiers (tels que les noms renvoyés par la commande open) n'est plus partagé entre les interpréteurs. Des commandes explicites sont fournies pour partager des fichiers et pour transférer des références à des fichiers ouverts d'un interpréteur à un

autre.

La commande interp fournit également un support pour les interpréteurs sûrs. Un interpréteur sûr est un enfant dont les fonctions ont été fortement restreintes, de sorte qu'il est sûr d'exécuter des scripts non fiables sans crainte qu'ils n'endommagent d'autres interpréteurs ou l'environnement de l'application. Par exemple, toutes les commandes de création de canaux d'E/S et les commandes de création de sous-processus sont rendues inaccessibles aux interpréteurs sûrs. Voir INTERPRÉTEURS SÛRS ci-dessous pour plus d'informations sur les fonctionnalités présentes dans un interpréteur sûr. Les fonctionnalités dangereuses ne sont pas supprimées de l'interpréteur sûr ; au lieu de cela, elles sont cachées, de sorte que seuls les interpréteurs de confiance peuvent y accéder. Pour une explication détaillée des commandes cachées, voir COMMANDES CACHÉES, ci-dessous. Le mécanisme d'alias peut être utilisé pour une communication protégée (analogue à un appel système) entre un interpréteur enfant et son parent.

child COMMAND

Por cada intérprete hijo creado con el comando interp, se crea un nuevo comando Tcl en el intérprete padre con el mismo nombre que el nuevo intérprete. Este comando puede ser utilizado para invocar varias operaciones en el intérprete. Tiene la siguiente forma general:

child command ?arg arg ...?

child es el nombre del intérprete, y command y los args determinan el comportamiento exacto del comando. Las formas válidas de este comando son:

child aliases
Devuelve una lista Tcl cuyos elementos son los tokens de todos los alias en child. Los tokens corresponden a los valores devueltos cuando se crearon los alias (que pueden no ser los mismos que los nombres actuales de los comandos).
child alias srcToken
Devuelve una lista Tcl cuyos elementos son el targetCmd y los args asociados con el alias representado por srcToken (este es el valor devuelto cuando se creó el alias; es posible que el comando fuente real en el hijo sea diferente de srcToken).
child alias srcToken {}
Elimina el alias para srcToken en el intérprete hijo. srcToken se refiere al valor devuelto cuando se creó el alias; si el comando fuente ha sido renombrado, se eliminará el comando renombrado.
child alias srcCmd targetCmd ?arg ..?
Crea un alias de tal manera que cada vez que se invoque srcCmd en child, se invocará targetCmd en el padre. Los argumentos arg se pasarán a targetCmd como argumentos adicionales, antepuestos a cualquier argumento pasado en la invocación de srcCmd. Consulte ALIAS INVOCATION a continuación para obtener detalles. El comando devuelve un token que identifica de forma única el comando creado srcCmd, incluso si el comando se renombra posteriormente. El token puede ser igual o no a srcCmd.
child bgerror ?cmdPrefix?
Este comando obtiene o establece el manejador de excepciones en segundo plano actual para el intérprete child. Si cmdPrefix está ausente, se devuelve el manejador de excepciones en segundo plano actual, y si está presente, es una lista de palabras (de longitud mínima uno) que describe lo que se debe establecer como manejador de excepciones en segundo plano del intérprete. Consulte la sección BACKGROUND EXCEPTION HANDLING para obtener más detalles.
child eval arg ?arg ..?
Este comando concatena todos los argumentos arg de la misma manera que el comando concat, luego evalúa la cadena resultante como un script Tcl en child. El resultado de esta evaluación (incluyendo todas las opciones de return, como la información de -errorinfo y -errorcode, si ocurre un error) se devuelve al intérprete invocador. Tenga en cuenta que el script se ejecutará en el marco de pila de contexto actual de child; esto es para que las implementaciones (en un intérprete padre) de alias en un intérprete hijo puedan ejecutar scripts en el hijo que obtengan información sobre el estado y el marco de pila actuales del hijo.

Si ya existe un comando expuesto con el nombre objetivo, este comando falla. Para más detalles sobre comandos ocultos, consulte HIDDEN COMMANDS, a continuación.

Si ya existe un comando oculto con el nombre objetivo, este comando falla. Actualmente, tanto exposedCmdName como hiddenCmdName no pueden contener calificadores de espacio de nombres, o se generará un error. Los comandos que se ocultarán se buscan en el espacio de nombres global, incluso si el espacio de nombres actual no es el global. Esto evita que los hijos engañen a un intérprete padre para que oculte el comando incorrecto, al hacer que el espacio de nombres actual sea diferente del global. Para más detalles sobre comandos ocultos, consulte HIDDEN COMMANDS, a continuación.

Este comando invoca el comando oculto hiddenName con los argumentos suministrados, en child. No se aplican sustituciones ni evaluaciones a los argumentos. Si se proporciona la bandera -global, el comando se invoca en el nivel global en el hijo; de lo contrario, se invoca en el marco de llamada actual y puede acceder a variables locales en ese o en marcos de llamada externos. Si se proporcionan ambas banderas -namespace y -global, se ignora la bandera -namespace. Tenga en cuenta que el comando oculto se ejecutará (por defecto) en el marco de pila de contexto actual de child. Para más detalles sobre comandos ocultos, consulte HIDDEN COMMANDS, a continuación.

Marca el intérprete hijo como confiable. Solo puede ser invocado por un intérprete confiable. Este comando no expone ningún comando oculto en el intérprete hijo. El comando no tiene ningún efecto si el hijo ya es confiable.
child recursionlimit ?newlimit?
Devuelve la profundidad máxima de anidamiento permitida para el intérprete child. Si se especifica newlimit, el límite de recursión en child se establecerá de manera que el anidamiento de más de newlimit llamadas a Tcl_Eval() y procedimientos relacionados en child devolverá un error. El valor newlimit también se devuelve. El valor newlimit debe ser un entero positivo entre 1 y el valor máximo de un entero no long en la plataforma.

El comando establece solo el tamaño máximo de la pila de llamadas Tcl. Por sí solo, no puede evitar desbordamientos de pila en la pila C utilizada por la aplicación. Si su máquina tiene un límite en el tamaño de la pila C, es posible que obtenga desbordamientos de pila antes de alcanzar el límite establecido por el comando. Si esto sucede, vea si hay algún mecanismo en su sistema para aumentar el tamaño máximo de la pila C.

SAFE INTERPRETERS

Un intérprete seguro es uno con funcionalidad restringida, por lo que es seguro ejecutar un script arbitrario de tu peor enemigo sin temor a que ese script dañe la aplicación envolvente o el resto de tu entorno informático. Para hacer que un intérprete sea seguro, ciertos comandos y variables se eliminan del intérprete. Por ejemplo, se eliminan los comandos para crear archivos en disco y el comando exec, ya que podría usarse para causar daños a través de subprocesos. Se puede proporcionar acceso limitado a estas instalaciones, creando alias al intérprete padre que verifiquen cuidadosamente sus argumentos y proporcionen acceso restringido a un subconjunto seguro de instalaciones. Por ejemplo, se podría permitir la creación de archivos en un subdirectorio particular y se podría permitir la invocación de subprocesos para un conjunto de programas fijo y cuidadosamente seleccionado.

Un intérprete seguro se crea especificando el modificador -safe al comando interp create. Además, cualquier hijo creado por un intérprete seguro también será seguro.

INVOCATION D'ALIAS Le mécanisme d'alias a été soigneusement conçu de sorte qu'il puisse être utilisé en toute sécurité dans un script non fiable qui s'exécute dans

un

interpréteur sûr même si la cible de l'alias n'est pas un interpréteur sûr. La chose la plus importante pour garantir la sécurité est de s'assurer que les informations passées de l'enfant au parent ne sont jamais évaluées ou substituées dans le parent ; si cela se produisait, cela permettrait à un script malveillant dans l'enfant d'invoquer des fonctions arbitraires dans le parent, ce qui compromettrait la sécurité. Lorsque la source d'un alias est invoquée dans l'interpréteur enfant, les substitutions Tclhabituelles sont effectuées lors de l'analyse de cette commande. Cessubstitutions sont effectuées dans l'interpréteur source exactement comme elles le seraient pour toute autre commande invoquée dans cet interpréteur. La procédure de commande pour la commande source prend ses arguments et les fusionne avec le targetCmd et args de l'alias pour créer un nouveau tableau d' arguments. Si les mots de srcCmd étaient « srcCmd arg1 arg2 ... argN », le nouveau jeu de mots sera « targetCmd arg arg ... arg arg1 arg2 ... argN », où targetCmd et args sont les valeurs fournies lors de la création de l'alias. TargetCmd est ensuite utilisé pour localiser une procédure de commande dans l'interpréteur cible, et cette procédure de commande est invoquée avec le nouveau jeu d' arguments. Une erreur se produit s'il n'y a pas de commande nommée targetCmd dans l'interpréteur cible. Aucune substitution supplémentaire n'est effectuée sur les mots

:

la procédure de commande cible est invoquée directement, sans passer par le mécanisme d'évaluation Tcl normal. Les substitutions sont ainsi effectuées sur chaque mot exactement une fois : targ

etCmd et args ont été substitués lors de l'analyse de la commande qui a créé l'alias, e
t arg1 - argN sont substitués lorsque la commande source de l'alias est analysée dans l'

interpréteu

r

source. Lors de l'écriture des targetCmds pour les alias dans les interpréteurs sûrs, il est très important que les arguments de cette commande ne soient jamais évalués ou substitués, car cela fournirait un mécanisme d'évasion par lequel l'interpréteur enfant pourrait exécuter du code arbitraire dans le parent. Cela compromettrait à son tour la sécurité du système. COMMANDES CACHÉES Les interpréteurs sûrs restreignent fortement la fonctionnalité disponible pour les programmes Tcl qui s'exécutent en leur sein. Permettre au programme Tcl non fiable d' avoir un accès direct à cette fonctionnalité est dangereux, car elle peut être utilisée pour une variété d'attaques sur l'environnement. Cependant, il y a des moments où il y a un besoin légitime d'utiliser la

fonctionnalité

dangereuse dans le contexte de l'interpréteur sûr. Par exemple, parfois un programme doit être sourcé dans l'interpréteur. Un autre exemple est Tk, où les fenêtres sont liées à la hiérarchie des fenêtres pour un interpréteur spécifique ; certaines fonctions potentiellement dangereuses, par ex. la gestion des fenêtres, doivent être effectuées sur ces fenêtres dans le contexte de l'interpréteur. La commande interp fournit une solution à ce problème sous la forme de commandes cachées. Au lieu de supprimer complètement les commandes dangereuses d'un interpréteur sûr, ces commandes sont cachées pour qu'elles deviennent indisponibles pour les scripts Tcl s'exécutant

dans

l'interpréteur. Cependant, de telles commandes cachées peuvent être invoquées par tout ancêtre fiable de l'interpréteur sûr, dans le contexte de l'interpréteur sûr, en utilisant interp invoke. Les commandes cachées et les commandes exposées résident dans des espaces de noms séparés. Il est possible de définir une commande cachée et une commande exposée portant le même nom au sein d'un même interpréteur. Les commandes cachées dans un interpréteur enfant peuvent être invoquées dans le corps des procédures appelées dans le parent lors de l'invocation d'un alias. Par exemple, un alias pour source dans l'interpréteur enfant pour réellement sourcer le contenu du fichier. Notez que deux commandes nommées source existent

dans

l'interpréteur enfant : l'alias, et la commande cachée. Parce qu'un interpréteur parent peut invoquer une commande cachée dans le cadre du traitement d'une invocation d'alias, une grande prudence doit être prise pour éviter d'évaluer les arguments passés via l'invocation d'alias. Sinon, des interpréteurs enfants malveillants pourraient amener un interpréteur parent fiable à exécuter des commandes dangereuses en leur nom. Voir la section sur INVOCATION D'ALIAS pour une discussion plus complète de ce sujet. Pour aider à éviter ce problème, aucune substitution ni évaluation

n'est

appliquée aux arguments de interp invokehidden. Les interpréteurs sûrs ne sont pas autorisés à invoquer des commandes cachées en eux-mêmes ou chez leurs descendants. Cela les empêche d'obtenir l'accès à des

fonctionnalités

cachées en eux-mêmes ou chez leurs descendants. L'ensemble des commandes cachées dans un interpréteur peut être manipulé par un interpréteur fiable en utilisant interp expose et interp hide. La commande interp expose déplace une commande cachée vers l'ensemble des commandes exposées dans l'interpréteur identifié par path, potentiellement en renommant la commande au passage. Si une commande exposée portant le nom cible existe déjà, l'opération échoue. De même, interp hide déplace une commande exposée vers l'ensemble des commandes cachées dans cet interpréteur. Les interpréteurs sûrs ne sont pas autorisés à déplacer des commandes entre l'ensemble des commandes cachées et

exposées,

ni en eux-mêmes ni chez leurs descendants. différent

du global. LIMITES DE RESSOURCES Chaque interpréteur a deux types de limites de ressources qui peuvent être imposées par n'importe quel interpréteur parent à ses enfants. MANEJO DE EXCEPCIONES EN SEGUNDO

PLANO

Cuando ocurre una excepción en una situación en la que no puede reportarse directamente hacia arriba en la pila (por ejemplo, al procesar eventos en una update o vwait call) la excepción se reporta a través del mecanismo de manejo de excepciones en segundo plano. Cada intérprete tiene un manejador de excepciones en segundo plano registrado; el manejador de excepciones por defecto organiza que se llame al bgerror command en el espacio de nombres global del intérprete, pero se pueden instalar otros manejadores de excepciones y procesar excepciones en segundo plano de maneras sustancialmente

diferentes.

Un manejador de excepciones en segundo plano consiste en una lista no vacía de palabras a la que se le añadirán dos palabras más en el momento de la invocación. La primera palabra será el resultado del intérprete en el momento de la excepción, típicamente un mensaje de error, y la segunda será el diccionario de opciones de retorno en el momento de la excepción. Estos son los mismos valores que catch puede capturar cuando controla la evaluación de scripts en una situación no de segundo plano. La lista r

esultante se ejecutará entonces en el espacio de nombre
s global del intérprete sin realizar más sustituciones.
