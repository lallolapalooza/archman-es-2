NOMBRE

os-release, initrd-release, extension-release - Identificación del sistema operativo

SINOPSIS

/etc/os-release
/usr/lib/os-release
/etc/initrd-release
/usr/lib/extension-release.d/extension-release.IMAGEN

DESCRIPCIÓN

Los archivos /etc/os-release y /usr/lib/os-release contienen datos de identificación del sistema operativo.

El formato de os-release es una lista separada por saltos de línea de asignaciones de variables compatibles con el shell, similares a las variables de entorno. Es posible cargar la configuración desde scripts de shell Bourne, sin embargo, más allá de simples asignaciones de variables, no se admiten funciones de shell (esto significa que la expansión de variables no se admite explícitamente), lo que permite a las aplicaciones leer el archivo sin implementar un motor de ejecución compatible con el shell. Los valores de asignación de variables deben estar entre comillas dobles o simples si contienen espacios, punto y coma u otros caracteres especiales fuera de A–Z, a–z, 0–9. (Las asignaciones que no contienen estos caracteres especiales también pueden entrecomillarse, pero esto es opcional). Los caracteres especiales del shell ("$", comillas, barra invertida, acento grave) deben escaparse con barras invertidas, siguiendo el estilo del shell. Todas las cadenas deben estar en codificación UTF-8, y no deben usarse caracteres no imprimibles. La concatenación de varias cadenas entrecomilladas individualmente no es compatible. Las líneas que comienzan con "#" se tratan como comentarios. Las líneas en blanco están permitidas y se ignoran.

El archivo /etc/os-release tiene prioridad sobre /usr/lib/os-release. Las aplicaciones deben verificar el primero y usar exclusivamente sus datos si existe, y solo recurrir a /usr/lib/os-release si este falta. Las aplicaciones no deben combinar los datos de ambos archivos. /usr/lib/os-release es el lugar recomendado para almacenar la información de lanzamiento del SO como parte de los árboles de proveedores. /etc/os-release debe ser un enlace simbólico relativo a /usr/lib/os-release, para proporcionar compatibilidad con las aplicaciones que solo buscan en /etc/. Un enlace simbólico relativo en lugar de uno absoluto es necesario para evitar romper el enlace en un entorno chroot o initrd.

os-release contiene datos definidos por el proveedor del sistema operativo y, en general, no debe ser modificado por el administrador.

Dado que este archivo solo codifica nombres e identificadores, no debe localizarse.

Los archivos /etc/os-release y /usr/lib/os-release pueden ser enlaces simbólicos a otros archivos, pero es importante que el archivo esté disponible desde el inicio más temprano y, por lo tanto, debe ubicarse en el sistema de archivos raíz.

os-release no debe contener claves repetidas. Sin embargo, los lectores deben seleccionar las entradas que aparecen más tarde en el archivo en caso de repeticiones, de manera similar a como lo haría un shell al cargar el archivo. Un lector puede advertir sobre entradas repetidas.

Para una explicación más detallada de os-release, consulte el Anuncio de /etc/os-release[1].

/etc/initrd-release

En el initrd[2] y exitrd, /etc/initrd-release juega el mismo papel que os-release en el sistema principal. Además, la presencia de ese archivo significa que el sistema está en la fase initrd/exitrd. /etc/os-release debe ser un enlace simbólico a /etc/initrd-release (o viceversa), para que los programas que solo buscan /etc/os-release (como se describe anteriormente) funcionen correctamente.

El resto de este documento que habla sobre os-release debe entenderse que se aplica también a initrd-release.

/usr/lib/extension-release.d/extension-release.IMAGEN

/usr/lib/extension-release.d/extension-release.IMAGEN desempeña el mismo papel para las imágenes de extensión que os-release para el sistema principal, y sigue la sintaxis y las reglas descritas en la página Servicios Portátiles[3]. El propósito de este archivo es identificar la extensión y permitir que el sistema operativo verifique que la imagen de extensión coincide con el sistema operativo base. Esto se implementa típicamente verificando que la opción ID= de la extensión coincida con la opción ID= del host o esté incluida en la opción ID_LIKE= del host, y que exista SYSEXT_LEVEL= y coincida, o si no está presente, VERSION_ID= exista y coincida. Esto garantiza la compatibilidad ABI/API entre las capas y evita la fusión de una imagen incompatible en una superposición.

Para identificar la imagen de extensión en sí, los mismos campos definidos a continuación se pueden agregar al archivo de extensión con un prefijo SYSEXT_ (para desambiguar de los campos utilizados para la coincidencia en la imagen base). Por ejemplo: SYSEXT_ID=myext, SYSEXT_VERSION_ID=1.2.3.

En el nombre de archivo extension-release.IMAGEN, la parte IMAGEN debe coincidir exactamente con el nombre del archivo de la imagen contenedora sin el sufijo. En caso de que no sea posible garantizar que el nombre de un archivo de imagen sea estable y no cambie entre las fases de compilación y despliegue, es posible relajar esta comprobación: si existe exactamente un archivo cuyo nombre coincida con "extension-release.*" en este directorio, y el archivo está etiquetado con un atributo xattr(7) user.extension-release.strict establecido en la cadena "0", se utilizará en su lugar.

El resto de este documento que habla sobre os-release debe entenderse que se aplica también a extension-release.

OPCIONES

Los siguientes parámetros de identificación del SO pueden establecerse usando os-release:

Información general que identifica el sistema operativo

NOMBRE=

Una cadena que identifica el sistema operativo, sin componente de versión, y adecuada para presentar al usuario. Si no se establece, se puede usar un valor predeterminado de "NOMBRE=Linux".

Ejemplos: "NOMBRE=Fedora", "NOMBRE="Debian GNU/Linux"".

ID=

Una cadena en minúsculas (sin espacios ni otros caracteres fuera de 0–9, a–z, ".", "_" y "-") que identifica el sistema operativo, excluyendo cualquier información de versión y adecuada para su procesamiento por scripts o uso en nombres de archivo generados. Si no se establece, se puede usar un valor predeterminado de "ID=linux". Tenga en cuenta que, aunque esta cadena no puede incluir caracteres que requieran comillas de shell, las comillas pueden usarse de todos modos.

Ejemplos: "ID=fedora", "ID=debian".

ID_LIKE=

Una lista separada por espacios de identificadores del sistema operativo en la misma sintaxis que el ajuste ID=. Debe listar identificadores de sistemas operativos que estén estrechamente relacionados con el sistema operativo local en lo que respecta a empaquetado e interfaces de programación, por ejemplo, enumerar uno o más identificadores de SO de los cuales el SO local es un derivado. Un SO generalmente solo debe listar otros identificadores de SO de los cuales es un derivado, y no ningún SO que se derive de él, aunque las relaciones simétricas son posibles. Los scripts de compilación y similares deben verificar esta variable si necesitan identificar el sistema operativo local y el valor de ID= no es reconocido. Los sistemas operativos deben enumerarse en orden de cuán estrechamente se relaciona el sistema operativo local con los enumerados, comenzando por el más cercano. Este campo es opcional.

Ejemplos: para un sistema operativo con "ID=centos", una asignación de "ID_LIKE="rhel fedora"" sería apropiada. Para un sistema operativo con "ID=ubuntu", una asignación de "ID_LIKE=debian" es apropiada.

NOMBRE_BONITO=

Un nombre de sistema operativo bonito en un formato adecuado para presentar al usuario. Puede contener o no un nombre de código de lanzamiento o una versión del SO de algún tipo, según corresponda. Si no se establece, se puede usar un valor predeterminado de "NOMBRE_BONITO="Linux""

Ejemplo: "NOMBRE_BONITO="Fedora 17 (Beefy Miracle)"".

CPE_NAME=

Un nombre CPE para el sistema operativo, en sintaxis de enlace URI, siguiendo la Especificación de Enumeración Común de Plataformas[4] propuesta por el NIST. Este campo es opcional.

Ejemplo: "CPE_NAME="cpe:/o:fedoraproject:fedora:17""

VARIANTE=

Una cadena que identifica una variante o edición específica del sistema operativo adecuada para presentar al usuario. Este fi

Este sitio no está asociado de ninguna forma con Arch Linux ni afiliado a este proyecto. El contenido es únicamente una traducción de las páginas del manual de Arch publicadas en man.archlinux.org.

El campo puede usarse para informar al usuario de que la configuración de este sistema está sujeta a un conjunto específico de reglas divergentes o a ajustes de configuración predeterminados. Este campo es opcional y puede no estar implementado en todos los sistemas.

Ejemplos: "VARIANT="Server Edition"", "VARIANT="Smart Refrigerator Edition"".

Nota: este campo es solo para visualización. El VARIANT_ID campo debe usarse para tomar decisiones programáticas.

Añadido en la versión 220.

VARIANT_ID=

Una cadena en minúsculas (sin espacios ni otros caracteres fuera de 0–9, a–z, ".", "_" y "-"), que identifica una variante o edición específica del sistema operativo. Esto puede ser interpretado por otros paquetes para determinar una configuración predeterminada divergente. Este campo es opcional y puede no estar implementado en todos los sistemas.

Ejemplos: "VARIANT_ID=server", "VARIANT_ID=embedded".

Añadido en la versión 220.

Información sobre la versión del sistema operativo

VERSION=

Una cadena que identifica la versión del sistema operativo, excluyendo cualquier información del nombre del SO, posiblemente incluyendo un nombre en clave de la versión, y adecuada para presentación al usuario. Este campo es opcional.

Ejemplos: "VERSION=17", "VERSION="17 (Beefy Miracle)"".

VERSION_ID=

Una cadena en minúsculas (principalmente numérica, sin espacios ni otros caracteres fuera de 0–9, a–z, ".", "_" y "-") que identifica la versión del sistema operativo, excluyendo cualquier información del nombre del SO o nombre en clave de la versión, y adecuada para el procesamiento por scripts o para su uso en nombres de archivo generados. Este campo es opcional.

Ejemplos: "VERSION_ID=17", "VERSION_ID=11.04".

VERSION_CODENAME=

Una cadena en minúsculas (sin espacios ni otros caracteres fuera de 0–9, a–z, ".", "_" y "-") que identifica el nombre en clave de la versión del sistema operativo, excluyendo cualquier información del nombre del SO o versión de lanzamiento, y adecuada para el procesamiento por scripts o para su uso en nombres de archivo generados. Este campo es opcional y puede no estar implementado en todos los sistemas.

Ejemplos: "VERSION_CODENAME=buster", "VERSION_CODENAME=xenial".

Añadido en la versión 231.

BUILD_ID=

Una cadena que identifica de forma única la imagen del sistema utilizada originalmente como base de instalación. En la mayoría de los casos, VERSION_ID o IMAGE_ID+IMAGE_VERSION se actualizan cuando la imagen del sistema completa se reemplaza durante una actualización. BUILD_ID puede usarse en distribuciones donde la versión de la imagen de instalación original es importante: VERSION_ID cambiaría durante actualizaciones incrementales del sistema, pero BUILD_ID no lo haría. Este campo es opcional.

Ejemplos: "BUILD_ID="2013-03-20.3"", "BUILD_ID=201303203".

Añadido en la versión 200.

IMAGE_ID=

Una cadena en minúsculas (sin espacios ni otros caracteres fuera de 0–9, a–z, ".", "_" y "-"), que identifica una imagen específica del sistema operativo. Esto está destinado a usarse en entornos donde las imágenes del SO se preparan, construyen, distribuyen y actualizan como imágenes completas y coherentes del SO. Este campo es opcional y puede no estar implementado en todos los sistemas, en particular no en aquellos que no se gestionan mediante imágenes sino que se ensamblan y actualizan a partir de paquetes individuales en el sistema local.

Ejemplos: "IMAGE_ID=vendorx-cashier-system", "IMAGE_ID=netbook-image".

Añadido en la versión 249.

IMAGE_VERSION=

Una cadena en minúsculas (principalmente numérica, sin espacios ni otros caracteres fuera de 0–9, a–z, ".", "_" y "-") que identifica la versión de la imagen del SO. Esto está destinado a usarse junto con IMAGE_ID descrito anteriormente, para discernir diferentes versiones de la misma imagen.

Ejemplos: "IMAGE_VERSION=33", "IMAGE_VERSION=47.1rc1".

Añadido en la versión 249.

RELEASE_TYPE=

Una cadena en minúsculas (sin espacios ni otros caracteres fuera de 0-9, a-z, ".", "_", y "-"), que describe qué tipo de lanzamiento es esta versión del SO. Los valores conocidos son los siguientes:
•"stable" es para lanzamientos normales del sistema, adecuados para uso en producción. Generalmente, las versiones estables alcanzan el fin de vida poco después de que se publique la siguiente versión estable principal, aunque esto podría no ser el caso si, por ejemplo, una distribución adopta un modelo de lanzamiento continuo y aún está lista para producción. Los ejemplos incluyen Fedora 40, Ubuntu 23.10, OpenSUSE Tumbleweed y Arch Linux.
•"lts" es para lanzamientos de soporte a largo plazo del sistema, adecuados para uso en producción y soportados durante un período de tiempo extendido. Generalmente, las versiones LTS continúan recibiendo soporte incluso si están disponibles versiones principales más nuevas de la distribución. Los ejemplos incluyen Ubuntu 24.04, Debian 12 Bookworm y RHEL 9.4.
•"development" es para versiones inestables del sistema, no adecuadas para uso en producción, como versiones alfa, beta o continuas inestables. Los ejemplos incluyen Fedora Rawhide, Debian Testing, Fedora 40 Beta y GNOME OS Nightly.
•"experiment" es para compilaciones experimentales del sistema, creadas específicamente para probar alguna funcionalidad en desarrollo. Esto está destinado a usarse en combinación con EXPERIMENT=.

Si no está establecido, o es un valor desconocido, asuma que el lanzamiento es "stable".

Ejemplos: "RELEASE_TYPE=development", "RELEASE_TYPE=lts".

Añadido en la versión 257.

Para resumir: si las actualizaciones de la imagen se construyen y distribuyen como unidades completas, IMAGE_ID+IMAGE_VERSION es lo más adecuado. De lo contrario, si las actualizaciones eventualmente reemplazan completamente los contenidos previamente instalados, como en una distribución binaria típica, VERSION_ID debe usarse para identificar las versiones principales del sistema operativo. BUILD_ID puede usarse en lugar de o además de VERSION_ID cuando la versión de la imagen del sistema original es importante.

Información de presentación y enlaces

HOME_URL=, DOCUMENTATION_URL=, SUPPORT_URL=, BUG_REPORT_URL=, PRIVACY_POLICY_URL=

Enlaces a recursos en Internet relacionados con el sistema operativo. HOME_URL= debería referirse a la página principal del sistema operativo, o alternativamente a alguna página principal de la versión específica del sistema operativo. DOCUMENTATION_URL= debería referirse a la página principal de documentación de este sistema operativo. SUPPORT_URL= debería referirse a la página principal de soporte del sistema operativo, si la hay. Esto está destinado principalmente a sistemas operativos para los que los proveedores ofrecen soporte. BUG_REPORT_URL= debería referirse a la página principal de informe de errores del sistema operativo, si la hay. Esto está destinado principalmente a sistemas operativos que dependen de QA comunitario. PRIVACY_POLICY_URL= debería referirse a la página principal de política de privacidad del sistema operativo, si la hay. Estas configuraciones son opcionales, y es común proporcionar solo algunas de ellas. Estas URL están destinadas a exponerse en interfaces de usuario "Acerca de este sistema" detrás de enlaces con leyendas como "Acerca de este Sistema Operativo", "Obtener Soporte", "Informar un Error" o "Política de Privacidad". Los valores deberían estar en formato RFC3986[5], y deberían ser URL "http:" o "https:", y posiblemente "mailto:" o "tel:". Solo se debe listar una URL en cada configuración. Si se necesitan referenciar múltiples recursos, se recomienda proporcionar una página de destino en línea que enlace todos los recursos disponibles.

Ejemplos: "HOME_URL="https://fedoraproject.org/"", "BUG_REPORT_URL="https://bugzilla.redhat.com/"".

SUPPORT_END=

La fecha en la que finaliza el soporte para esta versión del SO. (Lo que exactamente significa "falta de soporte" varía entre proveedores, pero generalmente los usuarios deben asumir que no se proporcionarán actualizaciones, incluyendo correcciones de seguridad.) El valor es una fecha en formato ISO 8601 "YYYY-MM-DD", y especifica el primer día en el que el soporte no se proporciona.

Por ejemplo, "SUPPORT_END=2001-01-01" significa que el sistema fue soportado hasta el final del último día del milenio anterior.

Añadido en la versión 252.

LOGO=

Una cadena, que especifica el nombre de un icono según lo definido por freedesktop.org Icon Theme Specification[6]. Esto puede ser usado por aplicaciones gráficas para mostrar el logotipo de un sistema operativo o distribuidor. Este campo es opcional y no necesariamente puede estar implementado en todos los sistemas.

Ejemplos: "LOGO=fedora-logo", "LOGO=distributor-logo-opensuse"

Añadido en la versión 240.

ANSI_COLOR=

Un color de presentación sugerido al mostrar el nombre del SO en la consola. Esto debería especificarse como una cadena adecuada para su inclusión en el código de escape ANSI/ECMA-48 ESC [ m para establecer la representación gráfica. Este campo es opcional.

Ejemplos: "ANSI_COLOR="0;31"" para rojo, "ANSI_COLOR="1;34"" para azul claro, o "ANSI_COLOR="0;38;2;60;110;180"" para el azul de Fedora.

VENDOR_NAME=

El nombre del proveedor del SO. Este es el nombre de la organización o empresa que produce el SO. Este campo es opcional.

Este nombre está destinado a exponerse en interfaces de usuario "Acerca de este sistema" o interfaces de actualización de software cuando sea necesario distinguir al proveedor del SO del propio SO. Está destinado a ser legible para humanos.

Ejemplos: "VENDOR_NAME="Fedora Project"" para Fedora Linux, "VENDOR_NAME="Canonical"" para Ubuntu.

Añadido en la versión 254.

VENDOR_URL=

La página principal del proveedor del SO. Este campo es opcional. El campo VENDOR_NAME= debería establecerse si este lo está, aunque los clientes deben ser robustos ante la ausencia de cualquiera de los dos campos.

El valor debería estar en formato RFC3986[5], y deberían ser URL "http:" o "https:". Solo se debe listar una URL en la configuración.

Ejemplos: "VENDOR_URL="g/'>https://fedoraproject.org/"", "VENDOR_URL="https://canonical.com/"".

Añadido en la versión 254.

EXPERIMENT=

Una descricción presentable para humanos de lo que hace que esta compilación del SO sea experimental. Este campo es opcional. El RELEASE_TYPE campo debería establecerse a "experiment" si este campo está definido, de lo contrario los clientes deberían ignorar este campo.

Esta descricción está destinada a exponerse en el momento de la instalación del sistema, o en las interfaces de usuario de "Acerca de este sistema", para advertir al usuario de que está instalando/ejecutando una compilación experimental del SO. Si RELEASE_TYPE es "experiment" pero este campo no está definido, la interfaz de usuario aún debería advertir al usuario, pero no podrá explicar qué es exactamente lo que es experimental en la compilación actual del SO.

Ejemplos: "EXPERIMENT="Switch to DNF5"" para una compilación experimental de Fedora Linux creada para probar DNF5, "EXPERIMENT="Port to Apple M3 chip"" para compilaciones experimentales de Asahi Linux portadas al SoC Apple M3, "EXPERIMENT="Mutter !1441: Dynamic triple/double buffering (v4)"" para compilaciones de GNOME OS creadas por la CI de Mutter para la solicitud de fusión !1441.

Añadido en la versión 257.

EXPERIMENT_URL=

La página informativa principal sobre lo que hace que la compilación actual del SO sea experimental, donde los usuarios pueden aprender más sobre el estado del experimento y potencialmente dejar comentarios. Este campo es opcional. El EXPERIMENT= campo debería establecerse si este lo está, aunque los clientes deben ser robustos ante la posibilidad de que ninguno de los dos campos esté definido.

El valor debería estar en formato RFC3986[5], y deberían ser URLs "http:" o "https:". Solo se debe listar una URL en la configuración.

Ejemplos, correspondientes a los ejemplos anteriores en EXPERIMENT=: "EXPERIMENT_URL="https://fedoraproject.org/wiki/Changes/SwitchToDnf5"", "EXPERIMENT_URL="https://github.com/AsahiLinux/docs/wiki/M3-Series-Feature-Support"", "EXPERIMENT_URL="https://gitlab.gnome.org/GNOME/mutter/-/merge_requests/1441"".

Añadido en la versión 257.

Valores predeterminados y metadatos a nivel de distribución

DEFAULT_HOSTNAME=

Una cadena que especifica el nombre de host si hostname(5) no está presente y ninguna otra fuente de configuración especifica el nombre de host. Debe ser o bien una única etiqueta DNS (una cadena compuesta por caracteres ASCII de 7 bits en minúsculas y sin espacios ni puntos, limitada al formato permitido para etiquetas de nombres de dominio DNS), o una secuencia de tales etiquetas separadas por puntos simples que forme un FQDN DNS válido. El nombre de host debe tener como máximo 64 caracteres, lo cual es una limitación de Linux (DNS permite nombres más largos).

Si el carácter de signo de interrogación "?" aparece en el nombre de host, se sustituye automáticamente por un carácter hexadecimal derivado del machine-id(5) cuando se aplica, de forma segura y determinista mediante hashing criptográfico. Ejemplo: "foobar-????-????" se expandirá automáticamente a "foobar-92a9-061c" o similar, dependiendo del ID de máquina local.

Consulte org.freedesktop.hostname1(5) para una descripción de cómo systemd-hostnamed.service(8) determina el nombre de host de reserva.

Añadido en la versión 248.

ARCHITECTURE=

Una cadena que especifica qué arquitectura de CPU requieren los binarios del espacio de usuario. Los identificadores de arquitectura son los mismos que para ConditionArchitecture= descrito en systemd.unit(5). El campo es opcional y solo debería usarse cuando se admite una única arquitectura. Puede proporcionar información redundante cuando se usa en una partición GPT con un tipo GUID que ya codifica la arquitectura. Si no es el caso, la arquitectura debería especificarse, por ejemplo, en una imagen de extensión, para evitar que un host incompatible la cargue.

Añadido en la versión 252.

SYSEXT_LEVEL=

Una cadena en minúsculas (principalmente numérica, sin espacios ni otros caracteres fuera de 0–9, a–z, ".", "_" y "-") que identifica el nivel de soporte de extensiones del sistema operativo, para indicar qué imágenes de extensión son soportadas. Consulte /usr/lib/extension-release.d/extension-release.IMAGE, initrd[2] y systemd-sysext(8)) para más información.

Ejemplos: "SYSEXT_LEVEL=2", "SYSEXT_LEVEL=15.14".

Añadido en la versión 248.

CONFEXT_LEVEL=

Semánticamente lo mismo que SYSEXT_LEVEL= pero para imágenes confext. Consulte /etc/extension-release.d/extension-release.IMAGE para más información.

Ejemplos: "CONFEXT_LEVEL=2", "CONFEXT_LEVEL=15.14".

Añadido en la versión 254.

SYSEXT_SCOPE=

Acepta una lista separada por espacios de una o más de las cadenas "system", "initrd" y "portable". Este campo solo es soportado en archivos extension-release.d/ e indica a qué entornos aplica la extensión del sistema: es decir, a sistemas regulares, a initrds y exitrds, o a imágenes de servicios portátiles. Si no se especifica, se implica "SYSEXT_SCOPE=system portable", es decir, cualquier extensión del sistema sin este campo aplica a sistemas regulares y a entornos de servicios portátiles, pero no a entornos initrd/exitrd.

Añadido en la versión 250.

CONFEXT_SCOPE=

Semánticamente lo mismo que SYSEXT_SCOPE= pero para imágenes confext.

Añadido en la versión 254.

PORTABLE_PREFIXES=

Acepta una lista separada por espacios de una o más cadenas de coincidencia de prefijo válidas para la lógica de Servicios Portátiles[3]. Este campo sirve para dos propósitos: es informativo, identificando imágenes de servicios portátiles como tales (y por lo tanto permitiendo distinguirlas de otras imágenes del SO, como imágenes de sistema arrancables). También se usa cuando se adjunta una imagen de servicio portátil: el prefijo de servicio portátil especificado o implícito se comprueba contra la lista especificada aquí, para hacer cumplir restricciones sobre cómo se pueden adjuntar las imágenes a un sistema.

Añadido en la versión 250.

Notas

Si está usando este archivo para determinar el SO o una versión específica de él, use los campos ID y VERSION_ID , posiblemente con ID_LIKE como reserva para ID. Cuando busque una cadena de identificación del SO para presentarla al usuario, use el campo PRETTY_NAME .

Tenga en cuenta que los proveedores del sistema operativo pueden optar por no proporcionar información de versión, por ejemplo, para acomodar lanzamientos continuos. En este caso, VERSION y VERSION_ID pueden no estar definidos. Las aplicaciones no deberían depender de que estos campos estén definidos.

Los proveedores del sistema operativo pueden extender el formato del archivo e introducir nuevos campos. Se recomienda encarecidamente que los nuevos campos se prefijen con un nombre específico del SO para evitar conflictos de nombres. Las aplicaciones que lean este archivo deben ignorar los campos desconocidos.

Ejemplo: "DEBIAN_BTS="debbugs://bugs.debian.org/"".

Los gestores de tiempo de ejecución de contenedores y sandbox pueden poner los datos de identificación del host disponibles para las aplicaciones proporcionando el /etc/os-release del host (si está disponible, de lo contrario /usr/lib/os-release como reserva) como /run/host/os-release.

Ejemplo 5. Leyendo os-release en python(1) (cualquier versión)

#!/usr/bin/python
# SPDX-License-Identifier: MIT-0
import ast
import re
import sys
def read_os_release():
    try:
        filename = '/etc/os-release'
        f = open(filename)
    except FileNotFoundError:
        filename = '/usr/lib/os-release'
        f = open(filename)
    for line_number, line in enumerate(f, start=1):
        line = line.rstrip()
        if not line or line.startswith('#'):
            continue
        m = re.match(r'([A-Z][A-Z_0-9]+)=(.*)', line)
        if m:
            name, val = m.groups()
            if val and val[0] in '"\'':
                val = ast.literal_eval(val)
            yield name, val
        else:
            print(f'{filename}:{line_number}: bad line {line!r}',
                  file=sys.stderr)

NAME


initrd-release - Information about the initramfs and the operating system release






SYNOPSIS


/etc/initrd-release






DESCRIPTION


The /etc/initrd-release file may be used to store information
    about the initramfs and the operating system release. It is a plain text file
    intended to be read by programs. It should be in the same format as
    os-release(5).


Currently, the initramfs toolchain only uses this file to store
    the operating system release information, similar to how
    os-release(5) is used.


The file is read by the dracut(8)
    utility. This information is then embedded into the initramfs image.


The following variables are expected to be defined in
    /etc/initrd-release:



  
NAME

  
A string giving the operating system name, for display to end users.
      This field is mandatory.

  
VERSION

  
A string giving the operating system version, for display to end
      users. This field is optional.

  
ID

  
A single word string which should be suitable for use as an
      identifier (e.g. in scripts). This identifier should be lowercase and
      unique among operating systems. This field is mandatory.

  
ID_LIKE

  
A space-separated list of strings, which are identifiers of other
      operating systems. This may be used to indicate compatibility, for
      example, a derivative of a system might list the identifier of its
      base system here. This field is optional.

  
PRETTY_NAME

  
A string giving a pretty operating system name, for display to end
      users. This field is optional.

  
VERSION_ID

  
A string giving the operating system version, including any
      displayname or version codename, for easier assembly of
      notifications and upgrade instructions. This field is optional.

  
VERSION_CODENAME

  
A string giving the operating system's version codename. This field is
      optional.

  
BUILD_ID

  
A string identifying a specific build of the operating system. This
      field is optional.

  
HOME_URL

  
A string giving a URL for the operating system's home page. This field
      is optional.

  
SUPPORT_URL

  
A string giving a URL for documentation or support resources for the
      operating system. This field is optional.

  
BUG_REPORT_URL

  
A string giving a URL for reporting bugs in the operating system. This
      field is optional.

  
PRIVACY_POLICY_URL

  
A string giving a URL for the operating system's privacy policy. This
      field is optional.

  
LOGO

  
A string giving the filename of a logo for the operating system. The
      logo should be in SVG format and named similarly to the ID string. This
      field is optional.




All variables are defined as NAME=VALUE. Lines starting with
    `#' are ignored. Values may be enclosed in double quotes.






OPTIONS


None.

Python code snippet that reads and parses the file:




import os.path
import platform

def read_os_release():
    os_release = {}
    try:
        with open('/etc/os-release', 'r') as f:
            for line in f:
                line = line.strip()
                if not line or line.startswith('#'):
                    continue
                if '=' in line:
                    key, value = line.split('=', 1)
                    if value.startswith('"') and value.endswith('"'):
                        value = value[1:-1]
                    os_release[key] = value
    except FileNotFoundError:
        pass
    return os_release

os_release = read_os_release()
pretty_name = os_release.get('PRETTY_NAME', 'Linux')
print(f'Running on {pretty_name!r}')
if 'debian' in [os_release.get('ID', 'linux'),
                *os_release.get('ID_LIKE', '').split()]:
    print('Looks like Debian!')




Note that the above version that uses the built-in implementation
    is preferred in most cases, and the open-coded version here is provided for
    reference.
