include_server.py inicia un proce

so de servidor de include. Este pr
oceso responde a consultas de

distcc(1

)

clientes sobre qué archivos incluir en compilaciones de C/C++. El comando include_server.py en sí mismo termina tan pronto como el servidor de include ha sido generado. El argumento INCLUDE_SERVER_PORT es el nombre de un socket utilizado para toda la comunicación entre los clientes distcc y el servidor de

include.
El

pump(1

)

comando es responsable de crear la ubicación del socket, de pasarlo a este script y de pasarlo a todos los clientes distcc a través de la variable de entorno llamada INCLUDE_SERVER_PORT. El protocolo utilizado por el servidor de include usa la implementación RPC de distcc. Cada petición distcc consiste en (1) el directorio actual y (2) la lista de argumentos del comando de

compilación.

Si el servidor de include es capaz de procesar la petición, entonces responde al cliente distcc enviando una lista de rutas de archivo. Las rutas de archivo son las de los archivos fuente y de cabecera comprimidos que se han encontrado necesarios para la compilación a través del análisis de include. La lista también comprende enlaces simbólicos e incluso archivos ficticios necesarios para que el servidor de compilación construya una réplica precisa de las partes del sistema de archivos necesarias para la compilación. De esta manera, un archivo de cabecera necesario como /path/foo.h se comprime, se renombra y se almacena en una ubicación temporal, como /dev/shm/tmpiAvfGv.include_server-9368-1/path/foo.h.lzo. El cliente distcc pasará estos archivos a un servidor de compilación, donde se descomprimirán y se montarán temporalmente. Si el servidor de include no es capaz de procesar la petición, entonces devuelve la lista vacía al cliente

distcc.

Hay dos tipos de fallos que se relacionan con el servidor de include. El servidor de include puede fallar al calcular los includes o fallar de otras maneras, vea la

sección

Preprocesando localmente. El servidor de include no cubre: No se pudieron determinar los directorios de include del sistema
predeterminados
Para determinar los directorios de cabeceras del sistema predeterminados, el servidor de include ejecuta el compilador una vez para cada lenguaje necesario durante su sesión. Este mensaje indica que el compilador especificado para distcc no está presente en el
cliente.
Preprocesando localmente. El servidor de include no cubre: Abandonando porque el servidor de include gastó más de ...s de tiempo de usuario manejando la
petición
En situaciones poco comunes, el servidor de include falla al analizar expresiones de macro muy complicadas. El cliente distcc usará el modo distcc
simple.

lo es
El servidor de include no acepta rutas de archivo absolutas, como /usr/include/stdio.h, en las directivas de include, porqu
e no hay garantía de que este archivo de cabecera en la máquina del servidor de compilación sea el mismo que en el cl
iente. El servidor de include renuncia a analizar el cierre de include. El cliente distcc no puede usar el modo pump. "Bl-tag">
Para superar este problema de una manera no siempre fiable, establezca la variable de e

Se está utilizando --unsafe_absolute_includes. Esta situación ocurre bajo las mismas circunstancias que cuando se emite "Filepath must be relative but isn't", pero en este caso la inclusión proporcionará una respuesta al cliente
distcc.
Advertencia: La ruta '/PATH/FILE' cambió/entró en existencia/dejó de
existir
Estas advertencias se emiten al usar los desencadenantes de reinicio de stat (stat reset triggers). Debido a que /PATH/FILE cambió, el servidor de inclusión limpia sus cachés; la nueva versión del archivo (o su ausencia) invalida el análisis de inclusiones. Este mensaje generalmente se puede ignorar; sí indica un uso algo precario de archivos por parte del sistema de compilación. Se recomienda corregir el sistema de compilación para que los archivos no sean

DISTCC SÍNTOMAS DE

DISCREPANCIA

Las interacciones entre el sistema de compilación, distcc y el servidor de inclusión son algo complejas. Cuando un comando distcc recibe una compilación fallida del servidor remoto, reintenta la compilación localmente. Esta sección discute las causas de las discrepancias entre la compilación remota y la local. Estas se señalan con el mensaje de

degradación:

__________Advertencia: ... compilación(es) en modo pump fallaron en el servidor, pero tuvieron éxito localmente.
__________Distcc-pump fue degradado al modo simple (plain mode). Vea la sección Distcc Discrepancy Symptoms en el manual include_server(1) [[14]]. El script pump emite este mensaje al final de la compilación. Esto significa que para al menos una invocación de distcc una compilación local tuvo éxito después de que la compilación remota fallara. Cada invocación de distcc para la cual ocurrió tal

discrepancia a su vez también emite un mensaje como:

Advertencia: la compilación remota de '...'

falló,

se reintentó localmente y se obtuvo un resultado diferente. La degradación hace que las invocaciones subsecuentes de distcc usen el modo distcc simple (plain). Así, el preprocesamiento se realizará en la máquina local para el resto de la compilación. Esta técnica evita compilaciones muy lentas donde todas las compilaciones terminan en la máquina local después de fallar

remotamente.

Por supuesto, si la compilación local falla después de los fallos remotos, entonces la invocación de distcc sale con el estado distinto de cero de la compilación local. Los mensajes de error impresos también son los de la compilación

local.

El comportamiento de respaldo del modo distcc-pump a la compilación local se puede deshabilitar estableciendo la variable de entorno DISTCC_FALLBACK a 0, lo que hace que el comando distcc falle tan pronto como la compilación remota haya fallado. Esta configuración es muy útil para depurar por qué la compilación remota salió mal, porque ahora la salida del servidor será

impresa.

A continuación discutimos las posibles causas de

discrepancias.

El usuario cambió un archivo de origen o de cabecera durante la

compilación.
Esto produce resultados inconsistentes, por
supuesto.
Un archivo de origen o de cabecera cambió durante la
compilación.
El sistema de compilación reescribe un archivo. Para el kernel de Linux 2.6, esto ocurre para 'include/linux/compile.h' y 'include/asm/asm-offsets.h'. Esta condición se corrige haciendo saber al servidor de inclusión que debe reiniciar sus cachés cuando el stat de cualquiera de los archivos cambie. Prácticamente, esto se hace recopilando los archivos en una lista separada por dos puntos y luego estableciendo la variable de entorno INCLUDE_SERVER_ARGS al invocar el script
pump, de modo que pase la
opción --stat_reset_triggers ; por ejemplo,


INCLUDE_SERVER_ARGS="--stat_res

et_triggers=include/linux/compi
le.h:include/asm/asm-offsets.h"
Un archivo de cabecera es potencialmente incluido, pero no existe, y es incluido más
tarde.
Esto ocurre cuando algún archivo de cabecera foo.h incluye otro archivo de cabecera trick.h, pero el archivo trick.h aún no ha sido generado y la inclusión es realmente ignorada debido a directivas de preprocesamiento. El servidor de inclusión buscará la existencia de trick.h, porque sobreaproxima todas las formas posibles en que las directivas realmente se evalúan. Se determina que el archivo trick.h no existe. Si es generado más tarde, y luego realmente incluido, entonces el servidor de inclusión creerá falsamente que el archivo todavía no existe. La solución a este problema es hacer que el sistema de compilación genere trick.h antes de la primera vez que cualquier archivo de cabecera sea incluido que haga una referencia sintáctica a trick.
h

ncludes .

Dichas inclusiones a menudo están protegidas por directivas condicionales que se evalúan de modo que son realmente usadas solo en plataformas específicas y a menudo poco comunes. Si no está compilando para una plataforma así, entonces puede ser correcto usar --unsafe_absolute
