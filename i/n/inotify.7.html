NOTA

S

Los descriptores de archivo de inotify se pueden monitorear usando select(2), poll(2), y epoll(7). Cuando hay un evento disponible, el descriptor de archivo indica que es

legible.

Desde Linux 2.6.25, la notificación de E/S dirigida por señal está disponible para los descriptores de archivo de inotify; véase la discusión de F_SETFL (para establecer la bandera O_ASYNC), F_SETOWN, y F_SETSIG en fcntl(2). La estructura siginfo_t (descrita en sigaction(2)) que se pasa al manejador de señal tiene los siguientes campos establecidos: si_fd se establece al número de descriptor de archivo de inotify; si_signo se establece al número de señal; si_code se establece a POLL_IN; y POLLIN se establece en si_band

.

Si los eventos de inotify de salida sucesivos producidos en el descriptor de archivo de inotify son idénticos (mismo wd, mask, cookie, y name), tcuando se fusionan en un solo evento si el evento más antiguo aún no ha sido leído (pero ver ERRORES). Esto reduce la cantidad de memoria del kernel requerida para la cola de eventos, pero también significa que una aplicación no puede usar inotify para contar eventos de archivos de manera

fiable.

Los eventos devueltos al leer desde un descriptor de archivo de inotify forman una cola ordenada. Así, por ejemplo, se garantiza que al renombrar de un directorio a otro, se producirán eventos en el orden correcto en el descriptor de archivo de

inotify.

El conjunto de descriptores de vigilancia que se está monitoreando a través de un descriptor de archivo de inotify se puede ver a través de la entrada para el descriptor de archivo de inotify en el /proc/pid/fdinfo del proceso. Vea proc(5) para más detalles. El FIONREAD ioctl(2) devuelve el número de bytes disponibles para leer desde un descriptor de archivo de

inotify.

Limitaciones y

advertencias

La API de inotify no proporciona información sobre el usuario o proceso que desencadenó el evento de inotify. En particular, no hay una manera fácil para un proceso que monitorea eventos a través de inotify de distinguir los eventos que desencadena él mismo de aquellos que son desencadenados por otros

procesos.

Inotify solo reporta eventos que un programa de espacio de usuario desencadena a través de la API del sistema de archivos. Como resultado, no captura eventos remotos que ocurren en sistemas de archivos de red. (Las aplicaciones deben recurrir a la consulta del sistema de archivos para capturar tales eventos.) Además, varios pseudo-sistemas de archivos como /proc, /sys, y /dev/pts no se pueden monitorear con

inotify.

La API de inotify no reporta accesos y modificaciones de archivos que pueden ocurrir debido a mmap(2), msync(2), y munmap(

2).

La API de inotify identifica los archivos afectados por nombre de archivo. Sin embargo, para cuando una aplicación procesa un evento de inotify, el nombre de archivo ya puede haber sido eliminado o

renombrado.

La API de inotify identifica eventos a través de descriptores de vigilancia. Es responsabilidad de la aplicación almacenar en caché un mapeo (si se necesita) entre descriptores de vigilancia y rutas de acceso. Tenga en cuenta que los renombrados de directorios pueden afectar a múltiples rutas de acceso almacenadas en

caché.

El monitoreo de directorios con inotify no es recursivo: para monitorear subdirectorios bajo un directorio, se deben crear vigilancias adicionales. Esto puede llevar una cantidad significativa de tiempo para árboles de directorios

grandes.

Si está monitoreando un subárbol completo de directorios, y se crea un nuevo subdirectorio en ese árbol o un directorio existente se renombra dentro de ese árbol, tenga en cuenta de que para cuando usted cree una vigilancia para el nuevo subdirectorio, nuevos archivos (y subdirectorios) pueden ya existir dentro del subdirectorio. Por lo tanto, es posible que desee escanear el contenido del subdirectorio inmediatamente después de agregar la vigilancia (y, si lo desea, agregar recursivamente vigilancias para cualquier subdirectorio que contenga)

.

Tenga en cuenta de que la cola de eventos puede desbordarse. En este caso, los eventos se pierden. Las aplicaciones robustas deben manejar la posibilidad de eventos perdidos con elegancia. Por ejemplo, puede ser necesario reconstruir parte o toda la caché de la aplicación. (Un enfoque simple, pero posiblemente costoso, es cerrar el descriptor de archivo de inotify, vaciar la caché, crear un nuevo descriptor de archivo de inotify, y luego recrear las vigilancias y las entradas de caché para los objetos a monitorear.

)

Si un sistema de archivos se monta encima de un directorio monitoreado, no se genera ningún evento, y no

se generan eventos para los objetos inmediatamente debajo del nuevo punto de montaje. Si el sistema de
archivos se desmonta posteriormente, se generarán eventos para el directorio y los objetos que contiene.

Manejo de eventos

rename()

Como se indicó anteriormente, el par de eventos IN_MOVED_FROM e IN_MOVED_TO generado por rename(2) se puede emparejar a través de su valor de cookie compartido. Sin embargo, la tarea de emparejar tiene algunos

desafíos.

Estos dos eventos suelen ser consecutivos en el flujo de eventos disponible al leer desde el descriptor de archivo de inotify. Sin embargo, esto no está garantizado. Si múltiples procesos están desencadenando eventos para objetos monitoreados, entonces (en ocasiones raras) un número arbitrario de otros eventos puede aparecer entre los eventos IN_MOVED_FROM e IN_MOVED_TO. Además, no está garantizado que el par de eventos se inserte atómicamente en la cola: puede haber un breve intervalo donde el IN_MOVED_FROM haya aparecido, pero el IN_MOVED_T

O no.

Emparejar el par de eventos IN_MOVED_FROM e IN_MOVED_TO generado por rename(2) es por lo tanto inherentemente propenso a condiciones de carrera. (No olvide que si un objeto se renombra fuera de un directorio monitoreado, puede que ni siquiera haya un evento IN_MOVED_TO.) Se pueden usar enfoques heurísticos (p. ej., asumir que los eventos siempre son consecutivos) para asegurar una coincidencia en la mayoría de los casos, pero inevitablemente se perderán algunos casos, haciendo que la aplicación perciba los eventos IN_MOVED_FROM e IN_MOVED_TO como no relacionados. Si los descriptores de vigilancia se destruyen y se recrean como resultado, entonces esos descriptores de vigilancia serán inconsistentes con los descriptores de vigilancia en cualquier evento pendiente. (Recrear el descriptor de archivo de inotify y reconstruir la caché puede ser útil para manejar este escenario.

)

Las aplicaciones también deben permitir la posibilidad de que el evento IN_MOVED_FROM fuera el último evento que cabía en el búfer devuelto por la llamada actual a read(2), y el evento IN_MOVED_TO acompañante podría obtenerse solo en la siguiente read(2), la cual debe hacerse con un tiempo de espera (pequeño) para permitir el hecho de que la inserción del par de eventos IN_MOVED_FROM+IN_MOVED_TO no es atómica, y también la posibilidad de que no haya ningún evento I

ERRORE

S

Antes de Linux 3.19, fallocate(2) no creaba ningún evento de inotify. Desde Linux 3.19, las llamadas a fallocate(2) generan eventos IN_M

ODIFY.

Antes de Linux 2.6.16, la máscara IN_ONESHOT no funcio

naba.

Tal como fue diseñado e implementado originalmente, el indicador IN_ONESHOT no causaba que se generara un evento IN_IGNORED cuando la vigilancia se eliminaba después de un evento. Sin embargo, como un efecto no deseado de otros cambios, desde Linux 2.6.36, un evento IN_IGNORED se genera en este

caso.

Antes de Linux 2.6.25, el código del kernel que estaba destinado a fusionar eventos idénticos sucesivos (es decir, los dos eventos más recientes podrían potencialmente fusionarse si el más antiguo aún no había sido leído) en su lugar verificaba si el evento más reciente podía fusionarse con el evento no leído más

antiguo.

Cuando un descriptor de vigilancia se elimina llamando a inotify_rm_watch(2) (o porque un archivo de vigilancia se elimina o el sistema de archivos que lo contiene se desmonta), cualquier evento pendiente no leído para ese descriptor de vigilancia permanece disponible para leer. A medida que los descriptores de vigilancia se asignan posteriormente con inotify_add_watch(2), el kernel recorre el rango de posibles descriptores de vigilancia (1 a INT_MAX) incrementalmente. Al asignar un descriptor de vigilancia libre, no se realiza ninguna verificación para ver si ese número de descriptor de vigilancia tiene algún evento pendiente no leído en la cola de inotify. Por lo tanto, puede suceder que un descriptor de vigilancia se reasigne incluso cuando existen eventos pendientes no leídos para una encarnación anterior de ese número de descriptor de vigilancia, con el resultado de que la aplicación podría entonces leer esos eventos e interpretarlos como pertenecientes al archivo asociado con el descriptor de vigilancia reciclado recientemente. En la práctica, la probabilidad de encontrar este error puede ser extremadamente baja, ya que requiere que una aplicación recorra INT_MAX descriptores de vigilancia, libere un descriptor de vigilancia dejando eventos no leídos para ese descriptor de vigilancia en la cola, y luego recicle ese descriptor de vigilancia. Por est

a razón, y porque no ha habido informes de la ocurrencia de este error en aplicaciones del mundo real
, a partir de Linux 3.15, aún no se han hecho cambios en el kernel para eliminar este posible error.

    char buf[4096]

NAME


inotify - monitor filesystem events






DESCRIPTION


The inotify API allows a Linux application to monitor
    filesystem events (e.g. open, close, modify, delete, create, move) on
    specified files or directories. The filesystem is not polled; instead,
    inotify generates events, which are queued, and a user-space application
    can read them from a file descriptor.


The typical use of inotify involves these steps:




1.


Create an inotify instance using
        inotify_init(2) or
        inotify_init1(2). This returns a file
        descriptor.


2.


Add watches for files or directories using
        inotify_add_watch(2). Each watch is associated
        with a watch descriptor (wd), which is a positive integer. A watch
        specifies which events to monitor for a particular filesystem object.
        These objects can be files, directories, or symbolic links. If a watch
        is added for a directory, events happening within that directory
        (for its immediate children) are reported.


3.


Read events from the inotify file descriptor. Events are returned as a
        sequence of struct inotify_event structures.
        Each event structure is followed by the filename associated with the
        event, if any. The filename is not null-terminated; it is followed
        immediately by the next event structure (or the end of the buffer).
        The size of the buffer returned by read() can be calculated from the
        size variable (see code example below). The
        size of each event structure is described by
        inotify_event(7).


4.


Remove watches using inotify_rm_watch(2).


5.


Close the inotify file descriptor to release all resources.




inotify supports watching the following events:




IN_ACCESS


File was accessed (e.g., read()).


IN_ATTRIB


Metadata changed (e.g., permissions, timestamps, extended attributes).


IN_CLOSE_NOWRITE


File opened for writing was closed, or file opened in read-only mode was closed.


IN_CLOSE_WRITE


File opened for writing was closed.


IN_CREATE


File/directory created in watched directory.


IN_DELETE


File/directory deleted from watched directory.


IN_DELETE_SELF


Watched file/directory was deleted itself.


IN_MODIFY


File was modified.


IN_MOVE_SELF


Watched file/directory was moved itself.


IN_MOVED_FROM


File/directory moved out of watched directory.


IN_MOVED_TO


File/directory moved into watched directory.


IN_OPEN


File was opened.




The following bits can be set in the mask
    field of the struct inotify_event structure:




IN_DONT_FOLLOW


Do not follow a symbolic link. By default, inotify(7) follows
        symbolic links.


IN_EXCL_UNLINK


Exclude events on items with a watch that is currently marked for
        deletion.


IN_MASK_ADD


Add the specified event mask to the existing mask for the watched
        file/directory; it does not replace the existing mask.


IN_ONLYDIR


Watch only the directory, not the files/subdirectories inside it. This
        option is only meaningful if the specified pathname is a
        directory.




The following bits can be set in the mask
    argument when adding a watch using
    inotify_add_watch(2):




IN_ALL_EVENTS


A mask containing all the events listed above.


IN_CLOSE


A shorthand for
        IN_CLOSE_WRITE | IN_CLOSE_NOWRITE.


IN_MOVE


A shorthand for
        IN_MOVED_FROM | IN_MOVED_TO.




The following bit can be set in the mask
    field of the struct inotify_event structure to
    indicate the type of filesystem object involved:




IN_ISDIR


Indicates that the event occurred on a directory.


IN_IGNORED


Indicates that the watch instance associated with the event has been
        ignored. This happens when a watched file/directory is deleted or
        moved, or when a watch descriptor is removed using
        inotify_rm_watch(2).




inotify file descriptors support poll(2) and
    select(2).


#include <sys/inotify.h>

struct inotify_event {
    int wd;                 /* Watch descriptor */
    uint32_t mask;          /* Mask of events */
    uint32_t cookie;        /* Related event in a rename sequence */
    size_t len;             /* Size of the name field */
    char name[0];           /* Optional filename */
};



The wd field identifies the watch
    descriptor on which the event occurred. The mask
    field describes the event(s) that occurred. The cookie
    field is used in pairs of events, for example, for rename operations
    (one IN_MOVED_FROM event and one
    IN_MOVED_TO event), the same cookie
    value is given for both events. The len field
    specifies the length of the filename in the name
    field. If there is no filename associated with the event (e.g.,
    IN_Q_OVERFLOW), then len is
    0, and the name field is empty.


When reading from an inotify file descriptor, you read a
    buffer containing zero or more struct inotify_event
    structures. The size of the buffer can vary because the name
    field can have variable length. The total size of a structure including the
    name is
    sizeof(struct inotify_event) + event->len.
    The total size of the buffer read from the file descriptor is returned by
    the read() system call. You must loop over the buffer,
    calculating the size of each event structure and advancing the pointer
    accordingly. The last event structure in the buffer may not be complete;
    if you try to read it, read() will return fewer
    bytes than requested, and you should then read more data.


If the inotify instance reaches its limit of queued events
    (e.g. because the application is not reading them fast enough), events
    may be dropped. An IN_Q_OVERFLOW event is generated
    to indicate this. The wd field is set to -1, and
    the mask field is set to
    IN_Q_OVERFLOW.


The maximum number of watches per inotify instance is limited by
    `/proc/sys/fs/inotify/max_user_watches`. The maximum number of events that
    can be queued per inotify file descriptor is limited by
    `/proc/sys/fs/inotify/max_queued_events`.


inotify file descriptors are created using the
    open(2) system call with the
    O_RDONLY | O_CLOEXEC flags.


inotify has a number of limitations:


    

  • inotify does not monitor access times.
    • 

  • inotify does not monitor changes to file permissions or ownership.
    • 

  • inotify does not monitor modifications to files opened in read-only mode.
    • 

  • inotify does not report events for files that are created directly in a directory being watched. Instead, it reports events for files that are created in a subdirectory of a directory being watched.
    • 

  • inotify does not report events for files that are deleted directly from a directory being watched. Instead, it reports events for files that are deleted from a subdirectory of a directory being watched.
    • 



inotify does not support the following:


    

  • Monitoring of network filesystems (NFS, SMB).
    • 

  • Monitoring of filesystems that do not support all the requested events.
    • 



inotify is a Linux-specific API. For portability, consider using
    fanotify(7).


static void
handle_events(int fd, int *wd, int argc, char *argv[])
{
    /* some buffer (1024 bytes for example) */
    const struct inotify_event *event;
    ssize_t length = read(fd, buf, 1024);

    if (length <= 0)
        break;
    /* Loop over all events in the buffer.  */
    for (char *ptr = buf; ptr < buf + size;
            ptr += sizeof(struct inotify_event) + event->len) {
        event = (const struct inotify_event *) ptr;
        /* Print event type.  */
        if (event->mask & IN_OPEN)
            printf("IN_OPEN: ");
        if (event->mask & IN_CLOSE_NOWRITE)
            printf("IN_CLOSE_NOWRITE: ");
        if (event->mask & IN_CLOSE_WRITE)
            printf("IN_CLOSE_WRITE: ");
        /* Print the name of the watched directory.  */
        for (size_t i = 1; i < argc; ++i) {
            if (wd[i] == event->wd) {
                printf("%s/", argv[i]);
                break;
            }
        }
        /* Print the name of the file.  */
        if (event->len)
            printf("%s", event->name);
        /* Print type of filesystem object.  */
        if (event->mask & IN_ISDIR)
            printf(" [directory]\n");
        else
            printf(" [file]\n");
    }
}
int
main(int argc, char* argv[])
{
    char buf;
    int fd, i, poll_num;
    int *wd;
    nfds_t nfds;
    struct pollfd fds[2];
    if (argc < 2) {
        printf("Usage: %s PATH [PATH ...]\n", argv[0]);
        exit(EXIT_FAILURE);
    }
    printf("Press ENTER key to terminate.\n");
    /* Create the file descriptor for accessing the inotify API.  */
    fd = inotify_init1(IN_NONBLOCK);
    if (fd == -1) {
        perror("inotify_init1");
        exit(EXIT_FAILURE);
    }
    /* Allocate memory for watch descriptors.  */
    wd = calloc(argc, sizeof(int));
    if (wd == NULL) {
        perror("calloc");
        exit(EXIT_FAILURE);
    }
    /* Mark directories for events
       - file was opened
       - file was closed */
    for (i = 1; i < argc; i++) {
        wd[i] = inotify_add_watch(fd, argv[i],
                                  IN_OPEN | IN_CLOSE);
        if (wd[i] == -1) {
            fprintf(stderr, "Cannot watch '%s': %s\n",
                    argv[i], strerror(errno));
            exit(EXIT_FAILURE);
        }
    }
    /* Prepare for polling.  */
    nfds = 2;
    fds[0].fd = STDIN_FILENO;       /* Console input */
    fds[0].events = POLLIN;
    fds[1].fd = fd;                 /* Inotify input */
    fds[1].events = POLLIN;
    /* Wait for events and/or terminal input.  */
    printf("Listening for events.\n");
    while (1) {
        poll_num = poll(fds, nfds, -1);
        if (poll_num == -1) {
            if (errno == EINTR)
                continue;
            perror("poll");
            exit(EXIT_FAILURE);
        }
        if (poll_num > 0) {
            if (fds[0].revents & POLLIN) {
                /* Console input is available.  Empty stdin and quit.  */
                while (read(STDIN_FILENO, &buf, 1) > 0 && buf != '\n')
                    continue;
                break;
            }
            if (fds[1].revents & POLLIN) {
                /* Inotify events are available.  */
                handle_events(fd, wd, argc, argv);
            }
        }
    }
    printf("Listening for events stopped.\n");
    /* Close inotify file descriptor.  */
    close(fd);
    free(wd);
    exit(EXIT_SUCCESS);
}







STANDARDS


The inotify API is Linux-specific. There is no direct equivalent in
    POSIX. For portability, consider using fanotify(7).






HISTORY


The inotify API was introduced in Linux kernel 2.6.13.






NOTES


The name field in
    struct inotify_event is not null-terminated. Accessing
    it beyond its length is undefined behavior. You should use the len
    field to determine the actual length of the name.


When a directory is deleted or moved, all events for that
    directory and its children will be ignored, and all watches on it will be
    removed. An IN_IGNORED event will be generated for
    each watch that is removed.


The IN_MOVED_FROM and
    IN_MOVED_TO events are reported for files moved into or
    out of a watched directory. These events are reported only if the source and
    destination directories are watched. If the source or destination is not
    watched, then only one event (IN_MOVED_FROM or
    IN_MOVED_TO) will be reported.


The IN_CREATE and IN_DELETE
    events are reported for files created or deleted in a watched directory.
    These events are only reported if the file is not a symbolic link.


If you watch a directory and then create a file within it, you will
    receive an IN_CREATE event. If you then open and close
    that file, you will receive IN_OPEN and
    IN_CLOSE_WRITE events. If you then delete the file, you
    will receive an IN_DELETE event.


If you watch a file and then open and close it, you will receive
    IN_OPEN and IN_CLOSE_WRITE events.
    If you then delete the file, you will receive an
    IN_DELETE_SELF event.






BUGS


The behavior of IN_ATTRIB can be subtle. It
    is reported when metadata changes, but not all metadata changes necessarily
    trigger an event. For example, changing the last access time of a file
    might not trigger IN_ATTRIB.


The IN_MOVED_FROM and
    IN_MOVED_TO events are not always reported for cross-device
    moves. For example, if you move a file from one filesystem to another,
    only one of the events might be reported.


The kernel documentation states that IN_MODIFY
    is not reported if the file is opened with O_TRUNC. This
    is a known limitation.






EXAMPLES


The following program monitors specified directories for
    IN_OPEN and IN_CLOSE events. It
    exits when you press Enter.


#include <sys/inotify.h>
#include <limits.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <errno.h>
#include <unistd.h>
#include <poll.h>

/* Read all available inotify events on the inotify file descriptor 'fd'.
   'wd' is an array mapping watch descriptors to directory names.
   'argc' is the number of command-line arguments (and thus directories).
   'argv' is the array of command-line arguments (directory names). */

static void
handle_events(int fd, int *wd, int argc, char *argv[])
{
    /* Some buffer (1024 bytes for example) */
    char buf[1024];
    const struct inotify_event *event;
    ssize_t length = read(fd, buf, sizeof(buf));

    if (length <= 0)
        return;

    /* Loop over all events in the buffer.  */
    for (char *ptr = buf; ptr < buf + length; ) {
        event = (const struct inotify_event *) ptr;

        /* Print event type.  */
        if (event->mask & IN_OPEN)
            printf("IN_OPEN: ");
        if (event->mask & IN_CLOSE_NOWRITE)
            printf("IN_CLOSE_NOWRITE: ");
        if (event->mask & IN_CLOSE_WRITE)
            printf("IN_CLOSE_WRITE: ");

        /* Print the name of the watched directory.  */
        for (size_t i = 1; i < argc; ++i) {
            if (wd[i] == event->wd) {
                printf("%s/", argv[i]);
                break;
            }
        }

        /* Print the name of the file.  */
        if (event->len)
            printf("%s", event->name);

        /* Print type of filesystem object.  */
        if (event->mask & IN_ISDIR)
            printf(" [directory]\n");
        else
            printf(" [file]\n");

        /* Move pointer to the next event */
        ptr += sizeof(struct inotify_event) + event->len;
    }
}

int
main(int argc, char* argv[])
{
    char buf;
    int fd, i, poll_num;
    int *wd;
    nfds_t nfds;
    struct pollfd fds[2];

    if (argc < 2) {
        printf("Usage: %s PATH [PATH ...]\n", argv[0]);
        exit(EXIT_FAILURE);
    }

    printf("Press ENTER key to terminate.\n");

    /* Create the file descriptor for accessing the inotify API.  */
    fd = inotify_init1(IN_NONBLOCK);
    if (fd == -1) {
        perror("inotify_init1");
        exit(EXIT_FAILURE);
    }

    /* Allocate memory for watch descriptors.  */
    wd = calloc(argc, sizeof(int));
    if (wd == NULL) {
        perror("calloc");
        exit(EXIT_FAILURE);
    }

    /* Mark directories for events
       - file was opened
       - file was closed */
    for (i = 1; i < argc; i++) {
        wd[i] = inotify_add_watch(fd, argv[i],
                                  IN_OPEN | IN_CLOSE);
        if (wd[i] == -1) {
            fprintf(stderr, "Cannot watch '%s': %s\n",
                    argv[i], strerror(errno));
            /* Continue execution even if some watches fail */
        }
    }

    /* Prepare for polling.  */
    nfds = 2;
    fds[0].fd = STDIN_FILENO;       /* Console input */
    fds[0].events = POLLIN;
    fds[1].fd = fd;                 /* Inotify input */
    fds[1].events = POLLIN;

    /* Wait for events and/or terminal input.  */
    printf("Listening for events.\n");
    while (1) {
        poll_num = poll(fds, nfds, -1);
        if (poll_num == -1) {
            if (errno == EINTR)
                continue;
            perror("poll");
            exit(EXIT_FAILURE);
        }

        if (poll_num > 0) {
            if (fds[0].revents & POLLIN) {
                /* Console input is available.  Empty stdin and quit.  */
                while (read(STDIN_FILENO, &buf, 1) > 0 && buf != '\n')
                    continue;
                break;
            }

            if (fds[1].revents & POLLIN) {
                /* Inotify events are available.  */
                handle_events(fd, wd, argc, argv);
            }
        }
    }

    printf("Listening for events stopped.\n");

    /* Close inotify file descriptor.  */
    close(fd);
    free(wd);
    exit(EXIT_SUCCESS);
}
