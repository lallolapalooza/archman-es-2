NOTA

S

Los descriptores de archivo de inotify se pueden monitorear usando select(2), poll(2), y epoll(7). Cuando hay un evento disponible, el descriptor de archivo indica que es

legible.

Desde Linux 2.6.25, la notificación de E/S dirigida por señal está disponible para los descriptores de archivo de inotify; véase la discusión de F_SETFL (para establecer la bandera O_ASYNC), F_SETOWN, y F_SETSIG en fcntl(2). La estructura siginfo_t (descrita en sigaction(2)) que se pasa al manejador de señal tiene los siguientes campos establecidos: si_fd se establece al número de descriptor de archivo de inotify; si_signo se establece al número de señal; si_code se establece a POLL_IN; y POLLIN se establece en si_band

.

Si los eventos de inotify de salida sucesivos producidos en el descriptor de archivo de inotify son idénticos (mismo wd, mask, cookie, y name), tcuando se fusionan en un solo evento si el evento más antiguo aún no ha sido leído (pero ver ERRORES). Esto reduce la cantidad de memoria del kernel requerida para la cola de eventos, pero también significa que una aplicación no puede usar inotify para contar eventos de archivos de manera

fiable.

Los eventos devueltos al leer desde un descriptor de archivo de inotify forman una cola ordenada. Así, por ejemplo, se garantiza que al renombrar de un directorio a otro, se producirán eventos en el orden correcto en el descriptor de archivo de

inotify.

El conjunto de descriptores de vigilancia que se está monitoreando a través de un descriptor de archivo de inotify se puede ver a través de la entrada para el descriptor de archivo de inotify en el /proc/pid/fdinfo del proceso. Vea proc(5) para más detalles. El FIONREAD ioctl(2) devuelve el número de bytes disponibles para leer desde un descriptor de archivo de

inotify.

Limitaciones y

advertencias

La API de inotify no proporciona información sobre el usuario o proceso que desencadenó el evento de inotify. En particular, no hay una manera fácil para un proceso que monitorea eventos a través de inotify de distinguir los eventos que desencadena él mismo de aquellos que son desencadenados por otros

procesos.

Inotify solo reporta eventos que un programa de espacio de usuario desencadena a través de la API del sistema de archivos. Como resultado, no captura eventos remotos que ocurren en sistemas de archivos de red. (Las aplicaciones deben recurrir a la consulta del sistema de archivos para capturar tales eventos.) Además, varios pseudo-sistemas de archivos como /proc, /sys, y /dev/pts no se pueden monitorear con

inotify.

La API de inotify no reporta accesos y modificaciones de archivos que pueden ocurrir debido a mmap(2), msync(2), y munmap(

2).

La API de inotify identifica los archivos afectados por nombre de archivo. Sin embargo, para cuando una aplicación procesa un evento de inotify, el nombre de archivo ya puede haber sido eliminado o

renombrado.

La API de inotify identifica eventos a través de descriptores de vigilancia. Es responsabilidad de la aplicación almacenar en caché un mapeo (si se necesita) entre descriptores de vigilancia y rutas de acceso. Tenga en cuenta que los renombrados de directorios pueden afectar a múltiples rutas de acceso almacenadas en

caché.

El monitoreo de directorios con inotify no es recursivo: para monitorear subdirectorios bajo un directorio, se deben crear vigilancias adicionales. Esto puede llevar una cantidad significativa de tiempo para árboles de directorios

grandes.

Si está monitoreando un subárbol completo de directorios, y se crea un nuevo subdirectorio en ese árbol o un directorio existente se renombra dentro de ese árbol, tenga en cuenta de que para cuando usted cree una vigilancia para el nuevo subdirectorio, nuevos archivos (y subdirectorios) pueden ya existir dentro del subdirectorio. Por lo tanto, es posible que desee escanear el contenido del subdirectorio inmediatamente después de agregar la vigilancia (y, si lo desea, agregar recursivamente vigilancias para cualquier subdirectorio que contenga)

.

Tenga en cuenta de que la cola de eventos puede desbordarse. En este caso, los eventos se pierden. Las aplicaciones robustas deben manejar la posibilidad de eventos perdidos con elegancia. Por ejemplo, puede ser necesario reconstruir parte o toda la caché de la aplicación. (Un enfoque simple, pero posiblemente costoso, es cerrar el descriptor de archivo de inotify, vaciar la caché, crear un nuevo descriptor de archivo de inotify, y luego recrear las vigilancias y las entradas de caché para los objetos a monitorear.

)

Si un sistema de archivos se monta encima de un directorio monitoreado, no se genera ningún evento, y no

se generan eventos para los objetos inmediatamente debajo del nuevo punto de montaje. Si el sistema de
archivos se desmonta posteriormente, se generarán eventos para el directorio y los objetos que contiene.

Manejo de eventos

rename()

Como se indicó anteriormente, el par de eventos IN_MOVED_FROM e IN_MOVED_TO generado por rename(2) se puede emparejar a través de su valor de cookie compartido. Sin embargo, la tarea de emparejar tiene algunos

desafíos.

Estos dos eventos suelen ser consecutivos en el flujo de eventos disponible al leer desde el descriptor de archivo de inotify. Sin embargo, esto no está garantizado. Si múltiples procesos están desencadenando eventos para objetos monitoreados, entonces (en ocasiones raras) un número arbitrario de otros eventos puede aparecer entre los eventos IN_MOVED_FROM e IN_MOVED_TO. Además, no está garantizado que el par de eventos se inserte atómicamente en la cola: puede haber un breve intervalo donde el IN_MOVED_FROM haya aparecido, pero el IN_MOVED_T

O no.

Emparejar el par de eventos IN_MOVED_FROM e IN_MOVED_TO generado por rename(2) es por lo tanto inherentemente propenso a condiciones de carrera. (No olvide que si un objeto se renombra fuera de un directorio monitoreado, puede que ni siquiera haya un evento IN_MOVED_TO.) Se pueden usar enfoques heurísticos (p. ej., asumir que los eventos siempre son consecutivos) para asegurar una coincidencia en la mayoría de los casos, pero inevitablemente se perderán algunos casos, haciendo que la aplicación perciba los eventos IN_MOVED_FROM e IN_MOVED_TO como no relacionados. Si los descriptores de vigilancia se destruyen y se recrean como resultado, entonces esos descriptores de vigilancia serán inconsistentes con los descriptores de vigilancia en cualquier evento pendiente. (Recrear el descriptor de archivo de inotify y reconstruir la caché puede ser útil para manejar este escenario.

)

Las aplicaciones también deben permitir la posibilidad de que el evento IN_MOVED_FROM fuera el último evento que cabía en el búfer devuelto por la llamada actual a read(2), y el evento IN_MOVED_TO acompañante podría obtenerse solo en la siguiente read(2), la cual debe hacerse con un tiempo de espera (pequeño) para permitir el hecho de que la inserción del par de eventos IN_MOVED_FROM+IN_MOVED_TO no es atómica, y también la posibilidad de que no haya ningún evento I

ERRORE

S

Antes de Linux 3.19, fallocate(2) no creaba ningún evento de inotify. Desde Linux 3.19, las llamadas a fallocate(2) generan eventos IN_M

ODIFY.

Antes de Linux 2.6.16, la máscara IN_ONESHOT no funcio

naba.

Tal como fue diseñado e implementado originalmente, el indicador IN_ONESHOT no causaba que se generara un evento IN_IGNORED cuando la vigilancia se eliminaba después de un evento. Sin embargo, como un efecto no deseado de otros cambios, desde Linux 2.6.36, un evento IN_IGNORED se genera en este

caso.

Antes de Linux 2.6.25, el código del kernel que estaba destinado a fusionar eventos idénticos sucesivos (es decir, los dos eventos más recientes podrían potencialmente fusionarse si el más antiguo aún no había sido leído) en su lugar verificaba si el evento más reciente podía fusionarse con el evento no leído más

antiguo.

Cuando un descriptor de vigilancia se elimina llamando a inotify_rm_watch(2) (o porque un archivo de vigilancia se elimina o el sistema de archivos que lo contiene se desmonta), cualquier evento pendiente no leído para ese descriptor de vigilancia permanece disponible para leer. A medida que los descriptores de vigilancia se asignan posteriormente con inotify_add_watch(2), el kernel recorre el rango de posibles descriptores de vigilancia (1 a INT_MAX) incrementalmente. Al asignar un descriptor de vigilancia libre, no se realiza ninguna verificación para ver si ese número de descriptor de vigilancia tiene algún evento pendiente no leído en la cola de inotify. Por lo tanto, puede suceder que un descriptor de vigilancia se reasigne incluso cuando existen eventos pendientes no leídos para una encarnación anterior de ese número de descriptor de vigilancia, con el resultado de que la aplicación podría entonces leer esos eventos e interpretarlos como pertenecientes al archivo asociado con el descriptor de vigilancia reciclado recientemente. En la práctica, la probabilidad de encontrar este error puede ser extremadamente baja, ya que requiere que una aplicación recorra INT_MAX descriptores de vigilancia, libere un descriptor de vigilancia dejando eventos no leídos para ese descriptor de vigilancia en la cola, y luego recicle ese descriptor de vigilancia. Por est

a razón, y porque no ha habido informes de la ocurrencia de este error en aplicaciones del mundo real
, a partir de Linux 3.15, aún no se han hecho cambios en el kernel para eliminar este posible error.

#include <unistd.h>
#include <string.h>
/* Read all available inotify events from the file descriptor 'fd'.
   wd is the table of watch descriptors for the directories in argv.
   argc is the size of wd and argv.
   argv is the list of watched directories.
   Entry 0 of wd and argv is unused.  */
static void
handle_events(int fd, int *wd, int argc, char* argv[])
{
    /* Some systems cannot read integer variables if they are not
       properly aligned.  On other systems, incorrect alignment may
       decrease performance.  Hence, the buffer used for reading from
       the inotify file descriptor should have the same alignment as
       struct inotify_event.  */
    char buf[4096]
        __attribute__ ((aligned(__alignof__(struct inotify_event))));
    const struct inotify_event *event;
    ssize_t size;
    /* Loop while events can be read from inotify file descriptor.  */
    for (;;) {
        /* Read some events.  */
        size = read(fd, buf, sizeof(buf));

            perror("read");
            exit(EXIT_FAILURE);
        }
