NNTP

pour

Il gère le protocole standard IHAVE ainsi que l'extension de flux CHECK/TAKETHIS. innfeed peut alimenter un nombre quelconque de hôtes distants à la fois et ouvrira plusieurs connexions à chaque hôte si cela est configuré. Les seules limites sont les limites du processus concernant les descripteurs de fichiers ouverts et la mémoire. En alternative à l'utilisation de NNTP, INN

peut

également être alimenté vers un serveur IMAP. Cela se fait en utilisant un exécutable appelé imapfeed, qui est identique à innfeed à l'exception du processus de livraison. La nouvelle version a deux types de connexions : une connexion LMTP pour livrer les messages réguliers et une connexion IMAP pour gérer les messages de contrôle. Utilisé en conjonction avec delayer(8)

,

innfeed peut envoyer un flux différé aux pairs distants ou à une autre instance locale de innd, notamment pour permettre le rejet du spam avant qu'il n'arrive réellement. MODE

S innfeed a trois mode

canal

En mode canal, innfeed s'exécute avec stdin connecté via un tube à innd. Chaque fois que innd ferme ce tube (et il a plusieurs raisons de le faire lors du traitement normal), innfeed se terminera. Il essaiera d'abord de terminer l'envoi de tous les articles qu'il était en train de transmettre, avant d'émettre une commande QUIT. Cela signifie que innfeed peut prendre un certain temps pour se terminer, selon la lenteur de vos pairs. Il ne coupe jamais (ou presque jamais) la connexion. La manière recommandée de redémarrer innfeed lorsqu'il s'exécute en mode canal est donc de dire à innd de fermer le tube et de lancer un nouveau processus innfeed. Cela peut être fait avec "ctlinnd flush feed " où feed est le nom du flux decanal innfeed dans le fichier newsfeeds. Le mode fichier-entonnoir est utilisé lor

squ'un

nom de fichier est donné en argument ou que le mot-clé input-file est donné dans le fichier de configuration. En mode fichier-entonnoir, il lit le fichier spécifié pour les mêmes informations formatées que innd donnerait en mode canal. On s'attend à ce que innd écrive continuellement dans ce fichier, donc lorsque innfeed atteint la fin du fichier, il vérifiera périodiquement la présence de nouvelles informations. Pour empêcher le fichier entonnoir de croître sans limites, vous devrez périodiquement déplacer le fichier sur le côté (ou simplement le supprimer) et faire innd vider le fichier. Ensuite, après que le fichier a été vidé par innd, vous pouvez envoyer un SIGALRM à innfeed, et il fermera également le fichier et ouvrira le nouveau fichier créé par innd. Quelque chose comme : innfeed -p

OPTIONS

-a
The -a flag is used to tell innfeed not to read its configuration from innfeed.conf, but to read it from the standard input. This is useful for testing purposes.
-c
The -c flag tells innfeed to only process batch files. This is intended for use with the innd batch processing mechanism and is not to be confused with the -x flag.
-d
The -d flag is used to prevent innfeed from forking. This is useful for debugging purposes.
-f file
The -f flag specifies an alternative configuration file for innfeed to use. This overrides the default location of innfeed.conf.
-i
The -i flag tells innfeed to process articles from the input pipe only once. This is useful when you want to avoid processing the same articles multiple times.
-l
The -l flag causes innfeed to log all its activity to stderr. This is useful for debugging.
-m memory-size
The -m flag specifies the amount of memory in kilobytes that innfeed should use to store article data. The default is determined by the system. The value given with this option is used to limit the amount of memory that innfeed is supposed to keep in memory. This does not work properly yet.
-p pid-file
The -p flag is used to specify the file name to write the pid of the process into. A relative path is relative to pathrun as set in inn.conf. The default is innfeed.pid.

You are encouraged to use the pid-file parameter in the configuration file to declare a specific file name, as otherwise scanlogs won't get it and the log file won't be properly flushed before being rotated.

-s command
The -s flag specifies the name of a command to run in a subprocess and read article information from. This is similar to channel mode operation, only that command takes the place usually occupied by innd.
-S status-file
The -S flag specifies the name of the file to write the periodic status to. If the path is relative, it is considered relative to pathlog as set in inn.conf. The default is innfeed.status.
-v
When the -v flag is given, version information is printed to stderr and then innfeed exits.
-x
The -x flag is used to tell innfeed not to expect any article information from innd but just to process any backlog files that exist and then exit.
-y
The -y flag is used to allow dynamic peer binding. If this flag is used and article information is received from innd that specifies an unknown peer, then the peer name is taken to be the IP name too, and an association with it is created. Using this, it is possible to only have the global defaults in the innfeed.conf file, provided the peer name as used by innd is the same as the IP name.

Note that innfeed with -y and no peer in innfeed.conf would cause a problem that innfeed drops the first article.

-z
The -z flag is used to cause each connection, in a parallel feed configuration, to report statistics when the controller for the connections prints its statistics.

BUGS

When using the -x option, the config file entry's initial-connections field will be the total number of connections created and used, no matter how many big the batch file, and no matter how big the max-connections field specifies. Thus a value of 0 for initial-connections means nothing will happen in -x mode.

innfeed does not automatically grab the file out of pathoutgoing. This needs to be prepared for it by external means.

Probably too many other bugs to count.

ALTERNATIVE

An alternative to innfeed can be innduct, maintained by Ian Jackson and available at http://www.chiark.greenend.org.uk/ucgi/~ian/git-manpage/innduct.git/innduct.8. It is intended to solve a design issue in the way innfeed works. As a matter of fact, the program feed protocol spoken between innd and innfeed is lossy: if innfeed dies unexpectedly, articles which innd has written to the pipe to innfeed will be skipped. innd has no way of telling which articles those are, no useful records, and no attempts to resend these articles.
