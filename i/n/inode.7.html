NOMBRE

inode - información del inode de un archivo

DESCRIPCIÓN

Cada archivo tiene un inode que contiene metadatos sobre el archivo. Una aplicación puede recuperar estos metadatos usando stat(2) (o llamadas relacionadas), que devuelve una stat estructura, o statx(2), que devuelve una statx estructura.

La siguiente es una lista de la información que se encuentra típicamente en, o asociada con, el inode del archivo, con los nombres de los campos de la estructura correspondientes devueltos por stat(2) y statx(2):

Dispositivo donde reside el inode
stat.st_dev; statx.stx_dev_minor y statx.stx_dev_major
Cada inode (así como el archivo asociado) reside en un sistema de archivos que está alojado en un dispositivo. Ese dispositivo se identifica por la combinación de su ID mayor (que identifica la clase general del dispositivo) y su ID menor (que identifica una instancia específica dentro de la clase general).
Número de inode
stat.st_ino; statx.stx_ino
Cada archivo en un sistema de archivos tiene un número de inode único. Se garantiza que los números de inode sean únicos solo dentro de un sistema de archivos (es decir, los mismos números de inode pueden ser usados por diferentes sistemas de archivos, que es la razón por la que los enlaces duros no pueden cruzar límites de sistemas de archivos). Este campo contiene el número de inode del archivo.
Tipo de archivo y modo
stat.st_mode; statx.stx_mode
Vea la discusión sobre el tipo de archivo y modo, más abajo.
Conteo de enlaces
stat.st_nlink; statx.stx_nlink
Este campo contiene el número de enlaces duros al archivo. Enlaces adicionales a un archivo existente se crean usando link(2).
ID de usuario
stat.st_uid; statx.stx_uid
Este campo registra el ID de usuario del propietario del archivo. Para archivos recién creados, el ID de usuario del archivo es el ID de usuario efectivo del proceso que lo crea. El ID de usuario de un archivo puede ser cambiado usando chown(2).
ID de grupo
stat.st_gid; statx.stx_gid
El inode registra el ID del grupo propietario del archivo. Para archivos recién creados, el ID de grupo del archivo es o bien el ID de grupo del directorio padre o el ID de grupo efectivo del proceso que lo crea, dependiendo de si el bit set-group-ID está establecido o no en el directorio padre (vea más abajo). El ID de grupo de un archivo puede ser cambiado usando chown(2).
Dispositivo representado por este inode
stat.st_rdev; statx.stx_rdev_minor y statx.stx_rdev_major
Si este archivo (inode) representa un dispositivo, entonces el inode registra el ID mayor y menor de ese dispositivo.
Tamaño del archivo
stat.st_size; statx.stx_size
Este campo da el tamaño del archivo (si es un archivo regular o un enlace simbólico) en bytes. El tamaño de un enlace simbólico es la longitud de la ruta de acceso que contiene, sin un byte nulo final.
Tamaño de bloque preferido para E/S
stat.st_blksize; statx.stx_blksize
Este campo da el tamaño de bloque "preferido" para una E/S eficiente en el sistema de archivos. (Escribir en un archivo en trozos más pequeños puede causar una lectura-modificación-reescritura ineficiente.)
Número de bloques asignados al archivo
stat.st_blocks; statx.stx_blocks
Este campo indica el número de bloques asignados al archivo, en unidades de 512 bytes, (Esto puede ser menor que st_size/512 cuando el archivo tiene huecos.)
El estándar POSIX.1 nota que la unidad para el miembro st_blocks de la estructura stat no está definida por el estándar. En muchas implementaciones es de 512 bytes; en algunos sistemas, se usa una unidad diferente, como 1024. Además, la unidad puede diferir por sistema de archivos.
Marca de tiempo de último acceso (atime)
stat.st_atime; statx.stx_atime
Esta es la marca de tiempo del último acceso al archivo. Es cambiada por accesos al archivo, por ejemplo, por execve(2), mknod(2), pipe(2), utime(2), y read(2) (de más de cero bytes). Otras interfaces, como mmap(2), pueden o no actualizar la marca de tiempo atime
Algunos tipos de sistemas de archivos permiten ser montados de tal manera que los accesos a archivos y/o directorios no causan una actualización de la marca de tiempo atime. (Vea noatime, nodiratime, y relatime en mount(8), e información relacionada en mount(2).) Además, la marca de tiempo atime no se actualiza si un archivo es abierto con el indicador O_NOATIME ; vea open(2).
Marca de tiempo de creación (nacimiento) del archivo (btime)
(no devuelta en la stat estructura); statx.stx_btime
La marca de tiempo de creación del archivo. Esta se establece en la creación del archivo y no cambia posteriormente.
La marca de tiempo btime no estaba históricamente presente en los sistemas UNIX y no es soportada actualmente por la mayoría de los sistemas de archivos de Linux.
Marca de tiempo de última modificación (mtime)
stat.st_mtime; statx.stx_mtime
Esta es la marca de tiempo de la última modificación del archivo. Es cambiada por modificaciones del archivo, por ejemplo, por mknod(2), truncate(2), utime(2), y write(2) (de más de cero bytes). Además, la marca de tiempo mtime de un directorio es cambiada por la creación o eliminación de archivos en ese directorio. La marca de tiempo mtime es no cambiada por cambios en el propietario, grupo, conteo de enlaces duros, o modo.
Marca de tiempo de último cambio de estado (ctime)
stat.st_ctime; statx.stx_ctime
Esta es la marca de tiempo del último cambio de estado del archivo. Es cambiada por escrituras o por la configuración de información del inode (es decir, propietario, grupo, conteo de enlaces, modo, etc.).

Los campos de marca de tiempo reportan el tiempo medido con un punto cero en la Época, 1970-01-01 00:00:00 +0000, UTC (vea time(7)).

Las marcas de tiempo en nanosegundos son soportadas en XFS, JFS, Btrfs, y ext4 (desde Linux 2.6.23). Las marcas de tiempo en nanosegundos no son soportadas en ext2, ext3, y Reiserfs. Para devolver marcas de tiempo con precisión de nanosegundos, los campos de marca de tiempo en las estructuras stat y statx están definidos como estructuras que incluyen un componente de nanosegundos. Vea stat(2) y statx(2) para detalles. En sistemas de archivos que no soportan marcas de tiempo de subsegundo, los campos de nanosegundos en las estructuras stat y statx se devuelven con el valor 0.

El tipo de archivo y modo

El stat.st_mode campo (para statx(2), el statx.stx_mode campo) contiene el tipo de archivo y el modo.

POSIX se refiere a los bits de stat.st_mode correspondientes a la máscara S_IFMT (ver abajo) como el tipo de archivo, los 12 bits correspondientes a la máscara 07777 como los bits de modo de archivo y los 9 bits menos significativos (0777) como los bits de permisos de archivo.

Se definen los siguientes valores de máscara para el tipo de archivo:

S_IFMT 0170000 máscara de bits para el campo de bits del tipo de archivo
S_IFSOCK 0140000 socket
S_IFLNK 0120000 enlace simbólico
S_IFREG 0100000 archivo regular
S_IFBLK 0060000 dispositivo de bloques
S_IFDIR 0040000 directorio
S_IFCHR 0020000 dispositivo de caracteres
S_IFIFO 0010000 FIFO

Así, para comprobar si es un archivo regular (por ejemplo), se podría escribir:


stat(pathname, &sb);
if ((sb.st_mode & S_IFMT) == S_IFREG) {
    /* Handle regular file */
}

Debido a que las pruebas de la forma anterior son comunes, POSIX define macros adicionales para permitir que la prueba del tipo de archivo en st_mode se pueda escribir de forma más concisa:

S_ISREG(m)
¿es un archivo regular?
S_ISDIR(m)
¿directorio?
S_ISCHR(m)
¿dispositivo de caracteres?
S_ISBLK(m)
¿dispositivo de bloques?
S_ISFIFO(m)
¿FIFO (tubería con nombre)?
S_ISLNK(m)
¿enlace simbólico? (No en POSIX.1-1996.)
S_ISSOCK(m)
¿socket? (No en POSIX.1-1996.)

El fragmento de código anterior podría reescribirse así:


stat(pathname, &sb);
if (S_ISREG(sb.st_mode)) {
    /* Handle regular file */
}

Las definiciones de la mayoría de las macros de prueba de tipo de archivo anteriores se proporcionan si se define alguna de las siguientes macros de prueba de características: _BSD_SOURCE (en glibc 2.19 y anteriores), _SVID_SOURCE (en glibc 2.19 y anteriores), o _DEFAULT_SOURCE (en glibc 2.20 y posteriores). Además, se proporcionan las definiciones de todas las macros anteriores excepto S_IFSOCK y S_ISSOCK() si se define _XOPEN_SOURCE .

La definición de S_IFSOCK también puede exponerse ya sea definiendo _XOPEN_SOURCE con un valor de 500 o superior, o (desde glibc 2.24) definiendo tanto _XOPEN_SOURCE como _XOPEN_SOURCE_EXTENDED.

La definición de S_ISSOCK() se expone si se define alguna de las siguientes macros de prueba de características: _BSD_SOURCE (en glibc 2.19 y anteriores), _DEFAULT_SOURCE (en glibc 2.20 y posteriores), _XOPEN_SOURCE con un valor de 500 o superior, _POSIX_C_SOURCE con un valor de 200112L o superior, o (desde glibc 2.24) definiendo tanto _XOPEN_SOURCE como _XOPEN_SOURCE_EXTENDED.

Se definen los siguientes valores de máscara para el componente de modo de archivo del campo st_mode :

S_ISUID 04000 bit set-user-ID (ver execve (2))
S_ISGID 02000 bit set-group-ID (ver abajo)
S_ISVTX 01000 bit sticky (ver abajo)
S_IRWXU 00700 el propietario tiene permisos de lectura, escritura y ejecución
S_IRUSR 00400 el propietario tiene permiso de lectura
S_IWUSR 00200 el propietario tiene permiso de escritura
S_IXUSR 00100 el propietario tiene permiso de ejecución
S_IRWXG 00070 el grupo tiene permisos de lectura, escritura y ejecución
S_IRGRP 00040 el grupo tiene permiso de lectura
S_IWGRP 00020 el grupo tiene permiso de escritura
S_IXGRP 00010 el grupo tiene permiso de ejecución
S_IRWXO 00007 otros (no pertenecientes al grupo) tienen permisos de lectura, escritura y ejecución
S_IROTH 00004 otros tienen permiso de lectura
S_IWOTH 00002 otros tienen permiso de escritura
S_IXOTH 00001 otros tienen permiso de ejecución

El bit set-group-ID (S_ISGID) tiene varios usos especiales. Para un directorio, indica que se deben usar la semántica de BSD para ese directorio: los archivos creados allí heredan su ID de grupo del directorio, no del ID de grupo efectivo del proceso que los crea, y los directorios creados allí también tendrán el bit S_ISGID establecido. Para un archivo ejecutable, el bit set-group-ID hace que el ID de grupo efectivo de un proceso que ejecute el archivo cambie como se describe en execve(2). Para un archivo que no tiene el bit de ejecución de grupo (S_IXGRP) establecido, el bit set-group-ID indica bloqueo obligatorio de archivos/registros.

El bit sticky (S_ISVTX) en un directorio significa que un archivo en ese directorio solo puede ser renombrado o eliminado por el propietario del archivo, por el propietario del directorio y por un proceso privilegiado.

ESTÁNDARES

POSIX.1-2008.

HISTORIA

POSIX.1-2001.

POSIX.1-1990 no describía las constantes S_IFMT, S_IFSOCK, S_IFLNK, S_IFREG, S_IFBLK, S_IFDIR, S_IFCHR, S_IFIFOy S_ISVTX , sino que especificaba el uso de las macros S_ISDIR() y demás.

Las macros S_ISLNK() y S_ISSOCK() no estaban en POSIX.1-1996; la primera proviene de SVID 4, la segunda de SUSv2.

UNIX V7 (y sistemas posteriores) tenía S_IREAD, S_IWRITE, S_IEXEC, y donde POSIX prescribe los sinónimos S_IRUSR, S_IWUSRy S_IXUSR.

NOTAS

Para los pseudoficheros que son autogenerados por el kernel, el tamaño del archivo (stat.st_size; statx.stx_size) informado por el kernel no es preciso. Por ejemplo, se devuelve el valor 0 para muchos archivos bajo el directorio /proc , mientras que varios archivos bajo /sys informan un tamaño de 4096 bytes, aunque el contenido del archivo sea más pequeño. Para tales archivos, se debe simplemente intentar leer tantos bytes como sea posible (y añadir '\0' al búfer devuelto si se va a interpretar como una cadena).
