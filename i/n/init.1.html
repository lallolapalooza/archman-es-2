NOMBRE

systemd, init - gestor de sistema y servicios de systemd

SINOPSIS

/usr/lib/systemd/systemd [OPCIONES...]

init [OPCIONES...]

DESCRIPCIÓN

systemd es un gestor de sistema y servicios para sistemas operativos Linux. Cuando se ejecuta como primer proceso al arrancar (como PID 1), actúa como sistema de inicio (init) que activa y mantiene los servicios del espacio de usuario. Se inician instancias separadas para los usuarios conectados para iniciar sus servicios.

systemd normalmente no es invocado directamente por el usuario, sino que se instala como el enlace simbólico /sbin/init y se inicia durante el arranque temprano. Las instancias del gestor de usuario se inician automáticamente a través del servicio user@.service(5).

Cuando se ejecuta como una instancia del sistema, systemd interpreta el archivo de configuración system.conf y los archivos en los directorios system.conf.d; cuando se ejecuta como una instancia de usuario, systemd interpreta el archivo de configuración user.conf y los archivos en los directorios user.conf.d. Consulte systemd-system.conf(5) para obtener más información.

systemd contiene implementaciones nativas de varias tareas que deben ejecutarse como parte del proceso de arranque. Por ejemplo, establece el nombre del host o configura el dispositivo de red de bucle inverso. También configura y monta varios sistemas de archivos de la API, como /sys/, /proc/, y /dev/.

systemd también reiniciará el reloj del sistema durante el arranque temprano si parece estar configurado incorrectamente. Consulte la sección "Época del reloj del sistema" a continuación.

Tenga en cuenta que algunas, pero no todas, las interfaces proporcionadas por systemd están cubiertas por la Promesa de Estabilidad y Portabilidad de la Interfaz[1].

La API de D-Bus de systemd se describe en org.freedesktop.systemd1(5) y org.freedesktop.LogControl1(5).

Los sistemas que invocan systemd en un entorno de contenedor o initrd deberían implementar las especificaciones de la Interfaz de Contenedor[2] o la Interfaz de initrd[3], respectivamente.

UNIDADES

systemd proporciona un sistema de dependencias entre varias entidades llamadas "unidades" de 11 tipos diferentes. Las unidades encapsulan varios objetos que son relevantes para el arranque y mantenimiento del sistema. La mayoría de las unidades se configuran en archivos de configuración de unidades, cuya sintaxis y conjunto básico de opciones se describe en systemd.unit(5), sin embargo, algunas se crean automáticamente a partir de otros archivos de configuración, dinámicamente a partir del estado del sistema o programáticamente en tiempo de ejecución. Las unidades pueden estar en varios estados, descritos en la siguiente tabla. Tenga en cuenta que los diversos tipos de unidades pueden tener varios subestados adicionales, que se mapean a los estados de unidad generalizados descritos aquí.

Tabla 1. Estados ACTIVAS de la unidad

Estado Descripción
active Iniciado, enlazado, conectado, ..., dependiendo del tipo de unidad.
inactive Detenido, desenlazado, desconectado, ..., dependiendo del tipo de unidad.
failed Similar a inactive, pero la unidad falló de alguna manera (el proceso devolvió un código de error al salir, se bloqueó, una operación expiró, o después de demasiados reinicios).
activating Cambiando de inactive a active.
deactivating Cambiando de active a inactive.
maintenance La unidad está inactive y se está realizando una operación de mantenimiento.
reloading La unidad está active y está recargando su configuración.
refreshing La unidad está active y se está activando un nuevo montaje en su espacio de nombres.

Los siguientes tipos de unidades están disponibles:

1.Unidades de servicio (Service units), que inician y controlan demonios y los procesos que los componen. Para más detalles, consulte systemd.service(5).
2.Unidades de socket (Socket units), que encapsulan sockets IPC o de red locales en el sistema, útiles para la activación basada en sockets. Para detalles sobre unidades de socket, consulte systemd.socket(5), para detalles sobre la activación basada en sockets y otras formas de activación, consulte daemon(7).
3.Unidades de destino (Target units) son útiles para agrupar unidades, o proporcionar puntos de sincronización conocidos durante el arranque, consulte systemd.target(5).
4.Unidades de dispositivo (Device units) exponen los dispositivos del kernel en systemd y pueden usarse para implementar la activación basada en dispositivos. Para detalles, consulte systemd.device(5).
5.Unidades de montaje (Mount units) controlan los puntos de montaje en el sistema de archivos, para detalles consulte systemd.mount(5).
6.Unidades de montaje automático (Automount units) proporcionan capacidades de montaje automático, para el montaje bajo demanda de sistemas de archivos, así como para el arranque paralelo. Consulte systemd.automount(5).
7.Unidades de temporizador (Timer units) son útiles para activar otras unidades basándose en temporizadores. Puede encontrar detalles en systemd.timer(5).
8.Unidades de intercambio (Swap units) son muy similares a las unidades de montaje y encapsulan particiones o archivos de intercambio de memoria del sistema operativo. Se describen en systemd.swap(5).
9.Unidades de ruta (Path units) pueden usarse para activar otros servicios cuando los objetos del sistema de archivos cambian o se modifican. Consulte systemd.path(5).
10.Unidades de slice (Slice units) pueden usarse para agrupar unidades que gestionan procesos del sistema (como unidades de servicio y de ámbito) en un árbol jerárquico para fines de gestión de recursos. Consulte systemd.slice(5).
11.Unidades de ámbito (Scope units) son similares a las unidades de servicio, pero gestionan procesos externos en lugar de iniciarlos también. Consulte systemd.scope(5).

Las unidades se nombran como sus archivos de configuración. Algunas unidades tienen semánticas especiales. Una lista detallada está disponible en systemd.special(7).

systemd conoce varios tipos de dependencias, incluyendo dependencias de requisito positivas y negativas (es decir, Requires= y Conflicts=) así como dependencias de ordenación (After= y Before=). NB: las dependencias de ordenación y requisito son ortogonales. Si solo existe una dependencia de requisito entre dos unidades (por ejemplo, foo.service requiere bar.service), pero ninguna dependencia de ordenación (por ejemplo, foo.service después de bar.service) y se solicita que ambas se inicien, se iniciarán en paralelo. Es un patrón común que se incluyan dependencias tanto de requisito como de ordenación entre dos unidades. Tenga en cuenta también que la mayoría de las dependencias son creadas y mantenidas implícitamente por systemd. En la mayoría de los casos, no debería ser necesario declarar dependencias adicionales manualmente, sin embargo, es posible hacerlo.

Las aplicaciones y las unidades (a través de dependencias) pueden solicitar cambios de estado de las unidades. En systemd, estas solicitudes se encapsulan como 'jobs' y se mantienen en una cola de jobs. Los jobs pueden tener éxito o fallar, su ejecución se ordena basándose en las dependencias de ordenación de las unidades para las que se han programado.

Al arrancar, systemd activa la unidad de destino default.target, cuya tarea es activar los servicios y otras unidades de arranque mediante su inclusión a través de dependencias. Normalmente, el nombre de la unidad es solo un alias (enlace simbólico) para graphical.target (para arranques completos a la interfaz de usuario) o multi-user.target (para arranques limitados solo a la consola para uso en entornos integrados o de servidor, o similares; un subconjunto de graphical.target). Sin embargo, queda a discreción del administrador configurarlo como un alias para cualquier otra unidad de destino. Consulte systemd.special(7) para obtener detalles sobre estas unidades de destino.

En el primer arranque, systemd habilitará o deshabilitará unidades de acuerdo con la política preestablecida. Consulte systemd.preset(5) y la sección "Semántica del primer arranque" en machine-id(5).

1.Se encuentra en un estado activo, de activación, de desactivación o fallido (es decir, en cualquier estado de unidad excepto "inactivo")

Los procesos que genera systemd se colocan en grupos de control individuales de Linux con el nombre de la unidad a la que pertenecen en la jerarquía privada de systemd. (véase Control Groups v2[4] para más información sobre los grupos de control, o "cgroups" en corto). systemd utiliza esto para hacer un seguimiento eficaz de los procesos. systemd es compatible con varias funcionalidades Unix establecidas como /etc/fstab o la base de datos

utmp.

systemd tiene un sistema de transacciones mínimo: si se solicita que una unidad arranque o se apague, se añadirá a ella y a todas sus dependencias a una transacción temporal. Luego, verificará si la transacción es consistente (es decir, si el ordenamiento de todas las unidades está libre de ciclos). Si no lo está, systemd intentará corregirla y eliminará los trabajos no esenciales de la transacción que podrían eliminar el bucle. Además, systemd intenta suprimir trabajos no esenciales en la transacción que detendrían un servicio en ejecución. Finalmente, se comprueba si los trabajos de la transacción contradicen trabajos que ya han sido encolados, y opcionalmente la transacción se aborta entonces. Si todo resulta bien y la transacción es consistente y minimizada en su impacto, se fusiona con todos los trabajos ya pendientes y se añade a la cola de ejecución. Efectivamente, esto significa que antes de ejecutar una operación solicitada, systemd verificará que tenga sentido, corrigiéndolo si es posible, y solo fallando si realmente no puede

funcionar.

Tenga en cuenta que las transacciones se generan independientemente del estado de una unidad en tiempo de ejecución, por lo tanto, por ejemplo, si se solicita un trabajo de inicio en una unidad ya iniciada, aún generará una transacción y despertará cualquier dependencia inactiva (y causará la propagación de otros trabajos según las relaciones definidas). Esto se debe a que el trabajo encolado se compara en el momento de la ejecución con el estado de la unidad de destino y se marca como exitoso y completo cuando ambos se satisfacen. Sin embargo, este trabajo también arrastra otras dependencias debido a las relaciones definidas y, por lo tanto, conduce a, en nuestro ejemplo, que los trabajos de inicio para cualquiera de esas unidades inactivas también se

encolen.

Las unidades pueden generarse dinámicamente en el arranque y en el momento de recarga del gestor del sistema, por ejemplo, basándose en otros archivos de configuración o parámetros pasados en la línea de comandos del kernel. Para más detalles, véase systemd.ge

nerator(7).

SIGNALS

The following signals are handled by the systemd manager:

SIGHUP

Reloads the main systemd configuration files, by executing systemctl(1) daemon in the background. This is similar to systemctl daemon-reexec, but is asynchronous.

SIGINT, SIGTERM

Shuts down all running units and exits cleanly.

SIGUSR1

Flushes all runtime data to disk.

SIGUSR2

Enters the systemd manager into a special debugging mode. All units are put into a disabled state, and no new units are started. This mode is useful for analysing the system state before a crash.

SIGQUIT

The systemd manager dumps core. This signal is only honored if the manager was built with debug support.

SIGWINCH

Relays the signal to all processes that are managed by the systemd manager.

SIGRTMIN+1

Restores the configured log level and target. The configured values are derived from – in order of priority – the values specified with systemd.log-level= and systemd.log-target= on the kernel command line, or the values specified with LogLevel= and LogTarget= in the configuration file, or the built-in defaults.

Added in version 239.

SIGRTMIN+2

Toggles the verbosity of the logging output. This signal may be sent multiple times to cycle through the available log levels.

Added in version 237.

SIGRTMIN+3

Toggles the log target. This signal may be sent multiple times to cycle through the available log targets.

Added in version 237.

SIGRTMIN+4

Toggles the timestamp logging. This signal may be sent multiple times to cycle through the available timestamp settings.

Added in version 237.

SIGRTMIN+5

Toggles the location logging. This signal may be sent multiple times to cycle through the available location settings.

Added in version 237.

SIGRTMIN+6

Toggles the thread ID logging. This signal may be sent multiple times to cycle through the available thread ID settings.

Added in version 247.

SIGRTMIN+7

Toggles the colorized logging. This signal may be sent multiple times to cycle through the available color settings.

Added in version 237.

SIGRTMIN+8

Forces a reload of the machine-id. The value is read from /etc/machine-id.

Added in version 237.

ENVIRONMENT

The environment block for the system manager is initially set by the kernel. (In particular, "key=value" assignments on the kernel command line are turned into environment variables for PID 1). For the user manager, the system manager sets the environment as described in the "Environment Variables in Spawned Processes" section of systemd.exec(5). The DefaultEnvironment= setting in the system manager applies to all services including user@.service. Additional entries may be configured (as for any other service) through the Environment= and EnvironmentFile= settings for user@.service (see systemd.exec(5)). Also, additional environment variables may be set through the ManagerEnvironment= setting in systemd-system.conf(5) and systemd-user.conf(5).

Some of the variables understood by systemd:

$SYSTEMD_LOG_LEVEL

The maximum log level of emitted messages (messages with a higher log level, i.e. less important ones, will be suppressed). Takes a comma-separated list of values. A value may be either one of (in order of decreasing importance) emerg, alert, crit, err, warning, notice, info, debug, or an integer in the range 0...7. See syslog(3) for more information. Each value may optionally be prefixed with one of console, syslog, kmsg or journal followed by a colon to set the maximum log level for that specific log target (e.g. SYSTEMD_LOG_LEVEL=debug,console:info specifies to log at debug level except when logging to the console which should be at info level). Note that the global maximum log level takes priority over any per target maximum log levels.

This can be overridden with --log-level=.

$SYSTEMD_LOG_COLOR

A boolean. If true, messages written to the tty will be colored according to priority.

This can be overridden with --log-color=.

$SYSTEMD_LOG_TIME

A boolean. If true, console log messages will be prefixed with a timestamp.

This can be overridden with --log-time=.

Added in version 246.

$SYSTEMD_LOG_LOCATION

A boolean. If true, messages will be prefixed with a filename and line number in the source code where the message originates.

This can be overridden with --log-location=.

$SYSTEMD_LOG_TID

A boolean. If true, messages will be prefixed with the current numerical thread ID (TID).

Added in version 247.

$SYSTEMD_LOG_TARGET

The destination for log messages. One of console (log to the attached tty), console-prefixed (log to the attached tty but with prefixes encoding the log level and "facility", see syslog(3), kmsg (log to the kernel circular log buffer), journal (log to the journal), journal-or-kmsg (log to the journal if available, and to kmsg otherwise), auto (determine the appropriate log target automatically, the default), null (disable log output).

This can be overridden with --log-target=.

$SYSTEMD_LOG_RATELIMIT_KMSG

Whether to ratelimit kmsg or not. Takes a boolean. Defaults to "true". If disabled, systemd will not ratelimit messages written to kmsg.

Added in version 254.

The systemd user manager uses these variables in accordance to the XDG Base Directory specification[5] to find its configuration.

$SYSTEMD_UNIT_PATH, $SYSTEMD_GENERATOR_PATH, $SYSTEMD_ENVIRONMENT_GENERATOR_PATH

Controls where systemd looks for unit files and generators.

These variables may contain a list of paths, separated by colons (":"). When set, if the list ends with an empty component ("...:"), this list is prepended to the usual set of paths. Otherwise, the specified list replaces the usual set of paths.

$SYSTEMD_PAGER, $PAGER

Pager to use when --no-pager is not given. $SYSTEMD_PAGER is used if set; otherwise $PAGER is used. If neither $SYSTEMD_PAGER nor $PAGER are set, a set of well-known pager implementations is tried in turn, including less(1) and more(1), until one is found. If no pager implementation is discovered, no pager is invoked. Setting those environment variables to an empty string or the value "cat" is equivalent to passing --no-pager.

Note: if $SYSTEMD_PAGERSECURE is not set, $SYSTEMD_PAGER and $PAGER can only be used to disable the pager (with "cat" or ""), and are otherwise ignored.

$SYSTEMD_LESS

Override the options passed to less (by default "FRSXMK").

Users might want to change two options in particular:

K

This option instructs the pager to exit immediately when Ctrl+C is pressed. To allow less to handle Ctrl+C itself to switch back to the pager command prompt, unset this option.

If the value of $SYSTEMD_LESS does not include "K", and the pager that is invoked is less, Ctrl+C will be ignored by the executable, and needs to be handled by the pager.

X

This option instructs the pager to not send termcap initialization and deinitialization strings to the terminal. It is set by default to allow command output to remain visible in the terminal even after the pager exits. Nevertheless, this prevents some pager functionality from working, in particular paged output cannot be scrolled with the mouse.

Note that setting the regular $LESS environment variable has no effect for less invocations by systemd tools.

See less(1) for more discussion.

$SYSTEMD_LESSCHARSET

Override the charset passed to less (by default "utf-8", if the invoking terminal is determined to be UTF-8 compatible).

Note that setting the regular $LESSCHARSET environment variable has no effect for less invocations by systemd tools.

When commands are invoked with elevated privileges, for example under sudo(8) or pkexec(1), the pager becomes a security boundary. Care must be taken that only programs with strictly limited functionality are used as pagers, and unintended interactive features like opening or creation of new files or starting of subprocesses are not allowed. "Secure mode" for the pager may be enabled as described below, if the pager supports that (most pagers are not written in a way that takes this into consideration). It is recommended to either explicitly enable "secure mode" or to completely disable the pager using --no-pager or PAGER=cat when allowing untrusted users to execute commands with elevated privileges.

This option takes a boolean argument. When set to true, the "secure mode" of the pager is enabled. In "secure mode", LESSSECURE=1 will be set when invoking the pager, which instructs the pager to disable commands that open or create new files or start new subprocesses. Currently only less(1) is known to understand this variable and implement "secure mode".

When set to false, no limitation is placed on the pager. Setting SYSTEMD_PAGERSECURE=0 or not removing it from the inherited environment may allow the user to invoke arbitrary commands.

When $SYSTEMD_PAGERSECURE is not set, systemd tools attempt to automatically figure out if "secure mode" should be enabled and whether the pager supports it. In those cases, SYSTEMD_PAGERSECURE=1 will be set and pagers which are not known to implement "secure mode" will not be used at all. VARIABLES DE ENTORNO

systemd y sus utilidades relacionadas entienden varias variables de entorno que permiten modificar su comportamiento. Si una variable de entorno no se menciona aquí, se ignora por completo.

$SYSTEMD_PAGER

Especifica el paginador que se utilizará para mostrar la salida. Si no está configurado, se intenta determinar un paginador apropiado automáticamente (usando $PAGER, $SYSTEMD_PAGER o internamente `less`). Si se establece en la cadena vacía, el paginador se deshabilita explícitamente. Si se establece en `systemd-pager`, se utiliza el paginador integrado de systemd.

$SYSTEMD_PAGERSECURE

Controla si el paginador se ejecuta en modo seguro. Si está configurado, el paginador se ejecutará en modo seguro, lo que significa que se deshabilitarán las opciones potencialmente inseguras del paginador (como la ejecución de comandos). Esto se recomienda para prevenir la ejecución de código arbitrario a través de la paginación.

$SYSTEMD_PAGEROPTS

Opciones para pasar al paginador. Por defecto, se pasa `-p` (o `--push-scroll`) si el paginador es `less`.

$SYSTEMD_COLORS

Controla el uso de colores en la salida. Si está configurado como `1` o `true`, se usarán colores. Si está configurado como `0` o `false`, la salida será monocromática. También puede tomar los valores `16` o `256` para restringir el uso de colores a los esquemas ANSI base de 16 o 256 colores. Esto puede anular la decisión automática basada en la variable `$TERM` y el tipo de consola conectada.

$SYSTEMD_COLORS_ENABLED

Un alias para $SYSTEMD_COLORS.

$SYSTEMD_URLIFY

Si está configurado como `1` o `true`, se generarán enlaces interactivos en la salida para emuladores de terminal que lo soporten. Si está configurado como `0` o `false`, no se generarán enlaces. Esto puede anular la decisión automática de systemd basada en la variable `$TERM` y otras condiciones.

$SYSTEMD_LOG_COLOR

Si está configurado como `1` o `true`, los mensajes de registro se mostrarán en color. Si está configurado como `0` o `false`, se suprimirá el color.

$SYSTEMD_LOG_LEVEL

Controla el nivel de detalle de los mensajes de registro. Puede tomar valores como `debug`, `info`, `notice`, `warning`, `err`, `crit`, `alert`, `emerg`. El valor por defecto es `notice`.

$SYSTEMD_LOG_LOCATION

Si está configurado como `1` o `true`, se incluirán la ruta del archivo y el número de línea de donde se generó el mensaje de registro. Si está configurado como `0` o `false`, se suprimirá esta información.

$SYSTEMD_LOG_TARGET

Controla el destino de los mensajes de registro. Puede tomar valores como `stderr`, `journal`, `kmsg`, `null`. El valor por defecto es `journal`. Si se establece en `journal+console`, los mensajes se enviarán tanto al journal como a la consola.

$SYSTEMD_LOG_TIME

Si está configurado como `1` o `true`, se incluirá la marca de tiempo de cada mensaje de registro. Si está configurado como `0` o `false`, se suprimirá la marca de tiempo.

$SYSTEMD_LOG_TID

Si está configurado como `1` o `true`, se incluirá el ID del hilo (TID) que generó el mensaje de registro. Si está configurado como `0` o `false`, se suprimirá el TID.

$SYSTEMD_LOG_RATELIMIT_KMSG

Controla la tasa de limitación de los mensajes enviados al `kmsg` (kernel message buffer). Si está configurado como `0` o `false`, se deshabilita la limitación de tasa para `kmsg`. El valor por defecto es `10` mensajes por segundo.

$SYSTEMD_NSS_SLEEP_SORT_ORDER

Controla el orden de clasificación de los resultados de las llamadas a `getaddrinfo()` y `getnameinfo()`. Puede ser `ipv4` o `ipv6`. El valor por defecto es `ipv4`.

$SYSTEMD_HOME

Se utiliza para establecer el directorio de inicio del usuario actual. Esto es útil para probar o para configuraciones específicas del usuario.

$SYSTEMD_TEST_DIR

Especifica un directorio que se utilizará como raíz para las pruebas.

$SYSTEMD_TEST_UMASK

Establece la máscara de creación de archivos (umask) para las pruebas.

$SYSTEMD_SUPERVISOR

Identifica a systemd como un supervisor.

$SYSTEMD_PIDFILE

Especifica la ruta a un archivo PID.

$SYSTEMD_CONFDIR

Especifica un directorio alternativo para los archivos de configuración.

$SYSTEMD_RUNTIME_DIR

Especifica un directorio alternativo para los directorios de tiempo de ejecución.

$SYSTEMD_STATE_DIR

Especifica un directorio alternativo para los directorios de estado.

$SYSTEMD_CONFIG_ONLY

Si está configurado como `1` o `true`, systemd solo leerá la configuración y no iniciará ningún servicio.

$SYSTEMD_GUILE

Si está configurado como `1` o `true`, habilita la integración con Guile Scheme.

$SYSTEMD_EDITOR

Especifica el editor a utilizar. Si no está configurado, se intentará determinar un editor apropiado automáticamente (usando `$EDITOR`, `$VISUAL` o internamente `nano`).

$SYSTEMD_PAGER y $PAGER

Si se respetan las variables $SYSTEMD_PAGER o $PAGER (que no sea para deshabilitar el paginador), $SYSTEMD_PAGERSECURE debe estar configurado también.

$SYSTEMD_COLORS

Toma un argumento booleano. Cuando es `true`, systemd y las utilidades relacionadas usarán colores en su salida, de lo contrario, la salida será monocromática. Adicionalmente, la variable puede tomar uno de los siguientes valores especiales: "16", "256" para restringir el uso de colores a los colores ANSI base 16 o 256, respectivamente. Esto puede especificarse para anular la decisión automática basada en $TERM y a qué está conectada la consola.

$SYSTEMD_URLIFY

El valor debe ser booleano. Controla si se deben generar enlaces interactivos en la salida para los emuladores de terminal que lo soporten. Esto puede especificarse para anular la decisión que systemd toma basada en $TERM y otras condiciones.

$LISTEN_PID, $LISTEN_FDS, $LISTEN_FDNAMES

Establecidas por systemd para procesos supervisados durante la activación basada en sockets. Consulte sd_listen_fds(3) para más información.

$NOTIFY_SOCKET

Establecida por el gestor de servicios para sus servicios para notificaciones de estado y preparación. También consumida por el gestor de servicios para notificar a los gestores de contenedores supervisores o gestores de servicios superiores sobre su propio progreso. Consulte sd_notify(3) y la sección relevante a continuación para más información.

Para más variables de entorno entendidas por systemd y sus diversos componentes, consulte Variables de Entorno Conocidas[7].

LÍNEA DE COMANDOS DEL KERNEL

Cuando se ejecuta como instancia del sistema, systemd analiza una serie de opciones que se enumeran a continuación. Pueden especificarse como argumentos de línea de comandos del kernel que se analizan a partir de una serie de fuentes dependiendo del entorno en el que se ejecute systemd. Si se ejecuta dentro de un contenedor Linux, estas opciones se analizan a partir de los argumentos de línea de comandos pasados al propio systemd, junto con cualquiera de las opciones de línea de comandos enumeradas en la sección Opciones anterior. Si se ejecuta fuera de contenedores Linux, estos argumentos se analizan a partir de /proc/cmdline en su lugar.

Las siguientes variables son entendidas:

systemd.unit=, rd.systemd.unit=

Anula la unidad a activar al arrancar. Por defecto es default.target. Esto puede usarse para arrancar temporalmente en una unidad de arranque diferente, por ejemplo, rescue.target o emergency.service. Consulte systemd.special(7) para obtener detalles sobre estas unidades. La opción prefijada con "rd." solo se tiene en cuenta en el initrd, mientras que la que no tiene prefijo solo en el sistema principal.

systemd.dump_core

Toma un argumento booleano o habilita la opción si se especifica sin argumento. Si está habilitado, el gestor systemd (PID 1) vuelca un core dump cuando falla. De lo contrario, no se crea ningún core dump. Por defecto está habilitado.

Añadido en la versión 233.

systemd.crash_chvt

Toma un entero positivo, o un argumento booleano. También se puede especificar sin argumento, con el mismo efecto que un booleano positivo. Si se especifica un entero positivo (en el rango 1-63), el gestor del sistema (PID 1) activará la terminal virtual especificada cuando falle. Por defecto está deshabilitado, lo que significa que no se intenta ningún cambio. Si se establece en `true`, se utiliza la terminal virtual a la que se escriben los mensajes del kernel en su lugar.

Añadido en la versión 233.

systemd.crash_shell

Toma un argumento booleano o habilita la opción si se especifica sin argumento. Si está habilitado, el gestor del sistema (PID 1) inicia un shell cuando falla. De lo contrario, no se inicia ningún shell. Por defecto está deshabilitado, por razones de seguridad, ya que el shell no está protegido por autenticación de contraseña.

Añadido en la versión 233.

systemd.crash_action=

Toma uno de "freeze", "reboot" o "poweroff". Por defecto es "freeze". Si se establece en "freeze", el sistema se colgará indefinidamente cuando falle el gestor del sistema (PID 1). Si se establece en "reboot", el gestor del sistema (PID 1) reiniciará la máquina automáticamente cuando falle, después de un retraso de 10 segundos. Si se establece en "poweroff", el gestor del sistema (PID 1) apagará la máquina inmediatamente cuando falle. Si se combina con systemd.crash_shell, la acción de fallo configurada se ejecuta después de que el shell salga.

Añadido en la versión 256.

systemd.confirm_spawn

Toma un argumento booleano o una ruta a la consola virtual donde se deben emitir los mensajes de confirmación. También se puede especificar sin argumento, con el mismo efecto que un booleano positivo. Si está habilitado, el gestor del sistema (PID 1) solicita confirmación al iniciar procesos usando /dev/console. Si se proporciona una ruta o un nombre de consola (como "ttyS0"), se utilizará la consola virtual apuntada por esta ruta o descrita por el nombre dado en su lugar. Por defecto está deshabilitado.

Añadido en la versión 233.

systemd.service_watchdogs=

Toma un argumento booleano. Si está deshabilitado, todos los watchdogs de tiempo de ejecución de servicios (WatchdogSec=) y las acciones de emergencia (por ejemplo, OnFailure= o StartLimitAction=) son ignorados por el gestor del sistema (PID 1); consulte systemd.service(5). Por defecto está habilitado, es decir, los watchdogs y las acciones de fallo se procesan normalmente. El watchdog de hardware no se ve afectado por esta opción.

Añadido en la versión 237.

systemd.show_status

Toma un argumento booleano o las constantes `error` y `auto`. También se puede especificar sin argumento, con el mismo efecto que un booleano positivo. Si está habilitado, el gestor systemd (PID 1) muestra actualizaciones de estado de servicio concisas en la consola durante el arranque. Con `error`, solo se muestran mensajes sobre fallos, pero el arranque es silencioso de lo contrario. `auto` se comporta como `false` hasta que hay un retraso significativo en el arranque. Por defecto está habilitado, a menos que se pase `quiet` como opción de línea de comandos del kernel, en cuyo caso por defecto es `error`. Si se especifica, anula la opción del archivo de configuración del gestor del sistema ShowStatus=, consulte systemd-system.conf(5).

Añadido en la versión 233.

systemd.status_unit_format=

Toma `name`, `description` o `combined` como valor. Si es `name`, el gestor del sistema usará nombres de unidad en los mensajes de estado. Si es `combined`, el gestor del sistema usará nombres de unidad y descripción en los mensajes de estado. Cuando se especifica, anula la opción del archivo de configuración del gestor del sistema StatusUnitFormat=, consulte systemd-system.conf(5).

Añadido en la versión 243.

systemd.log_color, systemd.log_level=, systemd.log_location, systemd.log_target=, systemd.log_time, systemd.log_tid, systemd.log_ratelimit_kmsg

Controla la salida de registro, con el mismo efecto que las variables de entorno $SYSTEMD_LOG_COLOR, $SYSTEMD_LOG_LEVEL, $SYSTEMD_LOG_LOCATION, $SYSTEMD_LOG_TARGET, $SYSTEMD_LOG_TIME, $SYSTEMD_LOG_TID y $SYSTEMD_LOG_RATELIMIT_KMSG descritas anteriormente. systemd.log_color, systemd.log_location, systemd.log_time, systemd.log_tid y systemd.log_ratelimit_kmsg pueden especificarse sin argumento, con el mismo efecto que un booleano positivo.

Controla la salida estándar y de error por defecto para servicios y sockets. Es decir, controla el valor por defecto de StandardOutput= y StandardError= (consulte systemd.exec(5) para detalles). Toma uno de `inherit`, `null`, `tty`, `journal`, `journal+console`, `kmsg`, `kmsg+console`. systemd.setenv=

Toma un argumento de cadena en el formato VARIABLE=VALOR. Puede usarse para establecer variables de entorno por defecto que se añadirán a los procesos hijos creados. Puede usarse varias veces para establecer múltiples variables.

systemd.machine_id=

Toma un valor hexadecimal de 32 caracteres para establecer el machine-id. Destinado principalmente a arranques de red donde se desea el mismo machine-id para cada arranque.

Establece una credencial del sistema, que luego puede propagarse a los servicios del sistema usando la configuración ImportCredential= o LoadCredential=, consulte systemd.exec(5) para detalles. OPCIONES DEL NÚCLEO DE ARRANQUE

Las siguientes opciones son entendidas por el administrador de servicios systemd (PID 1) y sus componentes relacionados, y pueden ser pasadas en la línea de comandos del kernel. Tenga en cuenta que muchas de ellas son para fines de compatibilidad con sistemas de inicio anteriores y pueden ser reemplazadas por los objetivos de systemd y sus correspondientes parámetros de línea de comandos.

init=/path/to/systemd

Inicia el administrador de servicios systemd como el primer proceso (PID 1). Si no se especifica, systemd intentará determinar la ruta correcta a sí mismo y la utilizará.

systemd.unit=UNIT

Inicia el sistema en el objetivo especificado UNIT en lugar del objetivo por defecto. El objetivo por defecto está determinado por el enlace simbólico /etc/systemd/system/default.target.

systemd.journal-upload=yes|no|host:port

Habilita o deshabilita la carga del journal a un servidor remoto. Si se establece en yes, la carga se habilitará con la configuración por defecto. Si se especifica un valor host:port, el journal se cargará en el servidor especificado.

systemd.log_color=always|auto|never

Controla si los mensajes del journal deben ser coloreados. always habilita el color siempre, auto habilita el color solo si la salida está conectada a una terminal, y never deshabilita el color.

systemd.log_level=emerg|alert|crit|err|warning|notice|info|debug

Establece el nivel mínimo de mensajes del journal que se registrarán.

systemd.log_target=default|null|console|kmsg|journal|wall

Establece el destino de los mensajes del journal. default usa la configuración por defecto, null descarta todos los mensajes, console los envía a la consola del kernel, kmsg los envía al buffer de mensajes del kernel, journal los envía al journal de systemd, y wall los envía a todos los usuarios conectados.

systemd.networkd=yes|no

Habilita o deshabilita el servicio systemd-networkd.

systemd.nvdimm=...

Opciones relacionadas con la inicialización de NVDIMMs. Consulte la documentación de pmem para más detalles.

systemd.preset-mode=enable|disable|only

Controla cómo se aplican los archivos preset. enable habilita las unidades especificadas, disable las deshabilita, y only deshabilita todas las unidades que no estén explícitamente habilitadas.

systemd.recoverable=yes|no

Indica si el sistema es recuperable después de un fallo.

systemd.service-watchdogs=yes|no

Habilita o deshabilita los perros guardianes de servicio.

systemd.show-environment=yes|no

Muestra las variables de entorno utilizadas por systemd.

systemd.sizegroups=yes|no

Habilita o deshabilita los grupos de tamaño para los recursos.

systemd.state_identity=...

Identidad del estado del sistema.

systemd.udev-auto-depth=yes|no

Habilita o deshabilita la profundidad automática de udev.

systemd.vconsole_fonts=...

Fuentes para la consola virtual.

systemd.watchdog-device=...

Dispositivo para el perro guardián.

debug-shell

Habilita un shell de depuración en el puerto serie.

emergency, -b

Arranca en modo de emergencia. Esto es equivalente a systemd.unit=emergency.target y se proporciona por razones de compatibilidad y para que sea más fácil de escribir.

hwclock=...

Configura el comportamiento del reloj de hardware.

init=/path/to/init

Similar a init=/path/to/systemd, pero especifica un binario init diferente.

kernel.log_level=...

Nivel de registro del kernel.

locale.accept.LANG=...

Establece el idioma y la configuración regional del sistema.

rd.shell

Arranca un shell en el entorno initramfs.

rd.shell.shell=...

Especifica el shell a utilizar en el entorno initramfs.

rd.skip.shell

Omite el arranque de un shell en el entorno initramfs.

rd.systemd.debug_shell=...

Habilita un shell de depuración en el entorno initramfs.

rd.systemd.install_units=...

Instala unidades en el entorno initramfs.

rd.systemd.machine_id=...

Establece el ID de máquina en el entorno initramfs.

rd.systemd.offset=...

Compensa el tiempo de inicio en el entorno initramfs.

rd.systemd.run...

Opciones relacionadas con la ejecución de systemd en el entorno initramfs.

rd.systemd.skip_ifxtures=...

Omite la carga de fijaciones en el entorno initramfs.

rd.systemd.unit=UNIT

Inicia el sistema en el objetivo especificado UNIT dentro del entorno initramfs.

rd.udev.disable_exec=...

Deshabilita la ejecución de programas por udev en el entorno initramfs.

rescue, rd.rescue, single, s, S, 1

Arranca en modo de rescate. Esto es equivalente a systemd.unit=rescue.target o rd.systemd.unit=rescue.target, respectivamente, y se proporciona por razones de compatibilidad y para que sea más fácil de escribir.

Para otros parámetros de línea de comandos del kernel entendidos por componentes del sistema operativo central, por favor consulte kernel-command-line(7).

CRED_ENCIALES DEL SISTEMA

Durante la inicialización, el administrador de servicios importará credenciales de varias fuentes al conjunto de credenciales del sistema, las cuales luego podrán propagarse a los servicios y ser consumidas por los generadores:

•Cuando el administrador de servicios se inicializa por primera vez, leerá las credenciales del sistema de las cadenas de proveedor SMBIOS Tipo 11 io.systemd.credential:name=value, y io.systemd.credential.binary:name=value.
•Al mismo tiempo, importará credenciales de la "fw_cfg" de QEMU. (Tenga en cuenta que el mecanismo SMBIOS es generalmente preferido, ya que es más rápido y genérico.)
•Las credenciales pueden pasarse a través de la línea de comandos del kernel, utilizando el parámetro systemd.set-credential=, ver arriba.
•Las credenciales pueden pasarse desde el entorno UEFI a través de systemd-stub(7).
•Cuando el administrador de servicios se invoca durante la transición initrd -> host, importará todos los archivos en /run/credentials/@initrd/ como credenciales del sistema.

Invoque systemd-creds(1) de la siguiente manera para ver la lista de credenciales pasadas al sistema:

# systemd-creds --system list

Para más información, consulte la documentación de Credenciales del Sistema y del Servicio[8].

El administrador de servicios, cuando se ejecuta como PID 1, consume las siguientes credenciales del sistema:

vmm.notify_socket

Contiene una dirección AF_VSOCK o AF_UNIX a la que enviar un mensaje de notificación READY=1 cuando el administrador de servicios haya completado el arranque. Consulte sd_notify(3) y la siguiente sección para más información. Tenga en cuenta que en caso de que el hipervisor no soporte SOCK_DGRAM sobre AF_VSOCK, se intentará SOCK_SEQPACKET en su lugar. La carga útil de la credencial para AF_VSOCK debe ser una cadena en el formato "vsock:CID:PORT". "vsock-stream", "vsock-dgram" y "vsock-seqpacket" pueden usarse en lugar de "vsock" para forzar el uso del tipo de socket correspondiente.

Esta característica es útil para administradores de máquinas u otros procesos en el host para recibir una notificación a través de VSOCK cuando una máquina virtual ha terminado de arrancar.

Añadido en la versión 254.

system.machine_id

Toma un ID hexadecimal de 128 bits para inicializar /etc/machine-id desde él, si el archivo no está configurado aún. Consulte machine-id(5) para más detalles.

Añadido en la versión 254.

Para una lista de credenciales del sistema que consumen varios otros componentes de systemd, consulte systemd.system-credentials(7).

PROTOCOLO DE LISTO

El administrador de servicios implementa un protocolo de notificación de disponibilidad tanto entre el administrador y sus servicios (es decir, hacia abajo en la pila), como entre el administrador y un posible supervisor más arriba en la pila (este último podría ser un administrador de máquinas o contenedores, o en el caso de un administrador de servicios por usuario, la instancia del administrador de servicios del sistema). El protocolo básico (y la API sugerida para él) se describe en sd_notify(3).

El socket de notificación que el administrador de servicios (incluido PID 1) utiliza para reportar la disponibilidad a su propio supervisor se establece a través de la variable de entorno habitual $NOTIFY_SOCKET (ver arriba). Dado que esto solo se puede establecer directamente para administradores de contenedores y para la instancia por usuario del administrador de servicios, hay un mecanismo adicional para configurarlo, especialmente destinado a su uso en entornos de VM: la credencial del sistema vmm.notify_socket (ver arriba) se puede establecer en un socket adecuado (típicamente uno AF_VSOCK) a través de cadenas de proveedor SMBIOS Tipo 11. Para más detalles, consulte arriba.

El protocolo de notificación desde el administrador de servicios hacia arriba, hacia un supervisor, admite una serie de campos de extensión que permiten a un supervisor conocer propiedades específicas del sistema y seguir el progreso del arranque. Específicamente, los siguientes campos se envían:

•Se enviará un mensaje X_SYSTEMD_HOSTNAME=... una vez que se haya determinado el nombre de host inicial del sistema. Tenga en cuenta que durante el tiempo de ejecución posterior, el nombre de host puede cambiarse de nuevo programáticamente y (actualmente) no se envían más notificaciones en ese caso.

Añadido en la versión 256.

•Se enviará un mensaje X_SYSTEMD_MACHINE_ID=... una vez que se haya determinado el ID de máquina del sistema. Consulte machine-id(5) para más detalles.

Añadido en la versión 256.

•Se enviará un mensaje X_SYSTEMD_SIGNALS_LEVEL=... una vez que el administrador de servicios haya instalado los diversos manejadores de señales de procesos UNIX descritos anteriormente. El valor del campo es un entero sin signo formateado como una cadena decimal, e indica el nivel de característica del administrador de servicios para señales de procesos UNIX soportadas. Actualmente, solo se define un nivel de característica:
•X_SYSTEMD_SIGNALS_LEVEL=2 cubre las diversas señales de procesos UNIX documentadas anteriormente, que son un superconjunto de las soportadas por el sistema de inicio SysV histórico.

Las señales enviadas a PID 1 antes de que se envíe este mensaje podrían no ser manejadas correctamente todavía. Un consumidor de estos mensajes debe analizar el valor como un entero sin signo que indica el nivel de soporte. Por ahora, solo se define el nivel 2 mencionado, pero más adelante podrían definirse niveles adicionales con enteros más altos, que implementarán un superconjunto del comportamiento definido actualmente.

Añadido en la versión 256.

•Se enviarán mensajes X_SYSTEMD_UNIT_ACTIVE=... y X_SYSTEMD_UNIT_INACTIVE=... para cada unidad de destino a medida que se activa o deja de estar activa. Esto es útil para seguir el progreso y la funcionalidad del arranque. Por ejemplo, una vez que la unidad ssh-access.target se reporta iniciada, el acceso SSH suele estar disponible, consulte systemd.special(7) para más detalles.

Añadido en la versión 256.

•Se enviará un mensaje X_SYSTEMD_SHUTDOWN=... muy poco antes de que el sistema se apague. El valor es una de las cadenas "reboot", "halt", "poweroff", "kexec" e indica qué tipo de apagado se está ejecutando.

Añadido en la versión 256.

•También se enviará un mensaje X_SYSTEMD_REBOOT_PARAMETER=... muy poco antes de que el sistema se apague. Su valor es el argumento de reinicio tal como se configuró con systemctl --reboot-argument=....

Añadido en la versión 256.

Tenga en cuenta que estos campos de extensión se envían además de las notificaciones regulares "READY=1" y "RELOADING=1".

SYSTEM CLOCK EPOCH

When systemd is started or restarted, it may set the system clock to the "epoch". This mechanism is used to ensure that the system clock remains somewhat reasonably initialized and roughly monotonic across reboots, in case no battery-backed local RTC is available or it does not work correctly.

The epoch is the lowest date above which the system clock time is assumed to be set correctly. When initializing, the local clock is advanced to the epoch if it was set to a lower value. As a special case, if the local clock is sufficiently far in the future (by default 15 years, but this can be configured at build time), the hardware clock is assumed to be broken, and the system clock is rewound to the epoch.

The epoch is set to the highest of: the build time of systemd, the modification time ("mtime") of /usr/lib/clock-epoch, and the modification time of /var/lib/systemd/timesync/clock.

FILES

/run/systemd/notify

Daemon status notification socket. This is an AF_UNIX datagram socket and is used to implement the daemon notification logic as implemented by sd_notify(3).

/run/systemd/private

Used internally as communication channel between systemctl(1) and the systemd process. This is an AF_UNIX stream socket. This interface is private to systemd and should not be used in external projects.

/usr/lib/clock-epoch

The modification time ("mtime") of this file is used for the time epoch, see previous section.

Added in version 247.

/var/lib/systemd/timesync/clock

The modification time ("mtime") of this file is updated by systemd-timesyncd.service(8). If present, the modification time of file is used for the epoch, see previous section.

Added in version 257.
