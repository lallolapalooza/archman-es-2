IUCODE_TOOL(8) Manual de iucode_tool IUCODE_TOOL(8)

NOMBRE

iucode_tool - Herramienta para manipular paquetes de microcódigo Intel® IA-32/X86-64

SINOPSIS

iucode_tool [opciones] [[-ttipo] nombre_archivo|nombre_directorio] ...

DESCRIPCIÓN

iucode_tool es una utilidad que puede cargar datos de microcódigo de procesadores Intel® desde archivos en formatos de paquete de microcódigo, tanto en texto como en binario.

Puede mostrar una lista de los microcódigos en estos archivos, fusionarlos, cargarlos en el kernel (para actualizar el microcódigo en los núcleos del procesador del sistema) o escribir algunos de ellos en un archivo en formato binario para su uso posterior.

iucode_tool cargará todos los microcódigos de los archivos y directorios especificados en memoria, para poder procesarlos. Los microcódigos duplicados y obsoletos serán descartados. Puede leer datos de microcódigo desde la entrada estándar (stdin), especificando el nombre de archivo “-” (signo menos).

Se asume que los archivos de datos de microcódigo están en formato de texto .dat si tienen una extensión .dat, y en formato binario de lo contrario. Se asume que la entrada estándar (stdin) está en formato de texto .dat. La opción -t se puede usar para cambiar el tipo de los archivos especificados después de ella, incluyendo stdin.

Si se especifica un directorio, se cargarán todos los archivos cuyos nombres no comiencen con un punto, en orden no especificado. Los directorios anidados se omiten.

Los archivos y directorios vacíos se ignoran y se omiten.

Puede seleccionar qué microcódigos deben escribirse, listarse o cargarse en el kernel usando las opciones -S, -s, --date-before y --date-after. Si no se especifica ninguna de estas opciones, se seleccionarán todos los microcódigos.

Puede cargar los microcódigos seleccionados en el kernel, escribirlos en un archivo (en formato binario), en un archivo initramfs temprano de Linux, en archivos por firma de procesador en un directorio, o en archivos por microcódigo en un directorio usando las opciones -w, --write-earlyfw, -k, -K y -W.

iucode_tool identificará los microcódigos en sus mensajes de salida y error usando una notación “n/k”, donde “n” es el número de paquete y “k” es el número de microcódigo dentro de ese paquete. La salida de la opción --list-all al procesar múltiples archivos de entrada es el mejor ejemplo de cómo funciona.

Para más información sobre los microcódigos de procesadores Intel, por favor, lea la documentación incluida y los manuales de Intel listados en la sección VER TAMBIÉN.

OPCIONES

iucode_tool acepta las siguientes opciones:

-q, --quiet
Inhibir la salida habitual.
-v, --verbose
Imprimir más información. Usar más de una vez para mayor verbosidad.
-h, -?, --help
Listar todas las opciones disponibles y sus significados.
--usage
Mostrar resumen de opciones.
-V, --version
Mostrar la versión del programa.
-t tipo
Establece el tipo de archivo de los siguientes archivos. tipo puede ser:
b
formato binario. Este es el mismo formato utilizado por el driver del kernel y la BIOS/EFI, que se describe en detalle en el Manual del Desarrollador de Software de Arquitecturas Intel 64 e IA-32, Volumen 3A, sección 9.11.
d
formato de texto .dat de microcódigo Intel. Este es el formato que Intel usa normalmente para distribuir archivos de datos de microcódigo.
r
recuperar microcódigo en formato binario. Busca archivos binarios genéricos sin comprimir para obtener microcódigos en formato binario de microcódigo Intel. Nota: Puede encontrar microcódigo que no pase verificaciones estrictas, y por lo tanto hacer que iucode_tool salga si las opciones --no-strict-checks o --ignore-broken no están en efecto.
a
(por defecto) iucode_tool usará la extensión del nombre de archivo para seleccionar el tipo de archivo: formato de texto .dat para archivos que tienen la extensión .dat, y tipo binario en caso contrario. Tenga en cuenta que para stdin, se asume formato de texto .dat.
--downgrade
Cuando se dispone de varias versiones del microcódigo para un procesador específico de diferentes archivos, se mantiene la del archivo cargado últimamente, independientemente de los niveles de revisión. Los archivos siempre se cargan en el orden en que se especificaron en la línea de comandos. Esta opción no tiene efecto cuando solo se ha cargado un archivo.
--no-downgrade
Cuando se dispone de varias versiones del microcódigo para un procesador específico de diferentes archivos, se mantiene la con el nivel de revisión más alto. Este es el modo de operación por defecto.
--strict-checks
Realiza verificaciones estrictas en los datos del microcódigo. Se negará a cargar microcódigos y archivos de datos de microcódigo con tamaño y metadatos inesperados. También se negará a cargar entradas de microcódigo que tengan los mismos metadatos, pero diferente carga útil. Este es el modo de operación por defecto.
--no-strict-checks
Realiza verificaciones menos estrictas en los datos del microcódigo. Úselo solo si se encuentra con un archivo de datos de microcódigo que tiene microcódigos con tamaños extraños o metadatos no críticos incorrectos (como fechas inválidas), que desea conservar. Si solo desea omitir esos, use la opción --ignore-broken.
--ignore-broken
Omite las entradas de microcódigo rotas al cargar un archivo de datos de microcódigo, en lugar de abortar la ejecución del programa. Si la entrada de microcódigo tiene un formato no soportado o su cabecera estaba severamente corrupta, todos los datos restantes en el archivo tendrán que ser ignorados. En ese caso, se recomienda usar un tipo de archivo de recuperar microcódigo en formato binario (opción -tr), ya que puede omitir datos de microcódigo mal manipulados.
--no-ignore-broken
Aborta la ejecución del programa si se encuentra un microcódigo roto al cargar un archivo de datos de microcódigo. Este es el modo de operación por defecto.
-s ! | [!]firma[,[pf_mask][,[lt:|eq:|gt:]revision]]
Selecciona microcódigos por la firma, máscara de flags del procesador (pf_mask) y revisión especificadas.

Si se especifica la máscara de flags del procesador, seleccionará solo microcódigos que sean adecuados para al menos una de las combinaciones de flags del procesador presentes en la máscara.

Si se especifica la revisión, opcionalmente prefijada por uno de los operadores “eq:”, “lt:” o “gt:”, seleccionará solo microcódigos que tengan esa misma revisión (si no hay operador, o si se usa el operador “eq:”), o microcódigos que tengan una revisión menor que (operador “lt:”), o mayor que (operador “gt:”), la especificada.

Especifique más de una vez para seleccionar más microcódigos. Esta opción se puede combinar con la opción --scan-system para seleccionar más microcódigos. Si firma está prefijada por un signo de exclamación (“!”), deseleccionará microcódigos en su lugar. El orden importa, con las opciones -s posteriores anulando a las anteriores, incluyendo --scan-system.

Al especificar firma y pf_mask, los números hexadecimales deben ir prefijados con “0x”, y los números octales con “0”. Los números decimales no deben tener ceros iniciales, de lo contrario se interpretarían como números octales.

La notación especial -s! (sin parámetro signature) instruye a iucode_tool a requerir la inclusión explícita de firmas de microcódigo (usando la forma no negada de -s, o us

ing --scan-system).

-S, --scan-system[=mode]
Selecciona microcódigos escaneando los procesadores en línea de este sistema en busca de sus firmas.

Esta opción solo se puede usar una vez y se puede combinar con la opción -s para seleccionar más microcódigos. Los microcódigos seleccionados por --scan-system también se pueden deseleccionar con una opción posterior -s !signature.

El argumento opcional mode (aceptado solo por la versión larga de la opción) selecciona la estrategia utilizada para escanear procesadores:

0 o auto
Actualmente, lo mismo que fast, pero esto podría cambiar en futuras versiones si Intel alguna vez implementa sistemas de múltiples firmas que vayan más allá de los "steppings" mixtos. Este es el modo de operación predeterminado, para compatibilidad con versiones anteriores de iucode_tool.
1 o fast
Utiliza la instrucción cpuid para detectar la firma del procesador en el que se está ejecutando iucode_tool, y selecciona todos los "steppings" para el tipo, familia y modelo de ese procesador. Admite sistemas de "stepping" mixtos.
2 o exact
Utiliza controladores del kernel para escanear directamente la firma de cada procesador en línea. Este modo admite sistemas de múltiples firmas. Este modo de escaneo será lento en sistemas grandes con muchos procesadores, y probablemente requerirá permisos especiales (como ejecutarse como usuario root). Si el escaneo falla por algún motivo, como medida de seguridad, emitirá una advertencia y considerará todos los "steppings" posibles para cada firma que logró escanear con éxito.
--date-before=YYYY-MM-DD y --date-after=YYYY-MM-DD
Limita los microcódigos seleccionados por un rango de fechas. La fecha debe proporcionarse en formato ISO, con cuatro dígitos para el año y dos dígitos para el mes y el día, y el signo “-” (guion) como separador. Las fechas no se validan en rango, por lo que puedes usar --date-after=2000-00-00 para seleccionar todos los microcódigos con fecha posterior al 1 de enero de 2000.
--loose-date-filtering
Cuando se especifica un rango de fechas, se considerarán todas las revisiones del microcódigo para su selección (ignorando solo el rango de fechas, todos los demás filtros siguen aplicándose) si alguna de las revisiones del microcódigo se encuentra dentro del rango de fechas.
--strict-date-filtering
Cuando se especifica un rango de fechas, selecciona solo los microcódigos que se encuentran dentro del rango de fechas. Este es el modo de operación predeterminado.
-l, --list
Lista las firmas de microcódigo seleccionadas en la salida estándar (stdout).
-L, --list-all
Lista todas las firmas de microcódigo mientras se procesan en la salida estándar (stdout).
-k[device], --kernel[=device]
Carga los microcódigos seleccionados en el kernel. Opcionalmente, se puede especificar la ruta del dispositivo (predeterminado: /dev/cpu/microcode). Este método de actualización está obsoleto: eventualmente se eliminará del kernel y de iucode_tool.
-K[directory], --write-firmware[=directory]
Escribe los microcódigos seleccionados con los nombres de archivo esperados por el cargador de firmware del kernel de Linux. Opcionalmente, se puede especificar el directorio de destino (predeterminado: /lib/firmware/intel‐ucode).
-wfile, --write-to=file
Escribe los microcódigos seleccionados en un archivo en formato binario.
--write-earlyfw=file
Escribe los microcódigos seleccionados en un archivo de arranque temprano (initramfs), que debe anteponerse al initramfs regular para permitir que el kernel actualice el microcódigo del procesador muy temprano durante el arranque del sistema.
-Wdirectory, --write-named-to=directory
Escribe los microcódigos seleccionados en el directorio especificado, un microcódigo por archivo, en formato binario. Los nombres de archivo reflejan la firma del microcódigo, la máscara de banderas del procesador y la revisión.
--write-all-named-to=directory
Escribe cada microcódigo en el directorio especificado, un microcódigo por archivo, en formato binario. Los nombres de archivo reflejan la firma del microcódigo, la máscara de banderas del procesador y la revisión. Esta es la única forma de escribir todas las revisiones del mismo microcódigo.
--overwrite
Elimina el archivo de destino antes de escribir, si existe y no es un directorio. El archivo de destino no se sobrescribe en el lugar. Los enlaces físicos se romperán, y cualquier permiso de acceso existente, ACLs y otros atributos extendidos del archivo de destino antiguo se perderán.
--no-overwrite
Aborta si el archivo de destino ya existe. Este es el modo de operación predeterminado. Tenga en cuenta que iucode_tool no sigue los enlaces simbólicos que no son directorios al escribir archivos.
--mini-earlyfw
Optimiza el contenedor cpio del initramfs temprano para un tamaño mínimo. Cambiará el tamaño del bloque cpio a 16 bytes y eliminará las entradas de encabezado de los directorios padre del archivo de datos del microcódigo. Como resultado, el archivo de datos del microcódigo no estará disponible para el initramfs regular, y las herramientas podrían quejarse del tamaño de bloque cpio no estándar.

Esto generalmente reducirá el tamaño del initramfs temprano en 736 bytes.

--normal-earlyfw
Optimiza el tamaño del initramfs temprano para la compatibilidad con herramientas. Este es el modo de operación predeterminado. El archivo de datos del microcódigo también estará disponible dentro del initramfs regular.

NOTAS

iucode_tool lee todos los datos a memoria antes de realizar cualquier procesamiento. Aplica un límite de seguridad de un máximo de 1 Gib de datos de microcódigo binario por archivo de datos de microcódigo.

Todos los mensajes informativos y de error se envían a la salida de error estándar (stderr), mientras que la salida solicitada por el usuario (como la salida generada por las opciones de listado) se envía a la salida estándar (stdout).

iucode_tool crea archivos con permisos 0644 (rw-r--r--), modificados por la umask actual.

La lista de microcódigos seleccionados y los archivos de salida de microcódigo de iucode_tool se ordenan primero por firma del procesador (en orden ascendente) y luego por máscara de banderas del procesador (en orden descendente).

Cuando se seleccionan múltiples revisiones de un microcódigo, las anteriores se omitirán. Solo la revisión seleccionada más reciente de un microcódigo (o la última en orden de carga cuando la opción --downgrade está activa) se escribirá en un archivo o se cargará en el kernel.

Los archivos de datos de microcódigo de Intel, tanto en formato binario como de texto, se pueden concatenar para generar un archivo de datos de microcódigo más grande y aún válido.

iucode_tool no sigue enlaces simbólicos al escribir archivos de datos de microcódigo. Se negará a escribir el archivo y abortará (modo de operación predeterminado) o (cuando la opción --overwrite está activa) eliminará el enlace simbólico o archivo de destino (y por lo tanto romperá enlaces físicos) *antes* de escribir el nuevo archivo.

iucode_tool sí sigue los enlaces simbólicos de directorios para localizar el directorio donde escribir los archivos.

Notas de Linux

Antes de Linux v4.4, el controlador de actualización de microcódigo se dividía en dos partes: el controlador de actualización de microcódigo temprano (que obtiene los datos del microcódigo del initramfs) y el controlador de actualización de microcódigo tardío, que podía ser un módulo y obtenía los datos del microcódigo del subsistema de firmware. Los dos controladores se unificaron en Linux v4.4.

El controlador de actualización de microcódigo necesita estar presente en el sistema en todo momento para garantizar que las actualizaciones de microcódigo se reapliquen al reanudar desde la suspensión y en el hotplug de CPU. No descargue el módulo de microcódigo, a menos que sepa lo que está haciendo. Desde Linux v4.4, el controlador de microcódigo tardío ya no puede ser un módulo y siempre estará presente en el sistema cuando esté habilitado.

Actualizar el microcódigo temprano es más seguro. Solo se puede hacer al arrancar y requiere un initramfs, pero se recomienda encarecidamente: las actualizaciones de microcódigo tardías (que leen datos de microcódigo de /lib/firmware) no pueden cambiar de forma segura las características visibles del procesador.

Las actualizaciones tempranas de microcódigo están disponibles desde Linux v3.9. Pueden cambiar de forma segura las características visibles del procesador (como las actualizaciones de microcódigo que deshabilitaron las instrucciones TSX de Intel en los núcleos Haswell de Intel). Requieren una imagen initramfs sin comprimir con los datos de actualización de microcódigo en /kernel/x86/microcode/GenuineIntel.bin. Esta imagen initramfs sin comprimir debe venir antes de cualquier imagen initramfs comprimida y tiene un nombre especial: early initramfs.

Los datos de actualización de microcódigo dentro de la imagen initramfs temprana deben estar alineados a un límite de 16 bytes debido a un error en varias versiones del controlador de actualización de microcódigo temprano del kernel de Linux. Esto requiere pasos especiales al crear el archivo initramfs con los datos del microcódigo, y será manejado automáticamente por la opción --write-earlyfw de iucode_tool.

Desde Linux v4.2, también es posible compilar un kernel con los datos de actualización de microcódigo como firmware incorporado, utilizando las instalaciones de CONFIG_FIRMWARE_IN_KERNEL. Esta característica aún no es madura en las versiones Linux v4.2.8, v4.4.11, v4.5.5 y v4.6, y podría no funcionar en todos los casos.

La interfaz de actualización /dev/cpu/microcode ha sido declarada obsoleta y no debe usarse. Tiene un requisito especial: cada llamada al sistema de escritura debe contener microcódigos completos. Se puede acceder a ella a través de iucode_tool --kernel.

Hasta Linux v3.5, las actualizaciones de microcódigo tardías debían activarse por núcleo, escribiendo el número 1 en /sys/devices/system/cpu/*/microcode/reload para cada cpu. Dependiendo de la versión del kernel, debe activarla en cada núcleo para evitar una situación peligrosa donde algunos núcleos usan microcódigo desactualizado, o el kernel aceptará la solicitud solo para el procesador de arranque y la usará para activar una actualización en todos los núcleos del sistema.

Desde Linux v3.6, el controlador de actualización de microcódigo tardío tiene una nueva interfaz que activa explícitamente una actualización para cada núcleo a la vez cuando se escribe el número 1 en /sys/devices/system/cpu/microcode/reload.
