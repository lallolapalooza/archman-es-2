DESCRIPCIÓ

N

Aunque los módulos ya están disponibles desde hace bastante tiempo, el compilador gnu g++ todavía muestra una serie de errores relacionados con los módulos de C++ (cf. https://gcc.gnu.org/bugzilla/show_bug.cgi?id=103524). Así que es posible que al usar módulos te encuentres con algunos de estos (o nuevos) errores. Los errores probablemente se habrán corregido en futuras versiones del compilador, y el estado actual de las cosas al menos te permite ganar algo de experiencia en el uso de

módulos.

Los módulos no pueden importarse mutuamente. En consecuencia siempre hay una jerarquía de módulos lineal, no circular, lo que debe tenerse en cuenta al compilar archivos que definen y usan módulos. El programa icmodmap determina este orden y prepara la construcción de los módulos usados por los

programas.

Icmodmap asume que los módulos están definidos en subdirectorios separados, y que las interfaces de los módulos están definidas en (por defecto) archivos llamados module.cc. Si un programa define dos módulos First y Second (p. ej., en los subdirectorios first y second y el second/module.cc importa el módulo First entonces first/module.cc debe compilarse antes de compilar second/module.cc. Esto es manejado por icmodmap. Una vez que los archivos module.cc han sido compilados, los archivos fuente restantes del programa pueden compilarse como de

costumbre.

Icmodmap espera que los proyectos que usan módulos estén organizados de la siguiente

manera:
o
El directorio de nivel superior del proyecto contiene un archivo CLASSES, donde cada línea (ignorando los comentarios enC++) especifica el nombre de un subdirectorio que implementa uno de los componentes del proyecto. Alternativamente, se puede especificar un (subconjunto de) los subdirectorios del directorio. Cada subdirectorio puede definir un módulo, una partición de módulo, una clase (no parte de un módulo, pero que puede usar módulos), o funciones de nivel global (también que pueden usar módulos)
;
o
Si el proyecto define un programa, el directorio de nivel superior del proyecto contiene archivos fuente (como main.cc) que definen la función main. El directorio de nivel superior no define un módulo, pero sus fuentes pueden usar
módulos;
o
Los subdirectorios que definen módulos o particiones contienen por defecto un archivo module.cc, que define el nombre del módulo y su interfaz (en lugar de module.cc se puede especificar otro nombre de archivo)
;
o
Los módulos y las particiones pueden definir clases (una clase por mód
ulo, una clase por partición). Si es así, las funciones miembro de es
as clases se definen en el subdirectorio del módulo o de la partición.

Icmodmap(1) inspecciona cada subdirectorio especificado. Si contiene el archivo module.cc (o su nombre alternativo), entonces ese archivo (que tiene la siguiente estructura) es

inspeccionado:
o
su primera línea no vacía: define el nombre del módulo o de la
partición;
o
las líneas de import pueden especif
icar cabeceras de
l sistema, módulos
y/o particiones.

OPCIONE

S

Icmodmap soporta las siguientes

opciones:
o
--colors (-c)
por defecto el compilador es llamado usando la opción -fdiagnostics-color=never. Usa esta opción para suprimir esta
opción;
o
--dependencies (-d)
las dependencias entre módulos se muestran usando esta opción. Los archivos fuente que definen módulos no se compilan. La salida de icmodmap puede verse así: 
    Square:l
    DepSquare: Square
aquí, el sufijo :l indica que Square es un módulo definido por el proyecto, que no depende de otros módulos. Cuando las definiciones de módulos sí dependen de otros módulos, se listan a continuación: DepSquare es otro módulo definido por el proyecto, que depende del módulo
Square.
También es posible que los módulos dependan de módulos definidos por otros proyectos. En ese caso la salida puede verse así: 
    Square:e
    Mod1: Square:e
    Mod2: Square:e Mod1 
    Mod3: Square:e Mod1  Mod2
En este ejemplo el módulo Square es un módulo externo, indicado por el sufijo :e. Todos los demás módulos dependen de Square, y (p. ej.) Mod3 también depende de los módulos definidos localmente Mod1 y Mod2. En este último ejemplo el archivo Square.gcm debe estar disponible en el directorio gcm.cache del proyecto (podría ser un enlace simbólico al archivo real)
;
o
--help (-h)
Proporciona información de uso, devolviendo 0 al sistema
operativo;
o
--module=archivo (-m)
Por defecto los módulos se definen en los archivos fuente module.cc. Si los módulos están definidos en archivos fuente con otros nombres, entonces esos nombres se pueden especificar usando esta opción. P. ej., cuando los módulos están definidos en archivos interface.cc, entonces especifica la opción --module interface.cc. No se soporta el uso de archivos de definición de módulos con nombres
diferentes;
o
--subdir (-s)
Por defecto los archivos compilados que definen módulos se encuentran en el subdirectorio tmp/o del proyecto, donde cada archivo compilado ha recibido un prefijo con el número de orden de compilación (p. ej., tmp/o/1module.o, tmp/o/2module.o, ...). Al especificar la opción --subdir los archivos compilados se encuentran en el mismo subdirectorio que los archivos que definen los módulos (sin usar el prefijo del número de orden)
;
o
--version (-v)
Muestra la versión de
icmodmap.
o
--verbose (-V)
Muestra salida adicional al determ
inar el orden de compilación de
los módulos y al compilar los
archivos de definición de módulos.

EJEMPL

O

El siguiente programa define un módulo Square en su subdirectorio square, que contiene este archivo module.

cc: 
export module Square;
export
{
    double square(double value);
    class Square
    {
        double d_amount;
        public:
            Square(double amount = 0);          // initialize
            void amount(double value);          // change d_amount
            double amount() const;              // return d_amount
            double lastSquared() const;         // returns g_squared
            double square() const;              // returns sqr(d_amount)
    };
}
double
g_squared;

La función main importa el módulo Square y usa sus instalaciones. También importa la cabecera del sistema compilada como módulo iostream. Esa cabecera no es inspeccionada por icmodmap, y debe estar disponible antes de que el archivo main.cc pueda ser compilado. Aquí está el archivo fuente main.

cc: 
import Square;
import <iostream>;
int main(int argc, char **argv)
{
    std::cout << "the square of " << argc << " is " 
                                        << square(argc) << ’\n’;
    Square obj{12};
    std::cout << "the square of 12 is " << obj.square() << "\n"
                "the last computed square is " << 
                obj.lastSquared() << ’\n’;
}

Ejecutando icmodmap -d . muestra Square como un módulo

local: 
    Square:
l

Ejecutando icmodmap -V . muestra la compilación de square/modu

le.cc: 
    Module: Square
    square:
    /bin/g++ --std=c++26 -fdiagnostics-color=never  -c -fmodules-ts 
            -Wall -o ../tmp/o/1module.o module.
cc

También define el subdirectorio gcm.cache, que contiene Square.gcm y un enlace simbólico usr -> /usr, y debido a este enlace simbólico el compilador

DESCRIPCIÓN

Encuentra los archivos de cabecera del sistema compilados por módulos. También define el enlace simbólico square/gcm.cache -> ../gcm.cache: esos enlaces simbólicos se definen en todos los subdirectorios utilizados por el programa, permitiendo que todos los archivos fuente en todos los subdirectorios del programa importen todos los módulos definidos en el directorio gcm.cache del directorio principal.
