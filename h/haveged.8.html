DESCRIPCIÓ

N

haveged genera un flujo impredecible de números aleatorios recolectados de los efectos indirectos de los eventos de hardware en el estado oculto del procesador (cachés, predictores de ramificación, tablas de traducción de memoria, etc.) usando el algoritmo HAVEGE (HArdware Volatile Entropy Gathering and Expansion). El algoritmo opera en el espacio de usuario, no se requiere ningún privilegio especial para el acceso al sistema de archivos al flujo de

salida.

Linux acumula aleatoriedad para su distribución a través de las interfaces de dispositivo /dev/random y /dev/urandom. Los mecanismos estándar para llenar el pool de /dev/random pueden no ser suficientes para satisfacer la demanda en sistemas con altas necesidades o interacción de usuario limitada. En esas circunstancias, haveged puede ejecutarse como un demonio privilegiado para llenar el pool de /dev/random siempre que el suministro de bits aleatorios en /dev/random caiga por debajo del nivel de agua baja del

dispositivo.

haveged se ajusta a su entorno y proporciona la misma suite de pruebas integrada para el flujo de salida que se usa en dispositivos de seguridad de hardware certificados. Vea NOTAS más abajo pa

ra más inf

Especifica las pruebas en línea que se ejecutarán. El <spec> consiste en grupos opcionales "t"ot y "c"ontinuous, cada grupo indica los procedimientos a ejecutar, usando "a<n>" para indicar una variante A del procedimiento AIS-31 y "b" para indicar el procedimiento B de AIS. Las especificaciones son independientes del orden (el procedimiento B siempre se ejecuta primero en cada grupo) e insensibles a mayúsculas y minúsculas. Las variaciones a<n> existen para mitigar una prueba lenta de autocorrelación (test5). Normalmente, todas las pruebas del procedimiento A, excepto la primera, se repiten 257 veces. Una opción a<n> indica que test5 solo debe ejecutarse cada módulo <n> veces durante las 257 repeticiones del procedimiento. El efecto es tan notable que A8 es la elección habitual.

Las pruebas "tot" se ejecutan solo en la inicialización - no hay consecuencias negativas de rendimiento excepto por un ligero aumento en el tiempo requerido para inicializar. Las pruebas "tot" garantizan que haveged se ha inicializado correctamente. El uso de ambos procedimientos de prueba en la prueba "tot" es altamente recomendable porque las dos pruebas enfatizan diferentes aspectos de la calidad del

RNG.

En la prueba continua, la secuencia de pruebas se cicla repetidamente. Por ejemplo, la cadena "tbca8b" (apropiada para un dispositivo AIS NTG.1) ejecutaría el procedimiento B para la prueba "tot", luego ciclaría entre el procedimiento A8 y el procedimiento B continuamente para toda la salida posterior. La prueba continua no es gratuita, afectando tanto el rendimiento como el consumo de recursos. La prueba continua también abre la posibilidad de un fallo en la prueba. Un procedimiento estricto de reintento se recupera de fallos espurios en todos los casos excepto en las circunstancias más extremas. Cuando el reintento falla, la operación terminará a menos que se haya añadido una "w" al token de prueba para hacer que la prueba sea solo consultiva. En nuestro ejemplo anterior, la cadena "tbca8wbw" haría que todas las pruebas continuas fueran consultivas. Para información más detallada sobre los reintentos de AIS, vea NOTAS más

abajo.

NOTA

S

haveged ajusta el algoritmo HAVEGE para una efectividad máxima usando una jerarquía de valores predeterminados, opciones de línea de comandos, información del sistema de archivos virtual y información de cpuid cuando esté disponible. En la mayoría de las circunstancias, no se requiere entrada del usuario para obtener excelentes

resultados.

Las pruebas en tiempo de ejecución proporcionan garantía del correcto funcionamiento de haveged. La suite de pruebas en tiempo de ejecución se basa en la especificación AIS-31 del organismo alemán de Criterios Comunes, BIS. Esta especificación se aplica típicamente a dispositivos de hardware, requiriendo certificación formal y pruebas de inicio y operación continuas obligatorias. Debido a que haveged se ejecuta en muchas plataformas de hardware diferentes, la certificación no puede ser un objetivo, pero la suite de pruebas AIS-31 proporciona los medios para evaluar la salida de haveged con las mismas pruebas operativas aplicadas a dispositivos de hardware

certificados.

El procedimiento de prueba A de AIS realiza 6 pruebas para verificar un comportamiento estadísticamente inconspicuo. El procedimiento de prueba B de AIS realiza más pruebas teóricas como verificar probabilidades de transición multi-paso y hacer una estimación empírica de entropía. El procedimiento A es mucho más intensivo en recursos y cómputo de los dos, pero aún se recomienda para las pruebas de inicio de haveged. El procedimiento B es adecuado para el uso de haveged como demonio porque la estimación de entropía de la prueba confirma la estimación de entropía que haveged usa al añadir entropía al

dispositivo

/dev/random. Ninguna prueba es perfecta. Existe una probabilidad de 10e-4 de que un generador perfecto falle cualquiera de los procedimientos de prueba. AIS-31 exige una política de reintentos estricta para filtrar las falsas alarmas y haveged siempre registr
