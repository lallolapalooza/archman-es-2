ERRORE

S

El procedimiento ::http::geturl lanzará errores en los siguientes casos: opciones de línea de comando inválidas, una URL inválida, una URL en un host inexistente, o una URL en un puerto incorrecto en un host existente. Estos errores significan que ni siquiera puede comenzar la transacción de red. También lanzará un error si obtiene un error de E/S mientras escribe el encabezado de solicitud HTTP. Para llamadas ::http::geturl síncronas (donde -command no está especificado), lanzará un error si obtiene un error de E/S mientras lee los encabezados de respuesta HTTP o los datos. Debido a que ::http::geturl no retorna un token en estos casos, hace toda la limpieza requerida y no hay problema de que su aplicación tenga que llamar a ::http::cle

anup.

Para llamadas ::http::geturl asíncronas, todas las situaciones de error anteriores se aplican, excepto que si hay algún error mientras lee los encabezados de respuesta HTTP o los datos, no se lanza ninguna excepción. Esto se debe a que después de escribir los encabezados HTTP, ::http::geturl retorna, y el resto de la transacción HTTP ocurre en segundo plano. El callback del comando puede verificar si ocurrió algún error durante la lectura llamando a ::http::status para verificar el estado y si su error, llamando a ::http::error para obtener el mensaje de

error.

Alternativamente, si el flujo principal del programa llega a un punto donde necesita saber el resultado de la solicitud HTTP asíncrona, puede llamar a ::http::wait y luego verificar el estado y el error, igual que lo hace el

callback.

El comando ::http::geturl ejecuta los -command, -handler, y -proxyfilter callbacks dentro de un catch command. Por lo tanto un error en el comando callback no llama al manejador bgerror. Al depurar uno de estos callbacks, puede ser conveniente reportar errores usando un comando catch dentro del comando callback mismo, ej. para escribir un mensaje de error en

stdout.

En cualquier caso, usted aún debe llamar a ::http::cleanup para eliminar el arreglo de estado cuando haya

terminado.

Una

conexión persistente permite que múltiples transacciones HTTP/1.1 se realicen sobre la misma conexión TCP. El *pipelining* permite a un cliente hacer múltiples solicitudes sobre una conexión persistente sin esperar cada respuesta. El servidor envía las respuestas en el mismo orden en que las solicitudes

fueron

recibidas. Si una solicitud POST falla al completarse, típicamente se necesita la confirmación del usuario antes de enviar la solicitud de nuevo. El usuario puede desear verificar si el servidor fue modificado por la solicitud POST

fallida,

antes de enviar la misma solicitud de nuevo. Una solicitud HTTP usará un socket persistente si la llamada a http::geturl tiene la opción -keepalive true. Usará *pipelining* donde esté permitido si la opción http::config -pipeline

es

booleana true (su valor por defecto). El paquete http no mantiene más de una conexión persistente a cada servidor (es decir, cada valor de "domain:port"). Si http::geturl es llamado para hacer una solicitud sobre una conexión persistente mientras la conexión está ocupada con otra solicitud, la nueva solicitud será

retenida

las

solicitudes POST, y las opciones para lidiar con estos casos. De acuerdo con RFC 7230, http::geturl no hace *pipelining* de solicitudes que usan el método POST. Si un POST usa una conexión persistente y no es la primera solicitud en esa conexión, http::geturl espera hasta haber recibido la respuesta de la solicitud anterior; o (si la opción http::config -postfresh es

booleana

true) usa una conexión nueva para cada POST. Si el servidor está procesando un número desolicitudes en *pipeline* y envía una cabecera de respuesta "Connection: close" con una de las respuestas (distinta de la última), entonces las respuestas subsiguientes no se cumplirán. http::

geturl

enviará las solicitudes no cumplidas de nuevo sobre una conexión nueva. Surge una dificultad cuando un cliente HTTP envía una solicitud sobre una conexión persistente que ha estado inactiva por un tiempo. El servidor HTTP puede cerrar a medias una conexión aparentemente inactiva mientras el cliente está enviando una solicitud, pero antes de que la solicitud llegue al servidor: en este caso (un "evento de cierre asincrónico") la solicitud fallará. La dificultad surge porque el cliente no puede estar seguro de si el POST modificó el estado del servidor. Para solicitudes HEAD o GET, http::geturl abre otra conexión y retransmite la solicitud fallida. Sin embargo, si la solicitud era un POST, RFC 7230 prohíbe el reintento automático por defecto, sugiriendo ya sea la confirmación del usuario, o la confirmación por software

*user-agent*

que tiene comprensión semántica de la aplicación. La opción http::config -repost permite cualquiera de las dos posibilidades. Los eventos de cierre asincrónicos solo pueden ocurrir en un intervalo corto de tiempo. El paquete http monitorea cada conexión persistente para

su

cierre por el servidor. Al detectarlo, la conexión también se cierra en el extremo del cliente, y las solicitudes subsiguientes usarán una conexión nueva. Si el comando http::geturl es llamado con laopción -keepalive true, entonces tanto intentará usar una conexión persistente existente (si

una

está disponible), como enviará al servidor una cabecera de solicitud "Connection:

keep-alive"

pidiendo mantener la conexión abierta para futuras solicitudes. Las opciones http::config -pipeline, -postfresh, y -repost se relacionan con conexiones persistentes. La opción -pipeline, si es booleana true, hará *pipelining* de solicitudes GET y HEAD hechas sobre una conexión persistente. Las solicitudes POST no serán en *pipeline* - si el POST no es la primera transacción en la conexión, su solicitud no se enviará hasta que

la

respuesta anterior haya terminado. Las solicitudes GET y HEAD hechas después de un POST no se enviarán hasta que la respuesta del POST haya

sido

entregada, y no se enviarán si el POST falla. La opción -postfresh, si es booleana true, sobreescribirá la opción http::geturl -keepalive, y siempre abrirá una conexión nueva para una solicitud POST. La opción -repost, si es true, permite el reintento automático de una solicitud POST que falla porque usa una conexión persistente que el servidor ha cerrado a medias (un "evento de cierre asincrónico"). Las solicitudes GET y H

EAD subsiguientes en un *pipeline* fallid
o también serán reintentadas. La opción
-repost debe usarse solo si la aplicación

entiende que

el

reintento es apropiado - específicamente, la aplicación debe saber que si el POST fallido modificó exitosamente el estado del servidor, un POST repetido no tendría efectos adversos. ACTUALIZACIONES DE PROTOCOLO Las cabeceras de cliente HTTP/1.1 Connection y Upgrade informan al servidor que el cliente desea cambiar el protocolo usado sobre la conexión existente (RFC 7230).

Este

mecanismo puede usarse para solicitar un WebSocket (RFC 6455), una versión superior del protocolo HTTP (HTTP 2), o cifrado TLS. Si el servidor acepta la solicitud de actualización, su código de respuesta será 101. Para solicitar una actualización de protocolo al llamar a http::geturl, la opción -headers debe proveer valores apropiados para Connection y Upgrade, y la opción -command debe proveer un comando que implemente el protocolo solicitado y que también pueda manejar la respuesta del servidor si el servidor rechaza

la

actualización del protocolo. Para solicitudes de actualización http::geturl ignora el valor de la opción -keepalive, y

siempre usa el valor 0 de modo que la solicitud de

actualización

no se haga sobre una conexión destinada a múltiples solicitudes HTTP. La biblioteca Tcllib websocket implementa WebSockets, y hace las llamadas necesarias a comandos en el paquete http. Actualmente no existe una biblioteca cliente nativa de Tcl para HTTP/2. El mecanismo Upgrade no se usa para solicitar

TLS

en navegadores web, porque http y https se sirven sobre diferentes puertos. Es usado por protocolos como Internet Printing Protocol (IPP) que están construidos sobre http(s) y usan el mismo número de puerto TCP tanto para tráfico seguro como inseguro. En los navegadores, el cifrado oportunista se implementa en cambio por la cabecera de cliente Upgrade-I
