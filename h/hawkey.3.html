Introducció

n

Este documento describe los cambios en la API que los usuarios de la biblioteca deben conocer antes de actualizar a cada versión respectiva. Es nuestro plan que la cantidad de cambios que requieran modificar el código del cliente se reduzca al mínimo después de que la biblioteca alcance la versión 1.0.

0.

Los elementos de la API obsoletos (clases, métodos, etc.) se designan como tales en este documento. La primera versión en la que se puede abandonar completamente el soporte para dichos elementos debe emitirse al menos cinco meses después de la emisión de la versión que anunció la obsolescencia y al mismo tiempo tener, en relación con la versión que la declaró obsoleta, cualquiera de las

siguientes:
  • un número de versión principal más alto,
    • o
  • un número de versión secundario más alto,

    • l me

Es probable que estos criterios se endurezcan en el futuro a medida que hawkey

madure.

Los cambios reales en la API también se anuncian en este documento. Los cambios de ABI, incluidos cambios en el número o tipo de parámetros de las funciones o la eliminación de símbolos públicos de libhawkey, implican un aumento en

la versión SONAME

Internamente, para mantener la información del paquete y realizar la resolución canónica, hawkey usa Libsolv https://github.com/openSUSE/libsolv. RAZÓN DE

DISEÑO

Los Selectors no son

Queries

Dado que tanto un Query como un Selector trabajan para limitar el conjunto de todos los paquetes del Sack a un subconjunto, se podría sugerir que los dos conceptos deberían ser el mismo y que, por ejemplo, los Queries deberían usarse para las especificaciones de Goal en lugar de los

Selectors: 
// crear sack, goal, ...
HyQuery q = hy_query_create(sack);
hy_query_filter(q, HY_PKG_NAME, HY_EQ, "anaconda")
hy_goal_install_query
(
q
)

Este arreglo se usó de hecho en hawkey antes de la versión 0.3.0, simplemente porque los Queries parecían una estructura conveniente para contener este tipo de información. Desafortunadamente, fue confuso para los programadores: observe cómo evaluar el Query q generalmente produciría varios paquetes (anaconda para diferentes arquitecturas y luego diferentes versiones) pero de alguna manera cuando el mismo Query se pasa a los métodos del goal siempre resulta en hasta un paquete seleccionado para la operación. Esta es una discrepancia principal. Además, Query es universal y permite limitar el conjunto de paquetes con todo tipo de criterios, coincidentes de diferentes maneras (subcadenas, globbing, operaciones de conjunto) mientras que los Selectors solo soportan unos pocos. Finalmente, mientras que un Query nuevo sin filtros aplicados corresponde a todos los paquetes del Sack, un Selector nuevo sin límites establecidos no tiene

significado.

Una alternativa a introducir un concepto completamente diferente fue añadir una función constructora separada para Query, una que desde el principio designara el Query para solo aceptar ajustes compatibles con su propósito de convertirse en elng en una operación Goal (en Python esto probablemente se implementaría como una subclase de Query). Pero eso rompería las suposiciones del cliente sobre Query (el FAQ no oficial de C++ http://www.parashift.com/c++-faq/circle-ellipse.html trata el tema)

.

Nota de implementación: Los Selectors reflejan el tipo de especificaciones que se pueden traducir directamente en trabajos de Libsolv, sin buscar de hecho un paquete concreto para poner allí. En otras palabras, los Selectors están diseñados específicamente para no iterar sobre los datos del paquete (con excepciones, como la coincidencia de glob) como lo hacen los Queries. Aunque Hawkey apunta principalmente a ocultar cualquier giro y complejidad de la biblioteca subyacente, en este caso las razones combinadas justifican una

concesión.
