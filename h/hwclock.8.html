HWCLOCK(8) Administración del Sistema HWCLOCK(8)

NOMBRE

hwclock - utilidad de relojes de tiempo

SINOPSIS

hwclock [función] [opción...]

DESCRIPCIÓN

hwclock es una herramienta de administración para los relojes de tiempo. Puede: mostrar la hora del Reloj de Hardware; establecer el Reloj de Hardware a una hora especificada; establecer el Reloj de Hardware desde el Reloj del Sistema; establecer el Reloj del Sistema desde el Reloj de Hardware; compensar la deriva del Reloj de Hardware; corregir la escala de tiempo del Reloj del Sistema; establecer la zona horaria del kernel, la escala de tiempo NTP y la época (solo Alpha); y predecir valores futuros del Reloj de Hardware basándose en su tasa de deriva.

Desde la versión 2.26 se introdujeron cambios importantes en la función --hctosys y la opción --directisa, y se añadió una nueva opción --update-drift. Consulte sus descripciones respectivas a continuación.

FUNCIONES

Las siguientes funciones son mutuamente excluyentes, solo se puede dar una a la vez. Si no se proporciona ninguna, el valor predeterminado es --show.

-a, --adjust

Suma o resta tiempo al Reloj de Hardware para tener en cuenta la deriva sistemática desde la última vez que se configuró o ajustó el reloj. Consulte la discusión a continuación, bajo La Función de Ajuste.

--getepoch; --setepoch

Estas funciones son solo para máquinas Alpha y solo están disponibles a través del controlador RTC del kernel de Linux.

Se utilizan para leer y establecer el valor de época del Reloj de Hardware del kernel. La época es el número de años después de Cristo al que se refiere un valor de año cero en el Reloj de Hardware. Por ejemplo, si la BIOS de la máquina establece el contador de años en el Reloj de Hardware para contener el número de años completos desde 1952, entonces el valor de época del Reloj de Hardware del kernel debe ser 1952.

La función --setepoch requiere el uso de la opción --epoch para especificar el año. Por ejemplo:

hwclock --setepoch --epoch=1952

El controlador RTC intenta adivinar el valor de época correcto, por lo que es posible que no sea necesario establecerlo.

Este valor de época se utiliza cada vez que hwclock lee o establece el Reloj de Hardware en una máquina Alpha. Para máquinas ISA, el kernel utiliza la época fija del Reloj de Hardware de 1900.

--param-get=parámetro; --param-set=parámetro=valor

Lee y establece el parámetro del RTC. Esto es útil, por ejemplo, para recuperar la característica del RTC o para establecer el Modo de conmutación de respaldo del RTC.

parámetro es un valor de parámetro RTC numérico (consulte include/uapi/linux/rtc.h del kernel) o un alias. Consulte --help para obtener una lista de alias válidos. parámetro y valor, si van precedidos por 0x, se interpretan como valores hexadecimales, de lo contrario, decimales.

--predict

Predice qué leerá el Reloj de Hardware en el futuro basándose en la hora proporcionada por la opción --date y la información en /etc/adjtime. Esto es útil, por ejemplo, para tener en cuenta la deriva al configurar una alarma de encendido del Reloj de Hardware. Consulte rtcwake(8).

No utilice esta función si el Reloj de Hardware está siendo modificado por algo que no sea el comando hwclock del sistema operativo actual, como el 'modo de 11 minutos' o al arrancar otro SO.

-r, --show; --get

Lee el Reloj de Hardware y muestra su hora en la salida estándar en formato ISO 8601. La hora que se muestra siempre está en hora local, incluso si mantiene su Reloj de Hardware en UTC. Consulte la opción --localtime.

Mostrar la hora del Reloj de Hardware es la acción predeterminada cuando no se especifica ninguna función.

La función --get también aplica corrección de deriva a la hora leída, basándose en la información en /etc/adjtime. No utilice esta función si el Reloj de Hardware está siendo modificado por algo que no sea el comando hwclock del sistema operativo actual, como el 'modo de 11 minutos' o al arrancar otro SO.

-s, --hctosys

Establece el Reloj del Sistema a partir del Reloj de Hardware. La hora leída del Reloj de Hardware se compensa para tener en cuenta la deriva sistemática antes de usarla para establecer el Reloj del Sistema. Consulte la discusión a continuación, bajo La Función de Ajuste.

El Reloj del Sistema debe mantenerse en la escala de tiempo UTC para que las aplicaciones de fecha y hora funcionen correctamente junto con la zona horaria configurada para el sistema. Si el Reloj de Hardware se mantiene en hora local, la hora leída de él debe cambiarse a la escala de tiempo UTC antes de usarla para establecer el Reloj del Sistema. La función --hctosys realiza esto basándose en la información del archivo /etc/adjtime o en los argumentos de línea de comandos --localtime y --utc. Nota: no se realiza ningún ajuste de horario de verano. Consulte la discusión a continuación, bajo LOCAL vs UTC.

El kernel también mantiene un valor de zona horaria, la función --hctosys lo establece a la zona horaria configurada para el sistema. La zona horaria del sistema se configura mediante la variable de entorno TZ o el archivo /etc/localtime, tal como lo interpretaría tzset(3). El campo obsoleto tz_dsttime del valor de zona horaria del kernel se establece en cero. (Para obtener detalles sobre lo que significaba este campo, consulte settimeofday(2)).

Cuando se utiliza en un script de inicio, haciendo que la función --hctosys sea la primera en llamar a settimeofday(2) desde el arranque, establecerá la escala de tiempo 'modo de 11 minutos' de NTP a través de la variable del kernel persistent_clock_is_local. Si la configuración de la escala de tiempo del Reloj de Hardware se cambia, se requerirá un reinicio para informar al kernel. Consulte la discusión a continuación, bajo Sincronización Automática del Reloj de Hardware por el Kernel.

Esta es una buena función para usar en uno de los scripts de inicio del sistema antes de que los sistemas de archivos se monten en lectura/escritura.

Esta función nunca debe usarse en un sistema en ejecución. Saltar la hora del sistema causará problemas, como marcas de tiempo corruptas en el sistema de archivos. Además, si algo ha cambiado el Reloj de Hardware, como el 'modo de 11 minutos' de NTP, entonces --hctosys establecerá la hora incorrectamente al incluir la compensación de deriva.

La compensación de deriva se puede inhibir estableciendo el factor de deriva en /etc/adjtime a cero. Esta configuración será persistente siempre que la opción --update-drift no se use con --systohc al apagar (o en cualquier otro lugar). Otra forma de inhibir esto es usando la opción --noadjfile al llamar a la función --hctosys. Un tercer método es eliminar el archivo /etc/adjtime. Hwclock usará por defecto la escala de tiempo UTC para el Reloj de Hardware. Si el Reloj de Hardware está configurado en hora local, deberá definirse en el archivo. Esto se puede hacer llamando a hwclock --localtime --adjust; cuando el archivo no está presente, este comando en realidad no ajustará el Reloj, pero creará el archivo con la hora local configurada y un factor de deriva de cero.

Una condición bajo la cual inhibir la corrección de deriva de hwclock puede ser deseable es al arrancar múltiples sistemas operativos. Si mientras esta instancia de Linux está detenida, otro SO cambia el valor del Reloj de Hardware, entonces cuando esta instancia se inicie de nuevo, la corrección de deriva aplicada será incorrecta.

Para que la corrección de deriva de hwclock funcione correctamente, es imperativo que nada cambie el Reloj de Hardware mientras su instancia de Linux no esté en ejecución.

--set

Establece el Reloj de Hardware a la hora proporcionada por la opción --date y actualiza las marcas de tiempo en /etc/adjtime. Con la opción --update-drift también se (re)calcula el factor de deriva. Inténtelo sin la opción si --set falla. Consulte --update-drift a continuación.

--systz

Esta es una alternativa a la función --hctosys que no lee el Reloj de Hardware ni establece el Reloj del Sistema; en consecuencia, no hay corrección de deriva. Está destinado a usarse en un script de inicio en sistemas con kernels superiores a la versión 2.6 donde se sabe que el kernel ha establecido el Reloj del Sistema a partir del Reloj de Hardware durante el arranque.

Realiza las siguientes acciones detalladas anteriormente en la función --hctosys:

•Corrige la escala de tiempo del Reloj del Sistema a UTC según sea necesario. Solo

Arch Linux, Arch Linux ARM, Arch Linux LTS, ArchBang, Manjaro Linux, Garuda Linux, EndeavourOS, ArcoLinux, etc.

Este sitio no está asociado de ninguna forma con Arch Linux ni afiliado a este proyecto. El contenido es únicamente una traducción de las páginas del manual de Arch publicadas en man.archlinux.org.

en lugar de lograr esto configurando el Reloj del Sistema, hwclock simplemente se lo informa al kernel y este maneja el cambio.
•Establece la escala de tiempo del modo '11 minutos' NTP del kernel.
•Establece la zona horaria del kernel.

Los dos primeros solo están disponibles en la primera llamada a settimeofday(2) después del arranque. En consecuencia, esta opción solo tiene sentido cuando se usa en un script de inicio. Si se cambia la configuración de la escala de tiempo del Reloj de Hardware, se requeriría un reinicio para informar al kernel.

-w, --systohc

Establece el Reloj de Hardware a partir del Reloj del Sistema y actualiza las marcas de tiempo en /etc/adjtime. Con la opción --update-drift también (re)calcula el factor de deriva. Inténtalo sin la opción si --systohc falla. Ver --update-drift a continuación.

--vl-read, --vl-clear

Algunos dispositivos RTC son capaces de monitorear el voltaje de la batería de respaldo y, por lo tanto, proporcionan una forma para que el usuario sepa que la batería debería ser reemplazada. La función --vl-read recupera la información de Voltaje Bajo y decodifica el resultado en un formato legible por humanos. La función --vl-clear restablece la información de Voltaje Bajo, lo cual es necesario para algunos dispositivos RTC después del reemplazo de la batería.

Consulte la sección include/uapi/linux/rtc.h del Kernel para obtener detalles sobre qué información puede ser devuelta. Tenga en cuenta que no todos los dispositivos RTC tienen esta capacidad de monitoreo, ni todos los controladores necesariamente admiten la lectura de la información.

Muestra el texto de ayuda y sale.

-V, --version

Muestra la versión y sale.

OPCIONES

--adjfile=nombre_archivo

Anula la ruta predeterminada del archivo /etc/adjtime.

--date=cadena_fecha

Esta opción debe usarse con las funciones --set o --predict, de lo contrario se ignora.

hwclock --set --date='16:45'

hwclock --predict --date='2525-08-14 07:11:05'

El argumento debe estar en hora local, incluso si mantiene su Reloj de Hardware en UTC. Consulte la opción --localtime. Por lo tanto, el argumento no debe incluir información de zona horaria. Tampoco debe ser un tiempo relativo como " +5 minutos ", porque la precisión de hwclock depende de la correlación entre el valor del argumento y el momento en que se presiona la tecla Enter. Los segundos fraccionarios se descartan silenciosamente. Esta opción es capaz de entender muchos formatos de fecha y hora, pero se deben observar los parámetros anteriores.

--delay=segundos

Esta opción se puede usar para anular el retardo utilizado internamente al configurar la hora del reloj. El valor predeterminado es 0.5 (500 ms) para rtc_cmos; para otros tipos de RTC, el retardo es 0. Si el tipo de RTC es imposible de determinar (desde sysfs), también se establece en 0.5 para ser compatible con versiones anteriores.

El valor predeterminado de 500 ms se basa en el hardware de reloj compatible con MC146818A (x86) de uso común. Este Reloj de Hardware solo se puede configurar a cualquier hora entera más medio segundo. La hora entera es necesaria porque no hay una interfaz para configurar u obtener fracciones de segundo. El medio segundo adicional de retardo se debe a que el Reloj de Hardware se actualiza al segundo siguiente precisamente 500 ms después de configurar la nueva hora. Desafortunadamente, este comportamiento es específico del hardware y, en algunos casos, se requiere otro retardo.

-D, --debug

Use --verbose. La opción --debug ha sido deprecada y puede ser reasignada o eliminada en una futura versión.

--directisa

Esta opción es significativa para máquinas compatibles con ISA en la familia x86 y x86_64. Para otras máquinas, no tiene efecto. Esta opción le dice a hwclock que use instrucciones de E/S explícitas para acceder al Reloj de Hardware. Sin esta opción, hwclock usará el archivo del dispositivo rtc, que asume que está controlado por el controlador de dispositivo RTC de Linux. A partir de la v2.26, ya no usará directisa automáticamente cuando el controlador rtc no esté disponible; esto causaba una condición insegura que podía permitir que dos procesos accedieran al Reloj de Hardware al mismo tiempo. El acceso directo al hardware desde el espacio de usuario solo debe usarse para pruebas, solución de problemas y como último recurso cuando todos los demás métodos fallen. Consulte la opción --rtc.

--epoch=año

Esta opción es necesaria cuando se utiliza la función --setepoch. El valor mínimo de año es 1900. El máximo depende del sistema (ULONG_MAX - 1).

-f, --rtc=nombre_archivo

Anula el nombre del archivo del dispositivo rtc predeterminado de hwclock. De lo contrario, utilizará el primero que encuentre en este orden: /dev/rtc0, /dev/rtc, /dev/misc/rtc. Para IA-64: /dev/efirtc /dev/misc/efirtc

-l, --localtime; -u, --utc

Indica en qué escala de tiempo está configurado el Reloj de Hardware.

El Reloj de Hardware puede configurarse para usar la escala de tiempo UTC o local, pero nada en el propio reloj indica qué alternativa se está utilizando. Las opciones --localtime o --utc proporcionan esta información al comando hwclock. Si especifica la incorrecta (o no especifica ninguna y toma una predeterminada incorrecta), tanto la configuración como la lectura del Reloj de Hardware serán incorrectas.

Si no especifica ni --utc ni --localtime, se utilizará la última especificada con una función de configuración (--set, --systohc o --adjust), tal como se registra en /etc/adjtime. Si el archivo adjtime no existe, el valor predeterminado es UTC.

Nota: los cambios de horario de verano pueden ser inconsistentes cuando el Reloj de Hardware se mantiene en hora local. Consulte la discusión a continuación, en LOCAL vs UTC.

--noadjfile

Deshabilita las facilidades proporcionadas por /etc/adjtime. hwclock no leerá ni escribirá en ese archivo con esta opción. Se debe especificar ya sea --utc o --localtime al usar esta opción.

--test

No cambie nada en el sistema, es decir, los Relojes o /etc/adjtime (--verbose es implícito con esta opción).

--update-drift

Actualiza el factor de deriva del Reloj de Hardware en /etc/adjtime. Solo se puede usar con --set o --systohc.

Se requiere un período mínimo de cuatro horas entre configuraciones. Esto es para evitar cálculos inválidos. Cuanto más largo sea el período, más preciso será el factor de deriva resultante.

Esta opción se agregó en la v2.26, porque es típico que los sistemas ejecuten hwclock --systohc al apagar; con el comportamiento anterior, esto (re)calculaba automáticamente el factor de deriva, lo que causaba varios problemas:

•Al usar NTP con un kernel en modo '11 minutos', el factor de deriva se reduciría a casi cero.
•No permitiría el uso de corrección de deriva 'en frío'. Con la mayoría de las configuraciones, usar la corrección 'en frío' dará resultados favorables. En frío, significa cuando la máquina está apagada, lo que puede tener un impacto significativo en el factor de deriva.
•(Re)calcular el factor de deriva en cada apagado produce resultados subóptimos. Por ejemplo, si condiciones efímeras provocan que la máquina esté anormalmente caliente, el cálculo del factor de deriva estaría fuera de rango.
•Tiempos de apagado del sistema significativamente aumentados (a partir de la v2.31, cuando no se usa --update-drift, el RTC no se lee).

Que hwclock calcule el factor de deriva es un buen punto de partida, pero para obtener resultados óptimos, probablemente será necesario ajustarlo editando directamente el archivo /etc/adjtime. Para la mayoría de las configuraciones, una vez que el factor de deriva óptimo de una máquina se ha elaborado, no debería ser necesario cambiarlo. Por lo tanto, el comportamiento anterior de (re)calcular automáticamente la deriva se cambió y ahora requiere el uso de esta opción. Consulte la discusión a continuación, en La Función de Ajuste.

Esta opción requiere leer el Reloj de Hardware antes de configurarlo. Si no se puede leer, esta opción hará que las funciones de configuración fallen. Esto puede suceder, por ejemplo, si el Reloj de Hardware está corrupto por un corte de energía. En ese caso, primero se debe configurar el reloj sin esta opción. A pesar de que no funcione, el factor de corrección de deriva resultante sería inválido de todos modos.

-v, --verbose

Muestra más detalles sobre lo que hwclock está haciendo internamente.

NOTAS

Relojes en un Sistema Linux

Hay dos tipos de relojes de fecha y hora:

El Reloj de Hardware: Este reloj es un dispositivo de hardware independiente, con su propio dominio de energía (batería, condensador, etc.), que opera cuando la máquina está apagada, o incluso desenchufada.

En un sistema compatible con ISA, este reloj se especifica como parte del estándar ISA. Un programa de control puede leer o configurar este reloj solo a segundos enteros, pero también puede detectar los flancos de los tics del reloj de 1 segundo, por lo que el reloj en realidad tiene una precisión virtualmente infinita.

Este reloj se llama comúnmente reloj de hardware, reloj de tiempo real, RTC, reloj de BIOS y reloj CMOS. Hardware Clock, en su forma capitalizada, se acuñó para su uso por hwclock. El kernel de Linux también se refiere a él como el reloj persistente.

Algunos sistemas no ISA tienen algunos relojes de tiempo real, de los cuales solo uno tiene su propio dominio de energía. Se podría utilizar un chip de reloj externo de muy bajo consumo I2C o SPI con una batería de respaldo como reloj de hardware para inicializar un reloj de tiempo real integrado más funcional que se utiliza para la mayoría de los demás propósitos.

El Reloj del Sistema: Este reloj forma parte del kernel de Linux y está impulsado por una interrupción del temporizador. (En una máquina ISA, la interrupción del temporizador es parte del estándar ISA). Solo tiene sentido mientras Linux se ejecuta en la máquina. El Tiempo del Sistema es el número de segundos transcurridos desde las 00:00:00 del 1 de enero de 1970 UTC (o más concisamente, el número de segundos desde 1969 UTC). El Tiempo del Sistema no es un entero, sin embargo. Tiene una precisión virtualmente infinita.

El Tiempo del Sistema es el tiempo que importa. El propósito básico del Reloj de Hardware es mantener el tiempo cuando Linux no se está ejecutando para que el Reloj del Sistema pueda inicializarse a partir de él al arrancar. Tenga en cuenta que en DOS, para el cual fue diseñado ISA, el Reloj de Hardware es el único reloj de tiempo real.

Es importante que el Tiempo del Sistema no tenga discontinuidades, como las que ocurrirían si utilizara el programa date(1) parao establecerlo mientras el sistema está en funcionamiento. Sin embargo, puede hacer lo que quiera con el Reloj de Hardware mientras el sistema está en funcionamiento, y la próxima vez que Linux arranque, lo hará con la hora ajustada del Reloj de Hardware. Nota: actualmente esto no es posible en la mayoría de los sistemas porque hwclock --systohc se llama al apagar.

La zona horaria del kernel de Linux se establece mediante hwclock. Pero no se deje engañar: a casi nadie le importa en qué zona horaria cree el kernel que está. En su lugar, los programas que se preocupan por la zona horaria (quizás porque quieren mostrar una hora local para usted) casi siempre usan un método más tradicional para determinar la zona horaria: Usan la variable de entorno TZ o el archivo /etc/localtime , como se explica en la página del manual de tzset(3). Sin embargo, algunos programas y partes periféricas del kernel de Linux, como los sistemas de archivos, usan el valor de la zona horaria del kernel. Un ejemplo es el sistema de archivos vfat. Si el valor de la zona horaria del kernel es incorrecto, el sistema de archivos vfat informará y establecerá marcas de tiempo incorrectas en los archivos. Otro ejemplo es el 'modo de 11 minutos' de NTP del kernel. Si el valor de la zona horaria del kernel y/o la variable persistent_clock_is_local son incorrectos, entonces el Reloj de Hardware se establecerá incorrectamente por el 'modo de 11 minutos'. Vea la discusión más abajo, en Sincronización Automática del Reloj de Hardware por el Kernel.

hwclock establece la zona horaria del kernel al valor indicado por TZ o /etc/localtime con las funciones --hctosys o --systz .

El valor de la zona horaria del kernel en realidad consta de dos partes: 1) un campo tz_minuteswest que indica cuántos minutos la hora local (sin ajuste por horario de verano) se retrasa con respecto a UTC, y 2) un campo tz_dsttime que indica el tipo de convención de Horario de Verano (DST) que está vigente en la localidad en el momento actual. Este segundo campo no se usa bajo Linux y siempre es cero. Vea también settimeofday(2).

Métodos de Acceso al Reloj de Hardware

hwclock usa muchas formas diferentes de obtener y establecer valores del Reloj de Hardware. La forma más normal es hacer E/S al archivo especial de dispositivo rtc, que se presume está controlado por el controlador de dispositivo rtc. Además, los sistemas Linux que usan el marco de trabajo rtc con udev son capaces de soportar múltiples Relojes de Hardware. Esto puede traer la necesidad de anular el dispositivo rtc predeterminado especificando uno con la opción --rtc .

Sin embargo, este método no siempre está disponible, ya que los sistemas más antiguos no tienen un controlador rtc. En estos sistemas, el método de acceso al Reloj de Hardware depende del hardware del sistema.

En un sistema compatible con ISA, hwclock puede acceder directamente a los registros de "memoria CMOS" que constituyen el reloj, haciendo E/S a los Puertos 0x70 y 0x71. Lo hace con instrucciones de E/S reales y, en consecuencia, solo puede hacerlo si se ejecuta con el identificador de usuario efectivo de superusuario. Este método puede usarse especificando la opción --directisa .

Este es un método realmente pobre para acceder al reloj, por todas las razones por las que generalmente se supone que los programas de espacio de usuario no deben hacer E/S directa y deshabilitar interrupciones. hwclock lo proporciona para pruebas, resolución de problemas, y porque puede ser el único método disponible en sistemas ISA que no tienen un controlador de dispositivo rtc funcional.

La Función de Ajuste

El Reloj de Hardware generalmente no es muy preciso. Sin embargo, gran parte de su imprecisión es completamente predecible: gana o pierde la misma cantidad de tiempo todos los días. Esto se llama deriva sistemática. hwclock's --adjust la función le permite aplicar correcciones de deriva sistemática al Reloj de Hardware.

Funciona de esta manera: hwclock mantiene un archivo, /etc/adjtime, que guarda cierta información histórica. Esto se llama el archivo adjtime.

Suponga que comienza sin un archivo adjtime. Emite un comando hwclock --set para establecer el Reloj de Hardware en la hora actual verdadera. hwclock crea el archivo adjtime y registra en él la hora actual como la última vez que se calibró el reloj. Cinco días después, el reloj ha ganado 10 segundos, así que emite un comando hwclock --set --update-drift para retrocederlo 10 segundos. hwclock actualiza el archivo adjtime para mostrar la hora actual como la última vez que se calibró el reloj, y registra 2 segundos por día como la tasa de deriva sistemática. Pasan 24 horas, y luego emite un comando hwclock --adjust . hwclock consulta el archivo adjtime y ve que el reloj gana 2 segundos por día cuando se deja solo y que se ha dejado solo exactamente un día. Así que resta 2 segundos del Reloj de Hardware. Luego registra la hora actual como la última vez que se ajustó el reloj. Pasan otras 24 horas y usted emite otro hwclock --adjust. hwclock hace lo mismo: resta 2 segundos y actualiza el archivo adjtime con la hora actual como la última vez que se ajustó el reloj.

Cuando usa la opción --update-drift con --set o --systohc, la tasa de deriva sistemática se (re)calcula comparando la hora actual del Reloj de Hardware completamente corregida por deriva con la nueva hora establecida, a partir de ella deriva la tasa de deriva de 24 horas basada en la última marca de tiempo calibrada del archivo adjtime. Este factor de deriva actualizado se guarda luego en /etc/adjtime.

Se cuela una pequeña cantidad de error cuando se establece el Reloj de Hardware, por lo que --adjust se abstiene de hacer cualquier ajuste que sea menor de 1 segundo. Más adelante, cuando solicite un ajuste de nuevo, la deriva acumulada será más de 1 segundo y --adjust hará el ajuste incluyendo cualquier cantidad fraccionaria.

hwclock --hctosys también usa los datos del archivo adjtime para compensar el valor leído del Reloj de Hardware antes de usarlo para establecer el Reloj del Sistema. No comparte la limitación de 1 segundo de --adjust, y corregirá valores de deriva sub-segundo inmediatamente. No cambia la hora del Reloj de Hardware ni el archivo adjtime. Esto puede eliminar la necesidad de usar --adjust, a menos que algo más en el sistema necesite que el Reloj de Hardware sea compensado.

El Archivo Adjtime

Aunque lleva el nombre de su propósito histórico de controlar solo los ajustes, en realidad contiene otra información usada por hwclock de una invocación a la siguiente.

El formato del archivo adjtime es, en ASCII:

Línea 1: Tres números, separados por espacios en blanco: 1) la tasa de deriva sistemática en segundos por día, decimal de punto flotante; 2) el número resultante de segundos desde 1969 UTC del ajuste o calibración más reciente, entero decimal; 3) cero (por compatibilidad con clock(8)) como decimal de punto flotante.

Línea 2: Un número: el número resultante de segundos desde 1969 UTC de la calibración más reciente. Cero si aún no ha habido una calibración o si se sabe que cualquier calibración anterior es irrelevante (por ejemplo, porque se ha descubierto que el Reloj de Hardware, desde esa calibración, no contiene una hora válida). Este es un entero decimal.

Línea 3: "UTC" o "LOCAL". Indica si el Reloj de Hardware está establecido en Tiempo Universal Coordinado o en hora local. Siempre puede anular este valor con opciones en la línea de comandos de hwclock .

Puede usar un archivo adjtime que fue usado previamente con el programa clock(8) con hwclock.

Sincronización Automática del Reloj de Hardware por el Kernel

Debe ser consciente de otra forma en que el Reloj de Hardware se mantiene sincronizado en algunos sistemas. El kernel de Linux tiene un modo en el que copia la Hora del Sistema al Reloj de Hardware cada 11 minutos. Este modo es una opción de compilación, por lo que no todos los kernels tendrán esta capacidad. Este es un buen modo para usar cuando está usando algo sofisticado como NTP para mantener su Reloj del Sistema sincronizado. (NTP es una forma de mantener su Hora del Sistema sincronizada ya sea con un servidor de tiempo en algún lugar de la red o con un reloj de radio conectado a su sistema. Vea RFC 1305.)

Si el kernel está compilado con la opción 'modo de 11 minutos', estará activo cuando la disciplina del reloj del kernel esté en un estado sincronizado. Cuando esté en este estado, el bit 6 (el bit que está establecido en la máscara 0x0040) de la variable time_status del kernel no está establecido. Este valor se emite como la línea 'status' de los comandos adjtimex --print o ntptime .

Se necesita una influencia externa, como el demonio NTP, para poner la disciplina del reloj del kernel en un estado sincronizado y, por lo tanto, activar el 'modo de 11 minutos'. Puede apagarse ejecutando cualquier cosa que establezca el Reloj del Sistema a la manera antigua, incluyendo hwclock --hctosys. Sin embargo, si el demonio NTP sigue en ejecución, volverá a activar el 'modo de 11 minutos' la próxima vez que sincronice el Reloj del Sistema.

Si su sistema se ejecuta con el 'modo de 11 minutos' activado, puede necesitar usar --hctosys o --systz en un script de inicio, especialmente si el Reloj de Hardware está configurado para usar la escala de tiempo local. A menos que se le informe al kernel qué escala de tiempo está usando el Reloj de Hardware, puede pisarla con la incorrecta. El kernel usa UTC por defecto.

El primer comando de espacio de usuario que establece el Reloj del Sistema le informa al kernel qué escala de tiempo está usando el Reloj de Hardware. Esto sucede a través de la variable del kernel persistent_clock_is_local . Si --hctosys o --systz es el primero, establecerá esta variable de acuerdo con el archivo adjtime o el argumento de línea de comandos apropiado. Tenga en cuenta que al usar esta capacidad y si se cambia la configuración de la escala de tiempo del Reloj de Hardware, se requiere un reinicio para notificar al kernel.

hwclock --adjust no debe usarse con el 'modo de 11 minutos' de NTP.

Valor del Siglo del Reloj de Hardware ISA

Existe algún tipo de estándar que define el Byte 50 de la memoria CMOS en una máquina ISA como un indicador de qué siglo es. hwclock no usa ni establece ese byte porque hay algunas máquinas que no definen el byte de esa manera, y realmente no es necesario de todos modos, ya que el año del siglo hace un buen trabajo de implicar de qué siglo se trata.

Si tiene un uso legítimo para un byte de siglo CMOS, contacte al hwclock mantenedor; una opción podría ser apropiada.

NOMBRE

hwclock - gestor del reloj de hardware del sistema

SINOPSIS

hwclock [opciones...]

hwclock --help

DESCRIPCIÓN

hwclock es una utilidad para leer y establecer el reloj del hardware (también conocido como el reloj RTC o BIOS) en un sistema Linux. El reloj del sistema (el reloj de fecha y hora que el kernel de Linux mantiene) se puede mantener sincronizado con el reloj del hardware. También se puede mantener sincronizado con un servidor de tiempo externo usando NTP (Network Time Protocol). Una vez que el reloj del sistema está sincronizado con el reloj del hardware, el reloj del hardware puede usarse para inicializar el reloj del sistema después de un reinicio.

hwclock puede usarse para administrar el reloj del hardware. También se usa para ajustar el reloj del sistema, o para ajustar los parámetros de corrección de deriva del reloj del sistema. El ajuste del reloj del sistema se realiza usando la llamada al sistema `adjtime()`. Esta llamada permite ajustar el reloj del sistema de manera que se tengan en cuenta la deriva (el error que ocurre cuando un reloj corre más rápido o más lento de lo que debería) y los efectos de la sincronización con el reloj del hardware.

La siguiente discusión se basa en las siguientes condiciones:

•Nada se está ejecutando que altere los relojes de fecha y hora, como el demonio NTP o un trabajo cron.
•La zona horaria del sistema está configurada para la hora local correcta. Consulte más abajo, en POSIX vs 'RIGHT'.
•Temprano durante el inicio se llaman los siguientes comandos, en este orden: adjtimex --tick valor --frequency valor hwclock --hctosys
•Durante el apagado se llama lo siguiente: hwclock --systohc
•Los sistemas sin adjtimex pueden usar ntptime.

Ya sea que se mantenga la hora de precisión con el demonio NTP o no, tiene sentido configurar el sistema para que mantenga una fecha y hora razonablemente precisas por sí mismo.

El primer paso para lograrlo es tener una comprensión clara del panorama general. Hay dos dispositivos de hardware completamente separados que funcionan a su propia velocidad y se desvían de la hora 'correcta' a sus propias tasas. Los métodos y el software para la corrección de deriva son diferentes para cada uno de ellos. Sin embargo, la mayoría de los sistemas están configurados para intercambiar valores entre estos dos relojes al inicio y al apagado. Ahora los errores de mantenimiento de hora del dispositivo individual se transfieren de un lado a otro. Si se intenta configurar la corrección de deriva para solo uno de ellos, la deriva del otro se superpondrá a ella.

Este problema se puede evitar al configurar la corrección de deriva para el Reloj del Sistema simplemente no apagando la máquina. Esto, además del hecho de que toda la precisión de hwclock (incluido el cálculo de los factores de deriva) depende de que la tasa del Reloj del Sistema sea correcta, significa que la configuración del Reloj del Sistema debe hacerse primero.

La deriva del Reloj del Sistema se corrige con las opciones --tick y --frequency del comando adjtimex(8). Estas dos funcionan juntas: tick es el ajuste grueso y frequency es el ajuste fino. (Para sistemas que no tienen un paquete adjtimex, se puede usar ntptime -f ppm en su lugar).

Algunas distribuciones de Linux intentan calcular automáticamente la deriva del Reloj del Sistema con la operación de comparación de adjtimex. Intentar corregir un reloj que se desvía usando otro reloj que se desvía como referencia es similar a un perro tratando de atrapar su propia cola. El éxito puede ocurrir eventualmente, pero es probable que lo precedan un gran esfuerzo y frustración. Esta automatización puede producir una mejora en comparación con ninguna configuración, pero esperar resultados óptimos sería un error. Una mejor opción para la configuración manual sería las opciones --log de adjtime.

Puede ser más efectivo simplemente rastrear la deriva del Reloj del Sistema con sntp, o date -Ins y un reloj de precisión, y luego calcular la corrección manualmente.

Después de establecer los valores de tick y frequency, continúe probando y refinando los ajustes hasta que el Reloj del Sistema mantenga la hora correctamente. Consulte adjtimex(2) para obtener más información y el ejemplo que demuestra los cálculos manuales de deriva.

Una vez que el Reloj del Sistema funcione sin problemas, pase al Reloj del Hardware.

Como regla general, la deriva en frío funcionará mejor para la mayoría de los casos de uso. Esto debería ser cierto incluso para máquinas que funcionan las 24 horas del día, los 7 días de la semana, cuyo tiempo de inactividad normal consiste en un reinicio. En ese caso, el valor del factor de deriva tiene poca importancia. Pero en la rara ocasión en que la máquina se apaga durante un período prolongado, la deriva en frío debería arrojar mejores resultados.

Pasos para calcular la deriva en frío:

1

Asegúrese de que el demonio NTP no se iniciará al arrancar.

2

¡La hora del Reloj del Sistema debe ser correcta al apagar!

3

Apague el sistema.

4

Deje pasar un período prolongado sin cambiar el Reloj del Hardware.

5

Inicie el sistema.

6

Use inmediatamente hwclock para establecer la hora correcta, agregando la opción --update-drift.

Nota: si el paso 6 usa --systohc, entonces el Reloj del Sistema debe configurarse correctamente (paso 6a) justo antes de hacerlo.

Que hwclock calcule el factor de deriva es un buen punto de partida, pero para obtener resultados óptimos, probablemente será necesario editar directamente el archivo /etc/adjtime. Continúe probando y refinando el factor de deriva hasta que el Reloj del Hardware se corrija correctamente al inicio. Para verificar esto, primero asegúrese de que la Hora del Sistema sea correcta antes de apagar y luego use sntp, o date -Ins y un reloj de precisión, inmediatamente después de iniciar.

LOCAL vs UTC

Mantener el Reloj del Hardware en una escala de tiempo local provoca resultados inconsistentes en el horario de verano:

•Si Linux se ejecuta durante un cambio de horario de verano, la hora escrita en el Reloj del Hardware se ajustará al cambio.
•Si Linux NO se ejecuta durante un cambio de horario de verano, la hora leída del Reloj del Hardware NO se ajustará al cambio.

El Reloj del Hardware en un sistema compatible con ISA solo guarda una fecha y hora, no tiene concepto de zona horaria ni de horario de verano. Por lo tanto, cuando se le dice a hwclock que está en hora local, asume que está en la hora local 'correcta' y no realiza ningún ajuste a la hora leída de él.

Linux maneja los cambios de horario de verano de forma transparente solo cuando el Reloj del Hardware se mantiene en la escala de tiempo UTC. Hacerlo es fácil para los administradores del sistema, ya que hwclock utiliza la hora local para su salida y como argumento para la opción --date.

Los sistemas POSIX, como Linux, están diseñados para que el Reloj del Sistema funcione en la escala de tiempo UTC. El propósito del Reloj del Hardware es inicializar el Reloj del Sistema, por lo que mantenerlo también en UTC tiene sentido.

Linux, sin embargo, intenta acomodar que el Reloj del Hardware esté en la escala de tiempo local. Esto es principalmente para la configuración de arranque dual con versiones anteriores de MS Windows. A partir de Windows 7, la clave de registro RealTimeIsUniversal debería funcionar correctamente para que su Reloj del Hardware pueda mantenerse en UTC.

POSIX vs 'RIGHT'

Una discusión sobre la configuración de fecha y hora estaría incompleta sin abordar las zonas horarias; esto está en gran medida bien cubierto por tzset(3). Un área que parece no tener documentación es el directorio 'right' de la Base de Datos de Zonas Horarias, a veces llamada tz o zoneinfo.

Hay dos bases de datos separadas en el sistema zoneinfo, posix y 'right'. 'Right' (ahora llamado zoneinfo-leaps) incluye segundos intercalares y posix no. Para usar la base de datos 'right', el Reloj del Sistema debe estar configurado en (UTC + segundos intercalares), que es equivalente a (TAI - 10). Esto permite calcular el número exacto de segundos entre dos fechas que cruzan una época de segundo intercalar. Luego, el Reloj del Sistema se convierte a la hora civil correcta, incluida la UTC, utilizando los archivos de zona horaria 'right' que restan los segundos intercalares. Nota: esta configuración se considera experimental y se sabe que tiene problemas.

Para configurar un sistema para usar una base de datos en particular, todos los archivos ubicados en su directorio deben copiarse a la raíz de /usr/share/zoneinfo. Los archivos nunca se usan directamente desde los subdirectorios posix o 'right', por ejemplo, TZ='right/Europe/Dublin'. Este hábito se estaba volviendo tan común que el proyecto upstream zoneinfo reestructuró el árbol de archivos del sistema moviendo los subdirectorios posix y 'right' fuera del directorio zoneinfo y a directorios hermanos:

/usr/share/zoneinfo, /usr/share/zoneinfo-posix, /usr/share/zoneinfo-leaps

Desafortunadamente, algunas distribuciones de Linux lo están cambiando de nuevo a la antigua estructura de árbol en sus paquetes. Por lo tanto, persiste el problema de que los administradores del sistema accedan al subdirectorio 'right'. Esto hace que la zona horaria del sistema se configure para incluir segundos intercalares, mientras que la base de datos zoneinfo aún está configurada para excluirlos. Luego, cuando una aplicación como un reloj mundial necesita el archivo de zona horaria South_Pole; o un MTA de correo, o hwclock necesita el archivo de zona horaria UTC; los obtiene de la raíz de /usr/share/zoneinfo, porque eso es lo que se supone que deben hacer. Esos archivos excluyen los segundos intercalares, pero el Reloj del Sistema ahora los incluye, causando una conversión de hora incorrecta.

Intentar mezclar y combinar archivos de estas bases de datos separadas no funcionará, porque cada una requiere que el Reloj del Sistema use una escala de tiempo diferente. La base de datos zoneinfo debe estar configurada para usar posix o 'right', como se describe anteriormente, o asignando una ruta de base de datos a la variable de entorno TZDIR.
