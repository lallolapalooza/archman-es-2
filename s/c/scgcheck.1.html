SCGCHECK(1) COMANDOS DE USUARIO de Schily SCGCHECK(1)

NOMBRE

scgcheck - comprobar y validar la ABI de libscg

SINOPSIS

scgcheck [ opciones ]

DESCRIPCIÓN

Scgcheck se utiliza para comprobar y verificar la Interfaz Binaria de Aplicación (ABI) de libscg.

Nombre de dispositivos

La mayoría de los usuarios no necesitan preocuparse en absoluto por el nombre de los dispositivos, ya que en modo -auto, scgcheck implementa el soporte de target automático y encuentra automáticamente una unidad de prueba en caso de que solo haya disponible una unidad tipo CD-ROM en el sistema.

OPCIONES

-version
Imprime información de la versión y sale.
-auto
En lugar de pedir confirmación antes de ejecutar cada prueba, scgcheck intenta realizar una prueba totalmente automatizada.
dev=destino
Establece el destino SCSI para el dispositivo, véanse las notas anteriores. Una especificación típica de dispositivo de destino es dev=1,6,0 . Si se debe proporcionar un nombre de archivo junto con la especificación numérica de destino, el nombre de archivo depende de la implementación. El nombre de archivo correcto en este caso se puede encontrar en los manuales específicos del sistema operativo de destino. En un sistema FreeBSD sin soporte CAM, necesita usar el dispositivo de control (por ejemplo, /dev/rcd0.ctl). Una especificación de dispositivo correcta en este caso podría ser dev=/dev/rcd0.ctl:@ .

Direccionamiento SCSI general
El dispositivo de destino de la opción dev= se refiere a scsibus/target/lun del dispositivo. La comunicación en SunOS se realiza con el controlador general SCSI scg. Otros sistemas operativos utilizan una simulación de biblioteca de este controlador. La sintaxis posible es: dev= scsibus,target,lun o dev= target,lun. En este último caso, el dispositivo debe estar conectado al bus SCSI predeterminado de la máquina. Scsibus, target y lun son números enteros. Algunos sistemas operativos o implementaciones de transporte SCSI pueden requerir que se proporcione un nombre de archivo adicional. En este caso, la sintaxis correcta para el dispositivo es: dev= nombre_dispositivo:scsibus,target,lun o dev= nombre_dispositivo:target,lun. Si el nombre del nodo dispositivo especificado en dicho sistema se refiere a un único dispositivo SCSI, se puede utilizar una forma abreviada en la forma dev= nombre_dispositivo:@ o dev= nombre_dispositivo:@,lun en lugar de dev= nombre_dispositivo:scsibus,target,lun.

Direccionamiento SCSI remoto
Para acceder a dispositivos SCSI remotos, necesita anteponer el nombre del dispositivo SCSI con un indicador de dispositivo remoto. El indicador de dispositivo remoto es REMOTE:usuario@host: o REMOTE:host: Un nombre de dispositivo SCSI remoto válido puede ser: REMOTE:usuario@host: para permitir el escaneo remoto del bus SCSI o REMOTE:usuario@host:1,0,0 para acceder al dispositivo SCSI en host conectado al bus SCSI n.º 1, destino 0, lun 0. Para permitir el acceso remoto a un host específico, el programa rscsi(1) debe estar presente y configurado en el host.

Transportes SCSI alternativos
Las unidades ATAPI son simplemente unidades SCSI que utilizan inherentemente la interfaz de paquetes ATA como capa de transporte de comandos SCSI integrada en el transporte IDE (ATA). Es posible que necesite especificar una capa de transporte alternativa en la línea de comandos si su sistema operativo no implementa un subsistema de controlador de kernel completamente integrado que permita acceder a cualquier unidad utilizando comandos SCSI a través de una única interfaz de usuario.

Para acceder a dispositivos SCSI a través de capas de transporte alternativas, necesita anteponer el nombre del dispositivo SCSI con un indicador de capa de transporte. El indicador de capa de transporte puede ser algo como USCSI: o ATAPI:. Para obtener una lista de capas de transporte compatibles para su plataforma, use dev= AYUDA:

Antecedentes de portabilidad
Para hacer que scgcheck sea portable a todas las plataformas UNIX, se prefiere la sintaxis dev= nombre_dispositivo:scsibus,target,lun, ya que oculta el conocimiento específico del sistema operativo sobre los nombres de los dispositivos al usuario. Un sistema operativo específico puede no soportar necesariamente una forma de especificar un nombre de archivo de dispositivo real ni una forma de especificar scsibus,target,lun.

Scsibus 0 es el bus SCSI predeterminado en la máquina. Observe los mensajes de arranque para obtener más información o consulte /var/adm/messages para obtener más información sobre la configuración SCSI de su máquina. Si tiene problemas para determinar qué valores para scsibus,target,lun deben usarse, pruebe la opción -scanbus de scgcheck descrita a continuación.

Modo Autotarget
Si no está presente ninguna opción dev=, o si solo contiene un especificador de transporte pero ninguna notación de dirección, scgcheck intenta escanear el espacio de direcciones SCSI en busca de unidades de CD-ROM. Si se encuentra exactamente una, se utiliza de forma predeterminada.

timeout=#
Establece el valor del tiempo de espera predeterminado del comando SCSI a # segundos. El tiempo de espera predeterminado del comando SCSI es el tiempo de espera mínimo utilizado para enviar comandos SCSI. Si un comando SCSI falla debido a un tiempo de espera, puede intentar aumentar el tiempo de espera predeterminado del comando SCSI por encima del valor de tiempo de espera del comando fallido. Si el comando se ejecuta correctamente con un tiempo de espera de comando aumentado, informe el mejor valor de tiempo de espera y el comando correspondiente al autor del programa. Si no hay ninguna opción timeout presente, se utiliza un tiempo de espera predeterminado de 40 segundos.
debug=#, -d
Establece el valor de depuración miscelánea en # (con debug=#) o incrementa el nivel de depuración miscelánea en uno (con -d). Si especifica -dd, esto equivale a debug=2. Esto puede ayudar a encontrar problemas al abrir un controlador para libscg, así como con los tamaños y tipos de sector. Usar -debug ralentiza el proceso y puede ser la causa de una subejecución de búfer.
kdebug=#, kd=#
Indica al controlador scg que modifique el valor de depuración del kernel mientras se ejecutan los comandos SCSI.
scgopts=lista
Una lista separada por comas de opciones SCSI que son manejadas por libscg. Las opciones implementadas pueden actualizarse independientemente de las aplicaciones. Actualmente, se admite una opción: ignore-resid para solucionar un error del kernel de Linux.
-silent, -s
No imprima un informe de estado para los comandos SCSI fallidos.
-v
Incrementa en uno el nivel de verbosidad general. Esto se utiliza, por ejemplo, para mostrar el progreso del proceso.
-V
Incrementa en uno el nivel de verbosidad con respecto al transporte del comando SCSI. Esto ayuda a depurar problemas durante el proceso que ocurren en el grabador de CD. Si obtiene mensajes de error incomprensibles, debe utilizar esta opción para obtener una salida más detallada. -VV mostrará además el contenido del búfer de datos. Usar -V o -VV ralentiza el proceso.
f=archivo
Especifica el archivo de registro a utilizar en lugar de check.log.

NOTAS

Afortunadamente, el controlador sg en Linux tiene varios errores graves:

•
No puede saber si un comando SCSI no se pudo enviar en absoluto.
•
No puede obtener el byte de estado SCSI. Scgcheck por esta razón no puede informar de comandos SCSI fallidos en algunas situaciones.
•
No puede obtener el recuento real de DMA de la transferencia. Scgcheck no puede decirle si hay un recuento residual de DMA.
•
No puede obtener el número de bytes válidos en los datos de solicitud automática. Scgcheck no puede decirle si el dispositivo no transfiere ningún dato de solicitud en absoluto.
•
Recupera muy pocos datos en la solicitud automática de sentido (CCS/SCSI-2/SCSI-3 requiere >= 18).

DIAGNÓSTICOS

Un mensaje de error típico para un comando SCSI se parece a:

scgcheck: I/O error. test unit ready: scsi sendcmd: no error
CDB:  00 20 00 00 00 00
status: 0x2 (CHECK CONDITION)
Sense Bytes: 70 00 05 00 00 00 00 0A 00 00 00 00 25 00 00 00 00 00
Sense Key: 0x5 Illegal Request, Segment 0
Sense Code: 0x25 Qual 0x00 (unidad lógica no soportada) Fru 0x0
Sense flags: Blk 0 (no válido)
cmd finished after 0.002s timeout 40s
La primera línea proporciona información sobre el transporte del comando. El texto después de los dos puntos da el texto del error para la llamada al sistema desde la perspectiva del kernel. Normalmente es: I/O error a menos que ocurran otros problemas. Las siguientes palabras contienen una breve descripción del comando SCSI que falla. El resto de la línea le indica si hubo algún problema para el transporte del comando a través del bus SCSI. fatal error significa que no fue posible transportar el comando (es decir, no hay dispositivo presente en la dirección SCSI solicitada).

La segunda línea imprime el bloque de descriptores de comandos SCSI para el comando fallido.

La tercera línea proporciona información sobre el código de estado SCSI devuelto por el comando, si el transporte del comando tiene éxito. Esta es información de error del dispositivo SCSI.

La cuarta línea es un volcado hexadecimal de la información de solicitud automática de sentido para el comando.

La quinta línea es el texto del error para la clave de sentido si está disponible, seguido del número de segmento que solo es válido si el comando fue un comando de copia. Si el mensaje de error no está directamente relacionado con el comando actual, se añade el texto deferred error.

La sexta línea es el texto del error para el código de sentido y el calificador de sentido si están disponibles. Si se conoce el tipo de dispositivo, los datos de sentido se decodifican de tablas en scsierrs.c. El texto va seguido del valor de error de una unidad reemplazable en campo.

La séptima línea imprime el número de bloque que está relacionado con el comando fallido y el texto para varios indicadores de error. El número de bloque puede no ser válido.

La octava línea informa del tiempo de espera establecido para este comando y el tiempo que realmente necesitó el comando para completarse.
