scr_dump(5) Formatos de archivo scr_dump(5)

NOMBRE

scr_dump - volcado de pantalla de curses

DESCRIPCIÓN

La biblioteca curses proporciona a las aplicaciones la capacidad de escribir el contenido de una ventana a un archivo externo usando scr_dump o putwin, y leerlo de nuevo usando scr_restore o getwin.

Las funciones putwin y getwin hacen el trabajo; mientras que scr_dump y scr_restore guardan y restauran convenientemente toda la pantalla, es decir, stdscr.

ncurses6

Una implementación de larga data de volcado de pantalla fue revisada con ncurses6 para remediar problemas con el enfoque anterior:

•
Se escribe un "número mágico" al principio del archivo de volcado, permitiendo a las aplicaciones (como file(1)) reconocer los archivos de volcado de curses.
Dado que ncurses6 utiliza un nuevo formato, que requiere un nuevo número mágico que no era utilizado por otras aplicaciones. Este número de 16 bits no se utilizaba:
0x8888 (octal “\210\210”)

pero para estar más seguro, se eligió este número de 32 bits:

0x88888888 (octal “\210\210\210\210”)

Este es el patrón enviado a los mantenedores del programa file:

#
# ncurses5 (y anteriores) no usaban un número mágico,
# haciendo que los volcados de pantalla fueran "datos".
#
# ncurses6 (2015) usa este formato, ignorando el orden de bytes
0    string    \210\210\210\210ncurses    imagen de pantalla ncurses6
#
•
Los volcados de pantalla se escriben en forma textual, de modo que los tamaños de datos internos no están directamente relacionados con el formato de volcado, y permitiendo a la biblioteca leer volcados de configuraciones de caracteres estrechos o anchos.
La configuración de biblioteca *estrecha* almacena caracteres y atributos de video en un chtype de 32 bits, mientras que la biblioteca de *caracteres anchos* almacena esta información en la estructura cchar_t, que es mucho más grande que 32 bits.
  • Es posible leer un volcado de pantalla en una terminal con un tamaño de pantalla diferente, ya que la biblioteca trunca o rellena la pantalla según sea necesario.
  • El getwin de ncurses6 lee los volcados de pantalla heredados de ncurses5.

ncurses5 (Legado)

La función de volcado de pantalla se añadió a ncurses en junio de 1995. Aunque hubo correcciones y mejoras en años posteriores, el esquema básico no cambió:

  • La estructura WINDOW se escribía en formato binario.
  • La estructura WINDOW hace referencia a líneas de datos, que se escribían como una matriz de datos binarios después de la WINDOW.
  • Cuando getwin restauraba la ventana, realizaba un seguimiento de los desplazamientos en la matriz de datos de línea y ajustaba la estructura WINDOW que se leía de nuevo en memoria.

Esto es similar a Unix System V, pero no escribe un "número mágico" para identificar el formato del archivo.

PORTABILIDAD

No existe un formato estándar para los volcados de pantalla de curses. Una breve encuesta de las implementaciones existentes sigue.

X/Open Curses

X/Open Curses, Issue 7 especifica poco. Dice (énfasis en negrita añadido)

“[l]a función getwin() lee datos relacionados con la ventana almacenados en el archivo por putwin(). La función luego crea e inicializa una nueva ventana utilizando esos datos.

La función putwin() escribe todos los datos asociados con win en el flujo stdio al que apunta filep, utilizando un formato no especificado. Esta información puede recuperarse más tarde utilizando getwin().”

A mediados de la década de 1990, cuando se escribió el documento X/Open Curses, todavía existían sistemas System V que utilizaban bibliotecas curses más antiguas y menos capaces. El curses de BSD no era relevante para X/Open porque no cumplía los criterios de conformidad de nivel básico; véase ncurses(3X).

System V

El curses de System V identificaba el formato del archivo escribiendo un "número mágico" al principio del volcado. Los datos de WINDOW y las líneas de texto siguen, todo en formato binario.

El curses de Solaris tiene las siguientes definiciones.

/* número mágico de terminfo */
#define MAGNUM  0432
/* número mágico de volcado de pantalla curses */
#define SVR2_DUMP_MAGIC_NUMBER  0433
#define SVR3_DUMP_MAGIC_NUMBER  0434

Es decir, la función se introdujo probablemente en SVr2 (1984) y se mejoró en SVr3 (1987). El curses de Solaris no tiene número mágico para SVr4 (1989). Otros sistemas operativos System V (AIX y HP-UX) utilizan un número mágico que correspondería a lo siguiente.

/* número mágico de volcado de pantalla curses */
#define SVR4_DUMP_MAGIC_NUMBER  0435

Ese número octal en bytes es 001, 035. Dado que la mayoría de los proveedores de Unix en ese momento utilizaban hardware de orden de bytes big-endian, el número mágico se escribe con el byte de orden superior primero.

\001\035

Después del número mágico, la estructura WINDOW y los datos de línea se escriben en formato binario. Si bien el número mágico utilizado por estos sistemas puede observarse con od(1), ninguno de ellos documenta el formato utilizado para los volcados de pantalla.

Tampoco utilizan un formato idéntico, incluso dentro de la familia System V. El programa de prueba savescreen de ncurses se utilizó para recopilar información para esta página del manual. Produjo volcados de diferentes tamaños (todos en hardware de 64 bits, en pantallas de 40x80):

  • AIX (51817 bytes)
  • HP-UX (90093 bytes)
  • Solaris 10 (13273 bytes)
  • ncurses5 (12888 bytes)

Solaris

Como se señaló anteriormente, el curses de Solaris no tiene un número mágico que corresponda al curses SVr4. Esto es extraño, ya que Solaris fue el primer sistema operativo que cumplió las directrices SVr4. Solaris además proporciona dos versiones de curses.

  • La biblioteca curses predeterminada utiliza el número mágico SVr3.
  • Una biblioteca curses alternativa (que denominamos xcurses), disponible en /usr/xpg4, utiliza un formato textual sin número mágico.
Según su aviso de copyright, esta biblioteca xcurses fue desarrollada por MKS (Mortice Kern Systems) de 1990 a 1995.
Al igual que ncurses6, incluye una cabecera con parámetros. A diferencia de ncurses6, el contenido de la ventana se escribe pieza por pieza, con coordenadas y atributos para cada fragmento de texto en lugar de escribir toda la ventana de arriba a abajo.

PDCurses

PDCurses añadió soporte para volcados de pantalla en la versión 2.7 (2005). Al igual que System V y ncurses5, escribe la estructura WINDOW en binario, pero comienza el archivo con su identificador de tres bytes "PDC", seguido de un número de versión de un byte.

“PDC\001”

NetBSD

A partir de abril de 2017, el curses de NetBSD no soporta scr_dump y scr_restore (o scr_init, scr_set), aunque tiene putwin y getwin.

Al igual que ncurses5, el putwin de NetBSD no identifica sus volcados con un número mágico útil. Escribe

  • las versiones principal y secundaria de la biblioteca compartida de curses como los dos primeros bytes (por ejemplo, 7 y 1),
  • seguido de un volcado binario de la WINDOW,
  • algunos datos para caracteres anchos referenciados por la estructura WINDOW, y
  • finalmente, líneas como hacen otras implementaciones.

EJEMPLOS

Dado un programa simple que escribe texto en la pantalla (y por el bien del ejemplo, limitando el tamaño de la pantalla a 10x20):

#include &l
scr_dump(5) — ncurses 6.5

NAME

scr_dump, scr_restore, scr_init - screen dump and restore routines

SYNOPSIS

#include <curses.h>

int scr_dump(const char *filename);
int scr_restore(const char *filename);
int scr_init(const char *filename, FILE *file);

DESCRIPTION

The scr_dump function writes the contents of the current screen, including cursor position and attributes, to the specified filename. The format is specific to the implementation, and is not guaranteed to be stable between releases.

The scr_restore function reads screen contents from the specified filename, and restores the screen to that state. This implies that the screen is cleared, and then filled from the file. This is useful for saving and restoring the screen in the middle of a program's execution.

The scr_init function is similar to scr_restore, but it uses the given file pointer instead of a filename. This is useful if the screen dump is stored in memory or on some other stream.

These functions are useful for debugging or for creating simple screen capture utilities. The format of the screen dump is not intended for use by applications.

PORTABILITY

The format of the screen dump is not portable. The scr_dump(5) routine writes a human-readable screen dump to the file. This format is used by ncurses, and is described in the following section.

The format for screen dumps differs between implementations of curses. The following example shows a dump from a simple program:

#include <curses.h>
int
main(void)
{
    putenv("LINES=10");
    putenv("COLUMNS=20");
    initscr();
    start_color();
    init_pair(1, COLOR_WHITE, COLOR_BLUE);
    init_pair(2, COLOR_RED, COLOR_BLACK);
    bkgd(COLOR_PAIR(1));
    move(4, 5);
    attron(A_BOLD);
    addstr("Hello");
    move(5, 5);
    attroff(A_BOLD);
    attrset(A_REVERSE | COLOR_PAIR(2));
    addstr("World!");
    refresh();
    scr_dump("foo.out");
    endwin();
    return 0;
}

The first four octal escapes are actually nonprinting characters, while the remainder of the file is printable text. You may notice:

  • The actual color pair values are not written to the file.
  • All characters are shown in printable form; spaces are “\s” to ensure they are not overlooked.
  • Attributes are written in escaped curly braces, e.g., “{BOLD}”, and may include a color pair (C1 or C2 in this example).
  • The parameters in the header are written out only if they are nonzero. When reading back, order does not matter.
