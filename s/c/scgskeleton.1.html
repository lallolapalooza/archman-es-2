SCGSKELETON(1L) COMANDOS DE USUARIO de Schily SCGSKELETON(1L)

NOMBRE

scgskeleton - Programa esqueleto para transporte SCSI usando libscg

SINOPSIS

scgskeleton dev=dispositivo [ opciones ]

DESCRIPCIÓN

Scgskeleton es un programa esqueleto para demostrar las interfaces y capacidades de la biblioteca de transporte SCSI libscg.

Nomenclatura de dispositivos

Para obtener una lista de posibles parámetros de nombre de dispositivo, ejecute scgskeleton -scanbus o scgskeleton dev=help y luego use el parámetro dev= correcto basado en la lista de dispositivos.

OPCIONES

-ayuda
Imprime un resumen corto de las opciones de p y sale.
-version
Imprime información de versión y sale.
dev=objetivo
Establece el objetivo SCSI para el grabador de CD/DVD/Blu-ray, ver notas arriba. Una especificación de dispositivo de objetivo típica es dev=1,6,0. Si se debe proporcionar un nombre de archivo junto con la especificación numérica del objetivo, el nombre de archivo depende de la implementación. El nombre de archivo correcto en este caso se puede encontrar en los manuales específicos del sistema operativo de destino. En un sistema FreeBSD sin soporte CAM, necesita usar el dispositivo de control (por ejemplo, /dev/rcd0.ctl). Una especificación de dispositivo correcta en este caso puede ser dev=/dev/rcd0.ctl:@.

Direccionamiento SCSI general
El dispositivo objetivo para la opción dev= se refiere a scsibus/objetivo/lun del grabador de CD/DVD/Blu-ray. La comunicación en SunOS se realiza con el controlador general SCSI scg. Otros sistemas operativos utilizan una simulación de biblioteca de este controlador. La sintaxis posible es: dev= scsibus,objetivo,lun o dev= objetivo,lun. En este último caso, el grabador de CD/DVD/Blu-ray debe estar conectado al bus SCSI predeterminado de la máquina. Scsibus, objetivo y lun son números enteros. Algunos sistemas operativos o implementaciones de transporte SCSI pueden requerir especificar un nombre de archivo adicionalmente. En este caso, la sintaxis correcta para el dispositivo es: dev= nombredispositivo:scsibus,objetivo,lun o dev= nombredispositivo:objetivo,lun. Si el nombre del nodo del dispositivo especificado en dicho sistema se refiere a exactamente un dispositivo SCSI, se puede usar una forma abreviada en la forma dev= nombredispositivo:@ o dev= nombredispositivo:@,lun en lugar de dev= nombredispositivo:scsibus,objetivo,lun.

Direccionamiento SCSI remoto
Para acceder a dispositivos SCSI remotos, necesita anteponer el nombre del dispositivo SCSI con un indicador de dispositivo remoto. El indicador de dispositivo remoto es REMOTE:usuario@host: o REMOTE:host:. Un nombre de dispositivo SCSI remoto válido puede ser: REMOTE:usuario@host: para permitir el escaneo remoto del bus SCSI o REMOTE:usuario@host:1,0,0 para acceder al dispositivo SCSI en host conectado al bus SCSI # 1, objetivo 0, lun 0. Para permitir el acceso remoto a un host específico, el programa rscsi(1) debe estar presente y configurado en el host.

Transportes SCSI alternativos
Las unidades ATAPI son solo unidades SCSI que utilizan inherentemente la interfaz de paquetes ATA como capa de transporte de comandos SCSI incorporada en el transporte IDE (ATA). Es posible que deba especificar una capa de transporte alternativa en la línea de comandos si su sistema operativo no implementa un subsistema de controladores del kernel totalmente integrado que permita acceder a cualquier unidad utilizando comandos SCSI a través de una única interfaz de usuario.

Para acceder a dispositivos SCSI a través de capas de transporte alternativas, necesita anteponer el nombre del dispositivo SCSI con un indicador de capa de transporte. El indicador de capa de transporte puede ser algo como USCSI: o ATAPI:. Para obtener una lista de capas de transporte compatibles para su plataforma, use dev= HELP:

Antecedentes de portabilidad
Para hacer que scgskeleton sea portable a todas las plataformas UNIX, se prefiere la sintaxis dev= nombredispositivo:scsibus,objetivo,lun, ya que oculta el conocimiento específico del sistema operativo sobre los nombres de los dispositivos al usuario. Un sistema operativo específico puede no admitir necesariamente una forma de especificar un nombre de archivo de dispositivo real ni una forma de especificar scsibus,objetivo,lun.

El scsibus 0 es el bus SCSI predeterminado en la máquina. Observe los mensajes de arranque para obtener más información o busque en /var/adm/messages para obtener más información sobre la configuración SCSI de su máquina. Si tiene problemas para determinar qué valores para scsibus,objetivo,lun se deben usar, pruebe la opción -scanbus de scgskeleton descrita a continuación.

Uso de nombres lógicos para dispositivos
Si no hay una opción dev presente, scgskeleton intentará obtener el dispositivo del entorno CDR_DEVICE.

Si existe un archivo /etc/default/cdrecord, y si el argumento de la opción dev= o el entorno CDR_DEVICE no contienen los caracteres ',', '/', '@' o ':', se interpreta como un nombre de etiqueta de dispositivo definido en el archivo /etc/default/cdrecord (ver sección ARCHIVOS).

Modo Autotarget
Si no hay una opción dev= y no hay un entorno CDR_DEVICE presente, o si solo contiene un especificador de transporte pero no una notación de dirección, scgskeleton intenta escanear el espacio de direcciones SCSI en busca de unidades de CD-ROM. Si se encuentra exactamente una, se usa por defecto.

timeout=#
Establece el valor de tiempo de espera predeterminado del comando SCSI a # segundos. El tiempo de espera predeterminado del comando SCSI es el tiempo de espera mínimo utilizado para enviar comandos SCSI. Si un comando SCSI falla debido a un tiempo de espera, puede intentar aumentar el tiempo de espera predeterminado del comando SCSI por encima del valor de tiempo de espera del comando fallido. Si el comando se ejecuta correctamente con un tiempo de espera de comando aumentado, informe el valor de tiempo de espera mejorado y el comando correspondiente al autor del programa. Si no hay una opción timeout presente, se utiliza un tiempo de espera predeterminado de 40 segundos.
debug=#, -d
Establece el valor de depuración misceláneo en # (con debug=#) o incrementa el nivel de depuración misceláneo en uno (con -d). Si especifica -dd, esto equivale a debug=2. Esto puede ayudar a encontrar problemas al abrir un controlador para libscg, así como con los tamaños y tipos de sectores. Usar -debug ralentiza el proceso y puede ser la razón de una subejecución del búfer.
kdebug=#, kd=#
Indica al controlador scg que modifique el valor de depuración del kernel mientras se ejecutan los comandos SCSI.
-silencioso, -s
No imprime un informe de estado para los comandos SCSI fallidos.
-v
Incrementa el nivel de verbosidad general en uno. Esto se usa, por ejemplo, para mostrar el progreso del proceso.
-V
Incrementa el nivel de verbosidad con respecto al transporte del comando SCSI en uno. Esto ayuda a depurar problemas durante el proceso que ocurren en el grabador de CD. Si recibe mensajes de error incomprensibles, debe usar esta bandera para obtener una salida más detallada. -VV mostrará el contenido del búfer de datos además. Usar -V o -VV ralentiza el proceso. -scanbus Escanea todos los dispositivos SCSI en todos los buses SCSI e imprime las cadenas de consulta. Esta opción se puede usar para encontrar la dirección SCSI de los dispositivos en un sistema. Los números impresos como etiquetas se calculan mediante: bus * 100 + target
scgopts=lista
Una lista separada por comas de opciones SCSI que son manejadas por libscg. Las opciones implementadas pueden actualizarse independientemente de las aplicaciones. Actualmente, se admite una opción: ignore-resid para solucionar un error del kernel de Linux.
ts=#
Establece el tamaño máximo de transferencia para un solo comando SCSI

NAME

scgskeleton

skeleton for SCSI command generation

SYNOPSIS

scgskeleton [ -f fs ] [ -b bs ] [ -t ts ] [ -d ] [ -v ] [ -i scsi-device ] [ -p scsi-device ] [ -m scsi-device ] [ -h ] [ device-name ...]

DESCRIPTION

scgskeleton is a skeleton program that shows how to implement SCSI command generation. It is a part of the cdrecord package and is intended for people who want to write their own SCSI programs.

The program supports remote SCSI access (see ENVIRONMENT section).

OPTIONS

The following options are supported:

-f fs
Set the block size for SCSI commands to fs bytes. The default is 2048 bytes. This is the size that is used for CDBs that specify a block length.
-b bs
Set the block size for SCSI commands to bs bytes. The default is 2048 bytes. This is the size that is used for CDBs that specify a block length.
-t ts
Set the transfer size for SCSI commands to ts bytes. The default is 256 kB. The syntax for the ts= option is the same as for cdrecord fs=# or sdd bs=#.
-d
Dump all SCSI commands that are sent to the SCSI device.
-v
Verbose mode. This option increments the verbosity level of the message output.
-i scsi-device
Initialize the SCSI device specified by scsi-device . This option is not used by scgskeleton but is passed to the underlying SCSI library.
-p scsi-device
Probe the SCSI device specified by scsi-device . This option is not used by scgskeleton but is passed to the underlying SCSI library.
-m scsi-device
Mount the SCSI device specified by scsi-device . This option is not used by scgskeleton but is passed to the underlying SCSI library.
-h
Print help message and exit.

If no ts= option has been specified, scgskeleton defaults to a transfer size of 256 kB. If libscg gets lower values from the operating system, the value is reduced to the maximum value that is possible with the current operating system. Sometimes, it may help to further reduce the transfer size or to enhance it, but note that it may take a long time to find a better value by experimenting with the ts= option.

EXAMPLES

ENVIRONMENT

RSH
If the RSH environment is present, the remote connection will not be created via rcmd(3) but by calling the program pointed to by RSH. Use e.g. RSH=/usr/bin/ssh to create a secure shell connection.

Note that this forces cdrecord to create a pipe to the rsh(1) program and disallows cdrecord to directly access the network socket to the remote server. This makes it impossible to set up performance parameters and slows down the connection compared to a root initiated rcmd(3) connection.

RSCSI
If the RSCSI environment is present, the remote SCSI server will not be the program /opt/schily/sbin/rscsi but the program pointed to by RSCSI. Note that the remote SCSI server program name will be ignored if you log in using an account that has been created with a remote SCSI server program as login shell.

SEE ALSO

cdrecord(1), scg(7), rcmd(3), ssh(1).

DIAGNOSTICS

A typical error message for a SCSI command looks like:

scgskeleton: I/O error. test unit ready: scsi sendcmd: no error
CDB:  00 20 00 00 00 00
status: 0x2 (CHECK CONDITION)
Sense Bytes: 70 00 05 00 00 00 00 0A 00 00 00 00 25 00 00 00 00 00
Sense Key: 0x5 Illegal Request, Segment 0
Sense Code: 0x25 Qual 0x00 (logical unit not supported) Fru 0x0
Sense flags: Blk 0 (not valid)
cmd finished after 0.002s timeout 40s
The first line gives information about the transport of the command. The text after the first colon gives the error text for the system call from the view of the kernel. It usually is: I/O error unless other problems happen. The next words contain a short description for the SCSI command that fails. The rest of the line tells you if there were any problems for the transport of the command over the SCSI bus. fatal error means that it was not possible to transport the command (i.e. no device present at the requested SCSI address).

The second line prints the SCSI command descriptor block for the failed command.

The third line gives information on the SCSI status code returned by the command, if the transport of the command succeeds. This is error information from the SCSI device.

The fourth line is a hex dump of the auto request sense information for the command.

The fifth line is the error text for the sense key if available, followed by the segment number that is only valid if the command was a copy command. If the error message is not directly related to the current command, the text deferred error is appended.

The sixth line is the error text for the sense code and the sense qualifier if available. If the type of the device is known, the sense data is decoded from tables in scsierrs.c . The text is followed by the error value for a field replaceable unit.

The seventh line prints the block number that is related to the failed command and text for several error flags. The block number may not be valid.

The eight line reports the timeout set up for this command and the time that the command really needed to complete.
