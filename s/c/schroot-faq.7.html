NOMBRE

schroot - preguntas frecuentes

DESCRIPCIÓN

Esta página del manual cubre varias preguntas frecuentes sobre la configuración y el uso de schroot.

CONFIGURACIÓN

¿Por qué schroot sobrescribe los archivos de configuración en el chroot?

Por defecto, schroot copia las bases de datos NSS del sistema (‘passwd’, ‘shadow’, ‘group’, ‘gshadow’, ‘services’, ‘protocols’, ‘networks’, y ‘hosts’, etc.) al chroot. La razón de esto es que el entorno chroot no es un sistema completamente separado, y copiarlos los mantiene sincronizados. Sin embargo, esto no siempre es deseable, particularmente si la instalación de un paquete en el chroot crea usuarios y grupos del sistema que no están presentes en el host, ya que estos desaparecerán la próxima vez que se copien las bases de datos.

La solución sugerida aquí es deshabilitar la copia. Esto se puede lograr estableciendo la clave setup.nssdatabases como vacía en schroot.conf. En versiones anteriores de schroot, esto se hacía comentando el archivo NSSDATABASES para el chroot (/etc/schroot/default/config por defecto). La lista de bases de datos también se puede personalizar editando el archivo que contiene la lista de bases de datos (/etc/schroot/default/nssdatabases por defecto).

En el futuro, trabajaremos en un esquema mejor para mantener las bases de datos del host y del chroot sincronizadas que pueda fusionar entradas en lugar de sobrescribir toda la base de datos, lo que preservaría los cambios específicos del chroot.

¿Debería usar el tipo de chroot simple o directorio?

Estos dos tipos de chroot son básicamente equivalentes, ya que ambos son solo directorios en el sistema de archivos. 'plain' es muy simple y no realiza ninguna tarea de configuración; la única razón por la que querrías usarlo es si estás actualizando desde un programa como dchroot(1) o chroot(8) que no hacen nada más que ejecutar un comando o shell en un directorio. Por otro lado, los chroots de directorio sí ejecutan scripts de configuración, que pueden montar sistemas de archivos adicionales y realizar otras tareas de configuración.

CONFIGURACIÓN AVANZADA

¿Qué son las instantáneas y las uniones?

Algunos tipos de chroot soportan clonación. Esto significa que cuando inicias una sesión, obtienes una copia del chroot que dura solo mientras la sesión está activa. Esto es útil cuando deseas una copia limpia y temporal de un sistema para una sola tarea, que luego se elimina automáticamente cuando terminas con ella. Por ejemplo, los demonios de construcción de paquetes de Debian ejecutan sbuild(1) para construir paquetes de Debian, y este programa usa schroot para crear un entorno de construcción limpio para cada paquete. Sin las instantáneas, el chroot necesitaría ser restaurado a su estado inicial al final de cada construcción para prepararlo para la siguiente, y cualquier residuo de eliminaciones de paquetes o construcciones anteriores podría interferir con la siguiente construcción.

El método de instantáneas más utilizado es usar instantáneas LVM (tipo de chroot 'lvm-snapshot'). En este caso, el chroot debe existir en un volumen lógico LVM (LV); las instantáneas de un LV pueden crearse con lvcreate(8) durante la configuración de la sesión chroot. Sin embargo, estas consumen mucho espacio en disco. Un método más nuevo es usar instantáneas Btrfs que consumen mucho menos espacio en disco (tipo de chroot 'btrfs-snapshot') y pueden ser más fiables que las instantáneas LVM. Sin embargo, Btrfs sigue siendo experimental, pero se espera que se convierta en el método recomendado a medida que madura.

Las uniones son una alternativa a las instantáneas. En esta situación, en lugar de crear una copia del sistema de archivos del chroot, superponemos un sistema de archivos temporal de solo lectura/escritura sobre el sistema de archivos del chroot para que cualquier modificación se almacene en la capa superpuesta, dejando el sistema de archivos del chroot original intacto. El kernel de Linux aún no ha integrado soporte para sistemas de archivos de unión como aufs y unionfs, por lo que las instantáneas LVM siguen siendo el método recomendado en la actualidad.

USO

¿Puedo ejecutar un demonio en un chroot?

Un problema común es intentar ejecutar un demonio en un chroot y descubrir que no funciona. Típicamente, el demonio se detiene poco después de arrancar.

Cuando schroot se ejecuta, inicia una sesión, ejecuta el comando o shell especificado, espera a que el comando o shell termine y luego finaliza la sesión. Para un comando o shell normal, esto funciona bien. Sin embargo, los demonios normalmente se inician ejecutándose en segundo plano y desvinculándose de la terminal de control. Lo hacen bifurcándose dos veces y dejando que los procesos padres salgan. Desafortunadamente, esto significa que schroot detecta que el programa ha salido (el demonio es un nieto huérfano de este proceso) y finaliza la sesión. Parte de finalizar la sesión es matar todos los procesos que se ejecutan dentro del chroot, lo que significa que el demonio se mata cuando termina la sesión.

En consecuencia, no es posible ejecutar un demonio *directamente* con schroot. Sin embargo, puedes hacerlo si creas una sesión con --begin-session y luego ejecutas el demonio con --run-session. Es tu responsabilidad finalizar la sesión con --end-session cuando el demonio haya terminado o ya no lo necesites.

¿Cómo limpio manualmente una sesión rota?

Ocasionalmente, puede ser necesario limpiar manualmente las sesiones. Si algo cambia en tu sistema que causa que los scripts de configuración fallen al finalizar una sesión, por ejemplo, la eliminación de un archivo o directorio necesario, schroot puede no ser capaz de limpiar todo automáticamente. Para cada uno de los directorios de sesión enumerados en la sección “Directorios de sesión” en schroot(1), se deben eliminar los archivos con el nombre del ID de sesión, y los directorios con el nombre del ID de sesión deben desmontarse (si hay algún sistema de archivos montado debajo) y luego también eliminarse.

Por ejemplo, para eliminar una sesión llamada mi-sesion manualmente:

•
Eliminar el archivo de configuración de la sesión 
% rm /var/lib/schroot/session/mi-sesion↵
•
Comprobar si hay sistemas de archivos montados 
% /usr/lib/schroot/schroot-listmounts -m \
  /var/run/schroot/mount/mi-sesion↵
•
Desmontar cualquier sistema de archivos montado
•
Eliminar /var/run/schroot/mount/mi-sesion
•
Repetir para otros directorios como /var/lib/schroot/union/underlay, /var/lib/schroot/union/overlay y /var/lib/schroot/unpack

NOTA: ¡No elimine ningún directorio sin comprobar si hay sistemas de archivos montados debajo de ellos, ya que los sistemas de archivos como /home aún podrían estar montados mediante enlace! ¡Hacerlo podría causar una pérdida de datos irrecuperable!

ADVANCED USAGE

When you run schroot to execute a single command, such as in the example above where schroot is used to run a command inside of a chroot, a temporary session is created which is used to run the command, and then this session is automatically removed when the command has completed. This means that the chroot state is reset between commands.

If you want to run more than one command within the same chroot, you would normally have to run a shell within the chroot and run the commands interactively, or alternatively write a shell script and run that inside the chroot. This is not always convenient, and may not be suitable for running commands from a program or script where the commands to be run are not known in advance.

Sessions provide a way to run multiple commands within the same chroot, and to preserve the chroot state in between commands. When a session is created using the --begin-session option, the session is not automatically removed when the command has completed. Instead, the session is persistent, and may be re-used by subsequent commands by specifying the session name or session ID when running commands with the --run-session option.

When schroot is used with the --begin-session option, it will automatically create and set up a session. The session is automatically given a unique name based upon the name of the chroot that it is based upon, for example squeeze-57a69547-e014-4f5d-a98b-f4f35a005307. This name or ID is printed to standard output, and can be saved as a shell variable.

Example:

% schroot --begin-session -c squeeze↵
squeeze-57a69547-e014-4f5d-a98b-f4f35a005307

Once the session has been created, commands may be run within the session using the --run-session option, specifying either the session name or ID:

% schroot --run-session -c squeeze-57a69547-e014-4f5d-a98b-f4f35a005307 \
  -- command1↵

or

% SESSION=$(schroot --begin-session -c squeeze)↵
% schroot --run-session -c "$SESSION" -- command1↵

Subsequent commands may be run within the same session:

% schroot --run-session -c "$SESSION" -- command2↵
% schroot --run-session -c "$SESSION" -- command3↵

When you have finished with the session, it should be cleaned up and removed using the --end-session option:

% schroot --end-session -c "$SESSION"↵

Using the automatically generated session names can be long and unwieldy. The --session-name option may be used to specify a custom session name:

% schroot --begin-session -c squeeze --session-name my-session-name↵
my-session-name

The session may then be referred to using the custom name:

% schroot --run-session -c my-session-name -- command1↵
% schroot --end-session -c my-session-name↵

When using sessions, it is important to note that schroot cannot know when you have finished with the session. If you do not explicitly terminate the session using --end-session, the session will continue to exist until it is manually removed or expires due to inactivity.

CONTRIBUTING

Getting help and getting involved

The mailing list <buildd-tools-devel@lists.alioth.debian.org> is used for both user support and development discussion. The list may be subscribed to from the project website at https://alioth.debian.org/projects/buildd-tools/ or the Mailman list interface at http://lists.alioth.debian.org/mailman/listinfo/buildd-tools-devel.

Reporting bugs

On Debian systems, bugs may be reported using the reportbug(1) tool, or alternatively by mailing <submit@bugs.debian.org> (see http://bugs.debian.org for details on how to do that).

Getting the latest sources

schroot is maintained in the git version control system. You can get the latest sources from git://git.debian.org/git/buildd-tools/schroot.

% git clone git://git.debian.org/git/buildd-tools/schroot↵

The master branch contains the current development release. Stable releases are found on branches, for example the 1.4 series of releases are on the schroot-1.4 branch.
