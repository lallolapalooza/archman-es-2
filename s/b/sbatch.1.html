sbatch(1) Comandos Slurm sbatch(1)

NOMBRE

sbatch - Enviar un script de batch a Slurm.

SINOPSIS

sbatch [OPCIONES(0)...] [ : [OPCIONES(N)...]] script(0) [args(0)...]

La(s) opción(es) definen múltiples trabajos en un trabajo heterogéneo co-programado. Para más detalles sobre trabajos heterogéneos, consulte el documento
https://slurm.schedmd.com/heterogeneous_jobs.html

DESCRIPCIÓN

sbatch envía un script de batch a Slurm. El script de batch puede ser proporcionado a sbatch a través de un nombre de archivo en la línea de comandos, o si no se especifica ningún nombre de archivo, sbatch leerá un script de la entrada estándar.

El script de batch puede contener una o más líneas que comiencen con "#SBATCH" seguidas de cualquiera de las opciones de la línea de comandos documentadas en esta página. Las directivas #SBATCH son leídas directamente por Slurm, por lo que la sintaxis específica del shell, incluyendo nombres de variables, se leerá como texto literal. Una vez que se ha alcanzado la primera línea que no es un comentario ni un espacio en blanco, no se procesarán más directivas #SBATCH. Véase el ejemplo a continuación.

sbatch sale inmediatamente después de que el script se transfiere exitosamente al controlador de Slurm y se le asigna un ID de trabajo de Slurm. El script de batch no necesariamente obtiene recursos de inmediato, puede permanecer en la cola de trabajos pendientes durante algún tiempo antes de que sus recursos requeridos estén disponibles.

Por defecto, tanto la salida estándar como el error estándar se dirigen a un archivo con el nombre "slurm-%j.out", donde "%j" se reemplaza con el número de asignación del trabajo. El archivo se generará en el primer nodo de la asignación del trabajo. Aparte del propio script de batch, Slurm no realiza ningún movimiento de archivos del usuario.

Cuando finalmente se concede la asignación del trabajo para el script de batch, Slurm ejecuta una única copia del script de batch en el primer nodo del conjunto de nodos asignados.

El siguiente documento describe la influencia de varias opciones en la asignación de CPUs a trabajos y tareas.
https://slurm.schedmd.com/cpu_management.html

VALOR DE RETORNO

sbatch devolverá 0 en caso de éxito o un código de error en caso de fallo.

RESOLUCIÓN DE RUTA DEL SCRIPT

El script de batch se resuelve en el siguiente orden:

1. Si el script comienza con ".", la ruta se construye como: directorio de trabajo actual / script
2. Si el script comienza con "/", la ruta se considera absoluta.
3. Si el script está en el directorio de trabajo actual.
4. Si el script puede resolverse a través de PATH. Ver path_resolution(7).

El directorio de trabajo actual es el directorio de trabajo del proceso llamante, a menos que se pase el argumento --chdir, que anulará el directorio de trabajo actual.

OPCIONES

-A, --account=<cuenta>
Cargar los recursos utilizados por este trabajo a la cuenta especificada. La cuenta es una cadena arbitraria. El nombre de la cuenta puede ser modificado después de la presentación del trabajo utilizando el comando scontrol.
--acctg-freq=<tipo_dato>=<intervalo>[,<tipo_dato>=<intervalo>...]
Definir los intervalos de muestreo de contabilidad y perfilado del trabajo en segundos. Esto puede ser utilizado para anular el parámetro JobAcctGatherFrequency en el archivo slurm.conf. <tipo_dato>=<intervalo> especifica el intervalo de muestreo de tareas para el plugin jobacct_gather o un intervalo de muestreo para un tipo de perfilado por el plugin acct_gather_profile. Se pueden especificar múltiples pares separados por comas de <tipo_dato>=<intervalo>. Los valores de tipo_dato soportados son:
task
Intervalo de muestreo para los plugins jobacct_gather y para el perfilado de tareas por el plugin acct_gather_profile.
NOTA: Esta frecuencia se utiliza para monitorizar el uso de memoria. Si se imponen límites de memoria, la frecuencia más alta que un usuario puede solicitar es la configurada en el archivo slurm.conf. No puede ser desactivada.
energy
Intervalo de muestreo para el perfilado de energía utilizando el plugin acct_gather_energy.
network
Intervalo de muestreo para el perfilado de infiniband utilizando el plugin acct_gather_interconnect.
filesystem
Intervalo de muestreo para el perfilado del sistema de archivos utilizando el plugin acct_gather_filesystem.

El valor por defecto para el intervalo de muestreo de tareas es de 30 segundos. El valor por defecto para todos los demás intervalos es 0. Un intervalo de 0 deshabilita el muestreo del tipo especificado. Si el intervalo de muestreo de tareas es 0, la información de contabilidad se recopila solo al finalizar el trabajo (reduciendo la interferencia de Slurm con el trabajo).
Valores más pequeños (no cero) tienen un mayor impacto en el rendimiento del trabajo, pero un valor de 30 segundos probablemente no será notorio para aplicaciones con menos de 10,000 tareas.

-a, --array=<índices>
Enviar un array de trabajos, múltiples trabajos a ser ejecutados con parámetros idénticos. La especificación de índices identifica qué valores de índice de array deben ser utilizados. Se pueden especificar múltiples valores utilizando una lista separada por comas y/o un rango de valores con un separador "-". Por ejemplo, "--array=0-15" o "--array=0,6,16-32". También se puede especificar una función de paso con un sufijo que contenga dos puntos y un número. Por ejemplo, "--array=0-15:4" es equivalente a "--array=0,4,8,12". Se puede especificar un número máximo de tareas ejecutándose simultáneamente del array de trabajos utilizando un separador "%". Por ejemplo, "--array=0-15%4" limitará el número de tareas ejecutándose simultáneamente de este array de trabajos a 4. El valor mínimo del índice es 0. el valor máximo es uno menos que el parámetro de configuración MaxArraySize. NOTA: Actualmente, los arrays de trabajos federados solo se ejecutan en el clúster local.
--batch=<lista>
Los nodos pueden tener características asignadas por el administrador de Slurm. Los usuarios pueden especificar cuáles de estas características son requeridas por su script de batch utilizando estas opciones. Por ejemplo, la asignación de un trabajo puede incluir nodos Intel Haswell y KNL con las características "haswell" y "knl" respectivamente. En tal configuración, el script de batch normalmente se beneficiaría de ejecutarse en un nodo Haswell más rápido. Esto se especificaría utilizando la opción "--batch=haswell". La especificación puede incluir operadores AND y OR utilizando los separadores ampersand y barra vertical. Por ejemplo: "--batch=haswell|broadwell" o "--batch=haswell|big_memory". El argumento --batch debe ser un subconjunto del argumento --constraint=<lista> del trabajo (es decir, el trabajo no puede solicitar solo nodos KNL, pero requerir que el script se ejecute en un nodo Haswell). Si la solicitud no puede ser satisfecha con los recursos asignados al trabajo, el script de batch se ejecutará en el primer nodo de la asignación del trabajo.
--bb=<especificación>
Especificación de buffer de ráfaga. La forma de la especificación depende del sistema. Ver también --bbf. Cuando se utiliza la opción --bb, Slurm analiza esta opción y crea un archivo de script de buffer de ráfaga temporal que es utilizado internamente por los plugins de buffer de ráfaga. Ver la guía de buffer de ráfaga de Slurm para más información y ejemplos

Este sitio no está asociado de ninguna forma con Arch Linux ni afiliado a este proyecto. El contenido es únicamente una traducción de las páginas del manual de Arch publicadas en man.archlinux.org.

s:
https://slurm.schedmd.com/burst_buffer.html
--bbf=<nombre_archivo>
Ruta del archivo que contiene la especificación del buffer de ráfaga. La forma de la especificación depende del sistema. Estas directivas de buffer de ráfaga se insertarán en el script de lotes enviado. Consulte la guía de buffer de ráfaga de Slurm para obtener más información y ejemplos:
https://slurm.schedmd.com/burst_buffer.html
-b, --begin=<tiempo>
Envía el script de lotes al controlador de Slurm inmediatamente, como de costumbre, pero indica al controlador que posponga la asignación del trabajo hasta la hora especificada.

El tiempo puede tener el formato HH:MM:SS para ejecutar un trabajo a una hora específica del día (los segundos son opcionales). (Si esa hora ya ha pasado, se asume el día siguiente.) También puede especificar midnight, noon, elevenses (11 AM), fika (3 PM) o teatime (4 PM) y puede tener una hora del día con el sufijo AM o PM para ejecutar por la mañana o por la tarde. También puede indicar el día en que se ejecutará el trabajo, especificando una fecha en formato MMDDYY o MM/DD/YY YYYY-MM-DD. Combine la fecha y la hora usando el siguiente formato YYYY-MM-DD[THH:MM[:SS]]. También puede indicar tiempos como now + count time-units, donde las unidades de tiempo pueden ser seconds (por defecto), minutes, hours, days o weeks y puede indicar a Slurm que ejecute el trabajo hoy con la palabra clave today y que ejecute el trabajo mañana con la palabra clave tomorrow. El valor puede cambiarse después del envío del trabajo usando el comando scontrol. Por ejemplo:

   --begin=16:00
   --begin=now+1hour
   --begin=now+60           (segundos por defecto)
   --begin=2010-01-20T12:34:00

Notas sobre las especificaciones de fecha/hora:
- Aunque el campo 'segundos' de la especificación de tiempo HH:MM:SS está permitido por el código, tenga en cuenta que el tiempo de sondeo del planificador de Slurm no es lo suficientemente preciso para garantizar el envío del trabajo en el segundo exacto. El trabajo será elegible para comenzar en el siguiente sondeo después de la hora especificada. El intervalo de sondeo exacto depende del planificador de Slurm (por ejemplo, 60 segundos con el planificador incorporado por defecto).
- Si no se especifica hora (HH:MM:SS), el valor predeterminado es (00:00:00).
- Si se especifica una fecha sin año (por ejemplo, MM/DD), se asume el año actual, a menos que la combinación de MM/DD y HH:MM:SS ya haya pasado para ese año, en cuyo caso se utiliza el año siguiente.

-D, --chdir=<directorio>
Establece el directorio de trabajo del script de lotes a directorio antes de que se ejecute. La ruta se puede especificar como ruta completa o ruta relativa al directorio donde se ejecuta el comando.
--cluster-constraint=[!]<lista>
Especifica las características que debe tener un clúster federado para que un trabajo hermano se envíe a él. Slurm intentará enviar un trabajo hermano a un clúster si tiene al menos una de las características especificadas. Si se incluye la opción "!", Slurm intentará enviar un trabajo hermano a un clúster que no tenga ninguna de las características especificadas.
-M, --clusters=<cadena>
Clústeres a los que emitir comandos. Se pueden especificar varios nombres de clúster separados por comas. El trabajo se enviará al clúster que ofrezca el tiempo de inicio del trabajo esperado más temprano. El valor predeterminado es el clúster actual. Un valor de 'all' consultará para ejecutar en todos los clústeres. Tenga en cuenta la opción --export para controlar las variables de entorno exportadas entre clústeres. Tenga en cuenta que slurmdbd debe estar activo para que esta opción funcione correctamente, a menos que se ejecute en una federación con FederationParameters=fed_display configurado.
--comment=<cadena>
Un comentario arbitrario entre comillas dobles si se utilizan espacios o caracteres especiales.
--consolidate-segments
Asegura que todos los segmentos de la asignación se consolidarán en un bloque agregado de nivel superior.

Esta opción se aplica a las asignaciones de trabajos. NOTA: Esta opción solo funcionará con el plugin topology/block.

-C, --constraint=<lista>
Los nodos pueden tener características asignadas por el administrador de Slurm. Los usuarios pueden especificar qué características requieren sus trabajos usando la opción de restricción. Si está buscando restricciones 'suaves', consulte --prefer para obtener más información. Solo se utilizarán los nodos que tengan características que coincidan con las restricciones del trabajo para satisfacer la solicitud. Se pueden especificar varias restricciones con AND, OR, OR coincidentes, recuentos de recursos, etc. (algunos operadores no son compatibles con todos los tipos de sistemas).

NOTA: Las características modificables son características definidas por un plugin NodeFeatures.

Las opciones compatibles para --constraint incluyen:

Nombre Único
Solo se utilizarán los nodos que tengan la característica especificada. Por ejemplo, --constraint="intel"
Recuento de Nodos
Una solicitud puede especificar el número de nodos necesarios con alguna característica al añadir un asterisco y el recuento después del nombre de la característica. Por ejemplo, --nodes=16 --constraint="graphics*4" indica que el trabajo requiere 16 nodos y que al menos cuatro de esos nodos deben tener la característica "graphics". Si solicita más de una característica y utiliza recuentos de nodos, la solicitud debe ir entre corchetes.

NOTA: Esta opción no es compatible con el plugin NodeFeatures de ayuda. Se pueden utilizar trabajos heterogéneos en su lugar.

AND
Solo se utilizarán los nodos que tengan todas las características especificadas. El ampersand se usa para el operador AND. Por ejemplo, --constraint="intel&gpu"
OR
Solo se utilizarán los nodos que tengan al menos una de las características especificadas. La barra vertical se usa para el operador OR. Si no se solicitan características modificables, los nodos en la asignación pueden tener características diferentes. Por ejemplo, salloc -N2 --constraint="intel|amd" puede resultar en una asignación de trabajo donde un nodo tiene la característica intel y el otro nodo tiene la característica amd. Sin embargo, si la expresión contiene una característica modificable, todos los operadores OR se tratan automáticamente como OR Coincidentes para que todos los nodos de la asignación de trabajos tengan el mismo conjunto de características. Por ejemplo, salloc -N2 --constraint="foo|bar&baz" El trabajo se asigna a dos nodos donde ambos nodos tienen foo, o bar y baz (uno o ambos nodos podrían tener foo, bar y baz). El plugin NodeFeatures de ayuda encontrará el primer conjunto de características de nodos que coincida con todos los nodos de la asignación de trabajos; estas características se establecen como características activas en el nodo y se pasan a RebootProgram (ver slurm.conf(5)) y al script de ayuda (ver helpers.conf(5)). En este caso, el plugin de ayuda utiliza el primero de "foo" o "bar,baz" que coincida con los dos nodos de la asignación de trabajos.
OR Coincidente
Si solo una de un conjunto de opciones posibles debe usarse para todos los nodos asignados, use el operador OR y encierre las opciones entre corchetes. Por ejemplo, --constraint="[rack1|rack2|rack3|rack4]" podría usarse para especificar que todos los nodos deben asignarse en un solo rack del clúster, pero se puede usar cualquiera de esos cuatro racks.
Recuentos Múltiples
Se pueden especificar recuentos específicos de múltiples recursos usando el operador AND y encerrando las opciones entre corchetes. Por ejemplo, --constraint="[rack1*2&rack2*4]" podría usarse para especificar que se deben asignar dos nodos de nodos con la característica "rack1" y cuatro nodos deben asignarse de nodos con la característica "rack2".

NOTA: Esta opción no es compatible con el plugin NodeFeatures de ayuda.

NOTA: Los Recuentos Múltiples pueden hacer que los trabajos se asignen con una disposición de red no óptima.

Corchetes
Se pueden usar corchetes para indicar que está buscando un conjunto de nodos con los diferentes requisitos contenidos dentro de los corchetes. Por ejemplo, --constraint="[(rack1|rack2)*1&(rack3)*2]" le proporcionará un nodo con la característica "rack1" o "rack2" y dos nodos con la característica "rack3". Si solicita más de una característica y utiliza recuentos de nodos, la solicitud debe ir entre corchetes.

NOTA: Los corchetes solo están reservados para la sintaxis de Recuentos Múltiples y OR Coincidente. Los operadores AND requieren un recuento para cada característica dentro de corchetes (es decir, "[quad*2&hemi*1]"). Slurm solo permitirá un conjunto de restricciones entre corchetes por trabajo.

NOT: Los corchetes cuadrados no son compatibles con el plugin NodeFeatures de los ayudantes. Se puede solicitar una coincidencia OR sin corchetes cuadrados utilizando el carácter de barra vertical con al menos una característica cambiable.

Paréntesis
Los paréntesis se pueden usar para agrupar características de nodo similares. Por ejemplo, --constraint="[(knl&snc4&flat)*4&haswell*1]" podría usarse para especificar que se requieren cuatro nodos con las características "knl", "snc4" y "flat" más un nodo con la característica "haswell". Los paréntesis también se pueden usar para agrupar operaciones. Sin paréntesis, las características de nodo se analizan estrictamente de izquierda a derecha. Por ejemplo, --constraint="foo&bar|baz" solicita nodos con foo y bar, o baz. --constraint="foo|bar&baz" solicita nodos con foo y baz, o bar y baz (tenga en cuenta cómo baz se unió con todo). --constraint="foo&(bar|baz)" solicita nodos con foo y al menos uno de bar o baz. NOTA: El OR dentro de los paréntesis no debe usarse con un plugin KNL NodeFeatures, pero es compatible con el plugin NodeFeatures de los ayudantes.
--container=<ruta_al_contenedor>
Ruta absoluta al paquete de contenedor OCI.
--container-id=<id_del_contenedor>
Nombre único para el contenedor OCI.
--contiguous
Si se establece, los nodos asignados deben formar un conjunto contiguo.

NOTA: Esta opción solo funcionará con el plugin topology/flat. Otros plugins de topología modifican el orden de los nodos y evitan que esta opción tenga efecto.

-S, --core-spec=<num>
Número de núcleos especializados por nodo reservado por el trabajo para operaciones del sistema y no utilizado por la aplicación. Si AllowSpecResourcesUsage está habilitado, un trabajo puede anular el CoreSpecCount de todos sus nodos asignados con esta opción. Los núcleos especializados anulados seguirán reservados para procesos del sistema. El trabajo obtendrá una asignación implícita de --exclusive para el resto de los núcleos en los nodos, lo que resultará en que los procesos del trabajo puedan usar (y se les facture por) todos los núcleos en los nodos, excepto los núcleos especializados anulados. Esta opción no se puede usar con la opción --thread-spec.

NOTA: Establecer explícitamente el valor de núcleos especializados de un trabajo establece implícitamente la opción --exclusive.

--cores-per-socket=<núcleos>
Restringe la selección de nodos a aquellos con al menos el número especificado de núcleos por socket. Consulte información adicional en la opción -B anterior cuando el plugin task/affinity esté habilitado.
NOTA: Esta opción puede establecer implícitamente el número de tareas (si no se especificó -n) como una tarea por hilo solicitado.
--cpu-freq=<p1>[-p2][:p3]

Solicita que los pasos del trabajo iniciados por comandos srun dentro de este script sbatch se ejecuten a una frecuencia solicitada, si es posible, en las CPU seleccionadas para el paso en los nodos de cómputo.

p1 puede ser [#### | low | medium | high | highm1], que establecerá la velocidad de escalado (scaling_speed) al valor correspondiente y establecerá el gobernador de escalado (scaling_governor) a UserSpace. Consulte a continuación la definición de los valores.

p1 puede ser [Conservative | OnDemand | Performance | PowerSave], que establecerá el gobernador (governor) al valor correspondiente. El gobernador debe estar en la lista establecida por la opción CpuFreqGovernors de slurm.conf.

Cuando p2 está presente, p1 será la frecuencia mínima de escalado y p2 será la frecuencia máxima de escalado. En ese caso, el gobernador p3 o CpuFreqDef no pueden ser UserSpace, ya que no admite un rango.

p2 puede ser [#### | medium | high | highm1]. p2 debe ser mayor que p1 y es incompatible con el gobernador UserSpace.

p3 puede ser [Conservative | OnDemand | Performance | PowerSave | SchedUtil | UserSpace], que establecerá el gobernador al valor correspondiente.

Si p3 es UserSpace, la velocidad de escalado de frecuencia (scaling_speed), la frecuencia máxima de escalado (scaling_max_freq) y la frecuencia mínima de escalado (scaling_min_freq) se establecerán estáticamente al valor definido por p1.

Cualquier frecuencia solicitada por debajo de la frecuencia mínima disponible se redondeará a la frecuencia mínima disponible. De la misma manera, cualquier frecuencia solicitada por encima de la frecuencia máxima disponible se redondeará a la frecuencia máxima disponible.

El parámetro CpuFreqDef en slurm.conf se utilizará para establecer el gobernador en ausencia de p3. Si no hay CpuFreqDef, el gobernador predeterminado será usar el gobernador actual del sistema establecido en cada cpu. Por lo tanto, especificar un rango sin CpuFreqDef o un gobernador específico no está permitido.

Los valores aceptables en este momento incluyen:

####
frecuencia en kilohertzios
Low
la frecuencia más baja disponible
High
la frecuencia más alta disponible
HighM1
(high menos uno) seleccionará la siguiente frecuencia disponible más alta
Medium
intenta establecer una frecuencia en el medio del rango disponible
Conservative
intenta usar el gobernador de CPU Conservative
OnDemand
intenta usar el gobernador de CPU OnDemand (el valor predeterminado)
Performance
intenta usar el gobernador de CPU Performance
PowerSave
intenta usar el gobernador de CPU PowerSave
UserSpace
intenta usar el gobernador de CPU UserSpace

La siguiente variable de entorno informativa se establece en el paso del trabajo cuando se solicita la opción --cpu-freq.

        SLURM_CPU_FREQ_REQ

Esta variable de entorno también se puede usar para proporcionar el valor para la solicitud de frecuencia de CPU si está establecida cuando se emite el comando 'srun'. La opción --cpu-freq en la línea de comandos anulará el valor de la variable de entorno. La forma en la variable de entorno es la misma que en la línea de comandos. Consulte la sección VARIABLES DE ENTORNO para obtener una descripción de la variable SLURM_CPU_FREQ_REQ.

NOTA: Este parámetro se trata como una solicitud, no como un requisito. Si el nodo del paso del trabajo no admite el establecimiento de la frecuencia de CPU, o si el valor solicitado está fuera de los límites de las frecuencias legales, se registra un error, pero se permite que el paso del trabajo continúe.

NOTA: Establecer la frecuencia solo para las CPU del paso del trabajo implica que las tareas están confinadas a esas CPU. Si el confinamiento de tareas (es decir, el plugin TaskPlugin task/affinity está habilitado, o el plugin TaskPlugin task/cgroup está habilitado con "ConstrainCores=yes" establecido en cgroup.conf) no está configurado, este parámetro se ignora.

NOTA: Cuando el paso finaliza, la frecuencia y el gobernador de cada CPU seleccionada se restablecen a los valores anteriores.

NOTA: Al enviar trabajos con la opción --cpu-freq con linuxproc como ProctrackType, puede hacer que los trabajos se ejecuten demasiado rápido antes de que Accounting pueda consultar la información del trabajo. Como resultado, no toda la información de contabilidad estará presente.

--cpus-per-gpu=<ncpu>
Solicita que se asignen ncpu procesadores por GPU asignada. Los pasos que heredan este valor implicarán --exact. No es compatible con la opción --cpus-per-task.
-c, --cpus-per-task=<ncpu>
Avisa al controlador de Slurm de que los pasos del trabajo subsiguientes requerirán ncpu procesadores por tarea. Sin esta opción, el controlador intentará asignar un procesador por tarea.

Por ejemplo, considere una aplicación que tiene 4 tareas, cada una requiere 3 procesadores. Si nuestro clúster está compuesto por nodos con cuatro procesadores y simplemente pedimos 12 procesadores, el controlador podría darnos solo 3 nodos. Sin embargo, al usar la opción --cpus-per-task=3, el controlador sabe que cada tarea requiere 3 procesadores en el mismo nodo, y el controlador otorgará una asignación de 4 nodos, uno para cada una de las 4 tareas.

--deadline=<OPT>
Elimina el trabajo si no es posible un final antes de esta fecha límite (inicio > (fecha límite - tiempo[-min])). El valor predeterminado es sin fecha límite. Tenga en cuenta que si ni DefaultTime ni MaxTime están configurados en la partición en la que se encuentra el trabajo, el trabajo deberá especificar alguna forma de límite de tiempo.
(--tiempo[-min]) si se va a usar una fecha límite.

Los formatos de tiempo válidos son:
HH:MM[:SS] [AM|PM]
MMDD[AA] o MM/DD[/AA] o MM.DD[.AA]
MM/DD[/AA]-HH:MM[:SS]
AAAA-MM-DD[THH:MM[:SS]]
ahora[+contador[segundos(por defecto)|minutos|horas|días|semanas]]
medianoche, las once (11 AM), mediodía, fika (3 PM), té (4 PM) o mañana

Se pueden especificar una o más cadenas de tiempo (por ejemplo, 'mañana18:00'). Si hay un conflicto entre ellas, la última prevalecerá silenciosamente.

--delay-boot=<minutos>

Si el trabajo ha esperado menos que el período especificado, utilizará solo nodos que ya tengan las características especificadas. El argumento está en unidades de minutos. Un administrador del sistema puede establecer un valor predeterminado utilizando la opción delay_boot del parámetro de configuración SchedulerParameters en el archivo slurm.conf; de lo contrario, el valor predeterminado es cero (sin retraso).
-d, --dependency=<lista_dependencias>
Aplazar el inicio de este trabajo hasta que se cumplan las dependencias especificadas. Una vez que se satisface una dependencia, se elimina del trabajo. <lista_dependencias> tiene el formato <tipo:id_trabajo[:id_trabajo][,tipo:id_trabajo[:id_trabajo]]> o <tipo:id_trabajo[:id_trabajo][?tipo:id_trabajo[:id_trabajo]]>. Todas las dependencias deben cumplirse si se usa el separador ",". Cualquiera dependencia puede cumplirse si se usa el separador "?". Solo se puede usar un separador. Por ejemplo:

significa que cualquiera de las condiciones (afterok:20 O afterok:21 O afterany:23) será suficiente para liberar el trabajo. Muchos trabajos pueden compartir la misma dependencia y estos trabajos pueden incluso pertenecer a diferentes usuarios. El valor puede ser cambiado después de la presentación del trabajo usando el comando scontrol. Se permiten dependencias en trabajos remotos en una federación. Una vez que falla una dependencia de trabajo debido al estado de terminación de un trabajo anterior, el trabajo dependiente nunca se ejecutará, incluso si el trabajo anterior se reinicia y tiene un estado de terminación diferente en una ejecución posterior.

Después de que los trabajos especificados comiencen o sean cancelados y 'tiempo' en minutos desde el inicio o cancelación del trabajo ocurra, este trabajo puede comenzar su ejecución. Si no se da 'tiempo', no hay demora después del inicio o cancelación.

Este trabajo puede comenzar su ejecución después de que los trabajos especificados hayan terminado. Este es el tipo de dependencia predeterminado.

Este trabajo puede comenzar su ejecución después de que los trabajos especificados hayan terminado y las operaciones de escritura asociadas al burst buffer se hayan completado.

Una tarea de esta matriz de trabajos puede comenzar su ejecución después de que la tarea correspondiente ID en el trabajo especificado haya completado con éxito (se ejecutó hasta completar con un código de salida cero). Si el trabajo especificado no es una matriz, esto se trata de la misma manera que afterok.
afternotok:id_trabajo[:id_trabajo...]
Este trabajo puede comenzar su ejecución después de que los trabajos especificados hayan terminado en algún estado fallido (código de salida no cero, fallo de nodo, tiempo de espera agotado, etc.). Este trabajo debe ser presentado mientras el trabajo especificado aún está activo o dentro de MinJobAge segundos después de que el trabajo especificado haya terminado. Si el ID del trabajo dependiente no se encuentra y está en el mismo clúster que la presentación del trabajo, el trabajo es rechazado. Si el ID del trabajo dependiente no se encuentra y está en un clúster diferente al de la presentación del trabajo, la dependencia se marca como fallida.
afterok:id_trabajo[:id_trabajo...]
Este trabajo puede comenzar su ejecución después de que los trabajos especificados se hayan ejecutado correctamente (se ejecutaron hasta completar con un código de salida cero). Este trabajo debe ser presentado mientras el trabajo especificado aún está activo o dentro de MinJobAge segundos después de que el trabajo especificado haya terminado. Si el ID del trabajo dependiente no se encuentra y está en el mismo clúster que la presentación del trabajo, el trabajo es rechazado. Si el ID del trabajo dependiente no se encuentra y está en un clúster diferente al de la presentación del trabajo, la dependencia se marca como fallida.
singleton
Este trabajo puede comenzar su ejecución después de que cualquier trabajo lanzado previamente que comparta el mismo nombre de trabajo y usuario haya terminado. En otras palabras, solo un trabajo con ese nombre y propiedad de ese usuario puede estar ejecutándose o suspendido en cualquier momento. En una federación, una dependencia singleton debe cumplirse en todos los clústeres a menos que se use DependencyParameters=disable_remote_singleton en slurm.conf.

Especificar métodos de distribución alternativos para procesos remotos. Para la asignación de trabajos, esto establece variables de entorno que serán utilizadas por solicitudes srun posteriores y también afecta a los núcleos que se seleccionarán para la asignación de trabajos.

Esta opción controla la distribución de tareas a los nodos en los que se han asignado recursos, y la distribución de esos recursos a las tareas para el enlace (afinidad de tareas). El primer método de distribución (antes de la primera ":") controla la distribución de tareas a los nodos. El segundo método de distribución (después de la primera ":") controla la distribución de las CPU asignadas a través de los sockets para el enlace a las tareas. El tercer método de distribución (después de la segunda ":") controla la distribución de las CPU asignadas a través de los núcleos para el enlace a las tareas. Las distribuciones segunda y tercera solo se aplican si la afinidad de tareas está habilitada. La tercera distribución solo se admite si el plugin de tarea/cgroup está configurado. El valor predeterminado para cada tipo de distribución se especifica mediante *.

Tenga en cuenta que con select/cons_tres, el número de CPU asignadas a cada socket y nodo puede ser diferente. Consulte https://slurm.schedmd.com/mc_support.html para obtener más información sobre la asignación de recursos, la distribución de tareas a los nodos y el enlace de tareas a las CPU.

Primer método de distribución (distribución de tareas entre nodos):
*
Utilice el método predeterminado para distribuir tareas a los nodos (block).
block
El método de distribución por bloques distribuirá las tareas a un nodo de tal manera que las tareas consecutivas compartan un nodo. Por ejemplo, considere una asignación de tres nodos cada uno con dos CPU. Una solicitud de distribución por bloques de cuatro tareas distribuirá esas tareas a los nodos con las tareas uno y dos en el primer nodo, la tarea tres en el segundo nodo y la tarea cuatro en el tercer nodo. La distribución por bloques es el comportamiento predeterminado si el número de tareas excede el número de nodos asignados.
cyclic
El método de distribución cíclica distribuirá las tareas a un nodo de tal manera que las tareas consecutivas se distribuyan en nodos consecutivos (en un orden circular). Por ejemplo, considere una asignación de tres nodos cada uno con dos CPU. Una solicitud de distribución cíclica de cuatro tareas distribuirá esas tareas a los nodos con las tareas uno y cuatro en el primer nodo, la tarea dos en el segundo nodo y la tarea tres en el tercer nodo. Tenga en cuenta que cuando SelectType es select/cons_tres, es posible que no se asignen la misma cantidad de CPU en cada nodo. La distribución de tareas será en orden circular entre todos los nodos con CPU aún por asignar a las tareas. La distribución cíclica es el comportamiento predeterminado si el número de tareas no es mayor que el número de nodos asignados nodos.
plane
Las tareas se distribuyen en bloques de tamaño <tamaño>. El tamaño debe proporcionarse o debe establecerse SLURM_DIST_PLANESIZE. El número de tareas distribuidas a cada nodo es el mismo que para la distribución cíclica, pero los id de tarea asignados a cada nodo dependen del tamaño del plano. Las especificaciones de distribución adicionales no se pueden combinar con esta opción. Para obtener más detalles (incluidos ejemplos y diagramas), consulte https://slurm.schedmd.com/mc_support.html y https://slurm.schedmd.com/dist_plane.html
arbitrary
El método de distribución arbitraria asignará procesos en orden según lo que aparece en el archivo designado por la variable de entorno SLURM_HOSTFILE. Si esta variable está presente, anulará cualquier otro método especificado. Si no está configurada, el método será block por defecto. Dentro del archivo hostfile debe contener como mínimo el número de hosts solicitados y ser uno por línea o separado por comas. Si se especifica una tarea

DISTRIBUCIÓN DE TAREAS

Este es el método de distribución de tareas de la segunda distribución (distribución de CPUs en sockets para enlace):

arbitrary
Las tareas de un paso de trabajo se asignarán a los nodos en el orden en que se especifican en la lista de nodos con la opción -N, --nodes y la opción -n, --ntasks. Sus tareas se distribuirán en los nodos en el orden del archivo.
NOTA: La opción de distribución arbitraria en una asignación de trabajo solo controla los nodos que se asignarán al trabajo y no la asignación de CPUs en esos nodos. Esta opción está destinada principalmente a controlar la disposición de las tareas de un paso de trabajo en una asignación de trabajo existente para el comando srun.
NOTA: Si se proporciona el número de tareas y también una lista de nodos solicitados, el número de nodos utilizados de esa lista se reducirá para que coincida con el número de tareas si el número de nodos en la lista es mayor que el número de tareas.

Segundo método de distribución (distribución de CPUs en sockets para enlace):

*
Utilice el método predeterminado para distribuir CPUs entre sockets (cíclico).
block
El método de distribución por bloques distribuirá las CPUs asignadas consecutivamente desde el mismo socket para el enlace a las tareas, antes de utilizar el siguiente socket consecutivo.
cyclic
El método de distribución cíclica distribuirá las CPUs asignadas para el enlace a una tarea determinada de forma consecutiva desde el mismo socket, y desde el siguiente socket consecutivo para la siguiente tarea, de forma rotatoria entre los sockets. Las tareas que requieran más de una CPU tendrán todas esas CPUs asignadas en un solo socket si es posible.
NOTA: En nodos con hyper-threading habilitado, una tarea que no solicite núcleos completos puede distribuirse entre sockets. Esto se puede evitar especificando --ntasks-per-core=1, que fuerza a las tareas a asignar núcleos completos.
fcyclic
El método de distribución fcyclic distribuirá las CPUs asignadas para el enlace a las tareas desde sockets consecutivos de forma rotatoria entre los sockets. Las tareas que requieran más de una CPU tendrán cada CPU asignada de forma cíclica entre los sockets.

Tercer método de distribución (distribución de CPUs en núcleos para enlace):

*
Utilice el método predeterminado para distribuir CPUs entre núcleos (heredado del segundo método de distribución).
block
El método de distribución por bloques distribuirá las CPUs asignadas consecutivamente desde el mismo núcleo para el enlace a las tareas, antes de utilizar el siguiente núcleo consecutivo.
cyclic
El método de distribución cíclica distribuirá las CPUs asignadas para el enlace a una tarea determinada de forma consecutiva desde el mismo núcleo, y desde el siguiente núcleo consecutivo para la siguiente tarea, de forma rotatoria entre los núcleos.
fcyclic
El método de distribución fcyclic distribuirá las CPUs asignadas para el enlace a las tareas desde núcleos consecutivos de forma rotatoria entre los núcleos.

En lugar de distribuir uniformemente las tareas de un paso de trabajo entre sus nodos asignados, empaquételas lo más apretadamente posible en los nodos. Esto solo se aplica cuando se utiliza el método de distribución de tareas "block".

El usuario no puede especificar variables de entorno explícitas con "NONE". Ejemplo: --export=ALL,EDITOR=/bin/emacs

Especifica que el trabajo por lotes nunca debe ser reenviado bajo ninguna circunstancia (ver nota a continuación). Establecer esta opción impedirá que los administradores del sistema puedan reiniciar el trabajo (por ejemplo, después de una interrupción programada), recuperarse de un fallo de nodo o ser reenviado debido a una preempción por un trabajo de mayor prioridad. Cuando un trabajo se reenvía, el script por lotes se inicia desde el principio. Consulte también la opción --requeue. El parámetro de configuración JobRequeue controla el comportamiento predeterminado en el clúster.

NOTA: ForceRequeueOnFail si se establece como una opción para el parámetro PrologFlags en slurm.conf puede anular esta configuración.

-F, --nodefile=<archivo_nodos>
De manera similar a --nodelist, pero la lista se contiene en un archivo llamado archivo_nodos. El nombre del nodo
may also span multiple lines in the file. Duplicate node names in the file will be ignored. The order of the node names in the list is not important; the node names will be sorted by Slurm.
-w, --nodelist=<lista_nombres_nodos>
Solicita una lista específica de hosts. El trabajo contendrá *todos* estos hosts y posiblemente hosts adicionales según sea necesario para satisfacer los requisitos de recursos. La lista puede especificarse como una lista de hosts separada por comas, un rango de hosts (host[1-5,7,...] por ejemplo) o un nombre de archivo. Se asumirá que la lista de hosts es un nombre de archivo si contiene un carácter "/". Si especifica un número mínimo de nodos o procesadores mayor de lo que puede satisfacer la lista de hosts proporcionada, se asignarán recursos adicionales en otros nodos según sea necesario. Los nombres de nodos duplicados en la lista serán ignorados. El orden de los nombres de nodos en la lista no es importante; los nombres de nodos serán ordenados por Slurm.
-N, --nodes=<minnodos>[-maxnodos]|<cadena_tamaño>
Solicita que se asignen como mínimo minnodos nodos a este trabajo. También se puede especificar un número máximo de nodos con maxnodos. Si solo se especifica un número, este se utiliza tanto como recuento mínimo como máximo de nodos. El recuento de nodos también se puede especificar como cadena_tamaño. La especificación de cadena_tamaño identifica qué valores de nodos se deben utilizar. Se pueden especificar varios valores utilizando una lista separada por comas o con una función de paso mediante un sufijo que contenga dos puntos y valores numéricos con un separador "-". Por ejemplo, "--nodes=1-15:4" es equivalente a "--nodes=1,5,9,13". Los límites de nodos de la partición anulan los del trabajo. Si los límites de nodos de un trabajo están fuera del rango permitido para su partición asociada, el trabajo permanecerá en estado PENDING. Esto permite una posible ejecución en un momento posterior, cuando cambie el límite de la partición. Si el límite de nodos de un trabajo excede el número de nodos configurados en la partición, el trabajo será rechazado. Tenga en cuenta que la variable de entorno SLURM_JOB_NUM_NODES se establecerá en el recuento de nodos realmente asignados al trabajo. Consulte la sección **VARIABLES DE ENTORNO** para obtener más información. Si no se especifica **-N**, el comportamiento predeterminado es asignar suficientes nodos para satisfacer los recursos solicitados tal como se expresan mediante opciones de especificación por trabajo, por ejemplo, **-n**, **-c** y **--gpus**. Al trabajo se le asignará la mayor cantidad de nodos posible dentro del rango especificado y sin retrasar el inicio del trabajo. La especificación del recuento de nodos puede incluir un valor numérico seguido de un sufijo "k" (multiplica el valor numérico por 1.024) o "m" (multiplica el valor numérico por 1.048.576).

NOTA: Esta opción no se puede utilizar con distribución arbitraria.

-n, --ntasks=<número>
sbatch no lanza tareas, solicita una asignación de recursos y envía un script de lote. Esta opción informa al controlador Slurm de que los pasos del trabajo que se ejecutan dentro de la asignación lanzarán un máximo de número tareas y proporcionarán recursos suficientes. El valor predeterminado es una tarea por nodo, pero tenga en cuenta que la opción --cpus-per-task cambiará este valor predeterminado.
--ntasks-per-core=<ntareas>
Solicita que se invoquen como máximo ntareas en cada núcleo. Pensada para usarse con la opción **--ntasks**. Relacionada con **--ntasks-per-node** excepto a nivel de núcleo en lugar de nivel de nodo. Esta opción será heredada por srun. Slurm puede asignar más cpus de los solicitados para respetar esta opción.
NOTA: Esta opción no es compatible cuando se utiliza SelectType=select/linear. Este valor no puede ser mayor que --threads-per-core.
--ntasks-per-gpu=<ntareas>
Solicita que se invoquen ntareas por cada GPU. Esta opción puede funcionar de dos maneras: 1) especificar **--ntasks** además, en cuyo caso se determinará automáticamente una especificación de GPU sin tipo para satisfacer **--ntasks-per-gpu**, o 2) especificar las GPUs deseadas (por ejemplo, mediante **--gpus** o **--gres**) sin especificar **--ntasks**, y el recuento total de tareas se determinará automáticamente. El número de CPUs necesarias se incrementará automáticamente si es necesario para permitir cualquier recuento de tareas calculado. Esta opción establecerá implícitamente **--tres-bind=gres/gpu:single:<ntareas>**, pero eso puede ser anulado con una especificación explícita de **--tres-bind=gres/gpu**. Esta opción no es compatible con un rango de nodos (es decir, -N<minnodos-maxnodos>). Esta opción no es compatible con **--gpus-per-task**, **--gpus-per-socket** o **--ntasks-per-node**. Esta opción no es compatible a menos que SelectType=cons_tres esté configurado (directa o indirectamente en sistemas Cray).
--ntasks-per-node=<ntareas>
Solicita que se invoquen ntareas en cada nodo. Si se usa con la opción **--ntasks**, la opción **--ntasks** tendrá precedencia y **--ntasks-per-node** se tratará como un recuento *máximo* de tareas por nodo. Pensada para usarse con la opción **--nodes**. Está relacionada con **--cpus-per-task**=ncpu, pero no requiere conocimiento del número real de cpus en cada nodo. En algunos casos, es más conveniente poder solicitar que no se invoquen más de un número específico de tareas en cada nodo. Los ejemplos de esto incluyen enviar una aplicación híbrida MPI/OpenMP donde solo se debe asignar una "tarea/rango" MPI a cada nodo, permitiendo que la parte de OpenMP utilice todo el paralelismo presente en el nodo, o enviar un único trabajo de configuración/limpieza/monitorización a cada nodo de una asignación preexistente como un paso en un script de trabajo más grande.
--ntasks-per-socket=<ntareas>
Solicita que se invoquen como máximo ntareas en cada socket. Pensada para usarse con la opción **--ntasks**. Relacionada con **--ntasks-per-node** excepto a nivel de socket en lugar de nivel de nodo. NOTA: Esta opción no es compatible cuando se utiliza SelectType=select/linear.
--oom-kill-step[={0|1}]
Indica si se debe finalizar todo el paso si se detecta un evento OOM en cualquier tarea de un paso. Esto anula la configuración "OOMKillStep" de TaskPluginParam en slurm.conf. Cuando no se establece, utilizará la configuración en slurm.conf. Cuando se establece, un valor de "0" deshabilitará la finalización de todo el paso, mientras que un valor de "1" lo habilitará. Esto se aplica a toda la asignación, excepto al paso externo. El valor predeterminado es "1" (habilitado) cuando la opción se encuentra sin valor.
--open-mode={append|truncate}
Abre los archivos de salida y error utilizando el modo de añadir o truncar, según se especifique. El valor predeterminado es el especificado por el parámetro de configuración del sistema JobFileAppend.
-o, --output=<patrón_nombre_archivo>
Instruye a Slurm para que conecte la salida estándar del script de lote directamente al archivo especificado en el "patrón de nombre de archivo". Por defecto, tanto la salida estándar como el error estándar se dirigen al mismo archivo. Para los arrays de trabajos, el nombre de archivo predeterminado es "slurm-%A_%a.out", donde "%A" se reemplaza por el ID del trabajo y "%a" por el índice del array. Para otros trabajos, el nombre de archivo predeterminado es "slurm-%j.out", donde "%j" se reemplaza por el ID del trabajo. Consulte la sección de **patrón de nombre de archivo** a continuación para ver las opciones de especificación de nombres de archivo.
-O, --overcommit
Aprovisionamiento excesivo de recursos.

Cuando se aplica a una asignación de trabajo (sin incluir trabajos que solicitan acceso exclusivo a los nodos), los recursos se asignan como si solo se solicitara una tarea por nodo. Esto significa que el número de cpus solicitados por tarea (**-c**, **--cpus-per-task**) se asignan por nodo en lugar de multiplicarse por el número de tareas. Se ignoran las opciones utilizadas para especificar el número de tareas por nodo, socket, núcleo, etc.

Cuando se aplica a las asignaciones de pasos de trabajo (el comando srun cuando se ejecuta dentro de una asignación de trabajo existente), esta opción se puede usar para lanzar más de una tarea por CPU. Normalmente, srun no asignará más de un proceso por CPU. Al especificar **--overcommit**, permite explícitamente más de un proceso por CPU. Sin embargo, no se permite que más de MAX_TASKS_PER_NODE tareas se ejecuten por nodo. NOTA: MAX_TASKS_PER_NODE se define en el archivo slurm.h y no es una variable, se establece en el momento de la compilación de Slurm.

-s, --oversubscribe
La asignación del trabajo puede sobreutilizar recursos con otros trabajos en ejecución. Los recursos a sobreutilizar pueden ser nodos, sockets, núcleos y/o hyperthreads según la configuración. El comportamiento de sobreutilización predeterminado depende de la configuración del sistema y la opción OverSubscribe de la partición tiene prioridad sobre la opción del trabajo. Esta opción puede resultar en que la asignación se conceda antes que si la opción --oversubscribe no estuviera establecida y permitir una mayor utilización del sistema, pero el rendimiento de la aplicación probablemente se verá afectado debido a la competencia por los recursos. Consulte también la opción --exclusive.

NOTA: Esta opción es mutuamente excluyente con --exclusive.

--parsable
Solo muestra el número de ID del trabajo y el nombre del clúster si está presente. Los valores se separan por punto y coma. Los errores se seguirán mostrando.
-p, --partition=<nombres_particion>
Solicita una partición específica para la asignación de recursos. Si no se especifica, el comportamiento predeterminado es permitir que el controlador de Slurm seleccione la partición predeterminada según lo designado por el administrador del sistema. Si el trabajo puede usar más de una partición, especifique sus nombres en una lista separada por comas y se utilizará la que ofrezca la iniciación más temprana sin tener en cuenta el orden de los nombres de las particiones (aunque se considerarán primero las particiones de mayor prioridad). Cuando se inicia el trabajo, el nombre de la partición utilizada se colocará primero en la cadena de partición del registro del trabajo.
--prefer=<lista>
Los nodos pueden tener características asignadas por el administrador de Slurm. Los usuarios pueden especificar cuáles de estas características son deseadas pero no requeridas por su trabajo utilizando la opción prefer. Esta opción opera independientemente de --constraint y anulará lo que esté establecido allí si es posible. Al programar, las características en --prefer se intentan primero. Si no hay un conjunto de nodos disponible con esas características, entonces se intenta --constraint. Consulte --constraint para obtener más información, esta opción se comporta de la misma manera.
--priority=<valor>
Solicita una prioridad de trabajo específica. Puede estar sujeta a restricciones específicas de configuración. valor debe ser un valor numérico o "TOP" (para el valor más alto posible). Solo los operadores y administradores de Slurm pueden establecer la prioridad de un trabajo.
--profile={all|none|<tipo>[,<tipo>...]}
Habilita la recopilación detallada de datos por el plugin acct_gather_profile. Los datos detallados suelen ser series temporales que se almacenan en un archivo HDF5 para el trabajo o en una base de datos InfluxDB, dependiendo del plugin configurado.
All
Se recopilan todos los tipos de datos. (No se puede combinar con otros valores).
None
No se recopilan tipos de datos. Este es el valor predeterminado.
(No se puede combinar con otros valores.)

Energy

Task

Lustre
Se recopilan datos de Lustre.
Network
Se recopilan datos de red (InfiniBand).

Permite a los usuarios especificar qué límites de recursos modificables (suaves) se propagarán a los nodos de cómputo y se aplicarán a sus trabajos. -q, --qos=<qos>
Solicita una calidad de servicio para el trabajo, o una lista de QOS separadas por comas. Si se solicita una lista, se ordenará según la prioridad de la QOS dada, siendo la primera la de mayor prioridad. Los valores QOS se pueden definir para cada asociación de usuario/clúster/cuenta en la base de datos de Slurm. Los usuarios estarán limitados al conjunto de QOS definido por su asociación cuando el parámetro de configuración de Slurm, AccountingStorageEnforce, incluya "qos" en su definición.
-Q, --quiet
Suprime mensajes informativos de sbatch, como el ID del trabajo. Solo se seguirán mostrando los errores.
--reboot
Fuerza el reinicio de los nodos asignados antes de iniciar el trabajo. Esto solo se admite con algunas configuraciones del sistema y, de lo contrario, se ignorará silenciosamente. Solo root, SlurmUser o los administradores pueden reiniciar nodos.
--requeue[=expedited]
Especifica que el trabajo por lotes debe ser elegible para ser puesto de nuevo en cola. El trabajo puede ser puesto de nuevo en cola explícitamente por un administrador del sistema, después de un fallo del nodo, o tras la interrupción por un trabajo de mayor prioridad. Cuando un trabajo se pone de nuevo en cola, el script por lotes se inicia desde el principio con el mismo ID de trabajo. Consulte también la opción --no-requeue. El parámetro de configuración JobRequeue controla el comportamiento predeterminado en el clúster.

El parámetro opcional expedited solicitará que el trabajo sea inmediatamente elegible para comenzar de nuevo, y que se programe con la prioridad más alta posible. Esto solo sucederá si se permiten reinicios acelerados globalmente con SlurmctldParameters=enable_expedited_requeue en slurm.conf.

--reservation=<nombres_reserva>
Asigna recursos para el trabajo de la reserva con nombre. Si el trabajo puede utilizar más de una reserva, especifique sus nombres en una lista separada por comas y se utilizará la que ofrezca la iniciación más temprana. Se considerará cada reserva en el orden en que se solicitó. Todas las reservas se enumerarán en scontrol/squeue durante la vida del trabajo. En la contabilidad, la primera reserva será visible y después de que el trabajo comience, la reserva utilizada la reemplazará.
--resources=<nombres_recursos>
Especificación de recursos jerárquicos que deben asignarse a este trabajo. Los nombres de los recursos pueden ir seguidos de dos puntos y una cuenta (la cuenta predeterminada es uno). Se pueden solicitar varios recursos en Modo 1 y Modo 2 en una lista separada por comas, pero solo se puede solicitar uno del Modo 3. Por ejemplo, "--resources=flat:2,natural:1".

Consulte https://slurm.schedmd.com/hres.html para obtener más información sobre el uso de recursos jerárquicos con Slurm.

--resv-ports[=cuenta]
Reserva puertos de comunicación para este trabajo. Los usuarios pueden especificar el número de puertos que desean reservar. El parámetro MpiParams=ports=12000-12999 debe especificarse en slurm.conf. Si el número de puertos reservados es cero, entonces no se reservan puertos. Se utiliza solo para PMI nativo de Cray. Esta opción solo se puede utilizar si la gestión de pasos slurmstepd está habilitada. Esta opción se aplica a las asignaciones de trabajos. Consulte --stepmgr.
--segment=<tamaño_segmento>
Cuando se utiliza una topología de bloque, esto define el tamaño de los segmentos que serán
utilizado para crear la asignación de trabajos. No se impondría ningún requisito en todos los segmentos para que un trabajo se coloque dentro del mismo bloque de nivel superior.

NOTA: El número de nodos solicitado debe ser siempre divisible por el tamaño del segmento solicitado.

NOTA: Cuando se usa junto con --nodelist=<lista_de_nodos>: El número de nodos solicitados debe ser menor o igual al número total de nodos únicos especificados en el argumento --nodelist. Solicitar más nodos que los nodos únicos disponibles en el --nodelist proporcionado dará como resultado que el trabajo sea rechazado por slurmctld.

--signal=[{R|B}:]<num_sig>[@tiempo_sig]
Cuando un trabajo esté a menos de tiempo_sig segundos de su hora de finalización, envíale la señal num_sig. Debido a la resolución del manejo de eventos por Slurm, la señal puede enviarse hasta 60 segundos antes de lo especificado. num_sig puede ser un número o un nombre de señal (por ejemplo, "10" o "USR1"). tiempo_sig debe tener un valor entero entre 0 y 65535. Por defecto, no se envía ninguna señal antes de la hora de finalización del trabajo. Si se especifica un num_sig sin ningún tiempo_sig, el tiempo predeterminado será de 60 segundos. Use la opción "B:" para señalar solo el shell de lotes, ninguno de los otros procesos será señalado. Por defecto, todos los pasos del trabajo serán señalados, pero no el shell de lotes en sí. Use la opción "R:" para permitir que este trabajo se superponga con una reserva con MaxStartDelay establecido. Si se usa la opción "R:", la preemptión debe estar habilitada en el sistema, y si el trabajo es preemptido, será puesto en cola nuevamente si se permite, de lo contrario, el trabajo será cancelado. Para que la señal se envíe en el momento de la preemptión, consulte el parámetro send_user_signal PreemptParameter.
--sockets-per-node=<sockets>
Restringe la selección de nodos a nodos con al menos el número especificado de sockets. Consulte información adicional en la opción -B anterior cuando el plugin de tarea/afinidad está habilitado.
NOTA: Esta opción puede establecer implícitamente el número de tareas (si no se especificó -n) como una tarea por hilo solicitado.
--spread-job
Distribuye la asignación del trabajo en tantos nodos como sea posible e intenta distribuir uniformemente las tareas en los nodos asignados. Esta opción deshabilita el plugin de topología/árbol.
--spread-segments
Evita que los nodos dentro del mismo bloque base se asignen a segmentos separados dentro del mismo bloque.

Esta opción se aplica a las asignaciones de trabajos. NOTA: Esta opción solo funcionará con el plugin topology/block.

--stepmgr
Habilita la gestión de pasos de slurmstepd por trabajo si no está habilitada en todo el sistema. Esto permite que los pasos del trabajo sean gestionados por un único slurmstepd externo asociado al trabajo para gestionar los pasos. Esto es beneficioso para trabajos que envían muchos pasos dentro de sus asignaciones. Debe estar configurado PrologFlags=contain.
--switches=<count>[@max-time]
Cuando se usa una topología de árbol, esto define el número máximo de switches de hoja deseados para la asignación del trabajo y, opcionalmente, el tiempo máximo de espera para ese número de switches. Si Slurm encuentra una asignación que contiene más switches que el recuento especificado, el trabajo permanece pendiente hasta que encuentra una asignación con el recuento de switches deseado o el límite de tiempo expira. Si no hay límite en el recuento de switches, no hay demora en el inicio del trabajo. Los formatos de tiempo aceptables incluyen "minutos", "minutos:segundos", "horas:minutos:segundos", "días-horas", "días-horas:minutos" y "días-horas:minutos:segundos". El tiempo máximo de retraso del trabajo puede ser limitado por el administrador del sistema utilizando el parámetro de configuración SchedulerParameters con la opción de parámetro max_switch_wait. En una red dragonfly, el único recuento de switches admitido es 1, ya que el rendimiento de la comunicación será el más alto cuando un trabajo asigne recursos en un switch de hoja o en más de 2 switches de hoja. El tiempo máximo predeterminado es el SchedulerParameters max_switch_wait.
--test-only
Valida el script de lotes y devuelve una estimación de cuándo se programaría un trabajo para ejecutarse dadas la cola de trabajos actual y todos los demás argumentos que especifican los requisitos del trabajo. No se envía realmente ningún trabajo.
--thread-spec=<num>
Número de hilos especializados por nodo reservados por el trabajo para operaciones del sistema y no utilizados por la aplicación. La aplicación no utilizará estos hilos, pero se le facturará su asignación. Esta opción no se puede usar con la opción --core-spec.

NOTA: Establecer explícitamente el valor de hilos especializados de un trabajo establece implícitamente su opción --exclusive, reservando nodos completos para el trabajo.

--threads-per-core=<hilos>
Restringe la selección de nodos a nodos con al menos el número especificado de hilos por núcleo. En la disposición de tareas, utiliza el número máximo especificado de hilos por núcleo. NOTA: "Hilos" se refiere al número de unidades de procesamiento en cada núcleo en lugar del número de tareas de la aplicación que se lanzarán por núcleo. Consulte información adicional en la opción -B anterior cuando el plugin de tarea/afinidad está habilitado.
NOTA: Esta opción puede establecer implícitamente el número de tareas (si no se especificó -n) como una tarea por hilo solicitado.
-t, --time=<tiempo>
Establece un límite en el tiempo total de ejecución de la asignación del trabajo. Si el límite de tiempo solicitado excede el límite de tiempo de la partición, el trabajo permanecerá en estado PENDIENTE (posiblemente indefinidamente). El límite de tiempo predeterminado es el límite de tiempo predeterminado de la partición. Cuando se alcanza el límite de tiempo, a cada tarea en cada paso del trabajo se le envía SIGTERM seguido de SIGKILL. El intervalo entre señales se especifica mediante el parámetro de configuración de Slurm KillWait. El parámetro de configuración OverTimeLimit puede permitir que el trabajo se ejecute más tiempo del programado. La resolución de tiempo es de un minuto y los valores de segundo se redondean al minuto siguiente.

Un límite de tiempo de cero solicita que no se imponga ningún límite de tiempo. Los formatos de tiempo aceptables incluyen "minutos", "minutos:segundos", "horas:minutos:segundos", "días-horas", "días-horas:minutos" y "días-horas:minutos:segundos".

--time-min=<tiempo>
Establece un límite mínimo de tiempo en la asignación del trabajo. Si se especifica, el límite de tiempo del trabajo puede reducirse a un valor no inferior a --time-min si hacer esto permite que el trabajo comience a ejecutarse antes de lo que sería posible. El límite de tiempo del trabajo no se modificará después de que el trabajo haya sido asignado a recursos. Esto lo realiza un algoritmo de programación de backfill para asignar recursos que de otro modo estarían reservados para trabajos de mayor prioridad. Los formatos de tiempo aceptables incluyen "minutos", "minutos:segundos", "horas:minutos:segundos", "días-horas", "días-horas:minutos" y "días-horas:minutos:segundos".
--tmp=<tamaño>[unidades]
Especifica una cantidad mínima de espacio en disco temporal por nodo. Las unidades predeterminadas son megabytes. Se pueden especificar diferentes unidades usando el sufijo [K|M|G|T].

[verbose,]<tipo>...] Especifica una lista de tres con sus opciones de vinculación de tareas. Actualmente, los gres son los únicos tres soportados para esta opción. Especifica los gres como "gres/<nombre_gres>" (por ejemplo, gres/gpu).

TASK PROFILING AND BINDING

The following options are used to modify the task profiling and binding behavior of SLURM.

--tres-bind=<arg>
Bind tasks to specific trackable resources (TRES). The argument is a comma-separated list of TRES specifications. Each specification can be prefixed with a list of task ids or ranges to which the specification applies. If no task ids are specified, the specification applies to all tasks in the job. The format for each specification is "[task_list:]tres_type[/tres_name][:mode]".

The tres_type is the type of trackable resource requested (e.g. cpu, gres, license). The tres_name is the name of the trackable resource, as can be seen with sacctmgr show tres. This is required when it exists for tres types such as gres, license, etc. (e.g. gpu, gpu:a100). The mode specifies how the binding should be performed. The following modes are supported:

closest
Bind tasks to the TRES that are closest to the task's assigned CPU cores. The distance is determined by the socket affinity of the task and the socket affinity of the TRES as specified in gres.conf's Cores parameter.
flat
Bind tasks to TRES in a flat, sequential manner. The first task is bound to the first available TRES, the second task to the second available TRES, and so on. This mode is useful for ensuring that each task has exclusive access to a TRES.
mask:<gres_mask>
Bind tasks to TRES using a bitmask. The gres_mask is a hexadecimal value that specifies which TRES to bind to. The mask is applied to the tasks on each node individually. The mapping is specified for a node and identical mapping is applied to the tasks on every node (i.e. the lowest task ID on each node is mapped to the first mask specified in the list, etc.). gres masks are always interpreted as hexadecimal values but can be preceded with an optional '0x'. To simplify support for large task counts, the lists may follow a map with an asterisk and repetition count. For example "mask:0x0f*4,0xf0*4". If the task/cgroup plugin is used and ConstrainDevices is set in cgroup.conf, then the gres IDs are zero-based indexes relative to the gres allocated to the job (e.g. the first gres is 0, even if the global ID is 3). Otherwise, the gres IDs are global IDs, and all gres on each node in the job should be allocated for predictable binding results.
none
Do not bind tasks to this gres (turns off implicit binding from --tres-per-task and --gpus-per-task).
per_task:<gres_per_task>
Each task will be bound to the number of gres specified in <gres_per_task>. Tasks are preferentially assigned gres with affinity to cores in their allocation like in closest, though they will take any gres if they are unavailable. If no affinity exists, the first task will be assigned the first x number of gres on the node etc. Shared gres will prefer to bind one sharing device per task if possible.
single:<tasks_per_gres>
Like closest, except that each task can only be bound to a single gres, even when it can be bound to multiple gres that are equally close. The gres to bind to is determined by <tasks_per_gres>, where the first <tasks_per_gres> tasks are bound to the first gres available, the second <tasks_per_gres> tasks are bound to the second gres available, etc. This is basically a block distribution of tasks onto available gres, where the available gres are determined by the socket affinity of the task and the socket affinity of the gres as specified in gres.conf's Cores parameter.

NOTE: Shared gres binding is currently limited to per_task or none

--tres-per-task=<list>
Specifies a comma-delimited list of trackable resources required for the job on each task to be spawned in the job's resource allocation. The format for each entry in the list is "trestype[/tresname]=count". The trestype is the type of trackable resource requested (e.g. cpu, gres, license, etc). The tresname is the name of the trackable resource, as can be seen with sacctmgr show tres. This is required when it exists for tres types such as gres, license, etc. (e.g. gpu, gpu:a100). In order to request a license with this option, the license(s) must be defined in the AccountingStorageTRES parameter of slurm.conf. The count is the number of those resources.
The count can have a suffix of
"k" or "K" (multiple of 1024),
"m" or "M" (multiple of 1024 x 1024),
"g" or "G" (multiple of 1024 x 1024 x 1024),
"t" or "T" (multiple of 1024 x 1024 x 1024 x 1024),
"p" or "P" (multiple of 1024 x 1024 x 1024 x 1024 x 1024).
Examples: 
--tres-per-task=cpu=4
--tres-per-task=cpu=8,license/ansys=1
--tres-per-task=gres/gpu=1
--tres-per-task=gres/gpu:a100=2
The specified resources will be allocated to the job on each node. The available trackable resources are configurable by the system administrator.
NOTE: This option with gres/gpu or gres/shard will implicitly set --tres-bind=gres/[gpu|shard]:per_task:<tres_per_task>, or if multiple gpu types are specified --tres-bind=gres/gpu:per_task:<gpus_per_task_type_sum>. This can be overridden with an explicit --tres-bind specification.
NOTE: Invalid TRES for --tres-per-task include bb,billing,energy,fs,mem,node,pages,vmem.
--uid=<user>
Attempt to submit and/or run a job as user instead of the invoking user id. The invoking user's credentials will be used to check access permissions for the target partition. User root may use this option to run jobs as a normal user in a RootOnly partition for example. If run as root, sbatch will drop its permissions to the uid specified after node allocation is successful. user may be the user name or numerical user ID.
--usage
Display brief help message and exit.
--use-min-nodes
If a range of node counts is given, prefer the smaller count.
-v, --verbose
Increase the verbosity of sbatch's informational messages. Multiple errors will be displayed.
-V, --version
Display version information and exit.
-W, --wait
Do not exit until the submitted job terminates. The exit code of the sbatch command will be the same as the exit code of the submitted job. If the job terminated due to a signal rather than a normal exit, the exit code will be set to 1. In the case of a job array, the exit code recorded will be the highest value for any task in the job array.
--wait-all-nodes=<value>
Controls when the execution of the command begins. By default the job will begin execution as soon as the allocation is made.
0
Begin execution as soon as allocation can be made. Do not wait for all nodes to be ready for use (i.e. booted).
1
Do not begin execution until all nodes are ready for use.
--wckey=<wckey>
Specify wckey to be used with job. If TrackWCKey=no (default) in the slurm.conf this value is ignored.
--wrap=<command_string>
Sbatch will wrap the specified command string in a simple "sh" shell script, and submit that script to the slurm controller. When --wrap is used, a script name and arguments may not be specified on the command line; instead the sbatch-generated wrapper script is used.

sbatch allows for a filename pattern to contain one or more replacement symbols, which are a percent sign "%" followed by a letter (e.g. %j).

\\
Do not process any of the replacement symbols.
%%
The character "%".
%A
Job array's master job allocation number.
%a
Job array ID (index) number.
%b
Job array ID (index) number modulo 10.
%J
jobid.stepid of the running job (e.g. "128.0"). The stepid is only expanded for regular steps, not for special steps like "batch" or "extern".
%j
jobid of the running job.
%N
short hostname. This will create a separate IO file per node.

Node identifier relative to current job (e.g. "0" is the first node of the running job) This will create a separate IO file per node.
%r
Restart count of the running job.

SLUID of the running job.
%s
stepid of the running job.
%t
task identifier (rank) relative to current job. This will create a separate IO file per task.

User name.

Job name.

A number placed between the percent character and format specifier may be used to zero-p

RENDIMIENTO

La ejecución de sbatch envía una llamada a procedimiento remoto a slurmctld. Si llegan demasiadas llamadas de sbatch u otros comandos cliente de Slurm que envían llamadas a procedimiento remoto al demonio slurmctld al mismo tiempo, puede provocar una degradación del rendimiento del demonio slurmctld, lo que podría resultar en una denegación de servicio.

No ejecute sbatch u otros comandos cliente de Slurm que envíen llamadas a procedimiento remoto a slurmctld desde bucles en scripts de shell u otros programas. Asegúrese de que los programas limiten las llamadas a sbatch al mínimo necesario para la información que intenta recopilar.

SLURM_THREADS_PER_CORE
Esto solo se establece si se especificaron --threads-per-core o SBATCH_THREADS_PER_CORE. El valor se establecerá al valor especificado por --threads-per-core o SBATCH_THREADS_PER_CORE. Esto es utilizado por las llamadas posteriores a srun dentro de la asignación de trabajo.
SLURM_TOPOLOGY_ADDR
Esto se establece solo si el sistema tiene configurado el plugin topology/tree. El valor se establecerá en los nombres de los switches de red que puedan estar involucrados en las comunicaciones del trabajo, desde el switch de nivel superior del sistema hasta el switch de hoja y terminando con el nombre del nodo. Se usa un punto para separar cada nombre de componente de hardware.
SLURM_TOPOLOGY_ADDR_PATTERN
Esto se establece solo si el sistema tiene configurado el plugin topology/tree. El valor se establecerá a los tipos de componentes listados en SLURM_TOPOLOGY_ADDR. Cada componente se identificará como "switch" o "node". Se usa un punto para separar cada tipo de componente de hardware.
SLURM_TRES_PER_TASK
Se establece al valor de --tres-per-task. Si se especifican --cpus-per-task o --gpus-per-task, también se establece en SLURM_TRES_PER_TASK como si se hubiera especificado en --tres-per-task.
SLURMD_NODENAME
Nombre del nodo que ejecuta el script del trabajo.

EJEMPLOS

Especificar un script de lote en la línea de comandos. El script de lote especifica un límite de tiempo de 1 minuto para el trabajo.
$ cat myscript
#!/bin/sh
#SBATCH --time=1
srun hostname |sort
$ sbatch -N4 myscript
salloc: Granted job allocation 65537
$ cat slurm-65537.out
host1
host2
host3
host4
Pasar un script de lote a sbatch por entrada estándar:
$ sbatch -N4 <<EOF
> #!/bin/sh
> srun hostname |sort
> EOF
sbatch: Submitted batch job 65541
$ cat slurm-65541.out
host1
host2
host3
host4
Para crear un trabajo heterogéneo con 3 componentes, cada uno asignando un conjunto único de nodos:
$ sbatch -w node[2-3] : -w node4 : -w node[5-7] work.bash
Submitted batch job 34987
