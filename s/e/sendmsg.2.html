send(2) System Calls Manual send(2)

NOMBRE

send, sendto, sendmsg - enviar un mensaje en un socket

BIBLIOTECA

Standard C library (libc, -lc)

SINOPSIS

#include <sys/socket.h>
ssize_t send(int sockfd, const void *buf, size_t size, int flags);
ssize_t sendto(int sockfd, const void *buf, size_t size, int flags,
               const struct sockaddr *dest_addr, socklen_t addrlen);
ssize_t sendmsg(int sockfd, const struct msghdr *msg, int flags);

DESCRIPCIÓN

Las llamadas al sistema send(), sendto(), y sendmsg() se utilizan para transmitir un mensaje a otro socket.

La llamada send() sólo puede utilizarse cuando el socket está en estado conectado (para que el destinatario previsto se conozca). La única diferencia entre send() y write(2) es la presencia de flags. Con un argumento flags cero, send() es equivalente a write(2). Además, la siguiente llamada


send(sockfd, buf, size, flags);

es equivalente a


sendto(sockfd, buf, size, flags, NULL, 0);

El argumento sockfd es el descriptor de archivo del socket que envía.

Si sendto() se utiliza en un socket de modo conexión (SOCK_STREAM, SOCK_SEQPACKET), los argumentos dest_addr y addrlen se ignoran (y el error EISCONN puede ser devuelto cuando no son NULL y 0), y el error ENOTCONN se devuelve cuando el socket no estaba realmente conectado. De lo contrario, la dirección del destino se proporciona mediante dest_addr con addrlen especificando su tamaño. Para sendmsg(), la dirección del destino se proporciona mediante msg.msg_name, con msg.msg_namelen especificando su tamaño.

Para send() y sendto(), el mensaje se encuentra en buf y tiene un tamaño de size. Para sendmsg(), el mensaje está apuntado por los elementos del array msg.msg_iov. La llamada sendmsg() también permite enviar datos auxiliares (también conocidos como información de control).

Si el mensaje es demasiado largo para pasarlo de forma atómica a través del protocolo subyacente, se devuelve el error EMSGSIZE y el mensaje no se transmite.

No hay ninguna indicación implícita de fallo de entrega en un send(). Los errores detectados localmente se indican mediante un valor de retorno de -1.

Cuando el mensaje no cabe en el búfer de envío del socket, send() normalmente se bloquea, a menos que el socket se haya colocado en modo de E/S no bloqueante. En modo no bloqueante, fallaría con el error EAGAIN o EWOULDBLOCK en este caso. La llamada select(2) puede utilizarse para determinar cuándo es posible enviar más datos.

El argumento flags

El argumento flags es el OR bit a bit de cero o más de las siguientes banderas.

MSG_CONFIRM (desde Linux 2.3.15)
Indica a la capa de enlace que se produjo un progreso hacia adelante: se recibió una respuesta exitosa del otro lado. Si la capa de enlace no recibe esto, sondeará periódicamente al vecino (por ejemplo, mediante una ARP de unicast). Sólo es válido en sockets SOCK_DGRAM y SOCK_RAW y actualmente implementado sólo para IPv4 e IPv6. Consulte arp(7) para más detalles.
MSG_DONTROUTE
No utilizar una pasarela para enviar el paquete, enviar sólo a hosts en redes directamente conectadas. Esto se utiliza normalmente sólo por programas de diagnóstico o enrutamiento. Esto está definido sólo para familias de protocolos que enrutan; los sockets de paquetes no lo hacen.
MSG_DONTWAIT (desde Linux 2.2)
Habilita la operación no bloqueante; si la operación se bloquearía, se devolvería EAGAIN o EWOULDBLOCK. Esto proporciona un comportamiento similar a establecer la bandera O_NONBLOCK (a través de la operación F_SETFL de fcntl(2)), pero difiere en que MSG_DONTWAIT es una opción por llamada, mientras que O_NONBLOCK es una configuración en la descripción del archivo abierto (ver open(2)), que afectará a todos los hilos del proceso que llama, así como a otros procesos que mantengan descriptores de archivo que se refieran a la misma descripción de archivo abierto.
MSG_EOR (desde Linux 2.2)
Termina un registro (cuando esta noción es soportada, como para sockets de tipo SOCK_SEQPACKET).
MSG_MORE (desde Linux 2.4.4)
El llamante tiene más datos que enviar. Esta bandera se utiliza con sockets TCP para obtener el mismo efecto que la opción de socket TCP_CORK (ver tcp(7)), con la diferencia de que esta bandera puede establecerse por llamada.
Desde Linux 2.6, esta bandera también es compatible con sockets UDP, e informa al kernel de que empaquete todos los datos enviados en llamadas con esta bandera establecida en un único datagrama que sólo se transmite cuando se realiza una llamada que no especifica esta bandera. (Ver también la opción de socket UDP_CORK descrita en udp(7)).
MSG_NOSIGNAL (desde Linux 2.2)
No generar una señal SIGPIPE si el par en un socket orientado a flujo ha cerrado la conexión. El error EPIPE todavía se devuelve. Esto proporciona un comportamiento similar a usar sigaction(2) para ignorar SIGPIPE, pero, mientras que MSG_NOSIGNAL es una característica por llamada, ignorar SIGPIPE establece un atributo de proceso que afecta a todos los hilos del proceso.
MSG_OOB
Envía datos fuera de banda en sockets que soportan esta noción (por ejemplo, de tipo SOCK_STREAM); el protocolo subyacente también debe soportar datos fuera de banda.
MSG_FASTOPEN (desde Linux 3.7)
Intenta TCP Fast Open (RFC7413) y envía datos en el SYN como una combinación de connect(2) y write(2), realizando implícitamente una operación connect(2). Se bloquea hasta que los datos se almacenan en búfer y el handshake se completa. Para un socket no bloqueante, devuelve el número de bytes almacenados en búfer y enviados en el paquete SYN. Si la cookie no está disponible localmente, devuelve EINPROGRESS y envía un SYN con una solicitud de cookie Fast Open automáticamente. El llamante necesita escribir los datos de nuevo cuando el socket esté conectado. En caso de error, establece el mismo errno que connect(2) si el handshake falla. Esta bandera requiere habilitar el soporte del cliente TCP Fast Open en el sysctl net.ipv4.tcp_fastopen.
Consulte la opción de socket TCP_FASTOPEN_CONNECT en tcp(7) para un enfoque alternativo.

sendmsg()

La definición de la estructura msghdr utilizada por sendmsg() es la siguiente:


struct msghdr {
    void         *msg_name;       /* Dirección opcional */
    socklen_t     msg_namelen;    /* Tamaño de la dirección */
    struct iovec *msg_iov;        /* Array scatter/gather */
    size_t        msg_iovlen;     /* # de elementos en msg_iov */
    void         *msg_control;    /* Datos auxiliares, ver abajo */
    size_t        msg_controllen; /* Tamaño del búfer de datos auxiliares */
    int           msg_flags;      /* Flags (no utilizados) */
};

El campo msg_name se utiliza en un socket no conectado para especificar la dirección de destino de un datagrama. Apunta a un búfer que contiene la dirección; el campo msg_namelen debe establecerse al tamaño de la dirección. Para un socket conectado, estos campos deben especificarse como NULL y 0, respectivamente.

Los campos msg_iov y msg_iovlen especifican ubicaciones de scatter-gather, como en writev(2).

NAME

sendmsg - Enviar un mensaje a través de un socket

LIBRARY

Librería C estándar (libc)

SYNOPSIS

#include <sys/types.h>
#include <sys/socket.h>
#include <ctime.h>
#include <sys/uio.h>

ssize_t sendmsg(int sockfd, const struct msghdr *msg, int flags);

DESCRIPTION

The sendmsg() system call is a more general interface for sending messages than send(2) or sendto(2). It allows the caller to specify more information about the message being sent, such as ancillary data.

The msg argument is a pointer to a msghdr structure, which contains information to be used by the calling interface.

    struct msghdr {
        void         *msg_name;       /* Optional address to send message to. */
        socklen_t     msg_namelen;    /* Size of message data structure. */
        struct iovec *msg_iov;        /* Scatter/gather format array of
                                         buffers. */
        int           msg_iovlen;     /* Number of elements in msg_iov. */
        void         *msg_control;    /* Ancillary data (eg, control information). */
        socklen_t     msg_controllen; /* Ancillary data buffer length. */
        int           msg_flags;      /* Flags on send. */
    };

The members of the structure msghdr are:

msg_name
Specifies the destination address. This is required for connectionless sockets (like UDP) if they have not been previously connected using connect(2) or connectat(2). For connection-mode sockets (like TCP), this member must be NULL.
msg_namelen
Specifies the length of the address structure pointed to by msg_name.
msg_iov
Points to an array of iovec structures. Each iovec structure specifies the base address and the length of a buffer in memory. 
        struct iovec {
            void  *iov_base; /* Starting address of buffer */
            size_t iov_len;  /* Length of buffer */
        };
The sendmsg() call will transmit the data in these buffers sequentially, as if they were concatenated into a single message. The msg_iovlen member specifies the number of structures in the msg_iov array.
msg_control
Points to a buffer for ancillary data. Ancillary data can be used to pass protocol-specific control information (e.g., IP options or TCP control bits) along with a normal data message. If the socket is of a type that supports ancillary data, and the caller supplies ancillary data, sendmsg(2) will transmit this data. If the caller does not want to send ancillary data, msg_control should be NULL and msg_controllen should be 0. The format of ancillary data is described in cmsg(3).
msg_controllen
Specifies the length of the ancillary data buffer pointed to by msg_control.
msg_flags
Specifies flags that modify the behavior of the send operation. The following flags are recognized:

The msg_flags field is ignored.

RETURN VALUE

On success, these calls return the number of bytes sent. On error, -1 is returned, and errno is set to indicate the error.

ERRORS

These are some standard errors generated by the socket layer. Additional errors may be generated and returned from the underlying protocol modules; see their respective manual pages.

EACCES
(For UNIX domain sockets, which are identified by pathname) Write permission is denied on the destination socket file, or search permission is denied for one of the directories the path prefix. (See path_resolution(7).)
(For UDP sockets) An attempt was made to send to a network/broadcast address as though it was a unicast address.
EAGAIN or EWOULDBLOCK
The socket is marked nonblocking and the requested operation would block. POSIX.1-2001 allows either error to be returned for this case, and does not require these constants to have the same value, so a portable application should check for both possibilities.
EAGAIN
(Internet domain datagram sockets) The socket referred to by sockfd had not previously been bound to an address and, upon attempting to bind it to an ephemeral port, it was determined that all port numbers in the ephemeral port range are currently in use. See the discussion of /proc/sys/net/ipv4/ip_local_port_range in ip(7).
EALREADY
Another Fast Open is in progress.
EBADF
sockfd is not a valid open file descriptor.
ECONNRESET
Connection reset by peer.
EDESTADDRREQ
The socket is not connection-mode, and no peer address is set.
EFAULT
An invalid user space address was specified for an argument.
EINTR
A signal occurred before any data was transmitted; see signal(7).
EINVAL
Invalid argument passed.
EISCONN
The connection-mode socket was connected already but a recipient was specified. (Now either this error is returned, or the recipient specification is ignored.)
EMSGSIZE
The socket type requires that message be sent atomically, and the size of the message to be sent made this impossible.
ENOBUFS
The output queue for a network interface was full. This generally indicates that the interface has stopped sending, but may be caused by transient congestion. (Normally, this does not occur in Linux. Packets are just silently dropped when a device queue overflows.)
ENOMEM
No memory available.
ENOTCONN
The socket is not connected, and no target has been given.
ENOTSOCK
The file descriptor sockfd does not refer to a socket.
EOPNOTSUPP
Some bit in the flags argument is inappropriate for the socket type.
EPIPE
The local end has been shut down on a connection oriented socket. In this case, the process will also receive a SIGPIPE unless MSG_NOSIGNAL is set.

VERSIONS

According to POSIX.1-2001, the msg_controllen field of the msghdr structure should be typed as socklen_t, and the msg_iovlen field should be typed as int, but glibc currently types both as size_t.

STANDARDS

POSIX.1-2024.

MSG_CONFIRM is a Linux extension.

HISTORY

4.4BSD, SVr4, POSIX.1-2001. (first appeared in 4.2BSD).

POSIX.1-2001 describes only the MSG_OOB and MSG_EOR flags. POSIX.1-2008 adds a specification of MSG_NOSIGNAL.

NOTES

See sendmmsg(2) for information about a Linux-specific system call that can be used to transmit multiple datagrams in a single call.

BUGS

Linux may return EPIPE instead of ENOTCONN.

EXAMPLES

An example of the use of sendto() is shown in getaddrinfo(3).
