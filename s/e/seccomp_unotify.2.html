NOMBRE

seccomp_unotify - Mecanismo de notificación al espacio de usuario de Seccomp

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

DESCRIPCIÓN

Esta página describe el mecanismo de notificación al espacio de usuario proporcionado por la instalación de Computación Segura (seccomp). Además del uso de la bandera SECCOMP_FILTER_FLAG_NEW_LISTENER, el valor de acción SECCOMP_RET_USER_NOTIF y la operación SECCOMP_GET_NOTIF_SIZES descritas en seccomp(2), este mecanismo implica el uso de una serie de operaciones relacionadas de ioctl(2) (descritas a continuación).

Visión general

En el uso convencional de un filtro seccomp, la decisión sobre cómo tratar una llamada al sistema la toma el propio filtro. Por el contrario, el mecanismo de notificación al espacio de usuario permite que el filtro seccomp delegue el manejo de la llamada al sistema a otro proceso del espacio de usuario. Tenga en cuenta que este mecanismo explícitamente no está destinado como un método para implementar políticas de seguridad; véase NOTAS.

En la discusión que sigue, los hilos sobre los que está instalado el filtro seccomp se denominan el *objetivo*, y el proceso que es notificado por el mecanismo de notificación al espacio de usuario se denomina el *supervisor*.

Un supervisor adecuadamente privilegiado puede usar el mecanismo de notificación al espacio de usuario para realizar acciones en nombre del objetivo. La ventaja del mecanismo de notificación al espacio de usuario es que el supervisor generalmente podrá recuperar información sobre el objetivo y la llamada al sistema realizada que el propio filtro seccomp no puede. (Un filtro seccomp está limitado en la información que puede obtener y en las acciones que puede realizar, ya que se ejecuta en una máquina virtual dentro del kernel.)

Una visión general de los pasos realizados por el objetivo y el supervisor es la siguiente:

(1)
El objetivo establece un filtro seccomp de la manera habitual, pero con dos diferencias:
•
El argumento flags de seccomp(2) incluye la bandera SECCOMP_FILTER_FLAG_NEW_LISTENER. En consecuencia, el valor de retorno de la llamada (exitosa) a seccomp(2) es un nuevo descriptor de archivo "de escucha" que se puede utilizar para recibir notificaciones. Solo se puede instalar un filtro seccomp "de escucha" por hilo.
•
En los casos en que sea apropiado, el filtro seccomp devuelve el valor de acción SECCOMP_RET_USER_NOTIF. Este valor de retorno activará un evento de notificación.
(2)
Para que el supervisor pueda obtener notificaciones utilizando el descriptor de archivo de escucha, (un duplicado de) ese descriptor de archivo debe pasarse del objetivo al supervisor. Una forma de hacerlo es pasando el descriptor de archivo a través de una conexión de socket de dominio UNIX entre el objetivo y el supervisor (utilizando el tipo de mensaje auxiliar SCM_RIGHTS descrito en unix(7)). Otra forma de hacerlo es mediante el uso de pidfd_getfd(2).
(3)
El supervisor recibirá eventos de notificación en el descriptor de archivo de escucha. Estos eventos se devuelven como estructuras del tipo seccomp_notif. Dado que esta estructura y su tamaño pueden evolucionar con las versiones del kernel, el supervisor primero debe determinar el tamaño de esta estructura utilizando la operación SECCOMP_GET_NOTIF_SIZES de seccomp(2), que devuelve una estructura del tipo seccomp_notif_sizes. El supervisor asigna un búfer de tamaño seccomp_notif_sizes.seccomp_notif bytes para recibir eventos de notificación. Además, el supervisor asigna otro búfer de tamaño seccomp_notif_sizes.seccomp_notif_resp bytes para la respuesta (una estructura seccomp_notif_resp) que proporcionará al kernel (y, por lo tanto, al objetivo).
(4)
El objetivo realiza entonces su carga de trabajo, que incluye llamadas al sistema que serán controladas por el filtro seccomp. Siempre que una de estas llamadas al sistema haga que el filtro devuelva el valor de acción SECCOMP_RET_USER_NOTIF, el kernel no ejecuta (todavía) la llamada al sistema; en su lugar, la ejecución del objetivo se bloquea temporalmente dentro del kernel (en un estado de espera que puede ser interrumpido por señales) y se genera un evento de notificación en el descriptor de archivo de escucha.
(5)
El supervisor ahora puede monitorizar repetidamente el descriptor de archivo de escucha para eventos activados por SECCOMP_RET_USER_NOTIF. Para hacer esto, el supervisor utiliza la operación ioctl(2) SECCOMP_IOCTL_NOTIF_RECV para leer información sobre un evento de notificación; esta operación se bloquea hasta que hay un evento disponible. La operación devuelve una estructura seccomp_notif que contiene información sobre la llamada al sistema que está intentando el objetivo. (Como se describe en NOTAS, el descriptor de archivo también puede ser monitorizado con select(2), poll(2) o epoll(7).)
(6)
La estructura seccomp_notif devuelta por la operación SECCOMP_IOCTL_NOTIF_RECV incluye la misma información (una estructura seccomp_data) que se pasó al filtro seccomp. Esta información permite al supervisor descubrir el número de llamada al sistema y los argumentos de la llamada al sistema del objetivo. Además, el evento de notificación contiene el ID del hilo que activó la notificación y un valor de cookie único que se utiliza en operaciones posteriores de SECCOMP_IOCTL_NOTIF_ID_VALID y SECCOMP_IOCTL_NOTIF_SEND.
La información en la notificación se puede utilizar para descubrir los valores de los argumentos de puntero para la llamada al sistema del objetivo. (Esto es algo que no se puede hacer desde dentro de un filtro seccomp.) Una forma en que el supervisor puede hacer esto es abrir el archivo correspondiente de /proc/tid/mem (ver proc(5)) y leer bytes de la ubicación que corresponde a uno de los argumentos de puntero cuyo valor se proporciona en el evento de notificación. (El supervisor debe tener cuidado de evitar una condición de carrera que pueda ocurrir al hacer esto; véase la descripción de la operación ioctl(2) SECCOMP_IOCTL_NOTIF_ID_VALID más abajo.) Además, el supervisor puede acceder a otra información del sistema que sea visible en el espacio de usuario pero que no sea accesible desde un filtro seccomp.
(7)
Habiendo obtenido información según el paso anterior, el supervisor puede entonces elegir realizar una acción en respuesta a la llamada al sistema del objetivo (que, como se mencionó anteriormente, no se ejecuta cuando el filtro seccomp devuelve el valor de acción SECCOMP_RET_USER_NOTIF).
Un caso de uso de ejemplo aquí se relaciona con los contenedores. El objetivo puede estar ubicado dentro de un contenedor donde no tiene suficientes capacidades para montar un sistema de archivos en el espacio de nombres de montaje del contenedor. Sin embargo, el supervisor puede ser un proceso más privilegiado que sí tiene suficientes capacidades para realizar la operación de montaje.
(8)
El supervisor luego envía una respuesta a la notificación. La información en esta respuesta es utilizada por el kernel para construir un valor de retorno para la llamada al sistema del objetivo y proporcionar un valor que se asignará a la variable errno del objetivo.
La respuesta se envía utilizando la operación ioctl(2) SECCOMP_IOCTL_NOTIF_SEND, que se utiliza para transmitir una estructura seccomp_notif_resp al kernel. Esta estructura incluye un valor de cookie que el supervisor obtuvo en la estructura seccomp_notif devuelta por la operación ioctl(2) SECCOMP_IOCTL_NOTIF_RECV.

El mecanismo de notificación

El mecanismo de notificación se inicia configurando un filtro seccomp con la bandera SECCOMP_FILTER_FLAG_NEW_LISTENER. Esto hace que la llamada al sistema seccomp(2) devuelva un descriptor de archivo (el descriptor de archivo de escucha) en lugar de la usualmente esperada (y en este caso, vacía) estructura sockaddr. Este descriptor de archivo de escucha se puede duplicar y pasar a otro proceso (el supervisor).

Un filtro seccomp que utiliza este mecanismo debe configurarse para devolver el valor de acción SECCOMP_RET_USER_NOTIF para las llamadas al sistema que se desean delegar al supervisor.

Cuando una llamada al sistema se activa con el valor de acción SECCOMP_RET_USER_NOTIF, el kernel no ejecuta la llamada al sistema. En su lugar, se genera un evento de notificación en el descriptor de archivo de escucha. El proceso del objetivo se bloquea en la llamada al sistema hasta que el supervisor proporciona una respuesta.

Las notificaciones se reciben utilizando la operación SECCOMP_IOCTL_NOTIF_RECV en el descriptor de archivo de escucha. Esta operación se bloquea hasta que llega una notificación. La estructura seccomp_notif devuelta contiene información sobre la llamada al sistema que se está intentando, incluyendo la estructura seccomp_data y un valor de cookie.

La estructura seccomp_data dentro de seccomp_notif contiene la siguiente información:

nr
El número de llamada al sistema (como se define en /usr/include/asm/unistd_64.h).
args[0..4]
Los primeros cinco argumentos de la llamada al sistema. Tenga en cuenta que estos son valores de 64 bits incluso en sistemas de 32 bits, por lo que es posible que deba tener en cuenta el relleno.

El supervisor utiliza el valor de cookie para identificar la notificación específica cuando envía una respuesta usando la operación SECCOMP_IOCTL_NOTIF_SEND. La respuesta (en una estructura seccomp_notif_resp) especifica los valores de retorno y errno que el kernel utilizará para reanudar la llamada al sistema bloqueada del objetivo.

La operación SECCOMP_IOCTL_NOTIF_ADDFD permite al supervisor transferir descriptores de archivo adicionales al objetivo. Esto es útil si el supervisor necesita proporcionar al objetivo acceso a ciertos recursos (por ejemplo, un puerto de red abierto) para que el objetivo pueda completar su tarea después de que el supervisor haya intervenido.

La operación SECCOMP_IOCTL_NOTIF_ID_VALID permite al supervisor validar si una notificación (identificada por su ID) todavía está activa. Esto es útil para evitar condiciones de carrera cuando se intenta leer datos del espacio de direcciones del objetivo usando /proc/tid/mem. El supervisor debe llamar a esta operación después de abrir el archivo de memoria, pero antes de leerlo. Si la operación devuelve éxito, el supervisor puede proceder a leer la memoria; de lo contrario, debe obtener una nueva notificación.

El supervisor debe usar seccomp(2) con la operación SECCOMP_GET_NOTIF_SIZES para obtener los tamaños correctos de las estructuras de notificación y respuesta. Esto se debe a que estas estructuras pueden cambiar entre versiones del kernel.

Estructuras

La estructura seccomp_notif está definida en <linux/seccomp.h> como:

struct seccomp_notif {
    __u64 id;
    __u32 error;
    __u32 __unused;
    struct seccomp_data data;
};

La estructura seccomp_notif_resp está definida en <linux/seccomp.h> como:

struct seccomp_notif_resp {
    __u64 id;
    __s64 val;
    __s32 errno;
};

La estructura seccomp_notif_sizes está definida en <linux/seccomp.h> como:

struct seccomp_notif_sizes {
    __u16 seccomp_notif;
    __u16 seccomp_notif_resp;
};

La estructura seccomp_notif_addfd está definida en <linux/seccomp.h> como:

struct seccomp_notif_addfd {
    __u64 id;
    __u32 srcfd;
    __u32 flags;
};

Operaciones de ioctl

Las siguientes operaciones de ioctl(2) se aplican al descriptor de archivo de escucha:

SECCOMP_IOCTL_NOTIF_RECV
Lee la siguiente notificación del descriptor de archivo de escucha. Bloquea si no hay notificaciones pendientes. El argumento es un puntero a una estructura seccomp_notif.
SECCOMP_IOCTL_NOTIF_SEND
Envía una respuesta a una notificación pendiente. El argumento es un puntero a una estructura seccomp_notif_resp. El valor de id en la respuesta debe coincidir con el de la notificación que se está respondiendo.
SECCOMP_IOCTL_NOTIF_ID_VALID
Comprueba si una notificación con el ID dado sigue siendo válida. El argumento es un puntero a un __u64 que contiene el ID. Devuelve 0 en caso de éxito y -1 en caso de error (por ejemplo, si la notificación ya ha expirado).
SECCOMP_IOCTL_NOTIF_ADDFD
Transfiere un descriptor de archivo del supervisor al objetivo. El argumento es un puntero a una estructura seccomp_notif_addfd. El campo id debe coincidir con el de la notificación para la que se está añadiendo el descriptor de archivo. El campo srcfd es el descriptor de archivo que se va a transferir. El campo flags se puede usar para controlar el comportamiento (actualmente no se utilizan flags, así que debe ser 0).

Valores de retorno y errores

La llamada al sistema seccomp(2) devuelve el descriptor de archivo de escucha en caso de éxito, o -1 en caso de error y establece errno adecuadamente.

Las operaciones de ioctl(2) devuelven 0 en caso de éxito, o -1 en caso de error y establecen errno adecuadamente.

Los errores posibles para las operaciones de ioctl(2) incluyen:

EBADF
El descriptor de archivo proporcionado no es válido.
EFAULT
El argumento de puntero es inválido.
EINVAL
La operación de ioctl no es válida para el descriptor de archivo, o el ID de notificación no es válido.
ENOTTY
El descriptor de archivo no está asociado a un archivo de dispositivo apropiado (necesario para ioctl).
ENOMSG
No hay notificaciones pendientes para SECCOMP_IOCTL_NOTIF_RECV.
EPERM
El ID de notificación no es válido para SECCOMP_IOCTL_NOTIF_SEND o SECCOMP_IOCTL_NOTIF_ADDFD (por ejemplo, ya ha expirado o fue respondido).

CONFORMIDAD

Este mecanismo se introdujo en Linux 5.4. Las operaciones de ioctl(2) se introdujeron en Linux 5.11.

NOTAS

Este mecanismo no está destinado a la implementación de políticas de seguridad. Está diseñado para permitir que los procesos supervisen y posiblemente modifiquen el comportamiento de otros procesos en escenarios controlados, como la depuración o la monitorización.

La comunicación entre el objetivo y el supervisor (por ejemplo, pasar el descriptor de archivo de escucha) debe manejarse con cuidado para evitar condiciones de carrera y garantizar la seguridad.

Cuando se utiliza el mecanismo de notificación, el filtro seccomp debe diseñarse cuidadosamente para evitar bucles infinitos o la denegación de servicio. Por ejemplo, un filtro que notifica incondicionalmente un bucle podría hacer que el proceso se congele si el supervisor no responde.

El supervisor tiene acceso a información más detallada que la que el filtro seccomp podría obtener por sí mismo. Esto incluye la capacidad de leer la memoria del proceso objetivo. El supervisor debe ser consciente de las implicaciones de seguridad de esto y manejarlo con cuidado.

La operación SECCOMP_IOCTL_NOTIF_ADDFD transfiere la propiedad del descriptor de archivo del proceso supervisor al proceso objetivo. El objetivo es entonces responsable de cerrar el descriptor de archivo.

Tenga en cuenta que la llamada al sistema seccomp(2) cuando se utiliza la bandera SECCOMP_FILTER_FLAG_NEW_LISTENER devuelve el descriptor de archivo de escucha en lugar de la estructura sockaddr. Este descriptor de archivo de escucha está destinado a ser utilizado únicamente con operaciones de ioctl(2) y no es un descriptor de archivo de socket normal.

Es importante manejar el campo error en la estructura seccomp_notif. Si el supervisor no está preparado para manejar un error específico y simplemente devuelve 0 para el valor de retorno y el código de error, el error se devolverá al proceso objetivo como si hubiera ocurrido un error de sistema real.

EJEMPLOS

Los siguientes fragmentos de código ilustran el uso básico del mecanismo de notificación. Son simplificaciones y omiten el manejo de errores y otros detalles necesarios para una implementación robusta.

Objetivo (proceso que se somete a seccomp):

#include <linux/seccomp.h>
#include <linux/filter.h>
#include <sys/ioctl.h>
#include <stdio.h>
#include <unistd.h>
#include <stdlib.h>
#include <poll.h>

// Suponiendo que tenemos una función para establecer el filtro
// y obtener el descriptor de archivo de escucha.
// Por ejemplo:
// int install_user_notif_filter(int syscall_num);

int main() {
    int listener_fd = install_user_notif_filter( __NR_read ); // Notificar sobre read()

    if (listener_fd < 0) {
        perror("install_user_notif_filter");
        exit(EXIT_FAILURE);
    }

    // Pasar listener_fd al supervisor (por ejemplo, a través de un socket UNIX)

    // Ahora, realizar una llamada al sistema que se notificará
    char buf[100];
    ssize_t bytes_read = read(STDIN_FILENO, buf, sizeof(buf) - 1);
    // El programa se bloqueará aquí hasta que el supervisor responda.

    if (bytes_read > 0) {
        buf[bytes_read] = '\0';
        printf("Read %zd bytes: %s\n", bytes_read, buf);
    } else {
        perror("read");
    }

    close(listener_fd);
    return 0;
}

Supervisor:

#include <linux/seccomp.h>
#include <linux/filter.h>
#include <sys/ioctl.h>
#include <stdio.h>
#include <unistd.h>
#include <stdlib.h>
#include <poll.h>

// Suponiendo que tenemos una función para recibir el descriptor de archivo
// de escucha del objetivo (por ejemplo, a través de un socket UNIX).
// int receive_listener_fd();

int main() {
    int listener_fd = receive_listener_fd(); // Obtener el descriptor de archivo de escucha

    if (listener_fd < 0) {
        perror("receive_listener_fd");
        exit(EXIT_FAILURE);
    }

    // Obtener tamaños de estructura
    struct seccomp_notif_sizes sizes;
    if (seccomp(SECCOMP_GET_NOTIF_SIZES, 0, &sizes) == -1) {
        perror("seccomp(SECCOMP_GET_NOTIF_SIZES)");
        exit(EXIT_FAILURE);
    }

    struct seccomp_notif notification;
    struct seccomp_notif_resp response;

    // Esperar una notificación
    struct pollfd pfd = { .fd = listener_fd, .events = POLLIN };
    if (poll(&pfd, 1, -1) == -1) {
        perror("poll");
        exit(EXIT_FAILURE);
    }

    // Recibir la notificación
    if (ioctl(listener_fd, SECCOMP_IOCTL_NOTIF_RECV, &notification) == -1) {
        perror("ioctl(SECCOMP_IOCTL_NOTIF_RECV)");
        exit(EXIT_FAILURE);
    }

    printf("Received notification ID: %llu, Syscall: %d, Args: %llu, %llu, ...\n",
           (unsigned long long)notification.id,
           notification.data.nr,
           (unsigned long long)notification.data.args[0],
           (unsigned long long)notification.data.args[1]);

    // Preparar la respuesta (por ejemplo, permitir la llamada al sistema con éxito)
    response.id = notification.id;
    response.val = 0; // Valor de retorno exitoso
    response.errno = 0; // Sin error

    // Enviar la respuesta
    if (ioctl(listener_fd, SECCOMP_IOCTL_NOTIF_SEND, &response) == -1) {
        perror("ioctl(SECCOMP_IOCTL_NOTIF_SEND)");
        exit(EXIT_FAILURE);
    }

    printf("Responded to notification.\n");

    close(listener_fd);
    return 0;
}

OPERACIONES IOCTL

Las siguientes operaciones de ioctl(2) son compatibles con el descriptor de archivo de notificación del espacio de usuario de seccomp. Para cada una de estas operaciones, el primer argumento (descriptor de archivo) de ioctl(2) es el descriptor de archivo de escucha devuelto por una llamada a seccomp(2) con la bandera SECCOMP_FILTER_FLAG_NEW_LISTENER.

SECCOMP_IOCTL_NOTIF_RECV

La operación SECCOMP_IOCTL_NOTIF_RECV (disponible desde Linux 5.0) se utiliza para obtener un evento de notificación del espacio de usuario. Si no hay ningún evento de este tipo pendiente actualmente, la operación se bloquea hasta que ocurre un evento. El tercer argumento de ioctl(2) es un puntero a una estructura de la siguiente forma que contiene información sobre el evento. Esta estructura debe inicializarse a cero antes de la llamada.


struct seccomp_notif {
    __u64  id;              /* Cookie */
    __u32  pid;             /* TID del hilo destino */
    __u32  flags;           /* Actualmente no utilizado (0) */
    struct seccomp_data data;   /* Véase seccomp(2) */
};

Los campos de esta estructura son los siguientes:

id
Este es un cookie para la notificación. Se garantiza que cada cookie es único para el filtro seccomp correspondiente.
•
El cookie se puede utilizar con la operación SECCOMP_IOCTL_NOTIF_ID_VALID de ioctl(2) descrita a continuación.
•
Al devolver una respuesta de notificación al kernel, el supervisor debe incluir el valor del cookie en la estructura seccomp_notif_resp que se especifica como argumento de la operación SECCOMP_IOCTL_NOTIF_SEND.
pid
Este es el ID del hilo destino que activó el evento de notificación.
flags
Esta es una máscara de bits de banderas que proporciona información adicional sobre el evento. En la implementación actual, este campo es siempre cero.
data
Esta es una estructura seccomp_data que contiene información sobre la llamada al sistema que activó la notificación. Esta es la misma estructura que se pasa al filtro seccomp. Consulte seccomp(2) para obtener detalles de esta estructura.

En caso de éxito, esta operación devuelve 0; en caso de fallo, se devuelve -1 y errno se establece para indicar el error. Esta operación puede fallar con los siguientes errores:

EINVAL (desde Linux 5.5)
La estructura seccomp_notif que se pasó a la llamada contenía campos distintos de cero.
ENOENT
El hilo destino fue eliminado por una señal mientras se generaba la información de notificación, o la llamada al sistema (bloqueada) del destino fue interrumpida por un manejador de señales.

SECCOMP_IOCTL_NOTIF_ID_VALID

La operación SECCOMP_IOCTL_NOTIF_ID_VALID (disponible desde Linux 5.0) se utiliza para verificar que un ID de notificación devuelto por una operación anterior SECCOMP_IOCTL_NOTIF_RECV sigue siendo válido (es decir, que el destino todavía existe y su llamada al sistema todavía está bloqueada esperando una respuesta).

El tercer argumento de ioctl(2) es un puntero al cookie (id) devuelto por la operación SECCOMP_IOCTL_NOTIF_RECV.

Esta operación es necesaria para evitar condiciones de carrera que pueden ocurrir cuando el pid devuelto por la operación SECCOMP_IOCTL_NOTIF_RECV termina, y ese ID de proceso es reutilizado por otro proceso. Un ejemplo de este tipo de carrera es el siguiente:

(1)
Se genera una notificación en el descriptor de archivo de escucha. La seccomp_notif devuelta contiene el TID del hilo destino (en el campo pid de la estructura).
(2)
El destino termina.
(3)
Otro hilo o proceso se crea en el sistema que, por casualidad, reutiliza el TID que se liberó cuando el destino terminó.
(4)
El supervisor abre el archivo /proc/tid/mem para el TID obtenido en el paso 1, con la intención de (por ejemplo) inspeccionar la(s) ubicación(es) de memoria que contienen el(los) argumento(s) de la llamada al sistema que activó la notificación en el paso 1.

(Tenga en cuenta que si el destino termina después del último paso, una posterior read(2) del descriptor de archivo puede devolver 0, indicando fin de archivo).

Consulte NOTAS para una discusión de otros casos en los que deben realizarse comprobaciones de SECCOMP_IOCTL_NOTIF_ID_VALID.

En caso de éxito (es decir, el ID de notificación sigue siendo válido), esta operación devuelve 0. En caso de fallo (es decir, el ID de notificación ya no es válido), se devuelve -1 y errno se establece en ENOENT.

DESCRIPTION

The purpose of the user-space notification feature is to allow system calls to be performed on behalf of the target. The target's system call should either be handled by the supervisor or allowed to continue normally in the kernel (where standard security policies will be applied).

Note well: this mechanism must not be used to make security policy decisions about the system call, which would be inherently race-prone for reasons described next.

The SECCOMP_USER_NOTIF_FLAG_CONTINUE flag must be used with caution. If set by the supervisor, the target's system call will continue. However, there is a time-of-check, time-of-use race here, since an attacker could exploit the interval of time where the target is blocked waiting on the "continue" response to do things such as rewriting the system call arguments.

Note furthermore that a user-space notifier can be bypassed if the existing filters allow the use of seccomp(2) or prctl(2) to install a filter that returns an action value with a higher precedence than SECCOMP_RET_USER_NOTIF (see seccomp(2)).

It should thus be absolutely clear that the seccomp user-space notification mechanism can not be used to implement a security policy! It should only ever be used in scenarios where a more privileged process supervises the system calls of a lesser privileged target to get around kernel-enforced security restrictions when the supervisor deems this safe. In other words, in order to continue a system call, the supervisor should be sure that another security mechanism or the kernel itself will sufficiently block the system call if its arguments are rewritten to something unsafe.

Caveats regarding the use of

/proc/tid/mem The discussion above noted the need to use the SECCOMP_IOCTL_NOTIF_ID_VALID ioctl(2) when opening the /proc/tid/mem file of the target to avoid the possibility of accessing the memory of the wrong process in the event that the target terminates and its ID is recycled by another (unrelated) thread. However, the use of this ioctl(2) operation is also necessary in other situations, as explained in the following paragraphs.

Consider the following scenario, where the supervisor tries to read the pathname argument of a target's blocked mount(2) system call:

(1)
From one of its functions (func()), the target calls mount(2), which triggers a user-space notification and causes the target to block.
(2)
The supervisor receives the notification, opens /proc/tid/mem, and (successfully) performs the SECCOMP_IOCTL_NOTIF_ID_VALID check.
(3)
The target receives a signal, which causes the mount(2) to abort.
(4)
The signal handler executes in the target, and returns.
(5)
Upon return from the handler, the execution of func() resumes, and it returns (and perhaps other functions are called, overwriting the memory that had been used for the stack frame of func()).
(6)
Using the address provided in the notification information, the supervisor reads from the target's memory location that used to contain the pathname.
(7)
The supervisor now calls mount(2) with some arbitrary bytes obtained in the previous step.

The conclusion from the above scenario is this: since the target's blocked system call may be interrupted by a signal handler, the supervisor must be written to expect that the target may abandon its system call at any time; in such an event, any information that the supervisor obtained from the target's memory must be considered invalid.

To prevent such scenarios, every read from the target's memory must be separated from use of the bytes so obtained by a SECCOMP_IOCTL_NOTIF_ID_VALID check. In the above example, the check would be placed between the two final steps. An example of such a check is shown in EXAMPLES.

Following on from the above, it should be clear that a write by the supervisor into the target's memory can never be considered safe.

Caveats regarding blocking system calls

Suppose that the target performs a blocking system call (e.g., accept(2)) that the supervisor should handle. The supervisor might then in turn execute the same blocking system call.

In this scenario, it is important to note that if the target's system call is now interrupted by a signal, the supervisor is not informed of this. If the supervisor does not take suitable steps to actively discover that the target's system call has been canceled, various difficulties can occur. Taking the example of accept(2), the supervisor might remain blocked in its accept(2) holding a port number that the target (which, after the interruption by the signal handler, perhaps closed its listening socket) might expect to be able to reuse in a bind(2) call.

Therefore, when the supervisor wishes to emulate a blocking system call, it must do so in such a way that it gets informed if the target's system call is interrupted by a signal handler. For example, if the supervisor itself executes the same blocking system call, then it could employ a separate thread that uses the SECCOMP_IOCTL_NOTIF_ID_VALID operation to check if the target is still blocked in its system call. Alternatively, in the accept(2) example, the supervisor might use poll(2) to monitor both the notification file descriptor (so as to discover when the target's accept(2) call has been interrupted) and the listening file descriptor (so as to know when a connection is available).

If the target's system call is interrupted, the supervisor must take care to release resources (e.g., file descriptors) that it acquired on behalf of the target.

Interaction with SA_RESTART signal handlers

Consider the following scenario:

(1)
The target process has used sigaction(2) to install a signal handler with the SA_RESTART flag.
(2)
The target has made a system call that triggered a seccomp user-space notification and the target is currently blocked until the supervisor sends a notification response.
(3)
A signal is delivered to the target and the signal handler is executed.
(4)
When (if) the supervisor attempts to send a notification response, the SECCOMP_IOCTL_NOTIF_SEND ioctl(2)) operation will fail with the ENOENT error.

In this scenario, the kernel will restart the target's system call. Consequently, the supervisor will receive another user-space notification. Thus, depending on how many times the blocked system call is interrupted by a signal handler, the supervisor may receive multiple notifications for the same instance of a system call in the target.

One oddity is that system call restarting as described in this scenario will occur even for the blocking system calls listed in signal(7) that would never normally be restarted by the SA_RESTART flag.

Furthermore, if the supervisor response is a file descriptor added with SECCOMP_IOCTL_NOTIF_ADDFD, then the flag SECCOMP_ADDFD_FLAG_SEND can be used to atomically add the file descriptor and return that value, making sure no file descriptors are inadvertently leaked into the target.

BUGS

If a SECCOMP_IOCTL_NOTIF_RECV ioctl(2) operation is performed after the target terminates, then the ioctl(2) call simply blocks (rather than returning an error to indicate that the target no longer exists).
