setfsuid(2) Manual de llamadas al sistema setfsuid(2)

NOMBRE

setfsuid - establece la identidad de usuario utilizada para las comprobaciones del sistema de archivos

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

SINOPSIS

#include <sys/fsuid.h>
[[deprecated]] int setfsuid(uid_t fsuid);

DESCRIPCIÓN

En Linux, un proceso tiene tanto un ID de usuario del sistema de archivos como un ID de usuario efectivo. El ID de usuario del sistema de archivos (específico de Linux) se utiliza para las comprobaciones de permisos al acceder a objetos del sistema de archivos, mientras que el ID de usuario efectivo se utiliza para varios otros tipos de comprobaciones de permisos (véase credentials(7)).

Normalmente, el valor del ID de usuario del sistema de archivos del proceso es el mismo que el valor de su ID de usuario efectivo. Esto se debe a que cada vez que se cambia el ID de usuario efectivo de un proceso, el kernel también cambia el ID de usuario del sistema de archivos para que sea el mismo que el nuevo valor del ID de usuario efectivo. Un proceso puede hacer que el valor de su ID de usuario del sistema de archivos diverja de su ID de usuario efectivo utilizando setfsuid() para cambiar su ID de usuario del sistema de archivos al valor proporcionado en fsuid.

Las llamadas explícitas a setfsuid() y setfsgid(2) se utilizaban (eran utilizadas) normalmente solo por programas como el servidor NFS de Linux que necesitaban cambiar el ID de usuario y grupo que se utilizaba para el acceso a archivos sin un cambio correspondiente en los ID de usuario y grupo reales y efectivos. Un cambio en los ID de usuario normales para un programa como el servidor NFS es (era) un agujero de seguridad que puede exponerlo a señales no deseadas. (Sin embargo, este problema es histórico; véase más abajo).

setfsuid() tendrá éxito solo si el llamador es el superusuario o si fsuid coincide con el ID de usuario real, el ID de usuario efectivo, el ID de usuario guardado o el ID de usuario actual del sistema de archivos del llamador.

VALOR DE RETORNO

Tanto en caso de éxito como de fallo, esta llamada devuelve el ID de usuario del sistema de archivos anterior del llamador.

ESTÁNDARES

Linux.

HISTORIAL

Linux 1.2.

En el momento en que se introdujo esta llamada al sistema, un proceso podía enviar una señal a otro proceso con el mismo ID de usuario efectivo. Esto significaba que si un proceso privilegiado cambiaba su ID de usuario efectivo con el propósito de la verificación de permisos de archivos, entonces podría volverse vulnerable a recibir señales enviadas por otro proceso (no privilegiado) con el mismo ID de usuario. Por lo tanto, se agregó el atributo de ID de usuario del sistema de archivos para permitir que un proceso cambie su ID de usuario con el propósito de la verificación de permisos de archivos sin volverse vulnerable al mismo tiempo a recibir señales no deseadas. Desde Linux 2.0, el manejo de permisos de señales es diferente (véase kill(2)), lo que resulta en que un proceso puede cambiar su ID de usuario efectivo sin ser vulnerable a recibir señales de procesos no deseados. Por lo tanto, setfsuid() hoy en día es innecesario y debe evitarse en aplicaciones nuevas (lo mismo ocurre con setfsgid(2)).

La llamada al sistema original de Linux setfsuid() solo admitía ID de usuario de 16 bits. Posteriormente, Linux 2.4 agregó setfsuid32() que admite ID de 32 bits. La función de envoltura setfsuid() de glibc se encarga de forma transparente de la variación entre versiones del kernel.

Diferencias entre la biblioteca C y el kernel

En glibc 2.15 y versiones anteriores, cuando la envoltura para esta llamada al sistema determina que el argumento no se puede pasar al kernel sin truncamiento de enteros (porque el kernel es antiguo y no admite ID de usuario de 32 bits), devolverá -1 y establecerá errno en EINVAL sin intentar la llamada al sistema.

ERRORES

No se devuelven indicaciones de error de ningún tipo al llamador, y el hecho de que tanto las llamadas exitosas como las fallidas devuelvan el mismo valor hace que sea imposible determinar directamente si la llamada tuvo éxito o falló. En su lugar, el llamador debe recurrir a examinar el valor de retorno de una llamada posterior como setfsuid(-1) (que siempre fallará), para determinar si una llamada anterior a setfsuid() cambió el ID de usuario del sistema de archivos. Como mínimo, se debería devolver EPERM cuando la llamada falla (porque el llamador carece de la capacidad CAP_SETUID).

VéASE TAMBIÉN

kill(2), setfsgid(2), capabilities(7), credentials(7)
