sendfile(2) Manual de Llamadas al Sistema sendfile(2)

NOMBRE

sendfile - transferir datos entre descriptores de archivo

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

SINOPSIS

#include <sys/sendfile.h>
ssize_t sendfile(int out_fd, int in_fd, off_t *_Nullable offset,
                 size_t count);

DESCRIPCIÓN

sendfile() copia datos entre un descriptor de archivo y otro. Debido a que esta copia se realiza dentro del kernel, sendfile() es más eficiente que la combinación de read(2) y write(2), que requeriría transferir datos hacia y desde el espacio del usuario.

in_fd debe ser un descriptor de archivo abierto para lectura y out_fd debe ser un descriptor abierto para escritura.

Si offset no es NULL, entonces apunta a una variable que contiene el desplazamiento de archivo desde el cual sendfile() comenzará a leer datos de in_fd. Cuando sendfile() retorna, esta variable se establecerá al desplazamiento del byte siguiente al último byte que se leyó. Si offset no es NULL, entonces sendfile() no modifica el desplazamiento de archivo de in_fd; de lo contrario, el desplazamiento de archivo se ajusta para reflejar el número de bytes leídos de in_fd.

Si offset es NULL, entonces los datos se leerán de in_fd comenzando en el desplazamiento de archivo, y el desplazamiento de archivo se actualizará con la llamada.

count es el número de bytes a copiar entre los descriptores de archivo.

El argumento in_fd debe corresponder a un archivo que soporte operaciones tipo mmap(2) (es decir, no puede ser un socket). Excepto desde Linux 5.12 y si out_fd es una tubería (pipe), en cuyo caso sendfile() se descompone en un splice(2) y se aplican sus restricciones.

Antes de Linux 2.6.33, out_fd debía referirse a un socket. Desde Linux 2.6.33 puede ser cualquier archivo. Si es buscable, entonces sendfile() cambia apropiadamente el desplazamiento del archivo.

VALOR DE RETORNO

Si la transferencia fue exitosa, se devuelve el número de bytes escritos en out_fd. Tenga en cuenta que una llamada exitosa a sendfile() puede escribir menos bytes de los solicitados; el llamador debe estar preparado para reintentar la llamada si hubo bytes no enviados. Ver también NOTAS.

En caso de error, se devuelve -1 y se establece errno para indicar el error.

ERRORES

EAGAIN
Se ha seleccionado E/S no bloqueante usando O_NONBLOCK y la escritura bloquearía.
EBADF
El archivo de entrada no se abrió para lectura o el archivo de salida no se abrió para escritura.
EFAULT
Dirección incorrecta.
EINVAL
El descriptor no es válido o está bloqueado, o una operación tipo mmap(2) no está disponible para in_fd, o count es negativo.
EINVAL
out_fd tiene el flag O_APPEND establecido. Esto no está actualmente soportado por sendfile().
EIO
Error no especificado al leer de in_fd.
ENOMEM
Memoria insuficiente para leer de in_fd.
EOVERFLOW
count es demasiado grande, la operación resultaría en exceder el tamaño máximo del archivo de entrada o del archivo de salida.
ESPIPE
offset no es NULL pero el archivo de entrada no es buscable.

VERSIONES

Otros sistemas UNIX implementan sendfile() con semánticas y prototipos diferentes. No debe usarse en programas portables.

ESTÁNDARES

Ninguno.

HISTORIA

Linux 2.2, glibc 2.1.

En Linux 2.4 y anteriores, out_fd también podía referirse a un archivo regular; esta posibilidad desapareció en la serie de kernels Linux 2.6.x, pero se restauró en Linux 2.6.33.

La llamada al sistema original sendfile() de Linux no fue diseñada para manejar desplazamientos de archivo grandes. En consecuencia, Linux 2.4 añadió sendfile64(), con un tipo más amplio para el argumento offset. La función de envoltura sendfile() de glibc maneja transparente las diferencias del kernel.

NOTAS

sendfile() transferirá como máximo 0x7ffff000 (2.147.479.552) bytes, devolviendo el número de bytes realmente transferidos. (Esto es cierto tanto en sistemas de 32 como de 64 bits).

Si planea usar sendfile() para enviar archivos a un socket TCP, pero necesita enviar algunos datos de encabezado delante del contenido del archivo, le resultará útil emplear la opción TCP_CORK, descrita en tcp(7), para minimizar el número de paquetes y optimizar el rendimiento.

Las aplicaciones pueden desear recurrir a read(2) y write(2) en el caso en que sendfile() falle con EINVAL o ENOSYS.

Si out_fd se refiere a un socket o tubería con soporte de copia cero (zero-copy), los llamadores deben asegurarse de que las porciones transferidas del archivo al que se refiere in_fd permanezcan sin modificar hasta que el lector en el otro extremo de out_fd haya consumido los datos transferidos.

La llamada splice(2) específica de Linux soporta la transferencia de datos entre descriptores de archivo arbitrarios siempre que uno (o ambos) de ellos sea una tubería.

VER TAMBIÉN
