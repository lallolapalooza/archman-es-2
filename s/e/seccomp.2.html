seccomp(2) Manual de llamadas al sistema seccomp(2)

NOMBRE

seccomp - operar sobre el estado de Computación Segura del proceso

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

SINOPSIS

#include <linux/seccomp.h>  /* Definición de las constantes SECCOMP_* */
#include <linux/filter.h>   /* Definición de struct sock_fprog */
#include <linux/audit.h>    /* Definición de las constantes AUDIT_* */
#include <linux/signal.h>   /* Definición de las constantes SIG* */
#include <sys/ptrace.h>     /* Definición de las constantes PTRACE_* */
#include <sys/syscall.h>    /* Definición de las constantes SYS_* */
#include <unistd.h>
int syscall(SYS_seccomp, unsigned int operacion, unsigned int flags,
            void *args);

Nota: glibc no proporciona un envoltorio para seccomp(), lo que hace necesario el uso de syscall(2).

DESCRIPCIÓN

La llamada al sistema seccomp() opera sobre el estado de Computación Segura (seccomp) del proceso que llama.

Actualmente, Linux soporta los siguientes valores de operacion:

SECCOMP_SET_MODE_STRICT
Las únicas llamadas al sistema que el hilo que llama tiene permitido realizar son read(2), write(2), _exit(2) (pero no exit_group(2)), y sigreturn(2). Otras llamadas al sistema resultan en la terminación del hilo que llama, o la terminación de todo el proceso con la señal SIGKILL cuando solo hay un hilo. El modo estricto de computación segura es útil para aplicaciones de cálculo numérico que pueden necesitar ejecutar código de bytes no confiable, quizás obtenido al leer de una tubería o socket.
Tenga en cuenta que aunque el hilo que llama ya no puede llamar a sigprocmask(2), puede usar sigreturn(2) para bloquear todas las señales aparte de SIGKILL y SIGSTOP. Esto significa que alarm(2) (por ejemplo) no es suficiente para restringir el tiempo de ejecución del proceso. En su lugar, para terminar de manera confiable el proceso, se debe usar SIGKILL. Esto se puede hacer usando timer_create(2) con SIGEV_SIGNAL y sigev_signo establecido a SIGKILL, o usando setrlimit(2) para establecer el límite duro para RLIMIT_CPU.
Esta operación solo está disponible si el kernel está configurado con CONFIG_SECCOMP habilitado.
El valor de flags debe ser 0, y args debe ser NULL.
Esta operación es funcionalmente idéntica a la llamada:

prctl(PR_SET_SECCOMP, SECCOMP_MODE_STRICT);

SECCOMP_SET_MODE_FILTER
Las llamadas al sistema permitidas se definen por un puntero a un Filtro de Paquetes Berkeley (BPF) pasado a través de args. Este argumento es un puntero a una struct sock_fprog; puede diseñarse para filtrar llamadas al sistema arbitrarias y argumentos de llamadas al sistema. Si el filtro no es válido, seccomp() falla, devolviendo EINVAL en errno.
Si fork(2) o clone(2) están permitidos por el filtro, cualquier proceso hijo estará limitado a los mismos filtros de llamadas al sistema que el padre. Si execve(2) está permitido, los filtros existentes se conservarán a través de una llamada a execve(2).
Para usar la operación SECCOMP_SET_MODE_FILTER, el hilo que llama debe tener la capacidad CAP_SYS_ADMIN en su espacio de nombres de usuario, o el hilo ya debe tener el bit no_new_privs establecido. Si ese bit no estaba ya establecido por un ancestro de este hilo, el hilo debe hacer la siguiente llamada:

prctl(PR_SET_NO_NEW_PRIVS, 1);

De lo contrario, la operación SECCOMP_SET_MODE_FILTER falla y devuelve EACCES en errno. Este requisito garantiza que un proceso no privilegiado no pueda aplicar un filtro malicioso y luego invocar un programa set-user-ID u otro programa privilegiado usando execve(2), comprometiendo así potencialmente ese programa. (Tal filtro malicioso podría, por ejemplo, hacer que un intento de usar setuid(2) para establecer los IDs de usuario del llamante a valores distintos de cero devuelva en su lugar 0 sin realizar realmente la llamada al sistema. Por lo tanto, el programa podría ser engañado para retener privilegios de superusuario en circunstancias en las que es posible influir en él para que haga cosas peligrosas porque en realidad no eliminó privilegios.)
Si prctl(2) o seccomp() están permitidos por el filtro adjunto, se pueden agregar filtros adicionales. Esto aumentará el tiempo de evaluación, pero permite una mayor reducción de la superficie de ataque durante la ejecución de un hilo.
La operación SECCOMP_SET_MODE_FILTER solo está disponible si el kernel está configurado con CONFIG_SECCOMP_FILTER habilitado.
Cuando flags es 0, esta operación es funcionalmente idéntica a la llamada:

prctl(PR_SET_SECCOMP, SECCOMP_MODE_FILTER, args);

Las flags reconocidas son:
SECCOMP_FILTER_FLAG_LOG (desde Linux 4.14)
Todas las acciones de retorno del filtro excepto SECCOMP_RET_ALLOW deberían registrarse. Un administrador puede anular esta bandera de filtro impidiendo que acciones específicas se registren a través del archivo /proc/sys/kernel/seccomp/actions_logged.
SECCOMP_FILTER_FLAG_NEW_LISTENER (desde Linux 5.0)
Después de instalar con éxito el programa filtro, devuelva un nuevo descriptor de archivo de notificación del espacio de usuario. (La bandera de cierre en ejecución está establecida para el descriptor de archivo.) Cuando el filtro devuelve SECCOMP_RET_USER_NOTIF, se enviará una notificación a este descriptor de archivo.
Como máximo, se puede instalar un filtro seccomp usando la bandera SECCOMP_FILTER_FLAG_NEW_LISTENER para un hilo.
Vea seccomp_unotify(2) para más detalles.
SECCOMP_FILTER_FLAG_SPEC_ALLOW (desde Linux 4.17)
Deshabilita la mitigación de Speculative Store Bypass.
SECCOMP_FILTER_FLAG_TSYNC
Al agregar un nuevo filtro, sincronice todos los demás hilos del proceso llamante al mismo árbol de filtros seccomp. Un "árbol de filtros" es la lista ordenada de filtros adjuntos a un hilo. (Adjuntar filtros idénticos en llamadas separadas a seccomp() resulta en filtros diferentes desde esta perspectiva.)
Si algún hilo no puede sincronizarse al mismo árbol de filtros, la llamada no adjuntará el nuevo filtro seccomp y fallará, devolviendo el primer ID de hilo encontrado que no puede sincronizarse. La sincronización fallará si otro hilo en el mismo proceso está en SECCOMP_MODE_STRICT o si ha adjuntado nuevos filtros seccomp a sí mismo, divergiendo del árbol de filtros del hilo que llama.
SECCOMP_GET_ACTION_AVAIL (desde Linux 4.14)
Prueba para ver si una acción es soportada por el kernel. Esta operación es útil para confirmar que el kernel conoce una acción de retorno de filtro añadida más recientemente, ya que el kernel trata todas las acciones desconocidas como SECCOMP_RET_KILL_PROCESS.
El valor de flags debe ser 0, y args debe ser un puntero a una acción de retorno de filtro sin signo de 32 bits.
La operación SECCOMP_GET_ACTION_AVAIL está disponible solo si el kernel está configurado con CONFIG_SECCOMP habilitado.

DIAGNÓSTICOS

En caso de éxito, seccomp() devuelve 0. En caso de error, devuelve -1 y errno se establece para indicar el error.

Los errores comunes son:

EACCES
Se intentó usar SECCOMP_SET_MODE_FILTER sin tener previamente establecido el bit no_new_privs y sin tener la capacidad CAP_SYS_ADMIN.
EINVAL
El valor de operation no es válido, o el filtro especificado por args en SECCOMP_SET_MODE_FILTER no es válido.
EPERM
El proceso ya tiene un modo seccomp establecido (es decir, estricto o basado en filtro) y no se permite agregar más filtros o cambiar a un modo diferente.
EBUSY
Se intentó usar SECCOMP_FILTER_FLAG_TSYNC pero otro hilo ya está en un modo seccomp incompatible (por ejemplo, SECCOMP_MODE_STRICT).

VERSIONES

La llamada al sistema seccomp() se introdujo en Linux 3.5. La operación SECCOMP_SET_MODE_STRICT se introdujo originalmente en Linux 2.6.32 (como una característica de prctl(2), prctl(2)(2)). La operación SECCOMP_SET_MODE_FILTER se introdujo en Linux 3.5.

Las banderas SECCOMP_FILTER_FLAG_LOG y SECCOMP_GET_ACTION_AVAIL se introdujeron en Linux 4.14.

La bandera SECCOMP_FILTER_FLAG_SPEC_ALLOW se introdujo en Linux 4.17.

La bandera SECCOMP_FILTER_FLAG_NEW_LISTENER se introdujo en Linux 5.0.

CONFORMIDAD CON LA ESTANDARIZACIÓN

Esta llamada al sistema no está estandarizada. Su comportamiento puede variar en futuras versiones del kernel de Linux.

Filtros

Al agregar filtros a través de SECCOMP_SET_MODE_FILTER, args apunta a un programa de filtro:


struct sock_fprog {
    unsigned short      len;    /* Número de instrucciones BPF */
    struct sock_filter *filter; /* Puntero a matriz de
                                   instrucciones BPF */
};

Cada programa debe contener una o más instrucciones BPF:


struct sock_filter {            /* Bloque de filtro */
    __u16 code;                 /* Código de filtro real */
    __u8  jt;                   /* Salto verdadero */
    __u8  jf;                   /* Salto falso */
    __u32 k;                    /* Campo genérico multiuso */
};

Al ejecutar las instrucciones, el programa BPF opera sobre la información de llamada al sistema disponible (es decir, usa el modo de direccionamiento BPF_ABS) como un búfer (de solo lectura) de la siguiente forma:


struct seccomp_data {
    int   nr;                   /* Número de llamada al sistema */
    __u32 arch;                 /* Valor AUDIT_ARCH_*
                                   (ver <linux/audit.h>) */
    __u64 instruction_pointer;  /* Puntero de instrucción de la CPU */
    __u64 args[6];              /* Hasta 6 argumentos de llamada al sistema */
};

Debido a que la numeración de las llamadas al sistema varía entre arquitecturas y algunas arquitecturas (por ejemplo, x86-64) permiten que el código del espacio de usuario utilice las convenciones de llamada de múltiples arquitecturas (y la convención utilizada puede variar durante la vida de un proceso que utiliza execve(2) para ejecutar binarios que emplean diferentes convenciones), generalmente es necesario verificar el valor del campo arch.

Se recomienda encarecidamente utilizar un enfoque de lista de permitidos siempre que sea posible, ya que dicho enfoque es más robusto y simple. Una lista de denegación tendrá que actualizarse cada vez que se agregue una llamada al sistema potencialmente peligrosa (o una bandera u opción peligrosa si se deniegan), y a menudo es posible alterar la representación de un valor sin alterar su significado, lo que lleva a eludir la lista de denegación. Ver también Advertencias a continuación.

El campo arch no es único para todas las convenciones de llamada. La ABI x86-64 y la ABI x32 utilizan ambas AUDIT_ARCH_X86_64 como arch, y se ejecutan en los mismos procesadores. En su lugar, se utiliza la máscara __X32_SYSCALL_BIT en el número de llamada al sistema para distinguir entre las dos ABI.

Esto significa que una política debe denegar todas las llamadas al sistema con __X32_SYSCALL_BIT o debe reconocer las llamadas al sistema con y sin __X32_SYSCALL_BIT establecido. Una lista de llamadas al sistema a denegar basada en nr que no contenga también valores nr con __X32_SYSCALL_BIT establecido puede ser eludida por un programa malicioso que establezca __X32_SYSCALL_BIT.

Además, los kernels anteriores a Linux 5.4 permitían incorrectamente nr en los rangos 512-547, así como las llamadas al sistema no x32 correspondientes OR con __X32_SYSCALL_BIT. Por ejemplo, nr == 521 y nr == (101 | __X32_SYSCALL_BIT) resultarían en invocaciones de ptrace(2) con semántica x32 vs x86_64 potencialmente confusa en el kernel. Las políticas destinadas a funcionar en kernels anteriores a Linux 5.4 deben garantizar que deniegan o manejan correctamente estas llamadas al sistema. En Linux 5.4 y versiones posteriores, tales llamadas al sistema fallarán con el error ENOSYS, sin hacer nada.

El campo instruction_pointer proporciona la dirección de la instrucción del lenguaje máquina que realizó la llamada al sistema. Esto puede ser útil en conjunto con el uso de /proc/pid/maps para realizar comprobaciones basadas en qué región (mapeo) del programa realizó la llamada al sistema. (Probablemente, sea prudente bloquear las llamadas al sistema mmap(2) y mprotect(2) para evitar que el programa subvierta dichas comprobaciones.)

Al verificar valores de args, tenga en cuenta que los argumentos a menudo se truncan silenciosamente antes de ser procesados, pero después de la verificación seccomp. Por ejemplo, esto ocurre si se utiliza la ABI i386 en un kernel x86-64: aunque el kernel normalmente no mirará más allá de los 32 bits menos significativos de los argumentos, los valores de los registros completos de 64 bits estarán presentes en los datos seccomp. Un ejemplo menos sorprendente es que si se utiliza la ABI x86-64 para realizar una llamada al sistema que toma un argumento de tipo int, la mitad más significativa del registro de argumento es ignorada por la llamada al sistema, pero visible en los datos seccomp.

Un filtro seccomp devuelve un valor de 32 bits que consta de dos partes: los 16 bits más significativos (correspondientes a la máscara definida por la constante SECCOMP_RET_ACTION_FULL) contienen uno de los valores de "acción" que se enumeran a continuación; los 16 bits menos significativos (definidos por la constante SECCOMP_RET_DATA) son "datos" para asociar con este valor de retorno.

Si existen múltiples filtros, todos se ejecutan, en orden inverso a su adición al árbol de filtros —es decir, el filtro instalado más recientemente se ejecuta primero. (Tenga en cuenta que todos los filtros se llamarán incluso si uno de los filtros anteriores devuelve SECCOMP_RET_KILL. Esto se hace para simplificar el código del kernel y para proporcionar una pequeña mejora en la ejecución de conjuntos de filtros al evitar una comprobación de este caso poco común). El valor de retorno para la evaluación de una llamada al sistema dada es el valor de acción visto por primera vez de mayor precedencia (junto con sus datos adjuntos) devuelto por la ejecución de todos los filtros.

En orden decreciente de precedencia, los valores de acción que pueden ser devueltos por un filtro seccomp son:

SECCOMP_RET_KILL_PROCESS (desde Linux 4.14)
Este valor resulta en la terminación inmediata del proceso, con un volcado del núcleo. La llamada al sistema no se ejecuta. A diferencia de SECCOMP_RET_KILL_THREAD a continuación, todos los hilos del grupo de hilos se terminan. (Para una discusión sobre grupos de hilos, ver la descripción de la bandera CLONE_THREAD en clone(2).)
El proceso termina como si hubiera sido terminado por una señal SIGSYS. Incluso si se ha registrado un manejador de señales para SIGSYS, el manejador será ignorado en este caso y el proceso siempre termina. Para un proceso padre que está esperando a este proceso (usando waitpid(2) o similar), el wstatus devuelto indicará que su hijo fue terminado como si por una señal SIGSYS.
SECCOMP_RET_KILL_THREAD (o SECCOMP_RET_KILL)
Este valor resulta en la terminación inmediata del hilo que realizó la llamada al sistema. La llamada al sistema no se ejecuta. Otros hilos del mismo grupo de hilos continuarán ejecutándose.
El hilo termina como si hubiera sido terminado por una señal SIGSYS. Ver SECCOMP_RET_KILL_PROCESS arriba.
Antes de Linux 4.11, cualquier proceso terminado de esta manera no activaría un volcado del núcleo (aunque SIGSYS está documentado en signal(7) como con una acción predeterminada de terminación con volcado del núcleo). Desde Linux 4.11, un proceso de un solo hilo volcará el núcleo si se termina de esta manera.
Con la adición de SECCOMP_RET_KILL_PROCESS en Linux 4.14, SECCOMP_RET_KILL_THREAD se añadió como sinónimo de SECCOMP_RET_KILL, para distinguir más claramente las dos acciones.
Nota: el uso de SECCOMP_RET_KILL_THREAD para terminar un solo hilo en un proceso multihilo probablemente dejará al proceso en un estado permanentemente inconsistente y posiblemente corrupto.
SECCOMP_RET_TRAP
Este valor resulta en que el kernel envíe una señal SIGSYS dirigida al hilo al hilo que la desencadenó. (La llamada al sistema no se ejecuta). Varios campos se establecerán en la estructura siginfo_t (ver sigaction(2)) asociada a la señal:
•
si_signo contendrá SIGSYS.
•
si_call_addr mostrará la dirección de la instrucción de llamada al sistema.
•
si_syscall y si_arch indicarán qué llamada al sistema se intentó.
•
si_code contendrá SYS_SECCOMP.
•
si_errno contendrá la porción SECCOMP_RET_DATA del valor de retorno del filtro.
El contador de programa estará como si la llamada al sistema hubiera ocurrido (es decir, el contador de programa no apuntará a la instrucción de llamada al sistema). El registro de valor de retorno contendrá un valor dependiente de la arquitectura; si se reanuda la ejecución, establézcalo en algo apropiado para la llamada al sistema. (La dependencia de la arquitectura se debe a que reemplazarlo con ENOSYS podría sobrescribir información útil).
SECCOMP_RET_ERRNO
Este valor resulta en que la porción SECCOMP_RET_DATA del valor de retorno del filtro se pase al espacio de usuario como valor errno sin ejecutar la llamada al sistema.
SECCOMP_RET_USER_NOTIF (desde Linux 5.0)
Reenviar la llamada al sistema a un proceso supervisor de espacio de usuario adjunto para permitir que ese proceso decida qué hacer con la llamada al sistema. Si no hay un supervisor adjunto (ya sea porque el filtro no se instaló con la bandera SECCOMP_FILTER_FLAG_NEW_LISTENER o porque el descriptor de archivo se cerró), el filtro devuelve ENOSYS (similar a lo que sucede cuando un filtro devuelve SECCOM
