SELECT_TUT(2) Manual de llamadas al sistema SELECT_TUT(2)

NOMBRE

select, pselect - multiplexación de E/S síncrona

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

SINOPSIS

Véase select(2)

DESCRIPCIÓN

Las llamadas al sistema select() y pselect() se utilizan para monitorizar eficientemente múltiples descriptores de archivo, para ver si alguno de ellos está, o se vuelve, "listo"; es decir, para ver si la E/S es posible, o ha ocurrido una "condición excepcional" en alguno de los descriptores de archivo.

Esta página proporciona información de fondo y tutorial sobre el uso de estas llamadas al sistema. Para obtener detalles sobre los argumentos y la semántica de select() y pselect(), consulte select(2).

Combinación de eventos de señal y datos

pselect() es útil si está esperando una señal además de que los descriptores de archivo estén listos para E/S. Los programas que reciben señales normalmente usan el manejador de señales solo para activar una bandera global. La bandera global indicará que el evento debe procesarse en el bucle principal del programa. Una señal provocará que la llamada select() (o pselect()) regrese con errno establecido en EINTR. Este comportamiento es esencial para que las señales puedan ser procesadas en el bucle principal del programa, de lo contrario select() se bloquearía indefinidamente.

Ahora, en algún lugar del bucle principal habrá una condición para comprobar la bandera global. Entonces debemos preguntar: ¿qué pasa si una señal llega después de la condición, pero antes de la llamada select()? La respuesta es que select() se bloquearía indefinidamente, aunque en realidad haya un evento pendiente. Esta condición de carrera se resuelve con la llamada pselect(). Esta llamada se puede utilizar para establecer la máscara de señales a un conjunto de señales que solo se recibirán dentro de la llamada pselect(). Por ejemplo, supongamos que el evento en cuestión era la salida de un proceso hijo. Antes del inicio del bucle principal, bloquearíamos SIGCHLD usando sigprocmask(2). Nuestra llamada pselect() habilitaría SIGCHLD usando una máscara de señal vacía. Nuestro programa se vería así:

static volatile sig_atomic_t got_SIGCHLD = 0;
static void
child_sig_handler(int sig)
{
    got_SIGCHLD = 1;
}
int
main(int argc, char *argv[])
{
    sigset_t sigmask, empty_mask;
    struct sigaction sa;
    fd_set readfds, writefds, exceptfds;
    int r;
    sigemptyset(&sigmask);
    sigaddset(&sigmask, SIGCHLD);
    if (sigprocmask(SIG_BLOCK, &sigmask, NULL) == -1) {
        perror("sigprocmask");
        exit(EXIT_FAILURE);
    }
    sa.sa_flags = 0;
    sa.sa_handler = child_sig_handler;
    sigemptyset(&sa.sa_mask);
    if (sigaction(SIGCHLD, &sa, NULL) == -1) {
        perror("sigaction");
        exit(EXIT_FAILURE);
    }
    sigemptyset(&empty_mask);
    for (;;) {          /* bucle principal */
        /* Inicializar readfds, writefds y exceptfds
           antes de la llamada a pselect(). (Código omitido.)  */
        r = pselect(nfds, &readfds, &writefds, &exceptfds,
                    NULL, &empty_mask);
        if (r == -1 && errno != EINTR) {
            /* Manejar error */
        }
        if (got_SIGCHLD) {
            got_SIGCHLD = 0;
            /* Manejar evento con señal aquí; por ejemplo, wait() para todos
               los hijos terminados. (Código omitido.)  */
        }
        /* cuerpo principal del programa */
    }
}

Práctico

Entonces, ¿cuál es el propósito de select()? ¿No puedo simplemente leer y escribir en mis descriptores de archivo cuando quiera? El propósito de select() es que vigila múltiples descriptores al mismo tiempo y pone correctamente el proceso a dormir si no hay actividad. Los programadores de UNIX a menudo se encuentran en una posición en la que tienen que manejar E/S de más de un descriptor de archivo donde el flujo de datos puede ser intermitente. Si solo creara una secuencia de llamadas read(2) y write(2), encontraría que una de sus llamadas podría bloquearse esperando datos de/hacia un descriptor de archivo, mientras que otro descriptor de archivo no se utiliza aunque esté listo para E/S. select() maneja eficientemente esta situación.

Ley de select

Muchas personas que intentan usar select() se encuentran con un comportamiento difícil de entender y que produce resultados no portátiles o limítrofes. Por ejemplo, el programa anterior está cuidadosamente escrito para no bloquearse en ningún momento, aunque no establezca sus descriptores de archivo en modo no bloqueante. Es fácil introducir errores sutiles que eliminarán la ventaja de usar select(), por lo que aquí hay una lista de elementos esenciales a tener en cuenta al usar select().

1.
Siempre debe intentar usar select() sin tiempo de espera. Su programa no debería hacer nada si no hay datos disponibles. El código que depende de los tiempos de espera generalmente no es portátil y es difícil de depurar.
2.
El valor nfds debe calcularse correctamente para obtener eficiencia, como se explicó anteriormente.
3.
No se debe agregar ningún descriptor de archivo a ningún conjunto si no tiene la intención de verificar su resultado después de la llamada select() y responder apropiadamente. Consulte la siguiente regla.
4.
Después de que select() regrese, todos los descriptores de archivo en todos los conjuntos deben ser verificados para ver si están listos.
5.
Las funciones read(2), recv(2), write(2) y send(2) no necesariamente leen/escriben la cantidad completa de datos que ha solicitado. Si leen/escriben la cantidad completa, es porque tiene una carga de tráfico baja y un flujo rápido. Este no siempre será el caso. Debe tener en cuenta el caso en que sus funciones logren enviar o recibir solo un solo byte.
6.
Nunca lea/escriba solo un byte a la vez, a menos que esté realmente seguro de que tiene una pequeña cantidad de datos para procesar. Es extremadamente ineficiente no leer/escribir tantos datos como pueda almacenar en búfer cada vez. Los búferes en el ejemplo a continuación son de 1024 bytes, aunque fácilmente podrían ser más grandes.
7.
Las llamadas a read(2), recv(2), write(2) y send(2) pueden fallar con el error EINTR, y las llamadas a read(2), recv(2), write(2) y send(2) pueden fallar con errno establecido en EAGAIN (EWOULDBLOCK). Estos resultados deben gestionarse correctamente (no se hace correctamente arriba). Si su programa no va a recibir ninguna señal, es poco probable que obtenga EINTR. Si su programa no establece E/S no bloqueante, no obtendrá EAGAIN.
8.
Nunca llame a read(2), recv(2), write(2) o send(2) con una longitud de búfer de cero.
9.
Si las funciones read(2), recv(2), write(2) y send(2) fallan con errores distintos a los enumerados en 7., o una de las funciones de entrada devuelve 0, lo que indica fin de archivo, entonces no debe volver a pasar ese descriptor de archivo a select(). En el ejemplo siguiente, cierro el descriptor de archivo inmediatamente y luego lo establezco a -1 para evitar que se incluya en un conjunto.
10.
El valor de tiempo de espera debe inicializarse con cada nueva llamada a select(), ya que algunos sistemas operativos modifican la estructura. Sin embargo, pselect() no modifica su estructura de tiempo de espera.
11.
Dado que select() modifica sus conjuntos de descriptores de archivo, si la llamada se está utilizando en un bucle, los conjuntos deben reinicializarse antes de cada llamada.

VALOR DE RETORNO

Véase select(2).
