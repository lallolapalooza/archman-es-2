NOMBRE

secure-logging --- Proporciona integridad de reenvío y confidencialidad para los registros del sistema.

SINOPSIS

$(slog --key-file <archivo clave del host> --mac-file <archivo MAC> ${RAWMSG})

DESCRIPCIÓN

El registro seguro es una extensión de syslog-ng OSE que proporciona integridad de reenvío y confidencialidad de los registros del sistema. Se implementa en forma de un módulo y se configura como una plantilla en el archivo de configuración de syslog-ng OSE.

El objetivo principal del módulo de registro seguro es proporcionar registros a prueba de manipulaciones, por ejemplo, para proteger adecuadamente los registros de un sistema y proporcionar un sensor que indique intentos de acceso no autorizado. El módulo de registro seguro logra esto mediante el cifrado auténtico de cada registro de registro con una clave criptográfica individual utilizada una sola vez y protegiendo la integridad de todo el archivo de registros mediante un código de autenticación criptográfica. Cualquier intento de manipular un registro de registro individual o el archivo de registros mismo se detecta inmediatamente durante la verificación del archivo de registros. Debido a esto, un atacante ya no puede manipular los registros de registro sin ser detectado.

Para utilizar el archivo de registro creado por el módulo de registro seguro para análisis, el archivo de registro debe primero ser descifrado y su integridad debe ser verificada. Esto se logra con una utilidad de línea de comandos que forma parte del módulo de registro seguro y se instala como parte del paquete syslog-ng OSE. Esta utilidad puede integrarse en el módulo de importación de los entornos de análisis existentes.

El entorno de registro seguro utiliza una clave criptográfica para cifrar las entradas de registro. Las entradas de registro individuales se cifran con sus propias claves que se descartan inmediatamente después de un cifrado exitoso para proporcionar integridad futura. Un algoritmo eficiente genera la clave para la siguiente entrada de registro basándose en la clave utilizada para cifrar la entrada de registro anterior. La cadena de claves resultante preserva la integridad futura, por ejemplo, un atacante potencial no puede deducir la clave anterior de la clave actual.

Para optimizar la verificación y el análisis de registros, se añade un número de secuencia a cada entrada de registro. El número de secuencia también se añade a la clave de cifrado creando una correspondencia uno a uno de la clave de cifrado con la entrada de registro. Para evitar ataques de truncamiento o la eliminación de entradas de registro individuales, se aplica iterativamente un código de autenticación de mensajes (MAC) a todo el archivo de registros y se almacena en un archivo separado. Se utiliza al verificar para comprobar la integridad de todo el archivo de registros.

Antes de que el módulo de registro seguro pueda ser utilizado como parte de una instalación existente de syslog-ng OSE, son necesarias varias actividades preparatorias.

GENERACIÓN DE CLAVES

Para iniciar el sistema, se debe crear una clave inicial (k0) y instalarla en el host de registro antes de que el entorno de registro seguro se inicie por primera vez.

La clave de host creada inicialmente (k0) tiene su contador establecido en 0, marcándola como la clave de host inicial. Esta clave de host debe mantenerse en secreto y no puede ser revelada a terceros. Es necesaria para descifrar y verificar con éxito los archivos de registro procesados por el entorno de registro seguro. Como cada entrada de registro se cifra con su propia clave, se creará una nueva clave de host después del procesamiento exitoso de una entrada de registro y reemplazará la clave anterior. Por lo tanto, la clave de host inicial debe almacenarse en un lugar seguro antes de iniciar el entorno de registro seguro, ya que se elimina del host de registro después del procesamiento de la primera entrada de registro. Los siguientes pasos deben realizarse antes de iniciar el entorno de registro seguro. Los pasos 1 y 2 se realizan con la utilidad slogkey. Consulte la página del manual slogkey.1 para obtener detalles sobre cómo generar una clave maestra y derivar una clave de host de ella. El paso 3 y 4 dependen del despliegue real en un entorno de destino. 1. Cree una clave maestra. 2. Derive una clave de host inicial (k0) de la clave maestra (clave1). Almacene la clave k0 en una ubicación segura fuera del host de registro. 3. Implemente k0 en el host de registro, donde se utilizará el módulo de registro seguro.

CONFIGURACIÓN

El registro seguro se puede configurar añadiendo las sentencias correspondientes al archivo syslog-ng.conf.

El registro seguro se implementa como una plantilla y se configura en consecuencia. Aparte de la configuración de plantilla real, no se requiere ninguna otra configuración para activar el registro seguro.

El registro seguro se activa añadiendo la siguiente sentencia en el archivo de configuración:

template("$(slog --key-file  <archivo clave del host> --mac-file <archivo MAC> ${RAWMSG})\n");

El propósito de los elementos dentro de la sentencia: * slog

El nombre de la función de plantilla de registro seguro. Este nombre también se puede encontrar llamando a syslog-ng OSE con los argumentos --module-registry y comprobando la propiedad template-func del módulo de registro seguro en la salida correspondiente.
•
--key-file o -k

El archivo de clave del host. <archivo clave del host> es la ruta completa del archivo que almacena la clave del host en el host de registro. Si este argumento no se proporciona o no apunta a un archivo de clave válido, syslog-ng OSE no se inicia y muestra un mensaje de error.

•
--mac-file o -m

El archivo MAC. <archivo MAC> es la ruta completa del archivo MAC en el host de registro. El archivo se crea automáticamente al inicio inicial. Si la ruta no es correcta, syslog-ng OSE no se inicia y muestra un mensaje de error correspondiente.

•
${RAWMSG}

${RAWMSG} proporciona acceso al mensaje de registro original recibido en la fuente. Esta macro solo está disponible si el flag store-raw-message se estableció para la fuente. De lo contrario, se pasa una cadena vacía a la plantilla de registro seguro. Si el acceso al mensaje original no está disponible, por ejemplo, si la fuente no admite el flag store-raw-message, entonces la macro ${MSG} también puede usarse. En este caso, sin embargo, la garantía de integridad proporcionada por el registro seguro se limita al contenido que proporciona esta macro y no protege el mensaje original completo.

•
\n

\n es un separador de línea y su uso es importante, ya que la plantilla de registro seguro espera que las entradas de registro estén separadas. Al detectar un separador de línea, la entrada de registro se considera completa y se cifra con la clave de host actual. Por lo tanto, solo un sing

Secure Logging Template

The secure logging template can be used to protect the integrity of log messages. It uses cryptographic methods to ensure that log messages are not altered or deleted. The template encrypts log messages and creates a cryptographic chain of trust between individual log entries. This makes it possible to detect any tampering with the log data. The template requires a line separator to be present. If the source does not provide a line separator, one will be added.

The secure logging template can be combined with any source or destination with the following limitations:

  • Sources must be line-oriented. Secure logging uses a line separator in order to distinguish between individual log entries. Sources which provide data in a different format, for example, in the form of raw data obtained directly from a database system, cannot currently be used with the secure logging template, as the separation of log entries is not clearly defined for this type of data.
  • Only sources for which the store-raw-message flag is implemented and set do benefit from the integrity guarantee provided by the secure logging template. Secure logging aims at protecting the integrity of complete log messages including all associated meta-data, such as timestamps and host names. syslog-ng OSE parses the log message into its internal format and provide easy access to parts of a message through macros. While this is convenient when rewriting log messages, it is not helpful for secure logging. syslog-ng OSE provides the store-raw-message flag which provides access to a copy of the original log message after parsing. This is the log message processed and protected by the secure logging template. If the source does not support the store-raw-message flag, then the ${RAWMSG} macro can also be used. However, in this case the integrity guarantee provided by secure logging is limited to the content that this macro provides.
  • Log rotation of any kind cannot be used with destinations using secure logging, because log rotate overwrites or deletes previous log files. This compromises the cryptographic chain of trust of the log entries preve recovery. To efficiently handle log files, the secure logging environment features iterative verification. Using iterative verification, a log file can be verified in steps. For this to work, the log file must first be downloaded from the log host, together with the corresponding host key and MAC file to a verification host. After downloading, the log file can be safely deleted from the log host. Verification is then performed on the verification host using the iterative mode of the slogverify utility.

Ejemplo: plantilla de registro seguro en un destino de archivo

#############################################
# Archivo syslog-ng.conf mínimo con registro seguro activado. Las entradas de registro cifradas se registran en un único archivo llamado /var/log/messages.slog
#
@version: 4.4
@include "scl.conf"
source s_local {
    system();
    internal();
};
source s_network {
    network(
        transport("udp")
        port(514)
        flags(store-raw-message)
    );
};
# Definición de la plantilla de registro seguro
template secure_logging {
    template("$(slog --key-file /etc/syslog-ng/host.key --mac-file /etc/syslog-ng/mac.dat ${RAWMSG})\n");
};
# Esto configura un destino de registro seguro
destination d_local {
    file("/var/log/messages.slog" template(secure_logging));
};
log {
    source(s_local);
    # Esta fuente tiene la bandera de mensaje sin procesar establecida
    source(s_network);
    # Esta declaración activa el registro seguro para este destino
    destination(d_local);
};

Verificación de registros

Para analizar el archivo de registro creado en un entorno de registro seguro, los archivos de registro deben descifrarse y verificarse su integridad. La verificación requiere tanto la clave de host inicial (k0) como el archivo MAC correspondiente y se realiza con la utilidad slogverify. Normalmente no se realiza en el host de registro donde el entorno de registro seguro está produciendo datos de registro. En una implementación típica, los archivos de registro se recuperarían del host de registro y se transferirían a un recolector de registros central donde se realizaría la verificación. Dado que la verificación requiere el uso de k0, solo debe realizarse en un entorno de confianza.

Modo Normal

En modo normal, se verifica un archivo de registro completo a la vez. En un entorno típico, esto significaría recuperar un archivo de registro junto con su archivo MAC del host de registro y recuperar la clave inicial correspondiente k0 de una ubicación segura y proporcionárselos a la utilidad slogverify. Una secuencia de llamadas típica para el modo normal se presenta en el siguiente ejemplo:

slogverify --key-file host0.key --mac-file mac.dat /var/log/messages.slog /var/log/verified/messages

El propósito de los elementos dentro de la declaración:

•
host0.key

La clave de host inicial (k0). Proporcionar k0 es suficiente para descifrar todas las entradas de registro, ya que el algoritmo de derivación de claves puede generar las claves necesarias para todas las entradas de registro posteriores basándose en k0.

•
mac.dat

El archivo MAC del host de registro.

•
/var/log/messages.slog

El archivo que contiene las entradas de registro cifradas tal como se recuperaron de un host de registro.

•
/var/log/verified/messages

El archivo que recibe el registro en texto plano después del descifrado.

Los archivos de registro pueden volverse demasiado grandes y no caber en la memoria del sistema. Por lo tanto, la verificación se realiza en fragmentos. Cada parte del archivo de registro se transfiere a un búfer interno en el que se realiza la verificación. Después de que se procesa el búfer, se recupera el siguiente fragmento. Se puede proporcionar un argumento de búfer opcional a la utilidad slogverify para cambiar el tamaño de búfer predeterminado de 1000 entradas de registro a un número adecuado para el sistema en el que se realiza la verificación, por ejemplo:

slogverify --key-file host.key --mac-file mac.dat /var/log/messages.slog /var/log/verified/messages 8000

Para obtener más información sobre la verificación en modo normal, consulte [[slogverify|adm-man-slogkey]].

Modo Iterativo

La verificación en modo normal puede no ser adecuada para algunos escenarios de aplicación. Muchos hosts de registro utilizan la rotación de registros para preservar el espacio de almacenamiento. En la rotación de registros, se define un umbral para la cantidad máxima de espacio de almacenamiento y el número de generaciones para diferentes tipos de archivos de registro. Cuando se agota el espacio de almacenamiento o se alcanza el número de generaciones, el archivo de registro más antiguo se sobrescribe con nuevos datos de registro entrantes. Este procedimiento no es posible en un entorno de registro seguro, ya que sobrescribir, es decir, eliminar un archivo de registro, rompería la cadena criptográfica que se establece entre las entradas de registro. Esto no es sorprendente, ya que uno de los objetivos principales del registro seguro es proteger contra la eliminación de entradas de registro por parte de un posible atacante.

Para habilitar un procedimiento similar a la rotación de registros, el entorno de registro seguro presenta un modo iterativo. En modo iterativo, los archivos de registro se pueden dividir en diferentes archivos y cada uno de estos archivos se puede verificar por separado. Tenga cuidado al realizar la verificación en modo iterativo, ya que cada uno de los diferentes archivos de registro debe ir acompañado de una copia de la clave del host y los archivos MAC presentes en el sistema en el momento de la recuperación. A continuación se presenta un escenario de uso típico para el modo iterativo en una lista de pasos:

1
Defina un umbral de almacenamiento para el destino del archivo de registro seguro. En este ejemplo se define un umbral de 500 MB.
2
Permita que el entorno de registro seguro produzca datos de registro que se escriban en el destino hasta que se alcance el espacio asignado de 500 MB.
3
Detenga el entorno de registro seguro y recupere el archivo de registro, la clave del host y los archivos MAC del host de registro.
4
Elimine el archivo de registro en el host de registro, pero deje intactos la clave del host y el archivo MAC.
5
Reinicie el entorno de registro seguro.
6
Realice la verificación en modo iterativo con el archivo de registro, la clave del host y el MAC que se recuperó.

Los pasos 2-6 deben repetirse cada vez que el archivo de registro alcanza un tamaño de 50 MB. Suponiendo que las partes del archivo de registro se nombran según la iteración, por ejemplo log.1, log.2, log.3, etc., y se aplica una convención similar a las claves de host y los archivos MAC, una secuencia de llamadas típica para la validación de una parte del archivo de registro en modo iterativo después de tres iteraciones sería la siguiente:

slogverify --iterative --prev-key-file host.key.2 --prev-mac-file mac.dat.2 --mac-file mac.dat /var/log/messages.slog.3 /var/log/verified/messages.3

El propósito de los elementos dentro de la declaración:

•
host.key.2

La clave del host de la iteración anterior. En este ejemplo, esta es la segunda iteración.

•
mac.dat.2

El archivo MAC de la iteración anterior. En el ejemplo, la verificación se realiza durante la tercera iteración, por lo que se requiere el archivo MAC de la segunda iteración.

•
mac.dat

El archivo MAC actual del host de registro.

•
/var/log/messages.slog.3

El elemento de archivo que contiene las entradas de registro cifradas tal como se recuperaron del host de registro durante la tercera iteración.

•
/var/log/verified/messages.3

El archivo que recibe el registro en texto plano después del descifrado durante la tercera iteración.

En una implementación real, los pasos anteriores normalmente se automatizarían utilizando un motor de scripts. Consulte [[slogverify|adm-man-slogver]] para obtener detalles sobre la verificación en modo iterativo.
