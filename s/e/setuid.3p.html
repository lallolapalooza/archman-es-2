SETUID(3P) Manual del programador POSIX SETUID(3P)

PROLOGO

Esta página del manual forma parte del Manual del programador POSIX. La implementación de esta interfaz en Linux puede diferir (consulte la página del manual correspondiente de Linux para obtener detalles sobre el comportamiento de Linux), o la interfaz puede no estar implementada en Linux.

NOMBRE

setuid — establecer el ID de usuario

SINTAXIS

#include <unistd.h>
int setuid(uid_t uid);

DESCRIPCIÓN

Si el proceso tiene los privilegios apropiados, setuid() establecerá el ID de usuario real, el ID de usuario efectivo y el ID de usuario salvo del proceso que llama a uid.

Si el proceso no tiene los privilegios apropiados, pero uid es igual al ID de usuario real o al ID de usuario salvo, setuid() establecerá el ID de usuario efectivo a uid; el ID de usuario real y el ID de usuario salvo permanecerán sin cambios.

La función setuid() no afectará a la lista de grupos suplementarios de ninguna manera.

VALOR DE RETORNO

Al completarse con éxito, se devolverá 0. De lo contrario, se devolverá -1 y se establecerá errno para indicar el error.

ERRORES

La función setuid() fallará, devolverá -1 y establecerá errno al valor correspondiente si uno o más de los siguientes son ciertos:

EINVAL
El valor del argumento uid es inválido y no está soportado por la implementación.
EPERM
El proceso no tiene los privilegios apropiados y uid no coincide con el ID de usuario real o el ID de usuario salvo.

RACIONAMIENTO

Los diversos comportamientos de las funciones setuid() y setgid() cuando son llamadas por procesos no privilegiados reflejan el comportamiento de diferentes implementaciones históricas. Para portabilidad, se recomienda que las nuevas aplicaciones no privilegiadas utilicen las funciones seteuid() y setegid() en su lugar.

La capacidad de ID de usuario salvo permite que un programa recupere el ID de usuario efectivo establecido en la última llamada exec. Similarmente, la capacidad de ID de grupo salvo permite que un programa recupere el ID de grupo efectivo establecido en la última llamada exec. Estas capacidades se derivan de System V. Sin ellas, un programa podría tener que ejecutarse como superusuario para realizar las mismas funciones, ya que el superusuario puede escribir en los archivos del usuario. Este es un problema porque un programa de este tipo puede escribir en los archivos de cualquier usuario y, por lo tanto, debe escribirse cuidadosamente para emular correctamente los permisos del proceso que llama. En System V, estas capacidades se han implementado tradicionalmente solo a través de las funciones setuid() y setgid() para procesos no privilegiados. El hecho de que el comportamiento de esas funciones fuera diferente para usuarios privilegiados y no privilegiados las hacía difíciles de usar. El estándar POSIX.1-1990 definió la función setuid() para comportarse de manera diferente para usuarios privilegiados y no privilegiados. Cuando el llamador tenía los privilegios apropiados, la función establecía el ID de usuario real, el ID de usuario efectivo y el ID de usuario salvo del proceso que llama en implementaciones que lo soportaban. Cuando el llamador no tenía los privilegios apropiados, la función establecía solo el ID de usuario efectivo, sujeto a comprobaciones de permisos. El primer uso es generalmente necesario para utilidades como login y su, que no son aplicaciones conformes y, por lo tanto, están fuera del alcance de POSIX.1-2008. Estas utilidades desean cambiar el ID de usuario de forma irrevocable a un nuevo valor, generalmente el de un usuario no privilegiado. El segundo uso es necesario para aplicaciones conformes que se instalan con el bit set-user-ID y necesitan realizar operaciones utilizando el ID de usuario real.

POSIX.1-2008 aumenta la funcionalidad anterior con una característica obligatoria llamada _POSIX_SAVED_IDS. Esta característica permite a una aplicación set-user-ID cambiar su ID de usuario efectivo entre los valores de su ID de usuario real en el momento de la ejecución y su ID de usuario efectivo. Desafortunadamente, el estándar POSIX.1-1990 no permitía que una aplicación conforme que utilizara esta característica funcionara correctamente cuando se ejecutaba accidentalmente con privilegios (definidos por la implementación). Además, la aplicación ni siquiera tenía un medio para saber si tenía este privilegio. Dado que la característica de ID de usuario salvo es muy deseable para las aplicaciones, como lo demuestra el hecho de que NIST la requirió en FIPS 151-2, ha sido obligatoria por POSIX.1-2008. Sin embargo, hay implementadores que han sido reacios a admitirla dadas las limitaciones descritas anteriormente.

El sistema 4.3BSD maneja el problema admitiendo funciones separadas: setuid() (que siempre establece tanto los ID de usuario real como efectivo, como setuid() en POSIX.1-2008 para usuarios privilegiados) y seteuid() (que siempre establece solo el ID de usuario efectivo, como setuid() en POSIX.1-2008 para usuarios no privilegiados). Esta separación de funcionalidad en funciones distintas parece deseable. 4.3BSD no soporta la característica de ID de usuario salvo. Soporta una funcionalidad similar de cambiar el ID de usuario efectivo de un lado a otro a través de setreuid(), que permite intercambiar los ID de usuario real y efectivo. Este modelo parece menos deseable que el ID de usuario salvo porque el ID de usuario real cambia como efecto secundario. El 4.4BSD actual incluye ID efectivos salvados y los utiliza para seteuid() y setegid() como se describe anteriormente. Las funciones setreuid() y setregid() serán obsoletas o eliminadas.

La solución aquí es:

*
Requerir que todas las implementaciones soporten la funcionalidad del ID de usuario salvo, que es establecido por las funciones exec y por llamadas privilegiadas a setuid().
*
Añadir las funciones seteuid() y setegid() como alternativas portátiles a setuid() y setgid() para procesos no privilegiados y privilegiados.

Los sistemas históricos han proporcionado dos mecanismos para que un proceso set-user-ID cambie su ID de usuario efectivo para que sea el mismo que su ID de usuario real de tal manera que pueda volver al ID de usuario efectivo original: el uso de la función setuid() en presencia de un ID de usuario salvo, o el uso de la función setreuid() de BSD, que era capaz de intercambiar los ID de usuario real y efectivo. Los cambios incluidos en POSIX.1-2008 proporcionan un nuevo mecanismo que utiliza seteuid() en conjunción con un ID de usuario salvo. Por lo tanto, todas las implementaciones con el nuevo mecanismo seteuid() mantendrán un ID de usuario salvo para cada proceso, y la mayor parte del comportamiento controlado por _POSIX_SAVED_IDS se ha modificado para que coincida con el caso en que la opción estaba definida. La función kill() es una excepción. Los implementadores del nuevo mecanismo seteuid() generalmente deberán mantener la compatibilidad con los mecanismos anteriores soportados anteriormente por sus sistemas. Sin embargo, la compatibilidad con este uso de setreuid() y con el comportamiento de _POSIX_SAVED_IDS de kill() es desafortunadamente complicada. Si una implementación con un ID de usuario salvo permite que un proceso utilice setreuid() para intercambiar sus ID de usuario real y efectivo, pero dejara el ID de usuario salvo sin modificar, el proceso tendría entonces un ID de usuario efectivo igual al ID de usuario real original, y tanto el ID de usuario real como el ID de usuario salvo serían iguales al ID de usuario efectivo original. En ese estado, el usuario real no podría terminar el proceso, aunque el ID de usuario efectivo del proceso coincida con el del usuario real, si se utilizara el comportamiento de kill() de _POSIX_SAVED_IDS. Esto es obviamente inaceptable. La elección alternativa, que se utiliza en al menos una implementación, es cambiar el ID de usuario salvo al ID de usuario efectivo durante la mayoría de las llamadas a setreuid(). Los desarrolladores del estándar consideraron que esta alternativa era menos correcta que la retención del comportamiento antiguo de kill() en tales sistemas. Las aplicaciones conformes actuales deberán dar cabida a cualquiera de los comportamientos de kill(), y no parece haber ninguna razón sólida para que kill() verifique el ID de usuario salvo rather que el ID de usuario efectivo.
