sensord(8) Administración del Sistema Linux sensord(8)

NOMBRE

sensord - Demonio de registro de información de sensores.

SINOPSIS

sensord [ opciones ] [ chips ]

DESCRIPCIÓN

Sensord es un demonio que puede ser usado para registrar periódicamente lecturas de sensores de chips de monitoreo de salud del hardware a syslog(3) o a una base de datos circular (RRD) y para alertar cuando se señaliza una alarma del sensor; por ejemplo, si un ventilador falla, se excede un límite de temperatura, etc.

OPCIONES

-i, --interval tiempo
Especifica el intervalo entre escaneos de alarmas de sensores; el valor predeterminado es escanear cada minuto.

El tiempo debe especificarse como un entero bruto (segundos) o con un sufijo `s' para segundos, `m' para minutos o `h' para horas; por ejemplo, el intervalo predeterminado es `60' o `1m'.

Especifica un intervalo de cero para suprimir explícitamente el escaneo de alarmas.

-l, --log-interval tiempo
Especifica el intervalo entre el registro de todas las lecturas de sensores; el valor predeterminado es registrar todas las lecturas cada media hora.

El tiempo se especifica como antes; por ejemplo, `30m'.

Especifica un intervalo de cero para suprimir el registro de lecturas de sensores regulares.

-1, --oneline
Registra el valor del sensor, chip y adaptador en una sola línea para facilitar el análisis.
-t, --rrd-interval tiempo
Especifica el intervalo entre el registro de todas las lecturas de sensores a una base de datos circular; el valor predeterminado es registrar todas las lecturas cada cinco minutos si se configura una base de datos circular.

El tiempo se especifica como antes; por ejemplo, `5m'.

-T, --rrd-no-average
Especifica que la base de datos circular no debe promediarse.
-r, --rrd-file archivo
Especifica una base de datos circular en la que registrar todas las lecturas de sensores; por ejemplo, `/var/log/sensord.rrd'. Esta base de datos se creará si no existe. Por defecto, no se utiliza ninguna base de datos circular.

Vea la sección BASES DE DATOS CIRCULARES más abajo para más detalles.

-c, --config-file archivo
Especifica un archivo de configuración de libsensors(3). Si no se especifica ningún archivo, se utiliza el archivo de configuración predeterminado de libsensors.
-p, --pid-file archivo
Especifica qué archivo PID escribir; el valor predeterminado es escribir el archivo `/run/sensord.pid'. Siempre debe especificar una ruta absoluta aquí. El archivo se elimina cuando el demonio sale.
-f, --syslog-facility instalación
Especifica la instalación(3) de syslog que se utilizará al registrar lecturas y alarmas de sensores; el valor predeterminado es usar daemon.

Otras instalaciones posibles incluyen local0 a local7 y user.

-g, --rrd-cgi directorio
Imprime un script CGI de ejemplo de rrdcgi(1) que se puede usar para mostrar gráficos de información reciente de sensores en una página web, y sale. Debe especificar el directorio, escribible por todos y accesible a través de la web, donde se deben almacenar los gráficos; el script CGI asume que esto se accederá bajo el directorio `/sensord/' en el servidor web. Vea la sección BASES DE DATOS CIRCULARES más abajo para más detalles.
-a, --load-average
Incluye el promedio de carga en la base de datos RRD. También debe especificar esta bandera cuando cree el script CGI.
-d, --debug
Imprime una pequeña cantidad de información adicional de depuración.
-h, --help
Imprime un mensaje de ayuda y sale.
-v, --version
Muestra la versión del programa y sale.

CHIPS

Para restringir los dispositivos que son escaneados por este demonio, opcionalmente puede especificar una lista de nombres de chips. Por defecto, se escanean todos los chips disponibles.

Un nombre de chip típico sería `w83782d-*' (puede que quiera escapar el `*' para su shell) lo que escanearía cualquier chip W83782D en cualquier bus. Vea sensors.conf(5) para más detalles. Otra opción es simplemente no cargar los módulos del sensor para los chips que no le interesan.

SEÑALES

Al recibir una SIGTERM (ver signal(7) para detalles) este demonio debería apagarse limpiamente.

Al recibir una SIGHUP, este demonio reescaneará la interfaz del kernel para chips y características, y recargará el archivo de configuración de libsensors.

REGISTRO

Todos los mensajes de este demonio se registran en syslog(3) bajo el nombre de programa `sensord' y la instalación daemon, o lo que se especifique en la línea de comandos.

Las lecturas regulares de sensores se registran al nivel info. Las alarmas se registran al nivel alert. Los mensajes de estado no trascendentales se registran al nivel mínimo, debug, cuando la depuración está habilitada.

Puede usar un archivo `/etc/syslog.conf' apropiado para dirigir estos mensajes de manera útil. Vea syslog.conf(5) para detalles completos. Asumiendo que establece la instalación de registro a local4, la siguiente es una configuración de ejemplo:

# Entradas de ejemplo de syslog.conf
*.info;...;local4.none;local4.warn  /var/log/messages
local4.info                        -/var/log/sensors
local4.alert                        /dev/console
local4.alert                        *

La primera línea asegura que las lecturas regulares de sensores no saturen `/var/log/messages'; primero decimos `local4.none' para eliminar los mensajes informativos; luego `local4.warn' para habilitar las advertencias y superiores. La segunda línea indica registrar todas las lecturas regulares de sensores en `/var/log/sensors'; el guion inicial `-' significa que este archivo no se vacía después de cada mensaje. Las dos últimas líneas aseguran que las alarmas se impriman en la consola del sistema, así como a todos los usuarios conectados (además de `/var/log/messages' y `/var/log/sensors').

ROTACIÓN DE REGISTROS

En un sistema típico con un buen chip de sensor, espere aproximadamente 2KB por lectura de sensor en el archivo de registro. Esto equivale a aproximadamente 3MB por mes. Debería estar rotando sus archivos de syslog de todos modos, pero para estar seguro, querrá usar algo como logrotate(8) o equivalente. Podría, por ejemplo, querer una entrada en `/etc/logrotate.d/syslog' que contenga:

# Entrada de ejemplo de logrotate.d
/var/log/sensors {
    postrotate
        /usr/sbin/killall -HUP syslogd
    endscript
}

Tenga en cuenta, por supuesto, que desea reiniciar syslogd(8) y no sensord(8)

ALARMAS

Las alarmas generalmente indican una condición crítica; por ejemplo, un fallo del ventilador o una temperatura o voltaje inaceptable. Sin embargo, algunos chips de sensor no admiten alarmas, mientras que otros están configurados incorrectamente y pueden señalar alarmas incorrectamente.

Tenga en cuenta que algunos controladores pueden carecer de soporte para la notificación de alarmas, a pesar de que los chips que soportan tienen alarmas. A partir de Linux 2.6.23, muchos controladores todavía no informan alarmas en un formato adecuado para libsensors 3.

BIPS

Si ve `(beep)' junto a alguna lectura de sensor, eso solo significa que su sistema está configurado para emitir una advertencia de audio desde la placa base si se señaliza una alarma en ese sensor.

BASES DE DATOS CIRCULARES

Sensord(8) proporciona soporte para almacenar lecturas de sensores en una base de datos circular. Esto puede ser una alternativa útil al uso de syslog(3).

La base de datos se crea con el comando rrdtool(1). Por ejemplo, para crear una base de datos que almacene 1024 puntos de datos para cada uno de los 20 sensores que el demonio está configurado para monitorear, con un intervalo de 5 minutos, el comando sería:

rrdtool create /var/log/sensord.rrd --step 300 \
    DS:sensor1:GAUGE:600:-50:150 \
    DS:sensor2:GAUGE:600:-50:150 \
    ...
    DS:sensor20:GAUGE:600:-50:150 \
    RRA:AVERAGE:0.5:1:1024 \
    RRA:MIN:0.5:1:1024 \
    RRA:MAX:0.5:1:1024 \
    RRA:AVERAGE:0.5:12:1024 \
    RRA:MIN:0.5:12:1024 \
    RRA:MAX:0.5:12:1024

Cada línea `DS:' define una fuente de datos (un sensor) que se registrará en la base de datos. El `600' es el tiempo de espera antes de que un punto de datos se considere obsoleto; el `-50:150' son los valores mínimo y máximo esperados para el sensor.

Cada línea `RRA:' define una entrada de archivo de registro redondo (round-robin archive). El `0.5' es la consistencia del archivo de registro (un valor entre 0 y 1). El `1' es el período de consolidación (cuántos puntos de datos se promedian o se toman el mínimo/máximo). El `1024' es el número de puntos de datos a almacenar.

Los tres primeros `RRA:'s almacenan datos en bruto (sin promediar) con un período de consolidación de 1 (es decir, cada 5 minutos). Los siguientes tres `RRA:'s almacenan datos con un período de consolidación de 12 (es decir, cada hora).

Los nombres de los sensores se pueden encontrar ejecutando `sensors -u'. Por ejemplo, si tuviera un sensor llamado `temp1' en la entrada `Adapter:ISA adapter (driver=coretemp)' y quisiera registrarlo, el nombre de la fuente de datos podría ser `coretemp-isa-temp1'.

Si especifica la opción `-g', se creará un script CGI de ejemplo que mostrará gráficos de sus datos de sensor. Debe colocar esto en el directorio apropiado de su servidor web (por ejemplo, `/var/www/cgi-bin/sensord.cgi') y asegurarse de que la opción `-g' se especifica con el nombre del directorio donde deben almacenarse los gráficos (por ejemplo, `/var/www/html/sensord/'). Debe asegurarse de que este directorio sea escribible por el usuario bajo el cual se ejecuta el script CGI.

Por ejemplo, si su servidor web se ejecuta como el usuario `httpd', debería ejecutar:

mkdir -p /var/www/html/sensord
chown httpd:httpd /var/www/html/sensord
chmod 755 /var/www/html/sensord
sensord -g /var/www/html/sensord -r /var/log/sensord.rrd ...

Luego, debería poder ver gráficos de sus datos de sensores en su navegador web yendo a `http://su-servidor-web/cgi-bin/sensord.cgi/`. Para ver los gráficos, debe asegurarse de que el script CGI tenga permisos de ejecución.

DIAGNÓSTICO

Si sus sensores no están funcionando correctamente, consulte sensors.conf(5) y libsensors(3) para obtener más detalles.

VER TAMBIÉN

sensors.conf(5), libsensors(3), rrdtool(1), syslog(3), syslog.conf(5)

ROUND ROBIN DATABASES

Las bases de datos round-robin son bases de datos de tamaño constante que se pueden utilizar para almacenar, por ejemplo, lecturas de sensores de una semana. Las lecturas posteriores almacenadas en la base de datos sobrescribirán las lecturas que tengan más de una semana. Esta capacidad es extremadamente útil porque permite almacenar información útil de una manera de fácil acceso durante un período de tiempo útil, sin la carga de archivos de registro en constante crecimiento.

La utilidad rrdtool(1) y su biblioteca asociada proporcionan el marco básico para la base de datos round-robin debajo de sensord(8). Además, las utilidades rrdcgi(1) y rrdgraph(1) proporcionan soporte para generar gráficos de estos datos para su visualización en una página web.

Si desea utilizar la configuración predeterminada de la base de datos round-robin, que almacena lecturas de sensores de una semana a intervalos de cinco minutos, simplemente inicie sensord(8) y especifique dónde desea que se almacene la base de datos. Se creará y configurará automáticamente utilizando estos parámetros predeterminados.

Si desea que las lecturas se almacenen durante un período más largo, o desea que varias lecturas se promedien en cada entrada de la base de datos, debe crear y configurar manualmente la base de datos antes de iniciar sensord(8). Consulte el manual de rrdcreate(1) para obtener detalles. Tenga en cuenta que la base de datos debe coincidir exactamente con los nombres y el orden de los sensores leídos por sensord(8). Se recomienda crear la base de datos predeterminada y luego usar rrdinfo(1) para obtener esta información, y/o rrdtune(1) para modificarla.

Después de crear la base de datos round-robin, debe configurar su servidor web para mostrar la información del sensor. Esto asume que tiene un servidor web preconfigurado y funcionando en su máquina. Sensord(8) proporciona una opción de línea de comandos --rrd-cgi para generar un script CGI básico para mostrar estos gráficos; puede personalizar este script según sus preferencias. Consulte el manual de rrdcgi(1) para obtener detalles. Este script CGI requiere un directorio grabable por todos y accesible a través de la web en el que escribir los gráficos que genera.

A continuación, se muestra un ejemplo de cómo configurar gráficos accesibles a través de la web de lecturas de sensores recientes:

sensord --log-interval 0 \
  --load-average \
  --rrd-file /var/log/sensord.rrd

Aquí, iniciamos sensord(8) y lo configuramos para almacenar lecturas en una base de datos round-robin; tenga en cuenta que deshabilitamos el registro de lecturas de sensores en syslog(3) y habilitamos el registro de la carga promedio.

mkdir /var/www/sensord
chown www-data:staff /var/www/sensord
chmod a=rwxs /var/www/sensord

Aquí, creamos un directorio grabable por todos y accesible a través de la web en el que se almacenarán los gráficos; establecemos la propiedad y los permisos de este directorio apropiadamente. Deberá determinar la ubicación y la propiedad que sean adecuadas para su máquina.

sensord --load-average \
  --rrd-file /var/log/sensord.rrd \
  --rrd-cgi /var/www/sensord \
  > /usr/lib/cgi-bin/sensord.cgi
chmod a+rx /usr/lib/cgi-bin/sensord.cgi

Aquí, creamos un script CGI que mostrará las lecturas de los sensores de la base de datos. Debe especificar la ubicación de la base de datos round-robin, la ubicación del directorio donde se deben almacenar las imágenes y si desea que se muestre la carga promedio. El parámetro de línea de comandos --rrd-cgi hace que sensord(8) muestre un script CGI adecuado en stdout y luego salga. Deberá escribir este script en el directorio bin CGI de su servidor web y editar el script si el directorio de imágenes que eligió no es el directorio `/sensord/' de su servidor web.

Finalmente, debería poder ver sus lecturas de sensores desde la URL `http://localhost/cgi-bin/sensord.cgi'.

MÓDULOS

Se espera que todos los módulos de sensores requeridos se carguen antes de iniciar este demonio. Esto se puede lograr con un esquema de carga de módulos específico del sistema (por ejemplo, enumerando los módulos requeridos en el archivo `/etc/modules' en Debian) o con comandos explícitos de modprobe(1) en un script de inicio antes de cargar el demonio.

Por ejemplo, un script de inicialización de `sensord' podría contener (entre otros) los siguientes comandos:

# Ejemplo de script init.d
echo -n "Cargando módulo AMD756: "
modprobe i2c-amd756 || { echo Fallo. ; exit 1 ; }
echo OK.
echo -n "Cargando módulo W83781D: "
modprobe w83781d || { echo Fallo. ; exit 1 ; }
echo OK.
echo -n "Iniciando sensord: "
daemon sensord

Ignore las funciones de shell específicas de la plataforma; la idea general debería ser bastante clara.

ERRORES

Los errores encontrados por este demonio se registran en syslogd(8), después de lo cual el demonio saldrá.

ERRORES

El soporte de bases de datos round-robin no maneja chips de sensores múltiples con etiquetas de sensores duplicadas.
