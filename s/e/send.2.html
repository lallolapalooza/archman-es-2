send(2) Manual de Llamadas al Sistema send(2)

NOMBRE

send, sendto, sendmsg - enviar un mensaje a un socket

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

SINOPSIS

#include <sys/socket.h>
ssize_t send(size_t size;
               int sockfd, const void buf[size], size_t size, int flags);
ssize_t sendto(size_t size;
               int sockfd, const void buf[size], size_t size, int flags,
               const struct sockaddr *dest_addr, socklen_t addrlen);
ssize_t sendmsg(int sockfd, const struct msghdr *msg, int flags);

DESCRIPCIÓN

Las llamadas al sistema send(), sendto() y sendmsg() se utilizan para transmitir un mensaje a otro socket.

La llamada send() solo puede usarse cuando el socket está en estado conectado (para que el destinatario previsto sea conocido). La única diferencia entre send() y write(2) es la presencia de los flags. Con un argumento flags cero, send() es equivalente a write(2). Además, la siguiente llamada


send(sockfd, buf, size, flags);

es equivalente a


sendto(sockfd, buf, size, flags, NULL, 0);

El argumento sockfd es el descriptor de archivo del socket de envío.

Si sendto() se usa en un socket de modo de conexión (SOCK_STREAM, SOCK_SEQPACKET), los argumentos dest_addr y addrlen se ignoran (y puede devolverse el error EISCONN cuando no son NULL y 0), y se devuelve el error ENOTCONN cuando el socket no estaba realmente conectado. De lo contrario, la dirección del destino está dada por dest_addr con addrlen especificando su tamaño. Para sendmsg(), la dirección del destino está dada por msg.msg_name, con msg.msg_namelen especificando su tamaño.

Para send() y sendto(), el mensaje se encuentra en buf y tiene un tamaño de size. Para sendmsg(), el mensaje está apuntado por los elementos del array msg.msg_iov. La llamada sendmsg() también permite enviar datos auxiliares (también conocidos como información de control).

Si el mensaje es demasiado largo para pasar atómicamente a través del protocolo subyacente, se devuelve el error EMSGSIZE y no se transmite el mensaje.

No hay ninguna indicación implícita de fallo de entrega en un send(). Los errores detectados localmente se indican mediante un valor de retorno de -1.

Cuando el mensaje no cabe en el búfer de envío del socket, send() normalmente se bloquea, a menos que el socket se haya colocado en modo de E/S no bloqueante. En modo no bloqueante, fallaría con el error EAGAIN o EWOULDBLOCK en este caso. La llamada select(2) puede usarse para determinar cuándo es posible enviar más datos.

El argumento flags

El argumento flags es la OR bit a bit de cero o más de los siguientes flags.

MSG_CONFIRM (desde Linux 2.3.15)
Indicar a la capa de enlace que se produjo un progreso hacia adelante: recibiste una respuesta exitosa del otro lado. Si la capa de enlace no recibe esto, sondeará periódicamente al vecino (por ejemplo, a través de una ARP unicast). Válido solo en sockets SOCK_DGRAM y SOCK_RAW y actualmente implementado solo para IPv4 e IPv6. Ver arp(7) para detalles.
MSG_DONTROUTE
No usar una pasarela para enviar el paquete, enviar solo a hosts en redes directamente conectadas. Esto se usa generalmente solo para programas de diagnóstico o enrutamiento. Esto solo se define para familias de protocolos que enrutan; los sockets de paquete no lo hacen.
MSG_DONTWAIT (desde Linux 2.2)
Habilita la operación no bloqueante; si la operación se bloquearía, se devuelve EAGAIN o EWOULDBLOCK. Esto proporciona un comportamiento similar a establecer el flag O_NONBLOCK (a través de la operación F_SETFL de fcntl(2)), pero difiere en que MSG_DONTWAIT es una opción por llamada, mientras que O_NONBLOCK es una configuración en el descriptor de archivo abierto (ver open(2)), que afectará a todos los hilos del proceso que llama, así como a otros procesos que tengan descriptores de archivo que se refieran a la misma descripción de archivo abierta.
MSG_EOR (desde Linux 2.2)
Termina un registro (cuando esta noción es soportada, como para sockets de tipo SOCK_SEQPACKET).
MSG_MORE (desde Linux 2.4.4)
El llamante tiene más datos para enviar. Este flag se utiliza con sockets TCP para obtener el mismo efecto que la opción de socket TCP_CORK (ver tcp(7)), con la diferencia de que este flag se puede establecer por llamada.
Desde Linux 2.6, este flag también es compatible con sockets UDP e informa al kernel para empaquetar todos los datos enviados en llamadas con este flag establecido en un solo datagrama que se transmite solo cuando se realiza una llamada que no especifica este flag. (Ver también la opción de socket UDP_CORK descrita en udp(7).)
MSG_NOSIGNAL (desde Linux 2.2)
No generar una señal SIGPIPE si el par en un socket orientado a flujo ha cerrado la conexión. El error EPIPE todavía se devuelve. Esto proporciona un comportamiento similar a usar sigaction(2) para ignorar SIGPIPE, pero, mientras que MSG_NOSIGNAL es una característica por llamada, ignorar SIGPIPE establece un atributo del proceso que afecta a todos los hilos del proceso.
MSG_OOB
Envía datos fuera de banda en sockets que soportan esta noción (por ejemplo, de tipo SOCK_STREAM); el protocolo subyacente también debe soportar datos fuera de banda.
MSG_FASTOPEN (desde Linux 3.7)
Intenta TCP Fast Open (RFC7413) y envía datos en el SYN como una combinación de connect(2) y write(2), realizando una operación implícita de connect(2). Se bloquea hasta que los datos se búferen y se complete el handshake. Para un socket no bloqueante, devuelve el número de bytes almacenados en búfer y enviados en el paquete SYN. Si la cookie no está disponible localmente, devuelve EINPROGRESS y envía un SYN con una solicitud de cookie Fast Open automáticamente. El llamante debe volver a escribir los datos cuando el socket esté conectado. En caso de error, establece el mismo errno que connect(2) si el handshake falla. Este flag requiere habilitar el soporte del cliente TCP Fast Open en el sysctl net.ipv4.tcp_fastopen.
Consulte la opción de socket TCP_FASTOPEN_CONNECT en tcp(7) para un enfoque alternativo.

sendmsg()

La definición de la estructura msghdr empleada por sendmsg() es la siguiente:


struct msghdr {
    void         *msg_name;       /* Dirección opcional */
    socklen_t     msg_namelen;    /* Tamaño de la dirección */
    struct iovec *msg_iov;        /* Array de scatter/gather */
    size_t        msg_iovlen;     /* # de elementos en msg_iov */
    void         *msg_control;    /* Datos auxiliares, ver abajo */
    size_t        msg_controllen; /* Tamaño del búfer de datos auxiliares */
    int           msg_flags;      /* Flags (no utilizados) */
};

send(2) — Arch Linux man pages

NAME

send, sendto, sendmsg — enviar datos desde un socket

LIBRARY

Librería C estándar (libc)

SYNOPSIS

#include <sys/socket.h>

ssize_t send(int sockfd, const void *buf, size_t len, int flags);

ssize_t sendto(int sockfd, const void *buf, size_t len, int flags, const struct sockaddr *dest_addr, socklen_t addrlen);

ssize_t sendmsg(int sockfd, const struct msghdr *msg, int flags);

DESCRIPTION

Estas llamadas al sistema se usan para enviar datos a través de un socket. Las diferencias entre ellas son las siguientes:

  • send(): Es la interfaz más simple. Transmite un número de bytes igual a len desde el buffer apuntado por buf hasta el socket especificado por sockfd.

    Si el socket no está conectado, la dirección de destino debe ser especificada explícitamente en la llamada a connect() antes de llamar a send(). Para sockets orientados a conexión, send() envía datos solo a aquellos hosts a los que se haya conectado previamente.

    Para sockets sin conexión, send() equivale a sendto() con dest_addr y addrlen establecidos a NULL y 0, respectivamente.

  • sendto(): Transmite un número de bytes igual a len desde el buffer apuntado por buf hasta el socket especificado por sockfd. La estructura dest_addr y la longitud addrlen especifican la dirección de destino del socket.

    Si el socket no está conectado, la dirección de destino debe ser especificada explícitamente. Si el socket está conectado, los argumentos dest_addr y addrlen deben ser NULL y 0, respectivamente.

  • sendmsg(): Es la interfaz más general. Transmite datos especificados por una cadena de estructuras iovec (múltiples buffers) usando una estructura msghdr. Esta interfaz permite enviar información adicional (datos auxiliares o "ancillary data") junto con los datos del mensaje.

    La estructura msghdr se define como sigue:

    struct msghdr {
    void         *msg_name;       /* Nombre del socket de destino */
    socklen_t     msg_namelen;    /* Longitud del nombre del socket */
    struct iovec *msg_iov;        /* Estructuras de datos de scatter/gather */
    size_t        msg_iovlen;     /* Número de estructuras en msg_iov */
    void         *msg_control;    /* Datos auxiliares */
    size_t        msg_controllen; /* Longitud del buffer de datos auxiliares */
    int           msg_flags;      /* Flags de entrada/salida */
};

    El miembro msg_name y msg_namelen especifican la dirección de destino; si son NULL y 0, respectivamente, se usa la dirección de destino previamente establecida (para sockets conectados). Para sockets sin conexión, estos campos deben especificar la dirección de destino.

    Los miembros msg_iov y msg_iovlen especifican ubicaciones de scatter-gather, como en writev(2).

    Puede enviar información de control (datos auxiliares) usando los miembros msg_control y msg_controllen. El tamaño máximo del buffer de control que el kernel puede procesar está limitado por socket por el valor en /proc/sys/net/core/optmem_max; consulte socket(7). Para más información sobre el uso de datos auxiliares en varios dominios de socket, consulte unix(7) y ip(7).

    El miembro msg_flags se ignora.

RETURN VALUE

En caso de éxito, estas llamadas devuelven el número de bytes enviados. En caso de error, se devuelve -1 y se establece errno para indicar el error.

ERRORS

Estos son algunos errores estándar generados por la capa de socket. Pueden generarse y devolverse errores adicionales desde los módulos de protocolo subyacentes; consulte sus páginas de manual respectivas.

EACCES
(Para sockets de dominio UNIX, que se identifican por nombre de archivo) Se niega el permiso de escritura en el archivo del socket de destino, o se niega el permiso de búsqueda para uno de los directorios del prefijo de la ruta. (Véase path_resolution(7)).
(Para sockets UDP) Se intentó enviar a una dirección de red/broadcast como si fuera una dirección unicast.
EAGAIN o EWOULDBLOCK
El socket está marcado como no bloqueante y la operación solicitada se bloquearía. POSIX.1-2001 permite que cualquiera de estos errores se devuelva para este caso, y no exige que estas constantes tengan el mismo valor, por lo que una aplicación portable debe verificar ambas posibilidades.
EAGAIN
(Sockets de datagramas de dominio Internet) El socket al que se refiere sockfd no se había vinculado previamente a una dirección y, al intentar vincularlo a un puerto efímero, se determinó que todos los números de puerto en el rango de puertos efímeros están actualmente en uso. Véase la discusión de /proc/sys/net/ipv4/ip_local_port_range en ip(7).
EALREADY
Otra operación Fast Open está en curso.
EBADF
sockfd no es un descriptor de archivo abierto válido.
ECONNRESET
Conexión reiniciada por el par.
EDESTADDRREQ
El socket no es de modo conexión y no se ha establecido una dirección de par.
EFAULT
Se especificó una dirección de espacio de usuario inválida para un argumento.
EINTR
Ocurrió una señal antes de que se transmitieran datos; véase signal(7).
EINVAL
Se pasó un argumento inválido.
EISCONN
El socket de modo conexión ya estaba conectado pero se especificó un destinatario. (Ahora se devuelve este error, o la especificación del destinatario se ignora).
EMSGSIZE
El tipo de socket requiere que los mensajes se envíen de forma atómica, y el tamaño del mensaje a enviar hizo esto imposible.
ENOBUFS
La cola de salida para una interfaz de red estaba llena. Esto generalmente indica que la interfaz ha dejado de enviar, pero puede ser causado por congestión transitoria. (Normalmente, esto no ocurre en Linux. Los paquetes se descartan silenciosamente cuando una cola de dispositivo se desborda).
ENOMEM
No hay memoria disponible.
ENOTCONN
El socket no está conectado y no se ha proporcionado ningún destino.
ENOTSOCK
El descriptor de archivo sockfd no se refiere a un socket.
EOPNOTSUPP
Algún bit en el argumento flags es inapropiado para el tipo de socket.
EPIPE
El extremo local se ha cerrado en un socket orientado a conexión. En este caso, el proceso también recibirá una señal SIGPIPE a menos que se establezca MSG_NOSIGNAL.

VERSIONS

Según POSIX.1-2001, el campo msg_controllen de la estructura msghdr debe ser de tipo socklen_t, y el campo msg_iovlen debe ser de tipo int, pero glibc actualmente los tipifica como size_t.

STANDARDS

POSIX.1-2024.

MSG_CONFIRM es una extensión de Linux.

HISTORY

4.4BSD, SVr4, POSIX.1-2001. (apareció por primera vez en 4.2BSD).

POSIX.1-2001 solo describe las banderas MSG_OOB y MSG_EOR. POSIX.1-2008 añade una especificación de MSG_NOSIGNAL.

NOTES

Consulte sendmmsg(2) para obtener información sobre una llamada al sistema específica de Linux que se puede utilizar para transmitir múltiples datagramas en una sola llamada.

BUGS

Linux puede devolver EPIPE en lugar de ENOTCONN.
