send(2) Manual de llamadas al sistema send(2)

NOMBRE

send, sendto, sendmsg - enviar un mensaje a un socket

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

SINOPSIS

#include <sys/socket.h>
ssize_t send(int sockfd, const void buf[.size], size_t size, int flags);
ssize_t sendto(int sockfd, const void buf[.size], size_t size, int flags,
               const struct sockaddr *dest_addr, socklen_t addrlen);
ssize_t sendmsg(int sockfd, const struct msghdr *msg, int flags);

DESCRIPCIÓN

Las llamadas al sistema send(), sendto() y sendmsg() se utilizan para transmitir un mensaje a otro socket.

La llamada send() solo puede usarse cuando el socket está en estado conectado (para que el destinatario previsto sea conocido). La única diferencia entre send() y write(2) es la presencia de flags. Con un argumento flags cero, send() es equivalente a write(2). Además, la siguiente llamada


send(sockfd, buf, size, flags);

es equivalente a


sendto(sockfd, buf, size, flags, NULL, 0);

El argumento sockfd es el descriptor de archivo del socket emisor.

Si sendto() se usa en un socket de modo conexión (SOCK_STREAM, SOCK_SEQPACKET), los argumentos dest_addr y addrlen se ignoran (y el error EISCONN puede ser devuelto cuando no son NULL y 0), y el error ENOTCONN se devuelve cuando el socket no estaba realmente conectado. De lo contrario, la dirección del destino se indica mediante dest_addr con addrlen especificando su tamaño. Para sendmsg(), la dirección del destino se indica mediante msg.msg_name, con msg.msg_namelen especificando su tamaño.

Para send() y sendto(), el mensaje se encuentra en buf y tiene un tamaño de size. Para sendmsg(), el mensaje es señalado por los elementos del array msg.msg_iov. La llamada sendmsg() también permite enviar datos auxiliares (también conocidos como información de control).

Si el mensaje es demasiado largo para pasar atómicamente a través del protocolo subyacente, se devuelve el error EMSGSIZE y el mensaje no se transmite.

Ninguna indicación de fallo de entrega está implícita en un send(). Los errores detectados localmente se indican con un valor de retorno de -1.

Cuando el mensaje no cabe en el búfer de envío del socket, send() normalmente se bloquea, a menos que el socket se haya colocado en modo de E/S no bloqueante. En modo no bloqueante, fallaría con el error EAGAIN o EWOULDBLOCK en este caso. La llamada select(2) puede usarse para determinar cuándo es posible enviar más datos.

El argumento flags

El argumento flags es el OR a nivel de bits de cero o más de las siguientes banderas.

MSG_CONFIRM (desde Linux 2.3.15)
Indica a la capa de enlace que se ha producido un progreso: se ha recibido una respuesta exitosa del otro lado. Si la capa de enlace no recibe esto, investigará periódicamente al vecino (p. ej., a través de una ARP unicast). Válido solo en sockets SOCK_DGRAM y SOCK_RAW y actualmente implementado solo para IPv4 e IPv6. Consulte arp(7) para más detalles.
MSG_DONTROUTE
No usar un gateway para enviar el paquete, enviar solo a hosts en redes directamente conectadas. Esto generalmente se usa solo por programas de diagnóstico o enrutamiento. Esto solo se define para familias de protocolos que enrutan; los sockets de paquetes no lo hacen.
MSG_DONTWAIT (desde Linux 2.2)
Habilita la operación no bloqueante; si la operación se bloquearía, se devuelve EAGAIN o EWOULDBLOCK. Esto proporciona un comportamiento similar al establecimiento de la bandera O_NONBLOCK (a través de la operación F_SETFL de fcntl(2)), pero difiere en que MSG_DONTWAIT es una opción por llamada, mientras que O_NONBLOCK es una configuración en la descripción del archivo abierto (ver open(2)), que afectará a todos los hilos del proceso que llama, así como a otros procesos que mantengan descriptores de archivo que se refieran a la misma descripción de archivo abierto.
MSG_EOR (desde Linux 2.2)
Termina un registro (cuando esta noción es compatible, como en los sockets de tipo SOCK_SEQPACKET).
MSG_MORE (desde Linux 2.4.4)
El llamante tiene más datos para enviar. Esta bandera se usa con sockets TCP para obtener el mismo efecto que la opción de socket TCP_CORK (ver tcp(7)), con la diferencia de que esta bandera se puede establecer por llamada.
Desde Linux 2.6, esta bandera también es compatible con sockets UDP e informa al kernel que empaquete todos los datos enviados en llamadas con esta bandera establecida en un solo datagrama que se transmite solo cuando se realiza una llamada que no especifica esta bandera. (Ver también la opción de socket UDP_CORK descrita en udp(7).)
MSG_NOSIGNAL (desde Linux 2.2)
No generar una señal SIGPIPE si el par en un socket orientado a flujo ha cerrado la conexión. El error EPIPE todavía se devuelve. Esto proporciona un comportamiento similar a usar sigaction(2) para ignorar SIGPIPE, pero, mientras que MSG_NOSIGNAL es una característica por llamada, ignorar SIGPIPE establece un atributo de proceso que afecta a todos los hilos del proceso.
MSG_OOB
Envía datos fuera de banda en sockets que admiten esta noción (p. ej., de tipo SOCK_STREAM); el protocolo subyacente también debe admitir datos fuera de banda.
MSG_FASTOPEN (desde Linux 3.7)
Intenta TCP Fast Open (RFC7413) y envía datos en el SYN como una combinación de connect(2) y write(2), realizando una operación implícita de connect(2). Se bloquea hasta que los datos se almacenan en búfer y se completa el handshake. Para un socket no bloqueante, devuelve el número de bytes almacenados en búfer y enviados en el paquete SYN. Si la cookie no está disponible localmente, devuelve EINPROGRESS y envía un SYN con una solicitud de cookie Fast Open automáticamente. El llamante necesita escribir los datos nuevamente cuando el socket esté conectado. En caso de error, establece el mismo errno que connect(2) si falla el handshake. Esta bandera requiere habilitar el soporte del cliente TCP Fast Open en el sysctl net.ipv4.tcp_fastopen.
Consulte la opción de socket TCP_FASTOPEN_CONNECT en tcp(7) para un enfoque alternativo.

sendmsg()

La definición de la estructura msghdr empleada por sendmsg() es la siguiente:


struct msghdr {
    void         *msg_name;       /* Dirección opcional */
    socklen_t     msg_namelen;    /* Tamaño de la dirección */
    struct iovec *msg_iov;        /* Array de scatter/gather */
    size_t        msg_iovlen;     /* # de elementos en msg_iov */
    void         *msg_control;    /* Datos auxiliares, ver abajo */
    size_t        msg_controllen; /* Tamaño del búfer de datos auxiliares */
    int           msg_flags;      /* Banderas (no utilizadas) */
};

El campo msg_name se usa en un socket no conectado para especificar la dirección de destino para un datagrama. Señala a un búfer que contiene la dirección; el campo msg_namelen debe establecerse al tamaño de la dirección. Para un socket conectado, estos campos deben especificarse como NULL y 0, respectivamente.

Los campos msg_iov y msg_iovlen especifican las ubicaciones de scatter-gather, como en writev(2)

sendto(2) - Páginas del manual de Linux

NAME

sendto - enviar datos a través de un socket

LIBRARY

Librería C estándar (libc)

SYNOPSIS

#include <sys/types.h>
#include <sys/socket.h>

ssize_t sendto(int sockfd, const void *buf, size_t len, int flags, const struct sockaddr *dest_addr, socklen_t dest_len);

DESCRIPTION

La llamada al sistema sendto envía un mensaje que consta de un búfer de datos de longitud len en el búfer que apunta buf. El envío se realiza a través del socket abierto asociado con el descriptor de archivo sockfd.

Si el socket no está conectado (es decir, no se ha llamado a connect(2)), la dirección del destinatario se especifica mediante dest_addr y dest_len. Estos argumentos especifican la dirección del par al que se enviará el datagrama.

Si el socket está conectado, los argumentos dest_addr y dest_len pueden ser NULL y 0 respectivamente. En este caso, los datos se envían al par al que se conectó el socket.

El argumento flags es una OR bit a bit de cero o más de las siguientes banderas:

MSG_CONFIRM
Indica que el remitente espera una confirmación de entrega. Solo se aplica a sockets de tipo SOCK_DGRAM y SOCK_RAW. Ver send(2) para más detalles.
MSG_DONTROUTE
Indica que se deben omitir las rutinas de enrutamiento normales. En su lugar, se utiliza una entrada de tabla de enrutamiento directa (solo para interfaces de red). Esta bandera puede ser utilizada solo por el privilegio de superusuario.
MSG_DONTWAIT
Establece la bandera del socket SO_DONTWAIT solo para esta operación. Esto significa que la llamada no bloqueará y, si la operación tendría que bloquearse, se devolverá inmediatamente con un error.
MSG_EOR
Indica el final del registro. Si el socket es de tipo stream, puede enviar todos los datos hasta este punto, y el par podría no ser capaz de detectar el final de cada registro.
MSG_MORE
(Solo Linux) Indica que se enviarán más datos al mismo destino. Esto puede permitir que el remitente optimice el envío, por ejemplo, al agrupar varios mensajes pequeños en un solo paquete. La llamada al sistema send(2) tiene la misma bandera.
MSG_NOSIGNAL
(Solo Linux) Evita que se envíe la señal SIGPIPE si el socket está desconectado.
MSG_OOB
Envía datos fuera de banda. Ver send(2) para más detalles.

Puede enviar información de control (datos auxiliares) utilizando los miembros msg_control y msg_controllen. El tamaño máximo del búfer de control que el kernel puede procesar está limitado por socket al valor en /proc/sys/net/core/optmem_max; ver socket(7). Para más información sobre el uso de datos auxiliares en varios dominios de socket, ver unix(7) y ip(7).

El campo msg_flags se ignora.

RETURN VALUE

En caso de éxito, estas llamadas devuelven el número de bytes enviados. En caso de error, se devuelve -1 y se establece la variable global errno para indicar el error.

ERRORS

Estos son algunos errores estándar generados por la capa de sockets. Pueden generarse y devolverse errores adicionales de los módulos de protocolo subyacentes; ver sus páginas de manual correspondientes.

EACCES
(Para sockets de dominio UNIX, identificados por ruta) Se niega el permiso de escritura en el archivo de socket de destino, o se niega el permiso de búsqueda en alguno de los directorios del prefijo de la ruta. (Ver path_resolution(7).)
(Para sockets UDP) Se intentó enviar a una dirección de red/difusión como si fuera una dirección unicast.
EAGAIN o EWOULDBLOCK
El socket está marcado como no bloqueante y la operación solicitada bloquearía. POSIX.1-2001 permite que cualquiera de estos errores se devuelva para este caso, y no requiere que estas constantes tengan el mismo valor, por lo que una aplicación portable debe comprobar ambas posibilidades.
EAGAIN
(Sockets de datagramas de dominio Internet) El socket al que se refiere sockfd no se había enlazado previamente a una dirección y, al intentar enlazarlo a un puerto efímero, se determinó que todos los números de puerto en el rango de puertos efímeros están actualmente en uso. Ver la discusión de /proc/sys/net/ipv4/ip_local_port_range en ip(7).
EALREADY
Otro Fast Open está en progreso.
EBADF
sockfd no es un descriptor de archivo válido y abierto.
ECONNRESET
Conexión reiniciada por el par.
EDESTADDRREQ
El socket no es de modo conexión y no se ha establecido ninguna dirección de par.
EFAULT
Se especificó una dirección inválida en el espacio de usuario para un argumento.
EINTR
Ocurrió una señal antes de que se transmitiera algún dato; ver signal(7).
EINVAL
Se pasó un argumento inválido.
EISCONN
El socket de modo conexión ya estaba conectado pero se especificó un destinatario. (Ahora se devuelve este error o se ignora la especificación del destinatario).
EMSGSIZE
El tipo de socket requiere que los mensajes se envíen atómicamente, y el tamaño del mensaje a enviar lo hizo imposible.
ENOBUFS
La cola de salida de una interfaz de red estaba llena. Esto generalmente indica que la interfaz ha dejado de enviar, pero puede ser causado por congestión transitoria. (Normalmente, esto no ocurre en Linux. Los paquetes se descartan silenciosamente cuando una cola de dispositivo se satura).
ENOMEM
No hay memoria disponible.
ENOTCONN
El socket no está conectado y no se ha proporcionado ningún destino.
ENOTSOCK
El descriptor de archivo sockfd no se refiere a un socket.
EOPNOTSUPP
Algún bit en el argumento flags es inapropiado para el tipo de socket.
EPIPE
El extremo local se ha cerrado en un socket orientado a conexión. En este caso, el proceso también recibirá una señal SIGPIPE, a menos que se establezca MSG_NOSIGNAL.

VERSIONS

Según POSIX.1-2001, el campo msg_controllen de la estructura msghdr debe ser de tipo socklen_t, y el campo msg_iovlen debe ser de tipo int, pero glibc actualmente los clasifica como size_t.

STANDARDS

POSIX.1-2024.

MSG_CONFIRM es una extensión de Linux.

HISTORY

4.4BSD, SVr4, POSIX.1-2001. (apareció por primera vez en 4.2BSD).

POSIX.1-2001 solo describe las banderas MSG_OOB y MSG_EOR. POSIX.1-2008 añade una especificación para MSG_NOSIGNAL.

NOTES

Ver sendmmsg(2) para información sobre una llamada al sistema específica de Linux que se puede usar para transmitir múltiples datagramas en una sola llamada.

BUGS

Linux puede devolver EPIPE en lugar de ENOTCONN.

EXAMPLES

Se muestra un ejemplo del uso de sendto() en getaddrinfo(3).
