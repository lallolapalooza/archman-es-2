NOMBRE

/etc/ser2net/ser2net.yaml - Archivo de configuración del proxy serie a red

DESCRIPCIÓN

ser2net solía ser un programa para conectar conexiones de red a puertos serie. Ahora es un programa para conectar gensios aceptadores a gensios conectores. Ver gensio(5) para detalles sobre gensios.

ser2net se configura con YAML, que es flexible y fácil de usar. Busque documentación de yaml en internet para saber cómo funciona.

Sin embargo, hay dos tipos de archivos YAML que ser2net puede usar: versión 1 y versión 2. Los archivos YAML versión 1 tienen más capacidad que los archivos versión 2, pero no son YAML estándar, un analizador YAML estándar no puede leerlos. ser2net detectará automáticamente la versión según lo que encuentre.

En la versión 2, puede tener múltiples documentos en un archivo y ser2net los leerá todos. YAML separa los documentos en un archivo con un solo "---" por sí mismo al principio de una línea. Aunque solo puede haber un conjunto de valores predeterminados, definiciones, conexiones, etc. en un documento, puede tener múltiples documentos en un archivo para permitir más de uno. Podría, por ejemplo, agrupar todas las conexiones con un conjunto particular de valores predeterminados en su propio documento.

ESPECIFICACIÓN DE DEFINICIÓN

YAML tiene la capacidad de crear alias que pueden usarse en otras partes del archivo de configuración. Estos se pueden usar para vincular cosas entre partes del archivo o (como una extensión de YAML) para sustitución de cadenas.

Define un alias en la versión 1 con lo siguiente:

define: &nombre_alias texto del alias

Esto creará un alias con el nombre dado. Luego puede usarlo en otro lugar como:

banner: *nombre_alias

y el banner será "texto del alias". A diferencia del YAML estándar, también puede usar esto dentro de cadenas usando

*(nombre_alias)

así que si tiene

banner: Mi banner *(nombre_alias) está aquí

El banner será "Mi banner texto del alias está aquí". Ver la documentación de YAML sobre cómo se manejan los espacios, pero como nota, use comillas si no está seguro, como:

define: &nombre_alias "texto del alias"
banner: "Mi banner *(nombre_alias) está aquí"

Si por alguna razón necesita "*(" en su texto, use "*(*" para eso.

Para los archivos YAML versión 2, la definición es:

defines:
nombre_alias: texto del alias
nombre_alias2: texto del alias 2

donde puede listar tantos alias como desee. En la versión 2, siempre se refiere a un alias con "=" en lugar de "*", como:


banner: "Mi banner =(nombre_alias) está aquí"

y si por alguna razón necesita "=(" en su texto, use "=(=" para eso.

En la versión 2, según el estándar YAML, solo puede haber una sección de definiciones, por lo que deben estar todas juntas.

INCLUYENDO OTROS ARCHIVOS

Un archivo YAML puede incluir otro archivo en el nivel principal, con:

include: <nombre_archivo>

Este nombre de archivo puede incluir comodines y se incluyen todos los archivos referenciados. Estos deben ser archivos yaml completos, pero se incluyen en contexto en este punto, con todas las definiciones, nombres de conexión, etc. Esto puede permitirle tener conexiones individuales en archivos individuales para facilitar la gestión.

En la versión 2, solo puede haber una inclusión en cada documento para que sea YAML legal, por lo que si necesita múltiples inclusiones, tendrá que tener múltiples documentos.

USANDO ARCHIVOS EXTERNOS

Puede que desee almacenar contraseñas y similares en archivos externos para mayor seguridad. Para la versión 1, poner "*{nombre_archivo}" en un escalar YAML insertará el contenido del archivo en ese punto. Si necesita un "*{" en la cadena por alguna razón, use "*{*".

Para la versión 2, use "={nombre_archivo}" en su lugar. Y "={=" para incluir un "={" en un archivo.

ESPECIFICACIÓN DE CONEXIÓN

Una conexión es una estructura que describe cómo conectar un gensio aceptador a un gensio conector.

Una especificación de conexión en la versión 1 comienza con:

connection: &<alias>
<definición>

En la versión 2, se especifica como:

connections:
<alias>:
<definición>

En la versión 2, todas las conexiones deben ocurrir juntas en un solo lugar.

La <definición> de una conexión es la misma para la versión 1 y la versión 2:

accepter: <aceptador>
timeout: <número>
enable: on|off
connector: <conector>
options:
<nombre_opción>: <valor_opción>
<nombre_opción>: <valor_opción>...

Un <aceptador> es una especificación de gensio aceptador. Cuando ser2net recibe una conexión en el aceptador, intenta establecer una conexión con el gensio <conector>. El alias es obligatorio, establece el nombre que se utiliza para la conexión en la interfaz de administración y para hacer referencia desde los rotadores.

Si la conexión no recibe ninguna actividad en <timeout> segundos, ser2net cerrará la conexión. Establecer <timeout> en cero deshabilita el tiempo de espera. El campo de tiempo de espera es opcional y por defecto es cero.

La conexión puede habilitarse o deshabilitarse con enable. El campo enable es opcional y por defecto es on. Esto es útil para deshabilitar temporalmente un puerto estableciendo enable en off y enviando una SIGHUP. Si hay usuarios conectados y deshabilita un puerto y envía una SIGHUP, los usuarios serán desconectados.

Una opción es una configuración que no tiene nada que ver con gensios específicos, son controles para ser2net en general. La sección de opciones es opcional.

Ver gensio(5) para mucha información sobre los gensios específicos disponibles.

Para permitir una conexión TCP a un puerto serie e ignorar el control del módem, puede hacer:

connection: &a_S0tcp
accepter: tcp,1234
connector: serialdev,/dev/ttyS0,local

Tanto los gensios aceptadores como los conectores se apilan, así que si desea agregar telnet con soporte RFC2217, puede hacer:

connection: &a_S0telnet
accepter: telnet(rfc2217),tcp,1234
connector: serialdev,/dev/ttyS0,local

Si desea aceptar una conexión telnet sobre SCTP solo en localhost IPv6 y conectarse a una conexión telnet con SSL sobre tcp, puede hacer:

connection: &a_mi_host
accepter: telnet,sctp,::1,1234
connector: telnet,ssl,tcp,mi_host.dominio.org,1234

El soporte RFC2217 solo tiene sentido con un dispositivo capaz de serie como conector. Tenga en cuenta también que IPv6 es totalmente compatible. Los aceptadores generalmente, por defecto, serán tanto IPv4 como IPv6 a menos que se especifique lo contrario. Ver gensio(5) para detalles.

Y sí, SCTP es compatible y muy recomendable si puede usarlo. El multihoming por sí solo vale la pena.

Podría crear un inicio de sesión seguro con soporte telnet RFC2217 que luego se conecte a una conexión IPMI sol. Tenga en cuenta cómo se divide la línea del conector con YAML.

connection: &authsol

accepter: telnet(rfc2217),mux,certauth,ssl,sctp,1234
connector: ipmisol,lan -U usuario_ipmi -P test -p 9001
servidor_ipmi.dominio.org,9600
options:
banner: Mi banner

Estos son algunos ejemplos. Para SSL y certauth, he omitido la configuración de autenticación, más sobre eso más adelante. Se recomienda encarecidamente el uso de la autenticación, ahora es fácil con gtlssh y si necesita usarlo desde un programa, es fácil con gensio. Incluso hay soporte en Python. Agregar soporte para otros lenguajes de scripting no debería ser demasiado difícil.

SPECIAL STRING HANDLING

Some parameters, like filenames and banners, have special formatting for inserting various values. These are all prepended with '\'. This takes the standard "C" \x characters.

\a - campana
\b - retroceso
\f - avance de página
\n - nueva línea
\r - retorno de carro
\t - tabulación
\v - tabulación vertical
\\ - \
\? - ?
\' - '
\" - "
\nnn - valor octal para nnn
\xXX - valor hexadecimal para XX
\d - La cadena de conexión (/dev/ttyS0, etc.)
\o - El nombre de la conexión.
\p - Número de puerto de red
\B - Los parámetros del puerto serie (ej. 9600N81) si son aplicables
\Y -> año
\y -> día del año (días desde el 1 de enero)
\M -> mes (ene, feb, mar, etc.)
\m -> mes (como número)
\A -> día de la semana (lun, mar, etc.)
\D -> día del mes
\e -> época (segundos desde el 1 de enero de 1970)
\U -> microsegundos en el segundo actual
\p -> número de puerto local
\I -> dirección IP remota (en formato de puntos)
\H -> hora (formato 24 horas)
\h -> hora (formato 12 horas)
\i -> minuto
\S -> segundo
\q -> am/pm
\P -> AM/PM

Estas secuencias pueden usarse para hacer que el nombre del archivo sea único por cada conexión abierta y para identificar de qué puerto/dispositivo proviene el nombre del archivo. Ten en cuenta que en los nombres de archivo, al usar \d o \o, se elimina todo hasta la última / en el nombre del dispositivo, inclusive, porque no se puede tener una / en un nombre de archivo. Así, en un nombre de archivo /dev/ttyS0 se convertiría en ttyS0.

Ten en cuenta que en los banners y otras cadenas que salen (no en nombres de archivo) debes usar \r\n para enviar una nueva línea; esto es manejo crudo y \n solo bajará una línea, no volverá al principio de la línea.

OPCIONES DE ESPECIFICACIÓN DE CONEXIÓN

kickolduser: true|false establece el puerto para que el usuario anterior sea expulsado si entra un nuevo usuario. Útil si olvidas desconectarte de algún lugar con frecuencia.

banner: <cadena del banner> muestra el banner dado cuando un cliente se conecta. Utiliza el manejo de cadenas como se describe en "MANEJO ESPECIAL DE CADENAS" arriba.

signature: <cadena de firma> envía la firma RFC2217 a solicitud del cliente. Esto puede ser una cadena vacía.

openstr: <cadena del nombre openstr> Envía la cadena dada al dispositivo al abrir por primera vez. Esto puede ser una cadena vacía. Utiliza el manejo de cadenas como se describe en "MANEJO ESPECIAL DE CADENAS" arriba.

closestr: <nombre clostr> Envía la cadena dada al dispositivo al cerrar por última vez. Esto puede ser una cadena vacía. Utiliza el manejo de cadenas como se describe en "MANEJO ESPECIAL DE CADENAS" arriba.

closeon: <cadena closeon> Si se ve la cadena dada proveniente del lado del conector de la conexión, cierra la conexión. La comparación aquí es, por simplicidad, simplista. Las expresiones complejas con cosas repetitivas pueden no compararse correctamente. Por ejemplo, si tu cadena closeon es "ababc" y tu cadena de entrada es "abababc", la comparación fallará porque el algoritmo de comparación verá "ababa" y fallará en la "a" final y comenzará de nuevo con "abc", lo que no coincidirá. Esto no debería causar problemas en la mayoría de los casos, pero si lo hace, contacta a los autores y se puede mejorar.

accepter-retry-time: <tiempo en segundos> Si el aceptador no se inicia al arrancar, espera esta cantidad de segundos y vuelve a intentarlo.

connector-retry-time: <tiempo en segundos> En un puerto de reconexión, si el conector no se inicia o se cae. Espera esta cantidad de segundos y vuelve a intentarlo.

trace-read: <nombre de archivo> Cuando se abre el aceptador, abre el archivo dado y almacena todos los datos leídos del dispositivo físico (y, por lo tanto, escritos en la red del cliente/puerto aceptador) en el archivo. Si el archivo ya existe, se anexa. El archivo se cierra cuando se cierra el puerto. El nombre del archivo utiliza el manejo de cadenas como se describe en "MANEJO ESPECIAL DE CADENAS" arriba.

trace-write: <nombre de archivo> Similar a tr, pero rastrea los datos escritos en el gensio de conexión.

trace-both: <nombre de archivo> rastrea los datos de lectura y escritura en el mismo archivo. Ten en cuenta que esto es independiente de tr y tw, por lo que puedes estar rastreando lectura, escritura y ambos en archivos diferentes.

trace-hexdump: true|false activa/desactiva la salida hexdump en todos los archivos de rastreo. Cada línea en el archivo de rastreo tendrá 8 (o menos) bytes en formato hexadecimal/ASCII canónico. Esto es útil para depurar un protocolo binario.

trace-timestamp: true|false añade/elimina una marca de tiempo a todos los archivos de rastreo. Se antepone una marca de tiempo a cada línea si hexdump está activo para el archivo de rastreo. También se registra una línea con marca de tiempo en el archivo de rastreo cuando un cliente remoto se conecta o desconecta del puerto.

[trace-read-|trace-write-|trace-both-]hexdump: true|false activa/desactiva la salida hexdump para un solo archivo de rastreo. Se puede combinar con hexdump. El orden es importante.

[trace-read-|trace-write-|trace-both-]timestamp: true|false añade/elimina una marca de tiempo a solo uno de los archivos de rastreo. Se puede combinar con [-]timestamp. El orden es importante.

telnet-brk-on-sync: true|false hace que una operación de sincronización telnet envíe una interrupción. Por defecto, los datos se vacían hasta la marca de datos, pero no se envía ninguna interrupción.

chardelay: true|false habilita la pequeña espera después de cada carácter recibido en el gensio de conexión antes de enviar datos al gensio aceptado. Normalmente, ser2net esperará el tiempo necesario para recibir 2 caracteres del puerto serie, o al menos 1000us, antes de enviar. Esto permite un uso más eficiente de los recursos de red al recibir grandes cantidades de datos, pero proporciona una interactividad razonable. El valor predeterminado es true.

Ten en cuenta que esta función está diseñada para equilibrar la eficiencia de la red y la interactividad. No está diseñada para garantizar tamaños mínimos de fragmentos de datos, ya que la programación de tareas y las pilas de red también pueden modificar estas cosas.

chardelay-scale: <número> establece el tiempo, medido en décimas de caracteres del puerto serie, a esperar después de recibir algo de la conexión antes de enviar a el gensio aceptado. Por lo tanto, establecer esto en 25 hará que ser2net espere el tiempo necesario para recibir 2.5 caracteres del puerto serie después de recibir el último carácter antes de enviar los datos al puerto TCP. El valor predeterminado es 20, el máximo es 1000. Esto se ignora para gensios no serie.

chardelay-min: <número> es lo mismo que chardelay-scale, pero en microsegundos. Se utiliza el mayor valor entre chardelay-scale y chardelay-min. El valor predeterminado es 1000, el máximo es 100000.

chardelay-max: <número> establece el retraso máximo que ser2net esperará, en microsegundos, después de recibir un carácter, antes de enviar los datos. El valor predeterminado es 20000, el máximo es 1000000. Esto mantiene la conexión funcionando sin problemas a bajas velocidades.

sendon: <cadena sendon> Si se ve la cadena dada proveniente del lado del conector de la conexión, envía los datos almacenados en búfer hasta e incluyendo la cadena. Deshabilitado por defecto. Como ejemplo, esto se puede establecer en \r\n con la configuración de chardelay apropiada para enviar una línea a la vez. Utiliza el manejo de cadenas como se describe en "MANEJO ESPECIAL DE CADENAS" arriba. Consulta las notas sobre la cadena closeon para obtener información importante sobre cómo se realiza la comparación.

dev-to-net-bufsize: <número> establece el tamaño del búfer que lee del gensio de conexión y escribe en el gensio aceptado.

net-to-dev-bufsize: <número> establece el tamaño del búfer que lee del gensio aceptado y escribe en el gensio de conexión.

led-tx: <alias de led> usa el led definido previamente para indicar el tráfico tx serie en este puerto. Para la versión 2, esto debería ser un alias YAML, como *led2. Para la versión 2, solo usa el nombre, como led2.

led-rx: <alias de led> usa el led definido previamente para indicar el tráfico rx serie en este puerto. Para la versión 2, esto debería ser un alias YAML, como *led2. Para la versión 2, solo usa el nombre, como led2.

max-connections: <número> establece el número máximo de conexiones que se pueden realizar en este puerto TCP en particular. Si realizas más de una conexión al mismo puerto, la salida de cada puerto va al dispositivo, y la salida del dispositivo va a todos los puertos simultáneamente. Consulta "CONEXIONES MÚLTIPLES" a continuación para obtener detalles. El valor predeterminado es 1.

remaddr: <dirección>[;<dirección>[;...]] especifica las conexiones remotas permitidas, donde la dirección es una dirección estándar, generalmente en el formato <dirección IP>,<puerto>. Se pueden separar varias direcciones con punto y coma, y puedes especificar remaddr más de una vez.

Si estableces el puerto para una dirección en cero, ser2net aceptará una conexión desde cualquier puerto del host de red dado.

no-con-to-acc: true|false Si es true, no transfiere ningún dato del conector al aceptador. Descarta cualquier dato recibido del conector.

no-acc-to-con: true|false Si es true, no transfiere ningún dato del aceptador al conector. Descarta cualquier dato recibido del aceptador.

connback: <conector>[;<conector>[;...]] especifica las conexiones inversas que se realizarán cuando lleguen datos al dispositivo. Cuando llegan datos al lado del dispositivo (el conector principal de la conexión), ser2net se conectará a cada connback especificado. No se realiza ninguna conexión hasta que lleguen datos, y se aplican los tiempos de espera de conexión normales.

Ten en cuenta que esto utilizará una de las conexiones del puerto de forma continua. Es posible que necesites aumentar max-connections si necesitas más de una o si también deseas aceptar conexiones entrantes.

Las direcciones de conexión inversa deben coincidir con el formato de la dirección del aceptador. Por ejemplo, si tu aceptador es "telnet,tcp,1234", tu dirección de conexión inversa debe ser algo como "telnet,tcp,hostname,1123".

El puerto no enviará datos a ningún connback hasta que todos los connbacks estén conectados.

Un puerto de conexión inversa también puede tener conexiones realizadas a él si estableces el número de conexiones mayor que el número de connbacks especificados. Sin embargo, esas conexiones no recibirán datos del puerto a menos que se hayan establecido todos los connbacks.

connback-timeout: <tiempo en segundos> especifica un tiempo de espera separado para los puertos de conexión inversa. Normalmente utiliza el tiempo de espera principal, esto te permite tener uno diferente. Establecerlo en cero, como el tiempo de espera principal, deshabilita el tiempo de espera.

authdir: <cadena de directorio> especifica el directorio de autenticación a utilizar para esta conexión.

pamauth: <nombre del servicio> habilita la autenticación PAM y establece el nombre del servicio PAM.

allowed-users: <lista de nombres separados por espacios> Los usuarios que tienen permitido usar esta conexión. Esto no tiene significado si au

AUTHENTICATION

A connection may be restricted to only allow specific users to connect to it. This is done using the parameter allowed-users.

allowed-users: [ ! ] <user> [ , [ ! ] <user> [ , ... ] ] Specifies a list of users that are allowed to connect to the connection. If the first character is a "!" then the user is not allowed. The default is that all users are allowed.

For example:

connection:
name: con1
...
allowed-users: bob, carol, !fred

This allows bob and carol to connect, but not fred. If the list is empty then no users are allowed.

There are two other methods of authentication.

authdir: /usr/share/ser2net/auth Specifies the directory where the authentication files are stored. The files are named after the connection name, and contain a list of users that are allowed to connect. Blank lines and lines starting with # are ignored. The user list is comma separated.

authdir-admin: /etc/ser2net/auth Specifies the directory where the authentication files for admin connections are stored. Admin connections are specified in the admin section of the configuration file.

pamauth: <service> Use PAM for authentication. If this is specified, then the authdir and allowed-users are ignored. <service> is the name of the PAM service file to use. If this is not specified, then PAM authentication is disabled.

pamauth-admin: <service> Use PAM for admin connection authentication. If this is specified, then the authdir-admin is ignored. <service> is the name of the PAM service file to use. If this is not specified, then PAM authentication is disabled for admin connections.

Note that only one authentication method can be used per connection. If pamauth is specified, then authdir and allowed-users are ignored.

Note that authentication is not enabled on the connections. If this is not set or defaulted, all users are allowed. If this is set to an empty set of users, then no users are allowed. This may be specified more than once, each one adds more users.

mdns: true|false Enables/disables mdns support for the connection. If you set this and mdns is available, ser2net will create a service on mdns for the port.

mdns-interface: <num> Sets the specific network interface to advertise the device. Defaults to -1, which means all network interfaces.

mdns-nettype: unspec|ipv4|ipv6 Sets which network type to provide for the device advertisement. Defaults to unspec, which means do ipv4 and ipv6.

mdns-name: <string> Sets the name in the mDNS advertisement. Defaults to the connection name.

mdns-type: <string> Sets the type in the mDNS advertisement. Defaults to "_iostream._xxx" where xxx is either tcp, udp # # or sctp base on the gensio type.

mdns-domain: <string> Sets the name in the mDNS advertisement. Defaults to the system setting. Don't set this unless you really know what you are doing.

mdns-host: <string> Sets the host in the mDNS advertisement. Defaults to the system setting. Don't set this unless you really know what you are doing.

mdns-txt: <string> Adds a text string to the mDNS advertisement. The string should be in the form "name=value". You can put anything you want in the strings. Two default strings are added by ser2net: "provider=ser2net" and "gensiostack=..." where the stack of gensios is added, like "telnet(rfc2217),tcp)". The idea of gensiostack is you can just tack on the address to the end an make a connection using str_to_gensio().

mdns-sysattrs: true|false On Linux adds system attributes from sysfs for USB serial ports to the mDNS txt fields. If the serial port is USB, it adds "devicetype=serialusb" and the following attributes from sysfs: bInterfaceNumber, interface, idProduct, idVendor, serial, manufacturer, product. If they are not present in sysfs, they are not added. If the serial port is not USB, then "devicetype=serial" is added.

Note: Be *very* careful when using a gensiostack with str_to_gensio(). Just blindly calling str_to_gensio() with it could result in significant security issues, as it can pass pty, stdio, trace, etc. gensios in it. You must either validate that the stack is a safe set or just use it for information. You have been warned. Be careful.

ROTATOR

A rotator allows a single network connection to connect to one of a number of connections.

A version 1 rotator specification starts with:

rotator: <alias>
<definition>

A version 2 rotator specification starts with:

rotators:
<alias>:
<definition>

Just like connections, in version 2 you have to put all the rotators together.

The definition of a rotator is almost the same between version 1 and version 2:

accepter: <accepter>
connections: [
<connection alias>,
<connection alias>....
]
options:
<option name>: <option val>
<option name>: <option val>...

A rotator has four possible options, "authdir", "pamauth", "allowed-users", and "accepter-retry-time", both same as connections.

For version 1, you should use YAML aliases for the connections. For version 2, just use the alias names.

Connections to the accepter will go through the set of connections and find the first unused one and use that. The next connection will start after the last connection used. Note that disabled connections are still accessible through rotators.

Note that the security of the connection is NOT used, only the security of the rotator.

SER2NET DEFAULTS

To set a default in version 1, do:

default:

name: <default name>
value: <default value>
class: <default class>

In version 2, like other things, the defaults are all in one place in a document, like:

defaults:
<name>:
value: <default value>
class: <default class>
<name2>:
value: <default value>
class: <default class>

The class is optional, if it is not there it sets the base default for all classes that is used unelss overridden for a specific class. If the class is there, it sets the default for a specific gensio class. There is also a ser2net class that is for ser2net specific options.

The class is useful if you want different values for different gensio types. For instance, if you wanted all serial ports to run at 9600 baud and all IPMI SOL connections to run at 115200 baud, you could do:

default:
name: speed
value: 9600
class: serialdev
default:
name: speed
value: 115200
class: ipmisol

The value is also optional, if it is not present a string value is set to NULL and an integer value is set to 0.

The order in the file is important, you must set a default before it is used, and you can change the value of the default. It will affect all uses following the setting.

To delete a default value for class (so it will use the base default), for version 1 do:

delete_default:
name: <default name>,
class: <default class>

For version 2, do:

delete_defaults:
<default name>: [ <class1>, <class2>, ... ]
<default name2>: [ <class1>, <class2>, ... ]
and it will delete the defaults for the classes in the list after it.

You must supply the class, you cannot delete base defaults.

The following default values are specific to ser2net, given with their default values:

So setting this to 25 will cause ser2net to wait the amount of time it takes to receive 2.5 serial port characters before sending the data on to the TCP port. This can range from 1-1000.

dev-to-net-bufsize: 64

If a "!" is given at the beginning of the address, the address is a "connect back" address. If data comes in on the device, ser2net will attempt to connect to the address. This works on TCP and UDP.

CONEXIONES DE ADMINISTRADOR

Hay un aceptador de administrador que puedes definir para ser2net, te permite iniciar sesión, ver el estado y cambiar algunas cosas. Consulte "INTERFAZ DE ADMINISTRADOR" en ser2net(8) para obtener detalles sobre cómo usarlo. El formato es:

admin: [&<nombre>]
accepter: <aceptador>
options:
<nombre de opción>: <valor de opción>
<nombre de opción>: <valor de opción>...

Las siguientes opciones de autenticación disponibles son "authdir-admin", que establece el directorio de autenticación para el puerto de administrador, y "pamauth-admin", que establece el nombre del servicio PAM y habilita la autenticación PAM. Ambas son diferentes de "authdir" resp. "pamauth" para las conexiones, aunque puedes establecerlas al mismo valor.

Además, las mismas opciones mDNS están disponibles para los puertos de administrador que para las conexiones. Y puedes establecer un alias opcional que también establecerá el nombre mdna.

Al igual que las conexiones, las opciones mDNS predeterminadas funcionan para "mdns-interface", "mdna-type", "mdns-domain" y "mdns-host". A diferencia de las conexiones, el booleano "mdns" no proviene del valor predeterminado, debes especificarlo como una opción de administrador para activar mDNS para el puerto de administrador. Esto permite que se especifique por separado y mantener la compatibilidad con versiones anteriores.

LEDs

ser2net puede hacer parpadear LEDs durante la actividad serie. Para crear un LED en la versión 1, haz:

led: &<alias>
driver: sysfs
options:
<nombre de opción>: <valor de opción>
<nombre de opción>: <valor de opción>

En la versión 2, usa:

leds:
<alias>:
driver: sysfs
options:
<nombre de opción>: <valor de opción>
<nombre de opción>: <valor de opción>
<alias>:
driver: sysfs
options:
<nombre de opción>: <valor de opción>
<nombre de opción>: <valor de opción>

El único controlador compatible es sysfs. Las opciones compatibles son:

device: <nombre de dispositivo sysfs> da el nombre del LED en /sys/class/led. Estos generalmente tienen ":" en ellos, por lo que necesitarás poner el nombre entre comillas. Esto es obligatorio.

duration: <tiempo en ms> El tiempo en milisegundos para hacer parpadear el LED. Predeterminado a 10.

state: <número> El valor que se establecerá en el LED para habilitarlo. Predeterminado a 1, pero puede necesitar ser un valor diferente.

Haces referencia al LED por alias en la sección de opciones de conexión, consulta esa sección para obtener detalles. Asegúrate de haber ejecutado "modprobe ledtrig-transient" o los desencadenadores no funcionarán, ya que requieren el desencadenador transitorio.

También es probable que necesites acceso de root para acceder a la configuración de los LEDs.

Los nombres de archivo, banners, cadenas de apertura/cierre, cadenas de cierre y cadenas de envío pueden contener secuencias de escape normales de "C" y una gran cantidad de otras secuencias de escape, además:

\xXX - valor hexadecimal para XX
\d - La cadena gensio de conexión (serialdev,/dev/ttyS0, etc.)
\o - El dispositivo especificado en la línea de configuración (antes de la sustitución de DEVICE)
\N - El nombre del puerto
\p - La cadena aceptadora
\B - Los parámetros del puerto serie (por ejemplo, 9600N81)

Además, por motivos de compatibilidad con versiones anteriores, ya que los nombres de archivo y los banners solían tener un formato diferente, \s son los parámetros del puerto serie si está en un banner y segundos si está en un nombre de archivo. Se desaconseja su uso, ya que puede cambiar en el futuro.

Estas secuencias se pueden usar para hacer que el nombre del archivo sea único por apertura y para identificar para qué puerto/dispositivo era el nombre del archivo. Tenga en cuenta que en los nombres de archivo cuando se usa \d o \o, se elimina todo hasta la última / en el nombre del dispositivo, incluida, ya que no puede haber una / en un nombre de archivo. Por lo tanto, en un nombre de archivo /dev/ttyS0 se convertiría solo en ttyS0.

MANEJO DE COMILLAS Y FORMATO DE CADENAS

yaml procesará secuencias de escape "\" entre comillas dobles, por lo que no se recomienda el uso de comillas dobles para lo anterior. Si pones los valores entre comillas simples, yaml no los procesará y en su lugar los pasará para que puedan ser procesados por ser2net.

ESPACIOS, COMILLAS Y COLOCACIÓN DE ESPACIOS EN CADENAS

YAML y el procesamiento del aceptador/conector interactúan al tratar con las comillas. Por defecto, YAML ignora la cantidad de espacios entre elementos separados por espacios. Las líneas que están indentadas después de un elemento se consideran una continuación del elemento, por lo que algo como:

connector: serialdev,/dev/ttyUSB0,
9600n81
local nobreak
rtscts
es lo mismo que
connector: serialdev,/dev/ttyUSB0, 9600n81 local nobreak rtscts

YAML tiene sus propios mecanismos de comillas estándar, por lo que si haces:

connector: "serialdev,/dev/ttyUSB0,9600n81 local"

los dos espacios antes de "local" se conservarán cuando se pasen al procesamiento del conector (aunque en este caso no importará porque el procesamiento del conector ignorará los espacios adicionales).

Si necesitas un espacio significativo, por ejemplo, en un nombre de archivo pasado a una clave, no puedes hacer:

accepter: ssl(CA=/etc/ser2net/my CA/),tcp,3000

porque el procesamiento del aceptador dividirá los argumentos en el espacio y no reconocerá qué es "CA/". Tampoco puedes hacer:

accepter: ssl(CA="/etc/ser2net/my CA/"),tcp,3000

porque YAML eliminará las comillas, esto es funcionalmente equivalente al ejemplo anterior. Y

accepter: ssl(CA="/etc/ser2net/my\ CA/"),tcp,3000

tampoco funcionará; dentro de comillas dobles, YAML convertirá "\ " en un espacio. Tienes un par de opciones. Puedes hacer:

accepter: ssl(CA=/etc/ser2net/my\ CA/),tcp,3000

o

accepter: ssl(CA='/etc/ser2net/my\ CA/'),tcp,3000

porque fuera de las comillas, YAML no procesará el "\ " y no lo procesará entre comillas simples. O si tienes muchos espacios o dos puntos, también puedes hacer:

accepter: ssl(CA="\"/etc/ser2net/my CA/\""),tcp,3000

porque dentro de las comillas exteriores, YAML convertirá el '\'"'' en un '"' y lo pasará al procesamiento del aceptador, que interpretarán las comillas como esperarías.

UDP

El manejo de UDP es un poco diferente de lo que podrías imaginar, porque es difícil para ser2net saber a dónde enviar los datos. Para manejar esto, los puertos UDP todavía tienen el concepto de una "conexión". Si un puerto UDP no está conectado, entonces si recibe un paquete, la dirección remota de ese paquete se establecerá en el extremo remoto de la "conexión". Realizará todas las operaciones normales de nueva conexión. ser2net aceptará nuevas conexiones hasta "max-connections" y luego ignorará los paquetes de otras direcciones hasta que ocurra una desconexión.

Desafortunadamente, no hay una manera fácil de saber cuándo desconectarse. Tienes dos opciones básicas:

  • Establece un tiempo de espera; si no se ha tenido noticias del extremo remoto antes del tiempo de espera, el puerto se desconecta y alguien más puede conectarse. Esto significa que todo lo que use el puerto debe enviar periódicamente un paquete (vacío está bien) a ser2net para mantener la conexión activa.
  • Usa la opción kickolduser en el puerto; cualquier nueva conexión que llegue reemplazará la conexión anterior.

Tenga en cuenta que los puertos UDP manejan múltiples conexiones al igual que los puertos TCP, por lo que puede tener múltiples escuchadores UDP.

También tienes una tercera opción. Si estableces una dirección remota (remaddr) con un puerto distinto de cero y un puerto de conexión de retorno (consulte la discusión sobre direcciones remotas anteriormente), ser2net tomará una de las conexiones y la asignará permanentemente a ese puerto. Esto se llama una dirección remota fija. Todo el tráfico del dispositivo irá a ese puerto. Cada dirección remota fija en un puerto UDP debe tener una conexión correspondiente, por lo que si tiene 3 direcciones remotas fijas, debe tener al menos 3 conexiones.

MÚLTIPLES CONEXIONES

Como se mencionó anteriormente, puedes establecer max-connections=<n> en un puerto para permitir más de una conexión a la vez al mismo puerto serie. Estas conexiones compartirán todas las configuraciones. No puedes tener dos puertos TCP separados conectados al mismo puerto al mismo tiempo.

Esto tiene algunas interacciones significativas con otras características:

control de flujo no es exactamente una característica,

but more an interacción entre las diferentes conexiones. Si un puerto TCP deja de recibir datos de ser2net, todos los puertos TCP conectados se controlarán por flujo. Esto significa que una única conexión TCP puede detener todas las demás.

closeon cerrará todas las conexiones cuando se vea la secuencia de cierre.

openstr solo se envía cuando el puerto no está conectado y se establece la primera conexión.

closestr solo se envía cuando el último puerto se desconecta y no hay más conexiones al puerto.

Cualquier monitor ("monitor start" desde una conexión de control) capturará la entrada de todas las conexiones de red.

kickolduser desconectará una conexión existente si llega una conexión a un puerto que ya tiene el número máximo de conexiones. La conexión desconectada se elige de forma arbitraria y el algoritmo está sujeto a cambios.

tracing rastreará datos de todas las conexiones de red.

rfc2217 (control de serie por telnet remoto) cambiará la configuración de la conexión en el dispositivo y se aceptará desde cualquier conexión de red.

reconfig on SIGHUP Consulte la sección "SIGHUP" de ser2net(8) para obtener detalles.

ROTATOR solo elegirá un puerto si no hay conexiones en absoluto en ese puerto. Tenga en cuenta que el uso de un rotador con un puerto con max-connections > 1 resultará en un comportamiento indefinido.

timeout será por puerto TCP y solo desconectará ese puerto TCP en caso de tiempo de espera agotado.

telnet_brk_on_sync enviará una interrupción para cualquier puerto TCP que realice una sincronización.

showport en la interfaz de administración mostrará todas las conexiones posibles, por lo que si dice max-connections=3, obtendrá tres entradas.

showshortport en la interfaz de administración solo mostrará la primera conexión activa, o si no hay ninguna conexión presente, mostrará la que fue la primera la última vez que estuvo presente una conexión.

AUTENTICACIÓN Y CIFRADO

TCP WRAPPERS

ser2net utiliza la interfaz de TCP wrappers para implementar la seguridad basada en host. Consulte hosts_access(5) para obtener una descripción de la configuración del archivo. ser2net utiliza dos demonios: "ser2net" es para los puertos de datos y "ser2net-control" es para los puertos de control.

CIFRADO

ser2net admite el cifrado SSL utilizando el gensio ssl. Para habilitar el cifrado, use un aceptador como:

telnet,ssl,tcp,1234

Luego puede usar gensiot para conectarse:

gensiot telnet,ssl,<servidor>,1234

o puede instalar telnet-ssl y hacer

telnet -z ssl,secure <servidor> 1234

La conexión SSL se realiza utilizando las claves proporcionadas. En este ejemplo, ser2net utiliza las claves predeterminadas (como se establecen en el valor predeterminado, ver más abajo). También puede establecerlas usando (key=<archivo_clave>,cert=<archivo_certificado>) después de ssl arriba, o modificar los valores predeterminados.

Si no tiene certificados genuinos de una autoridad certificadora, la conexión fallará debido a un error de certificado. Obtener certificados de esta manera es muy inconveniente, por lo que hay otra forma. Puede hacer:

gtlssh-keygen --keydir /etc/ser2net --commonname "hostname-ser2net" serverkey ser2net

para generar las claves predeterminadas en /etc/ser2net (o donde sea). El certificado/clave se llamará /etc/ser2net/ser2net.crt|key.

NOTA: Si compila ser2net usted mismo, por defecto autoconf establece el directorio de configuración del sistema (normalmente /etc) como /usr/etc. Esto es una gran molestia con autoconf. Por lo tanto, si no lo cambia, necesitaría /usr/etc donde dice /etc. Sin embargo, generalmente la forma correcta de hacerlo es agregar "--sysconfdir=/etc" al comando de configuración al configurar ser2net. Si una distribución ha compilado ser2net para usted, eso debería haberlo hecho por defecto, por lo que no hay de qué preocuparse en ese caso.

Luego, copie ser2net.crt al sistema del usuario y proporciónelo a los comandos de conexión, como:

gensiot telnet,ssl(CA=ser2net.crt),<servidor>,1234

o

telnet -z ssl,secure,cacert=ser2net.crt 1234

Luego tendrá una conexión cifrada. Solo asegúrese de que sus certificados sean válidos.

Tenga en cuenta que el "-ser2net" al final de la clave es importante porque hace que el nombre común del certificado sea más único. Realmente puede poner lo que quiera para lo que proporcione a keygen, siempre y cuando lo renueve correctamente. Ese será el nombre común del certificado.

AUTENTICACIÓN CON SSL

ser2net proporciona una forma de autenticarse con SSL. No es lo mejor, pero funciona. Debe habilitar clientauth en ssl:

telnet,ssl(clientauth),tcp,1234

o establecerlo en el valor predeterminado. Luego, debe crear un certificado con el nombre de usuario como nombre común. Puede hacerlo con:

gtlssh-keygen --keydir directorio_salida --commonname nombre_usuario generar_clave nombre_clave

que generará nombre_clave.crt y nombre_clave.key en directorio_salida. Luego, coloque nombre_clave.crt en el <authdir>/nombre_usuario/allowed_certs de ser2net. Por defecto, <authdir> es /usr/share/ser2net/auth, pero puede cambiarlo con el valor predeterminado de authdir en el archivo de configuración de ser2net o estableciendo authdir en conexiones individuales (en caso de que desee diferentes para diferentes puertos). Luego, debe volver a hashear el directorio allowed_certs:

gtlssh-keygen rehash <authdir>/nombre_usuario/allowed_certs

Luego, reinicie/recargue ser2net y use una de estas líneas muy largas para conectarse por telnet:

gensiot telnet,ssl(CA=ser2net.crt,cert=nombre_usuario.crt,key=nombre_usuario.key),<servidor>,1234

telnet -z ssl,secure,cacert=ser2net.crt,cert=nombre_usuario.crt,key=nombre_usuario.key servidor 1234

AUTENTICACIÓN CON CERTAUTH (GTLSSH)

Todo lo anterior es una gran molestia. Afortunadamente, hay una forma más fácil. gtlssh es un programa similar a ssh, pero se ejecuta sobre TLS e implementa un protocolo de autenticación similar a ssh utilizando el gensio certauth.

ser2net admite este sistema de autenticación que se ejecuta sobre los gensios ssl y certauth. Esos gensios proporcionan el marco para manejar la autenticación, ser2net mismo la controla.

Esto utiliza el mismo directorio authdir y claves permitidas que antes, y aún requiere un certificado de servidor, pero el autofirmado generado con gtlssh-keygen funciona bien sin hacer nada especial. Agregue certauth a la línea del puerto:

telnet,mux,certauth,ssl,tcp,1234

y *asegúrese* de que clientauth esté deshabilitado para ssl (o ssl seguirá intentando autenticar al cliente). Deshabilitado es el valor predeterminado, pero en caso de que lo haya cambiado, el valor predeterminado...

La entrada mux se debe a que gtlssh utiliza el gensio mux para permitir múltiples canales en la misma sesión. No estaba allí con versiones anteriores (anteriores a 1.2) de gtlssh, pero es necesario para las más nuevas. gtlssh también tiene una opción --nomux, por si acaso.

El programa gtlssh maneja su propio manejo de certificados. Consulte la página man de gtlssh para obtener detalles al respecto. Tome el certificado para gtlssh y colóquelo en el directorio authdir/nombre_usuario/allowed_certs y vuelva a hashearlo como antes. gtlssh *no* utilizará el nombre común proporcionado en el certificado, sino que utilizará un nombre de usuario proporcionado por gtlssh. Luego, conéctese con gtlssh:

gtlssh --nosctp --telnet nombre_usuario@servidor 1234

El --nosctp evita que gtlssh intente usar sctp, lo que fallará porque pusimos tcp en la línea del puerto. ¡Podría usar sctp allí y obtener todas sus ventajas de forma gratuita! Entonces, --nosctp ya no sería necesario para evitar las advertencias.

El nombre de usuario es opcional si es el mismo que su usuario actual. Si no se ha conectado a ese servidor/puerto antes, gtlssh le pedirá que lo verifique, de manera similar a como lo hace ssh. Si los certificados, la dirección IP, etc. cambian, gtlssh se lo informará.

Si no desea utilizar un certificado (los certificados son ciertamente preferibles, pero pueden no ser siempre viables), también puede utilizar un inicio de sesión con contraseña. Debe establecer enable-password en las opciones del gensio certauth para que las contraseñas funcionen. Cuando se conecte con gtlssh, si la validación del certificado falla, se le pedirá la contraseña. La autenticación de contraseña se puede realizar de dos maneras diferentes. Ambas son mutuamente excluyentes, dependiendo de si pamauth está configurado o no:

  • Para autenticarse utilizando la biblioteca PAM, establezca el nombre del servicio PAM a través de la opción pamauth.
  • Coloque una contraseña en authdir/nombre_usuario/password. Si coincide con la primera línea del archivo de contraseñas y pamauth no está configurado, la autenticación tendrá éxito.

AUTENTICACIÓN Y ROTADORES

Los rotadores son un caso especial. TENGA CUIDADO. Un rotador tiene su propia autenticación. Si configura la autenticación en un puerto que forma parte de un rotador, la autenticación de ese puerto no se utiliza. Solo se utiliza la autenticación del rotador.

CIFRADO, AUTENTICACIÓN, Y CERTIFICADOS PREDETERMINADOS

ser2net espera certificados y claves públicas predeterminados en /etc/ser2net, y estos se establecen como valores predeterminados de gensio. Esto significa que cualquier conexión saliente desde ser2net, ya sea en un conector o en un connback, utilizará estas claves. Si no están allí o han expirado o algo similar, obtendrá errores confusos sobre no poder abrir los certificados.

Para solucionar esto, puede deshabilitar los certificados agregando "cert=" a la especificación del gensio para ssl y certauth en conexiones salientes. Esto deshabilitará los certificados para el gensio específico, y probablemente sea lo que desea. Si está realizando conexiones y autenticándose en el servidor remoto, es probable que el certificado y la clave privada predeterminados tampoco sean lo que desea.
