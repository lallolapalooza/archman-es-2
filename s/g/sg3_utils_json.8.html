NOMBRE

sg3_utils_json - Salida JSON para algunas utilidades de sg3_utils

SINOPSIS

sg_* --json[=JO] [--js-file=JFN] [OTRAS_OPCIONES] [DISPOSITIVO]

DESCRIPCIÓN

sg3_utils es un paquete de utilidades que envían comandos SCSI al DISPOSITIVO dado a través de una interfaz de paso a través de SCSI proporcionada por el sistema operativo anfitrión. Algunas utilidades, principalmente aquellas que decodifican datos estructurados devueltos por comandos SCSI (por ejemplo, sg_vpd), pueden proporcionar opcionalmente salida JSON, en lugar de salida simple de texto plano. La salida predeterminada sigue siendo texto plano.

JavaScript Object Notation (JSON) es un formato de archivo estándar abierto que se puede utilizar para el intercambio de datos entre programas, incluso a través de una red. Ver https://en.wikipedia.org/wiki/JSON . JSON viene en muchos sabores y este utiliza la implementación C de json-builder que se encuentra en https://github.com/json-parser/json-builder que implementa cuatro tipos de datos JSON simples: cadena, entero, booleano y nulo. Sus otros tipos de datos son objeto JSON y array JSON.

Este proyecto utiliza la convención 'snake_case' para los nombres de objetos JSON: todo en minúsculas o números con palabras individuales unidas con un solo guion bajo (por ejemplo, "starting_lba"). No debe haber caracteres de guion bajo al principio ni al final. La biblioteca json-builder utiliza la licencia SPDX-License-Identifier: BSD-2-Clause, que es la misma licencia que la mayor parte de las utilidades en el paquete sg3_utils.

La biblioteca json-builder es relativamente ligera (700 líneas de código C) y está 'oculta' completamente dentro de la biblioteca sg3_utils para que su interfaz de función y sus tipos de datos no estén disponibles (directamente) para las utilidades del paquete sg3_utils. Es por eso que la interfaz de json-builder (un archivo llamado sg_json_builder.h) está en el directorio lib y no en el directorio include. Tal como se presenta en github, json-builder comparte algunos archivos de encabezado con su compañero json-parser. El autor ha modificado el encabezado de json-builder para incluir lo que se necesita del encabezado de json-parser para que solo se compile el constructor y no el analizador. El analizador podría agregarse más adelante, pero actualmente no parece haber necesidad de él.

La interfaz de usuario para la funcionalidad JSON en el paquete sg3_utils se basa en gran medida en lo que han hecho Christian Franke y otros en smartctl, una utilidad en el paquete smartmontools para obtener información S.M.A.R.T. de discos (y otros dispositivos de almacenamiento).

Esta página man discute las opciones de línea de comandos --json[=JO] y --js-file=JFN. Tenga en cuenta que el argumento para --json es opcional. En su forma más corta, la opción --json puede ser -j o -J (se prefiere la minúscula si aún no está en uso). La forma más corta también puede tomar un argumento, pero un "=" debe preceder al argumento JO sin espacios a ambos lados del "=".

Se ha prestado cierta atención a las comillas en esta página man. Se utilizan comillas dobles alrededor de los nombres de objetos JSON, se utilizan comillas simples para todos los demás propósitos.

VARIABLES DE ENTORNO

La variable de entorno SG3_UTILS_JSON_OPTS permite al usuario anular los valores predeterminados de la configuración JO. Esos ajustes pueden ser anulados nuevamente por la opción de línea de comandos --json[=JO]. Si la cadena asociada con SG3_UTILS_JSON_OPTS no se puede analizar, este mensaje de error se envía a stderr: 'error parsing SG3_UTILS_JSON_OPTS environment variable, ignore'.

OPCIONES

Dado que el argumento de --json[=JO] es opcional, en la forma más corta no puede haber espacios entre la opción y su argumento.

-j[=JO], --json[=JO]
JO es una cadena de cero o más caracteres cuyo orden no es significativo, aparte de los caracteres de negación (se prefiere '-'). El carácter de negación debe aparecer inmediatamente antes de la característica (booleana) que está alternando.
En la forma corta, la letra de opción puede ser distinta de -j si esa letra ya está en uso (se prefiere -J a continuación). Por ejemplo, la utilidad sg_ses usa -j para su operación de 'unir'. Además, dado que el argumento de la opción corta es opcional, no puede haber espacios entre la opción corta, el "=" y JO, si se proporciona. Algunos ejemplos de forma corta: '-jl' solicita salida JSON (sin opción de argumento) y lo que sea que signifique la opción corta '-l' en la utilidad invocada; '-j=h' solicita salida JSON con algunos enteros renderizados adicionalmente como cadenas JSON de hexadecimal.
-J, --js-file=JFN
la salida está en formato JSON y se envía a un archivo llamado JFN. Si ese archivo existe, se trunca. Por defecto, la salida JSON se envía a stdout.
Cuando se proporciona esta opción, la opción --json[=JO] se implica y no es necesario proporcionarla. La opción --json[=JO] aún puede necesitarse para establecer el parámetro JO a valores distintos de los predeterminados.
La opción corta puede ser distinta de -J si esa opción corta ya estaba en uso.

CARACTERES DE CONTROL JSON

Cada cadena JO está compuesta por cero o más de los siguientes caracteres de control JSON.

0
Si se imprime JSON de forma bonita, tabulación a 2 espacios.
2
Si se imprime JSON de forma bonita, tabulación a 2 espacios.
4
Si se imprime JSON de forma bonita, tabulación a 4 espacios.
Esta es la configuración de tabulación predeterminada para imprimir JSON de forma bonita.
8
Si se imprime JSON de forma bonita, tabulación a 8 espacios.
-
carácter de negación. Alterna el sentido (booleano) del siguiente carácter de control.
e
este es un carácter de control booleano para "estado de salida". Si está activo, se coloca un campo "exit_status" al final de la salida JSON. El valor entero de este campo es el valor de estado de salida de Unix que se devuelve al sistema operativo cuando esta utilidad sale. El valor 0 es una buena salida (es decir, no se detectaron errores).
Este carácter de control está activo por defecto (verdadero).
h
este es un carácter de control booleano para 'hexadecimal'. Muchos valores asociados con SCSI se ven mejor (o al menos históricamente) en hexadecimal, mientras que la salida JSON prefiere enteros decimales (que se asume tienen un tamaño máximo de 64 bits, con signo). El tamaño máximo de la mayoría de los campos SCSI es de 64 bits _sin signo_. Además, algunos campos SCSI son máscaras que se ven mejor en hexadecimal. Cuando este carácter de control está activo, la mayoría de los campos (no triviales) que tienen un valor entero reciben en su lugar un subobjeto que contiene al menos un campo "i" con el valor entero y un campo "hex" con el valor hexadecimal correspondiente en una cadena JSON. Esa cadena hexadecimal no tiene decoraciones hexadecimales (es decir, sin prefijo '0x' ni sufijo 'h').
Este carácter de control está desactivado por defecto (falso).
k
este es un carácter de control booleano para un control más fino de la salida JSON que no se imprime de forma bonita. Si el carácter de control 'p' está activado (verdadero), esta opción no tiene efecto.
Si el carácter de control 'p' está desactivado (falso) y este carácter de control está desactivado (falso), entonces la salida JSON de una sola línea contiene algunos espacios para facilitar la lectura. Si el carácter de control 'p' está desactivado (falso) y este carácter de control está activado (verdadero), entonces la salida JSON de una sola línea se 'empaqueta' eliminando todos los espacios innecesarios.
Este carácter de control está desactivado por defecto (falso).
l
este es un carácter de control booleano para controlar si se generan los campos de introducción (lead-in). Los campos de introducción están al principio de la salida JSON e incluyen subobjetos "json_format_version" y "utility_invoked". El subobjeto "utility_invoked" incluye campos de cadena "name", "version_date" y un array JSON llamado "argv" con una entrada por cada argumento de línea de comandos. Si el carácter de control o también está activo, entonces si está disponible, la salida no JSON (es decir, la forma original, 'texto plano') se coloca en un array llamado "plain_text_output" con un elemento por línea de salida 'normal'.

JSON CONTROL CHARACTERS

The following control characters can be added to the --json[=JO] option. They are placed in the JO argument which is a string of characters. Each character controls a specific aspect of the JSON output.

a
this is a boolean control character to place the entire JSON output within a top level JSON object. The name of this object is typically "utility_invoked" (but this can be overridden with the "u" control character). This control character is default on (true).
b
this is a boolean control character to turn off the JSON output. This is primarily for testing the control character mechanism. It is default off (false).
c
this boolean control character controls whether the JSON output is split into multiple lines when multiple commands are given in the one invocation. If this control character is present, the JSON output for each command is preceded by a newline character. It is default off (false).
d
this boolean control character controls whether the T10 "def" field (in T10 sense data) is output. This field is only present in some error conditions. It is default off (false).
e
this boolean control character controls whether T10 "field" information is output. This information is associated with T10 sense data and is usually presented as a list of "field" objects. It is default off (false).
f
this boolean control character controls whether the JSON output includes an "exit_status" integer field. This field mirrors the numeric exit status of the utility. It is default on (true).
g
this boolean control character controls whether the SCSI command data (i.e. the CDB) is output. The CDB is placed in a JSON string named "cdb_as_hex". It is default off (false).
h
this boolean control character controls whether the T10 sense data is output. The sense data is placed in a JSON object named "sense_data". It is default on (true).
i
this boolean control character controls whether the JSON output is 'pretty printed' (see 'p' control character) or sent in a relatively compact stream suitable for more efficient transmission over a communications channel. This is the inverse of the 'p' control character. It is default off (false).
k
this boolean control character controls whether the JSON output is 'pretty printed' or sent in a relatively compact stream suitable for more efficient transmission over a communications channel. This is the inverse of the 'p' control character. It is default off (false).
l
this boolean control character controls whether normal (i.e. non-JSON) lines of output are placed in a JSON array within the utility_invoked subject. The name of the array is "plain_text_output". This control character is active even if the lead-in fields control character (o) is negated. It is default on (true).
m
this boolean control character controls whether the 'meaning' field (in T10 sense data) is output. It is default on (true).
n
this is a boolean control character for "name_extra". It is used to provide additional information about the name it is a sub-object of. The most common usage is to spell out an abbreviated name (e.g. a T10 name like 'SKSV' to 'Sense Key Specific Valid'). Another use is to note that a T10 field is obsolete and in which T10 standard it first became obsolete. Also if the named field's value is a physical quantity where the unit is unclear (e.g. a timeout) then "name_extra" can state that (e.g. 'unit: millisecond'). Only some fields have associated "name_extra" data.
This boolean control character is default off (false).
o
this is a boolean control character to control whether normal (i.e. non-JSON) lines of output are placed in a JSON array (one element per line of normal output) within the utility_invoked subject (see control character l). The name of the array is "plain_text_output". This control character is active even if the lead-in fields control character (l) is negated.
This boolean control character is default off (false).
p
this boolean control character controls whether the JSON output is 'pretty printed' or sent in a relatively compact stream suitable for more efficient transmission over a communications channel.
The pretty printed form of output has one JSON name with its associated integer, string or boolean value per line; and one array element per line. JSON objects and arrays that have an associated JSON object as their value, have their name on a separate line. These lines are indented with the current tab setting to indicate the level of nesting. Basically the pretty printed form is for human consumption.
There are two forms of non-pretty printed output, see the 'packed' control character ['k'].
This boolean control character is default on (true).
s
this boolean control character controls whether T10 field values that have a defined meaning are broken out with an added JSON sub-object usually named "meaning". When active the field name has a sub-object that contains at least an "i" field with the integer value of the field and a JSON string object, usually named "meaning", with a string that corresponds to the T10 defined meaning of the value in the "i" field.
This boolean control character is default on (true).
v
this is an integer control character that controls the amount of debug output. It can be given multiple times to increase the level of JSON debug verbosity in the output.
Note that this verbose control character is JSON specific while the --verbose option (short form: fI-v often repeated: fI-vvv) that most utilities support is more general.
This integer control character is set to 0 by default.

OUTPUT PROCESSING

The default remains the same for all utilities that support the --json option, namely the decoded information is sent to stdout in plain text form. Errors are reported to stderr and may cause the early termination of a utility (e.g. command line option syntax error).

When the --json option is given and no errors are detected, then only JSON is normally sent to stdout. As the SCSI response is parsed, a JSON representation is built as a tree in memory. After all other actions (perhaps apart from the final exit status report) that JSON tree is 'dumped' to stdout. This means if there is any non-JSON output sent to stdout that it will appear _before_ the JSON output.

If the 'o' control character is in the JO argument to the --json option, then the former plain text output is placed in a JSON array named "plain_text_output" within a JSON object named "utility_invoked".
Each line of the former 'plain text' output is placed in its own element of the JSON array.

A JSON tree is built in memory as the utility parses the data returned from the SCSI device (e.g. sg_vpd parsing a VPD page returned from a SCSI INQUIRY command). SCSI 'list's become JSON named arrays (e.g. in the Device Identification VPD page there is a 'Designation descriptor list' that becomes a JSON array named "designation_descriptor_list").

At the completion of the utility that JSON tree is 'measured' taking into account the form of output (i.e. pretty-printed, single line or packed single line). For the pretty-printed JSON output, the size of each indentation in spaces is also given (i.e. the tab width). The JSON is then output to a single C string, then sent to stdout. If a NULL character (ASCII zero and C string terminator) somehow finds its way into a field that should (according to the spec) be space padded, then the JSON output may appear truncated.

Note that this JSON processing means that if a utility is aborted for whatever reason then no JSON output will appear. With the normal, plain text output processing, some output may appear before the utility aborts in such bad situations.

BOOLEAN OR 0/1

In general, the JSON generated by this package outputs 1 bit SCSI fields as the integer value 0 (for false) and 1 (for true). This follows the SCSI convention which predates the common use of boolean. Also SCSI reserved fields are output as the integer value 0. Extensions to SCSI commands and associated data descriptors typically use parts of commands or data descriptors that were previously reserved.

INTERACTION WITH OTHER OPTIONS

As stated above, the default output is in plain text form using 7 bit ASCII. The --json[=JO] option is designed to be an alternative to that plain text form. There are other alternative output formats such as the response output as a hexadecimal sequence of bytes or in 'raw' binary output; both of those take precedence over the --json[=JO] option. Other specialized output format (e.g. 'sg_inq --export') will usually take precedence over JSON output.

When the --raw option is used together with the --inhex=FN option only the data input to the utility is interpreted as binary. So the output format defaults to plain text form and thus can be changed to JSON if the --json[=JO] option is also used.

There is typically only one form of JSON output so options like --brief and --quiet are ignored in the JSON output. In some cases (i.e 'sg_inq --descriptors') the JSON output is expanded.

ERRORS

No attempts have been made to translate errors into JSON form, apart from the final "exit_status" JSON object where a value of 0 means 'no errors'. Exit status values indicating a problem range from 1 to 255.

The sg_decode_sense utility will parse SCSI sense data into JSON form if requested. So if another utility is failing with a sense data report (most often seen when the --verbose option is used). That sense data (in hex bytes) could be cut-and-pasted onto the command line following 'sg_decode_sense -j ' which should then render that sense data in JSON.

Otherwise, when a error is detected while JSON output is selected, the error message is sent to stderr in plain text form. Typically once an error is detected the utility will exit, first dumping the JSON in-memory tree as discussed above and a non-zero exit status will be set. The JSON output will be well formed but missing any fields or list elements following the point that the error was detected.

The summary is that when JSON output is selected and an error occurs each utility will process the error the same way as it would if JSON output had not been selected. In most cases error messages, in plain text form, are sent to stderr.
