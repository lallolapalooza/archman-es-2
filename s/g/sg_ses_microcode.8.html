NOMBRE

sg_ses_microcode - enviar microcódigo a una enclosure SCSI

SINOPSIS

sg_ses_microcode [--bpw=CS] [--dry-run] [--ealsd] [--help] [--id=ID] [--in=ARCHIVO] [--length=LEN] [--mode=MO] [--non] [--offset=OFF] [--skip=SKIP] [--subenc=MS] [--tlength=TLEN] [--verbose] [--version] DISPOSITIVO

DESCRIPCIÓN

Esta utilidad intenta descargar microcódigo a una enclosure (o a una de sus sub-enclosures) asociada con el DISPOSITIVO. El proceso para hacer esto está definido en los estándares y borradores de SCSI Enclosure Services (SES) mantenidos por el comité T10.

El proceso consiste en enviar una o más secuencias que contienen un comando SCSI SEND DIAGNOSTIC seguido opcionalmente por un comando RECEIVE DIAGNOSTIC RESULTS. El primero envía una página de diagnóstico de control de descarga de microcódigo (dpage) y el segundo recupera una página de estado de descarga de microcódigo que puede ser vista como un informe del comando anterior.

La acción por defecto (es decir, cuando la opción --mode=MO no se proporciona) es recuperar la página de estado de descarga de microcódigo y decodificarla. Esto no requiere el microcódigo (firmware) en sí, por lo que la opción --in=ARCHIVO no es necesaria.

La referencia más reciente para esta utilidad es el borrador del documento SCSI Enclosure Services 3 (SES-3) T10/2149-D Revisión 7 en http://www.t10.org . Los estándares existentes para SES y SES-2 son ANSI INCITS 305-1998 y ANSI INCITS 448-2008 respectivamente.

La mayor parte del soporte para SES en este paquete (aparte de la descarga de microcódigo) se encuentra en la utilidad sg_ses. Otra forma de descargar firmware a un dispositivo SCSI es con el comando WRITE BUFFER definido en SPC-4, vea la utilidad sg_write_buffer.

OPCIONES

Los argumentos a las opciones largas son obligatorios también para las opciones cortas.

-b, --bpw=CS
donde CS es el tamaño del fragmento en bytes y debe ser un múltiplo de 4. Este será el número máximo de bytes enviados por comando SEND DIAGNOSTIC. Por lo tanto, si CS es menor que la longitud efectiva del microcódigo, se envían múltiples comandos SEND DIAGNOSTIC, cada uno tomando el siguiente fragmento de los datos leídos y aumentando el campo de desplazamiento del búfer en la dpage de control de descarga de microcódigo por la cantidad apropiada. El valor por defecto es un tamaño de fragmento de 0, que se interpreta como un número muy grande, por lo que solo se enviará un comando SEND DIAGNOSTIC.
El número en CS puede ir seguido opcionalmente por ",act" o ",activate". En este caso, después de que el microcódigo se haya enviado con éxito al DISPOSITIVO, se envía una dpage de control de descarga de microcódigo adicional con su modo establecido en "Activate deferred microcode" [0xf].
-d, --dry-run
las llamadas reales para realizar los comandos SEND DIAGNOSTIC y RECEIVE DIAGNOSTIC RESULTS se omiten cuando se proporciona esta opción. No se envían comandos SCSI al DISPOSITIVO, pero aún se abre y se requiere que se proporcione. Se puede usar un dispositivo ficticio como /dev/null (en Unix).
Esta utilidad espera una respuesta "sensata" al comando RECEIVE DIAGNOSTIC RESULTS que envía (y abortará si no recibe una). Por lo tanto, esta opción proporciona respuestas ficticias con una enclosure primaria y tres sub-enclosures. Las respuestas ficticias incluyen valores de estado buenos.
-e, --ealsd
salir después del último comando SEND DIAGNOSTIC. Un dispositivo SES no debería iniciar su actualización de firmware inmediatamente después del último fragmento recibido de su firmware. Más bien, debería esperar hasta que se envíe al menos un comando RECEIVE DIAGNOSTIC RESULTS para dar al dispositivo la oportunidad de informar cualquier error. Sin embargo, algunos dispositivos inician la actualización de firmware inmediatamente, lo que provoca que el comando RECEIVE DIAGNOSTIC RESULTS de seguimiento se mantenga pendiente y a menudo se aborte con un error de "reset de destino".
Esta opción hace que se omita el comando RECEIVE DIAGNOSTIC RESULTS de seguimiento. Esta opción se usaría típicamente con la opción --bpw=CS.
Antes de la versión 1.10 de esta utilidad [20180112], esta acción (es decir, omitir el último comando RECEIVE DIAGNOSTIC RESULTS) era la acción por defecto.
-h, --help
mostrar el mensaje de uso y luego salir. Si se usa varias veces, también imprime los nombres de los modos y sus acrónimos.
-i, --id=ID
esta opción establece el campo BUFFER ID en la dpage de control de descarga de microcódigo. ID es un valor entre 0 (por defecto) y 255 inclusive.
-I, --in=ARCHIVO
leer datos del archivo ARCHIVO que se enviarán con el comando SEND DIAGNOSTIC. Si ARCHIVO es '-' entonces se lee stdin hasta que se detecta un EOF (esta es la misma acción que --raw). Los datos se leen desde el principio de ARCHIVO, excepto en el caso en que sea un archivo regular y se proporcione la opción --skip=SKIP.
-l, --length=LEN
donde LEN es la longitud, en bytes, de los datos a escribir en el dispositivo. Si no se proporciona (y la longitud no puede deducirse de --in=ARCHIVO o --raw), entonces por defecto es cero. Si se proporciona la opción y la longitud deducida de --in=ARCHIVO o --raw es menor (o no se proporcionan datos), entonces se utilizan bytes de 0xff como bytes de relleno.
-m, --mode=MO
esta opción establece el MODO. MO es un valor entre 0 (que es dmc_status y el valor por defecto) y 255 inclusive. Alternativamente, se puede proporcionar una abreviatura. Consulte la sección MODOS a continuación. Para listar las abreviaturas de modo disponibles en tiempo de ejecución, proporcione una inválida (por ejemplo, '--mode=xxx') o use la opción '-h'.
-N, --non
permite implementaciones no estándar que reinician su motor de descarga de microcódigo después de enviar un comando RECEIVE DIAGNOSTIC RESULTS con la dpage de estado de descarga de microcódigo. Cuando se proporciona esta opción, se evita enviar esa combinación de comando y dpage a menos que ya haya ocurrido un error.
-o, --offset=OFF
esta opción establece el campo BUFFER OFFSET en la dpage de control de descarga de microcódigo. OFF es un valor entre 0 (por defecto) y 2**32-1. Es un desplazamiento en bytes. Esta opción se ignora (y se envía una advertencia a stderr) si también se proporciona la opción --bpw=CS.
-s, --skip=SKIP
esta opción solo está activa cuando se proporciona --in=ARCHIVO y ARCHIVO es un archivo regular, en lugar de stdin. Los datos se leen comenzando en el desplazamiento de bytes SKIP hasta el final del archivo (o la cantidad dada por --length=LEN). Si no se proporciona, el desplazamiento de bytes por defecto es 0 (es decir, el inicio del archivo).
-S, --subenc=SEID
SEID es el identificador de la sub-enclosure. Por defecto es 0, que es el identificador de la enclosure primaria.
-t, --tlength=TLEN
TLEN es la longitud total en bytes del microcódigo que se va a (o está siendo) descargar. Por defecto es 0, lo cual está bien en la mayoría de los casos. Esta opción solo entra en juego cuando TLEN es mayor que LEN. En este caso, TLEN se envía al DISPOSITIVO SES para que sepa que cuando solo recibe LEN bytes de esta invocación, debe esperar más por enviar en el futuro cercano (por ejemplo, mediante otra invocación). Esta opción solo es necesaria cuando se envían secciones de microcódigo en invocaciones separadas de esta utilidad (por ejemplo, el microcódigo está distribuido en dos archivos).
-v, --verbose
aumentar el nivel de verbosidad (es decir, salida de depuración).
-V, --version
imprimir la cadena de versión y luego salir.

MODOS

A continuación se muestra una lista aceptada por el argumento MO de esta utilidad. Primero se muestra un acrónimo seguido entre corchetes por los valores decimales y hexadecimales correspondientes que también se pueden dar para MO.

dmc_status [0, 0x0]

Realiza una lectura de la página de estado de descarga de microcódigo.

La salida se presenta en un formato similar a la tabla siguiente (los valores reales varían):

    Page Code: 0x00  (Download microcode status)
    Sub-enclosure ID: 0
    Num active IAs: 3
    Busy: No
    Sequence error: No
    Unsupported function: No
    Reset required: No
    Deferred reset: No
    Microcode not loaded: No
    Microcode load failed: No
    Invalid header offset: No
    Invalid segment offset: No
    Invalid segment length: No
    Insufficient buffer: No
    Microcode deactivated: No
    Microcode already loaded: No
    Microcode update aborted: No
    Microcode update completed: Yes
    Microcode not verified: No
    Microcode update aborted (unknown): No
    Microcode update not performed: Yes
    Current firmware version: 0x1234abcd
    Microcode sequence: 0x5
    Buffer offset: 0
    Buffer length: 0
    Total length: 0
    ...

Nota: los campos de firmware y secuencia de microcódigo pueden no ser siempre precisos ya que algunos firmware no los soportan. El campo "Microcode update aborted (unknown)" es un campo de error genérico y si se establece (a 1) entonces se asume que un error ha ocurrido. Si el campo "Microcode update aborted" (o el "unknown" anterior) está a 1, o si "Microcode load failed" está a 1, entonces se considera que se ha producido un error. Si el campo "Microcode update completed" está a 1, se considera que ha tenido éxito.

dmc_control [1, 0x1]

Envia una dpage de control de descarga de microcódigo. Se requiere la opción --in=ARCHIVO. La dpage tiene un campo de control (el primer byte) que toma un valor de 0 a 15 (0xf). El valor por defecto es 0 (sin acción)

Los valores de control más comunes son:

0x0
Sin acción. Útil para obtener la longitud total de la imagen de firmware.
0x1
Descargar datos de microcódigo.
0x2
Cargar microcódigo (normalmente se hace después de descargar con 0x1).
0x3
Borrar microcódigo.
0x4
Establecer el registro de firmware.
0x5
Descargar y cargar microcódigo.
0xf
Activar microcódigo diferido.

Esta opción también puede enviar un comando RECEIVE DIAGNOSTIC RESULTS para obtener el estado y lo imprime. Ver la descripción de 'dmc_status' para el formato de salida.

Si el usuario proporciona --bpw=CS, entonces esta utilidad enviará múltiples comandos SEND DIAGNOSTIC (cada uno con un tamaño de fragmento) si el contenido de ARCHIVO es mayor que CS. Después de que todos los fragmentos hayan sido enviados, un comando final RECEIVE DIAGNOSTIC RESULTS se ejecuta para obtener el estado.

dmc_read_buffer [2, 0x2]

Lee el búfer de microcódigo. Por defecto, lee desde el principio del búfer hasta el final. Se pueden usar las opciones --offset y --length para leer partes específicas del búfer.

dmc_write_buffer [3, 0x3]

Escribe en el búfer de microcódigo. Se requiere la opción --in=ARCHIVO. La escritura se realiza a partir de la posición dada por --offset y con la longitud dada por --length. Si --length no se proporciona, se utiliza la longitud de los datos en ARCHIVO.

EJEMPLOS

Para descargar el archivo firmware 'my_firmware.bin' a la enclosure SCSI dev/sg0:

  sg_ses_microcode --in=my_firmware.bin /dev/sg0

Para descargar el archivo firmware 'my_firmware.bin' en fragmentos de 1024 bytes a la enclosure SCSI dev/sg0 y luego activar el firmware:

  sg_ses_microcode --in=my_firmware.bin --bpw=1024,activate /dev/sg0

Para consultar el estado de descarga de microcódigo de la enclosure SCSI dev/sg1 (sin enviar ningún firmware):

  sg_ses_microcode /dev/sg1

Para obtener la longitud del firmware almacenado en la enclosure SCSI dev/sg2 y luego imprimir el estado:

  sg_ses_microcode --mode=dmc_control --length=0 /dev/sg2

Para descargar el firmware desde stdin en un dispositivo que no reinicia su motor de descarga después de un comando de estado:

  cat my_firmware.bin | sg_ses_microcode --in=- --non /dev/sg0

ERRORES

El código de salida es 0 en caso de éxito, y diferente de 0 en caso de error.

MODES

mc_status [0, 0x0]
Use RECEIVE DIAGNOSTIC RESULTS para obtener la página de datos del estado de descarga de microcódigo y mostrarla.
dmc_offs [6, 0x6]
Descargar microcódigo con offsets y activar.
dmc_offs_save [7, 0x7]
Descargar microcódigo con offsets, guardar y activar.
dmc_offs_defer [14, 0xe]
Descargar microcódigo con offsets, guardar y posponer la activación.
activate_mc [15, 0xf]
Activar microcódigo diferido. No hay un RECEIVE DIAGNOSTIC RESULTS de seguimiento para obtener la página de datos del estado de descarga de microcódigo ya que el DEVICE podría estar reiniciándose.

Aparte de dmc_status, estos se colocan en el campo de modo de descarga de microcódigo en la página de datos de control de descarga de microcódigo. En el caso de dmc_status, la página de datos del estado de descarga de microcódigo se obtiene con el comando RECEIVE DIAGNOSTIC RESULTS y se decodifica.

CUANDO FALLA LA DESCARGA

En primer lugar, si tiene éxito, esta utilidad debería permanecer en silencio y regresar. Típicamente los vendedores cambiarán la cadena de "revisión" (que tiene 4 caracteres de largo) cada vez que lancen nuevo firmware. Eso se puede ver en la respuesta a un comando SCSI INQUIRY, por ejemplo, usando la utilidad sg_inq. Es posible que el dispositivo deba ser encendido/apagado (power cycled) antes de que el nuevo microcódigo se active. También si se usa el modo dmc_offs_defer [0xe] para descargar el microcódigo, entonces puede ser necesaria otra invocación con activate_mc.

Si algo sale mal, típicamente habrá mensajes impresos por esta utilidad. Lo primero a comprobar es el archivo de microcódigo (firmware) en sí. ¿Está diseñado para el modelo de dispositivo? ¿Ha sido corrompido? y si se está degradando (es decir, intentando reinstalar firmware antiguo), ¿lo permite el vendedor?

Obtener nuevo firmware en un dispositivo es una operación delicada que no siempre está bien definida por los estándares y borradores de T10. Uno podría especular que son deliberadamente vagos. Al probar esta utilidad, la interpretación de un vendedor del estándar fue algo sorprendente. La opción --non se agregó para hacer frente a su interpretación. Así que, si las sugerencias anteriores no ayudan, intente agregar la opción --non.

NOTAS

Esta utilidad puede manejar un tamaño máximo de 128 MB de microcódigo, lo que debería ser suficiente para la mayoría de los propósitos. En un sistema con memoria restringida, asignaciones de memoria tan grandes pueden fallar.

El usuario debe ser consciente de que la mayoría de los sistemas operativos tienen límites en la cantidad de datos que se pueden enviar con un comando SCSI. En Linux esto depende del mecanismo de traspaso utilizado (por ejemplo, SG_IO de bloque o el controlador sg) y varias configuraciones en sysfs en la serie Linux lk 2.6/3 (por ejemplo, /sys/block/sda/queue/max_sectors_kb). Los dispositivos (es decir, unidades lógicas) también suelen tener límites en la cantidad máxima de datos que pueden manejar en un comando. Estas dos limitaciones sugieren que los modos que contienen la palabra "offset" junto con la opción --bpw=CS son necesarios a medida que los archivos de firmware se hacen cada vez más grandes. Y CS puede ser bastante pequeño, por ejemplo, 4096 bytes, lo que resulta en el envío de muchos comandos SEND DIAGNOSTIC.

El error exacto de la implementación no estándar fue una clave de sentido ILLEGAL REQUEST y un código asc/ascq de 0x26,0x0, que es "Campo inválido en la lista de parámetros". Si eso se ve, intente de nuevo con la opción --non.

La descarga de microcódigo incorrecto en un dispositivo tiene la capacidad de dejar ese dispositivo inutilizable. Uno esperaría que el vendedor del dispositivo verifique los datos antes de activarlos.

Se establece un tiempo de espera largo (del sistema operativo) de 7200 segundos en cada comando SEND DIAGNOSTIC.

Se asume que todos los números dados con opciones están en decimal. Alternativamente, los valores numéricos se pueden dar en hexadecimal precedidos por "0x" o "0X" (o tienen un sufijo "h" o "H").

EJEMPLOS

Si no se proporciona ningún archivo de microcódigo/firmware, esta utilidad obtiene y decodifica la página de datos del estado de descarga de microcódigo, que posiblemente podría mostrar a otro iniciador en el proceso de actualización del microcódigo. Incluso si eso está sucediendo, obtener la página de estado no debería causar ningún problema:


$ sg_ses_microcode /dev/sg3
Download microcode status diagnostic page:
number of secondary sub-enclosures: 0
generation code: 0x0
sub-enclosure identifier: 0 [primary]
download microcode status: No download microcode operation in progress [0x0]
download microcode additional status: 0x0
download microcode maximum size: 1048576 bytes
download microcode expected buffer id: 0x0
download microcode expected buffer id offset: 0

Lo siguiente envía un nuevo microcódigo/firmware a una carcasa. El envío de un archivo de 1.5 MB en un solo comando hizo que la carcasa se bloqueara temporalmente y no actualizó el firmware. Dividir el archivo de firmware en fragmentos de 4 KB (una suposición educada) tuvo más éxito:


sg_ses_microcode -b 4k -m dmc_offs_save -I firmware.bin /dev/sg4

La actualización del firmware ocurrió en el siguiente ciclo de encendido/apagado de la carcasa. Con una carcasa moderna, la página de consulta extendida (Extended Inquiry VPD page) da indicaciones en qué situaciones se realizará una actualización de firmware.

ESTADO DE SALIDA

El estado de salida de sg_ses_microcode es 0 cuando tiene éxito. De lo contrario, consulte la página del manual sg3_utils(8).
