SPFD(1) Documentación de Perl contribuida por el usuario SPFD(1)

NOMBRE

spfd - (Mail::SPF) - Demonio simple de bifurcación para proporcionar servicios de consulta SPF

VERSIÓN

versión 3.20250505

SINOPSIS

spfd --port|-p puerto [--set-user|-u uid|nombre de usuario] [--set-group|-g gid|nombre de grupo] [OPCIONES]

spfd --socket|-s nombre de archivo [--socket-user uid|nombre de usuario] [--socket-group gid|nombre de grupo] [--socket-perms permisos octales] [--set-user|-u uid|nombre de usuario] [--set-group|-g gid|nombre de grupo] [OPCIONES]

spfd --version|-V

spfd --help

DESCRIPCIÓN

spfd es un servidor de consulta simple de Sender Policy Framework (SPF) mediante bifurcación. spfd recibe y responde a las solicitudes SPF en un socket de dominio TCP/IP o UNIX. Para más información sobre SPF, consulte https://tools.ietf.org/html/rfc7208.

La forma --port escucha en un socket TCP/IP en el puerto especificado. El puerto por defecto es 5970.

La forma --socket escucha en un socket de dominio UNIX que se crea con el nombre de archivo especificado. El socket puede tener asignada una propiedad de usuario y grupo específica con las opciones --socket-user y --socket-group, y permisos de sistema de archivos específicos con la opción --socket-perms.

Generalmente, se puede instruir a spfd con las opciones --set-user y --set-group para que renuncie a los privilegios de root y cambie a otro usuario y grupo antes de comenzar a escuchar las solicitudes.

La forma --version imprime información de la versión de spfd. La forma --help imprime información de uso para spfd.

OPCIONES

spfd acepta cualquiera de las siguientes OPCIONES:

--default-explanation cadena
--def-exp cadena
Utiliza la cadena especificada como explicación por defecto si el dominio de autoridad no especifica su propia cadena de explicación.
--hostname nombre de host
Utiliza nombre de host como nombre del sistema local en lugar de detectarlo automáticamente.
--debug
Imprime información de depuración sobre la operación de spfd, las solicitudes entrantes y las respuestas enviadas.

SOLICITUD

Una solicitud consiste en una serie de líneas delimitadas por caracteres \x0A (LF) (o lo que sea que su sistema considere un salto de línea). Cada línea debe tener el formato opción=valor, donde las siguientes opciones son compatibles:

versions
Una lista separada por comas de los números de versión SPF de los registros SPF que se pueden utilizar. 1 significa que se deben utilizar los registros "v=spf1". 2 significa que se deben utilizar los registros "spf2.0". Por defecto es 1,2, es decir, utiliza cualquier registro SPF disponible. Se prefieren los registros de versión superior.
scope
El ámbito de autorización de la identidad que debe comprobarse. Por defecto es 'mfrom'. Los siguientes valores de ámbito son compatibles: 'helo', 'mfrom', 'pra'. Consulte "new" en Mail::SPF::Request para más información.
identity
Requerido. La identidad del remitente cuya autorización debe comprobarse. Es un nombre de dominio para el ámbito "helo", y una dirección de correo electrónico para los ámbitos "mfrom" y "pra".
ip_address
Requerido para comprobaciones con los ámbitos "helo", "mfrom" y "pra". La dirección IP del host que reclama la identidad que se está comprobando. Puede ser una dirección IPv4 o IPv6. Una dirección IPv6 mapeada a IPv4 (por ejemplo, '::ffff:192.168.0.1') se trata como una dirección IPv4.
helo_identity
El parámetro de la transacción SMTP "HELO" en el caso de que la identidad principal sea de un ámbito distinto de "helo". Esta identidad se utiliza entonces simplemente para la expansión de macros "%{h}" durante la evaluación de la política de la identidad principal. Si no se especifica con un ámbito distinto de "helo", por defecto es "unknown". Si la identidad principal es del ámbito "helo", esta opción no se utiliza.

RESPUESTA

spfd responde a las solicitudes SPF con una serie similar de líneas con el formato clave=valor. Las claves de respuesta más importantes son:

result
El código de resultado de la comprobación SPF:
pass
La dirección IP especificada es un remitente SMTP autorizado para la identidad.
fail
La dirección IP especificada no es un remitente SMTP autorizado para la identidad.
softfail
La dirección IP especificada no es un remitente SMTP autorizado para la identidad, sin embargo, el dominio de autoridad todavía está probando su política SPF.
neutral
El dominio de autoridad de la identidad no hace ninguna afirmación sobre el estado de la dirección IP.
permerror
Se produjo un error permanente al evaluar la política del dominio de autoridad (por ejemplo, un error de sintaxis en el registro SPF). Se requiere intervención manual por parte del dominio de autoridad.
temperror
Se produjo un error temporal al evaluar la política del dominio de autoridad (por ejemplo, un error de DNS). Vuelva a intentarlo más tarde.
none
No existe una política SPF aplicable para el dominio de la identidad.
local_explanation
Una explicación generada localmente del resultado SPF.
authority_explanation
La explicación del dominio de autoridad para el resultado SPF. Tenga en cuenta que el dominio de autoridad puede ser una parte maliciosa y, por lo tanto, la explicación de la autoridad no debe ser confiada ciegamente. Consulte RFC 4408, 10.5, para una discusión detallada de este problema.
received_spf_header
Un campo de encabezado "Received-SPF" apropiado para el resultado SPF.
spf_record
El registro SPF del dominio de autoridad que se utilizó para la evaluación de la política.

EJEMPLO

Un spfd en ejecución podría probarse utilizando la utilidad "netcat" de la siguiente manera (se añadieron saltos de línea para mayor claridad):

$ echo -e "identity=user@example.com\nip_address=1.2.3.4\n" \
    | nc localhost 5970
result=fail
local_explanation=example.com: Sender is not authorized by default to use
    'user@example.com' in 'mfrom' identity (mechanism '-all' matched)
authority_explanation=Rejected by SPF record.
received_spf_header=Received-SPF: fail (example.com: Sender is not
    authorized by default to use 'user@example.com' in 'mfrom' identity
    (mechanism '-all' matched)) receiver=localhost; identity=mfrom;
    env

spfd(1p) — Arch manual pages

NAME

spfd — SPF verification daemon

VERSION

This manual page describes spfd version 2.000.

SYNOPSIS

  spfd [options]

DESCRIPTION

spfd is a daemon that performs SPF checks on behalf of other applications, typically mail transfer agents (MTAs). It listens on a network socket for incoming SPF check requests, performs the requested check, and returns the result.

The daemon is configured via command-line options. Some options can also be specified in a configuration file.

OPTIONS

The following options are available:

-a, --address address
Specifies the local address and port on which to listen for incoming connections. If only a port is specified, it defaults to listening on all network interfaces. Example: -a 127.0.0.1:54321 or -a :54321.
-c, --config file
Specifies a configuration file that may contain additional configuration directives. See spfd.conf(5) for details.
-d, --daemonize
Causes spfd to fork into the background and become a daemon.
-f, --foreground
Run spfd in the foreground. This is the default behavior.
-h, --help
Display a help message and exit.
-l, --listen type
Specifies the type of listener to use. Currently, only "inet" (for TCP/IP sockets) is supported. This is the default.
-p, --pidfile file
Specifies a file in which to write the process ID (PID) of the daemon when running in the background. This is useful for later stopping the daemon.
-P, --privileged
Drop privileges to the user and group specified in the configuration file after opening the listening socket. This is the default behavior.
-u, --unprivileged
Do not drop privileges. This is useful for testing or when spfd is run as a non-root user.
-v, --version
Display version information and exit.

REQUEST

Requests are sent to spfd as simple text lines over a TCP connection. Each request consists of key-value pairs separated by spaces. Valid keys are:

identity
The identity to check. This is typically an email address for the "MAIL FROM" SMTP identity.
scope
The scope of the identity. Can be "mfrom" (MAIL FROM), "helo" (HELO/EHLO identity), or "rcpt" (RCPT TO identity).
ip_address
The IP address of the connecting host.
helo_identity
The HELO or EHLO identity presented by the connecting host.

All keys are mandatory except for "scope", which defaults to "mfrom".

RESPONSE

Responses are sent back to the client as simple text lines, containing key-value pairs. The primary key is:

result
The result of the SPF check. Possible values are:
  • pass
  • fail
  • softfail
  • neutral
  • temperror (temporary error during check)
  • permerror (permanent error in SPF record)
  • none (no SPF record found)

Other keys may include:

local_explanation
A local explanation string.
authority_explanation
An explanation string from the authority (i.e., the SPF record itself).
spf_record
The SPF record that was checked.
received_spf_header
The value that should be added to the Received-SPF header.

EXAMPLE

A client might send the following request to spfd:

identity=user@example.com client-ip=1.2.3.4

And receive a response like:

result=pass spf_record=v=spf1 mx -all

COMPATIBILITY

spfd has undergone the following interface changes compared to earlier versions:

2.000
  • A new preferred request style has been introduced. Instead of the old "sender" request option, which is specific to the "MAIL FROM" SMTP identity, a generic "identity" option should now be specified. In addition, a "scope" option may be given to specify the identity's scope, otherwise a scope of "mfrom" is assumed. The old "ip" and "helo" options have been replaced by the "ip_address" and "helo_identity" options, respectively.

    This is how legacy requests with the "mfrom" scope would translate to the new preferred request style:

     Legacy request style       | New request style
----------------------------+---------------------------------------
                            | scope=mfrom
 sender=<mfrom-identity>    | identity=<mfrom-identity>
 ip=<ip-address>            | ip_address=<ip-address>
 helo=<helo-identity>       | helo_identity=<helo-identity>

    A new response style featuring new response values has also been introduced:

     Legacy response style      | New response style
----------------------------+---------------------------------------
 result=<result-code>       | result=<result-code>
 header_comment=<local-exp> | local_explanation=<local-exp>
 smtp_comment=<local-exp    | authority_explanation=<authority-exp>
   or authority-exp>        | 
 spf_record=<spf-record>    | spf_record=<spf-record>
                            | received_spf_header=<header>

    The legacy request style is deprecated but still supported for backwards compatibility. The legacy response values are still returned for backwards compatibility in addition to the new response values, but may be removed in the future. Adjust your code to use the new request and response styles.

  • The former "unknown" and "error" result codes have been renamed to "permerror" and "temperror", respectively, in order to comply with RFC 4408 terminology.
  • In the case of an empty "MAIL FROM" SMTP transaction parameter ("MAIL FROM:<>"), the identity checked will be postmaster@helo name as specified in RFC 7208.

SEE ALSO

Mail::SPF, spfquery(1)

http://tools.ietf.org/html/rfc4408
