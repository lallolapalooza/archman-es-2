NOMBRE

SPANK - Arquitectura de Plug-ins de Slurm para Control de Nodo y Tarea (K)ontrol

DESCRIPCIÓN

Este manual describe brevemente las capacidades de la Arquitectura de Plug-ins de Slurm para Control de Nodo y Tarea (SPANK) así como el archivo de configuración de SPANK: (Por defecto: plugstack.conf).

SPANK proporciona una interfaz muy genérica para plug-ins apilables que pueden ser usados para modificar dinámicamente el código de lanzamiento de tareas en Slurm. Los plug-ins de SPANK pueden ser construidos sin acceso al código fuente de Slurm. Solo necesitan ser compilados contra el archivo de cabecera spank.h de Slurm, añadidos al archivo de configuración de SPANK plugstack.conf, y serán cargados en tiempo de ejecución durante el próximo lanzamiento de tarea. Por lo tanto, la infraestructura de SPANK proporciona a los administradores y otros desarrolladores una habilidad de bajo costo y bajo esfuerzo para modificar dinámicamente el comportamiento en tiempo de ejecución del lanzamiento de tareas de Slurm.

NOTA: Todos los plug-ins de SPANK deben ser recompilados al actualizar Slurm a una nueva versión mayor. La API de SPANK no está garantizada para ser compatible a nivel de ABI entre versiones mayores. Cualquier plug-in de SPANK que enlace con alguna de las librerías de Slurm debe ser cuidadosamente revisado ya que las APIs y cabeceras de Slurm pueden cambiar entre versiones mayores.

PLUGINS DE SPANK

Los plug-ins de SPANK son cargados en hasta cinco contextos separados durante una tarea de Slurm. Brevemente, los cinco contextos son:

local
En contexto local, el plug-in es cargado por srun. (es decir, la parte "local" de una tarea paralela).
remoto
En contexto remoto, el plug-in es cargado por slurmstepd. (es decir, la parte "remota" de una tarea paralela).
allocator
En contexto allocator, el plug-in es cargado en una de las utilidades de asignación de tareas salloc, sbatch o scrontab.
slurmd
En contexto slurmd, el plug-in es cargado en el propio demonio slurmd. NOTA: Los plug-ins cargados en el contexto slurmd persisten durante todo el tiempo que slurmd esté en ejecución, por lo que si la configuración cambia o los plug-ins se actualizan, slurmd debe ser reiniciado para que los cambios surtan efecto.
job_script
En el contexto job_script, los plug-ins se cargan en el contexto del prólogo o epílogo de la tarea. NOTA: Los plug-ins se cargan en el contexto job_script en cada ejecución del prólogo o epílogo de la tarea, en un espacio de direcciones separado de los plug-ins en el contexto slurmd. Esto significa que no hay estado compartido entre este contexto y otros contextos, ni siquiera entre una llamada a slurm_spank_job_prolog o slurm_spank_job_epilog y llamadas subsiguientes.

En el contexto local, solo se llaman las funciones init, exit, init_post_opt y local_user_init. En el contexto allocator, solo se llaman las funciones init, exit y init_post_opt. De manera similar, en el contexto slurmd, solo están activas las llamadas de retorno init y slurmd_exit, y en el contexto job_script, solo se utilizan las llamadas de retorno job_prolog y job_epilog. Los plug-ins pueden consultar el contexto en el que se están ejecutando con las funciones spank_context y spank_remote definidas en spank.h.

Los plug-ins de SPANK pueden ser llamados desde múltiples puntos durante el lanzamiento de la tarea de Slurm. Un plug-in puede definir las siguientes funciones:

slurm_spank_init
Se llama justo después de que los plug-ins son cargados. En contexto remoto, esto es justo después de que la etapa de la tarea se inicializa. Esta función se llama antes de procesar cualquier opción del plug-in.
slurm_spank_job_prolog
Se llama al mismo tiempo que el prólogo de la tarea. Si esta función devuelve un valor distinto de cero y el plug-in SPANK que la contiene es requerido en plugstack.conf, el nodo donde se ejecuta será drenado.
slurm_spank_init_post_opt
Se llama en el mismo punto que slurm_spank_init, pero después de que se han procesado todas las opciones del usuario para el plug-in. La razón por la que las llamadas de retorno init e init_post_opt están separadas es para que los plug-ins puedan procesar las opciones del sistema especificadas en plugstack.conf en la llamada init, luego procesar las opciones del usuario, y finalmente tomar alguna acción en slurm_spank_init_post_opt si es necesario. En el caso de una tarea heterogénea, slurm_spank_init se invoca una vez por componente de la tarea.
slurm_spank_local_user_init
Se llama en contexto local (srun) solo después de que se han procesado todas las opciones. Esto se llama después de que el ID de la tarea y los IDs de etapa están disponibles. Esto ocurre en srun después de que se realiza la asignación, pero antes de que se lancen las tareas.
slurm_spank_user_init
Se llama después de que los privilegios se han reducido temporalmente. (solo contexto remoto)
slurm_spank_task_init_privileged
Se llama para cada tarea justo después de fork, pero antes de que se reduzcan todos los privilegios elevados. Esto puede ejecutarse en paralelo con slurm_spank_task_post_fork. (solo contexto remoto)
slurm_spank_task_init
Se llama para cada tarea justo antes de execve(2). Si estás restringiendo la memoria con cgroups, la memoria asignada aquí estará en el cgroup de la tarea. (solo contexto remoto)
slurm_spank_task_post_fork
Se llama para cada tarea desde el proceso padre después de que fork(2) se haya completado. Debido a que slurmd no ejecuta ninguna tarea hasta que todas las tareas hayan completado el fork(2), esta llamada se garantiza que se ejecutará antes de que la tarea del usuario sea ejecutada. Esto puede ejecutarse en paralelo con slurm_spank_task_init_privileged. (solo contexto remoto)
slurm_spank_task_exit
Se llama para cada tarea a medida que su estado de salida es recogido por Slurm. (solo contexto remoto)
slurm_spank_exit
Se llama una vez justo antes de que slurmstepd salga en contexto remoto. En contexto local, se llama antes de que srun salga.
slurm_spank_job_epilog
Se llama al mismo tiempo que el epílogo de la tarea. Si esta función devuelve un valor distinto de cero y el plug-in SPANK que la contiene es requerido en plugstack.conf, el nodo donde se ejecuta será drenado.
slurm_spank_slurmd_exit
Se llama en slurmd cuando el demonio se apaga.

Todas estas funciones tienen el mismo prototipo, por ejemplo:

   int slurm_s
pank_init (spank_t spank, int ac, char *argv[])

Donde spank es el manejador SPANK que debe ser devuelto a Slurm cuando el plugin llama a funciones como spank_get_item y spank_getenv. Los argumentos configurados (ver CONFIGURACIÓN abajo) se pasan en el vector de argumentos argv con el recuento de argumentos ac.

Un plugin también puede definir las siguientes variables que serán utilizadas por Slurm:

slurm_spank_init_failure_mode
Cuando una llamada a slurm_spank_init falla, cambia cómo Slurm maneja ese fallo. Los valores reconocidos son:
ESPANK_NODE_FAILURE
Slurm considera que el nodo es el culpable y lo marca como drenado. El trabajo puede ser vuelto a encolar. Este es el valor por defecto.
ESPANK_JOB_FAILURE
Slurm considera que el trabajo es el culpable y lo marca como fallido (no será vuelto a encolar). El nodo no será drenado.

Los plugins SPANK pueden consultar la lista actual de símbolos de slurm_spank compatibles para determinar si la versión actual admite un hook de plugin determinado. Esto puede ser útil porque la lista de símbolos de plugin puede crecer en el futuro. La consulta se realiza utilizando la función spank_symbol_supported, que tiene el siguiente prototipo:

    int spank_symbol_supported (const char *sym);

El valor de retorno es 1 si el símbolo es compatible, 0 si no lo es.

Los plugins SPANK no tienen acceso directo a las estructuras de datos definidas internamente por Slurm. En su lugar, la información sobre el trabajo que se está ejecutando actualmente se obtiene a través de la llamada a la función spank_get_item.

  spank_err_t spank_get_item (spank_t spank, spank_item_t item, ...);

La llamada a spank_get_item debe pasar el manejador SPANK actual, así como el elemento solicitado, que se define por el spank_item_t pasado. También se pasa un número variable de argumentos de puntero, dependiendo del elemento solicitado por el plugin. Una lista de los valores válidos para item se mantiene en el archivo de cabecera spank.h. Algunos ejemplos son:

S_JOB_UID
ID de usuario del trabajo en ejecución. (uid_t *) es el tercer argumento de spank_get_item
S_JOB_STEPID
ID del paso del trabajo en ejecución. (uint32_t *) es el tercer argumento de spank_get_item.
S_TASK_EXIT_STATUS
Estado de salida de la tarea que ha finalizado. Solo es válido a partir de slurm_spank_task_exit. (int *) es el tercer argumento de spank_get_item.
S_JOB_ARGV
Línea de comandos completa del trabajo. El tercer y cuarto argumento de spank_get_item son (int *, char ***).

Ver spank.h para más detalles.

Las funciones SPANK en el entorno local y allocator deben utilizar las funciones getenv, setenv y unsetenv para ver y modificar el entorno del trabajo. Las funciones SPANK en el entorno remoto deben utilizar las funciones spank_getenv, spank_setenv y spank_unsetenv para ver y modificar el entorno del trabajo. spank_getenv busca en el entorno del trabajo la variable de entorno var y copia el valor actual en un búfer buf de longitud len. spank_setenv permite que un plugin SPANK establezca o sobrescriba una variable en el entorno del trabajo, y spank_unsetenv elimina una variable de entorno del entorno del trabajo. Los prototipos son:

 spank_err_t spank_getenv (spank_t spank, const char *var,
		           char *buf, int len);
 spank_err_t spank_setenv (spank_t spank, const char *var,
		           const char *val, int overwrite);
 spank_err_t spank_unsetenv (spank_t spank, const char *var);

Estas solo son necesarias en el contexto remoto, ya que las modificaciones del entorno de proceso estándar utilizando setenv (3), getenv (3) y unsetenv (3) pueden utilizarse en el contexto local.

También hay funciones disponibles desde dentro de los plugins SPANK para establecer variables de entorno que se exportarán a los programas PrologSlurmctld, Prolog, Epilog y EpilogSlurmctld de Slurm (el llamado entorno de control de trabajos). El nombre de las variables de entorno establecidas por estas llamadas se antepondrá con la cadena SPANK_ para evitar implicaciones de seguridad de control arbitrario de variables de entorno. (Después de todo, los scripts de control de trabajos se ejecutan como root o como el usuario de Slurm).

Estas funciones están disponibles solo desde el contexto local.

  spank_err_t spank_job_control_getenv(spank_t spank, const char *var,
		             char *buf, int len);
  spank_err_t spank_job_control_setenv(spank_t spank, const char *var,
		             const char *val, int overwrite);
  spank_err_t spank_job_control_unsetenv(spank_t spank, const char *var);

Ver spank.h para más información.

Muchas de las funciones SPANK descritas disponibles para los plugins devuelven errores a través del tipo de error spank_err_t. En caso de éxito, el valor de retorno se establecerá en ESPANK_SUCCESS, mientras que en caso de fallo, el valor de retorno se establecerá en uno de los muchos valores de error definidos en spank.h. La interfaz SPANK proporciona una función simple

  const char * spank_strerror(spank_err_t err);
que puede utilizarse para traducir un valor spank_err_t a su representación de cadena.

La función slurm_spank_log puede utilizarse para imprimir mensajes al usuario a nivel de error. Esto es para evitar que los usuarios tengan que depender de la función slurm_error, que puede ser confusa porque antepone "error:" a cada mensaje.

OPCIONES DE SPANK

Los plugins SPANK también tienen una interfaz a través de la cual pueden definir e implementar opciones de trabajo adicionales. Estas opciones se ponen a disposición del usuario a través de comandos de Slurm como srun(1), salloc(1) y sbatch(1). Si el usuario especifica la opción, su valor se reenvía y se registra con el plugin en slurmd cuando se ejecuta el trabajo. De esta manera, los plugins SPANK pueden proporcionar dinámicamente nuevas opciones y funcionalidades a Slurm.

Cada opción registrada por un plugin en Slurm tiene la forma de una struct spank_option que se declara en spank.h como

   struct spank_option {
      char *         name;
      char *         arginfo;
      char *         usage;
      int            has_arg;
      int            val;
      spank_opt_cb_f cb;
   };

Donde

name
es el nombre de la opción. Su longitud está limitada a SPANK_OPTION_MAXLEN definido en spank.h.
arginfo
es una descripción del argumento de la opción, si la opción toma un argumento.
usage
es una breve descripción de la opción adecuada para la salida de --help.
has_arg
0 si la opción no toma argumento, 1 si la opción toma argumento, y 2 si la opción toma un argumento opcional. (Ver getopt_long (3)).
val
Un valor local del plugin que se devuelve a la función de callback de la opción.
cb
Una función de callback que se invoca cuando la opción del plugin se registra en Slurm. spank_opt_cb_f es un typedef en spank.h como
  typedef int (*spank_opt_cb_f) (int val, const char *optarg,
		                 int remote);
Donde val es el valor del campo val en la estructura spank_option, optarg es el argumento proporcionado si es aplicable, y remote es 0 si la función se está llamando desde el host "local" (por ejemplo, el host donde se invocan srun o sbatch/salloc) o 1 desde el host "remoto" (host donde se ejecutan slurmd/slurmstepd) pero solo ejecutado por slurmstepd (contexto remoto) si la opción se registró para dicho contexto.

Las opciones del plugin pueden registrarse en Slurm utilizando la función spank_option_register. Esta función solo es válida cuando se llama desde el manejador slurm_spank_init del plugin, y registra una opción a la vez. El prototipo es

   spank_err_t spank_option_register (spank_t sp,
		   struct spank_option *opt);
Esta función devolverá ESPANK_SUCCESS si el registro de una opción es exitoso, o ESPANK_BAD_ARG por errores que incluyen un manejador spank_t inválido, o cuando la función no se llama desde la función slurm_spank_init. Todas las opciones deben registrarse desde todos los contextos en los que se utilizarán. Por ejemplo, si una opción solo se utiliza en contextos locales (srun) y remotos (slurmd), entonces spank_option_register solo debe llamarse desde dentro de esos contextos. Por ejemplo: 
   if (spank_context() != S_CTX_ALLOCATOR)
      spank_option_register (sp, opt);
Si, sin embargo, la opción se utiliza en todos los contextos, spank_option_register debe llamarse en todas partes.

Además de spank_option_register, los plugins también pueden exportar opciones a Slurm definiendo una tabla de struct spank_option con el nombre de símbolo spank_options. Sin embargo, este método no se admite para su uso con sbatch y salloc (contexto de asignador), por lo tanto, se prefiere el uso de spank_option_register. Al utilizar la tabla spank_options, el último elemento de la matriz debe rellenarse con ceros. Una SPANK_OPTIONS

OPTIONS

The SPANK plug-in interface provides mechanisms for plugins to accept configuration options from the user. These options can be set on the command line, in environment variables, or in job scripts.

When an option is provided by the user on the local side, either by command line options or by environment variables, Slurm will immediately invoke the option's callback with remote=0. This is meant for the plugin to do local sanity checking of the option before the value is sent to the remote side during job launch. If the argument the user specified is invalid, the plugin should issue an error and issue a non-zero return code from the callback. The plugin should be able to handle cases where the spank option is set multiple times through environment variables and command line options. Environment variables are processed before command line options.

On the remote side, options and their arguments are registered just after SPANK plugins are loaded and before the spank_init handler is called. This allows plugins to modify behavior of all plugin functionality based on the value of user-provided options.

As an alternative to use of an option callback and global variable, plugins can use the spank_option_getopt option to check for supplied options after option processing. This function has the prototype:

   spank_err_t spank_option_getopt(spank_t sp,
       struct spank_option *opt, char **optargp);
This function returns ESPANK_SUCCESS if the option defined in the struct spank_option opt has been used by the user. If optargp is non-NULL then it is set to any option argument passed (if the option takes an argument). The use of this method is required to process options in job_script context (slurm_spank_job_prolog and slurm_spank_job_epilog). This function is valid in the following contexts: slurm_spank_job_prolog, slurm_spank_local_user_init, slurm_spank_user_init, slurm_spank_task_init_privileged, slurm_spank_task_init, slurm_spank_task_exit, and slurm_spank_job_epilog.

CONFIGURATION

The default SPANK plug-in stack configuration file is plugstack.conf in the same directory as slurm.conf(5), though this may be changed via the Slurm config parameter PlugStackConfig. Normally the plugstack.conf file should be identical on all nodes of the cluster. The config file lists SPANK plugins, one per line, along with whether the plugin is required or optional, and any global arguments that are to be passed to the plugin for runtime configuration. Comments are preceded with '#' and extend to the end of the line. If the configuration file is missing or empty, it will simply be ignored.

NOTE: The SPANK plugins need to be installed on the machines that execute slurmd (compute nodes) as well as on the machines that execute job allocation utilities such as salloc, sbatch, etc (login nodes).

The format of each non-comment line in the configuration file is: 

  required/optional   plugin   arguments
For example: 
  optional /usr/lib/slurm/test.so
Tells slurmd to load the plugin test.so passing no arguments. If a SPANK plugin is required, then failure of any of the plugin's functions will cause slurmd, or the job allocator command to terminate the job, while optional plugins only cause a warning.

If a fully-qualified path is not specified for a plugin, then the currently configured PluginDir in slurm.conf(5) is searched.

SPANK plugins are stackable, meaning that more than one plugin may be placed into the config file. The plugins will simply be called in order, one after the other, and appropriate action taken on failure given that state of the plugin's optional flag.

Additional config files or directories of config files may be included in plugstack.conf with the include keyword. The include keyword must appear on its own line, and takes a glob as its parameter, so multiple files may be included from one include line. For example, the following syntax will load all config files in the /etc/slurm/plugstack.conf.d directory, in local collation order:

  include /etc/slurm/plugstack.conf.d/*
which might be considered a more flexible method for building up a spank plugin stack.

The SPANK config file is re-read on each job launch, so editing the config file will not affect running jobs. However care should be taken so that a partially edited config file is not read by a launching job.

NAME

spank

Simple Plugin API for Node and Kernel

DESCRIPTION

SPANK is a simple plugin API for Node and Kernel. It is used by Slurm to load and manage plugins that extend Slurm functionality.

SPANK plugins are loaded dynamically and can be configured in the slurm.conf and plugstack.conf files.

The following is an example of how to configure SPANK plugins in plugstack.conf:

loadable_components {
  task/cgroup {

Errors

The following errors can occur when using SPANK:

SPANK plugin could not be loaded
This error occurs when SPANK is unable to load a plugin. This can be due to an incorrect plugin path or a missing plugin file.
SPANK plugin initialization failed
This error occurs when a loaded SPANK plugin fails to initialize. This can be due to an incorrect configuration or a bug in the plugin.
SPANK plugin exit failed
This error occurs when a SPANK plugin fails to exit properly. This can be due to a bug in the plugin.
