NOMBRE

spufs - Sistema de archivos SPU

DESCRIPCIÓN

El sistema de archivos SPU se utiliza en máquinas PowerPC que implementan la Arquitectura Cell Broadband Engine para acceder a las Unidades de Procesamiento Sinérgico (SPU).

El sistema de archivos proporciona un espacio de nombres similar a la memoria compartida POSIX o a las colas de mensajes. Los usuarios que tienen permisos de escritura en el sistema de archivos pueden usar spu_create(2) para establecer contextos SPU bajo el directorio raíz de spufs.

Cada contexto SPU se representa mediante un directorio que contiene un conjunto predefinido de archivos. Estos archivos se pueden utilizar para manipular el estado de la SPU lógica. Los usuarios pueden cambiar los permisos de los archivos, pero no pueden añadir ni eliminar archivos.

Opciones de montaje

uid=<uid>
Establece el usuario propietario del punto de montaje; el valor predeterminado es 0 (root).
gid=<gid>
Establece el grupo propietario del punto de montaje; el valor predeterminado es 0 (root).
mode=<mode>
Establece el modo del directorio de nivel superior en spufs, como una cadena de modo octal. El valor predeterminado es 0775.

Archivos

Los archivos en spufs siguen en su mayoría el comportamiento estándar para llamadas al sistema regulares como read(2) o write(2), pero a menudo solo admiten un subconjunto de las operaciones admitidas en sistemas de archivos regulares. Esta lista detalla las operaciones admitidas y las desviaciones del comportamiento estándar descritas en las páginas del manual correspondientes.

Todos los archivos que admiten la operación read(2) también admiten readv(2) y todos los archivos que admiten la operación write(2) también admiten writev(2). Todos los archivos admiten las operaciones de la familia access(2) y stat(2), pero para esta última llamada, los únicos campos de la estructura stat devuelta que contienen información fiable son st_mode, st_nlink, st_uid y st_gid.

Todos los archivos admiten las operaciones chmod(2)/fchmod(2) y chown(2)/fchown(2), pero no podrán conceder permisos que contradigan las operaciones posibles (por ejemplo, acceso de lectura en el archivo wbox).

El conjunto actual de archivos es:

/capabilities
Contiene una cadena separada por comas que representa las capacidades de este contexto SPU. Las capacidades posibles son:
sched
Este contexto puede ser programado.
step
Este contexto puede ejecutarse en modo de un solo paso, para depuración.

Es posible que se añadan nuevas banderas de capacidades en el futuro.

/mem
El contenido de la memoria de almacenamiento local de la SPU. Esto se puede acceder como un archivo de memoria compartida normal y contiene código y datos en el espacio de direcciones de la SPU. Las operaciones posibles en un archivo mem abierto son:
read(2)
pread(2)
write(2)
pwrite(2)
lseek(2)
Estas operan como de costumbre, con la excepción de que lseek(2), write(2) y pwrite(2) no están soportados más allá del final del archivo. El tamaño del archivo es el tamaño del almacenamiento local de la SPU, que normalmente es de 256 kilobytes.
mmap(2)
Mapear mem en el espacio de direcciones del proceso proporciona acceso al almacenamiento local de la SPU dentro del espacio de direcciones del proceso. Solo se permiten mapeos MAP_SHARED.
/regs
Contiene los registros de propósito general guardados del contexto SPU. Este archivo contiene los valores de 128 bits de cada registro, desde el registro 0 hasta el registro 127, en orden. Esto permite inspeccionar los registros de propósito general para depuración.
Leer o escribir en este archivo requiere que el contexto esté desprogramado, por lo que no se recomienda el uso de este archivo en la operación normal del programa.
El archivo regs no está presente en los contextos que se han creado con la bandera SPU_CREATE_NOSCHED.
/mbox
El primer buzón de comunicación SPU-a-CPU. Este archivo es de solo lectura y se puede leer en unidades de 4 bytes. El archivo solo se puede usar en modo no bloqueante; incluso poll(2) no se puede usar para bloquear en este archivo. La única operación posible en un archivo mbox abierto es:
read(2)
Si count es menor que cuatro, read(2) devuelve -1 y establece errno a EINVAL. Si no hay datos disponibles en el buzón (es decir, la SPU no ha enviado un mensaje de buzón), el valor de retorno se establece a -1 y errno se establece a EAGAIN. Cuando los datos se han leído correctamente, se colocan cuatro bytes en el búfer de datos y se devuelve el valor cuatro.
/ibox
El segundo buzón de comunicación SPU-a-CPU. Este archivo es similar al primer archivo del buzón, pero se puede leer en modo de E/S bloqueante, por lo que llamar a read(2) en un archivo ibox abierto bloqueará hasta que la SPU haya escrito datos en su canal de buzón de interrupción (a menos que el archivo se haya abierto con O_NONBLOCK, ver más abajo). Además, se pueden usar llamadas al sistema como poll(2) para monitorear la presencia de datos en el buzón.
Las operaciones posibles en un archivo ibox abierto son:
read(2)
Si count es menor que cuatro, read(2) devuelve -1 y establece errno a EINVAL. Si no hay datos disponibles en el buzón y el descriptor de archivo se ha abierto con O_NONBLOCK, el valor de retorno se establece a -1 y errno se establece a EAGAIN.
Si no hay datos disponibles en el buzón y el descriptor de archivo se ha abierto sin O_NONBLOCK, la llamada se bloqueará hasta que la SPU escriba en su canal de buzón de interrupción. Cuando los datos se han leído correctamente, se colocan cuatro bytes en el búfer de datos y se devuelve el valor cuatro.
poll(2)
Poll en el archivo ibox devuelve (POLLIN | POLLRDNORM) siempre que haya datos disponibles para leer.
/wbox
El buzón de comunicación CPU-a-SPU. Es de solo escritura y se puede escribir en unidades de cuatro bytes. Si el buzón está lleno, write(2) se bloqueará, y poll(2) se puede usar para bloquear hasta que el buzón esté disponible para escribir de nuevo. Las operaciones posibles en un archivo wbox abierto son:
write(2)
Si count es menor que cuatro, write(2) devuelve -1 y establece errno a EINVAL. Si no hay espacio disponible en el buzón y el descriptor de archivo se ha abierto con O_NONBLOCK, el valor de retorno se establece a -1 y errno se establece a EAGAIN.
Si no hay espacio disponible en el buzón y el descriptor de archivo se ha abierto sin O_NONBLOCK, la llamada se bloqueará hasta que la SPU lea datos de su canal de buzón de interrupción. Cuando los datos se han escrito correctamente, cuatro bytes se leen del búfer de datos y se devuelve el valor cuatro.
poll(2)
Poll en el archivo wbox devuelve POLLOUT cuando el buzón está listo para escribir.
/signal
Permite enviar señales a la SPU. Solo se admite la escritura y la operación es similar a kill(2). Las señales solo pueden enviarse al SPU del proceso propietario del contexto. Las señales válidas son:
SIGKILL
Termina la SPU.
SIGUSR1
Se utiliza para despertar a la SPU, por ejemplo, si la SPU está en modo de espera.
SIGUSR2
Similar a SIGUSR1, pero se puede utilizar para diferentes fines. El uso de esta señal debe ser acordado entre la aplicación y el programa que se ejecuta en la SPU.
/run
Permite el control de la ejecución de la SPU. La escritura en este archivo solo admite los siguientes valores:
RUN_START
Inicia la ejecución de la SPU.
RUN_STOP
Detiene la ejecución de la SPU. Esto solo es posible si la SPU se está ejecutando en modo de un solo paso.
RUN_STEP
Ejecuta la SPU en modo de un solo paso.
/wintrp
Este archivo permite enviar mensajes de interrupción a la CPU desde la SPU. Este archivo solo puede ser escrito por la SPU. El programa que se ejecuta en la SPU debe haber configurado el buzón de interrupción de forma apropiada.
/wgetting
Este archivo contiene el estado del contexto de la SPU.
READY
La SPU está lista para ser programada.
RUNNING
La SPU se está ejecutando.
STOPPED
La SPU está detenida.
TERMINATED
La SPU ha terminado su ejecución.
WAITING
La SPU está esperando una señal.
/wpage_attrs
Permite al usuario establecer los atributos de página de la memoria local de la SPU. Los atributos de página solo se pueden escribir si la SPU está en el estado STOPPED.
write(2)
El archivo puede escribirse con un desplazamiento, seguido de un valor de atributo. Por ejemplo, para establecer los atributos de página 0x1234 en el desplazamiento 0x5678, el siguiente comando se ejecutará:
        # echo 0x5678:0x1234 > /spu/context/wpage_attrs
/rpage_attrs
Permite al usuario leer los atributos de página de la memoria local de la SPU. El formato es el mismo que para wpage_attrs.

CAVEATS

El acceso al sistema de archivos spufs se realiza a través de archivos especiales que mapean operaciones de E/S a llamadas de sistema específicas para SPUs. La mayoría de las operaciones de E/S en estos archivos son síncronas y pueden bloquear el hilo que las realiza. Se recomienda encarecidamente utilizar llamadas asíncronas como aio(7) cuando sea posible.

El acceso a los archivos mbox y wbox requiere una cuidadosa sincronización para evitar la pérdida de datos o bloqueos inesperados. El uso de poll(2) o select(2) es la forma recomendada de manejar las operaciones de buzón de forma asíncrona.

El archivo regs solo es accesible cuando la SPU está detenida. Intentar leer o escribir en regs mientras la SPU está en ejecución generará un error.

Los archivos wpage_attrs y rpage_attrs solo son relevantes para arquitecturas específicas de SPU y pueden no estar disponibles en todas las implementaciones.

Si no hay espacio disponible en el buzón y el descriptor de archivo se ha abierto sin O_NONBLOCK, la llamada se bloqueará hasta que la SPU lea de su canal de buzón PPE (PowerPC Processing Element). Cuando los datos se hayan escrito correctamente, la llamada al sistema devolverá cuatro como resultado de su función.
poll(2)
Una llamada a poll en el archivo wbox devuelve (POLLOUT | POLLWRNORM) cada vez que hay espacio disponible para escribir.
/mbox_stat
/ibox_stat
/wbox_stat
Estos son archivos de solo lectura que contienen la longitud de la cola actual de cada buzón —es decir, cuántas palabras se pueden leer de mbox o ibox o cuántas palabras se pueden escribir en wbox sin bloquear. Los archivos solo se pueden leer en unidades de cuatro bytes y devuelven un número entero binario en formato big-endian. La única operación posible en un archivo abierto *box_stat es:
read(2)
Si count es menor que cuatro, read(2) devuelve -1 y establece errno en EINVAL. De lo contrario, se coloca un valor de cuatro bytes en el búfer de datos. Este valor es el número de elementos que se pueden leer de (para mbox_stat e ibox_stat) o escribir en (para wbox_stat) el buzón respectivo sin bloquear o devolver un error EAGAIN.
/npc
/decr
/decr_status
/spu_tag_mask
/event_mask
/event_status
/srr0
/lslr
Registros internos de la SPU. Estos archivos contienen una cadena ASCII que representa el valor hexadecimal del registro especificado. Las lecturas y escrituras en estos archivos (excepto para npc, véase más abajo) requieren que el contexto de la SPU se desprograme, por lo que no se recomienda el acceso frecuente a estos archivos para la operación normal del programa.
El contenido de estos archivos es:
npc
Siguiente Contador de Programa — válido solo cuando la SPU está en estado detenido.
decr
Decrementador de SPU
decr_status
Estado del Decrementador
spu_tag_mask
Máscara de etiquetas MFC para DMA de SPU
event_mask
Máscara de eventos para interrupciones de SPU
event_status
Número de eventos de SPU pendientes (solo lectura)
srr0
Registro de dirección de retorno de interrupción
lslr
Registro Límite de Almacenamiento Local
Las operaciones posibles en estos archivos son:
read(2)
Lee el valor actual del registro. Si el valor del registro es mayor que el búfer pasado a la llamada del sistema read(2), las lecturas subsiguientes continuarán leyendo desde el mismo búfer, hasta que se alcance el final del búfer.
Cuando se ha leído una cadena completa, todas las operaciones de lectura posteriores devolverán cero bytes y se deberá abrir un nuevo descriptor de archivo para leer un nuevo valor.
write(2)
Una operación de write(2) en el archivo establece el registro al valor proporcionado en la cadena. La cadena se analiza desde el principio hasta el primer carácter no numérico o el final del búfer. Las escrituras posteriores en el mismo descriptor de archivo sobrescriben la configuración anterior.
Excepto para el archivo npc, estos archivos no están presentes en los contextos que se han creado con el flag SPU_CREATE_NOSCHED.
/fpcr
Este archivo proporciona acceso al Registro de Estado y Control de Punto Flotante (fcpr) como un archivo binario de cuatro bytes. Las operaciones en el archivo fpcr son:
read(2)
Si count es menor que cuatro, read(2) devuelve -1 y establece errno en EINVAL. De lo contrario, se coloca un valor de cuatro bytes en el búfer de datos; este es el valor actual del registro fpcr.
write(2)
Si count es menor que cuatro, write(2) devuelve -1 y establece errno en EINVAL. De lo contrario, se copia un valor de cuatro bytes desde el búfer de datos, actualizando el valor del registro fpcr.
/signal1
/signal2
Los archivos proporcionan acceso a los dos canales de notificación de señales de una SPU. Son archivos de lectura/escritura que operan con palabras de cuatro bytes. Escribir en uno de estos archivos activa una interrupción en la SPU. El valor escrito en los archivos de señal se puede leer desde la SPU a través de una lectura de canal o desde el espacio de usuario del host a través del archivo. Después de que el valor ha sido leído por la SPU, se restablece a cero. Las operaciones posibles en un archivo abierto signal1 o signal2 son:
read(2)
Si count es menor que cuatro, read(2) devuelve -1 y establece errno en EINVAL. De lo contrario, se coloca un valor de cuatro bytes en el búfer de datos; este es el valor actual del registro de notificación de señal especificado.
write(2)
Si count es menor que cuatro, write(2) devuelve -1 y establece errno en EINVAL. De lo contrario, se copia un valor de cuatro bytes desde el búfer de datos, actualizando el valor del registro de notificación de señal especificado. El registro de notificación de señal será reemplazado con los datos de entrada o se actualizará a la operación OR a nivel de bits del valor antiguo y los datos de entrada, dependiendo del contenido de los archivos signal1_type o signal2_type respectivamente.
/signal1_type
/signal2_type
Estos dos archivos cambian el comportamiento de los archivos de notificación signal1 y signal2. Contienen una cadena numérica ASCII que se lee como "1" o "0". En el modo 0 (sobrescritura), el hardware reemplaza el contenido del canal de señal con los datos que se escriben en él. En el modo 1 (OR lógico), el hardware acumula los bits que se escriben posteriormente en él. Las operaciones posibles en un archivo abierto signal1_type o signal2_type son:
read(2)
Cuando el recuento proporcionado a la llamada read(2) es más corto que la longitud requerida para el dígito (más un carácter de nueva línea), las lecturas subsiguientes del mismo descriptor de archivo completarán la cadena. Cuando se haya leído una cadena completa, todas las operaciones de lectura posteriores devolverán cero bytes y se deberá abrir un nuevo descriptor de archivo para leer el valor nuevamente.
write(2)
Una operación de write(2) en el archivo establece el registro al valor proporcionado en la cadena. La cadena se analiza desde el principio hasta el primer carácter no numérico o el final del búfer. Las escrituras posteriores en el mismo descriptor de archivo sobrescriben la configuración anterior.
/mbox_info
/ibox_info
/wbox_info
/dma_into
/proxydma_info
Archivos de solo lectura que contienen el estado guardado de los buzones y colas DMA de la SPU. Esto permite inspeccionar el estado de la SPU, principalmente para depuración. Los archivos mbox_info e ibox_info contienen cada uno el mensaje del buzón de cuatro bytes que ha sido escrito por la SPU. Si no se ha escrito ningún mensaje en estos buzones, entonces el contenido de estos archivos es indefinido. Los archivos mbox_stat, ibox_stat y wbox_stat contienen el recuento de mensajes disponibles.
El archivo wbox_info contiene una matriz de mensajes de buzón de cuatro bytes, que se han enviado a la SPU. Con las máquinas CBEA actuales, la matriz tiene una longitud de cuatro elementos, por lo que se pueden leer hasta 4 * 4 = 16 bytes de este archivo. Si alguna entrada de la cola del buzón está vacía, los bytes leídos en la ubicación correspondiente son indefinidos.
El archivo dma_info contiene el contenido de la cola DMA de la SPU MFC, representado como la siguiente estructura:

struct spu_dma_info {
    uint64_t         dma_info_type;
    uint64_t         dma_info_mask;
    uint64_t         dma_info_status;
    uint64_t         dma_info_stall_and_notify;
    uint64_t         dma_info_atomic_command_status;
    struct mfc_cq_sr dma_info_command_data[16];
};

El último miembro de esta estructura de datos es la cola DMA real, que contiene 16 entradas. La estructura mfc_cq_sr se define como:

struct mfc_cq_sr {
    uint64_t mfc_cq_data0_RW;
    uint64_t mfc_cq_data1_RW;
    uint64_t mfc_cq_data2_RW;
    uint64_t mfc_cq_data3_RW;
};

El archivo proxydma_info contiene información similar, pero describe la cola DMA proxy (es decir, DMAs iniciadas por entidades fuera de la SPU) en su lugar. El archivo está en el siguiente formato:

struct spu_proxydma_info {
    uint64_t         proxydma_info_type;
    uint64_t         proxydma_info_mask;
    uint64_t         proxydma_info_status;
    struct mfc_cq_sr proxydma_info_command_data[8];
};

El acceso a estos archivos requiere que el contexto de la SPU esté desprogramado; un uso frecuente puede ser ineficiente. Estos archivos no deben usarse para ni
mal operación del programa.
Estos archivos no están presentes en contextos que se han creado con la bandera SPU_CREATE_NOSCHED.
/cntl
Este archivo proporciona acceso a los registros de control de ejecución y estado de SPU, como una cadena de texto ASCII. Las siguientes operaciones son compatibles:
read(2)
Las lecturas del archivo cntl devolverán una cadena ASCII con el valor hexadecimal del registro de estado de SPU.
write(2)
Las escrituras en el archivo cntl establecerán el registro de control de ejecución de SPU del contexto.
/mfc
Proporciona acceso al controlador de flujo de memoria (MFC) del SPU. La lectura del archivo devuelve el contenido del registro de estado de etiquetas del MFC del SPU, y la escritura en el archivo inicia una DMA desde el MFC. Las siguientes operaciones son compatibles:
write(2)
Las escrituras en este archivo deben tener el formato de un comando DMA del MFC, definido como sigue:

struct mfc_dma_command {
    int32_t  pad;    /* reservado */
    uint32_t lsa;    /* dirección de almacenamiento local */
    uint64_t ea;     /* dirección efectiva */
    uint16_t size;   /* tamaño de transferencia */
    uint16_t tag;    /* etiqueta del comando */
    uint16_t class;  /* ID de clase */
    uint16_t cmd;    /* opcode del comando */
};

Las escrituras deben tener un tamaño exactamente de sizeof(struct mfc_dma_command) bytes. El comando se enviará a la cola proxy del MFC del SPU, y la etiqueta se almacenará en el kernel (ver abajo).
read(2)
Lee el contenido del registro de estado de etiquetas. Si el archivo se abre en modo bloqueante (es decir, sin O_NONBLOCK), la lectura se bloqueará hasta que una etiqueta DMA (realizada por una escritura previa) se complete. En modo no bloqueante, el registro de estado de etiquetas del MFC se devolverá sin esperar.
poll(2)
Llamar a poll(2) en el archivo mfc se bloqueará hasta que se pueda iniciar una nueva DMA (comprobando POLLOUT) o hasta que una DMA iniciada previamente (comprobando POLLIN) se haya completado.
/mss Proporciona acceso a la instalación de Sincronización Multi-Fuente (MSS) del MFC. Mediante mmap(2)-ing este archivo, los procesos pueden acceder al área MSS del SPU.
Las siguientes operaciones son compatibles:
mmap(2)
Mapear mss en el espacio de direcciones del proceso da acceso al área MSS del SPU dentro del espacio de direcciones del proceso. Solo se permiten mapeos MAP_SHARED.
/psmap
Proporciona acceso a todo el mapeo del estado del problema del SPU. Las aplicaciones pueden usar esta área para interactuar con el SPU, en lugar de escribir en archivos de registro individuales en spufs.
Las siguientes operaciones son compatibles:
mmap(2)
Mapear psmap le da a un proceso un mapa directo del área de estado del problema del SPU. Solo se admiten mapeos MAP_SHARED.
/phys-id
Archivo de solo lectura que contiene el número físico del SPU en el que se está ejecutando el contexto del SPU. Cuando el contexto no se está ejecutando, este archivo contiene la cadena ""-1"".
El número físico del SPU se proporciona como una cadena hexadecimal ASCII.
/object-id
Permite a las aplicaciones almacenar (o recuperar) un único ID de 64 bits en el contexto. Este ID es utilizado posteriormente por las herramientas de perfilado para identificar de forma única el contexto.
write(2)
Al escribir un valor hexadecimal ASCII en este archivo, las aplicaciones pueden establecer el ID del objeto del contexto SPU. Cualquier valor anterior del ID del objeto se sobrescribe.
read(2)
Leer este archivo proporciona una cadena hexadecimal ASCII que representa el ID del objeto para este contexto SPU.

EJEMPLOS

Para montar(8) automáticamente el sistema de archivos SPU al arrancar, en la ubicación /spu elegida por el usuario, coloque esta línea en el archivo de configuración fstab(5):

none /spu spufs gid=spu 0 0
