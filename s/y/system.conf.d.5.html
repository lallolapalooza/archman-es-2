NOMBRE

systemd-system.conf, system.conf.d, systemd-user.conf, user.conf.d - Archivos de configuración del gestor de servicios del sistema y de la sesión

SINOPSIS

/etc/systemd/system.conf, /run/systemd/system.conf, /usr/lib/systemd/system.conf, /etc/systemd/system.conf.d/*.conf, /run/systemd/system.conf.d/*.conf, /usr/lib/systemd/system.conf.d/*.conf

~/.config/systemd/user.conf, /etc/systemd/user.conf, /run/systemd/user.conf, /usr/lib/systemd/user.conf, /etc/systemd/user.conf.d/*.conf, /run/systemd/user.conf.d/*.conf, /usr/lib/systemd/user.conf.d/*.conf

DESCRIPCIÓN

Cuando se ejecuta como una instancia del sistema, systemd interpreta el archivo de configuración system.conf y los archivos de los directorios system.conf.d; cuando se ejecuta como una instancia de usuario, interpreta el archivo de configuración user.conf (en orden de prioridad, en el directorio personal del usuario y bajo /etc/systemd/, /run/systemd/, y /usr/lib/systemd/) y los archivos de los directorios user.conf.d. Estos archivos de configuración contienen algunas opciones que controlan las operaciones básicas del gestor.

Consulte systemd.syntax(7) para una descripción general de la sintaxis.

DIRECTORIOS DE CONFIGURACIÓN Y PRECEDENCIA

La configuración predeterminada se establece durante la compilación, por lo que la configuración solo es necesaria cuando es necesario desviarse de esos valores predeterminados. El archivo de configuración principal se carga desde uno de los directorios listados en orden de prioridad, solo se utiliza el primer archivo encontrado: /etc/systemd/, /run/systemd/, /usr/local/lib/systemd/ [1], /usr/lib/systemd/. La versión del proveedor del archivo contiene entradas comentadas que muestran los valores predeterminados como guía para el administrador. También se pueden crear sustituciones locales creando archivos adicionales (drop-ins), como se describe a continuación. El archivo de configuración principal también se puede editar para este propósito (o una copia en /etc/ si se distribuye bajo /usr/), sin embargo, se recomienda el uso de archivos adicionales para la configuración local en lugar de modificar el archivo de configuración principal.

Además del archivo de configuración principal, los fragmentos de configuración adicionales se leen de /usr/lib/systemd/*.conf.d/, /usr/local/lib/systemd/*.conf.d/, y /etc/systemd/*.conf.d/. Estos archivos adicionales tienen mayor precedencia y anulan el archivo de configuración principal. Los archivos en los subdirectorios de configuración *.conf.d/ se ordenan por su nombre de archivo en orden lexicográfico, independientemente de en cuál de los subdirectorios residan. Cuando varios archivos especifican la misma opción, para opciones que solo aceptan un único valor, la entrada en el archivo ordenado último tiene precedencia, y para opciones que aceptan una lista de valores, las entradas se recopilan según aparecen en los archivos ordenados.

Cuando los paquetes necesitan personalizar la configuración, pueden instalar archivos adicionales bajo /usr/. Los archivos en /etc/ están reservados para el administrador local, quien puede usar esta lógica para anular los archivos de configuración instalados por los paquetes del proveedor. Los archivos adicionales deben usarse para anular los archivos adicionales de los paquetes, ya que el archivo de configuración principal tiene menor precedencia. Se recomienda prefijar todos los nombres de archivo en estos subdirectorios con un número de dos dígitos y un guion, para simplificar el orden. Esto también define un concepto de prioridades de archivos adicionales para permitir que los proveedores de sistemas operativos distribuyan archivos adicionales dentro de un rango específico menor que el rango utilizado por los usuarios. Esto debería reducir el riesgo de que los archivos adicionales de los paquetes anulen accidentalmente los archivos adicionales definidos por los usuarios. Se recomienda usar el rango 10-40 para los archivos adicionales en /usr/ y el rango 60-90 para los archivos adicionales en /etc/ y /run/, para asegurarse de que los archivos adicionales locales y transitorios tengan prioridad sobre los archivos adicionales distribuidos por el proveedor del sistema operativo.

Para deshabilitar un archivo de configuración proporcionado por el proveedor, la forma recomendada es colocar un enlace simbólico a /dev/null en el directorio de configuración en /etc/, con el mismo nombre de archivo que el archivo de configuración del proveedor.

OPCIONES

Todas las opciones se configuran en la sección [Manager]:

LogColor=, LogLevel=, LogLocation=, LogTarget=, LogTime=, DumpCore=yes, CrashChangeVT=no, CrashShell=no, CrashAction=freeze, ShowStatus=yes, DefaultStandardOutput=journal, DefaultStandardError=inherit

Configura varios parámetros de la operación básica del gestor. Estas opciones pueden ser anuladas por los respectivos argumentos del proceso y de la línea de comandos del kernel. Consulte systemd(1) para obtener detalles.

CtrlAltDelBurstAction=

Define qué acción se realizará si el usuario presiona Ctrl-Alt-Suprimir más de 7 veces en 2 segundos. Puede configurarse en "reboot-force", "poweroff-force", "reboot-immediate", "poweroff-immediate" o deshabilitarse con "none". El valor predeterminado es "reboot-force".

Añadido en la versión 232.

StatusUnitFormat=

Toma name, description o combined como valor. Si es name, el gestor del sistema utilizará los nombres de unidad en los mensajes de estado (por ejemplo, "systemd-journald.service"), en lugar de las descripciones más largas e informativas establecidas con Description= (por ejemplo, "Servicio de registro de Journal"). Si es combined, el gestor del sistema utilizará tanto los nombres de unidad como las descripciones en los mensajes de estado (por ejemplo, "systemd-journald.service - Servicio de registro de Journal").

Consulte systemd.unit(5) para obtener detalles sobre nombres de unidad y Description=.

AccuracySec= establecido en unidades individuales anula el valor predeterminado global para la unidad específica. El valor predeterminado es 1min. Tenga en cuenta que la precisión de las unidades de temporizador también se ve afectada por el tiempo de espera del temporizador configurado para PID 1, consulte TimerSlackNSec= arriba.

GESTIÓN DE RECURSOS

TimerSlackNSec=

Establece el tiempo de espera del temporizador en nanosegundos para PID 1, que se hereda de todos los procesos ejecutados, a menos que se anule individualmente, por ejemplo, con la configuración TimerSlackNSec= en las unidades de servicio (para detalles, consulte systemd.exec(5)). El tiempo de espera del temporizador controla la precisión de los despertares activados por los temporizadores del sistema. Consulte prctl(2) para obtener más información. Tenga en cuenta que, a diferencia de la mayoría de las otras definiciones de intervalos de tiempo, este parámetro toma un valor entero en nanosegundos si no se especifica ninguna unidad. También se entienden las unidades de tiempo habituales.

DefaultLimitCPU=, DefaultLimitFSIZE=, DefaultLimitDATA=, DefaultLimitSTACK=, DefaultLimitCORE=, DefaultLimitRSS=, DefaultLimitNOFILE=, DefaultLimitAS=, DefaultLimitNPROC=, DefaultLimitMEMLOCK=, DefaultLimitLOCKS=, DefaultLimitSIGPENDING=, DefaultLimitMSGQUEUE=, DefaultLimitNICE=, DefaultLimitRTPRIO=, DefaultLimitRTTIME=

HARDWARE WATCHDOG

RuntimeWatchdogSec=, RebootWatchdogSec=, KExecWatchdogSec=

Configura el watchdog de hardware en tiempo de ejecución y al reiniciar. Toma un valor de tiempo de espera en segundos (o en otras unidades de tiempo si va seguido de "ms", "min", "h", "d", "w"), o las cadenas especiales "off" o "default". Si se establece en "off" (alternativamente: "0") la lógica del watchdog se deshabilita: no se abre, configura ni hace ping a ningún dispositivo watchdog. Si se establece en la cadena especial "default" el watchdog se abre y se hace ping a intervalos regulares, pero el tiempo de espera no se cambia del valor por defecto. Si se establece en cualquier otro valor de tiempo, el tiempo de espera del watchdog se configura al valor especificado (o un valor cercano a él, dependiendo de las capacidades del hardware).

Si RuntimeWatchdogSec= se establece en un valor distinto de cero, el hardware del watchdog (/dev/watchdog0 o la ruta especificada con WatchdogDevice= o la opción del kernel systemd.watchdog_device=) se programará para reiniciar automáticamente el sistema si no se contacta dentro del intervalo de tiempo de espera especificado. El gestor del sistema se asegurará de contactarlo al menos una vez en la mitad del intervalo de tiempo de espera especificado. Esta característica requiere un dispositivo watchdog de hardware, ya que es común en sistemas embebidos y de servidor. No todos los watchdogs de hardware permiten la configuración de todos los posibles valores de tiempo de espera de reinicio, en cuyo caso se elige el tiempo de espera disponible más cercano.

RebootWatchdogSec= puede ser usado para configurar el hardware watchdog cuando se solicita reiniciar el sistema. Funciona como una red de seguridad para asegurar que el reinicio se produzca incluso si un intento de reinicio limpio excede el tiempo de espera. Tenga en cuenta que el tiempo de espera de RebootWatchdogSec= se aplica solo a la segunda fase del reinicio, es decir, después de que todos los servicios regulares ya hayan terminado, y después de que el gestor del sistema y de servicios (PID 1) se haya reemplazado por el binario systemd-shutdown, vea el manual bootup(7) para más detalles. Durante la primera fase de la operación de apagado, el sistema y el gestor de servicios permanecen en ejecución y, por lo tanto, RuntimeWatchdogSec= sigue siendo respetado. Para definir un tiempo de espera en esta primera fase del apagado del sistema, configure JobTimeoutSec= y JobTimeoutAction= en la sección [Unit] de la unidad shutdown.target. Por defecto, RuntimeWatchdogSec= es 0 (apagado), y RebootWatchdogSec= es 10min.

KExecWatchdogSec= puede ser usado para habilitar adicionalmente el watchdog cuando se está ejecutando kexec en lugar de reiniciar. Tenga en cuenta que si el kernel no reinicia el watchdog en kexec (dependiendo del hardware y/o controlador específico), en este caso el watchdog podría no ser deshabilitado después de que kexec tenga éxito y, por lo tanto, el sistema podría reiniciarse, a menos que RuntimeWatchdogSec= también esté habilitado al mismo tiempo. Por esta razón, se recomienda habilitar KExecWatchdogSec= solo si RuntimeWatchdogSec= también está habilitado.

Estas configuraciones no tienen efecto si no hay un hardware watchdog disponible.

Añadido en la versión 198.

RuntimeWatchdogPreSec=

Configura el valor del pre-timeout del dispositivo watchdog de hardware. Toma un valor de tiempo de espera en segundos (o en otras unidades de tiempo similares a RuntimeWatchdogSec=). Un pre-timeout del watchdog es una notificación generada por el watchdog antes de que pueda ocurrir el reinicio del watchdog en caso de que el watchdog no haya sido atendido. Esta notificación es manejada por el kernel y puede ser configurada para tomar una acción (es decir, generar un pánico de kernel) usando RuntimeWatchdogPreGovernor=. No todo el hardware o los controladores watchdog soportan la generación de un pre-timeout y dependiendo del estado del sistema, el kernel puede no ser capaz de tomar la acción configurada antes de que el watchdog reinicie. El watchdog se configurará para generar el evento de pre-timeout en la cantidad de tiempo especificada por RuntimeWatchdogPreSec= antes del tiempo de espera del watchdog en tiempo de ejecución (establecido por RuntimeWatchdogSec=). Por ejemplo, si tenemos RuntimeWatchdogSec=30 y RuntimeWatchdogPreSec=10, entonces el evento de pre-timeout ocurrirá si el watchdog no ha hecho ping durante 20s (10s antes de que el watchdog se active). Por defecto, RuntimeWatchdogPreSec= es 0 (apagado). El valor establecido para RuntimeWatchdogPreSec= debe ser menor que el valor de tiempo de espera para RuntimeWatchdogSec=. Esta configuración no tiene efecto si no hay un hardware watchdog disponible o si el hardware watchdog no soporta un pre-timeout y será ignorada por el kernel si la configuración es mayor que el tiempo de espera real del watchdog.

Añadido en la versión 251.

RuntimeWatchdogPreGovernor=

Configura la acción tomada por el dispositivo watchdog de hardware cuando expira el pre-timeout. La acción por defecto para el evento de pre-timeout depende de la configuración del kernel, pero generalmente es registrar un mensaje del kernel. Para una lista de acciones válidas disponibles para un dispositivo watchdog dado, revise el contenido del archivo /sys/class/watchdog/watchdogX/pretimeout_available_governors. Típicamente, los tipos de gobernador disponibles son noop y panic. La disponibilidad, nombres y funcionalidad pueden variar dependiendo del controlador de dispositivo específico en uso. Si el archivo sysfs pretimeout_available_governors está vacío, el gobernador podría estar compilado como un módulo del kernel y podría necesitar ser cargado manualmente (por ejemplo, pretimeout_noop.ko), o el dispositivo watchdog podría no soportar pre-timeouts.

Añadido en la versión 251.

WatchdogDevice=

Configura el dispositivo watchdog de hardware que usarán los temporizadores watchdog de tiempo de ejecución y de apagado. Por defecto es /dev/watchdog0. Esta configuración no tiene efecto si no hay un hardware watchdog disponible.

SECURITY

CapabilityBoundingSet=

Controla qué capacidades se incluyen en el conjunto de límites de capacidades para PID 1 y sus hijos. Vea capabilities(7) para más detalles. Toma una lista separada por espacios de nombres de capacidades tal como las lee cap_from_name(3). Las capacidades listadas se incluirán en el conjunto de límites, todas las demás se eliminarán. Si la lista de capacidades va prefijada con ~,
todo lo incluido, excepto las capacidades listadas, será incluido, con el efecto de la asignación invertido. Tenga en cuenta que esta opción también afecta a las capacidades respectivas en los conjuntos de capacidades efectivo, permitido y heredable. El conjunto de límites de capacidades también puede ser configurado individualmente para unidades usando la directiva CapabilityBoundingSet= para unidades, pero tenga en cuenta que las capacidades eliminadas para PID 1 no se pueden recuperar en unidades individuales, se pierden para siempre.

Añadido en la versión 198.

NoNewPrivileges=

Acepta un argumento booleano. Si es verdadero, asegura que PID 1 y todos sus hijos nunca puedan obtener nuevos privilegios a través de execve(2) (por ejemplo, a través de bits setuid o setgid, o capacidades del sistema de archivos). Por defecto es falso. Las distribuciones de propósito general comúnmente dependen de ejecutables con bits setuid o setgid y, por lo tanto, no funcionarán correctamente con esta opción habilitada. Las unidades individuales no pueden deshabilitar esta opción. Véase también la Opción No New Privileges[2].

Añadido en la versión 239.

ProtectSystem=

Acepta un argumento booleano o la cadena "auto". Si se establece en verdadero, volverá a montar /usr/ como solo lectura. Si se establece en "auto" (el valor predeterminado) y se ejecuta en un initrd equivalente a verdadero, de lo contrario falso. Esto implementa un subconjunto restringido de la configuración por unidad del mismo nombre, consulte systemd.exec(5) para más detalles: actualmente, los valores "full" o "strict" no son compatibles.

Añadido en la versión 256.

SystemCallArchitectures=

Acepta una lista separada por espacios de identificadores de arquitectura. Selecciona desde qué arquitecturas se pueden invocar llamadas al sistema en este sistema. Esto puede usarse como una forma efectiva de deshabilitar la invocación de binarios no nativos en todo el sistema, por ejemplo, para prohibir la ejecución de binarios x86 de 32 bits en sistemas x86-64 de 64 bits. Esta opción opera en todo el sistema y actúa de manera similar a la configuración SystemCallArchitectures= de los archivos de unidad, consulte systemd.exec(5) para más detalles. Esta configuración tiene como valor predeterminado la lista vacía, en cuyo caso no se aplica ningún filtrado de llamadas al sistema basado en la arquitectura. Los identificadores de arquitectura conocidos son "x86", "x86-64", "x32", "arm" y el identificador especial "native". Este último se mapea implícitamente a la arquitectura nativa del sistema (o más específicamente, la arquitectura para la que se compiló el gestor del sistema). Establezca esta configuración en "native" para prohibir la ejecución de cualquier binario no nativo. Cuando un binario ejecuta una llamada al sistema de una arquitectura que no está listada en esta configuración, se terminará inmediatamente con la señal SIGSYS.

TEMPORIZADORES Y LÍMITES DE TASA

DefaultTimeoutStartSec=, DefaultTimeoutStopSec=, DefaultTimeoutAbortSec=, DefaultRestartSec=

Configura los temporizadores predeterminados para iniciar, detener y abortar unidades, así como el tiempo predeterminado para esperar entre reinicios automáticos de unidades, según se configuran por unidad en TimeoutStartSec=, TimeoutStopSec=, TimeoutAbortSec= y RestartSec= (para servicios, consulte systemd.service(5) para más detalles sobre la configuración por unidad). Para unidades que no son servicios, DefaultTimeoutStartSec= establece el valor predeterminado de TimeoutSec=.

DefaultTimeoutStartSec= y DefaultTimeoutStopSec= tienen como valor predeterminado 90 s en el gestor del sistema y 90 s en el gestor de usuario. DefaultTimeoutAbortSec= no está configurado por defecto para que todas las unidades recurran a TimeoutStopSec=. DefaultRestartSec= tiene como valor predeterminado 100 ms.

DefaultStartLimitBurst= tiene como valor predeterminado 5.

Añadido en la versión 209.

ReloadLimitIntervalSec=, ReloadLimitBurst=

Límite de tasa para las solicitudes daemon-reload y (desde v256) daemon-reexec. La configuración se aplica a ambas operaciones, pero los límites de tasa se rastrean por separado. Por defecto no están definidos, y se pueden solicitar cualquier número de operaciones en cualquier momento. ReloadLimitIntervalSec= toma un valor en segundos para configurar la ventana del límite de tasa, y ReloadLimitBurst= toma un entero positivo para configurar el número máximo permitido de operaciones dentro de la ventana de tiempo configurada.

Añadido en la versión 253.

ENTORNO

DefaultEnvironment=

Configura las variables de entorno que se pasan a todos los procesos ejecutados. Acepta una lista separada por espacios de asignaciones de variables. Consulte environ(7) para más detalles sobre las variables de entorno. Este bloque de entorno es interno, y los cambios no se reflejan en el /proc/PID/environ del gestor.

Se admite la expansión simple de especificadores "%", véase más abajo para obtener una lista de los especificadores admitidos.

Ejemplo:

DefaultEnvironment="VAR1=word1 word2" VAR2=word3 "VAR3=word 5 6"

Establece tres variables "VAR1", "VAR2", "VAR3".

Añadido en la versión 205.

ManagerEnvironment=

Establece variables de entorno para el propio proceso gestor. Acepta una lista separada por espacios de asignaciones de variables en el mismo formato que DefaultEnvironment=, consulte más arriba. Estas variables se fusionan en el bloque de entorno existente del proceso gestor. En particular, en el caso del gestor del sistema, este bloque incluye variables establecidas por el kernel basándose en la línea de comandos del kernel, y en el caso del gestor de usuario, las variables pasadas por el gestor del sistema. Después de que esas variables se hayan fusionado, persistirán hasta que se anulen, incluso si el gestor se recarga o se reejecuta. En el caso del gestor de usuario, estas variables también son heredadas por los procesos generados por el gestor. Al igual que con DefaultEnvironment=, este bloque de entorno es interno, y los cambios no se reflejan en el /proc/PID/environ del gestor.

Establecer variables de entorno para el proceso gestor puede ser útil para modificar su comportamiento. Consulte Variables de Entorno Conocidas[3] para una descripción de algunas variables entendidas por systemd.

Se admite la expansión simple de especificadores "%", véase más abajo para obtener una lista de los especificadores admitidos.

Añadido en la versión 248.

SPECIFIERS

Various directives accept a list of specifiers, which are expanded when the service manager is processing the directive. The following specifiers are understood:

Especificador Significado Detalles
"%a" Arquitectura Una cadena corta que identifica la arquitectura del sistema local. Una cadena como x86, x86-64 o arm64. Consulte las arquitecturas definidas para ConditionArchitecture= en systemd.unit(5) para una lista completa.
"%A" Versión de la imagen del sistema operativo El identificador de versión de la imagen del sistema operativo del sistema en ejecución, tal como se lee del campo IMAGE_VERSION= de /etc/os-release. Si no está establecido, se resuelve como una cadena vacía. Consulte os-release(5) para más información.
"%b" ID de arranque El ID de arranque del sistema en ejecución, formateado como cadena. Consulte random(4) para más información.
"%B" ID de compilación del sistema operativo El identificador de compilación del sistema operativo del sistema en ejecución, tal como se lee del campo BUILD_ID= de /etc/os-release. Si no está establecido, se resuelve como una cadena vacía. Consulte os-release(5) para más información.
"%H" Nombre del host El nombre del host del sistema en ejecución.
"%l" Nombre de host corto El nombre del host del sistema en ejecución, truncado en el primer punto para eliminar cualquier componente de dominio.
"%m" ID de máquina El ID de máquina del sistema en ejecución, formateado como cadena. Consulte machine-id(5) para más información.
"%M" Identificador de imagen del sistema operativo El identificador de imagen del sistema operativo del sistema en ejecución, tal como se lee del campo IMAGE_ID= de /etc/os-release. Si no está establecido, se resuelve como una cadena vacía. Consulte os-release(5) para más información.
"%o" ID del sistema operativo El identificador del sistema operativo del sistema en ejecución, tal como se lee del campo ID= de /etc/os-release. Consulte os-release(5) para más información.
"%v" Versión del kernel Idéntico a la salida de uname -r.
"%w" ID de versión del sistema operativo La versió

"%A" Architecture name (full) The architecture name of the running system, as read from ID_ARCH= in /etc/os-release. If not set, this expands to an empty string. See os-release(5) for more information.
"%b" Base operating system name The operating system name of the running system, as read from ID= in /etc/os-release. If not set, this expands to an empty string. See os-release(5) for more information.
"%B" Base operating system name (full) The operating system name of the running system, as read from ID_LIKE= in /etc/os-release. If not set, this expands to an empty string. See os-release(5) for more information.
"%c" Operating system CPE name The operating system CPE name of the running system, as read from CPE_NAME= in /etc/os-release. If not set, this expands to an empty string. See os-release(5) for more information.
"%C" Canonical operating system name The canonical operating system name of the running system, as read from PRETTY_NAME= in /etc/os-release. If not set, this expands to an empty string. See os-release(5) for more information.
"%e" Kernel version The kernel version of the running system, as read from uname(2).
"%E" Kernel version (full) The kernel version of the running system, as read from uname(2) (e.g. 4.19.13-1-default).
"%H" Hostname The hostname of the running system.
"%h" Host name (short) The hostname of the running system, shortened to the first label (i.e. up to the first dot).
"%L" Kernel release The kernel release of the running system, as read from uname(2).
"%m" Machine hardware name The machine hardware name of the running system, as read from uname(2).
"%M" Machine hardware name (full) The machine hardware name of the running system, as read from MACHINE_HW_NAME= in /etc/os-release. If not set, this expands to an empty string. See os-release(5) for more information.
"%n" Node name The node name of the running system, as read from uname(2).
"%o" Operating system name The operating system name of the running system, as read from NAME= in /etc/os-release. If not set, this expands to an empty string. See os-release(5) for more information.
"%O" Operating system name (full) The operating system name of the running system, as read from PRETTY_NAME= in /etc/os-release. If not set, this expands to an empty string. See os-release(5) for more information.
"%p" Process ID The process ID of the unit being started or executed. This is only available for processes started by systemd.
"%P" PID of the service manager instance The process ID of the service manager instance itself.
"%r" Operating system release The operating system release of the running system, as read from VERSION_ID= in /etc/os-release. If not set, this expands to an empty string. See os-release(5) for more information.
"%R" Operating system variant ID The operating system variant identifier of the running system, as read from VARIANT_ID= in /etc/os-release. If not set, this resolves to an empty string. See os-release(5) for more information.
"%T" Directory for temporary files This is either /tmp or the path "$TMPDIR", "$TEMP" or "$TMP" are set to. (Note that the directory may be specified without a trailing slash.)
"%V" Directory for larger and persistent temporary files This is either /var/tmp or the path "$TMPDIR", "$TEMP" or "$TMP" are set to. (Note that the directory may be specified without a trailing slash.)
"%h" User home directory This is the home directory of the user running the service manager instance.
"%u" Username This is the username of the user running the service manager instance.
"%U" User id This is the user id of the user running the service manager instance.
"%g" Primary group This is the primary group of the user running the service manager instance.
"%G" Primary group id This is the primary group id of the user running the service manager instance.
"%s" User shell This is the shell of the user running the service manager instance.
"%%" Single percent sign Use "%%" in place of "%" to specify a single percent sign.
