SYSTEM(3P) Manual de Programador de POSIX SYSTEM(3P)

PROLOG

Esta página del manual forma parte del Manual del Programador de POSIX. La implementación de esta interfaz en Linux puede diferir (consulte la página del manual de Linux correspondiente para conocer los detalles del comportamiento en Linux), o la interfaz puede no estar implementada en Linux.

NOMBRE

system — ejecutar un comando

SINOPSIS

#include <stdlib.h>
int system(const char *command);

DESCRIPCIÓN

La funcionalidad descrita en esta página de referencia está alineada con el estándar ISO C. Cualquier conflicto entre los requisitos descritos aquí y el estándar ISO C es no intencional. Este volumen de POSIX.1-2017 se remite al estándar ISO C.

Si command es un puntero nulo, la función system() determinará si el entorno del host tiene un procesador de comandos. Si command no es un puntero nulo, la función system() pasará la cadena apuntada por command a ese procesador de comandos para ser ejecutada de una manera definida por la implementación; esto podría hacer que el programa que llama a system() se comporte de manera no conforme o que termine.

La función system() se comportará como si se creara un proceso hijo usando fork(), y el proceso hijo invocara la utilidad sh usando execl() de la siguiente manera:

execl(<ruta_shell>, "sh", "-c", command, (char *)0);

donde <ruta_shell> es una ruta no especificada para la utilidad sh. No se especifica si los manejadores registrados con pthread_atfork() se llaman como parte de la creación del proceso hijo.

La función system() ignorará las señales SIGINT y SIGQUIT, y bloqueará la señal SIGCHLD, mientras espera que el comando termine. Si esto pudiera causar que la aplicación pierda una señal que la hubiera matado, entonces la aplicación debería examinar el valor de retorno de system() y tomar la acción apropiada para la aplicación si el comando terminó debido a la recepción de una señal.

La función system() no afectará el estado de terminación de ningún hijo de los procesos que llaman, excepto los procesos que ella misma crea.

La función system() no retornará hasta que el proceso hijo haya terminado.

La función system() no es necesariamente segura para hilos (thread-safe).

VALOR DE RETORNO

Si command es un puntero nulo, system() devolverá un valor distinto de cero para indicar que hay un procesador de comandos disponible, o cero si no hay ninguno disponible. La función system() siempre devolverá un valor distinto de cero cuando command sea NULL.

Si command no es un puntero nulo, system() devolverá el estado de terminación del intérprete del lenguaje de comandos en el formato especificado por waitpid(). El estado de terminación será tal como se define para la utilidad sh; de lo contrario, el estado de terminación no se especifica. Si algún error impide que el intérprete del lenguaje de comandos se ejecute después de la creación del proceso hijo, el valor de retorno de system() será como si el intérprete del lenguaje de comandos hubiera terminado usando exit(127) o _exit(127). Si no se puede crear un proceso hijo, o si no se puede obtener el estado de terminación del intérprete del lenguaje de comandos, system() devolverá -1 y establecerá errno para indicar el error.

ERRORES

La función system() puede establecer valores de errno como los descritos por fork().

Además, system() puede fallar si:

ECHILD
El estado del proceso hijo creado por system() ya no está disponible.

Las siguientes secciones son informativas.

EJEMPLOS

Ninguno.

USO POR LA APLICACIÓN

Si el valor de retorno de system() no es -1, su valor puede decodificarse mediante el uso de las macros descritas en <sys/wait.h>. Para mayor comodidad, estas macros también se proporcionan en <stdlib.h>.

Tenga en cuenta que, aunque system() debe ignorar SIGINT y SIGQUIT y bloquear SIGCHLD mientras espera que el hijo termine, el manejo de señales en el comando ejecutado es como se especifica en fork() y exec. Por ejemplo, si SIGINT se está capturando o está configurado como SIG_DFL cuando se llama a system(), entonces el hijo se inicia con el manejo de SIGINT configurado como SIG_DFL.

Ignorar SIGINT y SIGQUIT en el proceso padre evita problemas de coordinación (dos procesos leyendo de la misma terminal, por ejemplo) cuando el comando ejecutado ignora o captura una de las señales. También suele ser la acción correcta cuando el usuario ha dado un comando a la aplicación para que sea ejecutado sincrónicamente (como en el comando '!' en muchas aplicaciones interactivas). En cualquier caso, la señal solo debe entregarse al proceso hijo, no a la aplicación en sí. Hay una situación en la que ignorar las señales podría tener un efecto menor al deseado. Esto ocurre cuando la aplicación utiliza system() para realizar alguna tarea invisible para el usuario. Si el usuario escribiera el carácter de interrupción ("^C", por ejemplo) mientras system() se utiliza de esta manera, uno esperaría que la aplicación se matara, pero solo se mata el comando ejecutado. Las aplicaciones que utilizan system() de esta manera deben comprobar cuidadosamente el estado de retorno de system() para ver si el comando ejecutado tuvo éxito y deben tomar las medidas apropiadas cuando el comando falla.

Bloquear SIGCHLD mientras se espera que el hijo termine evita que la aplicación capture la señal y obtenga el estado del proceso hijo de system() antes de que system() pueda obtener el estado por sí misma.

El contexto en el que la utilidad se ejecuta finalmente puede diferir de aquel en el que se llamó a system(). Por ejemplo, los descriptores de archivo que tienen establecida la bandera FD_CLOEXEC se cierran, y el ID del proceso y el ID del proceso padre son diferentes. Además, si la utilidad ejecutada cambia sus variables de entorno o su directorio de trabajo actual, ese cambio no se reflejará en el contexto del llamador.

No hay una forma definida para que una aplicación encuentre la ruta específica del shell. Sin embargo, confstr() puede proporcionar un valor para PATH que garantiza encontrar la utilidad sh.

Usar la función system() en más de un hilo en un proceso o cuando la señal SIGCHLD está siendo manipulada por más de un hilo en un proceso puede producir resultados inesperados.

FUNDAMENTO

La función system() no debe ser utilizada por programas que hayan establecido privilegios de ID de usuario (o grupo). En su lugar, se deben utilizar las funciones de la familia fork() y exec (excepto execlp() y execvp()). Esto evita cualquier manipulación imprevista del entorno del usuario que pudiera causar la ejecución de comandos no previstos por el programa llamador.

Existen tres niveles de especificación para la función system(). El estándar ISO C proporciona el más básico. Requiere que la función exista y define una forma para que una aplicación consulte si existe un intérprete de lenguaje de comandos. No dice nada sobre el lenguaje de comandos o el entorno en el que se interpreta el comando.

POSIX.1-2008 impone restricciones adicionales a system(). Requiere que, si existe un intérprete de lenguaje de comandos, el entorno sea como se especifica en fork() y exec. Esto garantiza, por ejemplo, que close-on-exec funcione, que los bloqueos de archivo no se hereden y que el ID del proceso sea diferente. También especifica el valor de retorno de system() cuando la línea de comandos se puede ejecutar, dando así a la aplicación cierta información sobre el estado de finalización del comando.

Finalmente, POSIX.1-2008 requiere que el comando se interprete como en el lenguaje de comandos del shell definido en el volumen de Shell y Utilidades de POSIX.1-2017.

Tenga en cuenta que system(NULL) debe devolver un valor distinto de cero, lo que indica que existe un intérprete de lenguaje de comandos

NAME

system - execute a system command

SYNOPSIS

#include <stdlib.h>

int system(const char *cmd);

DESCRIPTION

The system() utility shall execute cmd in a manner equivalent to executing the command processor (shell) that would result from executing the command

sh -c cmd

in a separate invocation of the shell. The argument cmd is a character string containing the command to be executed.

If cmd is a NULL pointer, system() shall return a non-zero value if and only if the command processor is available.

The status returned by system() is interpreted by the calling process. If the command processor is invoked, the return value shall be the exit status of the command processor. If the command processor is not invoked, the return value shall be -1 and errno shall be set to indicate the error.

The system() function shall ignore SIGCHLD, SIGINT, and SIGQUIT while setting up and executing the command. SIGINT and SIGQUIT shall be ignored if the command processor is terminated by a signal. The state of SIGCHLD, SIGINT, and SIGQUIT shall be restored before system() returns.

The system() function shall not return until the command initiated by system() terminates.

RETURN VALUE

If cmd is NULL, system() returns a non-zero value if the command processor is available, and 0 otherwise. Otherwise, system() returns the exit status of the command processor. If the command processor cannot be executed, system() returns -1 and sets errno to indicate the error.

The exit status of the command processor is normally the exit status of the command specified by cmd. If the command processor is terminated by a signal, the return value is normally 128 plus the signal number. The exact interpretation is implementation-dependent.

ERRORS

EINVAL
The value of cmd is invalid (e.g., too long).

ENOMEM
Not enough memory available to create a child process.

ECHILD
A child process was already created by system(), but has not yet terminated.

EAGAIN
Not enough resources available to create a child process.

Other errors may be set by fork(2) or execve(2).

EXAMPLES

Execute the ls -l command and print its output.

#include <stdlib.h>
#include <stdio.h>
#include <errno.h>

int
main(void)
{
    int ret;

    ret = system("ls -l");
    if (ret == -1) {
        perror("system");
        return 1;
    } else {
        printf("Command exited with status %d\n", ret);
    }

    /* Check if shell is available */
    if (system(NULL) == 0) {
        printf("Command processor is not available.\n");
    }

    return 0;
}

APPLICATION USAGE

The POSIX standard leaves the interpretation of the exit status somewhat open. The common convention is that if the command is run and terminates normally, the exit status is that of the command. If the command is terminated by a signal, the exit status is 128 + signal number. For example, if the command is killed by signal 9 (SIGKILL), the exit status will be 137.

If the cmd argument is NULL, system() can be used to check if a command interpreter exists. A return value of 0 indicates that the command interpreter is not available, while a non-zero value indicates that it is.

RATIONALE

The POSIX.1‐2008 standard's description of system() explicitly states that systems conforming to that standard must have a command language interpreter. It also states that system(NULL) should return zero if and only if the command language interpreter cannot be invoked. This is somewhat contradictory. If a system conforms to POSIX.1, it must have a command language interpreter, and therefore system(NULL) should return non-zero. It is therefore permissible for the system() function on such a system to implement the behavior specified by the ISO C standard as long as it is understood that the implementation does not conform to POSIX.1‐2008 if system(NULL) returns zero.

It was explicitly decided that when command is NULL, system() should not be required to check to make sure that the command language interpreter actually exists with the correct mode, that there are enough processes to execute it, and so on. The call system(NULL) could, theoretically, check for such problems as too many existing child processes, and return zero. However, it would be inappropriate to return zero due to such a (presumably) transient condition. If some condition exists that is not under the control of this application and that would cause any system() call to fail, that system has been rendered non-conforming.

Early drafts required, or allowed, system() to return with errno set to [EINTR] if it was interrupted with a signal. This error return was removed, and a requirement that system() not return until the child has terminated was added. This means that if a waitpid() call in system() exits with errno set to [EINTR], system() must reissue the waitpid(). This change was made for two reasons:

1.
There is no way for an application to clean up if system() returns [EINTR], short of calling wait(), and that could have the undesirable effect of returning the status of children other than the one started by system().
2.
While it might require a change in some historical implementations, those implementations already have to be changed because they use wait() instead of waitpid().

Note that if the application is catching SIGCHLD signals, it will receive such a signal before a successful system() call returns.

To conform to POSIX.1‐2008, system() must use waitpid(), or some similar function, instead of wait().

The following code sample illustrates how system() might be implemented on an implementation conforming to POSIX.1‐2008.

#include <signal.h>
int system(const char *cmd)
{
    int stat;
    pid_t pid;
    struct sigaction sa, savintr, savequit;
    sigset_t saveblock;
    if (cmd == NULL)
        return(1);
    sa.sa_handler = SIG_IGN;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = 0;
    sigemptyset(&savintr.sa_mask);
    sigemptyset(&savequit.sa_mask);
    sigaction(SIGINT, &sa, &savintr);
    sigaction(SIGQUIT, &sa, &savequit);
    sigaddset(&sa.sa_mask, SIGCHLD);
    sigprocmask(SIG_BLOCK, &sa.sa_mask, &saveblock);
    if ((pid = fork()) == 0) {
        sigaction(SIGINT, &savintr, (struct sigaction *)0);
        sigaction(SIGQUIT, &savequit, (struct sigaction *)0);
        sigprocmask(SIG_SETMASK, &saveblock, (sigset_t *)0);
        execl("/bin/sh", "sh", "-c", cmd, (char *)0);
        _exit(127);
    }
    if (pid == -1) {
        stat = -1; /* errno comes from fork() */
    } else {
        while (waitpid(pid, &stat, 0) == -1) {
            if (errno != EINTR){
                stat = -1;
                break;
            }
        }
    }
    sigaction(SIGINT, &savintr, (struct sigaction *)0);
    sigaction(SIGQUIT, &savequit, (struct sigaction *)0);
    sigprocmask(SIG_SETMASK, &saveblock, (sigset_t *)0);
    return(stat);
}

Note that, while a particular implementation of system() (such as the one above) can assume a particular path for the shell, such a path is not necessarily valid on another system. The above example is not portable, and is not intended to be.

Note also that the above example implementation is not thread-safe. Implementations can provide a thread-safe system() function, but doing so involves complications such as how to restore the signal dispositions for SIGINT and SIGQUIT correctly if there are overlapping calls, and how to deal with cancellation. The example above would not restore the signal dispositions and would leak a process ID if cancelled. This does not matter for a non-thread-safe implementation since canceling a non-thread-safe function results in undefined behavior (see Section 2.9.5.2, Cancellation Points). To avoid leaking a process ID, a thread-safe implementation would need to terminate the child process when acting on a cancellation.

One reviewer suggested that an implementation of system() might want to use an environment variable such as SHELL to determine which command interpreter to use. The supposed implementation would use the default command interpreter if the one specified by the environment variable was not available. This would allow a user, when using an application that prompts for command lines to be processed using system(), to specify a different command interpreter. Such an implementation is discouraged. If the alternate command interpreter did not follow the command line syntax specified in the Shell and Utilities volume of POSIX.1‐2017, then changing SHELL would render system() non-conforming. This would affect applications that expected the specified behavior from system(), and since the Shell and Utilities volume of POSIX.1‐2017 does not mention that SHELL affects system(), the application would not know that it needed to unset SHELL.
