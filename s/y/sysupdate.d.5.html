SYSUPDATE.D(5) sysupdate.d SYSUPDATE.D(5)

NOMBRE

sysupdate.d - Archivos de definición de transferencia para actualizaciones automáticas

SINOPSIS

/etc/sysupdate.d/*.transfer
/run/sysupdate.d/*.transfer
/usr/local/lib/sysupdate.d/*.transfer
/usr/lib/sysupdate.d/*.transfer

DESCRIPCIÓN

Estos archivos describen cómo se actualizarán recursos específicos en el sistema local desde una fuente remota. Cada uno de estos archivos define una transferencia: típicamente una fuente HTTP/HTTPS remota; y un archivo, directorio o partición local como destino. Esto puede ser utilizado como un mecanismo de actualización simple, automático y atómico para el propio sistema operativo, para contenedores, servicios portátiles o imágenes de extensión del sistema —pero de hecho puede ser usado para actualizar cualquier tipo de archivo desde una fuente remota.

El comando systemd-sysupdate(8) lee estos archivos y los utiliza para determinar qué recursos locales deben ser actualizados, y luego ejecuta la actualización.

Tanto la fuente HTTP/HTTPS remota como el destino local suelen existir en múltiples versiones concurrentes, para implementar esquemas de actualización flexibles, por ejemplo, actualizaciones A/B (o un superconjunto de ellas, por ejemplo, A/B/C, A/B/C/D,...).

Cada archivo *.transfer define una transferencia, es decir, describe un recurso a actualizar. Típicamente, múltiples de estos archivos (es decir, múltiples de tales transferencias) se definen juntos, y se vinculan mediante un identificador de versión común para actualizar múltiples recursos a la vez en cada operación de actualización, por ejemplo, para actualizar un kernel, un sistema de archivos raíz y una partición Verity en una operación combinada y sincronizada, de modo que solo una actualización combinada de los tres constituya una actualización completa. Llamaremos a tal colección de transferencias un objetivo. systemd-sysupdate(8) siempre opera en un solo objetivo.

Las transferencias pueden agruparse en conjuntos que pueden ser habilitados o deshabilitados individualmente por el administrador del sistema, llamados "Características Opcionales": sysupdate.features(5).

Cada archivo *.transfer contiene tres secciones: [Transfer], [Source] y [Target].

MODO BÁSICO DE OPERACIÓN

Las actualizaciones del sistema operativo basadas en imágenes de disco suelen constar de múltiples recursos diferentes que deben actualizarse juntos, por ejemplo, una actualización segura del sistema operativo podría consistir en una imagen del sistema de archivos raíz para colocar en una partición, una imagen de partición de datos de integridad Verity coincidente, y una imagen del kernel preparada para arrancar en la combinación de las dos particiones. Los dos primeros recursos son archivos que se descargan y se colocan en una partición de disco, el último es un archivo que se descarga y se coloca en un archivo regular en el sistema de archivos de arranque (por ejemplo, la partición del sistema EFI).

Por lo tanto, durante una actualización de un sistema operativo hipotético "foobarOS" a una versión hipotética 47, se deben realizar las siguientes operaciones:

1.Un archivo "https://download.example.com/foobarOS_47.root.xz" debe ser descargado, descomprimido y escrito en una partición previamente no utilizada con el tipo de partición GPT UUID 4f68bce3-e8cd-4db1-96e7-fbcaf984b709 para x86-64, según la Especificación de Particiones Descubribles[1].
2.De manera similar, un archivo "https://download.example.com/foobarOS_47.verity.xz" debe ser descargado, descomprimido y escrito en una partición previamente vacía con el tipo de partición GPT UUID de 2c7357ed-ebd2-46d9-aec1-23d437ec2bf5 (es decir, el tipo de partición para la información de integridad de Verity para sistemas de archivos raíz x86-64).
3.Finalmente, un archivo "https://download.example.com/foobarOS_47.efi" (un kernel unificado, según la Especificación del Cargador de Arranque[2] Tipo #2) debe ser descargado, descomprimido y escrito en el sistema de archivos $BOOT, es decir, a EFI/Linux/foobarOS_47.efi en la partición ESP o XBOOTLDR.

La generalización independiente de la versión de esto sería (usando el marcador especial ""@v"" como comodín para el identificador de versión):

1.Una transferencia de un archivo "https://download.example.com/foobarOS_@v.root.xz" → una partición GPT local, previamente vacía, de tipo 4f68bce3-e8cd-4db1-96e7-fbcaf984b709, con la etiqueta establecida a ""foobarOS_@v"".
2.Una transferencia de un archivo "https://download.example.com/foobarOS_@v.verity.xz" → una partición GPT local, previamente vacía, de tipo 2c7357ed-ebd2-46d9-aec1-23d437ec2bf5 (es decir, el tipo de partición para la información de integridad Verity para sistemas de archivos raíz x86-64), con la etiqueta establecida a ""foobarOS_@v_verity"".
3.Una transferencia de un archivo "https://download.example.com/foobarOS_@v.efi" → un archivo local $BOOT/EFI/Linux/foobarOS_@v.efi.

Una actualización solo puede completarse si las URLs relevantes proporcionan sus recursos para la misma versión, es decir, para el mismo valor de ""@v"".

Lo anterior puede traducirse en tres archivos *.transfer en sysupdate.d/, uno para cada recurso a transferir. Los archivos *.transfer configuran el tipo de descarga y el lugar donde escribir la descarga (es decir, si en una partición o en un archivo en el sistema de archivos). Lo más importante es que estos archivos contienen los patrones de URL, nombre de partición y nombre de archivo que se muestran arriba y que describen cómo se llaman estos recursos en la fuente y cómo se llamarán en el destino.

Para enumerar las versiones disponibles y determinar los candidatos para actualizar, se necesita un mecanismo para listar los archivos adecuados:

•Para particiones: la tabla de particiones GPT circundante contiene una lista de particiones definidas, incluyendo un UUID de tipo de partición y una etiqueta de partición (en este esquema, la etiqueta de partición juega un papel para la partición similar al nombre de archivo para un archivo regular).
•Para archivos regulares: la lista del directorio que contiene los archivos proporciona una lista de archivos existentes de una manera sencilla.
•Para fuentes HTTP/HTTPS se utiliza un esquema simple: un archivo de manifiesto SHA256SUMS, siguiendo el formato definido por sha256sum(1), enumera nombres de archivo y sus hashes SHA256.

Las transferencias se realizan en orden alfabético de los nombres de los archivos .transfer en los que se definen. Primero, los datos del recurso se descargan directamente en un archivo/directorio/partición de destino. Una vez completado esto para todas las transferencias definidas, en un segundo paso, los archivos/directorios/particiones se renombran a sus nombres finales según lo definido por el MatchPattern= del destino, nuevamente en el orden en que dictan los nombres de los archivos de transferencia. Este paso no es atómico, sin embargo, se garantiza que se ejecutará estrictamente en orden con la sincronización de disco adecuada. Típicamente, al actualizar un SO, una de las transferencias define el punto de entrada al arrancar. Por lo tanto, generalmente es una buena idea ordenar los recursos a través de los nombres de los archivos de configuración de transferencia para que el punto de entrada se escriba al último, asegurando que cualquier terminación anormal no deje un punto de entrada cuyo respaldo no esté establecido todavía. En el ejemplo anterior, tendría sentido establecer la imagen del kernel EFI al último y, por lo tanto, dar a su archivo de configuración de transferencia el nombre alfabéticamente último.

Ver más abajo para un ejemplo extendido y más específico basado en lo anterior.

TIPOS DE RECURSOS

Cada archivo de transferencia define un recurso de origen a transferir a un recurso de destino. Se soportan los siguientes tipos de recursos:

1.Los recursos de tipo "url-file" encapsulan un archivo en un servidor web, referenciado a través de una URL HTTP o HTTPS. Cuando se realiza una actualización, el archivo se descarga y se descomprime y luego se escribe en el archivo o partición de destino. Este tipo de recurso solo está disponible para fuentes, no para destinos. La lista de versiones disponibles de los recursos de este tipo está codificada en archivos de manifiesto SHA256SUMS, acompañados de firmas desprendidas SHA256SUMS.gpg.
2.El tipo de recurso "url-tar" es similar, pero el archivo debe ser un archivo .tar. Cuando se realiza una actualización, el archivo se descomprime y se desempaqueta en un directorio o subvolumen btrfs. Este tipo de recurso solo está disponible para fuentes, no para destinos. Al igual que "url-file", la enumeración de versiones de "url-tar" utiliza archivos SHA256SUMS, autenticados a través de SHA256SUMS.gpg.

Este sitio no está asociado de ninguna forma con Arch Linux ni afiliado a este proyecto. El contenido es únicamente una traducción de las páginas del manual de Arch publicadas en man.archlinux.org.

3.El tipo de recurso "archivo-regular" encapsula un archivo local en disco. Durante las actualizaciones, el archivo se descomprime y se escribe en el archivo o partición de destino. Este tipo de recurso está disponible tanto como fuente como destino. Al actualizar, no se realiza ninguna verificación de integridad o autenticación para los recursos de este tipo.
4.El tipo de recurso "partición" es similar a "archivo-regular" y encapsula una partición GPT en disco. Al actualizar, la partición debe existir previamente y tener el tipo de partición GPT correcto. Una partición cuya etiqueta de partición GPT esté configurada como "_empty" se considera vacía y candidata para colocar un recurso recién descargado. La etiqueta de partición GPT se utiliza para almacenar información de versión, una vez que una partición se actualiza. Este tipo de recurso solo está disponible para recursos de destino.
5.El tipo de recurso "tar" encapsula archivos de archivo .tar locales. Cuando se realiza una actualización, los archivos se descomprimen y desempaquetan en un directorio de destino o un subvolumen btrfs. El comportamiento de "tar" y "url-tar" es generalmente similar, pero este último descarga de fuentes remotas y realiza comprobaciones de integridad y autenticación, mientras que el primero no. El tipo de recurso "tar" solo está disponible para recursos de origen.
6.El tipo de recurso "directorio" encapsula árboles de directorios locales. Este tipo está disponible tanto para recursos de origen como de destino. Si se realiza una actualización en un recurso de origen de este tipo, se realiza una copia recursiva del directorio.
7.El tipo de recurso "subvolumen" es idéntico a "directorio", excepto cuando se utiliza como destino, en cuyo caso el árbol de archivos se coloca en un subvolumen btrfs en lugar de un directorio simple, si el sistema de archivos subyacente lo admite (es decir, es btrfs).

Como ya se indicó, solo se admite un subconjunto de combinaciones de tipos de recursos de origen y destino:

PATRONES DE COINCIDENCIA

Tanto los recursos de origen como los de destino suelen existir en múltiples versiones simultáneamente. Una operación de actualización se realiza siempre que la versión más reciente de las fuentes sea más reciente que la versión más reciente de los destinos. Para determinar la versión más reciente de los recursos, se utiliza un listado de directorios, un listado de particiones o un listado de manifiestos, se selecciona un subconjunto de entradas que cumplan los criterios de ese listado, y el identificador de versión se extrae de los nombres de archivo o las etiquetas de partición de estas entradas seleccionadas. La selección de subconjuntos y la extracción del identificador de versión (además de otros metadatos potenciales) se realizan mediante patrones de coincidencia, configurados en
MatchPattern= en las secciones [Source] y [Target]. Estos patrones son cadenas que describen cómo se nombran los archivos o las particiones, con comodines con nombre para campos específicos como el identificador de versión. Los siguientes comodines están definidos:

Tabla 2. Comodines de Patrones de Coincidencia

Comodín Descripción Formato Notas
"@v" Identificador de versión Cadena de versión válida Obligatorio
"@u" UUID de partición GPT Cadena UUID válida de 128 bits Solo relevante si el tipo de recurso de destino elegido es partición
"@f" Banderas de partición GPT Entero hexadecimal formateado Solo relevante si el tipo de recurso de destino elegido es partición
"@a" Bandera de partición GPT NoAuto "0" o "1" Controla el bit NoAuto de las banderas de partición GPT, según la Especificación de Particiones Descubribles[1]; solo relevante si el tipo de recurso de destino elegido es partición
"@g" Bandera de partición GPT GrowFileSystem "0" o "1" Controla el bit GrowFileSystem de las banderas de partición GPT, según la Especificación de Particiones Descubribles[1]; solo relevante si el tipo de recurso de destino elegido es partición
"@r" Bandera de solo lectura "0" o "1" Controla el bit ReadOnly de las banderas de partición GPT, según la Especificación de Particiones Descubribles[1] y otras banderas de solo lectura de salida, ver ReadOnly= a continuación
"@t" Hora de modificación del archivo Entero decimal formateado, µs desde la época UNIX 1 de enero de 1970 Solo relevante si el tipo de recurso de destino elegido es archivo-regular
"@m" Modo de acceso al archivo Entero octal formateado, al estilo UNIX Solo relevante si el tipo de recurso de destino elegido es archivo-regular
"@s" Tamaño del archivo después de la descompresión Entero decimal formateado Útil para medir el progreso y mejorar la lógica de asignación de particiones
"@d" Intentos realizados Entero decimal formateado Útil al operar con archivos de imagen del kernel, según la Evaluación Automática de Arranque[3]
"@l" Intentos restantes Entero decimal formateado Útil al operar con archivos de imagen del kernel, según la Evaluación Automática de Arranque[3]
"@h" Hash SHA256 del archivo comprimido 64 caracteres hexadecimales El hash SHA256 del archivo comprimido; no es útil para url-archivo o url-tar donde el hash SHA256 ya está incluido en el archivo de manifiesto de todos modos

De estos comodines, solo
"@v" debe estar presente en un patrón válido; todos los demás comodines son opcionales. Cada comodín se puede usar como máximo una vez en cada patrón. Un patrón típico para hacer coincidir una imagen de origen del sistema de archivos podría ser "MatchPattern=foobar_@v.raw.xz", es decir, cualquier archivo cuyo nombre comience con "foobar_", seguido de un ID de versión y sufijo ".raw.xz".

No confunda el prefijo del comodín de coincidencia de patrones "@" con el prefijo de expansión del especificador "%". El primero encapsula una parte variable de una cadena de patrón de coincidencia, mientras que el segundo son atajos simples que se expanden mientras se analizan los archivos de inserción. Para obtener detalles sobre los especificadores, consulte a continuación.

OPCIONES DE SECCIÓN [TRANSFER]

Esta sección define las propiedades generales de esta transferencia.

MinVersion=

Especifica la versión mínima requerida para que esta transferencia tenga lugar. Si los patrones de origen o destino en esta definición de transferencia coinciden con archivos más antiguos que esta versión, se considerarán obsoletos y nunca se tendrán en cuenta para la operación de actualización.

Añadido en la versión 251.

ProtectVersion=

Toma una o más cadenas de versión para marcarlas como "protegidas". Las versiones protegidas nunca se eliminan al hacer espacio para versiones nuevas y actualizadas. Esto es útil para garantizar que la versión del sistema operativo que se está ejecutando actualmente (o los recursos auxiliares asociados con ella) no se reemplace/sobrescriba durante las actualizaciones, para evitar corrupciones del sistema de archivos en tiempo de ejecución.

Al igual que muchas de las configuraciones en estos archivos de configuración, esta configuración admite la expansión de especificadores. Es particularmente útil establecer esta configuración en uno de los especificadores "%A", "%B" o "%w" para referirse automáticamente a la versión actual del sistema operativo del sistema en ejecución. Ver a continuación para más detalles sobre los especificadores compatibles.

Añadido en la versión 251.

Verify=

Toma un valor booleano, por defecto es sí. Controla si se verifican criptográficamente los recursos descargados (específicamente: valida las firmas GPG para los archivos de manifiesto SHA256SUMS descargados, a través de sus archivos de firma adjuntos SHA256SUMS.gpg en combinación con el keyring del sistema /usr/lib/systemd/import-pubring.pgp o /etc/systemd/import-pubring.pgp).

Esta opción es esencial para proporcionar garantías de integridad para los recursos descargados y, por lo tanto, debe dejarse habilitada, fuera de los entornos de prueba.

Tenga en cuenta que los archivos de carga útil descargados se verifican incondicionalmente contra los hashes SHA256 enumerados en el manifiesto. Esta opción solo controla si se verifican las firmas de estos manifiestos.

Esta opción solo tiene efecto si el tipo de recurso de origen se selecciona como url-archivo o url-tar, ya que la comprobación de integridad y autenticación solo está disponible para transferencias desde fuentes remotas.

Añadido en la versión 251.

ChangeLog=

Opcionalmente toma una URL presentable por humanos a un sitio web que contiene un registro de cambios del recurso que se está actualizando.

Este puede establecerse varias veces en una única definición de transferencia. Si se establece varias veces, los valores se recopilan en una lista de URLs. Añadir un valor de cadena vacía borrará la lista existente de todos los valores.

Esta configuración admite la expansión de especificadores. Ver abajo para detalles sobre los especificadores admitidos. Esta configuración también expandirá el patrón comodín "@v". Ver arriba para detalles.

Añadido en la versión 257.

AppStream=

Opcionalmente toma una URL a un archivo XML de **AppStream catalog**[4]. Esto puede ser utilizado por centros de software (como GNOME Software o KDE Discover) para presentar metadatos enriquecidos sobre los recursos que se están actualizando. Esto incluye nombres de visualización, registros de cambios, iconos y más. El catálogo especificado debe incluir **metadatos especiales**[5] para ser asociado correctamente con systemd-sysupdate(8) por los centros de software.

Esta configuración admite la expansión de especificadores. Ver abajo para detalles sobre los especificadores admitidos.

Añadido en la versión 257.

Features=

Una lista separada por espacios de sysupdate.features(5) a las que pertenece esta transferencia, por nombre. Esta opción puede especificarse más de una vez, en cuyo caso la lista especificada de características se fusiona. Si se asigna una cadena vacía a esta opción, la lista se restablece y todas las asignaciones anteriores no tendrán efecto. Por ejemplo: "Features=foo bar" especifica que la transferencia pertenece a "foo.feature" y "bar.feature".

Si la lista de características está vacía, esta transferencia se usa siempre. Si esta transferencia pertenece a más de una característica, se utilizará si *cualquiera* de las características listadas está habilitada. Un nombre que no corresponde a una característica definida se resolverá en una característica implícita que siempre está deshabilitada.

Añadido en la versión 257.

RequisiteFeatures=

Esto es como Features=, excepto que *todas* las características listadas aquí deben estar habilitadas para que esta transferencia se habilite. Si ambas opciones se especifican, ambas se aplican: la transferencia se habilitará solo si todas las características especificadas aquí están habilitadas, y al menos una característica listada en Features= está habilitada.

Añadido en la versión 257.

[SOURCE] OPCIONES DE SECCIÓN

Esta sección define las propiedades de la fuente de transferencia.

Type=

Especifica el tipo de recurso de la fuente para la transferencia. Toma uno de url-file, url-tar, tar, regular-file, directory o subvolume. Para detalles sobre los tipos de recursos, ver arriba. Esta opción es obligatoria.

Tenga en cuenta que solo se admiten ciertas combinaciones de tipos de recursos de origen y destino, ver arriba.

Añadido en la versión 251.

Path=

Especifica dónde encontrar las versiones de origen de este recurso.

Si el tipo de origen se selecciona como url-file o url-tar, debe ser una URL HTTP/HTTPS. La URL se sufija con /SHA256SUMS para adquirir el archivo de manifiesto, con /SHA256SUMS.gpg para adquirir la firma separada del mismo, y con los nombres de archivo listados en el archivo de manifiesto en caso de que se ejecute una actualización y se descargue un recurso.

Para todos los demás tipos de recursos de origen, debe ser una ruta local en el sistema de archivos, que se refiere a un directorio local donde encontrar las versiones de este recurso.

Añadido en la versión 251.

MatchPattern=

Especifica uno o más patrones de coincidencia de nombres de archivo que seleccionan el subconjunto de archivos que son candidatos de actualización como fuente para esta transferencia. Ver arriba para detalles sobre patrones de coincidencia.

Esta opción es obligatoria. Cualquier patrón listado debe contener al menos el comodín "@v", para que se pueda extraer un identificador de versión del nombre del archivo. Todos los demás comodines son opcionales.

Si el tipo de origen es regular-file o directory, el patrón puede contener caracteres de barra. En este caso, coincidirá con el archivo o directorio en el subdirectorio correspondiente. Por ejemplo "MatchPattern=foo_@v/bar.efi" coincidirá con "bar.efi" en el directorio "foo_1".

Añadido en la versión 251.

[TARGET] OPCIONES DE SECCIÓN

Esta sección define las propiedades del destino de la transferencia.

Type=

Especifica el tipo de recurso del destino para la transferencia. Toma uno de partition, regular-file, directory o subvolume. Para detalles sobre los tipos de recursos, ver arriba. Esta opción es obligatoria.

Tenga en cuenta que solo se admiten ciertas combinaciones de tipos de recursos de origen y destino, ver arriba.

Añadido en la versión 251.

Path=

Especifica una ruta del sistema de archivos donde buscar versiones ya instaladas o colocar nuevas versiones descargadas de este recurso configurado. Si Type= se establece como partition, espera una ruta a un nodo de dispositivo de bloque (entero), o la cadena especial "auto" en cuyo caso se determina y utiliza automáticamente el dispositivo de bloque que contiene el sistema de archivos raíz del sistema actualmente arrancado. Si Type= se establece como regular-file, directory o subvolume, debe referirse a una ruta en el sistema de archivos local que haga referencia al directorio donde encontrar o colocar los archivos o directorios de versión.

Tenga en cuenta que este mecanismo no se puede utilizar para crear o eliminar particiones, en caso de que Type= se establezca como partition. Las particiones deben existir ya, y se utiliza una etiqueta especial de partición "_empty" para indicar particiones vacías. Para generar automáticamente particiones adecuadas en el primer arranque, utilice una herramienta como systemd-repart(8).

Añadido en la versión 251.

PathRelativeTo=

Especifica respecto a qué punto de anclaje se resolverá Path=. Toma uno de root, esp, xbootldr, boot o explicit. Si no se especifica, por defecto es root.

Si se establece como root, esp, xbootldr, la ruta Path= especificada se resolverá en relación con el punto de montaje de la partición correspondiente, tal como se define en la **Especificación del cargador de arranque**[2].

Si se establece como boot, la ruta Path= especificada se resolverá en relación con el punto de montaje de la partición $BOOT (es decir, ESP o XBOOTLDR), tal como se define en la **Especificación del cargador de arranque**[2].

Si se establece como explicit, la ruta Path= especificada se resolverá en relación con el directorio especificado con --transfer-source= al invocar systemd-sysupdate(8).

Los valores esp, xbootldr y boot solo son compatibles cuando Type= se establece como regular-file o directory.

Añadido en la versión 254.

MatchPattern=

Especifica uno o más patrones de coincidencia de nombres de archivo o etiquetas de partición que seleccionan el subconjunto de archivos o particiones que son candidatos de actualización como destinos para esta transferencia. Ver arriba para detalles sobre patrones de coincidencia.

Esta opción es obligatoria. Cualquier patrón listado debe contener al menos el comodín "@v", para que se pueda extraer un identificador de versión del nombre del archivo. Todos los demás comodines son opcionales.

Este patrón se utiliza tanto para hacer coincidir versiones instaladas existentes como para determinar el nombre de las nuevas versiones a instalar. Si se especifican varios patrones, el primero especificado se utiliza para nombrar las versiones recién instaladas.

Si el tipo de destino es regular-file o directory, el patrón puede contener caracteres de barra. En este caso, coincidirá con el archivo o directorio en el subdirectorio correspondiente. Por ejemplo "MatchPattern=foo_@v/bar.efi" coincidirá con "bar.efi" en el directorio "foo_1". Los directorios en la ruta se crearán cuando se instale el archivo. Los directorios vacíos se eliminarán cuando se elimine el archivo.

Añadido en la versión 251.

MatchPartitionType=

Si no se especifica, se utiliza el tipo de partición GPT linux-generic. Acepta tanto un UUID de tipo literal como un identificador de tipo simbólico. Para una lista de identificadores de tipo admitidos, ver la configuración Type= en repart.d(5).

Añadido en la versión 251.

PartitionUUID=, PartitionFlags=, PartitionNoAuto=, PartitionGrowFileSystem=

Cuando el destino Type= se elige como partition, selecciona el UUID de partición GPT y las banderas de partición a utilizar para la partición actualizada. Espera una cadena UUID válida, un entero hexadecimal o booleanos, respectivamente. Si no se establece, pero el patrón de coincidencia de origen incluye comodines para estos campos (es decir, "@u", "@f", "@a" o "@g"), se utilizan los valores de los patrones. Si no se configuran con comodines ni con estas configuraciones explícitas, los valores se dejan sin modificar. Si se utilizan tanto la configuración general de banderas PartitionFlags= como las configuraciones individuales de banderas PartitionNoAuto= y PartitionGrowFileSystem= (o los comodines para ellas), entonces estas últimas anulan a la primera, es decir, el bit de bandera individual anula el valor general de las banderas. Ver **Especificación de Particiones Detectables**[1] para detalles sobre estas banderas.

Tenga en cuenta que estas configuraciones no se utilizan para coincidir, solo tienen efecto en las particiones recién escritas en caso de que se produzca una transferencia.

Finalmente, si el tipo de destino Type= se selecciona como directory, se establece el atributo de archivo "inmutable", ver chattr(1) para detalles.

OPCIONES

Las siguientes opciones de configuración se aplican a las transferencias, y se pueden establecer en las secciones [Source], [Target], y [Transfer]:

Mode=

Toma una cadena de texto que define los permisos del archivo en formato octal (por ejemplo, 0644). Si no se define, se utiliza el modo predeterminado del archivo de origen, o 0600 para los archivos sin nombre. Esta opción solo tiene efecto si el tipo de destino es regular-file.

Owner=, Group=

Toma una cadena de texto que identifica al propietario y al grupo del archivo. Si se omite, se mantiene el propietario/grupo del archivo de origen. Si se especifica como una cadena vacía, se utiliza el ID de usuario o grupo predeterminado del sistema. Estas opciones solo tienen efecto si el tipo de destino es regular-file.

ProtectID=, ProtectHost=, ProtectVersion=, ProtectKernel=, ProtectMachine=, ProtectImage=, ProtectOS=, ProtectVariant=

Estas opciones toman un valor booleano (true o false) y controlan si una actualización debe omitirse si la versión del sistema operativo/imagen/kernel/host/ID/arquitectura/máquina coincide con la de la versión que se está actualizando. Útil para evitar actualizar un sistema a la misma versión que ya está en ejecución. Por ejemplo, ProtectVersion=true evita que se actualice un archivo si la versión del archivo de origen es la misma que la versión actual del sistema (determinada por el especificador %A). Todas estas opciones se pueden utilizar junto con especificadores como %a, %A, %b, %B, %H, %m, %M, %o, %v, %W. Para ProtectVersion=, el valor especificado se compara con %A. Para ProtectKernel=, se compara con %v. Para ProtectImage=, se compara con %M. Para ProtectOS=, se compara con %o. Para ProtectVariant=, se compara con %W. Para ProtectHost=, se compara con %H y %l. Para ProtectMachine=, se compara con %m. Las opciones ProtectID= y ProtectVersion= funcionan de forma similar, comparando el valor especificado con %A.

NoCopy=

Toma un valor booleano. Si es true, se salta la transferencia de este archivo. Útil para hacer referencia a archivos existentes sin copiarlos, por ejemplo, en un sistema de archivos especial.

UseSignature=

Toma una cadena de texto que especifica la extensión de un archivo de firma (por ejemplo, .sig). Si el archivo de origen tiene esta extensión, la firma se verifica antes de la transferencia.

Required=

Toma un valor booleano. Si es true (predeterminado), la transferencia fallará si este archivo no se puede transferir. Si es false, la transferencia continuará incluso si este archivo no se puede transferir.

Priority=

Toma un entero. Define la prioridad de esta transferencia en relación con otras transferencias del mismo grupo. Un número más alto indica una prioridad más alta.

TemporaryMaxSpace=

Toma un entero que representa el tamaño máximo en bytes que puede ocupar un archivo temporal. Si el archivo excede este tamaño, se eliminará. Solo se aplica a archivos temporales.

MinVersion=, MaxVersion=

Estas opciones toman una cadena de texto que representa una versión del sistema operativo. Controlan si la transferencia se aplica a sistemas cuya versión está dentro del rango especificado. La comparación se realiza utilizando la cadena de versión del sistema operativo.

PathRelativeTo=

Toma el nombre de un directorio relativo como argumento. El directorio de destino se interpreta en relación con este directorio. Por ejemplo, si PathRelativeTo=boot y Path=/EFI/Linux, el directorio de destino será /boot/EFI/Linux. Esto solo se aplica si el tipo de destino es regular-file, directory o subvolume.

MatchPartitionType=

Toma una cadena de texto que representa el tipo de partición según el estándar systemd.gpt-auto-generator[1]. Esta opción se utiliza para seleccionar una partición específica en el disco de destino basándose en su tipo. Solo se aplica si el tipo de destino es partition.

MatchPartitionLabel=, MatchPartitionUUID=, MatchPartitionUniqueGUID=

Toma una cadena de texto que representa la etiqueta, UUID o GUID único de una partición. Estas opciones se utilizan para seleccionar una partición específica en el disco de destino basándose en estos identificadores. Solo se aplican si el tipo de destino es partition.

PartitionFlags=

Toma un entero. Esta opción se utiliza para establecer banderas específicas en la tabla de particiones GPT. Las banderas deben codificarse como un número entero decimal o hexadecimal. El valor predeterminado es 0. Solo se aplica si el tipo de destino es partition.

ReadOnly=

Toma un valor booleano. Si es true, la partición de destino se marca como de solo lectura después de la transferencia. Si es false (predeterminado), la partición se marca como de lectura/escritura. Solo se aplica si el tipo de destino es partition.

TriesDone=, TriesLeft=

Estas opciones toman enteros decimales positivos y controlan el número de intentos realizados y restantes para este archivo. Estas configuraciones son útiles para administrar imágenes de kernel, siguiendo el esquema definido en Evaluación Automática de Arranque[3], y solo tienen efecto si el patrón de destino incluye los comodines "@d" o "@l".

Añadido en la versión 251.

InstancesMax=

Toma un entero decimal igual o mayor que 2. Configura cuántas versiones concurrentes del recurso se deben mantener. Cada vez que se inicia una nueva actualización, se asegura que no existan más que el número de versiones especificadas aquí menos una en el destino. Cualquier versión excedente se elimina (en caso de que el tipo de destino Type= de regular-file, directory, subvolume se use) o se vacía (en caso de que el tipo de destino Type= de partition se use; vaciar en este caso simplemente significa establecer la etiqueta de la partición a la cadena especial "_empty"; tenga en cuenta que en realidad no se eliminan particiones). Después de que se completa una actualización, el número de versiones concurrentes de los recursos de destino es igual o inferior al número especificado aquí.

Tenga en cuenta que esta configuración se puede establecer de manera diferente para cada transferencia. Sin embargo, generalmente es aconsejable mantener esta configuración igual para todas las transferencias, ya que de lo contrario quedarán combinaciones incompletas de archivos o particiones instaladas.

Si el tipo de destino Type= se selecciona como partition, el número de versiones concurrentes a mantener se restringe además por el número de ranuras de partición del tipo correcto en la tabla de particiones. Es decir, si solo hay 2 ranuras de partición para el tipo de partición seleccionado, establecer este valor en mayor que 2 no tiene efecto, ya que de todos modos no se podrían almacenar más de 2 versiones concurrentes en la imagen.

Añadido en la versión 251.

RemoveTemporary=

Toma un argumento booleano. Si esta opción está habilitada (lo cual es el valor predeterminado) antes de iniciar una actualización, se eliminan todas las actualizaciones incompletas restantes de un intento anterior del directorio de destino. Esto solo tiene efecto si el tipo de recurso de destino Type= se selecciona como regular-file, directory o subvolume.

Añadido en la versión 251.

CurrentSymlink=

Toma un nombre de enlace simbólico como argumento. Si se usa esta opción, como último paso de la actualización se crea/actualiza un enlace simbólico con el nombre especificado apuntando a la actualización completada. Esto es útil para proporcionar un nombre estable que siempre apunte a la versión más reciente del recurso. Esto solo se admite si el tipo de recurso de destino Type= se selecciona como regular-file, directory o subvolume.

Añadido en la versión 251.

Lo anterior define el mecanismo de actualización para la partición Verity del sistema de archivos raíz. Bajo la suposición de que esta actualización se ejecuta desde la propia imagen, la versión actual de la imagen (es decir, el especificador "%A") se marca como protegida, para garantizar que no se corrompa mientras se arranca. Path=https://download.example.com/

Lo anterior define una definición de transferencia coincidente para el sistema de archivos raíz.

# /usr/lib/sysupdate.d/70-kernel.transfer

NOMBRE

systemd.resource-control - .d directory para controlar los recursos de un servicio

SINOPSIS

systemd.unit(5) .d/
systemd.exec(5) .d/
systemd.kill(5) .d/
systemd.resource-control(5) .d/

DESCRIPCIÓN

Un servicio puede tener archivos de configuración separados en un directorio `.d` que se fusionan en la configuración principal del servicio. La configuración en estos archivos se utiliza para limitar los recursos que el servicio puede utilizar.

Los archivos en el directorio `.d` se fusionan en orden alfabético antes de que se apliquen las opciones de configuración del archivo principal. Si un archivo en el directorio `.d` establece una opción que también está presente en el archivo principal, el valor del archivo `.d` tendrá prioridad.

Los archivos del directorio `.d` se aplican a la unidad como un todo. Las opciones solo se aplican si la unidad tiene un tipo que soporta el control de recursos (por ejemplo, `Type=simple`, `Type=forking`, `Type=oneshot`, `Type=notify`, `Type=dbus` o `Type=notify` donde el proceso principal es el principal). Las unidades de tipo `service` son las únicas que utilizan estas configuraciones de control de recursos.

Las opciones de control de recursos disponibles son las que se aplican al grupo de control (`cgroup`). Estas opciones se derivan de las opciones disponibles en systemd.exec(5) y se refieren a las siguientes áreas:

  • Límites de CPU
  • Límites de memoria
  • Límites de I/O
  • Límites de red
  • Límites de procesos
  • Límites de dispositivos

Para una lista completa de las opciones de control de recursos disponibles, consulte la página del manual de systemd.exec(5).

El nombre del archivo de configuración en el directorio `.d` debe terminar con el sufijo `.conf`.

Ejemplo 1. Configuración de ejemplo para limitar el uso de CPU.

# /etc/systemd/system/my-service.service.d/override-cpu.conf
[Service]
CPUQuota=20%
CPUShares=500

Este ejemplo limitaría el uso de CPU del servicio `my-service.service` al 20% de la CPU disponible y establecería sus participaciones de CPU en 500. El orden de aplicación de las opciones es importante; por ejemplo, si se especifica `CPUQuota` y `CPUShares`, `CPUQuota` tendrá prioridad.

Ejemplo 2. Configuración de ejemplo para limitar el uso de memoria.

# /etc/systemd/system/my-service.service.d/override-memory.conf
[Service]
MemoryMax=256M
MemoryHigh=128M

Este ejemplo limitaría el uso de memoria del servicio `my-service.service` a 256M y lo establecería en 128M. Si se especifica `MemoryMax` y `MemoryHigh`, `MemoryMax` tendrá prioridad.

Ejemplo 3. Configuración de ejemplo para limitar el número de procesos.

# /etc/systemd/system/my-service.service.d/override-processes.conf
[Service]
TasksMax=100

Este ejemplo limitaría el número de procesos que el servicio `my-service.service` puede crear a 100.

Ejemplo 4. Configuración de ejemplo para limitar el uso de I/O.

# /etc/systemd/system/my-service.service.d/override-io.conf
[Service]
IOWeight=500

Este ejemplo establecería el peso de I/O del servicio `my-service.service` en 500. Los valores más altos indican más I/O. Si se especifica `IOWeight`, las operaciones de I/O del servicio tendrán prioridad sobre las operaciones de I/O con menor peso.

Ejemplo 5. Configuración de ejemplo para limitar el uso de red.

# /etc/systemd/system/my-service.service.d/override-network.conf
[Service]
NetworkPriority=10

Este ejemplo establecería la prioridad de red del servicio `my-service.service` en 10. Los valores más bajos indican mayor prioridad. Esto afecta a las operaciones de red, como el ancho de banda de la red. Si se especifica `NetworkPriority`, el tráfico de red del servicio tendrá prioridad sobre el tráfico de red con mayor prioridad.

Ejemplo 6. Configuración de ejemplo para limitar el acceso a dispositivos.

# /etc/systemd/system/my-service.service.d/override-devices.conf
[Service]
DeviceAllow=/dev/null rw
DeviceAllow=/dev/tty[0-9]* rw

Este ejemplo permitiría al servicio `my-service.service` leer y escribir en `/dev/null` y leer y escribir en los dispositivos tty del 0 al 9. Todos los demás accesos a dispositivos están prohibidos. Si se especifica `DeviceAllow`, todos los accesos a dispositivos no especificados están prohibidos.

Ejemplo 7. Configuración de ejemplo para limitar el uso de PIDs.

# /etc/systemd/system/my-service.service.d/override-pids.conf
[Service]
CPUPower=100%
CPUQuota=50%

Este ejemplo limita el uso de CPU del servicio al 100% de la potencia de CPU. Si se especifican `CPUPower` y `CPUQuota`, `CPUPower` tendrá prioridad.
