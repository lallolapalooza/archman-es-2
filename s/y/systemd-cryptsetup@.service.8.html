NOMBRE

systemd-cryptsetup, systemd-cryptsetup@.service - Lógica de descifrado de disco completo

SINOPSIS

systemd-cryptsetup [OPCIONES...] attach VOLUMEN DISPOSITIVO-ORIGEN [ARCHIVO-CLAVE] [OPCIONES-CRYPTTAB]

systemd-cryptsetup [OPCIONES...] detach VOLUMEN

systemd-cryptsetup@.service

system-systemd\x2dcryptsetup.slice

DESCRIPCIÓN

systemd-cryptsetup se utiliza para configurar (con attach) y desmantelar (con detach) el acceso a un dispositivo de bloque cifrado. Se utiliza principalmente a través de systemd-cryptsetup@.service durante el arranque temprano, pero también puede ser llamado manualmente. Los argumentos posicionales VOLUMEN, DISPOSITIVO-ORIGEN, ARCHIVO-CLAVE y OPCIONES-CRYPTTAB tienen el mismo significado que los campos en crypttab(5).

systemd-cryptsetup@.service es un servicio responsable de proporcionar acceso a dispositivos de bloque cifrados. Se instancia para cada dispositivo que requiere descifrado.

Las instancias de systemd-cryptsetup@.service forman parte del slice system-systemd\x2dcryptsetup.slice, que solo se destruye muy tarde en el procedimiento de apagado. Esto permite que los dispositivos cifrados permanezcan activos hasta que los sistemas de archivos se hayan desmontado.

systemd-cryptsetup@.service solicitará contraseñas de disco duro a través de la lógica del agente de contraseñas[1], para consultar al usuario la contraseña utilizando el mecanismo correcto al arrancar y durante el tiempo de ejecución.

Al principio del arranque y cuando se recarga la configuración del gestor del sistema, /etc/crypttab se traduce en unidades de systemd-cryptsetup@.service por systemd-cryptsetup-generator(8).

Para desbloquear un volumen se requiere una contraseña o una clave binaria. systemd-cryptsetup@.service intenta adquirir una contraseña o clave binaria adecuada a través de los siguientes mecanismos, probados en orden:

1. Si se configura explícitamente un archivo de clave (a través de la tercera columna en /etc/crypttab), se utiliza una clave leída de él. Si se configura un token PKCS#11, token FIDO2 o dispositivo TPM2 (usando las opciones pkcs11-uri=, fido2-device=, tpm2-device=) la clave se descifra antes de su uso.
2. Si no se configura explícitamente un archivo de clave de esta manera, se carga automáticamente un archivo de clave desde /etc/cryptsetup-keys.d/volumen.key y /run/cryptsetup-keys.d/volumen.key, si están presentes. Aquí también, si se configura un token/dispositivo PKCS#11/FIDO2/TPM2, cualquier clave encontrada de esta manera se descifra antes de su uso.
3. Si se especifica la opción try-empty-password, se intenta desbloquear el volumen con una contraseña vacía.
4. Si la opción password-cache= está establecida a "yes" o "read-only", se comprueba entonces el keyring del kernel en busca de una contraseña cacheada adecuada de intentos anteriores.
5. Finalmente, se solicita al usuario una contraseña, posiblemente varias veces, a menos que se establezca la opción headless.

Si no se puede adquirir ninguna clave adecuada a través de ninguno de los mecanismos descritos anteriormente, la activación del volumen falla.

CREDENCIALES

systemd-cryptsetup admite la lógica de credenciales de servicio implementada por ImportCredential=/LoadCredential=/SetCredential= (consulte systemd.exec(5) para obtener detalles). Las siguientes credenciales son utilizadas por "systemd-crypsetup@root.service" (generada por systemd-gpt-auto-generator) cuando se pasan:

cryptsetup.passphrase

Esta credencial especifica la frase de contraseña del volumen LUKS.

Añadido en la versión 256.

cryptsetup.tpm2-pin

Esta credencial especifica el pin de TPM.

Añadido en la versión 256.

cryptsetup.fido2-pin

Esta credencial especifica el pin del token FIDO2.

Añadido en la versión 256.

cryptsetup.pkcs11-pin

Esta credencial especifica el pin del token PKCS11.

Añadido en la versión 256.

cryptsetup.luks2-pin

Esta credencial especifica el pin solicitado por módulos de token genéricos LUKS2.

Añadido en la versión 256.
