SYSTEMD-SYSEXT(8) systemd-sysext SYSTEMD-SYSEXT(8)

NOMBRE

systemd-sysext, systemd-sysext.service, systemd-sysext-initrd.service, systemd-confext, systemd-confext.service, systemd-confext-initrd.service - Activa Imágenes de Extensión del Sistema

SINOPSIS

systemd-sysext [OPCIONES...] COMANDO

systemd-sysext.service

systemd-confext [OPCIONES...] COMANDO

systemd-confext.service

DESCRIPCIÓN

systemd-sysext activa/desactiva imágenes de extensión del sistema. Las imágenes de extensión del sistema pueden — dinámicamente en tiempo de ejecución — extender las jerarquías de directorios /usr/ y /opt/ con archivos adicionales. Esto es particularmente útil en imágenes inmutables del sistema donde una jerarquía /usr/ y/o /opt/ que reside en un sistema de archivos de solo lectura debe extenderse temporalmente en tiempo de ejecución sin realizar modificaciones persistentes.

Las imágenes de extensión del sistema deben contener archivos y directorios de manera similar a un árbol de sistema operativo normal. Cuando una o más imágenes de extensión del sistema se activan, sus jerarquías /usr/ y /opt/ se combinan mediante "overlayfs" con las mismas jerarquías del sistema operativo anfitrión, y el /usr/ y /opt/ del anfitrión se montan por encima de ella ("fusión"). Cuando se desactivan, el punto de montaje se desmonta — revelando nuevamente la versión original no modificada del anfitrión de la jerarquía ("desfusión"). La fusión hace que los recursos de la extensión aparezcan de repente debajo de las jerarquías /usr/ y /opt/ como si estuvieran incluidos en la propia imagen del sistema base. Desfusionar hace que desaparezcan de nuevo, dejando solo los archivos que se enviaron con la imagen del sistema base.

Los archivos y directorios contenidos en las imágenes de extensión fuera de las jerarquías /usr/ y /opt/ *no* se fusionan, y por lo tanto no tienen efecto cuando se incluyen en una imagen de extensión del sistema. En particular, los archivos en /etc/ y /var/ incluidos en una imagen de extensión del sistema *no* aparecerán en las jerarquías respectivas después de la activación.

Las imágenes de extensión del sistema son estrictamente de solo lectura por defecto. En sistemas de archivos anfitriones mutables, las jerarquías /usr/ y /opt/ se vuelven de solo lectura mientras se fusionan las extensiones, a menos que se habilite la mutabilidad. La mutabilidad se puede habilitar mediante la opción --mutable=; consulte "Mutabilidad" a continuación para obtener más información.

Las extensiones del sistema están destinadas a ser puramente aditivas, es decir, están destinadas a incluir solo archivos que no existen en la imagen del sistema base subyacente. Sin embargo, el mecanismo subyacente (overlayfs) también permite superponer o eliminar archivos, pero se recomienda no hacer uso de esto.

Las imágenes de extensión del sistema pueden proporcionarse en los siguientes formatos:

1. Directorios simples o subvolúmenes btrfs que contienen el árbol del SO
2. Imágenes de disco con una etiqueta de disco GPT, siguiendo la Especificación de Particiones Descubribles[1]
3. Imágenes de disco sin tabla de particiones, con un sistema de archivos Linux desnudo (por ejemplo, erofs, squashfs o ext4)

Estos formatos de imagen son los mismos que systemd-nspawn(1) soporta a través de sus opciones --directory=/--image= y aquellos que el administrador del servicio soporta a través de RootDirectory=/RootImage=. Similar a ellos, pueden llevar opcionalmente información de autenticación Verity.

Las extensiones del sistema se buscan en los directorios /etc/extensions/, /run/extensions/ y /var/lib/extensions/. Los dos primeros directorios listados no son adecuados para contener imágenes binarias grandes, sin embargo, son útiles para contener enlaces simbólicos a ellas. El lugar principal para instalar extensiones del sistema es /var/lib/extensions/. Cualquier directorio encontrado en estos directorios de búsqueda se considera una imagen de extensión basada en directorios; cualquier archivo con el sufijo .raw se considera una imagen de extensión basada en disco.

Cuando se invoca en el initrd, el directorio adicional /.extra/sysext/ se incluye en los directorios que se buscan para las imágenes de extensión. Tenga en cuenta, sin embargo, que por defecto se aplica una política de imagen más estricta a las imágenes que se encuentran allí, ver más abajo. Este directorio es poblado por systemd-stub(7) con imágenes de extensión encontradas en la Partición del Sistema EFI del sistema.

Durante el arranque, las imágenes de extensión del sistema se activan automáticamente si systemd-sysext.service está habilitado. Tenga en cuenta que este servicio se ejecuta solo después de que los sistemas de archivos subyacentes donde pueden ubicarse las extensiones del sistema se hayan montado. Esto significa que no son adecuadas para enviar recursos que son procesados por subsistemas que se ejecutan en el arranque más temprano. Específicamente, las imágenes de extensión del sistema no son adecuadas para enviar servicios del sistema o definiciones de systemd-sysusers(8). Consulte la página de Servicios Portátiles[2] para un mecanismo sencillo para enviar servicios del sistema en imágenes de disco, de manera similar a las extensiones del sistema. Tenga en cuenta el diferente aislamiento en estos dos mecanismos: mientras que las extensiones del sistema extienden directamente la imagen del sistema subyacente con archivos adicionales que aparecen de manera muy similar a como si se hubieran enviado en la propia imagen del sistema y, por lo tanto, no implican aislamiento de seguridad, los servicios portátiles implican sandboxing a nivel de servicio de una forma u otra. Se garantiza que el servicio systemd-sysext.service termina de iniciarse antes de que se alcance basic.target; es decir, cuando los servicios regulares se inicializan (aquellos que no usan DefaultDependencies=no), los archivos y directorios que las extensiones del sistema proporcionan están disponibles en /usr/ y /opt/ y pueden ser accedidos.

Tenga en cuenta que no existe el concepto de habilitar/deshabilitar imágenes de extensión del sistema instaladas: todas las imágenes de extensión instaladas se activan automáticamente al arrancar. Sin embargo, puede colocar un directorio vacío con el nombre de la extensión (sin .raw) en /etc/extensions/ para "enmascarar" una extensión con el mismo nombre en una carpeta del sistema con menor precedencia.

Se aplica un mecanismo sencillo de compatibilidad de versiones: una imagen de extensión del sistema debe llevar un archivo /usr/lib/extension-release.d/extension-release.NOMBRE, que debe coincidir con su nombre de imagen, que se compara con el archivo os-release del host: los campos ID= contenidos deben coincidir a menos que se establezca "_any" para la extensión. Si el ID= de la extensión no es "_any", el campo SYSEXT_LEVEL= (si está definido) debe coincidir. Si este último no está definido, el campo VERSION_ID= debe coincidir en su lugar. Si la extensión define el campo ARCHITECTURE= y el valor no es "_any", debe coincidir con la arquitectura del kernel reportada por uname(2), pero los identificadores de arquitectura utilizados son los mismos que para ConditionArchitecture= descritos en systemd.unit(5). EXTENSION_RELOAD_MANAGER= se puede establecer en 1 si la extensión requiere una recarga del administrador del servicio después de la aplicación de la extensión. Tenga en cuenta que por las razones mencionadas anteriormente, los Servicios Portátiles[2] siguen siendo la forma recomendada de distribuir servicios del sistema. Las extensiones del sistema no deben distribuir un archivo /usr/lib/os-release (ya que se fusionaría en el árbol /usr/ del host, anulando los datos de la versión del SO del host, lo cual no es deseable). El archivo extension-release sigue el mismo formato y semántica, y lleva el mismo contenido, que el archivo os-release del SO, pero describe los recursos contenidos en la imagen de extensión.

El concepto systemd-confext sigue el mismo principio que la funcionalidad de systemd-sysext(8) pero en lugar de trabajar en /usr y /opt, confext extenderá solo /etc. Los archivos y directorios contenidos en las imágenes confext fuera de la jerarquía /etc/ *no* se fusionan, y por lo tanto no tienen efecto cuando se incluyen en la imagen. Los formatos para estas imágenes son los mismos que los de las imágenes sysext. La jerarquía fusionada se montará con "nosuid" y (si no se deshabilita con --noexec=false) "noexec".

Al igual que los sysext, los confext son estrictamente de solo lectura por defecto. La fusión de confext en sistemas de archivos anfitriones mutables hará que /etc/ sea de solo lectura. Al igual que con los sysext, la mutabilidad se puede habilitar mediante la opción --mutable=. Consulte "Mutabilidad" a continuación para obtener más información.

Los confext se buscan en los directorios /run/confexts/, /var/lib/confexts/, /usr/lib/confexts/ y /usr/local/lib/confexts/. El primer directorio listado no es adecuado para contener imágenes binarias grandes, sin embargo, es útil para contener enlaces simbólicos a ellas. El lugar principal para instalar extensiones de configuración es /var/lib/confexts/. Cualquier directorio encontrado en estos directorios de búsqueda se considera una imagen confext basada en directorios; cualquier archivo con el sufijo .raw se considera una imagen confext basada en disco.

Nuevamente, al igual que las imágenes sysext, las imágenes confext contendrán un archivo /etc/extension-release.d/extension-release.NOMBRE, que debe coincidir con el i

Nombre de la imagen (con la puerta de escape habitual de user.extension-release.strict xattr(7)), y de nuevo con el contenido siendo uno o más de ID=, VERSION_ID= y CONFEXT_LEVEL. Las imágenes Confext se comprobarán y se compararán con la capa base del sistema operativo.

USOS

El caso de uso principal de las imágenes del sistema son entornos inmutables donde las herramientas de depuración y desarrollo deben estar disponibles opcionalmente, pero no incluidas en la propia imagen base inmutable del sistema operativo (por ejemplo, strace(1) y gdb(1) deben ser una adición instalable opcionalmente para facilitar la depuración/desarrollo). Las imágenes de extensión del sistema no deben malinterpretarse como un marco genérico de empaquetado de software, ya que no hay un esquema de dependencias disponible: las extensiones del sistema deben llevar todos los archivos que necesiten, excepto aquellos que ya se distribuyen en la imagen subyacente del sistema anfitrión. Típicamente, las imágenes de extensión del sistema se construyen al mismo tiempo que la imagen base del sistema operativo — dentro del mismo sistema de compilación.

Otro caso de uso para el concepto de extensión del sistema es la sustitución temporal de recursos suministrados por el sistema operativo por otros más nuevos, por ejemplo, para instalar una versión de desarrollo compilada localmente de algún componente de bajo nivel sobre la imagen inmutable del sistema operativo sin realizar una reconstrucción completa del sistema operativo o modificar la imagen nominalmente inmutable. (por ejemplo, "instalar" un paquete compilado localmente con DESTDIR=/var/lib/extensions/mytest make install && systemd-sysext refresh, haciéndolo disponible en /usr/ como si se hubiera instalado en la propia imagen del sistema operativo.) Este caso funciona independientemente de si el /usr/ anfitrión subyacente se gestiona como una imagen de disco inmutable o es un árbol controlable por un gestor de paquetes tradicional (es decir, escribible).

Con systemd-confext se puede realizar la reconfiguración en tiempo de ejecución de los servicios del sistema operativo. A veces, existe la necesidad de intercambiar ciertos valores de parámetros de configuración o reiniciar solo un servicio específico sin implementar código nuevo o una implementación completa del sistema operativo. En otras palabras, queremos poder vincular las opciones configuradas con más frecuencia a indicadores actualizables en tiempo de ejecución que puedan cambiarse sin reiniciar el sistema. Esto ayudará a reducir los tiempos de servicio cuando sea necesario cambiar la configuración del sistema operativo. También proporciona una herramienta fiable para la gestión de la configuración, ya que todos los archivos de configuración antiguos desaparecen cuando se elimina la imagen de systemd-confext.

INMUTABILIDAD

Por defecto, la fusión de extensiones del sistema en sistemas de archivos anfitriones mutables hará que las jerarquías /usr/ y /opt/ sean de solo lectura. La fusión de extensiones de configuración tendrá el mismo efecto en /etc/. El modo mutable permite escrituras en estas ubicaciones cuando se fusionan las extensiones.

Los siguientes modos son compatibles:

1.desactivado: Fuerza el modo inmutable incluso si existen directorios de enrutamiento de escritura debajo de /var/lib/extensions.mutable/. Este es el valor predeterminado.
2.auto: Modo automático. La mutabilidad está desactivada por defecto y solo se habilita si existe un directorio de enrutamiento de escritura correspondiente debajo de /var/lib/extensions.mutable/.
3.activado: Fuerza el modo mutable y crea automáticamente directorios de enrutamiento de escritura debajo de /var/lib/extensions.mutable/ cuando sea necesario.
4.importar: Fuerza el modo inmutable como desactivado anteriormente, pero fusiona el contenido de los directorios debajo de /var/lib/extensions.mutable/ en el sistema de archivos anfitrión.
5.efímero: Fuerza el modo mutable como activado anteriormente, pero en lugar de usar directorios de enrutamiento de escritura debajo de /var/lib/extensions.mutable/, systemd-sysext utilizará directorios efímeros vacíos. Esto significa que las modificaciones realizadas en las jerarquías fusionadas se perderán cuando las jerarquías se desfusionen.
6.efímero-importar: Fuerza el modo mutable como efímero anteriormente, pero en lugar de ignorar el contenido de los directorios de enrutamiento de escritura bajo /var/lib/extensions.mutable/, los fusiona en el sistema de archivos anfitrión, como hace importar.

Consulte "Opciones" a continuación para especificar modos utilizando la opción de línea de comandos --mutable=.

Con la excepción del modo efímero, el modo mutable enruta las escrituras a subdirectorios en /var/lib/extensions.mutable/.

Las escrituras en /usr/ se dirigen a /var/lib/extensions.mutable/usr/
Las escrituras en /opt/ se dirigen a /var/lib/extensions.mutable/opt/, y
Las escrituras en /etc/ van a /var/lib/extensions.mutable/etc/.

Si usr/, opt/ o etc/ en /var/lib/extensions.mutable/ son enlaces simbólicos, entonces las escrituras se dirigen a los destinos de los enlaces simbólicos. En consecuencia, para mantener la mutabilidad de un sistema de archivos anfitrión, cree enlaces simbólicos

/var/lib/extensions.mutable/etc/ → /etc/
/var/lib/extensions.mutable/usr/ → /usr/
/var/lib/extensions.mutable/opt/ → /opt/
para redirigir las escrituras de vuelta a la jerarquía del directorio base original.

Alternativamente, se puede montar un sistema de archivos temporal en /var/lib/extensions.mutable/, o los enlaces simbólicos en /var/lib/extensions.mutable/ pueden apuntar a subdirectorios en un sistema de archivos temporal (por ejemplo, debajo de /tmp/) para permitir solo cambios efímeros. Tenga en cuenta que esto no es lo mismo que el modo efímero, porque el sistema de archivos temporal seguirá existiendo después de desfusionarse.

Añadido en la versión 256.

COMANDOS

Los siguientes comandos son entendidos tanto por el concepto sysext como por el confext:

status

Cuando se invoca sin ningún verbo de comando, o cuando se especifica status, se muestra el estado de fusión actual, por separado (tanto para /usr/ como para /opt/ de sysext y para /etc/ de confext).

Añadido en la versión 248.

merge

Fusiona todas las imágenes de extensión del sistema instaladas actualmente en /usr/ y /opt/, sobremontando estas jerarquías con un sistema de archivos "overlayfs" que combina las jerarquías subyacentes con las incluidas en las imágenes de extensión. Este comando fallará si las jerarquías ya están fusionadas. Para confext, la fusión se realiza en el directorio /etc/ en su lugar.

Añadido en la versión 248.

unmerge

Desmonta todas las imágenes de extensión del sistema instaladas actualmente de /usr/ y /opt/ para sysext y /etc/, para confext, desmontando los sistemas de archivos "overlayfs" creados previamente por merge.

Añadido en la versión 248.

refresh

Una combinación de unmerge y merge: si ya está montado, la instancia "overlayfs" existente se desmonta temporalmente y luego se reemplaza por una nueva versión. Este comando es útil después de instalar/eliminar imágenes de extensión del sistema, para actualizar el sistema de archivos "overlayfs" en consecuencia. Si no hay extensiones del sistema instaladas cuando se ejecuta este comando, se ejecuta el equivalente de unmerge, sin establecer ninguna nueva instancia "overlayfs". Tenga en cuenta que actualmente hay un breve momento en el que ni el sistema de archivos "overlayfs" antiguo ni el nuevo están montados. Esto implica que todos los recursos proporcionados por una extensión del sistema desaparecerán brevemente — incluso si existe continuamente durante la operación de refresco.

Añadido en la versión 248.

list

Se muestra una lista breve de las imágenes de extensión instaladas.

Añadido en la versión 248.

-h, --help

Imprime un texto de ayuda corto y sale.

--version

Imprime una cadena de versión corta y sale.

OPCIONES

--root=

Opera en relación con el directorio raíz especificado, es decir, establece el montaje "overlayfs" no en las jerarquías superiores /usr/ y /opt/ del anfitrión para sysext o /etc/ para confext, sino debajo de algún directorio raíz especificado.

Añadido en la versión 248.

--force

Al fusionar extensiones del sistema en /usr/ y /opt/ para sysext y /etc/ para confext, ignora las incompatibilidades de versión, es decir, fuerza la fusión independientemente de si la información de versión incluida en las imágenes coincide o no con la del anfitrión.

Añadido en la versión 248.

--image-policy=política

Toma una cadena de política de imagen como argumento, según systemd.image-policy(7). La política se aplica al operar en imágenes de disco de extensión del sistema. Si no se especifica, por defecto es "root=verity+signed+encrypted+unprotected+absent:usr=verity+signed+encrypted+unprotected+absent" para extensiones del sistema, es decir, solo se utilizan los sistemas de archivos raíz y /usr/ en la imagen. Para extensiones de configuración, el valor predeterminado es "root=verity+signed+encrypted+unprotected+absent". Cuando se ejecuta en el initrd y opera en una imagen de extensión del sistema almacenada en el directorio /.extra/sysext/ se utiliza una política ligeramente más estricta por defecto: "root=signed+absent:usr=signed+absent", véase arriba para más detalles.

Añadido en la versión 254.

--mutable=BOOL|auto|importar|efímero|efímero-importar

Establece el modo mutable.

no

Fuerza el modo inmutable incluso con directorios de enrutamiento de escritura presentes. Este es el valor predeterminado.

Añadido en la versión 256.

auto

Habilita el modo mutable individualmente para /usr/, /opt/ y /etc/ si existen subdirectorios o enlaces simbólicos de enrutamiento de escritura en /var/lib/extensions.mutable/; de lo contrario, lo deshabilita. Consulte "Inmutabilidad" anterior para obtener más información sobre el enrutamiento de escritura.

Añadido en la versión 256.

yes

Fuerza el modo mutable. Se crearán directorios de enrutamiento de escritura en /var/lib/extensions.mutable/ si no existen.

Añadido en la versión 256.

importar

Modo inmutable, pero con el contenido de los directorios de enrutamiento de escritura en /var/lib/extensions.mutable/ también fusionado en el sistema de archivos anfitrión.

Añadido en la versión 256.

efímero

Fuerza el modo mutable, pero con el contenido de los directorios de enrutamiento de escritura en /var/lib/extensions.mutable/ ignorado, y las modificaciones del sistema de archivos anfitrión descartadas después de desfusionar.

Añadido en la versión 256.

efímero-importar

Fuerza el modo mutable, con el contenido de los directorios de enrutamiento de escritura en /var/lib/extensions.mutable/ fusionado en el sistema de archivos anfitrión, pero con las modificaciones realizadas en el sistema de archivos anfitrión descartadas después de desfusionar.

Añadido en la versión 256.

systemd-confext.service(8) — systemd Manual

NAME

systemd-confext.service, systemd-confext — Manage configuration extensions

SYNOPSIS

systemd-confext merge [--force] [--no-dependencies] [--no-reload] [--no-pager] [--no-legend] [--json=MODE] [UNIT...]

systemd-confext unmerge [--force] [--no-dependencies] [--no-reload] [--no-pager] [--no-legend] [--json=MODE] [UNIT...]

systemd-confext refresh [--no-dependencies] [--no-reload] [--no-pager] [--no-legend] [--json=MODE] [UNIT...]

systemd-confext list [--no-pager] [--no-legend] [--json=MODE] [UNIT...]

systemd-confext status [--no-pager] [--no-legend] [--json=MODE] [UNIT...]

systemd-confext export [--no-pager] [--no-legend] [--json=MODE] UNIT...

systemd-confext show [--no-pager] [--no-legend] [--json=MODE] UNIT...

systemd-confext reload [--no-pager] [--no-legend] [--json=MODE]

systemd-confext help [COMMAND]

DESCRIPTION

The systemd-confext utility manages configuration extensions that are stored in /etc/systemd/system/, /usr/lib/systemd/system/, /run/systemd/system/ and /etc/systemd/user/, /usr/lib/systemd/user/, /run/systemd/user/.

Configuration files may be located in one of the directories listed above. On disk, these directories are ordered with respect to specificity. When using merge, systemd-confext makes it possible to override settings in specific configuration files. It does this by creating a new configuration file in /etc/systemd/system/ that imports the original configuration file and applies overrides.

The configuration extension directories are defined by the Discoverable Partitions Specification. See NOTES for a link to the specification.

The command operates on unit files. The UNIT... arguments may be unit names (e.g. foo.service) or paths to unit files.

When operating on unit files, systemd-confext interacts with systemd(1). Changes made via systemd-confext are reflected in systemd's runtime configuration. This may involve reloading systemd daemon or other services.

USES

The primary use case for configuration extensions is to allow for system-level configuration files to be easily overridden by system administrators without modifying the original files. This is particularly useful for package updates, as it prevents administrator customizations from being lost when a package is upgraded.

Another use case is for creating portable services, where a service can be packaged with its own configuration and deployed to any system running systemd. See NOTES for a link to the Portable Services specification.

MUTABILITY

systemd-confext manages configuration files that are generally intended to be modified by the system administrator. However, care should be taken when modifying these files, as incorrect configurations can lead to system instability or security vulnerabilities.

The tool does not modify files in /usr/lib/systemd/system/ or /usr/lib/systemd/user/. It only creates new files in /etc/systemd/system/ or /etc/systemd/user/.

COMMANDS

merge
Merges the specified unit files into the configuration extension directory. This command will create new files in /etc/systemd/system/ (or /etc/systemd/user/) that import the original unit files and apply overrides. It will automatically reload the systemd daemon if necessary.
unmerge
Removes the configuration extensions for the specified unit files. This command will remove the corresponding files from /etc/systemd/system/ (or /etc/systemd/user/) and reload the systemd daemon.
refresh
refreshes the configuration extensions for the specified unit files. This command is useful when the original unit files in /usr/lib/systemd/system/ (or /usr/lib/systemd/user/) have changed and the extensions need to be updated accordingly. It will automatically reload the systemd daemon if necessary.
list
Lists all unit files that have configuration extensions. If UNIT arguments are given, only list extensions for those specific units.
status
Shows the status of configuration extensions for the specified unit files. If UNIT arguments are given, only show status for those specific units.
export
Exports the configuration extensions for the specified unit files. This command will output the configuration extension files in a format that can be used to recreate them on another system.
show
Shows the content of the configuration extension files for the specified unit files. If UNIT arguments are given, only show extensions for those specific units.
reload
Reloads the systemd daemon configuration. This command is useful to apply changes made to configuration extension files that were not automatically reloaded.
help
Shows help information for a given command.

OPTIONS

The following options are available:

--force
Force the operation, even if it might be risky. For example, this will overwrite existing configuration extensions during a merge operation.
--no-dependencies
When used with merge, unmerge or refresh, do not process dependencies of the specified units. By default, dependencies are processed to ensure consistency.
--no-exec=BOOL
When merging configuration extensions into /etc/ the "MS_NOEXEC" mount flag is used by default. This option can be used to disable it.

Added in version 254.

--no-reload
When used with merge, unmerge or refresh, do not reload daemon after executing the changes even if an extension that is applied requires a reload via the EXTENSION_RELOAD_MANAGER= set to 1.

Added in version 255.

--no-pager
Do not pipe output into a pager.
--no-legend
Do not print the legend, i.e. column headers and the footer with hints.
--json=MODE
Shows output formatted as JSON. Expects one of "short" (for the shortest possible output without any redundant whitespace or line breaks), "pretty" (for a pretty version of the same, with indentation and line breaks) or "off" (to turn off JSON output, the default).

EXIT STATUS

On success, 0 is returned.
