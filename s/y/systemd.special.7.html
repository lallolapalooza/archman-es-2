DESCRIPCIÓN

Algunas unidades son tratadas especialmente por systemd. Muchas de ellas tienen semánticas internas especiales y no pueden ser renombradas, mientras que otras simplemente tienen un significado estándar y deben estar presentes en todos los sistemas.

UNIDADES GESTIONADAS POR EL GESTOR DE SERVICIOS DEL SISTEMA

Unidades Especiales del Sistema

-.mount

El punto de montaje raíz, es decir, la unidad de montaje para la ruta /. Esta unidad está activa incondicionalmente, durante todo el tiempo que el sistema está encendido, ya que el espacio de usuario básico se ejecuta desde este punto de montaje.

Añadido en la versión 235.

basic.target

Una unidad de destino especial que cubre el arranque básico.

systemd automáticamente añade dependencias del tipo After= para esta unidad de destino a todos los servicios (excepto a aquellos con DefaultDependencies=no).

Normalmente, esto debería activar todos los puntos de montaje locales más /var/, /tmp/ y /var/tmp/, dispositivos swap, sockets, temporizadores, unidades de rutas y otra inicialización básica necesaria para demonios de propósito general. Los puntos de montaje mencionados se tratan de forma especial para permitir que sean remotos.

Este destino normalmente no activa ninguna unidad no-destino directamente, sino indirectamente a través de otros destinos de arranque temprano. En su lugar, está destinado a ser un punto de sincronización para servicios de arranque tardío. Consulte bootup(7) para obtener detalles sobre los destinos involucrados.

boot-complete.target

Esta unidad de destino está pensada como un punto de sincronización genérico para servicios que deben determinar o actuar sobre si el proceso de arranque se completó con éxito. Ordene las unidades que deben tener éxito para que un proceso de arranque se considere exitoso antes de esta unidad, y añada una dependencia Requires= de la unidad de destino a ellas. Ordene las unidades que solo deben ejecutarse cuando se considere que el proceso de arranque ha sido exitoso después de la unidad de destino y activen la unidad de destino a partir de ella, también con Requires=. Tenga en cuenta que por defecto esta unidad de destino no forma parte de la transacción de arranque inicial, sino que se supone que se activa solo si la requieren unidades que desean ejecutarse solo en arranques exitosos.

Consulte systemd-boot-check-no-failures.service(8) para un servicio que implementa una verificación genérica de la salud del sistema y se ordena a sí mismo antes de boot-complete.target.

Consulte systemd-bless-boot.service(8) para un servicio que propaga la información de éxito del arranque al gestor de arranque y se ordena a sí mismo después de boot-complete.target.

Añadido en la versión 240.

ctrl-alt-del.target

systemd inicia esta unidad de destino cada vez que se presiona Control+Alt+Suprimir en la consola. Normalmente, esto debería ser un alias (enlace simbólico) a reboot.target.

cryptsetup.target

Una unidad de destino que activa los servicios de configuración para todos los dispositivos de bloque cifrados.

veritysetup.target

Una unidad de destino que activa los servicios de configuración para todos los dispositivos de bloque protegidos por integridad de verity.

Añadido en la versión 248.

dbus.service

Una unidad especial para el demonio de bus D-Bus. Tan pronto como este servicio se inicie completamente, systemd se conectará a él y registrará su servicio.

dbus.socket

Una unidad especial para el socket del bus del sistema D-Bus. Todas las unidades con Type=dbus obtienen automáticamente una dependencia de esta unidad.

default.target

La unidad predeterminada que systemd inicia al arrancar. Normalmente, esto debería ser un alias (enlace simbólico) a multi-user.target o graphical.target. Consulte bootup(7) para más detalles.

La unidad predeterminada que systemd inicia al arrancar se puede sobrescribir con la opción de línea de comandos del kernel systemd.unit=, o de forma más conveniente, con los nombres cortos como single, rescue, 1, 3, 5, ...; consulte systemd(1).

Para archivos de unidad típicos, establezca "WantedBy=" en un destino regular (como multi-user.target o graphical.target), en lugar de default.target, ya que dicho servicio también se ejecutará en arranques especiales como en actualizaciones del sistema, arranque de emergencia...

display-manager.service

El servicio del gestor de pantalla. Normalmente, debería ser un alias (enlace simbólico) a gdm.service o un servicio de gestor de pantalla similar.

emergency.target

Una unidad de destino especial que inicia un shell de emergencia en la consola principal. Esta unidad de destino no activa otros servicios o montajes. Es la versión más mínima de inicio del sistema para obtener un shell interactivo; los únicos procesos en ejecución suelen ser el gestor del sistema (PID 1) y el proceso del shell. Esta unidad puede ser usada especificando emergency en la línea de comandos del kernel; también se usa cuando falla una verificación del sistema de archivos en un sistema de archivos requerido y el arranque no puede continuar. Compare con rescue.target, que cumple un propósito similar, pero también inicia los servicios más básicos y monta todos los sistemas de archivos.

En muchos sentidos, arrancar en emergency.target es similar al efecto de arrancar con "init=/bin/sh" en la línea de comandos del kernel, excepto que el modo de emergencia le proporciona el sistema completo y el gestor de servicios, y permite iniciar unidades individuales para continuar el proceso de arranque en pasos.

Tenga en cuenta que dependiendo de cómo se llegue a emergency.target, el sistema de archivos raíz puede estar montado de solo lectura o de lectura/escritura (no se realiza ningún remontaje especialmente para esta unidad de destino). Por ejemplo, el sistema puede arrancar con la raíz montada de solo lectura cuando se usa ro en la línea de comandos del kernel y permanecer así para emergency.target, o el sistema puede transicionar a emergency.target después de que el sistema haya sido iniciado parcialmente y los discos ya se hayan remontado de lectura/escritura.

exit.target

Una unidad de servicio especial para apagar el sistema o el gestor de servicios de usuario. Es equivalente a poweroff.target en sistemas que no son contenedores, y también funciona en contenedores.

systemd iniciará esta unidad cuando reciba la señal SIGTERM o SIGINT cuando se ejecute como un demonio de servicios de usuario.

Normalmente, esto (indirectamente) activa shutdown.target, que a su vez debe ser conflictivo por todas las unidades que desean ser programadas para el apagado cuando el gestor de servicios comience a salir.

Añadido en la versión 186.

factory-reset.target

Una unidad de destino especial para solicitar una operación de restablecimiento de fábrica. Esto normalmente almacenará persistentemente una marca de solicitud para el próximo arranque y luego se reiniciará para restablecer el sistema a su estado de fábrica.

Consulte Restablecimiento de Fábrica[1] para más información.

Añadido en la versión 250.

factory-reset-now.target

Una unidad de destino especial que se inicia en los arranques que deben ejecutar el
e una restauración de fábrica. Puede ser utilizado para incorporar servicios adicionales que se invocarán durante una operación de restauración de fábrica. También actúa como barrera de ordenación: una vez alcanzado el objetivo, el estado de restauración de fábrica se marca como "completado".

Véase Factory Reset[1] para más información.

Añadido en la versión 258.

final.target

Una unidad objetivo especial que se utiliza durante la lógica de apagado y puede ser utilizada para incorporar servicios tardíos después de que todos los servicios normales ya hayan sido terminados y todos los montajes desmontados.

getty.target

Una unidad objetivo especial que incorpora instancias locales de TTY getty configuradas estáticamente.

graphical.target

Una unidad objetivo especial para configurar una pantalla de inicio de sesión gráfica. Esto incorpora multi-user.target.

Las unidades que son necesarias para los inicios de sesión gráficos deben añadir dependencias de tipo Wants= para su unidad a esta unidad (o multi-user.target) durante la instalación. Esto se configura mejor a través de WantedBy=graphical.target en la sección [Install] de la unidad.

hibernate.target

Una unidad objetivo especial para hibernar el sistema. Esto incorpora sleep.target.

hybrid-sleep.target

Una unidad objetivo especial para hibernar y suspender el sistema al mismo tiempo. Esto incorpora sleep.target.

Añadido en la versión 196.

suspend-then-hibernate.target

Una unidad objetivo especial para suspender el sistema durante un período de tiempo, despertarlo y ponerlo en hibernación. Esto incorpora sleep.target.

Añadido en la versión 239.

halt.target

Una unidad objetivo especial para apagar y detener el sistema. Tenga en cuenta que este objetivo es distinto de poweroff.target en que generalmente solo detiene el sistema en lugar de apagarlo.

Las aplicaciones que deseen detener el sistema no deben iniciar esta unidad directamente, sino que deben ejecutar systemctl halt (posiblemente con la opción --no-block) o llamar directamente al método D-Bus org.freedesktop.systemd1.Manager.Halt de systemd(1).

imports.target

Una unidad objetivo que incorpora todos los trabajos de descarga de imágenes de disco para que se ejecuten al arrancar el sistema. Esto es utilizado por systemd-import-generator(8).

Añadido en la versión 258.

init.scope

Esta unidad de ámbito es donde reside el sistema y el gestor de servicios (PID 1). Está activa mientras el sistema está en funcionamiento.

Añadido en la versión 235.

initrd.target

Este es el objetivo predeterminado en el initrd, similar a default.target en el sistema principal. Se utiliza para montar la raíz real y hacer la transición a ella. Consulte bootup(7) para más discusión.

Añadido en la versión 245.

initrd-fs.target

systemd-fstab-generator(8) añade automáticamente dependencias de tipo Before= a sysroot.mount y a todos los puntos de montaje encontrados en /etc/fstab que tengan la opción de montaje x-initrd.mount establecida y no tengan la opción de montaje noauto establecida. También se ordena indirectamente después de sysroot.mount. Por lo tanto, una vez alcanzado este objetivo, la jerarquía /sysroot/ está completamente configurada, en preparación para la transición al sistema operativo host.

Añadido en la versión 199.

initrd-root-device.target

Una unidad objetivo especial del initrd que se alcanza cuando el dispositivo del sistema de archivos raíz está disponible, pero antes de que se haya montado. systemd-fstab-generator(8) y systemd-gpt-auto-generator(8) configuran automáticamente las dependencias apropiadas para que esto suceda.

Añadido en la versión 230.

initrd-root-fs.target

systemd-fstab-generator(8) añade automáticamente dependencias de tipo Before= a la unidad sysroot.mount, que se genera a partir de la configuración root= de la línea de comandos del kernel (o equivalente).

Añadido en la versión 199.

initrd-usr-fs.target

systemd-fstab-generator(8) añade automáticamente dependencias de tipo Before= a la unidad sysusr.mount, que se genera a partir del argumento usr= de la línea de comandos del kernel. Los servicios pueden ordenarse después de esta unidad objetivo para ejecutarse una vez que la jerarquía /sysusr/ esté disponible, en sistemas que arrancan inicialmente sin un sistema de archivos raíz, pero con un /usr/ inicializado y necesitan acceder a él antes de configurar el sistema de archivos raíz para finalmente cambiar a él. En sistemas donde no se utiliza usr=, este objetivo se ordena después de sysroot.mount y, por lo tanto, es en gran medida equivalente a initrd-root-fs.target. En efecto, en cualquier sistema, una vez alcanzado este objetivo, el sistema de archivos que soporta /usr/ está montado, aunque posiblemente en dos ubicaciones diferentes, ya sea debajo de las jerarquías /sysusr/ o /sysroot/.

Añadido en la versión 249.

kbrequest.target

systemd inicia esta unidad objetivo cada vez que se presiona Alt+ArrowUp en la consola. Tenga en cuenta que cualquier usuario con acceso físico a la máquina podrá hacerlo, sin autenticación, por lo que debe usarse con precaución.

kexec.target

Una unidad objetivo especial para apagar y reiniciar el sistema a través de kexec.

Las aplicaciones que deseen reiniciar el sistema no deben iniciar esta unidad directamente, sino que deben ejecutar systemctl kexec (posiblemente con la opción --no-block) o llamar directamente al método D-Bus org.freedesktop.login1.Manager.RebootWithFlags() de systemd-logind(8).

Véase systemd-kexec.service(8) para más detalles sobre la operación que esta unidad objetivo incorpora.

local-fs.target

systemd-fstab-generator(8) añade automáticamente dependencias de tipo Before= a todas las unidades de montaje que se refieren a puntos de montaje locales para esta unidad objetivo. Además, añade dependencias de tipo Wants= a esta unidad objetivo para los montajes listados en /etc/fstab que tengan la opción de montaje auto establecida.

machines.target

Una unidad objetivo estándar para iniciar todos los contenedores y otras máquinas virtuales. Consulte systemd-nspawn@.service como ejemplo.

Añadido en la versión 233.

multi-user.target

Una unidad objetivo especial para configurar un sistema multiusuario (no gráfico). Esto es incorporado por graphical.target.

Las unidades que son necesarias para un sistema multiusuario deben añadir dependencias de tipo Wants= para su unidad a esta unidad durante la instalación. Esto se configura mejor a través de WantedBy=multi-user.target en la sección [Install] de la unidad.

network-online.target

Las unidades que requieren estrictamente una conexión de red configurada deben incorporar network-online.target (a través de una dependencia de tipo Wants=) y ordenarse después de él. Esta unidad objetivo está destinada a incorporar un servicio que retrasa la ejecución posterior hasta que la red esté suficientemente configurada. Lo que precisamente esto requiere se deja a la implementación del servicio de gestión de red.

Tenga en cuenta la distinción entre esta unidad y network.target. Esta unidad es una unidad activa (es decir, incorporada por el consumidor en lugar del proveedor de esta funcionalidad) e incorpora un servicio que posiblemente añade retrasos sustanciales a la ejecución posterior. En contraste, network.target es una unidad pasiva (es decir, incorporada por el proveedor de la funcionalidad, en lugar del consumidor) que generalmente no retrasa mucho la ejecución. Normalmente, network.target forma parte del arranque de la mayoría de los sistemas, mientras que network-online.target no lo es, excepto cuando al menos una unidad lo requiere. Consulte también Running Services After the Network Is Up[2] para más información.

Todas las unidades de montaje para sistemas de archivos de red remotos incorporan automáticamente esta unidad y se ordenan después de ella. Tenga en cuenta que los demonios de red que simplemente *proveen* funcionalidad a otros hosts (en contraposición a *consumir* funcionalidad de otros hosts) generalmente no necesitan incorporar esto.

systemd añade automáticamente dependencias de tipo Wants= y After= para esta unidad objetivo a todas las unidades de servicio de scripts de inicio SysV con una cabecera LSB que se refiera a la facilidad "$network".

Tenga en cuenta que esta unidad solo es útil durante la lógica de inicio del sistema original. Después de que el sistema haya completado el arranque, ya no rastreará el estado en línea del sistema. Debido a esto, no puede usarse como un concepto de monitor de conexión de red, es puramente un concepto de inicio de sistema único.

Añadido en la versión 200.

paths.target

Una unidad objetivo especial que configura todas las unidades de ruta (véase systemd.path(5) para más detalles) que deben estar activas después del arranque.

Se recomienda que las unidades de ruta instaladas por las aplicaciones sean incorporadas a través de dependencias Wants= de esta unidad. Esto se configura mejor a través de WantedBy=paths.target en la sección [Install] de la unidad de ruta.

Añadido en la versión 199.

poweroff.target

Una unidad objetivo especial para apagar y desconectar el sistema.

Las aplicaciones que deseen apagar el sistema no deben iniciar esta unidad directamente, sino que deben ejecutar systemctl poweroff (posiblemente con la opción --no-block) o llamar directamente al método D-Bus org.freedesktop.login1.Manager.PowerOff de systemd-logind(8).

reboot.target

Una unidad objetivo especial para apagar y reiniciar el sistema.

Las aplicaciones que deseen reiniciar el sistema no deben iniciar esta unidad directamente, sino que deben ejecutar systemctl reboot (posiblemente con la opción --no-block) o llamar directamente al método D-Bus org.freedesktop.login1.Manager.Reboot() de systemd-logind(8).

Véase systemd-reboot.service(8) para más detalles sobre la operación que esta unidad objetivo incorpora.

remote-cryptsetup.target

Similar a cryptsetup.target, pero para dispositivos cifrados a los que se accede a través de la red. Se utiliza para entradas de crypttab(5) marcadas con _netdev.

Añadido en la versión 235.

remote-integritysetup.target

Similar a integritysetup.target, pero para dispositivos protegidos contra la integridad a los que se accede a través de la red. Se utiliza para entradas de integritytab(5) marcadas con _netdev.

Añadido en la versión 258.

DESCRIPTION

This manual page lists and describes the special system units provided by systemd. These units are not meant to be configured or enabled by users directly, but rather used by systemd itself or as dependencies by other service units.

The actual unit files are typically located in /lib/systemd/system/, and are symlinked into /etc/systemd/system/ when necessary.

TARGET UNITS

Target units are used to group other units together and make them start or stop in a synchronized manner. They often represent a certain system state.

basic.target

The most basic system initialization target. It sets up basic system initialization like mounting file system volume instances, starting daemons specified in configuration files, setting host name, configuring network interfaces, starting low-level hardware initialization, and similar.

boot-complete.target

This target is activated when the boot process is considered complete. It is ordered after all other fundamental boot targets (local-fs.target, remote-fs.target, network.target, etc.), but before login prompts are shown or user sessions are started.

cryptsetup.target

This target is activated when all local file systems requiring encrypted devices have been set up. It is used to activate swap partitions and swap files requiring encryption. It is pulled in by local-fs.target.

ctrl-alt-del.target

This target is activated when the Ctrl-Alt-Delete key combination is pressed. It may be used to implement a clean system reboot. systemd does not reboot by default when this combination is pressed.

default.target

This target represents the default system state after boot. It is typically a symbolic link to either multi-user.target (for server-like systems) or graphical.target (for desktop systems).

emergency.target

A very minimal target that brings up the system to a single-user shell with only the most basic file systems mounted and services running. Compare with rescue.target, which is less reduced.

final.target

This target is activated very late in the boot process, after most other services have started. It's primarily used for cleanup or finalization tasks.

getty.target

This target is activated when login prompts (getty instances) are expected to be available on the virtual consoles. It is pulled in by multi-user.target.

halt.target

A target unit that stops all services and halts the system.

hardware-events.target

This target is activated when hardware event events are processed.

initrd-fs.target

This target is reached after the initrd's file systems have been mounted.

initrd-root.target

This target is reached after the initrd's root file system has been set up.

initrd.target

This target represents the completion of the initrd system initialization.

kexec.target

This target is used to perform a system reboot using kexec(8).

local-fs-pre.target

This target is activated before local file systems are mounted.

local-fs.target

This target is activated when all local file systems have been mounted.

machine-namespace.target

A target unit that is activated when systemd-machined.service(8) is running and ready to handle machine namespaces.

machine.slice

The slice unit used for system services and user sessions. Services and user processes are placed into this slice by default.

multi-user.target

This target represents a non-graphical multi-user system with networking enabled. It is typically the default target for server systems.

network-online.target

This target is activated when the system's network is configured and the network is considered "online". This is often used by services that require network connectivity to start.

network-pre.target

This target is activated before network configuration begins.

network.target

This target is activated when the system's network is up and running, but not necessarily fully configured or "online".

nss-lookup.target

This target is activated when the Name Service Switch (NSS) lookups are ready.

nss-user-lookup.target

This target is activated when user lookups via NSS are ready.

paths.target

A special target unit that sets up all path units (see systemd.path(5) for details) that shall be active after boot.

It is recommended that path units installed by applications get pulled in via Wants= dependencies from this unit. This is best configured via WantedBy=paths.target in the path unit's [Install] section.

poweroff.target

A target unit that stops all services and powers off the system.

remote-cryptsetup.target

Similar to cryptsetup.target, but for remote file systems which require encrypted devices.

remote-fs-pre.target

This target is activated before remote file systems are mounted.

remote-fs.target

Similar to local-fs.target, but for remote mount points.

systemd automatically adds dependencies of type After= for this target unit to all SysV init script service units with an LSB header referring to the "$remote_fs" facility.

rescue.target

A special target unit that pulls in the base system (including system mounts) and spawns a rescue shell. Isolate to this target in order to administer the system in single-user mode with all file systems mounted but with no services running, except for the most basic. Compare with emergency.target, which is much more reduced and does not provide the file systems or most basic services. Compare with multi-user.target, this target could be seen as single-user.target.

Use the "systemd.unit=rescue.target" kernel command line option to boot into this mode. A short alias for this kernel command line option is "1", for compatibility with SysV.

shutdown.target

A special target unit that terminates the services on system shutdown.

Services that shall be terminated on system shutdown shall add Conflicts= and Before= dependencies to this unit for their service unit, which is implicitly done when DefaultDependencies=yes is set (the default).

sigpwr.target

A special target that is started when systemd receives the SIGPWR process signal, which is normally sent by the kernel or UPS daemons when power fails.

sleep.target

A special target unit that is pulled in by suspend.target, hibernate.target, suspend-then-hibernate.target, and hybrid-sleep.target and may be used to hook units into the sleep state logic.

In order to hook external programs before the actual system sleep operation, place their command line in a service unit file's ExecStart= line (use Type=oneshot), and ensure the unit is pulled in by sleep.target and ordered before it. In order to hook program code after the actual system sleep operation (i.e. to be run after the system woke up again), place the command in ExecStop= instead, and make sure to enable StopWhenUnneeded= and RemainAfterExit=. Both approaches can be combined into one unit file in order to run programs both before and after the sleep operation.

Example 1. Combined Example

[Unit]
DefaultDependencies=no
StopWhenUnneeded=yes
Before=sleep.target
[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=/usr/bin/some-before-command
ExecStop=/usr/bin/some-after-command
[Install]
WantedBy=sleep.target

slices.target

A special target unit that sets up all slice units (see systemd.slice(5) for details) that shall always be active after boot. By default, the generic system.slice slice unit as well as the root slice unit -.slice are pulled in and ordered before this unit (see below).

Adding slice units to slices.target is generally not necessary. Instead, when some unit that uses Slice= is started, the specified slice will be started automatically. Adding WantedBy=slices.target lines to the [Install] section should only be done for units that need to be always active. In that case care needs to be taken to avoid creating a loop through the automatic dependencies on "parent" slices.

Added in version 229.

sockets.target

A special target unit that sets up all socket units (see systemd.socket(5) for details) that shall be active after boot.

Services that can be socket-activated shall add Wants= dependencies to this unit for their socket unit during installation. This is best configured via a WantedBy=sockets.target in the socket unit's [Install] section.

soft-reboot.target

A special target unit for shutting down and rebooting the userspace of the system (leaving the kernel running).

Applications wanting to reboot the system should not start this unit directly, but should instead execute systemctl soft-reboot (possibly with the --no-block option) or call systemd-logind(8)'s org.freedesktop.login1.Manager.RebootWithFlags() D-Bus method directly.

See systemd-soft-reboot.service(8) for further details of the operation this target pulls in.

Added in version 254.

storage-target-mode.target

A special target unit that can be booted into that selects the "Storage Target Mode" for the OS. In this mode all local storage disks are exposed to external systems as block devices. This invokes systemd-storagetm.service(8) which exposes all local disks as NVMe-TCP devices for access over the network. It might as well invoke other services too that make local disks available via other mechanisms.

Added in version 255.

suspend.target

A special target unit for suspending the system. This pulls in sleep.target.

swap.target

Similar to local-fs.target, but for swap partitions and swap files.

sysinit.target

systemd automatically adds dependencies of the types Requires= and After= for this target unit to all services (except for those with DefaultDependencies=no).

This target pulls in the services required for system initialization. System services pulled in by this target should declare DefaultDependencies=no and specify all their dependencies manually, including access to anything more than a read only root filesystem. For details on the dependencies of this target, refer to bootup(7).

syslog.socket

The socket unit syslog implementations should listen on. All userspace log messages will be made available on this socket. For more information about syslog integration, please consult the Syslog Interface[3] document.

system-update.target, system-update-pre.target, system-update-cleanup.service

A special target unit that is used for offline system updates. systemd-system-update-generator(8) will redirect the boot process to this target if /system-update or /etc/system-update exists. For more information see systemd.offline-updates(7).

Updates should happen before the system-update.target is reached, and the services which implement them should cause the machine to reboot. The main units executing the update should order themselves after system-update-pre.target but not pull it in. Services which want to run during system updates only, but before the actual system update is executed should order themselves before this unit and pull it in. As a safety measure, if this does not happen, and /system-update or /etc/system-update still exists after system-update.target is reached, system-update-cleanup.service will remove the symlinks and reboot the machine.

Added in version 186.

timers.target

A special target unit that sets up all timer units (see systemd.timer(5) for details) that shall be active after boot.

It is recommended that timer units installed by applications get pulled in via Wants= dependencies from this unit. This is best configured via WantedBy=timers.target in the timer unit's [Install] section.

Added in version 199.

umount.target

A special target unit that unmounts all mount and automount points on system shutdown.

Mounts that shall be unmounted on system shutdown shall add Conflicts dependencies to this unit for their mount unit, which is implicitly done when DefaultDependencies=yes is set (the default).

verity-net.target

Similar to veritysetup.target, but for verity protected devices which are accessed over the network. It is used for veritytab(5) entries marked with _netdev.

Added in version 248.

veritysetup.target

This target is used to set up device-mapper verity devices. It is pulled in by local-fs.target and remote-fs.target if needed.

Special System Units for Devices

Some target units are automatically pulled in as devices of certain kinds show up in the system. These may be used to automatically activate various services based on the specific type of the available hardware.

bluetooth.target

This target is started automatically as soon as a Bluetooth controller is plugged in or becomes available at boot.

This may be used to pull in Bluetooth management daemons dynamically when Bluetooth hardware is found.

printer.target

This target is started automatically as soon as a printer is plugged in or becomes available at boot.

This may be used to pull in printer management daemons dynamically when printer hardware is found.

smartcard.target

This target is started automatically as soon as a smartcard controller is plugged in or becomes available at boot.

This may be used to pull in smartcard management daemons dynamically when smartcard hardware is found.

sound.target

This target is started automatically as soon as a sound card is plugged in or becomes available at boot.

This may be used to pull in audio management daemons dynamically when audio hardware is found.

usb-gadget.target

This target is started automatically as soon as a USB Device Controller becomes available at boot.

This may be used to pull in usb gadget dynamically when UDC hardware is found.

Added in version 242.

tpm2.target

This target is started automatically if a TPM2 device is discovered, either by the OS or by the firmware. It acts as synchronization point for services that require TPM2 device access. The target unit is enqueued by systemd-tpm2-generator(8) if it detects that the firmware has discovered a TPM2 device but the OS kernel has not activated a driver for it yet. It is also pulled in whenever systemd-udevd.service(8) discovers a TPM2 device. The target unit is ordered after the /dev/tpmrm0 device node, so that it only becomes active once the TPM2 device is actually accessible. Early boot programs that intend to access the TPM2 device should hence order themselves after this target unit, but not pull it in.

Unidades Especiales Pasivas del Sistema

Se definen una serie de objetivos especiales del sistema que pueden utilizarse para ordenar correctamente el arranque de servicios opcionales. Estos objetivos generalmente no forman parte de la transacción de arranque inicial, a menos que sean invocados explícitamente por uno de los servicios que los implementan. Tenga en cuenta específicamente que estas unidades de objetivo *pasivas* generalmente no son invocadas por el consumidor de un servicio, sino por el proveedor del servicio. Esto significa: un servicio consumidor debe ordenarse después de estos objetivos (según corresponda), pero no invocarlos. Un servicio proveedor debe ordenarse antes de estos objetivos (según corresponda) e invocarlos (a través de una dependencia del tipo Wants=).

Tenga en cuenta que estas unidades pasivas no pueden iniciarse manualmente, es decir, "systemctl start time-sync.target" fallará con un error. Solo pueden ser invocadas por dependencia. Esto se aplica ya que existen solo con fines de ordenación y, por lo tanto, no son útiles como única unidad dentro de una transacción.

blockdev@.target

Esta unidad plantilla se utiliza para ordenar las unidades de montaje y otros consumidores de dispositivos de bloque después de los servicios que sintetizan estos dispositivos de bloque. En particular, está diseñada para usarse con servicios de almacenamiento (como systemd-cryptsetup@.service(5)/ systemd-veritysetup@.service(8)) que asignan y administran un dispositivo de bloque virtual. Los servicios de almacenamiento se ordenan antes de una instancia de blockdev@.target, y las unidades consumidoras después de ella. El orden es particularmente relevante durante el apagado, ya que garantiza que el montaje se desactive primero y el servicio que respalda el montaje más tarde. La instancia blockdev@.target debe ser invocada a través de una dependencia Wants= del demonio de almacenamiento y, por lo tanto, generalmente no ser parte de ninguna transacción a menos que se utilice un demonio de almacenamiento. El nombre de instancia para las instancias de esta unidad plantilla debe ser una ruta de nodo de dispositivo de bloque debidamente escapada, por ejemplo, blockdev@dev-mapper-foobar.target para el dispositivo de almacenamiento /dev/mapper/foobar.

Añadido en la versión 245.

cryptsetup-pre.target

Esta unidad de objetivo pasiva puede ser invocada por servicios que desean ejecutarse antes de que se configure cualquier dispositivo de bloque cifrado. Todos los dispositivos de bloque cifrados se configuran después de que se alcanza este objetivo. Dado que el orden de apagado es implícitamente el orden de inicio inverso entre las unidades, este objetivo es particularmente útil para garantizar que un servicio se apague solo después de que todos los dispositivos de bloque cifrados se detengan por completo.

Añadido en la versión 215.

veritysetup-pre.target

Esta unidad de objetivo pasiva puede ser invocada por servicios que desean ejecutarse antes de que se configure cualquier dispositivo de bloque con protección de integridad verity. Todos los dispositivos de bloque con protección de integridad verity se configuran después de que se alcanza este objetivo. Dado que el orden de apagado es implícitamente el orden de inicio inverso entre las unidades, este objetivo es particularmente útil para garantizar que un servicio se apague solo después de que todos los dispositivos de bloque con protección de integridad verity se detengan por completo.

Añadido en la versión 248.

first-boot-complete.target

Este objetivo pasivo está destinado a ser un punto de sincronización para las unidades que necesitan ejecutarse una vez durante el primer arranque. Solo después de que todas las unidades ordenadas antes de este objetivo hayan finalizado, la machine-id(5) se confirmará en el disco, marcando el primer arranque como completado. Si el arranque se interrumpe en algún momento antes de eso, el siguiente arranque volverá a ejecutar cualquier unidad con ConditionFirstBoot=yes.

Añadido en la versión 247.

getty-pre.target

Una unidad de objetivo pasiva especial. Se espera que los usuarios de este objetivo lo invoquen en la transacción de arranque a través de una dependencia (por ejemplo, Wants=). Ordene su unidad antes de esta unidad si desea utilizar la consola justo antes de que se inicie getty.

Añadido en la versión 235.

imports-pre.target

Una unidad pasiva que se ordena antes de todos los trabajos de descarga de imágenes de disco para ejecutar al arrancar el sistema. Esto es utilizado por systemd-import-generator(8).

Añadido en la versión 258.

local-fs-pre.target

Esta unidad de objetivo se ordena automáticamente antes de todos los puntos de montaje locales marcados con auto (ver arriba). Puede usarse para ejecutar ciertas unidades antes de todos los montajes locales.

network.target

Se supone que esta unidad indica cuándo está disponible la funcionalidad de red, pero solo está definida de forma muy débil lo que se supone que significa. Sin embargo, lo siguiente debería aplicarse como mínimo:
•Al arrancar, cualquier dispositivo de red sintético configurado (es decir, no dispositivos físicos que requieran hardware para aparecer y ser sondeados, sino dispositivos virtuales como puentes y similares que se crean mediante programación) que no dependan de ningún hardware subyacente debería asignarse cuando se alcance este objetivo. No es necesario que estas interfaces también hayan completado la configuración a nivel de IP cuando se alcance network.target.
•Al apagar, una unidad que se ordena después de network.target se detendrá antes de que la red — hasta el nivel que pueda estar configurada en ese momento — se apague. Por lo tanto, es útil al escribir archivos de servicio que requieren acceso a la red al apagar, que deberían ordenarse después de este objetivo, pero no invocarlo. Consulte también Ejecución de Servicios Después de que la Red Esté Arriba[2] para obtener más información.

Debe enfatizarse que al arrancar no hay garantía de que los dispositivos basados en hardware hayan aparecido cuando se alcanza este objetivo, o incluso que hayan adquirido una configuración IP completa. Para ese propósito, use network-online.target como se describe arriba.

network-pre.target

Esta unidad de objetivo pasiva puede ser invocada por servicios que desean ejecutarse antes de que se configure cualquier red, por ejemplo, con el propósito de configurar un firewall. Todo el software de gestión de red se ordena después de este objetivo, pero no lo invoca. Consulte también Ejecución de Servicios Después de que la Red Esté Arriba[2] para obtener más información.

Añadido en la versión 214.

nss-lookup.target

Un objetivo que debe usarse como punto de sincronización para todas las búsquedas de servicios de nombres de host/red. Tenga en cuenta que esto es independiente de las búsquedas de nombres de usuario/grupo de UNIX para las cuales se debe usar nss-user-lookup.target. Todos los servicios para los que la disponibilidad de la resolución completa de nombres de host/red es esencial deben ordenarse después de este objetivo, pero no invocarlo. systemd agrega automáticamente dependencias de tipo After= para esta unidad de objetivo a todas las unidades de servicio de script de inicio SysV con una cabecera LSB que se refiere a la facilidad "$named".

nss-user-lookup.target

Un objetivo que debe usarse como punto de sincronización para todas las búsquedas regulares de servicios de nombres de usuario/grupo de UNIX. Tenga en cuenta que esto es independiente de las búsquedas de nombres de host/red para las cuales se debe usar nss-lookup.target. Todos los servicios para los que la disponibilidad de la base de datos completa de usuarios/grupos es esencial deben ordenarse después de este objetivo, pero no invocarlo. Todos los servicios que proporcionan partes de la base de datos de usuarios/grupos deben ordenarse antes de este objetivo e invocarlo. Tenga en cuenta que esta unidad solo es relevante para usuarios y grupos regulares; los usuarios y grupos del sistema deben ser resolubles desde el principio del arranque, y por lo tanto no necesitan ningún orden especial con respecto a este objetivo.

remote-fs-pre.target

Esta unidad de objetivo se ordena automáticamente antes de todas las unidades de puntos de montaje (ver arriba) y dispositivos cryptsetup/veritysetup marcados con _netdev. Puede usarse para ejecutar ciertas unidades antes de que se establezcan los dispositivos y montajes cifrados remotos. Tenga en cuenta que esta unidad generalmente no forma parte de la transacción inicial, a menos que la unidad que desea ordenarse antes de todos los montajes remotos la invoque a través de una dependencia del tipo Wants=. Si la unidad desea ser invocada por el primer montaje remoto que aparece, debería usar network-online.target (ver arriba).

rpcbind.target

El portmapper/rpcbind invoca este objetivo y se ordena antes de él, para indicar su disponibilidad. systemd agrega automáticamente dependencias de tipo After= para esta unidad de objetivo a todas las unidades de servicio de script de inicio SysV con una cabecera LSB que se refiere a la facilidad "$portmap".

ssh-access.target

Las unidades de servicio y socket que proporcionan acceso remoto seguro SSH al sistema local deben invocar esta unidad y ordenarse antes que ella. Se supone que actúa como un hito que indica si y cuándo el acceso SSH al sistema está disponible. Solo debe activarse cuando se vincula un puerto SSH para clientes remotos (es decir, si SSH se utiliza como un mecanismo local de escalada de privilegios, *no* debería involucrar esta unidad de objetivo), independientemente de las opciones de protocolo, es decir, independientemente de si se utiliza IPv4, IPv6 o AF_VSOCK.

Añadido en la versión 256.

time-set.target

Los servicios responsables de establecer el reloj del sistema (CLOCK_REALTIME) desde una fuente local (como un archivo de marca de tiempo mantenido o un reloj de tiempo real impreciso) deben invocar este objetivo y ordenarse antes de él. Los servicios para los que se desea un tiempo aproximado y aproximadamente monótono deben ordenarse después de esta unidad, pero no invocarla.

Este objetivo no proporciona las garantías de precisión de time-sync.target (ver más abajo), sin embargo, no depende de que las fuentes de reloj remotas sean alcanzables, es decir, el objetivo generalmente no se retrasa por problemas de red y similares. Se recomienda el uso de este objetivo para servicios donde se desea una precisión de reloj aproximada y monotonicidad aproximada, pero la activación no debe retrasarse debido a una comunicación de red posiblemente poco fiable.

El gestor de servicios agrega automáticamente dependencias de tipo After= para esta unidad de objetivo a todas las unidades de temporizador con al menos una directiva OnCalendar=.

El servicio systemd-timesyncd.service(8) es un demonio simple que invoca este objetivo y se ordena antes de él. Además de implementar el protocolo de red SNTP, mantiene un archivo de marca de tiempo en el disco cuyo tiempo de modificación se actualiza regularmente. Al iniciar el servicio, el reloj del sistema local se establece a partir de esa hora de modificación, asegurando que aumente de forma aproximadamente monótona.

Tenga en cuenta que ordenar una unidad después de time-set.target solo tiene efecto si realmente hay un servicio ordenado antes que ella que lo retrasa hasta que el reloj se ajusta para una monotonicidad aproximada. De lo contrario, este objetivo podría alcanzarse antes de que el reloj se ajuste para ser aproximadamente monótono. Habilite systemd-timesyncd.service(8), o una implementación NTP alternativa para retrasar el objetivo.

Añadido en la versión 242.

time-sync.target

Servicios que indican la sincronización completada del reloj del sistema (CLOCK_REALTIME) con una fuente remota

time-sync.target

time-sync.target se alcanza cuando se ha logrado la sincronización de la hora del sistema. Este objetivo es un punto de sincronización para los servicios que requieren que la hora del sistema se sincronice con una fuente de hora externa y precisa.

Los servicios que necesitan una hora exacta deben ser ordenados después de esta unidad y configurarse para que la arrastren. Los servicios para los que la hora precisa es esencial deben ordenarse después de esta unidad, pero sin arrastrarla.

El gestor de servicios añade automáticamente dependencias de tipo After= para esta unidad de destino a todas las unidades de servicio de scripts de inicio SysV con una cabecera LSB que hace referencia a la instalación de "$time", así como a todas las unidades de temporizador con al menos una directiva OnCalendar=.

Este objetivo proporciona garantías de precisión del reloj más estrictas que time-set.target (ver arriba), pero probablemente requiere comunicación de red y, por lo tanto, introduce retrasos impredecibles. Los servicios que requieren precisión del reloj y donde los retrasos en la comunicación de red son aceptables deben usar este objetivo. Los servicios que requieren un reloj menos preciso, y solo un comportamiento de reloj aproximado y más o menos monótono, deben usar time-set.target en su lugar.

Tenga en cuenta que ordenar una unidad después de time-sync.target solo tiene efecto si hay un servicio ordenado antes que ella que la retrasa hasta que se alcanza la sincronización del reloj. De lo contrario, este objetivo podría alcanzarse antes de que el reloj se sincronice con cualquier reloj de referencia preciso remoto. Al utilizar systemd-timesyncd.service(8), habilite systemd-time-wait-sync.service(8) para retrasar el objetivo; o utilice un servicio equivalente para otras implementaciones NTP.

UNIDADES ADMINISTRADAS POR EL GESTOR DE SERVICIOS DE USUARIO

Unidades de Usuario Especiales

Cuando systemd se ejecuta como una instancia de usuario, las siguientes unidades especiales están disponibles:

default.target

Este es el objetivo principal del gestor de servicios de usuario, iniciado por defecto cuando se invoca el gestor de servicios. Varios servicios que componen la sesión normal del usuario deben ser arrastrados a este objetivo. A este respecto, default.target es similar a multi-user.target en la instancia del sistema, pero es una unidad real, no un alias.

Añadido en la versión 242.

capsule@.target

Este es el objetivo principal de los gestores de servicios de cápsulas, iniciado por defecto, instanciado con el nombre de la cápsula. Esto puede usarse para definir diferentes conjuntos de unidades que se inician para diferentes cápsulas a través de definiciones de unidades genéricas. Para más detalles sobre las cápsulas, consulte capsule@.service(5).

Añadido en la versión 255.

Además, las siguientes unidades están disponibles que tienen definiciones similares a sus contrapartes del sistema: exit.target, shutdown.target, sockets.target, timers.target, paths.target, bluetooth.target, printer.target, smartcard.target, sound.target.

Unidades Pasivas de Usuario Especiales

graphical-session.target

Este objetivo está activo siempre que se esté ejecutando alguna sesión gráfica. Se utiliza para detener los servicios de usuario que solo se aplican a una sesión gráfica (X, Wayland, etc.) cuando la sesión termina. Dichos servicios deben tener "PartOf=graphical-session.target" en su sección [Unit]. Un objetivo para una sesión particular (por ejemplo, gnome-session.target) inicia y detiene "graphical-session.target" con "BindsTo=graphical-session.target".

Qué servicios se inician por un objetivo de sesión se determina por las dependencias "Wants=" y "Requires=". Para los servicios que se pueden habilitar de forma independiente, se deben usar enlaces simbólicos en ".wants/" y ".requires/", consulte systemd.unit(5). Dichos enlaces simbólicos deben distribuirse en paquetes, o añadirse dinámicamente después de la instalación, por ejemplo, usando "systemctl add-wants", consulte systemctl(1).

Ejemplo 2. Nautilus como parte de una sesión GNOME "gnome-session.target" arrastra Nautilus como servicio de nivel superior:

[Unit]
Description=Servicios de usuario systemd para sesión gráfica GNOME
Wants=nautilus.service
BindsTo=graphical-session.target

"nautilus.service" se detiene cuando la sesión termina:

[Unit]
Description=Renderizar los iconos del escritorio con Nautilus
PartOf=graphical-session.target
[Service]
...

Añadido en la versión 234.

graphical-session-pre.target

Este objetivo contiene servicios que configuran el entorno o la configuración global de una sesión gráfica, como agentes SSH/GPG (que necesitan exportar una variable de entorno a todos los procesos de escritorio) o la migración de claves d-conf obsoletas después de una actualización del sistema operativo (que debe ocurrir antes de iniciar cualquier proceso que pueda usarlas). Este objetivo debe iniciarse antes de iniciar una sesión gráfica como gnome-session.target.

Añadido en la versión 234.

xdg-desktop-autostart.target

La especificación XDG define una forma de iniciar automáticamente aplicaciones utilizando archivos de escritorio XDG. systemd distribuye systemd-xdg-autostart-generator(8) para los archivos de escritorio XDG en los directorios de inicio automático. Los Entornos de Escritorio pueden optar por utilizar este servicio añadiendo una dependencia Wants= en xdg-desktop-autostart.target.

Añadido en la versión 246.

-.slice

app.slice

Por defecto, todos los servicios y aplicaciones de usuario administrados por systemd se encuentran en este slice. Todas las aplicaciones iniciadas interactivamente, como navegadores web y editores de texto, así como servicios no críticos, deben colocarse en este slice.

session.slice

Todos los servicios y aplicaciones esenciales requeridos para la sesión deben usar este slice. Estos son servicios que no se pueden reiniciar fácilmente o donde los problemas de latencia pueden afectar la interactividad del sistema y las aplicaciones. Esto incluye el servidor de pantalla, lectores de pantalla y otros servicios como DBus o portales XDG. Dichos servicios deben configurarse para ser parte de este slice añadiendo Slice=session.slice a sus archivos de unidad.

Añadido en la versión 247.

background.slice

Todos los servicios que ejecutan tareas en segundo plano de baja prioridad deben usar este slice. Esto permite que los recursos se asignen preferentemente a los otros slices. Los ejemplos incluyen tareas no interactivas como la indexación de archivos o las operaciones de copia de seguridad donde la latencia no es importante.

Añadido en la versión 247.
