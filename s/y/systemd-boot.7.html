NOMBRE

systemd-boot, sd-boot - Un gestor de arranque UEFI simple

DESCRIPCIÓN

systemd-boot (abreviado: sd-boot) es un gestor de arranque UEFI simple. Proporciona un menú textual para seleccionar la entrada a arrancar y un editor para la línea de comandos del kernel. systemd-boot solo soporta sistemas con firmware UEFI.

systemd-boot carga la información de las entradas de arranque desde la partición del sistema EFI (ESP), normalmente montada en /efi/, /boot/, o /boot/efi/ durante el tiempo de ejecución del sistema operativo, así como desde la partición Extended Boot Loader (XBOOTLDR) si existe (normalmente montada en /boot/). Los fragmentos de archivos de configuración, kernels, initrds y otras imágenes EFI a arrancar generalmente deben residir en la ESP o en la partición Extended Boot Loader. Los kernels de Linux deben estar compilados con CONFIG_EFI_STUB para poder ser ejecutados directamente como una imagen EFI. Durante el arranque, systemd-boot ensambla automáticamente una lista de entradas de arranque de las siguientes fuentes:

•Entradas de arranque definidas con archivos de descripción de Tipo #1 de la Especificación del Cargador de Arranque[1] ubicados en /loader/entries/ en la ESP y en la Partición Extended Boot Loader. Estos normalmente describen imágenes de kernel de Linux con imágenes initrd asociadas, pero alternativamente también pueden describir otros ejecutables EFI arbitrarios.
•Imágenes de kernel unificadas, Tipo #2 de la Especificación del Cargador de Arranque[1], que son binarios ejecutables EFI en /EFI/Linux/ en la ESP y en la Partición Extended Boot Loader.
•El gestor de arranque EFI de Microsoft Windows, si está instalado.
•El gestor de arranque de Apple macOS, si está instalado.
•La shell EFI, si está instalada.
•Una opción de "Reiniciar en la Interfaz de Firmware", si es soportada por el firmware UEFI.
•Inscripción de variables de Arranque Seguro si el firmware UEFI está en modo de configuración y se proporcionan archivos en la ESP.

systemd-boot soporta las siguientes características:

•Cambios básicos de configuración del gestor de arranque (como configuración de tiempo de espera, selección de entrada de arranque por defecto, ...) pueden hacerse directamente desde la interfaz del gestor de arranque al arrancar, así como durante el tiempo de ejecución del sistema con variables EFI.
•El gestor de arranque se integra con el comando systemctl para implementar características como systemctl reboot --boot-loader-entry=... (para reiniciar en una entrada específica del menú de arranque, es decir, "reiniciar en Windows") y systemctl reboot --boot-loader-menu=... (para reiniciar en el menú del gestor de arranque), implementando la Interfaz del Cargador de Arranque[2]. Ver systemctl(1) para más detalles.
•Una variable EFI establecida por el gestor de arranque informa al SO sobre la Partición del Sistema EFI utilizada durante el arranque. Esto se usa para montar automáticamente la Partición del Sistema EFI correcta en /efi/ o /boot/ durante el tiempo de ejecución del SO. Ver systemd-gpt-auto-generator(8) para más detalles.
•El gestor de arranque proporciona información sobre el tiempo de arranque invertido en el firmware UEFI utilizando la Interfaz del Cargador de Arranque[2]. Esta información puede mostrarse usando systemd-analyze(1).
•El gestor de arranque implementa el conteo de arranques y el fallback automático a entradas de arranque anteriores y funcionales en caso de fallo. Ver Evaluación Automática del Arranque[3].
•El gestor de arranque lee opcionalmente una semilla aleatoria de la partición ESP, la combina con un 'token de sistema' almacenado en una variable EFI persistente y deriva una semilla aleatoria para que el SO la use como inicialización del pool de entropía, proporcionando un pool de entropía completo durante el arranque temprano.
•El gestor de arranque permite la inscripción de variables de Arranque Seguro si el firmware UEFI está en modo de configuración. Adicionalmente, las variables pueden ser inscritas automáticamente si se configuran.

bootctl(1) puede ser usado desde un sistema en ejecución para localizar la ESP y la Partición Extended Boot Loader, listar las entradas disponibles e instalar el propio systemd-boot.

kernel-install(8) puede ser usado para copiar imágenes de kernel a la ESP o a la Partición Extended Boot Loader y para generar archivos de descripción conformes a la Especificación del Cargador de Arranque.

systemd-stub(7) puede ser usado como stub de arranque UEFI para kernels ejecutados, lo cual es útil para mostrar salpicaduras gráficas de arranque antes de transicionar al mundo Linux. También es capaz de recoger automáticamente imágenes de extensión del sistema y archivos de credenciales auxiliares (para parametrización de arranque), como archivos complementarios a las imágenes de kernel arrancadas.

DESCRIPCIÓN

systemd-boot se puede configurar para actualizar automáticamente una clase de entradas de arranque del menú de arranque en un número configurable de intentos de arranque. Esto se puede usar para probar automáticamente nuevas versiones del kernel o el propio systemd-boot. systemd-boot implementa la especificación de arranque automático [3]. Esta función solo está disponible cuando systemd-boot se arranca en modo UEFI y no se arranca desde un firmware de máquina virtual que se usa directamente.

Solo las entradas de arranque que siguen la especificación de arranque [1] y que se configuran mediante la actualización de entradas de menú del boot loader (como se describe en la sección bootctl(1)) están sujetas a esta función. Las imágenes de kernel unificadas que son detectadas por systemd-boot y que se colocan en el directorio /efi/loader/entries/ también están sujetas a esta función.

La característica solo se puede habilitar mediante el servicio systemd-boot-update.service. Este servicio habilita la función si el archivo de configuración /etc/systemd/boot/systemd-boot.conf está presente y contiene la opción `automatic-updates=true`. De lo contrario, el comportamiento es el mismo que en versiones anteriores de systemd-boot.

Las entradas de arranque en modo de actualización automática están sujetas a reescritura y se les puede asignar un estado que indica si un intento de arranque tuvo éxito. Si un intento de arranque no tiene éxito, las entradas de arranque en modo de actualización automática se irán modificando progresivamente. Si un intento de arranque tiene éxito, el sistema reconocerá que ha tenido éxito y cambiará el estado de la entrada de arranque en consecuencia. Con el tiempo, esto significa que solo las entradas de arranque que fallaron repetidamente serán eliminadas progresivamente, mientras que las entradas de arranque exitosas permanecerán en su lugar.

Se puede configurar la cantidad de intentos de arranque a través del archivo de configuración /etc/systemd/boot/systemd-boot.conf, con la opción `max-tries=`. Por defecto, se configuran 3 intentos de arranque, lo que significa que la entrada de arranque actual se mantendrá hasta un máximo de 3 intentos de arranque fallidos antes de ser reemplazada por la entrada de arranque anterior que sí tuvo éxito. Si solo queda una entrada de arranque y falla, se seguirá intentando arrancar esa entrada.

La función de actualización automática de systemd-boot no modifica ni elimina entradas de arranque que no estén configuradas para ello. Las entradas de arranque que no sean modificables, por ejemplo, porque se encuentren en una partición de solo lectura, no se verán afectadas por esta función.

A diferencia de las entradas de arranque normales, las entradas de arranque en modo de actualización automática tienen un sufijo numérico. Por ejemplo, una entrada de arranque con el nombre arch.conf se puede transformar en arch+3.conf, donde el número indica el número de intentos de arranque restantes. Después de un intento de arranque exitoso, la entrada de arranque se renombrará a arch.conf, lo que indica que ya no está sujeta a actualizaciones automáticas. Si un intento de arranque falla, la entrada de arranque se renombrará a arch+2.conf, y así sucesivamente, hasta que el número de intentos de arranque restantes llegue a cero. En ese punto, la entrada de arranque se considerará fallida y se intentará arrancar la siguiente entrada de arranque válida.

El servicio systemd-bless-boot.service(8) se utiliza para marcar un intento de arranque como exitoso. Este servicio se ejecuta al final del proceso de arranque y renombra la entrada de arranque actual de `entrada+N.conf` a `entrada.conf` para indicar que se ha arrancado correctamente.

Esta función solo se aplica a las entradas de arranque UEFI de systemd-boot. No afecta a otros gestores de arranque ni a otros tipos de entradas de arranque.

La función de recuento de arranques se puede deshabilitar en cualquier momento eliminando el archivo de configuración /etc/systemd/boot/systemd-boot.conf o estableciendo la opción `automatic-updates=false` en el archivo.

Se añadió en la versión 258.

CUENTA DE ARRANQUES

systemd-boot implementa un mecanismo simple de cuenta de arranques sobre la Especificación del Gestor de Arranque[1], para la reversión automática y desatendida a versiones anteriores del kernel / entradas del gestor de arranque cuando una entrada específica falla continuamente. Cualquier archivo de entrada del gestor de arranque y archivo de imagen de kernel unificada que contenga un "+" seguido de uno o dos números (si son dos, deben estar separados por un "-"), antes del sufijo .conf o .efi está sujeto a la cuenta de arranques: el primero de los dos números ('intentos restantes') se reduce en uno en cada intento de arranque, el segundo de los dos números ('intentos realizados') se incrementa en uno (si 'intentos realizados' está ausente se considera equivalente a 0). Dependiendo del valor actual de estos dos contadores, la entrada de arranque se considera en uno de los tres estados:

1. Si el contador de 'intentos restantes' de una entrada es mayor que cero, la entrada se considera en estado 'indeterminado'. Esto significa que la entrada aún no ha completado el arranque con éxito, pero tampoco se ha determinado que no funciona.
2. Si el contador de 'intentos restantes' de una entrada es cero, se considera en estado 'malo'. Esto significa que no se realizarán más intentos para arrancar este elemento (es decir, a menos que todas las demás entradas de arranque también estén en estado 'malo'), ya que todos los intentos de arrancar esta entrada no se han completado con éxito.
3. Si los contadores de 'intentos restantes' e 'intentos realizados' de una entrada están ausentes, se considera en estado 'bueno'. Esto significa que la cuenta de arranques para la entrada está desactivada, ya que arrancó con éxito al menos una vez. El servicio systemd-bless-boot.service(8) mueve la entrada actualmente arrancada del estado 'indeterminado' al estado 'bueno' cuando un intento de arranque se completa con éxito.

En general, cuando se añaden nuevas entradas al gestor de arranque, comienzan en estado 'indeterminado', es decir, con un contador de 'intentos restantes' mayor que cero. La entrada de arranque permanece en este estado hasta que logra completar un arranque completo con éxito al menos una vez (en cuyo caso estará en estado 'bueno') — o el contador de 'intentos restantes' llega a cero (en cuyo caso estará en estado 'malo').

Ejemplo: digamos que un archivo de entrada del gestor de arranque foo.conf está configurado para 3 intentos de arranque. El instalador lo creará en adelante bajo el nombre foo+3.conf. En el primer arranque, el gestor de arranque lo renombrará a foo+2-1.conf. Si ese arranque no se completa con éxito, el gestor de arranque lo renombrará a foo+1-2.conf en el siguiente arranque. Si eso también falla, finalmente será renombrado a foo+0-3.conf por el gestor de arranque en el próximo arranque, después de lo cual se considerará 'malo'. Si el arranque tiene éxito, sin embargo, el archivo de entrada será renombrado a foo.conf por el SO, de modo que se considerará 'bueno' a partir de entonces.

El menú de arranque tiene en cuenta el contador de 'intentos restantes' al ordenar las entradas del menú: las entradas en estado 'malo' se ordenan al principio de la lista, y las entradas en estado 'bueno' o 'indeterminado' al final. El usuario puede elegir libremente arrancar cualquier entrada del menú, incluidas las que ya están marcadas como 'malas'. Si la entrada del menú a arrancar se determina automáticamente, esto significa que las entradas 'buenas' o 'indeterminadas' generalmente se prefieren (ya que el elemento inferior del menú es el que se arranca por defecto), y las entradas 'malas' solo se considerarán si no quedan entradas 'buenas' o 'indeterminadas'.

El marco de instalación del kernel kernel-install(8) opcionalmente establece el contador inicial de 'intentos restantes' al valor especificado en /etc/kernel/tries cuando se crea por primera vez una entrada del gestor de arranque.

USO DE SYSTEMD-BOOT EN MÁQUINAS VIRTUALES

Cuando se usa qemu con OVMF (Firmware UEFI para máquinas virtuales), el modificador -kernel funciona no solo para kernels de Linux, sino para cualquier binario EFI, incluyendo sd-boot e imágenes de kernel de Linux unificadas. Ejemplo de línea de comandos para cargar systemd-boot en x64:

qemu-system-x86_64 [ ... ] -kernel /usr/lib/systemd/boot/efi/systemd-bootx64.efi

systemd-boot detectará que se inició directamente en lugar de ser cargado desde ESP y buscará el ESP en ese caso, teniendo en cuenta la información del orden de arranque del hipervisor (si está disponible).
