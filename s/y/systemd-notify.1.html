NOMBRE

systemd-notify - Notificar al gestor de servicios sobre la finalización del inicio y otros cambios de estado del demonio

SINOPSIS

systemd-notify [OPCIONES...] [VARIABLE=VALOR...]

systemd-notify --exec [OPCIONES...] [VARIABLE=VALOR...] ; -- {COMANDO...}

systemd-notify --fork [OPCIONES...] -- {COMANDO...}

DESCRIPCIÓN

systemd-notify puede ser llamado por scripts de servicio para notificar al gestor de servicios que lo invoca sobre cambios de estado. Puede ser utilizado para enviar información arbitraria, codificada en una lista de cadenas estilo bloque de entorno. Lo más importante es que puede ser utilizado para la notificación de finalización de inicio.

Esto es principalmente un envoltorio para sd_notify() y pone esta funcionalidad a disposición de los scripts de shell. Para más detalles consulte sd_notify(3).

La línea de comandos puede contener una lista de variables de entorno para enviar como parte de la actualización de estado.

Tenga en cuenta que systemd rechazará la recepción de actualizaciones de estado de este comando a menos que NotifyAccess= esté configurado adecuadamente para la unidad de servicio desde la que se llama a este comando. Consulte systemd.service(5) para más detalles.

Tenga en cuenta que las notificaciones de sd_notify() solo pueden atribuirse correctamente a las unidades si el proceso que envía el mensaje todavía está activo en el momento en que el gestor de servicios procesa el mensaje, o si el proceso que envía el mensaje es rastreado explícitamente en tiempo de ejecución por el gestor de servicios. Esto último ocurre si el gestor de servicios creó originalmente el proceso, es decir, en todos los procesos que coinciden con NotifyAccess=main o NotifyAccess=exec. Por el contrario, si un proceso auxiliar de la unidad envía un mensaje sd_notify() y sale inmediatamente, es posible que el gestor de servicios no pueda atribuir correctamente el mensaje a la unidad y, por lo tanto, lo ignorará, incluso si NotifyAccess=all está configurado para ella. Para abordar esto, systemd-notify esperará hasta que el mensaje de notificación haya sido procesado por el gestor de servicios. Cuando se usa --no-block, esta sincronización para la recepción de notificaciones se desactiva y, por lo tanto, la carrera mencionada anteriormente puede ocurrir si el proceso que invoca no es el gestor de servicios o no fue generado por el gestor de servicios.

systemd-notify intentará primero invocar sd_notify() pretendiendo tener el PID del proceso padre de systemd-notify (es decir, el proceso que invoca). Esto solo tendrá éxito cuando se invoque con privilegios suficientes. En caso de fallo, recurrirá a invocarlo bajo su propio PID. Este comportamiento es útil para que, cuando la herramienta se invoque desde un script de shell, el proceso de shell — y no el proceso systemd-notify — aparezca como el remitente del mensaje, lo cual es útil si el proceso de shell es el proceso principal de un servicio, debido a las limitaciones de NotifyAccess=all. Use el interruptor --pid= para ajustar este comportamiento.

OPCIONES

Se entienden las siguientes opciones:

--ready

Informar al gestor de servicios que lo invoca sobre la finalización del inicio o la recarga de la configuración del servicio. Esto equivale a systemd-notify READY=1. Para detalles sobre la semántica de esta opción, consulte sd_notify(3).

--reloading

Informar al gestor de servicios que lo invoca sobre el inicio de un ciclo de recarga de configuración. Esto equivale a systemd-notify RELOADING=1 (pero también establece implícitamente un campo MONOTONIC_USEC= como se requiere para servicios Type=notify-reload, consulte systemd.service(5) para más detalles). Para detalles sobre la semántica de esta opción, consulte sd_notify(3).

Añadido en la versión 253.

--stopping

Informar al gestor de servicios que lo invoca sobre el inicio de la fase de apagado del servicio. Esto equivale a systemd-notify STOPPING=1. Para detalles sobre la semántica de esta opción, consulte sd_notify(3).

Añadido en la versión 253.

--pid=

Informar al gestor de servicios sobre el PID principal del servicio. Toma un PID como argumento. Si el argumento se especifica como "auto" u se omite, se utiliza el PID del proceso que invocó systemd-notify, a menos que sea el gestor de servicios. Si el argumento se especifica como "self", se utiliza el PID del propio comando systemd-notify, y si se especifica "parent", se utiliza el PID del proceso que llama — incluso si es el gestor de servicios. --pid=auto equivale a systemd-notify --pid=$PID. Para detalles sobre la semántica de esta opción, consulte sd_notify(3).

systemd-notify intentará primero invocar sd_notify() pretendiendo tener el PID especificado con --pid=. Esto solo tendrá éxito cuando se invoque con privilegios suficientes. En caso de fallo, recurrirá a invocarlo bajo su propio PID. Efectivamente, esto significa que una invocación privilegiada de systemd-notify --pid= puede eludir las restricciones NotifyAccess=main o NotifyAccess=exec impuestas a un servicio.

Si se utiliza este interruptor en una invocación no privilegiada de systemd-notify desde un proceso que se convertirá en el nuevo proceso principal de un servicio — y que no es el proceso generado por el gestor de servicios (o el proceso principal actual) —, entonces es esencial establecer NotifyAccess=all en el archivo de unidad del servicio, o de lo contrario la notificación se ignorará por razones de seguridad. Consulte systemd.service(5) para más detalles.

--uid=USUARIO

Establece el ID de usuario desde el cual enviar la notificación. Toma un nombre de usuario de UNIX o un UID numérico. Cuando se especifica, el mensaje de notificación se enviará con el UID especificado como remitente, en lugar del usuario con el que se invocó el comando. Esta opción requiere privilegios suficientes para poder manipular la identidad del usuario del proceso.

Añadido en la versión 237.

--status=

Envía una cadena de estado legible por humanos de forma libre para el demonio al gestor de servicios. Esta opción toma la cadena de estado como argumento. Esto equivale a systemd-notify STATUS=.... Para detalles sobre la semántica de esta opción, consulte sd_notify(3). Esta información se muestra en la salida de status de systemctl(1), entre otros lugares.

--booted

Devuelve 0 si el sistema se inició con systemd, de lo contrario un valor distinto de cero. Si se pasa esta opción, no se envía ningún mensaje. Por lo tanto, esta opción no está relacionada con las demás opciones. Para detalles sobre la semántica de esta opción, consulte sd_booted(3). Una forma alternativa de comprobar este estado es llamar a systemctl(1) con el comando is-system-running. Devolverá "offline" si el sistema no se inició con systemd.

--no-block

No esperar síncronamente a que finalice la operación solicitada. El uso de esta opción solo se recomienda cuando systemd-notify es generado por el gestor de servicios, o cuando el proceso que lo invoca es generado directamente por el gestor de servicios y tiene suficientes privilegios para permitir que systemd-notify envíe la notificación en su nombre. Enviar notificaciones con esta opción configurada es propenso a condiciones de carrera en todos los demás casos.

Añadido en la versión 246.

--exec

Si se especifica, systemd-notify ejecutará otra línea de comandos después de completar su operación, reemplazando su propio proceso. Si se usa, la lista de asignaciones a incluir en el mensaje enviado debe ir seguida de un carácter ";" (como argumento separado), seguido de la línea de comandos a ejecutar. Esto permite encadenar comandos, es decir, emitir una operación, seguida inmediatamente por otra, sin cambiar los PIDs.

Tenga en cuenta que muchos shells interpretan ";" como su propio separador para las líneas de comandos, por lo tanto, cuando systemd-notify es invocado desde un shell, el punto y coma debe ser escapado generalmente como "\;".

Añadido en la versión 254.

Añadido en la versión 254.

--fdname=

Establece un nombre para asignar a los descriptores de archivo pasados a través de --fd= (ver arriba). Esto controla el campo "FDNAME=". Esta configuración solo se puede especificar una vez y se aplica a todos los descriptores de archivo pasados. Invoque esta herramienta varias veces en caso de que se deban enviar varios descriptores de archivo con diferentes nombres de descriptores de archivo.

Añadido en la versión 254.

--fork

En lugar de enviar un mensaje de notificación, crea un proceso hijo de línea de comandos y espera hasta que se reciba un mensaje "READY=1" de él. En otras palabras: esto hace que systemd-notify sea el receptor de los mensajes de notificación en lugar del remitente, intercambiando roles. Esto es útil para crear rápidamente un proceso que implemente el protocolo sd_notify() desde un script de shell. La línea de comandos invocada tendrá la entrada estándar y la salida estándar conectadas a /dev/null, pero el error estándar se heredará del proceso invocador. El ID numérico del proceso se escribe en la salida estándar por systemd-notify (a menos que se especifique --quiet), que puede usarse para terminar posteriormente el proceso creado.

Tenga en cuenta que los procesos creados de esta manera probablemente seguirán ejecutándose después de que systemd-notify ya haya regresado, lo que, por lo tanto, resultará en que se les reasigne al proceso recolector de procesos más cercano, es decir, típicamente al gestor de servicios por usuario o del sistema.

Tenga en cuenta que esta opción no debe usarse para invocar servicios completos ad-hoc, use systemd-run para eso.

También tenga en cuenta que cuando se invoca con este interruptor, systemd-notify saldrá con éxito bajo dos condiciones distintas:

1.systemd-notify recibió una notificación "READY=1" del hijo que acaba de crear.
2.El proceso hijo salió limpiamente (con estado de salida cero) antes de enviar "READY=1".

Ejemplo de uso:

# PID=$(systemd-notify --fork -- mycommand)
...
kill "$PID"
unset PID

Añadido en la versión 258.

--quiet, -q

Desactiva la salida del ID numérico del proceso cuando se usa --fork.

Añadido en la versión 258.

Imprime un breve texto de ayuda y sale.

--version

ESTADO DE SALIDA

En caso de éxito, se devuelve 0, en caso contrario, un código de error distinto de cero.

EJEMPLO

Ejemplo 1. Notificación de inicio y actualizaciones de estado

Un simple demonio de shell que envía notificaciones de inicio después de haber configurado su canal de comunicación. Durante la ejecución, envía más actualizaciones de estado al sistema de inicio:

#!/bin/sh
mkfifo /tmp/waldo
systemd-notify --ready --status="Esperando datos..."
while : ; do
        read -r a < /tmp/waldo
        systemd-notify --status="Procesando $a"
        # Hacer algo con $a ...
        systemd-notify --status="Esperando datos..."
done
