NOMBRE

systemd-sysext, systemd-sysext.service, systemd-sysext-initrd.service, systemd-confext, systemd-confext.service, systemd-confext-initrd.service - Activa Imágenes de Extensión del Sistema

SINOPSIS

systemd-sysext [OPCIONES...] COMANDO

systemd-sysext.service

systemd-confext [OPCIONES...] COMANDO

systemd-confext.service

DESCRIPCIÓN

systemd-sysext activa/desactiva imágenes de extensión del sistema. Las imágenes de extensión del sistema pueden, dinámicamente en tiempo de ejecución, extender las jerarquías de directorios /usr/ y /opt/ con archivos adicionales. Esto es particularmente útil en imágenes de sistema inmutables donde una jerarquía /usr/ y/o /opt/ que reside en un sistema de archivos de solo lectura debe extenderse temporalmente en tiempo de ejecución sin realizar modificaciones persistentes.

Las imágenes de extensión del sistema deben contener archivos y directorios de manera similar a un árbol de sistema operativo normal. Cuando una o más imágenes de extensión del sistema se activan, sus jerarquías /usr/ y /opt/ se combinan mediante "overlayfs" con las mismas jerarquías del SO host, y se monta sobre ellas el /usr/ y /opt/ del host ("fusión"). Cuando se desactivan, el punto de montaje se desmonta, revelando nuevamente la versión original no modificada del host de la jerarquía ("desfusión"). La fusión hace que los recursos de la extensión aparezcan repentinamente debajo de las jerarquías /usr/ y /opt/ como si estuvieran incluidos en la propia imagen del SO base.

Los archivos y directorios contenidos en las imágenes de extensión fuera de las jerarquías /usr/ y /opt/ no se fusionan y, por lo tanto, no tienen efecto cuando se incluyen en una imagen de extensión del sistema. En particular, los archivos en /etc/ y /var/ incluidos en una imagen de extensión del sistema no aparecerán en las jerarquías respectivas después de la activación.

Las imágenes de extensión del sistema son estrictamente de solo lectura por defecto. En sistemas de archivos host mutables, las jerarquías /usr/ y /opt/ se vuelven de solo lectura mientras se fusionan las extensiones, a menos que se habilite la mutabilidad. La mutabilidad se puede habilitar a través de la opción --mutable=; consulte "Mutabilidad" a continuación para obtener más información.

Se supone que las extensiones del sistema son puramente aditivas, es decir, se supone que solo incluyen archivos que no existen en la imagen base del SO subyacente. Sin embargo, el mecanismo subyacente (overlayfs) también permite superponer o eliminar archivos, pero se recomienda no hacer uso de esto.

Las imágenes de extensión del sistema pueden proporcionarse en los siguientes formatos:

1. Directorios simples o subvolúmenes btrfs que contienen el árbol del SO
2. Imágenes de disco con una etiqueta de disco GPT, que siguen la Especificación de Particiones Detectables[1]
3. Imágenes de disco que carecen de tabla de particiones, con un sistema de archivos Linux desnudo (por ejemplo, erofs, squashfs o ext4)

Estos formatos de imagen son los mismos que systemd-nspawn(1) soporta a través de sus opciones --directory=/--image= y aquellos que el gestor de servicios soporta a través de RootDirectory=/RootImage=. De manera similar a ellos, pueden llevar opcionalmente información de autenticación Verity.

Las extensiones del sistema se buscan en los directorios /etc/extensions/, /run/extensions/ y /var/lib/extensions/. Los dos primeros directorios listados no son adecuados para contener imágenes binarias grandes, sin embargo, son útiles para contener enlaces simbólicos a ellas. El lugar principal para instalar extensiones del sistema es /var/lib/extensions/. Cualquier directorio encontrado en estos directorios de búsqueda se considera una imagen de extensión basada en directorio; cualquier archivo con la extensión .raw se considera una imagen de extensión basada en imagen de disco. Cuando se invoca en el initrd, el directorio adicional /.extra/sysext/ se incluye en los directorios que se buscan para imágenes de extensión. Tenga en cuenta, sin embargo, que por defecto se aplica una política de imagen más estricta a las imágenes que se encuentran allí, ver abajo. Este directorio es poblado por systemd-stub(7) con las imágenes de extensión encontradas en la Partición EFI del Sistema.

Durante el arranque, las imágenes de extensión del SO se activan automáticamente si systemd-sysext.service está habilitado. Tenga en cuenta que este servicio se ejecuta solo después de que se hayan montado los sistemas de archivos subyacentes donde pueden ubicarse las extensiones del sistema. Esto significa que no son adecuadas para distribuir recursos que son procesados por subsistemas que se ejecutan en el arranque más temprano. Específicamente, las imágenes de extensión del SO no son adecuadas para distribuir servicios del sistema o definiciones de systemd-sysusers(8). Consulte la página de Servicios Portátiles[2] para un mecanismo simple para distribuir servicios del sistema en imágenes de disco, de manera similar a las extensiones del SO. Tenga en cuenta el diferente aislamiento en estos dos mecanismos: mientras que las extensiones del sistema extienden directamente la imagen del SO subyacente con archivos adicionales que aparecen de manera muy similar a como si se distribuyeran en la propia imagen del SO y, por lo tanto, no implican aislamiento de seguridad, los servicios portátiles implican aislamiento a nivel de servicio de una forma u otra. Se garantiza que el servicio systemd-sysext.service finalice el inicio antes de que se alcance basic.target; es decir, cuando los servicios normales se inicializan (aquellos que no usan DefaultDependencies=no), los archivos y directorios que proporcionan las extensiones del sistema están disponibles en /usr/ y /opt/ y pueden ser accedidos.

Tenga en cuenta que no existe el concepto de habilitar/deshabilitar imágenes de extensión del sistema instaladas: todas las imágenes de extensión instaladas se activan automáticamente al arrancar. Sin embargo, puede colocar un directorio vacío con el nombre de la extensión (sin .raw) en /etc/extensions/ para "enmascarar" una extensión con el mismo nombre en una carpeta del sistema con menor precedencia.

Se impone un mecanismo simple de compatibilidad de versiones: una imagen de extensión del sistema debe tener un archivo /usr/lib/extension-release.d/extension-release.NOMBRE, que debe coincidir con el nombre de su imagen, y que se compara con el archivo os-release del host: los campos ID= contenidos deben coincidir a menos que se establezca "_any" para la extensión. Si el ID= de la extensión no es "_any", el campo SYSEXT_LEVEL= (si está definido) debe coincidir. Si este último no está definido, el campo VERSION_ID= debe coincidir en su lugar. Si la extensión define el campo ARCHITECTURE= y el valor no es "_any", debe coincidir con la arquitectura del kernel reportada por uname(2), pero los identificadores de arquitectura utilizados son los mismos que para ConditionArchitecture= descritos en systemd.unit(5). EXTENSION_RELOAD_MANAGER= puede establecerse en 1 si la extensión requiere una recarga del gestor de servicios después de la aplicación de la extensión. Tenga en cuenta que por las razones mencionadas anteriormente, Servicios Portátiles[2] siguen siendo la forma recomendada de distribuir servicios del sistema. Las extensiones del sistema no deben distribuir un archivo /usr/lib/os-release (ya que se fusionaría en el árbol /usr/ del host, anulando los datos de la versión del SO del host, lo cual no es deseable). El archivo extension-release sigue el mismo formato y semántica, y contiene el mismo contenido que el archivo os-release del SO, pero describe los recursos contenidos en la imagen de extensión.

El concepto systemd-confext sigue el mismo principio que la funcionalidad de systemd-sysext(8), pero en lugar de trabajar en /usr y /opt, confext extenderá solo /etc. Los archivos y directorios contenidos en las imágenes de confext fuera de la jerarquía /etc/ no se fusionan y, por lo tanto, no tienen efecto cuando se incluyen en la imagen. Los formatos para estas imágenes son los mismos que para las imágenes de sysext. La jerarquía fusionada se montará con "nosuid" y (si no se deshabilita con --noexec=false) "noexec".

Al igual que los sysext, los confext son estrictamente de solo lectura por defecto. La fusión de confext en sistemas de archivos host mutables hará que /etc/ sea de solo lectura. Al igual que con los sysext, la mutabilidad se puede habilitar a través de la opción --mutable=. Consulte "Mutabilidad" a continuación para obtener más información.

Los confext se buscan en los directorios /run/confexts/, /var/lib/confexts/, /usr/lib/confexts/ y /usr/local/lib/confexts/. El primer directorio listado no es adecuado para contener imágenes binarias grandes, sin embargo, es útil para contener enlaces simbólicos a ellas. El lugar principal para instalar extensiones de configuración es /var/lib/confexts/. Cualquier directorio encontrado en estos directorios de búsqueda se considera una imagen de confext basada en directorio; cualquier archivo con la extensión .raw se considera una imagen de confext basada en imagen de disco.

Nuevamente, al igual que las imágenes de sysext, las imágenes de confext contendrán un archivo /etc/extension-release.d/extension-release.NOMBRE, que debe coincidir con el nombre de la imagen

DESCRIPCIÓN

systemd-sysext y systemd-confext son utilidades para gestionar imágenes de disco de sistema de extensiones. Las imágenes de disco de sistema de extensiones son imágenes de disco de archivos que pueden ser montadas encima de jerarquías del sistema de archivos existente, generalmente como parte de un sistema operativo inmutable, para añadir o modificar archivos en ellas. El primer tipo, las extensiones del sistema (sysext), son para extensiones de nivel de sistema, que se montan sobre las jerarquías de archivos /usr/ y /opt/. El segundo tipo, las extensiones de configuración (confext), se diseñan para extensiones de configuración, que se montan sobre la jerarquía de archivos /etc/.

Las imágenes de disco del sistema de extensiones se implementan como imágenes de disco comprimidas y firmadas (por defecto, firmadas con sigstore, véase systemd-image-store(8)). Las imágenes de sistema de extensiones se empaquetan de forma similar a las imágenes de disco completas del sistema operativo, pero contienen solo subconjuntos de archivos para extensiones específicas. Deben contener un directorio de extensión, que es el directorio raíz de la imagen y que contiene los archivos de la extensión. Dentro del directorio de extensión, se puede colocar información de versión y metadatos bajo el directorio /usr/lib/extension/. Específicamente, se espera que contenga un archivo /usr/lib/extension/id que contiene la cadena de identificación de la extensión, y opcionalmente /usr/lib/extension/version que contiene una cadena de identificación de la versión.

Las extensiones del sistema se identifican por la combinación de los contenidos de los directorios /usr/lib/extension/, /etc/extension/ y /var/lib/extension/ dentro de la imagen del disco. Las imágenes de disco de extensiones del sistema, que se utilizan para extender /usr/ y /opt/, se identifican principalmente por el contenido de /usr/lib/extension/. Las imágenes de disco de extensiones de configuración, que se utilizan para extender /etc/, se identifican principalmente por el contenido de /etc/extension/. Los archivos de la imagen del disco pueden ser imágenes de disco de sistema sin comprimir o comprimidas con zstd, xz, o gzip. El tipo de archivo de imagen se determina por la extensión del archivo (.raw, .raw.zst, .raw.xz, .raw.gz).

Las imágenes de disco del sistema se instalan copiando su contenido a /var/lib/extensions/. El sistema mantiene un registro de las extensiones instaladas en /etc/systemd/sysext.d/ y /etc/systemd/confext.d/. Después de instalar una imagen de disco, se debe ejecutar systemd-sysext refresh (o systemd-confext refresh) para que los cambios surtan efecto. El sistema de archivos subyacente (por ejemplo, /usr/) se monta con una capa de montaje de solo lectura encima de ella, con la imagen de extensión montada encima de esa capa. La mayoría de las implementaciones utilizan overlayfs para lograr esto, pero otras opciones son posibles. Para las extensiones de configuración, se utiliza la misma lógica, pero para la jerarquía /etc/.

Se puede usar un campo de extensibilidad extendido para el control de la compatibilidad de la versión, como se describe en systemd.extensible.system(7). En resumen, el contenido de /usr/lib/extension/id y /usr/lib/extension/version se compara con la información de la versión del host, que se puede encontrar en /etc/os-release y /usr/lib/os-release. La información de la versión se puede utilizar para evitar la instalación de extensiones incompatibles.

Las imágenes de disco del sistema se pueden verificar de forma opcional después de la instalación usando el campo de metadatos IMAGE_VERIFICATION en /etc/systemd/sysext.d/ o /etc/systemd/confext.d/. Esta verificación se puede configurar de varias maneras, incluido el uso de metadatos de imagen (consulte systemd.image-policy(7)) o un mecanismo de firma de clave pública más tradicional, que se puede añadir mediante el uso de atributos extendidos de archivos en el archivo /usr/lib/extension/ (con la posible exclusión de la user.extension-release.strict xattr(7)), y de nuevo con el contenido siendo uno o más de ID=, VERSION_ID= y CONFEXT_LEVEL. Las imágenes de confext se comprobarán y cotejarán con la capa base del sistema operativo.

USOS

El caso de uso principal para las imágenes del sistema son entornos inmutables donde las herramientas de depuración y desarrollo se pondrán a disposición opcionalmente, pero no se incluirán en la imagen base del sistema operativo inmutable en sí misma (por ejemplo, strace(1) y gdb(1) serán una adición instalable opcionalmente para facilitar la depuración/desarrollo). Las imágenes de extensión del sistema no deben malinterpretarse como un marco de empaquetado de software genérico, ya que no hay un esquema de dependencias disponible: las extensiones del sistema deben llevar todos los archivos que necesitan por sí mismas, excepto aquellos que ya se envían en la imagen del sistema host subyacente. Típicamente, las imágenes de extensión del sistema se construyen al mismo tiempo que la imagen base del sistema operativo, dentro del mismo sistema de compilación.

Otro caso de uso para el concepto de extensión del sistema es la sustitución temporal de recursos suministrados por el sistema operativo por otros más nuevos, por ejemplo, para instalar una versión de desarrollo compilada localmente de algún componente de bajo nivel sobre la imagen del sistema operativo inmutable sin realizar una reconstrucción completa del sistema operativo o modificar la imagen nominalmente inmutable. (por ejemplo, "instalar" un paquete compilado localmente con DESTDIR=/var/lib/extensions/mytest make install && systemd-sysext refresh, haciéndolo disponible en /usr/ como si estuviera instalado en la propia imagen del sistema operativo.) Este caso funciona independientemente de si el host /usr/ subyacente se gestiona como una imagen de disco inmutable o es un árbol tradicional controlado por un gestor de paquetes (es decir, escribible).

Con systemd-confext se puede realizar la reconfiguración en tiempo de ejecución de los servicios del sistema operativo. A veces, es necesario intercambiar ciertos valores de parámetros de configuración o reiniciar solo un servicio específico sin desplegar nuevo código o una despliegue completo del sistema operativo. En otras palabras, queremos poder vincular las opciones configuradas con más frecuencia a indicadores actualizables en tiempo de ejecución que se puedan cambiar sin reiniciar el sistema. Esto ayudará a reducir los tiempos de servicio cuando sea necesario cambiar la configuración del sistema operativo. También proporciona una herramienta fiable para gestionar la configuración, ya que todos los archivos de configuración antiguos desaparecen cuando se elimina la imagen de systemd-confext.

MUTABILIDAD

Por defecto, al fusionar extensiones del sistema en sistemas de archivos host mutables, las jerarquías /usr/ y /opt/ se vuelven de solo lectura. La fusión de extensiones de configuración tendrá el mismo efecto en /etc/. El modo mutable permite escrituras en estas ubicaciones cuando se fusionan las extensiones.

Los siguientes modos son compatibles:

1.disabled: Fuerza el modo inmutable incluso si existen directorios de enrutamiento de escritura debajo de /var/lib/extensions.mutable/. Este es el valor predeterminado.
2.auto: Modo automático. La mutabilidad está desactivada por defecto y solo se habilita si existe un directorio de enrutamiento de escritura correspondiente debajo de /var/lib/extensions.mutable/.
3.enabled: Fuerza el modo mutable y crea directorios de enrutamiento de escritura automáticamente debajo de /var/lib/extensions.mutable/ cuando sea necesario.
4.import: Fuerza el modo inmutable como disabled arriba, pero fusiona el contenido de los directorios debajo de /var/lib/extensions.mutable/ en el sistema de archivos del host.
5.ephemeral: Fuerza el modo mutable como enabled arriba, pero en lugar de usar directorios de enrutamiento de escritura debajo de /var/lib/extensions.mutable/, systemd-sysext utilizará directorios efímeros vacíos. Esto significa que las modificaciones realizadas en las jerarquías fusionadas se perderán cuando las jerarquías se desfusionen.
6.ephemeral-import: Fuerza el modo mutable como ephemeral arriba, pero en lugar de ignorar el contenido de los directorios de enrutamiento de escritura bajo /var/lib/extensions.mutable/, los fusiona en el sistema de archivos del host, como lo hace import.

Consulte "Opciones" a continuación para especificar modos utilizando la opción de línea de comandos --mutable=.

Con la excepción del modo efímero, el modo mutable enruta las escrituras a subdirectorios en /var/lib/extensions.mutable/.

Las escrituras en /usr/ se dirigen a /var/lib/extensions.mutable/usr/
las escrituras en /opt/ se dirigen a /var/lib/extensions.mutable/opt/, y
las escrituras en /etc/ van a /var/lib/extensions.mutable/etc/.

Si usr/, opt/, o etc/ en /var/lib/extensions.mutable/ son enlaces simbólicos, entonces las escrituras se dirigen a los destinos de los enlaces simbólicos. En consecuencia, para mantener la mutabilidad de un sistema de archivos host, cree enlaces simbólicos

/var/lib/extensions.mutable/etc/ → /etc/
/var/lib/extensions.mutable/usr/ → /usr/
/var/lib/extensions.mutable/opt/ → /opt/
para dirigir las escrituras de vuelta a la jerarquía de directorios base original.

Alternativamente, se puede montar un sistema de archivos temporal en /var/lib/extensions.mutable/, o los enlaces simbólicos en /var/lib/extensions.mutable/ pueden apuntar a subdirectorios en un sistema de archivos temporal (por ejemplo, debajo de /tmp/) para permitir solo cambios efímeros. Tenga en cuenta que esto no es lo mismo que el modo efímero, ya que el sistema de archivos temporal todavía existirá después de la desinstalación.

Añadido en la versión 256.

COMANDOS

Los siguientes comandos son entendidos por ambos conceptos, sysext y confext:

status

Cuando se invoca sin ningún verbo de comando, o cuando se especifica status, se muestra el estado de fusión actual, por separado (tanto para /usr/ y /opt/ de sysext como para /etc/ de confext).

Añadido en la versión 248.

merge

Fusiona todas las imágenes de extensión del sistema instaladas actualmente en /usr/ y /opt/, sobremontando estas jerarquías con un sistema de archivos "overlayfs" que combina las jerarquías subyacentes con las incluidas en las imágenes de extensión. Este comando fallará si las jerarquías ya están fusionadas. Para confext, la fusión se realiza en el directorio /etc/ en su lugar.

Añadido en la versión 248.

unmerge

Desmonta todas las imágenes de extensión del sistema instaladas actualmente de /usr/ y /opt/ para sysext y /etc/, para confext, desmontando los sistemas de archivos "overlayfs" creados previamente por merge.

Añadido en la versión 248.

refresh

Una combinación de unmerge y merge: si ya está montado, la instancia existente de "overlayfs" se desmonta temporalmente y luego se reemplaza por una nueva versión. Este comando es útil después de instalar/eliminar imágenes de extensión del sistema, para actualizar el sistema de archivos "overlayfs" en consecuencia. Si no hay extensiones del sistema instaladas cuando se ejecuta este comando, se ejecuta el equivalente a unmerge, sin establecer ninguna nueva instancia de "overlayfs". Tenga en cuenta que actualmente existe un breve momento en el que ni el sistema de archivos "overlayfs" antiguo ni el nuevo están montados. Esto implica que todos los recursos suministrados por una extensión del sistema desaparecerán brevemente, incluso si existe de forma continua durante la operación de actualización.

Añadido en la versión 248.

list

Se muestra una lista breve de las imágenes de extensión instaladas.

Añadido en la versión 248.

-h, --help

Imprime un texto de ayuda corto y sale.

--version

Imprime una cadena de versión corta y sale.

OPCIONES

--root=

Opera en relación con el directorio raíz especificado, es decir, establece el montaje "overlayfs" no en las jerarquías principales de /usr/ y /opt/ para sysext o /etc/ para confext, sino debajo de algún directorio raíz especificado.

Añadido en la versión 248.

--force

Al fusionar extensiones del sistema en /usr/ y /opt/ para sysext y /etc/ para confext, ignora las incompatibilidades de versión, es decir, fuerza la fusión independientemente de si la información de versión incluida en las imágenes coincide con la del host o no.

Añadido en la versión 248.

--image-policy=policy

Toma una cadena de política de imagen como argumento, según systemd.image-policy(7). La política se aplica al operar en imágenes de disco de extensión del sistema. Si no se especifica, por defecto es "root=verity+signed+encrypted+unprotected+absent:usr=verity+signed+encrypted+unprotected+absent" para extensiones del sistema, es decir, solo se utilizan los sistemas de archivos root y /usr/ en la imagen. Para extensiones de configuración, el valor predeterminado es "root=verity+signed+encrypted+unprotected+absent". Al ejecutarse en el initrd y operar en una imagen de extensión del sistema almacenada en el directorio /.extra/sysext/ se utiliza una política ligeramente más estricta por defecto: "root=signed+absent:usr=signed+absent", consulte arriba para más detalles.

Añadido en la versión 254.

--mutable=BOOL|auto|import|ephemeral|ephemeral-import

Establece el modo mutable.

no

Fuerza el modo inmutable incluso con directorios de enrutamiento de escritura presentes. Este es el valor predeterminado.

Añadido en la versión 256.

auto

Habilita el modo mutable individualmente para /usr/, /opt/, y /etc/ si hay subdirectorios o enlaces simbólicos de enrutamiento de escritura en /var/lib/extensions.mutable/; desactiva de lo contrario. Consulte "Mutabilidad" arriba para más información sobre el enrutamiento de escritura.

Añadido en la versión 256.

yes

Fuerza el modo mutable. Se crearán directorios de enrutamiento de escritura en /var/lib/extensions.mutable/ si no están presentes.

Añadido en la versión 256.

import

Modo inmutable, pero con el contenido de los directorios de enrutamiento de escritura en /var/lib/extensions.mutable/ también fusionado en el sistema de archivos del host.

Añadido en la versión 256.

ephemeral

Fuerza el modo mutable, pero con el contenido de los directorios de enrutamiento de escritura en /var/lib/extensions.mutable/ siendo ignorado, y las modificaciones del sistema de archivos del host siendo descartadas después de la desinstalación.

Añadido en la versión 256.

ephemeral-import

Fuerza el modo mutable, con el contenido de los directorios de enrutamiento de escritura en /var/lib/extensions.mutable/ siendo fusionado en el sistema de archivos del host, pero con las modificaciones realizadas en el sistema de archivos del host siendo descartadas después de la desinstalación.

Añadido en la versión 256.

systemd-confext(8) — systemd manual pages

NAME

systemd-confext.service, systemd-confext — Configure systemd extensions

SYNOPSIS

systemd-confext.service

systemd-confext [OPTIONS...] { COMMAND }

DESCRIPTION

systemd-confext is a tool used to manage systemd configuration extensions, as described in the Discoverable Partitions Specification1. Configuration extensions are directory trees that are mounted read-only into the main systemd configuration directory (/etc/). They allow customization of systemd services, units, and other configurations without modifying the original system configuration.

The systemd-confext.service unit manages the automatic mounting and unmounting of these extensions during boot and shutdown, respectively.

USES

Configuration extensions are typically discovered via the systemd.special(7) partition type or via the /etc/systemd/system-confext.d/ directory.

Each configuration extension must contain a /confext/ directory, which holds the actual configuration files to be merged.

MUTABILITY

Configuration extensions are mounted read-only. Modifications should be made to the source of the extension, not on the mounted filesystem.

COMMANDS

The following commands are available:

merge
Merges the specified configuration extension into the main /etc/ directory. If the extension is already mounted, it is first unmounted and then remounted with the new content. This command should usually be run by systemd-confext.service.
unmerge
Unmounts and removes the specified configuration extension from /etc/. This command should usually be run by systemd-confext.service during shutdown.
refresh
Reloads all currently mounted configuration extensions. This is useful if the underlying filesystem of an extension has changed.
list
Lists all discovered and currently mounted configuration extensions.

OPTIONS

The following options are available:

--directory=DIR

Specifies the root directory of the configuration extension to operate on. This is usually a path under /run/systemd/system-confext/ or a discovered partition mount point.

--mountpoint=DIR

Specifies the mount point where the configuration extension should be mounted. This defaults to /etc/.

--source=DIR

Specifies the source directory containing the /confext/ subdirectory. This option is used when --directory is not sufficient, for example, when dealing with partitions.

--priority=NUM

Sets the priority for merging. Higher numbers indicate higher priority. When multiple extensions contain the same file, the one with the highest priority wins. Defaults to 0.

--no-create-paths

Do not automatically create parent directories for paths in the configuration extension.

--no-paths=PATH...

Do not merge the specified paths from the configuration extension. Multiple paths can be specified by repeating this option.

--paths=PATH...

Only merge the specified paths from the configuration extension. If this option is used, only the listed paths will be merged. Multiple paths can be specified by repeating this option.

--all

Merge all discovered configuration extensions.

--no-fallback

When merging configuration extensions into /etc/ the "MS_NOEXEC" mount flag is used by default. This option can be used to disable it.

Added in version 254.

--no-reload

When used with merge, unmerge or refresh, do not reload daemon after executing the changes even if an extension that is applied requires a reload via the EXTENSION_RELOAD_MANAGER= set to 1.

Added in version 255.

--no-pager

Do not pipe output into a pager.

--no-legend

Do not print the legend, i.e. column headers and the footer with hints.

--json=MODE

Shows output formatted as JSON. Expects one of "short" (for the shortest possible output without any redundant whitespace or line breaks), "pretty" (for a pretty version of the same, with indentation and line breaks) or "off" (to turn off JSON output, the default).

EXIT STATUS

On success, 0 is returned.
