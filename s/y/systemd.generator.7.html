NOMBRE

systemd.generator - Generadores de unidades de systemd

SINOPSIS

/ruta/al/generador directorio-normal [directorio-temprano] [directorio-tardío]

/run/systemd/system-generators/*
/etc/systemd/system-generators/*
/usr/local/lib/systemd/system-generators/*
/usr/lib/systemd/system-generators/*
/run/systemd/user-generators/*
/etc/systemd/user-generators/*
/usr/local/lib/systemd/user-generators/*
/usr/lib/systemd/user-generators/*

DESCRIPCIÓN

Los generadores son ejecutables pequeños ubicados en /usr/lib/systemd/system-generators/ y otros directorios listados arriba. systemd(1) ejecutará estos binarios muy temprano al arrancar y al recargar la configuración — antes de que se carguen los archivos de unidad. Su propósito principal es convertir la configuración y los parámetros del contexto de ejecución que no son nativos del gestor de servicios en archivos de unidad generados dinámicamente, enlaces simbólicos o archivos de unidad drop-in, para que puedan extender la jerarquía de archivos de unidad que el gestor de servicios carga y opera posteriormente.

systemd llamará a cada generador con tres rutas de directorio que se utilizarán para la salida del generador. En estos tres directorios, los generadores pueden generar dinámicamente archivos de unidad (regulares, instancias, así como plantillas), archivos de unidad .d/ drop-ins, y crear enlaces simbólicos a archivos de unidad para añadir dependencias adicionales, crear alias o instanciar plantillas existentes. Esos directorios se incluyen en la ruta de carga de unidades, permitiendo que la configuración generada extienda o anule las definiciones existentes.

Los generadores ejecutados por el gestor del sistema se invocan en un entorno aislado (sandbox) con un /tmp/ privado escribible y donde la mayor parte del sistema de archivos es de solo lectura, excepto los directorios de salida del generador.

Las rutas de los directorios para la salida del generador difieren por prioridad: .../generator.early tiene prioridad más alta que la configuración del administrador en /etc/, mientras que .../generator tiene menor prioridad que /etc/ pero mayor que la configuración del proveedor en /usr/, y .../generator.late tiene menor prioridad que toda la demás configuración. Vea la siguiente sección y la discusión sobre rutas de carga de unidades y anulación de unidades en systemd.unit(5).

Los generadores se cargan desde un conjunto de rutas determinadas durante la compilación, como se enumera arriba. Los generadores del sistema y del usuario se cargan desde directorios cuyos nombres terminan en system-generators/ y user-generators/, respectivamente. Los generadores encontrados en directorios listados anteriormente anulan los del mismo nombre en directorios más abajo en la lista [1]. Se puede usar un enlace simbólico a /dev/null o un archivo vacío para enmascarar un generador, evitando así su ejecución. Tenga en cuenta que el orden de los dos directorios con mayor prioridad está invertido con respecto a la ruta de carga de unidades, y los generadores en /run/ anulan los de /etc/.

Después de instalar nuevos generadores o actualizar la configuración, se puede ejecutar systemctl daemon-reload. Esto eliminará la configuración previa creada por los generadores, volverá a ejecutar todos los generadores y hará que systemd recargue las unidades desde el disco. Vea systemctl(1) para más información.

DIRECTORIOS DE SALIDA

Los generadores se invocan con tres argumentos: rutas a directorios donde los generadores pueden colocar sus archivos de unidad generados o enlaces simbólicos. Por defecto, estas rutas son directorios de tiempo de ejecución que se incluyen en la ruta de búsqueda de systemd, pero un generador puede ser llamado con rutas diferentes con fines de depuración. Si solo se proporciona un argumento, el generador debe usar el mismo directorio para las tres rutas de salida.

1.directorio-normal

En uso normal, este es /run/systemd/generator para los generadores del sistema y $XDG_RUNTIME_DIR/systemd/generator para los generadores de usuario. Los archivos de unidad colocados en este directorio tienen prioridad sobre la configuración de unidades del proveedor, pero no sobre la configuración de unidades nativa del usuario/administrador.

2.directorio-temprano

En uso normal, este es /run/systemd/generator.early para los generadores del sistema y $XDG_RUNTIME_DIR/systemd/generator.early para los generadores de usuario. Los archivos de unidad colocados en este directorio anulan los archivos de unidad en /usr/, /run/ y /etc/. Esto significa que los archivos de unidad colocados en este directorio tienen prioridad sobre toda la configuración normal, tanto del proveedor como del usuario/administrador.

3.directorio-tardío

En uso normal, este es /run/systemd/generator.late para los generadores del sistema y $XDG_RUNTIME_DIR/systemd/generator.late para los generadores de usuario. Este directorio puede usarse para extender el árbol de archivos de unidad sin anular ningún otro archivo de unidad. Los archivos de configuración nativos proporcionados por el proveedor o el usuario/administrador tienen prioridad.

Nota: los generadores *no deben* escribir en otras ubicaciones ni realizar cambios en el estado del sistema. La salida del generador debe durar solo hasta el próximo daemon-reload o daemon-reexec; si el generador se reemplaza o se enmascara, sus efectos deberían desaparecer.

AMBIENTE

El gestor de servicios establece una serie de variables de entorno al invocar los ejecutables del generador. Llevan información sobre el contexto de ejecución del generador, para simplificar la condicionalización de los generadores a entornos específicos. Se establecen las siguientes variables de entorno:

$SYSTEMD_SCOPE

Si el generador se invoca desde el gestor de servicios del sistema, esta variable se establece como "system"; si se invoca desde el gestor de servicios por usuario, se establece como "user".

Añadido en la versión 251.

$SYSTEMD_IN_INITRD

Si el generador se ejecuta como parte de un initrd, se establece como "1". Si se ejecuta desde el host regular (es decir, después de la transición de initrd a host), se establece como "0". Esta variable de entorno solo se establece para generadores del sistema.

Añadido en la versión 251.

$SYSTEMD_SOFT_REBOOTS_COUNT

Si el sistema se ha reiniciado de forma suave (soft-reboot), esta variable se establece como el recuento de reinicios suaves. Esta variable de entorno solo se establece para generadores del sistema.

Añadido en la versión 257.

$SYSTEMD_FIRST_BOOT

Si este ciclo de arranque se considera un "primer arranque", se establece como "1"; si es un arranque regular posterior, se establece como "0". Para más detalles, consulte la documentación de ConditionFirstBoot= en systemd.unit(5). Esta variable de entorno solo se establece para generadores del sistema.

Añadido en la versión 251.

$SYSTEMD_VIRTUALIZATION

Si el gestor de servicios se ejecuta en un entorno virtualizado, $SYSTEMD_VIRTUALIZATION se establece como un par de cadenas, separadas por dos puntos. La primera cadena es "vm" o "container", categorizando el tipo de virtualización. La segunda cadena identifica la implementación de la tecnología de virtualización. Si no se detecta virtualización, esta variable no se establecerá. Estos datos son idénticos a lo que detecta e informa systemd-detect-virt(1), y utiliza el mismo vocabulario de identificadores de implementación de virtualización.

Añadido en la versión 251.

$SYSTEMD_ARCHITECTURE

Esta variable se establece en un identificador corto de la arquitectura informada del sistema. Para obtener detalles sobre los valores definidos, consulte la documentación de ConditionArchitecture= en systemd.unit(5).

Añadido en la versión 251.

$CREDENTIALS_DIRECTORY, $ENCRYPTED_CREDENTIALS_DIRECTORY

Si se establecen, se refieren al directorio donde se han colocado las credenciales del sistema. Las credenciales pasadas al sistema en texto plano se colocarán en $CREDENTIALS_DIRECTORY, y las pasadas en forma cifrada se colocarán en $ENCRYPTED_CREDENTIALS_DIRECTORY. Utilice el comando systemd-creds(1) para descifrar/autenticar automáticamente las credenciales pasadas, si es necesario. Específicamente, use el comando systemd-creds --system cat.

Añadido en la vers

systemd.generator 7

NAME

systemd.generator — systemd generator programs

SYNOPSIS

/usr/lib/systemd/system-generators/*

/etc/systemd/system-generators/*

/run/systemd/system-generators/*

DESCRIPTION

systemd is a system and service manager. It is compatible with SysVinit scripts, understands dependency and ordering specified by LSB init.d scripts, and can be used to control services through a socket-activated, on-demand activation mechanism, and manages logging via systemd-journald.

During the early boot process, systemd initializes itself and then invokes all programs found in the directories listed in systemd.generator. These programs are executed one after the other, in alphabetical order, and are passed the same command line arguments.

Generators are used to dynamically generate systemd unit files based on the system's current state or configuration files. They are executed before systemd starts processing any actual unit files.

The primary goal of generators is to translate system state or configuration into native systemd units. This allows systemd to manage services and devices that might not have explicit unit files defined in `/usr/lib/systemd/system` or `/etc/systemd/system`.

OUTPUT DIRECTORIES

Generators should write their output to one of the directories specified in the command line arguments passed to them. The first argument (argv[1]) is the directory for units intended to be overridden by vendor configuration. The second argument (argv[2]) is the directory for units intended to be overridden by user configuration. The third argument (argv[3]) is the directory for units intended to be overridden by runtime configuration. Typically, argv[1] should point to `/usr/lib/systemd/system`, argv[2] to `/etc/systemd/system`, and argv[3] to `/run/systemd/system`.

ENVIRONMENT

Generators may rely on certain environment variables being set by systemd.

$SYSTEMD_EXEC_STATUS

If this variable is set, generators should write their output to standard output, and systemd will ensure that the output is saved and processed correctly. This is mostly used for debugging purposes. Added in version 254.

$SYSTEMD_GENERATOR_OUTPUT_DIR

This variable holds the directory where generators should write their output. This is identical to argv[1] passed to the generator. Added in version 254.

$SYSTEMD_CONFIDENTIAL_VIRTUALIZATION

If the service manager is run in a confidential virtualized environment, $SYSTEMD_CONFIDENTIAL_VIRTUALIZATION is set to a string that identifies the confidential virtualization hardware technology. If no confidential virtualization is detected this variable will not be set. This data is identical to what systemd-detect-virt(1) detects and reports, and uses the same vocabulary of confidential virtualization technology identifiers.

Added in version 254.

NOTES ABOUT WRITING GENERATORS

•All generators are executed in parallel. That means all executables are started at the very same time and need to be able to cope with this parallelism.
•Generators are run very early at boot and cannot rely on any external services. They may not talk to any other process. That includes simple things such as logging to syslog(3), or systemd itself (this means: no systemctl(1))! Non-essential file systems like /var/ and /home/ are mounted after generators have run. Generators can however rely on the most basic kernel functionality to be available, as well as mounted /sys/, /proc/, /dev/, /usr/ and /run/ file systems.
•Units written by generators are removed when the configuration is reloaded. That means the lifetime of the generated units is closely bound to the reload cycles of systemd itself.
•Generators should only be used to generate unit files, .d/*.conf drop-ins for them and symlinks to them, not any other kind of non-unit related configuration. Due to the lifecycle logic mentioned above, generators are not a good fit to generate dynamic configuration for other services. If you need to generate dynamic configuration for other services, do so in normal services you order before the service in question.

Note that using the StandardInputData=/StandardInputText= settings of service unit files (see systemd.exec(5)), it is possible to make arbitrary input data (including daemon-specific configuration) part of the unit definitions, which often might be sufficient to embed data or configuration for other programs into unit files in a native fashion.

•Since syslog(3) is not available (see above), log messages have to be written to /dev/kmsg instead.
•The generator should always include its own name in a comment at the top of the generated file, so that the user can easily figure out which component created or amended a particular unit.

The SourcePath= directive should be used in generated files to specify the source configuration file they are generated from. This makes things more easily understood by the user and also has the benefit that systemd can warn the user about configuration files that changed on disk but have not been read yet by systemd. The SourcePath= value does not have to be a file in a physical filesystem. For example, in the common case of the generator looking at the kernel command line, SourcePath=/proc/cmdline should be used.

•Generators may write out dynamic unit files or just hook unit files into other units with the usual .wants/ or .requires/ symlinks. Often, it is nicer to simply instantiate a template unit file from /usr/ with a generator instead of writing out entirely dynamic unit files. Of course, this works only if a single parameter is to be used.
•If you are careful, you can implement generators in shell scripts. We do recommend C code however, since generators are executed synchronously and hence delay the entire boot if they are slow.
•Regarding overriding semantics: there are two rules we try to follow when thinking about the overriding semantics:
1.User configuration should override vendor configuration. This (mostly) means that stuff from /etc/ should override stuff from /usr/.
2.Native configuration should override non-native configuration. This (mostly) means that stuff you generate should never override native unit files for the same purpose.

Of these two rules the first rule is probably the more important one and breaks the second one sometimes. Hence, when deciding whether to use argv[1], argv[2], or argv[3], your default choice should probably be argv[1].

•Instead of heading off now and writing all kind of generators for legacy configuration file formats, please think twice! It is often a better idea to just deprecate old stuff instead of keeping it artificially alive.

EXAMPLES

Example 1. systemd-fstab-generator

systemd-fstab-generator(8) converts /etc/fstab into native mount units. It uses argv[1] as location to place the generated unit files in order to allow the user to override /etc/fstab with their own native unit files, but also to ensure that /etc/fstab overrides any vendor default from /usr/.

After editing /etc/fstab, the user should invoke systemctl daemon-reload. This will re-run all generators and cause systemd to reload units from disk. To actually mount new directories added to fstab, systemctl start /path/to/mountpoint or systemctl start local-fs.target may be used.

Example 2. systemd-system-update-generator

systemd-system-update-generator(8) temporarily redirects default.target to system-update.target, if a system update is scheduled. Since this needs to override the default user configuration for default.target, it uses argv[2]. For details about this logic, see systemd.offline-updates(7).

Example 3. Debugging a generator

dir=$(mktemp -d)
SYSTEMD_LOG_LEVEL=debug /usr/lib/systemd/system-generators/systemd-fstab-generator \
        "$dir" "$dir" "$dir"
find $dir
