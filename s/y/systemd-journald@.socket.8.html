DESCRIPCIÓN

systemd-journald es un servicio del sistema que recopila y almacena datos de registro. Crea y mantiene bitácoras estructuradas e indexadas basadas en la información de registro que se recibe de una variedad de fuentes:

•Mensajes de registro del kernel, vía kmsg
•Mensajes de registro de sistema simples, vía la llamada syslog(3) de la libc
•Mensajes de registro de sistema estructurados vía la API nativa de la bitácora, ver sd_journal_print(3) y Native Journal Protocol[1]
•Salida estándar y error estándar de las unidades de servicio. Para más detalles ver abajo.
•Registros de auditoría, originados del subsistema de auditoría del kernel

El demonio recopilará implícitamente numerosos campos de metadatos para cada mensaje de registro de forma segura e infalsificable. Ver systemd.journal-fields(7) para más información sobre los metadatos recopilados.

Los datos de registro recopilados por la bitácora son principalmente basados en texto, pero también pueden incluir datos binarios cuando sea necesario. Los campos individuales que componen un registro de bitácora almacenado en la bitácora pueden tener hasta 2⁴-1 bytes de tamaño.

El servicio de bitácora almacena los datos de registro de forma persistente debajo de /var/log/journal o de forma volátil debajo de /run/log/journal/ (en este último caso, se pierde al reiniciar). Por defecto, los datos de registro se almacenan de forma persistente si /var/log/journal/ existe durante el arranque, con un fallback implícito al almacenamiento volátil en caso contrario. Utilice Storage= en journald.conf(5) para configurar dónde se colocan los datos de registro, independientemente de la existencia de /var/log/journal/.

Tenga en cuenta que journald utilizará inicialmente almacenamiento volátil, hasta que una llamada a journalctl --flush (o el envío de SIGUSR1 a journald) hará que cambie al registro persistente (bajo las condiciones mencionadas anteriormente). Esto se hace automáticamente al arrancar a través de "systemd-journal-flush.service".

En sistemas donde /var/log/journal/ aún no existe pero donde se desea el registro persistente (y se usa el journald.conf predeterminado), es suficiente crear el directorio y asegurarse de que tenga los modos de acceso y la propiedad correctos:

mkdir -p /var/log/journal
systemd-tmpfiles --create --prefix /var/log/journal

Ver journald.conf(5) para información sobre la configuración de este servicio.

REGISTRO DE FLUJO

El gestor de servicios systemd invoca todos los procesos de servicio con salida estándar y error estándar conectados a la bitácora por defecto. Este comportamiento puede ser modificado a través de la configuración de unidad StandardOutput=/StandardError=, ver systemd.exec(5) para detalles. La bitácora convierte el flujo de bytes de registro recibido de esta manera en registros de bitácora individuales, dividiendo el flujo en bytes de nueva línea ("\n", ASCII 10) y NUL.

Si systemd-journald.service se detiene, las conexiones de flujo asociadas con todos los servicios se terminan. Escrituras posteriores a esos flujos por el servicio resultarán en errores EPIPE. Para reaccionar graciosamente en este caso, se recomienda que los programas que registran en salida/error estándar ignoren dichos errores. Si el manejador de señales UNIX SIGPIPE no está bloqueado o desactivado, los intentos de escritura resultarán también en la generación de tales señales de proceso, ver signal(7). Para mitigar este problema, el gestor de servicios systemd desactiva explícitamente la señal SIGPIPE para todos los procesos invocados por defecto (esto puede cambiarse para cada unidad individualmente a través de la opción IgnoreSIGPIPE=, ver systemd.exec(5) para detalles). Después de que los flujos de salida estándar/error estándar se hayan terminado, es posible que no se recuperen hasta que los servicios a los que están asociados se reinicien. Tenga en cuenta que durante la operación normal, systemd-journald.service almacena copias de los descriptores de archivo para esos flujos en el gestor de servicios. Si systemd-journald.service se reinicia usando systemctl restart o una operación equivalente en lugar de un par de comandos separados systemctl stop y systemctl start (u operaciones equivalentes), estas conexiones de flujo no se terminan y sobreviven al reinicio. Por lo tanto, es seguro reiniciar systemd-journald.service, pero no se recomienda detenerlo.

Tenga en cuenta que los metadatos del registro para los registros transferidos a través de dichos flujos de salida/error estándar reflejan los metadatos del par para el cual se creó originalmente el flujo. Si la conexión de flujo se pasa a otros procesos (como procesos hijos adicionales generados desde el proceso de servicio principal), los registros de bitácora no reflejarán sus metadatos, sino que continuarán describiendo el proceso original. Esto es diferente de los otros transportes de registro enumerados anteriormente, que se basan intrínsecamente en registros y donde los metadatos siempre se asocian con el registro individual.

Además del registro implícito de salida/error estándar de los servicios, el registro de flujo también está disponible a través de la herramienta de línea de comandos systemd-cat(1).

Actualmente, el número de flujos de registro paralelos que systemd-journald aceptará se limita a 4096. Cuando se alcanza este límite, es posible que se establezcan flujos de registro adicionales pero recibirán EPIPE desde el principio.

ESPACIOS DE NOMBRE DE LA BITÁCORA

Los 'espacios de nombre' de la bitácora son tanto un mecanismo para aislar lógicamente el flujo de registro de proyectos que consisten en uno o más servicios del resto del sistema como un mecanismo para mejorar el rendimiento. Múltiples espacios de nombre de bitácora pueden existir simultáneamente, cada uno definiendo su propio flujo de registro independiente administrado por su propia instancia de systemd-journald. Los espacios de nombre son independientes entre sí, tanto en el almacén de datos como en la interfaz IPC. Por defecto, solo existe un único 'espacio de nombre predeterminado', administrado por systemd-journald.service (y sus unidades de socket asociadas). Los espacios de nombre adicionales se crean iniciando una instancia de la plantilla de servicio systemd-journald@.service. El nombre de la instancia es el identificador del espacio de nombre, que es una cadena corta utilizada para referenciar el espacio de nombre de la bitácora. Las unidades de servicio pueden asignarse a un espacio de nombre de bitácora específico a través de la configuración del archivo de unidad LogNamespace=, ver systemd.exec(5) para detalles. El modificador --namespace= de journalctl(1) puede usarse para ver el flujo de registro de un espacio de nombre específico. Si no se usa el modificador, se muestra el flujo de registro del espacio de nombre predeterminado, es decir, los datos de registro de otros espacios de nombre no son visibles.

Los servicios asociados con un espacio de nombre de bitácora específico pueden registrarse a través de syslog(3), el protocolo nativo de registro de la bitácora y a través de stdout/stderr; el registro de los tres transportes se asocia con el espacio de nombre.

Por defecto, solo el espacio de nombre predeterminado recopilará mensajes de registro del kernel y de auditoría.

La instancia systemd-journald del espacio de nombre predeterminado se configura a través de /etc/systemd/journald.conf (ver abajo), mientras que las otras instancias se configuran a través de /etc/systemd/journald@NAMESPACE.conf. Los datos de registro de la bitácora para el espacio de nombre predeterminado se colocan en /var/log/journal/MACHINE_ID (ver abajo) mientras que los datos para los otros espacios de nombre se encuentran en /var/log/journal/MACHINE_ID.NAMESPACE.

NAME

systemd-journald.service — journal/log collection and processing service

SYNOPSIS

systemd-journald.service(8)

DESCRIPTION

systemd-journald is a system service that collects and stores logging data. It receives message from a variety of sources, processes them, and stores them in a structured, indexed, and efficient binary format. It makes these logs available for querying with journalctl(1), and can forward them to other services, such as syslog(8) or journald-remote(8).

This man page primarily documents the runtime behavior of the daemon, the signals it understands, the journal namespaces it supports, and how kernel command line parameters and credentials might affect it.

For configuration, see journald.conf(5).

For the file format, see journal-files(5).

For the native journal protocol, see sd-journal(3).

For information about querying the journal, see journalctl(1).

STREAM LOGGING

By default, systemd-journald listens for log messages on the Unix domain socket journald.conf(5) and on the systemd-journald.service(8) for audit messages. It may also listen on the legacy syslog socket (/dev/log) if configured to do so.

Furthermore, it listens for log messages on the systemd.exec(5) IPC-mechanism, making it available for all processes started by systemd via this mechanism.

To receive log messages directly from the kernel's log buffer, systemd-journald may be configured via ReadKmsg= in journald.conf(5). This requires appropriate privileges.

To receive log messages from other systems, systemd-journald may be configured to listen on a network socket, see ListenNetlink= and ListenUserDatagram= in journald.conf(5).

JOURNAL NAMESPACES

The journal may be placed in one of several distinct namespaces. This allows different sets of logs to be maintained, isolated from each other. See systemd.exec(5) for details about the general concept of service unit namespaces. When journald is run in a non-default namespace (e.g. a virtual machine's namespace), it will by default write to a journal file suffixed with the namespace identifier (e.g. machine-id(7)).

Journal namespaces are primarily used by systemd-run(1) and machinectl(1) when creating transient services or machines.

SIGNALS

systemd-journald understands the following signals:

SIGUSR1

Request flushing of all currently written journal files to disk. Use the journalctl --flush command to request flushing of the journal files, and wait for the operation to complete. See journalctl(1) for details.

Added in version 186.

SIGUSR2

Request immediate rotation of the journal files. Use the journalctl --rotate command to request journal file rotation, and wait for the operation to complete.

Added in version 186.

SIGRTMIN+1

Request that all unwritten log data is written to disk. Use the journalctl --sync command to trigger journal synchronization, and wait for the operation to complete.

Added in version 228.

SIGHUP

Upon reception of the SIGHUP process signal systemd-journald will reload its configuration values and update the kernel log buffer and journals to reflect the new configuration. If ReadKmsg= has changed, the kernel log buffer will be flushed and updated as part of the reload. The active journal (e.g., persistent, volatile) will continue to be used with the updated configuration. However, if the storage mode has changed from persistent to volatile and the current journal in use is the persistent journal, then the active journal will be switched to the volatile journal.

Added in version 258.

CREDENTIALS

systemd-journald supports the service credentials logic as implemented by ImportCredential=/LoadCredential=/SetCredential= (see systemd.exec(5) for details). The following credentials are used when passed in:

journal.forward_to_socket

May contain a socket address to which logs should be forwarded. See ForwardToSocket= in journald.conf(5).

Added in version 256.

journal.storage

May be used to specify where journal files should be stored. See Storage= in journald.conf(5).

Added in version 256.

KERNEL COMMAND LINE

A few configuration parameters from journald.conf may be overridden on the kernel command line:

systemd.journald.forward_to_syslog=, systemd.journald.forward_to_kmsg=, systemd.journald.forward_to_console=, systemd.journald.forward_to_wall=

Enables/disables forwarding of collected log messages to syslog, the kernel log buffer, the system console or wall.

See journald.conf(5) for information about these settings.

Added in version 186.

systemd.journald.max_level_store=, systemd.journald.max_level_syslog=, systemd.journald.max_level_kmsg=, systemd.journald.max_level_console=, systemd.journald.max_level_wall=, systemd.journald.max_level_socket=

Controls the maximum log level of messages that are stored in the journal, forwarded to syslog(3), kmsg, the console, wall(1), or a socket. This kernel command line options override the settings of the same names in the journald.conf(5) file.

Added in version 232.

Note that these kernel command line options are only honoured by the default namespace, see above.

ACCESS CONTROL

Journal files are, by default, owned and readable by the "systemd-journal" system group but are not writable. Adding a user to this group thus enables them to read the journal files.

By default, each user, with a UID outside the range of system users, dynamic service users, and the nobody user, will get their own set of journal files in /var/log/journal/. See Users, Groups, UIDs and GIDs on systemd systems[2] for more details about UID ranges. These journal files will not be owned by the user, however, in order to avoid that the user can write to them directly. Instead, file system ACLs are used to ensure the user gets read access only.

Additional users and groups may be granted access to journal files via file system access control lists (ACL). Distributions and administrators may choose to grant read access to all members of the "wheel" and "adm" system groups with a command such as the following:

# setfacl -Rnm g:wheel:rx,d:g:wheel:rx,g:adm:rx,d:g:adm:rx /var/log/journal/

Note that this command will update the ACLs both for existing journal files and for future journal files created in the /var/log/journal/ directory.

FILES

/etc/systemd/journald.conf

Configure systemd-journald behavior. See journald.conf(5).

Added in version 206.

/run/log/journal/machine-id/*.journal, /run/log/journal/machine-id/*.journal~, /var/log/journal/machine-id/*.journal, /var/log/journal/machine-id/*.journal~

systemd-journald writes entries to files in /run/log/journal/machine-id/ or /var/log/journal/machine-id/ with the ".journal" suffix. If the daemon is stopped uncleanly, or if the files are found to be corrupted, they are renamed using the ".journal~" suffix, and systemd-journald starts writing to a new file. /run/ is used when /var/log/journal is not available, or when Storage=volatile is set in the journald.conf(5) configuration file.

When systemd-journald ceases writing to a journal file, it will be renamed to "original-name@suffix.journal" (or "original-name@suffix.journal~"). Such files are "archived" and will not be written to any more.

In general, it is safe to read or copy any journal file (active or archived). journalctl(1) and the functions in the sd-journal(3) library should be able to read all entries that have been fully written.

systemd-journald will automatically remove the oldest archived journal files to limit disk use. See SystemMaxUse= and related settings in journald.conf(5).

Added in version 206.

/dev/kmsg, /dev/log, /run/systemd/journal/dev-log, /run/systemd/journal/socket, /run/systemd/journal/stdout

Sockets and other file node paths that systemd-journald will listen on and are visible in the file system. In addition to these, systemd-journald can listen for audit events using netlink(7), depending on whether "systemd-journald-audit.socket" is enabled or not.

Added in version 228.

If journal namespacing is used these paths are slightly altered to include a namespace identifier, see above.
