NOMBRE

systemd.socket - Configuración de unidad de socket

SINOPSIS

socket.socket

DESCRIPCIÓN

Un archivo de configuración de unidad cuyo nombre termina en ".socket" codifica información sobre un socket IPC o de red o una FIFO del sistema de archivos controlado y supervisado por systemd, para la activación basada en sockets.

Esta página del manual enumera las opciones de configuración específicas de este tipo de unidad. Consulte systemd.unit(5) para ver las opciones comunes de todos los archivos de configuración de unidad. Los elementos de configuración comunes se configuran en las secciones genéricas [Unit] e [Install]. Las opciones de configuración específicas del socket se configuran en la sección [Socket].

Opciones adicionales se enumeran en systemd.exec(5), que definen el entorno de ejecución en el que se ejecutan los comandos ExecStartPre=, ExecStartPost=, ExecStopPre= y ExecStopPost=, y en systemd.kill(5), que definen la forma en que se terminan los procesos, y en systemd.resource-control(5), que configuran los ajustes de control de recursos para los procesos del socket.

Por cada unidad de socket, debe existir una unidad de servicio correspondiente, que describa el servicio a iniciar ante el tráfico entrante en el socket (consulte systemd.service(5) para más información sobre las unidades .service). El nombre de la unidad .service es por defecto el mismo que el nombre de la unidad .socket, pero puede ser modificado con la opción Service= descrita a continuación. Dependiendo del ajuste de la opción Accept= descrita a continuación, esta unidad .service debe llamarse como la unidad .socket, pero con el sufijo reemplazado, a menos que se anule con Service=; o debe ser una unidad plantilla llamada de la misma manera. Ejemplo: un archivo de socket foo.socket necesita un servicio correspondiente foo.service si se establece Accept=no. Si se establece Accept=yes, debe existir una plantilla de servicio foo@.service a partir de la cual se instancien servicios para cada conexión entrante.

No se añade ninguna dependencia implícita de WantedBy= o RequiredBy= desde el socket al servicio. Esto significa que el servicio puede iniciarse sin el socket, en cuyo caso debe ser capaz de abrir sockets por sí mismo. Para evitar esto, se puede añadir una dependencia explícita de Requires=.

Las unidades de socket pueden usarse para implementar el inicio de servicios bajo demanda, así como el inicio paralelizado de servicios. Vea las historias de blog enlazadas al final para una introducción.

Tenga en cuenta que el software demonio configurado para la activación de sockets con unidades de socket necesita ser capaz de aceptar sockets de systemd, ya sea a través de la interfaz nativa de systemd para pasar sockets (consulte sd_listen_fds(3) para más detalles sobre el protocolo preciso utilizado y el orden en que se pasan los descriptores de archivo) o a través del paso de sockets tradicional estilo inetd(8) (es decir, sockets pasados a través de la entrada y salida estándar, usando StandardInput=socket en el archivo de servicio).

Todos los sockets de red asignados a través de unidades .socket se asignan en el espacio de nombres de red del host (consulte network_namespaces(7)). Sin embargo, esto no significa que el servicio activado por una unidad de socket configurada tenga que formar parte también del espacio de nombres de red del host. Se admite e incluso es una buena práctica ejecutar servicios en sus propios espacios de nombres de red (por ejemplo, a través de PrivateNetwork=, consulte systemd.exec(5)), recibiendo solo los sockets configurados a través de la activación de sockets desde el espacio de nombres del host. En tal configuración, la comunicación dentro del espacio de nombres de red del host solo se permite a través de los sockets de activación pasados, mientras que todos los sockets asignados desde el código del servicio estarán asociados con el propio espacio de nombres del servicio, y por lo tanto, posiblemente sujetos a una configuración restrictiva.

DEPENDENCIAS AUTOMÁTICAS

Dependencias Implícitas

Las siguientes dependencias se añaden implícitamente:

•Las unidades de socket obtienen automáticamente una dependencia Before= en las unidades de servicio que activan.
•Las unidades de socket que hacen referencia a rutas del sistema de archivos (como sockets AF_UNIX o FIFOs) obtienen implícitamente dependencias Requires= y After= en todas las unidades de montaje necesarias para acceder a esas rutas.
•Las unidades de socket que utilizan el ajuste BindToDevice= obtienen automáticamente una dependencia BindsTo= y After= en la unidad de dispositivo que encapsula la interfaz de red especificada.

Se pueden añadir dependencias implícitas adicionales como resultado de los parámetros de ejecución y control de recursos, según se documenta en systemd.exec(5) y systemd.resource-control(5).

Dependencias Predeterminadas

Las siguientes dependencias se añaden a menos que se establezca DefaultDependencies=no:

•Las unidades de socket obtienen automáticamente una dependencia Before= en sockets.target.
•Las unidades de socket obtienen automáticamente un par de dependencias After= y Requires= en sysinit.target, y un par de dependencias Before= y Conflicts= en shutdown.target. Estas dependencias aseguran que la unidad de socket se inicie antes que los servicios normales al arrancar, y se detenga al apagar. Solo los sockets involucrados en el arranque temprano o en el apagado tardío del sistema deben deshabilitar la opción DefaultDependencies=.

OPCIONES

Los archivos de unidad de socket pueden incluir secciones [Unit] e [Install], que se describen en systemd.unit(5).

Los archivos de unidad de socket deben incluir una sección [Socket], que contiene información sobre el socket o FIFO que supervisa. Una serie de opciones que pueden usarse en esta sección se comparten con otros tipos de unidad. Estas opciones se documentan en systemd.exec(5), systemd.kill(5) y systemd.resource-control(5). Las opciones específicas de la sección [Socket] de las unidades de socket son las siguientes:

ListenStream=, ListenDatagram=, ListenSequentialPacket=

Especifica una dirección en la que escuchar para un socket de flujo (SOCK_STREAM), datagrama (SOCK_DGRAM) o paquete secuencial (SOCK_SEQPACKET), respectivamente. La dirección puede escribirse en varios formatos:

Si la dirección comienza con una barra ("/"), se lee como un socket del sistema de archivos en la familia de sockets AF_UNIX.

Si la dirección comienza con un arroba ("@"), se lee como un socket del espacio de nombres abstracto en la familia AF_UNIX. El "@" se reemplaza con un carácter NUL antes de enlazar. Para más detalles, consulte unix(7).

Si la cadena de dirección es un solo número, se lee como un número de puerto para escuchar vía IPv6. Dependiendo del valor de BindIPv6Only= (ver abajo) esto podría resultar en que el servicio esté disponible tanto vía IPv6 como IPv4 (predeterminado) o solo vía IPv6.

Si la cadena de dirección es una cadena en el formato "v.w.x.y:z", se interpreta como una dirección IPv4 v.w.x.y y un puerto z.

Si la cadena de dirección es una cadena en el formato "[x]:y", se interpreta como una dirección IPv6 x y un puerto y. Se puede especificar un alcance de interfaz opcional (nombre o número de interfaz) después de un símbolo "%": "[x]:y%dev". Los alcances de interfaz solo son útiles con direcciones de enlace local, ya que el kernel las ignora en otros casos. Tenga en cuenta que si una dirección se especifica como IPv6, aún podría hacer que el servicio esté disponible también a través de IPv4, dependiendo de la configuración de BindIPv6Only= (ver abajo).

Si la cadena de dirección es una cadena en el formato "vsock:x:y", se lee como un CID x en un puerto y dirección en la familia AF_VSOCK. El CID es un identificador único de 32 bits en AF_VSOCK análogo a una dirección IP. La especificación del CID es opcional y puede establecerse como una cadena vacía. "vsock" puede ser reemplazado por "vsock-stream", "vsock-dgram"

or "vsock-seqpacket" para forzar el uso del tipo de socket correspondiente.

Tenga en cuenta que SOCK_SEQPACKET (es decir, ListenSequentialPacket=) solo está disponible para sockets AF_UNIX. SOCK_STREAM (es decir, ListenStream=) cuando se usa para sockets IP se refiere a sockets TCP, SOCK_DGRAM (es decir, ListenDatagram=) a UDP.

Estas opciones se pueden especificar varias veces, en cuyo caso el tráfico entrante en cualquiera de los sockets activará la activación del servicio, y todos los sockets listados se pasarán al servicio, sin importar si hay tráfico entrante en ellos o no. Si se asigna la cadena vacía a alguna de estas opciones, se restablece la lista de direcciones en las que escuchar, y todos los usos previos de cualquiera de estas opciones no tendrán efecto.

También es posible tener más de una unidad de socket para el mismo servicio al usar Service=, y el servicio recibirá todos los sockets configurados en todas las unidades de socket. Los sockets configurados en una unidad se pasan en el orden de configuración, pero no se especifica ningún orden entre las unidades de socket.

Si se utiliza una dirección IP aquí, a menudo es deseable escuchar en ella antes de que la interfaz en la que está configurada esté activa y en funcionamiento, e incluso independientemente de si estará activa y en funcionamiento en algún momento. Para lidiar con esto, se recomienda establecer la opción FreeBind= descrita a continuación.

ListenFIFO=

Especifica una FIFO del sistema de archivos (consulte fifo(7) para obtener detalles) en la que escuchar. Esto espera una ruta de archivo del sistema de archivos absoluta como argumento. El comportamiento de lo contrario es muy similar a la directiva ListenDatagram= anterior.

ListenSpecial=

Especifica un archivo especial en el sistema de archivos en el que escuchar. Esto espera una ruta de archivo del sistema de archivos absoluta como argumento. El comportamiento de lo contrario es muy similar a la directiva ListenFIFO= anterior. Úselo para abrir nodos de dispositivo de caracteres, así como archivos especiales en /proc/ y /sys/.

ListenNetlink=

Especifica una familia Netlink para crear un socket en el que escuchar. Esto espera una cadena corta que se refiere al nombre de la familia AF_NETLINK (como audit o kobject-uevent) como argumento, opcionalmente seguido por un espacio y un número entero de grupo multicast. El comportamiento de lo contrario es muy similar a la directiva ListenDatagram= anterior.

ListenMessageQueue=

Especifica un nombre de cola de mensajes POSIX en el que escuchar (consulte mq_overview(7) para obtener detalles). Esto espera un nombre de cola de mensajes válido (es decir, que comience con "/"). El comportamiento de lo contrario es muy similar a la directiva ListenFIFO= anterior. En Linux, los descriptores de cola de mensajes son en realidad descriptores de archivo y pueden heredarse entre procesos.

ListenUSBFunction=

Especifica una ubicación de puntos finales de USB FunctionFS[1] en la que escuchar, para la implementación de funciones de gadget USB. Esto espera una ruta de archivo absoluta del punto de montaje de FunctionFS como argumento. El comportamiento de lo contrario es muy similar a la directiva ListenFIFO= anterior. Úselo para abrir el punto final ep0 de FunctionFS. Al usar esta opción, el servicio activado debe tener establecidas las opciones USBFunctionDescriptors= y USBFunctionStrings=.

Añadido en la versión 227.

SocketProtocol=

Toma uno de udplite, sctp o mptcp. El socket utilizará el protocolo UDP-Lite (IPPROTO_UDPLITE), SCTP (IPPROTO_SCTP) o MPTCP (IPPROTO_MPTCP), respectivamente.

Añadido en la versión 229.

BindIPv6Only=

Toma uno de default, both o ipv6-only. Controla la opción de socket IPV6_V6ONLY (consulte ipv6(7) para obtener detalles). Si es both, los sockets IPv6 vinculados serán accesibles tanto a través de IPv4 como de IPv6. Si es ipv6-only, solo serán accesibles a través de IPv6. Si es default (que es el valor predeterminado, ¡sorpresa!), se utiliza la configuración predeterminada a nivel de sistema, controlada por /proc/sys/net/ipv6/bindv6only, que a su vez es equivalente a both.

Backlog=

Toma un argumento de entero sin signo de 32 bits. Especifica el número de conexiones en cola que aún no se han aceptado. Esta configuración solo es relevante para sockets de flujo y paquetes secuenciales. Consulte listen(2) para obtener detalles. El valor predeterminado es 4294967295. Tenga en cuenta que este valor es silenciosamente limitado por el sysctl "net.core.somaxconn", que normalmente es 4096 por defecto, por lo que normalmente el sysctl es la configuración que realmente importa.

BindToDevice=

Especifica el nombre de una interfaz de red a la que vincular este socket. Si se establece, el tráfico solo se aceptará de las interfaces de red especificadas. Esto controla la opción de socket SO_BINDTODEVICE (consulte socket(7) para obtener detalles). Si se utiliza esta opción, se crea una dependencia implícita de esta unidad de socket en la unidad del dispositivo de interfaz de red (consulte systemd.device(5)). Tenga en cuenta que establecer este parámetro puede resultar en la adición de dependencias adicionales a la unidad (ver arriba).

SocketUser=, SocketGroup=

Toma un nombre de usuario/grupo de UNIX. Cuando se especifican, todos los sockets AF_UNIX, nodos FIFO y colas de mensajes son propiedad del usuario y grupo especificados. Si no se establecen (predeterminado), los nodos son propiedad del usuario/grupo root (si se ejecuta en contexto de sistema) o del usuario/grupo que invoca (si se ejecuta en contexto de usuario). Si solo se especifica un usuario pero no un grupo, el grupo se deriva del grupo predeterminado del usuario.

Añadido en la versión 214.

SocketMode=

Si se escucha en un socket del sistema de archivos, FIFO o cola de mensajes, esta opción especifica el modo de acceso del sistema de archivos utilizado al crear el nodo de archivo. Toma un modo de acceso en notación octal. El valor predeterminado es 0666.

DirectoryMode=

Si se escucha en un socket del sistema de archivos o FIFO, los directorios padres se crean automáticamente si es necesario. Esta opción especifica el modo de acceso del sistema de archivos utilizado al crear estos directorios. Toma un modo de acceso en notación octal. El valor predeterminado es 0755.

Accept=

Toma un argumento booleano. Si es sí, se crea una instancia de servicio para cada conexión entrante y solo se le pasa el socket de conexión. Si es no, todos los sockets de escucha se pasan a la unidad de servicio iniciada, y solo se crea una unidad de servicio para todas las conexiones (ver también arriba). Este valor se ignora para los sockets de datagramas y FIFOs, donde una única unidad de servicio maneja incondicionalmente todo el tráfico entrante. El valor predeterminado es no.

Típicamente, para servicios sensibles al rendimiento, la opción Accept=no es preferible, ya que de esa manera solo la primera conexión tendrá que pagar el costo de recursos de activación. Por otro lado, para servicios utilizados esporádicamente, Accept=yes puede ser preferible ya que simplifica la implementación (ya que el código del programa de servicio solo tiene que procesar una única conexión en lugar de manejar múltiples) y permite una mayor seguridad (ya que las diversas opciones de aislamiento se pueden usar para aislar conexiones paralelas entre sí, ya que cada una es atendida por una instancia y proceso de servicio separados).

Un servicio que escucha en un socket AF_UNIX puede, pero no necesita, llamar a close(2) en el socket recibido antes de salir. Sin embargo, no debe eliminar el socket del sistema de archivos. No debe invocar shutdown(2) en los sockets que obtuvo con Accept=no, pero puede hacerlo para los sockets que obtuvo con Accept=yes establecido.

Establecer Accept=yes es particularmente útil para permitir que los demonios diseñados para su uso con inetd(8) funcionen sin modificaciones con la activación de sockets de systemd.

Tenga en cuenta que, dependiendo de esta configuración, los servicios activados por unidades de este tipo son servicios regulares (en caso de Accept=no) o instancias de servicios plantillas (en caso de Accept=yes). Consulte la sección Descripción anterior para una discusión más detallada de las reglas de nomenclatura de los servicios activados.

Para conexiones IPv4 e IPv6, la variable de entorno $REMOTE_ADDR contendrá la dirección IP remota, y $REMOTE_PORT contendrá el número de puerto remoto. Estas dos variables corresponden a las definidas por la interfaz CGI para servicios web (consulte RFC 3875[2]).

Para conexiones de socket AF_UNIX, la variable de entorno $REMOTE_ADDR contendrá la ruta del sistema de archivos del socket remoto comenzando con una barra ("/") o su dirección en el espacio de nombres abstracto comenzando con un arroba ("@"). Si el socket no tiene nombre, $REMOTE_ADDR no se establecerá.

Si se usa Accept=yes, el proceso de servicio activado tendrá establecida la variable de entorno $SO_COOKIE con la cookie del socket de Linux, formateada como un entero decimal. La cookie del socket se puede obtener de lo contrario a través de getsockopt(7).

Se recomienda establecer CollectMode=inactive-or-failed para las instancias de servicio activadas a través de Accept=yes, para asegurar que los servicios de conexión fallidos se limpien y se liberen de la memoria, y no se acumulen.

Writable=

Toma un argumento booleano. Solo se puede usar junto con ListenSpecial=. Si es verdadero, el archivo especial especificado se abre en modo de lectura/escritura; si es falso, en modo de solo lectura. El valor predeterminado es falso.

Añadido en la versión 227.

FlushPending=

Toma un argumento booleano. Solo se puede usar cuando Accept=no. Si es sí, los búferes del socket se borran después de que el servicio activado haya salido. Esto hace que se vacíen los datos pendientes y se rechacen las conexiones entrantes pendientes. Si es no, los búferes del socket no se borrarán, lo que permitirá al servicio manejar cualquier conexión pendiente después de reiniciar, que es el comportamiento esperado normalmente. El valor predeterminado es no.

Añadido en la versión 247.

MaxConnections=

El número máximo de conexiones para las que se ejecutarán simultáneamente instancias de servicio, cuando se establece Accept=yes. Si llegan más conexiones concurrentes, se rechazarán hasta que al menos una conexión existente termine. Esta configuración no tiene ningún efecto en los sockets configurados con Accept=no o sockets de datagramas. El valor predeterminado es 64.

MaxConnectionsPerSource=

El número máximo de conexiones para un servicio por dirección IP de origen (en caso de IPv4/IPv6), por CID de origen (en caso de AF_VSOCK) o UID de origen (en caso de AF_UNIX). Esto es muy similar a la directiva MaxConnections= anterior. El valor predeterminado es 0, es decir, deshabilitado.

Añadido en la versión 232.

KeepAlive=

Toma un argumento booleano. Si es verdadero, la pila TCP/IP enviará un mensaje keep alive después de 2 horas (dependiendo de la configuración de /proc/sys/net/ipv4/tcp_keepalive_time) para todos los flujos TCP aceptados en este socket. Esto controla la opción de socket SO_KEEPALIVE (consulte socket(7) y el TCP Keepalive HOWTO[3] para más detalles). Por defecto es false.

KeepAliveTimeSec=

Toma tiempo (en segundos) como argumento. La conexión debe permanecer inactiva antes de que TCP comience a enviar sondeos de keepalive. Esto controla la opción de socket TCP_KEEPIDLE (consulte socket(7) y el TCP Keepalive HOWTO[3] para más detalles). El valor predeterminado es 7200 segundos (2 horas).

Añadido en la versión 216.

KeepAliveIntervalSec=

Toma tiempo (en segundos) como argumento entre sondeos individuales de keepalive, si la opción de socket SO_KEEPALIVE se ha establecido en este socket. Esto controla la opción de socket TCP_KEEPINTVL (consulte socket(7) y el TCP Keepalive HOWTO[3] para más detalles). El valor predeterminado es 75 segundos.

Añadido en la versión 216.

KeepAliveProbes=

Toma un entero como argumento. Es el número de sondeos no confirmados que se enviarán antes de considerar la conexión muerta y notificar a la capa de aplicación. Esto controla la opción de socket TCP_KEEPCNT (consulte socket(7) y el TCP Keepalive HOWTO[3] para más detalles). El valor predeterminado es 9.

Añadido en la versión 216.

NoDelay=

Toma un argumento booleano. El algoritmo Nagle de TCP funciona combinando un número de mensajes pequeños de salida y enviándolos todos a la vez. Esto controla la opción de socket TCP_NODELAY (consulte tcp(7)). Por defecto es false.

Añadido en la versión 216.

Priority=

Toma un argumento entero que controla la prioridad para todo el tráfico enviado desde este socket. Esto controla la opción de socket SO_PRIORITY (consulte socket(7) para más detalles.).

DeferAcceptSec=

Toma tiempo (en segundos) como argumento. Si se establece, el proceso de escucha solo se activará cuando lleguen datos al socket, y no inmediatamente cuando se establezca la conexión. Cuando se establece esta opción, se utilizará la opción de socket TCP_DEFER_ACCEPT (consulte tcp(7)), y el kernel ignorará los paquetes ACK iniciales sin datos. El argumento especifica la cantidad aproximada de tiempo que el kernel debe esperar datos entrantes antes de recurrir al comportamiento normal de honorar los paquetes ACK vacíos. Esta opción es beneficiosa para protocolos en los que el cliente envía primero los datos (por ejemplo, HTTP, en contraste con SMTP), ya que el proceso del servidor no se activará innecesariamente antes de que pueda tomar alguna acción.

Si el cliente también utiliza la opción TCP_DEFER_ACCEPT, la latencia de la conexión inicial puede reducirse, ya que el kernel enviará datos en el paquete final que establece la conexión (el tercer paquete en el "apretón de manos de tres vías").

Desactivada por defecto.

Añadido en la versión 216.

ReceiveBuffer=, SendBuffer=

Toma un argumento entero que controla los tamaños del búfer de recepción o envío de este socket, respectivamente. Esto controla las opciones de socket SO_RCVBUF y SO_SNDBUF (consulte socket(7) para más detalles.). Los sufijos habituales K, M, G son compatibles y se entienden en base 1024.

IPTOS=

Toma un argumento entero que controla el campo de Tipo de Servicio de IP para los paquetes generados desde este socket. Esto controla la opción de socket IP_TOS (consulte ip(7) para más detalles.). Se puede especificar una cadena numérica o una de las opciones low-delay, throughput, reliability o low-cost.

IPTTL=

Toma un argumento entero que controla el campo Time-To-Live de IPv4/Hop Count de IPv6 para los paquetes generados desde este socket. Esto establece las opciones de socket IP_TTL/IPV6_UNICAST_HOPS (consulte ip(7) y ipv6(7) para más detalles.)

Mark=

Toma un valor entero. Controla la marca del firewall de los paquetes generados por este socket. Esto se puede utilizar en la lógica del firewall para filtrar paquetes de este socket. Esto establece la opción de socket SO_MARK. Consulte iptables(8) para más detalles.

ReusePort=

Toma un valor booleano. Si es verdadero, permite múltiples bind(2)s a este puerto TCP o UDP. Esto controla la opción de socket SO_REUSEPORT. Consulte socket(7) para más detalles.

Añadido en la versión 206.

SmackLabel=, SmackLabelIPIn=, SmackLabelIPOut=

Toma un valor de cadena. Controla los atributos extendidos "security.SMACK64", "security.SMACK64IPIN" y "security.SMACK64IPOUT", respectivamente, es decir, la etiqueta de seguridad del FIFO, o la etiqueta de seguridad para las conexiones entrantes o salientes del socket, respectivamente. Consulte Smack[4] para más detalles.

Añadido en la versión 196.

SELinuxContextFromNet=

Toma un argumento booleano. Cuando es verdadero, systemd intentará determinar la etiqueta SELinux utilizada para el servicio instanciado a partir de la información proporcionada por el par a través de la red. Tenga en cuenta que solo se utiliza el nivel de seguridad de la información proporcionada por el par. Otras partes del contexto SELinux resultante se originan en el binario de destino que se activa efectivamente por la unidad de socket o en el valor de la opción SELinuxContext=. Esta opción de configuración solo se aplica cuando el servicio activado se pasa en un único descriptor de archivo de socket, es decir, servicios que tienen la entrada estándar conectada a un socket o servicios activados por exactamente una unidad de socket. Tenga en cuenta también que esta opción solo es útil cuando se implementa la política SELinux MLS/MCS. Por defecto es "false".

Añadido en la versión 217.

PipeSize=

Toma un tamaño en bytes. Controla el tamaño del búfer de tubería de los FIFOs configurados en esta unidad de socket. Consulte fcntl(2) para más detalles. Los sufijos habituales K, M, G son compatibles y se entienden en base 1024.

MessageQueueMaxMessages=, MessageQueueMessageSize=

Estas dos configuraciones toman valores enteros y controlan el campo mq_maxmsg o el campo mq_msgsize, respectivamente, al crear la cola de mensajes. Tenga en cuenta que se deben establecer ninguna o ambas de estas variables. Consulte mq_setattr(3) para más detalles.

FreeBind=

Toma un valor booleano. Controla si el socket puede ser vinculado a direcciones IP no locales. Esto es útil para configurar sockets que escuchan en direcciones IP específicas antes de que esas direcciones IP se configuren correctamente en una interfaz de red. Esto establece la opción de socket IP_FREEBIND/IPV6_FREEBIND. Por razones de robustez, se recomienda utilizar esta opción siempre que se vincule un socket a una dirección IP específica. Por defecto es false.

Transparent=

Toma un valor booleano. Controla la opción de socket IP_TRANSPARENT/IPV6_TRANSPARENT. Por defecto es false.

Broadcast=

SERVICE DIRECTIVES

Socket units do not have many directives of their own. They largely inherit directives from other unit types, especially from systemd.exec(5) and systemd.kill(5). The following directives are specific to socket units:

ListenStream=, ListenSequentialStream=, ListenDatagram=, ListenSequentialPacket=, ListenFIFO=, ListenSpecial=, ListenNetlink=, ListenMessageQueue=
Configures listening endpoints. These directives take an address description (for network sockets) or a file system path (for FIFO or Unix domain sockets). The syntax of the address description is described in systemd.socket(5). For network sockets, a specific address may be prefixed with an identifier such as "127.0.0.1:" or "[::1]:". If no address is given, the socket is bound to all available interfaces. For sockets in the file system, the path must be absolute. For Unix domain sockets, the socket type is determined by the directive used. For network sockets, ListenStream= should be used for TCP and Datagram= for UDP.

Only one of these directives may be used per unit file. There are exceptions: multiple Listen...= directives may be used if they refer to different address families (e.g. IPv4 and IPv6) or to different protocols within the same address family (e.g. TCP and UDP). Furthermore, they may be mixed with ListenFIFO=, ListenSpecial=, ListenNetlink=, or ListenMessageQueue=.

It is possible to configure multiple addresses for a single socket by repeating the directive. The set of addresses is then unionized.

Defaults to an empty list.

Service=
Specifies the service unit name to activate on incoming traffic. This setting is only allowed for sockets with Accept=no. It defaults to the service that bears the same name as the socket (with the suffix replaced). In most cases, it should not be necessary to use this option. Note that setting this parameter might result in additional dependencies to be added to the unit (see above).
SocketUser=, SocketGroup=
Specifies the user and group to set the socket and its file descriptors to. If one of them is not specified, the primary user/group of the user specified in the other is used. If neither is specified, the socket is created with the privileges of the system instance. These settings are only available for sockets that are created in the file system. Defaults to empty (socket created with system instance privileges).
SocketMode=
Specifies the file system mode for sockets that are created in the file system. Expects a file mode in octal notation. Defaults to 0660.
DirectoryMode=
Specifies the file system mode for directories that are created underneath the socket path. Expects a file mode in octal notation. Defaults to 0755.
Accept=
Configures socket-based activation. If set to "yes", the socket is a listening socket. When a connection arrives, the socket is duplicated and the original socket is kept listening. The duplicated socket is passed to the activated service. If set to "no", the socket is a connection socket. When a connection arrives, the socket is duplicated and the original socket is kept listening. The duplicated socket is passed to the activated service. If set to "hash", the socket is a connection socket. The duplicated socket is passed to the activated service. It differs from Accept=no in that the socket descriptor is passed to the service unit, rather than creating a new connection on a pre-existing socket. Defaults to "no".
MaxConnections=
Configures the maximum number of concurrent connections for a socket. This option is only available for sockets configured with Accept=yes. It defaults to 100. A value of 0 disables the limit.
MaxFiles=
Configures the maximum number of file descriptors that may be opened by this socket unit. This option is only available for sockets configured with Accept=yes. It defaults to the value of DefaultMaxFiles= in systemd-system.conf(5), which is 32768. A value of 0 disables the limit.
NoDelay=
Enables or disables the TCP_NODELAY socket option. See TCP Keepalive HOWTO[3] for details. Defaults to off.
DeferAcceptSec=
Configures the time to wait for data after a connection has been established before accepting it. This option is only available for sockets configured with Accept=yes. It defaults to 0s, meaning connections are accepted immediately. Set to "infinity" to disable the timeout logic. See systemd.kill(5).
KeepAlive=
Configures the parameters for TCP keepalive. This option is only available for sockets configured with Accept=yes. It defaults to off. The value is a time span (see systemd.time(7)). When enabled, the kernel will periodically send packets to the peer to check if the connection is still alive. If the peer does not respond after several attempts, the connection is torn down.
KeepAliveTimeSec=, KeepAliveIntervalSec=, KeepAliveProbes=
Configures the parameters for TCP keepalive. These values override the settings in the kernel. See TCP Keepalive HOWTO[3] for details. The values are unit-less integers representing seconds, or time spans (see systemd.time(7)).
BindToDevice=
Binds the socket to a specific network device. This is only useful for network sockets. If the specified device does not exist or is not configured, the socket activation fails. If the device is specified with a trailing asterisk, the socket is bound to all devices with that prefix. If an empty string is assigned, the list of devices is reset. Defaults to an empty list.
SmackOnly=
Takes a boolean argument. If enabled, the socket will only be accessible to services running with Smack security labels. This is only useful for sockets in the file system. Defaults to off. See Smack[4].
SmackLabel=
Sets the Smack label for sockets in the file system. Defaults to empty.
SmackCommunicator=
Sets the Smack label for communicating socket endpoints. Defaults to empty.
SmackTaskLabel=
Sets the Smack label for tasks associated with the socket. Defaults to empty.
Freebind=
Takes a boolean argument. If enabled, allows binding to non-local IP addresses. This is useful for multi-homed hosts or when setting up proxies. Defaults to off.
ReuseAddress=
Takes a boolean argument. If enabled, allows the socket to bind to an address that is already in use. This is useful for server applications that need to be restarted quickly. Defaults to off.
Transparent=
Takes a boolean argument. If enabled, allows the socket to send and receive packets with the IP address of another host. This is useful for proxying and load balancing. Defaults to off.
IPv6Only=
Takes a boolean argument. If enabled, the socket will only accept IPv6 connections. This is only useful for network sockets. Defaults to off.
Broadcast=
Takes a boolean argument. If enabled, allows sending broadcast messages. This is only useful for datagram sockets. Defaults to off.
ReceiveBufferSiz=, SendBufferSiz=
Configures the size of the receive and send buffers for the socket. Takes a unit-less value in bytes, or a time span value such as "5min 20s". Pass "0" to disable the setting (use system default). Defaults to 0.
ListenNetlinkGroup=, ListenNetlinkSubsystem=
Configures Netlink sockets. ListenNetlinkGroup= takes a comma-separated list of group IDs to subscribe to. ListenNetlinkSubsystem= takes a comma-separated list of subsystem names. See systemd.socket(5) for details.
DeferCloseSrv=
Takes a boolean argument. If enabled, the socket will not be closed until the service that was activated by it has terminated. This is useful for services that need to keep the socket open after they have been activated. Defaults to off.
TimeoutSec=
Configures the timeout for socket activation. If the service is not activated within this time, the socket is closed and activation fails. Takes a unit-less value in seconds, or a time span value such as "5min 20s". Pass "0" to disable the timeout logic. Defaults to DefaultTimeoutStartSec= from the manager configuration file (see systemd-system.conf(5)). (This directive is equivalent to TimeoutStartSec= in systemd.kill(5).) Takes a unit-less value in seconds, or a time span value such as "5min 20s". Pass "0" to disable the timeout logic. Defaults to DefaultTimeoutStartSec= from the manager configuration file (see systemd-system.conf(5)).
Service=
Specifies the service unit name to activate on incoming traffic. This setting is only allowed for sockets with Accept=no. It defaults to the service that bears the same name as the socket (with the suffix replaced). In most cases, it should not be necessary to use this option. Note that setting this parameter might result in additional dependencies to be added to the unit (see above).
RemoveOnStop=
Takes a boolean argument. If enabled, any file nodes created by this socket unit are removed when it is stopped. This applies to AF_UNIX sockets in the file system, POSIX message queues, FIFOs, as well as any symlinks to them configured with Symlinks=. Normally, it should not be necessary to use this option, and is not recommended as services might continue to run after the socket unit has been terminated and it should still be possible to communicate with them via their file system node. Defaults to off.

Added in version 214.

Symlinks=
Takes a list of file system paths. The specified paths will be created as symlinks to the AF_UNIX socket path or FIFO path of this socket unit. If this setting is used, only one AF_UNIX socket in the file system or one FIFO may be configured for the socket unit. Use this option to manage one or more symlinked alias names for a socket, binding their lifecycle together. Note that if creation of a symlink fails this is not considered fatal for the socket unit, and the socket unit may still start. If an empty string is assigned, the list of paths is reset. Defaults to an empty list.

Added in version 214.

FileDescriptorName=
Assigns a name to all file descriptors this socket unit encapsulates. This is useful to help activated services identify specific file descriptors, if multiple fds are passed. Services may use the sd_listen_fds_with_names(3) call to acquire the names configured for the received file descriptors. Names may contain any ASCII character, but must exclude control characters and ":", and must be at most 255 characters in length. If this setting is not used, the file descriptor name defaults to the name of the socket unit (including its .socket suffix) when Accept=no, "connection" otherwise.

Added in version 227.

TriggerLimitIntervalSec=, TriggerLimitBurst=
Configures a limit on how often this socket unit may be activated within a specific time interval. The TriggerLimitIntervalSec= setting may be used to configure the length of the time interval in the usual time units "us", "ms", "s", "min", "h", ... and defaults to 2s (See systemd.time(7) for details on the various time units understood). The TriggerLimitBurst= setting takes a positive integer value and specifies the number of permitted activations per time interval, and defaults to 200 for Accept=yes sockets (thus by default permitting 200 activations per 2s), and 20 otherwise (20 activations per 2s). Set either to 0 to disable any form of trigger rate limiting.

If the limit is hit, the socket unit is placed into a failure mode, and will not be connectible anymore until restarted. Note that this limit is enforced before the service activation is enqueued.

Compare with PollLimitIntervalSec=/PollLimitBurst= described below, which implements a temporary slowdown if a socket unit is flooded with incoming traffic, as opposed to the permanent failure state TriggerLimitIntervalSec=/TriggerLimitBurst= results in.

Added in version 230.

PollLimitIntervalSec=, PollLimitBurst=
Configures a limit on how often polling events on the file descriptors backing this socket unit will be considered. This pair of settings is similar to TriggerLimitIntervalSec=/TriggerLimitBurst= but instead of putting a (fatal) limit on the activation frequency puts a (transient) limit on the polling frequency. The expected parameter syntax and range are identical to that of the aforementioned options, and can be disabled the same way.

If the polling limit is hit polling is temporarily disabled on it until the specified time window passes. The polling limit hence slows down connection attempts if hit, but unlike the trigger limit will not cause permanent failures. It's the recommended mechanism to deal with DoS attempts through packet flooding.

The polling limit is enforced per file descriptor to listen on, as opposed to the trigger limit which is enforced for the entire socket unit. This distinction matters for socket units that listen on multiple file descriptors (i.e. have multiple ListenXYZ= stanzas).

These setting defaults to 150 (in case of Accept=yes) and 15 (otherwise) polling events per 2s. This is considerably lower than the default values for the trigger limit (see above) and means that the polling limit should typically ensure the trigger limit is never hit, unless one of them is reconfigured or disabled.

Added in version 255.

DeferTrigger=
Takes a boolean argument, or "patient". May only be used when Accept=no. If enabled, job mode "lenient" instead of "replace" is used when triggering the service, which means currently activating/running units that conflict with the service won't be disturbed/brought down. Furthermore, if a conflict exists, the socket unit will wait for current job queue to complete and potentially defer the activation by then. An upper limit of total time to wait can be configured via DeferTriggerMaxSec=. If set to yes, the socket unit will fail if all jobs have finished or the timeout has been reached but the conflict remains. If patient, always wait until DeferTriggerMaxSec= elapses. Defaults to no.

This setting is particularly useful if the socket unit should stay active across switch-root/soft-reboot operations while the triggered service is stopped.

Added in version 258.

DeferTriggerMaxSec=
Configures the maximum time to defer the triggering when DeferTrigger= is enabled. If the service cannot be activated within the specified time, the socket will be considered failed and get terminated. Takes a unit-less value in seconds, or a time span value such as "5min 20s". Pass "0" or "infinity" to disable the timeout logic (the default).

Added in version 258.

PassFileDescriptorsToExec=
Takes a boolean argument. Defaults to off. If enabled, file descriptors created by the socket unit are passed to ExecStartPost=, ExecStopPre=, and ExecStopPost= commands from the socket unit. The passed file descriptors can be accessed with sd_listen_fds(3) as if the commands were invoked from the associated service units. Note that ExecStartPre= command cannot access socket file descriptors.

Added in version 256.
