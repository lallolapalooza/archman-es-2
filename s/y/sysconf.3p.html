SYSCONF(3P) Manual del programador POSIX SYSCONF(3P)

PROLOG

Esta página del manual forma parte del Manual del programador POSIX. La implementación de Linux de esta interfaz puede diferir (consulte la página del manual de Linux correspondiente para conocer los detalles del comportamiento de Linux), o la interfaz puede no estar implementada en Linux.

NOMBRE

sysconf — obtener variables configurables del sistema

SINOPSIS

#include <unistd.h>
long sysconf(int name);

DESCRIPCIÓN

La función sysconf() proporciona un método para que la aplicación determine el valor actual de un límite u opción configurable del sistema (variable). La implementación deberá soportar todas las variables listadas en la siguiente tabla y puede soportar otras.

El argumento name representa la variable del sistema a consultar. La siguiente tabla lista el conjunto mínimo de variables del sistema de <limits.h> o <unistd.h> que pueden ser devueltas por sysconf(), y las constantes simbólicas definidas en <unistd.h> que son los valores correspondientes usados para name.

VER TAMBIÉN

pathconf(3p), fpathconf(3p), confstr(3p), limits.h(3p), unistd.h(3p)

ESTÁNDARES

La especificación POSIX.1-2008™ ™ sysconf()

DISPONIBILIDAD

La funcionalidad de este comando está disponible en la mayoría de los sistemas que implementan POSIX.1-2008.

COPYRIGHT

La información proporcionada aquí se basa en la especificación POSIX.1-2008. Los detalles específicos de implementación pueden variar entre sistemas.

VALOR DE RETORNO

Si name es un valor inválido, sysconf() devolverá -1 y establecerá errno para indicar el error. Si la variable correspondiente a name se describe en <limits.h> como un valor máximo o mínimo y la variable no tiene límite, sysconf() devolverá -1 sin cambiar el valor de errno. Tenga en cuenta que los límites indefinidos no implican límites infinitos; vea <limits.h>.

De lo contrario, sysconf() devolverá el valor actual de la variable en el sistema. El valor devuelto no será más restrictivo que el valor correspondiente descrito a la aplicación cuando fue compilada con el <limits.h> o <unistd.h> de la implementación. El valor no cambiará durante la vida del proceso que llama, excepto que sysconf(_SC_OPEN_MAX) puede devolver valores diferentes antes y después de una llamada a setrlimit() que cambie el límite suave RLIMIT_NOFILE.

Si la variable correspondiente a name depende de una opción no soportada, los resultados no están especificados.

ERRORES

La función sysconf() fallará si:

EINVAL
El valor del argumento name es inválido.

EJEMPLOS

Ninguno.

USO EN APLICACIONES

Como -1 es un valor de retorno permisible en una situación exitosa, una aplicación que desee verificar situaciones de error debe establecer errno a 0, luego llamar a sysconf(), y, si devuelve -1, verificar si errno es distinto de cero.

Los desarrolladores de aplicaciones deben verificar si una opción, como _POSIX_TRACE, está soportada antes de obtener y usar valores para variables relacionadas, como _POSIX_TRACE_NAME_MAX.

FUNDAMENTO

Esta funcionalidad se añadió en respuesta a los requisitos de los desarrolladores de aplicaciones y de los proveedores de sistemas que manejan muchas configuraciones de sistemas internacionales. Está estrechamente relacionada con pathconf() y fpathconf().

Aunque una aplicación que cumple puede ejecutarse en todos los sistemas sin demandar más recursos que los valores mínimos publicados en este volumen de POSIX.1-2017, es útil para esa aplicación poder usar el valor real de la cantidad de recursos disponibles en cualquier sistema dado. Para hacer esto, la aplicación hace uso del valor de una constante simbólica en <limits.h> o <unistd.h>.

Sin embargo, una vez compilada, la aplicación aún debe ser capaz de manejar si la cantidad de recurso disponible aumenta. Para ello, una aplicación puede necesitar un medio para determinar la cantidad de un recurso, o la presencia de una opción, en tiempo de ejecución.

Se ofrecen dos ejemplos:

1.
Las aplicaciones pueden desear actuar de manera diferente en sistemas con o sin control de trabajos. Los proveedores de aplicaciones que deseen distribuir solo un paquete binario a todas las instancias de una arquitectura de computadora se verían obligados a asumir que el control de trabajos nunca está disponible si dependieran únicamente del valor de <unistd.h> publicado en este volumen de POSIX.1-2017.
2.
Los proveedores de aplicaciones internacionales requieren ocasionalmente conocimiento del número de ticks de reloj por segundo. Sin estas facilidades, se verían obligados a distribuir sus aplicaciones parcialmente en formato fuente o a tener versiones de 50 Hz y 60 Hz para los diversos países en los que operan.

Es el conocimiento de que muchas aplicaciones se distribuyen ampliamente en forma ejecutable lo que lleva a esta facilidad. Si se limitan a los valores más restrictivos en las cabeceras, tales aplicaciones tendrían que estar preparadas para aceptar los entornos más limitados que ofrecen las microcomputadoras más pequeñas. Aunque esto es completamente portable, hubo un consenso en que deberían poder aprovechar las facilidades ofrecidas por los sistemas grandes, sin las restricciones asociadas con las distribuciones de fuente y objeto.

Durante las discusiones de esta característica, se señaló que casi siempre es posible que una aplicación determine cuál podría ser un valor en tiempo de ejecución probando adecuadamente las diversas funciones. Y, en cualquier caso, siempre se podría escribir para manejar adecuadamente los retornos de error de las diversas funciones.

RATIONALE

The POSIX.1-2001 standard introduced the sysconf() function to provide an interface to implementation-dependent configuration parameters. Before POSIX.1-2001, only pathconf() and fpathconf() were available, and they were defined in terms of pathnames or file descriptors. The committee felt that it was useful to have a way to query system-wide configuration parameters without reference to a specific file or directory.

The initial proposal included many more parameters, but it was felt that this imposed an unreasonable level of complication and sophistication on the application developer.

This runtime facility is not meant to provide ever-changing values that applications have to check multiple times. The values are seen as changing no more frequently than once per system initialization, such as by a system administrator or operator with an automatic configuration program. This volume of POSIX.1‐2017 specifies that they shall not change within the lifetime of the process.

Some values apply to the system overall and others vary at the file system or directory level. The latter are described in fpathconf().

Note that all values returned must be expressible as integers. String values were considered, but the additional flexibility of this approach was rejected due to its added complexity of implementation and use.

Some values, such as {PATH_MAX}, are sometimes so large that they must not be used to, say, allocate arrays. The sysconf() function returns a negative value to show that this symbolic constant is not even defined in this case.

Similar to pathconf(), this permits the implementation not to have a limit. When one resource is infinite, returning an error indicating that some other resource limit has been reached is conforming behavior.
