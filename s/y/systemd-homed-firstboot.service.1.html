NOMBRE

homectl, systemd-homed-firstboot.service - Crear, eliminar, cambiar o inspeccionar directorios de inicio

SINOPSIS

homectl [OPCIONES...] {COMANDO} [NOMBRE...]

DESCRIPCIÓN

homectl puede usarse para crear, eliminar, cambiar o inspeccionar el directorio de inicio de un usuario. Es principalmente un comando que interactúa con systemd-homed.service(8), el cual gestiona los directorios de inicio de los usuarios.

Los directorios de inicio gestionados por systemd-homed.service son autónomos y, por lo tanto, incluyen el registro completo de metadatos del usuario en el propio almacenamiento de datos del inicio, lo que facilita su migración entre máquinas. En particular, un directorio de inicio describe un registro de usuario correspondiente, y cada registro de usuario gestionado por systemd-homed.service implica también la existencia y encapsulación de un directorio de inicio. La cuenta de usuario y el directorio de inicio se convierten en el mismo concepto.

Los siguientes mecanismos de almacenamiento de respaldo son compatibles:

•Un archivo individual de loopback cifrado LUKS2 para un usuario, almacenado en /home/*.home. Al iniciar sesión, el sistema de archivos contenido en este archivo se monta después de que el volumen cifrado LUKS2 ha sido adjuntado. La contraseña del usuario es idéntica a la contraseña de cifrado del volumen LUKS2. Por lo tanto, el acceso a los datos sin una autenticación previa del usuario no es posible, ni siquiera para el administrador del sistema. Este mecanismo de almacenamiento proporciona la mayor seguridad de datos y, por lo tanto, se recomienda.

•Similar, pero el sistema de archivos cifrado LUKS2 se encuentra en un dispositivo de bloque regular, como una memoria USB. En este modo, los directorios de inicio y todos los datos que incluyen son fácilmente migratorios entre máquinas, simplemente conectando la memoria USB a diferentes sistemas en diferentes momentos.

•Un directorio cifrado utilizando "fscrypt" en sistemas de archivos que lo admiten (actualmente, esto es principalmente "ext4"), ubicado en /home/*.homedir. Este mecanismo también proporciona cifrado, pero sustancialmente más débil que LUKS2, ya que la mayoría de los metadatos del sistema de archivos no están protegidos. Además, actualmente no admite el cambio de contraseñas de usuario una vez que se ha creado el directorio de inicio.

•Una subvolumen de "btrfs" para cada usuario, también ubicada en /home/*.homedir. Esto no proporciona cifrado, pero sí un buen soporte de cuotas.

•Un directorio regular para cada usuario, también ubicado en /home/*.homedir. Esto no proporciona cifrado, pero es una alternativa adecuada disponible en todas las máquinas, incluso donde no hay soporte para LUKS2, "fscrypt" o "btrfs".

•Un recurso compartido de archivos de Windows (CIFS) individual para cada usuario.

Tenga en cuenta que systemd-homed.service y homectl no gestionarán cuentas de usuario UNIX "clásicas", como las creadas con useradd(8) o herramientas similares. En particular, esta funcionalidad no es adecuada para gestionar usuarios del sistema (es decir, usuarios con un UID inferior a 1000), sino que es exclusiva para usuarios regulares ("humanos").

Tenga en cuenta que los usuarios/directorios de inicio gestionados a través de systemd-homed.service no aparecen en /etc/passwd y archivos similares; se sintetizan a través de glibc NSS durante la ejecución. Por lo tanto, son resolubles y pueden ser enumerados a través de la herramienta getent(1).

Esta herramienta interactúa directamente con systemd-homed.service y puede ejecutar comandos específicos en los directorios de inicio que gestiona. Dado que cada directorio de inicio gestionado de esa manera también define un registro de usuario y grupo JSON, estos directorios de inicio también pueden ser inspeccionados y enumerados a través de userdbctl(1).

Los directorios de inicio gestionados por systemd-homed.service suelen estar en uno de dos estados, o en un estado de transición entre ellos: cuando están "activos", están desbloqueados y montados, y por lo tanto accesibles para el sistema y sus programas; cuando están "inactivos", no están montados y, por lo tanto, no son accesibles. La activación ocurre automáticamente al iniciar sesión del usuario y generalmente solo puede completarse después de haber proporcionado una contraseña (u otro token de autenticación). La desactivación ocurre después de que el usuario cierra completamente la sesión. Un directorio de inicio permanece activo mientras el usuario haya iniciado sesión al menos una vez, es decir, tenga al menos una sesión iniciada. Cuando el usuario inicia sesión por segunda vez simultáneamente, el directorio de inicio permanece activo. Se desactiva solo después de que finaliza la última de las sesiones del usuario.

OPCIONES

Las siguientes opciones generales son entendidas (más opciones que controlan las diversas propiedades de los registros de usuario gestionados por systemd-homed.service se documentan más abajo):

--identity=ARCHIVO

Lee el registro JSON del usuario desde el archivo especificado. Si se pasa como "-" lee el registro del usuario desde la entrada estándar. El objeto JSON proporcionado debe seguir la estructura documentada en Registros de Usuario JSON[1]. Esta opción se puede usar junto con los comandos create y update (ver más abajo), donde permite configurar el registro de usuario en JSON tal cual, en lugar de establecer las propiedades individuales del registro de usuario (ver más abajo).

Añadido en la versión 245.

--json=FORMATO, -j

Controla si se debe mostrar el registro de usuario en formato JSON, si se usa el comando inspect (ver más abajo). Toma uno de los valores "pretty", "short" o "off". Si es "pretty", se insertan espacios en blanco y saltos de línea amigables para humanos en la salida para hacer los datos JSON más legibles. Si es "short", se suprimen todos los espacios en blanco superfluos. Si es "off" (el predeterminado), la información del usuario no se muestra en formato JSON sino en un formato amigable y legible para humanos. La opción -j selecciona "pretty" cuando se ejecuta interactivamente y "short" en caso contrario.

Añadido en la versión 245.

--export-format=FORMATO, -E, -EE

Cuando se usa con el verbo inspect en modo JSON (ver arriba), puede usarse para suprimir ciertos aspectos del registro de usuario JSON en la salida. Específicamente, si se usa el formato "stripped", se eliminan los campos de enlace y ejecución del registro. Si se usa el formato "minimal", también se elimina la firma criptográfica. Si se usa el formato "full", se muestra el registro JSON completo (este es el predeterminado). Esta opción es útil para copiar un registro de usuario existente a un sistema diferente para crear un usuario similar allí con la misma configuración. Específicamente: homectl inspect -EE | ssh root@othersystem homectl create -i- puede usarse como comando simple para replicar un usuario en otro host. -E es equivalente a -j --export-format=stripped, -EE a -j --export-format=minimal. Tenga en cuenta que al replicar cuentas de usuario, los registros de usuario adquiridos en modo "stripped" conservarán las firmas criptográficas originales y, por lo tanto, solo podrán modificarse cuando la clave privada para actualizarlos esté disponible en la máquina de destino. Al replicar usuarios en modo "minimal", la firma se elimina durante la replicación y, por lo tanto, el registro se firmará implícitamente con la clave de la máquina de destino y podrá actualizarse allí sin ninguna replicación de clave privada.

Añadido en la versión 245.

--offline

No intente actualizar la copia del registro de usuario y el directorio de blobs incrustado dentro del área de inicio. Esto permite operar en áreas de inicio ausentes, o sin necesidad de autenticarse como el usuario que se está modificando.

Añadido en la versión 256.

--key-name=

Cuando se usa con el comando add-signing-key, especifica o anula el nombre bajo el cual se almacenará la clave pública que se está agregando. El nombre especificado puede elegirse libremente, pero debe tener el sufijo ".public". Si no se usa esta opción, el nombre se deriva del nombre de archivo especificado. Si una clave se lee desde la entrada estándar, esta opción es obligatoria para proporcionar un nombre adecuado para la clave que se está agregando.

Añadido en la versión 258.

--seize=

Toma un argumento booleano. Cuando se usa con create o register, controla si se deben eliminar las firmas criptográficas de los registros de usuario JSON proporcionados, lo que tiene el efecto de firmarlos con la clave de firma local (local.public) en su lugar. Si este interruptor se establece en true, los registros de usuario añadidos se convertirán en gestionados localmente (y, por lo tanto, podrán modificarse localmente), mientras que si se establece en false, los registros de usuario seguirán siendo gestionados y propiedad de su origen (y, por lo tanto, no podrán modificarse localmente). Este interruptor se establece predeterminadamente en true para create y false para register.

Añadido en la versión 258.

--prompt-new-user

Si se usa en conjunción con firstb

COMMAND LINE OPTIONS

The following options are available:

--wipe=
systemd-homed.service(8)'s home directory management service supports wiping home directories from devices. This is useful for securely deleting user data. This command does nothing if the home directory is not found or is empty.
--user-unit=UNIT
Takes a systemd unit name. This is the systemd user instance manager unit that is started when the user logs in. If not specified, it defaults to user@.service. This switch is only useful when creating or updating a user, not when querying or deleting. Added in version 245.
--image-path=PATH
Takes a path to a directory that holds the user's home directory image. The image may be a plain directory, or a LUKS-encrypted block device. If not specified, defaults to /home/$USER. See Encrypted Home Directories[1] for details.
--fs-type=TYPE
Takes a file system type (e.g. "ext4", "btrfs", "xfs", "luks"). This is used to determine the type of file system to create for the home directory image. If not specified, defaults to "ext4". This option is only useful when creating a home directory.
--wipe-device=
Takes a path to a block device. If specified, the entire block device is wiped using ATA Secure Erase or the `blkdiscard(8)` operation before being used as a home directory image. This is useful for securely deleting user data from a dedicated partition or disk.
--key-file=PATH
Takes a path to a file containing a cryptographic key. This key is used to encrypt or decrypt the user's home directory image. This option is only useful when creating or updating a home directory that is encrypted with LUKS. The key file must contain the raw key material in binary format. Added in version 256.
--password-file=PATH
Takes a path to a file containing the user's password hash. This is used to set the user's password when creating a new account. The password hash must be in a format recognized by `crypt(3)`. Added in version 256.
--password-empty=
If this switch is used, the user's password will be set to empty. This is generally not recommended for security reasons. Added in version 256.
--root-auth=
If this switch is used, systemd-homed will attempt to authenticate the user as root for privileged operations. This is useful when running homectl as a non-root user but requiring root privileges to modify user accounts. Added in version 256.
--system=
If this switch is used, the user account created will be a system account rather than a regular user account. System accounts typically have UIDs below 1000 and are used for system services. Added in version 256.
--match=, -A, -N, -T
Takes one of "this", "other", "any" or "auto". Some user record settings can be defined to match only specific machines, or all machines but one, or all machines. With this switch it is possibly to control to which machines to apply the settings appearing on the command line after it. If "this" is specified the setting will only apply to the local system (positive match), if "other" it will apply to all but the local system (negative match), if "any" it will apply to all systems (unless there's a matching positive or negative per-machine setting). If "auto" returns to the default logic: whether a setting applies by default to the local system or all systems depends on the option in question.

Note that only some user record settings can be conditioned like this. This option has no effect on the others and is ignored there. This option may appear multiple times in a single command line to apply settings conditioned by different matches to the same user record. See JSON User Records[1] for details on which settings may be used with such per-machine matching and which ones may not.

-A is a shortcut for --match=any, -T is short for --match=this and -N is short for --match=other.

Here's an example call that sets the storage field to "luks" on the local system, but to "cifs" on all others:

# homectl update lennart -T --storage=luks -N --storage=cifs

Added in version 258.

-H, --host=
Execute the operation remotely. Specify a hostname, or a username and hostname separated by "@" to connect to. The hostname may optionally be suffixed by a port ssh is listening on, separated by ":" and then a container name, separated by "/", which connects directly to a specific container on the specified host. This will use SSH to talk to the remote machine manager instance. Container names may be enumerated with machinectl -H HOST. Put IPv6 addresses in brackets.
-M, --machine=
Execute operation on a local container. Specify a container name to connect to, optionally prefixed by a user name to connect as and a separating "@" character. If the special string ".host" is used in place of the container name, a connection to the local system is made (which is useful to connect to a specific user's user bus: "--user --machine=lennart@.host"). If the "@" syntax is not used, the connection is made as root user. If the "@" syntax is used either the left hand side or the right hand side may be omitted (but not both) in which case the local user name and ".host" are implied.
--no-pager
Do not pipe output into a pager.
--no-legend
Do not print the legend, i.e. column headers and the footer with hints.
--no-ask-password
Do not query the user for authentication for privileged operations.
-h, --help
Print a short help text and exit.
--version
Print a short version string and exit.

GENERAL USER RECORD PROPERTIES

The following options control various properties of the user records/home directories that systemd-homed.service manages. These switches may be used in conjunction with the create and update commands for configuring various aspects of the home directory and the user account:

--real-name=NAME, -c NAME
The real name for the user. This corresponds with the GECOS field on classic UNIX NSS records.

Added in version 245.

--realm=REALM
The realm for the user. The realm associates a user with a specific organization or installation, and allows distinguishing users of the same name defined in different contexts. The realm can be any string that also qualifies as valid DNS domain name, and it is recommended to use the organization's or installation's domain name for this purpose, but this is not enforced nor required. On each system only a single user of the same name may exist, and if a user with the same name and realm is seen it is assumed to refer to the same user while a user with the same name but different realm is considered a different user. Note that this means that two users sharing the same name but with distinct realms are not allowed on the same system. Assigning a realm to a user is optional.

Added in version 245.

--alias=NAME[,NAME...]
Additional names for the user. Takes one or more valid UNIX user names, separated by commas. May be used multiple times to define multiple aliases. An alias username may be specified wherever the primary user name may be specified, and resolves to the same user record.

Added in version 258.

--email-address=EMAIL
Takes an electronic mail address to associate with the user. On log-in the $EMAIL environment variable is initialized from this value.

Added in version 245.

--location=TEXT
Takes location specification for this user. This is free-form text, which might or might not be usable by geo-location applications. Example: --location="Berlin, Germany" or --location="Basement, Room 3a"

Added in version 245.

--icon-name=ICON
Takes an icon name to associate with the user, following the scheme defined by the Icon Naming Specification[2].

Added in version 245.

--home-dir=PATH, -dPATH
Takes a path to use as home directory for the user. Note that this is the directory the user's home directory is mounted to while the user is logged in. This is not where the user's data is actually stored, see --image-path= for that. If not specified, defaults to /home/$USER.

Added in version 245.

--uid=UID
Takes a preferred numeric UNIX UID to assign this user. If a user is to be created with the specified UID and it is already taken by a different user on the local system then creation of the home directory is refused. Note though, if after creating the home directory it is used on a different system and the configured UID is taken by another user there, then systemd-homed may assign the user a different UID on that system. The specified UID must be outside of the system user range. It is recommended to use the 60001...60513 UID range for this purpose. If not specified, the UID is automatically picked. If the home directory is found to be owned by a different UID when logging in, the home directory and everything underneath it will have its ownership changed automatically before login completes.

Note that changing this option for existing home directories generally has no effect on home directories that already have been registered locally (have a local binding), as the UID used for an account on the local system is determined when the home directory is first activated on it, and then remains in effect until the home directory is removed.

Note that users managed by systemd-homed always have a matching group associated with the same name as well as a GID matching the UID of the user. Thus, configuring the GID separately is not permitted.

Added in version 245.

--member-of=GROUP, -G GROUP
Takes a comma-separated list of auxiliary UNIX groups this user shall belong to. Example: --member-of=wheel to provide the user with administrator privileges. Note that systemd-homed does not manage any groups besides a group matching the user in name and numeric UID/GID. Thus any groups listed here must be registered independently, for example with groupadd(8). Any non-existent groups are ignored. This option may be used more than once, in which case all specified group lists are combined. If the user is currently a member of a group which is not listed, the user will be removed from the group.

Added in version 245.

--capability-bounding-set=CAPABILITIES, --capability-ambient-set=CAPABILITIES
These options take a space separated list of process capabilities (e.g. CAP_WAKE_ALARM, CAP_BLOCK_SUSPEND, ...) that shall be set in the capability bounding and ambient sets for all the user's sessions. See capabilities(7) for details on the capabilities concept. These options may be used more than once, in which case the specified lists are combined. If the parameter begins with a "~" character the effect is inverted: the specified capability is dropped from the specific set.

Added in version 254.

--access-mode=MODE
Takes a UNIX file access mode written in octal. Configures the access mode of the home directory itself. Note that this is only used when the directory is first created, and the user may change this any time afterwards. Example: --access-mode=0700

Added in version 245.

--umask=MASK
Takes the access mode mask (in octal syntax) to apply to newly created files and directories of the user ("umask"). If set this controls the initial umask set for all login sessions of the user, possibly overriding the system's defaults.

Added in version 245.

--skel=PATH
Takes a file system path to a directory. Specifies the skeleton directory to initialize the home directory with. All files and directories in the specified path are copied into any newly create home directory. If not specified, defaults to /etc/skel/.

Added in version 245.

--shell=SHELL
Takes a file system path. Specifies the shell binary to execute on terminal logins. If not specified, defaults to /bin/bash.

Added in version 245.

PROPIEDADES DEL REGISTRO DE USUARIO DEL ENTORNO

--set-environment=NAME=VALUE, -E NAME=VALUE

Establece una variable de entorno para todos los procesos del usuario. Puede usarse varias veces para establecer múltiples variables de entorno. Cuando se omiten "=" y VALOR, se utilizará el valor de la variable con el mismo nombre en el entorno del programa.

Tenga en cuenta que una serie de otras configuraciones también resultan en el establecimiento de variables de entorno para el usuario, incluyendo --email=, --timezone= y --language=.

Añadido en la versión 245.

--timezone=TIMEZONE

Toma un nombre de ubicación de zona horaria que establece la zona horaria para el usuario especificado. Cuando el usuario inicia sesión, la variable de entorno $TZ se inicializa a partir de esta configuración. Ejemplo: --timezone=Europe/Amsterdam resultará en la variable de entorno "TZ=:Europe/Amsterdam". (Se usa ":" intencionalmente como parte de la especificación de la zona horaria, consulte tzset(3)).

Añadido en la versión 245.

--language=LANG

Toma una lista de idiomas preferidos por el usuario, separados por comas o dos puntos, ordenados por prioridad descendente. Las variables de entorno $LANG y $LANGUAGE se inicializan a partir de este valor al iniciar sesión, y por lo tanto, los valores adecuados para estas variables de entorno se aceptan aquí, por ejemplo --language=de_DE.UTF-8. Esta opción puede usarse más de una vez, en cuyo caso las listas de idiomas se concatenan.

Añadido en la versión 245.

--default-area=AREA

Toma una cadena que identifica un "área" de directorio principal para usarla como predeterminada. Las áreas son directorios principales secundarios dentro del directorio principal primario de un usuario. Al iniciar sesión, un usuario puede especificar el área en la que desea iniciar sesión, lo que garantiza que la variable de entorno $HOME se establezca en `~/Areas/` seguido del nombre del área.

Para obtener detalles sobre el concepto de área, consulte pam_systemd_home(8). Tenga en cuenta que esta opción solo define el valor predeterminado, que puede ser anulado al iniciar sesión.

Cuando esta opción se especifica con una cadena vacía como valor, cualquier área predeterminada declarada previamente se elimina del registro del usuario.

Añadido en la versión 258.

PROPIEDADES DEL REGISTRO DE USUARIO DE AUTENTICACIÓN

--ssh-authorized-keys=KEYS

Toma una línea de clave autorizada SSH para asociar con el registro del usuario o un carácter "@" seguido de una ruta a un archivo para leer una o más líneas de este tipo. Las claves SSH configuradas de esta manera se ponen a disposición de SSH para permitir el acceso a este directorio principal y registro de usuario. Esta opción puede usarse más de una vez para configurar múltiples claves SSH.

Añadido en la versión 245.

--pkcs11-token-uri=URI

Toma una URI PKCS#11 RFC 7512 que hace referencia a un token de seguridad (por ejemplo, YubiKey o tarjeta inteligente PIV) que podrá desbloquear la cuenta de usuario. La URI del token de seguridad debe hacer referencia a un token de seguridad con exactamente un par de certificado X.509 y clave privada. A continuación, se genera una clave secreta aleatoria, se cifra con la clave pública del certificado X.509 y se almacena como parte del registro del usuario. Al iniciar sesión, se descifra con el módulo PKCS#11 y luego se utiliza para desbloquear la cuenta y los recursos asociados. Vea a continuación un ejemplo de cómo configurar la autenticación con un token de seguridad.

En lugar de una URI PKCS#11 válida, se pueden especificar las cadenas especiales "list" y "auto". Si se pasa "list", se muestra una tabla breve de tokens de hardware PKCS#11 adecuados, actualmente conectados, junto con sus URIs. Si se pasa "auto", se selecciona automáticamente un token de hardware PKCS#11 adecuado (esta operación fallará si no se descubre exactamente un token adecuado). Este último es un atajo útil para el caso más común en el que se conecta un único token de hardware PKCS#11.

Tenga en cuenta que muchos tokens de seguridad de hardware implementan tanto PKCS#11/PIV como FIDO2 con la extensión "hmac-secret" (por ejemplo: la serie YubiKey 5), como se admite con la opción --fido2-device= a continuación. Ambos mecanismos son igualmente potentes, aunque FIDO2 es la tecnología más moderna. Los tokens PKCS#11/PIV tienen la ventaja de ser reconocibles antes de la autenticación y, por lo tanto, se pueden usar para implicar la identidad del usuario para iniciar sesión, lo que FIDO2 no permite. Los dispositivos PKCS#11/PIV generalmente requieren inicialización (es decir, almacenar un par de claves privada/pública en ellos, vea el ejemplo a continuación) antes de que puedan usarse; los tokens de seguridad FIDO2 generalmente no requieren eso y funcionan directamente.

Añadido en la versión 245.

--fido2-credential-algorithm=STRING

Especifica el algoritmo COSE utilizado en la generación de credenciales. El valor predeterminado es "es256". Los valores admitidos son "es256", "rs256" y "eddsa".

"es256" denota ECDSA sobre NIST P-256 con SHA-256. "rs256" denota RSA de 2048 bits con relleno PKCS#1.5 y SHA-256. "eddsa" denota EDDSA sobre Curve25519 con SHA-512.

Tenga en cuenta que su autenticador puede optar por no admitir algunos algoritmos.

Añadido en la versión 251.

--fido2-device=PATH

Toma una ruta a un dispositivo "hidraw" de Linux (por ejemplo, /dev/hidraw1), que hace referencia a un token de seguridad FIDO2 que implementa la extensión "hmac-secret" y que podrá desbloquear la cuenta de usuario. Se genera un valor de sal aleatorio en el host y se pasa al dispositivo FIDO2, que calcula un hash HMAC de la sal utilizando una clave secreta interna. El resultado se utiliza luego como clave para desbloquear la cuenta de usuario. La sal aleatoria se incluye en el registro del usuario, por lo que cada vez que se necesite autenticación, se puede pasar al token FIDO2 nuevamente.

En lugar de una ruta válida a un dispositivo "hidraw" FIDO2, se pueden especificar las cadenas especiales "list" y "auto". Si se pasa "list", se muestra una tabla breve de dispositivos FIDO2 adecuados detectados. Si se pasa "auto", se selecciona automáticamente un token FIDO2 adecuado si se detecta exactamente uno. Este último es un atajo útil para el caso más común en el que se conecta un único token de hardware FIDO2.

Tenga en cuenta que los dispositivos FIDO2 adecuados para esta opción deben implementar la extensión "hmac-secret". La mayoría de los dispositivos actuales (como la serie YubiKey 5) lo hacen. Si la extensión no está implementada, el dispositivo no se puede utilizar para desbloquear directorios principales.

El dispositivo FIDO2 puede eliminarse posteriormente estableciendo la ruta del dispositivo a una cadena vacía (por ejemplo, homectl update $USER --fido2-device="").

Tenga en cuenta que muchos tokens de seguridad de hardware implementan tanto FIDO2 como PKCS#11/PIV (y, por lo tanto, pueden usarse tanto con --fido2-device= como con --pkcs11-token-uri=), para una discusión, consulte anteriormente.

LUKS2 USER RECORD PROPERTIES

--luks-discard=BOOL

Configura la función de "descarte" (discard) del sistema de archivos. Si está habilitada, el sistema de archivos sobre el volumen LUKS2 informará información de bloques vacíos a LUKS2 y al archivo de loopback inferior, asegurando que el espacio vacío en el directorio de inicio se devuelva al sistema de archivos subyacente debajo del volumen LUKS2, lo que resulta en un archivo de loopback "disperso" (sparse). Esta opción generalmente está desactivada, ya que permite la sobreasignación de directorios de inicio, lo que resulta en errores de E/S si el sistema de archivos subyacente se llena mientras el sistema de archivos superior desea asignar un bloque. Dichos errores de E/S generalmente no son bien manejados por los sistemas de archivos ni por las aplicaciones. Cuando se utiliza almacenamiento LUKS2 sobre dispositivos de bloques regulares (en lugar de sobre un archivo de loopback), la lógica de descarte está activada por defecto.

--auto-resize-mode=

Configura si se debe aumentar y/o reducir automáticamente el sistema de archivos subyacente al iniciar y cerrar sesión. Toma una de las cadenas "off", "grow", "shrink-and-grow". Actualmente, solo se aplica al backend LUKS2 y si el sistema de archivos btrfs se utiliza dentro de él (ya que solo entonces se admite el crecimiento/reducción en línea del sistema de archivos). # smbpasswd -a lennart

$ homectl get-signing-key | ssh targetsystem homectl add-signing-key --key-name="<$HOSTNAME>".public
$ homectl inspect -E lennart | ssh targetsystem homectl register -
$ ssh lennart@targetsystem

Esto primero asegura que la cuenta de usuario "lennart" sea conocida y accesible por Samba. Luego agrega la clave de firma de cuenta del sistema local al sistema de destino. Luego registra la cuenta de usuario local en el sistema de destino. Finalmente, inicia sesión en la cuenta en el sistema de destino. El sistema de destino se conectará de nuevo a través de SMB/CIFS para acceder al directorio personal.

homectl(1) - Arch Linux DE

NOMBRE

homectl - gestor de directorios personales de usuario

SINOPSIS

homectl [opción...] comando [ARGUMENTO...]

homectl --help

homectl --version

DESCRIPCIÓN

homectl es una utilidad de línea de comandos para configurar y gestionar directorios personales de usuarios en sistemas que utilizan systemd(1). Permite crear, eliminar y consultar información sobre directorios personales.

COMANDOS

Los siguientes comandos están disponibles:

[create] NAME [USER]
Crea un nuevo directorio personal para el usuario especificado por NAME. Si se proporciona USER, se utiliza ese nombre de usuario para la propiedad del directorio. De lo contrario, se intenta determinar el nombre de usuario a partir del nombre del directorio. Se pueden especificar credenciales de servicio adicionales para personalizar la creación (ver CREDENTIALS).
[delete] NAME...
Elimina los directorios personales especificados por NAME. Los directorios se eliminan de forma recursiva. Puede requerir privilegios elevados.
[list]
Lista todos los directorios personales gestionados por homectl. Muestra el nombre, el usuario asociado y la ruta del directorio.
[info] NAME...
Muestra información detallada sobre los directorios personales especificados por NAME. Incluye el usuario asociado, la ruta, los permisos y otros metadatos.
[firstboot]
Ejecuta la configuración inicial de directorios personales. Normalmente se invoca durante el primer arranque del sistema.
[add-signing-key] NAME
Añade una clave pública de firma identificada por NAME a la lista de claves que controlan desde qué orígenes se permiten directorios personales para el inicio de sesión. Añadido en la versión 258.
[remove-signing-key] NAME...
Elimina la clave pública identificada por el nombre especificado de la lista de claves que controlan desde qué orígenes se permiten directorios personales para el inicio de sesión. Añadido en la versión 258.

CREDENTIALS

Cuando se invoca con el comando firstboot, homectl soporta la lógica de credenciales de servicio implementada por ImportCredential=/LoadCredential=/SetCredential= (ver systemd.exec(5) para detalles). Las siguientes credenciales se utilizan cuando se pasan:

home.create.*

Si se pasan una o más credenciales cuyos nombres comienzan con "home.create.", seguido de un nombre de usuario UNIX válido, se crea una nueva área personal, una para cada registro de usuario especificado.

Añadido en la versión 256.

LINEA DE COMANDOS DEL KERNEL

systemd.firstboot=

Este booleano deshabilitará el efecto del comando homectl firstboot. Es interpretado principalmente por systemd-firstboot(1).

Añadido en la versión 256.

ESTADO DE SALIDA

En caso de éxito, se devuelve 0, y en caso contrario, un código de error distinto de cero.

Cuando un comando se invoca con with, se propaga el estado de salida del hijo. Efectivamente, homectl saldrá sin error si el comando se invoca correctamente y finaliza correctamente.

ENTORNO

$SYSTEMD_LOG_LEVEL

El nivel de registro máximo de los mensajes emitidos (los mensajes con un nivel de registro superior, es decir, menos importantes, se suprimirán). Toma una lista separada por comas de valores. Un valor puede ser uno de los siguientes (en orden de importancia decreciente): emerg, alert, crit, err, warning, notice, info, debug, o un entero en el rango 0...7. Ver syslog(3) para más información. Cada valor puede ir opcionalmente prefijado con uno de console, syslog, kmsg o journal seguido de dos puntos para establecer el nivel de registro máximo para ese destino de registro específico (por ejemplo, SYSTEMD_LOG_LEVEL=debug,console:info especifica registrar a nivel de depuración, excepto cuando se registra en la consola, que debería estar a nivel de información). Tenga en cuenta que el nivel de registro máximo global tiene prioridad sobre cualquier nivel de registro máximo por destino.

$SYSTEMD_LOG_COLOR

Un booleano. Si es verdadero, los mensajes escritos en la tty se colorearán según la prioridad.

Esta configuración solo es útil cuando los mensajes se escriben directamente en la terminal, ya que journalctl(1) y otras herramientas que muestran los registros colorearán los mensajes según el nivel de registro por sí mismas.

$SYSTEMD_LOG_TIME

Un booleano. Si es verdadero, los mensajes de registro de la consola se prefijarán con una marca de tiempo.

Esta configuración solo es útil cuando los mensajes se escriben directamente en la terminal o en un archivo, ya que journalctl(1) y otras herramientas que muestran los registros adjuntarán marcas de tiempo basadas en los metadatos de la entrada por sí mismas.

$SYSTEMD_LOG_LOCATION

Un booleano. Si es verdadero, los mensajes se prefijarán con un nombre de archivo y número de línea en el código fuente donde se origina el mensaje.

Tenga en cuenta que la ubicación del registro a menudo se adjunta como metadatos a las entradas del journal de todos modos. Incluirlo directamente en el texto del mensaje puede ser conveniente al depurar programas.

$SYSTEMD_LOG_TID

Un booleano. Si es verdadero, los mensajes se prefijarán con el ID numérico de hilo (TID) actual.

Tenga en cuenta que esta información se adjunta como metadatos a las entradas del journal de todos modos. Incluirlo directamente en el texto del mensaje puede ser conveniente al depurar programas.

$SYSTEMD_LOG_TARGET

El destino de los mensajes de registro. Uno de console (registrar en la tty adjunta), console-prefixed (registrar en la tty adjunta pero con prefijos que codifican el nivel de registro y la "instalación", ver syslog(3), kmsg (registrar en el búfer de registro circular del kernel), journal (registrar en el journal), journal-or-kmsg (registrar en el journal si está disponible, y en kmsg en caso contrario), auto (determinar automáticamente el destino de registro apropiado, el predeterminado), null (deshabilitar la salida de registro).

$SYSTEMD_LOG_RATELIMIT_KMSG

Si limitar la tasa de kmsg o no. Toma un booleano. Predetermina a "true". Si está deshabilitado, systemd no limitará la tasa de los mensajes escritos en kmsg.

$SYSTEMD_PAGER, $PAGER

Paginador a usar cuando no se especifica --no-pager. Se usa $SYSTEMD_PAGER si está establecido; de lo contrario, se usa $PAGER. Si ninguno de $SYSTEMD_PAGER ni $PAGER están establecidos, se intentan una serie de implementaciones de paginadores conocidos en orden, incluyendo less(1) y more(1), hasta que se encuentre uno. Si no se descubre ninguna implementación de paginador, no se invoca ningún paginador. Establecer estas variables de entorno a una cadena vacía o al valor "cat" es equivalente a pasar --no-pager.

Nota: si $SYSTEMD_PAGERSECURE no está establecido, $SYSTEMD_PAGER y $PAGER solo se pueden usar para deshabilitar el paginador (con "cat" o ""), y de lo contrario se ignoran.

$SYSTEMD_LESS

Anula las opciones pasadas a less (por defecto "FRSXMK").

Los usuarios pueden querer cambiar dos opciones en particular:

K

Esta opción instruye al paginador a salir inmediatamente cuando se presiona Ctrl+C. Para permitir que less maneje Ctrl+C por sí mismo para volver al prompt de comandos del paginador, des Establecer esta opción.

Si el valor de $SYSTEMD_LESS no incluye "K", y el paginador invocado es less, Ctrl+C será ignorado por el ejecutable y deberá ser manejado por el paginador.

X

Esta opción instruye al paginador a no enviar cadenas de inicialización y desinicialización de termcap a la terminal. Se establece por defecto para permitir que la salida del comando permanezca visible en la terminal incluso después de que el paginador salga. Sin embargo, esto impide que funcione cierta funcionalidad del paginador, en particular, la salida paginada no se puede desplazar con el ratón.

Tenga en cuenta que establecer la variable de entorno regular $LESS no tiene efecto para las invocaciones de less por parte de las herramientas de systemd.

Ver less(1) para más discusión.

$SYSTEMD_LESSCHARSET

Anula el conjunto de caracteres pasado a less (por defecto "utf-8", si se determina que la terminal invocadora es compatible con UTF-8).

Tenga en cuenta que establecer la variable de entorno regular $LESSCHARSET no tiene efecto para las invocaciones de less por parte de las herramientas de systemd.

$SYSTEMD_PAGERSECURE

Los comandos de paginador comunes como less(1), además de "paginar", es decir, desplazarse por la salida, admiten abrir o escribir en otros archivos y ejecutar comandos de shell arbitrarios. Cuando los comandos se invocan con privilegios elevados, por ejemplo bajo sudo(8) o pkexec(1), el paginador se convierte en un límite de seguridad. Se debe tener cuidado de que solo se utilicen como paginadores programas con funcionalidad estrictamente limitada, y no se permitan funciones interactivas no deseadas como abrir o crear nuevos archivos o iniciar subprocesos. El "modo seguro" para el paginador puede habilitarse como se describe a continuación, si el paginador lo soporta (la mayoría de los paginadores no están escritos de manera que tomen esto en consideración). Se recomienda habilitar explícitamente el "modo seguro" o deshabilitar completamente el paginador usando --no-pager o PAGER=cat al permitir que usuarios no confiables ejecuten comandos con privilegios elevados.

Esta opción toma un argumento booleano. Cuando se establece en verdadero, se habilita el "modo seguro" del paginador. En "modo seguro", se establecerá LESSSECURE=1 al invocar el paginador, lo que instruye al paginador a deshabilitar comandos que abran o creen nuevos archivos o inicien nuevos subprocesos. Actualmente, solo se sabe que less(1) entiende esta variable e implementa el "modo seguro".

Cuando se establece en falso, no se impone ninguna limitación al paginador. Establecer SYSTEMD_PAGERSECURE=0 o no eliminarlo del entorno heredado puede permitir al usuario invocar comandos arbitrarios.

Cuando $SYSTEMD_PAGERSECURE no está establecido, las herramientas de systemd intentan determinar automáticamente si se debe habilitar el "modo seguro" y si el paginador lo soporta. El "modo seguro" se habilita si el UID efectivo no es el mismo que el propietario de la sesión de inicio de sesión, ver geteuid(2) y sd_pid_get_owner_uid(3), o cuando se ejecuta bajo sudo(8) o herramientas similares (se establece $SUDO_UID [5]). En esos casos, se establecerá SYSTEMD_PAGERSECURE=1 y no se utilizarán los paginadores que no se sabe que implementen el "modo seguro". Tenga en cuenta que esta autodetección solo cubre los mecanismos más comunes para elevar privilegios y está destinada como una conveniencia. Se recomienda establecer explícitamente $SYSTEMD_PAGERSECURE o deshabilitar el paginador.

Tenga en cuenta que si las variables $SYSTEMD_PAGER o $PAGER deben ser honradas, aparte de deshabilitar el paginador, también debe establecerse $SYSTEMD_PAGERSECURE.

$SYSTEMD_COLORS

Toma un argumento booleano. Cuando es verdadero, systemd y las utilidades relacionadas usarán colores en su salida, de lo contrario, la salida será monocromática. Adicionalmente, la variable puede tomar uno de los siguientes valores especiales: "16", "256" para restringir el uso de colores a los colores ANSI base 16 o 256, respectivamente. Esto se puede especificar para anular la decisión automática basada en $TERM y a qué está conectada la consola.

$SYSTEMD_URLIFY

El valor debe ser un booleano. Controla si se deben generar enlaces en la salida para los emuladores de terminal que soportan esto. Esto se puede especificar para anular la decisión que systemd toma basándose en $TERM y otras condiciones.

EJEMPLOS

Ejemplo 1. Crear un usuario "waldo" en el grupo de administradores "wheel", y asígnales 500 MiB de espacio en disco.

homectl create waldo --real-name="Waldo McWaldo" -G wheel --disk-size=500M

Ejemplo 2. Crear un usuario "wally" en una memoria USB y asignar un máximo de 500 tareas concurrentes.

homectl create wally --real-name="Wally McWally" --image-path=/dev/disk/by-id/usb-SanDisk_Ultra_Fit_476fff954b2b5c44-0:0 --tasks-max=500

Ejemplo 3. Cambiar el nivel de nice del usuario "odlaw" a +5 y asegurarse de que la variable de entorno $SOME se establezca en la cadena "THING" para él al iniciar sesión.

homectl update odlaw --nice=5 --setenv=SOME=THING

Ejemplo 4. Configurar la autenticación con un token de seguridad YubiKey utilizando PKCS#11/PIV:

# Limpiar la Yubikey de claves antiguas (¡cuidado!)
ykman piv reset
# Generar un nuevo par de claves pública/privada en el dispositivo, almacenar la clave pública en 'pubkey.pem'.
ykman piv generate-key -a RSA2048 9d pubkey.pem
# Crear un certificado autofirmado a partir de esta clave pública y almacenarlo en el dispositivo.
ykman piv generate-certificate --subject "Knobelei" 9d pubkey.pem
# Ya no necesitamos la clave pública en disco
rm pubkey.pem
# Permitir que el token de seguridad desbloquee la cuenta del usuario 'lafcadio'.
homectl update lafcadio --pkcs11-token-uri=auto
