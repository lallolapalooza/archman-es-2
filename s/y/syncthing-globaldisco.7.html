SYNCTHING-GLOBALDISCO(7) Syncthing SYNCTHING-GLOBALDISCO(7)

NOMBRE

syncthing-globaldisco - Protocolo de Descubrimiento Global v3

ANUNCIOS

Un dispositivo debe anunciarse al inicio. Lo hace mediante una solicitud POST HTTPS a la URL del servidor de anuncios. El descubrimiento estándar requiere actualmente que la ruta sea "/v2/", aunque esto puede depender del servidor de descubrimiento. La solicitud POST tiene una carga útil JSON que enumera las direcciones de conexión (si las hay):

{
        addresses: ["tcp://192.0.2.45:22000", "tcp://:22000", "relay://192.0.2.99:22028"],
}

Está bien que el campo "addresses" sea una lista vacía ([]), null, o que falte por completo. Sin embargo, un anuncio con el campo ausente o vacío no es útil...

Cualquier dirección IP vacía o no especificada (es decir, direcciones como tcp://:22000, tcp://0.0.0.0:22000, tcp://[::]:22000) se interpreta como que se refiere a la dirección IP de origen del anuncio.

El ID del dispositivo que anuncia no forma parte del anuncio. En cambio, el servidor requiere que el cliente realice autenticación de certificado. El ID del dispositivo se deduce del certificado presentado.

La respuesta del servidor está vacía, con el código 204 (Sin contenido) en caso de éxito. Si no se presentó ningún certificado, se devuelve el estado 403 (Prohibido). Si los datos enviados no se ajustan al formato esperado, se devuelve 400 (Solicitud incorrecta).

En las respuestas exitosas, el servidor puede devolver una cabecera Reannounce-After que contiene el número de segundos después del cual el cliente debe realizar un nuevo anuncio.

En las respuestas de error, el servidor puede devolver una cabecera Retry-After que contiene el número de segundos después del cual el cliente debe reintentar.

Realizar anuncios con mucha más frecuencia que la indicada por las cabeceras Reannounce-After o Retry-After puede provocar que el cliente sea limitado. En tales casos, el servidor puede responder con el código de estado 429 (Demasiadas solicitudes).

CONSULTAS

Las consultas se realizan como solicitudes GET HTTPS a la URL del servidor de anuncios. El ID del dispositivo solicitado se pasa como parámetro de consulta "device", en forma de cadena canónica, es decir, https://discovery.syncthing.net/?device=ABC12345-....

Las respuestas exitosas tendrán el código de estado 200 (OK) y contendrán una carga útil JSON del mismo formato que el anuncio anterior. La respuesta no contendrá direcciones vacías o no especificadas.

Si el parámetro de consulta "device" falta o está mal formado, se devuelve el código de estado 400 (Solicitud incorrecta).

Si el ID del dispositivo tiene un formato válido pero no se encuentra en el registro, se devuelve 404 (No encontrado).

Si el cliente ha superado un límite de velocidad, el servidor puede responder con 429 (Demasiadas solicitudes).

AUTENTICACIÓN

El descubrimiento global se realiza a través de HTTPS y está protegido contra atacantes de la misma manera que el tráfico HTTPS normal. Sin embargo, hay algunas consideraciones específicas de Syncthing además de esto. Como se mencionó anteriormente, para los anuncios, el cliente debe proporcionar un certificado para probar la propiedad del ID del dispositivo anunciado.

Además, Syncthing tiene un mecanismo para verificar la identidad del servidor de descubrimiento. Si bien esto normalmente se lograría utilizando un certificado firmado por una CA, Syncthing a menudo se ejecuta en entornos con paquetes de CA raíz obsoletos o simplemente inexistentes. En cambio, Syncthing puede verificar la huella digital del certificado del servidor de descubrimiento utilizando el mecanismo de ID del dispositivo. Esto es "certificate pinning" y se comunica en la configuración de Syncthing como un parámetro sintético "id" en la URL del servidor de descubrimiento: https://discovery.syncthing.net/?id=.... El parámetro "id" no se envía, de hecho, al servidor de descubrimiento; es utilizado por el propio Syncthing para saber qué certificado esperar en el lado del servidor.

La red de descubrimiento pública utiliza este mecanismo de autenticación en lugar de certificados firmados por CA.

El servidor de descubrimiento imprime su ID de certificado de esta manera al inicio.
