DESCRIPCIÓN

Un archivo de unidad es un archivo de texto plano estilo ini que codifica información sobre un servicio, un socket, un dispositivo, un punto de montaje, un punto de montaje automático, un archivo o partición swap, un objetivo de inicio, una ruta de sistema de archivos observada, un temporizador controlado y supervisado por systemd(1), un slice de gestión de recursos o un grupo de procesos creados externamente. Consulte systemd.syntax(7) para una descripción general de la sintaxis.

Esta página del manual enumera las opciones de configuración comunes de todos los tipos de unidades. Estas opciones deben configurarse en las secciones [Unit] o [Install] de los archivos de unidad.

Además de las secciones genéricas [Unit] e [Install] descritas aquí, cada unidad puede tener una sección específica del tipo, por ejemplo, [Service] para una unidad de servicio. Consulte las páginas del manual correspondientes para obtener más información: systemd.service(5), systemd.socket(5), systemd.device(5), systemd.mount(5), systemd.automount(5), systemd.swap(5), systemd.target(5), systemd.path(5), systemd.timer(5), systemd.slice(5), systemd.scope(5).

Los archivos de unidad se cargan desde un conjunto de rutas determinadas durante la compilación, descrito en la siguiente sección.

Los nombres de unidad válidos consisten en un "prefijo de nombre de unidad" y un sufijo que especifica el tipo de unidad y que comienza con un punto. El "prefijo de nombre de unidad" debe constar de uno o más caracteres válidos (letras ASCII, dígitos, ":", "-", "_", "." y "\"). La longitud total del nombre de unidad, incluido el sufijo, no debe superar los 255 caracteres. El sufijo del tipo de unidad debe ser uno de los siguientes: ".service", ".socket", ".device", ".mount", ".automount", ".swap", ".target", ".path", ".timer", ".slice" o ".scope".

Los nombres de unidad pueden ser parametrizados por un único argumento llamado "nombre de instancia". La unidad se construye entonces basándose en un "archivo de plantilla" que sirve como definición de múltiples servicios u otras unidades. Una unidad de plantilla debe tener un único símbolo "@" al final del prefijo del nombre de unidad (justo antes del sufijo de tipo). El nombre de la unidad completa se forma insertando el nombre de la instancia entre el "@" y el sufijo del tipo de unidad. En el propio archivo de unidad, el parámetro de instancia puede ser referido usando "%i" y otros especificadores, ver más abajo.

Los archivos de unidad pueden contener opciones adicionales además de las listadas aquí. Si systemd encuentra una opción desconocida, escribirá un mensaje de registro de advertencia pero continuará cargando la unidad. Si una opción o un nombre de sección está prefijado con X-, será ignorado completamente por systemd. Las opciones dentro de una sección ignorada no necesitan el prefijo. Las aplicaciones pueden usar esto para incluir información adicional en los archivos de unidad. Para acceder a esas opciones, las aplicaciones necesitan analizar los archivos de unidad por sí mismas.

Las unidades pueden ser alias (tener un nombre alternativo), creando un enlace simbólico del nuevo nombre al nombre existente en una de las rutas de búsqueda de unidades. Por ejemplo, systemd-networkd.service tiene el alias dbus-org.freedesktop.network1.service, creado durante la instalación como un enlace simbólico, por lo que cuando se le pide a systemd a través de D-Bus que cargue dbus-org.freedesktop.network1.service, cargará systemd-networkd.service. Como otro ejemplo, default.target — el objetivo del sistema por defecto que se inicia al arrancar — a menudo se aliasa a multi-user.target o graphical.target para seleccionar qué se inicia por defecto. Los nombres de alias pueden ser utilizados en comandos como disable, start, stop, status y similares, y en todas las directivas de dependencia de unidad, incluyendo Wants=, Requires=, Before=, After=. Los alias no pueden ser utilizados con el comando preset.

Los alias cumplen las siguientes restricciones: una unidad de un tipo determinado (".service", ".socket", ...) solo puede ser aliasada por un nombre con el mismo sufijo de tipo. Una unidad simple (no una plantilla o una instancia), solo puede ser aliasada por un nombre simple. Una instancia de plantilla solo puede ser aliasada por otra instancia de plantilla, y la parte de la instancia debe ser idéntica. Una plantilla puede ser aliasada por otra plantilla (en cuyo caso el alias se aplica a todas las instancias de la plantilla). Como caso especial, una instancia de plantilla (por ejemplo, "alias@inst.service") puede ser un enlace simbólico a una plantilla diferente (por ejemplo, "template@inst.service"). En ese caso, solo esa instancia específica es aliasada, mientras que otras instancias de la plantilla (por ejemplo, "alias@foo.service", "alias@bar.service") no son aliasadas. Estas reglas preservan el requisito de que la instancia (si existe) siempre se defina de forma única para una unidad dada y todos sus alias. El destino del enlace simbólico del alias debe apuntar a una ubicación válida del archivo de unidad, es decir, el nombre del archivo de enlace debe coincidir con el nombre de la fuente del enlace como se describe, y la ruta de destino debe estar en una de las rutas de búsqueda de unidades, ver la sección de RUTA DE ARCHIVO DE UNIDAD a continuación para más detalles. Tenga en cuenta que el archivo de destino podría no existir, es decir, el enlace simbólico podría ser colgante.

Los archivos de unidad pueden especificar alias a través de la directiva Alias= en la sección [Install]. Cuando la unidad se habilita, se crearán enlaces simbólicos para esos nombres, y se eliminarán cuando la unidad se deshabilite. Por ejemplo, reboot.target especifica Alias=ctrl-alt-del.target, por lo que cuando se habilita, se crea el enlace simbólico /etc/systemd/system/ctrl-alt-del.target que apunta al archivo reboot.target, y cuando se invoca Ctrl+Alt+Del, systemd buscará ctrl-alt-del.target, seguirá el enlace simbólico a reboot.target, y ejecutará reboot.service como parte de ese objetivo. systemd no mira la sección [Install] en absoluto durante la operación normal, por lo que cualquier directiva en esa sección solo tiene efecto a través de los enlaces simbólicos creados durante la habilitación.

Junto con un archivo de unidad foo.service, puede existir el directorio foo.service.wants/. Todos los archivos de unidad enlazados simbólicamente desde dicho directorio se añaden implícitamente como dependencias de tipo Wants= a la unidad. Funcionalidad similar existe para dependencias de tipo Requires=, el sufijo del directorio es .requires/ en este caso. SEMÁNTICA DE WANTS= Y REQUIRES=

Consulte abajo. La forma preferida de crear enlaces simbólicos en los directorios .wants/ o .requires/ es especificando la dependencia en la sección [Install] de la unidad objetivo y creando el enlace simbólico en el sistema de archivos con los comandos enable o preset de systemctl(1). El objetivo puede ser una unidad normal (ya sea simple o una instancia específica de una unidad plantilla). En caso de que la unidad de origen sea una plantilla, el objetivo también puede ser una plantilla, en cuyo caso la instancia se "propagará" a la unidad objetivo para formar una instancia de unidad válida. El objetivo de los enlaces simbólicos en .wants/ o .requires/ debe, por lo tanto, apuntar a una ubicación de archivo de unidad válida, es decir, el nombre del destino del enlace simbólico debe cumplir los requisitos descritos, y la ruta de destino debe estar en una de las rutas de búsqueda de unidades; consulte la sección UNIT FILE LOAD PATH más abajo para obtener más detalles. Tenga en cuenta que el archivo de destino podría no existir, es decir, el enlace simbólico podría estar colgando.

Junto con un archivo de unidad foo.service, puede existir un directorio "drop-in" foo.service.d/. Todos los archivos con el sufijo ".conf" de este directorio se fusionarán en orden alfanumérico y se analizarán después de que se haya analizado el propio archivo de unidad principal. Esto es útil para alterar o agregar configuraciones para una unidad, sin tener que modificar los archivos de unidad. Cada archivo drop-in debe contener encabezados de sección apropiados. Para unidades instanciadas, esta lógica primero buscará el subdirectorio de la instancia ".d/" (por ejemplo, "foo@bar.service.d/") y leerá sus archivos ".conf", seguido del subdirectorio de la plantilla ".d/" (por ejemplo, "foo@.service.d/") y los archivos ".conf" allí. Además, para nombres de unidades que contienen guiones ("-"), también se busca el conjunto de directorios generados al truncar repetidamente el nombre de la unidad después de todos los guiones. Específicamente, para un nombre de unidad foo-bar-baz.service no solo se busca el directorio drop-in regular foo-bar-baz.service.d/ sino también foo-bar-.service.d/ y foo-.service.d/. Esto es útil para definir drop-ins comunes para un conjunto de unidades relacionadas, cuyos nombres comienzan con un prefijo común. Este esquema es particularmente útil para unidades de montaje, automontaje y slice, cuya estructura de nomenclatura sistemática se basa en guiones como separadores de componentes. Tenga en cuenta que los archivos drop-in con el mismo nombre más abajo en la jerarquía de prefijos anulan a los de más arriba, es decir, foo-bar-.service.d/10-override.conf anula a foo-.service.d/10-override.conf.

En casos de alias de unidades (descritos anteriormente), se cargan los drop-ins para el nombre aliased y todos los alias. En el ejemplo de default.target que aliasa a graphical.target, se leerían default.target.d/, default.target.wants/, default.target.requires/, graphical.target.d/, graphical.target.wants/, graphical.target.requires/. Para las plantillas, se leen los drop-ins para la plantilla, cualquier alias de plantilla, la instancia de plantilla y todas las instancias de alias. Cuando solo se aliasa una instancia de plantilla específica, se leen los drop-ins para la plantilla de destino, la instancia de plantilla de destino y la instancia de plantilla de alias.

Además de /etc/systemd/system, los directorios drop-in ".d/" para servicios del sistema pueden ubicarse en los directorios /usr/lib/systemd/system o /run/systemd/system. Los archivos drop-in en /etc/ tienen prioridad sobre los de /run/, que a su vez tienen prioridad sobre los de /usr/lib/. Los archivos drop-in en cualquiera de estos directorios tienen prioridad sobre los archivos de unidad dondequiera que se encuentren. Múltiples archivos drop-in con nombres diferentes se aplican en orden lexicográfico, independientemente de en qué directorios residan.

Las unidades también admiten un drop-in de nivel superior con tipo.d/, donde tipo puede ser, por ejemplo, "service" o "socket", lo que permite alterar o agregar configuraciones a todos los archivos de unidad correspondientes en el sistema. El formato y la prioridad de aplicación de las configuraciones drop-in siguen lo definido anteriormente. Los archivos en tipo.d/ tienen menor prioridad en comparación con los archivos en directorios de anulación específicos del nombre. Se aplican las reglas habituales: se aplican múltiples archivos drop-in con nombres diferentes en orden lexicográfico, independientemente de en qué directorios residan, por lo que un archivo en tipo.d/ se aplica a una unidad solo si no hay drop-ins o máscaras con ese nombre en directorios con mayor prioridad. Consulte Ejemplos.

Tenga en cuenta que, si bien systemd ofrece un sistema flexible de dependencias entre unidades, se recomienda utilizar esta funcionalidad solo con moderación y confiar en técnicas como la activación basada en bus o basada en socket, que hacen que las dependencias sean implícitas, lo que resulta en un sistema tanto más simple como más flexible.

Como se mencionó anteriormente, una unidad puede ser instanciada a partir de un archivo de plantilla. Esto permite la creación de múltiples unidades a partir de un único archivo de configuración. Si systemd busca un archivo de configuración de unidad, primero buscará el nombre literal de la unidad en el sistema de archivos. Si eso no tiene éxito y el nombre de la unidad contiene un carácter "@", systemd buscará una plantilla de unidad que comparta el mismo nombre pero con la cadena de instancia (es decir, la parte entre el carácter "@" y el sufijo) eliminada. Ejemplo: si se solicita un servicio getty@tty3.service y no se encuentra ningún archivo con ese nombre, systemd buscará getty@.service e instanciará un servicio a partir de ese archivo de configuración si se encuentra.

Para referirse a la cadena de instancia desde dentro del archivo de configuración, puede usar el especificador especial "%i" en muchas de las opciones de configuración. Consulte más abajo para obtener detalles.

Si un archivo de unidad está vacío (es decir, tiene tamaño de archivo 0) o está enlazado simbólicamente a /dev/null, su configuración no se cargará y aparecerá con un estado de carga de "enmascarado", y no se podrá activar. Utilice esto como una forma efectiva de deshabilitar completamente una unidad, haciendo imposible iniciarla incluso manualmente.

El formato del archivo de unidad está cubierto por la Promesa de Portabilidad y Estabilidad de la Interfaz[1].

ESCAPADO DE CADENAS PARA INCLUSIÓN EN NOMBRES DE UNIDADES

A veces es útil convertir cadenas arbitrarias en nombres de unidades. Para facilitar esto, se utiliza un método de escapado de cadenas, con el fin de mapear cadenas que contienen valores de bytes arbitrarios (excepto NUL) a nombres de unidades válidos y su conjunto de caracteres restringido. Un caso especial común son los nombres de unidades que reflejan rutas a objetos en la jerarquía del sistema de archivos. Ejemplo: una unidad de dispositivo dev-sda.device se refiere a un dispositivo con el nodo de dispositivo /dev/sda en el sistema de archivos.

El algoritmo de escapado opera de la siguiente manera: dada una cadena, cualquier carácter "/" se reemplaza por "-", y todos los demás caracteres que no son alfanuméricos ASCII, ":", "_" o "." se reemplazan por escapes de estilo C "\x2d". Además, "." se reemplaza por un escape de estilo C cuando aparece como primer carácter en la cadena escapada.

Cuando la entrada califica como una ruta de sistema de archivos absoluta, este algoritmo se extiende ligeramente: la ruta al directorio raíz "/" se codifica como un guion simple "-". Además, los caracteres "/" iniciales, finales o duplicados se eliminan de la cadena antes de la transformación. Ejemplo: /foo//bar/baz/ se convierte en "foo-bar-baz".

Este escapado es completamente reversible, siempre y cuando se sepa si la cadena escapada era una ruta (los resultados de desempaquetado son diferentes para rutas y cadenas que no son rutas). El comando systemd-escape(1) puede usarse para aplicar y revertir el escapado en cadenas arbitrarias. Use systemd-escape --path para escapar cadenas de rutas, y systemd-escape sin --path en caso contrario.

DEPENDENCIAS AUTOMÁTICAS

Dependencias Implícitas

Se establece un número de dependencias de unidad de forma implícita, dependiendo del tipo de unidad y la configuración de la unidad. Estas dependencias implícitas pueden hacer que los archivos de configuración de unidades sean más limpios. Para las dependencias implícitas en cada tipo de unidad, consulte la sección "Dependencias Implícitas" en las páginas de manual correspondientes.

Por ejemplo, las unidades de servicio con Type=dbus adquieren automáticamente dependencias de tipo Requires= y After= sobre dbus.socket. Consulte systemd.service(5) para obtener detalles.

Dependencias Predeterminadas

Las dependencias predeterminadas son similares a las dependencias implícitas, pero se pueden activar y desactivar estableciendo DefaultDependencies= en yes (el valor predeterminado) y no, mientras que las dependencias implícitas siempre están en efecto. Consulte la sección "Default Dependencies" en las páginas de manual correspondientes para conocer el efecto de habilitar DefaultDependencies= en cada tipo de unidad.

Por ejemplo, las unidades de destino complementarán todas las dependencias configuradas de tipo Wants= o Requires= con dependencias de tipo After=. Consulte systemd.target(5) para obtener detalles. Tenga en cuenta que este comportamiento puede ser excluido estableciendo DefaultDependencies=no en las unidades especificadas, o puede ser anulado selectivamente a través de una dependencia explícita Before=.

Moreover, additional units might be loaded into systemd from directories not on the unit load path by creating a symlink pointing to a unit file in the directories. You can use systemctl link for this; see systemctl(1). The file system where the linked unit files are located must be accessible when systemd is started (e.g. anything underneath /home/ or /var/ is not allowed, unless those directories are located on the root file system).

It is important to distinguish "linked unit files" from "unit file aliases": any symlink where the symlink target is within the unit load path becomes an alias: the source name and the target file name must satisfy specific constraints listed above in the discussion of aliases, but the symlink target does not have to exist, and in fact the symlink target path is not used, except to check whether the target is within the unit load path. In contrast, a symlink which goes outside of the unit load path signifies a linked unit file. The symlink is followed when loading the file, but the destination name is otherwise unused (and may even not be a valid unit file name). For example, symlinks /etc/systemd/system/alias1.service → service1.service, /etc/systemd/system/alias2.service → /usr/lib/systemd/service1.service, /etc/systemd/system/alias3.service → /etc/systemd/system/service1.service are all valid aliases and service1.service will have four names, even if the unit file is located at /run/systemd/system/service1.service. In contrast, a symlink /etc/systemd/system/link1.service → ../link1_service_file means that link1.service is a "linked unit" and the contents of /etc/systemd/link1_service_file provide its configuration.

UNIT GARBAGE COLLECTION

The system and service manager loads a unit's configuration automatically when a unit is referenced for the first time. It will automatically unload the unit configuration and state again when the unit is not needed anymore ("garbage collection"). A unit may be referenced through a number of different mechanisms:

1.Another loaded unit references it with a dependency such as After=, Wants=, ...
2.The unit is currently starting, running, reloading or stopping.
3.The unit is currently in the failed state. (But see below.)
4.A job for the unit is pending.
5.The unit is pinned by an active IPC client program.
6.The unit is a special "perpetual" unit that is always active and loaded. Examples for perpetual units are the root mount unit -.mount or the scope unit init.scope that the service manager itself lives in.
7.The unit has running processes associated with it.

The garbage collection logic may be altered with the CollectMode= option, which allows configuration whether automatic unloading of units that are in failed state is permissible, see below.

Note that when a unit's configuration and state is unloaded, all execution results, such as exit codes, exit signals, resource consumption and other statistics are lost, except for what is stored in the log subsystem.

Use systemctl daemon-reload or an equivalent command to reload unit configuration while the unit is already loaded. In this case, all configuration settings are flushed out and replaced with the new configuration (which however might not be in effect immediately), however all runtime state is saved/restored.

[UNIT] SECTION OPTIONS

The unit file may include a [Unit] section, which carries generic information about the unit that is not dependent on the type of unit:

Description=

A brief, meaningful, human-readable text identifying the unit. This may be used by systemd (and suitable UIs) as a user-visible label for the unit, so this string should identify the unit rather than just describe it, despite the name. This string also should not just repeat the unit name. "Apache HTTP Server" or "Postfix Mail Server" are good examples. Bad examples are "high-performance lightweight HTTP server" (too generic) or "Apache" (meaningless for people who do not know the Apache HTTP server project, duplicates the unit name). systemd may use this string as a noun in status messages ("Starting Description...", "Started Description.", "Reached target Description.", "Failed to start Description."), so it should be capitalized, and should not be a full sentence, or a phrase with a verb conjugated in the present continuous, or end in a full stop. Bad examples include "exiting the container", "updating the database once per day.", or "OpenSSH server second instance daemon".

Dependency Settings

The following dependency settings may be used to define relationships between units:

Wants=

Configures a weak, informal dependency. If unit foo.service wants unit bar.service, then starting foo.service will also start bar.service. However, if bar.service fails to start, this is ignored and foo.service is still started. The inverse is not true: stopping or restarting bar.service does not affect foo.service.

This setting may be specified multiple times. If multiple units are listed, they are all wanted. If foo.service and bar.service are both wanted by baz.service, and foo.service is started, bar.service is also started. If foo.service has an ordering dependency configured with After=bar.service and both units are started simultaneously. If foo.service has no ordering specified with After= or Before=, then both units will be started simultaneously and without any delay between them if foo.service is activated.

Added in version 201.

Requires=

Similar to Wants=, but declares a stronger requirement dependency. Dependencies of this type may also be configured by adding a symlink to a .requires/ directory accompanying the unit file.

If this unit gets activated, the units listed will be activated as well. If one of the other units fails to activate, and an ordering dependency After= on the failing unit is set, this unit will not be started. Besides, with or without specifying After=, this unit will be stopped (or restarted) if one of the other units is explicitly stopped (or restarted).

Often, it is a better choice to use Wants= instead of Requires= in order to achieve a system that is more robust when dealing with failing services.

Note that this dependency type does not imply that the other unit always has to be in active state when this unit is running. Specifically: failing condition checks (such as ConditionPathExists=, ConditionPathIsSymbolicLink=, ... — see below) do not cause the start job of a unit with a Requires= dependency on it to fail. Also, some unit types may deactivate on their own (for example, a service process may decide to exit cleanly, or a device may be unplugged by the user), which is not propagated to units having a Requires= dependency. Use the BindsTo= dependency type together with After= to ensure that a unit may never be in active state without a specific other unit also in active state (see below).

Added in version 201.

Requisite=

Similar to Requires=. However, if the units listed here are not started already, they will not be started and the starting of this unit will fail immediately. Requisite= does not imply an ordering dependency, even if both units are started in the same transaction. Hence this setting should usually be combined with After=, to ensure this unit is not started before the other unit.

When Requisite=b.service is used on a.service, this dependency will show as RequisiteOf=a.service in property listing of b.service. RequisiteOf= dependency cannot be specified directly.

Added in version 201.

BindsTo=

Configures requirement dependencies, very similar in style to Requires=. However, this dependency type is stronger: in addition to the effect of Requires= it declares that if the unit bound to is stopped, this unit will be stopped too. This means a unit bound to another unit that suddenly enters inactive state will be stopped too. Units can suddenly, unexpectedly enter inactive state for different reasons: the main process of a service unit might terminate on its own choice, the backing device of a device unit might be unplugged or the mount point of a mount unit might be unmounted without involvement of the system and service manager.

When used in conjunction with After= on the same unit the behaviour of BindsTo= is even stronger. In this case, the unit bound to strictly has to be in active state for this unit to also be in active state. This not only means a unit bound to another unit that suddenly enters inactive state, but also one that is bound to another unit that gets skipped due to an unmet condition check (such as ConditionPathExists=, ConditionPathIsSymbolicLink=, ... — see below) will be stopped, should it be running. Hence, in many cases it is best to combine BindsTo= with After=.

When BindsTo=b.service is used on a.service, this dependency will show as BoundBy=a.service in property listing of b.service. BoundBy= dependency cannot be specified directly.

Added in version 201.

PartOf=

Configures dependencies similar to Requires=, but limited to stopping and restarting of units. When systemd stops or restarts the units listed here, the action is propagated to this unit. Note that this is a one-way dependency — changes to this unit do not affect the listed units.

Added in version 201.

Upholds=

Configures dependencies similar to Wants=, but as long as this unit is up, all units listed in Upholds= are started whenever found to be inactive or failed, and no job is queued for them. While a Wants= dependency on another unit has a one-time effect when this units started, a Upholds= dependency on it has a continuous effect, constantly restarting the unit if necessary. This is an alternative to the Restart= setting of service units, to ensure they are kept running whatever happens. The restart happens without delay, and usual per-unit rate-limit applies.

When Upholds=b.service is used on a.service, this dependency will show as UpheldBy=a.service in the property listing of b.service.

Conflicts=

A space-separated list of unit names. Configures negative requirement dependencies. If a unit has a Conflicts= requirement on a set of other units, then starting it will stop all of them and starting any of them will stop it.

Note that this setting does not imply an ordering dependency, similarly to the Wants= and Requires= dependencies described above. This means that to ensure that the conflicting unit is stopped before the other unit is started, an After= or Before= dependency must be declared. It does not matter which of the two ordering dependencies is used, because stop jobs are always ordered before start jobs, see the discussion in Before=/After= below.

If unit A that conflicts with unit B is scheduled to be started at the same time as B, the transaction will either fail (in case both are required parts of the transaction) or be modified to be fixed (in case one or both jobs are not a required part of the transaction). In the latter case, the job that is not required will be removed, or in case both are not required, the unit that conflicts will be started and the unit that is conflicted is stopped.

Added in version 201.

Before=, After=

These two settings expect a space-separated list of unit names. They may be specified more than once, in which case dependencies for all listed names are created.

Those two settings configure ordering dependencies between units. If unit foo.service contains the setting Before=bar.service and both units are being started, bar.service's start-up is delayed until foo.service has finished starting up. After= is the inverse of Before=, i.e. while Before= ensures that the configured unit is started before the listed unit begins starting up, After= ensures the opposite, that the listed unit is fully started up before the configured unit is started.

When two units with an ordering dependency between them are shut down, the inverse of the start-up order is applied. I.e. if a unit is configured with After= on another unit, the former is stopped before the latter if both are shut down. Given two units with any ordering dependency between them, if one unit is shut down and the other is started up, the shutdown is ordered before the start-up. It does not matter if the ordering dependency is After= or Before=, in this case. It also does not matter which of the two is shut down, as long as one is shut down and the other is started up; the shutdown is ordered before the start-up in all cases. If two units have no ordering dependencies between them, they are shut down or started up simultaneously, and no ordering takes place. It depends on the unit type when precisely a unit has finished starting up. Most importantly, for service units start-up is considered completed for the purpose of Before=/After= when all its configured start-up commands have been invoked and they either failed or reported start-up success. Note that this includes ExecStartPost= (or ExecStopPost= for the shutdown case).

Note that those settings are independent of and orthogonal to the requirement dependencies as configured by Requires=, Wants=, Requisite=, or BindsTo=. It is a common pattern to include a unit name in both the After= and Wants= options, in which case the unit listed will be started before the unit that is configured with these options.

Note that Before= dependencies on device units have no effect and are not supported. Devices generally become available as a result of an external hotplug event, and systemd creates the corresponding device unit without delay.

Los archivos de unidad pueden incluir una sección [Install], que contiene información de instalación para la unidad. Esta sección no es interpretada por systemd(1) durante la ejecución; es utilizada por los comandos enable y disable de la herramienta systemctl(1) durante la instalación de una unidad.

Alias=

Una lista separada por espacios de nombres adicionales bajo los cuales se instalará esta unidad. Los nombres listados aquí deben tener el mismo sufijo (es decir, tipo) que el nombre del archivo de la unidad. WantedBy=, RequiredBy=, UpheldBy=

Esta opción se puede usar varias veces, o se puede dar una lista separada por espacios de nombres de unidades. Se crea un enlace simbólico en el directorio .wants/, .requires/, o .upholds/ de cada una de las unidades listadas cuando esta unidad es instalada por systemctl enable. Esto tiene el efecto de que una dependencia de tipo Wants=, Requires=, o Upholds= se añade desde la unidad listada a la unidad actual. Ver la descripción de los tipos de dependencia mencionados en la sección [Unit] para más detalles.

En el caso de unidades de plantilla que listan unidades no de plantilla, la unidad que lista debe tener DefaultInstance= configurado, o systemctl enable debe ser llamado con un nombre de instancia. La instancia (por defecto o especificada) se añadirá a la lista .wants/, .requires/, o .upholds/ de la unidad listada. Por ejemplo, WantedBy=getty.target en un servicio getty@.service resultará en que systemctl enable getty@tty2.service creará un enlace getty.target.wants/getty@tty2.service a getty@.service. Esto también se aplica a listar instancias específicas de unidades con plantilla: esta instancia específica ganará la dependencia. Una unidad de plantilla también puede listar una unidad de plantilla, en cuyo caso se añadirá una dependencia genérica donde cada instancia de la unidad que lista tendrá una dependencia en una instancia de la plantilla listada con el mismo valor de instancia. Por ejemplo, WantedBy=container@.target en un servicio monitor@.service resultará en que systemctl enable monitor@.service creará un enlace container@.target.wants/monitor@.service a monitor@.service, lo que se aplica a todas las instancias de container@.target.

EXAMPLES

Example 1. Allowing units to be enabled

The following snippet (highlighted) allows a unit (e.g. foo.service) to be enabled via systemctl enable:

[Unit]
Description=Foo
[Service]
ExecStart=/usr/sbin/foo-daemon
[Install]
WantedBy=multi-user.target

After running systemctl enable, a symlink /etc/systemd/system/multi-user.target.wants/foo.service linking to the actual unit will be created. It tells systemd to pull in the unit when starting multi-user.target. The inverse systemctl disable will remove that symlink again.

Example 2. Overriding vendor settings

There are two methods of overriding vendor settings in unit files: copying the unit file from /usr/lib/systemd/system to /etc/systemd/system and modifying the chosen settings. Alternatively, one can create a directory named unit.d/ within /etc/systemd/system and place a drop-in file name.conf there that only changes the specific settings one is interested in. Note that multiple such drop-in files are read if present, processed in lexicographic order of their filename.

The advantage of the first method is that one easily overrides the complete unit, the vendor unit is not parsed at all anymore. It has the disadvantage that improvements to the unit file by the vendor are not automatically incorporated on updates.

The advantage of the second method is that one only overrides the settings one specifically wants, where updates to the unit by the vendor automatically apply. This has the disadvantage that some future updates by the vendor might be incompatible with the local changes.

This also applies for user instances of systemd, but with different locations for the unit files. See the section on unit load paths for further details.

Suppose there is a vendor-supplied unit /usr/lib/systemd/system/httpd.service with the following contents:

[Unit]
Description=Some HTTP Server
After=remote-fs.target sqldb.service
Requires=sqldb.service
AssertPathExists=/srv/webserver
[Service]
Type=notify
ExecStart=/usr/sbin/some-fancy-httpd-server
Nice=5
[Install]
WantedBy=multi-user.target

Now one wants to change some settings as an administrator: firstly, in the local setup, /srv/webserver might not exist, because the HTTP server is configured to use /srv/www instead. Secondly, the local configuration makes the HTTP server also depend on a memory cache service, memcached.service, that should be pulled in (Requires=) and also be ordered appropriately (After=). Thirdly, in order to harden the service a bit more, the administrator would like to set the PrivateTmp= setting (see systemd.exec(5) for details). And lastly, the administrator would like to reset the niceness of the service to its default value of 0.

The first possibility is to copy the unit file to /etc/systemd/system/httpd.service and change the chosen settings:

[Unit]
Description=Some HTTP Server
After=remote-fs.target sqldb.service memcached.service
Requires=sqldb.service memcached.service
AssertPathExists=/srv/www
[Service]
Type=notify
ExecStart=/usr/sbin/some-fancy-httpd-server
Nice=0
PrivateTmp=yes
[Install]
WantedBy=multi-user.target

Alternatively, the administrator could create a drop-in file /etc/systemd/system/httpd.service.d/local.conf with the following contents:

[Unit]
After=memcached.service
Requires=memcached.service
# Reset all assertions and then re-add the condition we want
AssertPathExists=
AssertPathExists=/srv/www
[Service]
Nice=0
PrivateTmp=yes

Note that for drop-in files, if one wants to remove entries from a setting that is parsed as a list (and is not a dependency), such as AssertPathExists= (or e.g. ExecStart= in service units), one needs to first clear the list before re-adding all entries except the one that is to be removed. Dependencies (After=, etc.) cannot be reset to an empty list, so dependencies can only be added in drop-ins. If you want to remove dependencies, you have to override the entire unit.

OPCIONES DE LA SECCIÓN [INSTALL]

Las unidades pueden incluir una sección [Install] que describe cómo habilitar y deshabilitar la unidad. Los siguientes parámetros son compatibles:

WantedBy=
Añade la unidad a las dependencias de la unidad especificada cuando la unidad se habilita. Por ejemplo, una unidad con WantedBy=multi-user.target será iniciada cuando el sistema entre en el nivel de ejecución multiusuario.
RequiredBy=
Similar a WantedBy=, pero la unidad especificada es requerida por la unidad habilitada. Si la unidad habilitada se detiene, la unidad especificada también se detendrá.
Also=
Especifica unidades adicionales que deben habilitarse o deshabilitarse junto con la unidad actual. Útil para habilitar un servicio y su archivo de socket, por ejemplo.
Alias=
Define alias para la unidad. Estos alias se pueden usar para activar la unidad. Útil para proporcionar compatibilidad con versiones anteriores o para ofrecer múltiples formas de activar la misma unidad.

OPCIONES DE LA SECCIÓN [UNIT]

La sección [Unit] contiene metadatos sobre la unidad y define sus relaciones con otras unidades. Los siguientes parámetros son compatibles:

Description=
Una descripción legible por humanos de la unidad. Esta cadena se mostrará en la salida de comandos como systemctl status.
Documentation=
Una o más URLs o rutas de archivos que apuntan a la documentación relacionada con la unidad. Estas se mostrarán en la salida de systemctl status.
Requires=
Define una dependencia fuerte con otras unidades. Si alguna de las unidades especificadas falla o no se inicia, la unidad actual también fallará. La unidad actual también iniciará las unidades especificadas.
Wants=
Define una dependencia débil con otras unidades. Si alguna de las unidades especificadas falla o no se inicia, la unidad actual continuará ejecutándose. La unidad actual intentará iniciar las unidades especificadas.
BindsTo=
Similar a Requires=, pero la dependencia es bidireccional. Si la unidad actual se detiene o falla, las unidades especificadas también se detendrán o fallarán.
PartOf=
Similar a BindsTo=, pero la dependencia se aplica a las acciones de inicio y detención. Si la unidad actual se inicia o se detiene, las unidades especificadas también se iniciarán o detendrán. Sin embargo, las unidades especificadas pueden iniciarse o detenerse independientemente de la unidad actual.
Requisite=
Similar a Requires=, pero la unidad actual solo se iniciará si todas las unidades especificadas ya se están ejecutando. Si alguna de las unidades especificadas no está en ejecución, la unidad actual no se iniciará.
Upholds=
Similar a Requires=, pero la dependencia es en la otra dirección. Si la unidad actual falla, la unidad especificada se detendrá. Útil para unidades que solo deben ejecutarse mientras otra unidad esté activa.
Conflicts=
Define un conflicto entre unidades. Si la unidad actual se inicia, todas las unidades especificadas se detendrán. Si alguna de las unidades especificadas se inicia, la unidad actual se detendrá.
Before=
Define una orden de inicio. La unidad actual se iniciará antes que las unidades especificadas.
After=
Define una orden de inicio. La unidad actual se iniciará después de que las unidades especificadas se hayan iniciado por completo.
OnFailure=
Define unidades que se iniciarán si la unidad actual falla. Esto es útil para la gestión de errores y el registro.
OnSuccess=
Define unidades que se iniciarán si la unidad actual se completa con éxito. Útil para encadenar unidades o realizar acciones posteriores a la finalización exitosa.
OnAbort=
Define unidades que se iniciarán si la unidad actual se detiene o aborta (por ejemplo, debido a una dependencia en conflicto o a una señal). Útil para la limpieza.
PropagatesReloadTo=
Especifica unidades que recibirán una señal de recarga cuando la unidad actual reciba una señal de recarga. Esto permite la recarga coordinada de múltiples unidades.
JoinsNamespaceOf=
Hace que la unidad se una al mismo espacio de nombres (namespace) que las unidades especificadas. Útil para unidades que necesitan compartir recursos de red o de montaje.
JoinsControlGroupOf=
Hace que la unidad se una al mismo grupo de control (cgroup) que las unidades especificadas. Útil para la gestión de recursos y la limitación.
CollectMode=
Controla cómo se recopilan los errores de las unidades dependientes. Las opciones son 'none' (predeterminado), 'failed' (solo se cuentan las unidades fallidas) y 'watch' (se cuentan todas las unidades, incluidas las activas).

RECOLECCIÓN DE BASURA DE UNIDADES

Systemd limpia automáticamente las unidades que ya no son necesarias. Esto incluye unidades que fueron iniciadas como dependencias pero ya no se necesitan, o unidades que fueron instanciadas a partir de plantillas pero que ya no se utilizan. La recolección de basura se produce cuando el sistema está inactivo o cuando se detectan unidades obsoletas. Esto ayuda a mantener el sistema limpio y eficiente. Para controlar el comportamiento de la recolección de basura, se pueden usar las siguientes opciones:

KeepIfEmpty=
Especifica si la unidad debe mantenerse incluso si no tiene unidades dependientes. Útil para unidades de marcador o unidades que se utilizan para agrupar otras unidades.
CollectMode=
Controla cómo se cuentan las unidades para la recolección de basura. Las opciones son 'none', 'failed' y 'watch'.

RUTA DE CARGA DE ARCHIVOS DE UNIDAD

Systemd busca archivos de unidad en varios directorios en un orden específico. Este orden asegura que las unidades del sistema tengan prioridad sobre las unidades del usuario y que las personalizaciones locales anulen las unidades proporcionadas por el paquete. Los directorios de búsqueda son:

  • /etc/systemd/system/ : Configuraciones y personalizaciones del administrador del sistema. Tienen la máxima prioridad.
  • /run/systemd/system/ : Unidades generadas dinámicamente o temporales.
  • /usr/lib/systemd/system/ : Unidades predeterminadas proporcionadas por los paquetes instalados. Tienen la menor prioridad.

Los archivos de configuración drop-in, que se utilizan para anular o complementar configuraciones de unidades existentes, se colocan en subdirectorios de estos directorios principales. Por ejemplo, los drop-ins para foo.service se encuentran en /etc/systemd/system/foo.service.d/.

DEPENDENCIAS AUTOMÁTICAS

Systemd puede inferir ciertas dependencias automáticamente basándose en las propiedades de las unidades. Esto reduce la necesidad de especificar explícitamente todas las dependencias en los archivos de unidad.

Servicios vinculados a sockets:
Si una unidad de servicio está vinculada a una unidad de socket a través de la opción Service= en el archivo de socket, systemd automáticamente tratará el socket como una dependencia Requires= y After= del servicio. Esto significa que el socket se iniciará antes que el servicio y el servicio fallará si el socket no está disponible.
Unidades de montaje y dispositivo:
Systemd también infiere dependencias para puntos de montaje y dispositivos. Por ejemplo, si una unidad de servicio necesita que se monte un sistema de archivos específico, puede especificarlo usando Requires= o After= en la unidad de servicio, o systemd puede inferirlo si la unidad de servicio hace referencia a un punto de montaje definido en un archivo .mount. Las unidades .device representan dispositivos de hardware y systemd las utiliza para garantizar que los dispositivos estén disponibles antes de que se inicie un servicio que los necesite.

ESCAPADO DE CADENAS PARA INCLUSIÓN EN NOMBRES DE UNIDAD

Al incluir cadenas en nombres de unidades, especialmente en nombres de instancias de plantillas, es posible que necesite escapar ciertos caracteres para evitar problemas de análisis. Systemd proporciona mecanismos para esto:

Caracteres de escape:
Los caracteres especiales como '/', ':', '@', '.' y '\' deben escaparse con una barra invertida inversa ('\') cuando se usan en nombres de instancia de plantilla. Por ejemplo, si necesita crear una instancia de plantilla con el nombre mi\nombre/de/servicio, el nombre real de la unidad sería mi\\nombre\/de\/servicio.service.
Formato de unidad de ruta:
Para unidades que representan rutas de sistema de archivos, systemd puede usar un formato especial para codificar las barras invertidas y otros caracteres especiales. Por ejemplo, una unidad que representa el directorio /home/user/docs podría nombrarse home-user-docs.mount. Consulte la documentación de systemd.unit para obtener detalles sobre la codificación de rutas.

DESCRIPCIÓN

El archivo systemd.unit define la estructura y el comportamiento de las unidades de systemd. Las unidades son los bloques de construcción básicos de systemd, que representan diversos recursos del sistema, como servicios, dispositivos, puntos de montaje, sockets, etc. Este archivo describe las diferentes secciones y directivas que se pueden utilizar para configurar estas unidades.

SINOPSIS

Los archivos de unidad de systemd utilizan un formato INI simple con las siguientes secciones principales:

  • [Unit]: Metadatos y dependencias de la unidad.
  • [Service]: Opciones específicas para unidades de servicio.
  • [Socket]: Opciones específicas para unidades de socket.
  • [Device]: Opciones específicas para unidades de dispositivo.
  • [Mount]: Opciones específicas para unidades de montaje.
  • [Automount]: Opciones específicas para unidades de automontaje.
  • [Timer]: Opciones específicas para unidades de temporizador.
  • [Path]: Opciones específicas para unidades de ruta.
  • [Target]: Opciones específicas para unidades de destino.
  • [Install]: Información de instalación para habilitar/deshabilitar la unidad.
