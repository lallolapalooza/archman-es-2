NOMBRE

systemd.journal-fields - Campos especiales del journal

DESCRIPCIÓN

Las entradas del journal (tal como las escribe systemd-journald.service(8)) se parecen a un bloque de entorno de un proceso UNIX en sintaxis, pero con valores de campo que pueden incluir datos binarios y con nombres de campo no únicos permitidos. Principalmente, los valores de los campos son cadenas de texto UTF-8 formateadas; la codificación binaria se usa solo cuando el formateo como cadenas de texto UTF-8 tiene poco sentido. Las aplicaciones pueden definir libremente nuevos campos, pero unos pocos campos tienen significados especiales, que se enumeran a continuación. Típicamente, los campos solo pueden aparecer una vez por entrada de registro, sin embargo, existen excepciones especiales: algunos campos pueden aparecer más de una vez por entrada, en cuyo caso esto se menciona explícitamente a continuación. Aunque el subsistema de registro no impone restricciones sobre los valores no únicos que acepta para los campos, se recomienda encarecidamente evitar depender de esto para los campos enumerados a continuación (excepto donde se indique lo contrario, como se menciona) para evitar incompatibilidades innecesarias con otras aplicaciones.

CAMPOS DE JOURNAL DE USUARIO

Los campos de usuario son campos que se pasan directamente desde los clientes y se almacenan en el journal.

MESSAGE=

La cadena de mensaje legible por humanos para esta entrada. Se supone que este es el texto principal que se muestra al usuario. Por lo general, no se traduce (pero podría serlo en algunos casos) y no se supone que se analice para metadatos. Para codificar varias líneas en una sola entrada de registro, sepárelas con caracteres de nueva línea (código ASCII 10), pero codifíquelos como un solo campo MESSAGE=. No agregue múltiples valores de este tipo de campo a la misma entrada (vea también arriba), ya que las aplicaciones consumidoras generalmente no esperan esto y es poco probable que muestren todos los valores en ese caso.

MESSAGE_ID=

Un identificador de mensaje de 128 bits para reconocer ciertos tipos de mensajes, si esto es deseable. Debe contener un ID de 128 bits formateado como una cadena hexadecimal en minúsculas, sin guiones ni similares. Se recomienda que sea un ID compatible con UUID, pero esto no se aplica y se formatea de manera diferente. Los desarrolladores pueden generar un nuevo ID para este propósito con systemd-id128 new.

PRIORITY=

Un valor de prioridad entre 0 ("emerg") y 7 ("debug") formateado como una cadena decimal. Este campo es compatible con el concepto de prioridad de syslog.

CODE_FILE=, CODE_LINE=, CODE_FUNC=

La ubicación del código que genera este mensaje, si se conoce. Contiene el nombre del archivo fuente, el número de línea y el nombre de la función.

ERRNO=

El número de error de Unix de bajo nivel que causa esta entrada, si lo hay. Contiene el valor numérico de errno(3) formateado como una cadena decimal.

Añadido en la versión 188.

INVOCATION_ID=, USER_INVOCATION_ID=

Un ID aleatorio y único de 128 bits que identifica cada ciclo de ejecución de la unidad. Esto es diferente de _SYSTEMD_INVOCATION_ID en que solo se utiliza para mensajes provenientes del código de systemd (por ejemplo, registros del gestor del sistema/usuario o de procesos bifurcados que realizan la configuración relacionada con systemd).

Añadido en la versión 245.

SYSLOG_FACILITY=, SYSLOG_IDENTIFIER=, SYSLOG_PID=, SYSLOG_TIMESTAMP=

Campos de compatibilidad con syslog que contienen la facilidad (formateada como cadena decimal), la cadena de identificador (es decir, "etiqueta"), el PID del cliente y la marca de tiempo según lo especificado en el datagrama original. (Tenga en cuenta que la etiqueta generalmente se deriva de la variable program_invocation_short_name de glibc, consulte program_invocation_short_name(3).)

Tenga en cuenta que el servicio de journal no valida los valores de ningún campo de journal estructurado cuyo nombre no comience con un guion bajo, y esto incluye cualquier campo relacionado con syslog como estos. Por lo tanto, se espera que las aplicaciones que proporcionan una facilidad, PID o nivel de registro lo hagan correctamente formateado, es decir, como enteros formateados como decimales.

SYSLOG_RAW=

El contenido original de la línea syslog recibida en el datagrama syslog. Este campo solo se incluye si el campo MESSAGE= fue modificado en comparación con la carga útil original o si la marca de tiempo no se pudo ubicar correctamente y no está incluida en SYSLOG_TIMESTAMP=. Se produce truncamiento del mensaje cuando el mensaje contiene espacios en blanco iniciales o finales (se eliminan los espacios en blanco iniciales y finales), o contiene un byte **NULO** incrustado (el byte **NULO** y cualquier cosa después de él no se incluye). Por lo tanto, la línea syslog original se almacena como SYSLOG_RAW= o se puede recrear basándose en la prioridad y facilidad almacenadas, la marca de tiempo, el identificador y la carga útil del mensaje en MESSAGE=.

Añadido en la versión 240.

DOCUMENTATION=

Una URL de documentación con información adicional sobre el tema del mensaje de registro. Herramientas como journalctl incluirán un hipervínculo a una URL especificada de esta manera en su salida. Debe ser una URL "http://", "https://", "file:/", "man:" o "info:".

Añadido en la versión 246.

TID=

El ID de hilo numérico (TID) del que se origina el mensaje de registro.

Añadido en la versión 247.

UNIT=, USER_UNIT=

El nombre de una unidad. Utilizado por los gestores del sistema y de usuario al registrar información sobre unidades específicas.

Cuando se usan --unit=nombre o --user-unit=nombre con journalctl(1), se generará un patrón de coincidencia que incluye "UNIT=nombre.service" o "USER_UNIT=nombre.service".

Añadido en la versión 251.

CAMPOS DE JOURNAL CONFIABLES

Los campos prefijados con un guion bajo son campos confiables, es decir, campos que se agregan implícitamente por el journal y no pueden ser alterados por el código del cliente.

_PID=, _UID=, _GID=

El número de proceso, número de usuario y número de grupo del proceso del que se origina la entrada del journal, formateados como decimales. Tenga en cuenta que las entradas obtenidas a través de "stdout" o "stderr" de procesos bifurcados contendrán credenciales válidas para un proceso padre (que inició la conexión a systemd-journald).

_COMM=, _EXE=, _CMDLINE=

El nombre, la ruta del ejecutable y la línea de comandos del proceso del que se origina la entrada del journal.

_CAP_EFFECTIVE=

Las capabilities(7) efectivas del proceso del que se origina la entrada del journal.

Añadido en la versión 206.

_AUDIT_SESSION=, _AUDIT_LOGINUID=

La sesión y el UID de inicio de sesión del proceso del que se origina la entrada del journal, tal como los mantiene el subsistema de auditoría del kernel.

_SYSTEMD_CGROUP=, _SYSTEMD_SLICE=, _SYSTEMD_UNIT=, _SYSTEMD_USER_UNIT=, _SYSTEMD_USER_SLICE=, _SYSTEMD_SESSION=, _SYSTEMD_OWNER_UID=

La ruta del grupo de control en la jerarquía de systemd, el nombre de la unidad slice de systemd, el nombre de la unidad de systemd, el nombre de la unidad en el gestor de usuario de systemd (si lo hay), el ID de sesión de systemd (si lo hay) y el UID del propietario de la unidad de usuario de systemd o la sesión de systemd (si lo hay) del proceso del que se origina la entrada del journal.

_SELINUX_CONTEXT=

El contexto de seguridad SELinux (etiqueta) del proceso del que se origina la entrada del journal.

_SOURCE_REALTIME_TIMESTAMP=

La marca de tiempo confiable más temprana del mensaje, si se conoce alguna que sea diferente de la hora de recepción del journal. La marca de tiempo es la hora de CLOCK_REALTIME en microsegundos, formateada como un decimal.

_SOURCE_BOOTTIME_TIMESTAMP=

La marca de tiempo confiable más temprana del mensaje en la hora de CLOCK_BOOTTIME, en el mismo formato que _SOURCE_REALTIME_TIMESTAMP=.

Añadido en la versión 257.

_BOOT_ID=

El ID de arranque del kernel para el arranque en el que se generó el mensaje, formateado como una cadena hexadecimal de 128 bits.

_MACHINE_ID=

El ID de la máquina del host de origen, como se describe en machine-id(5).

VEDA TAMBIÉN

systemd-journald.service(8), journalctl(1), systemd.exec(5), systemd.unit(5)

NAME

systemd.journal-fields – Metadata fields in journald

DESCRIPTION

The systemd journal is structured, timestamped event logging mechanism. It is an extensible system, and various components may log arbitrary key=value pairs, which are then stored alongside the message. This page lists the fields that are specifically recognised and understood by the journal service itself, or that are part of the common logging interface.

The fields understood by journald itself are prefixed with an underscore (_). Fields that are part of the internal journal structure, such as cursor strings, are not loggable via journal client libraries like sd_journal_send(3) and are described in the ADDRESS FIELDS section.

CORE FIELDS

These fields are automatically added to every log message and are used for basic identification and filtering of log messages.

_BOOT_ID=

The boot identifier of the system. This is a time 128-bit identifier that is created when the system boots up. It may be used to group all log messages belonging to the same boot. See machine-id(5).

_SYSTEMD_UNIT=

The name of the systemd unit that the message was logged from. This field is only available for messages logged from within a systemd unit.

_SYSTEMD_SESSION=

The login session identifier that the message was logged from. This field is only available for messages logged from within a user login session.

_SYSTEMD_OWNER_UID=

The UID of the user that owns the login session the message was logged from. This field is only available for messages logged from within a user login session.

_SYSTEMD_USER_UNIT=

The name of the user session unit that the message was logged from. This field is only available for messages logged from within a user session unit.

_COMM=

The command name of the process that logged the message. This is usually limited to 15 characters.

_EXE=

The absolute path to the executable of the process that logged the message.

_CMDLINE=

The full command line of the process that logged the message.

_CAP_EFFECTIVE=

The effective capabilities of the process that logged the message. See capabilities(7).

_PID=

The process ID of the process that logged the message.

_UID=

The user ID of the process that logged the message.

_GID=

The group ID of the process that logged the message.

_CREDS_UID=

The effective user ID of the process when the message was logged. This may be different from _UID= if the process uses privilege dropping.

_CREDS_GID=

The effective group ID of the process when the message was logged. This may be different from _GID= if the process uses privilege dropping.

_CREDS_Eeffective=

The effective capabilities of the process when the message was logged. This may be different from _CAP_EFFECTIVE= if the process uses privilege dropping.

_SYSTEMD_CGROUP=

The control group path of the process that logged the message.

_SOURCE_REALTIME_TIMESTAMP=

The wallclock time (CLOCK_REALTIME) at the point in time the message was originally generated by the logging process, in microseconds since the epoch UTC, formatted as a decimal. This is the most accurate timestamp related to the message generation time, but is only available if the logging process explicitly provides it.

_AUDIT_TID=

The audit thread ID.

_AUDIT_SESSION=

The audit session ID.

_AUDIT_LOGINUID=

The login UID associated with the audit session.

_MACHINE_ID=

The machine identifier of the host the message originated from. See machine-id(5).

_SYSTEMD_INVOCATION_ID=

The invocation ID for the runtime cycle of the unit the message was generated in, as available to processes of the unit in $INVOCATION_ID (see systemd.exec(5)).

Added in version 233.

_HOSTNAME=

The hostname of the originating host.

_TRANSPORT=

How the entry was received by the journal service. Valid transports are:

audit

for those read from the kernel audit subsystem

Added in version 227.

driver

for internally generated messages

Added in version 205.

syslog

for those received via the local syslog socket with the syslog protocol

Added in version 205.

journal

for those received via the native journal protocol

Added in version 205.

stdout

for those read from a service's standard output or error output

Added in version 205.

kernel

for those read from the kernel

Added in version 205.

_STREAM_ID=

Only applies to "_TRANSPORT=stdout" records: specifies a randomized 128-bit ID assigned to the stream connection when it was first created. This ID is useful to reconstruct individual log streams from the log records: all log records carrying the same stream ID originate from the same stream.

Added in version 235.

_LINE_BREAK=

Only applies to "_TRANSPORT=stdout" records: indicates that the log message in the standard output/error stream was not terminated with a normal newline character ("\n", i.e. ASCII 10). Specifically, when set this field is one of nul (in case the line was terminated by a NUL byte), line-max (in case the maximum log line length was reached, as configured with LineMax= in journald.conf(5)), eof (if this was the last log record of a stream and the stream ended without a final newline character), or pid-change (if the process which generated the log output changed in the middle of a line). Note that this record is not generated when a normal newline character was used for marking the log line end.

Added in version 235.

_NAMESPACE=

If this file was written by a systemd-journald instance managing a journal namespace that is not the default, this field contains the namespace identifier. See systemd-journald.service(8) for details about journal namespaces.

Added in version 245.

_RUNTIME_SCOPE=

A string field that specifies the runtime scope in which the message was logged. If "initrd", the log message was processed while the system was running inside the initrd. If "system", the log message was generated after the system switched execution to the host root filesystem.

Added in version 252.

KERNEL JOURNAL FIELDS

Kernel fields are fields that are used by messages originating in the kernel and stored in the journal.

_KERNEL_DEVICE=

The kernel device name. If the entry is associated to a block device, contains the major and minor numbers of the device node, separated by ":" and prefixed by "b". Similarly for character devices, but prefixed by "c". For network devices, this is the interface index prefixed by "n". For all other devices, this is the subsystem name prefixed by "+", followed by ":", followed by the kernel device name.

Added in version 189.

_KERNEL_SUBSYSTEM=

The kernel subsystem name.

Added in version 189.

_UDEV_SYSNAME=

The kernel device name as it shows up in the device tree below /sys/.

Added in version 189.

_UDEV_DEVNODE=

The device node path of this device in /dev/.

Added in version 189.

_UDEV_DEVLINK=

Additional symlink names pointing to the device node in /dev/. This field is frequently set more than once per entry.

Added in version 189.

FIELDS TO LOG ON BEHALF OF A DIFFERENT PROGRAM

Fields in this section are used by programs to specify that they are logging on behalf of another program or unit.

Fields used by the systemd-coredump coredump kernel helper:

COREDUMP_UNIT=, COREDUMP_USER_UNIT=

Used to annotate messages containing coredumps from system and session units. See coredumpctl(1).

Added in version 198.

Privileged programs (currently UID 0) may attach OBJECT_PID= to a message. This will instruct systemd-journald to attach additional fields on behalf of the caller:

OBJECT_PID=PID

PID of the program that this message pertains to.

Added in version 205.

OBJECT_UID=, OBJECT_GID=, OBJECT_COMM=, OBJECT_EXE=, OBJECT_CMDLINE=, OBJECT_AUDIT_SESSION=, OBJECT_AUDIT_LOGINUID=, OBJECT_SYSTEMD_CGROUP=, OBJECT_SYSTEMD_SESSION=, OBJECT_SYSTEMD_OWNER_UID=, OBJECT_SYSTEMD_UNIT=, OBJECT_SYSTEMD_USER_UNIT=

These are additional fields added automatically by systemd-journald. Their meaning is the same as _UID=, _GID=, _COMM=, _EXE=, _CMDLINE=, _AUDIT_SESSION=, _AUDIT_LOGINUID=, _SYSTEMD_CGROUP=, _SYSTEMD_SESSION=, _SYSTEMD_UNIT=, _SYSTEMD_USER_UNIT=, and _SYSTEMD_OWNER_UID= as described above, except that the process identified by PID is described, instead of the process which logged the message.

Added in version 205.

OBJECT_SYSTEMD_INVOCATION_ID=

An additional field added automatically by systemd-journald. The meaning is mostly the same as _SYSTEMD_INVOCATION_ID=, with the difference described above.

Added in version 235.

ADDRESS FIELDS

During serialization into external formats, such as the Journal Export Format[1] or the Journal JSON Format[2], the addresses of journal entries are serialized into fields prefixed with double underscores. Note that these are not proper fields when stored in the journal but for addressing metadata of entries. They cannot be written as part of structured log entries via calls such as sd_journal_send(3). They may also not be used as matches for sd_journal_add_match(3).

__CURSOR=

The cursor for the entry. A cursor is an opaque text string that uniquely describes the position of an entry in the journal and is portable across machines, platforms and journal files.

__REALTIME_TIMESTAMP=

The wallclock time (CLOCK_REALTIME) at the point in time the entry was received by the journal, in microseconds since the epoch UTC, formatted as a decimal. This has different properties from "_SOURCE_REALTIME_TIMESTAMP=", as it is usually a bit later but more likely to be monotonic.

__MONOTONIC_TIMESTAMP=

The monotonic time (CLOCK_MONOTONIC) at the point in time the entry was received by the journal in microseconds, formatted as a decimal. To be useful as an address for the entry, this should be combined with the boot ID in "_BOOT_ID=".

__SEQNUM=, __SEQNUM_ID=

The sequence number (and associated sequence number ID) of this journal entry in the journal file it originates from. See sd_journal_get_seqnum(3) for details.

Added in version 254.
