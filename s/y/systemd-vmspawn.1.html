NOMBRE

systemd-vmspawn - Iniciar un SO en una máquina virtual

SINOPSIS

systemd-vmspawn [OPCIONES...] [ARGUMENTOS...]

DESCRIPCIÓN

systemd-vmspawn puede usarse para iniciar una máquina virtual a partir de una imagen de SO. En muchos aspectos es similar a systemd-nspawn(1), pero lanza una máquina virtual completa en lugar de usar espacios de nombres.

Los descriptores de archivo para /dev/kvm y /dev/vhost-vsock se pueden pasar a systemd-vmspawn a través de la interfaz nativa de paso de sockets de systemd (ver sd_listen_fds(3) para más detalles sobre el protocolo exacto utilizado y el orden en que se pasan los descriptores de archivo), estos descriptores de archivo deben pasarse con los nombres "kvm" y "vhost-vsock" respectivamente.

Nota: en derivados de Ubuntu/Debian, systemd-vmspawn requiere que el usuario esté en el grupo "kvm" para usar las opciones de VSOCK.

OPCIONES

Los argumentos restantes se pasan como argumentos adicionales de la línea de comandos del kernel usando SMBIOS.

Se entienden las siguientes opciones:

-q, --quieto

Desactiva cualquier salida de estado de la propia herramienta. Cuando se utiliza este interruptor, la única salida de vmspawn será la salida de la consola del propio SO de la Máquina Virtual.

Añadido en la versión 256.

Opciones de Imagen

-D, --directorio=

Directorio a utilizar como raíz del sistema de archivos para la máquina virtual.

Se debe especificar una de las opciones --directorio= o --imagen=. Si no se especifica ninguna, se asume --directorio=..

Nota: Si montas un directorio que no es propiedad del root, puede que necesites --usuarios-privados= para mapear en el espacio de nombres de subuid del usuario. Más adelante se proporciona un ejemplo de cómo usar /etc/subuid para esto.

Añadido en la versión 256.

-i, --imagen=

Imagen de disco de la raíz del sistema de archivos (o nodo de dispositivo) para la máquina virtual.

Añadido en la versión 255.

Configuración del Host

--cpus=CPUS

El número de CPUs con los que iniciar la máquina virtual. Predeterminado a 1.

Añadido en la versión 255.

--ram=BYTES

La cantidad de memoria con la que iniciar la máquina virtual. Predeterminado a 2G.

Añadido en la versión 255.

--kvm=BOOL

Si no se especifica --kvm=, el soporte KVM se detectará automáticamente. Si es verdadero, KVM siempre se usa, y si es falso, KVM nunca se usa.

Añadido en la versión 255.

--vsock=BOOL

Si no se especifica --vsock=, el soporte de red VSOCK se detectará automáticamente. Si es verdadero, la red VSOCK siempre se usa, y si es falso, la red VSOCK nunca se usa.

Añadido en la versión 255.

--vsock-cid=CID

Establece el CID específico a usar para el invitado. Los CIDs válidos están en el rango de 3 a 4294967294 (0xFFFF_FFFE). Los CIDs fuera de este rango están reservados. Por defecto, vmspawn intentará derivar un CID para el invitado a partir del nombre de la máquina, recurriendo a un CID aleatorio si este CID está ocupado.

Añadido en la versión 255.

--tpm=BOOL

Si no se especifica --tpm=, vmspawn detectará la presencia de swtpm(8) y lo usará si está disponible. Si se especifica sí, swtpm(8) siempre se usa, y si se establece no, swtpm(8) nunca se usa.

Añadido en la versión 256.

--tpm-estado=RUTA|auto|off

Configura dónde colocar el estado del TPM, en caso de que el soporte de TPM esté habilitado (ver --tpm= arriba). Esto toma una ruta de archivo absoluta a un directorio para colocar de forma persistente el estado. Si el directorio falta, se crea según sea necesario. Si se establece en la cadena especial "auto", se deriva automáticamente una ruta persistente de la ruta de la imagen de la VM o la ruta del directorio, con el sufijo ".tpmstate" añadido. Si se establece en la cadena especial "off", el estado del TPM solo se mantiene de forma transitoria y se descarta cuando la VM se apaga. Este modo no es adecuado para VMs que bloquean las claves de cifrado de disco al TPM, ya que estas claves se perderán en cada reinicio. Predeterminado a "auto".

Añadido en la versión 258.

--linux=RUTA

Establece la imagen del kernel de Linux a usar para el arranque directo del kernel. Si se usa una imagen de tipo directorio y se omitió --linux=, vmspawn buscará entradas del cargador de arranque de acuerdo con la Especificación del Cargador de Arranque[1] asumiendo que XBOOTLDR se encuentra en /boot y ESP en /efi respectivamente. Si no se instaló ningún kernel en la imagen, la imagen fallará al arrancar.

Añadido en la versión 256.

--initrd=RUTA

Establece el initrd a usar para el arranque directo del kernel. Si la entrada proporcionada con --linux= es una entrada de tipo #2 de la Especificación del Cargador de Arranque[1], entonces este argumento no es necesario. Si no se instaló ningún initrd en la imagen, la imagen fallará al arrancar.

--initrd= se puede especificar varias veces y vmspawn las fusionará.

Añadido en la versión 256.

-n, --tap-red

Crea un dispositivo TAP para conectarse en red con la máquina virtual.

Nota: se requieren privilegios de root para usar la red TAP. Adicionalmente, systemd-networkd(8) debe estar en ejecución y correctamente configurado en el host para aprovisionar la interfaz del host. El archivo ".network" relevante se encuentra en /usr/lib/systemd/network/80-vm-vt.network.

Añadido en la versión 255.

--network-user-mode

Usa la red en modo de usuario.

Añadido en la versión 255.

--firmware=RUTA

Toma una ruta absoluta, o una ruta relativa que comience con ./. Especifica un archivo de definición de firmware JSON, que permite seleccionar el firmware para arrancar en la VM. Si no se especifica, se descubre automáticamente un firmware adecuado. Si se especifica la cadena especial "list", se listan todos los firmwares descubiertos.

Añadido en la versión 256.

--discard-disk=BOOL

Controla si qemu procesa las solicitudes de descarte de la VM. Esto evita que las VMs de larga ejecución utilicen más espacio en disco del necesario. Esto está habilitado por defecto.

Añadido en la versión 256.

--secure-boot=BOOL

Configura si se busca firmware que soporte Secure Boot.

Si la opción no se especifica, se usará el primer firmware detectado. Si la opción se establece en sí, se seleccionará el primer firmware con soporte Secure Boot. Si se especifica no, se seleccionará el primer firmware sin Secure Boot.

Añadido en la versión 255.

--grow-image=BYTES, -G BYTES

Aumenta el tamaño del archivo de imagen especificado por --imagen= al tamaño especificado en bytes si es menor. No realiza ninguna operación si no se utiliza ningún archivo de imagen o si el archivo de imagen ya es tan grande o más grande de lo solicitado. El tamaño especificado acepta los sufijos habituales K, M, G (con base 1024). Los valores especificados se redondean al múltiplo de 4096.

Añadido en la versión 258.

--smbios11=CADENA, -s CADENA

Pasa la cadena especificada a la VM como una cadena de proveedor SMBIOS Tipo #11. Esto es útil para parametrizar la VM invocada de varias maneras. Ver smbios-type-11(7) para más detalles.

Añadido en la versión 258.

--notify-ready=

Configura el soporte para notificaciones del proceso init de la VM a systemd-vmspawn. Si es verdadero, systemd-vmspawn considerará la máquina lista solo cuando haya recibido un mensaje "READY=1" del proceso init en la VM. Opciones de Identidad del Sistema

-M, --machine=

Establece el nombre de la máquina para esta máquina virtual. Este nombre puede usarse para identificar esta máquina virtual durante su ejecución (por ejemplo en herramientas como machinectl(1) y similares).

Añadido en la versión 255.

--uuid=

Establece el UUID especificado para la máquina virtual. El sistema init inicializará /etc/machine-id a partir de este si este archivo aún no está establecido. Tenga en cuenta que esta opción solo tendrá efecto si /etc/machine-id en la máquina virtual no está poblado.

Añadido en la versión 256.

Opciones de Propiedades

-S, --slice=

Hace que la VM forme parte del slice especificado, en lugar del valor predeterminado machine.slice. Esto solo se aplica si la máquina se ejecuta en su propia unidad de scope, es decir, si no se utiliza --keep-unit.

Añadido en la versión 258.

--property=

Establece una propiedad de unidad en la unidad de scope para registrarse para la máquina. Esto solo se aplica si la máquina se ejecuta en su propia unidad de scope, es decir, si no se utiliza --keep-unit. Acepta asignaciones de propiedades de unidad en el mismo formato que systemctl set-property. Esto es útil para establecer límites de memoria y similares para la VM.

Añadido en la versión 258.

--register=

Controla si la máquina virtual se registra en systemd-machined(8). Acepta un argumento booleano, que por defecto es "yes" cuando se ejecuta como root, y "no" cuando se ejecuta como un usuario normal. Esto asegura que la máquina virtual sea accesible a través de machinectl(1).

Nota: se requieren privilegios de root para usar esta opción, ya que el registro en systemd-machined(8) requiere llamadas a métodos D-Bus privilegiados.

Añadido en la versión 256.

Opciones de Namespacing de Usuarios

--private-users=UID_SHIFT[:UID_RANGE]

Controla el namespacing de usuarios bajo --directory=. Si está habilitado, se le indica a virtiofsd(1) que mapee los IDs de usuario y grupo (UIDs y GIDs). Esto implica mapear los UIDs/GIDs privados utilizados en la máquina virtual (comenzando con el usuario root 0 de la máquina virtual y superiores) a un rango de UIDs/GIDs en el host que no se utilicen para otros fines (generalmente en el rango más allá de 65536 del UID/GID del host).

Si se especifican uno o dos números separados por dos puntos, el namespacing de usuarios se activa. UID_SHIFT especifica el primer UID/GID del host al que se mapeará, UID_RANGE es opcional y especifica el número de UIDs/GIDs del host que se asignarán a la máquina virtual. Si se omite UID_RANGE, se asignarán 65536 UIDs/GIDs.

Cuando se utilizan namespaces de usuarios, el rango de GIDs asignado a cada máquina virtual se elige siempre idéntico al rango de UIDs.

Añadido en la versión 256.

Opciones de Montaje

--bind=PATH, --bind-ro=PATH

Monta un directorio del host dentro de la máquina virtual. Acepta una de las siguientes opciones: un argumento de ruta —en cuyo caso la ruta especificada se montará desde el host a la misma ruta en la máquina virtual, o un par de rutas separadas por dos puntos —en cuyo caso la primera ruta especificada es la fuente en el host y la segunda ruta es el destino en la máquina virtual. Si la ruta de origen no es absoluta, se resuelve en relación con el directorio de trabajo actual. La opción --bind-ro= crea montajes bind de solo lectura. Se interpretan los escapes de barra invertida, por lo que "\:" puede usarse para incrustar dos puntos en cualquiera de las rutas. Esta opción puede especificarse varias veces para crear múltiples puntos de montaje bind independientes.

Añadido en la versión 256.

--extra-drive=PATH

Toma una imagen de disco o dispositivo de bloque en el host y la proporciona a la máquina virtual como otra unidad.

Añadido en la versión 256.

Opciones de Integración

--forward-journal=FILE|DIR

Reenvía el journal de la máquina virtual al host. Actualmente se utiliza systemd-journal-remote(8) para recibir las entradas del journal reenviadas de la VM invitada. Esta opción determina dónde se guarda este journal en el host y tiene la misma semántica que -o/--output descrita en systemd-journal-remote(8).

Añadido en la versión 256.

--pass-ssh-key=BOOL

Por defecto, se genera una clave SSH para permitir que systemd-vmspawn abra una conexión D-Bus al bus del sistema de la VM. Establecer esto en "no" deshabilitará la generación de claves SSH.

Las claves generadas son efímeras. Es decir, solo son válidas para la invocación actual de systemd-vmspawn, y generalmente no se persisten.

Añadido en la versión 256.

--ssh-key-type=TYPE

Configura el tipo de clave SSH a generar, consulte ssh-keygen(1) para más información.

Por defecto, se generan claves "ed25519", sin embargo, las claves "rsa" también pueden ser útiles si la VM tiene una versión particularmente antigua de sshd(8).

Añadido en la versión 256.

Opciones de Entrada/Salida

--console=MODE

Configura cómo configurar la consola de la VM. Acepta uno de los siguientes valores: "interactive", "read-only", "native", "gui". El valor predeterminado es "interactive". "interactive" proporciona una interfaz de terminal interactiva a la VM. "read-only" es similar, pero es estrictamente de solo lectura, es decir, no acepta ninguna entrada del usuario. "native" también proporciona una interfaz basada en TTY, pero utiliza la implementación nativa de qemu (lo que significa que el monitor de qemu está disponible). "gui" muestra la interfaz gráfica de qemu.

Añadido en la versión 256.

--background=COLOR

Cambia el color de fondo de la terminal al color ANSI especificado mientras la VM se esté ejecutando. El color especificado debe ser un color de fondo SGR de ANSI X3.64, es decir, cadenas como "40", "41", ..., "47", "48;2;...", "48;5;...". Consulte ANSI Escape Code (Wikipedia)[2] para obtener detalles. Asigne una cadena vacía para deshabilitar cualquier color. Esto solo tiene efecto en los modos --console=interactive y --console=read-only.

Añadido en la versión 256.

Credenciales

--load-credential=ID:PATH, --set-credential=ID:VALUE

Pasa una credencial a la máquina virtual. Estas dos opciones corresponden a la configuración LoadCredential= y SetCredential= en los archivos de unidad. Consulte systemd.exec(5) para obtener detalles sobre estos conceptos, así como la sintaxis de los argumentos de la opción.

Para incrustar datos binarios en los datos de credenciales para --set-credential=, use escapes de estilo C (es decir, "\n" para incrustar un salto de línea, o "\x00" para incrustar un byte NUL). Tenga en cuenta que la shell invocadora puede aplicar un deshacer escapes una vez, ¡por lo que esto podría requerir un doble escape!

Añadido en la versión 255.

Ambiente

$SYSTEMD_LOG_LEVEL

El nivel de registro máximo de los mensajes emitidos (los mensajes con un nivel de registro más alto, es decir, menos importantes, se suprimirán). Acepta una lista de valores separados por comas. Un valor puede ser uno de (en orden de importancia decreciente) emerg, alert, crit, err, warning, notice, info, debug, o un entero en el rango 0...7. Consulte syslog(3) para obtener más información. Cada valor puede opcionalmente prefijarse con uno de console, syslog, kmsg o journal seguido de dos puntos para establecer el nivel de registro máximo para ese objetivo de registro específico (por ejemplo, SYSTEMD_LOG_LEVEL=debug,console:info especifica registrar a nivel de depuración excepto cuando se registra en la consola, que debería estar a nivel de información). Tenga en cuenta que el nivel de registro máximo global tiene prioridad sobre cualquier nivel de registro máximo por objetivo.

$SYSTEMD_LOG_COLOR

Un booleano. Si es verdadero, los mensajes escritos en el tty se colorearán según la prioridad.

Esta configuración solo es útil cuando los mensajes se escriben directamente en la terminal, ya que journalctl(1) y otras herramientas que muestran los registros colorearán los mensajes según el nivel de registro por sí mismas.

$SYSTEMD_LOG_TIME

Un booleano. Si es verdadero, los mensajes de registro de la consola se prefijarán con una marca de tiempo.

Esta configuración solo es útil cuando los mensajes se escriben directamente en la terminal o en un archivo, ya que journalctl(1) y otras herramientas que muestran los registros adjuntarán marcas de tiempo según los metadatos de la entrada por sí mismas.

$SYSTEMD_LOG_LOCATION

Un booleano. Si es verdadero, los mensajes se prefijarán con un nombre de archivo y número de línea
en el código fuente donde se origina el mensaje.

Tenga en cuenta que la ubicación del registro a menudo se adjunta como metadatos a las entradas del diario de todos modos. Incluirlo directamente en el texto del mensaje puede ser conveniente para depurar programas.

$SYSTEMD_LOG_TID

Un valor booleano. Si es verdadero, los mensajes se antepondrán con el ID numérico del hilo (TID) actual.

Tenga en cuenta que esta información se adjunta como metadatos a las entradas del diario de todos modos. Incluirla directamente en el texto del mensaje puede ser conveniente para depurar programas.

$SYSTEMD_LOG_TARGET

El destino de los mensajes de registro. Uno de console (registrar en la tty adjunta), console-prefixed (registrar en la tty adjunta pero con prefijos que codifican el nivel de registro y la "instalación", ver syslog(3), kmsg (registrar en el búfer de registro circular del kernel), journal (registrar en el diario), journal-or-kmsg (registrar en el diario si está disponible, y en kmsg de lo contrario), auto (determinar el destino de registro apropiado automáticamente, el predeterminado), null (deshabilitar la salida de registro).

$SYSTEMD_LOG_RATELIMIT_KMSG

Si se debe limitar la velocidad de kmsg o no. Toma un valor booleano. Por defecto es "true". Si está deshabilitado, systemd no limitará la velocidad de los mensajes escritos en kmsg.

$SYSTEMD_PAGER, $PAGER

Paginador a utilizar cuando no se proporcione --no-pager. Se utiliza $SYSTEMD_PAGER si está establecido; de lo contrario, se utiliza $PAGER. Si no se establecen ni $SYSTEMD_PAGER ni $PAGER, se prueban una serie de implementaciones de paginadores conocidos en orden, incluyendo less(1) y more(1), hasta que se encuentra uno. Si no se descubre ninguna implementación de paginador, no se invoca ningún paginador. Establecer estas variables de entorno en una cadena vacía o en el valor "cat" es equivalente a pasar --no-pager.

Nota: si $SYSTEMD_PAGERSECURE no está establecido, $SYSTEMD_PAGER y $PAGER solo se pueden usar para deshabilitar el paginador (con "cat" o ""), y de lo contrario se ignoran.

$SYSTEMD_LESS

Anula las opciones pasadas a less (por defecto "FRSXMK").

Los usuarios pueden querer cambiar dos opciones en particular:

K

Esta opción instruye al paginador a salir inmediatamente cuando se presiona Ctrl+C. Para permitir que less maneje Ctrl+C por sí mismo para volver al indicador de comandos del paginador, desactive esta opción.

Si el valor de $SYSTEMD_LESS no incluye "K", y el paginador que se invoca es less, Ctrl+C será ignorado por el ejecutable y deberá ser manejado por el paginador.

X

Esta opción instruye al paginador a no enviar cadenas de inicialización y desinicialización de termcap a la terminal. Está establecida por defecto para permitir que la salida del comando permanezca visible en la terminal incluso después de que el paginador salga. Sin embargo, esto impide que funcione cierta funcionalidad del paginador, en particular la salida paginada no se puede desplazar con el ratón.

Tenga en cuenta que establecer la variable de entorno regular $LESS no tiene efecto para las invocaciones de less por parte de las herramientas de systemd.

Ver less(1) para más discusión.

$SYSTEMD_LESSCHARSET

Anula el conjunto de caracteres pasado a less (por defecto "utf-8", si se determina que la terminal invocadora es compatible con UTF-8).

Tenga en cuenta que establecer la variable de entorno regular $LESSCHARSET no tiene efecto para las invocaciones de less por parte de las herramientas de systemd.

$SYSTEMD_PAGERSECURE

Los comandos de paginador comunes como less(1), además de "paginar", es decir, desplazarse por la salida, admiten la apertura o escritura de otros archivos y la ejecución de comandos de shell arbitrarios. Cuando los comandos se invocan con privilegios elevados, por ejemplo, bajo sudo(8) o pkexec(1), el paginador se convierte en un límite de seguridad. Se debe tener cuidado de que solo se utilicen programas con funcionalidad estrictamente limitada como paginadores, y no se permitan características interactivas no deseadas como la apertura o creación de nuevos archivos o el inicio de subprocesos. El "modo seguro" para el paginador puede habilitarse como se describe a continuación, si el paginador lo admite (la mayoría de los paginadores no están escritos de manera que tengan esto en cuenta). Se recomienda habilitar explícitamente el "modo seguro" o deshabilitar completamente el paginador usando --no-pager o PAGER=cat al permitir que usuarios no confiables ejecuten comandos con privilegios elevados.

Esta opción toma un argumento booleano. Cuando se establece en verdadero, se habilita el "modo seguro" del paginador. En "modo seguro", se establecerá LESSSECURE=1 al invocar el paginador, lo que instruye al paginador a deshabilitar los comandos que abren o crean nuevos archivos o inician nuevos subprocesos. Actualmente, solo se sabe que less(1) entiende esta variable e implementa el "modo seguro".

Cuando se establece en falso, no se impone ninguna limitación al paginador. Establecer SYSTEMD_PAGERSECURE=0 o no eliminarlo del entorno heredado puede permitir al usuario invocar comandos arbitrarios.

Cuando $SYSTEMD_PAGERSECURE no está establecido, las herramientas de systemd intentan determinar automáticamente si se debe habilitar el "modo seguro" y si el paginador lo admite. El "modo seguro" se habilita si el UID efectivo no es el mismo que el propietario de la sesión de inicio de sesión, ver geteuid(2) y sd_pid_get_owner_uid(3), o cuando se ejecuta bajo sudo(8) o herramientas similares (se establece $SUDO_UID [3]). En esos casos, se establecerá SYSTEMD_PAGERSECURE=1 y los paginadores que no se sabe que implementen el "modo seguro" no se utilizarán en absoluto. Tenga en cuenta que esta autodetección solo cubre los mecanismos más comunes para elevar privilegios y está destinada a ser una conveniencia. Se recomienda establecer explícitamente $SYSTEMD_PAGERSECURE o deshabilitar el paginador.

Tenga en cuenta que si las variables $SYSTEMD_PAGER o $PAGER deben respetarse, aparte de deshabilitar el paginador, también debe establecerse $SYSTEMD_PAGERSECURE.

$SYSTEMD_COLORS

Toma un argumento booleano. Cuando es verdadero, systemd y las utilidades relacionadas utilizarán colores en su salida, de lo contrario, la salida será monocromática. Además, la variable puede tomar uno de los siguientes valores especiales: "16", "256" para restringir el uso de colores a los 16 o 256 colores ANSI base, respectivamente. Esto se puede especificar para anular la decisión automática basada en $TERM y a qué está conectada la consola.

$SYSTEMD_URLIFY

El valor debe ser booleano. Controla si se generarán enlaces clickables en la salida para los emuladores de terminal que admitan esto. Esto se puede especificar para anular la decisión que systemd toma basándose en $TERM y otras condiciones.

EJEMPLOS

Ejemplo 1. Ejecutar una imagen VM de Arch Linux generada por mkosi

$ mkosi -d arch -p systemd -p linux --autologin -o image.raw -f build
$ systemd-vmspawn --image=image.raw

Ejemplo 2. Importar y ejecutar una imagen en la nube de Fedora 42 usando machinectl

$ curl -L \
       -O https://download.fedoraproject.org/pub/fedora/linux/releases/42/Cloud/x86_64/images/Fedora-Cloud-Base-42-1.1.x86_64.raw.xz \
       -O https://download.fedoraproject.org/pub/fedora/linux/releases/42/Cloud/x86_64/images/Fedora-Cloud-42-1.1-x86_64-CHECKSUM \
       -O https://fedoraproject.org/fedora.gpg

Ejemplo 3. Construir y ejecutar la imagen del sistema de systemd y reenviar el diario de la VM a un archivo local

$ mkosi build
$ systemd-vmspawn \
    -D mkosi.output/system \
    --private-users $(grep $(whoami) /etc/subuid | cut -d: -f2) \
    --linux mkosi.output/system.efi \
    --forward-journal=vm.journal \
    enforcing=0

Nota: este ejemplo también utiliza un argumento de línea de comandos del kernel para asegurar que SELinux no se inicie en modo de imposición.

Ejemplo 4. SSH a una VM en ejecución usando systemd-ssh-proxy

$ mkosi build
$ my_vsock_cid=3735928559
$ systemd-vmspawn \

    enforcing=0
$ ssh root@vsock/$my_vsock_cid -i /run/user/$UID/systemd/vmspawn/machine-*-system-ed25519

NAME

systemd-vmspawn - Spawn execution environments (like VMs or containers)

SYNOPSIS

systemd-vmspawn [OPTIONS...] [IMAGE] [ARGUMENT...]

systemd-vmspawn [OPTIONS...] --destroy [CONTAINER]

systemd-vmspawn [OPTIONS...] --kill [CONTAINER]

systemd-vmspawn [OPTIONS...] --signal SIGNAL [CONTAINER]

systemd-vmspawn [OPTIONS...] --stop [CONTAINER]

systemd-vmspawn [OPTIONS...] --interface [CONTAINER]

systemd-vmspawn [OPTIONS...] --machineinfo [CONTAINER]

systemd-vmspawn [OPTIONS...] --shell [CONTAINER]

systemd-vmspawn [OPTIONS...] --transition-started-service

systemd-vmspawn [OPTIONS...] --transition-stopped-service

systemd-vmspawn --help

systemd-vmspawn --version

DESCRIPTION

systemd-vmspawn is a versatile tool for spawning and managing execution environments. These environments can range from simple chroots to full virtual machines, or containers (like systemd-nspawn containers or similar lightweight virtualization technologies). It integrates seamlessly with systemd's service management and machine tracking capabilities.

The primary use case is to start a new execution environment, execute a command within it, and then either keep it running as a service or shut it down after the command completes. It excels at managing environments for specific applications or services, providing isolation and resource control.

When spawning a new environment, systemd-vmspawn can use various backends, including systemd-nspawn, QEMU, KVM, or even simple chroots. The specific backend used can be influenced by the image type and system configuration.

It leverages systemd's "machine" concept, registering the spawned environment as a systemd machine. This allows for unified management, logging, and resource control through systemd tools like systemctl and machinectl.

OPTIONS

-M MACHINE, --machine=MACHINE
Specifies the name of the machine to operate on. This is especially relevant when managing existing machines (destroy, kill, signal, stop, interface, machineinfo, shell). If omitted when spawning, a name is generated automatically.
-D DIR, --directory=DIR
Specifies the directory that contains the root filesystem of the execution environment. This is used when the image is a directory tree.
-U UUID, --uuid=UUID
Specifies the UUID for the machine. If not provided, a random UUID is generated.
-u IMAGE_UUID, --image-uuid=IMAGE_UUID
Specifies the UUID of the image used to create the environment.
-b, --boot
Boots the specified execution environment. This is often implied when spawning a new environment.
-S SERVICE, --service=SERVICE
Runs the environment as a systemd service unit. The service name is derived from the machine name.
-P PID_FILE, --pid-file=PID_FILE
Specifies a file to write the main process ID of the spawned environment to.
-p LISTEN_PORT, --listen-port=LISTEN_PORT
Specifies a TCP port on the host to listen on for connections to the environment's serial console.
-i INTERFACE, --interface=INTERFACE
Configures the network interface for the spawned environment. Can be specified multiple times.
-n NAMESERVER, --nameserver=NAMESERVER
Configures a DNS nameserver for the spawned environment.
--setenv=VARIABLE=VALUE
Sets an environment variable within the spawned environment.
--bind=HOST_PATH:CONTAINER_PATH[:MODE]
Binds a host path to a path inside the container. MODE can be read-only (ro) or read-write (rw).
--image-feature=FEATURE
Enables specific features for the image, such as kernel modules or system services.
--deprecated-options...
Options marked as deprecated. Refer to the man page for specifics.
--destroy
Destroys the specified machine (stops and removes it).
--kill
Kills the main process of the specified machine.
--signal=SIGNAL
Sends a signal to the main process of the specified machine.
--stop
Stops the specified machine gracefully.
--interface
Prints the network interface configuration for the specified machine.
--machineinfo
Prints machine information for the specified machine.
--shell
Opens a shell inside the specified machine.
--transition-started-service
Internal option for systemd service management transitions.
--transition-stopped-service
Internal option for systemd service management transitions.
--help
Prints a help message and exits.
--version
Prints version information and exits.

ENVIRONMENT

The behavior of systemd-vmspawn can be influenced by the following environment variables:

SYSTEMD_LOG_LEVEL
Controls the verbosity of logging.
SYSTEMD_LOG_TARGET
Determines where logs are sent (e.g., "journal").
IMAGE_PATH
Can be used to specify a default search path for images.

EXAMPLES

Start a new container named 'my-container' based on a directory image and run a command:

$ systemd-vmspawn -D /path/to/rootfs -M my-container -- /usr/bin/my-app --config /etc/my-app.conf

Start a container that runs as a systemd service:

$ systemd-vmspawn -D /var/lib/containers/my-service/rootfs -S my-service.service

Destroy an existing container:

$ systemd-vmspawn -M my-container --destroy

Open a shell inside a running container:

$ systemd-vmspawn -M my-container --shell

Connect to the serial console of a VM:

$ systemd-vmspawn -M my-vm --listen-port=5000

EXIT STATUS

systemd-vmspawn exits with a status code of 0 on success, and a non-zero value on failure. The specific exit code may indicate the type of failure (e.g., invalid arguments, failure to start the environment, failure to execute the command).

SEE ALSO

systemd-nspawn(1), machinectl(1), systemctl(1), systemd.unit(5)

NOTES

systemd-vmspawn acts as a higher-level abstraction over various container and VM technologies. For detailed information about the underlying mechanisms, consult the documentation for systemd-nspawn, QEMU, KVM, and other relevant virtualization tools.

The management of spawned environments as systemd services is a powerful feature. Ensure that the service units are correctly configured for desired behavior regarding startup, shutdown, and dependencies.

Security considerations are paramount when running isolated environments. Always use trusted images and configure network access and resource limits appropriately.
