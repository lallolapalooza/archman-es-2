NOMBRE

syncthing-device-ids - Entendiendo los IDs de dispositivo

Cada dispositivo está identificado por un ID de dispositivo. El ID de dispositivo se utiliza para la resolución de direcciones, autenticación y autorización. El término “ID de dispositivo” podría haber sido intercambiablemente “ID de clave” ya que el ID de dispositivo es una propiedad directa de la clave pública en uso.

CLAVES

Para entender los IDs de dispositivo, necesitamos mirar los mecanismos subyacentes. Al inicio, Syncthing creará un par de claves pública/privada.

Actualmente, esta es una clave ECDSA de 384 bits (RSA de 3072 bits antes de la v0.12.5, que es lo que se usa como ejemplo en este artículo). Las claves se guardan en forma de clave privada (key.pem) y un certificado autofirmado (cert.pem). La parte de autofirma en realidad no añade ninguna seguridad ni funcionalidad en lo que respecta a Syncthing, pero permite el uso de las claves en un intercambio TLS estándar.

El certificado típico se verá algo así, inspeccionado con openssl x509:

Un usuario avanzado podría reemplazar los archivos key.pem y cert.pem con un par de claves generado directamente por la utilidad openssl u otro mecanismo.

IDS DE DISPOSITIVO

Para formar un ID de dispositivo, se calcula el hash SHA-256 de los datos del certificado en formato DER. Esto significa que el hash cubre toda la información bajo la sección Certificado: anterior.

El hash resulta en un hash de 256 bits que codificamos usando base32. Base32 codifica cinco bits por carácter, por lo que necesitamos 256 / 5 = 51.2 caracteres para codificar el ID de dispositivo. Esto se convierte en 52 caracteres en la práctica, pero 52 caracteres de base32 decodificarían a 260 bits, lo cual no es un número entero de bytes. La codificación base32 añade relleno hasta 280 bits (el siguiente múltiplo de 5 y 8 bits), por lo que el ID resultante se ve algo así:

MFZWI3DBONSGYYLTMRWGC43ENRQXGZDMMFZWI3DBONSGYYLTMRWA====

Se elimina el relleno (====), el ID de dispositivo se divide en cuatro grupos y se añaden dígitos de verificación https://forum.syncthing.net/t/v0-9-0-new-node-id-format/478 para cada grupo. Para fines de presentación, el ID de dispositivo se agrupa con guiones, lo que resulta en el valor final:

MFZWI3D-BONSGYC-YLTMRWG-C43ENR5-QXGZDMM-FZWI3DP-BONSGYY-LTMRWAD

Establecimiento de la conexión

Ahora que sabemos qué son los IDs de dispositivo, aquí se explica cómo se utilizan en Syncthing. Cuando añade un ID de dispositivo a la configuración, Syncthing intentará conectarse a ese dispositivo. Lo primero que necesitamos hacer es averiguar la IP y el puerto a los que conectarse. Hay tres posibilidades aquí:

  • La IP y el puerto se pueden establecer de forma estática en la configuración. La IP puede ser igualmente un nombre de host, por lo que si tiene una IP estática o una configuración de DNS dinámico, esta podría ser una buena opción.
  • Usando descubrimiento local, si está habilitado. Cada instancia de Syncthing en una LAN transmite periódicamente información sobre sí misma (ID de dispositivo, dirección, número de puerto). Si hemos visto una de estas transmisiones para un ID de dispositivo determinado, ahí es donde intentamos conectarnos.
  • Usando descubrimiento global, si está habilitado. Cada instancia de Syncthing se anuncia al servicio de descubrimiento global (ID de dispositivo y número de puerto externo: la dirección interna no se anuncia al servidor global). Si no tenemos una dirección estática y no hemos visto ningún anuncio local, se consultará al servidor de descubrimiento global para obtener una dirección.

Una vez que tenemos una dirección y un puerto, se establece una conexión TCP y se realiza un apretón de manos TLS. Como parte del apretón de manos, ambos dispositivos presentan sus certificados. Una vez que el apretón de manos ha finalizado y se conoce el certificado del par, se realizan los siguientes pasos:

1.
Calcular el ID del dispositivo remoto procesando el certificado recibido como se describió anteriormente.
2.
Descartar algunas posibles configuraciones erróneas, es decir, si el ID del dispositivo es el del dispositivo local o el de un dispositivo al que ya tenemos una conexión activa. En estos casos, se cierra la conexión.
3.
Verificar el ID del dispositivo remoto contra la configuración. Si no es un ID de dispositivo con el que esperamos hablar, se cierra la conexión.
4.
Verificar el CommonName del certificado contra la configuración. Por defecto, esperamos que sea syncthing, pero cuando se usan certificados personalizados, esto se puede cambiar.
5.
Si todo está en orden hasta ahora, se acepta la conexión.

UNA NOTA SOBRE LAS COLISIONES

El hash SHA-256 es criptográficamente resistente a colisiones. Esto significa que no hay ninguna forma conocida de crear dos mensajes diferentes con el mismo hash.

Se puede argumentar que, por supuesto, existen colisiones: hay una cantidad infinita de entradas y una cantidad finita de salidas, por lo que por definición existen infinitos mensajes que resultan en el mismo hash.

Voy a citar a stack overflow https://stackoverflow.com/questions/4014090/is-it-safe-to-ignore-the-possibility-of-sha-collisions-in-practice aquí:

La respuesta habitual es la siguiente: ¿cuál es la probabilidad de que un asteroide rogue choque contra la Tierra en el próximo segundo, aniquilando la civilización tal como la conocemos y matando a unos pocos miles de millones de personas? Se puede argumentar que cualquier evento desafortunado con una probabilidad menor que esa no es realmente muy importante.

Si tenemos una función hash “perfecta” con tamaño de salida n, y tenemos p mensajes para hashear (la longitud del mensaje individual no es importante), entonces la probabilidad de colisión es de aproximadamente p²/2n+1 (esta es una aproximación válida para p “pequeño”, es decir, sustancialmente menor que 2n/2). Por ejemplo, con SHA-256 (n=256) y mil millones de mensajes (p=109), la probabilidad es de aproximadamente 4.3\*10-60.

Una roca espacial masacradora ocurre aproximadamente una vez cada 30 millones de años en promedio. Esto lleva a una probabilidad de que tal evento ocurra en el próximo segundo de aproximadamente 10-15. Eso es 45 órdenes de magnitud más probable que la colisión SHA-256. En pocas palabras, si las colisiones SHA-256 le asustan, sus prioridades están equivocadas.

También vale la pena señalar que la propiedad de SHA-256 que estamos utilizando no es simplemente resistencia a colisiones, sino resistencia a un ataque de preimagen, es decir, incluso si puedes encontrar dos mensajes que resulten en una colisión de hash, eso no te ayuda a atacar Syncthing (o TLS en general). Necesitas crear un mensaje que se hashee exactamente al hash que mi certificado ya tiene, o no podrás entrar.

syncthing-device-ids - Device IDs in Syncthing

CLAVES

Each Syncthing node has a public cryptographic key, which serves as its device ID. This key is an ED25519 public key, encoded as a SHA256 hash of the certificate that contains it. The certificate is DER-encoded and signed by the CA. The certificate contains the public key. The device ID is the SHA256 hash of the DER-encoded certificate. This gives us the following properties:

  • The device ID is a public key.
  • The device ID is verifiable. If you are given a device ID, you can check if a given certificate corresponds to it.
  • The device ID is immutable. If the certificate changes, the device ID changes.

The device ID is used to identify remote nodes. When you connect to a remote node, you supply its device ID. When a remote node connects to you, it supplies its device ID. We use these to verify that we are connecting to the correct node.

The device ID is a SHA256 hash. It is a 32-byte value. We represent it as a 5x8 block of Base32 encoding, totaling 40 characters. The Base32 encoding uses the alphabet consisting of A-Z and 2-7. This encoding is case-insensitive and error-correcting.

The device ID is used in several places:

  • In the connection string when connecting to a remote server.
  • In the list of devices in the web UI.
  • In the configuration file, in the devices section.

IDS DE DISPOSITIVO

The device ID is a SHA256 hash of the DER-encoded certificate. This certificate is signed by a Certificate Authority (CA). In the future, we might want to use certificates that are signed by a CA that we control. This would allow us to issue certificates to our users and verify them.

However, for now, we are using self-signed certificates. This means that each device generates its own certificate and signs it with its own private key. This is not ideal, as it means that we cannot verify the authenticity of the certificate. We are relying on the user to verify the device ID out of band.

The device ID is a 32-byte SHA256 hash. We encode this hash as a 40-character string using Base32 encoding. The Base32 encoding uses the alphabet A-Z and 2-7. This encoding is case-insensitive and error-correcting.

The device ID is used to identify remote devices. When you connect to a remote device, you need to provide its device ID. When a remote device connects to you, it provides its device ID. We use these to verify that we are connecting to the correct device.

UNA OPINION SOBRE COLISIONES

The device ID is a SHA256 hash of the certificate. SHA256 is a cryptographic hash function that produces a 256-bit (32-byte) hash value. Finding a collision for SHA256 (i.e., finding two different inputs that produce the same hash) is computationally infeasible with current technology.

However, let’s imagine a scenario where we want to trick a user into connecting to our malicious server. We would need to create a fake certificate that has the same SHA256 hash as the legitimate server’s certificate. This is known as a collision attack.

The difficulty of finding a SHA256 collision is extremely high. It is estimated that it would require more computational power than is currently available in the world to find a SHA256 collision. Even if a collision were found, it would be specific to the particular inputs used in the collision discovery. This means that the attacker would need to find a collision that is specific to the legitimate server’s certificate.

To make matters even more difficult, the certificate must be valid and signed by a trusted CA. This adds another layer of complexity to the attack. The attacker would need to create a valid DER-encoded, signed certificate that has the same hash as the legitimate server’s certificate. The difficulty of this is staggeringly far beyond the already staggering difficulty of finding a SHA256 collision.

PROBLEMAS Y VULNERABILIDADES

As far as I know, these are the issues or potential issues with the above mechanism.

Suplantacion de Descubrimiento

Currently, the local discovery mechanism isn’t protected by crypto. This means that any device can in theory announce itself for any device ID and potentially receive connections for that device from the local network.

Los IDS de Dispositivo largos son molestos

It’s a mouthful to read over the phone, annoying to type into an SMS or even into a computer. And it needs to be done twice, once for each side.

This isn’t a vulnerability as such, but a user experience problem. There are various possible solutions:

  • Use shorter device IDs with verification based on the full ID (“You entered MFZWI3; I found and connected to a device with the ID MFZWI3-DBONSG-YYLTMR-WGC43E-NRQXGZ-DMMFZW-I3DBON-SGYYLT-MRWA, please confirm that this is correct”).
  • Use shorter device IDs with an out of band authentication, a la Bluetooth pairing. You enter a one time PIN into Syncthing and give that PIN plus a short device ID to another user. On initial connect, both sides verify that the other knows the correct PIN before accepting the connection.
