NOMBRE

systemd.exec - Configuración del entorno de ejecución

SINOPSIS

service.service, socket.socket, mount.mount, swap.swap

DESCRIPCIÓN

Los archivos de configuración de unidades para servicios, sockets, puntos de montaje y dispositivos swap comparten un subconjunto de opciones de configuración que definen el entorno de ejecución de los procesos generados.

Esta página del manual enumera las opciones de configuración compartidas por estos cuatro tipos de unidades. Consulte systemd.unit(5) para las opciones comunes de todos los archivos de configuración de unidades, y systemd.service(5), systemd.socket(5), systemd.swap(5) y systemd.mount(5) para más información sobre los archivos de configuración de unidades específicos. Las opciones de configuración específicas de ejecución se configuran en las secciones [Service], [Socket], [Mount] o [Swap], dependiendo del tipo de unidad.

Además, las opciones que controlan los recursos a través de los Grupos de Control de Linux (cgroups) se enumeran en systemd.resource-control(5). Estas opciones complementan las opciones enumeradas aquí.

DEPENDENCIAS IMPLÍCITAS

Algunos parámetros de ejecución dan lugar a dependencias adicionales y automáticas:

•Las unidades con WorkingDirectory=, RootDirectory=, RootImage=, RuntimeDirectory=, StateDirectory=, CacheDirectory=, LogsDirectory= o ConfigurationDirectory= establecidas automáticamente obtienen dependencias de tipo Requires= y After= en todas las unidades de montaje necesarias para acceder a las rutas especificadas. Esto es equivalente a tenerlas listadas explícitamente en RequiresMountsFor=.
•Las unidades con PrivateTmp=yes obtienen automáticamente dependencias de tipo Wants= y After= en todos los montajes necesarios para acceder a /tmp/ y /var/tmp/. También obtendrán una dependencia After= automática en systemd-tmpfiles-setup.service(8).
•Las unidades con PrivateTmp=disconnected obtienen automáticamente dependencias de tipo Wants= y After= en el montaje necesario para acceder a /var/, a menos que se especifiquen DefaultDependencies=no y/o RootDirectory=/RootImage=.
•Las unidades cuya salida estándar o de error esté conectada a journal o kmsg (o sus combinaciones con salida de consola, ver más abajo) adquirirán automáticamente dependencias de tipo After= en systemd-journald.socket.
•Las unidades que utilizan LogNamespace= obtendrán automáticamente dependencias de ordenación y requisitos en las dos unidades de socket asociadas con instancias de systemd-journald@.service.

RUTAS

Los siguientes ajustes pueden usarse para cambiar la vista de un servicio del sistema de archivos. Tenga en cuenta que las rutas deben ser absolutas y no deben contener un componente de ruta "..".

ExecSearchPath=

Toma una lista de rutas absolutas separadas por dos puntos en relación con la cual se puede encontrar el ejecutable utilizado por las propiedades Exec*= (por ejemplo, ExecStart=, ExecStop=, etc.). ExecSearchPath= anula $PATH si $PATH no es proporcionado por el usuario a través de Environment=, EnvironmentFile= o PassEnvironment=. Asignar una cadena vacía elimina asignaciones previas y establecer ExecSearchPath= a un valor varias veces se añadirá a la configuración anterior.

Añadido en la versión 250.

WorkingDirectory=

Toma una ruta de directorio relativa al directorio raíz del servicio especificado por RootDirectory=, o el valor especial "~". Establece el directorio de trabajo para los procesos ejecutados. Si se establece a "~", se utiliza el directorio personal del usuario especificado en User=. Si no se establece, por defecto es el directorio raíz cuando systemd se ejecuta como una instancia del sistema y el directorio personal del usuario respectivo si se ejecuta como usuario. Si el ajuste se antepone con el carácter "-", un directorio de trabajo faltante no se considera fatal. Si RootDirectory=/RootImage= no está establecido, entonces WorkingDirectory= es relativo a la raíz del sistema que ejecuta el gestor de servicios. Tenga en cuenta que el establecimiento de este parámetro puede dar lugar a dependencias adicionales que se añadirán a la unidad (ver arriba).

RootDirectory=

Toma una ruta de directorio relativa al directorio raíz del host (es decir, la raíz del sistema que ejecuta el gestor de servicios). Establece el directorio raíz para los procesos ejecutados, con la llamada al sistema pivot_root(2) o chroot(2). Si se utiliza, se debe asegurar que el binario del proceso y todos sus archivos auxiliares estén disponibles en la nueva raíz. Tenga en cuenta que el establecimiento de este parámetro puede dar lugar a dependencias adicionales que se añadirán a la unidad (ver arriba).

Las opciones MountAPIVFS= y PrivateUsers= son particularmente útiles en combinación con RootDirectory=. Para más detalles, véase abajo.

Si RootDirectory=/RootImage= se usan juntos con NotifyAccess=, el socket de notificación se montará automáticamente desde el host dentro del entorno raíz, para asegurar que la interfaz de notificación pueda funcionar correctamente.

Tenga en cuenta que los servicios que utilizan RootDirectory=/RootImage= no podrán registrarse a través de los protocolos syslog o journal en la infraestructura de registro del host, a menos que los sockets relevantes se monten desde el host, específicamente:

El archivo os-release(5) del host estará disponible para el servicio (solo lectura) como /run/host/os-release. Se actualizará automáticamente en el reinicio suave (ver: systemd-soft-reboot.service(8)), en caso de que el servicio esté configurado para sobrevivir a él.

Ejemplo 1. Montaje de sockets de registro en el entorno raíz

BindReadOnlyPaths=/dev/log /run/systemd/journal/socket /run/systemd/journal/stdout

En lugar de la ruta del directorio, se puede especificar un directorio versionado ".v/", ver systemd.v(7) para más detalles.

Esta opción solo está disponible para servicios del sistema, o para servicios que se ejecutan en instancias por usuario del gestor de servicios, en cuyo caso PrivateUsers= se habilita implícitamente (requiere soporte de espacios de nombres de usuario no privilegiados habilitado en el kernel a través del sysctl "kernel.unprivileged_userns_clone=").

RootImage=

Toma una ruta a un nodo de dispositivo de bloque o a un archivo regular como argumento. Esta llamada es similar a RootDirectory=, sin embargo, monta una jerarquía de sistema de archivos desde un nodo de dispositivo de bloque o un archivo de loopback en lugar de un directorio. El nodo del dispositivo o el archivo de imagen del sistema de archivos necesita contener un sistema de archivos sin tabla de particiones, o un sistema de archivos dentro de una tabla de particiones MBR/MS-DOS o GPT con solo una única partición compatible con Linux, o un conjunto de sistemas de archivos dentro de una tabla de particiones GPT que siga la Especificación de Particiones Descubribles[1].

Cuando DevicePolicy= se establece en "closed" o "strict", o se establece en "auto" y se establece DeviceAllow=, esta configuración añade /dev/loop-control con modo rw, "block-loop" y "block-blkext" con modo rwm a DeviceAllow=. Consulte systemd.resource-control(5) para obtener detalles sobre DevicePolicy= o DeviceAllow=. Además, consulte PrivateDevices= a continuación, ya que puede cambiar el ajuste de DevicePolicy=.

Las unidades que hacen uso de RootImage= obtienen automáticamente una dependencia After= de systemd-udevd.service.

El archivo os-release(5) del host estará disponible para el servicio (solo lectura) como /run/host/os-release. Se actualizará automáticamente en el reinicio suave (ver: systemd-soft-reboot.service(8)), en caso de que el servicio esté configurado para sobrevivir a él.

En lugar de la ruta de la imagen, se puede especificar un directorio versionado ".v/", ver systemd.v(7) para más detalles.

Esta opción solo está disponible para servicios del sistema y no es compatible con servicios que se ejecutan en instancias por usuario del gestor de servicios.

Añadido en la versión 233.

OpcionesDeImagenRaíz=

Toma una lista de opciones de montaje separadas por comas que se utilizarán en las imágenes de disco especificadas por RootImage=. Opcionalmente, se puede prefijar un nombre de partición, seguido de dos puntos, en caso de que la imagen tenga varias particiones; de lo contrario, se implica el nombre de partición "root". Las opciones para varias particiones se pueden especificar en una sola línea con separadores de espacio. Asignar una cadena vacía elimina las asignaciones previas. Las opciones duplicadas se ignoran. Para obtener una lista de opciones de montaje válidas, consulte mount(8).

Los nombres de partición válidos siguen la Especificación de particiones descubribles[1]: root, usr, home, srv, esp, xbootldr, tmp, var.

Esta opción solo está disponible para servicios del sistema y no se admite para servicios que se ejecutan en instancias de administrador de servicios por usuario.

Añadido en la versión 247.

RootEphemeral=

Toma un argumento booleano. Si está habilitado, los procesos ejecutados se ejecutarán en una copia efímera del directorio raíz o imagen raíz. La copia efímera se coloca en /var/lib/systemd/ephemeral-trees/ mientras el servicio está activo y se limpia cuando el servicio se detiene o reinicia. Si se utiliza RootDirectory= y el directorio raíz es un subvolumen, la copia efímera se creará realizando una instantánea del subvolumen.

Para asegurarse de que la creación de copias efímeras se pueda realizar de manera eficiente, el directorio raíz o la imagen raíz deben ubicarse en el mismo sistema de archivos que /var/lib/systemd/ephemeral-trees/. Al usar RootEphemeral= con directorios raíz, se debe usar btrfs(5) como sistema de archivos y el directorio raíz debe ser idealmente un subvolumen que systemd pueda instantáneamente para crear la copia efímera. Para imágenes raíz, se debe utilizar un sistema de archivos con soporte para reflink para garantizar una copia efímera eficiente.

Esta opción solo está disponible para servicios del sistema y no se admite para servicios que se ejecutan en instancias de administrador de servicios por usuario.

Añadido en la versión 254.

RootHash=

Toma un hash raíz de integridad de datos (dm-verity) especificado en hexadecimal, o la ruta a un archivo que contiene un hash raíz en formato hexadecimal ASCII. Esta opción habilita las comprobaciones de integridad de datos mediante dm-verity, si la imagen utilizada contiene los datos de integridad apropiados (ver arriba) o si se utiliza RootVerity=. El hash especificado debe coincidir con el hash raíz de los datos de integridad, y generalmente tiene al menos 256 bits (y, por lo tanto, 64 caracteres hexadecimales formateados) de longitud (en el caso de SHA256, por ejemplo). Si esta opción no se especifica, pero el archivo de imagen tiene el atributo de archivo extendido "user.verity.roothash" (ver xattr(7)), entonces el hash raíz se lee de él, también como caracteres hexadecimales formateados. Si no se encuentra el atributo de archivo extendido (o no es compatible con el sistema de archivos subyacente), pero se encuentra un archivo con el sufijo .roothash junto al archivo de imagen, con el mismo nombre (excepto si la imagen tiene el sufijo .raw, en cuyo caso el archivo de hash raíz no debe tenerlo en su nombre), el hash raíz se lee de él y se utiliza automáticamente, también como caracteres hexadecimales formateados.

Si la imagen de disco contiene una partición /usr/ separada, también puede estar protegida por Verity, en cuyo caso el hash raíz puede configurarse a través de un atributo de archivo extendido "user.verity.usrhash" o un archivo .usrhash adyacente a la imagen de disco. Actualmente no hay una opción para configurar el hash raíz para el sistema de archivos /usr/ directamente desde el archivo de unidad.

Esta opción solo está disponible para servicios del sistema y no se admite para servicios que se ejecutan en instancias de administrador de servicios por usuario.

Añadido en la versión 246.

RootHashSignature=

Toma una firma PKCS7 de la opción RootHash= como ruta a un archivo de firma codificado en DER, o como una cadena ASCII base64 que codifica una firma codificada en DER prefijada con "base64:". El volumen dm-verity solo se abrirá si la firma del hash raíz es válida y está firmada por una clave pública presente en el keyring del kernel. Si esta opción no se especifica, pero se encuentra un archivo con el sufijo .roothash.p7s junto al archivo de imagen, con el mismo nombre (excepto si la imagen tiene el sufijo .raw, en cuyo caso el archivo de firma no debe tenerlo en su nombre), la firma se lee de él y se utiliza automáticamente.

Si la imagen de disco contiene una partición /usr/ separada, también puede estar protegida por Verity, en cuyo caso la firma del hash raíz puede configurarse a través de un archivo .usrhash.p7s adyacente a la imagen de disco. Actualmente no hay una opción para configurar la firma del hash raíz para /usr/ directamente desde el archivo de unidad.

Esta opción solo está disponible para servicios del sistema y no se admite para servicios que se ejecutan en instancias de administrador de servicios por usuario.

Añadido en la versión 246.

RootVerity=

Toma la ruta a un archivo de integridad de datos (dm-verity). Esta opción habilita las comprobaciones de integridad de datos mediante dm-verity, si se utiliza RootImage= y se proporciona un hash raíz, y si la imagen utilizada en sí no contiene los datos de integridad. Los datos de integridad deben coincidir con el hash raíz. Si esta opción no se especifica, pero se encuentra un archivo con el sufijo .verity junto al archivo de imagen, con el mismo nombre (excepto si la imagen tiene el sufijo .raw, en cuyo caso el archivo de datos de verity no debe tenerlo en su nombre), los datos de verity se leen de él y se utilizan automáticamente.

Esta opción solo se admite para imágenes de disco que contienen un único sistema de archivos, sin una tabla de particiones envolvente. Las imágenes que contienen una tabla de particiones GPT deben incluir tanto el sistema de archivos raíz como los datos de Verity correspondientes en la misma imagen, implementando la Especificación de particiones descubribles[1].

Esta opción solo está disponible para servicios del sistema y no se admite para servicios que se ejecutan en instancias de administrador de servicios por usuario.

Añadido en la versión 246.

RootImagePolicy=, MountImagePolicy=, ExtensionImagePolicy=

Toma una cadena de política de imagen según systemd.image-policy(7) para usar al montar las imágenes de disco (DDI) especificadas en RootImage=, MountImage=, ExtensionImage=, respectivamente. Si no se especifica, la siguiente cadena de política es el valor predeterminado para RootImagePolicy= y MountImagePolicy: 
root=verity+signed+encrypted+unprotected+absent: \
        usr=verity+signed+encrypted+unprotected+absent: \
        home=encrypted+unprotected+absent: \
        srv=encrypted+unprotected+absent: \
        tmp=encrypted+unprotected+absent: \
        var=encrypted+unprotected+absent

La política predeterminada para ExtensionImagePolicy= es:

root=verity+signed+encrypted+unprotected+absent: \
        usr=verity+signed+encrypted+unprotected+absent

Añadido en la versión 254.

MountAPIVFS=

Toma un argumento booleano. Si está activado, se crea un espacio de nombres de montaje privado para los procesos de la unidad y se montan los sistemas de archivos de la API /proc/, /sys/, /dev/ y /run/ (como un "tmpfs" vacío) dentro de él, a menos que ya estén montados. Tenga en cuenta que esta opción no tiene ningún efecto a menos que se utilice junto con RootDirectory=/RootImage=, ya que estos cuatro montajes generalmente se montan en el host de todos modos, y a menos que se cambie el directorio raíz, el espacio de nombres de montaje privado será una copia 1:1 de la del host, e incluirá estos cuatro montajes. Tenga en cuenta que el sistema de archivos /dev/ del host se monta por enlace si se utiliza esta opción sin PrivateDevices=. Para ejecutar el servicio con una versión privada y mínima de /dev/, combine esta opción con PrivateDevices=.

Para permitir la propagación de montajes en tiempo de ejecución de manera segura, se utilizará /run/systemd/propagate/ en el host para configurar nuevos montajes, y /run/host/incoming/ en el espacio de nombres privado se utilizará como paso intermedio para almacenarlos antes de moverlos al punto de montaje final.

Añadido en la versión 233.

BindLogSockets=

Toma un argumento booleano. Si es verdadero, los sockets de systemd-journald.socket(8) se enlazarán y montarán en el espacio de nombres de montaje. Esto es particularmente útil cuando se emplea una instancia diferente de /run/, para asegurarse de que los procesos que se ejecutan en el espacio de nombres aún puedan utilizar sd-journal(3).

Esta opción se implica cuando se utiliza LogNamespace=, cuando MountAPIVFS=yes, o cuando se utiliza PrivateDevices=yes junto con RootDirectory= o RootImage=.

Añadido en la versión 257.

ProtectProc=

Toma una de las opciones "noaccess", "invisible", "ptraceable" o "default" (que es su valor predeterminado). Cuando se establece, esto controla la opción de montaje "hidepid=" de la instancia "procfs" para la unidad que controla qué directorios con metainformación de procesos (/proc/PID) son visibles y accesibles: cuando se establece en "noaccess", se quita la capacidad de acceder a la mayoría de los metadatos de procesos de otros usuarios en /proc/ para los procesos del servicio. Cuando se establece en "invisible", los procesos propiedad de otros usuarios se ocultan de /proc/. Si "ptraceable", todos los procesos que no pueden ser ptrace()'ados por un proceso se ocultan a él. Si "default", no se realizan restricciones en el acceso o visibilidad de /proc/. Para más detalles, consulte El sistema de archivos /proc[2]. Generalmente se recomienda ejecutar la mayoría de los servicios del sistema con esta opción establecida en "invisible". Esta opción se implementa a través del espacio de nombres del sistema de archivos, y por lo tanto, no se puede utilizar con servicios que deban poder instalar puntos de montaje en la jerarquía del sistema de archivos del host. Tenga en cuenta que el usuario root no se ve afectado por esta opción, por lo que para que sea efectiva debe usarse junto con User= o DynamicUser=yes, y también sin la capacidad "CAP_SYS_PTRACE", que también permite que un proceso eluda esta característica. No se puede utilizar para servicios que necesitan acceder a metainformación sobre procesos de otros usuarios. Esta opción implica MountAPIVFS=.

Si el kernel no admite opciones de montaje hidepid= por punto de montaje, esta configuración permanecerá sin efecto y los procesos de la unidad podrán acceder y ver otros procesos como si la opción no se hubiera utilizado.

Esta opción solo está disponible para servicios del sistema y no se admite para servicios que se ejecutan en instancias de administrador de servicios por usuario.

Añadido en la versión 247.

ProcSubset=

Toma una de las opciones "all" (el valor predeterminado) y "pid". Si es "pid", todos los archivos y directorios no directamente asociados con la gestión e introspección de procesos se vuelven invisibles en el sistema de archivos /proc/ configurado para los procesos de la unidad. Esto controla la opción de montaje "subset=" de la instancia "procfs" para la unidad. Para más detalles cee El Sistema de Archivos /proc[2]. Tenga en cuenta que Linux expone varias API del kernel a través de /proc/, que no están disponibles con esta configuración. Dado que estas API se utilizan con frecuencia, esta opción solo es útil en unos pocos casos específicos y no es adecuada para la mayoría de los programas no triviales.

Al igual que ProtectProc= anterior, esto se implementa a través de namespacio de montaje del sistema de archivos, y por lo tanto se aplican las mismas restricciones: solo está disponible para servicios del sistema, deshabilita la propagación de montaje a la tabla de montaje del host e implica MountAPIVFS=. Además, al igual que ProtectProc=, esta configuración se deshabilita elegantemente si el kernel utilizado no admite la opción de montaje "subset=" de "procfs".

Añadido en la versión 247.

BindPaths=, BindReadOnlyPaths=

Configura montajes bind específicos de la unidad. Un montaje bind hace que un archivo o directorio particular esté disponible en un lugar adicional en la vista del sistema de archivos de la unidad. Cualquier montaje bind creado con esta opción es específico de la unidad y no es visible en la tabla de montaje del host. Esta opción espera una lista separada por espacios en blanco de definiciones de montaje bind. Cada definición consiste en un triple separado por dos puntos de ruta de origen, ruta de destino y cadena de opciones, donde las dos últimas son opcionales. Si solo se especifica una ruta de origen, el origen y el destino se toman como iguales. La cadena de opciones puede ser "rbind" o "norbind" para configurar un montaje bind recursivo o no recursivo. Si se omite la ruta de destino, la cadena de opciones también debe omitirse. Cada definición de montaje bind puede prefijarse con "-", en cuyo caso se ignorará cuando su ruta de origen no exista.

BindPaths= crea montajes bind regulares y escribibles (a menos que el montaje del sistema de archivos de origen ya esté marcado como solo lectura), mientras que BindReadOnlyPaths= crea montajes bind de solo lectura. Estas configuraciones se pueden usar más de una vez, cada uso se añade a la lista de montajes bind de la unidad. Si se asigna la cadena vacía a cualquiera de estas dos opciones, se restablece toda la lista de montajes bind definidos previamente. Tenga en cuenta que, en este caso, se restablecen tanto los montajes bind de solo lectura como los regulares, independientemente de cuál de las dos configuraciones se utilice.

El uso de esta opción implica que se asigna un espacio de nombres de montaje para la unidad, es decir, implica el efecto de PrivateMounts= (ver abajo).

Esta opción es particularmente útil cuando se utiliza RootDirectory=/RootImage=. En este caso, la ruta de origen se refiere a una ruta en el sistema de archivos del host, mientras que la ruta de destino se refiere a una ruta debajo del directorio raíz de la unidad.

Tenga en cuenta que el directorio de destino debe existir o systemd debe ser capaz de crearlo. Por lo tanto, no es posible utilizar esas opciones para puntos de montaje anidados debajo de las rutas especificadas en InaccessiblePaths=, o debajo de /home/ y otros directorios protegidos si se especifica ProtectHome=yes. Se debe usar TemporaryFileSystem= con ":ro" o ProtectHome=tmpfs en su lugar.

Añadido en la versión 233.

MountImages=

Esta configuración es similar a RootImage= en que monta un jerarquía de sistemas de archivos desde un nodo de dispositivo de bloque o un archivo de loopback, pero el directorio de destino se puede especificar, así como las opciones de montaje. Esta opción espera una lista separada por espacios en blanco de definiciones de montaje. Cada definición consiste en una tupla separada por dos puntos de la ruta de origen y la definición de destino, opcionalmente seguida por dos puntos y una lista de opciones de montaje.

Las opciones de montaje se pueden definir como una sola lista de opciones separadas por comas, en cuyo caso se aplicarán implícitamente a la partición raíz en la imagen, o una serie de tuplas separadas por dos puntos de nombre de partición y opciones de montaje. Los nombres de partición y las opciones de montaje válidos son los mismos que para la configuración RootImageOptions= descrita anteriormente.

Cada definición de montaje puede prefijarse con "-", en cuyo caso se ignorará cuando su ruta de origen no exista. El argumento de origen es una ruta a un nodo de dispositivo de bloque o un archivo regular. Si el origen o el destino contienen un ":", debe escaparse como "\:". El nodo del dispositivo o el archivo de imagen del sistema de archivos deben seguir las mismas reglas que se especifican para RootImage=. Cualquier montaje creado con esta opción es específico de la unidad y no es visible en la tabla de montaje del host.

Estas configuraciones se pueden usar más de una vez, cada uso se añade a la lista de rutas de montaje de la unidad. Si se asigna la cadena vacía, se restablece toda la lista de rutas de montaje definidas previamente.

Tenga en cuenta que el directorio de destino debe existir o systemd debe ser capaz de crearlo. Por lo tanto, no es posible utilizar esas opciones para puntos de montaje anidados debajo de las rutas especificadas en InaccessiblePaths=, o debajo de /home/ y otros directorios protegidos si se especifica ProtectHome=yes.

Cuando DevicePolicy= se establece en "closed" o "strict", o se establece en "auto" y se establece DeviceAllow=, esta configuración agrega /dev/loop-control con modo rw, "block-loop" y "block-blkext" con modo rwm a DeviceAllow=. Consulte systemd.resource-control(5) para obtener detalles sobre DevicePolicy= o DeviceAllow=. Además, consulte PrivateDevices= a continuación, ya que puede cambiar la configuración de DevicePolicy=.

Esta opción solo está disponible para servicios del sistema y no es compatible con servicios que se ejecutan en instancias de administrador de servicios por usuario.

Añadido en la versión 247.

ExtensionImages=

Esta configuración es similar a MountImages= en que monta una jerarquía de sistemas de archivos desde un nodo de dispositivo de bloque o un archivo de loopback, pero en lugar de proporcionar una ruta de destino, se configurará una superposición. Esta opción espera una lista separada por espacios en blanco de definiciones de montaje. Cada definición consiste en una ruta de origen, seguida opcionalmente por dos puntos y una lista de opciones de montaje.

Se configurará un OverlayFS de solo lectura sobre las jerarquías de /usr/ y /opt/ para las imágenes sysext y la jerarquía de /etc/ para las imágenes confext. El orden en que se enumeran las imágenes determinará el orden en que se aplica la superposición: las imágenes especificadas de principio a fin darán como resultado capas de overlayfs de abajo hacia arriba.

Las opciones de montaje se pueden definir como una sola lista de opciones separadas por comas, en cuyo caso se aplicarán implícitamente a la partición raíz en la imagen, o una serie de tuplas separadas por dos puntos de nombre de partición y opciones de montaje. Los nombres de partición y las opciones de montaje válidos son los mismos que para la configuración RootImageOptions= descrita anteriormente.

Cada definición de montaje puede prefijarse con "-", en cuyo caso se ignorará cuando su ruta de origen no exista. El argumento de origen es una ruta a un nodo de dispositivo de bloque o un archivo regular. Si la ruta de origen contiene ":", debe escaparse como "\:". El nodo del dispositivo o el archivo de imagen del sistema de archivos deben seguir las mismas reglas que se especifican para RootImage=. Cualquier montaje creado con esta opción es específico de la unidad y no es visible en la tabla de montaje del host.

Estas configuraciones se pueden usar más de una vez, cada uso se añade a la lista de rutas de imagen de la unidad. Si se asigna la cadena vacía, se restablece toda la lista de rutas de montaje definidas previamente.

Cada imagen sysext debe contener un archivo /usr/lib/extension-release.d/extension-release.IMAGE, mientras que cada imagen confext debe contener un archivo /etc/extension-release.d/extension-release.IMAGE, con metadatos apropiados que coincidan con RootImage=/RootDirectory= o el host. Consulte: os-release(5). Para deshabilitar la verificación de seguridad de que el nombre del archivo extension-release coincida con el nombre del archivo de imagen, se puede agregar la opción de montaje x-systemd.relax-extension-release-check.

Esta opción se puede usar junto con un tipo de servicio notify-reload y systemd.v(7) para administrar actualizaciones de configuración. Cuando dicho servicio que contiene imágenes confext se recarga a través de systemctl reload foo.service o un método D-Bus equivalente, la propia confext se recargará para incorporar cualquier cambio. Esto solo se aplica a las extensiones confext. Tenga en cuenta que en caso de que un servicio tenga esta configuración habilitada por primera vez, y luego se elimine posteriormente en una actualización seguida de una operación de recarga de demonio, la recarga de las confexts será una operación nula y se requerirá un reinicio completo del servicio en su lugar. Consulte también systemd.service(5) para obtener detalles.

Cuando DevicePolicy= se establece en "closed" o "strict", o se establece en "auto" y se establece DeviceAllow=, esta configuración agrega /dev/loop-control con modo rw, "block-loop" y "block-blkext" con modo rwm a DeviceAllow=. Consulte systemd.resource-control(5) para obtener detalles sobre DevicePolicy= o DeviceAllow=. Además, consulte PrivateDevices= a continuación, ya que puede cambiar la configuración de DevicePolicy=.

En lugar de la ruta de la imagen, se puede especificar un directorio versionado ".v/", consulte systemd.v(7) para obtener detalles.

Esta opción solo está disponible para servicios del sistema y no es compatible con servicios que se ejecutan en instancias de administrador de servicios por usuario.

IDENTIDAD DE USUARIO/GRUPO

Estas opciones solo están disponibles para servicios del sistema y no son compatibles con los servicios que se ejecutan en instancias de usuario del gestor de servicios.

User=, Group=

Establece el usuario o grupo de UNIX en el que se ejecutan los procesos, respectivamente. Toma un solo nombre de usuario o grupo, o un ID numérico como argumento. Para los servicios del sistema (servicios ejecutados por el gestor de servicios del sistema, es decir, gestionados por PID 1) y para los servicios de usuario del usuario root (servicios gestionados por la instancia de root de systemd --user), el valor predeterminado es "root", pero se puede usar User= para especificar un usuario diferente. Para los servicios de usuario de cualquier otro usuario, no se permite cambiar la identidad del usuario, por lo que la única configuración válida es el mismo usuario bajo el cual se está ejecutando el gestor de servicios del usuario. Si no se establece un grupo, se utiliza el grupo predeterminado del usuario. Esta configuración no afecta a los comandos cuya línea de comandos esté prefijada con "+".

Tenga en cuenta que esto impone solo restricciones débiles en la sintaxis de los nombres de usuario/grupo, pero generará advertencias en muchos casos en los que los nombres de usuario/grupo no cumplan las siguientes reglas: el nombre especificado solo debe contener los caracteres a-z, A-Z, 0-9, "_" y "-", excepto el primer carácter que debe ser uno de a-z, A-Z y "_" (es decir, los dígitos y "-" no están permitidos como primer carácter). El nombre de usuario/grupo debe tener al menos un carácter y como máximo 31. Estas restricciones se hacen para evitar ambigüedades y garantizar que los nombres de usuario/grupo y los archivos de unidad sigan siendo portátiles entre los sistemas Linux. Para más detalles sobre los nombres aceptados y los nombres sobre los que se advierte, consulte Sintaxis de Nombres de Usuario/Grupo[3].

Cuando se usa junto con DynamicUser=, el nombre de usuario/grupo especificado se asigna dinámicamente en el momento en que se inicia el servicio y se libera en el momento en que se detiene el servicio, a menos que ya esté asignado estáticamente (ver más abajo). Si no se usa DynamicUser=, el usuario y grupo especificados deben haber sido creados estáticamente en la base de datos de usuarios no más tarde del momento en que se inicia el servicio, por ejemplo, utilizando el mecanismo de sysusers.d(5), que se aplica al arrancar o al instalar un paquete. Si el usuario no existe para entonces, la invocación del programa fallará.

Si se utiliza la configuración User=, la lista de grupos suplementarios se inicializa a partir de la lista de grupos predeterminada del usuario especificado, tal como se define en la base de datos de usuarios y grupos del sistema. Se pueden configurar grupos adicionales a través de la configuración SupplementaryGroups= (ver más abajo).

DynamicUser=

Toma un parámetro booleano. Si está configurado, se asigna dinámicamente un par de usuario y grupo de UNIX cuando se inicia la unidad y se libera tan pronto como se detiene. El usuario y el grupo no se añadirán a /etc/passwd ni a /etc/group, sino que se gestionarán de forma transitoria durante el tiempo de ejecución. El módulo NSS glibc nss-systemd(8) proporciona la integración de estos usuarios/grupos dinámicos en las bases de datos de usuarios y grupos del sistema. El nombre de usuario y grupo a utilizar se puede configurar a través de User= y Group= (ver arriba). Si no se utilizan estas opciones y la asignación dinámica de usuario/grupo está habilitada para una unidad, el nombre del usuario/grupo dinámico se deriva implícitamente del nombre de la unidad. Si el nombre de la unidad sin el sufijo de tipo califica como un nombre de usuario válido, se utiliza directamente; de lo contrario, se utiliza un nombre que incorpora un hash del mismo. Si ya existe un usuario o grupo asignado estáticamente con el nombre configurado, se utiliza y no se asigna ningún usuario/grupo dinámico. Tenga en cuenta que si se especifica User= y existe el grupo estático con ese nombre, entonces es necesario que el usuario estático con ese nombre ya exista. De manera similar, si se especifica Group= y existe el usuario estático con ese nombre, entonces es necesario que el grupo estático con ese nombre ya exista. Los usuarios/grupos dinámicos se asignan desde el rango UID/GID 61184...65519. Se recomienda evitar este rango para usuarios de sistema o de inicio de sesión regulares. En cualquier momento, cada UID/GID de este rango solo se asigna a cero o un usuario/grupo dinámico asignado que esté en uso. Sin embargo, los UID/GID se reciclan después de que una unidad se termina. Se debe tener cuidado de que ningún proceso que se ejecute como parte de una unidad para la que se habiliten usuarios/grupos dinámicos deje archivos o directorios propiedad de estos usuarios/grupos, ya que otra unidad podría obtener el mismo UID/GID asignado más tarde y, por lo tanto, obtener acceso a estos archivos o directorios. Si DynamicUser= está habilitado, RemoveIPC= se implica (y no se puede desactivar). Esto asegura que la vida útil de los objetos IPC y los archivos temporales creados por los procesos ejecutados esté ligada al tiempo de ejecución del servicio, y por lo tanto, a la vida útil del usuario/grupo dinámico. Dado que /tmp/ y /var/tmp/ son generalmente los únicos directorios universalmente escribibles en un sistema, a menos que PrivateTmp= se establezca manualmente en "true", se implicaría "disconnected". Esto asegura que una unidad que haga uso de la asignación de usuario/grupo dinámico no pueda dejar archivos después de la terminación de la unidad. Además, NoNewPrivileges= y RestrictSUIDSGID= se habilitan implícitamente (y no se pueden desactivar), para garantizar que los procesos invocados no puedan beneficiarse o crear archivos o directorios SUID/SGID. Además, se implican ProtectSystem=strict y ProtectHome=read-only, prohibiendo así que el servicio escriba en ubicaciones arbitrarias del sistema de archivos. Para permitir que el servicio escriba en ciertos directorios, deben ser incluidos en la lista blanca utilizando ReadWritePaths=, pero se debe tener cuidado para que la reutilización de UID/GID no cree problemas de seguridad relacionados con archivos creados por el servicio. Utilice RuntimeDirectory= (ver más abajo) para asignar un directorio de tiempo de ejecución escribible a un servicio, propiedad del usuario/grupo dinámico y eliminado automáticamente cuando se termina la unidad. Utilice StateDirectory=, CacheDirectory= y LogsDirectory= para asignar un conjunto de directorios escribibles para fines específicos al servicio de manera que estén protegidos contra vulnerabilidades debido a la reutilización de UID (ver más abajo). Si esta opción está habilitada, se debe tener cuidado de que los procesos de la unidad no obtengan acceso a directorios fuera de los configurados y gestionados explícitamente. Específicamente, no utilice BindPaths= y tenga cuidado con el paso de descriptores de archivo AF_UNIX para descriptores de archivo de directorios, ya que esto permitiría a los procesos crear archivos o directorios propiedad del usuario/grupo dinámico que no estén sujetos a las garantías de ciclo de vida y acceso del servicio. Tenga en cuenta que esta opción es actualmente incompatible con las políticas de D-Bus, por lo que un servicio que utilice esta opción actualmente no puede asignar un nombre de servicio D-Bus (tenga en cuenta que esto no afecta a las llamadas a otros servicios D-Bus). Por defecto está desactivado.

PAMName=

Establece el nombre del servicio PAM para configurar una sesión. Si está configurado, el proceso ejecutado se registrará como una sesión PAM bajo el nombre de servicio especificado. Esto solo es útil en conjunción con la configuración User=, y de lo contrario se ignora. Si no está configurado, no se abrirá ninguna sesión PAM para los procesos ejecutados. Consulte pam(8) para más detalles.

Tenga en cuenta que para cada unidad que utilice esta opción, se mantendrá un proceso manejador de sesiones PAM como parte de la unidad y permanecerá activo mientras la unidad esté activa, para garantizar que se puedan tomar las acciones apropiadas cuando la unidad y, por lo tanto, la sesión PAM terminen. Este proceso se llama "(sd-pam)" y es un hijo inmediato del proceso principal de la unidad.

Tenga en cuenta que cuando esta opción se utiliza para una unidad, es muy probable (dependiendo de la configuración de PAM) que el proceso principal de la unidad sea migrado a su propia unidad de ámbito de sesión cuando se active. Este proceso se asociará, por lo tanto, con dos unidades: la unidad desde la que se inició originalmente (y para la cual se configuró PAMName=), y la unidad de ámbito de sesión. Sin embargo, cualquier proceso hijo de ese proceso se asociará solo con la unidad de ámbito de sesión. Esto tiene implicaciones cuando se utiliza en combinación con NotifyAccess=all, ya que estos procesos hijos no podrán afectar los cambios en la unidad original a través de mensajes de notificación. Estos mensajes se considerarán pertenecientes a la unidad de ámbito de sesión y no a la unidad original. Por lo tanto, no se recomienda usar PAMName= en combinación con NotifyAccess=all.

CAPACIDADES

Estas opciones solo están disponibles para servicios del sistema, o para servicios que se ejecutan en instancias de administrador de servicios por usuario, en cuyo caso PrivateUsers= se habilita implícitamente (requiere que los espacios de nombres de usuario no privilegiados sean compatibles y estén habilitados en el kernel a través del sysctl "kernel.unprivileged_userns_clone=").

CapabilityBoundingSet=

Controla qué capacidades incluir en el conjunto de límites de capacidades para el proceso ejecutado. Consulte capabilities(7) para obtener detalles. Acepta una lista separada por espacios de nombres de capacidades, por ejemplo, CAP_SYS_ADMIN, CAP_DAC_OVERRIDE, CAP_SYS_PTRACE. Las capacidades enumeradas se incluirán en el conjunto de límites; todas las demás se eliminarán. Si la lista de capacidades va precedida de "~", se incluirán todas excepto las enumeradas, invirtiendo el efecto de la asignación. Tenga en cuenta que esta opción también afecta a las capacidades respectivas en los conjuntos de capacidades efectivo, permitido e heredable. Si no se utiliza esta opción, el conjunto de límites de capacidades no se modifica al ejecutar el proceso, por lo que no se aplican límites a las capacidades del proceso. Esta opción puede aparecer más de una vez, en cuyo caso los conjuntos de límites se fusionan mediante OR, o mediante AND si las líneas van precedidas de "~" (ver más abajo). Si se asigna una cadena vacía a esta opción, el conjunto de límites se restablece al conjunto de capacidades vacío, y todas las configuraciones previas no tienen efecto. Si se establece en "~" (sin ningún otro argumento), el conjunto de límites se restablece al conjunto completo de capacidades disponibles, deshaciendo también cualquier configuración previa. Esto no afecta a los comandos precedidos de "+".

Utilice el comando capability de systemd-analyze(1) para obtener una lista de las capacidades definidas en el sistema local.

Ejemplo: si una unidad tiene lo siguiente,

CapabilityBoundingSet=CAP_A CAP_B
CapabilityBoundingSet=CAP_B CAP_C

entonces se establecen CAP_A, CAP_B y CAP_C. Si la segunda línea va precedida de "~", por ejemplo,

CapabilityBoundingSet=CAP_A CAP_B
CapabilityBoundingSet=~CAP_B CAP_C

entonces, solo se establece CAP_A.

AmbientCapabilities=

Controla qué capacidades incluir en el conjunto de capacidades ambientales para el proceso ejecutado. Acepta una lista separada por espacios de nombres de capacidades, por ejemplo, CAP_SYS_ADMIN, CAP_DAC_OVERRIDE, CAP_SYS_PTRACE. Esta opción puede aparecer más de una vez, en cuyo caso los conjuntos de capacidades ambientales se fusionan (ver los ejemplos anteriores en CapabilityBoundingSet=). Si la lista de capacidades va precedida de "~", se incluirán todas excepto las enumeradas, invirtiendo el efecto de la asignación. Si se asigna una cadena vacía a esta opción, el conjunto de capacidades ambientales se restablece al conjunto de capacidades vacío, y todas las configuraciones previas no tienen efecto. Si se establece en "~" (sin ningún otro argumento), el conjunto de capacidades ambientales se restablece al conjunto completo de capacidades disponibles, deshaciendo también cualquier configuración previa. Tenga en cuenta que agregar capacidades al conjunto de capacidades ambientales las agrega al conjunto de capacidades heredadas del proceso.

Los conjuntos de capacidades ambientales son útiles si desea ejecutar un proceso como un usuario no privilegiado pero aún así desea darle algunas capacidades. Tenga en cuenta que, en este caso, la opción keep-caps se agrega automáticamente a SecureBits= para conservar las capacidades después del cambio de usuario. AmbientCapabilities= no afecta a los comandos precedidos de "+".

SEGURIDAD

NoNewPrivileges=

Acepta un argumento booleano. Si es verdadero, asegura que el proceso de servicio y todos sus hijos nunca puedan obtener nuevos privilegios a través de execve() (por ejemplo, a través de bits setuid o setgid, o capacidades del sistema de archivos). Esta es la forma más simple y efectiva de garantizar que un proceso y sus hijos nunca puedan elevar privilegios nuevamente. El valor predeterminado es falso. En caso de que el servicio se ejecute en un nuevo espacio de nombres de montaje de todos modos y SELinux esté deshabilitado, todos los sistemas de archivos se montarán con el indicador MS_NOSUID. Consulte también el Indicador No Nuevos Privilegios[5].

Tenga en cuenta que esta configuración solo tiene efecto en los procesos de la unidad en sí (o en cualquier proceso derivado directa o indirectamente de ellos). No tiene efecto en los procesos invocados potencialmente a solicitud de ellos a través de herramientas como at(1), crontab(1), systemd-run(1), o servicios IPC arbitrarios.

PROPIEDADES DEL PROCESO

LimitCPU=, LimitFSIZE=, LimitDATA=, LimitSTACK=, LimitCORE=, LimitRSS=, LimitNOFILE=, LimitAS=, LimitNPROC=, LimitMEMLOCK=, LimitLOCKS=, LimitSIGPENDING=, LimitMSGQUEUE=, LimitNICE=, LimitRTPRIO=, LimitRTTIME=

Establece límites blandos y duros en varios recursos para los procesos ejecutados. Consulte setrlimit(2) para obtener detalles sobre el concepto de límite de recursos del proceso. Los límites de recursos del proceso pueden especificarse en dos formatos: como un valor único para establecer un límite blando y duro específico al mismo valor, o como un par separado por dos puntos blando:duro para establecer ambos límites individualmente (por ejemplo, "LimitAS=4G:16G"). Utilice la cadena infinity para configurar ningún límite en un recurso específico. Los sufijos multiplicadores K, M, G, T, P y E (en base 1024) se pueden utilizar para límites de recursos medidos en bytes (por ejemplo, "LimitAS=16G"). Para los límites que se refieren a valores de tiempo, se pueden utilizar las unidades de tiempo habituales ms, s, min, h, etc. (consulte systemd.time(7) para obtener detalles). Tenga en cuenta que si no se especifica ninguna unidad de tiempo para LimitCPU=, se implícita la unidad predeterminada de segundos, mientras que para LimitRTTIME=, se implícita la unidad predeterminada de microsegundos. Además, tenga en cuenta que la granularidad efectiva de los límites podría influir en su aplicación. Por ejemplo, los límites de tiempo especificados para LimitCPU= se redondearán implícitamente al múltiplo de 1s. Para LimitNICE= el valor puede especificarse en dos sintaxis: si va precedido de "+" o "-", el valor se entiende como un valor nice de Linux normal en el rango -20...19. Si no se antepone de esta manera, el valor se entiende como un parámetro de límite de recursos bruto en el rango 0...40 (con 0 equivalente a 1).

Tenga en cuenta que la mayoría de los límites de recursos del proceso configurados con estas opciones son por proceso, y los procesos pueden bifurcarse para adquirir un nuevo conjunto de recursos que se contabilizan independientemente del proceso original, y por lo tanto pueden escapar de los límites establecidos. Tenga en cuenta también que LimitRSS= no está implementado en Linux y su configuración no tiene ningún efecto. A menudo es aconsejable preferir los controles de recursos enumerados en systemd.resource-control(5) sobre estos límites por proceso, ya que se aplican a los servicios en su conjunto, pueden modificarse dinámicamente en tiempo de ejecución y son generalmente más expresivos. Por ejemplo, MemoryMax= es un reemplazo más potente (y funcional) para LimitRSS=.

Tenga en cuenta que LimitNPROC= limitará el número de procesos de una UID (real) y no el número de procesos iniciados (bifurcados) por el servicio. RESOURCE LIMITS

LimitCPU=, LimitFSIZE=, LimitDATA=, LimitSTACK=, LimitCORE=, LimitRSS=, LimitNOFILE=, LimitAS=, LimitNPROC=, LimitMEMLOCK=, LimitLOCKS=, LimitSIGPENDING=, LimitMSGQUEUE=, LimitNICE=, LimitRTPRIO=, LimitRTTIME=

These directives control the resource limits of the processes run by the service. They are equivalent to the respective shell `ulimit` commands (see ulimit(1)) and may take a value or `infinity`. The units are listed in the table below. For directives that limit memory or file size, the string `~VALUE' may be used instead of `infinity' to limit the resource to `VALUE' bytes minus the system's default hard limit for that resource. The default for all limits is the value inherited from the parent process, except for `LimitCPU=' and `LimitFSIZE=' where the default is `infinity'.

These resource limits are set before the service's main process is executed. If the service is configured to run as a specific user (see User= and Group=), the limits are applied in that user's context. Otherwise, they are applied in the context of the service manager process itself. It is important to note that for system services, these limits are often set by the service manager (PID 1) as root, and may not be effective if the service drops privileges (e.g., by using User=) and the kernel's limit mechanisms do not support per-user limits. For services that run as root, these limits are set by the service manager directly. For security reasons, increasing limits beyond the system's default hard limits is generally disallowed for unprivileged users.

For services that are not running as root, the effective resource limits are often limited by the limits of the user that the service manager itself is running as. Therefore, for user services (which run under the per-user service manager), the resource limits configured in the service unit file cannot be arbitrarily increased beyond the limits already set for the user manager.

The directives LimitDATA= and LimitAS= are generally not recommended for limiting memory usage. They restrict the virtual address space, not the actual physical memory consumption. For memory limiting, it is better to use MemoryMax= and MemoryHigh= (see systemd.resource-control(5)). Similarly, LimitRSS= has no effect on Linux. For limiting the number of processes, TasksMax= is usually preferred over LimitNPROC= because LimitNPROC= is enforced per user, and a service might be running as a user that has other processes running, which might unintentionally hit the limit.

If a service is running as root, and not dropping privileges, then the resource limits are set by the service manager itself. Due to these limitations, TasksMax= (see systemd.resource-control(5)) is typically a better choice than LimitNPROC=.

Resource limits not configured explicitly for a unit default to the value configured in the various DefaultLimitCPU=, DefaultLimitFSIZE=, ... options available in systemd-system.conf(5), and – if not configured there – the kernel or per-user defaults, as defined by the OS (the latter only for user services, see below).

For system units these resource limits may be chosen freely. When these settings are configured in a user service (i.e. a service run by the per-user instance of the service manager) they cannot be used to raise the limits above those set for the user manager itself when it was first invoked, as the user's service manager generally lacks the privileges to do so. In user context these configuration options are hence only useful to lower the limits passed in or to raise the soft limit to the maximum of the hard limit as configured for the user. To raise the user's limits further, the available configuration mechanisms differ between operating systems, but typically require privileges. In most cases it is possible to configure higher per-user resource limits via PAM or by setting limits on the system service encapsulating the user's service manager, i.e. the user's instance of user@.service. After making such changes, make sure to restart the user's service manager.

KeyringMode=

Controls how the kernel session keyring is set up for the service (see session-keyring(7) for details on the session keyring). Takes one of inherit, private, shared. If set to inherit no special keyring setup is done, and the kernel's default behaviour is applied. If private is used a new session keyring is allocated when a service process is invoked, and it is not linked up with any user keyring. This is the recommended setting for system services, as this ensures that multiple services running under the same system user ID (in particular the root user) do not share their key material among each other. If shared is used a new session keyring is allocated as for private, but the user keyring of the user configured with User= is linked into it, so that keys assigned to the user may be requested by the unit's processes. In this mode multiple units running processes under the same user ID may share key material. Unless inherit is selected the unique invocation ID for the unit (see below) is added as a protected key by the name "invocation_id" to the newly created session keyring. Usually the 64-bit versions of the various system architectures support their immediate 32-bit personality architecture counterpart, but no others. For example, x86-64 systems support the x86-64 and x86 personalities but no others. The personality feature is useful when running 32-bit services on a 64-bit host system. If not specified, the personality is left unmodified and thus reflects the personality of the host system's kernel. This option is not useful on architectures for which only one native word width was ever available, such as m68k (32-bit only) or alpha (64-bit only).

Nice=

Sets the default nice level (scheduling priority) for executed processes. Takes an integer between -20 (highest priority) and 19 (lowest priority). In case of resource contention, smaller values mean más recursos se pondrán a disposición de los procesos de la unidad, valores más grandes significan que se dispondrán de menos recursos. Consulte setpriority(2) para obtener más información.

CPUSchedulingPolicy=

Establece la política de planificación de CPU para los procesos ejecutados. Admite uno de los valores: other, batch, idle, fifo o rr. Consulte sched_setscheduler(2) para obtener más información.

Establece la prioridad de planificación de CPU para los procesos ejecutados. El rango de prioridad disponible depende de la política de planificación de CPU seleccionada (ver arriba). Para las políticas de planificación en tiempo real, se puede usar un número entero entre 1 (prioridad más baja) y 99 (prioridad más alta). En caso de contención de recursos de CPU, valores más pequeños significan menos tiempo de CPU disponible para el servicio, valores más grandes significan más. Consulte sched_setscheduler(2) para obtener más información.

Admite un argumento booleano. Esta opción se puede especificar más de una vez, en cuyo caso las máscaras de afinidad de CPU especificadas se combinan. SANDBOXING

Las siguientes opciones de sandboxing son una forma eficaz de limitar la exposición del sistema a los procesos de la unidad. Se recomienda activar tantas de estas opciones para cada unidad como sea posible sin afectar negativamente la capacidad del proceso para operar. Tenga en cuenta que muchas de estas funciones de sandboxing se desactivan elegantemente en sistemas donde el mecanismo de seguridad subyacente no está disponible. Por ejemplo, ProtectSystem= no tiene ningún efecto si el kernel está compilado sin espacios de nombres de sistemas de archivos o si el gestor de servicios se ejecuta en un gestor de contenedores que hace que los espacios de nombres de sistemas de archivos no estén disponibles para su carga útil. De manera similar, RestrictRealtime= no tiene ningún efecto en sistemas que carecen de soporte para filtrado de llamadas al sistema SECCOMP, o en contenedores donde el soporte para esto está desactivado.

También tenga en cuenta que algunas funcionalidades de sandboxing generalmente no están disponibles en servicios de usuario (es decir, servicios ejecutados por el gestor de servicios por usuario). Específicamente, la variedad de configuraciones que requieren soporte de espacios de nombres de sistemas de archivos (como ProtectSystem=) no están disponibles, ya que la funcionalidad del kernel subyacente solo es accesible para procesos con privilegios. Sin embargo, la mayoría de las configuraciones de espacios de nombres, que no funcionarán por sí solas en servicios de usuario, funcionarán cuando se utilicen junto con PrivateUsers=true.

Tenga en cuenta que las diversas opciones que vuelven los directorios de solo lectura (como ProtectSystem=, ReadOnlyPaths=, ...) no afectan la capacidad de los programas para conectarse y comunicarse con sockets AF_UNIX en esos directorios. Por lo tanto, estas opciones no se pueden utilizar para proteger el acceso a los servicios IPC.

ProtectSystem=

Admite un argumento booleano o los valores especiales "full" o "strict". Si es verdadero, monta los directorios /usr/ y los cargadores de arranque (/boot y /efi) en modo de solo lectura para los procesos invocados por esta unidad. Si se establece en "full", el directorio /etc/ también se monta en modo de solo lectura. Si se establece en "strict", toda la jerarquía del sistema de archivos se monta en modo de solo lectura, excepto las subrutas del sistema de archivos API /dev/, /proc/ y /sys/ (proteja estos directorios usando PrivateDevices=, ProtectKernelTunables=, ProtectControlGroups=). Esta configuración garantiza que se prohíba cualquier modificación del sistema operativo suministrado por el proveedor (y opcionalmente su configuración, y montajes locales) para el servicio. Se recomienda habilitar esta configuración para todos los servicios de larga ejecución, a menos que estén involucrados en actualizaciones del sistema o necesiten modificar el sistema operativo de otras maneras. Si se utiliza esta opción, ReadWritePaths= puede usarse para excluir directorios específicos de ser puestos en modo de solo lectura. De manera similar, StateDirectory=, LogsDirectory=, ... y las configuraciones de directorio relacionadas (ver abajo) también excluyen los directorios específicos del efecto de ProtectSystem=. Esta configuración se implica si se establece DynamicUser=. Esta configuración no puede garantizar la protección en todos los casos. En general, tiene las mismas limitaciones que ReadOnlyPaths=, ver abajo. Por defecto está desactivada.

Tenga en cuenta que si ProtectSystem= se establece en "strict" y PrivateTmp= está habilitado, entonces /tmp/ y /var/tmp/ serán escribibles.

Añadido en la versión 214.

ProtectHome=

Admite un argumento booleano o los valores especiales "read-only" o "tmpfs". Si es verdadero, los directorios /home/, /root, y /run/user se hacen inaccesibles y vacíos para los procesos invocados por esta unidad. Si se establece en "read-only", los tres directorios se hacen en modo de solo lectura en su lugar. Si se establece en "tmpfs", se montan sistemas de archivos temporales en los tres directorios en modo de solo lectura. El valor "tmpfs" es útil para ocultar directorios no relevantes para los procesos invocados por la unidad, al tiempo que permite que los directorios necesarios se hagan visibles cuando se listan en BindPaths= o BindReadOnlyPaths=.

Establecer esto en "yes" es en gran medida equivalente a establecer los tres directorios en InaccessiblePaths=. De manera similar, "read-only" es en gran medida equivalente a ReadOnlyPaths=, y "tmpfs" es en gran medida equivalente a TemporaryFileSystem= con ":ro".

Se recomienda habilitar esta configuración para todos los servicios de larga ejecución (en particular los que se enfrentan a la red), para asegurar que no puedan acceder a datos privados de usuario, a menos que los servicios realmente requieran acceso a los datos privados del usuario. Esta configuración se implica si se establece DynamicUser=. Esta configuración no puede garantizar la protección en todos los casos. En general, tiene las mismas limitaciones que ReadOnlyPaths=, ver abajo.

Esta opción solo está disponible para servicios del sistema, o para servicios que se ejecutan en instancias de gestor de servicios por usuario en cuyo caso PrivateUsers= se habilita implícitamente (requiere soporte de espacios de nombres de usuario sin privilegios habilitado en el kernel a través del sysctl "kernel.unprivileged_userns_clone=").

RuntimeDirectory=, StateDirectory=, CacheDirectory=, LogsDirectory=, ConfigurationDirectory=

Estas opciones admiten una lista de nombres de directorios separados por espacios en blanco. Los nombres de directorios especificados deben ser relativos y no pueden incluir "..". Si se establecen, cuando se inicie la unidad, se crearán uno o más directorios con los nombres especificados (incluidos sus padres) debajo de las ubicaciones definidas en la siguiente tabla. Además, la variable de entorno correspondiente se definirá con las rutas completas de los directorios. Si se establecen varios directorios, entonces en la variable de entorno las rutas se concatenan con dos puntos (":").

Si se utiliza DynamicUser=, y si la versión del kernel admite montajes con mapeo de ID[8], los directorios especificados serán propiedad de "nobody" en el espacio de nombres del host y se mapearán a (y serán propiedad de) el UID/GID del servicio en su propio espacio de nombres. El parámetro RuntimeDirectory= se utiliza para especificar uno o más directorios de tiempo de ejecución que se crearán y se vincularán a la vida útil del servicio. Estos directorios se crean en /run por defecto. La vida útil de estos directorios está vinculada a la del servicio; se eliminan automáticamente cuando el servicio se detiene.

Los parámetros StateDirectory=, CacheDirectory=, LogsDirectory= y ConfigurationDirectory= funcionan de manera similar, pero crean directorios en /var/lib, /var/cache, /var/log y /etc, respectivamente. Estos directorios no se eliminan cuando se detiene el servicio y están diseñados para persistir datos de estado, caché, registros y configuración.

En el caso de RuntimeDirectory=, los subdirectorios más internos se eliminan cuando se detiene la unidad. Es posible conservar los directorios especificados en este caso si RuntimeDirectoryPreserve= se configura en restart o yes (ver más abajo). Los directorios especificados con StateDirectory=, CacheDirectory=, LogsDirectory=, ConfigurationDirectory= no se eliminan cuando se detiene la unidad.

Excepto en el caso de ConfigurationDirectory=, los directorios más internos especificados serán propiedad del usuario y grupo especificados en User= y Group=. Si los directorios especificados ya existen y su usuario o grupo propietario no coincide con los configurados, todos los archivos y directorios debajo de los directorios especificados, así como los propios directorios, cambiarán recursivamente su propiedad para que coincidan con lo configurado. Como optimización, si los directorios especificados ya son propiedad del usuario y grupo correctos, los archivos y directorios debajo de ellos se dejan como están, incluso si no coinciden con lo solicitado. Los directorios más internos especificados ajustarán su modo de acceso al especificado en RuntimeDirectoryMode=, StateDirectoryMode=, CacheDirectoryMode=, LogsDirectoryMode= y ConfigurationDirectoryMode=.

Estas opciones implican BindPaths= para las rutas especificadas. Cuando se combinan con RootDirectory= o RootImage=, estas rutas residen siempre en el host y se montan desde allí en el espacio de nombres del sistema de archivos de la unidad.

Si se utiliza DynamicUser=, la lógica para CacheDirectory=, LogsDirectory= y StateDirectory= se altera ligeramente: los directorios se crean debajo de /var/cache/private, /var/log/private y /var/lib/private, respectivamente, que son directorios del host que se vuelven inaccesibles para usuarios no privilegiados, lo que garantiza que no se pueda acceder a estos directorios a través de la reutilización de ID de usuario dinámicos. Se crean enlaces simbólicos para ocultar esta diferencia de comportamiento. Tanto desde la perspectiva del host como desde dentro de la unidad, los directorios relevantes siempre aparecen directamente debajo de /var/cache, /var/log y /var/lib.

Utilice RuntimeDirectory= para administrar uno o más directorios de tiempo de ejecución para la unidad y vincular su vida útil al tiempo de ejecución del demonio. Esto es particularmente útil para demonios no privilegiados que no pueden crear directorios de tiempo de ejecución en /run/ debido a la falta de privilegios, y para asegurarse de que el directorio de tiempo de ejecución se limpie automáticamente después de su uso. Para directorios de tiempo de ejecución que requieren una configuración o garantías de vida útil más complejas o diferentes, considere usar tmpfiles.d(5).

RuntimeDirectory=, StateDirectory=, CacheDirectory= y LogsDirectory= admiten opcionalmente dos parámetros más, separados por ":". El segundo parámetro se interpretará como una ruta de destino que se creará como un enlace simbólico al directorio. Los enlaces simbólicos se crearán después de que se hayan configurado las opciones BindPaths= o TemporaryFileSystem=, para permitir el enlace simbólico efímero. La misma fuente puede tener múltiples enlaces simbólicos, utilizando el mismo primer parámetro, pero un segundo parámetro diferente. El tercer parámetro es un campo de indicadores y, desde la versión 257, puede tener el valor ro para hacer que el directorio solo sea de lectura para el servicio. Esto también es compatible con ConfigurationDirectory=. Si se configuran varios enlaces simbólicos, el directorio será de solo lectura si al menos uno está configurado como de solo lectura. Para pasar un indicador sin un enlace simbólico de destino, el segundo parámetro puede estar vacío, por ejemplo:

ConfigurationDirectory=foo::ro

Los directorios definidos por estas opciones siempre se crean bajo las rutas estándar utilizadas por systemd (/var/, /run/, /etc/, ...). Si el servicio necesita directorios en una ubicación diferente, se debe usar un mecanismo diferente para crearlos.

tmpfiles.d(5) proporciona funcionalidad que se superpone con estas opciones. Se recomienda el uso de estas opciones, ya que la vida útil de los directorios está directamente vinculada a la vida útil de la unidad, y no es necesario garantizar que la configuración de tmpfiles.d se ejecute antes de que se inicie la unidad.

Para eliminar cualquiera de los directorios creados por estas configuraciones, utilice el comando systemctl clean ... en las unidades relevantes, consulte systemctl(1) para obtener detalles.

Ejemplo: si una unidad de servicio del sistema tiene lo siguiente:

RuntimeDirectory=foo/bar baz

el administrador de servicios crea /run/foo (si no existe), /run/foo/bar y /run/baz. Los directorios /run/foo/bar y /run/baz, excepto /run/foo, son propiedad del usuario y grupo especificados en User= y Group=, y se eliminan cuando se detiene el servicio.

Ejemplo: si una unidad de servicio del sistema tiene lo siguiente:

RuntimeDirectory=foo/bar
StateDirectory=aaa/bbb ccc

entonces la variable de entorno "RUNTIME_DIRECTORY" se establece con "/run/foo/bar", y "STATE_DIRECTORY" se establece con "/var/lib/aaa/bbb:/var/lib/ccc".

Ejemplo: si una unidad de servicio del sistema tiene lo siguiente:

RuntimeDirectory=foo:bar foo:baz

el administrador de servicios crea /run/foo (si no existe), y /run/bar más /run/baz como enlaces simbólicos a /run/foo.

systemd.resource-control

NAME

systemd.resource-control - Service resource control directives for systemd.unit(5)

DESCRIPTION

The following resource control directives may be used to configure the resource limits and namespaces of a service. These directives are valid in service units, which are units of type "service".

PrivateUsers=

Takes a boolean argument or one of "self", "identity", or "full". Defaults to false. If enabled, sets up a new user namespace for the executed processes and configures a user and group mapping. If set to a true value or "self", a minimal user and group mapping is configured that maps the "root" user and group as well as the unit's own user and group to themselves and everything else to the "nobody" user and group. This is useful to securely detach the user and group databases used by the unit from the rest of the system, and thus to create an effective sandbox environment. All files, directories, processes, IPC objects and other resources owned by users/groups not equaling "root" or the unit's own will stay visible from within the unit but appear owned by the "nobody" user and group.

If the parameter is "identity", user namespacing is set up with an identity mapping for the first 65536 UIDs/GIDs. Any UIDs/GIDs above 65536 will be mapped to the "nobody" user and group, respectively. While this does not provide UID/GID isolation, since all UIDs/GIDs are chosen identically it does provide process capability isolation, and hence is often a good choice if proper user namespacing with distinct UID maps is not appropriate.

If the parameter is "full", user namespacing is set up with an identity mapping for all UIDs/GIDs. In addition, for system services, "full" allows the unit to call setgroups() system calls (by setting /proc/pid/setgroups to "allow"). Similar to "identity", this does not provide UID/GID isolation, but it does provide process capability isolation.

If this mode is enabled, all unit processes are run without privileges in the host user namespace (regardless of whether the unit's own user/group is "root" or not). Specifically this means that the process will have zero process capabilities on the host's user namespace, but full capabilities within the service's user namespace. Settings such as CapabilityBoundingSet= will affect only the latter, and there's no way to acquire additional capabilities in the host's user namespace.

When this setting is set up by a per-user instance of the service manager, the mapping of the "root" user and group to itself is omitted (unless the user manager is root). Additionally, in the per-user instance manager case, the user namespace will be set up before most other namespaces. This means that combining PrivateUsers=true with other namespaces will enable use of features not normally supported by the per-user instances of the service manager.

This setting is particularly useful in conjunction with RootDirectory=/RootImage=, as the need to synchronize the user and group databases in the root directory and on the host is reduced. See systemd.exec(5) for a full list of settings that affect service execution.

Added in version 241.

PrivateGroups=

Takes a boolean argument. Defaults to false. If true, sets up a new group ID namespace for the executed processes. The group ID namespace isolates the list of group IDs known to the processes. Group IDs used within the namespace are independent of group IDs outside. This is useful to ensure that processes do not gain group memberships unintentionally. Note that this has no effect on user IDs, and it is recommended to combine this setting with PrivateUsers= to isolate both.

This option is only available for system services, or for services running in per-user instances of the service manager in which case PrivateUsers= is implicitly enabled (requires unprivileged user namespaces support to be enabled in the kernel via the "kernel.unprivileged_userns_clone=" sysctl).

Added in version 248.

PrivateMounts=

Takes a boolean argument. Defaults to false. If true, sets up a new mount namespace for the executed processes. This is useful to turn off access to the host's file system hierarchy, and thus create a sandbox environment. All mount points defined in the unit, e.g. via Mounts=, will be available within this namespace. It is possible to run two or more units within the same private mount namespace by using the JoinsNamespaceOf= directive, see systemd.unit(5) for details.

Note that this option may be impossible to implement (for example if mount namespaces are not available), and the unit should be written in a way that does not solely rely on this setting for security.

When this option is enabled, MountAPIVFS= is implied.

This option is only available for system services, or for services running in per-user instances of the service manager in which case PrivateUsers= is implicitly enabled (requires unprivileged user namespaces support to be enabled in the kernel via the "kernel.unprivileged_userns_clone=" sysctl).

Added in version 241.

MountAPIVFS=

Takes a boolean argument. Defaults to false. If true, the systemd.exec(5) namespace is created for the executed processes, which includes a tmpfs mount at /run and /tmp. If PrivateMounts=, PrivateNetwork=, PrivateIPC=, PrivateUTS=, PrivatePID= or PrivateUsers= are enabled, this option is implied and automatically enabled.

Added in version 241.

PrivateNetwork=

Takes a boolean argument. If true, sets up a new network namespace for the executed processes and configures only the loopback network device "lo" inside it. No other network devices will be available to the executed process. This is useful to turn off network access by the executed process. Defaults to false. It is possible to run two or more units within the same private network namespace by using the JoinsNamespaceOf= directive, see systemd.unit(5) for details. Note that this option will disconnect all socket families from the host, including AF_NETLINK and AF_UNIX. Effectively, for AF_NETLINK this means that device configuration events received from systemd-udevd.service(8) are not delivered to the unit's processes. And for AF_UNIX this has the effect that AF_UNIX sockets in the abstract socket namespace of the host will become unavailable to the unit's processes (however, those located in the file system will continue to be accessible).

Note that the implementation of this setting might be impossible (for example if network namespaces are not available), and the unit should be written in a way that does not solely rely on this setting for security.

When this option is enabled, PrivateMounts= is implied unless it is explicitly disabled, and /sys will be remounted to associate it with the new network namespace.

When this option is used on a socket unit any sockets bound on behalf of this unit will be bound within a private network namespace. This may be combined with JoinsNamespaceOf= to listen on sockets inside of network namespaces of other services.

This option is only available for system services, or for services running in per-user instances of the service manager in which case PrivateUsers= is implicitly enabled (requires unprivileged user namespaces support to be enabled in the kernel via the "kernel.unprivileged_userns_clone=" sysctl).

Added in version 209.

NetworkNamespacePath=

Takes an absolute file system path referring to a Linux network namespace pseudo-file (i.e. a file like /proc/$PID/ns/net or a bind mount or symlink to one). When set the invoked processes are added to the network namespace referenced by that path. The path has to point to a valid namespace file at the moment the processes are forked off. If this option is used PrivateNetwork= has no effect. If this option is used together with JoinsNamespaceOf= then it only has an effect if this unit is started before any of the listed units that have PrivateNetwork= or NetworkNamespacePath= configured, as otherwise the network namespace of those units is reused.

When this option is enabled, PrivateMounts= is implied unless it is explicitly disabled, and /sys will be remounted to associate it with the new network namespace.

When this option is used on a socket unit any sockets bound on behalf of this unit will be bound within the specified network namespace.

This option is only available for system services, or for services running in per-user instances of the service manager in which case PrivateUsers= is implicitly enabled (requires unprivileged user namespaces support to be enabled in the kernel via the "kernel.unprivileged_userns_clone=" sysctl).

Added in version 242.

PrivateIPC=

Takes a boolean argument. If true, sets up a new IPC namespace for the executed processes. Each IPC namespace has its own set of System V IPC identifiers and its own POSIX message queue file system. This is useful to avoid name clash of IPC identifiers. Defaults to false. It is possible to run two or more units within the same private IPC namespace by using the JoinsNamespaceOf= directive, see systemd.unit(5) for details.

Note that IPC namespacing does not have an effect on AF_UNIX sockets, which are the most common form of IPC used on Linux. Instead, AF_UNIX sockets in the file system are subject to mount namespacing, and those in the abstract namespace are subject to network namespacing. IPC namespacing only has an effect on SysV IPC (which is mostly legacy) as well as POSIX message queues (for which AF_UNIX/SOCK_SEQPACKET sockets are typically a better replacement). IPC namespacing also has no effect on POSIX shared memory (which is subject to mount namespacing) either. See ipc_namespaces(7) for the details.

Note that the implementation of this setting might be impossible (for example if IPC namespaces are not available), and the unit should be written in a way that does not solely rely on this setting for security.

This option is only available for system services, or for services running in per-user instances of the service manager in which case PrivateUsers= is implicitly enabled (requires unprivileged user namespaces support to be enabled in the kernel via the "kernel.unprivileged_userns_clone=" sysctl).

IPCNamespacePath=

Takes an absolute file system path referring to a Linux IPC namespace pseudo-file (i.e. a file like /proc/$PID/ns/ipc or a bind mount or symlink to one). When set the invoked processes are added to the network namespace referenced by that path. The path has to point to a valid namespace file at the moment the processes are forked off. If this option is used PrivateIPC= has no effect. If this option is used together with JoinsNamespaceOf= then it only has an effect if this unit is started before any of the listed units that have PrivateIPC= or IPCNamespacePath= configured, as otherwise the network namespace of those units is reused.

This option is only available for system services, or for services running in per-user instances of the service manager in which case PrivateUsers= is implicitly enabled (requires unprivileged user namespaces support to be enabled in the kernel via the "kernel.unprivileged_userns_clone=" sysctl).

MemoryKSM=

Takes a boolean argument. When set, it enables KSM (kernel samepage merging) for the processes. KSM is a memory-saving de-duplication feature. Anonymous memory pages with identical content can be replaced by a single write-protected page. This feature should only be enabled for jobs that share the same security domain. For details, see Kernel Samepage Merging[12] in the kernel documentation.

Note that this functionality might not be available, for example if KSM is disabled in the kernel, or the kernel does not support controlling KSM at the process level through prctl(2).

Added in version 254.

PrivatePIDs=

Takes a boolean argument. Defaults to false. If enabled, sets up a new PID namespace for the executed processes. Each executed process is now PID 1 - the init process - in the new namespace. /proc/ is mounted such that only processes in the PID namespace are visible. If PrivatePIDs= is set, MountAPIVFS=yes is implied.

PrivatePIDs= is only supported for service units. This setting is not supported with Type=forking since the kernel will kill all processes in the PID namespace if the init process terminates.

This setting will be ignored if the kernel does not support PID namespaces.

Note unprivileged user services (i.e. a service run by the per-user instance of the service manager) will fail with PrivatePIDs=yes if /proc/ is masked (i.e. /proc/kmsg is over-mounted with tmpfs like systemd-nspawn(1) does). This is due to a kernel restriction not allowing unprivileged user namespaces to mount a less restrictive instance of /proc/.

Added in version 257.

PrivateUTS=

Takes a boolean argument. Defaults to false. If true, sets up a new UTS namespace for the executed processes. This isolates the hostname and NIS domain name. This is useful to ensure that units do not accidentally change the system's hostname. Defaults to false. It is possible to run two or more units within the same private UTS namespace by using the JoinsNamespaceOf= directive, see systemd.unit(5) for details.

Note that this option may be impossible to implement (for example if UTS namespaces are not available), and the unit should be written in a way that does not solely rely on this setting for security.

When this option is enabled, PrivateMounts= is implied unless it is explicitly disabled.

Added in version 241.

PrivateMounts=

Toma un parámetro booleano. Si se establece, los procesos de esta unidad se ejecutarán en su propio espacio de nombres de sistema de archivos (montaje) privado con toda la propagación de montajes desde los procesos hacia el espacio de nombres del sistema de archivos principal del host desactivada. Esto significa que cualquier punto de montaje del sistema de archivos establecido o eliminado por los procesos de la unidad será privado para ellos y no será visible para el host. Sin embargo, los puntos de montaje del sistema de archivos establecidos o eliminados en el host se propagarán a los procesos de la unidad. Ver mount_namespaces(7) para más detalles sobre los espacios de nombres del sistema de archivos. Por defecto está desactivado.

Cuando se activa, esto ejecuta tres operaciones por cada proceso invocado: se crea un nuevo espacio de nombres CLONE_NEWNS, después de lo cual todos los montajes existentes se vuelven a montar como MS_SLAVE para deshabilitar la propagación desde los procesos de la unidad al host (pero dejando la propagación en la dirección opuesta en efecto). Finalmente, los montajes se vuelven a montar al modo de propagación configurado con MountFlags=, ver más abajo.

Los espacios de nombres del sistema de archivos se configuran individualmente para cada proceso creado por el administrador de servicios. Por lo tanto, los montajes establecidos en el espacio de nombres del proceso creado por ExecStartPre= se limpiarán automáticamente tan pronto como ese proceso salga y no estarán disponibles para los procesos posteriores creados para ExecStart= (y lo mismo se aplica a los diversos otros comandos configurados para las unidades). De manera similar, JoinsNamespaceOf= no permite compartir espacios de nombres de kernel de montaje entre unidades, solo permite compartir los directorios /tmp/ y /var/tmp/.

Otras configuraciones de espacios de nombres del sistema de archivos de la unidad — PrivateTmp=, PrivateDevices=, ProtectSystem=, ProtectHome=, ReadOnlyPaths=, InaccessiblePaths=, ReadWritePaths=, BindPaths=, BindReadOnlyPaths=, ... — también habilitan el espacio de nombres del sistema de archivos de una manera equivalente a esta opción. Por lo tanto, es principalmente útil solicitar explícitamente este comportamiento si no se utilizan ninguna de las otras configuraciones.

Esta opción solo está disponible para servicios del sistema, o para servicios que se ejecutan en instancias de usuario de administrador de servicios, en cuyo caso PrivateUsers= se habilita implícitamente (requiere soporte de espacios de nombres de usuario no privilegiados habilitado en el kernel a través del sysctl "kernel.unprivileged_userns_clone=").

MOUNT PROPERTY

MountAPIVFS=

This option controls the file system namespace propagation between the unit's processes and the host's file system namespace.

This setting only controls the final propagation setting in effect on all mount points of the file system namespace created for each process of this unit. Other file system namespacing unit settings (see the discussion in PrivateMounts= above) will implicitly disable mount and unmount propagation from the unit's processes towards the host by changing the propagation setting of all mount points in the unit's file system namespace to slave first. Setting this option to shared does not reestablish propagation in that case.

If not set – but file system namespaces are enabled through another file system namespace unit setting – shared mount propagation is used, but — as mentioned — as slave is applied first, propagation from the unit's processes to the host is still turned off.

It is not recommended to use private mount propagation for units, as this means temporary mounts (such as removable media) of the host will stay mounted and thus indefinitely busy in forked off processes, as unmount propagation events will not be received by the file system namespace of the unit.

Usually, it is best to leave this setting unmodified, and use higher level file system namespacing options instead, in particular PrivateMounts=, see above.

This option is only available for system services, or for services running in per-user instances of the service manager in which case PrivateUsers= is implicitly enabled (requires unprivileged user namespaces support to be enabled in the kernel via the "kernel.unprivileged_userns_clone=" sysctl).

FILTRADO DE LLAMADAS AL SISTEMA

SystemCallFilter=

Toma una lista separada por espacios de nombres de llamadas al sistema o grupos de llamadas al sistema. Si se utiliza esta configuración, las llamadas al sistema ejecutadas por los procesos de la unidad, excepto las enumeradas, resultarán en la denegación de la llamada al sistema (lista blanca). Si el primer carácter de la lista es "~", el efecto se invierte: solo se denegarán las llamadas al sistema enumeradas (lista negra). Esta opción se puede especificar varias veces, en cuyo caso las máscaras de filtro se fusionan. Si se asigna la cadena vacía, se restablece el filtro y todas las asignaciones anteriores no tendrán efecto.

Los comandos precedidos por "+" no están sujetos a filtrado. Las llamadas al sistema execve(), exit(), exit_group(), getrlimit(), rt_sigreturn(), sigreturn() y las llamadas al sistema para consultar la hora y dormir están implícitamente en la lista blanca y no necesitan enumerarse explícitamente.

La acción predeterminada cuando se deniega una llamada al sistema es terminar los procesos con una señal SIGSYS. Esto se puede cambiar usando SystemCallErrorNumber=, ver más abajo. Además, las llamadas al sistema y los grupos de llamadas al sistema incluidos en la lista negra pueden ir seguidos opcionalmente por dos puntos (":") y un argumento en el mismo formato que SystemCallErrorNumber=, para tomar esta acción cuando se realiza la llamada al sistema correspondiente. Esto tiene prioridad sobre la acción especificada en SystemCallErrorNumber=.

Esta característica utiliza las interfaces del modo de computación segura 2 del kernel (filtrado 'seccomp') y es útil para aplicar un entorno mínimo de aislamiento (sandboxing).

Tenga en cuenta que en sistemas que admiten múltiples ABIs (como x86/x86-64) se recomienda desactivar las ABIs alternativas para los servicios, de modo que no se puedan utilizar para eludir las restricciones de esta opción. Específicamente, se recomienda combinar esta opción con SystemCallArchitectures=native o similar.

Tenga en cuenta que los filtros estrictos de llamadas al sistema pueden afectar las rutas de código de ejecución y manejo de errores de la invocación del servicio. Específicamente, se requiere acceso a la llamada al sistema execve() para la ejecución del binario del servicio; si se bloquea, la invocación del servicio fallará necesariamente. Además, si la ejecución del binario del servicio falla por algún motivo (por ejemplo: ejecutable del servicio faltante), la lógica de manejo de errores puede requerir acceso a un conjunto adicional de llamadas al sistema para procesar y registrar correctamente esta falla. Puede ser necesario deshabilitar temporalmente los filtros de llamadas al sistema para permitir la depuración de dichas fallas.

Si especifica ambos tipos de esta opción (es decir, lista blanca y lista negra), la primera encontrada tendrá prioridad y dictará la acción predeterminada (terminación o aprobación de una llamada al sistema). Luego, las siguientes ocurrencias de esta opción agregarán o eliminarán las llamadas al sistema enumeradas del conjunto de llamadas al sistema filtradas, dependiendo de su tipo y la acción predeterminada. (Por ejemplo, si comenzó con una regla de lista blanca para read() y write(), y justo después agregó una regla de lista negra para write(), entonces write() se eliminará del conjunto).

Dado que el número de llamadas al sistema posibles es grande, se proporcionan grupos predefinidos de llamadas al sistema. Un grupo comienza con el carácter "@", seguido del nombre del conjunto.

Tenga en cuenta que, a medida que surgen nuevas llamadas al sistema

Se agregan al kernel, se pueden agregar llamadas al sistema adicionales a los grupos anteriores. El contenido de los conjuntos también puede cambiar entre versiones de systemd. Además, la lista de llamadas al sistema depende de la versión del kernel y la arquitectura para la que se compiló systemd. Utilice
systemd-analyze syscall-filter para listar la lista real de llamadas al sistema en cada filtro.

Generalmente, permitir explícitamente llamadas al sistema (en lugar de denegarlas) es el modo de operación más seguro. Se recomienda aplicar listas de permisos de llamadas al sistema para todos los servicios del sistema que se ejecutan continuamente. Específicamente, las siguientes líneas son una opción básica relativamente segura para la mayoría de los servicios del sistema:

[Service]
SystemCallFilter=@system-service
SystemCallErrorNumber=EPERM

Tenga en cuenta que varias llamadas al sistema del kernel se definen redundantemente: hay múltiples llamadas al sistema para ejecutar la misma operación. Por ejemplo, la llamada al sistema pidfd_send_signal() puede usarse para ejecutar operaciones similares a lo que se puede hacer con la llamada al sistema kill() más antigua, por lo que bloquear esta última sin la primera solo proporciona una protección débil. Dado que se agregan nuevas llamadas al sistema regularmente al kernel a medida que avanza el desarrollo, mantener las listas de denegación de llamadas al sistema completas requiere un trabajo constante. Por lo tanto, se recomienda utilizar la lista de permisos en su lugar, que ofrece el beneficio de que las nuevas llamadas al sistema se bloquean implícitamente por defecto hasta que se actualiza la lista de permisos.

Tenga en cuenta también que una serie de llamadas al sistema deben estar accesibles para que el enlazador dinámico funcione. El enlazador dinámico es necesario para ejecutar la mayoría de los programas normales (en específico: todos los binarios ELF dinámicos, que es cómo la mayoría de las distribuciones compilan programas empaquetados). Esto significa que bloquear estas llamadas al sistema (que incluyen open(), openat() o mmap()) hará que la mayoría de los programas que se envían típicamente con distribuciones genéricas sean inutilizables.

Se recomienda combinar las opciones relacionadas con el espacio de nombres del sistema de archivos con SystemCallFilter=~@mount, para prohibir que los procesos de la unidad deshagan las asignaciones. Específicamente, estas son las opciones PrivateTmp=, PrivateDevices=, ProtectSystem=, ProtectHome=, ProtectKernelTunables=, ProtectControlGroups=, ProtectKernelLogs=, ProtectClock=, ReadOnlyPaths=, InaccessiblePaths= y ReadWritePaths=.

Environment=

Establece variables de entorno para los procesos ejecutados. Cada línea se analiza sin comillas según las reglas descritas en la sección "Quoting" de systemd.syntax(7) y se convierte en una lista de asignaciones de variables. Si necesita asignar un valor que contenga espacios o el signo igual a una variable, ponga comillas alrededor de toda la asignación. La expansión de variables no se realiza dentro de las cadenas y el carácter "$" no tiene un significado especial. Se realiza la expansión de especificadores, consulte la sección "Specifiers" en systemd.unit(5).

Esta opción se puede especificar más de una vez, en cuyo caso se establecerán todas las variables listadas. Si la misma variable se lista dos veces, la configuración posterior anulará la configuración anterior. Si se asigna la cadena vacía a esta opción, se restablece la lista de variables de entorno, todas las asignaciones anteriores no tienen efecto.

Los nombres de las variables pueden contener letras ASCII, dígitos y el carácter de subrayado. Los nombres de las variables no pueden estar vacíos ni comenzar con un dígito. En los valores de las variables, se permiten la mayoría de los caracteres, pero los caracteres no imprimibles se rechazan actualmente.

Ejemplo:

Environment="VAR1=palabra1 palabra2" VAR2=palabra3 "VAR3=$palabra 5 6"

da tres variables "VAR1", "VAR2", "VAR3" con los valores "palabra1 palabra2", "palabra3", "$palabra 5 6".

Consulte environ(7) para obtener detalles sobre las variables de entorno.

Tenga en cuenta que las variables de entorno no son adecuadas para pasar secretos (como contraseñas, material de clave, ...) a los procesos del servicio. Las variables de entorno establecidas para una unidad se exponen a clientes no privilegiados a través de IPC de D-Bus y, por lo general, no se consideran datos que requieren protección. Además, las variables de entorno se propagan en el árbol de procesos, incluso a través de límites de seguridad (como ejecutables setuid/setgid), y, por lo tanto, podrían filtrarse a procesos que no deberían tener acceso a los datos secretos. Utilice LoadCredential=, LoadCredentialEncrypted= o SetCredentialEncrypted= (ver más abajo) para pasar datos a los procesos de la unidad de forma segura.

EnvironmentFile=

Similar a Environment=, pero lee las variables de entorno de un archivo de texto. El archivo de texto debe contener asignaciones de variables separadas por saltos de línea. Las líneas vacías, las líneas sin un separador "=" o las líneas que comienzan con ";" o "#" se ignorarán, lo que puede usarse para comentarios. El archivo debe estar codificado en UTF-8. Los caracteres válidos son valores escalares de unicode[14] distintos de no caracteres unicode[15], U+0000 NUL, y U+FEFF marca de orden de bytes de unicode[16]. Se permiten códigos de control distintos de NUL.

En el archivo, un valor sin comillas después del "=" se analiza con las mismas reglas de escape de barra invertida que el texto sin comillas de shell POSIX[17], pero a diferencia de un shell, el espacio en blanco interior se conserva y las comillas después del primer carácter que no sea un espacio en blanco se conservan. El espacio en blanco inicial y final (espacio, tabulación, retorno de carro) se descarta, pero el espacio en blanco interior dentro de la línea se conserva literalmente. Una línea que termina con una barra invertida se continuará en la siguiente, con el salto de línea descartado. Una barra invertida "\" seguida de cualquier carácter que no sea un salto de línea conservará el carácter siguiente, de modo que "\\" se convertirá en el valor "\".

En el archivo, un valor entre comillas simples ("'") después del "=" puede abarcar varias líneas y contener cualquier carácter literalmente excepto la comilla simple, como el texto de shell POSIX entre comillas simples[18]. No se reconocen secuencias de escape de barra invertida. El espacio en blanco inicial y final fuera de las comillas simples se descarta.

En el archivo, un valor entre comillas dobles (""") después del "=" puede abarcar varias líneas, y se reconocen las mismas secuencias de escape que en el texto de shell POSIX entre comillas dobles[19]. La barra invertida ("\") seguida de cualquiera de ""\`$" conservará ese carácter. Una barra invertida seguida de un salto de línea es una continuación de línea, y el salto de línea en sí se descarta. Una barra invertida seguida de cualquier otro carácter se ignora; tanto la barra invertida como el carácter siguiente se conservan literalmente. El espacio en blanco inicial y final fuera de las comillas dobles se descarta.

El argumento pasado debe ser un nombre de archivo absoluto o una expresión comodín, opcionalmente prefijado con "-", lo que indica que si el archivo no existe, no se leerá y no se registrará ningún mensaje de error o advertencia. Esta opción se puede especificar más de una vez, en cuyo caso se leen todos los archivos especificados. Si se asigna la cadena vacía a esta opción, se restablece la lista de archivos a leer, todas las asignaciones anteriores no tienen efecto.

Los archivos listados con esta directiva se leerán poco antes de que se ejecute el proceso (más específicamente, después de que todos los procesos de un estado de unidad anterior hayan terminado. Esto significa que puede generar estos archivos en un estado de unidad y leerlos con esta opción en el siguiente. Los archivos se leen desde el sistema de archivos del administrador del servicio, antes de que se realicen cambios en el sistema de archivos, como montajes bind).

LogLevelMax=

Establece el nivel de registro máximo para los mensajes de registro generados por esta unidad. Toma un nivel de registro de syslog, uno de emerg (nivel de registro más bajo, solo mensajes de máxima prioridad), alert, crit, err, warning, notice, info, debug (nivel de registro más alto, también mensajes de menor prioridad). Consulte syslog(3) para más detalles. Por defecto, el nivel de registro máximo no se anula.

Esta opción se puede utilizar para configurar el sistema de registro para descartar mensajes de registro de un servicio específico por encima del nivel especificado. Por ejemplo, establezca LogLevelMax=info para desactivar el registro de depuración de una unidad particularmente verbosa. Alternativamente, esta opción se puede utilizar para habilitar el registro adicional sobre una unidad específica por parte de los procesos del gestor del sistema o del usuario sin cambiar el nivel de registro global para los procesos del gestor del sistema o del usuario estableciendo LogLevelMax=debug.

Tenga en cuenta que el nivel configurado se aplica a cualquier mensaje de registro escrito por cualquiera de los procesos que pertenecen a esta unidad, así como a cualquier mensaje de registro escrito por los procesos del gestor del sistema o del usuario en referencia a esta unidad, enviado a través de cualquier protocolo de registro compatible. La anulación se aplica temprano en el pipeline de registro, antes de que se realice cualquier tipo de procesamiento adicional. Además, los mensajes que pasan por este filtro con éxito aún pueden ser descartados por filtros aplicados en una etapa posterior en el subsistema de registro. Por ejemplo, MaxLevelStore= configurado en journald.conf(5) podría prohibir que los mensajes de niveles de registro más altos se almacenen en disco, aunque el LogLevelMax= por unidad permitiera su procesamiento.

Configura la limitación de velocidad que se aplica a los mensajes de registro generados por esta unidad. Si, en el intervalo de tiempo definido por LogRateLimitIntervalSec=, se registran más mensajes de los especificados en LogRateLimitBurst= por un servicio, todos los mensajes posteriores dentro del intervalo se descartan hasta que termine el intervalo. LogFilterPatterns=

Define una expresión regular extendida para filtrar mensajes de registro basándose en el campo MESSAGE= del mensaje estructurado. Si el primer carácter del patrón es "~", las entradas de registro que coincidan con el patrón deben descartarse. Esta opción toma un solo patrón como argumento, pero se puede usar varias veces para crear una lista de patrones permitidos y denegados. Si no se definen patrones permitidos, todos los mensajes se procesan directamente después de pasar por los filtros denegados.

n en cuenta. Los mensajes de registro filtrados no se reenviarán a los demonios syslog tradicionales, al búfer de registro del kernel (kmsg), a la consola de systemd ni se enviarán como mensajes de difusión a todos los usuarios conectados.

CREDENCIALES

LoadCredential=ID[:PATH], LoadCredentialEncrypted=ID[:PATH]

Pasa una credencial a la unidad. Las credenciales son objetos binarios o textuales de tamaño limitado que pueden pasarse a los procesos de la unidad. Están principalmente destinadas a pasar claves criptográficas (tanto públicas como privadas) o certificados, información de cuentas de usuario o información de identidad del host a los servicios, pero pueden usarse libremente para pasar cualquier tipo de información de tamaño limitado a un servicio. Los datos son accesibles desde los procesos de la unidad a través del sistema de archivos, en una ubicación de solo lectura que (si es posible y está permitido) está respaldada por memoria no paginable. Los datos solo son accesibles para el usuario asociado con la unidad, a través de la configuración User=/DynamicUser= (así como para el superusuario). Cuando está disponible, la ubicación de las credenciales se exporta como la variable de entorno $CREDENTIALS_DIRECTORY a los procesos de la unidad.

La configuración LoadCredential= toma un ID textual para usarlo como nombre de una credencial más una ruta de sistema de archivos, separadas por dos puntos. El ID debe ser una cadena ASCII corta adecuada como nombre de archivo en el sistema de archivos, y puede ser elegido libremente por el usuario. Si la ruta especificada es absoluta, se abre como un archivo normal y se leen los datos de la credencial. Si la ruta absoluta se refiere a un socket de flujo AF_UNIX en el sistema de archivos, se establece una conexión con él (una vez en la invocación del proceso) y se leen los datos de la credencial de la conexión, proporcionando un punto de integración IPC fácil para transferir dinámicamente credenciales de otros servicios.

Si la ruta especificada no es absoluta y califica en sí misma como un identificador de credencial válido, se intenta encontrar una credencial que el propio gestor de servicios recibió bajo el nombre especificado — que puede usarse para propagar credenciales de un entorno de invocación (por ejemplo, un gestor de contenedores que invocó al gestor de servicios) a un servicio. Si no se encuentra ninguna credencial pasada coincidente, el gestor de servicios del sistema buscará en los directorios /etc/credstore/, /run/credstore/ y /usr/lib/credstore/ archivos bajo el nombre de la credencial — que, por lo tanto, son ubicaciones recomendadas para los datos de credenciales en disco. Si se utiliza LoadCredentialEncrypted=, también se buscarán /run/credstore.encrypted/, /etc/credstore.encrypted/ y /usr/lib/credstore.encrypted/. El gestor de servicios por usuario buscará en $XDG_CONFIG_HOME/credstore/, $XDG_RUNTIME_DIR/credstore/, $HOME/.local/lib/credstore/ (y las contrapartes que terminan en .../credstore.encrypted/) en su lugar. La herramienta systemd-path(1) puede usarse para consultar la ruta de búsqueda precisa del almacén de credenciales.

Si la ruta del sistema de archivos se omite, se elige idéntica al nombre de la credencial, es decir, es una forma abreviada de declarar credenciales para heredar del gestor de servicios o de los directorios de almacén de credenciales en un servicio. Esta opción se puede usar varias veces, definiendo cada vez una credencial adicional para pasar a la unidad.

Tenga en cuenta que si la ruta no se especifica o se da un identificador de credencial válido, es decir, en los dos casos anteriores, una credencial faltante no se considera un error fatal.

Si se especifica una ruta absoluta que se refiere a un directorio, cada archivo en ese directorio (recursivamente) se cargará como una credencial separada. El ID de cada credencial será el ID proporcionado, con el sufijo "_$FILENAME" (por ejemplo, "Key_file1"). Al cargar desde un directorio, se ignorarán los enlaces simbólicos.

El contenido del archivo/socket puede ser datos binarios o textuales arbitrarios, incluidos caracteres de nueva línea y bytes NUL.

La configuración LoadCredentialEncrypted= es idéntica a LoadCredential=, excepto que los datos de la credencial se descifran y autentican antes de pasarse a los procesos ejecutados. Específicamente, la ruta referenciada debe apuntar a un archivo o socket con una credencial cifrada, según lo implementado por systemd-creds(1). Esta credencial se carga, se descifra, se autentica y luego se pasa a la aplicación en texto plano, de la misma manera que lo haría una credencial regular especificada a través de LoadCredential=. Una credencial configurada de esta manera puede cifrarse/autenticarse simétricamente con una clave secreta derivada del chip de seguridad TPM2 del sistema, o con una clave secreta almacenada en /var/lib/systemd/credential.secret, o con ambas. El uso de credenciales cifradas y autenticadas mejora la seguridad ya que las credenciales no se almacenan en texto plano y solo se autentican y descifran a texto plano en el momento en que se inicia un servicio que las requiere. Además, las credenciales pueden vincularse al hardware y las instalaciones locales, de modo que puedan

n no se puede analizar fácilmente sin conexión, o generarse externamente. Consulte systemd.resource-control(5) para obtener detalles sobre DevicePolicy= o DeviceAllow=.

Tenga en cuenta que las credenciales cifradas destinadas a los servicios del administrador de servicios por usuario deben cifrarse con systemd-creds encrypt --user, y las destinadas al administrador de servicios del sistema sin la opción --user. Las credenciales cifradas siempre se dirigen a un usuario específico o al sistema en su conjunto, y se garantiza que los administradores de servicios por usuario no pueden descifrar secretos destinados al sistema o a otros usuarios.

Los archivos/sockets IPC de credenciales deben ser accesibles para el administrador de servicios, pero no tienen que ser directamente accesibles para los procesos de la unidad: los datos de las credenciales se leen y se copian en copias separadas y de solo lectura para la unidad, que son accesibles para los procesos con los privilegios adecuados. Esto es particularmente útil en combinación con DynamicUser=, ya que de esta manera los datos privilegiados se pueden poner a disposición de los procesos que se ejecutan bajo una UID dinámica (es decir, no una previamente conocida) sin tener que abrir el acceso a todos los usuarios.

Para hacer referencia a la ruta desde la que se puede leer una credencial dentro de una línea de comando ExecStart=, utilice "${CREDENTIALS_DIRECTORY}/mycred", por ejemplo, "ExecStart=cat ${CREDENTIALS_DIRECTORY}/mycred". Para hacer referencia a la ruta desde la que se puede leer una credencial dentro de una línea Environment=, utilice "%d/mycred", por ejemplo, "Environment=MYCREDPATH=%d/mycred". Para servicios del sistema, la ruta también se puede referenciar como "/run/credentials/NOMBRE_DE_UNIDAD" en los casos en que no sea posible la interpolación, por ejemplo, en archivos de configuración de software que aún no admiten credenciales de forma nativa. Sin embargo, $CREDENTIALS_DIRECTORY se considera la interfaz principal para buscar credenciales, ya que también funciona para servicios de usuario.

Actualmente, se aplica un límite acumulado de tamaño de credencial de 1 MB por unidad.

El propio administrador de servicios puede recibir credenciales del sistema que se pueden propagar a los servicios desde un administrador de contenedores huésped o un hipervisor de VM. Consulte la documentación de la Interfaz de Contenedores[21] para obtener detalles sobre la primera. Para esta última, pase las entradas de la tabla de cadenas OEM de DMI/SMBIOS[22] (tipo de campo 11) con un prefijo de "io.systemd.credential:" o "io.systemd.credential.binary:". En ambos casos, se espera un par clave/valor separado por "=". En este último caso, el lado derecho se decodifica Base64 al analizarlo (lo que permite pasar datos binarios). Ejemplo de opción de qemu[23]: "-smbios type=11,value=io.systemd.credential:xx=yy", o "-smbios type=11,value=io.systemd.credential.binary:rick=TmV2ZXIgR29ubmEgR2l2ZSBZb3UgVXA=". Alternativamente, utilice el nodo "fw_cfg" de qemu "opt/io.systemd.credentials/". Ejemplo de opción de qemu: "-fw_cfg name=opt/io.systemd.credentials/mycred,string=supersecret". También se pueden pasar desde el entorno de firmware UEFI a través de systemd-stub(7), desde initrd (ver systemd(1)), o especificarse en la línea de comandos del kernel utilizando las opciones "systemd.set_credential=" y "systemd.set_credential_binary=" (ver systemd(1) – esto no se recomienda ya que los usuarios sin privilegios pueden leer la línea de comandos del kernel).

Si se hace referencia a un socket de flujo AF_UNIX para conectarse, la conexión se originará en un socket de espacio de nombres abstracto, que incluye información sobre la unidad y el ID de la credencial en su nombre de socket. Utilice getpeername(2) para consultar esta información. El nombre del socket devuelto tiene el formato NUL ALEATORIO "/unit/" UNIDAD "/" ID, es decir, un byte NUL (según lo requerido para los nombres de sockets de espacio de nombres abstractos), seguido de una cadena aleatoria (que consta de caracteres alfanuméricos), seguido de la cadena literal "/unit/", seguido del nombre de la unidad que solicita, seguido del carácter literal "/", seguido del ID de credencial textual solicitado. Ejemplo: "\0adf9d86b6eda275e/unit/foobar.service/credx" en caso de que la credencial "credx" se solicite para una unidad "foobar.service". Esta funcionalidad es útil para utilizar un único socket de escucha para servir credenciales a múltiples consumidores.

Para más información, consulte la documentación de Credenciales del Sistema y del Servicio[24].

ImportCredential=GLOB

Pasa una o más credenciales a la unidad. Toma un nombre de credencial para el cual intentaremos encontrar una credencial que el administrador de servicios recibió bajo el nombre especificado — que puede ser utilizado para propagar credenciales desde un entorno invocador (por ejemplo, un administrador de contenedores que invocó al administrador de servicios) a un servicio. Si el nombre de la credencial es un glob, todas las credenciales que coincidan con el glob se pasan a la unidad. Las credenciales coincidentes se buscan en las credenciales del sistema, las credenciales cifradas del sistema y en /etc/credstore/, /run/credstore/, /usr/lib/credstore/, /run/credstore.encrypted/, /etc/credstore.encrypted/, y /usr/lib/credstore.encrypted/ en ese orden. Cuando se encuentran múltiples credenciales del mismo nombre, se utiliza la primera encontrada.

La expresión de globbing implementa un subconjunto restrictivo de glob(7): solo se puede especificar un único comodín de asterisco final. No se permiten los comodines "?" ni "[]", ni tampoco comodines "*" en ningún lugar excepto al final de la expresión de glob.

Opcionalmente, al nombre de la credencial o al glob se le puede seguir dos puntos y un patrón de renombrado. Si se especifica, todas las credenciales que coincidan con el nombre de la credencial o el glob se renombran según el patrón dado. Por ejemplo, si se especifica "ImportCredential=my.original.cred:my.renamed.cred", el administrador de servicios leerá la credencial "my.original.cred" y la pondrá a disposición como la credencial "my.renamed.cred" para el servicio. Del mismo modo, si se especifica "ImportCredential=my.original.*:my.renamed.", el administrador de servicios leerá todas las credenciales que comiencen con "my.original." y las pondrá a disposición como "my.renamed.xxx" para el servicio.

Si se especifica ImportCredential= varias veces y múltiples credenciales terminan con el mismo nombre después de renombrarlas, se conserva la primera y se descartan las posteriores.

Cuando se encuentran múltiples credenciales del mismo nombre, las credenciales encontradas por LoadCredential= y LoadCredentialEncrypted= tienen prioridad sobre las credenciales encontradas por ImportCredential=.

Tenga en cuenta que si el descifrado o la autenticación de una credencial seleccionada como resultado de ImportCredential= fallan, se omitirá graciosamente (se generará una advertencia, pero la credencial no se pondrá a disposición del servicio invocado). Esto es diferente para las configuradas a través de SetCredentialEncrypted=/LoadCredentialEncrypted=, donde el descifrado/autenticación fallido resultará en un fallo del servicio.

VARIABLES DE ENTORNO EN PROCESOS DESPLEGADOS

Los procesos iniciados por el administrador de servicios se ejecutan con un bloque de variables de entorno ensamblado a partir de múltiples

Los procesos iniciados por el gestor de servicios del sistema generalmente no heredan las variables de entorno establecidas para el propio gestor de servicios (pero esto puede modificarse mediante PassEnvironment=), pero los procesos iniciados por las instancias del gestor de servicios del usuario generalmente heredan todas las variables de entorno establecidas para el propio gestor de servicios.

Para cada proceso invocado, la lista de variables de entorno establecidas se compila de las siguientes fuentes:

•Variables configuradas globalmente para el gestor de servicios, utilizando el ajuste DefaultEnvironment= en systemd-system.conf(5), la opción de línea de comandos del kernel systemd.setenv= entendida por systemd(1), o mediante el verbo set-environment de systemctl(1).
•Variables definidas por el propio gestor de servicios (ver la lista a continuación).
•Variables establecidas en el propio bloque de variables de entorno del gestor de servicios (sujeto a PassEnvironment= para el gestor de servicios del sistema).
•Variables establecidas mediante Environment= en el archivo de unidad.
•Variables leídas de los archivos especificados mediante EnvironmentFile= en el archivo de unidad.
•Variables establecidas por los módulos PAM en caso de que PAMName= esté en vigor, cf. pam_env(8).

Si la misma variable de entorno se establece por múltiples de estas fuentes, la última fuente —según el orden de la lista anterior— gana. Tenga en cuenta que como último paso, todas las variables listadas en UnsetEnvironment= se eliminan de la lista de variables de entorno compilada, inmediatamente antes de que se pase al proceso ejecutado.

La filosofía general es exponer una lista pequeña y seleccionada de variables de entorno a los procesos. Los servicios iniciados por el gestor del sistema (PID 1) se iniciarán, sin configuración adicional específica del servicio, solo con unas pocas variables de entorno. El gestor de usuarios hereda variables de entorno como cualquier otro servicio del sistema, pero además puede recibir variables de entorno adicionales de PAM y, típicamente, variables adicionales importadas cuando el usuario inicia una sesión gráfica. Se recomienda mantener los bloques de entorno en los gestores del sistema y del usuario concisos. Se desaconseja encarecidamente importar todas las variables heredadas de la sesión gráfica o de una de las shells del usuario.

Indicación: systemd-run -P env y systemd-run --user -P env imprimen los bloques de entorno de servicios efectivos del sistema y del usuario.

Variables de entorno establecidas o propagadas por el gestor de servicios

Las siguientes variables de entorno son propagadas por el gestor de servicios o generadas internamente para cada proceso invocado:

Lista de directorios separados por dos puntos para usar al lanzar ejecutables. systemd utiliza un valor fijo de "/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin" en el gestor del sistema. En el caso del gestor de usuarios, la distribución puede configurar una ruta diferente. Se recomienda no depender del orden de las entradas y tener solo un programa con un nombre dado en $PATH.

$JOURNAL_STREAM

Si la salida estándar o la salida de error estándar de los procesos ejecutados se conectan al journal (por ejemplo, estableciendo StandardError=journal), $JOURNAL_STREAM contiene los números de dispositivo e inodo del descriptor de archivo de conexión, formateados en decimal, separados por dos puntos (":"). Esto permite que los procesos invocados detecten de forma segura si su salida estándar o salida de error estándar están conectadas al journal. Los números de dispositivo e inodo de los descriptores de archivo deben compararse con los valores establecidos en la variable de entorno para determinar si la salida del proceso todavía está conectada al journal. Tenga en cuenta que generalmente no es suficiente verificar si $JOURNAL_STREAM está establecido en absoluto, ya que los servicios podrían invocar procesos externos reemplazando su salida estándar o salida de error estándar, sin desestablecer la variable de entorno.

Si tanto la salida estándar como la salida de error estándar de los procesos ejecutados están conectadas al journal a través de un socket de flujo, esta variable de entorno contendrá información sobre el flujo de salida de error, ya que suele ser el destino preferido para los datos de registro. (Tenga en cuenta que normalmente se utiliza el mismo flujo para la salida estándar y la salida de error estándar, por lo que es muy probable que la variable de entorno contenga información de dispositivo e inodo que coincida con ambos descriptores de archivo de flujo).

Esta variable de entorno es principalmente útil para permitir que los servicios actualicen opcionalmente su protocolo de registro utilizado al protocolo nativo del journal (utilizando sd_journal_print(3) y otras funciones) si su salida estándar o salida de error estándar están conectadas al journal de todos modos, permitiendo así la entrega de metadatos estructurados junto con los mensajes registrados.

systemd.exec(5) — Arch Linux

NOMBRE

systemd.exec — Límites y configuración de ejecución de procesos

SINOPSIS

/etc/systemd/system.conf, /run/systemd/system.conf, /usr/lib/systemd/system.conf, ~/.config/systemd/user.conf, /etc/systemd/user.conf, /run/systemd/user.conf, /usr/lib/systemd/user.conf

DESCRIPCIÓN

El archivo systemd.exec se utiliza para configurar los límites de recursos y otras opciones de seguridad para todos los procesos iniciados por systemd.

Estos archivos definen directivas que controlan cómo se ejecutan los procesos, incluyendo restricciones de recursos, variables de entorno y códigos de salida.

DIRECTIVAS

Las siguientes directivas se pueden utilizar en los archivos de configuración:

  • CPUQuota=: Limita el uso de CPU.
  • IOWeight=: Establece el peso de I/O.
  • MemoryLimit=: Limita el uso de memoria.
  • LimitAS=, LimitRSS=, LimitDATA=, etc.: Establece límites de recursos del sistema (ver setrlimit(2)).
  • User=, Group=: Establece el usuario y grupo bajo los cuales se ejecutarán los procesos.
  • SupplementaryGroups=: Establece grupos suplementarios.
  • Environment=: Establece variables de entorno.
  • PasswdChangeMax=: Límite máximo de cambios de contraseña.
  • PermissionsStartOnly=: Permite iniciar el servicio solo si los permisos son correctos.
  • PrivateTmp=: Crea un espacio de nombres de montaje temporal privado para el proceso.
  • ProtectSystem=: Protege el sistema de archivos del sistema.
  • ProtectHome=: Protege los directorios del usuario.
  • NoNewPrivileges=: Evita que el proceso obtenga nuevos privilegios.
  • CapabilityBoundingSet=: Limita las capacidades del kernel.
  • DevicePolicy=: Controla el acceso a dispositivos.
  • SystemCallFilter=: Filtra las llamadas al sistema.
  • SystemCallArchitectures=: Especifica las arquitecturas de llamadas al sistema permitidas.

COMPATIBILIDAD CON SYSTEM V

systemd proporciona compatibilidad con System V en cuanto a la gestión de servicios y el inicio de procesos.

VARIABLES DE ENTORNO EN PROCESOS INICIADOS

Las variables de entorno se pueden configurar explícitamente utilizando la directiva Environment=. De lo contrario, los procesos heredan el entorno del proceso padre (systemd).

CÓDIGOS DE SALIDA DE PROCESOS

Los códigos de salida de los procesos se manejan de acuerdo con las convenciones estándar de Unix. systemd puede interpretar ciertos códigos de salida para determinar si un servicio debe reiniciarse.

EJEMPLOS

Un ejemplo de archivo systemd.exec podría verse así:


CPUQuota=50%
MemoryLimit=1G
User=nobody
Group=nogroup
ProtectSystem=full
NoNewPrivileges=true

VER TAMBIÉN

systemd.service(5), systemd.scope(5), systemd.slice(5), systemd.conf(5), setrlimit(2)

NOTAS

Las configuraciones aplicadas a través de systemd.exec afectan a todos los procesos gestionados por systemd, a menos que se anulen en archivos de unidad específicos (como .service, .scope, etc.).
