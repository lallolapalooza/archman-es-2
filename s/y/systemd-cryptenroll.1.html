NOMBRE

systemd-cryptenroll - Inscribir token/dispositivos PKCS#11, FIDO2, TPM2 en volúmenes encriptados LUKS2

SINOPSIS

systemd-cryptenroll [OPCIONES...] [DISPOSITIVO]

DESCRIPCIÓN

systemd-cryptenroll es una herramienta para inscribir tokens y dispositivos de seguridad de hardware en un volumen encriptado LUKS2, que puede ser utilizado para desbloquear el volumen durante el arranque. Específicamente, admite tokens y credenciales de los siguientes tipos para ser inscritos:

1. Tokens de seguridad y tarjetas inteligentes PKCS#11 que pueden contener un par de claves RSA o EC (por ejemplo, varias YubiKeys)
2. Tokens de seguridad FIDO2 que implementan la extensión "hmac-secret" (la mayoría de las claves FIDO2, incluidas las YubiKeys)
3. Dispositivos de seguridad TPM2
4. Frases de contraseña normales
5. Claves de recuperación. Estas son similares a las frases de contraseña normales, sin embargo, se generan aleatoriamente en el ordenador y, por lo tanto, generalmente tienen mayor entropía que las frases de contraseña elegidas por el usuario. Su conjunto de caracteres ha sido diseñado para garantizar que sean fáciles de escribir, al tiempo que tienen alta entropía. También pueden ser escaneadas fuera de la pantalla usando códigos QR. Las claves de recuperación pueden ser utilizadas para desbloquear volúmenes LUKS2 donde se aceptan frases de contraseña. Están destinadas a ser utilizadas en combinación con un token de seguridad de hardware inscrito, como opción de recuperación cuando se pierde el token.

Además, la herramienta puede ser utilizada para enumerar los tokens de seguridad actualmente inscritos y borrar un subconjunto de ellos. Esto último puede combinarse con la operación de inscripción de un nuevo token de seguridad, para actualizar o reemplazar inscripciones.

La herramienta solo admite volúmenes LUKS2, ya que almacena metadatos del token en el área de token JSON de LUKS2, que no está disponible en otros formatos de encriptación.

systemd-cryptsetup opera en el dispositivo de respaldo de /var/ si no se especifica ningún dispositivo explícitamente, y no se solicita ninguna operación de borrado. (Tenga en cuenta que en el caso típico donde /var/ está en el mismo sistema de archivos que el sistema de archivos raíz, esto inscribe una clave en el dispositivo de respaldo del sistema de archivos raíz).

PCRs y políticas de TPM2

Los PCRs permiten la vinculación de la encriptación de secretos a versiones de software y estados del sistema específicos, de modo que la clave inscrita solo sea accesible (pueda ser "desvelada") si se utiliza software y/o configuración confiables específicos. Dichas vinculaciones pueden ser creadas con la opción --tpm2-pcrs= descrita a continuación.

Los secretos también pueden vincularse indirectamente: se proporciona una política firmada para un estado de alguna combinación de valores PCR, y el secreto se vincula a la parte pública de la clave utilizada para firmar esta política. Esto significa que el propietario de una clave puede generar una secuencia de políticas firmadas, para versiones de software y estados del sistema específicos, y el secreto puede ser descifrado siempre que el estado de la máquina coincida con una de esas políticas. Por ejemplo, un proveedor puede proporcionar dicha política para cada actualización de kernel+initrd, permitiendo a los usuarios encriptar secretos para que puedan ser descifrados cuando ejecuten cualquier kernel+initrd firmado por el proveedor. Dichas vinculaciones pueden ser creadas con las opciones --tpm2-public-key=, --tpm2-public-key-pcrs=, --tpm2-signature= descritas a continuación.

Consulte el Registro de PCRs de TPM de Linux[1] para obtener una lista autorizada de PCRs y cómo se actualizan. La siguiente tabla contiene una referencia rápida, que describe en particular los PCRs modificados por systemd.

En general, los volúmenes encriptados se vincularían a alguna combinación de los PCRs 7, 11 y 14 (si se utiliza shim/MOK). Para permitir las actualizaciones de firmware y versiones del sistema operativo, generalmente no es aconsejable utilizar PCRs como 0 y 2, ya que el código del programa que cubren ya está cubierto indirectamente a través de los certificados medidos en el PCR 7. La validación a través de hashes de certificados es típicamente preferible a la validación a través de mediciones directas, ya que es menos frágil en el contexto de actualizaciones del sistema operativo/firmware: las mediciones cambiarán en cada actualización, pero las firmas deberían permanecer sin cambios. LIMITACIONES

Tenga en cuenta que actualmente, al inscribir una nueva clave de uno de los cinco tipos admitidos mencionados anteriormente, se requiere primero proporcionar una frase de contraseña, una clave de recuperación, un token FIDO2 o una clave TPM2. Actualmente no se admite desbloquear un dispositivo con una clave PKCS#11 para inscribir una nueva clave PKCS#11. Por lo tanto, si en el futuro se desea un cambio de clave, generalmente se recomienda asegurarse de que siempre se inscriba una frase de contraseña, una clave de recuperación, un token FIDO2 o una clave TPM2.

Tenga también en cuenta que el soporte para inscribir múltiples tokens FIDO2 es actualmente limitado. Cuando se inscriben múltiples tokens FIDO2, systemd-cryptsetup realizará solicitudes de pre-vuelo para intentar identificar cuáles de los tokens inscritos están actualmente conectados. ENROLLMENT DE RECUPERACIÓN

Las siguientes opciones se entienden que pueden ser utilizadas para inscribir información de recuperación:

--recovery-key

Inscribe una clave de recuperación. Las claves de recuperación son casi idénticas a las contraseñas, pero son generadas por computadora en lugar de ser elegidas por un humano, y por lo tanto tienen una alta entropía garantizada. La clave utiliza un conjunto de caracteres que es fácil de escribir y puede ser escaneada desde la pantalla a través de un código QR.

Añadido en la versión 248.

ENLACE_TPM2

Las siguientes opciones se entienden que pueden ser utilizadas para enlazar el dispositivo TPM2:

--tpm2-device=RUTA

Enlaza un chip TPM2. Espera una ruta de nodo de dispositivo que se refiera al chip TPM2 (por ejemplo, /dev/tpmrm0). Alternativamente, se puede especificar el valor especial "auto", para determinar automáticamente el nodo del dispositivo de un dispositivo TPM2 descubierto actualmente (del cual debe haber exactamente uno). El valor especial "list" se puede utilizar para enumerar todos los dispositivos TPM2 adecuados descubiertos actualmente.

Para desbloquear un volumen LUKS2 con un chip TPM2 enlazado, especifique la opción tpm2-device= en la línea /etc/crypttab correspondiente:

myvolume /dev/sda1 none tpm2-device=auto

Consulte crypttab(5) para un ejemplo más completo de una invocación de systemd-cryptenroll y su línea /etc/crypttab correspondiente.

Añadido en la versión 256.

--tpm2-allow-signing=BOOLEANO

Cuando se enlaza un dispositivo TPM2, controla si se permite la firma para la desprotección. Por defecto es "yes". Si se establece en "no", la desprotección solo puede realizarse mediante un código de acceso o una clave de recuperación. Si se establece en "yes", la desprotección puede realizarse utilizando la clave de firma del TPM2, junto con el código de acceso opcional.

Añadido en la versión 256.

--tpm2-with-pin=BOOLEANO

Cuando se enlaza un dispositivo TPM2, controla si se requiere que el usuario introduzca un PIN para desproteger el volumen (la función TPM2 "PIN de cliente"). Por defecto es "yes". (Nota: esta configuración no tiene efecto si el chip TPM2 no admite la función "PIN de cliente" en absoluto, o no permite habilitarla o deshabilitarla).

Añadido en la versión 256.

--tpm2-with-pinch-policy=BOOLEANO

Cuando se enlaza un dispositivo TPM2, controla si se requiere que el usuario confirme la presencia (presionando el chip TPM2, la función TPM2 "política de pellizco") al desproteger el volumen. Por defecto es "yes". (Nota: esta configuración no tiene efecto si el chip TPM2 no admite la función "política de pellizco" en absoluto, o no permite habilitarla o deshabilitarla).

Añadido en la versión 256.

--tpm2-with-user-verification=BOOLEANO

Cuando se enlaza un dispositivo TPM2, controla si se requiere verificación del usuario al desproteger el volumen (la función TPM2 "verificación del usuario"). Por defecto es "no". (Nota: esta configuración no tiene efecto si el chip TPM2 no admite la función "verificación del usuario" en absoluto, o no permite habilitarla o deshabilitarla).

Añadido en la versión 256.

LIMITACIONES

Si se utilizan varios tokens (por ejemplo, un token de hardware y un escaneo de huellas dactilares, o un token de hardware y un PIN), solo el primer token se utilizará como método de desbloqueo principal. Los tokens subsiguientes solo se intentarán si el desbloqueo principal falla (por ejemplo, si el dispositivo biométrico no funciona, en cuyo caso se recurrirá a intentar cada token inscrito uno por uno). Esto resultará en múltiples solicitudes de PIN y verificación del usuario. Esta limitación no se aplica a los tokens PKCS#11.

COMPATIBILIDAD

La tecnología de seguridad tanto en systemd como en la industria en general evoluciona constantemente. Para proporcionar las mejores garantías de seguridad, la forma en que se inscriben los dispositivos TPM2, FIDO2 y PKCS#11 se actualiza regularmente en versiones más recientes de systemd. Siempre que esto ocurra, se dan las siguientes garantías de compatibilidad:

•Las inscripciones antiguas siguen siendo compatibles y pueden desbloquearse con versiones más recientes de systemd-cryptsetup@.service(8).
•Lo contrario no está garantizado; sin embargo, es posible que no sea posible desbloquear volúmenes con inscripciones hechas con una versión más reciente de systemd-cryptenroll con una versión anterior de systemd-cryptsetup.

Dicho esto, generalmente se recomienda utilizar versiones coincidentes de systemd-cryptenroll y systemd-cryptsetup, ya que esto está mejor probado y soportado.

Podría ser aconsejable volver a inscribir las inscripciones existentes para beneficiarse de las nuevas características de seguridad, a medida que se añaden a systemd.

Se comprenden las siguientes opciones que pueden utilizarse para desbloquear el dispositivo en preparación de las operaciones de inscripción:

--unlock-key-file=RUTA

Utilice un archivo en lugar de una contraseña/frase de contraseña leída desde stdin para desbloquear el volumen. Espera la RUTA del archivo que contiene su clave para desbloquear el volumen. Actualmente no hay nada como --key-file-offset= o --key-file-size=, por lo que este archivo solo debe contener la clave completa.

Tenga en cuenta que actualmente los dispositivos FIDO2 inscritos sin un token LUKS2 acompañante (es decir, --fido2-parameters-in-header=no) no se pueden utilizar para desbloquear.

Alternativamente, se puede especificar el valor especial "auto", para determinar automáticamente el nodo del dispositivo de un dispositivo TPM2 descubierto actualmente (del cual debe haber exactamente uno).

INSCRIPCIÓN_PKCS#11

La siguiente opción se entiende que puede ser utilizada para inscribir tokens PKCS#11:

--pkcs11-token-uri=URI

Inscribe un token de seguridad PKCS#11 o tarjeta inteligente (por ejemplo, una YubiKey). Espera una URI PKCS#11 que permita encontrar un certificado X.509 o una clave pública en el token. La URI también debe ser adecuada para encontrar una clave privada relacionada después de cambiar el tipo de objeto en ella. Alternativamente, se puede especificar el valor especial "auto", para determinar automáticamente la URI adecuada si se conecta un único token de seguridad que contiene un único par de claves. El valor especial "list" se puede utilizar para enumerar todos los tokens PKCS#11 adecuados actualmente conectados.

El token PKCS#11 debe contener un par de claves RSA o EC que se utilizará para desbloquear un volumen LUKS2. Para RSA, una clave de volumen generada aleatoriamente se cifra con una clave pública en el token y se almacena en el área de encabezado del token JSON de LUKS2. Para desbloquear un volumen, la clave de volumen cifrada almacenada se descifrará con una clave privada en el token. Para ECC, se utiliza el algoritmo ECDH: generamos un par de claves EC en el mismo grupo EC, luego derivamos un secreto compartido utilizando la clave privada generada y la clave pública en el token. El secreto compartido derivado se utiliza como clave de volumen. La clave pública generada se almacena en el área de encabezado del token JSON de LUKS2. La clave privada generada se borra. Para desbloquear un volumen, derivamos el secreto compartido con la clave pública almacenada y una clave privada en el token.

Para desbloquear un volumen LUKS2 con un token de seguridad PKCS#11 inscrito, especifique la opción pkcs11-uri= en la línea /etc/crypttab correspondiente:

myvolume /dev/sda1 none pkcs11-uri=auto

Consulte crypttab(5) para un ejemplo más completo de una invocación de systemd-cryptenroll y su línea /etc/crypttab correspondiente.

Añadido en la versión 248.

INSCRIPCIÓN_FIDO2

Las siguientes opciones se entienden que pueden ser utilizadas para inscribir tokens FIDO2:

--fido2-device=RUTA

Inscribe un token de seguridad FIDO2 que implementa la extensión "hmac-secret" (por ejemplo, una YubiKey). Espera un dispositivo hidraw que se refiera al dispositivo FIDO2 (por ejemplo, /dev/hidraw1). El valor especial "list" se puede utilizar para enumerar todos los tokens FIDO2 adecuados actualmente conectados. Tenga en cuenta que muchos tokens de seguridad de hardware que implementan FIDO2 también implementan el estándar PKCS#11 más antiguo. Típicamente, FIDO2 es preferible, dado que es más simple de usar y más moderno.

Para desbloquear un volumen LUKS2 con un token de seguridad FIDO2 inscrito, especifique la opción fido2-device= en la línea /etc/crypttab correspondiente:

myvolume /dev/sda1 none fido2-device=auto

Consulte crypttab(5) para un ejemplo más completo de una invocación de systemd-cryptenroll y su línea /etc/crypttab correspondiente.

Añadido en la versión 248.

--fido2-credential-algorithm=CADENA

Especifica el algoritmo COSE utilizado en la generación de credenciales. El valor predeterminado es "es256". Los valores soportados son "es256", "rs256" y "eddsa".

"es256" denota ECDSA sobre NIST P-256 con SHA-256. "rs256" denota RSA de 2048 bits con relleno PKCS#1.5 y SHA-256. "eddsa" denota EDDSA sobre Curve25519 con SHA-512.

Tenga en cuenta que su autenticador puede optar por no admitir algunos algoritmos.

Añadido en la versión 251.

Si se establece en "no", la opción fido2-cid= debe especificarse manualmente en la línea /etc/crypttab correspondiente junto con un archivo de clave. Consulte crypttab(5) para más detalles.

--tpm2-device-key=PATH

Registre un chip de seguridad TPM2 utilizando su clave pública. Espera una ruta que haga referencia a la clave pública TPM2 en formato TPM2B_PUBLIC. Esto no se puede usar con --tpm2-device=, ya que realiza la misma operación, pero sin conectarse al chip de seguridad TPM2; en su lugar, el registro se calcula utilizando la clave TPM2 proporcionada. Esto es útil en situaciones en las que el chip de seguridad TPM2 no está disponible en el momento del registro.

La clave, en la mayoría de los casos, debe ser la Clave Raíz de Almacenamiento (SRK) de un chip de seguridad TPM2 local. Si se utiliza una clave de otro identificador (no la SRK), debe especificar su índice de identificador utilizando --tpm2-seal-key-handle=.

El servicio systemd-tpm2-setup.service(8) escribe la SRK en /run/systemd/tpm2-srk-public-key.tpm2b_public automáticamente durante el arranque, en el formato correcto.

Alternativamente, puede utilizar systemd-analyze srk para recuperar explícitamente la SRK del chip de seguridad TPM2. Consulte systemd-analyze(1) para obtener detalles. Ejemplo:

systemd-analyze srk > srk.tpm2b_public

Añadido en la versión 255.

--tpm2-seal-key-handle=HANDLE

Configura la clave principal que se utilizará para sellar, utilizando el identificador (índice) de la clave TPM. Esto se utiliza para "sellar" (cifrar) un secreto y debe utilizarse más tarde para "desellar" (descifrar) el secreto. Espera un entero de 32 bits hexadecimal, opcionalmente prefijado con "0x". Los valores permitidos son cualquier índice de identificador en los rangos persistente ("0x81000000"-"0x81ffffff") o transitorio ("0x80000000"-"0x80ffffff"). Dado que los identificadores transitorios se pierden después de un reinicio de TPM y pueden ser eliminados durante el cambio de contexto de TPM, no deben utilizarse excepto para casos de uso muy específicos, por ejemplo, pruebas.

El valor predeterminado es el índice del identificador de la Clave Raíz de Almacenamiento (SRK) "0x81000001". Un valor de 0 utilizará el valor predeterminado. Para el identificador de SRK, se creará una nueva clave y se almacenará en el TPM si aún no existe; para cualquier otro identificador, la clave ya debe existir en el TPM en el índice de identificador especificado.

Esto no debe cambiarse a menos que sepa lo que está haciendo.

Añadido en la versión 255.

--tpm2-pcrs=PCR[+PCR...]

Configura los PCR (Registros de Configuración de Plataforma) de TPM2 a los que vincularse cuando se solicita el registro a través de --tpm2-device=. Toma una lista de entradas de PCR, donde cada entrada comienza con un nombre o índice numérico en el rango 0...23, seguido opcionalmente por ":" y un nombre de algoritmo hash (especificando el banco de PCR), seguido opcionalmente por "=" y un valor de resumen hash. Múltiples entradas de PCR están separadas por "+". Si se especifica una cadena vacía, vincula el registro a ningún PCR (este es también el valor predeterminado, si no se utiliza esta opción). Consulte la tabla anterior para obtener una lista de los PCR disponibles.

Ejemplo: --tpm2-pcrs=boot-loader-code+platform-config+boot-loader-config especifica que se deben usar los registros de PCR 4, 1 y 5.

Ejemplo: --tpm2-pcrs=7:sha256 especifica que se debe usar el registro de PCR 7 del banco SHA256.

Ejemplo: --tpm2-pcrs=4:sha1=3a3f780f11a4b49969fcaa80cd6e3957c33b2275 especifica que se debe usar el registro de PCR 4 del banco SHA1, y se utilizará un valor de resumen hash de 3a3f780f11a4b49969fcaa80cd6e3957c33b2275 en lugar de leer el valor actual del PCR.

Añadido en la versión 248.

--tpm2-with-pin=BOOL

Al registrar un dispositivo TPM2, controla si se requiere que el usuario ingrese un PIN al desbloquear el volumen además de la vinculación de PCR, basándose en la autenticación de la política TPM2. El valor predeterminado es "no". A pesar de llamarse PIN, se puede usar cualquier carácter, no solo números.

Tenga en cuenta que la entrada incorrecta del PIN al desbloquear incrementa el mecanismo de bloqueo por ataque de diccionario de TPM y puede bloquear a los usuarios durante un tiempo prolongado, dependiendo de su configuración. El mecanismo de bloqueo es una propiedad global del TPM, systemd-cryptenroll no controla ni configura el mecanismo de bloqueo. Puede utilizar herramientas de tpm2-tss para inspeccionar o configurar el bloqueo por ataque de diccionario, con los comandos tpm2_getcap(1) y tpm2_dictionarylockout(1), respectivamente.

Añadido en la versión 251.

--tpm2-public-key=PATH, --tpm2-public-key-pcrs=PCR[+PCR...], --tpm2-signature=PATH

Configura una política de PCR firmada por TPM2 para vincular el cifrado. La opción --tpm2-public-key= acepta una ruta a una clave pública RSA codificada en PEM, para vincular el cifrado. Si no se especifica explícitamente, pero existe un archivo tpm2-pcr-public-key.pem en uno de los directorios /etc/systemd/, /run/systemd/, /usr/lib/systemd/ (buscados en este orden), se utiliza automáticamente. La opción --tpm2-public-key-pcrs= toma una lista de índices de PCR de TPM2 a los que vincularse (misma sintaxis que --tpm2-pcrs= descrita anteriormente). Si no se especifica, el valor predeterminado es 11 (es decir, esto vincula la política a cualquier imagen de kernel unificada para la que se pueda proporcionar una firma de PCR).

Tenga en cuenta la diferencia entre --tpm2-pcrs= y --tpm2-public-key-pcrs=: el primero vincula el descifrado a los valores actuales y específicos de PCR; el segundo vincula el descifrado a cualquier conjunto de valores de PCR para los que se pueda proporcionar una firma de la clave pública especificada. El segundo es, por lo tanto, más útil en escenarios donde las actualizaciones de software deben ser posibles sin perder el acceso a todos los volúmenes LUKS2 cifrados anteriormente. Al igual que con --tpm2-pcrs=, los nombres definidos en la tabla anterior también se pueden utilizar para especificar los registros, por ejemplo --tpm2-public-key-pcrs=boot-loader-code+system-identity.

La opción --tpm2-signature= toma una ruta a un archivo de firma de PCR de TPM2 generado por la herramienta systemd-measure(1). Si no se especifica explícitamente, se busca y utiliza un archivo de firma adecuado tpm2-pcr-signature.json en /etc/systemd/, /run/systemd/, /usr/lib/systemd/ (en este orden). Si se especifica o se encuentra un archivo de firma, se utiliza para verificar si el volumen se puede desbloquear con él dado el estado actual de PCR, antes de que se escriba la nueva ranura en el disco. Esto está destinado como una red de seguridad para garantizar que no se pierda el acceso a un volumen si se registra una clave pública para la cual no hay una firma válida para el estado actual de PCR disponible. Si la firma proporcionada no desbloquea la combinación actual de estado de PCR y clave pública, no se registra ninguna ranura y la operación fallará. Si no se especifica ni se encuentra ningún archivo de firma, no se realiza ninguna verificación de seguridad.

Añadido en la versión 252.

--tpm2-pcrlock=PATH

Configura una política de pcrlock de TPM2 para vincular el cifrado. Espera una ruta a un archivo de política de pcrlock generado por la herramienta systemd-pcrlock(8). Si se registra un dispositivo TPM2 y no se utiliza esta opción, pero se encuentra un archivo pcrlock.json en /run/systemd/ o /var/lib/systemd/, se utiliza automáticamente. Asigne una cadena vacía para desactivar este comportamiento.

Añadido en la versión 255.

OTRAS OPCIONES

Se entienden las siguientes opciones adicionales:

--wipe-slot=SLOT[,SLOT...]

Borra una o más ranuras de claves LUKS2. Toma una lista separada por comas de índices de ranuras numéricas, o las cadenas especiales "all" (para borrar todas las ranuras de claves), "empty" (para borrar todas las ranuras de claves que se desbloquean con una contraseña vacía), "password" (para borrar todas las ranuras de claves que se desbloquean con una contraseña tradicional), "recovery" (para borrar todas las ranuras de claves que se desbloquean con una clave de recuperación), "pkcs11" (para borrar todas las ranuras de claves que se desbloquean con un token PKCS#11), "fido2" (para borrar todas las ranuras de claves que se desbloquean con un token FIDO2), "tpm2" (para borrar todas las ranuras de claves que se desbloquean con un chip TPM2), o cualquier combinación de estas cadenas o índices numéricos, en cuyo caso se borran todas las ranuras que coinciden. Como medida de seguridad, se rechaza una operación que borra todas las ranuras sin excepción (de modo que el volumen ya no se puede desbloquear, a menos que se conozca la clave del volumen).

Este interruptor se puede usar solo, en cuyo caso solo se ejecuta la operación de borrado solicitada. También se puede usar en combinación con cualquiera de las opciones de registro enumeradas anteriormente, en cuyo caso el registro se completa primero, y solo cuando tiene éxito se ejecuta la operación de borrado, y la ranura recién agregada siempre se excluye del borrado. Combinar registro y borrado de ranuras puede usarse así para actualizar registros existentes:

systemd-cryptenroll /dev/sda1 --wipe-slot=tpm2 --tpm2-device=auto --unlock-tpm2-device=auto

El comando anterior registrará el chip TPM2 y luego borrará todos los registros TPM2 creados previamente en el volumen LUKS2, dejando solo el recién creado. Combinar borrado y registro también puede usarse para reemplazar registros de diferentes tipos, por ejemplo, para cambiar de un registro PKCS#11 a uno FIDO2:

systemd-cryptenroll /dev/sda1 --wipe-slot=pkcs11 --fido2-device=auto

O para reemplazar una contraseña vacía registrada por TPM2:

systemd-cryptenroll /dev/sda1 --wipe-slot=empty --tpm2-device=auto

--list-devices

Muestra una lista de dispositivos de bloque candidatos en los que este comando puede operar. Los dispositivos deben implementar la extensión hmac-secret para ser utilizables.
