NOMBRE

systemd-system.conf, system.conf.d, systemd-user.conf, user.conf.d - Archivos de configuración del gestor de servicios del sistema y de la sesión

SINOPSIS

/etc/systemd/system.conf, /run/systemd/system.conf, /usr/lib/systemd/system.conf, /etc/systemd/system.conf.d/*.conf, /run/systemd/system.conf.d/*.conf, /usr/lib/systemd/system.conf.d/*.conf

~/.config/systemd/user.conf, /etc/systemd/user.conf, /run/systemd/user.conf, /usr/lib/systemd/user.conf, /etc/systemd/user.conf.d/*.conf, /run/systemd/user.conf.d/*.conf, /usr/lib/systemd/user.conf.d/*.conf

DESCRIPCIÓN

Cuando se ejecuta como instancia del sistema, systemd interpreta el archivo de configuración system.conf y los archivos en los directorios system.conf.d; cuando se ejecuta como instancia de usuario, interpreta el archivo de configuración user.conf (en orden de prioridad, en el directorio home del usuario y bajo /etc/systemd/, /run/systemd/, y /usr/lib/systemd/) y los archivos en los directorios user.conf.d. Estos archivos de configuración contienen algunas opciones que controlan las operaciones básicas del gestor.

Consulte systemd.syntax(7) para una descripción general de la sintaxis.

DIRECTORIOS DE CONFIGURACIÓN Y PRECEDENCIA

La configuración predeterminada se establece durante la compilación, por lo que la configuración solo es necesaria cuando es preciso desviarse de esos valores predeterminados. El archivo de configuración principal se carga desde uno de los directorios listados en orden de precedencia, solo se utiliza el primer archivo encontrado: /etc/systemd/, /run/systemd/, /usr/local/lib/systemd/ [1], /usr/lib/systemd/. La versión del proveedor del archivo contiene entradas comentadas que muestran los valores predeterminados como guía para el administrador. También se pueden crear anulaciones locales colocando "drop-ins", como se describe a continuación. El archivo de configuración principal también se puede editar para este propósito (o una copia en /etc/ si se distribuye bajo /etc/), sin embargo, se recomienda usar "drop-ins" para la configuración local en lugar de modificaciones al archivo de configuración principal.

Además del archivo de configuración principal, se leen fragmentos de configuración "drop-in" de /usr/lib/systemd/*.conf.d/, /usr/local/lib/systemd/*.conf.d/, y /etc/systemd/*.conf.d/. Estos "drop-ins" tienen mayor precedencia y anulan el archivo de configuración principal. Los archivos en los subdirectorios de configuración *.conf.d/ se ordenan por su nombre de archivo en orden lexicográfico, independientemente de en cuál de los subdirectorios residan. Cuando varios archivos especifican la misma opción, para opciones que aceptan solo un valor, la entrada en el archivo ordenado último tiene precedencia, y para opciones que aceptan una lista de valores, las entradas se recopilan según aparecen en los archivos ordenados.

Cuando los paquetes necesitan personalizar la configuración, pueden instalar "drop-ins" bajo /usr/. Los archivos en /etc/ están reservados para el administrador local, quien puede usar esta lógica para anular los archivos de configuración instalados por los paquetes del proveedor. Los "drop-ins" deben usarse para anular los "drop-ins" de los paquetes, ya que el archivo de configuración principal tiene menor precedencia. Se recomienda prefijar todos los nombres de archivo en estos subdirectorios con un número de dos dígitos y un guion, para simplificar el ordenamiento. Esto también define un concepto de prioridades de "drop-in" para permitir a los proveedores de SO distribuir "drop-ins" dentro de un rango específico inferior al rango utilizado por los usuarios. Esto debería reducir el riesgo de que los "drop-ins" de los paquetes anulen accidentalmente los "drop-ins" definidos por los usuarios. Se recomienda usar el rango 10-40 para los "drop-ins" en /usr/ y el rango 60-90 para los "drop-ins" en /etc/ y /run/, para asegurarse de que los "drop-ins" locales y transitorios tengan prioridad sobre los "drop-ins" distribuidos por el proveedor del SO.

Para deshabilitar un archivo de configuración proporcionado por el proveedor, la forma recomendada es colocar un enlace simbólico a /dev/null en el directorio de configuración en /etc/, con el mismo nombre de archivo que el archivo de configuración del proveedor.

OPCIONES

Todas las opciones se configuran en la sección [Manager]:

LogColor=, LogLevel=, LogLocation=, LogTarget=, LogTime=, DumpCore=yes, CrashChangeVT=no, CrashShell=no, CrashAction=freeze, ShowStatus=yes, DefaultStandardOutput=journal, DefaultStandardError=inherit

Configura varios parámetros de la operación básica del gestor. Estas opciones pueden ser anuladas por los respectivos argumentos del proceso y de la línea de comandos del kernel. Consulte systemd(1) para más detalles.

Añadido en la versión 198.

CtrlAltDelBurstAction=

Define qué acción se realizará si el usuario presiona Ctrl-Alt-Supr más de 7 veces en 2 segundos. Puede configurarse como "reboot-force", "poweroff-force", "reboot-immediate", "poweroff-immediate" o deshabilitarse con "none". Por defecto es "reboot-force".

Añadido en la versión 232.

StatusUnitFormat=

Acepta name, description o combined como valor. Si es name, el gestor del sistema usará nombres de unidad en los mensajes de estado (por ejemplo, "systemd-journald.service"), en lugar de las descripciones más largas y más informativas establecidas con Description= (por ejemplo, "Servicio de registro de Journal"). Si es combined, el gestor del sistema usará tanto los nombres de unidad como las descripciones en los mensajes de estado (por ejemplo, "systemd-journald.service - Servicio de registro de Journal").

Consulte systemd.unit(5) para detalles sobre nombres de unidades y Description=.

Añadido en la versión 243.

DefaultTimerAccuracySec=

Establece la precisión predeterminada de las unidades de temporizador. Esto controla el valor predeterminado global para la configuración AccuracySec= de las unidades de temporizador, consulte systemd.timer(5) para más detalles. AccuracySec= establecido en unidades individuales anula el valor predeterminado global para la unidad específica. Por defecto es 1 minuto. Tenga en cuenta que la precisión de las unidades de temporizador también se ve afectada por el tiempo de espera del temporizador configurado para PID 1, consulte TimerSlackNSec= arriba.

GESTIÓN DE RECURSOS

TimerSlackNSec=

Establece el tiempo de espera del temporizador en nanosegundos para PID 1, que es heredado por todos los procesos ejecutados, a menos que se anule individualmente, por ejemplo, con la configuración TimerSlackNSec= en unidades de servicio (para más detalles, consulte systemd.exec(5)). El tiempo de espera del temporizador controla la precisión de los despertares activados por los temporizadores del sistema. Consulte prctl(2) para más información. Tenga en cuenta que, a diferencia de la mayoría de las otras definiciones de períodos de tiempo, este parámetro acepta un valor entero en nanosegundos si no se especifica una unidad. También se entienden las unidades de tiempo habituales.

DefaultLimitCPU=, DefaultLimitFSIZE=, DefaultLimitDATA=, DefaultLimitSTACK=, DefaultLimitCORE=, DefaultLimitRSS=, DefaultLimitNOFILE=, DefaultLimitAS=, DefaultLimitNPROC=, DefaultLimitMEMLOCK=, DefaultLimitLOCKS=, DefaultLimitSIGPENDING=, DefaultLimitMSGQUEUE=, DefaultLimitNICE=, DefaultLimitRTPRIO=, DefaultLimitRTTIME=

•DefaultLimitMEMLOCK= por defecto es 8M.

HARDWARE WATCHDOG

RuntimeWatchdogSec=, RebootWatchdogSec=, KExecWatchdogSec=

Configura el watchdog de hardware en tiempo de ejecución y al reiniciar. Toma un valor de tiempo de espera en segundos (o en otras unidades de tiempo si se sufija con "ms", "min", "h", "d", "w"), o las cadenas especiales "off" o "default". Si se establece en "off" (alternativamente: "0"), la lógica del watchdog se deshabilita: no se abre, configura ni se hace ping a ningún dispositivo watchdog. Si se establece en la cadena especial "default", se abre y se hace ping al watchdog a intervalos regulares, pero el tiempo de espera no se cambia del valor predeterminado. Si se establece en cualquier otro valor de tiempo, el tiempo de espera del watchdog se configura al valor especificado (o un valor cercano a él, dependiendo de las capacidades del hardware).

Si RuntimeWatchdogSec= se establece en un valor distinto de cero, el hardware watchdog (/dev/watchdog0 o la ruta especificada con WatchdogDevice= o la opción del kernel systemd.watchdog_device=) se programará para reiniciar automáticamente el sistema si no se contacta dentro del intervalo de tiempo de espera especificado. El gestor del sistema se asegurará de contactarlo al menos una vez en la mitad del intervalo de tiempo de espera especificado. Esta función requiere un dispositivo hardware watchdog presente, como suele ocurrir en sistemas integrados y de servidor. No todos los watchdogs de hardware permiten la configuración de todos los valores de tiempo de espera de reinicio posibles, en cuyo caso se elige el tiempo de espera disponible más cercano.

RebootWatchdogSec= puede usarse para configurar el hardware watchdog cuando se solicita reiniciar el sistema. Funciona como una red de seguridad para asegurar que el reinicio se lleve a cabo incluso si un intento de reinicio limpio falla por tiempo de espera. Tenga en cuenta que el tiempo de espera de RebootWatchdogSec= se aplica solo a la segunda fase del reinicio, es decir, después de que todos los servicios regulares ya hayan sido terminados, y después de que el sistema y el proceso del gestor de servicios (PID 1) hayan sido reemplazados por el binario systemd-shutdown, ver bootup(7) para obtener más detalles. Durante la primera fase de la operación de apagado, el sistema y el gestor de servicios permanecen en ejecución y, por lo tanto, RuntimeWatchdogSec= todavía se respeta. Para definir un tiempo de espera en esta primera fase de apagado del sistema, configure JobTimeoutSec= y JobTimeoutAction= en la sección [Unit] de la unidad shutdown.target. Por defecto, RuntimeWatchdogSec= es 0 (apagado), y RebootWatchdogSec= es 10min.

KExecWatchdogSec= puede usarse para habilitar adicionalmente el watchdog cuando se ejecuta kexec en lugar de reiniciar. Tenga en cuenta que si el kernel no restablece el watchdog en kexec (dependiendo del hardware y/o controlador específico), en este caso el watchdog podría no deshabilitarse después de que kexec tenga éxito y, por lo tanto, el sistema podría reiniciarse, a menos que RuntimeWatchdogSec= también esté habilitado al mismo tiempo. Por esta razón, se recomienda habilitar KExecWatchdogSec= solo si RuntimeWatchdogSec= también está habilitado.

Estos ajustes no tienen efecto si no hay un hardware watchdog disponible.

Añadido en la versión 198.

RuntimeWatchdogPreSec=

Configura el valor de pre-tiempo de espera del dispositivo hardware watchdog. Toma un valor de tiempo de espera en segundos (o en otras unidades de tiempo similares a RuntimeWatchdogSec=). Un pre-tiempo de espera del watchdog es una notificación generada por el watchdog antes de que ocurra el reinicio del watchdog en caso de que el watchdog no haya sido atendido. Esta notificación es manejada por el kernel y puede configurarse para tomar una acción (es decir, generar un pánico del kernel) utilizando RuntimeWatchdogPreGovernor=. No todo el hardware watchdog o los controladores admiten la generación de un pre-tiempo de espera y, dependiendo del estado del sistema, el kernel puede no ser capaz de tomar la acción configurada antes del reinicio del watchdog. El watchdog se configurará para generar el evento de pre-tiempo de espera en la cantidad de tiempo especificada por RuntimeWatchdogPreSec= antes del tiempo de espera del watchdog en tiempo de ejecución (establecido por RuntimeWatchdogSec=). Por ejemplo, si tenemos RuntimeWatchdogSec=30 y RuntimeWatchdogPreSec=10, entonces el evento de pre-tiempo de espera ocurrirá si el watchdog no ha hecho ping durante 20s (10s antes de que el watchdog se active). Por defecto, RuntimeWatchdogPreSec= es 0 (apagado). El valor establecido para RuntimeWatchdogPreSec= debe ser menor que el valor de tiempo de espera para RuntimeWatchdogSec=. Este ajuste no tiene efecto si no hay un hardware watchdog disponible o si el hardware watchdog no admite un pre-tiempo de espera y será ignorado por el kernel si el ajuste es mayor que el tiempo de espera real del watchdog.

Añadido en la versión 251.

RuntimeWatchdogPreGovernor=

Configura la acción que toma el dispositivo hardware watchdog cuando expira el pre-tiempo de espera. La acción predeterminada para el evento de pre-tiempo de espera depende de la configuración del kernel, pero generalmente es registrar un mensaje del kernel. Para obtener una lista de las acciones válidas disponibles para un dispositivo watchdog dado, consulte el contenido del archivo /sys/class/watchdog/watchdogX/pretimeout_available_governors. Típicamente, los tipos de gobernador disponibles son noop y panic. La disponibilidad, los nombres y la funcionalidad pueden variar dependiendo del controlador de dispositivo específico en uso. Si el archivo sysfs pretimeout_available_governors está vacío, el gobernador podría estar compilado como un módulo del kernel y podría necesitar ser cargado manualmente (por ejemplo, pretimeout_noop.ko), o el dispositivo watchdog podría no soportar pre-tiempos de espera.

Añadido en la versión 251.

WatchdogDevice=

Configura el dispositivo hardware watchdog que los temporizadores watchdog en tiempo de ejecución y de apagado abrirán y utilizarán. Por defecto, es /dev/watchdog0. Este ajuste no tiene efecto si no hay un hardware watchdog disponible.

Añadido en la versión 236.

SECURITY

CapabilityBoundingSet=

Controla qué capacidades incluir en el conjunto de límites de capacidades para PID 1 y sus hijos. Ver capabilities(7) para obtener más detalles. Toma una lista de nombres de capacidades separadas por espacios en blanco, tal como las lee cap_from_name(3). Las capacidades listadas se incluirán en el conjunto de límites, todas las demás se eliminarán. Si la lista de capacidades está prefijada con
h ~, todas las capacidades excepto las listadas serán incluidas, el efecto de la asignación se invertirá. Tenga en cuenta que esta opción también afecta a las capacidades respectivas en los conjuntos de capacidades efectivo, permitido y heredable. El conjunto de límites de capacidades también puede configurarse individualmente para unidades usando la directiva CapabilityBoundingSet= para las unidades, pero tenga en cuenta que las capacidades eliminadas para PID 1 no se pueden recuperar en unidades individuales, se pierden definitivamente.

Añadido en la versión 198.

NoNewPrivileges=

Acepta un argumento booleano. Si es verdadero, asegura que PID 1 y todos sus hijos nunca puedan obtener nuevos privilegios a través de execve(2) (por ejemplo, a través de bits setuid o setgid, o capacidades del sistema de archivos). Por defecto es falso. Las distribuciones de propósito general suelen depender de ejecutables con bits setuid o setgid y, por lo tanto, no funcionarán correctamente con esta opción habilitada. Las unidades individuales no pueden deshabilitar esta opción. Consulte también el No New Privileges Flag[2].

Añadido en la versión 239.

ProtectSystem=

Acepta un argumento booleano o la cadena "auto". Si se establece en verdadero, volverá a montar /usr/ como de solo lectura. Si se establece en "auto" (el valor por defecto) y se ejecuta en un initrd, será equivalente a verdadero, de lo contrario a falso. Esto implementa un subconjunto restringido de la configuración por unidad del mismo nombre, consulte systemd.exec(5) para más detalles: actualmente, los valores "full" o "strict" no son compatibles.

Añadido en la versión 256.

SystemCallArchitectures=

Acepta una lista de identificadores de arquitectura separados por espacios. Selecciona de qué arquitecturas se pueden invocar las llamadas al sistema en este sistema. Esto puede usarse como una forma efectiva de deshabilitar la invocación de binarios no nativos en todo el sistema, por ejemplo, para prohibir la ejecución de binarios x86 de 32 bits en sistemas x86-64 de 64 bits. Esta opción opera en todo el sistema y actúa de manera similar a la configuración SystemCallArchitectures= de los archivos de unidad, consulte systemd.exec(5) para más detalles. Esta configuración tiene por defecto una lista vacía, en cuyo caso no se aplica ningún filtrado de llamadas al sistema basado en la arquitectura. Los identificadores de arquitectura conocidos son "x86", "x86-64", "x32", "arm" y el identificador especial "native". Este último se mapea implícitamente a la arquitectura nativa del sistema (o más específicamente, a la arquitectura para la que se compiló el gestor del sistema). Configure esta opción en "native" para prohibir la ejecución de cualquier binario no nativo. Cuando un binario ejecuta una llamada al sistema de una arquitectura que no está listada en esta configuración, será terminado inmediatamente con la señal SIGSYS.

TIEMPOS DE ESPERA Y LÍMITES DE TASA

DefaultTimeoutStartSec=, DefaultTimeoutStopSec=, DefaultTimeoutAbortSec=, DefaultRestartSec=

Configura los tiempos de espera predeterminados para el inicio, la detención y la interrupción de unidades, así como el tiempo predeterminado para esperar entre reinicios automáticos de unidades, según se configuren por unidad en TimeoutStartSec=, TimeoutStopSec=, TimeoutAbortSec= y RestartSec= (para servicios, consulte systemd.service(5) para más detalles sobre la configuración por unidad). Para unidades que no son de servicio, DefaultTimeoutStartSec= establece el valor TimeoutSec= predeterminado.

DefaultTimeoutStartSec= y DefaultTimeoutStopSec= tienen por defecto 90 s en el gestor del sistema y 90 s en el gestor de usuario. DefaultTimeoutAbortSec= no se configura por defecto, de modo que todas las unidades recurren a TimeoutStopSec=. DefaultRestartSec= tiene por defecto 100 ms.

Puede cambiarse por dispositivo a través de la opción x-systemd.device-timeout= en /etc/fstab y /etc/crypttab (consulte systemd.mount(5), crypttab(5)). Por defecto es 90 s en el gestor del sistema y 90 s en el gestor de usuario.

Añadido en la versión 252.

Configura la limitación de la tasa de inicio de unidades predeterminada, según se configura por servicio con StartLimitIntervalSec= y StartLimitBurst=. Consulte systemd.service(5) para más detalles sobre la configuración por servicio. DefaultStartLimitIntervalSec= tiene por defecto 10 s. DefaultStartLimitBurst= tiene por defecto 5.

Añadido en la versión 209.

ReloadLimitIntervalSec=, ReloadLimitBurst=

Limitación de la tasa para solicitudes de daemon-reload y (desde la v256) daemon-reexec. La configuración se aplica a ambas operaciones, pero los límites de tasa se rastrean por separado. Por defecto no está configurado, y se pueden solicitar cualquier número de operaciones en cualquier momento. ReloadLimitIntervalSec= acepta un valor en segundos para configurar la ventana del límite de tasa, y ReloadLimitBurst= acepta un entero positivo para configurar el número máximo de operaciones permitidas dentro de la ventana de tiempo configurada.

Añadido en la versión 253.

ENTORNO

DefaultEnvironment=

Configura las variables de entorno que se pasan a todos los procesos ejecutados. Acepta una lista separada por espacios de asignaciones de variables. Consulte environ(7) para más detalles sobre las variables de entorno. Este bloque de entorno es interno, y los cambios no se reflejan en el /proc/PID/environ del gestor.

Se admite la expansión simple de especificadores "%", consulte más abajo para obtener una lista de los especificadores admitidos.

Ejemplo:

DefaultEnvironment="VAR1=palabra1 palabra2" VAR2=palabra3 "VAR3=palabra 5 6"

Establece tres variables: "VAR1", "VAR2", "VAR3".

Añadido en la versión 205.

ManagerEnvironment=

Establece variables de entorno para el propio proceso gestor. Acepta una lista separada por espacios de asignaciones de variables en el mismo formato que DefaultEnvironment=, consulte más arriba. Estas variables se fusionan en el bloque de entorno existente del proceso gestor. En particular, en el caso del gestor del sistema, este bloque incluye variables establecidas por el kernel basándose en la línea de comandos del kernel, y en el caso del gestor de usuario, las variables pasadas por el gestor del sistema. Después de que estas variables se hayan fusionado, persistirán hasta ser anuladas, incluso si el gestor se recarga o se reejecuta. En el caso del gestor de usuario, estas variables también son heredadas por los procesos generados por el gestor. Al igual que con DefaultEnvironment=, este bloque de entorno es interno, y los cambios no se reflejan en el /proc/PID/environ del gestor.

Establecer variables de entorno para el propio proceso gestor puede ser útil para modificar su comportamiento. Consulte Known Environment Variables[3] para una descripción de algunas variables entendidas por systemd.

Se admite la expansión simple de especificadores "%", consulte más abajo para obtener una lista de los especificadores admitidos.

Añadido en la versión 248.

systemd-user.conf(5)

NAME

systemd-user.conf, systemd-user-group.conf — user service instance configuration file

SYNOPSIS

systemd-user.conf, systemd-user-group.conf

DESCRIPTION

The systemd-user.conf and systemd-user-group.conf files are used to configure the systemd user instance. The configuration files are part of the systemd user session infrastructure, which is used to manage services and user sessions.

These files are read by the systemd user manager process, which is typically started by logind.service(8) when a user logs in.

The configuration files are located in /etc/systemd/user.conf and /etc/systemd/user-group.conf. If these files do not exist, default settings are used.

CONFIGURATION DIRECTORIES AND PRECEDENCE

In addition to the main configuration files, systemd also looks for configuration snippets in the following directories:

  • /etc/systemd/user.conf.d/
  • /run/systemd/user.conf.d/
  • /usr/local/etc/systemd/user.conf.d/
  • /usr/lib/systemd/user.conf.d/

Configuration files in these directories are parsed in alphabetical order. If multiple files specify the same option, the last one read takes precedence.

OPTIONS

The configuration files support the following options:

DefaultEnvironment=
Sets environment variables for all user services. See systemd.exec(5) for details. Multiple values may be given, separated by spaces, or the option may be specified multiple times.
DefaultEnvironmentFile=
Reads environment variables from a file. See systemd.exec(5) for details. Multiple values may be given, separated by spaces, or the option may be specified multiple times.
DefaultMemoryLimit=
Sets the default memory limit for user services. See systemd.resource-control(5) for details.
DefaultIOPriority=
Sets the default I/O scheduling priority for user services. See systemd.resource-control(5) for details.
DefaultCPUQuota=
Sets the default CPU quota for user services. See systemd.resource-control(5) for details.
DefaultIPAddressDeny=, DefaultIPAddressAllow=
Sets the default IP address allow/deny lists for user services. See systemd.resource-control(5) for details.
DefaultTasksMax=
Sets the default maximum number of tasks for user services. See systemd.resource-control(5) for details.
DefaultDevicePolicy=
Sets the default device policy for user services. See systemd.exec(5) for details.

RESOURCE MANAGEMENT

The following options control resource limits for user services:

DefaultCPUAccounting=
Enables or disables CPU accounting for user services. See systemd.exec(5) for details.
DefaultIOAccounting=
Enables or disables I/O accounting for user services. See systemd.exec(5) for details.
DefaultBlockIOAccounting=
Enables or disables block I/O accounting for user services. See systemd.exec(5) for details.
DefaultIPAccounting=
Enables or disables IP accounting for user services. See systemd.exec(5) for details.
DefaultTasksAccounting=
Enables or disables tasks accounting for user services. See systemd.exec(5) for details.

HARDWARE WATCHDOG

The following option controls the hardware watchdog for user services:

DefaultWatchdog=
Enables or disables the hardware watchdog for user services. See systemd.service(5) for details.
DefaultWatchdogSec=
Sets the watchdog timeout for user services. See systemd.service(5) for details.

SECURITY

The following options control security settings for user services:

DefaultCapabilityBoundingSet=
Sets the capability bounding set for user services. See systemd.exec(5) for details.
DefaultAmbientCapabilities=
Sets the ambient capabilities for user services. See systemd.exec(5) for details.
DefaultSuppressDevicePolicy=
Controls whether the device policy is suppressed for user services. See systemd.exec(5) for details.
DefaultRestrictAddressFamilies=
Sets the allowed address families for user services. See systemd.exec(5) for details.
DefaultRestrictNamespaces=
Controls whether user namespaces are restricted for user services. See systemd.exec(5) for details.
DefaultRestrictRealtime=
Controls whether realtime scheduling is restricted for user services. See systemd.exec(5) for details.
DefaultRestrictSUIDS=
Controls whether SUID binaries are restricted for user services. See systemd.exec(5) for details.
DefaultRemoveIPC=
Controls whether IPC mechanisms are removed for user services. See systemd.exec(5) for details.

TIMEOUTS AND RATE LIMITS

The following options control timeouts and rate limits for user services:

DefaultTimeoutStartSec=
Sets the default timeout for starting user services. See systemd.service(5) for details.
DefaultTimeoutStopSec=
Sets the default timeout for stopping user services. See systemd.service(5) for details.
DefaultTimeoutAbortSec=
Sets the default timeout for aborting user services. See systemd.service(5) for details.
DefaultStartLimitIntervalSec=
Sets the default interval for limiting service starts. See systemd.service(5) for details.
DefaultStartLimitBurst=
Sets the default burst limit for service starts. See systemd.service(5) for details.

ENVIRONMENT

The following environment variables are recognized:

$TMPDIR, $TEMP, $TMP
Used to determine the directory for temporary files. See environ(7) for details.

SPECIFIERS

The following specifiers may be used in the configuration files:

"%N" Operating system name The operating system name of the running system, as read from the PRETTY_NAME= field of /etc/os-release. If not set, resolves to an empty string. See os-release(5) for more information.
"%O" Operating system version ID The operating system version identifier of the running system, as read from the VERSION_ID= field of /etc/os-release. If not set, resolves to an empty string. See os-release(5) for more information.
"%W" Operating system variant ID The operating system variant identifier of the running system, as read from the VARIANT_ID= field of /etc/os-release. If not set, resolves to an empty string. See os-release(5) for more information.
"%T" Directory for temporary files This is either /tmp or the path "$TMPDIR", "$TEMP" or "$TMP" are set to. (Note that the directory may be specified without a trailing slash.)
"%V" Directory for larger and persistent temporary files This is either /var/tmp or the path "$TMPDIR", "$TEMP" or "$TMP" are set to. (Note that the directory may be specified without a trailing slash.)
"%h" User home directory This is the home directory of the user running the service manager instance.
"%u" Username This is the username of the user running the service manager instance.
"%U" User id This is the user id of the user running the service manager instance.
"%g" Primary group This is the primary group of the user running the service manager instance.
"%G" Primary group id This is the primary group id of the user running the service manager instance.
"%s" User shell This is the shell of the user running the service manager instance.
"%%" Single percent sign Use "%%" in place of "%" to specify a single percent sign.

HISTORY

systemd 252

Option DefaultBlockIOAccounting= was deprecated. Please switch to the unified cgroup hierarchy.

systemd 258

DefaultCPUAccounting= setting is deprecated, because CPU accounting is always available on the unified cgroup hierarchy and such setting has no effect.
