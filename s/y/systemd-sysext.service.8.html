SYSTEMD-SYSEXT(8) systemd-sysext SYSTEMD-SYSEXT(8)

NOMBRE

systemd-sysext, systemd-sysext.service, systemd-sysext-initrd.service, systemd-confext, systemd-confext.service, systemd-confext-initrd.service - Activa Imágenes de Extensión del Sistema

SINOPSIS

systemd-sysext [OPCIONES...] COMANDO

systemd-sysext.service

systemd-confext [OPCIONES...] COMANDO

systemd-confext.service

DESCRIPCIÓN

systemd-sysext activa/desactiva imágenes de extensión del sistema. Las imágenes de extensión del sistema pueden – dinámicamente en tiempo de ejecución – extender las jerarquías de directorios /usr/ y /opt/ con archivos adicionales. Esto es particularmente útil en imágenes de sistema inmutables donde una jerarquía /usr/ y/o /opt/ que reside en un sistema de archivos de solo lectura debe extenderse temporalmente en tiempo de ejecución sin realizar modificaciones persistentes.

Las imágenes de extensión del sistema deben contener archivos y directorios de manera similar a la estructura del sistema operativo regular. Cuando una o más imágenes de extensión del sistema se activan, sus jerarquías /usr/ y /opt/ se combinan mediante "overlayfs" con las mismas jerarquías del sistema operativo host, y el /usr/ y /opt/ del host se superponen con él ("fusionando"). Cuando se desactivan, el punto de montaje se desensambla – revelando nuevamente la versión modificada original del host de la jerarquía ("desfusionando"). La fusión, por lo tanto, hace que los recursos de la extensión aparezcan repentinamente debajo de las jerarquías /usr/ y /opt/ como si estuvieran incluidos en la propia imagen del sistema base. La des-fusión hace que desaparezcan, dejando en su lugar solo los archivos que se enviaron con la propia imagen del sistema base.

Los archivos y directorios contenidos en las imágenes de extensión fuera de las jerarquías /usr/ y /opt/ *no* se fusionan y, por lo tanto, no tienen efecto cuando se incluyen en una imagen de extensión del sistema. En particular, los archivos en /etc/ y /var/ incluidos en una imagen de extensión del sistema *no* aparecerán en las jerarquías respectivas después de la activación.

Las imágenes de extensión del sistema son estrictamente de solo lectura por defecto. En sistemas de archivos host mutables, las jerarquías /usr/ y /opt/ se vuelven de solo lectura mientras las extensiones se fusionan, a menos que se habilite la mutabilidad. La mutabilidad se puede habilitar mediante la opción --mutable=; consulte "Mutabilidad" a continuación para obtener más información.

Las extensiones del sistema están destinadas a ser puramente aditivas, es decir, solo deben incluir archivos que no existan en la imagen del sistema base subyacente. Sin embargo, el mecanismo subyacente (overlayfs) también permite superponer o eliminar archivos, pero se recomienda no hacer uso de esto.

Las imágenes de extensión del sistema pueden proporcionarse en los siguientes formatos:

1. Directorios planos o subvolúmenes btrfs que contienen el árbol del SO
2. Imágenes de disco con una etiqueta de disco GPT, siguiendo la Especificación de Particiones Descubribles[1]
3. Imágenes de disco sin tabla de particiones, con un sistema de archivos Linux desnudo (por ejemplo, erofs, squashfs o ext4)

Estos formatos de imagen son los mismos que systemd-nspawn(1) soporta a través de sus opciones --directory=/--image= y los que el gestor de servicios soporta a través de RootDirectory=/RootImage=. De forma similar a ellos, opcionalmente pueden llevar información de autenticación Verity.

Las extensiones del sistema se buscan en los directorios /etc/extensions/, /run/extensions/ y /var/lib/extensions/. Los dos primeros directorios listados no son adecuados para contener imágenes binarias grandes, sin embargo, son útiles para contener enlaces simbólicos a ellas. El lugar principal para instalar extensiones del sistema es /var/lib/extensions/. Cualquier directorio encontrado en estos directorios de búsqueda se considera una imagen de extensión basada en directorios; cualquier archivo con el sufijo .raw se considera una imagen de extensión basada en imagen de disco. Cuando se invoca en el initrd, el directorio adicional /.extra/sysext/ se incluye en los directorios que se buscan para obtener imágenes de extensión. Tenga en cuenta, sin embargo, que por defecto se aplica una política de imagen más estricta a las imágenes que se encuentran allí, aunque, véase más abajo. Este directorio es poblado por systemd-stub(7) con imágenes de extensión encontradas en la Partición del Sistema EFI del sistema.

Durante el arranque, las imágenes de extensión del SO se activan automáticamente, si systemd-sysext.service está habilitado. Tenga en cuenta que este servicio se ejecuta solo después de que los sistemas de archivos subyacentes donde se pueden ubicar las extensiones del sistema hayan sido montados. Esto significa que no son adecuadas para enviar recursos que son procesados por subsistemas que se ejecutan en el arranque más temprano. Específicamente, las imágenes de extensión del SO no son adecuadas para enviar servicios del sistema o definiciones de systemd-sysusers(8). Consulte la página de Servicios Portátiles[2] para un mecanismo simple para enviar servicios del sistema en imágenes de disco, de manera similar a las extensiones del SO. Tenga en cuenta el diferente aislamiento en estos dos mecanismos: mientras que las extensiones del sistema extienden directamente la imagen del SO subyacente con archivos adicionales que aparecen de manera muy similar a como si se enviaran en la propia imagen del SO y, por lo tanto, no implican aislamiento de seguridad, los servicios portátiles implican sandboxing a nivel de servicio de una forma u otra. Se garantiza que el servicio systemd-sysext.service finaliza su inicio antes de que se alcance basic.target; es decir, cuando los servicios regulares se inicializan (aquellos que no usan DefaultDependencies=no), los archivos y directorios que proporcionan las extensiones del sistema están disponibles en /usr/ y /opt/ y pueden ser accedidos.

Tenga en cuenta que no existe el concepto de habilitar/deshabilitar imágenes de extensión del sistema instaladas: todas las imágenes de extensión instaladas se activan automáticamente al arrancar. Sin embargo, puede colocar un directorio vacío con el nombre de la extensión (sin .raw) en /etc/extensions/ para "enmascarar" una extensión con el mismo nombre en un directorio del sistema con menor precedencia.

Se aplica un mecanismo simple para la compatibilidad de versiones: una imagen de extensión del sistema debe llevar un archivo /usr/lib/extension-release.d/extension-release.NOMBRE, que debe coincidir con el nombre de su imagen, y que se compara con el archivo os-release del host: los campos ID= contenidos deben coincidir a menos que se establezca "_any" para la extensión. Si el ID= de la extensión no es "_any", el campo SYSEXT_LEVEL= (si está definido) debe coincidir. Si este último no está definido, el campo VERSION_ID= debe coincidir en su lugar. Si la extensión define el campo ARCHITECTURE= y el valor no es "_any", debe coincidir con la arquitectura del kernel reportada por uname(2), pero los identificadores de arquitectura utilizados son los mismos que para ConditionArchitecture= descritos en systemd.unit(5). EXTENSION_RELOAD_MANAGER= puede establecerse en 1 si la extensión requiere una recarga del gestor de servicios después de la aplicación de la extensión. Tenga en cuenta que, por las razones mencionadas anteriormente, los Servicios Portátiles[2] siguen siendo la forma recomendada de enviar servicios del sistema. Las extensiones del sistema no deben enviar un archivo /usr/lib/os-release (ya que se fusionaría en el árbol /usr/ del host, sobrescribiendo los datos de la versión del SO host, lo cual no es deseable). El archivo extension-release sigue el mismo formato y semántica, y contiene el mismo contenido, que el archivo os-release del SO, pero describe los recursos contenidos en la imagen de extensión.

El concepto systemd-confext sigue el mismo principio que la funcionalidad de systemd-sysext(8) pero en lugar de trabajar en /usr y /opt, confext extenderá solo /etc. Los archivos y directorios contenidos en las imágenes de confext fuera de la jerarquía /etc/ *no* se fusionan y, por lo tanto, no tienen efecto cuando se incluyen en la imagen. Los formatos para estas imágenes son los mismos que las imágenes sysext. La jerarquía fusionada se montará con "nosuid" y (si no se deshabilita con --noexec=false) "noexec".

Al igual que sysext, los confext son estrictamente de solo lectura por defecto. La fusión de confext en sistemas de archivos host mutables resultará en que /etc/ se vuelva de solo lectura. Al igual que con sysext, la mutabilidad se puede habilitar a través de la opción --mutable=. Consulte "Mutabilidad" a continuación para obtener más información.

Los confext se buscan en los directorios /run/confexts/, /var/lib/confexts/, /usr/lib/confexts/ y /usr/local/lib/confexts/. El primer directorio listado no es adecuado para contener imágenes binarias grandes, sin embargo, es útil para contener enlaces simbólicos a ellas. El lugar principal para instalar extensiones de configuración es /var/lib/confexts/. Cualquier directorio encontrado en estos directorios de búsqueda se considera una imagen de confext basada en directorio; cualquier archivo con el sufijo .raw se considera una imagen de confext basada en imagen de disco.

Nuevamente, al igual que las imágenes sysext, las imágenes confext contendrán un archivo /etc/extension-release.d/extension-release.NOMBRE, que debe coincidir con la im

edad nombre (con la salida habitual de escape de user.extension-release.strict xattr(7)), y de nuevo con el contenido siendo uno o más de ID=, VERSION_ID=, y CONFEXT_LEVEL. Las imágenes confext se comprobarán y se cotejarán con la capa base del sistema operativo.

USOS

El caso de uso principal para las imágenes del sistema son entornos inmutables donde las herramientas de depuración y desarrollo se pondrán opcionalmente a disposición, pero no se incluirán en la propia imagen base del sistema operativo inmutable (por ejemplo, strace(1) y gdb(1) serán una adición instalable opcionalmente para facilitar la depuración/desarrollo). Las imágenes de extensión del sistema no deben malinterpretarse como un marco genérico de empaquetado de software, ya que no hay un esquema de dependencias disponible: las extensiones del sistema deben llevar todos los archivos que necesiten, excepto aquellos que ya se envían en la imagen subyacente del sistema host. Típicamente, las imágenes de extensión del sistema se construyen al mismo tiempo que la imagen base del sistema operativo — dentro del mismo sistema de compilación.

Otro caso de uso para el concepto de extensión del sistema es la sustitución temporal de recursos suministrados por el sistema operativo por otros más nuevos, por ejemplo, para instalar una versión de desarrollo compilada localmente de algún componente de bajo nivel sobre la imagen inmutable del sistema operativo sin realizar una recompilación completa del sistema operativo ni modificar la imagen nominalmente inmutable. (por ejemplo, "instalar" un paquete compilado localmente con DESTDIR=/var/lib/extensions/mytest make install && systemd-sysext refresh, haciéndolo disponible en /usr/ como si se hubiera instalado en la propia imagen del sistema operativo.) Este caso funciona independientemente de si el host /usr/ subyacente se gestiona como una imagen de disco inmutable o es un árbol tradicional controlado por un gestor de paquetes (es decir, escribible).

Con systemd-confext se puede realizar la reconfiguración en tiempo de ejecución de los servicios del sistema operativo. A veces, es necesario intercambiar ciertos valores de parámetros de configuración o reiniciar solo un servicio específico sin desplegar nuevo código o un despliegue completo del sistema operativo. En otras palabras, queremos poder vincular las opciones configuradas con mayor frecuencia a indicadores actualizables en tiempo de ejecución que se puedan cambiar sin reiniciar el sistema. Esto ayudará a reducir los tiempos de servicio cuando sea necesario cambiar la configuración del sistema operativo. También proporciona una herramienta fiable para gestionar la configuración, ya que todos los archivos de configuración antiguos desaparecen cuando se elimina la imagen de systemd-confext.

INMUTABILIDAD

Por defecto, la fusión de extensiones del sistema en sistemas de archivos de host mutables dejará las jerarquías /usr/ y /opt/ de solo lectura. La fusión de extensiones de configuración tendrá el mismo efecto en /etc/. El modo mutable permite escrituras en estas ubicaciones cuando se fusionan las extensiones.

Los siguientes modos son compatibles:

1.desactivado: Fuerza el modo inmutable incluso si existen directorios de enrutamiento de escritura debajo de /var/lib/extensions.mutable/. Este es el valor por defecto.
2.auto: Modo automático. La mutabilidad está desactivada por defecto y solo se habilita si existe un directorio de enrutamiento de escritura correspondiente debajo de /var/lib/extensions.mutable/.
3.habilitado: Fuerza el modo mutable y crea automáticamente directorios de enrutamiento de escritura debajo de /var/lib/extensions.mutable/ cuando sea necesario.
4.importar: Fuerza el modo inmutable como desactivado anteriormente, pero fusiona el contenido de los directorios debajo de /var/lib/extensions.mutable/ en el sistema de archivos del host.
5.efímero: Fuerza el modo mutable como habilitado anteriormente, pero en lugar de usar directorios de enrutamiento de escritura debajo de /var/lib/extensions.mutable/, systemd-sysext utilizará directorios efímeros vacíos. Esto significa que las modificaciones realizadas en las jerarquías fusionadas se perderán cuando se desfusionen las jerarquías.
6.efímero-importar: Fuerza el modo mutable como efímero anteriormente, pero en lugar de ignorar el contenido de los directorios de enrutamiento de escritura bajo /var/lib/extensions.mutable/, los fusiona en el sistema de archivos del host, como lo hace importar.

Vea "Opciones" a continuación sobre cómo especificar modos usando la opción de línea de comandos --mutable=.

Con la excepción del modo efímero, el modo mutable enruta las escrituras a subdirectorios en /var/lib/extensions.mutable/.

Las escrituras a /usr/ se dirigen a /var/lib/extensions.mutable/usr/
las escrituras a /opt/ se dirigen a /var/lib/extensions.mutable/opt/, y
las escrituras a /etc/ van a /var/lib/extensions.mutable/etc/.

Si usr/, opt/, o etc/ en /var/lib/extensions.mutable/ son enlaces simbólicos, entonces las escrituras se dirigen a los objetivos de los enlaces simbólicos. En consecuencia, para retener la mutabilidad de un sistema de archivos de host, cree enlaces simbólicos

/var/lib/extensions.mutable/etc/ → /etc/
/var/lib/extensions.mutable/usr/ → /usr/
/var/lib/extensions.mutable/opt/ → /opt/
para dirigir las escrituras de vuelta a la jerarquía de directorios base original.

Alternativamente, se puede montar un sistema de archivos temporal en /var/lib/extensions.mutable/, o los enlaces simbólicos en /var/lib/extensions.mutable/ pueden apuntar a subdirectorios en un sistema de archivos temporal (por ejemplo, debajo de /tmp/) para permitir solo cambios efímeros. Tenga en cuenta que esto no es lo mismo que el modo efímero, porque el sistema de archivos temporal todavía existirá después de la desfusión.

Añadido en la versión 256.

COMANDOS

Los siguientes comandos son entendidos por ambos conceptos, sysext y confext:

status

Cuando se invoca sin ningún verbo de comando, o cuando se especifica status se muestra el estado de fusión actual, por separado (tanto para /usr/ y /opt/ de sysext como para /etc/ de confext).

Añadido en la versión 248.

merge

Fusiona todas las imágenes de extensión del sistema instaladas actualmente en /usr/ y /opt/, sobremontando estas jerarquías con un sistema de archivos "overlayfs" que combina las jerarquías subyacentes con las incluidas en las imágenes de extensión. Este comando fallará si las jerarquías ya están fusionadas. Para confext, la fusión se realiza en el directorio /etc/ en su lugar.

Añadido en la versión 248.

unmerge

Desfusiona todas las imágenes de extensión del sistema instaladas actualmente de /usr/ y /opt/ para sysext y /etc/, para confext, desmontando los sistemas de archivos "overlayfs" creados por merge anteriormente.

Añadido en la versión 248.

refresh

Una combinación de unmerge y merge: si ya está montada, la instancia "overlayfs" existente se desmonta temporalmente y luego se reemplaza por una nueva versión. Este comando es útil después de instalar/eliminar imágenes de extensión del sistema, para actualizar el sistema de archivos "overlayfs" en consecuencia. Si no hay extensiones del sistema instaladas cuando se ejecuta este comando, se ejecuta el equivalente a unmerge, sin establecer ninguna nueva instancia "overlayfs". Tenga en cuenta que actualmente hay un breve momento en el que ni el sistema de archivos "overlayfs" antiguo ni el nuevo están montados. Esto implica que todos los recursos suministrados por una extensión del sistema desaparecerán brevemente — incluso si existe de forma continua durante la operación de actualización.

Añadido en la versión 248.

list

Se muestra una lista breve de las imágenes de extensión instaladas.

Añadido en la versión 248.

-h, --help

Imprime un breve texto de ayuda y sale.

--version

Imprime una breve cadena de versión y sale.

OPCIONES

--root=

Opera en relación con el directorio raíz especificado, es decir, establece el montaje "overlayfs" no en las jerarquías de nivel superior del host /usr/ y /opt/ para sysext o /etc/ para confext, sino debajo de algún directorio raíz especificado.

Añadido en la versión 248.

--force

Al fusionar extensiones del sistema en /usr/ y /opt/ para sysext y /etc/ para confext, ignora las incompatibilidades de versión, es decir, fuerza la fusión independientemente de si la información de versión incluida en las imágenes coincide o no con el host.

Añadido en la versión 248.

--image-policy=política

Toma una cadena de política de imagen como argumento, según systemd.image-policy(7). La política se aplica al operar en imágenes de disco de extensión del sistema. Si no se especifica, por defecto es "root=verity+signed+encrypted+unprotected+absent:usr=verity+signed+encrypted+unprotected+absent" para las extensiones del sistema, es decir, solo se utilizan los sistemas de archivos root y /usr/ en la imagen. Para las extensiones de configuración, por defecto es "root=verity+signed+encrypted+unprotected+absent". Cuando se ejecuta en el initrd y opera en una imagen de extensión del sistema almacenada en el directorio /.extra/sysext/ se utiliza una política ligeramente más estricta por defecto: "root=signed+absent:usr=signed+absent", ver arriba para más detalles.

Añadido en la versión 254.

--mutable=BOOL|auto|importar|efímero|efímero-importar

Establece el modo mutable.

no

fuerza el modo inmutable incluso con directorios de enrutamiento de escritura presentes. Este es el valor por defecto.

Añadido en la versión 256.

auto

habilita el modo mutable individualmente para /usr/, /opt/, y /etc/ si existen subdirectorios o enlaces simbólicos de enrutamiento de escritura en /var/lib/extensions.mutable/; desactiva en caso contrario. Ver "Inmutabilidad" arriba para más información sobre el enrutamiento de escritura.

Añadido en la versión 256.

sí

fuerza el modo mutable. Se crearán directorios de enrutamiento de escritura en /var/lib/extensions.mutable/ si no existen.

Añadido en la versión 256.

importar

modo inmutable, pero con el contenido de los directorios de enrutamiento de escritura en /var/lib/extensions.mutable/ también fusionado en el sistema de archivos del host.

Añadido en la versión 256.

efímero

fuerza el modo mutable, pero con el contenido de los directorios de enrutamiento de escritura en /var/lib/extensions.mutable/ siendo ignorado, y las modificaciones del sistema de archivos del host siendo descartadas después de la desfusión.

Añadido en la versión 256.

efímero-importar

fuerza el modo mutable, con el contenido de los directorios de enrutamiento de escritura en /var/lib/extensions.mutable/ siendo fusionado en el sistema de archivos del host, pero con las modificaciones realizadas en el sistema de archivos del host siendo descartadas después de la desfusión.

Añadido en la versión 256.

systemd-sysext.service(8) — systemd Manual

NAME

systemd-sysext.service, systemd-sysext - Apply system extension images

SYNOPSIS

systemd-sysext --query [--json]

systemd-sysext merge [--no-exec] [--no-reload] [--json] IMAGE_PATH...

systemd-sysext unmerge [--no-exec] [--no-reload] [--json] IMAGE_PATH...

systemd-sysext refresh [--no-exec] [--no-reload] [--json]

systemd-sysext update [--no-exec] [--no-reload] [--json]

systemd-sysext --help

systemd-sysext --version

DESCRIPTION

systemd-sysext is a tool to manage system extension images. System extensions are used to add or update binaries, configuration files, and data files to a running system without modifying the root file system directly. This is useful for decoupling components from the operating system, or for providing custom environments.

The primary mechanism is placing read-only file system images (e.g. SquashFS images) into /etc/systemd/system-extensions/. The systemd-sysext service, systemd-sysext.service, is activated periodically or on-demand to merge these extension images into the running system's file hierarchy.

The merging happens by mounting the extension images into /etc/systemd/system/, /usr/lib/systemd/system/, /run/systemd/system/, and other similar directories. This allows systemd units, binaries, and data from the extension to be used as if they were part of the main system.

The merging process respects the Discoverable Partitions Specification [1]. The images are expected to be named *.raw or *.squashfs and reside in directories like /etc/systemd/system-extensions/ or on partitions marked with the systemd partition type GUID.

Changes made by merging are not persistent across reboots unless the underlying extension images are present and mounted on boot.

USES

1.
systemd units, binaries, and data are added to the running system.
2.
Portable services can be deployed using system extension images.

MUTABILITY

The merged file system is read-only. Modifications to files originating from an extension image are not possible. New files may be created in /run/systemd/system-extensions/.

COMMANDS

The following commands are available:

--query
Show information about the currently merged system extensions and available extension images. If --json is used, the output is formatted as JSON.
merge IMAGE_PATH...
Merges the specified system extension images. The images are expected to be file system images (e.g., SquashFS or raw disk images). The command requires root privileges. This command is typically run by systemd-sysext.service.
unmerge IMAGE_PATH...
Unmerges the specified system extension images. This reverts the changes made by merging. The command requires root privileges.
refresh
Scans the configured directories for system extension images, merges new or updated images, and unmerges removed or outdated ones. This command is usually run automatically by systemd-sysext.service periodically or when relevant events occur.
update
Equivalent to refresh.
--help
Print a short help message and exit.
--version
Print a short version message and exit.

OPTIONS

The following options are available:

--no-exec=BOOL

When merging configuration extensions into /etc/ the "MS_NOEXEC" mount flag is used by default. This option can be used to disable it.

Added in version 254.

--no-reload

When used with merge, unmerge or refresh, do not reload daemon after executing the changes even if an extension that is applied requires a reload via the EXTENSION_RELOAD_MANAGER= set to 1.

Added in version 255.

--no-pager

Do not pipe output into a pager.

--no-legend

Do not print the legend, i.e. column headers and the footer with hints.

--json=MODE

Shows output formatted as JSON. Expects one of "short" (for the shortest possible output without any redundant whitespace or line breaks), "pretty" (for a pretty version of the same, with indentation and line breaks) or "off" (to turn off JSON output, the default).

EXIT STATUS

On success, 0 is returned.
