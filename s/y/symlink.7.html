NOMBRE

symlink - manejo de enlaces simbólicos

DESCRIPCIÓN

Los enlaces simbólicos son archivos que actúan como punteros a otros archivos. Para entender su comportamiento, primero debe entender cómo funcionan los enlaces duros.

Un enlace duro a un archivo es indistinguible del archivo original porque es una referencia al objeto subyacente al nombre de archivo original. (Para ser precisos: cada uno de los enlaces duros a un archivo es una referencia al mismo número de inodo, donde un número de inodo es un índice en la tabla de inodos, que contiene metadatos sobre todos los archivos en un sistema de archivos. Ver stat(2)). Los cambios en un archivo son independientes del nombre utilizado para referirse al archivo. Los enlaces duros no pueden referirse a directorios (para evitar la posibilidad de bucles dentro del árbol del sistema de archivos, lo que confundiría a muchos programas) y no pueden referirse a archivos en diferentes sistemas de archivos (porque los números de inodo no son únicos entre sistemas de archivos).

Un enlace simbólico es un tipo especial de archivo cuyo contenido es una cadena que es la ruta de acceso de otro archivo, el archivo al que se refiere el enlace. (El contenido de un enlace simbólico se puede leer usando readlink(2)). En otras palabras, un enlace simbólico es un puntero a otro nombre, y no a un objeto subyacente. Por esta razón, los enlaces simbólicos pueden referirse a directorios y pueden cruzar límites de sistemas de archivos.

No hay ningún requisito de que la ruta de acceso a la que se refiere un enlace simbólico deba existir. Un enlace simbólico que se refiere a una ruta de acceso que no existe se dice que es un enlace colgante.

Debido a que un enlace simbólico y el objeto al que se refiere coexisten en el espacio de nombres del sistema de archivos, puede surgir confusión al distinguir entre el enlace en sí y el objeto al que se refiere. En sistemas históricos, los comandos y las llamadas al sistema adoptaron sus propias convenciones de seguimiento de enlaces de manera algo ad-hoc. Las reglas para un enfoque más uniforme, tal como se implementan en Linux y otros sistemas, se describen aquí. Es importante que las aplicaciones locales del sitio también cumplan con estas reglas, para que la interfaz de usuario pueda ser lo más consistente posible.

Enlaces mágicos

Existe una clase especial de objetos similares a enlaces simbólicos conocidos como "enlaces mágicos", que se pueden encontrar en ciertos pseudofilesystems como proc(5) (los ejemplos incluyen /proc/pid/exe y /proc/pid/fd/*). A diferencia de los enlaces simbólicos normales, los enlaces mágicos no se resuelven a través de la expansión de la ruta de acceso, sino que actúan como referencias directas a la representación interna del kernel de un manejador de archivo. Como tales, estos enlaces mágicos permiten a los usuarios acceder a archivos que no se pueden referenciar con rutas normales (como archivos desvinculados que aún son referenciados por un programa en ejecución).

Debido a que pueden eludir las restricciones ordinarias basadas en mount_namespaces(7), los enlaces mágicos se han utilizado como vectores de ataque en varios exploits.

Propiedad, permisos y marcas de tiempo de enlaces simbólicos

La propiedad y el grupo de un enlace simbólico existente se pueden cambiar usando lchown(2). La propiedad de un enlace simbólico importa cuando el enlace se está eliminando o renombrando en un directorio que tiene el bit sticky configurado (ver inode(7)), y cuando el sysctl fs.protected_symlinks está configurado (ver proc(5)).

Las marcas de tiempo de último acceso y última modificación de un enlace simbólico se pueden cambiar usando utimensat(2) o lutimes(3).

En Linux, los permisos de un enlace simbólico ordinario no se utilizan en ninguna operación; los permisos son siempre 0777 (lectura, escritura y ejecución para todas las categorías de usuario) y no se pueden cambiar.

Sin embargo, los enlaces mágicos no siguen esta regla. Pueden tener un modo distinto de 0777, aunque este modo no se utiliza actualmente en ninguna comprobación de permisos.

Obtener un descriptor de archivo que se refiere a un enlace simbólico

Usando la combinación de las banderas O_PATH y O_NOFOLLOW para open(2) se obtiene un descriptor de archivo que se puede pasar como argumento dirfd en llamadas al sistema como fstatat(2), fchownat(2), fchmodat(2), linkat(2) y readlinkat(2), para operar sobre el propio enlace simbólico (en lugar del archivo al que se refiere).

Por defecto (es decir, si la bandera AT_SYMLINK_FOLLOW no se especifica), si name_to_handle_at(2) se aplica a un enlace simbólico, devuelve un manejador para el enlace simbólico (en lugar del archivo al que se refiere). Uno puede entonces obtener un descriptor de archivo para el enlace simbólico (en lugar del archivo al que se refiere) especificando la bandera O_PATH en una llamada posterior a open_by_handle_at(2). De nuevo, ese descriptor de archivo se puede utilizar en las llamadas al sistema mencionadas anteriormente para operar sobre el propio enlace simbólico.

Manejo de enlaces simbólicos por llamadas al sistema y comandos

Los enlaces simbólicos se manejan operando sobre el propio enlace, o operando sobre el objeto al que se refiere el enlace. En este último caso, se dice que una aplicación o llamada al sistema sigue el enlace. Los enlaces simbólicos pueden referirse a otros enlaces simbólicos, en cuyo caso los enlaces se desreferencian hasta que se encuentra un objeto que no es un enlace simbólico, se encuentra un enlace simbólico que se refiere a un archivo que no existe, o se detecta un bucle. (La detección de bucles se realiza estableciendo un límite superior en el número de enlaces que se pueden seguir, y se produce un error si se excede este límite).

Hay tres áreas separadas que necesitan ser discutidas. Son las siguientes:

•
Enlaces simbólicos utilizados como argumentos de nombre de archivo para llamadas al sistema.
•
Enlaces simbólicos especificados como argumentos de línea de comandos a utilidades que no están recorriendo un árbol de archivos.
•
Enlaces simbólicos encontrados por utilidades que están recorriendo un árbol de archivos (especificados en la línea de comandos o encontrados como parte del recorrido de la jerarquía de archivos).

Antes de describir el tratamiento de los enlaces simbólicos por parte de las llamadas al sistema y los comandos, necesitamos alguna terminología. Dado un nombre de archivo de la forma a/b/c, la parte anterior a la última barra (es decir, a/b) se llama componente dirname, y la parte posterior a la última barra (es decir, c) se llama componente basename.

Tratamiento de enlaces simbólicos en llamadas al sistema

La primera área son los enlaces simbólicos utilizados como argumentos de nombre de archivo para llamadas al sistema.

El tratamiento de los enlaces simbólicos dentro de un nombre de archivo pasado a una llamada al sistema es el siguiente:

(1)
Dentro del componente dirname de un nombre de archivo, los enlaces simbólicos siempre se siguen en casi todas las llamadas al sistema. (Esto también es cierto para los comandos). La única excepción es openat2(2), que proporciona banderas que se pueden usar para evitar explícitamente el seguimiento de enlaces simbólicos en el componente dirname.
(2)
Excepto como se indica a continuación, todas las llamadas al sistema siguen los enlaces simbólicos en el componente basename de un nombre de archivo. Por ejemplo, si hubiera un enlace simbólico slink que apuntara a un archivo llamado afile, la llamada al sistema open("slink" ...) devolvería un descriptor de archivo que se refiere al archivo afile.

Varias llamadas al sistema no siguen enlaces en el componente basename de un nombre de archivo, y operan sobre el propio enlace simbólico. Son: lchown(2), lgetxattr(2), llistxattr(2), lremovexattr(2), lsetxattr(2), lstat(2), SYNOPSIS

#include <unistd.h>

int symlink(const char *oldpath, const char *newpath);

int symlinkat(const char *oldpath, int dirfd, const char *newpath);

DESCRIPTION

The symlink() function creates a new symbolic link named newpath (SYNTAX ERROR) that references the file named oldpath (SYNTAX ERROR). oldpath is not interpreted by the file system; it is simply a string that is stored in the new symbolic link. Subsequent operations on newpath that are not specifically designed to operate on symbolic links will operate on the file referenced by oldpath.

The symlinkat() function is similar to symlink(), but allows a symbolic link to be created relative to an existing directory descriptor. The newpath argument is interpreted relative to the directory referred to by the file descriptor dirfd (which must have been opened with the O_DIRECTORY flag). If newpath is an absolute path, then dirfd is ignored. If newpath is a relative path, then it is interpreted relative to the directory named by dirfd. If newpath is the empty string, then it refers to the directory referred to by dirfd.

The symbolic link is created with read and write permissions for all users, but these permissions are ignored; the mode of the symbolic link (except for the set-user-ID, set-group-ID, and sticky bits) is irrelevant because it is not used when the file is opened. The owner and group of the symbolic link are set to the effective user ID and group ID of the calling process, respectively.

The symlink() function fails if newpath already exists. The symbolic link is created with the same ownership and permissions as if created by the link() system call.

Symbolic links can be created on any file system. However, the symlink() call does not traverse symbolic links. If newpath is a symbolic link, symlink() fails with EEXIST.

The symbolic link's st_mode field will have the type S_IFLNK. The symbolic link's st_size field will be the length of the string stored in the link.

Symbolic links are subject to pathname resolution. By default, most system calls that operate on pathnames will follow symbolic links. There are exceptions:

unlink(2), rmdir(2)
These calls operate on the symbolic link itself, not the file it references. However, rmdir(2) fails with ENOTDIR if applied to a symbolic link.
link(2)
By default, link(2) does not follow symbolic links. POSIX.1-2001 specified that it should, but POSIX.1-2008 changed this to allow either behavior.
rename(2)
The rename(2) call operates on the symbolic link itself, not the file it references. However, if the new name refers to a directory, rename(2) fails with EISDIR.
stat(2), lstat(2)
stat(2) follows symbolic links, while lstat(2) does not.
readlink(2)
This call reads the target of a symbolic link.

Certain other system calls optionally follow symbolic links in the basename component of a pathname. They are: faccessat(2), fchownat(2), fstatat(2), linkat(2), name_to_handle_at(2), open(2), openat(2), open_by_handle_at(2), and utimensat(2); see their manual pages for details. Because remove(3) is an alias for unlink(2), that library function also does not follow symbolic links. When rmdir(2) is applied to a symbolic link, it fails with the error ENOTDIR.

link(2) warrants special discussion. POSIX.1-2001 specifies that link(2) should dereference oldpath if it is a symbolic link. However, Linux does not do this. (By default, Solaris is the same, but the POSIX.1-2001 specified behavior can be obtained with suitable compiler options.) POSIX.1-2008 changed the specification to allow either behavior in an implementation.

Commands not traversing a file tree

The second area is symbolic links, specified as command-line filename arguments, to commands which are not traversing a file tree.

Except as noted below, commands follow symbolic links named as command-line arguments. For example, if there were a symbolic link slink which pointed to a file named afile, the command cat slink would display the contents of the file afile.

It is important to realize that this rule includes commands which may optionally traverse file trees; for example, the command chown file is included in this rule, while the command chown -R file, which performs a tree traversal, is not. (The latter is described in the third area, below.)

If it is explicitly intended that the command operate on the symbolic link instead of following the symbolic link —for example, it is desired that chown slink change the ownership of the file that slink is, whether it is a symbolic link or not— then the -h option should be used. In the above example, chown root slink would change the ownership of the file referred to by slink, while chown -h root slink would change the ownership of slink itself.

There are some exceptions to this rule:

•
The mv(1) and rm(1) commands do not follow symbolic links named as arguments, but respectively attempt to rename and delete them. (Note, if the symbolic link references a file via a relative path, moving it to another directory may very well cause it to stop working, since the path may no longer be correct.)
•
The ls(1) command is also an exception to this rule. For compatibility with historic systems (when ls(1) is not doing a tree walk—that is, -R option is not specified), the ls(1) command follows symbolic links named as arguments if the -H or -L option is specified, or if the -F, -d, or -l options are not specified. (The ls(1) command is the only command where the -H and -L options affect its behavior even though it is not doing a walk of a file tree.)
•
The file(1) command is also an exception to this rule. The file(1) command does not follow symbolic links named as argument by default. The file(1) command does follow symbolic links named as argument if the -L option is specified.

Commands traversing a file tree

The following commands either optionally or always traverse file trees: chgrp(1), chmod(1), chown(1), cp(1), du(1), find(1), ls(1), pax(1), rm(1), and tar(1).

It is important to realize that the following rules apply equally to symbolic links encountered during the file tree traversal and symbolic links listed as command-line arguments.

The first rule applies to symbolic links that reference files other than directories. Operations that apply to symbolic links are performed on the links themselves, but otherwise the links are ignored.

The command rm -r slink directory will remove slink, as well as any symbolic links encountered in the tree traversal of directory, because symbolic links may be removed. In no case will rm(1) affect the file referred to by slink.

The second rule applies to symbolic links that refer to directories. Symbolic links that refer to directories are never followed by default. This is often referred to as a "physical" walk, as opposed to a "logical" walk (where symbolic links that refer to directories are followed).

Certain conventions are (should be) followed as consistently as possible by commands that perform file tree walks:

•
A command can be made to follow any symbolic links named on the command line, regardless of the type of file they reference, by specifying the -H (for "half-logical") flag. This flag is intended to make the command-line name space look like the logical name space. (Note, for commands that do not always do file tree traversals, the -H flag will be ignored if the -R flag is not also specified.)
For example, the command chown -HR user slink will traverse the file hierarchy rooted in the file pointed to by slink. Note, the -H is not the same as the previously discussed -h flag. The -H flag causes symbolic links specified on the command line to be dereferenced for the purposes of both the action to be performed and the tree walk, and it is as if the user had specified the name of the file to which the symbolic link pointed.
•
A command can be made to follow any symbolic links named on the command line, as well as any symbolic links encountered during the traversal, regardless of the type of file they reference, by specifying the -L (for "logical") flag. This flag is intended to make the entire name space look like the logical name space. (Note, for commands that do not always do file tree traversals, the -L flag will be ignored if the -R flag is not also specified.)
For example, the command chown -LR user slink will change the owner of the file referred to by slink. If slink refers to a directory, chown will traverse the file hierarchy rooted in the directory that it references. In addition, if any symbolic links are encountered in any file tree that chown traverses, they will be treated in the same fashion as slink.
•
A command can be made to provide the default behavior by specifying the -P (for "physical") flag. This flag is intended to make the entire name space look like the physical name space.

For commands that do not by default do file tree traversals, the -H, -L, and -P flags are ignored if the -R flag is not also specified. In addition, you may specify the -H, -L, and -P options more than once; the last one specified determines the command's behavior. This is intended to permit you to alias commands to behave one way or the other, and then override that behavior on the command line.

The ls(1) and rm(1) commands have exceptions to these rules:

•
The rm(1) command operates on the symbolic link, and not the file it references, and therefore never follows a symbolic link. The rm(1) command does not support the -H, -L, or -P options.
•
To maintain compatibility with historic systems, the ls(1) command acts a little differently. If you do not specify the -F, -d, or -l options, ls(1) will follow symbolic links specified on the command line. If the -L flag is specified, ls(1) follows all symbolic links, regardless of their type, whether specified on the command line or encountered in the tree walk.

symlink(7)

NAME

symlink - overview of symbolic links

DESCRIPTION

Symbolic links (also known as symlinks or soft links) are special files whose contents are a text string that is interpreted to be a path to another file. The operating system checks to see if the file referred to by the link exists, and if it does, the link is treated as an alias for that file. This works for both reading and writing files.

Symbolic links can refer to files or directories. They can also refer to files or directories that do not exist. If a symbolic link refers to a nonexistent file or directory, it is called a dangling symlink.

A symbolic link is created using the symlink(2) system call, or the ln(1) command-line utility:

   ln -s target link_name

Where target is the file or directory to which the link points, and link_name is the name of the symbolic link file being created.

If the target string is not an absolute path (i.e., it does not start with a leading slash), then it is interpreted relative to the directory in which the symbolic link file resides.

For example, suppose you have a directory structure like this:

   /home/user/
       links/
           my_link -> ../docs/file.txt
       docs/
           file.txt

If you are in the /home/user/links directory and run

   cat my_link

The kernel will interpret my_link as referring to /home/user/docs/file.txt, and will display the contents of that file.

However, if you create the link as follows:

   ln -s /home/user/docs/file.txt /home/user/links/my_link

Then my_link will always refer to /home/user/docs/file.txt, regardless of the current working directory.

Symbolic links have several advantages over hard links:

  • They can refer to files or directories.

  • They can refer to files on different filesystems.

  • They can refer to nonexistent files (though this is usually an error).

  • They can be created as ordinary users.

However, they also have some disadvantages:

  • They can cause infinite loops if not handled carefully (e.g., a link pointing to itself).

  • They may be slower than hard links because the kernel has to perform an extra lookup.
