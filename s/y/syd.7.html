NOMBRE

Descripción general del aislamiento con Syd

AISLAMIENTO

La lista de categorías de aislamiento disponibles se muestra a continuación:

stat Restringe el acceso a metadatos de archivos. Esta categoría de aislamiento puede usarse para ocultar archivos y directorios efectivamente del proceso aislado. La lista de llamadas al sistema filtradas son access(2), faccessat(2), faccessat2(2), getdents64(2), readlink(2), readlinkat(2) stat(2), fstat(2), lstat(2), statx(2), newfstatat(2), getxattr(2), getxattrat(2), lgetxattr(2), fgetxattr(2), listxattr(2), listxattrat(2), flistxattr(2), llistxattr(2), statfs(2), statfs64(2), fstatfs(2), fstatfs64(2), fanotify_mark(2), y inotify_add_watch(2). Además, las rutas pueden ser enmascaradas usando el comando mask. En este caso, todas las llamadas al sistema filtradas en la ruta se ejecutarán en el dispositivo de caracteres /dev/null en su lugar. Consulte la descripción del comando mask en la página del manual de syd(2) para más información.
walk Restringe el recorrido de rutas. Esta categoría de aislamiento se usa durante la canonicalización de rutas para restringir los recorridos de rutas. Como tal, sus argumentos no son necesariamente rutas completamente canonicalizadas, pero se garantiza que sean rutas absolutas sin componentes de . (punto) o .. (doble punto). Se ha separado de la categoría stat a partir de la versión 3.39.0. Junto con la categoría stat, el ocultamiento de rutas proporciona una implementación completa resistente a intentos de desocultar rutas previamente ocultas al atravesarlas durante la canonicalización de rutas. Notablemente, unveil(2) de OpenBSD fue pionero en capacidades similares y sigue siendo una implementación de referencia madura y ampliamente respetada.
read Restringe la lectura de archivos. La lista de llamadas al sistema filtradas son open(2), openat(2) y openat2(2) con las banderas O_RDONLY u O_RDWR.
write Restringe la escritura de archivos. La lista de llamadas al sistema filtradas son open(2), openat(2) y openat2(2) con las banderas O_WRONLY u O_RDWR.
exec Restringe la ejecución de binarios y la carga de bibliotecas dinámicas. La lista de llamadas al sistema filtradas son execve(2), execveat(2), mmap(2), mmap2(2) y memfd_create(2). Tenga en cuenta que, para scripts, la verificación de acceso se realiza tanto para el script como para el binario intérprete. A partir de la versión 3.16.3, Syd verifica las rutas de las bibliotecas dinámicas a las que está enlazado un ejecutable para el acceso de ejecución también. Esto solo funciona para binarios ELF. A partir de la versión 3.21.2, Syd sella los descriptores de archivo de memoria como no ejecutables por defecto, por lo tanto, los descriptores de archivo de memoria no se verifican para el acceso de ejecución a menos que la opción trace/allow_unsafe_memfd:1 se establezca para levantar esta restricción. A partir de la versión 3.21.3, Syd se engancha a las llamadas al sistema mmap(2) y mmap2(2) y verifica el descriptor de archivo para el acceso de ejecución cuando el modo de protección de memoria incluye PROT_EXEC y las banderas no incluyen MAP_ANONYMOUS, lo que típicamente indica un dlopen(3). Por lo tanto, las bibliotecas cargadas dinámicamente en tiempo de ejecución también se verifican para el acceso de ejecución. Además, se utiliza SegvGuard para denegar la ejecución si el binario falla repetidamente, lo que es similar a la implementación de Grsecurity & HardenedBSD. Consulte la sección SegvGuard para obtener más información.
ioctl Restringe la llamada al sistema ioctl(2) para el acceso al sistema de archivos. Este tipo de aislamiento puede usarse para acceder de forma segura a GPU, PTY, DRM, KVM, etc. Además, las solicitudes de ioctl(2) pueden permitirse o denegarse añadiéndolas a la lista respectiva utilizando las opciones ioctl/allow+ y ioctl/deny+. A partir de la versión 3.38.0, se introdujo la decodificación de ioctl(2) independiente de la arquitectura, lo que permite especificar los ioctls por nombre además de los valores numéricos. Consulte la página del manual de syd(2) para obtener más información.
create Restringe la creación de archivos regulares y descriptores de archivo de memoria. La lista de llamadas al sistema filtradas son creat(2), mknod(2), mknodat(2) y memfd_create(2). Además, las llamadas al sistema open open(2), openat(2) y openat2(2) se filtran si la bandera O_CREAT está establecida y la bandera O_TMPFILE no está establecida en los argumentos. El argumento de nombre de memfd_create(2) se antepone con !memfd: antes de la verificación de acceso. Use, por ejemplo, deny/create+!memfd:** para denegar el acceso a descriptores de archivo de memoria independientemente del nombre. A partir de la versión 3.37.0, el argumento de nombre de memfd_create(2) se antepone con !memfd-hugetlb: antes de la verificación de acceso en caso de que las banderas incluyan MFD_HUGETLB.
delete Restringe la eliminación de archivos. La lista de llamadas al sistema filtradas son unlink(2) y unlinkat(2). A partir de la versión 3.33.0, unlinkat(2) es restringido por esta categoría si y solo si AT_REMOVEDIR no está establecido en las banderas, de lo contrario, es restringido por la categoría rmdir.
rename Restringe el renombrado de archivos y la creación de enlaces duros. La lista de llamadas al sistema filtradas son rename(2), renameat(2), renameat2(2), link(2) y linkat(2).
symlink Restringe la creación de enlaces simbólicos. La lista de llamadas al sistema filtradas son symlink(2) y symlinkat(2).
truncate Restringe el truncamiento de archivos. La lista de llamadas al sistema filtradas son truncate(2), truncate64(2), ftruncate(2), ftruncate64(2) y fallocate(2). Además, las llamadas al sistema open open(2), openat(2) y openat2(2) se filtran si la bandera O_TRUNC está establecida en los argumentos y las banderas O_TMPFILE u O_CREAT no están establecidas en los argumentos.
chdir Restringe los cambios de directorio. La lista de llamadas al sistema filtradas son chdir(2) y fchdir(2). Se puede lograr un endurecimiento adicional utilizando la opción trace/deny_dotdot:1 para denegar los recorridos de directorios padre. Es posible establecer esta opción en tiempo de ejecución antes de que el aislamiento se bloquee. Esto permite un aislamiento incremental. Consulte la sección Restricción de Resolución de Rutas para Llamadas Chdir y Open para obtener más información.
readdir Restringe la enumeración de directorios. La lista de llamadas al sistema filtradas son open(2), openat(2) y openat2(2) cuando se llaman en un directorio existente independientemente de la bandera O_DIRECTORY.
mkdir Restringe la creación de directorios. La lista de llamadas al sistema filtradas son mkdir(2), mkdirat(2), mknod(2) y mknodat(2).

Force Sandboxing

Force Sandboxing asegura la integridad de los binarios ejecutados mediante un escrutinio de la ruta proporcionada a las llamadas del sistema execve(2) y execveat(2), comparándolas con un mapa de Fuerza de Integridad predefinido: un registro de correlaciones ruta-a-checksum. Al invocar estas llamadas, el sandbox calcula el checksum del binario objetivo y lo cruza con el mapa. Las discrepancias activan acciones definidas por reglas: la ejecución puede continuar con una advertencia registrada o culminar en la terminación del proceso infractor. Este mecanismo permite una aplicación rigurosa de la integridad binaria, haciendo eco del ethos preventivo de Integriforce de HardenedBSD y Veriexec de NetBSD al mitigar proactivamente la ejecución de código no autorizado, aunque con un énfasis único en una gestión de consecuencias flexible y definida por el usuario que va desde alertas permisivas hasta bloqueos de ejecución estrictos.

Distintiéndose por la personalización centrada en el usuario, Force Sandboxing ofrece un enfoque versátil para la integridad de la ejecución. Los administradores pueden adaptar la respuesta del sandbox a las no coincidencias de checksum (matar, denegar o advertir), equilibrando así las necesidades de seguridad con la flexibilidad operativa. Esta adaptabilidad, combinada con herramientas como syd-sha(1) para el cálculo de checksum y syd-path(1) para la creación de reglas, posiciona a Force Sandboxing como un poderoso aliado en la preservación de la integridad del sistema. Consulte el comando force en la página del manual de syd(2) sobre cómo agregar/eliminar entradas del mapa de Fuerza de Integridad.

Desde la versión 3.16.3, Syd también verifica las rutas de las bibliotecas dinámicas a las que un ejecutable está enlazado para acceso de fuerza. Esto solo funciona para archivos ELF.

Desde la versión 3.21.3, Syd se engancha en las llamadas del sistema mmap(2) y mmap2(2) y verifica el descriptor de archivo para acceso de Fuerza cuando el modo de protección de memoria incluye PROT_EXEC y las banderas no incluyen MAP_ANONYMOUS, lo que típicamente indica una llamada a dlopen(3). Por lo tanto, las bibliotecas cargadas dinámicamente en tiempo de ejecución también se verifican para acceso de Fuerza.

TPE sandboxing

Desde la versión 3.21.0, Syd introduce Trusted Path Execution (TPE) sandboxing, que restringe la ejecución de binarios para asegurar que provienen de directorios confiables. Desde la versión 3.37.2, el archivo binario debe ser confiable, así como su directorio padre. La intención es hacer más difícil la escalada de privilegios cuando se compromete una cuenta restringida por TPE, ya que el atacante no podrá ejecutar binarios personalizados que no estén en la ruta confiable. Un binario es confiable si el archivo y su directorio padre cumplen los siguientes criterios:

  • No es escribible por el grupo ni por otros.
  • Opcionalmente propiedad de root, controlado por la opción tpe/root_owned.
  • Opcionalmente propiedad del usuario actual o de root, controlado por la opción tpe/user_owned.
  • Opcionalmente parte del sistema de archivos raíz, controlado por la opción tpe/root_mount.

Si no se cumplen estos criterios, la ejecución se deniega con un error EACCES errno(3) y, opcionalmente, el proceso infractor puede ser terminado con la señal SIGKILL utilizando la opción default/tpe:kill. Este mecanismo asegura que solo se puedan ejecutar binarios de rutas seguras y confiables, mejorando la seguridad al prevenir la ejecución de código no autorizado. El TPE sandboxing opera verificando los ejecutables en tres etapas:

  • Durante la entrada de la llamada al sistema de execve(2) y execveat(2) para verificar scripts.
  • En el evento exec de ptrace(2) para verificar el ejecutable ELF y el cargador dinámico.
  • En mmap(2) cuando las bibliotecas dinámicas se mapean en memoria, típicamente con dlopen(3).

TPE puede configurarse para aplicarse a un grupo de usuarios específico. Por defecto, TPE se aplica a todos los usuarios. Sin embargo, los administradores pueden especificar un GID no confiable con la configuración tpe/gid, restringiendo TPE solo a los usuarios de ese grupo. Adicionalmente, TPE puede negar la lógica del GID con la configuración tpe/negate, haciendo que el grupo especificado sea confiable y esté exento de TPE.

La implementación de TPE de Syd se basa en la de HardenedBSD, que está inspirada en el TPE de GrSecurity. Consulte los siguientes enlaces para obtener más información:

Lock Sandboxing

Lock sandboxing utiliza el Landlock Linux Security Module para un control de acceso simple sin privilegios. Se aplica completamente en el espacio del kernel y la política también se aplica al proceso Syd, de modo que un proceso Syd comprometido sigue atrapado dentro del sandbox de landlock(7), por lo tanto, el sandboxing de Lock puede usarse para construir un sandbox de múltiples capas para mayor seguridad. El sandboxing de Lock puede activarse con el comando de sandbox sandbox/lock:on al inicio. Las rutas a archivos y jerarquías de archivos deben poblarse usando las categorías lock/*, especificándolas una a la vez, por ejemplo, allow/lock/read+/usr, allow/lock/write+/dev/null o especificándolas como una lista separada por comas, por ejemplo, allow/lock/read,write,ioctl+/dev/null. El atajo lock/all se proporciona para facilitar la configuración y representa la unión de las categorías lock/read, lock/write, lock/exec, lock/ioctl, lock/create, lock/delete, lock/rename, lock/symlink, lock/truncate, lock/readdir, lock/mkdir, lock/rmdir, lock/mkdev, lock/mkfifo y lock/bind. Desde la versión 3.29.0, se admite la confinación de red y los puertos permitidos para bind(2) y connect(2) se pueden especificar usando los comandos allow/lock/bind+port y allow/lock/connect+port. También se puede especificar un rango cerrado en formato port1-port2 en lugar de un número de puerto único. Use la categoría lock/bind con una ruta absoluta para confinar la creación, renombrado y enlaces de sockets de dominio UNIX, por ejemplo, allow/lock/bind+/run/user/${SYD_UID}. Desde la versión 3.35.0, el nivel de compatibilidad predeterminado se ha cambiado a Requisito Obligatorio. En comparación con el antiguo valor predeterminado Mejor Esfuerzo, este nivel garantiza que el sandbox se aplique completamente. Además, los errores ENOENT ("No existe tal archivo o directorio") se vuelven fatales en este nivel. El nivel de compatibilidad se puede cambiar al inicio utilizando el comando default/lock. Crypt Sandboxing

Esta categoría de sandboxing proporciona cifrado de archivos transparente utilizando AES-CTR, con HMAC-SHA256 asegurando el manejo seguro de datos sin pasos de cifrado manuales. Cuando se establece sandbox/crypt:on, los archivos que coinciden con los patrones de glob(3) especificados por crypt+ se cifran al escribir y se descifran al leer. La configuración incluye especificar un ID de serie de clave de cifrado decimal de 32 bits para la interfaz de keyrings(7) usando crypt/key/main, y especificar un ID de serie de clave de autenticación decimal de 32 bits para la interfaz de keyrings(7) usando crypt/key/auth. Se permite especificar el mismo ID de serie de clave para ambas opciones y la opción crypt/key se puede usar como atajo para establecer ambos IDs de serie de clave. Los IDs de serie de clave especificados se utilizan con la operación setsockopt(2) ALG_SET_KEY_BY_KEY_SERIAL, que es nueva en Linux-6.2, por lo tanto, Crypt sandboxing requiere Linux-6.2 o más reciente. Las claves deben tener permiso de búsqueda, es decir, tener el bit(s) de permiso KEY_(POS|USR|GRP|OTH)_SEARCH establecido(s) para que el kernel pueda localizar y copiar los datos de la clave a la API de criptografía; de lo contrario, la operación se denegará (EPERM: "Operación no permitida"). Consulte el siguiente enlace para obtener más información https://lkml.org/lkml/2022/10/4/1014.

La utilidad syd-key(1) puede usarse para generar claves de cifrado y guardarlas en keyrings(7) para su uso con Crypt sandboxing. Para evitar incluir los IDs de serie de clave en el archivo de configuración, el usuario puede establecer los IDs de serie de clave usando una variable de entorno y luego especificar esta variable de entorno, por ejemplo: crypt/key:${SYD_KEY_ID}. El usuario debe usar un nombre de variable de entorno que comience con el prefijo SYD_ pero que no comience con el prefijo SYD_TEST_, ya que dichas variables de entorno no se filtran al proceso sandbox. De manera similar, el usuario debe abstenerse de usar cualquier variable de entorno especificada en la sección ENTORNO de la página del manual de syd(1).

El cifrado opera a través de sockets de la API de criptografía del kernel de Linux, utilizando técnicas de cero copia con splice(2) y tee(2) para evitar datos sin cifrar en memoria. Para asegurar que usamos cero copia exclusivamente y respetamos la privacidad del usuario evitando leer texto plano en memoria a toda costa, los hilos syd_aes, responsables del cifrado, están confinados con un filtro de seccomp(2) para denegar las llamadas al sistema read(2), open(2) y socket(2) (y muchas más) y permitir la llamada al sistema write(2) solo hasta 32 bytes, que es lo necesario para escribir la etiqueta HMAC y el IV aleatorio en el archivo. Los sockets de configuración se crean al inicio, la clave se selecciona usando la interfaz de keyrings(7) sin copiar el material de la clave al espacio de usuario. La unicidad del IV se garantiza generando un IV aleatorio usando getrandom(2) por archivo. En caso de error al recuperar entropía vía getrandom(2), se utilizan los bytes aleatorios en AT_RANDOM en su lugar. El IV por archivo se antepone a los archivos cifrados. Esto garantiza la seguridad al prevenir la reutilización del IV. Syd asegura que los IV por archivo se limpian de forma segura al ser descartados.

Crypt sandboxing employs the AES-CTR algorithm, a secure and efficient symmetric key encryption method suitable for various applications. It operates as a stream cipher (skcipher) with a block size of 1 byte, allowing data to be encrypted in a byte-by-byte manner. The algorithm uses a fixed key size of 32 bytes (256 bits) by default, providing robust security, and a fixed initialization vector (IV) size of 16 bytes to ensure randomness and uniqueness in each encryption operation. Processing data in byte-sized chunks, the algorithm maintains a consistent walk size of 16 bytes for traversal and operations, ensuring seamless encryption and decryption processes. This configuration, with its secure default key size, significantly enhances security, preventing common encryption weaknesses and supporting efficient, transparent file encryption within the sandbox environment. The inclusion of HMAC-SHA256 for integrity checking further enhances security by detecting any unauthorized modifications or corruption of data. CTR is infinitely parallelizable because each block in the stream can be encrypted independently. This allows for encryption and decryption processes to be split across multiple processors, significantly increasing throughput. With hardware support such as AES-NI CPU instructions, speeds can easily exceed a gigabyte per second.

File Format: Each file encrypted within the Crypt sandboxing framework follows a structured format to ensure consistency, secure handling, and clear identification. Each encrypted file starts with a five-byte magic header, \x7fSYD3, where \x7fSYD indicates that the file is encrypted by Syd, and 3 denotes the current API version. This header is followed by a 32-byte HMAC (SHA256) message authentication tag, providing integrity checking by authenticating the encrypted content. Next is followed by a 16-byte initialization vector (IV), which is unique per file, ensuring strong cryptographic security. The AES-CTR-encrypted ciphertext follows the IV, providing the file's protected content. Syd will only process files that match this format and have a compatible version; if a file does not have the correct file format header or API version, or if it exists unencrypted, Syd will leave it untouched. This approach prevents unintended operations on incompatible or unencrypted files.

  • Large files are not handled efficiently during decryption by default due to usage of in-memory files, specify a secure temporary backing directory with crypt/tmp:/path to workaround this. Ideally this directory should be on encrypted storage as Syd is going to write plaintext here.
  • Concurrent Access: Encrypted file access utilises Linux OFD locks, which are now standardized in POSIX 2024. Ensure that the underlying filesystem fully supports OFD locks to enable effective advisory file locking. Modern filesystems and NFS implementations compliant with POSIX 2024 typically provide this support, mitigating issues present in older versions. The multithreaded architecture of Syd relies on OFD locks to ensure safe and efficient concurrent access, eliminating the need for alternative locking mechanisms such as POSIX advisory locks. For further details, refer to the fcntl_locking(2) manual page.
  • Crash Safety: Currently, encrypted data is flushed to disk only after all file descriptors are closed. In the event of a system or sandbox crash, this may result in incomplete writes or potential data loss, as in-flight data might not be persisted. Future enhancements will focus on implementing transactional flush mechanisms and crash recovery procedures to ensure atomicity and integrity of encrypted data, thereby improving resilience against unexpected terminations.

Proxy Sandboxing

As of version 3.22.0, Proxy sandboxing in Syd confines network communication exclusively through a designated SOCKS proxy, enforced by the helper utility syd-tor(1). Configured at startup with sandbox/proxy:on, this type implies the use of unshare/net:1, isolating network namespaces to prevent direct network access. Traffic is forwarded from a specified local port (proxy/port:9050) to an external address and port (proxy/ext/host:127.0.0.1, proxy/ext/port:9050). As of version 3.34.1, you may also specify an external UNIX domain socket using e.g. proxy/ext/unix:/path/socks5.sock. This setup ensures all network interactions route through the proxy, leveraging zero-copy data transfers and edge-triggered epoll(7) for efficient event handling. The implementation enhances security by employing seccomp and Landlock for additional confinement, preventing unauthorized network access and ensuring strict adherence to the defined network path. This approach minimizes the risk of proxy bypasses and maintains the integrity of the network isolation.

PTY Sandboxing

As of version 3.36.0, PTY Sandboxing runs the target process inside a dedicated pseudoterminal managed by the syd-pty(1) helper, isolating all terminal I/O from the host TTY and preventing direct ioctl(2) or control-sequence escapes. The PTY main is proxied via an edge-triggered epoll(7) loop with non-blocking zero-copy splice(2), ensuring no unencrypted data ever traverses user space. A minimal seccomp(2) filter confines only the essential PTY syscalls (e.g. TIOCGWINSZ, TIOCSWINSZ) and denies all others -- including injection via TIOCSTI -- while Landlock locks down access to the PTY device, filesystem, and network. Combined with no-exec memory seals and namespace isolation, this approach hardens against terminal-based attacks and preserves the confidentiality and integrity of the sandboxed session.

This sandboxing category handles the system calls brk(2), mmap(2), mmap2(2), and mremap(2) and checks the per-process memory usage on each memory allocation request. Subsequent to the delivery of the signal, the process_mrelease(2) system call is called on the process to immediately release memory. The default action may be changed using the default/mem option. Memory sandboxing

Este tipo de sandboxing se centra en la gestión y el seguimiento del uso de la memoria.

  • Pss (Proportional Set Size) es similar a Rss, pero tiene en cuenta la memoria compartida de forma más precisa al dividirla entre los procesos que la comparten. Rss (Resident Set Size) es la porción de memoria ocupada por un proceso que se mantiene en RAM.

A partir de la versión 3.43.1, el sistema de sandboxing de memoria se ha actualizado para mejorar el seguimiento del uso de la memoria. Syd ahora aplica un estricto límite de memoria basado en la granularidad de asignación, lo que significa que los programas no pueden exceder los límites de memoria definidos, ni siquiera por la cantidad que asignan de una vez. Este cambio alinea el límite con el tamaño de asignación en lugar de permitir cualquier desbordamiento más allá del límite. Además, el seguimiento de la memoria se ha optimizado al cambiar de iterar sobre proc_pid_smaps(5) al uso de /proc/pid/smaps_rollup, que es más eficiente y consolida la información de uso de memoria para un mejor rendimiento y una aplicación más precisa de las restricciones de memoria.

¡El sandboxing de memoria no es una alternativa a cgroups(7)! Deberías usar cgroups(7) cuando puedas. Esta categoría de sandboxing está pensada para entornos más restringidos donde cgroups(7) no es compatible o no está disponible debido a permisos faltantes u otras restricciones similares.

Sandboxing PID

Esta categoría de sandboxing maneja las llamadas al sistema fork(2), vfork(2), clone(2) y clone3(2) y verifica el número total de tareas en ejecución en el sistema en cada solicitud de creación de proceso. Si el recuento alcanza el valor máximo definido por pid/max, la llamada al sistema se deniega con EAGAIN. Si pid/kill se establece en true, la señal SIGKILL se entrega al proceso infractor. Esta categoría de sandboxing se combina mejor con un espacio de nombres PID usando unshare/pid. En este modo, Syd verificará el número de tareas en ejecución solo en el espacio de nombres actual.

A partir de la versión 3.40.0, con unshare/pid:1 el límite y la contabilidad se aplican por espacio de nombres PID; en Linux 6.14 y versiones más recientes, el kernel.pid_max de espacio de nombres sysctl(8) se establece en max(pid/max, 301) para que los 300 PIDs reservados del kernel no reduzcan el margen configurado, y en kernels más antiguos, kernel.pid_max sysctl(8) no se modifica.

SafeSetID

SafeSetID, introducido en la versión 3.16.8, mejora la gestión de las transiciones de UID/GID. Esta característica permite un control más granular al permitir a los administradores especificar explícitamente las transiciones permitidas para los cambios de UID y GID, reforzando así las restricciones de seguridad en torno a la gestión de privilegios de procesos. Funciona permitiendo transiciones predefinidas de UID y GID que se configuran explícitamente utilizando los comandos setuid+<source_uid>:<target_uid> y setgid+<source_gid>:<target_gid> en la configuración de Syd. Esto asegura que las transiciones solo puedan ocurrir entre IDs de usuario y grupo especificados, y se bloquean las escaladas de privilegios no autorizadas. Por ejemplo, se podría permitir una transición de un usuario con mayores privilegios a uno con menos privilegios, pero no viceversa, evitando así cualquier escalada de privilegios a través de estas llamadas al sistema.

A partir de la versión 3.24.5, Syd aplica un filtro seccomp(2) a nivel de kernel por defecto para denegar todas las llamadas al sistema set*uid con UID menor o igual a 11, que suele ser el usuario operador, y todas las llamadas al sistema set*gid con GID menor o igual a 14, que suele ser el grupo uucp. Esto significa que incluso un proceso Syd comprometido no puede elevar privilegios utilizando estas llamadas al sistema. Consulte la salida del comando syd-ls setid para ver la lista completa de llamadas al sistema en este grupo.

Cuando se define una transición de UID o GID, Syd mantiene las capacidades CAP_SETUID y CAP_SETGID respectivamente, y el proceso sandbox heredará estas capacidades de Syd. Desde la versión 3.24.6, Syd elimina la capacidad CAP_SETUID después de la primera transición de UID exitosa y, de manera similar, la capacidad CAP_SETGID después de la primera transición de GID exitosa. Esto significa que Syd solo puede cambiar su UID y GID una vez en su vida. Sin embargo, esto no bloquea completamente las llamadas al sistema setid en el proceso sandbox: las transiciones al UID y GID actuales de Syd continúan en el proceso sandbox, lo que significa que la primera transición exitosa de UID y GID seguirá funcionando siempre que el proceso sandbox conserve las capacidades CAP_SETUID y CAP_SETGID respectivas. Esto permite contener demonios, como nginx(1), que inician múltiples procesos trabajadores sin privilegios a partir de un único proceso principal privilegiado.

Modo Ghost

Modo Ghost, introducido en la versión 3.20.0 de Syd, es un modo de sandboxing unidireccional, que se asemeja mucho a seccomp(2) Nivel 1, también conocido como Modo Estricto. Este modo mejora la seguridad al permitir que un proceso transicione a un estado altamente restrictivo después de completar su configuración inicial. Cuando un proceso en sandbox está listo para este nivel superior de confinamiento, invoca el Modo Ghost ejecutando la llamada al sistema stat(2) con la ruta virtual /dev/syd/ghost. Al recibir este comando, Syd cierra el descriptor de archivo seccomp_unotify(2). Esta acción eleva todas las llamadas al sistema previamente interceptadas a una denegación a nivel de kernel con el error ENOSYS ("Función no implementada") errno(3), haciéndolas efectivamente indisponibles. La transición al Modo Ghost es irreversible; una vez que se cierra el descriptor de archivo, el proceso queda bloqueado en este estado restringido. Este mecanismo asegura que el proceso en sandbox solo pueda realizar un conjunto muy limitado de operaciones, similar a las permitidas en Seccomp Nivel 1, reduciendo así significativamente su superficie de ataque potencial. El Modo Ghost proporciona una medida de seguridad robusta al denegar todas las llamadas al sistema excepto las más esenciales, lo cual es crucial para aplicaciones que requieren el máximo aislamiento y seguridad después de su fase de configuración inicial.

El modo se llama acertadamente "ghost" (fantasma) porque, al cerrar el descriptor de archivo seccomp_unotify(2), el proceso en sandbox se desvincula efectivamente de Syd y se vuelve independiente, muy parecido a un fantasma. La entrada en el modo ghost hace que el hilo supervisor syd_mon y todos los hilos emuladores syd_emu salgan, y el hilo restante syd_main simplemente espera a que el proceso sandbox salga sin más intervención. Esta desvinculación subraya la finalidad y el aislamiento del Modo Ghost, asegurando que el proceso opere en un entorno seguro y estrictamente confinado sin más interacción de Syd. Este mecanismo es particularmente útil para procesos que requieren la máxima seguridad y la mínima exposición a llamadas al sistema después de su fase de configuración inicial, proporcionando una capa robusta de protección contra diversas explotaciones y vulnerabilidades.

Un proceso no puede entrar en modo Ghost una vez que el bloqueo del sandbox está establecido. Alternativamente, sin embargo, un proceso puede establecer su atributo de volcado de proceso a cero utilizando PR_SET_DUMPABLE prctl(2). Bajo Syd, esto logra casi el mismo efecto ya que Syd no podrá emular llamadas al sistema con el directorio por proceso inaccesible. Esto proporciona una forma sin privilegios de entrar en modo Ghost.

SEGURIDAD

Syd destaca por su capacidad de operar sin requerir privilegios elevados, eliminando la necesidad de acceso root. Esta característica simplifica significativamente la configuración y el uso. Los usuarios se benefician de la capacidad de configurar dinámicamente el sandbox desde dentro, con opciones para asegurarlo aún más según sea necesario. Consejo: Para echar un rápido vistazo a los filtros seccomp aplicados por Syd bajo diversas configuraciones diferentes, usa syd <flags...> -Epfc donde PFC significa Pseudo Filter Code, que genera un volcado textual legible por humanos de los filtros seccomp(2) de Syd. Syd enriquece aún más la salida de este volcado textual con comentarios de #.

Modelo de Amenaza

Syd se adhiere estrictamente al modelo de amenaza actual de seccomp(2). El objetivo es restringir cómo las aplicaciones de espacio de usuario no confiables interactúan con el kernel compartido del sistema operativo a través de llamadas al sistema para proteger el kernel de exploits de espacio de usuario (por ejemplo, shellcode o payload ROP). Se confía en el kernel. El modelo de amenaza de Syd delinea el sandbox como el interceptor confiable de llamadas al sistema, mientras que todas las aplicaciones de usuario que se ejecutan dentro del sandbox se consideran no confiables. Estas aplicaciones no confiables pueden manipular su entorno de ejecución a través de llamadas al sistema, y se asume que los atacantes tienen la capacidad de ejecutar código arbitrario dentro de estas aplicaciones. Syd utiliza varios mecanismos, incluidos seccomp y ptrace para el filtrado de llamadas al sistema, Landlock para restricciones de acceso al sistema de archivos y namespaces para el aislamiento de procesos y dispositivos, para limitar el impacto de estos posibles ataques. El modelo de amenaza asume que los atacantes tienen control sobre el espacio de usuario no confiable y pueden intentar lecturas, escrituras o ejecución de código arbitrario que podrían influir en el comportamiento del sandbox confiable o explotar el manejo de llamadas al sistema. La seguridad de Syd se basa en la corrección de su implementación y las características subyacentes del kernel de Linux que utiliza. Se asume que no hay vulnerabilidades en la intercepción y el manejo de llamadas al sistema de Syd, ni en los mecanismos de aplicación proporcionados por Landlock y namespaces. Los ataques externos a través de vectores de red o acceso físico al hardware se consideran fuera del alcance de este modelo de amenaza.

"El bloqueo del sandbox" es un componente integral de la arquitectura de seguridad de Syd, que rige la configurabilidad y la integridad del entorno del sandbox. Por defecto, el bloqueo del sandbox está configurado en on, lo que efectivamente evita cualquier comando de sandbox adicional después de la configuración inicial, asegurando así que una vez que el sandbox se configura y se ejecuta el proceso principal, las políticas de seguridad permanezcan inalteradas por cualquier

DESCRIPTION

Syd proporciona varios mecanismos de seguridad para proteger el entorno de ejecución del proceso dentro de un sandbox. Uno de estos mecanismos es el bloqueo de la configuración del sandbox. El parámetro sandbox.lock controla cómo se pueden modificar y acceder a la configuración del sandbox después de la inicialización:

  • off: En este modo, todos los procesos dentro del sandbox pueden acceder y modificar la configuración del sandbox. Esta flexibilidad es útil durante la fase de configuración inicial.

  • exec: Solo el proceso inicial del sandbox tiene autoridad para acceder y modificar la configuración. Esto permite que un proceso de confianza establezca los parámetros del sandbox de forma segura. Además, mantiene un pidfd (descriptor de archivo del ID de proceso) del proceso inicial para proteger contra ataques de reciclaje de PID.

  • ipc: La configuración del sandbox se puede acceder a través de un socket UNIX. La accesibilidad desde dentro del sandbox depende de las reglas ACL del sandbox.

  • read: La configuración del sandbox es accesible solo para lectura, no para edición.

  • on: Este modo sella la configuración del sandbox, haciéndola inmutable. Una vez que el sandbox está en este modo, ninguna modificación posterior es posible.

Las transiciones de los modos off, exec e ipc a read o on son unidireccionales e idempotentes. Resultan en que la política del sandbox se sella en memoria utilizando la llamada al sistema mseal(2), ya sea inmediatamente o simultáneamente con el inicio del proceso del sandbox. Las transiciones entre los modos read y on no están permitidas.

"Crypt Sandboxing" en Syd garantiza la confidencialidad e integridad de los archivos especificados cifrándolos de forma transparente utilizando AES-CTR con HMAC-SHA256, incluso cuando los adversarios controlan completamente los procesos dentro del sandbox (es decir, los atacantes pueden ejecutar código arbitrario y realizar cualquier llamada al sistema permitida). En este modelo de amenaza extendido, se reconoce que si bien los atacantes pueden acceder a datos en texto plano dentro de la memoria del sandbox durante la ejecución del proceso, no pueden extraer claves de cifrado ni datos en texto plano fuera del entorno controlado, ni pueden interferir con el proceso de cifrado para filtrar claves o texto plano a almacenamiento persistente o canales externos. Las operaciones criptográficas se realizan a través de sockets de la API de criptografía a nivel de kernel utilizando técnicas de copia cero para evitar que el texto plano resida en buffers de memoria del espacio de usuario accesibles a los atacantes. Los hilos syd_aes responsables del cifrado están confinados con estrictos filtros de seccomp(2), negándoles llamadas al sistema críticas como read(2), open(2) y socket(2), y permitiendo solo operaciones mínimas de write(2) requeridas para metadatos de cifrado (por ejemplo, escribir la etiqueta HMAC y el IV aleatorio en el archivo). Este confinamiento evita la explotación que podría filtrar datos sensibles. Las claves de cifrado se manejan utilizando la interfaz del kernel keyrings(7) y la opción ALG_SET_KEY_BY_KEY_SERIAL de setsockopt(2). El modelo de amenaza confía en el kernel y en la implementación de Syd, asumiendo que los atacantes no pueden explotar vulnerabilidades del kernel para acceder a claves o texto plano dentro de la memoria del kernel u operaciones criptográficas. Además, se emplean bloqueos de archivos antes de intentar cifrar archivos para garantizar un acceso concurrente seguro. En contraste con el modelo de amenaza general, Crypt Sandboxing reconoce que los procesos no confiables dentro del sandbox tienen acceso a datos en texto plano en memoria durante la operación normal, ya que necesitan leer o escribir los archivos en texto plano. Sin embargo, el objetivo es evitar que los atacantes accedan al texto plano fuera del entorno controlado o manipulen el proceso de cifrado para comprometer la confidencialidad e integridad. Esto se logra asegurando que las claves de cifrado permanezcan seguras y que los procesos de cifrado y descifrado estén estrictamente controlados y aislados del código no confiable.

Acceso a la memoria de procesos remotos

Syd niega varias llamadas al sistema que pueden acceder a la memoria de procesos remotos, como ptrace(2) y process_vm_writev(2), y los perfiles de sandboxing comunes como paludis y user, prohíben el acceso de escritura al archivo /proc/pid/mem. Esto hace que los vectores de ataque TOCTOU sean más difíciles de realizar. Consulte la salida del comando syd-ls deny para ver la lista completa de llamadas al sistema denegadas.

Manejo mejorado de PTRACE_TRACEME

A partir de la versión 3.16.3, Syd introdujo una nueva función para gestionar la operación PTRACE_TRACEME, con el objetivo de mejorar el sigilo contra la detección. Tradicionalmente, PTRACE_TRACEME es la única operación de ptrace(2) permitida por un tracee, lo que la convierte en un objetivo común para la detección de ptracers. Al convertir PTRACE_TRACEME en una operación nula (no-op) que siempre tiene éxito, Syd tiene como objetivo prevenir sutilmente métodos de detección simples que dependen de esta operación. Además, otras operaciones de ptrace(2) se modifican para devolver un EPERM ("Operación no permitida") errno(3) en lugar de ENOSYS ("Función no implementada"), lo que ayuda a reducir la probabilidad de que el sandbox sea detectado a través de estos errores. Este enfoque mejora la discreción de la operación de Syd al mitigar tácticas de detección directas utilizadas por procesos monitoreados.

A partir de la versión 3.19.0, Syd extiende esta mitigación y convierte la llamada al sistema ptrace(2) en una no-operación. Nuevamente, esto proporciona una mitigación de mejor esfuerzo contra el uso de solicitudes como PTRACE_ATTACH o PTRACE_SEIZE para detectar un ptracer.

Tenga en cuenta que esta mitigación es simple y de costo cero; sin embargo, un detector de ptrace(2) inteligente puede eludirla con, por ejemplo, un doble ptrace(2) como se ejemplifica aquí: https://arxiv.org/pdf/2109.06127

if(ptrace(PTRACE_TRACEME)==0 && ptrace(PTRACE_TRACEME)==-1){
	evade();
}

Dado que este ejemplo se basa en estados internos de la función y efectos secundarios, elude la mitigación de Syd. En tales casos, el usuario puede optar por la opción trace/allow_unsafe_ptrace:1, cuando Syd no utilizará ptrace(2) *en absoluto*, por lo que no habrá ningún ptracer que detectar para el malware con la bomba lógica.

procfs y devfs reforzados

Para mejorar la seguridad del sistema y mitigar posibles vectores de ataque, Syd impone restricciones en los sistemas de archivos procfs(5) y devfs implementando varias medidas clave: denegando tanto la enumeración como la apertura de dispositivos de bloque y archivos de tipos desconocidos al omitir entradas correspondientes a estos tipos de archivo (identificados por DT_BLK y DT_UNKNOWN) de las listas de directorios y al rechazar operaciones de open(2) sobre ellos. Esto impide la enumeración y el acceso no autorizados a los dispositivos de almacenamiento del sistema, mitigando así la divulgación de información y la manipulación potencial.

Syd también restringe la visibilidad dentro del directorio /proc para que los procesos solo puedan ver sus propios IDs de proceso, evitando efectivamente el descubrimiento y la posible interacción con otros procesos en ejecución, lo que reduce los riesgos de fuga de información, escalada de privilegios y manipulación de procesos. Se niega explícitamente el acceso a las entradas de /proc del propio proceso Syd, lo que protege al gestor del sandbox de la inspección o interferencia y evita el acceso a información sensible sobre el mecanismo de sandboxing que podría ser explotada para eludir los controles de seguridad o escapar del sandbox.

Además, Syd aborda los riesgos asociados con los enlaces simbólicos mágicos en /proc —como /proc/[pid]/exe y /proc/[pid]/fd/*— al denegar el acceso a estos enlaces cuando se refieren a procesos distintos del proceso que realiza la llamada, evitando así la exposición de descriptores de archivo o rutas ejecutables sensibles de otros procesos y mitigando el acceso no autorizado o escenarios de escape de contenedores; esta mitigación puede deshabilitarse con la opción trace/allow_unsafe_magiclinks:1 si es necesario, aunque no se recomienda hacerlo.

En conjunto, estos controles reforzados sobre procfs y devfs reducen significativamente la superficie de ataque al prevenir la divulgación de información, el acceso no autorizado y las posibles escaladas de privilegios, asegurando que las aplicaciones sandboxed operen dentro de un entorno estrictamente controlado y seguro que se adhiere al principio de mínimo privilegio y mantiene la integridad del sistema. proc_pid_status(5) reforzado

A partir de la versión 3.38.0, Syd filtra proc_pid_status(5) en el límite de open(2) para derrotar las heurísticas comunes de huellas dactilares de sandbox al tiempo que preserva la compatibilidad con las herramientas ordinarias. Cuando un proceso (o sus hilos) lee /proc/<pid>/status o /proc/<pid>/task/<tid>/status, Syd normaliza solo los campos críticos para la seguridad: pone a cero TracerPid, NoNewPrivs, Seccomp y Seccomp_filters, y reescribe las frases que revelan la sandbox en Speculation_Store_Bypass y SpeculationIndirectBranch. Esta normalización específica rompe las comprobaciones triviales anti-análisis (presencia de ptracer, sondeos de seccomp/no_new_privs, huellas dactilares de mitigación especulativa) sin alterar el estado del proceso.

El impacto en la seguridad es doble: el código no confiable pierde un oráculo de bajo costo para el descubrimiento del entorno, lo que reduce la probabilidad de bombas lógicas o control de capacidades basado en la detección de sandbox, y los defensores conservan la observabilidad porque la aplicación real del kernel todavía se aplica; solo la vista del espacio de usuario de estos campos seleccionados está enmascarada. Para flujos de trabajo forenses y de depuración que necesitan explícitamente la vista sin filtrar, esta mitigación se puede relajar temporalmente por cada traza con trace/allow_unsafe_proc_pid_status:1, después de lo cual al volver a :0 se restaura el valor predeterminado reforzado que preserva el sigilo.

Denegación de ioctl TIOCLINUX

La limitación en el uso del comando ioctl(2) TIOCLINUX dentro de entornos seguros, similar a la sandbox de Syd, es una medida de seguridad esencial que aborda vulnerabilidades específicas de las operaciones de terminal Linux. El comando ioctl(2) TIOCLINUX ofrece diversas funcionalidades, incluyendo pero sin limitarse a la manipulación de la configuración de la consola, el cambio de modos del teclado y el control de la salida de pantalla. Si bien estas capacidades pueden ser aprovechadas para tareas legítimas de administración del sistema, también introducen riesgos de seguridad potenciales, particularmente en entornos multiusuario o en el contexto de aplicaciones en sandbox.

Las preocupaciones de seguridad que rodean a TIOCLINUX se derivan de su capacidad para alterar comportamientos y configuraciones de terminal de formas que podrían ser explotadas para la divulgación no autorizada de información, la toma de control de terminales o la escalada de privilegios. En resumen, la restricción de TIOCLINUX dentro de entornos seguros es una estrategia de seguridad vital, que aborda los complejos riesgos asociados con las capacidades de manipulación directa de terminales. Esta precaución está en consonancia con los esfuerzos más amplios de la comunidad de seguridad para mitigar vulnerabilidades conocidas y mejorar la postura de seguridad de los sistemas que manejan procesos y datos sensibles.

Syd Sandbox Security Features

Syd is a security-focused sandbox that leverages numerous Linux kernel features to provide robust isolation for sandboxed processes. It implements a comprehensive set of security measures designed to minimize the attack surface and prevent potential vulnerabilities.

Filesystem Security Enhancements

Syd incorporates advanced filesystem security features to restrict sandboxed processes' access. It can mount filesystems with options such as nodev, nosuid, and noexec by default, preventing the execution of arbitrary code and the misuse of device files. Furthermore, Syd allows for fine-grained control over filesystem access by enabling users to specify allowed or denied paths using the allow and deny directives, respectively. This flexibility extends to the ability to explicitly exclude or include specific files or directories, such as /dev/null, /dev/random, /dev/urandom, and /dev/fuse, providing a versatile tool for further restricting sandboxed processes' access to the filesystem.

Syd also introduces enhanced isolation within the mount namespace by offering options to bind mount temporary directories over /dev/shm and /tmp, ensuring that sandboxed processes have private instances of these directories. This prevents inter-process communication through shared memory and mitigates the risk of temporary file-based attacks, further solidifying the sandbox's defence mechanisms. As of version 3.35.2, an empty mount namespace may be built from scratch starting with the root:tmpfs command. As of version 3.11.2, Syd mounts the procfs(5) filesystem privately with the hidepid=2 option, enhancing privacy by concealing process information from unauthorised users. As of version 3.37.2, this option is changed to hidepid=4 which is new in Linux>=5.8 for added hardening. As of version 3.39.0 the option subset=pid is also supplied to private procfs(5) mount for added hardening. This option is also new in Linux>=5.8.

Syd's container and immutable profiles exemplify its adaptability, offering from isolated to highly restrictive environments. The container profile provides a general-purpose sandbox, while the immutable profile enforces stricter controls, such as making essential system directories read-only, to prevent tampering. This comprehensive approach underlines Syd's adept use of kernel features for robust sandbox security, ensuring a secure and controlled execution environment for sandboxed applications. See syd-cat -pcontainer, and syd-cat -pimmutable to list the rules in these sandboxing profiles.

As of version 3.23.0, Syd has further strengthened its security with the introduction of a time namespace, represented by the unshare/time:1 option, allows Syd to reset the boot-time clock, ensuring that the uptime(1) command reports container uptime instead of host uptime. Moreover, the creation of namespaces, including mount, UTS, IPC, user, PID, net, cgroup, and time is denied by default to prevent unauthorized namespace manipulation that could undermine path sandboxing security. To allow specific namespace types, administrators must explicitly enable them via the trace/allow_unsafe_namespace setting. Another restriction to note is that the system calls mount(2), mount_setattr(2), umount(2), and umount2(2) are denied by default unless mount namespace is allowed. This change ensures tighter control over process capabilities and isolation, reinforcing the defense mechanisms against potential security breaches.

Restricting environment and trace/allow_unsafe_env

As of version 3.11.1, Syd has implemented measures to clear unsafe environment variables, such as LD_PRELOAD, enhancing security by preventing the manipulation of dynamic linker behavior by sandboxed processes. This action mitigates risks associated with dynamic linker hijacking, where adversaries may load malicious shared libraries to execute unauthorised code, potentially leading to privilege escalation, persistence, or defence evasion. Variables like LD_PRELOAD allow specifying additional shared objects to be loaded before any others, which could be exploited to override legitimate functions with malicious ones, thus hijacking the execution flow of a program. To accommodate scenarios where developers might need to use these variables for legitimate purposes, Syd allows this security feature to be disabled at startup with trace/allow_unsafe_env:1, offering flexibility while maintaining a strong security posture. This careful balance ensures that sandboxed applications operate within a tightly controlled environment, significantly reducing the attack surface and enhancing the overall security framework within which these applications run. Refer to the output of the command syd-ls env to see the full list of environment variables that Syd clears from the environment of the sandbox process. As of version 3.39.0, Syd additionally clears LANG and the full set of LC_* locale variables (e.g. LC_CTYPE, LC_TIME, LC_ALL, etc.) to avoid leaking locale settings into the sandboxed process -- preventing subtle behavior differences or information disclosure that could be abused. Similarly, the TZ variable is cleared to prevent leaking timezone settings to the sandbox process. The builtin linux profile masks the file /etc/localtime and the glob(3p) pattern /usr/share/zoneinfo/** with the file /usr/share/zoneinfo/UTC preventing another vector of timezone settings leaking into the environment of the sandbox process. For controlled exceptions, the CLI -e flag provides fine-grained control: -e var=val injects var=val into the child environment, -e var removes var from the child environment, and -e var= explicitly passes through an otherwise unsafe variable; any of these forms may be repeated as needed.

Managing Linux Capabilities for Enhanced Security

Since its 3.0.17 release, Syd strategically curtails specific Linux capabilities(7) for sandboxed processes to bolster security. By revoking privileges such as CAP_SYS_ADMIN among others, Syd significantly reduces the risk of privilege escalation and system compromise. This proactive measure ensures that even if a sandboxed process is compromised, its ability to perform sensitive operations is severely limited. The comprehensive list of dropped capabilities, including but not limited to CAP_NET_ADMIN, CAP_SYS_MODULE, and CAP_SYS_RAWIO, reflects a meticulous approach to minimizing the attack surface. Refer to the output of the command syd-ls drop to see the full list of capabilities(7) that Syd drops at startup.

Exceptions to this stringent policy, introduced in version 3.11.1, such as retaining CAP_NET_BIND_SERVICE with trace/allow_unsafe_bind:1, CAP_NET_RAW with trace/allow_unsafe_socket:1, CAP_SYSLOG with trace/allow_unsafe_syslog:1 and CAP_SYS_TIME with trace/allow_unsafe_time:1, offer a nuanced security model. These exceptions allow for necessary network, syslog and time adjustments within the sandbox, providing flexibility without significantly compromising security.

Since version 3.12.5, Syd allows the user to prevent dropping capabilities at startup using the command trace/allow_unsafe_caps:1. This command may be used to construct privileged containers with Syd.

This balanced strategy of restricting capabilities(7), coupled with selective permissions, exemplifies Syd's commitment to crafting a secure yet functional sandbox environment. By leveraging the granularity of Linux capabilities(7), Syd offers a robust framework for safeguarding applications against a variety of threats, underscoring its role as a pivotal tool in the security arsenal of Linux environments.

Path Resolution Restriction For Chdir and Open Calls

In Syd version 3.15.1, a configurable security feature is available to address the risk of directory traversal attacks by restricting the use of .. components in path arguments for chdir(2), open(2), openat(2), openat2(2), and creat(2) system calls. This feature is off by default, ensuring broad compatibility and operational flexibility for a range of applications. When enabled with the trace/deny_dotdot:1 command, Syd strengthens its defence mechanisms against unauthorised directory access, echoing the flexibility seen in FreeBSD's vfs.lookup_cap_dotdot sysctl. This allows for a nuanced approach to filesystem security, where administrators can tailor the sandbox's behavior to match specific security requirements or operational contexts. By drawing on the security insights of FreeBSD and HardenedBSD, Syd provides a versatile toolset for managing path traversal security, adaptable to the unique demands of various application environments. Enhanced Symbolic Link Validation

As of version 3.13.0, Syd enhances security by enforcing stricter validation on symbolic links within /proc/pid/fd, /proc/pid/cwd, /proc/pid/exe, and /proc/pid/root, addressing potential misuse in container escape scenarios. Según la página man de Linux para execve(2): "En Linux, argv y envp pueden especificarse como NULL. En ambos casos, esto tiene el mismo efecto que especificar el argumento como un puntero a una lista que contiene un solo puntero nulo. No aproveche esta característica errónea no estándar y no portable. En muchos otros sistemas UNIX, especificar argv como NULL resultará en un error (EFAULT: "Dirección incorrecta"). Algunos otros sistemas UNIX tratan el caso envp==NULL igual que Linux." Basado en esta guía, Syd ahora rechaza execve(2) y execveat(2) con EFAULT cuando uno de los argumentos pathname, argv y envp es NULL. Esta mitigación se dirige a cadenas ROP básicas donde se utilizan punteros NULL como marcadores de posición para eludir las comprobaciones de validación de argumentos, una táctica común en la explotación de vulnerabilidades de desbordamiento de búfer. Por ejemplo, una cadena ROP típica que intenta ejecutar execve(2) con argv y envp establecidos en NULL sería interceptada y denegada bajo estas reglas:

0x0000:         0x40ee2b pop rdx; ret
0x0008:              0x0 [arg2] rdx = 0
0x0010:         0x402885 pop rsi; ret
0x0018:              0x0 [arg1] rsi = 0
0x0020:         0x4013cc pop rdi; ret
0x0028:         0x460000 [arg0] rdi = 4587520
0x0030:         0x438780 execve

Un atacante podría eludir esta mitigación asegurándose de que ninguno de los argumentos críticos de la llamada al sistema sea NULL. Esto requiere una configuración más sofisticada en la cadena ROP, aumentando potencialmente la complejidad de la explotación y reduciendo el número de objetivos vulnerables. Esta medida de seguridad enfocada mejora la resiliencia del sistema contra exploits ROP simples mientras mantiene el cumplimiento de los estándares POSIX, promoviendo la robustez y la seguridad multiplataforma.

A partir de la versión 3.25.0, Syd termina el proceso al entrar en estas llamadas al sistema con argumentos NULL en lugar de denegarlas con EFAULT. Esto asegura que el administrador del sistema reciba una notificación a través del registro de auditoría del kernel, es decir, dmesg(1), sobre actividad potencialmente maliciosa. Además, los fallos repetidos activarán SegvGuard.

Securebits y Ejecutabilidad Asistida por Kernel

A partir de la versión 3.41.0, Syd inicializa los securebits por hilo de manera cooperativa con el kernel: en Linux 6.14 y versiones posteriores, que proporcionan la interfaz de verificación de ejecutabilidad (execveat(2) con AT_EXECVE_CHECK) y los securebits correspondientes de auto-restricción del intérprete, Syd primero intenta instalar una configuración integral de securebits (con bloqueos) que refuerza la semántica de capacidades y las restricciones de ejecución; si el kernel rechaza los cambios debido a privilegios (por ejemplo, CAP_SETPCAP no presente) y devuelve EPERM ("Operación no permitida"), Syd degrada de forma determinista a la política desprivilegiada orientada al intérprete solamente, habilitando y bloqueando así una verificación de ejecutabilidad basada en descriptores de archivo y prohibiendo la ejecución de fragmentos interactivos a menos que la misma sonda del kernel tenga éxito, mientras que en kernels más antiguos la configuración de la política secure-exec se trata como una operación nula y el inicio procede sin alterar el comportamiento de ejecutabilidad; esta inicialización se hereda a través de forks y execs (con la regla del kernel de que el flag base de mantener capacidades se borra en exec), es ortogonal al atributo no_new_privs, y está diseñada para ser monótona y predecible en despliegues de privilegios mixtos y kernels mixtos: las características no soportadas se ignoran, los fallos de permiso no abortan el inicio, y el estado resultante es la política más fuerte que el kernel aceptará; Mitigación contra la Programación Orientada a Sigretorno (SROP)

A partir de la versión 3.30.0, Syd emplea una estrategia de mitigación robusta y de múltiples capas contra la Programación Orientada a Sigretorno (SROP), una sofisticada técnica de explotación que manipula el comportamiento de restauración del estado de la llamada al sistema sigreturn(2) para secuestrar la ejecución del proceso. Este enfoque aborda la capacidad de SROP para eludir protecciones críticas de memoria como ASLR, NX y RELRO parcial al configurar un marco de pila falso para redirigir el flujo de control al retornar de una señal. Inspirado en la propuesta de Erik Bosman de mayo de 2014 (LKML PATCH 3/4), Syd incorpora un mecanismo de conteo de señales para rastrear el número de señales entregadas a un grupo de hilos, asegurando que cada invocación de sigreturn(2) corresponda a un manejador de señales real y en curso. Una llamada sigreturn(2) no deseada que viola esta regla provoca la terminación del proceso con la señal SIGKILL. Este método proporciona una protección más precisa que los "canaries" del marco de sigreturn(2), que son susceptibles de ser eludidos bajo ciertas condiciones y mejora significativamente la integridad de los entornos sandbox, bloqueando eficazmente una clase crítica de ataques. Los administradores pueden deshabilitar estas mitigaciones a través de la opción trace/allow_unsafe_sigreturn:1, aunque hacerlo expone los sistemas a la explotación y socava la seguridad. Mitigación de Ejecución Especulativa

A partir de la versión 3.30.0, Syd integra un robusto mecanismo de mitigación que aprovecha la llamada al sistema prctl(2) para aplicar controles de ejecución especulativa que fortalezcan el sandbox contra vulnerabilidades avanzadas de ejecución especulativa, como Spectre y ataques de canal lateral relacionados. Tras la inicialización, Syd intenta aplicar la configuración PR_SPEC_FORCE_DISABLE para características críticas de ejecución especulativa — es decir, PR_SPEC_STORE_BYPASS, PR_SPEC_INDIRECT_BRANCH y PR_SPEC_L1D_FLUSH —, deshabilitando así irrevocablemente estas malas características a nivel de CPU cuando sea permisible. Esta postura proactiva asegura que, donde sea compatible con el kernel y el hardware subyacente, la ejecución especulativa se restrinja para eliminar posibles vías de fuga de datos y escalada de privilegios entre dominios de privilegio. La mitigación se aplica de forma condicional basándose en la disponibilidad de control por tarea a través de prctl(2), y cualquier incapacidad para aplicar estas configuraciones debido a restricciones arquitectónicas o permisos insuficientes resulta en mensajes informativos registrados sin interrumpir las operaciones del sandbox. Además, los administradores conservan la capacidad de anular esta estricta postura de seguridad a través de la opción de configuración trace/allow_unsafe_exec_speculative:1, lo que permite flexibilidad en entornos donde los controles de ejecución especulativa pueden necesitar ser relajados por razones de compatibilidad o rendimiento. Este enfoque dual equilibra la aplicación rigurosa de la seguridad con la adaptabilidad operacional, asegurando que Syd mantenga un entorno de ejecución reforzado mientras proporciona mecanismos para excepciones controladas. Al deshabilitar sistemáticamente las vulnerabilidades de ejecución especulativa a nivel de interfaz del kernel, Syd mitiga significativamente el riesgo de sofisticados ataques de canal lateral, mejorando así la integridad y confidencialidad generales de las aplicaciones sandbox. Consulte los siguientes enlaces para obtener más información:

  • https://docs.kernel.org/admin-guide/hw-vuln/spectre.html
  • https://docs.kernel.org/userspace-api/spec_ctrl.html

A partir de la versión 3.35.2, Syd deshabilita las mitigaciones de Speculative Store Bypass para los filtros de seccomp(2) cuando trace/allow_unsafe_exec_speculative:1 se establece al inicio.

Sysinfo Criptográficamente Aleatorizado

Desde Syd 3.28.0, la llamada al sistema sysinfo(2) se ha ofuscado criptográficamente aplicando desplazamientos de alta entropía a los campos de memoria (por ejemplo, RAM total, RAM libre) y limitándolos a límites plausibles de potencias de dos, frustrando intentos triviales de huella digital del sistema. Específicamente, los contadores de tiempo de actividad e inactividad incorporan cada uno un desplazamiento distinto de hasta 0xFF_FFFF (~194 días), mientras que las cargas promedio se aleatorizan en formato de punto fijo y se limitan a límites superiores realistas. Los administradores que buscan métricas de sistema genuinas pueden deshabilitar estas transformaciones a través de trace/allow_unsafe_sysinfo:1, aunque a costa de permitir una correlación sencilla y una posible fuga de datos.

Sellado de Memoria de Regiones de Política del Sandbox al Bloquear

A partir de la versión 3.33.1, Syd aplica la llamada al sistema mseal(2) de Linux para aplicar la inmutabilidad de las regiones de memoria críticas para la política en el momento en que el sandbox se bloquea con lock:on. En este punto, todas las estructuras mutables que influyen en el control de acceso —como ACL, filtros de acciones y reglas de mediación de llamadas al sistema— se sellan a nivel de memoria virtual. A diferencia de los esquemas de permisos tradicionales (por ejemplo, W^X o mprotect(2)), mseal(2) protege contra la manipulación estructural de los propios mapeos de memoria, evitando que mmap(2), mremap(2), mprotect(2), munmap(2) y operaciones destructivas de madvise(2) alteren los VMA sellados. Esto elimina primitivas de atacante que dependen de la recuperación, remapeo o cambio de permisos en los datos de aplicación, cerrando así rutas de explotación avanzadas orientadas a datos, como la subversión de políticas a través de ACL remapeadas o la revocación de restricciones mediante restablecimientos de permisos de memoria. Syd permite la configuración legítima tardía de políticas durante el inicio y difiere el sellado hasta que se llama a lock:on, después de lo cual la mutación del estado de aplicación se congela estructuralmente. El proceso es unidireccional e idempotente; la memoria sellada no se puede desellar, asegurando fuertes garantías una vez que el bloqueo se completa. Para entornos de diagnóstico o no reforzados, este mecanismo puede deshabilitarse explícitamente a través del interruptor de inicio trace/allow_unsafe_nomseal:1, que solo debe usarse con plena conciencia de la relajación resultante en la protección. Cuando está habilitado, el sellado eleva sustancialmente el umbral de integridad del sandbox, asegurando que la aplicación de políticas posterior al bloqueo sea inmune a la manipulación tanto directa como indirecta a nivel de memoria.

Forzar Descriptores de Archivo Close-on-Exec

La opción trace/force_cloexec, introducida en la versión 3.35.2 de Syd, asegura que todas las llamadas al sistema creat(2), open(2), openat(2), openat2(2), memfd_create(2), socket(2), accept(2) y accept4(2) realizadas por el proceso sandbox incluyan el flag O_CLOEXEC. Esta característica se puede activar en tiempo de ejecución a través de la API de estado virtual de Syd, permitiendo el ajuste dinámico de los niveles de confinamiento según sea necesario. El flag O_CLOEXEC, cuando se establece en los descriptores de archivo, asegura que se cierren automáticamente al ejecutar un nuevo programa a través de execve(2) o llamadas al sistema similares. Este cierre automático de descriptores de archivo es crucial para mejorar la seguridad y la protección, ya que evita que los descriptores de archivo se hereden involuntariamente por programas recién ejecutados, lo que de lo contrario podría conducir a acceso no autorizado a archivos o recursos sensibles. Al forzar el flag O_CLOEXEC en todas las llamadas open(2), Syd mitiga el riesgo de fuga de descriptores de archivo, aislando eficazmente el entorno sandbox y asegurando un contexto de ejecución limpio para los procesos recién iniciados.

Forzar Descriptores de Archivo Aleatorizados

La opción trace/force_rand_fd, introducida en la versión 3.35.2 de Syd, asegura que todas las llamadas al sistema creat(2), open(2), openat(2), openat2(2), memfd_create(2), socket(2), accept(2) y accept4(2) llamadas al sistema realizadas por el sandbox el proceso asigna descriptores de archivo en ranuras disponibles aleatorias en lugar de la de menor número. Cuando esta característica está habilitada, Syd especifica una ranura disponible aleatoria (en lugar de la de menor número) a la operación SECCOMP_IOCTL_NOTIF_ADDFD que se utiliza para instalar un descriptor de archivo en el proceso sandbox. La aleatorización de los números de descriptor de archivo hace que sea significativamente más difícil para un atacante predecir o reutilizar deliberadamente descriptores críticos, elevando así la barrera contra ataques de reutilización y colisión de descriptores de archivo. Tenga en cuenta que habilitar esto puede romper programas que dependen de la garantía POSIX de que open(2) devuelve el descriptor disponible más bajo. Este comportamiento se puede alternar en tiempo de ejecución a través de la API de stat virtual de Syd, permitiendo a los operadores habilitar o deshabilitar la aleatorización de descriptores sin reiniciar o recompilar el proceso en sandbox. También estamos cooperando con el proyecto HardenedBSD para implementar una característica similar en el kernel de BSD. Consulte el siguiente enlace para obtener más información: https://git.hardenedbsd.org/hardenedbsd/HardenedBSD/-/issues/117

Cookies de Argumentos de Llamada al Sistema

Para endurecer aún más el límite de seccomp(2), a partir de la versión 3.35.2 Syd incrusta "cookies" criptográficamente seguras, por instancia, en ranuras de argumentos de llamadas al sistema no utilizadas definidas por la arquitectura (por ejemplo, el 5º y 6º argumentos de openat2(2)). Estas cookies se generan al inicio a través del generador de números aleatorios del sistema operativo utilizando getrandom(2), y se verifican en el filtro BPF para que solo se permitan las llamadas que porten los valores correctos de 32 o 64 bits. Al requerir este token impredecible, Syd eleva la barrera contra llamadas al sistema arbitrarias o falsificadas: los atacantes primero deben descubrir o filtrar las cookies aleatorizadas a pesar de la aleatorización del espacio de direcciones (ASLR) antes de montar una operación de ruta o red exitosa. Este enfoque transforma efectivamente los parámetros de llamada al sistema no utilizados en un mecanismo de autorización a nivel de aplicación, evitando la reutilización trivial de rutas de código legítimas y mitigando cargas útiles de tiempo de verificación a tiempo de uso (TOCTTOU) y ROP que dependen de adivinar u omitir argumentos opcionales. En combinación con la aplicación de rutas absolutas y la denegación de descriptores relativos (por ejemplo, AT_FDCWD), las cookies de argumentos de llamadas al sistema forman una comprobación de integridad ligera y de costo cero que mejora el endurecimiento de las llamadas al sistema sin modificaciones del kernel ni penalizaciones de rendimiento. Endurecimiento de Permisos de Memoria Compartida

A partir de la versión 3.37.0, Syd introduce una mitigación impuesta por el kernel contra la apropiación indebida de memoria compartida de System V al condicionar las reglas de permiso a máscaras de permisos estrictas. Al inspeccionar los bits de modo pasados a las llamadas al sistema shmget(2), msgget(2), semget(2) y mq_open(2), el sandbox admite creaciones solo cuando los campos de permisos de usuario, grupo y otros excluyen flags de escritura o ejecución inseguros (es decir, ningún bit establecido en la máscara 0o177). Esta medida evita que procesos no confiables eleven permisos después de la creación o exploten segmentos IPC heredados con ACL permisivas, lo que podría llevar a la divulgación o corrupción de páginas compartidas. Basado en la taxonomía de ataques descrita en Memory Squatting: Attacks on System V Shared Memory (Portcullis, 2013), las verificaciones de modo se realizan dentro del filtro BPF de seccomp(2) antes de cualquier mapeo. Las operaciones IPC_SET de las llamadas al sistema shmctl(2), msgctl(2) y semctl(2) también se deniegan, lo que evita cambios de permisos después de la creación. Además, cualquier intento de adjuntar un segmento de memoria compartida con el flag SHM_EXEC a través de shmat(2) se deniega para aplicar políticas W^X, bloqueando mapeos ejecutables a través de memoria compartida. El filtro de seccomp(2) también bloquea las operaciones MSG_STAT_ANY, SEM_STAT_ANY y SHM_STAT_ANY (Linux 4.17+), que de lo contrario devolverían metadatos del segmento sin verificar su modo, mitigando fugas de información no deseadas. Esta mitigación se aplica en el filtro de seccomp(2) padre, asegurando que el propio proceso Syd esté sujeto a estas restricciones. Los administradores pueden relajar esta política al inicio utilizando las opciones trace/allow_unsafe_mqueue:1 y trace/allow_unsafe_shm:1, pero al hacerlo se reintroducen las vulnerabilidades clásicas de apropiación indebida documentadas en CVE-2013-0254 e investigación relacionada. NAME

syd - an unprivileged Linux container

SYNOPSIS

syd [OPTION...] COMMAND [ARG...]
syd [OPTION...] -C CONFIG [COMMAND] [ARG...]
syd [OPTION...] -p PROFILE [COMMAND] [ARG...]

DESCRIPTION

Syd is an unprivileged container designed for running applications in isolated environments. It aims to provide a flexible and robust sandboxing solution that can be tailored to various use cases, from development and testing to secure application deployment.

Syd utilizes Linux namespaces, seccomp, and other kernel features to restrict the capabilities and resources available to the sandboxed process. It can enforce fine-grained policies for file system access, network communication, process management, and more.

SANDBOXING

Syd offers a comprehensive sandboxing model that can be configured through command-line options, configuration files, or predefined profiles. The core of Syd's sandboxing capabilities relies on a strict allow-listing approach for system calls and file system operations. This ensures that only explicitly permitted actions are allowed within the sandbox, minimizing the attack surface.

Key features include:

  • System Call Filtering: Utilizes seccomp(2) to filter system calls, allowing only necessary calls for the sandboxed application.
  • File System Isolation: Provides mechanisms to restrict access to specific directories and files, including read-only mounts and symbolic link management.
  • Network Restrictions: Allows for disabling or limiting network access within the sandbox.
  • Resource Limits: Can enforce limits on CPU, memory, and other system resources.
  • Privilege Separation: Designed to run without root privileges, enhancing security.

SECURITY

Syd's security model is built around the principle of least privilege. By default, it restricts applications to the minimum necessary permissions. This includes:

  • No Privilege Escalation: Syd is designed to run unprivileged and does not allow the sandboxed process to gain elevated privileges.
  • Controlled System Calls: A carefully crafted allow-list of system calls prevents potentially harmful operations.
  • Resource Capping: Limits on resources prevent denial-of-service attacks or excessive resource consumption.
  • Secure Defaults: Sensible default configurations aim to provide a secure environment out of the box.

madvise(2) Hardening

Syd implements hardening for the madvise(2) system call to mitigate potential security vulnerabilities. By default, certain `madvise` advice flags that could be misused in an unprivileged container context are blocked. This applies to advice that might allow leaking information about the host system or bypassing sandbox restrictions.

These potentially unsafe `madvise` calls are blocked even if they would otherwise be permitted by the sandbox's general capability checks, as they fall outside the sandbox contract and could pose a security risk. This design choice aligns with the strict system call and argument allow-listing discipline employed by systems like Google's Sandbox2/Sandboxed-API, while remaining specific to Syd's threat model.

To temporarily relax this mitigation for tracing or compatibility purposes, you can set the option trace/allow_unsafe_madvise:1 at startup. Otherwise, unsafe `madvise` advice remains blocked by default.

HISTORY & DESIGN

  • sydbox-0 https://git.sr.ht/~alip/syd/tree/sydbox-0 is a ptrace(2) based sandbox.
  • sydbox-1 https://git.sr.ht/~alip/syd/tree/sydbox-1 is a ptrace(2) and seccomp(2) based sandbox.
  • sydbox-2 https://git.sr.ht/~alip/syd/tree/sydbox-1 is a seccomp(2) and seccomp-notify based sandbox.
  • sydbox-3 is a rewrite of sydbox-2 in Rust and it's what you are looking at.

This codebase has a history of a bit over 15 years and up to this point we have used C11 as our implementation language for various reasons. With sydbox-3 we are moving forwards one step and writing the sandbox from scratch using the Rust programming language with the only non-Rust dependency being libseccomp. Although we inherit many ideas and design decisions from the old codebase, we also don't shy away from radically changing the internal implementation making it much simpler, idiomatic, and less prone to bugs. We have proper multiarch support since release 3.0.11, e.g on x86-64, you can run your x32 or x86 binaries just fine under Syd.

This version takes advantage of multithreading and handles system calls using a thread pool whose size is equal to the number of CPUs on the running machine and utilises globsets to match a list of patterns at once, thus continues to perform reasonably well even with very long rulesets. This version also comes with four new sandboxing categories called Lock Sandboxing, Memory Sandboxing, PID sandboxing, Stat Sandboxing, Force Sandboxing: Lock Sandboxing utilises the Landlock Linux Security Module (LSM), Memory Sandboxing allows the user to define a per-process memory limit, PID sandboxing allows the user to define a limit on the maximum number of running tasks under the sandbox, Stat Sandboxing can be used to effectively hide files and directories from the sandboxed process whereas Force Sandboxing can be used to verify file checksums prior to exec, similar to HardenedBSD's Integriforce and NetBSD's Veriexec.

Finally, the new Syd has support for namespaces. Use e.g. syd -munshare/user:1 to create a user namespace. You may use mount, uts, ipc, pid, net, and cgroup instead of user to create various namespaces. You may use the container profile as a shorthand to create namespaces with syd -pcontainer.

You may use Syd as your login shell because it is very practical to have a restricted user. To do this simply add /path/to/syd to the file /etc/shells and do chsh -s /path/to/syd username as root. In this mode the sandbox may be configured using the files /etc/user.syd-3 and ~/.user.syd-3. If you want to restrict user configuration of the sandbox, lock the sandbox using lock:on at the end of the site-wide configuration file.

EXHERBO

Syd is the default sandbox of Exherbo Linux. We use it to provide a restricted environment under which package builds run with controlled access to file system and network resources. exheres-0 has a function called esandbox to interact with Syd.
