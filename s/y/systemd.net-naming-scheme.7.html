NOMBRE

systemd.net-naming-scheme - Esquemas de nombres para dispositivos de red

DESCRIPCIÓN

Los nombres de las interfaces de red y las direcciones MAC pueden ser generados basándose en ciertos atributos estables de la interfaz. Esto es posible cuando hay suficiente información sobre el dispositivo para generar dichos atributos y se configura el uso de esta información. Esta página describe la asignación de nombres a las interfaces, es decir, qué nombres posibles pueden generarse. Estos nombres son generados por la función interna net_id del servicio systemd-udevd.service(8) y exportados como propiedades de udev(7) (ID_NET_NAME_ONBOARD=, ID_NET_LABEL_ONBOARD=, ID_NET_NAME_PATH=, ID_NET_NAME_SLOT=).

Los nombres y las direcciones MAC se derivan de varios atributos estables de metadatos del dispositivo. Las versiones más recientes de systemd-udevd tienen en cuenta más de estos atributos, mejorando (y por lo tanto, posiblemente cambiando) los nombres y direcciones utilizados para los mismos dispositivos. Diferentes versiones de estas reglas de generación se denominan "esquemas de nombres". El esquema de nombres predeterminado se selecciona en el momento de la compilación. Normalmente, será la última versión implementada, pero también es posible establecer una de las versiones anteriores para preservar la compatibilidad. Esto puede ser útil, por ejemplo, para distribuciones que introducen nuevas versiones de systemd en versiones estables sin cambiar el esquema de nombres. El esquema de nombres también puede ser anulado utilizando el parámetro de línea de comandos del kernel net.naming_scheme=, consulte systemd-udevd.service(8). Los esquemas de nombres disponibles se describen a continuación.

Después de generar las propiedades de udev, se pueden utilizar las reglas de udev apropiadas para renombrar dispositivos basándose en esas propiedades. Consulte la descripción de NamePolicy= y MACAddressPolicy= en systemd.link(5).

Tenga en cuenta que, si bien el concepto de esquemas de nombres de interfaces de red es principalmente relevante en el contexto de systemd-udevd.service, el administrador de contenedores systemd-nspawn(1) también lo tiene en cuenta al asignar nombres a las interfaces de red, consulte a continuación.

El dominio PCI solo se antepone cuando no es 0. Todos los dispositivos PCI multifunción llevarán el número de
ffunción en el nombre del dispositivo, incluido el dispositivo con función 0. Para dispositivos no multifunción, el número se suprime si es 0. Se utiliza el nombre de puerto nombre_puerto, o el número de puerto dpuerto_disp si el nombre no se conoce.

Para dispositivos BCMA, el número de núcleo se suprime cuando es 0.

Para dispositivos USB, se compone la cadena completa de números de puerto de los concentradores. Si el nombre excede el número máximo de 15 caracteres, no se exporta. Los valores habituales de número de configuración USB 1 y número de interfaz 0 se suprimen.

Los dispositivos virtuales SR-IOV se nombran basándose en el nombre de la interfaz padre, con el sufijo v y el número del dispositivo virtual, eliminando los ceros iniciales. Se ignora el número de bus.

Los representadores de dispositivos virtuales SR-IOV se nombran basándose en el nombre de la interfaz del dispositivo físico, con el sufijo r y el número del dispositivo virtual vinculado al representador particular, eliminando los ceros iniciales. Se ignora el nombre del puerto físico y el número de bus.

En algunas configuraciones, un puente PCI padre de un controlador de red dado puede estar asociado con un slot. En ese caso, no generamos esta propiedad del dispositivo para evitar posibles conflictos de nombres.

HISTORIA

Se han definido los siguientes "esquemas de nombres" (que pueden ser elegidos en tiempo de arranque del sistema a través del conmutador de línea de comandos del kernel net.naming_scheme=, véase más arriba):

v238

Este es el esquema de nombres que se implementó en systemd 238.

Añadido en la versión 243.

v239

Se modificó la denominación de las interfaces de red virtuales creadas con SR-IOV y NPAR, y para dispositivos en los que el controlador de red PCI no tiene una ranura asociada.

Los dispositivos virtuales SR-IOV se nombran basándose en el nombre de la interfaz principal, con el sufijo "vport", donde port es el número del dispositivo virtual. Anteriormente, esos dispositivos virtuales se nombraban como si fueran completamente independientes.

Los dispositivos virtuales NPAR noveno y posteriores se nombran siguiendo el esquema utilizado para las ocho primeras particiones NPAR. Anteriormente, esos dispositivos no se renombaban y se utilizaba el valor predeterminado del kernel ("ethN").

También se generan nombres para dispositivos PCI en los que el controlador de red PCI no tiene una ranura asociada, pero sí uno de sus padres. Anteriormente, esos dispositivos no se renombaban y se utilizaba el valor predeterminado del kernel.

Añadido en la versión 243.

v240

Se introdujo el prefijo "ib" y los nombres estables para los dispositivos infiniband. Anteriormente, esos dispositivos no se renombaban.

El campo de índice ACPI (utilizado en ID_NET_NAME_ONBOARD=) se utiliza ahora también cuando es 0.

Se introdujo una nueva política de nombres NamePolicy=keep. Con esta política, si el nombre del dispositivo de red ya estaba establecido por el espacio de usuario, el dispositivo no se renombrará de nuevo. Anteriormente, esta política de nombres se aplicaba implícitamente, y ahora debe solicitarse explícitamente. En efecto, esto significa que los dispositivos de red se renombrarán de acuerdo con la configuración, incluso si ya se han renombrado, si keep no se especifica como política de nombres en el archivo .link. Véase systemd.link(5) para una descripción de NamePolicy=.

Añadido en la versión 243.

v241

MACAddressPolicy=persistent se amplió para establecer las direcciones MAC basándose en el nombre del dispositivo. Anteriormente, las direcciones solo se basaban en los atributos ID_NET_NAME_*, lo que significaba que nunca se generarían nombres de interfaz para dispositivos virtuales. Ahora se generará una dirección persistente para la mayoría de los dispositivos, incluidos en particular los puentes.

Nota: cuando el espacio de usuario no establece una dirección MAC para un dispositivo puente, el kernel asignará inicialmente una dirección aleatoria y luego la cambiará cuando el primer dispositivo se esclavice al puente. Con este cambio en la política de nombres, los puentes obtienen una dirección MAC persistente basada en el nombre del puente en lugar del primer dispositivo esclavizado.

Añadido en la versión 243.

v243

Se añadió soporte para renombrar dispositivos netdevsim (simulación de red). Anteriormente, esos dispositivos no se renombaban.

Anteriormente, se anteponía un prefijo de tipo de interfaz de dos letras a ID_NET_LABEL_ONBOARD=. Esto ya no se hace.

Añadido en la versión 243.

v245

Cuando systemd-nspawn(1) deriva el nombre de la interfaz de red del lado del host creada con --network-veth a partir del nombre del contenedor, anteriormente simplemente truncaba el resultado a 15 caracteres si era más largo (ya que esa es la longitud máxima para los nombres de interfaz de red). A partir de ahora, para cualquier nombre de interfaz que fuera más largo que 15 caracteres, los últimos 4 caracteres se establecerán en un valor hash de 24 bits del nombre completo de la interfaz. De esta manera, las colisiones de nombres de interfaz de red entre varios contenedores con nombres similares (que solo difieren en el sufijo del nombre del contenedor) deberían ser menos probables (pero aún posibles, ya que el valor hash de 24 bits es muy pequeño).

Añadido en la versión 245.

v247

Cuando una ranura PCI está asociada a un puente PCI que tiene varios controladores de red hijos, el mismo valor de la propiedad ID_NET_NAME_SLOT podría derivarse para esos controladores. Esto causaría un conflicto de nombres si la propiedad se selecciona como el nombre del dispositivo. Ahora, detectamos esta situación y no producimos la propiedad ID_NET_NAME_SLOT.

Añadido en la versión 247.

v249

Los nombres de ranura PCI hotplug para el controlador PCI s390 son una representación hexadecimal del atributo de dispositivo function_id. Este atributo se utiliza ahora para construir ID_NET_NAME_SLOT. Antes de eso, todos los nombres de ranura se analizaban como números decimales, lo que podía dar lugar a un valor incorrecto de la propiedad ID_NET_NAME_SLOT o a ninguno en absoluto.

Algunas implementaciones de firmware e hipervisor reportan números irrazonablemente altos para el índice integrado. Para evitar la generación de nombres de interfaz integrados falsos, se ignoraron los números de índice mayores que 16381 (2¹⁴-1). Para los dispositivos PCI s390, los valores de índice de hasta 65535 (2¹⁶-1) son válidos. Para tener en cuenta esto, el límite se incrementó a 65535.

La regla de udev(7) NAME= reemplaza ":", "/" y "%" por un guion bajo ("_"), y rechaza cadenas que solo contienen dígitos.

Añadido en la versión 249.

v250

Se añadió un esquema de nombres para las interfaces Xen netfront "vif" basado en el número VIF del lado del invitado establecido desde la configuración de Xen (o el índice de la interfaz en AWS EC2).

Añadido en la versión 250.

v251

Desde la versión v247 ya no establecemos ID_NET_NAME_SLOT si detectamos que un dispositivo PCI asociado a una ranura es un puente PCI, ya que eso crearía un conflicto de nombres si hay más dispositivos hijos en ese puente. Ahora, esto se relaja y utilizaremos la información de la ranura para generar el nombre basándonos en ella, pero solo si el dispositivo PCI tiene múltiples funciones. Esto es seguro porque el número de función distinto forma parte del nombre del dispositivo para los dispositivos multifunción. Nota: esto se revierte en v255. Véase más abajo.

Añadido en la versión 251.

v252

Se añadió un esquema de nombres para dispositivos de plataforma con alias de árbol de dispositivos.

Añadido en la versión 252.

v253

Se estableció ID_NET_NAME_PATH para dispositivos USB no conectados a través de un bus PCI.

Añadido en la versión 253.

v254

Se cambió la denominación de los representadores de dispositivos virtuales SR-IOV, que se puede configurar opcionalmente en tiempo de compilación. Se añadió el sufijo "rslot" para diferenciar los representadores de dispositivos virtuales SR-IOV conectados a una única interfaz de dispositivo físico. Debido a un error, este esquema no fue el esquema predeterminado para la versión 254 de systemd.

Añadido en la versión 255.

Si detectamos que un dispositivo PCI asociado a una ranura es un puente PCI, ya no establecemos ID_NET_NAME_SLOT, revirtiendo un cambio introducido en v251.

Añadido en la versión 255.

El número de ranura PCI ahora se lee del archivo sysfs firmware_node/sun.

LIMITACIÓN DEL USO DE ATRIBUTOS ESPECÍFICOS DE SYSFS

Al crear nombres para tarjetas de red, algunos esquemas de nombres utilizan datos de sysfs poblados por el kernel. Esto significa que, aunque se elija un esquema de nombres específico en udev(7), el nombre de la tarjeta de red aún puede cambiar cuando una nueva versión del kernel agregue un nuevo atributo sysfs. Por ejemplo, si el kernel comienza a establecer phys_port_name, udev agregará el sufijo "nphys_port_name" al nombre del dispositivo.

NAME

systemd.net-naming-scheme - Network device naming scheme

DESCRIPTION

Modern Linux operating systems use a static network interface naming scheme to ensure predictability. This scheme assigns a fixed name to each network device based on its characteristics, rather than relying on the order in which devices are discovered. This manual page describes the scheme used by systemd and how to configure it.

The scheme assigns names following the pattern prefixslot.index. The prefix indicates the type of interface, and the slot and index provide information about its location or characteristics.

The following prefixes are commonly used:

en
Ethernet device.
enC
Ethernet device, where C is a class identifier such as onboard, pci, usb, etc.
wl
Wireless LAN device.
ww
WWAN (Mobile Broadband) device.
ib
InfiniBand device.
tm
Tuner device.
fx
Full-duplex Ethernet device.
sl
Serial line IP device.
us
Unusual device.

The following naming schemes are supported, in order of preference:

1. Onboard device index
Names devices based on their onboard index. This is generally the most reliable scheme for identifying onboard devices. Example: eno1.
2. PCI slot/function number
Names devices based on their PCI Express (PCIe) slot and function number. This is useful for identifying expansion cards. Example: enp3s0.
3. Firmware index number
Names devices based on a firmware-assigned index number. This can be useful when other identifiers are not available or reliable. Example: ens1.
4. MAC address
Names devices based on their MAC address. This is a universally unique identifier but can be less intuitive. Example: enx78e7d1ea46da.
5. Interface path
Names devices based on their path in the sysfs filesystem. This scheme reflects the device's location in the system's hardware tree. Example: enp0s31f6.

The scheme aims to be consistent across reboots and hardware changes, providing a stable naming convention for network interfaces.

POLICIES

The naming scheme follows these policies:

  1. Onboard devices: Network devices physically integrated into the motherboard are assigned names starting with eno. They are enumerated numerically, starting from 1.
  2. PCI devices: Network devices installed in PCI Express slots are assigned names starting with enp (for Ethernet), wlp (for wireless), etc. The name includes the PCI bus, device, and function numbers. For example, a device on bus 00:19.0 would be named enp0s19.
  3. USB devices: Network devices connected via USB are assigned names starting with enx, followed by the device's MAC address.
  4. MAC address: As a fallback, or for certain types of devices like USB adapters, the MAC address is used to generate the interface name. The name starts with enx, wilx, etc., followed by the MAC address.
  5. Interface path: The physical path to the network device in the sysfs filesystem can also be used to derive the name. This scheme is useful for identifying devices in complex or virtualized environments. Example: enp0s31f6.

HISTORY

The predictable network interface naming scheme was introduced to address the variability of interface names assigned by the kernel in older systems. The current scheme, as implemented by systemd, builds upon previous efforts to provide a consistent and understandable naming convention.

This version of the documentation relates to systemd v256 and later.

LIMITING THE USE OF SPECIFIC SYSFS ATTRIBUTES

udev may use information from sysfs attributes to generate network interface names. To control which sysfs attributes udev is allowed to use for this purpose, the following options can be configured:

ID_NET_NAME_ALLOW

This option controls whether udev reads sysfs attributes by default when composing the device name.
  • If set to 0, udev will not read any sysfs attribute by default, unless it is explicitly allowlisted.
  • If set to 1, udev can use any sysfs attribute unless it is explicitly forbidden.

The default value is 1.

Added in version 256.

ID_NET_NAME_ALLOW_sysfsattr=BOOL

This udev property explicitly states if udev shall use the specified sysfsattr, when composing the device name.

Added in version 256.

With these options, users can set an allowlist or denylist for sysfs attributes. To create an allowlist, the user needs to set ID_NET_NAME_ALLOW=0 for the device and then list the allowed attributes with the ID_NET_NAME_ALLOW_sysfsattr=1 options. In case of a denylist, the user needs to provide the list of denied attributes with the ID_NET_NAME_ALLOW_sysfsattr=0 options.
