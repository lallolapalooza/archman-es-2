NOMBRE

systemd-resolved.service, systemd-resolved - Gestor de resolución de nombres de red

SINOPSIS

systemd-resolved.service

/usr/lib/systemd/systemd-resolved

DESCRIPCIÓN

systemd-resolved es un servicio del sistema que proporciona resolución de nombres de red a las aplicaciones locales. Implementa un gestor almacenador en caché y validador de DNS/DNSSEC de tipo stub, así como un gestor y respondedor de LLMNR y MulticastDNS. Las aplicaciones locales pueden enviar solicitudes de resolución de nombres de red a través de tres interfaces:

•La API nativa y con todas las funciones que systemd-resolved expone a través de D-Bus, consulte org.freedesktop.resolve1(5) y org.freedesktop.LogControl1(5) para más detalles. Generalmente se recomienda a los clientes el uso de esta API, ya que es asíncrona y completa (por ejemplo, devuelve correctamente el estado de validación DNSSEC y el ámbito de la interfaz para las direcciones, según sea necesario para soportar redes de enlace local).

•La API nativa que systemd-resolved expone a través de Varlink en el socket AF_UNIX /run/systemd/resolve/io.systemd.Resolve. Esto proporciona una funcionalidad similar a la interfaz D-Bus, pero está disponible durante toda la ejecución, sin necesidad de un servicio broker de bus del sistema D-Bus en ejecución.
•La API glibc getaddrinfo(3) definida por RFC3493[1] y sus funciones relacionadas de resolución, incluida gethostbyname(3). Esta API es ampliamente compatible, incluso fuera de la plataforma Linux. En su forma actual no expone información sobre el estado de validación DNSSEC y solo es síncrona. Esta API está respaldada por el módulo Name Service Switch (NSS) de glibc (nss(5)). Se requiere el uso del módulo NSS nss-resolve(8) para permitir que las funciones de resolución NSS de glibc resuelvan nombres de host a través de systemd-resolved.
•Además, systemd-resolved proporciona un oyente DNS local de tipo stub en las direcciones IP 127.0.0.53 y 127.0.0.54 en la interfaz de loopback local. Los programas que emiten solicitudes DNS directamente, omitiendo cualquier API local, pueden ser dirigidos a este stub, con el fin de conectarlos a systemd-resolved. Tenga en cuenta, sin embargo, que se recomienda encarecidamente que los programas locales utilicen en su lugar las API de bus o NSS de glibc (como se describe anteriormente), ya que varios conceptos de resolución de red (como el direccionamiento de enlace local o los dominios Unicode LLMNR) no se pueden mapear al protocolo DNS de unicast.

El gestor DNS de tipo stub en 127.0.0.53 proporciona el conjunto completo de funciones del gestor local, que incluye la oferta de resolución LLMNR/MulticastDNS. El gestor DNS de tipo stub en 127.0.0.54 proporciona un gestor más limitado, que opera solo en modo "proxy", es decir, pasará la mayoría de los mensajes DNS relativamente sin modificar a los servidores DNS actuales, pero no intentará procesar los mensajes localmente, y por lo tanto no valida DNSSEC ni ofrece LLMNR/MulticastDNS. (Sin embargo, se traducirá a comunicación DNS-over-TLS si es necesario).

Los servidores DNS contactados se determinan a partir de la configuración global en /etc/systemd/resolved.conf, la configuración estática por enlace en los archivos /etc/systemd/network/*.network (en caso de que se utilice systemd-networkd.service(8)), la configuración dinámica por enlace recibida por DHCP, la información proporcionada a través de resolvectl(1) y cualquier información de servidor DNS disponible a través de otros servicios del sistema. Consulte resolved.conf(5) y systemd.network(5) para obtener detalles sobre los propios archivos de configuración de systemd para servidores DNS. Para mejorar la compatibilidad, se lee /etc/resolv.conf para descubrir los servidores DNS del sistema configurados, pero solo si no es un enlace simbólico a /run/systemd/resolve/stub-resolv.conf, /usr/lib/systemd/resolv.conf o /run/systemd/resolve/resolv.conf (ver más abajo).

REGISTROS SINTÉTICOS

systemd-resolved sintetiza registros de recursos DNS (RR) para los siguientes casos:

•El nombre de host local configurado se resuelve a todas las direcciones IP configuradas localmente, ordenadas por su ámbito, o — si no hay ninguna configurada — la dirección IPv4 127.0.0.2 (que está en la interfaz de loopback local) y la dirección IPv6 ::1 (que es el host local).
•Los nombres "localhost" y "localhost.localdomain", así como cualquier nombre de host que termine en ".localhost" o ".localhost.localdomain" se resuelven a las direcciones IP 127.0.0.1 y ::1.
•El nombre de host "_gateway" se resuelve a todas las direcciones de puerta de enlace de enrutamiento predeterminadas actuales, ordenadas por su métrica. Esto asigna un nombre de host estable a la puerta de enlace actual, útil para referenciarla independientemente del estado de configuración de red actual.
•El nombre de host "_outbound" se resuelve a las direcciones IP locales IPv4 e IPv6 que son más probables de utilizarse para la comunicación con otros hosts. Estas son las direcciones de origen preferidas de las puertas de enlace predeterminadas si se especifican, o se determinan solicitando una decisión de enrutamiento a las puertas de enlace predeterminadas configuradas desde el kernel y luego utilizando las direcciones IP locales seleccionadas por esta decisión. Este nombre de host solo está disponible si hay al menos una puerta de enlace saliente local configurada. Esto asigna un nombre de host estable a las direcciones IP de salida locales, útil para referenciarlas independientemente del estado de configuración de red actual.
•El nombre de host "_localdnsstub" se resuelve a la dirección IP 127.0.0.53, es decir, la dirección en la que escucha el stub DNS local (ver más arriba).
•El nombre de host "_localdnsproxy" se resuelve a la dirección IP 127.0.0.54, es decir, la dirección en la que escucha el proxy DNS local (ver más arriba).
•Las asignaciones definidas en /etc/hosts se resuelven a sus direcciones configuradas y viceversa, pero no afectarán a las búsquedas de tipos que no sean de direcciones (como MX). El soporte para /etc/hosts puede deshabilitarse con ReadEtcHosts=no, consulte resolved.conf(5).

PROTOCOLOS Y ENRUTAMIENTO

Las solicitudes de consulta que recibe systemd-resolved.service se enrutan a los servidores DNS disponibles, interfaces LLMNR y MulticastDNS de acuerdo con las siguientes reglas:

•Los nombres para los que se generan registros sintéticos (el nombre de host local, "localhost" y "localdomain", la puerta de enlace local, como se indica en la sección anterior) y las direcciones configuradas en /etc/hosts nunca se enrutan a la red y se envía una respuesta inmediatamente.
•Los nombres de etiqueta única se resuelven usando LLMNR en todas las interfaces locales donde LLMNR está habilitado. Las consultas de direcciones IPv4 solo se envían a través de LLMNR en IPv4, y las consultas de direcciones IPv6 solo se envían a través de LLMNR en IPv6. Tenga en cuenta que las consultas de nombres sintetizados de etiqueta única no se enrutan a LLMNR, MulticastDNS ni a DNS de unicast.
•Las consultas de los registros de direcciones (A y AAAA) de nombres de etiqueta única no sintetizados se resuelven a través de DNS de unicast utilizando dominios de búsqueda. Para cualquier interfaz que defina dominios de búsqueda, dichas consultas se enrutan a los servidores definidos para esa interfaz, sufijados con cada uno de esos dominios de búsqueda. Cuando se definen dominios de búsqueda globales, dichas consultas se enrutan a los servidores globales. Para cada dominio de búsqueda, se realizan consultas sufijando el nombre con cada uno de los dominios de búsqueda en turno. Además, la consulta de nombres de etiqueta única a través de DNS de unicast puede habilitarse con la configuración ResolveUnicastSingleLabel=yes. Los detalles de qué servidores se consultan y cómo se elige la respuesta final se describen a continuación. Tenga en cuenta que esto significa que las consultas de direcciones para nombres de etiqueta única nunca se envían a servidores DNS remotos por defecto, y la resolución solo es posible si se definen dominios de búsqueda.
•Los nombres de etiquetas múltiples con el sufijo de dominio ".local" se resuelven utilizando MulticastDNS en todas las interfaces locales donde MulticastDNS está habilitado. Al igual que con LLMNR, las consultas de direcciones IPv4 se envían a través de IPv4 y las consultas de direcciones IPv6 se envían a través de IPv6.
•Las consultas de nombres de etiquetas múltiples se enrutan a través de DNS de unicast en interfaces locales que tienen un servidor DNS configurado, más los servidores DNS configurados globalmente si los hay. Esto significa que en redes donde el dominio ".local" está definido en un servidor DNS específico del sitio, se necesitan configurar dominios de búsqueda o enrutamiento explícitos para que las búsquedas funcionen dentro de este dominio DNS. Si las búsquedas se enrutan a varias interfaces, se devuelve la primera respuesta exitosa (fusionando efectivamente las zonas de búsqueda en todas las interfaces coincidentes). Si la búsqueda falló en todas las interfaces, se devuelve la última respuesta fallida.

El enrutamiento de las búsquedas se determina por los dominios de enrutamiento por interfaz (búsqueda y solo enrutamiento) y los dominios de búsqueda globales. Consulte systemd.network(5) y resolvectl(1) para obtener una descripción de cómo se configuran dinámicamente estas configuraciones y la discusión de Domains= en resolved.conf(5) para obtener una descripción de la configuración DNS configurada globalmente.

La siguiente lógica de enrutamiento de consultas se aplica a las búsquedas DNS unicast iniciadas por systemd-resolved.service:

• Si un nombre a buscar coincide (es decir, es igual o tiene como sufijo) con alguno de los dominios de enrutamiento configurados (búsqueda o solo enrutamiento) de cualquier enlace, o la configuración DNS global, se determina el dominio de enrutamiento "que mejor coincide": el que coincide con más etiquetas. La consulta se envía entonces a todos los servidores DNS de cualquier enlace o a los servidores DNS configurados globalmente asociados con este dominio de enrutamiento "que mejor coincide". (Tenga en cuenta que más de un enlace puede tener este mismo dominio de enrutamiento "que mejor coincide" configurado, en cuyo caso la consulta se envía a todos ellos en paralelo).

En el caso de nombres de una sola etiqueta, cuando se definen dominios de búsqueda, se aplica la misma lógica, excepto que el nombre se sufija primero con cada uno de los dominios de búsqueda por turno. Tenga en cuenta que esta lógica de búsqueda no se aplica a ningún nombre con al menos un punto. Consulte también la discusión sobre la compatibilidad con el tradicional resolvedor glibc a continuación.

• Si una consulta no coincide con ningún dominio de enrutamiento configurado (ya sea por enlace o global), se envía a todos los servidores DNS configurados en enlaces configurados como ruta predeterminada, así como al servidor DNS configurado globalmente.
• Si no hay servidores DNS configurados en ningún enlace configurado también como ruta predeterminada y no hay ningún servidor DNS global configurado, se utiliza uno de los servidores DNS de reserva compilados.
• De lo contrario, la consulta DNS unicast falla, ya que no se pueden determinar servidores DNS adecuados.

Si un enlace es la ruta predeterminada o no, se puede configurar con el comando resolvectl default-route o la configuración DNSDefaultRoute= en los archivos .network. Si no se configura explícitamente, se determina implícitamente según los dominios DNS configurados para un enlace: si hay un dominio solo de enrutamiento distinto de "~.", se establece como falso por defecto, de lo contrario como verdadero.

Efectivamente, esto significa: para admitir nombres de una sola etiqueta no sintetizados, defina dominios de búsqueda apropiados. Para enrutar preferentemente todas las consultas DNS que no coinciden explícitamente con la configuración del dominio de enrutamiento a un enlace específico, configure un dominio solo de enrutamiento "~." en él. Esto garantizará que otros enlaces no se consideren para estas consultas (a menos que también contengan dicho dominio de enrutamiento). Para enrutar todas estas consultas DNS a un enlace específico solo si ningún otro enlace es preferido, configure el enlace como la ruta predeterminada y no configure un dominio solo de enrutamiento "~." en él. Finalmente, para evitar que un enlace específico reciba tráfico DNS que no coincida con ninguno de sus dominios de enrutamiento configurados, no lo convierta en una ruta predeterminada.

Consulte org.freedesktop.resolve1(5) para obtener información sobre las API de D-Bus que proporciona systemd-resolved.

COMPATIBILIDAD CON EL TRADICIONAL RESOLVEDOR DE ARRANQUE GLIBC

Esta sección proporciona un breve resumen de las diferencias en el resolvedor implementado por nss-resolve(8) junto con systemd-resolved y el tradicional resolvedor de arranque implementado en nss-dns.

• Algunos nombres siempre se resuelven internamente (ver Registros Sintéticos arriba). Tradicionalmente se resolverían por nss-files si se proporcionan en /etc/hosts. Pero tenga en cuenta que los detalles de cómo se construye una consulta están bajo el control de la biblioteca cliente. nss-dns primero intentará resolver nombres utilizando dominios de búsqueda e incluso si esas consultas se enrutan a systemd-resolved, las enviará a través de la red utilizando las reglas habituales para el enrutamiento de nombres de varias etiquetas [3].
• Los nombres de una sola etiqueta no se resuelven para registros A y AAAA utilizando DNS unicast (a menos que se anule con ResolveUnicastSingleLabel=, consulte resolved.conf(5)). Esto es similar a la opción no-tld-query establecida en resolv.conf(5).
• Los dominios de búsqueda no se utilizan para "sufijar" nombres de varias etiquetas. (Sin embargo, los dominios de búsqueda se utilizan para el enrutamiento de la búsqueda, para nombres que originalmente se especificaron como de una sola etiqueta o de varias etiquetas). Cualquier nombre con al menos un punto siempre se interpreta como un FQDN. nss-dns resolvería nombres tanto como relativos (usando dominios de búsqueda) como FQDN absolutos. Algunos nombres se resolverían como relativos primero, y después de que esa consulta fallara, como absolutos, mientras que otros nombres se resolverían en orden inverso. La opción ndots en /etc/resolv.conf se utilizaba para controlar cuántos puntos necesitaba tener el nombre para resolverse como relativo primero. Este resolvedor de arranque no implementa esto en absoluto: los nombres de varias etiquetas solo se resuelven como FQDN.[4]
• Este resolvedor tiene una noción del dominio especial ".local" utilizado para MulticastDNS, y no enrutará consultas con ese sufijo a servidores DNS unicast a menos que se configure explícitamente, ver arriba. Además, las búsquedas inversas de direcciones de enlace local no se envían a servidores DNS unicast.
• Este resolvedor lee y almacena en caché /etc/hosts internamente. (En otras palabras, nss-resolve reemplaza nss-files además de nss-dns). Las entradas en /etc/hosts tienen la máxima prioridad.
• Este resolvedor también implementa LLMNR y MulticastDNS además del clásico protocolo DNS unicast, y resolverá nombres de una sola etiqueta utilizando LLMNR (cuando esté habilitado) y nombres que terminan en ".local" utilizando MulticastDNS (cuando esté habilitado).
• Las variables de entorno $LOCALDOMAIN y $RES_OPTIONS descritas en resolv.conf(5) no son compatibles actualmente.
• El resolvedor nss-dns mantiene poco estado entre consultas DNS posteriores, y para cada consulta siempre habla primero con el primer servidor DNS listado de /etc/resolv.conf, y en caso de fallo continúa con el siguiente hasta llegar al final de la lista, momento en el que la consulta falla. Sin embargo, el resolvedor en systemd-resolved mantiene el estado y hablará continuamente con el mismo servidor para todas las consultas dentro de un ámbito de búsqueda particular hasta que se vea alguna forma de error, momento en el que cambiará al siguiente servidor, y permanecerá con él para todas las consultas en el ámbito hasta el próximo fallo, y así sucesivamente, eventualmente regresando al primer servidor configurado. Esto se hace para optimizar los tiempos de búsqueda, especialmente dado que el resolvedor normalmente debe primero sondear los conjuntos de características del servidor al hablar con un servidor, lo que lleva tiempo. Este comportamiento diferente implica que los servidores DNS listados por ámbito de búsqueda deben ser equivalentes en las zonas que sirven, de modo que enviar una consulta a uno de ellos produzca los mismos resultados que enviarla a otro servidor DNS configurado.

/ETC/RESOLV.CONF

Se admiten cuatro modos de manejo de /etc/resolv.conf (consulte resolv.conf(5)):

• **systemd-resolved** mantiene el archivo /run/systemd/resolve/stub-resolv.conf para compatibilidad con programas Linux tradicionales. Este archivo enumera el stub DNS 127.0.0.53 (ver arriba) como el único servidor DNS. También contiene una lista de dominios de búsqueda que están en uso por systemd-resolved. La lista de dominios de búsqueda se mantiene siempre actualizada. Tenga en cuenta que /run/systemd/resolve/stub-resolv.conf no debe ser utilizado directamente por las aplicaciones, sino solo a través de un enlace simbólico desde /etc/resolv.conf. Este archivo puede ser enlazado simbólicamente desde /etc/resolv.conf para conectar todos los clientes locales que omiten las API de DNS locales a systemd-resolved con la configuración correcta de dominios de búsqueda. Se recomienda este modo de operación.
• Se proporciona un archivo estático /usr/lib/systemd/resolv.conf que enumera el stub DNS 127.0.0.53 (ver arriba) como el único servidor DNS. Este archivo puede ser enlazado simbólicamente desde /etc/resolv.conf para conectar todos los clientes locales que omiten las API de DNS locales a systemd-resolved. Este archivo no contiene dominios de búsqueda.
• **systemd-resolved** mantiene el archivo /run/systemd/resolve/resolv.conf para compatibilidad con programas Linux tradicionales. Este archivo puede ser enlazado simbólicamente desde /etc/resolv.conf y se mantiene siempre actualizado, conteniendo información sobre todos los servidores DNS conocidos. Tenga en cuenta las limitaciones del formato del archivo: no conoce el concepto de servidores DNS por interfaz y, por lo tanto, solo contiene definiciones de servidores DNS a nivel de sistema. Tenga en cuenta que /run/systemd/resolve/resolv.conf no debe ser utilizado directamente por las aplicaciones, sino solo a través de un enlace simbólico desde /etc/resolv.conf. Si se utiliza este modo de operación, los clientes locales que omiten cualquier API de DNS local también omitirán systemd-resolved y hablarán directamente con los servidores DNS conocidos.
• Alternativamente, /etc/resolv.conf puede ser gestionado por otros paquetes, en cuyo caso systemd-resolved lo leerá para obtener datos de configuración DNS. En este modo de operación, systemd-resolved es un consumidor en lugar de un proveedor de este archivo de configuración.

Tenga en cuenta que el modo de operación seleccionado para este archivo se detecta de forma totalmente automática, dependiendo de si /etc/resolv.conf es un enlace simbólico a /run/systemd/resolve/resolv.conf o enumera 127.0.0.53 como servidor DNS.

SEÑALES

SIGUSR1

Al recibir la señal del proceso SIGUSR1, systemd-resolved volcará el contenido de todos los DN
S registro de recursos las cachés que mantiene, así como toda la información de nivel de características que aprendió sobre servidores DNS configurados en los registros del sistema.

Añadido en la versión 231.

SIGUSR2

Al recibir la señal de proceso SIGUSR2, systemd-resolved vaciará todas las cachés que mantiene. Tenga en cuenta que normalmente no debería ser necesario solicitar esto explícitamente, excepto con fines de depuración, ya que systemd-resolved vacía las cachés automáticamente de todos modos cada vez que cambia la configuración de red del host. Enviar esta señal a systemd-resolved es equivalente al comando resolvectl flush-caches, sin embargo, se recomienda este último ya que opera de forma síncrona.

Añadido en la versión 231.

SIGRTMIN+1

Al recibir la señal de proceso SIGRTMIN+1, systemd-resolved olvidará todo lo que aprendió sobre los servidores DNS configurados. Específicamente, se eliminará toda la información sobre el soporte de características del servidor y la lógica de sondeo de características del servidor se reiniciará en la próxima solicitud, comenzando con el nivel más completo. Tenga en cuenta que normalmente no debería ser necesario solicitar esto explícitamente, excepto con fines de depuración, ya que systemd-resolved olvida automáticamente la información aprendida cada vez que cambia la configuración del servidor DNS. Enviar esta señal a systemd-resolved es equivalente al comando resolvectl reset-server-features, sin embargo, se recomienda este último ya que opera de forma síncrona.

Añadido en la versión 235.

SIGHUP

Al recibir la señal de proceso SIGHUP, systemd-resolved vaciará todas las cachés que mantiene, cerrará todas las conexiones TCP abiertas (si las hay) y recargará sus archivos de configuración.

Añadido en la versión 256.

CREDENTIALS

systemd-resolved soporta la lógica de credenciales de servicio tal como está implementada por ImportCredential=/LoadCredential=/SetCredential= (ver systemd.exec(5) para más detalles). Las siguientes credenciales se utilizan cuando se pasan:

network.dns, network.search_domains

Puede contener una lista separada por espacios de direcciones IP de servidores DNS y dominios de búsqueda DNS. Esta información solo se utiliza cuando no se ha proporcionado ninguna configuración explícita a través de /etc/systemd/resolved.conf, /etc/resolv.conf o la línea de comandos del kernel.

Añadido en la versión 253.

LÍNEA DE COMANDOS DEL KERNEL

systemd-resolved también respeta dos opciones de línea de comandos del kernel:

nameserver=, domain=

Toma la dirección IP de un servidor DNS (en el caso de nameserver=) y un dominio de búsqueda DNS (en el caso de domain=). Puede usarse varias veces para definir múltiples servidores DNS/dominios de búsqueda. Si se especifica alguna de estas opciones, no se leerá /etc/resolv.conf y se ignorarán los ajustes DNS= y Domains= de resolved.conf(5). Por lo tanto, estas dos opciones de línea de comandos del kernel anulan la configuración del sistema.

Añadido en la versión 253.

PUERTOS IP

El servicio systemd-resolved escucha en los siguientes puertos IP:

•Puerto 53 en las direcciones IPv4 127.0.0.53 y 127.0.0.54 (ambas en la interfaz de loopback local "lo"). Este es el stub DNS local, como se discutió anteriormente. Se cubren tanto UDP como TCP.
•Puerto 5353 en todas las direcciones locales, tanto IPv4 como IPv6 (0.0.0.0 y ::0), para MulticastDNS en UDP. Tenga en cuenta que aunque el socket está enlazado a todas las interfaces locales a través de las direcciones IP "wildcard" seleccionadas, los datagramas entrantes se filtran por la interfaz de red en la que llegan, y se mantienen alcances de enlace local MulticastDNS separados para cada uno, teniendo en cuenta si MulticastDNS está habilitado para la interfaz o no.
•Puerto 5355 en todas las direcciones locales, tanto IPv4 como IP6 (0.0.0.0 y ::0), para LLMNR, tanto en TCP como en UDP. Al igual que con MulticastDNS, se aplica el filtrado por la interfaz de red entrante.

Actualmente hay más de 1500 nombres de dominio de nivel superior definidos, y se añaden nuevos regularmente, a menudo utilizando nombres "atractivos" que también es probable que se utilicen localmente. No buscar nombres de varias etiquetas de esta manera evita la fragilidad en ambas direcciones: un nombre global válido podría ser oscurecido por un nombre local, y la resolución de un nombre local relativo podría romperse repentinamente cuando se crea un nuevo dominio de nivel superior, o cuando se registra un nuevo subdominio de un dominio de nivel superior. La resolución de cualquier nombre dado como relativo o absoluto evita esta ambigüedad.
