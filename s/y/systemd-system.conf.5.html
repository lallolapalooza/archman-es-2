SYSTEMD-SYSTEM.CONF(5) systemd-system.conf SYSTEMD-SYSTEM.CONF(5)

NOMBRE

systemd-system.conf, system.conf.d, systemd-user.conf, user.conf.d - Archivos de configuración del gestor de servicios del sistema y de la sesión

SINOPSIS

/etc/systemd/system.conf, /run/systemd/system.conf, /usr/lib/systemd/system.conf, /etc/systemd/system.conf.d/*.conf, /run/systemd/system.conf.d/*.conf, /usr/lib/systemd/system.conf.d/*.conf

~/.config/systemd/user.conf, /etc/systemd/user.conf, /run/systemd/user.conf, /usr/lib/systemd/user.conf, /etc/systemd/user.conf.d/*.conf, /run/systemd/user.conf.d/*.conf, /usr/lib/systemd/user.conf.d/*.conf

DESCRIPCIÓN

Cuando se ejecuta como instancia del sistema, systemd interpreta el archivo de configuración system.conf y los archivos en los directorios system.conf.d; cuando se ejecuta como instancia de usuario, interpreta el archivo de configuración user.conf (en orden de prioridad, en el directorio principal del usuario y en /etc/systemd/, /run/systemd/, y /usr/lib/systemd/) y los archivos en los directorios user.conf.d. Estos archivos de configuración contienen algunas configuraciones que controlan las operaciones básicas del gestor.

Ver systemd.syntax(7) para una descripción general de la sintaxis.

DIRECTORIOS DE CONFIGURACIÓN Y PRECEDENCIA

La configuración por defecto se establece durante la compilación, por lo que solo se necesita configuración cuando es necesario desviarse de esos valores predeterminados. El archivo de configuración principal se carga desde uno de los directorios listados en orden de prioridad, solo se utiliza el primer archivo encontrado: /etc/systemd/, /run/systemd/, /usr/local/lib/systemd/ [1], /usr/lib/systemd/. La versión del proveedor del archivo contiene entradas comentadas que muestran los valores predeterminados como guía para el administrador. También se pueden crear anulaciones locales creando "drop-ins", como se describe a continuación. El archivo de configuración principal también se puede editar para este propósito (o una copia en /etc/ si se distribuye bajo /etc/), sin embargo, se recomienda usar "drop-ins" para la configuración local en lugar de modificaciones al archivo de configuración principal.

Además del archivo de configuración principal, se leen fragmentos de configuración "drop-in" de /usr/lib/systemd/*.conf.d/, /usr/local/lib/systemd/*.conf.d/, y /etc/systemd/*.conf.d/. Estos "drop-ins" tienen mayor precedencia y anulan el archivo de configuración principal. Los archivos en los subdirectorios de configuración *.conf.d/ se ordenan por su nombre de archivo en orden lexicográfico, independientemente de en cuál de los subdirectorios residan. Cuando varios archivos especifican la misma opción, para las opciones que aceptan solo un valor único, la entrada en el archivo ordenado último tiene precedencia, y para las opciones que aceptan una lista de valores, las entradas se recopilan a medida que aparecen en los archivos ordenados.

Cuando los paquetes necesitan personalizar la configuración, pueden instalar "drop-ins" bajo /usr/. Los archivos en /etc/ están reservados para el administrador local, quien puede usar esta lógica para anular los archivos de configuración instalados por los paquetes del proveedor. Se deben usar "drop-ins" para anular los "drop-ins" de paquetes, ya que el archivo de configuración principal tiene menor precedencia. Se recomienda prefijar todos los nombres de archivo en esos subdirectorios con un número de dos dígitos y un guion, para simplificar el orden. Esto también define un concepto de prioridades de "drop-in" para permitir a los proveedores de sistemas operativos distribuir "drop-ins" dentro de un rango específico inferior al rango utilizado por los usuarios. Esto debería disminuir el riesgo de que los "drop-ins" de paquetes anulen accidentalmente los "drop-ins" definidos por los usuarios. Se recomienda usar el rango 10-40 para "drop-ins" en /usr/ y el rango 60-90 para "drop-ins" en /etc/ y /run/, para asegurarse de que los "drop-ins" locales y transitorios tengan prioridad sobre los "drop-ins" distribuidos por el proveedor del sistema operativo.

Para deshabilitar un archivo de configuración proporcionado por el proveedor, la forma recomendada es colocar un enlace simbólico a /dev/null en el directorio de configuración en /etc/, con el mismo nombre de archivo que el archivo de configuración del proveedor.

OPCIONES

Todas las opciones se configuran en la sección [Manager]:

LogColor=, LogLevel=, LogLocation=, LogTarget=, LogTime=, DumpCore=yes, CrashChangeVT=no, CrashShell=no, CrashAction=freeze, ShowStatus=yes, DefaultStandardOutput=journal, DefaultStandardError=inherit

Configura varios parámetros de la operación básica del gestor. Estas opciones pueden ser anuladas por los respectivos argumentos del proceso y de la línea de comandos del kernel. Ver systemd(1) para más detalles.

Añadido en la versión 198.

CtrlAltDelBurstAction=

Define qué acción se realizará si el usuario presiona Ctrl-Alt-Suprimir más de 7 veces en 2 segundos. Puede configurarse a "reboot-force", "poweroff-force", "reboot-immediate", "poweroff-immediate" o deshabilitarse con "none". Por defecto es "reboot-force".

Añadido en la versión 232.

StatusUnitFormat=

Toma name, description o combined como valor. Si es name, el gestor del sistema usará nombres de unidad en los mensajes de estado (por ejemplo, "systemd-journald.service"), en lugar de las descripciones más largas y útiles establecidas con Description= (por ejemplo, "Servicio de registro de Journal"). Si es combined, el gestor del sistema usará tanto los nombres de unidad como las descripciones en los mensajes de estado (por ejemplo, "systemd-journald.service - Servicio de registro de Journal").

Ver systemd.unit(5) para más detalles sobre nombres de unidad y Description=.

Añadido en la versión 243.

DefaultTimerAccuracySec=

Establece la precisión por defecto de las unidades de temporizador. Esto controla el valor predeterminado global para el ajuste AccuracySec= de las unidades de temporizador, ver systemd.timer(5) para más detalles. AccuracySec= establecido en unidades individuales anula el valor predeterminado global para la unidad específica. Por defecto es 1 minuto. Tenga en cuenta que la precisión de las unidades de temporizador también se ve afectada por el tiempo de espera del temporizador configurado para PID 1, ver TimerSlackNSec= arriba.

GESTIÓN DE RECURSOS

TimerSlackNSec=

Establece el tiempo de espera del temporizador en nanosegundos para PID 1, que se hereda por todos los procesos ejecutados, a menos que se anule individualmente, por ejemplo, con el ajuste TimerSlackNSec= en las unidades de servicio (para más detalles ver systemd.exec(5)). El tiempo de espera del temporizador controla la precisión de los despertares activados por los temporizadores del sistema. Ver prctl(2) para más información. Tenga en cuenta que, a diferencia de la mayoría de las otras definiciones de intervalos de tiempo, este parámetro toma un valor entero en nanosegundos si no se especifica ninguna unidad. Las unidades de tiempo habituales también se entienden.

Añadido en la versión 198.

CPUAffinity=

Configura la afinidad de CPU para el gestor de servicios, así como la afinidad de CPU por defecto para todos los procesos que se crean. Toma una lista de índices o rangos de CPU separados por espacios en blanco o comas. Los rangos de CPU se especifican por los índices de CPU inferiores y superiores separados por un guion. Esta opción se puede especificar más de una vez, en cuyo caso se fusionan las máscaras de afinidad de CPU especificadas. Si se asigna la cadena vacía, se restablece la máscara, todas las asignaciones anteriores a esta no tendrán efecto. Los servicios individuales pueden anular la afinidad de CPU para sus procesos con el ajuste CPUAffinity= en los archivos de unidad, ver systemd.exec(5).

DefaultTasksMax=

Configure el valor predeterminado para el ajuste TasksMax= por unidad. Consulte systemd.resource-control(5) para obtener detalles. Este ajuste se aplica a todos los tipos de unidades que admiten ajustes de control de recursos, con la excepción de las unidades slice. El valor predeterminado es el 15% del mínimo entre kernel.pid_max=, kernel.threads-max= y el valor pids.max del cgroup raíz. El kernel tiene un valor predeterminado para kernel.pid_max= y un algoritmo de conteo en caso de tener más de 32 núcleos. Por ejemplo, con el kernel.pid_max= predeterminado, DefaultTasksMax= se establece por defecto en 4915, pero podría ser mayor en otros sistemas o menor en contenedores de SO.

DefaultLimitCPU=, DefaultLimitFSIZE=, DefaultLimitDATA=, DefaultLimitSTACK=, DefaultLimitCORE=, DefaultLimitRSS=, DefaultLimitNOFILE=, DefaultLimitAS=, DefaultLimitNPROC=, DefaultLimitMEMLOCK=, DefaultLimitLOCKS=, DefaultLimitSIGPENDING=, DefaultLimitMSGQUEUE=, DefaultLimitNICE=, DefaultLimitRTPRIO=, DefaultLimitRTTIME=

Estos ajustes controlan varios límites de recursos predeterminados para los procesos ejecutados por las unidades. Consulte setrlimit(2) para obtener detalles. Estos ajustes pueden ser sobrescritos en unidades individuales utilizando las directivas LimitXXX= correspondientes y aceptan la misma sintaxis de parámetros, consulte systemd.exec(5) para obtener detalles. Tenga en cuenta que estos límites de recursos son solo valores predeterminados para las unidades, no se aplican al propio proceso del gestor de servicios (es decir, PID 1).

La mayoría de estos ajustes no están definidos, lo que significa que los límites de recursos se heredan del kernel o, si se invoca en un contenedor, del gestor de contenedores. Sin embargo, los siguientes tienen valores predeterminados:

•DefaultLimitNOFILE= tiene el valor predeterminado 1024:524288.
•DefaultLimitMEMLOCK= tiene el valor predeterminado 8M.
•DefaultLimitCORE= no tiene un valor predeterminado, pero vale la pena mencionar que RLIMIT_CORE se establece en "infinito" por PID 1, que es heredado por sus hijos.

Tenga en cuenta que el gestor de servicios internamente en PID 1 aumenta RLIMIT_NOFILE y RLIMIT_MEMLOCK a valores más altos, sin embargo, el límite se revierte a los valores predeterminados mencionados para todos los procesos hijos creados.

WATCHDOG HARDWARE

RuntimeWatchdogSec=, RebootWatchdogSec=, KExecWatchdogSec=

Configure el watchdog de hardware en tiempo de ejecución y en reinicio. Toma un valor de tiempo de espera en segundos (o en otras unidades de tiempo si va seguido de "ms", "min", "h", "d", "w"), o las cadenas especiales "off" o "default". Si se establece en "off" (alternativamente: "0"), la lógica del watchdog se deshabilita: no se abre, configura ni se contacta ningún dispositivo watchdog. Si se establece en la cadena especial "default", el watchdog se abre y se contacta a intervalos regulares, pero el tiempo de espera no se cambia del valor predeterminado. Si se establece en cualquier otro valor de tiempo, el tiempo de espera del watchdog se configura al valor especificado (o a un valor cercano, dependiendo de las capacidades del hardware).

Si RuntimeWatchdogSec= se establece en un valor distinto de cero, el hardware watchdog (/dev/watchdog0 o la ruta especificada con WatchdogDevice= o la opción del kernel systemd.watchdog_device=) se programará para reiniciar automáticamente el sistema si no se contacta dentro del intervalo de tiempo de espera especificado. El gestor del sistema se asegurará de contactarlo al menos una vez en la mitad del intervalo de tiempo de espera especificado. Esta función requiere la presencia de un dispositivo watchdog de hardware, como suele ser el caso en sistemas embebidos y de servidores. No todos los watchdogs de hardware permiten la configuración de todos los valores posibles de tiempo de espera de reinicio, en cuyo caso se selecciona el tiempo de espera disponible más cercano.

RebootWatchdogSec= se puede utilizar para configurar el watchdog de hardware cuando se solicita reiniciar el sistema. Funciona como una red de seguridad para garantizar que el reinicio se produzca incluso si un intento de reinicio limpio falla por tiempo de espera. Tenga en cuenta que el tiempo de espera RebootWatchdogSec= se aplica solo a la segunda fase del reinicio, es decir, después de que todos los servicios regulares ya se hayan terminado, y después de que el proceso del gestor de sistema y servicios (PID 1) haya sido reemplazado por el binario systemd-shutdown, consulte bootup(7) para obtener detalles. Durante la primera fase de la operación de apagado, el sistema y el gestor de servicios permanecen en ejecución, por lo que RuntimeWatchdogSec= todavía se respeta. Para definir un tiempo de espera en esta primera fase del apagado del sistema, configure JobTimeoutSec= y JobTimeoutAction= en la sección [Unit] de la unidad shutdown.target. Por defecto, RuntimeWatchdogSec= es 0 (apagado), y RebootWatchdogSec= es 10min.

KExecWatchdogSec= se puede utilizar para habilitar adicionalmente el watchdog cuando se está ejecutando kexec en lugar de reiniciar. Tenga en cuenta que si el kernel no reinicia el watchdog en kexec (dependiendo del hardware y/o controlador específico), en este caso el watchdog podría no deshabilitarse después de que kexec se ejecute con éxito y, por lo tanto, el sistema podría reiniciarse, a menos que RuntimeWatchdogSec= también esté habilitado al mismo tiempo. Por esta razón, se recomienda habilitar KExecWatchdogSec= solo si RuntimeWatchdogSec= también está habilitado.

Estas configuraciones no tienen efecto si no hay un watchdog de hardware disponible.

Añadido en la versión 198.

RuntimeWatchdogPreSec=

Configure el valor de pre-tiempo de espera del dispositivo watchdog de hardware. Toma un valor de tiempo de espera en segundos (o en otras unidades de tiempo similares a RuntimeWatchdogSec=). Un pre-tiempo de espera del watchdog es una notificación generada por el watchdog antes de que ocurra el reinicio del watchdog en caso de que el watchdog no haya sido atendido. Esta notificación es manejada por el kernel y puede configurarse para realizar una acción (es decir, generar un pánico del kernel) usando RuntimeWatchdogPreGovernor=. No todo el hardware o los controladores watchdog admiten la generación de un pre-tiempo de espera y, dependiendo del estado del sistema, el kernel puede ser incapaz de realizar la acción configurada antes de que el watchdog reinicie. El watchdog se configurará para generar el evento de pre-tiempo de espera en la cantidad de tiempo especificada por RuntimeWatchdogPreSec= antes del tiempo de espera del watchdog en tiempo de ejecución (establecido por RuntimeWatchdogSec=). Por ejemplo, si tenemos RuntimeWatchdogSec=30 y RuntimeWatchdogPreSec=10, entonces el evento de pre-tiempo de espera ocurrirá si el watchdog no ha sido contactado durante 20 segundos (10 segundos antes de que el watchdog se active). Por defecto, RuntimeWatchdogPreSec= es 0 (apagado). El valor establecido para RuntimeWatchdogPreSec= debe ser menor que el valor de tiempo de espera para RuntimeWatchdogSec=. Esta configuración no tiene efecto si no hay un watchdog de hardware disponible o si el watchdog de hardware no admite un pre-tiempo de espera, y será ignorada por el kernel si la configuración es mayor que el tiempo de espera real del watchdog.

Añadido en la versión 251.

RuntimeWatchdogPreGovernor=

Configure la acción que toma el dispositivo watchdog de hardware cuando expira el pre-tiempo de espera. La acción predeterminada para el evento de pre-tiempo de espera depende de la configuración del kernel, pero generalmente es registrar un mensaje del kernel. Para obtener una lista de las acciones válidas disponibles para un dispositivo watchdog determinado, consulte el contenido del archivo /sys/class/watchdog/watchdogX/pretimeout_available_governors. Normalmente, los tipos de gobernador disponibles son noop y panic. La disponibilidad, los nombres y la funcionalidad pueden variar según el controlador de dispositivo específico que se utilice. Si el archivo sysfs pretimeout_available_governors está vacío, el gobernador podría estar compilado como un módulo del kernel y podría necesitar cargarse manualmente (por ejemplo, pretimeout_noop.ko), o el dispositivo watchdog podría no soportar pre-tiempos de espera.

Añadido en la versión 251.

WatchdogDevice=

Configure el dispositivo watchdog de hardware que utilizarán los temporizadores watchdog en tiempo de ejecución y de apagado. Por defecto es /dev/watchdog0. Este ajuste no tiene efecto si no hay un watchdog de hardware disponible.

Añadido en la versión 236.

SEGURIDAD

CapabilityBoundingSet=

Controla qué capacidades se incluyen en el conjunto de límites de capacidades para PID 1 y sus hijos. Consulte capabilities(7) para obtener detalles. Toma una lista de nombres de capacidades separadas por espacios en blanco, tal como las lee cap_from_name(3). Las capacidades listadas se incluirán
en el conjunto de límites, todos los demás se eliminan. Si la lista de capacidades está precedida por ~, se incluirán todas excepto las capacidades listadas, invirtiendo el efecto de la asignación. Tenga en cuenta que esta opción también afecta a las capacidades respectivas en los conjuntos de capacidades efectivo, permitido e heredable. El conjunto de límites de capacidades también puede configurarse individualmente para las unidades usando la directiva CapabilityBoundingSet= para las unidades, pero tenga en cuenta que las capacidades eliminadas para el PID 1 no se pueden recuperar en unidades individuales, se pierden para siempre.

Añadido en la versión 198.

NoNewPrivileges=

Acepta un argumento booleano. Si es verdadero, asegura que el PID 1 y todos sus hijos nunca puedan obtener nuevos privilegios a través de execve(2) (por ejemplo, a través de bits setuid o setgid, o capacidades del sistema de archivos). Por defecto es falso. Las distribuciones de propósito general comúnmente dependen de ejecutables con bits setuid o setgid y, por lo tanto, no funcionarán correctamente con esta opción habilitada. Las unidades individuales no pueden deshabilitar esta opción. Consulte también el **Indicador No Nuevos Privilegios**[2].

Añadido en la versión 239.

ProtectSystem=

Acepta un argumento booleano o la cadena "auto". Si se establece en verdadero, se volverá a montar /usr/ como de solo lectura. Si se establece en "auto" (el valor por defecto) y se ejecuta en un initrd equivalente a verdadero, de lo contrario falso. Esto implementa un subconjunto restringido de la configuración por unidad del mismo nombre, consulte systemd.exec(5) para más detalles: actualmente, los valores "full" o "strict" no son compatibles.

Añadido en la versión 256.

SystemCallArchitectures=

Acepta una lista separada por espacios de identificadores de arquitectura. Selecciona de qué arquitecturas se pueden invocar llamadas al sistema en este sistema. Esto puede usarse como una forma efectiva de deshabilitar la invocación de binarios no nativos en todo el sistema, por ejemplo, para prohibir la ejecución de binarios x86 de 32 bits en sistemas x86-64 de 64 bits. Esta opción opera en todo el sistema y actúa de manera similar a la configuración SystemCallArchitectures= de los archivos de unidad, consulte systemd.exec(5) para más detalles. Esta configuración tiene como valor por defecto una lista vacía, en cuyo caso no se aplica ningún filtrado de llamadas al sistema basado en la arquitectura. Los identificadores de arquitectura conocidos son "x86", "x86-64", "x32", "arm" y el identificador especial "native". Este último se mapea implícitamente a la arquitectura nativa del sistema (o más específicamente, a la arquitectura para la que se compiló el gestor del sistema). Establezca esta configuración en "native" para prohibir la ejecución de cualquier binario no nativo. Cuando un binario ejecuta una llamada al sistema de una arquitectura que no está listada en esta configuración, será terminado inmediatamente con la señal SIGSYS.

TIEMPOS DE ESPERA Y LÍMITES DE TASA

DefaultTimeoutStartSec=, DefaultTimeoutStopSec=, DefaultTimeoutAbortSec=, DefaultRestartSec=

Configura los tiempos de espera por defecto para iniciar, detener y abortar unidades, así como el tiempo por defecto para esperar entre reinicios automáticos de unidades, tal como se configura por unidad en TimeoutStartSec=, TimeoutStopSec=, TimeoutAbortSec= y RestartSec= (para servicios, consulte systemd.service(5) para obtener detalles sobre la configuración por unidad). Para unidades que no son de servicio, DefaultTimeoutStartSec= establece el valor por defecto de TimeoutSec=.

DefaultTimeoutStartSec= y DefaultTimeoutStopSec= tienen como valor por defecto 90 s en el gestor del sistema y 90 s en el gestor de usuario. DefaultTimeoutAbortSec= no se establece por defecto, de modo que todas las unidades recurran a TimeoutStopSec=. DefaultRestartSec= tiene como valor por defecto 100 ms.

Añadido en la versión 209.

DefaultDeviceTimeoutSec=

Configura el tiempo de espera por defecto para esperar dispositivos. Puede cambiarse por dispositivo a través de la opción x-systemd.device-timeout= en /etc/fstab y /etc/crypttab (consulte systemd.mount(5), crypttab(5)). Por defecto es 90 s en el gestor del sistema y 90 s en el gestor de usuario.

Añadido en la versión 252.

DefaultStartLimitIntervalSec=, DefaultStartLimitBurst=

Configuran el límite de tasa de inicio de unidades por defecto, tal como se configura por servicio con StartLimitIntervalSec= y StartLimitBurst=. Consulte systemd.service(5) para obtener detalles sobre la configuración por servicio. DefaultStartLimitIntervalSec= tiene como valor por defecto 10 s. DefaultStartLimitBurst= tiene como valor por defecto 5.

Añadido en la versión 209.

ReloadLimitIntervalSec=, ReloadLimitBurst=

Límite de tasa para las solicitudes daemon-reload y (desde v256) daemon-reexec. La configuración se aplica a ambas operaciones, pero los límites de tasa se rastrean por separado. Por defecto, no está configurado, y se puede solicitar cualquier número de operaciones en cualquier momento. ReloadLimitIntervalSec= acepta un valor en segundos para configurar la ventana de límite de tasa, y ReloadLimitBurst= acepta un entero positivo para configurar el número máximo de operaciones permitidas dentro de la ventana de tiempo configurada.

Añadido en la versión 253.

ENTORNO

DefaultEnvironment=

Configura las variables de entorno que se pasan a todos los procesos ejecutados. Acepta una lista separada por espacios de asignaciones de variables. Consulte environ(7) para obtener detalles sobre las variables de entorno. Este bloque de entorno es interno, y los cambios no se reflejan en el /proc/PID/environ del gestor.

Se admite la expansión simple de especificadores "%", consulte a continuación para ver una lista de especificadores admitidos.

Ejemplo:

DefaultEnvironment="VAR1=palabra1 palabra2" VAR2=palabra3 "VAR3=palabra 5 6"

Establece tres variables "VAR1", "VAR2", "VAR3".

Añadido en la versión 205.

ManagerEnvironment=

Establece variables de entorno para el propio proceso gestor. Acepta una lista separada por espacios de asignaciones de variables en el mismo formato que DefaultEnvironment=, consulte arriba. Estas variables se fusionan en el bloque de entorno existente del proceso gestor. En particular, en el caso del gestor del sistema, este bloque incluye variables establecidas por el kernel basadas en la línea de comandos del kernel, y en el caso del gestor de usuario, las variables pasadas por el gestor del sistema. Después de fusionar estas variables, persistirán hasta que se invaliden, incluso si el gestor se recarga o se reejecuta. En el caso del gestor de usuario, estas variables también son heredadas por los procesos generados por el gestor. Al igual que con DefaultEnvironment=, este bloque de entorno es interno, y los cambios no se reflejan en el /proc/PID/environ del gestor.

Establecer variables de entorno para el proceso gestor puede ser útil para modificar su comportamiento. Consulte **Variables de Entorno Conocidas**[3] para una descripción de algunas variables entendidas por systemd.

Se admite la expansión simple de especificadores "%", consulte a continuación para ver una lista de especificadores admitidos.

Añadido en la versión 248.
