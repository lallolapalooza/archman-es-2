NOMBRE

dnssec-trust-anchors.d, systemd.positive, systemd.negative - archivos de configuración de anclas de confianza DNSSEC

SINOPSIS

/etc/dnssec-trust-anchors.d/*.positive
/run/dnssec-trust-anchors.d/*.positive
/usr/local/lib/dnssec-trust-anchors.d/*.positive
/usr/lib/dnssec-trust-anchors.d/*.positive
/etc/dnssec-trust-anchors.d/*.negative
/run/dnssec-trust-anchors.d/*.negative
/usr/local/lib/dnssec-trust-anchors.d/*.negative
/usr/lib/dnssec-trust-anchors.d/*.negative

DESCRIPCIÓN

Los archivos de configuración de anclas de confianza DNSSEC definen las anclas de confianza positivas y negativas sobre las que systemd-resolved.service(8) basa las pruebas de integridad DNSSEC.

ANCLAS DE CONFIANZA POSITIVAS

Los archivos de configuración de anclas de confianza positivas contienen definiciones de registros de recursos DNSKEY y DS que se utilizan como base para las pruebas de integridad DNSSEC. Consulte la RFC 4035, Sección 4.4[1] para obtener más información sobre las anclas de confianza DNSSEC.

Las anclas de confianza positivas se leen de archivos con el sufijo .positive ubicados en /etc/dnssec-trust-anchors.d/, /run/dnssec-trust-anchors.d/ y /usr/lib/dnssec-trust-anchors.d/. Estos directorios se buscan en el orden especificado, y un archivo de ancla de confianza del mismo nombre en una ruta anterior anula los archivos de ancla de confianza en una ruta posterior. Para deshabilitar un archivo de ancla de confianza distribuido en /usr/lib/dnssec-trust-anchors.d/, es suficiente proporcionar un archivo con el mismo nombre en /etc/dnssec-trust-anchors.d/ o /run/dnssec-trust-anchors.d/ que esté vacío o sea un enlace simbólico a /dev/null ("enmascarado").

Los archivos de anclas de confianza positivas son archivos de texto simples que se parecen a los archivos de zona DNS, como se documenta en la RFC 1035, Sección 5[2]. Se puede listar un registro de recursos DS o DNSKEY por línea. Las líneas vacías y las líneas que comienzan con "#" o ";" se ignoran, lo que se puede usar para comentar. Un registro de recursos DS se especifica como en el siguiente ejemplo:

. IN DS 19036 8 2 49aac11d7b6f6446702e54a1607371607a1a41855200fd2ce1cdde32f24e8fb5

La primera palabra especifica el dominio, use "." para el dominio raíz. El dominio se puede especificar con o sin punto final, lo cual se considera equivalente. La segunda palabra debe ser "IN", la tercera palabra "DS". Las siguientes palabras especifican la etiqueta de clave, el algoritmo de firma, el algoritmo de resumen, seguido de la huella digital de la clave codificada en hexadecimal. Consulte la RFC 4034, Sección 5[3] para obtener detalles sobre la sintaxis precisa y el significado de estos campos.

Alternativamente, se pueden usar registros de recursos DNSKEY para definir anclas de confianza, como en el siguiente ejemplo:

. IN DNSKEY 257 3 8 AwEAAagAIKlVZrpC6Ia7gEzahOR+9W29euxhJhVVLOyQbSEW0O8gcCjFFVQUTf6v58fLjwBd0YI0EzrAcQqBGCzh/RStIoO8g0NfnfL2MTJRkxoXbfDaUeVPQuYEhg37NZWAJQ9VnMVDxP/VHL496M/QZxkjf5/Efucp2gaDX6RS6CXpoY68LsvPVjR0ZSwzz1apAzvN9dlzEheX7ICJBBtuA6G3LQpzW5hOA2hzCTMjJPJ8LbqF6dsV6DoBQzgul0sGIcGOYl7OyQdXfZ57relSQageu+ipAdTTJ25AsRTAoub8ONGcLmqrAmRLKBP1dfwhYB4N7knNnulqQxA+Uk1ihz0=

La primera palabra especifica nuevamente el dominio, la segunda palabra debe ser "IN", seguida de "DNSKEY". Las palabras subsiguientes codifican los campos de indicadores, protocolo y algoritmo de DNSKEY, seguidas de los datos de la clave codificados en Base64. Consulte la RFC 4034, Sección 2[4] para obtener detalles sobre la sintaxis precisa y el significado de estos campos.

Si se definen varios registros DS o DNSKEY para el mismo dominio (posiblemente incluso en diferentes archivos de anclas de confianza), se utilizan todas las claves y se consideran equivalentes como base para las pruebas DNSSEC.

Tenga en cuenta que systemd-resolved utilizará automáticamente una clave de ancla de confianza incorporada para el dominio raíz de Internet si no se definen anclas de confianza positivas para el dominio raíz. En la mayoría de los casos, por lo tanto, no es necesario definir una clave explícita con archivos de anclas de confianza. La clave incorporada se deshabilita tan pronto como se define al menos una clave de ancla de confianza para el dominio raíz en los archivos de anclas de confianza.

En general, se recomienda codificar las anclas de confianza en registros de recursos DS, en lugar de registros de recursos DNSKEY.

Si se encuentra que un ancla de confianza especificada a través de un registro DS ha sido revocada, se elimina automáticamente de la base de datos de anclas de confianza durante la ejecución. Consulte la RFC 5011[5] para obtener detalles sobre las anclas de confianza revocadas. Tenga en cuenta que systemd-resolved no actualizará su base de datos de anclas de confianza de los servidores DNS automáticamente. En su lugar, se recomienda actualizar el software del resolvedor o actualizar la nueva ancla de confianza agregando nuevos archivos de anclas de confianza.

El ancla de confianza DNSSEC actual para el dominio raíz de Internet está disponible en la página de Anclas de confianza y claves de la IANA[6].

ANCLAS DE CONFIANZA NEGATIVAS

Las anclas de confianza negativas definen dominios donde la validación DNSSEC debe desactivarse. Los archivos de anclas de confianza negativas se encuentran en la misma ubicación que los archivos de anclas de confianza positivas y siguen las mismas reglas de anulación. Son archivos de texto con el sufijo .negative. Las líneas vacías y las líneas cuyo primer carácter es ";" se ignoran. Cada línea especifica un nombre de dominio que es la raíz de un subárbol DNS donde la validación debe deshabilitarse. Por ejemplo:

# Mapeos inversos de IPv4
10.in-addr.arpa
16.172.in-addr.arpa
168.192.in-addr.arpa
...
# Algunos dominios personalizados
prod
stag

Las anclas de confianza negativas son útiles para admitir subárboles DNS privados que no están referenciados desde la jerarquía DNS de Internet y no están firmados.

Consulte la RFC 7646[7] para obtener detalles sobre las anclas de confianza negativas.

Si no se configuran archivos de anclas de confianza negativas, se utiliza un conjunto incorporado de dominios de zona DNS privados conocidos como anclas de confianza negativas.

También es posible definir anclas de confianza negativas por interfaz utilizando la configuración DNSSECNegativeTrustAnchors= en los archivos de systemd.network(5).

NAME

systemd.negative(5)

SYNOPSIS

/etc/systemd/system.conf.d/, /usr/lib/systemd/system.conf.d/, /etc/systemd/user.conf.d/, /usr/lib/systemd/user.conf.d/, /etc/systemd/system.conf, /usr/lib/systemd/system.conf, /etc/systemd/user.conf, /usr/lib/systemd/user.conf

DESCRIPTION

The systemd manager and its components may be configured using a variety of files. The configuration files are specified in the SYNOPSIS section. This page is an overview of the configuration parameters available for the systemd manager instance. For a full list of configuration parameters, see systemd.conf(5).

The systemd manager is a system-wide singleton daemon that is responsible for starting, stopping, and supervising system services. It also manages system resources such as devices, mounts, and sockets.

The configuration files are read in the order specified in the SYNOPSIS section. If multiple files specify the same option, the last one read takes precedence.

The configuration files use an INI-style syntax, with sections enclosed in square brackets and options specified as key-value pairs. For example:

[Manager]
LogLevel=info

This sets the log level of the systemd manager to "info".

POSITIVE TRUST ANCHORS

Positive trust anchors are a set of cryptographic keys that are used to verify the authenticity of other cryptographic keys. Systemd uses positive trust anchors to verify the authenticity of the keys used by D-Bus services and other system components.

The following table lists the positive trust anchors used by systemd:

Key Description
systemd.github.com The public key of the systemd project on GitHub. Used to verify the authenticity of systemd releases.
archlinux.org The public key of the Arch Linux project. Used to verify the authenticity of Arch Linux packages.

The positive trust anchors are stored in the /etc/systemd/trust/ directory. Each trust anchor is stored in a separate file, with the filename corresponding to the key name.

For example, the systemd GitHub public key is stored in the /etc/systemd/trust/systemd.github.com file.

NEGATIVE TRUST ANCHORS

Negative trust anchors are a set of cryptographic keys that are used to identify and reject untrusted or compromised cryptographic keys. Systemd uses negative trust anchors to prevent the use of compromised keys by D-Bus services and other system components.

The following table lists the negative trust anchors used by systemd:

Key Description
compromised.github.com A list of compromised keys from the systemd project on GitHub. Used to reject compromised systemd releases.
compromised.archlinux.org A list of compromised keys from the Arch Linux project. Used to reject compromised Arch Linux packages.

The negative trust anchors are stored in the /etc/systemd/badkeys/ directory. Each negative trust anchor is stored in a separate file, with the filename corresponding to the key name.

For example, the list of compromised GitHub keys is stored in the /etc/systemd/badkeys/compromised.github.com file.
