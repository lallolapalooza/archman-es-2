NOMBRE

systemd.network - Configuración de red

SINOPSIS

network.network

DESCRIPCIÓN

Un archivo de texto plano estilo ini que codifica la configuración de red para las interfaces de red que coinciden, utilizado por systemd-networkd(8). Consulte systemd.syntax(7) para una descripción general de la sintaxis.

El archivo de red principal debe tener la extensión .network; otras extensiones se ignoran. Las redes se aplican a los enlaces tan pronto como estos aparecen.

Tenga en cuenta que no todas las configuraciones se pueden realizar con archivos .network, y que puede ser necesario usar archivos systemd.link(5) o systemd.netdev(5) junto con los archivos .network al trabajar con dispositivos de red físicos y virtuales, respectivamente.

Los archivos .network se leen de los archivos ubicados en los directorios de red del sistema /usr/lib/systemd/network y /usr/local/lib/systemd/network [1], el directorio de red volátil en tiempo de ejecución /run/systemd/network y el directorio de administración local de red /etc/systemd/network. Todos los archivos de configuración se ordenan y procesan colectivamente en orden alfanumérico, independientemente de los directorios en los que residan. Sin embargo, los archivos con nombres de archivo idénticos se reemplazan mutuamente. Se recomienda que cada nombre de archivo vaya precedido de un número menor que "70" (por ejemplo, 10-eth0.network). De lo contrario, los archivos .network predeterminados o los generados por systemd-network-generator.service(8) pueden tener precedencia sobre los archivos configurados por el usuario. Los archivos en /etc/ tienen la máxima prioridad, los archivos en /run/ tienen precedencia sobre los archivos con el mismo nombre en /usr/. Esto se puede utilizar para anular un archivo de configuración proporcionado por el sistema con un archivo local si es necesario. Como caso especial, un archivo vacío (tamaño de archivo 0) o un enlace simbólico con el mismo nombre que apunte a /dev/null deshabilita el archivo de configuración por completo (se "enmascara").

Junto con el archivo de red foo.network, puede existir un directorio "drop-in" foo.network.d/. Todos los archivos con el sufijo ".conf" de este directorio se fusionarán en orden alfanumérico y se analizarán después de que se haya analizado el archivo principal. Esto es útil para modificar o agregar configuraciones, sin tener que modificar el archivo de configuración principal. Cada archivo drop-in debe tener encabezados de sección apropiados.

Además de /etc/systemd/network, los directorios drop-in ".d" pueden colocarse en los directorios /usr/lib/systemd/network o /run/systemd/network. Los archivos drop-in en /etc/ tienen precedencia sobre los de /run/, que a su vez tienen precedencia sobre los de /usr/lib/. Los archivos drop-in en cualquiera de estos directorios tienen precedencia sobre el archivo de red principal dondequiera que se encuentre.

OPCIONES DE SECCIÓN [MATCH]

El archivo de red contiene una sección [Match], que determina si un archivo de red dado puede aplicarse a una interfaz dada; y una sección [Network] que especifica cómo debe configurarse la interfaz. Se aplica el primero (en orden alfanumérico) de los archivos de red que coinciden con una interfaz dada, todos los archivos posteriores se ignoran, incluso si también coinciden.

Tenga en cuenta que las interfaces de red que tienen la propiedad udev ID_NET_MANAGED_BY= establecida nunca coincidirán con ningún archivo .network – a menos que el valor de la propiedad sea la cadena "io.systemd.Network" – incluso si la sección [Match] coincidiera de otra manera. Esto puede usarse para excluir interfaces de red específicas de la gestión de systemd-networkd(8), manteniendo genérica la sección [Match]. La propiedad ID_NET_MANAGED_BY= declara así la *propiedad* prevista del dispositivo y permite garantizar que las implementaciones de gestión de red concurrentes no compitan por la gestión de dispositivos específicos.

Se dice que un archivo de red coincide con una interfaz de red si se satisfacen todas las coincidencias especificadas por la sección [Match]. Cuando un archivo de red no contiene configuraciones válidas en la sección [Match], el archivo coincidirá con todas las interfaces y systemd-networkd advertirá sobre ello. Indicación: para evitar la advertencia y dejar claro que se deben emparejar todas las interfaces, agregue lo siguiente:

Name=*

[LINK] SECTION OPTIONS

The [Link] section accepts the following keys:

MACAddress=

The hardware address to set for the device.

Added in version 218.

MTUBytes=

The maximum transmission unit in bytes to set for the device. The usual suffixes K, M, G, are supported and are understood to the base of 1024.

Note that if IPv6 is enabled on the interface, and the MTU is chosen below 1280 (the minimum MTU for IPv6) it will automatically be increased to this value.

Takes a boolean. If set to true, the IPv4 ARP (low-level Address Resolution Protocol) and IPv6 NDP (Neighbor Discovery Protocol) for this interface are enabled. For example, disabling ARP is useful when creating multiple MACVLAN or VLAN virtual interfaces atop a single lower-level physical interface, which will then only serve as a link/"bridge" device aggregating traffic to the same physical link and not participate in the network otherwise. Defaults to unset, and enabled when the IPv4 link-local addressing is enabled in LinkLocalAddressing= or an IPv4 address with DuplicateAddressDetection= enabled is requested. Otherwise, the kernel's default will be used.

Added in version 232.

Multicast=

Takes a boolean. If set to true, the multicast flag on the device is enabled. Defaults to unset and the flag is unchanged. When disabled, IPv6AcceptRA= and IPv6SendRA= cannot be enabled.

Added in version 239.

AllMulticast=

Takes a boolean. If set to true, the driver retrieves all multicast packets from the network. This happens when multicast routing is enabled. Defaults to unset.

Added in version 239.

Promiscuous=

Takes a boolean. If set to true, promiscuous mode of the interface is enabled. Defaults to unset.

If this is set to false for the underlying link of a "passthru" mode MACVLAN/MACVTAP, the virtual interface will be created with the "nopromisc" flag set.

Takes a boolean. When "yes", no attempts are made to bring up or configure matching links, equivalent to when there are no matching network files. Defaults to "no".

[LINK] SECTION OPTIONS

El archivo .link se utiliza para configurar la interfaz de red en el momento en que se descubre. Las opciones aplicables a las secciones [Link] y [Match] se describen a continuación.

El servicio systemd-networkd cambia el flag "IFF_UP" del dispositivo de red, que a veces es controlado por los administradores del sistema ejecutando, por ejemplo, ip link set dev eth0 up o ip link set dev eth0 down, y también puede cambiarse con networkctl up eth0 o networkctl down eth0.

Toma uno de "up", "always-up", "manual", "always-down", "down", o "bound". Cuando es "manual", systemd-networkd no cambiará el estado administrativo del enlace automáticamente; el administrador del sistema deberá subir o bajar la interfaz manualmente, según sea deseado. Cuando es "up" (el valor predeterminado) o "always-up", o "down" o "always-down", systemd-networkd activará o desactivará el enlace, respectivamente, cuando la interfaz sea (re)configurada. Cuando es "always-up" o "always-down", systemd-networkd activará o desactivará el enlace, respectivamente, cada vez que systemd-networkd detecte un cambio en el estado administrativo. Cuando BindCarrier= también está configurado, este se establece automáticamente en "bound" y cualquier otro valor se ignora.

Cuando la política se establece en "down" o "manual", el valor predeterminado de RequiredForOnline= es "no". Cuando la política se establece en "always-down", el valor de RequiredForOnline= se fuerza a "no".

El estado administrativo no es lo mismo que el estado de portadora (carrier), por lo que usar "always-up" no significa que el enlace nunca perderá la portadora. La portadora del enlace depende tanto del estado administrativo como de la conexión física del dispositivo de red. Sin embargo, para evitar fallos de reconfiguración, cuando se utiliza "always-up", IgnoreCarrierLoss= se fuerza a true.

Añadido en la versión 248.

[SR-IOV] SECTION OPTIONS

SR-IOV proporciona la capacidad de particionar un único recurso físico PCI en funciones PCI virtuales que luego pueden ser, por ejemplo, inyectadas en una VM. En el caso de las VFs de red, SR-IOV reduce la latencia y la utilización de la CPU para el tráfico de red norte-sur (es decir, tráfico con puntos finales fuera de la máquina host), al permitir que el tráfico omita la pila de red de la máquina host.

La presencia de una sección [SR-IOV] en un archivo .link provocará la creación y configuración de la función virtual especificada. Dentro de un archivo .network, se configurará la función virtual especificada, pero esta debe existir previamente. Especifique varias secciones [SR-IOV] para configurar varias SR-IOVs.

La sección [SR-IOV] acepta las siguientes claves.

VirtualFunction=

Especifica una Función Virtual (VF), una función PCIe ligera diseñada únicamente para mover datos hacia adentro y hacia afuera. Toma un entero en el rango 0...2147483646. Esta opción es obligatoria.

Añadido en la versión 251.

VLANId=

Especifica el ID de VLAN de la función virtual. Toma un entero en el rango 1...4095.

Añadido en la versión 251.

QualityOfService=

Especifica la calidad de servicio de la función virtual. Toma un entero en el rango 1...4294967294.

Añadido en la versión 251.

VLANProtocol=

Especifica el protocolo VLAN de la función virtual. Toma "802.1Q" o "802.1ad".

Añadido en la versión 251.

MACSpoofCheck=

Toma un booleano. Controla la verificación de suplantación de MAC. Cuando no se establece, se utilizará el valor predeterminado del kernel.

Añadido en la versión 251.

QueryReceiveSideScaling=

Toma un booleano. Activa la capacidad de consultar la configuración de escalado del lado de recepción (RSS) de la función virtual (VF). La información RSS de la VF, como la clave hash RSS, puede considerarse sensible en algunos dispositivos donde esta información se comparte entre la VF y la función física (PF). Cuando no se establece, se utilizará el valor predeterminado del kernel.

Añadido en la versión 251.

Trust=

Toma un booleano. Permite establecer el modo de confianza de la función virtual (VF). Cuando está establecido, los usuarios de VF pueden configurar una característica específica que puede afectar la seguridad y/o el rendimiento. Cuando no se establece, se utilizará el valor predeterminado del kernel.

Añadido en la versión 251.

LinkState=

Permite establecer el estado del enlace de la función virtual (VF). Toma un booleano o un valor especial "auto". Establecer en "auto" significa un reflejo del estado del enlace de la función física (PF), "yes" permite que la VF se comunique con otras VFs en este host incluso si el estado del enlace de la PF está inactivo, "no" hace que el hardware descarte cualquier paquete enviado por la VF. Cuando no se establece, se utilizará el valor predeterminado del kernel.

Añadido en la versión 251.

MACAddress=

Especifica la dirección MAC para la función virtual.

Añadido en la versión 251.

[NETWORK] SECTION OPTIONS

La sección [Network] acepta las siguientes claves:

Description=

Una descripción del dispositivo. Esto solo se utiliza para fines de presentación.

Añadido en la versión 211.

DHCP=

Habilita el soporte del cliente DHCPv4 y/o DHCPv6. Acepta "yes", "no", "ipv4", o "ipv6". El valor predeterminado es "no".

Tenga en cuenta que DHCPv6 se activará por defecto mediante Anuncios de Enrutador (Router Advertisements), si la recepción está habilitada, independientemente de este parámetro. Al habilitar explícitamente el soporte DHCPv6 aquí, el cliente DHCPv6 se iniciará en el modo especificado por la configuración WithoutRA= en la sección [DHCPv6], independientemente de la presencia de enrutadores en el enlace, o de las banderas que pasen los enrutadores. Consulte IPv6AcceptRA=.

Además, tenga en cuenta que, por defecto, el nombre de dominio especificado a través de DHCP no se utiliza para la resolución de nombres. Consulte la opción UseDomains= a continuación.

Consulte las secciones [DHCPv4] o [DHCPv6] a continuación para ver opciones de configuración adicionales para el soporte del cliente DHCP.

Añadido en la versión 211.

DHCPServer=

Toma un booleano. Si se establece en "yes", se iniciará el servidor DHCPv4. El valor predeterminado es "no". Se pueden establecer configuraciones adicionales para el servidor DHCP en la sección [DHCPServer] descrita a continuación.

Incluso si esto está habilitado, el servidor DHCP no se iniciará automáticamente y esperará a que el almacenamiento persistente esté listo para cargar/guardar concesiones en el almacenamiento, a menos que se especifiquen RelayTarget= o PersistLeases=no/runtime en la sección [DHCPServer]. Se iniciará después de que se inicie el servicio systemd-networkd-persistent-storage, que llama a networkctl persistent-storage yes. Consulte networkctl(1) para obtener más detalles.

Añadido en la versión 215.

LinkLocalAddressing=

Habilita la autoconfiguración de direcciones de enlace local. Acepta un booleano, ipv4 y ipv6. Se configura una dirección de enlace local IPv6 cuando es yes o ipv6. Se configura una dirección de enlace local IPv4 cuando es yes o ipv4 y cuando la autoconfiguración DHCPv4 ha sido infructuosa durante algún tiempo. (La autoconfiguración de direcciones de enlace local IPv4 generalmente ocurrirá en paralelo con intentos repetidos de adquirir una concesión DHCPv4).

El valor predeterminado es no cuando se establece KeepMaster= o Bridge= o cuando el MACVLAN=/MACVTAP= especificado tiene Mode=passthru, o ipv6 en caso contrario.

Cuando el direccionamiento de enlace local IPv4 está habilitado, ARP= se habilita a menos que se configure explícitamente.

Añadido en la versión 219.

Especifica cómo se genera la dirección de enlace local IPv6. Toma uno de "eui64", "none", "stable-privacy" y "random". Cuando no se establece, se utiliza "stable-privacy" si se especifica IPv6StableSecretAddress=, y si no, se utiliza "eui64". Tenga en cuenta que si LinkLocalAddressing= es "no" o "ipv4", entonces IPv6LinkLocalAddressGenerationMode= será ignorado. Además, incluso si LinkLocalAddressing= es "yes" o "ipv6", establecer IPv6LinkLocalAddressGenerationMode=none deshabilita la configuración de una dirección de enlace local IPv6.

Toma una dirección IPv6. La dirección especificada se utilizará como secreto estable para generar la dirección de enlace local IPv6. Si esta configuración no se especifica y "stable-privacy" se establece en IPv6LinkLocalAddressGenerationMode=, entonces se generará una dirección secreta estable a partir del ID de la máquina local y el nombre de la interfaz.

Especifica la primera dirección de enlace local IPv4 a intentar. Domains=

Una lista de dominios separados por espacios que deberían resolverse utilizando los servidores DNS en este enlace. El dominio de "enrutamiento solamente" "~." (la tilde que indica la definición de un dominio de enrutamiento, el punto que se refiere al dominio raíz DNS que es el sufijo implícito de todos los nombres DNS válidos) tiene un efecto especial. Esta configuración es útil para preferir un cierto conjunto de servidores DNS si un enlace en el que están conectados está disponible.

Esta configuración es leída por systemd-resolved.service(8). Los "dominios de búsqueda" corresponden a las entradas domain y search en resolv.conf(5). El enrutamiento de nombres de dominio no tiene equivalente en la API tradicional de glibc, que no tiene concepto de servidores de nombres de dominio limitados a un enlace específico.

Etiqueta de Red=etiqueta

Esta configuración proporciona un método para integrar la configuración de red estática y dinámica en las reglas del subsistema **NetLabel**[16] de Linux, utilizado por los **Módulos de Seguridad de Linux (LSMs)**[17] para el control de acceso a la red. La etiqueta, con las reglas LSM adecuadas, puede usarse para controlar la conectividad de (por ejemplo) un servicio con pares en la red local. Al menos con SELinux, solo se puede controlar la entrada, pero no la salida. El beneficio de usar esta configuración es que puede ser posible aplicar la parte de la configuración de NetLabel independiente de la interfaz en una etapa muy temprana de la secuencia de arranque del sistema, en el momento en que las interfaces de red aún no están disponibles, con netlabelctl(8), y la configuración por interfaz con **systemd-networkd** una vez que las interfaces aparecen más tarde. Actualmente, esta característica solo está implementada para SELinux.

La opción espera una sola etiqueta NetLabel. La etiqueta debe cumplir con las restricciones léxicas de las etiquetas LSM. Cuando una interfaz se configura con direcciones IP, las direcciones y las máscaras de subred se anexarán a las reglas de **Etiquetado de Pares de Respaldo de NetLabel**[18]. Se eliminarán cuando la interfaz se desconfigure. Los errores al administrar las etiquetas se ignorarán.


Advertencia
Una vez que el etiquetado está habilitado para el tráfico de red, muchos puntos de control de acceso LSM en la pila de red de Linux pasan de latentes a activos. Se debe tener cuidado para evitar caer en una situación en la que, por ejemplo, la conectividad remota se rompa, cuando la política de seguridad no se ha actualizado para considerar los controles de acceso LSM por paquete y no hay reglas que permitan ningún tráfico de red. Tenga en cuenta también que se necesita configuración adicional con netlabelctl(8).
Ejemplo: 
[Dirección]
Etiqueta de Red=system_u:object_r:localnet_peer_t:s0

Con las reglas de ejemplo aplicándose a la interfaz "eth0", cuando la interfaz se configura con una dirección IPv4 de 10.0.0.123/8, **systemd-networkd** realiza el equivalente a la operación de **netlabelctl**

netlabelctl unlbl add interface eth0 address:10.0.0.0/8 label:system_u:object_r:localnet_peer_t:s0

y la operación inversa cuando la dirección IPv4 se desconfigura. La configuración se puede usar con reglas LSM; en el caso de SELinux para permitir que un dominio SELinux reciba datos de objetos de la clase "peer" de SELinux. Por ejemplo:

type localnet_peer_t;
allow my_server_t localnet_peer_t:peer recv;

El efecto de la configuración y las reglas anteriores (en ausencia de otras reglas, como puede ser el caso) es permitir solo a "my_server_t" (y nada más) recibir datos de la subred local 10.0.0.0/8 de la interfaz "eth0".

Conjunto NFT=fuente:familia:tabla:conjunto

Esta configuración proporciona un método para integrar la configuración de red en reglas de firewall con conjuntos **NFT**[19]. El beneficio de usar la configuración es que la configuración de red estática (o direcciones de red obtenidas dinámicamente, ver directivas similares en otras secciones) se puede usar en reglas de firewall con la indirección de los conjuntos NFT. Por ejemplo, se podría otorgar acceso solo a hosts en la subred local. Las reglas de firewall que utilizan la dirección IP de una interfaz también se actualizan instantáneamente cuando la configuración de red cambia, por ejemplo, a través de DHCP.

Esta opción espera una lista separada por espacios de definiciones de conjuntos NFT. Cada definición consiste en una tupla separada por dos puntos de tipo de origen (uno de "dirección", "prefijo" o "ifindex"), familia de direcciones NFT (uno de "arp", "bridge", "inet", "ip", "ip6", o "netdev"), nombre de tabla y nombre de conjunto. Los nombres de las tablas y conjuntos deben cumplir con las restricciones léxicas de los nombres de tablas NFT. El tipo del elemento utilizado en el filtro NFT debe coincidir con el tipo implícito por la directiva ("dirección", "prefijo" o "ifindex") y el tipo de dirección (IPv4 o IPv6) como se muestra en la tabla a continuación.

Tabla 1. Valores definidos de tipo de origen

Tipo de origen Descripción Nombre de tipo NFT correspondiente
"dirección" dirección IP del host "ipv4_addr" o "ipv6_addr"
"prefijo" prefijo de red "ipv4_addr" o "ipv6_addr", con "intervalo de banderas"
"ifindex" índice de interfaz "iface_index"

Cuando una interfaz se configura con direcciones IP, las direcciones, las máscaras de subred o el índice de interfaz se agregarán a los conjuntos NFT. La información se eliminará cuando la interfaz se desconfigure.
**systemd-networkd** solo inserta elementos en los conjuntos (o los elimina), por lo que las reglas, tablas y conjuntos NFT relacionados deben prepararse en otro lugar con antelación. Los errores al administrar los conjuntos se ignorarán.

Ejemplo:

[Dirección]
Conjunto NFT=prefijo:netdev:filter:eth_ipv4_prefix

Reglas NFT correspondientes:

table netdev filter {
        set eth_ipv4_prefix {
                type ipv4_addr
                flags interval
        }
        chain eth_ingress {
                type filter hook ingress device "eth0" priority filter; policy drop;
                ip daddr != @eth_ipv4_prefix drop
                accept
        }
}

OPCIONES DE LA SECCIÓN [DHCPSERVER]

La sección [DHCPServer] contiene la configuración para el servidor DHCP, si está habilitado a través de la opción DHCPServer= descrita anteriormente:

ServerAddress=

Especifica la dirección del servidor para el servidor DHCP. Toma una dirección IPv4 con longitud de prefijo separada por una barra, por ejemplo, "192.168.0.1/24". [Network]

Address=192.168.0.1/24
Address=192.168.0.2/24
[DHCPServer]
ServerAddress=192.168.0.1/24

o

[Network]
DHCPServer=yes
[Address]
Address=192.168.0.1/24
[Address]
Address=192.168.0.2/24
[DHCPServer]
ServerAddress=192.168.0.1/24

son equivalentes a lo siguiente:

[Network]
DHCPServer=yes
Address=192.168.0.2/24
[DHCPServer]
ServerAddress=192.168.0.1/24

Desde la versión 255, al igual que la configuración Address= en la sección [Network] o [Address], esto también admite una dirección nula, por ejemplo, "0.0.0.0/24", y se seleccionará automáticamente una dirección no utilizada. Para más detalles sobre la selección automática de direcciones, ver la configuración Address= en la sección [Network] arriba.

Configura el grupo de direcciones a repartir. PoolOffset= toma el desplazamiento del grupo desde el inicio de la subred, o cero para usar el valor predeterminado. Controlan el tiempo de arrendamiento DHCP predeterminado y máximo que se pasa a los clientes. # /etc/systemd/network/55-dhcpv6-pd-upstream.network
[Match]
Name=enp1s0
[Network]
DHCP=ipv6
# Las líneas de abajo son opcionales, para asignar también una dirección en el prefijo delegado
# a la interfaz upstream. Descomente las líneas de abajo si es necesario.
#[Network]
#DHCPPrefixDelegation=yes
#[DHCPPrefixDelegation]
#UplinkInterface=:self
#SubnetId=0
#Announce=no
# Si la red upstream no proporciona mensajes de Anuncio de Enrutador (RA),

# modo administrado.
#[Network]
#IPv6AcceptRA=no
#[DHCPv6]
#WithoutRA=solicit
# Si la red upstream proporciona mensajes de Anuncio de Enrutador (RA) con el
# bit Managed sin establecer, descomente las líneas de abajo para que el cliente DHCPv6
# se inicie forzosamente en modo administrado cuando se reciba un RA.
#[DHCPv6]
#UseAddress=no
#[IPv6AcceptRA]
#DHCPv6Client=always
# /etc/systemd/network/55-dhcpv6-pd-downstream.network

Name=enp2s0
