SYDTUTORIAL(7) Manual de Información Miscelánea SYDTUTORIAL(7)

NOMBRE

sydtutorial - Introducción tutorial a Syd

SINOPSIS

syd *

DESCRIPCIÓN

Este tutorial explica cómo hacer sandboxing de aplicaciones usando Syd, escribir perfiles de sandbox y configurar Syd en tiempo de ejecución desde dentro del sandbox. Si en su lugar está interesado principalmente en usar Syd como un sandbox para la compilación de paquetes, como hacemos en Exherbo Linux, puede preferir comenzar con syd(2) y el perfil "paludis" cuyas reglas puede listar usando "syd-cat -p paludis".

INTRODUCCIÓN

Syd es seguro por defecto y altamente configurable para el caso de uso de su aplicación. A medida que avanzamos en los pasos, aprenderá a restringir una aplicación de varias maneras y al mismo tiempo a mantener el sandbox flexible para casos en los que la restricción no es posible y/o necesaria. Para sacar el máximo provecho de este tutorial, se recomienda elegir una aplicación cuya funcionalidad sistémica le sea conocida e intentar hacer sandboxing de esta aplicación de manera similar a las instrucciones en el capítulo respectivo. Esta funcionalidad, sobre todo, incluye las llamadas al sistema que el proceso realiza para interactuar con el kernel de Linux y qué partes del sistema de archivos/red necesita acceder la aplicación para cumplir su funcionalidad correctamente. bpftrace(1) y strace(1) son sus amigos. En un capítulo posterior también conoceremos pandora(1), que es una herramienta para generar perfiles de Syd automáticamente para una aplicación dada, ¡esté atento!

En su sentido más simple, puede pensar en Syd como un proxy entre el kernel de Linux y el proceso del sandbox: Syd verifica los argumentos de las llamadas al sistema para acceder y, si el acceso se otorga, Syd ejecutará la llamada al sistema *en nombre del proceso del sandbox* y devolverá el resultado al proceso del sandbox. De ahora en adelante, esto es importante de tener en cuenta: desde el punto de vista del kernel de Linux, es uno de los hilos manejadores de syscall de Syd el que está ejecutando la syscall, *no* el proceso del sandbox. Esto es necesario para lograr un sandbox libre de "Time-of-check to Time-of-use". Syd hace todo lo posible para reducir los efectos secundarios, por ejemplo, con `ls /proc/self`, el proceso del sandbox todavía verá su propio ID de proceso, no el de Syd.

1.
Aprender haciendo: ¡Trace sus aplicaciones, aprenda los detalles!
2.
Experimentar: ¡Ajuste Syd de varias maneras diferentes y observe los efectos!
3.
Conviértalo en un juego: ¡Intente romper su propio perfil de sandbox que configuró, luego hágalo más estricto y vuelva a intentarlo!

Nota: las versiones están firmadas con esta clave PGP https://keybase.io/alip/pgp_keys.asc, así que tómese el tiempo para verificar el archivo tar que descargó. Si usa cargo para instalar, necesita instalar la biblioteca "libseccomp" manualmente. Esta es una biblioteca relativamente común y está empaquetada por casi todas las distribuciones de Linux en la actualidad. Dos cosas a tener en cuenta:

1.
Instale los encabezados de desarrollo de libseccomp (generalmente incluidos o vienen con, por ejemplo, el paquete libseccomp-devel).
2.
Instale las bibliotecas estáticas de libseccomp si desea enlazar Syd estáticamente (generalmente incluidos o vienen con, por ejemplo, el paquete libseccomp-static).

Una nota final, en el momento de escribir esto, con la versión 2.5.5 de libseccomp, se requiere un libseccomp parcheado para que las interrupciones funcionen correctamente bajo Syd (libseccomp.git ya tiene soporte para la nueva bandera del kernel de Linux, también agregamos un parche para establecerla por defecto). La versión binaria se compila con un libseccomp parcheado y la compilación de fuentes de Exherbo parchea el paquete libseccomp durante la fase de preparación. Tenga en cuenta que, en nuestra experiencia, este error es más notable cuando se hace sandboxing de aplicaciones escritas en el lenguaje Go. De lo contrario, rara vez lo notará con la última versión de libseccomp. Como referencia, el conjunto de parches se encuentra aquí: https://gitlab.exherbo.org/exherbo/arbor/-/tree/master/packages/sys-libs/libseccomp/files

SYD 101

Primero, si ejecuta Syd sin argumentos, entrará silenciosamente en un nuevo shell. Esto se debe a que Syd está diseñado para actuar como un shell de inicio de sesión y en este caso utiliza el perfil de sandbox "user". Llegaremos a los perfiles en un capítulo posterior, pero si tiene curiosidad, ejecute "syd-cat -p user | less" y lea las reglas.

Segundo, Syd es seguro por defecto y le permite construir un sandbox según las necesidades de sus aplicaciones. Así es como se ve el estado del sandbox antes de pasarle alguna opción a Syd:

$ syd -mstat
syd:
Process ID: 0
Lock: None
Capabilities: Read, Stat, Write, Execute, Connect, Bind
Options:
Memory Max: 134217728
Virtual Memory Max: 4294967296
Pid Max: 128
SegvGuard Max Crashes: 5
SegvGuard Expiry: 120 seconds
SegvGuard Suspension: 600 seconds
Allowed UID Transitions: (total: 0, source -> target)
Allowed GID Transitions: (total: 0, source -> target)
Cidr Rules: (total 0, highest precedence first)
Glob Rules: (total 0, highest precedence first)
Mask Rules: (total 1)
1. Pattern: /proc/cmdline
Force Rules: (total 0, default action: Kill)
$

Por ahora, prestemos atención a la línea "Capabilities". Estos son los tipos de sandboxing que están habilitados por defecto al inicio.

Inicialmente, haremos lo mínimo e intentaremos ejecutar un binario enlazado estáticamente bajo Syd. busybox(1) es una herramienta útil para nuestro experimento:

$ file $(which busybox)
/usr/host/bin/busybox: ELF 64-bit LSB executable, x86-64, version 1 (SYSV), statically linked, stripped
$ syd busybox true
syd: exec error: No such file or directory
$ echo $?
2
$ syd-sys -e 2
2       ENOENT  No such file or directory
$

Obtenemos un error de que la ruta no existe. Esto se debe a que el "Sandboxing de Estado" está activado por defecto y la ruta al binario de busybox(1) está oculta. Syd aclara esto por su valor de salida, que error causó que la ejecución fallara. Usamos la utilidad syd-sys(1), una de las muchas utilidades que vienen con syd(1), para buscar la definición del error por el código de salida.

Intentemos permitir y reintentar:

$ syd -m'allow/stat+/usr/host/bin/busybox' busybox true
syd: exec error: No such file or directory
$

Sin suerte, obtenemos el mismo error. Esto se debe a que la ruta que especificamos a "allow/stat" no es una ruta canónica. Una ruta canónica es una ruta que comienza con "/" y no tiene "." ni ".." ni barras repetidas ni enlaces simbólicos en ninguno de sus componentes de ruta. Descubramos la ruta canónica a nuestro binario de busybox(1) y reintentemos con ella.

$ readlink -f /usr/host/bin/busybox
/usr/x86_64-pc-linux-musl/bin/busybox
$ syd -m'allow/stat+/usr/x86_64-pc-linux-musl/bin/busybox' busybox true
{"act":"Deny","cap":"x","ctx":"access","id":"nostalgic_black","l":2,"path":"/usr/x86_64-pc-linux-musl/bin/busybox","pid":2602591,"sys":"execve","uid":1000,...}
syd: exec error: Permission denied
$ echo $?
13
$ syd-sys -e 13
13      EACCES  Permission denied
$

Volvemos a obtener un error, pero esta vez tenemos contexto. Dado que el Sandboxing de Estado se trata de ocultar rutas, informar violaciones de acceso sobre él en la salida estándar iría en contra de su propósito, por lo que Syd fue silencioso. Sin embargo, esta vez vemos el "Sandboxing de Ejecución" en acción y Syd nos da detalles sobre la violación de acceso. El formato es líneas JSON. Puede ser difícil de leer al principio, pero el hecho de que sea fácilmente procesable

seable te permite buscar fácilmente registros de violación de acceso de Syd en el registro de tu sistema y filtrar usando herramientas como jq(1).

Volviendo a la tarea, por ahora observemos brevemente que se trató de una violación de acceso ("ctx":"access") sobre la llamada al sistema execve(2) ("sys":"execve"). La violación de acceso es de la categoría Ejecución ("cap":"x") y la ruta de destino es "/usr/x86_64-pc-linux-musl/bin/busybox". La decisión fue denegar la llamada al sistema ("act":"Deny"). También tenemos metadatos útiles como el ID del proceso ("pid") y el ID del usuario ("uid") que ejecuta la llamada al sistema infractora. El campo "id" es un nombre legible por humanos generado a partir del campo "pid" para facilitar el seguimiento de los registros. Hay más información en los campos omitidos; se recomienda que eches un vistazo a una entrada completa de registro de violación de acceso por tu cuenta y tomes nota de los campos que son de valor para ti. Vamos a permitir esta vez nuestro binario de busybox(1) para ejecución y reintentaremos:

$ syd -m'allow/exec,stat+/usr/x86_64-pc-linux-musl/bin/busybox' busybox true
$ echo $?
$ 0

¡Tarea completada! Nota cómo usamos la notación corta "allow/exec,stat+/ruta", que es una forma conveniente de pasar -m "allow/exec+/ruta" -m "allow/stat+/ruta" como una única regla.

Ahora intentemos de nuevo con un ejecutable enlazado dinámicamente y averigüemos qué tenemos que agregar para que funcione. Esta vez usaremos la utilidad gtrue(1) del proyecto GNU coreutils, que está enlazada dinámicamente en este sistema:

$ file $(which gtrue)
/usr/host/bin/gtrue: ELF 64-bit LSB pie executable, x86-64, version 1 (SYSV), dynamically linked, interpreter /usr/x86_64-pc-linux-musl/lib/ld-musl-x86_64.so.1, stripped
$ lddtree $(which gtrue)
/usr/x86_64-pc-linux-musl/lib/ld-musl-x86_64.so.1 => /usr/x86_64-pc-linux-musl/lib/libc.so
libc.so => /usr/x86_64-pc-linux-musl/lib/libc.so
$ readlink -f $(which gtrue)
/usr/x86_64-pc-linux-musl/bin/gtrue
$ syd -m'allow/exec,stat+/usr/x86_64-pc-linux-musl/bin/gtrue' gtrue
{"act":"Kill","cap":"x","ctx":"access","id":"compassionate_spence","l":2,"path":"/usr/x86_64-pc-linux-musl/lib/libc.so","pid":2601331,"sys":"exec","uid":1000,...}
$ echo $?
137
$

Observando la ruta infractora de la nueva violación de acceso, entendemos que se deniega el acceso de ejecución a libc.so. También podemos observar que, esta vez, Syd ha terminado el proceso ("act":"Kill") en lugar de denegar el acceso a la llamada al sistema ("act":"Deny"). Esto también es evidente en el código de salida, que es 137 = 128 + 9, donde 9 es el valor de la señal "SIGKILL". La distinción entre denegar/matar proviene de los detalles internos de Syd y no es significativa para nosotros en este punto. Basta decir que en ambos casos la ejecución se ha detenido antes de que cualquier código del binario de destino tuviera la oportunidad de ejecutarse.

Durante la verificación de acceso para el Aislamiento de Ejecución, Syd trata los ejecutables enlazados dinámicamente y su árbol de dependencias de bibliotecas dinámicas como una sola unidad. En ese sentido, "allow/read+/ruta/a/libc.so" y "allow/exec+/ruta/a/libc.so" cumplen dos propósitos diferentes: el primero te permite leer literalmente el contenido del archivo, mientras que el segundo te permite cargar el archivo en memoria como parte de un ejecutable.

Con esto aclarado, permitamos libc.so y volvamos a intentarlo:

$ syd -m'allow/exec,stat+/usr/x86_64-pc-linux-musl/bin/gtrue' -m 'allow/exec+/usr/x86_64-pc-linux-musl/lib/libc.so' gtrue
$ echo $?
0
$

¡Tarea completada! El lector curioso reconocerá que no tuvimos que agregar una cláusula "allow/stat" para "libc.so". Esto se debe a que los conceptos de Aislamiento de Estadísticas y Ocultación de Rutas se refieren específicamente al acceso directo a las rutas de archivos. La carga de bibliotecas en memoria es parte del proceso de ejecución y, por lo tanto, solo está sujeta al Aislamiento de Ejecución (y al Aislamiento Forzado, también conocido como Verificación de Binarios, del que hablaremos más adelante).

Ahora, en el tercer paso, generalizaremos nuestro pequeño sandbox para que permita cualquier versión del binario de true(1) que ejecutemos; además, también permitirá la ejecución de cualquier otra utilidad de coreutils prefijada con "g*". Tampoco queremos preocuparnos si "libc.so" tiene un sufijo de versión y queremos permitir todas las bibliotecas bajo las rutas de bibliotecas comunes sin tener que listarlas una por una. Para lograr todo esto, vamos a usar patrones de glob(3):

$ eclectic coreutils list
Available providers for coreutils:
[1]   gnu
[2]   busybox *
$ readlink -f /bin/true
/usr/x86_64-pc-linux-musl/bin/busybox
$ syd -m'allow/stat,exec+/usr/**/bin/{busybox,g*}' -m 'allow/exec+/usr/**/lib*/*.so*' true
$ echo $?
0
$ doas eclectic coreutils set -1
$ readlink -f /bin/true
/usr/x86_64-pc-linux-musl/bin/gtrue
$ syd -m'allow/stat,exec+/usr/**/bin/{busybox,g*}' -m 'allow/exec+/usr/**/lib*/*.so*' true
$ echo $?
0
$

Hemos visto cómo los patrones de glob(3) nos facilitan la vida en la configuración de nuestro sandbox. Hemos visto que es posible usar "**" para coincidir recursivamente y que se admiten las alternativas de la forma "{foo,bar}". Syd también admite alternativas vacías de la forma "foo/{bar/,}baz" y la extensión de triple estrella, es decir, "foo/*** "es equivalente a la combinación de los dos patrones "foo" y "foo/**". Finalmente, podemos ver que logramos permitir mucho más usando la misma cantidad de reglas. Syd tiene muchas más características potentes que hacen que la edición de reglas sea simple y eficiente, como:

  • Puedes especificar rutas denegadas con "deny/" además de "allow/".
  • Puedes especificar rutas filtradas con "filter/", similar a "deny/" y "allow/" para silenciar las violaciones de acceso pero aún así denegar el acceso.
  • Si más de una regla coincide con la ruta de destino, la última regla coincidente gana.
  • Se pueden ensamblar muchas reglas en un archivo de configuración y pasarlas a Syd con -P<ruta>.
  • Los archivos que tienen conjuntos de reglas comunes se pueden incluir desde otros archivos de configuración utilizando la cláusula "include <ruta>".
  • Las rutas relativas en las cláusulas "include" se canonizan basándose en el directorio padre del archivo de configuración actual (no en el directorio de trabajo actual).
  • Las variables de entorno se expanden en los archivos de configuración. Las variables de entorno no establecidas causarán un error.
  • La configuración se puede bloquear en cualquier momento con la cláusula "lock:on", lo que impide ediciones posteriores del sandbox.

En este punto, se recomienda encarecidamente que experimentes con la configuración de Syd. No tengas miedo de agregar tantas reglas como quieras. Internamente, Syd mantiene los patrones de glob(3) como globsets y los compila en una única expresión regular para una coincidencia eficiente. Esto ofrece un rendimiento aceptable hasta aproximadamente 10.000 reglas en mi sistema; tu experiencia puede variar.

Hemos echado un vistazo a cómo configurar las listas de permitidos de rutas de Syd. Esto es similar para otros tipos de aislamiento. Dejaremos esos para más adelante y exploraremos otra forma de configurar Syd. Esta vez lo haremos en tiempo de ejecución, desde dentro del sandbox. Puede ser un shock desde una perspectiva de seguridad permitir el acceso a la política del sandbox desde dentro del sandbox, pero Syd tiene un buen conjunto de restricciones para proporcionar este caso de uso de forma segura y, como veremos más adelante, esto da la oportunidad de restringir aún más el proceso del sandbox. Otra alternativa es hacer que Syd cargue una biblioteca dinámica al inicio en lugar de ejecutar un comando, lo cual es otro tema avanzado para más adelante. La idea de la configuración en tiempo de ejecución depende del Bloqueo del Sandbox y el bloqueo puede tener tres estados: "on", "off" y "exec". Los dos primeros se explican por sí mismos, mientras que "exec" permite el acceso a la política del sandbox solo para el proceso inicial del sandbox. Una vez que el bloqueo del sandbox se establece en "on", no hay vuelta atrás, por lo que las ediciones posteriores del sandbox ya no serán posibles. Ahora ejecutemos un shell bajo Syd. Esta vez no enviaremos ninguna configuración al inicio y ejecutaremos Syd sin argumentos. Esto pondrá a Syd en modo de inicio de sesión, momento en el cual Syd utilizará el perfil "user" dinámico incorporado y generará un shell. No profundizaremos en los detalles del perfil de usuario por ahora, consulta "syd-cat -p user" si tienes curiosidad. Basta decir que proporciona un conjunto relativamente seguro de reglas de acceso a las rutas del sistema y acceso de lectura+escritura a tu directorio HOME y a las rutas de tiempo de ejecución de usuario "/run".
