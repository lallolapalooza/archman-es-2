NOMBRE

systemd.resource-control - Ajustes de control de recursos de unidad

SINOPSIS

slice.slice, scope.scope, service.service, socket.socket, mount.mount, swap.swap

DESCRIPCIÓN

Los archivos de configuración de unidad para servicios, slices, scopes, sockets, puntos de montaje y dispositivos de swap comparten un subconjunto de opciones de configuración para el control de recursos de los procesos generados. Internamente, esto se basa en el concepto del kernel de Grupos de Control (cgroups) para organizar procesos en una jerarquía de grupos nombrados con el propósito de gestión de recursos.

Esta página del manual enumera las opciones de configuración compartidas por estos seis tipos de unidades. Consulte systemd.unit(5) para las opciones comunes de todos los archivos de configuración de unidades, y systemd.slice(5), systemd.scope(5), systemd.service(5), systemd.socket(5), systemd.mount(5), y systemd.swap(5) para más información sobre los archivos de configuración de unidades específicos. Las opciones de configuración de control de recursos se configuran en las secciones [Slice], [Scope], [Service], [Socket], [Mount] o [Swap], dependiendo del tipo de unidad.

Además, las opciones que controlan los recursos disponibles para los programas *ejecutados* por systemd se enumeran en systemd.exec(5). Estas opciones complementan las opciones enumeradas aquí.

Habilitación y deshabilitación de controladores

Los controladores en la jerarquía de cgroup son jerárquicos, y el control de recursos se realiza distribuyendo asignaciones de recursos entre hermanos en ramas de la jerarquía de cgroup. No es necesario *habilitar* explícitamente un controlador de cgroup para una unidad. systemd instruirá al kernel para habilitar un controlador para una unidad dada cuando esta unidad tenga configuración para un controlador determinado. Por ejemplo, cuando se establece CPUWeight=, se habilitará el controlador de cpu, y cuando se establezca TasksMax=, se habilitará el controlador de pids. Además, varios controladores también pueden habilitarse explícitamente mediante la configuración MemoryAccounting=/TasksAccounting=/IOAccounting=. Debido a cómo funciona la jerarquía de cgroup, los controladores se habilitarán automáticamente para todas las unidades padre y para cualquier unidad hermana, comenzando por el nivel más bajo en el que se habilita un controlador. Las unidades para las que se habilita un controlador pueden estar sujetas a control de recursos, incluso si no tienen ninguna configuración explícita.

Establecer Delegate= habilita cualquier controlador delegado para esa unidad (ver más abajo). El delegado puede entonces habilitar controladores para sus hijos según corresponda. En particular, si el delegado es systemd (en la unidad user@.service), repetirá la misma lógica que la instancia del sistema y habilitará controladores para las unidades de usuario que tengan límites de recursos configurados, y sus hermanos, padres y hermanos de los padres.

Los controladores pueden ser *deshabilitados* para partes de la jerarquía de cgroup con DisableControllers= (ver más abajo).

Ejemplo 1. Habilitación y deshabilitación de controladores

                      -.slice
                     /       \
              /-----/         \--------------\
             /                                \
      system.slice                       user.slice
        /       \                          /      \
       /         \                        /        \
      /           \              user@42.service  user@1000.service
     /             \             Delegate=        Delegate=yes
a.service       b.slice                             /        \
CPUWeight=20   DisableControllers=cpu              /          \
                 /  \                      app.slice      session.slice
                /    \                     CPUWeight=100  CPUWeight=100
               /      \
       b1.service   b2.service
                    CPUWeight=1000

En esta jerarquía, el controlador cpu está habilitado para todas las unidades mostradas excepto b1.service y b2.service. Debido a que no hay configuración explícita para system.slice y user.slice, los recursos de CPU se dividirán equitativamente entre ellos. De manera similar, los recursos se asignan equitativamente entre los hijos de user.slice y entre los slices hijos debajo de user@1000.service. Suponiendo que no hay más configuración de recursos o delegación debajo de los slices app.slice o session.slice, el controlador cpu no se habilitaría para las unidades en esos slices y los recursos de CPU se asignarían adicionalmente utilizando otros mecanismos, por ejemplo, basados en los niveles de nice.

La configuración CPUWeight= en el servicio b2.service se neutraliza con DisableControllers= en el slice b.slice, por lo que el controlador cpu no se habilitaría para los servicios b1.service y b2.service, y los recursos de CPU se asignarían adicionalmente utilizando otros mecanismos, por ejemplo, basados en los niveles de nice.

Establecer controles de recursos para un grupo de unidades relacionadas

Como se describe en systemd.unit(5), los ajustes enumerados aquí pueden configurarse a través del archivo principal de una unidad y fragmentos de caída (drop-in) en directorios *.d/. La lista de directorios buscados para fragmentos de caída incluye nombres formados al truncar repetidamente el nombre de la unidad después de todos los guiones. Esto es particularmente conveniente para establecer límites de recursos para un grupo de unidades con nombres similares.

Por ejemplo, cada usuario obtiene su propio slice user-nnn.slice. Los fragmentos de caída con configuración local que afectan al usuario 1000 pueden colocarse en /etc/systemd/system/user-1000.slice, /etc/systemd/system/user-1000.slice.d/*.conf, pero también /etc/systemd/system/user-.slice.d/*.conf. Este último directorio se aplica a todos los slices de usuario.

Consulte las Nuevas Interfaces de Grupo de Control[1] para obtener una introducción sobre cómo utilizar las APIs de control de recursos desde programas.

OPCIONES

Las unidades de los tipos listados anteriormente pueden tener ajustes para la configuración del control de recursos:

Control de CPU

CPUWeight=peso, StartupCPUWeight=peso

Estos ajustes controlan el controlador cpu en la jerarquía unificada.

Estas opciones aceptan un valor entero o la cadena especial "idle":

•Si se establece en un valor entero, asigna el peso de tiempo de CPU especificado a los procesos ejecutados, si la jerarquía de grupo de control unificada está en uso en el sistema. Estas opciones controlan el atributo de grupo de control "cpu.weight". El rango permitido es de 1 a 10000. Por defecto, no está establecido, pero el valor predeterminado del kernel es 100. Para obtener detalles sobre este atributo de grupo de control, consulte Grupos de Control v2[2] y Scheduler CFS[3]. El tiempo de CPU disponible se divide entre todas las unidades dentro de un slice en relación con su peso de tiempo de CPU. Un peso mayor significa más tiempo de CPU, un peso menor significa menos.
•Si se establece en la cadena especial "idle", marca el cgroup para la "planificación ociosa", lo que significa que recibirá recursos de CPU solo cuando no haya procesos que no estén marcados de esta manera para ejecutarse en este cgroup o sus hermanos. Esta configuración corresponde al atributo de cgroup "cpu.idle".

Tenga en cuenta que este valor solo tiene efecto en cgroup-v2, para cgroup-v1 es equivalente al peso mínimo.

Mientras que StartupCPUWeight= se aplica a la s

startup y shutdown fases del sistema, CPUWeight= se aplica al tiempo de ejecución normal del sistema y, si el primero no está configurado, también a las fases de arranque y apagado. Usar StartupCPUWeight= permite priorizar servicios específicos al arrancar y apagar de manera diferente que durante el tiempo de ejecución normal.

Además de la asignación de recursos realizada por el controlador cpu, el kernel puede dividir automáticamente los recursos basándose en la agrupación por ID de sesión; véase la sección "La función autogroup" en sched(7). El efecto de esta función es similar al controlador cpu sin configuración explícita, por lo que los usuarios deben tener cuidado de no confundir una con la otra.

Añadido en la versión 232.

CPUQuota=

Esta configuración controla el controlador cpu en la jerarquía unificada.

Asigna la cuota de tiempo de CPU especificada a los procesos ejecutados. Toma un valor porcentual, con el sufijo "%". El porcentaje especifica cuánta cantidad de tiempo de CPU obtendrá la unidad como máximo, en relación con el tiempo total de CPU disponible en una CPU. Usa valores superiores a 100% para asignar tiempo de CPU en más de una CPU. Esto controla el atributo "cpu.max" en la jerarquía de cgroup unificada y "cpu.cfs_quota_us" en la antigua. Para más detalles sobre estos atributos de cgroup, véase Control Groups v2[2] y CFS Bandwidth Control[4]. Establecer CPUQuota= a un valor vacío desactiva la cuota.

Ejemplo: CPUQuota=20% asegura que los procesos ejecutados nunca obtendrán más del 20% del tiempo de CPU en una sola CPU.

Añadido en la versión 213.

CPUQuotaPeriodSec=

Esta configuración controla el controlador cpu en la jerarquía unificada.

Asigna la duración durante la cual se mide la cuota de tiempo de CPU especificada por CPUQuota=. Toma un valor de duración de tiempo en segundos, con un sufijo opcional como "ms" para milisegundos (o "s" para segundos). La configuración predeterminada es 100ms. El período se limita al rango soportado por el kernel, que es [1ms, 1000ms]. Adicionalmente, el período se ajusta hacia arriba para que el intervalo de cuota sea también de al menos 1 ms. Establecer CPUQuotaPeriodSec= a un valor vacío lo restaura a su valor predeterminado.

Esto controla el segundo campo del atributo "cpu.max" en la jerarquía de cgroup unificada y "cpu.cfs_period_us" en la antigua. Para más detalles sobre estos atributos de cgroup, véase Control Groups v2[2] y CFS Scheduler[3].

Ejemplo: CPUQuotaPeriodSec=10ms para solicitar que la cuota de CPU se mida en períodos de 10ms.

Añadido en la versión 242.

AllowedCPUs=, StartupAllowedCPUs=

Esta configuración controla el controlador cpuset en la jerarquía unificada.

Restringe los procesos para que se ejecuten en CPUs específicas. Toma una lista de índices de CPU o rangos separados por espacios en blanco o comas. Los rangos de CPU se especifican mediante los índices de CPU inferior y superior separados por un guion.

Establecer AllowedCPUs= o StartupAllowedCPUs= no garantiza que todas las CPUs serán utilizadas por los procesos, ya que pueden estar limitadas por las unidades padre. La configuración efectiva se informa como EffectiveCPUs=.

Mientras que StartupAllowedCPUs= se aplica a las fases de arranque y apagado del sistema, AllowedCPUs= se aplica al tiempo de ejecución normal del sistema y, si el primero no está configurado, también a las fases de arranque y apagado. Usar StartupAllowedCPUs= permite priorizar servicios específicos al arrancar y apagar de manera diferente que durante el tiempo de ejecución normal.

Esta configuración solo se soporta con la jerarquía de cgroup unificada.

Contabilidad y Control de Memoria

MemoryAccounting=

Esta configuración controla el controlador memory en la jerarquía unificada.

Activa la contabilidad de memoria del kernel y de los procesos para esta unidad. Toma un argumento booleano. Tenga en cuenta que activar la contabilidad de memoria para una unidad también la activará implícitamente para todas las unidades contenidas en el mismo slice y para todos sus slices padre y las unidades que contengan. El valor predeterminado del sistema para esta configuración puede controlarse con DefaultMemoryAccounting= en systemd-system.conf(5).

Añadido en la versión 208.

MemoryMin=bytes, MemoryLow=bytes, StartupMemoryLow=bytes, DefaultStartupMemoryLow=bytes

Estas configuraciones controlan el controlador memory en la jerarquía unificada.

Especifica la protección del uso de memoria de los procesos ejecutados en esta unidad. Al recuperar memoria, la unidad se trata como si estuviera usando menos memoria, lo que resulta en que la memoria se recupere preferentemente de las unidades no protegidas. Usar MemoryLow= resulta en una protección más débil donde la memoria aún puede ser recuperada para evitar invocar al OOM killer en caso de que no haya otra memoria recuperable.

Para que una protección sea efectiva, generalmente se requiere establecer una asignación correspondiente en todos los ancestros, que luego se distribuye entre los hijos (con la excepción del slice raíz). Cualquier asignación MemoryMin= o MemoryLow= que no se distribuya explícitamente a hijos específicos se utiliza para crear una protección compartida para todos los hijos. Dado que es una protección compartida, los hijos competirán libremente por la memoria.

Toma un tamaño de memoria en bytes. Si el valor tiene el sufijo K, M, G o T, el tamaño de memoria especificado se analiza como Kilobytes, Megabytes, Gigabytes o Terabytes (con base 1024), respectivamente. Alternativamente, se puede especificar un valor porcentual, que se toma en relación con la memoria física instalada en el sistema. Si se asigna el valor especial "infinity", se protege toda la memoria disponible, lo que puede ser útil para heredar siempre toda la protección ofrecida por los ancestros. Esto controla el atributo de cgroup "memory.min" o "memory.low". Para más detalles sobre este atributo de cgroup, véase Memory Interface Files[5].

Las unidades pueden hacer que sus hijos utilicen un valor predeterminado de "memory.min" o "memory.low" especificando DefaultMemoryMin= o DefaultMemoryLow=, que tiene la misma semántica que MemoryMin= y MemoryLow=, o DefaultStartupMemoryLow= que tiene la misma semántica que StartupMemoryLow=. Esta configuración no afecta a "memory.min" o "memory.low" en la unidad misma. Usarla para establecer una asignación hija predeterminada solo es útil en kernels anteriores a 5.7, que no soportan la opción de montaje "memory_recursiveprot" de cgroup2.

Mientras que StartupMemoryLow= se aplica a las fases de arranque y apagado del sistema, MemoryMin= se aplica al tiempo de ejecución normal del sistema y, si el primero no está configurado, también a las fases de arranque y apagado. Usar StartupMemoryLow= permite priorizar servicios específicos al arrancar y apagar de manera diferente que durante el tiempo de ejecución normal.

MemoryHigh=bytes, StartupMemoryHigh=bytes

Estas configuraciones controlan el controlador memory en la jerarquía unificada.

Especifica el límite de limitación en el uso de memoria de los procesos ejecutados en esta unidad. El uso de memoria puede superar el límite si es inevitable, pero los procesos se ralentizan considerablemente y la memoria se retira agresivamente en tales casos. Este es el mecanismo principal para controlar el uso de memoria de una unidad.

Toma un tamaño de memoria en bytes. Si el valor tiene el sufijo K, M, G o T, el tamaño de memoria especificado se analiza como Kilobytes, Megabytes, Gigabytes o Terabytes (con base 1024), respectivamente. Alternativamente, se puede especificar un valor porcentual, que se toma en relación con la memoria física instalada en el sistema. Si se asigna el valor especial "infinity", no se aplica ninguna limitación de memoria. Esto controla el atributo de cgroup "memory.high". Para más detalles sobre este atributo de cgroup, véase Memory Interface Files[5]. La configuración efectiva se informa como EffectiveMemoryHigh= (véase también EffectiveMemoryMax=).

Mientras que StartupMemoryHigh= se aplica a las fases de arranque y apagado del sistema, MemoryHigh= se aplica al tiempo de ejecución normal del sistema y, si el primero no está configurado, también a las fases de arranque y apagado. Usar StartupMemoryHigh= permite priorizar servicios específicos al arrancar y apagar de manera diferente que durante el tiempo de ejecución normal.

MemoryZSwapMax=bytes, StartupMemoryZSwapMax=bytes

Estos ajustes controlan el controlador memory en la jerarquía unificada.

Especifique el límite absoluto del uso de zswap de los procesos de esta unidad. Zswap es una caché comprimida ligera para páginas de swap. Si se alcanza el límite especificado, no se almacenarán entradas de esta unidad en el grupo hasta que las entradas existentes se vuelvan a cargar o se escriban en el disco. Consulte la documentación del kernel sobre Zswap[6] para obtener más detalles.

Acepta un tamaño en bytes. Si el valor va seguido de K, M, G o T, el tamaño especificado se analiza como Kilobytes, Megabytes, Gigabytes o Terabytes (con base 1024), respectivamente. Si se asigna el valor especial "infinity", no se aplica ningún límite. Estos ajustes controlan el atributo de grupo de control "memory.zswap.max". Para obtener detalles sobre este atributo de grupo de control, consulte Archivos de interfaz de memoria[5].

Mientras que StartupMemoryZSwapMax= se aplica a las fases de inicio y apagado del sistema, MemoryZSwapMax= se aplica al funcionamiento normal del sistema y, si el primero no está establecido, también a las fases de inicio y apagado. Contabilidad y Control de Procesos

TasksAccounting=

Este ajuste controla el controlador pids en la jerarquía unificada.

Activa la contabilidad de tareas para esta unidad. Acepta un argumento booleano. Si está habilitado, el kernel realizará un seguimiento del número total de tareas en la unidad y sus descendientes. Este número incluye tanto hilos del kernel como procesos de espacio de usuario, contando cada hilo individualmente. Tenga en cuenta que activar la contabilidad de tareas para una unidad también la activará implícitamente para todas las unidades contenidas en la misma slice y para todas sus slices padre y las unidades contenidas en ellas. El valor predeterminado del sistema para este ajuste se puede controlar con DefaultTasksAccounting= en systemd-system.conf(5).

Añadido en la versión 227.

TasksMax=N

Este ajuste controla el controlador pids en la jerarquía unificada.

Especifique el número máximo de tareas que se pueden crear en la unidad. Esto garantiza que el número de tareas contabilizadas para la unidad (ver arriba) se mantenga por debajo de un límite específico. Esto acepta un número absoluto de tareas o un valor porcentual que se toma en relación con el número máximo configurado de tareas en el sistema. Si se asigna el valor especial "infinity", no se aplica ningún límite de tareas. Esto controla el atributo de grupo de control "pids.max". Para obtener detalles sobre este atributo de grupo de control, consulte el controlador pids[7]. La configuración efectiva se informa como EffectiveTasksMax=.

El valor predeterminado del sistema para este ajuste se puede controlar con DefaultTasksMax= en systemd-system.conf(5).

IOWeight=weight, StartupIOWeight=weight

Estos ajustes controlan el controlador io en la jerarquía unificada.

Establece el peso predeterminado general de E/S de bloque para los procesos ejecutados, si la jerarquía de grupos de control unificada se utiliza en el sistema. Acepta un único valor de peso (entre 1 y 10000) para establecer el peso de E/S de bloque predeterminado. Esto controla el atributo de grupo de control "io.weight", que por defecto es 100. Para obtener detalles sobre este atributo de grupo de control, consulte Archivos de interfaz de E/S[8]. Contabilidad y Control de Red

IPAccounting=

Toma un argumento booleano. Si es verdadero, activa la contabilidad del tráfico de red IPv4 e IPv6 para los paquetes enviados o recibidos por la unidad. Cuando esta opción está activada, se contabilizan todos los sockets IPv4 e IPv6 creados por cualquier proceso de la unidad.

Cuando esta opción se utiliza en unidades de socket, se aplica a todos los sockets IPv4 e IPv6 asociados a ella (incluidos los sockets de escucha y los de conexión, cuando corresponda). Tenga en cuenta que para los servicios activados por socket, la configuración de esta opción y los datos de contabilidad de la unidad de servicio y la unidad de socket se mantienen separados y se muestran por separado. No se realiza ninguna propagación de la configuración y las estadísticas recopiladas, en ninguna dirección. Además, cualquier tráfico enviado o recibido en cualquiera de los sockets de la unidad de socket se contabiliza en la unidad de socket, y nunca en la unidad de servicio que pueda haber activado, incluso si el socket es utilizado por ella.

El valor predeterminado del sistema para esta configuración puede controlarse con DefaultIPAccounting= en systemd-system.conf(5).

Tenga en cuenta que esta funcionalidad solo está disponible para servicios del sistema, no para servicios por usuario.

IPAddressAllow=DIRECCIÓN[/LONGITUD_DE_PREFIJO]..., IPAddressDeny=DIRECCIÓN[/LONGITUD_DE_PREFIJO]...

Activa el filtrado de tráfico de red para paquetes IP enviados y recibidos a través de sockets AF_INET y AF_INET6. Ambas directivas toman una lista separada por espacios de direcciones IPv4 o IPv6, cada una opcionalmente seguida de una longitud de prefijo de dirección en bits después de un carácter "/". Si se omite el sufijo, la dirección se considera una dirección de host, es decir, el filtro cubre toda la dirección (32 bits para IPv4, 128 bits para IPv6).

Las listas de acceso configuradas con esta opción se aplican a todos los sockets creados por los procesos de esta unidad (o en el caso de unidades de socket, asociadas a ella). Las listas se combinan implícitamente con cualquier lista configurada para alguna de las unidades de slice padre de las que esta unidad pueda ser miembro. Por defecto, ambas listas de acceso están vacías. El tráfico de entrada y salida es filtrado por estas configuraciones. En caso de tráfico de entrada, se verifica la dirección IP de origen contra estas listas de acceso; en caso de tráfico de salida, se verifica la dirección IP de destino. Las siguientes reglas se aplican en orden:

•El acceso se concede cuando la dirección IP verificada coincide con una entrada en la lista IPAddressAllow=.
•De lo contrario, el acceso se deniega cuando la dirección IP verificada coincide con una entrada en la lista IPAddressDeny=.
•De lo contrario, el acceso se concede.

Para implementar un firewall IP de lista blanca, se recomienda usar una configuración IPAddressDeny=any en una unidad de slice de nivel superior (como la slice raíz -.slice o la slice que contiene todos los servicios del sistema system.slice – consulte systemd.special(7) para más detalles sobre estas unidades de slice), más líneas individuales IPAddressAllow= por servicio que permitan el acceso a la red a los servicios relevantes, y solo a ellos.

Tenga en cuenta que para los servicios activados por socket, la lista de acceso IP configurada en la unidad de socket se aplica a todos los sockets asociados directamente a ella, pero no a ningún socket creado por los servicios activados en última instancia para ella. Por el contrario, la lista de acceso IP configurada para el servicio no se aplica a ningún socket que se pase al servicio a través de la activación por socket. Por lo tanto, generalmente es una buena idea replicar las listas de acceso IP tanto en la unidad de socket como en la de servicio. Sin embargo, puede tener sentido mantener una lista más abierta y la otra más restringida, dependiendo del caso de uso.

Si estas configuraciones se utilizan varias veces en la misma unidad, las listas especificadas se combinan. Si se asigna una cadena vacía a estas configuraciones, la lista de acceso específica se reinicia y se anulan todas las configuraciones anteriores.

SocketBindAllow=regla-bind, SocketBindDeny=regla-bind

Configura restricciones sobre la capacidad de los procesos de la unidad para invocar bind(2) en un socket. Se pueden definir reglas de permiso y denegación que restringen a qué direcciones se puede enlazar un socket.

regla-bind describe propiedades del socket como familia-direccion, protocolo-transporte y puertos-ip.

regla-bind := { [familia-direccion:][protocolo-transporte:][puertos-ip] | any }

familia-direccion := { ipv4 | ipv6 }

protocolo-transporte := { tcp | udp }

puertos-ip := { puerto-ip | rango-puertos-ip }

Una familia-direccion opcional espera valores ipv4 o ipv6. Si no se especifica, una regla coincidirá para direcciones IPv4 e IPv6 y se aplicará según otros campos del socket, por ejemplo, protocolo-transporte, puerto-ip.

Un protocolo-transporte opcional espera nombres de protocolo de transporte tcp o udp. Si no se especifica, una regla coincidirá para cualquier protocolo de transporte.

Un valor puerto-ip opcional debe estar dentro del intervalo 1...65535 inclusive, es decir, el puerto dinámico 0 no está permitido. Un rango de puertos secuenciales se describe mediante rango-puertos-ip := puerto-ip-bajo-puerto-ip-alto, donde puerto-ip-bajo es menor o igual que puerto-ip-alto y ambos están dentro del intervalo 1...65535 inclusive.

Se puede utilizar el valor especial any para aplicar una regla a cualquier familia de direcciones, protocolo de transporte y cualquier puerto con un valor positivo.

Para permitir múltiples reglas, asigne SocketBindAllow= o SocketBindDeny= varias veces. Para borrar las asignaciones existentes, pase una asignación vacía de SocketBindAllow= o SocketBindDeny=.

Para cada uno de SocketBindAllow= y SocketBindDeny=, el número máximo de asignaciones permitidas es 128.

•El enlace a un socket se permite cuando una dirección de socket coincide con una entrada en la lista SocketBindAllow=.
•De lo contrario, el enlace se deniega cuando la dirección del socket coincide con una entrada en la lista SocketBindDeny=.
•De lo contrario, el enlace se permite.

El especificador de nodo de dispositivo es una ruta a un nodo de dispositivo en el sistema de archivos, comenzando con /dev/, o una cadena que comienza con "char-" o "block-" seguida de un nombre de grupo de dispositivos, como se enumera en /proc/devices. Gestión de Grupos de Control

Slice=

El nombre de la unidad slice en la que colocar la unidad. El valor predeterminado es system.slice para todas las unidades no instanciadas de todos los tipos de unidad (excepto para las unidades slice mismas, véase más abajo). Las unidades de instancia se colocan por defecto en un sub-slice de system.slice que se nombra según el nombre de la plantilla.

Esta opción puede usarse para organizar las unidades de systemd en una jerarquía de slices en las que cada uno podría tener configuraciones de recursos aplicadas.

Para unidades de tipo slice, el único valor aceptado para esta configuración es el slice padre. Dado que el nombre de una unidad slice implica el slice padre, es redundante establecer este parámetro directamente para las unidades slice.

Se debe tener especial cuidado al depender de la asignación de slice predeterminada en unidades de servicio de plantilla que tienen establecido DefaultDependencies=no, véase systemd.service(5), sección "Dependencias Predeterminadas" para más detalles.

Añadido en la versión 208.

Delegate=

Activa la delegación de una mayor partición de control de recursos a los procesos de la unidad. Las unidades donde esto está habilitado pueden crear y gestionar su propia subjerarquía privada de grupos de control por debajo del grupo de control de la unidad misma. Para servicios no privilegiados (es decir, aquellos que usan la configuración User=), el grupo de control de la unidad se hará accesible al usuario relevante.

Cuando está habilitado, el administrador de sistemas se abstendrá de manipular grupos de control o mover procesos por debajo del grupo de control de la unidad, de modo que se establezca un claro concepto de propiedad: el árbol de grupos de control a nivel del grupo de control de la unidad y superiores (es decir, hacia el grupo de control raíz) es propiedad y está gestionado por el administrador de sistemas del host, mientras que el árbol de grupos de control por debajo del grupo de control de la unidad es propiedad y está gestionado por la propia unidad.

Toma un argumento booleano o una lista (posiblemente vacía) de nombres de controladores de grupos de control. Si es verdadero, la delegación se activa y todos los controladores compatibles se habilitan para la unidad, poniéndolos a disposición de los procesos de la unidad para su gestión. Si es falso, la delegación se desactiva completamente (y ningún controlador adicional se habilita). Si se establece en una lista de controladores, la delegación se activa y se habilitan los controladores especificados para la unidad. Asignar la cadena vacía habilitará la delegación, pero restablecerá la lista de controladores, y todas las asignaciones anteriores a esta no tendrán efecto. Tenga en cuenta que es posible que se pongan a disposición controladores adicionales además de los especificados, dependiendo de la configuración de la unidad slice contenedora u otras unidades contenidas en ella. El valor predeterminado es falso.

Tenga en cuenta que la delegación de controladores a código menos privilegiado solo es segura en la jerarquía unificada de grupos de control. En consecuencia, el acceso a los controladores especificados no se concederá a servicios no privilegiados en la jerarquía heredada, incluso cuando se solicite.

Los siguientes nombres de controladores pueden especificarse: cpu, cpuset, io, memory, pids, bpf-firewall, bpf-devices, bpf-foreign, bpf-socket-bind y bpf-restrict-network-interfaces.

Sin embargo, no todos estos controladores están disponibles en todos los kernels, y algunos son específicos de la jerarquía unificada, mientras que otros son específicos de la jerarquía heredada. Tenga en cuenta también que el kernel puede admitir controladores adicionales que aún no se cubren aquí, ya que la delegación no es compatible en absoluto para ellos o no está definida claramente.

Tenga en cuenta que, debido a la naturaleza jerárquica de la jerarquía de cgroup, todos los controladores que se deleguen estarán habilitados para las unidades padre y hermanas de la unidad con delegación.

Para más detalles sobre el modelo de delegación, consulte APIs de Control de Grupos y Delegación[12].

Añadido en la versión 218.

DelegateSubgroup=

Coloca los procesos de la unidad en el subgrupo especificado del grupo de control de la unidad. Toma un nombre de grupo de control válido (¡no una ruta!) como parámetro, o una cadena vacía para desactivar esta función. El valor predeterminado es desactivado. El nombre del grupo de control debe ser utilizable como nombre de archivo y evitar conflictos con los archivos de atributos de grupo de control del kernel (es decir, cgroup.procs no es un nombre aceptable, ya que el kernel expone un archivo de atributo de grupo de control nativo con ese nombre). Esta opción no tiene ningún efecto a menos que la delegación de grupos de control esté activada a través de Delegate=, véase más arriba. Tenga en cuenta que esta configuración solo se aplica a los procesos "principales" de una unidad, es decir, para los servicios a ExecStart=, pero no para ExecReload= y similares. Si la delegación está activada, los últimos se colocan siempre dentro de un subgrupo llamado .control. El subgrupo especificado se crea automáticamente (y potencialmente la propiedad se transfiere al usuario/grupo configurado de la unidad) cuando se inicia un proceso en él.

Esta opción es útil para evitar mover manualmente el proceso invocado a un subgrupo después de que se haya iniciado. Dado que ningún proceso debería residir en nodos internos del árbol de grupos de control, casi siempre es necesario ejecutar el proceso principal (de "supervisión") de una unidad que tiene delegación activada en un subgrupo.

Añadido en la versión 254.

DisableControllers=

Desactiva los controladores para que no se habiliten para los hijos de una unidad. Si un controlador listado ya está en uso en su subárbol, el controlador se eliminará del subárbol. Esto se puede usar para evitar que la configuración en unidades secundarias pueda habilitar implícita o explícitamente un controlador. El valor predeterminado es vacío.

Se pueden especificar varios controladores, separados por espacios. También puede pasar DisableControllers= varias veces, en cuyo caso cada nueva instancia agrega otro controlador para deshabilitar. Pasar DisableControllers= por sí solo sin ningún nombre de controlador presente restablece la lista de controladores deshabilitados.

Puede que no sea posible deshabilitar un controlador después de que se hayan iniciado las unidades, si la unidad o cualquier hijo de la unidad en cuestión delega controladores a sus hijos, ya que cualquier subárbol delegado de la jerarquía de cgroup no es gestionado por systemd.

Los siguientes nombres de controladores pueden especificarse: cpu, cpuset, io, memory, pids, bpf-firewall, bpf-devices, bpf-foreign, bpf-socket-bind y bpf-restrict-network-interfaces.

NAME

systemd.resource-control - Control group (cgroup) directives for service units

SYNOPSIS

*.service

Delegate=

AllowedCPUs=, AllowedMemoryNodes=

CPUShares=, CPUQuota=, CPUWeight=, CPUQuotaPeriodSec=

IOWeight=, PIOBudget=, DevicePolicy=, DeviceAllow=

MemoryLimit=, MemoryLimitRecursionDepth=, MemorySwapMax=

DeviceReadIOPS=, DeviceWriteIOPS=, DeviceReadBPS=, DeviceWriteBPS=

TaskStartToMemoryMax=

AllowedCPUAllocations=

TimerSlackNSec=

DESCRIPTION

This man page describes the directives used to control the resource usage of service units. These directives are typically used in .service unit files, but some may also appear in other unit types such as .scope units.

These directives primarily configure parameters for Linux Control Groups (cgroups), which are a mechanism for limiting, accounting for, and isolating resource usage (CPU, memory, disk I/O, network, etc.) of process groups.

The directives described here are a subset of the available cgroup configuration options. For a comprehensive list and detailed explanations, refer to the cgroups documentation for your specific kernel version.

IMPLICIT DEPENDENCIES

Setting resource control directives may implicitly pull in other units or dependencies. For example, using cgroup v2 features might require certain kernel configurations or systemd versions.

OPTIONS

The following directives can be used to control resource usage:

Delegate= (boolean)
Controls whether the unit is allowed to delegate its control group subtree to child processes. If true, child processes can create their own cgroups. Defaults to false.
AllowedCPUs= (string)
Specifies a list of CPUs or CPU sets that the unit's processes are allowed to run on. Example: "0,2-4,8".
AllowedMemoryNodes= (string)
Specifies a list of NUMA memory nodes that the unit's processes are allowed to allocate memory from. Example: "0,2,4-8".
CPUShares= (integer)
Sets the relative CPU time weight for the unit. Higher values mean more CPU time. Defaults to 1024.
CPUQuota= (string)
Sets a hard limit on the amount of CPU time the unit's processes can use. Can be specified as a percentage (e.g., "50%") or a quota per period (e.g., "20000" for 20ms per 100ms period).
CPUWeight= (integer)
Similar to CPUShares=, but uses a different scale (1-1000). Defaults to 100.
CPUQuotaPeriodSec= (time)
Specifies the period duration for CPUQuota=. Defaults to 100ms.
IOWeight= (integer)
Sets the relative I/O bandwidth weight for the unit. Higher values mean more I/O bandwidth. Scales from 1 to 1000. Defaults to 100.
PIOBudget= (string)
Sets a hard limit on the amount of I/O the unit's processes can perform within a given period. Specified in bytes per second. Example: "100M".
DevicePolicy= (string)
Controls access to devices. Possible values: "strict", "closed", "mixed", "auto". Defaults to "auto".
DeviceAllow= (string)
Allows access to a specific device. Format: "type major:minor rwm". Example: "char-device 1:3 rwm" for /dev/null.
MemoryLimit= (memory size)
Sets a hard limit on the amount of memory the unit's processes can use. Example: "512M".
MemoryLimitRecursionDepth= (integer)
Sets the memory limit recursion depth. Defaults to 0 (no limit).
MemorySwapMax= (memory size)
Sets a hard limit on the amount of swap the unit's processes can use. Example: "1G".
DeviceReadIOPS= (iops)
Sets a limit on the number of IO operations per second for reading from a specific device.
DeviceWriteIOPS= (iops)
Sets a limit on the number of IO operations per second for writing to a specific device.
DeviceReadBPS= (bytes)
Sets a limit on the number of bytes per second for reading from a specific device.
DeviceWriteBPS= (bytes)
Sets a limit on the number of bytes per second for writing to a specific device.
TaskStartToMemoryMax= (memory size)
Sets the maximum memory a task is allowed to consume when it starts. Example: "100M".
AllowedCPUFeatures= (string)
Specifies a list of CPU features that the unit's processes are allowed to use. Example: "sse4.2".
AllowedCPUAllocations= (string)
Allows specifying cpu.shares, cpu.cfs_period_us, and cpu.cfs_quota_us in a single directive.
TimerSlackNSec= (time)
Sets the timer slack for the unit. Controls the maximum latency allowed for timers.
