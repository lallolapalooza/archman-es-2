NOMBRE

systemd-resolved.service, systemd-resolved - Gestor de resolución de nombres de red

SINOPSIS

systemd-resolved.service

/usr/lib/systemd/systemd-resolved

DESCRIPCIÓN

systemd-resolved es un servicio del sistema que proporciona resolución de nombres de red a las aplicaciones locales. Implementa un gestor de caché y validación de DNS/DNSSEC, así como un gestor y respondedor de LLMNR y MulticastDNS. Las aplicaciones locales pueden enviar solicitudes de resolución de nombres de red a través de tres interfaces:

•La API nativa y con todas las funciones que systemd-resolved expone a través de D-Bus, consulte org.freedesktop.resolve1(5) y org.freedesktop.LogControl1(5) para más detalles. En general, se recomienda a los clientes utilizar esta API, ya que es asíncrona y con todas las funciones (por ejemplo, devuelve correctamente el estado de validación de DNSSEC y el ámbito de la interfaz para las direcciones, según sea necesario para admitir redes de enlace local).

•La API nativa que systemd-resolved expone a través de Varlink en el socket AF_UNIX /run/systemd/resolve/io.systemd.Resolve. Esto proporciona una funcionalidad similar a la interfaz D-Bus, pero está disponible durante todo el tiempo de ejecución, sin necesidad de un servicio de bus de sistema D-Bus en ejecución.
•La API glibc getaddrinfo(3), tal como se define en **RFC3493**[1] y sus funciones de resolución relacionadas, incluyendo gethostbyname(3). Esta API es ampliamente compatible, incluso en plataformas distintas de Linux. En su forma actual, no expone información sobre el estado de validación de DNSSEC y solo es síncrona. Esta API está respaldada por el módulo Name Service Switch (NSS) de glibc (nss(5)). Se requiere el uso del módulo NSS de glibc nss-resolve(8) para permitir que las funciones del resolvedor NSS de glibc resuelvan nombres de host a través de systemd-resolved.
•Además, systemd-resolved proporciona un escucha DNS local en las direcciones IP 127.0.0.53 y 127.0.0.54 en la interfaz de bucle local. Los programas que emiten solicitudes DNS directamente, eludiendo cualquier API local, pueden ser dirigidos a este stub, para conectarlos a systemd-resolved. Tenga en cuenta, sin embargo, que se recomienda encarecidamente que los programas locales utilicen las APIs de bus o NSS de glibc en su lugar (como se describe anteriormente), ya que varios conceptos de resolución de red (como el direccionamiento de enlace local o los dominios Unicode LLMNR) no se pueden mapear al protocolo DNS unicast.

El resolvedor stub DNS en 127.0.0.53 proporciona el conjunto completo de funciones del resolvedor local, que incluye la oferta de resolución LLMNR/MulticastDNS. El resolvedor stub DNS en 127.0.0.54 proporciona un resolvedor más limitado, que opera solo en modo "proxy", es decir, pasará la mayoría de los mensajes DNS relativamente sin modificar a los servidores DNS ascendentes actuales y de vuelta, pero no intentará procesar los mensajes localmente, y por lo tanto no valida DNSSEC, ni ofrece LLMNR/MulticastDNS. (Sin embargo, se traducirá a comunicación DNS-over-TLS si es necesario).

Los servidores DNS contactados se determinan a partir de la configuración global en /etc/systemd/resolved.conf, la configuración estática por enlace en los archivos /etc/systemd/network/*.network (en caso de que se utilice systemd-networkd.service(8)), la configuración dinámica por enlace recibida a través de DHCP, la información proporcionada a través de resolvectl(1) y cualquier información de servidor DNS disponible a través de otros servicios del sistema. Consulte resolved.conf(5) y systemd.network(5) para obtener detalles sobre los propios archivos de configuración de systemd para servidores DNS. Para mejorar la compatibilidad, se lee /etc/resolv.conf para descubrir los servidores DNS del sistema configurados, pero solo si no es un enlace simbólico a /run/systemd/resolve/stub-resolv.conf, /usr/lib/systemd/resolv.conf o /run/systemd/resolve/resolv.conf (consulte más abajo).

REGISTROS SINTÉTICOS

systemd-resolved sintetiza registros de recursos (RR) DNS para los siguientes casos:

•El nombre de host local configurado se resuelve a todas las direcciones IP configuradas localmente, ordenadas por su ámbito, o — si no se ha configurado ninguna — la dirección IPv4 127.0.0.2 (que está en la interfaz de bucle local) y la dirección IPv6 ::1 (que es el host local).
•Los nombres de host "localhost" y "localhost.localdomain", así como cualquier nombre de host que termine en ".localhost" o ".localhost.localdomain" se resuelven a las direcciones IP 127.0.0.1 y ::1.
•El nombre de host "_gateway" se resuelve a todas las direcciones de puerta de enlace de enrutamiento predeterminado actuales, ordenadas por su métrica. Esto asigna un nombre de host estable a la puerta de enlace actual, útil para referenciarla independientemente del estado de configuración de red actual.
•El nombre de host "_outbound" se resuelve a las direcciones IPv4 e IPv6 locales que son más probables que se utilicen para la comunicación con otros hosts. Estas son las direcciones de origen preferidas de las puertas de enlace predeterminadas si se especifican, o determinadas solicitando una decisión de enrutamiento a las puertas de enlace predeterminadas configuradas del kernel y luego utilizando las direcciones IP locales seleccionadas por esta decisión. Este nombre de host solo está disponible si hay al menos una puerta de enlace predeterminada local configurada. Esto asigna un nombre de host estable a las direcciones IP de salida locales, útil para referenciarlas independientemente del estado de configuración de red actual.
•El nombre de host "_localdnsstub" se resuelve a la dirección IP 127.0.0.53, es decir, la dirección en la que escucha el stub DNS local (véase más arriba).
•El nombre de host "_localdnsproxy" se resuelve a la dirección IP 127.0.0.54, es decir, la dirección en la que escucha el proxy DNS local (véase más arriba).
•Los mapeos definidos en /etc/hosts se resuelven a sus direcciones configuradas y viceversa, pero no afectarán a las búsquedas de tipos no direccionales (como MX). El soporte para /etc/hosts puede ser deshabilitado con ReadEtcHosts=no, consulte resolved.conf(5).

PROTOCOLOS Y ENRUTAMIENTO

Las solicitudes de búsqueda que recibe systemd-resolved.service se enrutan a los servidores DNS, LLMNR y MulticastDNS disponibles según las siguientes reglas:

•Los nombres para los que se generan registros sintéticos (el nombre de host local, "localhost" y "localdomain", puerta de enlace local, como se indica en la sección anterior) y las direcciones configuradas en /etc/hosts nunca se enrutan a la red y se envía una respuesta inmediatamente.
•Los nombres de una sola etiqueta se resuelven utilizando LLMNR en todas las interfaces locales donde LLMNR esté habilitado. Las búsquedas de direcciones IPv4 solo se envían a través de LLMNR en IPv4, y las búsquedas de direcciones IPv6 solo se envían a través de LLMNR en IPv6. Tenga en cuenta que las búsquedas de nombres sintéticos de una sola etiqueta no se enrutan a LLMNR, MulticastDNS o unicast DNS.
•Las consultas para los registros de direcciones (A y AAAA) de nombres no sintéticos de una sola etiqueta se resuelven a través de DNS unicast utilizando dominios de búsqueda. Para cualquier interfaz que defina dominios de búsqueda, dichas búsquedas se enrutan a los servidores definidos para esa interfaz, se les añade cada uno de esos dominios de búsqueda. Cuando se definen dominios de búsqueda globales, dichas búsquedas se enrutan a los servidores globales. Para cada dominio de búsqueda, las consultas se realizan añadiendo el nombre con cada uno de los dominios de búsqueda en secuencia. Además, la búsqueda de nombres de una sola etiqueta a través de DNS unicast puede habilitarse con la configuración ResolveUnicastSingleLabel=yes. Los detalles de qué servidores se consultan y cómo se elige la respuesta final se describen a continuación. Tenga en cuenta que, por defecto, las búsquedas de nombres de una sola etiqueta no se envían a servidores DNS remotos, y la resolución solo es posible si se definen dominios de búsqueda.
•Los nombres de varias etiquetas con el sufijo de dominio ".local" se resuelven utilizando MulticastDNS en todas las interfaces locales donde MulticastDNS esté habilitado. Al igual que con LLMNR, las búsquedas de direcciones IPv4 se envían a través de IPv4 y las búsquedas de direcciones IPv6 se envían a través de IPv6.
•Las consultas para nombres de varias etiquetas se enrutan a través de DNS unicast en interfaces locales que tienen un servidor DNS configurado, más los servidores DNS configurados globalmente si los hay. Qué interfaces se utilizan se determina mediante la lógica de enrutamiento basada en dominios de búsqueda y solo de ruta, descrita a continuación. Tenga en cuenta que, por defecto, las búsquedas de dominios con el sufijo ".local" no se enrutan a servidores DNS, un

Esto significa que en redes donde el dominio ".local" esté definido en un servidor DNS específico del sitio, se necesitarán dominios de búsqueda o enrutamiento explícitos para que las búsquedas funcionen dentro de este dominio DNS. Tenga en cuenta que en la actualidad, generalmente se recomienda evitar definir ".local" en un servidor DNS, ya que RFC6762[2] reserva este dominio para uso exclusivo de MulticastDNS.
•Las búsquedas de direcciones (búsquedas inversas) se enrutan de manera similar a los nombres de múltiples etiquetas, con la excepción de que las direcciones del rango de direcciones de enlace local nunca se enrutan a DNS unicast y solo se resuelven utilizando LLMNR y MulticastDNS (cuando están habilitados).

Si las búsquedas se enrutan a múltiples interfaces, se devuelve la primera respuesta exitosa (fusionando efectivamente las zonas de búsqueda en todas las interfaces coincidentes). Si la búsqueda falló en todas las interfaces, se devuelve la última respuesta fallida.

El enrutamiento de las búsquedas se determina por los dominios de enrutamiento por interfaz (búsqueda y solo enrutamiento) y los dominios de búsqueda globales. Consulte systemd.network(5) y resolvectl(1) para obtener una descripción de cómo se configuran dinámicamente estas configuraciones y la discusión sobre Domains= en resolved.conf(5) para obtener una descripción de la configuración global de DNS.

La siguiente lógica de enrutamiento de consultas se aplica a las búsquedas de DNS unicast iniciadas por systemd-resolved.service:

•Si un nombre a buscar coincide (es decir, es igual o tiene como sufijo) con alguno de los dominios de enrutamiento configurados (búsqueda o solo enrutamiento) de cualquier enlace, o con la configuración global de DNS, se determina el dominio de enrutamiento "que mejor coincide": el que coincide con la mayor cantidad de etiquetas. Luego, la consulta se envía a todos los servidores DNS de cualquier enlace o a los servidores DNS configurados globalmente asociados con este dominio de enrutamiento "que mejor coincide". (Tenga en cuenta que más de un enlace puede tener este mismo dominio de enrutamiento "que mejor coincide" configurado, en cuyo caso la consulta se envía a todos ellos en paralelo).

En el caso de nombres de etiqueta única, cuando se definen dominios de búsqueda, se aplica la misma lógica, excepto que el nombre se antepone primero con cada uno de los dominios de búsqueda por turno. Tenga en cuenta que esta lógica de búsqueda no se aplica a ningún nombre con al menos un punto. Consulte también la discusión sobre la compatibilidad con el solucionador glibc tradicional a continuación.

•Si una consulta no coincide con ningún dominio de enrutamiento configurado (ya sea por enlace o global), se envía a todos los servidores DNS que están configurados en enlaces configurados como ruta predeterminada, así como al servidor DNS configurado globalmente.
•Si no hay servidores DNS configurados en ningún enlace configurado también como ruta predeterminada y no hay un servidor DNS global configurado, se utiliza uno de los servidores DNS de reserva compilados.
•De lo contrario, la consulta DNS unicast falla, ya que no se pueden determinar servidores DNS adecuados.

Si un enlace es la ruta predeterminada o no, se puede configurar con el comando resolvectl default-route o el ajuste DNSDefaultRoute= en los archivos .network. Si no se configura explícitamente, se determina implícitamente basándose en los dominios DNS configurados para un enlace: si existe un dominio de solo enrutamiento distinto de "~.", el valor predeterminado es falso, de lo contrario es verdadero.

Efectivamente, esto significa: para admitir nombres de etiqueta única no sintetizados, defina dominios de búsqueda apropiados. Para enrutar preferentemente todas las consultas DNS no coincidentes explícitamente por la configuración del dominio de enrutamiento a un enlace específico, configure un dominio de solo enrutamiento "~." en él. Esto garantizará que otros enlaces no se consideren para estas consultas (a menos que también tengan dicho dominio de enrutamiento). Para enrutar todas estas consultas DNS a un enlace específico solo si ningún otro enlace es preferido, configure el enlace como ruta predeterminada y no configure un dominio de solo enrutamiento "~." en él. Finalmente, para evitar que un enlace específico reciba tráfico DNS que no coincida con ninguno de sus dominios de enrutamiento configurados, no lo convierta en una ruta predeterminada.

Consulte org.freedesktop.resolve1(5) para obtener información sobre las API de D-Bus que proporciona systemd-resolved.

COMPATIBILIDAD CON EL SOLUCIONADOR DE RESPALDO TRADICIONAL DE GLIBC

Esta sección proporciona un breve resumen de las diferencias en el solucionador implementado por nss-resolve(8) junto con systemd-resolved y el solucionador de respaldo tradicional implementado en nss-dns.

•Algunos nombres se resuelven siempre internamente (ver Registros Sintéticos arriba). Tradicionalmente se resolverían por nss-files si se proporcionaran en /etc/hosts. Pero tenga en cuenta que los detalles de cómo se construye una consulta están bajo el control de la biblioteca cliente. nss-dns intentará primero resolver nombres utilizando dominios de búsqueda e incluso si esas consultas se enrutan a systemd-resolved, las enviará a través de la red utilizando las reglas habituales para el enrutamiento de nombres de múltiples etiquetas [3].
•Los nombres de etiqueta única no se resuelven para registros A y AAAA utilizando DNS unicast (a menos que se anule con ResolveUnicastSingleLabel=, ver resolved.conf(5)). Esto es similar a la opción no-tld-query establecida en resolv.conf(5).
•Los dominios de búsqueda no se utilizan para la "sufijación" de nombres de múltiples etiquetas. (Sin embargo, los dominios de búsqueda se utilizan para el "enrutamiento" de búsquedas, para nombres que originalmente se especificaron como de etiqueta única o de múltiples etiquetas). Cualquier nombre con al menos un punto se interpreta siempre como un FQDN. nss-dns resolvería nombres tanto como relativos (usando dominios de búsqueda) como FQDN absolutos. Algunos nombres se resolverían como relativos primero, y después de que esa consulta fallara, como absolutos, mientras que otros nombres se resolverían en orden inverso. La opción ndots en /etc/resolv.conf se utilizaba para controlar cuántos puntos necesitaba tener el nombre para resolverse como relativo primero. Este solucionador de respaldo no implementa esto en absoluto: los nombres de múltiples etiquetas solo se resuelven como FQDN.[4]
•Este solucionador tiene una noción del dominio especial ".local" utilizado para MulticastDNS, y no enrutará consultas con ese sufijo a servidores DNS unicast a menos que se configuren explícitamente, ver arriba. Además, las búsquedas inversas para direcciones de enlace local no se envían a servidores DNS unicast.
•Este solucionador lee y almacena en caché /etc/hosts internamente. (En otras palabras, nss-resolve reemplaza nss-files además de nss-dns). Las entradas en /etc/hosts tienen la máxima prioridad.
•Este solucionador también implementa LLMNR y MulticastDNS además del protocolo clásico de DNS unicast, y resolverá nombres de etiqueta única utilizando LLMNR (cuando esté habilitado) y nombres que terminan en ".local" utilizando MulticastDNS (cuando esté habilitado).
•Las variables de entorno $LOCALDOMAIN y $RES_OPTIONS descritas en resolv.conf(5) no son compatibles actualmente.
•El solucionador nss-dns mantiene poco estado entre consultas DNS posteriores, y para cada consulta siempre habla primero con el primer servidor DNS listado de /etc/resolv.conf, y en caso de fallo continúa con el siguiente hasta llegar al final de la lista, momento en el cual la consulta falla. Sin embargo, el solucionador en systemd-resolved mantiene el estado y hablará continuamente con el mismo servidor para todas las consultas en un ámbito de búsqueda particular hasta que se vea alguna forma de error, momento en el cual cambiará al siguiente servidor y permanecerá con él para todas las consultas en el ámbito hasta el próximo fallo, y así sucesivamente, regresando eventualmente al primer servidor configurado. Esto se hace para optimizar los tiempos de búsqueda, especialmente dado que el solucionador típicamente debe primero sondear los conjuntos de características del servidor al hablar con él, lo que lleva tiempo. Este comportamiento diferente implica que los servidores DNS listados por ámbito de búsqueda deben ser equivalentes en las zonas que sirven, para que enviar una consulta a uno de ellos arroje los mismos resultados que enviarla a otro servidor DNS configurado.

/ETC/RESOLV.CONF

Se admiten cuatro modos de manejo de /etc/resolv.conf (ver resolv.conf(5)):

•systemd-resolved mantiene el archivo /run/systemd/resolve/stub-resolv.conf para compatibilidad con programas tradicionales de Linux. Este archivo lista el stub DNS 127.0.0.53 (ver arriba) como el único servidor DNS. También contiene una lista de dominios de búsqueda que están en uso por systemd-resolved. La lista de dominios de búsqueda siempre se mantiene actualizada. Tenga en cuenta que las aplicaciones no deben usar directamente /run/systemd/resolve/stub-resolv.conf, sino solo a través de un enlace simbólico desde /etc/resolv.conf. Este archivo puede ser enlazado simbólicamente desde /etc/resolv.conf para conectar todos los clientes locales que omiten las API DNS locales a systemd-resolved con la configuración correcta de dominios de búsqueda. Se recomienda este modo de operación.
•Se proporciona un archivo estático /usr/lib/systemd/resolv.conf que lista el stub DNS 127.0.0.53 (ver arriba) como único servidor DNS. Este archivo puede ser enlazado simbólicamente desde /etc/resolv.conf para conectar todos los clientes locales que omiten las API DNS locales a systemd-resolved. Este archivo no contiene dominios de búsqueda.
•systemd-resolved mantiene el archivo /run/systemd/resolve/resolv.conf para compatibilidad con programas tradicionales de Linux. Este archivo puede ser enlazado simbólicamente desde /etc/resolv.conf y siempre se mantiene actualizado, conteniendo información sobre todos los servidores DNS conocidos. Tenga en cuenta las limitaciones del formato del archivo: no conoce el concepto de servidores DNS por interfaz y, por lo tanto, solo contiene definiciones de servidores DNS a nivel de sistema. Tenga en cuenta que las aplicaciones no deben usar directamente /run/systemd/resolve/resolv.conf, sino solo a través de un enlace simbólico desde /etc/resolv.conf. Si se utiliza este modo de operación, los clientes locales que omiten cualquier API DNS local también omitirán systemd-resolved y hablarán directamente con los servidores DNS conocidos.
•Alternativamente, /etc/resolv.conf puede ser gestionado por otros paquetes, en cuyo caso systemd-resolved lo leerá para obtener datos de configuración DNS. En este modo de operación, systemd-resolved es un consumidor en lugar de un proveedor de este archivo de configuración.

Tenga en cuenta que el modo de operación seleccionado para este archivo se detecta de forma totalmente automática, dependiendo de si /etc/resolv.conf es un enlace simbólico a /run/systemd/resolve/resolv.conf o si enumera 127.0.0.53 como servidor DNS.

SEÑALES

SIGUSR1

Al recibir la señal de proceso SIGUSR1, systemd-resolved volcará el contenido de todas las cachés de registros de recursos DNS que mantiene, así como toda la información de nivel de características que haya aprendido sobre
systemd-resolved(8) — systemd manual pages

SIGNALS

The following signals are understood by the systemd-resolved process:

SIGUSR1

Upon reception of the SIGUSR1 process signal systemd-resolved will reload the system DNS configuration from /etc/resolv.conf. Note that it should normally not be necessary to request this explicitly – except for debugging purposes – as systemd-resolved automatically reloads the configuration any time the host's network configuration changes. Sending this signal to systemd-resolved is equivalent to the resolvectl reload-configuration command, however the latter is recommended since it operates in a synchronous way and logs the configured DNS servers into the system logs.

Added in version 231.

SIGUSR2

Upon reception of the SIGUSR2 process signal systemd-resolved will flush all caches it maintains. Note that it should normally not be necessary to request this explicitly – except for debugging purposes – as systemd-resolved flushes the caches automatically anyway any time the host's network configuration changes. Sending this signal to systemd-resolved is equivalent to the resolvectl flush-caches command, however the latter is recommended since it operates in a synchronous way.

Added in version 231.

SIGRTMIN+1

Upon reception of the SIGRTMIN+1 process signal systemd-resolved will forget everything it learnt about the configured DNS servers. Specifically any information about server feature support is flushed out, and the server feature probing logic is restarted on the next request, starting with the most fully featured level. Note that it should normally not be necessary to request this explicitly – except for debugging purposes – as systemd-resolved automatically forgets learnt information any time the DNS server configuration changes. Sending this signal to systemd-resolved is equivalent to the resolvectl reset-server-features command, however the latter is recommended since it operates in a synchronous way.

Added in version 235.

SIGHUP

Upon reception of the SIGHUP process signal systemd-resolved will flush all caches it maintains, drop all open TCP connections (if any), and reload its configuration files.

Added in version 256.

CREDENTIALS

systemd-resolved supports the service credentials logic as implemented by ImportCredential=/LoadCredential=/SetCredential= (see systemd.exec(5) for details). The following credentials are used when passed in:

network.dns, network.search_domains

May contain a space separated list of DNS server IP addresses and DNS search domains. This information is only used when no explicit configuration via /etc/systemd/resolved.conf, /etc/resolv.conf or the kernel command line has been provided.

Added in version 253.

KERNEL COMMAND LINE

systemd-resolved also honours two kernel command line options:

nameserver=, domain=

Takes the IP address of a DNS server (in case of nameserver=), and a DNS search domain (in case of domain=). May be used multiple times, to define multiple DNS servers/search domains. If either of these options are specified /etc/resolv.conf will not be read and the DNS= and Domains= settings of resolved.conf(5) will be ignored. These two kernel command line options hence override system configuration.

Added in version 253.

IP PORTS

The systemd-resolved service listens on the following IP ports:

•Port 53 on IPv4 addresses 127.0.0.53 and 127.0.0.54 (both are on the local loopback interface "lo"). This is the local DNS stub, as discussed above. Both UDP and TCP are covered.
•Port 5353 on all local addresses, both IPv4 and IPv6 (0.0.0.0 and ::0), for MulticastDNS on UDP. Note that even though the socket is bound to all local interfaces via the selected "wildcard" IP addresses, the incoming datagrams are filtered by the network interface they are coming in on, and separate MulticastDNS link-local scopes are maintained for each, taking into consideration whether MulticastDNS is enabled for the interface or not.
•Port 5355 on all local addresses, both IPv4 and IP6 (0.0.0.0 and ::0), for LLMNR, on both TCP and UDP. As with MulticastDNS filtering by incoming network interface is applied.
