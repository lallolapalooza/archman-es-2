NOMBRE

systemd, init - gestor de sistema y servicios de systemd

SINOPSIS

/usr/lib/systemd/systemd [OPCIONES...]

init [OPCIONES...]

DESCRIPCIÓN

systemd es un gestor de sistema y servicios para sistemas operativos Linux. Cuando se ejecuta como primer proceso al arrancar (como PID 1), actúa como sistema init que inicia y mantiene los servicios del espacio de usuario. Se inician instancias separadas para los usuarios que inician sesión para que inicien sus servicios.

systemd normalmente no es invocado directamente por el usuario, sino que se instala como el enlace simbólico /sbin/init y se inicia durante el arranque temprano. Las instancias del gestor de usuario se inician automáticamente a través del servicio user@.service(5).

Cuando se ejecuta como una instancia del sistema, systemd interpreta el archivo de configuración system.conf y los archivos en los directorios system.conf.d; cuando se ejecuta como una instancia de usuario, systemd interpreta el archivo de configuración user.conf y los archivos en los directorios user.conf.d. Consulte systemd-system.conf(5) para más información.

systemd contiene implementaciones nativas de varias tareas que deben ejecutarse como parte del proceso de arranque. Por ejemplo, establece el nombre de host o configura el dispositivo de red de bucle invertido. También configura y monta varios sistemas de archivos de API, como /sys/, /proc/, y /dev/.

systemd también reiniciará el reloj del sistema durante el arranque temprano si parece estar configurado incorrectamente. Consulte la sección "Época del reloj del sistema" a continuación.

Tenga en cuenta que algunas, pero no todas, las interfaces proporcionadas por systemd están cubiertas por la Promesa de Estabilidad y Portabilidad de la Interfaz[1].

La API de D-Bus de systemd se describe en org.freedesktop.systemd1(5) y org.freedesktop.LogControl1(5).

Los sistemas que invocan systemd en un entorno de contenedor o initrd deben implementar las especificaciones de la Interfaz de Contenedor[2] o la Interfaz initrd[3], respectivamente.

UNIDADES

systemd proporciona un sistema de dependencias entre varias entidades llamadas "unidades" de 11 tipos diferentes. Las unidades encapsulan varios objetos que son relevantes para el arranque y mantenimiento del sistema. La mayoría de las unidades se configuran en archivos de configuración de unidades, cuya sintaxis y conjunto básico de opciones se describe en systemd.unit(5), sin embargo, algunas se crean automáticamente a partir de otros archivos de configuración, dinámicamente a partir del estado del sistema o mediante programación en tiempo de ejecución. Las unidades pueden estar en varios estados, descritos en la siguiente tabla. Tenga en cuenta que los diversos tipos de unidades pueden tener varios subestados adicionales, que se mapean a los estados generales de unidad descritos aquí.

Tabla 1. Estados ACTIVOs de las unidades

Estado Descripción
active Iniciado, enlazado, conectado, ..., dependiendo del tipo de unidad.
inactive Detenido, desenlazado, desconectado, ..., dependiendo del tipo de unidad.
failed Similar a inactive, pero la unidad falló de alguna manera (el proceso devolvió un código de error al salir, se bloqueó, una operación expiró, o después de demasiados reinicios).
activating Cambiando de inactive a active.
deactivating Cambiando de active a inactive.
maintenance La unidad está inactive y una operación de mantenimiento está en progreso.
reloading La unidad está active y está recargando su configuración.
refreshing La unidad está active y se está activando un nuevo montaje en su espacio de nombres.

Los siguientes tipos de unidades están disponibles:

1.Unidades de servicio, que inician y controlan demonios y los procesos que los componen. Para más detalles, consulte systemd.service(5).
2.Unidades de socket, que encapsulan sockets IPC locales o de red en el sistema, útiles para la activación basada en sockets. Para más detalles sobre unidades de socket, consulte systemd.socket(5), para más detalles sobre la activación basada en sockets y otras formas de activación, consulte daemon(7).
3.Las unidades de destino son útiles para agrupar unidades, o proporcionar puntos de sincronización conocidos durante el arranque, consulte systemd.target(5).
4.Las unidades de dispositivo exponen dispositivos del kernel en systemd y pueden usarse para implementar la activación basada en dispositivos. Para más detalles, consulte systemd.device(5).
5.Las unidades de montaje controlan los puntos de montaje en el sistema de archivos, para más detalles consulte systemd.mount(5).
6.Las unidades de automontaje proporcionan capacidades de automontaje, para el montaje bajo demanda de sistemas de archivos, así como arranque paralelo. Consulte systemd.automount(5).
7.Las unidades de temporizador son útiles para activar otras unidades basándose en temporizadores. Puede encontrar detalles en systemd.timer(5).
8.Las unidades de swap son muy similares a las unidades de montaje y encapsulan particiones o archivos de intercambio de memoria del sistema operativo. Se describen en systemd.swap(5).
9.Las unidades de ruta pueden usarse para activar otros servicios cuando los objetos del sistema de archivos cambian o se modifican. Consulte systemd.path(5).
10.Las unidades de slice pueden usarse para agrupar unidades que gestionan procesos del sistema (como unidades de servicio y scope) en un árbol jerárquico para fines de gestión de recursos. Consulte systemd.slice(5).
11.Las unidades de scope son similares a las unidades de servicio, pero gestionan procesos externos en lugar de iniciarlos. Consulte systemd.scope(5).

Las unidades se nombran como sus archivos de configuración. Algunas unidades tienen semántica especial. Una lista detallada está disponible en systemd.special(7).

systemd conoce varios tipos de dependencias, incluidas dependencias de requisito positivas y negativas (es decir, Requires= y Conflicts=), así como dependencias de orden (After= y Before=). NOTA: las dependencias de orden y requisito son ortogonales. Si solo existe una dependencia de requisito entre dos unidades (por ejemplo, foo.service requiere bar.service), pero ninguna dependencia de orden (por ejemplo, foo.service después de bar.service) y ambas se solicitan iniciar, se iniciarán en paralelo. Es un patrón común que tanto las dependencias de requisito como las de orden se coloquen entre dos unidades. Tenga en cuenta también que la mayoría de las dependencias son creadas y mantenidas implícitamente por systemd. En la mayoría de los casos, no debería ser necesario declarar dependencias adicionales manualmente, sin embargo, es posible hacerlo.

Los programas de aplicación y las unidades (a través de dependencias) pueden solicitar cambios de estado de las unidades. En systemd, estas solicitudes se encapsulan como 'jobs' y se mantienen en una cola de jobs. Los jobs pueden tener éxito o fallar, su ejecución se ordena basándose en las dependencias de orden de las unidades para las que se han programado.

Al arrancar, systemd activa la unidad de destino por defecto default.target, cuyo trabajo es activar servicios y otras unidades de arranque al iniciar, al ser invocadas mediante dependencias. Normalmente, el nombre de la unidad es solo un alias (enlace simbólico) para graphical.target (para arranques completos a la interfaz gráfica) o multi-user.target (para arranques limitados solo a consola para uso en entornos integrados o de servidor, o similares; un subconjunto de graphical.target). Sin embargo, queda a discreción del administrador configurarlo como un alias para cualquier otra unidad de destino. Consulte systemd.special(7) para más detalles sobre estas unidades de destino.

En el primer arranque, systemd habilitará o deshabilitará unidades de acuerdo con la política preestablecida. Consulte systemd.preset(5) y la sección "Semántica del Primer Arranque" en machine-id(5).

1. Está en un estado activo, activando, desactivando o fallido (es decir, en cualquier estado de unidad excepto "inactivo")
2. Tiene un trabajo en cola para ella
3. Es una dependencia de al menos otra unidad que esté cargada en memoria

5. Ha sido fijada en memoria programáticamente mediante una llamada D-Bus

systemd cargará automáticamente y de forma implícita unidades desde el disco (si aún no están cargadas) tan pronto como se soliciten operaciones sobre ellas. Por lo tanto, en muchos aspectos, el hecho de que una unidad esté cargada o no es invisible para los clientes. Usa systemctl list-units --all para listar exhaustivamente todas las unidades actualmente cargadas. Cualquier unidad para la que no se aplique ninguna de las condiciones anteriores se descargará rápidamente. Ten en cuenta que cuando una unidad se descarga de la memoria, sus datos de contabilidad también se eliminan. Sin embargo, estos datos generalmente no se pierden, ya que se genera un registro de journal que declara los recursos consumidos siempre que una unidad se apaga.

Los procesos que systemd crea se colocan en grupos de control de Linux individuales con nombres que se corresponden con la unidad a la que pertenecen en la jerarquía privada de systemd. (ver Control Groups v2[4] para más información sobre grupos de control, o "cgroups" en resumen). systemd utiliza esto para realizar un seguimiento efectivo de los procesos. La información del grupo de control se mantiene en el kernel y es accesible a través de la jerarquía del sistema de archivos (debajo de /sys/fs/cgroup/), o en herramientas como systemd-cgls(1) o ps(1) (ps xawf -eo pid,user,cgroup,args es particularmente útil para listar todos los procesos y las unidades de systemd a las que pertenecen).

systemd es compatible con varias funcionalidades establecidas de Unix como /etc/fstab o la base de datos utmp.

systemd tiene un sistema de transacciones mínimo: si se solicita a una unidad que se inicie o se detenga, se agregará a sí misma y a todas sus dependencias a una transacción temporal. Luego, verificará si la transacción es consistente (es decir, si el ordenamiento de todas las unidades está libre de ciclos). Si no lo está, systemd intentará corregirla y eliminará trabajos no esenciales de la transacción que puedan eliminar el bucle. Además, systemd intenta suprimir trabajos no esenciales en la transacción que detendrían un servicio en ejecución. Finalmente, se comprueba si los trabajos de la transacción contradicen los trabajos que ya se han puesto en cola y, opcionalmente, la transacción se aborta en ese momento. Si todo funcionó y la transacción es consistente y minimiza su impacto, se fusiona con todos los trabajos pendientes y se agrega a la cola de ejecución. Efectivamente, esto significa que antes de ejecutar una operación solicitada, systemd verificará que tenga sentido, la corregirá si es posible y solo fallará si realmente no puede funcionar.

Ten en cuenta que las transacciones se generan independientemente del estado de una unidad en tiempo de ejecución, por lo tanto, por ejemplo, si se solicita un trabajo de inicio en una unidad ya iniciada, aún generará una transacción y activará cualquier dependencia inactiva (y causará la propagación de otros trabajos según las relaciones definidas). Esto se debe a que el trabajo en cola se compara en el momento de la ejecución con el estado de la unidad de destino y se marca como exitoso y completo cuando ambos se satisfacen. Sin embargo, este trabajo también atrae a otras dependencias debido a las relaciones definidas y, por lo tanto, conduce, en nuestro ejemplo, a que también se pongan en cola trabajos de inicio para cualquiera de esas unidades inactivas.

Las unidades pueden generarse dinámicamente al arrancar y al recargar el gestor del sistema, por ejemplo, basándose en otros archivos de configuración o parámetros pasados en la línea de comandos del kernel. Para más detalles, ver systemd.generator(7).

DIRECTORIOS

Directorios de unidades del sistema

El gestor del sistema systemd lee la configuración de unidades de varios directorios. Los paquetes que deseen instalar archivos de unidades deben colocarlos en el directorio devuelto por pkg-config systemd --variable=systemdsystemunitdir. Otros directorios que se revisan son /usr/local/lib/systemd/system y /usr/lib/systemd/system. La configuración del usuario siempre tiene precedencia. pkg-config systemd --variable=systemdsystemconfdir devuelve la ruta del directorio de configuración del sistema. Los paquetes solo deben alterar el contenido de estos directorios con los comandos enable y disable de la herramienta systemctl(1). La lista completa de directorios se proporciona en systemd.unit(5).

Directorios de unidades de usuario

Reglas similares se aplican a los directorios de unidades de usuario. Sin embargo, aquí se sigue la especificación de directorios base XDG[5] para encontrar unidades. Las aplicaciones deben colocar sus archivos de unidades en el directorio devuelto por pkg-config systemd --variable=systemduserunitdir. La configuración global se realiza en el directorio reportado por pkg-config systemd --variable=systemduserconfdir. Los comandos enable y disable de la herramienta systemctl(1) pueden manejar tanto la habilitación/deshabilitación global (es decir, para todos los usuarios) como la privada (para un usuario) de unidades. La lista completa de directorios se proporciona en systemd.unit(5).

SEÑALES

El servicio escucha varias señales de procesos UNIX que se pueden utilizar para solicitar diversas acciones de forma asíncrona. El manejo de señales se habilita muy temprano durante el arranque, antes de que se invoquen otros procesos. Sin embargo, un gestor de contenedores supervisor o similar que pretenda solicitar estas operaciones a través de este mecanismo debe tener en cuenta que esta funcionalidad no está disponible durante la fase de inicialización más temprana. Se emite un mensaje de notificación sd_notify() que contiene el campo X_SYSTEMD_SIGNALS_LEVEL=2 una vez que los manejadores de señales están habilitados, ver más abajo. Esto puede utilizarse para programar la entrega de estas señales correctamente.

SIGTERM

Al recibir esta señal, el gestor del sistema systemd serializa su estado, se reejecuta a sí mismo y deserializa el estado guardado nuevamente. Esto es en gran medida equivalente a systemctl daemon-reexec.

Los gestores de usuario de systemd iniciarán la unidad exit.target cuando reciban esta señal. Esto es en gran medida equivalente a systemctl --user start exit.target --job-mode=replace-irreversibly.

SIGINT

Al recibir esta señal, el gestor del sistema systemd iniciará la unidad ctrl-alt-del.target. Esto es en gran medida equivalente a systemctl start ctrl-alt-del.target --job-mode=replace-irreversibly. Si esta señal se recibe más de 7 veces en 2 segundos, se desencadenará un reinicio inmediato. Ten en cuenta que presionar Ctrl+Alt+Del en la consola activará esta señal. Por lo tanto, si un reinicio se cuelga, presionar Ctrl+Alt+Del más de 7 veces en 2 segundos es una forma relativamente segura de desencadenar un reinicio inmediato.

Los gestores de usuario de systemd tratan esta señal de la misma manera que SIGTERM.

SIGWINCH

Al recibir esta señal, el gestor del sistema systemd iniciará la unidad kbrequest.target. Esto es en gran medida equivalente a systemctl start kbrequest.target.

Esta señal es ignorada por los gestores de usuario de systemd.

SIGPWR

Al recibir esta señal, el gestor de systemd iniciará la unidad sigpwr.target. Esto es en gran medida equivalente a systemctl start sigpwr.target.

SIGUSR1

Al recibir esta señal, el gestor de systemd intentará reconectarse al bus D-Bus.

SIGUSR2

Al recibir esta señal, el gestor de systemd registrará su estado completo en formato legible por humanos. Los datos registrados son los mismos que los impresos por systemd-analyze dump.

SIGHUP

Recarga la configuración completa del demonio. Esto es en gran medida equivalente a systemctl daemon-reload.

SIGRTMIN+0

Entra en modo por defecto, inicia la unidad default.target. Esto es en gran medida equivalente a systemctl isolate default.target.

SIGRTMIN+1

Entra en modo de rescate, inicia la unidad rescue.target. Esto es en gran medida equivalente a systemctl isolate rescue.target.

SIGRTMIN+2

Entra en modo de emergencia, inicia la unidad emergency.service. Esto es en gran medida equivalente a systemctl isolate emergency.service.

SIGRTMIN+3

Detiene la máquina, inicia la unidad halt.target. Esto es en gran medida equivalente a systemctl start halt.target --job-mode=replace-irreversibly.

SIGRTMIN+4

Apaga la máquina, inicia la unidad poweroff.target. Esto es en gran medida equivalente a systemctl start poweroff.target --job-mode=replace-irreversibly.

SIGRTMIN+5

Reinicia la máquina, inicia la unidad reboot.target. Esto es en gran medida equivalente a systemctl start reboot.target --job-mode=replace-irreversibly.

SIGRTMIN+6

Reinicia la máquina mediante kexec, inicia la unidad kexec.target. Esto es en gran medida equivalente a systemctl start kexec.target --job-mode=replace-irreversibly.

SIGRTMIN+7

Reinicia el espacio de usuario, inicia la unidad soft-reboot.target. Esto es en gran medida equivalente a systemctl start soft-reboot.target --job-mode=replace-irreversibly.

Añadido en la versión 254.

Detiene la máquina inmediatamente.

SIGRTMIN+14

Apaga la máquina inmediatamente.

SIGRTMIN+15

Reinicia la máquina inmediatamente.

SIGRTMIN+16

SIGRTMIN+20

Habilita la visualización de mensajes de estado en la consola, según se controle mediante systemd.show_status=1 en la línea de comandos del kernel.

Es posible que desees usar SetShowStatus() en lugar de SIGRTMIN+20 para evitar condiciones de carrera. Ver org.freedesktop.systemd1(5).

Inhabilita la visualización de mensajes de estado en la consola, según se controle mediante systemd.show_status=0 en la línea de comandos del kernel.

Es posible que desees usar SetShowStatus() en lugar de SIGRTMIN+21 para prevenir condiciones de carrera. Ver org.freedesktop.systemd1(5).

Establece el nivel de registro del administrador del servicio a "debug", de manera equivalente a systemd.log_level=debug en la línea de comandos del kernel.

El valor configurado se deriva de — en orden de prioridad — el valor especificado con systemd.log-level= en la línea de comandos del kernel, o el valor especificado con LogLevel= en el archivo de configuración, o el valor predeterminado interno de "info".

El administrador del sistema systemd trata esta señal de la misma manera que SIGTERM.

ENTORNO

El bloque de entorno para el administrador del sistema se establece inicialmente por el kernel. (En particular, las asignaciones "key=value" en la línea de comandos del kernel se convierten en variables de entorno para PID 1). Para el administrador de usuario, el administrador del sistema establece el entorno como se describe en la sección "Variables de Entorno en Procesos Generados" de systemd.exec(5). La configuración de DefaultEnvironment= en el administrador del sistema se aplica a todos los servicios, incluido user@.service. Se pueden configurar entradas adicionales (como para cualquier otro servicio) a través de la configuración de Environment= y EnvironmentFile= para user@.service (ver systemd.exec(5)). Además, se pueden establecer variables de entorno adicionales a través de la configuración de ManagerEnvironment= en systemd-system.conf(5) y systemd-user.conf(5).

Algunas de las variables entendidas por systemd:

$SYSTEMD_LOG_LEVEL

El nivel de registro máximo de los mensajes emitidos (los mensajes con un nivel de registro más alto, es decir, menos importantes, se suprimirán). Toma una lista separada por comas de valores. Un valor puede ser uno de (en orden de importancia decreciente) emerg, alert, crit, err, warning, notice, info, debug, o un entero en el rango 0...7. Ver syslog(3) para más información. Cada valor puede ir opcionalmente precedido por uno de console, syslog, kmsg o journal seguido de dos puntos para establecer el nivel de registro máximo para ese destino de registro específico (por ejemplo, SYSTEMD_LOG_LEVEL=debug,console:info especifica registrar a nivel de depuración excepto cuando se registra en la consola, que debe estar a nivel de información). Tenga en cuenta que el nivel de registro máximo global tiene prioridad sobre cualquier nivel de registro máximo por destino.

Esto puede ser anulado con --log-level=.

$SYSTEMD_LOG_COLOR

Un booleano. Si es verdadero, los mensajes escritos en el tty se colorearán según la prioridad.

Esto puede ser anulado con --log-color=.

$SYSTEMD_LOG_TIME

Un booleano. Si es verdadero, los mensajes de registro de la consola se prefijarán con una marca de tiempo.

Esto puede ser anulado con --log-time=.

Añadido en la versión 246.

$SYSTEMD_LOG_LOCATION

Un booleano. Si es verdadero, los mensajes se prefijarán con un nombre de archivo y número de línea en el código fuente de donde se origina el mensaje.

Esto puede ser anulado con --log-location=.

$SYSTEMD_LOG_TID

Un booleano. Si es verdadero, los mensajes se prefijarán con el ID de hilo (TID) numérico actual.

Añadido en la versión 247.

$SYSTEMD_LOG_TARGET

El destino de los mensajes de registro. Uno de console (registrar en el tty adjunto), console-prefixed (registrar en el tty adjunto pero con prefijos que codifican el nivel de registro y la "instalación", ver syslog(3), kmsg (registrar en el búfer de registro circular del kernel), journal (registrar en el journal), journal-or-kmsg (registrar en el journal si está disponible, y en kmsg de lo contrario), auto (determinar automáticamente el destino de registro apropiado, el predeterminado), null (deshabilitar la salida de registro).

Esto puede ser anulado con --log-target=.

$SYSTEMD_LOG_RATELIMIT_KMSG

Si limitar la tasa de kmsg o no. Toma un booleano. Predeterminado es "true". Si está deshabilitado, systemd no limitará la tasa de mensajes escritos en kmsg.

Añadido en la versión 254.

$XDG_CONFIG_HOME, $XDG_CONFIG_DIRS, $XDG_DATA_HOME, $XDG_DATA_DIRS

El administrador de usuario de systemd utiliza estas variables de acuerdo con la especificación de directorios base de XDG[5] para encontrar su configuración.

$SYSTEMD_UNIT_PATH, $SYSTEMD_GENERATOR_PATH, $SYSTEMD_ENVIRONMENT_GENERATOR_PATH

Controla dónde busca systemd los archivos de unidad y generadores.

Estas variables pueden contener una lista de rutas, separadas por dos puntos (":"). Cuando se establecen, si la lista termina con un componente vacío ("...:"), esta lista se antepone al conjunto habitual de rutas. De lo contrario, la lista especificada reemplaza el conjunto habitual de rutas.

$SYSTEMD_PAGER, $PAGER

Paginador a usar cuando no se proporciona --no-pager. $SYSTEMD_PAGER se usa si está establecido; de lo contrario, se usa $PAGER. Si ni $SYSTEMD_PAGER ni $PAGER están establecidos, se intentan en orden una serie de implementaciones de paginador conocidas, incluidas less(1) y more(1), hasta que se encuentre una. Si no se descubre ninguna implementación de paginador, no se invoca ningún paginador. Establecer estas variables de entorno a una cadena vacía o al valor "cat" es equivalente a pasar --no-pager.

Nota: si $SYSTEMD_PAGERSECURE no está establecido, $SYSTEMD_PAGER y $PAGER solo se pueden usar para deshabilitar el paginador (con "cat" o ""), y de lo contrario se ignoran.

$SYSTEMD_LESS

Anula las opciones pasadas a less (por defecto "FRSXMK").

Los usuarios pueden querer cambiar dos opciones en particular:

K

Esta opción instruye al paginador para que salga inmediatamente cuando se presione Ctrl+C. Para permitir que less maneje Ctrl+C por sí mismo para volver al prompt del comando del paginador, desactive esta opción.

Si el valor de $SYSTEMD_LESS no incluye "K", y el paginador que se invoca es less, el ejecutable ignorará Ctrl+C, y deberá ser manejado por el paginador.

X

Esta opción instruye al paginador para que no envíe las cadenas de inicialización y desinicialización de termcap al terminal. Se establece por defecto para permitir que la salida del comando permanezca visible en el terminal incluso después de que el paginador salga. Sin embargo, esto impide que funcione cierta funcionalidad del paginador, en particular, la salida paginada no se puede desplazar con el ratón.

Tenga en cuenta que establecer la variable de entorno regular $LESS no tiene efecto para las invocaciones de less por herramientas de systemd.

Ver less(1) para más discusión.

$SYSTEMD_LESSCHARSET

Anula el conjunto de caracteres pasado a less (por defecto "utf-8", si el terminal invocador se determina que es compatible con UTF-8).

Tenga en cuenta que establecer la variable de entorno regular $LESSCHARSET no tiene efecto para las invocaciones de less por herramientas de systemd.

$SYSTEMD_PAGERSECURE

Los comandos de paginador comunes como less(1), además de la "paginación", es decir, la navegación por la salida, admiten la apertura o escritura de otros archivos y la ejecución de comandos arbitrarios del shell. Cuando se invocan comandos con privilegios elevados, por ejemplo bajo sudo(8) o pkexec(1), el paginador se convierte en un límite de seguridad. Se debe tener cuidado de que solo se utilicen programas con funcionalidad estrictamente limitada como paginadores, y que no se permitan funciones interactivas no deseadas como la apertura o creación de nuevos archivos o el inicio de subprocesos. El "modo seguro" para el paginador se puede habilitar como se describe a continuación, si el paginador lo admite (la mayoría de los paginadores no están escritos de manera que tengan esto en cuenta). Se recomienda habilitar explícitamente el "modo seguro" o deshabilitar completamente el paginador usando --no-pager o PAGER=cat al permitir que los usuarios no confiables ejecuten comandos con privilegios elevados.

Esta opción toma un argumento booleano. Cuando se establece en verdadero, se habilita el "modo seguro" del paginador. En "modo seguro", se establecerá LESSSECURE=1 al invocar el paginador, lo que instruye al paginador para deshabilitar comandos que abren o crean nuevos archivos o inician nuevos subprocesos. Actualmente, solo less(1) entiende esta variable e implementa el "modo seguro".

Cuando se establece en falso, no se impone ninguna limitación al paginador. Establecer SYSTEMD_PAGERSECURE=0 o no eliminarlo del entorno heredado puede permitir al usuario invocar comandos arbitrarios.

Cuando $SYSTEMD_PAGERSECURE no está establecido, las herramientas de systemd intentan determinar automáticamente si se debe habilitar el "modo seguro" y si el paginador lo admite. El "modo seguro" se habilita si el UID efectivo no es el mismo que el propietario de la sesión de inicio de sesión, ver geteuid(2) y sd_pid_get_owner_uid(3), o cuando se ejecuta bajo sudo(8) o herramientas similares (se establece $SUDO_UID [6]). En esos casos, SYSTEMD_PAGERSECURE=

VARIABLES DE ENTORNO

Las siguientes variables de entorno son entendidas por systemd y sus utilidades:

$SYSTEMD_PAGER

Si se establece, se utiliza para paginar la salida de las utilidades de systemd. Por defecto, se utilizan paginadores que no son conscientes de la seguridad del modo seguro (como more(1)). Si esta variable está establecida, se utilizará el paginador especificado. Si está vacía, se desactiva el paginador. Si no está configurada, se cae a $PAGER, y si esa tampoco está configurada, se utiliza el comportamiento por defecto. Véase también systemd.PagerSecure.

$SYSTEMD_PAGERSECURE

Si se establece como un valor booleano positivo (por ejemplo, "1", "true"), se habilitará el modo seguro para el paginador. En este modo, se pasa la variable LESSSECURE con el valor "1" a less(1), y se pasan los argumentos apropiados para habilitar el modo seguro a otros paginadores conocidos. Si se establece como un valor booleano negativo (por ejemplo, "0", "false"), el modo seguro del paginador se deshabilitará. Si no está configurada, se utilizará un modo seguro predeterminado basado en la autodetección de la seguridad del paginador. El modo seguro del paginador se establecerá y los paginadores que no se sepa que implementan el "modo seguro" no se utilizarán en absoluto. Tenga en cuenta que esta autodetección solo cubre los mecanismos más comunes para elevar privilegios y está destinada a ser una conveniencia. Se recomienda establecer explícitamente $SYSTEMD_PAGERSECURE o deshabilitar el paginador.

Tenga en cuenta que si las variables $SYSTEMD_PAGER o $PAGER van a ser tenidas en cuenta, aparte de para deshabilitar el paginador, también debe estar configurada $SYSTEMD_PAGERSECURE.

$SYSTEMD_COLORS

Toma un argumento booleano. Cuando es verdadero, systemd y las utilidades relacionadas utilizarán colores en su salida, de lo contrario la salida será monocromática. Adicionalmente, la variable puede tomar uno de los siguientes valores especiales: "16", "256" para restringir el uso de colores a los 16 o 256 colores ANSI base, respectivamente. Esto puede especificarse para anular la decisión automática basada en $TERM y a qué está conectada la consola.

$SYSTEMD_URLIFY

El valor debe ser booleano. Controla si se generarán enlaces clicables en la salida para emuladores de terminal que lo soporten. Esto puede especificarse para anular la decisión que systemd toma basándose en $TERM y otras condiciones.

$LISTEN_PID, $LISTEN_FDS, $LISTEN_FDNAMES

Configuradas por systemd para procesos supervisados durante la activación basada en socket. Véase sd_listen_fds(3) para más información.

$NOTIFY_SOCKET

Configurada por el gestor de servicios para sus servicios para notificaciones de estado y preparación. También es consumida por el gestor de servicios para notificar a los gestores de contenedores supervisores o gestores de servicios de nivel superior sobre su propio progreso. Véase sd_notify(3) y la sección relevante a continuación para más información.

Para más variables de entorno entendidas por systemd y sus diversos componentes, véase Variables de Entorno Conocidas[7].

CREDENTIALES DEL SISTEMA

Durante la inicialización, el gestor de servicios importará credenciales de varias fuentes al conjunto de credenciales del sistema, que luego podrán propagarse a los servicios y ser consumidas por los generadores:

•Cuando el gestor de servicios se inicializa por primera vez, leerá las credenciales del sistema de las cadenas de proveedor SMBIOS Tipo 11 io.systemd.credential:name=value, y io.systemd.credential.binary:name=value.
•Al mismo tiempo, importará credenciales del QEMU "fw_cfg". (Ten en cuenta que el mecanismo SMBIOS es generalmente preferido, ya que es más rápido y genérico.)
•Las credenciales pueden pasarse a través de la línea de comandos del kernel, utilizando el parámetro systemd.set-credential=, véase más arriba.
•Las credenciales pueden pasarse desde el entorno UEFI a través de systemd-stub(7).
•Cuando se invoca el gestor de servicios durante la transición initrd → host, importará todos los archivos en /run/credentials/@initrd/ como credenciales del sistema.

Invoca systemd-creds(1) de la siguiente manera para ver la lista de credenciales pasadas al sistema:

# systemd-creds --system list

Para más información, consulta la documentación de Credenciales del Sistema y del Servicio[8].

El gestor de servicios, cuando se ejecuta como PID 1, consume las siguientes credenciales del sistema:

vmm.notify_socket

Contiene una dirección AF_VSOCK o AF_UNIX a la que enviar un mensaje de notificación READY=1 cuando el gestor de servicios haya completado el arranque. Consulta sd_notify(3) y la siguiente sección para más información. Ten en cuenta que en caso de que el hipervisor no soporte SOCK_DGRAM sobre AF_VSOCK, se intentará usar SOCK_SEQPACKET en su lugar. La carga útil de la credencial para AF_VSOCK debe ser una cadena con el formato "vsock:CID:PORT". Se pueden usar "vsock-stream", "vsock-dgram" y "vsock-seqpacket" en lugar de "vsock" para forzar el uso del tipo de socket correspondiente.

Esta función es útil para gestores de máquinas u otros procesos en el host para recibir una notificación a través de VSOCK cuando una máquina virtual ha terminado de arrancar.

Añadido en la versión 254.

system.machine_id

PROTOCOLO DE DISPONIBILIDAD

El gestor de servicios implementa un protocolo de notificación de disponibilidad tanto entre el gestor y sus servicios (es decir, hacia abajo en la pila), como entre el gestor y un supervisor potencial más arriba en la pila (este último podría ser un gestor de máquinas o contenedores, o en el caso de un gestor de servicios por usuario, la instancia del gestor de servicios del sistema). El protocolo básico (y la API sugerida para él) se describe en sd_notify(3).

El socket de notificación que el gestor de servicios (incluido PID 1) utiliza para informar de su disponibilidad a su propio supervisor se establece a través de la variable de entorno habitual $NOTIFY_SOCKET (véase más arriba). Dado que esto solo se puede configurar directamente para gestores de contenedores y para la instancia por usuario del gestor de servicios, hay disponible un mecanismo adicional para configurarlo, especialmente destinado a entornos de VM: el credential del sistema vmm.notify_socket (véase más arriba) se puede establecer en un socket adecuado (típicamente uno AF_VSOCK) a través de las cadenas de proveedor SMBIOS Tipo 11. Para más detalles, véase más arriba.

El protocolo de notificación del gestor de servicios hacia arriba en la pila hacia un supervisor soporta varios campos de extensión que permiten a un supervisor conocer propiedades específicas del sistema y rastrear su progreso de arranque. Específicamente, se envían los siguientes campos:

•Se enviará un mensaje X_SYSTEMD_HOSTNAME=... una vez determinado el nombre de host inicial del sistema. Ten en cuenta que durante el tiempo de ejecución posterior, el nombre de host puede cambiar de nuevo programáticamente, y (actualmente) no se envían más notificaciones en ese caso.

Añadido en la versión 256.

•Se enviará un mensaje X_SYSTEMD_MACHINE_ID=... una vez determinado el ID de máquina del sistema. Consulta machine-id(5) para más detalles.

Añadido en la versión 256.

•Se enviará un mensaje X_SYSTEMD_SIGNALS_LEVEL=... una vez que el gestor de servicios haya instalado los diversos manejadores de señales de procesos UNIX descritos anteriormente. El valor del campo es un entero sin signo formateado como una cadena decimal, e indica el nivel de función de señales de procesos UNIX soportado por el gestor de servicios. Actualmente, solo se define un nivel de función:
•X_SYSTEMD_SIGNALS_LEVEL=2 cubre las diversas señales de procesos UNIX documentadas anteriormente – que son un superconjunto de las soportadas por el sistema init histórico de SysV.

Las señales enviadas a PID 1 antes de que se envíe este mensaje podrían no ser manejadas correctamente todavía. Un consumidor de estos mensajes debe analizar el valor como un entero sin signo que indica el nivel de soporte. Por ahora, solo se define el nivel 2 mencionado, pero más adelante se podrían definir niveles adicionales con enteros más altos, que implementarán un superconjunto del comportamiento definido actualmente.

Añadido en la versión 256.

•Se enviarán mensajes X_SYSTEMD_UNIT_ACTIVE=... y X_SYSTEMD_UNIT_INACTIVE=... para cada unidad de destino a medida que se active o deje de estarlo. Esto es útil para seguir el progreso y la funcionalidad del arranque. Por ejemplo, una vez que la unidad ssh-access.target se reporte como iniciada, el acceso SSH normalmente estará disponible, consulta systemd.special(7) para más detalles.

Añadido en la versión 256.

•Se enviará un mensaje X_SYSTEMD_SHUTDOWN=... muy poco antes de que el sistema se apague. El valor es una de las cadenas "reboot", "halt", "poweroff", "kexec" e indica qué tipo de apagado se está ejecutando.

Añadido en la versión 256.

•También se enviará un mensaje X_SYSTEMD_REBOOT_PARAMETER=... muy poco antes de que el sistema se apague. Su valor es el argumento de reinicio configurado con systemctl --reboot-argument=....

Añadido en la versión 256.

Ten en cuenta que estos campos de extensión se envían además de las notificaciones regulares "READY=1" y "RELOADING=1".

OPCIONES

systemd se invoca muy raramente de forma directa, ya que se inicia temprano y ya está en ejecución cuando los usuarios pueden interactuar con él. Normalmente, se utilizan herramientas como systemctl(1) para dar comandos al gestor. Dado que systemd generalmente no se invoca directamente, las opciones listadas a continuación son principalmente útiles para depuración y propósitos especiales.

Determina la transacción de inicio inicial (es decir, la lista de trabajos en cola al inicio), la muestra y sale — sin ejecutar realmente ninguno de los trabajos determinados. See systemd.default_standard_output= and systemd.default_standard_error= above. SYSTEM CLOCK EPOCH When systemd is started or restarted, it may set the system clock to the "epoch". This mechanism is used to ensure that the system clock remains somewhat reasonably initialized and roughly monotonic across reboots, in case no battery-backed local RTC is available or it does not work correctly. The epoch is the lowest date above which the system clock time is assumed to be set correctly. When initializing, the local clock is *advanced* to the epoch if it was set to a lower value. As a special case, if the local clock is sufficiently far in the future (by default 15 years, but this can be configured at build time), the hardware clock is assumed to be broken, and the system clock is *rewound* to the epoch. The epoch is set to the highest of: the build time of systemd, the modification time ("mtime") of /usr/lib/clock-epoch, and the modification time of /var/lib/systemd/timesync/clock.
