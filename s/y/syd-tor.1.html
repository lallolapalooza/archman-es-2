SYD-TOR(1) Manual de comandos generales SYD-TOR(1)

NOMBRE

syd-tor - Reenviador de proxy SOCKS

SINOPSIS

syd-tor [-dh] -p <pid-fd> -i <socket-fd> [-o addr:puerto] [-u sockunix]

DESCRIPCIÓN

Recibe un socket de escucha del fd y reenvía el tráfico a addr:puerto o a un socket UNIX.

La dirección externa debe ser una dirección IPv4, IPv6 o una ruta a un socket de dominio UNIX, por defecto es 127.0.0.1:9050.

El descriptor de archivo PID se utiliza para rastrear la salida del proceso Syd.

OPCIONES

-h Mostrar ayuda.
-d Ejecutar en modo de depuración sin confinamiento.
-p pid-fd Descriptor de archivo PID del proceso Syd.
-i socket-fd Descriptor de archivo de socket para recibir el socket de escucha.
-o dir-ext Especificar la dirección externa a la que reenviar el tráfico.
La dirección puede ser una dirección IPv4/IPv6 en formato "dir:puerto".
Por defecto es "127.0.0.1:9050".
-u sockunix Especificar un socket de dominio UNIX al que reenviar el tráfico.
Esta opción tiene precedencia sobre -o.

USO

syd-tor(1) no está diseñado para ser utilizado como una herramienta independiente. Syd invoca a syd-tor(1) al inicio cuando el "Proxy sandboxing" está activado con "sandbox/proxy:on". Consulte la sección PROXY SANDBOXING de la página del manual de syd(7) para más información. Si desea utilizar syd-tor(1) en su propio proyecto, lo primero que debe hacer es pasarle un fd PID *no bloqueante* de su propio proceso con el argumento "-p <pid-fd>" para que syd-tor(1) pueda salir simultáneamente con él. Se debe tener cuidado en esta etapa, ya que los descriptores de archivo PID son "O_CLOEXEC" por defecto. A continuación, cree un par de sockets UNIX, ingrese a un espacio de nombres de red, active el dispositivo de loopback, bind(2) un socket a un puerto en él y luego envíe este descriptor de archivo de socket a través del extremo de escritura del par de sockets con la opción "SCM_RIGHTS" de sendmsg(2). Finalmente, pase el extremo de lectura del par de sockets a syd-tor(1) con el argumento "-i <socket-fd>".

IMPLEMENTACIÓN

syd-tor(1) está diseñado teniendo en cuenta el rendimiento, la seguridad y la privacidad, utilizando técnicas avanzadas como epoll(7) con disparador de borde para una notificación de eventos eficiente y operaciones completamente asíncronas para manejar múltiples conexiones sin bloquear. Emplea transferencia de datos de cero copia utilizando la llamada al sistema splice(2) para mover datos directamente entre descriptores de archivo dentro del kernel, garantizando un alto rendimiento y privacidad de los datos. Para facilitar la comunicación bidireccional, syd-tor(1) utiliza dos pares de tuberías, lo que permite un flujo de datos sin interrupciones entre el cliente y la dirección externa. Además, syd-tor(1) confinamiento su entorno de ejecución utilizando seccomp(2) y landlock(7), restringiendo las llamadas al sistema y los accesos a archivos para minimizar la superficie de ataque. En comparación con socksns, que utiliza el tiempo de ejecución de Tokio para E/S asíncronas, syd-tor(1) enfatiza la eficiencia a nivel de kernel y la seguridad, lo que lo convierte en una solución robusta para el reenvío de proxies SOCKS.

SEGURIDAD

syd-tor(1) implementa medidas de seguridad integrales para mitigar los riesgos asociados con la ejecución fuera del sandbox de Syd, previniendo así posibles ataques "Man-in-the-Middle" (MITM) contra contenedores. Los filtros de seccomp(2) están cuidadosamente configurados para permitir solo las llamadas al sistema requeridas. La llamada al sistema socket(2) se limita a un único dominio, tipo y protocolo, mientras que connect(2) se restringe a una única dirección de memoria, evitando conexiones de red no autorizadas. Las llamadas al sistema sigaction(2) y rt_sigaction(2) no están permitidas para instalar nuevos manejadores de señales. Las llamadas al sistema pipe2(2), socket(2), connect(2), accept4(2) y shutdown(2) están protegidas por cookies de argumentos de llamadas al sistema determinadas aleatoriamente utilizando getrandom(2) con GRND_RANDOM al inicio. Consulte la sección Cookies de Argumentos de Llamadas al Sistema de la página del manual de syd(7) para obtener más información sobre las cookies de argumentos. Estas mitigaciones son más efectivas en arquitecturas de 64 bits, pero en sistemas de 32 bits, la interfaz socketcall(2) puede ser explotada. Por lo tanto, se implementan medidas de protección adicionales. En Linux 6.10 y posteriores, el área de memoria que contiene la dirección de red externa se sella usando mseal(2) y la memoria circundante se protege con páginas centinela para evitar desbordamientos o corrupción adyacente. La memoria ejecutable también está prohibida para prevenir ataques de inyección de código. Si están disponibles, landlock(7) y namespaces(7) imponen restricciones adicionales al prohibir todo acceso al sistema de archivos, proporcionando así una capa adicional de seguridad. En conjunto, estas técnicas garantizan que incluso si syd-tor(1) se ve comprometido, el alcance de las acciones maliciosas se limita significativamente, manteniendo la integridad y seguridad generales del sistema.

AMBIENTE

SYD_TOR_DEBUG Ejecutar en modo de depuración sin confinamiento, equivalente a la opción "-d"
SYD_TOR_RULES Imprimir reglas de seccomp en formato legible para humanos en la salida de error estándar al inicio

ADVERTENCIAS

El proceso syd-tor(1) se ejecuta como un solo proceso y potencialmente puede alcanzar límites de descriptores de archivo (FD) debido a la cantidad de FDs que abre por conexión. Cada conexión de cliente implica seis FDs: uno para el socket del cliente, uno para el socket externo y cuatro para las tuberías utilizadas para la transferencia bidireccional de datos (dos tuberías con un FD de entrada y uno de salida cada una). Para mitigar esto, syd-tor(1) establece el límite file-max al límite duro al anular el límite blando al inicio. Sin embargo, en algunos casos, esto puede no ser suficiente y puede ser necesario ajustar manualmente los límites de FD.
