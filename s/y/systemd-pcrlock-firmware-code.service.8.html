NOMBRE

systemd-pcrlock, systemd-pcrlock-file-system.service, systemd-pcrlock-firmware-code.service, systemd-pcrlock-firmware-config.service, systemd-pcrlock-machine-id.service, systemd-pcrlock-make-policy.service, systemd-pcrlock-secureboot-authority.service, systemd-pcrlock-secureboot-policy.service - Analizar y predecir estados de código PCR de TPM2 y generar una política de acceso a partir de la predicción

SINOPSIS

/usr/lib/systemd/systemd-pcrlock [OPCIONES...]

DESCRIPCIÓN

Nota: este comando es experimental por ahora. Aunque es probable que se convierta en un componente habitual de systemd, su comportamiento e interfaz aún pueden cambiar.

systemd-pcrlock es una herramienta que puede usarse para analizar y predecir mediciones de PCR de TPM2, y generar políticas de acceso de TPM2 a partir de la predicción, las cuales almacena en un índice NV de TPM2 (es decir, en la memoria no volátil de TPM2). Esto puede usarse posteriormente para restringir el acceso a objetos de TPM2 (como claves de cifrado de disco) a arranques del sistema en los que solo se utilizan componentes específicos y confiables.

systemd-pcrlock utiliza como entrada para su análisis y predicción:

•El registro de eventos TPM2 del firmware UEFI (es decir, /sys/kernel/security/tpm0/binary_bios_measurements) del arranque actual.
•El registro de eventos TPM2 del espacio de usuario (es decir, /run/log/systemd/tpm2-measure.log) del arranque actual.
•El estado actual de los PCR del chip TPM2.
•Archivos de definición de componentes de arranque (*.pcrlock y *.pcrlock.d/*.pcrlock, ver systemd.pcrlock(5)) que cada uno define las mediciones esperadas para un componente del proceso de arranque, permitiendo variantes alternativas para cada uno. (Las variantes pueden usarse para bendecir múltiples versiones del kernel o del cargador de arranque al mismo tiempo.)

Utiliza estas entradas para generar un registro de eventos combinado, validándolo contra los estados de los PCR. Luego, intenta reconocer los registros del registro de eventos y los compara con los componentes definidos. Para cada PCR donde esto se pueda hacer de manera exhaustiva (es decir, donde todos los registros enumerados y todos los componentes definidos se hayan emparejado) esto puede usarse para predecir mediciones futuras de PCR, teniendo en cuenta las variantes alternativas definidas para cada componente. Esta predicción puede convertirse en una política de acceso de TPM2 (que consta de elementos PolicyPCR y PolicyOR de TPM2), que luego se almacena en un índice NV en el TPM2. Esto puede usarse para bloquear secretos (como claves de cifrado de disco) a estas políticas (a través de una política PolicyAuthorizeNV de TPM2).

Utilice herramientas como systemd-cryptenroll(1) o systemd-repart(8) para vincular el cifrado de disco a una política de TPM2 de systemd-pcrlock. Específicamente, consulte los interruptores --tpm2-pcrlock= de estas herramientas.

La lógica de la política de acceso requiere un dispositivo TPM2 que implemente el comando "PolicyAuthorizeNV", es decir, que implemente TPM 2.0 versión 1.38 o posterior.

COMANDOS

Se entienden los siguientes comandos:

log

Lee el registro de eventos TPM2 combinado, lo valida, lo compara con los valores actuales de los PCR y muestra ambos en formato tabular. Combine con --json= para generar la salida en formato JSON.

Añadido en la versión 255.

cel

Lee el registro de eventos TPM2 combinado y lo escribe en STDOUT en el Formato de Registro de Eventos Canónicos de TCG (CEL-JSON)[1].

Añadido en la versión 255.

list-components

Muestra una lista de definiciones de componentes y sus variantes, es decir, los archivos *.pcrlock descubiertos en /var/lib/pcrlock.d/, /usr/lib/pcrlock.d/, y otros directorios compatibles. Ver systemd.pcrlock(5) para detalles sobre estos archivos y la lista completa de directorios buscados.

Añadido en la versión 255.

predict

Predice el estado de los PCR en arranques futuros. Esto analizará el registro de eventos TPM2 como se describe anteriormente, reconocerá los componentes y luego generará todos los valores de PCR resultantes posibles para todas las combinaciones de variantes de componentes. Tenga en cuenta que no se realiza ninguna predicción para los PCR cuyo valor no coincida con los registros del registro de eventos, para los cuales se descubren mediciones no reconocidas o para los cuales se definen componentes que no se pueden encontrar en el registro de eventos. Esta es una medida de seguridad para garantizar que cualquier política de acceso generada se pueda cumplir correctamente en los arranques actuales y futuros.

Añadido en la versión 255.

make-policy

Predice el estado de los PCR para arranques futuros, de forma similar al comando predict anterior. Luego utiliza estos datos para generar una política de acceso de TPM2 que almacena en un índice NV de TPM2. La predicción y la información sobre el TPM2 utilizado y su índice NV se escriben en /var/lib/systemd/pcrlock.json.

El índice NV se asigna en la primera invocación y se actualiza en invocaciones posteriores.

El contenido del índice NV puede modificarse (y, por lo tanto, la política almacenada en él puede actualizarse) proporcionando un PIN de acceso. Este PIN normalmente se genera automáticamente y se almacena en forma cifrada (con una política de acceso que lo vincula al propio índice NV) en el archivo de política JSON mencionado anteriormente. Este PIN puede ser elegido por el usuario, a través del interruptor --recovery-pin=. Si se especifica, puede usarse como ruta alternativa de acceso para actualizar la política.

Si la nueva predicción coincide con la antigua, este comando termina rápidamente y no realiza ninguna otra operación. (A menos que se especifique --force, ver más abajo).

A partir de la v256, se codifica una copia del archivo de política /var/lib/systemd/pcrlock.json en una credencial (ver systemd-creds(1) para más detalles) y se escribe en la partición EFI System Partition o XBOOTLDR, en el subdirectorio /loader/credentials/. Allí es recogida en el arranque por systemd-stub(7) y pasada al initrd invocado, donde puede usarse para desbloquear el sistema de archivos raíz (que típicamente contiene /var/, que es donde se encuentra la copia principal de la política, la cual, por lo tanto, no puede usarse para desbloquear el sistema de archivos raíz). El archivo de credencial se nombra según el token de entrada de arranque de la instalación (ver bootctl(1)), lo cual es configurable mediante el interruptor --entry-token=, ver más abajo.

Añadido en la versión 255.

remove-policy

Elimina una política generada previamente. Elimina el archivo /var/lib/systemd/pcrlock.json y desasigna el índice NV.

Añadido en la versión 255.

is-supported

Comprueba si el TPM2 local soporta toda la funcionalidad para que systemd-pcrlock funcione correctamente. Esto realiza pruebas similares a systemd-analyze has-tpm2, pero también verifica la compatibilidad de las operaciones de TPM2 requeridas por systemd-pcrlock. Muestra uno de los siguientes: "no", "partial" (en caso de que algunas partes del soporte de TPM2 estén disponibles en hardware, firmware, SO, pero no de forma completa), "obsolete" (si el soporte de TPM2 está disponible en hardware, firmware y SO, pero faltan las operaciones requeridas para systemd-pcrlock), "yes". Devuelve un estado de salida de cero si el soporte completo está disponible, de lo contrario, un valor distinto de cero.

Si se combina con --quiet, suprime la salida de la cadena.

Actualmente, esto verifica la compatibilidad con el comando TPM2 PolicyAuthorizeNV, así como con el algoritmo hash SHA-256.

Añadido en la versión 258.

lock-firmware-code, unlock-firmware-code

Genera/elimina archivos .pcrlock basados en el registro de eventos TPM2 del arranque actual que cubren todos los registros para los PCR 0 ("código de plataforma") y 2 ("código externo").

Esta operación permite bloquear el proceso de arranque a la versión actual del firmware del sistema y sus tarjetas de extensión. Esta operación solo debe usarse si el proveedor del sistema no proporciona datos pcrlock adecuados de antemano.

Tenga en cuenta que estos datos solo coinciden con la versión actual del firmware. Si se aplica una actualización de firmware, estos datos quedarán obsoletos y cualquier política de acceso generada a partir de ellos ya no pasará. Por lo tanto, se recomienda invocar unlock-firmware-code antes de realizar una actualización de firmware, seguido de make-policy para actualizar la política.

systemd-pcrlock lock-firmware-code se invoca automáticamente en el arranque a través de la unidad systemd-pcrlock-firmware-code.service, si está habilitada. Esto asegura que una política de acceso administrada por systemd-pcrlock se bloquea automáticamente a la nueva versión del firmware cada vez que la política

Añadido en la versión 255.

lock-firmware-config, unlock-firmware-config

Esto es similar a lock-firmware-code/unlock-firmware-code pero bloquea la configuración del firmware, es decir, los PCR 1 ("platform-config") y 3 ("external-config").

Esta funcionalidad debe usarse con cuidado, ya que en la mayoría de los escenarios un cambio menor en la configuración del firmware no debería invalidar las políticas de acceso a los objetos de TPM2. Tenga en cuenta también que algunos sistemas miden información inestable e impredecible (por ejemplo, voltajes actuales de la CPU, temperaturas, como parte de los datos SMBIOS) en estos PCR, lo que significa que esta forma de bloqueo no se puede utilizar de forma fiable en tales sistemas. Utilice esta funcionalidad solo si el sistema y el hardware son bien conocidos y no sufren estas limitaciones, por ejemplo, en entornos virtualizados.

Utilice unlock-firmware-config antes de realizar cambios en la configuración del firmware. Si la unidad systemd-pcrlock-firmware-config.service está habilitada, generará automáticamente un archivo pcrlock a partir de las nuevas mediciones.

Esto escribe/elimina los archivos /var/lib/pcrlock.d/250-firmware-config-early.pcrlock.d/generated.pcrlock y /var/lib/pcrlock.d/550-firmware-config-late.pcrlock.d/generated.pcrlock.

Añadido en la versión 255.

lock-secureboot-policy, unlock-secureboot-policy

Genera/elimina un archivo .pcrlock basado en la política SecureBoot actualmente aplicada. Esto analiza las variables EFI de SecureBoot, PK, KEK, db, dbx, dbt, dbr y predice sus mediciones para el PCR 7 ("secure-boot-policy") en el próximo arranque.

Utilice unlock-firmware-config antes de aplicar actualizaciones de la política SecureBoot. Si la unidad systemd-pcrlock-secureboot-policy.service está habilitada, generará automáticamente un archivo pcrlock a partir de la política descubierta.

Esto escribe/elimina el archivo /var/lib/pcrlock.d/230-secureboot-policy.pcrlock.d/generated.pcrlock.

lock-secureboot-authority, unlock-secureboot-authority

Genera/elimina un archivo .pcrlock basado en las autoridades SecureBoot utilizadas para validar la ruta de arranque. Las autoridades SecureBoot son las entradas específicas de la base de datos SecureBoot que se utilizaron para validar los binarios PE de UEFI ejecutados en el arranque. Esto analiza el registro de eventos del arranque actual y utiliza mediciones relevantes en el PCR 7 ("secure-boot-policy").

Esto escribe/elimina el archivo /var/lib/pcrlock.d/620-secureboot-authority.pcrlock.d/generated.pcrlock.

Añadido en la versión 255.

Si no se especifica ningún disco, determina automáticamente el dispositivo de bloque que respalda el sistema de archivos raíz. Esto bloquea el estado del particionamiento del disco del medio arrancado, que el firmware mide en el PCR 5 ("boot-loader-config").

Esto escribe/elimina el archivo /var/lib/pcrlock.d/600-gpt.pcrlock.d/generated.pcrlock.

Añadido en la versión 255.

lock-pe [BINARY], unlock-pe

Genera/elimina un archivo .pcrlock basado en el binario PE especificado. Esto es útil para predecir las mediciones que el firmware realiza en el PCR 4 ("boot-loader-code") si el binario especificado forma parte del proceso de arranque UEFI. Úselo en binarios de cargador de arranque y similares. Utilice lock-uki (ver más abajo) para binarios PE que son imágenes de kernel unificadas (UKI).

Espera una ruta al binario PE UKI como argumento. Si no se especifica, lee el binario de STDIN en su lugar.

OPCIONES

Se entienden las siguientes opciones:

--raw-description

Al mostrar el registro de eventos de TPM2, no intente decodificar los registros para proporcionar una cadena de descripción de evento amigable. En su lugar, muestre los datos de la carga útil binaria en formato escapado.

Añadido en la versión 255.

--pcr=

Especifica el número de PCR a utilizar. Puede especificarse varias veces para seleccionar varios PCR.

Esto es utilizado por lock-raw y lock-pe para seleccionar el PCR contra el que bloquear.

Si se usa con predict y make-policy, esto anulará qué PCR se incluirán en la predicción y la política. Si no se especifica, por defecto son los PCR 0-5, 7, 11-15. Tenga en cuenta que estos comandos no incluirán ningún PCR en la predicción/política (incluso si se especifica explícitamente) si hay mediciones en el registro de eventos que no coinciden con el valor actual del PCR, o hay mediciones no reconocidas en el registro de eventos, o los componentes definen mediciones no vistas en el registro de eventos.

Añadido en la versión 255.

--nv-index=

Especifica el índice NV en el que almacenar la política. Respetado por make-policy. Si no se especifica, el comando elegirá automáticamente un índice NV libre.

Añadido en la versión 255.

--components=

Toma una ruta para leer archivos *.pcrlock y *.pcrlock.d/*.pcrlock. Se puede usar varias veces para especificar varios directorios de este tipo. Si no se especifica, por defecto es /etc/pcrlock.d/, /run/pcrlock.d/, /var/lib/pcrlock.d/, /usr/local/lib/pcrlock.d/, /usr/lib/pcrlock.d/.

Añadido en la versión 255.

--location=

Toma una cadena o un par de cadenas separadas por dos puntos. Configura hasta qué punto en la lista ordenada de componentes definidos para analizar/predecir PCR. Típicamente, la herramienta systemd-pcrlock se invoca desde un sistema completamente arrancado después del arranque y antes del apagado. Esto significa que varios componentes que están definidos para el apagado aún no se han medido y no deben buscarse. Esta opción permite restringir qué componentes se consideran para el análisis (teniendo en cuenta solo los componentes anteriores a algún punto, ignorando los componentes posteriores a ellos). La cadena esperada se ordena frente a los nombres de archivo de los componentes definidos. Cualquier componente con un nombre lexicográficamente posterior se ignora. Esta lógica se aplica a los verbos log, predict y make-policy. Si se especifica un par de cadenas separadas por dos puntos, seleccionan qué fases del arranque incluir en la predicción/política. La primera cadena define dónde se realizará la primera predicción, y la segunda cadena define dónde se realizará la última predicción. Todas estas predicciones se combinan en un conjunto.

Si se usa con list-components, el rango de ubicación seleccionado se resaltará en la lista de componentes.

Por defecto es ""760-:940-"", lo que significa que las políticas generadas por defecto cubrirán básicamente todo el tiempo de ejecución del espacio de usuario del sistema operativo, desde el initrd (ya que "760-" sigue de cerca a 750-enter-initrd.pcrlock) hasta (e incluyendo) el tiempo de ejecución principal del sistema (ya que "940-" es seguido de cerca por 950-shutdown.pcrlock). Consulte systemd.pcrlock(5) para obtener una lista completa de componentes conocidos, que ilustran dónde se ubica este rango por defecto.

Añadido en la versión 255.

--recovery-pin=

Toma uno de "hide", "show" o "query". Por defecto es "hide". Respetado por make-policy. Si es "query", se le pedirá al usuario un PIN para desbloquear

NAME

systemd-pcrlock-firmware-code.service, systemd-pcrlock-firmware-code - obtain PCR values from firmware

SYNOPSIS

systemd-pcrlock-firmware-code --machine-id=ID --tpm2-device=DEVICE --nv-index=INDEX --pin=PIN

systemd-pcrlock-firmware-code --machine-id=ID --tpm2-device=DEVICE --nv-index=INDEX --pin=PIN --pin-digest=PIN_DIGEST

systemd-pcrlock-firmware-code --machine-id=ID --tpm2-device=DEVICE --nv-index=INDEX --hide

systemd-pcrlock-firmware-code --machine-id=ID --tpm2-device=DEVICE --nv-index=INDEX --show

systemd-pcrlock-firmware-code --machine-id=ID --tpm2-device=DEVICE --nv-index=INDEX --make-policy [ --force ] [ --entry-token=TOKEN ]

systemd-pcrlock-firmware-code --machine-id=ID --tpm2-device=DEVICE --nv-index=INDEX --lock-policy [ --pin=PIN ] [ --pcrlock=PATH ] [ --policy=PATH ]

systemd-pcrlock-firmware-code --machine-id=ID --tpm2-device=DEVICE --nv-index=INDEX --unlock-policy --pin=PIN

systemd-pcrlock-firmware-code --machine-id=ID --tpm2-device=DEVICE --nv-index=INDEX --is-supported [ --quiet ]

systemd-pcrlock-firmware-code --version

systemd-pcrlock-firmware-code --help

DESCRIPTION

The systemd-pcrlock-firmware-code command is used to obtain a set of PCR values from the system's firmware and store them in a TPM2 NV index. This is useful for ensuring that the system's firmware hasn't been tampered with, as any changes to the firmware will result in different PCR values.

The command supports several operations, including:

  • PIN: A PIN used to protect the TPM2 NV index. If no policy was created before, this PIN is used to protect the newly allocated NV index. If a policy has been created before, the PIN is used to unlock write access to the NV index. If either "hide" or "show" is used, a PIN is automatically generated and displayed on screen (only in case of "show"). Regardless if user supplied or automatically generated, it is stored in encrypted form in the policy metadata file. The recovery PIN may be used to regain write access to an NV index in case the access policy became out of date.
  • PCK LOCK: Takes a file system path as an argument. If specified, configures where to write the generated pcrlock data to. Honoured by the various lock-* commands. If not specified, a default path is generally used.
  • POLICY: Takes a file system path as an argument. If specified, configures where to write pcrlock policy metadata to. If not specified, defaults to /var/lib/systemd/pcrlock.json.
  • FORCE: If specified with make-policy, the predicted policy will be written to the NV index even if it is detected to be the same as the previously stored one.
  • ENTRY TOKEN: Sets the boot entry token to use for the file name for the pcrlock policy credential in the EFI System Partition or XBOOTLDR partition. See the bootctl(1) option of the same regarding expected values. This switch has an effect on the make-policy command only.
  • QUIET: If specified suppresses output when invoked for is-supported.
  • JSON: Shows output formatted as JSON. Expects one of "short" (for the shortest possible output without any redundant whitespace or line breaks), "pretty" (for a pretty version of the same, with indentation and line breaks) or "off" (to turn off JSON output, the default).

Added in version 255.

--json=MODE
Shows output formatted as JSON. Expects one of "short" (for the shortest possible output without any redundant whitespace or line breaks), "pretty" (for a pretty version of the same, with indentation and line breaks) or "off" (to turn off JSON output, the default).
--no-pager
Do not pipe output into a pager.
-h, --help
Print a short help text and exit.
--version
Print a short version string and exit.

EXIT STATUS

On success, 0 is returned, a non-zero failure code otherwise.
