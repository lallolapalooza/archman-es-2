SYSTEMD-RUN(1) systemd-run SYSTEMD-RUN(1)

NOMBRE

systemd-run - Ejecutar programas en unidades de ámbito transitorio, unidades de servicio o unidades de servicio activadas por ruta, socket o temporizador

SINOPSIS

systemd-run [OPCIONES...] COMANDO [ARGUMENTOS...]

systemd-run [OPCIONES...] [OPCIONES_RUTA ...] {COMANDO [ARGUMENTOS...]}

systemd-run [OPCIONES...] [OPCIONES_SOCKET ...] {COMANDO [ARGUMENTOS...]}

systemd-run [OPCIONES...] [OPCIONES_TEMPORIZADOR ...] {COMANDO [ARGUMENTOS...]}

DESCRIPCIÓN

systemd-run puede usarse para crear e iniciar una unidad .service o .scope transitoria y ejecutar el COMANDO especificado en ella. También puede usarse para crear e iniciar una unidad .path, .socket o .timer transitoria, que activa una unidad .service cuando se dispara.

Si se ejecuta un comando como una unidad de servicio transitoria, será iniciada y gestionada por el gestor de servicios como cualquier otro servicio, y por lo tanto aparecerá en la salida de systemctl list-units como cualquier otra unidad. Se ejecutará en un entorno de ejecución limpio y separado, con el gestor de servicios como su proceso padre. En este modo, systemd-run iniciará el servicio asíncronamente en segundo plano y regresará después de que el comando haya comenzado su ejecución (a menos que se especifiquen --no-block, --wait, --pipe o --pty, ver abajo).

Si se ejecuta un comando como una unidad de ámbito transitorio, será ejecutado por systemd-run mismo como proceso padre y, por lo tanto, heredará el entorno de ejecución del llamador. Sin embargo, los procesos del comando son gestionados por el gestor de servicios de manera similar a los servicios normales y aparecerán en la salida de systemctl list-units. La ejecución en este caso es síncrona y regresará solo cuando el comando finalice. Este modo se habilita mediante el interruptor --scope (ver abajo).

Si se ejecuta un comando con opciones de ruta, socket o temporizador como --on-calendar= (ver abajo), se crea una unidad de ruta, socket o temporizador transitoria junto con la unidad de servicio para el comando especificado. Solo la unidad de ruta, socket o temporizador transitoria se inicia inmediatamente; la unidad de servicio transitoria será activada por la unidad de ruta, socket o temporizador. Si se especifica la opción --unit=, se puede omitir el COMANDO. En este caso, systemd-run crea solo una unidad .path, .socket o .timer que activa la unidad especificada.

Por defecto, los servicios creados con systemd-run son de tipo simple, ver la descripción de Type= en systemd.service(5) para más detalles. Tenga en cuenta que cuando se utiliza este tipo, el gestor de servicios (y por lo tanto el comando systemd-run) considera que el inicio del servicio es exitoso tan pronto como la llamada fork() para el proceso principal del servicio ha tenido éxito, es decir, antes de que se invoque execve(), y por lo tanto, incluso si el comando especificado no puede iniciarse. Considere usar el tipo de servicio exec (es decir, --property=Type=exec) para asegurar que systemd-run regrese exitosamente solo si la línea de comandos especificada ha sido iniciada exitosamente.

Después de que systemd-run pase el comando al gestor de servicios, el gestor realiza la expansión de variables. Esto significa que los signos de dólar ("$") que no deben expandirse deben escaparse como "$$". La expansión también se puede deshabilitar usando --expand-environment=no.

OPCIONES

Se entienden las siguientes opciones:

--scope

Crea una unidad .scope transitoria en lugar de la unidad .service transitoria predeterminada (ver arriba).

Añadida en la versión 206.

--unit=, -u

Usa este nombre de unidad en lugar de uno generado automáticamente.

Añadida en la versión 206.

--property=, -p

Establece una propiedad en la unidad de ámbito o servicio que se crea. Esta opción toma una asignación en el mismo formato que el comando set-property de systemctl(1).

Añadida en la versión 211.

--description=

Proporciona una descripción para la unidad de servicio, ámbito, ruta, socket o temporizador. Si no se especifica, el propio comando se usará como descripción. Ver Description= en systemd.unit(5).

Añadida en la versión 206.

--slice=

Hace que la nueva unidad .service o .scope forme parte de la unidad slice especificada, en lugar de system.slice (cuando se ejecuta en modo --system) o la unidad slice raíz (cuando se ejecuta en modo --user).

Añadida en la versión 206.

--slice-inherit

Hace que la nueva unidad .service o .scope forme parte de la unidad slice en la que se invocó systemd-run. Esta opción puede combinarse con --slice=, en cuyo caso la unidad slice especificada a través de --slice= se colocará dentro de la unidad slice en la que se invoca el comando systemd-run.

Ejemplo: considere que se invoca systemd-run en la unidad slice foo.slice, y el argumento --slice= es bar. La unidad se colocará entonces bajo foo-bar.slice.

Añadida en la versión 246.

--expand-environment=BOOL

Expande variables de entorno en los argumentos del comando. Si se habilita (por defecto), las variables de entorno especificadas como "${VARIABLE}" se expandirán de la misma manera que en los comandos especificados mediante ExecStart= en las unidades. Con --scope, esta expansión la realiza el propio systemd-run, y en otros casos el gestor de servicios que inicia el comando. Tenga en cuenta que esto es similar, pero no idéntico, a la expansión de variables en bash(1) y otros shells.

Ver systemd.service(5) para una descripción de la expansión de variables. Deshabilitar la expansión de variables es útil si el comando especificado incluye o puede incluir un signo "$".

Añadida en la versión 254.

-r, --remain-after-exit

Después de que el proceso del servicio haya terminado, mantén el servicio activo hasta que se detenga explícitamente. Esto es útil para recopilar información de tiempo de ejecución sobre el servicio después de que haya finalizado. Ver también RemainAfterExit= en systemd.service(5).

Añadida en la versión 207.

--send-sighup

Al terminar la unidad de ámbito o servicio, envía una señal SIGHUP inmediatamente después de SIGTERM. Esto es útil para indicar a los shells y procesos similares a shells que la conexión se ha cortado. Ver también SendSIGHUP= en systemd.kill(5).

Añadida en la versión 207.

--service-type=

Establece el tipo de servicio. Ver también Type= en systemd.service(5). Esta opción no tiene efecto en conjunción con --scope. Por defecto es simple.

Añadida en la versión 211.

--uid=, --gid=

Ejecuta el proceso del servicio bajo el usuario y grupo UNIX especificados. Ver también User= y Group= en systemd.exec(5).

Añadida en la versión 211.

--nice=

Ejecuta el proceso del servicio con el nivel de nice especificado. Ver también Nice= en systemd.exec(5).

Añadida en la versión 211.

--working-directory=

Ejecuta el proceso del servicio con el directorio de trabajo especificado. Ver también WorkingDirectory= en systemd.exec(5).

Añadida en la versión 240.

--same-dir, -d

Similar a --working-directory=, pero usa el directorio de trabajo actual del llamador para la ejecución del servicio.

Añadida en la versión 240.

-E NOMBRE[=VALOR], --setenv=NOMBRE[=VALOR]

Ejecuta el proceso del servicio con la variable de entorno especificada establecida. Este parámetro se puede usar varias veces para establecer múltiples variables. Cuando se omite "=" y VALOR, se usará el valor de la variable con el mismo nombre en el entorno del programa.

Ver también Environment= en systemd.exec(5).

Añadida en la versión 211.

--pty, -t

>Al invocar el comando, el servicio transitorio conecta su entrada, salida y error estándar a la terminal en la que se invoca systemd-run, a través de un dispositivo pseudo TTY. Esto permite ejecutar programas que esperan entrada/salida interactiva del usuario como servicios, como los shells de comandos interactivos.

Esta opción hará que systemd-run espere de forma síncrona a que el servicio transitorio termine, de forma similar a especificar --wait. Si se especifica junto con --wait, systemd-run no saldrá al desconectarse manualmente del dispositivo pseudo TTY.

Tenga en cuenta que el comando shell de machinectl(1) suele ser una mejor alternativa para solicitar una nueva sesión de inicio de sesión interactiva en el host local o en un contenedor local.

Consulte a continuación los detalles sobre cómo se combina este modificador con --pipe.

Añadido en la versión 219.

--pty-late, -T

Al igual que --pty, pero la comunicación PTY solo comienza una vez que se completa el inicio de la unidad. Esto significa efectivamente que la entrada PTY durante ExecStartPre= de un servicio no está disponible al usar --pty-late, mientras que está disponible al usar --pty, para la mayoría de los tipos de servicio. Sin embargo, si se usa esta opción, el acceso al TTY invocador está disponible para consultas de contraseña (ver --no-ask-password a continuación) durante el inicio de la unidad.

Añadido en la versión 258.

--pipe, -P

Si se especifica, la entrada, salida y error estándar del servicio transitorio se heredan del propio comando systemd-run. Esto permite que systemd-run se utilice dentro de tuberías de shell.

Tenga en cuenta que este modo no es adecuado para shells de comandos interactivos y similares, ya que el proceso del servicio no se convertirá en un controlador TTY cuando se invoque en una terminal. Utilice --pty en su lugar en ese caso.

Cuando se utilizan --pipe y --pty en combinación, se determina y se utiliza automáticamente la opción más apropiada. Específicamente, cuando se invoca con la entrada, salida y error estándar conectados a un TTY, se utiliza --pty y, de lo contrario, --pipe.

Esta opción hará que systemd-run espere de forma síncrona a que el servicio transitorio termine, de forma similar a especificar --wait.

Cuando se utiliza esta opción, los descriptores de archivo originales que recibe systemd-run se pasan a los procesos del servicio tal cual. Si el servicio se ejecuta con privilegios diferentes a los de systemd-run, esto significa que el servicio podría no poder reabrir los descriptores de archivo pasados, debido a las restricciones normales de acceso a descriptores de archivo. Si el proceso invocado es un script de shell que utiliza la construcción echo "hello" >/dev/stderr para escribir mensajes en stderr, esto podría causar problemas, ya que esto solo funciona si stderr se puede reabrir. Para mitigar esto, utilice en su lugar la construcción echo "hello" >&2, que es mayormente equivalente y evita esta dificultad.

Añadido en la versión 235.

--shell, -S

Un atajo para "--pty --same-dir --wait --collect --service-type=exec $SHELL", es decir, solicita un shell interactivo en el directorio de trabajo actual, ejecutándose en contexto de servicio, accesible con un solo modificador.

Añadido en la versión 240.

--quiet, -q

Suprime la salida informativa adicional mientras se ejecuta. Esto es particularmente útil en combinación con --pty, ya que suprime el mensaje inicial que explica cómo terminar la conexión TTY.

Añadido en la versión 219.

-v, --verbose

Muestra la salida del registro de la unidad mientras se ejecuta.

Añadido en la versión 258.

--on-active=, --on-boot=, --on-startup=, --on-unit-active=, --on-unit-inactive=

Define un temporizador monótono relativo a diferentes puntos de inicio para iniciar el comando especificado. Consulte OnActiveSec=, OnBootSec=, OnStartupSec=, OnUnitActiveSec= y OnUnitInactiveSec= en systemd.timer(5) para obtener detalles. Estas opciones son atajos para --timer-property= con las propiedades relevantes. Estas opciones no se pueden combinar con --scope o --pty.

Añadido en la versión 218.

--on-calendar=

Define un temporizador de calendario para iniciar el comando especificado. Consulte OnCalendar= en systemd.timer(5). Esta opción es un atajo para --timer-property=OnCalendar=. Esta opción no se puede combinar con --scope o --pty.

Añadido en la versión 218.

--on-clock-change, --on-timezone-change

Define un desencadenante basado en saltos del reloj del sistema o cambios de zona horaria para iniciar el comando especificado. Consulte OnClockChange= y OnTimezoneChange= en systemd.timer(5). Estas opciones son atajos para --timer-property=OnClockChange=yes y --timer-property=OnTimezoneChange=yes. Estas opciones no se pueden combinar con --scope o --pty.

Añadido en la versión 242.

--path-property=, --socket-property=, --timer-property=

Establece una propiedad en la unidad de ruta, socket o temporizador que se crea. Esta opción es similar a --property=, pero se aplica a la unidad transitoria de ruta, socket o temporizador creada en lugar de a la unidad de servicio transitoria creada. Esta opción toma una asignación en el mismo formato que el comando set-property de systemctl(1). Estas opciones no se pueden combinar con --scope o --pty.

Añadido en la versión 218.

--no-block

No espere síncronamente a que finalice la operación de inicio de la unidad. Si no se especifica esta opción, la solicitud de inicio para la unidad transitoria se verificará, se pondrá en cola y systemd-run esperará hasta que se complete el inicio de la unidad. Al pasar este argumento, solo se verifica y se pone en cola. Esta opción no se puede combinar con --wait.

Añadido en la versión 220.

--wait

Espere de forma síncrona a que termine el servicio transitorio. Si se especifica esta opción, se verifica, se pone en cola y se espera la solicitud de inicio de la unidad transitoria. Posteriormente, se supervisa la unidad invocada y se espera hasta que se desactive de nuevo (lo más probable es que porque el comando especificado ha finalizado). Al salir, se muestra información concisa sobre el tiempo de ejecución de la unidad, incluido el tiempo total de ejecución (así como datos de contabilidad de CPU, memoria, E/S e IP, si están habilitadas las configuraciones de contabilidad de cgroup correspondientes) y el código de salida y el estado del proceso principal. Esta salida se puede suprimir con --quiet. Esta opción no se puede combinar con --no-block, --scope ni con las diversas opciones de ruta, socket o temporizador.

Añadido en la versión 232.

-G, --collect

Descarga la unidad transitoria después de que haya completado, incluso si falló. Normalmente, sin esta opción, todas las unidades que se ejecutaron y fallaron se mantienen en memoria hasta que el usuario restablece explícitamente su estado de fallo con systemctl reset-failed o un comando equivalente. Por otro lado, las unidades que se ejecutaron correctamente se descargan inmediatamente. Si se activa esta opción, la "recolección de basura" de unidades es más agresiva, y descarga las unidades independientemente de si salieron con éxito o fallaron. Esta opción es un atajo para --property=CollectMode=inactive-or-failed, consulte la explicación de CollectMode= en systemd.unit(5) para obtener más información.

Añadido en la versión 236.

--job-mode=MODE

Al poner en cola un nuevo trabajo, esta opción controla cómo tratar los trabajos ya en cola.

La opción toma los mismos valores de modo que la opción --job-mode= de systemctl(1). El modo de trabajo predeterminado es "fail".

Ejecutar --job-mode=help muestra una lista de los modos de trabajo disponibles.

Añadido en la versión 258.

--ignore-failure

Por defecto, si el comando especificado falla, la unidad invocada se marcará como fallida (aunque aún puede descargarse, consulte --collect=, más arriba), y esto se informará en los registros. Si se especifica este modificador, esto se suprime y cualquier estado/código de salida no exitoso del comando se trata como un éxito.

Añadido en la versión 256.

--background=COLOR

Cambia el color de fondo de la terminal al color ANSI especificado mientras dure la sesión. El color especificado debe ser un color de fondo SGR ANSI X3.64, es decir, cadenas como "40", "41", ..., "47", "48;2;...", "48;5;...". Consulte ANSI Escape Code (Wikipedia)[1] para obtener detalles.

Añadido en la versión 256.

--user

Comuníquese con el administrador de servicios del usuario que llama, en lugar del administrador de servicios del sistema.

--system

Comuníquese con el administrador de servicios del sistema. Este es el valor predeterminado implícito.

-H, --host=

Ejecute la operación de forma remota. Especifique un nombre de host, o un nombre de usuario y un nombre de host separados por "@", para conectarse. El nombre de host puede ir opcionalmente seguido de un puerto en el que escucha ssh, separado por ":", y luego un nombre de contenedor, separado por "/", que se conecta directamente a un contenedor específico en el host especificado. Esto utilizará SSH para comunicarse con la instancia remota del administrador de máquinas. Los nombres de contenedores se pueden enumerar con machinectl -H HOST. Coloque las direcciones IPv6 entre corchetes.

-M, --machine=

Ejecute la operación en un contenedor local. Especifique un nombre de contenedor para conectarse, opcionalmente prefijado por un nombre de usuario para conectarse y un carácter separador "@". Si se utiliza la cadena especial ".host" en lugar del nombre del contenedor, se establece una conexión con el sistema local (lo que es útil para conectarse al bus de usuario de un usuario específico: "--user --machine=lennart@.host"). Si no se utiliza la sintaxis "@", la conexión se realiza como usuario root. Si se utiliza la sintaxis "@", se puede omitir el lado izquierdo o el derecho (pero no ambos) en cuyo caso se implican el nombre de usuario local y ".host".

-C, --capsule=

Ejecute la operación en una cápsula. Especifique un nombre de cápsula para conectarse. Consulte capsule@.service(5) para obtener detalles sobre las cápsulas.

Añadido en la versión 256.

--no-ask-password

No solicite al usuario autenticación para operaciones privilegiadas.

-h, --help

Imprime un texto de ayuda corto y sale.

--version

NAME

systemd-run

run a systemd service or scope unit synchronously or asynchronously

SYNOPSIS

systemd-run [OPTIONS...] [COMMAND [ARG]... | --scope]

systemd-run --user [OPTIONS...] [COMMAND [ARG]... | --scope]

systemd-run --property=PROPERTY --value=VALUE ... [COMMAND [ARG]...]

systemd-run --load-property-from-path=FILE ... [COMMAND [ARG]...]

systemd-run --help

DESCRIPTION

systemd-run may be used to run an arbitrary system command synchronously or asynchronously as a systemd unit. If no command is given, an interactive shell is started. If --scope is passed, a scope unit is created instead of a service unit. If --user is passed, the units are created in the user systemd instance instead of the system instance.

By default, the command is run as a transient service. It is assigned a unit name like run-<ID>.service. If --scope is used, a scope unit is created, like run-<ID>.scope.

If the command is started successfully, systemd-run will either exit immediately (default), or wait for the started unit to terminate (using --wait), or until a specified time (using --on-active=, --on-boot-ticks=, etc.).

The command line arguments of the executed process are the same as the arguments passed to systemd-run after the first non-option argument. Special care must be taken if the executed command is a shell; in that case, the command line arguments are passed directly to the shell, and shell expansion might occur unexpectedly. Use quotes around arguments or use -c with shells like sh or bash.

Options that configure the unit's properties (like -p, --property=, --load-property-from-path=) may be specified multiple times. If the command line contains options that are not recognized by systemd-run, they are assumed to be options for the command being executed, and are passed along.

Unless --scope is used, the command is executed within a service unit. Otherwise, it's executed within a scope unit. Scope units are primarily for grouping existing processes, while service units are for managing daemons and other processes that systemd should control.

The following options are available:

OPTIONS

The following options are understood:

-., --milliseconds=TIME
Equivalent to --property=OperationTimeoutSec=TIME. Sets the timeout for the operation itself.
-A, --asynchronous
Exit immediately after the unit has been started. This is the default.
-t, --tty
Allocate a pseudo-TTY for the process, and connect its standard input, output, and error streams to the calling TTY. This is useful for interactive programs. This is equivalent to setting systemd.service(5) TTYPath= to the calling TTY.
-p, --property=PROPERTY
Sets a unit property. The property name is specified without the "<UnitType>" prefix. For example, to set CPUQuota= use -p CPUQuota=. This option may be specified multiple times.
-q, --quiet
Suppresses all output, including errors.
-u, --user
Run in user mode. Create units in the user systemd instance.
-e, --expand-environment
Enable expansion of environment variables like ${VAR} or $VAR by the systemd manager. This is enabled by default. See --expand-environment=no.
-E, --set-environment=STRING
Adds a single environment variable assignment STRING to the unit's execution environment. The format is VAR=VALUE.
-X, --run-in-shell
Execute the command in a shell. This is equivalent to running /bin/sh -c '...'. Note that this is different from -t, which connects the process to the TTY but does not necessarily run it in a shell.
-D, --remove-argument
Remove arguments that match the specified pattern from the command line of the executed process. This is useful if systemd-run should not pass certain arguments to the executed command.
-I, --invocation-id
Print the invocation ID of the started unit. This is a unique identifier for this specific invocation of the command.
-w, --wait
Wait for the started unit to terminate and print its exit code. If the unit is a service, the exit code of the service process is returned. If it is a scope, the exit code is 0 if the scope has terminated cleanly, and non-zero otherwise. See also EXIT STATUS.
--scope
Create a scope unit instead of a service unit. This is useful for grouping existing processes or for running commands that are not intended to be long-running daemons.
--slice=SLICE
Assign the unit to the specified slice instead of the default.
--status-output=MODE
Control status output. Expects one of "short" (only print unit name, default), "full" (print full status information), or "off" (suppress status output).
--json=MODE
Shows output formatted as JSON. Expects one of "short" (for the shortest possible output without any redundant whitespace or line breaks), "pretty" (for a pretty version of the same, with indentation and line breaks) or "off" (to turn off JSON output, the default).
--no-pager
Do not pipe output into a pager. This currently only applies to --help. (The pager is not started during normal operation.)

Added in version 258.

All command line arguments after the first non-option argument become part of the command line of the launched process.

EXIT STATUS

On success, 0 is returned. If systemd-run failed to start the service, a non-zero return value will be returned. If systemd-run waits for the service to terminate, the return value will be propagated from the service. 0 will be returned on success, including all the cases where systemd considers a service to have exited cleanly, see the discussion of SuccessExitStatus= in systemd.service(5).

EXAMPLES

Example 1. Logging environment variables provided by systemd to services

# systemd-run env
Running as unit: run-19945.service
# journalctl -u run-19945.service
Sep 08 07:37:21 bupkis systemd[1]: Starting /usr/bin/env...
Sep 08 07:37:21 bupkis systemd[1]: Started /usr/bin/env.
Sep 08 07:37:21 bupkis env[19948]: PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin
Sep 08 07:37:21 bupkis env[19948]: LANG=en_US.UTF-8
Sep 08 07:37:21 bupkis env[19948]: BOOT_IMAGE=/vmlinuz-3.11.0-0.rc5.git6.2.fc20.x86_64

Example 2. Limiting resources available to a command

# systemd-run -p IOWeight=10 updatedb

This command invokes the updatedb(8) tool, but lowers the block I/O weight for it to 10. See systemd.resource-control(5) for more information on the IOWeight= property.

Example 3. Running commands at a specified time

The following command will touch a file after 30 seconds.

# date; systemd-run --on-active=30 --timer-property=AccuracySec=100ms /bin/touch /tmp/foo
Mon Dec  8 20:44:24 KST 2014
Running as unit: run-71.timer
Will run service as unit: run-71.service
# journalctl -b -u run-71.timer
-- Journal begins at Fri 2014-12-05 19:09:21 KST, ends at Mon 2014-12-08 20:44:54 KST. --
Dec 08 20:44:38 container systemd[1]: Starting /bin/touch /tmp/foo.
Dec 08 20:44:38 container systemd[1]: Started /bin/touch /tmp/foo.
# journalctl -b -u run-71.service
-- Journal begins at Fri 2014-12-05 19:09:21 KST, ends at Mon 2014-12-08 20:44:54 KST. --
Dec 08 20:44:48 container systemd[1]: Starting /bin/touch /tmp/foo...
Dec 08 20:44:48 container systemd[1]: Started /bin/touch /tmp/foo.

Example 4. Allowing access to the tty

The following command invokes bash(1) as a service passing its standard input, output and error to the calling TTY.

# systemd-run -t --send-sighup bash

Example 5. Start screen as a user service

$ systemd-run --scope --user screen
Running scope as unit run-r14b0047ab6df45bfb45e7786cc839e76.scope.
$ screen -ls
There is a screen on:
        492..laptop     (Detached)
1 Socket in /var/run/screen/S-fatima.

This starts the screen process as a child of the systemd --user process that was started by user@.service, in a scope unit. A systemd.scope(5) unit is used instead of a systemd.service(5) unit, because screen will exit when detaching from the terminal, and a service unit would be terminated. Running screen as a user unit has the advantage that it is not part of the session scope. If KillUserProcesses=yes is configured in logind.conf(5), the default, the session scope will be terminated when the user logs out of that session.

The user@.service is started automatically when the user first logs in, and stays around as long as at least one login session is open. After the user logs out of the last session, user@.service and all services underneath it are terminated. This behavior is the default, when "lingering" is not enabled for that user. Enabling lingering means that user@.service is started automatically during boot, even if the user is not logged in, and that the service is not terminated when the user logs out.

Enabling lingering allows the user to run processes without being logged in, for example to allow screen to persist after the user logs out, even if the session scope is terminated. In the default configuration, users can enable lingering for themselves:

$ loginctl enable-linger

Example 6. Variable expansion by the manager

$ systemd-run -t echo "<${INVOCATION_ID}>" '<${INVOCATION_ID}>'
      <> <5d0149bfa2c34b79bccb13074001eb20>

The first argument is expanded by the shell (double quotes), but the second one is not expanded by the shell (single quotes). echo(1) is called with ["/usr/bin/echo", "<>", "<${INVOCATION_ID}>"] as the argument array, and then systemd(1) generates ${INVOCATION_ID} and substitutes it in the command-line. This substitution could not be done on the client side, because the target ID that will be set for the service is not known before the call is made.

Example 7. Variable expansion and output redirection using a shell

Variable expansion by systemd(1) can be disabled with --expand-environment=no.

Disabling variable expansion can be useful if the command to execute contains dollar characters and escaping them would be inconvenient. For example, when a shell is used:

$ systemd-run --expand-environment=no -t bash \
      -c 'echo $SHELL $$ >/dev/stdout'
/bin/bash 12345

The last argument is passed verbatim to the bash(1) shell which is started by the service unit. The shell expands "$SHELL" to the path of the shell, and "$$" to its process number, and then those strings are passed to the echo built-in and printed to standard output (which, in this case, is connected to the calling terminal).

Example 8. Return value

$ systemd-run --user --wait true
$ systemd-run --user --wait -p SuccessExitStatus=11 bash -c 'exit 11'
$ systemd-run --user --wait -p SuccessExitStatus=SIGUSR1 --expand-environment=no \
      bash -c 'kill -SIGUSR1 $$'

Those three invocations will succeed, i.e. terminate with an exit code of 0.
