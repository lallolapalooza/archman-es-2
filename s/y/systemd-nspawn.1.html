NOMBRE

systemd-nspawn - Iniciar un comando o un SO en un contenedor ligero

SINOPSIS

systemd-nspawn [OPCIONES...] [COMANDO [ARGUMENTOS...]]

systemd-nspawn --boot [OPCIONES...] [ARGUMENTOS...]

DESCRIPCIÓN

systemd-nspawn se puede utilizar para ejecutar un comando o un SO en un contenedor ligero de espacios de nombres. En muchos aspectos es similar a chroot(1), pero más potente ya que virtualiza el árbol de directorios del sistema de archivos, así como el árbol de procesos, los diversos subsistemas IPC y los nombres de host y dominio.

systemd-nspawn puede invocarse sobre cualquier árbol de directorios que contenga un árbol de sistema operativo, utilizando la opción de línea de comandos --directory=. Al usar la opción --machine=, se busca automáticamente un árbol de SO en un par de ubicaciones, especialmente en /var/lib/machines/, el directorio sugerido para colocar las imágenes de contenedores de SO instaladas en el sistema.

A diferencia de chroot(1), systemd-nspawn puede utilizarse para arrancar sistemas operativos completos basados en Linux en un contenedor.

systemd-nspawn limita el acceso a varias interfaces del kernel dentro del contenedor a solo lectura, como /sys/, /proc/sys/, o /sys/fs/selinux/. Las interfaces de red del host y el reloj del sistema no pueden modificarse desde dentro del contenedor. No se pueden crear nodos de dispositivos. El sistema host no puede reiniciarse y no se pueden cargar módulos del kernel desde dentro del contenedor. *Esta zona de pruebas se puede evitar fácilmente desde dentro del contenedor si no se utilizan espacios de nombres de usuario*. Esto significa que el código no confiable siempre debe ejecutarse en un espacio de nombres de usuario, consulte la discusión de la opción --private-users= a continuación.

Utilice una herramienta como dnf(8), debootstrap(8), o pacman(8) para configurar un árbol de directorios de SO adecuado como jerarquía de sistema de archivos para los contenedores de systemd-nspawn. Consulte la sección Ejemplos a continuación para obtener detalles sobre la invocación adecuada de estos comandos.

Como verificación de seguridad, systemd-nspawn verificará la existencia de /usr/lib/os-release o /etc/os-release en el árbol del contenedor antes de arrancar un contenedor (consulte os-release(5)). Puede ser necesario agregar este archivo manualmente al árbol del contenedor si el SO del contenedor es demasiado antiguo para contener este archivo directamente.

systemd-nspawn puede invocarse directamente desde la línea de comandos interactiva o ejecutarse como un servicio del sistema en segundo plano. En este modo, cada instancia del contenedor se ejecuta como su propia instancia de servicio; se proporciona un archivo de unidad de plantilla predeterminado, systemd-nspawn@.service, para facilitar esto, tomando el nombre del contenedor como identificador de instancia. Tenga en cuenta que se aplican diferentes opciones predeterminadas cuando systemd-nspawn es invocado por el archivo de unidad de plantilla que interactivamente en la línea de comandos. La mayoría de las diferencias con los valores predeterminados son documentadas junto con las diversas opciones soportadas a continuación.

La herramienta machinectl(1) puede utilizarse para ejecutar una serie de operaciones en los contenedores. En particular, proporciona comandos fáciles de usar para ejecutar contenedores como servicios del sistema utilizando el archivo de unidad de plantilla systemd-nspawn@.service.

Junto con cada contenedor, puede existir un archivo de configuración con el sufijo .nspawn, que contiene configuraciones adicionales a aplicar al ejecutar el contenedor. Consulte systemd.nspawn(5) para obtener detalles. Los archivos de configuración anulan las opciones predeterminadas utilizadas por el archivo de unidad de plantilla systemd-nspawn@.service, lo que generalmente hace innecesario modificar este archivo de plantilla directamente.

Tenga en cuenta que systemd-nspawn montará sistemas de archivos privados para el contenedor en /dev/, /run/, y similares. Estos no serán visibles fuera del contenedor y su contenido se perderá cuando el contenedor salga.

Tenga en cuenta que ejecutar dos contenedores systemd-nspawn desde el mismo árbol de directorios no hará que los procesos en ellos se vean entre sí. La separación del espacio de nombres PID de los dos contenedores es completa y los contenedores compartirán muy pocos objetos en tiempo de ejecución, excepto el sistema de archivos subyacente. En su lugar, utilice los comandos login o shell de machinectl(1) para solicitar una sesión de inicio de sesión adicional en un contenedor en ejecución.

systemd-nspawn implementa la especificación de la **Interfaz de Contenedor**[1].

Mientras se ejecutan, los contenedores invocados con systemd-nspawn se registran con el servicio systemd-machined(8) que realiza un seguimiento de los contenedores en ejecución y proporciona interfaces de programación para interactuar con ellos.

OPERACIÓN SIN PRIVILEGIOS

systemd-nspawn puede invocarse con o sin privilegios. La funcionalidad completa actualmente solo está disponible cuando se invoca con privilegios. Cuando se invoca sin privilegios, se aplican varias limitaciones, que incluyen, entre otras:

•Solo se admiten contenedores basados en imágenes de disco (es decir, --image=). Los basados en directorios (es decir, --directory=) no son compatibles.
•El registro de máquinas mediante --machine= no es compatible.
•Solo se admiten los modos de red --private-network y --network-veth.

Al ejecutarse en modo sin privilegios, algunas funcionalidades necesarias se proporcionan a través de systemd-mountfsd.service(8) y systemd-nsresourced.service(8).

OPCIONES

Si se especifica la opción --boot, los argumentos se utilizan como argumentos para el programa init. De lo contrario, COMANDO especifica el programa a iniciar en el contenedor y los argumentos restantes se utilizan como argumentos para este programa. Si no se usa --boot y no se especifican argumentos, se inicia un shell en el contenedor.

Se entienden las siguientes opciones:

-q, --quiet

Desactiva cualquier salida de estado de la propia herramienta. Cuando se utiliza este interruptor, la única salida de nspawn será la salida de la consola del propio SO del contenedor.

--settings=MODO

Controla si systemd-nspawn debe buscar y utilizar configuraciones adicionales por contenedor de los archivos .nspawn. Acepta un valor booleano o los valores especiales override o trusted.

Si está habilitado (el valor predeterminado), se busca un archivo de configuración con el nombre de la máquina (como se especifica con el ajuste --machine=, o derivado del nombre del directorio o archivo de imagen) con el sufijo .nspawn en /etc/systemd/nspawn/ y /run/systemd/nspawn/. Si se encuentra allí, se leen y utilizan sus configuraciones. Si no se encuentra allí, se busca posteriormente en el mismo directorio que el archivo de imagen o en el padre inmediato del directorio raíz del contenedor. En este caso, si se encuentra el archivo, sus configuraciones también se leerán y utilizarán, pero se ignorarán las configuraciones potencialmente inseguras. Tenga en cuenta que en ambos casos, las configuraciones en la línea de comandos tienen prioridad sobre las configuraciones correspondientes de los archivos .nspawn cargados, si ambos se especifican. Las configuraciones inseguras se consideran todas las configuraciones que elevan los privilegios del contenedor o conceden acceso a recursos adicionales como archivos o directorios del host. Para obtener detalles sobre el formato y el contenido de los archivos .nspawn, consulte systemd.nspawn(5).

Si esta opción se establece en override, el archivo se busca, se lee y se utiliza de la misma manera, sin embargo, el orden de precedencia se invierte: las configuraciones leídas del archivo .nspawn tendrán prioridad sobre las opciones de línea de comandos correspondientes, si ambas se especifican.

Si esta opción se establece en trusted, el archivo se busca, se lee y se utiliza de la misma manera, pero independientemente de si se encuentra en /etc/systemd/nspawn/, /run/systemd/nspawn/ o junto al archivo de imagen o al directorio raíz del contenedor, todas las configuraciones tendrán efecto, sin embargo, los argumentos de la línea de comandos aún tendrán prioridad sobre las configuraciones correspondientes.

Si se deshabilita, no se lee ningún archivo .nspawn y no entran en vigor configuraciones distintas de las de la línea de comandos.

Opciones de imagen

-D, --directory=

Directorio a usar como raíz del sistema de archivos para el contenedor.

Si no se especifica ni --directory= ni --image=, el directorio se determina buscando un directorio con el mismo nombre que el nombre de la máquina especificado con --machine=. Consulte la sección "Archivos y Directorios" de machinectl(1) para conocer la ruta de búsqueda precisa.

En lugar de la ruta del directorio, se puede especificar un directorio versionado ".v/", consulte systemd.v(7) para más detalles.

Si no se especifican --directory=, --image= ni --machine=, se utilizará el directorio actual. No se puede especificar junto con --image=.

--template=

Directorio o subvolumen "btrfs" a utilizar como plantilla para el directorio raíz del contenedor. Si se especifica esto y el directorio raíz del contenedor (tal como está configurado por --directory=) aún no existe, se crea como una instantánea "btrfs" (si es compatible) o un directorio normal (de lo contrario) y se popula desde este árbol de plantillas. Idealmente, la ruta de la plantilla especificada se refiere a la raíz de un subvolumen "btrfs", en cuyo caso se toma una simple instantánea de copia en escritura, y la población del directorio raíz es instantánea. Si la ruta de la plantilla especificada no se refiere a la raíz de un subvolumen "btrfs" (o ni siquiera a un sistema de archivos "btrfs"), el árbol se copia (aunque posiblemente en un esquema de copia en escritura 'reflink' - si el sistema de archivos lo soporta), lo que puede llevar considerablemente más tiempo. Tenga en cuenta que la instantánea tomada es del directorio o subvolumen especificado, incluyendo todos los subdirectorios y subvolúmenes debajo de él, pero excluyendo cualquier submontaje. No se puede especificar junto con --image= o --ephemeral.

Tenga en cuenta que este modificador deja el nombre de host, el ID de la máquina y todas las demás configuraciones que podrían identificar la instancia sin modificar.

Añadido en la versión 219.

-x, --ephemeral

Si se especifica, el contenedor se ejecuta con una instantánea temporal de su sistema de archivos que se elimina inmediatamente cuando el contenedor termina. No se puede especificar junto con --template=.

Tenga en cuenta que este modificador deja el nombre de host, el ID de la máquina y todas las demás configuraciones que podrían identificar la instancia sin modificar. Tenga en cuenta que, al igual que con --template=, tomar la instantánea temporal es más eficiente en sistemas de archivos que admiten instantáneas de subvolúmenes o 'reflinks' de forma nativa ("btrfs" o el nuevo "xfs") que en sistemas de archivos más tradicionales que no lo hacen ("ext4"). Tenga en cuenta que la instantánea tomada es del directorio o subvolumen especificado, incluyendo todos los subdirectorios y subvolúmenes debajo de él, pero excluyendo cualquier submontaje.

Con esta opción, no se conservan las modificaciones de la imagen del contenedor. Utilice --volatile= (descrito a continuación) para otros mecanismos que restringen la persistencia de las imágenes de contenedor durante la ejecución.

Añadido en la versión 219.

-i, --image=

Imagen de disco desde la cual montar la raíz del sistema de archivos para el contenedor. Toma una ruta a un archivo regular o a un nodo de dispositivo de bloque. El archivo o dispositivo de bloque debe contener:
•Una tabla de particiones MBR con una sola partición de tipo 0x83 marcada como arrancable.
•Una tabla de particiones GUID (GPT) con una sola partición de tipo 0fc63daf-8483-4772-8e79-3d69d8477de4.
•Una tabla de particiones GUID (GPT) con una partición raíz marcada que se monta como directorio raíz del contenedor. Opcionalmente, las imágenes GPT pueden contener una partición de datos de servidor y/o de inicio que se montan en los lugares apropiados en el contenedor. Todas estas particiones deben identificarse mediante los tipos de partición definidos por la Especificación de Particiones Descubribles[2].
•Sin tabla de particiones, y un único sistema de archivos que abarca toda la imagen.

En imágenes GPT, si se descubre una partición del sistema EFI (ESP), se monta automáticamente en /efi (o /boot como respaldo) en caso de que exista un directorio con ese nombre y esté vacío.

Las particiones cifradas con LUKS se descifran automáticamente. Además, en imágenes GPT, se configuran particiones de hash de integridad de datos dm-verity si el hash raíz para ellas se especifica mediante la opción --root-hash=.

Las imágenes de un solo sistema de archivos (es decir, sistemas de archivos sin tabla de particiones envolvente) se pueden abrir usando dm-verity si los datos de integridad se pasan usando las opciones --root-hash= y --verity-data= (y opcionalmente --root-hash-sig=).

Cualquier otra partición, como particiones extranjeras o particiones de intercambio, no se monta. No se puede especificar junto con --directory=, --template=.

En lugar de la ruta de la imagen, se puede especificar un directorio versionado ".v/", consulte systemd.v(7) para más detalles.

Añadido en la versión 211.

--image-policy=policy

Toma una cadena de política de imagen como argumento, según systemd.image-policy(7). La política se aplica al operar sobre la imagen de disco especificada a través de --image=, ver arriba. Si no se especifica, el valor predeterminado es "root=verity+signed+encrypted+unprotected+absent:usr=verity+signed+encrypted+unprotected+absent:home=encrypted+unprotected+absent:srv=encrypted+unprotected+absent:esp=unprotected+absent:xbootldr=unprotected+absent:tmp=encrypted+unprotected+absent:var=encrypted+unprotected+absent", es decir, todos los sistemas de archivos reconocidos en la imagen se utilizan, pero no la partición de intercambio.

Añadido en la versión 254.

--oci-bundle=

Toma la ruta a un paquete de tiempo de ejecución OCI para invocar, según lo especificado en la Especificación de Tiempo de Ejecución OCI[3]. En este caso, no se carga ningún archivo .nspawn, y el directorio raíz y varias configuraciones se leen de los datos JSON del tiempo de ejecución OCI (pero los datos pasados en la línea de comandos tienen precedencia).

Añadido en la versión 242.

--read-only

Monta el sistema de archivos raíz del contenedor (y cualquier otro sistema de archivos contenido en la imagen del contenedor) como de solo lectura. Esto no tiene ningún efecto en montajes adicionales realizados con --bind=, --tmpfs= y opciones similares. Este modo se implica si el archivo o directorio de la imagen del contenedor está marcado como de solo lectura. También se implica si se utiliza --volatile=. En este caso, la imagen del contenedor en disco es estrictamente de solo lectura, mientras que los cambios están permitidos pero se guardan temporalmente en memoria. Para más detalles, véase a continuación.

--volatile, --volatile=MODE

Arranca el contenedor en modo volátil. Cuando no se pasa ningún parámetro de modo o cuando el modo se especifica como yes, se habilita el modo volátil completo. Esto significa que el directorio raíz se monta como una instancia "tmpfs" mayormente despoblada, y /usr/ del árbol del sistema operativo se monta en él en modo de solo lectura (el sistema arranca así con una imagen del sistema operativo de solo lectura, pero con estado y configuración prístinos, cualquier cambio se pierde al apagar). Cuando el parámetro de modo se especifica como state, el árbol del sistema operativo se monta de solo lectura, pero /var/ se monta como una instancia "tmpfs" escribible en él (el sistema arranca así con recursos y configuración del sistema operativo de solo lectura, pero con estado prístino, y cualquier cambio en este último se pierde al apagar). Cuando el parámetro de modo se especifica como overlay, el sistema de archivos raíz de solo lectura se combina con una instancia tmpfs escribible a través de "overlayfs", de modo que aparece como normalmente lo haría, pero cualquier cambio se aplica solo al sistema de archivos temporal y se pierde cuando el contenedor se termina. Cuando el parámetro de modo se especifica como no (el predeterminado), todo el árbol del sistema operativo se hace escribible (a menos que se especifique --read-only, ver arriba).

Tenga en cuenta que si se elige uno de los modos volátiles, su efecto se limita al sistema de archivos raíz (o /var/ en caso de state), y cualquier otro montaje colocado en la jerarquía no se ve afectado, independientemente de si se establecen automáticamente (por ejemplo, la partición del sistema EFI que podría montarse en /efi/ o /boot/) o explícitamente (por ejemplo, a través de una opción de línea de comandos adicional como --bind=, ver a continuación). Esto significa que, incluso si se utiliza --volatile=overlay, los cambios en /efi/ o /boot/ están prohibidos en caso de que exista dicha partición en la imagen del contenedor operada, e incluso si se utiliza --volatile=state, el archivo hipotético /etc/foobar es potencialmente escribible si se utiliza --bind=/etc/foobar para montarlo desde fuera del directorio /etc/ del contenedor de solo lectura.

La opción --ephemeral está estrechamente relacionada con esta configuración y proporciona un comportamiento similar al crear una copia temporal y efímera de toda la imagen del sistema operativo y ejecutarla. Para más detalles, véase arriba.

Las opciones --tmpfs= y --overlay= proporcionan una funcionalidad similar, pero solo para subdirectorios específicos de la imagen del sistema operativo. Para detalles, véase a continuación.

Esta opción proporciona una funcionalidad similar para los contenedores que el modificador de línea de comandos del kernel "systemd.volatile=" proporciona para los sistemas host. Consulte kernel-command-line(7) para detalles.

Tenga en cuenta que al configurar esta opción en yes o state, solo funcionará correctamente con sistemas operativos en el contenedor que puedan arrancar con solo /usr/ montado, y que puedan poblar automáticamente /var/ (y /etc/ en caso de "--volatile=yes"). Específicamente, esto significa que los sistemas operativos que siguen la división histórica de /bin/ y /lib/ (y directorios relacionados) de /usr/ (es decir, donde los primeros no son enlaces simbólicos a los segundos) no son compatibles con "--volatile=yes" como carga útil del contenedor. La opción overlay no requiere ninguna preparación particular en el sistema operativo, pero tenga en cuenta que el comportamiento de "overlayfs" difiere de los sistemas de archivos normales en varios aspectos, y por lo tanto, la compatibilidad es limitada.

Añadido en la versión 216.

--root-hash=

Toma un hash raíz de integridad de datos (dm-verity) especificado en hexadecimal. Esta opción habilita las comprobaciones de integridad de datos usando dm-verity, si la imagen utilizada contiene los datos de integridad apropiados (ver arriba). El hash especificado debe coincidir con el hash raíz de los datos de integridad, y generalmente tiene al menos 256 bits (y por lo tanto 64 caracteres hexadecimales) de longitud (en caso de SHA256, por ejemplo). Si esta opción no se especifica, pero el archivo de imagen contiene el atributo de archivo extendido "user.verity.roothash" (ver xattr(7)), entonces el hash raíz se lee del mismo, también como caracteres hexadecimales formateados. Si el atributo de archivo extendido no se encuentra (o no es compatible con el sistema de archivos subyacente), pero se encuentra un archivo con el sufijo .roothash junto al archivo de imagen, que de lo contrario tiene el mismo nombre (excepto si la imagen tiene el sufijo .raw, en cuyo caso el archivo hash raíz no debe tenerlo en su nombre), el hash raíz se lee de él y se utiliza automáticamente, también como caracteres hexadecimales formateados.

Tenga en cuenta que esto configura el hash raíz para el sistema de archivos raíz. Las imágenes de disco también pueden contener sistemas de archivos separados para la jerarquía /usr/, que también pueden estar protegidos por Verity. El hash raíz para esta protección puede configurarse a través del atributo de archivo extendido "user.verity.usrhash" o a través de un archivo .usrhash adyacente a la imagen de disco, siguiendo el mismo formato y lógica que para el hash raíz del sistema de archivos raíz descrito aquí. Tenga en cuenta que actualmente no hay un interruptor para configurar el hash raíz para /usr/ desde la línea de comandos.

Consulte también la opción RootHash= en systemd.exec(5).

Añadido en la versión 233.

--verity-data=

Toma la ruta a un archivo de integridad de datos (dm-verity). Esta opción habilita las comprobaciones de integridad de datos utilizando dm-verity, si se pasa un hash raíz y si la imagen utilizada no contiene los datos de integridad. Los datos de integridad deben coincidir con el hash raíz. Si esta opción no se especifica, pero se encuentra un archivo con el sufijo .verity junto al archivo de imagen, que de lo contrario tiene el mismo nombre (excepto si la imagen tiene el sufijo .raw, en cuyo caso el archivo de datos de verity no debe tenerlo en su nombre), los datos de verity se leen de él y se utilizan automáticamente.

Añadido en la versión 246.

--pivot-root=

Mueve el directorio especificado a / dentro del contenedor, y ya sea desmonta la raíz antigua del contenedor, o la mueve a otro directorio especificado. Toma uno de: un argumento de ruta (en cuyo caso la ruta especificada se moverá a / y la raíz antigua se desmontará); o un par separado por dos puntos de la nueva ruta raíz y el destino de la mudanza para la raíz antigua. La nueva ruta raíz se moverá a /, y la antigua / se moverá al otro directorio. Ambas rutas deben ser absolutas y se resuelven en el espacio de nombres del sistema de archivos del contenedor.

Esto es para contenedores que tienen varios directorios de arranque dentro de ellos; por ejemplo, varias implementaciones de OSTree[4]. Emula el comportamiento del cargador de arranque y el initrd que normalmente seleccionan qué directorio montar como raíz y en qué iniciar el PID 1 del contenedor.

Añadido en la versión 233.

Opciones de Ejecución

-a, --as-pid2

Invoca el shell o el programa especificado como proceso ID (PID) 2 en lugar de PID 1 (init). Por defecto, si no se usa esta opción ni --boot, el programa seleccionado se ejecuta como el proceso con PID 1, un modo solo adecuado para programas que son conscientes de la semántica especial que tiene el proceso con PID 1 en UNIX. Por ejemplo, necesita recolectar todos los procesos que se le reparentan y debe implementar el manejo de señales compatible con sysvinit (específicamente: necesita reiniciar en SIGINT, re-ejecutar en SIGTERM, recargar la configuración en SIGHUP, etc.). Con --as-pid2 se ejecuta un proceso init mínimo como PID 1 y el programa seleccionado se ejecuta como PID 2 (y por lo tanto no necesita implementar ninguna semántica especial). El proceso init mínimo recolectará procesos según sea necesario y reaccionará adecuadamente a las señales. Se recomienda usar este modo para invocar comandos arbitrarios en contenedores, a menos que hayan sido modificados para ejecutarse correctamente como PID 1. O en otras palabras: este interruptor debe usarse para casi todos los comandos, excepto cuando el comando se refiere a una implementación de init o shell, ya que estos generalmente son capaces de ejecutarse correctamente como PID 1. Esta opción no se puede combinar con --boot.

Añadido en la versión 229.

-b, --boot

Busca automáticamente un programa init y lo invoca como PID 1, en lugar de un shell o un programa proporcionado por el usuario. Si se usa esta opción, los argumentos especificados en la línea de comandos se usan como argumentos para el programa init. Esta opción no se puede combinar con --as-pid2.

La siguiente tabla explica los diferentes modos de invocación y la relación con --as-pid2 (ver arriba):

Tabla 1. Modo de Invocación

Interruptor Explicación
No se especifica ni --as-pid2 ni --boot Los parámetros pasados se interpretan como la línea de comandos, que se ejecuta como PID 1 en el contenedor.
Se especifica --as-pid2 Los parámetros pasados se interpretan como la línea de comandos, que se ejecuta como PID 2 en el contenedor. Se ejecuta un proceso init mínimo como PID 1.
Se especifica --boot Se busca automáticamente un programa init y se ejecuta como PID 1 en el contenedor. Los parámetros pasados se utilizan como parámetros de invocación para este proceso.

--chdir=

Opciones de Namespacio de Usuarios

--private-users=

Controla el namespacio de usuarios. Si está habilitado, el contenedor se ejecutará con su propio conjunto privado de IDs de usuario y grupo (UIDs y GIDs) de UNIX. Esto implica mapear los UIDs/GIDs privados utilizados en el contenedor (comenzando con el usuario root del contenedor 0 y hacia arriba) a un rango de UIDs/GIDs en el host que no se utilizan para otros fines (generalmente en el rango más allá del UID/GID 65536 del host). El parámetro puede especificarse de la siguiente manera:
1.Si se especifican uno o dos números separados por dos puntos, el namespacio de usuarios se activa. El primer parámetro especifica el primer UID/GID del host a asignar al contenedor, el segundo parámetro especifica el número de UIDs/GIDs del host a asignar al contenedor. Si se omite el segundo parámetro, se asignan 65536 UIDs/GIDs.
2.Si el parámetro es "yes", el namespacio de usuarios se activa. El rango de UIDs/GIDs a utilizar se determina automáticamente a partir de la propiedad de archivo del directorio raíz del árbol de directorios del contenedor. Para usar esta opción, asegúrese de preparar el árbol de directorios con anticipación y asegúrese de que todos los archivos y directorios en él sean propiedad de UIDs/GIDs en el rango que desea utilizar. Además, asegúrese de que los ACL de archivo utilizados hagan referencia exclusivamente a UIDs/GIDs en el rango apropiado. En este modo, el número de UIDs/GIDs asignados al contenedor es 65536, y el UID/GID propietario del directorio raíz debe ser un múltiplo de 65536.
3.El valor especial "pick" activa el namespacio de usuarios. En este caso, el rango de UIDs/GIDs se elige automáticamente. Como primer paso, se lee el UID/GID propietario del archivo del directorio raíz del árbol de directorios del contenedor, y se verifica que ningún otro contenedor lo esté utilizando actualmente. Si esta verificación es exitosa, se utiliza el rango de UIDs/GIDs determinado de esta manera, de forma similar al comportamiento si se especifica "yes". Si la verificación no es exitosa (y por lo tanto el rango de UIDs/GIDs indicado en el propietario del archivo del directorio raíz ya se está utilizando en otro lugar), se elige aleatoriamente un nuevo rango de UIDs/GIDs de 65536 UIDs/GIDs (actualmente no utilizado) entre los UIDs/GIDs del host de 524288 y 1878982656, siempre comenzando en un múltiplo de 65536 y, si es posible, hashado de forma consistente a partir del nombre de la máquina. Esta configuración implica --private-users-ownership=auto (ver más abajo), que posiblemente tenga el efecto de que los archivos y directorios en el árbol de directorios del contenedor sean propiedad de los usuarios apropiados del rango elegido. El uso de esta opción hace que el comportamiento del namespacio de usuarios sea completamente automático. Tenga en cuenta que la primera invocación de una imagen de contenedor previamente no utilizada podría resultar en la elección de un nuevo rango de UIDs/GIDs para ella, y por lo tanto en la (posiblemente costosa) operación de ajuste de propiedad de archivos. Sin embargo, las invocaciones posteriores del contenedor serán baratas (a menos, por supuesto, que el rango de UIDs/GIDs elegido se asigne a otro uso para entonces).
4.Si el parámetro es "no", el namespacio de usuarios se desactiva. Este es el valor predeterminado cuando se invoca systemd-nspawn directamente. (Tenga en cuenta que la unidad systemd-nspawn@.service habilita usuarios privados.) Esta opción no es segura y no debe usarse para ejecutar código no confiable.
5.Si el parámetro es "identity", se emplea el namespacio de usuarios con un mapeo de identidad para los primeros 65536 UIDs/GIDs. Esto es en gran medida equivalente a --private-users=0:65536. Si bien no proporciona aislamiento de UID/GID, ya que todos los UIDs/GIDs del host y del contenedor se eligen de manera idéntica, proporciona aislamiento de capacidades de proceso, pero puede ser útil si el namespacio de usuarios adecuado con mapas de UID distintos no es posible. Esta opción no es segura y no debe usarse para ejecutar código no confiable.
6.Si el parámetro es "managed", el namespacio de usuarios se emplea en modo *gestionado*, es decir, la asignación de un rango de UID se delega a systemd-nsresourced.service(8). Este modo se selecciona por defecto cuando se invoca sin privilegios, pero también se puede solicitar explícitamente cuando se tiene privilegios. En este modo se elige automáticamente un rango de UID de 64K.

Se recomienda asignar al menos 65536 UIDs/GIDs a cada contenedor, para que el rango usable de UID/GID en el contenedor cubra 16 bits. Para una seguridad óptima, no asigne rangos de UID/GID superpuestos a múltiples contenedores. Por lo tanto, es una buena idea usar los 16 bits superiores de los UIDs/GIDs de 32 bits del host como identificador del contenedor, mientras que los 16 bits inferiores codifican el UID/GID del contenedor utilizado. Este es de hecho el comportamiento impuesto por la opción --private-users=pick.

Cuando se utilizan namespaces de usuarios, el rango de GID asignado a cada contenedor se elige siempre idéntico al rango de UID.

En la mayoría de los casos, --private-users=managed (o cuando se tienen privilegios, también --private-users=pick) es la opción recomendada, ya que se aconseja el namespacio de usuarios por seguridad, y esta opción mejora masivamente la seguridad del contenedor mientras opera de forma totalmente automática en la mayoría de los casos.

Tenga en cuenta que el rango de UIDs/GIDs elegido no se escribe en /etc/passwd ni en /etc/group. De hecho, la asignación del rango no se almacena de forma persistente, excepto posiblemente en la propiedad de los archivos y directorios del contenedor, consulte --private-users-ownership=.

Tenga en cuenta que cuando se utiliza el namespacio de usuarios sin mapeo de UID (ver más abajo), la propiedad de los archivos en el disco lo refleja, y todos los archivos y directorios del contenedor son propiedad de los IDs de usuario y grupo efectivos del contenedor. Esto significa que copiar archivos desde y hacia la imagen del contenedor requiere la corrección de los valores numéricos de UID/GID, de acuerdo con el desplazamiento de UID/GID aplicado.

Tenga en cuenta que para un funcionamiento completamente sin privilegios en modo "gestionado", cualquier imagen de directorio debe ser propiedad del rango de UID externo.

Añadido en la versión 220.

--private-users-ownership=

Controla cómo ajustar los UIDs y GIDs de la imagen del contenedor para que coincidan con el rango de UID/GID elegido con --private-users=, ver más arriba. Toma uno de "off" (para dejar la imagen como está), "chown" (para hacer chown() recursivamente el árbol de directorios del contenedor según sea necesario), "map" (para usar montajes de mapeo de ID transparentes desde el UID 0 hasta el rango de UID de destino), "foreign" (lo mismo, pero desde la base del rango de UID externo) o "auto" para usar automáticamente "map" o "foreign", donde estén disponibles y sean aplicables, y "chown" donde no.

Si se selecciona "chown", todos los archivos y directorios en el árbol de directorios del contenedor se ajustarán para que sean propiedad de los UIDs/GIDs apropiados seleccionados para el contenedor (ver más arriba). Esta operación puede ser costosa, ya que implica iterar a través de todo el árbol de directorios del contenedor. Además de la propiedad real de los archivos, también se ajustan los ACL de archivo.

Típicamente "foreign" o "map" es la mejor opción, ya que mapea transparentemente los UIDs/GIDs en memoria según sea necesario sin modificar la imagen, y sin requerir una costosa operación de ajuste recursivo. Sin embargo, actualmente no está disponible para todos los sistemas de archivos.

La opción --private-users-ownership=auto se implica si se utiliza --private-users=pick. Esta opción no tiene efecto si no se utiliza el namespacio de usuarios.

systemd-dissect(1)'s --shift puede usarse para desplazar la propiedad de UID/GID desde o hacia el 0, externo o base de UID/GID de contenedor específica fuera de cualquier invocación de systemd-nspawn.

Añadido en la versión 230.

Opciones de Red

--private-network

Desconecta la red del contenedor de la máquina host. Esto hace que todas las interfaces de red no estén disponibles en el contenedor, con la excepción del dispositivo de loopback y las especificadas con --network-interface= y configuradas con --network-veth. Si se especifica esta opción, se añadirá la capacidad CAP_NET_ADMIN al conjunto de capacidades que retiene el contenedor. Esta última puede ser deshabilitada usando --drop-capability=. Si esta opción no se especifica (o se implica por una de las opciones listadas a continuación), el contenedor tendrá acceso completo a la red del host.

--network-interface=

Asigna la interfaz de red especificada al contenedor. Toma un solo nombre de interfaz, haciendo referencia al nombre en el host, o un par de interfaces separadas por dos puntos, en cuyo caso la primera hace referencia al nombre en el host y la segunda al nombre en el contenedor. Cuando el contenedor termina, la interfaz se mueve de nuevo al espacio de nombres de llamada y se renombra a su nombre original. Tenga en cuenta que --network-interface= implica --private-network. Esta opción puede usarse más de una vez para añadir múltiples interfaces de red al contenedor.

Tenga en cuenta que cualquier interfaz de red especificada de esta manera debe existir ya en el momento de iniciar el contenedor. Si el contenedor se va a iniciar automáticamente al arrancar a través de un archivo de unidad systemd-nspawn@.service, puede tener sentido añadir un archivo de anulación de unidad al servicio (por ejemplo, /etc/systemd/system/systemd-nspawn@foobar.service.d/50-network.conf) con contenido como el siguiente:

[Unit]
Wants=sys-subsystem-net-devices-ens1.device
After=sys-subsystem-net-devices-ens1.device

Esto asegurará que la activación del servicio del contenedor se retrase hasta que aparezca la interfaz de red "ens1". Esto es necesario ya que la detección de hardware es completamente asíncrona, y las interfaces de red pueden descubrirse más tarde durante el proceso de arranque, después de que el contenedor se iniciaría normalmente sin estas dependencias explícitas.

Añadido en la versión 209.

--network-macvlan=

Una interfaz "macvlan" es una interfaz virtual que añade una segunda dirección MAC a un enlace Ethernet físico existente. -n, --network-veth

Crea un enlace Ethernet virtual ("veth") entre el host y el contenedor. El lado del host del enlace Ethernet estará disponible como una interfaz de red nombrada según el nombre del contenedor (como se especifica con --machine=), prefijada con "ve-". El lado del contenedor del enlace Ethernet se nombrará "host0". La opción --network-veth implica --private-network.

Tenga en cuenta que systemd-networkd.service(8) incluye por defecto un archivo de red /usr/lib/systemd/network/80-container-ve.network que coincide con las interfaces del host creadas de esta manera, el cual contiene configuraciones para habilitar el aprovisionamiento automático de direcciones en el enlace virtual creado a través de DHCP, así como el enrutamiento IP automático a las interfaces de red externas del host. También contiene /usr/lib/systemd/network/80-container-host0.network que coincide con la interfaz del contenedor creada de esta manera, que contiene configuraciones para habilitar la asignación de direcciones del lado del cliente a través de DHCP. En caso de que systemd-networkd se esté ejecutando tanto en el host como dentro del contenedor, la comunicación IP automática desde el contenedor al host estará disponible, con conectividad adicional a la red externa.

Tenga en cuenta que --network-veth es el valor predeterminado si se utiliza el archivo de unidad de plantilla systemd-nspawn@.service.

Tenga en cuenta que en Linux los nombres de las interfaces de red pueden tener una longitud máxima de 15 caracteres, mientras que los nombres de los contenedores pueden tener una longitud de hasta 64 caracteres. Dado que esta opción deriva el nombre de la interfaz del lado del host del nombre del contenedor, el nombre posiblemente se trunca. Por lo tanto, se debe tener cuidado para asegurar que los nombres de las interfaces sigan siendo únicos en este caso, o mejor aún, que los nombres de los contenedores generalmente no se elijan con más de 12 caracteres para evitar el truncamiento. Si el nombre se trunca, systemd-nspawn añadirá automáticamente un valor hash de 4 dígitos al nombre para reducir la probabilidad de colisiones. Sin embargo, el algoritmo hash no está libre de colisiones. (Ver systemd.net-naming-scheme(7) para detalles sobre algoritmos de nomenclatura más antiguos para esta interfaz). Alternativamente, se puede usar la opción --network-veth-extra=, que permite la configuración libre del nombre de la interfaz del lado del host independientemente del nombre del contenedor — pero puede requerir un poco más de configuración adicional en caso de que se desee un puente de manera similar a --network-bridge=.

--network-zone=

Crea un enlace Ethernet virtual ("veth") al contenedor y lo añade a una interfaz de puente Ethernet gestionada automáticamente. La interfaz de puente se nombra según el argumento pasado, prefijado con "vz-". La interfaz de puente se crea automáticamente cuando se inicia el primer contenedor configurado para su nombre, y se elimina automáticamente cuando sale el último contenedor configurado para su nombre. Por lo tanto, cada interfaz de puente configurada de esta manera existe solo mientras haya al menos un contenedor que la referencie en ejecución. Esta opción es muy similar a --network-bridge=, además de esta creación/eliminación automática del dispositivo de puente.

Esta configuración facilita la colocación de múltiples contenedores relacionados en un dominio de difusión virtual común basado en Ethernet, aquí llamado una "zona". Cada contenedor solo puede formar parte de una zona, pero cada zona puede contener cualquier número de contenedores. Cada zona se referencia por su nombre. Tenga en cuenta que systemd-networkd.service(8) incluye por defecto un archivo de red /usr/lib/systemd/network/80-container-vz.network que coincide con las interfaces de puente creadas de esta manera, el cual contiene configuraciones para habilitar el aprovisionamiento automático de direcciones en la red virtual creada a través de DHCP, así como el enrutamiento IP automático a las interfaces de red externas del host. Por lo tanto, usar --network-zone= es en la mayoría de los casos completamente automático y suficiente para conectar múltiples contenedores locales en un dominio de difusión conjunto a la máquina host, con conectividad adicional a la red externa.

--resolv-conf=

Configura cómo se debe manejar /etc/resolv.conf dentro del contenedor (es decir, sincronización de configuración DNS del host al contenedor). Toma uno de "off", "copy-host", "copy-static", "copy-uplink", "copy-stub", "replace-host", "replace-static", "replace-uplink", "replace-stub", "bind-host", "bind-static", "bind-uplink", "bind-stub", "delete" o "auto".

Si se establece en "off", el archivo /etc/resolv.conf en el contenedor se deja tal como está incluido en la imagen, y ni se modifica ni se monta sobre él.

Si se establece en "copy-host", el archivo /etc/resolv.conf del host se copia al contenedor, a menos que el archivo ya exista y no sea un archivo regular (por ejemplo, un enlace simbólico). De manera similar, si se usa "replace-host", el archivo se copia, reemplazando cualquier inode existente, incluidos los enlaces simbólicos. De manera similar, si se usa "bind-host", el archivo se monta desde el host al contenedor.

Si se establece en "copy-static", "replace-static" o "bind-static", el archivo resolv.conf estático proporcionado con systemd-resolved.service(8) (específicamente: /usr/lib/systemd/resolv.conf) se copia o se monta en el contenedor.

Si se establece en "copy-uplink", "replace-uplink" o "bind-uplink", el archivo resolv.conf de enlace ascendente administrado por systemd-resolved.service (específicamente: /run/systemd/resolve/resolv.conf) se copia o se monta en el contenedor.

Si se establece en "copy-stub", "replace-stub" o "bind-stub", el archivo resolv.conf stub administrado por systemd-resolved.service (específicamente: /run/systemd/resolve/stub-resolv.conf) se copia o se monta en el contenedor.

Si se establece en "delete", se elimina el archivo /etc/resolv.conf en el contenedor si existe.

Finalmente, si se establece en "auto", el archivo se deja como está si la red privada está activada (ver --private-network). De lo contrario, si systemd-resolved.service se está ejecutando, se utiliza su archivo stub resolv.conf, y si no, el archivo /etc/resolv.conf del host. En estos últimos casos, el archivo se copia si la imagen es escribible y se monta de lo contrario.

Se recomienda usar "copy-..." o "replace-..." si el contenedor podrá realizar cambios en la configuración de DNS por sí mismo, desviándose de la configuración del host. De lo contrario, "bind" es preferible, ya que significa que no se permiten cambios directos en /etc/resolv.conf en el contenedor, ya que es un montaje bind de solo lectura (pero ten en cuenta que si el contenedor tiene suficientes privilegios, podría simplemente desmontar el montaje bind de todos modos). Ten en cuenta que tanto si el archivo se monta bind como si se copia, no se producirá ninguna propagación adicional

de configuración se realiza generalmente después de la inicialización temprana única (esto se debe a que el archivo generalmente se actualiza mediante copia y renombre). Por defecto es "auto".

Opciones de Montaje

--bind=, --bind-ro=

Monta con bind un archivo o directorio del host en el contenedor. Toma uno de: un argumento de ruta —en cuyo caso la ruta especificada se montará desde el host a la misma ruta en el contenedor, o un par de rutas separadas por dos puntos —en cuyo caso la primera ruta especificada es la fuente en el host, y la segunda ruta es el destino en el contenedor, o un triple separado por dos puntos de ruta de origen, ruta de destino y opciones de montaje. La ruta de origen puede ir opcionalmente prefijada con un carácter "+". Si es así, la ruta de origen se toma relativa al directorio raíz de la imagen. Esto permite configurar montajes bind dentro de la imagen del contenedor. La ruta de origen puede especificarse como una cadena vacía, en cuyo caso se utiliza un directorio temporal debajo del directorio /var/tmp/ del host. Se elimina automáticamente cuando el contenedor se apaga. Si la ruta de origen no es absoluta, se resuelve en relación con el directorio de trabajo actual. La opción --bind-ro= crea montajes bind de solo lectura. Se interpretan los escapes de barra invertida, por lo que "\:" puede usarse para incrustar dos puntos en cualquiera de las rutas. Esta opción puede especificarse varias veces para crear múltiples puntos de montaje bind independientes.

Las opciones de montaje están separadas por comas. rbind y norbind controlan si se crea un montaje bind recursivo o regular. Por defecto es rbind. noidmap, idmap, rootidmap y owneridmap controlan el mapeo de IDs.

El uso de idmap, rootidmap u owneridmap requiere soporte del sistema de archivos de origen para montajes con IDs de usuario/grupo mapeados. Por defecto es noidmap. Con x siendo el desplazamiento del rango de UID del contenedor, y siendo la longitud del rango de UID del contenedor, y p siendo el UID propietario del nodo de entrada del montaje bind en el host:

•Si se usa noidmap, cualquier usuario z en el rango 0 ... y visto desde dentro del contenedor se mapea a x + z en el rango x ... x + y en el host. Otros usuarios del host se mapean a nobody dentro del contenedor.
•Si se usa idmap, cualquier usuario z en el rango de UID 0 ... y visto desde dentro del contenedor se mapea al mismo z en el mismo rango 0 ... y en el host. Otros usuarios del host se mapean a nobody dentro del contenedor.
•Si se usa rootidmap, el usuario 0 visto desde dentro del contenedor se mapea a p en el host. Otros usuarios del host se mapean a nobody dentro del contenedor.
•Si se usa owneridmap, el propietario del directorio de destino dentro del contenedor se mapea a p en el host. Otros usuarios del host se mapean a nobody dentro del contenedor.

Independientemente de la opción de mapeo de IDs utilizada, se utilizará el mismo mapeo para los IDs de usuario y grupo. Si se utilizan rootidmap u owneridmap, el grupo propietario del directorio montado con bind no tendrá ningún efecto.

Tenga en cuenta que cuando se utiliza esta opción en combinación con --private-users, los puntos de montaje resultantes serán propiedad del usuario nobody. Esto se debe a que el montaje y sus archivos y directorios continúan siendo propiedad de los usuarios y grupos relevantes del host, que no existen en el contenedor, y por lo tanto aparecen bajo el UID comodín 65534 (nobody). Si se crean montajes bind de este tipo, se recomienda hacerlos de solo lectura, utilizando --bind-ro=. Alternativamente, puede usar la opción de montaje "idmap" para mapear los IDs del sistema de archivos.

--bind-user=

Monta el directorio home del usuario especificado en el host dentro del contenedor. Toma el nombre de un usuario existente en el host como argumento. Puede usarse varias veces para montar varios usuarios en el contenedor. Esto hace dos cosas:
1. El directorio home del usuario se monta con bind desde el host a /run/host/home/, utilizando un montaje con mapeo de IDs para mapear el UID/GID del usuario del host a su UID/GID asignado en el contenedor.
2. Se genera un registro JSON de usuario y grupo en /run/userdb/ que describe al usuario mapeado. Contiene una representación minimizada del registro de usuario del host, ajustado al UID/GID y la ruta del directorio home asignados al usuario en el contenedor. El módulo glibc NSS nss-systemd(8) capturará estos registros desde allí y los hará disponibles en las bases de datos de usuarios/grupos del contenedor.

La combinación de las dos operaciones anteriores asegura que sea posible iniciar sesión en el contenedor utilizando la misma información de cuenta que en el host. El usuario solo se mapea de forma transitoria, mientras el contenedor está en ejecución, y el mapeo en sí no produce cambios persistentes en el contenedor (excepto quizás para los mensajes de registro generados al iniciar sesión, y similares). Tenga en cuenta que, en particular, la asignación de UID/GID en el contenedor no se realiza de forma persistente. Si el usuario se mapea de forma transitoria, es mejor no permitir que el usuario realice cambios persistentes en el contenedor. Si el usuario deja archivos o directorios propiedad del usuario, y esos UID/GID se reutilizan durante invocaciones posteriores del contenedor (posiblemente con un mapeo --bind-user= diferente), esos archivos y directorios serán accesibles para el "nuevo" usuario.

El mapeo de registros de usuario/grupo solo funciona si el contenedor contiene systemd 249 o posterior, con nss-systemd configurado correctamente en nsswitch.conf. Consulte nss-systemd(8) para obtener detalles.

Tenga en cuenta que el registro de usuario propagado desde el host al contenedor contendrá el hash de contraseña UNIX del usuario, de modo que sean posibles inicios de sesión sin problemas en el contenedor. Si el contenedor es menos confiable que el host, es importante utilizar una función de hash de contraseña UNIX segura (por ejemplo, yescrypt o similar, con el prefijo de hash "$y$").

Al montar un usuario desde el host en el contenedor, se realizan comprobaciones para garantizar que el nombre de usuario aún no se conozca en el contenedor. Además, se comprueba que el UID/GID asignado para él no esté actualmente definido en las bases de datos de usuarios/grupos del contenedor. Ambas comprobaciones acceden directamente a los archivos /etc/passwd y /etc/group del contenedor, y por lo tanto, podrían no detectar cuentas existentes en otras bases de datos.

systemd-nspawn(1)

NAME

systemd-nspawn - Begin a defined system image in a namespace container

SYNOPSIS

systemd-nspawn [OPTIONS...] [executable [arguments...]]

DESCRIPTION

Runs a command (or an interactive shell if no command is specified) in a new namespace container based on a directory tree. This is often referred to as "chroot(8) on steroids".

The container can be started from a directory containing a system image, or from a raw disk image file. The directory tree is mounted into a new namespace, and the specified command is executed within this container. If no command is specified, an interactive shell is started. By default, the container runs in a separate network namespace, with a virtual network device, and in its own PID namespace.

The container is generally configured to run as root inside the container, and all file system paths are resolved relative to the container's root directory. It's possible to bind-mount directories or files from the host into the container.

The container runs under a systemd system and service manager instance, which is created automatically. This instance is managed by the caller's systemd instance. It is possible to control services inside the container via machinectl(1).

It is possible to run containers with various security and resource control features enabled, such as various isolation mechanisms and cgroups settings. Use systemd.directives(7) for a list of options available.

For more details on container interfaces, see the Container Interface specification.

UNPRIVILEGED OPERATION

When run by a normal user, systemd-nspawn attempts to create a minimal container environment with strong isolation guarantees. It is a best-effort approach and does not provide the same level of security as running as root.

The following features are available when running unprivileged:

  • User namespace setup for the container process.
  • Network namespace setup.
  • IPC namespace setup.
  • UTS namespace setup.
  • Mount namespace setup.
  • PID namespace setup.
  • Device nodes are not created and are not accessible by default.
  • No filesystem journaling.
  • No kernel module loading.
  • No access to host devices.
  • No access to host network.
  • No access to host IPC.
  • No access to host D-Bus.
  • No access to host system services.
  • Resource control via cgroups is not available.

The following options are implicitly enabled when running unprivileged:

  • --container-only
  • --drop-capability=CAP_SYS_ADMIN
  • --network-veth
  • --no-pivot-root
  • --private-dev
  • --private-home
  • --private-tmp
  • --read-only-tree
  • --register=no
  • --sync
  • --temp-dir

When run unprivileged, only the container's own root directory is accessible, and any user-owned files or directories are accessible as well. This means that the container's root filesystem must be owned by the user running systemd-nspawn.

OPTIONS

The following options are understood:

-D, --directory=ROOT
Use the specified directory ROOT as the container's root file system. If this option is not given, and -i is not used, the current directory is used.
-i, --image=FILE
Use the specified disk image file FILE as the container's root file system. The file may be a raw disk image, a qcow2 disk image, or an OSTree repository. The image will be mounted. It is possible to specify multiple image files, in which case they are stacked using overlayfs. See systemd.exec(5) for details on file system stacking.
-b, --boot
Boot the system inside the container. This implies starting the container's system and service manager instance. This option is implied when -i is used and no command is given.
--pivot-root
Use pivot-root(2) to change the root file system. This is the default when running as root. If this option is not given, the container's root directory is mounted into the host's root directory and the host's root directory is mounted over the container's root directory. This is often referred to as a "chroot-like" behaviour.
--no-pivot-root
Do not use pivot-root(2). This is the default when running unprivileged. The container's root file system is mounted under the host's root file system.
-x, --read-only-tree
Mount the container's root file system read-only. This is useful for ephemeral containers. Changes made during runtime will be lost on exit. This option is implied when running unprivileged.
--writable-tmpfs
Mounts /tmp and /var/tmp as private, writable directories using tmpfs. This is the default when running unprivileged.
--private-dev
Mounts /dev as a private, temporary file system. Device nodes created by systemd-udevd within the container are still available. This is the default when running unprivileged.
--no-private-dev
Do not mount /dev as a private, temporary file system. Existing device nodes are used.
--private-home
Mounts the user's home directory as a private, temporary file system. This is the default when running unprivileged.
--no-private-home
Do not mount the user's home directory as a private, temporary file system.
--private-etc=hosts,resolv.conf,hostname,machine-id
Mounts /etc/hosts, /etc/resolv.conf, /etc/hostname, and /etc/machine-id as private, temporary file systems. This is useful for running containers that should not share configuration with the host. Defaults to the listed files if not specified.
--no-private-etc
Do not mount private copies of /etc/hosts, /etc/resolv.conf, /etc/hostname, and /etc/machine-id.
--private-tmp
Mounts /tmp and /var/tmp as private, temporary file systems. This is the default when running unprivileged.
--no-private-tmp
Do not mount /tmp and /var/tmp as private, temporary file systems.
--resolv-conf=path
Mounts the specified path into the container as /etc/resolv.conf. Defaults to the host's /etc/resolv.conf.
--passwd-file=path
Mounts the specified path into the container as /etc/passwd. This is useful for running containers without a full user database.
--chroot-path=path
Treats the specified path as the root of the chroot environment. This is equivalent to setting the root directory with -D and then mounting it into the host's root directory.
-M, --machine=NAME
Register the container under the specified NAME with systemd's service manager. If this option is specified, the container will be managed like a systemd service. The name should follow the same naming conventions as systemd units. If the container is booted (-b), it will be started as a service. If the container is not booted, it will be executed as a transient unit.
--register={true|false|auto}
Whether to register the container with systemd's service manager. Defaults to auto, which means registration is enabled if -M is used or if the container is booted. If set to true, the container is registered as a transient service. If set to false, the container is not registered.
-u, --user=USER
Run the command as the specified USER inside the container. This user must exist within the container's user database.
-N, --namespace=NAMESPACE
Enable additional namespaces. Possible values are network, ipc, uts, pid, user, cgroup. Multiple namespaces can be specified. Defaults to enabling network, ipc, uts, pid, and cgroup namespaces.
--no-network
Disable network namespace setup. The container will share the host's network stack.
--network-veth
Create a virtual ethernet pair (veth) and connect one end to the container and the other end to the host's bridge interface. This is the default.
--network-bridge=BRIDGE
Connect the container's network interface to the specified bridge interface BRIDGE on the host. If not specified, a new bridge interface is created.
--network-serial-console=DEVICE
Connect the container's serial console to the specified host device DEVICE. This allows accessing the container's console via a serial port.
--bind=BINDINGS
Add bind mounts. Format is HOST_PATH[:CONTAINER_PATH[:OPTIONS]]. If CONTAINER_PATH is omitted, it defaults to HOST_PATH. OPTIONS may include ro (read-only), rw (read-write), bind, norecurse, private, slave, shared, unbindable, move. See mount(8) for details on mount options.
--overlay=OVERLAYS
Add overlay mounts. Format is UPPER_DIR:LOWER_DIR[:MERGED_DIR[:OPTIONS]]. If MERGED_DIR is omitted, it defaults to the current directory.
--copy-syslog-ng
Copy the host's syslog-ng configuration into the container. This is useful for running syslog-ng inside the container.
--directory-triggers=PATH
Specifies a directory that contains files which trigger the setup of directory-based container images. See systemd.directives(7) for more information.
--bind-proc-modules
Bind-mount kernel modules from the host's /proc/modules into the container. This is only useful if you intend to load kernel modules within the container.
--setenv=VARIABLE=VALUE
Set environment variable VARIABLE to VALUE inside the container.
--uidmap=MAP, --gidmap=MAP
Configure user and group ID mappings for the user namespace. The format of MAP is container_id:host_id:count. For example, `--uidmap=0:1000:1` maps container UID 0 to host UID 1000. Multiple maps can be specified.
-q, --quiet
Suppress informational output.
-v, --verbose
Enable verbose output.
-h, --help
Print a help message and exit.
--version
Print a short version string and exit.
