sys_socket.h(0P) Manual del programador POSIX sys_socket.h(0P)

PROLOG

Esta página del manual forma parte del Manual del programador POSIX. La implementación de Linux de esta interfaz puede diferir (consulte la página del manual de Linux correspondiente para conocer los detalles del comportamiento de Linux), o la interfaz puede no estar implementada en Linux.

NOMBRE

sys/socket.h — cabecera principal de sockets

SINOPSIS

#include <sys/socket.h>

DESCRIPCIÓN

La cabecera <sys/socket.h> definirá el tipo socklen_t, que es un tipo entero de al menos 32 bits de ancho; consulte USO DE LA APLICACIÓN.

La cabecera <sys/socket.h> definirá el tipo de entero sin signo sa_family_t.

La cabecera <sys/socket.h> definirá la estructura sockaddr, que incluirá al menos los siguientes miembros:

sa_family_t  sa_family  Familia de direcciones.
char         sa_data[]  Dirección del socket (datos de longitud variable).

La estructura sockaddr se utiliza para definir una dirección de socket que se emplea en las funciones bind(), connect(), getpeername(), getsockname(), recvfrom() y sendto().

La cabecera <sys/socket.h> definirá la estructura sockaddr_storage, que será:

*
Lo suficientemente grande como para acomodar todas las estructuras de direcciones específicas del protocolo soportadas
*
Alineada en un límite apropiado para que los punteros a ella puedan ser convertidos (casteados) como punteros a estructuras de direcciones específicas del protocolo y utilizados para acceder a los campos de dichas estructuras sin problemas de alineación

La estructura sockaddr_storage incluirá al menos los siguientes miembros:

sa_family_t   ss_family

Cuando un puntero a una estructura sockaddr_storage se convierte en un puntero a una estructura sockaddr, el campo ss_family de la estructura sockaddr_storage se mapeará sobre el campo sa_family de la estructura sockaddr. Cuando un puntero a una estructura sockaddr_storage se convierte en un puntero a una estructura de dirección específica del protocolo, el campo ss_family se mapeará sobre un campo de esa estructura que sea del tipo sa_family_t y que identifique la familia de direcciones del protocolo.

La cabecera <sys/socket.h> definirá la estructura msghdr, que incluirá al menos los siguientes miembros:

void          *msg_name        Dirección opcional.
socklen_t      msg_namelen     Tamaño de la dirección.
struct iovec  *msg_iov         Array de dispersión/recolección.
int            msg_iovlen      Miembros en msg_iov.
void          *msg_control     Datos auxiliares; véase más abajo.
socklen_t      msg_controllen  Tamaño del búfer de datos auxiliares len.
int            msg_flags       Banderas en el mensaje recibido.

La estructura msghdr se utiliza para minimizar el número de parámetros suministrados directamente a las funciones recvmsg() y sendmsg(). Esta estructura se utiliza como parámetro de valor‐resultado en la función recvmsg() y solo de valor para la función sendmsg().

La cabecera <sys/socket.h> definirá la estructura iovec tal como se describe en <sys/uio.h>.

La cabecera <sys/socket.h> definirá la estructura cmsghdr, que incluirá al menos los siguientes miembros:

socklen_t  cmsg_len    Número de bytes de datos, incluyendo el cmsghdr.
int        cmsg_level  Protocolo de origen.
int        cmsg_type   Tipo específico del protocolo.

La estructura cmsghdr se utiliza para el almacenamiento de información de objetos de datos auxiliares.

Los datos auxiliares consisten en una secuencia de pares, cada uno compuesto por una estructura cmsghdr seguida de un array de datos. El array de datos contiene el mensaje de datos auxiliares, y la estructura cmsghdr contiene información descriptiva que permite a una aplicación analizar correctamente los datos.

Los valores de cmsg_level serán valores legales para el argumento level de las funciones getsockopt() y setsockopt(). La documentación del sistema especificará las definiciones de cmsg_type para los protocolos soportados.

También es posible obtener datos auxiliares a nivel de socket. La cabecera <sys/socket.h> definirá la siguiente constante simbólica para su uso como valor de cmsg_type cuando cmsg_level es SOL_SOCKET:

SCM_RIGHTS
Indica que el array de datos contiene los derechos de acceso que se van a enviar o recibir.

La cabecera <sys/socket.h> definirá las siguientes macros para acceder a los arrays de datos en los datos auxiliares asociados a una cabecera de mensaje:

CMSG_DATA(cmsg)

Si el argumento es un puntero a una estructura cmsghdr, esta macro devolverá un puntero a carácter sin signo al array de datos asociado con la estructura cmsghdr.
CMSG_NXTHDR(mhdr,cmsg)

Si el primer argumento es un puntero a una estructura msghdr y el segundo argumento es un puntero a una estructura cmsghdr en los datos auxiliares apuntados por el campo msg_control de esa estructura msghdr, esta macro devolverá un puntero a la siguiente estructura cmsghdr, o un puntero nulo si esta estructura es la última cmsghdr en los datos auxiliares.
CMSG_FIRSTHDR(mhdr)

Si el argumento es un puntero a una estructura msghdr, esta macro devolverá un puntero a la primera estructura cmsghdr en los datos auxiliares asociados con esta estructura msghdr, o un puntero nulo si no hay datos auxiliares asociados con la estructura msghdr.

La cabecera <sys/socket.h> definirá la estructura linger, que incluirá al menos los siguientes miembros:

int  l_onoff   Indica si la opción linger está habilitada.
int  l_linger  Tiempo de espera (linger time), en segundos.

La cabecera <sys/socket.h> definirá las siguientes constantes simbólicas con valores distintos:

SOCK_DGRAM
Socket de datagramas.
SOCK_RAW
Interfaz de protocolo RAW.
SOCK_SEQPACKET
Socket de paquete secuenciado.
SOCK_STREAM
Socket de flujo de bytes.

La cabecera <sys/socket.h> definirá la siguiente constante simbólica para su uso como argumento level en las llamadas a setsockopt() y getsockopt().

SOL_SOCKET
Opciones a acceder a nivel de socket, no a nivel de protocolo.

La cabecera <sys/socket.h> definirá las siguientes constantes simbólicas con valores distintos para su uso como argumento option_name en las llamadas a getsockopt() o setsockopt() (consulte el volumen de Interfaces del Sistema de POSIX.1‐2017, Sección 2.10.16, Uso de Opciones):

SO_ACCEPTCONN
El socket está aceptando conexiones.
SO_BROADCAST
Se admite la transmisión de mensajes de difusión.
SO_DEBUG
Se están registrando información de depuración.
SO_DONTROUTE
Omitir el enrutamiento normal.
SO_ERROR
Estado de error del socket.
SO_KEEPALIVE
Las conexiones se mantienen activas con mensajes periódicos.
SO_LINGER
El socket espera (lingers) al cerrar.
SO_OOBINLINE
Los datos fuera de banda se transmiten en línea.
SO_RCVBUF
Tamaño del búfer de recepción.

    APPLICATION USAGE

    To forestall portability problems, it is recommended that applications not use values larger than 231 -1 for the socklen_t type.

    The sockaddr_storage structure solves the problem of declaring storage for automatic variables which is both large enough and aligned enough for storing the socket address data structure of any family. For example, code with a file descriptor and without the context of the address family can pass a pointer to a variable of this type, where a pointer to a socket address structure is expected in calls such as getpeername(), and determine the address family by accessing the received content after the call.

    The example below illustrates a data structure which aligns on a 64-bit boundary. An implementation-defined field _ss_align following _ss_pad1 is used to force a 64-bit alignment which covers proper alignment good enough for needs of at least sockaddr_in6 (IPv6) and sockaddr_in (IPv4) address data structures. The size of padding field _ss_pad1 depends on the chosen alignment boundary. The size of padding field _ss_pad2 depends on the value of overall size chosen for the total size of the structure. This size and alignment are represented in the above example by implementation-defined (not required) constants _SS_MAXSIZE (chosen value 128) and _SS_ALIGNMENT (with chosen value 8). Constants _SS_PAD1SIZE (derived value 6) and _SS_PAD2SIZE (derived value 112) are also for illustration and not required. The implementation-defined definitions and structure field names above start with an <underscore> to denote implementation private name space. Portable code is not expected to access or reference those fields or constants.

    /*
 *  Desired design of maximum size and alignment.
 */
#define _SS_MAXSIZE 128
    /* Implementation-defined maximum size. */
#define _SS_ALIGNSIZE (sizeof(int64_t))
    /* Implementation-defined desired alignment. */
    /*
 *  Definitions used for sockaddr_storage structure paddings design.
 */
#define _SS_PAD1SIZE (_SS_ALIGNSIZE - sizeof(sa_family_t))
#define _SS_PAD2SIZE (_SS_MAXSIZE - (sizeof(sa_family_t)+ \
                      _SS_PAD1SIZE + _SS_ALIGNSIZE))
struct sockaddr_storage {
    sa_family_t  ss_family;  /* Address family. */
/*
 *  Following fields are implementation-defined.
 */
    char _ss_pad1[_SS_PAD1SIZE];
        /* 6-byte pad; this is to make implementation-defined
           pad up to alignment field that follows explicit in
           the data structure. */
    int64_t _ss_align;  /* Field to force desired structure
                           storage alignment. */
    char _ss_pad2[_SS_PAD2SIZE];
        /* 112-byte pad to achieve desired size,
           _SS_MAXSIZE value minus size of ss_family
           __ss_pad1, __ss_align fields is 112. */
};
