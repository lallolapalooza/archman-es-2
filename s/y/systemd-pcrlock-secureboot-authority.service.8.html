NOMBRE

systemd-pcrlock, systemd-pcrlock-file-system.service, systemd-pcrlock-firmware-code.service, systemd-pcrlock-firmware-config.service, systemd-pcrlock-machine-id.service, systemd-pcrlock-make-policy.service, systemd-pcrlock-secureboot-authority.service, systemd-pcrlock-secureboot-policy.service - Analiza y predice estados de PCR de TPM2 y genera una política de acceso a partir de la predicción

SINOPSIS

/usr/lib/systemd/systemd-pcrlock [OPCIONES...]

DESCRIPCIÓN

Nota: este comando es experimental por ahora. Aunque es probable que se convierta en un componente regular de systemd, aún podría cambiar en su comportamiento e interfaz.

systemd-pcrlock es una herramienta que puede usarse para analizar y predecir mediciones de PCR de TPM2, y generar políticas de acceso de TPM2 a partir de la predicción, la cual almacena en un índice NV de TPM2 (es decir, en la memoria no volátil de TPM2). Esto puede ser utilizado para restringir el acceso a objetos de TPM2 (como claves de cifrado de disco) a arranques del sistema en los que solo se utilicen componentes específicos y confiables.

systemd-pcrlock utiliza como entrada para su análisis y predicción:

•El registro de eventos TPM2 del firmware UEFI (es decir, /sys/kernel/security/tpm0/binary_bios_measurements) del arranque actual.
•El registro de eventos TPM2 del espacio de usuario (es decir, /run/log/systemd/tpm2-measure.log) del arranque actual.
•El estado actual de los PCR del chip TPM2.
•Archivos de definición de componentes de arranque (*.pcrlock y *.pcrlock.d/*.pcrlock, véase systemd.pcrlock(5)) que cada uno define las mediciones esperadas para un componente del proceso de arranque, permitiendo variantes alternativas para cada uno. (Las variantes pueden usarse para bendecir múltiples versiones de kernel o versiones de gestor de arranque al mismo tiempo).

Utiliza estas entradas para generar un registro de eventos combinado, validándolo contra los estados de PCR. Luego intenta reconocer los registros del registro de eventos y los empareja con los componentes definidos. Para cada PCR donde esto se pueda hacer de manera integral (es decir, donde todos los registros listados y todos los componentes definidos hayan sido emparejados) esto puede entonces ser utilizado para predecir mediciones de PCR futuras, teniendo en cuenta las variantes alternativas definidas para cada componente. Esta predicción puede entonces convertirse en una política de acceso TPM2 (que consiste en elementos PolicyPCR y PolicyOR de TPM2), que luego se almacena en un índice NV en el TPM2. Esto puede usarse para luego bloquear secretos (como claves de cifrado de disco) a estas políticas (a través de una política PolicyAuthorizeNV de TPM2).

Utilice herramientas como systemd-cryptenroll(1) o systemd-repart(8) para vincular el cifrado de disco a una política TPM2 de systemd-pcrlock. Específicamente, véase los interruptores --tpm2-pcrlock= de estas herramientas.

La lógica de la política de acceso requiere un dispositivo TPM2 que implemente el comando "PolicyAuthorizeNV", es decir, que implemente TPM 2.0 versión 1.38 o más reciente.

COMANDOS

Se entienden los siguientes comandos:

log

Lee el registro de eventos TPM2 combinado, lo valida, lo empareja con los valores actuales de PCR y muestra ambos en formato tabular. Combine con --json= para generar la salida en formato JSON.

Añadido en la versión 255.

cel

Lee el registro de eventos TPM2 combinado y lo escribe en STDOUT en el Formato de Registro de Eventos Canónicos TCG (CEL-JSON)[1].

Añadido en la versión 255.

list-components

Muestra una lista de definiciones de componentes y sus variantes, es decir, los archivos *.pcrlock descubiertos en /var/lib/pcrlock.d/, /usr/lib/pcrlock.d/ y los otros directorios compatibles. Véase systemd.pcrlock(5) para más detalles sobre estos archivos y la lista completa de directorios buscados.

Añadido en la versión 255.

predict

Predice el estado de PCR en futuros arranques. Esto analizará el registro de eventos TPM2 como se describió anteriormente, reconocerá los componentes y luego generará todos los posibles valores de PCR resultantes para todas las combinaciones de variantes de componentes. Tenga en cuenta que no se realiza ninguna predicción para los PCR cuyo valor no coincida con los registros del registro de eventos, para los cuales se descubren mediciones no reconocidas o para los cuales se definen componentes que no se pueden encontrar en el registro de eventos. Esta es una medida de seguridad para garantizar que cualquier política de acceso generada se pueda cumplir correctamente en los arranques actuales y futuros.

Añadido en la versión 255.

make-policy

Predice el estado de PCR para futuros arranques, de forma muy similar al comando predict anterior. Luego utiliza estos datos para generar una política de acceso TPM2 que almacena en un índice NV de TPM2. La predicción y la información sobre el TPM2 utilizado y su índice NV se escriben en /var/lib/systemd/pcrlock.json.

El índice NV se asigna en la primera invocación y se actualiza en invocaciones posteriores.

El contenido del índice NV puede modificarse (y por lo tanto, la política almacenada en él actualizarse) proporcionando un PIN de acceso. Este PIN normalmente se genera automáticamente y se almacena cifrado (con una política de acceso que lo vincula al propio índice NV) en el archivo de política JSON mencionado anteriormente. Este PIN puede ser elegido por el usuario, a través del interruptor --recovery-pin=. Si se especifica, puede utilizarse como ruta alternativa de acceso para actualizar la política.

Si la nueva predicción coincide con la antigua, este comando termina rápidamente y no realiza ninguna operación adicional. (A menos que se especifique --force, véase más abajo).

A partir de la v256, se codifica una copia del archivo de política /var/lib/systemd/pcrlock.json en una credencial (véase systemd-creds(1) para más detalles) y se escribe en la partición del sistema EFI o en la partición XBOOTLDR, en el subdirectorio /loader/credentials/. Allí es captada al arrancar por systemd-stub(7) y pasada al initrd invocado, donde puede ser utilizada para desbloquear el sistema de archivos raíz (que típicamente contiene /var/, que es donde se encuentra la copia principal de la política, que por lo tanto no puede usarse para desbloquear el sistema de archivos raíz). El archivo de credenciales se nombra según el token de entrada de arranque de la instalación (véase bootctl(1)), que es configurable a través del interruptor --entry-token=, véase más abajo.

Añadido en la versión 255.

remove-policy

Elimina una política generada previamente. Borra el archivo /var/lib/systemd/pcrlock.json y desasigna el índice NV.

Añadido en la versión 255.

is-supported

Comprueba si el TPM2 local soporta toda la funcionalidad para que systemd-pcrlock funcione correctamente. Esto realiza pruebas similares a systemd-analyze has-tpm2, pero también comprueba el soporte de las operaciones de TPM2 requeridas por systemd-pcrlock. Produce una de las siguientes salidas: "no", "partial" (en caso de que algunas partes del soporte de TPM2 estén disponibles en hardware, firmware, SO, pero no sea completo), "obsolete" (si el soporte de TPM2 está disponible en hardware, firmware y SO, pero faltan las operaciones requeridas para systemd-pcrlock), "yes". Devuelve un estado de salida de cero si el soporte completo está disponible, de lo contrario un valor distinto de cero.

Si se combina con --quiet, suprime la salida de la cadena.

Actualmente, esto comprueba el soporte para el comando TPM2 PolicAuthorizeNV, así como el soporte del algoritmo de hash SHA-256.

Añadido en la versión 258.

lock-firmware-code, unlock-firmware-code

Genera/elimina archivos .pcrlock basados en el registro de eventos TPM2 del arranque actual que cubren todos los registros para los PCRs 0 ("platform-code") y 2 ("external-code").

Esta operación permite bloquear el proceso de arranque a la versión actual del firmware del sistema y sus tarjetas de extensión. Esta operación solo debe usarse si el proveedor del sistema no proporciona datos pcrlock adecuados de antemano.

Tenga en cuenta que estos datos solo coinciden con la versión actual del firmware. Si se aplica una actualización de firmware, estos datos quedarán obsoletos y cualquier política de acceso generada a partir de ellos ya no será válida. Por lo tanto, se recomienda invocar unlock-firmware-code antes de realizar una actualización de firmware, seguido de make-policy para actualizar la política.

systemd-pcrlock lock-firmware-code se invoca automáticamente al arrancar a través de la unidad systemd-pcrlock-firmware-code.service, si está habilitada. NAME

systemd-pcrlock-secureboot-authority.service - authorize secure boot keys

SYNOPSIS

/usr/lib/systemd/systemd-pcrlock-secureboot-authority.service [options]

DESCRIPTION

This service uses the secure boot authority key to unseal a TPM2 NV index and unblock write access to it. It is used to allow the secure boot keys stored on disk to authorize the unsealing of TPM2 NV indices that contain the PCR values required to unlock disk encryption, or other secrets protected by PCR values.

This service might be invoked by systemd-cryptenroll(1) to re-authorize access to disk encryption keys after a firmware update, or other events that might invalidate the secure boot policy.

The service expects the secure boot authority key to be stored in the secure boot policy file, which is usually located in /var/lib/systemd/pcrlock.json.

The service configures the TPM2 device by using the tpm2-policy(8) utility. It reads the policy from the secure boot policy file and uses the secure boot authority key to unseal the data stored in the specified TPM2 NV index.

COMMANDS

This service does not accept any explicit commands.

OPTIONS

The following options are understood:

--pin=PIN
The PIN used to unlock the TPM2 NV index. If the NV index is not yet initialized, this PIN is used to protect the newly allocated NV index. If a policy has already been created, the PIN is used to unlock write access to the NV index. If either "hide" or "show" is used, a PIN is automatically generated and, only in the case of "show", displayed on screen. Regardless of whether it is user-supplied or automatically generated, it is stored in encrypted form in the policy metadata file. The recovery PIN may be used to regain write access to an NV index in case the access policy became out of date.
Added in version 255.

--pcrlock=

Takes a file system path as argument. If specified, configures where to write the generated pcrlock data to. Honoured by the various lock-* commands. If not specified, a default path is generally used, as documented above.

Added in version 255.

--policy=

Takes a file system path as argument. If specified, configures where to write pcrlock policy metadata to. If not specified, defaults to /var/lib/systemd/pcrlock.json.

Added in version 255.

--force

If specified with make-policy, the predicted policy will be written to the NV index even if it is detected to be the same as the previously stored one.

Added in version 255.

--entry-token=

Sets the boot entry token to use for the file name for the pcrlock policy credential in the EFI System Partition or XBOOTLDR partition. See the bootctl(1) option of the same regarding expected values. This switch has an effect on the make-policy command only.

Added in version 256.

--quiet

If specified suppresses output when invoked for is-supported.

Added in version 258.

--json=MODE

Shows output formatted as JSON. Expects one of "short" (for the shortest possible output without any redundant whitespace or line breaks), "pretty" (for a pretty version of the same, with indentation and line breaks) or "off" (to turn off JSON output, the default).

--no-pager

Do not pipe output into a pager.

-h, --help

Print a short help text and exit.

--version

Print a short version string and exit.

EXIT STATUS

On success, 0 is returned, a non-zero failure code otherwise.
