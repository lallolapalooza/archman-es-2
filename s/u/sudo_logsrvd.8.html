NAME

sudo_logsrvd — servidor de registro de eventos y E/S de sudo

SYNOPSIS

sudo_logsrvd [-hnV] [-f archivo] [-R porcentaje]

DESCRIPTION

sudo_logsrvd es un servidor de registro de alta rendimiento que acepta registros de eventos y de E/S de sudo. Puede utilizarse para implementar el registro centralizado de los registros de sudo. El servidor tiene dos modos de funcionamiento: local y de retransmisión. Por defecto, sudo_logsrvd almacena los registros localmente, pero también puede configurarse para retransmitirlos a otro servidor que soporte el protocolo sudo_logsrv.proto(5).

Cuando no se está retransmitiendo, las entradas de registro de eventos pueden registrarse a través de syslog(3) o en un archivo local. Los registros de E/S almacenados localmente por sudo_logsrvd pueden reproducirse a través de la utilidad sudoreplay(8) de la misma manera que los registros generados directamente por el plugin de sudoers.

El servidor también admite la reanudación de transferencias de registro interrumpidas. Para distinguir los registros de E/S completados de los incompletos, el archivo de registro de tiempos de E/S se establece como de solo lectura cuando el registro está completo.

Los parámetros de configuración para sudo_logsrvd pueden especificarse en el archivo sudo_logsrvd.conf(5) o en el archivo especificado mediante la opción -f.

sudo_logsrvd vuelve a leer su archivo de configuración cuando recibe SIGHUP y escribe el estado del servidor en el archivo de depuración (si hay alguno configurado) cuando recibe SIGUSR1.

Las opciones son las siguientes:

-f archivo, --file=archivo
Lee la configuración del archivo archivo en lugar del predeterminado, /etc/sudo_logsrvd.conf.
-h, --help
Muestra un breve mensaje de ayuda en la salida estándar y sale.
-n, --no-fork
Ejecuta sudo_logsrvd en primer plano en lugar de desvincularse del terminal y convertirse en un demonio.
-R porcentaje, --random-drop=porcentaje
Para cada mensaje, hay una probabilidad del porcentaje de que el servidor desconecte. Esto solo está destinado a depurar la capacidad de un cliente para reiniciar una conexión.
-V, --version
Imprime la versión de sudo_logsrvd y sale.

Seguridad de las conexiones del servidor

Los datos de registro de E/S enviados a sudo_logsrvd pueden contener información confidencial como contraseñas y deben protegerse utilizando Transport Layer Security (TLS). Hacerlo requiere tener un certificado firmado en el servidor y, si tls_checkpeer está habilitado en sudo_logsrvd.conf(5), un certificado firmado también en el cliente.

Los certificados pueden ser firmados por una Autoridad de Certificación (CA) conocida, o se puede utilizar una CA privada. Las instrucciones para crear una CA privada se incluyen a continuación en la sección EJEMPLOS.

Depuración de sudo_logsrvd

sudo_logsrvd admite un marco de depuración flexible que se configura mediante líneas Debug en el archivo sudo.conf(5).

Para obtener más información sobre la configuración de sudo.conf(5), consulte su manual.

FILES

/etc/sudo.conf
Configuración del front-end de Sudo
/etc/sudo_logsrvd.conf
Archivo de configuración del servidor de registro de Sudo

Directorio donde se almacenan los nuevos diarios cuando la opción store_first relay está habilitada.

Directorio donde se almacenan los diarios completados cuando la opción store_first relay está habilitada.

EXAMPLES

Creación de certificados autofirmados

A menos que esté utilizando certificados firmados por una Autoridad de Certificación (CA) conocida (o una CA corporativa local), deberá crear su propia CA que pueda firmar los certificados utilizados por sudo_logsrvd, sudo_sendlog y el plugin de sudoers. Los siguientes pasos utilizan el comando openssl(1) para crear claves y certificados.

Configuración inicial

Primero, necesitamos crear una estructura de directorios para almacenar los archivos de la CA. Crearemos una nueva jerarquía de directorios en /etc/ssl/sudo para este propósito.

# mkdir /etc/ssl/sudo
# cd /etc/ssl/sudo
# mkdir certs csr newcerts private
# chmod 700 private
# touch index.txt
# echo 1000 > serial

Los archivos serial e index.txt se utilizan para mantener un registro de los certificados firmados.

A continuación, necesitamos hacer una copia del archivo openssl.conf y personalizarlo para nuestra nueva CA. La ruta a openssl.cnf depende del sistema, pero /etc/ssl/openssl.cnf es la ubicación más común. Deberá ajustar el siguiente ejemplo si tiene una ubicación diferente en su sistema.

# cp /etc/ssl/openssl.cnf .

Ahora edite el archivo openssl.conf en el directorio actual y asegúrese de que contenga las secciones “ca”, “CA_default”, “v3_ca” y “usr_cert”. Esas secciones deben incluir al menos la siguiente configuración:

[ ca ]
default_ca              = CA_default

[ CA_default ]
dir                     = /etc/ssl/sudo
certs                   = $dir/certs
database                = $dir/index.txt
certificate             = $dir/cacert.pem
serial                  = $dir/serial

[ v3_ca ]
subjectKeyIdentifier    = hash
authorityKeyIdentifier  = keyid:always,issuer
basicConstraints        = critical,CA:true
keyUsage                = cRLSign, keyCertSign

[ usr_cert ]
basicConstraints        = CA:FALSE
keyUsage                = nonRepudiation, digitalSignature, \
                          keyEncipherment
subjectKeyIdentifier    = hash
authorityKeyIdentifier  = keyid,issuer

Si su archivo openssl.conf ya tiene una sección “CA_default”, es posible que solo necesite modificar la configuración “dir” y habilitar la configuración “keyUsage” si está comentada.

Creación de la clave y el certificado de la CA

Para poder crear y firmar nuestros propios certificados, necesitamos crear una clave privada y un certificado para la raíz de la CA. Primero, cree la clave privada y protéjala con una frase de contraseña:

# openssl

NAME

sudo_logsrvd — sudo logging server

SYNOPSIS

sudo_logsrvd [ -d debuglevel ] [ -f confdir ] [ -h ] [ -V ]

DESCRIPTION

The sudo_logsrvd utility is a server process that runs on a central host and receives log messages from one or more sudo clients. It is typically configured to listen for connections over TLS.

The sudo server utility, sudoers.conf, can be configured to log to sudo_logsrvd over the network. This allows for centralized logging of sudo activity.

The sudo_logsrvd server supports logging in sudo.proto format, which is a binary format described in sudo_logsrv.proto(5). This is the default logging method when sudo.proto is enabled.

For TLS support, sudo_logsrvd uses OpenSSL. It expects the certificate authority (CA) certificate, the server's certificate, and the server's private key. The server's certificate must be signed by the CA.

Refer to sudo.conf(5) for details on how to configure sudo to log to sudo_logsrvd. Refer to sudo_logsrvd.conf(5) for details on how to configure sudo_logsrvd.

Arguments

-d debuglevel
Enable debugging messages for the specified debuglevel. This option is primarily for use when debugging sudo_logsrvd itself.
-f confdir
Specifies the directory containing the sudo_logsrvd.conf configuration file. The default is typically /etc/sudo_logsrvd.conf.
-h
Display a help message explaining all command-line options.
-V
Print the version number of sudo_logsrvd and exit.

FILES

/etc/sudo_logsrvd.conf
Configuration file for sudo_logsrvd.
/etc/sudo.conf
Configuration file for sudo clients.
/etc/ssl/sudo/cacert.pem
The certificate authority (CA) certificate file.
/etc/ssl/sudo/certs/logsrvd_cert.pem
The server's certificate file.
/etc/ssl/sudo/private/logsrvd_key.pem
The server's private key file.

EXAMPLES

This section provides an example of how to set up TLS for sudo_logsrvd.

Generating a self-signed CA

Create the necessary directory structure:

# mkdir -p /etc/ssl/sudo/{private,certs,csr}

Generate the root CA private key:

# openssl genrsa -aes256 -out private/cakey.pem 4096
# chmod 400 private/cakey.pem

Next, generate the root certificate, using appropriate values for the site-specific fields:

# openssl req -config openssl.cnf -key private/cakey.pem \
    -new -x509 -days 7300 -sha256 -extensions v3_ca \
    -out cacert.pem

Creating and signing certificates

The server and client certificates will be signed by the previously created root CA. Usually, the root CA is not used to sign server/client certificates directly. Instead, intermediate certificates are created and signed with the root CA and the intermediate certs are used to sign CSRs (Certificate Signing Request). In this example we'll skip this part for simplicity's sake and sign the CSRs with the root CA.

First, generate the private key without a pass phrase.

# openssl genrsa -out private/logsrvd_key.pem 2048
# chmod 400 private/logsrvd_key.pem

Next, create a certificate signing request (CSR) for the server's certificate. The organization name must match the name given in the root certificate. The common name should be either the server's IP address or a fully qualified domain name.

# openssl req -config openssl.cnf -key private/logsrvd_key.pem -new \
    -sha256 -out csr/logsrvd_csr.pem

To generate a client certificate, repeat the process above using a different file name.

Configuring sudo_logsrvd to use TLS

To use TLS for client/server communication, both sudo_logsrvd and the sudoers plugin need to be configured to use TLS. Configuring sudo_logsrvd for TLS requires the following settings, assuming the same path names used earlier:

# Listen on port 30344 for TLS connections to any address.
listen_address = *:30344(tls)

# Path to the certificate authority bundle file in PEM format.
tls_cacert = /etc/ssl/sudo/cacert.pem

# Path to the server's certificate file in PEM format.
tls_cert = /etc/ssl/sudo/certs/logsrvd_cert.pem

# Path to the server's private key file in PEM format.
tls_key = /etc/ssl/sudo/private/logsrvd_key.pem

The root CA cert (cacert.pem) must be installed on the system running sudo_logsrvd. If peer authentication is enabled on the client, a copy of cacert.pem must be present on the client system too.
