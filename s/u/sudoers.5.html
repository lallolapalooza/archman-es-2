SUDOERS(5) Manual de Formatos de Archivo SUDOERS(5)

NOMBRE

sudoers — plugin de seguridad de sudo por defecto

DESCRIPCIÓN

El plugin de política sudoers determina los privilegios sudo de un usuario. Es el plugin de política de sudo por defecto. La política se rige por el archivo /etc/sudoers o, opcionalmente, en LDAP. El formato de la política se describe en detalle en la sección FORMATO DEL ARCHIVO SUDOERS. Para obtener información sobre el almacenamiento de la información de la política de sudoers en LDAP, consulte sudoers.ldap(5).

Configuración de sudo.conf para sudoers

sudo consulta el archivo sudo.conf(5) para determinar qué plugins cargar. Si no existe ningún archivo sudo.conf(5), o si no contiene líneas Plugin, se utilizará sudoers para auditoría, decisiones de política y registro de E/S. Para configurar explícitamente sudo.conf(5) para usar el plugin sudoers, se puede usar la siguiente configuración.

Plugin sudoers_audit sudoers.so
Plugin sudoers_policy sudoers.so
Plugin sudoers_io sudoers.so

A partir de sudo 1.8.5, es posible especificar argumentos opcionales al plugin sudoers en el archivo sudo.conf(5). Los argumentos del plugin, si los hay, deben aparecer después de la ruta al plugin (es decir, después de sudoers.so). Los argumentos solo son efectivos para el plugin que abre (y analiza) el archivo sudoers.

Para sudo versión 1.9.1 y superior, este es el plugin sudoers_audit. Para versiones anteriores, es el plugin sudoers_policy. Se pueden especificar varios argumentos, separados por espacios en blanco. Por ejemplo:

Plugin sudoers_audit sudoers.so sudoers_mode=0400 error_recovery=false

Los siguientes argumentos de plugin son compatibles:

error_recovery=bool
El argumento error_recovery se puede usar para controlar si sudoers debe intentar recuperarse de errores de sintaxis en el archivo sudoers. Si se establece en true (el valor por defecto), sudoers intentará recuperarse de un error de sintaxis descartando la porción de la línea que contiene el error hasta el final de la línea. Un valor de false desactivará la recuperación de errores. Antes de la versión 1.9.3, no se realizaba recuperación de errores.
ignore_perms=bool
El argumento ignore_perms se puede usar para desactivar las comprobaciones de seguridad al cargar el archivo sudoers. Si está habilitado, el archivo sudoers se cargará independientemente del propietario o del modo del archivo. Este argumento está pensado para ser utilizado con fines de prueba y no debe habilitarse en sistemas de producción.
ldap_conf=ruta
El argumento ldap_conf se puede usar para anular la ruta por defecto al archivo ldap.conf.
ldap_secret=ruta
El argumento ldap_secret se puede usar para anular la ruta por defecto al archivo ldap.secret.
sudoers_file=ruta
El argumento sudoers_file se puede usar para anular la ruta por defecto al archivo sudoers.
sudoers_uid=id-usuario
El argumento sudoers_uid se puede usar para anular el propietario por defecto del archivo sudoers. Debe especificarse como un ID de usuario numérico.
sudoers_gid=id-grupo
El argumento sudoers_gid se puede usar para anular el grupo por defecto del archivo sudoers. Debe especificarse como un ID de grupo numérico (no un nombre de grupo).
sudoers_mode=modo
El argumento sudoers_mode se puede usar para anular el modo de archivo por defecto para el archivo sudoers. Debe especificarse como un valor octal.

Para más información sobre cómo configurar sudo.conf(5), consulte su manual.

Autenticación de Usuario

La política de seguridad sudoers requiere que la mayoría de los usuarios se autentiquen antes de poder usar sudo. No se requiere contraseña si el usuario que invoca es root, si el usuario de destino es el mismo que el usuario que invoca, o si la política ha desactivado la autenticación para el usuario o el comando. A diferencia de su(1), cuando sudoers requiere autenticación, valida las credenciales del usuario que invoca, no las del usuario de destino (o las de root). Esto se puede cambiar mediante las opciones rootpw, targetpw y runaspw, descritas más adelante.

Si un usuario que no está listado en la política intenta ejecutar un comando a través de sudo, se enviará un correo a las autoridades correspondientes. La dirección utilizada para dicho correo es configurable a través de la entrada de Valores Predeterminados mailto (descrita más adelante) y por defecto es root.

No se enviará correo si un usuario no autorizado intenta ejecutar sudo con la opción -l o -v, a menos que haya un error de autenticación y las opciones mail_always o mail_badpass estén habilitadas. Esto permite a los usuarios determinar por sí mismos si tienen permiso para usar sudo. Por defecto, todos los intentos de ejecutar sudo (exitosos o no) se registran, independientemente de si se envía correo o no.

Si sudo es ejecutado por root y la variable de entorno SUDO_USER está establecida, la política sudoers utilizará este valor para determinar quién es el usuario real. Esto puede ser utilizado por un usuario para registrar comandos a través de sudo incluso cuando se ha invocado un shell de root. También permite que la opción -e siga siendo útil incluso cuando se invoca a través de un script o programa ejecutado por sudo. Tenga en cuenta, sin embargo, que la búsqueda en el archivo sudoers todavía se realiza para root, no para el usuario especificado por SUDO_USER.

sudoers utiliza archivos de marca de tiempo por usuario para el almacenamiento en caché de credenciales. Una vez que un usuario ha sido autenticado, se escribe un registro que contiene el ID de usuario que se utilizó para autenticar, el ID de la sesión de terminal, la hora de inicio del líder de la sesión (o proceso padre) y una marca de tiempo (utilizando un reloj monótono si hay uno disponible). El usuario puede entonces usar sudo sin contraseña durante un corto período de tiempo (5 minutos, a menos que se anule con la opción timestamp_timeout). Por defecto, sudoers utiliza un registro separado para cada terminal, lo que significa que las sesiones de inicio de sesión de un usuario se autentican por separado. La opción timestamp_type se puede utilizar para seleccionar el tipo de registro de marca de tiempo que utilizará sudoers.

La utilidad tsdump, incluida en la distribución fuente de sudo, se puede utilizar para mostrar el contenido de un archivo de marca de tiempo. Consulte sudoers_timestamp(5) para obtener detalles sobre el formato del archivo de marca de tiempo.

Entorno del comando

Dado que las variables de entorno pueden influir en el comportamiento del programa, sudoers proporciona un medio para restringir qué variables del entorno del usuario se heredan por el comando que se va a ejecutar. Hay dos formas distintas en que sudoers puede tratar las variables de entorno.

Por defecto, la bandera env_reset está habilitada. Esto hace que los comandos se ejecuten con un entorno nuevo y mínimo. En AIX (y sistemas Linux sin PAM), el entorno se inicializa con el contenido del archivo /etc/environment. Las variables de entorno HOME, MAIL, SHELL, LOGNAME y USER se inicializan basándose en el usuario de destino y las variables SUDO_* se establecen basándose en el usuario que invoca. Variables adicionales, como DISPLAY, PATH y TERM, se conservan del entorno del usuario que invoca si lo permiten las opciones env_check o env_keep. Algunas variables de entorno se tratan de forma especial. Si las variables PATH y TERM no se conservan del entorno del usuario, se establecerán en valores predeterminados. LOGNAME y USER se manejan como una unidad. Si uno de ellos se conserva (o se elimina) del entorno del usuario, el otro también lo hará. Si LOGNAME y USER se van a conservar pero solo uno de ellos está presente en el entorno del usuario, el otro se establecerá en el mismo valor. Esto evita un entorno inconsistente donde una de las variables que describe el nombre de usuario se establece en el usuario que invoca y otra se establece en el usuario de destino. Las variables de entorno con un valor que comienza con ‘()’ se eliminan a menos que tanto el nombre como el valor coincidan con env_keep o env_check, ya que pueden ser interpretadas como funciones por el shell bash. Antes de la versión 1.8.11, tales variables siempre se eliminaban.

Si, sin embargo, la bandera env_reset está deshabilitada, cualquier variable no denegada explícitamente por las opciones env_check y env_delete está permitida y sus valores se heredan del proceso que invoca. Antes de la versión 1.8.21, las variables de entorno con un valor que comienza con ‘()’ siempre se eliminaban. A partir de la versión 1.8.21, se utiliza un patrón en env_delete para que coincida con las funciones del shell bash en su lugar. Dado que no es posible bloquear todas las variables de entorno potencialmente peligrosas, se recomienda el uso del comportamiento predeterminado env_reset.

Las variables de entorno especificadas por env_check, env_delete o env_keep pueden incluir uno o más caracteres ‘*’ que coincidirán con cero o más caracteres. No se admiten otros caracteres comodín.

Por defecto, las variables de entorno se comparan por nombre. Sin embargo, si el patrón incluye un signo igual (‘=’), tanto el nombre como el valor de la variable deben coincidir. Por ejemplo, una función del shell bash se puede hacer coincidir de la siguiente manera:

env_keep += "BASH_FUNC_my_func%%=()*"

Sin el sufijo ‘=()*’, esto no coincidiría, ya que las funciones del shell bash no se conservan por defecto.

La lista completa de variables de entorno que se conservan o eliminan, tal como la modifican los parámetros globales de Defaults en sudoers, se muestra cuando sudo es ejecutado por root con la opción -V. La lista de variables de entorno a eliminar varía según el sistema operativo en el que se ejecute sudo.

Otras configuraciones pueden influir en el entorno del comando:

  • sudoers opciones como always_set_home, secure_path, set_logname, set_home, y setenv.
  • Etiquetas de comando, como SETENV y NOSETENV. Tenga en cuenta que SETENV se implica si el comando que coincide es ALL.
  • Opciones de sudo, como -E y -i.

En sistemas que admiten PAM donde el módulo pam_env está habilitado para sudo, las variables en el entorno PAM pueden fusionarse en el entorno. Si una variable en el entorno PAM ya está presente en el entorno del usuario, el valor solo se anulará si la variable no fue conservada por sudoers. Cuando env_reset está habilitado, las variables conservadas del entorno del usuario que invoca por la lista env_keep tienen prioridad sobre las del entorno PAM. Cuando env_reset está deshabilitado, las variables presentes en el entorno del usuario que invoca tienen prioridad sobre las del entorno PAM a menos que coincidan con un patrón en la lista env_delete.

El enlazador dinámico en la mayoría de los sistemas operativos eliminará las variables que pueden controlar el enlazado dinámico del entorno de los ejecutables con conjunto de ID de usuario, incluido sudo. Dependiendo del sistema operativo, esto puede incluir _RLD*, DYLD_*, LD_*, LDR_*, LIBPATH, SHLIB_PATH y otros. Estos tipos de variables se eliminan del entorno antes de que sudo comience siquiera la ejecución y, como tales, no es posible que sudo las conserve.

Como caso especial, si se especifica la opción -i (inicio de sesión inicial), sudoers inicializará el entorno independientemente del valor de env_reset. Las variables DISPLAY, PATH y TERM permanecen sin cambios; HOME, MAIL, SHELL, USER y LOGNAME se establecen basándose en el usuario de destino. En AIX (y sistemas Linux sin PAM), el contenido de /etc/environment también se incluye. Todas las demás variables de entorno se eliminan a menos que lo permita env_keep o env_check, descritas anteriormente.

Finalmente, se aplican los archivos restricted_env_file y env_file, si están presentes. Las variables en restricted_env_file se aplican primero y están sujetas a las mismas restricciones que el entorno del usuario que invoca, como se detalla anteriormente. Las variables en env_file se aplican al final y no están sujetas a estas restricciones. En ambos casos, las variables presentes en los archivos solo se establecerán en sus valores especificados si no entraran en conflicto con una variable de entorno existente.

FORMATO DEL ARCHIVO SUDOERS

El archivo sudoers se compone de dos tipos de entradas: alias (básicamente variables) y especificaciones de usuario (que especifican quién puede ejecutar qué).

Cuando múltiples entradas coinciden para un usuario, se aplican en orden. Donde hay múltiples coincidencias, se utiliza la última coincidencia (que no es necesariamente la coincidencia más específica).

La gramática del archivo sudoers se describirá a continuación en Forma Extendida de Backus-Naur (EBNF). No te desesperes si no estás familiarizado con EBNF; es bastante simple y las definiciones a continuación están anotadas.

Límites de recursos

Por defecto, sudoers utiliza el método nativo del sistema operativo para establecer límites de recursos para el usuario de destino. En sistemas Linux, los límites de recursos suelen establecerse mediante el módulo PAM pam_limits.so. En algunos sistemas BSD, el archivo /etc/login.conf especifica los límites de recursos para el usuario. En sistemas AIX, los límites de recursos se configuran en el archivo /etc/security/limits. Si no hay un mecanismo del sistema para establecer límites de recursos por usuario, el comando se ejecutará con los mismos límites que el usuario que lo invoca. La única excepción es el tamaño del archivo de volcado central, que sudoers establece en 0 por defecto. Deshabilitar los volcados centrales por defecto hace posible evitar posibles problemas de seguridad en los que el archivo central se trata como entrada confiable.

Los límites de recursos también pueden establecerse en el propio archivo sudoers, en cuyo caso anulan los establecidos por el sistema. Consulte rlimit_as, rlimit_core, rlimit_cpu y rlimit_data para ver una lista de los límites de recursos que se pueden establecer en sudoers.

">rlimit_cpu, rlimit_data, rlimit_fsize, rlimit_locks, rlimit_memlock, rlimit_nofile, rlimit_nproc, rlimit_rss, rlimit_stack opciones descritas a continuación. Los límites de recursos en sudoers pueden especificarse en uno de los siguientes formatos:

“valor”
Tanto el límite de recursos blando como el duro se establecen al mismo valor. El valor especial “infinito” puede usarse para indicar que el valor es ilimitado.
“suave,duro”
Dos valores separados por comas. El límite suave se establece al primer valor y el límite duro se establece al segundo. Ambos valores deben estar encerrados entre comillas dobles, o la coma debe escaparse con una barra invertida (‘\’). El valor especial “infinito” puede usarse en lugar de cualquiera de los valores.
“predeterminado”
Se utilizará el límite de recursos predeterminado para el usuario. Este puede ser un valor específico del usuario (ver arriba) o el valor del límite de recursos cuando sudo se invocó para sistemas que no admiten límites por usuario.
“usuario”
Se conservarán los límites de recursos del usuario que invoca al ejecutar el comando.

Por ejemplo, para restaurar el comportamiento histórico del tamaño del archivo de volcado central, se puede usar una línea como la siguiente.

Defaults rlimit_core=default

Los límites de recursos en sudoers solo son compatibles con la versión 1.8.7 o superior.

Guía rápida de EBNF

EBNF es una forma concisa y exacta de describir la gramática de un idioma. Cada definición de EBNF está compuesta por reglas de producción. Por ejemplo:

símbolo ::= definición | alternativa1 | alternativa2 ...

Cada regla de producción hace referencia a otras y, por lo tanto, conforma una gramática para el idioma. EBNF también contiene los siguientes operadores, que muchos lectores reconocerán de las expresiones regulares. Sin embargo, no los confunda con caracteres de "comodín", que tienen significados diferentes.

?
Significa que el símbolo (o grupo de símbolos) anterior es opcional. Es decir, puede aparecer una vez o ninguna.
*
Significa que el símbolo (o grupo de símbolos) anterior puede aparecer cero o más veces.
+
Significa que el símbolo (o grupo de símbolos) anterior puede aparecer una o más veces.

Los paréntesis pueden usarse para agrupar símbolos. Para mayor claridad, usaremos comillas simples ('') para designar lo que es una cadena de caracteres literal (en contraposición a un nombre de símbolo).

Alias

Hay cuatro tipos de alias: User_Alias, Runas_Alias, Host_Alias y Cmnd_Alias. A partir de sudo 1.9.0, Cmd_Alias puede usarse en lugar de Cmnd_Alias si se desea.

Alias ::= 'User_Alias'  User_Alias_Spec (':' User_Alias_Spec)* |
          'Runas_Alias' Runas_Alias_Spec (':' Runas_Alias_Spec)* |
          'Host_Alias'  Host_Alias_Spec (':' Host_Alias_Spec)* |
          'Cmnd_Alias'  Cmnd_Alias_Spec (':' Cmnd_Alias_Spec)* |
          'Cmd_Alias'   Cmnd_Alias_Spec (':' Cmnd_Alias_Spec)*

NombreAlias ::= [A–Z]([A–Z][0–9]_)*

User_Alias_Spec ::= NombreAlias '=' User_List

Runas_Alias ::= NombreAlias

Runas_Alias_Spec ::= Runas_Alias '=' Runas_List

Host_Alias ::= NombreAlias

Host_Alias_Spec ::= Host_Alias '=' Host_List

Cmnd_Alias ::= NombreAlias

Cmnd_Alias_Spec ::= Cmnd_Alias '=' Cmnd_List

Cada definición de alias tiene la forma

TipoAlias Nombre = item1, item2, ...

donde TipoAlias es uno de User_Alias, Runas_Alias, Host_Alias, o Cmnd_Alias. Un Nombre es una cadena de letras mayúsculas, números y caracteres de subrayado (‘_’). Un Nombre debe comenzar con una letra mayúscula. Es posible poner varias definiciones de alias del mismo tipo en una sola línea, unidas por dos puntos (‘:’). Por ejemplo:

TipoAlias Nombre = item1, item2, item3 : Nombre = item4, item5

Es un error de sintaxis redefinir un alias existente. Es posible usar el mismo nombre para alias de diferentes tipos, pero no se recomienda.

Las definiciones de lo que constituye un miembro de alias válido son las siguientes.

User_List ::= Usuario |
              Usuario ',' User_List

Usuario ::= '!'* nombre de usuario |
            '!'* #id-de-usuario |
            '!'* %grupo |
            '!'* %#id-de-grupo |
            '!'* +netgroup |
            '!'* %:grupo_no_unix |
            '!'* %:#gid_no_unix |
            '!'* User_Alias

Una User_List está compuesta por uno o más nombres de usuario, IDs de usuario (precedidos por ‘#’), nombres y IDs de grupo del sistema (precedidos por ‘%’ y ‘%#’ respectivamente), netgroups (precedidos por ‘+’), nombres y IDs de grupo no Unix (precedidos por ‘%:’ y ‘%:#’ respectivamente) y User_Aliases. Cada elemento de la lista puede ir precedido por cero o más operadores ‘!’. Un número impar de operadores ‘!’ niega el valor del elemento; un número par simplemente se cancelan entre sí. Los netgroups de usuarios se comparan usando solo los miembros de usuario y dominio; el miembro de host no se utiliza al comparar.

Un nombre de usuario, id-de-usuario, grupo, id-de-grupo, netgroup, grupo_no_unix o gid_no_unix pueden estar encerrados entre comillas dobles para evitar la necesidad de escapar caracteres especiales. Alternativamente, los caracteres especiales pueden especificarse en modo hexadecimal escapado, por ejemplo, \x20 para espacio. Al usar comillas dobles, cualquier carácter de prefijo debe incluirse dentro de las comillas.

La sintaxis real de grupo_no_unix y gid_no_unix depende del plugin del proveedor de grupo subyacente. Por ejemplo, el plugin QAS AD admite los siguientes formatos:

  • Grupo en el mismo dominio: "%:Nombre Grupo"
  • Grupo en cualquier dominio: "%:Nombre Grupo@DOMINIO.COMPLETO.CALIFICADO"
  • SID de grupo: "%:S-1-2-34-5678901234-5678901234-5678901234-567"

Consulte PLUGINS DE PROVEEDOR DE GRUPOS para más información.

Las comillas alrededor de los nombres de grupo son opcionales. Las cadenas sin comillas deben usar una barra invertida (‘\’) para escapar espacios y caracteres especiales. Consulte Otros caracteres especiales y palabras reservadas para obtener una lista de caracteres que deben escaparse.

Runas_List ::= MiembroRunas |
               MiembroRunas ',' Runas_List

MiembroRunas ::= '!'* nombre de usuario |
                 '!'* #id-de-usuario |
                 '!'* %grupo |
                 '!'* %#id-de-grupo |
                 '!'* %:grupo_no_unix |
                 '!'* %:#gid_no_unix |
                 '!'* +netgroup |
                 '!'* Runas_Alias |
                 '!'* ALL

Una Runas_List es similar a una User_List excepto que en lugar de User_Aliases puede contener Runas_Aliases. Los nombres de usuario y grupos se comparan como cadenas. En otras palabras, dos usuarios (grupos) con el mismo ID de usuario (grupo) se consideran distintos. Si desea comparar todos los nombres de usuario con el mismo ID de usuario (por ejemplo, root y toor), puede usar un ID de usuario en lugar de un nombre (#0 en el ejemplo dado). El ID de usuario o ID de grupo especificado en un MiembroRunas no necesita estar listado en la base de datos de contraseñas o grupos.

Host_List ::= Host |
              Host ',' Host_List

Host ::= '!'* nombre de host |
         '!'* dir_ip |
         '!'* red(/máscara-red)? |
         '!'* +netgroup |
         '!'* Host_Alias |
         '!'* ALL

Una Host_List está compuesta por uno o más nombres de host, direcciones IP, números de red, netgroups (precedidos por ‘+’) y otros alias. Nuevamente, el valor de un elemento puede ser negado con el operador ‘!’. Los netgroups de host se comparan usando solo los miembros de host (tanto calificados como no calificados) y dominio; el miembro de usuario no se utiliza al comparar. Si especifica un número de red sin una máscara de red, sudo consultará cada una de las interfaces de red del host local y, si el número de red corresponde a una de las interfaces de red del host, usará la máscara de red de esa interfaz. La máscara de red puede especificarse en notación estándar de dirección IP (por ejemplo, 255.255.255.0 o ffff:ffff:ffff:ffff::), o en notación CIDR (número de bits, por ejemplo, 24 o 64). Un nombre de host puede incluir comodines de estilo shell (consulte la sección Comodines a continuación), pero a menos que el comando hostname en su máquina devuelva el nombre de host completamente calificado, necesitará usar la bandera fqdn para que los comodines sean útiles. sudo solo inspecciona las interfaces de red reales; esto significa que la dirección IP 127.0.0.1

(localhost) nunca coincidirá. Además, el nombre de host "localhost" solo coincidirá si ese es el nombre de host real, lo que generalmente solo ocurre en sistemas no conectados a la red.

digest ::= [A-Fa-f0-9]+ |
           [A-Za-z0-9+/=]+

Digest_Spec ::= "sha224" ':' digest |

Digest_List ::= Digest_Spec |

Cmnd ::= Digest_List? '!'* command |
         '!'* directory |
         '!'* Edit_Spec |
         '!'* List_Spec |

Una Cmnd_List es una lista de uno o más comandos, directorios o alias. Un comando es un nombre de archivo completamente calificado, que puede incluir comodines al estilo shell (ver la sección Wildcards más abajo), o una expresión regular que comienza con '^' y termina con '$' (ver la sección Regular expressions más abajo). Un directorio es un nombre de ruta completamente calificado que termina en '/'. Cuando se especifica un directorio en una Cmnd_List, el usuario podrá ejecutar cualquier archivo dentro de ese directorio (pero no en ningún subdirectorio dentro de él). Si no se especifican argumentos de línea de comandos, el usuario puede ejecutar el comando con los argumentos que elija. Los argumentos de línea de comandos pueden incluir comodines o ser una expresión regular que comienza con '^' y termina con '$'. Si los argumentos de línea de comandos consisten en '""', el comando solo se puede ejecutar con ningún argumento.

Si un Cmnd tiene argumentos de línea de comandos asociados, los argumentos en el Cmnd deben coincidir con los proporcionados por el usuario en la línea de comandos. Si los argumentos en un Cmnd comienzan con el carácter '^', se interpretarán como una expresión regular y coincidirán en consecuencia. De lo contrario, se utilizan comodines al estilo shell al coincidir. A menos que se especifique una expresión regular, los siguientes caracteres deben ser escapados con un '\' si se utilizan en los argumentos del comando: ',', ':', '=', '\'. Para evitar que los argumentos en un Cmnd que comienzan con un carácter '^' se interpreten como una expresión regular, el '^' debe ser escapado con un '\'.

Hay dos comandos integrados en sudo: "list" y "sudoedit". A diferencia de otros comandos, estos dos deben especificarse en el archivo sudoers sin una ruta inicial.

El "list" integrado se puede usar para permitir que un usuario liste los privilegios de otro usuario con la opción -U de sudo. Por ejemplo, "sudo -l -U otro_usuario". Un usuario con el privilegio "list" puede listar los privilegios de otro usuario incluso si no tiene permiso para ejecutar comandos como ese usuario. Por defecto, solo root o un usuario con la capacidad de ejecutar cualquier comando como root o como el usuario especificado en el host actual puede usar la opción -U. No se pueden especificar argumentos de línea de comandos con el comando integrado "list".

El "sudoedit" integrado se utiliza para permitir que un usuario ejecute sudo con la opción -e (o como sudoedit). Puede tomar argumentos de línea de comandos al igual que un comando normal. A diferencia de otros comandos, "sudoedit" está integrado en sudo y debe especificarse en el archivo sudoers sin una ruta inicial. Si hay una ruta inicial, por ejemplo /usr/bin/sudoedit, el nombre de la ruta se convertirá silenciosamente a "sudoedit". Una ruta completamente calificada para sudoedit es tratada como un error por visudo.

Un command puede ser precedido por una Digest_List, una lista separada por comas de una o más entradas Digest_Spec. Si está presente una Digest_List, el comando solo coincidirá con éxito si se puede verificar utilizando uno de los resúmenes SHA-2 de la lista. A partir de la versión 1.9.0, la palabra reservada ALL se puede usar junto con una Digest_List. Los siguientes formatos de resumen son soportados: sha224, sha256, sha384 y sha512. La cadena se puede especificar en formato hexadecimal o base64 (base64 es más compacto). Hay varias utilidades capaces de generar resúmenes SHA-2 en formato hexadecimal, como openssl, shasum, sha224sum, sha256sum, sha384sum, sha512sum.

Por ejemplo, usando openssl:

$ openssl dgst -sha224 /bin/ls
SHA224(/bin/ls)= 118187da8364d490b4a7debbf483004e8f3e053ec954309de2c41a25

También es posible usar openssl para generar salida base64:

$ openssl dgst -binary -sha224 /bin/ls | openssl base64
EYGH2oNk1JC0p9679IMATo8+BT7JVDCd4sQaJQ==

Advertencia: si el usuario tiene acceso de escritura al comando en sí (directa o a través de un comando sudo), el usuario puede reemplazar el comando después de que se haya realizado la verificación del resumen, pero antes de que se ejecute el comando. Una condición de carrera similar existe en sistemas que carecen de la llamada al sistema fexecve(2) cuando el directorio en el que se encuentra el comando es escribible por el usuario. Consulte la descripción de la configuración fdexec para obtener más información sobre cómo sudo ejecuta comandos que tienen un resumen asociado.

Los resúmenes de comandos solo son compatibles con la versión 1.8.7 o superior.

Defaults

Ciertas opciones de configuración se pueden cambiar de sus valores predeterminados en tiempo de ejecución a través de una o más líneas Default_Entry. Estas pueden afectar a todos los usuarios en cualquier host ('Defaults'), a todos los usuarios en un host específico ('Defaults@host'), a un usuario específico ('Defaults:user'), a un comando específico ('Defaults!cmnd'), o a comandos que se ejecutan como un usuario específico ('Defaults>runasuser').

No se permite espacio en blanco entre 'Defaults' y los caracteres '@', ':', '!', o '>'. Si bien se puede usar una lista separada por comas en lugar de un solo valor después del carácter '@', ':', '!' o '>', usar un alias en lugar de una lista a menudo mejora la legibilidad. Las entradas específicas de comando no pueden incluir argumentos de línea de comandos. Si necesita especificar argumentos, defina un Cmnd_Alias y refiérase a él en su lugar.

Default_Type ::= 'Defaults' |
                 'Defaults@' Host_List |
                 'Defaults:' User_List |
                 'Defaults!' Cmnd_List |
                 'Defaults>' Runas_List

Default_Entry ::= Default_Type Parameter_List

Parameter_List ::= Parameter |
                   Parameter ',' Parameter_List

Parameter ::= Parameter '=' Value |
              Parameter '+=' Value |
              Parameter '-=' Value |
              '!'* Parameter

Los parámetros pueden ser flags, valores integer, strings o lists. Los flags son implícitamente booleanos y se pueden desactivar mediante el operador '!'. Algunos parámetros enteros, de cadena y de lista también se pueden usar en un contexto booleano para deshabilitarlos. Los valores pueden estar encerrados entre comillas dobles ("") cuando contienen varias palabras. Los caracteres especiales se pueden escapar con una barra invertida ('\').

Para incluir un carácter de barra invertida literal en un argumento de línea de comandos, debe escapar la barra invertida dos veces. Por ejemplo, para coincidir con '\n' como parte de un argumento de línea de comandos, debe usar '\\n' en el archivo sudoers. Esto se debe a que hay dos niveles de escape, uno en el propio analizador de sudoers y otro cuando los argumentos de línea de comandos son emparejados por la función fnmatch(3) o regexec(3).

Las listas tienen dos operadores de asignación adicionales, '+=' y '-='. Estos operadores se utilizan para añadir y eliminar de una lista respectivamente. No es un error usar el operador '-=' para eliminar un elemento que no existe en una lista.

En general, la configuración de Defaults se aplica en orden, las entradas posteriores anulan las anteriores. Sin embargo, la configuración de Defaults específica del comando se aplica más tarde, una vez que se conoce la ruta del comando. Además, la siguiente configuración de Defaults debe aplicarse antes que todas las demás, ya que puede afectar a las entradas posteriores: fqdn, group_plugin, ignore_unknown_defaults, match_group_by_gid, runas_default, sudoers_locale.

Consulte SUDOERS OPTIONS para ver una lista de parámetros de Defaults compatibles.

User_Spec ::= User_List Host_List '=' Cmnd_Spec_List \
              (':' Host_List '=' Cmnd_Spec_List)*

Cmnd_Spec_List ::= Cmnd_Spec |
                   Cmnd_Spec ',' Cmnd_Spec_List

Cmnd_Spec ::= Runas_Spec? Option_Spec* (Tag_Spec ':')* Cmnd

Runas_Spec ::= '(' Runas_List? (':' Runas_List)? ')'

Option_Spec ::= (Date_Spec | Timeout_Spec | Chdir_Spec | Chroot_Spec)

Date_Spec ::= ('NOTBEFORE=timestamp' | 'NOTAFTER=timestamp')

Timeout_Spec ::= 'TIMEOUT=timeout'

Chdir_Spec ::= 'CWD=directory'

Chroot_Spec ::= 'CHROOT=directory'

Tag_Spec ::= ('EXEC' | 'NOEXEC' | 'FOLLOW' | 'NOFOLLOW' |
              'LOG_INPUT' | 'NOLOG_INPUT' | 'LOG_OUTPUT' |
              'NOLOG_OUTPUT' | 'MAIL' | 'NOMAIL' | 'INTERCEPT' |
              'NOINTERCEPT' | 'PASSWD' | 'NOPASSWD' | 'SETENV' |
              'NOSETENV')

Una especificación de usuario determina qué comandos puede ejecutar un usuario (y como qué usuario) en hosts especificados. Por defecto, los comandos se ejecutan como root (a menos que runas_default se haya establecido en un valor diferente), pero esto también se puede cambiar por comando.

La estructura básica de una especificación de usuario es "quién dónde = (como_quién) qué". Desglosemos esto en sus partes constituyentes:

Runas_Spec

Un Runas_Spec determina el usuario y/o el grupo como los que se puede ejecutar un comando. Un Runas_Spec completamente especificado consta de dos Runas_Lists (como se define anteriormente) separados por dos puntos (‘:’) y encerrados entre paréntesis. El primer Runas_List indica como qué usuarios se puede ejecutar el comando a través de la opción -u. El segundo define una lista de grupos que se pueden especificar a través de la opción -g (además de cualquiera de los grupos del usuario de destino). Si se especifican ambos Runas_Lists, el comando se puede ejecutar con cualquier combinación de usuarios y grupos listados en sus respectivos Runas_Lists. Si solo se especifica el primero, el comando se puede ejecutar como cualquier usuario de la lista y, opcionalmente, con cualquier grupo al que pertenezca el usuario de destino. Si el primer Runas_List está vacío pero se especifica el segundo, el comando se puede ejecutar como el usuario que invoca con el grupo establecido en cualquiera de los listados en el Runas_List. Si ambos Runas_Lists están vacíos, el comando solo se puede ejecutar como el usuario que invoca y el grupo, si se especifica, debe ser uno del que el usuario que invoca sea miembro. Si no se especifica ningún Runas_Spec, el comando solo se puede ejecutar como el usuario runas_default (root por defecto) y el grupo, si se especifica, debe ser uno del que el usuario runas_default sea miembro.

Un Runas_Spec establece el valor predeterminado para los comandos que le siguen. Lo que esto significa es que para la entrada:

dgb	boulder = (operator) /bin/ls, /bin/kill, /usr/bin/lprm

El usuario dgb puede ejecutar /bin/ls, /bin/kill y /usr/bin/lprm en el host boulder — pero solo como operator. Por ejemplo:

$ sudo -u operator /bin/ls

También es posible anular un Runas_Spec más adelante en una entrada. Si modificamos la entrada de la siguiente manera:

dgb	boulder = (operator) /bin/ls, (root) /bin/kill, /usr/bin/lprm

Entonces el usuario dgb ahora tiene permitido ejecutar /bin/ls como operator, pero /bin/kill y /usr/bin/lprm como root.

Podemos extender esto para permitir que dgb ejecute /bin/ls con el usuario o el grupo establecido en operator:

dgb	boulder = (operator : operator) /bin/ls, (root) /bin/kill,\
	/usr/bin/lprm

Mientras que la porción de grupo del Runas_Spec permite al usuario ejecutarse con ese grupo, no lo obliga a hacerlo. Si no se especifica ningún grupo en la línea de comandos, el comando se ejecutará con el grupo listado en la entrada de la base de datos de contraseñas del usuario de destino. Todas las siguientes serían permitidas por la entrada de sudoers anterior:

$ sudo -u operator /bin/ls
$ sudo -u operator -g operator /bin/ls
$ sudo -g operator /bin/ls

En el siguiente ejemplo, el usuario tcm puede ejecutar comandos que acceden a un archivo de dispositivo de módem con el grupo dialer.

tcm	boulder = (:dialer) /usr/bin/tip, /usr/bin/cu,\
	/usr/local/bin/minicom

En este ejemplo, solo se establecerá el grupo, el comando aún se ejecuta como el usuario tcm. Por ejemplo:

$ sudo -g dialer /usr/bin/cu

Múltiples usuarios y grupos pueden estar presentes en un Runas_Spec, en cuyo caso el usuario puede seleccionar cualquier combinación de usuarios y grupos a través de las opciones -u y -g. En este ejemplo:

alan	ALL = (root, bin : operator, system) ALL

el usuario alan puede ejecutar cualquier comando como el usuario root o bin, estableciendo opcionalmente el grupo a operator o system.

Option_Spec

Un Cmnd puede tener cero o más opciones asociadas. Las opciones pueden consistir en fechas de inicio y/o fin y tiempos de espera de comando. Una vez que se establece una opción para un Cmnd, los Cmnds subsiguientes en el Cmnd_Spec_List heredan esa opción a menos que sea anulada por otra opción. Los nombres de las opciones son palabras reservadas en sudoers. Esto significa que ninguno de los nombres de opciones válidos (ver más abajo) se puede utilizar al declarar un alias.

Date_Spec

Las reglas de sudoers se pueden especificar con una fecha de inicio y fin a través de la configuración NOTBEFORE y NOTAFTER. La marca de tiempo debe especificarse en "Tiempo Generalizado" según lo definido por RFC 4517. El formato es efectivamente 'yyyymmddHHMMSSZ' donde los minutos y segundos son opcionales. El sufijo 'Z' indica que la marca de tiempo está en Tiempo Universal Coordinado (UTC). También es posible especificar un desfase de zona horaria de UTC en horas y minutos en lugar de una 'Z'. Por ejemplo, '-0500' correspondería a la hora estándar del este en los EE. UU. Como una extensión, si no se especifica 'Z' ni un desfase de zona horaria, se utilizará la hora local.

Las siguientes son todas marcas de tiempo válidas:

20170214083000Z
2017021408Z
20160315220000-0500
20151201235900

Timeout_Spec

Un comando puede tener un tiempo de espera asociado. Si el tiempo de espera expira antes de que el comando haya terminado, el comando será terminado. El tiempo de espera se puede especificar en combinaciones de días, horas, minutos y segundos con un sufijo de una sola letra insensible a mayúsculas y minúsculas que indica la unidad de tiempo. Por ejemplo, un tiempo de espera de 7 días, 8 horas, 30 minutos y 10 segundos se escribiría como '7d8h30m10s'. Si se especifica un número sin una unidad, se asumen segundos. Se pueden omitir cualquiera de los días, minutos, horas o segundos. El orden debe ser de la unidad más grande a la más pequeña y una unidad no se puede especificar más de una vez.

Los siguientes son todos valores de tiempo de espera válidos: '7d8h30m10s', '14d', '8h30m', '600s', '3600'. Los siguientes son valores de tiempo de espera inválidos: '12m2w1d', '30s10m4h', '1d2d3h'.

Esta configuración solo es compatible con la versión 1.8.20 o posterior.

Chdir_Spec

El directorio de trabajo en el que se ejecutará el comando se puede especificar utilizando la configuración CWD. El directorio debe ser un nombre de ruta completamente calificado que comience con un carácter '/' o '~', o el valor especial "*" . Un valor de "*" indica que el usuario puede especificar el directorio de trabajo ejecutando sudo con la opción -D. Por defecto, los comandos se ejecutan desde el directorio de trabajo actual del usuario que invoca, a menos que se proporcione la opción -i. Los nombres de ruta del tipo ~usuario/ruta/nombre se interpretan como relativos al directorio de inicio del usuario especificado. Si se omite el nombre de usuario, la ruta será relativa al directorio de inicio del usuario que se ejecuta.

Esta configuración solo es compatible con la versión 1.9.3 o posterior.

Chroot_Spec

La compatibilidad con el establecimiento del directorio raíz está obsoleta y se eliminará en una versión futura de sudo.

El directorio raíz en el que se ejecutará el comando se puede especificar utilizando la configuración CHROOT. El directorio debe ser un nombre de ruta completamente calificado que comience con un carácter '/' o '~', o el valor especial "*". Un valor de "*" indica que el usuario puede especificar el directorio raíz ejecutando sudo con la opción -R. Esta configuración se puede utilizar para ejecutar el comando en una "sandbox" de chroot(2) similar a la utilidad chroot(8). Los nombres de ruta del tipo ~usuario/ruta/nombre se interpretan como relativos al directorio de inicio del usuario especificado. Si se omite el nombre de usuario, la ruta será relativa al directorio de inicio del usuario que se ejecuta.

Esta configuración solo es compatible con la versi

en 1.9.3 o superior.

Tag_Spec

Un comando puede tener cero o más etiquetas asociadas. Los siguientes valores de etiqueta son compatibles: EXEC, NOEXEC, FOLLOW, NOFOLLOW, LOG_INPUT, NOLOG_INPUT, LOG_OUTPUT, NOLOG_OUTPUT, MAIL, NOMAIL, INTERCEPT, NOINTERCEPT, PASSWD, NOPASSWD, SETENV, y NOSETENV. Una vez que una etiqueta se establece en un Cmnd, los siguientes Cmnds en la Cmnd_Spec_List, heredan la etiqueta a menos que sea anulada por la etiqueta opuesta (en otras palabras, PASSWD anula NOPASSWD y NOEXEC anula EXEC).

EXEC y NOEXEC

Si sudo ha sido compilado con soporte noexec y el sistema operativo subyacente lo soporta, la etiqueta NOEXEC se puede utilizar para evitar que un ejecutable enlazado dinámicamente ejecute comandos adicionales por sí mismo.

En el siguiente ejemplo, el usuario aaron puede ejecutar /usr/bin/more y /usr/bin/vi en el host shanty, pero los escapes de shell se deshabilitarán.

aaron	shanty = NOEXEC: /usr/bin/more, /usr/bin/vi

Vea la sección Prevenir escapes de shell más abajo para más detalles sobre cómo funciona NOEXEC y si funcionará o no en su sistema.

FOLLOW y NOFOLLOW

A partir de la versión 1.8.15, sudoedit no abrirá un archivo que sea un enlace simbólico a menos que el flag sudoedit_follow esté habilitado. Las etiquetas FOLLOW y NOFOLLOW anulan el valor de sudoedit_follow y pueden ser usadas para permitir (o denegar) la edición de enlaces simbólicos de forma individual por comando. Estas etiquetas solo son efectivas para el comando sudoedit y son ignoradas para todos los demás comandos.

LOG_INPUT y NOLOG_INPUT

Estas etiquetas anulan el valor del flag log_input de forma individual por comando. Para más información, vea REGISTRO DE E/S.

LOG_OUTPUT y NOLOG_OUTPUT

Estas etiquetas anulan el valor del flag log_output de forma individual por comando. Para más información, vea REGISTRO DE E/S.

MAIL y NOMAIL

Estas etiquetas proporcionan un control detallado sobre si se enviará correo cuando un usuario ejecuta un comando, anulando el valor del flag mail_all_cmnds de forma individual por comando. No tienen efecto cuando sudo se ejecuta con las opciones -l o -v. Una etiqueta NOMAIL también anulará las opciones mail_always y mail_no_perms. Para más información, vea las descripciones de mail_all_cmnds, mail_always, y mail_no_perms en la sección OPCIONES DE SUDOERS más abajo.

PASSWD y NOPASSWD

Por defecto, sudo requiere que un usuario se autentifique antes de ejecutar un comando. Este comportamiento se puede modificar mediante la etiqueta NOPASSWD. Al igual que un Runas_Spec, la etiqueta NOPASSWD establece un valor predeterminado para los comandos que la siguen en la Cmnd_Spec_List. Por el contrario, la etiqueta PASSWD se puede usar para invertir las cosas. Por ejemplo:

ray	rushmore = NOPASSWD: /bin/kill, /bin/ls, /usr/bin/lprm

permitiría al usuario ray ejecutar /bin/kill, /bin/ls, y /usr/bin/lprm como root en la máquina "rushmore" sin autenticarse. Si solo queremos que ray pueda ejecutar /bin/kill sin contraseña, la entrada sería:

ray	rushmore = NOPASSWD: /bin/kill, PASSWD: /bin/ls, /usr/bin/lprm

Sin embargo, tenga en cuenta que la etiqueta PASSWD no tiene efecto en los usuarios que están en el grupo especificado por la configuración de exempt_group.

Por defecto, si la etiqueta NOPASSWD se aplica a alguna de las entradas de un usuario para el host actual, el usuario podrá ejecutar 'sudo -l' sin contraseña. Además, un usuario solo podrá ejecutar 'sudo -v' sin contraseña si todas las entradas del usuario para el host actual tienen la etiqueta NOPASSWD. Este comportamiento se puede anular mediante las opciones verifypw y listpw.

SETENV y NOSETENV

Estas etiquetas anulan el valor del flag setenv de forma individual por comando. Si SETENV se ha establecido para un comando, el usuario puede deshabilitar el flag env_reset desde la línea de comandos mediante la opción -E. Además, las variables de entorno establecidas en la línea de comandos no están sujetas a las restricciones impuestas por env_check, env_delete, o env_keep. Como tales, solo se debería permitir a los usuarios de confianza establecer variables de esta manera. Si el comando coincidente es ALL, la etiqueta SETENV se implica para ese comando; este valor predeterminado puede ser anulado por el uso de la etiqueta NOSETENV.

INTERCEPT y NOINTERCEPT

Si sudo ha sido compilado con soporte de intercept y el sistema operativo subyacente lo soporta, la etiqueta INTERCEPT puede ser usada para causar que los programas iniciados por un comando sean validados contra sudoers y registrados como si se hubieran ejecutado a través de sudo directamente. Esto es útil en conjunción con comandos que permiten escapes de shell como editores, shells y paginadores. Hay una sobrecarga adicional debido a la verificación de políticas que puede agregar latencia al ejecutar comandos como scripts de shell que ejecutan un gran número de sub-comandos. Para comandos interactivos, como un shell o un editor, la sobrecarga generalmente no es notable.

En el siguiente ejemplo, el usuario chuck puede ejecutar cualquier comando en la máquina "research" en modo de interceptación.

chuck	research = INTERCEPT: ALL

Vea la sección Prevenir escapes de shell más abajo para más detalles sobre cómo funciona INTERCEPT y si funcionará o no en su sistema.

Comodines

sudo permite el uso de comodines estilo shell (también conocidos como meta o glob) en nombres de host, nombres de ruta y argumentos de línea de comandos en el archivo sudoers. La coincidencia de comodines se realiza mediante las funciones glob(3) y fnmatch(3) según lo especificado por IEEE Std 1003.1 ("POSIX.1").

*
Coincide con cualquier conjunto de cero o más caracteres (incluido el espacio en blanco).
?
Coincide con cualquier carácter individual (incluido el espacio en blanco).
[...]
Coincide con cualquier carácter en el rango especificado.
[!...]
Coincide con cualquier carácter que no esté en el rango especificado.
\x
Para cualquier carácter 'x', se evalúa como 'x'. Esto se utiliza para escapar caracteres especiales como: '*', '?', '[', y ']'.
Estas no son expresiones regulares.
A diferencia de una expresión regular, no hay forma de coincidir con uno o más caracteres dentro de un rango.

Las clases de caracteres pueden ser utilizadas si las funciones glob(3) y fnmatch(3) de su sistema las soportan. Sin embargo, debido a que el carácter ':' tiene un significado especial en sudoers, debe ser escapado. Por ejemplo:

/bin/ls [[\:alpha\:]]*

Coincidiría con cualquier nombre de archivo que comience con una letra.

Una barra inclinada ('/') no será coincidente por los comodines utilizados en la porción del nombre de archivo del comando. Esto es para hacer que una ruta como:

/usr/bin/*

coincida con /usr/bin/who pero no con ">/usr/bin/X11/xterm.

Al hacer coincidir los argumentos de la línea de comandos, sin embargo, una barra inclinada sí se hace coincidir con comodines, ya que los argumentos de la línea de comandos pueden contener cadenas arbitrarias y no solo nombres de ruta.

Los comodines en los argumentos de la línea de comandos deben usarse con cuidado.
Los comodines pueden coincidir con cualquier carácter, incluidos los espacios en blanco. En la mayoría de los casos, es más seguro usar una expresión regular para hacer coincidir los argumentos de la línea de comandos. Para más información, consulte Comodines en los argumentos de comandos más abajo.

Excepciones a las reglas de comodines

Las siguientes excepciones se aplican a las reglas anteriores:

""
Si la cadena vacía ‘""’ es el único argumento de la línea de comandos en la entrada del archivo sudoers, significa que no se permite ejecutar ese comando con ningún argumento.
sudoedit
Los argumentos de la línea de comandos para el comando integrado sudoedit siempre deben ser nombres de ruta, por lo que una barra inclinada (‘/’) no será coincidida por un comodín.

Expresiones regulares

A partir de la versión 1.9.10, es posible utilizar expresiones regulares para nombres de ruta y argumentos de línea de comandos. Las expresiones regulares son más expresivas que los comodines estilo shell y suelen ser más seguras porque proporcionan un mayor grado de control al hacer coincidir. El tipo de expresiones regulares admitidas por sudoers son expresiones regulares extendidas POSIX, similares a las utilizadas por la utilidad egrep(1). Normalmente se documentan en el manual regex(7) o re_format(7), según el sistema. Como extensión, si la expresión regular comienza con “(?i)”, se coincidirá sin distinción entre mayúsculas y minúsculas.

En sudoers, las expresiones regulares deben comenzar con un carácter ‘^’ y terminar con un carácter ‘$’. Esto hace explícito qué es o no es una expresión regular. Tanto el nombre de la ruta como los argumentos del comando pueden ser expresiones regulares. Dado que el nombre de la ruta y los argumentos se comparan por separado, incluso es posible usar comodines para el nombre de la ruta y expresiones regulares para los argumentos. No es posible usar una única expresión regular para coincidir tanto con el comando como con sus argumentos. Las expresiones regulares en sudoers están limitadas a 1024 caracteres.

No es necesario escapar los caracteres especiales de sudoers en una expresión regular, excepto el signo de almohadilla (‘#’).

En el siguiente ejemplo, el usuario john puede ejecutar el comando passwd(1) como root en cualquier host, pero no se le permite cambiar la contraseña de root. Este tipo de regla es imposible de expresar de forma segura usando comodines.

john	ALL = /usr/bin/passwd ^[a-zA-Z0-9_]+$,\
              !/usr/bin/passwd root

También es posible usar una expresión regular en conjunto con las reglas de sudoedit. La siguiente regla daría al usuario bob la capacidad de editar solo los archivos /etc/motd, /etc/issue y /etc/hosts.

bob    ALL = sudoedit ^/etc/(motd|issue|hosts)$

Las expresiones regulares también pueden usarse para coincidir con el propio comando. En este ejemplo, se utiliza una expresión regular para permitir que el usuario sid ejecute los comandos /usr/sbin/groupadd, /usr/sbin/groupmod, /usr/sbin/groupdel, /usr/sbin/useradd, /usr/sbin/usermod y /usr/sbin/userdel como root.

sid    ALL = ^/usr/sbin/(group|user)(add|mod|del)$

Una desventaja de usar una expresión regular para coincidir con el nombre del comando es que no es posible coincidir con rutas relativas como ./useradd o ../sbin/useradd. Esto tiene implicaciones de seguridad cuando se utiliza una expresión regular para el nombre del comando en conjunto con el operador de negación, ‘!’, ya que tales reglas pueden ser fácilmente eludidas. Debido a esto, usar una expresión regular negada para el nombre del comando está encarecidamente desaconsejado. Esto no se aplica a los comandos negados que solo usan una expresión regular para coincidir con los argumentos del comando. Ver Expresiones regulares en nombres de comandos más abajo para más información.

Inclusión de otros archivos desde sudoers

Es posible incluir otros archivos sudoers desde dentro del archivo sudoers que se está analizando actualmente utilizando las directivas @include y @includedir. Para compatibilidad con versiones de sudo anteriores a 1.9.1, también se aceptan #include y #includedir.

Un archivo de inclusión se puede utilizar, por ejemplo, para mantener un archivo sudoers para todo el sitio además de un archivo local por máquina. Para este ejemplo, el archivo sudoers para todo el sitio será /etc/sudoers y el local por máquina será /etc/sudoers.local. Para incluir /etc/sudoers.local desde /etc/sudoers se usaría la siguiente línea en /etc/sudoers:

@include /etc/sudoers.local

Cuando sudo alcanza esta línea, suspenderá el procesamiento del archivo actual (/etc/sudoers) y cambiará a /etc/sudoers.local. Al llegar al final de /etc/sudoers.local, se procesará el resto de /etc/sudoers. Los archivos que se incluyan pueden a su vez incluir otros archivos. Se aplica un límite estricto de 128 archivos de inclusión anidados para evitar bucles de archivos de inclusión.

A partir de la versión 1.9.1, la ruta al archivo de inclusión puede contener espacios en blanco si se escapa con una barra invertida (‘\’). Alternativamente, toda la ruta puede encerrarse entre comillas dobles (""), en cuyo caso no es necesario ningún escape. Para incluir una barra invertida literal en la ruta, se debe usar ‘\\’.

Si la ruta al archivo de inclusión no está completamente calificada (no comienza con una ‘/’), debe ubicarse en el mismo directorio que el archivo sudoers del que se incluyó. Por ejemplo, si /etc/sudoers contiene la línea:

@include sudoers.local

el archivo que se incluirá es /etc/sudoers.local.

El nombre del archivo también puede incluir el escape ‘%h’, que significa la forma corta del nombre de host. En otras palabras, si el nombre de host de la máquina es “xerxes”, entonces:

@include /etc/sudoers.%h

hará que sudo incluya el archivo /etc/sudoers.xerxes. Cualquier carácter separador de nombre de ruta (‘/’) presente en el nombre de host se reemplazará por un guion bajo (‘_’) durante la expansión.

La directiva @includedir se puede utilizar para crear un directorio sudoers.d en el que el gestor de paquetes del sistema pueda colocar reglas de archivos sudoers como parte de la instalación del paquete. Por ejemplo, dado:

@includedir /etc/sudoers.d

sudo suspenderá el procesamiento del archivo actual y leerá cada archivo en /etc/sudoers.d, omitendo nombres de archivo que terminan en ‘~’ o que contienen un carácter ‘.’ para evitar problemas con los archivos temporales/de copia de seguridad del gestor de paquetes o del editor.

Los archivos se analizan en orden léxico ordenado. Es decir, /etc/sudoers.d/01_first se analizará antes que /etc/sudoers.d/10_second. Tenga en cuenta que, debido a que la ordenación es léxica y no numérica, /etc/sudoers.d/1_whoops se cargaría después de /etc/sudoers.d/10_second. El uso de un número consistente de ceros iniciales en los nombres de archivo puede servir para evitar tales problemas. Después de analizar los archivos del directorio, el control regresa al archivo que contenía la directiva @includedir.

A diferencia de los archivos incluidos a través de @include, visudo no editará los archivos en un directorio @includedir a menos que uno de ellos contenga un error de sintaxis. Todavía es posible ejecutar visudo con la opción -f para editar los archivos directamente, pero esto no detectará la redefinición de un alias que también esté presente en otro archivo.

DESCRIPCIÓN

El comando sudo (SUperuser DO) permite a un usuario permitido ejecutar un comando como otro usuario (normalmente el superusuario root) de acuerdo con las reglas de seguridad establecidas en el archivo /etc/sudoers. El comando sudo registra la invocación del comando y su argumento, si procede.

Las entradas de el archivo /etc/sudoers controlan quién puede ejecutar qué comandos como qué usuarios en qué máquinas. El archivo /etc/sudoers debe ser editado únicamente con el comando visudo ya que de lo contrario se producirán errores de sintaxis en el archivo que podrían impedir que sudo funcione correctamente.

ESPECIFICACIÓN DE USUARIO

Una especificación de usuario se basa en los nombres de usuario de UNIX. Puede ser un nombre de usuario específico, un grupo de UNIX precedido por un signo de porcentaje (%), o un alias definido en el archivo /etc/sudoers. La lista de usuarios se puede separar por comas.

El alias especial ALL se puede usar para que coincida con todos los usuarios.

Si la entrada de el archivo /etc/sudoers está precedida por un signo de exclamación (!), indica que el usuario o grupo está excluido. Esto solo funciona si hay algo para excluir.

Los alias de usuario se definen usando la siguiente sintaxis:

User_Alias  name  =  user1, user2, user3, ...

Las reglas de el archivo /etc/sudoers se procesan en orden. La primera regla que coincide con el usuario, la máquina y el comando se utiliza para determinar si se permite o deniega el acceso.

ESPECIFICACIÓN DE HOST

Una especificación de host puede ser un nombre de host de DNS, un nombre corto de host, una dirección IP o un alias de host definido en el archivo /etc/sudoers. La lista de hosts se puede separar por comas.

El alias especial ALL se puede usar para que coincida con todos los hosts. El alias LOCAL coincide con todos los hosts locales.

Si la entrada de el archivo /etc/sudoers está precedida por un signo de exclamación (!), indica que el host está excluido. Esto solo funciona si hay algo para excluir.

Los alias de host se definen usando la siguiente sintaxis:

Host_Alias  name  =  host1, host2, host3, ...

ESPECIFICACIÓN DE COMANDO

Una especificación de comando es una ruta absoluta a un ejecutable o un alias de comando definido en el archivo /etc/sudoers. La lista de comandos se puede separar por comas.

El alias especial ALL se puede usar para que coincida con todos los comandos.

Si la entrada de el archivo /etc/sudoers está precedida por un signo de exclamación (!), indica que el comando está excluido. Esto solo funciona si hay algo para excluir.

Se pueden especificar argumentos de línea de comandos para un comando. Los argumentos se comparan literalmente con los argumentos pasados al comando.

Los alias de comandos se definen usando la siguiente sintaxis:

Cmnd_Alias  name  =  cmd1, cmd2, cmd3, ...

Si el nombre de un comando no comienza con una barra inclinada (/), se asumirá que está en el PATH del usuario que llama. Esto puede ser un riesgo de seguridad si el PATH del usuario no es seguro. Es mejor especificar la ruta completa al comando.

Los comandos pueden ser especificados con o sin argumentos. Si se especifican argumentos, se aplicarán de forma estricta. Por ejemplo, para permitir el comando vim con los argumentos -R o -r, deberá enumerarlos explícitamente:

    Cmnd_Alias VIMEDIT = /usr/bin/vim -R, /usr/bin/vim -r

Para permitir cualquier invocación de vim, simplemente proporcione la ruta completa del ejecutable:

    Cmnd_Alias VIMEDIT = /usr/bin/vim

ESPECIFICACIÓN DE RUNAS

La especificación de runas indica a qué usuario o usuarios se puede ejecutar un comando. Puede ser un nombre de usuario de UNIX, un grupo de UNIX precedido por un signo de porcentaje (%), o un alias de usuario definido en el archivo /etc/sudoers. La lista de usuarios se puede separar por comas.

El alias especial ALL se puede usar para que coincida con todos los usuarios. Por defecto, los comandos se ejecutan como el usuario root.

Si la entrada de el archivo /etc/sudoers está precedida por un signo de exclamación (!), indica que el usuario está excluido. Esto solo funciona si hay algo para excluir.

Los alias de runas se definen usando la siguiente sintaxis:

Runas_Alias  name  =  user1, user2, user3, ...

OPCIONES

Las opciones se aplican a la entrada de el archivo /etc/sudoers en la que se encuentran. Las opciones se especifican como pares clave-valor. La lista de opciones se puede separar por comas.

Las opciones disponibles son:

authenticate
Se requiere autenticación del usuario antes de ejecutar el comando.
nopasswd
No se requiere autenticación del usuario antes de ejecutar el comando.
always_set_home
Establece la variable de entorno HOME al directorio personal del usuario de destino.
set_home
Establece la variable de entorno HOME al directorio personal del usuario de destino.
env_reset
Restaura el entorno del usuario a un estado mínimo antes de ejecutar el comando.
env_keep
Lista de variables de entorno que se conservarán durante la ejecución del comando.
env_check
Lista de variables de entorno que se verificarán antes de ejecutar el comando.
secure_path
Establece la variable de entorno PATH a un valor seguro.
cwd
Establece el directorio de trabajo actual antes de ejecutar el comando.
chroot
Ejecuta el comando en un entorno chroot.
umask
Establece la máscara de creación de archivos (umask) para el comando.
timeout
Establece un tiempo de espera para la ejecución del comando.
notbefore
Establece una hora antes de la cual el comando no se puede ejecutar.
notafter
Establece una hora después de la cual el comando no se puede ejecutar.

Los siguientes nombres de alias están reservados y no se pueden utilizar como nombres de alias de usuario, host o comando:

  • ALL
  • LOCAL

Intentar definir un alias llamado ALL provocará un error de sintaxis. Usar ALL puede ser peligroso ya que, en un contexto de comando, permite al usuario ejecutar cualquier comando en el sistema.

Los siguientes nombres de opción permitidos en una Option_Spec también se consideran palabras reservadas: CHROOT, TIMEOUT, CWD, NOTBEFORE y NOTAFTER. Intentar definir un alias con el mismo nombre que una de las opciones provocará un error de sintaxis.

Un signo de exclamación (!) se puede usar como un operador lógico no en una lista o alias, así como delante de un Cmnd. Esto permite excluir ciertos valores. Para que el operador ‘!’ sea efectivo, debe haber algo que excluir. Por ejemplo, para que coincida con todos los usuarios excepto con root, se usaría:

ALL, !root

Si ALL se omite, como en:

!root

se denegaría explícitamente a root pero no coincidiría con ningún otro usuario. Esto es diferente de un operador de "negación" real.

Tenga en cuenta, sin embargo, que usar un ‘!’ en conjunción con el alias incorporado ALL para permitir que un usuario ejecute "todos menos unos pocos" comandos rara vez funciona como se espera (ver NOTAS DE SEGURIDAD a continuación).

Las líneas largas se pueden continuar con una barra invertida (\) como el último carácter de la línea.

Los espacios en blanco entre elementos en una lista, así como los caracteres sintácticos especiales en una User Specification (=, :, (, )) son opcionales.

Los siguientes caracteres deben escaparse con una barra invertida (\) cuando se usan como parte de una palabra (por ejemplo, un nombre de usuario o nombre de host): ‘!’, ‘=’, ‘:’, ‘,’, ‘(’, ‘)’, ‘\’.

OPCIONES DE SUDOERS

sudo puede modificar su comportamiento mediante líneas Default_Entry, como se explicó anteriormente. A continuación se presenta una lista de todos los parámetros de Defaults soportados, agrupados por tipo.

Flags booleanos:

always_query_group_plugin
Si se configura un group_plugin, úselo para resolver grupos de la forma ‘%group’ siempre que no haya también un grupo del sistema con el mismo nombre. Normalmente, solo los grupos de la forma ‘%:group’ se pasan al group_plugin. Esta bandera está en off por defecto.
always_set_home
Si está habilitado, sudo establecerá la variable de entorno HOME al directorio personal del usuario de destino (que es el usuario runas_default a menos que se use la opción -u). Esta bandera está en gran medida obsoleta y no tiene ningún efecto a menos que la bandera env_reset se haya deshabilitado o HOME esté presente en la lista env_keep, ambas cosas desaconsejadas. Esta bandera está en off por defecto.
authenticate
Si está establecido, los usuarios deben autenticarse con una contraseña (u otro medio de autenticación) antes de poder ejecutar comandos. Esta configuración predeterminada puede ser anulada mediante las etiquetas PASSWD y NOPASSWD. Esta bandera está en on por defecto.
case_insensitive_group
Si está habilitado, los nombres de grupo en sudoers se compararán sin distinción entre mayúsculas y minúsculas. Esto puede ser necesario cuando los usuarios se almacenan en LDAP o AD. Esta bandera está en on por defecto.
case_insensitive_user
Si está habilitado, los nombres de usuario en sudoers se compararán sin distinción entre mayúsculas y minúsculas. Esto puede ser necesario cuando los grupos se almacenan en LDAP o AD. Esta bandera está en on por defecto.
closefrom_override
Si está establecido, el usuario puede usar la opción -C que anula el punto de partida predeterminado desde el que sudo comienza a cerrar los descriptores de archivo abiertos. Esta bandera está en off por defecto.
compress_io
Si está establecido, y sudo está configurado para registrar la entrada o salida de un comando, los registros de E/S se comprimirán utilizando zlib. Esta bandera está en on por defecto cuando sudo se compila con soporte zlib.
exec_background
Por defecto, sudo ejecuta un comando como el proceso en primer plano siempre que sudo se ejecute en primer plano. Cuando la bandera exec_background está habilitada y el comando se está ejecutando en un pseudo-terminal (debido al registro de E/S o a la bandera use_pty), el comando se ejecutará como un proceso en segundo plano. Los intentos de leer desde la terminal de control (o de cambiar la configuración de la terminal) resultarán en la suspensión del comando con la señal SIGTTIN (o SIGTTOU en el caso de la configuración de la terminal). Si esto sucede cuando sudo es un proceso en primer plano, se otorgará al comando la terminal de control y se reanudará en primer plano sin intervención del usuario. La ventaja de ejecutar inicialmente el comando en segundo plano es que sudo no necesita leer de la terminal a menos que el comando lo solicite explícitamente. De lo contrario, cualquier entrada de terminal debe pasarse al comando, lo haya requerido o no (el kernel almacena en búfer las terminales, por lo que no es posible saber si el comando realmente quiere la entrada). Esto es diferente del comportamiento histórico de sudo o cuando el comando no se está ejecutando en un pseudo-terminal.

Para que esto funcione sin problemas, el sistema operativo debe soportar el reinicio automático de llamadas al sistema. Desafortunadamente, no todos los sistemas operativos lo hacen por defecto, e incluso aquellos que lo hacen pueden tener errores. Por ejemplo, macOS no reinicia las funciones tcgetattr(3) y tcsetattr(3) (esto es un error en macOS). Además, dado que este comportamiento depende de que el comando se detenga con las señales SIGTTIN o SIGTTOU, los programas que capturan estas señales y se suspenden con una señal diferente (normalmente SIGTOP) no se pondrán automáticamente en primer plano. Algunas versiones del comando linux su(1) se comportan de esta manera. Esta bandera está en off por defecto.

Esta configuración solo es compatible con la versión 1.8.7 o superior. No tiene ningún efecto a menos que el registro de E/S esté habilitado o la bandera use_pty esté habilitada.

env_editor
Si está establecido, visudo utilizará el valor de las variables de entorno SUDO_EDITOR, VISUAL o EDITOR antes de recurrir a la lista de editores predeterminada. Típicamente, visudo se ejecuta como root, por lo que esta bandera puede permitir que un usuario con privilegios de visudo ejecute comandos arbitrarios como root sin registrar. Una alternativa es colocar una lista separada por dos puntos de editores "seguros" en la configuración editor. visudo entonces solo usará SUDO_EDITOR, VISUAL o EDITOR si coinciden con un valor especificado en editor. Si la bandera env_reset está habilitada, las variables de entorno SUDO_EDITOR, VISUAL y/o EDITOR deben estar presentes en la lista env_keep para que la bandera env_editor funcione cuando visudo se invoca a través de sudo. Esta bandera está en on por defecto.
env_reset
Si está establecido, sudo ejecutará el comando en un entorno mínimo que contiene las variables TERM, PATH, HOME, MAIL, SHELL, LOGNAME, USER y SUDO_*. Luego se agregarán las variables del entorno del llamador o del archivo especificado por la configuración restricted_env_file que coincidan con las listas env_keep y env_check, seguidas de cualquier variable presente en el archivo especificado por la configuración env_file (si la hay). El contenido de las listas env_keep y env_check, según lo modificado por los parámetros globales de Defaults en sudoers, se mostrará cuando sudo sea ejecutado por root con la opción -V. Si la configuración secure_path está habilitada, su valor se utilizará para la variable de entorno PATH. Esta bandera está en on por defecto.
fast_glob
Normalmente, sudo utiliza la función glob(3) para realizar la expansión de patrones al estilo del shell al comparar nombres de ruta. Sin embargo, dado que accede al sistema de archivos, glob(3) puede tardar mucho tiempo en completarse para algunos patrones, especialmente cuando el patrón hace referencia a un sistema de archivos de red que se monta bajo demanda (auto-montado). El indicador fast_glob hace que sudo utilice la función fnmatch(3), que no accede al
el sistema de archivos para realizar su coincidencia. La desventaja de fast_glob es que no puede hacer coincidir rutas relativas como ./ls o ../bin/ls. Esto tiene implicaciones de seguridad cuando se utilizan nombres de ruta que incluyen caracteres de globbing con el operador de negación, ‘!’, ya que dichas reglas pueden ser trivialmente eludidas. Como tal, esta bandera no debe usarse cuando el archivo sudoers contiene reglas que incluyen nombres de ruta negados que incluyen caracteres de globbing. Esta bandera está desactivada por defecto.
log_passwords
La mayoría de los programas que requieren la contraseña de un usuario desactivarán el eco antes de leer la contraseña para evitar mostrar la contraseña en texto plano en la pantalla. Sin embargo, si la entrada de la terminal se está registrando (ver REGISTRO DE E/S), la contraseña aún estará presente en el registro de E/S. Si la opción log_passwords está desactivada, sudoers intentará evitar que se registren las contraseñas. Lo hace utilizando las expresiones regulares en passprompt_regex para hacer coincidir un aviso de contraseña en el búfer de salida de la terminal. Cuando se encuentra una coincidencia, los caracteres de entrada en el registro de E/S se reemplazarán por ‘*’ hasta que se encuentre un salto de línea o un retorno de carro en la entrada de la terminal o se reciba un nuevo búfer de salida de la terminal. Sin embargo, si un programa muestra caracteres mientras el usuario escribe (como sudo cuando está configurado pwfeedback), solo el primer carácter de la contraseña se reemplazará en el registro de E/S. Esta opción no tiene ningún efecto a menos que también estén configuradas log_input o log_ttyin. Esta bandera está activada por defecto.

Esta configuración solo es compatible con la versión 1.9.10 o superior.

fqdn
Establezca esta bandera si desea colocar nombres de host completos en el archivo sudoers cuando el nombre de host local (según lo devuelve el comando ‘hostname’) no contiene el nombre de dominio. En otras palabras, en lugar de mihost, usaría mihost.midominio.edu. Aún puede usar la forma corta si lo desea (e incluso mezclar ambas). Esta bandera solo es efectiva cuando el nombre de host “canónico”, según lo devuelve la función getaddrinfo(3) o gethostbyname(3), es un nombre de dominio completamente calificado. Este suele ser el caso cuando el sistema está configurado para usar DNS para la resolución de nombres de host.

Si el sistema está configurado para usar el archivo /etc/hosts con preferencia sobre DNS, el nombre de host “canónico” puede no estar completamente calificado. El orden en que se consultan las fuentes para la resolución de nombres de host generalmente se especifica en el archivo /etc/nsswitch.conf, /etc/netsvc.conf, /etc/host.conf, o, en algunos casos, /etc/resolv.conf. En el archivo /etc/hosts, el primer nombre de host de la entrada se considera el nombre “canónico”; los nombres subsiguientes son alias que no son utilizados por sudoers. Por ejemplo, la siguiente línea del archivo hosts para la máquina “xyzzy” tiene el nombre de dominio completamente calificado como el nombre de host “canónico”, y la versión corta como un alias.

192.168.1.1 xyzzy.sudo.ws xyzzy

Si la entrada del archivo hosts de la máquina no está formateada correctamente, la bandera fqdn no será efectiva si se consulta antes que DNS.

Tenga en cuenta que al usar DNS para la resolución de nombres de host, activar fqdn requiere que sudoers realice búsquedas en DNS, lo que hace que sudo no sea utilizable si DNS deja de funcionar (por ejemplo, si la máquina se desconecta de la red). Al igual que con el archivo hosts, debe usar el nombre “canónico” tal como lo conoce DNS. Es decir, no puede usar un alias de host (entrada CNAME) debido a problemas de rendimiento y al hecho de que no hay forma de obtener todos los alias de DNS.

Esta bandera está desactivada por defecto.

ignore_audit_errors
Permite que los comandos se ejecuten incluso si sudoers no puede escribir en el registro de auditoría. Si está habilitada, una falla al escribir en el registro de auditoría no se trata como un error fatal. Si está deshabilitada, un comando solo se puede ejecutar después de que el evento de auditoría se haya escrito con éxito. Esta bandera solo es efectiva en sistemas para los cuales sudoers admite el registro de auditoría, incluidos FreeBSD, Linux, macOS y Solaris. Esta bandera está activada por defecto.
ignore_dot
Si está configurada, sudo ignorará "." o "" (ambos denotan el directorio actual) en la variable de entorno PATH; el PATH en sí no se modifica. Esta bandera está activada por defecto.
ignore_iolog_errors
Permite que los comandos se ejecuten incluso si sudoers no puede escribir en el registro de E/S (local o remoto). Si está habilitada, una falla al escribir en el registro de E/S no se trata como un error fatal. Si está deshabilitada, el comando se terminará si no se puede escribir en el registro de E/S. Esta bandera está desactivada por defecto.
ignore_logfile_errors
Permite que los comandos se ejecuten incluso si sudoers no puede escribir en el archivo de registro. Si está habilitada, una falla al escribir en el archivo de registro no se trata como un error fatal. Si está deshabilitada, un comando solo se puede ejecutar después de que la entrada del archivo de registro se haya escrito con éxito. Esta bandera solo tiene un efecto cuando sudoers está configurado para usar registro basado en archivos a través de la configuración logfile. Esta bandera está activada por defecto.
ignore_local_sudoers
Si se establece a través de LDAP, se omitirá el análisis de /etc/sudoers. Esto está destinado a sitios que desean prevenir el uso de archivos sudoers locales para que solo se utilice LDAP. Esto funciona bien en sistemas donde el número de grupos listados en el archivo sudoers es mayor que el número de grupos a los que pertenece un usuario típico. En sistemas donde las búsquedas de grupos son lentas, donde los usuarios pueden pertenecer a un gran número de grupos, o donde el número de grupos listados en el archivo sudoers es relativamente pequeño, puede ser prohibitivamente costoso y ejecutar comandos a través de sudo puede llevar más tiempo de lo normal. En este caso, sudoers debe buscar cualquier nombre de grupo listado en el archivo sudoers y usar el ID de grupo en lugar del nombre del grupo al determinar si el usuario pertenece al grupo.

En tales sistemas, habilitar o deshabilitar match_group_by_gid se puede usar para elegir si las consultas de la base de datos de grupos se realizan por nombre (habilitado) o ID (deshabilitado), lo que puede ayudar a solucionar conflictos de entradas de grupo.

Ejecutar siempre por descriptor de archivo.
never
Nunca ejecutar por descriptor de archivo.
digest_only
Ejecutar solo por descriptor de archivo si el comando tiene un hash asociado en el archivo sudoers.

El valor por defecto es digest_only. Esto evita una condición de carrera de tiempo de verificación frente a tiempo de uso cuando el comando se encuentra en un directorio que puede ser escrito por el usuario que lo invoca.

fdexec cambiará el primer elemento del vector de argumentos para los scripts ($0 en el shell) debido a la forma en que el kernel ejecuta los intérpretes de scripts. En lugar de ser una ruta normal, hará referencia a un descriptor de archivo. Por ejemplo, /dev/fd/4 en Solaris y /proc/self/fd/4 en Linux. Una solución es usar la variable de entorno SUDO_COMMAND en su lugar.

La configuración de fdexec solo se utiliza cuando el comando coincide por nombre de ruta. No tiene ningún efecto si el comando coincide con el alias incorporado ALL.

Esta configuración solo es compatible con la versión 1.8.20 o superior. Si el sistema operativo no admite la llamada al sistema fexecve(2), esta configuración no tiene ningún efecto.

group_plugin
Una cadena que contiene un plugin de grupo de sudoers con argumentos opcionales. La cadena debe consistir en la ruta del plugin, ya sea completa o relativa al directorio /usr/lib/sudo, seguida de cualquier argumento de configuración que el plugin requiera. Estos argumentos (si los hay) se pasarán a la función de inicialización del plugin. Si hay argumentos presentes, la cadena debe ir entre comillas dobles ("").

En sistemas de 64 bits, si el plugin está presente pero no se puede cargar, sudoers buscará una versión de 64 bits y, si existe, la cargará como respaldo. Las reglas exactas para esto varían según el sistema. En Solaris, si el plugin se almacena en un directorio que termina en "lib", sudoers creará una ruta de respaldo añadiendo "/64" al nombre del directorio; /usr/lib/group_plugin.so se convierte en /usr/lib/64/group_plugin.so. En Linux, un directorio que termina en "lib" se transformará en "lib64" como ruta de respaldo; /usr/lib/group_plugin.so se convierte en /usr/lib64/group_plugin.so. En todos los demás sistemas, la ruta de respaldo se genera añadiendo un "64" antes de la extensión del archivo; group_plugin.so se convierte en group_plugin64.so.

En sistemas AIX, el plugin puede ser un objeto compartido que termine en ‘.so’ o un archivo de archivo que contenga un objeto compartido que termine en ‘.a’ con el nombre del objeto compartido entre paréntesis al final.

Para más información, véase PLUGINS PROVEEDORES DE GRUPOS.

lecture
Esta opción controla cuándo se imprimirá una breve conferencia junto con la solicitud de contraseña. Tiene los siguientes valores posibles:

Nunca imprimir la conferencia al usuario.
once

lecture_file
Ruta a un archivo que contiene una conferencia de sudo alternativa que se utilizará en lugar de la conferencia estándar si el archivo nombrado existe. Por defecto, sudo utiliza una conferencia incorporada.
listpw
Esta opción controla cuándo se requerirá una contraseña cuando un usuario ejecute sudo con la opción -l. Tiene los siguientes valores posibles:
all
Todas las entradas del archivo sudoers del usuario para el host actual deben tener el flag NOPASSWD establecido para evitar introducir una contraseña.

Si no se especifica ningún valor, se implica un valor de any. Negar la opción resulta en el uso del valor never. El valor por defecto es any.

log_format
El formato del registro de eventos. Los formatos de registro soportados son:
json
Actualmente, este es un alias de json_pretty. En una versión futura de sudo, json será equivalente a json_compact. Las entradas de registro JSON contienen los detalles completos del usuario, así como el entorno de ejecución si el comando fue permitido.
json_compact
Registrar eventos en formato JSON "compacto" (minificado). Cada evento se escribe como un objeto JSON separado en una sola línea sin espacios en blanco adicionales. Debido a las limitaciones del protocolo, los eventos JSON enviados a través de syslog pueden ser truncados.
json_pretty
Registrar eventos en formato JSON "pretty". Al registrar en un archivo, todo el archivo se trata como un único objeto JSON que consta de múltiples eventos, cada evento abarca varias líneas. Al registrar a través de syslog, no hay diferencia entre los formatos json_pretty y json_compact.
sudo
Registrar eventos en el formato tradicional de sudo, véase REGISTRO DE EVENTOS para más detalles.

Esta configuración afecta a los registros enviados a través de syslog(3), así como al archivo especificado por la configuración logfile, si existe. El valor por defecto es sudo.

logfile
Ruta al archivo de registro de sudo (no al archivo de registro de syslog). Establecer una ruta activa el registro en un archivo; negar esta opción lo desactiva. Por defecto, sudo registra a través de syslog.
mailerflags
Flags para usar al invocar el programa de correo. Por defecto es -t.
mailerpath
Ruta al programa de correo utilizado para enviar correos de advertencia (negar para evitar que sudo envíe correos). Por defecto es la ruta a sendmail encontrada en el momento de la configuración.
mailfrom
Dirección a utilizar para la dirección "de" al enviar correos de advertencia y error. La dirección debe ir entre comillas dobles ("") para protegerla de que sudo interprete el signo '@'. Por defecto es el nombre del usuario que ejecuta sudo.
mailto
Dirección a la que enviar los correos de advertencia y error (negar para evitar que sudo envíe correos). La dirección debe ir entre comillas dobles ("") para protegerla de que sudo interprete el signo ‘@’. Por defecto es root.
rlimit_as
El tamaño máximo al que puede crecer el espacio de direcciones del proceso (en bytes), si lo admite el sistema operativo. Véase Límites de recursos para más información.
rlimit_core
El tamaño máximo del archivo de volcado de memoria que se puede crear (en bytes). Véase Límites de recursos para más información. Por defecto es 0 (no se crea ningún volcado de memoria).
rlimit_cpu
El tiempo máximo de CPU que el proceso puede utilizar (en segundos). Véase Límites de recursos para más información.
rlimit_data
El tamaño máximo del segmento de datos para el proceso (en bytes). Véase Límites de recursos para más información.
rlimit_fsize
El tamaño máximo de archivo que el proceso puede crear (en bytes). Véase Límites de recursos para más información.
rlimit_locks
El número máximo de bloqueos que el proceso puede establecer, si lo admite el sistema operativo. Véase Límites de recursos para más información.
rlimit_memlock
El tamaño máximo que el proceso puede bloquear en memoria (en bytes), si lo admite el sistema operativo. Véase Límites de reso
rlimit_nofile
El número máximo de archivos que el proceso puede tener abiertos. Consulte Límites de recursos para obtener más información.
rlimit_nproc
El número máximo de procesos que el usuario puede ejecutar simultáneamente. Consulte Límites de recursos para obtener más información.
rlimit_rss
El tamaño máximo al que puede crecer el conjunto residente del proceso (en bytes). Consulte Límites de recursos para obtener más información.
rlimit_stack
El tamaño máximo al que puede crecer la pila del proceso (en bytes). Consulte Límites de recursos para obtener más información.
restricted_env_file
La opción restricted_env_file especifica la ruta completa a un archivo que contiene variables que se establecerán en el entorno del programa que se está ejecutando. Las entradas en este archivo deben ser asignaciones en el formato ‘VARIABLE=valor’ o ‘export VARIABLE=valor’, separadas por caracteres de nueva línea. El valor puede ir opcionalmente entre comillas simples o dobles. La sustitución de variables estilo shell no es compatible. Las líneas vacías y los comentarios que comienzan con un signo de almohadilla (‘#’) se ignoran. Las variables de este archivo solo se agregan si la variable no existe ya en el entorno. A diferencia de env_file, el contenido del archivo no se confía y se procesa de manera similar al entorno del usuario que lo invoca. Si env_reset está habilitado, las variables del archivo solo se agregarán si coinciden con la lista env_check o env_keep. Si env_reset está deshabilitado, las variables del archivo se agregarán siempre que no coincidan con la lista env_delete. En cualquier caso, el contenido de restricted_env_file se procesa antes que el contenido de env_file.
runchroot
Si se establece, sudo utilizará este valor para el directorio raíz al ejecutar un comando. El valor especial “*” permitirá al usuario especificar el directorio raíz a través de la opción -R de sudo. Consulte la sección Chroot_Spec para obtener más detalles.

Solo es posible utilizar runchroot como una configuración de Defaults específica del comando si el comando existe con la misma ruta dentro y fuera de la cárcel chroot. Esta restricción no se aplica a la configuración global, de host o de usuario de Defaults ni a un Cmnd_Spec que incluya un Chroot_Spec.

Esta configuración solo es compatible con la versión 1.9.3 o superior.

El soporte para establecer el directorio raíz está obsoleto y se eliminará en una versión futura de sudo.

runcwd
Si se establece, sudo utilizará este valor para el directorio de trabajo al ejecutar un comando. El valor especial “*” permitirá al usuario especificar el directorio de trabajo a través de la opción -D de sudo. Consulte la sección Chdir_Spec para obtener más detalles.

Esta configuración solo es compatible con la versión 1.9.3 o superior.

secure_path
Si se establece, sudo utilizará este valor en lugar de la variable de entorno PATH del usuario. Hay dos casos de uso básicos para secure_path:
  1. Para que sudo pueda encontrar comandos del administrador del sistema ubicados en directorios que pueden no estar en la ruta predeterminada del usuario, como /usr/sbin.
  2. Para ayudar a proteger scripts y programas que ejecutan otros comandos sin establecer primero PATH a un valor seguro. De lo contrario, un usuario con privilegios limitados podría ejecutar comandos arbitrarios manipulando PATH si el comando que se ejecuta invoca otros comandos sin usar un nombre de ruta completo.

Los usuarios del grupo especificado por la opción exempt_group no se ven afectados por secure_path. Esta opción está deshabilitada por defecto.

syslog
Instalación de syslog si se está utilizando syslog para el registro (negar para deshabilitar el registro de syslog). Por defecto es auth.

Se admiten las siguientes instalaciones de syslog: authpriv (si su sistema operativo lo admite), auth, daemon, user, local0, local1, local2, local3, local4, local5, local6, y local7.

syslog_badpri
Prioridad de syslog a utilizar cuando el usuario no tiene permiso para ejecutar un comando o cuando la autenticación no es exitosa. Por defecto es alert.

Se admiten las siguientes prioridades de syslog: alert, crit, debug, emerg, err, info, notice, warning, y none. Negar la opción o establecerla en un valor de none deshabilitará el registro de comandos no exitosos.

syslog_goodpri
Prioridad de syslog a utilizar cuando el usuario tiene permiso para ejecutar un comando y la autenticación es exitosa. Por defecto es notice.

Consulte syslog_badpri para ver la lista de prioridades de syslog admitidas. Negar la opción o establecerla en un valor de none deshabilitará el registro de comandos exitosos.

verifypw
Esta opción controla cuándo se requerirá una contraseña cuando un usuario ejecute sudo con la opción -v. Tiene los siguientes valores posibles:
all
Todas las entradas del archivo sudoers del usuario para el host actual deben tener el flag NOPASSWD establecido para evitar introducir una contraseña.
always
El usuario siempre debe introducir una contraseña para utilizar la opción -v.
any
Al menos una de las entradas del archivo sudoers del usuario para el host actual debe tener el flag NOPASSWD establecido para evitar introducir una contraseña.
never
El usuario nunca necesita introducir una contraseña para utilizar la opción -v.

Si no se especifica ningún valor, se asume el valor all. Negar la opción resulta en el uso del valor never. El valor predeterminado es all.

Listas que se pueden usar en un contexto booleano:

env_check
Variables de entorno que se eliminarán del entorno del usuario a menos que se consideren "seguras". Para todas las variables excepto TZ, "seguro" significa que el valor de la variable no contiene ningún carácter ‘%’ o ‘/’. Esto se puede usar para proteger contra vulnerabilidades de formato estilo printf en programas mal escritos. La variable TZ se considera insegura si se cumple alguna de las siguientes condiciones:
  • Consiste en un nombre de ruta completo, opcionalmente prefijado con dos puntos (‘:’), que no coincide con la ubicación del directorio zoneinfo.
  • Contiene un elemento de ruta ...
  • Contiene espacios en blanco o caracteres no imprimibles.
  • Es más largo que el valor de PATH_MAX.

El argumento puede ser una lista separada por espacios entre comillas dobles o un solo valor sin comillas. La lista puede ser reemplazada, agregada, eliminada o deshabilitada utilizando los operadores ‘=’, ‘+=’, ‘-=’ y ‘!’ respectivamente. Independientemente de si la opción env_reset está habilitada o deshabilitada, las variables especificadas por env_check se conservarán en el entorno si pasan la verificación mencionada. La lista global de variables de entorno a verificar se muestra cuando sudo es ejecutado por root con la opción -V.

env_delete
Variables de entorno que se eliminarán del entorno del usuario cuando la opción env_reset no esté en vigor. El argumento puede ser una lista separada por espacios entre comillas dobles o un solo valor sin comillas. La lista puede ser reemplazada, agregada, eliminada o deshabilitada utilizando los operadores ‘=’, ‘+=’, ‘-=’ y ‘!’ respectivamente. La lista global de variables de entorno a eliminar se muestra cuando sudo es ejecutado por root con la opción -V. Muchos sistemas operativos eliminarán variables potencialmente peligrosas del entorno de cualquier proceso set-user-ID (como sudo).
env_keep
Variables de entorno que se conservarán en el entorno del usuario cuando la opción env_reset esté en vigor. Esto permite un control detallado sobre el entorno sudo-spawned procesos. El argumento puede ser una lista separada por espacios entrecomillados dobles o un valor único sin comillas dobles. La lista puede ser reemplazada, aumentada, eliminada o deshabilitada usando los operadores ‘=’, ‘+=’, ‘-=’ y ‘!’ respectivamente. La lista global de variables a conservar se muestra cuando sudo es ejecutado por root con la opción -V.

Preservar la variable de entorno HOME tiene implicaciones de seguridad, ya que muchos programas la utilizan al buscar archivos de configuración o datos. Añadir HOME a env_keep puede permitir a un usuario ejecutar comandos sin restricciones a través de sudo y es muy desaconsejable. Los usuarios que deseen editar archivos con sudo deben ejecutar sudoedit (o sudo -e) para obtener la configuración de su editor habitual en lugar de invocar el editor directamente.

log_servers
Una lista de uno o más servidores para usar en el almacenamiento remoto de registros de eventos y E/S, separados por espacios en blanco. Los servidores de registro deben estar ejecutando sudo_logsrvd o un servicio que implemente el protocolo descrito por sudo_logsrv.proto(5).

Las direcciones de los servidores deben tener el formato “host[:puerto][(tls)]”. La parte del host puede ser un nombre de host, una dirección IPv4 o una dirección IPv6 entre corchetes.

Si la bandera opcional tls está presente, la conexión se asegurará con Transport Layer Security (TLS) versión 1.2 o 1.3. Las versiones de TLS anteriores a la 1.2 no son compatibles.

Si se especifica un puerto, puede ser un número de puerto o un nombre de servicio bien conocido, según se define en la base de datos de nombres de servicio del sistema. Si no se especifica ningún puerto, se utilizará el puerto 30343 para conexiones de texto plano y el puerto 30344 para conexiones TLS.

Cuando se establece log_servers, los datos del registro de eventos se registrarán tanto localmente (ver la configuración de syslog y log_file) como de forma remota, pero los datos del registro de E/S solo se registrarán de forma remota. Si se especifican varios hosts, se intentarán en orden inverso. Si no hay servidores de registro disponibles, el usuario no podrá ejecutar un comando a menos que se establezca la bandera ignore_iolog_errors (registro de E/S habilitado) o la bandera ignore_log_errors (registro de E/S deshabilitado). Del mismo modo, si la conexión al servidor de registro se interrumpe mientras sudo se está ejecutando, el comando se terminará a menos que se establezca la bandera ignore_iolog_errors (registro de E/S habilitado) o la bandera ignore_log_errors (registro de E/S deshabilitado).

Esta configuración solo es compatible con la versión 1.9.0 o superior.

passprompt_regex
Una lista de expresiones regulares extendidas POSIX utilizadas para hacer coincidir los indicadores de contraseña en la salida del terminal. Como extensión, si la expresión regular comienza con “(?i)”, se comparará sin distinguir mayúsculas y minúsculas. Cada expresión regular está limitada a 1024 caracteres. Esta opción solo se utiliza cuando se ha deshabilitado log_passwords. El valor predeterminado es “[Pp]assword[: ]*”

Esta configuración solo es compatible con la versión 1.9.10 o superior.

PLUGINS PROVEEDORES DE GRUPOS

El plugin sudoers admite su propia interfaz de plugin para permitir búsquedas de grupos no Unix que pueden consultar una fuente de grupos distinta de la base de datos de grupos Unix estándar. Esto se puede usar para implementar soporte para la sintaxis nonunix_group descrita anteriormente.

Los plugins de proveedor de grupos se especifican a través de la configuración group_plugin. El argumento para group_plugin debe consistir en la ruta del plugin, ya sea completamente calificada o relativa al directorio /usr/lib/sudo, seguida de las opciones de configuración que requiera el plugin. Estas opciones (si se especifican) se pasarán a la función de inicialización del plugin. Si hay opciones presentes, la cadena debe ir entre comillas dobles ("").

Los siguientes plugins de proveedor de grupos se instalan por defecto:

group_file
El plugin group_file admite un archivo de grupos alternativo que utiliza la misma sintaxis que el archivo /etc/group. La ruta al archivo de grupos debe especificarse como una opción del plugin. Por ejemplo, si el archivo de grupos a utilizar es /etc/sudo-group: 
Defaults group_plugin="group_file.so /etc/sudo-group"
system_group
El plugin system_group admite búsquedas de grupos a través de las funciones de la biblioteca C estándar getgrnam(3) y getgrid(3). Este plugin se puede usar en instancias donde el usuario pertenece a grupos que no están presentes en el vector de grupos suplementarios del usuario. Este plugin no requiere opciones: 
Defaults group_plugin=system_group.so

La API del plugin proveedor de grupos se describe en detalle en sudo_plugin(5).

REGISTRO DE EVENTOS

sudoers puede registrar eventos en formato JSON o en formato sudo; esta sección describe el formato de registro de sudo. Dependiendo de la configuración de sudoers, sudoers puede registrar eventos a través de syslog(3), en un archivo de registro local, o ambos. El formato de registro es casi idéntico en ambos casos. Cualquier carácter de control presente en los datos del registro se formatea en octal con un carácter ‘#’ delante. Por ejemplo, una tabulación horizontal se almacena como ‘#011’ y un retorno de carro incrustado se almacena como ‘#015’. Además, los espacios en la ruta del comando se almacenan como ‘#040’. Los argumentos de la línea de comandos que contienen espacios se encierran entre comillas simples (''). Esto hace posible distinguir múltiples argumentos de línea de comandos de un solo argumento que contiene espacios. Las comillas simples literales y los caracteres de barra invertida (‘\’) en los argumentos de la línea de comandos se escapan con una barra invertida.

Entradas de registro de comandos aceptados

Los comandos que sudo ejecuta se registran usando el siguiente formato (dividido en varias líneas para facilitar la lectura):

fecha nombre_host nombre_prog: nombre_usuario : TTY=nombre_tty ; CHROOT=chroot ; \
    PWD=cwd ; USER=usuario_ejecutar_como ; GROUP=grupo_ejecutar_como ; TSID=id_log ; \
    ENV=vars_entorno COMANDO=comando

Donde los campos son los siguientes:

fecha
La fecha en que se ejecutó el comando. Típicamente, está en el formato “MMM, DD, HH:MM:SS”. Si se registra a través de syslog(3), el formato de fecha real es controlado por el demonio syslog. Si se registra en un archivo y la opción log_year está habilitada, la fecha también incluirá el año.
nombre_host
El nombre del host en el que se ejecutó sudo. Este campo solo está presente cuando se registra a través de syslog(3).
nombre_prog
El nombre del programa, usualmente sudo o sudoedit. Este campo solo está presente cuando se registra a través de syslog(3).
nombre_usuario
El nombre de inicio de sesión del usuario que ejecutó sudo.
nombre_tty
El nombre corto del terminal (por ejemplo, “console”, “tty01”, o “pts/0”) en el que se ejecutó sudo, o “unknown” si no había terminal presente.
chroot
El directorio raíz en el que se ejecutó el comando, si se especificó alguno.
cwd
El directorio de trabajo actual en el que se ejecutó sudo.
usuario_ejecutar_como
El usuario con el que se ejecutó el comando.
grupo_ejecutar_como
El grupo con el que se ejecutó el comando si se especificó en la línea de comandos.
id_log
Un identificador de registro de E/S que se puede usar para reproducir la salida del comando. Esto solo está presente cuando la opción log_input o log_output está habilitada.
vars_entorno
Una lista de variables de entorno especificadas en la línea de comandos, si se especificaron.
comando
El comando real que se ejecutó, incluyendo cualquier argumento de línea de comandos.

Los mensajes se registran utilizando la configuración regional especificada por sudoers_locale, que por defecto es la configuración regional ‘C’.

Entradas de registro de comandos denegados

Si al usuario no se le permite ejecutar el comando, el motivo de la denegación seguirá al nombre de usuario. Los motivos posibles incluyen:

user NOT in sudoers
El usuario no está listado en el archivo sudoers.
user NOT authorized on host
El usuario está listado en el archivo sudoers pero no tiene permiso para ejecutar comandos en el host.
command not allowed
El usuario está listado en el archivo sudoers para el host pero no tiene permiso para ejecutar el comando especificado.
3 incorrect password attempts
El usuario no introdujo su contraseña después de 3 intentos. El número real de intentos variará según el número de intentos fallidos y el valor de la opción passwd_tries.
a password is required
Se especificó la opción -n pero se requería una contraseña.
sorry, you are not allowed to set the following environment variables<
variable de entorno
El usuario especificó variables de entorno en la línea de comandos que no estaban permitidas por sudoers.

Entradas del registro de errores

Si ocurre un error, sudoers registrará un mensaje y, en la mayoría de los casos, enviará un mensaje al administrador por correo electrónico. Los errores posibles incluyen:

error de análisis en /etc/sudoers cerca de la línea N
sudoers encontró un error al analizar el archivo especificado. En algunos casos, el error real puede estar una línea por encima o por debajo del número de línea indicado, dependiendo del tipo de error.
problema con las entradas de defaults
El archivo sudoers contiene una o más configuraciones de Defaults desconocidas. Esto no impide que sudo se ejecute, pero el archivo sudoers debe ser verificado usando visudo.
propietario de la marca de tiempo (nombre de usuario): No existe tal usuario
No se pudo encontrar el propietario del directorio de marcas de tiempo, tal como lo especifica la configuración timestampowner, en la base de datos de contraseñas.
imposible abrir/leer /etc/sudoers
No se pudo abrir el archivo sudoers para lectura. Esto puede suceder cuando el archivo sudoers se encuentra en un sistema de archivos remoto que mapea el ID de usuario 0 a un valor diferente. Normalmente, sudoers intenta abrir el archivo sudoers usando permisos de grupo para evitar este problema. Considere cambiar la propiedad de /etc/sudoers o agregar un argumento como “sudoers_uid=N” (donde ‘N’ es el ID de usuario que posee el archivo sudoers) al final de la línea sudoers Plugin en el archivo sudo.conf(5).
imposible abrir /etc/sudoers
Falta el archivo /etc/sudoers.
/etc/sudoers no es un archivo regular
El archivo /etc/sudoers existe pero no es un archivo regular ni un enlace simbólico.
/etc/sudoers pertenece a uid N, debería ser 0
El archivo sudoers tiene el propietario incorrecto. Si desea cambiar el propietario del archivo sudoers, agregue “sudoers_uid=N” (donde ‘N’ es el ID de usuario que posee el archivo sudoers) a la línea sudoers Plugin en el archivo sudo.conf(5).
/etc/sudoers se puede escribir por todos
Los permisos del archivo sudoers permiten que todos los usuarios escriban en él. El archivo sudoers no debe ser escribible por todos; el modo de archivo predeterminado es 0440 (legible por propietario y grupo, no escribible). El modo predeterminado se puede cambiar a través de la opción “sudoers_mode” en la línea sudoers Plugin en el archivo sudo.conf(5).
/etc/sudoers pertenece a gid N, debería ser 1
El archivo sudoers tiene la propiedad de grupo incorrecta. Si desea cambiar la propiedad de grupo del archivo sudoers, agregue “sudoers_gid=N” (donde ‘N’ es el ID de grupo que posee el archivo sudoers) a la línea sudoers Plugin en el archivo sudo.conf(5).
imposible abrir /run/sudo/ts/ID_de_usuario
sudoers no pudo leer o crear el archivo de marca de tiempo del usuario. Esto puede suceder cuando timestampowner se establece en un usuario que no sea root y el modo de /run/sudo no es accesible por grupo u otros. El modo predeterminado para /run/sudo es 0711.
imposible escribir en /run/sudo/ts/ID_de_usuario
sudoers no pudo escribir en el archivo de marca de tiempo del usuario.
/run/sudo/ts pertenece a uid X, debería ser Y
El directorio de marcas de tiempo pertenece a un usuario distinto de timestampowner. Esto puede ocurrir cuando se ha cambiado el valor de timestampowner. sudoers ignorará el directorio de marcas de tiempo hasta que se corrija el propietario.
/run/sudo/ts se puede escribir por grupo
El directorio de marcas de tiempo se puede escribir por grupo; solo debería ser escribible por timestampowner. El modo predeterminado para el directorio de marcas de tiempo es 0700. sudoers ignorará el directorio de marcas de tiempo hasta que se corrija el modo.

Notas sobre el registro a través de syslog

Por defecto, sudoers registra mensajes a través de syslog(3). Los campos date, hostname y progname son añadidos por la función syslog(3) del sistema, no por sudoers en sí. Como tal, pueden variar en formato en diferentes sistemas.

El tamaño máximo de los mensajes de syslog varía de un sistema a otro. La configuración syslog_maxlen se puede usar para cambiar el tamaño máximo del mensaje de syslog del valor predeterminado de 980 bytes. Para más información, consulte la descripción de syslog_maxlen.

Notas sobre el registro a un archivo

Si la opción logfile está configurada, sudoers registrará en un archivo local, como /var/log/sudo. Al registrar en un archivo, sudoers usa un formato similar a syslog(3), con algunas diferencias importantes:

  1. El campo progname no está presente.
  2. El hostname solo se registra si la opción log_host está habilitada.
  3. La fecha no incluye el año a menos que la opción log_year esté habilitada.
  4. Las líneas que son más largas que loglinelen caracteres (80 por defecto) se ajustan de línea y continúan en la siguiente línea con una sangría de cuatro caracteres. Esto hace que las entradas sean más fáciles de leer para un ser humano, pero dificulta el uso de grep(1) en los archivos de registro. Si la opción loglinelen se establece en 0 (o se niega con un ‘!’), el ajuste de línea se desactivará.

REGISTRO DE E/S

Cuando el registro de E/S está habilitado, sudo ejecuta el comando en un pseudo-terminal, registrando la entrada y/o salida del usuario, dependiendo de qué banderas de sudoers estén habilitadas. Hay cinco tipos distintos de E/S que se pueden registrar, cada uno con una bandera de sudoers correspondiente.

Tipo Bandera Descripción
entrada de terminal log_ttyin pulsaciones de teclas introducidas por el usuario
salida de terminal log_ttyout salida del comando mostrada en pantalla
entrada estándar log_stdin entrada desde una tubería o un archivo
salida estándar log_stdout salida a una tubería o un archivo
error estándar log_stderr salida a una tubería o un archivo

Además de las banderas descritas anteriormente, la bandera log_input y el conjunto de etiquetas de comando LOG_INPUT configuran tanto log_ttyin como log_stdin. La bandera log_output y el conjunto de etiquetas de comando LOG_OUTPUT configuran log_ttyout, log_stdout y log_stderr.

Para capturar la entrada y salida de la terminal, sudo ejecuta el comando en un pseudo-terminal, registrando la entrada y salida antes de pasarla al usuario. Para capturar la entrada estándar, salida estándar o error estándar, sudo usa una tubería para interponerse entre el flujo de entrada o salida, registrando la E/S antes de pasarla al otro extremo de la tubería.

La E/S se puede registrar tanto en la máquina local como en un servidor de registro remoto. Para registros locales, la E/S se registra en el directorio especificado por la opción iolog_dir ( /var/log/sudo-io por defecto) usando un ID de sesión único que se incluye en la línea de registro de sudo, prefijado con ‘TSID=’. La opción iolog_file puede usarse para controlar el formato del ID de sesión. Para registros remotos, la configuración log_servers se usa para especificar uno o más servidores de registro que ejecutan sudo_logsrvd u otro servidor que implemente el protocolo descrito en sudo_logsrv.proto(5).

Trampas del registro de E/S

Al registrar la entrada estándar, cualquier cosa enviada a la entrada estándar será consumida, independientemente de si el comando ejecutado a través de sudo está leyendo activamente la entrada estándar. Esto puede tener resultados inesperados al usar sudo en un script de shell que espera procesar la entrada estándar. Por ejemplo, dado el siguiente script de shell:

#!/bin/sh
sudo echo testing
echo done

Se comportará como se espera cuando el script se pasa al shell como un argumento:

$ sh test.sh
testing
done

Sin embargo, si el script se pasa al shell en la entrada estándar, el comando ‘sudo echo testing’ consumirá el resto del script. Esto significa que la declaración ‘echo done’ nunca se ejecuta.

$ sh -s < test.sh
testing

  1. Redirigir la entrada estándar desde /dev/null al ejecutar un comando a través de sudo

    CONFIGURACIÓN DEL REGISTRO DE E/S

    Para las entradas de registro de comandos de sudo, hay dos tipos principales de registro de entrada/salida (E/S): registro de entrada/salida en terminal (log_ttyin y log_ttyout) y registro de E/S de no terminal ( log_stdin y log_stdout). El comportamiento predeterminado es habilitar el registro de E/S en terminal cuando sea apropiado y el registro de E/S de no terminal cuando no lo sea.

    Las siguientes opciones pueden usarse en el archivo sudoers o pasarse como argumento de línea de comandos a sudo para modificar este comportamiento:

    log_input
    Habilita tanto log_ttyin como log_stdin. Este es el comportamiento predeterminado y se habilita automáticamente cuando se utiliza la opción LOG_INPUT.
    log_output
    Habilita tanto log_ttyout como log_stdout. Este es el comportamiento predeterminado y se habilita automáticamente cuando se utiliza la opción LOG_OUTPUT.
    log_stdin
    Registra la entrada estándar de un comando.
    log_stdout
    Registra la salida estándar de un comando.
    log_stderr
    Registra el error estándar de un comando.
    log_ttyin
    Registra la entrada del terminal. Si se establece esta opción, también se habilita log_input.
    log_ttyout
    Registra la salida del terminal. Si se establece esta opción, también se habilita log_output.
    log_passwords
    Registra las contraseñas escritas por el usuario. Esto está deshabilitado por defecto y solo se habilita si el usuario escribe explícitamente la opción LOG_PASSWORD.
    log_subcommand
    Registra el comando ejecutado por sudo. Esto está habilitado por defecto. Si se establece esta opción, también se habilitará log_input y log_output.
    quiet
    Suprime el registro de la entrada y salida del terminal. Esto está deshabilitado por defecto.
    compress_io
    Comprime los archivos de registro de E/S. Esto está habilitado por defecto. Si se deshabilita esta opción, los archivos de registro de E/S no se comprimirán.
    iolog_flush
    No almacena en búfer los archivos de registro de E/S. Esto está deshabilitado por defecto. Si se habilita esta opción, los datos de registro de E/S se escribirán en el disco tan pronto como estén disponibles.

    Las opciones anteriores pueden negarse añadiendo un signo de exclamación (!) delante del nombre de la opción. Por ejemplo, !log_stdin deshabilitará el registro de la entrada estándar.

    Para deshabilitar el registro de entrada/salida para un comando específico, puede usar la opción Defaults! seguida del nombre del comando y luego las opciones que desea deshabilitar. Por ejemplo, para deshabilitar el registro de la entrada estándar para el comando echo, puede añadir la siguiente línea al archivo sudoers:

    Defaults!/usr/bin/echo !log_stdin

    También es posible deshabilitar el registro de entrada/salida para un alias de comando. Por ejemplo, para deshabilitar el registro de entrada y salida para los comandos tar, cpio y rsync, puede añadir lo siguiente al archivo sudoers:

    Cmnd_Alias COPY_CMDS = /usr/bin/tar, /usr/bin/cpio, /usr/bin/rsync
Defaults!COPY_CMDS !log_stdin, !log_stdout

    Tenga en cuenta que habilitar el registro de E/S de terminal puede dar lugar a que se registren datos sensibles, como contraseñas, incluso si no se muestran en la pantalla. Si el registro de contraseñas es una preocupación, considere deshabilitar la opción log_passwords.

    FORMATO DEL REGISTRO DE E/S

    Para los registros de E/S locales y remotos, cada registro se almacena en un directorio separado que contiene los siguientes archivos:

    log
    Un archivo de texto que contiene información sobre el comando. La primera línea consta de los siguientes campos separados por dos puntos: la hora en que se ejecutó el comando, el nombre del usuario que ejecutó sudo, el nombre del usuario de destino, el nombre del grupo de destino (opcional), el terminal desde el que se ejecutó sudo y el número de líneas y columnas del terminal. La segunda y tercera líneas contienen el directorio de trabajo desde el que se ejecutó el comando y la ruta del propio comando (con argumentos si están presentes).
    log.json
    Un archivo con formato JSON que contiene información sobre el comando. Esto es similar al archivo log pero contiene información adicional y es fácilmente extensible. El archivo log.json será utilizado por sudoreplay(8) con preferencia al archivo log si existe. El archivo puede contener los siguientes elementos:
    timestamp
    Un objeto JSON que contiene la hora en que se ejecutó el comando. Consiste en dos valores, seconds y nanoseconds.
    columns
    El número de columnas del terminal en el que se ejecutó el comando, o cero si no había terminal presente.
    command
    La ruta completa del comando que se ejecutó.
    lines
    El número de líneas del terminal en el que se ejecutó el comando, o cero si no había terminal presente.
    runargv
    Un array JSON que representa el vector de argumentos del comando tal como se pasó a la llamada del sistema execve(2).
    runenv
    Un array JSON que representa el entorno del comando tal como se pasó a la llamada del sistema execve(2).
    rungid
    El ID del grupo con el que se ejecutó el comando. Este elemento solo está presente cuando el usuario especifica un grupo en la línea de comandos.
    rungroup
    El nombre del grupo con el que se ejecutó el comando. Este elemento solo está presente cuando el usuario especifica un grupo en la línea de comandos.
    runuid
    El ID de usuario con el que se ejecutó el comando.
    runuser
    El nombre del usuario con el que se ejecutó el comando.
    submitcwd
    El directorio de trabajo actual en el momento en que se ejecutó sudo.
    submithost
    El nombre del host en el que se ejecutó el comando.
    submituser
    El nombre del usuario que ejecutó el comando a través de sudo.
    ttyname
    El nombre de la ruta del terminal desde el que el usuario invocó sudo. Si el comando se ejecutó en un pseudo-terminal, ttyname será diferente del terminal en el que se ejecutó realmente el comando.
    timing
    Información de tiempo utilizada para reproducir la sesión. Cada línea consta del tipo de entrada del registro de E/S y la cantidad de tiempo transcurrido desde la última entrada, seguido de datos específicos del tipo. Los tipos de entrada del registro de E/S y sus datos específicos correspondientes son:
    0
    entrada estándar, número de bytes en la entrada
    1
    salida estándar, número de bytes en la entrada
    2
    error estándar, número de bytes en la entrada
    3
    entrada de terminal, número de bytes en la entrada
    4
    salida de terminal, número de bytes en la entrada
    5
    cambio de ventana, nuevo número de líneas y columnas
    6
    compatibilidad con errores para la salida de terminal de sudo 1.8.7
    7
    suspensión o reanudación de comando, señal recibida
    ttyin
    Entrada en bruto del terminal del usuario, exactamente como se recibió. Este archivo solo está presente si se establecen las opciones log_input o log_ttyin y sudo se ejecutó desde un terminal. No se realiza ningún post-procesamiento. Para la visualización manual, es posible que desee convertir los caracteres de retorno de carro en saltos de línea. Por ejemplo: ‘gunzip -c ttyin | tr "\r" "\n"’
    stdin
    La entrada estándar cuando no hay un terminal presente, o la entrada redirigida desde una tubería o archivo. Este archivo solo está presente si se establecen las opciones log_input o log_stdin y la entrada estándar no está conectada a un terminal.
    ttyout
    Salida del pseudo-terminal (lo que el comando escribe en la pantalla). Se realiza un post-procesamiento específico del terminal antes de registrar los datos. Esto significa que, por ejemplo, los saltos de línea se convierten normalmente en pares de salto de línea/retorno de carro y las tabulaciones pueden expandirse a espacios. Este archivo solo está presente si se establecen las opciones log_output o log_ttyout y sudo se ejecutó desde un terminal.
    stdout
    La salida estándar cuando no hay un terminal presente, o la salida redirigida a una tubería o archivo. Este archivo solo está presente si se establecen las opciones log_output o log_stdout y la salida estándar no está conectada a un terminal.
    stderr
    El error estándar cuando no hay un terminal presente, o la salida redirigida a una tubería o archivo. Este archivo solo está presente si se establecen las opciones log_output o log_stderr y el error estándar no está conectado a un terminal.

    Todos los archivos, excepto log, se comprimen en formato gzip, a menos que se haya deshabilitado la opción compress_io. Debido al almacenamiento en búfer, normalmente no es posible mostrar los registros de E/S en tiempo real mientras el programa se está ejecutando. Los datos del registro de E/S no estarán completos hasta que el programa ejecutado por sudo haya salido o haya sido terminado por una señal. La opción iolog_flush puede utilizarse para deshabilitar el almacenamiento en búfer, en cuyo caso los datos del registro de E/S se escriben en el disco tan pronto como estén disponibles. La parte de salida de un archivo de registro de E/S se puede ver con la utilidad sudoreplay(8), que también puede utilizarse para listar o buscar los registros disponibles.

    La entrada del usuario puede contener información sensible, como contraseñas (incluso si no se muestran en la pantalla), que se almacenará en el archivo de registro sin cifrar. En la mayoría de los casos, registrar la salida del comando a través de log_output o LOG_OUTPUT es todo lo que se requiere. Al registrar la entrada, considere deshabilitar la opción log_passwords.

    Dado que los registros de E/S de cada sesión se almacenan en un directorio separado, las utilidades tradicionales de rotación de registros no pueden utilizarse para limitar el número de registros de E/S. La forma más sencilla de limitar el número de registros de E/S es estableciendo la opción maxseq al número máximo de registros que desea almacenar. Una vez que el número de secuencia del registro de E/S alcance maxseq, se restablecerá a cero y sudoers truncará y reutilizará cualquier registro de E/S existente.

De esas redes, solo 128.138.204.0 tiene una máscara de red explícita (en notación CIDR) que indica que es una red de clase C. Para las otras redes en `CSNETS`, se utilizará la máscara de red de la máquina local durante la coincidencia. ```conf lisa CUNETS = ALL ``` La usuaria **lisa** puede ejecutar cualquier comando en cualquier host del alias `CUNETS` (la red de clase B 128.138.0.0). ```conf operator ALL = DUMPS, KILL, SHUTDOWN, HALT, REBOOT, PRINTING,\ sudoedit /etc/printcap, /usr/oper/bin/ ``` El usuario **operator** puede ejecutar comandos limitados a mantenimiento simple. Aquí, esos son comandos relacionados con copias de seguridad, finalización de procesos, el sistema de impresión, apagado del sistema y cualquier comando en el directorio `/usr/oper/bin/`. Un comando en el alias de comando `DUMPS` incluye un resumen sha224, `/home/operator/bin/start_backups`. Esto se debe a que el directorio que contiene el script es escribible por el usuario operador. Si el script se modifica (lo que resulta en una discrepancia de resumen), ya no será posible ejecutarlo a través de `sudo`. ```conf joe ALL = /usr/bin/su operator ``` El usuario **joe** solo puede hacer `su` a operator. ```conf pete HPPA = /usr/bin/passwd [A-Za-z]*, !/usr/bin/passwd *root* %opers ALL = (: ADMINGRP) /usr/sbin/ ``` Los usuarios del grupo **opers** pueden ejecutar comandos en `/usr/sbin/` como ellos mismos con cualquier grupo del alias de ejecución `ADMINGRP` (los grupos **adm** y **oper**). El usuario **pete** tiene permitido cambiar la contraseña de cualquiera, excepto de **root**, en las máquinas `HPPA`. Debido a que los argumentos de la línea de comandos se comparan como una única cadena concatenada, el comodín '*' coincidirá con múltiples palabras. Este ejemplo asume que `passwd` no toma múltiples nombres de usuario en la línea de comandos. En sistemas con `getopt` de GNU, las opciones para `passwd` se pueden especificar después del argumento del usuario. Como resultado, esta regla también permitirá: ```conf passwd username --expire ``` lo cual puede no ser deseable. ```conf bob SPARC = (OP) ALL : SGI = (OP) ALL ``` El usuario **bob** puede ejecutar cualquier cosa en las máquinas `SPARC` y `SGI` como cualquier usuario listado en el alias de ejecución `OP` (**root** y **operator**). ```conf jim +biglab = ALL ``` El usuario **jim** puede ejecutar cualquier comando en las máquinas del netgroup `biglab`. `sudo` sabe que "biglab" es un netgroup debido al prefijo '+'. ```conf +secretaries ALL = PRINTING, /usr/bin/adduser, /usr/bin/rmuser ``` Los usuarios del netgroup **secretaries** necesitan ayudar a administrar las impresoras, así como agregar y eliminar usuarios, por lo que se les permite ejecutar esos comandos en todas las máquinas. ```conf fred ALL = (DB) NOPASSWD: ALL ``` El usuario **fred** puede ejecutar comandos como cualquier usuario en el alias de ejecución `DB` (**oracle** o **sybase**) sin dar una contraseña. ```conf john ALPHA = /usr/bin/su [!-]*, !/usr/bin/su *root* ``` En las máquinas `ALPHA`, el usuario **john** puede hacer `su` a cualquiera excepto a **root**, pero no puede especificar ninguna opción al comando `su`. ```conf jen ALL, !SERVERS = ALL ``` La usuaria **jen** puede ejecutar cualquier comando en cualquier máquina, excepto en aquellas del alias de host `SERVERS` (primary, mail, www y ns). ```conf jill SERVERS = /usr/bin/, !SU, !SHELLS ``` Para cualquier máquina en el alias de host `SERVERS`, **jill** puede ejecutar cualquier comando en el directorio `/usr/bin/`, excepto aquellos comandos que pertenecen a los alias de comando `SU` y `SHELLS`. Aunque no se mencionan específicamente en la regla, los comandos en el alias de comando `PAGERS` residen en `/usr/bin` y tienen la opción `noexec` establecida. ```conf steve CSNETS = (operator) /usr/local/op_commands/ ``` El usuario **steve** puede ejecutar cualquier comando en el directorio `/usr/local/op_commands/` pero solo como el usuario operator. ```conf matt valkyrie = KILL ``` En su estación de trabajo personal, valkyrie, **matt** necesita poder finalizar procesos colgados. ```conf WEBADMIN www = (www) ALL, (root) /usr/bin/su www ``` En el host www, cualquier usuario del alias de usuario `WEBADMIN` (will, wendy y wim), puede ejecutar cualquier comando como el usuario www (que posee las páginas web) o simplemente hacer `su` a www. ```conf ALL CDROM = NOPASSWD: /sbin/umount /CDROM,\ /sbin/mount -o nosuid\,nodev /dev/cd0a /CDROM ``` Cualquier usuario puede montar o desmontar un CD-ROM en las máquinas del alias de host `CDROM` (orion, perseus, hercules) sin ingresar una contraseña. Esto es un poco tedioso para los usuarios.

    NOTAS DE SEGURIDAD

    Limitaciones del operador ‘!’

    Generalmente, no es eficaz "restar" comandos de TODOS utilizando el operador ‘!’. Un usuario puede sortear esto trivialmente copiando el comando deseado a otro nombre y luego ejecutándolo. Por ejemplo:

    bill	TODOS = TODOS, !SU, !SHELLS

    No impide realmente que bill ejecute los comandos listados en SU o SHELLS, ya que puede simplemente copiar esos comandos a otro nombre, o usar un escape de shell desde un editor u otro programa. Por lo tanto, este tipo de restricciones deben considerarse como, en el mejor de los casos, asesoramiento (y reforzadas por políticas).

    En general, si un usuario tiene sudo TODOS, no hay nada que impida que cree su propio programa que le proporcione un shell de root (o que cree su propia copia de un shell), independientemente de cualquier elemento ‘!’ en la especificación del usuario.

    Implicaciones de seguridad de fast_glob

    Si la opción fast_glob está en uso, no es posible negar de forma fiable comandos cuyos nombres de ruta incluyan caracteres de globbing (también conocidos como comodines). Esto se debe a que la función fnmatch(3) de la biblioteca C no puede resolver rutas relativas. Si bien esto suele ser solo un inconveniente para las reglas que otorgan privilegios, puede resultar en un problema de seguridad para las reglas que restan o revocan privilegios.

    Por ejemplo, dada la siguiente entrada en el archivo sudoers:

    john	TODOS = /usr/bin/passwd [a-zA-Z0-9]*, /usr/bin/chsh [a-zA-Z0-9]*,\
              /usr/bin/chfn [a-zA-Z0-9]*, !/usr/bin/* root

    El usuario john todavía puede ejecutar ‘/usr/bin/passwd root’ si fast_glob está habilitado, cambiando a /usr/bin y ejecutando en su lugar ‘./passwd root’.

    Otro problema potencial es que cuando sudo ejecuta el comando, debe usar el comando o la ruta especificada por el usuario en lugar de una ruta listada en el archivo sudoers. Esto puede conducir a una condición de carrera de "tiempo de verificación frente a tiempo de uso".

    Comodines en argumentos de comando

    Los argumentos de la línea de comandos se comparan como una única cadena concatenada. Esto significa que un carácter comodín como ‘?’ o ‘*’ coincidirá en los límites de las palabras, lo cual puede ser inesperado. Por ejemplo, mientras que una entrada de sudoers como:

    %operador TODOS = /bin/cat /var/log/messages*

    permitirá comandos como:

    $ sudo cat /var/log/messages.1

    También permitirá:

    $ sudo cat /var/log/messages /etc/shadow

    lo cual probablemente no era la intención. Una alternativa más segura es usar una expresión regular para comparar los argumentos de la línea de comandos. El ejemplo anterior se puede reescribir como una expresión regular:

    %operador TODOS = /bin/cat ^/var/log/messages[^[:space:]]*$

    La expresión regular solo coincidirá con un solo archivo con un nombre que comience con /var/log/messages y no incluya espacios en blanco en el nombre. A menudo es mejor procesar la línea de comandos fuera del archivo sudoers en un lenguaje de scripting para cualquier cosa no trivial.

    Expresiones regulares en nombres de comando

    Usar una expresión regular para comparar un nombre de comando tiene las mismas implicaciones de seguridad que usar la opción fast_glob:

    • No es posible negar de forma fiable los comandos cuando el nombre de ruta es una expresión regular.
    • Cuando sudo ejecuta el comando, debe usar el comando o la ruta especificada por el usuario en lugar de una ruta listada en el archivo sudoers. Esto puede conducir a una condición de carrera de "tiempo de verificación frente a tiempo de uso".

    Estos problemas no se aplican a las reglas donde solo se comparan las opciones de la línea de comandos usando una expresión regular.

    Prevención de escapes de shell

    Una vez que sudo ejecuta un programa, ese programa es libre de hacer lo que quiera, incluyendo ejecutar otros programas. Esto puede ser un problema de seguridad, ya que no es raro que un programa permita escapes de shell, lo que permite a un usuario eludir el control de acceso y el registro de sudo. Los programas comunes que permiten escapes de shell incluyen shells (obviamente), editores, paginadores, correo y programas de terminal.

    Existen cuatro enfoques básicos para este problema:

    restringir
    Evite otorgar a los usuarios acceso a comandos que les permitan ejecutar comandos arbitrarios. Muchos editores tienen un modo restringido donde los escapes de shell están deshabilitados, aunque sudoedit es una mejor solución para ejecutar editores a través de sudo. Debido a la gran cantidad de programas que ofrecen escapes de shell, restringir a los usuarios al conjunto de programas que no lo hacen a menudo no es factible.
    interceptar
    En la mayoría de los sistemas, la funcionalidad de interceptar de sudo puede usarse para interceptar transparentemente un intento de ejecutar un nuevo comando, permitirlo o denegarlo basándose en las reglas de sudoers, y registrar el resultado. Por ejemplo, esto puede usarse para restringir los comandos ejecutados desde dentro de un shell privilegiado o editor. Sin embargo, no todos los programas operan correctamente cuando interceptar está habilitado.

    Existen dos mecanismos subyacentes que pueden usarse para implementar el modo interceptar: dso y trace. La configuración intercept_type se puede usar para seleccionar entre ellos.

    El primer mecanismo, dso, reemplaza las funciones de la biblioteca C estándar que se usan para ejecutar un comando. Lo hace configurando una variable de entorno (generalmente LD_PRELOAD) a la ruta de un objeto compartido dinámico, o biblioteca compartida, que contiene versiones personalizadas de las funciones de biblioteca execve(2), execl(3), execle(3), execlp(3), execv(3), execvp(3), execvpe(3), y system(3) que se conectan de vuelta a sudo para una decisión de política. Tenga en cuenta, sin embargo, que esto se aplica solo a ejecutables enlazados dinámicamente. No es posible interceptar comandos para ejecutables enlazados estáticamente o ejecutables que se ejecutan bajo emulación binaria de esta manera. Debido a que la mayoría de los cargadores dinámicos ignoran LD_PRELOAD (o su equivalente) al ejecutar programas set-user-ID y set-group-ID, sudoers no permitirá que tales programas se ejecuten en modo interceptar por defecto. El mecanismo dso es incompatible con el soporte RBAC SELinux de sudo (pero vea abajo). SELinux deshabilita LD_PRELOAD por defecto e interfiere con la herencia de descriptores de archivo, en la que sudo se basa.

    El segundo mecanismo, trace, está disponible en sistemas Linux que admiten el filtrado seccomp(2). Utiliza ptrace(2) y seccomp(2) para interceptar la llamada al sistema execve(2) en lugar de pre-cargar un objeto compartido dinámico. Se admiten tanto ejecutables estáticos como dinámicos, y es compatible con el modo RBAC SELinux de sudo. Las funciones que utilizan la llamada al sistema execveat(2), como fexecve(3), no se interceptan actualmente. Los programas que dependen de ptrace(2), como depuradores y rastreadores de llamadas al sistema (como strace(1) y truss(1)) no podrán funcionar si interceptar está habilitado en modo trace. Esta misma restricción se aplica a la opción de sudoers log_subcmds.

    La función interceptar se sabe que funciona en Solaris, *BSD, Linux, macOS, HP-UX 11.x y AIX 5.3 y superior. Debería ser compatible con la mayoría de los sistemas operativos que admiten la variable de entorno LD_PRELOAD o un equivalente. No es posible interceptar comandos integrados en el shell ni restringir la capacidad de leer o escribir archivos sensibles desde dentro de un shell.

    Para habilitar el modo de interceptación por comando, use la etiqueta INTERCEPTAR como se documenta en la sección de Especificación de Usuario anterior. Aquí está ese ejemplo nuevamente:

    chuck	investigación = INTERCEPTAR: TODOS

    Esto permite al usuario chuck ejecutar cualquier comando en la máquina de “investigación” en modo de interceptación. Cualquier comando ejecutado a través de escapes de shell será validado y registrado por sudo. Si no está seguro de si su sistema es capaz de admitir interceptar, siempre puede probarlo y verificar si los comandos externos ejecutados a través de un shell se registran cuando interceptar está habilitado.

    intercept_verify

    Existe una condición de carrera inherente entre el momento en que se comprueba un comando contra las reglas de sudoers y el momento en que realmente se ejecuta. Si a un usuario se le permite ejecutar comandos arbitrarios, podría ser capaz de cambiar los argumentos de execve(2) en el programa después de que la comprobación de políticas de sudoers se haya completado, pero antes de que se ejecute el nuevo comando. A partir de la versión 1.9.12, el método trace verificará que el comando y sus argumentos no hayan cambiado después de que execve(2) se haya completado, pero antes de que la ejecución del nuevo programa tenga la oportunidad de ejecutarse. Este no es el caso con el método dso. Consulte la descripción de la configuración intercept_verify para obtener más información.

    log

    Hay dos formas separadas pero relacionadas de registrar comandos adicionales. La primera es habilitar el registro de E/S utilizando el indicador log_output. Esto registrará la salida del comando, pero no creará una entrada de registro de eventos cuando se ejecute el comando adicional. La segunda es habilitar el indicador log_subcmds en sudoers, que creará una entrada de registro de eventos cada vez que se ejecute un nuevo comando. Si también está habilitado el registro de E/S, la entrada de registro incluirá un desplazamiento de tiempo en el registro de E/S para indicar cuándo se ejecutó el comando. Este desplazamiento puede pasarse a la utilidad sudoreplay(8) para reproducir el registro de E/S en el momento exacto en que se ejecutó el comando. El indicador log_subcmds utiliza el mismo mecanismo que intercept (ver arriba) y tiene las mismas limitaciones.

    noexec

    La funcionalidad noexec de sudo se puede utilizar para evitar que un programa ejecutado por sudo ejecute cualquier otro programa. En la mayoría de los sistemas, utiliza el mismo mecanismo de LD_PRELOAD que intercept (ver arriba) y, por lo tanto, se aplican las mismas advertencias. La funcionalidad noexec es capaz de bloquear la ejecución de comandos ejecutados a través de las funciones execve(2), execl(3), execle(3), execlp(3), exect(3), execv(3), execveat(3), execvP(3), execvp(3), execvpe(3), fexecve(3), popen(3), posix_spawn(3), posix_spawnp(3), system(3) y wordexp(3). En Linux, se utiliza un filtro de seccomp(2) para implementar noexec. En Solaris 10 y versiones posteriores, noexec utiliza privilegios de Solaris en lugar de la variable de entorno LD_PRELOAD.

    Para habilitar noexec para un comando, use la etiqueta NOEXEC como se documenta en la sección Especificación de usuario anterior. Aquí está ese ejemplo nuevamente:

    aaron	shanty = NOEXEC: /usr/bin/more, /usr/bin/vi

    Esto permite al usuario aaron ejecutar /usr/bin/more y /usr/bin/vi con noexec habilitado. Esto evitará que esos dos comandos ejecuten otros comandos (como un shell). Si no está seguro de si su sistema es capaz de admitir noexec, siempre puede probarlo y verificar si las escapadas del shell funcionan cuando noexec está habilitado.

    Restringir las escapadas del shell no es una panacea. Los programas que se ejecutan como root todavía son capaces de muchas operaciones potencialmente peligrosas (como cambiar o sobrescribir archivos) que podrían conducir a una escalada de privilegios no deseada. En el caso específico de un editor, un enfoque más seguro es dar al usuario permiso para ejecutar sudoedit (ver abajo).

    Edición segura

    sudoers incluye soporte para sudoedit que permite a los usuarios editar archivos de forma segura con el editor de su elección. Como sudoedit es un comando integrado, debe especificarse en el archivo sudoers sin una ruta inicial. Sin embargo, puede aceptar argumentos de línea de comandos al igual que un comando normal. Se espera que los comodines utilizados en los argumentos de la línea de comandos de sudoedit sean nombres de ruta, por lo que un comodín no coincidirá con una barra diagonal ('/').

    A diferencia de otros comandos de sudo, el editor se ejecuta con los permisos del usuario que lo invoca y con el entorno sin modificar. Puede encontrar más información en la descripción de la opción -e en sudo(8).

    Por ejemplo, para permitir que el usuario operador edite el archivo "mensaje del día" en cualquier máquina:

    operator ALL = sudoedit /etc/motd

    El usuario operador luego ejecuta sudoedit de la siguiente manera:

    $ sudoedit /etc/motd

    El editor se ejecutará como el usuario operador, no como root, sobre una copia temporal de /etc/motd. Después de editar el archivo, /etc/motd se actualizará con el contenido de la copia temporal.

    Los usuarios nunca deben tener permiso sudoedit para editar un archivo que resida en un directorio al que el usuario tenga acceso de escritura, ya sea directamente o a través de un comodín. Si el usuario tiene acceso de escritura al directorio, es posible reemplazar el archivo legítimo con un enlace a otro archivo, lo que permite editar archivos arbitrarios. Para evitar esto, a partir de la versión 1.8.16, los enlaces simbólicos no se seguirán en directorios escribibles y sudoedit se negará a editar un archivo ubicado en un directorio escribible a menos que la opción sudoedit_checkdir se haya deshabilitado o el usuario que invoca sea root. Además, en la versión 1.8.15 y posteriores, sudoedit se negará a abrir un enlace simbólico a menos que la opción sudoedit_follow esté habilitada o el comando sudoedit sea precedido por la etiqueta FOLLOW en el archivo sudoers.

    Comprobaciones del archivo de marca de tiempo

    sudoers comprobará la propiedad de su directorio de marcas de tiempo (/run/sudo/ts por defecto) e ignorará el contenido del directorio si no es propiedad de root o si es escribible por un usuario que no sea root. Las versiones anteriores de sudo almacenaban archivos de marca de tiempo en /tmp; ya no se recomienda ya que podría ser posible que un usuario cree la marca de tiempo en sí mismo en sistemas que permiten a los usuarios no privilegiados cambiar la propiedad de los archivos que crean.

    Si bien el directorio de marcas de tiempo debería limpiarse al reiniciar, no todos los sistemas contienen un directorio /run o /var/run. Para evitar posibles problemas, sudoers ignorará los archivos de marca de tiempo anteriores al arranque de la máquina en sistemas donde el momento del arranque esté disponible.

    Algunos sistemas con entornos de escritorio gráficos permiten a los usuarios no privilegiados cambiar el reloj del sistema. Dado que sudoers se basa en el reloj del sistema para la validación de la marca de tiempo, en tales sistemas podría ser posible que un usuario ejecute sudo durante más tiempo que timestamp_timeout retrocediendo el reloj. Para combatir esto, sudoers utiliza un reloj monotónico (que nunca retrocede) para sus marcas de tiempo si el sistema lo admite.

    sudoers no honrará las marcas de tiempo establecidas muy en el futuro. Se ignorarán las marcas de tiempo con una fecha mayor que tiempo_actual + 2 * TIMEOUT y sudoers registrará y se quejará.

    Si la opción timestamp_type se establece en "tty", el registro de marca de tiempo incluye el número de dispositivo de la terminal con la que se autenticó el usuario. Esto proporciona granularidad por terminal, pero los registros de marca de tiempo aún pueden sobrevivir a la sesión del usuario.

    A menos que la opción timestamp_type se establezca en "global", el registro de marca de tiempo también incluye el ID de sesión del proceso que se autenticó por última vez. Esto evita que los procesos en diferentes sesiones de terminal utilicen el mismo registro de marca de tiempo. En sistemas donde se puede consultar la hora de inicio de un proceso, la hora de inicio del líder de la sesión se registra en el registro de marca de tiempo. Si no hay una terminal presente o la opción timestamp_type se establece en "ppid", se utiliza la hora de inicio del proceso padre en su lugar. En la mayoría de los casos, esto evitará que un registro de marca de tiempo se reutilice sin que el usuario ingrese una contraseña al cerrar sesión y volver a iniciarla.

ADVERTENCIAS

El archivo sudoers debe siempre editarse con la utilidad visudo, que bloquea el archivo y comprueba si hay errores de sintaxis. Si sudoers contiene errores de sintaxis, sudo puede negarse a ejecutarse, lo cual es un problema grave si sudo es su único método para obtener privilegios de superusuario. Las versiones recientes de sudoers intentarán recuperarse después de un error de sintaxis ignorando el resto de la línea tras encontrar un error. Las versiones anteriores de sudo no se ejecutarán si sudoers contiene un error de sintaxis.

Al usar netgroups de máquinas (en contraposición a usuarios), si almacena nombres de host completamente calificados en el netgroup (como suele ser el caso), debe tener el nombre de host de la máquina completamente calificado tal como lo devuelve el comando hostname o usar la opción fqdn en sudoers.
