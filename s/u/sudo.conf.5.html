SUDO.CONF(5) Manual de formatos de archivo SUDO.CONF(5)

NOMBRE

sudo.conf — configuración para el front-end de sudo

DESCRIPCIÓN

El archivo sudo.conf se utiliza para configurar el front-end de sudo. Se utiliza para configurar plugins de sudo, nombres de ruta agnósticos a plugins, flags de depuración y otras configuraciones.

El archivo sudo.conf soporta las siguientes directivas, descritas en detalle a continuación.

Plugin
un plugin de aprobación, auditoría, registro de E/S o política de seguridad
Path
una ruta agnóstica a plugins
Set
una configuración del front-end, como disable_coredump o group_source
Debug
flags de depuración para ayudar a depurar sudo, sudoreplay, visudo y el plugin sudoers.

El signo de almohadilla (‘#’) se usa para indicar un comentario. Tanto el carácter de comentario como cualquier texto después de él, hasta el final de la línea, se ignoran.

Las líneas largas se pueden continuar con una barra invertida (‘\’) como el último carácter de la línea. El espacio en blanco inicial se elimina del principio de las líneas incluso cuando se utiliza un carácter de continuación.

Las líneas que no son comentarios y que no comienzan con Plugin, Path, Debug, o Set se ignoran silenciosamente.

El archivo sudo.conf siempre se analiza en la localidad ‘C’.

Configuración de Plugins

sudo soporta una arquitectura de plugins para políticas de seguridad y registro de entrada/salida. Terceros pueden desarrollar y distribuir sus propios plugins de política y registro de E/S para trabajar sin problemas con el front-end de sudo. Los plugins se cargan dinámicamente basándose en el contenido de sudo.conf.

Una línea Plugin consiste en la palabra clave Plugin, seguida del nombre_símbolo y la ruta al objeto compartido dinámico que contiene el plugin. El nombre_símbolo es el nombre de la struct approval_plugin, struct audit_plugin, struct io_plugin, o struct policy_plugin definida por el plugin. Si un plugin implementa múltiples tipos de plugin, debe haber una línea Plugin para cada nombre de símbolo único. La ruta puede ser completamente calificada o relativa. Si no está completamente calificada, es relativa al directorio especificado por la configuración plugin_dir de tipo Path, que por defecto es /usr/lib/sudo. En otras palabras:

Plugin sudoers_policy sudoers.so

es equivalente a:

Plugin sudoers_policy /usr/lib/sudo/sudoers.so

Si el plugin se compiló estáticamente en el binario de sudo en lugar de instalarse como un objeto compartido dinámico, la ruta debe especificarse sin un directorio inicial, ya que realmente no existe en el sistema de archivos. Por ejemplo:

Plugin sudoers_policy sudoers.so

En sistemas AIX, el plugin puede ser un objeto compartido que termine en ‘.so’ o un archivo de archivo que contenga un objeto compartido que termine en ‘.a’ con el nombre del objeto compartido entre paréntesis al final.

A partir de sudo 1.8.5, cualquier parámetro adicional después de la ruta se pasa como argumento a la función open del plugin. Por ejemplo, para anular el modo del archivo sudoers por defecto en tiempo de compilación:

Plugin sudoers_policy sudoers.so sudoers_mode=0440

Consulte el manual de sudoers(5) para obtener una lista de argumentos compatibles.

El mismo objeto compartido dinámico puede contener múltiples plugins, cada uno con un nombre de símbolo diferente. El archivo debe pertenecer al usuario con ID 0 y solo ser escribible por su propietario. Debido a las ambigüedades que surgen de políticas compuestas, solo se puede especificar un plugin de política. Esta limitación no se aplica a los plugins de E/S.

Si no existe el archivo sudo.conf, o si no contiene líneas Plugin, el plugin sudoers se utilizará como política de seguridad por defecto, para el registro de E/S (si está habilitado por la política) y para la auditoría. Esto es equivalente a lo siguiente:

Plugin sudoers_policy sudoers.so
Plugin sudoers_io sudoers.so
Plugin sudoers_audit sudoers.so

A partir de la versión sudo 1.9.1, parte de la funcionalidad de registro del plugin sudoers se ha movido del plugin de política a un plugin de auditoría. Para mantener la compatibilidad con los archivos sudo.conf de versiones anteriores de sudo, si sudoers se configura como política de seguridad, también se utilizará como plugin de auditoría. Esto garantiza que el comportamiento de registro sea coherente con el de las versiones de sudo 1.9.0 y anteriores.

Para más información sobre la arquitectura de plugins de sudo, consulte el manual de sudo_plugin(5).

Configuraciones de Ruta

Una línea Path consiste en la palabra clave Path, seguida del nombre de la ruta a establecer y su valor. Por ejemplo:

Path intercept /usr/lib/sudo/sudo_intercept.so
Path noexec /usr/lib/sudo/sudo_noexec.so
Path askpass /usr/X11R6/bin/ssh-askpass

Si no se especifica un nombre de ruta, las características que dependen de la configuración especificada se deshabilitarán. Deshabilitar las configuraciones de Path solo es compatible en sudo versión 1.8.16 y superior.

Las siguientes rutas agnósticas a plugins pueden configurarse en el archivo /etc/sudo.conf:

askpass
La ruta completa a un programa auxiliar utilizado para leer la contraseña del usuario cuando no hay un terminal disponible. Esta puede ser la situación cuando sudo se ejecuta desde una aplicación gráfica (en contraposición a una basada en texto). El programa especificado por askpass debe mostrar el argumento que se le pasa como indicación y escribir la contraseña del usuario en la salida estándar. El valor de askpass puede ser anulado por la variable de entorno SUDO_ASKPASS.
devsearch
Una ruta de búsqueda ordenada y separada por dos puntos de directorios en los que buscar nodos de dispositivos. Esto se utiliza al mapear el número de dispositivo tty del proceso a un nombre de dispositivo en sistemas que no proporcionan dicho mecanismo. Sudo no recursará en subdirectorios. Si los dispositivos de terminal se pueden ubicar en un subdirectorio de /dev, esa ruta debe estar explícitamente listada en devsearch. El valor por defecto es /dev/pts:/dev/vt:/dev/term:/dev/zcons:/dev/pty:/dev

Esta opción se ignora en sistemas que soportan las funciones devname() o _ttyname_dev(), por ejemplo BSD, macOS y Solaris.

intercept
La ruta a una biblioteca compartida que contiene envolturas para las funciones de biblioteca execve(2), execl(3), execle(3), execlp(3), execv(3), execvp(3), execvpe(3), y system(3) que interceptan

ts intenta ejecutar comandos adicionales y realiza una verificación de políticas antes de permitir su ejecución. Esto se utiliza para implementar la funcionalidad de intercept y log_subcmds en sistemas que admiten LD_PRELOAD o su equivalente.

La ruta intercept puede establecerse como una única ruta completamente calificada, o, para sistemas que admiten variables de entorno LD_PRELOAD separadas para ejecutables de 32 y 64 bits, opcionalmente puede establecerse como dos rutas completamente calificadas separadas por dos puntos (‘:’). La primera ruta debe ser la versión de 32 bits y la segunda la de 64 bits. Esta forma de dos rutas actualmente solo se admite en sistemas AIX y Solaris. El valor predeterminado es /usr/lib/sudo/sudo_intercept.so.

noexec
La ruta a una biblioteca compartida que contiene envoltorios para las funciones de biblioteca execve(2), execl(3), execle(3), execlp(3), exect(3), execv(3), execveat(3), execvP(3), execvp(3), execvpe(3), fexecve(3), popen(3), posix_spawn(3), posix_spawnp(3), system(3) y wordexp(3) que impiden la ejecución de comandos adicionales. Esto se utiliza para implementar la funcionalidad de noexec en sistemas que admiten LD_PRELOAD o su equivalente.

La ruta noexec puede establecerse como una única ruta completamente calificada, o, para sistemas que admiten variables de entorno LD_PRELOAD separadas para ejecutables de 32 y 64 bits, opcionalmente puede establecerse como dos rutas completamente calificadas separadas por dos puntos (‘:’). La primera ruta debe ser la versión de 32 bits y la segunda la de 64 bits. Esta forma de dos rutas actualmente solo se admite en sistemas AIX y Solaris. El valor predeterminado es /usr/lib/sudo/sudo_noexec.so.

plugin_dir
El directorio predeterminado a utilizar al buscar complementos que se especifican sin un nombre de ruta completamente calificado. El valor predeterminado es /usr/lib/sudo.

Otras configuraciones

El archivo sudo.conf también admite la siguiente configuración del lado del cliente:

disable_coredump
Los volcados de memoria de sudo en sí mismos están deshabilitados por defecto para evitar la divulgación de información potencialmente sensible. Para ayudar a depurar fallos de sudo, es posible que desee volver a habilitar los volcados de memoria estableciendo “disable_coredump” en falso en sudo.conf de la siguiente manera: 
Set disable_coredump false

Todos los sistemas operativos modernos imponen restricciones a los volcados de memoria de procesos que establecen el ID de usuario como sudo, por lo que esta opción se puede habilitar sin comprometer la seguridad. Para obtener realmente un archivo de volcado de memoria de sudo, probablemente necesitará habilitar los volcados de memoria para procesos que establecen el ID de usuario. En sistemas BSD y Linux, esto se logra con el comando sysctl(8). En Solaris, se utiliza el comando coreadm(1m) para configurar el comportamiento de los volcados de memoria.

Esta configuración solo está disponible en la versión sudo 1.8.4 y posteriores.

group_source
sudo pasa la lista de grupos del usuario que llama al complemento de política y de E/S. En la mayoría de los sistemas, hay un límite superior para la cantidad de grupos a los que un usuario puede pertenecer simultáneamente (típicamente 16 para compatibilidad con NFS). En sistemas con la utilidad getconf(1), ejecutar:
getconf NGROUPS_MAX
devolverá el número máximo de grupos.

Sin embargo, todavía es posible ser miembro de un número mayor de grupos; simplemente no se incluirán en la lista de grupos devuelta por el kernel para el usuario. A partir de la versión sudo 1.8.7, si la lista de grupos del kernel del usuario tiene el número máximo de entradas, sudo consultará directamente la base de datos de grupos para determinar la lista de grupos. Esto hace posible que la política de seguridad realice coincidencias por nombre de grupo incluso cuando el usuario es miembro de más que el número máximo de grupos.

La configuración group_source permite al administrador cambiar este comportamiento predeterminado. Los valores admitidos para group_source son:

static
Utiliza la lista de grupos estática que devuelve el kernel. Recuperar la lista de grupos de esta manera es muy rápido, pero está sujeta a un límite superior como se describió anteriormente. Es "estático" en el sentido de que no refleja los cambios en la base de datos de grupos realizados después de que el usuario inicia sesión. Este fue el comportamiento predeterminado antes de sudo 1.8.7.
dynamic
Siempre consulta directamente la base de datos de grupos. Es "dinámico" en el sentido de que los cambios realizados en la base de datos de grupos después de que el usuario inicia sesión se reflejarán en la lista de grupos. En algunos sistemas, consultar la base de datos de grupos para todos los grupos de un usuario puede consumir mucho tiempo al consultar una base de datos de grupos basada en red. La mayoría de los sistemas operativos proporcionan un método eficiente para realizar tales consultas. Actualmente, sudo admite consultas eficientes de grupos en AIX, BSD, Linux, macOS y Solaris. Este es el comportamiento predeterminado en macOS en sudo 1.9.6 y posteriores.
adaptive
Solo consulta la base de datos de grupos si la lista de grupos estática devuelta por el kernel tiene el número máximo de entradas. Este es el comportamiento predeterminado en sistemas que no sean macOS en sudo 1.8.7 y posteriores.

Por ejemplo, para hacer que sudo use solo la lista estática de grupos del kernel para el usuario:

Set group_source static

Esta configuración solo está disponible en la versión sudo 1.8.7 y posteriores.

max_groups
El número máximo de grupos de usuario a recuperar de la base de datos de grupos. Los valores menores que uno o mayores que 1024 se ignorarán. Esta configuración solo se utiliza al consultar la base de datos de grupos directamente. Está destinada a usarse en sistemas donde no es posible detectar cuándo la matriz a poblar con entradas de grupo no es lo suficientemente grande. Por defecto, sudo asignará cuatro veces el número máximo de grupos del sistema (ver arriba) y volverá a intentar con el doble de ese número si la consulta de la base de datos de grupos falla.

Esta configuración solo está disponible en la versión sudo 1.8.7 y posteriores. No debería ser necesario en las versiones sudo 1.8.24 y posteriores, y puede eliminarse en una versión posterior.

probe_interfaces
Por defecto, sudo sondeará las interfaces de red del sistema y pasará la dirección IP de cada interfaz habilitada al complemento de política. Esto permite que el complemento coincida con reglas basadas en la dirección IP sin tener que consultar DNS. En sistemas Linux con un gran número de interfaces virtuales, esto puede llevar una cantidad de tiempo no despreciable. Si no se requiere la coincidencia basada en IP, la sonda de interfaces de red se puede deshabilitar de la siguiente manera: 
Set probe_interfaces false

Esta configuración solo está disponible en la versión sudo 1.8.10 y posteriores.

Configuraciones de depuración

sudo versiones 1.8.4 y posteriores admiten un marco de depuración flexible que puede registrar lo que sudo está haciendo internamente si hay un problema.

Una línea de Debug consiste en la palabra clave Debug, seguida del nombre del programa, complemento u objeto compartido a depurar, el nombre del archivo de depuración y una lista separada por comas de las banderas de depuración. La sintaxis de la bandera de depuración utilizada por sudo, el complemento sudoers junto con sus programas y objetos compartidos asociados es subsystem@priority, pero un complemento de terceros es libre de usar un formato diferente siempre que no incluya una coma (‘,’).

En sistemas AIX, una línea de Debug coincidirá con un complemento especificado como el nombre de un archivo de objeto compartido estilo SVR4 que termina en ‘.so’, un archivo de archivo que termina en ‘.a’, o un archivo de archivo que termina en ‘.a’ con el nombre del objeto compartido entre paréntesis.

Ejemplos:

Debug sudo /var/log/sudo_debug all@warn,plugin@info

registraría todas las declaraciones de depuración en el nivel warn y superiores, además de las del nivel info para el subsistema de complementos.

Debug sudo_intercept.so /var/log/intercept_debug all@debug

registraría todas las declaraciones de depuración, independientemente del nivel, para la biblioteca compartida sudo_intercept.so que implementa la funcionalidad de interceptación de sudo en algunos sistemas.

Debug sudoers.so /var/log/sudoers_debug all@debug

registraría todas las declaraciones de depuración, independientemente del nivel, para el complemento sudoers. Consulte sudoers(5) para obtener la lista completa de subsistemas admitidos por sudoers\n

sudo User Manual

NAME

sudo.conf — sudoers configuration file

DESCRIPTION

The sudoers configuration file, /etc/sudo.conf, is used to control the behavior of the sudo program. It is a simple key-value pair file.

Each line in the file is either a comment, an empty line, or a configuration directive. Comments begin with a # character and extend to the end of the line. Empty lines are ignored.

Configuration directives are of the form:

key: value

Whitespace around the key and value is ignored. Values may be quoted strings. If a value contains whitespace, it must be quoted.

The following configuration directives are supported:

Defaults
Sets default values for sudo options. The syntax is similar to the sudoers file, but only global options are allowed.
Path
Specifies a colon-separated list of directories to search for commands. This is equivalent to the secure_path option in sudoers.
Plugin
Specifies a plugin to load. The syntax is: 
Plugin: plugin_name plugin_path
The plugin_name is the name of the plugin (e.g., sudoers). The plugin_path is the full path to the plugin library.
Enable
Enables a specific feature. For example: 
Enable timestamp
This enables the sudo timestamp file functionality.
Disable
Disables a specific feature. For example: 
Disable login_defs
This disables the use of login_defs.

FILES

/etc/sudo.conf
The sudoers configuration file.

EXAMPLES

To specify a custom path for commands:

Path: /usr/local/bin:/usr/bin:/bin

To load a custom sudoers plugin:

Plugin: sudoers /usr/lib/sudo/sudoers.so
