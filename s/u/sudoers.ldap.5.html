SUDOERS.LDAP(5) Manual de Formatos de Archivo SUDOERS.LDAP(5)

NOMBRE

sudoers.ldap — configuración de sudo para LDAP

DESCRIPCIÓN

Además del archivo sudoers estándar, sudo se puede configurar a través de LDAP. Esto puede ser especialmente útil para sincronizar sudoers en un entorno distribuido y a gran escala.

Usar LDAP para sudoers tiene varios beneficios:

  • sudo ya no necesita leer sudoers en su totalidad. Cuando se utiliza LDAP, solo hay dos o tres consultas LDAP por invocación. Esto lo hace especialmente rápido y particularmente utilizable en entornos LDAP.
  • Es posible especificar opciones por entrada que anulen las opciones globales por defecto. /etc/sudoers solo admite opciones por defecto y opciones limitadas asociadas a usuarios/hosts/comandos/alias. La sintaxis es complicada y puede ser difícil de entender para los usuarios. Colocar las opciones directamente en la entrada es más natural.
  • El programa visudo ya no es necesario. visudo proporciona bloqueo y verificación de sintaxis del archivo /etc/sudoers. Dado que las actualizaciones de LDAP son atómicas, el bloqueo ya no es necesario. Como la sintaxis se verifica al insertar los datos en LDAP, no hay necesidad de una herramienta especializada para comprobar la sintaxis.

Contenedor LDAP de SUDOers

La configuración de sudoers está contenida en el contenedor LDAP ‘ou=SUDOers’.

Sudo primero busca la entrada ‘cn=defaults’ en el contenedor SUDOers. Si se encuentra, el atributo multivalor sudoOption se analiza de la misma manera que una línea global Defaults en /etc/sudoers. En el siguiente ejemplo, la variable SSH_AUTH_SOCK se conservará en el entorno para todos los usuarios.

dn: cn=defaults,ou=SUDOers,dc=my-domain,dc=com
objectClass: top
objectClass: sudoRole
cn: defaults
description: Default sudoOption's go here
sudoOption: env_keep+=SSH_AUTH_SOCK

El equivalente de un sudoer en LDAP es un sudoRole. Consta de los siguientes atributos:

sudoUser
Un nombre de usuario, ID de usuario (precedido por ‘#’), nombre o ID de grupo de Unix (precedido por ‘%’ o ‘%#’ respectivamente), netgroup de usuarios (precedido por ‘+’), o nombre o ID de grupo no Unix (precedido por ‘%:’ o ‘%:#’ respectivamente). Los netgroups de usuarios se comparan usando solo los miembros de usuario y dominio; el miembro de host no se utiliza al comparar. El soporte para grupos no Unix solo está disponible cuando un plugin_grupo apropiado está definido en el objeto sudoRole global de defaults. Si una entrada sudoUser está precedida por un signo de exclamación, ‘!’, y la entrada coincide, se ignorará el sudoRole en el que reside. Las entradas negadas de sudoUser solo son compatibles con la versión 1.9.9 o superior.
sudoHost
Un nombre de host, dirección IP, red IP o netgroup de hosts (precedido por un ‘+’). El valor especial ALL coincidirá con cualquier host. Los netgroups de hosts se comparan usando solo los miembros de host (tanto calificados como no calificados) y dominio; el miembro de usuario no se utiliza al comparar. Si una entrada sudoHost está precedida por un signo de exclamación, ‘!’, y la entrada coincide, se ignorará el sudoRole en el que reside. Las entradas negadas de sudoHost solo son compatibles con la versión 1.8.18 o superior.
sudoCommand
Un nombre de comando Unix completamente calificado con argumentos de línea de comandos opcionales, que potencialmente incluyen caracteres comodín (también conocidos como wildcards). Si un nombre de comando está precedido por un signo de exclamación, ‘!’, al usuario se le prohibirá ejecutar ese comando.

El comando incorporado “sudoedit” se utiliza para permitir a un usuario ejecutar sudo con la opción -e (o como sudoedit). Puede aceptar argumentos de línea de comandos al igual que un comando normal. A diferencia de otros comandos, “sudoedit” está incorporado en sudo y debe especificarse sin una ruta inicial.

El valor especial ALL coincidirá con cualquier comando.

Si un nombre de comando está precedido por un resumen SHA-2, solo se permitirá si el resumen coincide. Esto puede ser útil en situaciones en las que el usuario que invoca sudo tiene acceso de escritura al comando o a su directorio padre. Los siguientes formatos de resumen son compatibles: sha224, sha256, sha384 y sha512. El nombre del resumen debe ir seguido de dos puntos (‘:’) y luego el resumen real, en formato hexadecimal o base64. Por ejemplo, dado el siguiente valor para sudoCommand:

El usuario solo podrá ejecutar /bin/ls si su resumen sha224 coincide con el valor especificado. Los resúmenes de comandos solo son compatibles con la versión 1.8.7 o superior.

Idéntico en función a las opciones globales descritas anteriormente, pero específico del sudoRole en el que reside.
sudoRunAsUser
Un nombre de usuario o ID de usuario (precedido por ‘#’) como el que se pueden ejecutar los comandos o un grupo de Unix (precedido por un ‘%’) o netgroup de usuarios (precedido por un ‘+’) que contiene una lista de usuarios como los que se pueden ejecutar los comandos. El valor especial ALL coincidirá con cualquier usuario. Si una entrada sudoRunAsUser está precedida por un signo de exclamación, ‘!’, y la entrada coincide, se ignorará el sudoRole en el que reside. Si sudoRunAsUser está especificado pero vacío, coincidirá con el usuario que invoca. Si ni sudoRunAsUser ni sudoRunAsGroup están presentes, se utilizará el valor de la opción runas_default de sudoOption (por defecto es root).

sudoRunAsGroup

El atributo sudoRunAsGroup solo está disponible en las versiones 1.7.0 y superiores de sudo. Las entradas negadas de sudoRunAsGroup solo son compatibles con la versión 1.8.26 o superior.

LDAP sudoers

When sudo is configured to use an LDAP directory to store the sudoers information, it uses the sudoers(5) syntax, but stores the information in an LDAP schema.

The schema uses the object class sudoRole. A sudoRole entry contains the permissions for a set of users and hosts. The following attributes are available:

sudoUser
A user name, a Unix group name prefixed with a %, or a netgroup name prefixed with a @. The user, group, or netgroup is granted the permissions defined in the sudoRole. If multiple sudoUser entries are present, the user matches if they are a member of any of the listed users, groups, or netgroups.
sudoHost
A host name or a netgroup name prefixed with a @. The permissions defined in the sudoRole apply to the specified host(s). If multiple sudoHost entries are present, the host matches if it is a member of any of the listed hosts or netgroups. The special value ALL matches any host.
sudoCommand
A command path, a command name, or a command pattern. The permissions defined in the sudoRole apply to the specified command(s). If multiple sudoCommand entries are present, the command matches if it matches any of the listed commands or patterns. The special value ALL matches any command. Commands may be negated by prefixing with a !.
sudoRunAsUser
A user name, a Unix group name prefixed with a %, or a netgroup name prefixed with a @. The user defined in the sudoRole may run the command as the specified user(s). If multiple sudoRunAsUser entries are present, the user matches if they are a member of any of the listed users, groups, or netgroups. The special value ALL matches any user. The special value ROOT matches the root user.
sudoRunAsGroup
A Unix group name or a netgroup name prefixed with a @. The user defined in the sudoRole may run the command as the specified group(s). If multiple sudoRunAsGroup entries are present, the group matches if it is a member of any of the listed groups or netgroups. The special value ALL matches any group.
sudoOption
A sudo option (e.g., authenticate, nopasswd, noexec). The options defined in the sudoRole are applied when the user runs the command. If multiple sudoOption entries are present, all options are applied.
sudoNotBefore
A timestamp in the form ‘yyyymmddHHMMSSZ’ that indicates a start date/time, before which the sudoRole is not valid. If multiple sudoNotBefore entries are present, the earliest is used. Timestamps must be in Coordinated Universal Time (UTC), not the local timezone. The minute and seconds portions are optional, but some LDAP servers require that they be present (contrary to the RFC).

The sudoNotBefore attribute is only available in sudo versions 1.7.5 and higher and must be explicitly enabled via the SUDOERS_TIMED option in /etc/openldap/ldap.conf.

sudoNotAfter
A timestamp in the form ‘yyyymmddHHMMSSZ’ that indicates an expiration date/time, after which the sudoRole will no longer be valid. If multiple sudoNotAfter entries are present, the last one is used. Timestamps must be in Coordinated Universal Time (UTC), not the local timezone. The minute and seconds portions are optional, but some LDAP servers require that they be present (contrary to the RFC).

The sudoNotAfter attribute is only available in sudo versions 1.7.5 and higher and must be explicitly enabled via the SUDOERS_TIMED option in /etc/openldap/ldap.conf.

sudoOrder
The sudoRole entries retrieved from the LDAP directory have no inherent order. The sudoOrder attribute is an integer (or floating point value for LDAP servers that support it) that is used to sort the matching entries. This allows LDAP-based sudoers entries to more closely mimic the behavior of the sudoers file, where the order of the entries influences the result. If multiple entries match, the entry with the highest sudoOrder attribute is chosen. This corresponds to the “last match” behavior of the sudoers file. If the sudoOrder attribute is not present, a value of 0 is assumed.

The sudoOrder attribute is only available in sudo versions 1.7.5 and higher.

Each attribute listed above should contain a single value, but there may be multiple instances of each attribute type. A sudoRole must contain at least one sudoUser, sudoHost, and sudoCommand.

The following example allows users in group wheel to run any command on any host via sudo:

dn: cn=%wheel,ou=SUDOers,dc=my-domain,dc=com
objectClass: top
objectClass: sudoRole
cn: %wheel
sudoUser: %wheel
sudoHost: ALL
sudoCommand: ALL

Anatomy of LDAP sudoers lookup

When looking up a sudoer using LDAP there are only two or three LDAP queries per invocation. The first query is to parse the global options. The second is to match against the user's name and the groups that the user belongs to. (The special ALL tag is matched in this query too.) If no match is returned for the user's name and groups, a third query returns all entries containing user netgroups and other non-Unix groups and checks to see if the user belongs to any of them.

If timed entries are enabled with the SUDOERS_TIMED parameter, the LDAP queries include a sub-filter that limits retrieval to entries that satisfy the time constraints, if any.

If the NETGROUP_BASE parameter is present and NETGROUP_QUERY has not been disabled (see Configuring ldap.conf below), queries are performed to determine the list of netgroups the user belongs to before the sudoers query. This makes it possible to include netgroups in the sudoers query string in the same manner as Unix groups. The third query mentioned above is not performed unless a group provider plugin is also configured. The actual LDAP queries performed by sudo are as follows:

  1. Match all nisNetgroup records with a nisNetgroupTriple containing the user, host, and NIS domain. The query will match nisNetgroupTriple entries with either the short or long form of the host name or no host name specified in the tuple. If the NIS domain is set, the query will only match entries that include the domain or for which there is no domain present. If the NIS domain is not set, a wildcard is used to match any domain name but be aware that the NIS schema used by some LDAP servers may not support wild cards for nisNetgroupTriple.
  2. Repeated queries are performed to find any nested nisNetgroup records with a memberNisNetgroup entry that refers to an already-matched record.

For sites with a large number of netgroups, using NETGROUP_BASE can significantly speed up sudo's execution time as long as the LDAP server supports querying the nisNetgroup object by its nisNetgroupTriple attribute.

Differences between LDAP and non-LDAP sudoers

One of the major differences between LDAP and file-based sudoers is that in LDAP, sudo-specific Aliases are not supported.

For the most part, there is little need for sudo-specific Aliases. Unix groups, non-Unix groups (via the group_plugin), or user netgroups can be used in place of User_Aliases and Runas_Aliases. Host netgroups can be used in place of Host_Aliases. Since groups and netgroups can also be stored in LDAP there is no real need for sudo-specific aliases.

There are also some subtle differences in the way sudoers is handled once in LDAP. Probably the biggest is that according to the RFC, LDAP ordering is arbitrary and you cannot expect that Attributes and Entries are returned in any specific order.

The order in which different entries are applied can be controlled using the sudoOrder attribute, but there is no way to guarantee the order of attributes within a specific entry. If there are conflicting command rules in an entry, the negative takes precedence. This is called paranoid behavior (not necessarily the most specific match).

Here is an example:

# /etc/sudoers:
# Allow all commands except shell
johnny  ALL=(root) ALL,!/bin/sh
# Always allows all commands because ALL is matched last
puddles ALL=(root) !/bin/sh,ALL

# LDAP equivalent of johnny
# Allows all commands except shell
dn: cn=role1,ou=Sudoers,dc=my-domain,dc=com
objectClass: sudoRole
objectClass: top
cn: role1
sudoUser: johnny
sudoHost: ALL
sudoCommand: ALL
sudoCommand: !/bin/sh

# LDAP equivalent of puddles
# Notice that even though ALL comes last, it still behaves like
# role1 since the LDAP code assumes the more paranoid configuration
dn: cn=role2,ou=Sudoers,dc=my-domain,dc=com
objectClass: sudoRole
objectClass: top
cn: role2
sudoUser: puddles
sudoHost: ALL
sudoCommand: !/bin/sh
sudoCommand: ALL

Converting between file-based and LDAP sudoers

The cvtsudoers(1) utility can be used to convert between file-based and LDAP sudoers. However, there are features in the file-based sudoers that have no equivalent in LDAP-based sudoers (and vice versa). These cannot be converted automatically.

For example, a Cmnd_Alias in a sudoers file may be converted to a sudoRole that contains multiple commands. Multiple users and/or groups may be assigned to the sudoRole.

Also, host, user, runas, and command-based Defaults entries are not supported. However, a sudoRole may contain one or more sudoOption attributes which can often serve the same purpose.

Consider the following sudoers lines:

Cmnd_Alias PAGERS = /usr/bin/more, /usr/bin/pg, /usr/bin/less
Defaults!PAGERS noexec
alice, bob ALL = ALL

In this example, alice and bob are allowed to run all commands, but the commands listed in PAGERS will have the noexec flag set, preventing shell escapes.

When converting this to LDAP, two sudoRole objects can be used:

dn: cn=PAGERS,ou=SUDOers,dc=my-domain,dc=com
objectClass: top
objectClass: sudoRole
cn: PAGERS
sudoUser: alice
sudoUser: bob
sudoHost: ALL
sudoCommand: /usr/bin/more
sudoCommand: /usr/bin/pg
sudoCommand: /usr/bin/less
sudoOption: noexec
sudoOrder: 900

dn: cn=ADMINS,ou=SUDOers,dc=my-domain,dc=com
objectClass: top
objectClass: sudoRole
cn: ADMINS
sudoUser: alice
sudoUser: bob
sudoHost: ALL
sudoCommand: ALL
sudoOrder: 100

In the LDAP version, the sudoOrder attribute is used to guarantee that the PAGERS sudoRole with noexec has precedence. Unlike the sudoers version, the LDAP version requires that all users for whom the restriction should apply be assigned to the PAGERS sudoRole. Using a Unix group or netgroup in PAGERS rather than listing each user would make this easier to maintain.

Per-user Defaults entries can be emulated by using one or more sudoOption attributes in a sudoRole. Consider the following sudoers lines:

User_Alias ADMINS = john, sally
Defaults:ADMINS !authenticate
ADMINS ALL = (ALL:ALL) ALL

In this example, john and sally are allowed to run any command as any user or group.

When converting this to LDAP, we can use a Unix group instead of the User_Alias.

dn: cn=admins,ou=SUDOers,dc=my-domain,dc=com
objectClass: top
objectClass: sudoRole
cn: admins
sudoUser: %admin
sudoHost: ALL
sudoRunAsUser: ALL
sudoRunAsGroup: ALL
sudoCommand: ALL
sudoOption: !authenticate

This assumes that users john and sally are members of the “admins” Unix group.

Sudoers schema

Esquema Sudoers

Para poder usar el soporte LDAP de sudo, se debe instalar el esquema sudo en su servidor LDAP. Además, asegúrese de indexar el atributo sudoUser.

La distribución de sudo incluye versiones del esquema sudoers para múltiples servidores LDAP:

schema.ActiveDirectory
Microsoft Active Directory
schema.IBM_LDAP
IBM Directory Server, también conocido como IBM Tivoli Directory Server, IBM Security Directory Server e IBM Security Verify Directory
schema.iPlanet
Servidores derivados de Netscape como los servidores iPlanet, Oracle y 389 Directory
schema.olcSudo
OpenLDAP slapd 2.3 y superior cuando la configuración en línea está habilitada
schema.OpenLDAP
OpenLDAP slapd y OpenBSD ldapd

El esquema en formato OpenLDAP también se incluye en la sección EJEMPLOS.

Configuración de ldap.conf

Sudo lee el archivo /etc/openldap/ldap.conf para la configuración específica de LDAP. Típicamente, este archivo se comparte entre diferentes clientes compatibles con LDAP. Como tal, la mayoría de las configuraciones no son específicas de sudo. El archivo /etc/openldap/ldap.conf es analizado por el propio sudo y puede admitir opciones que difieren de las descritas en el manual ldap.conf(5) del sistema. La ruta a ldap.conf puede ser anulada a través del argumento del plugin ldap_conf en sudo.conf(5).

En sistemas que utilizan las bibliotecas OpenLDAP, no se utilizan los valores predeterminados especificados en /etc/openldap/ldap.conf o en los archivos .ldaprc del usuario.

sudo admite una variedad de implementaciones de bibliotecas LDAP, incluidas OpenLDAP, las derivadas de Netscape (también utilizadas por Solaris y HP-UX) y IBM LDAP (también conocido como Tivoli). Algunas opciones son específicas de ciertas implementaciones LDAP o tienen un comportamiento específico de la implementación. Estas diferencias se observan a continuación cuando corresponda.

Solo se respetan las opciones explícitamente enumeradas en /etc/openldap/ldap.conf como compatibles con sudo. Las opciones de configuración se enumeran a continuación en mayúsculas, pero se analizan de forma independiente de mayúsculas y minúsculas.

Las líneas que comienzan con un signo de almohadilla ('#') se ignoran. El espacio en blanco inicial se elimina del principio de las líneas.

BIND_TIMELIMIT segundos
El parámetro BIND_TIMELIMIT especifica el tiempo, en segundos, que se esperará al intentar conectarse a un servidor LDAP. Si se especifican varios URIs o HOSTs, este es el tiempo que se esperará antes de intentar el siguiente de la lista.
BINDDN DN
El parámetro BINDDN especifica la identidad, en forma de un Nombre Distinguido (DN), a utilizar al realizar operaciones LDAP. Si no se especifica, las operaciones LDAP se realizan con una identidad anónima. Por defecto, la mayoría de los servidores LDAP permiten el acceso anónimo.
BINDPW secreto
El parámetro BINDPW especifica la contraseña a utilizar al realizar operaciones LDAP. Esto se usa típicamente junto con el parámetro BINDDN. El secreto puede ser una contraseña en texto plano o una cadena codificada en base64 con un prefijo 'base64:'. Por ejemplo: 
BINDPW base64:dGVzdA==

Si se utiliza una contraseña en texto plano, debe ser una cadena simple sin comillas. Las contraseñas en texto plano no pueden incluir el carácter de comentario ('#') y no se admite el escape de caracteres especiales con una barra invertida ('\').

DEREF nunca/buscando/encontrando/siempre
Cómo se debe realizar la desreferenciación de alias al buscar. Consulte el manual ldap.conf(5) para una descripción completa de esta opción.
HOST nombre[:puerto] ...
Si no se especifica URI (ver más abajo), el parámetro HOST especifica una lista de servidores LDAP separada por espacios a los que conectarse. Cada host puede incluir un puerto opcional separado por dos puntos (':'). El parámetro HOST está obsoleto en favor de la especificación URI y se incluye solo por compatibilidad con versiones anteriores.
KRB5_CCNAME nombre de archivo
La ruta a la caché de credenciales Kerberos 5 a utilizar al autenticarse con el servidor remoto.

Esta opción solo es relevante cuando se utiliza la autenticación SASL (ver más abajo).

LDAP_VERSION número
La versión del protocolo LDAP a utilizar al conectarse al servidor. El valor predeterminado es la versión 3 del protocolo.
NETGROUP_BASE base
El DN base a utilizar al realizar consultas LDAP de netgroup. Típicamente, tiene la forma 'ou=netgroup,dc=mi-dominio,dc=com' para el dominio mi-dominio.com. Se pueden especificar varias líneas NETGROUP_BASE, en cuyo caso se consultan en el orden especificado.

Cuando esta opción está habilitada, sudo consultará directamente al servidor LDAP al hacer coincidir netgroups presentes en un sudoRole en lugar de depender de la función innetgr() de la biblioteca C.

Además, si el parámetro NETGROUP_QUERY (que está habilitado por defecto) no ha sido deshabilitado, las netgroups del usuario se consultarán directamente a través de LDAP para su uso en la consulta principal de sudoers. Esto suele ser más rápido que obtener todos los objetos sudoRole que contienen un sudoUser que comienza con un prefijo '+' y verificar si el usuario es miembro de cada uno. El esquema NIS utilizado por algunos servidores LDAP necesita una modificación para admitir la consulta del objeto nisNetgroup por su atributo nisNetgroupTriple. Por ejemplo, slapd de OpenLDAP requiere el siguiente cambio en el atributo nisNetgroupTriple:

attributetype ( 1.3.6.1.1.1.1.14 NAME 'nisNetgroupTriple'
   DESC 'Netgroup triple'
   EQUALITY caseIgnoreIA5Match
   SUBSTR caseIgnoreIA5SubstringsMatch
   SYNTAX 1.3.6.1.4.1.1466.115.121.1.26 )

Antes de habilitar NETGROUP_BASE, debe verificar que su servidor LDAP admita la coincidencia de nisNetgroupTriple. Por ejemplo, usando ldapsearch:

$ ldapsearch -b $NETGROUP_BASE \
  '(&(objectClass=nisNetgroup)(nisNetgroupTriple=\28*,USER,\29))'

donde sus datos de nisNetgroup incluyen un objeto con el siguiente nisNetgroupTriple:

nisNetgroupTriple: (,USER,)
NETGROUP_QUERY encendido/verdadero/sí/apagado/falso/no
El parámetro NETGROUP_QUERY indica si el servidor LDAP admite la consulta de objetos nisNetgroup coincidiendo con atributos nisNetgroupTriple. Por defecto, sudoers espera poder realizar consultas que coincidan con atributos nisNetgroupTriple cuando NETGROUP_BASE está configurado, pero no todos los servidores LDAP lo admiten.

Si NETGROUP_QUERY está deshabilitado, sudoers no intentará determinar la lista de netgroups a las que pertenece el usuario, pero aún usará NETGROUP_BASE directamente al hacer coincidir netgroups. Esto se puede usar para admitir netgroups en sistemas que carecen de la función de biblioteca C innetgr(). Consulte la descripción del parámetro NETGROUP_BASE para obtener más información.

NETGROUP_SEARCH_FILTER filtro_ldap
Un filtro LDAP que se utiliza para restringir el conjunto de registros devueltos al realizar una consulta LDAP de netgroup. Típicamente, tiene la forma 'atributo=valor' o '(&(atributo=valor)(atributo2=valor2))'. El filtro de búsqueda predeterminado es: 'objectClass=nisNetgroup'. Si se omite filtro_ldap, no se utilizará ningún filtro de búsqueda.

Esta opción solo se utiliza al consultar netgroups directamente a través de LDAP.

NETWORK_TIMEOUT segundos
Un alias para BIND_TIMELIMIT proporcionado para compatibilidad con OpenLDAP.
PORT número de puerto
Si no se especifica URI, el parámetro PORT especifica el puerto predeterminado al que conectarse en el servidor LDAP si un parámetro HOST no especifica el puerto en sí. Si no se
PORT port
El parámetro PORT especifica el puerto en el que se escucha el servicio LDAP. Si el parámetro PORT no se especifica, el valor predeterminado es el puerto 389 para LDAP y el puerto 636 para LDAP sobre TLS (SSL). El parámetro PORT está obsoleto en favor de la especificación URI y se incluye solo por compatibilidad con versiones anteriores.
ROOTBINDDN DN
El parámetro ROOTBINDDN especifica la identidad, en forma de Distinguished Name (DN), que se utilizará al realizar operaciones privilegiadas de LDAP, como las consultas de sudoers. La contraseña correspondiente a la identidad debe almacenarse en el o en la ruta especificada por el argumento del plugin ldap_secret en sudo.conf(5), que por defecto es /etc/ldap.secret. Si no se especifica ROOTBINDDN, se utiliza la identidad BINDDN (si la hay).
ROOTUSE_SASL on/true/yes/off/false/no
Habilita ROOTUSE_SASL para permitir la autenticación SASL al conectarse a un servidor LDAP desde un proceso privilegiado, como sudo.
SASL_AUTH_ID identidad
El nombre de usuario SASL a utilizar al conectarse al servidor LDAP. Por defecto, sudo utilizará una conexión anónima.

Esta opción solo es relevante cuando se utiliza la autenticación SASL.

SASL_MECH mecanismos
Una lista de mecanismos de autenticación SASL delimitada por espacios. Por defecto, sudo utilizará la autenticación GSSAPI.
SASL_SECPROPS ninguno/propiedades
Propiedades de seguridad SASL o ninguno para no tener propiedades. Consulte el manual del programador de SASL para obtener más detalles.

Esta opción solo es relevante cuando se utiliza la autenticación SASL.

SSL on/true/yes/off/false/no
Si el parámetro SSL se establece en on, true o yes, se utilizará siempre cifrado TLS (SSL) al comunicarse con el servidor LDAP. Normalmente, esto implica conectarse al servidor en el puerto 636 (ldaps).
SSL start_tls
Si el parámetro SSL se establece en start_tls, la conexión al servidor LDAP se inicia normalmente y el cifrado TLS comienza antes de enviar las credenciales de conexión. Esto tiene la ventaja de no requerir un puerto dedicado para comunicaciones cifradas. Este parámetro solo es compatible con servidores LDAP que admiten la extensión start_tls, como los servidores OpenLDAP e IBM Tivoli Directory.
SUDOERS_BASE base
El DN base a utilizar al realizar consultas LDAP de sudo. Normalmente tiene el formato ‘ou=SUDOers,dc=my-domain,dc=com’ para el dominio my-domain.com. Se pueden especificar varias líneas SUDOERS_BASE, en cuyo caso se consultan en el orden especificado.
SUDOERS_DEBUG nivel_depuracion
Esto establece el nivel de depuración para las consultas LDAP de sudo. La información de depuración se imprime en la salida de error estándar. Un valor de 1 produce una cantidad moderada de información de depuración. Un valor de 2 muestra los resultados de las coincidencias. Este parámetro no debe configurarse en un entorno de producción, ya que la información adicional probablemente confunda a los usuarios.

El parámetro SUDOERS_DEBUG está obsoleto y se eliminará en una futura versión. La misma información se registra ahora a través del framework de depuración de sudo utilizando el subsistema “ldap” en las prioridades diag y info para los valores nivel_depuracion 1 y 2 respectivamente. Consulte el manual de sudo.conf(5) para obtener detalles sobre cómo configurar la depuración de sudo.

SUDOERS_SEARCH_FILTER filtro_ldap
Un filtro LDAP que se utiliza para restringir el conjunto de registros devueltos al realizar una consulta LDAP de sudo. Normalmente, tiene el formato ‘atributo=valor’ o ‘(&(atributo=valor)(atributo2=valor2))’. El filtro de búsqueda predeterminado es: ‘objectClass=sudoRole’. Si se omite filtro_ldap, no se utilizará ningún filtro de búsqueda.
SUDOERS_TIMED on/true/yes/off/false/no
Si se evalúan o no los atributos sudoNotBefore y sudoNotAfter que implementan las entradas de sudoers dependientes del tiempo.
TIMELIMIT segundos
El parámetro TIMELIMIT especifica la cantidad de tiempo, en segundos, para esperar una respuesta a una consulta LDAP.
TIMEOUT segundos
El parámetro TIMEOUT especifica la cantidad de tiempo, en segundos, para esperar una respuesta de las diversas APIs LDAP.
TLS_CACERT nombre de archivo
Un alias para TLS_CACERTFILE para compatibilidad con OpenLDAP.
TLS_CACERTFILE nombre de archivo
La ruta a un paquete de autoridad de certificación que contiene los certificados de todas las Autoridades de Certificación que el cliente sabe que son válidos, por ejemplo, /etc/ssl/ca-bundle.pem.

Esta opción solo es compatible con las bibliotecas OpenLDAP. Las bibliotecas LDAP derivadas de Netscape utilizan la misma base de datos de certificados para CA y certificados de cliente (ver TLS_CERT).

TLS_CACERTDIR directorio
Similar a TLS_CACERTFILE, pero en lugar de un archivo, es un directorio que contiene certificados individuales de Autoridad de Certificación, por ejemplo, /etc/ssl/certs. El directorio especificado por TLS_CACERTDIR se comprueba después de TLS_CACERTFILE.

Esta opción solo es compatible con las bibliotecas OpenLDAP.

TLS_CERT nombre de archivo
La ruta a un archivo que contiene el certificado del cliente que puede ser utilizado para autenticar al cliente ante el servidor LDAP. El tipo de certificado depende de las bibliotecas LDAP utilizadas.
OpenLDAP:
‘tls_cert /etc/ssl/client_cert.pem’
Derivado de Netscape:
‘tls_cert /var/ldap/cert7.db’
IBM LDAP:
No utilizado, la base de datos de claves especificada por TLS_KEY contiene tanto claves como certificados.

Al utilizar bibliotecas derivadas de Netscape, este archivo también puede contener certificados de Autoridad de Certificación.

TLS_CHECKPEER on/true/yes/off/false/no
Si está habilitado, TLS_CHECKPEER provocará la verificación del certificado TLS del servidor LDAP. Si el certificado TLS del servidor no puede ser verificado (generalmente porque está firmado por una autoridad de certificación desconocida), sudo no podrá conectarse a él. Si TLS_CHECKPEER está deshabilitado, no se realiza ninguna comprobación. Deshabilitar esta comprobación crea una oportunidad para ataques man-in-the-middle, ya que la identidad del servidor no será autenticada. Si es posible, el certificado de la CA debe instalarse localmente para que pueda ser verificado.

Esta opción no es compatible con las bibliotecas IBM LDAP.

TLS_KEY nombre de archivo
La ruta a un archivo que contiene la clave privada que coincide con el certificado especificado por TLS_CERT. La clave privada no debe estar protegida por contraseña. El tipo de clave depende de las bibliotecas LDAP utilizadas.
OpenLDAP:
‘tls_key /etc/ssl/client_key.pem’
Derivado de Netscape:
‘tls_key /var/ldap/key3.db’
IBM LDAP:
‘tls_key /usr/ldap/ldapkey.kdb’

Al utilizar bibliotecas IBM LDAP, este archivo también puede contener certificados de Autoridad de Certificación y de cliente, y puede estar cifrado.

TLS_CIPHERS lista de cifrados
El parámetro TLS_CIPHERS permite al administrador restringir qué algoritmos de cifrado pueden utilizarse para conexiones TLS (SSL). Consulte el manual de OpenLDAP o IBM Tivoli Directory Server para obtener una lista de cifrados válidos.

Esta opción no es compatible con las bibliotecas derivadas de Netscape.

TLS_KEYPW secreto
El TLS_KEYPW contiene la contraseña utilizada para descifrar la base de datos de claves en los clientes que utilizan la biblioteca IBM LDAP. El secreto puede ser una contraseña en texto plano o un
TLS_KEYPW base64:dGVzdA==

Si se usa una contraseña en texto plano, debe ser una cadena simple sin comillas. Las contraseñas en texto plano no pueden incluir el carácter de comentario ('#') y no se admite el escape de caracteres especiales con una barra invertida ('\'). Si se utiliza esta opción, /etc/openldap/ldap.conf no debe ser legible para todos los usuarios para evitar la exposición de la contraseña. Alternativamente, se puede usar un archivo de ocultación para almacenar la contraseña en forma cifrada (ver más abajo).

Si no se especifica TLS_KEYPW, se utilizará un archivo de ocultación si existe. El archivo de ocultación debe tener la misma ruta que el archivo especificado por TLS_KEY, pero usar una extensión de archivo '.sth' en lugar de '.kdb', por ejemplo 'ldapkey.sth'. La base de datos de claves predeterminada 'ldapkey.kdb' que se distribuye con IBM Tivoli Directory Server está cifrada con la contraseña 'ssl_password'. La utilidad gsk8capicmd puede usarse para administrar la base de datos de claves y crear un archivo de ocultación.

Esta opción solo es compatible con las bibliotecas de IBM LDAP.

TLS_REQCERT nivel
El parámetro TLS_REQCERT controla cómo se verificará (si es que se verifica) el certificado TLS del servidor LDAP. Si el certificado TLS del servidor no se puede verificar (generalmente porque está firmado por una autoridad de certificación desconocida), sudo no podrá conectarse a él. Se admiten los siguientes valores de nivel:
never
El certificado del servidor no se solicitará ni se comprobará.
allow
Se solicitará el certificado del servidor. Un certificado faltante o inválido se ignora y no se considera un error.
try
Se solicitará el certificado del servidor. Un certificado faltante se ignora, pero un certificado inválido resultará en un error de conexión.
demand | hard
Se solicitará el certificado del servidor. Un certificado faltante o inválido resultará en un error de conexión. Este es el comportamiento predeterminado.

Esta opción solo es compatible con las bibliotecas de OpenLDAP. Otras bibliotecas LDAP solo admiten el parámetro TLS_CHECKPEER.

TLS_RANDFILE nombre de archivo
El parámetro TLS_RANDFILE especifica la ruta a una fuente de entropía para sistemas que carecen de un dispositivo aleatorio. Generalmente se usa en conjunción con prngd o egd.

Esta opción solo es compatible con las bibliotecas de OpenLDAP.

URI ldap[s]://[nombrehost[:puerto]] ...
Especifica una lista separada por espacios de uno o más URIs que describen los servidores LDAP a los que conectarse. El protocolo puede ser ldap o ldaps, siendo este último para servidores que admiten cifrado TLS (SSL). Si no se especifica ningún puerto, el predeterminado es el puerto 389 para 'ldap://' o el puerto 636 para 'ldaps://'. Si no se especifica ningún nombrehost, sudo se conectará a localhost. Múltiples líneas URI se tratan de manera idéntica a una línea URI que contiene múltiples entradas. Solo los sistemas que usan las bibliotecas OpenSSL admiten la mezcla de URIs 'ldap://' y 'ldaps://'. Tanto las bibliotecas LDAP derivadas de Netscape como las bibliotecas LDAP de IBM utilizadas en la mayoría de las versiones comerciales de Unix solo son capaces de admitir una u otra.
USE_SASL activado/verdadero/sí/desactivado/falso/no
Habilita USE_SASL para servidores LDAP que admiten autenticación SASL.
ROOTSASL_AUTH_ID identidad
El nombre de usuario SASL a utilizar cuando ROOTUSE_SASL está habilitado.

Consulte la entrada ldap.conf en la sección EJEMPLOS.

Configuración de nsswitch.conf

A menos que se deshabilite en tiempo de compilación, sudo consulta el archivo Name Service Switch, /etc/nsswitch.conf, para especificar el orden de búsqueda de sudoers. Sudo busca una línea que comience con sudoers: y la utiliza para determinar el orden de búsqueda. De forma predeterminada, sudo no detiene la búsqueda después de la primera coincidencia y las coincidencias posteriores tienen precedencia sobre las anteriores (a menos que se use '[SUCCESS=return]', ver más abajo). Se reconocen las siguientes fuentes:

files
leer sudoers de /etc/sudoers
ldap
leer sudoers de LDAP

Además, se admite un subconjunto de las sentencias de acción de nsswitch.conf, específicamente '[SUCCESS=return]' y '[NOTFOUND=return]'. Estas terminarán incondicionalmente la búsqueda si el usuario fue encontrado '[SUCCESS=return]' o no fue encontrado '[NOTFOUND=return]' en la fuente inmediatamente anterior. No se admiten otros tokens de sentencias de acción, ni la negación de pruebas con '!'.

Para consultar LDAP primero y luego el archivo sudoers local (si existe), use:

sudoers: ldap files

Para consultar LDAP solo cuando no se encuentra ninguna coincidencia en el archivo sudoers local (si existe), use:

sudoers: files [SUCCESS=return] ldap

El archivo sudoers local puede ser ignorado por completo usando:

sudoers: ldap

Si el archivo /etc/nsswitch.conf no está presente o no hay una línea de sudoers, se asume la siguiente opción predeterminada:

sudoers: files

El archivo /etc/nsswitch.conf es compatible incluso cuando el sistema operativo subyacente no lo admite, excepto en AIX (ver más abajo).

Configuración de netsvc.conf

En los sistemas AIX, se consulta el archivo /etc/netsvc.conf en lugar de /etc/nsswitch.conf. sudo trata simplemente netsvc.conf como una variante de nsswitch.conf; la información de la sección anterior no relacionada con el formato del archivo en sí todavía se aplica.

Para consultar LDAP primero y luego el archivo sudoers local (si existe), use:

sudoers = ldap, files

El archivo sudoers local puede ser ignorado por completo usando:

sudoers = ldap

Para tratar LDAP como autoritativo y usar solo el archivo sudoers local si el usuario no está presente en LDAP, use:

sudoers = ldap = auth, files

En el ejemplo anterior, el calificador auth solo afecta a las búsquedas de usuarios; tanto LDAP como sudoers serán consultados para entradas Defaults.

Si el archivo /etc/netsvc.conf no está presente o no hay una línea de sudoers, se asume la siguiente opción predeterminada:

sudoers = files

Integración con sssd

En sistemas con el System Security Services Daemon (SSSD) y donde sudo ha sido compilado con soporte SSSD, es posible usar SSSD para almacenar en caché las reglas de sudoers de LDAP. Para usar SSSD como fuente de sudoers, debe usar sss en lugar de ldap para la entrada sudoers en /etc/nsswitch.conf. El archivo /etc/openldap/ldap.conf no es utilizado por el backend de SSSD de sudo. Consulte sssd-sudo(5) para más información sobre cómo configurar sudo para trabajar con SSSD.
