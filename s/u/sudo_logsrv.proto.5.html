sudo_logsrv.proto(5)

Paquete: sudo

Licencias: custom

SUDO_LOGSRV.PROTO(5) Manual de formatos de archivo SUDO_LOGSRV.PROTO(5)

NOMBRE

sudo_logsrv.proto — protocolo del servidor de registro de Sudo

DESCRIPCIÓN

A partir de la versión 1.9.0, sudo soporta el envío de registros de eventos y E/S a un servidor de registro. El protocolo utilizado está escrito en el lenguaje de dominio específico de Protocol Buffers de Google. La sección EJEMPLOS incluye una descripción completa del protocolo en formato Protocol Buffers.

Debido a que no hay forma de determinar los límites de los mensajes al usar Protocol Buffers, el tamaño en la red de cada mensaje se envía inmediatamente antes del mensaje como un entero sin signo de 32 bits en orden de bytes de red. Esto se conoce como "framing con prefijo de longitud" y es como Google sugiere manejar la falta de delimitadores de mensajes.

El protocolo consta de dos mensajes básicos, ClientMessage y ServerMessage, descritos a continuación. El servidor debe aceptar mensajes de hasta dos megabytes de tamaño. El servidor puede devolver un error si el cliente intenta enviar un mensaje mayor de dos megabytes.

Mensajes del cliente

ClientMessage es un contenedor utilizado para encapsular todos los tipos de mensajes posibles que un cliente puede enviar al servidor.

message ClientMessage {
  oneof type {
    AcceptMessage accept_msg = 1;
    RejectMessage reject_msg = 2;
    ExitMessage exit_msg = 3;
    RestartMessage restart_msg = 4;
    AlertMessage alert_msg = 5;
    IoBuffer ttyin_buf = 6;
    IoBuffer ttyout_buf = 7;
    IoBuffer stdin_buf = 8;
    IoBuffer stdout_buf = 9;
    IoBuffer stderr_buf = 10;
    ChangeWindowSize winsize_event = 11;
    CommandSuspend suspend_event = 12;
    ClientHello hello_msg = 13;
  }
}

Los diferentes submensajes de ClientMessage que el cliente puede enviar al servidor se describen a continuación.

TimeSpec

message TimeSpec {
    int64 tv_sec = 1;
    int32 tv_nsec = 2;
}

TimeSpec es el equivalente a una struct timespec POSIX, que contiene los miembros de segundos y nanosegundos. El miembro tv_sec es un entero de 64 bits para admitir fechas posteriores al año 2038.

InfoMessage

message InfoMessage {
  message StringList {
    repeated string strings = 1;
  }
  message NumberList {
    repeated int64 numbers = 1;
  }
  string key = 1;
  oneof value {
    int64 numval = 2;
    string strval = 3;
    StringList strlistval = 4;
    NumberList numlistval = 5;
  }
}

Un InfoMessage se utiliza para representar información sobre el usuario que invoca el comando, así como el entorno de ejecución en el que se ejecuta el comando, en forma de pares clave-valor. La clave es siempre una cadena, pero el valor puede ser un entero de 64 bits, una cadena, una matriz de cadenas o una matriz de enteros de 64 bits. Los datos del registro de eventos se componen de entradas InfoMessage. Consulte la sección VARIABLES DE REGISTRO DE EVENTOS para obtener más información.

ClientHello hello_msg

message ClientHello {
  string client_id = 1;
}

Un mensaje ClientHello consta de información del cliente que puede enviarse al servidor cuando el cliente se conecta por primera vez.

client_id
Una descripción libre del cliente. Normalmente incluye el nombre y la versión de la implementación del cliente.

AcceptMessage accept_msg

message AcceptMessage {
  TimeSpec submit_time = 1;
  repeated InfoMessage info_msgs = 2;
  bool expect_iobufs = 3;
}

Un AcceptMessage es enviado por el cliente cuando un comando es permitido por la política de seguridad. Contiene los siguientes miembros:

submit_time
La hora del reloj de pared en que se envió el comando a la política de seguridad.
info_msgs
Una matriz de InfoMessage que describe al usuario que envió el comando, así como el entorno de ejecución del comando. Esta información se utiliza para generar una entrada de registro de eventos y también puede ser utilizada por el servidor para determinar dónde y cómo se almacena el registro de E/S.
expect_iobufs
Se establece en verdadero si el servidor debe esperar mensajes IoBuffer a continuación (para el registro de E/S) o en falso si el servidor solo debe almacenar el registro de eventos.

Si se envía un AcceptMessage, el cliente no debe enviar un RejectMessage o RestartMessage.

RejectMessage reject_msg

message RejectMessage {
  TimeSpec submit_time = 1;
  string reason = 2;
  repeated InfoMessage info_msgs = 3;
}

Un RejectMessage es enviado por el cliente cuando un comando es denegado por la política de seguridad. Contiene los siguientes miembros:

submit_time
La hora del reloj de pared en que se envió el comando a la política de seguridad.
reason
La razón por la cual la política de seguridad denegó el comando.
info_msgs
Una matriz de InfoMessage que describe al usuario que envió el comando, así como el entorno de ejecución del comando. Esta información se utiliza para generar una entrada de registro de eventos.

Si se envía un RejectMessage, el cliente no debe enviar un AcceptMessage o RestartMessage.

ExitMessage exit_msg

message ExitMessage {
  TimeSpec run_time = 1;
  int32 exit_value = 2;
  bool dumped_core = 3;
  string signal = 4;
  string error = 5;
}

Un ExitMessage es enviado por el cliente después de que el comando ha salido o ha sido terminado por una señal. Contiene los siguientes miembros:

run_time
El tiempo total transcurrido desde que el comando comenzó, calculado utilizando un reloj monótono siempre que sea posible. Esta no es la hora del reloj de pared.
exit_value
El valor de salida del comando en el rango 0-255.
dumped_core
Verdadero si el comando fue terminado por una señal y volcó la memoria principal (core dump).
signal
Si el comando fue terminado por una señal, esto se establece en el nombre de la señal sin el prefijo "SIG". Por ejemplo, INT, TERM, KILL, SEGV.
error
Un mensaje del cliente indicando que el comando fue terminado inesperadamente debido a un error.

Al realizar el registro de E/S, el cliente debe esperar un commit_point que corresponda al IoBuffer final antes de cerrar la conexión, a menos que ya se haya recibido el commit_point final.

RestartMessage restart_msg

message RestartMessage {
  string log_id = 1;
  TimeSpec resume_point = 2;
}

Un RestartMessage es enviado por el cliente para reanudar el envío de un registro de E/S existente que fue interrumpido previamente. Contiene los siguientes miembros:

log_id
El nombre del lado del servidor para un registro de E/S que fue enviado previamente al cliente por el servidor. Este puede ser un nombre de ruta en el servidor o algún otro tipo de identificador del lado del servidor.
resume_point
El punto en el tiempo después del cual reanudar el registro de E/S. Esto tiene el formato de un TimeSpec que representa la cantidad de tiempo transcurrido desde que comenzó el comando, no la hora del reloj de pared. El resume_point debe corresponder a un commit_point enviado previamente al cliente por el servidor. Si el servidor recibe un RestartMessage que contiene un resume_point que no ha visto previamente, se devolverá un error al cliente y la conexión se cerrará.

IoBuffer

message IoBuffer {
  TimeSpec time = 1;
  bytes buffer = 2;
  bool is_tty = 3;
  bool commit_point = 4;
}

Un IoBuffer contiene un fragmento de datos de E/S que se han registrado. Contiene los siguientes miembros:

time
El tiempo transcurrido desde que se inició el comando. Este es un valor monótono y no un tiempo de reloj de pared.
buffer
Los datos de E/S reales. Para los datos del terminal, el cliente puede omitir los caracteres de escape de nueva línea que a menudo se agregan automáticamente.
is_tty
Verdadero si los datos del búfer provienen de un tty, falso en caso contrario.
commit_point
Si se establece en verdadero, el cliente ha enviado todos los datos de E/S hasta este punto en el tiempo. Esto se puede utilizar como un punto de reinicio si es necesario.

AlertMessage alert_msg

message AlertMessage {
  string severity = 1;
  string message = 2;
}

Un mensaje AlertMessage es enviado por el cliente para indicar una condición de alerta. Contiene los siguientes miembros:

severity
El nivel de gravedad de la alerta (p. ej., "información", "advertencia", "error").
message
El mensaje de alerta descriptivo.

ChangeWindowSize

message ChangeWindowSize {
  int32 rows = 1;
  int32 cols = 2;
  TimeSpec time = 3;
}

Un mensaje ChangeWindowSize es enviado por el cliente para informar de un cambio en el tamaño de la ventana del terminal. Contiene los siguientes miembros:

rows
El número de filas del terminal.
cols
El número de columnas del terminal.
time
El tiempo transcurrido desde que se inició el comando.

CommandSuspend

message CommandSuspend {
  TimeSpec time = 1;
}

Un mensaje CommandSuspend es enviado por el cliente para indicar que el comando ha sido suspendido. Contiene los siguientes miembros:

time
El tiempo transcurrido desde que se inició el comando.

Mensajes del servidor

Un ServerMessage es un contenedor utilizado para encapsular todos los tipos de mensajes que un servidor puede enviar a un cliente.

message ServerMessage {
  oneof type {
    ServerHello hello_msg = 1;
    ServerAck ack_msg = 2;
    ServerReject reject_msg = 3;
    ServerLogId log_id_msg = 4;
    ServerCommitPoint commit_point_msg = 5;
  }
}

Los diferentes submensajes de ServerMessage que el servidor puede enviar al cliente se describen a continuación.

ServerHello

message ServerHello {
  string server_id = 1;
  string log_id = 2;
  repeated ServerEvent events = 3;
}

Un mensaje ServerHello es enviado por el servidor al cliente cuando el cliente se conecta por primera vez. Contiene los siguientes miembros:

server_id
Una descripción libre del servidor. Esto generalmente incluye el nombre y la versión de la implementación del servidor.
log_id
El identificador del registro del lado del servidor. Este puede ser un nombre de ruta en el servidor o algún otro tipo de identificador del lado del servidor.
events
Una matriz de eventos que ocurrieron antes de que el cliente se conectara. Esto permite que el cliente recupere eventos que podrían haber ocurrido antes de que pudiera registrarse.

ServerAck

message ServerAck {
  TimeSpec ack_time = 1;
}

Un mensaje ServerAck es enviado por el servidor al cliente para acusar recibo de un mensaje enviado por el cliente. Contiene los siguientes miembros:

ack_time
La hora en que el servidor recibió el mensaje.

ServerReject

message ServerReject {
  string reason = 1;
}

Un mensaje ServerReject es enviado por el servidor al cliente para indicar que el servidor ha rechazado un mensaje del cliente. Contiene el siguiente miembro:

reason
La razón por la cual el servidor rechazó el mensaje.

ServerLogId

message ServerLogId {
  string log_id = 1;
}

Un mensaje ServerLogId es enviado por el servidor al cliente para proporcionar el identificador del registro del lado del servidor. Esto se utiliza para el registro de E/S y puede ser necesario para reanudar un registro interrumpido. Contiene el siguiente miembro:

log_id
El identificador del registro del lado del servidor.

ServerCommitPoint

message ServerCommitPoint {
  TimeSpec time = 1;
}

Un mensaje ServerCommitPoint es enviado por el servidor al cliente para indicar que todos los datos de E/S hasta este punto en el tiempo se han almacenado de forma segura. Contiene el siguiente miembro:

time
El tiempo transcurrido desde que se inició el comando, que indica el punto hasta el cual se han guardado los datos de E/S.

VARIABLES DE REGISTRO DE EVENTOS

El registro de eventos de Sudo es una secuencia de pares clave-valor. La mayoría de las claves son estándar y se definen en la sección de documentación de sudo.conf(5). Sin embargo, el protocolo sudo_logsrv.proto permite el envío de pares clave-valor arbitrarios que se pasan directamente al registro de eventos. Estos pares clave-valor se envían en el campo info_msgs de los mensajes AcceptMessage, RejectMessage y ClientHello.

El servidor de registro puede usar estos pares clave-valor para filtrar o enriquecer los registros de eventos. Por ejemplo, un cliente puede enviar el nombre y la versión de su implementación utilizando las claves client_name y client_version respectivamente.

Las siguientes claves están reservadas para el uso del protocolo:

client_name
El nombre de la implementación del cliente.
client_version
La versión de la implementación del cliente.
server_name
El nombre de la implementación del servidor.
server_version
La versión de la implementación del servidor.
log_id
El identificador del registro asignado por el servidor.

EJEMPLOS

Aquí hay un ejemplo de un registro de eventos simple enviado desde un cliente a un servidor.

Client:
  ClientHello { client_id: "sudo client 1.9.0" }
Server:
  ServerHello { server_id: "sudo log server 1.0.0", log_id: "20210101T100000Z" }
Client:
  AcceptMessage {
    submit_time { tv_sec: 1609485600 tv_nsec: 0 }
    info_msgs { key: "user", strval: "johndoe" }
    info_msgs { key: "pwd", strval: "/home/johndoe" }
    info_msgs { key: "argc", numval: 2 }
    info_msgs { key: "argv", strlistval: { strings: [ "sudo", "ls" ] } }
    info_msgs { key: "client_name", strval: "sudo" }
    info_msgs { key: "client_version", strval: "1.9.0" }
    expect_iobufs: true
  }
Client:
  IoBuffer { time { tv_sec: 0 tv_nsec: 100000000 } buffer: "total 16\n" is_tty: false }
  IoBuffer { time { tv_sec: 0 tv_nsec: 200000000 } buffer: "drwxr-xr-x  2 johndoe users 4096 Jan  1 10:00 bin\n" is_tty: false }
  IoBuffer { time { tv_sec: 0 tv_nsec: 300000000 } buffer: "drwxr-xr-x  3 johndoe users 4096 Jan  1 10:00 etc\n" is_tty: false }
  IoBuffer { time { tv_sec: 0 tv_nsec: 400000000 } buffer: "drwxr-xr-x  5 johndoe users 4096 Jan  1 10:00 home\n" is_tty: false }
  IoBuffer { time { tv_sec: 0 tv_nsec: 500000000 } commit_point: true buffer: "" is_tty: false }

Client Messages

A ClientMessage is a container used to encapsulate all the possible message types the client may send to a client.

message ClientMessage {
  oneof type {
    ClientHello hello = 1;
    AcceptMessage accept = 2;
    RejectMessage reject = 3;
    RestartMessage restart = 4;
    AlertMessage alert = 5;
    IoBuffer ttyin_buf = 6;
    IoBuffer ttyout_buf = 7;
    IoBuffer stdin_buf = 8;
    IoBuffer stdout_buf = 9;
    IoBuffer stderr_buf = 10;
    ChangeWindowSize winsize_event = 11;
    CommandSuspend suspend_event = 12;
    ExitMessage exit = 13;
  }
}

The different ClientMessage sub-messages the client may sent to the server are described below.

ClientHello hello

message ClientHello {
  string client_id = 1;
  int32 version = 2;
}

The ClientHello message consists of client information sent when the client first connects. It contains the following members:

client_id
A free-form client identifier. Usually this includes the name and version of the client implementation.
version
The protocol version implemented by the client. This is currently 0.

AcceptMessage accept_msg

message AcceptMessage {
  bool expect_iobufs = 1;
  repeated InfoMessage info_msgs = 2;
}

An AcceptMessage is sent by the client to indicate that the command should be run. It contains the following members:

expect_iobufs
If true, the server should expect the client to send IoBuffer messages. If false, the server should not expect any I/O logs.
info_msgs
An optional array of InfoMessage describing the user who submitted the command as well as the execution environment of the command. This information is used to generate an event log entry.

RejectMessage reject_msg

message RejectMessage {
  string reason = 1;
  repeated InfoMessage info_msgs = 2;
}

A RejectMessage is sent by the client to indicate that the command should not be run. It contains the following members:

reason
The reason for rejection.
info_msgs
An optional array of InfoMessage describing the user who submitted the command as well as the execution environment of the command. This information is used to generate an event log entry.

RestartMessage restart_msg

message RestartMessage {
  string reason = 1;
}

A RestartMessage is sent by the client to indicate that the command should be restarted in a different context. It contains the following member:

reason
The reason for restarting the command.

If a RestartMessage is sent, the client must not send an AcceptMessage or RejectMessage.

AlertMessage alert_msg

message AlertMessage {
  TimeSpec alert_time = 1;
  string reason = 2;
  repeated InfoMessage info_msgs = 3;
}

An AlertMessage is sent by the client to indicate a problem detected by the security policy while the command is running that should be stored in the event log. It contains the following members:

alert_time
The wall clock time when the alert occurred.
reason
The reason for the alert.
info_msgs
An optional array of InfoMessage describing the user who submitted the command as well as the execution environment of the command. This information is used to generate an event log entry.

IoBuffer ttyin_buf | ttyout_buf | stdin_buf | stdout_buf | stderr_buf

message IoBuffer {
  TimeSpec delay = 1;
  bytes data = 2;
}

An IoBuffer is used to represent data from terminal input, terminal output, standard input, standard output, or standard error. It contains the following members:

delay
The elapsed time since the last record in the form of a TimeSpec. The delay should be calculated using a monotonic clock where possible.
data
The binary I/O log data from terminal input, terminal output, standard input, standard output, or standard error.

ChangeWindowSize winsize_event

message ChangeWindowSize {
  TimeSpec delay = 1;
  int32 rows = 2;
  int32 cols = 3;
}

A ChangeWindowSize message is sent by the client when the terminal running the command changes size. It contains the following members:

delay
The elapsed time since the last record in the form of a TimeSpec. The delay should be calculated using a monotonic clock where possible.
rows
The new number of terminal rows.
cols
The new number of terminal columns.

CommandSuspend suspend_event

message CommandSuspend {
  TimeSpec delay = 1;
  string signal = 2;
}

A CommandSuspend message is sent by the client when the command is either suspended or resumed. It contains the following members:

delay
The elapsed time since the last record in the form of a TimeSpec. The delay should be calculated using a monotonic clock where possible.
signal
The signal name without the leading “SIG”. For example, STOP, TSTP, CONT.

ExitMessage exit_msg

message ExitMessage {
  TimeSpec delay = 1;
  int32 exit_status = 2;
  bool signaled = 3;
}

An ExitMessage is sent by the client when the command being logged exits. It contains the following members:

delay
The elapsed time since the last record in the form of a TimeSpec. The delay should be calculated using a monotonic clock where possible.
exit_status
The exit status of the command. This is only valid if signaled is false.
signaled
True if the command was terminated by a signal, false otherwise. When true, the value of exit_status is the signal number.

Server Messages

A ServerMessage is a container used to encapsulate all the possible message types the server may send to a client.

message ServerMessage {
  oneof type {
    ServerHello hello = 1;
    TimeSpec commit_point = 2;
    string log_id = 3;
    string error = 4;
    string abort = 5;
  }
}

The different ServerMessage sub-messages the server may sent to the client are described below.

ServerHello hello

message ServerHello {
  string server_id = 1;
  string redirect = 2;
  repeated string servers = 3;
  bool subcommands = 4;
}

The ServerHello message consists of server information sent when the client first connects. It contains the following members:

server_id
A free-form server description. Usually this includes the name and version of the implementation running on the log server. This member is always present.
redirect
A host and port separated by a colon (‘’): that the client should connect to instead. The host may be a host name, an IPv4 address, or an IPv6 address in square brackets. This may be used for server load balancing. The server will disconnect after sending the ServerHello when it includes a redirect.
servers
A list of other known log servers. This can be used to implement log server redundancy and allows the client to discover all other log servers simply by connecting to one known server. This member may be omitted when there is only a single log server.
subcommands
If set, the server supports logging additional commands during a session. The client may send an AcceptMessage or RejectMessage when sudo is running in intercept mode. In this mode, commands spawned from the initial command authorized by sudo are subject to policy restrictions and/or are logged. If subcommands is false, the client must not attempt to log additional commands.

TimeSpec commit_point

A periodic time stamp sent by the server to indicate when I/O log buffers have been committed to storage. This message is not sent after every IoBuffer but rather at a server-configurable interval. When the server receives an ExitMessage, it will respond with a commit_point corresponding to the last received IoBuffer before closing the connection.

string log_id

The server-side ID of the I/O log being stored, sent in response to an AcceptMessage where expect_iobufs is true.

string error

A fatal server-side error. The server will close the connection after sending the error message.

string abort

An abort message from the server indicates that the client should kill the command and terminate the session. It may be used to implement simple server-side policy. The server will close the connection after sending the abort message.

Protocol flow of control

The expected protocol flow is as follows:

  1. Client connects to the first available server. If the client is configured to use TLS, a TLS handshake will be attempted.
  2. Client sends ClientHello. This is currently optional but allows the server to detect a non-TLS connection on the TLS port.
  3. Server sends ServerHello.
  4. Client responds with either AcceptMessage, RejectMessage, or RestartMessage.
  5. If client sent a AcceptMessage with expect_iobufs set, server creates a new I/O log and responds with a log_id.
  6. Client sends zero or more IoBuffer messages.
  7. Server periodically responds to IoBuffer messages with a commit_point.
  8. Client sends an ExitMessage when the command exits or is killed.
  9. Server sends the final commit_point if one is pending.
  10. Server closes the connection. After receiving the final commit_point, the client shuts down its side of the TLS connection if TLS is in use, and closes the connection.
  11. Server shuts down its side of the TLS connection if TLS is in use, and closes the connection.

At any point, the server may send an error or abort message to the client at which point the server will close the connection. If an abort message is received, the client should terminate the running command.

EVENT LOG VARIABLES

AcceptMessage, AlertMessage and RejectMessage classes contain an array of InfoMessage that should contain information about the user who submitted the command as well as information about the execution environment of the command if it was accepted.

Some variables have a client, run, or submit prefix. These prefixes are used to eliminate ambiguity for variables that could apply to the client program, the user submitting the command, or the command being run. Variables with a client prefix pertain to the program performing the connection to the log server, for example sudo. Variables with a run prefix pertain to the command that the user requested be run. Variables with a submit prefix pertain to the user submitting the request (the user running sudo).

The following InfoMessage entries are required:

Key Type Description
client.argv String The command line arguments used to invoke the client program.
client.pid Integer The process ID of the client program.
run.command String The command to be run.
run.ttysize Integer[2] The size of the terminal associated with the command, if any. The first element is the number of rows and the second element is the number of columns.
submit.euid Integer The effective user ID of the user submitting the command.
submit.gid Integer The group ID of the user submitting the command.
submit.login String The login name of the user submitting the command.
submit.tty String The terminal associated with the user submitting the command, if any.
submit.uid Integer The user ID of the user submitting the command.

El servidor debe aceptar otras variables no listadas anteriormente, pero puede ignorarlas.

EJEMPLOS

La descripción de Protocol Buffers del protocolo del servidor de registro, utilizando la sintaxis “proto3”, se incluye a continuación en su totalidad.

syntax = "proto3";

/*
 * Mensaje del cliente al servidor. Los mensajes en la red van
 * precedidos por un tamaño de 32 bits en orden de bytes de red.
 */
message ClientMessage {
  oneof type {
    AcceptMessage accept_msg = 1;
    RejectMessage reject_msg = 2;
    ExitMessage exit_msg = 3;
    RestartMessage restart_msg = 4;
    AlertMessage alert_msg = 5;
    IoBuffer ttyin_buf = 6;
    IoBuffer ttyout_buf = 7;
    IoBuffer stdin_buf = 8;
    IoBuffer stdout_buf = 9;
    IoBuffer stderr_buf = 10;
    ChangeWindowSize winsize_event = 11;
    CommandSuspend suspend_event = 12;
  }
}

/* Equivalente de la estructura POSIX timespec */
message TimeSpec {
    int64 tv_sec = 1;		/* segundos */
    int32 tv_nsec = 2;		/* nanosegundos */
}

/* Buffer de E/S con datos de pulsaciones de teclas */
message IoBuffer {
  TimeSpec delay = 1;		/* tiempo transcurrido desde el último registro */
  bytes data = 2;		/* datos de pulsaciones de teclas */
}

/*
 * Pares clave/valor, como la información de la estructura Privilege Manager.
 * El valor puede ser un número, una cadena o una lista de cadenas.
 */
message InfoMessage {
  message StringList {
    repeated string strings = 1;
  }
  message NumberList {
    repeated int64 numbers = 1;
  }
  string key = 1;
  oneof value {
    int64 numval = 2;
    string strval = 3;
    StringList strlistval = 4;
    NumberList numlistval = 5;
  }
}

/*
 * Datos del registro de eventos para comandos aceptados por la política.
 */
message AcceptMessage {
  TimeSpec submit_time = 1;		/* hora en que se envió el comando */
  repeated InfoMessage info_msgs = 2;	/* datos del registro de eventos clave, valor */
  bool expect_iobufs = 3;		/* verdadero si el registro de E/S está habilitado */
}

/*
 * Datos del registro de eventos para comandos rechazados por la política.
 */
message RejectMessage {
  TimeSpec submit_time = 1;		/* hora en que se envió el comando */
  string reason = 2;			/* razón por la que se rechazó el comando */
  repeated InfoMessage info_msgs = 3;	/* datos del registro de eventos clave, valor */
}

/* Mensaje enviado por el cliente cuando el comando sale. */
/* Posiblemente revisar runtime y usar end_time en su lugar */
message ExitMessage {
  TimeSpec run_time = 1;	/* tiempo total transcurrido de ejecución */
  int32 exit_value = 2;		/* 0 a 255 */
  bool dumped_core = 3;		/* verdadero si el comando generó un core dump */
  string signal = 4;		/* nombre de la señal si fue terminado por señal */
  string error = 5;		/* si fue terminado debido a otro error */
}

/* Mensaje de alerta, específico del módulo de política. */
message AlertMessage {
  TimeSpec alert_time = 1;		/* hora en que ocurrió el mensaje de alerta */
  string reason = 2;			/* cadena de error de alerta de política */
  repeated InfoMessage info_msgs = 3;	/* datos del registro de eventos clave, valor */
}

/* Se utiliza para reiniciar un registro de E/S existente en el servidor. */
message RestartMessage {
  string log_id = 1;		/* ID del registro que se está reiniciando */
  TimeSpec resume_point = 2;	/* punto de reanudación (tiempo transcurrido) */
}

/* Evento de cambio de tamaño de ventana. */
message ChangeWindowSize {
  TimeSpec delay = 1;		/* tiempo transcurrido desde el último registro */
  int32 rows = 2;		/* nuevo número de filas */
  int32 cols = 3;		/* nuevo número de columnas */
}

/* Evento de suspensión/reanudación de comando. */
message CommandSuspend {
  TimeSpec delay = 1;		/* tiempo transcurrido desde el último registro */
  string signal = 2;		/* señal que causó la suspensión/reanudación */
}

/*
 * Mensajes del servidor al cliente. Los mensajes en la red van
 * precedidos por un tamaño de 32 bits en orden de bytes de red.
 */
message ServerMessage {
  oneof type {
    ServerHello hello = 1;	/* mensaje de saludo del servidor */
    TimeSpec commit_point = 2;	/* tiempo acumulado de los registros almacenados */
    string log_id = 3;		/* ID del registro de E/S en el lado del servidor */
    string error = 4;		/* mensaje de error del servidor */
    string abort = 5;		/* mensaje de abortar, matar el comando */
  }
}

/* Mensaje de saludo del servidor cuando el cliente se conecta. */
message ServerHello {
  string server_id = 1;		/* descripción libre del servidor */
  string redirect = 2;		/* redirección opcional si está ocupado */
  repeated string servers = 3;	/* lista opcional de servidores conocidos */
}
