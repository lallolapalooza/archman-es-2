NOMBRE

sudo_plugin — API de Plugins de Sudo

DESCRIPCIÓN

A partir de la versión 1.8, sudo soporta una API de plugins para el registro de políticas y sesiones. Los plugins pueden compilarse como objetos compartidos dinámicos (la opción por defecto en sistemas que los soportan) o compilarse estáticamente en el binario de sudo mismo. Por defecto, el plugin sudoers proporciona capacidades de auditoría, política de seguridad y registro de E/S. A través de la API de plugins, sudo puede configurarse para usar plugins alternativos proporcionados por terceros. Los plugins a utilizar se especifican en el archivo sudo.conf(5).

La API está versionada con un número de versión principal y menor. El número de versión menor se incrementa cuando se realizan adiciones. El número de versión principal se incrementa cuando se realizan cambios incompatibles. Un plugin debe verificar la versión que se le pasa y asegurarse de que la versión principal coincida.

La API de plugins está definida por el archivo de cabecera <sudo_plugin.h>.

API de plugins de política

Un plugin de política debe declarar y poblar una estructura struct policy_plugin en el ámbito global. Esta estructura contiene punteros a las funciones que implementan las comprobaciones de política de sudo. El nombre del símbolo debe especificarse en sudo.conf(5) junto con una ruta al plugin para que sudo pueda cargarlo.

struct policy_plugin {
#define SUDO_POLICY_PLUGIN     1
    unsigned int type; /* always SUDO_POLICY_PLUGIN */
    unsigned int version; /* always SUDO_API_VERSION */
    int (*open)(unsigned int version, sudo_conv_t conversation,
        sudo_printf_t sudo_plugin_printf, char * const settings[],
        char * const user_info[], char * const user_env[],
        char * const plugin_options[], const char **errstr);
    void (*close)(int exit_status, int error);
    int (*show_version)(int verbose);
    int (*check_policy)(int argc, char * const argv[],
        char *env_add[], char **command_info[],
        char **argv_out[], char **user_env_out[], const char **errstr);
    int (*list)(int argc, char * const argv[], int verbose,
        const char *user, const char **errstr);
    int (*validate)(const char **errstr);
    void (*invalidate)(int rmcred);
    int (*init_session)(struct passwd *pwd, char **user_env[],
        const char **errstr);
    void (*register_hooks)(int version,
       int (*register_hook)(struct sudo_hook *hook));
    void (*deregister_hooks)(int version,
       int (*deregister_hook)(struct sudo_hook *hook));
    struct sudo_plugin_event * (*event_alloc)(void);
};

Una struct policy_plugin tiene los siguientes campos:

type
El campo type siempre debe establecerse en SUDO_POLICY_PLUGIN.
version
El campo version debe establecerse en SUDO_API_VERSION.

Esto permite a sudo determinar la versión de la API con la que se compiló el plugin.

open
int (*open)(unsigned int version, sudo_conv_t conversation,
    sudo_printf_t sudo_plugin_printf, char * const settings[],
    char * const user_info[], char * const user_env[],
    char * const plugin_options[], const char **errstr);

Devuelve 1 en caso de éxito, 0 en caso de fallo, -1 si ocurrió un error general, o -2 si hubo un error de uso. En este último caso, sudo imprimirá un mensaje de uso antes de salir. Si ocurre un error, el plugin puede opcionalmente llamar a la función conversation() o a la función sudo_plugin_printf() con SUDO_CONF_ERROR_MSG para presentar información adicional de error al usuario.

Los argumentos de la función son los siguientes:

version
La versión pasada por sudo permite al plugin determinar el número de versión principal y menor de la API de plugins soportada por sudo.
conversation
Un puntero a la función conversation() que puede ser utilizada por el plugin para interactuar con el usuario (ver API de Conversación para más detalles). Devuelve 0 en caso de éxito y -1 en caso de fallo.
sudo_plugin_printf
Un puntero a una función estilo printf() que puede usarse para mostrar mensajes informativos o de error (ver API de Conversación para más detalles). Devuelve el número de caracteres impresos en caso de éxito y -1 en caso de fallo.
settings
Un vector de configuraciones de sudo proporcionadas por el usuario en formato de cadenas de "nombre=valor". El vector se termina con un puntero NULL. Estas configuraciones corresponden a las opciones que el usuario especificó al ejecutar sudo. Como tales, solo estarán presentes cuando la opción correspondiente se haya especificado en la línea de comandos.

Al analizar settings, el plugin debe dividir en el primer signo igual (‘=’) ya que el campo nombre nunca incluirá uno, pero el valor sí podría.

Los siguientes valores pueden ser establecidos por sudo:

bsdauth_type=string
Tipo de autenticación, si se especificó con la opción -a, a utilizar en sistemas donde se soporta la autenticación BSD.
closefrom=number
Si se especifica, el usuario ha solicitado a través de la opción -C que sudo cierre todos los descriptores de archivo con un valor de number o superior. El plugin puede opcionalmente pasar este valor, u otro, en la lista command_info.
cmnd_chroot=string
El directorio raíz (ver chroot(2)) en el que ejecutar el comando, según lo especificado por el usuario a través de la opción -R. El plugin puede ignorar o restringir la capacidad del usuario para especificar un nuevo directorio raíz. Solo disponible a partir de la versión de API 1.16.
cmnd_cwd=string
El directorio de trabajo en el que ejecutar el comando, según lo especificado por el usuario a través de la opción -D. El plugin puede ignorar o restringir la capacidad del usuario para especificar un nuevo directorio de trabajo. Solo disponible a partir de la versión de API 1.16.
debug_flags=string
Un nombre de archivo de depuración seguido de un espacio y una lista separada por comas de flags de depuración que corresponden a la entrada Debug del plugin en sudo.conf(5), si la hay. Los flags se pasan al plugin exactamente como aparecen en sudo.conf(5). close
void (*close)(int exit_status, int error);

Este callback se llama cuando el plugin se está cerrando. Los argumentos son el estado de salida del comando y un código de error (si lo hay).

show_version
int (*show_version)(int verbose);

Este callback se llama cuando el usuario solicita información sobre la versión de sudo (por ejemplo, usando -V). Si el argumento verbose es distinto de cero, el plugin debe imprimir información detallada sobre su propia versión y dependencias. Devuelve 0 en caso de éxito, o -1 en caso de error.

check_policy
int (*check_policy)(int argc, char * const argv[],
        char *env_add[], char **command_info[],
        char **argv_out[], char **user_env_out[], const char **errstr);

Este callback es llamado para verificar la política de seguridad para la ejecución de un comando. sudo toma una decisión basada en el valor de retorno de este callback:

1
Se permite la ejecución del comando.
0
Se deniega la ejecución del comando.
-1
Ocurrió un error, sudo saldrá.
-2
Error de uso, sudo imprimirá un mensaje de uso y saldrá.

La función recibe los siguientes argumentos:

argc
El número de argumentos en el vector argv.
argv
Un vector de cadenas que representa el comando a ejecutar y sus argumentos. El primer elemento (argv[0]) es el nombre del comando.
env_add
Un vector de cadenas en el formato "nombre=valor" que se añadirán al entorno del proceso hijo. El plugin puede añadir o modificar elementos en este vector. El vector debe terminar en NULL.
command_info
Un puntero a un vector de cadenas que contiene información sobre el comando. El plugin puede añadir o modificar elementos en este vector. El vector debe terminar en NULL. Los elementos que se pueden establecer son:
argv_out
Si el plugin necesita modificar el comando o sus argumentos, puede asignar memoria para un nuevo vector de argumentos y asignarlo a argv_out. sudo se encargará de liberar esta memoria. El plugin también puede modificar argv directamente.
user_env_out
Si el plugin necesita modificar el entorno del usuario, puede asignar memoria para un nuevo vector de entorno y asignarlo a user_env_out. sudo se encargará de liberar esta memoria. El plugin también puede modificar user_env directamente.
errstr
Un puntero a un puntero a cadena que el plugin puede usar para devolver un mensaje de error descriptivo en caso de fallo.
list
int (*list)(int argc, char * const argv[], int verbose,
        const char *user, const char **errstr);

Este callback se llama cuando el usuario solicita listar los comandos permitidos para un usuario específico (por ejemplo, usando -l). Si el argumento verbose es distinto de cero, el plugin debe imprimir información detallada. Devuelve 0 en caso de éxito, o -1 en caso de error.

validate
int (*validate)(const char **errstr);

Este callback se llama para validar la configuración del plugin. Devuelve 0 en caso de éxito, o -1 en caso de error.

invalidate
void (*invalidate)(int rmcred);

Este callback se llama cuando la configuración del plugin se vuelve inválida (por ejemplo, debido a cambios en la configuración de sudo). Si el argumento rmcred es distinto de cero, el plugin debe eliminar las credenciales del usuario.

init_session
int (*init_session)(struct passwd *pwd, char **user_env[],
        const char **errstr);

Este callback se llama al inicio de una sesión de sudo. Puede ser utilizado para realizar tareas de inicialización específicas de la sesión. El plugin puede modificar el entorno del usuario asignando un nuevo vector a user_env. Devuelve 0 en caso de éxito, o -1 en caso de error.

register_hooks
void (*register_hooks)(int version,
       int (*register_hook)(struct sudo_hook *hook));

Este callback se llama para registrar hooks personalizados dentro de sudo. El plugin puede llamar a la función register_hook() para registrar funciones que se ejecutarán en puntos específicos del ciclo de vida de sudo.

deregister_hooks
void (*deregister_hooks)(int version,
       int (*deregister_hook)(struct sudo_hook *hook));

Este callback se llama para anular el registro de hooks previamente registrados.

event_alloc
struct sudo_plugin_event * (*event_alloc)(void);

Este callback se utiliza para asignar un nuevo evento de plugin. Devuelve un puntero a la estructura struct sudo_plugin_event en caso de éxito, o NULL en caso de error.

API de plugins de sesión

Un plugin de sesión debe declarar y poblar una estructura struct session_plugin en el ámbito global. Esta estructura contiene punteros a las funciones que implementan las operaciones de inicio y cierre de sesión.

struct session_plugin {
#define SUDO_SESSION_PLUGIN    2
    unsigned int type; /* always SUDO_SESSION_PLUGIN */
    unsigned int version; /* always SUDO_API_VERSION */
    int (*open)(unsigned int version, sudo_conv_t conversation,
        sudo_printf_t sudo_plugin_printf, char * const settings[],
        char * const user_info[], char * const user_env[],
        char * const plugin_options[], const char **errstr);
    void (*close)(int exit_status, int error);
    int (*show_version)(int verbose);
    int (*notify)(int message, int argc, char * const argv[],
        char **env_add[], char **command_info[], const char **errstr);
    int (*init_session)(struct passwd *pwd, char **user_env[],
        const char **errstr);
    void (*destroy_session)(struct passwd *pwd, int exit_status, int error);
    int (*log_io)(int message, int argc, char * const argv[],
        char *env_add[], char **command_info[], const char **errstr);
    int (*log_tty)(int message, int argc, char * const argv[],
        char *env_add[], char **command_info[], const char **errstr);
};

Una struct session_plugin tiene los siguientes campos:

type
El campo type debe establecerse siempre en SUDO_SESSION_PLUGIN.
version
El campo version debe establecerse en SUDO_API_VERSION.
open
Este callback es idéntico al de la API de plugins de política.
close
Este callback es idéntico al de la API de plugins de política.
show_version
Este callback es idéntico al de la API de plugins de política.
notify
int (*notify)(int message, int argc, char * const argv[],
        char **env_add[], char **command_info[], const char **errstr);

Este callback se llama para notificar al plugin sobre eventos relacionados con la sesión. El argumento message indica el tipo de evento. Los valores posibles para message son:

SUDO_EVENT_PREV_EXEC
Se llama antes de ejecutar un comando.
SUDO_EVENT_POST_EXEC
Se llama después de ejecutar un comando.
SUDO_EVENT_USER_AUTH
Se llama durante la autenticación del usuario.
SUDO_EVENT_ACCT
Se llama para la contabilidad.

Devuelve 0 en caso de éxito, o -1 en caso de error.

init_session
Este callback es idéntico al de la API de plugins de política.
destroy_session
void (*destroy_session)(struct passwd *pwd, int exit_status, int error);

Este callback se llama al final de una sesión de sudo. Puede ser utilizado para realizar tareas de limpieza específicas de la sesión.

log_io
int (*log_io)(int message, int argc, char * const argv[],
        char *env_add[], char **command_info[], const char **errstr);

Este callback se llama para registrar las operaciones de entrada/salida (E/S) de un comando. El argumento message indica el tipo de operación de E/S que se está registrando. Los valores posibles para message son:

SUDO_IO_STDIN
Se está registrando la entrada estándar.
SUDO_IO_STDOUT
Se está registrando la salida estándar.
SUDO_IO_STDERR
Se está registrando el error estándar.

Devuelve 0 en caso de éxito, o -1 en caso de error.

log_tty
int (*log_tty)(int message, int argc, char * const argv[],
        char *env_add[], char **command_info[], const char **errstr);

Este callback se llama para registrar las operaciones de TTY de un comando. El argumento message indica el tipo de operación de TTY que se está registrando. Los valores posibles para message son:

SUDO_TTY_SETATTR
Se están modificando los atributos del TTY.
SUDO_TTY_WINSIZE
Se está modificando el tamaño de la ventana del TTY.

Devuelve 0 en caso de éxito, o -1 en caso de error.

API de Conversación

La API de conversación permite a los plugins interactuar con el usuario para solicitar información (por ejemplo, contraseñas) o mostrar mensajes.

sudo_conv_t
int (*conversation)(int num_msgs, struct message *msgs,
        struct sudo_command_state *state);

Esta función es utilizada por el plugin para mostrar mensajes al usuario y/o leer su respuesta. El argumento num_msgs es el número de mensajes en el vector msgs. El argumento state es un puntero a una estructura que contiene información sobre el estado actual del comando de sudo.

La estructura struct message tiene los siguientes campos:

msg_type
El tipo de mensaje (por ejemplo, SUDO_CONV_PROMPT_ECHO_OFF para solicitar una contraseña).
msg
El texto del mensaje.
resp
Un puntero a una cadena donde se almacenará la respuesta del usuario.
user_data
Datos definidos por el usuario que se pasan a la función de conversación.

La función de conversación devuelve 0 en caso de éxito, o -1 en caso de error.

sudo_printf_t
int (*sudo_printf)(int msg_type, const char *fmt, ...);

Esta función es utilizada por el plugin para imprimir mensajes informativos o de error. El argumento msg_type indica el tipo de mensaje (por ejemplo, SUDO_DEBUG_MSG, SUDO_INFO_MSG, SUDO_ERROR_MSG). Los argumentos restantes son los argumentos estándar de printf().

La función devuelve el número de caracteres impresos en caso de éxito, o -1 en caso de error.

EJEMPLOS

Para utilizar un plugin de política personalizado llamado my_policy.so, añadiría lo siguiente al archivo sudo.conf(5):

Policy my_policy.so

Para utilizar un plugin de sesión personalizado llamado my_session.so:

Session my_session.so

Puede especificar un símbolo de plugin personalizado si es necesario:

Policy my_policy.so my_policy_sym

También puede pasar opciones al plugin:

Policy my_policy.so my_policy_sym debug_flags=1

sudo se utiliza para permitir que los usuarios ejecuten comandos como otro usuario (por defecto, root) según las especificaciones del archivo /etc/sudoers. sudoers solo puede ser editado por el usuario root utilizando un editor de texto normal, pero se recomienda encarecidamente utilizar el editor visudo. visudo bloquea el archivo /etc/sudoers para evitar que varios usuarios editen el archivo al mismo tiempo y valida la sintaxis del archivo de configuración antes de escribir los cambios.

/etc/sudo.conf es el archivo de configuración del plugin de sudo. Si este archivo no existe, sudo utiliza valores predeterminados para la mayoría de los ajustes. Si el archivo existe, se lee línea por línea y se ignoran las líneas que comienzan con una almohadilla (#) o que están en blanco.

close
void (*close)(int exit_status, int error);

La función close() se llama cuando sudo ha terminado, poco antes de salir. A partir de la versión 1.15 de la API, close() se llama independientemente de si se ejecutó o no un comando. Esto hace posible que los plugins realicen la limpieza incluso cuando no se ejecutó un comando. No es posible determinar si se ejecutó un comando basándose únicamente en los argumentos pasados a la función close(). Para determinar si se ejecutó realmente un comando, el plugin debe hacer un seguimiento de si la función check_policy() se ejecutó correctamente.

Los argumentos de la función son los siguientes:

El estado de salida del comando, tal como lo devuelve la llamada al sistema wait(2), o cero si no se ejecutó ningún comando. El valor de exit_status no está definido si error es distinto de cero.
error
Si el comando no pudo ser ejecutado, este se establece al valor de errno establecido por la llamada al sistema execve(2). El plugin es responsable de mostrar la información de error a través de la función conversation() o sudo_plugin_printf(). Si el comando se ejecutó correctamente, el valor de error es cero.

Si no se define ninguna función close(), no se cargan plugins de registro de E/S, y ni las opciones timeout ni use_pty están establecidas en la lista command_info, el frontend de sudo puede ejecutar el comando directamente en lugar de ejecutarlo como un proceso hijo.

La función show_version() es llamada por sudo cuando el usuario especifica la opción -V. El plugin puede mostrar la información de su versión al usuario a través de la función conversation() o sudo_plugin_printf() usando SUDO_CONV_INFO_MSG. Si el usuario solicita información detallada de la versión, el flag verbose será distinto de cero.

Devuelve 1 en caso de éxito, 0 en caso de fallo, -1 si ocurrió un error general, o -2 si hubo un error de uso, aunque el valor de retorno actualmente se ignora.

check_policy

    char **command_info[], char **argv_out[], char **user_env_out[],
    const char **errstr);

La función check_policy() es llamada por sudo para determinar si al usuario se le permite ejecutar los comandos especificados.

Si la opción sudoedit fue habilitada en el array settings pasado a la función open(), el usuario ha solicitado el modo sudoedit. sudoedit es un mecanismo para editar uno o varios archivos donde se ejecuta un editor con las credenciales del usuario en lugar de con privilegios elevados. sudo logra esto creando copias temporales de los archivos a editar que el usuario puede escribir y luego sobrescribiendo los originales con las copias temporales una vez completada la edición. Si el plugin soporta sudoedit, debe establecer sudoedit=true en la lista command_info. El plugin

es responsable de elegir el editor a utilizar, potencialmente a partir de una variable en el entorno del usuario, como EDITOR, y debe almacenarse en argv_out (las variables de entorno pueden incluir opciones de línea de comandos). Los archivos a editar deben copiarse de argv a argv_out, separados del editor y sus argumentos por un elemento ‘--’. El ‘--’ será eliminado por sudo antes de que se ejecute el editor. El plugin también puede establecer sudoedit_nfiles al número de archivos a editar en la lista command_info; esto solo será utilizado por el frontend de sudo a partir de la versión de API 1.21.

La función check_policy() devuelve 1 si el comando está permitido, 0 si no está permitido, -1 para un error general, o -2 para un error de uso o si se especificó sudoedit pero no es compatible con el plugin. En este último caso, sudo imprimirá un mensaje de uso antes de salir. Si ocurre un error, el plugin puede llamar opcionalmente a la función conversation() o sudo_plugin_printf() con SUDO_CONF_ERROR_MSG para presentar información adicional de error al usuario.

exec_background=bool
Por defecto, sudo ejecuta un comando como proceso en primer plano mientras sudo se esté ejecutando en primer plano. Cuando exec_background está habilitado y el comando se está ejecutando en un pseudo-terminal (debido al registro de E/S o a la configuración use_pty), el comando se ejecutará como un proceso en segundo plano. Los intentos de leer desde el terminal de control (o de cambiar la configuración del terminal) resultarán en la suspensión del comando con la señal SIGTTIN (o SIGTTOU en el caso de la configuración del terminal). Si esto ocurre cuando sudo es un proceso en primer plano, el comando recibirá el terminal de control y se reanudará en primer plano sin intervención del usuario. La ventaja de ejecutar inicialmente el comando en segundo plano es que sudo no necesita leer del terminal a menos que el comando lo solicite explícitamente. De lo contrario, cualquier entrada de terminal debe pasarse al comando, ya sea que la haya requerido o no (el kernel almacena en búfer los terminales, por lo que no es posible saber si el comando realmente quiere la entrada). Esto es diferente del comportamiento histórico de sudo o cuando el comando no se está ejecutando en un pseudo-terminal.

Para que esto funcione sin problemas, el sistema operativo debe soportar el reinicio automático de las llamadas al sistema. Desafortunadamente, no todos los sistemas operativos lo hacen por defecto, e incluso aquellos que lo hacen pueden tener errores. Por ejemplo, macOS falla al reiniciar las llamadas al sistema tcgetattr() y tcsetattr() (esto es un error en macOS). Además, dado que este comportamiento depende de que el comando se detenga con las señales SIGTTIN o SIGTTOU, los programas que capturan estas señales y se suspenden con una señal diferente (generalmente SIGTOP) no se pondrán en primer plano automáticamente. Algunas versiones del comando linux su(1) se comportan de esta manera. Debido a esto, un plugin no debería establecer exec_background a menos que sea habilitado explícitamente por el administrador y debería haber una forma de habilitarlo o deshabilitarlo por comando.

Esta configuración no tiene efecto a menos que el registro de E/S esté habilitado o use_pty esté habilitado.

Manejadores de señales

El frontend de sudo instala manejadores de señales predeterminados para atrapar señales comunes mientras se ejecutan las funciones del plugin. Las siguientes señales son atrapadas por defecto antes de que se ejecute el comando:

  • SIGALRM
  • SIGHUP
  • SIGINT
  • SIGPIPE
  • SIGQUIT
  • SIGTERM
  • SIGTSTP
  • SIGUSR1
  • SIGUSR2

Si se recibe una señal fatal antes de que se ejecute el comando, sudo llamará a la función close() del plugin con un estado de salida de 128 más el valor de la señal recibida. Esto permite un registro coherente de los comandos terminados por una señal para los plugins que registran dicha información en su función close(). Una excepción a esto es SIGPIPE, que se ignora hasta que se ejecuta el comando.

Un plugin puede instalar temporalmente sus propios manejadores de señales, pero debe restaurar el manejador original antes de que la función del plugin devuelva.

API de funciones de gancho

A partir de la versión 1.2 de la API de plugins, es posible instalar ganchos (hooks) para ciertas funciones llamadas por el frontend de sudo.

Actualmente, los únicos ganchos soportados se refieren al manejo de variables de entorno. Los ganchos se pueden usar para interceptar intentos de obtener, establecer o eliminar variables de entorno para que estos cambios se reflejen en la versión del entorno que se utiliza para ejecutar un comando. Una futura versión de la API soportará ganchos para funciones internas del frontend de sudo.

Estructura de gancho

Los ganchos en sudo se describen mediante la siguiente estructura:

typedef int (*sudo_hook_fn_t)();

struct sudo_hook {
    unsigned int hook_version;
    unsigned int hook_type;
    sudo_hook_fn_t hook_fn;
    void *closure;
};

Una struct sudo_hook tiene los siguientes campos:

hook_version
El campo hook_version debe establecerse en SUDO_HOOK_VERSION.
hook_type
El campo hook_type puede ser uno de los siguientes tipos de gancho soportados:
SUDO_HOOK_SETENV
La función setenv(3) de la biblioteca C. Cualquier gancho registrado se ejecutará antes de la implementación de la biblioteca C. El campo hook_fn debe ser una función que coincida con el siguiente typedef: 
typedef int (*sudo_hook_fn_setenv_t)(const char *name,
   const char *value, int overwrite, void *closure);

Si el gancho registrado no coincide con el typedef, los resultados no están definidos.

SUDO_HOOK_UNSETENV
La función unsetenv(3) de la biblioteca C. Cualquier gancho registrado se ejecutará antes de la implementación de la biblioteca C. El campo hook_fn debe ser una función que coincida con el siguiente typedef: 
typedef int (*sudo_hook_fn_unsetenv_t)(const char *name,
   void *closure);
SUDO_HOOK_GETENV

Hook API

The hook API is a subset of the plugin API. It allows plugins to intercept calls to certain existing C library functions that sudo uses internally. Currently, the following hook types are supported:

SUDO_HOOK_GETENV
The C library getenv(3) function. Any registered hooks will run before the C library implementation. The hook_fn field should be a function that matches the following typedef: 
typedef int (*sudo_hook_fn_getenv_t)(const char *name,
       char **value, void *closure);

If the registered hook does not match the typedef the results are unspecified.

SUDO_HOOK_PUTENV
The C library putenv(3) function. Any registered hooks will run before the C library implementation. The hook_fn field should be a function that matches the following typedef: 
typedef int (*sudo_hook_fn_putenv_t)(char *string,
       void *closure);

If the registered hook does not match the typedef the results are unspecified.

hook_fn
sudo_hook_fn_t hook_fn;

The hook_fn field should be set to the plugin's hook implementation. The actual function arguments will vary depending on the hook_type (see hook_type above). In all cases, the closure field of struct sudo_hook is passed as the last function parameter. This can be used to pass arbitrary data to the plugin's hook implementation.

The function return value may be one of the following:

SUDO_HOOK_RET_ERROR
The hook function encountered an error.
SUDO_HOOK_RET_NEXT
The hook completed without error, go on to the next hook (including the system implementation if applicable). For example, a getenv(3) hook might return SUDO_HOOK_RET_NEXT if the specified variable was not found in the private copy of the environment.
SUDO_HOOK_RET_STOP
The hook completed without error, stop processing hooks for this invocation. This can be used to replace the system implementation. For example, a setenv hook that operates on a private copy of the environment but leaves environ unchanged.

Care must be taken when hooking C library functions, it is very easy to create an infinite loop. For example, a getenv(3) hook that calls the snprintf(3) function may create a loop if the snprintf(3) implementation calls getenv(3) to check the locale. To prevent this, you may wish to use a static variable in the hook function to guard against nested calls. For example:

static int in_progress = 0; /* avoid recursion */
if (in_progress)
    return SUDO_HOOK_RET_NEXT;
in_progress = 1;
...
in_progress = 0;
return SUDO_HOOK_RET_STOP;

Event API

When sudo runs a command, it uses an event loop to service signals and I/O. Events may be triggered based on time, a file or socket descriptor becoming ready, or due to receipt of a signal. Starting with API version 1.15, it is possible for a plugin to participate in this event loop by calling the event_alloc() function.

Event structure

Events are described by the following structure:

typedef void (*sudo_plugin_ev_callback_t)(int fd, int what, void *closure);

struct sudo_plugin_event {
    int (*set)(struct sudo_plugin_event *pev, int fd, int events,
        sudo_plugin_ev_callback_t callback, void *closure);
    int (*add)(struct sudo_plugin_event *pev, struct timespec *timeout);
    int (*del)(struct sudo_plugin_event *pev);
    int (*pending)(struct sudo_plugin_event *pev, int events,
        struct timespec *ts);
    int (*fd)(struct sudo_plugin_event *pev);
    void (*setbase)(struct sudo_plugin_event *pev, void *base);
    void (*loopbreak)(struct sudo_plugin_event *pev);
    void (*free)(struct sudo_plugin_event *pev);
};

A struct sudo_plugin_event contains the following function pointers:

set
int (*set)(struct sudo_plugin_event *pev, int fd, int events,
    sudo_plugin_ev_callback_t callback, void *closure);

The set() function takes the following arguments:

struct sudo_plugin_event *pev
A pointer to the struct sudo_plugin_event itself.
fd
The file or socket descriptor for I/O-based events or the signal number for signal events. For time-based events, fd must be -1.
events
The following values determine what will trigger the event callback:
SUDO_PLUGIN_EV_TIMEOUT
callback is run after the specified timeout expires
SUDO_PLUGIN_EV_READ
callback is run when the file descriptor is readable
SUDO_PLUGIN_EV_WRITE
callback is run when the file descriptor is writable
SUDO_PLUGIN_EV_PERSIST
event is persistent and remains enabled until explicitly deleted
SUDO_PLUGIN_EV_SIGNAL
callback is run when the specified signal is received

The SUDO_PLUGIN_EV_PERSIST flag may be ORed with any of the event types. It is also possible to OR SUDO_PLUGIN_EV_READ and SUDO_PLUGIN_EV_WRITE together to run the callback when a descriptor is ready to be either read from or written to. All other event values are mutually exclusive.

sudo_plugin_ev_callback_t callback
typedef void (*sudo_plugin_ev_callback_t)(int fd, int what,
    void *closure);

The function to call when an event is triggered. The callback() function is run with the following arguments:

fd
The file or socket descriptor for I/O-based events or the signal number for signal events.
what
The event type that triggered that callback. For events that have multiple event types (for example SUDO_PLUGIN_EV_READ and SUDO_PLUGIN_EV_WRITE) or have an associated timeout, what can be used to determine why the callback was run.
closure
The generic pointer that was specified in the set() function.
closure
A generic pointer that will be passed to the callback function.

The set() function returns 1 on success, and -1 if a error occurred.

add
int (*add)(struct sudo_plugin_event *pev, struct timespec *timeout);

The add() function adds the event pev to sudo's event loop. The event must have previously been initialized via the set() function. If the timeout argument is not NULL, it should specify a (relative) timeout after which the event will be triggered if the main event criteria has not been met. This is often used to implement an I/O timeout where the event will fire if a descriptor is not ready within a certain time period. If the event is already present in the event loop, its timeout will be adjusted to match the new value, if any.

The add() function returns 1 on success, and -1 if a error occurred.

del
int (*del)(struct sudo_plugin_event *pev);

The del() function deletes the event pev from sudo's event loop. Deleted events can be added back via the add() function.

The del() function returns 1 on success, and -1 if a error occurred.

pending
int (*pending)(struct sudo_plugin_event *pev, int events,
        struct timespec *ts);

The pending() function checks if event pev is pending. If the events argument is non-zero, it specifies which event types to check for. The return value is a bitmask of pending event types. If a timeout was specified when the event was added and it has expired, SUDO_PLUGIN_EV_TIMEOUT will be included in the returned bitmask. If ts is not NULL, it will be filled with the remaining time until the next timeout occurs for this event.

The pending() function returns 1 on success, and -1 if a error occurred.

fd
int (*fd)(struct sudo_plugin_event *pev);

The fd() function returns the file descriptor associated with the event pev, or -1 if none is associated.

setbase
void (*setbase)(struct sudo_plugin_event *pev, void *base);

The setbase() function sets the event base for event pev. This is primarily used internally by sudo.

loopbreak
void (*loopbreak)(struct sudo_plugin_event *pev);

The loopbreak() function causes the event loop to terminate as soon as possible. This is primarily used internally by sudo.

free
void (*free)(struct sudo_plugin_event *pev);

The free() function frees the event structure pev and any associated resources. The event should have been removed from the event loop using del() before calling this function.

PLUGIN API CHANGELOG

Version 1.1 (sudo 1.8.5)
The behavior when an I/O logging plugin returns 0 has changed. Previously, output from the command would be displayed to the terminal even if an output logging function returned 0.
Version 1.7 (sudo 1.8.12)
The plugin_path entry was added to the settings list.

The debug_flags entry now starts with a debug file path name and may occur multiple times if there are multiple plugin-specific Debug lines in the sudo.conf(5) file.

Version 1.8 (sudo 1.8.15)
The sudoedit_checkdir and sudoedit_follow entries were added to the command_info list. The default value of sudoedit_checkdir was changed to true in sudo 1.8.16.

The sudo conversation() function now takes a pointer to a struct sudo_conv_callback as its fourth argument. The sudo_conv_t definition has been updated to match. The plugin must specify that it supports plugin API version 1.8 or higher to receive a conversation function pointer that supports this argument.

Version 1.9 (sudo 1.8.16)
The execfd entry was added to the command_info list.
Version 1.10 (sudo 1.8.19)
The umask entry was added to the user_info list. The iolog_group, iolog_mode, and iolog_user entries were added to the command_info list.
Version 1.11 (sudo 1.8.20)
The timeout entry was added to the settings list.
Version 1.12 (sudo 1.8.21)
The change_winsize() function was added to struct io_plugin.
Version 1.13 (sudo 1.8.26)
The log_suspend() function was added to struct io_plugin.
Version 1.14 (sudo 1.8.29)
The umask_override entry was added to the command_info list.
Version 1.15 (sudo 1.9.0)
The cwd_optional entry was added to the command_info list.

The event_alloc() function was added to struct policy_plugin and struct io_plugin.

The errstr argument was added to the policy and I/O plugin functions which the plugin function can use to return an error string. This string may be used by the audit plugin to report failure or error conditions set by the other plugins.

The close() function is now called regardless of whether or not a command was actually executed. This makes it possible for plugins to perform cleanup even when a command was not run.

SUDO_CONV_REPL_MAX has increased from 255 to 1023 bytes.

Support for audit and approval plugins was added.

Version 1.16 (sudo 1.9.3)
Initial resource limit values were added to the user_info list.

The cmnd_chroot and cmnd_cwd entries were added to the settings list.

Version 1.17 (sudo 1.9.4)
The event_alloc() function was added to struct audit_plugin and struct approval_plugin.
Version 1.18 (sudo 1.9.9)
The policy may now set resource limit values in the command_info list. The intercept and log_subcmds entries were added to the command_info list.
Version 1.19 (sudo 1.9.11)
The intercept_ptrace and intercept_setid entries were added to the settings list. The apparmor_profile and use_ptrace entries were added to the command_info list.
Version 1.20 (sudo 1.9.12)
The update_ticket entry was added to the settings list. The intercept_verify entry was added to the command_info list.
Version 1.21 (sudo 1.9.13)
The sudoedit_nfiles entry was added to the command_info list.
Version 1.22 (sudo 1.9.16)
The ttydev entry was added to the user_info list.
