NOMBRE

Swaks - Swiss Army Knife SMTP, la herramienta de prueba de transacciones SMTP para todo uso

DESCRIPCIÓN

El objetivo principal de diseño de Swaks es ser una herramienta de prueba SMTP orientada a transacciones y flexible, programable. Maneja características y extensiones SMTP como TLS, autenticación y pipelining; múltiples versiones del protocolo SMTP, incluyendo SMTP, ESMTP y LMTP; y múltiples métodos de transporte, incluyendo sockets de dominio UNIX, sockets de dominio de internet y tuberías a procesos generados. Las opciones se pueden especificar en variables de entorno, archivos de configuración y la línea de comandos, lo que permite la máxima configurabilidad y facilidad de uso para operadores y scripts.

ARRANQUE RÁPIDO

Entregar un correo electrónico de prueba estándar a usuario@ejemplo.com en el puerto 25 de test-server.example.net:

swaks --to usuario@ejemplo.com --server test-server.example.net

Entregar un correo electrónico de prueba estándar, requiriendo autenticación CRAM-MD5 como el usuario yo@ejemplo.com. Se agregará una cabecera "X-Test" al cuerpo del correo electrónico. Se le pedirá la contraseña de autenticación si no se puede obtener de su archivo .netrc.

swaks --to usuario@ejemplo.com --from yo@ejemplo.com --auth CRAM-MD5 --auth-user yo@ejemplo.com --header-X-Test "correo de prueba"

Probar un escáner de virus usando EICAR en un archivo adjunto. No mostrar la parte DATA del mensaje:

swaks -t usuario@ejemplo.com --attach - --server test-server.example.com --suppress-data </ruta/a/eicar.txt

Probar un escáner de spam usando GTUBE en el cuerpo de un correo electrónico, enrutado a través de los registros MX de ejemplo.com:

swaks --to usuario@ejemplo.com --body @/ruta/a/archivo/gtube

Entregar un correo electrónico de prueba estándar a usuario@ejemplo.com usando el protocolo LMTP a través de un archivo de socket de dominio UNIX

swaks --to usuario@ejemplo.com --socket /var/lda.sock --protocol LMTP

Reportar todos los destinatarios en un archivo de texto que no son verificables en un servidor de prueba:

for E in `cat /ruta/a/archivo/email`
do
    swaks --to $E --server test-server.example.com --quit-after RCPT --hide-all
    [ $? -ne 0 ] && echo $E
done

TÉRMINOS Y CONVENCIONES

Este documento intenta ser consistente y específico en el uso de los siguientes términos para reducir la confusión.

Objetivo
El objetivo de una transacción es aquello a lo que Swaks se conecta. Este término genérico se usa en toda la documentación porque la mayoría de los otros términos implican incorrectamente algo sobre el transporte utilizado.
Transporte
El transporte es el método subyacente utilizado para conectarse al objetivo.
Transacción
Una transacción es la apertura de una conexión a través de un transporte a un objetivo y el uso de un protocolo de mensajería para intentar entregar un mensaje.
Protocolo
El protocolo es el lenguaje de aplicación utilizado para comunicarse con el objetivo. Este documento utiliza SMTP para hablar genéricamente de los tres protocolos admitidos, a menos que indique que está hablando del protocolo específico 'SMTP' y excluyendo los otros.
Mensaje
Los protocolos SMTP existen para transferir mensajes, un conjunto de bytes en un formato acordado que tiene un remitente y un destinatario.
Envolvente
La envolvente de un mensaje contiene el remitente y el destinatario "reales" de un mensaje. También se puede hacer referencia a sus componentes: remitente de envolvente y destinatarios de envolvente. Es importante tener en cuenta que la envolvente de un mensaje no tiene que coincidir con sus encabezados "To:" y "From:".
DATOS
La parte DATA de una transacción SMTP es el mensaje real que se está transportando. Consta tanto de los encabezados como del cuerpo del mensaje. DATA y cuerpo a veces se usan indistintamente, pero siempre son dos cosas distintas en este documento.
Encabezados
Los encabezados de un mensaje se definen como todas las líneas en la sección DATA del mensaje antes de la primera línea en blanco. Contienen información sobre el correo electrónico que se mostrará al destinatario, como "To:", "From:", "Subject:", etc. En este documento, los encabezados siempre se escribirán con la primera letra en mayúscula y dos puntos al final.
Cuerpo
El cuerpo de un mensaje es la parte de su sección DATA que sigue a la primera línea en blanco.
Opción
Una opción es una bandera que cambia el comportamiento de Swaks. Siempre se le llama opción, independientemente de cómo se proporcione. Por ejemplo, "--no-data-fixup" es una opción.
Argumento
Cuando una opción toma datos adicionales además de la opción en sí, esos datos adicionales se denominan argumento de la opción. En "--quit-after <stop-point>", "<stop-point>" es el argumento de la opción "--quit-after".
<cadena-literal>
Cuando se utiliza en la definición de una opción, el texto que se encuentra entre corchetes angulares ("<>") indica una etiqueta descriptiva para un valor que el usuario debe proporcionar. Por ejemplo, "--quit-after <stop-point>" indica que "<stop-point>" debe reemplazarse por un valor de stop-point válido.
[<valor-opcional>]
Cuando se utiliza en la definición de una opción, el texto entre corchetes ([]) indica que el valor es opcional y se puede omitir. Por ejemplo, "--to [<destinatario>]" indica que la opción "--to" se puede usar con o sin un "<destinatario>" especificado.

PROCESAMIENTO DE OPCIONES

Para evitar confusiones potenciales en este documento, una bandera para Swaks siempre se denomina "opción". Si la opción toma datos adicionales, esos datos adicionales se denominan argumento de la opción. Por ejemplo, se podría proporcionar "--from fred@ejemplo.com" a Swaks en la línea de comandos, siendo "--from" la opción y "fred@ejemplo.com" el argumento de "--from".

Las opciones y los argumentos son la única forma de proporcionar información a Swaks. Si Swaks encuentra datos durante el procesamiento de opciones que no son ni una opción ni un argumento de una opción, generará un error y saldrá. Por ejemplo, si se encontrara "--no-data-fixup 1" en la línea de comandos, esto resultaría en un error porque "--no-data-fixup" no toma un argumento y, por lo tanto, Swaks no sabría qué hacer con 1.

Las opciones se pueden proporcionar a Swaks de tres maneras. Se pueden especificar en un archivo de configuración, en variables de entorno y en la línea de comandos. Dependiendo de la opción específica y de si se le proporciona un argumento, Swaks puede solicitar al usuario el argumento.

Cuando Swaks evalúa sus opciones, primero busca un archivo de configuración (ya sea en una ubicación predeterminada o especificado con "--config"). Luego evalúa las opciones en las variables de entorno. Finalmente, evalúa las opciones de la línea de comandos. En cada ronda de procesamiento, las opciones establecidas anteriormente se anularán. Además, cualquier opción puede prefijarse con "no-" para hacer que Swaks olvide que la variable se había establecido previamente (ya sea en una ronda anterior o antes en la misma ronda). Esta capacidad es necesaria porque muchas opciones tratan un valor definido pero sin argumento de manera diferente a un valor no definido.

Como regla general, si se proporciona la misma opción varias veces, se utilizará la última vez que se proporcione. Esto se aplica tanto a métodos internos (si se proporciona "--from user1@ejemplo.com --from user2@ejemplo.com", se utilizará "user2@ejemplo.com") como a métodos cruzados (si se proporciona "

t;desde user1@example.com" se proporciona en un archivo de configuración y "--from user2@example.com" se proporciona en la línea de comandos, se utilizará "user2@example.com").

Cada definición de opción termina con una sinopsis entre paréntesis de cómo se comporta la opción. Se pueden usar los siguientes códigos:

Arg-None, Arg-Optional, Arg-Required
Estos tres códigos son mutuamente excluyentes y describen si la opción toma o no un argumento. Tenga en cuenta que esto no describe necesariamente si el argumento debe especificarse directamente, sino si se requiere un argumento eventualmente. Por ejemplo, "--to" está etiquetado como Arg-Required, pero es legal especificar "--to" en la línea de comandos sin un argumento. Esto se debe a que Swaks puede solicitar el argumento requerido si no se proporciona directamente.
From-Prompt
Una opción etiquetada con From-Prompt solicitará interactivamente al usuario el argumento si no se proporciona ninguno.
From-File
Una opción etiquetada con From-File manejará los argumentos como archivos en ciertas situaciones.

Si el argumento inicial es "-", el argumento final es el contenido de "STDIN". Múltiples opciones pueden especificar "STDIN", pero se utilizará el mismo contenido para cada una de ellas.

Si el argumento inicial está prefijado con "@", el argumento se tratará como una ruta a un archivo. El archivo se abrirá y su contenido se utilizará como argumento final. Si no se puede leer el contenido del archivo, Swaks saldrá. Para especificar un valor de cadena literal que comience con un "@", use dos símbolos "@". El primero será eliminado. No es posible incluir un archivo no calificado que comience con un signo "@" (como "--attach @file.txt" o "--attach @@file.txt"), pero si incluye una ruta al archivo que divide los dos "@", eso funcionará (por ejemplo, "--attach @./@file.txt" incluirá el contenido del archivo @file.txt).

Sensitive
Si una opción marcada como Sensitive intenta solicitar un argumento al usuario y la opción "--protect-prompt" está configurada, Swaks intentará enmascarar la entrada del usuario para que no se muestre en la terminal. Swaks intenta enmascarar la entrada de varias maneras, pero si ninguna de ellas funciona, el flujo del programa continuará con la entrada sin enmascarar.
Deprecated
Una opción etiquetada como Deprecated ha sido oficialmente desaprobada y se eliminará en una versión futura. Consulte la sección "DEPRECATIONS" de esta documentación para obtener detalles sobre las desaprobaciones.

El mecanismo y el formato exactos para usar cada uno de los tipos se enumeran a continuación.

ARCHIVOS DE CONFIGURACIÓN
Se puede usar un archivo de configuración para establecer opciones comúnmente utilizadas o anormalmente detalladas. Por defecto, Swaks busca en orden en $SWAKS_HOME/.swaksrc, $HOME/.swaksrc, y $LOGDIR/.swaksrc. Si se encuentra que alguno de ellos existe (y no se ha utilizado "--config"), ese archivo se utiliza como archivo de configuración.

Además, se puede especificar un archivo de configuración en una ubicación no predeterminada usando "--config". Si se establece y no se le da un argumento, Swaks no utilizará ningún archivo de configuración, incluido ningún archivo predeterminado. Si "--config" apunta a un archivo legible, se utiliza como archivo de configuración, anulando cualquier predeterminado que pueda existir. Si apunta a un archivo no legible, se mostrará un error y Swaks saldrá.

También se puede crear un conjunto de valores predeterminados "portátiles" agregando opciones al final del archivo del programa Swaks. Tal como se distribuye, la última línea de Swaks debería ser "__END__". Cualquier línea agregada después de "__END__" se tratará como el contenido de un archivo de configuración. Esto permite que un conjunto de preferencias de usuario se copie automáticamente de un servidor a otro en un solo archivo.

Si los archivos de configuración no se han desactivado explícitamente, la configuración "__END__" siempre se lee. Solo se utilizará otro archivo de configuración por invocación de Swaks, incluso si se especifican varios archivos de configuración. Si se van a leer la configuración "__END__" y otra configuración, la configuración "__END__" se procesará primero. Especificar la opción "--config" sin ningún argumento desactiva el procesamiento tanto de la configuración "__END__" como de cualquier archivo de configuración real.

En un archivo de configuración, las líneas que comienzan con una almohadilla ("#") se ignoran. Todas las demás líneas se suponen que son una opción para Swaks, con el guión o guiones iniciales opcionales. Todo lo que sigue al primer espacio de la línea de opción se supone que es el argumento de la opción y no se procesa por shell. Por lo tanto, las comillas generalmente no son necesarias y se incluirán literalmente en el argumento.

Hay una sutil diferencia entre proporcionar una opción sin argumento y proporcionar una opción con un argumento vacío. Si una línea de opción no tiene un espacio, toda la línea se trata como una opción y no hay argumento. Si la línea termina en un solo espacio, se procesará como una opción con un argumento vacío. Entonces, "apt" se tratará como "--apt", pero "apt " se tratará como "--apt ''".

Aquí hay un ejemplo del contenido de un archivo de configuración:

# siempre usar este remitente, sin importar el servidor o el usuario conectado
--from fred@example.com
# Prefiero que mis correos de prueba tengan una cabecera de remitente bonita. Nota
# la falta de guiones en la opción y la falta de comillas alrededor de
# todo el argumento.
h-From: "Fred Example" <fred@example.com>

Opciones específicas del archivo de configuración:

--config [<archivo-configuracion>]
Esta opción proporciona una ruta a un archivo de configuración específico que se utilizará. Si se especifica sin argumento, no se procesará ningún archivo de configuración encontrado automáticamente (a través de $HOME, etc., o "__END__"). Si el argumento es un archivo válido, ese archivo se utilizará como archivo de configuración (después de la configuración "__END__"). Si el argumento no es un archivo válido y legible, Swaks mostrará un error y saldrá. Esta opción se puede especificar varias veces, pero solo se utilizará la primera vez que se especifique (en la variable de entorno y en el orden de búsqueda de la línea de comandos). (Arg-Opcional)
VARIABLES DE ENTORNO DE CONFIGURACIÓN
Las opciones se pueden proporcionar a través de variables de entorno. Las variables tienen la forma $SWAKS_OPT_nombre, donde "nombre" es el nombre de la opción que se especificaría en la línea de comandos. Dado que los guiones no están permitidos en los nombres de variables de entorno en la mayoría de los shells tipo UNIX, no se deben usar guiones iniciales y cualquier guion dentro del nombre de la opción debe reemplazarse con guiones bajos. Lo siguiente crearía las mismas opciones que se muestran en el ejemplo del archivo de configuración: 
$ SWAKS_OPT_from='fred@example.com'
$ SWAKS_OPT_h_From='"Fred Example" <fred@example.com>'

Establecer una variable en un valor vacío es lo mismo que especificarla en la línea de comandos sin argumento. Por ejemplo, establecer <SWAKS_OPT_server=""> haría que Swaks solicite al usuario el servidor al que conectarse en cada invocación. En Windows, no es posible establecer variables de entorno vacías. El comportamiento se puede simular estableciendo la variable de entorno en "<>" en su lugar. Además, incrustar el nombre de la cabecera en la opción de cabecera a través de la variable de entorno no está permitido en Windows (por ejemplo, "SWAKS_OPT_header_Foo=bar" resultará en un error, pero "SWAKS_OPT_header="Foo: bar"" funcionará).

Debido a que no hay un orden inherente en las opciones proporcionadas al establecer variables de entorno, las opciones se ordenan antes de procesarse. Esta no es una gran solución, pero al menos define el comportamiento, que de otro modo sería indefinido. Como ejemplo, si tanto $SWAKS_OPT_from como $SWAKS_OPT_f estuvieran configurados, se usaría el valor de $SWAKS_OPT_from, porque se ordena después de $SWAKS_OPT_f. También como resultado de no tener un orden inherente en el procesamiento de entornos, la desactivación de opciones con el prefijo "no-" no es confiable. Funciona si la opción que se desactiva se ordena antes de "no-", pero falla si se ordena después. Dado que "no-" está principalmente destinado a operar entre tipos de configuración (por ejemplo, desactivar desde la línea de comandos una opción que se estableció en un archivo de configuración), es poco probable que esto sea un problema.

Además de establecer el equivalente a las opciones de línea de comandos, $SWAKS_HOME se puede establecer en un directorio que contenga el .swaksrc predeterminado que se utilizará.

TLS / CIFRADO

Estas son opciones relacionadas con el cifrado de la transacción. Se han probado y confirmado que funcionan con los tres métodos de transporte. El módulo Net::SSLeay se utiliza para realizar el cifrado cuando se solicita. Si este módulo no se puede cargar, Swaks ignorará la solicitud TLS o generará un error, dependiendo de si la solicitud era opcional. STARTTLS se define como una extensión en el protocolo ESMTP y no estará disponible si "--protocol" se establece en una variación de SMTP simple. Dado que no está definido en el protocolo en sí, "--tls-on-connect" está disponible para cualquier tipo de protocolo si el objetivo lo admite.

No se requiere un certificado local para negociar una conexión TLS. Sin embargo, algunos servidores utilizan la verificación de certificados del cliente para verificar que el cliente tiene permiso para conectarse. Se puede indicar a Swaks que utilice un certificado local específico utilizando las opciones "--tls-cert" y "--tls-key", y opcionalmente que utilice una cadena de certificados utilizando la opción "--tls-chain".

-tls
Requerir que la conexión utilice STARTTLS. Salir si TLS no está disponible por ninguna razón (no anunciado, negociaciones fallidas, etc.). (Arg-Ninguno)
-tlso, --tls-optional
Intentar utilizar STARTTLS si está disponible, continuar con la transacción normal si TLS no pudo negociarse por ninguna razón. Tenga en cuenta que esta es una opción semi-inútil tal como está implementada actualmente, ya que después de un fallo de negociación, el estado de la conexión es desconocido. En algunos casos, como una discrepancia de versión, la conexión debe dejarse en texto plano. En otros, como un fallo de verificación, el lado del servidor puede pensar que debe continuar hablando TLS mientras que el cliente piensa que es texto plano. Puede haber un intento de añadir una detección de estado más granular en el futuro, pero por ahora, solo tenga en cuenta que las cosas extrañas...
-tlsos, --tls-optional-strict
Intenta utilizar STARTTLS si está disponible. Continúa con la transacción si TLS se negocia con éxito o si STARTTLS no se anuncia. Si STARTTLS se anuncia pero las negociaciones de TLS fallan, trátalo como un error y aborta la transacción. Debido a la advertencia mencionada anteriormente, esta es una opción mucho más sensata que "--tls-optional". (Arg-None)
-tlsc, --tls-on-connect
Inicia una conexión TLS inmediatamente al conectarse. Siguiendo la convención común, si se especifica esta opción, el puerto predeterminado cambia de 25 a 465, aunque esto aún se puede anular con la opción --port. (Arg-None)
-tlsp, --tls-protocol <tls-version-specification>
Especifica qué protocolos usar (o no usar) al negociar TLS. En el momento de escribir esto, los protocolos disponibles son sslv2, sslv3, tlsv1, tlsv1_1, tlsv1_2 y tlsv1_3. La disponibilidad de estos protocolos depende de su biblioteca OpenSSL subyacente, por lo que es posible que no todos estén disponibles. La lista de protocolos disponibles se muestra en la salida de "--dump" (suponiendo que TLS esté disponible en absoluto).

La cadena de especificación es una lista separada por comas de protocolos que se pueden usar o no. Por ejemplo, 'tlsv1,tlsv1_1' solo tendrá éxito si uno de esos dos protocolos está disponible tanto en el cliente como en el servidor. Por el contrario, 'no_sslv2,no_sslv3' intentará negociar cualquier protocolo excepto sslv2 y sslv3. Las dos formas de especificación no se pueden mezclar. (Arg-Required)

--tls-cipher <cipher-string>
El argumento de esta opción se pasa a la biblioteca OpenSSL subyacente para establecer la lista de cifrados aceptables que se utilizarán para la conexión. El formato de esta cadena es opaco para Swaks y se define en https://www.openssl.org/docs/manmaster/man1/openssl-ciphers.html#CIPHER-LIST-FORMAT. Un breve ejemplo sería "--tls-cipher '3DES:+RSA'". (Arg-Required)
--tls-verify
Indica a Swaks que intente verificar el certificado del servidor. Esta opción es idéntica a especificar ambas opciones "--tls-verify-ca" y "--tls-verify-host". Consulte esas opciones para obtener descripciones detalladas de cómo ajustar cada tipo de verificación.

Por defecto, la verificación TLS no es obligatoria. Si la verificación TLS es requerida por "--tls-verify", "--tls-verify-ca" o "--tls-verify-host" y el tipo de verificación solicitado falla, la negociación TLS no tendrá éxito. (Arg-None)

--tls-verify-ca
Requiere que el certificado del servidor sea firmado por una autoridad de certificación conocida y que no esté caducado. Por defecto, la lista de CAs conocidas será la que esté disponible a través del cliente en el que se esté ejecutando Swaks. Para proporcionar una CA personalizada, consulte "--tls-ca-path". (Arg-None)
--tls-verify-host
Requiere que el destino de la conexión actual esté listado en el Nombre Alternativo del Sujeto (SAN) o en el Nombre Común del Sujeto (CN) del certificado del servidor.

El destino que Swaks utiliza para la verificación variará. Puede ser un nombre de host, proporcionado directamente a través de la opción "--server" o buscado a través de registros MX. En este caso, la verificación funciona como se espera. Si el destino es una IP, la IP se buscará en el certificado, lo que es posible pero inusual. Si el transporte es "--pipe" o "--socket", no habrá un destino significativo para verificar en el certificado y la verificación fallará. En esta situación, es mejor usar solo "--tls-verify-ca" o anular el destino utilizado para la verificación con la opción "--tls-verify-target". (Arg-None)

--tls-verify-target <verification-string>
Cuando se establece, el argumento de esta opción se utilizará como el host que se verificará para "--tls-verify-host". Esto es necesario cuando se utiliza "--tls-verify-host" con los transportes "--pipe" o "--socket", que no tienen un destino verificable por defecto. También se puede utilizar para anular la búsqueda de destino predeterminada cuando se utiliza el transporte "--server". Por ejemplo, se puede usar para verificar que el certificado de un servidor al que se conecta explícitamente por IP contiene un certificado específico. (Arg-Required)
--tls-ca-path <ca-location>
Especifica una ubicación alternativa para la información de la CA para verificar los certificados del servidor. El argumento puede apuntar a un archivo o directorio. El comportamiento predeterminado es utilizar la información predeterminada de la biblioteca OpenSSL subyacente. (Arg-Required)
--tls-cert <cert-file>
Proporciona una ruta a un archivo que contiene el certificado local que Swaks debe usar si se negocia TLS. Si se necesita proporcionar una cadena de certificados, se puede proporcionar a través de este archivo o a través de un archivo separado con "--tls-chain". Se requiere el argumento de la ruta del archivo. Tal como está implementado actualmente, el certificado en el archivo debe estar en formato PEM. Póngase en contacto con el autor si existe una necesidad convincente de ASN1. Si se establece esta opción, también se requerirá "--tls-key". (Arg-Required)
--tls-key <key-file>
Proporciona una ruta a un archivo que contiene la clave privada local que Swaks debe usar si se negocia TLS. Se requiere el argumento de la ruta del archivo. Tal como está implementado actualmente, el certificado en el archivo debe estar en formato PEM. Póngase en contacto con el autor si existe una necesidad convincente de ASN1. Si se establece esta opción, también se requerirá "--tls-cert". (Arg-Required)
--tls-chain <chain-file>
Proporciona una ruta a un archivo que contiene la cadena de certificados local que Swaks debe usar si se negocia TLS. Se requiere el argumento de la ruta del archivo. Tal como está implementado actualmente, el certificado en el archivo debe estar en formato PEM. Póngase en contacto con el autor si existe una necesidad convincente de ASN1. Si se establece esta opción, también se requerirán "--tls-cert" y "--tls-key". (Arg-Required)
--tls-get-peer-cert [<output-file>]
Obtiene una copia del certificado del par TLS. Si no se proporciona ningún argumento, se mostrará en "STDOUT". Si se proporciona un argumento, se asume que es una ruta del sistema de archivos que especifica dónde se debe escribir el certificado. La cadena guardada se puede examinar utilizando herramientas estándar como el comando openssl. Si se especifica un archivo, su contenido se sobrescribirá. Esta opción solo devolverá un certificado. Para obtener todos los certificados enviados por el servidor, consulte "--tls-get-peer-chain". (Arg-Optional)
--tls-get-peer-chain [<output-file>]
Obtiene una copia de la cadena de certificados TLS enviada por el servidor. Si no se proporciona ningún argumento, se mostrará en "STDOUT". Si se proporciona un argumento, se asume que es una ruta del sistema de archivos que especifica dónde se debe escribir el certificado. La cadena guardada se puede examinar utilizando herramientas estándar como el comando openssl. Si se especifica un archivo, su contenido se sobrescribirá. Consulte también "--tls-get-peer-cert". (Arg-Optional)
--tls-sni <sni-string>
Especifica el campo Server Name Indication (SNI) a enviar cuando se inicia la conexión TLS. (Arg-Required)

AUTENTICACIÓN

Swaks intentará autenticarse en el servidor de correo de destino si se le indica que lo haga. Esta sección detalla los tipos de autenticación disponibles, los requisitos, las opciones y sus interacciones, y otros detalles finos en el uso de la autenticación. Dado que la autenticación se define como una extensión en el protocolo ESMTP, no estará disponible si "--protocol" se establece en una variación de SMTP.

Todos los métodos de autenticación requieren codificación base64. Si el módulo Perl MIME::Base64 se puede cargar, Swaks intenta usarlo para realizar estas codificaciones. Si MIME::Base64 no está disponible, Swaks utilizará sus propias rutinas base64 integradas. Estas son más lentas que las rutinas de MIME::Base64 y menos revisadas, aunque han sido probadas exhaustivamente. Se recomienda usar el módulo MIME::Base64.

Si la autenticación es necesaria (ver las opciones a continuación para cuándo es y cuándo no es obligatoria) y no se cumplen los requisitos para el tipo de autenticación disponible, Swaks muestra un error y sale. Dos formas en que esto puede suceder incluyen forzar a Swaks a usar un tipo de autenticación específico que Swaks no puede usar debido a requisitos faltantes, o permitir que Swaks use cualquier tipo de autenticación, pero el servidor solo anuncia tipos que Swaks no puede soportar. En el primer caso, Swaks genera un error en el momento del procesamiento de opciones, ya que sabe de antemano que no podrá autenticarse. En el segundo caso, Swaks generará un error en la etapa de autenticación de la transacción SMTP, ya que Swaks no será consciente de que no podrá autenticarse hasta ese momento.

A continuación se presentan los tipos de autenticación admitidos, incluidas las notas y los requisitos individuales.

Las siguientes opciones afectan el uso de la autenticación por parte de Swaks. Todas estas opciones están interrelacionadas. Por ejemplo, especificar "--auth-user" implica "--auth" y "--auth-password". Especificar "--auth-optional" implica "--auth-user" y "--auth-password", etc.

-a, --auth [<auth-type>[,<auth-type>[,...]]]
Requiere que Swaks se autentique. Si no se proporciona ningún argumento, se intentan todos los tipos de autenticación admitidos anunciados por el servidor hasta que uno tenga éxito o todos fallen. Si se especifican uno o más tipos de autenticación como argumento, se intentan cada uno que el servidor también admita, en orden, hasta que uno tenga éxito o todos fallen. Esta opción requiere que Swaks se autentique, por lo que si no se encuentran tipos de autenticación comunes o ninguna credencial tiene éxito, Swaks muestra un error y sale. (Arg-Optional)

La siguiente tabla enumera los tipos de autenticación válidos

AUTHENTICATION OPTIONS

Swaks supports the following authentication types:

LOGIN, PLAIN
Estos tipos de autenticación básicos son totalmente compatibles y probados, y no tienen requisitos adicionales
CRAM-MD5
El autenticador CRAM-MD5 requiere el módulo Digest::MD5. Se prueba completamente y se cree que funciona contra cualquier servidor que lo implemente.
DIGEST-MD5
El autenticador DIGEST-MD5 (RFC2831) requiere el módulo Authen::SASL. Las versiones 20100211.0 y anteriores utilizaban Authen::DigestMD5, que tenía algunos errores a nivel de protocolo que impedían que funcionara con algunos servidores. El manejo de DIGEST-MD5 de Authen::SASL es mucho más robusto.

La implementación de DIGEST-MD5 en Swaks es bastante inmadura. Actualmente solo admite el tipo qop "auth", por ejemplo. Si tiene experiencia con DIGEST-MD5 y desea ayudar a que Swaks admita mejor DIGEST-MD5, póngase en contacto conmigo.

El valor "realm" del protocolo DIGEST-MD5 se puede establecer utilizando la palabra clave "realm" de "--auth-extra". Si no se proporciona ningún reino, se utilizará un valor predeterminado razonable.

Los valores "digest-uri" del protocolo DIGEST-MD5 se pueden establecer utilizando la opción "--auth-extra". Por ejemplo, podría crear el valor digest-uri de "lmtp/mail.example.com/example.com" con la opción "--auth-extra dmd5-serv-type=lmtp,dmd5-host=mail.example.com,dmd5-serv-name=example.com". La cadena "digest-uri-value" y sus componentes se definen en RFC2831. Si no se proporcionan ninguno de estos valores, se utilizarán valores predeterminados razonables.

CRAM-SHA1
El autenticador CRAM-SHA1 requiere el módulo Digest::SHA. Este tipo solo se ha probado contra una implementación no estándar en un servidor Exim y, por lo tanto, puede tener algunas deficiencias de implementación.
NTLM/SPA/MSN
Estos autenticadores requieren el módulo Authen::NTLM. Este tipo se ha probado contra Exim, Communigate y Exchange 2007.

Además del nombre de usuario y la contraseña estándar, este tipo de autenticación también puede reconocer un "dominio". El dominio se puede establecer utilizando la palabra clave "domain" de "--auth-extra". Tenga en cuenta que esto nunca se ha probado con un servidor de correo que no ignore DOMAIN, por lo que podría estar implementado incorrectamente.

-ao, --auth-optional [<auth-type>[,<auth-type>[,...]]]
Esta opción se comporta de manera idéntica a "--auth", excepto que solicita autenticación en lugar de requerirla. Si no se encuentran tipos de autenticación comunes o si ninguna credencial tiene éxito, Swaks procede como si la autenticación no se hubiera solicitado. (Arg-Opcional)
-aos, --auth-optional-strict [<auth-type>[,<auth-type>[,...]]]
Esta opción es un compromiso entre "--auth" y "--auth-optional". Si la autenticación nunca se intenta (el servidor no anuncia autenticación o no se encuentran tipos de autenticación comunes), se comporta como "--auth-optional" y la transacción smtp continúa. Si se intenta la autenticación pero falla, se comporta como "--auth" y sale con un error. (Arg-Opcional)
-au, --auth-user [<username>]
Proporciona el nombre de usuario que se utilizará para la autenticación. Si no se proporciona ningún nombre de usuario, indica que Swaks debe intentar encontrar el nombre de usuario a través de .netrc (requiere el módulo Net::Netrc). Si no se proporciona ningún nombre de usuario y no se puede encontrar a través de .netrc, se le pedirá al usuario que proporcione uno. La cadena "<>" se puede suministrar para significar un nombre de usuario vacío. (Arg-Requiere, Desde-Prompt)
-ap, --auth-password [<password>]
Proporciona la contraseña que se utilizará para la autenticación. Si no se proporciona ninguna contraseña, indica que Swaks debe intentar encontrar la contraseña a través de .netrc (requiere el módulo Net::Netrc). Si no se proporciona ninguna contraseña y no se puede encontrar a través de .netrc, se le pedirá al usuario que proporcione una. La cadena "<>" se puede suministrar para significar una contraseña vacía. (Arg-Requiere, Desde-Prompt, Sensible)
-ae, --auth-extra <key-value-pair>[,<key-value-pair>[,...]]
Algunos de los tipos de autenticación permiten incluir información adicional en el proceso de autenticación. En lugar de agregar una nueva opción para cada detalle de cada autenticador, la opción "--auth-extra" permite que esta información se proporcione. El formato para <key-value-pair> es KEYWORD=VALUE. (Arg-Requiere)

La siguiente tabla enumera las palabras clave actualmente reconocidas y los autenticadores que las utilizan

realm, domain
Las palabras clave realm y domain son sinónimas. Usar cualquiera de ellas establecerá la opción "domain" en NTLM/MSN/SPA y la opción "realm" en DIGEST-MD5
dmd5-serv-type
La palabra clave dmd5-serv-type es utilizada por el autenticador DIGEST-MD5 y se utiliza, en parte, para construir la cadena digest-uri-value (ver RFC2831)
dmd5-host
La palabra clave dmd5-host es utilizada por el autenticador DIGEST-MD5 y se utiliza, en parte, para construir la cadena digest-uri-value (ver RFC2831)
dmd5-serv-name
La palabra clave dmd5-serv-name es utilizada por el autenticador DIGEST-MD5 y se utiliza, en parte, para construir la cadena digest-uri-value (ver RFC2831)
-am, --auth-map <key-value-pair>[,<key-value-pair>[,...]]
Proporciona una forma de mapear nombres alternativos a tipos de autenticación base. Útil para cualquier sitio que utilice nombres alternativos para tipos comunes. El formato para <key-value-pair> es AUTH-ALIAS=AUTH-TYPE. Esta funcionalidad se utiliza en realidad internamente para mapear los tipos SPA y MSN al tipo base NTLM. El argumento de línea de comandos para simular esto sería "--auth-map SPA=NTLM,MSN=NTLM". -apt, --auth-plaintext

-ahp, --auth-hide-password [<replacement-string>]
Si se especifica esta opción, cada vez que se imprima una contraseña legible en la terminal (específicamente AUTH PLAIN y AUTH LOGIN), la contraseña se reemplazará con la cadena 'PROVIDED_BUT_REMOVED' (o el contenido de <replacement-string> si se proporciona). Si se proporciona un argumento de "2", solo imprime errores. Si se proporciona "3", no muestra ninguna salida nunca. "--silent" afecta a la mayoría de la salida, pero no a toda. Por ejemplo, "--help", "--version", "--dump" y "--dump-mail" no se ven afectados. Por razones históricas, -S no se puede configurar a través de variables de entorno en Windows, use SWAKS_OPT_silent en su lugar. (Arg-Optional)
--support
Imprime las capacidades y sale. Ciertas características requieren módulos Perl no estándar. Esta opción evalúa si estos módulos están presentes y muestra qué funcionalidad está disponible y cuál no, y qué módulos necesitarían añadirse para obtener la funcionalidad faltante. (Arg-None)
--dump-mail
Hace que Swaks procese todas las opciones para generar el mensaje que enviaría, luego imprime ese mensaje en "STDOUT" en lugar de enviarlo. Esta salida es idéntica a la sección "data" de "--dump", excepto sin el punto final. (Arg-None)
--dump [<sección>[,<sección>[,...]]]
Esta opción hace que Swaks imprima los resultados del procesamiento de opciones, inmediatamente antes de que se enviara el correo. No se enviará ningún correo cuando se use "--dump". Tenga en cuenta que "--dump" es una herramienta de autodiagnóstico pura y no se hace ni se hará ningún esfuerzo para enmascarar contraseñas en la salida de "--dump". Si se proporciona una sección como argumento a esta opción, solo se mostrará la sección solicitada. Los argumentos actualmente soportados son SUPPORT, APP, OUTPUT, TRANSPORT, PROTOCOL, XCLIENT, PROXY, TLS, AUTH, DATA y ALL. Si no se proporciona ningún argumento, se muestran todas las secciones (Arg-Optional)

SINOPSIS

DESCRIPCIÓN

swaks (Swiss Army Knife for SMTP) es una herramienta de línea de comandos diseñada para enviar correos electrónicos a través de SMTP. Es útil para probar configuraciones de servidores SMTP, verificar la conectividad de red y para enviar correos electrónicos programados.

OPCIONES

swaks soporta una amplia variedad de opciones para controlar cómo se envían los correos electrónicos. Las opciones se agrupan en las siguientes categorías:

OPCIONES GENERALES

  • -t TYPE, --test-type TYPE: Especifica el tipo de prueba SMTP a realizar. Los tipos comunes incluyen connect, send, relay, vrfy, noop.
  • -f FROM, --from FROM: La dirección del remitente del correo electrónico.
  • -r RECIPIENT, --to RECIPIENT: La dirección del destinatario del correo electrónico. Se pueden especificar múltiples destinatarios.
  • -s SERVER, --server SERVER: El nombre del host o la dirección IP del servidor SMTP a contactar.
  • -p PORT, --port PORT: El número de puerto del servidor SMTP. El valor predeterminado es 25.
  • -S, --ssl: Habilita la conexión SSL/TLS implícita (comúnmente en el puerto 465).
  • -e EHLO, --ehlo EHLO: Especifica la cadena EHLO a enviar al servidor.
  • -c, --connect-only: Solo se conecta al servidor, no envía ningún correo.
  • -k, --ehlo-only: Solo envía el comando EHLO y sale.
  • -d, --debug: Habilita la salida detallada de depuración.
  • -v, --verbose: Incrementa la verbosidad de la salida.
  • -l, --log-file: Especifica un archivo para registrar la salida.
  • -h, --help: Muestra el mensaje de ayuda y sale.

OPCIONES DE DEBUG

  • -v, --verbose: Aumenta la verbosidad de la salida.

OPCIONES DE AUTENTICACIÓN

  • -a AUTH TYPE, --auth-type AUTH TYPE: Especifica el método de autenticación (por ejemplo, LOGIN, PLAIN, CRAM-MD5).
  • -au USERNAME, --auth-user USERNAME: El nombre de usuario para la autenticación.
  • -ap PASSWORD, --auth-password PASSWORD: La contraseña para la autenticación.
  • -aa ACCEPTED, --auth-accepted ACCEPTED: Especifica las respuestas aceptadas del servidor durante el desafío de autenticación.
  • -am METHOD, --auth-method METHOD: Especifica el método de autenticación.
  • -AO OPTIONS, --auth-options OPTIONS: Opciones adicionales para la autenticación.

OPCIONES DE TLS

  • -S, --ssl: Habilita la conexión SSL/TLS implícita.
  • -Tl, --starttls: Habilita STARTTLS para iniciar una sesión TLS explícita después de la conexión inicial.
  • -Tc, --tls-cert CERTFILE: Especifica un archivo de certificado para usar con TLS.
  • -Tf FROMFILE, --tls-from-file FROMFILE: Lee el certificado y la clave privada de un archivo.
