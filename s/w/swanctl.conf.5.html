NOMBRE

swanctl.conf - archivo de configuración de swanctl

DESCRIPCIÓN

swanctl.conf es el archivo de configuración utilizado por la herramienta swanctl(8) para cargar configuraciones y credenciales en el demonio IKE de strongSwan.

Para una descripción de la sintaxis básica del archivo, incluyendo formatos de número/tiempo, o cómo referenciar secciones o dividir la configuración en varios archivos incluyendo otros archivos, consulte strongswan.conf(5).

CONFIGURACIONES

Las siguientes configuraciones se pueden usar para configurar conexiones, credenciales y pools.

conexiones

Sección que define las configuraciones de conexión IKE.

La sección de conexiones define las configuraciones de conexión IKE, cada una en sus propias subsecciones. En la descripción de las palabras clave a continuación, la conexión se llama <conn>, pero se puede elegir un nombre de conexión arbitrario pero único para cada subsección de conexión.

conexiones.<conn>

Sección para una conexión IKE llamada <conn>.
conexiones.<conn>.version [0]
Versión principal de IKE a utilizar para la conexión. 1 usa IKEv1, también conocido como ISAKMP, 2 usa IKEv2. Una conexión que usa el valor predeterminado de 0 acepta tanto IKEv1 como IKEv2 como respondedor, e inicia la conexión activamente con IKEv2.
conexiones.<conn>.local_addrs [%any]
Dirección(es) local(es) a utilizar para la comunicación IKE, separadas por comas. Acepta direcciones IPv4/IPv6 individuales, nombres DNS, subredes CIDR o rangos de direcciones IP.

Como iniciador, la primera dirección que no sea un rango/subred se utiliza para iniciar la conexión desde ella. Como respondedor, la dirección de destino local debe coincidir al menos con una de las direcciones, subredes o rangos especificados.

Si se asignan FQDN, se resuelven cada vez que se realiza una búsqueda de configuración. Si la resolución DNS falla, la búsqueda se retrasará durante ese tiempo.

conexiones.<conn>.remote_addrs [%any]
Dirección(es) remota(s) a utilizar para la comunicación IKE, separadas por comas. Acepta direcciones IPv4/IPv6 individuales, nombres DNS, subredes CIDR o rangos de direcciones IP.

Como iniciador, la primera dirección que no sea un rango/subred se utiliza para iniciar la conexión hacia ella. Como respondedor, la dirección de origen del iniciador debe coincidir al menos con una de las direcciones, subredes o rangos especificados.

Si se asignan FQDN, se resuelven cada vez que se realiza una búsqueda de configuración. Si la resolución DNS falla, la búsqueda se retrasará durante ese tiempo.

Para iniciar una conexión, se debe especificar al menos una dirección específica o un nombre DNS.

conexiones.<conn>.local_port [500]
Puerto UDP local para la comunicación IKE. Por defecto, se utiliza el puerto del backend de sockets, que suele ser 500. Si se utiliza el puerto 500, se utiliza el flotado automático del puerto IKE al puerto 4500 para solucionar problemas de NAT.

El uso de un puerto IKE local no predeterminado requiere soporte del backend de sockets en uso (socket-dynamic).

conexiones.<conn>.remote_port [500]
Puerto UDP remoto para la comunicación IKE. Si se utiliza el valor predeterminado del puerto 500, se utiliza el flotado automático del puerto IKE al puerto 4500 para solucionar problemas de NAT.
conexiones.<conn>.proposals [default]
Una propuesta es un conjunto de algoritmos. Para propuestas IKE que no son AEAD, esto incluye un algoritmo de cifrado, un algoritmo de integridad, una función pseudoaleatoria y un método de intercambio de claves. Para propuestas AEAD, en lugar de algoritmos de cifrado e integridad, se utiliza un algoritmo de modo combinado.

Con pares que admiten múltiples intercambios de claves IKEv2 (RFC 9370), se pueden negociar hasta siete intercambios de claves adicionales. Se pueden configurar prefijando la palabra clave del algoritmo con keX_ (donde X es un número entre 1 y 7).

Para IKEv2, se pueden especificar múltiples algoritmos del mismo tipo en una sola propuesta, de los cuales se selecciona uno. Para IKEv1, solo se permite un algoritmo por tipo por propuesta; los algoritmos adicionales se eliminarán implícitamente. Use múltiples propuestas para ofrecer diferentes combinaciones de algoritmos con IKEv1.

Las palabras clave de los algoritmos se separan usando guiones. Múltiples propuestas pueden separarse con comas. El valor especial default forma una propuesta predeterminada de algoritmos considerados seguros y suele ser una buena opción para la interoperabilidad.

conexiones.<conn>.vips []
Lista separada por comas de IPs virtuales a solicitar en cargas útiles de configuración IKEv2 o Modo Config IKEv1. Las direcciones comodín 0.0.0.0 y :: solicitan una dirección arbitraria, se pueden definir direcciones específicas. Sin embargo, el respondedor puede devolver una dirección diferente, o ninguna.
conexiones.<conn>.aggressive [no]
Habilita el Modo Agresivo en lugar del Modo Principal con Protección de Identidad. El Modo Agresivo se considera menos seguro, porque las cargas útiles ID y HASH se intercambian sin protección. Esto permite a un atacante pasivo espiar las identidades del par, y peor aún, iniciar ataques de diccionario en la Clave Precompartida.
conexiones.<conn>.pull [yes]
Si se utiliza el valor predeterminado de yes, el Modo Config funciona en modo de extracción (pull), donde el iniciador solicita activamente una IP virtual. Con no, se utiliza el modo de empuje (push), donde el respondedor envía una IP virtual al par que inicia la conexión.

El modo de empuje es compatible actualmente con IKEv1, pero no con IKEv2. Solo es utilizado por unas pocas implementaciones, se recomienda el modo de extracción.

conexiones.<conn>.dscp [000000]
Codepoint del Campo de Servicios Diferenciados a establecer en los paquetes IKE salientes para esta conexión. El valor es una cadena codificada en binario de seis dígitos que especifica el Codepoint a establecer, según se define en RFC 2474.
conexiones.<conn>.encap [no]
Para forzar la encapsulación UDP de los paquetes ESP, el demonio IKE puede simular las cargas útiles de detección NAT. Esto hace que el par crea que se produce NAT en la ruta, obligándolo a encapsular los paquetes ESP en UDP.

Por lo general, esto no es necesario, pero puede ayudar a solucionar problemas de conectividad con firewalls intermedios demasiado restrictivos.

conexiones.<conn>.mobike [yes]
Habilita MOBIKE en conexiones IKEv2. MOBIKE está habilitado por defecto en conexiones IKEv2 y permite la movilidad de clientes y la multi-homing en servidores migrando túneles IPsec activos.

Normalmente, mantener MOBIKE habilitado no causa problemas, ya que no se utiliza si el par no indica soporte para él. Sin embargo, debido al diseño de MOBIKE, IKEv2 siempre flota al puerto 4500 a partir del segundo intercambio. A algunas implementaciones no les gusta este comportamiento, por lo tanto, se puede deshabilitar.

conexiones.<conn>.dpd_delay [0s]
Intervalo para comprobar la viabilidad de un par activamente utilizando intercambios INFORMACIONALES de IKEv2 o mensajes R_U_THERE de IKEv1. La comprobación activa de DPD solo se impone si no se ha recibido ningún paquete IKE o ESP/AH durante el retraso de DPD configurado.
conexiones.<conn>.dpd_timeout [0s]

connections.<conn>.fragmentation [yes]
Utiliza fragmentación IKE (extensión IKEv1 propietaria o fragmentación RFC 7383 IKEv2). Los valores aceptables son yes (por defecto), accept, force y no. Si se establece en yes, y el par lo soporta, los mensajes IKE de tamaño excesivo se enviarán en fragmentos. Si se establece en accept, se anuncia el soporte de fragmentación al par, pero el demonio no envía sus propios mensajes en fragmentos. Si se establece en force (solo compatible con IKEv1) el mensaje IKE inicial ya se fragmentará si es necesario. Finalmente, establecer la opción en no deshabilitará el anuncio de soporte para esta característica.

Tenga en cuenta que los mensajes IKE fragmentados enviados por un par siempre se aceptan independientemente del valor de esta opción (incluso cuando se establece en no).

connections.<conn>.childless [allow]
Utiliza la iniciación de IKE_SA sin hijos (RFC 6023) para IKEv2, con el primer CHILD_SA creado con un intercambio CREATE_CHILD_SA separado (por ejemplo, para usar un intercambio de claves independiente para todos los CHILD_SA). Los valores aceptables son allow (por defecto), prefer, force y never. Si se establece en allow, los respondedores aceptarán IKE_SAs sin hijos (indicado a través de notify en la respuesta IKE_SA_INIT) mientras que los iniciadores continúan creando IKE_SAs regulares con el primer CHILD_SA creado durante IKE_AUTH, a menos que el IKE_SA se inicie explícitamente sin hijos (lo que fallará si el respondedor no soporta o ha deshabilitado esta extensión). El efecto de prefer es el mismo que allow en los respondedores, pero como iniciador se inicia un IKE_SA sin hijos si el respondedor lo soporta. Si se establece en force, solo se acepta la iniciación sin hijos en cualquier rol. Finalmente, establecer la opción en never deshabilita el soporte para IKE_SAs sin hijos como respondedor.
connections.<conn>.send_certreq [yes]
Envía payloads de solicitud de certificado para ofrecer certificados de CA raíz confiables al par. Las solicitudes de certificado ayudan al par a elegir un certificado/clave privada apropiado para la autenticación y están habilitadas por defecto.

Deshabilitar las solicitudes de certificado puede ser útil si hay demasiados certificados de CA raíz confiables instalados, ya que cada solicitud de certificado aumenta el tamaño de los paquetes IKE iniciales.

connections.<conn>.send_cert [ifasked]
Envía payloads de certificado al usar autenticación por certificado. Con el valor por defecto de ifasked, el demonio envía payloads de certificado solo si se han recibido solicitudes de certificado. never deshabilita el envío de payloads de certificado por completo, always hace que los payloads de certificado se envíen incondicionalmente siempre que se utilice la autenticación por certificado.
connections.<conn>.ocsp [reply]
Envía solicitudes de estado OCSP en payloads de solicitud de certificado y/o envía respuesta de estado OCSP en payloads de certificado al usar autenticación por certificado. Con el valor por defecto de reply, el demonio envía respuestas de estado OCSP en payloads de certificado si se ha recibido una solicitud de estado OCSP en una solicitud de certificado, never deshabilita el envío de solicitudes y respuestas de estado OCSP por completo, request hace que las solicitudes de estado OCSP en payloads de solicitud de certificado se envíen siempre que se utilice la autenticación por certificado, both combina reply y request.
connections.<conn>.ppk_id []
Cadena que identifica la Clave Precompartida Postcuántica (PPK) a utilizar.
connections.<conn>.ppk_required [no]
Si se requiere una Clave Precompartida Postcuántica (PPK) para esta conexión.
connections.<conn>.keyingtries [1]
Número de secuencias de retransmisión a realizar durante la conexión inicial. En lugar de abandonar la iniciación después de la primera secuencia de retransmisión con el valor por defecto de 1, se pueden iniciar secuencias adicionales de acuerdo con el valor configurado. Un valor de 0 inicia una nueva secuencia hasta que la conexión se establece o falla con un error permanente.
connections.<conn>.unique [no]
Política de unicidad de conexión a aplicar. Para evitar múltiples conexiones del mismo usuario, se puede aplicar una política de unicidad. El valor never nunca aplica dicha política, incluso si un par incluyó mensajes de notificación INITIAL_CONTACT, mientras que no reemplaza las conexiones existentes para la misma identidad si una nueva tiene la notificación INITIAL_CONTACT. keep rechaza nuevos intentos de conexión si el mismo usuario ya tiene una conexión activa, replace elimina cualquier conexión existente si se establece una nueva para el mismo usuario.

Para comparar conexiones en cuanto a unicidad, se utiliza la identidad IKE remota. Si la autenticación EAP o XAuth está involucrada, la identidad EAP o el nombre de usuario XAuth se utilizan para aplicar la política de unicidad en su lugar.

En los iniciadores, esta configuración especifica si se envía una notificación INITIAL_CONTACT durante IKE_AUTH si no se encuentra ninguna conexión existente con el par remoto (determinado por las identidades de la primera ronda de autenticación). A menos que se establezca en never, el cliente enviará una notificación.

connections.<conn>.reauth_time [0s]
Tiempo para programar la reautenticación IKE. La reautenticación IKE recrea la SA IKE/ISAKMP desde cero y reevalúa las credenciales. En configuraciones asimétricas (con EAP o payloads de configuración) puede no ser posible reautenticar activamente como respondedor. La negociación de la vida útil de reautenticación IKEv2 puede instruir al cliente a realizar la reautenticación.

La reautenticación está deshabilitada por defecto. Habilitarla generalmente puede resultar en interrupciones cortas de la conexión, incluso cuando se utiliza la reautenticación make-before-break, que ahora es la predeterminada. Sin embargo, son significativamente más cortas que cuando se utiliza el enfoque heredado break-before-make.

connections.<conn>.rekey_time [4h]
El rekeying IKE actualiza el material de la clave utilizando un intercambio Diffie-Hellman, pero no vuelve a verificar las credenciales asociadas. Solo se admite en IKEv2; IKEv1 realiza un procedimiento de reautenticación en su lugar.

Con el valor por defecto, el rekeying IKE se programa cada 4 horas, menos el rand_time configurado. Si se configura un reauth_time, rekey_time se establece en cero por defecto, deshabilitando el rekeying; configure ambos explícitamente para forzar el rekeying y la reautenticación.

connections.<conn>.over_time [10% of rekey_time/reauth_time]
Vida útil dura de IKE_SA si rekey/reauth no se completa, como tiempo. Para evitar que una IKE/ISAKMP se mantenga activa si la reautenticación o el rekeying IKE fallan perpetuamente, se puede especificar una vida útil dura máxima. Si la IKE_SA no logra rekeying o reautenticarse dentro del tiempo especificado, la IKE_SA se cierra.

A diferencia del rekeying de CHILD_SA, over_time es relativo en el tiempo a los valores de rekey_time y reauth_time, ya que se aplica a ambos.

El valor por defecto es el 10% del mayor entre rekey_time y reauth_time.

connections.<conn>.rand_time [over_time]
Rango de tiempo desde el cual elegir un valor aleatorio para restar de los tiempos de rekey/reauth. Para evitar que ambos pares inicien el procedimiento de rekey/reauth simultáneamente, se resta un tiempo aleatorio de los tiempos de rekey/reauth.

El valor por defecto es igual al over_time configurado.

connections.<conn>.pools []
Lista separada por comas de pools de IP con nombre de los cuales asignar direcciones IP virtuales y otros atributos de configuración. Cada nombre hace referencia a un pool por nombre de la sección pools o de un pool externo.
connections.<conn>.if_id_in [0]
ID de interfaz XFRM establecido en políticas/SA de entrada, puede ser anulado por la configuración del hijo, vea allí para más detalles.

El valor especial %unique asigna un ID de interfaz único por IKE_SA, que es heredado por todos sus CHILD_SAs (a menos que se anule allí), además, el valor %unique-dir asigna un ID de interfaz único diferente para cada dirección (entrada/salida).

connections.<conn>.if_id_out [0]
ID de interfaz XFRM establecido en políticas/SA de salida, puede ser anulado por la configuración del hijo, vea allí para más detalles.

El valor especial %unique asigna un ID de interfaz único por IKE_SA, que es heredado por todos sus CHILD_SAs (a menos que se anule allí), además, el valor %unique-dir asigna un ID de interfaz único diferente para cada dirección (entrada/salida).

connections.<conn>.mediation [no]
Si esta conexión es una conexión de mediación, es decir, si esta conexión se utiliza para mediar otras conexiones utilizando la Extensión de Mediación IKEv2. Las conexiones de mediación no crean ningún CHILD_SA.
connections.<conn>.mediated_by []
El nombre de la conexión a través de la cual se mediará esta conexión. Si se proporciona, la conexión se mediará a través de la conexión de mediación nombrada. La conexión de mediación debe tener medi ation habilitada.
connections.<conn>.mediation_peer []
Identidad bajo la cual el par se registra en el servidor de mediación, es decir, la identidad IKE que el otro extremo de esta conexión utiliza como su identidad local en su conexión al servidor de mediación. Esta es la identidad con la que solicitamos al servidor de mediación que nos medie. Solo relevante en conexiones que establecen mediated_by. Si no se proporciona, se utilizará la identidad IKE remota de la primera ronda de autenticación de esta conexión.
connections.<conn>.local<suffix>

Sección para una ronda de autenticación local. Una ronda de autenticación local define las reglas sobre cómo se realiza la autenticación para el par local. Se pueden definir múltiples rondas para usar RFC 4739 de IKEv2 Autenticación Múltiple o XAuth de IKEv1.

Cada ronda se define en una sección que tiene local como prefijo y un sufijo único opcional. Para definir una única ronda de autenticación, se puede omitir el sufijo.

connections.<conn>.local<suffix>.round [0]
Identificador numérico opcional por el cual se ordenan las rondas de autenticación. Si no se especifica, las rondas se ordenan según su posición en el archivo de configuración/mensaje VICI.
connections.<conn>.local<suffix>.certs []
Lista separada por comas de candidatos a certificados para usar en la autenticación. Los certificados pueden usar una ruta relativa desde el directorio x509 de swanctl o una ruta absoluta.

El certificado utilizado para la autenticación se selecciona basándose en las cargas útiles de solicitud de certificado recibidas. Si no se encuentra ninguna CA adecuada, se utiliza el primer certificado.

connections.<conn>.local<suffix>.cert<suffix> []
Sección para un candidato a certificado para usar en la autenticación. Los certificados en certs se transmiten como blobs binarios, estas secciones ofrecen más flexibilidad.
connections.<conn>.local<suffix>.cert<suffix>.file []
Ruta absoluta al certificado a cargar. Se pasa tal cual al demonio, por lo que debe ser legible por él.

Configure este o handle, pero no ambos, en una misma sección.

connections.<conn>.local<suffix>.cert<suffix>.handle []
ID CKA codificado en hexadecimal de un certificado en un token.

Configure este o file, pero no ambos, en una misma sección.

connections.<conn>.local<suffix>.cert<suffix>.slot []
Número de ranura opcional del token que almacena el certificado.
connections.<conn>.local<suffix>.cert<suffix>.module []
Nombre del módulo PKCS#11 opcional.
connections.<conn>.local<suffix>.pubkeys []
Lista separada por comas de candidatos a claves públicas en bruto para usar en la autenticación. Las claves públicas pueden usar una ruta relativa desde el directorio pubkey de swanctl o una ruta absoluta.

Aunque en principio se podrían definir múltiples claves públicas locales, solo se utiliza la primera clave pública de la lista para la autenticación.

connections.<conn>.local<suffix>.auth [pubkey]
Autenticación a realizar localmente. pubkey utiliza autenticación de clave pública mediante una clave privada asociada a un certificado utilizable. psk utiliza autenticación de clave precompartida. El específico de IKEv1 xauth se utiliza para autenticación XAuth o Híbrida, mientras que la palabra clave específica de IKEv2 eap define la autenticación EAP.

Para xauth, se puede añadir un nombre de backend específico, separado por un guion. Se selecciona el backend xauth apropiado para realizar el intercambio XAuth. Para XAuth tradicional, el método xauth se define generalmente en la segunda ronda de autenticación después de una ronda inicial de pubkey (o psk). Usar xauth en la primera ronda realiza la autenticación del cliente en Modo Híbrido.

Para eap, se puede añadir un nombre de método EAP específico, separado por un guion. Se selecciona un módulo EAP que implemente el método apropiado para realizar la conversación EAP.

Si ambos pares admiten RFC 7427 ("Autenticación de Firma en IKEv2") los algoritmos de hash específicos a utilizar durante la autenticación IKEv2 pueden ser configurados. Para hacerlo use ike: seguido de una restricción de esquema de firma de cadena de confianza (ver descripción de la palabra clave auth de la sección remote). Por ejemplo, con ike:pubkey-sha384-sha256 se utilizaría un esquema de firma de clave pública con SHA-384 o SHA-256, en ese orden y dependiendo de los algoritmos de hash admitidos por el par. Si no se configuran algoritmos de hash específicos, el valor por defecto es preferir un algoritmo que iguale o supere la fuerza de la clave de firma. Si no se configuran restricciones con el prefijo ike: cualquier restricción de esquema de firma (sin prefijo ike:) también se aplicará a la autenticación IKEv2, a menos que esto esté deshabilitado en strongswan.conf(5). Para utilizar firmas RSASSA-PSS use rsa/pss en lugar de pubkey o rsa como en, por ejemplo, ike:rsa/pss-sha256. Si se configuran restricciones pubkey o rsa, las firmas RSASSA-PSS solo se utilizarán si están habilitadas en strongswan.conf(5).

connections.<conn>.local<suffix>.id []
Identidad IKE a utilizar para la ronda de autenticación. Al usar autenticación de certificado, la identidad IKE debe estar contenida en el certificado, ya sea como sujeto o como subjectAltName.

La identidad puede ser una dirección IP, un nombre de dominio completamente calificado, una dirección de correo electrónico o un Nombre Distinguido para el cual el tipo de ID se determina automáticamente y la cadena se convierte a la codificación apropiada. Para forzar un tipo de identidad específico, se puede usar un prefijo, seguido de dos puntos (:). Si el signo de número (#) sigue a los dos puntos, los datos restantes se interpretan como codificación hexadecimal, de lo contrario, la cadena se utiliza tal cual como datos de identificación. Tenga en cuenta que esto implica que no se realiza ninguna conversión para identidades no-cadena. Por ejemplo, ipv4:10.0.0.1 no crea una identidad IKE válida ID_IPV4_ADDR, ya que no se convierte a binario 0x0a000001. En su lugar, se podría usar ipv4:#0a000001 para obtener una identidad válida, pero usar simplemente el tipo implícito con conversión automática suele ser más sencillo. Lo mismo se aplica a los tipos codificados en ASN1. Los siguientes prefijos son conocidos: ipv4, ipv6, rfc822, email, userfqdn, fqdn, dns, asn1dn, asn1gn y keyid. Los prefijos de tipo personalizados se pueden especificar rodeando el valor numérico del tipo con corchetes.

connections.<conn>.local<suffix>.eap_id [id]
Identidad EAP del cliente a utilizar en el intercambio EAP y en el método EAP.
connections.<conn>.local<suffix>.aaa_id [remote-id]
Identidad EAP del lado del servidor a esperar en el método EAP. Algunos métodos EAP, como EAP-TLS, utilizan una identidad para que el servidor realice la autenticación mutua. Esta identidad puede diferir de la identidad IKE, especialmente cuando la autenticación EAP se delega desde el respondedor IKE a un backend AAA.

Para EAP-(T)TLS, esto define la identidad para la cual el servidor debe proporcionar un certificado en el intercambio TLS.

connections.<conn>.local<suffix>.xauth_id [id]
Nombre de usuario XAuth del cliente utilizado en el intercambio XAuth.
connections.<conn>.remote<suffix>

Sección para una ronda de autenticación remota. Una ronda de autenticación remota define las restricciones sobre cómo los pares deben autenticarse para usar esta conexión. Se pueden definir múltiples rondas para usar RFC 4739 de IKEv2 Autenticación Múltiple o XAuth de IKEv1.

Cada ronda se define en una sección que tiene remote como prefijo y un sufijo único opcional. Para definir una única ronda de autenticación, se puede omitir el sufijo.

connections.<conn>.remote<suffix>.round [0]
Identificador numérico opcional por el cual se ordenan las rondas de autenticación. Si no se especifica, las rondas se ordenan según su posición en el archivo de configuración/mensaje VICI.
connections.<conn>.remote<suffix>.id [%any]
Identidad IKE a esperar para la ronda de autenticación. Consulte la palabra clave id de la sección local para obtener detalles.

Es posible usar comodines para hacer coincidir identidades remotas (por ejemplo, *@strongswan.org, *.strongswan.org, o C=CH,O=strongSwan,CN=*). Las conexiones con coincidencias exactas tienen preferencia. Al usar nombres distinguido con comodines, la opción charon.rdn_matching en strongswan.conf(5) especifica cómo se comparan los RDN.

También se admiten expresiones regulares POSIX extendidas para la comparación de identidades remotas. Deben comenzar con un prefijo de tipo explícito, seguido de un carácter de intercalación ('^'), y terminar con un signo de dólar ('$') para indicar un patrón anclado. Asegúrese de escapar los caracteres de barra invertida al configurar identidades entre comillas dobles. Los tipos admitidos son rfc822, email, userfqdn, fqdn, dns y asn1dn. Si bien las expresiones regulares siempre se comparan con la representación de cadena de otras identidades, el tipo también debe coincidir. La comparación se realiza sin distinción entre mayúsculas y minúsculas. Ejemplos: email:^(moon|sun)@strongswan\.org$, fqdn:^vpn[0-9]+\.strongswan\.org$, "asn1dn:^.*CN=.+\\.strongswan\\.org$".

connections.<conn>.children.<child>.ah_proposals []
Propuestas AH a ofrecer para el CHILD_SA. Una propuesta es un conjunto de algoritmos. Para AH, esto incluye un algoritmo de integridad y un método opcional de intercambio de claves. Si se especifica un método KE, el rekeying de CHILD_SA/Quick Mode y la negociación inicial utilizan un intercambio de claves separado utilizando el método negociado (consulte esp_proposals para obtener detalles).

Con pares que admiten múltiples intercambios de claves IKEv2 (RFC 9370), se pueden negociar hasta siete intercambios de claves adicionales. Se pueden configurar prefijando la palabra clave del algoritmo con keX_ (donde X es un número entre 1 y 7).

Para IKEv2, se pueden especificar múltiples algoritmos del mismo tipo en una única propuesta, de la cual se selecciona uno. Para IKEv1, solo se permite un algoritmo por tipo por propuesta; los algoritmos adicionales se eliminarán implícitamente. Utilice múltiples propuestas para ofrecer diferentes combinaciones de algoritmos con IKEv1.

Las palabras clave de los algoritmos se separan usando guiones. Múltiples propuestas pueden separarse por comas. El valor especial default forma una propuesta predeterminada de algoritmos compatibles considerados seguros, y suele ser una buena opción para la interoperabilidad. Por defecto, no se incluyen propuestas AH, sino que se propone ESP.

connections.<conn>.children.<child>.esp_proposals [default]
Propuestas ESP a ofrecer para CHILD_SA. Una propuesta es un conjunto de algoritmos. Para propuestas ESP que no son AEAD, esto incluye un algoritmo de integridad, un algoritmo de cifrado, un método de intercambio de claves opcional y un indicador opcional de Modo de Secuencia Extendido. Para propuestas AEAD, se utiliza un algoritmo de modo combinado en lugar de los algoritmos de cifrado/integridad por separado.

Si se negocia un método de intercambio de claves, el rekeying de CHILD_SA/Quick Mode y la negociación inicial utilizan un intercambio de claves separado utilizando el método especificado. Sin embargo, para IKEv2, las claves de CHILD_SA creadas implícitamente con IKE_SA siempre se derivarán del material de claves de IKE_SA. Por lo tanto, cualquier método de intercambio de claves especificado aquí solo se aplicará cuando CHILD_SA se rekeyee más tarde o se cree con un intercambio CREATE_CHILD_SA separado. Por lo tanto, es posible que una discrepancia de propuesta no se note inmediatamente cuando se establece la SA, pero puede hacer que el rekeying falle más tarde. Si se configuran uno o más métodos de intercambio de claves en una propuesta, el intercambio de claves puede hacerse opcional agregando también none.

Con pares que admiten múltiples intercambios de claves IKEv2 (RFC 9370), se pueden negociar hasta siete intercambios de claves adicionales. Se pueden configurar prefijando la palabra clave del algoritmo con keX_ (donde X es un número entre 1 y 7). Los intercambios de claves adicionales pueden hacerse opcionales agregando keX_none a una propuesta.

El soporte de Secuencia Extendido puede indicarse con los valores esn y noesn, ambos pueden incluirse para indicar soporte para ambos modos. Si se omite, se asume noesn.

Para IKEv2, se pueden especificar múltiples algoritmos del mismo tipo en una única propuesta, de la cual se selecciona uno. Para IKEv1, solo se permite un algoritmo por tipo por propuesta; los algoritmos adicionales se eliminarán implícitamente. Utilice múltiples propuestas para ofrecer diferentes combinaciones de algoritmos con IKEv1.

Las palabras clave de los algoritmos se separan usando guiones. Múltiples propuestas pueden separarse por comas. El valor especial default forma una propuesta predeterminada de algoritmos compatibles considerados seguros, y suele ser una buena opción para la interoperabilidad. Si no se especifican algoritmos para AH ni para ESP, se incluye el conjunto predeterminado de algoritmos para ESP.

connections.<conn>.children.<child>.local_ts [dynamic]
Lista separada por comas de selectores de tráfico local para incluir en CHILD_SA. Cada selector es una definición de subred CIDR, seguida de un selector opcional de protocolo/puerto. El valor especial dynamic puede usarse en lugar de una definición de subred, que se reemplaza por la dirección externa del túnel o la IP virtual, si se negocia. Este es el valor predeterminado.

Un selector de protocolo/puerto está rodeado por corchetes de apertura y cierre. Entre estos corchetes, se puede especificar un nombre numérico o de protocolo de getservent(3). Después de la restricción opcional de protocolo, se puede especificar una restricción de puerto opcional, separada por una barra. La restricción de puerto puede ser numérica, un nombre de servicio de getservent(3), o el valor especial opaque para selectores OPAQUE de RFC 4301. También se pueden especificar rangos de puertos, aunque ninguno de los backends del kernel soporta actualmente rangos de puertos. Si el protocolo es icmp o ipv6-icmp, el puerto se interpreta como tipo de mensaje ICMP si es menor que 256 o como tipo y código si es mayor o igual a 256, con el tipo en los 8 bits más significativos y el código en los 8 bits menos significativos.

Cuando se usa IKEv1, solo se interpreta el primer selector, excepto si se usa el plugin de extensión Cisco Unity. Esto se debe a una limitación del protocolo IKEv1, que solo permite un único par de selectores por CHILD_SA. Por lo tanto, para tunelizar tráfico que coincida con varios pares de selectores cuando se usa IKEv1, se deben definir varios childs (CHILD_SAs) que cubran los selectores.

El demonio IKE utiliza el estrechamiento de selectores de tráfico para IKEv1, de la misma manera que está estandarizado e implementado para IKEv2. Sin embargo, esto puede causar problemas con otras implementaciones. Para evitarlo, configure selectores idénticos en tales escenarios.

El valor trap instala una política de trampa, que activa el túnel tan pronto como se detecta tráfico coincidente. El valor start inicia la conexión activamente. Estos dos modos pueden combinarse con trap|start, para iniciar inmediatamente una conexión para la cual se han instalado políticas de trampa.

Al descargar o reemplazar una configuración CHILD_SA que tiene una start_action diferente de none, se realiza la acción inversa. Las configuraciones con start se cierran, mientras que las configuraciones con trap se desinstalan (ambas ocurren para las conexiones con trap|start).

connections.<conn>.children.<child>.close_action [none]

close_action no proporciona ninguna garantía de que el CHILD_SA se mantenga activo. Actúa solo sobre mensajes de cierre explícitos, pero no sobre fallos de negociación. Utilice políticas de trampa para recrear de forma fiable los CHILD_SAs fallidos.
