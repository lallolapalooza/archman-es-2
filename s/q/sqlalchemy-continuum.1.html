NOMBRE

sqlalchemy-continuum - Documentación de SQLAlchemy-Continuum

SQLAlchemy-Continuum es una extensión de versionado para SQLAlchemy.

INTRODUCCIÓN

¿Por qué?

Como entusiasta de Python/SQLAlchemy, quería crear una herramienta de versionado de bases de datos para Python con todas las características de Envers y con una API tan intuitiva como papertrail. También quería hacerlo _rápido_ manteniendo las cosas lo más cerca posible de la base de datos.

Características

  • No almacena actualizaciones que no cambian nada
  • Soporta migraciones de Alembic
  • Puede revertir los datos de los objetos, así como todas las relaciones de los objetos en una transacción dada, incluso si el objeto fue eliminado
  • Las transacciones se pueden consultar posteriormente utilizando la sintaxis de consulta de SQLAlchemy
  • Consulta de registros modificados en una transacción dada
  • Consulta de versiones de una entidad que modificó una propiedad dada
  • Consulta de transacciones en las que cambiaron las entidades de una clase dada
  • Los modelos de historial dan acceso a las relaciones de los objetos padre en cualquier momento dado

Instalación

pip install SQLAlchemy-Continuum

Conceptos básicos

Para que tus modelos sean versionados, necesitas dos cosas:

1.
Llama a make_versioned() antes de que se definan tus modelos.
2.
Agrega \_\_versioned\_\_ a todos los modelos a los que quieras añadir versionado
import sqlalchemy as sa
from sqlalchemy_continuum import make_versioned
make_versioned(user_cls=None)
class Article(Base):
    __versioned__ = {}
    __tablename__ = 'article'
    id = sa.Column(sa.Integer, primary_key=True, autoincrement=True)
    name = sa.Column(sa.Unicode(255))
    content = sa.Column(sa.UnicodeText)
# después de haber definido todos tus modelos, llama a configure_mappers():
sa.orm.configure_mappers()

Después de esta configuración, SQLAlchemy-Continuum hace lo siguiente:

1.
Crea el modelo ArticleHistory que actúa como historial de versiones para el modelo Article
2.
Crea los modelos TransactionLog y TransactionChanges para el seguimiento del historial transaccional
3.
Agrega un par de listeners para que cada inserción, actualización y eliminación de objetos Article se registre

Cuando los modelos se han configurado, ya sea llamando a configure_mappers() o accediendo a alguno de ellos por primera vez, las siguientes cosas estarán disponibles:

from sqlalchemy_continuum import version_class, parent_class
version_class(Article)  # clase ArticleHistory
parent_class(version_class(Article))  # clase Article

Versiones y transacciones

Al final de cada transacción, SQLAlchemy-Continuum recopila todos los cambios y crea objetos de versión para cada entidad versionada modificada. Continuum también crea una entidad TransactionLog y N entidades TransactionChanges por transacción (donde N es el número de clases afectadas por transacción). Las entidades TransactionLog y TransactionChanges se crean para el seguimiento de transacciones.

article = Article(name=u'Some article')
session.add(article)
session.commit()
article.versions[0].name == u'Some article'
article.name = u'Some updated article'
session.commit()
article.versions[1].name == u'Some updated article'

OBJETOS DE VERSIÓN

Tipos de operación

Al modificar entidades y confirmar los resultados en la base de datos, Continuum guarda las operaciones utilizadas (INSERT, UPDATE o DELETE) en las entidades de versión. Los tipos de operación se almacenan por defecto en un pequeño campo entero llamado 'operation_type'. La clase llamada 'Operation' contiene constantes convenientes para estos valores, como se muestra a continuación:

from sqlalchemy_continuum import Operation
article = Article(name=u'Some article')
session.add(article)
session.commit()
article.versions[0].operation_type == Operation.INSERT
article.name = u'Some updated article'
session.commit()
article.versions[1].operation_type == Operation.UPDATE
session.delete(article)
session.commit()
article.versions[2].operation_type == Operation.DELETE

Recorrido de versiones

first_version = article.versions[0]
first_version.index
# 0
second_version = first_version.next
assert second_version == article.versions[1]
second_version.previous == first_version
# True
second_version.index
# 1

Conjunto de cambios

Continuum proporciona una forma fácil de obtener el conjunto de cambios de un objeto de versión dado. Cada versión contiene una propiedad changeset que contiene un diccionario de los campos cambiados en esa versión.

article = Article(name=u'New article', content=u'Some content')
session.add(article)
session.commit(article)
version = article.versions[0]
version.changeset
# {
#   'id': [None, 1],
#   'name': [None, u'New article'],
#   'content': [None, u'Some content']
# }
article.name = u'Updated article'
session.commit()
version = article.versions[1]
version.changeset
# {
#   'name': [u'New article', u'Updated article'],
# }
session.delete(article)
version = article.versions[2]
version.changeset
# {
#   'id': [1, None]
#   'name': [u'Updated article', None],
#   'content': [u'Some content', None]
# }

SQLAlchemy-Continuum también proporciona una función de utilidad llamada changeset. Con esta función, puedes verificar fácilmente el conjunto de cambios de un objeto dado en la transacción actual.

from sqlalchemy_continuum import changeset
article = Article(name=u'Some article')
changeset(article)
# {'name': [None, u'Some article']}

Relaciones de versión

Cada objeto de versión refleja todas las relaciones de los objetos padre. Puedes pensar en las relaciones de los objetos de versión como 'relaciones del objeto padre en un punto dado en el tiempo'.

Digamos que tienes dos modelos: Article y Category. Cada Article tiene una Category. En el siguiente ejemplo, primero agregamos objetos de artículo y categoría a la base de datos.

Continuum guarda nuevos registros de ArticleVersion y CategoryVersion en segundo plano. Después de eso, actualizamos la entidad de artículo creada para usar otra categoría. Continuum crea nuevos objetos de versión en consecuencia.

Por último, comprobamos las relaciones de categoría de diferentes versiones de artículo.

category = Category(name=u'Some category')
article = Article(
    name=u'Some article',
    category=category
)
session.add(article)
session.commit()
article.category = Category(name=u'Some other category')
session.commit()
article.versions[0].category.name  # u'Some category'
article.versions[1].category.name  # u'Some other category'

La lógica de cómo SQLAlchemy-Continuum construye estas relaciones se encuentra dentro de la clase RelationshipBuilder.

Relaciones con clases no versionadas

Tomemos el ejemplo anterior de Artículos y Categorías. Ahora consideremos que solo el modelo Artículo está versionado:

clase Artículo(Base):
    __tablename__ = 'articulo'
    __versioned__ = {}
    id = sa.Column(sa.Integer, autoincrement=True, primary_key=True)
    nombre = sa.Column(sa.Unicode(255), nullable=False)
clase Categoría(Base):
    __tablename__ = 'etiqueta'
    id = sa.Column(sa.Integer, autoincrement=True, primary_key=True)
    nombre = sa.Column(sa.Unicode(255))
    article_id = sa.Column(sa.Integer, sa.ForeignKey(Artículo.id))
    articulo = sa.orm.relationship(
        Artículo,
        backref=sa.orm.backref('categorías')
    )

Aquí las versiones de Artículo seguirán reflejando las relaciones del modelo Artículo pero simplemente devolverán objetos Categoría en lugar de objetos CategoríaVersion:

categoría = Categoría(nombre=u'Alguna categoría')
articulo = Artículo(
    nombre=u'Algún artículo',
    categoría=categoría
)
session.add(articulo)
session.commit()
articulo.categoría = Categoría(nombre=u'Alguna otra categoría')
session.commit()
version = articulo.versiones[0]
version.categoría.nombre                   # u'Alguna otra categoría'
isinstance(version.categoría, Categoría)  # True

Relaciones dinámicas

Si la clase padre tiene una relación dinámica, se reflejará como una propiedad que devuelve una consulta en la clase de versión asociada.

clase Artículo(Base):
    __tablename__ = 'articulo'
    __versioned__ = {}
    id = sa.Column(sa.Integer, autoincrement=True, primary_key=True)
    nombre = sa.Column(sa.Unicode(255), nullable=False)
clase Etiqueta(Base):
    __tablename__ = 'etiqueta'
    __versioned__ = {}
    id = sa.Column(sa.Integer, autoincrement=True, primary_key=True)
    nombre = sa.Column(sa.Unicode(255))
    article_id = sa.Column(sa.Integer, sa.ForeignKey(Artículo.id))
    articulo = sa.orm.relationship(
        Artículo,
        backref=sa.orm.backref(
            'etiquetas',
            lazy='dynamic'
        )
    )
articulo = Artículo()
articulo.nombre = u'Algún artículo'
articulo.contenido = u'Algún contenido'
session.add(articulo)
session.commit()
consulta_etiqueta = articulo.versiones[0].etiquetas
consulta_etiqueta.all()  # devuelve todas las etiquetas para la versión dada
consulta_etiqueta.count()  # devuelve el recuento de etiquetas para la versión dada

REVERSIÓN DE CAMBIOS

Uno de los principales beneficios de SQLAlchemy-Continuum es su capacidad para revertir cambios.

Revertir actualización

articulo = Artículo(nombre=u'Nuevo artículo', contenido=u'Algún contenido')
session.add(articulo)
session.commit(articulo)
version = articulo.versiones[0]
articulo.nombre = u'Artículo actualizado'
session.commit()
version.revertir()
session.commit()
articulo.nombre
# u'Nuevo artículo'

Revertir eliminación

articulo = Artículo(nombre=u'Nuevo artículo', contenido=u'Algún contenido')
session.add(articulo)
session.commit(articulo)
version = articulo.versiones[0]
session.delete(articulo)
session.commit()
version.revertir()
session.commit()
# ¡el artículo vive de nuevo!
session.query(Artículo).first()

Revertir relaciones

A veces, puedes tener casos en los que deseas revertir un objeto, así como algunas de sus relaciones, a un estado determinado. Considere la siguiente definición de modelo:

clase Artículo(Base):
    __tablename__ = 'articulo'
    __versioned__ = {}
    id = sa.Column(sa.Integer, autoincrement=True, primary_key=True)
    nombre = sa.Column(sa.Unicode(255))
clase Etiqueta(Base):
    __tablename__ = 'etiqueta'
    __versioned__ = {}
    id = sa.Column(sa.Integer, autoincrement=True, primary_key=True)
    nombre = sa.Column(sa.Unicode(255))
    article_id = sa.Column(sa.Integer, sa.ForeignKey(Artículo.id))
    articulo = sa.orm.relationship(Artículo, backref='etiquetas')

Ahora, supongamos que un usuario primero agrega un artículo con un par de etiquetas:

articulo = Artículo(
    nombre=u'Algún artículo',
    etiquetas=[Etiqueta(u'Bueno'), Etiqueta(u'Interesante')]
)
session.add(articulo)
session.commit()

Luego, supongamos que otro usuario elimina una de las etiquetas:

etiqueta = session.query(Etiqueta).filter_by(nombre=u'Interesante')
session.delete(etiqueta)
session.commit()

Ahora el primer usuario quiere devolver el artículo a su estado original. Esto se puede lograr de la siguiente manera (tenga en cuenta cómo utilizamos el parámetro `relations`):

articulo = session.get(Artículo, 1)
articulo.versiones[0].revertir(relations=['etiquetas'])
session.commit()

CONSULTAS

Puede consultar modelos de historial como cualquier otro modelo declarativo de SQLAlchemy.

from sqlalchemy_continuum import version_class
ArtículoVersion = version_class(Artículo)
session.query(ArtículoVersion).filter_by(nombre=u'algún nombre').all()

¿Cuántas transacciones se han ejecutado?

from sqlalchemy_continuum import transaction_class
Transacción = transaction_class(Artículo)
Transacción.query.count()

Consultar entidades de una clase en una revisión dada

En el siguiente ejemplo, encontramos todos los artículos que se vieron afectados por la transacción 33.

session.query(ArtículoVersion).filter_by(transaction_id=33)

Consultar transacciones, en las que cambiaron entidades de una clase dada

En este ejemplo, encontramos todas las transacciones que afectaron a cualquier instancia del modelo 'Artículo'. Esta consulta necesita el plugin `TransactionChangesPlugin`.

CambiosTransacción = Artículo.__versioned__['cambios_transaccion']
entradas = (
    session.query(Transacción)
    .innerjoin(Transacción.cambios)
    .filter(
        CambiosTransacción.entity_name.in_(['Artículo'])
    )
)

Consultar versiones de entidad que modificaron una propiedad dada

En el siguiente ejemplo, queremos encontrar todas las versiones de la clase Artículo que cambiaron el atributo 'nombre'. Este ejemplo asume que está utilizando `PropertyModTrackerPlugin`.

ArtículoVersion = version_class(Artículo)
session.query(HistorialArtículo).filter(ArtículoVersion.nombre_mod).all()

TRANSACCIONES

Transacción

Por cada transacción confirmada, SQLAlchemy-Continuum crea un nuevo registro de Transacción.

La Transacción se puede consultar como cualquier otro modelo declarativo de SQLAlchemy.

from sqlalchemy_continuum import transaction_class
Transacción = transaction_class(Artículo)
# encontrar todas las transacciones
session.query(Transacción).all()

Unidad de Trabajo

Por cada conexión a la base de datos, SQLAlchemy-Continuum crea un objeto interno `UnitOfWork`. Normalmente, estos objetos se crean en la fase `before_flush` del flujo de trabajo de la sesión. Sin embargo, también puede forzar la creación de una unidad de trabajo antes de esta fase.

uow = versioning_manager.unit_of_work(session)

Los objetos de transacción se crean normalmente durante la fase `before_flush`. Si necesita acceder al objeto de transacción antes de que comience la fase `flush`, puede hacerlo llamando al método `create_transaction` de la clase `UnitOfWork`.

transacción = uow.create_transaction(session)

Los objetos de versión se crean normalmente durante la fase `after_flush`, pero también puede forzar la creación de estos en cualquier momento llamando al método `make_versions`.

uow.make_versions(session)

Internos del flujo de trabajo

Considere el siguiente fragmento de código donde creamos un nuevo artículo.

articulo = Artículo()
articulo.nombre = u'Algún artículo'
articulo.contenido = u'Algún contenido'
session.add(articulo)
session.commit()

Esto ejecutaría las siguientes consultas SQL (en PostgreSQL)

1.
INSERT INTO article (name, content) VALUES (?, ?)
params: ('Algún artículo', 'Algún contenido')
2.
INSERT INTO transaction (issued_at) VALUES (?)
params: (datetime.utcnow())
3.
INSERT INTO article_version (id, name, content, transaction_id) VALUES (?, ?, ?, ?)
params: (<id del artículo de la consulta 1>, 'Algún artículo', 'Algún contenido', <id de la transacción de la consulta 2>)

VERSIONADO NATIVO

Desde la versión 1.1, SQLAlchemy-Continuum admite el versionado nativo para el dialecto de PostgreSQL. El versionado nativo crea disparadores SQL para todos los modelos versionados. Estos disparadores rastrean los cambios realizados en los modelos versionados. En comparación con el versionado basado en objetos, el versionado nativo tiene

>
  • Mucho más rápido que la versión basada en objetos normal
  • Mínima huella de memoria cuando se usa junto con las opciones de configuración create_tables=False y create_models=False.
  • Migraciones de base de datos más engorrosas, ya que los disparadores también deben actualizarse.

Uso

Para habilitar la versión nativa, debes establecer la opción de configuración native_versioning como True.

make_versioned(options={'native_versioning': True})

Migraciones de esquema

Al realizar migraciones de esquema (por ejemplo, agregar nuevas columnas a las tablas de versiones), debes recordar llamar a sync_trigger para mantener el disparador de versión actualizado.

from sqlalchemy_continuum.dialects.postgresql import sync_trigger
sync_trigger(conn, 'article_version')

Si no utilizas PropertyModTrackerPlugin, entonces tienes que deshabilitarlo:

sync_trigger(conn, 'article_version', use_property_mod_tracking=False)

PLUGINS

Uso de plugins

from sqlalchemy_continuum.plugins import PropertyModTrackerPlugin
versioning_manager.plugins.append(PropertyModTrackerPlugin())
versioning_manager.plugins  # <PluginCollection [...]>
# También puedes eliminar un plugin
del versioning_manager.plugins[0]

Actividad

El ActivityPlugin es el plugin más potente para rastrear cambios en entidades individuales. Si utilizas ActivityPlugin, probablemente no necesitarás usar los plugins TransactionChanges ni TransactionMeta.

Puedes inicializar el ActivityPlugin agregándolo al gestor de versiones.

Columna Tipo Descripción
id BigInteger La clave primaria de la actividad
verb Unicode El verbo define la acción de la actividad
data JSON Datos adicionales para la actividad en formato JSON
transaction_id BigInteger La transacción con la que se asoció esta actividad
object_id BigInteger La clave primaria del objeto. El objeto puede ser cualquier entidad que tenga un entero como clave primaria.
object_type Unicode El tipo del objeto (nombre de la clase como cadena)
object_tx_id BigInteger El último transaction_id asociado con el objeto. Esto se usa para recuperar eficientemente la versión del objeto asociada con esta actividad.
target_id BigInteger La clave primaria del objetivo. El objetivo puede ser cualquier entidad que tenga un entero como clave primaria.
target_type Unicode El tipo del objetivo (nombre de la clase como cadena)
target_tx_id BigInteger El último transaction_id asociado con el objetivo.

Limitaciones

Actualmente, todos los cambios en los modelos padre deben ser confirmados (flushed) o validados (committed) antes de crear actividades. Esto se debe a que todavía no existen procesadores de dependencia para las relaciones genéricas. Por lo tanto, cuando crees actividades y les asignes objetos / objetivos, recuerda confirmar la sesión antes de crear una actividad:

article = Article(name=u'Un artículo')
session.add(article)
session.flush()  # <- ¡IMPORTANTE!
first_activity = Activity(verb=u'create', object=article)
session.add(first_activity)
session.commit()

Los objetivos y objetos de una actividad dada deben tener una columna de clave primaria entera llamada id.

Crear actividades

Una vez que tus modelos han sido configurados, puedes obtener el modelo de Actividad de la clase ActivityPlugin con la propiedad activity_cls:

Activity = activity_plugin.activity_cls

Ahora, supongamos que tenemos un modelo llamado Article y otro llamado Category. Cada Artículo tiene una Categoría. Las actividades deben crearse junto con los cambios que realices en estos modelos.

article = Article(name=u'Un artículo')
session.add(article)
session.flush()
first_activity = Activity(verb=u'create', object=article)
session.add(first_activity)
session.commit()

La transacción actual se asigna automáticamente al objeto de actividad:

first_activity.transaction  # Objeto Transaction

Actualizar actividades

La propiedad object del objeto Activity contiene el objeto actual y object_version contiene la versión del objeto en el momento en que se creó la actividad.

article.name = u'¡Un artículo actualizado!'
session.flush()
second_activity = Activity(verb=u'update', object=article)
session.add(second_activity)
session.commit()
second_activity.object.name  # u'¡Un artículo actualizado!'
first_activity.object.name  # u'¡Un artículo actualizado!'
first_activity.object_version.name  # u'Un artículo'

Eliminar actividades

Las propiedades de versión son especialmente útiles para las actividades de eliminación. Una vez que la actividad se recupera de la base de datos, el objeto ya no está disponible (ya que ha sido eliminado), por lo tanto, la única forma en que podríamos mostrar alguna información sobre el objeto que el usuario eliminó es accediendo a la propiedad object_version.

session.delete(article)
session.flush()
third_activity = Activity(verb=u'delete', object=article)
session.add(third_activity)
session.commit()
third_activity.object_version.name  # u'¡Un artículo actualizado!'

Historiales de versiones locales usando objetivos

La propiedad target del modelo Activity ofrece una forma de rastrear los cambios de un objeto relacionado dado. En el siguiente ejemplo, creamos una nueva actividad al agregar una categoría para un artículo y luego marcamos el artículo como el objetivo de esta actividad.

session.add(Category(name=u'Primera categoría', article=article))
session.flush()
activity = Activity(
    verb=u'create',
    object=category,
    target=article
)
session.add(activity)
session.commit()

Ahora, si quisiéramos encontrar todos los cambios que afectaron a un artículo dado, podríamos hacerlo buscando en todas las actividades donde el objeto o el objetivo sea el artículo dado.

import sqlalchemy as sa
activities = session.query(Activity).filter(
    sa.or_(
        Activity.object == article,
        Activity.target == article
    )
)

Flask

FlaskPlugin ofrece una forma de integrar el framework Flask con SQLAlchemy-Continuum. Flask-Plugin agrega dos columnas al modelo Transaction, a saber, user_id y remote_addr.

Estas columnas se rellenan automáticamente cuando se crea el objeto transaction. La columna remote_addr se rellena con el valor de la dirección remota que realizó la solicitud actual. La columna user_id se rellena con el id del objeto current_user.

from sqlalchemy_continuum.plugins import FlaskPlugin
from sqlalchemy_continuum import make_versioned
make_versioned(plugins=[FlaskPlugin()])

PropertyModTracker

El PropertyModTrackerPlugin ofrece una forma de rastrear eficientemente modificaciones de propiedades individuales. Con PropertyModTrackerPlugin puedes realizar consultas eficientes como:

="Pp">Busca todas las versiones del modelo X donde el usuario actualizó la propiedad A o la propiedad B.

Busca todas las versiones del modelo X donde el usuario no actualizó la propiedad A.

PropertyModTrackerPlugin agrega una columna de seguimiento de modificaciones separada para cada columna versionada. Por ejemplo, si tienes un modelo versionado llamado Article con columnas name y content, este plugin agregaría dos columnas booleanas adicionales name_mod y content_mod para el modelo de versión. Cuando el usuario confirma transacciones, el plugin actualiza automáticamente estas columnas booleanas.

TransactionChanges

TransactionChanges proporciona una forma eficiente de rastrear qué modelos declarativos se modificaron en una transacción determinada. Esto puede ser útil cuando se necesitan consultar transacciones posteriormente para problemas como:

1.
Busca todas las transacciones que afectaron el modelo User.
2.
Busca todas las transacciones que no afectaron los modelos Entity y Event.

El plugin funciona de dos maneras. Durante la fase de instrumentación de la clase, este plugin crea un modelo de transacción especial llamado TransactionChanges. Este modelo está asociado a una tabla llamada transaction_changes, que tiene solo dos campos: transaction_id y entity_name. Si, por ejemplo, una transacción consistió en guardar 5 nuevas entidades de User y 1 entidad de Article, se insertarían dos nuevas filas en la tabla transaction_changes.

transaction_id entity_name
233678 User
233678 Article

TransactionMeta

TransactionMetaPlugin ofrece una forma de guardar datos clave-valor para transacciones. Puedes usar el plugin de la misma manera que otros plugins:

meta_plugin = TransactionMetaPlugin()
versioning_manager.plugins.append(meta_plugin)

TransactionMetaPlugin crea un modelo simple llamado TransactionMeta. Esta clase tiene tres columnas: transaction_id, key y value. TransactionMeta plugin también crea un proxy de asociación entre TransactionMeta y las clases Transaction para un fácil acceso basado en diccionario de pares clave-valor.

Puedes fácilmente 'etiquetar' transacciones con ciertos pares clave-valor dando estas claves y valores a la propiedad meta de la clase Transaction.

from sqlalchemy_continuum import versioning_manager
article = Article()
session.add(article)
uow = versioning_manager.unit_of_work(session)
tx = uow.create_transaction(session)
tx.meta = {u'some_key': u'some value'}
session.commit()
TransactionMeta = meta_plugin.model_class
Transaction = versioning_manager.transaction_cls
# encuentra todas las transacciones con etiquetas 'article'
query = (
    session.query(Transaction)
    .join(Transaction.meta_relation)
    .filter(
        db.and_(
            TransactionMeta.key == 'some_key',
            TransactionMeta.value == 'some value'
        )
    )
)

CONFIGURACIÓN

Configuración global y a nivel de clase

Todos los parámetros de configuración de Continuum se pueden establecer a nivel global (nivel de gestor) y a nivel de clase. Establecer una opción a nivel de gestor afecta a todas las clases dentro del ámbito del listener de instrumentación de clase del gestor (por defecto, todos los modelos declarativos de SQLAlchemy).

En el siguiente ejemplo, establecemos la opción de configuración 'transaction_column_name' en False a nivel de gestor.

make_versioned(options={'transaction_column_name': 'my_tx_id'})

Como su nombre indica, la configuración a nivel de clase solo se aplica a la clase dada. La configuración a nivel de clase se puede pasar al atributo de clase __versioned__.

class User(Base):
    __versioned__ = {

Estrategias de versionado

Similar a Hibernate Envers, SQLAlchemy-Continuum ofrece dos estrategias de versionado distintas: 'validity' y 'subquery'. La estrategia predeterminada es 'validity'.

Validity

La estrategia 'validity' guarda dos columnas en cada tabla de historial, específicamente 'transaction_id' y 'end_transaction_id'. Los nombres de estas columnas se pueden configurar con las opciones de configuración transaction_column_name y end_transaction_column_name.

Al igual que con la estrategia 'subquery', por cada entidad insertada, actualizada y eliminada, Continuum crea una nueva versión en la tabla de historial. Sin embargo, también actualiza el end_transaction_id de la versión anterior para apuntar a la versión actual. Esto crea una pequeña sobrecarga durante la manipulación de datos.

Con la estrategia 'validity', la traversa de versiones es muy rápida. Al acceder a una versión anterior, Continuum intenta encontrar el registro de versión donde las claves primarias coinciden y el end_transaction_id es el mismo que el transaction_id del registro de versión dado. Al acceder a la siguiente versión, Continuum intenta encontrar el registro de versión donde las claves primarias coinciden y el transaction_id es el mismo que el end_transaction_id del registro de versión dado.

Pros:
•
La traversa de versiones es mucho más rápida ya que no se necesitan subconsultas correlacionadas
Contras:
•
Las actualizaciones, inserciones y eliminaciones son un poco más lentas

Subquery

La estrategia 'subquery' utiliza una columna en cada tabla de historial, específicamente 'transaction_id'. El nombre de esta columna se puede configurar con la opción de configuración transaction_column_name.

Después de cada entidad insertada, actualizada y eliminada, Continuum crea una nueva versión en la tabla de historial y establece la columna 'transaction_id' para que apunte a la transacción actual.

Con la estrategia 'subquery', la traversa de versiones es lenta. Al acceder a versiones anteriores y siguientes de un objeto de versión dado, se necesitan subconsultas correlacionadas.

Pros:
•
Las actualizaciones, inserciones y eliminaciones son un poco más rápidas que en la estrategia 'validity'
Contras:
•
La traversa de versiones es mucho más lenta

Exclusión e inclusión de columnas

Con la opción de configuración exclude, puedes definir qué atributos de entidad quieres versionar. Por defecto, Continuum versiona todos los atributos de la entidad.

class User(Base):
    __versioned__ = {
        'exclude': ['picture']
    }
    id = sa.Column(sa.Integer, primary_key=True)
    name = sa.Column(sa.Unicode(255))
    picture = sa.Column(sa.LargeBinary)

make_versioned

En la mayoría de los casos, todo lo que necesita hacer es llamar a la función make_versioned. Esto se debe hacer *antes* de que la base de datos se configure, es decir, antes de que se llame a SQLAlchemy.configure().

make_versioned(user_cls='my_app.models.MyUser')

Si desea que las transacciones contengan referencias a usuarios, puede especificar la clase de usuario que su aplicación utiliza. De forma predeterminada, SQLAlchemy-Continuum buscará una clase de usuario llamada 'User' en el módulo raíz de su aplicación.

La clase de usuario se almacena en el objeto VersioningManager y se puede acceder a ella más tarde a través de versioning_manager.user_cls. El campo de usuario en la tabla de versiones se llamará por defecto 'user' (siempre que la clase de usuario no sea None).

Si no desea que las transacciones contengan ninguna referencia de usuario, también puede deshabilitar esta función.

make_versioned(user_cls=None)

Personalización de los mappers versionados

Por defecto, SQLAlchemy-Continuum versiona todos los mappers. Puede anular este comportamiento pasando la clase/objeto mapper deseado a la función make_versioned.

make_versioned(mapper=my_mapper)

Personalización de las sesiones versionadas

Por defecto, SQLAlchemy-Continuum versiona todas las sesiones. Puede anular este comportamiento pasando la clase/objeto de sesión deseado a la función make_versioned.

make_versioned(session=my_session)

ESQUEMA DE CONTINUUM

Tablas de versiones

Por defecto, SQLAlchemy-Continuum crea una tabla de versión para cada tabla de entidad versionada. Las tablas de versión se sufijan con '_version'. Así, por ejemplo, si tiene dos tablas versionadas 'article' y 'category', SQLAlchemy-Continuum crearía dos tablas de versión 'article_version' y 'category_version'.

Por defecto, las tablas de versión contienen estas columnas:

  • id de la entidad original (puede haber más de una columna en el caso de claves primarias compuestas)
  • transaction_id - un entero que coincide con el número de id en la tabla transaction_log.
  • end_transaction_id - un entero que coincide con el transaction_id del siguiente registro de versión. Si este es el registro de versión actual, este campo es nulo.
  • operation_type - un entero pequeño que define el tipo de la operación
  • campos versionados de la entidad original

Si está utilizando PropertyModTracker, Continuum también crea un campo booleano por cada campo versionado. Por defecto, estos campos booleanos se sufijan con '_mod'.

La clave primaria de cada tabla de versión es la combinación de la clave primaria de la tabla padre + el transaction_id. Esto significa que puede haber como máximo una entrada en la tabla de versiones para una instancia de entidad dada en una transacción dada.

Tablas de transacciones

Por defecto, Continuum crea una tabla de transacciones llamada transaction. Muchos plugins de continuum también crean tablas adicionales para el almacenamiento eficiente de transacciones. Si desea consultar transacciones de manera eficiente después, debería considerar utilizar algunos de estos plugins.

La tabla de transacciones solo contiene dos campos por defecto: id y issued_at.

MIGRACIONES DE ALEMBIC

Cada vez que realice cambios en la estructura de la base de datos, también debe cambiar las tablas de historial asociadas. Cuando realice cambios en sus modelos, SQLAlchemy-Continuum modifica automáticamente las definiciones de modelos de historial, por lo tanto, puede usar alembic revision --autogenerate al igual que antes. Solo necesita asegurarse de que la función make_versioned se llame antes de que alembic recopile todos sus modelos y que configure_mappers se llame después.

Preste mucha atención al eliminar o mover datos de tablas padre y al reflejar estos cambios en las tablas de historial.

Solución de problemas

Si alembic no detectó ningún cambio o genera una migración invertida (intenta eliminar tablas *_version de la base de datos en lugar de crearlas), asegúrese de que el comando de alembic llamó a configure_mappers.

Para cada elemento del lado 'muchos', devuelve su última versión siempre que la transacción de esa versión sea menor o igual a la transacción de obj.

Ejemplo

Usando la relación Artículo-Etiquetas, donde buscamos etiquetas de article_version con id = 3 y transaction = 5, el sql producido es

SELECT tags_version.* FROM tags_version WHERE tags_version.article_id = 3 AND tags_version.operation_type != 2 AND EXISTS (

SELECT 1 FROM tags_version as tags_version_last WHERE tags_version_last.transaction_id <= 5 AND tags_version_last.id = tags_version.id GROUP BY tags_version_last.id HAVING
MAX(tags_version_last.transaction_id) = tags_version.transaction_id

)
