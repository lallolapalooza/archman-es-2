SQLHIST(1) Manual de libtracefs SQLHIST(1)

NOMBRE

sqlhist - Herramienta que utiliza el lenguaje SQL para crear / mostrar la creación de histogramas de tracefs y eventos sintéticos.

SINOPSIS

sqlhist [OPCIONES] [COMANDO-SELECT-SQL]

DESCRIPCIÓN

sqlhist(1) tomará una declaración similar a SQL para crear histogramas de tracefs y eventos sintéticos que pueden realizar diversas acciones para el manejo de datos.

El sistema de archivos tracefs interactúa con la infraestructura de rastreo de Linux que tiene varios eventos dinámicos y estáticos en todo el kernel. Cada uno de estos eventos puede tener un "histograma" adjunto, donde los campos del evento definirán los cubos del histograma.

Un evento sintético es una forma de adjuntar dos eventos separados y utilizar los campos y las marcas de tiempo de esos eventos para crear un nuevo evento dinámico. Este nuevo evento dinámico se llama evento sintético. Los campos de cada evento pueden realizar cálculos simples, donde, por ejemplo, se puede tomar la diferencia entre un campo de un evento y un campo del otro. Esto también funciona para las marcas de tiempo de los eventos, donde la diferencia de tiempo entre los dos eventos también se puede extraer y colocar en el evento sintético.

Otras acciones se pueden realizar a partir de los campos de los eventos. Se puede tomar una instantánea del búfer de anillo del kernel cuando una variable utilizada en el evento sintético que crea aciertos alcanza un máximo, o simplemente cambia.

Los comandos para crear histogramas y eventos sintéticos son complejos y no fáciles de recordar. sqlhist se utiliza para convertir la sintaxis SQL en los comandos necesarios para crear el histograma o el evento sintético.

El COMANDO-SELECT-SQL es una cadena SQL definida por tracefs_sql(3).

Tenga en cuenta que esto debe ejecutarse como root (o con sudo), ya que interactuar con el directorio tracefs requiere privilegios de root, a menos que se proporcione la opción -t con una copia del directorio tracefs y sus eventos.

sqlhist es un programa simple cuyo código existe en la página del manual de tracefs_sql(3).

OPCIONES

-n nombre

El nombre del evento sintético a crear. Este evento puede ser utilizado como cualquier otro evento y habilitado a través de trace-cmd(1).

-t directorio-tracefs

Para probar esto como usuario no root, se puede usar una copia del directorio tracefs, y pasar ese directorio con esta opción permitirá que el programa funcione. Obviamente, -e no funcionará como no root porque no podrá ejecutarse. 
# mkdir /tmp/tracing
# cp -r /sys/kernel/tracing/events /tmp/tracing
# exit
$ ./sqlhist -t /tmp/tracing ...

-e

No solo muestre los comandos para crear el histograma, sino que también ejecútelos. Esto requiere privilegios de root.

-f archivo

En lugar de leer los comandos SQL desde la línea de comandos, léalos desde archivo. Si archivo es -, léalo de la entrada estándar.

-m var

Realice la acción dada cuando la variable var alcance un nuevo máximo. Esto no se puede usar con -c.

-c var

Realice la acción dada cuando la variable var cambie su valor. Esto no se puede usar con -m.

-s

Realice una instantánea en lugar de llamar al evento sintético.

-T

Realice tanto una instantánea como un rastreo del evento sintético.

-S campos[,campos]

Guarde los campos dados. Los campos deben ser campos del evento "final" dado en el COMANDO-SELECT-SQL

-B instancia

Para declaraciones simples que solo producen un histograma, la instancia dada aquí será donde se creará el histograma. Esto se ignora para la creación completa de eventos sintéticos, ya que los eventos sintéticos tienen un efecto global en todas las instancias de rastreo, mientras que los histogramas solo afectan a una instancia.

EJEMPLOS

Crear el ejecutable sqlhist:

   man tracefs_sql | sed -ne '/^EXAMPLE/,/FILES/ { /EXAMPLE/d ; /FILES/d ; p}' > sqlhist.c
   gcc -o sqlhist sqlhist.c `pkg-config --cflags --libs libtracefs`

Como se describe anteriormente, para fines de prueba, haga una copia del directorio de eventos:

   $ mkdir /tmp/tracing
   $ sudo cp -r /sys/kernel/tracing/events /tmp/tracing/
   $ sudo chmod -R 0644 /tmp/tracing/

Para un ejemplo de salida simple de histograma utilizando la copia del directorio tracefs.

   $ ./sqlhist -t /tmp/tracing/ 'SELECT CAST(call_site as SYM-OFFSET), bytes_req, CAST(bytes_alloc AS _COUNTER_) FROM kmalloc'

Produce la salida:

   echo 'hist:keys=call_site.sym-offset,bytes_req:vals=bytes_alloc' > /sys/kernel/tracing/events/kmem/kmalloc/trigger

Aquí se explican las opciones de sqlhist:

-n wakeup_lat

Nombra el evento sintético para usar wakeup_lat.

-e

Ejecuta los comandos que se imprimen.

-T

Realiza una acción de traza y luego una acción de instantánea (intercambia el búfer al búfer estático snapshot).

-m lat

Dispara las acciones cada vez que lat alcanza un nuevo valor máximo.

Ahora un desglose de la declaración SQL:

 'SELECT end.next_comm AS comm, (end.TIMESTAMP_USECS - start.TIMESTAMP_USECS) AS lat FROM ' \
    'sched_waking AS start JOIN sched_switch AS end ON start.pid = end.next_pid WHERE end.next_prio < 100 && end.next_comm == "cyclictest"'

end.next_comm AS comm

Guarda el campo next_comm de sched_switch y lo coloca en el campo comm del evento sintético wakeup_lat.

(end.TIMESTAMP_USECS - start.TIMESTAMP_USECS) AS lat

Toma la diferencia de las marcas de tiempo del evento sched_switch y del evento sched_waking. Como las marcas de tiempo suelen registrarse en nanosegundos, TIMESTAMP daría la marca de tiempo completa en nanosegundos, pero aquí, TIMESTAMP_USECS la truncará a microsegundos. El valor se guarda en la variable lat, que también se registrará en el evento sintético.

FROM sched_waking AS start JOIN sched_switch AS end ON start.pid = end.next_pid

Crea el evento sintético uniendo sched_waking con sched_switch, haciendo coincidir el campo pid de sched_waking con el campo next_pid de sched_switch. También se hace de start un alias para sched_waking y de end un alias para sched_switch, que luego se usan como sustitutos de sched_waking y sched_switch respectivamente en el resto de la declaración SQL.

WHERE end.next_prio < 100 && end.next_comm == "cyclictest"

Filtra la lógica para que se ejecute solo si el campo next_prio de sched_waking es menor que 100. (Nota, en el Kernel, las prioridades son inversas, y las prioridades en tiempo real se representan de 0 a 100, donde 0 es la prioridad más alta). También solo rastrea cuando el next_comm (la tarea que entra en planificación) del evento sched_switch tiene el nombre "cyclictest".

Para el comando trace-cmd(3):

   trace-cmd start -e all -e wakeup_lat -R stacktrace

trace-cmd start

Habilita el rastreo (no graba en un archivo).

-e all

Habilita todos los eventos

-e wakeup_lat -R stacktrace

Hace que el evento "wakeup_lat" (nuestro evento sintético) habilite el disparador stacktrace, donde por cada instancia del evento "wakeup_lat", se registrará un rastreo de pila del kernel en el búfer de anillo.

Después de llamar a cyclictest (una herramienta de tiempo real para medir la latencia de activación), lee el búfer de instantánea.

trace-cmd show -s

trace-cmd show lee el búfer de anillo del kernel, y la opción -s leerá el búfer de snapshot en lugar del normal.
 <idle>-0       [002] d..4 23454.902256: wakeup_lat: next_comm=cyclictest lat=17
Vemos que el evento "wakeup_lat" ocurrió en la CPU 2, con una latencia de activación de 17 microsegundos.

BUGS
