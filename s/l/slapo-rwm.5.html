NOMBRE

slapo-rwm - overlay de reescritura/remapeo para slapd

SINOPSIS

/etc/openldap/slapd.conf

DESCRIPCIÓN

El overlay rwm para slapd(8) realiza reescrituras básicas de DN/datos y mapeo de objectClass/attributeType. Su uso está mayormente destinado a proporcionar vistas virtuales de datos existentes, ya sea remotamente, en conjunción con el backend proxy descrito en slapd-ldap(5), o localmente, en conjunción con el backend relay descrito en slapd-relay(5).

Este overlay es experimental.

MAPEADO

Una característica importante del overlay rwm es la capacidad de mapear objectClasses y attributeTypes del conjunto local (o un subconjunto del mismo) a un conjunto extranjero, y viceversa. Esto se logra mediante la directiva rwm-map.

rwm-map {atributo | objectclass} [<nombre local> | *] {<nombre extranjero> | *}
Mapea attributeTypes y objectClasses del servidor extranjero a valores diferentes en el slapd local. La razón es que algunos atributos podrían no formar parte del esquema del slapd local, algunos nombres de atributos podrían ser diferentes pero cumplir el mismo propósito, etc. Si el nombre local o extranjero es `*', el nombre se preserva. Si el nombre local se omite, el nombre extranjero se elimina. Los nombres no mapeados se preservan si tanto el nombre local como el extranjero son `*', y se eliminan si el nombre local se omite y el nombre extranjero es `*'.

Los objectClasses y attributeTypes locales deben definirse en el esquema local; los extranjeros no tienen por qué hacerlo, pero se anima a los usuarios a definir explícitamente los attributeTypes remotos y los objectClasses que pretenden mapear. En general, al remapear un servidor remoto a través de back-ldap (slapd-ldap(5)) o back-meta (slapd-meta(5)) su definición puede obtenerse fácilmente consultando el subschemaSubentry del servidor remoto; el problema no debería existir al remapear una base de datos local. Sin embargo, nótese que la decisión de reescribir o no attributeTypes con sintaxis distinguishedName, requiere el conocimiento de la sintaxis del attributeType. Véase la sección REWRITING para más detalles.

Nótese que al mapear atributos con valor DN de local a extranjero, primero se reescribe el DN y luego se mapea el attributeType; mientras que al mapear de extranjero a local, primero se mapea el attributeType y luego se reescribe el DN. Por lo tanto, es importante que el attributeType local esté apropiadamente definido como que utiliza la sintaxis distinguishedName. Además, nótese que hay sintaxis relacionadas con DN (es decir, tipos compuestos con una porción con valor DN), como nameAndOptionalUID, cuyos valores actualmente no se reescriben.

Si el tipo extranjero de un mapeo de atributo no está definido en el servidor local, podría ser deseable que los valores de los atributos se normalicen después del proceso de mapeo. No normalizar los valores puede conducir a resultados incorrectos, cuando el overlay rwm se utiliza junto con, por ejemplo, el overlay pcache. Esta normalización puede habilitarse mediante la directiva rwm-normalize-mapped-attrs.

rwm-normalize-mapped-attrs {sí|no}
Establezca esto en "sí" si el overlay rwm debe intentar normalizar los valores de los atributos que se mapean desde un tipo de atributo desconocido para el servidor local. El valor por defecto de esta configuración es "no".
rwm-drop-unrequested-attrs {sí|no}
Establezca esto en "sí" si el overlay rwm debe eliminar los atributos que no son solicitados explícitamente por una operación de búsqueda. Cuando esto se establece en "no", el overlay rwm dejará todos los atributos en su lugar, para que los módulos posteriores puedan manipularlos. En cualquier caso, los atributos no solicitados serán omitidos de los resultados de búsqueda por el frontend, cuando se codifique el paquete de respuesta de entrada de búsqueda. El valor por defecto de esta configuración es "sí".

MANIPULACIÓN DE SUFIJOS

Una característica básica del overlay rwm es la capacidad de realizar manipulación de sufijos entre un contexto de nombres virtual y uno real mediante la directiva rwm-suffixmassage. Esto, en conjunción con los backends proxy, slapd-ldap(5) y slapd-meta(5), o con el backend relay, slapd-relay(5), permite crear vistas virtuales de bases de datos. Una característica distintiva de este overlay es que, cuando se instancia antes que cualquier base de datos, puede modificar el DN de las solicitudes *antes* de la selección de la base de datos. Por esta razón, las reglas que reescriben el DN vacío ("") o el DN subschemaSubentry (normalmente "cn=subschema"), impedirían a los clientes leer el DSE raíz o el esquema del DSA.

rwm-suffixmassage [<contexto de nombres virtual>] <contexto de nombres real>
Atajo para implementar la reescritura de contextos de nombres; la parte final del DN se reescribe del contexto de nombres virtual al real en los contextos de reescritura bindDN, searchDN, searchFilterAttrDN, compareDN, compareAttrDN, addDN, addAttrDN, modifyDN, modifyAttrDN, modrDN, newSuperiorDN, deleteDN, exopPasswdDN, y del contexto de nombres real al virtual en los contextos de reescritura searchEntryDN, searchAttrDN y matchedDN. Por defecto, no se produce reescritura para el searchFilter ni para los contextos de reescritura referralAttrDN y referralDN. Si no se proporciona un <contexto de nombres virtual>, se utiliza el primer sufijo de la base de datos; esto requiere que la directiva rwm-suffixmassage se defina *después* de la directiva suffix de la base de datos. La directiva rwm-suffixmassage activa automáticamente el rwm-rewriteEngine a ON.

Véase la sección REWRITING para más detalles.

REESCRITURA

Una cadena se reescribe de acuerdo con un conjunto de reglas, llamado `contexto de reescritura'. Las reglas se basan en expresiones regulares POSIX (''extendidas'') con coincidencia de subcadenas; se permite la sustitución de variables básica y la resolución de mapas de subcadenas mediante mecanismos específicos detallados a continuación. El comportamiento de la coincidencia/sustitución de patrones puede ser alterado por un conjunto de flags.

<contexto de reescritura> ::= <regla de reescritura> [...]
<regla de reescritura> ::= <patrón> <acción> [<flags>]

El concepto subyacente es construir un módulo de reescritura ligero para el servidor slapd (inicialmente dedicado al backend LDAP):

Pasadas

Una cadena entrante se compara con un conjunto de reglasDeReescritura. Las reglas constan de un patrón de coincidencia regex, un patrón de sustitución y un conjunto de acciones, descritas por un conjunto de flags opcionales. En caso de coincidencia, la reescritura de la cadena se realiza de acuerdo con el patrón de sustitución que permite referirse a subcadenas coincidentes en la cadena entrante. Las acciones, si las hay, se realizan finalmente. Cada regla se ejecuta recursivamente, a menos que se altere mediante flags de acción específicos; véase "Flags de Acción" para más detalles. Se establece un límite por defecto en el nivel de recursión, y puede ser alterado por la directiva rwm-rewriteMaxPasses, tal como se detalla en la sección "Sintaxis de Configuración Adicional". El patrón de sustitución permite la resolución de mapas de subcadenas. Un mapa es un objeto genérico que mapea un patrón de sustitución a un valor. Los flags se dividen en "Flags de Coincidencia de Patrón" y "Flags de Acción"; los primeros alteran el comportamiento del patrón de coincidencia regex, mientras que los segundos alteran las acciones que se toman después de la sustitución.

Flags de Coincidencia de Patrón

`C'
respeta mayúsculas/minúsculas en la coincidencia (por defecto es insensible a mayúsculas/minúsculas)
`R'
usa expresiones regulares ''básicas'' POSIX (por defecto son ''extendidas'')
`M{n}'
permite no más de n pasadas recursivas para una regla específica; no altera el número total máximo de pasadas, por lo que solo puede imponer un límite más estricto para una regla específica.

Flags de Acción

`L'
finaliza la reescritura para la regla actual (el resultado es devuelto sin más procesamiento).
`R'
termina la reescritura para el contexto dado (el resultado es devuelto sin más procesamiento).
`S'
la sustitución se realiza una sola vez y se detiene el procesamiento posterior (útil para reescribir la primera ocurrencia de un patrón).
`X'
ejecuta la acción de reescritura en modo recursivo.
`N'
si la reescritura falla, la cadena original es devuelta.

MAPAS

El mecanismo de reescritura de cadenas permite la resolución de mapas. Un mapa puede ser uno de los siguientes tipos:

map
contiene pares clave/valor. La clave es un patrón de coincidencia, y el valor es una cadena de sustitución.
regexmap
contiene pares patrón regex/valor. El patrón regex es usado para encontrar un valor.
pcremap
contiene pares patrón PCRE/valor. El patrón PCRE es usado para encontrar un valor.

Los mapas se definen globalmente en slapd.conf, y se referencian por nombre en las reglas de reescritura. Un mapa puede ser consultado con la sintaxis siguiente:

$MAP_NAME[(attribute=value), ...][,key=value]

Donde MAP_NAME es el nombre del mapa, y key=value son los pares clave-valor que definen la entrada a buscar en el mapa. La primera ocurrencia de un patrón que coincida con la clave se usa para la resolución. Las partes de la cadena de valor que son patrones de expresiones regulares PCRE pueden ser reescritas.

Los mapas pueden ser cargados desde archivos. El formato de archivo es el siguiente:

# Comentarios empiezan con #
# Clave y valor separados por uno o más espacios
clave1 valor1
clave2 valor2 ...

Por ejemplo, para definir un mapa y usarlo en una regla de reescritura:

# En slapd.conf
rwm-map mymap file:/etc/openldap/mymap.txt
...
# Regla de reescritura
rule1 "^oldDN" "$mymap(key=oldDN)"

CONFIGURACIÓN ADICIONAL

Las siguientes directivas pueden ser usadas para configurar el overlay rwm:

rwm-rewriteMaxPasses <n>
Establece el número máximo de pasadas recursivas permitidas para reescritura. El valor por defecto es 5.
rwm-rewriteMaxKeys <n>
Establece el número máximo de claves permitidas en un mapa. El valor por defecto es 100.

EJEMPLO

Aquí tienes un ejemplo de cómo usar el overlay rwm para remapear un sufijo y algunos atributos:

# slapd.conf
database ldap
    uri ldap://ldap.example.com
    suffix "dc=example,dc=com"

overlay rwm
    rwm-suffixmassage "dc=example,dc=com" "dc=example,dc=org"
    rwm-map objectclass user password
    rwm-map attribute userpassword unicodePwd

En este ejemplo, las solicitudes dirigidas a "dc=example,dc=com" serán reescritas para apuntar a "dc=example,dc=org" en el servidor LDAP remoto. Además, el objectClass "user" se mapeará a "password", y el attributeType "userpassword" se mapeará a "unicodePwd".

ADVERTENCIAS

Este overlay es experimental y puede no ser adecuado para entornos de producción.

El uso de reescritura de DN compleja puede llevar a resultados inesperados si no se maneja con cuidado.

La manipulación de sufijos antes de la selección de base de datos puede tener implicaciones de seguridad si no se configura correctamente.

Flags de Acción

`:'
aplica la regla solo una vez (el valor predeterminado es recursivo)
`@'
detiene la aplicación de reglas en caso de coincidencia; la regla actual todavía se aplica recursivamente; combínalo con `:' para aplicar la regla actual solo una vez y luego detenerse.
`#'
detiene la operación actual si la regla coincide, y emite un error de "no se puede realizar".
`G{n}'
salta n reglas hacia atrás y hacia adelante (¡cuidado con los bucles!). Ten en cuenta que `G{1}' es implícito en cada regla.
`I'
ignora los errores en la regla; esto significa que, en caso de error, por ejemplo, emitido por un mapa, el error se trata como una coincidencia fallida. El "no se puede realizar" no se anula.
`U{n}'
usa n como código de retorno si la regla coincide; el flag no altera el comportamiento recursivo de la regla, por lo que, para que se ejecute solo una vez, debe ser utilizado en combinación con `:', por ejemplo, `:U{32}' devuelve el valor `32' (indicando noSuchObject) después de exactamente una ejecución de la regla, si el patrón coincide. Como consecuencia, su comportamiento es equivalente a `@', con el código de retorno establecido en n; o, en otras palabras, `@' es equivalente a `U{0}'. Se permiten errores positivos, que indican los códigos de error LDAP relacionados según se especifica en RFC4511.

El orden de los flags puede ser significativo. Por ejemplo: `IG{2}' significa ignorar errores y saltar dos líneas hacia adelante tanto en caso de coincidencia como en caso de error, mientras que `G{2}I' significa ignorar errores, pero saltar dos líneas hacia adelante solo en caso de coincidencia.

Se agregarán más flags (principalmente Flags de Acción) según sea necesario.

Sintaxis del Patrón de Sustitución

Todo lo que comience con `$' requiere sustitución;

la única excepción obvia es `$$', que se convierte en un solo `$';

la sustitución básica es `$<d>', donde `<d>' es un dígito; 0 significa la cadena completa, mientras que 1-9 es una subcoincidencia, como se discute en regex(7) y/o re_format(7).

un `$' seguido de `{' invoca una sustitución avanzada. El patrón es:

`$' `{' [ <operador> ] <nombre> `(' <sustitución> `)' `}'

donde <nombre> debe ser un nombre legal para el mapa, es decir.

<nombre> ::= [a-z][a-z0-9]* (sin distinción entre mayúsculas y minúsculas)
<operador> ::= `>' `|' `&' `&&' `*' `**' `$'

y <sustitución> debe ser un patrón de sustitución legal, sin límites en el nivel de anidamiento.

Los operadores son:

>
invocación de subcontexto; <nombre> debe ser un nombre de contexto de reescritura legal y ya definido
|
invocación de comando externo; <nombre> debe referirse a un nombre de comando legal y ya definido (¡AÚN NO IMPLEMENTADO!)
&
asignación de variable; <nombre> define una variable en la estructura de operación en ejecución que puede ser desreferenciada más tarde; el operador & asigna una variable en el ámbito del contexto de reescritura; el operador && asigna una variable que abarca toda la sesión, por ejemplo, su valor puede ser desreferenciado más tarde por otros contextos de reescritura
*
desreferenciación de variable; <nombre> debe referirse a una variable que esté definida y asignada para la operación en ejecución; el operador * desreferencia una variable que abarca el contexto de reescritura; el operador ** desreferencia una variable que abarca toda la sesión, por ejemplo, el valor se pasa entre contextos de reescritura
$
desreferenciación de parámetro; <nombre> debe referirse a un parámetro existente; la idea es hacer que algunos parámetros en tiempo de ejecución establecidos por el sistema estén disponibles para el motor de reescritura, como el nombre del host del cliente, el DN de conexión si lo hay, parámetros constantes inicializados en el momento de la configuración, etc.; actualmente ni back-ldap ni back-meta establecen ningún parámetro, pero los parámetros constantes se pueden definir en el archivo de configuración utilizando la directiva rewriteParam.

El escape de sustitución se ha delegado al símbolo `$', que se usa en lugar de `\' en los patrones de sustitución de cadenas porque `\' ya está escapado por las rutinas de análisis de bajo nivel de slapd; como consecuencia, el escape de expresiones regulares requiere dos símbolos `\', por ejemplo, `.*\.foo\.bar' debe escribirse como `.*\\.foo\\.bar'.

Contexto de Reescribura

Un contexto de reescritura es un conjunto de reglas que se aplican en secuencia. La idea básica es que una aplicación inicialice un motor de reescritura (piense en mod_rewrite de Apache...) con un conjunto de contextos de reescritura; cuando se requiere reescritura de cadenas, se invoca el contexto de reescritura apropiado con la cadena de entrada y se obtiene la recién reescrita si no ocurren errores.

Cada operación básica del servidor se asocia a un contexto de reescritura; están divididas en dos grupos principales: reescritura cliente -> servidor y servidor -> cliente.

cliente -> servidor:

(predeterminado)            si está definido y no hay un contexto específico
                     disponible
bindDN               bind
searchDN             search
searchFilter         search
searchFilterAttrDN   search
compareDN            compare
compareAttrDN        compare AVA
addDN                add
addAttrDN            add AVA (porción DN de "ref" excluida)
modifyDN             modify
modifyAttrDN         modify AVA (porción DN de "ref" excluida)
referralAttrDN       porción DN de add/modify de referencias
                     (predeterminado a none)
renameDN             modrdn (el DN antiguo)
newSuperiorDN        modrdn (el nuevo DN padre, si existe)
newRDN               modrdn (el nuevo DN relativo)
deleteDN             delete
exopPasswdDN         operación extendida de modificación de contraseña DN

servidor -> cliente:

searchEntryDN        search (solo si está definido; sin predeterminado;
                     actúa sobre el DN de las entradas de búsqueda)
searchAttrDN         search AVA (solo si está definido; predeterminado
                     a searchEntryDN; actúa sobre atributos de sintaxis DN
                     de los resultados de búsqueda)
matchedDN            todas las ops (solo si es aplicable; predeterminado
                     a searchEntryDN)
referralDN           todas las ops (solo si es aplicable; predeterminado
                     a none)

Sintaxis Básica de Configuración

Todas las directivas de reescritura/remapeo comienzan con el prefijo rwm-

rwm-rewriteEngine { on | off }
Si es `on', se realiza la reescritura solicitada; si es `off', no se realiza ninguna reescritura (una forma fácil de detener la reescritura sin alterar demasiado el archivo de configuración).
rwm-rewriteContext <nombre del contexto> [ alias <nombre del contexto alias> ]
<Nombre del contexto> es el nombre que identifica el contexto, es decir, el nombre utilizado por la aplicación para referirse al conjunto de reglas que contiene. Se utiliza también para referenciar subcontextos en la reescritura de cadenas. Un contexto puede ser alias de otro. En este caso, el contexto alias no contiene ninguna regla, y cualquier referencia a él resultará en el acceso al alias.
rwm-rewriteRule <patrón de coincidencia regex> <patrón de sustitución> [ <flags> ]
Determina cómo se puede reescribir una cadena si se coincide con un patrón. Los ejemplos se presentan a continuación.

Sintaxis Adicional de Configuración

rwm-rewriteMap <tipo de mapa> <nombre del mapa> [ <atributos del mapa> ]
Permite definir un mapa que transforma la reescritura de subcadenas en algo más. El mapa se referencia dentro del patrón de sustitución de una regla.
rwm-rewriteParam <nombre del parámetro> <valor del parámetro>
Establece un valor con ámbito global, que puede ser desreferenciado por el comando `${$nombreParametro}'.
rwm-rewriteMaxPasses <número de pases> [<número de pases por regla>]
Establece el número máximo de pases de reescritura totales que se pueden realizar en una sola operación de reescritura (para evitar bucles). Un valor seguro predeterminado es 100; ten en cuenta que alcanzar este límite todavía se trata como un éxito; la invocación recursiva de reglas simplemente se interrumpe. El recuento se aplica a la operación de reescritura en su conjunto, no a ninguna regla individual; se puede establecer un límite opcional por regla. Este límite se anula estableciendo límites específicos por regla con el flag `M{n}'.

MAPAS

Actualmente, pocos mapas están integrados, pero se pueden registrar tipos de mapas adicionales en tiempo de ejecución.

Los mapas soportados son:

LDAP <URI> [bindwhen=<cuándo>] [version=<versión>] [binddn=<DN>] [credentials=<cred>]
El mapa LDAP expande un valor realizando una búsqueda LDAP simple. Su configuración se basa en una URI obligatoria, cuya porción attrs debe contener exactamente un atributo (usa entryDN para obtener el DN de una entrada). Si se utiliza un atributo multivaluado, solo se considera el primer valor.

El parámetro bindwhen determina cuándo se establece la conexión. Puede tomar los valores now, later y everytime, indicando respectivamente que la conexión debe crearse al inicio, cuando sea necesaria, o cada vez que se utilice. En los dos primeros casos, la conexión se almacena en caché, mientras que en el último se utiliza una nueva conexión todas las veces. Este es el valor predeterminado.

Los parámetros binddn y credentials representan el DN y la contraseña que se utilizan para realizar un enlace simple autenticado antes de realizar la operación de búsqueda; si no se proporcionan, se utiliza una conexión anónima.

El parámetro version puede ser 2 o 3 para indicar la versión del protocolo que se debe utilizar. El valor predeterminado es 3.

MAPPING

The following directives map the object class `groupOfNames' to the object class `groupOfUniqueNames' and the attribute type `member' to the attribute type `uniqueMember':

map objectclass groupOfNames groupOfUniqueNames
map attribute uniqueMember member

This presents a limited attribute set from the foreign server:

map attribute cn *
map attribute sn *
map attribute manager *
map attribute description *
map attribute *

These lines map cn, sn, manager, and description to themselves, and any other attribute gets "removed" from the object before it is sent to the client (or sent up to the LDAP server). This is obviously a simplistic example, but you get the point.

SUFFIX MASSAGING

The following directives massage the DNs passed to the front-end:

rwm-rewriteEngine on
rwm-rewriteContext default
rwm-rewriteRule "^(.*),dc=example,dc=com$" "$1,dc=example,dc=org" ":"

This rule takes any DN ending with `dc=example,dc=com' and changes the naming context to `dc=example,dc=org'.

For this to be effective, the DN must be matched exactly as it is in the directory.

The rwm-rewriteContext directive is used to select the current context for subsequent rewrite rules. The default context is `default'.

The rewrite rules are applied in the order they appear in the configuration file. The rewriting engine stops processing rules for the current context when a rule terminates with the action flag `:'.

When rules are processed for subsequent contexts, they are appended to the rules of the preceding contexts.

The contexts are processed in the following order:

  • searchFilter: rewrite search filters

  • searchEntryDN: rewrite DNs of entries being returned

  • searchAttrDN: rewrite DNs of attribute values being returned

  • addEntryDN: rewrite DNs of entries being added

  • addAttrDN: rewrite DNs of attribute values being added

  • modifyEntryDN: rewrite DNs of entries being modified

  • modifyAttrDN: rewrite DNs of attribute values being modified

  • bindDN: rewrite DNs used for binding

  • default: a catch-all context

When context names are repeated, the rules are appended.

Additional contexts can be defined by using the alias keyword:

rwm-rewriteContext searchAttrDN alias searchEntryDN

This directive makes searchAttrDN behave exactly like searchEntryDN.

REWRITING

The rewrite module performs rewriting based on context specific rules. The rules are evaluated in sequence within each context. The contexts are evaluated in a specific order, which can be altered using context aliases.

The rewriting engine is controlled by the rwm-rewriteEngine directive.

Rules are defined using the rwm-rewriteRule directive, which takes a pattern, a substitution string, and an optional action flag.

Patterns are POSIX Extended Regular Expressions, as supported by the system's regex library.

Substitution strings can contain backreferences to captured sub-expressions in the pattern (e.g., $1, $2, etc.). They can also contain references to other rewrite rules or maps.

The action flags determine what happens after a rule matches:

:
Stop processing rules in the current context. This is the default action if no flag is specified.
:I
Continue processing rules in the current context. The substitution string is passed to the next rule.
:S
Stop processing rules in the current context and continue with the next context. The substitution string is passed to the next context.
:T
Stop processing rules in the current context and continue with the next context. The substitution string is passed to the next context, and the original string is kept.
:N
Stop processing rules in the current context and discard the substitution string. The original string is kept.
:C
Stop processing rules in the current context and discard the substitution string. The original string is discarded.
:<
Stop processing rules in the current context and discard the substitution string. The original string is passed to the next context.
:>
Stop processing rules in the current context and pass the substitution string to the next context.
:#
Discard the substitution string and stop processing rules in the current context. The original string is kept.
:@
Discard the substitution string and stop processing rules in the current context. The original string is discarded.

Passes

The rewriting engine supports the following passes:

P
The string is rewritten according to the rules defined for the context specified in the rwm-rewriteContext directive.
PN
The string is rewritten according to the rules defined for the context specified in the rwm-rewriteContext directive. The result of the rewriting is passed to the Nth rule of the current context.
R
The string is rewritten according to the rules defined for the context specified in the rwm-rewriteContext directive. The result of the rewriting is returned to the client.
S
The string is rewritten according to the rules defined for the context specified in the rwm-rewriteContext directive. The result of the rewriting is stored in a session variable.

Pattern Matching Flags

The following flags can be used to modify the behavior of pattern matching:

i
Case-insensitive matching.
m
Multi-line matching. The pattern is treated as a sequence of lines, and any of the lines may match.
x
Extended regex. Whitespace is ignored, and comments are allowed.

Action Flags

The following flags can be used to modify the behavior of the action flags:

I
Case-insensitive matching for DN components.
N
Normalize DN before matching.

Pattern Matching

The pattern matching is performed using POSIX Extended Regular Expressions. The following special characters are available:

^
Matches the beginning of the string.
$
Matches the end of the string.
.
Matches any single character.
*
Matches the preceding element zero or more times.
+
Matches the preceding element one or more times.
?
Matches the preceding element zero or one time.
{}
Specifies a range of occurrences.
[]
Matches any one of the characters enclosed in the brackets.
()
Captures the enclosed sub-expression.
|
Alternation. Matches either the expression before or after the pipe.
\
Escapes the next character.

Substitution Pattern Syntax

The substitution pattern can contain backreferences to captured sub-expressions in the pattern. The backreferences are denoted by $N, where N is the number of the captured sub-expression.

The substitution pattern can also contain references to other rewrite rules or maps. The syntax for this is:

${mapname(argument)}
Calls the specified map with the given argument.

The following special substitutions are also available:

$0
The entire matched string.
$&
The entire matched string.
$~
The input string.
$>
The result of the last executed rewrite rule.

Rewrite Context

The rewrite module supports the following contexts:

default
The default context, used for general rewriting.
searchFilter
Rewriting of search filters.
searchEntryDN
Rewriting of DNs of entries being returned.
searchAttrDN
Rewriting of DNs of attribute values being returned.
addEntryDN
Rewriting of DNs of entries being added.
addAttrDN
Rewriting of DNs of attribute values being added.
modifyEntryDN
Rewriting of DNs of entries being modified.
modifyAttrDN
Rewriting of DNs of attribute values being modified.
bindDN
Rewriting of DNs used for binding.
referralDN
Rewriting of DNs used for referrals.
compareFilter
Rewriting of compare filters.
compareEntryDN
Rewriting of DNs of entries being compared.
compareAttrDN
Rewriting of DNs of attribute values being compared.
SASL
Rewriting of DNs used for SASL authentication.

The order of contexts is important. Rules for contexts that appear earlier in the list are applied before rules for contexts that appear later.

Basic Configuration Syntax

The basic configuration syntax for the rewrite module is as follows:

rwm-rewriteEngine on|off
rwm-rewriteContext <context> [alias] [<context>...]
rwm-rewriteRule "<pattern>" "<substitution>" [<action_flags>]

Additional Configuration Syntax

The rewrite module also supports the following directives:

rwm-rewriteMap mapname mapurl
Defines a rewrite map. The mapurl specifies the location of the map. The supported mapurl schemes are:
LDAP
LDAP URL. The URI must begin with ldap:/// (i.e., it must be an LDAP URI and it must not specify a host). As with the LDAP map, the attrs portion must contain exactly one attribute, and if a multi-valued attribute is used, only the first value is considered.
escape [escape2dn|escape2filter|unescapedn|unescapefilter]...
The escape map makes it possible use DNs or their parts in filter strings and vice versa. It processes a value according to the operations listed in order. Supported operations include:
escape2dn
takes a string and escapes it so it can safely be pasted in a DN
escape2filter
takes a string and escapes it so it can safely be pasted in a filter
unescapedn
takes a string and undoes DN escaping
unescapefilter
takes a string and undoes filter escaping
It is advised that each escape map ends with an escape operation as that is the only safe way to handle arbitrary strings.

REWRITE CONFIGURATION EXAMPLES

# set to `off' to disable rewriting
rwm-rewriteEngine on
# the rules the "suffixmassage" directive implies
rwm-rewriteEngine on
# all dataflow from client to server referring to DNs
rwm-rewriteContext default
rwm-rewriteRule "(.+,)?<virtualnamingcontext>$" "$1<realnamingcontext>" ":"
# empty filter rule
rwm-rewriteContext searchFilter
# all dataflow from server to client
rwm-rewriteContext searchEntryDN
rwm-rewriteRule "(.+,)?<realnamingcontext>$" "$1<virtualnamingcontext>" ":"
rwm-rewriteContext searchAttrDN alias searchEntryDN
rwm-rewriteContext matchedDN alias searchEntryDN
# misc empty rules
rwm-rewriteContext referralAttrDN
rwm-rewriteContext referralDN
# Everything defined here goes into the `default' context.
# This rule changes the naming context of anything sent
# to `dc=home,dc=net' to `dc=OpenLDAP, dc=org'
rwm-rewriteRule "(.+,)?dc=home,[ ]?dc=net$"
            "$1dc=OpenLDAP, dc=org"  ":"
# since a pretty/normalized DN does not include spaces
# after rdn separators, e.g. `,', this rule suffices:
rwm-rewriteRule "(.+,)?dc=home,dc=net$"
            "$1dc=OpenLDAP,dc=org"  ":"
# Start a new context (ends input of the previous one).
# This rule adds blanks between DN parts if not present.
rwm-rewriteContext  addBlanks
rwm-rewriteRule     "(.*),([^ ].*)" "$1, $2"
# This one eats blanks
rwm-rewriteContext  eatBlanks
rwm-rewriteRule     "(.*), (.*)" "$1,$2"
# Here control goes back to the default rewrite
# context; rules are appended to the existing ones.
# anything that gets here is piped into rule `addBlanks'
rwm-rewriteContext  default
rwm-rewriteRule     ".*" "${>addBlanks($0)}" ":"
# Rewrite the search base according to `default' rules.
rwm-rewriteContext  searchDN alias default
# Search results with OpenLDAP DN are rewritten back with
# `dc=home,dc=net' naming context, with spaces eaten.
rwm-rewriteContext  searchEntryDN
rwm-rewriteRule     "(.*[^ ],)?[ ]?dc=OpenLDAP,[ ]?dc=org$"
                "${>eatBlanks($1)}dc=home,dc=net"    ":"
# Transform a DN value such that it can be used in a filter
rwm-rewriteMap escape dn2filter unescapedn escape2filter
# Bind with email instead of full DN: we first need
# an ldap map that turns attributes into a DN (the
# argument used when invoking the map is appended to
# the URI and acts as the filter portion)
rwm-rewriteMap ldap attr2dn "ldap://host/dc=my,dc=org?dn?sub"
# Then we need to detect DN made up of a single email,
# e.g. `mail=someone@example.com'; note that the rule
# in case of match stops rewriting; in case of error,
# it is ignored.  In case we are mapping virtual
# to real naming contexts, we also need to rewrite
# regular DNs, because the definition of a bindDN
# rewrite context overrides the default definition.
#
# While actual email addresses tend not to contain filter
# special characters, the provided Bind DN has no such
# restrictions.
rwm-rewriteContext bindDN
rwm-rewriteRule "^(mail=)([^,]+@[^,]+)$"
                "${attr2dn($1${dn2filter($2)})}" ":@I"
# This is a rather sophisticated example. It massages a
# search filter in case who performs the search has
# administrative privileges.  First we need to keep
# track of the bind DN of the incoming request, which is
# stored in a variable called `binddn' with session scope,
# and left in place to allow regular binding:
rwm-rewriteContext  bindDN
rwm-rewriteRule     ".+" "${&&binddn($0)}$0" ":"
# A search filter containing `uid=' is rewritten only
# if an appropriate DN is bound.
# To do this, in the first rule the bound DN is
# dereferenced, while the filter is decomposed in a
# prefix, in the value of the `uid=<arg>' AVA, and
# in a suffix. A tag `<>' is appended to the DN.
# If the DN refers to an entry in the `ou=admin' subtree,
# the filter is rewritten OR-ing the `uid=<arg>' with
# `cn=<arg>'; otherwise it is left as is. This could be
# useful, for instance, to allow apache's auth_ldap-1.4
# module to authenticate users with both `uid' and
# `cn', but only if the request comes from a possible
# `cn=Web auth,ou=admin,dc=home,dc=net' user.
rwm-rewriteContext searchFilter
rwm-rewriteRule "(.*\\()uid=([a-z0-9_]+)(\\).*)"
  "${**binddn}<>${&prefix($1)}${&arg($2)}${&suffix($3)}"
  ":I"
rwm-rewriteRule "^[^,]+,ou=admin,dc=home,dc=net$"
  "${*prefix}|(uid=${*arg})(cn=${*arg})${*suffix}" ":@I"
rwm-rewriteRule ".*<>$" "${*prefix}uid=${*arg}${*suffix}" ":"
# This example shows how to strip unwanted DN-valued
# attribute values from a search result; the first rule
# matches DN values below "ou=People,dc=example,dc=com";
# in case of match the rewriting exits successfully.
# The second rule matches everything else and causes
# the value to be rejected.
rwm-rewriteContext searchEntryDN
rwm-rewriteRule ".+,ou=People,dc=example,dc=com$" "$0" ":@"
rwm-rewriteRule ".*" "" "#"

MAPPING EXAMPLES

The following directives map the object class `groupOfNames' to the object class `groupOfUniqueNames' and the attribute type `member' to the attribute type `uniqueMember':

map objectclass groupOfNames groupOfUniqueNames
map attribute uniqueMember member

This presents a limited attribute set from the foreign server:

map attribute cn *
map attribute sn *
map attribute manager *
map attribute description *
map attribute *

These lines map cn, sn, manager, and description to themselves, and any other attribute gets "removed" from the object before it is sent to the client (or sent up to the LDAP server). This is obviously a simplistic example, but you get the point.
