SLAPD.ACCESS(5) Manual de Formatos de Archivo SLAPD.ACCESS(5)

NOMBRE

slapd.access - configuración de acceso para slapd, el demonio LDAP independiente

SINOPSIS

/etc/openldap/slapd.conf

DESCRIPCIÓN

El archivo slapd.conf(5) contiene información de configuración para el demonio slapd(8). Este archivo de configuración también es utilizado por las herramientas de SLAPD slapacl(8), slapadd(8), slapauth(8), slapcat(8), slapdn(8), slapindex(8), slapmodify(8) y slaptest(8).

El archivo slapd.conf consta de una serie de opciones de configuración globales que se aplican a slapd en su conjunto (incluyendo todos los backends), seguidas de cero o más definiciones de backend de base de datos que contienen información específica de una instancia de backend.

El formato general de slapd.conf es el siguiente:

    # comentario - estas opciones se aplican a cada base de datos
    <opciones de configuración globales>
    # primera definición de base de datos y opciones de configuración
    database    <tipo de backend 1>
    <opciones de configuración específicas del backend 1>
    # definiciones de base de datos subsiguientes y opciones de configuración
    ...

Tanto la configuración global como cada sección específica del backend pueden contener información de acceso. Las directivas de control de acceso específicas del backend se utilizan para las entradas que pertenecen al backend, según su contexto de nombrado. En caso de que no se definan directivas de control de acceso para un backend o aquellas que se definan no sean aplicables, se utilizan las directivas de la sección de configuración global.

Si no hay controles de acceso presentes, la política predeterminada permite a cualquiera leer cualquier cosa, pero restringe las actualizaciones a rootdn. (por ejemplo, "access to * by * read").

Al tratar con una lista de acceso, dado que la lista de acceso global se anexa efectivamente a cada lista por base de datos, si la lista resultante no está vacía, la lista de acceso terminará con una directiva implícita de access to * by * none. Si no hay directivas de acceso aplicables a un backend, se utiliza un valor predeterminado de lectura.

¡Advertencia: rootdn siempre puede leer y escribir TODO!

Para las entradas que no están en ningún backend (como un DSE raíz), se utilizan las directivas globales.

Los argumentos que deben reemplazarse por texto real se muestran entre corchetes <>.

LA DIRECTIVA ACCESS

La estructura de las directivas de control de acceso es

access to <qué> [ by <quién> [ <acceso> ] [ <control> ] ]+
Otorga acceso (especificado por <acceso>) a un conjunto de entradas y/o atributos (especificado por <qué>) por uno o más solicitantes (especificado por <quién>).

Las listas de directivas de acceso se evalúan en el orden en que aparecen en slapd.conf. Cuando una cláusula <qué> coincide con el dato cuyo acceso se está evaluando, se verifica su lista de cláusulas <quién>. Cuando una cláusula <quién> coincide con las propiedades del solicitante, se evalúan sus cláusulas <acceso> y <control>.

La verificación del control de acceso se detiene en la primera coincidencia de la cláusula <qué> y <quién>, a menos que se indique lo contrario por la cláusula <control>. Cada lista de cláusulas <quién> se termina implícitamente con

by * none stop

cláusula <control>. Este <control> implícito detiene la evaluación de la directiva de acceso sin otorgar más privilegios de acceso a nadie más. Para detener la evaluación de la directiva de acceso solo cuando coinciden tanto <quién> como <qué>, agregue explícitamente

by * break

al final de la lista de cláusulas <quién>.

Cada lista de cláusulas <qué> se termina implícitamente con una

access to *
	by * none

cláusula que da como resultado no otorgar privilegios de acceso a un dato no especificado de otro modo.

EL CAMPO <QUÉ>

El campo <qué> especifica la entidad a la que se aplica la directiva de control de acceso. Puede tener las formas

dn[.<dnstyle>]=<dnpattern>
filter=<ldapfilter>
attrs=<attrlist>[ val[/matchingRule][.<attrstyle>]=<attrval>]

con

<dnstyle>={{exact|base(object)}|regex
	|one(level)|sub(tree)|children}
<attrlist>={<attr>|[{!|@}]<objectClass>}[,<attrlist>]
<attrstyle>={{exact|base(object)}|regex
	|one(level)|sub(tree)|children}

La declaración dn=<dnpattern> selecciona las entradas según su contexto de nombrado. El <dnpattern> es una representación de cadena del DN de la entrada. El comodín * representa todas las entradas, y se asume si no se proporciona ninguna forma de dn.

El <dnstyle> es opcional; sin embargo, se recomienda especificarlo para evitar ambigüedades. Base (sinónimo de baseObject), el valor predeterminado, o exact (un alias de base) indica la entrada cuyo DN es igual al <dnpattern>; one (sinónimo de onelevel) indica todas las entradas inmediatamente debajo del <dnpattern>, sub (sinónimo de subtree) indica todas las entradas en el subárbol en el <dnpattern>, children indica todas las entradas debajo (subordinadas a) del <dnpattern>.

Si el calificador <dnstyle> es regex, entonces <dnpattern> es un patrón de expresión regular POSIX (extendido), como se detalla en regex(7) y/o re_format(7), que coincide con una representación de cadena normalizada del DN de la entrada. La forma regex del patrón no soporta (aún) UTF-8.

La declaración filter=<ldapfilter> selecciona las entradas basándose en un filtro LDAP válido, tal como se describe en RFC 4515. Se asume un filtro de (objectClass=*) si no se proporciona ninguna forma de filter.

La declaración attrs=<attrlist> selecciona los atributos a los que se aplica la regla de control de acceso. Es una lista separada por comas de tipos de atributos, más los nombres especiales entry, que indica el acceso a la entrada en sí, y children, que indica el acceso a los hijos de la entrada. También se pueden especificar nombres de ObjectClass en esta lista, lo que afectará a todos los atributos que son requeridos y/o permitidos por esa objectClass. De hecho, los nombres en <attrlist> que están prefijados por @ se tratan directamente como nombres de objectClass. Un nombre prefijado por ! también se trata como una objectClass, pero en este caso la regla de acceso afecta a los atributos que no son requeridos ni permitidos por esa objectClass. Si no se proporciona ninguna forma de attrs, se asume attrs=@extensibleObject, es decir, se abordan todos los atributos.

Usando la forma attrs=<attr> val[/matchingRule][.<attrstyle>]=<attrval> se especifica acceso a un valor particular de un solo atributo. En este caso, solo se puede proporcionar un tipo de atributo. El <attrstyle> exact (el predeterminado) utiliza la regla de coincidencia de igualdad del atributo para comparar el valor, a menos que se especifique una regla de coincidencia diferente (y compatible). Si el <attrstyle> es regex, el valor proporcionado se utiliza como un patrón de expresión regular POSIX (extendido). Si el atributo tiene sintaxis de DN, el <attrstyle> puede ser cualquiera de base, onelevel, subtree o children, lo que resulta en una coincidencia de base, onelevel, subtree o children, respectivamente.

Las declaraciones dn, filter y attrs son aditivas; se pueden utilizar en secuencia para seleccionar entidades a las que se aplica la regla de acceso basándose en el contexto de nombrado, el valor y el tipo de atributo simultáneamente. Las subcoincidencias resultantes de la coincidencia regex se pueden desreferenciar en el campo <quién> utilizando la sintaxis ${v<n>}, donde <n> es el número de subcoincidencia. La sintaxis predeterminada, $<n>, es en realidad un alias de ${d<n>}, que corresponde a la desreferenciación de subcoincidencias de la parte dnpattern del campo <qué>.

El comodín * se refiere a todos.

Las palabras clave precedidas por real actúan como sus contrapartes sin prefijo; la verificación se realiza respectivamente con el DN de autenticación y el DN de autorización.

La palabra clave anonymous significa que se concede acceso a los clientes no autenticados; se utiliza principalmente para limitar el acceso a los recursos de autenticación (por ejemplo, el atributo userPassword) a los clientes no autenticados con fines de autenticación.

La palabra clave users significa que se concede acceso a los clientes autenticados.

La palabra clave self significa que se permite el acceso a una entrada a la propia entrada (por ejemplo, la entrada que se está accediendo y la entrada solicitante deben ser la misma). Permite el estilo level{<n>}, donde <n> indica qué ancestro del DN se va a utilizar en las coincidencias. Un valor positivo indica que se considerará el enésimo ancestro del DN del usuario; un valor negativo indica que se considerará el enésimo ancestro del objetivo. Por ejemplo, una cláusula "by self.level{1} ..." coincidiría cuando se accede al objeto "dc=example,dc=com" por "cn=User,dc=example,dc=com". Una cláusula "by self.level{-1} ..." coincidiría cuando el mismo usuario accede al objeto "ou=Address Book,cn=User,dc=example,dc=com".

La declaración dn=<DN> significa que se concede acceso al DN coincidente. El calificador de estilo opcional dnstyle permite las mismas opciones de la forma dn del campo <what>. Además, el estilo regex puede explotar la sustitución de subcadenas de subcoincidencias en la cláusula dn.regex=<DN> utilizando la forma $<dígito>, con dígito que va de 0 a 9 (donde 0 coincide con toda la cadena), o la forma ${<dígito>+}, para subcoincidencias superiores a 9. La sustitución de subcadenas a partir del valor del atributo se puede hacer utilizando la forma ${v<dígito>+}. Dado que el carácter de dólar se utiliza para indicar un reemplazo de subcadena, el carácter de dólar que se utiliza para indicar una coincidencia hasta el final de la cadena debe escaparse con un segundo carácter de dólar, por ejemplo: 

    access to dn.regex="^(.+,)?uid=([^,]+),dc=[^,]+,dc=com$"
        by dn.regex="^uid=$2,dc=[^,]+,dc=com$$" write

El calificador de estilo permite un modificador opcional. Actualmente, el único tipo permitido es expand, que provoca la sustitución de subcadenas de subcoincidencias incluso si dnstyle no es regex. Tenga en cuenta que el estilo dn regex en el ejemplo anterior puede ser útil solo si la cláusula <by> necesita ser una regex; de lo contrario, si el valor de la segunda (desde la derecha) porción dc= del DN en el ejemplo anterior fuera fijo, se podría usar la forma 

    access to dn.regex="^(.+,)?uid=([^,]+),dc=example,dc=com$"
        by dn.exact,expand="uid=$2,dc=example,dc=com" write

; si tuviera que coincidir con el valor en la cláusula <what>, se podría usar la forma 

    access to dn.regex="^(.+,)?uid=([^,]+),dc=([^,]+),dc=com$"
        by dn.exact,expand="uid=$2,dc=$3,dc=com" write

.

Las formas de la cláusula <what> distintas de regex pueden proporcionar subcoincidencias. Las formas base(object), sub(tree), one(level) y children proporcionan $0 como la coincidencia de toda la cadena. Las formas sub(tree), one(level) y children también proporcionan $1 como la coincidencia de la parte más a la derecha del DN tal como se define en la cláusula <what>. Esto puede ser útil, por ejemplo, para proporcionar acceso a todos los ancestros de un usuario definiendo 

    access to dn.subtree="dc=com"
        by dn.subtree,expand="$1" read

que significa que solo se permite el acceso a las entradas que aparecen en el DN de la cláusula <by>.

La forma level{<n>} es una extensión y una generalización de la forma onelevel, que coincide con todos los DN cuyo enésimo ancestro es el patrón. Por lo tanto, level{1} es equivalente a onelevel, y level{0} es equivalente a base.

Es completamente inútil otorgar privilegios de acceso a un DN que coincide exactamente con el rootdn de la base de datos a la que se aplican las ACL, ya que implícitamente posee privilegios de escritura para todo el árbol de esa base de datos. De hecho, el control de acceso se omite para el rootdn, para resolver el problema intrínseco del huevo y la gallina.

La declaración dnattr=<attrname> significa que se concede acceso a las solicitudes cuyo DN se encuentra en la entrada que se está accediendo bajo el atributo <attrname>.

La declaración group=<group> significa que se concede acceso a las solicitudes cuyo DN se encuentra en la entrada del grupo cuyo DN se indica mediante <group>. Los parámetros opcionales <objectclass> y <attrname> definen el objectClass y el attributeType miembro de la entrada del grupo. Los valores predeterminados son groupOfNames y member, respectivamente. El calificador de estilo opcional <style> puede ser expand, lo que significa que <group> se expandirá como una cadena de reemplazo (pero no como una expresión regular) según regex(7) y/o re_format(7), y exact, lo que significa que se utilizará una coincidencia exacta. Si el estilo de la porción DN de la cláusula <what> es regex, las subcoincidencias están disponibles según regex(7) y/o re_format(7); otros estilos proporcionan subcoincidencias limitadas como se discutió anteriormente sobre la forma DN de la cláusula <by>.

Para grupos estáticos, el attributeType especificado debe tener sintaxis DistinguishedName o NameAndOptionalUID. Para grupos dinámicos, el attributeType debe ser un subtipo del attributeType labeledURI. Solo se evaluarán las URI LDAP del formulario ldap:///<base>??<scope>?<filter> en un grupo dinámico, buscando solo en el servidor local.

Las declaraciones peername=<peername>, sockname=<sockname>, domain=<domain> y sockurl=<sockurl> significan que la IP del host de contacto (en el formato IP=<ip>:<port> para IPv4, o IP=[<ipv6>]:<port> para IPv6) o el nombre del canal con nombre del host de contacto (en el formato PATH=<path> si se conecta a través de un canal con nombre) para peername, el nombre del archivo del canal con nombre para sockname, el nombre del host de contacto para domain y la URL de contacto para sockurl se comparan con pattern para determinar el acceso. Las mismas reglas de style para la coincidencia de patrones descritas para el caso group se aplican, más el estilo regex, que implica la expansión de subcoincidencias y la coincidencia regex de los parámetros de conexión correspondientes. El estilo exact de la cláusula <peername> (el predeterminado) implica una coincidencia exacta que distingue entre mayúsculas y minúsculas en la IP del cliente, incluido el prefijo IP= y el sufijo :<port>, o la ruta del cliente, incluido el prefijo PATH= si se conecta a través de un canal con nombre. El estilo especial ip interpreta el patrón como <peername>=<ip>[%<mask>][{<n>}], donde <ip> y <mask> son representaciones de dígitos con puntos de la IP y la máscara, mientras que <n>, delimitado por llaves, es un puerto opcional. Lo mismo se aplica a las direcciones IPv6 cuando se utiliza el estilo especial ipv6. Al verificar los privilegios de acceso, se extrae la porción de IP del peername, eliminando el prefijo IP= y la parte :<port>, y se compara con la porción <ip> del patrón después de enmascararlo con <mask>: ((peername & <mask>) == <ip>). Como ejemplo, peername.ip=127.0.0.1 y peername.ipv6=::1 permiten conexiones solo desde localhost, peername.ip=192.168.1.0%255.255.255.0 permite conexiones desde cualquier IP del dominio de clase C 192.168.1, y peername.ip=192.168.1.16%255.255.255.240{9009} permite conexiones desde cualquier IP del rango 192.168.1.[16-31] del mismo dominio, solo si se utiliza el puerto 9009. El estilo especial path elimina el prefijo PATH= del peername al conectarse a través de un canal con nombre, y realiza una coincidencia exacta en el patrón dado. La cláusula <domain> también permite el estilo subtree, que tiene éxito cuando un nombre completamente calificado coincide exactamente con el patrón <domain>, o su parte final, después de un punto, coincide exactamente con el patrón <domain>. El estilo expand está permitido, lo que implica una coincidencia exacta con expansión de subcoincidencias; el uso de expand como modificador de estilo se considera más apropiado. Como ejemplo, domain.subtree=example.com coincidirá con www.example.com, pero no coincidirá con www.anotherexample.com. El dominio del host de contacto se determina realizando una búsqueda inversa en DNS. Dado que esta búsqueda se puede falsificar fácilmente, se desaconseja firmemente el uso de la declaración domain. Por defecto, las búsquedas inversas están deshabilitadas. El calificador opcional domainstyle de la cláusula <domain> permite una opción de modificador; el único valor actualmente admitido es expand, que provoca la sustitución de subcadenas de subcoincidencias incluso si domainstyle no es regex, muy parecido al uso análogo en la cláusula <dn>.

VERIFICACIONES DE CONTROL DE ACCESO

Las verificaciones de control de acceso se delegan al método definido por el administrador indicado por <nombre>, el cual puede registrarse en tiempo de ejecución mediante la declaración moduleload. Los campos <options>, <dynstyle> y <pattern> son opcionales y se pasan directamente a la rutina de análisis registrada. Dynacl es experimental; debe habilitarse en tiempo de compilación.

La declaración dynacl/aci[=<attrname>] significa que el control de acceso se determina por los valores en el attrname de la propia entrada. El <attrname> opcional indica qué attributeType contiene la información ACI en la entrada. Por defecto, se utiliza el atributo operacional OpenLDAPaci. Las ACIs son experimentales; deben habilitarse en tiempo de compilación.

Las declaraciones ssf=<n>, transport_ssf=<n>, tls_ssf=<n> y sasl_ssf=<n> establecen el Factor de Fortaleza de Seguridad (ssf) mínimo requerido para conceder acceso. El valor debe ser un entero positivo.

EL CAMPO <ACCESS>

El campo opcional <access> ::= [[real]self]{<level>|<priv>} determina el nivel de acceso o los privilegios de acceso específicos que tendrá el campo who. Sus componentes se definen como

<level> ::= none|disclose|auth|compare|search|read|{write|add|delete}|manage
<priv> ::= {=|+|-}{0|d|x|c|s|r|{w|a|z}|m}+

El modificador self permite operaciones especiales, como tener un cierto nivel de acceso o privilegio solo en caso de que la operación involucre el nombre del usuario que solicita el acceso. Implica que el usuario que solicita el acceso está autorizado. El modificador realself se refiere al DN autenticado en oposición al DN autorizado del modificador self. Un ejemplo es el selfwrite acceso al atributo miembro de un grupo, que permite agregar/eliminar el propio DN de la lista de miembros de un grupo, mientras no se permite afectar a otros miembros.

El modelo de acceso level se basa en una interpretación incremental de los privilegios de acceso. Los niveles posibles son none, disclose, auth, compare, search, read, write y manage. Cada nivel de acceso implica todos los anteriores, por lo tanto, manage otorga todo el acceso, incluido el acceso administrativo. Este acceso permite algunas modificaciones que de otro modo estarían prohibidas por el modelo de datos LDAP o el esquema del directorio, por ejemplo, cambiar la clase de objeto estructural de una entrada, o modificar un atributo operacional que se define como no modificable por el usuario. El acceso write es en realidad la combinación de add y delete, que respectivamente restringen el privilegio de escritura a agregar o eliminar el <what> especificado.

El nivel de acceso none prohíbe todo acceso, incluida la divulgación en caso de error.

El nivel de acceso disclose permite la divulgación de información en caso de error.

El nivel de acceso auth significa que se permite el acceso a un atributo para realizar operaciones de autenticación/autorización (por ejemplo, bind) sin ningún otro acceso. Esto es útil para otorgar a los clientes no autenticados el menor nivel de acceso posible a recursos críticos, como contraseñas.

El modelo de acceso priv se basa en el establecimiento explícito de privilegios de acceso para cada cláusula. El signo = restablece los accesos definidos previamente; como consecuencia, los privilegios de acceso finales serán solo los definidos por la cláusula. Los signos + y - agregan/eliminan privilegios de acceso a los existentes. Los privilegios son m para gestionar, w para escribir, a para agregar, z para eliminar, r para leer, s para buscar, c para comparar, x para autenticar y d para divulgar. Se pueden agregar más de uno de los privilegios anteriores en una sola declaración. 0 indica ningún privilegio y solo se usa por sí mismo (por ejemplo, +0). Tenga en cuenta que +az es equivalente a +w.

Si no se proporciona acceso, por defecto es +0.

EL CAMPO <CONTROL>

El campo opcional <control> controla el flujo de aplicación de las reglas de acceso. Puede tener las formas

stop
continue
break

donde stop, el valor predeterminado, significa que la verificación de acceso se detiene en caso de coincidencia. Las otras dos formas se utilizan para seguir procesando las cláusulas de acceso. En detalle, la forma continue permite que se consideren otras cláusulas <who> en la misma cláusula <access>, de modo que puedan resultar en la alteración incremental de los privilegios, mientras que la forma break permite que se procesen otras cláusulas <access> que coincidan con el mismo objetivo. Considere el ejemplo (tonto)

access to dn.subtree="dc=example,dc=com" attrs=cn
	by * =cs break
access to dn.subtree="ou=People,dc=example,dc=com"
	by * +r

que otorga privilegios de búsqueda y comparación a todos en el árbol "dc=example,dc=com", con la segunda regla que también permite leer en el subárbol "ou=People", o el ejemplo (aún más tonto)

access to dn.subtree="dc=example,dc=com" attrs=cn
	by * =cs continue
	by users +r

que otorga a todos privilegios de búsqueda y comparación, y agrega privilegios de lectura a los clientes autenticados.

Una aplicación útil es otorgar fácilmente privilegios de escritura a un updatedn que sea diferente del rootdn. En este caso, dado que el updatedn necesita acceso de escritura a (casi) todos los datos, se puede utilizar

access to *
	by dn.exact="cn=The Update DN,dc=example,dc=com" write
	by * break

como la primera regla de acceso. En consecuencia, a menos que la operación se realice con la identidad updatedn, el control se pasa directamente a las reglas subsiguientes.

REQUISITOS DE OPERACIÓN

Las operaciones requieren diferentes privilegios en diferentes porciones de las entradas. El siguiente resumen se aplica al backend de base de datos MDB principal. Los requisitos para otros backends pueden (y a menudo lo hacen) diferir.

La operación add requiere privilegios add (=a) en el pseudo-atributo entry de la entrada que se agrega, y privilegios add (=a) en el pseudo-atributo children del padre de la entrada. Al agregar la entrada de sufijo de una base de datos, se requiere acceso add a children del DN vacío (""). Además, si se ha configurado la verificación de ACL de contenido Add en la base de datos (consulte la página del manual slapd.conf(5) o slapd-config(5)), se requerirá add (=a) en todos los atributos que se agregan.

La operación bind, cuando las credenciales se almacenan en el directorio, requiere privilegios auth (=x) en el atributo donde se almacenan las credenciales (generalmente userPassword).

La operación compare requiere privilegios compare (=c) en el atributo que se está comparando.

La operación delete requiere privilegios delete (=z) en el pseudo-atributo entry de la entrada que se elimina, y privilegios delete (=d) en el pseudo-atributo children del padre de la entrada.

La operación modify requiere privilegios write (=w) en los atributos que se modifican. En detalle, se requiere add (=a) para agregar nuevos valores, se requiere delete (=z) para eliminar valores existentes, y se requieren tanto delete como add (=az), o write (=w), para reemplazar valores existentes.

La operación modrdn requiere privilegios write (=w) en el pseudo-atributo entry de la entrada cuyo DN relativo se está modificando, privilegios delete (=z) en el pseudo-atributo children de los padres de la entrada antigua, privilegios add (=a) en el pseudo-atributo children de los padres de la nueva entrada, y privilegios add (=a) en los atributos que están presentes en el nuevo DN relativo. También se requieren privilegios delete (=z) en los atributos que están presentes en el DN relativo antiguo si deleteoldrdn está establecido en 1.

La operación search, requiere privilegios search (=s) en el pseudo-atributo entry de la base de búsqueda (NOTA: esto se introdujo con OpenLDAP 2.4). Luego, para cada entrada, requiere privilegios search (=s) en los atributos que se definen en el filtro. Las entradas resultantes finalmente se prueban para obtener privilegios read (=r) en el pseudo-atributo entry (para acceso de lectura a la entrada en sí) y privilegios read (=r) en cada valor de cada atributo que se solicita. Además, para cada objeto referral utilizado en la generación de referencias de continuación, la operación requiere acceso read (=r) en el pseudo-atributo entry (para acceso de lectura al propio objeto de referencia), así como acceso read (=r) al atributo que contiene la información de referencia (generalmente el atributo ref).

Algunas operaciones internas y algunos controles requieren privilegios de acceso específicos.

El mapeo SASL authzID y el control LDAP proxyAuthz requieren privilegios auth (=x) en todos los atributos presentes en el filtro de búsqueda de los mapas regexp de URI (el lado derecho de las directivas authz-regexp). También se requieren privilegios Auth (=x) en el atributo authzTo de la identidad autorizante y/o en el atributo authzFrom de la identidad autorizada. En ambos casos, es la identidad autorizante la que requiere los privilegios (es decir, la identidad que se ha autenticado y ahora está tratando de realizar alguna operación utilizando los permisos de otra entidad).

En general, cuando se realiza una búsqueda interna con fines de autenticación o autorización, los privilegios específicos de búsqueda (ver los requisitos de acceso para la operación de búsqueda ilustrada anteriormente) se relajan a auth.

El control de acceso a las entradas de búsqueda lo realiza el frontend, por lo que es respetado completamente por todos los backends; para todas las demás operaciones y para la fase de descubrimiento de la operación de búsqueda, la semántica completa de ACL solo es compatible con los backends principales, es decir, slapd-mdb(5).

Algunos otros backends, como slapd-sql(5), pueden admitirlos completamente; otros solo pueden admitir una parte de la semántica descrita, o incluso diferir en algunos aspectos. Los detalles relevantes se describen en las páginas del manual específicas del backend.

PRECAUCIONES

Se recomienda encarecidamente utilizar explícitamente el <dnstyle> más apropiado en las cláusulas <what> y <who>, para evitar posibles especificaciones incorrectas del acceso r

CAVEATS

In general, the use of regex style DN matching is less efficient than using the exact or subtree styles. It is therefore recommended to use the latter styles whenever possible, for clarity as well as for performance (avoid unnecessary regex matching when an exact match suffices) reasons.

An administrator might create a rule of the form:

access to dn.regex="dc=example,dc=com"
	by ...

expecting it to match all entries in the subtree "dc=example,dc=com". However, this rule actually matches any DN which contains anywhere the substring "dc=example,dc=com". That is, the rule matches both "uid=joe,dc=example,dc=com" and "dc=example,dc=com,uid=joe".

To match the desired subtree, the rule would be more precisely written:

access to dn.regex="^(.+,)?dc=example,dc=com$"
	by ...

For performance reasons, it would be better to use the subtree style.

access to dn.subtree="dc=example,dc=com"
	by ...

When writing submatch rules, it may be convenient to avoid unnecessary regex <dnstyle> use; for instance, to allow access to the subtree of the user that matches the <what> clause, one could use

access to dn.regex="^(.+,)?uid=([^,]+),dc=example,dc=com$"
	by dn.regex="^uid=$2,dc=example,dc=com$$" write
	by ...

However, since all that is required in the <by> clause is substring expansion, a more efficient solution is

access to dn.regex="^(.+,)?uid=([^,]+),dc=example,dc=com$"
	by dn.exact,expand="uid=$2,dc=example,dc=com" write
	by ...

In fact, while a <dnstyle> of regex implies substring expansion, exact, as well as all the other DN specific <dnstyle> values, does not, so it must be explicitly requested.
