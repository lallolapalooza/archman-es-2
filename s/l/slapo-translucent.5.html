NOMBRE

slapo-translucent - Superposición de proxy translúcido para slapd

SINOPSIS

/etc/openldap/slapd.conf

DESCRIPCIÓN

La superposición de Proxy Translucente se puede utilizar con una base de datos de backend como slapd-mdb(5) para crear un "proxy translúcido". Las entradas recuperadas de un servidor LDAP remoto pueden tener algunos o todos los atributos anulados, o añadir nuevos atributos, mediante entradas en la base de datos local antes de ser presentadas al cliente.

Una operación de búsqueda se rellena primero con entradas del servidor LDAP remoto, cuyos atributos se anulan con cualquier atributo definido en la base de datos local. Las anulaciones locales pueden rellenarse con operaciones de añadir, modificar y modrdn, cuyo uso está restringido al usuario root.

Una operación de comparación realizará una comparación con los atributos definidos en el registro de la base de datos local (si los hay) antes de que se realice cualquier comparación con datos en la base de datos remota.

CONFIGURACIÓN

La superposición de Proxy Translucente utiliza una base de datos proxy, típicamente un (conjunto de) servidor(es) LDAP remoto(s), que se configura con las opciones que se muestran en slapd-ldap(5), slapd-meta(5) o similar. Estas opciones de slapd.conf son específicas de la superposición de Proxy Translucente; deben aparecer después de la directiva overlay que instancia la superposición translucent.

translucent_strict
Por defecto, los intentos de eliminar atributos en la base de datos local o remota se ignorarán silenciosamente. La directiva translucent_strict hace que estas modificaciones fallen con una Violación de Restricción.
translucent_no_glue
Esta opción de configuración deshabilita la creación automática de registros "glue" para una operación de añadir o modrdn, de modo que todos los padres de una entrada añadida a la base de datos local deben ser creados manualmente. Los registros de glue siempre se crean para una operación de modificar.
translucent_local <attr[,attr...]>
Especifique una lista de atributos que deben buscarse en la base de datos local cuando se utilicen en un filtro de búsqueda. Por defecto, los filtros de búsqueda solo son manejados por la base de datos remota. Con esta directiva, los filtros de búsqueda se dividirán en una porción local y una remota, y los atributos locales se buscarán localmente.
translucent_remote <attr[,attr...]>
Especifique una lista de atributos que deben buscarse en la base de datos remota cuando se utilicen en un filtro de búsqueda. Esta directiva complementa la directiva translucent_local. Los atributos pueden especificarse como locales y remotos si se desea.

Si no se especifican translucent_local ni translucent_remote, el comportamiento por defecto es buscar en la base de datos remota con el filtro de búsqueda completo. Si solo se especifica translucent_local, las búsquedas solo se ejecutarán en la base de datos local. Igualmente, si solo se especifica translucent_remote, las búsquedas solo se ejecutarán en la base de datos remota. En cualquier caso, tanto las entradas locales como las remotas correspondientes a un resultado de búsqueda se fusionarán antes de ser devueltas al cliente.

translucent_bind_local
Habilita la búsqueda de credenciales almacenadas localmente para el bind simple cuando el bind a la base de datos remota falla. Deshabilitado por defecto.
translucent_pwmod_local
Habilita la operación extendida de modificación de contraseña RFC 3062 en las credenciales almacenadas localmente. La operación solo se aplica a las entradas que existen en la base de datos remota. Deshabilitado por defecto.

CONTROL DE ACCESO

El control de acceso se delega a los DSA remotos o al backend de la base de datos local para las operaciones de autenticación y escritura. Se delega a los DSA remotos y al frontend para las operaciones de lectura. Las reglas de acceso locales que involucran datos devueltos por los DSA remotos deben diseñarse cuidadosamente. De hecho, las entradas son devueltas por los DSA remotos solo basándose en la fracción remota de los datos, basándose en la identidad con la que se realiza la operación. Como consecuencia, las reglas locales solo podrían permitir ver una porción de los datos remotos.

ADVERTENCIAS

La superposición de Proxy Translucente deshabilitará la verificación del esquema en la base de datos local, de modo que una entrada que consista en atributos de superposición no necesite adherirse al esquema completo.

Dado que la superposición translúcida no realiza ninguna reescritura de DN, las instancias de base de datos local y remota deben tener el mismo sufijo. Otras configuraciones probablemente fallarán con "No such object" y otros errores.

ARCHIVOS

/etc/openldap/slapd.conf
archivo de configuración por defecto de slapd

VER TAMBIÉN

slapd.conf(5), slapd-config(5), slapd-ldap(5).
