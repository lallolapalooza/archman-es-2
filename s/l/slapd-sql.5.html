NOMBRE

slapd-sql - Backend SQL para slapd

SINOPSIS

/etc/openldap/slapd.conf

DESCRIPCIÓN

El propósito principal de este backend de slapd(8) es PRESENTAR la información almacenada en algún SGBDR como un subárbol LDAP sin ninguna programación (algunos SQL y quizás procedimientos almacenados no se pueden considerar programación, de todos modos ;).

Es decir, por ejemplo, cuando usted (un proveedor de servicios de Internet) tiene información de cuenta que utiliza en un SGBDR y desea utilizar soluciones modernas que esperan dicha información en LDAP (para autenticar usuarios, realizar búsquedas de correo electrónico, etc.). O desea sincronizar o distribuir información entre diferentes sitios/aplicaciones que utilizan SGBDR y/o LDAP. O cualquier otra cosa...

NO está diseñado como un backend de propósito general que utiliza SGBDR en lugar de LMDB (como lo hace el backend MDB estándar), aunque se puede utilizar como tal con varias limitaciones. Puede consultar http://www.openldap.org/faq/index.cgi?file=378 (Preguntas Frecuentes de OpenLDAP/Preguntas Frecuentes Generales sobre LDAP/Directorios vs. bases de datos convencionales) para obtener más información sobre este punto.

La idea (detallada a continuación) es utilizar cierta metainformación para traducir consultas LDAP a consultas SQL, dejando intacto el esquema relacional, de modo que las aplicaciones antiguas puedan seguir utilizándolo sin modificaciones. Esto permite que las aplicaciones SQL y LDAP interactúen sin replicación e intercambien datos según sea necesario.

El backend SQL está diseñado para ser adaptable a prácticamente cualquier esquema relacional sin tener que cambiar el código fuente (a través de esa metainformación mencionada). Además, utiliza ODBC para conectarse a SGBDR y es altamente configurable para los dialectos SQL que puedan utilizar los SGBDR, por lo que puede utilizarse para la integración y distribución de datos en diferentes SGBDR, sistemas operativos, hosts, etc., en otras palabras, en entornos altamente heterogéneos.

Este backend es experimental.

CONFIGURACIÓN

Estas opciones de slapd.conf se aplican a la base de datos del backend SQL, lo que significa que deben seguir una línea "database sql" y aparecer antes de cualquier línea posterior de "backend" o "database". Otras opciones de base de datos no específicas de este backend se describen en la página del manual slapd.conf(5).

CONFIGURACIÓN DEL ORIGEN DE DATOS

dbname <nombre del origen de datos>
El nombre del origen de datos ODBC a utilizar.

dbhost <nombre del host>
dbpasswd <contraseña>
dbuser <nombre de usuario>

Las tres opciones anteriores generalmente no son necesarias, porque esta información se toma del origen de datos especificado por la directiva dbname. Permiten anular la configuración del origen de datos. Además, varios controladores de SGBDR tienden a requerir el paso explícito del usuario/contraseña, incluso si se proporcionan en el origen de datos (Nota: dbhost se ignora actualmente).

CONFIGURACIÓN DE ÁMBITO

Estas opciones especifican plantillas de consulta SQL para las búsquedas de ámbito.

subtree_cond <expresión SQL>
Especifica una plantilla de cláusula where utilizada para formar una condición de búsqueda de subárbol (dn="(.+,)?<dn>$"). Puede diferir de un dialecto SQL a otro (ver ejemplos). Por defecto, se construye basándose en el conocimiento de cómo normalizar los valores de DN (por ejemplo, "<upper_func>(ldap_entries.dn) LIKE CONCAT('%',?)"); consulte upper_func, upper_needs_cast, concat_pattern y strcast_func en "CONFIGURACIÓN DE AYUDA" para obtener más detalles.
children_cond <expresión SQL>
Especifica una plantilla de cláusula where utilizada para formar una condición de búsqueda de hijos (dn=".+,<dn>$"). Puede diferir de un dialecto SQL a otro (ver ejemplos). Por defecto, se construye basándose en el conocimiento de cómo normalizar los valores de DN (por ejemplo, "<upper_func>(ldap_entries.dn) LIKE CONCAT('%,',?)"); consulte upper_func, upper_needs_cast, concat_pattern y strcast_func en "CONFIGURACIÓN DE AYUDA" para obtener más detalles.
use_subtree_shortcut { SÍ | no }
No utilice la condición de subárbol cuando la base de búsqueda sea el sufijo de la base de datos y el ámbito sea subárbol; en su lugar, recopile todas las entradas.

CONFIGURACIÓN DE SENTENCIAS

Estas opciones especifican plantillas de consulta SQL para cargar metainformación de mapeo de esquema, añadir y eliminar entradas de ldap_entries, etc. Todas estas y subtree_cond deberían tener los valores predeterminados dados. Para el valor actual, se recomienda consultar las fuentes o la salida del registro cuando slapd se inicia con "-d 5" o superior. Tenga en cuenta que el número y el orden de los parámetros no deben cambiarse.

oc_query <expresión SQL>
La consulta que se utiliza para recopilar los datos de mapeo de objectClass de la tabla ldap_oc_mappings; consulte "METADATA UTILIZADA" para obtener más detalles. El valor predeterminado es "SELECT id, name, keytbl, keycol, create_proc, delete_proc, expect_return FROM ldap_oc_mappings".
at_query <expresión SQL>
La consulta que se utiliza para recopilar los datos de mapeo de attributeType de la tabla ldap_attr_mappings; consulte "METADATA UTILIZADA" para obtener más detalles. El valor predeterminado es "SELECT name, sel_expr, from_tbls, join_where, add_proc, delete_proc, param_order, expect_return FROM ldap_attr_mappings WHERE oc_map_id=?".
id_query <expresión SQL>
La consulta que se utiliza para mapear un DN a una entrada en la tabla ldap_entries; consulte "METADATA UTILIZADA" para obtener más detalles. El valor predeterminado es "SELECT id,keyval,oc_map_id,dn FROM ldap_entries WHERE <expresión de coincidencia de DN>", donde <expresión de coincidencia de DN> se construye basándose en el conocimiento de cómo normalizar los valores de DN (por ejemplo, "dn=?" si no hay medios para convertir a mayúsculas las cadenas; típicamente, se utiliza "<upper_func>(dn)=?"); consulte upper_func, upper_needs_cast, concat_pattern y strcast_func en "CONFIGURACIÓN DE AYUDA" para obtener más detalles.
insentry_stmt <expresión SQL>
La sentencia que se utiliza para insertar una nueva entrada en la tabla ldap_entries; consulte "METADATA UTILIZADA" para obtener más detalles. El valor predeterminado es "INSERT INTO ldap_entries (dn, oc_map_id, parent, keyval) VALUES (?, ?, ?, ?)".
delentry_stmt <expresión SQL>
La sentencia que se utiliza para eliminar una entrada existente de la tabla ldap_entries; consulte "METADATA UTILIZADA" para obtener más detalles. El valor predeterminado es "DELETE FROM ldap_entries WHERE id=?".
delobjclasses_stmt <expresión SQL>
La sentencia que se utiliza para eliminar el ID de una entrada existente de la tabla ldap_entry_objclasses; consulte "METADATA UTILIZADA" para obtener más detalles. El valor predeterminado es "DELETE FROM ldap_entry_objclasses WHERE entry_id=?".

upper_func <nombre de función SQL>
Especifica el nombre de una función que convierte un valor dado a mayúsculas. Esto se utiliza para coincidencias sin distinción entre mayúsculas y minúsculas cuando el SGBDR distingue entre mayúsculas y minúsculas. Puede diferir de un dialecto SQL a otro (por ejemplo, UCASE, UPPER o cualquier otro; véanse los ejemplos). Por defecto, no se utiliza ninguna, es decir, las cadenas no se convierten a mayúsculas, por lo que las coincidencias pueden distinguir entre mayúsculas y minúsculas.
upper_needs_cast { NO | yes }
Establezca esta directiva en yes si upper_func necesita una conversión explícita al aplicarse a cadenas literales. Se utiliza una conversión de tipo en la forma CAST (<argumento> AS VARCHAR(<longitud máxima del DN>)), donde <longitud máxima del DN> está integrada en back-sql; véase la macro BACKSQL_MAX_DN_LEN (actualmente 255; tenga en cuenta que el límite integrado de slapd, en la macro SLAP_LDAPDN_MAXLEN, se establece en 8192). Esto es experimental y puede cambiar en futuras versiones.
strcast_func <nombre de función SQL>
Especifica el nombre de una función que convierte un valor dado a una cadena para un ordenamiento adecuado. Esto se utiliza en sentencias "SELECT DISTINCT" para SGBDR fuertemente tipados con poca conversión implícita (como PostgreSQL), cuando se especifica una cadena literal. Esto es experimental y puede cambiar en futuras versiones.
concat_pattern <patrón>
Esta sentencia define el patrón que se utiliza para concatenar cadenas. El patrón DEBE contener dos signos de interrogación, '?', que serán reemplazados por las dos cadenas que deben concatenarse. El valor por defecto es CONCAT(?,?); una forma que se sabe que es muy portable (IBM db2, PostgreSQL) es ?||?, pero puede ser necesaria una conversión explícita al operar sobre cadenas literales: CAST(?||? AS VARCHAR(<longitud>)). En algunos SGBDR (IBM db2, MSSQL) la forma ?+? también funciona. Verifique cuidadosamente la documentación de su SGBDR o quédese con los ejemplos para los soportados. Esto es experimental y puede cambiar en futuras versiones.
aliasing_keyword <cadena>
Define la palabra clave de alias. Algunos SGBDR utilizan la palabra "AS" (por defecto), otros no utilizan ninguna.
aliasing_quote <cadena>
Define el carácter de comillas de la palabra clave de alias. Algunos SGBDR no requieren ninguna (por defecto), otros pueden requerir comillas simples o dobles.
has_ldapinfo_dn_ru { NO | yes }
Informa explícitamente al backend si la columna dn_ru (DN en forma inversa en mayúsculas) está presente en la tabla ldap_entries. Anula la comprobación automática (esto es necesario, por ejemplo, para PostgreSQL/unixODBC). Esto es experimental y puede cambiar en futuras versiones.
fail_if_no_mapping { NO | yes }
Cuando se establece en yes, fuerza que las operaciones de escritura de atributos fallen si no hay una correspondencia adecuada entre los atributos LDAP y los datos SQL disponibles. El comportamiento por defecto es ignorar los cambios que no se pueden mapear. No tiene impacto en el mapeo de objectClass, es decir, si la structuralObjectClass de una entrada no se puede mapear a SQL buscando su nombre en ldap_oc_mappings, una operación add fallará independientemente del interruptor fail_if_no_mapping; véase la sección "INFORMACIÓN METADATOS UTILIZADA" para más detalles. Esto es experimental y puede cambiar en futuras versiones.
allow_orphans { NO | yes }
Cuando se establece en yes, se pueden añadir entradas huérfanas (es decir, sin la entrada padre en la base de datos). Esta opción debe usarse con cuidado, posiblemente en conjunto con alguna regla especial en el lado del SGBDR que cree dinámicamente el padre faltante.
baseObject [ <nombre de archivo> ]
Instruye a la base de datos para que cree y gestione una entrada baseObject en memoria en lugar de buscar una en el SGBDR. Si se proporciona el argumento (opcional) <nombre de archivo>, la entrada se lee de ese archivo en formato LDIF(5); de lo contrario, se crea una entrada con objectClass extensibleObject basada en el contenido del RDN del baseObject. Esto es particularmente útil cuando la información de ldap_entries se almacena en una vista en lugar de en una tabla, y union no es compatible con vistas, por lo que la vista solo puede especificar una regla para calcular la estructura de la entrada para una objectClass. Este tema se discute con más detalle en la sección "INFORMACIÓN METADATOS UTILIZADA". Esto es experimental y puede cambiar en futuras versiones.
create_needs_select { NO | yes }
Instruye a la base de datos si la creación de entradas en la tabla ldap_entries necesita una selección posterior para recopilar el ID asignado automáticamente, en lugar de ser devuelto por un procedimiento almacenado.

fetch_attrs <lista de atributos>
fetch_all_attrs { NO | yes }

La primera sentencia permite proporcionar una lista de atributos que siempre deben ser recuperados además de los solicitados por cualquier operación específica, ya que son necesarios para el uso correcto del backend. Por ejemplo, aquí deben listarse todos los atributos utilizados en las ACL. La segunda sentencia es un atajo para requerir que todos los atributos se carguen siempre. Tenga en cuenta que los atributos generados dinámicamente, por ejemplo, hasSubordinates, entryDN y otros atributos dependientes de la implementación, **NO** se generan en este momento, por coherencia con el resto de slapd. Esto puede cambiar en el futuro.
check_schema { YES | no }
Instruye a la base de datos para que verifique la adherencia del esquema de las entradas después de las modificaciones, y la cadena de objectClass estructural cuando se construyen las entradas. Por defecto, se establece en yes.
sqllayer <nombre> [...]
Carga la capa <nombre> en una pila de ayudantes que se utilizan para mapear DNs de LDAP a representación SQL y viceversa. Los argumentos subsiguientes se pasan a la rutina de configuración de la capa. Esto es altamente experimental y debe usarse con extrema precaución. La API de las capas aún no está fijada, por lo que no está publicada.
autocommit { NO | yes }
Activa el autocommit; por defecto, está desactivado.

INFORMACIÓN METADATOS UTILIZADA

Casi todo lo mencionado a continuación se ilustra en ejemplos ubicados en el directorio servers/slapd/back-sql/rdbms_depend/ en el árbol de código fuente de OpenLDAP, y contiene scripts para generar bases de datos de ejemplo para Oracle, MS SQL Server, mySQL y más (incluyendo PostgreSQL e IBM db2).

Lo primero que hay que organizar es qué conjunto de clases de objetos LDAP pueden presentar la información de su SGBDR.

La forma más sencilla es crear una objectClass para cada entidad que tuviera en el diagrama ER al diseñar su esquema relacional. Cualquier esquema relacional, por muy normalizado que esté, se diseñó a partir de algún modelo del dominio de su aplicación (por ejemplo, cuentas, servicios, etc. en un ISP), y se utiliza en términos de sus entidades, no solo tablas de esquemas normalizados. Esto significa que para cada atributo de cada una de estas instancias, hay una consulta SQL efectiva que carga sus valores.

También puede desear que sus objectClasses se ajusten a algunos de los esquemas estándar como inetOrgPerson, etc.

Sin embargo, cuando lo piensa, debemos definir una forma de traducir las solicitudes de operación LDAP a (una serie de) consultas SQL. Tratemos la operación SEARCH.

Ejemplo: Supongamos que almacenamos información sobre personas que trabajan en nuestra organización en dos tablas:

  PERSONAS              TELEFONOS
  ----------           -------------
  id entero            id entero
  nombre varchar       pers_id entero references personas(id)
  apellido varchar     telefono
  segundo_nombre varchar
  ...

(TELEFONOS contiene números de teléfono asociados a personas). Una persona puede tener varios números, entonces TELEFONOS contiene varios registros con pers_id correspondiente, o ningún número (y ningún registro en TELEFONOS con dicho pers_id). Una objectClass LDAP para presentar dicha información podría verse así:

  persona
  -------
  DEBE cn
  PUEDE telephoneNumber $ firstName $ lastName
  ...

Para recuperar todos los valores para el atributo cn dada una identificación de persona, construimos la consulta:

  SELECT CONCAT(persons.first_name,' ',persons.last_name)
      AS cn FROM persons WHERE persons.id=?

para telephoneNumber podemos usar:

  SELECT phones.phone AS telephoneNumber FROM persons,phones
      WHERE persons.id=phones.pers_id AND persons.id=?

Si quisiéramos dar servicio a solicitudes LDAP con filtros como (telephoneNumber=123*), construiríamos algo como:

  SELECT ... FROM persons,phones
      WHERE persons.id=phones.pers_id
          AND persons.id=?
          AND phones.phone like '%1%2%3%'

(observe cómo la coincidencia de telephoneNumber se expande en múltiples comodines para tener en cuenta caracteres influyentes intercalados como espacios, guiones y otros; esto ocurre por diseño porque telephoneNumber se define después de una sintaxis especialmente reconocida). Por lo tanto, si tuviéramos información sobre qué tablas contienen valores para cada atributo, cómo unir estas tablas y organizar estos valores, podríamos intentar generar automáticamente estas sentencias y traducir los filtros de búsqueda a cláusulas WHERE de SQL.

Para almacenar dicha información, añadimos tres tablas más a nuestro esquema y las llenamos con datos (ver ejemplos):

  ldap_oc_mappings (algunas columnas no se listan por claridad)
  ---------------
  id=1
  name="person"
  keytbl="persons"
  keycol="id"

Esta tabla define un mapeo entre objectclass (su nombre se guarda en la columna "name"), y una tabla que contiene la clave primaria para las entidades correspondientes. Por ejemplo, en nuestro ejemplo, la entidad persona

slapd-sql(5)

NAME
slapd-sql - SQL backend for OpenLDAP

SYNOPSIS
slapd-sql is a backend for the slapd(8) server that allows users and group
information to be stored in a relational database. It is designed to
replace the traditional LDAP database with a SQL database.

DESCRIPTION
The SQL backend allows slapd to interact with a SQL database for storing
and retrieving LDAP entries. This can be useful for migrating existing
LDAP data to a SQL database, or for integrating LDAP with existing SQL
applications.

The SQL backend uses a mapping between LDAP attributes and SQL columns,
and between LDAP entries and SQL tables. This mapping is defined in the
OpenLDAP configuration file.

CONFIGURATION
The SQL backend is configured in the slapd.conf file. The following
options are available:

database sql
Specifies that the SQL backend is being used.
sql_dialect
Specifies the SQL dialect to be used (e.g., MySQL, PostgreSQL,
SQLite).
sql_dsn
Specifies the Data Source Name (DSN) for the SQL database.
This includes the database type, host, port, database name, username,
and password.
sql_schema_table
Specifies the name of the table that stores the LDAP schema.
sql_entry_table
Specifies the name of the table that stores the LDAP entries.
sql_attribute_table
Specifies the name of the table that stores the LDAP attributes.
sql_oc_support
Specifies whether to support object classes.
sql_require_thread
Specifies whether to require thread-local storage.

DATA SOURCE CONFIGURATION
The sql_dsn option is used to specify the connection details
for the SQL database. The format of the DSN depends on the SQL dialect
being used. For example, for MySQL, it might look like:

sql_dsn mysql://user:password@host:port/database

SCOPING CONFIGURATION
The SQL backend supports scoping of search results based on the base DN
of the search. This is configured using the
sql_base_dn directive in the slapd.conf file.

STATEMENT CONFIGURATION
The SQL backend uses SQL statements to perform LDAP operations. These
statements can be customized using the following directives:

sql_entry_statement
The SQL statement to use for retrieving entries.
sql_attribute_statement
The SQL statement to use for retrieving attributes.
sql_search_statement
The SQL statement to use for searching entries.
sql_add_statement
The SQL statement to use for adding entries.
sql_delete_statement
The SQL statement to use for deleting entries.
sql_mod_statement
The SQL statement to use for modifying entries.

HELPER CONFIGURATION
The SQL backend can use helper functions to assist with certain
operations, such as generating unique IDs or encoding passwords. These
helpers are configured using the
sql_helper directive.

METAINFORMATION USED
The SQL backend uses the following meta-information to map LDAP entries
to SQL tables and columns:

  • objectClass: Maps to the object class of the entry.
  • cn, uid, mail, etc.: Maps to attributes
    of the entry.
  • DN: Maps to the Distinguished Name of the entry.

TYPICAL SQL BACKEND OPERATION
When a client performs an LDAP operation (e.g., search, add, modify,
delete), the SQL backend translates the operation into one or more SQL
statements. These statements are then executed against the SQL database.
The results of the SQL query are then translated back into LDAP entries
and returned to the client.

COMMON TECHNIQUES

  1. Table Mapping: Designing SQL tables that closely mirror the structure of your
    LDAP directory.
  2. Attribute Mapping: Defining how LDAP attributes map to specific columns within your
    SQL tables.
  3. Statement Customization: Writing efficient SQL queries tailored to your database schema for
    various LDAP operations.
  4. Schema Definition: Ensuring your SQL schema supports the necessary object classes and
    attributes for your LDAP use case.
  5. Performance Tuning: Optimizing SQL queries and database indexing for faster LDAP
    response times.

CAVEATS

  • Performance: Depending on the complexity of the mapping and the efficiency of
    the SQL queries, performance might be lower than a native LDAP
    backend.
  • Schema Complexity: Mapping complex LDAP schemas to relational databases can be
    challenging.
  • Data Integrity: Maintaining data consistency between the LDAP view and the SQL
    database requires careful configuration.
  • Transaction Management: Handling complex transactions involving multiple LDAP operations
    can be intricate.
  • Attribute Uniqueness: Ensuring uniqueness for attributes that are unique in LDAP but
    might not be naturally unique in SQL tables requires specific
    handling.

BUGS
Report bugs to the OpenLDAP bug tracking system at
https://bugzilla.openldap.org/.

PROXY CACHE OVERLAY
The SQL backend can be used in conjunction with the
proxycache overlay to improve the performance of read-heavy
workloads. The overlay caches LDAP entries retrieved from the SQL
database, reducing the number of direct database queries.

EXAMPLES
A minimal configuration might look like this: 

database sql
sql_dialect mysql
sql_dsn mysql://user:password@localhost/ldap_db
sql_entry_table users
sql_attribute_table user_attributes

For more complex configurations, refer to the OpenLDAP documentation.

ACCESS CONTROL
Access control to entries is handled by OpenLDAP's standard access control
lists (ACLs), which are applied to the entries returned by the SQL backend.

FILES

  • slapd.conf: The main configuration file for slapd.
  • SQL Database Schema: The definition of the tables and columns used
    by the SQL backend.
