SLAPD.CONF(5) Manual de formatos de archivo SLAPD.CONF(5)

NOMBRE

slapd.conf - archivo de configuración para slapd, el demonio LDAP autónomo

SINOPSIS

/etc/openldap/slapd.conf

DESCRIPCIÓN

El archivo /etc/openldap/slapd.conf contiene información de configuración para el demonio slapd(8). Este archivo de configuración también es utilizado por las herramientas SLAPD slapacl(8), slapadd(8), slapauth(8), slapcat(8), slapdn(8), slapindex(8), slapmodify(8) y slaptest(8).

El archivo slapd.conf consiste en una serie de opciones de configuración globales que se aplican a slapd en su totalidad (incluyendo todos los backends), seguidas por cero o más definiciones de backend de base de datos que contienen información específica de una instancia de backend. Las opciones de configuración no distinguen entre mayúsculas y minúsculas; su valor, según el caso, puede distinguir entre mayúsculas y minúsculas.

El formato general de slapd.conf es el siguiente:

    # comentario - estas opciones se aplican a todas las bases de datos
    <opciones de configuración globales>
    # primera definición de base de datos y opciones de configuración
    database <tipo de backend 1>
    <opciones de configuración específicas del backend 1>
    # definiciones de bases de datos y opciones de configuración subsiguientes
    ...

Se pueden incluir tantas secciones específicas de backend como se desee. Las opciones globales pueden ser anuladas en un backend (para opciones que aparecen más de una vez, se utiliza la última aparición en el archivo slapd.conf).

Si una línea comienza con espacio en blanco, se considera una continuación de la línea anterior. Ninguna línea física debe tener más de 2000 bytes de longitud.

Las líneas en blanco y las líneas de comentario que comienzan con el carácter '#' se ignoran. Nota: las líneas de continuación se desenrollan antes de aplicar el procesamiento de comentarios.

Los argumentos en las líneas de configuración se separan por espacios en blanco. Si un argumento contiene espacios en blanco, debe ir entre comillas dobles. Si un argumento contiene una comilla doble (`"') o un carácter de barra invertida (`\'), el carácter debe ir precedido por una barra invertida.

Las opciones de configuración específicas se discuten a continuación en Opciones de Configuración Globales, Opciones Generales de Backend y Opciones Generales de Base de Datos. Las opciones específicas de backend se discuten en las páginas del manual slapd-<backend>(5). Consulte la "Guía del Administrador de OpenLDAP" para obtener más detalles sobre el archivo de configuración de slapd.

OPCIONES DE CONFIGURACIÓN GLOBALES

Las opciones descritas en esta sección se aplican a todos los backends, a menos que se anulen específicamente en una definición de backend. Los argumentos que deben reemplazarse por texto real se muestran entre corchetes <>.

access to <qué> [ by <quién> <acceso> <control> ]+
Concede acceso (especificado por <acceso>) a un conjunto de entradas y/o atributos (especificado por <qué>) por uno o más solicitantes (especificado por <quién>). Si no hay controles de acceso presentes, la política predeterminada permite que cualquiera y todos lean cualquier cosa, pero restringe las actualizaciones a rootdn. (por ejemplo, "access to * by * read"). ¡El rootdn siempre puede leer y escribir TODO! Consulte slapd.access(5) y la "Guía del Administrador de OpenLDAP" para obtener detalles.
allow <características>
Especifica un conjunto de características (separadas por espacios en blanco) para permitir (predeterminado: ninguna). bind_v2 permite la aceptación de solicitudes de bind LDAPv2. Tenga en cuenta que slapd(8) no implementa verdaderamente LDAPv2 (RFC 1777), ahora Histórico (RFC 3494). bind_anon_cred permite el bind anónimo cuando las credenciales no están vacías (por ejemplo, cuando el DN está vacío). bind_anon_dn permite el bind no autenticado (anónimo) cuando el DN no está vacío. update_anon permite que las operaciones de actualización no autenticadas (anónimas) se procesen (sujeto a controles de acceso y otros límites administrativos). proxy_authz_anon permite que el control de autorización proxy anónimo no autenticado se procese (sujeto a controles de acceso, autorización y otros límites administrativos).
argsfile <nombre_archivo>
El nombre (absoluto) de un archivo que contendrá la línea de comandos del servidor slapd (nombre del programa y opciones).
attributeoptions [nombre-opción]...
Define opciones de atributo de etiquetado o prefijos de etiqueta/rango. Las opciones no deben terminar con `-', los prefijos deben terminar con `-'. El prefijo `lang-' está predefinido. Si utiliza la directiva attributeoptions, `lang-' ya no se definirá y deberá especificarlo explícitamente si desea que se defina.

Una descripción de atributo con una opción de etiquetado es un subtipo de esa descripción de atributo sin la opción. Excepto por eso, las opciones definidas de esta manera no tienen semántica especial. Los prefijos definidos de esta manera funcionan como las opciones `lang-': Definen un prefijo para las opciones de etiquetado que comienzan con el prefijo. Es decir, si define el prefijo `x-foo-', puede usar la opción `x-foo-bar'. Además, en una búsqueda o comparación, un prefijo o nombre de rango (con un `-` al final) coincide con todas las opciones que comienzan con ese nombre, así como con la opción con el nombre de rango sin el `-` al final. Es decir, `x-foo-bar-' coincide con `x-foo-bar' y `x-foo-bar-baz'.

RFC 4520 reserva opciones que comienzan con `x-' para experimentos privados. Otras opciones deben registrarse en IANA, consulte RFC 4520 sección 3.5. OpenLDAP también tiene la opción `binary' incorporada, pero esta es una opción de transferencia, no una opción de etiquetado.

(Consulte la descripción de objectidentifier).
authid-rewrite<cmd> <args>
Utilizado por el marco de autenticación para convertir nombres de usuario simples en un DN de LDAP utilizado para fines de autorización. Su propósito es análogo al de authz-regexp (ver abajo). El prefijo authid- va seguido de un conjunto de reglas análogas a las descritas en slapo-rwm(5) para la reescritura de datos (reemplace el prefijo rwm- por authid-). Las reglas de authid-rewrite<cmd> y authz-regexp no deben mezclarse.
authz-policy <política>
Se utiliza para especificar qué reglas se utilizan para la Autorización Proxy. La autorización proxy permite a un cliente autenticarse ante el servidor utilizando las credenciales de un usuario, pero especificando una identidad diferente para fines de autorización y control de acceso. Esencialmente, permite que el usuario A inicie sesión como el usuario B, utilizando la contraseña del usuario A. El indicador none deshabilita la autorización proxy. Esta es la configuración predeterminada. El indicador from utilizará las reglas del atributo authzFrom del DN de autorización. El indicador to utilizará las reglas del atributo authzTo del DN de autenticación. El indicador any, un alias para el valor obsoleto de both, permitirá cualquiera de las opciones anteriores, lo que tenga éxito primero (comprobado en la secuencia to, from. El indicador all requiere que ambas autorizaciones tengan éxito.
Las reglas son mecanismos para especificar qué identidades tienen permitido realizar autorización proxy. El atributo authzFrom en una entrada especifica qué otros usuarios tienen permitido iniciar sesión proxy en esta entrada. El atributo authzTo en una entrada especifica qué otros usuarios puede autorizar este usuario. El uso de reglas authzTo puede ser fácilmente abusado si se permite a los usuarios escribir valores arbitrarios en este atributo. En general, el atributo authzTo debe protegerse con ACLs para que solo los usuarios privilegiados puedan modificarlo. El valor de authzFrom y authzTo describe una identidad o un conjunto de i
Identidades; puede tomar cinco formas:
ldap:///<base>??[<scope>]?<filter>
dn[.<dnstyle>]:<patrón>
u[.<mech>[/<realm>]]:<patrón>
grupo[/objectClass[/attributeType]]:<patrón>
<patrón>

<dnstyle>:={exacto|unilevel|hijos|subárbol|regex}

La primera forma es una URI LDAP válida donde las porciones <host>:<puerto>, <attrs> y <extensions> deben estar ausentes, para que la búsqueda se realice localmente en authzFrom o authzTo.

La segunda forma es un DN. Los modificadores opcionales de dnstyle exacto, unilevel, hijos y subárbol proporcionan coincidencias exactas, unilevel, de hijos y de subárbol, que hacen que <patrón> se normalice según las reglas de normalización de DN. El modificador especial dnstyle regex hace que <patrón> se trate como una expresión regular POSIX (''extendida''), como se describe en regex(7) y/o re_format(7). Un patrón de * significa cualquier DN no anónimo.

La tercera forma es un id SASL. Los campos opcionales <mech> y <realm> permiten la especificación de un mecanismo SASL, y eventualmente un realm SASL, para aquellos mecanismos que lo soporten. La necesidad de permitir la especificación de un mecanismo sigue siendo objeto de debate, y se desaconseja encarecidamente a los usuarios que confíen en esta posibilidad.

La cuarta forma es una especificación de grupo. Consiste en la palabra clave group, seguida opcionalmente de la especificación de la objectClass y attributeType del grupo. El objectClass por defecto es groupOfNames. El attributeType por defecto es member. El grupo con DN <patrón> se busca con ámbito base, filtrado por la objectClass especificada. Los valores del attributeType resultante se buscan para el DN afirmado.

La quinta forma se proporciona por compatibilidad hacia atrás. Si no se proporciona ningún tipo de identidad, es decir, solo está presente <patrón>, se asume un DN exacto; como consecuencia, <patrón> se somete a la normalización de DN.

Dado que la interpretación de authzFrom y authzTo puede afectar a la seguridad, se recomienda encarecidamente a los usuarios que establezcan explícitamente el tipo de especificación de identidad que se está utilizando. Un subconjunto de estas reglas puede utilizarse como tercer argumento en la sentencia authz-regexp (ver más abajo); en particular, la URI, siempre que resulte en una única entrada, y las formas dn.exacto:<dn>.

authz-regexp <coincidencia> <reemplazo>
Utilizado por el framework de autenticación para convertir nombres de usuario simples, como los proporcionados por el subsistema SASL, o extraídos de certificados en el caso de SASL EXTERNAL basado en certificados, o proporcionados dentro del control RFC 4370 "proxied authorization", a un DN LDAP utilizado para fines de autorización. Tenga en cuenta que el DN resultante no necesita referirse a una entrada existente para ser considerado válido. Cuando se recibe una solicitud de autorización del subsistema SASL, se toman el USERNAME, REALM y MECHANISM de SASL, cuando están disponibles, y se combinan en un nombre de la forma
UID=<username>[[,CN=<realm>],CN=<mechanism>],CN=auth
Este nombre se compara luego con la expresión regular POSIX (''extendida'') de coincidencia, y si la coincidencia es exitosa, el nombre se reemplaza con la cadena de reemplazo. Si hay cadenas comodín en la expresión regular de coincidencia que están entre paréntesis, por ejemplo,
UID=([^,]*),CN=.*
entonces la porción del nombre que coincidió con el comodín se almacenará en la variable comodín numerada $1. Si hay otras cadenas comodín entre paréntesis, las cadenas coincidentes estarán en $2, $3, etc. hasta $9. Los comodines pueden ser utilizados entonces en la cadena de reemplazo, por ejemplo,
UID=$1,OU=Accounts,DC=example,DC=com
El nombre reemplazado puede ser un DN, es decir, una cadena prefijada por "dn:", o una URI LDAP. Si es esto último, el servidor utilizará la URI para buscar en sus propias bases de datos y, si la búsqueda devuelve exactamente una entrada, el nombre se reemplazará por el DN de esa entrada. La URI LDAP no debe tener componentes hostport, attrs o extensions, pero el filtro es obligatorio, por ejemplo,
ldap:///OU=Accounts,DC=example,DC=com??one?(UID=$1)
La porción de protocolo de la URI debe ser estrictamente ldap. Tenga en cuenta que esta búsqueda está sujeta a controles de acceso. Específicamente, la identidad de autenticación debe tener acceso "auth" en el sujeto.

Se pueden dar múltiples opciones de authz-regexp en el archivo de configuración para permitir múltiples patrones de coincidencia y reemplazo. Los patrones de coincidencia se verifican en el orden en que aparecen en el archivo, deteniéndose en la primera coincidencia exitosa.

concurrency <entero>
Especifica un nivel de concurrencia deseado. Proporcionado al sistema de hilos subyacente como una pista. El valor predeterminado es no proporcionar ninguna pista. Esta configuración solo tiene sentido en algunas plataformas donde no hay una correspondencia uno a uno entre hilos de usuario e hilos del kernel.
conn_max_pending <entero>
Especifica el número máximo de solicitudes pendientes para una sesión anónima. Si las solicitudes se envían más rápido de lo que el servidor puede procesarlas, se pondrán en cola hasta este límite. Si se excede el límite, la sesión se cerrará. El valor predeterminado es 100.
conn_max_pending_auth <entero>
Especifica el número máximo de solicitudes pendientes para una sesión autenticada. El valor predeterminado es 1000.
defaultsearchbase <dn>
Especifica una base de búsqueda predeterminada a utilizar cuando el cliente envía una solicitud de búsqueda que no es base con un DN base vacío. Las solicitudes de búsqueda de ámbito base con un DN base vacío no se ven afectadas.
disallow <características>
Especifica un conjunto de características (separadas por espacios en blanco) a desautorizar (predeterminado ninguna). bind_anon deshabilita la aceptación de solicitudes de bind anónimo. Tenga en cuenta que esta configuración no prohíbe el acceso anónimo al directorio (ver "require authc"). bind_simple deshabilita la autenticación simple (bind). tls_2_anon deshabilita la forzadura de la sesión a estado anónimo (ver también tls_authc) al recibir la operación StartTLS. tls_authc deshabilita la operación StartTLS si está autenticada (ver también tls_2_anon). proxy_authz_non_critical deshabilita la aceptación del control proxied authorization (RFC4370) con criticidad establecida en FALSE. dontusecopy_non_critical deshabilita la aceptación del control dontUseCopy (en desarrollo) con criticidad establecida en FALSE.

ditcontentrule ( <oid> [NAME <nombre>] [DESC <descripción>] [OBSOLETO] [AUX <oids>] [MUST <oids>] [MAY <oids>] [NOT <oids>] )

Especifica una Regla de Contenido DIT utilizando la sintaxis LDAPv3 definida en RFC 4512. El analizador slapd extiende la definición de RFC 4512 permitiendo el uso de formas de cadena así como OIDs numéricos para el OID del atributo y el OID de la sintaxis del atributo. (Ver la descripción de objectidentifier).
gentlehup { on | off }
Una señal SIGHUP solo causará un intento de apagado "suave": Slapd dejará de escuchar nuevas conexiones, pero no cerrará las conexiones con los clientes actuales. Sin embargo, las futuras operaciones de escritura devolverán "unwilling-to-perform". Slapd terminará cuando todos los clientes hayan cerrado sus conexiones (si es que lo hacen), o, como antes, si recibe una señal SIGTERM. Esto puede ser útil si desea terminar el servidor y iniciar un nuevo servidor slapd con otra base de datos, sin interrumpir a los clientes actualmente activos. El valor predeterminado es off. Puede que desee utilizar idletimeout junto con esta opción.
idletimeout <entero>
Especifica el número de segundos a esperar antes de cerrar forzosamente una conexión de cliente inactiva. Un valor de 0 deshabilita esta característica. El valor predeterminado es 0. También puede que desee establecer la opción writetimeout.
include <nombre de archivo>
Lee información de configuración adicional del archivo dado antes de continuar con la siguiente línea del archivo actual.
index_hash64 { on | off }
Utiliza un hash de 64 bits para la indexación. El valor predeterminado es utilizar hashes de 32 bits. Estos hashes se utilizan para la indexación de igualdad y subcadenas. La versión de 64 bits puede ser necesaria para evitar colisiones de índices cuando el número de valores indexados supera los ~64 millones. (Tenga en cuenta que la indexación de subcadenas genera múltiples valores de índice por valor de atributo real.) Los índices generados con hashes de 32 bits son incompatibles con la versión de 64 bits, y viceversa. Todas las bases de datos existentes deben ser recargadas completamente al cambiar esta configuración. Esta directiva solo es compatible con CPU de 64 bits.
index_intlen <entero>
Especifica la longitud de la clave para los índices de enteros ordenados. Los bytes más significativos del entero binario se utilizarán para las claves de índice. El valor predeterminado es 4, que proporciona indexación exacta para valores de 31 bits. Se utiliza una representación de punto flotante para indexar valores demasiado grandes.

INDEX ATTRIBUTES

The following attributes may be indexed to improve the performance of searches.

index_substr_if_maxlen <integer>
Especifica la longitud máxima para los índices subiniciales y subfinales. Solo esta cantidad de caracteres de un valor de atributo será procesada por las funciones de indexación; cualquier carácter excedente se ignora. El valor predeterminado es 4.
index_substr_if_minlen <integer>
Especifica la longitud mínima para los índices subiniciales y subfinales. Un valor de atributo debe tener al menos esta cantidad de caracteres para ser procesado por las funciones de indexación. El valor predeterminado es 2.
index_substr_any_len <integer>
Especifica la longitud utilizada para los índices subcualquiera. Un valor de atributo debe tener al menos esta cantidad de caracteres para ser procesado. Los valores de atributo más largos que esta longitud se procesarán en segmentos de esta longitud. El valor predeterminado es 4. El índice subcualquiera también se utilizará en las búsquedas de índices subiniciales y subfinales cuando la cadena del filtro sea más larga que el valor de index_substr_if_maxlen.
index_substr_any_step <integer>
Especifica los pasos utilizados en las búsquedas de índices subcualquiera. Este valor establece el desplazamiento para los segmentos de una cadena de filtro que se procesan para una búsqueda de índice subcualquiera. El valor predeterminado es 2. Por ejemplo, con los valores predeterminados, una búsqueda utilizando este filtro "cn=*abcdefgh*" generaría búsquedas de índice para "abcd", "cdef" y "efgh".

Nota: El soporte de indexación depende del backend particular en uso. Además, cambiar estas configuraciones generalmente requerirá eliminar cualquier índice que dependa de estos parámetros y recrearlos con slapindex(8).

LDAP SYNTAX

ldapsyntax ( <oid> [DESC <description>] [X-SUBST <substitute-syntax>] )

Especifica una sintaxis LDAP utilizando la sintaxis LDAPv3 definida en RFC 4512. El analizador de slapd extiende la definición de RFC 4512 permitiendo que se utilicen formas de cadena, así como OIDs numéricos, para el OID de la sintaxis. (Consulte la descripción de objectidentifier). El analizador de slapd también respeta la extensión X-SUBST (una extensión específica de OpenLDAP), que permite utilizar la declaración ldapsyntax para definir una sintaxis no implementada junto con otra sintaxis, el valor de extensión substitute-syntax, como su reemplazo temporal. El substitute-syntax debe estar definido. Esto permite definir tipos de atributos que utilizan sintaxis no implementadas utilizando el OID de sintaxis correcto. A menos que se utilice X-SUBST, esta declaración de configuración resultaría en un error, ya que no se asociarían manejadores a la estructura de sintaxis resultante.
LISTENER THREADS
listener-threads <integer>
Especifica el número de hilos a utilizar para el gestor de conexiones. El valor predeterminado es 1 y esto es típicamente adecuado para hasta 16 núcleos de CPU. El valor debe establecerse como una potencia de 2.
LOCAL SECURITY STRENGTH FACTOR
localSSF <SSF>
Especifica el Factor de Fuerza de Seguridad (SSF) que se debe asignar a las sesiones LDAP locales, como las del listener ldapi://. Para una descripción de los valores SSF, consulte la descripción de la opción minssf de sasl-secprops. El valor predeterminado es 71.
LOGGING
logfile <filename>
Especifica un archivo para registrar los mensajes de depuración de slapd. Estos mensajes no están relacionados con los mensajes expuestos por el parámetro de configuración loglevel. Esta configuración solo afecta al demonio slapd y no tiene efecto en las herramientas de línea de comandos. Por defecto, estos mensajes solo van a stderr y no se registran en ningún otro lugar. Especificar un logfile copia los mensajes tanto a stderr como al logfile.
logfile-format debug|syslog-utc|syslog-localtime|rfc3339-utc
Especifica el formato del prefijo para los mensajes escritos en el logfile. El formato debug es el formato normal utilizado para los mensajes de depuración de slapd, con una marca de tiempo en hexadecimal, seguida de un ID de hilo. Las otras opciones son utilizar prefijos estilo syslog(3), con marcas de tiempo en UTC o en la zona horaria local. El valor predeterminado es el formato debug.
logfile-only on | off
Especifica que los mensajes de depuración solo deben ir al logfile configurado y no a stderr.
logfile-rotate <max> <Mbytes> <hours>
Especifica la rotación automática para el logfile configurado como el número máximo de archivos de log antiguos a conservar, un tamaño máximo en megabytes permitido para que un logfile crezca antes de la rotación, y una edad máxima en horas para que un logfile sea utilizado antes de la rotación. El número máximo debe estar en el rango 1-99. Establecer Mbytes o hours a cero deshabilita la comprobación de tamaño o edad, respectivamente. Al menos uno de Mbytes o hours debe ser distinto de cero. Por defecto, no se realizará ninguna rotación automática.
loglevel <integer> [...]
Especifica el nivel en el que las declaraciones de depuración y las estadísticas de operación deben ser registradas en el sistema (actualmente registradas en la instalación syslogd(8) LOG_LOCAL4). Deben considerarse subsistemas en lugar de niveles de registro cada vez más verbosos. Algunos mensajes con mayor prioridad se registran independientemente del loglevel configurado tan pronto como se configure cualquier registro. Los niveles de registro son aditivos y los niveles disponibles son:
1
(0x1 trace) rastreo de llamadas a funciones
2
(0x2 packets) depuración del manejo de paquetes
4
(0x4 args) depuración intensa (argumentos de función)
8
(0x8 conns) gestión de conexiones
16
(0x10 BER) impresión de paquetes enviados y recibidos
32
(0x20 filter) procesamiento de filtros de búsqueda
64
(0x40 config) procesamiento del archivo de configuración
128
(0x80 ACL) procesamiento de listas de control de acceso
256
(0x100 stats) conexiones, operaciones LDAP, resultados (recomendado)
512
(0x200 stats2) entradas de registro stats2 enviadas
1024
(0x400 shell) impresión de comunicación con backends de shell
2048
(0x800 parse) análisis de entradas
16384
(0x4000 sync) replicación LDAPSync
32768
(0x8000 none) solo mensajes que se registran independientemente del nivel de registro establecido
El nivel de registro deseado se puede introducir como un solo entero que combina los niveles deseados (ORed), tanto en notación decimal como hexadecimal, como una lista de enteros (que se combinan internamente), o como una lista de los nombres que se muestran entre paréntesis, de modo que 
    loglevel 129
      loglevel 0x81
      loglevel 128 1
      loglevel 0x80 0x1
      loglevel acl trace
son equivalentes. La palabra clave any puede usarse como atajo para habilitar el registro en todos los niveles (equivalente a -1). La palabra clave none, o su representación entera equivalente, hace que los mensajes que se registran independientemente del loglevel configurado se registren. De hecho, si el loglevel se establece en 0, no ocurre ningún registro, por lo que al menos el nivel none es necesario para que se registren los mensajes de alta prioridad.

Tenga en cuenta que los niveles packets, BER y parse solo están disponibles como salida de depuración en stderr y no se envían a syslog.

El loglevel predeterminado es stats. Este nivel generalmente también debe incluirse al usar otros niveles de registro, para ayudar a analizar los registros.

MODULE LOADING

Especifica el nombre de un módulo cargable dinámicamente para cargar y cualquier argumento adicional si es compatible con el módulo. OBJECT CLASS DEFINITION

objectclass ( <oid> [NAME <name>] [DESC <description>] [OBSOLETE] [SUP <oids>] [{ ABSTRACT | STRUCTURAL | AUXILIARY }] [MUST <oids>] [MAY <oids>] )

Define un nombre de cadena que equivale al OID dado. La cadena se puede usar en lugar del OID numérico en las definiciones de objectclass y attribute. El nombre también se puede usar con un sufijo de la forma ":xx" en cuyo caso se utilizará el valor "oid.xx".
PASSWORD HASHING
password-hash <hash> [<hash>...]
Esta opción configura uno o más hashes para ser utilizados en la generación de contraseñas de usuario almacenadas en el atributo userPassword durante el procesamiento de Operaciones Extendidas de Modificación de Contraseña LDAP (RFC 3062). El <hash> debe ser uno de {SSHA}, {SHA}, {SMD5}, {MD5}, {CRYPT} y {CLEARTEXT}. El valor predeterminado es {SSHA}.

{SHA} y {SSHA} utilizan el algoritmo SHA-1 (FIPS 160-1), el último con una semilla.

{MD5} y {SMD5} utilizan el algoritmo MD5 (RFC 1321), el último con una semilla.

{CRYPT} utiliza la función crypt(3).

{CLEARTEXT} indica que la nueva contraseña debe agregarse a userPassword como texto plano.

Tenga en cuenta que esta opción no altera el manejo normal de aplicaciones de usuario de u
password-crypt-salt-format <formato>
Especifica el formato de la sal que se pasa a crypt(3) al generar contraseñas {CRYPT} (ver password-hash) durante el procesamiento de las Operaciones Extendidas de Modificación de Contraseña LDAP (RFC 3062).

Esta cadena debe estar en formato sprintf(3) y puede incluir una (y solo una) conversión %s. Esta conversión será sustituida por una cadena de caracteres aleatorios de [A-Za-z0-9./]. Por ejemplo, "%.2s" proporciona una sal de dos caracteres y "$1$%.8s" indica a algunas versiones de crypt(3) que utilicen un algoritmo MD5 y proporciona 8 caracteres aleatorios de sal. El valor predeterminado es "%s", que proporciona 31 caracteres de sal.

Se utiliza para especificar las propiedades de seguridad de Cyrus SASL. El flag none (sin ninguna otra propiedad) provoca que las propiedades predeterminadas, "noanonymous,noplain", se borren. El flag noplain deshabilita los mecanismos susceptibles a ataques pasivos simples. El flag noactive deshabilita los mecanismos susceptibles a ataques activos. OPCIONES TLS

Si slapd está compilado con soporte para Transport Layer Security, hay más opciones que puedes especificar.

TLSCipherSuite <cipher-suite-spec>
Permite configurar qué cifrados se aceptarán y el orden de preferencia. <cipher-suite-spec> debe ser una especificación de cifrado para la biblioteca TLS en uso (OpenSSL o GnuTLS). Ejemplo:
OpenSSL:
TLSCipherSuite HIGH:MEDIUM:+SSLv2
GnuTLS:
TLSCiphersuite SECURE256:!AES-128-CBC

Para verificar qué cifrados selecciona una especificación dada en OpenSSL, usa:

openssl ciphers -v <cipher-suite-spec>

Con GnuTLS, las especificaciones disponibles se pueden encontrar en la página del manual de gnutls-cli(1) (consulta la descripción de la opción --priority).

En versiones anteriores de GnuTLS, donde gnutls-cli no soporta la opción --priority, puedes obtener la lista — más limitada — de cifrados llamando a:

gnutls-cli -l
TLSCACertificateFile <nombre_archivo>
Especifica el archivo que contiene los certificados de todas las Autoridades de Certificación que slapd reconocerá. El certificado de la CA que firmó el certificado del servidor debe (GnuTLS) / puede (OpenSSL) incluirse entre estos certificados. Si la CA firmante no era una CA de nivel superior (raíz), deben estar presentes los certificados de toda la secuencia de CAs desde la CA firmante hasta la CA de nivel superior. Múltiples certificados simplemente se agregan al archivo; el orden no es significativo.
TLSCACertificatePath <ruta>
Especifica la ruta de los directorios que contienen certificados de Autoridad de Certificación en archivos individuales separados. Normalmente solo se usa uno de estos o TLSCACertificateFile. Si se especifican ambos, se utilizarán ambas ubicaciones. Se pueden especificar múltiples directorios, separados por un punto y coma.
TLSCertificateFile <nombre_archivo>
Especifica el archivo que contiene el certificado del servidor slapd.

Al usar OpenSSL, ese archivo también puede contener cualquier número de certificados intermedios después del certificado del servidor.

TLSCertificateKeyFile <nombre_archivo>
Especifica el archivo que contiene la clave privada del servidor slapd que coincide con el certificado almacenado en el archivo TLSCertificateFile. Actualmente, la clave privada no debe estar protegida con contraseña, por lo que es de vital importancia que se proteja cuidadosamente.
TLSDHParamFile <nombre_archivo>
Esta directiva especifica el archivo que contiene los parámetros para el intercambio de claves Diffie-Hellman efímeras. Esto es necesario para usar un certificado DSA en el servidor, o un certificado RSA que carece del uso de clave "cifrado de clave". Ten en cuenta que la configuración de esta opción también puede habilitar intercambios de claves Diffie-Hellman anónimos en ciertas suites de cifrado no predeterminadas. Los intercambios de claves anónimos generalmente deben evitarse, ya que no proporcionan autenticación real del cliente o del servidor y no ofrecen protección contra ataques de intermediario. Debes agregar "!ADH" a tus suites de cifrado para asegurar que estas suites no se utilicen.
TLSECName <nombre>
Especifica el nombre de la(s) curva(s) a utilizar para el intercambio de claves efímeras Diffie-Hellman de curva elíptica. Esta opción solo se utiliza para OpenSSL. Esta opción no se utiliza con GnuTLS; las curvas se pueden elegir en la especificación de la suite de cifrado de GnuTLS.
TLSProtocolMin <mayor>[.<menor>]
Especifica la versión mínima del protocolo SSL/TLS que se negociará. Si el servidor no admite al menos esa versión, el handshake SSL fallará. Para requerir TLS 1.x o superior, establece esta opción en 3.(x+1), por ejemplo, 
TLSProtocolMin 3.2

requeriría TLS 1.1. Especificar un mínimo que sea superior al admitido por la implementación de OpenLDAP resultará en que requiera el nivel más alto que admite. Esta directiva se ignora con GnuTLS.

TLSRandFile <nombre_archivo>
Especifica el archivo del que obtener bits aleatorios cuando /dev/[u]random no está disponible. Generalmente se establece en el nombre del socket EGD/PRNGD. La variable de entorno RANDFILE también se puede usar para especificar el nombre del archivo. Esta directiva se ignora con GnuTLS.
TLSVerifyClient <nivel>
Especifica qué comprobaciones se realizan en los certificados del cliente en una sesión TLS entrante, si las hay. El <nivel> se puede especificar como una de las siguientes palabras clave:
never
Este es el valor predeterminado. slapd no solicitará un certificado al cliente.
allow
Se solicita el certificado del cliente. Si no se proporciona ningún certificado, la sesión continúa normalmente. Si se proporciona un certificado incorrecto, se ignorará y la sesión continuará normalmente.
try
Se solicita el certificado del cliente. Si no se proporciona ningún certificado, la sesión continúa normalmente. Si se proporciona un certificado incorrecto, la sesión se terminará inmediatamente.
demand | hard | true
Estas palabras clave son todas equivalentes, por razones de compatibilidad. Se solicita el certificado del cliente. Si no se proporciona ningún certificado o se proporciona un certificado incorrecto, la sesión se terminará inmediatamente.

Ten en cuenta que se requiere un certificado de cliente válido para utilizar el mecanismo de autenticación SASL EXTERNAL con una sesión TLS. Como tal, se debe elegir una configuración de TLSVerifyClient no predeterminada para habilitar la autenticación SASL EXTERNAL.

TLSCRLCheck <nivel>
Especifica si la Lista de Revocación de Certificados (CRL) de la CA debe usarse para verificar si los certificados del cliente no han sido revocados. Esto requiere que se establezca el parámetro TLSCACertificatePath. Esta directiva se ignora con GnuTLS. El <nivel> se puede especificar como una de las siguientes palabras clave:
none
No se realizan comprobaciones de CRL.
peer
Verifica la CRL del certificado del par.
all
Verifica la CRL para toda la cadena de certificados.
TLSCRLFile <nombre_archivo>
Especifica un archivo que contiene una Lista de Revocación de Certificados que se utilizará para verificar que los certificados no han sido revocados. Esta directiva solo es válida cuando se utiliza GnuTLS.

NAME

slapd.conf – OpenLDAP server configuration file format

SYNOPSIS

/etc/openldap/slapd.conf

DESCRIPTION

The OpenLDAP daemon, slapd(8), may be configured using a configuration file. The default configuration file is named slapd.conf and is located in /etc/openldap/. This configuration file is parsed line by line. Lines starting with a # are ignored.

Configuration options are specified as a keyword followed by arguments. The keyword and its arguments typically span a single line, though some options may span multiple lines.

Configuration directives are primarily categorized as general configuration options, database-specific options, and backend-specific options. Global configuration options apply to the server as a whole. Database options apply to a specific database instance. Backend options apply to the implementation of a specific database.

The configuration file format is described below, with sections covering global options, database-specific options, and backend-specific options. Backend-specific options are detailed in the respective backend manual pages.

GLOBAL CONFIGURATION OPTIONS

database <type>
Specifies the type of the database backend to use for the subsequent configuration options. The types are backend-specific; common types include mdb, ldap, meta, and null. See slapd.backends(5) for a full list.
suffix "<dn>"
Specifies the naming context (or suffixes) for the database. If the database is intended to hold the root of the DIT, the suffix should be set to the distinguished name of the root entry. For example:

suffix "dc=example,dc=com"

A database can have multiple suffixes defined by specifying the suffix directive multiple times. This is typically used with the meta backend.

rootdn "<dn>"
Specifies the distinguished name of the administrative user for the database. This user is typically granted unlimited access privileges. For example:

rootdn "cn=admin,dc=example,dc=com"

This option is only applicable to databases that support authentication and access control.

rootpw <password>
Specifies the password for the rootdn user. The password should be stored in a crypt(3) format or as a clear text password preceded by a single ". For example:

rootpw secret

rootpw "{SSHA}xyz..."

Using clear text passwords is highly discouraged. Use slappasswd(8) to generate the encrypted password string.

This option is only applicable to databases that support authentication and access control.

defaultsearchbase "<dn>"
Specifies the default search base for clients that do not specify one. This is useful for client applications that do not explicitly set a search base.
limits <dn> <who> <what>
Sets resource limits for specific users or scopes. The supported limits are time.limit (time limit), size.limit (size limit), and dn.size.limit (maximum number of entries in a DN). The <who> can be bydn, bygroup, byfilter, or anonymous. The <dn> specifies the DN for whom the limits are set. <what> is the limit value. The special DN * is used to set limits for all users. For example:

limits dn.size.limit=1000 bygroup="cn=users,dc=example,dc=com"

limits idle=30+0 timelimit=30+0 size.limit=500000 bydn="cn=user,dc=example,dc=com"

Limits are specified in the format type.limit=value. For time and size limits, a base value and a soft limit can be specified, separated by '+'. For example, timelimit=60+5 means a base limit of 60 seconds and a soft limit of 5 seconds.

password-hash {ARG……}
Specifies the password hashing algorithms to be used when storing user passwords. The default is {SSHA}. Supported algorithms include {SSHA}, {SHA}, {MD5}, {SMD5}, {CRYPT}, {BF}, and {CLEARTEXT}. Multiple algorithms can be specified, and the first one in the list that is supported by the server will be used. For example:

password-hash {SSHA} {SHA}

tls_configfile <file>
Specifies a configuration file for TLS settings. This can be used to centralize TLS configurations.
tls_cacertfile <file>
Specifies the file containing trusted Certificate Authority (CA) certificates for verifying client certificates.
tls_cacertdir <dir>
Specifies the directory containing trusted CA certificates. Certificates in this directory must be named according to the hashed subject name of the CA certificate.
tls_certfile <file>
Specifies the file containing the server's public key certificate.
tls_keyfile <file>
Specifies the file containing the server's private key.
tls_reqcert <level>
Specifies the level of certificate verification required for clients. Possible values are never, allow, try, and demand. demand is the default.
tls_reqsan <level>
Specifies the level of Subject Alternative Name (SAN) verification required for clients. Possible values are never, allow, try, and demand. allow is the default.
tls_cipher <cipherlist>
Specifies the list of acceptable TLS ciphers for the server.
tls_protocol <protocol>
Specifies the minimum TLS protocol version to be used. Supported values are SSLv3, TLSv1, TLSv1.1, TLSv1.2, and TLSv1.3.
tls_cert_type <type>
Specifies the type of certificate, e.g. rsa, dsa, ec.
tls_checkpeer <yes|no>
Specifies whether to check the peer's certificate. Defaults to yes when TLS is enabled.

Specifies the directory where the database files are stored. This option is backend-specific, but commonly used.

syncrepl ...
Configures the server to act as a replication consumer. This directive takes several sub-options:

<rid>

The replication context identifier. Used to distinguish multiple replication agreements from the same provider.

provider=<host>[:<port>]

The hostname and optional port of the replication provider.

The replication type. Currently, only refreshAndPersist is supported.

The interval at which to check for changes. Defaults to 1 hour.

The interval at which to retry a failed synchronization attempt. If specified as <0>, it means indefinite number of retries until success. If no retry is specified, by default syncrepl retries every hour forever.

The schema checking can be enforced at the LDAP Sync consumer site by turning on the schemachecking parameter. The default is off. Schema checking on means that replicated entries must have a structural objectClass, must obey to objectClass requirements in terms of required/allowed attributes, and that naming attributes and distinguished values must be present. As a consequence, schema checking should be off when partial replication is used.

The network-timeout parameter sets how long the consumer will wait to establish a network connection to the provider. Once a connection is established, the timeout parameter determines how long the consumer will wait for the initial Bind request to complete. The defaults for these parameters come from ldap.conf(5). The tcp-user-timeout parameter, if non-zero, corresponds to the TCP_USER_TIMEOUT set on the target connections, overriding the operating system setting. Only some systems support the customization of this parameter, it is ignored otherwise and system-wide settings are used.

A bindmethod of simple requires the options binddn and credentials and should only be used when adequate security services (e.g. TLS or IPSEC) are in place. REMEMBER: simple bind credentials must be in cleartext! A bindmethod of sasl requires the option saslmech. Depending on the mechanism, an authentication identity and/or credentials can be specified using authcid and credentials. The authzid parameter may be used to specify an authorization identity. Specific security properties (as with the sasl-secprops keyword above) for a SASL bind can be set with the secprops option. A non default SASL realm can be set with the realm option. The identity used for synchronization by the consumer should be allowed to receive an unlimited number of entries in response to a search request. The provider, other than allowing authentication of the syncrepl identity, should grant that identity appropriate access privileges to the data that is being replicated (access directive), and appropriate time and size limits. This can be accomplished by either allowing unlimited sizelimit and timelimit, or by setting an appropriate limits statement in the consumer's configuration (see sizelimit and limits for details).

The keepalive parameter sets the values of idle, probes, and interval used to check whether a socket is alive; idle is the number of seconds a connection needs to remain idle before TCP starts sending keepalive probes; probes is the maximum number of keepalive probes TCP should send before dropping the connection; interval is interval in seconds between individual keepalive probes. Only some systems support the customization of these values; the keepalive parameter is ignored otherwise, and system-wide settings are used.

The starttls parameter specifies use of the StartTLS extended operation to establish a TLS session before Binding to the provider. If the critical argument is supplied, the session will be aborted if the StartTLS request fails. Otherwise the syncrepl session continues without TLS. The tls_reqcert setting defaults to "demand", the tls_reqsan setting defaults to "allow", and the other TLS settings default to the same as the main slapd TLS settings.

The suffixmassage parameter allows the consumer to pull entries from a remote directory whose DN suffix differs from the local directory. The portion of the remote entries' DNs that matches the searchbase will be replaced with the suffixmassage DN.

Rather than replicating whole entries, the consumer can query logs of data modifications. This mode of operation is referred to as delta syncrepl. In addition to the above parameters, the logbase and logfilter parameters must be set appropriately for the log that will be used. The syncdata parameter must be set to either "accesslog" if the log conforms to the slapo-accesslog(5) log format, or "changelog" if the log conforms to the obsolete changelog format. If the syncdata parameter is omitted or set to "default" then the log parameters are ignored.

The lazycommit parameter tells the underlying database that it can store changes without performing a full flush after each change. This may improve performance for the consumer, while sacrificing safety or durability.

DATABASE-SPECIFIC OPTIONS

updatedn <dn>
This option is only applicable in a replica database. It specifies the DN permitted to update (subject to access controls) the replica. It is only needed in certain push-mode replication scenarios. Generally, this DN should not be the same as the rootdn used at the provider.
updateref <url>
Specify the referral to pass back when slapd(8) is asked to modify a replicated local database. If specified multiple times, each url is provided.

EXAMPLES

Here is a short example of a configuration file:

include   /etc/openldap/schema/core.schema
pidfile   /var/lib/openldap/run/slapd.pid
# Subtypes of "name" (e.g. "cn" and "ou") with the
# option ";x-hidden" can be searched for/compared,
# but are not shown.  See slapd.access(5).
attributeoptions x-hidden lang-
access to attrs=name;x-hidden by * =cs
# Protect passwords.  See slapd.access(5).
access    to attrs=userPassword  by * auth
# Read access to other attributes and entries.
access    to *  by * read
database  mdb
suffix    "dc=our-domain,dc=com"
# The database directory MUST exist prior to
# running slapd AND should only be accessible
# by the slapd/tools. Mode 0700 recommended.
directory /var/lib/openldap/openldap-data
# Indices to maintain
index     objectClass  eq
index     cn,sn,mail   pres,eq,approx,sub
# We serve small clients that do not handle referrals,
# so handle remote lookups on their behalf.
database  ldap
suffix    ""
uri       ldap://ldap.some-server.com/
lastmod   off
