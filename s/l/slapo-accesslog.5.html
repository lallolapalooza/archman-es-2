SLAPO-ACCESSLOG(5) Manual de Formatos de Archivo SLAPO-ACCESSLOG(5)

NOMBRE

slapo-accesslog - Superposición de registro de acceso para slapd

SINOPSIS

/etc/openldap/slapd.conf

DESCRIPCIÓN

La superposición de registro de acceso se puede utilizar para registrar todos los accesos a una base de datos determinada en otra base de datos. Esto permite revisar toda la actividad en una base de datos dada mediante consultas LDAP arbitrarias, en lugar de simplemente registrar en archivos de texto plano locales. Hay opciones de configuración disponibles para seleccionar un subconjunto de tipos de operación a registrar y para podar automáticamente los registros más antiguos de la base de datos de registro. Los registros se almacenan con el esquema de auditoría (ver más abajo) para garantizar su legibilidad, ya sea vistos como LDIF o en formato bruto.

CONFIGURACIÓN

Estas opciones de slapd.conf se aplican a la superposición de registro de acceso. Deben aparecer después de la directiva overlay.

logdb <sufijo>
Especifica el sufijo de una base de datos que se utilizará para almacenar los registros. La base de datos especificada debe definirse en otro lugar de la configuración y debe admitir un retorno ordenado de resultados, como slapd-mdb(5). Los controles de acceso a la base de datos de registro deben evitar el acceso general. La entrada de sufijo de la base de datos de registro será creada automáticamente por esta superposición. Las entradas de registro se generarán como hijos inmediatos de la entrada de sufijo.
logops <operaciones>
Especifica qué tipos de operaciones se registrarán. Los tipos de operación válidos son abandonar, agregar, enlazar, comparar, eliminar, extender, modificar, modrdn, buscar y desenlazar. También hay alias disponibles para conjuntos comunes de operaciones:
writes
agregar, eliminar, modificar, modrdn
reads
comparar, buscar
session
abandonar, enlazar, desenlazar
all
todas las operaciones
logbase <operaciones> <baseDN>
Especifica un conjunto de operaciones que solo se registrarán si ocurren bajo un subárbol específico de la base de datos. Los tipos de operación son los anteriores para la configuración logops y están delimitados por un carácter '|'.
logold <filtro>
Especifica un filtro para comparar entradas eliminadas y modificadas. Si la entrada coincide con el filtro, el contenido antiguo de la entrada se registrará junto con la solicitud actual.
logoldattr <attr> ...
Especifica una lista de atributos cuyo contenido antiguo se registra siempre en las solicitudes Modificar y ModRDN que coinciden con cualquiera de los filtros configurados en logold. Normalmente, solo se registrará el contenido de los atributos que se modificaron realmente; por defecto, no se registran atributos antiguos para las solicitudes ModRDN.
logpurge <edad> <intervalo>
Especifica la antigüedad máxima de las entradas de registro que se conservarán en la base de datos y con qué frecuencia se escaneará la base de datos en busca de entradas antiguas. Tanto la edad como el intervalo se especifican como un período de tiempo en días, horas, minutos y segundos. El formato de tiempo es [ddd+]hh:mm[:ss], es decir, los componentes de días y segundos son opcionales, pero las horas y los minutos son obligatorios. Excepto por los días, que pueden tener hasta 5 dígitos, cada campo numérico debe tener exactamente dos dígitos. Por ejemplo,
logpurge 2+00:00 1+00:00
especificaría que la base de datos de registro se escaneará diariamente en busca de entradas antiguas, y se eliminarán las entradas de más de dos días. Al utilizar una base de datos de registro que admita indexación ordenada en atributos generalizedTime, especificar un índice eq en el atributo reqStart beneficiará enormemente el rendimiento de la operación de purga.
logsuccess TRUE | FALSE
Si se establece en TRUE, solo se generarán registros para solicitudes exitosas, es decir, solicitudes que producen un código de resultado de 0 (LDAP_SUCCESS). Si es FALSE, se generarán registros para todas las solicitudes, ya sea que tengan éxito o no. El valor predeterminado es FALSE.

EJEMPLOS

database mdb
suffix dc=example,dc=com
...
overlay accesslog
logdb cn=log
logops writes reads
logbase search|compare ou=testing,dc=example,dc=com
logold (objectclass=person)
database mdb
suffix cn=log
...
index reqStart eq
access to *
  by dn.base="cn=admin,dc=example,dc=com" read

ESQUEMA

La superposición accesslog utiliza el esquema "audit" que se describe aquí. Este esquema está diseñado específicamente para la auditoría de accesslog y no está destinado a ser utilizado de otra manera. También se señala que el esquema descrito aquí está *en progreso* y, por lo tanto, sujeto a cambios sin previo aviso. El esquema se carga automáticamente con la superposición.

El esquema incluye una serie de clases de objetos y tipos de atributos asociados, como se describe a continuación.

La entrada raíz de la base de datos subyacente de accesslog utiliza la clase auditContainer, que es la siguiente:

( 1.3.6.1.4.1.4203.666.11.5.2.0
NAME 'auditContainer'
DESC 'AuditLog container'
SUP top STRUCTURAL
MAY ( cn $ reqStart $ reqEnd ) )

Existe una clase básica auditObject de la cual se derivan dos clases adicionales, auditReadObject y auditWriteObject. Las clases de objetos para cada tipo de operación LDAP se derivan posteriormente de estas clases. Esta jerarquía de clases de objetos está diseñada para permitir búsquedas flexibles pero eficientes en el registro basándose en la clase de un tipo de operación específico o en clasificaciones más generales. La definición de la clase auditObject es la siguiente:

( 1.3.6.1.4.1.4203.666.11.5.2.1
NAME 'auditObject'
DESC 'OpenLDAP request auditing'
SUP top STRUCTURAL
MUST ( reqStart $ reqType $ reqSession )
MAY ( reqDN $ reqAuthzID $ reqControls $ reqRespControls $
reqEnd $ reqResult $ reqMessage $ reqReferral $ reqEntryUUID ) )

Tenga en cuenta que todas las OIDs utilizadas en el esquema de registro residen actualmente bajo la rama Experimental de OpenLDAP. Se prevé que migren a una rama Estándar en el futuro.

Una descripción general de los atributos sigue: reqStart y reqEnd proporcionan la hora de inicio y fin de la operación, respectivamente. Utilizan la sintaxis generalizedTime. El atributo reqStart también se utiliza como el RDN para cada entrada de registro.

El atributo reqType es una cadena simple que contiene el tipo de operación que se está registrando, por ejemplo, add, delete, search, etc. Para operaciones extendidas, el tipo también incluye la OID de la operación extendida, por ejemplo, extended(1.1.1.1)

El atributo reqSession es un identificador específico de la implementación que es común a todas las operaciones asociadas con la misma sesión LDAP. Actualmente, este es el ID de conexión interno de slapd, almacenado en decimal.

El atributo reqDN es el distinguishedName del objetivo de la operación. Por ejemplo, para una solicitud Bind, este es el Bind DN. Para una solicitud Add, este es el DN de la entrada que se está agregando. Para una solicitud Search, este es el DN base de la búsqueda.

El atributo reqAuthzID es el distinguishedName del usuario que realizó la operación. Este será generalmente el mismo nombre que se estableció al inicio de una sesión mediante una solicitud Bind (si la hubiera), pero puede alterarse en diversas circunstancias.

Los atributos reqControls y reqRespControls transportan cualquier control enviado por el cliente en la solicitud y devuelto por el servidor en la respuesta, respectivamente. Los valores de los atributos son simplemente cadenas de octetos no interpretadas.

El atributo reqResult es el código de resultado numérico de LDAP de la operación, que indica éxito o un código de error LDAP específico. Un código de error puede ir acompañado de un mensaje de error de texto que se registrará en el atributo reqMessage.

NAME

slapo-accesslog - OpenLDAP access log overlay

SYNOPSIS

slapo-accesslog

DESCRIPTION

The accesslog overlay provides a mechanism to log all access-related operations performed by slapd. The log is maintained as a backend database, and can be configured to store a wide variety of information about each operation. This information can be used for a number of purposes, including security auditing, replication, and general troubleshooting.

The overlay works by intercepting standard slapd operations and writing corresponding entries into a separate backend database. The format of these log entries is defined by a set of object classes and attributes within the schema. The overlay itself does not interpret the log entries; it merely writes them.

CONFIGURATION

The accesslog overlay is configured using the slapd.conf file or through the runtime configuration mechanisms.

The following configuration options are specific to the accesslog overlay:

accesslog-logops [ op,... | all | none ]
Specifies which operations should be logged. The default is to log all operations.
accesslog-filter <filter>
Specifies a filter that is applied to entries before they are logged. Only entries that match the filter will be logged. This is useful for reducing the amount of log data generated. The filter syntax is the standard LDAP search filter syntax.
accesslog-maxops <number>
Specifies the maximum number of operations to store in the log. When this limit is reached, the oldest entries will be removed to make space for new ones. This is useful for managing the size of the log database.
accesslog-maxage <time>
Specifies the maximum age of log entries. Entries older than this time will be automatically removed. The time can be specified in seconds, or using the suffixes `d' for days, `h' for hours, or `m' for minutes.
accesslog-recorder <DN>
Specifies the DN to use when recording log entries. If not specified, the operation's bind DN is used. This is useful for security purposes, to ensure that the log entries are recorded with a consistent identity.
accesslog-rid <integer>
Specifies the request ID to use for logging. This is typically used in conjunction with the auditlog overlay to provide a consistent request ID across multiple overlays.
logold [ filter | on | off ]
Controls whether the previous contents of an entry are logged during delete and modify operations. If set to on, the previous contents are logged without filtering. If set to off, the previous contents are not logged. If a filter is specified, the previous contents are logged only if they match the filter.
logoldattr attribute,...
Specifies a list of attributes whose values should be logged when logold is enabled. If not specified, all attributes are logged.

EXAMPLES

To enable the access log overlay and configure it to log all operations to a backend database named "logdb":

database            ldap
suffix              "dc=example,dc=com"
...
overlay             accesslog
accesslog-logops    all
# The log database backend configuration follows
database            ldbm
suffix              "cn=accesslog"
directory           "/var/lib/ldap/logdb"
addcontent          TRUE
# ... other database parameters ...

SCHEMA

The accesslog overlay requires the following object classes and attributes to be defined in the schema:

( 1.3.6.1.4.1.4203.666.11.5.1.1
NAME 'auditLog'
DESC 'Audit Log Entry'
SUP top STRUCTURAL
MUST ( reqType )
MAY ( reqTimestamp $ reqID $ reqSession $ reqDistName $ reqCredName $
reqAuthId $ reqAuthType $ reqReferral $ reqEntryUUID ) )

The auditLog object class is the base class for all audit log entries. It contains attributes that are common to all operations:

reqType
The type of operation that was performed. This is an OID that corresponds to the operation (e.g., 1.3.6.1.4.1.4203.666.11.5.2.4 for Abandon).
reqTimestamp
The time at which the request was received.
reqID
The unique identifier for the request. This is useful for correlating multiple log entries related to the same request.
reqSession
The session identifier for the request. This can be used to group requests from the same client connection.
reqDistName
The DN of the client making the request.
reqCredName
The DN of the client credentials used for authentication.
reqAuthId
The authenticated ID of the client.
reqAuthType
The type of authentication used (e.g., SIMPLE, SASL).
reqReferral
The attribute carries any referrals that were returned with the result of the request.
reqEntryUUID
The attribute records the entryUUID attribute of the entry operated on, for an Add request, this is the entryUUID of the newly created entry.

Operation-specific classes are defined with additional attributes to carry all of the relevant parameters associated with the operation:

( 1.3.6.1.4.1.4203.666.11.5.2.4
NAME 'auditAbandon'
DESC 'Abandon operation'
SUP auditObject STRUCTURAL
MUST reqId )

For the Abandon operation the reqId attribute contains the message ID of the request that was abandoned.

( 1.3.6.1.4.1.4203.666.11.5.2.5
NAME 'auditAdd'
DESC 'Add operation'
SUP auditWriteObject STRUCTURAL
MUST reqMod )

The Add class inherits from the auditWriteObject class. The Add and Modify classes are very similar. The reqMod attribute carries all of the attributes of the original entry being added. (Or in the case of a Modify operation, all of the modifications being performed.) The values are formatted as

attribute:<+|-|=|#> [ value]
Where '+' indicates an Add of a value, '-' for Delete, '=' for Replace, and '#' for Increment. In an Add operation, all of the reqMod values will have the '+' designator.
( 1.3.6.1.4.1.4203.666.11.5.2.6
NAME 'auditBind'
DESC 'Bind operation'
SUP auditObject STRUCTURAL
MUST ( reqVersion $ reqMethod ) )

The Bind class includes the reqVersion attribute which contains the LDAP protocol version specified in the Bind as well as the reqMethod attribute which contains the Bind Method used in the Bind. This will be the string SIMPLE for LDAP Simple Binds or SASL(<mech>) for SASL Binds. Note that unless configured as a global overlay, only Simple Binds using DNs that reside in the current database will be logged.

( 1.3.6.1.4.1.4203.666.11.5.2.7
NAME 'auditCompare'
DESC 'Compare operation'
SUP auditObject STRUCTURAL
MUST reqAssertion )

For the Compare operation the reqAssertion attribute carries the Attribute Value Assertion used in the compare request.

( 1.3.6.1.4.1.4203.666.11.5.2.8
NAME 'auditDelete'
DESC 'Delete operation'
SUP auditWriteObject STRUCTURAL
MAY reqOld )

The Delete operation needs no further parameters. However, the reqOld attribute may optionally be used to record the contents of the entry prior to its deletion. The values are formatted as

attribute: value
The reqOld attribute is only populated if the entry being deleted matches the configured logold filter.
( 1.3.6.1.4.1.4203.666.11.5.2.9
NAME 'auditModify'
DESC 'Modify operation'
SUP auditWriteObject STRUCTURAL
MAY ( reqOld $ reqMod ) )

The Modify operation contains a description of modifications in the reqMod attribute, which was already described above in the Add operation. It may optionally contain the previous contents of any modified attributes in the reqOld attribute, using the same format as described above for the Delete operation. The reqOld attribute is only populated if the entry being modified matches the configured logold filter.

( 1.3.6.1.4.1.4203.666.11.5.2.10
NAME 'auditModRDN'
DESC 'ModRDN operation'
SUP auditWriteObject STRUCTURAL
MUST ( reqNewRDN $ reqDeleteOldRDN )
MAY ( reqNewSuperior $ reqMod $ reqOld ) )

The ModRDN class uses the reqNewRDN attribute to carry the new RDN of the request. The reqDeleteOldRDN attribute is a Boolean value showing TRUE if the old RDN was deleted from the entry, or FALSE if the old RDN was preserved. The reqNewSuperior attribute carries the DN of the new parent entry if the request specified the new parent. The reqOld attribute is only populated if the entry being modified matches the configured logold filter and contains attributes in the logoldattr list.

( 1.3.6.1.4.1.4203.666.11.5.2.11
NAME 'auditSearch'
DESC 'Search operation'
SUP auditReadObject STRUCTURAL
MUST ( reqScope $ reqDerefAliases $ reqAttrsOnly )
MAY ( reqFilter $ reqAttr $ reqEntries $ reqSizeLimit $
reqTimeLimit ) )

For the Search class the reqScope attribute contains the scope of the original search request, using the values specified for the LDAP URL format. I.e. base, one, sub, or subord. The reqDerefAliases attribute is one of never, finding, searching, or always, denoting how aliases will be processed during the search. The reqAttrsOnly attribute is a Boolean value showing TRUE if only attribute names were requested, or FALSE if attributes and their values were requested. The reqFilter attribute carries the filter used in the search request. The reqAttr attribute lists the requested attributes if specific attributes were requested. The reqEntries attribute is the integer count of how many entries were returned by this search request. The reqSizeLimit and reqTimeLimit attributes indicate what limits were requested on the search operation.

( 1.3.6.1.4.1.4203.666.11.5.2.12
NAME 'auditExtended'
DESC 'Extended operation'
SUP auditObject STRUCTURAL
MAY reqData )

The Extended class represents an LDAP Extended Operation. As noted above, the actual OID of the operation is included in the reqType attribute of the parent class. If any optional data was provided with the request, it will be contained in the reqData attribute as an uninterpreted octet string.

NOTES

The Access Log implemented by this overlay may be used for a variety of other tasks, e.g. as a ChangeLog for a replication mechanism, as well as for security/audit logging purposes.

FILES

/etc/openldap/slapd.conf
default slapd configuration file
