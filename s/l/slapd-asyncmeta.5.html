SLAPD-ASYNCMETA(5) Manual de formatos de archivo SLAPD-ASYNCMETA(5)

NOMBRE

slapd-asyncmeta - backend asíncrono de metadatos para slapd

SINOPSIS

/etc/openldap/slapd.conf

DESCRIPCIÓN

El backend asyncmeta para slapd(8) realiza proxy LDAP básico con respecto a un conjunto de servidores LDAP remotos, llamados "objetivos". La información contenida en estos servidores puede presentarse como perteneciente a un único Árbol de Información de Directorio (DIT).

Se recomienda un buen conocimiento de la funcionalidad del backend slapd-meta(5). Este backend ha sido diseñado como una versión asíncrona del backend meta. A diferencia de meta, los hilos que manejan las operaciones ya no esperan la respuesta del servidor remoto, lo que reduce el número de hilos necesarios para manejar la misma carga. Si bien asyncmeta mantiene la funcionalidad de meta y tiene una base de código en gran medida similar, se han agregado algunos cambios en la operación y algunas nuevas directivas de configuración. Se han eliminado algunas opciones de configuración, como conn-pool-max, conn-ttl, single-conn y use-temporary-conn, ya que ya no son relevantes.

Manejo de conexiones nuevo:

A diferencia de meta, que almacena en caché las conexiones enlazadas, asyncmeta funciona con un número máximo de conexiones configurado por objetivo. Para cada solicitud redirigida a un objetivo, se selecciona una conexión diferente. Cada conexión tiene una cola, a la que se agrega la solicitud antes de enviarla al servidor remoto, y se elimina después de recibir la última respuesta para esa solicitud.
Para cada nueva solicitud, se elige una nueva conexión utilizando la programación round-robin.

Sobrecargas (Overlays):

Debido a las especificidades de implementación, no hay garantía de que alguna de las sobrecargas existentes de OpenLDAP funcione con el backend asyncmeta.

EJEMPLOS

Consulte slapd-meta(5) para ver ejemplos de configuración.

CONFIGURACIÓN

Estas opciones de slapd.conf se aplican a la base de datos del backend ASYNCMETA. Es decir, deben seguir una línea de "database asyncmeta" y aparecer antes de cualquier línea posterior de "backend" o "database". Otras opciones de base de datos se describen en la página del manual slapd.conf(5).

DIRECTIVAS ESPECIALES DE CONFIGURACIÓN

La configuración del objetivo comienza con la directiva "uri". Todas las directivas de configuración que no son específicas de los objetivos deben definirse primero para mayor claridad, incluidas aquellas que son comunes a todos los backends. Estas son:

default-target none
Esta directiva obliga al backend a rechazar todas aquellas operaciones que deben resolverse en un único objetivo en caso de que no se seleccionen objetivos o se seleccionen varios. Estas incluyen: agregar, eliminar, modificar, modrdn; compare no está incluido, así como bind ya que, al no alterar las entradas, en caso de múltiples coincidencias se intenta realizar la operación en cualquier objetivo candidato, con la restricción de que a lo sumo uno debe tener éxito. Esta directiva también se puede usar al procesar objetivos para marcar un objetivo específico como predeterminado.
dncache-ttl {DISABLED|forever|<ttl>}
Esta directiva establece el tiempo de vida (time-to-live) de la caché de DN. Esto almacena en caché el objetivo que contiene un DN dado para acelerar la selección del objetivo en caso de que múltiples objetivos resulten de una búsqueda sin caché; forever significa que la caché nunca expira; disabled significa que no hay caché de DN; de lo contrario, se requiere un ttl válido ( > 0 ), en el formato ilustrado para la directiva idle-timeout.
onerr {CONTINUE|report|stop}
Esta directiva permite seleccionar el comportamiento en caso de que un objetivo devuelva un error durante una búsqueda. El valor predeterminado, continue, consiste en continuar la operación, intentando devolver la mayor cantidad de datos posible. Si el valor se establece en stop, la búsqueda se termina tan pronto como un objetivo devuelve un error y el error se propaga inmediatamente al cliente. Si el valor se establece en report, la búsqueda continúa hasta el final, pero en caso de que al menos un objetivo haya devuelto un código de error, se devuelve el primer código de error que no sea de éxito.
max-timeout-ops <número>
Especifica el número de solicitudes consecutivas con tiempo de espera agotado, después de las cuales la conexión se considerará defectuosa y se cerrará.
max-pending-ops <número>
El número máximo de solicitudes pendientes almacenadas en la cola de una conexión. El valor predeterminado es 128. Cuando se supera este número, se devolverá LDAP_BUSY al cliente.
max-target-conns <número>
El número máximo de conexiones por objetivo. A diferencia de slapd-meta(5), no se crearán nuevas conexiones una vez alcanzado este número. El valor predeterminado es 255.
norefs <NO|yes>
Si es yes, no devuelva respuestas de referencia de búsqueda. Por defecto, se devuelven a menos que la solicitud sea LDAPv2. Si se establece antes de cualquier especificación de objetivo, afecta a todos los objetivos, a menos que se anule mediante cualquier directiva por objetivo.
noundeffilter <NO|yes>
Si es yes, devuelva éxito en lugar de buscar si un filtro no está definido o contiene porciones indefinidas. Por defecto, la búsqueda se propaga después de reemplazar las porciones indefinidas con (!(objectClass=*)), lo que corresponde al conjunto de resultados vacío. Si se establece antes de cualquier especificación de objetivo, afecta a todos los objetivos, a menos que se anule mediante cualquier directiva por objetivo.
protocol-version {0,2,3}
Esta directiva indica qué versión del protocolo se debe utilizar para contactar al servidor remoto. Si se establece en 0 (el valor predeterminado), el proxy utiliza la misma versión del protocolo que utiliza el cliente, de lo contrario, se utiliza el protocolo solicitado. El proxy devuelve unwillingToPerform si se intenta una operación incompatible con el protocolo solicitado. Si se establece antes de cualquier especificación de objetivo, afecta a todos los objetivos, a menos que se anule mediante cualquier directiva por objetivo.
pseudoroot-bind-defer {YES|no}
Esta directiva, cuando se establece en yes, hace que la autenticación en los servidores remotos con la identidad de pseudo-raíz (la identidad definida en cada directiva idassert-bind) se retrase hasta que sea necesaria por operaciones posteriores. De lo contrario, todas las vinculaciones como rootdn se propagan a los objetivos.
quarantine <intervalo>,<num>[;<intervalo>,<num>[...]]
Activa la cuarentena de URIs que devolvieron LDAP_UNAVAILABLE, de modo que solo se intente reconectar en intervalos dados en lugar de cada vez que un cliente solicita una operación. El patrón es: reintentar solo después de que haya transcurrido al menos intervalo segundos desde el último intento, durante exactamente num veces; luego usar el siguiente patrón. Si num para el último patrón es "+", se reintentará para siempre; de lo contrario, no se realizarán más reintentos. Esta directiva debe aparecer antes de cualquier especificación de objetivo; afecta a todos los objetivos con el mismo patrón.
rebind-as-user <NO|yes>
Si se proporciona esta opción, las credenciales de vinculación del cliente se recuerdan para las re-vinculaciones, al intentar restablecer una conexión rota, o al seguir una referencia, si chase-referrals está establecido en yes.
session-tracking-request <NO|yes>
Agrega seguimiento de sesión para todas las solicitudes. La IP y el nombre de host del cliente, y la identidad asociada a cada solicitud, si se conocen, se envían al servidor remoto para fines informativos. Esta directiva es incompatible con el establecimiento de protocol-version a 2. Si se establece antes de cualquier especificación de objetivo, afecta a todos los objetivos, a menos que se anule mediante cualquier directiva por objetivo.

CONFIGURACIÓN DEL OBJETIVO

Las siguientes directivas se aplican a cada objetivo y deben especificarse después de la directiva uri que define el objetivo.

binddn <dn>
The DN to bind with when connecting to the target. If not specified, anonymous bind is performed.
bindpw <password>
The password to use with the binddn. If not specified, the password from the binddn is used.
chase-referrals <NO|yes>
If yes, referrals are chased. By default, they are not.
conn-ttl <ttl>
Specify the time-to-live for connections. Connections older than this time will be closed and reopened. This directive is only relevant when the target has not specified single-conn or use-temporary-conn.
idle-timeout <idle>
Specify the idle timeout for connections. Connections that have been idle for longer than this time will be closed. If set to 0, connections will never be closed. The default is 10 minutes.
idassert-bind sasl_openidc_bind options
Assert identity of the local user to the remote server. It is used typically when the client is authenticated, and the proxy needs to bind to the remote server with the client's credentials. See slapd-ldap(5) for details on the options.
keep-conn-alive <interval>
Keep connections alive by sending periodic keep-alive messages. The interval is specified in seconds.
local-filter filter
Apply a filter to entries local to the backend. This is useful for hiding entries from specific targets.
map-attribute from-attr to-attr
Map attributes from one name to another. This is useful for normalizing attribute names across different targets.
map-dn from-dn to-dn
Map DNs from one naming context to another. This is useful for presenting entries from different targets as belonging to a single DIT.
merge-mode {BLANK|OR|AND}
Specify how to merge results from multiple targets. BLANK means only entries that exist in all targets are returned. OR means entries that exist in any target are returned. AND means entries that exist in all targets are returned.
mod-at-timeout <timeout>
Specify the timeout for modifications. Modifications that take longer than this time will be aborted.
network-timeout <timeout>
Specify the network timeout for operations. Operations that take longer than this time will be aborted.
referral <url>
Specify the referral URL to return when an entry is not found in the target.
remote-filter filter
Apply a filter to entries returned by the target. This is useful for hiding entries from specific clients.
single-conn <yes|NO>
If yes, use a single connection to the target for all operations. This can improve performance by reducing the overhead of establishing connections.
uri <url>[...]
Specify the URI of the target server. This directive is mandatory and must be specified for each target.
uri-<id> <url>[...]
Specify the URI of the target server with an ID. This allows multiple URIs to be specified for the same target, which can be used for load balancing.
use-temporary-conn <yes|NO>
If yes, use temporary connections to the target for all operations. This can be useful for security reasons, as it prevents the proxy from maintaining persistent connections to the target.

NOTAS

El backend asyncmeta es una versión asíncrona del backend meta. Si bien ofrece una mejor escalabilidad, puede tener problemas de compatibilidad con algunas sobrecargas (overlays) y directivas de configuración que no son relevantes en el contexto asíncrono.

SLAPD_META
This backend implements a meta-directory. It allows you to present entries from various LDAP servers as if they were part of a single directory. The meta-directory is configured via the slapd.conf file (Section 5) or dynamically via LDIF entries. The configuration is done using directives that define the remote LDAP servers (targets) and how to map entries and attributes between them and the meta-directory.

The following directives are used to configure the slapd-meta backend:

provides suffix
Defines the DN suffix for the virtual naming context that this backend instance provides. This is mandatory for all backend configurations.
search-base suffix
Defines the base DN for the virtual naming context. Entries within this naming context will be presented by this backend instance. This is also mandatory.
uri protocol://[host]/naming context [flags]
Specifies the URI of the remote LDAP server to which the virtual naming context is delegated. The naming context part of the URI must match the search-base of the virtual naming context. Multiple URIs can be specified for load balancing and failover.
add [authcDN DN] [passwd password]
Specifies the DN and password to use when adding entries to the remote server. If not specified, the client's DN and credentials are used.
bind [method bind method] [dn DN] [credentials password]
Specifies the bind method and credentials to use when connecting to the remote server. Supported methods include anonymous, simple, and SASL. If not specified, anonymous bind is used.
chase-referrals {yes|no}
Determines whether to automatically follow referrals returned by the remote server. Defaults to yes.
flags [peername] [remotecert] [virtual]
Specifies flags to control the behavior of the backend.
  • peername: Use the peer's name as the authenticated ID.
  • remotecert: Use the remote certificate for authentication.
  • virtual: Treat the target as a virtual server.
idassert-authzFrom authz-regexp
Defines the set of local identities that are authorized to use identity assertion. The format of authz-regexp follows the rules for the authzFrom attribute.
idassert-bind bind parameters
Specifies the parameters for the identity assertion bind operation. This is used to authenticate to the target server using credentials that are different from the client's credentials.
idle-timeout time
Specifies the timeout for idle connections to the remote server. If a connection remains idle for the specified duration, it will be closed. The connection will be re-established when needed.
keepalive idle:probes:interval
Configures TCP keepalive probes for connections to the remote server. This helps detect and close dead connections.
map {attribute|objectclass} [|*] {|*}
Maps local attribute or object class names to foreign names on the remote server, and vice versa. This allows for attribute and object class renaming.
nretries {forever|never|nretries}
Defines the number of times to retry an operation if it fails due to temporary network issues or server unavailability. Defaults to 3.
network-timeout time
Sets the timeout for network operations, such as establishing a connection or sending a request. If the operation does not complete within the specified time, it will be considered a timeout.
rebind-as-user {yes|no}
Specifies whether to rebind to the remote server using the client's credentials when following referrals. Defaults to no.
suffixmassage local suffix remote suffix
Rewrites DN suffixes when communicating with the remote server. This is useful when the remote server uses a different suffix for the same entries.
tcp-user-timeout milliseconds
Sets the TCP_USER_TIMEOUT socket option for connections to the remote server. This allows fine-grained control over TCP connection timeouts.
timeout [=]val [...]
Sets per-operation timeouts for various LDAP operations such as bind, search, add, modify, delete, etc. The default timeout for all operations is 2 seconds.
tls {none|[try-]start|[try-]propagate|ldaps} [starttls=no] [tls_cert=file] [tls_key=file] [tls_cacert=file] [tls_cacertdir=path] [tls_reqcert=level] [tls_reqsan=level] [tls_cipher_suite=ciphers] [tls_ecname=names] [tls_crlcheck=level]
Configures TLS/SSL settings for connections to the remote server.
  • none: No TLS/SSL is used.
  • start: Use the StartTLS extended operation.
  • try-start: Attempt StartTLS, but proceed without it if it fails (not recommended).
  • propagate: Use StartTLS only if the original connection already has TLS enabled.
  • try-propagate: Attempt StartTLS propagation, but proceed without it if it fails (not recommended).
  • ldaps: Use the LDAPS protocol (port 636).
Other TLS parameters like certificates, keys, and cipher suites can also be specified.

ESPECIFICACIÓN DE DESTINO

La especificación del destino comienza con una directiva "uri":

uri <protocolo>://[<host>]/<contexto de nombres> [...]
Idéntico a meta. Ver slapd-meta(5) para más detalles.
acl-authcDN <DN administrativo para fines de control de acceso>
DN que se utiliza para consultar al servidor de destino para la comprobación de ACL, como en el backend LDAP; se supone que tiene acceso de lectura en el servidor de destino a los atributos utilizados en el proxy para la comprobación de ACL. No hay riesgo de divulgar tales valores; solo se utilizan para comprobar permisos. La identidad acl-authcDN no es utilizada implícitamente por el proxy cuando el cliente se conecta anónimamente.
acl-passwd <contraseña>
Contraseña utilizada con el acl-authcDN anterior.
bind-timeout <microsegundos>
Esta directiva define el tiempo de espera, en microsegundos, utilizado al esperar una respuesta después de una conexión de bind asíncrona. Ver slapd-meta(5) para más detalles.
chase-referrals {YES|no}
habilitar/deshabilitar el seguimiento automático de referencias, que se delega a la biblioteca libldap subyacente, con re-binding realizado eventualmente si la directiva rebind-as-user se utiliza. El valor predeterminado es seguir referencias. Si se establece antes de cualquier especificación de destino, afecta a todos los destinos, a menos que se anule con cualquier directiva por destino.
client-pr {accept-unsolicited|DISABLE|<<tamaño>>}
Esta función permite utilizar el control de Resultados Pagados RFC 2696 al realizar operaciones de búsqueda con un destino específico, independientemente de la solicitud del cliente. Ver slapd-meta(5) para más detalles.
default-target [<destino>]
La directiva "default-target" también se puede utilizar durante la especificación del destino. Sin argumentos, marca el destino actual como el predeterminado. El número opcional marca el destino <destino> como el predeterminado, comenzando desde 1. El destino <destino> debe estar definido.
filter <patrón>
Esta directiva permite especificar un patrón regex(5) para indicar qué términos del filtro de búsqueda son realmente servidos por un destino.

En una solicitud de búsqueda, si el filtro de búsqueda coincide con el patrón, el destino se considera al cumplir la solicitud; de lo contrario, el destino se ignora. Puede haber múltiples ocurrencias de la directiva filter para cada destino.

idassert-authzFrom <authz-regexp>
si se define, selecciona qué identidades *locales* están autorizadas a explotar la función de aserción de identidad. La cadena <authz-regexp> sigue las reglas definidas para el atributo authzFrom. Ver slapd.conf(5), sección relacionada con authz-policy, para más detalles sobre la sintaxis de este campo.

idassert-bind bindmethod=none|simple|sasl [binddn=<DN simple>] [credentials=<contraseña simple>] [saslmech=<SASL mech>] [secprops=<propiedades>] [realm=<realm>] [authcId=<ID de autenticación>] [authzId=<ID de autorización>] [authz={native|proxyauthz}] [mode=<modo>] [flags=<flags>] [starttls=no|yes|critical] [tls_cert=<archivo>] [tls_key=<archivo>] [tls_cacert=<archivo>] [tls_cacertdir=<ruta>] [tls_reqcert=never|allow|try|demand] [tls_reqsan=never|allow|try|demand] [tls_cipher_suite=<cifrados>] [tls_ecname=<nombres>] [tls_protocol_min=<mayor>[.<menor>]] [tls_crlcheck=none|peer|all] Permite definir los parámetros del método de autenticación que se utiliza internamente por el proxy para autorizar conexiones que están autenticadas por otras bases de datos. Ver slapd-meta(5) para más detalles.

idle-timeout <tiempo>
Esta directiva provoca que una conexión persistente se cierre después de que haya estado inactiva durante el tiempo especificado. La conexión se volverá a crear la próxima vez que se seleccione para su uso. Una conexión se considera inactiva si no ha habido intentos por parte del backend de usarla para enviar una solicitud al servidor de destino. Si todavía hay solicitudes pendientes en su cola, la conexión se cerrará después de que la última solicitud haya recibido un resultado o haya caducado.

[<d>d][<h>h][<m>m][<s>[s]]

donde <d>, <h>, <m> y <s> se tratan respectivamente como días, horas, minutos y segundos. Si se establece antes de cualquier especificación de destino, afecta a todos los destinos, a menos que se anule con cualquier directiva por destino.

keepalive <inactivo>:<sondas>:<intervalo>
El parámetro keepalive establece los valores de inactivo, sondas e intervalo utilizados para comprobar si un socket está vivo; inactivo es el número de segundos que una conexión debe permanecer inactiva antes de que TCP comience a enviar sondas keepalive; sondas es el número máximo de sondas keepalive que TCP debe enviar antes de cerrar la conexión; intervalo es el intervalo en segundos entre sondas keepalive individuales. Solo algunos sistemas admiten la personalización de estos valores; de lo contrario, el parámetro keepalive se ignora y se utilizan la configuración a nivel de sistema.
tcp-user-timeout <milisegundos>
Si no es cero, corresponde al TCP_USER_TIMEOUT establecido en las conexiones de destino, anulando la configuración del sistema operativo. Solo algunos sistemas admiten la personalización de este parámetro; de lo contrario, se ignora y se utilizan la configuración a nivel de sistema.
map {atributo|objectclass} [<nombre local>|*] {<nombre extranjero>|}
Esto mapea clases de objetos y atributos como en el backend LDAP. Ver slapd-ldap(5).
network-timeout <tiempo>
Establece el valor del tiempo de espera de red después del cual poll(2)/select(2) después de un connect(2) regresa en caso de no actividad mientras se envía una operación al destino remoto. El valor está en milisegundos y puede especificarse como para idle-timeout. Si se establece antes de cualquier especificación de destino, afecta a todos los destinos, a menos que se anule con cualquier directiva por destino.
nretries {forever|never|<<nretries>>}
Esta directiva define cuántas veces se debe reintentar el reenvío de una operación en caso de fallo temporal al contactar un destino. El número de reintentos es por operación, por lo que si primero es necesario un bind al destino, el número restante se decrementa. Si se define antes de cualquier especificación de destino, se aplica a todos los destinos (por defecto, 3 veces); el valor global puede ser anulado por redefiniciones dentro de cada especificación de destino.
subtree-{exclude|include} <regla>
Esta directiva permite indicar qué subárboles son realmente servidos por un destino. Ver slapd-meta(5) para más detalles.
suffixmassage <sufijo local> <sufijo remoto>
slapd-asyncmeta no admite el motor de reescritura utilizado por los backends LDAP y META. suffixmassage se puede utilizar para realizar la reescritura del sufijo DN, de la misma manera que la directiva obsoleta suffixmassage utilizada anteriormente por el backend LDAP.
t-f-support {NO|yes|discover}
habilitar si el servidor remoto admite filtros absolutos (ver RFC 4526 para más detalles). Si se establece en discover, el soporte se detecta leyendo el DSE raíz del servidor remoto. Si se establece antes de cualquier especificación de destino, afecta a todos los destinos, a menos que se anule con cualquier directiva por destino.
timeout [<op>=]<val> [...]
Esta directiva permite establecer tiempos de espera por operación. Las operaciones pueden ser

<op> ::= bind, add, delete, modrdn, modify, compare, search

Por defecto, el tiempo de espera para todas las operaciones es de 2 segundos.

Ver slapd-meta(5) para más detalles.

tls {none|[try-]start|[try-]propagate|ldaps}
B [starttls=no] [tls_cert=<archivo>] [tls_key=<archivo>] [tls_cacert=<archivo>] [tls_cacertdir=<ruta>] [tls_reqcert=never|allow|try|demand] [tls_reqsan=never|allow|try|demand] [tls_cipher_suite=<cifrados>] [tls_ecname=<nombres>] [tls_crlcheck=none|peer|all]
Especificar la configuración TLS para conexiones regulares.

Si el primer parámetro no es "none", entonces configura los ajustes TLS que se utilizarán para conexiones regulares. La operación extendida StartTLS se utilizará al establecer la conexión a menos que el esquema del protocolo de la directiva URI sea ldaps://. En ese caso, esta palabra clave solo puede establecerse en "ldaps" y la operación StartTLS no se utilizará.

Con propagate, el proxy emite la operación StartTLS solo si la conexión original tiene una capa TLS configurada. El prefijo try- instruye al proxy a continuar con las operaciones si la operación StartTLS falló; su uso no es recomendado.

La configuración TLS por defecto es la misma que la configuración TLS principal de slapd, excepto para tls_reqcert que por defecto es "demand", tls_reqsan que por defecto es "allow", y starttls que se ve eclipsado por la primera palabra clave y, por lo tanto, se ignora.

Si se establece antes de cualquier especificación de destino, afecta a todos los destinos, a menos que se anule con cualquier directiva por destino.

ESCENARIOS

Ver slapd-meta(5) para escenarios de configuración.

ACLs

El comportamiento de las ACLs es idéntico al de meta. Ver slapd-meta(5).

CONTROL DE ACCESO

El backend asyncmeta no respeta todos los semánticos de ACLs como se describe en slapd.access(5). En general, la verificación de acceso se delega al(los) servidor(es) remoto(s). Solo se respeta el acceso de lectura (=r) al pseudo-atributo entry y a los otros valores de atributos de las entradas devueltas por la operación search, que es realizada por el frontend.
