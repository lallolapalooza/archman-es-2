SLAPD-SOCK(5) Manual de formatos de archivo SLAPD-SOCK(5)

NOMBRE

slapd-sock - Backend/overlay de socket para slapd

SINOPSIS

/etc/openldap/slapd.conf

DESCRIPCIÓN

El backend de Socket para slapd(8) utiliza un programa externo para manejar consultas que escucha en un socket de dominio Unix. Esto permite tener un grupo de procesos, que persisten entre solicitudes. Esto permite operación multihilo y un alto nivel de eficiencia. El programa externo debe haber sido iniciado independientemente; slapd(8) en sí mismo no lo iniciará.

Este módulo también puede usarse como un overlay sobre alguna otra base de datos. Usarlo como overlay permite que acciones externas se activen en respuesta a operaciones en la base de datos principal.

CONFIGURACIÓN

Estas opciones de slapd.conf se aplican a la base de datos del backend SOCK. Es decir, deben seguir una línea "database sock" y aparecer antes de cualquier línea subsiguiente de "backend" o "database". Otras opciones de base de datos se describen en la página del manual slapd.conf(5).

Alternativamente, para usar este módulo como overlay, estas directivas deben seguir una línea "overlay sock" dentro de una definición de base de datos existente.

extensions [ binddn | peername | ssf | connid ]*
Habilita el envío de metadatos adicionales con cada solicitud. 
binddn: <DN enlazado>
peername: IP=<dirección>:<puerto>
ssf: <valor SSF>
connid: <ID de conexión>
socketpath <ruta>
Indica la ruta a un socket de dominio Unix al que se enviarán los comandos y del cual se recibirán las respuestas.

Cuando se usa como overlay, se definen estas directivas adicionales:

sockops [ bind | unbind | search | compare | modify | modrdn | add | delete | extended ]*
Especifica qué tipos de solicitud se enviarán al programa externo. El valor predeterminado es vacío (no se envían solicitudes).
sockresps [ result | search ]*
Especifica qué tipos de respuesta se enviarán al programa externo. "result" envía solo los resultados de una operación. "search" envía todas las entradas que la base de datos devolvió para una solicitud de búsqueda. El valor predeterminado es vacío (no se envían respuestas).
sockdnpat <regexp>
Especifica patrones de DN para los cuales actuará el overlay. Solo se procesarán las operaciones en DN que coincidan con la expresión regular especificada. El valor predeterminado es vacío (se procesan todos los DN).

PROTOCOLO

El protocolo utiliza una nueva línea para terminar los parámetros del comando. Los siguientes comandos se envían:

ADD
msgid: <ID del mensaje>
<repetir { "suffix:" <DN del sufijo de la base de datos> }>
<entrada en formato LDIF>
<línea en blanco>
BIND
msgid: <ID del mensaje>
<repetir { "suffix:" <DN del sufijo de la base de datos> }>
dn: <DN>
method: <número de método>
credlen: <longitud de <credenciales>>
cred: <credenciales>
<línea en blanco>
COMPARE
msgid: <ID del mensaje>
<repetir { "suffix:" <DN del sufijo de la base de datos> }>
dn: <DN>
<atributo>: <valor>
<línea en blanco>
DELETE
msgid: <ID del mensaje>
<repetir { "suffix:" <DN del sufijo de la base de datos> }>
dn: <DN>
<línea en blanco>
EXTENDED
msgid: <ID del mensaje>
<repetir { "suffix:" <DN del sufijo de la base de datos> }>
oid: <OID>
value: <valor codificado en base64>
<línea en blanco>
MODIFY
msgid: <ID del mensaje>
<repetir { "suffix:" <DN del sufijo de la base de datos> }>
dn: <DN>
<repetir {
    <"add"/"delete"/"replace">: <atributo>
    <repetir { <atributo>: <valor> }>
    -
}>
<línea en blanco>
MODRDN
msgid: <ID del mensaje>
<repetir { "suffix:" <DN del sufijo de la base de datos> }>
dn: <DN>
newrdn: <nuevo RDN>
deleteoldrdn: <0 o 1>
<si se especifica un nuevo superior: "newSuperior: <DN>">
<línea en blanco>
SEARCH
msgid: <ID del mensaje>
<repetir { "suffix:" <DN del sufijo de la base de datos> }>
base: <DN base>
scope: <0-2, ver ldap.h>
deref: <0-3, ver ldap.h>
sizelimit: <límite de tamaño>
timelimit: <límite de tiempo>
filter: <filtro>
attrsonly: <0 o 1>
attrs: <"todo" o lista de atributos separada por espacios>
<línea en blanco>
UNBIND
msgid: <ID del mensaje>
<repetir { "suffix:" <DN del sufijo de la base de datos> }>
<línea en blanco>

Los comandos, excepto unbind, deben generar:

RESULT
code: <entero>
matched: <DN coincidente>
info: <texto>
donde solo RESULT es obligatorio, y luego cerrar el socket. El RESULT de search debe ir precedido por las entradas en formato LDIF, cada entrada seguida por una línea en blanco. Las líneas que comienzan con `#` o `DEBUG:` se ignoran.

Cuando se usa como overlay, el programa externo debe devolver una respuesta CONTINUE si el procesamiento de la solicitud debe continuar normalmente, o una respuesta RESULT regular si el programa externo desea omitir la base de datos subyacente.

Si sockresps incluye result o search, el overlay también enviará mensajes de respuesta al programa externo (ver también LIMITACIONES CONOCIDAS). Estos aparecerán como un mensaje RESULT extendido o un mensaje ENTRY respectivamente, ambos se definen a continuación y no se espera que el programa responda a ellos.

El mensaje RESULT extendido es similar al anterior, pero también incluye el msgid y cualquier extensión configurada:

RESULT
msgid: <ID del mensaje>
code: <entero>
matched: <DN coincidente>
info: <texto>
<línea en blanco>

Típicamente, tanto el msgid como el connid serán necesarios para emparejar un mensaje de resultado con una solicitud. El mensaje ENTRY tiene la forma

ENTRY
msgid: <ID del mensaje>
<entrada en formato LDIF>
<línea en blanco>

LIMITACIONES CONOCIDAS

El backend sock no procesa resultados de operaciones extendidas de un programa externo.

Si se configura sockresps, el overlay sock no considera sockops ni sockdnpat para decidir qué respuestas se pasan al programa externo; en su lugar, actualmente se pasan todas las respuestas.

CONTROL DE ACCESO

El backend sock no respeta todas las semánticas de ACL descritas en slapd.access(5). En general, el acceso a los objetos se verifica utilizando un objeto ficticio que contiene solo el DN, por lo que las reglas de acceso que dependen del contenido del objeto no se respetan. En detalle:

La operación add no requiere acceso write (=w) al pseudo-atributo children de la entrada padre.

La operación bind requiere acceso auth (=x) al pseudo-atributo entry de la entrada cuya identidad se está evaluando; no se verifica el acceso auth (=x) a las credenciales, sino que se delega al programa subyacente.

La operación compare requiere acceso compare (=c) al pseudo-atributo entry del objeto cuyo valor se está afirmando; no se verifica el acceso compare (=c) al atributo cuyo valor se está afirmando.

La operación delete no requiere acceso write (=w) al pseudo-atributo children de la entrada padre.

La operación modify requiere acceso write (=w) al pseudo-atributo entry; no se verifica el acceso write (=w) a los atributos específicos que se modifican.

La operación modrdn no requiere acceso write (=w) al pseudo-atributo children de la entrada padre, ni al del nuevo padre, si es diferente; acceso write (=w)

NAME

slapd-sock - socket backend for slapd

SYNOPSIS

Slapd configuration file:

    database sock
    socketdir <directory>
    socktype <type>

DESCRIPTION

The sock backend is a generic backend for slapd(8) that provides a way to proxy LDAP operations to an external program listening on a Unix domain socket. The external program is responsible for implementing LDAP logic itself.

The backend supports the following configuration options:

socketdir <directory>
Specifies the directory where the socket file for this backend will be created. This directory must be writable by the user running slapd(8).
socktype <type>
Specifies the type of socket to create. Supported types are stream (for SOCK_STREAM sockets) and dgram (for SOCK_DGRAM sockets). Defaults to stream.

The database backend name is sock. This backend does not support any advanced features like replication, OLCs, or dynamic configurations.

CONFIGURATION

The sock backend is configured using the standard slapd.conf(5) file format or via dynamic configuration using LDAP schema and tools.

Example configuration using slapd.conf:

    database sock
    socketdir /var/run/openldap
    socktype stream

This configuration creates a Unix domain socket named /var/run/openldap/ldapsock (assuming the database is named ldapsock) of type stream.

The external program needs to be able to communicate with slapd using the LDAP protocol over the specified socket. For details on the communication protocol, refer to the documentation of the external program.

PROTOCOL

The sock backend communicates with the external program using the LDAP protocol. The external program acts as an LDAP server and handles LDAP requests sent by slapd.

The backend forwards the following operations to the external program:

  • Bind
  • Search
  • Add
  • Delete
  • Modify
  • Compare
  • Extended operations

The external program must implement the LDAP protocol and respond to these operations appropriately. The backend itself does not perform any LDAP processing.

KNOWN LIMITATIONS

The sock backend is a simple proxy and has several limitations:

  • It does not support any kind of caching.
  • It does not support replication.
  • It does not support advanced access control mechanisms. Access control must be handled by the external program.
  • It does not support modify RDN operations.

ACCESS CONTROL

The sock backend relies entirely on the external program for access control. The backend itself does not enforce any access controls.

The external program must implement its own access control logic to determine whether a client is allowed to perform a requested operation.

The bind operation requires auth access to the entry being bound. The add operation requires add access to the parent entry. The delete operation requires delete access to the entry being deleted. The modify operation requires write access to the entry being modified. The search operation requires search access to the base entry of the search.

The check for the read permission on the attributes requested in a search operation is not performed by the backend; it is up to the external program to check this.

The search operation does not require search (=s) access to the entry pseudo_attribute of the searchBase; search (=s) access to the attributes and values used in the filter is not checked.

The extended operation does not require any access special rights. The external program has to implement any sort of access control.

EXAMPLE

There is an example script in the slapd/back-sock/ directory in the OpenLDAP source tree.

FILES

/etc/openldap/slapd.conf
default slapd configuration file
