SLIRP4NETNS(1) Comandos de Usuario SLIRP4NETNS(1)

NOMBRE

slirp4netns - Red en modo de usuario para namespaces de red sin privilegios

SINOPSIS

slirp4netns [OPCIÓN]... PID|RUTA|FD [NOMBRE_TAP]

DESCRIPCIÓN

slirp4netns proporciona red en modo de usuario ("slirp") para namespaces de red.

A diferencia de veth(4), slirp4netns no requiere privilegios de root en el host.

Configuración por defecto:

  • MTU: 1500
  • CIDR: 10.0.2.0/24
  • Gateway/Host: 10.0.2.2 (dirección de red + 2)
  • DNS: 10.0.2.3 (dirección de red + 3)
  • Inicio DHCP: 10.0.2.15 (dirección de red + 15)
  • Fin DHCP: 10.0.2.30 (dirección de red + 30)
  • CIDR IPv6: fd00::/64
  • Gateway/Host IPv6: fd00::2
  • DNS IPv6: fd00::3

OPCIONES

-c, --configure activa la interfaz TAP. La IP se establecerá en 10.0.2.100 (dirección de red + 100) por defecto. La interfaz de loopback (lo) también se activará. A partir de la v0.4.0, la interfaz de loopback (lo) se activa también.

-e, --exit-fd=FD especifica el FD para terminar slirp4netns. Cuando se especifica el FD, slirp4netns sale cuando ocurre un evento poll(2) en el FD.

-r, --ready-fd=FD especifica el FD al que escribir cuando se terminan los pasos de inicialización. Cuando se especifica el FD, slirp4netns escribe "1" en el FD y cierra el FD. Antes de la v0.4.0, el FD se escribía después de la configuración de red (-c) pero antes de la configuración del socket de API (-a).

-m, --mtu=MTU (desde v0.2.0) especifica MTU (máx=65521).

-6, --enable-ipv6 (desde v0.2.0, EXPERIMENTAL) habilita IPv6

-a, --api-socket (desde v0.3.0) ruta del socket de API

--cidr (desde v0.3.0) especifica CIDR, ej. 10.0.2.0/24

--disable-host-loopback (desde v0.3.0) prohíbe la conexión a 127.0.0.1:* en el namespace del host

--netns-type=TYPE (desde v0.4.0) especifica el tipo de namespace de red ([path|pid|tapfd], por defecto=pid)

Si el tipo de namespace es tapfd, se espera que el primer argumento posicional sea un descriptor de archivo heredado que corresponda a una conexión /dev/net/tun. Esto entra en conflicto con --configure y se ignora un NOMBRE_TAP.

--userns-path=PATH (desde v0.4.0) especifica la ruta del namespace de usuario

--enable-sandbox (desde v0.4.0) entra en el namespace de usuario y crea un nuevo namespace de montaje donde solo /etc y /run se montan desde el host.

Requiere que /etc/resolv.conf no sea un enlace simbólico a un archivo fuera de /etc y /run.

Al ejecutarse como root, el proceso no entra en el namespace de usuario, pero se eliminan todas las capacidades excepto CAP_NET_BIND_SERVICE.

--enable-seccomp (desde v0.4.0, EXPERIMENTAL) habilita seccomp(2) para limitar las llamadas al sistema. Normalmente se usa en conjunción con --enable-sandbox.

--outbound-addr=IPv4 (desde v1.1.0, EXPERIMENTAL) especifica la dirección ipv4 saliente a la que slirp debe enlazarse

--outbound-addr=INTERFAZ (desde v1.1.0, EXPERIMENTAL) especifica la interfaz saliente a la que slirp debe enlazarse (solo tráfico ipv4)

--outbound-addr=IPv6 (desde v1.1.0, EXPERIMENTAL) especifica la dirección ipv6 saliente a la que slirp debe enlazarse

--outbound-addr6=INTERFAZ (desde v1.1.0, EXPERIMENTAL) especifica la interfaz saliente a la que slirp debe enlazarse (solo tráfico ipv6)

--disable-dns (desde v1.1.0) deshabilita el DNS incorporado (10.0.2.3 por defecto)

--macaddress (desde v1.1.9) especifica la dirección MAC de la interfaz TAP (solo válido con -c)

--target-type=TYPE (desde v1.2.0) especifica el tipo de destino ([netns|bess], por defecto=netns).

El modo bess (desde v1.2.0, EXPERIMENTAL) se espera que se use con User Mode Linux. El modo bess entra en conflicto con --configure, --netns-type y --userns-path.

-h, --help (desde v0.2.0) muestra la ayuda y sale

-v, --version (desde v0.2.0) muestra la versión y sale

EJEMPLO

Terminal 1: Crear namespaces de usuario/red/montaje

(host)$ unshare --user --map-root-user --net --mount
(namespace)$ echo $$ > /tmp/pid

En esta documentación, usamos (host)$ como el prompt del shell del host, (namespace)$ como el prompt del shell que se ejecuta en los namespaces.

Si unshare falla, intente los siguientes comandos (conocidos por ser necesarios en Debian, Arch y versiones antiguas de CentOS 7.X):

(host)$ sudo sh -c 'echo "user.max_user_namespaces=28633" >> /etc/sysctl.d/userns.conf'
(host)$ if [ -f /proc/sys/kernel/unprivileged_userns_clone ]; then sudo sh -c 'echo "kernel.unprivileged_userns_clone=1" >> /etc/sysctl.d/userns.conf'; fi
(host)$ sudo sysctl --system

Terminal 2: Iniciar slirp4netns

(host)$ slirp4netns --configure --mtu=65520 $(cat /tmp/pid) tap0
starting slirp, MTU=65520

Terminal 1: Asegurarse de que tap0 está configurado y conectado a Internet

(namespace)$ ip a
1: lo: <LOOPBACK> mtu 65536 qdisc noop state DOWN group default qlen 1000
    link/loopback 00:00:00:00:00:00 brd 00:00:00:00:00:00
3: tap0: <BROADCAST,UP,LOWER_UP> mtu 65520 qdisc fq_codel state UNKNOWN group default qlen 1000
    link/ether c2:28:0c:0e:29:06 brd ff:ff:ff:ff:ff:ff
    inet 10.0.2.100/24 brd 10.0.2.255 scope global tap0
       valid_lft forever preferred_lft forever
    inet6 fe80::c028:cff:fe0e:2906/64 scope link 
       valid_lft forever preferred_lft forever
(namespace)$ echo "nameserver 10.0.2.3" > /tmp/resolv.conf
(namespace)$ mount --bind /tmp/resolv.conf /etc/resolv.conf
(namespace)$ curl https://example.com

Montar mediante enlace /etc/resolv.conf solo es necesario cuando /etc/resolv.conf en el host hace referencia a direcciones de loopback (127.0.0.X, típicamente dnsmasq(8) o systemd-resolved.service(8)) a las que no se puede acceder desde el namespace.

Si su /etc/resolv.conf en el host es gestionado por networkmanager(8) o systemd-resolved.service(8), es posible que necesite montar un nuevo sistema de archivos en /etc en su lugar, para evitar que el nuevo /etc/resolv.conf se desmonte inesperadamente cuando se regenere /etc/resolv.conf en el host.

(namespace)$ mkdir /tmp/a /tmp/b
(namespace)$ mount --rbind /etc /tmp/a
(namespace)$ mount --rbind /tmp/b /etc
(namespace)$ mkdir /etc/.ro
(namespace)$ mount --move /tmp/a /etc/.ro
(namespace)$ cd /etc
(namespace)$ for f in .ro/*; do ln -s $f $(basename $f); done
(namespace)$ rm resolv.conf
(namespace)$ echo "nameserver 10.0.2.3" > resolv.conf
(namespace)$ curl https://example.com

Estos pasos se pueden simplificar con rootlesskit --copy-up=/etc si rootlesskit está instalado:

(host)$ rootlesskit --net=slirp4netns --copy-up=/etc bash
(namespace)$ cat /etc/resolv.conf
nameserver 10.0.2.3

ENRUTAMIENTO PAQUETES PING

Para enrutar paquetes ping, es posible que necesite configurar adecuadamente net.ipv4.ping_group_range como root.

ej.

(host)$ sudo sh -c 'echo "net.ipv4.ping_group_range=0   2147483647" > /etc/sysctl.d/ping_group_range.conf'
(host)$ sudo sysctl --system

FILTRADO DE CONEXIONES

Por defecto, los puertos que escuchan en INADDR_LOOPBACK (127.0.0.1) en el host son accesibles desde el namespace hijo a través del gateway (por defecto: 10.0.2.2). --disable-host-loopback puede usarse para prohibir la conexión a INADDR_LOOPBACK en el host.

Sin embargo, una dirección de loopback del host podría seguir siendo accesible a través del DNS incorporado (por defecto: 10.0.2.3) si /etc/resolv.conf en el host hace referencia a una dirección de loopback. Es posible que desee configurar iptables para limitar el acceso al DNS incorporado en tal caso.

(host)$ nsenter -t $(cat /tmp/pid) -U --p

API SOCKET

slirp4netns puede proporcionar un servidor API similar a QMP a través de un archivo de socket UNIX:

(host)$ slirp4netns --api-socket /tmp/slirp4netns.sock ...

add_hostfwd: Exponer un puerto (solo IPv4)

(namespace)$ json='{"execute": "add_hostfwd", "arguments": {"proto": "tcp", "host_addr": "0.0.0.0", "host_port": 8080, "guest_addr": "10.0.2.100", "guest_port": 80}}'
(namespace)$ echo -n $json | nc -U /tmp/slirp4netns.sock
{"return": {"id": 42}}

Si no se especifica host_addr, se usará por defecto "0.0.0.0".

Si no se especifica guest_addr, se establecerá a la dirección por defecto que corresponde a --configure.

list_hostfwd: Listar puertos expuestos

(namespace)$ json='{"execute": "list_hostfwd"}'
(namespace)$ echo -n $json | nc -U /tmp/slirp4netns.sock
{"return": {"entries": [{"id": 42, "proto": "tcp", "host_addr": "0.0.0.0", "host_port": 8080, "guest_addr": "10.0.2.100", "guest_port": 80}]}}

remove_hostfwd: Eliminar un puerto expuesto

(namespace)$ json='{"execute": "remove_hostfwd", "arguments": {"id": 42}}'
(namespace)$ echo -n $json | nc -U /tmp/slirp4netns.sock
{"return": {}}

Comentarios:

  • El cliente necesita cerrar la conexión (shutdown con SHUT_WR) al socket después de enviar cada solicitud. Es decir, no hay soporte para conexión persistente ni tiempo de espera.
  • slirp4netns "detiene el mundo" durante el procesamiento de solicitudes de API.
  • Una solicitud debe tener menos de 4096 bytes.
  • Las respuestas JSON pueden contener error en lugar de return.

RUTAS DE NAMESPACE DEFINIDAS

Un usuario puede definir una ruta de namespace de red en lugar del ID de proceso por defecto:

(host)$ slirp4netns --netns-type=path ... /ruta/a/netns tap0

Actualmente, el argumento netns-type=TIPO soporta los argumentos path o pid, siendo pid el valor por defecto.

Además, se puede incluir el argumento --userns-path=RUTA para anular cualquier valor por defecto de la ruta del namespace de usuario.

(host)$ slirp4netns --netns-type=path --userns-path=/ruta/a/userns /ruta/a/netns tap0

DIRECCIONES DE SALIDA

Un usuario puede definir direcciones preferidas de salida IPv4 e IPv6 en escenarios de IPs múltiples.

(host)$ slirp4netns --outbound-addr=10.2.2.10 --outbound-addr6=fe80::10 ...

Opcionalmente, se pueden usar nombres de interfaz en lugar de direcciones IP.

(host)$ slirp4netns --outbound-addr=eth0 --outbound-addr6=eth0 ...

COMUNICACIÓN ENTRE NAMESPACES

La forma más sencilla de permitir la comunicación entre namespaces es anidar namespaces de red dentro del namespace de red de slirp4netns.

(host)$ nsenter -t $(cat /tmp/pid) -U --preserve-credentials -n -m
(namespace)$ mount -t tmpfs none /run
(namespace)$ ip netns add foo
(namespace)$ ip netns add bar
(namespace)$ ip link add veth-foo type veth peer name veth-bar
(namespace)$ ip link set veth-foo netns foo
(namespace)$ ip link set veth-bar netns bar
(namespace)$ ip netns exec foo ip link set veth-foo name eth0
(namespace)$ ip netns exec bar ip link set veth-bar name eth0
(namespace)$ ip netns exec foo ip link set lo up
(namespace)$ ip netns exec bar ip link set lo up
(namespace)$ ip netns exec foo ip link set eth0 up
(namespace)$ ip netns exec bar ip link set eth0 up
(namespace)$ ip netns exec foo ip addr add 192.168.42.100/24 dev eth0
(namespace)$ ip netns exec bar ip addr add 192.168.42.101/24 dev eth0
(namespace)$ ip netns exec bar ping 192.168.42.100

Sin embargo, este método no funciona cuando se desea permitir la comunicación entre múltiples instancias de slirp4netns. Para permitir la comunicación entre múltiples instancias de slirp4netns, se necesita combinar otra pila de red como vde_plug(1) con slirp4netns.

(host)$ vde_plug --daemon switch:///tmp/switch null://
(host)$ nsenter -t $(cat /tmp/pid-instance0) -U --preserve-credentials -n
(namespace-instance0)$ vde_plug --daemon vde:///tmp/switch tap://vde
(namespace-instance0)$ ip link set vde up
(namespace-instance0)$ ip addr add 192.168.42.100/24 dev vde
(namespace-instance0)$ exit
(host)$ nsenter -t $(cat /tmp/pid-instance1) -U --preserve-credentials -n
(namespace-instance1)$ vde_plug --daemon vde:///tmp/switch tap://vde
(namespace-instance1)$ ip link set vde up
(namespace-instance1)$ ip addr add 192.168.42.101/24 dev vde
(namespace-instance1)$ ping 192.168.42.100

COMUNICACIÓN ENTRE HOSTS

VXLAN funciona bien. Consulte el proyecto Usernetes para ver un ejemplo de clúster Kubernetes multi-nodo sin root con VXLAN: https://github.com/rootless-containers/usernetes

MODO BESS (PARA USER MODE LINUX)

slirp4netns (desde la versión 1.2.0) también puede usarse como un servidor compatible con BESS para proporcionar conectividad de red a User Mode Linux.

Terminal 1: Iniciar slirp4netns

(host)$ slirp4netns --target-type=bess /tmp/bess.sock

Terminal 2: Iniciar User Mode Linux

(host)$ linux.uml vec0:transport=bess,dst=/tmp/bess.sock,depth=128,gro=1 root=/dev/root rootfstype=hostfs init=/bin/bash mem=2G
(UML)$ ip addr add 10.0.2.100/24 dev vec0
(UML)$ ip link set vec0 up
(UML)$ ip route add default via 10.0.2.2

Actualmente, solo se puede conectar una instancia de User Mode Linux al servidor BESS de slirp4netns.

Consulte también la documentación de User Mode Linux: https://www.kernel.org/doc/html/latest/virt/uml/user_mode_linux_howto_v2.html#bess-socket-transport

BUGS

El kernel 4.20 aumentó el valor por defecto de /proc/sys/net/ipv4/tcp_rmem de 87380 a 131072. Esto es conocido por ralentizar el reenvío de puertos en slirp4netns: https://github.com/rootless-containers/slirp4netns/issues/128.

Como solución temporal, puede ajustar el valor de /proc/sys/net/ipv4/tcp_rmem dentro del namespace. No se necesita un verdadero privilegio de root para modificar el archivo desde el kernel 4.15.

(host)$ nsenter -t $(cat /tmp/pid) -U --preserve-credentials -n -m
(namespace)$ c=$(cat /proc/sys/net/ipv4/tcp_rmem); echo $c | sed -e s/131072/87380/g > /proc/sys/net/ipv4/tcp_rmem
