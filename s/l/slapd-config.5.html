NOMBRE

slapd-config - backend de configuración para slapd

SINOPSIS

/etc/openldap/slapd.d

DESCRIPCIÓN

El backend config gestiona toda la información de configuración del demonio slapd(8). Esta información de configuración también es utilizada por las herramientas SLAPD slapacl(8), slapadd(8), slapauth(8), slapcat(8), slapdn(8), slapindex(8), slapmodify(8), y slaptest(8).

El backend config es compatible con versiones anteriores del archivo slapd.conf(5) pero proporciona la capacidad de cambiar la configuración dinámicamente en tiempo de ejecución. Si slapd se ejecuta solo con un archivo slapd.conf, se permitirán cambios dinámicos pero no persistirán tras un reinicio del servidor. Los cambios dinámicos solo se guardan cuando slapd se está ejecutando desde un directorio de configuración slapd.d.

A diferencia de otros backends, solo puede haber una instancia del backend config, y la mayor parte de su estructura está predefinida. La raíz de la base de datos está codificada como cn=config y esta entrada raíz contiene la configuración global para slapd. Múltiples entradas hijas debajo de la entrada raíz se utilizan para llevar otras configuraciones varias:

cn=Module
módulos cargados dinámicamente
cn=Schema
definiciones de esquema
olcBackend=xxx
configuración específica del backend
olcDatabase=xxx
configuración específica de la base de datos

Las entradas cn=Module solo aparecerán en configuraciones donde slapd fue compilado con soporte para módulos cargados dinámicamente. Puede haber múltiples entradas, una por cada ruta de módulo configurada. Dentro de cada entrada habrá valores registrados para cada módulo cargado en una ruta dada. Estas entradas no tienen hijos.

La entrada cn=Schema contiene todos los elementos de esquema codificados. Los hijos de esta entrada contienen todos los elementos de esquema definidos por el usuario. En esquemas que se cargaron desde archivos de inclusión, la entrada hija se nombrará según el archivo de inclusión del cual se cargó el esquema. Típicamente, la primera hija en este subárbol será cn=core,cn=schema,cn=config.

Las entradas olcBackend son para almacenar configuraciones específicas de un solo tipo de backend (y por lo tanto globales para todas las instancias de base de datos de ese tipo). Actualmente, solo back-mdb implementa alguna opción de este tipo, por lo que esta configuración no es necesaria para ningún otro backend.

Las entradas olcDatabase almacenan configuraciones específicas de una sola instancia de base de datos. Estas entradas pueden tener entradas hijas olcOverlay que correspondan a cualquier overlay configurado en la base de datos. Las entradas olcDatabase y olcOverlay también pueden tener entradas hijas misceláneas para otras configuraciones según sea necesario. Hay dos entradas de base de datos especiales que están predefinidas: una es una entrada para la propia base de datos de configuración, y la otra es para la base de datos "frontend". Las configuraciones en la base de datos frontend son heredadas por las otras bases de datos, a menos que sean explícitamente anuladas en una base de datos específica.

Las opciones de configuración específicas se discuten a continuación en Opciones de Configuración Global, Opciones Generales de Backend y Opciones Generales de Base de Datos. Las opciones se establecen definiendo atributos LDAP con valores específicos. En general, los nombres de los atributos LDAP son los mismos que las palabras clave correspondientes de slapd.conf, con el prefijo "olc" añadido.

El analizador para muchos de estos atributos es el mismo que se usa para analizar las palabras clave de slapd.conf. Como tal, las palabras clave de slapd.conf que permiten especificar múltiples elementos en una línea, separados por espacios en blanco, permitirán especificar múltiples elementos en un valor de atributo. Sin embargo, al leer el atributo a través de LDAP, los elementos se devolverán como valores de atributo individuales.

Las opciones específicas del backend se discuten en las páginas del manual slapd-<backend>(5). Consulte la "Guía del Administrador de OpenLDAP" para obtener más detalles sobre la configuración de slapd.

OPCIONES DE CONFIGURACIÓN GLOBALES

Las opciones descritas en esta sección se aplican al servidor en su conjunto. Los argumentos que deben ser reemplazados por texto real se muestran entre corchetes <>.

Estas opciones solo se pueden especificar en la entrada cn=config. Esta entrada debe tener un objectClass de olcGlobal.

olcAllows: <características>
Especifica un conjunto de características permitidas (por defecto, ninguna). bind_v2 permite la aceptación de solicitudes de bind LDAPv2. Tenga en cuenta que slapd(8) no implementa realmente LDAPv2 (RFC 1777), ahora Histórico (RFC 3494). bind_anon_cred permite el bind anónimo cuando las credenciales no están vacías (por ejemplo, cuando el DN está vacío). bind_anon_dn permite el bind no autenticado (anónimo) cuando el DN no está vacío. update_anon permite que se procesen operaciones de actualización no autenticadas (anónimas) (sujeto a controles de acceso y otros límites administrativos). proxy_authz_anon permite que se procese el control de autorización proxy no autenticado (anónimo) (sujeto a controles de acceso, autorización y otros límites administrativos).
olcArgsFile: <nombre_archivo>
El nombre (absoluto) de un archivo que contendrá la línea de comandos del servidor slapd (nombre del programa y opciones).
olcAttributeOptions: <nombre-opción>...
Define opciones de atributo de etiquetado o prefijos de etiqueta/rango. Las opciones no deben terminar en `-', los prefijos deben terminar en `-'. El prefijo `lang-' está predefinido. Si usa la directiva olcAttributeOptions, `lang-' ya no se definirá y debe especificarlo explícitamente si desea que se defina.

Una descripción de atributo con una opción de etiquetado es un subtipo de la descripción de atributo sin la opción. Excepto por eso, las opciones definidas de esta manera no tienen semántica especial. Los prefijos definidos de esta manera funcionan como las opciones `lang-': Definen un prefijo para las opciones de etiquetado que comienzan con el prefijo. Es decir, si define el prefijo `x-foo-', puede usar la opción `x-foo-bar'. Además, en una búsqueda o comparación, un nombre de prefijo o rango (con un `-` al final) coincide con todas las opciones que comienzan con ese nombre, así como con la opción con el nombre de rango sin el `-` al final. Es decir, `x-foo-bar-' coincide con `x-foo-bar' y `x-foo-bar-baz'.

RFC 4520 reserva opciones que comienzan con `x-' para experimentos privados. Otras opciones deben registrarse con IANA, ver la sección 3.5 de RFC 4520. OpenLDAP también tiene la opción `binary' incorporada, pero esta es una opción de transferencia, no una opción de etiquetado.

olcAuthIDRewrite: <regla-reescritura>
Utilizado por el framework de autenticación para convertir nombres de usuario simples en un DN LDAP utilizado para fines de autorización. Su propósito es análogo al de olcAuthzRegexp (ver más abajo). La regla-reescritura es un conjunto de reglas análogo a las descritas en slapo-rwm(5) para la reescritura de datos (después de eliminar el prefijo rwm-). olcAuthIDRewrite y olcAuthzRegexp no deben mezclarse.

El consumidor slapd enviará solicitudes de búsqueda al proveedor slapd de acuerdo con la especificación de búsqueda. La especificación de búsqueda incluye los parámetros searchbase, scope, filter, attrs, attrsonly, sizelimit y timelimit, como en la especificación de búsqueda normal. La opción exattrs también puede usarse para especificar atributos que deben omitirse de las entradas entrantes. El scope por defecto es sub, el filter por defecto es (objectclass=*), y no hay un searchbase por defecto. La lista attrs por defecto es "*,+" para devolver todos los atributos de usuario y operacionales, y attrsonly y exattrs no están definidos por defecto. Los parámetros sizelimit y timelimit solo aceptan "ilimitado" e enteros positivos, y ambos por defecto son "ilimitado". Los parámetros sizelimit y timelimit definen una limitación solicitada por el consumidor en el número de entradas que pueden ser devueltas por la operación LDAP Content Synchronization; estos deben dejarse sin cambios de los valores predeterminados, de lo contrario, la replicación podría no tener éxito. Tenga en cuenta, sin embargo, que cualquier límite del lado del proveedor para la identidad de replicación será aplicado por el proveedor independientemente de los límites solicitados por la operación LDAP Content Synchronization, al igual que para cualquier otra operación de búsqueda.

El protocolo LDAP Content Synchronization tiene dos tipos de operación. En la operación refreshOnly, la próxima operación de búsqueda de sincronización se reprograma periódicamente en un intervalo de tiempo (especificado por el parámetro interval; 1 día por defecto) después de que cada operación de sincronización finaliza. En la operación refreshAndPersist, una búsqueda de sincronización permanece persistente en el slapd del proveedor. Las actualizaciones posteriores al proveedor generarán searchResultEntry al slapd del consumidor como respuestas a la búsqueda de la búsqueda de sincronización persistente. Si la búsqueda inicial falla debido a un error, la próxima operación de búsqueda de sincronización se reprograma periódicamente en un intervalo de tiempo (especificado por el parámetro interval; 1 día por defecto)

Si ocurre un error durante la replicación, el consumidor intentará volver a conectarse de acuerdo con el parámetro retry, que es una lista de pares de <intervalo de reintento> y <# de reintentos>. Por ejemplo, retry="60 10 300 3" permite que el consumidor intente cada 60 segundos durante las primeras 10 veces y luego intente cada 300 segundos durante las siguientes 3 veces antes de dejar de intentar. El '+' en <# de reintentos> significa un número indefinido de reintentos hasta el éxito. Si no se especifica retry, por defecto syncrepl reintenta cada hora indefinidamente.

La verificación del esquema puede ser forzada en el sitio consumidor de LDAP Sync activando el parámetro schemachecking. El valor por defecto es off. La verificación del esquema on significa que las entradas replicadas deben tener una objectClass estructural, deben obedecer los requisitos de objectClass en términos de atributos requeridos/permitidos, y que los atributos de nomenclatura y los valores distinguidos deben estar presentes. Como consecuencia, la verificación del esquema debe estar en off cuando se utiliza replicación parcial.

El parámetro network-timeout establece cuánto tiempo esperará el consumidor para establecer una conexión de red con el proveedor. Una vez establecida la conexión, el parámetro timeout determina cuánto tiempo esperará el consumidor a que se complete la solicitud Bind inicial. Los valores predeterminados para estos parámetros provienen de ldap.conf(5). El parámetro tcp-user-timeout, si no es cero, corresponde al TCP_USER_TIMEOUT establecido en las conexiones de destino, anulando la configuración del sistema operativo. Solo algunos sistemas admiten la personalización de este parámetro; de lo contrario, se ignora y se utilizan las configuraciones a nivel de sistema.

Un bindmethod de simple requiere las opciones binddn y credentials y solo debe usarse cuando existen servicios de seguridad adecuados (por ejemplo, TLS o IPSEC). ¡RECUERDE: las credenciales de bind simple deben estar en texto plano! Un bindmethod de sasl requiere la opción saslmech. Dependiendo del mecanismo, una identidad de autenticación y/o credenciales pueden especificarse usando authcid y credentials. El parámetro authzid puede usarse para especificar una identidad de autorización. Propiedades de seguridad específicas (como con la palabra clave sasl-secprops anterior) para un bind SASL pueden configurarse con la opción secprops. Un dominio SASL no predeterminado puede configurarse con la opción realm. La identidad utilizada para la sincronización por el consumidor debe permitir recibir un número ilimitado de entradas en respuesta a una solicitud de búsqueda. El proveedor, además de permitir la autenticación de la identidad syncrepl, debe otorgar a esa identidad los privilegios de acceso apropiados a los datos que se están replicando (directiva access), y los límites de tiempo y tamaño apropiados. Esto se puede lograr permitiendo sizelimit y timelimit ilimitados, o configurando una declaración limits apropiada en la configuración del consumidor (ver sizelimit y limits para detalles).

El parámetro keepalive establece los valores de idle, probes e interval utilizados para verificar si un socket está vivo; idle es el número de segundos que una conexión debe permanecer inactiva antes de que TCP comience a enviar sondas keepalive; probes es el número máximo de sondas keepalive que TCP debe enviar antes de desconectar la conexión; interval es el intervalo en segundos entre sondas keepalive individuales. Solo algunos sistemas admiten la personalización de estos valores; de lo contrario, el parámetro keepalive se ignora y se utilizan las configuraciones a nivel de sistema.

El parámetro starttls especifica el uso de la operación extendida StartTLS para establecer una sesión TLS antes de enlazar al proveedor. Si se proporciona el argumento critical, la sesión se abortará si la solicitud StartTLS falla. De lo contrario, la sesión syncrepl continuará sin TLS. La configuración tls_reqcert por defecto es "demand", la configuración tls_reqsan por defecto es "allow", y las otras configuraciones TLS por defecto son las mismas que las configuraciones TLS principales de slapd.

El parámetro suffixmassage permite al consumidor extraer entradas de un directorio remoto cuyo sufijo DN difiere del directorio local. La porción de los DN de las entradas remotas que coincide con el searchbase será reemplazada con el DN de suffixmassage.

En lugar de replicar entradas completas, el consumidor puede consultar los registros de modificaciones de datos. Este modo de operación se denomina delta syncrepl. Además de los parámetros anteriores, los parámetros logbase y logfilter deben configurarse apropiadamente para el registro que se utilizará. El parámetro syncdata debe establecerse en "accesslog" si el registro se ajusta al formato de registro de slapo-accesslog(5), o "changelog" si el registro se ajusta al formato obsoleto changelog. Si el parámetro syncdata se omite o se establece en "default", los parámetros de registro se ignoran.

El parámetro lazycommit indica a la base de datos subyacente que puede almacenar cambios sin realizar un volcado completo después de cada cambio. Esto puede mejorar el rendimiento del consumidor, a costa de la seguridad o durabilidad.

olcUpdateDN: <dn>
Esta opción solo es aplicable en una base de datos réplica. Especifica el DN permitido para actualizar (sujeto a controles de acceso) la réplica. Solo es necesario en ciertos escenarios de replicación en modo push. Generalmente, este DN no debería ser el mismo que el rootdn utilizado en el proveedor.

olcUpdateRef

olcUpdateRef: <url>
Especifica la referencia a devolver cuando se le pide a slapd(8) que modifique una base de datos local replicada. Si se especifican varios valores, se proporciona cada url.

OPCIONES ESPECÍFICAS DE LA BASE DE DATOS

Cada base de datos puede permitir opciones de configuración específicas; están documentadas por separado en las páginas del manual de los backends. Consulte la página del manual de slapd.backends(5) para obtener una descripción general de los backends disponibles.

SOBREESCRITURAS

Una sobreescritura es un fragmento de código que intercepta las operaciones de la base de datos para extenderlas o modificarlas. Las sobreescrituras se colocan en una pila sobre la base de datos, por lo que se ejecutarán en el orden inverso al que fueron configuradas, y la propia base de datos recibirá el control en último lugar.

Las sobreescrituras deben configurarse como entradas hijas de una base de datos específica. El RDN de la entrada debe tener el formato olcOverlay={x}<tiposobreescritura> y la entrada debe tener la clase de objeto olcOverlayConfig. Normalmente, el motor de configuración genera automáticamente el índice "{x}" en el RDN, por lo que se puede omitir al cargar inicialmente estas entradas.

Consulte la página del manual de slapd.overlays(5) para obtener una descripción general de las sobreescrituras disponibles.

EJEMPLOS

Aquí hay un breve ejemplo de una configuración en LDIF adecuada para su uso con slapadd(8):

dn: cn=config
objectClass: olcGlobal
cn: config
olcPidFile: /var/lib/openldap/run/slapd.pid
olcAttributeOptions: x-hidden lang-
dn: cn=schema,cn=config
objectClass: olcSchemaConfig
cn: schema
include: file:///etc/openldap/schema/core.ldif
dn: olcDatabase=frontend,cn=config
objectClass: olcDatabaseConfig
objectClass: olcFrontendConfig
olcDatabase: frontend
# Subtipos de "name" (por ejemplo, "cn" y "ou") con la
# opción ";x-hidden" se pueden buscar/comparar,
# pero no se muestran. Ver slapd.access(5).
olcAccess: to attrs=name;x-hidden by * =cs
# Proteger contraseñas. Ver slapd.access(5).
olcAccess: to attrs=userPassword  by * auth
# Acceso de lectura a otros atributos y entradas.
olcAccess: to * by * read
# establecer una rootpw para la base de datos de configuración para que podamos enlazar.
# denegar el acceso a todos los demás.
dn: olcDatabase=config,cn=config
objectClass: olcDatabaseConfig
olcDatabase: config
olcRootPW: {SSHA}XKYnrjvGT3wZFQrDD5040US592LxsdLy
olcAccess: to * by * none
dn: olcDatabase=mdb,cn=config
objectClass: olcDatabaseConfig
objectClass: olcMdbConfig
olcDatabase: mdb
olcSuffix: "dc=our-domain,dc=com"
# El directorio de la base de datos DEBE existir antes de
# ejecutar slapd Y solo debe ser accesible
# por slapd/herramientas. Se recomienda modo 0700.
olcDbDirectory: /var/lib/openldap/openldap-data
# Índices a mantener
olcDbIndex:     objectClass  eq
olcDbIndex:     cn,sn,mail   pres,eq,approx,sub
# Servimos a clientes pequeños que no manejan referencias,
# así que manejamos las búsquedas remotas en su nombre.
dn: olcDatabase=ldap,cn=config
objectClass: olcDatabaseConfig
objectClass: olcLdapConfig
olcDatabase: ldap
olcSuffix: ""
olcDbUri: ldap://ldap.some-server.com/

Suponiendo que los datos anteriores se guardaron en un archivo llamado "config.ldif" y se creó el directorio /etc/openldap/slapd.d, este comando inicializará la configuración:

slapadd -F /etc/openldap/slapd.d -n 0 -l config.ldif

"OpenLDAP Administrator's Guide" contiene un ejemplo más largo y anotado de una configuración de slapd.

Alternativamente, un archivo slapd.conf existente puede ser convertido al nuevo formato usando slapd o cualquiera de las herramientas slap:

slaptest -f /etc/openldap/slapd.conf -F /etc/openldap/slapd.d
