SLAPD-RELAY(5) Manual de formatos de archivo SLAPD-RELAY(5)

NOMBRE

slapd-relay - backend de retransmisión para slapd

SINOPSIS

/etc/openldap/slapd.conf

DESCRIPCIÓN

El propósito principal de este backend de slapd(8) es mapear un contexto de nombres definido en una base de datos que se ejecuta en la misma instancia de slapd(8) en un contexto de nombres virtual, con manipulación de attributeType y objectClass, si es necesario. Requiere el overlay slapo-rwm(5).

Este backend y el overlay mencionado anteriormente son experimentales.

CONFIGURACIÓN

Las siguientes directivas de slapd.conf se aplican a la base de datos del backend de retransmisión. Es decir, deben seguir una línea "database relay" y aparecer antes de cualquier línea "backend" o "database" posterior. Otras opciones de base de datos se describen en la página del manual slapd.conf(5); solo la directiva suffix está permitida por el backend de relay.

relay <contexto de nombres real>
El contexto de nombres de la base de datos que se presenta bajo un contexto de nombres virtual. La presencia de esta directiva implica que una base de datos específica, es decir, la que sirve al contexto de nombres real, se presentará bajo un contexto de nombres virtual.

MANIPULACIÓN

La base de datos relay no reescribe automáticamente el contexto de nombres de las solicitudes y respuestas. Para este propósito, el overlay slapo-rwm(5) debe ser instanciado explícitamente y configurado según sea apropiado. Normalmente, la directiva rwm-suffixmassage es suficiente si solo se requiere la reescritura del contexto de nombres.

REGLAS DE ACCESO

Un problema importante es que las reglas de acceso se basan en la identidad que emitió la operación. Después de la manipulación del contexto de nombres virtual al real, el frontend ve la operación como realizada por la identidad en el contexto de nombres real. Además, dado que back-relay omite las operaciones de la base de datos real al acortar las operaciones a través de la API interna del backend, las reglas de acceso originales de la base de datos no se aplican, excepto en casos seleccionados, es decir, cuando el backend aplica control de acceso. Como consecuencia, las instancias de la base de datos de retransmisión deben proporcionar sus propias reglas de acceso que sean consistentes con las de la base de datos original, posiblemente añadiendo restricciones específicas adicionales. Por lo tanto, las reglas de acceso en la base de datos relay deben referirse a identidades en el contexto de nombres real. Los ejemplos se informan en la sección EJEMPLOS.

ESCENARIOS

Si no se proporciona la directiva relay, la base de datos relay no se refiere a ninguna base de datos específica, sino que se busca la más apropiada después de reescribir el DN de la solicitud para la operación que se está manejando.

Esto permite escribir reglas de reescritura cuidadosamente elaboradas que hacen que algunas solicitudes se dirijan a una base de datos y otras a otra; por ejemplo, la autenticación se puede mapear a una base de datos y las búsquedas a otra, o se pueden seleccionar diferentes bases de datos de destino basándose en el DN de la solicitud, y así sucesivamente.

Otra posibilidad es mapear la misma operación a diferentes bases de datos basándose en detalles del contexto de nombres virtual, por ejemplo, grupos en una base de datos y personas en otra.

EJEMPLOS

Para implementar un mapeo de contexto de nombres virtual simple que se refiere a una sola base de datos, use

  database                relay
  suffix                  "dc=virtual,dc=naming,dc=context"
  relay                   "dc=real,dc=naming,dc=context"
  overlay                 rwm
  rwm-suffixmassage       "dc=real,dc=naming,dc=context"

Para implementar un mapeo de contexto de nombres virtual simple que busca el contexto de nombres real para cada operación, use

  database                relay
  suffix                  "dc=virtual,dc=naming,dc=context"
  overlay                 rwm
  rwm-suffixmassage       "dc=real,dc=naming,dc=context"

Esto es útil, por ejemplo, para retransmitir diferentes bases de datos que comparten la porción terminal del contexto de nombres (la que se reescribe).

Para implementar el alias de sufijo a la antigua, por ejemplo, mapeando el contexto de nombres virtual al real, pero no los resultados del real al virtual, use

  database                relay
  suffix                  "dc=virtual,dc=naming,dc=context"
  relay                   "dc=real,dc=naming,dc=context"
  overlay                 rwm
  rwm-rewriteEngine       on
  rwm-rewriteContext      default
  rwm-rewriteRule         "dc=virtual,dc=naming,dc=context"
                          "dc=real,dc=naming,dc=context" ":@"
  rwm-rewriteContext      searchFilter
  rwm-rewriteContext      searchEntryDN
  rwm-rewriteContext      searchAttrDN
  rwm-rewriteContext      matchedDN

Tenga en cuenta que el overlay slapo-rwm(5) se instancia, pero las reglas de reescritura se escriben explícitamente, en lugar de automáticamente como con la declaración rwm-suffixmassage, para mapear todo el flujo de datos del contexto de nombres virtual a real, pero nada del real a virtual.

Reglas de acceso:

  database                mdb
  suffix                  "dc=example,dc=com"
  # omitir...
  access to dn.subtree="dc=example,dc=com"
          by dn.exact="cn=Supervisor,dc=example,dc=com" write
          by * read
  database                relay
  suffix                  "o=Example,c=US"
  relay                   "dc=example,dc=com"
  overlay                 rwm
  rwm-suffixmassage       "dc=example,dc=com"
  # omitir ...
  access to dn.subtree="o=Example,c=US"
          by dn.exact="cn=Supervisor,dc=example,dc=com" write
          by dn.exact="cn=Relay Supervisor,dc=example,dc=com" write
          by * read

Tenga en cuenta que, en ambas bases de datos, las identidades (la cláusula <quién>) están en el contexto de nombres real, es decir, `dc=example,dc=com', mientras que los objetivos (la cláusula <qué>) están en el contexto de nombres real y en el virtual, respectivamente.

CONTROL DE ACCESO

El backend relay no respeta ninguna de las semánticas de control de acceso descritas en slapd.access(5); todo el control de acceso se delega a las bases de datos retransmitidas. Solo se respeta el acceso de lectura (=r) al pseudo-atributo entry y a los valores de otros atributos de las entradas devueltas por la operación de búsqueda, que es realizada por el frontend.

ARCHIVOS

/etc/openldap/slapd.conf
archivo de configuración predeterminado de slapd

VER TAMBIÉN

slapd.conf(5), slapd-config(5), slapo-rwm(5), slapd(8).
