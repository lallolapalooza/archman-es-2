NOMBRE

slapd-mdb - Backend de base de datos mapeada en memoria para slapd

SINOPSIS

/etc/openldap/slapd.conf

DESCRIPCIÓN

El backend mdb de slapd(8) utiliza la biblioteca Lightning Memory-Mapped DB (LMDB) de OpenLDAP para almacenar datos. Depende completamente del sistema operativo subyacente para la gestión de la memoria y no realiza su propia caché. Es el backend de base de datos principal recomendado.

El backend mdb utiliza una disposición jerárquica de la base de datos que soporta renombrar subárboles.

CONFIGURACIÓN

Estas opciones de slapd.conf se aplican al backend mdb. Es decir, deben seguir una línea "backend mdb" y preceder a cualquier línea subsiguiente de "backend" o "database".

idlexp <exp>
Especifica una potencia de 2 para el tamaño máximo de una ranura de índice. El valor predeterminado es 16, lo que da un tamaño máximo de ranura de 2^16 o 65536. Una vez establecido, esta opción se aplica a cada instancia de base de datos mdb. El valor especificado debe estar en el rango de 16 a 30.

Estas opciones de slapd.conf se aplican a la base de datos backend mdb. Es decir, deben seguir una línea "database mdb" y preceder a cualquier línea subsiguiente de "backend" o "database". Otras opciones de base de datos se describen en la página del manual slapd.conf(5).

checkpoint <kbyte> <min>
Especifica la frecuencia de vaciado de los búferes de disco de la base de datos. Esta configuración solo es necesaria si se utiliza la opción dbnosync. El punto de control se producirá si se han escrito <kbyte> datos o si han transcurrido <min> minutos desde el último punto de control. Ambos argumentos tienen un valor predeterminado de cero, en cuyo caso se ignoran. Cuando el argumento <min> no es cero, una tarea interna se ejecutará cada <min> minutos para realizar el punto de control. Nota: actualmente, la configuración <kbyte> no está implementada.
dbnosync
Especifica que el contenido de la base de datos en disco no debe sincronizarse inmediatamente con los cambios en memoria. Habilitar esta opción puede mejorar el rendimiento a expensas de la seguridad de los datos. En particular, si el sistema operativo falla antes de que los cambios se vacíen, se pueden perder algunas transacciones. Por defecto, se realiza un vaciado/sincronización completa de los datos al confirmar cada transacción.
directory <directorio>
Especifica el directorio donde residen los archivos LMDB que contienen esta base de datos y los índices asociados. Se debe especificar un directorio separado para cada base de datos. El valor predeterminado es /var/lib/openldap/openldap-data.
envflags {nosync,nometasync,writemap,mapasync,nordahead}
Especifica banderas para un control más detallado de la operación de la biblioteca LMDB.
nosync
Esto es exactamente igual que la directiva dbnosync.
nometasync
Vacíe los datos en un commit, pero omita la sincronización de la página meta. Este modo es ligeramente más rápido que realizar una sincronización completa, pero puede potencialmente perder la última transacción confirmada si el sistema operativo falla. Si tanto nometasync como nosync están establecidos, la bandera nosync tiene prioridad.
writemap
Utiliza un mapa de memoria escribible en lugar de solo lectura. Esto acelera las operaciones de escritura, pero hace que la base de datos sea vulnerable a la corrupción en caso de que algún error en slapd cause escrituras errantes en la región mmap.
mapasync
Al utilizar un mapa de memoria escribible y realizar vaciados en cada commit, utiliza un vaciado asíncrono en lugar de uno síncrono (el valor predeterminado). Esta opción no tiene ningún efecto si no se ha establecido writemap. Tampoco tiene ningún efecto si está establecido nosync.
nordahead
Desactiva la lectura anticipada de archivos. Normalmente, el sistema operativo realiza lecturas anticipadas en cada solicitud de lectura. Esto generalmente mejora el rendimiento de lectura, pero puede ser perjudicial para el rendimiento de lectura de acceso aleatorio si la memoria del sistema está llena y la base de datos es más grande que la RAM. Esta opción no está implementada en Windows.
index {<listadeatributos>|default} [pres,eq,approx,sub,<especial>]
Especifica los índices que se mantendrán para el atributo (o lista de atributos) dado. Algunos atributos solo admiten un subconjunto de índices. Si solo se proporciona un <atributo>, se mantendrán los índices especificados para default. Tenga en cuenta que establecer un valor predeterminado no implica que todos los atributos se indexarán. Además, para un rendimiento óptimo, siempre se debe configurar un índice eq para el atributo objectClass.

Se puede especificar una serie de parámetros de índice especiales. El tipo de índice sub se puede descomponer en índices subinitial, subany y subfinal. El tipo especial nolang se puede especificar para prohibir el uso de este índice por subtipos de lenguaje. El tipo especial nosubtypes se puede especificar para prohibir el uso de este índice por subtipos nombrados. Nota: cambiar la configuración de index en slapd.conf(5) requiere reconstruir los índices, consulte slapindex(8); cambiar la configuración de index dinámicamente mediante LDAPModifying "cn=config" provoca automáticamente la reconstrucción de los índices en línea en una tarea en segundo plano.

maxentrysize <bytes>
Especifica el tamaño máximo de una entrada en bytes. Los intentos de almacenar una entrada más grande que este tamaño se rechazarán con el error LDAP_ADMINLIMIT_EXCEEDED. El valor predeterminado es 0, que es ilimitado.
maxreaders <entero>
Especifica el número máximo de hilos que pueden tener acceso de lectura concurrente a la base de datos. Herramientas como slapcat cuentan como un solo hilo, además de los hilos en cualquier proceso slapd activo. El valor predeterminado es 126.
maxsize <bytes>
Especifica el tamaño máximo de la base de datos en bytes. Se asigna un mapa de memoria de este tamaño al inicio y no se permitirá que la base de datos crezca más allá de este tamaño. El valor predeterminado es 10485760 bytes. Esta configuración se puede modificar hacia arriba si es necesario aumentar el límite configurado.

Nota: Es importante establecer esto en un valor lo más grande posible (en relación con el crecimiento previsto de los datos reales con el tiempo), ya que aumentar el tamaño más tarde puede no ser práctico cuando el sistema está bajo una carga pesada.

mode <entero>
Especifica el modo de protección de archivos que deben tener los archivos de base de datos recién creados. El valor predeterminado es 0600.
multival {<listadeatributos>|default} <entero alto>,<entero bajo>
Especifica el número de valores para los cuales un atributo multivalor se almacena en una tabla separada. Normalmente, las entradas se almacenan como un único blob dentro de la base de datos. Cuando una entrada se vuelve muy grande o contiene atributos con un número muy grande de valores, las modificaciones en esa entrada pueden volverse muy lentas. Separar los atributos grandes en una tabla separada puede mejorar el rendimiento de las operaciones de modificación. El umbral se especifica como un par de enteros. NAME

slapd-mdb - LMDB backend for slapd

SYNOPSIS

Configuration, or run time:

{suffix} ldap:///{suffix}#mdb

DESCRIPTION

The LMDB backend provides an implementation of an LDAP directory server using the LMDB memory-mapped database library. It is a high-performance, transactional database. It is intended as a replacement for the MDB backend, which was an older, different database engine.

The backend stores data in a directory specified by the directory option. All configuration options and database files are stored within this directory.

CONFIGURATION

The LMDB backend supports the following options:

directory <path>
The directory where the database files are stored. This option is mandatory.
subdir
When enabled, database files will be stored in subdirectories based on their names. This can be useful for organizing large databases.
maxreaders <n>
The maximum number of readers that can access the database concurrently. The default is 1024. LMDB limits the number of concurrent readers to prevent issues with stale transactions. If you encounter “LMDB_readers_needed” errors, you may need to increase this value.
mapsize <size>
The maximum size of the memory-mapped database file. The default is 104857600 bytes (100MB). This should be set to a value that is large enough to hold your entire database. If you encounter “LMDB_map_full” errors, you may need to increase this value. Use K, M, G, or T suffixes for Kilobytes, Megabytes, Gigabytes, or Terabytes respectively.
meminit <on|off>
When enabled (default is on), the database file will be initialized with zeros when it is first created. This can help to prevent certain types of data leakage if the database file is later re-purposed. However, it can also significantly increase the time it takes to create a new database. Disabling this option can improve performance for very large databases.
reclow <hi>:<lo>
Specify the low and high thresholds for attribute reclamation. Attributes that are not referenced by any entries will be reclaimed if their size is between the low and high thresholds. The default is UINT_MAX:UINT_MAX, which means no attributes are reclaimed by default. This setting can be used to save disk space by reclaiming unused attributes. The default can be configured for all other attributes. The default value for both hi and lo thresholds is UINT_MAX, which keeps all attributes in the main blob.
rtxnsize <entries>
Specify the maximum number of entries to process in a single read transaction when executing a large search. Long-lived read transactions prevent old database pages from being reused in write transactions, and so can cause significant growth of the database file when there is heavy write traffic. This setting causes the read transaction in large searches to be released and reacquired after the given number of entries has been read, to give writers the opportunity to reclaim old database pages. The default is 10000.
searchstack <depth>
Specify the depth of the stack used for search filter evaluation. Search filters are evaluated on a stack to accommodate nested AND / OR clauses. An individual stack is assigned to each server thread. The depth of the stack determines how complex a filter can be evaluated without requiring any additional memory allocation. Filters that are nested deeper than the search stack depth will cause a separate stack to be allocated for that particular search operation. These allocations can have a major negative impact on server performance, but specifying too much stack will also consume a great deal of memory. Each search stack uses 512K bytes per level. The default stack depth is 16, thus 8MB per thread is used.

ACCESS CONTROL

The mdb backend honors access control semantics as indicated in slapd.access(5).

FILES

/etc/openldap/slapd.conf
default slapd configuration file
