La biblioteca go.podman.io/image/v5 soporta firmas implementadas como blobs “adjuntos” a una imagen. Algunos transportes de imágenes (formatos de almacenamiento local y protocolos remotos) implementan estas firmas de forma nativa o trivial; para otros, son necesarias las extensiones de protocolo descritas a continuación.

docker/distribution registries—almacenamiento separado

Uso

Cualquier registro docker/distribution existente, independientemente de si soporta firmas de forma nativa o no, puede ser ampliado con almacenamiento de firmas separado configurando una URL de almacenamiento de firmas en ⟨containers-registries.d.md⟩. registries.d puede ser configurado para usar una URL de almacenamiento para todo un servidor docker/distribution, o también URLs separadas para espacios de nombres más pequeños o repositorios individuales dentro del servidor (lo que por ejemplo permite a los autores de imágenes gestionar su propio almacenamiento de firmas mientras publican las imágenes en el servidor público docker.io).

La URL de almacenamiento de firmas define la raíz de una jerarquía de rutas. Puede ser una URL file:///…, apuntando a una estructura de directorios local, o una URL http/https, apuntando a un servidor remoto. El almacenamiento de firmas file:/// puede ser leído y escrito, mientras que http/https solo soporta lectura.

La misma jerarquía de rutas se utiliza en ambos casos, por lo que el servidor HTTP/HTTPS puede ser un simple servidor web estático que sirva una estructura de directorios creada al escribir en un almacenamiento de firmas file:///. (Esto, por supuesto, no impide otras implementaciones de servidor, por ejemplo, un servidor HTTP leyendo firmas de una base de datos).

El flujo de trabajo habitual para producir y distribuir imágenes utilizando el mecanismo de almacenamiento separado es configurar el repositorio en registries.d con una URL lookaside-staging apuntando a un área de preparación privada file:///, y una URL lookaside apuntando a un servidor web público. Para publicar una imagen, el autor de la imagen firmaría la imagen según sea necesario (por ejemplo, usando skopeo copy), y luego copiaría la estructura de directorios creada desde el área de preparación file:/// a un subdirectorio de la raíz web del servidor web público para que sean accesibles utilizando la URL pública lookaside. El autor también indicaría a los consumidores de la imagen, o proporcionaría un archivo de configuración registries.d para, configurar una URL lookaside que apunte al servidor web público.

Estructura de rutas

Dada una URL base de almacenamiento de firmas configurada en registries.d como se mencionó anteriormente, y una imagen de contenedor almacenada en un registro docker/distribution utilizando el nombre expandido completamente nombrehost/espaciosdenombre/nombre{@digest,:tag} (por ejemplo, para docker.io/library/busybox:latest, espaciosdenombre es library, incluso si el usuario se refiere a la imagen usando la sintaxis más corta como busybox:latest), las firmas se acceden usando URLs de la forma > base/espaciosdenombre/nombre@algoritmodigest=valuedigest/signature-indice

donde algoritmodigest:valuedigest es un digest de manifiesto utilizable para referenciar el manifiesto de imagen relevante (es decir, incluso si el usuario referenció la imagen usando una etiqueta, el almacenamiento de firmas siempre se desambigua usando referencias de digest). Tenga en cuenta que en las URLs utilizadas para las firmas, algoritmodigest y valuedigest se separan usando el carácter =, no : como al acceder al manifiesto usando la API de docker/distribution.

Dentro de la URL, indice es un entero decimal (en forma canónica), comenzando en 1. Las firmas se almacenan en URLs con valores de indice sucesivos; para leer todas ellas, comience con indice=1, y continúe leyendo firmas e incrementando indice mientras existan firmas con esos valores de indice. De manera similar, para agregar una firma más a una imagen, encuentre el primer indice que no exista, y luego almacene la nueva firma usando ese valor de indice.

No hay forma de listar las firmas existentes más que iterando a través de los valores sucesivos de indice, y no hay forma de descargar todas las firmas a la vez.

Ejemplos

Para una imagen docker/distribution disponible como busybox@sha256:817a12c32a39bbe394944ba49de563e085f1d3c5266eb8e9723256bc4448680e (o como busybox:latest si la etiqueta latest apunta a un manifiesto con el mismo digest), y con una configuración registries.d que especifica una URL lookaside https://example.com/lookaside para la misma imagen, las siguientes URLs serían accedidas para descargar todas las firmas: > - https://example.com/lookaside/library/busybox@sha256=817a12c32a39bbe394944ba49de563e085f1d3c5266eb8e9723256bc4448680e/signature-1 > - https://example.com/lookaside/library/busybox@sha256=817a12c32a39bbe394944ba49de563e085f1d3c5266eb8e9723256bc4448680e/signature-2 > - …

Para una imagen docker/distribution disponible como example.com/ns1/ns2/ns3/repo@somedigest:digestvalue y la misma URL lookaside, las firmas estarían disponibles en > https://example.com/lookaside/ns1/ns2/ns3/repo@somedigest=digestvalue/signature-1

y así sucesivamente.

(OpenShift) extensión de la API docker/distribution

A partir de https://github.com/openshift/origin/pull/12504/, el registro integrado en OpenShift también proporciona una extensión de la API docker/distribution que permite un acceso más simple a las firmas, utilizando solo el endpoint de la API docker/distribution.

Esta API no es intrínsecamente específica de OpenShift (por ejemplo, el cliente no necesita conocer el endpoint de la API de OpenShift, y las credenciales suficientes para acceder al servidor de la API docker/distribution son suficientes para acceder a las firmas también), y es la forma preferida de implementar el almacenamiento de firmas en los registros.

Consulte https://github.com/openshift/openshift-docs/pull/3556 para obtener la documentación upstream de la API.

Para leer la firma, cualquier usuario con acceso a una imagen puede usar la ruta /extensions/v2/…/signatures/… para leer un array de firmas. Utilice solo los objetos de firma que tengan version igual a 2, type igual a atomic, y lea la firma desde content; ignore los otros campos del objeto de firma.

Para agregar una sola firma, PUT un nuevo objeto con version establecido en 2, type establecido en atomic, y content establecido en la firma. Establezca también name a un nombre único con la forma digest@nombreporimagen, donde digest es un digest de manifiesto de imagen (también utilizado en la URL), y nombreporimagen es cualquier identificador único.

Para agregar más de una firma, agréguelas una a la vez. Esta API no permite eliminar firmas.

Tenga en cuenta que debido a que las firmas se almacenan dentro de los objetos de imagen a nivel de clúster, es decir, diferentes espacios de nombres no pueden asociar diferentes conjuntos de firmas a la misma imagen, la actualización de firmas requiere un acceso a nivel de clúster al recurso imagesignatures (disponible por defecto para el rol system:image-signer),

Registros integrados en OpenShift

El registro integrado en OpenShift implementa la API ordinaria docker/distribution, y también expone imágenes a través de la API REST de OpenShift (accesible a través de los servidores del “maestro de API”).

Nota: Las versiones 1.5 y posteriores de OpenShift soportan la extensión de la API docker/distribution descrita anteriormente ⟨#openshift-dockerdistribution-api-extension⟩, que es más fácil de configurar y generalmente debería preferirse. Continúe leyendo para obtener detalles sobre el uso de versiones anteriores de OpenShift.

signature-protocols(5) - OpenShift Signature Protocols

NOMBRE

signature-protocols - OpenShift Signature Protocols

DESCRIPCIÓN

OpenShift extends the capabilities of docker/distribution by adding a signature protocol that allows image signatures to be associated with images in the registry. This functionality is available through the OpenShift API.

Images are identified by their digest and name. Signatures are associated with specific image manifests (identified by digest) and can be named with any unique identifier.

To interact with signatures, you need to know the URLs for both the docker/distribution y los puntos finales maestros de la API de OpenShift).

Para leer la firma, cualquier usuario con acceso a una imagen puede usar el recurso con ámbito de nombres imagestreamimages para leer un objeto Image y su matriz Signatures. Use solo los objetos ImageSignature que tengan Type igual a atomic, y lea la firma de Content; ignore los otros campos del objeto ImageSignature.

Para agregar o eliminar firmas, use el recurso imagesignatures (no con ámbito de nombres) a nivel de clúster, con Type establecido en atomic y Content establecido en la firma. Los nombres de las firmas deben tener el formato digest@nombre-por-imagen, donde digest es un resumen del manifiesto de la imagen (el «nombre de imagen» de OpenShift) y nombre-por-imagen es cualquier identificador único.

Tenga en cuenta que debido a que las firmas se almacenan dentro de los objetos de imagen a nivel de clúster, es decir, diferentes espacios de nombres no pueden asociar diferentes conjuntos de firmas a la misma imagen, la actualización de firmas requiere acceso a nivel de clúster al recurso imagesignatures (disponible por defecto para el rol system:image-signer), y se desaconseja encarecidamente la eliminación de firmas (elimina la firma de todos los espacios de nombres que contienen la misma imagen).
