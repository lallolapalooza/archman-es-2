NOMBRE

signal-safety - funciones seguras para señales asíncronas

DESCRIPCIÓN

Una función segura para señales asíncronas es aquella que se puede llamar de forma segura dentro de un manejador de señales. Muchas funciones no son seguras para señales asíncronas. En particular, las funciones no reentrantes son generalmente inseguras de llamar desde un manejador de señales.

Los tipos de problemas que hacen que una función sea insegura se pueden entender rápidamente al considerar la implementación de la biblioteca stdio, cuyas funciones no son seguras para señales asíncronas.

Al realizar E/S con búfer en un archivo, las funciones de stdio deben mantener un búfer de datos asignado estáticamente junto con contadores e índices asociados (o punteros) que registran la cantidad de datos y la posición actual en el búfer. Supongamos que el programa principal está en medio de una llamada a una función de stdio como printf(3) donde el búfer y las variables asociadas se han actualizado parcialmente. Si, en ese momento, el programa es interrumpido por un manejador de señales que también llama a printf(3), entonces la segunda llamada a printf(3) operará sobre datos inconsistentes, con resultados impredecibles.

Para evitar problemas con funciones inseguras, existen dos opciones posibles:

(a)
Asegurarse de que (1) el manejador de señales llame solo a funciones seguras para señales asíncronas y (2) el manejador de señales en sí mismo sea reentrante con respecto a las variables globales en el programa principal.
(b)
Bloquear la entrega de señales en el programa principal al llamar a funciones que son inseguras u operar sobre datos globales a los que también accede el manejador de señales.

Generalmente, la segunda opción es difícil en programas de cualquier complejidad, por lo que se elige la primera opción.

POSIX.1 especifica un conjunto de funciones que una implementación debe hacer seguras para señales asíncronas. (Una implementación puede proporcionar implementaciones seguras de funciones adicionales, pero esto no es requerido por el estándar y otras implementaciones pueden no proporcionar las mismas garantías.)

En general, una función es segura para señales asíncronas o bien porque es reentrante o bien porque es atómica con respecto a las señales (es decir, su ejecución no puede ser interrumpida por un manejador de señales).

Notas:

•
POSIX.1-2001 y POSIX.1-2001 TC2 requerían que las funciones fpathconf(3), pathconf(3), y sysconf(3) fueran seguras para señales asíncronas, pero este requisito fue eliminado en POSIX.1-2008.
•
Si un manejador de señales interrumpe la ejecución de una función no segura, y el manejador termina mediante una llamada a longjmp(3) o siglongjmp(3) y el programa posteriormente llama a una función no segura, entonces el comportamiento del programa es indefinido.
•
Los manejadores de señales asíncronas que llaman a funciones que son puntos de cancelación y se anidan sobre regiones de cancelación diferida pueden desencadenar una cancelación cuyo comportamiento es como si hubiera ocurrido cancelación asíncrona y puede hacer que el estado de la aplicación se vuelva inconsistente.

errno

Obtener y establecer el valor de errno es seguro para señales asíncronas siempre que el manejador de señales guarde errno al entrar y restaure su valor antes de retornar.

Desviaciones en la biblioteca C de GNU

Las siguientes desviaciones conocidas del estándar ocurren en la biblioteca C de GNU:

•
Antes de glibc 2.24, execl(3) y execle(3) empleaban realloc(3) internamente y, en consecuencia, no eran seguras para señales asíncronas. Esto se corrigió en glibc 2.24.

signal-safety - funciones seguras para señales (signal-safe)

DESCRIPCIÓN

Una función es segura para señales (signal-safe) si puede ser invocada de forma segura desde un manejador de señales.

Esto significa que la función no puede interferir con el código que la llamó, ni ser interferida por él. En particular, una función segura para señales no debe realizar ninguna de las siguientes acciones:

* Utilizar un mutex que pueda estar bloqueado por el código que la llamó (riesgo de
  interbloqueo (deadlock)).
* Utilizar la asignación de memoria dinámica (malloc(3), free(3), realloc(3),
  alloca(3)).
* Obtener o liberar un descriptor de archivo (open(2), close(2), socket(2),
  accept(2), etc.).
* Realizar operaciones de entrada/salida (read(2), write(2), send(2), recv(2),
  etc.).
* Gestionar el estado de señales (signal(2), sigaction(2), pause(2),
  sigwaitinfo(2), sigtimedwait(2), etc.).
* Utilizar stdio (printf(3), fprintf(3), etc.).
* Llamar a pthread_mutex_lock(3) o pthread_mutex_unlock(3).
* Llamar a pthread_cond_signal(3) o pthread_cond_broadcast(3).
* Llamar a pthread_join(3).

La lista anterior es extensa pero no exhaustiva. La documentación de cada función debe indicar si es segura para señales. Si no se especifica, se debe asumir que no lo es.

Si un manejador de señales necesita realizar acciones que no son seguras para señales, debe establecer una bandera y volver. El código principal debe comprobar periódicamente esta bandera y realizar las acciones necesarias cuando sea seguro hacerlo (es decir, no dentro de un manejador de señales).

Algunas funciones, aunque no sean seguras para señales por sí mismas, pueden ser utilizadas de forma segura dentro de un manejador de señales si se garantiza que no interactúan con el código que podría estar ejecutándose fuera del manejador de señales. Por ejemplo, una función que solo accede a variables globales locales y estáticas que no son modificadas por el código principal puede ser segura para señales. Sin embargo, confiar en este tipo de razonamiento puede ser peligroso y debe evitarse siempre que sea posible.

La función aio_suspend(3) no es segura para señales porque utiliza pthread_mutex_lock(3) internamente.
