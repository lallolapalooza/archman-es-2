signal(7) Manual de Información Miscelánea signal(7)

NOMBRE

signal - visión general de las señales

DESCRIPCIÓN

Linux soporta tanto señales fiables POSIX (en adelante, "señales estándar") como señales de tiempo real POSIX.

Disposiciones de señal

Cada señal tiene una disposición actual, que determina cómo se comporta el proceso cuando se le entrega la señal.

Las entradas en la columna "Acción" de la siguiente tabla especifican la disposición predeterminada para cada señal, como sigue:

Term
La acción predeterminada es terminar el proceso.
Ign
La acción predeterminada es ignorar la señal.
Core
La acción predeterminada es terminar el proceso y volcar el núcleo (ver core(5)).
Stop
La acción predeterminada es detener el proceso.
Cont
La acción predeterminada es continuar el proceso si está actualmente detenido.

Un proceso puede cambiar la disposición de una señal utilizando sigaction(2) o signal(2). (Este último es menos portable al establecer un manejador de señales; ver signal(2) para más detalles.) Usando estas llamadas al sistema, un proceso puede elegir uno de los siguientes comportamientos para que ocurra al entregar la señal: realizar la acción predeterminada; ignorar la señal; o capturar la señal con un manejador de señales, una función definida por el programador que se invoca automáticamente cuando se entrega la señal.

Por defecto, un manejador de señales se invoca en la pila normal del proceso. Es posible organizar que el manejador de señales utilice una pila alternativa; ver sigaltstack(2) para una discusión sobre cómo hacer esto y cuándo podría ser útil.

La disposición de señal es un atributo por proceso: en una aplicación multihilo, la disposición de una señal particular es la misma para todos los hilos.

Un hijo creado a través de fork(2) hereda una copia de las disposiciones de señales de su padre. Durante un execve(2), las disposiciones de las señales manejadas se restablecen a los valores predeterminados; las disposiciones de las señales ignoradas se dejan sin cambios.

Envío de una señal

Las siguientes llamadas al sistema y funciones de biblioteca permiten al llamador enviar una señal:

raise(3)
Envía una señal al hilo llamador.
kill(2)
Envía una señal a un proceso especificado, a todos los miembros de un grupo de procesos especificado, o a todos los procesos del sistema.
pidfd_send_signal(2)
Envía una señal a un proceso identificado por un descriptor de archivo PID.
killpg(3)
Envía una señal a todos los miembros de un grupo de procesos especificado.
pthread_kill(3)
Envía una señal a un hilo POSIX especificado dentro del mismo proceso que el llamador.
tgkill(2)
Envía una señal a un hilo especificado dentro de un proceso específico. (Esta es la llamada al sistema utilizada para implementar pthread_kill(3)).
sigqueue(3)
Envía una señal de tiempo real con datos adjuntos a un proceso especificado.

Esperar a que se capture una señal

Las siguientes llamadas al sistema suspenden la ejecución del hilo llamador hasta que se capture una señal (o una señal no manejada termine el proceso):

pause(2)
Suspende la ejecución hasta que se capture cualquier señal.
sigsuspend(2)
Cambia temporalmente la máscara de señales (ver más abajo) y suspende la ejecución hasta que se capture una de las señales no enmascaradas.

Aceptar una señal sincrónicamente

En lugar de capturar una señal de forma asíncrona a través de un manejador de señales, es posible aceptar la señal sincrónicamente, es decir, bloquear la ejecución hasta que se entregue la señal, momento en el cual el kernel devuelve información sobre la señal al llamador. Hay dos formas generales de hacer esto:

•
sigwaitinfo(2), sigtimedwait(2) y sigwait(3) suspenden la ejecución hasta que se entregue una de las señales de un conjunto especificado. Cada una de estas llamadas devuelve información sobre la señal entregada.
•
signalfd(2) devuelve un descriptor de archivo que se puede usar para leer información sobre las señales que se entregan al llamador. Cada read(2) desde este descriptor de archivo se bloquea hasta que se entrega una de las señales del conjunto especificado en la llamada signalfd(2) al llamador. El búfer devuelto por read(2) contiene una estructura que describe la señal.

Máscara de señales y señales pendientes

Una señal puede estar enmascarada, lo que significa que no se entregará hasta que posteriormente se desenmascare. Entre el momento en que se genera y cuando se entrega, se dice que una señal está pendiente.

Cada hilo en un proceso tiene una máscara de señales independiente, que indica el conjunto de señales que el hilo está actualmente enmascarando. Un hilo puede manipular su máscara de señales usando pthread_sigmask(3). En una aplicación tradicional de un solo hilo, sigprocmask(2) se puede usar para manipular la máscara de señales.

Un hijo creado a través de fork(2) hereda una copia de la máscara de señales de su padre; la máscara de señales se conserva a través de execve(2).

Una señal puede ser dirigida al proceso o al hilo. Una señal dirigida al proceso es una que está dirigida (y, por lo tanto, pendiente) para el proceso en su conjunto. Una señal puede ser dirigida al proceso porque fue generada por el kernel por razones distintas a una excepción de hardware, o porque fue enviada usando kill(2) o sigqueue(3). Una señal dirigida al hilo es una que está dirigida a un hilo específico. Una señal puede ser dirigida al hilo porque fue generada como consecuencia de ejecutar una instrucción específica del lenguaje máquina que desencadenó una excepción de hardware (por ejemplo, SIGSEGV por un acceso inválido a la memoria, o SIGFPE por un error matemático), o porque estaba dirigida a un hilo específico usando interfaces como tgkill(2) o pthread_kill(3).

Una señal dirigida al proceso puede entregarse a cualquiera de los hilos que no tenga actualmente la señal enmascarada. Si más de uno de los hilos tiene la señal sin enmascarar, entonces el kernel elige un hilo arbitrario al que entregar la señal.

Un hilo puede obtener el conjunto de señales que tiene actualmente pendientes usando sigpending(2).

Ejecución de manejadores de señales

Cada vez que hay una transición de la ejecución en modo kernel a modo de usuario (por ejemplo, al regresar de una llamada al sistema o al programar un hilo en la CPU), el kernel verifica si hay una señal pendiente no bloqueada para la cual el proceso ha establecido un manejador de señales. Si existe una señal pendiente de este tipo, ocurren los siguientes pasos:

(1)
El kernel realiza los pasos preparatorios necesarios para la ejecución del manejador de señales:
(1.1)
La señal se elimina del conjunto de señales pendientes.
(1.2)
Si el manejador de señales se instaló mediante una llamada a sigaction(2) que especificó la bandera SA_ONSTACK y el hilo ha definido una pila de señales alternativa (usando sigaltstack(2)), entonces se instala esa pila.
(1.3)
Varias piezas de contexto relacionadas con señales se guardan en un marco especial que se crea en la pila. La información guardada incluye:
•
el registro del contador de programa (es decir, la dirección de la siguiente instrucción en el programa principal que debe ejecutarse cuando regrese el manejador de señales);
•
el estado de los registros específico de la arquitectura requerido para reanudar el programa interrumpido;
•
la máscara de señales actual del hilo;
•
la configuración de la pila de señales alternativa del hilo.
Si el manejador de señales se instaló utilizando la bandera SA_SIGINFO de sigaction(2), entonces la información anterior es accesible a través del objeto ucontext_t al que apunta el tercer argumento del manejador de señales. Este objeto refleja el estado en el que se entrega la señal, en lugar de en el manejador; por ejemplo, la máscara de señales bloqueadas almacenada en este objeto no contendrá la máscara de nuevas señales bloqueadas a través de sigaction(2).
(1.4)
Cualquier señal especificada en act->sa_mask al registrar el manejador con sigaction(2) se agrega a la máscara de señales del hilo. La señal que se entrega también se agrega a la máscara de señales, a menos que se especificara SA_NODEFER al registrar el manejador. Por lo tanto, estas señales se bloquean mientras se ejecuta el manejador.
(2)
El kernel construye un marco para el manejador de señales en la pila. El kernel establece el contador de programa del hilo para que apunte a la primera instrucción de la función del manejador de señales y configura la dirección de retorno para que esa función apunte a un fragmento de código en el espacio de usuario conocido como el trampolín de señales (descrito en sigreturn(2)).
(3)
El kernel devuelve el control al espacio de usuario, donde la ejecución comienza en el inicio de la función del manejador de señales.
(4)
Cuando el manejador de señales regresa, el control pasa al código del trampolín de señales.
(5)
El trampolín de señales llama a sigreturn(2), una llamada al sistema que utiliza la información en el marco de pila creado en el paso 1 para restaurar el hilo a su estado antes de que se llamara al manejador de señales. La máscara de señales del hilo y la configuración de la pila de señales alternativa se restauran como parte de este procedimiento. Al completar la llamada a sigreturn(2), el kernel transfiere el control de vuelta al espacio de usuario, y el hilo reanuda la ejecución en el punto donde fue interrumpido por el manejador de señales.

Tenga en cuenta que si el manejador de señales no regresa (por ejemplo, el control se transfiere fuera del manejador usando siglongjmp(3), o el manejador ejecuta un nuevo programa con execve(2)), entonces el paso final no se realiza. En particular, en tales escenarios, es responsabilidad del programador restaurar el estado de la máscara de señales (usando sigprocmask(2)), si se desea desbloquear las señales que estaban bloqueadas al ingresar al manejador de señales. (Tenga en cuenta que siglongjmp(3) puede o no restaurar la máscara de señales, dependiendo del valor savesigs que se especificó en la llamada correspondiente a sigsetjmp(3).)

Desde el punto de vista del kernel, la ejecución del código del manejador de señales es exactamente la misma que la ejecución de cualquier otro código en el espacio de usuario. Es decir, el kernel no registra ninguna información de estado especial que indique que el hilo está ejecutando actualmente dentro de un manejador de señales. Toda la información de estado necesaria se mantiene en los registros del espacio de usuario y en la pila del espacio de usuario. Por lo tanto, la profundidad a la que se pueden invocar manejadores de señales anidados está limitada solo por la pila del espacio de usuario (¡y un diseño de software sensato!).

Las señales SIGKILL y SIGSTOP no pueden ser capturadas, bloqueadas o ignoradas.

Hasta e incluyendo Linux 2.2, el comportamiento por defecto para SIGSYS, SIGXCPU, SIGXFSZ y (en arquitecturas distintas de SPARC y MIPS) SIGBUS era terminar el proceso (sin volcado de memoria). (En algunos otros sistemas UNIX, la acción por defecto para SIGXCPU y SIGXFSZ es terminar el proceso sin volcado de memoria). SIGPWR (que no está especificado en POSIX.1-2001) es típicamente ignorada por defecto en aquellos otros sistemas UNIX donde aparece.

SIGIO (que no está especificado en POSIX.1-2001) es ignorado por defecto en varios otros sistemas UNIX.

Cola y semántica de entrega para señales estándar

Si varias señales estándar están pendientes para un proceso, el orden en que se entregan las señales no está especificado.

Las señales estándar no se ponen en cola. Si se generan varias instancias de una señal estándar mientras esa señal está bloqueada, entonces sólo se marca una instancia de la señal como pendiente (y la señal se entregará sólo una vez cuando se desbloquee). En el caso en que una señal estándar ya esté pendiente, la estructura siginfo_t (ver sigaction(2)) asociada con esa señal no se sobrescribe al llegar instancias subsiguientes de la misma señal. Por lo tanto, el proceso recibirá la información asociada con la primera instancia de la señal.

Señales en tiempo real

A partir de Linux 2.2, Linux soporta señales en tiempo real según lo definido originalmente en las extensiones de tiempo real de POSIX.1b (y ahora incluidas en POSIX.1-2001). El rango de señales en tiempo real soportadas se define mediante las macros SIGRTMIN y SIGRTMAX. POSIX.1-2001 requiere que una implementación soporte al menos _POSIX_RTSIG_MAX (8) señales en tiempo real.

El kernel de Linux soporta un rango de 33 señales diferentes en tiempo real, numeradas del 32 al 64. Sin embargo, la implementación de hilos POSIX de glibc utiliza internamente dos (para NPTL) o tres (para LinuxThreads) señales en tiempo real (ver pthreads(7)), y ajusta el valor de SIGRTMIN convenientemente (a 34 o 35). Debido a que el rango de señales en tiempo real disponibles varía según la implementación de hilos de glibc (y esta variación puede ocurrir en tiempo de ejecución según el kernel y glibc disponibles), y de hecho el rango de señales en tiempo real varía entre sistemas UNIX, los programas nunca deben referirse a señales en tiempo real usando números codificados, sino que siempre deben referirse a señales en tiempo real usando la notación SIGRTMIN+n, e incluir comprobaciones adecuadas (en tiempo de ejecución) de que SIGRTMIN+n no excede SIGRTMAX.

A diferencia de las señales estándar, las señales en tiempo real no tienen significados predefinidos: todo el conjunto de señales en tiempo real puede usarse para propósitos definidos por la aplicación.

La acción predeterminada para una señal en tiempo real no manejada es terminar el proceso receptor.

Las señales en tiempo real se distinguen por lo siguiente:

•
Se pueden poner en cola múltiples instancias de señales en tiempo real. Por el contrario, si se entregan múltiples instancias de una señal estándar mientras esa señal está actualmente bloqueada, solo se pone en cola una instancia.
•
Si la señal se envía usando sigqueue(2), se puede enviar un valor adjunto (un entero o un puntero) con la señal. Si el proceso receptor establece un manejador para esta señal usando la bandera SA_SIGINFO en sigaction(2), puede obtener estos datos a través del campo si_value de la estructura siginfo_t pasada como segundo argumento al manejador. Además, los campos si_pid y si_uid de esta estructura se pueden usar para obtener el PID y el ID de usuario real del proceso que envía la señal.
•
Las señales en tiempo real se entregan en un orden garantizado. Múltiples señales en tiempo real del mismo tipo se entregan en el orden en que se enviaron. Si se envían diferentes señales en tiempo real a un proceso, se entregan comenzando por la señal de menor número. (Es decir, las señales de menor número tienen mayor prioridad). Por el contrario, si hay múltiples señales estándar pendientes para un proceso, el orden en que se entregan no está especificado.

Si tanto señales estándar como en tiempo real están pendientes para un proceso, POSIX deja sin especificar cuál se entrega primero. Linux, al igual que muchas otras implementaciones, da prioridad a las señales estándar en este caso.

Según POSIX, una implementación debe permitir que se pongan en cola al menos _POSIX_SIGQUEUE_MAX (32) señales en tiempo real para un proceso. Sin embargo, Linux lo hace de manera diferente. Hasta Linux 2.6.7 inclusive, Linux impone un límite a nivel de sistema para el número de señales en tiempo real en cola para todos los procesos. Este límite se puede ver y (con privilegios) cambiar a través del archivo /proc/sys/kernel/rtsig-max. Un archivo relacionado, /proc/sys/kernel/rtsig-nr, se puede utilizar para saber cuántas señales en tiempo real están actualmente en cola. En Linux 2.6.8, estas interfaces de /proc fueron reemplazadas por el límite de recursos RLIMIT_SIGPENDING, que especifica un límite por usuario para señales en cola; ver setrlimit(2) para más detalles.

La adición de señales en tiempo real requirió la ampliación de la estructura del conjunto de señales (sigset_t) de 32 a 64 bits. En consecuencia, varias llamadas al sistema fueron reemplazadas por nuevas llamadas al sistema que soportaban los conjuntos de señales más grandes. Las llamadas al sistema antiguas y nuevas son las siguientes:

Linux 2.0 y anteriores Linux 2.2 y posteriores
sigaction(2) rt_sigaction(2)
sigpending(2) rt_sigpending(2)
sigprocmask(2) rt_sigprocmask(2)
sigreturn(2) rt_sigreturn(2)
sigsuspend(2) rt_sigsuspend(2)

Interrupción de llamadas al sistema y funciones de biblioteca por manejadores de señales

Si se invoca un manejador de señales mientras una llamada al sistema o a una función de biblioteca está bloqueada, entonces:

•
la llamada se reinicia automáticamente después de que el manejador de señales regresa; o
•
la llamada falla con el error EINTR.

Cuál de estos dos comportamientos ocurre depende de la interfaz y de si el manejador de señales se estableció o no usando la bandera SA_RESTART (ver sigaction(2)). Los detalles varían entre los sistemas UNIX; a continuación, los detalles para Linux.

Si una llamada bloqueada a una de las siguientes interfaces se interrumpe por un manejador de señales, entonces la llamada se reinicia automáticamente después de que el manejador de señales regresa si se usó la bandera SA_RESTART; de lo contrario, la llamada falla con el error EINTR:

•
read(2), readv(2), write(2), writev(2) y llamadas ioctl(2) en dispositivos "lentos". Un dispositivo "lento" es aquel en el que la llamada I/O puede bloquearse durante un tiempo indefinido, por ejemplo, una terminal, una tubería o un socket. Si una llamada I/O en un dispositivo lento ya ha transferido algunos datos cuando se interrumpe por un manejador de señales, entonces la llamada devolverá un estado de éxito (normalmente, el número de bytes transferidos). Tenga en cuenta que un disco (local) no es un dispositivo lento según esta definición; las operaciones I/O en dispositivos de disco no son interrumpidas por señales.
•
open(2), si puede bloquearse (por ejemplo, al abrir una FIFO; ver fifo(7)).
•
wait(2), wait3(2), wait4(2), waitid(2) y waitpid(2).
•
Interfaces de socket: accept(2), connect(2), recv(2), recvfrom(2), recvmmsg(2), recvmsg(2), send(2), sendto(2) y sendmsg(2), a menos que se haya establecido un tiempo de espera en el socket (ver más abajo).
•
Interfaces de bloqueo de archivos: flock(2) y las operaciones F_SETLKW y F_OFD_SETLKW de fcntl(2)
•
Interfaces de cola de mensajes POSIX: mq_receive(3), mq_timedreceive(3), mq_send(3) y mq_timedsend(3).
•
futex(2) FUTEX_WAIT (desde Linux 2.6.22; antes, siempre fallaba con EINTR.
).
•
getrandom(2).
•
futex(2) FUTEX_WAIT_BITSET.
•
Interfaces de semáforo POSIX: sem_wait(3) y sem_timedwait(3) (desde Linux 2.6.22; antes, siempre fallaba con EINTR).
•
read(2) desde un descriptor de archivo inotify(7) (desde Linux 3.8; antes, siempre fallaba con EINTR).

Las siguientes interfaces nunca se reinician después de ser interrumpidas por un manejador de señales, independientemente del uso de SA_RESTART; siempre fallan con el error EINTR cuando son interrumpidas por un manejador de señales:

•
Interfaces de socket de "entrada", cuando se ha establecido un tiempo de espera (SO_RCVTIMEO) en el socket usando setsockopt(2): accept(2), recv(2), recvfrom(2), recvmmsg(2) (también con un argumento timeout no nulo), y recvmsg(2).
•
Interfaces de socket de "salida", cuando se ha establecido un tiempo de espera (SO_SNDTIMEO) en el socket usando setsockopt(2): connect(2), send(2), sendto(2), y sendmsg(2).
•
Interfaces utilizadas para esperar señales: pause(2), sigsuspend(2), sigtimedwait(2), y sigwaitinfo(2).
•
Interfaces de multiplexación de descriptores de archivo: epoll_wait(2), epoll_pwait(2), poll(2), ppoll(2), select(2), y pselect(2).
•
Interfaces IPC de System V: msgrcv(2), msgsnd(2), semop(2), y semtimedop(2).
•
Interfaces de suspensión: clock_nanosleep(2), nanosleep(2), y usleep(3).
•
io_getevents(2).

La función sleep(3) tampoco se reinicia nunca si es interrumpida por un manejador, sino que devuelve éxito: el número de segundos restantes para dormir.

En ciertas circunstancias, la función de notificación al espacio de usuario de seccomp(2) puede provocar el reinicio de llamadas al sistema que de otro modo nunca serían reiniciadas por SA_RESTART; para más detalles, véase seccomp_unotify(2).

Interrupción de llamadas al sistema y funciones de biblioteca por señales de parada

En Linux, incluso en ausencia de manejadores de señales, ciertas interfaces de bloqueo pueden fallar con el error EINTR después de que el proceso sea detenido por una de las señales de parada y luego reanudado mediante SIGCONT. Este comportamiento no está sancionado por POSIX.1 y no ocurre en otros sistemas.

Las interfaces de Linux que muestran este comportamiento son:

•
Interfaces de socket de "entrada", cuando se ha establecido un tiempo de espera (SO_RCVTIMEO) en el socket usando setsockopt(2): accept(2), recv(2), recvfrom(2), recvmmsg(2) (también con un argumento timeout no nulo), y recvmsg(2).
•
Interfaces de socket de "salida", cuando se ha establecido un tiempo de espera (SO_SNDTIMEO) en el socket usando setsockopt(2): connect(2), send(2), sendto(2), y sendmsg(2), si se ha establecido un tiempo de espera de envío (SO_SNDTIMEO).
•
epoll_wait(2), epoll_pwait(2).
•
semop(2), semtimedop(2).
•
sigtimedwait(2), sigwaitinfo(2).
•
Linux 3.7 y anteriores: read(2) desde un descriptor de archivo inotify(7)
•
Linux 2.6.21 y anteriores: futex(2) FUTEX_WAIT, sem_timedwait(3), sem_wait(3).
•
Linux 2.6.8 y anteriores: msgrcv(2), msgsnd(2).
•
Linux 2.4 y anteriores: nanosleep(2).

NOTAS

Para una discusión sobre funciones seguras para señales asíncronas, consulte signal-safety(7).

El archivo /proc/pid/task/tid/status contiene varios campos que muestran las señales que un hilo está bloqueando (SigBlk), capturando (SigCgt) o ignorando (SigIgn). (El conjunto de señales que se capturan o ignoran será el mismo en todos los hilos de un proceso.) Otros campos muestran el conjunto de señales pendientes que se dirigen al hilo (SigPnd) así como el conjunto de señales pendientes que se dirigen al proceso en su conjunto (ShdPnd). Los campos correspondientes en /proc/pid/status muestran la información para el hilo principal. Véase proc(5) para más detalles.

ERRORES

Hay seis señales que pueden ser entregadas como consecuencia de una excepción de hardware: SIGBUS, SIGEMT, SIGFPE, SIGILL, SIGSEGV y SIGTRAP. Cuál de estas señales se entrega, para una determinada excepción de hardware, no está documentado y no siempre tiene sentido.

Por ejemplo, un acceso inválido a memoria que causa la entrega de SIGSEGV en una arquitectura de CPU puede causar la entrega de SIGBUS en otra arquitectura, o viceversa.

Para otro ejemplo, el uso de la instrucción x86 int con un argumento prohibido (cualquier número que no sea 3 o 128) causa la entrega de SIGSEGV, aunque SIGILL tendría más sentido, debido a cómo la CPU informa la operación prohibida al kernel.

    NOMBRE

    signal - señales POSIX

    DESCRIPCIÓN

    Una señal es una notificación asíncrona enviada a un proceso o a un hilo dentro de un proceso para informarle de que ha ocurrido un evento. Los eventos pueden ser:

    • La terminación de un proceso hijo (SIGCHLD).

    • Una condición de error de hardware (por ejemplo, SIGSEGV, SIGBUS).

    • Una interrupción del usuario (por ejemplo, SIGINT).

    • Una alarma temporizada (SIGALRM).

    • Una solicitud para finalizar un proceso (SIGTERM).

    • Una solicitud para detener un proceso (SIGSTOP).

    • El envío de una señal desde otro proceso (SIGUSR1, SIGUSR2).

    Las señales se pueden entregar de forma confiable o no confiable.

    Una señal confiable es aquella que se entrega al proceso o hilo de destino de forma garantizada. Si una señal confiable no se puede entregar inmediatamente porque el proceso o hilo de destino está ocupado, la señal se mantendrá pendiente hasta que el proceso o hilo de destino esté disponible para recibirla. Si se envían varias copias de la misma señal confiable antes de que se entregue, solo se entregará una copia.

    Una señal no confiable es aquella que no se entrega de forma garantizada. Si se envían varias copias de la misma señal no confiable antes de que se entregue, pueden entregarse varias copias o ninguna.

    Cuando se recibe una señal, el sistema operativo puede realizar una de las siguientes acciones:

    • Ignorar la señal.

    • Terminar el proceso.

    • Terminar el proceso y volcar la memoria (core dump).

    • Suspender el proceso (detener su ejecución temporalmente).

    • Reanudar un proceso suspendido.

    • Ejecutar un manejador de señales definido por el usuario.

    La acción predeterminada para cada señal está definida por el sistema operativo. Algunas señales se pueden capturar, bloquear o ignorar, mientras que otras, como SIGKILL y SIGSTOP, no se pueden capturar, bloquear ni ignorar.

    Las señales se pueden enviar utilizando la llamada al sistema kill(). La señal se envía al proceso o hilo especificado por su ID.

    Las señales se pueden recibir utilizando la llamada al sistema sigaction() o signal(). Estas llamadas al sistema permiten al proceso especificar una función de manejo de señales que se ejecutará cuando se reciba una señal determinada.

    Las señales se pueden bloquear utilizando la llamada al sistema sigprocmask(). Cuando una señal está bloqueada, no se entregará al proceso hasta que se desbloquee.

    Para obtener más información sobre señales específicas, consulte las páginas del manual correspondientes (por ejemplo, signal(2), kill(2), sigaction(2)).
