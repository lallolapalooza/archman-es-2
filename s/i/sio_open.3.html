DESCRIPCIÓN

La biblioteca sndio permite a los procesos de usuario acceder al hardware de audio(4) y al servidor de audio sndiod(8) de forma uniforme.

Abrir y cerrar un dispositivo de audio

Primero, la aplicación debe llamar a la función sio_open() para obtener un manejador del dispositivo; este se pasará más tarde como argumento hdl de la mayoría de las otras funciones. El parámetro name proporciona la cadena de dispositivo discutida en sndio(7). En la mayoría de los casos, debe establecerse en SIO_DEVANY para permitir que el usuario lo seleccione usando la variable de entorno AUDIODEVICE.

Los siguientes valores del parámetro mode son compatibles:

SIO_PLAY
Modo solo reproducción: los datos escritos serán reproducidos por el dispositivo.
SIO_REC
Modo solo grabación: las muestras son grabadas por el dispositivo y deben ser leídas.
SIO_PLAY | SIO_REC
El dispositivo reproduce y graba de forma síncrona; esto significa que la n-ésima muestra grabada fue muestreada físicamente exactamente cuando la n-ésima muestra reproducida fue realmente reproducida.

Si el argumento nbio_flag es verdadero (es decir, distinto de cero), entonces las funciones sio_read() y sio_write() (ver más abajo) no serán bloqueantes.

La función sio_close() detiene el dispositivo como si se llamara a sio_stop() y libera el manejador. Por lo tanto, ninguna muestra enviada con sio_write() se descarta.

Negociación de parámetros de audio

Las muestras de audio están entrelazadas. Un fotograma consiste en una muestra para cada canal. Por ejemplo, una codificación estéreo de 16 bits tiene dos muestras por fotograma y, dos bytes por muestra (por lo tanto, 4 bytes por fotograma).

El conjunto de parámetros del dispositivo que se pueden controlar se proporciona mediante la siguiente estructura:

struct sio_par {
	unsigned int bits;	/* bits por muestra */
	unsigned int bps;	/* bytes por muestra */
	unsigned int sig;	/* 1 = con signo, 0 = sin signo */
	unsigned int le;	/* 1 = LE, 0 = BE orden de bytes */
	unsigned int msb;	/* 1 = MSB, 0 = LSB alineado */
	unsigned int rchan;	/* número de canales para grabación */
	unsigned int pchan;	/* número de canales para reproducción */
	unsigned int rate;	/* fotogramas por segundo */
	unsigned int appbufsz;	/* tamaño mínimo del búfer sin xruns */
	unsigned int bufsz;	/* tamaño del búfer de extremo a extremo (solo lectura) */
	unsigned int round;	/* divisor de tamaño de búfer óptimo */
#define SIO_IGNORE	0	/* pausa durante xrun */
#define SIO_SYNC	1	/* resincronización después de xrun */
#define SIO_ERROR	2	/* terminar en xrun */
	unsigned int xrun;	/* qué hacer en desbordamiento/subdesbordamiento */
};

Los parámetros son los siguientes:

bits
Número de bits por muestra: debe estar entre 1 y 32.
bps
Bytes por muestra; si se especifica, debe ser lo suficientemente grande como para contener todos los bits. Por defecto, se establece en la menor potencia de dos lo suficientemente grande como para contener bits.
sig
Si se establece (es decir, distinto de cero), las muestras tienen signo, de lo contrario, sin signo.
le

>
Si está establecido, el orden de bytes es little endian, de lo contrario es big endian; es significativo solo si bps > 1.
msb
Si está establecido, entonces los bits están alineados en el paquete al bit más significativo (es decir, los bits inferiores se rellenan), de lo contrario, al menos significativo (es decir, los bits superiores se rellenan); es significativo solo si bits < bps * 8.
rchan
El número de canales grabados; significativo solo si se seleccionó el modo SIO_REC.
pchan
El número de canales reproducidos; significativo solo si se seleccionó el modo SIO_PLAY.
rate
La frecuencia de muestreo en Hz.
appbufsz
Tamaño del búfer en fotogramas que la aplicación debe mantener no vacío (en el extremo de reproducción) o no lleno (en el extremo de grabación) llamando a sio_write() o sio_read() lo suficientemente rápido como para evitar condiciones de desbordamiento (overrun) o subdesbordamiento (underrun). El subsistema de audio puede usar búferes adicionales, por lo tanto, este parámetro no se puede usar para cálculos de latencia.
bufsz
El número máximo de fotogramas que pueden ser almacenados en búfer. Este parámetro tiene en cuenta cualquier búfer y se puede utilizar para cálculos de latencia. Es de solo lectura.
round
Número óptimo de fotogramas que deben ser múltiplos de los búferes de la aplicación, para obtener el mejor rendimiento. Las aplicaciones pueden usar este parámetro para redondear su tamaño de bloque.
xrun
La acción cuando el cliente no acepta datos grabados o no proporciona datos para reproducir lo suficientemente rápido; se puede establecer en una de las constantes SIO_IGNORE, SIO_SYNC o SIO_ERROR.

Se recomienda el siguiente enfoque para negociar los parámetros del dispositivo:

  • Inicialice una estructura sio_par usando sio_initpar() y rellénela con los parámetros deseados. Luego llame a sio_setpar() para solicitar que el dispositivo los utilice. Los parámetros que no se establezcan en la estructura sio_par se establecerán en los valores predeterminados específicos del dispositivo.
  • Llame a sio_getpar() para recuperar los parámetros reales del dispositivo y comprobar que sean utilizables. Si no lo son, falle o configure una capa de conversión. A veces, la tasa establecida puede ser ligeramente diferente a la solicitada. Una diferencia de aproximadamente el 0.5% no es audible y debe ignorarse.

Los parámetros no se pueden cambiar después de que se haya llamado a sio_start(); se debe llamar a sio_stop() o sio_flush() antes de que los parámetros puedan ser modificados.

Si el dispositivo es expuesto por el servidor sndiod(8), que es la configuración predeterminada, se configurará automáticamente una capa de emulación transparente y, en este caso, se admitirá cualquier combinación de tasa, codificación y número de canales.

Para facilitar el llenado de la estructura sio_par, se pueden usar las siguientes macros:

SIO_BPS(bits)
Devuelve el valor más pequeño para bps que es una potencia de dos y que es lo suficientemente grande como para contener bits.
SIO_LE_NATIVE
Se puede utilizar para establecer el parámetro le cuando se requiere el orden de bytes nativo. Es 1 si el orden de bytes nativo es little endian o 0 en caso contrario.

Obtener capacidades del dispositivo

No hay forma de obtener una lista exhaustiva de todas las combinaciones de parámetros que admite el dispositivo. Las aplicaciones que necesitan tener un conjunto de combinaciones de parámetros funcionales por adelantado pueden usar la función sio_getcap(). Sin embargo, para la mayoría de las aplicaciones nuevas, generalmente no se recomienda usar sio_getcap(). En su lugar, siga las recomendaciones para negociar los parámetros del dispositivo (ver arriba).

La estructura sio_cap contiene la lista de configuraciones de parámetros. Cada configuración contiene múltiples conjuntos de parámetros. La aplicación debe examinar todas las configuraciones y elegir su conjunto de parámetros de una de las configuraciones. Los parámetros de diferentes configuraciones no son utilizables juntos.

struct sio_cap {
	struct sio_enc {		/* encodings permitidas */
		unsigned int bits;
		unsigned int bps;
		unsigned int sig;
		unsigned int le;
		unsigned int msb;
	} enc[SIO_NENC];
	unsigned int rchan[SIO_NCHAN];	/* rchans permitidos */
	unsigned int pchan[SIO_NCHAN];	/* pchans permitidos */
	unsigned int rate[SIO_NRATE];	/* tasas permitidas */
	unsigned int nconf;		/* num. de confs[] */
	struct sio_conf {
		unsigned int enc;	/* máscara de bits de índices de enc[] */
		unsigned int rchan;	/* máscara de bits de índices de rchan[] */
		unsigned int pchan;	/* máscara de bits de índices de pchan[] */
		unsigned int rate;	/* máscara de bits de índices de rate[] */
	} confs[SIO_NCONF];
};

Los parámetros son los siguientes:

enc[SIO_NENC]
Matriz de codificaciones compatibles. La tupla de parámetros bits, bps, sig, le y msb son utilizables en los parámetros correspondientes de la estructura sio_par.
rchan[SIO_NCHAN]
Matriz de números de canal compatibles para grabación utilizables en la estructura sio_par.
pchan[SIO_NCHAN]
Matriz de números de canal compatibles para reproducción utilizables en la estructura sio_par.
rate[SIO_NRATE]
Matriz de frecuencias de muestreo compatibles utilizables en la estructura sio_par.
nconf
Número de configuraciones diferentes disponibles, es decir, número de elementos rellenados del array confs[].
confs[SIO_NCONF]
Matriz de configuraciones disponibles. Cada configuración contiene máscaras de bits que indican qué elementos de las matrices de parámetros anteriores son válidos para la configuración dada. Por ejemplo, si el segundo bit de rate está establecido en la estructura sio_conf, entonces el segundo elemento de la matriz rate[SIO_NRATE] de la estructura sio_cap es válido para esta configuración. Como tal, al leer los elementos de la matriz en la estructura sio_cap, siempre se deben usar las máscaras de bits de sio_conf correspondientes.

Iniciar y detener el dispositivo

La función sio_start() prepara el dispositivo para comenzar. Una vez que el búfer de reproducción está lleno, es decir, se han puesto en cola sio_par.bufsz muestras con sio_write(), la reproducción comienza automáticamente. Si se selecciona el modo solo de grabación, sio_start() comienza a grabar inmediatamente. En modo dúplex completo, la reproducción y la grabación comenzarán de forma síncrona tan pronto como el búfer de reproducción esté lleno.

La función sio_stop() pone el subsistema de audio en el mismo estado que antes de llamar a sio_start(); detiene la grabación, vacía el búfer de reproducción y luego detiene la reproducción. Si hay muestras para reproducir puestas en cola pero la reproducción aún no ha comenzado, la reproducción se fuerza inmediatamente; la reproducción se detendrá una vez que el búfer se haya vaciado. En ningún caso se descartan las muestras en el búfer de reproducción.

La función sio_flush() detiene la reproducción y la grabación inmediatamente, posiblemente descartando el contenido del búfer de reproducción, y pone el subsistema de audio en el mismo estado que antes de llamar a sio_start().

Reproducción y grabación

Cuando se selecciona el modo de grabación, se debe llamar a la función sio_read() para recuperar los datos grabados; debe llamarse con la suficiente frecuencia para garantizar que los búferes internos no se desborden. Almacenará como máximo nbytes bytes en la ubicación addr y devolverá el número de bytes almacenados. A menos que se establezca la bandera nbio_flag, se bloqueará hasta que haya datos disponibles y devolverá cero solo en caso de error.

De manera similar, cuando se selecciona el modo de reproducción, se debe llamar a la función sio_write() para proporcionar datos para reproducir. A menos que se establezca la bandera nbio_flag, sio_write() se bloqueará hasta que se escriba la cantidad de datos solicitada.

Operación en modo no bloqueante

Si se establece la bandera nbio_flag en sio_open(), entonces las funciones sio_read() y sio_write() nunca se bloquearán; si no hay datos disponibles, devolverán cero inmediatamente.

DESCRIPTION

The functions described in this manual page allow applications to use the audio hardware for playing and/or recording digital audio streams.

The audio hardware is accessed through a sio_hdl handle, which is returned by the sio_open() function and must be passed to all other functions operating on the audio device. The sio_open() function opens the specified device, identified by name. If name is SIO_DEVANY, the system's default audio device is used. The mode parameter specifies whether the device is to be opened for playing (SIO_PLAY), recording (SIO_REC), or both (SIO_PLAY | SIO_REC). The par parameter is a pointer to a sio_par structure that specifies the desired audio parameters (number of channels, sample rate, encoding, etc.). If par is NULL, default parameters are used.

The sio_setpar() function sets the audio parameters. This must be done before calling sio_start(). The sio_getpar() function retrieves the current audio parameters. The sio_getcap() function retrieves the audio device capabilities.

The sio_start() function starts the audio device. It must be called after setting the parameters and before performing any read or write operations. The sio_stop() function stops the audio device. The sio_flush() function discards any pending data in the audio device buffers.

The sio_read() function reads recorded audio data from the device. The sio_write() function writes audio data to the device for playback. The number of bytes transferred is returned.

The sio_eof() function can be used to check for errors.

The sio_close() function closes the audio device and frees associated resources.

Polling the audio device

The sio_pollfd() function fills a pollfd structure with file descriptor and events suitable for use with the poll(2) system call. The caller must pass a pointer to a pre-allocated array of pollfd structures and its size. The function returns the number of structures filled. The caller is responsible for managing the returned file descriptor. The sio_nfds() function returns the number of pollfd structures that must be pre-allocated to hold all possible events. The bitmasks POLLIN and POLLOUT can be used to check the status of the device; refer to poll(2) for more details. The sio_revents() function returns the bitmask set by poll(2) in the pfd array of pollfd structures. If POLLIN is set, recorded samples are available in the device buffer and can be read with sio_read(). If POLLOUT is set, space is available in the device buffer and new samples to play can be submitted with sio_write(). POLLHUP may be set if an error occurs, even if it is not selected with sio_pollfd().

The size of the pfd array, which the caller must pre-allocate, is provided by the sio_nfds() function.

Synchronizing non-audio events to the audio stream in real-time

In order to perform actions at precise positions of the audio stream, such as displaying video in sync with the audio stream, the application must be notified in real-time of the exact position in the stream the hardware is processing.

The sio_onmove() function can be used to register the cb() callback function called at regular time intervals. The delta argument contains the number of frames the hardware played and/or recorded since the last call of cb(). It is called by sio_read(), sio_write(), and sio_revents(). When the first sample is played and/or recorded, right after the device starts, the callback is invoked with a zero delta argument. The value of the arg pointer is passed to the callback and can contain anything.

If desired, the application can maintain the current position by starting from zero (when sio_start() is called) and adding to the current position delta every time cb() is called.

Measuring the latency and buffers usage

The playback latency is the delay it will take for the frame just written to become audible, expressed in number of frames. The exact playback latency can be obtained by subtracting the current position from the number of frames written. Once playback is actually started (first sample audible), the latency will never exceed the bufsz parameter (see the sections above). There's a phase during which sio_write() only queues data; once there's enough data, actual playback starts. During this phase talking about latency is meaningless.

In any cases, at most bufsz frames are buffered. This value takes into account all buffers. The number of frames stored is equal to the number of frames written minus the current position.

The recording latency is obtained similarly, by subtracting the number of frames read from the current position.

Note that sio_write() might block even if there is buffer space left; using the buffer usage to guess if sio_write() would block is false and leads to unreliable programs – consider using poll(2) for this.

Handling buffer overruns and underruns

When the application cannot accept recorded data fast enough, the record buffer (of size appbufsz) might overrun; in this case recorded data is lost. Similarly if the application cannot provide data to play fast enough, the play buffer underruns and silence is played instead. Depending on the xrun parameter of the sio_par structure, the audio subsystem will behave as follows:

SIO_IGNORE
The device pauses during overruns and underruns, thus the current position (obtained through sio_onmove()) stops being incremented. Once the overrun and/or underrun condition is gone, the device resumes; play and record are always kept in sync. With this mode, the application cannot notice underruns and/or overruns and shouldn't care about them.

This mode is the default. It's suitable for applications, like audio players and telephony, where time is not important and overruns or underruns are not short.

SIO_SYNC
If the play buffer underruns, then silence is played, but in order to reach the right position in time, the same amount of written samples will be discarded once the application is unblocked. Similarly, if the record buffer overruns, then samples are discarded, but the same amount of silence will be returned later. The current position (obtained through sio_onmove()) is still incremented. When the play buffer underruns the play latency might become negative; when the record buffer overruns, the record latency might become larger than bufsz.

This mode is suitable for applications, like music production, where time is important and where underruns or overruns are short and rare.

SIO_ERROR
With this mode, on the first play buffer underrun or record buffer overrun, playback and/or recording is terminated and no other function than sio_close() will succeed.

This mode is mostly useful for testing.

Controlling the volume

The sio_setvol() function can be used to set playback attenuation. The vol parameter takes a value between 0 (maximum attenuation) and SIO_MAXVOL (no attenuation). It specifies the weight the audio subsystem will give to this stream. It is not meant to control hardware parameters like speaker gain; the mixerctl(8) interface should be used for that purpose instead.

An application can use the sio_onvol() function to register a callback function that will be called each time the volume is changed, including when sio_setvol() is used. The callback is always invoked when sio_onvol() is called in order to provide the initial volume. An application can safely assume that once sio_onvol() has returned a non-zero value, the callback has been invoked and thus the current volume is available. If there's no volume setting available, sio_onvol() returns 0 and the callback is never invoked and calls to sio_setvol() are ignored.

The sio_onvol() function can be called with a NULL argument to check whether a volume knob is available.

Error handling

Errors related to the audio subsystem (like hardware errors, dropped connections) and programming errors (e.g. call to sio_read() on a play-only stream) are considered fatal. Once an error occurs, all functions taking a sio_hdl argument, except sio_close() and sio_eof(), stop working (i.e. always return 0). The sio_eof() function can be used at any stage.

RETURN VALUES

The sio_open() function returns the newly created handle on success or NULL on failure.

The sio_setpar(), sio_getpar(), sio_getcap(), sio_start(), sio_stop(), sio_flush(), and sio_setvol() functions return 1 on success and 0 on failure.

The sio_pollfd() function returns the number of pollfd structures filled. The sio_nfds() function returns the number of pollfd structures the caller must preallocate in order to be sure that sio_pollfd() will never overrun.

The sio_read() and sio_write() functions return the number of bytes transferred.

The sio_eof() function returns 0 if there's no pending error, and a non-zero value if there's an error.

ERRORES

El controlador audio(4) no vacía los búferes de reproducción, por lo tanto, si sndio se utiliza para acceder directamente a un dispositivo audio(4), la función sio_stop() detendrá la reproducción inmediatamente.

Si la aplicación no consume los datos grabados lo suficientemente rápido, los “mensajes de control” del servidor sndiod(8) se retrasan y, en consecuencia, la devolución de llamada sio_onmove() o los cambios de volumen pueden retrasarse.

Las funciones sio_open(), sio_setpar(), sio_getpar(), sio_getcap(), sio_start(), sio_stop() y sio_flush() pueden bloquearse durante un período muy corto de tiempo, por lo tanto, deben evitarse en secciones de código donde el bloqueo no sea deseable.
