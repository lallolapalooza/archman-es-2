sigaltstack(2) Manual de llamadas al sistema sigaltstack(2)

NOMBRE

sigaltstack - configurar y/o obtener el contexto de la pila de señales

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

SINOPSIS

#include <signal.h>
int sigaltstack(const stack_t *_Nullable restrict ss,
                stack_t *_Nullable restrict old_ss);
Requisitos de Macro de Prueba de Funciones para glibc (ver feature_test_macros(7)):

sigaltstack():

    _XOPEN_SOURCE >= 500
        || /* Desde glibc 2.12: */ _POSIX_C_SOURCE >= 200809L
        || /* glibc <= 2.19: */ _BSD_SOURCE

DESCRIPCIÓN

sigaltstack() permite a un hilo definir una nueva pila de señales alternativa y/o recuperar el estado de una pila de señales alternativa existente. Una pila de señales alternativa se utiliza durante la ejecución de un manejador de señales si el establecimiento de dicho manejador (ver sigaction(2)) lo solicitó.

La secuencia normal de eventos para usar una pila de señales alternativa es la siguiente:

1.
Asignar un área de memoria para ser utilizada como pila de señales alternativa.
2.
Usar sigaltstack() para informar al sistema de la existencia y ubicación de la pila de señales alternativa.
3.
Al establecer un manejador de señales usando sigaction(2), informar al sistema que el manejador de señales debe ejecutarse en la pila de señales alternativa especificando la bandera SA_ONSTACK.

El argumento ss se utiliza para especificar una nueva pila de señales alternativa, mientras que el argumento old_ss se utiliza para recuperar información sobre la pila de señales actualmente establecida. Si solo nos interesa realizar una de estas tareas, el otro argumento puede especificarse como NULL.

El tipo stack_t utilizado para tipificar los argumentos de esta función se define de la siguiente manera:


typedef struct {
    void  *ss_sp;     /* Dirección base de la pila */
    int    ss_flags;  /* Banderas */
    size_t ss_size;   /* Número de bytes en la pila */
} stack_t;

Para establecer una nueva pila de señales alternativa, los campos de esta estructura se establecen de la siguiente manera:

ss.ss_flags
Este campo contiene 0 o la siguiente bandera:
SS_AUTODISARM (desde Linux 4.7)
Borra la configuración de la pila de señales alternativa al entrar en el manejador de señales. Cuando el manejador de señales retorna, se restaura la configuración anterior de la pila de señales alternativa.
Esta bandera se agregó para que sea seguro cambiar desde el manejador de señales con swapcontext(3). Sin esta bandera, una señal manejada posteriormente corromperá el estado del manejador de señales cambiado. En kernels donde esta bandera no es compatible, sigaltstack() falla con el error EINVAL cuando se proporciona esta bandera.
ss.ss_sp
Este campo especifica la dirección de inicio de la pila. Cuando se invoca un manejador de señales en la pila alternativa, el kernel alinea automáticamente la dirección dada en ss.ss_sp a un límite de dirección adecuado para la arquitectura de hardware subyacente.
ss.ss_size
Este campo especifica el tamaño de la pila. La constante SIGSTKSZ se define para que sea lo suficientemente grande como para cubrir los requisitos de tamaño habituales de una pila de señales alternativa, y la constante MINSIGSTKSZ define el tamaño mínimo requerido para ejecutar un manejador de señales.

Para deshabilitar una pila existente, especifique ss.ss_flags como SS_DISABLE. En este caso, el kernel ignora cualquier otra bandera en ss.ss_flags y los campos restantes en ss.

Si old_ss no es NULL, se utiliza para devolver información sobre la pila de señales alternativa que estaba en vigor antes de la llamada a sigaltstack(). Los campos old_ss.ss_sp y old_ss.ss_size devuelven la dirección de inicio y el tamaño de esa pila. old_ss.ss_flags puede devolver cualquiera de los siguientes valores:

SS_ONSTACK
El hilo se está ejecutando actualmente en la pila de señales alternativa. (Tenga en cuenta que no es posible cambiar la pila de señales alternativa si el hilo ya se está ejecutando en ella).
SS_DISABLE
La pila de señales alternativa está actualmente deshabilitada.
Alternativamente, este valor se devuelve si el hilo se está ejecutando actualmente en una pila de señales alternativa que se estableció utilizando la bandera SS_AUTODISARM. En este caso, es seguro cambiar desde el manejador de señales con swapcontext(3). También es posible configurar una pila de señales alternativa diferente mediante una llamada adicional a sigaltstack().
SS_AUTODISARM
La pila de señales alternativa se ha marcado para ser desarmada automáticamente, como se describe anteriormente.

Al especificar ss como NULL, y old_ss como un valor no NULL, se pueden obtener la configuración actual de la pila de señales alternativa sin cambiarla.

VALOR DE RETORNO

sigaltstack() devuelve 0 en caso de éxito, o -1 en caso de error con errno establecido para indicar el error.

ERRORES

EFAULT
Ya sea ss o old_ss no es NULL y apunta a un área fuera del espacio de direcciones del proceso.
EINVAL
ss no es NULL y el campo ss_flags contiene una bandera inválida.
ENOMEM
El tamaño especificado para la nueva pila de señales alternativa ss.ss_size era menor que MINSIGSTKSZ.
EPERM
Se intentó cambiar la pila de señales alternativa mientras estaba activa (es decir, el hilo ya se estaba ejecutando en la pila de señales alternativa actual).

ESTÁNDARES

POSIX.1-2024.

SS_AUTODISARM es una extensión de Linux.

HISTORIA

POSIX.1-2001, SUSv2, SVr4.

NOTAS

El uso más común de una pila de señales alternativa es para manejar la señal SIGSEGV que se genera si el espacio disponible para la pila estándar se agota: en este caso, un manejador de señales para SIGSEGV no puede invocarse en la pila estándar; si deseamos manejarla, debemos usar una pila de señales alternativa.

Establecer una pila de señales alternativa es útil si un hilo espera agotar su pila estándar. Esto puede ocurrir, por ejemplo, porque la pila crece tanto que entra en conflicto con el heap que crece hacia arriba, o alcanza un límite establecido por una llamada a setrlimit(RLIMIT_STACK, &rlim). Si la pila estándar se agota, el kernel envía al hilo una señal SIGSEGV. En estas circunstancias, la única forma de capturar esta señal es en una pila de señales alternativa.

En la mayoría de las arquitecturas de hardware compatibles con Linux, las pilas crecen hacia abajo. sigaltstack() tiene en cuenta automáticamente la dirección del crecimiento de la pila.

Las funciones llamadas desde un manejador de señales que se ejecuta en una pila de señales alternativa también utilizarán la pila de señales alternativa. (Esto también se aplica a cualquier manejador invocado para otras señales mientras el hilo se está ejecutando en la pila de señales alternativa). A diferencia de la pila estándar, el sistema no extiende automáticamente la pila de señales alternativa. Exceder el tamaño asignado de la pila de señales alternativa provocará resultados impredecibles.

Una llamada exitosa a execve(2) elimina cualquier pila de señales alternativa existente. Un proceso hijo creado a través de fork(2) hereda una copia de la configuración de la pila de señales alternativa de su padre. Lo mismo ocurre con un proceso hijo creado utilizando clone(2), a menos que las banderas de clonación incluyan CLONE_VM y no incluyan CLONE_VFORK, en cuyo caso cualquier pila de señales alternativa que se haya establecido en el padre se deshabilita en el proceso hijo.

sigaltstack() reemplaza la llamada anterior sigstack(). Para compatibilidad con versiones anteriores, glibc también proporciona sigstack(). Todas las aplicaciones nuevas deben escribirse utilizando sigaltstack().

Historial

4.2BSD tenía una llamada al sistema sigstack(). Utilizaba una estructura ligeramente diferente y tenía la gran desventaja de que el llamador tenía que conocer la dirección del crecimiento de la pila.

ERRORES

En Linux 2.2 y anteriores, la única bandera que se podía especificar en ss.sa_flags era SS_DISABLE. En el período previo al lanzamiento del kernel de Linux 2.4, se realizó un cambio para permitir que sigaltstack() permitiera ss.ss_flags==SS_ONSTACK con el mismo significado que ss.ss_flags==0 (es decir, la inclusión de SS_ONSTACK en ss.ss_flags es una operación nula). En otras implementaciones, y según POSIX.1, SS_ONSTACK aparece solo como una bandera reportada en old_ss.ss_flags. En Linux, nunca es necesario especificar SS_ONSTACK en ss.ss_flags, y de hecho, hacerlo debería evitarse por motivos de portabilidad: varios otros sistemas devuelven un error si se especifica SS_ONSTACK en ss.ss_flags.

EJEMPLOS

El siguiente segmento de código demuestra el uso de sigaltstack() (y sigaction(2)) para instalar una pila de señales alternativa que es utilizada por un manejador para la señal SIGSEGV:


stack_t ss;
ss.ss_sp = malloc(SIGSTKSZ);
if (ss.ss_sp == NULL) {
    perror("malloc");
    exit(EXIT_FAILURE);
}
ss.ss_size = SIGSTKSZ;
ss.ss_flags = 0;
if (sigaltstack(&ss, NULL) == -1) {
    perror("sigaltstack");
    exit(EXIT_FAILURE);
}
sa.sa_flags = SA_ONSTACK;
sa.sa_handler = handler();      /* Dirección de un manejador de señales */
sigemptyset(&sa.sa_mask);
if (sigaction(SIGSEGV, &sa, NULL) == -1) {
    perror("sigaction");
    exit(EXIT_FAILURE);
}
