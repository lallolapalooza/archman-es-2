signalfd(2) Manual de llamadas al sistema signalfd(2)

NOMBRE

signalfd - crear un descriptor de archivo para aceptar señales

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

SINOPSIS

#include <sys/signalfd.h>
int signalfd(int fd, const sigset_t *mask, int flags);

DESCRIPCIÓN

signalfd() crea un descriptor de archivo que puede usarse para aceptar señales dirigidas al llamador. Esto proporciona una alternativa al uso de un manejador de señales o sigwaitinfo(2), y tiene la ventaja de que el descriptor de archivo puede ser monitorizado por select(2), poll(2) y epoll(7).

El argumento mask especifica el conjunto de señales que el llamador desea aceptar a través del descriptor de archivo. Este argumento es un conjunto de señales cuyos contenidos pueden ser inicializados usando las macros descritas en sigsetops(3). Normalmente, el conjunto de señales que se recibirán a través del descriptor de archivo debe ser bloqueado usando sigprocmask(2), para evitar que las señales sean manejadas de acuerdo con sus disposiciones predeterminadas. No es posible recibir señales SIGKILL o SIGSTOP a través de un descriptor de archivo signalfd; estas señales son ignoradas silenciosamente si se especifican en mask.

Si el argumento fd es -1, la llamada crea un nuevo descriptor de archivo y asocia el conjunto de señales especificado en mask con ese descriptor de archivo. Si fd no es -1, debe especificar un descriptor de archivo signalfd existente válido, y mask se utiliza para reemplazar el conjunto de señales asociado con ese descriptor de archivo.

A partir de Linux 2.6.27, los siguientes valores pueden ser ORados bit a bit en flags para cambiar el comportamiento de signalfd():

SFD_NONBLOCK
Establece la bandera de estado de archivo O_NONBLOCK en la descripción de archivo (ver open(2)) referenciada por el nuevo descriptor de archivo. El uso de esta bandera ahorra llamadas adicionales a fcntl(2) para lograr el mismo resultado.
SFD_CLOEXEC
Establece la bandera close-on-exec (FD_CLOEXEC) en el nuevo descriptor de archivo. Ver la descripción de la bandera O_CLOEXEC en open(2) para conocer las razones por las que esto puede ser útil.

Hasta Linux 2.6.26, el argumento flags no se utiliza y debe ser especificado como cero.

signalfd() devuelve un descriptor de archivo que soporta las siguientes operaciones:

read(2)
Si una o más de las señales especificadas en mask están pendientes para el proceso, el buffer suministrado a read(2) se usa para devolver una o más estructuras signalfd_siginfo (ver más abajo) que describen las señales. La llamada a read(2) devuelve información para tantas señales como estén pendientes y quepan en el buffer suministrado. El buffer debe tener al menos sizeof(struct signalfd_siginfo) bytes. El valor de retorno de la llamada a read(2) es el número total de bytes leídos.
Como consecuencia de la llamada a read(2), las señales se consumen, de modo que ya no están pendientes para el proceso (es decir, no serán capturadas por manejadores de señales, ni podrán ser aceptadas usando sigwaitinfo(2)).
Si ninguna de las señales en mask está pendiente para el proceso, la llamada a read(2) se bloqueará hasta que una de las señales en mask sea generada para el proceso, o falle con el error EAGAIN si el descriptor de archivo se ha hecho no bloqueante.
poll(2)
select(2)
(y similares)
El descriptor de archivo es legible (el argumento readfds de select(2); la bandera POLLIN de poll(2)) si una o más de las señales en mask están pendientes para el proceso.
El descriptor de archivo signalfd también soporta las otras APIs de multiplexación de descriptores de archivo: pselect(2), ppoll(2) y epoll(7).
close(2)
Cuando el descriptor de archivo ya no sea necesario, debe ser cerrado. Cuando todos los descriptores de archivo asociados con el mismo objeto signalfd hayan sido cerrados, los recursos del objeto serán liberados por el kernel.

La estructura signalfd_siginfo

El formato de las estructuras signalfd_siginfo devueltas por las llamadas a read(2) desde un descriptor de archivo signalfd es el siguiente:


struct signalfd_siginfo {
    uint32_t ssi_signo;    /* Signal number */
    int32_t  ssi_errno;    /* Error number (unused) */
    int32_t  ssi_code;     /* Signal code */
    uint32_t ssi_pid;      /* PID of sender */
    uint32_t ssi_uid;      /* Real UID of sender */
    int32_t  ssi_fd;       /* File descriptor (SIGIO) */
    uint32_t ssi_tid;      /* Kernel timer ID (POSIX timers)
    uint32_t ssi_band;     /* Band event (SIGIO) */
    uint32_t ssi_overrun;  /* POSIX timer overrun count */
    uint32_t ssi_trapno;   /* Trap number that caused signal */
    int32_t  ssi_status;   /* Exit status or signal (SIGCHLD) */
    int32_t  ssi_int;      /* Integer sent by sigqueue(3) */
    uint64_t ssi_ptr;      /* Pointer sent by sigqueue(3) */
    uint64_t ssi_utime;    /* User CPU time consumed (SIGCHLD) */
    uint64_t ssi_stime;    /* System CPU time consumed
                              (SIGCHLD) */
    uint64_t ssi_addr;     /* Address that generated signal
                              (for hardware-generated signals) */
    uint16_t ssi_addr_lsb; /* Least significant bit of address
                              (SIGBUS; since Linux 2.6.37) */
    uint8_t  pad[X];       /* Pad size to 128 bytes (allow for
                              additional fields in the future) */
};

Cada uno de los campos de esta estructura es análogo al campo con el mismo nombre en la estructura siginfo_t. La estructura siginfo_t se describe en sigaction(2). No todos los campos de la estructura signalfd_siginfo devuelta serán válidos para una señal específica; el conjunto de campos válidos puede determinarse a partir del valor devuelto en el campo ssi_code. Este campo es análogo al campo si_code de siginfo_t; ver sigaction(2) para más detalles.

Semántica de fork(2)

Después de una llamada a fork(2), el hijo hereda una copia del descriptor de archivo signalfd. Una llamada a read(2) desde el descriptor de archivo en el hijo devolverá información sobre las señales en cola para el hijo.

Semántica del paso de descriptores de archivo

Al igual que con otros descriptores de archivo, los descriptores de archivo signalfd pueden ser pasados a otro proceso a través de un socket de dominio UNIX (ver unix(7)). En el proceso receptor, una llamada a read(2) desde el descriptor de archivo recibido devolverá información sobre las señales en cola para ese proceso.

Semántica de execve(2)

Al igual que cualquier otro descriptor de archivo, un descriptor de archivo signalfd permanece abierto a través de una llamada a execve(2), a menos que haya sido marcado para close-on-exec (ver fcntl(2)). Cualquier señal que estuviera disponible para leer antes de la llamada a execve(2) permanece disponible para el programa recién cargado. signalfd(2) - Linux manual page

NAME

signalfd - create a file descriptor that gathers signals

SYNOPSIS

#include <sys/signalfd.h>

int signalfd(int fd, const sigset_t *mask, int flags);

DESCRIPTION

The signalfd() system call creates a new file descriptor that receives a stream of values describing signals that have been delivered to the calling thread but not yet handled. The stream of signals is produced by reading from the returned file descriptor.

The fd argument specifies the file descriptor to create or reuse. If fd is -1, a new signalfd file descriptor is created. If fd is a valid file descriptor created by a previous call to signalfd(), then that existing file descriptor is reused, and its flags and signal mask are updated according to the values provided in the current call.

The mask argument is a pointer to a signal mask that specifies the set of signals to be received by the signalfd file descriptor. Signals specified in the mask are delivered to the signalfd file descriptor instead of being processed according to their default dispositions. If a signal is specified in mask, then the signal is blocked for the calling thread (see sigprocmask(2)). This means that the signal is held pending for the thread until it is unblocked or it is read from the signalfd file descriptor.

The flags argument specifies a bit mask that controls the behavior of the signalfd file descriptor. The following flags are supported:

SFD_NONBLOCK
Set the O_NONBLOCK file status flag on the new file descriptor. Thus, the file descriptor is opened non-blocking. This is equivalent to using the fcntl(2) F_SETFL with the O_NONBLOCK flag.
SFD_CLOEXEC
Set the close-on-exec flag for the new file descriptor. See the description of the O_CLOEXEC flag in open(2).

When a signal that is specified in the mask is delivered to the calling thread, a structure of type struct signalfd_siginfo is added to the buffer associated with the signalfd file descriptor. This structure contains the same information as is available via the siginfo_t argument of a signal handler.

Reading from the signalfd file descriptor retrieves the oldest pending struct signalfd_siginfo structure from the buffer. If multiple instances of the same signal have been delivered since the last read, only one structure is returned.

If the signalfd file descriptor is set to non-blocking mode and there are no signals available to be read, read(2) returns -1 and sets errno to EAGAIN.

The signals that are received via the signalfd file descriptor are not delivered by the kernel through the usual signal-handling mechanisms. Specifically, if a signal is caught by a signalfd file descriptor, the signal will not be delivered to any registered signal handler, nor will it invoke the default signal disposition. The signal is considered handled if it is read from the signalfd file descriptor.

If a signal is masked by the signalfd file descriptor and also by the thread's signal mask (using sigprocmask(2)), the signal remains pending for the thread. If the signal is unblocked by sigprocmask(2), and then read from the signalfd file descriptor, the signal is considered handled. If the signal is unblocked and not read from the signalfd file descriptor, the signal is delivered according to its disposition (which might be to a signal handler or the default disposition).

A signal that is blocked by the thread's signal mask (using sigprocmask(2)) can still be accepted via the signalfd file descriptor. However, if the signal is unblocked by the thread's signal mask, and if it is not read from the signalfd file descriptor, the signal will be delivered by the kernel according to its disposition (handler or default action). A signal that is not masked by the thread's signal mask and is not read from the signalfd file descriptor will be delivered by the kernel according to its disposition.

The signal mask supplied to signalfd() determines which signals are *intercepted* by the signalfd file descriptor. The thread's own signal mask determines whether a signal is *pending* for the thread. A signal can be received by the signalfd file descriptor only if it is in the mask supplied to signalfd() and it is pending for the thread. If a signal is in the mask supplied to signalfd(), it is automatically blocked for the thread, and remains pending for the thread until it is read from the signalfd file descriptor.

The signal mask specified in the mask argument is a pointer to a sigset_t value. The set of signals that will be accepted by this signalfd file descriptor is defined by this mask.

The flags argument can be 0 or any of the flags described above. In Linux versions before 2.6.26, the flags argument is not supported, and the call will fail with EINVAL if flags is nonzero.

When a signal is read from the signalfd file descriptor, the corresponding pending signal for the thread is cleared. This means that the signal is no longer pending for the thread.

A call to execve(2) does not affect a signalfd file descriptor. Signals that were pending and have been read remain read. Signals that are pending and not yet read remain pending.

Thread semantics

The semantics of signalfd file descriptors in a multithreaded program mirror the standard semantics for signals. In other words, when a thread reads from a signalfd file descriptor, it will read the signals that are directed to the thread itself and the signals that are directed to the process (i.e., the entire thread group). (A thread will not be able to read signals that are directed to other threads in the process.)

epoll(7) semantics

If a process adds (via epoll_ctl(2)) a signalfd file descriptor to an epoll(7) instance, then epoll_wait(2) returns events only for signals sent to that process. In particular, if the process then uses fork(2) to create a child process, then the child will be able to read(2) signals that are sent to it using the signalfd file descriptor, but epoll_wait(2) will not indicate that the signalfd file descriptor is ready. In this scenario, a possible workaround is that after the fork(2), the child process can close the signalfd file descriptor that it inherited from the parent process and then create another signalfd file descriptor and add it to the epoll instance. Alternatively, the parent and the child could delay creating their (separate) signalfd file descriptors and adding them to the epoll instance until after the call to fork(2).

RETURN VALUE

On success, signalfd() returns a signalfd file descriptor; this is either a new file descriptor (if fd was -1), or fd if fd was a valid signalfd file descriptor. On error, -1 is returned and errno is set to indicate the error.

ERRORS

EBADF
The fd file descriptor is not a valid file descriptor.
EINVAL
fd is not a valid signalfd file descriptor.
EINVAL
flags is invalid; or, in Linux 2.6.26 or earlier, flags is nonzero.
EMFILE
The per-process limit on the number of open file descriptors has been reached.
ENFILE
The system-wide limit on the total number of open files has been reached.
ENODEV
Could not mount (internal) anonymous inode device.
ENOMEM
There was insufficient memory to create a new signalfd file descriptor.

VERSIONS

C library/kernel differences

The underlying Linux system call requires an additional argument, size_t sizemask, which specifies the size of the mask argument. The glibc signalfd() wrapper function does not include this argument, since it provides the required value for the underlying system call.

There are two underlying Linux system calls: signalfd() and the more recent signalfd4(). The former system call does not implement a flags argument. The latter system call implements the flags values described above. Starting with glibc 2.9, the signalfd() wrapper function will use signalfd4() where it is available.

STANDARDS

Linux.

HISTORY

Linux 2.6.22, glibc 2.8.
signalfd4()
Linux 2.6.27.

NOTES

A process can create multiple signalfd file descriptors. This makes it possible to accept different signals on different file descriptors. (This may be useful if monitoring the file descriptors using select(2), poll(2), or epoll(7): the arrival of different signals will make different file descriptors ready.) If a signal appears in the mask of more than one of the file descriptors, then occurrences of that signal can be read (once) from any one of the file descriptors.

Attempts to include SIGKILL and SIGSTOP in mask are silently ignored.

The signal mask employed by a signalfd file descriptor can be viewed via the entry for the corresponding file descriptor in the process's /proc/pid/fdinfo directory. See proc(5) for further details.

Limitations

The signalfd mechanism can't be used to receive signals that are synchronously generated, such as the SIGSEGV signal that results from accessing an invalid memory address or the SIGFPE signal that results from an arithmetic error. Such signals can be caught only via signal handler.

As described above, in normal usage one blocks the signals that will be accepted via signalfd(). If spawning a child process to execute a helper program (that does not need the signalfd file descriptor), then, after the call to fork(2), you will normally want to unblock those signals before calling execve(2), so that the helper program can see any signals that it expects to see. Be aware, however, that this won't be possible in the case of a helper program spawned behind the scenes by any library function that the program may call. In such cases, one must fall back to using a traditional signal handler that writes to a file descriptor monitored by select(2), poll(2), or epoll(7).

BUGS

Before Linux 2.6.25, the ssi_ptr and ssi_int fields are not filled in with the data accompanying a signal sent by sigqueue(3).

EXAMPLES

The program below accepts the signals SIGINT and SIGQUIT via a signalfd file descriptor. The program terminates after accepting a SIGQUIT signal. The following shell session demonstrates the use of the program:


$ ./signalfd_demo
^C                   # Control-C generates SIGINT
Got SIGINT
^C
Got SIGINT
^\                    # Control-\ generates SIGQUIT
Got SIGQUIT
$

Program source

#include <err.h>
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/signalfd.h>
#include <sys/types.h>
#include <unistd.h>
int
main(void)
{
    int                      sfd;
    ssize_t                  s;
    sigset_t                 mask;
    struct signalfd_siginfo  fdsi;
    sigemptyset(&mask);
    sigaddset(&mask, SIGINT);
    sigaddset(&mask, SIGQUIT);
    /* Block signals so that they aren't handled
       according to their default dispositions.  */
    if (sigprocmask(SIG_BLOCK, &mask, NULL) == -1)
        err(EXIT_FAILURE, "sigprocmask");
    sfd = signalfd(-1, &mask, 0);
    if (sfd == -1)
        err(EXIT_FAILURE, "signalfd");
    for (;;) {
        s = read(sfd, &fdsi, sizeof(fdsi));
        if (s != sizeof(fdsi))
            err(EXIT_FAILURE, "read");
        if (fdsi.ssi_signo == SIGINT) {
            printf("Got SIGINT\n");
        } else if (fdsi.ssi_signo == SIGQUIT) {
            printf("Got SIGQUIT\n");
            exit(EXIT_SUCCESS);
        } else {
            printf("Read unexpected signal\n");
        }
    }
}
