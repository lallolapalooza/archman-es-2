signal(2) Manual de llamadas al sistema signal(2)

NOMBRE

signal - manejo de señales ANSI C

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

SINOPSIS

#include <signal.h>
typedef typeof(void (int))  *sighandler_t;
sighandler_t signal(int signum, sighandler_t handler);

DESCRIPCIÓN

ADVERTENCIA: el comportamiento de signal() varía entre versiones de UNIX, y también ha variado históricamente entre diferentes versiones de Linux. Evite su uso: use sigaction(2) en su lugar. Ver Portabilidad más abajo.

signal() establece la disposición de la señal signum a handler, que puede ser SIG_IGN, SIG_DFL, o la dirección de una función definida por el programador (un "manejador de señales").

Si la señal signum se entrega al proceso, entonces ocurre uno de los siguientes:

*
Si la disposición se establece a SIG_IGN, entonces la señal es ignorada.
*
Si la disposición se establece a SIG_DFL, entonces ocurre la acción predeterminada asociada con la señal (ver signal(7)).
*
Si la disposición se establece a una función, entonces primero o bien la disposición se restablece a SIG_DFL, o la señal se bloquea (ver Portabilidad más abajo), y luego se llama a handler con el argumento signum. Si la invocación del manejador provocó que la señal se bloqueara, entonces la señal se desbloquea al regresar del manejador.

Las señales SIGKILL y SIGSTOP no pueden ser capturadas o ignoradas.

VALOR DE RETORNO

signal() devuelve el valor anterior del manejador de señales. En caso de error, devuelve SIG_ERR y se establece errno para indicar el error.

ERRORES

EINVAL
signum es inválido.

VERSIONES

El uso de sighandler_t es una extensión GNU, expuesta si se define _GNU_SOURCE; glibc también define (derivado de BSD) sig_t si se define _BSD_SOURCE (glibc 2.19 y anteriores) o _DEFAULT_SOURCE (glibc 2.19 y posteriores). La definición estándar de signal() es:


typeof(void (int)) *signal(int signum, typeof(void (int)) *handler);

Portabilidad

El único uso portable de signal() es establecer la disposición de una señal a SIG_DFL o SIG_IGN. Las semánticas al usar signal() para establecer un manejador de señales varían entre sistemas (y POSIX.1 explícitamente permite esta variación); no lo use para este propósito.

POSIX.1 resolvió el desorden de portabilidad especificando sigaction(2), que proporciona control explícito de las semánticas al invocar un manejador de señales; use esa interfaz en lugar de signal().

ESTANDARES

C11, POSIX.1-2024.

HISTORIA

C89, POSIX.1-2001.

En los sistemas UNIX originales, cuando un manejador establecido mediante signal() era invocado por la entrega de una señal, la disposición de la señal se restablecía a SIG_DFL, y el sistema no bloqueaba la entrega de instancias posteriores de la señal. Esto es equivalente a llamar a sigaction(2) con las siguientes banderas:


sa.sa_flags = SA_RESETHAND | SA_NODEFER;

System V también proporciona estas semánticas para signal(). Esto era malo porque la señal podía entregarse de nuevo antes de que el manejador tuviera la oportunidad de restablecerse. Además, las entregas rápidas de la misma señal podían resultar en invocaciones recursivas del manejador.

BSD mejoró esta situación, pero desafortunadamente también cambió las semánticas de la interfaz existente de signal() al hacerlo. En BSD, cuando se invoca un manejador de señales, la disposición de la señal no se restablece, y las instancias posteriores de la señal se bloquean de ser entregadas mientras el manejador se está ejecutando. Además, ciertas llamadas al sistema bloqueantes se reinician automáticamente si son interrumpidas por un manejador de señales (ver signal(7)). Las semánticas de BSD son equivalentes a llamar a sigaction(2) con las siguientes banderas:


sa.sa_flags = SA_RESTART;

La situación en Linux es la siguiente:

•
La llamada al sistema signal() del kernel proporciona semánticas de System V.
•
Por defecto, en glibc 2 y posteriores, la función envoltorio signal() no invoca la llamada al sistema del kernel. En su lugar, llama a sigaction(2) usando banderas que proporcionan semánticas BSD. Este comportamiento predeterminado se proporciona siempre que se defina una macro de prueba de características adecuada: _BSD_SOURCE en glibc 2.19 y anteriores o _DEFAULT_SOURCE en glibc 2.19 y posteriores. (Por defecto, estas macros están definidas; ver feature_test_macros(7) para más detalles.) Si no se define dicha macro de prueba de características, entonces signal() proporciona semánticas de System V.

NOTAS

Los efectos de signal() en un proceso multihilo no están especificados.

Según POSIX, el comportamiento de un proceso es indefinido después de que ignora una señal SIGFPE, SIGILL o SIGSEGV que no fue generada por kill(2) o raise(3). La división entera por cero tiene un resultado indefinido. En algunas arquitecturas generará una señal SIGFPE. (Dividir el entero más negativo por -1 también puede generar SIGFPE). Ignorar esta señal podría llevar a un bucle infinito.

Ver sigaction(2) para detalles sobre lo que sucede cuando la disposición SIGCHLD se establece a SIG_IGN.

Ver signal-safety(7) para una lista de las funciones seguras asíncronas de señal que se pueden llamar de forma segura dentro de un manejador de señales.

signal(2)

Esta página de manual es para la versión 6.16-1 de las man-pages de Arch Linux.

NOMBRE

signal, kill, raise, alarm, pause - enviar una señal a un proceso o entre procesos

BIBLIOTECA

libc, como parte de glibc

SINÓPSIS

#include <signal.h>

int kill(pid_t pid, int sig);
int raise(int sig);
unsigned int alarm(unsigned int seconds);
int pause(void);

DESCRIPCIÓN

Estas funciones proporcionan una forma rudimentaria para que los procesos se comuniquen entre sí y para que un proceso se notifique a sí mismo sobre eventos. Las señales son notificaciones asíncronas que pueden ser enviadas a un proceso o a un grupo de procesos. Cuando un proceso recibe una señal, se produce una de varias acciones posibles:

  • Ignorar la señal.
  • Terminar el proceso.
  • Detener el proceso (y luego reanudarlo).
  • Ejecutar una función de manejo de señales específica.

kill() envía la señalsigal proceso con IDpid.

raise() envía la señalsigal propio proceso que realiza la llamada.

alarm() programa un temporizador de alarma para que envíe la señalSIGALRMal proceso que realiza la llamada después desecondssegundos. Si se llama aalarm()varias veces, se cancela cualquier temporizador pendiente y se inicia un nuevo temporizador.

pause() hace que el proceso que realiza la llamada duerma hasta que reciba una señal cuya acción sea ejecutar un manejador o terminar el proceso.

VALOR DE RETORNO

En caso de éxito,kill()yraise()devuelven 0.alarm()devuelve el número de segundos restantes del temporizador anterior, o 0 si no había ningún temporizador pendiente.pause()devuelve -1 y estableceerrnopara indicar el error.

En caso de error,kill()yraise()devuelven -1 y establecenerrnopara indicar el error.alarm()devuelve un valor que se puede usar para indicar que el temporizador anterior era de 0 segundos (lo que significa que no se canceló ningún temporizador).

ERRORES

EAGAIN
La señal no pudo ser enviada porque el proceso de destino no existe o el proceso que realiza la llamada no tiene permiso para enviar la señal.
EINVAL
Se especificó un número de señal inválido.
ENOSYS
La llamada al sistemakill()no está implementada.

VERSIÓNES

La llamada al sistemakill()ha estado disponible desde la versión 1.0.4 del kernel de Linux.raise()se introdujo en el estándar POSIX.1-1990.alarm()ypause()se introdujeron en la versión 7 de Unix.

ESTÁNDARES

kill(),raise(),alarm()ypause()están definidos por POSIX.1.

HISTORIAL

kill()se introdujo en la versión 2.0 de Unix.

NOTAS

Las señales son un mecanismo de comunicación complejo y potente. Es importante entender las diferentes señales disponibles y cómo manejarlas adecuadamente para evitar comportamientos inesperados o fallos del programa.

La llamada al sistemakill()no se limita a "matar" procesos; se puede usar para enviar cualquier señal válida a un proceso.

La señalSIGKILLySIGSTOPno pueden ser capturadas, bloqueadas ni ignoradas. Son señales de último recurso para terminar o detener un proceso.

VER TAMBIÉN

signal(7), sigaction(2), sigprocmask(2), sigsetops(3)
