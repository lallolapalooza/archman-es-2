SIGTIMEDWAIT(3P) Manual del Programador de POSIX SIGTIMEDWAIT(3P)

PROLOG

Esta página del manual forma parte del Manual del Programador de POSIX. La implementación de esta interfaz en Linux puede diferir (consulte la página del manual correspondiente de Linux para conocer los detalles del comportamiento en Linux), o la interfaz puede no estar implementada en Linux.

NOMBRE

sigtimedwait, sigwaitinfo — esperar señales en cola

SINOPSIS

#include <signal.h>
int sigtimedwait(const sigset_t *restrict set,
    siginfo_t *restrict info,
    const struct timespec *restrict timeout);
int sigwaitinfo(const sigset_t *restrict set,
    siginfo_t *restrict info);

DESCRIPCIÓN

La función sigtimedwait() será equivalente a sigwaitinfo() excepto que si ninguna de las señales especificadas por set está pendiente, sigtimedwait() esperará durante el intervalo de tiempo especificado en la estructura timespec a la que apunta timeout. Si la estructura timespec apuntada por timeout tiene un valor cero y ninguna de las señales especificadas por set está pendiente, entonces sigtimedwait() retornará inmediatamente con un error. Si timeout es un puntero nulo, el comportamiento no está especificado. Si se soporta la opción de Reloj Monotónico, se utilizará el reloj CLOCK_MONOTONIC para medir el intervalo de tiempo especificado por el argumento timeout.

La función sigwaitinfo() selecciona la señal pendiente del conjunto especificado por set. Si varias señales pendientes en el rango SIGRTMIN a SIGRTMAX fueran seleccionadas, será la de menor número. El orden de selección entre señales de tiempo real y no de tiempo real, o entre múltiples señales no de tiempo real pendientes, no está especificado. Si ninguna señal en set está pendiente en el momento de la llamada, el hilo que llama se suspenderá hasta que una o más señales en set estén pendientes o hasta que sea interrumpido por una señal desbloqueada y atrapada.

La función sigwaitinfo() será equivalente a la función sigwait(), excepto que el valor de retorno y el método de reporte de errores son diferentes (ver VALOR DE RETORNO), y que si el argumento info no es NULL, el número de señal seleccionado se almacenará en el miembro si_signo, y la causa de la señal se almacenará en el miembro si_code. Si algún valor está en cola para la señal seleccionada, el primer valor en cola se desencolará y, si el argumento info no es NULL, el valor se almacenará en el miembro si_value de info. El recurso del sistema utilizado para poner la señal en cola será liberado y devuelto al sistema para otro uso. Si no hay más señales en cola para la señal seleccionada, la indicación pendiente para esa señal se restablecerá.

VALOR DE RETORNO

Al completarse con éxito (es decir, una de las señales especificadas por set está pendiente o se genera), sigwaitinfo() y sigtimedwait() devolverán el número de señal seleccionado. De lo contrario, la función devolverá un valor de -1 y establecerá errno para indicar el error.

ERRORES

La función sigtimedwait() fallará si:

EAGAIN
Ninguna señal especificada por set se generó dentro del período de tiempo de espera especificado.

Las funciones sigtimedwait() y sigwaitinfo() pueden fallar si:

EINTR
La espera fue interrumpida por una señal desbloqueada y capturada. Se documentará en la documentación del sistema si este error causa que estas funciones fallen.

La función sigtimedwait() también puede fallar si:

EINVAL
El argumento timeout especificó un valor tv_nsec menor que cero o mayor o igual a 1000 millones.

Una implementación solo debería verificar este error si no hay ninguna señal pendiente en set y es necesario esperar.

Las siguientes secciones son informativas.

EJEMPLOS

Ninguno.

USO EN LA APLICACIÓN

La función sigtimedwait() caduca y devuelve un error [EAGAIN]. Los desarrolladores de aplicaciones deben tener en cuenta que esto es inconsistente con otras funciones como pthread_cond_timedwait() que devuelven [ETIMEDOUT].

Tenga en cuenta que para asegurar que las señales generadas se pongan en cola y los valores de señal pasados a sigqueue() estén disponibles en si_value, las aplicaciones que utilizan sigwaitinfo() o sigtimedwait() necesitan establecer el flag SA_SIGINFO para cada señal en el conjunto (ver Sección 2.4, Conceptos de Señales). Esto implica establecer que cada señal sea manejada por una función de captura de señales de tres argumentos, incluso si el manejador nunca se llama. No es posible (de forma portable) establecer un manejador de señales en SIG_DFL mientras se establece el flag SA_SIGINFO, ya que la asignación al miembro sa_handler de struct sigaction en lugar del miembro sa_sigaction resultaría en un comportamiento indefinido, y SIG_DFL no necesita ser asignable a sa_sigaction. Incluso si una asignación de SIG_DFL a sa_sigaction es aceptada por el compilador, la implementación no necesita tratar este valor como especial; podría ser simplemente tomado como la dirección de una función de captura de señales.

FUNDAMENTO

La práctica de programación existente en sistemas de tiempo real utiliza la capacidad de pausar esperando un conjunto seleccionado de eventos y manejar el primer evento que ocurre en línea en lugar de en una función de manejo de señales. Esto permite escribir aplicaciones en un estilo dirigido por eventos similar a una máquina de estados. Este estilo de programación es útil para el procesamiento de transacciones a gran escala en el que el rendimiento general de una aplicación y la capacidad de rastrear estados claramente son más importantes que la capacidad de minimizar el tiempo de respuesta del manejo de eventos individuales.

Es posible construir una función macro de espera de señales a partir del mecanismo de funciones de señales de tiempo real definido en este volumen de POSIX.1-2017. Sin embargo, tal macro tendría que incluir la definición de un manejador generalizado para todas las señales a las que se debe esperar. Una parte significativa de la sobrecarga del procesamiento del manejador se puede evitar si la función de espera de señales es proporcionada por el kernel. Por lo tanto, este volumen de POSIX.1-2017 proporciona dos funciones de espera de señales —una que espera indefinidamente y otra con tiempo de espera— como parte de la especificación general de la función de señales de tiempo real.

La especificación de una función con tiempo de espera permite escribir una aplicación que puede salir de una espera después de un período de tiempo establecido si no ha ocurrido ningún evento. Se argumentó que establecer un evento de temporizador antes de la espera y reconocer el evento de temporizador en la espera también implementaría la misma funcionalidad, pero a un nivel de rendimiento inferior. Debido a la degradación del rendimiento asociada con la especificación a nivel de usuario de un evento de temporizador y la posterior cancelación de ese evento de temporizador después de que la espera se complete para un evento válido, y la complejidad asociada con el manejo de posibles condiciones de carrera con el método a nivel de usuario, se ha incluido la función separada.

Tenga en cuenta que las semánticas de la función sigwaitinfo() son casi idénticas a las de la función sigwait() definida en este volumen de POSIX.1-2017. La única diferencia es que sigwaitinfo() devuelve el valor de la señal en cola en el argumento value. La devolución del valor en cola es necesaria para que las aplicaciones puedan diferenciar entre múltiples eventos en cola con el mismo número de señal.

Se mantienen las dos funciones distintas porque algunas implementaciones pueden optar por implementar las funciones de Extensión de Hilos de POSIX y no implementar las extensiones de señales en cola. Sin embargo, tenga en cuenta que sigwaitinfo() no devuelve el valor en cola si el argumento value es NULL, por lo que la extensión de Hilos de POSIX sigwait() puede implementarse como una macro sobre sigwaitinfo().

sigwaitinfo(2) — Arch Linux man pages

NAME

sigwaitinfo, sigtimedwait — wait for a signal to be delivered

SYNOPSIS

#include <signal.h>

int sigwaitinfo(const sigset_t *restrict set, siginfo_t *restrict info);
int sigtimedwait(const sigset_t *restrict set, siginfo_t *restrict info, const struct timespec *restrict timeout);

DESCRIPTION

The sigwaitinfo() function suspends the calling thread until one of the signals specified in the set set is delivered, or until the process receives a signal that is not in the process signal mask and is not ignored.

The sigtimedwait() function is similar to sigwaitinfo(), but it permits a timeout. If the timeout argument is not NULL, it specifies the maximum amount of time that sigtimedwait() will wait. If timeout is NULL, sigtimedwait() behaves like sigwaitinfo().

If info is not NULL, it points to a buffer that will be populated with information about the signal that caused the function to return. The structure is defined in <signal.h>.

The set of signals to be waited for is specified by the argument set, which points to a signal set bitmask.

If any of the signals specified in set are pending for the calling thread, one of these signals is chosen, removed from the thread's pending signal mask, and returned immediately. The signal information is stored in the location pointed to by info. The function then returns the number of the chosen signal.

If none of the signals specified in set are pending for the calling thread, the thread is suspended. If timeout is not NULL, the thread is suspended until one of the specified signals is delivered, or until the time specified by timeout elapses. If timeout is NULL, the thread is suspended indefinitely.

If the timeout expires before any of the signals in set are delivered, sigtimedwait() returns the error code EAGAIN, and the contents of the location pointed to by info are undefined.

If a signal is delivered that is not in set, and that signal is neither blocked nor ignored by the calling thread, the signal is delivered and processed normally. If the signal handler returns, the sigwaitinfo() or sigtimedwait() function resumes and returns the number of the signal that was delivered.

When sigwaitinfo() or sigtimedwait() return because one of the signals in set was delivered, the signal number is returned as the function's return value. The structure pointed to by info is filled with information about the signal.

The signal mask used by sigwaitinfo() and sigtimedwait() is the signal mask of the calling thread. The signal mask of a process is the union of the signal masks of all of its threads.

These functions remove the selected signal from the calling thread's pending signal list. If the selected signal was also pending for other threads in the process, it remains pending for those threads.

If the calling thread has blocked the signals specified in set, then sigwaitinfo() and sigtimedwait() will wait until one of the specified signals is unblocked and delivered, or until one of the specified signals occurs and is pending for the thread. If the signals are not blocked, they are delivered normally.

These functions are part of the POSIX real-time extensions.

RETURN VALUE

On success, sigwaitinfo() and sigtimedwait() return the signal number that was delivered.

If the timeout expires for sigtimedwait(), it returns EAGAIN.

On failure, these functions return -1 and set errno to indicate the error.

ERRORS

EINTR

A signal that was not blocked was delivered, and the signal handler returned.

EAGAIN

( sigtimedwait() only) The timeout expired before any of the specified signals were delivered.

EINVAL

The value pointed to by timeout is invalid.

ENOMEM

Insufficient memory to allocate internal data structures.

EXAMPLES

The following example shows how to use sigwaitinfo() to wait for the SIGINT signal:

#include <stdio.h>
#include <stdlib.h>
#include <signal.h>
#include <unistd.h>

int main() {
    sigset_t sigset;
    siginfo_t info;
    int signo;

    // Block SIGINT signal
    sigemptyset(&sigset);
    sigaddset(&sigset, SIGINT);
    if (sigprocmask(SIG_BLOCK, &sigset, NULL) == -1) {
        perror("sigprocmask");
        exit(EXIT_FAILURE);
    }

    printf("Waiting for SIGINT...\n");

    // Wait for SIGINT signal
    signo = sigwaitinfo(&sigset, &info);

    if (signo == -1) {
        perror("sigwaitinfo");
        exit(EXIT_FAILURE);
    }

    printf("Received signal %d: %s\n", signo, sys_siglist[signo]);
    printf("Signal was caught at time %ld.%02ld\n",
           info.si_stime, info.si_utime);

    // Unblock SIGINT signal
    if (sigprocmask(SIG_UNBLOCK, &sigset, NULL) == -1) {
        perror("sigprocmask");
        exit(EXIT_FAILURE);
    }

    return 0;
}

APPLICATION USAGE

The sigwaitinfo() and sigtimedwait() functions are useful for handling signals in a synchronous manner, allowing threads to wait for specific signals without using signal handlers. This can simplify signal handling logic in multithreaded applications.

When using sigtimedwait(), it is important to handle the EAGAIN error code, which indicates that the timeout expired.

RATIONALE

The introduction of sigwaitinfo() and sigtimedwait() functions was driven by the need to provide a more flexible and consistent interface for handling signals compared to the older sigwait() function. Concerns included the overloading of the timeout pointer in sigwait() to indicate indefinite wait, timed wait, and immediate return, as well as the inconsistency with other functions where conditional and timed waits were separate functions from the pure blocking function.

The semantics of sigtimedwait() are specified such that sigwaitinfo() could be implemented as a macro with a null pointer for timeout.

The sigwait functions provide a synchronous mechanism for threads to wait for asynchronously-generated signals. One important question was how many threads that are suspended in a call to a sigwait() function for a signal should return from the call when the signal is sent. Four choices were considered:

1.
Return an error for multiple simultaneous calls to sigwait functions for the same signal.
2.
One or more threads return.
3.
All waiting threads return.
4.
Exactly one thread returns.

Prohibiting multiple calls to sigwait() for the same signal was felt to be overly restrictive. The ``one or more'' behavior made implementation of conforming packages easy at the expense of forcing POSIX threads clients to protect against multiple simultaneous calls to sigwait() in application code in order to achieve predictable behavior. There was concern that the ``all waiting threads'' behavior would result in ``signal broadcast storms'', consuming excessive CPU resources by replicating the signals in the general case. Furthermore, no convincing examples could be presented that delivery to all was either simpler or more powerful than delivery to one.

Thus, the consensus was that exactly one thread that was suspended in a call to a sigwait function for a signal should return when that signal occurs. This is not an onerous restriction as:

*
A multi-way signal wait can be built from the single-way wait.
*
Signals should only be handled by application-level code, as library routines cannot guess what the application wants to do with signals generated for the entire process.
*
Applications can thus arrange for a single thread to wait for any given signal and call any needed routines upon its arrival.

In an application that is using signals for interprocess communication, signal processing is typically done in one place. Alternatively, if the signal is being caught so that process cleanup can be done, the signal handler thread can call separate process cleanup routines for each portion of the application. Since the application main line started each portion of the application, it is at the right abstraction level to tell each portion of the application to clean up.

Certainly, there exist programming styles where it is logical to consider waiting for a single signal in multiple threads. A simple sigwait_multiple() routine can be constructed to achieve this goal. A possible implementation would be to have each sigwait_multiple() caller registered as having expressed interest in a set of signals. The caller then waits on a thread-specific condition variable. A single server thread calls a sigwait() function on the union of all registered signals. When the sigwait() function returns, the appropriate state is set and condition variables are broadcast. New sigwait_multiple() callers may cause the pending sigwait() call to be canceled and reissued in order to update the set of signals being waited for.
