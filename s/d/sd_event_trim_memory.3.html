SD_EVENT_ADD_MEMORY_PRESSURE(3) sd_event_add_memory_pressure SD_EVENT_ADD_MEMORY_PRESSURE(3)

NOMBRE

sd_event_add_memory_pressure, sd_event_source_set_memory_pressure_type, sd_event_source_set_memory_pressure_period, sd_event_trim_memory - Añadir y configurar una fuente de eventos que se ejecuta como resultado de la presión de memoria

SINOPSIS

#include <systemd/sd-event.h>
typedef struct sd_event_source sd_event_source;

int sd_event_add_memory_pressure(sd_event *event, sd_event_source **ret_source, sd_event_handler_t handler, void *userdata);

int sd_event_source_set_memory_pressure_type(sd_event_source *source, const char *type);

int sd_event_source_set_memory_pressure_period(sd_event_source *source, uint64_t threshold_usec, uint64_t window_usec);

int sd_event_trim_memory(void);

DESCRIPCIÓN

sd_event_add_memory_pressure() añade una nueva fuente de eventos que se dispara cuando se detecta presión de memoria. Esta funcionalidad está construida en torno a la lógica de Información de Parada de Presión (PSI)[1] del kernel de Linux.

Espera un objeto de bucle de eventos como primer parámetro, y devuelve el objeto de fuente de eventos asignado en el segundo parámetro, si tiene éxito. El parámetro handler es una función a llamar cuando se detecta presión de memoria, o NULL. La función manejadora recibirá el puntero userdata, que puede ser elegido libremente por el llamante. El manejador puede devolver un valor negativo para señalar un error (ver más abajo), otros valores de retorno son ignorados. Si handler es NULL, se utilizará un manejador predeterminado que compacta las cachés de asignación mantenidas por libsystemd así como por glibc (a través de malloc_trim(3)).

Para destruir un objeto de fuente de eventos, utilice sd_event_source_unref(3), pero tenga en cuenta que la fuente de eventos solo se elimina del bucle de eventos cuando se sueltan todas las referencias a la fuente de eventos. Para asegurarse de que una fuente de eventos no se dispare más, incluso si todavía se referencia, deshabilite la fuente de eventos usando sd_event_source_set_enabled(3) con SD_EVENT_OFF.

Si el segundo parámetro de sd_event_add_memory_pressure() es NULL, no se devuelve ninguna referencia al objeto de fuente de eventos. En este caso, la fuente de eventos se considera "flotante" y se destruirá implícitamente cuando el propio bucle de eventos sea destruido.

La fuente de eventos se disparará según la siguiente lógica:

1. Si las variables de entorno $MEMORY_PRESSURE_WATCH/$MEMORY_PRESSURE_WRITE están establecidas en el momento en que se establece la fuente de eventos, vigilará el archivo, FIFO o socket AF_UNIX especificado a través de $MEMORY_PRESSURE_WATCH (que debe contener un nombre de ruta absoluta) para eventos POLLPRI (en caso de ser un archivo regular) o POLLIN (de lo contrario). Después de abrir el inodo, escribirá los datos (decodificados) de Base64 proporcionados a través de $MEMORY_PRESSURE_WRITE en él antes de empezar a consultarlo (la variable puede no estar establecida, en cuyo caso esto se omite). Típicamente, si se utiliza, $MEMORY_PRESSURE_WATCH contendrá una ruta como /proc/pressure/memory o una ruta a un archivo específico de memory.pressure en el sistema de archivos de control de grupo (cgroupfs).
2. Si estas variables de entorno no están establecidas, se utiliza el archivo de interfaz PSI local memory.pressure del grupo de control en el que se está ejecutando el proceso invocador.
3. Si ese archivo no existe, se vigila en su lugar el archivo de interfaz PSI a nivel de sistema /proc/pressure/memory.

O en otras palabras: preferiblemente se utiliza cualquier configuración explícita pasada por un gestor de servicios (o similar) como fuente de notificación, antes de recurrir a notificaciones locales del servicio, y finalmente a notificaciones globales del sistema.

Se recomienda que los servicios y aplicaciones que se comportan correctamente reaccionen a los eventos de presión de memoria ejecutando una o más de las siguientes operaciones, para garantizar un comportamiento óptimo incluso en sistemas cargados y con recursos limitados:

• Liberar cachés de asignación como malloc_trim() o similares, tanto implementadas en las bibliotecas consumidas por el programa como en cachés de asignación privadas del propio programa.
• Liberar cualquier otra forma de cachés en memoria que puedan recuperarse fácilmente si es necesario (por ejemplo, cachés de navegador).
• Terminar hilos o procesos de trabajo inactivos, o similares.
• Incluso salir completamente del programa si está inactivo y puede iniciarse automáticamente cuando sea necesario (por ejemplo, mediante activación por socket o bus).

Cualquiera de las operaciones sugeridas debería ayudar a aliviar las situaciones de presión de memoria y permitir que el sistema progrese reclamando la memoria para otros fines.

Esta fuente de eventos típicamente se dispara en paradas de presión de memoria, es decir, cuando ya se ha observado latencia operativa por encima de un umbral configurado. Esto debe tenerse en cuenta al discutir si la latencia posterior para readquirir cualquier recurso liberado es aceptable: generalmente es más importante pensar en las latencias que ya han ocurrido que en las que surgirán en el futuro.

Las funciones sd_event_source_set_memory_pressure_type() y sd_event_source_set_memory_pressure_period() se pueden utilizar para ajustar los parámetros de PSI para las notificaciones de presión. La primera acepta "some" o "full" como segundo parámetro, la segunda toma umbrales y periodos de tiempo en microsegundos como parámetros. Para más detalles sobre estos tres parámetros, consulte la documentación de PSI. Tenga en cuenta que estas dos llamadas deben invocarse inmediatamente después de asignar la fuente de eventos, ya que deben configurarse antes de que comience la consulta. También tenga en cuenta que estas llamadas fallarán si los parámetros de presión de memoria se pasaron a través de las variables de entorno $MEMORY_PRESSURE_WATCH/$MEMORY_PRESSURE_WRITE (o en otras palabras: la configuración proporcionada por un gestor de servicios tiene prioridad sobre la configuración interna).

La función sd_event_trim_memory() libera varias cachés de asignación internas mantenidas por libsystemd e invoca malloc_trim(3) de glibc. Esto hace que la operación ejecutada cuando el parámetro de la función manejadora de sd_event_add_memory_pressure se pasa como NULL sea directamente accesible para su invocación en cualquier momento (ver arriba). Esta función registrará un mensaje de registro estructurado a nivel LOG_DEBUG (con el ID de mensaje f9b0be465ad540d0850ad32172d57c21) sobre la operación de presión de memoria.

Para más detalles, consulte Memory Pressure Handling in systemd[2].

VALOR DE RETORNO

En caso de éxito, estas funciones devuelven 0 o un entero positivo. En caso de error, devuelven un código de error negativo estilo errno.

Errores

Los errores devueltos pueden indicar los siguientes problemas:

-ENOMEM

No hay suficiente memoria para asignar un objeto.

Añadido en la versión 254.

-EINVAL

Se ha pasado un argumento inválido.

Añadido en la versión 254.

-EHOSTDOWN

La variable $MEMORY_PRESSURE_WATCH se ha establecido en la cadena literal /dev/null, para deshabilitar explícitamente el manejo de la presión de memoria.

Añadido en la versión 254.

-EBADMSG

La variable $MEMORY_PRESSURE_WATCH se ha establecido en una cadena inválida, por ejemplo, una ruta relativa en lugar de una absoluta.

Añadido en la versión 254.

-ENOTTY

La variable $MEMORY_PRESSURE_WATCH apunta a un archivo regular fuera de los sistemas de archivos procfs o cgroupfs.

Añadido en la versión 254.

-EOPNOTSUPP

No se ha especificado ninguna configuración a través de $MEMORY_PRESSURE_WATCH y el kernel local no soporta la interfaz PSI.

Añadido en la versión 254.

-EBUSY

Esto lo devuelven sd_event_source_set_memory_pressure_type() y sd_event_source_set_memory_pressure_period() si se invocan en fuentes de eventos en un momento posterior al de su asignación inmediata.

Añadido en la versión 254.

-ESTALE

El bucle de eventos ya ha terminado.

Añadido en la versión 254.

NOMBRE

sd_event_add_memory_pressure, sd_event_source_set_memory_pressure_type, sd_event_source_set_memory_pressure_period, sd_event_trim_memory - Añadir un evento de presión de memoria al bucle de eventos

SINOPSIS

#include <systemd/sd-event.h> 

int sd_event_add_memory_pressure(sd_event *event, sd_event_source **source);
int sd_event_source_set_memory_pressure_type(sd_event_source *source,
                                             uint64_t type);
int sd_event_source_set_memory_pressure_period(sd_event_source *source,
                                                uint64_t usec);
int sd_event_trim_memory(sd_event *event, uint64_t size);

DESCRIPCIÓN

El bucle de eventos sd_event tiene soporte integrado para notificar sobre condiciones de alta presión de memoria en el sistema. La presión de memoria se mide a través de las características de información de presión de bloqueo (PSI) del kernel de Linux. Para obtener más detalles sobre PSI, consulte la Nota 1.

sd_event_add_memory_pressure() puede usarse para registrar un nuevo evento de fuente de presión de memoria en el bucle de eventos event. Este evento se activará cuando el sistema tenga problemas de presión de memoria, o cuando la presión de memoria se alivie.

El tipo de evento de presión de memoria que se activará se puede configurar usando sd_event_source_set_memory_pressure_type(). Por defecto, se activará en cualquier evento de presión de memoria. type es una máscara de bits de los tipos de eventos de memoria que se informarán. Los tipos de eventos de memoria definidos son:

SD_EVENT_MEMORY_PRESSURE_HIGH
Se activa cuando el sistema está bajo alta presión de memoria (por ejemplo, la reclamación de páginas es alta).
SD_EVENT_MEMORY_PRESSURE_CRITICAL
Se activa cuando el sistema está bajo presión de memoria crítica (por ejemplo, el OOM killer está a punto de activarse).
SD_EVENT_MEMORY_PRESSURE_NEARCRITICAL
Se activa cuando el sistema está bajo una presión de memoria cercana a la crítica.
SD_EVENT_MEMORY_PRESSURE_FREE
Se activa cuando la presión de memoria se ha aliviado.
SD_EVENT_MEMORY_PRESSURE_ANY
Una máscara de bits que incluye todos los tipos anteriores.

El período de sondeo para la presión de memoria se puede configurar con sd_event_source_set_memory_pressure_period(). El valor predeterminado es el especificado por el parámetro psi=! en el archivo de configuración de systemd (normalmente 10 segundos). usec es el período deseado en microsegundos.

Se puede usar sd_event_trim_memory() para solicitar una reducción de la memoria utilizada por los procesos del sistema. size especifica la cantidad de memoria (en bytes) que se desea liberar. Tenga en cuenta que esto es solo una solicitud; el sistema puede no ser capaz de liberar la cantidad solicitada de memoria. El sistema intentionará liberar la memoria trimando las cachés de páginas y los buffers del kernel.

El manejo de la presión de memoria en systemd se describe en detalle en la Nota 2.

VALOR DE RETORNO

En caso de éxito, sd_event_add_memory_pressure() devuelve 0 o un entero positivo. En caso de éxito, sd_event_source_set_memory_pressure_type(), sd_event_source_set_memory_pressure_period() y sd_event_trim_memory() devuelven 0. En caso de error, devuelven un código de error negativo.

Los códigos de retorno posibles son:

ECHILD
El bucle de eventos se ha creado en un proceso, biblioteca o instancia de módulo diferente.
EDOM
La fuente de evento proporcionada no es una fuente de evento de señal.

Añadido en la versión 254.

NOTAS

Las funciones descritas aquí están disponibles como una biblioteca compartida, que se puede compilar y enlazar con el archivo pkg-config(1) de libsystemd.

El código descrito aquí utiliza getenv, que se declara como no seguro para hilos. Esto significa que el código que llama a las funciones descritas aquí no debe llamar a setenv desde un hilo paralelo. Se recomienda realizar solo llamadas a setenv() desde una fase temprana del programa cuando aún no se han iniciado otros hilos.
