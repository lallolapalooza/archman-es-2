NOMBRE

sd_notify, sd_notifyf, sd_pid_notify, sd_pid_notifyf, sd_pid_notify_with_fds, sd_pid_notifyf_with_fds, sd_notify_barrier, sd_pid_notify_barrier - Notificar al gestor de servicios sobre la finalización del inicio y otros cambios de estado del servicio

SINOPSIS

#include <systemd/sd-daemon.h>

int sd_notify(int unset_environment, const char *state);

int sd_notifyf(int unset_environment, const char *format, ...);

int sd_pid_notify(pid_t pid, int unset_environment, const char *state);

int sd_pid_notifyf(pid_t pid, int unset_environment, const char *format, ...);

int sd_pid_notify_with_fds(pid_t pid, int unset_environment, const char *state, const int *fds, unsigned n_fds);

int sd_pid_notifyf_with_fds(pid_t pid, int unset_environment, const int *fds, size_t n_fds, const char *format, ...);

int sd_notify_barrier(int unset_environment, uint64_t timeout);

int sd_pid_notify_barrier(pid_t pid, int unset_environment, uint64_t timeout);

DESCRIPCIÓN

sd_notify() puede ser llamada por un servicio para notificar al gestor de servicios sobre cambios de estado. Se puede utilizar para enviar información arbitraria, codificada en una cadena similar a un bloque de entorno. Lo más importante es que se puede utilizar para notificaciones de finalización de inicio o recarga.

Si el parámetro unset_environment es distinto de cero, sd_notify() eliminará la variable de entorno $NOTIFY_SOCKET antes de retornar (independientemente de si la llamada a la función tuvo éxito o no). Las llamadas posteriores a sd_notify() entonces no harán nada silenciosamente, y la variable ya no será heredada por los procesos hijos.

El parámetro state debe contener una lista de asignaciones de variables separadas por saltos de línea, similar en estilo a un bloque de entorno. Se implica un salto de línea final si no se especifica ninguno. La cadena puede contener cualquier tipo de asignación de variables, pero consulte la siguiente sección para ver una lista de asignaciones entendidas por el gestor de servicios.

Tenga en cuenta que systemd aceptará datos de estado enviados por un servicio solo si la opción NotifyAccess= está correctamente configurada en el archivo de definición del servicio. Consulte systemd.service(5) para más detalles.

Tenga en cuenta que las notificaciones de sd_notify() solo pueden atribuirse correctamente a unidades si el proceso emisor todavía está activo cuando PID 1 procesa el mensaje, o si el proceso emisor está explícitamente rastreado en tiempo de ejecución por el gestor de servicios. Esto último ocurre si el gestor de servicios originó el proceso, es decir, en todos los procesos que coinciden con NotifyAccess=main o NotifyAccess=exec. Por el contrario, si un proceso auxiliar de la unidad envía un mensaje sd_notify() y sale inmediatamente, es posible que el gestor de servicios no pueda atribuir correctamente el mensaje a la unidad y, por lo tanto, lo ignorará, incluso si NotifyAccess=all está configurado para ella.

Por lo tanto, para eliminar todas las condiciones de carrera involucradas en la búsqueda de la unidad del cliente y la atribución correcta de las notificaciones a las unidades, se puede usar sd_notify_barrier(). Esta llamada actúa como un punto de sincronización y garantiza que todas las notificaciones enviadas antes de esta llamada hayan sido captadas por el gestor de servicios cuando retorna con éxito. El uso de sd_notify_barrier() es necesario para los clientes que no son invocados por el gestor de servicios; de lo contrario, este mecanismo de sincronización es innecesario para la atribución de notificaciones a la unidad.

sd_notifyf() es similar a sd_notify() pero toma una cadena de formato similar a printf() más argumentos.

sd_pid_notify() y sd_pid_notifyf() son similares a sd_notify() y sd_notifyf() pero toman un ID de proceso (PID) para usar como PID de origen para el mensaje como primer argumento. Esto es útil para enviar mensajes de notificación en nombre de otros procesos, siempre que se disponga de los privilegios apropiados. Efectivamente, esto significa que una invocación privilegiada de sd_pid_notify() puede eludir las restricciones NotifyAccess=main o NotifyAccess=exec aplicadas a un servicio. Si el argumento PID se especifica como 0, se utiliza el ID de proceso del proceso que llama, en cuyo caso las llamadas son completamente equivalentes a sd_notify() y sd_notifyf().

sd_pid_notify_with_fds() es similar a sd_pid_notify() pero toma una matriz adicional de descriptores de archivo. Estos descriptores de archivo se envían junto con el mensaje de notificación al gestor de servicios. Esto es particularmente útil para enviar mensajes "FDSTORE=1", como se describe anteriormente. Los argumentos adicionales son un puntero a la matriz de descriptores de archivo más el número de descriptores de archivo en la matriz. Si se pasa el número de descriptores de archivo como 0, la llamada es completamente equivalente a sd_pid_notify(), es decir, no se pasan descriptores de archivo. Tenga en cuenta que los descriptores de archivo enviados al gestor de servicios en un mensaje sin "FDSTORE=1" se cierran inmediatamente al recibirlos.

sd_pid_notifyf_with_fds() es una combinación de sd_pid_notify_with_fds() y sd_notifyf(), es decir, acepta tanto un PID como un conjunto de descriptores de archivo como entrada, y procesa una cadena de formato para generar la cadena de estado.

sd_notify_barrier() permite al llamador sincronizarse contra la recepción de mensajes de notificación enviados previamente y utiliza el comando BARRIER=1. Toma un valor de timeout relativo en microsegundos que se pasa a ppoll(2). Un valor de UINT64_MAX se interpreta como un tiempo de espera infinito.

sd_pid_notify_barrier() es igual que sd_notify_barrier(), pero permite especificar el PID de origen para el mensaje de notificación.

ASIGNACIONES BIEN CONOCIDAS

Las siguientes asignaciones tienen un significado definido:

READY=1

Indica al gestor de servicios que la inicialización del servicio ha finalizado, o que el servicio ha finalizado de recargar su configuración. Esto solo es utilizado por systemd si el archivo de definición del servicio tiene configurado Type=notify o Type=notify-reload. Dado que hay poco valor en señalar la no preparación, el único valor que los servicios deben enviar es "READY=1" (es decir, "READY=0" no está definido).

RELOADING=1

Indica al gestor de servicios que el servicio está comenzando a recargar su configuración. Esto es útil para permitir que el gestor de servicios rastree el estado interno del servicio y lo presente al usuario. Tenga en cuenta que un servicio que envía esta notificación también debe enviar una notificación "READY=1" cuando haya completado la recarga de su configuración. Las recargas de las que el gestor de servicios es notificado con este mecanismo se propagan de la misma manera que cuando se iniciaron originalmente a través del gestor de servicios. Este mensaje es particularmente relevante para los servicios Type=notify-reload, para informar al gestor de servicios que la solicitud de recarga del servicio ha sido recibida y se está procesando.

Añadido en la versión 217.

STOPPING=1

Indica al gestor de servicios que el servicio está comenzando su apagado. Esto es útil para permitir que el gestor de servicios rastree el estado interno del servicio y lo presente al usuario.

Añadido en la versión 217.

MONOTONIC_USEC=...

Un campo que transporta la marca de tiempo monotónica (según CLOCK_MONOTONIC) formateada en decimal en μs, cuando el cliente generó el mensaje de notificación. Esto se utiliza típicamente en combinación con "RELOADING=1", para permitir que el gestor de servicios sincronice correctamente los ciclos de recarga. Consulte systemd.service(5) para más detalles, específicamente "Type=notify-reload".

Añadido en la versión 253.

STATUS=...

Pasa una cadena de estado UTF-8 de una sola línea de vuelta al gestor de servicios que describe el estado del servicio. Esto es de formato libre y puede usarse para varios propósitos: los programas similares a fsck podrían pasar porcentajes de finalización y los programas que fallan podrían pasar un error legible por humanos.

Este sitio no está asociado de ninguna forma con Arch Linux ni afiliado a este proyecto. El contenido es únicamente una traducción de las páginas del manual de Arch publicadas en man.archlinux.org.

MESSAGE

Example: "STATUS=Completed 66% of file system check..."

Añadido en la versión 233.

NOTIFYACCESS=...

Restablece el acceso al socket de notificación de estado del servicio en tiempo de ejecución, anulando el ajuste NotifyAccess= en el archivo de unidad del servicio. Consulte systemd.service(5) para obtener más detalles, específicamente "NotifyAccess=" para una lista de valores aceptados.

Añadido en la versión 254.

ERRNO=...

Si un servicio falla, el código de error de estilo errno, formateado como cadena. Ejemplo: "ERRNO=2" para ENOENT.

Añadido en la versión 233.

BUSERROR=...

Si un servicio falla, el código de error de estilo D-Bus. Ejemplo: "BUSERROR=org.freedesktop.DBus.Error.TimedOut".

Añadido en la versión 233.

VARLINKERROR=...

Si un servicio falla, el código de error de estilo Varlink. Ejemplo: "VARLINKERROR=org.varlink.service.InvalidParameter".

Añadido en la versión 257.

EXIT_STATUS=...

El estado de salida de un servicio o del propio gestor. Tenga en cuenta que systemd actualmente no consume este valor cuando lo envían los servicios, por lo que esta asignación es solo informativa. El gestor enviará esta notificación a su socket de notificación, que puede utilizarse para recopilar un estado de salida del sistema (un contenedor o una VM) a medida que se apaga. Por ejemplo, mkosi(1) utiliza esto. El valor a devolver puede establecerse a través del verbo exit de systemctl(1).

Añadido en la versión 254.

MAINPID=...

Cambia el ID del proceso principal (PID) del servicio. Esto es especialmente útil en el caso de que el proceso principal real no sea generado directamente por el gestor de servicios. Ejemplo: "MAINPID=4711".

Añadido en la versión 233.

MAINPIDFDID=...

El número de inodo del pidfd del nuevo proceso principal (especificado a través de MAINPID=). Esta información se puede obtener a través de sd_pidfd_get_inode_id(3) en el pidfd y se utiliza para identificar el proceso de forma libre de condiciones de carrera. Alternativamente, se puede enviar un pidfd directamente al gestor de servicios (ver MAINPIDFD=1 a continuación).

Añadido en la versión 257.

MAINPIDFD=1

Similar a MAINPID= con MAINPIDFDID=, pero el proceso se referencia directamente por el pidfd pasado al gestor de servicios. Esto es útil si el ID del pidfd no es compatible con el sistema. Se espera exactamente un fd para esta notificación.

Añadido en la versión 257.

WATCHDOG=1

Indica al gestor de servicios que actualice la marca de tiempo del watchdog. Este es el ping de mantenimiento que los servicios deben enviar a intervalos regulares si WatchdogSec= está habilitado para ellos. Consulte systemd.service(5) para obtener información sobre cómo habilitar esta funcionalidad y sd_watchdog_enabled(3) para obtener detalles sobre cómo el servicio puede comprobar si el watchdog está habilitado.

WATCHDOG=trigger

Indica al gestor de servicios que el servicio ha detectado un error interno que debe ser manejado por las opciones de watchdog configuradas. Esto desencadenará el mismo comportamiento que si WatchdogSec= estuviera habilitado y el servicio no hubiera enviado "WATCHDOG=1" a tiempo. Tenga en cuenta que WatchdogSec= no necesita estar habilitado para que "WATCHDOG=trigger" active la acción del watchdog. Consulte systemd.service(5) para obtener información sobre el comportamiento del watchdog.

Añadido en la versión 243.

WATCHDOG_USEC=...

Restablece el valor watchdog_usec en tiempo de ejecución. Tenga en cuenta que esto no está disponible cuando se utiliza sd_event_set_watchdog() o sd_watchdog_enabled(). Ejemplo: "WATCHDOG_USEC=20000000"

Añadido en la versión 233.

EXTEND_TIMEOUT_USEC=...

Indica al gestor de servicios que extienda el tiempo de espera de inicio, ejecución o apagado del servicio correspondiente al estado actual. El valor especificado es un tiempo en microsegundos durante el cual el servicio debe enviar un nuevo mensaje. Se producirá un tiempo de espera del servicio si no se recibe el mensaje, pero solo si el tiempo de ejecución del estado actual supera los tiempos máximos originales de TimeoutStartSec=, RuntimeMaxSec= y TimeoutStopSec=. Consulte systemd.service(5) para ver los efectos en los tiempos de espera del servicio.

Añadido en la versión 236.

RESTART_RESET=1

Restablece el contador de reinicios del servicio, lo que tiene el efecto de restaurar la duración del reinicio a RestartSec= si se utilizan RestartSteps= y RestartMaxDelaySec=. Para más información, consulte systemd.service(5).

Añadido en la versión 258.

FDSTORE=1

Almacena descriptores de archivo en el gestor de servicios. Los descriptores de archivo enviados de esta manera serán retenidos para el servicio por el gestor de servicios y se devolverán más tarde utilizando la lógica habitual de paso de descriptores de archivo en el próximo inicio o reinicio del servicio, consulte sd_listen_fds(3). Cualquier socket abierto y otros descriptores de archivo que no deban cerrarse durante un reinicio pueden almacenarse de esta manera. Cuando se detiene un servicio, su almacén de descriptores de archivo se descarta y todos los descriptores de archivo en él se cierran, excepto cuando se anula con FileDescriptorStorePreserve=, consulte systemd.service(5).

El gestor de servicios aceptará mensajes para un servicio solo si su ajuste FileDescriptorStoreMax= es distinto de cero (por defecto es cero, consulte systemd.service(5)). El gestor de servicios establecerá la variable de entorno $FDSTORE para los servicios que tengan habilitado el almacén de descriptores de archivo, consulte systemd.exec(5).

Si no se establece FDPOLL=0 y los descriptores de archivo son encuestables (consulte epoll_ctl(2)), cualquier evento EPOLLHUP o EPOLLERR que se vea en ellos resultará en su eliminación automática del almacén.

Se pueden enviar varios conjuntos de descriptores de archivo en mensajes separados, en cuyo caso los conjuntos se combinan. El gestor de servicios elimina los descriptores de archivo duplicados (aquellos que apuntan al mismo objeto) antes de pasarlos al servicio.

Esta funcionalidad debe utilizarse para implementar servicios que puedan reiniciarse después de una solicitud explícita o un fallo sin perder estado. El estado de la aplicación puede serializarse en un archivo en /run/, o mejor aún, almacenarse en un descriptor de archivo de memoria memfd_create(2). Utilice sd_pid_notify_with_fds() para enviar mensajes con "FDSTORE=1". Se recomienda combinar FDSTORE= con FDNAME= para facilitar la gestión de los descriptores de archivo almacenados.

Para más información sobre el almacén de descriptores de archivo, consulte la descripción general del Almacén de descriptores de archivo[1].

Añadido en la versión 219.

FDSTOREREMOVE=1

Elimina descriptores de archivo del almacén de descriptores de archivo. Este campo debe combinarse con FDNAME= para especificar el nombre de los descriptores de archivo a eliminar.

Añadido en la versión 236.

FDNAME=...

Cuando se utiliza en combinación con FDSTORE=1, especifica un nombre para los descriptores de archivo enviados. Cuando se utiliza con FDSTOREREMOVE=1, especifica el nombre de los descriptores de archivo a eliminar. Este nombre se pasa al servicio durante la activación y se puede consultar utilizando sd_listen_fds_with_names(3). Los descriptores de archivo enviados sin este campo se llamarán "almacenados".

El nombre puede constar de caracteres ASCII arbitrarios excepto caracteres de control o ":". No puede tener más de 255 caracteres. Si un nombre enviado no sigue estas restricciones, se ignora.

Tenga en cuenta que si se envían varios descriptores de archivo en un solo mensaje, el nombre especificado se utilizará para todos ellos. Para asignar nombres diferentes a los descriptores de archivo enviados, envíelos en mensajes separados.

Añadido en la versión 233.

FDPOLL=0

Cuando se utiliza en combinación con FDSTORE=1, deshabilita el sondeo de los descriptores de archivo enviados, independientemente de si son encuestables o no. Como esta opción deshabilita la limpieza automática de los descriptores de archivo enviados en EPOLLERR y EPOLLHUP, se debe tener cuidado para garantizar una limpieza manual adecuada. El uso de esta opción no se recomienda en general, excepto cuando la limpieza automática tiene un comportamiento no deseado, como descartar prematuramente descriptores de archivo del almacén.

Añadido en la versión 246.

BARRIER=1

Indica al gestor de servicios que el cliente está solicitando explícitamente la sincronización mediante el cierre del descriptor de archivo enviado con este comando. El gestor de servicios garantiza que el procesamiento de un comando BARRIER=1 solo ocurrirá después de que se hayan procesado todos los mensajes de notificación anteriores enviados antes de este comando. Por lo tanto, este comando, acompañado de un solo descriptor de archivo, puede utilizarse para sincronizar la recepción de todos los mensajes de estado anteriores. Tenga en cuenta que este comando no se puede mezclar con otras notificaciones y debe enviarse en un mensaje separado al gestor de servicios, de lo contrario, todas las asignaciones se ignorarán. Tenga en cuenta que enviar 0 o más de 1 descriptor de archivo con este comando es una violación del protocolo.

Añadido en la versión 246.

Los mensajes de notificación enviados por los servicios son interpretados por el gestor de servicios. Las asignaciones desconocidas se ignoran. Por lo tanto, es seguro (pero a menudo sin efecto) enviar asignaciones que no están en esta lista. El protocolo es extensible, pero se debe tener cuidado para garantizar que las extensiones privadas sean reconocibles como tales. Específicamente, se recomienda prefijarlas con "X_" seguido de algún identificador de espacio de nombres. El gestor de servicios también envía algunos mensajes a su socket de notificación, que luego pueden ser consumidos por un gestor de supervisión de máquina o contenedor en la pila superior. El gestor de servicios envía varios campos de extensión, por ejemplo, X_SYSTEMD_UNIT_ACTIVE=, para más detalles consulte systemd(1).

VALOR DE RETORNO

En caso de fallo, estas llamadas devuelven un código de error negativo de estilo errno. Si $NOTIFY_SOCKET no estaba configurado y, por lo tanto, no se pudo enviar ningún mensaje de estado, se devuelve 0. Si el estado se envió, estas funciones devuelven un valor positivo. Para admitir tanto los gestores de servicios que implementan este esquema como los que no, generalmente se recomienda ignorar el valor de retorno de esta llamada. Tenga en cuenta que el valor de retorno simplemente indica si el mensaje de notificación se encoló correctamente, no refleja si el mensaje...

ENTORNO

$NOTIFY_SOCKET

Establecido por el gestor de servicios para procesos supervisados para la notificación de estado y finalización de inicio. Esta variable de entorno especifica el socket con el que habla sd_notify(). Ver arriba para más detalles.

EJEMPLOS

Ejemplo 1. Notificación de Inicio

Cuando un servicio termina de iniciarse, podría emitir la siguiente llamada para notificar al gestor de servicios:

sd_notify(0, "READY=1");

Ejemplo 2. Notificación de Inicio Extendida

Un servicio podría enviar lo siguiente después de completar la inicialización:

sd_notifyf(0, "READY=1\n"
              "STATUS=Procesando solicitudes...\n"
              "MAINPID=%lu",
           (unsigned long) getpid());

Ejemplo 3. Notificación de Causa de Error

Un servicio podría enviar lo siguiente poco antes de salir, en caso de fallo:

sd_notifyf(0, "STATUS=Error al iniciar: %s\n"
              "ERRNO=%i",
           strerror_r(errnum, (char[1024]){}, 1024),
           errnum);

Ejemplo 4. Almacenar un Descriptor de Archivo en el Gestor de Servicios

Para almacenar un descriptor de archivo abierto en el gestor de servicios, para continuar la operación después de un reinicio del servicio sin perder estado, use "FDSTORE=1":

sd_pid_notify_with_fds(0, 0, "FDSTORE=1\nFDNAME=foobar", &fd, 1);

Ejemplo 5. Eliminación de condiciones de carrera

Cuando el cliente que envía las notificaciones no es generado por el gestor de servicios, puede salir demasiado rápido y el gestor de servicios puede no atribuirlas correctamente a la unidad. Para evitar tales carreras, use sd_notify_barrier() para sincronizar contra la recepción de todas las notificaciones enviadas antes de que se realice esta llamada.

sd_notify(0, "READY=1");
/* establecer tiempo de espera a 5 segundos */
sd_notify_barrier(0, 5 * 1000000);
