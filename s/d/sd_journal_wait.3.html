NOMBRE

sd_journal_get_fd, sd_journal_get_events, sd_journal_get_timeout, sd_journal_process, sd_journal_wait, sd_journal_reliable_fd, SD_JOURNAL_NOP, SD_JOURNAL_APPEND, SD_JOURNAL_INVALIDATE - Interfaz de notificación de cambios del journal

SINOPSIS

#include <systemd/sd-journal.h>

int sd_journal_get_fd(sd_journal *j);

int sd_journal_get_events(sd_journal *j);

int sd_journal_get_timeout(sd_journal *j, uint64_t *timeout_usec);

int sd_journal_process(sd_journal *j);

int sd_journal_wait(sd_journal *j, uint64_t timeout_usec);

int sd_journal_reliable_fd(sd_journal *j);

DESCRIPCIÓN

sd_journal_get_fd() devuelve un descriptor de archivo que puede ser consultado asincrónicamente en un bucle de eventos externo y se señala tan pronto como el journal cambia, porque se añadieron nuevas entradas o archivos, tuvo lugar una rotación, o se eliminaron archivos, y similares. El descriptor de archivo es adecuado para su uso en poll(2). Utilice sd_journal_get_events() para obtener una máscara de eventos a vigilar. La llamada toma un argumento: el objeto de contexto del journal. Tenga en cuenta que no todos los sistemas de archivos son capaces de generar los eventos necesarios para que las activaciones desde este descriptor de archivo se noten inmediatamente. En particular, los sistemas de archivos de red no generan eventos de cambio de archivo adecuados en todos los casos. Casos como estos se pueden detectar con sd_journal_reliable_fd(), más abajo. sd_journal_get_timeout() se asegurará en estos casos de que las activaciones ocurran con la suficiente frecuencia para que los cambios se noten, aunque con cierta latencia.

sd_journal_get_events() devolverá la máscara de poll() a esperar. Esta función devolverá una combinación de POLLIN y POLLOUT y similares para rellenar en el campo ".events" de struct pollfd.

sd_journal_get_timeout() devolverá un valor de tiempo de espera para usarlo en poll(). Esto devuelve un valor en microsegundos desde la época de CLOCK_MONOTONIC para agotar el tiempo de espera de poll() en timeout_usec. Consulte clock_gettime(2) para obtener detalles sobre CLOCK_MONOTONIC. Si no hay tiempo de espera, rellenará con (uint64_t) -1 en su lugar. Tenga en cuenta que poll() toma un tiempo de espera relativo en milisegundos en lugar de un tiempo de espera absoluto en microsegundos. Para convertir el 'us' absoluto de tiempo de espera en 'ms' relativo, use código como el siguiente:

uint64_t t;
int msec;
sd_journal_get_timeout(m, &t);
if (t == (uint64_t) -1)
  msec = -1;
else {
  struct timespec ts;
  uint64_t n;
  clock_gettime(CLOCK_MONOTONIC, &ts);
  n = (uint64_t) ts.tv_sec * 1000000 + ts.tv_nsec / 1000;
  msec = t > n ? (int) ((t - n + 999) / 1000) : 0;
}

El código anterior no realiza ninguna comprobación de errores por brevedad. El entero msec calculado se puede pasar directamente como parámetro de tiempo de espera de poll().

Después de cada activación de poll(), se debe llamar a sd_journal_process() para procesar los eventos. Esta llamada también indicará qué tipo de cambio se ha detectado (ver más abajo; tenga en cuenta que son posibles activaciones espurias).

Una alternativa síncrona para usar sd_journal_get_fd(), sd_journal_get_events(), sd_journal_get_timeout() y sd_journal_process() es sd_journal_wait(). Esperará síncronamente hasta que el journal cambie. El tiempo máximo que esta llamada duerme puede ser controlado con el parámetro timeout_usec. Pase (uint64_t) -1 para esperar indefinidamente. Internamente, esta llamada simplemente combina sd_journal_get_fd(), sd_journal_get_events(), sd_journal_get_timeout(), poll() y sd_journal_process() en una sola.

sd_journal_reliable_fd() se puede utilizar para comprobar si los eventos de activación del descriptor de archivo devuelto por sd_journal_get_fd() se sabe que se activan rápidamente. En ciertos sistemas de archivos donde los eventos de cambio de archivo del sistema operativo no están disponibles (como NFS) los cambios deben ser consultados repetidamente, y por lo tanto se detectan solo con una latencia considerable. Esta llamada devolverá un valor positivo si los cambios del journal se detectan rápidamente y cero cuando necesitan ser consultados. Tenga en cuenta que generalmente no es necesario invocar esta función directamente ya que sd_journal_get_timeout() solicitará tiempos de espera apropiados igualmente.

Tenga en cuenta que todas las interfaces de notificación de cambios mencionadas anteriormente no informan los cambios instantáneamente. Se introducen latencias por múltiples razones: como se mencionó, ciertos backends de almacenamiento requieren sondeo basado en tiempo, en otros casos las activaciones se optimizan agrupando eventos, y el sistema operativo introduce latencias adicionales de programación de IO/CPU.

VALOR DE RETORNO

sd_journal_get_fd() devuelve un descriptor de archivo válido en caso de éxito o un código de error negativo estilo errno(2).

sd_journal_get_events() devuelve una combinación de POLLIN, POLLOUT y similares en caso de éxito o un código de error negativo estilo errno(2).

sd_journal_reliable_fd() devuelve un entero positivo si el descriptor de archivo devuelto por sd_journal_get_fd() generará activaciones inmediatas para todos los cambios del journal. Devuelve 0 si podría haber una latencia involucrada.

sd_journal_process() y sd_journal_wait() devuelven un código de error negativo estilo errno(2), o uno de SD_JOURNAL_NOP, SD_JOURNAL_APPEND o SD_JOURNAL_INVALIDATE en caso de éxito:

•Si se devuelve SD_JOURNAL_NOP, el journal no cambió desde la última invocación.
•Si se devuelve SD_JOURNAL_APPEND, se han añadido nuevas entradas al final del journal. En este caso, es suficiente simplemente continuar leyendo en la ubicación final anterior del journal, para leer las entradas recién añadidas.
•Si se devuelve SD_JOURNAL_INVALIDATE, se añadieron o eliminaron archivos del journal del conjunto de archivos del journal vigilados (por ejemplo, debido a rotación o limpieza), y por lo tanto las entradas podrían haber aparecido o desaparecido en lugares arbitrarios en el flujo de registro, posiblemente antes o después del final anterior del flujo de registro. Si se devuelve SD_JOURNAL_INVALIDATE, las UI de vista en vivo que deseen reflejar en pantalla el estado preciso de los datos de registro en disco probablemente deberían actualizar toda su pantalla (en relación con el cursor de la entrada de registro en la parte superior de la pantalla). Los programas interesados solo en un flujo de datos de registro estrictamente secuencial pueden tratar SD_JOURNAL_INVALIDATE de la misma manera que SD_JOURNAL_APPEND, ignorando así cualquier cambio en la vista del registro anterior al final antiguo del flujo de registro.

SEGURIDAD DE SEÑALES

En general, sd_journal_get_fd(), sd_journal_get_events() y sd_journal_get_timeout() *no* son "seguras para señales asíncronas" en el sentido de signal-safety(7). Sin embargo, solo la primera llamada a cualquiera de estas tres funciones realiza operaciones inseguras, por lo que las llamadas posteriores *son* seguras.

sd_journal_process() y sd_journal_wait() no son seguras. sd_journal_reliable_fd() es segura.

NOTAS

Todas las funciones aquí descritas son agnósticas a hilos y solo un hilo puede operar en un objeto dado en un momento dado. Diferentes hilos pueden acceder al mismo objeto en diferentes momentos. Se pueden utilizar múltiples objetos independientes desde diferentes hilos en paralelo.

Las funciones descritas aquí están disponibles como una biblioteca compartida, que puede ser compilada y enlazada con el archivo libsystemd de pkg-config(1).

sd_journal_wait(3) — systemd-libs

NAME

sd_journal_wait, sd_journal_process, sd_journal_get_fd, sd_journal_reliable_fd, sd_journal_get_events, sd_journal_get_timeout - Esperar a que el diario del sistema de systemd se actualice

SYNOPSIS

#include <systemd/sd-journal.h>
int sd_journal_wait(sd_journal *j, uint64_t timeout_usec);
int sd_journal_process(sd_journal *j);
int sd_journal_get_fd(sd_journal *j);
int sd_journal_reliable_fd(sd_journal *j);
int sd_journal_get_events(sd_journal *j);
int sd_journal_get_timeout(sd_journal *j, uint64_t *timeout_usec);

DESCRIPTION

El diario del sistema de systemd es un búfer circular de entradas de registro. Las aplicaciones pueden leer de él de forma secuencial, y también se pueden registrar para ser notificadas cuando se añaden nuevas entradas. Esta última funcionalidad se implementa a través de los mecanismos descritos en esta página de manual.

sd_journal_get_fd() devuelve un descriptor de archivo que se puede utilizar para detectar cuándo se han añadido nuevas entradas al diario. Este descriptor de archivo se activará (POLLIN) cuando haya nuevas entradas disponibles para su lectura. Es necesario llamar a sd_journal_process() para consumir las nuevas entradas antes de que el descriptor de archivo se desactive.

sd_journal_reliable_fd() es similar a sd_journal_get_fd(), pero garantiza que el descriptor de archivo devuelto no se cerrará accidentalmente cuando el diario se reinicie internamente. Si se sospecha que el diario puede reiniciarse (por ejemplo, si el sistema sale de la suspensión), se debe utilizar este descriptor de archivo en lugar de sd_journal_get_fd().

sd_journal_get_events() devuelve una máscara de bits de eventos de `poll(2)` que se deben esperar en el descriptor de archivo devuelto por sd_journal_get_fd() o sd_journal_reliable_fd(). Actualmente, esto siempre devuelve `POLLIN`.

sd_journal_get_timeout() rellena *timeout_usec con el tiempo máximo en microsegundos que se esperará por nuevas entradas del diario. Si se pasa `(uint64_t) -1`, el tiempo de espera es infinito. Si se devuelve `0`, el tiempo de espera es inmediato. Esto es útil para implementar bucles de sondeo eficientes y evitar el uso constante de CPU.

sd_journal_wait() es una función de conveniencia que combina la espera de un evento en el descriptor de archivo del diario y el procesamiento de las nuevas entradas. Espera hasta *timeout_usec microsegundos (o indefinidamente si se pasa `(uint64_t) -1`) para que el descriptor de archivo del diario se active. Si el descriptor de archivo se activa o el tiempo de espera expira, llama a sd_journal_process() para consumir las nuevas entradas y devuelve el resultado de sd_journal_process().

sd_journal_process() debe llamarse para que el descriptor de archivo del diario se desactive y para que las nuevas entradas estén disponibles para su lectura. Si esta función devuelve un valor positivo, indica que se han procesado ese número de nuevas entradas. Si devuelve 0, significa que no hay nuevas entradas disponibles, pero el descriptor de archivo sigue activo, lo que indica la posibilidad de que haya entradas pendientes después de un reinicio del diario. Si devuelve un valor negativo, se ha producido un error.

Un uso típico es:

  1. Abrir un objeto de diario con sd_journal_open().
  2. Obtener el descriptor de archivo y los eventos esperados con sd_journal_get_fd() y sd_journal_get_events().
  3. Preparar una estructura `pollfd` con el descriptor de archivo y los eventos.
  4. Llamar a `poll()` con un tiempo de espera obtenido de sd_journal_get_timeout().
  5. Si `poll()` devuelve un evento, llamar a sd_journal_process() para procesar las nuevas entradas.
  6. Leer las nuevas entradas utilizando otras funciones de la API del diario (por ejemplo, sd_journal_get_data()).
  7. Repetir desde el paso 3.

Alternativamente, se puede usar sd_journal_wait() para simplificar el bucle.

RETURN VALUE

sd_journal_get_fd() y sd_journal_reliable_fd() devuelven el descriptor de archivo del diario o un valor negativo en caso de error. El descriptor de archivo devuelto es válido hasta que se llame a sd_journal_close().

sd_journal_get_events() devuelve una máscara de bits de eventos de `poll(2)` o un valor negativo en caso de error.

sd_journal_get_timeout() devuelve 0 si tiene éxito, o un valor negativo en caso de error. El valor de tiempo de espera real se almacena en el argumento de salida *timeout_usec.

sd_journal_process() devuelve el número de entradas nuevas que se han puesto a disposición para su lectura, 0 si no hay entradas nuevas pero el descriptor de archivo sigue activo, o un valor negativo en caso de error. Los valores de retorno positivos indican que el descriptor de archivo debería ser re-evaluado, ya que podrían haber más entradas disponibles. Los errores comunes son `-ECHILD` si el diario ya no es confiable (por ejemplo, después de un reinicio), `-ENOMEM` si no se pudo asignar memoria, y `-ESTALE` si el descriptor de archivo se volvió obsoleto y debe ser reabierto.

sd_journal_wait() devuelve el resultado de la llamada subyacente a sd_journal_process() después de esperar las actualizaciones. Devuelve `-ECHILD` si el diario se reinició mientras se esperaba.

SIGNAL SAFETY

sd_journal_get_fd(), sd_journal_process(), sd_journal_get_events() y sd_journal_get_timeout() son seguros para su uso en manipuladores de señales.

sd_journal_wait() y sd_journal_reliable_fd() no son seguros para su uso en manipuladores de señales.

NOTES

Las funciones sd_journal_*() no son necesariamente seguras para el uso en hilos. Es responsabilidad del código de llamada asegurarse de que un objeto sd_journal *j no se utiliza desde varios hilos simultáneamente.

Para un rendimiento óptimo, se recomienda utilizar un bucle de sondeo con poll() y sd_journal_get_timeout() en lugar de un bucle de sondeo constante con sd_journal_process() sin espera.

Si sd_journal_process() devuelve `0`, significa que no hay entradas disponibles para leer en ese momento, pero el descriptor de archivo sigue siendo válido. Esto puede ocurrir si las entradas se han borrado del búfer circular del diario entre la última vez que se llamó a sd_journal_process() y la llamada actual.

Si sd_journal_process() o sd_journal_wait() devuelven `-ECHILD`, significa que el diario se ha reiniciado y el objeto sd_journal *j ya no es válido. En este caso, el objeto debe ser cerrado y reabierto.

sd_journal_get_fd() puede devolver un descriptor de archivo que se cierra si el proceso se desvincula del diario (por ejemplo, llamando a sd_journal_close()). Si se necesita un descriptor de archivo persistente que no se vea afectado por la desvinculación, use sd_journal_reliable_fd().

El tiempo de espera devuelto por sd_journal_get_timeout() se calcula en relación con la hora actual. Por lo tanto, si el tiempo de espera es de 1000000 microsegundos (1 segundo), y el descriptor de archivo se activa después de 500000 microsegundos, el siguiente tiempo de espera calculado será nuevamente de 1000000 microsegundos. Si el tiempo de espera expira, el tiempo de espera para la siguiente llamada será de 0 microsegundos, lo que significa que el siguiente `poll()` será no bloqueante. Esto asegura que el código pueda responder rápidamente a las nuevas entradas después de un período de inactividad.

EXAMPLES

/* SPDX-License-Identifier: MIT-0 */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <errno.h>
#include <systemd/sd-journal.h>
int main(int argc, char *argv[]) {
  sd_journal *j = NULL;
  const char *d;
  size_t l;
  int r;
  /* Open the journal for reading all entries */
  r = sd_journal_open(&j, SD_JOURNAL_LOCAL_ONLY);
  if (r < 0) {
    fprintf(stderr, "Failed to open journal: %s\n", strerror(-r));
    return 1;
  }
  /* Move to the end of the journal */
  r = sd_journal_seek_tail(j);
  if (r < 0) {
    fprintf(stderr, "Failed to seek journal to tail: %s\n", strerror(-r));
    goto finish;
  }
  /* Read all subsequent entries */
  for (;;) {
    r = sd_journal_wait(j, (uint64_t) -1); /* Wait indefinitely */
    if (r < 0) {
      fprintf(stderr, "Failed to wait for journal entry: %s\n", strerror(-r));
      break;
    }
    if (r == 0) {
      /* No new entries, continue waiting */
      continue;
    }
    /* Get the MESSAGE field from the current entry */
    r = sd_journal_get_data(j, "MESSAGE", &d, &l);
    if (r < 0) {
      fprintf(stderr, "Failed to get MESSAGE field: %s\n", strerror(-r));
      continue;
    }
    printf("%.*s\n", (int) l, d);
  }
finish:
  sd_journal_close(j);
  return 0;
}

Solicitud de sondeo de entradas nuevas:

/* SPDX-License-Identifier: MIT-0 */
#define _GNU_SOURCE 1
#include <errno.h>
#include <poll.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <systemd/sd-journal.h>
int main(void) {
  sd_journal *j = NULL;
  const char *data;
  size_t length;
  int r;
  struct pollfd pfd;
  uint64_t timeout_usec;
  /* Open journal, seek to end */
  r = sd_journal_open(&j, SD_JOURNAL_LOCAL_ONLY);
  if (r < 0) {
    fprintf(stderr, "Failed to open journal: %s\n", strerror(-r));
    return 1;
  }
  r = sd_journal_seek_tail(j);
  if (r < 0) {
    fprintf(stderr, "Failed to seek journal to tail: %s\n", strerror(-r));
    goto finish;
  }
  /* Prepare for polling */
  pfd.fd = sd_journal_get_fd(j);
  if (pfd.fd < 0) {
    fprintf(stderr, "Failed to get journal file descriptor: %s\n",
            strerror(-pfd.fd));
    goto finish;
  }
  pfd.events = sd_journal_get_events(j);
  /* Event loop */
  for (;;) {
    /* Get timeout, wait for events */
    r = sd_journal_get_timeout(j, &timeout_usec);
    if (r < 0) {
      fprintf(stderr, "Failed to get journal timeout: %s\n", strerror(-r));
      goto finish;
    }
    /* Update pollfd events before polling */
    pfd.events = sd_journal_get_events(j);
    r = poll(&pfd, 1, timeout_usec & (uint64_t) -1);
    if (r < 0) {
      fprintf(stderr, "Failed to poll journal: %s\n", strerror(-r));
      goto finish;
    }
    if (r == 0) {
      /* Timeout */
      fprintf(stderr, "Polling timeout reached.\n");
      continue;
    }
    /* Process journal entries */
    r = sd_journal_process(j);
    if (r < 0) {
      fprintf(stderr, "Failed to process journal entry: %s\n", strerror(-r));
      /* Check for -ECHILD specifically for journal restart */
      if (r == -ECHILD) {
        fprintf(stderr, "Journal has restarted, re-opening...\n");
        sd_journal_close(j);
        /* Re-open and seek to tail again */
        r = sd_journal_open(&j, SD_JOURNAL_LOCAL_ONLY);
        if (r < 0) {
          fprintf(stderr, "Failed to re-open journal: %s\n", strerror(-r));
          return 1;
        }
        r = sd_journal_seek_tail(j);
        if (r < 0) {
          fprintf(stderr, "Failed to seek journal to tail again: %s\n",
                  strerror(-r));
          goto finish;
        }
        /* Update file descriptor and events */
        pfd.fd = sd_journal_get_fd(j);
        if (pfd.fd < 0) {
          fprintf(stderr, "Failed to get new journal file descriptor: %s\n",
                  strerror(-pfd.fd));
          goto finish;
        }
        pfd.events = sd_journal_get_events(j);
        continue; /* Continue the loop to poll again */
      }
      break; /* Other error */
    }
    if (r == 0) {
      /* No new entries, but file descriptor still valid */
      continue;
    }
    /* Read and print new entries */
    for (int i = 0; i < r; ++i) {
      r = sd_journal_get_data(j, "MESSAGE", &d, &l);
      if (r < 0) {
        fprintf(stderr, "Failed to read message field: %s\n", strerror(-r));
        continue;
      }
      printf("%.*s\n", (int) l, (const char*) d);
    }
  }
finish:
  sd_journal_close(j);
  return 0;
}

Esperar con poll() (este ejemplo carece de toda comprobación de errores por simplicidad):

/* SPDX-License-Identifier: MIT-0 */
#define _GNU_SOURCE 1
#include <poll.h>
#include <time.h>
#include <systemd/sd-journal.h>
int wait_for_changes(sd_journal *j) {
  uint64_t t;
  int msec;
  struct pollfd pollfd;
  sd_journal_get_timeout(j, &t);
  if (t == (uint64_t) -1)
    msec = -1;
  else {
    struct timespec ts;
    uint64_t n;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    n = (uint64_t) ts.tv_sec * 1000000 + ts.tv_nsec / 1000;
    msec = t > n ? (int) ((t - n + 999) / 1000) : 0;
  }
  pollfd.fd = sd_journal_get_fd(j);
  pollfd.events = sd_journal_get_events(j);
  poll(&pollfd, 1, msec);
  return sd_journal_process(j);
}
