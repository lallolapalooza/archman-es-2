sd_event_add_signal(3)

Paquete: systemd-libs

Licencias: LGPL-2.1-or-later, CC0-1.0, GPL-2.0-or-later WITH Linux-syscall-note

SD_EVENT_ADD_SIGNAL(3) sd_event_add_signal SD_EVENT_ADD_SIGNAL(3)

NOMBRE

sd_event_add_signal, sd_event_source_get_signal, sd_event_signal_handler_t, SD_EVENT_SIGNAL_PROCMASK - Añadir una fuente de eventos de señal de proceso UNIX a un bucle de eventos

SINOPSIS

#include <systemd/sd-event.h>
typedef struct sd_event_source sd_event_source;
SD_EVENT_SIGNAL_PROCMASK

typedef int (*sd_event_signal_handler_t)(sd_event_source *s, const struct signalfd_siginfo *si, void *userdata);

int sd_event_add_signal(sd_event *event, sd_event_source **source, int signal, sd_event_signal_handler_t handler, void *userdata);

int sd_event_source_get_signal(sd_event_source *source);

DESCRIPCIÓN

sd_event_add_signal() añade una nueva fuente de eventos de señal de proceso UNIX a un bucle de eventos. El objeto del bucle de eventos se especifica en el parámetro event, y el objeto de la fuente de eventos se devuelve en el parámetro source. El parámetro signal especifica la señal numérica a manejar (ver signal(7)).

El parámetro handler es una función a llamar cuando se recibe la señal, o NULL. La función manejadora recibirá el puntero userdata, que puede ser elegido libremente por el llamador. El manejador también recibe un puntero a una estructura signalfd_siginfo que contiene información sobre la señal recibida. Ver signalfd(2) para más información. El manejador puede devolver un valor negativo para indicar un error (ver más abajo), otros valores de retorno son ignorados. Si handler es NULL, se utilizará un manejador por defecto que llama a sd_event_exit(3).

Solo se puede instalar un manejador para una señal específica. La señal debe estar bloqueada en todos los hilos antes de llamar a esta función (usando sigprocmask(2) o pthread_sigmask(3)). Para mayor comodidad, si el flag especial SD_EVENT_SIGNAL_PROCMASK se combina (mediante OR) con la señal especificada, la señal se enmascarará automáticamente según sea necesario, para el hilo que llama. Tenga en cuenta que esto solo funciona de manera fiable si la señal ya está enmascarada en todos los demás hilos del proceso, o si no hay otros hilos en el momento de la invocación.

Por defecto, la fuente de eventos está habilitada permanentemente (SD_EVENT_ON), pero esto puede cambiarse con sd_event_source_set_enabled(3). Si la función manejadora devuelve un código de error negativo, se deshabilitará después de la invocación, incluso si se solicitó el modo SD_EVENT_ON antes, o provocará que el bucle termine, ver sd_event_source_set_exit_on_failure(3).

Para destruir un objeto de fuente de eventos use sd_event_source_unref(3), pero tenga en cuenta que la fuente de eventos solo se elimina del bucle de eventos cuando se sueltan todas las referencias a la fuente de eventos. Para asegurarse de que una fuente de eventos no se dispare más, incluso si todavía se referencia, deshabilite la fuente de eventos usando sd_event_source_set_enabled(3) con SD_EVENT_OFF.

Si el segundo parámetro de sd_event_add_signal() es NULL, no se devuelve ninguna referencia al objeto de la fuente de eventos. En este caso, la fuente de eventos se considera "flotante" y se destruirá implícitamente cuando el propio bucle de eventos sea destruido.

Si el parámetro handler de sd_event_add_signal() es NULL, y la fuente de eventos se dispara, esto se considerará una solicitud para salir del bucle de eventos. En este caso, el parámetro userdata, convertido a un entero, se pasa como parámetro del código de salida a sd_event_exit(3).

sd_event_source_get_signal() devuelve el número de señal configurado de una fuente de eventos creada previamente con sd_event_add_signal(). Toma el objeto de la fuente de eventos como parámetro source.

VALOR DE RETORNO

En caso de éxito, estas funciones devuelven 0 o un entero positivo. En caso de error, devuelven un código de error negativo estilo errno.

Errores

Los errores devueltos pueden indicar los siguientes problemas:

-ENOMEM

No hay suficiente memoria para asignar un objeto.

-EINVAL

Se ha pasado un argumento inválido.

-EBUSY

Ya hay un manejador instalado para esta señal o la señal no estaba bloqueada previamente.

-ESTALE

El bucle de eventos ya ha terminado.

-ECHILD

El bucle de eventos se creó en un proceso, librería o instancia de módulo diferente.

-EDOM

La fuente de eventos pasada no es una fuente de eventos de señal.

NOTAS

Las funciones descritas aquí están disponibles como una biblioteca compartida, que se puede compilar y enlazar con el archivo libsystemd pkg-config(1).

El código descrito aquí utiliza getenv(3), que se declara como no seguro para múltiples hilos. Esto significa que el código que llama a las funciones descritas aquí no debe llamar a setenv(3) desde un hilo paralelo. Se recomienda hacer llamadas a setenv() solo desde una fase temprana del programa cuando no se hayan iniciado otros hilos.

HISTORIA

sd_event_add_signal(), sd_event_signal_handler_t() y sd_event_source_get_signal() se añadieron en la versión 217.

sd_event_add_signal(3)

sd_event_add_signal(3) Library Functions Manual sd_event_add_signal(3)

NAME

sd_event_add_signal - Add a watch for a process signal to an event loop

SYNOPSIS

#include <systemd/sd-event.h>

int sd_event_add_signal(sd_event *event, int *fd, int signal,
                        sd_event_handler_t handler, void *userdata);

DESCRIPTION

The sd_event_add_signal() function may be used to register a listener for a specific process signal with an event loop. The event loop is passed in the event parameter.

The fd parameter is a pointer to an integer. If it is not NULL, the file descriptor that will receive the signal event will be written there. This file descriptor will be set to non-blocking mode. It is recommended to pass a non-NULL file descriptor, so the caller knows which file descriptor to poll and can close it later.

The signal parameter specifies the signal number to listen for. This should be a valid signal number as defined in <signal.h>. Currently, only SIGTERM, SIGINT, SIGHUP, SIGUSR1 and SIGUSR2 are supported.

The handler parameter is a callback function to be invoked when the signal is received. The callback function receives the event loop, the signal number, and the userdata pointer as arguments. The callback should return a positive integer for success (e.g. 1) or a non-positive integer for failure (e.g. 0 or -EESCAPE).

The userdata parameter is an arbitrary pointer that will be passed to the handler callback.

The event handler is added to the event loop *event*. An event handler might be triggered multiple times, depending on the signal and system configuration. The signal handler is invoked when the specified signal is delivered to the process. If the file descriptor is registered, it will become readable when the signal is delivered.

The file descriptor associated with the signal handler is created using signalfd(2). This file descriptor will be automatically closed when the handler is removed using sd_event_source_del().

Use sd_event_source_get_fd() to get the file descriptor associated with the event source. You may use sd_event_source_get_userdata() and sd_event_source_get_event() to get the userdata and event loop associated with the event source.

If you want to stop listening for the signal, use sd_event_source_del().

RETURN VALUE

On success, sd_event_add_signal() returns a reference to the new event source object. This reference must be unreferenced by sd_event_unref() when it is no longer needed.

On failure, sd_event_add_signal() returns a negative errno error code.

NOTES

The file descriptor returned via fd is not yet activated. You still need to call sd_event_add_io() or sd_event_add_time() to activate it.

Signals are tricky. A signal is delivered to a process. If multiple threads are running in a process, the signal is delivered to one arbitrary thread. When using sd-event, signals are delivered to the main thread. It is generally recommended to block all signals except the ones that you explicitly want to catch using signalfd. This can be done using sigprocmask(2) or pthread_sigmask(3). For example:

sigset_t sigmask;
sigemptyset(&sigmask);
sigaddset(&sigmask, SIGINT);
sigaddset(&sigmask, SIGTERM);
pthread_sigmask(SIG_BLOCK, &sigmask, NULL);

Signals that are blocked this way will not be delivered until they are unblocked. Then, they will be delivered to the process, and sd_event_add_signal() will receive them.

EXAMPLE

The following example demonstrates how to set up a signal handler for SIGINT:

#include <stdio.h>
#include <stdlib.h>
#include <signal.h>
#include <systemd/sd-event.h>

static int signal_handler(sd_event_source *s, int signal, void *userdata) {
    fprintf(stderr, "Caught signal %d\n", signal);
    sd_event_exit(sd_event_source_get_event(s), 0); // Exit the event loop
    return 0; // Do not re-run the handler
}

int main(void) {
    sd_event *event = NULL;
    sd_event_source *signal_source = NULL;
    int r;

    r = sd_event_new(&event);
    if (r < 0) {
        fprintf(stderr, "Failed to create event loop: %s\n", strerror(-r));
        return 1;
    }

    // Block SIGINT and SIGTERM
    sigset_t sigmask;
    sigemptyset(&sigmask);
    sigaddset(&sigmask, SIGINT);
    sigaddset(&sigmask, SIGTERM);
    pthread_sigmask(SIG_BLOCK, &sigmask, NULL);

    // Add a handler for SIGINT
    r = sd_event_add_signal(event, NULL, SIGINT, signal_handler, NULL);
    if (r < 0) {
        fprintf(stderr, "Failed to add signal handler: %s\n", strerror(-r));
        goto finish;
    }

    fprintf(stderr, "Waiting for SIGINT or SIGTERM...\n");
    r = sd_event_loop(event);
    if (r < 0) {
        fprintf(stderr, "Failed to run event loop: %s\n", strerror(-r));
        goto finish;
    }

finish:
    sd_event_unref(event); // Release the reference to the event loop
    return r < 0 ? 1 : 0;
}
