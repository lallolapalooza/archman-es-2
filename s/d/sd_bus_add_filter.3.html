DESCRIPCIÓN

sd_bus_add_object_vtable() se utiliza para declarar atributos para la ruta del objeto path conectada a la conexión de bus bus bajo la interfaz interface. La tabla vtable puede contener declaraciones de propiedades usando SD_BUS_PROPERTY() o SD_BUS_WRITABLE_PROPERTY(), declaraciones de métodos usando SD_BUS_METHOD(), SD_BUS_METHOD_WITH_NAMES(), SD_BUS_METHOD_WITH_OFFSET(), o SD_BUS_METHOD_WITH_NAMES_OFFSET(), y declaraciones de señales usando SD_BUS_SIGNAL_WITH_NAMES() o SD_BUS_SIGNAL(), véase más adelante. El parámetro userdata contiene un puntero que se pasará a varias funciones de callback. Puede especificarse como NULL si no se necesita ningún valor. Una interfaz puede tener cualquier número de vtables adjuntas a ella.

sd_bus_add_fallback_vtable() es similar a sd_bus_add_object_vtable(), pero se utiliza para registrar atributos "fallback". Al buscar una declaración de atributo, se comprueban primero las rutas de objetos de bus registradas con sd_bus_add_object_vtable(). Si no se encuentra ninguna coincidencia, se comprueban las vtables fallback para cada prefijo de la ruta del objeto de bus, es decir, eliminando sucesivamente los últimos componentes separados por barras. Esto permite que la vtable se utilice para un número arbitrario de objetos creados dinámicamente.

El parámetro find es una función que se utiliza para localizar el objeto de destino basándose en la ruta del objeto de bus path. Debe devolver 1 y establecer el parámetro de salida ret_found si se encuentra el objeto, devolver 0 si no se encontró el objeto, y devolver un código de error negativo de estilo errno o inicializar la estructura de error ret_error en caso de error. El puntero pasado en ret_found se utilizará como parámetro userdata para las funciones de callback (desplazado por los desplazamientos offset según se especifica en las entradas de la vtable).

sd_bus_add_object() adjunta un callback directamente a la ruta del objeto path. Una ruta de objeto puede tener cualquier número de callbacks adjuntos. Cada callback se antepone a la lista de callbacks que siempre se llaman en orden. sd_bus_add_fallback() es similar a sd_bus_add_object() pero se aplica a las rutas fallback en su lugar.

sd_bus_add_filter() instala un callback que se invoca para cada mensaje D-Bus entrante. Los filtros se pueden usar para manejar lógica común a todos los mensajes recibidos por un servicio (por ejemplo, autenticación o autorización).

Cuando se recibe una solicitud, se llaman secuencialmente todos los callbacks asociados hasta que un callback devuelva un entero distinto de cero. Devuelva cero de un callback para dar a otros callbacks la oportunidad de procesar la solicitud. Los callbacks se llaman en el siguiente orden: primero, se llaman los callbacks globales instalados con sd_bus_add_filter(). Segundo, se llaman los callbacks adjuntos directamente a la ruta del objeto de la solicitud, seguidos de cualquier callback de método D-Bus adjunto a la ruta del objeto de la solicitud, interfaz y miembro. Finalmente, se llaman los callbacks de propiedad adjuntos a la ruta del objeto de la solicitud, interfaz y miembro. Si el callback final devuelve cero, se envía una respuesta de error.

Tenga en cuenta que puede devolver un entero positivo de una función de retorno de llamada de método sin enviar una respuesta inmediatamente. Esto informa a sd-bus que esta función de retorno de llamada asumirá la responsabilidad de responder a la solicitud sin forzar a la función de retorno de llamada a producir una respuesta de inmediato. Esto permite que una función de retorno de llamada realice cualquier número de operaciones asíncronas necesarias para construir una respuesta. Sin embargo, si la producción de una respuesta lleva demasiado tiempo, la llamada al método expirará en el llamador. Esto solo está disponible para métodos y no para propiedades.

Si se invocó una función de retorno de llamada para manejar una solicitud que espera una respuesta y la función de retorno de llamada devuelve un valor negativo, el valor se interpreta como un código de error negativo estilo errno y se envía de vuelta al llamador como un error de D-Bus como si se hubiera llamado a sd_bus_reply_method_errno(3). Además, todas las funciones de retorno de llamada toman un parámetro de salida sd_bus_error que se puede utilizar para proporcionar información de error más detallada. Si ret_error se establece cuando la función de retorno de llamada finaliza, el error de D-Bus correspondiente se envía de vuelta al llamador como si se hubiera llamado a sd_bus_reply_method_error(3). Cualquier error almacenado en ret_error tiene prioridad sobre cualquier valor negativo devuelto por la misma función de retorno de llamada al determinar qué error enviar de vuelta al llamador. Use sd_bus_error_set(3) o una de sus variantes para establecer ret_error y devolver un entero negativo de una función de retorno de llamada con una única llamada a función. Para enviar una respuesta de error después de que una función de retorno de llamada ya haya finalizado, use sd_bus_reply_method_errno(3) o una de sus variantes.

Para todas las funciones, se crea internamente una ranura de coincidencia. Si el parámetro de salida slot es NULL, se crea un objeto de ranura "flotante", vea sd_bus_slot_set_floating(3). De lo contrario, se devuelve un puntero al objeto de ranura. En ese caso, la referencia al objeto de ranura debe liberarse cuando la vtable ya no sea necesaria, vea sd_bus_slot_unref(3).

El arreglo sd_bus_vtable

El arreglo consta de las estructuras de tipo sd_bus_vtable, pero nunca debe rellenarse manualmente, sino a través de una de las siguientes macros:

SD_BUS_VTABLE_START(flags), SD_BUS_VTABLE_END

Estos deben ser siempre el primer y el último elemento. El parámetro flags se puede utilizar para establecer atributos que se apliquen a todo el arreglo; vea la sección "Flags" a continuación.

SD_BUS_METHOD_WITH_ARGS_OFFSET(), SD_BUS_METHOD_WITH_ARGS()

Declara un método D-Bus con el nombre member, argumentos args y resultado result. args espera una secuencia de pares tipo/nombre de argumento envueltos en la macro SD_BUS_ARGS(). Los elementos en índices pares en esta lista describen los tipos de los argumentos del método. La firma de parámetros del método es la concatenación de todos los literales de cadena en índices pares en args. Si un método no tiene parámetros, pase SD_BUS_NO_ARGS a args. Los elementos en índices impares describen los nombres de los argumentos del método. result espera una secuencia de pares tipo/nombre envueltos en la macro SD_BUS_RESULT() en el mismo formato que SD_BUS_ARGS(). La firma del resultado del método es la concatenación de todos los literales de cadena en índices pares en result. Si un método no tiene resultado, pase SD_BUS_NO_RESULT a result. Tenga en cuenta que se espera que los tipos de argumento sean literales de cadena entre comillas y los nombres de argumento sean literales de cadena sin comillas. Vea abajo un ejemplo completo.

La función manejadora handler debe ser de tipo sd_bus_message_handler_t. Se llamará para manejar los mensajes entrantes que llaman a este método. Recibe un puntero que es el parámetro userdata pasado a la función de registro con un desplazamiento de offset bytes. Esto se puede usar para pasar punteros a diferentes campos en la misma estructura de datos a diferentes métodos en la misma vtable. Para enviar una respuesta desde handler, llame a sd_bus_reply_method_return(3) con el mensaje con el que se invocó la función de retorno de llamada. El parámetro flags es una combinación de flags, vea abajo.

SD_BUS_METHOD_WITH_ARGS() es una abreviatura para llamar a SD_BUS_METHOD_WITH_ARGS_OFFSET() con un desplazamiento de cero.

SD_BUS_METHOD_WITH_NAMES_OFFSET(), SD_BUS_METHOD_WITH_NAMES(), SD_BUS_METHOD_WITH_OFFSET(), SD_BUS_METHOD()

Declara un método D-Bus con el nombre member, firma de parámetros signature, firma de resultado result. Los parámetros in_names y out_names especifican los nombres de los argumentos de los argumentos de entrada y salida en la firma de la función. in_names y out_names deben crearse usando la macro SD_BUS_PARAM(), vea abajo. En todos los demás aspectos, esta macro se comporta exactamente igual que SD_BUS_METHOD_WITH_ARGS_OFFSET().

SD_BUS_METHOD_WITH_NAMES(), SD_BUS_METHOD_WITH_OFFSET() y SD_BUS_METHOD() son variantes que especifican un desplazamiento cero (el parámetro userdata se pasa sin cambios), dejan los nombres sin establecer (es decir, sin nombres de parámetro) o ambos.

Prefiera usar SD_BUS_METHOD_WITH_ARGS_OFFSET() y SD_BUS_METHOD_WITH_ARGS() sobre estas macros, ya que permiten especificar los tipos y nombres de los argumentos uno al lado del otro, lo que es menos propenso a errores que primero especificar todos los tipos de argumentos seguidos de la especificación de todos los nombres de argumentos.

SD_BUS_SIGNAL_WITH_ARGS()

Declara una señal D-Bus con el nombre member y argumentos args. args espera una secuencia de pares tipo/nombre de argumento envueltos en la macro SD_BUS_ARGS(). Los elementos en índices pares en esta lista describen los tipos de los argumentos de la señal. La firma de parámetros de la señal es la concatenación de todos los literales de cadena en índices pares en args. Si una señal no tiene parámetros, pase SD_BUS_NO_ARGS a args. Los elementos en índices impares describen los nombres de los argumentos de la señal. El parámetro flags es una combinación de flags. Vea abajo un ejemplo completo.

SD_BUS_SIGNAL_WITH_NAMES(), SD_BUS_SIGNAL()

Declara una señal D-Bus con el nombre member, firma de parámetros signature y nombres de argumentos names. names debe crearse usando la macro SD_BUS_PARAM(), vea abajo. El parámetro flags es una combinación de flags, vea abajo.

SD_BUS_SIGNAL() es equivalente a SD_BUS_SIGNAL_WITH_NAMES() con el parámetro names sin establecer (es decir, sin nombres de parámetro).

Prefiera usar SD_BUS_SIGNAL_WITH_ARGS() sobre estas macros, ya que permite especificar los tipos y nombres de los argumentos uno al lado del otro, lo que es menos propenso a errores que primero especificar todos los tipos de argumentos seguidos de la especificación de todos los nombres de argumentos.

SD_BUS_WRITABLE_PROPERTY(), SD_BUS_PROPERTY()

Declara una propiedad D-Bus con el nombre member y firma de valor signature. Los parámetros get y set son los métodos de obtención y establecimiento. Se llaman con un puntero que es el parámetro userdata pasado a la función de registro con un desplazamiento de offset bytes. Esto se puede usar para pasar punteros a diferentes campos en la misma estructura de datos a diferentes métodos de establecimiento y obtención en la misma vtable. El parámetro flags es una combinación de flags, vea abajo.

Los métodos de establecimiento y obtención pueden omitirse (especificarse como NULL), si la propiedad es uno de los tipos básicos o "as" en el caso de propiedades de solo lectura. En esos casos, los parámetros userdata y offset deben apuntar juntos a una variable válida del tipo correspondiente. Se proporcionará un método de establecimiento y obtención predeterminado, que simplemente copia el argumento entre esta variable y el mensaje.

SD_BUS_PROPERTY() se utiliza para definir una propiedad de solo lectura.

SD_BUS_PARAM()

Los nombres de los parámetros deben envolverse en esta macro, vea el ejemplo a continuación.

Flags

El parámetro flags se utiliza para especificar una combinación de **anotaciones de D-Bus**[1].

SD_BUS_VTABLE_DEPRECATED

Marca esta entrada de vtable como obsoleta usando la anotación org.freedesktop.DBus.Deprecated en los datos de introspección. Si se especifica para SD_BUS_VTABLE_START(), la anotación se aplica a la interfaz contenedora.

SD_BUS_VTABLE_HIDDEN

Oculta esta entrada de vtable. No se mostrará en los datos de introspección. Si se especifica para SD_BUS_VTABLE_START(), todas las entradas del arreglo se ocultan.

SD_BUS_VTABLE_METHOD_NO_REPLY

Marca esta entrada de vtable como un método que no devolverá una respuesta usando la anotación org.freedesktop.DBus.Method.NoReply en los datos de introspección.

SD_BUS_VTABLE_PROPERTY_CONST, SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE, SD_BUS_VTABLE_PROPERTY_EMITS_INVALIDATION

Estos tres flags corresponden a diferentes valores de la anotación org.freedesktop.DBus.Property.EmitsChangedSignal, que especifica si la señal org.freedesktop.DBus.Properties.PropertiesChanged se emite cada vez que cambia la propiedad. SD_BUS_VTABLE_PROPERTY_CONST corresponde a const y significa que la propiedad nunca cambia durante la vida útil del objeto al que pertenece, por lo que no es necesario emitir ninguna señal. SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE corresponde a true y significa que se emite la señal. SD_BUS_VTABLE_PROPERTY_EMITS_INVALIDATION corresponde a invalidates y significa que se emite la señal, pero el valor no se incluye en la señal.

SD_BUS_VTABLE_PROPERTY_EXPLICIT

Marca esta entrada de propiedad vtable como que requiere una solicitud explícita para que se muestre el valor (generalmente porque el valor es grande o lento de calcular). Esta entrada no se puede combinar con SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE y no se mostrará en las listas de propiedades de forma predeterminada (por ejemplo, busctl introspect). Esto corresponde a la anotación org.freedesktop.systemd1.Explicit en los datos de introspección.

SD_BUS_VTABLE_SENSITIVE

Marca esta entrada de método vtable como que procesa datos sensibles. Cuando se establece, los mensajes de llamada de método entrantes y sus mensajes de respuesta salientes se marcan como sensibles usando sd_bus_message_sensitive(3), para que se borren de la memoria cuando se liberan.

SD_BUS_VTABLE_ABSOLUTE_OFFSET

Marca esta entrada de método o propiedad vtable para que el puntero de datos de usuario

SD_BUS_VTABLE_OPTIONS

These flags control the behavior of individual vtable entries. They are listed here for documentation purposes, but are usually passed via helper macros such as SD_BUS_METHOD(), SD_BUS_PROPERTY(), and others. The flags are ORed together.

SD_BUS_VTABLE_DEPRECATED

Marks this vtable entry as deprecated. This means that it should not be used anymore, but it is still available for backward compatibility. When introspection data is generated, this flag results in the org.freedesktop.DBus.Deprecated() annotation being added with the value true.

SD_BUS_VTABLE_MAYBE

Allows this vtable entry to be registered multiple times. If this flag is not set, registering a vtable entry for an existing interface and object path will fail.

SD_BUS_VTABLE_HIDDEN

Hides this vtable entry from introspection. This flag has no effect on runtime behavior, but it prevents the entry from appearing in the XML description of the interface. This is useful for internal implementation details that should not be exposed to clients.

SD_BUS_VTABLE_CONSTRUCTOR(constructor)

The constructor function, of type int(sd_bus_message*, void*, sd_bus_error*), is called when a new object is created for this interface. This is useful for initializing object-specific data structures. The function is called before any method calls or property accesses on the new object.

SD_BUS_VTABLE_DESTRUCTOR(destructor)

The destructor function, of type int(sd_bus_message*, void*, sd_bus_error*), is called when an object is destroyed. This is useful for freeing resources allocated by the constructor or during the object's lifetime. The function is called after all method calls and property accesses have finished.

SD_BUS_VTABLE_ACCESSOR(accessor)

The accessor function, of type int(sd_bus_message*, void*, sd_bus_error*), is called before any method call or property access on this vtable entry. This can be used for access control or for performing common setup tasks. The function receives the same arguments as the handler function.

SD_BUS_VTABLE_UNPRIVILEGED

Mark this vtable entry as unprivileged. Access to privileged entries is limited to users with appropriate capabilities as described in SD_BUS_VTABLE_CAPABILITY(). In practice many vtable entries are marked as unprivileged, and either are open to everyone, or the decision whether to allow access is taken later, e.g. by delegating to polkit[2].

The whole bus may be marked as trusted, in which case annotations at the entry level are ignored, see sd_bus_set_trusted(3).

When not specified, the org.freedesktop.systemd1.Privileged annotation with value "true" will be shown in introspection data.

SD_BUS_VTABLE_UNPRIVILEGED may not be applied to read-only properties, but read access (to both read-only and writable properties) is always unrestricted.

Note that this page describes checks implemented in the D-Bus client. The D-Bus server has an additional policy that may permit or deny connections, see "CONFIGURATION FILE" in dbus-daemon(1).

SD_BUS_VTABLE_CAPABILITY(capability)

Access to this vtable entry will be allowed if the calling process has the capability capability, as described in sd_bus_query_sender_privilege(3). If used for SD_BUS_VTABLE_START(), provides a default for all entries in the array. If not specified, either for an individual entry or the whole array, CAP_SYS_ADMIN is checked by default. See capabilities(7) for information about capabilities.

Note that vtable entries may be marked as unprivileged and the whole bus may be marked as trusted, see the discussion of SD_BUS_VTABLE_UNPRIVILEGED above.

SD_BUS_VTABLE_OFFSET(offset)

This flag specifies an offset into the user data structure. The handler function will receive a pointer to the specific member of the structure by adding this offset to the user data pointer specified during vtable registration. This is useful when the same vtable structure is used for multiple objects, and each object needs its own specific data.

SD_BUS_VTABLE_SIGNATURE(signature)

Specifies the D-Bus signature string for the arguments of a method or signal. This is only used for methods and signals that do not have explicit argument names defined. If this flag is used, it overrides any signature string provided in the macro arguments.

SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE

This flag indicates that a change in the property will emit the `PropertiesChanged` signal. This is the default behavior for writable properties.

SD_BUS_VTABLE_PROPERTY_EMITS_INVALIDATION

This flag indicates that a change in the property will emit the `PropertiesChanged` signal with the property name in the `invalidated_properties` array. This is used for properties that can change in ways not directly related to a write operation.

SD_BUS_VTABLE_PROPERTY_READONLY

Marks the property as read-only. This flag is implicit for properties defined with SD_BUS_READONLY_PROPERTY().

SD_BUS_VTABLE_PROPERTY_WRITABLE

Marks the property as writable. This flag is implicit for properties defined with SD_BUS_WRITABLE_PROPERTY().

SD_BUS_VTABLE_ARG(name, type)

Defines an argument for a method or signal with the given name and type. This can be used multiple times to define all arguments.

SD_BUS_RESULT(name, type)

Defines the return value of a method with the given name and type. This can only be used once per method.

SD_BUS_PARAM(name)

Declares a named parameter for a method or signal. The type is inferred from the context or the corresponding `_WITH_NAMES` macro. This is a shorthand for defining parameters in methods and signals.

SD_BUS_METHOD_WITH_NAMES_OFFSET(name, in_signature, out_signature, handler, offset, flags)

This macro is similar to SD_BUS_METHOD(), but allows explicitly naming input and output arguments using SD_BUS_PARAM(). It also takes an additional offset argument, which specifies an offset into the user data structure. This offset is added to the user data pointer provided during vtable registration, and the resulting pointer is passed to the handler function. This is useful when the handler function needs access to specific members of the user data structure.

SD_BUS_METHOD_WITH_ARGS_OFFSET(name, args..., result, handler, offset, flags)

This macro is similar to SD_BUS_METHOD(), but allows explicitly defining the argument names and types using SD_BUS_ARG() and return value using SD_BUS_RESULT(). It also takes an additional offset argument, which specifies an offset into the user data structure. The offset parameter of the entry is added to the user data pointer specified during vtable registration, and the resulting pointer is passed to the handler function.

The offset parameter for handler functions is determined slightly differently: instead of adding the offset parameter of the entry to the user data pointer specified during vtable registration, the offset is passed directly, converted to a pointer, without taking the user data pointer specified during vtable registration into account.

EXAMPLES

Example 1. Create a simple listener on the bus

/* SPDX-License-Identifier: MIT-0 */
#define _GNU_SOURCE 1
#include <errno.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdlib.h>
#include <stdio.h>
#include <systemd/sd-bus.h>
#define _cleanup_(f) __attribute__((cleanup(f)))
typedef struct object {
  char *name;
  uint32_t number;
} object;
static int method(sd_bus_message *m, void *userdata, sd_bus_error *error) {
  int r;
  printf("Got called with userdata=%p\n", userdata);
  if (sd_bus_message_is_method_call(m,
                                    "org.freedesktop.systemd.VtableExample",
                                    "Method4"))
    return 1;
  const char *string;
  r = sd_bus_message_read(m, "s", &string);
  if (r < 0) {
    fprintf(stderr, "sd_bus_message_read() failed: %s\n", strerror(-r));
    return 0;
  }
  r = sd_bus_reply_method_return(m, "s", string);
  if (r < 0) {
    fprintf(stderr, "sd_bus_reply_method_return() failed: %s\n", strerror(-r));
    return 0;
  }
  return 1;
}
static const sd_bus_vtable vtable[] = {
        SD_BUS_VTABLE_START(0),
        SD_BUS_METHOD(
            "Method1", "s", "s", method, 0),
        SD_BUS_METHOD_WITH_NAMES_OFFSET(
            "Method2",
            "so", SD_BUS_PARAM(string) SD_BUS_PARAM(path),
            "s", SD_BUS_PARAM(returnstring),
            method, offsetof(object, number),
            SD_BUS_VTABLE_DEPRECATED),
        SD_BUS_METHOD_WITH_ARGS_OFFSET(
            "Method3",
            SD_BUS_ARGS("s", string, "o", path),
            SD_BUS_RESULT("s", returnstring),
            method, offsetof(object, number),
            SD_BUS_VTABLE_UNPRIVILEGED),
        SD_BUS_METHOD_WITH_ARGS(
            "Method4",
            SD_BUS_NO_ARGS,
            SD_BUS_NO_RESULT,
            method,
            SD_BUS_VTABLE_UNPRIVILEGED),
        SD_BUS_SIGNAL(
            "Signal1",
            "so",
            0),
        SD_BUS_SIGNAL_WITH_NAMES(
            "Signal2",
            "so", SD_BUS_PARAM(string) SD_BUS_PARAM(path),
            0),
        SD_BUS_SIGNAL_WITH_ARGS(
            "Signal3",
            SD_BUS_ARGS("s", string, "o", path),
            0),
        SD_BUS_WRITABLE_PROPERTY(
            "AutomaticStringProperty", "s", NULL, NULL,
            offsetof(object, name),
            SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE),
        SD_BUS_WRITABLE_PROPERTY(
            "AutomaticIntegerProperty", "u", NULL, NULL,
            offsetof(object, number),
            SD_BUS_VTABLE_PROPERTY_EMITS_INVALIDATION),
        SD_BUS_VTABLE_END
};
int main(int argc, char **argv) {
  _cleanup_(sd_bus_flush_close_unrefp) sd_bus *bus = NULL;
  int r;
  sd_bus_default(&bus);
  object object = { .number = 666 };
  object.name = strdup("name");
  if (!object.name) {
    fprintf(stderr, "OOM\n");
    return EXIT_FAILURE;
  }
  r = sd_bus_add_object_vtable(bus, NULL,
                               "/org/freedesktop/systemd/VtableExample",
                               "org.freedesktop.systemd.VtableExample",
                               vtable,
                               &object);
  if (r < 0) {
    fprintf(stderr, "sd_bus_add_object_vtable() failed: %s\n", strerror(-r));
    return EXIT_FAILURE;
  }
  r = sd_bus_request_name(bus,
                          "org.freedesktop.systemd.VtableExample",
                          0);
  if (r < 0) {
    fprintf(stderr, "sd_bus_request_name() failed: %s\n", strerror(-r));
    return EXIT_FAILURE;
  }
  for (;;) {
    r = sd_bus_wait(bus, UINT64_MAX);
    if (r < 0) {
      fprintf(stderr, "sd_bus_wait() failed: %s\n", strerror(-r));
      return EXIT_FAILURE;
    }
    r = sd_bus_process(bus, NULL);
    if (r < 0) {
      fprintf(stderr, "sd_bus_process() failed: %s\n", strerror(-r));
      return EXIT_FAILURE;
    }
  }
  r = sd_bus_release_name(bus, "org.freedesktop.systemd.VtableExample");
  if (r < 0) {
    fprintf(stderr, "sd_bus_release_name() failed: %s\n", strerror(-r));
    return EXIT_FAILURE;
  }
  free(object.name);
  return 0;
}

RETURN VALUE

On success, sd_bus_add_object_vtable() and sd_bus_add_fallback_vtable() return a non-negative integer. On failure, they return a negative errno-style error code.

Errors

Returned errors may indicate the following problems:

-EINVAL

One of the required parameters is NULL or invalid. A reserved D-Bus interface was passed as the interface parameter.

-ENOPKG

The bus cannot be resolved.

-ECHILD

The bus was created in a different process, library or module instance.

-ENOMEM

Memory allocation failed.

-EPROTOTYPE

sd_bus_add_object_vtable() and sd_bus_add_fallback_vtable() have been both called for the same bus object path, which is not allowed.

-EEXIST

This vtable has already been registered for this interface and path.

Functions described here are availab

como una biblioteca compartida, que puede ser compilada y enlazada con el archivo pkg-config(1) de libsystemd.
