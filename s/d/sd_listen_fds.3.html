SD_LISTEN_FDS(3) sd_listen_fds SD_LISTEN_FDS(3)

NOMBRE

sd_listen_fds, sd_listen_fds_with_names, SD_LISTEN_FDS_START - Comprobar descriptores de archivo pasados por el gestor del sistema

SINOPSIS

#include <systemd/sd-daemon.h>
#define SD_LISTEN_FDS_START 3

int sd_listen_fds(int unset_environment);

int sd_listen_fds_with_names(int unset_environment, char*** names);

DESCRIPCIÓN

sd_listen_fds() puede ser invocada por un demonio para comprobar los descriptores de archivo pasados por el gestor de servicios como parte de la lógica de activación basada en sockets y almacenamiento de descriptores de archivo. Devuelve el número de descriptores de archivo recibidos. Si no se han recibido descriptores de archivo, se devuelve cero. El primer descriptor de archivo puede encontrarse en el número de descriptor de archivo 3 (es decir, SD_LISTEN_FDS_START), los descriptores restantes siguen en 4, 5, 6, ..., si los hay.

Los descriptores de archivo pasados de esta manera pueden ser cerrados libremente por los procesos que los reciben: depende de los propios procesos cerrarlos después de usarlos o dejarlos abiertos hasta que el proceso termine (en cuyo caso el kernel los cierra automáticamente). Tenga en cuenta que los descriptores de archivo recibidos por los demonios son duplicados de los descriptores de archivo que el gestor de servicios asignó y enlazó originalmente y de los que continuamente mantiene una copia (excepto si se usa Accept=yes). Esto significa que los cambios en las opciones del socket y otros cambios realizados en los sockets serán visibles para el gestor de servicios también. Lo más importante es que, en general, no es una buena idea invocar shutdown(2) en dichos sockets, ya que cerrará la comunicación en el descriptor de archivo que el gestor de servicios tiene para el mismo socket. Tenga en cuenta también que si un demonio se reinicia (y sus sockets asociados no lo hacen) recibirá descriptores de archivo para los mismos sockets que las invocaciones anteriores, por lo que todas las opciones de socket aplicadas entonces seguirán aplicándose.

Si un demonio recibe más de un descriptor de archivo, se pasarán en el mismo orden que se configuran en el archivo de unidad de socket de systemd (ver systemd.socket(5) para más detalles) — si solo hay un archivo de este tipo (ver abajo). No obstante, se recomienda verificar los tipos de socket correctos antes de usarlos. Para simplificar esta verificación, se proporcionan las funciones sd_is_fifo(3), sd_is_socket(3), sd_is_socket_inet(3), sd_is_socket_unix(3). Con el fin de maximizar la flexibilidad, se recomienda hacer estas comprobaciones lo más flexibles posible sin permitir configuraciones incorrectas. es decir, a menudo, el número de puerto real al que está enlazado un socket importa poco para que el servicio funcione, por lo que no debe verificarse. Por otro lado, si un socket es un socket de datagrama o de flujo importa mucho para la lógica más común del programa y debe verificarse.

Esta llamada a función establecerá la bandera FD_CLOEXEC para todos los descriptores de archivo pasados para evitar una mayor herencia a los hijos del proceso que llama.

Si varias unidades de socket activan el mismo servicio, el orden de los descriptores de archivo pasados a su proceso principal no está definido. Si se han pasado descriptores de archivo adicionales al gestor de servicios mediante mensajes "FDSTORE=1" de sd_pid_notify_with_fds(3), estos descriptores de archivo se pasan al final, en orden arbitrario y sin duplicados.

Si el parámetro unset_environment es distinto de cero, sd_listen_fds() anulará las variables de entorno $LISTEN_FDS, $LISTEN_PID y $LISTEN_FDNAMES antes de devolver (independientemente de si la llamada a la función tuvo éxito o no). Las llamadas posteriores a sd_listen_fds() devolverán entonces cero, pero las variables ya no se heredarán por los procesos hijos.

sd_listen_fds_with_names() es como sd_listen_fds(), pero opcionalmente también devuelve una matriz de cadenas con nombres de identificación para los descriptores de archivo pasados, si están disponibles y el parámetro names no es NULL. Esta información se lee de la variable $LISTEN_FDNAMES, que puede contener una lista de nombres separada por dos puntos. Para los servicios activados por socket, estos nombres pueden configurarse con el ajuste FileDescriptorName= en los archivos de unidad de socket, ver systemd.socket(5) para más detalles. Para los descriptores de archivo insertados en el almacén de descriptores de archivo (ver arriba), el nombre se establece a través del campo FDNAME= transmitido a través de sd_pid_notify_with_fds(). El caso de uso principal para estos nombres son los servicios que aceptan una variedad de descriptores de archivo que no son reconocibles solo con funciones como sd_is_socket(), y que por lo tanto requieren identificación a través de un nombre. Se recomienda depender de descriptores de archivo con nombre solo si la identificación mediante sd_is_socket() y llamadas relacionadas no es suficiente. Tenga en cuenta que los nombres utilizados no son únicos de ninguna manera. La matriz de cadenas devuelta tiene tantas entradas como descriptores de archivo se hayan recibido, más un puntero NULL final que termina la matriz. El llamador necesita liberar la matriz en sí y cada uno de sus elementos con la llamada free() de libc después de su uso. Si el parámetro names es NULL, la llamada es completamente equivalente a sd_listen_fds().

Bajo condiciones específicas, se devuelven los siguientes nombres de descriptor de archivo automáticos:

Tabla 1.  Nombres especiales

Nombre Descripción
"unknown" El proceso no recibió ningún nombre para el descriptor de archivo específico del gestor de servicios.
"stored" El descriptor de archivo se origina en el almacén de descriptores de archivo por servicio del gestor de servicios, y el campo FDNAME= estuvo ausente cuando el descriptor de archivo se envió al gestor de servicios.
"connection" El servicio se activó en estilo por conexión usando Accept=yes en el archivo de unidad de socket, y el descriptor de archivo es el socket de conexión.

Para más información sobre el almacén de descriptores de archivo, consulte la descripción general del
Almacén de Descriptores de Archivo[1].

VALOR DE RETORNO

En caso de error, estas llamadas devuelven un código de error negativo de estilo errno. Si $LISTEN_FDS/$LISTEN_PID no estaba configurado o no estaba configurado correctamente para este demonio y por lo tanto no se recibieron descriptores de archivo, se devuelve 0. De lo contrario, se devuelve el número de descriptores de archivo pasados. La aplicación puede encontrarlos a partir del descriptor de archivo SD_LISTEN_FDS_START, es decir, el descriptor de archivo 3.

NOTAS

Las funciones descritas aquí están disponibles como una biblioteca compartida, que puede compilarse y enlazarse con el archivo libsystemd pkg-config(1).

El código descrito aquí usa getenv(3), que está declarado como no seguro para hilos. Esto significa que el código que llama a las funciones descritas aquí no debe llamar a setenv(3) desde un hilo paralelo. Se recomienda hacer llamadas a setenv() solo desde una fase temprana del programa cuando no se han iniciado otros hilos.

Internamente, sd_listen_fds() comprueba si la variable de entorno $LISTEN_PID coincide con el PID del demonio. Si no es así, devuelve inmediatamente. De lo contrario, analiza el número pasado en la variable de entorno $LISTEN_FDS, luego establece la bandera FD_CLOEXEC para el número de descriptores de archivo analizado comenzando desde SD_LISTEN_FDS_START. Finalmente, devuelve el número analizado. sd_listen_fds_with_names() hace lo mismo pero también analiza $LISTEN_FDNAMES si está configurado.

Estas funciones no están diseñadas para servicios que especifican StandardInput=socket ya que la variable $LISTEN_FDS no está configurada en su entorno.

ENTORNO

$LISTEN_PID, $LISTEN_FDS, $LISTEN_FDNAMES

Configurado por el gestor de servicios para procesos supervisados que utilizan activación basada en sockets. Esta variable de entorno especifica los datos que analizan sd_listen_fds() y sd_listen_fds_with_names(). Ver arriba para más detalles.

NAME

sd_listen_fds - count and retrieve file descriptors passed by a systemd service

SYNOPSIS

#include <systemd/sd-daemon.h>

int sd_listen_fds(void);
int sd_listen_fds_with_pid(pid_t pid);

DESCRIPTION

sd_listen_fds may be used by a daemon process to check if it was invoked by systemd and if systemd passed any file descriptors to it. This is commonly used by services that are designed to be managed by systemd, for example servers that accept network connections.

systemd may pass file descriptors to child processes it invokes. These file descriptors are passed via the UNIX domain socket descriptor 2 (STDERR_FILENO). The service manager announces the available file descriptors by sending them via this socket, and the service might then receive them. This is often used for network sockets, but also for other types of file descriptors.

If the service process is started directly by systemd, and systemd has file descriptors to pass, it sends them over STDERR_FILENO. The program is then expected to read these descriptors from STDERR_FILENO, and acknowledge their receipt. This function may be used to count how many file descriptors are available for reading from STDERR_FILENO.

If the function returns a value greater than 0, it means that this many file descriptors are available for reading from STDERR_FILENO. If it returns 0, no file descriptors were passed. If it returns a negative value, an error occurred.

A common pattern is to check the return value of sd_listen_fds at the beginning of main(). If the value is greater than 0, the service should assume it is managed by systemd and should use the passed file descriptors. If the value is 0, the service should fall back to a different mechanism for acquiring the necessary file descriptors (e.g. binding and listening itself).

sd_listen_fds_with_pid() is similar to sd_listen_fds(), but checks for file descriptors passed to a specific process ID pid. This is useful for the rare case where a service might fork, and the parent process needs to check if the child process (identified by pid) received file descriptors.

Note that these functions do not actually *retrieve* the file descriptors. They only check how many are available. To receive file descriptors, use sd_fd_ready(3), sd_export_fds(3), sd_accept_serial_fd(3), sd_nth_fd(3), and sd_get_seats(3).

For a detailed explanation of systemd's file descriptor passing mechanism, see https://systemd.io/FILE_DESCRIPTOR_STORE.

RETURN VALUE

On success, returns the number of file descriptors passed via STDERR_FILENO, or 0 if none were passed. On failure, returns a negative errno-style error code.

NOTES

These functions are available as a shared library, which is part of libsystemd. To link against it, use the pkg-config(1) utility:

pkg-config --cflags --libs libsystemd

The logic for receiving and acknowledging the file descriptors is automatically performed by systemd's service manager when it launches a service configured with StandardInput=fd or StandardInput=socket. The service process does not need to perform any special actions to receive them, beyond calling sd_listen_fds() to check their availability.

The main process of the service is expected to call this function. If the service forks, the child process will not be able to receive file descriptors using this mechanism, unless it is explicitly passed them (e.g. via a socket). The sd_listen_fds_with_pid() function can be used to check if the forked child process received the file descriptors, but it requires the parent to know the child's PID.

The file descriptors passed are typically sockets, but might be other types of file descriptors as well. The type and intended use of each file descriptor is determined by the service configuration in systemd.socket(5).

ENVIRONMENT

The sd_listen_fds() function relies on file descriptor passing implemented by the systemd service manager. It does not directly depend on environment variables.

HISTORY

sd_listen_fds() and sd_listen_fds_with_pid() were introduced in systemd version 215.
