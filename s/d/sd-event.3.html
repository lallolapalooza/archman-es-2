NOMBRE

sd-event - Una implementación genérica de bucle de eventos

SINOPSIS

#include <systemd/sd-event.h>

pkg-config --cflags --libs libsystemd

DESCRIPCIÓN

sd-event.h es parte de libsystemd(3) y proporciona una implementación genérica de bucle de eventos, basada en el epoll(7) de Linux.

Ver sd_event_new(3), sd_event_run(3), sd_event_add_io(3), sd_event_add_time(3), sd_event_add_signal(3), sd_event_add_child(3), sd_event_add_inotify(3), sd_event_add_defer(3), sd_event_add_memory_pressure(3), sd_event_source_unref(3), sd_event_source_set_priority(3), sd_event_source_set_enabled(3), sd_event_source_set_userdata(3), sd_event_source_get_event(3), sd_event_source_get_pending(3), sd_event_source_set_description(3), sd_event_source_set_prepare(3), sd_event_source_set_ratelimit(3), sd_event_wait(3), sd_event_get_fd(3), sd_event_set_watchdog(3), sd_event_exit(3), sd_event_now(3) para más información sobre las funciones disponibles.

El diseño del bucle de eventos está enfocado en ejecutar una instancia separada del bucle de eventos en cada hilo; no tiene el concepto de distribuir eventos desde una única instancia de bucle de eventos a múltiples hilos de trabajo. La distribución de eventos está estrictamente ordenada y sujeta a prioridades configurables. En cada iteración del bucle de eventos se despacha una única fuente de eventos. Cada vez que se despacha una fuente de eventos, se consulta al kernel por nuevos eventos, antes de que se despache la siguiente fuente de eventos. El bucle de eventos está diseñado para respetar las prioridades y proporcionar equidad dentro de cada prioridad. No está diseñado para proporcionar un rendimiento óptimo, ya que esto contradice estos objetivos debido a las limitaciones de las primitivas subyacentes de epoll(7).

La implementación del bucle de eventos proporciona las siguientes características:

1.Fuentes de eventos de E/S, basadas en la monitorización de descriptores de archivo de epoll(7), incluyendo eventos activados por borde (EPOLLET). Ver sd_event_add_io(3).
2.Fuentes de eventos de temporizador, basadas en timerfd_create(2), que soportan los relojes CLOCK_MONOTONIC, CLOCK_REALTIME, CLOCK_BOOTTIME, así como los relojes CLOCK_REALTIME_ALARM y CLOCK_BOOTTIME_ALARM que pueden reanudar el sistema desde la suspensión. Al crear eventos de temporizador, se puede especificar un parámetro de precisión requerida que permite la coalescencia de eventos de temporizador para minimizar el consumo de energía. Ver sd_event_add_time(3).
3.Eventos de señales de procesos UNIX, basados en signalfd(2), incluyendo soporte completo para señales en tiempo real y parámetros en cola. Ver sd_event_add_signal(3).
4.Eventos de cambio de estado de procesos hijos, basados en waitid(2). Ver sd_event_add_child(3).
5.Fuentes de eventos estáticas, de tres tipos: defer, post y exit, para invocar llamadas en cada bucle de eventos, después de otras fuentes de eventos o al finalizar el bucle de eventos. Ver sd_event_add_defer(3).
6.Las fuentes de eventos pueden tener asignado un valor de prioridad de 64 bits, que controla el orden en el que se despachan las fuentes de eventos si varias están pendientes simultáneamente. Ver sd_event_source_set_priority(3).
7.El bucle de eventos puede enviar automáticamente mensajes de notificación de watchdog al gestor de servicios. Ver sd_event_set_watchdog(3).
8.El bucle de eventos puede integrarse en bucles de eventos ajenos, como el de GLib. Ver sd_event_get_fd(3) para un ejemplo.

NOTAS

Las funciones descritas aquí están disponibles como una biblioteca compartida, que puede compilarse y enlazarse con el archivo libsystemd pkg-config(1).

El código descrito aquí utiliza getenv(3), que se declara como no seguro para subprocesos (thread-safe). Esto significa que el código que llama a las funciones descritas aquí no debe llamar a setenv(3) desde un hilo paralelo. Se recomienda realizar llamadas a setenv() solo desde una fase temprana del programa cuando aún no se han iniciado otros hilos.
