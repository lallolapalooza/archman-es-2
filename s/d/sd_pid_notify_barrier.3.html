NOMBRE

sd_notify, sd_notifyf, sd_pid_notify, sd_pid_notifyf, sd_pid_notify_with_fds, sd_pid_notifyf_with_fds, sd_notify_barrier, sd_pid_notify_barrier - Notificar al gestor de servicios sobre la finalización de la inicialización y otros cambios de estado del servicio

SINOPSIS

#include <systemd/sd-daemon.h>

int sd_notify(int unset_environment, const char *state);

int sd_notifyf(int unset_environment, const char *format, ...);

int sd_pid_notify(pid_t pid, int unset_environment, const char *state);

int sd_pid_notifyf(pid_t pid, int unset_environment, const char *format, ...);

int sd_pid_notify_with_fds(pid_t pid, int unset_environment, const char *state, const int *fds, unsigned n_fds);

int sd_pid_notifyf_with_fds(pid_t pid, int unset_environment, const int *fds, size_t n_fds, const char *format, ...);

int sd_notify_barrier(int unset_environment, uint64_t timeout);

int sd_pid_notify_barrier(pid_t pid, int unset_environment, uint64_t timeout);

DESCRIPCIÓN

sd_notify() puede ser llamada por un servicio para notificar al gestor de servicios sobre cambios de estado. Puede usarse para enviar información arbitraria, codificada en una cadena similar a un bloque de entorno. Lo más importante es que puede usarse para notificaciones de finalización de inicio o recarga.

Si el parámetro unset_environment no es cero, sd_notify() eliminará la variable de entorno $NOTIFY_SOCKET antes de retornar (independientemente de si la llamada a la función tuvo éxito o no). Llamadas posteriores a sd_notify() no harán nada silenciosamente, y la variable ya no será heredada por los procesos hijos.

El parámetro state debe contener una lista de asignaciones de variables separadas por saltos de línea, similar en estilo a un bloque de entorno. Se implica un salto de línea final si no se especifica ninguno. La cadena puede contener cualquier tipo de asignaciones de variables, pero vea la siguiente sección para una lista de asignaciones entendidas por el gestor de servicios.

Tenga en cuenta que systemd aceptará datos de estado enviados por un servicio solo si la opción NotifyAccess= está configurada correctamente en el archivo de definición del servicio. Consulte systemd.service(5) para obtener detalles.

Tenga en cuenta que las notificaciones de sd_notify() solo pueden atribuirse correctamente a unidades si el proceso que envía aún está activo en el momento en que PID 1 procesa el mensaje, o si el proceso que envía está rastreado explícitamente en tiempo de ejecución por el gestor de servicios. Esto último ocurre si el gestor de servicios inició originalmente el proceso, es decir, en todos los procesos que coinciden con NotifyAccess=main o NotifyAccess=exec. Por el contrario, si un proceso auxiliar de la unidad envía un mensaje sd_notify() y sale inmediatamente, el gestor de servicios podría no ser capaz de atribuir correctamente el mensaje a la unidad y, por lo tanto, lo ignorará, incluso si NotifyAccess=all está configurado para ella.

Por lo tanto, para eliminar todas las condiciones de carrera que implican la búsqueda de la unidad del cliente y la atribución correcta de notificaciones a las unidades, se puede usar sd_notify_barrier(). Esta llamada actúa como un punto de sincronización y garantiza que todas las notificaciones enviadas antes de esta llamada hayan sido captadas por el gestor de servicios cuando retorna exitosamente. El uso de sd_notify_barrier() es necesario para clientes que no son invocados por el gestor de servicios; de lo contrario, este mecanismo de sincronización es innecesario para la atribución de notificaciones a la unidad.

sd_notifyf() es similar a sd_notify() pero toma una cadena de formato similar a printf() más argumentos.

sd_pid_notify() y sd_pid_notifyf() son similares a sd_notify() y sd_notifyf() pero toman un ID de proceso (PID) para usar como PID de origen del mensaje como primer argumento. Esto es útil para enviar mensajes de notificación en nombre de otros procesos, siempre que se disponga de los privilegios adecuados. Efectivamente, esto significa que una invocación privilegiada de sd_pid_notify() puede eludir las restricciones NotifyAccess=main o NotifyAccess=exec aplicadas a un servicio. Si el argumento PID se especifica como 0, se utiliza el ID de proceso del proceso de llamada, en cuyo caso las llamadas son completamente equivalentes a sd_notify() y sd_notifyf().

sd_pid_notify_with_fds() es similar a sd_pid_notify() pero toma un array adicional de descriptores de archivos. Estos descriptores de archivos se envían junto con el mensaje de notificación al gestor de servicios. Esto es particularmente útil para enviar mensajes "FDSTORE=1", como se describe anteriormente. Los argumentos adicionales son un puntero al array de descriptores de archivos más el número de descriptores de archivos en el array. Si se pasa el número de descriptores de archivos como 0, la llamada es completamente equivalente a sd_pid_notify(), es decir, no se pasan descriptores de archivos. Tenga en cuenta que los descriptores de archivos enviados al gestor de servicios en un mensaje sin "FDSTORE=1" se cierran inmediatamente al recibirlos.

sd_pid_notifyf_with_fds() es una combinación de sd_pid_notify_with_fds() y sd_notifyf(), es decir, acepta tanto un PID como un conjunto de descriptores de archivos como entrada, y procesa una cadena de formato para generar la cadena de estado.

sd_notify_barrier() permite al llamador sincronizarse contra la recepción de mensajes de notificación enviados previamente y utiliza el comando BARRIER=1. Toma un valor de timeout relativo en microsegundos que se pasa a ppoll(2). Un valor de UINT64_MAX se interpreta como un tiempo de espera infinito.

sd_pid_notify_barrier() es igual que sd_notify_barrier(), pero permite especificar el PID de origen del mensaje de notificación.

ASIGNACIONES CONOCIDAS

Las siguientes asignaciones tienen un significado definido:

READY=1

Indica al gestor de servicios que la inicialización del servicio ha finalizado, o que el servicio ha finalizado la recarga de su configuración. Esto solo es utilizado por systemd si el archivo de definición del servicio tiene Type=notify o Type=notify-reload configurado. Dado que hay poco valor en señalar la no preparación, el único valor que los servicios deben enviar es "READY=1" (es decir, "READY=0" no está definido).

RELOADING=1

Indica al gestor de servicios que el servicio está comenzando a recargar su configuración. Esto es útil para permitir que el gestor de servicios rastree el estado interno del servicio y lo presente al usuario. Tenga en cuenta que un servicio que envía esta notificación también debe enviar una notificación "READY=1" cuando haya completado la recarga de su configuración. Las recargas de las que se notifica al gestor de servicios con este mecanismo se propagan de la misma manera que cuando se inician originalmente a través del gestor de servicios. Este mensaje es particularmente relevante para los servicios Type=notify-reload, para informar al gestor de servicios que la solicitud de recarga del servicio ha sido recibida y está siendo procesada.

Añadido en la versión 217.

STOPPING=1

Indica al gestor de servicios que el servicio está comenzando su apagado. Esto es útil para permitir que el gestor de servicios rastree el estado interno del servicio y lo presente al usuario.

Añadido en la versión 217.

MONOTONIC_USEC=...

Un campo que transporta la marca de tiempo monotónica (según CLOCK_MONOTONIC) formateada en decimal en μs, cuando el cliente generó el mensaje de notificación. Esto se usa típicamente en combinación con "RELOADING=1", para permitir que el gestor de servicios sincronice correctamente los ciclos de recarga. Consulte systemd.service(5) para obtener detalles, específicamente "Type=notify-reload".

Añadido en la versión 253.

STATUS=...

Pasa una cadena de estado UTF-8 de una sola línea al gestor de servicios que describe el estado del servicio. Esto es de formato libre y puede usarse para varios propósitos: los programas similares a fsck podrían pasar porcentajes de finalización y los programas que fallan podrían pasar una cadena legible por humanos

Errores

Los errores devueltos pueden indicar los siguientes problemas:

-E2BIG

Se pasaron más descriptores de archivo a la vez de los que el sistema permite. En Linux, el número de descriptores de archivo que se pueden pasar a través de sockets AF_UNIX a la vez es 253, vea unix(7) para más detalles.

Añadido en la versión 257.

NOTAS

Las funciones descritas aquí están disponibles como una biblioteca compartida, que se puede compilar y enlazar con el archivo libsystemd pkg-config(1).

El código descrito aquí utiliza getenv(3), que se declara que no es seguro para el uso en múltiples hilos. Esto significa que el código que llama a las funciones descritas aquí no debe llamar a setenv(3) desde un hilo paralelo. Se recomienda realizar solo llamadas a setenv() desde una fase temprana del programa cuando no se hayan iniciado otros hilos.

Estas funciones envían un único datagrama con la cadena de estado como carga útil al socket referenciado en la variable de entorno $NOTIFY_SOCKET. Si el primer carácter de $NOTIFY_SOCKET es "/" o "@", la cadena se entiende como un socket AF_UNIX o un socket del espacio de nombres abstracto de Linux (respectivamente), y en ambos casos el datagrama va acompañado de las credenciales del proceso del servicio que envía, utilizando SCM_CREDENTIALS. Si la cadena comienza con "vsock:", entonces la cadena se entiende como una dirección AF_VSOCK, que es útil para que los hipervisores/VMM u otros procesos en el host reciban una notificación cuando una máquina virtual ha terminado de arrancar. Tenga en cuenta que en caso de que el hipervisor no soporte SOCK_DGRAM sobre AF_VSOCK, se utilizará SOCK_SEQPACKET en su lugar. Se pueden usar "vsock-stream", "vsock-dgram" y "vsock-seqpacket" en lugar de "vsock" para forzar el uso del tipo de socket correspondiente. La dirección debe tener el formato: "vsock:CID:PORT". Tenga en cuenta que, a diferencia de otros usos de vsock, el CID es obligatorio y no puede ser "VMADDR_CID_ANY". Tenga en cuenta que PID1 enviará los paquetes VSOCK desde un puerto privilegiado (es decir, inferior a 1024), como un intento de abordar las preocupaciones de que los procesos no privilegiados en el invitado puedan intentar enviar notificaciones maliciosas al host, llevándolo a tomar decisiones destructivas basadas en ellas.

Implementaciones Independientes

Tenga en cuenta que, si bien se debe preferir el uso de esta biblioteca para evitar la duplicación de código, también es posible reimplementar el simple protocolo de notificación de preparación sin dependencias externas, como se demuestra en los siguientes ejemplos autocontenidos de varios idiomas:

C 

/* SPDX-License-Identifier: MIT-0 */
/* Implementa el protocolo de notificación de systemd sin dependencias externas.
 * Soporta la notificación de preparación al iniciar y al recargar,
 * según el protocolo definido en:
 * https://www.freedesktop.org/software/systemd/man/latest/sd_notify.html
 * Este protocolo está garantizado como estable según:
 * https://systemd.io/PORTABILITY_AND_STABILITY/ */
#define _GNU_SOURCE 1
#include <errno.h>
#include <inttypes.h>
#include <signal.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdlib.h>
#include <stdio.h>
#include <string.h>
#include <sys/socket.h>
#include <sys/un.h>
#include <time.h>
#include <unistd.h>
#define _cleanup_(f) __attribute__((cleanup(f)))
static void closep(int *fd) {
  if (!fd || *fd < 0)
    return;
  close(*fd);
  *fd = -1;
}
static int notify(const char *message) {
  union sockaddr_union {
    struct sockaddr sa;
    struct sockaddr_un sun;
  } socket_addr = {
    .sun.sun_family = AF_UNIX,
  };
  size_t path_length, message_length;
  _cleanup_(closep) int fd = -1;
  const char *socket_path;
  /* Verifica el argumento primero */
  if (!message)
    return -EINVAL;
  message_length = strlen(message);
  if (message_length == 0)
    return -EINVAL;
  /* Si la variable no está establecida, el protocolo es una no-op */
  socket_path = getenv("NOTIFY_SOCKET");
  if (!socket_path)
    return 0; /* ¿No establecido? Nada que hacer */
  /* Solo AF_UNIX es compatible, con sockets de ruta o abstractos */
  if (socket_path[0] != '/' && socket_path[0] != '@')
    return -EAFNOSUPPORT;
  path_length = strlen(socket_path);
  /* Asegúrate de que hay espacio para el byte NUL */
  if (path_length >= sizeof(socket_addr.sun.sun_path))
    return -E2BIG;
  memcpy(socket_addr.sun.sun_path, socket_path, path_length);
  /* Soporte para socket abstracto */
  if (socket_addr.sun.sun_path[0] == '@')
    socket_addr.sun.sun_path[0] = 0;
  fd = socket(AF_UNIX, SOCK_DGRAM|SOCK_CLOEXEC, 0);
  if (fd < 0)
    return -errno;
  if (connect(fd, &socket_addr.sa, offsetof(struct sockaddr_un, sun_path) + path_length) != 0)
    return -errno;
  ssize_t written = write(fd, message, message_length);
  if (written != (ssize_t) message_length)
    return written < 0 ? -errno : -EPROTO;
  return 1; /* ¡Notificado! */
}
static int notify_ready(void) {
  return notify("READY=1");
}
static int notify_reloading(void) {
  /* Un buffer con longitud suficiente para formatear el valor máximo de UINT64. */
  char reload_message[sizeof("RELOADING=1\nMONOTONIC_USEC=18446744073709551615")];
  struct timespec ts;
  uint64_t now;
  /* Notifica a systemd que estamos recargando, incluyendo una marca de tiempo CLOCK_MONOTONIC en microsegundos
   * para que el programa sea compatible con un servicio Type=notify-reload. */
  if (clock_gettime(CLOCK_MONOTONIC, &ts) < 0)
    return -errno;
  if (ts.tv_sec < 0 || ts.tv_nsec < 0 ||
      (uint64_t) ts.tv_sec > (UINT64_MAX - (ts.tv_nsec / 1000ULL)) / 1000000ULL)
    return -EINVAL;
  now = (uint64_t) ts.tv_sec * 1000000ULL + (uint64_t) ts.tv_nsec / 1000ULL;
  if (snprintf(reload_message, sizeof(reload_message), "RELOADING=1\nMONOTONIC_USEC=%" PRIu64, now) < 0)
    return -EINVAL;
  return notify(reload_message);
}
static int notify_stopping(void) {
  return notify("STOPPING=1");
}
static volatile sig_atomic_t reloading = 0;
static volatile sig_atomic_t terminating = 0;
static void signal_handler(int sig) {
  if (sig == SIGHUP)
    reloading = 1;
  else if (sig == SIGINT || sig == SIGTERM)
    terminating = 1;
}
int main(int argc, char **argv) {
  struct sigaction sa = {
    .sa_handler = signal_handler,
    .sa_flags = SA_RESTART,
  };
  int r;
  /* Configura los manejadores de señales */
  sigemptyset(&sa.sa_mask);
  sigaction(SIGHUP, &sa, NULL);
  sigaction(SIGINT, &sa, NULL);
  sigaction(SIGTERM, &sa, NULL);
  /* Realiza más trabajo de inicialización del servicio aquí... */
  /* Ahora que todos los pasos de preparación están hechos, notifica la preparación */
  r = notify_ready();
  if (r < 0) {
    fprintf(stderr, "Fallo al notificar la preparación a $NOTIFY_SOCKET: %s\n", strerror(-r));
    return EXIT_FAILURE;
  }
  while (!terminating) {
    if (reloading) {
      reloading = false;
      /* Como característica separada pero relacionada, también podemos notificar al gestor
       * al recargar la configuración. Esto permite un seguimiento preciso del estado
       * y también la integración automática de 'systemctl reload' sin tener que
       * especificar manualmente una línea ExecReload= en el archivo de unidad. */
      r = notify_reloading();
      if (r < 0) {
        fprintf(stderr, "Fallo al notificar la recarga a $NOTIFY_SOCKET: %s\n", strerror(-r));
        return EXIT_FAILURE;
      }
      /* Realiza algún trabajo de reconfiguración aquí... */
      r = notify_ready();
      if (r < 0) {
        fprintf(stderr, "Fallo al notificar la preparación a $NOTIFY_SOCKET: %s\n", strerror(-r));
        return EXIT_FAILURE;
      }
    }
    /* Realiza algún trabajo de demonio aquí... */
    sleep(5);
  }
  r = notify_stopping();
  if (r < 0) {
    fprintf(stderr, "Fallo al reportar la terminación a $NOTIFY_SOCKET: %s\n", strerror(-r));
    return EXIT_FAILURE;
  }
  /* Realiza algún trabajo de apagado aquí... */
  return EXIT_SUCCESS;
}

Python 

#!/usr/bin/python
# SPDX-License-Identifier: MIT-0
#
# Implementa el protocolo de notificación de systemd sin dependencias externas.
# Soporta la notificación de preparación al iniciar y al recargar,
# según el protocolo definido en:
# https://www.freedesktop.org/software/systemd/man/latest/sd_notify.html
# Este protocolo está garantizado como estable según:
# https://systemd.io/PORTABILITY_AND_STABILITY/
import errno
import os
import signal
import socket
import sys
import time
reloading = False
terminating = False
def notify(message):
    if not message:
        raise ValueError("notify() requiere un mensaje")
    socket_path = os.environ.get("NOTIFY_SOCKET")
    if not socket_path:
        return
    if socket_path[0] not in ("/", "@"):
        raise OSError(errno.EAFNOSUPPORT, "Tipo de socket no soportado")
    # Maneja el socket abstracto.
    if socket_path[0] == "@":
        socket_path = "\0" + socket_path[1:]
    with socket.socket(socket.AF_UNIX, socket.SOCK_DGRAM | socket.SOCK_CLOEXEC) as sock:
        sock.connect(socket_path)
        sock.sendall(message)
def notify_ready():
    notify(b"READY=1")
def notify_reloading():
    microsecs = time.clock_gettime_ns(time.CLOCK_MONOTONIC) // 1000
    notify(f"RELOADING=1\nMONOTONIC_USEC={microsecs}".encode())
def notify_stopping():
    notify(b"STOPPING=1")
def reload(signum, frame):
    global reloading
    reloading = True
def terminate(signum, frame):
    global terminating
    terminating = True
def main():
    print("Realizando configuración inicial")
    global reloading, terminating
    # Configura los manejadores de señales.
    print("Configurando manejadores de señales")
    signal.signal(signal.SIGHUP, reload)
    signal.signal(signal.SIGINT, terminate)
    signal.signal(signal.SIGTERM, terminate)
    # Realiza cualquier otro trabajo de configuración aquí.
    # Una vez que toda la configuración esté hecha, notifica la preparación.
    print("Configuración terminada")
    notify_ready()
    print("Iniciando bucle")
    while not terminating:
        if reloading:
            print("Recargando")
            reloading = False
            # Soporta notificar al gestor al recargar la configuración.
            # Esto permite un seguimiento preciso del estado, así como
            # habilitar automáticamente 'systemctl reload' sin necesidad de
            # especificar manualmente una línea ExecReload= en el archivo de unidad.
            notify_reloading()
            # Realiza algún trabajo de reconfiguración aquí.
            print("Recarga terminada")
            notify_ready()
        # Realiza el trabajo real aquí...
        print("Durmiendo durante cinco segundos")
        time.sleep(5)
    print("Terminando")
    notify_stopping()
if __name__ == "__main__":
    sys.stdout.reconfigure(line_buffering=True)
    print("Iniciando aplicación")
    main()
    print("Aplicación detenida")

ENTORNO

$NOTIFY_SOCKET

Establecido por el gestor de servicios para procesos supervisados para notificación de estado y finalización de inicio. Esta variable de entorno especifica el socket con el que habla sd_notify(). Ver arriba para más detalles.

EJEMPLOS

Ejemplo 1. Notificación de Inicio

Cuando un servicio termina de iniciarse, podría emitir la siguiente llamada para notificar al gestor de servicios:

sd_notify(0, "READY=1");

Ejemplo 2. Notificación de Inicio Extendido

Un servicio podría enviar lo siguiente después de completar la inicialización:

sd_notifyf(0, "READY=1\n"
              "STATUS=Procesando solicitudes...\n"
              "MAINPID=%lu",
           (unsigned long) getpid());

Ejemplo 3. Notificación de Causa de Error

Un servicio podría enviar lo siguiente poco antes de salir, en caso de fallo:

sd_notifyf(0, "STATUS=Fallo al iniciar: %s\n"
              "ERRNO=%i",
           strerror_r(errnum, (char[1024]){}, 1024),
           errnum);

Ejemplo 4. Almacenar un Descriptor de Archivo en el Gestor de Servicios

Para almacenar un descriptor de archivo abierto en el gestor de servicios, para continuar la operación después de un reinicio del servicio sin perder estado, usa "FDSTORE=1":

sd_pid_notify_with_fds(0, 0, "FDSTORE=1\nFDNAME=foobar", &fd, 1);

Ejemplo 5. Eliminar condiciones de carrera

Cuando el cliente que envía las notificaciones no es generado por el gestor de servicios, puede salir demasiado rápido y el gestor de servicios puede no atribuirlas correctamente a la unidad. Para prevenir tales carreras, usa sd_notify_barrier() para sincronizar la recepción de todas las notificaciones enviadas antes de que se realice esta llamada.

sd_notify(0, "READY=1");
/* establecer tiempo de espera a 5 segundos */
sd_notify_barrier(0, 5 * 1000000);

sd_pid_notifyf_with_fds() y sd_notify_barrier() se añadieron en la versión 254.
