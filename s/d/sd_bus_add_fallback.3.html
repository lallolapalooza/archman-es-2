DESCRIPCIÓN

sd_bus_add_object_vtable() se utiliza para declarar atributos para la ruta de objeto path conectada a la conexión de bus bus bajo la interfaz interface. La tabla vtable puede contener declaraciones de propiedades usando SD_BUS_PROPERTY() o SD_BUS_WRITABLE_PROPERTY(), declaraciones de métodos usando SD_BUS_METHOD(), SD_BUS_METHOD_WITH_NAMES(), SD_BUS_METHOD_WITH_OFFSET(), o SD_BUS_METHOD_WITH_NAMES_OFFSET(), y declaraciones de señales usando SD_BUS_SIGNAL_WITH_NAMES() o SD_BUS_SIGNAL(), véase más abajo. El parámetro userdata contiene un puntero que se pasará a varias funciones de devolución de llamada. Puede especificarse como NULL si no se necesita ningún valor. Una interfaz puede tener cualquier número de vtables adjuntas a ella.

sd_bus_add_fallback_vtable() es similar a sd_bus_add_object_vtable(), pero se utiliza para registrar atributos de "fallback". Al buscar una declaración de atributo, primero se comprueban las rutas de objeto de bus registradas con sd_bus_add_object_vtable(). Si no se encuentra ninguna coincidencia, se comprueban las vtables de fallback para cada prefijo de la ruta de objeto de bus, es decir, eliminando sucesivamente los últimos componentes separados por barras. Esto permite que la vtable se utilice para un número arbitrario de objetos creados dinámicamente.

El parámetro find es una función que se utiliza para localizar el objeto de destino basándose en la ruta del objeto de bus path. Debe devolver 1 y establecer el parámetro de salida ret_found si se encuentra el objeto, devolver 0 si el objeto no se encontró, y devolver un código de error de estilo errno negativo o inicializar la estructura de error ret_error en caso de error. El puntero pasado en ret_found se utilizará como parámetro userdata para las funciones de devolución de llamada (desplazado por los desplazamientos offset especificados en las entradas de la vtable).

sd_bus_add_object() adjunta una devolución de llamada directamente a la ruta de objeto path. Una ruta de objeto puede tener cualquier número de devoluciones de llamada adjuntas. Cada devolución de llamada se antepone a la lista de devoluciones de llamada que siempre se llaman en orden. sd_bus_add_fallback() es similar a sd_bus_add_object() pero se aplica a rutas de fallback en su lugar.

sd_bus_add_filter() instala una devolución de llamada que se invoca para cada mensaje D-Bus entrante. Los filtros se pueden utilizar para manejar la lógica común a todos los mensajes recibidos por un servicio (por ejemplo, autenticación o autorización).

Cuando se recibe una solicitud, se llaman las devoluciones de llamada asociadas secuencialmente hasta que una devolución de llamada devuelve un entero distinto de cero. Devuelve cero desde una devolución de llamada para dar a otras devoluciones de llamada la oportunidad de procesar la solicitud. Las devoluciones de llamada se llaman en el siguiente orden: primero, se llaman las devoluciones de llamada globales instaladas con sd_bus_add_filter(). Segundo, se llaman las devoluciones de llamada adjuntas directamente a la ruta de objeto de la solicitud, seguidas de las devoluciones de llamada de métodos D-Bus adjuntas a la ruta de objeto de la solicitud, interfaz y miembro. Finalmente, se llaman las devoluciones de propiedad adjuntas a la ruta de objeto de la solicitud, interfaz y miembro. Si la devolución de llamada final devuelve cero, se genera un error de respuesta (a menos que se haya registrado explícitamente un manejador de objetos de fallback o de bus con sd_bus_add_object()).

y se envía de vuelta al llamador indicando que no se encontró ningún objeto coincidente para la solicitud.

Tenga en cuenta que puede devolver un entero positivo desde una función de retorno de llamada de método sin enviar una respuesta inmediatamente. Esto informa a sd-bus que la función de retorno de llamada asumirá la responsabilidad de responder a la solicitud sin obligar a la función de retorno de llamada a producir una respuesta de inmediato. Esto permite que una función de retorno de llamada realice cualquier cantidad de operaciones asíncronas necesarias para construir una respuesta. Sin embargo, si la producción de una respuesta tarda demasiado, la llamada al método expirará en el llamador. Esto solo está disponible para métodos y no para propiedades.

Si se invocó una función de retorno de llamada para manejar una solicitud que espera una respuesta y la función de retorno de llamada devuelve un valor negativo, el valor se interpreta como un código de error negativo de estilo errno y se envía de vuelta al llamador como un error de D-Bus, como si se hubiera llamado a sd_bus_reply_method_errno(3). Además, todas las funciones de retorno de llamada toman un parámetro de salida sd_bus_error que se puede usar para proporcionar información de error más detallada. Si ret_error se establece cuando la función de retorno de llamada finaliza, el error de D-Bus correspondiente se envía de vuelta al llamador como si se hubiera llamado a sd_bus_reply_method_error(3). Cualquier error almacenado en ret_error tiene prioridad sobre cualquier valor negativo devuelto por la misma función de retorno de llamada al determinar qué error enviar de vuelta al llamador. Use sd_bus_error_set(3) o una de sus variantes para establecer ret_error y devolver un entero negativo desde una función de retorno de llamada con una sola llamada a función. Para enviar una respuesta de error después de que una función de retorno de llamada haya finalizado, use sd_bus_reply_method_errno(3) o una de sus variantes.

Para todas las funciones, se crea internamente una ranura de coincidencia. Si el parámetro de salida slot es NULL, se crea un objeto de ranura "flotante", consulte sd_bus_slot_set_floating(3). De lo contrario, se devuelve un puntero al objeto de ranura. En ese caso, la referencia al objeto de ranura debe liberarse cuando la vtable ya no sea necesaria, consulte sd_bus_slot_unref(3).

El array sd_bus_vtable

El array consta de las estructuras de tipo sd_bus_vtable, pero nunca debe rellenarse manualmente, sino a través de una de las siguientes macros:

SD_BUS_VTABLE_START(flags), SD_BUS_VTABLE_END

Estos deben ser siempre el primer y último elemento. El parámetro flags se puede utilizar para establecer atributos que se apliquen a todo el array; consulte la sección "Flags" a continuación.

SD_BUS_METHOD_WITH_ARGS_OFFSET(), SD_BUS_METHOD_WITH_ARGS()

Declara un método D-Bus con el nombre member, argumentos args y resultado result. args espera una secuencia de pares tipo/nombre de argumento encapsulados en la macro SD_BUS_ARGS(). Los elementos en índices pares de esta lista describen los tipos de los argumentos del método. La firma del parámetro del método es la concatenación de todas las cadenas literales en índices pares de args. Si un método no tiene parámetros, pase SD_BUS_NO_ARGS a args. Los elementos en índices impares describen los nombres de los argumentos del método. result espera una secuencia de pares tipo/nombre encapsulados en la macro SD_BUS_RESULT() en el mismo formato que SD_BUS_ARGS(). La firma del resultado del método es la concatenación de todas las cadenas literales en índices pares de result. Si un método no tiene resultado, pase SD_BUS_NO_RESULT a result. Tenga en cuenta que se espera que los tipos de los argumentos sean cadenas literales entre comillas y los nombres de los argumentos sean cadenas literales sin comillas. La función manejadora handler debe ser del tipo sd_bus_message_handler_t. Se llamará para manejar los mensajes entrantes que llamen a este método. SD_BUS_METHOD_WITH_NAMES_OFFSET(), SD_BUS_METHOD_WITH_NAMES(), SD_BUS_METHOD_WITH_OFFSET(), SD_BUS_METHOD()

Declara un método D-Bus con el nombre member, firma de parámetros signature, firma de resultado result. Los parámetros in_names y out_names especifican los nombres de los argumentos de entrada y salida en la firma de la función. in_names y out_names deben crearse usando la macro SD_BUS_PARAM(), consulte a continuación. En todos los demás aspectos, esta macro se comporta exactamente igual que SD_BUS_METHOD_WITH_ARGS_OFFSET().

SD_BUS_METHOD_WITH_NAMES(), SD_BUS_METHOD_WITH_OFFSET() y SD_BUS_METHOD() son variantes que especifican un offset cero (el parámetro userdata se pasa sin cambios), dejan los nombres sin establecer (es decir, sin nombres de parámetro) o ambos.

Prefiera usar SD_BUS_METHOD_WITH_ARGS_OFFSET() y SD_BUS_METHOD_WITH_ARGS() sobre estas macros, ya que permiten especificar los tipos y nombres de los argumentos uno al lado del otro, lo que es menos propenso a errores que especificar primero todos los tipos de argumentos seguidos de la especificación de todos los nombres de argumentos.

SD_BUS_WRITABLE_PROPERTY(), SD_BUS_PROPERTY()

Declara una propiedad D-Bus con el nombre member y firma de valor signature. Los parámetros get y set son los métodos de obtención y establecimiento. Se llaman con un puntero que es el parámetro userdata pasado a la función de registro compensado por offset bytes. Los métodos de establecimiento y obtención se pueden omitir (especificar como NULL), si la propiedad es uno de los tipos básicos o "as" en caso de propiedades de solo lectura. Se proporcionará un establecedor y un obtendedor predeterminados, que simplemente copian el argumento entre esta variable y el mensaje.

SD_BUS_PROPERTY() se utiliza para definir una propiedad de solo lectura.

Flags

El parámetro flags se utiliza para especificar una combinación de **anotaciones de D-Bus**[1].

SD_BUS_VTABLE_DEPRECATED

Marca esta entrada de vtable como obsoleta usando la anotación org.freedesktop.DBus.Deprecated en los datos de introspección. Si se especifica para SD_BUS_VTABLE_START(), la anotación se aplica a la interfaz envolvente.

SD_BUS_VTABLE_HIDDEN

Oculta esta entrada de vtable. No se mostrará en los datos de introspección. Si se especifica para SD_BUS_VTABLE_START(), todas las entradas del array se ocultan.

SD_BUS_VTABLE_METHOD_NO_REPLY

Marca esta entrada de vtable como un método que no devolverá una respuesta usando la anotación org.freedesktop.DBus.Method.NoReply en los datos de introspección.

SD_BUS_VTABLE_PROPERTY_CONST, SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE, SD_BUS_VTABLE_PROPERTY_EMITS_INVALIDATION

Estos tres flags corresponden a diferentes valores de la anotación org.freedesktop.DBus.Property.EmitsChangedSignal, que especifica si la señal org.freedesktop.DBus.Properties.PropertiesChanged se emite cada vez que cambia la propiedad. SD_BUS_VTABLE_PROPERTY_CONST corresponde a const y significa que la propiedad nunca cambia durante la vida útil del objeto al que pertenece, por lo que no es necesario emitir ninguna señal. SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE corresponde a true y significa que se emite la señal. SD_BUS_VTABLE_PROPERTY_EMITS_INVALIDATION corresponde a invalidates y significa que se emite la señal, pero el valor no se incluye en la señal.

SD_BUS_VTABLE_PROPERTY_EXPLICIT

Marca esta entrada de propiedad de vtable como que requiere una solicitud explícita para que se muestre el valor (generalmente porque el valor es grande o lento de calcular). Esta entrada no se puede combinar con SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE y no se mostrará en las listas de propiedades de forma predeterminada (por ejemplo, busctl introspect). Esto corresponde a la anotación org.freedesktop.systemd1.Explicit en los datos de introspección.

SD_BUS_VTABLE_SENSITIVE

Marca esta entrada de método de vtable como que procesa datos sensibles. Cuando se establece, los mensajes de llamada de método entrantes y sus mensajes de respuesta salientes se marcan como sensibles usando sd_bus_message_sensitive(3), para que se eliminen de la memoria cuando se liberan.

sd_bus_add_object_vtable

Add a vtable for an object

Synopsis

#include <systemd/sd-bus.h>
int sd_bus_add_object_vtable(sd_bus *bus,
                             sd_bus_slot **slot,
                             const char *path,
                             const char *interface,
                             const sd_bus_vtable *vtable,
                             void *userdata);

Description

Registers a set of D-Bus method and signal handlers for a specific object path and interface. The vtable is an array of sd_bus_vtable structures, which must be NULL-terminated. The userdata pointer is passed to all handler functions.

The object path is specified in the path parameter, and the D-Bus interface name in the interface parameter. The slot parameter is optional. If it is not NULL, a pointer to the new slot object will be stored there. The slot object is an opaque handle which can be used later to remove the registered vtable using sd_bus_slot_unref(3).

If bus is connected to the system bus, the registered object will be owned by the user running the process. If it is connected to the session bus, the object will be owned by the user running the session.

To implement objects that are available on the session bus, use sd_bus_default(3) to get a connection to the session bus. To implement objects that are available on the system bus, use sd_bus_get_system(3).

The following flags may be passed in the flags field of sd_bus_vtable entries:

SD_BUS_VTABLE_START(flags)

The first entry in the vtable array. The flags field is a bitmask of SD_BUS_VTABLE_ALLOW_INTERACTIVE_AUTHORIZATION and SD_BUS_VTABLE_UNPRIVILEGED. These flags apply to all entries in the vtable unless overridden by an individual entry.

Same as SD_BUS_WRITABLE_PROPERTY_OFFSET(), with offset set to 0.

SD_BUS_READONLY_PROPERTY_NO_OFFSET(name, signature, getter, flags)

Same as SD_BUS_READONLY_PROPERTY_OFFSET(), with offset set to 0.

SD_BUS_VTABLE_END

Marks the end of the vtable array.

SD_BUS_VTABLE_OFFSET(member)

This macro expands to the offset of the member member within the userdata structure. It is used for the offset parameter of SD_BUS_METHOD_WITH_OFFSET, SD_BUS_SIGNAL_WITH_OFFSET, and SD_BUS_PROPERTY.

SD_BUS_VTABLE_DEPRECATED

Mark this vtable entry as deprecated. This will result in the org.freedesktop.DBus.Deprecated annotation being added to the introspection data.

SD_BUS_VTABLE_UNPRIVILEGED

Mark this vtable entry as unprivileged. Access to privileged entries is limited to users with appropriate capabilities as described below. In practice many vtable entries are marked as unprivileged, and either are open to everyone, or the decision whether to allow access is taken later, e.g. by delegating to polkit[2].

The whole bus may be marked as trusted, in which case annotations at the entry level are ignored, see sd_bus_set_trusted(3).

When not specified, the org.freedesktop.systemd1.Privileged annotation with value "true" will be shown in introspection data.

SD_BUS_VTABLE_UNPRIVILEGED may not be applied to read-only properties, but read access (to both read-only and writable properties) is always unrestricted.

Note that this page describes checks implemented in the D-Bus client. The D-Bus server has an additional policy that may permit or deny connections, see "CONFIGURATION FILE" in dbus-daemon(1).

SD_BUS_VTABLE_CAPABILITY(capability)

Access to this vtable entry will be allowed if the calling process has the capability capability, as described in sd_bus_query_sender_privilege(3). If used for SD_BUS_VTABLE_START(), provides a default for all entries in the array. If not specified, either for an individual entry or the whole array, CAP_SYS_ADMIN is checked by default. See capabilities(7) for information about capabilities.

Note that vtable entries may be marked as unprivileged and the whole bus may be marked as trusted, see the discussion of SD_BUS_VTABLE_UNPRIVILEGED above.

SD_BUS_VTABLE_ALLOW_INTERACTIVE_AUTHORIZATION

Mark this vtable entry as requiring interactive authorization. If the calling process does not have the necessary permissions, an authorization dialog will be shown. This flag has no effect if the entry is also marked as SD_BUS_VTABLE_UNPRIVILEGED.

The offset parameter passed to handler functions is determined slightly differently depending on whether SD_BUS_METHOD_WITH_OFFSET or similar macros are used. If the offset is explicitly passed, it is directly used as a pointer. If SD_BUS_VTABLE_OFFSET is used, the offset parameter passed to its associated handler functions is determined slightly differently: instead of adding the offset parameter of the entry to the user data pointer specified during vtable registration, the offset is passed directly, converted to a pointer, without taking the user data pointer specified during vtable registration into account.

Example 1. Create a simple listener on the bus

/* SPDX-License-Identifier: MIT-0 */
#define _GNU_SOURCE 1
#include <errno.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdlib.h>
#include <stdio.h>
#include <systemd/sd-bus.h>
#define _cleanup_(f) __attribute__((cleanup(f)))
typedef struct object {
  char *name;
  uint32_t number;
} object;
static int method(sd_bus_message *m, void *userdata, sd_bus_error *error) {
  int r;
  printf("Got called with userdata=%p\n", userdata);
  if (sd_bus_message_is_method_call(m,
                                    "org.freedesktop.systemd.VtableExample",
                                    "Method4"))
    return 1;
  const char *string;
  r = sd_bus_message_read(m, "s", &string);
  if (r < 0) {
    fprintf(stderr, "sd_bus_message_read() failed: %s\n", strerror(-r));
    return 0;
  }
  r = sd_bus_reply_method_return(m, "s", string);
  if (r < 0) {
    fprintf(stderr, "sd_bus_reply_method_return() failed: %s\n", strerror(-r));
    return 0;
  }
  return 1;
}
static const sd_bus_vtable vtable[] = {
        SD_BUS_VTABLE_START(0),
        SD_BUS_METHOD(
            "Method1", "s", "s", method, 0),
        SD_BUS_METHOD_WITH_NAMES_OFFSET(
            "Method2",
            "so", SD_BUS_PARAM(string) SD_BUS_PARAM(path),
            "s", SD_BUS_PARAM(returnstring),
            method, offsetof(object, number),
            SD_BUS_VTABLE_DEPRECATED),
        SD_BUS_METHOD_WITH_ARGS_OFFSET(
            "Method3",
            SD_BUS_ARGS("s", string, "o", path),
            SD_BUS_RESULT("s", returnstring),
            method, offsetof(object, number),
            SD_BUS_VTABLE_UNPRIVILEGED),
        SD_BUS_METHOD_WITH_ARGS(
            "Method4",
            SD_BUS_NO_ARGS,
            SD_BUS_NO_RESULT,
            method,
            SD_BUS_VTABLE_UNPRIVILEGED),
        SD_BUS_SIGNAL(
            "Signal1",
            "so",
            0),
        SD_BUS_SIGNAL_WITH_NAMES(
            "Signal2",
            "so", SD_BUS_PARAM(string) SD_BUS_PARAM(path),
            0),
        SD_BUS_SIGNAL_WITH_ARGS(
            "Signal3",
            SD_BUS_ARGS("s", string, "o", path),
            0),
        SD_BUS_WRITABLE_PROPERTY(
            "AutomaticStringProperty", "s", NULL, NULL,
            offsetof(object, name),
            SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE),
        SD_BUS_WRITABLE_PROPERTY(
            "AutomaticIntegerProperty", "u", NULL, NULL,
            offsetof(object, number),
            SD_BUS_VTABLE_PROPERTY_EMITS_INVALIDATION),
        SD_BUS_VTABLE_END
};
int main(int argc, char **argv) {
  _cleanup_(sd_bus_flush_close_unrefp) sd_bus *bus = NULL;
  int r;
  sd_bus_default(&bus);
  object object = { .number = 666 };
  object.name = strdup("name");
  if (!object.name) {
    fprintf(stderr, "OOM\n");
    return EXIT_FAILURE;
  }
  r = sd_bus_add_object_vtable(bus, NULL,
                               "/org/freedesktop/systemd/VtableExample",
                               "org.freedesktop.systemd.VtableExample",
                               vtable,
                               &object);
  if (r < 0) {
    fprintf(stderr, "sd_bus_add_object_vtable() failed: %s\n", strerror(-r));
    return EXIT_FAILURE;
  }
  r = sd_bus_request_name(bus,
                          "org.freedesktop.systemd.VtableExample",
                          0);
  if (r < 0) {
    fprintf(stderr, "sd_bus_request_name() failed: %s\n", strerror(-r));
    return EXIT_FAILURE;
  }
  for (;;) {
    r = sd_bus_wait(bus, UINT64_MAX);
    if (r < 0) {
      fprintf(stderr, "sd_bus_wait() failed: %s\n", strerror(-r));
      return EXIT_FAILURE;
    }
    r = sd_bus_process(bus, NULL);
    if (r < 0) {
      fprintf(stderr, "sd_bus_process() failed: %s\n", strerror(-r));
      return EXIT_FAILURE;
    }
  }
  r = sd_bus_release_name(bus, "org.freedesktop.systemd.VtableExample");
  if (r < 0) {
    fprintf(stderr, "sd_bus_release_name() failed: %s\n", strerror(-r));
    return EXIT_FAILURE;
  }
  free(object.name);
  return 0;
}

One of the required parameters is NULL or invalid. A reserved D-Bus interface was passed as the interface parameter.

-ENOPKG

The bus cannot be resolved.

-ECHILD

The bus was created in a different process, library or module instance.

-ENOMEM

Memory allocation failed.

-EPROTOTYPE

sd_bus_add_object_vtable() and sd_bus_add_fallback_vtable() have been both called for the same bus object path, which is not allowed.

-EEXIST

This vtable has already been registered for this interface and path.

sd_bus_add_fallback.3.en - Arch Linux

NAME

sd_bus_add_fallback, sd_bus_add_fallback_vtable — Add a fallback object implementation for a service

SYNOPSIS

#include <systemd/sd-bus.h>

int sd_bus_add_fallback(sd_bus *bus, const char *path,
                        const char *interface,
                        sd_bus_message_handler_t handler,
                        void *userdata);
int sd_bus_add_fallback_vtable(sd_bus *bus, const char *path,
                               const char *interface,
                               const sd_bus_vtable *vtable,
                               void *userdata);

DESCRIPTION

The D-Bus message bus is a central system for inter-process communication. Services register implementations for objects under specific paths on the bus, identified by interfaces. These implementations handle requests directed at these objects.

Sometimes, a service might be running in multiple instances, or there might be multiple services that can provide the same functionality. In such cases, it is desirable to have a "fallback" implementation. When a client sends a request for an object, the bus daemon checks if any service has registered a specific implementation for that object.

If no specific implementation is found, the bus daemon will then check for fallback implementations. A fallback implementation is registered for a specific interface but a general object path prefix. If a client requests an object path that matches the prefix (e.g. /com/example/Foo matches the prefix /com/example), and no specific implementation is found for the requested object, the fallback implementation will be invoked.

This allows for a service to act as a general provider of certain interfaces, handling requests for objects that are not specifically implemented by other services.

The sd_bus_add_fallback function registers a general message handler (handler) for all methods and signals of the given interface, for any object path that starts with the given path prefix. The path prefix must end with a '/' character.

The sd_bus_add_fallback_vtable function is similar, but registers a set of method handlers defined in the vtable. This is a more structured way to register implementations.

The interface parameter is the name of the D-Bus interface for which this is a fallback implementation (e.g. org.freedesktop.DBus.ObjectManager).

The path parameter is the object path prefix. It must end with a slash character (e.g. /com/example/).

The handler parameter is a pointer to a function of type sd_bus_message_handler_t, which will be called when a message is received for an object path matching the prefix and the specified interface, and for which no specific implementation exists. The handler function has the signature:

int (*sd_bus_message_handler_t)(sd_bus_message *m, void *userdata);

The vtable parameter is a pointer to an array of sd_bus_vtable(3) structures, describing the methods implemented by the fallback object. The array must be terminated by a zero entry.

The userdata parameter is a user-provided pointer that will be passed to the handler function or through the vtable methods.

These functions should be called on a bus object obtained via sd_bus_open_user(3), sd_bus_open_system(3), or sd_bus_add_node(3).

Note that fallback objects are only considered if no specific object implementation is found for the requested object path. This means that if a service explicitly registers an implementation for /com/example/MyObject, that specific implementation will be used, and any fallback for /com/example/ will not be invoked for that object path.

EXAMPLES

Registering a fallback handler for all objects implementing the org.example.FallbackInterface under the path prefix /org/example/:

int ret;
sd_bus *bus = NULL;

ret = sd_bus_open_user(&bus);
if (ret < 0) {
    fprintf(stderr, "Failed to connect to bus: %s\n", strerror(-ret));
    exit(1);
}

ret = sd_bus_add_fallback(bus, "/org/example/", "org.example.FallbackInterface",
                          my_fallback_handler, NULL);
if (ret < 0) {
    fprintf(stderr, "Failed to add fallback: %s\n", strerror(-ret));
    goto finish;
}

// ... event loop ...

finish:
sd_bus_unref(bus);

RETURN VALUE

On success, sd_bus_add_fallback and sd_bus_add_fallback_vtable return 0. On failure, they return a negative error number.

NOTES

The sd_bus_add_fallback and sd_bus_add_fallback_vtable functions are available as a shared library, which can be compiled against and linked to with the libsystemd pkg-config(1) file.

The code described here uses getenv(3), which is declared to be not multi-thread-safe. This means that the code calling the functions described here must not call setenv(3) from a parallel thread. It is recommended to only do calls to setenv() from an early phase of the program when no other threads have been started.
