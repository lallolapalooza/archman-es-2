SD_EVENT_ADD_MEMORY_PRESSURE(3) sd_event_add_memory_pressure SD_EVENT_ADD_MEMORY_PRESSURE(3)

NOMBRE

sd_event_add_memory_pressure, sd_event_source_set_memory_pressure_type, sd_event_source_set_memory_pressure_period, sd_event_trim_memory - Añadir y configurar una fuente de eventos que se ejecuta como resultado de la presión de memoria

SINOPSIS

#include <systemd/sd-event.h>
typedef struct sd_event_source sd_event_source;

int sd_event_add_memory_pressure(sd_event *event, sd_event_source **ret_source, sd_event_handler_t handler, void *userdata);

int sd_event_source_set_memory_pressure_type(sd_event_source *source, const char *type);

int sd_event_source_set_memory_pressure_period(sd_event_source *source, uint64_t threshold_usec, uint64_t window_usec);

int sd_event_trim_memory(void);

DESCRIPCIÓN

sd_event_add_memory_pressure() añade una nueva fuente de eventos que se activa cuando se detecta presión de memoria. Esta funcionalidad está construida alrededor de la lógica de Pressure Stall Information (PSI)[1] del kernel de Linux.

Espera un objeto de bucle de eventos como primer parámetro, y devuelve el objeto de fuente de eventos asignado en el segundo parámetro, si tiene éxito. El parámetro handler es una función a llamar cuando se detecta presión de memoria, o NULL. A la función handler se le pasará el puntero userdata, que puede ser elegido libremente por el llamador. El handler puede devolver negativo para señalar un error (ver abajo), otros valores de retorno son ignorados. Si handler es NULL, se utilizará un handler por defecto que compacta las cachés de asignación mantenidas por libsystemd y también por glibc (a través de malloc_trim(3)).

Para destruir un objeto de fuente de eventos use sd_event_source_unref(3), pero tenga en cuenta que la fuente de eventos solo se elimina del bucle de eventos cuando se sueltan todas las referencias a la fuente de eventos. Para asegurarse de que una fuente de eventos no se dispare más, incluso si todavía está referenciada, deshabilite la fuente de eventos usando sd_event_source_set_enabled(3) con SD_EVENT_OFF.

Si el segundo parámetro de sd_event_add_memory_pressure() es NULL, no se devuelve ninguna referencia al objeto de fuente de eventos. En este caso, la fuente de eventos se considera "flotante" y se destruirá implícitamente cuando el propio bucle de eventos sea destruido.

La fuente de eventos se activará según la siguiente lógica:

1.Si las variables de entorno $MEMORY_PRESSURE_WATCH/$MEMORY_PRESSURE_WRITE están establecidas en el momento en que se crea la fuente de eventos, observará el archivo, FIFO o socket AF_UNIX especificado a través de $MEMORY_PRESSURE_WATCH (que debe contener un nombre de ruta absoluta) para eventos POLLPRI (en caso de ser un archivo regular) o POLLIN (de lo contrario). Después de abrir el inodo, escribirá los datos Base64 (decodificados) proporcionados a través de $MEMORY_PRESSURE_WRITE en él antes de comenzar a hacer polling sobre él (la variable puede no estar establecida en cuyo caso esto se omite). Típicamente, si se usa, $MEMORY_PRESSURE_WATCH contendrá una ruta como /proc/pressure/memory o una ruta a un archivo memory.pressure específico en el sistema de archivos de control de grupos (cgroupfs).
2.Si estas variables de entorno no están establecidas, se utiliza el archivo de interfaz PSI a nivel local memory.pressure del grupo de control en el que se está ejecutando el proceso invocador.
3.Si ese archivo no existe, se observa en su lugar el archivo de interfaz PSI a nivel del sistema /proc/pressure/memory.

O en otras palabras: preferiblemente se utiliza cualquier configuración explícita pasada por un gestor de servicios (o similar) como fuente de notificación, antes de recurrir a notificaciones locales del servicio, y finalmente a notificaciones globales del sistema.

Se recomienda a los servicios y aplicaciones que se comportan bien que reaccionen a los eventos de presión de memoria ejecutando una o más de las siguientes operaciones, con el fin de garantizar un comportamiento óptimo incluso en sistemas cargados y con recursos limitados:

•Liberar cachés de asignación como malloc_trim() o similar, tanto implementadas en las bibliotecas consumidas por el programa como en cachés de asignación privadas del propio programa.
•Liberar cualquier otra forma de cachés en memoria que se puedan recuperar fácilmente si es necesario (por ejemplo, cachés de navegador).
•Terminar hilos o procesos de trabajo inactivos, o similar.
•Incluso salir completamente del programa si está inactivo y se puede iniciar automáticamente cuando sea necesario (por ejemplo, mediante activación por socket o bus).

Cualquiera de las operaciones sugeridas debería ayudar a aliviar las situaciones de presión de memoria y permitir que el sistema progrese al recuperar la memoria para otros fines.

Esta fuente de eventos típicamente se activa en momentos de parada por presión de memoria, es decir, cuando ya se ha observado una latencia operativa por encima de un umbral configurado. Esto debe tenerse en cuenta al discutir si la latencia posterior para readquirir cualquier recurso liberado es aceptable: generalmente es más importante pensar en las latencias que ya ocurrieron que en las que vendrán en el futuro.

Las funciones sd_event_source_set_memory_pressure_type() y sd_event_source_set_memory_pressure_period() se pueden usar para ajustar los parámetros de PSI para las notificaciones de presión. La primera toma como segundo parámetro "some" o "full", la segunda toma umbrales y períodos de tiempo en microsegundos como parámetros. Para detalles sobre estos tres parámetros, consulte la documentación de PSI. Tenga en cuenta que estas dos llamadas deben invocarse inmediatamente después de asignar la fuente de eventos, ya que deben configurarse antes de que comience el polling. Tenga en cuenta también que estas llamadas fallarán si los parámetros de presión de memoria se han pasado a través de las variables de entorno $MEMORY_PRESSURE_WATCH/$MEMORY_PRESSURE_WRITE (o en otras palabras: la configuración proporcionada por un gestor de servicios gana sobre la configuración interna).

La función sd_event_trim_memory() libera varias cachés de asignación internas mantenidas por libsystemd e invoca malloc_trim(3) de glibc. Esto hace que la operación ejecutada cuando el parámetro de la función handler de sd_event_add_memory_pressure se pasa como NULL sea directamente accesible para su invocación en cualquier momento (ver arriba). Esta función registrará un mensaje de registro estructurado a nivel LOG_DEBUG (con el ID de mensaje f9b0be465ad540d0850ad32172d57c21) sobre la operación de presión de memoria.

Para más detalles, consulte Manejo de Presión de Memoria en systemd[2].

VALOR DE RETORNO

En caso de éxito, estas funciones devuelven 0 o un entero positivo. En caso de error, devuelven un código de error negativo estilo errno.

Errores

Los errores devueltos pueden indicar los siguientes problemas:

-ENOMEM

Memoria insuficiente para asignar un objeto.

Añadido en la versión 254.

-EINVAL

Se ha pasado un argumento inválido.

Añadido en la versión 254.

-EHOSTDOWN

La variable $MEMORY_PRESSURE_WATCH se ha establecido en la cadena literal /dev/null, para deshabilitar explícitamente el manejo de presión de memoria.

Añadido en la versión 254.

-EBADMSG

La variable $MEMORY_PRESSURE_WATCH se ha establecido en una cadena inválida, por ejemplo una ruta relativa en lugar de una ruta absoluta.

Añadido en la versión 254.

-ENOTTY

La variable $MEMORY_PRESSURE_WATCH apunta a un archivo regular fuera de los sistemas de archivos procfs o cgroupfs.

Añadido en la versión 254.

-EOPNOTSUPP

No se ha especificado ninguna configuración a través de $MEMORY_PRESSURE_WATCH y el kernel local no admite la interfaz PSI.

Añadido en la versión 254.

-EBUSY

Esto lo devuelven sd_event_source_set_memory_pressure_type() y sd_event_source_set_memory_pressure_period() si se invocan en fuentes de eventos en un momento posterior al de su asignación inmediata.

Añadido en la versión 254.

-ESTALE

El bucle de eventos ya ha terminado.

Añadido en la versión 2

sd_event_source_set_memory_pressure_period(3) — systemd manual pages

NAME

sd_event_source_set_memory_pressure_period, sd_event_add_memory_pressure, sd_event_source_set_memory_pressure_type, sd_event_trim_memory — Add a memory pressure event source, configure memory pressure event source properties, and trim memory

SYNOPSIS

#include <systemd/sd-event.h>

int sd_event_add_memory_pressure(sd_event *event, const char *path, sd_event_handler_t handler, void *userdata);

int sd_event_source_set_memory_pressure_type(sd_event_source *source, uint64_t type);

int sd_event_source_set_memory_pressure_period(sd_event_source *source, useconds_t usec);

int sd_event_trim_memory(sd_event *event, uint64_t amount);

DESCRIPTION

The sd_event_add_memory_pressure() function may be used to add a new event source to the event loop instance event that monitors memory pressure events on the system. The path parameter specifies the PSI path (e.g. "/proc/pressure/memory") to monitor.

The handler is the callback function to be invoked when memory pressure is detected. The userdata parameter is passed to the handler.

The sd_event_source_set_memory_pressure_type() function configures the type of the event source source. This should be one of the MEMORY_PRESSURE_TYPE_* flags defined in <systemd/sd-event.h>. Currently, only MEMORY_PRESSURE_TYPE_READ is supported, which corresponds to reading the PSI values periodically.

The sd_event_source_set_memory_pressure_period() function configures the polling interval for the memory pressure event source source. The interval is specified in microseconds.

The sd_event_trim_memory() function may be used to trigger memory trimming. The amount parameter specifies the desired amount of memory in bytes to trim. This function is intended for testing and debugging purposes.

Added in version 254.

RETURN VALUE

On success, sd_event_add_memory_pressure(), sd_event_source_set_memory_pressure_type(), sd_event_source_set_memory_pressure_period(), and sd_event_trim_memory() return a non-negative event source or error code. On failure, they return a negative error number.

Possible error codes are:

-EINVAL
Invalid argument supplied.
-ENOMEM
Out of memory.
-EPERM
Operation not permitted.
-ESTALE
The event loop instance is stale and was created in a different process.
-EXDEV
The event loop instance is stale and was created in a different library or module instance.

The following error codes are possible in addition to the general list above:

-ECHILD

The event loop has been created in a different process, library or module instance.

Added in version 254.

-EDOM

The passed event source is not a signal event source.

Added in version 254.

NOTES

Functions described here are available as a shared library, which can be compiled against and linked to with the libsystemd pkg-config(1) file.

The code described here uses getenv(3), which is declared to be not multi-thread-safe. This means that the code calling the functions described here must not call setenv(3) from a parallel thread. It is recommended to only do calls to setenv() from an early phase of the program when no other threads have been started.
