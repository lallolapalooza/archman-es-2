NOMBRE

sd_event_add_defer, sd_event_add_post, sd_event_add_exit, sd_event_handler_t - Añadir fuentes de eventos estáticas a un bucle de eventos

SINOPSIS

#include <systemd/sd-event.h>
typedef struct sd_event_source sd_event_source;

typedef int (*sd_event_handler_t)(sd_event_source *s, void *userdata);

int sd_event_add_defer(sd_event *event, sd_event_source **source, sd_event_handler_t handler, void *userdata);

int sd_event_add_post(sd_event *event, sd_event_source **source, sd_event_handler_t handler, void *userdata);

int sd_event_add_exit(sd_event *event, sd_event_source **source, sd_event_handler_t handler, void *userdata);

DESCRIPCIÓN

Estas tres funciones añaden nuevas fuentes de eventos estáticas a un bucle de eventos. El objeto del bucle de eventos se especifica en el parámetro event, y el objeto de la fuente de eventos se devuelve en el parámetro source. Las fuentes de eventos se habilitan estáticamente y se "dispararán" cuando se ejecute el bucle de eventos y se cumplan las condiciones descritas a continuación.

El handler es una función a llamar o NULL. La función handler recibirá el puntero userdata, que puede ser elegido libremente por el llamador. El handler puede devolver negativo para indicar un error (ver abajo); se ignoran otros valores de retorno. Si handler es NULL, se utilizará un handler predeterminado que llama a sd_event_exit(3).

sd_event_add_defer() añade una nueva fuente de eventos que se gestionará instantáneamente, antes de que el bucle de eventos vuelva a dormir y espere nuevos eventos. Por defecto, el handler se llamará una vez (SD_EVENT_ONESHOT). Tenga en cuenta que si la fuente de eventos se establece en SD_EVENT_ON, el bucle de eventos nunca volverá a dormir, sino que llamará continuamente al handler, posiblemente intercalado con otras fuentes de eventos.

sd_event_add_post() añade una nueva fuente de eventos que se ejecuta antes de que el bucle de eventos duerma y espere nuevos eventos, pero solo después de que al menos otra fuente de eventos no-post haya sido gestionada. Por defecto, la fuente se habilita permanentemente (SD_EVENT_ON). Tenga en cuenta que este tipo de fuente de eventos permitirá que el bucle de eventos vuelva a dormir, incluso si se establece en SD_EVENT_ON, siempre que ninguna otra fuente de eventos se active nunca.

sd_event_add_exit() añade una nueva fuente de eventos que se gestionará cuando el bucle de eventos se termine con sd_event_exit(3).

La función sd_event_source_set_enabled(3) puede usarse para habilitar la fuente de eventos permanentemente (SD_EVENT_ON) o para hacer que se dispare solo una vez (SD_EVENT_ONESHOT).

Si la función handler devuelve un código de error negativo, se deshabilitará después de la invocación, incluso si se solicitó el modo SD_EVENT_ON anteriormente, o provocará la terminación del bucle, ver sd_event_source_set_exit_on_failure(3).

Para destruir un objeto de fuente de eventos, use sd_event_source_unref(3), pero tenga en cuenta que la fuente de eventos solo se elimina del bucle de eventos cuando se sueltan todas las referencias a ella. Para asegurarse de que una fuente de eventos no se dispare más, incluso cuando todavía hay una referencia a ella, considere establecer la fuente de eventos en SD_EVENT_OFF con sd_event_source_set_enabled(3).

Si el segundo parámetro de estas funciones se pasa como NULL, no se devuelve ninguna referencia al objeto de la fuente de eventos. En este caso, la fuente de eventos se considera "flotante" y se destruirá implícitamente cuando se destruya el propio bucle de eventos.

Si el parámetro handler para sd_event_add_defer() o sd_event_add_post() es NULL, y la fuente de eventos se dispara, esto se considerará una solicitud para salir del bucle de eventos. En este caso, el parámetro userdata, convertido a entero, se pasará como parámetro de código de salida a sd_event_exit(3). Una funcionalidad similar no está disponible para sd_event_add_exit(), ya que estos tipos de fuentes de eventos solo se gestionan al salir de todos modos.

VALOR DE RETORNO

En caso de éxito, estas funciones devuelven 0 o un entero positivo. En caso de fallo, devuelven un código de error negativo estilo errno.

Errores

Los errores devueltos pueden indicar los siguientes problemas:

-ENOMEM

No hay suficiente memoria para asignar un objeto.

-EINVAL

Se pasó un argumento no válido.

-ESTALE

El bucle de eventos ya está terminado.

-ECHILD

El bucle de eventos se creó en un proceso, biblioteca o instancia de módulo diferente.

NOTAS

Las funciones descritas aquí están disponibles como una biblioteca compartida, que se puede compilar y enlazar con el archivo libsystemd pkg-config(1).

El código descrito aquí utiliza getenv(3), que se declara como no seguro para hilos múltiples. Esto significa que el código que llama a las funciones descritas aquí no debe llamar a setenv(3) desde un hilo paralelo. Se recomienda hacer las llamadas a setenv() solo desde una fase temprana del programa cuando no se hayan iniciado otros hilos.

HISTORIA

sd_event_add_defer(), sd_event_add_post(), sd_event_add_exit(), y sd_event_handler_t() se añadieron en la versión 217.

sd_event_add_defer(3)

sd_event_add_defer(3) sd_event_add_defer(3)

NAME

sd_event_add_defer - Añadir un evento diferido al bucle de eventos

SYNOPSIS

#include <systemd/sd-event.h>

int sd_event_add_defer(sd_event *event, sd_event_source **source, sd_event_handler_t *callback, void *userdata, uint64_t usec);

DESCRIPTION

El hook sd_event_add_defer() se utiliza para añadir un evento diferido al bucle de eventos especificado por event.

El hook se ejecutará después de que el bucle de eventos haya procesado todos los eventos actualmente disponibles y la llamada a sd_event_dispatch() esté a punto de regresar. Esto es útil para realizar operaciones que deben ejecutarse tan pronto como sea posible, pero que no deben bloquear el bucle de eventos principal.

Si se proporciona source, se almacenará un puntero al objeto fuente recién creado allí.

callback es un puntero a la función que se llamará cuando el evento se active. La función callback toma tres argumentos: el evento del que forma parte, el ID fuente y los datos del usuario proporcionados por userdata. Debe devolver un valor entero: si devuelve un valor positivo, el evento se volverá a añadir al bucle de eventos para su posterior ejecución; si devuelve 0, el evento se eliminará del bucle de eventos después de su ejecución; si devuelve un valor negativo, se producirá un error.

userdata se puede utilizar para pasar datos específicos de la aplicación a la función callback.

usec especifica el retardo mínimo en microsegundos hasta que el evento puede activarse. Si se establece en 0, el evento se activará lo antes posible.

ARGUMENTS

  • event: El bucle de eventos al que se añadirá el evento diferido.
  • source: Un puntero a un puntero `sd_event_source *` donde se almacenará la nueva fuente de evento. Puede ser `NULL`.
  • callback: La función a llamar cuando el evento se active.
  • userdata: Datos definidos por el usuario para pasar a la función callback.
  • usec: El retardo mínimo en microsegundos.

RETURN VALUE

En caso de éxito, sd_event_add_defer() devuelve 0 o un valor positivo. En caso de error, devuelve un valor negativo, donde se puede encontrar más información sobre el error en la variable global errno.

NOTES

Los eventos diferidos se procesan en el orden en que se añadieron al bucle de eventos.

Es importante tener en cuenta que los eventos diferidos se ejecutan *después* de que se hayan procesado todos los eventos pendientes. Esto significa que si se añaden muchos eventos diferidos en rápida sucesión, podrían no ejecutarse hasta que se complete el procesamiento de los eventos actuales.

HISTORY

sd_event_add_defer() estuvo disponible primero en la versión 237 de systemd.
