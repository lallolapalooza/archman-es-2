sd_listen_fds_with_names(3)

Paquete: systemd-libs

Licencias: LGPL-2.1-or-later, CC0-1.0, GPL-2.0-or-later WITH Linux-syscall-note

SD_LISTEN_FDS(3) sd_listen_fds SD_LISTEN_FDS(3)

NOMBRE

sd_listen_fds, sd_listen_fds_with_names, SD_LISTEN_FDS_START - Comprobar descriptores de archivo pasados por el gestor del sistema

SINOPSIS

#include <systemd/sd-daemon.h>
#define SD_LISTEN_FDS_START 3

int sd_listen_fds(int unset_environment);

int sd_listen_fds_with_names(int unset_environment, char*** names);

DESCRIPCIÓN

sd_listen_fds() puede ser invocada por un demonio para comprobar los descriptores de archivo pasados por el gestor de servicios como parte de la lógica de activación por sockets y almacenamiento de descriptores de archivo. Devuelve el número de descriptores de archivo recibidos. Si no se han recibido descriptores de archivo, se devuelve cero. El primer descriptor de archivo se puede encontrar en el descriptor de archivo número 3 (es decir, SD_LISTEN_FDS_START), los descriptores restantes siguen en 4, 5, 6, ..., si los hay.

Los descriptores de archivo pasados de esta manera pueden ser cerrados a voluntad por los procesos que los reciben: depende de los propios procesos cerrarlos después de su uso o dejarlos abiertos hasta que el proceso termine (en cuyo caso el kernel los cierra automáticamente). Tenga en cuenta que los descriptores de archivo recibidos por los demonios son duplicados de los descriptores de archivo que el gestor de servicios asignó y enlazó originalmente y de los cuales continuamente mantiene una copia (excepto si se usa Accept=yes). Esto significa que los cambios en las opciones del socket y otros cambios realizados en los sockets también serán visibles para el gestor de servicios. Lo más importante es que, en general, no es una buena idea invocar shutdown(2) en dichos sockets, ya que cerrará la comunicación en el descriptor de archivo que el gestor de servicios mantiene para el mismo socket. Tenga en cuenta también que si un demonio se reinicia (y sus sockets asociados no), recibirá descriptores de archivo para los mismos sockets que las invocaciones anteriores, por lo que todas las opciones de socket aplicadas entonces seguirán aplicándose.

Si un demonio recibe más de un descriptor de archivo, se pasarán en el mismo orden que se configuran en el archivo de unidad de socket de systemd (consulte systemd.socket(5) para más detalles) — si solo hay un archivo de este tipo (ver más abajo). No obstante, se recomienda verificar los tipos de socket correctos antes de utilizarlos. Para simplificar esta comprobación, se proporcionan las funciones sd_is_fifo(3), sd_is_socket(3), sd_is_socket_inet(3), sd_is_socket_unix(3). Con el fin de maximizar la flexibilidad, se recomienda hacer estas comprobaciones lo más flexibles posible sin permitir configuraciones incorrectas. Es decir, a menudo, el número de puerto real al que está enlazado un socket importa poco para que el servicio funcione, por lo que no debería verificarse. Por otro lado, si un socket es un socket de datagrama o de flujo importa mucho para la lógica del programa más común y debería comprobarse.

Esta llamada a función establecerá la bandera FD_CLOEXEC para todos los descriptores de archivo pasados para evitar la herencia adicional a los hijos del proceso que llama.

Si varias unidades de socket activan el mismo servicio, el orden de los descriptores de archivo pasados a su proceso principal no está definido. Si se han pasado descriptores de archivo adicionales al gestor de servicios mediante mensajes de "FDSTORE=1" de sd_pid_notify_with_fds(3), estos descriptores de archivo se pasan al final, en orden arbitrario y con duplicados eliminados.

Si el parámetro unset_environment no es cero, sd_listen_fds() anulará las variables de entorno $LISTEN_FDS, $LISTEN_PID y $LISTEN_FDNAMES antes de devolver (independientemente de si la propia llamada a la función tuvo éxito o no). Las llamadas posteriores a sd_listen_fds() devolverán entonces cero, pero las variables ya no serán heredadas por los procesos hijos.

sd_listen_fds_with_names() es como sd_listen_fds(), pero opcionalmente también devuelve una matriz de cadenas con nombres de identificación para los descriptores de archivo pasados, si están disponibles y el parámetro names no es NULL. Esta información se lee de la variable $LISTEN_FDNAMES, que puede contener una lista de nombres separados por dos puntos. Para los servicios activados por socket, estos nombres se pueden configurar con el ajuste FileDescriptorName= en los archivos de unidad de socket, consulte systemd.socket(5) para más detalles. Para los descriptores de archivo introducidos en el almacén de descriptores de archivo (ver arriba), el nombre se establece a través del campo FDNAME= transmitido a través de sd_pid_notify_with_fds(). El caso de uso principal para estos nombres son los servicios que aceptan una variedad de descriptores de archivo que no son reconocibles solo con funciones como sd_is_socket() y, por lo tanto, requieren identificación a través de un nombre. Se recomienda depender de descriptores de archivo nombrados solo si la identificación a través de sd_is_socket() y llamadas relacionadas no es suficiente. Tenga en cuenta que los nombres utilizados no son únicos en ningún sentido. La matriz de cadenas devuelta tiene tantas entradas como descriptores de archivo se hayan recibido, más un puntero NULL final que termina la matriz. El llamante debe liberar la matriz en sí y cada uno de sus elementos con la llamada free() de libc después de su uso. Si el parámetro names es NULL, la llamada es totalmente equivalente a sd_listen_fds().

Bajo condiciones específicas, se devuelven los siguientes nombres automáticos de descriptores de archivo:

Tabla 1. Nombres especiales

Nombre Descripción
"unknown" El proceso no recibió ningún nombre para el descriptor de archivo específico del gestor de servicios.
"stored" El descriptor de archivo se origina en el almacén de descriptores de archivo por servicio del gestor de servicios, y el campo FDNAME= estaba ausente cuando el descriptor de archivo se envió al gestor de servicios.
"connection" El servicio se activó en estilo por conexión usando Accept=yes en el archivo de unidad de socket, y el descriptor de archivo es el socket de conexión.

Para más información sobre el almacén de descriptores de archivo, consulte la descripción general del
Almacén de Descriptores de Archivo[1].

VALOR DE RETORNO

En caso de error, estas llamadas devuelven un código de error negativo estilo errno. Si $LISTEN_FDS/$LISTEN_PID no estaba establecido o no estaba correctamente establecido para este demonio y, por lo tanto, no se recibieron descriptores de archivo, se devuelve 0. De lo contrario, se devuelve el número de descriptores de archivo pasados. La aplicación puede encontrarlos a partir del descriptor de archivo SD_LISTEN_FDS_START, es decir, el descriptor de archivo 3.

NOTAS

Las funciones descritas aquí están disponibles como una biblioteca compartida, que puede ser compilada y enlazada con el archivo pkg-config(1) de libsystemd.

El código descrito aquí utiliza getenv(3), que está declarado como no seguro para hilos múltiples. Esto significa que el código que llama a las funciones descritas aquí no debe llamar a setenv(3) desde un hilo paralelo. Se recomienda hacer llamadas a setenv() solo desde una fase temprana del programa cuando no se hayan iniciado otros hilos.

Internamente, sd_listen_fds() comprueba si la variable de entorno $LISTEN_PID es igual al PID del demonio. Si no es así, devuelve inmediatamente. De lo contrario, analiza el número pasado en la variable de entorno $LISTEN_FDS, luego establece la bandera FD_CLOEXEC para el número de descriptores de archivo analizado a partir de SD_LISTEN_FDS_START. Finalmente, devuelve el número analizado. sd_listen_fds_with_names() hace lo mismo pero también analiza $LISTEN_FDNAMES si está establecido.

Estas funciones no están diseñadas para servicios que especifican StandardInput=socket ya que la variable $LISTEN_FDS no está establecida en su entorno.

ENTORNO

$LISTEN_PID, $LISTEN_FDS, $LISTEN_FDNAMES

Establecidas por el gestor de servicios para procesos supervisados que utilizan activación por sockets. Estas variables de entorno especifican los datos que sd_listen_fds() y sd_listen_fds_with_names() analizan. Ver arriba para más detalles.
