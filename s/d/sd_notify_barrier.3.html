Paquete: systemd-libs

SD_NOTIFY(3) sd_notify SD_NOTIFY(3)

NOMBRE

sd_notify, sd_notifyf, sd_pid_notify, sd_pid_notifyf, sd_pid_notify_with_fds, sd_pid_notifyf_with_fds, sd_notify_barrier, sd_pid_notify_barrier - Notificar al gestor de servicios sobre la finalización del inicio y otros cambios de estado del servicio

SINOPSIS

#include <systemd/sd-daemon.h>

int sd_notify(int unset_environment, const char *state);

int sd_notifyf(int unset_environment, const char *format, ...);

int sd_pid_notify(pid_t pid, int unset_environment, const char *state);

int sd_pid_notifyf(pid_t pid, int unset_environment, const char *format, ...);

int sd_pid_notify_with_fds(pid_t pid, int unset_environment, const char *state, const int *fds, unsigned n_fds);

int sd_pid_notifyf_with_fds(pid_t pid, int unset_environment, const int *fds, size_t n_fds, const char *format, ...);

int sd_notify_barrier(int unset_environment, uint64_t timeout);

int sd_pid_notify_barrier(pid_t pid, int unset_environment, uint64_t timeout);

DESCRIPCIÓN

sd_notify() puede ser llamada por un servicio para notificar al gestor de servicios sobre cambios de estado. Puede usarse para enviar información arbitraria, codificada en una cadena similar a un bloque de entorno. Lo más importante es que puede usarse para notificaciones de finalización de inicio o recarga.

Si el parámetro unset_environment es distinto de cero, sd_notify() desestablecerá la variable de entorno $NOTIFY_SOCKET antes de retornar (independientemente de si la llamada a la función tuvo éxito o no). Las llamadas posteriores a sd_notify() no harán nada silenciosamente, y la variable ya no será heredada por los procesos hijos.

El parámetro state debe contener una lista separada por saltos de línea de asignaciones de variables, similar en estilo a un bloque de entorno. Se implica un salto de línea final si no se especifica ninguno. La cadena puede contener cualquier tipo de asignación de variables, pero vea la siguiente sección para una lista de asignaciones entendidas por el gestor de servicios.

Tenga en cuenta que systemd aceptará datos de estado enviados por un servicio solo si la opción NotifyAccess= está correctamente configurada en el archivo de definición del servicio. Vea systemd.service(5) para más detalles.

Tenga en cuenta que las notificaciones de sd_notify() solo pueden atribuirse correctamente a las unidades si el proceso que envía aún existe en el momento en que PID 1 procesa el mensaje, o si el proceso que envía es rastreado explícitamente en tiempo de ejecución por el gestor de servicios. Esto último ocurre si el gestor de servicios originalmente creó el proceso, es decir, en todos los procesos que coinciden con NotifyAccess=main o NotifyAccess=exec. Por el contrario, si un proceso auxiliar de la unidad envía un mensaje de sd_notify() y sale inmediatamente, el gestor de servicios podría no poder atribuir correctamente el mensaje a la unidad y, por lo tanto, lo ignorará, incluso si NotifyAccess=all está configurado para ella.

Por lo tanto, para eliminar todas las condiciones de carrera que involucran la búsqueda de la unidad del cliente y la atribución correcta de notificaciones a las unidades, se puede usar sd_notify_barrier(). Esta llamada actúa como un punto de sincronización y asegura que todas las notificaciones enviadas antes de esta llamada hayan sido recogidas por el gestor de servicios cuando retorna con éxito. El uso de sd_notify_barrier() es necesario para clientes que no son invocados por el gestor de servicios, de lo contrario este mecanismo de sincronización es innecesario para la atribución de notificaciones a la unidad.

sd_notifyf() es similar a sd_notify() pero toma una cadena de formato similar a printf() más argumentos.

sd_pid_notify() y sd_pid_notifyf() son similares a sd_notify() y sd_notifyf() pero toman un ID de proceso (PID) para usar como PID de origen para el mensaje como primer argumento. Esto es útil para enviar mensajes de notificación en nombre de otros procesos, siempre que se disponga de los privilegios adecuados. Efectivamente, esto significa que una invocación privilegiada de sd_pid_notify() puede eludir las restricciones de NotifyAccess=main o NotifyAccess=exec impuestas para un servicio. Si el argumento PID se especifica como 0, se usa el ID de proceso del proceso que llama, en cuyo caso las llamadas son totalmente equivalentes a sd_notify() y sd_notifyf().

sd_pid_notify_with_fds() es similar a sd_pid_notify() pero toma un array adicional de descriptores de archivo. Estos descriptores de archivo se envían junto con el mensaje de notificación al gestor de servicios. Esto es particularmente útil para enviar mensajes de "FDSTORE=1", como se describe anteriormente. Los argumentos adicionales son un puntero al array de descriptores de archivo más el número de descriptores de archivo en el array. Si se pasa el número de descriptores de archivo como 0, la llamada es totalmente equivalente a sd_pid_notify(), es decir, no se pasan descriptores de archivo. Tenga en cuenta que los descriptores de archivo enviados al gestor de servicios en un mensaje sin "FDSTORE=1" se cierran inmediatamente al recibirlos.

sd_pid_notifyf_with_fds() es una combinación de sd_pid_notify_with_fds() y sd_notifyf(), es decir, acepta tanto un PID como un conjunto de descriptores de archivo como entrada, y procesa una cadena de formato para generar la cadena de estado.

sd_notify_barrier() permite al llamador sincronizarse con la recepción de los mensajes de notificación enviados previamente y utiliza el comando BARRIER=1. Toma un valor de timeout relativo en microsegundos que se pasa a ppoll(2). Un valor de UINT64_MAX se interpreta como un tiempo de espera infinito.

sd_pid_notify_barrier() es igual que sd_notify_barrier(), pero permite especificar el PID de origen para el mensaje de notificación.

ASIGNACIONES CONOCIDAS

Las siguientes asignaciones tienen un significado definido:

READY=1

Indica al gestor de servicios que la finalización del inicio del servicio ha terminado, o que el servicio ha completado la recarga de su configuración. Esto solo lo utiliza systemd si el archivo de definición del servicio tiene configurado Type=notify o Type=notify-reload. Dado que hay poco valor en señalar la no preparación, el único valor que los servicios deben enviar es "READY=1" (es decir, "READY=0" no está definido).

RELOADING=1

Indica al gestor de servicios que el servicio está comenzando a recargar su configuración. Esto es útil para permitir que el gestor de servicios rastree el estado interno del servicio y lo presente al usuario. Tenga en cuenta que un servicio que envía esta notificación también debe enviar una notificación "READY=1" cuando haya completado la recarga de su configuración. Las recargas sobre las que se notifica al gestor de servicios con este mecanismo se propagan de la misma manera que cuando se inician originalmente a través del gestor de servicios. Este mensaje es particularmente relevante para los servicios Type=notify-reload, para informar al gestor de servicios que la solicitud de recargar el servicio ha sido recibida y se está procesando.

Añadido en la versión 217.

STOPPING=1

Indica al gestor de servicios que el servicio está comenzando su apagado. Esto es útil para permitir que el gestor de servicios rastree el estado interno del servicio y lo presente al usuario.

Añadido en la versión 217.

MONOTONIC_USEC=...

Un campo que transporta la marca de tiempo monotónica (según CLOCK_MONOTONIC) formateada en decimal en μs, cuando el cliente generó el mensaje de notificación. Esto se usa típicamente en combinación con "RELOADING=1", para permitir que el gestor de servicios sincronice correctamente los ciclos de recarga. Vea systemd.service(5) para más detalles, específicamente "Type=notify-reload".

Añadido en la versión 253.

STATUS=...

Pasa una cadena de estado UTF-8 de una sola línea al gestor de servicios que describe el estado del servicio. Esto es de formato libre y puede usarse para varios propósitos: los programas tipo fsck podrían pasar porcentajes de finalización y los programas fallidos podrían pasar un er legible por humanos.

MENSAJES DE NOTIFICACIÓN

Los servicios pueden enviar mensajes de notificación al gestor de servicios a través del socket de notificación especificado por la variable de entorno $NOTIFY_SOCKET. Estos mensajes consisten en una serie de asignaciones de clave=valor, una por línea, terminadas por un carácter de nueva línea. Los mensajes pueden contener campos de notificación definidos por systemd, así como campos privados. Los campos desconocidos son ignorados.

Los siguientes campos de notificación están definidos:

STATUS=...

Cadena de estado arbitraria. A menudo se utiliza para indicar el progreso de la inicialización o para enviar mensajes de error. Ejemplo: "STATUS=66% de la comprobación del sistema de archivos completada..."

Añadido en la versión 233.

NOTIFYACCESS=...

Restablece el acceso al socket de notificación de estado del servicio durante el tiempo de ejecución, anulando la configuración de NotifyAccess= en el archivo de unidad del servicio. Consulte systemd.service(5) para obtener más detalles, específicamente "NotifyAccess=" para obtener una lista de los valores aceptados.

Añadido en la versión 254.

ERRNO=...

Si un servicio falla, el código de error estilo errno, formateado como cadena. Ejemplo: "ERRNO=2" para ENOENT.

Añadido en la versión 233.

BUSERROR=...

Si un servicio falla, el código de error estilo D-Bus. Ejemplo: "BUSERROR=org.freedesktop.DBus.Error.TimedOut".

Añadido en la versión 233.

VARLINKERROR=...

Si un servicio falla, el código de error estilo Varlink. Ejemplo: "VARLINKERROR=org.varlink.service.InvalidParameter".

Añadido en la versión 257.

EXIT_STATUS=...

El estado de salida de un servicio o del propio gestor. Tenga en cuenta que systemd actualmente no consume este valor cuando lo envían los servicios, por lo que esta asignación es solo informativa. El gestor enviará esta notificación al socket de notificación del gestor, que puede utilizarse para recopilar un estado de salida del sistema (un contenedor o una VM) mientras se apaga. Por ejemplo, mkosi(1) hace uso de esto. El valor a devolver puede establecerse mediante el verbo exit de systemctl(1).

Añadido en la versión 254.

MAINPID=...

Cambia el ID del proceso principal (PID) del servicio. Esto es especialmente útil en el caso de que el proceso principal real no sea directamente bifurcado por el gestor de servicios. Ejemplo: "MAINPID=4711".

Añadido en la versión 233.

MAINPIDFDID=...

El número de inodo del pidfd del nuevo proceso principal (especificado a través de MAINPID=). Esta información se puede adquirir a través de sd_pidfd_get_inode_id(3) en el pidfd y se utiliza para identificar el proceso de forma libre de condiciones de carrera. Alternativamente, un pidfd se puede enviar directamente al gestor de servicios (consulte MAINPIDFD=1 a continuación).

Añadido en la versión 257.

MAINPIDFD=1

Similar a MAINPID= con MAINPIDFDID=, pero el proceso se referencia directamente por el pidfd pasado al gestor de servicios. Esto es útil si el ID del pidfd no es compatible en el sistema. Se espera exactamente un fd para esta notificación.

Añadido en la versión 257.

WATCHDOG=1

Indica al gestor de servicios que actualice la marca de tiempo del watchdog. Este es el ping de "mantener vivo" que los servicios deben emitir a intervalos regulares si WatchdogSec= está habilitado para ellos. Consulte systemd.service(5) para obtener información sobre cómo habilitar esta funcionalidad y sd_watchdog_enabled(3) para obtener detalles sobre cómo el servicio puede comprobar si el watchdog está habilitado.

WATCHDOG=trigger

Indica al gestor de servicios que el servicio ha detectado un error interno que debe ser manejado por las opciones de watchdog configuradas. Esto activará el mismo comportamiento que si WatchdogSec= estuviera habilitado y el servicio no hubiera enviado "WATCHDOG=1" a tiempo. Tenga en cuenta que WatchdogSec= no necesita estar habilitado para que "WATCHDOG=trigger" active la acción del watchdog. Consulte systemd.service(5) para obtener información sobre el comportamiento del watchdog.

Añadido en la versión 243.

WATCHDOG_USEC=...

Restablece el valor de watchdog_usec durante el tiempo de ejecución. Tenga en cuenta que esto no está disponible cuando se utiliza sd_event_set_watchdog() o sd_watchdog_enabled(). Ejemplo: "WATCHDOG_USEC=20000000"

Añadido en la versión 233.

EXTEND_TIMEOUT_USEC=...

Indica al gestor de servicios que extienda el tiempo de espera de inicio, ejecución o apagado del servicio correspondiente al estado actual. El valor especificado es un tiempo en microsegundos durante el cual el servicio debe enviar un nuevo mensaje. Se producirá un tiempo de espera del servicio si no se recibe el mensaje, pero solo si el tiempo de ejecución del estado actual supera los tiempos máximos originales de TimeoutStartSec=, RuntimeMaxSec= y TimeoutStopSec=. Consulte systemd.service(5) para conocer los efectos en los tiempos de espera del servicio.

Añadido en la versión 236.

RESTART_RESET=1

Restablece el contador de reinicios del servicio, lo que tiene el efecto de restaurar la duración del reinicio a RestartSec= si se utilizan RestartSteps= y RestartMaxDelaySec=. Para más información, consulte systemd.service(5).

Añadido en la versión 258.

FDSTORE=1

Almacena descriptores de archivo en el gestor de servicios. Los descriptores de archivo enviados de esta manera serán retenidos para el servicio por el gestor de servicios y se devolverán más tarde utilizando la lógica habitual de paso de descriptores de archivo en el próximo inicio o reinicio del servicio, consulte sd_listen_fds(3). Se pueden almacenar así los sockets abiertos y otros descriptores de archivo que no deban cerrarse durante un reinicio. Cuando un servicio se detiene, su almacén de descriptores de archivo se descarta y todos los descriptores de archivo en él se cierran, excepto cuando se anula con FileDescriptorStorePreserve=, consulte systemd.service(5).

El gestor de servicios aceptará mensajes para un servicio solo si su configuración FileDescriptorStoreMax= no es cero (predeterminado a cero, consulte systemd.service(5)). El gestor de servicios establecerá la variable de entorno $FDSTORE para los servicios que tengan habilitado el almacén de descriptores de archivo, consulte systemd.exec(5).

Si FDPOLL=0 no está establecido y los descriptores de archivo son pollable (consulte epoll_ctl(2)), cualquier evento EPOLLHUP o EPOLLERR que se observe en ellos resultará en su eliminación automática del almacén.

Se pueden enviar varios conjuntos de descriptores de archivo en mensajes separados, en cuyo caso los conjuntos se combinan. El gestor de servicios elimina los descriptores de archivo duplicados (aquellos que apuntan al mismo objeto) antes de pasarlos al servicio.

Esta funcionalidad debe utilizarse para implementar servicios que puedan reiniciarse después de una solicitud explícita o un fallo sin perder estado. El estado de la aplicación se puede serializar a un archivo en /run/, o mejor aún, almacenar en un descriptor de archivo de memoria memfd_create(2). Utilice sd_pid_notify_with_fds() para enviar mensajes con "FDSTORE=1". Se recomienda combinar FDSTORE= con FDNAME= para facilitar la gestión de los descriptores de archivo almacenados.

Para más información sobre el almacén de descriptores de archivo, consulte la descripción general del Almacén de Descriptores de Archivo[1].

Añadido en la versión 219.

FDSTOREREMOVE=1

Elimina descriptores de archivo del almacén de descriptores de archivo. Este campo debe combinarse con FDNAME= para especificar el nombre de los descriptores de archivo a eliminar.

Añadido en la versión 236.

FDNAME=...

Cuando se utiliza en combinación con FDSTORE=1, especifica un nombre para los descriptores de archivo enviados. Cuando se utiliza con FDSTOREREMOVE=1, especifica el nombre de los descriptores de archivo a eliminar. Este nombre se pasa al servicio durante la activación y se puede consultar utilizando sd_listen_fds_with_names(3). Los descriptores de archivo enviados sin este campo se llamarán "almacenados".

El nombre puede consistir en caracteres ASCII arbitrarios excepto caracteres de control o ":". No puede tener más de 255 caracteres. Si un nombre enviado no cumple estas restricciones, se ignora.

Tenga en cuenta que si se envían varios descriptores de archivo en un solo mensaje, el nombre especificado se utilizará para todos ellos. Para asignar nombres diferentes a los descriptores de archivo enviados, envíelos en mensajes separados.

Añadido en la versión 233.

FDPOLL=0

Cuando se utiliza en combinación con FDSTORE=1, deshabilita el sondeo de los descriptores de archivo enviados, independientemente de si son pollable o no. Como esta opción deshabilita la limpieza automática de los descriptores de archivo enviados en EPOLLERR y EPOLLHUP, se debe tener cuidado para garantizar una limpieza manual adecuada. El uso de esta opción generalmente no se recomienda, excepto cuando la limpieza automática tiene un comportamiento no deseado, como descartar prematuramente descriptores de archivo del almacén.

Añadido en la versión 246.

BARRIER=1

Indica al gestor de servicios que el cliente está solicitando explícitamente la sincronización mediante el cierre del descriptor de archivo enviado con este comando. El gestor de servicios garantiza que el procesamiento de un comando BARRIER=1 solo ocurrirá después de que se hayan procesado todos los mensajes de notificación anteriores enviados antes de este comando. Por lo tanto, este comando acompañado de un solo descriptor de archivo se puede utilizar para sincronizar la recepción de todos los mensajes de estado anteriores. Tenga en cuenta que este comando no se puede mezclar con otras notificaciones y debe enviarse en un mensaje separado al gestor de servicios, de lo contrario, todas las asignaciones se ignorarán. Tenga en cuenta que enviar 0 o más de 1 descriptor de archivo con este comando es una violación del protocolo.

Añadido en la versión 246.

Los mensajes de notificación enviados por los servicios son interpretados por el gestor de servicios. Las asignaciones desconocidas son ignoradas. Por lo tanto, es seguro (pero a menudo sin efecto) enviar asignaciones que no están en esta lista. El protocolo es extensible, pero se debe tener cuidado para garantizar que las extensiones privadas sean reconocibles como tales. Específicamente, se recomienda prefijarlas con "X_" seguido de algún identificador de espacio de nombres. El gestor de servicios también envía algunos mensajes a su socket de notificación, que luego pueden ser consumidos por una máquina supervisora o un gestor de contenedores en la pila superior. El gestor de servicios envía varios campos de extensión, por ejemplo, X_SYSTEMD_UNIT_ACTIVE=, para más detalles consulte systemd(1).

VALOR DE RETORNO

En caso de error, estas llamadas devuelven un código de error negativo estilo errno. Si $NOTIFY_SOCKET no estaba establecido y, por lo tanto, no se pudo enviar ningún mensaje de estado, se devuelve 0. Si el estado se envió, estas funciones devuelven un valor positivo. Para admitir tanto a los gestores de servicios que implementan este esquema como a los que no, generalmente se recomienda ignorar el valor de retorno de esta llamada. Tenga en cuenta que el valor de retorno simplemente indica si el mensaje de notificación se puso en cola correctamente, no refleja si el

e message could be processed successfully. Specifically, no error is returned when a file descriptor is attempted to be stored using FDSTORE=1 but the service is not actually configured to permit storing of file descriptors (see above).

Errores

Los errores devueltos pueden indicar los siguientes problemas:

-E2BIG

Se pasaron más descriptores de archivo a la vez de los que permite el sistema. En Linux, el número de descriptores de archivo que se pueden pasar a través de sockets AF_UNIX a la vez es 253, consulte unix(7) para obtener más detalles.

Añadido en la versión 257.

NOTAS

Las funciones descritas aquí están disponibles como una biblioteca compartida, que se puede compilar y enlazar con el archivo libsystemd pkg-config(1).

El código descrito aquí utiliza getenv(3), que se declara como no seguro para subprocesos (thread-safe). Esto significa que el código que llama a las funciones descritas aquí no debe llamar a setenv(3) desde un subproceso paralelo. Se recomienda realizar llamadas a setenv() solo en una fase temprana del programa, cuando no se hayan iniciado otros subprocesos.

Estas funciones envían un único datagrama con la cadena de estado como carga útil al socket referenciado en la variable de entorno $NOTIFY_SOCKET. Si el primer carácter de $NOTIFY_SOCKET es "/" o "@", la cadena se entiende como un socket de espacio de nombres abstracto AF_UNIX o de Linux (respectivamente), y en ambos casos el datagrama va acompañado de las credenciales del proceso del servicio de envío, utilizando SCM_CREDENTIALS. Si la cadena comienza con "vsock:", se entiende como una dirección AF_VSOCK, útil para hipervisores/VMM u otros procesos en el host para recibir una notificación cuando una máquina virtual ha terminado de arrancar. Tenga en cuenta que en caso de que el hipervisor no admita SOCK_DGRAM sobre AF_VSOCK, se utilizará SOCK_SEQPACKET en su lugar. Se pueden usar "vsock-stream", "vsock-dgram" y "vsock-seqpacket" en lugar de "vsock" para forzar el uso del tipo de socket correspondiente. La dirección debe tener el formato: "vsock:CID:PORT". Tenga en cuenta que, a diferencia de otros usos de vsock, el CID es obligatorio y no puede ser "VMADDR_CID_ANY". Tenga en cuenta que PID1 enviará los paquetes VSOCK desde un puerto privilegiado (es decir, inferior a 1024), como un intento de abordar las preocupaciones de que procesos no privilegiados en el huésped puedan intentar enviar notificaciones maliciosas al host, llevándolo a tomar decisiones destructivas basadas en ellas.

Implementaciones Independientes

Tenga en cuenta que, si bien se debe preferir el uso de esta biblioteca para evitar la duplicación de código, también es posible reimplementar el simple protocolo de notificación de disponibilidad sin dependencias externas, como se demuestra en los siguientes ejemplos autocontenidos de varios idiomas:

C 

/* SPDX-License-Identifier: MIT-0 */
/* Implementa el protocolo de notificación de systemd sin dependencias externas.
 * Admite la notificación de disponibilidad al iniciar y al recargar,
 * según el protocolo definido en:
 * https://www.freedesktop.org/software/systemd/man/latest/sd_notify.html
 * Se garantiza que este protocolo es estable según:
 * https://systemd.io/PORTABILITY_AND_STABILITY/ */
#define _GNU_SOURCE 1
#include <errno.h>
#include <inttypes.h>
#include <signal.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdlib.h>
#include <stdio.h>
#include <string.h>
#include <sys/socket.h>
#include <sys/un.h>
#include <time.h>
#include <unistd.h>
#define _cleanup_(f) __attribute__((cleanup(f)))
static void closep(int *fd) {
  if (!fd || *fd < 0)
    return;
  close(*fd);
  *fd = -1;
}
static int notify(const char *message) {
  union sockaddr_union {
    struct sockaddr sa;
    struct sockaddr_un sun;
  } socket_addr = {
    .sun.sun_family = AF_UNIX,
  };
  size_t path_length, message_length;
  _cleanup_(closep) int fd = -1;
  const char *socket_path;
  /* Verifica primero el argumento */
  if (!message)
    return -EINVAL;
  message_length = strlen(message);
  if (message_length == 0)
    return -EINVAL;
  /* Si la variable no está establecida, el protocolo es un no-op */
  socket_path = getenv("NOTIFY_SOCKET");
  if (!socket_path)
    return 0; /* ¿No está configurado? Nada que hacer */
  /* Solo se admite AF_UNIX, con sockets de ruta o abstractos */
  if (socket_path[0] != '/' && socket_path[0] != '@')
    return -EAFNOSUPPORT;
  path_length = strlen(socket_path);
  /* Asegura que haya espacio para el byte NUL */
  if (path_length >= sizeof(socket_addr.sun.sun_path))
    return -E2BIG;
  memcpy(socket_addr.sun.sun_path, socket_path, path_length);
  /* Soporte para socket abstracto */
  if (socket_addr.sun.sun_path[0] == '@')
    socket_addr.sun.sun_path[0] = 0;
  fd = socket(AF_UNIX, SOCK_DGRAM|SOCK_CLOEXEC, 0);
  if (fd < 0)
    return -errno;
  if (connect(fd, &socket_addr.sa, offsetof(struct sockaddr_un, sun_path) + path_length) != 0)
    return -errno;
  ssize_t written = write(fd, message, message_length);
  if (written != (ssize_t) message_length)
    return written < 0 ? -errno : -EPROTO;
  return 1; /* ¡Notificado! */
}
static int notify_ready(void) {
  return notify("READY=1");
}
static int notify_reloading(void) {
  /* Un búfer con longitud suficiente para formatear el valor máximo de UINT64. */
  char reload_message[sizeof("RELOADING=1\nMONOTONIC_USEC=18446744073709551615")];
  struct timespec ts;
  uint64_t now;
  /* Notifica a systemd que estamos recargando, incluyendo una marca de tiempo CLOCK_MONOTONIC en microsegundos
   * para que el programa sea compatible con un servicio Type=notify-reload. */
  if (clock_gettime(CLOCK_MONOTONIC, &ts) < 0)
    return -errno;
  if (ts.tv_sec < 0 || ts.tv_nsec < 0 ||
      (uint64_t) ts.tv_sec > (UINT64_MAX - (ts.tv_nsec / 1000ULL)) / 1000000ULL)
    return -EINVAL;
  now = (uint64_t) ts.tv_sec * 1000000ULL + (uint64_t) ts.tv_nsec / 1000ULL;
  if (snprintf(reload_message, sizeof(reload_message), "RELOADING=1\nMONOTONIC_USEC=%" PRIu64, now) < 0)
    return -EINVAL;
  return notify(reload_message);
}
static int notify_stopping(void) {
  return notify("STOPPING=1");
}
static volatile sig_atomic_t reloading = 0;
static volatile sig_atomic_t terminating = 0;
static void signal_handler(int sig) {
  if (sig == SIGHUP)
    reloading = 1;
  else if (sig == SIGINT || sig == SIGTERM)
    terminating = 1;
}
int main(int argc, char **argv) {
  struct sigaction sa = {
    .sa_handler = signal_handler,
    .sa_flags = SA_RESTART,
  };
  int r;
  /* Configura los manejadores de señales */
  sigemptyset(&sa.sa_mask);
  sigaction(SIGHUP, &sa, NULL);
  sigaction(SIGINT, &sa, NULL);
  sigaction(SIGTERM, &sa, NULL);
  /* Realiza más trabajo de inicialización del servicio aquí... */
  /* Ahora que todos los pasos de preparación están hechos, señala la disponibilidad */
  r = notify_ready();
  if (r < 0) {
    fprintf(stderr, "Fallo al notificar la disponibilidad a $NOTIFY_SOCKET: %s\n", strerror(-r));
    return EXIT_FAILURE;
  }
  while (!terminating) {
    if (reloading) {
      reloading = false;
      /* Como una característica separada pero relacionada, también podemos notificar al gestor
       * al recargar la configuración. Esto permite un seguimiento preciso del estado
       * y también la integración automática de 'systemctl reload' sin tener que
       * especificar manualmente una línea ExecReload= en el archivo de unidad. */
      r = notify_reloading();
      if (r < 0) {
        fprintf(stderr, "Fallo al notificar la recarga a $NOTIFY_SOCKET: %s\n", strerror(-r));
        return EXIT_FAILURE;
      }
      /* Realiza algún trabajo de reconfiguración aquí... */
      r = notify_ready();
      if (r < 0) {
        fprintf(stderr, "Fallo al notificar la disponibilidad a $NOTIFY_SOCKET: %s\n", strerror(-r));
        return EXIT_FAILURE;
      }
    }
    /* Realiza algún trabajo de demonio aquí... */
    sleep(5);
  }
  r = notify_stopping();
  if (r < 0) {
    fprintf(stderr, "Fallo al informar la terminación a $NOTIFY_SOCKET: %s\n", strerror(-r));
    return EXIT_FAILURE;
  }
  /* Realiza algún trabajo de apagado aquí... */
  return EXIT_SUCCESS;
}

#!/usr/bin/python
# SPDX-License-Identifier: MIT-0
#
# Implementa el protocolo de notificación de systemd sin dependencias externas.
# Admite la notificación de disponibilidad al iniciar y al recargar,
# según el protocolo definido en:
# https://www.freedesktop.org/software/systemd/man/latest/sd_notify.html
# Se garantiza que este protocolo es estable según:
# https://systemd.io/PORTABILITY_AND_STABILITY/
import errno
import os
import signal
import socket
import sys
import time
reloading = False
terminating = False
def notify(message):
    if not message:
        raise ValueError("notify() requiere un mensaje")
    socket_path = os.environ.get("NOTIFY_SOCKET")
    if not socket_path:
        return
    if socket_path[0] not in ("/", "@"):
        raise OSError(errno.EAFNOSUPPORT, "Tipo de socket no compatible")
    # Maneja el socket abstracto.
    if socket_path[0] == "@":
        socket_path = "\0" + socket_path[1:]
    with socket.socket(socket.AF_UNIX, socket.SOCK_DGRAM | socket.SOCK_CLOEXEC) as sock:
        sock.connect(socket_path)
        sock.sendall(message)
def notify_ready():
    notify(b"READY=1")
def notify_reloading():
    microsecs = time.clock_gettime_ns(time.CLOCK_MONOTONIC) // 1000
    notify(f"RELOADING=1\nMONOTONIC_USEC={microsecs}".encode())
def notify_stopping():
    notify(b"STOPPING=1")
def reload(signum, frame):
    global reloading
    reloading = True
def terminate(signum, frame):
    global terminating
    terminating = True
def main():
    print("Realizando configuración inicial")
    global reloading, terminating
    # Configura los manejadores de señales.
    print("Configurando manejadores de señales")
    signal.signal(signal.SIGHUP, reload)
    signal.signal(signal.SIGINT, terminate)
    signal.signal(signal.SIGTERM, terminate)
    # Realiza cualquier otro trabajo de configuración aquí.
    # Una vez que se completa toda la configuración, señala la disponibilidad.
    print("Configuración completa")
    notify_ready()
    print("Iniciando bucle")
    while not terminating:
        if reloading:
            print("Recargando")
            reloading = False
            # Admite notificar al gestor al recargar la configuración.
            # Esto permite un seguimiento preciso del estado, así como la habilitación automática
            # de 'systemctl reload' sin necesidad de especificar manualmente
            # una línea ExecReload= en el archivo de unidad.
            notify_reloading()
            # Realiza algún trabajo de reconfiguración aquí.
            print("Recarga completa")
            notify_ready()
        # Haz el trabajo real aquí...
        print("Durmiendo durante cinco segundos")
        time.sleep(5)
    print("Terminando")
    notify_stopping()
if __name__ == "__main__":
    sys.stdout.reconfigure(line_buffering=True)
    print("Iniciando aplicación")
    main()
    print("Aplicación detenida")
sd_notify_barrier(3) — systemd — Arch Linux

NOMBRE

sd_notify, sd_notifyf, sd_pid_notify, sd_pid_notifyf, sd_pid_notify_with_fds, sd_pid_notifyf_with_fds, sd_notify_barrier - enviar notificaciones al gestor de servicios del sistema

SINOPSIS

#include <systemd/sd-daemon.h>

int sd_notify(int unset_environment, const char *state);

int sd_notifyf(int unset_environment, const char *format, ...);

int sd_pid_notify(pid_t pid, int unset_environment, const char *state);

int sd_pid_notifyf(pid_t pid, int unset_environment, const char *format, ...);

int sd_pid_notify_with_fds(pid_t pid, int unset_environment, const char *state, int *fds, size_t n_fds);

int sd_pid_notifyf_with_fds(pid_t pid, int unset_environment, const char *state, int *fds, size_t n_fds);

int sd_notify_barrier(int unset_environment, uint64_t timeout_usec);

DESCRIPCION

La función sd_notify() se utiliza para enviar mensajes de notificación al gestor de servicios del sistema, systemd(1). Esto se usa típicamente para informar sobre el estado de inicio, para indicar que el servicio está listo para aceptar conexiones, para indicar un error durante el inicio, o para enviar información de estado arbitraria. systemd(1) espera estas notificaciones en un socket de dominio de Unix que se establece a través de la variable de entorno $NOTIFY_SOCKET.

La llamada sólo tiene efecto si la variable de entorno $NOTIFY_SOCKET está establecida. Si unset_environment es distinto de cero, esta variable de entorno se eliminará de las variables de entorno del proceso que llama después de que se haya enviado la notificación. Esto es útil para evitar que los procesos secundarios heredan el socket de notificación de forma accidental.

La cadena de estado state debe estar codificada en formato de pares clave=valor, separados por saltos de línea. Los pares clave=valor comunes se describen en sd-daemon(3). Las llaves válidas incluyen STATUS=, READY=, RELOADING=, STOPPING=, MAINPID=, BUSERROR=, FDSTORE=, FDNAME=.

La función sd_notifyf() es similar a sd_notify(), pero utiliza un formato de cadena similar a printf(3) para construir el mensaje de estado. Esto facilita la incorporación de valores variables en el mensaje de estado.

Las funciones sd_pid_notify() y sd_pid_notifyf() son similares a sd_notify() y sd_notifyf(), respectivamente, pero envían las notificaciones a un proceso específico identificado por su PID, en lugar de a systemd. Esto puede ser útil para que los procesos demonio se comuniquen entre sí.

Las funciones sd_pid_notify_with_fds() y sd_pid_notifyf_with_fds() son similares a sd_pid_notify() y sd_pid_notifyf(), pero también permiten pasar una matriz de descriptores de archivo abiertos junto con la notificación. Esto es útil para enviar descriptores de archivo a otros procesos, por ejemplo, para el almacenamiento en caché de descriptores de archivo. El parámetro fds es un puntero a una matriz de descriptores de archivo, y n_fds es el número de descriptores de archivo en la matriz.

La función sd_notify_barrier() se utiliza para sincronizar con la recepción de notificaciones. Cuando se llama a sd_notify_barrier(), espera hasta que el gestor de servicios del sistema haya recibido y procesado todas las notificaciones enviadas antes de esta llamada. Esto es útil para evitar condiciones de carrera en las que un proceso cliente se cierra demasiado rápido y el gestor de servicios del sistema no puede atribuir correctamente las notificaciones a la unidad. El parámetro timeout_usec especifica un tiempo de espera en microsegundos para la barrera. Si la barrera no se puede alcanzar dentro de este tiempo, la función devolverá un error.

ASIGNACIONES BIEN CONOCIDAS

Las siguientes asignaciones de clave se reconocen en el parámetro state:

READY=1
Indica que el servicio ha terminado de inicializarse y está listo para aceptar conexiones o solicitudes. El gestor de servicios del sistema desbloqueará las unidades dependientes que esperan este servicio.
BUSERROR=
Indica que ha ocurrido un error de bus al iniciar el servicio. El argumento es una cadena que describe el error. El servicio se considerará fallido.
STATUS=
Una cadena de texto descriptiva que indica el estado actual del servicio. Esto se puede actualizar dinámicamente.
MAINPID=
El PID del proceso principal del servicio. Esto se establece típicamente al inicio del servicio.
RELOADING=1
Indica que el servicio está recargando su configuración. Esto es útil para indicar que el servicio está temporalmente no disponible mientras se recarga.
STOPPING=1
Indica que el servicio se está cerrando. Esto se puede usar para indicar que el servicio ya no acepta nuevas conexiones.
FDSTORE=1
Indica que los descriptores de archivo adjuntos deben ser almacenados por el gestor de servicios del sistema. Esto es útil para pasar descriptores de archivo entre reinicios del servicio. La clave FDNAME= se puede usar para nombrar los descriptores de archivo almacenados.

VALOR DE RETORNO

En caso de éxito, estas funciones devuelven 0. En caso de error, devuelven un código de error negativo. Los códigos de error posibles son:

-EINVAL
El argumento state no era válido o unset_environment no es 0 o 1.
-ENOMEM
Memoria insuficiente para construir el mensaje de notificación.
-EPROTO
El socket de notificación no se encontró o el protocolo no es compatible.
-ESRCH
El PID especificado para sd_pid_notify*() no existe.

NOTAS

Si unset_environment es distinto de cero, la variable de entorno $NOTIFY_SOCKET se elimina del proceso que llama. Sin embargo, esto no afecta a los procesos secundarios que puedan haber sido creados antes de que se llamara a sd_notify().

Las notificaciones se envían de forma asíncrona. No hay garantía de que las notificaciones se reciban inmediatamente después de llamar a la función.

El uso de sd_notify_barrier() es importante para evitar condiciones de carrera en las que el proceso cliente sale demasiado rápido, lo que podría impedir que el gestor de servicios del sistema atribuya correctamente las notificaciones a la unidad. El tiempo de espera de la barrera debe ser lo suficientemente largo como para permitir que el gestor de servicios del sistema reciba y procese todas las notificaciones pendientes.

AMBIENTE

$NOTIFY_SOCKET

Establecido por el gestor de servicios para los procesos supervisados para la notificación de estado y finalización de inicio. Esta variable de entorno especifica el socket con el que habla sd_notify(). Ver arriba para más detalles.

EJEMPLOS

Ejemplo 1. Notificación de inicio

Cuando un servicio ha terminado de iniciarse, podría emitir la siguiente llamada para notificar al gestor de servicios:

sd_notify(0, "READY=1");

Ejemplo 2. Notificación de inicio extendida

Un servicio podría enviar lo siguiente después de completar la inicialización:

sd_notifyf(0, "READY=1\n"
              "STATUS=Procesando solicitudes...\n"
              "MAINPID=%lu",
           (unsigned long) getpid());

Ejemplo 3. Notificación de causa de error

Un servicio podría enviar lo siguiente poco antes de salir, en caso de error:

sd_notifyf(0, "STATUS=Fallo al iniciar: %s\n"
              "ERRNO=%i",
           strerror_r(errnum, (char[1024]){}, 1024),
           errnum);

Ejemplo 4. Almacenar un descriptor de archivo en el gestor de servicios

Para almacenar un descriptor de archivo abierto en el gestor de servicios, con el fin de continuar la operación después de un reinicio del servicio sin perder estado, utilice "FDSTORE=1":

sd_pid_notify_with_fds(0, 0, "FDSTORE=1\nFDNAME=foobar", &fd, 1);

Ejemplo 5. Eliminación de condiciones de carrera

Cuando el cliente que envía las notificaciones no es generado por el gestor de servicios, puede salir demasiado rápido y el gestor de servicios puede no atribuirlas correctamente a la unidad. Para evitar tales carreras, utilice sd_notify_barrier() para sincronizar contra la recepción de todas las notificaciones enviadas antes de que se realice esta llamada.

sd_notify(0, "READY=1");
/* establecer tiempo de espera a 5 segundos */
sd_notify_barrier(0, 5 * 1000000);
