DESCRIPCIÓN

sd_bus_add_object_vtable() se utiliza para declarar atributos para la ruta de objeto path conectada a la conexión de bus bus bajo la interfaz interface. La tabla vtable puede contener declaraciones de propiedades usando SD_BUS_PROPERTY() o SD_BUS_WRITABLE_PROPERTY(), declaraciones de métodos usando SD_BUS_METHOD(), SD_BUS_METHOD_WITH_NAMES(), SD_BUS_METHOD_WITH_OFFSET(), o SD_BUS_METHOD_WITH_NAMES_OFFSET(), y declaraciones de señales usando SD_BUS_SIGNAL_WITH_NAMES() o SD_BUS_SIGNAL(), ver más abajo. El parámetro userdata contiene un puntero que se pasará a varias funciones de devolución de llamada. Puede especificarse como NULL si no se necesita ningún valor. Una interfaz puede tener cualquier número de vtables adjuntas a ella.

sd_bus_add_fallback_vtable() es similar a sd_bus_add_object_vtable(), pero se utiliza para registrar atributos de "fallback". Al buscar una declaración de atributo, primero se comprueban las rutas de objetos de bus registradas con sd_bus_add_object_vtable(). Si no se encuentra ninguna coincidencia, se comprueban las vtables de fallback para cada prefijo de la ruta del objeto del bus, es decir, eliminando sucesivamente los últimos componentes separados por barras. Esto permite que la vtable se utilice para un número arbitrario de objetos creados dinámicamente.

El parámetro find es una función que se utiliza para localizar el objeto de destino basándose en la ruta del objeto del bus path. Debe devolver 1 y establecer el parámetro de salida ret_found si se encuentra el objeto, devolver 0 si no se encontró el objeto, y devolver un código de error negativo de estilo errno o inicializar la estructura de error ret_error en caso de error. El puntero pasado en ret_found se utilizará como parámetro userdata para las funciones de devolución de llamada (desplazado por los desplazamientos offset como se especifica en las entradas de la vtables).

sd_bus_add_object() adjunta una devolución de llamada directamente a la ruta del objeto path. Una ruta de objeto puede tener cualquier número de devoluciones de llamada adjuntas. Cada devolución de llamada se antepone a la lista de devoluciones de llamada que siempre se llaman en orden. sd_bus_add_fallback() es similar a sd_bus_add_object() pero se aplica a rutas de fallback en su lugar.

sd_bus_add_filter() instala una devolución de llamada que se invoca para cada mensaje D-Bus entrante. Los filtros se pueden utilizar para manejar la lógica común a todos los mensajes recibidos por un servicio (por ejemplo, autenticación o autorización).

Cuando se recibe una solicitud, se llaman secuencialmente todas las devoluciones de llamada asociadas hasta que una devolución de llamada devuelve un entero distinto de cero. Devuelva cero desde una devolución de llamada para dar a otras devoluciones de llamada la oportunidad de procesar la solicitud. Las devoluciones de llamada se llaman en el siguiente orden: primero, se llaman las devoluciones de llamada globales instaladas con sd_bus_add_filter(). Segundo, se llaman las devoluciones de llamada adjuntas directamente a la ruta del objeto de la solicitud, seguidas de cualquier devolución de llamada de método D-Bus adjunta a la ruta del objeto de la solicitud, interfaz y miembro. Finalmente, se llaman las devoluciones de llamada de propiedad adjuntas a la ruta del objeto de la solicitud, interfaz y miembro. Si la devolución de llamada final devuelve cero, se informa un error.

o se devuelve al llamador indicando que no se encontró ningún objeto coincidente para la solicitud.

Tenga en cuenta que puede devolver un entero positivo de una función de llamada de _método_ sin enviar inmediatamente una respuesta. Esto informa a sd-bus que la función de llamada se hará responsable de responder a la solicitud sin obligar a la función de llamada a producir una respuesta de inmediato. Esto permite que una función de llamada realice cualquier número de operaciones asíncronas necesarias para construir una respuesta. Sin embargo, si la producción de una respuesta lleva demasiado tiempo, la llamada al método caducará en el llamador. Esto solo está disponible para métodos y no para propiedades.

Si se invocó una función de llamada para manejar una solicitud que espera una respuesta y la función de llamada devuelve un valor negativo, el valor se interpreta como un código de error negativo al estilo errno y se devuelve al llamador como un error de D-Bus, como si se hubiera llamado a sd_bus_reply_method_errno(3). Además, todas las funciones de llamada toman un parámetro de salida sd_bus_error que se puede utilizar para proporcionar información de error más detallada. Si _ret_error_ se establece cuando la función de llamada finaliza, el error de D-Bus correspondiente se devuelve al llamador como si se hubiera llamado a sd_bus_reply_method_error(3). Cualquier error almacenado en _ret_error_ tiene prioridad sobre cualquier valor negativo devuelto por la misma función de llamada al determinar qué error enviar de vuelta al llamador. Utilice sd_bus_error_set(3) o una de sus variantes para establecer _ret_error_ y devolver un entero negativo desde una función de llamada con una sola llamada a función. Para enviar una respuesta de error después de que una función de llamada haya finalizado, utilice sd_bus_reply_method_errno(3) o una de sus variantes.

Para todas las funciones, se crea internamente una ranura de coincidencia. Si el parámetro de salida _slot_ es NULL, se crea un objeto de ranura "flotante", consulte sd_bus_slot_set_floating(3). De lo contrario, se devuelve un puntero al objeto de ranura. En ese caso, la referencia al objeto de ranura debe eliminarse cuando la vtable ya no sea necesaria, consulte sd_bus_slot_unref(3).

La matriz sd_bus_vtable

La matriz consta de estructuras de tipo sd_bus_vtable, pero nunca debe llenarse manualmente, sino a través de una de las siguientes macros:

SD_BUS_VTABLE_START(flags), SD_BUS_VTABLE_END

Estos deben ser siempre el primer y último elemento. El parámetro _flags_ se puede utilizar para establecer atributos que se aplican a toda la matriz; consulte la sección "Flags" a continuación.

SD_BUS_METHOD_WITH_ARGS_OFFSET(), SD_BUS_METHOD_WITH_ARGS()

Declara un método D-Bus con el nombre _member_, argumentos _args_ y resultado _result_. _args_ espera una secuencia de pares de tipo/nombre de argumento encapsulados en la macro SD_BUS_ARGS(). Los elementos en índices pares de esta lista describen los tipos de los argumentos del método. La firma del parámetro del método es la concatenación de todas las cadenas literales en índices pares en _args_. Si un método no tiene parámetros, pase SD_BUS_NO_ARGS a _args_. Los elementos en índices impares describen los nombres de los argumentos del método. _result_ espera una secuencia de pares de tipo/nombre encapsulados en la macro SD_BUS_RESULT() en el mismo formato que SD_BUS_ARGS(). La firma del resultado del método es la concatenación de todas las cadenas literales en índices pares en _result_. Si un método no tiene resultado, pase SD_BUS_NO_RESULT a _result_. Tenga en cuenta que se espera que los tipos de argumento sean cadenas literales entre comillas y los nombres de argumento sean cadenas literales sin comillas. Consulte a continuación un ejemplo completo.

La función de manejo _handler_ debe ser de tipo sd_bus_message_handler_t. Se llamará para manejar los mensajes entrantes que llaman a este método. Recibe un puntero que es el parámetro _userdata_ pasado a la función de registro desplazado _offset_ bytes. Esto se puede utilizar para pasar punteros a diferentes campos de la misma estructura de datos a diferentes métodos en la misma vtable. Para enviar una respuesta desde _handler_, llame a sd_bus_reply_method_return(3) con el mensaje con el que se invocó la función de llamada. El parámetro _flags_ es una combinación de flags, consulte a continuación.

SD_BUS_METHOD_WITH_ARGS() es una abreviatura para llamar a SD_BUS_METHOD_WITH_ARGS_OFFSET() con un desplazamiento de cero.

SD_BUS_METHOD_WITH_NAMES_OFFSET(), SD_BUS_METHOD_WITH_NAMES(), SD_BUS_METHOD_WITH_OFFSET(), SD_BUS_METHOD()

Declara un método D-Bus con el nombre _member_, firma de parámetros _signature_, firma de resultado _result_. Los parámetros _in_names_ y _out_names_ especifican los nombres de los argumentos de los argumentos de entrada y salida en la firma de la función. _in_names_ y _out_names_ deben crearse utilizando la macro SD_BUS_PARAM(), consulte a continuación. En todos los demás aspectos, esta macro se comporta exactamente igual que SD_BUS_METHOD_WITH_ARGS_OFFSET().

SD_BUS_METHOD_WITH_NAMES(), SD_BUS_METHOD_WITH_OFFSET() y SD_BUS_METHOD() son variantes que especifican un desplazamiento cero (el parámetro _userdata_ se pasa sin cambios), dejan los nombres sin establecer (es decir, sin nombres de parámetros) o ambos.

Prefiera usar SD_BUS_METHOD_WITH_ARGS_OFFSET() y SD_BUS_METHOD_WITH_ARGS() sobre estas macros, ya que permiten especificar tipos y nombres de argumentos uno al lado del otro, lo que es menos propenso a errores que especificar primero todos los tipos de argumentos seguidos de la especificación de todos los nombres de argumentos.

SD_BUS_SIGNAL_WITH_ARGS()

Declara una señal D-Bus con el nombre _member_ y argumentos _args_. _args_ espera una secuencia de pares de tipo/nombre de argumento encapsulados en la macro SD_BUS_ARGS(). Los elementos en índices pares de esta lista describen los tipos de los argumentos de la señal. La firma del parámetro de la señal es la concatenación de todas las cadenas literales en índices pares en _args_. Si una señal no tiene parámetros, pase SD_BUS_NO_ARGS a _args_. Los elementos en índices impares describen los nombres de los argumentos de la señal. El parámetro _flags_ es una combinación de flags. Consulte a continuación un ejemplo completo.

SD_BUS_SIGNAL_WITH_NAMES(), SD_BUS_SIGNAL()

Declara una señal D-Bus con el nombre _member_, firma de parámetros _signature_ y nombres de argumentos _names_. _names_ debe crearse utilizando la macro SD_BUS_PARAM(), consulte a continuación. El parámetro _flags_ es una combinación de flags, consulte a continuación.

SD_BUS_SIGNAL() es equivalente a SD_BUS_SIGNAL_WITH_NAMES() con el parámetro _names_ sin establecer (es decir, sin nombres de parámetros).

Prefiera usar SD_BUS_SIGNAL_WITH_ARGS() sobre estas macros, ya que permite especificar tipos y nombres de argumentos uno al lado del otro, lo que es menos propenso a errores que especificar primero todos los tipos de argumentos seguidos de la especificación de todos los nombres de argumentos.

SD_BUS_WRITABLE_PROPERTY(), SD_BUS_PROPERTY()

Declara una propiedad D-Bus con el nombre _member_ y firma de valor _signature_. Los parámetros _get_ y _set_ son los métodos de obtención y establecimiento. Se llaman con un puntero que es el parámetro _userdata_ pasado a la función de registro desplazado _offset_ bytes. Esto se puede utilizar para pasar punteros a diferentes campos de la misma estructura de datos a diferentes métodos de establecimiento y obtención en la misma vtable. El parámetro _flags_ es una combinación de flags, consulte a continuación.

El método de establecimiento y el método de obtención se pueden omitir (especificarse como NULL), si la propiedad es uno de los tipos básicos o "as" en caso de propiedades de solo lectura. En esos casos, los parámetros _userdata_ y _offset_ deben apuntar juntos a una variable válida del tipo correspondiente. Se proporcionará un método de establecimiento y obtención predeterminado, que simplemente copia el argumento entre esta variable y el mensaje.

SD_BUS_PROPERTY() se utiliza para definir una propiedad de solo lectura.

SD_BUS_PARAM()

Los nombres de los parámetros deben envolverse en esta macro, consulte el ejemplo a continuación.

Flags

El parámetro _flags_ se utiliza para especificar una combinación de **Anotaciones de D-Bus**[1].

SD_BUS_VTABLE_DEPRECATED

Marque esta entrada de vtable como obsoleta utilizando la anotación org.freedesktop.DBus.Deprecated en los datos de introspección. Si se especifica para SD_BUS_VTABLE_START(), la anotación se aplica a la interfaz que la contiene.

SD_BUS_VTABLE_HIDDEN

Haga que esta entrada de vtable sea oculta. No se mostrará en los datos de introspección. Si se especifica para SD_BUS_VTABLE_START(), todas las entradas de la matriz se ocultan.

SD_BUS_VTABLE_METHOD_NO_REPLY

Marque esta entrada de vtable como un método que no devolverá una respuesta utilizando la anotación org.freedesktop.DBus.Method.NoReply en los datos de introspección.

SD_BUS_VTABLE_PROPERTY_CONST, SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE, SD_BUS_VTABLE_PROPERTY_EMITS_INVALIDATION

Estos tres flags corresponden a diferentes valores de la anotación org.freedesktop.DBus.Property.EmitsChangedSignal, que especifica si la señal org.freedesktop.DBus.Properties.PropertiesChanged se emite cada vez que cambia la propiedad. SD_BUS_VTABLE_PROPERTY_CONST corresponde a const y significa que la propiedad nunca cambia durante la vida útil del objeto al que pertenece, por lo que no es necesario emitir ninguna señal. SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE corresponde a true y significa que la señal se emite. SD_BUS_VTABLE_PROPERTY_EMITS_INVALIDATION corresponde a invalidates y significa que la señal se emite, pero el valor no se incluye en la señal.

SD_BUS_VTABLE_PROPERTY_EXPLICIT

Marque esta entrada de propiedad vtable como que requiere una solicitud explícita para que se muestre el valor (generalmente porque el valor es grande o lento de calcular). Esta entrada no se puede combinar con SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE y no se mostrará en las listas de propiedades de forma predeterminada (por ejemplo, busctl introspect). Esto corresponde a la anotación org.freedesktop.systemd1.Explicit en los datos de introspección.

SD_BUS_VTABLE_SENSITIVE

Marque esta entrada de método vtable como que procesa datos sensibles. Cuando se establece, los mensajes de llamada de método entrantes y sus mensajes de respuesta salientes se marcan como sensibles utilizando sd_bus_message_sensitive(3), de modo que se borren de la memoria cuando se liberen.

SD_BUS_VTABLE_ABSOLUTE_OFFSET

Marque esta entrada de método o propiedad vtable para que el usuario da

DESCRIPTION

This flag is only meaningful for methods. It is used in combination with SD_BUS_METHOD_WITH_NAMES_OFFSET() and SD_BUS_METHOD_WITH_ARGS_OFFSET(). When this flag is specified, the offset parameter of the entry is added to the user data pointer passed to the handler. The result is then passed as the userdata parameter to the handler.

For example, if userdata is set to a pointer to a structure, and SD_BUS_METHOD_WITH_NAMES_OFFSET() is used with an offset into that structure, the pointer to that member of the structure is passed to the handler. This is useful for passing different members of the same structure to different handlers.

This differs from the default behaviour where the offset is ignored and the original userdata pointer is passed to the handler.

When the argument is passed to its associated handler functions, the pointer is determined slightly differently: instead of adding the offset parameter of the entry to the user data pointer specified during vtable registration, the offset is passed directly, converted to a pointer, without taking the user data pointer specified during vtable registration into account.

SD_BUS_VTABLE_CAPABILITY(capability)

El acceso a esta entrada de la vtable se permitirá si el proceso que llama tiene la capacidad capability, como se describe en sd_bus_query_sender_privilege(3). Si se utiliza para SD_BUS_VTABLE_START(), proporciona un valor predeterminado para todas las entradas de la matriz. Si no se especifica, ya sea para una entrada individual o para toda la matriz, se verifica CAP_SYS_ADMIN por defecto. Consulte capabilities(7) para obtener información sobre las capacidades.

Tenga en cuenta que las entradas de la vtable pueden marcarse como no privilegiadas y toda la conexión de bus puede marcarse como confiable, consulte la discusión de SD_BUS_VTABLE_UNPRIVILEGED a continuación.

SD_BUS_VTABLE_UNPRIVILEGED

Marque esta entrada de la vtable como no privilegiada. El acceso a las entradas privilegiadas se limita a los usuarios con las capacidades adecuadas, como se describe anteriormente. En la práctica, muchas entradas de vtable se marcan como no privilegiadas, y o bien están abiertas para todos, o bien la decisión de permitir el acceso se toma más tarde, por ejemplo, delegando a polkit[2].

Toda la conexión de bus puede marcarse como confiable, en cuyo caso las anotaciones a nivel de entrada se ignoran, consulte sd_bus_set_trusted(3).

Cuando no se especifica, la anotación org.freedesktop.systemd1.Privileged con el valor "true" se mostrará en los datos de introspección.

SD_BUS_VTABLE_UNPRIVILEGED no se puede aplicar a propiedades de solo lectura, pero el acceso de lectura (tanto a propiedades de solo lectura como escribibles) siempre está sin restricciones.

Tenga en cuenta que esta página describe las comprobaciones implementadas en el cliente D-Bus. El servidor D-Bus tiene una política adicional que puede permitir o denegar conexiones, consulte "ARCHIVO DE CONFIGURACIÓN" en dbus-daemon(1).

EJEMPLOS

Ejemplo 1. Crear un oyente simple en el bus

/* SPDX-License-Identifier: MIT-0 */
#define _GNU_SOURCE 1
#include <errno.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdlib.h>
#include <stdio.h>
#include <systemd/sd-bus.h>
#define _cleanup_(f) __attribute__((cleanup(f)))
typedef struct object {
  char *name;
  uint32_t number;
} object;
static int method(sd_bus_message *m, void *userdata, sd_bus_error *error) {
  int r;
  printf("Got called with userdata=%p\n", userdata);
  if (sd_bus_message_is_method_call(m,
                                    "org.freedesktop.systemd.VtableExample",
                                    "Method4"))
    return 1;
  const char *string;
  r = sd_bus_message_read(m, "s", &string);
  if (r < 0) {
    fprintf(stderr, "sd_bus_message_read() failed: %s\n", strerror(-r));
    return 0;
  }
  r = sd_bus_reply_method_return(m, "s", string);
  if (r < 0) {
    fprintf(stderr, "sd_bus_reply_method_return() failed: %s\n", strerror(-r));
    return 0;
  }
  return 1;
}
static const sd_bus_vtable vtable[] = {
        SD_BUS_VTABLE_START(0),
        SD_BUS_METHOD(
            "Method1", "s", "s", method, 0),
        SD_BUS_METHOD_WITH_NAMES_OFFSET(
            "Method2",
            "so", SD_BUS_PARAM(string) SD_BUS_PARAM(path),
            "s", SD_BUS_PARAM(returnstring),
            method, offsetof(object, number),
            SD_BUS_VTABLE_DEPRECATED),
        SD_BUS_METHOD_WITH_ARGS_OFFSET(
            "Method3",
            SD_BUS_ARGS("s", string, "o", path),
            SD_BUS_RESULT("s", returnstring),
            method, offsetof(object, number),
            SD_BUS_VTABLE_UNPRIVILEGED),
        SD_BUS_METHOD_WITH_ARGS(
            "Method4",
            SD_BUS_NO_ARGS,
            SD_BUS_NO_RESULT,
            method,
            SD_BUS_VTABLE_UNPRIVILEGED),
        SD_BUS_SIGNAL(
            "Signal1",
            "so",
            0),
        SD_BUS_SIGNAL_WITH_NAMES(
            "Signal2",
            "so", SD_BUS_PARAM(string) SD_BUS_PARAM(path),
            0),
        SD_BUS_SIGNAL_WITH_ARGS(
            "Signal3",
            SD_BUS_ARGS("s", string, "o", path),
            0),
        SD_BUS_WRITABLE_PROPERTY(
            "AutomaticStringProperty", "s", NULL, NULL,
            offsetof(object, name),
            SD_BUS_VTABLE_PROPERTY_EMITS_CHANGE),
        SD_BUS_WRITABLE_PROPERTY(
            "AutomaticIntegerProperty", "u", NULL, NULL,
            offsetof(object, number),
            SD_BUS_VTABLE_PROPERTY_EMITS_INVALIDATION),
        SD_BUS_VTABLE_END
};
int main(int argc, char **argv) {
  _cleanup_(sd_bus_flush_close_unrefp) sd_bus *bus = NULL;
  int r;
  sd_bus_default(&bus);
  object object = { .number = 666 };
  object.name = strdup("name");
  if (!object.name) {
    fprintf(stderr, "OOM\n");
    return EXIT_FAILURE;
  }
  r = sd_bus_add_object_vtable(bus, NULL,
                               "/org/freedesktop/systemd/VtableExample",
                               "org.freedesktop.systemd.VtableExample",
                               vtable,
                               &object);
  if (r < 0) {
    fprintf(stderr, "sd_bus_add_object_vtable() failed: %s\n", strerror(-r));
    return EXIT_FAILURE;
  }
  r = sd_bus_request_name(bus,
                          "org.freedesktop.systemd.VtableExample",
                          0);
  if (r < 0) {
    fprintf(stderr, "sd_bus_request_name() failed: %s\n", strerror(-r));
    return EXIT_FAILURE;
  }
  for (;;) {
    r = sd_bus_wait(bus, UINT64_MAX);
    if (r < 0) {
      fprintf(stderr, "sd_bus_wait() failed: %s\n", strerror(-r));
      return EXIT_FAILURE;
    }
    r = sd_bus_process(bus, NULL);
    if (r < 0) {
      fprintf(stderr, "sd_bus_process() failed: %s\n", strerror(-r));
      return EXIT_FAILURE;
    }
  }
  r = sd_bus_release_name(bus, "org.freedesktop.systemd.VtableExample");
  if (r < 0) {
    fprintf(stderr, "sd_bus_release_name() failed: %s\n", strerror(-r));
    return EXIT_FAILURE;
  }
  free(object.name);
  return 0;
}

VALOR DE RETORNO

En caso de éxito, sd_bus_add_object_vtable() y sd_bus_add_fallback_vtable() devuelven un entero no negativo. En caso de error, devuelven un código de error negativo estilo errno.

Errores

Los errores devueltos pueden indicar los siguientes problemas:

-EINVAL

Uno de los parámetros requeridos es NULL o inválido. Se pasó una interfaz D-Bus reservada como parámetro interface.

-ENOPKG

El bus no se puede resolver.

-ECHILD

El bus se creó en un proceso, biblioteca o instancia de módulo diferente.

-ENOMEM

Fallo en la asignación de memoria.

-EPROTOTYPE

Se han llamado tanto sd_bus_add_object_vtable() como sd_bus_add_fallback_vtable() para la misma ruta de objeto de bus, lo cual no está permitido.

-EEXIST

Esta vtable ya se ha registrado para esta interface y path.

NOTAS

Las funciones descritas aquí son

disponible como una biblioteca compartida, que puede ser compilada y enlazada con el archivo pkg-config(1) libsystemd.

El código descrito aquí utiliza getenv(3), que se declara como no seguro para múltiples hilos. Esto significa que el código que llama a las funciones descritas aquí no debe llamar a setenv(3) desde un hilo paralelo. Se recomienda realizar llamadas a setenv() solo desde una fase temprana del programa cuando no se hayan iniciado otros hilos.
