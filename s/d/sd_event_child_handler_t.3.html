DESCRIPCIÓN

sd_event_add_child() añade una nueva fuente de eventos de cambio de estado de proceso hijo a un bucle de eventos. El objeto del bucle de eventos se especifica en el parámetro event, el objeto de la fuente de eventos se devuelve en el parámetro source. El parámetro pid especifica el PID del proceso a vigilar, que debe ser un proceso hijo directo del proceso que invoca. El parámetro options determina qué cambios de estado se vigilarán. Debe contener una máscara OR de WEXITED (vigilar la terminación del proceso hijo), WSTOPPED (vigilar la detención del proceso hijo por una señal) y WCONTINUED (vigilar la reanudación del proceso hijo por una señal). Consulte waitid(2) para obtener más información.

El handler debe ser una función a llamar cuando el proceso cambie de estado o NULL. A la función manejadora se le pasará el puntero userdata, que puede ser elegido libremente por el llamador. El manejador también recibe un puntero a una estructura siginfo_t que contiene información sobre el evento del proceso hijo. El manejador puede devolver un valor negativo para indicar un error (ver más abajo), otros valores de retorno se ignoran. Si handler es NULL, se utilizará un manejador predeterminado que llama a sd_event_exit(3).

Solo se puede instalar un manejador para un proceso hijo específico. El manejador está habilitado para un solo evento (SD_EVENT_ONESHOT), pero esto se puede cambiar con sd_event_source_set_enabled(3). Si la función manejadora devuelve un código de error negativo, se deshabilitará después de la invocación, incluso si se solicitó el modo SD_EVENT_ON antes, o causará que el bucle termine, consulte sd_event_source_set_exit_on_failure(3).

Para destruir un objeto fuente de eventos, utilice sd_event_source_unref(3), pero tenga en cuenta que la fuente de eventos solo se elimina del bucle de eventos cuando todas las referencias a la fuente de eventos se liberan. Para asegurarse de que una fuente de eventos no se active de nuevo, incluso cuando todavía hay una referencia a ella, considere establecer la fuente de eventos en SD_EVENT_OFF con sd_event_source_set_enabled(3).

La señal SIGCHLD debe estar bloqueada en todos los hilos antes de llamar a esta función (usando sigprocmask(2) o pthread_sigmask(3)).

Si se pasa el segundo parámetro de sd_event_add_child() como NULL, no se devolverá ninguna referencia al objeto fuente de eventos. En este caso, la fuente de eventos se considera "flotante" y se destruirá implícitamente cuando se destruya el propio bucle de eventos.

Tenga en cuenta que la función handler se invoca en un momento en que el proceso hijo aún no ha sido recogido (y por lo tanto todavía está expuesto como un proceso zombi por el kernel). Sin embargo, el hijo será recogido automáticamente después de que la función devuelva. Los procesos hijos para los que no se instalan fuentes de eventos de cambio de estado de proceso hijo no serán recogidos por la implementación del bucle de eventos.

Si el parámetro handler de sd_event_add_child() es NULL, y la fuente de eventos se dispara, esto se considerará una solicitud para salir del bucle de eventos. En este caso, el parámetro userdata, convertido a un entero, se pasa como parámetro de código de salida a sd_event_exit(3).

Si tanto una fuente de eventos de cambio de estado de proceso hijo como una fuente de eventos de señal SIGCHLD están instaladas en el mismo bucle de eventos, las prioridades de fuente de eventos configuradas deciden qué fuente de eventos se despacha primero. Si el manejador de señales se procesa primero, debe dejar los procesos hijos para los que están instaladas fuentes de eventos de cambio de estado de proceso hijo sin recoger.

sd_event_add_child_pidfd() es similar a sd_event_add_child() pero toma un descriptor de archivo que hace referencia al proceso ("pidfd") en lugar del PID numérico. Se puede obtener un descriptor de archivo adecuado a través de pidfd_open(2) y llamadas relacionadas. El descriptor de archivo pasado no se cierra cuando la fuente de eventos se libera de nuevo, a menos que se utilice sd_event_source_set_child_pidfd_own() para activar este comportamiento. Tenga en cuenta que independientemente de si se utiliza sd_event_add_child() o sd_event_add_child_pidfd() para asignar una fuente de eventos, el proceso vigilado debe ser un proceso hijo directo del proceso que invoca. También en ambos casos SIGCHLD debe estar bloqueado en el proceso que invoca.

sd_event_source_get_child_pid() recupera el PID configurado de una fuente de eventos de cambio de estado de proceso hijo creada previamente con sd_event_add_child(). Toma el objeto fuente de eventos como parámetro source y un puntero a una variable pid_t para devolver el ID del proceso.

sd_event_source_get_child_pidfd() recupera el descriptor de archivo que hace referencia al proceso vigilado ("pidfd"). El bucle de eventos utiliza internamente pidfds para vigilar procesos hijos, independientemente de si las fuentes de eventos individuales se asignan a través de sd_event_add_child() o sd_event_add_child_pidfd(). Si se utilizó esta última llamada para asignar la fuente de eventos, esta función devuelve el descriptor de archivo original utilizado para la asignación. Esta llamada toma el objeto fuente de eventos como parámetro source y devuelve el descriptor de archivo numérico.

sd_event_source_get_child_pidfd_own() se puede utilizar para consultar si el pidfd que encapsula la fuente de eventos debe cerrarse cuando se libera la fuente de eventos. Esta función devuelve cero si el pidfd debe dejarse abierto y positivo si debe cerrarse automáticamente. Por defecto, esta configuración es activa si la fuente de eventos se asignó a través de sd_event_add_child() y desactivada si se asignó a través de sd_event_add_child_pidfd(). La función sd_event_source_set_child_pidfd_own() se puede utilizar para cambiar la configuración y toma un parámetro booleano con la nueva configuración.

sd_event_source_get_child_process_own() se puede utilizar para consultar si el proceso que vigila la fuente de eventos debe ser matado (con SIGKILL) y recogido cuando se libera la fuente de eventos. Esta función devuelve cero si el proceso debe dejarse en ejecución y positivo si debe ser matado y recogido automáticamente. Por defecto, esta configuración es desactivada. DESCRIPCIÓN

Estas funciones se utilizan para registrar un gestor que será llamado cuando un proceso hijo específico termine, entre en un estado de detención o se reanude.

sd_event_add_child() registra un nuevo evento para el proceso hijo identificado por pid. Cuando el proceso hijo cambia de estado según lo especificado por event_mask, el manejador handler es invocado con userdata y un puntero al evento de origen. El manejador puede obtener el PID del hijo con sd_event_source_get_child_pid().

sd_event_add_child_pidfd() es similar, pero en lugar de un PID, se toma un descriptor de archivo de proceso (pidfd_open(2)) que identifica al proceso hijo. El descriptor de archivo se cerrará automáticamente cuando la fuente de eventos se elimine, a menos que sd_event_source_set_child_pidfd_own() se use para establecer la propiedad en falso.

El argumento event_mask es una máscara de bits que puede ser una combinación de las siguientes banderas: WEXITED, WSTOPPED, y WCONTINUED. Vea waitid(2) para más detalles. Si se especifica un cero, el manejo se produce cuando el proceso hijo sale.

Si el manejador es NULL, se utiliza el manejador por defecto, que actualmente termina el bucle de eventos en el que se creó la fuente de eventos, devolviendo el valor pasado en userdata. Actualmente, el valor devuelto por el manejador se pasa como el valor de retorno del bucle de eventos.

A diferencia de waitid(2), estas funciones no pueden usarse para esperar a múltiples hijos. Para monitorear múltiples hijos, se deben crear múltiples fuentes de eventos, una por cada hijo.

sd_event_source_get_child_pid() obtiene el PID del proceso hijo asociado con la fuente de eventos dada.

sd_event_source_get_child_pidfd() y sd_event_source_get_child_pidfd_own() obtienen el descriptor de archivo del proceso hijo y un indicador booleano que muestra si la fuente de eventos es propietaria del descriptor de archivo, respectivamente.

sd_event_source_set_child_pidfd_own() establece el modo de propiedad del descriptor de archivo del proceso hijo para la fuente de eventos dada.

sd_event_source_get_child_process_own() y sd_event_source_set_child_process_own() funcionan de manera similar, pero se refieren a la propiedad del propio proceso hijo, que es lo que ocurre por defecto.

Tenga en cuenta que actualmente si el proceso de llamada se termina de forma anómala, el proceso vigilado podría sobrevivir aunque la fuente de eventos deje de existir. Este comportamiento podría cambiar eventualmente.

sd_event_source_send_child_signal() puede usarse para enviar una señal UNIX al proceso vigilado a través de pidfd_send_signal(2). Los parámetros especificados coinciden con los de la llamada al sistema subyacente, excepto que info nunca se modifica (y por lo tanto se declara constante). Al igual que para la llamada al sistema subyacente, el parámetro flags actualmente debe ser cero.

VALOR DE RETORNO

En caso de éxito, estas funciones devuelven 0 o un entero positivo. En caso de error, devuelven un código de error negativo de estilo errno.

Errores

Los errores devueltos pueden indicar los siguientes problemas:

-ENOMEM

No hay suficiente memoria para asignar un objeto.

-EINVAL

Se ha pasado un argumento no válido. Esto incluye especificar una máscara vacía en options o una máscara que contenga valores diferentes a una combinación de WEXITED, WSTOPPED y WCONTINUED.

-EBUSY

Ya hay un manejador instalado para este proceso hijo, o SIGCHLD no está bloqueado.

-ESTALE

El bucle de eventos ya ha terminado.

-ECHILD

El bucle de eventos se ha creado en un proceso, biblioteca o instancia de módulo diferente.

-EDOM

La fuente de eventos pasada no es una fuente de eventos de proceso hijo.

NOTAS

Las funciones descritas aquí están disponibles como una biblioteca compartida, que se puede compilar y enlazar con el archivo libsystemd pkg-config(1).

El código descrito aquí utiliza getenv(3), que se declara como no seguro para hilos múltiples. Esto significa que el código que llama a las funciones descritas aquí no debe llamar a setenv(3) desde un hilo paralelo. Se recomienda realizar solo llamadas a setenv() desde una fase temprana del programa cuando no se hayan iniciado otros hilos.

EJEMPLO

Ejemplo 1. Salir del bucle cuando el hijo termina

/* SPDX-License-Identifier: MIT-0 */
#define _GNU_SOURCE 1
#include <assert.h>
#include <stdio.h>
#include <unistd.h>
#include <systemd/sd-event.h>
int main(int argc, char **argv) {
  pid_t pid = fork();
  assert(pid >= 0);
  /* La señal SIGCHLD debe estar bloqueada para que sd_event_add_child funcione */
  sigset_t ss;
  sigemptyset(&ss);
  sigaddset(&ss, SIGCHLD);
  sigprocmask(SIG_BLOCK, &ss, NULL);
  if (pid == 0)  /* hijo */
    sleep(1);
  else {         /* padre */
    sd_event *e = NULL;
    int r;
    /* Crear el bucle de eventos por defecto */
    sd_event_default(&e);
    assert(e);
    /* Creamos una fuente de eventos hijo flotante (adjunta a 'e').
     * El manejador por defecto será llamado con 666 como userdata, lo que
     * se convertirá en el valor de salida del bucle. */
    r = sd_event_add_child(e, NULL, pid, WEXITED, NULL, (void*) 666);
    assert(r >= 0);
    r = sd_event_loop(e);
    assert(r == 666);
    sd_event_unref(e);
  }
  return 0;
}
