DESCRIPCIÓN

sd_bus_default() adquiere un objeto de conexión de bus al bus de usuario cuando se invoca dentro de un slice de usuario (cualquier sesión bajo "user-*.slice", por ejemplo: "user@1000.service"), o al bus del sistema en caso contrario. El objeto de conexión está asociado al hilo que lo invoca. Cada vez que la función se invoca desde el mismo hilo, se devuelve el mismo objeto, pero su contador de referencias se incrementa en uno, siempre que se mantenga al menos una referencia. Cuando se suelta la última referencia a la conexión (usando la llamada sd_bus_unref(3)), la conexión se termina. Tenga en cuenta que la conexión no se termina automáticamente cuando finaliza el hilo asociado. Es importante soltar la última referencia a la conexión del bus explícitamente antes de que el hilo finalice, ya que de lo contrario, la conexión se filtrará. Además, los mensajes en cola pero no leídos o no escritos mantienen una referencia al bus, véase más abajo.

sd_bus_default_user() devuelve un objeto de conexión del bus de usuario asociado al hilo que lo invoca. sd_bus_default_system() es similar, pero se conecta al bus del sistema. Tenga en cuenta que sd_bus_default() es idéntico a estas dos llamadas, dependiendo del contexto de ejecución.

sd_bus_open() crea una nueva conexión de bus independiente al bus de usuario cuando se invoca en contexto de usuario, o al bus del sistema en caso contrario. sd_bus_open_user() es similar, pero solo se conecta al bus de usuario. sd_bus_open_system() hace lo mismo, pero se conecta al bus del sistema. A diferencia de sd_bus_default(), sd_bus_default_user() y sd_bus_default_system(), estas llamadas devuelven objetos de conexión nuevos e independientes que no están asociados al hilo que los invoca y no son compartidos entre múltiples invocaciones. Se recomienda compartir conexiones por hilo para hacer un uso eficiente de los recursos disponibles. Por lo tanto, se recomienda utilizar sd_bus_default(), sd_bus_default_user() y sd_bus_default_system() para conectarse a los buses de usuario o del sistema.

sd_bus_open_with_description(), sd_bus_open_user_with_description() y sd_bus_open_system_with_description() son similares a sd_bus_open(), sd_bus_open_user() y sd_bus_open_system(), pero permiten establecer una cadena de descripción, véase sd_bus_set_description(3). description puede ser NULL, en cuyo caso esta función es equivalente a sd_bus_open(). Esta cadena de descripción se utiliza en los mensajes de registro sobre el objeto del bus, y la inclusión de un "nombre" para el bus los hace más fáciles de entender. Algunos mensajes se emiten durante la inicialización del bus, por lo que el uso de esta función es preferible a establecer la descripción más tarde con sd_bus_open_with_description(). El argumento se copia internamente y no se referenciará después de que la función devuelva.

Si la variable de entorno $DBUS_SESSION_BUS_ADDRESS está establecida (cf. environ(7)), se utilizará como la dirección del bus de usuario. Esta variable puede contener múltiples direcciones separadas por ";". Si esta variable no está establecida, se utilizará un valor predeterminado adecuado para la instancia D-Bus de usuario por defecto.

Si la variable de entorno $DBUS_SYSTEM_BUS_ADDRESS está establecida, se utilizará como la dirección del bus del sistema. Esta variable utiliza la misma sintaxis que $DBUS_SESSION_BUS_ADDRESS. Si esta variable no está establecida, se utilizará un valor predeterminado adecuado para la instancia D-Bus del sistema por defecto.

sd_bus_open_system_remote() se conecta al bus del sistema en el host especificado utilizando ssh(1). host consiste en un nombre de usuario opcional seguido del símbolo "@", y el nombre del host, opcionalmente seguido de un ":" y un puerto, opcionalmente seguido de un "/" y un nombre de máquina. Si se proporciona el nombre de la máquina, se crea una conexión al bus del sistema en el contenedor especificado en la máquina remota, y de lo contrario, se crea una conexión al bus del sistema en el host especificado.

Tenga en cuenta que entrar en un contenedor es una operación privilegiada y es probable que solo funcione para el usuario root en la máquina remota.

sd_bus_open_system_machine() se conecta al bus del sistema en la machine especificada, donde machine es el nombre de un contenedor local, posiblemente prefijado por un nombre de usuario y un separador "@". Si el nombre del contenedor se especifica como la cadena especial ".host", la conexión se realiza al sistema local. Esto es útil para conectarse al bus del sistema local como un usuario específico, por ejemplo, "foobar@.host" para conectarse al bus del sistema local como el usuario local "foobar". Si se utiliza la sintaxis "@", se puede omitir el lado izquierdo o el derecho (pero no ambos) en cuyo caso se implica el nombre de usuario local o ".host". Si no se utiliza la sintaxis "@", la conexión se realiza siempre como usuario root. Véase sd_bus_set_address(3) para una descripción de la sintaxis de la dirección, y machinectl(1) para más información sobre el concepto de "máquina". Tenga en cuenta que las conexiones a contenedores locales solo están disponibles para procesos privilegiados en este momento.

sd_bus_open_user_machine() es similar a sd_bus_open_system_machine(), pero se conecta al bus de usuario del usuario root, o si se utiliza la sintaxis "@", del usuario especificado.

Estas llamadas asignan un objeto de conexión de bus e inician la conexión a un bus bien conocido de alguna forma. Una alternativa a utilizar estas llamadas de alto nivel es crear un objeto de bus no conectado con sd_bus_new(3) y conectarlo con sd_bus_start(3).

PROPIEDAD DE REFERENCIA

Las funciones sd_bus_open(), sd_bus_open_user(), sd_bus_open_user_machine(), sd_bus_open_system(), sd_bus_open_system_remote() y sd_bus_open_system_machine() devuelven un nuevo objeto de conexión y el llamante es el único propietario de la referencia. Cuando ya no se necesite, esta referencia debe destruirse con sd_bus_unref(3).

Las funciones sd_bus_default(), sd_bus_default_user() y sd_bus_default_system() no crean necesariamente un nuevo objeto, sino que incrementan la referencia de conexión de un objeto de conexión existente en uno. Utilice sd_bus_unref(3) para soltar la referencia.

Los mensajes en cola pero no escritos/leídos mantienen una referencia a su objeto de conexión de bus. Por esta razón, incluso si una aplicación soltó todas las referencias a una conexión de bus, es posible que no se destruya de inmediato. Hasta que se lean todos los mensajes entrantes en cola, y hasta que se escriban todos los mensajes salientes no escritos, el objeto del bus permanecerá vivo. sd_bus_flush() puede usarse para escribir todos los mensajes salientes en cola para que suelten sus referencias. sd_bus_open_system_machine(3) — systemd-libs — Arch Linux

NAME

sd_bus_open_system_machine, sd_bus_open_user_machine, sd_bus_open_system_machine_with_description, sd_bus_open_user_machine_with_description - connect to the system or user service manager bus of a local or remote container or machine

SYNOPSIS

#include <systemd/sd-bus.h>

int sd_bus_open_system_machine(const char *machine, sd_bus **bus);
int sd_bus_open_user_machine(const char *machine, sd_bus **bus);
int sd_bus_open_system_machine_with_description(const char *machine, const char *description, sd_bus **bus);
int sd_bus_open_user_machine_with_description(const char *machine, const char *description, sd_bus **bus);

DESCRIPTION

The sd_bus_open_system_machine() function connects to the D-Bus system bus of the specified machine (container or VM). The machine parameter is the name of the machine as registered with machinectl(1). This call is equivalent to sd_bus_open_system_with_description(machine_get_bus_name(machine), NULL, bus), where machinectl(1) is a helper utility to query the D-Bus name of a given machine.

The sd_bus_open_user_machine() function connects to the D-Bus user bus of the specified machine. This call is equivalent to sd_bus_open_user_with_description(machine_get_bus_name(machine), NULL, bus).

The sd_bus_open_system_machine_with_description() and sd_bus_open_user_machine_with_description() functions are similar, but allow passing an additional description string that is used in the connection establishment. This description is used by the system and user service managers to identify the client connecting to the bus.

For a description of the bus output parameter and the bus object life cycle, please refer to sd_bus_new(3). If the connection is established successfully, a reference to the new bus object is returned in bus. The caller is responsible for releasing this reference by calling sd_bus_unref(3).

These functions allow clients to connect to the system or user service manager bus of a local or remote container or virtual machine, as managed by systemd-machined.service(8). If the machine parameter is NULL or an empty string, the functions will attempt to connect to the D-Bus bus of the calling process's current machine.

If the connection is established, the returned bus object is already connected and ready for use. The bus object will be configured to use the appropriate connection parameters for the target machine's bus. The connection will be opened asynchronously. Use sd_bus_wait(3) or similar functions to wait for the connection to be established.

To close the connection and free the bus object, use sd_bus_close(). It is recommended to call sd_bus_flush() before sd_bus_close() to ensure all pending messages are sent.

REFERENCE OWNERSHIP

In the common case, you are given a reference to the bus object which is unique and must be released with sd_bus_unref(3) when you are done with it. It is not valid to call sd_bus_close() on such a bus object, as this will only close the connection, but not release the bus object itself. It is a bug to incorrectly unreference, or close, a bus object returned by these functions.

If the return value is NULL, no reference is returned. If the return value is positive, a reference to the bus object is returned. If the return value is negative, an error code is returned and bus is set to NULL. The reference count of the bus object is then zero, and it should not be used further.

When using the default bus logic, it is a good idea to first invoke sd_bus_flush() followed by sd_bus_close() when a thread or process terminates, and thus its bus connection object should be freed.

Normally, slot objects (as created by sd_bus_add_match(3) and similar calls) keep a reference to their bus connection object, too. Thus, as long as a bus slot object remains referenced its bus object will remain allocated too. Optionally, bus slot objects may be placed in "floating" mode. When in floating mode the life cycle of the bus slot object is bound to the bus object, i.e. when the bus object is freed the bus slot object is automatically unreferenced too. The floating state of a slot object may be controlled explicitly with sd_bus_slot_set_floating(3), though usually floating bus slot objects are created by passing NULL as the slot parameter of sd_bus_add_match() and related calls, thus indicating that the caller is not directly interested in referencing and managing the bus slot object.

The life cycle of the default bus connection should be the responsibility of the code that creates/owns the thread the default bus connection object is associated with. Library code should neither call sd_bus_flush() nor sd_bus_close() on default bus objects unless it does so in its own private, self-allocated thread. Library code should not use the default bus object in other threads unless it is clear that the program using it will life cycle the bus connection object and flush and close it before exiting from the thread. In libraries where it is not clear that the calling program will life cycle the bus connection object, it is hence recommended to use sd_bus_open_system() instead of sd_bus_default_system() and related calls.

RETURN VALUE

On success, these calls return 0 or a positive integer. On failure, these calls return a negative errno-style error code.

Errors

Returned errors may indicate the following problems:

-EINVAL

The specified parameters are invalid.

-ENOMEDIUM

The requested bus type is not available because of invalid environment (for example the user session bus is not available because $XDG_RUNTIME_DIR is not set).

-ENOMEM

Memory allocation failed.

-ESOCKTNOSUPPORT

The protocol version required to connect to the selected bus is not supported.

In addition, other connection-related errors may be returned. See sd_bus_send(3).

NOTES

Functions described here are available as a shared library, which can be compiled against and linked to with the libsystemd pkg-config(1) file.

The code described here uses getenv(3), which is declared to be not multi-thread-safe. This means that the code calling the functions described here must not call setenv(3) from a parallel thread. It is recommended to only do calls to setenv() from an early phase of the program when no other threads have been started.
