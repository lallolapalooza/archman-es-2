DESCRIPCIÓN

systemd-stub (almacenado en archivos por arquitectura linuxx64.efi.stub, linuxia32.efi.stub, linuxaa64.efi.stub en disco) es una sencilla stub de arranque UEFI. Una stub de arranque UEFI se adjunta a una imagen binaria de kernel de Linux y es una pieza de código que se ejecuta en el entorno del firmware UEFI antes de pasar al entorno del kernel de Linux. La stub de arranque UEFI garantiza que un kernel de Linux sea ejecutable como un binario UEFI regular y es capaz de realizar diversas preparaciones antes de cambiar el sistema al mundo Linux.

La stub de arranque UEFI busca varios recursos para la invocación del kernel dentro del propio binario PE de UEFI. Esto permite combinar varios recursos dentro de una única imagen binaria PE (una "Imagen de Kernel Unificada" o "UKI" para abreviar), que luego puede firmarse mediante UEFI SecureBoot en su totalidad, cubriendo todos los recursos individuales a la vez. Específicamente, puede incluir las siguientes secciones PE:

•Una sección ".linux" con la imagen del kernel de Linux ELF. Esta sección es obligatoria.
•Una sección opcional ".osrel" con información de la versión del SO, es decir, el contenido del archivo os-release(5) del SO al que pertenece el kernel.
•Una sección opcional ".cmdline" con la línea de comandos del kernel para pasar al kernel invocado.
•Una sección opcional ".initrd" con el initrd.
•Una sección opcional ".ucode" con un initrd que contiene microcódigo, para ser entregado al kernel antes que cualquier otro initrd. Este initrd no debe estar comprimido.
•Una sección opcional ".splash" con una imagen (en formato .BMP de Windows) para mostrar en pantalla antes de invocar al kernel.
•Una sección opcional ".dtb" con un DeviceTree binario compilado.
•Cero o más secciones ".dtbauto". systemd-stub siempre usará la primera que coincida. La coincidencia se realiza tomando la primera cadena "compatible" del DeviceTree suministrada por el firmware en las tablas de configuración y comparándola con la primera cadena "compatible" de cada una de las secciones ".dtbauto". Si el firmware no proporciona un DeviceTree, la coincidencia se realiza utilizando la sección ".hwids" en su lugar. Después de seleccionar una sección ".hwids" (ver la descripción a continuación), la cadena "compatible" de esa sección se utilizará para realizar el mismo procedimiento de coincidencia. Si se encuentra una coincidencia, esa sección ".dtbauto" se cargará y anulará a ".dtb" si está presente.
•Cero o más secciones ".efifw" para la imagen del firmware. Funciona de manera similar a las secciones ".dtbauto". systemd-stub siempre usará la primera que coincida. La coincidencia se realiza seleccionando primero la entrada más apropiada en la sección ".hwids" basándose en los ID de hardware suministrados por SMBIOS (ver más abajo). Si se encuentra una entrada adecuada, la cadena "fwid" de esa entrada se utilizará para realizar el procedimiento de coincidencia para los blobs de firmware en la sección ".efifw". Se cargará el primer firmware coincidente.
•Cero o más secciones ".hwids" con IDs de hardware de las máquinas para hacer coincidir los DeviceTrees. systemd-stub utilizará los datos SMBIOS para calcular los IDs de hardware de la máquina (según la especificación[1]), y luego intentará encontrar alguno de ellos en cada una de las secciones ".hwids". Se utilizará la primera sección coincidente.
•Una sección opcional ".uname" con información de la versión del kernel, es decir, la salida de uname -r para el kernel incluido en la sección ".linux".
•Una sección opcional ".sbat" con metadatos de revocación de SBAT[2].
•Una sección opcional ".pcrsig" con un conjunto de firmas criptográficas para los valores esperados de PCR de TPM2 después de que el kernel se haya iniciado, en formato JSON. Esto es útil para implementar políticas de TPM2 que vinculan el cifrado de disco y similares a kernels firmados por una clave específica.
•Una sección opcional ".pcrpkey" con una clave pública en formato PEM que coincide con los datos de firma en la sección ".pcrsig".

En una UKI básica, las secciones enumeradas anteriormente aparecen como máximo una vez, con la excepción de las secciones ".dtbauto" y ".hwids". En una UKI multi-perfil, múltiples conjuntos de estas secciones están presentes en un solo archivo y forman "perfiles", uno de los cuales se puede seleccionar al arrancar. Para esto, se define la sección PE ".profile" para ser utilizada como separador entre conjuntos de secciones. La propia sección ".profile" puede contener metainformación sobre la sección y sigue una estructura similar a la del contenido de la sección ".osrel". Para más detalles sobre UKIs multi-perfil, ver más abajo.

Si UEFI SecureBoot está habilitado y la sección ".cmdline" está presente en la imagen ejecutada, se ignorarán todos los intentos de anular la línea de comandos del kernel pasándola como parámetros de invocación al binario EFI. Por lo tanto, para permitir la anulación de la línea de comandos del kernel, deshabilite UEFI SecureBoot o no incluya una sección PE de línea de comandos del kernel en el archivo de imagen del kernel. Si se acepta una línea de comandos a través de parámetros de invocación EFI al binario EFI, se medirá en el TPM PCR 12 (si hay un TPM presente).

Si un DeviceTree está incrustado en la sección ".dtb", reemplaza un DeviceTree existente en la tabla de configuración EFI correspondiente. systemd-stub solicitará al firmware a través del protocolo "EFI_DT_FIXUP_PROTOCOL" correcciones específicas del hardware para el DeviceTree.

El contenido de 11 de estas 12 secciones se mide en el TPM PCR 11. De lo contrario, no se utiliza y, por lo tanto, el resultado se puede precalcular sin demasiado esfuerzo. La sección ".pcrsig" no se incluye en esta medición PCR, ya que se supone que contiene firmas para la salida de la operación de medición y, por lo tanto, no puede ser una entrada para ella. Si una UKI contiene múltiples perfiles, solo las secciones PE del perfil seleccionado (y las del perfil base, a menos que se anulen) se miden.

Si es distinto de cero, el perfil numérico seleccionado se mide en el PCR 12.

Cuando las secciones ".pcrsig" y/o ".pcrpkey" están presentes en una imagen de kernel unificada, su contenido se pasa al kernel arrancado en un archivo de initrd cpio sintético que los coloca en los archivos /.extra/tpm2-pcr-signature.json y /.extra/tpm2-pcr-public-key.pem. Típicamente, una línea de tmpfiles.d(5) asegura entonces que se copien en /run/systemd/tpm2-pcr-signature.json y /run/systemd/tpm2-pcr-public-key.pem donde permanecen accesibles incluso después de que el sistema transicione del entorno initrd al sistema de archivos del host. Herramientas como systemd-cryptsetup@.service(8), systemd-cryptenroll(1) y systemd-creds(1) utilizarán automáticamente los archivos presentes en estas rutas para desbloquear recursos protegidos (almacenamiento cifrado o credenciales) o vincular el cifrado a kernels arrancados.

Para más detalles sobre el concepto de UKI, ver la especificación UKI[3].

ARCHIVOS COMPAÑEROS

La stub de arranque UEFI systemd-stub recopila automáticamente tres tipos de archivos auxiliares compañeros opcionalmente colocados en directorios de sustitución en la misma partición que el binario EFI, genera dinámicamente archivos initrd cpio a partir de ellos y los pasa al kernel. ly:

•Para un binario del kernel llamado foo.efi, buscará archivos con la extensión .cred en un directorio llamado foo.efi.extra.d/ adyacente. Si el binario del kernel utiliza un contador para el propósito de la Evaluación Automática de Arranque[4], este contador será ignorado. Por ejemplo, foo+3-0.efi buscará en el directorio foo.efi.extra.d/. Se genera un archivo cpio a partir de todos los archivos encontrados de esta manera, colocándolos en el directorio /.extra/credentials/ de la jerarquía de archivos initrd. El initrd principal podrá acceder a ellos en este directorio. Esto se supone que se utiliza para almacenar credenciales auxiliares, cifradas y autenticadas para su uso con LoadCredentialEncrypted en la Partición del Sistema UEFI. Consulte systemd.exec(5) y systemd-creds(1) para obtener detalles sobre credenciales cifradas. El archivo cpio generado se mide en el PCR 12 de TPM (si hay un TPM presente).
•De manera similar, los archivos foo.efi.extra.d/*.sysext.raw se empaquetan en un archivo cpio y se colocan en el directorio /.extra/sysext/ en la jerarquía de archivos initrd. Esto se supone que se utiliza para pasar imágenes de extensión del sistema adicionales específicas de UKI al initrd. Consulte systemd-sysext(8) para obtener detalles sobre imágenes de extensión del sistema. El archivo cpio generado que contiene estas imágenes de extensión del sistema se mide en el PCR 13 de TPM (si hay un TPM presente).
•De manera similar, los archivos /loader/extensions/*.sysext.raw se empaquetan en un archivo cpio y se colocan en el directorio /.extra/global_sysext/ en la jerarquía de archivos initrd. Esto se supone que se utiliza para pasar imágenes de extensión del sistema globales adicionales al initrd. Consulte systemd-sysext(8) para obtener detalles sobre imágenes de extensión del sistema. El archivo cpio generado que contiene estas imágenes de extensión del sistema se mide en el PCR 13 de TPM (si hay un TPM presente).
•De manera similar, los archivos foo.efi.extra.d/*.confext.raw se empaquetan en un archivo cpio y se colocan en el directorio /.extra/confext/ en la jerarquía de archivos initrd. Esto se supone que se utiliza para pasar imágenes de extensión de configuración adicionales específicas de UKI al initrd. Consulte systemd-confext(8) para obtener detalles sobre imágenes de extensión de configuración. El archivo cpio generado que contiene estas imágenes de extensión de configuración se mide en el PCR 12 de TPM (si hay un TPM presente).
•De manera similar, los archivos /loader/extensions/*.confext.raw se empaquetan en un archivo cpio y se colocan en el directorio /.extra/global_confext/ en la jerarquía de archivos initrd. Esto se supone que se utiliza para pasar imágenes de extensión de configuración globales adicionales al initrd. Consulte systemd-confext(8) para obtener detalles sobre imágenes de extensión de configuración. El archivo cpio generado que contiene estas imágenes de extensión de configuración se mide en el PCR 12 de TPM (si hay un TPM presente).
•De manera similar, los archivos foo.efi.extra.d/*.addon.efi se cargan y verifican como binarios PE, y se cargan secciones específicas de ellos. Los complementos se utilizan para pasar parámetros de línea de comandos del kernel adicionales (".cmdline"), o blobs de DeviceTree (".dtb"), initrds adicionales (".initrd") y actualizaciones de microcódigo (".ucode"). Los complementos permiten pasar estos recursos independientemente de la versión del kernel que se esté arrancando, permitiendo por ejemplo que los proveedores de plataformas distribuyan configuraciones específicas de la plataforma.

En caso de que Secure Boot esté habilitado, estos archivos serán validados usando claves en la DB de UEFI, la DB de Shim o el MOK de Shim, y solo se cargarán si la verificación es exitosa. Adicionalmente, si tanto el complemento como el UKI contienen una sección ".uname", el complemento será rechazado si no coinciden exactamente. Se recomienda añadir siempre una sección ".sbat" a todos los complementos firmados, para que puedan ser revocados con una actualización de la política de SBAT, sin necesidad de incluirlos en la lista negra mediante DBX/MOKX. La herramienta ukify(1) añadirá una política de SBAT por defecto si no se proporciona ninguna al construir complementos. Para más información sobre SBAT consulte la documentación de Shim[2].

Los archivos de complementos se ordenan, cargan y miden en el PCR 12 de TPM (si hay un TPM presente) y se añaden a la línea de comandos del kernel. Las opciones de línea de comandos del UKI se listan primero, luego las opciones de los complementos en /loader/addons/*.addon.efi, y finalmente los complementos específicos del UKI. Los blobs de Device Tree se cargan y miden siguiendo el mismo algoritmo. Los complementos de microcódigo se pasan al kernel en orden inverso (complementos específicos del UKI, complementos globales, sección incrustada del UKI). Esto se debe a que el controlador de actualización de microcódigo se detiene en el primer nombre de archivo coincidente. Los complementos siempre se cargan en el mismo orden según el nombre del archivo, de modo que, dado el mismo conjunto de complementos, se puede esperar el mismo conjunto de mediciones en el PCR12. Sin embargo, tenga en cuenta que el nombre del archivo no está protegido por la firma PE, y como tal, un atacante con acceso de escritura al ESP podría potencialmente renombrar estos archivos para cambiar el orden en que se cargan, de una manera que podría alterar la funcionalidad del kernel, ya que algunas opciones podrían depender del orden. Si firma tales complementos, debe prestar atención a los valores del PCR12 y utilizar un servicio de atestación para que el uso indebido de sus complementos firmados pueda ser detectado y tratado utilizando uno de los mecanismos de revocación mencionados.

•Los archivos /loader/credentials/*.cred se empaquetan en un archivo cpio y se colocan en el directorio /.extra/global_credentials/ de la jerarquía de archivos initrd. Esto se supone que se utiliza para pasar credenciales adicionales al initrd, independientemente de la versión del kernel que se esté arrancando. El archivo cpio generado se mide en el PCR 12 de TPM (si hay un TPM presente).
•Adicionalmente, los archivos /loader/addons/*.addon.efi se cargan y verifican como binarios PE, y se analizan en ellos las secciones ".cmdline", ".dtb", ".initrd" y ".ucode". Esto se supone que se utiliza para pasar parámetros de línea de comandos adicionales, blobs de DeviceTree, initrds y actualizaciones de microcódigo al kernel, independientemente de la versión del kernel que se esté arrancando.

Estos mecanismos pueden utilizarse para parametrizar y extender imágenes initrd inmutables y confiables (es decir, firmadas) de una manera razonablemente segura: todos los datos que contienen se miden en los PCR de TPM. En el acceso deben validarse adicionalmente: en el caso de las credenciales cifrándolas/autenticándolas a través de TPM, como expone systemd-creds encrypt -T (consulte systemd-creds(1) para obtener detalles); en el caso de las imágenes de extensión del sistema utilizando imágenes Verity firmadas.

UKIS MULTIPERFIL

En muchos contextos es útil permitir la invocación de un único UKI en múltiples modos (o "perfiles") diferentes sin comprometer la integridad criptográfica, las mediciones y demás del proceso de arranque. Por ejemplo, un único UKI podría proporcionar tres perfiles distintos: uno de arranque normal, uno que invoca una operación de "restablecimiento de fábrica" y uno que arranca en modo de destino de almacenamiento (como en systemd-storagetm.service(8)). Cada perfil utilizaría entonces las mismas secciones ".linux" y ".initrd", pero tendría una sección ".cmdline" separada. Por ejemplo, los dos últimos perfiles extenderían la línea de comandos del kernel normal con "systemd.unit=factory-reset.target" o "rd.systemd.unit=storagetm.target".

Un único UKI puede soportar múltiples perfiles mediante la sección especial PE ".profile". Esta sección actúa como separador entre las secciones PE de los perfiles individuales. Por lo tanto, las secciones PE ".profile" pueden aparecer varias veces en un único UKI, y las otras secciones PE enumeradas anteriormente también pueden aparecer varias veces, si se utilizan ".profile", pero solo una vez antes de la primera sección ".profile", una vez entre cada par subsiguiente, y una vez después de la última aparición de ".profile". Las secciones listadas antes de la primera sección ".profile" se consideran el perfil "base" del UKI. Cada sección ".profile" introduce entonces un nuevo perfil, que se numera a partir de cero. Las secciones PE que siguen a cada ".profile" son específicas de ese perfil. Al arrancar en un perfil específico, los perfiles de la sección base se utilizan en combinación con las secciones del perfil específico: si la misma sección está definida en ambos, la sección por perfil anula la versión del perfil base, de lo contrario se utilizan las secciones del perfil base.

Un UKI que no contenga ".profile" se considera equivalente a uno que solo contenga una única ".profile", como si tuviera un solo perfil "@0".

Si el primer argumento no se especifica de esa manera, el UKI arrancará automáticamente en el perfil 0.

NAME

sd-stub – systemd EFI boot stub

SYNOPSIS

sd-stub

DESCRIPTION

The sd-stub is an EFI executable that may be used as the systemd-boot(7) loader entry’s efi-stub. It is designed to be embedded within a Unified Kernel Image (UKI) alongside the kernel binary itself.

When booted, sd-stub performs several tasks:

  • Determines the boot mode (e.g., interactive or automatic) based on configuration.
  • Optionally measures PCRs (Platform Configuration Registers) in a Trusted Platform Module (TPM).
  • Optionally verifies the kernel and initrd.
  • Sets up the kernel command line.
  • Executes the kernel.

The primary goal of sd-stub is to make the boot process more secure and auditable, especially in environments requiring measured boot or confidential computing.

COMPANION FILES

The sd-stub may embed or load companion files required for boot-time operations. These files are typically included within the UKI itself or loaded from specific locations during the early boot process.

Kernel command line

Kernel command line arguments can be provided via multiple sources:

  • Embedded within the UKI itself, typically in a dedicated section.
  • Passed by the bootloader (e.g., systemd-boot(7)).
  • Read from EFI variables.
  • Read from SMBIOS Type 11 strings.

The final kernel command line is a combination of these sources, with specific precedence rules applied.

MULTI-PROFILE UKIS

The sd-stub supports Unified Kernel Images (UKIs) that contain multiple profiles. A profile allows different boot configurations to be embedded within a single UKI, selectable at boot time. This is often managed through the systemd-boot(7) configuration or other bootloader mechanisms.

When multiple profiles are present, sd-stub will attempt to select the appropriate profile based on bootloader arguments or other runtime conditions.

TPM PCR NOTES

When TPM2 support is enabled, sd-stub performs measurements into specific PCRs. These measurements help ensure the integrity of the boot process.

PCR 0-7:
Typically used by the firmware for platform integrity measurements.
PCR 8:
Often used for measurements related to boot configuration and loader decisions.
PCR 9:
May be used for measurements related to bootloader configuration.
PCR 10:
May be used for measurements related to Secure Boot and kernel parameters.
PCR 11:
Often used for measurements related to the kernel command line and initrd.
PCR 12:
May be used for measurements related to extended kernel command line parameters.
PCR 13:
May be used for measurements related to the initrd contents.
PCR 14:
May be used for measurements related to system extensions (sysext).
PCR 15:
Reserved or used for specific system configurations.

The exact PCR usage may vary depending on the system configuration and the specific version of sd-stub and related firmware.

EFI VARIABLES

Configuration for sd-stub can be provided through EFI variables. These variables allow runtime modification of boot parameters without altering the UKI image itself.

Specific EFI variables used by sd-stub include:

  • LoaderConfigParameters: May contain additional kernel command line parameters.
  • KernelCmdLine: May contain the primary kernel command line.

The interpretation and use of these variables depend on the bootloader and the specific configuration.

INITRD RESOURCES

During its execution, sd-stub may utilize or extract certain resources into the initrd environment. These resources are typically part of the UKI and are made available in the early boot process.

The following files are placed in the /.extra/ directory within the initrd filesystem:

/.extra/tpm2-pcr-signature.json

The PCR signature data from the ".pcrsig" PE section of the unified kernel image is copied into the /.extra/tpm2-pcr-signature.json file in the initrd execution environment.

Added in version 252.

/.extra/tpm2-pcr-public-key.pem

The PEM public key included in the ".pcrpkey" PE section of the unified kernel image is copied into the /.extra/tpm2-pcr-public-key.pem file in the initrd execution environment.

Added in version 252.

/.extra/profile, /.extra/os-release

The contents of the ".profile" and ".osrel" sections of the selected profile, if any.

Added in version 257.

Note that all these files are located in the "tmpfs" file system the kernel sets up for the initrd file hierarchy and are thus lost when the system transitions from the initrd execution environment into the host file system. If these resources shall be kept around over this transition they need to be copied to a place that survives the transition first, for example via a suitable tmpfiles.d(5) line. By default, this is done for the TPM2 PCR signature and public key files.

SMBIOS TYPE 11 STRINGS

systemd-stub can be configured using SMBIOS Type 11 strings. Applicable strings consist of a name, followed by "=", followed by the value. Unless systemd-stub detects it is running inside a confidential computing environment, systemd-stub will search the table for a string with a specific name, and if found, use its value. The following strings are read:

io.systemd.stub.kernel-cmdline-extra

If set, the value of this string is added to the list of kernel command line arguments that are measured in PCR12 and passed to the kernel.

Added in version 254.

ASSEMBLING KERNEL IMAGES

In order to assemble a bootable Unified Kernel Image from various components as described above, use ukify(1).
