sd_journal_get_timeout(3)

SD_JOURNAL_GET_FD(3) sd_journal_get_fd SD_JOURNAL_GET_FD(3)

NOMBRE

sd_journal_get_fd, sd_journal_get_events, sd_journal_get_timeout, sd_journal_process, sd_journal_wait, sd_journal_reliable_fd, SD_JOURNAL_NOP, SD_JOURNAL_APPEND, SD_JOURNAL_INVALIDATE - Interfaz de notificación de cambios en el registro (journal)

SINOPSIS

#include <systemd/sd-journal.h>

int sd_journal_get_fd(sd_journal *j);

int sd_journal_get_events(sd_journal *j);

int sd_journal_get_timeout(sd_journal *j, uint64_t *timeout_usec);

int sd_journal_process(sd_journal *j);

int sd_journal_wait(sd_journal *j, uint64_t timeout_usec);

int sd_journal_reliable_fd(sd_journal *j);

DESCRIPCIÓN

sd_journal_get_fd() devuelve un descriptor de archivo que puede ser consultado de forma asíncrona en un bucle de eventos externo y que se señaliza tan pronto como el registro (journal) cambia, porque se agregaron nuevas entradas o archivos, tuvo lugar una rotación, o se eliminaron archivos, y similares. El descriptor de archivo es adecuado para su uso en poll(2). Utilice sd_journal_get_events() para una máscara de eventos a la que prestar atención. La llamada toma un argumento: el objeto de contexto del registro (journal). Tenga en cuenta que no todos los sistemas de archivos son capaces de generar los eventos necesarios para despertar de este descriptor de archivo para que los cambios se noten inmediatamente. En particular, los sistemas de archivos de red no generan eventos de cambio de archivo adecuados en todos los casos. Casos como estos pueden ser detectados con sd_journal_reliable_fd(), más abajo. sd_journal_get_timeout() asegurará en estos casos que los despertares ocurran con suficiente frecuencia para que los cambios sean notados, aunque con cierta latencia.

sd_journal_get_events() devolverá la máscara de poll() a esperar. Esta función devolverá una combinación de POLLIN y POLLOUT y similares para rellenar en el campo ".events" de struct pollfd.

sd_journal_get_timeout() devolverá un valor de tiempo de espera para su uso en poll(). Esto devuelve un valor en microsegundos desde la época de CLOCK_MONOTONIC para agotar el tiempo de espera de poll() en timeout_usec. Consulte clock_gettime(2) para obtener detalles sobre CLOCK_MONOTONIC. Si no hay tiempo de espera, se rellenará con (uint64_t) -1 en su lugar. Tenga en cuenta que poll() toma un tiempo de espera relativo en milisegundos en lugar de un tiempo de espera absoluto en microsegundos. Para convertir el tiempo de espera absoluto 'us' en 'ms' relativo, utilice código como el siguiente:

uint64_t t;
int msec;
sd_journal_get_timeout(m, &t);
if (t == (uint64_t) -1)
  msec = -1;
else {
  struct timespec ts;
  uint64_t n;
  clock_gettime(CLOCK_MONOTONIC, &ts);
  n = (uint64_t) ts.tv_sec * 1000000 + ts.tv_nsec / 1000;
  msec = t > n ? (int) ((t - n + 999) / 1000) : 0;
}

El código anterior no realiza ninguna comprobación de errores por brevedad. El entero msec calculado se puede pasar directamente como parámetro de tiempo de espera de poll().

Después de cada despertar de poll(), se debe llamar a sd_journal_process() para procesar los eventos. Esta llamada también indicará qué tipo de cambio se ha detectado (ver más abajo; tenga en cuenta que son posibles despertares espurios).

Una alternativa síncrona para usar sd_journal_get_fd(), sd_journal_get_events(), sd_journal_get_timeout() y sd_journal_process() es sd_journal_wait(). Esperará síncronamente hasta que el registro (journal) cambie. El tiempo máximo que esta llamada duerme puede ser controlado con el parámetro timeout_usec. Pase (uint64_t) -1 para esperar indefinidamente. Internamente, esta llamada simplemente combina sd_journal_get_fd(), sd_journal_get_events(), sd_journal_get_timeout(), poll() y sd_journal_process() en una sola.

sd_journal_reliable_fd() puede usarse para verificar si los eventos de despertar del descriptor de archivo devuelto por sd_journal_get_fd() se sabe que se activan rápidamente. En ciertos sistemas de archivos donde los eventos de cambio de archivo del SO no están disponibles (como NFS), los cambios deben ser consultados repetidamente y, por lo tanto, solo se detectan con una latencia considerable. Esta llamada devolverá un valor positivo si los cambios del registro (journal) se detectan rápidamente y cero si se necesita consultarlos. Tenga en cuenta que generalmente no hay necesidad de invocar esta función directamente, ya que sd_journal_get_timeout() solicitará tiempos de espera apropiados de todos modos.

Tenga en cuenta que ninguna de las interfaces de notificación de cambios mencionadas anteriormente informa los cambios al instante. Se introducen latencias por múltiples razones: como se mencionó, ciertos backends de almacenamiento requieren sondeos basados en tiempo, en otros casos los despertares se optimizan agrupando eventos, y el SO introduce latencias adicionales de planificación de E/S/CPU.

VALOR DE RETORNO

sd_journal_get_fd() devuelve un descriptor de archivo válido en caso de éxito o un código de error negativo de estilo errno.

sd_journal_get_events() devuelve una combinación de POLLIN, POLLOUT y similares en caso de éxito o un código de error negativo de estilo errno.

sd_journal_reliable_fd() devuelve un entero positivo si el descriptor de archivo devuelto por sd_journal_get_fd() generará despertares inmediatamente para todos los cambios del registro (journal). Devuelve 0 si podría haber una latencia involucrada.

sd_journal_process() y sd_journal_wait() devuelven un código de error negativo de estilo errno, o uno de SD_JOURNAL_NOP, SD_JOURNAL_APPEND o SD_JOURNAL_INVALIDATE en caso de éxito:

•Si se devuelve SD_JOURNAL_NOP, el registro (journal) no ha cambiado desde la última invocación.
•Si se devuelve SD_JOURNAL_APPEND, se han agregado nuevas entradas al final del registro (journal). En este caso, es suficiente continuar leyendo en la ubicación anterior del final del registro (journal) para leer las entradas recién agregadas.
•Si se devuelve SD_JOURNAL_INVALIDATE, se han agregado o eliminado archivos del registro (journal) del conjunto de archivos del registro (journal) observados (por ejemplo, debido a rotación o limpieza), y por lo tanto, las entradas pueden haber aparecido o desaparecido en lugares arbitrarios del flujo de registro, posiblemente antes o después del final anterior del flujo de registro. Si se devuelve SD_JOURNAL_INVALIDATE, las interfaces de vista en vivo que quieran reflejar en pantalla el estado preciso de los datos del registro (journal) en disco probablemente deberían actualizar su visualización completa (en relación con el cursor de la entrada del registro en la parte superior de la pantalla). Los programas interesados únicamente en un flujo estrictamente secuencial de datos de registro pueden tratar SD_JOURNAL_INVALIDATE de la misma manera que SD_JOURNAL_APPEND, ignorando así cualquier cambio en la vista del registro anterior al final antiguo del flujo de registro.

SEGURIDAD DE SEÑALES

En general, sd_journal_get_fd(), sd_journal_get_events(), y sd_journal_get_timeout() *no* son "seguros para señales asíncronas" en el sentido de signal-safety(7). Sin embargo, solo la primera llamada a cualquiera de estas tres funciones realiza operaciones inseguras, por lo que las llamadas subsiguientes *son* seguras.

sd_journal_process() y sd_journal_wait() no son seguros. sd_journal_reliable_fd() es seguro.

NOTAS

Todas las funciones descritas aquí son agnósticas a hilos y solo un único hilo puede operar en un objeto dado en cualquier momento dado. Diferentes hilos pueden acceder al mismo objeto en momentos diferentes. Múltiples objetos independientes pueden ser utilizados desde diferentes hilos en paralelo.

Las funciones descritas aquí están disponibles como una biblioteca compartida, que puede ser compilada y enlazada con el archivo libsystemd pkg-config(1).

Esperando con poll() (este ejemplo carece de todo control de errores por motivos de simplicidad):

/* SPDX-License-Identifier: MIT-0 */
#define _GNU_SOURCE 1
#include <poll.h>
#include <time.h>
#include <systemd/sd-journal.h>
int wait_for_changes(sd_journal *j) {
  uint64_t t;
  int msec;
  struct pollfd pollfd;
  sd_journal_get_timeout(j, &t);
  if (t == (uint64_t) -1)
    msec = -1;
  else {
    struct timespec ts;
    uint64_t n;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    n = (uint64_t) ts.tv_sec * 1000000 + ts.tv_nsec / 1000;
    msec = t > n ? (int) ((t - n + 999) / 1000) : 0;
  }
  pollfd.fd = sd_journal_get_fd(j);
  pollfd.events = sd_journal_get_events(j);
  poll(&pollfd, 1, msec);
  return sd_journal_process(j);
}
