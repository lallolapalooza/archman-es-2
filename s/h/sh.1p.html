PRÓLOGO

Esta página de manual es parte del Manual del Programador POSIX. La implementación de esta interfaz en Linux puede diferir (consulte la página de manual correspondiente de Linux para conocer los detalles del comportamiento de Linux), o la interfaz puede no estar implementada en Linux.

NOMBRE

sh — shell, el intérprete estándar del lenguaje de comandos

SINOPSIS

sh [-abCefhimnuvx] [-o opción]... [+abCefhimnuvx] [+o opción]...
    [archivo_comando [argumento...]]
sh -c [-abCefhimnuvx] [-o opción]... [+abCefhimnuvx] [+o opción]...
    cadena_comando [nombre_comando [argumento...]]
sh -s [-abCefhimnuvx] [-o opción]... [+abCefhimnuvx] [+o opción]...
    [argumento...]

DESCRIPCIÓN

La utilidad sh es un intérprete de lenguaje de comandos que ejecutará comandos leídos desde una cadena de línea de comandos, la entrada estándar o un archivo especificado. La aplicación garantizará que los comandos que se ejecutarán estén expresados en el lenguaje descrito en el Capítulo 2, Lenguaje de Comandos del Shell.

La expansión de nombres de ruta no fallará debido al tamaño de un archivo.

Las redirecciones de entrada y salida del shell tienen un desplazamiento máximo definido por la implementación que se establece en la descripción del archivo abierto.

OPCIONES

La utilidad sh se ajustará a las Definiciones Base del volumen POSIX.1‐2017, Sección 12.2, Directrices de Sintaxis de Utilidades, con una extensión para admitir un signo de más (<signo más>) ('+') como se indica a continuación.

Las opciones -a, -b, -C, -e, -f, -m, -n, -o opción, -u, -v y -x se describen como parte de la utilidad set en Sección 2.14, Utilidades Especiales Integradas. Las letras de opción derivadas de la utilidad especial set también se aceptarán con un signo de más (<signo más>) ('+') en lugar de un guion menos (<guion menos>) (lo que significa el caso inverso de la opción como se describe en este volumen de POSIX.1‐2017).

Las siguientes opciones adicionales deberán ser soportadas:

-c
Lee comandos de la operando cadena_comando. Establece el valor del parámetro especial 0 (ver Sección 2.5.2, Parámetros Especiales) a partir del valor del operando nombre_comando y los parámetros posicionales ($1, $2, etc.) en secuencia a partir de los operandos argumento restantes. No se leerán comandos de la entrada estándar.
-i
Especifica que el shell es interactivo; ver más abajo. Una implementación puede tratar la especificación de la opción -i como un error si el ID de usuario real del proceso que llama no es igual al ID de usuario efectivo o si el ID de grupo real no es igual al ID de grupo efectivo.
-s
Lee comandos de la entrada estándar.

Si no hay operandos y la opción -c no está especificada, se asumirá la opción -s.

Si está presente la opción -i, o si no hay operandos y la entrada estándar y la salida de error del shell están conectadas a una terminal, el shell se considerará interactivo.

OPERANDOS

Los siguientes operandos deberán ser soportados:

-
Un solo guion menos (<guion menos>) se tratará como el primer operando y luego se ignorará. Si tanto '-' como "--" se proporcionan como argumentos, o si otros operandos preceden al guion menos simple, los resultados son indefinidos.
argumento
Los parámetros posicionales ($1, $2, etc.) se establecerán a argumentos, si los hay.
archivo_comando
El nombre de ruta de un archivo que contiene comandos. Si el nombre de ruta contiene uno o más caracteres de barra (<barra>):
*
La implementación intentará leer ese archivo; el archivo no necesita ser ejecutable.
*
Si el nombre de ruta no contiene un carácter de barra (<barra>):
*
La implementación intentará leer ese archivo desde el directorio de trabajo actual; el archivo no necesita ser ejecutable.
*
Si el archivo no está en el directorio de trabajo actual, la implementación puede realizar una búsqueda de un archivo ejecutable utilizando el valor de PATH, como se describe en Sección 2.9.1.1, Búsqueda y Ejecución de Comandos.

El parámetro especial 0 (ver Sección 2.5.2, Parámetros Especiales) se establecerá al valor de archivo_comando. Si sh se llama usando una forma de sinopsis que omite archivo_comando, el parámetro especial 0 se establecerá al valor del primer argumento pasado a sh desde su padre (por ejemplo, argv[0] para un programa C), que normalmente es un nombre de ruta utilizado para ejecutar la utilidad sh.

nombre_comando

Una cadena asignada al parámetro especial 0 al ejecutar los comandos en cadena_comando. Si nombre_comando no se especifica, el parámetro especial 0 se establecerá al valor del primer argumento pasado a sh desde su padre (por ejemplo, argv[0] para un programa C), que normalmente es un nombre de ruta utilizado para ejecutar la utilidad sh.
cadena_comando

Una cadena que será interpretada por el shell como uno o más comandos, como si la cadena fuera el argumento de la función system() definida en el volumen de Interfaces del Sistema de POSIX.1‐2017. Si el operando cadena_comando es una cadena vacía, sh saldrá con un estado de salida cero.

ENTRADA ESTÁNDAR

La entrada estándar se utilizará solo si se cumple una de las siguientes condiciones:

*
Se especifica la opción -s.
*
La opción -c no está especificada y no hay operandos.
*
El script ejecuta uno o más comandos que requieren entrada de la entrada estándar (como un comando read que no redirige su entrada).

Ver la sección ARCHIVOS DE ENTRADA.

Cuando el shell esté utilizando la entrada estándar y invoque un comando que también utilice la entrada estándar, el shell garantizará que el puntero del archivo de entrada estándar apunte directamente después del comando que ha leído cuando el comando comience su ejecución. No leerá anticipadamente de tal manera que los caracteres destinados a ser leídos por el comando invocado sean consumidos por el shell (ya sean interpretados por el shell o no) o que los caracteres que no son leídos por el comando invocado no sean vistos por el shell. Cuando el comando que espera leer la entrada estándar se inicia de forma asíncrona por un shell interactivo, es indefinido si los caracteres son leídos por el comando o interpretados por el shell.

Si la entrada estándar a sh es una FIFO o un dispositivo terminal y se establece en lecturas no bloqueantes, entonces sh habilitará lecturas bloqueantes en la entrada estándar. Esto permanecerá en vigor cuando el comando complete.

ARCHIVOS DE ENTRADA

El archivo de entrada será un archivo de texto, excepto que las longitudes de línea no tendrán límites. Si el archivo de entrada consiste únicamente en cero o más líneas en blanco y comentarios, sh saldrá con un estado de salida cero.

NAME

sh - shell, the command interpreter

SYNOPSIS

sh [-«aBcDeEfhimnOoP…] [argument…]

sh -c string [-«aBcDeEfhimnOoP…] [argument…]

sh -t [-«aBcDeEfhimnOoP…] [argument…]

sh -s [-«aBcDeEfhimnOoP…] [argument…]

DESCRIPTION

The sh utility shall invoke the shell, a command language interpreter that reads commands from the standard input or a specified file. The shell is used to invoke and manage other utilities. The shell shall conform to the Shell Command Language specification in the Base Definitions volume of POSIX.1‐2017, Chapter 2. (See the EXTENDED DESCRIPTION section.)

The sh utility shall support the options described below.

-« options
One or more options from the list below. Options that take an argument can be specified as -«option argument or, if not ambiguous, as -«argument. Options can be combined (e.g., -«xyz is equivalent to -«x -«y -«z).
-a
Do not write assignments to the environment for subsequent commands. This is the default for the non-interactive shell.
-b
Notify the user when a background job changes state. The nature of the notification is implementation-defined. This option is effective only when the shell is interactive.
-c
Read commands from the string following the -c option. A trailing argument (if any) is assigned to name (see Section 2.6.1, Shell Grammar). Shell script execution occurs as described in the EXTENDED DESCRIPTION section. This option shall not be used in conjunction with the -s option.
-d
A non-empty string value for the CDPATH environment variable is used to search for the directory containing the target of a directory name in a cd command. If CDPATH is unset or null, the current directory is used. Otherwise, the directories named by the pathnames in CDPATH are searched in order until a directory containing the target is found. The current directory is searched only if no matching directory is found in CDPATH or if the pathnames in CDPATH end with a slash. The shell shall then change to that directory. If the cd command is successful, the new current directory name is stored in the PWD environment variable. The behavior of the cd command when the target directory is `.' or `..' is implementation-defined.
This option overrides the default behavior of the cd utility when CDPATH is unset or null.
-e
Exit immediately if a simple command exits with a non-zero status. Exit status 126 shall be reported if a command is found but cannot be executed. Exit status 127 shall be reported if a command is not found. An interactive shell shall also exit if any of the commands executed to set up the shell environment exit with a non-zero status. This option is the default for the non-interactive shell.
This option is the default for the non-interactive shell.
-f
Disable filename expansion (globbing).
-h
Scan the command line for alias definitions and for functions at the beginning of the command line, rather than waiting to scan until the first command is read.
-i
Prompt for commands if the standard input is a terminal, even if not interactive.
-m
Monitor all child processes. This means that when a process run by the shell exits, or a signal is received by a process run by the shell, the shell shall take appropriate action. This option is only relevant when the shell is interactive.
-n
Read commands but do not execute them. This is useful for checking the syntax of shell scripts.
-o name
The behavior of this option is described in the EXTENDED DESCRIPTION section under the heading Shell Execution Environment.
-P
Disable the translation of the ~, ~name, and ~+, ~- characters, as described in Section 2.6.1, Tilde Expansion. This is the default for the non-interactive shell.
-s
Read commands from the standard input. This option is the default for the interactive shell. This option shall not be used in conjunction with the -c option.
-t
Read and execute commands from the standard input until end-of-file is encountered. Exit status 126 shall be reported if a command is found but cannot be executed. Exit status 127 shall be reported if a command is not found. This option shall not be used in conjunction with the -c option.

The arguments following the options shall be treated as positional parameters (see Section 2.5.2, Special Parameters). An argument of the form name=value shall be treated as an environment variable assignment.

If the -c option is used, the first argument after the string is assigned to the shell variable name. Subsequent arguments are assigned to the positional parameters $1, $2, and so on. If there are no arguments following the string, positional parameter $1 is unset.

If neither -c nor -s is specified, the first non-option argument shall be taken as the name of a file of commands to be executed. The options following this file argument shall be passed to the shell as positional parameters, starting with $1. The shell shall then attempt to execute commands from this file.

The shell shall implement the following environment variables:

CDPATH
Used to determine the search path for directories when processing a cd command. The format of this variable is described under the -d option.
ENV
When the shell is invoked, the value of this variable shall be used as the name of an initialization file. If the expanded value is a non-empty string, it shall be treated as the name of a file to be read in before the first command is executed. The file shall be read in its entirety if it is found and is readable. It is not required that the expanded value be executable. If the expanded value of ENV is not an absolute pathname, the results are unspecified. ENV shall be ignored if the real and effective user IDs or real and effective group IDs of the process are different.
FCEDIT
This variable, when expanded by the shell, shall determine the default value for the -e editor option's editor option-argument. If FCEDIT is null or unset, ed shall be used as the editor.
HISTFILE
Determine a pathname naming a command history file. If the HISTFILE variable is not set, the shell may attempt to access or create a file .sh_history in the directory referred to by the HOME environment variable. If the shell cannot obtain both read and write access to, or create, the history file, it shall use an unspecified mechanism that allows the history to operate properly. (References to history ``file'' in this section shall be understood to mean this unspecified mechanism in such cases.) An implementation may choose to access this variable only when initializing the history file; this initialization shall occur when fc or sh first attempt to retrieve entries from, or add entries to, the file, as the result of commands issued by the user, the file named by the ENV variable, or implementation-defined system start-up files. Implementations may choose to disable the history list mechanism for users with appropriate privileges who do not set HISTFILE; the specific circumstances under which this occurs are implementation-defined. If more than one instance of the shell is using the same history file, it is unspecified how updates to the history file from those shells interact. As entries are deleted from the history file, they shall be deleted oldest first. It is unspecified when history file entries are physically removed from the history file.
HISTSIZE
Determine a decimal number representing the limit to the number of previous commands that are accessible. If this variable is unset, an unspecified default greater than or equal to 128 shall be used. The maximum number of commands in the history list is unspecified, but shall be at least 128. An implementation may choose to access this variable only when initializing the history file, as described under HISTFILE. Therefore, it is unspecified whether changes made to HISTSIZE after the history file has been initialized are effective.
HOME
Determine the pathname of the user's home directory. The contents of HOME are used in tilde expansion as described in Section 2.6.1, Tilde Expansion.
LANG
Provide a default value for the internationalization variables that are unset or null. (See the Base Definitions volume of POSIX.1‐2017, Section 8.2, Internationalization Variables for the precedence of internationalization variables used to determine the values of locale categories.)
LC_ALL
If set to a non-empty string value, override the values of all the other internationalization variables.
LC_COLLATE

Determine the behavior of range expressions, equivalence classes, and multi-character collating elements within pattern matching.
LC_CTYPE
Determine the locale for the interpretation of sequences of bytes of text data as characters (for example, single-byte as opposed to multi-byte characters in arguments and input files), which characters are defined as letters (character class alpha), and the behavior of character classes within pattern matching.
LC_MESSAGES

Determine the locale that should be used to affect the format and contents of diagnostic messages written to standard error.
MAIL
Determine a pathname of the user's mailbox file for purposes of incoming mail notification. If this variable is set, the shell shall inform the user if the file named by the variable is created or if its modification time has changed. Informing the user shall be accomplished by writing a string of unspecified format to standard error prior to the writing of the next primary prompt string. Such check shall be performed only after the completion of the interval defined by the MAILCHECK variable after the last such check. The user shall be informed only if MAIL is set and MAILPATH is not set.
MAILCHECK

Establish a decimal integer value that specifies how often (in seconds) the shell shall check for the arrival of mail in the files specified by the MAILPATH or MAIL variables. The default value shall be 600 seconds. If set to zero, the shell shall check before issuing each primary prompt.
MAILPATH
Provide a list of pathnames and optional messages separated by <colon> characters. If this variable is set, the shell shall inform the user if any of the files named by the variable are created or if any of their modification times change. (See the preceding entry for MAIL for descriptions of mail arrival and user informing.) Each pathname can be followed by '%' and a string that shall be subjected to parameter expansion and written to standard error when the modification time changes. If a '%' character in the pathname is preceded by a <backslash>, it shall be treated as a literal '%' in the pathname. The default message is unspecified.

The MAILPATH environment variable takes precedence over the MAIL variable.

NLSPATH
Determine the location of message catalogs for the processing of LC_MESSAGES.
PATH
Establish a string formatted as described in the Base Definitions volume of POSIX.1‐2017, Chapter 8, Environment Variables, used to effect command interpretation; see Section 2.9.1.1, Command Search and Execution.
PWD
This variable shall represent an absolute pathname of the current working directory. Assignments to this variable may be ignored.

ASYNCHRONOUS EVENTS

The sh utility shall take the standard action for all signals (see Section 1.4, Utility Description Defaults) with the following exceptions.

If the shell is interactive, SIGINT signals received during command line editing shall be handled as described in the EXTENDED DESCRIPTION, and SIGINT signals received at other times shall be caught but no action performed.

If the shell is interactive:

*
SIGQUIT and SIGTERM signals shall be ignored.
*
If the -m option is in effect, SIGTTIN, SIGTTOU, and SIGTSTP signals shall be ignored.
*
If the -m option is not in effect, it is unspecified whether SIGTTIN, SIGTTOU, and SIGTSTP signals are ignored, set to the default action, or caught. If they are caught, the shell shall, in the signal-catching function, set the signal to the default action and raise the signal (after taking any appropriate steps, such as restoring terminal settings).

The standard actions, and the actions described above for interactive shells, can be overridden by use of the trap special built-in utility (see trap and Section 2.11, Signals and Error Handling).

STDOUT

See the STDERR section.

STDERR

Except as otherwise stated (by the descriptions of any invoked utilities or in interactive mode), standard error shall be used only for diagnostic messages.

OUTPUT FILES

None.

EXTENDED DESCRIPTION

See Chapter 2, Shell Command Language. The functionality described in the rest of the EXTENDED DESCRIPTION section shall be provided on implementations that support the User Portability Utilities option (and the rest of this section is not further shaded for this option).

Command History List

When the sh utility is being used interactively, it shall maintain a list of commands previously entered from the terminal in the file named by the HISTFILE environment variable. The type, size, and internal format of this file are unspecified. Multiple sh processes can share access to the file for a user, if file access permissions allow this; see the description of the HISTFILE environment variable.

Command Line Editing

When sh is being used interactively from a terminal, the current command and the command history (see fc) can be edited using vi-mode command line editing. This mode uses commands, described below, similar to a subset of those described in the vi utility. Implementations may offer other command line editing modes corresponding to other editing utilities.

The command set -o vi shall enable vi-mode editing and place sh into vi insert mode (see Command Line Editing (vi-mode)). This command also shall disable any other editing mode that the implementation may provide. The command set +o vi disables vi-mode editing.

Certain block-mode terminals may be unable to support shell command line editing. If a terminal is unable to provide either edit mode, it need not be possible to set -o vi when

 usando el shell en esta terminal.

En las siguientes secciones, los caracteres erase, interrupt, kill y end-of-file son aquellos establecidos por la utilidad stty.

Edición de línea de comandos (modo vi)

En el modo de edición vi, habrá una línea distinguida, la línea de edición. Todas las operaciones de edición que modifican una línea afectan a la línea de edición. La línea de edición es siempre la línea más reciente en el búfer del historial de comandos.

Con el modo vi activado, sh puede alternar entre el modo de inserción y el modo de comando.

Cuando está en modo de inserción, un carácter ingresado se insertará en la línea de comandos, excepto según se indica en Modo de Inserción de Edición de Línea vi. Al ingresar sh y después de la terminación del comando anterior, sh estará en modo de inserción.

Presionar una tecla de escape cambiará sh al modo de comando (ver Modo de Comando de Edición de Línea vi). En el modo de comando, un carácter ingresado invocará una operación definida, se usará como parte de una operación de múltiples caracteres, o se tratará como un error. Un carácter que no se reconoce como parte de un comando de edición terminará cualquier comando de edición específico y alertará la terminal. Si sh recibe una señal SIGINT en modo de comando (ya sea generada al presionar el carácter de interrupt o por otros medios), terminará la edición de la línea de comandos en la línea actual, reemitirá el prompt en la siguiente línea de la terminal y restablecerá el historial de comandos (ver fc) para que el comando ejecutado más recientemente sea el comando anterior (es decir, el comando que se estaba editando cuando se interrumpió no se vuelve a ingresar en el historial).

En las siguientes secciones, la frase "mover el cursor al principio de la palabra" significará "mover el cursor al primer carácter de la palabra actual" y la frase "mover el cursor al final de la palabra" significará "mover el cursor al último carácter de la palabra actual". La frase "principio de la línea de comandos" indica el punto entre el final de la cadena de prompt emitida por el shell (o el principio de la línea de terminal, si no hay cadena de prompt) y el primer carácter del texto del comando.

Modo de Inserción de Edición de Línea vi

Mientras está en modo de inserción, cualquier carácter escrito se insertará en la línea de comandos actual, a menos que sea del siguiente conjunto.

<newline>
Ejecuta la línea de comandos actual. Si la línea de comandos actual no está vacía, esta línea se ingresará en el historial de comandos (ver fc).
erase
Elimina el carácter anterior a la posición actual del cursor y mueve la posición actual del cursor hacia atrás un carácter. En modo de inserción, los caracteres se eliminarán tanto de la pantalla como del búfer al retroceder.
interrupt
Si sh recibe una señal SIGINT en modo de inserción (ya sea generada al presionar el carácter de interrupt o por otros medios), terminará la edición de la línea de comandos con los mismos efectos descritos para interrumpir el modo de comando; ver Edición de línea de comandos (modo vi).
kill
Borra todos los caracteres de la línea de entrada.
<control>‐V
Inserta el siguiente carácter de entrada, incluso si el carácter es de otro modo un carácter especial de inserción.
<control>‐W
Elimina los caracteres desde el que precede al cursor hasta el límite de la palabra anterior. El límite de la palabra en este caso es el más cercano al cursor, ya sea el principio de la línea o un carácter que no está clasificado ni como espacio ni como puntuación en la configuración regional actual.
end-of-file
Se interpreta como el final de la entrada en sh. Esta interpretación ocurrirá solo al principio de una línea de entrada. Si end-of-file se ingresa en otro lugar que no sea al principio de la línea, los resultados no están especificados.
<ESC>
Coloca sh en modo de comando.

Modo de Comando de Edición de Línea vi

En el modo de comando para la función de edición de línea de comandos, los dígitos decimales que no comienzan con 0 y que preceden a una letra de comando se recordarán. Algunos comandos utilizan estos dígitos decimales como un número de conteo que afecta la operación.

El término comando de movimiento representa uno de los comandos:

<espacio>  0  b  F  l  W  ^  $  ;  E  f  T  w  |  ,  B  e  h  t

Si la línea actual no es la línea de edición, cualquier comando que modifique la línea actual hará que el contenido de la línea actual reemplace el contenido de la línea de edición, y la línea actual se convertirá en la línea de edición. Este reemplazo no se puede deshacer (ver los comandos u y U a continuación). La modificación solicitada se realizará entonces a la línea de edición. Cuando la línea actual es la línea de edición, la modificación se realizará directamente en la línea de edición.

Cualquier comando que vaya precedido de conteo tomará un conteo (el valor numérico de cualquier dígito decimal precedente). A menos que se indique lo contrario, este conteo hará que la operación especificada se repita tantas veces como especifique el conteo. También, a menos que se indique lo contrario, un conteo que esté fuera de rango se considera una condición de error y alertará la terminal, pero ni la posición del cursor ni la línea de comandos cambiarán.

Los términos palabra y palabra grande se usan como se definen en la descripción de vi. El término búfer de guardado corresponde al término búfer sin nombre en vi.

Los siguientes comandos se reconocerán en modo de comando:

<newline>
Ejecuta la línea de comandos actual. Si la línea de comandos actual no está vacía, esta línea se ingresará en el historial de comandos (ver fc).
<control>‐L
Redibuja la línea de comandos actual. Posiciona el cursor en la misma ubicación en la línea redibujada.
#
Inserta el carácter '#' al principio de la línea de comandos actual y trata la línea de edición resultante como un comentario. Esta línea se ingresará en el historial de comandos; ver fc.
=
Muestra las posibles expansiones de palabras del shell (ver Sección 2.6, Expansiones de Palabras) de la palabra grande en la posición actual de la línea de comandos.
Nota:
Esto no modifica el contenido de la línea actual y, por lo tanto, no hace que la línea actual se convierta en la línea de edición.

Estas expansiones se mostrarán en líneas de terminal subsiguientes. Si la palabra grande no contiene ninguno de los caracteres '?', '*' o '[', se asumirá implícitamente un asterisco ('*') al final. Si se encuentran directorios, estas expansiones tendrán un carácter '/' agregado. Después de la expansión, la línea se redibujará, el cursor se reposicionará en la posición actual del cursor y sh se pondrá en modo de comando.

\
Realiza la expansión de nombres de ruta (ver Sección 2.6.6, Expansión de Nombres de Ruta) en la palabra grande actual, hasta el conjunto más grande de caracteres que se pueden emparejar de forma única. Si la palabra grande no contiene ninguno de los caracteres '?', '*' o '[', se asumirá implícitamente un asterisco ('*') al final. Esta expansión máxima reemplazará la palabra grande original en la línea de comandos, y el cursor se colocará después de esta expansión. Si la palabra grande resultante coincide completa y únicamente con un directorio, se insertará un carácter '/' directamente después de la palabra grande. Si se coincide completamente con otro archivo, se insertará un único espacio (<space>) después de la palabra grande. Después de esta operación, sh se pondrá en modo de inserción.
*

USO DE APLICACIONES

La entrada estándar y el error estándar son los archivos que determinan si un shell es interactivo cuando no se especifica -i. Por ejemplo:

sh > archivo

y:

sh 2> archivo

crean shells interactivos y no interactivos, respectivamente. Aunque ambos aceptan entrada del terminal, los resultados de las condiciones de error son diferentes, como se describe en la Sección 2.8.1, Consecuencias de los Errores del Shell; en el segundo ejemplo, un error de redirección encontrado por una utilidad interna especial aborta el shell.

Una aplicación que cumpla debe proteger su primer operando, si comienza con un <signo más>, anteponiéndole el argumento "--" que denota el fin de las opciones.

Las aplicaciones deben tener en cuenta que la ruta estándar PATH al shell no puede asumirse como /bin/sh o /usr/bin/sh, y debe determinarse interrogando la ruta PATH devuelta por getconf PATH, asegurándose de que la ruta devuelta sea una ruta absoluta y no una incorporada del shell.

Por ejemplo, para determinar la ubicación de la utilidad estándar sh:

command -v sh

En algunas implementaciones esto podría devolver:

/usr/xpg4/bin/sh

Además, en sistemas que soportan scripts ejecutables (la construcción "#! "), se recomienda que las aplicaciones que usen scripts ejecutables los instalen usando getconf PATH para determinar la ruta del shell y actualizar el script "#! " apropiadamente a medida que se instala (por ejemplo, con sed). Por ejemplo:

#
# Script de instalación para instalar la ruta de shell POSIX correcta
#
# Obtener lista de rutas a comprobar
#
Sifs=$IFS
Sifs_set=${IFS+y}
IFS=:
set -- $(getconf PATH)
if [ "$Sifs_set" = y ]
then
    IFS=$Sifs
else
    unset IFS
fi
#
# Comprobar cada ruta en busca de 'sh'
#
for i
do
    if [ -x "${i}"/sh ]
    then
        Pshell=${i}/sh
    fi
done
#
# Esta es la lista de scripts a actualizar. Deberían ser de la
# forma '${nombre}.source' y se transformarán a '${nombre}'.
# Cada script debe comenzar:
#
# #!RUTA_SHELL_INSTALACION
#
scripts="a b c"
#
# Transformar cada script
#
for i in ${scripts}
do
    sed -e "s|RUTA_SHELL_INSTALACION|${Pshell}|" < ${i}.source > ${i}
done

RAZONAMIENTO

La utilidad sh y la utilidad incorporada especial set comparten un conjunto común de opciones.

El nombre IFS era originalmente una abreviatura de ``Separadores de Campos de Entrada''; sin embargo, este nombre es engañoso ya que los caracteres IFS se utilizan en realidad como terminadores de campos. Una justificación para ignorar el contenido de IFS al entrar en el script, además de consideraciones de seguridad, es ayudar a posibles compiladores de shell futuros. Permitir que IFS se importe del entorno evita muchas optimizaciones que de otro modo podrían realizarse mediante análisis de flujo de datos del propio script.

El texto en la sección STDIN sobre lecturas no bloqueantes se refiere a una instancia de sh que se ha invocado, probablemente por un programa en lenguaje C, con la entrada estándar abierta con la bandera O_NONBLOCK; consulte open() en el volumen de Interfaces del Sistema de POSIX.1‐2017. Si el shell no restableciera esta bandera, terminaría inmediatamente porque aún no habría datos de entrada disponibles y eso se consideraría lo mismo que el fin de archivo.

Las opciones asociadas con un shell restringido (nombre de comando rsh y la opción -r) se excluyeron porque los desarrolladores estándar consideraron que el nivel de seguridad implícito no se podía lograr y no querían generar falsas expectativas.

En los sistemas que admiten scripts set-user-ID, una puerta trasera histórica ha sido enlazar un script con el nombre -i. Cuando se llama mediante una secuencia como:

sh -

o por:

#! /usr/bin/sh -

los sistemas históricos han asumido que no siguen letras de opción. Por lo tanto, este volumen de POSIX.1‐2017 permite que el único <guion-menos> marque el final de las opciones, además del uso del argumento regular "--", porque se consideró que la práctica anterior era tan generalizada. KornShell adopta un enfoque alternativo, donde los IDs de usuario/grupo reales y efectivos deben coincidir para un shell interactivo; este comportamiento está permitido específicamente por este volumen de POSIX.1‐2017.

Nota:
Existen otros problemas con los scripts set-user-ID que los dos enfoques descritos aquí no resuelven.

El proceso de inicialización del archivo de historial puede depender de los archivos de inicio del sistema, ya que pueden contener comandos que prevalecen efectivamente la configuración del usuario de HISTFILE y HISTSIZE. Por ejemplo, los comandos de definición de funciones se registran en el archivo de historial, a menos que se establezca la opción set -o nolog. Si el administrador del sistema incluye definiciones de funciones en algún archivo de inicio del sistema llamado antes del archivo ENV, el archivo de historial se inicializa antes de que el usuario tenga la oportunidad de influir en sus características. En algunos shells históricos, el archivo de historial se inicializa justo después de procesar el archivo ENV. Por lo tanto, la efectividad de los cambios realizados en HISTFILE después de la inicialización del archivo de historial depende de la implementación.

Los mensajes predeterminados para los diversos mensajes relacionados con MAIL no están especificados porque varían entre implementaciones. Los mensajes típicos son:

"tienes correo\n"

o:

"tienes correo nuevo\n"

Es importante que las descripciones de la edición de línea de comandos se refieran al mismo shell que en POSIX.1‐2008 para que los usuarios interactivos también puedan ser programadores de aplicaciones sin tener que lidiar con diferencias programáticas en sus dos entornos. También es esencial que se especifique el nombre de la utilidad sh porque este nombre de utilidad explícito está demasiado firmemente arraigado en la práctica histórica de los programas de aplicación como para que cambie.

Se consideró la posibilidad de exigir un mensaje de diagnóstico al intentar establecer el modo vi en terminales que no admiten la edición de línea de comandos. Sin embargo, no es una práctica histórica que el shell sea consciente de todos los tipos de terminal y, por lo tanto, sea capaz de detectar terminales inapropiados en todos los casos. Se alienta a las implementaciones a proporcionar diagnósticos en este caso siempre que sea posible, en lugar de dejar al usuario en un estado donde los comandos de edición funcionen incorrectamente.

En las propuestas iniciales, se incluyó el modo emacs de edición de línea de comandos derivado de KornShell, aunque el editor emacs en sí mismo no estaba incluido. La comunidad de proponentes de emacs fue inflexible en que el editor completo emacs no se estandarizara porque estaban preocupados de que un intento de estandarizar este entorno tan potente animara a los proveedores a lanzar versiones que cumplieran estrictamente con la norma, pero carecieran de la extensibilidad requerida por la comunidad. El autor del programa original emacs también expresó su deseo de omitir el programa. Además, había un número de sistemas históricos que no incluían emacs, o lo incluían sin soportarlo, pero había muy pocos que no incluían y soportaban vi. El modo de edición de línea de comandos emacs del shell finalmente se omitió porque se hizo evidente que la versión de KornShell y el editor que se distribuía con el sistema GNU habían divergido en algunos aspectos. El autor de emacs solicitó que el modo emacs de POSIX se eliminara o tuviera un número significativo de condiciones no especificadas. Aunque el autor de KornShell accedió a considerar cambios para alinear el shell, los desarrolladores del estándar decidieron posponer la especificación en ese momento. En ese momento, se asumió que convergerían en una definición aceptable para un borrador posterior, pero eso no ha ocurrido y parece no haber ningún ímpetu para hacerlo. En cualquier caso, las implementaciones son libres de ofrecer modos adicionales de edición de línea de comandos basados en los modelos exactos de editores con los que sus usuarios se sienten más cómodos.

Las propuestas iniciales tenían la siguiente entrada en el modo de inserción de edición de línea vi:

\
Si va seguido del carácter erase o kill, ese carácter se insertará en la línea de entrada. De lo contrario, el propio <barra invertida> se insertará en la línea de entrada.

Sin embargo, esto no es en realidad una característica del modo de inserción de edición de línea de comandos de sh, sino de algunos controladores de línea de terminal históricos. Algunas implementaciones conformes continúan haciendo esto cuando la bandera stty iexten está establecida.

En los shells interactivos, SIGTERM se ignora para que kill 0 no mate al shell, y SIGINT se captura para que wait sea interrumpible. Si el shell no ignora las señales SIGTTIN, SIGTTOU y SIGTSTP cuando es interactivo y la opción -m no está en efecto, estas señales suspenden el shell si no es un líder de sesión. Si es un líder de sesión, las señales se descartan si detendrían el proceso, según lo requiere el volumen de Interfaces del Sistema de POSIX.1‐2017, Sección 2.4.3, Acciones de Señales para grupos de procesos huérfanos.
