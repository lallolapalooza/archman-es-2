SHM_OPEN(3P) Manual del Programador POSIX SHM_OPEN(3P)

PROLOG

Esta página del manual es parte del Manual del Programador POSIX. La implementación de Linux de esta interfaz puede diferir (consulte la página del manual de Linux correspondiente para obtener detalles sobre el comportamiento de Linux), o la interfaz puede no estar implementada en Linux.

NOMBRE

shm_open — abrir un objeto de memoria compartida (REALTIME)

SINOPSIS

#include <sys/mman.h>
int shm_open(const char *name, int oflag, mode_t mode);

DESCRIPCIÓN

La función shm_open() establecerá una conexión entre un objeto de memoria compartida y un descriptor de archivo. Creará una descripción de archivo abierto que se refiere al objeto de memoria compartida y un descriptor de archivo que se refiere a esa descripción de archivo abierto. El descriptor de archivo se asignará según se describe en la Sección 2.14, Asignación de Descriptores de Archivo, y puede ser utilizado por otras funciones para referirse a ese objeto de memoria compartida. El argumento name apunta a una cadena que nombra un objeto de memoria compartida. No se especifica si el nombre aparece en el sistema de archivos y es visible para otras funciones que toman rutas como argumentos. El argumento name se ajusta a las reglas de construcción de una ruta, excepto que la interpretación de los caracteres <barra> distintos de la barra inicial <barra> en name es definida por la implementación, y que los límites de longitud para el argumento name son definidos por la implementación y no necesitan ser los mismos que los límites de ruta {PATH_MAX} y {NAME_MAX}. Si name comienza con el carácter de <barra>, entonces los procesos que llaman a shm_open() con el mismo valor de name se refieren al mismo objeto de memoria compartida, siempre que ese nombre no haya sido eliminado. Si name no comienza con el carácter de <barra>, el efecto es definido por la implementación.

Si tiene éxito, shm_open() devolverá un descriptor de archivo para el objeto de memoria compartida. La descripción de archivo abierto es nueva y, por lo tanto, el descriptor de archivo no la comparte con ningún otro proceso. No se especifica si se establece la posición del archivo. El indicador de descriptor de archivo FD_CLOEXEC asociado con el nuevo descriptor de archivo está establecido.

Los indicadores de estado del archivo y los modos de acceso al archivo de la descripción del archivo abierto se ajustan al valor de oflag. El argumento oflag es la máscara de bits OR inclusiva de los siguientes indicadores definidos en el encabezado <fcntl.h>. Las aplicaciones especifican exactamente uno de los dos primeros valores (modos de acceso) a continuación en el valor de oflag:

O_RDONLY
Abrir solo para acceso de lectura.
O_RDWR
Abrir para acceso de lectura o escritura.

Cualquier combinación de los indicadores restantes puede ser especificada en el valor de oflag:

O_CREAT
Si el objeto de memoria compartida existe, este indicador no tiene efecto, excepto como se indica en O_EXCL a continuación. De lo contrario, se crea el objeto de memoria compartida. El ID de usuario del objeto de memoria compartida se establecerá en el ID de usuario efectivo del proceso. El ID de grupo del objeto de memoria compartida se establecerá en el ID de grupo efectivo del proceso; sin embargo, si el argumento name es visible en el sistema de archivos, el ID de grupo puede establecerse en el ID de grupo del directorio contenedor. Los bits de permiso del objeto de memoria compartida se establecerán en el valor del argumento mode, excepto aquellos establecidos en la máscara de creación de modo de archivo del proceso. Cuando se establecen bits en mode distintos de los bits de permiso de archivo, el efecto no se especifica. El argumento mode no afecta si el objeto de memoria compartida se abre para lectura, escritura o ambas. El objeto de memoria compartida tiene un tamaño de cero.
O_EXCL
Si O_EXCL y O_CREAT están establecidos, shm_open() falla si el objeto de memoria compartida existe. La verificación de la existencia del objeto de memoria compartida y la creación del objeto si no existe es atómica con respecto a otros procesos que ejecutan shm_open() nombrando el mismo objeto de memoria compartida con O_EXCL y O_CREAT establecidos. Si O_EXCL está establecido y O_CREAT no está establecido, el resultado no está definido.
O_TRUNC
Si el objeto de memoria compartida existe, y se abre correctamente con O_RDWR, el objeto se truncará a longitud cero y el modo y el propietario no serán modificados por esta llamada a función. El resultado de usar O_TRUNC con O_RDONLY no está definido.

Cuando se crea un objeto de memoria compartida, el estado del objeto de memoria compartida, incluidos todos los datos asociados con el objeto de memoria compartida, persiste hasta que el objeto de memoria compartida sea eliminado (unlinked) y todas las demás referencias hayan desaparecido. No se especifica si el nombre y el estado del objeto de memoria compartida siguen siendo válidos después de un reinicio del sistema.

VALOR DEVUELTO

Al completarse con éxito, la función shm_open() devolverá un entero no negativo que representa el descriptor de archivo. De lo contrario, devolverá -1 y establecerá errno para indicar el error.

ERRORES

La función shm_open() fallará si:

EACCES
El objeto de memoria compartida existe y se deniegan los permisos especificados por oflag, o el objeto de memoria compartida no existe y se deniega el permiso para crear el objeto de memoria compartida, o se especifica O_TRUNC y se deniega el permiso de escritura.
EEXIST
O_CREAT y O_EXCL están establecidos y el objeto de memoria compartida nombrado ya existe.
EINTR
La operación shm_open() fue interrumpida por una señal.
EINVAL
La operación shm_open() no es compatible con el nombre dado.
EMFILE
Todos los descriptores de archivo disponibles para el proceso están actualmente abiertos.
ENFILE
Hay demasiados objetos de memoria compartida actualmente abiertos en el sistema.
ENOENT
O_CREAT no está establecido y el objeto de memoria compartida nombrado no existe.
ENOSPC
No hay suficiente espacio para la creación del nuevo objeto de memoria compartida.

La función shm_open() puede fallar si:

ENAMETOOLONG

La longitud del argumento name excede {_POSIX_PATH_MAX} en sistemas que no soportan la opción XSI o excede {_XOPEN_PATH_MAX} en sistemas XSI, o tiene un componente de ruta más largo que {_POSIX_NAME_MAX} en sistemas que no soportan la opción XSI o más largo que {_XOPEN_NAME_MAX} en sistemas XSI.

EJEMPLOS

Creación y Mapeo de un Objeto de Memoria Compartida

El siguiente segmento de código demuestra el uso de shm_open() para crear un objeto de memoria compartida que luego se dimensiona usando ftruncate() antes de ser mapeado en el espacio de direcciones del proceso usando mmap():

#include <unistd.h>
#include <sys/mman.h>
...
#define MAX_LEN 10000
struct region {        /* Define la "estructura" de la memoria compartida */
    int len;
    char buf[MAX_LEN];
};
struct region *rptr;
int fd;
/* Crear objeto de memoria compartida y establecer su tamaño */
fd = shm_open("/myregion", O_CREAT | O_RDWR, S_IRUSR | S_IWUSR);
if (fd == -1)
    /* Manejar error */;
if (ftruncate(fd, sizeof(struct region)) == -1)
    /* Manejar error */;
/* Mapear objeto de memoria compartida */
rptr = mmap(NULL, sizeof(struct region),
       PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
if (rptr == MAP_FAILED)
    /* Manejar error */;
/* Ahora podemos referirnos a la región mapeada usando los campos de rptr;
   por ejemplo, rptr->len */
...

USO DE LA APLICACIÓN

Ninguno.

FUNDAMENTO

Cuando se soporta la opción de Archivos Mapeados en Memoria, se utiliza la llamada normal open() para obtener un descriptor de un archivo que se va a mapear según la práctica existente con mmap(). Cuando se soporta la opción de Objetos de Memoria Compartida, la función shm_open() obtendrá un descriptor del objeto de memoria compartida que se va a mapear.

Existe un amplio precedente para que un descriptor de archivo represente varios tipos de objetos. En el estándar POSIX.1-1990, un descriptor de archivo puede representar un archivo, una tubería, una FIFO, una tty o un directorio. Muchas implementaciones simplemente tienen un vector de operaciones, indexado por el tipo de descriptor de archivo, que realiza operaciones muy diferentes. Tenga en cuenta que en algunos casos el descriptor de archivo pasado a operaciones genéricas en descriptores de archivo es devuelto por open() o creat(), y en algunos casos es devuelto por funciones alternativas, como pipe(). Esta última técnica es utilizada por shm_open().

Tenga en cuenta que tales objetos de memoria compartida pueden ser implementados como archivos mapeados. En ambos casos, el tamaño se puede establecer después de abrir utilizando ftruncate(). La función shm_open() en sí misma no crea un objeto compartido de un tamaño especificado porque esto duplicaría una función existente que establece el tamaño de un objeto referenciado por un descriptor de archivo.

En implementaciones donde los objetos de memoria se implementan utilizando el sistema de archivos existente, la función shm_open() puede implementarse utilizando una macro que invoca open(), y la función shm_unlink() puede implementarse utilizando una macro que invoca unlink().

Para implementaciones sin un sistema de archivos permanente, se permite que el nombre de los objetos de memoria no sobreviva a un reinicio del sistema. Tenga en cuenta que esto permite que los sistemas con un sistema de archivos permanente implementen objetos de memoria como estructuras de datos internas a la implementación.

En implementaciones que eligen implementar objetos de memoria directamente usando memoria, se puede usar un shm_open() seguido de un ftruncate() y close() para preasignar un área de memoria compartida y establecer el tamaño de esa preasignación. Esto puede ser necesario para sistemas sin soporte de hardware de memoria virtual para asegurar que la memoria sea contigua.

El conjunto de indicadores de apertura válidos para shm_open() se restringió a O_RDONLY, O_RDWR, O_CREAT y O_TRUNC porque podían implementarse fácilmente en la mayoría de los sistemas de mapeo de memoria. Este volumen de POSIX.1-2017 guarda silencio sobre los resultados si la implementación no puede suministrar el modo solicitado debido a razones definidas por la implementación, incluidas las de hardware.

Las condiciones de error [EACCES] y [ENOTSUP] se proporcionan para informar a la aplicación que la implementación no puede completar una solicitud.

[EACCES] indica por razones definidas por la implementación, probablemente relacionadas con el hardware, que la implementación no puede cumplir con un modo solicitado porque entra en conflicto con otro modo solicitado. Un ejemplo podría ser que una aplicación desee abrir un objeto de memoria dos veces, mapeando diferentes áreas con diferentes modos de acceso. Si la implementación no puede mapear una única área en el espacio de un proceso en dos lugares, lo que sería necesario si se requirieran diferentes modos de acceso para las dos áreas, entonces la implementación puede informar a la aplicación en el momento de la segunda apertura.

[ENOTSUP] indica por razones definidas por la implementación, probablemente relacionadas con el hardware, que la implementación no puede cumplir con un modo solicitado en absoluto. Un ejemplo sería que el hardware de la implementación no puede soportar áreas de memoria compartida de solo escritura.

En todas las implementaciones, puede ser deseable restringir la ubicación de los objetos de memoria a sistemas de archivos específicos por razones de rendimiento (como un disco RAM) o definidas por la implementación (memoria compartida soportada directamente solo en ciertos sistemas de archivos). La función shm_open() puede ser utilizada para forzar estas restricciones. Hay una serie de métodos disponibles para la aplicación para determinar un nombre de archivo apropiado o la ubicación de un directorio adecuado. Una forma es desde el entorno a través de getenv(). Otra sería desde un archivo de configuración.

Este volumen de POSIX.1-2017 especifica que los objetos de memoria tienen contenidos iniciales de cero cuando se crean. Esto es consistente con el comportamiento actual tanto para archivos como para memoria recién asignada. Para aquellas implementaciones que utilizan memoria física, sería posible que tales implementaciones simplemente usaran memoria disponible y la dieran al proceso sin inicializar. Esto, sin embargo, no es consistente con el comportamiento estándar para el área de datos no inicializada, la pila y, por supuesto, los archivos. Finalmente, es muy deseable establecer la memoria asignada a cero por razones de seguridad. Por lo tanto, se requiere inicializar los objetos de memoria a cero.

DIRECCIONES FUTURAS

Una versión futura podría requerir que las funciones shm_open() y shm_unlink() tengan semánticas similares a las operaciones normales del sistema de archivos.
