SM-NOTIFY(8) Manual del Administrador del Sistema SM-NOTIFY(8)

NOMBRE

sm-notify - enviar notificaciones de reinicio a pares NFS

SINOPSIS

/usr/sbin/sm-notify [-dfn] [-m minutos] [-v nombre] [-p puerto-notificación] [-P ruta]

DESCRIPCIÓN

Los bloqueos de archivos no forman parte del estado persistente del sistema de archivos. Por lo tanto, el estado de bloqueo se pierde cuando un host se reinicia.

Los sistemas de archivos de red también deben detectar cuándo se pierde el estado de bloqueo porque un host remoto se ha reiniciado. Después de que un cliente NFS se reinicia, un servidor NFS debe liberar todos los bloqueos de archivos mantenidos por aplicaciones que se ejecutaban en ese cliente. Después de que un servidor se reinicia, un cliente debe recordar al servidor los bloqueos de archivos mantenidos por aplicaciones que se ejecutan en ese cliente.

Para NFS versión 2 y versión 3, el protocolo Network Status Monitor (o NSM, en resumen) se utiliza para notificar a los pares NFS sobre reinicios. En Linux, dos componentes separados en el espacio de usuario constituyen el servicio NSM:

sm-notify
Un programa auxiliar que notifica a los pares NFS después de que el sistema local se reinicia.
rpc.statd
Un demonio que escucha notificaciones de reinicio de otros hosts y gestiona la lista de hosts a los que se notificará cuando el sistema local se reintegre.

El gestor de bloqueos NFS local alerta a su rpc.statd local de cada par remoto que debe ser monitorizado. Cuando el sistema local se reinicia, el comando sm-notify notifica al servicio NSM en los pares monitorizados sobre el reinicio. Cuando un remoto se reinicia, ese par notifica al rpc.statd local, que a su vez pasa la notificación de reinicio al gestor de bloqueos NFS local.

OPERACIÓN NSM EN DETALLE

La primera interacción de bloqueo de archivos entre un cliente y un servidor NFS hace que los gestores de bloqueos NFS en ambos pares se pongan en contacto con su servicio NSM local para almacenar información sobre el par opuesto. En Linux, el gestor de bloqueos local contacta con rpc.statd.

rpc.statd registra información sobre cada par NFS monitorizado en almacenamiento persistente. Esta información describe cómo contactar a un par remoto en caso de que el sistema local se reinicie, cómo reconocer qué par monitorizado informa de un reinicio y cómo notificar al gestor de bloqueos local cuando un par monitorizado indica que se ha reiniciado.

Un cliente NFS envía un nombre de host, conocido como nombre_llamada del cliente, en cada solicitud de bloqueo de archivos. Un servidor NFS puede utilizar este nombre de host para enviar llamadas GRANT asíncronas a un cliente, o para notificar al cliente que se ha reiniciado.

El servidor NFS de Linux puede proporcionar el nombre_llamada del cliente o la dirección de red del cliente a rpc.statd. A efectos del protocolo NSM, este nombre o dirección se conoce como el nombre_monitorizado del par monitorizado. Además, el gestor de bloqueos local indica a rpc.statd cuál cree que es su propio nombre de host. A efectos del protocolo NSM, este nombre de host se conoce como mi_nombre.

No existe una interacción equivalente entre un servidor NFS y un cliente para informar al cliente del nombre_llamada del servidor. Por lo tanto, los clientes NFS no saben realmente qué nombre_monitorizado puede usar un servidor NFS en una solicitud SM_NOTIFY. El cliente NFS de Linux registra el nombre de host del servidor utilizado en el comando mount para identificar los servidores NFS que se reinician.

Notificación de reinicio

Cuando el sistema local se reinicia, el comando sm-notify lee la lista de pares monitorizados del almacenamiento persistente y envía una solicitud SM_NOTIFY al servicio NSM de cada par remoto listado. Utiliza la cadena nombre_monitorizado como destino. Para identificar qué host se ha reiniciado, el comando sm-notify normalmente envía la cadena mi_nombre registrada cuando se monitorizó ese remoto como argumento nombre_monitorizado. El rpc.statd remoto compara las solicitudes SM_NOTIFY entrantes utilizando esta cadena, o la dirección de red del llamador, con uno o más pares de su propia lista de monitorización.

Si rpc.statd no encuentra un par en su lista de monitorización que coincida con una solicitud SM_NOTIFY entrante, la notificación no se reenvía al gestor de bloqueos local. Además, cada par tiene su propio número de estado NSM, un entero de 32 bits que se incrementa después de cada reinicio por el comando sm-notify. rpc.statd utiliza este número para distinguir entre reinicios reales y notificaciones repetidas.

Parte de la recuperación de bloqueos de NFS es redescubrir qué pares deben ser monitorizados nuevamente. El comando sm-notify borra la lista de monitorización en el almacenamiento persistente después de cada reinicio.

OPCIONES

-d
Mantiene sm-notify adjunto a su terminal de control y ejecutándose en primer plano para que el progreso de la notificación pueda ser monitoreado directamente.
-f
Envía notificaciones incluso si sm-notify ya se ha ejecutado desde el último reinicio del sistema.
-m tiempo-reintento
Especifica el tiempo, en minutos, durante el cual se continuarán intentando las notificaciones a hosts que no responden. Si no se especifica esta opción, sm-notify intenta enviar notificaciones durante 15 minutos. Especificar un valor de 0 hace que sm-notify continúe enviando notificaciones a pares que no responden hasta que se mate manualmente.
Se reintentan las notificaciones si falla el envío, el remoto no responde, el servicio NSM del remoto no está registrado, o si hay un fallo de DNS que impide que el nombre_monitorizado del remoto se resuelva a una dirección.
Los hosts no se eliminan de la lista de notificación hasta que se haya recibido una respuesta válida. Sin embargo, el procedimiento SM_NOTIFY tiene un resultado vacío. No hay forma de que sm-notify sepa si el remoto reconoció al remitente y ha iniciado la recuperación de bloqueo apropiada.
-n
Evita que sm-notify actualice el número de estado NSM del sistema local.
-p puerto
Especifica el número de puerto de origen que sm-notify debe usar al enviar notificaciones de reinicio. Si no se especifica esta opción, se utiliza un puerto efímero elegido aleatoriamente.
Esta opción se puede usar para atravesar un firewall entre cliente y servidor.
-P, --ruta-directorio-estado ruta
Especifica la ruta del directorio padre donde residen la información de estado NSM. Si no se especifica esta opción, sm-notify utiliza /var/lib/nfs por defecto.
Después de iniciarse, sm-notify intenta establecer su UID y GID efectivos al propietario y grupo del subdirectorio sm de este directorio. Después de cambiar los ids efectivos, sm-notify solo necesita acceder a los archivos en sm y sm.bak dentro de la ruta-directorio-estado.
-v direccion-ip | nombre-host
Especifica la dirección de red desde la cual enviar notificaciones de reinicio, y el argumento nombre_monitorizado a usar al enviar solicitudes SM_NOTIFY. Si no se especifica esta opción, sm-notify utiliza una dirección comodín como dirección de enlace de transporte, y utiliza el mi_nombre registrado cuando se monitorizó el remoto como argumento nombre_monitorizado al enviar solicitudes SM_NOTIFY.
La forma direccion-ip puede expresarse como una dirección de presentación IPv4 o IPv6. Si se usa la forma direccion-ip, el comando sm-notify convierte esta dirección a un nombre de host para usarlo como argumento nombre_monitorizado al enviar solicitudes SM_NOTIFY.
Esta opción puede ser útil en configuraciones multi-homed donde el remoto requiere notificación desde una dirección de red específica.

ARCHIVO DE CONFIGURACIÓN

Muchas de las opciones que se pueden establecer en la línea de comandos también se pueden controlar a través de valores establecidos en la sección [sm-notify] o, en un caso, en la sección [statd] del archivo de configuración /etc/nfs.conf.

El archivo de configuración se puede usar para especificar parámetros como:

  • El tiempo de espera de reintento de notificación (opción -m).
  • El directorio de estado (opción -P).
  • La dirección IP o nombre de host desde el que enviar notificaciones (opción -v).

Por ejemplo, una sección [sm-notify] en /etc/nfs.conf podría parecerse a esto:

[sm-notify]
retry-time = 30
state-directory-path = /var/nfs/state
notify-source-address = 192.168.1.100

Esta configuración establecería el tiempo de espera de reintento a 30 minutos, el directorio de estado a /var/nfs/state y la dirección de origen de notificación a 192.168.1.100.

Consulte la página del manual de nfs.conf(5) para obtener más información sobre el archivo de configuración.

VER TAMBIÉN

nfs.conf(5), rpc.statd(8)

NAME

sm-notify — notify NLM clients and servers about server reboots

SYNOPSIS

sm-notify [-v] [-p port] [-m retries]

DESCRIPTION

The sm-notify command is part of the Network Lock Manager (NLM) protocol used by NFS. It is responsible for notifying NLM clients and servers about server reboots, which is crucial for recovering file locks after a server restart.

When an NFS server restarts, it needs to inform its clients that it has rebooted. This allows clients to re-establish locks on files that were previously locked. The sm-notify command facilitates this notification process.

NSM OPERATION IN DETAIL

The Network Status Monitor (NSM) protocol is used to track the status of NFS servers and clients. When an NFS server starts up, it registers itself with the NSM service. If the server reboots, it needs to notify its clients and potentially other servers that it has restarted. This notification is sent via the NSM protocol.

The sm-notify command is typically invoked by the rpc.statd(8) daemon. rpc.statd maintains a list of clients and servers to notify. When it detects that the local server has rebooted (e.g., by noticing a change in the server's state number), it calls sm-notify to send out the notifications.

The sm-notify command sends NSM_NOTIFY messages to all registered hosts. These messages inform the recipients about the server's reboot. Clients that receive these notifications can then attempt to recover their locks.

OPTIONS

·-m retries
Set the number of retry attempts for sending notifications. Default is 9.
·-p port
Specify the port number to use for outgoing notifications. Default is 2049.
·-v
Verbose mode. Print debugging information to standard output.

CONFIGURATION FILE

The sm-notify command can be configured using a configuration file, typically located at /etc/sm-notify.conf. The configuration file is divided into sections, such as [sm-notify] and [statd].

Values recognized in the [sm-notify] section include: retry-time, outgoing-port, and outgoing-addr. These have the same effect as the command line options m, p, and v respectively.

An additional value recognized in the [sm-notify] section is lift-grace. By default, sm-notify will lift lockd's grace period early if it has no hosts to notify. Some high availability configurations will run one sm-notify per floating IP address. In these configurations, lifting the grace period early may prevent clients from reclaiming locks. Setting lift-grace to n will prevent sm-notify from ending the grace period early. lift-grace has no corresponding command line option.

The value recognized in the [statd] section is state-directory-path.

SECURITY

The sm-notify command must be started as root to acquire privileges needed to access the state information database. It drops root privileges as soon as it starts up to reduce the risk of a privilege escalation attack.

During normal operation, the effective user ID it chooses is the owner of the state directory. This allows it to continue to access files in that directory after it has dropped its root privileges. To control which user ID rpc.statd chooses, simply use chown(1) to set the owner of the state directory.

ADDITIONAL NOTES

Lock recovery after a reboot is critical to maintaining data integrity and preventing unnecessary application hangs.

To help rpc.statd match SM_NOTIFY requests to NLM requests, a number of best practices should be observed, including:

The UTS nodename of your systems should match the DNS names that NFS peers use to contact them
The UTS nodenames of your systems should always be fully qualified domain names
The forward and reverse DNS mapping of the UTS nodenames should be consistent
The hostname the client uses to mount the server should match the server's mon_name in SM_NOTIFY requests it sends

Unmounting an NFS file system does not necessarily stop either the NFS client or server from monitoring each other. Both may continue monitoring each other for a time in case subsequent NFS traffic between the two results in fresh mounts and additional file locking.

On Linux, if the lockd kernel module is unloaded during normal operation, all remote NFS peers are unmonitored. This can happen on an NFS client, for example, if an automounter removes all NFS mount points due to inactivity.

IPv6 and TI-RPC support

TI-RPC is a pre-requisite for supporting NFS on IPv6. If TI-RPC support is built into the sm-notify command ,it will choose an appropriate IPv4 or IPv6 transport based on the network address returned by DNS for each remote peer. It should be fully compatible with remote systems that do not support TI-RPC or IPv6.

Currently, the sm-notify command supports sending notification only via datagram transport protocols.
