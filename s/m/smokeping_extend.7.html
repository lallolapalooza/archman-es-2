NOMBRE

smokeping_extend - Notas sobre la extensión de Smokeping

VISIÓN GENERAL

Este documento está destinado a guiar a los autores potenciales en la escritura de nuevas sondas de Smokeping. Describe principalmente la interfaz entre Smokeping y sus módulos de sonda. Si parece demasiado complicado de entender, consulta los módulos existentes para ver ejemplos.

Se aceptan comentarios y propuestas de cambios o adiciones. Por favor, envíalos a la lista de correo de smokeping-users. Los parches contra el código fuente POD de este documento son muy apreciados.

ELEGIR UNA CLASE BASE

Lo primero que debes decidir es qué clase base utilizar para tu sonda. Para la mayoría de los usos (si no todos), es una elección entre "Smokeping::probes::base" y "Smokeping::probes::basefork". La primera está destinada a sondas que pueden medir sus objetivos de una sola vez, mientras que la segunda es para sondearlos uno a uno, posiblemente en varios subprocesos concurrentes.

En este momento, las únicas sondas que utilizan "Smokeping::probes::base" son las derivadas de FPing. Todas las demás utilizan "Smokeping::probes::basefork", y lo más probable es que tú también deberías hacerlo. Por lo tanto, este documento se concentrará en este último caso.

ARCHIVO ESQUELÉTICO

El módulo Smokeping::probes::skel es una sonda no funcional que está destinada a ser una buena base para un nuevo módulo de sonda. Copia el archivo, "lib/probes/skel.pm", a un nuevo nombre y simplemente rellena los huecos :). Ten en cuenta que los nombres de los módulos de sonda reales deben empezar con una letra mayúscula.

DOCUMENTACIÓN DE LA SONDA

La documentación de la sonda se genera a partir del código fuente con los argumentos de smokeping "--man" o "--makepod". La documentación POD incrustada debe apuntar a esta documentación real, de modo que los usuarios curiosos del comando "perldoc" sepan lo que está pasando. Todas las sondas actuales hacen esto.

Debes proporcionar el método "pod_hash" que devuelve una referencia a un hash con claves correspondientes a los nombres de sección que deseas en la página man. Los nombres de sección admitidos son "name", "overview", "description", "authors", "notes", "bugs" y "see_also". Si no necesitas una sección particular, simplemente déjala fuera.

Las secciones especiales "synopsis" y "variables" se generan automáticamente a partir de la descripción de tus variables. Véase más abajo.

Ten en cuenta que si utilizas 'here documents' ('<<') que tienen marcado POD en su interior, deberías escapar el marcado para que no aparezca en la documentación POD incrustada. La mayoría de las sondas lo hacen así:

my $e = "=";
my $doc = <<DOC;
${e}head1 TÍTULO DE SECCIÓN
DOC

DESCRIPCIÓN DE LA SONDA

La sonda debe ofrecer el método "ProbeDesc" que devuelve una breve descripción de lo que hace. Esto se utilizará en los gráficos producidos por el frontend web.

VARIABLES

Todas las sondas de Smokeping deben definir sus variables implementando un método "probevars" para variables específicas de la sonda y un método "targetvars" para variables específicas del objetivo. Si aún no sabes la diferencia entre estas, consulta smokeping_examples.

(Las sondas que se derivan de "Smokeping::probes::base" no admiten variables específicas del objetivo, por lo que solo utilizan el método "probevars".)

Las clases base también ofrecen estos métodos para proporcionar las variables que son comunes a todas las sondas (por ejemplo, la variable "step" específica de la sonda y la variable "pings" específica del objetivo. Si no quieres añadir nada a las variables de la clase base (quizás porque todas tus variables son de naturaleza específica del objetivo, por lo que no necesitas nuevas variables específicas de la sonda en absoluto), puedes omitir el método correspondiente y se heredará de la clase base.

Cuando proporciones tu propio método "probevars" o "targetvars", debes combinar tus variables con las de la superclase. Hay un método de conveniencia llamado "_makevars" que hace esto, y el modismo común es

sub probevars {
       my $class = shift;
       return $class->_makevars($class->SUPER::probevars, {
               # tus variables van aquí
       }
}

Las variables se declaran en una sintaxis que proviene del módulo utilizado para analizar el archivo de configuración, "Config::Grammar". Cada variable debe ser un hash que utiliza las "claves de variables especiales" documentadas en Config::Grammar. Consulta "Smokeping::probes::skel" y las otras sondas para ver ejemplos.

A modo de referencia, aquí están las claves que debe tener el hash. Gran parte de esto se toma directamente del manual de "Config::Grammar".

Claves que debes proporcionar
_doc
Descripción de la variable.
_example
Un valor de ejemplo. Se utilizará en la sección SYNOPSIS del manual de la sonda.
Claves opcionales
_default
Un valor predeterminado que se asignará a la variable si no se especifica o hereda ninguno.
_re
Expresión regular sobre la cual se comprobará el valor.
_re_error
Cadena que contiene el error devuelto en caso de que la expresión regular no coincida (si no se especifica, se devolverá un mensaje genérico de 'error de sintaxis').
_sub
Un puntero a función. Se llama para cada valor, con el valor pasado como su primer argumento. Si la función devuelve un valor definido, se asume que la prueba no tuvo éxito y se genera un error con la cadena devuelta como contenido.

Los métodos "probevars" y "targetvars" deben devolver referencias a hashes que contengan los nombres de las variables como claves y los hashes descritos anteriormente como valores. Además, la clave de sección especial "Config::Grammar" "_mandatory" es compatible y debe contener una referencia a una lista de variables obligatorias. El método "_makevars" es consciente de esta clave especial y fusiona las listas obligatorias en sus argumentos. Ten en cuenta que no se admiten otras claves de sección especial de "Config::Grammar".

INICIALIZACIÓN

Si necesitas hacer algo en el momento de la inicialización de la sonda, como comprobar que el programa externo que vas a utilizar se comporta como esperas, deberías hacerlo en el método "new". Probablemente también deberías asegurarte de no ejecutar las pruebas innecesariamente en modo CGI. La forma habitual de hacerlo es comprobar $ENV{SERVER_SOFTWARE}. Consulta el módulo "Smokeping::probes::skel" para ver un ejemplo.

NAME

smokeping_extend - How to write new probes for Smokeping

OVERVIEW

Smokeping uses external programs called "probes" to measure network latency. These probes are implemented as Perl modules. This document explains how to write your own probes.

The probes are located in the "Smokeping::probes" namespace. To add a new probe, you need to create a Perl module under this namespace, e.g. "Smokeping::probes::MyProbe".

CHOOSING A BASE CLASS

Most probes can inherit from "Smokeping::probes::base". This base class provides a lot of functionality needed by most probes.

If your probe needs to run external programs (like ping, traceroute, or fping), you should inherit from "Smokeping::probes::basefork" instead. This base class handles process management and communication with the external program.

SKELETON FILE

Here's a skeleton for a simple probe:

package Smokeping::probes::MyProbe;

use strict;
use Smokeping::probes::base;

use base qw(Smokeping::probes::base);

our @p = (
    \%Smoke::probes::base::Probe,
    # Put your probe-specific variables here. Example:
    # %my_probe_vars = (
    #    'timeout'  => {
    #        _type    => 'int',
    #        _default => 5,
    #        _desc    => "Max time to wait for the ping to finish.",
    #    },
    # );
);

sub probevars {
    my $class = shift;
    return $class->SUPER::probevars, \%my_probe_vars;
}

sub setup_targets {
    my ($self, $targets) = @_;
    # 'targets' is a hash containing targets known to this probe.
    # You can add target-specific variables here.
    # Example:
    # if ($targets->{example.com}{name} eq 'example.com') {
    #    $targets->{example.com}{port} = 80;
    # }
    return;
}

sub run {
    my ($self, $target) = @_;

    # $target is a hash containing information about the target host.
    # It contains:
    #   name: the hostname or IP address
    #   probe: the probe name (e.g. 'MyProbe')
    #   vars: a hash of probe-specific and target-specific variables
    #   auth: authentication details (if any)

    # $self->{properties} contains probe-specific variables.
    # $target->{vars} contains target-specific variables.

    # Get the number of pings for this target:
    my $count = $self->pings($target);

    # Replace this with your actual probing logic.
    # For example, to simulate some latency:
    my @results;
    for (1..$count) {
        my $latency = rand(100); # Simulate latency in ms
        push @results, $latency;
        # If a ping fails, don't add anything to the array.
        # For example:
        # next if rand() < 0.1; # 10% chance of failure
    }

    # Return a sorted array of latency times.
    return sort { $a <=> $b } @results;
}

1;

PROBE DOCUMENTATION

The probe documentation is generated from POD sections in your probe module. Typically, you would add a "=head1" section for each of the following:

NAME
A short description of the probe.
SYNOPSIS
An example configuration snippet showing how to use the probe.
DESCRIPTION
A more detailed explanation of what the probe does and its features.
PARAMETERS
A list of probe-specific and target-specific variables supported by the probe, along with their types, defaults, and descriptions.
EXAMPLE CONFIGURATIONS
One or more complete example configurations demonstrating how to use the probe in different scenarios.

See the existing probe modules in "Smokeping::probes" for examples.

PROBE DESCRIPTION

The "=head1 NAME" section should contain a short, one-line description of the probe. This description is used in the main Smokeping display.

VARIABLES

Probe variables are defined in the "probevars" subroutine. Probe-specific variables are defined within the probe module itself, while target-specific variables can be defined in the main "smokeping_config" file or within the probe module in the "setup_targets" subroutine.

Variables are defined as hashes with the following keys:

_type
The data type of the variable (e.g., 'int', 'string', 'bool').
_default
The default value of the variable if not specified otherwise.
_desc
A description of the variable, used in the probe documentation.

Example:

our %my_vars = (
    'port' => {
        _type    => 'int',
        _default => 80,
        _desc    => "Port to connect to.",
    },
    'timeout' => {
        _type    => 'int',
        _default => 5,
        _desc    => "Max time to wait for the probe to complete.",
    },
);

INITIALIZATION

The "setup_targets" subroutine is called once when Smokeping starts. It receives a hash of targets known to this probe and can be used to add or modify target-specific variables.

PINGING

The "run" subroutine is called for each target. It receives a hash containing information about the target to be probed.

You can access the probe-specific variables here via the "$self->{properties}" hash and the target-specific ones via the "$target->{vars}" hash. You get the number of pings needed for the target via the "pings" method: "my $count = $self->pings($target)".

You should return a sorted array of the latency times measured. If a ping fails, don't put anything in the array.

That's it, you're done!

EXAMPLE CONFIGURATIONS

If you would like to provide a documented example configuration for your probe (in addition to the automatically generated SYNOPSIS section in the probe manual), you can do so by adding it to the Smokeping::Examples module. Look for the 'examples' subroutine and add your example there.

Future versions of Smokeping might provide a way to embed examples in the probe modules too. The author's motivation for implementing this would be greatly increased by even a single demand for it, so please speak up if you think you'd use it.

TIMEOUT HANDLING

If you deal with timeouts (for example because your program offers a parameter for specifying the timeout for the pings), you should know a few things.

First, there's timeout logic in "Smokeping::probes::basefork" that kills the probe when the timeout is reached. By default the timeout is (# of pings * 5 seconds) + 1 second. If you expect that your pings can take longer, you should modify the default value of the probe-specific variable "timeout". This would be done like this:

sub probevars {
       my $class = shift;
       my $h = $class->SUPER::probevars;
       $h->{timeout}{_default} = 10; # override the superclass default
       return $class->_makevars($h, {
               # your variables go here
       }

If you want to provide a target-specific "timeout" setting, you should delete the probe-specific variable and be sure to provide a default for your target-specific one. See eg. "Smokeping::probes::AnotherDNS" for an example of how this is done.

Providing a target-specific "timeout" will make the timeout in "Smokeping::probes::basefork" be (# of pings * the maximum timeout of all targets) + 1 second. The 1 second is added so that the own timeout logic of the probe has time to kick in even in the worst case (ie. all pings are lost) before "Smokeping::probes::basefork" starts killing the processes.
