NOMBRE

smtpd-filters — API de filtrado para el demonio smtpd

DESCRIPCIÓN

El demonio smtpd(8) proporciona una implementación del Protocolo Simple de Transferencia de Correo (SMTP), que permite que las máquinas ordinarias se conviertan en Intercambiadores de Correo (MX). Algunas características comúnmente usadas por los MX, como los informes de entrega o el filtrado de spam, están fuera del alcance de SMTP y son demasiado complejas para caber en smtpd(8).

Dado que un MX puede necesitar proporcionar estas características, smtpd(8) proporciona una API para extender su comportamiento a través de smtpd-filters.

En tiempo de ejecución, smtpd(8) puede informar de eventos a los smtpd-filters, consultando qué debe responder a estos eventos. Esto permite que la lógica de decisión dependa de programas de terceros.

DISEÑO

smtpd-filters son programas que se ejecutan como procesos independientes únicos, no comparten el espacio de memoria de smtpd(8). Son ejecutados por smtpd(8) al inicio y se espera que se ejecuten en un bucle infinito, leyendo eventos y solicitudes de filtrado desde stdin(4), escribiendo respuestas en stdout(4) y registrando en stderr(4). No se les permite terminar.

Dado que los smtpd-filters son programas independientes que se comunican con smtpd(8) a través de fd(4), pueden ejecutarse como usuarios diferentes a smtpd(8) y pueden estar escritos en cualquier idioma. Los smtpd-filters no deben usar E/S bloqueante, deben admitir respuestas asíncronas a smtpd(8).

INFORMAR Y FILTRAR

La API se basa en dos flujos, informe y filtro.

El flujo de informe es un flujo unidireccional que permite a smtpd(8) informar a los smtpd-filters en tiempo real sobre eventos. Los eventos de informe no esperan una respuesta de los smtpd-filters; solo pretenden proporcionar información. Un filtro debería poder replicar el estado de smtpd(8) para una sesión recopilando información proveniente de eventos de informe. El flujo de informe nunca toma decisiones.

El flujo de filtro es un flujo bidireccional que permite a smtpd(8) consultar a los smtpd-filters sobre lo que debe hacer con una sesión en una fase determinada. Las solicitudes de filtro esperan una respuesta de los smtpd-filters; smtpd(8) no permitirá que la sesión avance hasta entonces. El flujo de filtro siempre debe tomar una decisión.

A veces es posible confiar en las solicitudes de filtro para recopilar información, pero dado que se espera una respuesta de smtpd(8), esto es más costoso que usar eventos de informe. El patrón correcto para escribir filtros es usar eventos de informe para crear un estado local para una sesión, luego usar solicitudes de filtro para tomar decisiones basadas en este estado. El único caso en el que es correcto usar solicitudes de filtro en lugar de eventos de informe es cuando se requiere una decisión para la solicitud de filtro y no se necesita más información que la del propio evento.

PROTOCOLO

El protocolo consiste en líneas legibles por humanos intercambiadas entre los smtpd-filters y smtpd(8), a través de fd(4).

El protocolo comienza con un saludo. Primero, smtpd(8) proporciona a los smtpd-filters información general de configuración en forma de líneas clave-valor:

config|smtpd-version|7.8.0
config|protocol|0.7
config|smtp-session-timeout|300
config|subsystem|smtp-in
config|ready

Luego, los smtpd-filters registran el flujo, el subsistema y el evento que desean manejar:

register|report|smtp-in|link-connect
register|ready

Finalmente, smtpd(8) emite eventos de informe y solicitudes de filtro, esperando que los smtpd-filters respondan o no dependiendo del flujo:

report|0.7|1576146008.006099|smtp-in|link-connect|7641df9771b4ed00|mail.openbsd.org|pass|199.185.178.25:33174|45.77.67.80:25
report|0.7|1576147242.200225|smtp-in|link-connect|7641dfb3798eb5bf|mail.openbsd.org|pass|199.185.178.25:31205|45.77.67.80:25
report|0.7|1576148447.982572|smtp-in|link-connect|7641dfc063102cbd|mail.openbsd.org|pass|199.185.178.25:24786|45.77.67.80:25

El carácter “|” solo puede aparecer en el último campo de una carga útil, en cuyo caso debe considerarse un carácter regular y no un separador. Ningún otro campo puede contener un “|”.

La lista de subsistemas y eventos, así como el formato de las solicitudes y respuestas, se documentan en las siguientes secciones.

CONFIGURACIÓN

Durante el saludo inicial, smtpd(8) emite una serie de claves y valores de configuración. La lista está pensada para ser ignorada por los smtpd-filters que no la necesiten y consumida amablemente por los filtros que sí lo hagan.

Actualmente hay tres claves:

config|smtpd-version|7.8.0
config|protocol|0.7
config|smtp-session-timeout|300
config|subsystem|smtp-in

Cuando smtpd(8) ha enviado todas las claves de configuración, emite la siguiente línea:

config|ready

EVENTOS DE INFORME

Actualmente solo hay un subsistema compatible en la API: smtp-in.

Cada evento de informe es generado por smtpd(8) como una única línea similar a la siguiente:

report|0.7|1576146008.006099|smtp-in|link-connect|7641df9771b4ed00|mail.openbsd.org|pass|199.185.178.25:33174|45.77.67.80:25

El formato consta de un prefijo de protocolo que contiene el flujo, la versión del protocolo, la marca de tiempo, el subsistema, el evento y el identificador único de la sesión, separados por “|”:

report|0.7|1576146008.006099|smtp-in|link-connect|7641df9771b4ed00

Le sigue un sufijo que contiene los parámetros específicos del evento, también separados por “|”:

mail.openbsd.org|pass|199.185.178.25:33174|45.77.67.80:25

La lista de eventos y parámetros específicos del evento para smtp-in son las siguientes:

link-connect: rdns fcrdns src dest
Este evento se genera al conectar.

rdns contiene el nombre de host DNS inverso para el extremo remoto o una cadena vacía si no hay ninguno.

fcrdns contiene la cadena “pass” o “fail” dependiendo de si el extremo remoto valida FCrDNS.

src contiene la dirección IP y el puerto de la dirección de origen, en el formato “address:port”, o la ruta a un socket UNIX en el formato “unix:/path”.

dest contiene la dirección IP y el puerto de la dirección de destino, en el formato “address:port”, o la ruta a un socket UNIX en el formato “unix:/path”.

link-greeting: hostname
Este evento se genera al mostrar el banner del servidor.

hostname contiene el nombre de host mostrado en el banner.

EVENT TYPES

link-identify: method identity
Este evento se genera al recibir el comando “HELO” o “EHLO” del cliente.

method contiene la cadena “HELO” o “EHLO” indicando el método utilizado por el cliente.

identity contiene la identidad proporcionada por el cliente.

link-tls: tls-string
Este evento se genera tras la negociación exitosa de TLS.

tls-string contiene una lista separada por dos puntos de propiedades TLS que incluyen la versión TLS, el conjunto de cifrado utilizado por la sesión y la fortaleza del cifrado en bits.

link-disconnect
Este evento se genera al desconectarse el cliente.
link-auth: result username
Este evento se genera al producirse un intento de autenticación por parte del cliente.

result contiene la cadena “pass”, “fail” o “error” dependiendo del resultado del intento de autenticación.

username contiene el nombre de usuario utilizado para el intento de autenticación.

tx-reset: [message-id]
Este evento se genera cuando se restablece una transacción.

Si el restablecimiento se produjo durante una transacción, message-id contiene el identificador de la transacción que se está restableciendo.

tx-begin: message-id
Este evento se genera cuando se inicia una transacción.

message-id contiene el identificador de la transacción.

tx-mail: message-id result address
Este evento se genera cuando el cliente emite “MAIL FROM”.

message-id contiene el identificador de la transacción.

result contiene “ok” si el remitente fue aceptado, “permfail” si fue rechazado o “tempfail” si fue rechazado por un error transitorio.

address contiene la dirección de correo electrónico del remitente. La dirección se normaliza y se limpia, se eliminan los caracteres “<” y “>”, junto con cualquier parámetro de “MAIL FROM”.

tx-rcpt: message-id result address
Este evento se genera cuando el cliente emite “RCPT TO”.

message-id contiene el identificador de la transacción.

result contiene “ok” si el destinatario fue aceptado, “permfail” si fue rechazado o “tempfail” si fue rechazado por un error transitorio.

address contiene la dirección de correo electrónico del destinatario. La dirección se normaliza y se limpia, se eliminan los caracteres “<” y “>”, junto con cualquier parámetro de “RCPT TO”.

tx-envelope: message-id envelope-id
Este evento se genera cuando se acepta un sobre.

envelope-id contiene el identificador único del sobre.

tx-data: message-id result
Este evento se genera cuando el cliente ha emitido “DATA”.

message-id contiene el identificador único de la transacción.

result contiene “ok” si el servidor aceptó el mensaje para su procesamiento, “permfail” si no ha sido aceptado y “tempfail” si un error transitorio impidió el procesamiento del mensaje.

tx-commit: message-id message-size
Este evento se genera cuando el servidor ha aceptado una transacción.

message-id contiene el identificador único de la transacción SMTP.

message-size contiene el tamaño del mensaje enviado en la fase “DATA” de la transacción SMTP.

tx-rollback: message-id
Este evento se genera cuando el servidor ha rechazado una transacción.

message-id contiene el identificador único de la transacción SMTP.

protocol-client: command
Este evento se genera para cada comando enviado por el cliente. Contiene el comando bruto tal como lo recibió el servidor.

command contiene el comando emitido por el cliente al servidor.

protocol-server: response
Este evento se genera para cada respuesta emitida por el servidor. Contiene la respuesta bruta tal como la emitió el servidor.

response contiene la respuesta emitida por el servidor al cliente.

filter-report: filter-kind name message
Este evento se genera cuando un filtro emite un informe.

filter-kind puede ser “builtin” o “proc” dependiendo de si el filtro es un filtro incorporado de smtpd(8) o un filtro de proceso que implementa la API.

name es el nombre del filtro que generó el informe.

message es un mensaje específico del filtro.

filter-response: phase response [param]
Este evento se genera cuando un filtro responde a una solicitud de filtrado.

phase contiene el nombre de la fase de la solicitud. Las fases se documentan en la siguiente sección.

response contiene la respuesta del filtro a la solicitud, y es una de las siguientes: “proceed”, “report”, “reject”, “disconnect”, “junk” o “rewrite”.

Si se especifica, param es el parámetro de la respuesta.

timeout
Este evento se genera cuando ocurre un tiempo de espera para una sesión.

Actualmente, solo se admite un subsistema en la API: smtp-in.

Las solicitudes de filtro permiten a smtpd(8) consultar a smtpd-filters sobre qué hacer con una sesión en una fase particular. Además, permiten a smtpd-filters alterar el contenido de un mensaje añadiendo, modificando o suprimiendo líneas de entrada de una manera similar a lo que harían programas como sed(1) o grep(1).

Cada solicitud de filtro es generada por smtpd(8) como una sola línea similar a la siguiente. Los campos están separados por el carácter “|”.

filter|0.7|1576146008.006099|smtp-in|connect|7641df9771b4ed00|1ef1c203cc576e5d|mail.openbsd.org|199.185.178.25

El formato consiste en un prefijo de protocolo que contiene el flujo, la versión del protocolo, la marca de tiempo, el subsistema, la fase de filtrado, el identificador único de la sesión y un token opaco que el filtro debe proporcionar en su respuesta:

filter|0.7|1576146008.006099|smtp-in|connect|7641df9771b4ed00|1ef1c203cc576e5d

Le sigue un sufijo que contiene los parámetros específicos de la fase de la solicitud de filtro, también separados por “|”:

mail.openbsd.org|199.185.178.25

A diferencia de los eventos de informe, smtpd(8) espera respuestas de las solicitudes de filtro y no permitirá que una sesión avance hasta que el filtro haya instruido a smtpd(8) sobre cómo tratarla.

filter-result|7641df9771b4ed00|1ef1c203cc576e5d|proceed
filter-result|7641df9771b4ed00|1ef1c203cc576e5d|reject|550 nope

NOMBRE

smtpd-filters — filtros para OpenSMTPD

DESCRIPCIÓN

El demonio smtpd(8) se puede extender con filtros. Estos filtros son programas externos que se ejecutan en un momento determinado durante el protocolo SMTP para inspeccionar o modificar la conexión. Los filtros se invocan a través de la directiva filter en el archivo de configuración de OpenSMTPD.

La directiva filter tiene la siguiente sintaxis:

filter <nombre>
    match <evento> [<evento>...]
    action <comando> [<comando>...]
    listen on <dirección>[:<puerto>]
    listen on <socket>

donde:

nombre:
Un nombre para este filtro. Se utiliza para referenciarlo más adelante en el archivo de configuración.
match <evento>:
Indica qué eventos del protocolo SMTP deben activar este filtro. La lista de eventos válidos se detalla en la sección REPORT EVENTS.
action <comando>:
El comando que se ejecutará para cada evento coincidente. El comando se ejecuta en el contexto del usuario que ejecuta OpenSMTPD, o en el usuario especificado en la configuración.
listen on <dirección>[:<puerto>]:
El filtro se ejecutará como un servidor que escucha en la dirección y puerto especificados. Solo se permite un listen on por filtro.
listen on <socket>:
El filtro se ejecutará como un servidor que escucha en el socket UNIX especificado. Solo se permite un listen on por filtro.

Cuando un filtro coincide con un evento, se le envía una solicitud a través de la interfaz de red o socket UNIX especificada. La solicitud contiene el tipo de evento y los parámetros asociados, codificados como líneas de texto separadas por saltos de línea. El filtro debe responder con una decisión, también codificada como una línea de texto.

DISEÑO

Los filtros están diseñados para ser independientes y solo necesitan entender el protocolo de comunicación definido aquí. No tienen acceso directo al estado del servidor SMTP ni a ninguna otra configuración de OpenSMTPD, excepto por la información proporcionada en la propia solicitud del filtro.

El protocolo de comunicación entre OpenSMTPD y los filtros es simple y se basa en líneas de texto. Cada línea está prefijada con un identificador de evento o decisión, seguido de parámetros separados por el carácter barra vertical (|).

REPORTE Y FILTRO

Existen dos tipos de filtros: de reporte y de filtrado.

report
Los filtros de reporte se utilizan para registrar información sobre la conexión SMTP o los mensajes. No pueden modificar el comportamiento del servidor SMTP.
filter
Los filtros de filtrado pueden tomar decisiones que afectan el flujo de la conexión SMTP, como rechazar un remitente, marcar un mensaje como spam o incluso desconectar al cliente.

PROTOCOLO

El protocolo utiliza una combinación de solicitudes y respuestas. OpenSMTPD envía solicitudes al filtro, y el filtro responde con una decisión.

Las solicitudes de eventos se formatean como:

evento|sesión-id|token-opaco|parámetro1|parámetro2|...

donde:

evento:
El tipo de evento que ocurrió (por ejemplo, connect, helo, etc.).
sesión-id:
Un identificador único para la sesión SMTP actual.
token-opaco:
Un token opaco que debe ser devuelto por el filtro en su respuesta. Esto ayuda a OpenSMTPD a correlacionar las respuestas con las solicitudes correctas.
parámetro1|parámetro2|...:
Los parámetros específicos del evento.

Las respuestas del filtro se formatean como:

decisión|sesión-id|token-opaco|parámetro1|parámetro2|...

donde decisión es una de las acciones disponibles (ver sección FILTER REQUESTS).

La respuesta a las solicitudes de “data-line” utiliza su propia estructura. Un prefijo “filter-dataline”, seguido del identificador de sesión único, el token opaco y la línea de salida como sigue:

filter-dataline|7641df9771b4ed00|1ef1c203cc576e5d|línea 1
filter-dataline|7641df9771b4ed00|1ef1c203cc576e5d|línea 2
filter-dataline|7641df9771b4ed00|1ef1c203cc576e5d|.|

CONFIGURACIÓN

Los filtros se configuran en el archivo /etc/smtpd.conf utilizando la directiva filter. Por ejemplo:

filter check_spam
    match connect helo
    listen on 127.0.0.1:8025

filter log_mail
    match mail-from rcpt-to data
    action log

El ejemplo anterior define dos filtros:

  • check_spam: que escucha en la dirección local en el puerto 8025 y coincide con los eventos connect y helo.
  • log_mail: que coincide con los eventos mail-from, rcpt-to y data, y luego registra la información utilizando la acción log.

EVENTOS DE REPORTE

La siguiente lista de eventos y parámetros específicos para smtp-in son los siguientes:

connect: rdns src
Este evento se emite después de la conexión, antes de que se muestre el banner. src contiene la dirección IP de origen (a.b.c.d para IPv4 o [x:x:x:x:x:x:x:x] para IPv6) o “local” (para sockets UNIX).
helo: identity
Este evento se emite después de que el cliente emite “HELO”.
ehlo: identity
Este evento se emite después de que el cliente emite “EHLO”.
starttls: tls-string
Este evento se emite después de que el cliente solicita “STARTTLS”.
auth: auth
Este evento se emite después de que el cliente solicita “AUTH”.
mail-from: address
Este evento se emite después de que el cliente solicita “MAIL FROM”.
rcpt-to: address
Este evento se emite después de que el cliente solicita “RCPT TO”.
data
Este evento se emite después de que el cliente solicita “DATA”.
data-line: line
Este evento se emite para cada línea de entrada durante la fase “DATA”. Las líneas son datos de entrada SMTP crudos con escape de puntos, terminados con un solo punto.
commit
Este evento se emite después de recibir el punto final único.

SOLICITUDES DE FILTRO

Para cada fase de filtrado, excepto “data-line”, las siguientes decisiones pueden ser tomadas por un filtro:

proceed
No se toma ninguna acción, la sesión o transacción puede pasar al siguiente filtro.
junk
La sesión o transacción se marca como spam. smtpd(8) prepondrá una cabecera “X-Spam” al mensaje.
reject error
El comando se rechaza con el mensaje error. El mensaje debe ser un mensaje SMTP válido que incluya el código de estado, 5xx o 4xx.

Los mensajes que comienzan con un estado 5xx resultan en un fallo permanente, aquellos que comienzan con un estado 4xx resultan en un fallo temporal.

Los mensajes que comienzan con un estado 421 resultarán en una desconexión del cliente.

disconnect error
El cliente se desconecta con el mensaje error. El mensaje debe ser un mensaje SMTP válido que incluya el código de estado, 5xx o 4xx.

Los mensajes que comienzan con un estado 5xx resultan en un fallo permanente, aquellos que comienzan con un estado 4xx resultan en un fallo temporal.

rewrite parameter
El parámetro del comando se reescribe.

Esta decisión permite a un filtro realizar una reescritura de los comandos enviados por el cliente antes de que sean procesados por el motor SMTP. Se espera que parameter sea un parámetro SMTP válido para el comando.

report parameter
Genera un reporte con parameter para este filtro.
