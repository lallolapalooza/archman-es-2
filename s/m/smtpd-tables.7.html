NOMBRE

smtpd-tables — API de tablas para el demonio smtpd

DESCRIPCIÓN

El demonio smtpd(8) proporciona una implementación del Protocolo Simple de Transferencia de Correo (SMTPD), que permite a las máquinas ordinarias convertirse en Intercambiadores de Correo (MX). Algunas características comúnmente utilizadas por los MX, como la consulta de bases de datos para credenciales de usuario, están fuera del alcance de SMTP y son demasiado complejas para encajar en smtpd(8).

Dado que un MX puede necesitar proporcionar estas características, smtpd(8) proporciona una API para implementar backends de table(5) con un protocolo simple basado en texto.

DISEÑO

smtpd-tables son programas que se ejecutan como procesos independientes únicos, no comparten el espacio de direcciones de smtpd(8). Son ejecutados por smtpd(8) al inicio y se espera que se ejecuten en un bucle infinito, leyendo eventos y consultas de la entrada estándar y escribiendo respuestas en la salida estándar. No se les permite terminar.

Dado que smtpd-tables son programas independientes que se comunican con smtpd(8), pueden ejecutarse con usuarios diferentes a smtpd(8) y pueden estar escritos en cualquier idioma. smtpd-tables no debe usar E/S bloqueante, debe admitir responder asincrónicamente a smtpd(8).

PROTOCOLO

El protocolo consiste en líneas legibles por humanos intercambiadas entre smtpd-tables y smtpd(8).

El protocolo comienza con un apretón de manos. Primero, smtpd(8) proporciona a smtpd-tables información general de configuración en forma de líneas clave-valor, terminadas por ‘config|ready’. Por ejemplo:

config|smtpd-version|7.8.0
config|protocol|0.1
config|tablename|devs
config|ready

Luego, smtpd-tables registra los servicios compatibles, terminando con ‘register|ready’. Por ejemplo:

register|alias
register|credentials
register|ready

Finalmente, smtpd(8) puede comenzar a consultar la tabla. Por ejemplo:

table|0.1|1713795082.354255|devs|lookup|alias|b72508d|op

El carácter “|” se usa para separar los campos y solo puede aparecer literalmente en el último campo de la carga útil, en cuyo caso debe considerarse un carácter regular y no un separador. Ningún otro campo puede contener un “|”.

Cada solicitud tiene un conjunto común de campos, seguido de otros campos que son específicos de la operación. El formato común consiste en un prefijo de protocolo ‘table’, la versión del protocolo, la marca de tiempo y el nombre de la tabla. Por ejemplo:

table|0.1|1713795091.202157|devs

El protocolo es inherentemente asincrónico, por lo que se pueden enviar múltiples solicitudes sin esperar la respuesta de la tabla. Todas las respuestas tienen un prefijo común, seguido de la respuesta específica de la operación. El formato común consiste en un prefijo con el nombre de la operación seguido de ‘-result’, y el identificador único de la solicitud. Por ejemplo:

lookup-result|b72508d

La lista de operaciones, parámetros y respuestas específicos de la operación son los siguientes:

update id
Solicita a la tabla que recargue su configuración. El resultado es ‘ok’ en caso de éxito o ‘error’ y un mensaje en caso de fallo al hacerlo.
check servicio id consulta
Comprueba si consulta está presente en la tabla. El resultado es ‘found’ si se encuentra, ‘not-found’ si no, o ‘error’ y un mensaje en caso de error.
lookup servicio id consulta
Busca un valor en la tabla dada la consulta. El resultado es ‘found’ y el valor si se encuentra, ‘not-found’ si no se encuentra, o ‘error’ y un mensaje en caso de error.
fetch servicio id
Obtiene el siguiente elemento de la tabla, eventualmente volviendo al principio. Solo se admite para los servicios source y relayhost. El resultado es ‘found’ y el valor si se encuentra, ‘not-found’ si la tabla está vacía, o ‘error’ y un mensaje en caso de error.

Cada servicio tiene un formato específico para el resultado. La sintaxis exacta de los valores y eventualmente las claves se describe en table(5). Los servicios y su formato de resultado son los siguientes:

alias
Uno o más alias separados por coma.
auth
Solo utilizable para check. La clave de búsqueda es el nombre de usuario y la contraseña en texto plano separada por ‘:’.
domain
Un nombre de dominio.
credentials
El nombre de usuario, seguido de ‘:’ y la contraseña cifrada según el subcomando encrypt de smtpctl(8).
netaddr
Dirección o máscara de red IPv4 e IPv6.
userinfo
El ID de usuario, seguido de ‘:’ luego el ID de grupo, luego ‘:’ y finalmente el directorio de inicio.
source
Dirección IPv4 e IPv6.
mailaddr
Un nombre de usuario, un dominio o una dirección de correo electrónico completa.
addrname
Se utiliza para mapear direcciones IP a nombres de host.

EJEMPLOS

Suponiendo que la tabla se llama “devs”, aquí hay un ejemplo de una transacción update fallida:

table|0.1|1713795097.394049|devs|update|478ff0d2
update-result|478ff0d2|error|failed to connect to the database

Una solicitud check para el servicio netaddr para la dirección IPv4 192.168.0.7 que no está en la tabla:

table|0.1|1713795103.314423|devs|check|netaddr|e5862859|192.168.0.7
check-result|e5862859|not-found

Una solicitud lookup exitosa para el servicio userinfo para el usuario ‘op’:

table|0.1|1713795110.354921|devs|lookup|userinfo|f993c74|op
lookup-result|f993c74|found|1000:1000:/home/op

Una serie de solicitudes fetch para el servicio source que se reinicia:

table|0.1|1713795116.227321|devs|fetch|source|189bd3ee
lookup-result|189bd3ee|found|192.168.1.7
table|0.1|1713795120.162438|devs|fetch|source|9e4c56d4
lookup-result|9e4c56d4|found|10.0.0.8
table|0.1|1713795122.930928|devs|fetch|source|f2c8b906
lookup-result|f2c8b906|found|192.168.1.7
