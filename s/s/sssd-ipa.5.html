SSSD-IPA(5) Formatos de archivo y convenciones SSSD-IPA(5)

NOMBRE

sssd-ipa - Proveedor IPA de SSSD

DESCRIPCIÓN

Esta página del manual describe la configuración del proveedor IPA para sssd(8). Para una referencia de sintaxis detallada, consulte la sección “FORMATO DEL ARCHIVO” de la página del manual de sssd.conf(5).

El proveedor IPA es un backend utilizado para conectarse a un servidor IPA. (Consulte el sitio web freeipa.org para obtener información sobre los servidores IPA). Este proveedor requiere que la máquina esté unida al dominio IPA; la configuración se autodescubre casi por completo y se obtiene directamente del servidor.

El proveedor IPA permite a SSSD utilizar el proveedor de identidad sssd-ldap(5) y el proveedor de autenticación sssd-krb5(5) con optimizaciones para entornos IPA. El proveedor IPA acepta las mismas opciones que utilizan los proveedores sssd-ldap y sssd-krb5, con algunas excepciones. Sin embargo, no es necesario ni recomendable establecer estas opciones.

El proveedor IPA principalmente copia las opciones predeterminadas tradicionales de los proveedores ldap y krb5, con algunas excepciones. Las diferencias se enumeran en la sección “OPCIONES PREDETERMINADAS MODIFICADAS”.

Como proveedor de acceso, el proveedor IPA tiene una configuración mínima (ver “ipa_access_order”) ya que utiliza principalmente reglas HBAC (control de acceso basado en host). Por favor, consulte freeipa.org para obtener más información sobre HBAC.

Si se configura “auth_provider=ipa” o “access_provider=ipa” en sssd.conf, entonces id_provider también debe establecerse en “ipa”.

El proveedor IPA utilizará el respondedor PAC si los tickets Kerberos de los usuarios de reinos confiables contienen un PAC. Para facilitar la configuración, el respondedor PAC se inicia automáticamente si se configura el proveedor de ID de IPA.

OPCIONES DE CONFIGURACIÓN

Consulte la sección “SECCIONES DE DOMINIO” de la página del manual de sssd.conf(5) para obtener detalles sobre la configuración de un dominio SSSD.

ipa_domain (cadena)

Especifica el nombre del dominio IPA. Esto es opcional. Si no se proporciona, se utiliza el nombre del dominio de configuración.

ipa_server, ipa_backup_server (cadena)

La lista separada por comas de direcciones IP o nombres de host de los servidores IPA a los que SSSD debe conectarse, en orden de preferencia. Para obtener más información sobre la conmutación por error y la redundancia de servidores, consulte la sección “CONMUTACIÓN POR ERROR”. Esto es opcional si la autodescubrimiento está habilitada. Para obtener más información sobre el descubrimiento de servicios, consulte la sección “DESCUBRIMIENTO DE SERVICIOS”.

ipa_hostname (cadena)

Opcional. Puede establecerse en máquinas donde el nombre de host (5) no refleja el nombre completo utilizado en el dominio IPA para identificar este host. El nombre de host debe ser completo.

dyndns_update (booleano)

Opcional. Esta opción indica a SSSD que actualice automáticamente el servidor DNS integrado en FreeIPA con la dirección IP de este cliente. La actualización se asegura utilizando GSS-TSIG. La dirección IP de la conexión LDAP de IPA se utiliza para las actualizaciones, si no se especifica de otra manera utilizando la opción “dyndns_iface”.

NOTA: En sistemas más antiguos (como RHEL 5), para que este comportamiento funcione de manera confiable, el reino Kerberos predeterminado debe estar configurado correctamente en /etc/krb5.conf.

NOTA: Aunque todavía es posible usar la antigua opción ipa_dyndns_update, los usuarios deberían migrar al uso de dyndns_update en su archivo de configuración.

Predeterminado: falso

dyndns_ttl (entero)

El TTL que se aplicará al registro DNS del cliente al actualizarlo. Si dyndns_update es falso, esto no tiene ningún efecto. Esto anulará el TTL en el servidor si lo establece un administrador.

NOTA: Aunque todavía es posible usar la antigua opción ipa_dyndns_ttl, los usuarios deberían migrar al uso de dyndns_ttl en su archivo de configuración.

Predeterminado: 1200 (segundos)

dyndns_iface (cadena)

Opcional. Aplicable solo cuando dyndns_update es verdadero. Elija la interfaz o una lista de interfaces cuyas direcciones IP se utilizarán para actualizaciones de DNS dinámicas. El nombre de la interfaz puede ser un patrón comodín. Consulte man 7 glob para obtener detalles sobre los patrones.

NOTA: Aunque todavía es posible usar la antigua opción ipa_dyndns_iface, los usuarios deberían migrar al uso de dyndns_iface en su archivo de configuración.

Predeterminado: Utilice las direcciones IP de la interfaz que se utiliza para la conexión LDAP de IPA.

Ejemplo: dyndns_iface = em1, vnet1, vnet2

dyndns_auth (cadena)

Si la utilidad nsupdate debe usar autenticación GSS-TSIG para actualizaciones seguras con el servidor DNS, se pueden enviar actualizaciones inseguras estableciendo esta opción en 'none'.

Predeterminado: GSS-TSIG

dyndns_auth_ptr (cadena)

Si la utilidad nsupdate debe usar autenticación GSS-TSIG para actualizaciones PTR seguras con el servidor DNS, se pueden enviar actualizaciones inseguras estableciendo esta opción en 'none'.

Predeterminado: Igual que dyndns_auth

ipa_enable_dns_sites (booleano)

Habilita los sitios DNS - descubrimiento de servicios basado en la ubicación.

Si es verdadero y el descubrimiento de servicios (ver el párrafo Service Discovery en la parte inferior de la página del manual) está habilitado, SSSD primero intentará el descubrimiento basado en la ubicación utilizando una consulta que contenga "_location.nombredehost.ejemplo.com" y luego recurrirá al descubrimiento SRV tradicional. Si el descubrimiento basado en la ubicación tiene éxito, los servidores IPA ubicados con el descubrimiento basado en la ubicación se tratan como servidores primarios y los servidores IPA ubicados utilizando el descubrimiento SRV tradicional se utilizan como servidores de respaldo.

Predeterminado: falso

dyndns_refresh_interval (entero)

¿Con qué frecuencia el backend realizará una actualización DNS periódica además de la actualización automática realizada cuando el backend se conecta. Esta opción es opcional y solo aplicable cuando dyndns_update es verdadero.

Predeterminado: 0 (deshabilitado)

dyndns_update_ptr (booleano)

Si el registro PTR también debe actualizarse explícitamente al actualizar los registros DNS del cliente. Aplicable solo cuando dyndns_update es verdadero.

Esta opción debería ser Falsa en la mayoría de las implementaciones IPA, ya que el servidor IPA genera los registros PTR automáticamente cuando se cambian los registros directos.

Tenga en cuenta que el parámetro dyndns_update_per_family no se aplica a las actualizaciones de registros PTR. Esas actualizaciones siempre se envían por separado.

Predeterminado: Falso (deshabilitado)

dyndns_force_tcp (booleano)

Si la utilidad nsupdate debe utilizar TCP por defecto para comunicarse con el servidor DNS.

Predeterminado: Falso (deje que nsupdate elija el protocolo)

dyndns_server (cadena)

El servidor DNS a utilizar al realizar una actualización DNS. En la mayoría de las configuraciones, se recomienda dejar esta opción sin establecer.

Establecer esta opción tiene sentido para entornos donde el servidor DNS es diferente del servidor de identidad o cuando usamos DNS cifrado.

El parámetro puede ser una cadena simple que contenga el nombre o la dirección IP del DNS. También puede ser una URI. La URI puede parecer dns://nombredelservidor/ o dns+tls://1.2.3.4:853#nombredelservidor/.

El segundo ejemplo habilita el protocolo DNS-over-TLS para actualizaciones DNS. La utilidad nsupdate debe admitir DoT; consulte la página man nsupdate antes de habilitarlo en SSSD.

Tenga en cuenta que esta opción solo se utilizará en un intento de reserva cuando el intento anterior utilizando la configuración autodetectada falló o cuando se habilita DNS-over-TLS.

Predeterminado: Ninguno (deje que nsupdate elija el servidor)

dyndns_update_per_family (booleano)

La actualización DNS se realiza por defecto en dos pasos: actualización IPv4 y luego actualización IPv6. En algunos casos, podría ser deseable realizar la actualización IPv4 e IPv6 en un solo paso.

Predeterminado: verdadero

dyndns_dot_cacert (cadena)

Esta opción especifica el archivo de los certificados de las autoridades certificadoras (en formato PEM) para verificar el certificado del servidor remoto TLS al usar DoT.

Predeterminado: Ninguno (usar el almacén de certificados global)

dyndns_dot_cert (cadena)

Esta opción establece el archivo de certificado(s) para la autenticación del transporte DoT al servidor remoto. Se espera la cadena de certificados.

Este sitio no está asociado de ninguna forma con Arch Linux ni afiliado a este proyecto. El contenido es únicamente una traducción de las páginas del manual de Arch publicadas en man.archlinux.org.

IPA ACCESS CONTROL OPTIONS

dyndns_dot_cert (string)

This option sets the certificate file for authenticated encryption for the DoT transport to the remote server. The certificate file is expected to be in PEM format.

The dyndns_dot_cert and dyndns_dot_key options must be both set to achieve mutual TLS authentication.

Default: None (Do not use TLS authentication)

dyndns_dot_key (string)

This option sets the key file for authenticated encryption for the DoT transport to the remote server. The private key file is expected to be in PEM format.

Default: None (Do not use TLS authentication)

ipa_access_order (string)

Comma separated list of access control options. Allowed values are:

expire: use IPA's account expiration policy.

pwd_expire_policy_reject, pwd_expire_policy_warn, pwd_expire_policy_renew: These options are useful if users are interested in being warned that password is about to expire and authentication is based on using a different method than passwords - for example SSH keys.

The difference between these options is the action taken if user password is expired:

•pwd_expire_policy_reject - user is denied to log in,
•pwd_expire_policy_warn - user is still able to log in,
•pwd_expire_policy_renew - user is prompted to change their password immediately.

Please note that 'access_provider = ipa' must be set for this feature to work.

ipa_deskprofile_search_base (string)

Optional. Use the given string as search base for Desktop Profile related objects.

Default: Use base DN

ipa_hbac_search_base (string)

Optional. Use the given string as search base for HBAC related objects.

Default: Use base DN

ipa_host_search_base (string)

Deprecated. Use ldap_host_search_base instead.

ipa_selinux_search_base (string)

Optional. Use the given string as search base for SELinux user maps.

See “ldap_search_base” for information about configuring multiple search bases.

Default: the value of ldap_search_base

ipa_subdomains_search_base (string)

Optional. Use the given string as search base for trusted domains.

See “ldap_search_base” for information about configuring multiple search bases.

Default: the value of cn=trusts,%basedn

ipa_master_domain_search_base (string)

Optional. Use the given string as search base for master domain object.

See “ldap_search_base” for information about configuring multiple search bases.

Default: the value of cn=ad,cn=etc,%basedn

ipa_views_search_base (string)

Optional. Use the given string as search base for views containers.

See “ldap_search_base” for information about configuring multiple search bases.

Default: the value of cn=views,cn=accounts,%basedn

krb5_realm (string)

The name of the Kerberos realm. This is optional and defaults to the value of “ipa_domain”.

The name of the Kerberos realm has a special meaning in IPA - it is converted into the base DN to use for performing LDAP operations.

krb5_confd_path (string)

Absolute path of a directory where SSSD should place Kerberos configuration snippets.

To disable the creation of the configuration snippets set the parameter to 'none'.

Default: not set (krb5.include.d subdirectory of SSSD's pubconf directory)

ipa_deskprofile_refresh (integer)

The amount of time between lookups of the Desktop Profile rules against the IPA server. This will reduce the latency and load on the IPA server if there are many desktop profiles requests made in a short period.

Default: 5 (seconds)

ipa_deskprofile_request_interval (integer)

The amount of time between lookups of the Desktop Profile rules against the IPA server in case the last request did not return any rule.

Default: 60 (minutes)

ipa_hbac_refresh (integer)

The amount of time between lookups of the HBAC rules against the IPA server. This will reduce the latency and load on the IPA server if there are many access-control requests made in a short period.

Default: 5 (seconds)

ipa_hbac_selinux (integer)

The amount of time between lookups of the SELinux maps against the IPA server. This will reduce the latency and load on the IPA server if there are many user login requests made in a short period.

Default: 5 (seconds)

ipa_server_mode (boolean)

This option will be set by the IPA installer (ipa-server-install) automatically and denotes if SSSD is running on an IPA server or not.

On an IPA server SSSD will lookup users and groups from trusted domains directly while on a client it will ask an IPA server.

NOTE: There are currently some assumptions that must be met when SSSD is running on an IPA server.

•The “ipa_server” option must be configured to point to the IPA server itself. This is already the default set by the IPA installer, so no manual change is required.
•The “full_name_format” option must not be tweaked to only print short names for users from trusted domains.

Default: false

ipa_automount_location (string)

The automounter location this IPA client will be using

Default: The location named "default"

Please note that the automounter only reads the master map on startup, so if any autofs-related changes are made to the sssd.conf, you typically also need to restart the automounter daemon after restarting the SSSD.

VIEWS AND OVERRIDES

SSSD can handle views and overrides which are offered by FreeIPA 4.1 and later version. Since all paths and objectclasses are fixed on the server side there is basically no need to configure anything. For completeness the related options are listed here with their default values.

ipa_view_class (string)

Objectclass of the view container.

Default: nsContainer

ipa_view_name (string)

Name of the attribute holding the name of the view.

Default: cn

ipa_override_object_class (string)

Objectclass of the override objects.

Default: ipaOverrideAnchor

ipa_anchor_uuid (string)

Name of the attribute containing the reference to the original object in a remote domain.

Default: ipaAnchorUUID

ipa_user_override_object_class (string)

Name of the objectclass for user overrides. It is used to determine if the found override object is related to a user or a group.

User overrides can contain attributes given by

•ldap_user_name
•ldap_user_uid_number
•ldap_user_gid_number
•ldap_user_gecos
•ldap_user_home_directory
•ldap_user_shell
•ldap_user_ssh_public_key

Default: ipaUserOverride

ipa_group_override_object_class (string)

Name of the objectclass for group overrides. It is used to determine if the found override object is related to a user or a group.

Group overrides can contain attributes given by

•ldap_group_name
•ldap_group_gid_number

Default: ipaGroupOverride

SUBDOMAINS PROVIDER

The IPA subdomains provider behaves slightly differently if it is configured explicitly or implicitly.

If the option 'subdomains_provider = ipa' is found in the domain section of sssd.conf, the IPA subdomains provider is configured explicitly, and all subdomain requests are sent to the IPA server if necessary.

If the option 'subdomains_provider' is not set in the domain section of sssd.conf but there is the option 'id_provider = ipa', the IPA subdomains provider is configured implicitly. In this case, if a subdomain request fails and indicates that the server does not support subdomains, i.e. is not configured for trusts, the IPA subdomains provider is disabled. After an hour or after the IPA provider goes online, the subdomains provider is enabled again.

CONFIGURACIÓN DE DOMINIOS DE CONFIANZA

Algunas opciones de configuración también se pueden establecer para un dominio de confianza. Una configuración de dominio de confianza se puede establecer usando la subsección de dominio de confianza como se muestra en el siguiente ejemplo. Alternativamente, la opción “subdomain_inherit” puede ser utilizada en el dominio padre.

[domain/ipa.domain.com/ad.domain.com]
ad_server = dc.ad.domain.com

Para más detalles, consulte la página del manual sssd.conf(5).

Las diferentes opciones de configuración se pueden ajustar para un dominio de confianza dependiendo de si está configurando SSSD en un servidor IPA o en un cliente IPA.

OPCIONES AJUSTABLES EN MASTERS IPA

Las siguientes opciones se pueden establecer en una sección de subdominio en un master IPA:

•ad_server
•ad_backup_server
•ad_site
•ipa_server
•ipa_backup_server
•ldap_search_base
•ldap_user_search_base
•ldap_group_search_base
•use_fully_qualified_names

Las opciones prefijadas con 'ad_' o 'ipa_' solo se aplican a su respectivo tipo de subdominio.

OPCIONES AJUSTABLES EN CLIENTES IPA

Las siguientes opciones se pueden establecer en una sección de subdominio AD en un cliente IPA:

•ad_server
•ad_site

Tenga en cuenta que si ambas opciones están establecidas, solo se evalúa “ad_server”.

Dado que cualquier solicitud de identidad de usuario o grupo de un dominio de confianza activada desde un cliente IPA es resuelta por el servidor IPA, las opciones “ad_server” y “ad_site” solo afectan a qué DC de AD se realizará la autenticación. En particular, las direcciones resueltas de estas listas se escribirán en los archivos “kdcinfo” leídos por el plugin localizador Kerberos. Consulte la página del manual sssd_krb5_locator_plugin(8) para más detalles sobre el plugin localizador Kerberos.

FALLO DE REDUNDANCIA

La característica de fallo de redundancia permite que los backends cambien automáticamente a un servidor diferente si el servidor actual falla.

Sintaxis de fallo de redundancia

La lista de servidores se proporciona como una lista separada por comas; se permite cualquier número de espacios alrededor de la coma. Los servidores se listan en orden de preferencia. La lista puede contener cualquier número de servidores.

Para cada opción de configuración habilitada para fallo de redundancia, existen dos variantes: *primaria* y *de respaldo*. La idea es que los servidores en la lista primaria son preferidos y los servidores de respaldo solo se buscan si no se puede acceder a ningún servidor primario. Si se selecciona un servidor de respaldo, se establece un tiempo de espera de 31 segundos. Después de este tiempo de espera, SSSD intentará periódicamente reconectarse a uno de los servidores primarios. Si tiene éxito, reemplazará al servidor activo actual (de respaldo).

El mecanismo de fallo de redundancia

El mecanismo de fallo de redundancia distingue entre una máquina y un servicio. El backend primero intenta resolver el nombre de host de una máquina dada; si este intento de resolución falla, la máquina se considera desconectada. No se realizan más intentos para conectarse a esta máquina para ningún otro servicio. Si el intento de resolución tiene éxito, el backend intenta conectarse a un servicio en esta máquina. Si el intento de conexión del servicio falla, entonces solo este servicio en particular se considera desconectado y el backend cambia automáticamente al siguiente servicio. La máquina todavía se considera conectada y aún se puede intentar para otro servicio.

Se realizan intentos de conexión adicionales a máquinas o servicios marcados como desconectados después de un período de tiempo especificado; actualmente está codificado a 30 segundos.

Si no quedan más máquinas para intentar, el backend en su conjunto cambia al modo desconectado, y luego intenta reconectarse cada 30 segundos.

Tiempos de espera y ajuste del fallo de redundancia

Resolver un servidor al que conectarse puede ser tan simple como realizar una única consulta DNS o puede implicar varios pasos, como encontrar el sitio correcto o probar varios nombres de host en caso de que algunos de los servidores configurados no sean accesibles. Los escenarios más complejos pueden llevar algún tiempo y SSSD necesita equilibrar entre proporcionar tiempo suficiente para completar el proceso de resolución y, por otro lado, no intentar durante demasiado tiempo antes de volver al modo desconectado. Si los registros de depuración de SSSD muestran que la resolución del servidor está fallando antes de contactar a un servidor activo, puede considerar cambiar los tiempos de espera.

Esta sección enumera los ajustables disponibles. Consulte su descripción en la página del manual sssd.conf(5).

dns_resolver_server_timeout

Tiempo en milisegundos que establece cuánto tiempo SSSD hablará con un servidor DNS único antes de intentar con el siguiente.

Por defecto: 1000

dns_resolver_op_timeout

Tiempo en segundos para indicar cuánto tiempo SSSD intentará resolver una consulta DNS única (por ejemplo, resolución de un nombre de host o un registro SRV) antes de intentar el siguiente nombre de host o dominio de descubrimiento.

Por defecto: 3

dns_resolver_timeout

Cuánto tiempo SSSD intentará resolver un servicio de fallo de redundancia. Esta resolución de servicio puede incluir internamente varios pasos, como resolver consultas SRV DNS o localizar el sitio.

Por defecto: 6

Para proveedores basados en LDAP, la operación de resolución se realiza como parte de una operación de conexión LDAP. Por lo tanto, la marca de tiempo “ldap_opt_timeout” también debe establecerse en un valor mayor que “dns_resolver_timeout”, que a su vez debe establecerse en un valor mayor que “dns_resolver_op_timeout”, que debe ser mayor que “dns_resolver_server_timeout”.

DESCUBRIMIENTO DE SERVICIOS

La característica de descubrimiento de servicios permite que los backends encuentren automáticamente los servidores apropiados a los que conectarse utilizando una consulta DNS especial. Esta característica no es compatible con los servidores de respaldo.

Configuración

Si no se especifican servidores, el backend utiliza automáticamente el descubrimiento de servicios para intentar encontrar un servidor. Opcionalmente, el usuario puede optar por usar tanto direcciones de servidor fijas como descubrimiento de servicios insertando una palabra clave especial, “_srv_”, en la lista de servidores. Se mantiene el orden de preferencia. Esta característica es útil si, por ejemplo, el usuario prefiere utilizar el descubrimiento de servicios siempre que sea posible y recurrir a un servidor específico cuando no se puedan descubrir servidores mediante DNS.

El nombre de dominio

Consulte el parámetro “dns_discovery_domain” en la página del manual sssd.conf(5) para más detalles.

El protocolo

Las consultas generalmente especifican _tcp como protocolo. Las excepciones se documentan en la descripción de la opción respectiva.

Ver También

Para más información sobre el mecanismo de descubrimiento de servicios, consulte RFC 2782.

EJEMPLO

El siguiente ejemplo asume que SSSD está configurado correctamente y example.com es uno de los dominios en la sección [sssd]. Estos ejemplos solo muestran las opciones específicas del proveedor ipa.

[domain/example.com]
id_provider = ipa
ipa_server = ipaserver.example.com
ipa_hostname = myhost.example.com
