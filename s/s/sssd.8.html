NOMBRE

sssd - Demonio de servicios de seguridad del sistema

SINOPSIS

sssd [opciones]

DESCRIPCIÓN

SSSD proporciona un conjunto de demonios para gestionar el acceso a directorios remotos y mecanismos de autenticación. Ofrece una interfaz NSS y PAM hacia el sistema y un sistema backend enchufable para conectarse a múltiples fuentes de cuentas diferentes, así como una interfaz D-Bus. Es también la base para proporcionar servicios de auditoría y políticas para proyectos como FreeIPA. Proporciona una base de datos más robusta para almacenar usuarios locales, así como datos de usuario extendidos.

OPCIONES

-d,--debug-level NIVEL

SSSD soporta dos representaciones para especificar el nivel de depuración. La más simple es especificar un valor decimal de 0-9, que representa la habilitación de ese nivel y todos los mensajes de depuración de niveles inferiores. La opción más completa es especificar una máscara de bits hexadecimal para habilitar o deshabilitar niveles específicos (como si se desea suprimir un nivel).

Tenga en cuenta que cada servicio de SSSD registra en su propio archivo de registro. Tenga en cuenta también que habilitar “debug_level” en la sección “[sssd]” solo habilita la depuración para el proceso sssd en sí, no para los procesos de respuesta o proveedor. El parámetro “debug_level” debe agregarse a todas las secciones de las que se deseen generar registros de depuración.

Además de cambiar el nivel de registro en el archivo de configuración usando el parámetro “debug_level”, que es persistente, pero requiere reiniciar SSSD, también es posible cambiar el nivel de depuración sobre la marcha usando la herramienta sss_debuglevel(8).

Niveles de depuración actualmente soportados:

0, 0x0010: Fallos fatales. Cualquier cosa que impida que SSSD se inicie o cause que deje de ejecutarse.

1, 0x0020: Fallos críticos. Un error que no mata a SSSD, pero uno que indica que al menos una característica importante no funcionará correctamente.

2, 0x0040: Fallos graves. Un error que anuncia que una solicitud u operación particular ha fallado.

3, 0x0080: Fallos menores. Estos son los errores que se propagarían hacia abajo para causar el fallo de operación 2.

4, 0x0100: Configuraciones.

5, 0x0200: Datos de función.

6, 0x0400: Mensajes de rastreo para funciones de operación.

7, 0x1000: Mensajes de rastreo para funciones de control internas.

8, 0x2000: Contenidos de variables internas de función que pueden ser interesantes.

9, 0x4000: Información de rastreo extremadamente de bajo nivel.

9, 0x20000: Datos de rendimiento y estadísticos, tenga en cuenta que debido a la forma en que se procesan las solicitudes internamente, el tiempo de ejecución registrado de una solicitud puede ser más largo de lo que realmente fue.

10, 0x10000: Información de rastreo de libldb aún más de bajo nivel. Casi nunca es realmente necesario.

Para registrar los niveles de depuración de máscara de bits requeridos, simplemente sume sus números como se muestra en los siguientes ejemplos:

Ejemplo: Para registrar fallos fatales, fallos críticos, fallos graves y datos de función, use 0x0270.

Ejemplo: Para registrar fallos fatales, configuraciones, datos de función, mensajes de rastreo para funciones de control internas, use 0x1310.

Nota: El formato de máscara de bits de los niveles de depuración se introdujo en la versión 1.7.0.

Por defecto: 0x0070 (es decir, fallos fatales, críticos y graves; corresponde a establecer 2 en notación decimal)

--debug-timestamps=modo

1: Añadir una marca de tiempo a los mensajes de depuración

0: Deshabilitar marca de tiempo en los mensajes de depuración

Por defecto: 1

--debug-microseconds=modo

1: Añadir microsegundos a la marca de tiempo en los mensajes de depuración

0: Deshabilitar microsegundos en la marca de tiempo

Por defecto: 0

--logger=valor

Ubicación donde SSSD enviará los mensajes de registro.

stderr: Redirigir los mensajes de depuración a la salida de error estándar.

files: Redirigir los mensajes de depuración a los archivos de registro. Por defecto, los archivos de registro se almacenan en /var/log/sssd y hay archivos de registro separados para cada servicio y dominio de SSSD.

journald: Redirigir los mensajes de depuración a systemd-journald

Por defecto: no establecido (recurrir a journald si está disponible, de lo contrario a stderr)

-D,--daemon

Convertirse en un demonio después de iniciarse.

-i,--interactive

Ejecutar en primer plano, no convertirse en un demonio.

-c,--config

Especificar un archivo de configuración no predeterminado. El valor predeterminado es /etc/sssd/sssd.conf. Para referencia sobre la sintaxis y opciones del archivo de configuración, consulte la página del manual sssd.conf(5).

-?,--help

Mostrar mensaje de ayuda y salir.

--version

Imprimir el número de versión y salir.

SEÑALES

SIGTERM/SIGINT

Informa a SSSD que termine graciosamente todos sus procesos hijos y luego apague el monitor.

SIGHUP

Indica a SSSD que deje de escribir en sus descriptores de archivo de depuración actuales y que los cierre y reabra. Esto está destinado a facilitar la rotación de registros con programas como logrotate.

SIGUSR1

Indica a SSSD que simule operación sin conexión durante la duración del parámetro “offline_timeout”. Esto es útil para pruebas. La señal se puede enviar al proceso sssd o a cualquier proceso sssd_be directamente.

SIGUSR2

Indica a SSSD que se ponga en línea inmediatamente. Esto es útil para pruebas. La señal se puede enviar al proceso sssd o a cualquier proceso sssd_be directamente.

SIGRTMIN+1

Indica a SSSD que reprograme las tareas periódicas. El vigilante interno envía esta señal a los proveedores cuando se detecta un cambio de reloj, aunque se puede enviar a cualquier proceso sssd_be directamente.

ESTADO DE SALIDA

0

SSSD se apagó graciosamente.

1

Configuración o opción de línea de comandos incorrecta.

2

Error de asignación de memoria.

6

SSSD ya se está ejecutando.

Otros códigos

Otros códigos denotan diferentes errores, muy probablemente sobre derechos de acceso requeridos faltantes. Consulte los registros del sistema y de SSSD para obtener detalles.

NOTAS

Si la variable de entorno SSS_NSS_USE_MEMCACHE está establecida en "NO", las aplicaciones cliente no utilizarán la caché rápida en memoria.

Si la variable de entorno SSS_LOCKFREE está establecida en "NO", las solicitudes de múltiples hilos de una sola aplicación se serializarán.
