NOMBRE

sss-certmap - Reglas de Coincidencia y Mapeo de Certificados de SSSD

DESCRIPCIÓN

La página del manual describe las reglas que pueden ser utilizadas por SSSD y otros componentes para hacer coincidir certificados X.509 y mapearlos a cuentas.

Cada regla tiene cuatro componentes: una "prioridad", una "regla de coincidencia", una "regla de mapeo" y una "lista de dominios". Todos los componentes son opcionales. Una "prioridad" faltante agregará la regla con la prioridad más baja. La "regla de coincidencia" predeterminada coincidirá con certificados con el uso de clave digitalSignature y el uso de clave extendido clientAuth. Si la "regla de mapeo" está vacía, los certificados se buscarán en el atributo userCertificate como binario codificado en DER. Si no se proporcionan dominios, solo se buscará el dominio local.

Para permitir extensiones o un estilo de regla completamente diferente, las "reglas de mapeo" y "reglas de coincidencia" pueden contener un prefijo separado por un ':' de la parte principal de la regla. El prefijo solo puede contener letras mayúsculas ASCII y números. Si se omite el prefijo, se utilizará el tipo predeterminado, que es 'KRB5' para las reglas de coincidencia y 'LDAP' para las reglas de mapeo.

La utilidad 'sssctl' proporciona el comando 'cert-eval-rule' para verificar si un certificado dado coincide con una regla de coincidencia y cómo sería la salida de una regla de mapeo.

COMPONENTES DE LA REGLA

PRIORIDAD

Las reglas se procesan por prioridad, donde el número '0' (cero) indica la prioridad más alta. Cuanto mayor sea el número, menor será la prioridad. Un valor faltante indica la prioridad más baja. El procesamiento de reglas se detiene cuando se encuentra una regla que coincide y no se verifican más reglas.

Internamente, la prioridad se trata como un entero sin signo de 32 bits; usar un valor de prioridad mayor que 4294967295 causará un error.

Si varias reglas tienen la misma prioridad y solo una de las reglas de coincidencia relacionadas se aplica, se elegirá esa regla. Si hay varias reglas con la misma prioridad que coinciden, se elige una, pero cuál es indefinido. Para evitar este comportamiento indefinido, use prioridades diferentes o haga que las reglas de coincidencia sean más específicas, por ejemplo, usando patrones de <ISSUER> distintos.

REGLA DE COINCIDENCIA

La regla de coincidencia se utiliza para seleccionar un certificado al que se aplicará la regla de mapeo. Utiliza un sistema similar al utilizado por la opción “pkinit_cert_match” de MIT Kerberos. Consiste en una palabra clave encerrada entre '<' y '>' que identifica una parte cierta del certificado y un patrón que debe encontrarse para que la regla coincida. Se pueden unir múltiples pares de palabra clave y patrón con '&&' (y) o '||' (o).

Dada la similitud con MIT Kerberos, el prefijo de tipo para esta regla es 'KRB5'. Pero 'KRB5' también será el valor predeterminado para las "reglas de coincidencia", por lo que "<SUBJECT>.*,DC=MI,DC=DOMINIO" y "KRB5:<SUBJECT>.*,DC=MI,DC=DOMINIO" son equivalentes.

Las opciones disponibles son:

<SUBJECT>expresión-regular

Con esto se puede hacer coincidir una parte o el nombre completo del sujeto del certificado. Para la coincidencia, se utiliza la sintaxis de Expresión Regular Extendida POSIX, consulte regex(7) para más detalles.

Para la coincidencia, el nombre del sujeto almacenado en el certificado en ASN.1 codificado en DER se convierte en una cadena según RFC 4514. Esto significa que el componente de nombre más específico va primero. Tenga en cuenta que no todos los nombres de atributos posibles están cubiertos por RFC 4514. Los nombres incluidos son 'CN', 'L', 'ST', 'O', 'OU', 'C', 'STREET', 'DC' y 'UID'. Otros nombres de atributos pueden mostrarse de manera diferente en diferentes plataformas y por diferentes herramientas. Para evitar confusiones, es mejor no usar estos nombres de atributos o cubrirlos con una expresión regular adecuada.

Ejemplo: <SUBJECT>.*,DC=MI,DC=DOMINIO

Tenga en cuenta que los caracteres "^.[$()|*+?{\" tienen un significado especial en las expresiones regulares y deben escaparse con la ayuda del carácter '\' para que coincidan como caracteres ordinarios.

Ejemplo: <SUBJECT>^CN=.* \(Admin\),DC=MI,DC=DOMINIO$

<ISSUER>expresión-regular

Con esto se puede hacer coincidir una parte o el nombre completo del emisor del certificado. Todos los comentarios para <SUBJECT> se aplican aquí también.

Ejemplo: <ISSUER>^CN=Mi-CA,DC=MI,DC=DOMINIO$

<KU>uso-de-clave

Esta opción se puede utilizar para especificar qué valores de uso de clave deben tener los certificados. Los siguientes valores se pueden utilizar en una lista separada por comas:
•digitalSignature
•nonRepudiation
•keyEncipherment
•dataEncipherment
•keyAgreement
•keyCertSign
•cRLSign
•encipherOnly
•decipherOnly

También se puede utilizar un valor numérico en el rango de un entero sin signo de 32 bits para cubrir casos de uso especiales.

Ejemplo: <KU>digitalSignature,keyEncipherment

<EKU>uso-de-clave-extendido

Esta opción se puede utilizar para especificar qué uso de clave extendido debe tener el certificado. El siguiente valor se puede utilizar en una lista separada por comas:
•serverAuth
•clientAuth
•codeSigning
•emailProtection
•timeStamping
•OCSPSigning
•KPClientAuth
•pkinit
•msScLogin

Los usos de clave extendidos que no se enumeran arriba se pueden especificar con su OID en notación decimal punteada.

Ejemplo: <EKU>clientAuth,1.3.6.1.5.2.3.4

<SAN>expresión-regular

Para ser compatible con el uso de MIT Kerberos, esta opción coincidirá con los principales de Kerberos en el SAN de PKINIT o AD NT Principal, tal como lo hace <SAN:Principal>.

Ejemplo: <SAN>.*@MI\.REALM

<SAN:Principal>expresión-regular

Coincide con los principales de Kerberos en el SAN de PKINIT o AD NT Principal.

Ejemplo: <SAN:Principal>.*@MI\.REALM

<SAN:ntPrincipalName>expresión-regular

Coincide con los principales de Kerberos del SAN de AD NT Principal.

Ejemplo: <SAN:ntPrincipalName>.*@MI.AD.REALM

<SAN:pkinit>expresión-regular

Coincide con los principales de Kerberos del SAN de PKINIT.

Ejemplo: <SAN:ntPrincipalName>.*@MI\.PKINIT\.REALM

<SAN:dotted-decimal-oid>expresión-regular

Toma el valor del componente SAN otherName dado por el OID en notación decimal punteada, lo interpreta como una cadena e intenta hacerlo coincidir con la expresión regular.

Ejemplo: <SAN:1.2.3.4>prueba

<SAN:otherName>cadena-base64

Realiza una coincidencia binaria con el blob codificado en base64 contra todos los componentes SAN otherName. Con esta opción es posible hacer coincidir componentes otherName personalizados con codificaciones especiales que no se pudieron tratar como cadenas.

Ejemplo: <SAN:otherName>MTIz

<SAN:rfc822Name>expresión-regular

Coincide con el valor del SAN rfc822Name.

Ejemplo: <SAN:rfc822Name>.*@correo\.dominio

<SAN:dNSName>expresión-regular

Coincide con el valor del SAN dNSName.

Ejemplo: <SAN:dNSName>.*\.mi\.dns\.dominio

<SAN:x400Address>cadena-base64

Coincidencia binaria del valor del SAN x400Address.

Ejemplo: <SAN:x400Address>MTIz

<SAN:directoryName>expresión-regular

Coincide con el valor del SAN directoryName. Los mismos comentarios dados para <ISSUER> y <SUBJECT> se aplican aquí también.

Ejemplo: <SAN:directoryName>.*,DC=com

<SAN:ediPartyName>cadena-base64

SUBJECT ALTERNATIVE NAME

The subject alternative name (SAN) extension allows identities to be specified in the certificate other than the subject's principal name (RFC 6125, section 4.2.1.6). It is defined as an extension that is a sequence of general name strings.

The following general name types are recognized:

• ediPartyName

• uniformResourceIdentifier

• iPAddress

• registeredID

• otherName

• directoryName

• iPNetworkAddress

• dNSName

• x400Address

• rFC822Name

The following general name types can be used in the mapping rule:

<SAN:ediPartyName>regular-expression

Coincide el valor del ediPartyName SAN.

Ejemplo: <SAN:ediPartyName>MTIz

<SAN:uniformResourceIdentifier>regular-expression

Coincide el valor del uniformResourceIdentifier SAN.

Ejemplo: <SAN:uniformResourceIdentifier>URN:.*

<SAN:iPAddress>regular-expression

Coincide el valor del iPAddress SAN.

Ejemplo: <SAN:iPAddress>192\.168\..*

<SAN:registeredID>regular-expression

Coincide el valor del registeredID SAN como cadena decimal con puntos.

Ejemplo: <SAN:registeredID>1\.2\.3\..*

REGLA DE MAPEO

La regla de mapeo se usa para asociar un certificado con una o más cuentas. Una tarjeta inteligente con el certificado y la clave privada correspondiente puede usarse entonces para autenticarse como una de esas cuentas.

Actualmente, SSSD básicamente solo admite LDAP para buscar información de usuario (la excepción es el proveedor proxy que no es de relevancia aquí). Debido a esto, la regla de mapeo se basa en la sintaxis del filtro de búsqueda LDAP con plantillas para agregar contenido del certificado al filtro. Se espera que el filtro solo contenga los datos específicos necesarios para el mapeo y que el llamador lo incruste en otro filtro para realizar la búsqueda real. Debido a esto, la cadena del filtro debe comenzar y terminar con '(' y ')', respectivamente.

En general, se recomienda usar atributos del certificado y agregarlos a atributos especiales del objeto de usuario LDAP. Por ejemplo, se puede usar el atributo 'altSecurityIdentities' en AD o el atributo 'ipaCertMapData' para IPA.

Esto debería preferirse a leer datos específicos del usuario del certificado, como por ejemplo una dirección de correo electrónico, y buscarlo en el servidor LDAP. La razón es que los datos específicos del usuario en LDAP pueden cambiar por varias razones y romperían el mapeo. Por otro lado, sería difícil romper el mapeo a propósito para un usuario específico.

El tipo de “regla de mapeo” predeterminado es 'LDAP', que se puede agregar como prefijo a una regla como, por ejemplo, 'LDAP:(userCertificate;binary={cert!bin})'. Existe una extensión llamada 'LDAPU1' que ofrece más plantillas para mayor flexibilidad. Para permitir que las versiones anteriores de esta biblioteca ignoren la extensión, se debe usar el prefijo 'LDAPU1' al usar las nuevas plantillas en una “regla de mapeo”, de lo contrario, la versión antigua de esta biblioteca fallará con un error de análisis. Las nuevas plantillas se describen en la sección llamada “extensión LDAPU1”.

Las plantillas para agregar datos de certificado al filtro de búsqueda se basan en cadenas de formato de estilo Python. Consisten en una palabra clave entre llaves con un especificador de subcomponente opcional separado por un '.' o una opción de conversión/formato opcional separada por un '!'. Los valores permitidos son:

{issuer_dn[!((ad|ad_x500)|ad_ldap|nss_x500|(nss|nss_ldap))]}

Esta plantilla agregará el DN del emisor completo convertido a una cadena de acuerdo con RFC 4514. Si el orden X.500 (el RDN más específico va al final) se debe usar una opción con el prefijo '_x500'.

Las opciones de conversión que comienzan con 'ad_' usarán nombres de atributos como los utilizados por AD, por ejemplo, 'S' en lugar de 'ST'.

Las opciones de conversión que comienzan con 'nss_' usarán nombres de atributos como los utilizados por NSS.

La opción de conversión predeterminada es 'nss', es decir, nombres de atributos de acuerdo con el orden NSS y LDAP/RFC 4514.

Ejemplo: (ipacertmapdata=X509:<I>{issuer_dn!ad}<S>{subject_dn!ad})

{subject_dn[!((ad|ad_x500)|ad_ldap|nss_x500|(nss|nss_ldap))]}

Esta plantilla agregará el DN del sujeto completo convertido a una cadena de acuerdo con RFC 4514. Si el orden X.500 (el RDN más específico va al final) se debe usar una opción con el prefijo '_x500'.

Las opciones de conversión que comienzan con 'ad_' usarán nombres de atributos como los utilizados por AD, por ejemplo, 'S' en lugar de 'ST'.

Las opciones de conversión que comienzan con 'nss_' usarán nombres de atributos como los utilizados por NSS.

La opción de conversión predeterminada es 'nss', es decir, nombres de atributos de acuerdo con el orden NSS y LDAP/RFC 4514.

Ejemplo: (ipacertmapdata=X509:<I>{issuer_dn!nss_x500}<S>{subject_dn!nss_x500})

{cert[!bin|base64]}

Esta plantilla agregará el certificado completo codificado en DER como una cadena al filtro de búsqueda. Dependiendo de la opción de conversión, el certificado binario se convertirá en una secuencia hexadecimal de escape '\xx' o base64. La secuencia hexadecimal de escape es la predeterminada y se puede usar, por ejemplo, con el atributo LDAP 'userCertificate;binary'.

Ejemplo: (userCertificate;binary={cert!bin})

{subject_principal[.short_name]}

Esta plantilla agregará el principal Kerberos, que se toma del SAN utilizado por pkinit o del utilizado por AD. El componente 'short_name' representa la primera parte del principal antes del signo '@'.

Ejemplo: (|(userPrincipal={subject_principal})(samAccountName={subject_principal.short_name}))

{subject_pkinit_principal[.short_name]}

Esta plantilla agregará el principal Kerberos, que es proporcionado por el SAN utilizado por pkinit. El componente 'short_name' representa la primera parte del principal antes del signo '@'.

Ejemplo: (|(userPrincipal={subject_pkinit_principal})(uid={subject_pkinit_principal.short_name}))

{subject_nt_principal[.short_name]}

Esta plantilla agregará el principal Kerberos, que es proporcionado por el SAN utilizado por AD. El componente 'short_name' representa la primera parte del principal antes del signo '@'.

Ejemplo: (|(userPrincipalName={subject_nt_principal})(samAccountName={subject_nt_principal.short_name}))

{subject_rfc822_name[.short_name]}

Esta plantilla agregará la cadena que se almacena en el componente rfc822Name del SAN, típicamente una dirección de correo electrónico. El componente 'short_name' representa la primera parte de la dirección antes del signo '@'.

Ejemplo: (|(mail={subject_rfc822_name})(uid={subject_rfc822_name.short_name}))

{subject_dns_name[.short_name]}

Esta plantilla agregará la cadena que se almacena en el componente dNSName del SAN, típicamente un nombre de host completamente calificado. El componente 'short_name' representa la primera parte del nombre antes del primer signo '.'.

Ejemplo: (|(fqdn={subject_dns_name})(host={subject_dns_name.short_name}))

{subject_uri}

Esta plantilla agregará la cadena que se almacena en el componente uniformResourceIdentifier del SAN.

Ejemplo: (uri={subject_uri})

{subject_ip_address}

Esta plantilla agregará la cadena que se almacena en el componente iPAddress del SAN.

Ejemplo: (ip={subject_ip_address})

{subject_x400_address}

Esta plantilla agregará el valor que se almacena en el componente x400Address del SAN como una secuencia hexadecimal de escape.

Ejemplo: (attr:binary={subject_x400_address})

{subject_directory_name[!((ad|ad_x500)|ad_ldap|nss_x500|(nss|nss_ldap))]}

Esta plantilla agregará la cadena DN del valor que se almacena en el componente directoryName del SAN.

Ejemplo: (orig_dn={subject_directory_name})

{subject_ediparty_name}

Esta plantilla agregará el valor que se almacena en el componente ediPartyName del SAN como una secuencia hexadecimal de escape.

Ejemplo: (attr:binary={subject_ediparty_name})

{subject_registered_id}

Esta plantilla agregará el OID que se almacena en el componente registeredID del SAN como una cadena decimal con puntos.

Ejemplo: (oid={subject_registered_id})

Extensión LDAPU1

Las siguientes plantillas están disponibles al usar la extensión 'LDAPU1':

{serial_number[!(dec|hex[_ucr])]}

Esta plantilla agregará el número de serie del certificado. Por defecto, se imprimirá como un número hexadecimal con letras minúsculas.

Con la opción de formato '!dec', el número se imprimirá como una cadena decimal. La salida hexadecimal se puede imprimir con letras mayúsculas ('!hex_u'), con dos puntos separando los bytes hexadecimales ('!hex_c') o con los bytes hexadecimales en orden inverso ('!hex_r'). Los sufijos de letras se pueden combinar, de modo que, por ejemplo, '!hex_uc' producirá una cadena hexadecimal separada por dos puntos con letras mayúsculas.

Ejemplo: LDAPU1:(serial={serial_number})

{subject_key_id[!hex[_ucr]]}

Esta plantilla agregará el ID de clave del sujeto del certificado. Por defecto, se imprimirá como un número hexadecimal con letras minúsculas.

La salida hexadecimal se puede imprimir con letras mayúsculas ('!hex_u'), con dos puntos separando los bytes hexadecimales ('!hex_c') o con los bytes hexadecimales en orden inverso ('!hex_r'). Los sufijos de letras se pueden combinar, de modo que, por ejemplo, '!hex_uc' producirá una cadena hexadecimal separada por dos puntos con letras mayúsculas.

Ejemplo: LDAPU1:(ski={subject_key_id})

{cert[!DIGEST[_ucr]]}

Esta plantilla agregará el resumen/hash hexadecimal del certificado, donde DIGEST debe reemplazarse con el nombre de una función de resumen/hash compatible con OpenSSL, por ejemplo, 'sha512'.

La salida hexadecimal se puede imprimir con letras mayúsculas ('!sha512_u'), con dos puntos separando los bytes hexadecimales ('!sha512_c') o con los bytes hexadecimales en orden inverso ('!sha512_r'). Los sufijos de letras se pueden combinar, de modo que, por ejemplo, '!sha512_uc' producirá una cadena hexadecimal separada por dos puntos con letras mayúsculas.

Ejemplo: LDAPU1:(dgst={cert!sha256})

{subject_dn_component[(.attr_name|[number]]}

Esta plantilla agregará un valor de atributo de un componente del DN del sujeto, por defecto el valor del componente más específico.

Se puede seleccionar un componente diferente por nombre de atributo, por ejemplo, {subject_dn_component.uid} o por posición, por ejemplo, {subject_dn_component.[2]}, donde los números positivos comienzan a contar desde el componente más específico y los números negativos comienzan a contar desde el componente menos específico. El nombre del atributo y la posición se pueden combinar, como por ejemplo, {subject_dn_component.uid[2]}, lo que significa que el nombre del segundo componente debe ser 'uid'.

Ejemplo: LDAPU1:(uid={subject_dn_component.uid})

{issuer_dn_component[(.attr_name|[number]]}

Esta plantilla agregará un valor de atributo de un componente del DN del emisor, por defecto el valor del componente más específico.

Ver 'subject_dn_component' para obtener detalles sobre los especificadores de nombre de atributo y posición.

Ejemplo: LDAPU1:(domain=

sss-certmap.5.es — SSSD

NOMBRE

sss-certmap.5 - sssd-certmap.conf(5) configuración de SSSD

DESCRIPCIÓN

El archivo /etc/sssd/sss-certmap.conf contiene la configuración para el mapeo de certificados a usuarios. Actualmente, SSSD soporta el mapeo de certificados de cliente PKI a cuentas de usuario para el backend de autenticación de SSSD. Se puede habilitar y configurar en el archivo sssd.conf(5) bajo la sección [certmap/...].

Los certificados X.509 son una forma común de autenticación criptográfica. SSSD puede ser configurado para autenticar a los usuarios basándose en la información contenida en sus certificados. Esto es especialmente útil en entornos donde los usuarios ya están autenticados con certificados, como en el acceso VPN o a sitios web seguros.

La configuración de sss-certmap es una forma de indicar a SSSD cómo extraer información del certificado y cómo usarla para encontrar un usuario correspondiente en el directorio de autenticación (como LDAP o Active Directory).

COMPONENTES DE REGLA

Las reglas de mapeo de certificados son cadenas que definen cómo extraer información de un certificado. Cada regla se compone de varios componentes, separados por el carácter /.

OTRO FORMATO

Indica si la regla de mapeo se aplica a certificados X.509 estándar o a certificados de S/MIME. El valor puede ser X509 o SMIME.

LUGAR DE ALMACENAMIENTO

Define dónde se almacenará la información extraída del certificado. Puede ser uno de los siguientes:

  • LDAPU: User Principal Name (UPN) para LDAP.
  • LDAPDN: Distinguished Name (DN) para LDAP.
  • LDAP_URI: URI LDAP.

  • OBJECTSID: El SID de Objeto (Object Security Identifier) de Windows. Esta opción puede utilizar varios especificadores:

    • {sid}: Añade el SID de Objeto completo.
    • {rid}: Añade solo el Relative Identifier (RID) del SID.

IDENTIFICADOR DEL EMISOR

El identificador del emisor del certificado. Puede ser un distinguished name (DN) completo o un componente de él, usando especificadores.

Ejemplos de especificadores:

  • {id}: El valor del componente especificado.
  • dc: Domain Component.
  • ou: Organizational Unit.
  • o: Organization.
  • cn: Common Name.

El valor del identificador del emisor se compara con el campo Issuer del certificado.

Ejemplo de componente:

issuer_dn_component.dc

Ejemplo de regla completa:

X509/LDAPDN/issuer_dn_component.o=Example,issuer_dn_component.dc=com

También se pueden usar comodines:

X509/LDAPDN/issuer_dn_component.o=*

Si se usa LDAP_URI como LUGAR_DE_ALMACENAMIENTO, se puede construir una URI LDAP usando el identificador del emisor y el identificador del sujeto.

Ejemplo:

X509/LDAP_URI/ldap://{issuer_dn_component.o={o},issuer_dn_component.dc={dc}}

IDENTIFICADOR DEL SUJETO

El identificador del sujeto del certificado. Similar al identificador del emisor, puede ser un distinguished name (DN) completo o un componente de él, usando especificadores.

Ejemplos de especificadores son los mismos que para el identificador del emisor.

El valor del identificador del sujeto se compara con el campo Subject del certificado.

Ejemplo de componente:

subject_dn_component.cn

Ejemplo de regla completa:

X509/LDAPDN/subject_dn_component.cn

Si se usa LDAP_URI como LUGAR_DE_ALMACENAMIENTO, se puede construir una URI LDAP usando el identificador del emisor y el identificador del sujeto.

Ejemplo:

X509/LDAP_URI/ldap://{issuer_dn_component.o={o},issuer_dn_component.dc={dc}}/{sid}

SID

Este componente se utiliza para añadir el Security Identifier (SID) de un usuario. Si se utiliza el especificador .rid, solo se añadirá el Relative Identifier (RID) del SID.

Esta plantilla añadirá el SID si la extensión correspondiente introducida por Microsoft con el OID 1.3.6.1.4.1.311.25.2 está disponible. Con el selector '.rid', solo se añadirá el último componente, es decir, el RID.

Ejemplo: LDAPU1:(objectsid={sid})

LISTA DE DOMINIOS

Si la lista de dominios no está vacía, los usuarios mapeados a un certificado dado no solo se buscarán en el dominio local, sino también en los dominios listados, siempre que sean conocidos por SSSD. Los dominios no conocidos por SSSD serán ignorados.
