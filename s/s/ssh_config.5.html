SSH_CONFIG(5) Manual de formatos de archivo SSH_CONFIG(5)

NOMBRE

ssh_config — Archivo de configuración del cliente OpenSSH

DESCRIPCIÓN

ssh(1) obtiene datos de configuración de las siguientes fuentes en el siguiente orden:

  1. Opciones de línea de comandos
  2. Archivo de configuración del usuario (~/.ssh/config)
  3. Archivo de configuración a nivel de sistema (/etc/ssh/ssh_config)

A menos que se indique lo contrario, para cada parámetro, se utilizará el primer valor obtenido. Los archivos de configuración contienen secciones separadas por especificaciones Host, y esa sección solo se aplicará a los hosts que coincidan con uno de los patrones dados en la especificación. El nombre de host coincidente suele ser el proporcionado en la línea de comandos (ver la opción CanonicalizeHostname para excepciones).

Dado que se utiliza el primer valor obtenido para cada parámetro, las declaraciones más específicas del host deben aparecer cerca del principio del archivo y los valores predeterminados generales al final.

El archivo contiene pares de palabra clave y argumento, uno por línea. Las líneas que comienzan con ‘#’ y las líneas vacías se interpretan como comentarios. Los argumentos se pueden encerrar opcionalmente entre comillas dobles (") para representar argumentos que contienen espacios. Las opciones de configuración se pueden separar por espacios en blanco o por espacios en blanco opcionales y exactamente un ‘=’; el último formato es útil para evitar la necesidad de citar espacios en blanco al especificar opciones de configuración utilizando la opción -o de ssh, scp y sftp.

Las palabras clave posibles y sus significados son los siguientes (tenga en cuenta que las palabras clave no distinguen entre mayúsculas y minúsculas y los argumentos sí):

Host
Restringe las siguientes declaraciones (hasta la siguiente palabra clave Host o Match) a aplicarse solo a aquellos hosts que coincidan con uno de los patrones dados después de la palabra clave. Si se proporcionan varios patrones, deben separarse por espacios en blanco. Se puede usar un solo ‘*’ como patrón para proporcionar valores predeterminados globales para todos los hosts. El host suele ser el argumento nombre de host dado en la línea de comandos (ver la palabra clave CanonicalizeHostname para excepciones).

Una entrada de patrón puede ser negada prefijándola con un signo de exclamación (‘!’). Si se coincide con una entrada negada, se ignora la entrada Host, independientemente de si coinciden otros patrones en la línea. Por lo tanto, las coincidencias negadas son útiles para proporcionar excepciones a las coincidencias comodín.

Consulte PATTERNS para obtener más información sobre los patrones.

Match
Restringe las siguientes declaraciones (hasta la siguiente palabra clave Host o Match) a usarse solo cuando se cumplen las condiciones posteriores a la palabra clave Match. Las condiciones de coincidencia se especifican usando uno o más criterios o el token único all, que siempre coincide. Las palabras clave de criterio disponibles son: canonical, final, exec, localnetwork, host, originalhost, tagged, command, user, localuser y version. El criterio all debe aparecer solo o inmediatamente después de canonical o final. Otros criterios se pueden combinar arbitrariamente. Todos los criterios excepto all, canonical y final requieren un argumento. Los criterios pueden ser negados anteponiendo un signo de exclamación (‘!’).

La palabra clave canonical coincide solo cuando el archivo de configuración se está volviendo a analizar después de la canonización del nombre de host (ver la opción CanonicalizeHostname). Esto puede ser útil para especificar condiciones que funcionen solo con nombres de host canónicos.

La palabra clave final solicita que el archivo de configuración se vuelva a analizar (independientemente de si CanonicalizeHostname está habilitado) y coincide solo durante este pase final. Si CanonicalizeHostname está habilitado, entonces canonical y final coinciden durante el mismo pase.

La palabra clave exec ejecuta el comando especificado bajo el shell del usuario. Si el comando devuelve un estado de salida cero, la condición se considera verdadera. Los comandos que contienen caracteres de espacio en blanco deben entrecomillarse. Los argumentos para exec aceptan los tokens descritos en la sección TOKENS.

La palabra clave localnetwork coincide con las direcciones de las interfaces de red locales activas contra la lista proporcionada de redes en formato CIDR. Esto puede ser conveniente para variar la configuración efectiva en dispositivos que se desplazan entre redes. Tenga en cuenta que la dirección de red no es un criterio confiable en muchas situaciones (por ejemplo, cuando la red se configura automáticamente usando DHCP) y, por lo tanto, se debe tener precaución si se usa para controlar la configuración sensible a la seguridad.

Los criterios de las otras palabras clave deben ser entradas únicas o listas separadas por comas y pueden usar los operadores comodín y de negación descritos en la sección PATTERNS.

Los criterios para la palabra clave host se comparan con el nombre de host de destino, después de cualquier sustitución por las opciones Hostname o CanonicalizeHostname. La palabra clave originalhost coincide con el nombre de host tal como se especificó en la línea de comandos.

La palabra clave tagged coincide con un nombre de etiqueta especificado por una directiva previa Tag o en la línea de comandos de ssh(1) usando el indicador -P. La palabra clave command coincide con el comando remoto solicitado, o el nombre del subsistema que se está invocando (por ejemplo, "sftp" para una sesión SFTP). La cadena vacía coincidirá con el caso en que no se haya especificado un comando o una etiqueta, es decir, ‘Match tag ""’. La palabra clave version coincide con la cadena de versión de ssh(1), por ejemplo, “OpenSSH_10.0”.

La palabra clave user coincide con el nombre de usuario de destino en el host remoto. La palabra clave localuser coincide con el nombre del usuario local que ejecuta ssh(1) (esta palabra clave puede ser útil en archivos ssh_config a nivel de sistema).

Finalmente, la palabra clave sessiontype coincide con el tipo de sesión solicitada, que puede ser shell para sesiones interactivas, exec para sesiones de ejecución de comandos, subsystem para invocaciones de subsistemas como sftp(1), o none para sesiones solo de transporte, como cuando ssh(1) se inicia con el indicador -N.

AgentForwarding
Specifies whether user authentication via the ssh-agent(1) protocol is enabled. The default is no. If set to yes, ssh(1) will forward the connection to the authentication agent running on the local machine to the remote machine. This allows authentication using keys managed by the agent on the remote machine.

If the AgentForwarding option is set to ask, ssh(1) will require confirmation using the SSH_ASKPASS program before adding a key (see ssh-add(1) for details). If this option is set to confirm, each use of the key must be confirmed, as if the -c option was specified to ssh-add(1). If this option is set to no, no keys are added to the agent. Alternately, this option may be specified as a time interval using the format described in the TIME FORMATS section of sshd_config(5) to specify the key's lifetime in ssh-agent(1), after which it will automatically be removed. The argument must be no (the default), yes, confirm (optionally followed by a time interval), ask or a time interval.

AddressFamily
Specifies which address family to use when connecting. Valid arguments are any (the default), inet (use IPv4 only), or inet6 (use IPv6 only).
BatchMode
If set to yes, user interaction such as password prompts and host key confirmation requests will be disabled. This option is useful in scripts and other batch jobs where no user is present to interact with ssh(1). The argument must be yes or no (the default).
BindAddress
Use the specified address on the local machine as the source address of the connection. Only useful on systems with more than one address.
BindInterface
Use the address of the specified interface on the local machine as the source address of the connection.
CanonicalDomains
When CanonicalizeHostname is enabled, this option specifies the list of domain suffixes in which to search for the specified destination host.
CanonicalizeFallbackLocal
Specifies whether to fail with an error when hostname canonicalization fails. The default, yes, will attempt to look up the unqualified hostname using the system resolver's search rules. A value of no will cause ssh(1) to fail instantly if CanonicalizeHostname is enabled and the target hostname cannot be found in any of the domains specified by CanonicalDomains.
CanonicalizeHostname
Controls whether explicit hostname canonicalization is performed. The default, no, is not to perform any name rewriting and let the system resolver handle all hostname lookups. If set to yes then, for connections that do not use a ProxyCommand or ProxyJump, ssh(1) will attempt to canonicalize the hostname specified on the command line using the CanonicalDomains suffixes and CanonicalizePermittedCNAMEs rules. If CanonicalizeHostname is set to always, then canonicalization is applied to proxied connections too.

If this option is enabled, then the configuration files are processed again using the new target name to pick up any new configuration in matching Host and Match stanzas. A value of none disables the use of a ProxyJump host.

CanonicalizeMaxDots
Specifies the maximum number of dot characters in a hostname before canonicalization is disabled. The default, 1, allows a single dot (i.e. hostname.subdomain).
CanonicalizePermittedCNAMEs
Specifies rules to determine whether CNAMEs should be followed when canonicalizing hostnames. The rules consist of one or more arguments of source_domain_list:target_domain_list, where source_domain_list is a pattern-list of domains that may follow CNAMEs in canonicalization, and target_domain_list is a pattern-list of domains that they may resolve to.

For example, "*.a.example.com:*.b.example.com,*.c.example.com" will allow hostnames matching "*.a.example.com" to be canonicalized to names in the "*.b.example.com" or "*.c.example.com" domains.

A single argument of "none" causes no CNAMEs to be considered for canonicalization. This is the default behaviour.

CASignatureAlgorithms
Specifies which algorithms are allowed for signing of certificates by certificate authorities (CAs). The default is: 
ssh-ed25519,ecdsa-sha2-nistp256,
ecdsa-sha2-nistp384,ecdsa-sha2-nistp521,
sk-ssh-ed25519@openssh.com,
sk-ecdsa-sha2-nistp256@openssh.com,
rsa-sha2-512,rsa-sha2-256

If the specified list begins with a ‘+’ character, then the specified algorithms will be appended to the default set instead of replacing them. If the specified list begins with a ‘-’ character, then the specified algorithms (including wildcards) will be removed from the default set instead of replacing them.

ssh(1) will not accept host certificates signed using algorithms other than those specified.

CertificateFile
Specifies a file from which the user's certificate is read. A corresponding private key must be provided separately in order to use this certificate either from an IdentityFile directive or -i flag to ssh(1), via ssh-agent(1), or via a PKCS11Provider or SecurityKeyProvider.

Arguments to CertificateFile may use the tilde syntax to refer to a user's home directory, the tokens described in the TOKENS section and environment variables as described in the ENVIRONMENT VARIABLES section.

It is possible to have multiple certificate files specified in configuration files; these certificates will be tried in sequence. Multiple CertificateFile directives will add to the list of certificates used for authentication.

ChannelTimeout
Specifies whether and how quickly ssh(1) should close inactive channels. Timeouts are specified as one or more “type=interval” pairs separated by whitespace, where the “type” must be the special keyword “global” or a channel type name from the list below, optionally containing wildcard characters.

The timeout value “interval” is specified in seconds or may use any of the units documented in the TIME FORMATS section. For example, “session=5m” would cause interactive sessions to terminate after five minutes of inactivity. Specifying a zero value disables the inactivity timeout.

The special timeout “global” applies to all active channels, taken together. Traffic on any active channel will reset the timeout, but when the timeout expires then all open channels will be closed. Note that this global timeout is not matched by wildcards and must be specified explicitly.

The available channel type names include:

agent-connection
Open connections to ssh-agent(1).
direct-tcpip, direct-streamlocal@openssh.com
Open TCP or Unix socket (respectively) connections that have been established from an ssh(1) local forwarding, i.e. LocalForward or DynamicForward.
forwarded-tcpip, forwarded-streamlocal@openssh.com
Open TCP or Unix socket (respectively) connections that have been established to an sshd(8) listening on behalf of an ssh(1) remote forwarding, i.e. RemoteForward.
session
The interactive main session, including shell session, command execution, scp(1), sftp(1), etc.
tun-connection
Open TunnelForward connections.
x11-connection
Open X11 forwarding sessions.

Note that in all the above cases, termi

una sesión inactiva no garantiza la eliminación de todos los recursos asociados con la sesión; por ejemplo, los procesos de shell o los clientes X11 relacionados con la sesión pueden seguir ejecutándose.

Además, terminar un canal o sesión inactiva no cierra necesariamente la conexión SSH, ni impide que un cliente solicite otro canal del mismo tipo. En particular, expirar una sesión de reenvío inactiva no impide que se cree posteriormente otro reenvío idéntico.

El valor predeterminado es no expirar canales de ningún tipo por inactividad.

CheckHostIP
Si se establece en yes, ssh(1) verificará adicionalmente la dirección IP del host en el archivo known_hosts. Esto permite detectar si una clave de host cambió debido a un suplantación de DNS y agregará direcciones de hosts de destino a ~/.ssh/known_hosts en el proceso, independientemente de la configuración de StrictHostKeyChecking. Si la opción se establece en no (el valor predeterminado), la verificación no se ejecutará.
Ciphers
Especifica los cifrados permitidos y su orden de preferencia. Múltiples cifrados deben estar separados por comas. Si la lista especificada comienza con un carácter ‘+’, los cifrados especificados se agregarán al conjunto predeterminado en lugar de reemplazarlo. Si la lista especificada comienza con un carácter ‘-’, los cifrados especificados (incluidos los comodines) se eliminarán del conjunto predeterminado en lugar de reemplazarlo. Si la lista especificada comienza con un carácter ‘^’, los cifrados especificados se colocarán al principio del conjunto predeterminado.

Los cifrados admitidos son:

3des-cbc
aes128-cbc
aes192-cbc
aes256-cbc
aes128-ctr
aes192-ctr
aes256-ctr
aes128-gcm@openssh.com
aes256-gcm@openssh.com
chacha20-poly1305@openssh.com

El valor predeterminado es:

chacha20-poly1305@openssh.com,
aes128-gcm@openssh.com,aes256-gcm@openssh.com,
aes128-ctr,aes192-ctr,aes256-ctr

La lista de cifrados disponibles también se puede obtener usando "ssh -Q cipher".

ClearAllForwardings
Especifica que se deben borrar todos los reenvíos de puertos locales, remotos y dinámicos especificados en los archivos de configuración o en la línea de comandos. Esta opción es principalmente útil cuando se usa desde la línea de comandos de ssh(1) para borrar los reenvíos de puertos establecidos en los archivos de configuración, y es establecida automáticamente por scp(1) y sftp(1). El argumento debe ser yes o no (el valor predeterminado).
Compression
Especifica si se debe usar compresión. El argumento debe ser yes o no (el valor predeterminado).
ConnectionAttempts
Especifica el número de intentos (uno por segundo) a realizar antes de salir. El argumento debe ser un entero. Esto puede ser útil en scripts si la conexión falla ocasionalmente. El valor predeterminado es 1.
ConnectTimeout
Especifica el tiempo de espera (en segundos) utilizado al conectarse al servidor SSH, en lugar de utilizar el tiempo de espera TCP predeterminado del sistema. Este tiempo de espera se aplica tanto a la establecimiento de la conexión como a la realización del protocolo SSH inicial, el handshake y el intercambio de claves.
ControlMaster
Habilita el uso compartido de múltiples sesiones a través de una única conexión de red. Cuando se establece en yes, ssh(1) escuchará las conexiones en un socket de control especificado usando el argumento ControlPath. Las sesiones adicionales pueden conectarse a este socket usando el mismo ControlPath con ControlMaster establecido en no (el valor predeterminado). Estas sesiones intentarán reutilizar la conexión de red de la instancia maestra en lugar de iniciar nuevas, pero recurrirán a la conexión normal si el socket de control no existe o no está escuchando.

Establecer esto en ask hará que ssh(1) escuche las conexiones de control, pero requerirá confirmación usando ssh-askpass(1). Si no se puede abrir el ControlPath, ssh(1) continuará sin conectarse a una instancia maestra.

Se admite el reenvío de X11 y ssh-agent(1) a través de estas conexiones multiplexadas; sin embargo, la pantalla y el agente reenviados serán los que pertenecen a la conexión maestra, es decir, no es posible reenviar múltiples pantallas o agentes.

Dos opciones adicionales permiten la multiplexación oportunista: intentar usar una conexión maestra pero recurrir a crear una nueva si no existe. Estas opciones son: auto y autoask. La segunda requiere confirmación como la opción ask.

ControlPath
Especifica la ruta al socket de control utilizado para compartir conexiones, como se describe en la sección ControlMaster anterior, o la cadena none para deshabilitar el uso compartido de conexiones. Los argumentos de ControlPath pueden usar la sintaxis de tilde para referirse al directorio de inicio de un usuario, los tokens descritos en la sección TOKENS y las variables de entorno como se describe en la sección ENVIRONMENT VARIABLES. Se recomienda que cualquier ControlPath utilizado para compartir conexiones oportunistas incluya al menos %h, %p y %r (o alternativamente %C) y se coloque en un directorio que no sea escribible por otros usuarios. Esto asegura que las conexiones compartidas se identifiquen de forma única.
ControlPersist
Cuando se usa junto con ControlMaster, especifica que la conexión maestra debe permanecer abierta en segundo plano (esperando futuras conexiones de clientes) después de que la conexión de cliente inicial se haya cerrado. Si se establece en no (el valor predeterminado), la conexión maestra no se colocará en segundo plano y se cerrará tan pronto como se cierre la conexión de cliente inicial. Si se establece en yes o 0, la conexión maestra permanecerá en segundo plano indefinidamente (hasta que se mate o se cierre mediante un mecanismo como el "ssh -O exit"). Si se establece en un tiempo en segundos, o en un tiempo en cualquiera de los formatos documentados en sshd_config(5), la conexión maestra en segundo plano se terminará automáticamente después de que haya permanecido inactiva (sin conexiones de clientes) durante el tiempo especificado.
DynamicForward
Especifica que un puerto TCP en la máquina local se reenviará a través del canal seguro, y el protocolo de la aplicación se utilizará para determinar a dónde conectarse desde la máquina remota.

El argumento debe ser [bind_address:]port. Las direcciones IPv6 se pueden especificar encerrando las direcciones entre corchetes. Por defecto, el puerto local se enlaza de acuerdo con la configuración de GatewayPorts. Sin embargo, se puede usar una bind_address explícita para enlazar la conexión a una dirección específica. La bind_address de localhost indica que el puerto de escucha debe ser solo para uso local, mientras que una dirección vacía o ‘*’ indica que el puerto debe estar disponible desde todas las interfaces.

Actualmente se admiten los protocolos SOCKS4 y SOCKS5, y ssh(1) actuará como un servidor SOCKS. Se pueden especificar múltiples reenvíos, y se pueden proporcionar reenvíos adicionales en la línea de comandos. Solo el superusuario puede reenviar puertos privilegiados.

EnableEscapeCommandline
Habilita la opción de línea de comandos en el menú EscapeChar para sesiones interactivas (por defecto ‘~C’). Por defecto, la línea de comandos está deshabilitada.
EnableSSHKeysign
Establecer esta opción en yes en el archivo de configuración global del cliente /etc/ssh/ssh_config habilita el uso del programa auxiliar ssh-keysign(8) durante HostbasedAuthentication. El argumento debe ser yes o no (el valor predeterminado). Esta opción debe colocarse en la sección no específica del host. Consulte ssh-keysign(8) para obtener más información.
EscapeChar
Establece el carácter de escape (predeterminado: ‘~’). El carácter de escape también se puede establecer en la línea de comandos. El argumento debe ser un solo carácter, ‘^’ seguido de una letra, o none para deshabilitar completamente el carácter de escape (haciendo la conexión transparente para datos binarios).
ExitOnForwardFailure
Especifica si ssh(1) debe terminar la conexión si no puede establecer todos los reenvíos de puertos dinámicos, de túnel, locales y remotos solicitados (por ejemplo, si uno de los extremos no puede enlazar y escuchar en un puerto especificado). Tenga en cuenta que ExitOnForwardFailure no se aplica a las conexiones realizadas a través de reenvíos de puertos y no,
por ejemplo, cause ssh(1) a salir si las conexiones TCP al destino final del reenvío fallan. El argumento debe ser yes o no (el valor por defecto).
FingerprintHash
Especifica el algoritmo de hash utilizado al mostrar las huellas dactilares de las claves. Las opciones válidas son: md5 y sha256 (el valor por defecto).
ForkAfterAuthentication
Solicita a ssh que se ponga en segundo plano justo antes de ejecutar un comando. Esto es útil si ssh va a pedir contraseñas o frases de contraseña, pero el usuario quiere que se ejecute en segundo plano. Esto implica que la opción de configuración StdinNull esté establecida a "yes". La forma recomendada de iniciar programas X11 en un sitio remoto es con algo como ssh -f host xterm, que es lo mismo que ssh host xterm si la opción de configuración ForkAfterAuthentication está establecida a "yes".

Si la opción de configuración ExitOnForwardFailure está establecida a "yes", entonces un cliente iniciado con la opción de configuración ForkAfterAuthentication establecida a "yes" esperará a que todos los reenvíos de puertos remotos se establezcan correctamente antes de ponerse en segundo plano. El argumento para esta palabra clave debe ser yes (igual que la opción -f) o no (el valor por defecto).

ForwardAgent
Especifica si la conexión al agente de autenticación (si existe) se reenviará a la máquina remota. El argumento puede ser yes, no (el valor por defecto), una ruta explícita a un socket de agente o el nombre de una variable de entorno (que comience con '$') en la que encontrar la ruta.

El reenvío de agente debe habilitarse con precaución. Los usuarios con la capacidad de omitir los permisos de archivo en el host remoto (para el socket del dominio Unix del agente) pueden acceder al agente local a través de la conexión reenviada. Un atacante no puede obtener material de clave del agente, sin embargo, pueden realizar operaciones sobre las claves que les permitan autenticarse utilizando las identidades cargadas en el agente.

ForwardX11
Especifica si las conexiones X11 se redirigirán automáticamente a través del canal seguro y se establecerá la variable DISPLAY. El argumento debe ser yes o no (el valor por defecto).

El reenvío X11 debe habilitarse con precaución. Los usuarios con la capacidad de omitir los permisos de archivo en el host remoto (para la base de datos de autorización X11 del usuario) pueden acceder a la pantalla X11 local a través de la conexión reenviada. Un atacante podría entonces ser capaz de realizar actividades como la monitorización de pulsaciones de teclas si la opción ForwardX11Trusted también está habilitada.

ForwardX11Timeout
Especifica un tiempo de espera para el reenvío X11 no confiable utilizando el formato descrito en la sección FORMATOS DE TIEMPO de sshd_config(5). Las conexiones X11 recibidas por ssh(1) después de este tiempo serán rechazadas. Establecer ForwardX11Timeout a cero deshabilitará el tiempo de espera y permitirá el reenvío X11 durante la vida de la conexión. El valor por defecto es deshabilitar el reenvío X11 no confiable después de que hayan transcurrido veinte minutos.
ForwardX11Trusted
Si esta opción se establece en yes, los clientes X11 remotos tendrán acceso completo a la pantalla X11 original.

Si esta opción se establece en no (el valor por defecto), los clientes X11 remotos se considerarán no confiables y se les impedirá robar o manipular datos pertenecientes a clientes X11 confiables. Además, el token xauth(1) utilizado para la sesión se establecerá para que expire después de 20 minutos. Se denegará el acceso a los clientes remotos después de este tiempo.

Consulte la especificación de la extensión X11 SECURITY para obtener detalles completos sobre las restricciones impuestas a los clientes no confiables.

GatewayPorts
Especifica si se permite a los hosts remotos conectarse a puertos reenviados locales. Por defecto, ssh(1) enlaza los reenvíos de puertos locales a la dirección de loopback. Esto evita que otros hosts remotos se conecten a los puertos reenviados. GatewayPorts se puede usar para especificar que ssh debe enlazar los reenvíos de puertos locales a la dirección comodín, permitiendo así que los hosts remotos se conecten a los puertos reenviados. El argumento debe ser yes o no (el valor por defecto).
GlobalKnownHostsFile
Especifica uno o más archivos para usar para la base de datos global de claves de host, separados por espacios en blanco. El valor por defecto es /etc/ssh/ssh_known_hosts, /etc/ssh/ssh_known_hosts2.
GSSAPIAuthentication
Especifica si se permite la autenticación de usuario basada en GSSAPI. El valor por defecto es no.
GSSAPIDelegateCredentials
Reenvía (delegan) credenciales al servidor. El valor por defecto es no.
HashKnownHosts
Indica que ssh(1) debe hashear los nombres de host y direcciones cuando se agregan a ~/.ssh/known_hosts. Estos nombres hasheados pueden ser usados normalmente por ssh(1) y sshd(8), pero no revelan visualmente información identificativa si el contenido del archivo se divulga. El valor por defecto es no. Tenga en cuenta que los nombres y direcciones existentes en los archivos known hosts no se convertirán automáticamente, pero pueden hashearse manualmente usando ssh-keygen(1).
HostbasedAcceptedAlgorithms
Especifica los algoritmos de firma que se utilizarán para la autenticación basada en host como una lista de patrones separada por comas. Alternativamente, si la lista especificada comienza con un carácter '+', entonces los algoritmos de firma especificados se añadirán al conjunto por defecto en lugar de reemplazarlo. Si la lista especificada comienza con un carácter '-', entonces los algoritmos de firma especificados (incluidos los comodines) se eliminarán del conjunto por defecto en lugar de reemplazarlo. ProxyCommand
Allows you to specify a remote command to use for the connection. This can be used to connect to hosts that are not directly reachable from your local host, or to filter connections to the host. If this option is specified, ssh will execute the command in the argument instead of trying to connect directly to the destination. The command's standard input and output must be connected to the ssh client and server. Arguments to ProxyCommand accept the tokens described in the TOKENS section. If the command is found in the user's PATH, it will be run directly. If the command is not found in the user's PATH, ssh will assume that the command is a binary to be executed with nc.

The default command is:

nc %h %p

The default ProxyCommand can be overridden by specifying the ProxyCommand option in the configuration file, or via the ProxyCommand command-line option.

When using ProxyCommand, you may want to protect against command injection by using nc -Q proxy_protocol instead of passing arbitrary arguments to nc directly.

Example:

ProxyCommand /usr/bin/nc -X connect -x 192.0.2.0:8080 %h %p
ProxyJump
Specifies one or more jump proxies as either [user@]host[:port] or an ssh URI. Multiple proxies may be separated by comma characters and will be visited sequentially. Setting this option will cause ssh(1) to connect to the target host by first making an ssh(1) connection to the specified ProxyJump host and then establishing a TCP forwarding to the ultimate target from there. Setting the host to none disables this option entirely.

Note that this option will compete with the ProxyCommand option - whichever is specified first will prevent later instances of the other from taking effect.

Note also that the configuration for the destination host (either supplied via the command-line or the configuration file) is not generally applied to jump hosts. ~/.ssh/config should be used if specific configuration is required for jump hosts.

The remote port may either be forwarded to a specified host and port or Unix-domain socket from the local machine, or may act as a SOCKS 4/5 proxy that allows a remote client to connect to arbitrary destinations from the local machine. The first argument is the listening specification and may be [bind_address:]port or, if the remote host supports it, a Unix domain socket path. al es solicitado ya que es requerido por el protocolo. Consulte AcceptEnv en sshd_config(5) para ver cómo configurar el servidor. Las variables se especifican por nombre, que puede contener caracteres comodín. Múltiples variables de entorno pueden estar separadas por espacios en blanco o distribuidas en varias directivas SendEnv.

Vea PATTERNS para más información sobre patrones.

Es posible borrar nombres de variables de SendEnv previamente establecidos prefijando los patrones con -. El valor predeterminado es no enviar ninguna variable de entorno.

ServerAliveCountMax
Establece el número de mensajes de "server alive" (ver abajo) que pueden enviarse sin que ssh(1) reciba ningún mensaje de vuelta del servidor. Si se alcanza este umbral mientras se envían mensajes de "server alive", ssh se desconectará del servidor, terminando la sesión. Es importante notar que el uso de mensajes de "server alive" es muy diferente de TCPKeepAlive (abajo). Los mensajes de "server alive" se envían a través del canal encriptado y, por lo tanto, no podrán ser falsificados. La opción de "keepalive" de TCP habilitada por TCPKeepAlive sí puede ser falsificada. El mecanismo de "server alive" es valioso cuando el cliente o el servidor dependen de saber cuándo una conexión se ha vuelto no responsiva.

El valor predeterminado es 3. Si, por ejemplo, ServerAliveInterval (ver abajo) se establece en 15 y ServerAliveCountMax se deja en el valor predeterminado, si el servidor deja de responder, ssh se desconectará después de aproximadamente 45 segundos.

ServerAliveInterval
Establece un intervalo de tiempo de espera en segundos después del cual, si no se ha recibido ningún dato del servidor, ssh(1) enviará un mensaje a través del canal encriptado para solicitar una respuesta del servidor. El valor predeterminado es 0, lo que indica que estos mensajes no se enviarán al servidor.
SessionType
Puede usarse para solicitar la invocación de un subsistema en el sistema remoto, o para evitar la ejecución de un comando remoto en absoluto. Esto último es útil solo para reenviar puertos. El argumento de esta palabra clave debe ser none (igual que la opción -N), subsystem (igual que la opción -s) o default (ejecución de shell o comando).
SetEnv
Especifica directamente una o más variables de entorno y sus contenidos para ser enviados al servidor en el formato "NOMBRE=VALOR". Similar a SendEnv, con la excepción de la variable TERM, el servidor debe estar preparado para aceptar la variable de entorno.

El "VALOR" puede usar los tokens descritos en la sección TOKENS y las variables de entorno como se describe en la sección ENVIRONMENT VARIABLES.

StdinNull
Redirige stdin desde /dev/null (de hecho, previene la lectura desde stdin). Cualquiera de estas o la opción equivalente -n debe usarse cuando ssh se ejecuta en segundo plano. El argumento de esta palabra clave debe ser yes (igual que la opción -n) o no (el valor predeterminado).
StreamLocalBindMask
Establece la máscara de modo de creación de archivo octal (umask) que se utiliza al crear un archivo de socket de dominio Unix para el reenvío de puertos local o remoto. Esta opción solo se usa para el reenvío de puertos a un archivo de socket de dominio Unix.

El valor predeterminado es 0177, que crea un archivo de socket de dominio Unix que es legible y escribible solo por el propietario. Tenga en cuenta que no todos los sistemas operativos respetan el modo de archivo en los archivos de socket de dominio Unix.

StreamLocalBindUnlink
Especifica si se debe eliminar un archivo de socket de dominio Unix existente para el reenvío de puertos local o remoto antes de crear uno nuevo. Si el archivo de socket ya existe y StreamLocalBindUnlink no está habilitado, ssh no podrá reenviar el puerto al archivo de socket de dominio Unix. Esta opción solo se usa para el reenvío de puertos a un archivo de socket de dominio Unix.

El argumento debe ser yes o no (el valor predeterminado).

StrictHostKeyChecking
Si esta bandera se establece en yes, ssh(1) nunca agregará automáticamente claves de host al archivo ~/.ssh/known_hosts, y se negará a conectarse a hosts cuya clave de host haya cambiado. Esto proporciona la máxima protección contra ataques de hombre en el medio (MITM), aunque puede ser molesto cuando el archivo /etc/ssh/ssh_known_hosts está mal mantenido o cuando se establecen conexiones a hosts nuevos con frecuencia. Esta opción obliga al usuario a agregar manualmente todos los hosts nuevos.

Si esta bandera se establece en accept-new, ssh agregará automáticamente nuevas claves de host al archivo known_hosts del usuario, pero no permitirá conexiones a hosts con claves de host cambiadas. Si esta bandera se establece en no o off, ssh agregará automáticamente nuevas claves de host a los archivos de hosts conocidos del usuario y permitirá que las conexiones a hosts con claves de host cambiadas continúen, sujeto a algunas restricciones. Si esta bandera se establece en ask (el valor predeterminado), las nuevas claves de host se agregarán a los archivos de hosts conocidos del usuario solo después de que el usuario haya confirmado que eso es lo que realmente quiere hacer, y ssh se negará a conectarse a hosts cuya clave de host haya cambiado. Las claves de host de los hosts conocidos se verificarán automáticamente en todos los casos.

SyslogFacility
Proporciona el código de instalación que se utiliza al registrar mensajes de ssh(1). Los valores posibles son: DAEMON, USER, AUTH, LOCAL0, LOCAL1, LOCAL2, LOCAL3, LOCAL4, LOCAL5, LOCAL6, LOCAL7. El valor predeterminado es USER.
TCPKeepAlive
Especifica si el sistema debe enviar mensajes TCP keepalive al otro lado. Si se envían, la muerte de la conexión o el fallo de una de las máquinas se notará correctamente. Sin embargo, esto significa que las conexiones morirán si la ruta está caída temporalmente, y a algunas personas les resulta molesto.

El valor predeterminado es yes (para enviar mensajes TCP keepalive), y el cliente notará si la red se cae o si el host remoto muere. Esto es importante en los scripts, y muchos usuarios también lo quieren.

Para deshabilitar los mensajes TCP keepalive, el valor debe establecerse en no. Vea también ServerAliveInterval para los keepalives a nivel de protocolo.

Tag
Especifica un nombre de etiqueta de configuración que puede ser utilizado posteriormente por una directiva Match para seleccionar un bloque de configuración.
Tunnel
Solicita el reenvío del dispositivo tun(4) entre el cliente y el servidor. El argumento debe ser yes, point-to-point (capa 3), ethernet (capa 2), o no (el valor predeterminado). Especificar yes solicita el modo de túnel predeterminado, que es point-to-point.
TunnelDevice
Especifica los dispositivos tun(4) a abrir en el cliente (local_tun) y el servidor (remote_tun).

El argumento debe ser local_tun[:remote_tun]. Los dispositivos pueden especificarse por ID numérico o la palabra clave any, que utiliza el siguiente dispositivo de túnel disponible. Si remote_tun no se especifica, se predetermina a any. El valor predeterminado es any:any.

UpdateHostKeys
Especifica si ssh(1) debe aceptar notificaciones de claves de host adicionales del servidor enviadas después de que la autenticación se haya completado y agregarlas a UserKnownHostsFile. El argumento debe ser yes, no o ask. Esta opción permite aprender claves de host alternativas para un servidor y admite la rotación de claves sin problemas al permitir que un servidor envíe claves públicas de reemplazo antes de que se eliminen las antiguas.

Las claves de host adicionales solo se aceptan si la clave utilizada para autenticar el host ya era de confianza o fue aceptada explícitamente por el usuario, el host fue autenticado a través de UserKnownHostsFile (es decir, no GlobalKnownHostsFile) y el host fue autenticado utilizando una clave simple y no un certificado.

UpdateHostKeys está habilitado por defecto si el usuario no ha anulado la configuración predeterminada de UserKnownHostsFile y no ha habilitado VerifyHostKeyDNS; de lo contrario, UpdateHostKeys se establecerá en no.

Si UpdateHostKeys se establece en ask, se le pedirá al usuario que confirme las modificaciones en el archivo known_hosts. La confirmación es actualmente incompatible con ControlPersist y se deshabilitará si está habilitada.

Actualmente, solo sshd(8) de OpenSSH 6.8 y posteriores soportan la extensión de protocolo "hostkeys@openssh.com" utilizada para informar al cliente de todas las claves de host del servidor.

User
Especifica el usuario con el que iniciar sesión. Esto puede ser útil cuando se utiliza un nombre de usuario diferente en distintas máquinas. Esto evita tener que recordar proporcionar el nombre de usuario en la línea de comandos. Los argumentos para User pueden usar los tokens descritos en la sección TOKENS (con la excepción de %r y %C) y las variables de entorno, como se describe en la sección VARIABLES DE ENTORNO.
UserKnownHostsFile
Especifica uno o más archivos para usar para la base de datos de claves de host del usuario, separados por espacios en blanco. Cada nombre de archivo puede usar la notación de tilde para referirse al directorio principal del usuario, los tokens descritos en la sección TOKENS y las variables de entorno como se describe en la sección VARIABLES DE ENTORNO. Un valor de none hace que ssh(1) ignore los archivos de hosts conocidos específicos del usuario. El valor predeterminado es ~/.ssh/known_hosts, ~/.ssh/known_hosts2.
VerifyHostKeyDNS
Especifica si se debe verificar la clave remota usando DNS y registros de recursos SSHFP. Si esta opción se establece en yes, el cliente confiará implícitamente en las claves que coincidan con una huella digital segura de DNS. Las huellas digitales inseguras se manejarán como si esta opción se hubiera establecido en ask. Si esta opción se establece en ask, se mostrará información sobre la coincidencia de la huella digital, pero el usuario aún deberá confirmar las nuevas claves de host de acuerdo con la opción StrictHostKeyChecking. El valor predeterminado es no.

Vea también VERIFICACIÓN DE CLAVES DE HOST en ssh(1).

VersionAddendum
Opcionalmente, especifica texto adicional para añadir al banner del protocolo SSH enviado por el cliente al conectarse. El valor predeterminado es none.
VisualHostKey
Si esta bandera se establece en yes, una representación en arte ASCII de la huella digital de la clave de host remota se imprimirá además de la cadena de huella digital al iniciar sesión y para claves de host desconocidas. Si esta bandera se establece en no (predeterminado), no se imprimirán cadenas de huellas digitales al iniciar sesión y solo se imprimirá la cadena de huella digital para claves de host desconocidas.
WarnWeakCrypto
controla si se advierte al usuario cuando los algoritmos criptográficos negociados para la conexión son débiles o se desaconsejan por otras razones. Las advertencias pueden deshabilitarse desactivando una advertencia específica o deshabilitando todas las advertencias. Las advertencias sobre conexiones que no usan un intercambio de claves post-cuántico pueden deshabilitarse usando la bandera no-pq-kex. no deshabilitará todas las advertencias. El valor predeterminado, equivalente a yes, es habilitar todas las advertencias.
XAuthLocation
Especifica la ruta completa del programa xauth(1). El valor predeterminado es /usr/bin/xauth.

PATRONES

Un patrón consiste en cero o más caracteres que no sean espacios en blanco, ‘*’ (un comodín que coincide con cero o más caracteres) o ‘?’ (un comodín que coincide exactamente con un carácter). Por ejemplo, para especificar un conjunto de declaraciones para cualquier host en el conjunto de dominios ".co.uk", se podría usar el siguiente patrón:

Host *.co.uk

El siguiente patrón coincidirá con cualquier host en el rango de red 192.168.0.[0-9]:

Host 192.168.0.?

Una lista de patrones es una lista de patrones separados por comas. Los patrones dentro de las listas de patrones pueden ser negados precediéndolos con un signo de exclamación (‘!’). Por ejemplo, para permitir que una clave se use desde cualquier lugar dentro de una organización excepto desde el pool de "dialup", se podría usar la siguiente entrada (en authorized_keys):

from="!*.dialup.example.com,*.example.com"

Tenga en cuenta que una coincidencia negada nunca producirá un resultado positivo por sí sola. Por ejemplo, intentar hacer coincidir "host3" con la siguiente lista de patrones fallará:

from="!host1,!host2"

La solución aquí es incluir un término que produzca una coincidencia positiva, como un comodín:

from="!host1,!host2,*"

TOKENS

Los argumentos para algunas palabras clave pueden hacer uso de tokens, que se expanden en tiempo de ejecución:

%%
Un literal ‘%’.
%C
Hash de %l%h%p%r%j.
%d
Directorio principal del usuario local.
%f
La huella digital de la clave de host del servidor.
%H
El nombre de host o la dirección del known_hosts que se está buscando.
%h
El nombre de host remoto.
%I
Una cadena que describe el motivo de una ejecución de KnownHostsCommand: ya sea ADDRESS al buscar un host por dirección (solo cuando CheckHostIP está habilitado), HOSTNAME al buscar por nombre de host, o ORDER al preparar la lista de preferencias de algoritmos de clave de host a utilizar para el host de destino.
%i
El ID de usuario local.
%j
El contenido de la opción ProxyJump, o la cadena vacía si esta opción no está establecida.
%K
La clave de host codificada en base64.
%k
El alias de la clave de host si se especifica, de lo contrario, el nombre de host remoto original dado en la línea de comandos.
%L
El nombre de host local.
%l
El nombre de host local, incluido el nombre de dominio.
%n
El nombre de host remoto original, tal como se proporcionó en la línea de comandos.
%p
El puerto remoto.
%r
El nombre de usuario remoto.
%T
La interfaz de red tun(4) o tap(4) local asignada si se solicitó reenvío de túnel, o "NONE" en caso contrario.
%t
El tipo de la clave de host del servidor, por ejemplo, ssh-ed25519.
%u
El nombre de usuario local.

CertificateFile, ControlPath, IdentityAgent, IdentityFile, Include, KnownHostsCommand, LocalForward, Match exec, RemoteCommand, RemoteForward, RevokedHostKeys, UserKnownHostsFile y VersionAddendum aceptan los tokens %%, %C, %d, %h, %i, %j, %k, %L, %l, %n, %p, %r y %u.

KnownHostsCommand acepta además los tokens %f, %H, %I, %K y %t.

Hostname acepta los tokens %% y %h.

LocalCommand acepta todos los tokens.

ProxyCommand y ProxyJump aceptan los tokens %%, %h, %n, %p y %r.

Tenga en cuenta que algunas de estas directivas construyen comandos para ser ejecutados a través del shell. Dado que ssh(1) no realiza ningún filtrado ni escape de caracteres que tengan un significado especial en los comandos del shell (por ejemplo, comillas), es responsabilidad del usuario asegurarse de que los argumentos pasados a ssh(1) no contengan dichos caracteres y que los tokens estén apropiadamente entrecomillados cuando se utilicen.

VARIABLES DE ENTORNO

Los argumentos de algunas palabras clave pueden expandirse en tiempo de ejecución a partir de variables de entorno en el cliente encerrándolos entre ${}, por ejemplo ${HOME}/.ssh se referiría al directorio .ssh del usuario. Si la variable de entorno especificada no existe, se producirá un error y la configuración para esa palabra clave se ignorará.

Las palabras clave CertificateFile, ControlPath, IdentityAgent, IdentityFile, Include, KnownHostsCommand y UserKnownHostsFile admiten variables de entorno. Las palabras clave LocalForward y RemoteForward solo admiten variables de entorno para rutas de sockets de dominio Unix.

ARCHIVOS

~/.ssh/config
Este es el archivo de configuración por usuario. El formato de este archivo se describe anteriormente. Este archivo es utilizado por el cliente SSH. Debido a la posibilidad de abuso, este archivo debe tener permisos estrictos: lectura/escritura para el usuario y no escribible por otros.
/etc/ssh/ssh_config
Archivo de configuración de todo el sistema. Este archivo proporciona valores predeterminados para aquellos valores que no se especifican en el archivo de configuración del usuario y para aquellos usuarios que no tienen un archivo de configuración. Este archivo debe ser legible por todos.
