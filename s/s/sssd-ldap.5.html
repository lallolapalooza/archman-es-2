NOMBRE

sssd-ldap - Proveedor LDAP de SSSD

DESCRIPCIÓN

Esta página del manual describe la configuración de dominios LDAP para sssd(8). Consulte la sección “FORMATO DE ARCHIVO” de la página del manual de sssd.conf(5) para obtener detalles de la sintaxis.

Puede configurar SSSD para usar más de un dominio LDAP.

El backend LDAP soporta los proveedores id, auth, access y chpass. Si desea autenticarse contra un servidor LDAP, se requiere TLS/SSL o LDAPS. sssd *no* soporta la autenticación a través de un canal sin cifrar. Incluso si el servidor LDAP solo se utiliza como proveedor de identidad, se recomienda encarecidamente un canal cifrado. Consulte la opción de configuración “ldap_access_filter” para obtener más información sobre el uso de LDAP como proveedor de acceso.

OPCIONES DE CONFIGURACIÓN

Todas las opciones de configuración comunes que se aplican a los dominios de SSSD también se aplican a los dominios LDAP. Consulte la sección “SECCIONES DE DOMINIO” de la página del manual de sssd.conf(5) para obtener detalles completos. Tenga en cuenta que los atributos de mapeo de SSSD LDAP se describen en la página del manual de sssd-ldap-attributes(5).

ldap_uri, ldap_backup_uri (cadena)

Especifica la lista separada por comas de las URI de los servidores LDAP a los que SSSD debe conectarse en orden de preferencia. Consulte la sección “FAILOVER” para obtener más información sobre la conmutación por error y la redundancia de servidores. Si no se especifica ninguna de las opciones, se habilita el descubrimiento de servicios. Para obtener más información, consulte la sección “DESCUBRIMIENTO DE SERVICIOS”.

El formato de la URI debe coincidir con el formato definido en RFC 2732:

ldap[s]://<host>[:puerto]

Para direcciones IPv6 explícitas, <host> debe estar entre corchetes []

ejemplo: ldap://[fc00::126:25]:389

ldap_chpass_uri, ldap_chpass_backup_uri (cadena)

Especifica la lista separada por comas de las URI de los servidores LDAP a los que SSSD debe conectarse en orden de preferencia para cambiar la contraseña de un usuario. Consulte la sección “FAILOVER” para obtener más información sobre la conmutación por error y la redundancia de servidores.

Para habilitar el descubrimiento de servicios, se debe establecer ldap_chpass_dns_service_name.

Predeterminado: vacío, es decir, se utiliza ldap_uri.

ldap_search_base (cadena)

El DN base predeterminado a utilizar para realizar operaciones de usuario LDAP.

A partir de SSSD 1.7.0, SSSD admite múltiples bases de búsqueda utilizando la sintaxis:

search_base[?scope?[filter][?search_base?scope?[filter]]*]

El alcance puede ser uno de "base", "onelevel" o "subtree".

El filtro debe ser un filtro de búsqueda LDAP válido según lo especificado por http://www.ietf.org/rfc/rfc2254.txt

Ejemplos:

ldap_search_base = dc=example,dc=com (que es equivalente a) ldap_search_base = dc=example,dc=com?subtree?

ldap_search_base = cn=host_specific,dc=example,dc=com?subtree?(host=thishost)?dc=example.com?subtree?

Nota: No se admiten bases de búsqueda múltiples que hagan referencia a objetos con nombres idénticos (por ejemplo, grupos con el mismo nombre en dos bases de búsqueda diferentes). Esto provocará un comportamiento impredecible en las máquinas cliente.

Predeterminado: Si no se establece, se utiliza el valor del atributo defaultNamingContext o namingContexts del RootDSE del servidor LDAP. Si defaultNamingContext no existe o tiene un valor vacío, se utilizan namingContexts. El atributo namingContexts debe tener un solo valor con el DN de la base de búsqueda del servidor LDAP para que esto funcione. No se admiten valores múltiples.

ldap_read_rootdse (cadena)

SSSD lee RootDSE para obtener información sobre LDAP y sus capacidades. Por defecto, esto se hace de forma anónima. Sin embargo, esto puede no ser permitido por el servidor LDAP. En tales casos, podemos usar esta opción para influir en el comportamiento de SSSD.

Los valores permitidos son:

•anónimo
•autenticado
•nunca

Por defecto, utilizando la opción "anónimo", SSSD intenta leer RootDSE de forma anónima. Si falla, SSSD reintenta el intento con autenticación.

Predeterminado: anónimo

ldap_schema (cadena)

Especifica el tipo de esquema en uso en el servidor LDAP de destino. Dependiendo del esquema seleccionado, los nombres de atributos predeterminados obtenidos de los servidores pueden variar. La forma en que se manejan algunos atributos también puede diferir.

Actualmente se admiten cuatro tipos de esquema:

•rfc2307
•rfc2307bis
•IPA
•AD

La principal diferencia entre estos tipos de esquema es cómo se registran las membresías de grupo en el servidor. Con rfc2307, los miembros del grupo se enumeran por nombre en el atributo memberUid. Con rfc2307bis e IPA, los miembros del grupo se enumeran por DN y se almacenan en el atributo member. El tipo de esquema AD establece los atributos para que correspondan con los valores de Active Directory 2008r2.

Predeterminado: rfc2307

ldap_pwmodify_mode (cadena)

Especifica la operación que se utiliza para modificar la contraseña del usuario.

Actualmente se admiten dos modos:

•exop - Operación extendida de modificación de contraseña (RFC 3062)
•ldap_modify - Modificación directa de userPassword (no recomendado).
•exop_force - Intenta la operación extendida de modificación de contraseña (RFC 3062) incluso si no quedan inicios de sesión de cortesía. Dependiendo del tipo y la configuración del servidor LDAP, el cambio de contraseña podría fallar porque no es posible una vinculación autenticada.

Nota: Primero, se establece una nueva conexión para verificar la contraseña actual vinculándose como el usuario que solicitó el cambio de contraseña. Si tiene éxito, esta conexión se utiliza para cambiar la contraseña; por lo tanto, el usuario debe tener acceso de escritura al atributo userPassword.

Predeterminado: exop

ldap_default_bind_dn (cadena)

El DN de vinculación predeterminado a utilizar para realizar operaciones LDAP.

ldap_default_authtok_type (cadena)

El tipo de token de autenticación del DN de vinculación predeterminado.

Los dos mecanismos que se admiten actualmente son:

password

obfuscated_password

Predeterminado: password

Consulte la página del manual de sss_obfuscate(8) para obtener más información.

ldap_default_authtok (cadena)

El token de autenticación del DN de vinculación predeterminado.

ldap_force_upper_case_realm (booleano)

Algunos servidores de directorios, por ejemplo Active Directory, podrían entregar la parte del reino del UPN en minúsculas, lo que podría provocar que la autenticación falle. Establezca esta opción a un valor distinto de cero si desea utilizar un reino en mayúsculas.

Predeterminado: falso

ldap_enumeration_refresh_timeout (entero)

Especifica cuántos segundos debe esperar SSSD antes de actualizar su caché de registros enumerados.

Predeterminado: 300

ldap_purge_cache_timeout (entero)

Determina con qué frecuencia se comprueba la caché de entradas inactivas (como grupos sin miembros y usuarios que nunca han iniciado sesión) y se eliminan para ahorrar espacio.

Establecer esta opción a cero deshabilitará la operación de limpieza de caché. Tenga en cuenta que si la enumeración está habilitada, la tarea de limpieza es necesaria para detectar las entradas eliminadas del servidor y no se puede deshabilitar. Por defecto, la tarea de limpieza se ejecutará cada 3 horas con la enumeración habilitada.

Esta opción también se puede establecer por subdominio o heredar a través de subdomain_inherit.

Predeterminado: 0 (deshabilitado)

ldap_group_nesting_level (entero)

Si ldap_schema se establece en un formato de esquema que admite grupos anidados (por ejemplo, RFC2307bis), entonces esta opción controla cuántos niveles de anidamiento seguirá SSSD. Esta opción no tiene ningún efecto en el esquema RFC2307.

Nota: Esta opción especifica el nivel garantizado de grupos anidados que se procesarán para cualquier búsqueda. Sin embargo, los grupos anidados más allá de este límite *pueden* ser devueltos si las búsquedas anteriores ya r

Niveles de anidamiento más profundos. Además, las búsquedas posteriores de otros grupos pueden ampliar el conjunto de resultados para la búsqueda original si se vuelve a consultar.

Si ldap_group_nesting_level se establece en 0, no se procesan grupos anidados. Sin embargo, cuando se conecta a Active-Directory Server 2008 y versiones posteriores utilizando “id_provider=ad”, también es necesario deshabilitar el uso de Token-Groups estableciendo ldap_use_tokengroups en false para restringir el anidamiento de grupos.

Valor predeterminado: 2

ldap_use_tokengroups

Esta opción habilita o deshabilita el uso del atributo Token-Groups al realizar initgroup para usuarios de Active Directory Server 2008 y versiones posteriores.

Esta opción también se puede establecer por subdominio o heredar a través de subdomain_inherit.

Valor predeterminado: True para AD e IPA, de lo contrario False.

ldap_host_search_base (cadena)

Opcional. Utilice la cadena dada como base de búsqueda para objetos de host.

Consulte “ldap_search_base” para obtener información sobre la configuración de varias bases de búsqueda.

Valor predeterminado: el valor de ldap_search_base

ldap_service_search_base (cadena)

Una base DN, un alcance de búsqueda y un filtro LDAP opcionales para restringir las búsquedas LDAP para este tipo de atributo.

sintaxis:

search_base[?scope?[filter][?search_base?scope?[filter]]*]

El alcance puede ser uno de "base", "onelevel" o "subtree". El alcance funciona como se especifica en la sección 4.5.1.2 de http://tools.ietf.org/html/rfc4511

El filtro debe ser un filtro de búsqueda LDAP válido según lo especificado por http://www.ietf.org/rfc/rfc2254.txt

Para ver ejemplos de esta sintaxis, consulte la sección de ejemplos de “ldap_search_base”.

Valor predeterminado: el valor de ldap_search_base

Tenga en cuenta que la especificación del alcance o el filtro no se admite para búsquedas contra un servidor Active Directory que pueda generar un gran número de resultados y activar la extensión de recuperación de rangos en la respuesta.

ldap_search_timeout (entero)

Especifica el tiempo de espera (en segundos) que las búsquedas ldap pueden ejecutarse antes de que se cancelen y se devuelvan los resultados almacenados en caché (y se entre en modo sin conexión).

Nota: esta opción está sujeta a cambios en futuras versiones de SSSD. Probablemente será reemplazada en algún momento por una serie de tiempos de espera para tipos de búsqueda específicos.

Esta opción también se puede establecer por subdominio o heredar a través de subdomain_inherit.

Valor predeterminado: 6

ldap_enumeration_search_timeout (entero)

Especifica el tiempo de espera (en segundos) que las búsquedas ldap para enumeraciones de usuarios y grupos pueden ejecutarse antes de que se cancelen y se devuelvan los resultados almacenados en caché (y se entre en modo sin conexión).

Valor predeterminado: 60

ldap_network_timeout (entero)

Especifica el tiempo de espera (en segundos) después del cual poll(2) / select(2) después de una connect(2) retorna en caso de no actividad.

Esta opción también se puede establecer por subdominio o heredar a través de subdomain_inherit.

Valor predeterminado: 6

ldap_opt_timeout (entero)

Especifica un tiempo de espera (en segundos) después del cual las llamadas a las API LDAP síncronas se abortarán si no se recibe respuesta. También controla el tiempo de espera al comunicarse con el KDC en caso de enlace SASL, el tiempo de espera de una operación de enlace LDAP, la operación extendida de cambio de contraseña y la operación StartTLS.

Esta opción también se puede establecer por subdominio o heredar a través de subdomain_inherit.

Valor predeterminado: 8

ldap_connection_expire_timeout (entero)

Especifica un tiempo de espera (en segundos) durante el cual se mantendrá una conexión a un servidor LDAP. Después de este tiempo, la conexión se restablecerá. Si se utiliza en paralelo con SASL/GSSAPI, se utilizará el menor de los dos valores (este valor frente a la vida útil del TGT).

Si la conexión está inactiva (no está ejecutando activamente una operación) dentro de los segundos ldap_opt_timeout de la expiración, se cerrará antes para garantizar que una nueva consulta no requiera que la conexión permanezca abierta más allá de su expiración. Esto implica que las conexiones siempre se cerrarán inmediatamente y nunca se reutilizarán si ldap_connection_expire_timeout <= ldap_opt_timout

Este tiempo de espera puede extenderse con un valor aleatorio especificado por ldap_connection_expire_offset

Esta opción también se puede establecer por subdominio o heredar a través de subdomain_inherit.

Valor predeterminado: 900 (15 minutos)

ldap_connection_expire_offset (entero)

Se agrega un desplazamiento aleatorio entre 0 y el valor configurado a ldap_connection_expire_timeout.

Esta opción también se puede establecer por subdominio o heredar a través de subdomain_inherit.

Valor predeterminado: 0

ldap_connection_idle_timeout (entero)

Especifica un tiempo de espera (en segundos) durante el cual se mantendrá una conexión inactiva a un servidor LDAP. Si la conexión está inactiva durante más tiempo que este, se cerrará.

Puede deshabilitar este tiempo de espera estableciendo el valor en 0.

Esta opción también se puede establecer por subdominio o heredar a través de subdomain_inherit.

Valor predeterminado: 900 (15 minutos)

ldap_page_size (entero)

Especifique el número de registros a recuperar de LDAP en una sola solicitud. Algunos servidores LDAP imponen un límite máximo por solicitud.

Valor predeterminado: 1000

ldap_disable_paging (booleano)

Deshabilita el control de paginación LDAP. Esta opción debe usarse si el servidor LDAP informa que admite el control de paginación LDAP en su RootDSE pero no está habilitado o no se comporta correctamente.

Ejemplo: Servidores OpenLDAP con el módulo de control de paginación instalado en el servidor pero no habilitado lo informarán en el RootDSE pero no podrán usarlo.

Ejemplo: 389 DS tiene un error por el cual solo puede admitir un control de paginación a la vez en una sola conexión. En clientes ocupados, esto puede resultar en la denegación de algunas solicitudes.

Valor predeterminado: False

ldap_disable_range_retrieval (booleano)

Deshabilita la recuperación de rangos de Active Directory.

Active Directory limita el número de miembros que se pueden recuperar en una sola búsqueda utilizando la política MaxValRange, que por defecto es 1500 miembros. Si un grupo contiene más de 1500 miembros, la respuesta incluye una extensión de rango específica de AD. Cuando está habilitada, esta opción evita que SSSD analice la extensión de rango. Como resultado, los grupos grandes aparecerán como si no tuvieran miembros. Esta opción no permite que SSSD lea rangos subsiguientes. Para recuperar todos los miembros de un grupo, debe aumentar la configuración MaxValRange en Active Directory.

Valor predeterminado: False

ldap_sasl_minssf (entero)

Al comunicarse con un servidor LDAP utilizando SASL, especifique el nivel de seguridad mínimo necesario para establecer la conexión. Los valores de esta opción están definidos por OpenLDAP.

Valor predeterminado: Usar el valor predeterminado del sistema (generalmente especificado por ldap.conf)

ldap_sasl_maxssf (entero)

Al comunicarse con un servidor LDAP utilizando SASL, especifique el nivel de seguridad máximo necesario para establecer la conexión. Los valores de esta opción están definidos por OpenLDAP.

Valor predeterminado: Usar el valor predeterminado del sistema (generalmente especificado por ldap.conf)

ldap_deref_threshold (entero)

Especifique el número de miembros del grupo que deben faltar en la caché interna para activar una búsqueda de desreferencia. Si faltan menos miembros, se buscan individualmente.

Puede desactivar completamente las búsquedas de desreferencia estableciendo el valor en 0. Tenga en cuenta que hay algunas rutas de código en SSSD, como el proveedor IPA HBAC, que solo se implementan utilizando la llamada de desreferencia, por lo que incluso con la desreferencia deshabilitada explícitamente, esas partes seguirán utilizando la desreferencia si el servidor lo admite y anuncia el control de desreferencia en el objeto rootDSE.

Una búsqueda de desreferencia es un medio para obtener todos los miembros del grupo en una sola llamada LDAP. Diferentes servidores LDAP pueden implementar diferentes métodos de desreferencia. Los servidores compatibles actualmente son 389/RHDS, OpenLDAP y Active Directory.

Nota: Si alguna de las bases de búsqueda especifica un filtro de búsqueda, la mejora del rendimiento de la búsqueda de desreferencia se deshabilitará independientemente de esta configuración.

Valor predeterminado: 10

ldap_ignore_unreadable_references (booleano)

Ignorar referencias de entradas LDAP ilegibles. en grupos. atributo de miembro. Si este parámetro se establece en falso, se devolverá un error y la operación fallará en lugar de simplemente ignorar la entrada ilegible.

Este parámetro puede ser útil al usar el proveedor AD y la cuenta del equipo que sssd utiliza para conectarse a AD no tiene acceso a una entrada particular o subárbol LDAP por razones de seguridad.

Por defecto: False

ldap_tls_reqcert (cadena)

Especifica qué comprobaciones realizar en los certificados del servidor en una sesión TLS, si las hay. Se puede especificar como uno de los siguientes valores:

nunca = El cliente no solicitará ni comprobará ningún certificado de servidor.

permitir = Se solicita el certificado del servidor. Si no se proporciona ningún certificado, la sesión continúa normalmente. Si se proporciona un certificado incorrecto, se ignorará y la sesión continuará normalmente.

intentar = Se solicita el certificado del servidor. Si no se proporciona ningún certificado, la sesión continúa normalmente. Si se proporciona un certificado incorrecto, la sesión se terminará inmediatamente.

exigir = Se solicita el certificado del servidor. Si no se proporciona ningún certificado, o si se proporciona un certificado incorrecto, la sesión se terminará inmediatamente.

duro = Igual que "exigir"

Por defecto: duro

ldap_tls_cacert (cadena)

Especifica el archivo que contiene los certificados de todas las Autoridades Certificadoras que **sssd** reconocerá.

Por defecto: usar los valores predeterminados de OpenLDAP, típicamente en /etc/openldap/ldap.conf

ldap_tls_cacertdir (cadena)

Especifica la ruta de un directorio que contiene certificados de Autoridad Certificadora en archivos individuales separados. Típicamente los nombres de archivo deben ser el hash del certificado seguido de '.0'. Si está disponible, **openssl rehash** o **c_rehash** se pueden usar para crear los nombres correctos.

Por defecto: usar los valores predeterminados de OpenLDAP, típicamente en /etc/openldap/ldap.conf

ldap_tls_cert (cadena)

Especifica el archivo que contiene el certificado de la clave del cliente.

Por defecto: no establecido

ldap_tls_key (cadena)

Especifica el archivo que contiene la clave del cliente.

Por defecto: no establecido

ldap_tls_cipher_suite (cadena)

Especifica las suites de cifrado aceptables. Típicamente es una lista separada por dos puntos. Consulte ldap.conf(5) para el formato.

Por defecto: usar los valores predeterminados de OpenLDAP, típicamente en /etc/openldap/ldap.conf

ldap_id_use_start_tls (booleano)

Especifica que la conexión del proveedor de identificación debe usar también tls para proteger el canal. Se recomienda encarecidamente *verdadero* por razones de seguridad.

Por defecto: verdadero

ldap_id_mapping (booleano)

Especifica que SSSD debe intentar mapear los ID de usuario y grupo de los atributos ldap_user_objectsid y ldap_group_objectsid en lugar de depender de ldap_user_uid_number y ldap_group_gid_number.

Actualmente, esta función solo admite el mapeo de objectSID de ActiveDirectory.

Por defecto: falso

ldap_min_id, ldap_max_id (entero)

En contraste con el mapeo de ID basado en SID que se utiliza si ldap_id_mapping se establece en verdadero, el rango de ID permitido para ldap_user_uid_number y ldap_group_gid_number no tiene límites. En una configuración con dominios subordinados/confiables, esto podría conducir a colisiones de ID. Para evitar colisiones, se pueden establecer ldap_min_id y ldap_max_id para restringir el rango permitido para los ID que se leen directamente del servidor. Los dominios subordinados pueden entonces elegir otros rangos para mapear ID.

Por defecto: no establecido (ambas opciones se establecen en 0)

ldap_sasl_mech (cadena)

Especifica el mecanismo SASL a utilizar. Actualmente solo GSSAPI y GSS-SPNEGO han sido probados y son compatibles.

Si el backend admite dominios subordinados, el valor de ldap_sasl_mech se heredará automáticamente a los dominios subordinados. Si se necesita un valor diferente para un dominio subordinado, se puede sobrescribir estableciendo ldap_sasl_mech explícitamente para este dominio subordinado. Consulte la SECCIÓN DE DOMINIO CONFIABLE en sssd.conf(5) para obtener detalles.

Por defecto: no establecido

ldap_sasl_authid (cadena)

Especifica el ID de autorización SASL a utilizar. Cuando se utilizan GSSAPI/GSS-SPNEGO, esto representa el principal de Kerberos utilizado para la autenticación en el directorio. Esta opción puede contener el principal completo (por ejemplo, host/mi_host@EJEMPLO.COM) o solo el nombre del principal (por ejemplo, host/mi_host). Por defecto, el valor no está establecido y se utilizan los siguientes principales: 
hostname@REALM
netbiosname$@REALM
host/hostname@REALM
*$@REALM
host/*@REALM
host/*

Si ninguno de ellos se encuentra, se devuelve el primer principal en el keytab.

Por defecto: host/hostname@REALM

ldap_sasl_realm (cadena)

Especifica el reino SASL a utilizar. Cuando no se especifica, esta opción tiene como valor predeterminado el valor de krb5_realm. Si ldap_sasl_authid contiene también el reino, esta opción se ignora.

Por defecto: el valor de krb5_realm.

ldap_sasl_canonicalize (booleano)

Si se establece en verdadero, la biblioteca LDAP realizaría una búsqueda inversa para canonizar el nombre del host durante una vinculación SASL.

Por defecto: falso;

ldap_krb5_keytab (cadena)

Especifica el keytab a utilizar cuando se utiliza SASL/GSSAPI/GSS-SPNEGO.

Esta opción también se puede establecer por subdominio o heredar a través de subdomain_inherit.

FAILOVER

The failover feature allows back ends to automatically switch to a different server if the current server fails.

Failover Syntax

The list of servers is given as a comma-separated list; any number of spaces is allowed around the comma. The servers are listed in order of preference. The list can contain any number of servers.

For each failover-enabled config option, two variants exist: primary and backup. The idea is that servers in the primary list are preferred and backup servers are only searched if no primary servers can be reached. If a backup server is selected, a timeout of 31 seconds is set. After this timeout SSSD will periodically try to reconnect to one of the primary servers. If it succeeds, it will replace the current active (backup) server.

The Failover Mechanism

The failover mechanism distinguishes between a machine and a service. The back end first tries to resolve the hostname of a given machine; if this resolution attempt fails, the machine is considered offline. No further attempts are made to connect to this machine for any other service. If the resolution attempt succeeds, the back end tries to connect to a service on this machine. If the service connection attempt fails, then only this particular service is considered offline and the back end automatically switches over to the next service. The machine is still considered online and might still be tried for another service.

Further connection attempts are made to machines or services marked as offline after a specified period of time; this is currently hard coded to 30 seconds.

If there are no more machines to try, the back end as a whole switches to offline mode, and then attempts to reconnect every 30 seconds.

Failover time outs and tuning

The failover mechanism can be tuned using the following options:

ldap_netgroup_timeout (integer)

Sets the timeout in seconds for the failover mechanism when trying to connect to a server.

Default: 30

ldap_netgroup_retry_delay (integer)

Sets the delay in seconds before attempting to reconnect to a server that failed.

Default: 30

ldap_sudo_timeout (integer)

Sets the timeout in seconds for the failover mechanism when trying to connect to a server.

Default: 30

ldap_sudo_retry_delay (integer)

Sets the delay in seconds before attempting to reconnect to a server that failed.

Default: 30

ldap_autofs_timeout (integer)

Sets the timeout in seconds for the failover mechanism when trying to connect to a server.

Default: 30

ldap_autofs_retry_delay (integer)

Sets the delay in seconds before attempting to reconnect to a server that failed.

Default: 30

TUNING

Resolver un servidor al que conectarse puede ser tan simple como ejecutar una única consulta DNS o puede implicar varios pasos, como encontrar el sitio correcto o probar varios nombres de host en caso de que algunos de los servidores configurados no sean accesibles. Los escenarios más complejos pueden llevar tiempo y SSSD necesita equilibrar el tiempo suficiente para completar el proceso de resolución y, por otro lado, no intentar durante demasiado tiempo antes de volver al modo sin conexión. Si los registros de depuración de SSSD muestran que la resolución del servidor excede el tiempo de espera antes de contactar con un servidor en funcionamiento, puede considerar cambiar los tiempos de espera.

Esta sección enumera los ajustables disponibles. Consulte su descripción en la página del manual sssd.conf(5).

dns_resolver_server_timeout

Tiempo en milisegundos que indica cuánto tiempo SSSD hablará con un único servidor DNS antes de probar el siguiente.

Por defecto: 1000

dns_resolver_op_timeout

Tiempo en segundos que indica cuánto tiempo SSSD intentará resolver una única consulta DNS (por ejemplo, la resolución de un nombre de host o un registro SRV) antes de probar el siguiente nombre de host o dominio de descubrimiento.

Por defecto: 3

dns_resolver_timeout

Cuánto tiempo intentará SSSD resolver un servicio de conmutación por error. La resolución de este servicio internamente puede incluir varios pasos, como la resolución de consultas DNS SRV o la localización del sitio.

Por defecto: 6

Para los proveedores basados en LDAP, la operación de resolución se realiza como parte de una operación de conexión LDAP. Por lo tanto, la marca de tiempo «ldap_opt_timeout» también debe establecerse en un valor mayor que «dns_resolver_timeout», que a su vez debe establecerse en un valor mayor que «dns_resolver_op_timeout», que debería ser mayor que «dns_resolver_server_timeout».

DESCUBRIMIENTO DE SERVICIOS

La función de descubrimiento de servicios permite a los backends encontrar automáticamente los servidores apropiados a los que conectarse utilizando una consulta DNS especial. Esta función no se admite para servidores de copia de seguridad.

Configuración

Si no se especifican servidores, el backend utiliza automáticamente el descubrimiento de servicios para intentar encontrar un servidor. Opcionalmente, el usuario puede optar por utilizar tanto direcciones de servidor fijas como descubrimiento de servicios insertando una palabra clave especial, «_srv_», en la lista de servidores. Se mantiene el orden de preferencia. Esta función es útil si, por ejemplo, el usuario prefiere utilizar el descubrimiento de servicios siempre que sea posible y recurrir a un servidor específico cuando no se puedan descubrir servidores mediante DNS.

El nombre de dominio

Consulte el parámetro «dns_discovery_domain» en la página del manual sssd.conf(5) para obtener más detalles.

El protocolo

Las consultas suelen especificar _tcp como protocolo. Las excepciones se documentan en la descripción de la opción correspondiente.

Véase también

Para obtener más información sobre el mecanismo de descubrimiento de servicios, consulte RFC 2782.

MAPEO DE ID

La función de mapeo de ID permite a SSSD actuar como cliente de Active Directory sin necesidad de que los administradores extiendan los atributos de usuario para admitir atributos POSIX para identificadores de usuario y grupo.

NOTA: Cuando el mapeo de ID está habilitado, los atributos uidNumber y gidNumber se ignoran. Esto es para evitar la posibilidad de conflictos entre valores asignados automáticamente y valores asignados manualmente. Si necesita utilizar valores asignados manualmente, TODOS los valores deben ser asignados manualmente.

Tenga en cuenta que el cambio de las opciones de configuración relacionadas con el mapeo de ID provocará cambios en los ID de usuario y grupo. Por el momento, SSSD no admite el cambio de ID, por lo que la base de datos de SSSD debe eliminarse. Dado que las contraseñas almacenadas en caché también se almacenan en la base de datos, la eliminación de la base de datos solo debe realizarse mientras los servidores de autenticación sean accesibles, de lo contrario, los usuarios podrían quedar bloqueados. Para almacenar en caché la contraseña, se debe realizar una autenticación. No es suficiente utilizar sss_cache(8) para eliminar la base de datos, sino que el proceso consiste en:

•Asegurarse de que los servidores remotos sean accesibles
•Detener el servicio SSSD
•Eliminar la base de datos
•Iniciar el servicio SSSD

Además, dado que el cambio de ID podría requerir el ajuste de otras propiedades del sistema, como la propiedad de archivos y directorios, es aconsejable planificar con antelación y probar exhaustivamente la configuración del mapeo de ID.

Algoritmo de mapeo

Active Directory proporciona un objectSID para cada objeto de usuario y grupo en el directorio. Este objectSID se puede dividir en componentes que representan la identidad del dominio de Active Directory y el identificador relativo (RID) del objeto de usuario o grupo.

El algoritmo de mapeo de ID de SSSD toma un rango de UID disponibles y lo divide en secciones de componentes de tamaño igual, llamadas «segmentos». Cada segmento representa el espacio disponible para una identidad de Active Directory.

Cuando se encuentra por primera vez una entrada de usuario o grupo para un dominio determinado, SSSD asigna uno de los segmentos disponibles para ese dominio. Para que esta asignación de segmentos sea repetible en diferentes máquinas cliente, seleccionamos el segmento según el siguiente algoritmo:

La cadena SID se pasa a través del algoritmo murmurhash3 para convertirla en un valor hash de 32 bits. Luego tomamos el módulo de este valor con el número total de segmentos disponibles para elegir el segmento.

NOTA: Es posible encontrar colisiones en el hash y el módulo subsiguiente. En estas situaciones, seleccionaremos el siguiente segmento disponible, pero es posible que no se pueda reproducir exactamente el mismo conjunto de segmentos en otras máquinas (ya que el orden en que se encuentran determinará sus segmentos). En esta situación, se recomienda cambiar al uso de atributos POSIX explícitos en Active Directory (deshabilitando el mapeo de ID) o configurar un dominio predeterminado para garantizar que al menos uno sea siempre coherente. Consulte «Configuración» para obtener más detalles.

Configuración

Configuración mínima (en la sección «[domain/DOMAINNAME]»):

ldap_id_mapping = True
ldap_schema = ad

La configuración predeterminada da como resultado la configuración de 10.000 segmentos, cada uno capaz de contener hasta 200.000 ID, comenzando desde 200.000 y llegando hasta 2.000.200.000. Esto debería ser suficiente para la mayoría de las implementaciones.

Configuración avanzada

ldap_idmap_range_min (entero)

Especifica el límite inferior (inclusivo) del rango de ID POSIX a utilizar para mapear los SID de usuario y grupo de Active Directory. Es el primer ID POSIX que se puede utilizar para el mapeo.

NOTA: Esta opción es diferente de «min_id» en que «min_id» actúa para filtrar la salida de las solicitudes a este dominio, mientras que esta opción controla el rango de asignación de ID. Es una distinción sutil, pero un buen consejo general sería que «min_id» sea menor o igual a «ldap_idmap_range_min»

Por defecto: 200000

ldap_idmap_range_max (entero)

Especifica el límite superior (exclusivo) del rango de ID POSIX a utilizar para mapear los SID de usuario y grupo de Active Directory. Es el primer ID POSIX que ya no se puede utilizar para el mapeo, es decir, uno mayor que el último que se puede utilizar para el mapeo.

NOTA: Esta opción es diferente de «max_id» en que «max_id» actúa para filtrar la salida de las solicitudes a este dominio, mientras que esta opción controla el rango de asignación de ID. Es una distinción sutil, pero un buen consejo general sería que «max_id» sea mayor o igual a «ldap_idmap_range_max»

Por defecto: 2000200000

ldap_idmap_range_size (entero)

Especifica el número de ID disponibles para cada segmento. Si el tamaño del rango no divide uniformemente los valores mínimo y máximo, creará tantos segmentos completos como sea posible.

NOTA: El valor de esta opción debe ser al menos tan grande como el RID de usuario más alto planificado para su uso en el servidor de Active Directory. Las búsquedas de usuarios y el inicio de sesión fallarán para cualquier usuario cuyo RID sea mayor que este valor.

Por ejemplo, si su usuario de Active Directory añadido más recientemente tiene objectSid=S-1-5-21-2153326666-2176343378-3404031434-1107, «ldap_idmap_range_size» debe ser al menos 1108, ya que el tamaño del rango es igual al RID máximo menos el RID mínimo más uno (por ejemplo, 1108 = 1107 - 0 + 1).

Es importante planificar la expansión futura, ya que el cambio de este valor provocará un cambio en todos los mapeos de ID del sistema, lo que resultará en que los usuarios tengan ID locales diferentes a los que tenían anteriormente.

Por defecto: 200000

ldap_idmap_default_domain_sid (cadena)

Especifica el SID de dominio del dominio predeterminado. Esto garantizará que este dominio siempre se asigne al segmento cero en el mapa de ID, eludiendo el algoritmo murmurhash descrito anteriormente.

Por defecto: no establecido

ldap_idmap_default_domain (cadena)

Especifica el nombre del dominio predeterminado.

Por defecto: no establecido

ldap_idmap_autorid_compat (booleano)

Cambia el comportamiento del algoritmo de mapeo de ID para que sea más similar al algoritmo «idmap_autorid» de winbind.

Cuando se configura esta opción, los dominios se asignarán comenzando desde el segmento cero y aumentando monótonamente con cada dominio adicional.

NOTA: Este algoritmo no es determinista (depende del orden en que se solicitan los usuarios y grupos). Si este modo es necesario para la compatibilidad con máquinas que ejecutan winbind, se recomienda utilizar también la opción «ldap_idmap_default_domain_sid» para garantizar que al menos un dominio se asigne consistentemente al segmento cero.

Por defecto: Falso

ldap_idmap_helper_table_size (entero)

Número máximo de segmentos secundarios que se intentan al realizar el mapeo

NAME

sssd-ldap - SSSD LDAP client configuration

DESCRIPTION

The sssd-ldap client is a provider for SSSD which can be used to access user, group, Netgroup, and SSH public key information stored in an LDAP directory. It is designed to provide this information to local Linux clients through the SSSD Name Service Switch (NSS) and the SSSD Authentication Service (SAS).

The sssd-ldap client can be configured in the /etc/sssd/sssd.conf file under a [domain/...] section.

ID MAPPING

The sssd-ldap client supports mapping of UNIX identifiers (UIDs and GIDs) to and from LDAP attribute values. This mapping is typically used when the LDAP server does not store UNIX identifiers but instead relies on SSSD to generate them.

When mapping from UNIX id to SID, SSSD checks if the RID part of the SID fits into the secondary slices which were generated by the ldap_idmap_helper_table_size option. If the RID is out of range, SSSD may generate additional secondary slices to cover the range.

Note: Additional secondary slices might be generated when SID is being mapped to UNIX id and RID part of SID is out of range for secondary slices generated so far. If value of ldap_idmap_helper_table_size is equal to 0 then no additional secondary slices are generated.

Default: 10

Well-Known SIDs

SSSD supports to look up the names of Well-Known SIDs, i.e. SIDs with a special hardcoded meaning. Since the generic users and groups related to those Well-Known SIDs have no equivalent in a Linux/UNIX environment no POSIX IDs are available for those objects.

The SID name space is organized in authorities which can be seen as different domains. The authorities for the Well-Known SIDs are

•Null Authority
•World Authority
•Local Authority
•Creator Authority
•Mandatory Label Authority
•Authentication Authority
•NT Authority
•Built-in

The capitalized version of these names are used as domain names when returning the fully qualified name of a Well-Known SID.

Since some utilities allow to modify SID based access control information with the help of a name instead of using the SID directly SSSD supports to look up the SID by the name as well. To avoid collisions only the fully qualified names can be used to look up Well-Known SIDs. As a result the domain names “NULL AUTHORITY”, “WORLD AUTHORITY”, “LOCAL AUTHORITY”, “CREATOR AUTHORITY”, “MANDATORY LABEL AUTHORITY”, “AUTHENTICATION AUTHORITY”, “NT AUTHORITY” and “BUILTIN” should not be used as domain names in sssd.conf.

EXAMPLE

The following example assumes that SSSD is correctly configured and LDAP is set to one of the domains in the [domains] section.

[domain/LDAP]
id_provider = ldap
auth_provider = ldap
ldap_uri = ldap://ldap.mydomain.org
ldap_search_base = dc=mydomain,dc=org
ldap_tls_reqcert = demand
cache_credentials = true

LDAP ACCESS FILTER EXAMPLE

The following example assumes that SSSD is correctly configured and to use the ldap_access_order=lockout.

[domain/LDAP]
id_provider = ldap
auth_provider = ldap
access_provider = ldap
ldap_access_order = lockout
ldap_pwdlockout_dn = cn=ppolicy,ou=policies,dc=mydomain,dc=org
ldap_uri = ldap://ldap.mydomain.org
ldap_search_base = dc=mydomain,dc=org
ldap_tls_reqcert = demand
cache_credentials = true

NOTES

The descriptions of some of the configuration options in this manual page are based on the ldap.conf(5) manual page from the OpenLDAP 2.4 distribution.
