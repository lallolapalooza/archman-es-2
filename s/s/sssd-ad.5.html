NOMBRE

sssd-ad - Proveedor de Active Directory de SSSD

DESCRIPCIÓN

Esta página del manual describe la configuración del proveedor AD para sssd(8). Para una referencia de sintaxis detallada, consulte la sección “FORMATO DE ARCHIVO” de la página del manual de sssd.conf(5).

El proveedor AD es un backend utilizado para conectarse a un servidor de Active Directory. Este proveedor requiere que la máquina esté unida al dominio AD y que haya una clave (keytab) disponible. La comunicación del backend se realiza a través de un canal cifrado con GSSAPI; las opciones SSL/TLS no deben usarse con el proveedor AD y serán sustituidas por el uso de Kerberos.

El proveedor AD soporta la conexión a Active Directory 2008 R2 o posterior. Versiones anteriores pueden funcionar, pero no están soportadas.

El proveedor AD puede ser utilizado para obtener información de usuarios y autenticar usuarios de dominios de confianza. Actualmente, solo se reconocen dominios de confianza en el mismo bosque. Además, los servidores de dominios de confianza siempre se descubren automáticamente.

El proveedor AD permite a SSSD utilizar el proveedor de identidad sssd-ldap(5) y el proveedor de autenticación sssd-krb5(5) con optimizaciones para entornos de Active Directory. El proveedor AD acepta las mismas opciones que los proveedores sssd-ldap y sssd-krb5, con algunas excepciones. Sin embargo, no es necesario ni recomendable configurar estas opciones.

El proveedor AD copia principalmente las opciones predeterminadas tradicionales de los proveedores ldap y krb5, con algunas excepciones. Las diferencias se enumeran en la sección “OPCIONES PREDETERMINADAS MODIFICADAS”.

El proveedor AD también puede usarse como proveedor de acceso (access), cambio de contraseña (chpass), sudo y autofs. No se requiere configuración del proveedor de acceso en el lado del cliente.

Si se configura “auth_provider=ad” o “access_provider=ad” en sssd.conf, entonces el id_provider también debe establecerse en “ad”.

Por defecto, el proveedor AD mapeará los valores de UID y GID del parámetro objectSID en Active Directory. Para más detalles sobre esto, ver la sección “MAPEADO DE IDENTIDAD” más abajo. Si desea deshabilitar el mapeado de identidad y en su lugar confiar en los atributos POSIX definidos en Active Directory, debe establecer

ldap_id_mapping = False

Si se deben usar atributos POSIX, se recomienda por razones de rendimiento que los atributos también se repliquen al Catálogo Global. Si los atributos POSIX se replican, SSSD intentará localizar el dominio de un ID numérico solicitado con la ayuda del Catálogo Global y solo buscará en ese dominio. En contraste, si los atributos POSIX no se replican al Catálogo Global, SSSD debe buscar en todos los dominios del bosque secuencialmente. Tenga en cuenta que la opción “cache_first” también puede ser útil para acelerar las búsquedas sin dominio. Tenga en cuenta que si solo un subconjunto de atributos POSIX está presente en el Catálogo Global, los atributos no replicados actualmente no se leen del puerto LDAP.

Los usuarios, grupos y otras entidades servidas por SSSD siempre se tratan como no sensibles a mayúsculas y minúsculas en el proveedor AD para compatibilidad con la implementación LDAP de Active Directory.

SSSD solo resuelve Grupos de Seguridad de Active Directory. Para más información sobre los tipos de grupos de AD, ver: Grupos de seguridad de Active Directory[1]

SSSD filtra los grupos de Dominio Local de dominios remotos en el bosque AD. Por defecto, se filtran por ejemplo al seguir una jerarquía de grupos anidados en dominios remotos porque no son válidos en el dominio local. Esto se hace para estar de acuerdo con la asignación de membresía de grupos de Active Directory, que se puede ver en el PAC del ticket Kerberos de un usuario emitido por Active Directory.

OPCIONES DE CONFIGURACIÓN

Consulte la sección “SECCIONES DE DOMINIO” de la página del manual de sssd.conf(5) para obtener detalles sobre la configuración de un dominio SSSD.

ad_domain (cadena)

Especifica el nombre del dominio de Active Directory. Esto es opcional. Si no se proporciona, se utiliza el nombre del dominio de configuración.

Para un funcionamiento correcto, esta opción debe especificarse como la versión en minúsculas de la versión larga del dominio de Active Directory.

El nombre corto del dominio (también conocido como nombre NetBIOS o plano) se detecta automáticamente por SSSD.

ad_enabled_domains (cadena)

Una lista separada por comas de dominios de Active Directory habilitados. Si se proporciona, SSSD ignorará cualquier dominio no listado en esta opción. Si se deja sin establecer, todos los dominios descubiertos del bosque AD estarán disponibles.

Durante el descubrimiento de los dominios, SSSD filtrará algunos dominios donde las banderas o atributos indican que no pertenecen al bosque local o no son de confianza. Si se establece ad_enabled_domains, SSSD intentará habilitar todos los dominios listados.

Para un funcionamiento correcto, esta opción debe especificarse completamente en minúsculas y como el nombre de dominio completo del dominio de Active Directory. Por ejemplo:

ad_enabled_domains = sales.example.com, eng.example.com

El nombre corto del dominio (también conocido como nombre NetBIOS o plano) será detectado automáticamente por SSSD.

Predeterminado: No establecido

ad_server, ad_backup_server (cadena)

La lista separada por comas de nombres de host de los servidores AD a los que SSSD debe conectarse en orden de preferencia. Para más información sobre conmutación por error (failover) y redundancia de servidores, ver la sección “CONMUTACIÓN POR ERROR”.

Esto es opcional si el descubrimiento automático está habilitado. Para más información sobre el descubrimiento de servicios, consulte la sección “DESCUBRIMIENTO DE SERVICIOS”.

Nota: Los dominios de confianza siempre descubrirán servidores automáticamente, incluso si el servidor principal se define explícitamente en la opción ad_server.

ad_hostname (cadena)

Opcional. En máquinas donde el hostname(5) no refleja el nombre completo, sssd intentará expandir el nombre corto. Si no es posible o el nombre corto debe usarse realmente en su lugar, establezca este parámetro explícitamente.

Este campo se utiliza para determinar el principal del host en uso en el keytab y para realizar actualizaciones dinámicas de DNS. Debe coincidir con el nombre de host para el cual se emitió el keytab.

ad_enable_dns_sites (booleano)

Habilita sitios DNS (descubrimiento de servicios basado en la ubicación).

Si es verdadero y el descubrimiento de servicios (ver párrafo de Descubrimiento de Servicios al final de la página del manual) está habilitado, SSSD primero intentará descubrir el servidor de Active Directory al que conectarse utilizando el Descubrimiento de Sitios de Active Directory y luego recurrirá a los registros SRV de DNS si no se encuentra ningún sitio AD. La configuración SRV de DNS, incluido el dominio de descubrimiento, también se utiliza durante el descubrimiento del sitio.

Predeterminado: verdadero

ad_access_filter (cadena)

Especifica un filtro de control de acceso LDAP que un usuario debe cumplir para obtener acceso. La opción “access_provider” debe configurarse explícitamente como “ad” para que esta opción tome efecto. Si desea utilizar “ad_access_filter” como el único esquema de control de acceso, debe deshabilitar el control de acceso basado en GPO (ver la opción “ad_gpo_access_control” para más detalles).

La opción también admite la especificación de filtros diferentes por dominio o bosque. Este filtro extendido consistiría en: “PALABRA_CLAVE:NOMBRE:FILTRO”. La palabra clave puede ser “DOM”, “FOREST” o estar ausente.

Si la palabra clave es igual a “DOM” o está ausente, entonces “NOMBRE” especifica el dominio o subdominio al que se aplica el filtro. Si la palabra clave es igual a “FOREST”, entonces el filtro se aplica a todos los dominios del bosque especificado por “NOMBRE”.

Múltiples filtros pueden separarse con el carácter “?”, de forma similar a como funcionan las bases de búsqueda.

La membresía de grupo anidada debe buscarse utilizando un OID especial “:1.2.840.113556.1.4.1941:” además de la sintaxis completa DOM:domain.example.org: para asegurar que el analizador no intente interpretar los caracteres de dos puntos asociados con el OID. Si no usa este OID, la membresía de grupo anidada no se resolverá. Vea el ejemplo de uso a continuación y consulte aquí para obtener más información sobre el OID: [MS-ADTS] sección extensiones LDAP[2]

La coincidencia más específica siempre se usa. Por ejemplo, si la opción especifica un filtro para un dominio del que el usuario es miembro y un filtro global, se aplicará el filtro por dominio. Si hay más coincidencia

Ejemplos:

# aplicar filtro solo en el dominio llamado dom1:
dom1:(memberOf=cn=admins,ou=groups,dc=dom1,dc=com)

Por defecto: No establecido

ad_site (string)

Especifica el sitio AD al que el cliente debe intentar conectarse. Si esta opción no se proporciona, el sitio AD se descubrirá automáticamente.

Por defecto: No establecido

ad_enable_gc (boolean)

Por defecto, SSSD se conecta primero al Catálogo Global para recuperar usuarios de dominios de confianza y utiliza el puerto LDAP para recuperar membresías de grupos o como alternativa. Deshabilitar esta opción hace que SSSD solo se conecte al puerto LDAP del servidor AD actual.

Tenga en cuenta que deshabilitar el soporte del Catálogo Global no deshabilita la recuperación de usuarios de dominios de confianza. SSSD se conectaría al puerto LDAP de los dominios de confianza en su lugar. Sin embargo, se debe utilizar el Catálogo Global para poder resolver las membresías de grupos entre dominios.

Por defecto: true

ad_gpo_access_control (string)

Esta opción especifica el modo de operación para la funcionalidad de control de acceso basada en GPO: si opera en modo deshabilitado, modo de aplicación o modo permisivo. Tenga en cuenta que la opción “access_provider” debe establecerse explícitamente en “ad” para que esta opción tenga efecto.

La funcionalidad de control de acceso basada en GPO utiliza la configuración de políticas de GPO para determinar si un usuario en particular tiene permitido iniciar sesión en el host. Para obtener más información sobre la configuración de políticas admitidas, consulte las opciones “ad_gpo_map”.

Tenga en cuenta que la versión actual de SSSD no admite los grupos integrados de Active Directory. Los grupos integrados (como Administradores con SID S-1-5-32-544) en las reglas de control de acceso de GPO serán ignorados por SSSD. Consulte el rastreador de problemas upstream https://github.com/SSSD/sssd/issues/5063.

Antes de realizar el control de acceso, SSSD aplica el filtrado de seguridad de políticas de grupo a los GPO. Para cada inicio de sesión de usuario, se comprueba la aplicabilidad de los GPO vinculados al host. Para que un GPO se aplique a un usuario, el usuario o al menos uno de los grupos a los que pertenece debe tener los siguientes permisos sobre el GPO:

•Lectura: El usuario o uno de sus grupos debe tener acceso de lectura a las propiedades del GPO (RIGHT_DS_READ_PROPERTY)
•Aplicar directiva de grupo: El usuario o al menos uno de sus grupos debe tener permitido aplicar el GPO (RIGHT_DS_CONTROL_ACCESS).

Por defecto, el grupo Usuarios Autenticados está presente en un GPO y este grupo tiene derechos de acceso tanto de Lectura como de Aplicar Directiva de Grupo. Dado que la autenticación de un usuario debe haberse completado correctamente antes de que se inicie el filtrado de seguridad de GPO y el control de acceso, los permisos del grupo Usuarios Autenticados en el GPO siempre se aplican también al usuario.

NOTA: Si el modo de operación está configurado como enforcing, es posible que los usuarios que anteriormente tenían acceso permitido ahora se les niegue el acceso (según la configuración de la política de GPO). Para facilitar una transición fluida para los administradores, hay disponible un modo permisivo que no aplicará las reglas de control de acceso, pero las evaluará y emitirá un mensaje de syslog si se hubiera denegado el acceso. Al examinar los registros, los administradores pueden realizar los cambios necesarios antes de establecer el modo en enforcing. Para registrar la depuración del control de acceso basado en GPO, se requiere el nivel de depuración 'trace functions' (consulte la página del manual sssctl(8)).

Hay tres valores admitidos para esta opción:

•disabled: Las reglas de control de acceso basadas en GPO no se evalúan ni se aplican.
•enforcing: Las reglas de control de acceso basadas en GPO se evalúan y se aplican.
•permissive: Las reglas de control de acceso basadas en GPO se evalúan, pero no se aplican. En su lugar, se emitirá un mensaje de syslog indicando que al usuario se le habría denegado el acceso si el valor de esta opción se hubiera establecido en enforcing.

Por defecto: enforcing

ad_gpo_implicit_deny (boolean)

Normalmente, cuando no se encuentran GPO aplicables, se permite el acceso a los usuarios. Cuando esta opción se establece en True, solo se permitirá el acceso a los usuarios cuando sea explícitamente permitido por una regla de GPO. De lo contrario, se denegará el acceso a los usuarios. Esto se puede utilizar para mejorar la seguridad, pero tenga cuidado al usar esta opción, ya que puede denegar el acceso incluso a los usuarios del grupo integrado de Administradores si no se aplican reglas de GPO a ellos.

Por defecto: False

ad_gpo_ignore_unreadable (boolean)

Normalmente, cuando SSSD no puede leer algunos contenedores de políticas de grupo (objetos AD) de los objetos de directiva de grupo aplicables, se deniega el acceso a los usuarios. Esta opción permite ignorar los contenedores de políticas de grupo y las políticas asociadas si sus atributos en los contenedores de políticas de grupo no son legibles para SSSD.

Por defecto: False

ad_gpo_cache_timeout (integer)

El tiempo entre búsquedas de archivos de políticas de GPO en el servidor AD. Esto reducirá la latencia y la carga en el servidor AD si se realizan muchas solicitudes de control de acceso en un corto período de tiempo.

Por defecto: 5 (segundos)

ad_gpo_map_interactive (string)

Una lista separada por comas de nombres de servicios PAM para los cuales se evalúa el control de acceso basado en GPO según la configuración de las políticas InteractiveLogonRight y DenyInteractiveLogonRight. Solo se evalúan aquellos GPO para los que el usuario tiene permiso de Lectura y Aplicar Directiva de Grupo (ver opción “ad_gpo_access_control”). Si un GPO evaluado contiene la configuración de denegación de inicio de sesión interactivo para el usuario o uno de sus grupos, se deniega el acceso local al usuario. Si ninguno de los GPO evaluados tiene definida una configuración de inicio de sesión interactivo, se otorga acceso local al usuario. Si al menos un GPO evaluado contiene configuraciones de derecho de inicio de sesión interactivo, se otorga acceso local al usuario solo si él o al menos uno de sus grupos forma parte de la configuración de la política.

Nota: Usando el Editor de administración de directivas de grupo, este valor se denomina "Permitir inicio de sesión local" y "Denegar inicio de sesión local".

Es posible agregar otro nombre de servicio PAM al conjunto por defecto usando “+nombre_servicio” o eliminar explícitamente un nombre de servicio PAM del conjunto por defecto usando “-nombre_servicio”. Por ejemplo, para reemplazar un nombre de servicio PAM predeterminado para este derecho de inicio de sesión (por ejemplo, “login”) con un nombre de servicio PAM personalizado (por ejemplo, “my_pam_service”), usaría la siguiente configuración:

ad_gpo_map_interactive = +my_pam_service, -login

•gdm-password
•gdm-smartcard
•kdm

•sddm

ad_gpo_map_remote_interactive (string)

Una lista separada por comas de nombres de servicios PAM para los cuales se evalúa el control de acceso basado en GPO según la configuración de las políticas RemoteInteractiveLogonRight y DenyRemoteInteractiveLogonRight. Solo se evalúan aquellos GPO para los que el usuario tiene permiso de Lectura y Aplicar Directiva de Grupo (ver opción “ad_gpo_access_control”). Si un GPO evaluado contiene la configuración de denegación de inicio de sesión remoto para el usuario o uno de sus grupos, se deniega el acceso interactivo remoto al usuario. Si ninguno de los GPO evaluados tiene definida una configuración de inicio de sesión interactivo remoto, se otorga acceso remoto al usuario. Si al menos un GPO evaluado contiene configuraciones de derecho de inicio de sesión interactivo remoto, se otorga acceso remoto al usuario solo si él o al menos uno de sus grupos forma parte de la configuración de la política.

Nota: Usando el Editor de administración de directivas de grupo, este valor se denomina "Permitir inicio de sesión a través de Servicios de Escritorio remoto" y "Denegar inicio de sesión a través de Servicios de Escritorio remoto".

FAILOVER

La función de failover permite que los backends cambien automáticamente a un servidor diferente si el servidor actual falla.

Sintaxis de Failover

La lista de servidores se proporciona como una lista separada por comas; se permiten cualquier número de espacios alrededor de la coma. Los servidores se enumeran en orden de preferencia. La lista puede contener cualquier número de servidores.

Para cada opción de configuración habilitada para failover, existen dos variantes: primary y backup. La idea es que los servidores de la lista primaria son preferidos y los servidores de respaldo solo se buscan si no se puede acceder a ningún servidor primario. Si se selecciona un servidor de respaldo, se establece un tiempo de espera de 31 segundos. Después de este tiempo de espera, SSSD intentará periódicamente reconectarse a uno de los servidores primarios. Si tiene éxito, reemplazará el servidor activo (de respaldo) actual.

El Mecanismo de Failover

Changes the behavior of the ID-mapping algorithm to be more similar to winbind’s “idmap_autorid” algorithm.

When this option is configured, domains will be allocated starting with slice zero and increasing monotonically with each additional domain.

NOTE: This algorithm is non-deterministic (it depends on the order that users and groups are requested). If this mode is required for compatibility with machines running winbind, it is recommended to also use the “ldap_idmap_default_domain_sid” option to guarantee that at least one domain is consistently allocated to slice zero.

Default: False

ldap_idmap_helper_table_size (integer)

Maximal number of secondary slices that is tried when performing mapping from UNIX id to SID.

Note: Additional secondary slices might be generated when SID is being mapped to UNIX id and RID part of SID is out of range for secondary slices generated so far. If value of ldap_idmap_helper_table_size is equal to 0 then no additional secondary slices are generated.

Default: 10

Well-Known SIDs

SSSD supports to look up the names of Well-Known SIDs, i.e. SIDs with a special hardcoded meaning. Since the generic users and groups related to those Well-Known SIDs have no equivalent in a Linux/UNIX environment no POSIX IDs are available for those objects.

The SID name space is organized in authorities which can be seen as different domains. The authorities for the Well-Known SIDs are

•Null Authority
•World Authority
•Local Authority
•Creator Authority
•Mandatory Label Authority
•Authentication Authority
•NT Authority
•Built-in

The capitalized version of these names are used as domain names when returning the fully qualified name of a Well-Known SID.

Since some utilities allow to modify SID based access control information with the help of a name instead of using the SID directly SSSD supports to look up the SID by the name as well. To avoid collisions only the fully qualified names can be used to look up Well-Known SIDs. As a result the domain names “NULL AUTHORITY”, “WORLD AUTHORITY”, “LOCAL AUTHORITY”, “CREATOR AUTHORITY”, “MANDATORY LABEL AUTHORITY”, “AUTHENTICATION AUTHORITY”, “NT AUTHORITY” and “BUILTIN” should not be used as domain names in sssd.conf.

EXAMPLE

The following example assumes that SSSD is correctly configured and example.com is one of the domains in the [sssd] section. This example shows only the AD provider-specific options.

[domain/EXAMPLE]
id_provider = ad
auth_provider = ad
access_provider = ad
chpass_provider = ad
ad_server = dc1.example.com
ad_hostname = client.example.com
ad_domain = example.com

NOTES

The AD access control provider checks if the account is expired. It has the same effect as the following configuration of the LDAP provider:

access_provider = ldap
ldap_access_order = expire
ldap_account_expire_policy = ad

However, unless the “ad” access control provider is explicitly configured, the default access provider is “permit”. Please note that if you configure an access provider other than “ad”, you need to set all the connection parameters (such as LDAP URIs and encryption details) manually.

When the autofs provider is set to “ad”, the RFC2307 schema attribute mapping (nisMap, nisObject, ...) is used, because these attributes are included in the default Active Directory schema.
