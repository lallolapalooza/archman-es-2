SSSD.CONF(5) Formatos de archivo y convenciones SSSD.CONF(5)

NOMBRE

sssd.conf - el archivo de configuración para SSSD

FORMATO DEL ARCHIVO

El archivo tiene una sintaxis estilo ini y consta de secciones y parámetros. Una sección comienza con el nombre de la sección entre corchetes y continúa hasta que comienza la siguiente sección. Un ejemplo de sección con parámetros de uno y varios valores:

[seccion]
clave = valor
clave2 = valor2,valor3

Los tipos de datos utilizados son cadena (no se necesitan comillas), entero y booleano (con valores de “TRUE/FALSE”).

Una línea de comentario comienza con un signo de almohadilla (“#”) o un punto y coma (“;”). Los comentarios en línea no son compatibles.

Todas las secciones pueden tener un parámetro opcional descripción. Su función es solo como etiqueta para la sección.

sssd.conf debe ser un archivo regular al que solo pueda acceder el usuario utilizado para ejecutar el servicio SSSD o root.

FRAGMENTOS DE CONFIGURACIÓN DEL DIRECTORIO INCLUDE

El archivo de configuración sssd.conf incluirá fragmentos de configuración utilizando el directorio de inclusión conf.d.

Cualquier archivo colocado en conf.d que termine en “.conf” y no comience con un punto (“.”) se usará junto con sssd.conf para configurar SSSD.

Los fragmentos de configuración de conf.d tienen mayor prioridad que sssd.conf y anularán sssd.conf cuando ocurran conflictos. Si hay varios fragmentos en conf.d, se incluirán en orden alfabético (basado en la localidad). Los archivos incluidos más tarde tienen mayor prioridad. Los prefijos numéricos (01_fragmento.conf, 02_fragmento.conf, etc.) pueden ayudar a visualizar la prioridad (un número mayor significa mayor prioridad).

Los archivos fragmento requieren el mismo propietario y permisos que sssd.conf.

OPCIONES GENERALES

Las siguientes opciones son utilizables en más de una sección de configuración.

Opciones utilizables en todas las secciones

debug_level (entero)

SSSD admite dos representaciones para especificar el nivel de depuración. La más simple es especificar un valor decimal de 0 a 9, que representa habilitar ese nivel y todos los mensajes de depuración de niveles inferiores. La opción más completa es especificar una máscara de bits hexadecimal para habilitar o deshabilitar niveles específicos (por ejemplo, si desea suprimir un nivel).

Tenga en cuenta que cada servicio SSSD registra sus mensajes en su propio archivo de registro. También tenga en cuenta que habilitar “debug_level” en la sección “[sssd]” solo habilita la depuración solo para el proceso sssd en sí, no para los procesos del respondedor o proveedor. El parámetro “debug_level” debería añadirse a todas las secciones de las que desee obtener registros de depuración.

Además de cambiar el nivel de registro en el archivo de configuración utilizando el parámetro “debug_level”, que es persistente pero requiere reiniciar SSSD, también es posible cambiar el nivel de depuración sobre la marcha utilizando la herramienta sss_debuglevel(8).

Niveles de depuración actualmente compatibles:

0, 0x0010: Fallos fatales. Cualquier cosa que impida que SSSD se inicie o cause que deje de ejecutarse.

1, 0x0020: Fallos críticos. Un error que no mata SSSD, pero que indica que al menos una característica importante no funcionará correctamente.

2, 0x0040: Fallos graves. Un error que anuncia que una solicitud u operación particular ha fallado.

3, 0x0080: Fallos menores. Estos son los errores que se propagarían hacia abajo para causar el fallo de operación de 2.

4, 0x0100: Configuraciones.

5, 0x0200: Datos de función.

6, 0x0400: Mensajes de rastreo para funciones de operación.

7, 0x1000: Mensajes de rastreo para funciones de control internas.

8, 0x2000: Contenidos de variables internas de función que pueden ser interesantes.

9, 0x4000: Información de rastreo extremadamente de bajo nivel.

9, 0x20000: Datos de rendimiento y estadísticas, tenga en cuenta que debido a la forma en que las solicitudes se procesan internamente, el tiempo de ejecución registrado de una solicitud podría ser más largo de lo que realmente fue.

10, 0x10000: Información de rastreo de libldb aún más de bajo nivel. Casi nunca es realmente necesario.

Para registrar los niveles de depuración de la máscara de bits requeridos, simplemente sume sus números como se muestra en los siguientes ejemplos:

Ejemplo: Para registrar fallos fatales, fallos críticos, fallos graves y datos de función, use 0x0270.

Ejemplo: Para registrar fallos fatales, configuraciones, datos de función, mensajes de rastreo para funciones de control internas, use 0x1310.

Nota: El formato de máscara de bits de los niveles de depuración se introdujo en la versión 1.7.0.

Por defecto: 0x0070 (es decir, fallos fatales, críticos y graves; corresponde a establecer 2 en notación decimal)

debug (entero)

SSSD 1.14 y posteriores también incluyen el alias debug para debug_level como una característica de conveniencia. Si se especifican ambos, se utilizará el valor de debug_level.

debug_timestamps (booleano)

Añade una marca de tiempo a los mensajes de depuración. Si journald está habilitado para el registro de depuración de SSSD, esta opción se ignora.

Por defecto: true

debug_microseconds (booleano)

Añade microsegundos a la marca de tiempo en los mensajes de depuración. Si journald está habilitado para el registro de depuración de SSSD, esta opción se ignora.

Por defecto: false

debug_backtrace_enabled (booleano)

Habilita el rastreo de depuración.

En caso de que SSSD se ejecute con debug_level menor que 9, todo se registra en un búfer de anillo en memoria y se vuelca a un archivo de registro ante cualquier error hasta e incluyendo `min(0x0040, debug_level)` (es decir, si debug_level se establece explícitamente en 0 o 1, solo esos niveles de error activarán el rastreo, de lo contrario, hasta 2).

La característica solo es compatible con `logger == files` (es decir, la configuración no tiene efecto para otros tipos de logger).

Por defecto: true

Opciones utilizables en las secciones SERVICIO y DOMINIO

timeout (entero)

Tiempo de espera en segundos entre latidos para este servicio. Se utiliza para garantizar que el proceso esté activo y sea capaz de responder a las solicitudes. Tenga en cuenta que después de tres latidos perdidos, el proceso se terminará a sí mismo.

Por defecto: 10

La sección [sssd]

Piezas individuales de la funcionalidad de SSSD son proporcionadas por servicios SSSD especiales que se inician y detienen junto con SSSD. Los servicios son administrados por un servicio especial llamado frecuentemente "monitor". La sección "[sssd]" se utiliza para configurar el monitor, así como algunas otras opciones importantes como los dominios de identidad.

Parámetros de sección

services

Lista separada por comas de los servicios que se inician cuando SSSD se inicia. La lista de servicios es opcional en plataformas donde se admite systemd, ya que se activarán por socket o D-Bus cuando sea necesario.

Servicios compatibles: nss, pam, ifp , sudo , autofs , ssh , pac

Por defecto, todos los servicios están deshabilitados y el administrador debe habilitar los que se permiten usar ejecutando: "systemctl enable sssd-@service@.socket".

Este parámetro describe la lista de dominios en el orden en que desea que se consulten. Se recomienda que un nombre de dominio contenga solo caracteres ASCII alfanuméricos, guiones, puntos y guiones bajos. El carácter '/' está prohibido.

Esta cadena se utilizará como nombre de dominio predeterminado para todos los nombres sin un componente de nombre de dominio. El caso de uso principal es en entornos donde el dominio principal está destinado a administrar políticas de host y todos los usuarios se encuentran en un dominio de confianza. La opción permite que esos usuarios inicien sesión solo con su nombre de usuario sin proporcionar un nombre de dominio.

Tenga en cuenta que si esta opción está configurada, todos los usuarios del dominio principal deben usar su nombre completamente calificado, por ejemplo, usuario@dominio.nombre, para iniciar sesión. Configurar esta opción cambia el valor predeterminado de use_fully_qualified_names a True. No está permitido usar esta opción junto con use_fully_qualified_names configurado en False.

override_space (string)

Este parámetro reemplazará los espacios (barra espaciadora) con el carácter dado para los nombres de usuario y grupo. por ejemplo, (_). El nombre de usuario "john doe" se convertirá en "john_doe". Esta función se agregó para ayudar a la compatibilidad con scripts de shell que tienen dificultades para manejar espacios, debido al separador de campos predeterminado en el shell.

Tenga en cuenta que es un error de configuración usar un carácter de reemplazo que podría usarse en nombres de usuario o grupo. Si un nombre contiene el carácter de reemplazo, SSSD intenta devolver el nombre sin modificar, pero en general, el resultado de una búsqueda no está definido.

disable_netlink (boolean)

SSSD se integra con la interfaz netlink para monitorear cambios en rutas, direcciones y enlaces, y para activar ciertas acciones.

Los cambios de estado de SSSD causados por eventos de netlink pueden ser indeseables y se pueden deshabilitar estableciendo esta opción en 'true'

Por defecto: false (se detectan los cambios de netlink)

domain_resolution_order

Lista separada por comas de dominios y subdominios que representan el orden de búsqueda que se seguirá. La lista no tiene que incluir todos los dominios posibles, ya que los dominios faltantes se buscarán según el orden en que se presenten en la opción de configuración de “dominios”. Los subdominios que no estén listados como parte de “lookup_order” se buscarán en un orden aleatorio para cada dominio padre.

Tenga en cuenta que cuando se establece esta opción, el formato de salida de todos los comandos es siempre completamente calificado, incluso cuando se usan nombres cortos para la entrada. En caso de que el administrador desee que la salida no esté completamente calificada, se puede utilizar la opción full_name_format como se muestra a continuación: “full_name_format=%1$s”. Sin embargo, tenga en cuenta que durante el inicio de sesión, las aplicaciones de inicio de sesión a menudo canonizan el nombre de usuario llamando a getpwnam(3) que, si se devuelve un nombre corto para una entrada calificada (al intentar alcanzar un usuario que existe en varios dominios), podría redirigir el intento de inicio de sesión al dominio que usa nombres cortos, lo que hace que esta solución alternativa no sea recomendable en casos donde los nombres de usuario pueden superponerse entre dominios.

Por defecto: No establecido

Consulte la página man prctl:PR_SET_DUMPABLE en Linux o procctl:PROC_TRACE_CTL en FreeBSD para obtener detalles.

Tenga en cuenta que esta configuración no tiene ningún efecto en 'ldap_child', 'krb5_child' y 'sssd_pam', ya que esos binarios privilegiados pueden tener una copia de los datos del keytab del host en la memoria y su comportamiento en este sentido se rige por la configuración del sistema /proc/sys/fs/suid_dumpable.

Por defecto: true

OFFLINE CONFIGURATION OPTIONS

These options control the behavior of SSSD when it is offline.

offline_timeout (integer)

The time in seconds before SSSD attempts to go back online after a previous attempt has failed. After each unsuccessful attempt to go online, the new interval is recalculated by the following:

new_delay = Minimum(old_delay * 2, offline_timeout_max) + random[0...offline_timeout_random_offset]

The offline_timeout default value is 60. The offline_timeout_max default value is 3600. The offline_timeout_random_offset default value is 30. The end result is amount of seconds before next retry.

Note that the maximum length of each interval is defined by offline_timeout_max (apart of random part).

Default: 60

offline_timeout_max (integer)

Controls by how much the time between attempts to go online can be incremented following unsuccessful attempts to go online.

A value of 0 disables the incrementing behaviour.

The value of this parameter should be set in correlation to offline_timeout parameter value.

With offline_timeout set to 60 (default value) there is no point in setting offlinet_timeout_max to less than 120 as it will saturate instantly. General rule here should be to set offline_timeout_max to at least 4 times offline_timeout.

Although a value between 0 and offline_timeout may be specified, it has the effect of overriding the offline_timeout value so is of little use.

Default: 3600

offline_timeout_random_offset (integer)

When SSSD is in offline mode it keeps probing backend servers in specified time intervals:

new_delay = Minimum(old_delay * 2, offline_timeout_max) + random[0...offline_timeout_random_offset]

This parameter controls the value of the random offset used for the above equation. Final random_offset value will be random number in range:

[0 - offline_timeout_random_offset]

A value of 0 disables the random offset addition.

Default: 30

responder_idle_timeout

This option specifies the number of seconds that an SSSD responder process can be up without being used. This value is limited in order to avoid resource exhaustion on the system. The minimum acceptable value for this option is 60 seconds. Setting this option to 0 (zero) means that no timeout will be set up to the responder. This option only has effect when SSSD is built with systemd support and when services are either socket or D-Bus activated.

Default: 300

cache_first

This option specifies whether the responder should query all caches before querying the Data Providers.

Default: true

NSS configuration options

These options can be used to configure the Name Service Switch (NSS) service.

enum_cache_timeout (integer)

How many seconds should nss_sss cache enumerations (requests for info about all users)

Default: 120

entry_cache_nowait_percentage (integer)

The entry cache can be set to automatically update entries in the background if they are requested beyond a percentage of the entry_cache_timeout value for the domain.

For example, if the domain's entry_cache_timeout is set to 30s and entry_cache_nowait_percentage is set to 50 (percent), entries that come in after 15 seconds past the last cache update will be returned immediately, but the SSSD will go and update the cache on its own, so that future requests will not need to block waiting for a cache update.

Valid values for this option are 0-99 and represent a percentage of the entry_cache_timeout for each domain. For performance reasons, this percentage will never reduce the nowait timeout to less than 10 seconds. (0 disables this feature)

Default: 50

entry_negative_timeout (integer)

Specifies for how many seconds nss_sss should cache negative cache hits (that is, queries for invalid database entries, like nonexistent ones) before asking the back end again.

Default: 15

filter_users, filter_groups (string)

Exclude certain users or groups from being fetched from the sss NSS database. This is particularly useful for system accounts. This option can also be set per-domain or include fully-qualified names to filter only users from the particular domain or by a user principal name (UPN).

NOTE: The filter_groups option doesn't affect inheritance of nested group members, since filtering happens after they are propagated for returning via NSS. E.g. a group having a member group filtered out will still have the member users of the latter listed.

Default: root

filter_users_in_groups (bool)

If you want filtered user still be group members set this option to false.

Default: true

override_homedir (string)

Override the user's home directory. You can either provide an absolute value or a template. In the template, the following sequences are substituted:

%u

login name

%U

UID number

%d

domain name

%f

fully qualified user name (user@domain)

%l

The first letter of the login name.

%P

UPN - User Principal Name (name@REALM)

%o

The homedir value that is defined in the directory of the identity provider.

This substitution is designed to be used in an IPA-AD trust scenario. If this substitution is used for the subdomain_homedir option, it propagates the home directory value from the AD domain to the IPA clients. In this scenario, the option must be set in the SSSD configuration on the IPA server where SSSD is running in server mode.

%h

The path defined for the homedir directory attribute of the identity provider, but in lower case. For details of use, see %o.

%H

The value of configure option homedir_substring.

%%

a literal '%'

This option can also be set per-domain.

example:

override_homedir = /home/%u

Default: Not set (SSSD will use the value retrieved from LDAP)

Please note, the home directory from a specific override for the user, either locally (see sss_override(8)) or centrally managed IPA id-overrides, has a higher precedence and will be used instead of the value given by override_homedir.

homedir_substring (string)

The value of this option will be used in the expansion of the override_homedir option if the template contains the format string %H. An LDAP directory entry can directly contain this template so that this option can be used to expand the home directory path for each client machine (or operating system). It can be set per-domain or globally in the [nss] section. A value specified in a domain section will override one set in the [nss] section.

Default: /home

fallback_homedir (string)

Set a default template for a user's home directory if one is not specified explicitly by the domain's data provider.

The available values for this option are the same as for override_homedir.

example:

fallback_homedir = /home/%u

Default: not set (no substitution for unset home directories)

override_shell (string)

Override the login shell for all users. This option supersedes any other shell options if it takes effect and can be set either in the [nss] section or per-domain.

Default: not set (SSSD will use the value retrieved from LDAP)

allowed_shells (string)

Restrict user shell to one of the listed values. The order of evaluation is:

1. If the shell is present in “/etc/shells”, it is used.

2. If the shell is in the allowed_shells list but not in “/etc/shells”, use the value of the shell_fallback parameter.

3. If the shell is not in the allowed_shells list and not in “/etc/shells”, a nologin shell is used.

The wildcard (*) can be used to allow any shell.

The (*) is useful if you want to use shell_fallback in case that user's shell is not in “/etc/shells” and maintaining list of all allowed shells in allowed_shells would be to much overhead.

An empty string for shell is passed as-is to libc.

The “/etc/shells” is only read on SSSD start up, which means that a restart of the SSSD is required in case a new shell is installed.

Default: Not set. The user shell is automatically used.

vetoed_shells (string)

Replace any instance of these shells with the shell_fallback

shell_fallback (string)

The default shell to use if an allowed shell is not installed on the machine.

Default: /bin/sh

pam_gssapi_check_upn

Si es Verdadero, SSSD requerirá que el principal de usuario Kerberos que se autenticó exitosamente a través de GSSAPI pueda asociarse con el usuario que se está autenticando. La autenticación fallará si la verificación falla.

Nota: Esta opción también se puede establecer por dominio, lo que anula el valor en la sección [pam]. También se puede establecer para un dominio de confianza, lo que anula el valor en la sección del dominio.

Predeterminado: Verdadero

Cada elemento de la lista puede ser un nombre de indicador de autenticación o un par "servicio:indicador". Los indicadores no prefijados con el nombre del servicio PAM serán requeridos para acceder a cualquier servicio PAM configurado para ser usado con pam_gssapi_services. Una lista resultante de indicadores por servicio PAM se compara luego con los indicadores en el ticket Kerberos durante la autenticación por pam_sss_gss.so. Cualquier indicador del ticket que coincida con la lista resultante de indicadores para el servicio PAM concederá acceso. Si ninguno de los indicadores de la lista coincide, se denegará el acceso. Si la lista resultante de indicadores para el servicio PAM está vacía, la verificación no impedirá el acceso.

Para deshabilitar la verificación de indicadores de autenticación GSSAPI, establece esta opción a "-" (guion). Para deshabilitar la verificación para un servicio PAM específico, agrega "servicio:-".

Nota: Esta opción también se puede establecer por dominio, lo que anula el valor en la sección [pam]. También se puede establecer para un dominio de confianza, lo que anula el valor en la sección del dominio.

•pkinit -- preautenticación usando certificados X.509 -- ya sea almacenados en archivos o en tarjetas inteligentes.
•hardened -- preautenticación SPAKE o cualquier preautenticación envuelta en un canal FAST.
•radius -- preautenticación con la ayuda de un servidor RADIUS.
•otp -- preautenticación usando autenticación integrada de dos factores (2FA o contraseña de un solo uso, OTP) en IPA.
•idp -- preautenticación usando un proveedor de identidad externo.

Ejemplo: para requerir acceso a servicios SUDO solo para usuarios que obtuvieron sus tickets Kerberos con preautenticación de certificado de X.509 (PKINIT), establece

El respondedor PAC trabaja junto con el plugin de datos de autorización para MIT Kerberos sssd_pac_plugin.so y un proveedor de subdominio. El plugin envía los datos PAC durante una autenticación GSSAPI al respondedor PAC. El proveedor de subdominio recopila el SID del dominio y los rangos de ID del dominio al que está unido el cliente y de los dominios de confianza remotos desde el controlador de dominio local. Si el PAC se decodifica y evalúa, se realizan algunas de las siguientes operaciones:

•Si el usuario remoto no existe en la caché, se crea. La UID se determina con la ayuda del SID, los dominios de confianza tendrán UPGs y la GID tendrá el mismo valor que la UID. El directorio personal se establece según el parámetro subdomain_homedir. El shell estará vacío por defecto, es decir, se usarán los valores predeterminados del sistema, pero se puede anular con el parámetro default_shell.
•Si hay SIDs de gr

OUPS FROM DOMAINS SSSD

conoce, al usuario se le agregará a esos grupos.

Estas opciones se pueden usar para configurar el respondedor PAC.

allowed_uids (string)

Especifica la lista separada por comas de valores de UID o nombres de usuario que tienen permitido acceder al respondedor PAC. Los nombres de usuario se resuelven a UIDs al inicio.

Por defecto: 0, sssd (solo el root y los usuarios del servicio SSSD tienen permitido acceder al respondedor PAC)

Tenga en cuenta que los valores por defecto se sobrescribirán con esta opción. Si todavía desea permitir que el usuario root y/o 'sssd' accedan al respondedor PAC, lo cual sería el caso típico, debe agregarlos explícitamente a la lista de UIDs permitidos.

pac_lifetime (integer)

Tiempo de vida de la entrada PAC en segundos. Mientras el PAC sea válido, los datos del PAC se pueden utilizar para determinar las membresías de grupo de un usuario.

Por defecto: 300

pac_check (string)

Aplica verificaciones adicionales al PAC del ticket Kerberos que está disponible en dominios de Active Directory y FreeIPA, si están configurados. Tenga en cuenta que la validación del ticket Kerberos debe estar habilitada para poder verificar el PAC, es decir, la opción krb5_validate debe estar configurada en 'True', que es el valor por defecto para los proveedores IPA y AD. Si krb5_validate está configurado en 'False', las verificaciones del PAC se omitirán.

Las siguientes opciones se pueden usar solas o en una lista separada por comas:

no_check

El PAC no debe estar presente y, aunque esté presente, no se realizarán verificaciones adicionales.

pac_present

El PAC debe estar presente en el ticket de servicio que SSSD solicitará con la ayuda del TGT del usuario. Si el PAC no está disponible, la autenticación fallará.

check_upn

Si el PAC está presente, verifique si la información del nombre principal del usuario (UPN) es coherente.

check_upn_allow_missing

Esta opción debe usarse junto con 'check_upn' y maneja el caso en que se establece un UPN en el lado del servidor pero SSSD no lo lee. El ejemplo típico es un dominio FreeIPA donde 'ldap_user_principal' está configurado en un nombre de atributo inexistente. Esto se hizo típicamente para solucionar problemas en el manejo de principales empresariales. Pero esto se ha solucionado desde hace bastante tiempo y FreeIPA puede manejar principales empresariales perfectamente y ya no es necesario configurar 'ldap_user_principal'.

Actualmente, esta opción está configurada por defecto para evitar regresiones en dichos entornos. Se agregará un mensaje de registro al registro del sistema y al registro de depuración de SSSD en caso de que se encuentre un UPN en el PAC pero no en la caché de SSSD. Para evitar este mensaje de registro, lo mejor sería evaluar si la opción 'ldap_user_principal' se puede eliminar. Si esto no es posible, eliminar 'check_upn' omitirá la prueba y evitará el mensaje de registro.

upn_dns_info_present

El PAC debe contener el buffer UPN-DNS-INFO, implica 'check_upn'.

check_upn_dns_info_ex

Si el PAC está presente y la extensión del buffer UPN-DNS-INFO está disponible, verifique si la información en la extensión es coherente.

upn_dns_info_ex_present

El PAC debe contener la extensión del buffer UPN-DNS-INFO, implica 'check_upn_dns_info_ex', 'upn_dns_info_present' y 'check_upn'.

Por defecto: no_check (proveedor AD e IPA 'check_upn, check_upn_allow_missing, check_upn_dns_info_ex')

Opciones de configuración de grabación de sesión

La grabación de sesión funciona en conjunto con tlog-rec-session(8), una parte del paquete tlog, para registrar lo que los usuarios ven y escriben cuando inician sesión en una terminal de texto. Ver también sssd-session-recording(5).

Estas opciones se pueden usar para configurar la grabación de sesión.

scope (string)

Una de las siguientes cadenas que especifica el alcance de la grabación de sesión:

"none"

No se graba ningún usuario.

"some"

Se graban los usuarios/grupos especificados por las opciones users y groups.

"all"

Se graban todos los usuarios.

Por defecto: "none"

users (string)

Una lista de usuarios separada por comas a los que se les debe habilitar la grabación de sesión. Coincide con los nombres de usuario devueltos por NSS. Es decir, después del posible reemplazo de espacios, cambios de mayúsculas, etc.

Por defecto: Vacío. No coincide con ningún usuario.

groups (string)

Una lista de grupos separada por comas, cuyos miembros deben tener habilitada la grabación de sesión. Coincide con los nombres de grupo devueltos por NSS. Es decir, después del posible reemplazo de espacios, cambios de mayúsculas, etc.

NOTA: usar esta opción (tenerla configurada en cualquier valor) tiene un costo de rendimiento considerable, ya que cada solicitud no cacheada para un usuario requiere recuperar y comparar los grupos de los que el usuario es miembro.

Por defecto: Vacío. No coincide con ningún grupo.

exclude_users (string)

Una lista de usuarios separada por comas que se excluirán de la grabación, solo aplicable con 'scope=all'.

Por defecto: Vacío. No se excluyen usuarios.

exclude_groups (string)

Una lista de grupos separada por comas, cuyos miembros deben ser excluidos de la grabación. Solo aplicable con 'scope=all'.

NOTA: usar esta opción (tenerla configurada en cualquier valor) tiene un costo de rendimiento considerable, ya que cada solicitud no cacheada para un usuario requiere recuperar y comparar los grupos de los que el usuario es miembro.

Por defecto: Vacío. No se excluyen grupos.

SECCIONES DE DOMINIO

Estas opciones de configuración pueden estar presentes en una sección de configuración de dominio, es decir, en una sección llamada “[domain/NAME]”

enabled

Habilita o deshabilita explícitamente el dominio. Si es “true”, el dominio está siempre “habilitado”. Si es “false”, el dominio está siempre “deshabilitado”. Si esta opción no está configurada, el dominio se habilita solo si está listado en la opción domains en la sección “[sssd]”.

domain_type (string)

Especifica si el dominio está destinado a ser utilizado por clientes con conocimiento de POSIX como Name Service Switch o por aplicaciones que no necesitan que los datos POSIX estén presentes o generados. Solo los objetos de los dominios POSIX están disponibles para las interfaces y utilidades del sistema operativo.

Los valores permitidos para esta opción son “posix” y “application”.

Los dominios POSIX son accesibles por todos los servicios. Los dominios de aplicación solo son accesibles desde el respondedor InfoPipe (ver sssd-ifp(5)) y el respondedor PAM.

NOTA: Los dominios de aplicación actualmente están bien probados solo con “id_provider=ldap”.

Para una forma sencilla de configurar dominios no POSIX, consulte la sección “Dominios de aplicación”.

Por defecto: posix

min_id,max_id (integer)

Límites de UID y GID para el dominio. Si un dominio contiene una entrada que está fuera de estos límites, se ignora.

Para los usuarios, esto afecta al límite de GID primario. El usuario no será devuelto a NSS si el UID o el GID primario están fuera del rango. Para las membresías de grupo no primarias, las que estén dentro del rango se informarán como se espera.

Estos límites de ID afectan incluso al guardado de entradas en la caché, no solo a su devolución por nombre o ID.

Por defecto: 1 para min_id, 0 (sin límite) para max_id

enumerate (bool)

Determina si un dominio puede ser enumerado, es decir, si el dominio puede listar todos los usuarios y grupos que contiene. Tenga en cuenta que no es necesario habilitar la enumeración para que se muestren los grupos secundarios. Este parámetro puede tener uno de los siguientes valores:

TRUE = Se enumeran usuarios y grupos

FALSE = No hay enumeraciones para este dominio

Por defecto: FALSE

Enumerar un dominio requiere que SSSD descargue y almacene TODAS las entradas de usuario y grupo del servidor remoto.

La función solo se admite para dominios con id_provider = ldap o id_provider = proxy.

Nota: Habilitar la enumeración tiene un impacto severo en el rendimiento de SSSD mientras la enumeración se ejecuta. Puede tardar hasta varios minutos después del inicio de SSSD para completar completamente las enumeraciones. Durante este tiempo, las solicitudes individuales de información irán directamente a LDAP, aunque puede ser lento, debido al pesado procesamiento de la enumeración. Guardar un gran número de entradas en la caché después de que la enumeración se complete también puede ser intensivo en CPU, ya que las membresías deben recalcularse. Esto puede hacer que el proceso “sssd_be” no responda o incluso sea reiniciado por el perro guardián interno.

Mientras se ejecuta la primera enumeración, las solicitudes de listas completas de usuarios o grupos pueden no devolver ningún resultado hasta que se completen.

Además, habilitar la enumeración puede aumentar el tiempo necesario para detectar la desconexión de la red, ya que se requieren tiempos de espera más largos para garantizar que las búsquedas de enumeración se completen con éxito. Para obtener más información, consulte las páginas man del id_provider específico en uso.

Por las razones citadas anteriormente, no se recomienda habilitar la enumeración, especialmente en entornos grandes.

Nota: el proveedor proxy se prueba con módulos de código abierto como 'libnss_files' y 'libnss_ldap'. Los módulos de terceros deben seguir el comportamiento documentado de los módulos nss para ser utilizados en esta configuración.

sssd-ldap sssd-ldap - LDAP provider for SSSD September 28, 2022 2.7.3
DESCRIPTION

The SSSD (System Security Services Daemon) is a service that provides access to identity and authentication remote resources. SSSD can cache credentials and user information locally, which allows users to log in even when the network is unavailable.

The sssd-ldap service is a provider for SSSD that retrieves user and group information from LDAP servers.

This man page describes the configuration options specific to the LDAP provider.

CONFIGURATION

The configuration of the SSSD LDAP provider is done in the /etc/sssd/sssd.conf file.

The LDAP provider can be configured in the section.

Example:

[domain/example.com] id_provider = ldap authselect_map = files sss ldap_uri = ldap://ldap.example.com ldap_search_base = dc=example,dc=com
OPTIONS

The following options are specific to the LDAP provider:

id_provider (string)

The provider which should handle identity and authentication related requests. Supported values are:

“ldap” to use the LDAP provider.

“proxy” to use the proxy provider.

“files” to use the files provider.

“ipa” to use the IPA provider.

“ad” to use the AD provider.

“none” disables the id provider.

Default: “ldap”

sudo_provider (string)

The provider which should handle sudo related requests. Supported values are:

“ldap” to load sudo rules from LDAP. See sssd-ldap(5) for more information on configuring LDAP.

“ipa” to load sudo rules from IPA.

“none” disables SUDO explicitly.

Default: The value of “id_provider” is used if it is set and can handle sudo requests.

The detailed instructions for configuration of sudo_provider are in the manual page sssd-sudo(5). There are many configuration options that can be used to adjust the behavior. Please refer to "ldap_sudo_*" in sssd-ldap(5).

NOTE: Sudo rules are periodically downloaded in the background unless the sudo provider is explicitly disabled. Set sudo_provider = None to disable all sudo-related activity in SSSD if you do not want to use sudo with SSSD at all.

selinux_provider (string)

The provider which should handle loading of selinux settings. Note that this provider will be called right after access provider ends. Supported selinux providers are:

“ipa” to load selinux settings from an IPA server. See sssd-ipa(5) for more information on configuring IPA.

“none” disallows fetching selinux settings explicitly.

Default: “id_provider” is used if it is set and can handle selinux loading requests.

subdomains_provider (string)

The provider which should handle fetching of subdomains. This value should be always the same as id_provider. Supported subdomain providers are:

“ipa” to load a list of subdomains from an IPA server. See sssd-ipa(5) for more information on configuring IPA.

“ad” to load a list of subdomains from an Active Directory server. See sssd-ad(5) for more information on configuring the AD provider.

“none” disallows fetching subdomains explicitly.

Default: The value of “id_provider” is used if it is set and can handle subdomain requests.

session_provider (string)

The provider which configures and manages user session related tasks. The only user session task currently provided is the integration with Fleet Commander, which works only with IPA. Supported session providers are:

“ipa” to allow performing user session related tasks.

“none” does not perform any kind of user session related tasks.

Default: “id_provider” is used if it is set and can perform session related tasks.

The autofs provider used for the domain. Supported autofs providers are:

“ldap” to load maps stored in LDAP. See sssd-ldap(5) for more information on configuring LDAP.

“ipa” to load maps stored in an IPA server. See sssd-ipa(5) for more information on configuring IPA.

“ad” to load maps stored in an AD server. See sssd-ad(5) for more information on configuring the AD provider.

re_expression (string)

Regular expression for this domain that describes how to parse the string containing user name and domain into these components. The "domain" can match either the SSSD configuration domain name, or, in the case of IPA trust subdomains and Active Directory domains, the flat (NetBIOS) name of the domain.

Default: “^((?P<name>.+)@(?P<domain>[^@]*)|(?P<name>[^@]+))$” which allows two different styles for user names:

•username

•username@domain.name

Default for the AD and IPA provider: “^(((?P<domain>[^\\]+)\\(?P<name>.+))|((?P<name>.+)@(?P<domain>[^@]+))|((?P<name>[^@\\]+)))$” which allows three different styles for user names:

•username

•username@domain.name

•domain\username

While the first two correspond to the general default the third one is introduced to allow easy integration of users from Windows domains.

The default re_expression uses the “@” character as a separator between the name and the domain. As a result of this setting the default does not accept the “@” character in short names (as it is allowed in Windows group names). If a user wishes to use short names with “@” they must create their own re_expression.

A printf(3)-compatible format that describes how to compose a fully qualified name from user name and domain name components.

The following expansions are supported:

%1$s

user name

%2$s

domain name as specified in the SSSD config file.

%3$s

domain flat name. Mostly usable for Active Directory domains, both directly configured or discovered via IPA trusts.

Default: “%1$s@%2$s”.

Default: True (False for AD provider)

subdomain_inherit (string)

Specifies a list of configuration parameters that should be inherited by a subdomain. Please note that only selected parameters can be inherited. Currently the following options can be inherited:

ldap_search_timeout

case_sensitive

Ejemplo:

subdomain_inherit = ldap_purge_cache_timeout

Predeterminado: ninguno

subdomain_homedir (cadena)

Utilice este directorio personal como valor predeterminado para todos los subdominios dentro de este dominio en la confianza de IPA AD. Consulte override_homedir para obtener información sobre los valores posibles. Además de esos, la expansión a continuación solo se puede utilizar con subdomain_homedir.

%F

nombre plano (NetBIOS) de un subdominio.

El valor puede ser anulado por la opción override_homedir.

Predeterminado: /home/%d/%u

realmd_tags (cadena)

Varias etiquetas almacenadas por el servicio de configuración de realmd para este dominio.

cached_auth_timeout (entero)

Especifica el tiempo en segundos desde la última autenticación en línea exitosa para la cual el usuario será autenticado usando credenciales almacenadas en caché mientras SSSD está en modo en línea. Si las credenciales son incorrectas, SSSD recurre a la autenticación en línea.

El valor de esta opción se hereda de todos los dominios de confianza. En el momento no es posible establecer un valor diferente por dominio de confianza.

El valor especial 0 implica que esta característica está deshabilitada.

Tenga en cuenta que si "cached_auth_timeout" es más largo que "pam_id_timeout", el backend podría ser llamado para manejar "initgroups".

Predeterminado: 0

local_auth_policy (cadena)

Política de métodos de autenticación locales. Algunos backends (es decir, LDAP, proveedor proxy) solo admiten la autenticación basada en contraseñas, mientras que otros pueden manejar la autenticación de tarjeta inteligente basada en PKINIT (AD, IPA), autenticación de dos factores (IPA) u otros métodos contra una instancia central. Por defecto en tales casos, la autenticación solo se realiza con los métodos compatibles con el backend. Con esta opción se pueden habilitar métodos adicionales que se evalúan y verifican localmente.

Hay tres valores posibles para esta opción: match, only, enable. "match" se usa para hacer coincidir los estados sin conexión y en línea para métodos Kerberos. "only" ignora los métodos en línea y solo ofrece los locales. enable permite definir explícitamente los métodos para la autenticación local. Como ejemplo, "enable:passkey" solo habilita passkey para la autenticación local. Múltiples valores de enable deben separarse con comas, como "enable:passkey, enable:smartcard"

La siguiente tabla muestra qué métodos de autenticación, si se configuran correctamente, están actualmente habilitados o deshabilitados para cada backend, con la política local_auth_policy predeterminada: "match"

local_auth_policy = match (predeterminado)
  Passkey Tarjeta Inteligente
IPA habilitado habilitado
AD deshabilitado habilitado
LDAP deshabilitado deshabilitado

Tenga en cuenta que si la autenticación local con tarjeta inteligente está habilitada y hay una tarjeta inteligente presente, la autenticación con tarjeta inteligente tendrá prioridad sobre los métodos de autenticación admitidos por el backend. Es decir, aparecerá un mensaje de solicitud de PIN en lugar de, por ejemplo, un mensaje de solicitud de contraseña.

El siguiente ejemplo de configuración permite a los usuarios locales autenticarse localmente utilizando cualquier método habilitado (es decir, tarjeta inteligente, passkey).

[domain/shadowutils]
id_provider = proxy
proxy_lib_name = files
auth_provider = none
local_auth_policy = only

Predeterminado: match

auto_private_groups (cadena)

Esta opción toma cualquiera de los tres valores disponibles:

true

Crea el grupo privado del usuario incondicionalmente a partir del número UID del usuario. El número GID se ignora en este caso.

NOTA: Debido a que el número GID y el grupo privado del usuario se infieren del número UID, no se admite tener múltiples entradas con el mismo número UID o GID con esta opción. En otras palabras, habilitar esta opción impone la unicidad en todo el espacio de ID.

false

Utiliza siempre el número GID principal del usuario. El número GID debe hacer referencia a un objeto de grupo en la base de datos LDAP.

hybrid

Se genera automáticamente un grupo principal para las entradas de usuario cuyos números UID y GID tienen el mismo valor y, al mismo tiempo, el número GID no corresponde a un objeto de grupo real en LDAP. Si los valores son los mismos, pero el GID principal en la entrada del usuario también lo utiliza un objeto de grupo, el GID principal del usuario se resuelve en ese objeto de grupo.

Si el UID y el GID de un usuario son diferentes, entonces el GID debe corresponder a una entrada de grupo; de lo contrario, el GID simplemente no se puede resolver.

Esta característica es útil para entornos que desean dejar de mantener objetos de grupo separados para los grupos privados de usuarios, pero también desean conservar los grupos privados de usuarios existentes.

Para los proveedores de ID basados en LDAP (LDAP, IPA y AD), el valor predeterminado para el dominio configurado suele ser False porque las fuentes tienen el concepto de grupo principal. El proveedor de ID IdP usa True porque los IdP típicamente no tienen grupos principales.

Para los subdominios, el valor predeterminado es False para los subdominios que utilizan ID POSIX asignados y True para los subdominios que utilizan mapeo automático de ID.

El valor de auto_private_groups se puede establecer por subdominio en una subsección, por ejemplo:

[domain/forest.domain/sub.domain]
auto_private_groups = false

o globalmente para todos los subdominios en la sección principal del dominio utilizando la opción subdomain_inherit:

[domain/forest.domain]
subdomain_inherit = auto_private_groups
auto_private_groups = false

Opciones válidas para dominios proxy.

proxy_pam_target (cadena)

El objetivo PAM del proxy al que se proxy.

Predeterminado: no establecido por defecto, tiene que tomar una configuración PAM existente o crear una nueva y agregar el nombre del servicio aquí. Como alternativa, puede habilitar la autenticación local con la opción local_auth_policy.

proxy_lib_name (cadena)

El nombre de la biblioteca NSS a utilizar en los dominios proxy. Las funciones NSS que se buscan en la biblioteca tienen la forma _nss_$(libName)_$(function), por ejemplo _nss_files_getpwent.

proxy_resolver_lib_name (cadena)

El nombre de la biblioteca NSS a utilizar para las búsquedas de hosts y redes en los dominios proxy. Las funciones NSS que se buscan en la biblioteca tienen la forma _nss_$(libName)_$(function), por ejemplo _nss_dns_gethostbyname2_r.

proxy_fast_alias (booleano)

Cuando se busca un usuario o grupo por nombre en el proveedor proxy, se realiza una segunda búsqueda por ID para "canonicalizar" el nombre en caso de que el nombre solicitado fuera un alias. Establecer esta opción en true haría que SSSD realizara la búsqueda de ID desde la caché por razones de rendimiento.

Predeterminado: false

proxy_max_children (entero)

Esta opción especifica el número de procesos hijos proxy pre-forked. Es útil para entornos SSSD de alta carga donde sssd puede quedarse sin ranuras de procesos hijos disponibles, lo que causaría algunos problemas debido a que las solicitudes se ponen en cola.

Predeterminado: 10

Dominios de aplicación

SSSD, con su interfaz D-Bus (ver sssd-ifp(5)) es atractivo para las aplicaciones como puerta de enlace a un directorio LDAP donde se almacenan usuarios y grupos. Sin embargo, a diferencia del despliegue tradicional de SSSD donde todos los usuarios y grupos tienen atributos POSIX o esos atributos se pueden inferir de los SID de Windows, en muchos casos los usuarios y grupos en el escenario de soporte de aplicaciones no tienen atributos POSIX. En lugar de configurar una sección "[domain/NAME]", el administrador puede configurar una sección "[application/NAME]" que internamente representa un dominio de tipo "application" que opcionalmente hereda la configuración de un dominio SSSD tradicional.

Tenga en cuenta que el dominio de aplicación aún debe estar explícitamente habilitado en el parámetro "domains" para que el orden de búsqueda entre el dominio de aplicación y su dominio hermano POSIX se establezca correctamente.

Parámetros del dominio de aplicación

inherit_from (cadena)

El dominio POSIX de SSSD del cual el dominio de aplicación hereda toda la configuración. El dominio de aplicación puede, además, agregar su propia configuración a la configuración de la aplicación que aumenta o anula la configuración del dominio "hermano".

Predeterminado: No establecido

El siguiente ejemplo ilustra el uso de un dominio de aplicación. En esta configuración, el dominio POSIX está conectado a un servidor LDAP y es utilizado por el sistema operativo a través del respondedor NSS. Además, el dominio de aplicación también solicita el atributo telephoneNumber, lo almacena como el atributo phone en la caché y hace que el atributo phone sea accesible a través de la interfaz D-Bus.

[sssd]
domains = appdom, posixdom
[ifp]
user_attributes = +phone
[domain/posixdom]
id_provider = ldap
ldap_uri = ldap://ldap.example.com
ldap_search_base = dc=example,dc=com
[application/appdom]
inherit_from = posixdom
ldap_user_extra_attrs = phone:telephoneNumber

SECCION DE MAPEO DE CERTIFICADOS

Para permitir la autenticación con tarjetas inteligentes y certificados, SSSD debe ser capaz de mapear certificados a usuarios. Esto se puede hacer añadiendo el certificado completo al objeto LDAP del usuario o a una anulación local. Si bien el uso del certificado completo es necesario para utilizar la función de autenticación con tarjeta inteligente de SSH (consulte sss_ssh_authorizedkeys(8) para más detalles), puede ser engorroso o incluso imposible hacerlo para el caso general en el que los servicios locales utilizan PAM para la autenticación.

Para que el mapeo sea más flexible, se añadieron reglas de mapeo y coincidencia a SSSD (consulte sss-certmap(5) para más detalles).

Una regla de mapeo y coincidencia se puede añadir a la configuración de SSSD en su propia sección con un nombre como “[certmap/NOMBRE_DEL_DOMINIO/NOMBRE_DE_LA_REGLA]”. En esta sección se permiten las siguientes opciones:

matchrule (cadena)

Solo se procesarán los certificados de la tarjeta inteligente que coincidan con esta regla, todas las demás se ignorarán.

Predeterminado: KRB5:<EKU>clientAuth, es decir, solo certificados que tengan el Uso Extendido de Clave "clientAuth"

maprule (cadena)

Define cómo se encuentra el usuario para un certificado dado.

Predeterminado:

•LDAP:(userCertificate;binary={cert!bin}) para proveedores basados en LDAP como "ldap", "AD" o "ipa".
•Si maprule no está configurado y el proveedor es "proxy", se asume que el nombre RULE_NAME es el nombre del usuario que coincide.

domains (cadena)

Lista separada por comas de nombres de dominio a los que se aplicará la regla. Por defecto, una regla solo es válida en el dominio configurado en sssd.conf. Si el proveedor admite subdominios, esta opción se puede utilizar para añadir la regla también a los subdominios.

Predeterminado: el dominio configurado en sssd.conf

priority (entero)

Valor entero sin signo que define la prioridad de la regla. Cuanto mayor sea el número, menor será la prioridad. "0" representa la prioridad más alta, mientras que "4294967295" es la más baja.

Predeterminado: la prioridad más baja

SECCION DE CONFIGURACION DE SOLICITUDES

Si existe un archivo especial (/var/lib/sss/pubconf/pam_preauth_available), el módulo PAM pam_sss de SSSD le pedirá a SSSD que determine qué métodos de autenticación están disponibles para el usuario que intenta iniciar sesión. Según los resultados, pam_sss solicitará al usuario las credenciales apropiadas.

Con el creciente número de métodos de autenticación y la posibilidad de que haya varios para un solo usuario, la heurística utilizada por pam_sss para seleccionar la solicitud puede no ser adecuada para todos los casos de uso. Las siguientes opciones deberían proporcionar una mayor flexibilidad aquí.

Cada método de autenticación compatible tiene su propia subsección de configuración bajo "[prompting/...]". Actualmente hay:

[prompting/password]

para configurar la solicitud de contraseña, las opciones permitidas son:

password_prompt

para cambiar la cadena de la solicitud de contraseña

[prompting/2fa]

para configurar la solicitud de autenticación de dos factores, las opciones permitidas son:

first_prompt

para cambiar la cadena de la solicitud del primer factor

second_prompt

para cambiar la cadena de la solicitud del segundo factor

single_prompt

valor booleano, si es Verdadero, solo habrá una única solicitud utilizando el valor de first_prompt, donde se espera que ambos factores se introduzcan como una única cadena. Tenga en cuenta que ambos factores deben introducirse aquí, incluso si el segundo factor es opcional.

Si el segundo factor es opcional y se debe poder iniciar sesión solo con la contraseña o con ambos factores, se debe utilizar la solicitud en dos pasos.

Algunos clientes, como SSH con 'PasswordAuthentication yes', generan sus propias solicitudes y no utilizan las solicitudes proporcionadas por SSSD u otros módulos PAM. Además, para SSH con PasswordAuthentication, si la autenticación de dos factores está disponible, SSSD espera que las credenciales introducidas por el usuario en la solicitud de contraseña de SSH siempre sean los dos factores en una única cadena, incluso si la autenticación de dos factores es opcional.

[prompting/passkey]

para configurar la solicitud de autenticación de clave de acceso, las opciones permitidas son:

interactive

valor booleano, si es Verdadero, muestra un mensaje y espera antes de probar la presencia de un dispositivo de clave de acceso. Se recomienda si su dispositivo no tiene un disparador táctil.

interactive_prompt

para cambiar el mensaje de la solicitud interactiva.

touch

valor booleano, si es Verdadero, muestra un mensaje para recordar al usuario que toque el dispositivo.

touch_prompt

para cambiar el mensaje de la solicitud táctil.

Es posible añadir una subsección para servicios PAM específicos, por ejemplo, "[prompting/password/sshd]" para cambiar individualmente la solicitud para ese servicio.

NAME

sssd.conf — sssd configuration file

SYNOPSIS

User and system-wide configuration data for the System Security Services Daemon (SSSD) is located in /etc/sssd/sssd.conf.

DESCRIPTION

The SSSD configuration file is divided into several sections. The first section, marked with `[domain/]`, defines the parameters for a specific domain. The second section, `[sssd]`, specifies global options. The third section, `[nss]`, specifies options for the Name Service Switch (NSS) module. The fourth section, `[pam]`, specifies options for the Pluggable Authentication Modules (PAM) module. The fifth section, `[secrets]`, contains sensitive information such as keys and passwords.

The file is a INI-style text file with sections denoted by square brackets. Each section contains key-value pairs. Lines starting with '#' or ';' are comments.

EXAMPLES

```ini [sssd] config_file_version = 2 services = nss, pam ```

```ini [nss] filter_users = root filter_groups = root ```

```ini [pam] pam_show_passwords = false ```

```ini [domain/example.com] id = example.com id_type = ldap auth_provider = ldap auth_realm = EXAMPLE.COM ldap_uri = ldap://ldap.example.com ldap_search_base = dc=example,dc=com ldap_id_use_start_tls = true ldap_tls_reqcert = demand ldap_tls_cacert = /etc/pki/tls/certs/ca-bundle.crt ```

SECTIONS

_**[sssd]**_

Global options for the SSSD daemon.

_**[nss]**_

Options for the SSSD Name Service Switch (NSS) module.

_**[pam]**_

Options for the SSSD Pluggable Authentication Modules (PAM) module.

_**[secrets]**_

Options for storing sensitive information, such as keys and passwords. This section is optional and is typically used for advanced configurations.

_**[domain/]**_

Options for a specific domain. The `` should be replaced with the actual domain name, for example, `[domain/example.com]`.

OPTIONS

The following options are available:

_**config_file_version**_

Specifies the version of the configuration file format. The default is 1. This option should be set to 2 for newer configurations.

_**services**_

A comma-separated list of services to be enabled. Possible values are `nss`, `pam`, `be` (basic enumeration), `sudo`, `graph`. The default is `nss, pam`.

_**domains**_

A comma-separated list of domains to be used. This option is deprecated and has been replaced by the `[domain/]` sections.

_**debug_level**_

Specifies the debug level for SSSD. The default is `0` (no debugging).

_**log_file**_

Specifies the path to the SSSD log file. The default is `/var/log/sssd.log`.

_**reap**_

If set to `true`, SSSD will reap dead child processes. The default is `true`.

_**fd_limit**_

Specifies the maximum number of file descriptors that SSSD can use. The default is `1024`.

_**max_idlen**_

Specifies the maximum length of user and group IDs. The default is `32`.

_**filter_users**_

A comma-separated list of users to be filtered out. These users will not be accessible through SSSD. The default is an empty list.

_**filter_groups**_

A comma-separated list of groups to be filtered out. These groups will not be accessible through SSSD. The default is an empty list.

_**ldap_uri**_

Specifies the URI of the LDAP server. For example, `ldap://ldap.example.com` or `ldaps://ldap.example.com`.

_**ldap_search_base**_

Specifies the base DN for searching users and groups in LDAP. For example, `dc=example,dc=com`.

_**ldap_id_use_start_tls**_

If set to `true`, SSSD will use Start-TLS to encrypt the LDAP connection. The default is `false`.

_**ldap_tls_reqcert**_

Specifies the certificate verification level for TLS/SSL connections. Possible values are `never`, `allow`, `try`, `demand`. The default is `demand`.

_**ldap_tls_cacert**_

Specifies the path to the CA certificate file for verifying the LDAP server's certificate. The default is `/etc/pki/tls/certs/ca-bundle.crt`.
