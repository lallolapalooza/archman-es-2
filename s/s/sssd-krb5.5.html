NOMBRE

sssd-krb5 - Proveedor Kerberos de SSSD

DESCRIPCIÓN

Esta página del manual describe la configuración del backend de autenticación Kerberos 5 para sssd(8). Para una referencia de sintaxis detallada, consulte la sección “FORMATO DE ARCHIVO” de la página del manual de sssd.conf(5).

El backend de autenticación Kerberos 5 contiene proveedores de autenticación y cambio de contraseña (chpass). Debe combinarse con un proveedor de identidad para funcionar correctamente (por ejemplo, id_provider = ldap). Parte de la información requerida por el backend de autenticación Kerberos 5 debe ser proporcionada por el proveedor de identidad, como el Nombre Principal de Usuario (UPN) de Kerberos. La configuración del proveedor de identidad debe tener una entrada para especificar el UPN. Consulte la página del manual del proveedor de identidad aplicable para obtener detalles sobre cómo configurarlo.

Este backend también proporciona control de acceso basado en el archivo .k5login en el directorio personal del usuario. Vea k5login(5) para más detalles. Tenga en cuenta que un archivo .k5login vacío denegará todo acceso a este usuario. Para activar esta función, use 'access_provider = krb5' en su configuración de SSSD.

En caso de que el UPN no esté disponible en el backend de identidad, sssd construirá un UPN utilizando el formato nombredeusuario@dominio_krb5.

OPCIONES DE CONFIGURACIÓN

Si se utiliza el módulo de autenticación krb5 en un dominio SSSD, se deben usar las siguientes opciones. Consulte la página del manual de sssd.conf(5), sección “SECCIONES DE DOMINIO”, para obtener detalles sobre la configuración de un dominio SSSD.

krb5_server, krb5_backup_server (cadena)

Especifica la lista separada por comas de direcciones IP o nombres de host de los servidores Kerberos a los que SSSD debe conectarse, en orden de preferencia. Para más información sobre la conmutación por error (failover) y la redundancia de servidores, consulte la sección “CONMUTACIÓN POR ERROR”. Se puede añadir un número de puerto opcional (precedido por dos puntos) a las direcciones o nombres de host. Si está vacío, el descubrimiento de servicios está habilitado; para más información, consulte la sección “DESCUBRIMIENTO DE SERVICIOS”.

Al usar el descubrimiento de servicios para servidores KDC o kpasswd, SSSD primero busca entradas DNS que especifican _udp como protocolo y recurre a _tcp si no encuentra ninguna.

Esta opción se llamaba “krb5_kdcip” en versiones anteriores de SSSD. Aunque el nombre heredado se reconoce por el momento, se recomienda a los usuarios migrar sus archivos de configuración para usar “krb5_server” en su lugar.

krb5_realm (cadena)

El nombre del dominio Kerberos. Esta opción es obligatoria y debe especificarse.

krb5_kpasswd, krb5_backup_kpasswd (cadena)

Si el servicio de cambio de contraseña no se está ejecutando en el KDC, se pueden definir servidores alternativos aquí. Se puede añadir un número de puerto opcional (precedido por dos puntos) a las direcciones o nombres de host.

Para más información sobre la conmutación por error y la redundancia de servidores, consulte la sección “CONMUTACIÓN POR ERROR”. NOTA: Incluso si no quedan más servidores kpasswd para intentar, el backend no se cambia a modo sin conexión si la autenticación contra el KDC sigue siendo posible.

Por defecto: Usar el KDC

krb5_ccachedir (cadena)

Directorio para almacenar las cachés de credenciales. Todas las secuencias de sustitución de krb5_ccname_template también se pueden usar aquí, excepto %d y %P. El directorio se crea como privado y es propiedad del usuario, con permisos establecidos en 0700.

Por defecto: /tmp

krb5_ccname_template (cadena)

Ubicación de la caché de credenciales del usuario. Actualmente se admiten tres tipos de caché de credenciales: “FILE”, “DIR” y “KEYRING:persistent”. La caché se puede especificar como TIPO:RESIDUAL, o como una ruta absoluta, que implica el tipo “FILE”. En la plantilla, se sustituyen las siguientes secuencias:

%u

nombre de inicio de sesión

%U

UID de inicio de sesión

%p

nombre principal

%r

nombre del dominio

%h

directorio personal

%d

valor de krb5_ccachedir

%P

el ID de proceso del cliente SSSD

%%

un '%' literal

Si la plantilla termina en 'XXXXXX', mkstemp(3) se utiliza para crear un nombre de archivo único de forma segura.

Al usar tipos KEYRING, el único mecanismo admitido es “KEYRING:persistent:%U”, que utiliza el keyring del kernel de Linux para almacenar credenciales por UID. Esta es también la opción recomendada, ya que es el método más seguro y predecible.

El valor por defecto para el nombre de la caché de credenciales se obtiene del perfil almacenado en el archivo de configuración krb5.conf del sistema en la sección [libdefaults]. El nombre de la opción es default_ccache_name. Consulte el párrafo EXPANSION DE PARÁMETROS de krb5.conf(5) para obtener información adicional sobre el formato de expansión definido por krb5.conf.

NOTA: Tenga en cuenta que la plantilla de expansión de caché de libkrb5 de krb5.conf(5) utiliza secuencias de expansión diferentes a las de SSSD.

Por defecto: (de libkrb5)

krb5_keytab (cadena)

La ubicación de la keytab a utilizar al validar las credenciales obtenidas de los KDC.

Por defecto: Keytab del sistema, normalmente /etc/krb5.keytab

krb5_store_password_if_offline (booleano)

Almacena la contraseña del usuario si el proveedor está sin conexión y la utiliza para solicitar un TGT cuando el proveedor vuelve a estar en línea.

NOTA: esta función solo está disponible en Linux. Las contraseñas almacenadas de esta manera se guardan en texto plano en el keyring del kernel y son potencialmente accesibles por el usuario root (con dificultad).

Por defecto: falso

krb5_use_fast (cadena)

Habilita el túnel seguro de autenticación flexible (FAST) para la preautenticación Kerberos. Se admiten las siguientes opciones:

never usa FAST. Esto equivale a no establecer esta opción en absoluto.

try intenta usar FAST. Si el servidor no admite FAST, continúa la autenticación sin él.

demand exige usar FAST. La autenticación falla si el servidor no requiere fast.

Por defecto: no establecido, es decir, FAST no se utiliza.

NOTA: se requiere una keytab o soporte para PKINIT anónimo para usar FAST.

NOTA: SSSD solo admite FAST con MIT Kerberos versión 1.8 y posteriores. Si SSSD se utiliza con una versión anterior de MIT Kerberos, el uso de esta opción es un error de configuración.

krb5_fast_principal (cadena)

Especifica el principal del servidor a utilizar para FAST.

krb5_fast_use_anonymous_pkinit (booleano)

Si se establece en verdadero, intenta usar PKINIT anónimo en lugar de una keytab para obtener la credencial requerida para FAST. La opción krb5_fast_principal se ignora en este caso.

Por defecto: falso

krb5_use_kdcinfo (booleano)

Especifica si SSSD debe indicar a las bibliotecas Kerberos qué dominio y qué KDCs usar. Esta opción está activada por defecto; si la deshabilita, deberá configurar la biblioteca Kerberos utilizando el archivo de configuración krb5.conf(5).

Consulte la página del manual de sssd_krb5_locator_plugin(8) para obtener más información sobre el plugin localizador.

Por defecto: verdadero

krb5_kdcinfo_lookahead (cadena)

Cuando krb5_use_kdcinfo se establece en verdadero, puede limitar la cantidad de servidores que se pasan a sssd_krb5_locator_plugin(8). Esto puede ser útil cuando se descubren demasiados servidores utilizando registros SRV.

La opción krb5_kdcinfo_lookahead contiene dos números separados por dos puntos. El primer número representa el número de servidores primarios utilizados y el segundo número especifica el número de servidores de respaldo.

Por ejemplo, 10:0 significa que se pasarán hasta 10 servidores primarios a sssd_krb5_locator_plugin(8) pero ningún servidor de respaldo.

Por defecto: 3:1

krb5_use_enterprise_principal (booleano)

Especifica si el principal del usuario debe tratarse como empresarial

Este sitio no está asociado de ninguna forma con Arch Linux ni afiliado a este proyecto. El contenido es únicamente una traducción de las páginas del manual de Arch publicadas en man.archlinux.org.

principal. Véase la sección 5 de RFC 6806 para más detalles sobre principales empresariales.

Predeterminado: falso (proveedor AD: verdadero)

El proveedor IPA establecerá la opción a 'verdadero' si detecta que el servidor es capaz de manejar principales empresariales y la opción no se establece explícitamente en el archivo de configuración.

krb5_use_subdomain_realm (booleano)

Especifica el uso de reinos de subdominios para la autenticación de usuarios de dominios de confianza. Esta opción se puede establecer a 'verdadero' si se utilizan principales empresariales con upnSuffixes que no son conocidos en los KDC del dominio padre. Si la opción se establece a 'verdadero', SSSD intentará enviar la solicitud directamente a un KDC del dominio de confianza del que proviene el usuario.

Predeterminado: falso

krb5_map_user (cadena)

La lista de mapeos se proporciona como una lista separada por comas de pares “nombredeusuario:primario” donde “nombredeusuario” es un nombre de usuario UNIX y “primario” es la parte de usuario de un principal Kerberos. Este mapeo se utiliza cuando el usuario se autentica utilizando “auth_provider = krb5”.

ejemplo:

krb5_realm = REALM
krb5_map_user = joe:juser,dick:richard

“joe” y “dick” son nombres de usuario UNIX y “juser” y “richard” son los primarios de los principales Kerberos. Para el usuario “joe” resp. “dick”, SSSD intentará hacer kinit como “juser@REALM” resp. “richard@REALM”.

Predeterminado: no establecido

krb5_auth_timeout (entero)

Tiempo de espera en segundos después de que una solicitud de autenticación en línea o una solicitud de cambio de contraseña sea abortada. Si es posible, la solicitud de autenticación continúa sin conexión.

Predeterminado: 6

krb5_validate (booleano)

Verifica con la ayuda de krb5_keytab si el TGT obtenido no ha sido falsificado. La tabla de claves se verifica secuencialmente, y la primera entrada con un reino coincidente se utiliza para la validación. Si ninguna entrada coincide con el reino, se utiliza la última entrada en la tabla de claves. Este proceso se puede utilizar para validar entornos que utilizan confianza entre reinos colocando la entrada apropiada de la tabla de claves como la última entrada o la única entrada en el archivo de tabla de claves.

Predeterminado: falso (proveedor IPA y AD: verdadero)

Tenga en cuenta que la validación del ticket es el primer paso al verificar el PAC (ver 'pac_check' en la página del manual de sssd.conf(5) para más detalles). Si la validación del ticket está deshabilitada, los cheques PAC también se omitirán.

krb5_renewable_lifetime (cadena)

Solicita un ticket renovable con una vida útil total, dada como un entero seguido inmediatamente por una unidad de tiempo:

s para segundos

m para minutos

h para horas

d para días.

Si no se proporciona unidad, se asumen s.

NOTA: No es posible mezclar unidades. Para establecer la vida útil renovable a una hora y media, use '90m' en lugar de '1h30m'.

Predeterminado: no establecido, es decir, el TGT no es renovable

krb5_lifetime (cadena)

Solicita un ticket con una vida útil, dada como un entero seguido inmediatamente por una unidad de tiempo:

s para segundos

m para minutos

h para horas

d para días.

Si no se proporciona unidad, se asumen s.

NOTA: No es posible mezclar unidades. Para establecer la vida útil a una hora y media, use '90m' en lugar de '1h30m'.

Predeterminado: no establecido, es decir, la vida útil del ticket predeterminada configurada en el KDC.

krb5_renew_interval (cadena)

El tiempo en segundos entre dos comprobaciones si el TGT debe renovarse. Los TGT se renuevan si se excede aproximadamente la mitad de su vida útil, dada como un entero seguido inmediatamente por una unidad de tiempo:

s para segundos

m para minutos

h para horas

d para días.

Si no se proporciona unidad, se asumen s.

NOTA: No es posible mezclar unidades. Para establecer la vida útil renovable a una hora y media, use '90m' en lugar de '1h30m'.

Si esta opción no está establecida o es 0, la renovación automática está deshabilitada.

Predeterminado: no establecido

krb5_canonicalize (booleano)

Especifica si el principal de host y usuario debe ser canónico. Esta característica está disponible con MIT Kerberos 1.7 y versiones posteriores.

Predeterminado: falso

FAILOVER

La característica de failover permite a los backends cambiar automáticamente a un servidor diferente si el servidor actual falla.

Sintaxis de Failover

La lista de servidores se proporciona como una lista separada por comas; se permiten cualquier número de espacios alrededor de la coma. Los servidores se listan en orden de preferencia. La lista puede contener cualquier número de servidores.

Para cada opción de configuración habilitada para failover, existen dos variantes: primary (primario) y backup (respaldo). La idea es que los servidores en la lista primaria son preferidos y los servidores de respaldo solo se buscan si no se puede acceder a ningún servidor primario. Si se selecciona un servidor de respaldo, se establece un tiempo de espera de 31 segundos. Después de este tiempo de espera, SSSD intentará periódicamente reconectarse a uno de los servidores primarios. Si tiene éxito, reemplazará el servidor activo actual (de respaldo).

El Mecanismo de Failover

El mecanismo de failover distingue entre una máquina y un servicio. El backend primero intenta resolver el nombre de host de una máquina dada; si este intento de resolución falla, la máquina se considera fuera de línea. No se realizan más intentos para conectarse a esta máquina para ningún otro servicio. Si el intento de resolución tiene éxito, el backend intenta conectarse a un servicio en esta máquina. Si el intento de conexión al servicio falla, entonces solo este servicio en particular se considera fuera de línea y el backend cambia automáticamente al siguiente servicio. La máquina aún se considera en línea y aún se puede intentar para otro servicio.

Se realizan intentos de conexión adicionales a máquinas o servicios marcados como fuera de línea después de un período de tiempo especificado; actualmente, esto está codificado en 30 segundos.

Si no quedan más máquinas para probar, el backend en su conjunto cambia al modo fuera de línea, y luego intenta reconectar cada 30 segundos.

Tiempos de espera y ajuste de Failover

Resolver un servidor al que conectarse puede ser tan simple como ejecutar una sola consulta DNS o puede implicar varios pasos, como encontrar el sitio correcto o probar varios nombres de host en caso de que algunos de los servidores configurados no sean accesibles. Los escenarios más complejos pueden llevar tiempo y SSSD necesita equilibrar entre proporcionar suficiente tiempo para completar el proceso de resolución, pero por otro lado, no intentar demasiado antes de volver al modo fuera de línea. Si los registros de depuración de SSSD muestran que la resolución del servidor está fallando antes de que se contacte a un servidor activo, puede considerar cambiar los tiempos de espera.

Esta sección enumera los parámetros ajustables. Consulte sus descripciones en la página del manual de sssd.conf(5).

dns_resolver_server_timeout

Tiempo en milisegundos que establece cuánto tiempo hablará SSSD con un solo servidor DNS antes de probar el siguiente.

Predeterminado: 1000

dns_resolver_op_timeout

Tiempo en segundos para indicar cuánto tiempo intentará SSSD resolver una consulta DNS única (por ejemplo, resolución de un nombre de host o un registro SRV) antes de intentar el siguiente nombre de host o dominio de descubrimiento.

Predeterminado: 3

dns_resolver_timeout

Cuánto tiempo intentará SSSD resolver un servicio de failover. La resolución de este servicio internamente puede incluir varios pasos, como resolver consultas DNS SRV o localizar el sitio.

Predeterminado: 6

Para los proveedores basados en LDAP, la operación de resolución se realiza como parte de una operación de conexión LDAP. Por lo tanto, el tiempo de espera “ldap_opt_timeout” también debe establecerse en un valor mayor que “dns_resolver_timeout”, que a su vez debe establecerse en un valor mayor que “dns_resolver_op_timeout”, que debe ser mayor que “dns_resolver_server_timeout”.

DESCUBRIMIENTO DE SERVICIOS

La característica de descubrimiento de servicios permite a los backends encontrar automáticamente los servidores apropiados a los que conectarse utilizando una consulta DNS especial. Esta característica no es compatible con los servidores de respaldo.

Configuración

Si no se especifican servidores, el backend utiliza automáticamente el descubrimiento de servicios para intentar encontrar un servidor. Opcionalmente, el usuario puede optar por utilizar tanto direcciones de servidor fijas como descubrimiento de servicios insertando una palabra clave especial, “_srv_”, en la lista de servidores. Se mantiene el orden de preferencia. Esta característica es útil si, por ejemplo, el usuario prefiere usar el descubrimiento de servicios siempre que sea posible y recurrir a un servidor específico cuando no se puedan descubrir servidores mediante DNS.

El nombre de dominio

Consulte el parámetro “dns_discovery_domain” en la página del manual de sssd.conf(5) para más detalles.

El protocolo

Las consultas suelen especificar _tcp como protocolo. Las excepciones se documentan en la descripción de la opción respectiva.

Véase también

Para obtener más información sobre el mecanismo de descubrimiento de servicios, consulte RFC 2782.

EJEMPLO

El siguiente ejemplo asume que SSSD está configurado correctamente y FOO es uno de los dominios en la sección [sssd]. Este ejemplo solo muestra la configuración de la autenticación Kerberos; no incluye ningún proveedor de identidad.

[domain/FOO]
auth_provider = krb5
krb5_server = 192.168.1.1
krb5_realm = EXAMPLE.COM
