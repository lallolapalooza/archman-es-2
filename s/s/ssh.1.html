SSH(1) Manual de comandos generales SSH(1)

NOMBRE

ssh — cliente de inicio de sesión remoto OpenSSH

SINOPSIS

ssh [-46AaCfGgKkMNnqsTtVvXxYy] [-B interfaz_de_enlace] [-b direccion_enlace] [-c espec_cifrado] [-D [direccion_enlace:]puerto] [-E archivo_log] [-e caracter_escape] [-F archivo_config] [-I pkcs11] [-i archivo_identidad] [-J destino] [-L direccion] [-l nombre_login] [-m espec_mac] [-O comando_ctl] [-o opcion] [-P etiqueta] [-p puerto] [-R direccion] [-S ruta_ctl] [-W host:puerto] [-w tun_local[:tun_remoto]] destino [comando [argumento ...]]

ssh [-Q opcion_consulta]

DESCRIPCIÓN

ssh (cliente SSH) es un programa para iniciar sesión en una máquina remota y para ejecutar comandos en una máquina remota. Está diseñado para proporcionar comunicaciones seguras y cifradas entre dos hosts no confiables a través de una red insegura. Las conexiones X11, puertos TCP arbitrarios y sockets de UNIX también pueden ser reenviados a través del canal seguro.

ssh se conecta e inicia sesión en el destino especificado, que puede ser indicado como user@]hostname o como una URI de la forma ssh://[user@]hostname[:puerto]. El usuario debe probar su identidad a la máquina remota usando uno de varios métodos (ver abajo).

Si se especifica un comando, se ejecutará en el host remoto en lugar de un shell de inicio de sesión. Una línea de comando completa puede especificarse como comando, o puede tener argumentos adicionales. Si se proporcionan, los argumentos se añadirán al comando, separados por espacios, antes de que se envíe al servidor para su ejecución.

Las opciones son las siguientes:

-4
Fuerza a ssh a usar solo direcciones IPv4.
-6
Fuerza a ssh a usar solo direcciones IPv6.
-A
Habilita el reenvío de conexiones desde un agente de autenticación como ssh-agent(1). Esto también puede especificarse de forma individual para cada host en un archivo de configuración.

El reenvío de agente debe habilitarse con precaución. Los usuarios con la capacidad de omitir los permisos de archivo en el host remoto (para el socket UNIX del agente) pueden acceder al agente local a través de la conexión reenviada. Sin embargo, un atacante no puede obtener material de clave del agente. Una alternativa más segura puede ser usar un host de salto (ver -J).

-a
Deshabilita el reenvío de la conexión del agente de autenticación.
-B interfaz_de_enlace
Enlaza a la dirección de interfaz_de_enlace antes de intentar conectarse al host de destino. Esto solo es útil en sistemas con más de una dirección.
-b direccion_enlace
Usa direccion_enlace en la máquina local como la dirección de origen de la conexión. Solo es útil en sistemas con más de una dirección.
-C
Solicita la compresión de todos los datos (incluyendo stdin, stdout, stderr y datos para reenvío de X11, TCP y conexiones de UNIX). El algoritmo de compresión es el mismo utilizado por gzip(1). La compresión es deseable en líneas de módem y otras conexiones lentas, pero solo ralentizará las cosas en redes rápidas. El valor predeterminado puede establecerse por host en los archivos de configuración; ver la opción Compression en ssh_config(5).
-c espec_cifrado
Selecciona la especificación de cifrado para encriptar la sesión. espec_cifrado es una lista separada por comas de cifrados listados en orden de preferencia. Ver la palabra clave Ciphers en ssh_config(5) para más información.
-D [direccion_enlace:]puerto
Especifica un reenvío de puerto local “dinámico” a nivel de aplicación. Esto funciona asignando un socket para escuchar en puerto en el lado local, opcionalmente enlazado a la direccion_enlace especificada. Cada vez que se realiza una conexión a este puerto, la conexión se reenvía a través del canal seguro, y el protocolo de la aplicación se utiliza para determinar a dónde conectarse desde la máquina remota. Actualmente se soportan los protocolos SOCKS4 y SOCKS5, y ssh actuará como un servidor SOCKS. Solo el superusuario puede reenviar puertos privilegiados. Los reenvíos de puerto dinámicos también pueden especificarse en el archivo de configuración.

Las direcciones IPv6 se pueden especificar encerrando la dirección entre corchetes. Solo el superusuario puede reenviar puertos privilegiados. Por defecto, el puerto local se enlaza de acuerdo con la configuración GatewayPorts. Sin embargo, se puede usar una direccion_enlace explícita para enlazar la conexión a una dirección específica. La direccion_enlace de “localhost” indica que el puerto de escucha se enlazará solo para uso local, mientras que una dirección vacía o ‘*’ indica que el puerto debe estar disponible desde todas las interfaces.

-E archivo_log
Añade los logs de depuración a archivo_log en lugar de a la salida de error estándar.
-e caracter_escape
Establece el carácter de escape para sesiones con un pty (predeterminado: ‘~’). El carácter de escape solo se reconoce al principio de una línea. El carácter de escape seguido de un punto (‘.’) cierra la conexión; seguido de Control-Z suspende la conexión; y seguido de sí mismo envía el carácter de escape una vez. Establecer el carácter en “none” deshabilita cualquier escape y hace que la sesión sea completamente transparente.
-F archivo_config
Especifica un archivo de configuración alternativo por usuario.

Este sitio no está asociado de ninguna forma con Arch Linux ni afiliado a este proyecto. El contenido es únicamente una traducción de las páginas del manual de Arch publicadas en man.archlinux.org.

file. Si se proporciona un archivo de configuración en la línea de comandos, se ignorará el archivo de configuración del sistema (/etc/ssh/ssh_config). El valor predeterminado para el archivo de configuración por usuario es ~/.ssh/config. Si se establece en "none", no se leerán archivos de configuración.
-f
Solicita que ssh se ponga en segundo plano justo antes de la ejecución del comando. Esto es útil si ssh va a solicitar contraseñas o frases de contraseña, pero el usuario desea que esté en segundo plano. Esto implica -n. La forma recomendada de iniciar programas X11 en un sitio remoto es con algo como ssh -f host xterm.

Si la opción de configuración ExitOnForwardFailure está establecida en "yes", entonces un cliente iniciado con -f esperará a que todos los reenvíos de puertos remotos se establezcan correctamente antes de ponerse en segundo plano. Consulte la descripción de ForkAfterAuthentication en ssh_config(5) para obtener más detalles.

-G
Hace que ssh imprima su configuración después de evaluar los bloques Host y Match y salir.
-g
Permite que los hosts remotos se conecten a puertos reenviados locales. Si se utiliza en una conexión multiplexada, esta opción debe especificarse en el proceso maestro.
-I pkcs11
Especifica la biblioteca compartida PKCS#11 que ssh debe utilizar para comunicarse con un token PKCS#11 que proporcione claves para la autenticación del usuario.
-i identity_file
Selecciona un archivo del cual se lee la identidad (clave privada) para la autenticación de clave pública. También puede especificar un archivo de clave pública para utilizar la clave privada correspondiente que está cargada en ssh-agent(1) cuando el archivo de clave privada no está presente localmente. El valor predeterminado es ~/.ssh/id_rsa, ~/.ssh/id_ecdsa, ~/.ssh/id_ecdsa_sk, ~/.ssh/id_ed25519 y ~/.ssh/id_ed25519_sk. Los archivos de identidad también pueden especificarse por host en el archivo de configuración. Es posible tener múltiples opciones -i (y múltiples identidades especificadas en archivos de configuración). Si no se han especificado explícitamente certificados mediante la directiva CertificateFile, ssh también intentará cargar información de certificados del nombre de archivo obtenido al agregar -cert.pub a los nombres de archivo de identidad.
-J destination
Conéctese al host de destino estableciendo primero una conexión ssh al host de salto descrito por destination y luego estableciendo un reenvío TCP al destino final desde allí. Se pueden especificar múltiples saltos de salto separados por comas. Las direcciones IPv6 se pueden especificar encerrando la dirección entre corchetes. Esto es un atajo para especificar una directiva de configuración ProxyJump. Tenga en cuenta que las directivas de configuración proporcionadas en la línea de comandos generalmente se aplican al host de destino y no a ningún host de salto especificado. Utilice ~/.ssh/config para especificar la configuración de los hosts de salto.
-K
Habilita la autenticación basada en GSSAPI y el reenvío (delegación) de credenciales GSSAPI al servidor.
-k
Deshabilita el reenvío (delegación) de credenciales GSSAPI al servidor.
-L [bind_address:]port:host:hostport
 
-L [bind_address:]port:remote_socket
 
-L local_socket:host:hostport
 
-L local_socket:remote_socket
Especifica que las conexiones al puerto TCP o socket Unix dado en el host local (cliente) se reenviarán al host y puerto, o socket Unix, dados en el lado remoto. Esto funciona asignando un socket para escuchar un puerto TCP en el lado local, opcionalmente enlazado a la bind_address especificada, o a un socket Unix. Cada vez que se realiza una conexión al puerto o socket local, la conexión se reenvía a través del canal seguro y se establece una conexión a host puerto hostport, o al socket Unix remote_socket, desde la máquina remota.

Los reenvíos de puertos también se pueden especificar en el archivo de configuración. Solo el superusuario puede reenviar puertos privilegiados. Las direcciones IPv6 se pueden especificar encerrando la dirección entre corchetes.

Por defecto, el puerto local se enlaza de acuerdo con la configuración GatewayPorts. Sin embargo, se puede utilizar una bind_address explícita para enlazar la conexión a una dirección específica. La bind_address de "localhost" indica que el puerto de escucha se enlaza solo para uso local, mientras que una dirección vacía o '*' indica que el puerto debe estar disponible desde todas las interfaces.

-l login_name
Especifica el usuario con el que iniciar sesión en la máquina remota. Esto también se puede especificar por host en el archivo de configuración.
-M
Coloca el cliente ssh en modo "maestro" para compartir conexiones. Múltiples opciones -M colocan ssh en modo "maestro" pero con confirmación requerida utilizando ssh-askpass(1) antes de cada operación que cambie el estado de multiplexación (por ejemplo, abrir una nueva sesión). Consulte la descripción de ControlMaster en ssh_config(5) para obtener más detalles.
-m mac_spec
Una lista separada por comas de algoritmos MAC (código de autenticación de mensajes), especificados en orden de preferencia. Consulte la palabra clave MACs en ssh_config(5) para obtener más información.
-N
No ejecute un comando remoto. Esto es útil solo para reenviar puertos. Consulte la descripción de SessionType en ssh_config(5) para obtener más detalles.
-n
Redirige stdin desde /dev/null (de hecho, evita leer de stdin). Esto debe usarse cuando ssh se ejecuta en segundo plano. Un truco común es usar esto para ejecutar programas X11 en una máquina remota. Por ejemplo, ssh -n shadows.cs.hut.fi emacs & iniciará un emacs en shadows.cs.hut.fi, y la conexión X11 se reenviará automáticamente a través de un canal encriptado. El programa ssh se pondrá en segundo plano. (Esto no funciona si ssh necesita solicitar una contraseña o frase de contraseña; vea también la opción -f.) Consulte la descripción de StdinNull en ssh_config(5) para obtener más detalles.
-O ctl_cmd
Controla un proceso maestro de multiplexación de conexiones activo. Cuando se especifica la opción -O, el argumento ctl_cmd se interpreta y se pasa al proceso maestro. Los comandos válidos son: "check" (verificar que el proceso maestro esté en ejecución), "forward" (solicitar reenvíos sin ejecución de comandos), "cancel" (cancelar reenvíos), "proxy" (conectarse a un maestro de multiplexación en ejecución en modo proxy), "exit" (solicitar al maestro que salga) y "stop" (solicitar al maestro que deje de aceptar más solicitudes de multiplexación).
-o option
Se puede utilizar para proporcionar opciones en el formato utilizado en el archivo de configuración. Esto es útil para especificar opciones para las que no hay un indicador de línea de comandos separado. Para obtener detalles completos de las opciones enumeradas a continuación y sus posibles valores, consulte ssh_config(5).

-P tag
Especifica un nombre de etiqueta que se puede utilizar para seleccionar la configuración en ssh_config(5). Consulte las palabras clave Tag y Match en ssh_config(5) para obtener más información.
-p port
Puerto al que conectarse en el host remoto. Esto se puede especificar por host en el archivo de configuración.
-Q query_option
Consulta los algoritmos compatibles con una de las siguientes características: cipher (cifrados simétricos compatibles), cipher-auth (cifrados simétricos que admiten cifrado autenticado), help (términos de consulta admitidos para usar con la opción -Q), mac (códigos de integridad de mensajes compatibles), kex (algoritmos de intercambio de claves), key (tipos de claves), key-ca-sign (algoritmos de firma de CA válidos para certificados), key-cert (tipos de claves de certificado), key-plain (tipos de claves no de certificado), key-sig (todos los tipos de claves y algoritmos de firma), protocol-version (versiones de protocolo SSH compatibles), y sig (algoritmos de firma compatibles). Alternativamente, cualquier palabra clave de ssh_config(5) o sshd_config(5) que acepte una lista de algoritmos se puede usar como alias para la query_option correspondiente.
-q
Modo silencioso. Suprime la mayoría de los mensajes de advertencia y diagnóstico.
-R [bind_address:]port:host:hostport
 
-R [bind_address:]port:local_socket
 
-R remote_socket:host:hostport
 
-R remote_socket:local_socket
 
-R [bind_address:]port
Especifica que las conexiones al puerto TCP o socket Unix dado en el host remoto (servidor) se reenviarán al lado local.

Esto funciona asignando un socket para escuchar en un puerto TCP o en un socket Unix en el lado remoto. Cada vez que se realiza una conexión a este puerto o socket Unix, la conexión se reenvía a través del canal seguro, y se realiza una conexión desde la máquina local a un destino explícito especificado por host puerto hostport, o local_socket, o, si no se especificó ningún destino explícito, ssh actuará como un proxy SOCKS 4/5 y reenviará las conexiones a los destinos solicitados por el cliente SOCKS remoto.

Los reenvíos de puertos también se pueden especificar en el archivo de configuración. Los puertos privilegiados solo se pueden reenviar cuando se inicia sesión como root en la máquina remota. Las direcciones IPv6 se pueden especificar encerrando la dirección entre corchetes.

Por defecto, los sockets de escucha TCP en el servidor se vincularán únicamente a la interfaz de bucle invertido. Esto puede anularse especificando una bind_address. Una bind_address vacía, o la dirección ‘*’, indica que el socket remoto debe escuchar en todas las interfaces. Especificar una bind_address remota solo tendrá éxito si la opción GatewayPorts del servidor está habilitada (ver sshd_config(5)).

Si el argumento port es ‘0’, el puerto de escucha se asignará dinámicamente en el servidor y se informará al cliente en tiempo de ejecución. Cuando se usa junto con -O forward, el puerto asignado se imprimirá en la salida estándar.

-S ctl_path
Especifica la ubicación de un socket de control para compartir conexiones, o la cadena “none” para deshabilitar el compartir conexiones. Consulte la descripción de ControlPath y ControlMaster en ssh_config(5) para más detalles.
-s
Puede ser usado para solicitar la invocación de un subsistema en el sistema remoto. Los subsistemas facilitan el uso de SSH como un transporte seguro para otras aplicaciones (ej. sftp(1)). El subsistema se especifica como el comando remoto. Consulte la descripción de SessionType en ssh_config(5) para más detalles.
-T
Deshabilita la asignación de pseudo-terminal.
-t
Fuerza la asignación de pseudo-terminal. Esto puede ser usado para ejecutar programas arbitrarios basados en pantalla en una máquina remota, lo cual puede ser muy útil, ej. al implementar servicios de menú. Múltiples opciones -t fuerzan la asignación de tty, incluso si ssh no tiene un tty local.
-V
Muestra el número de versión y sale.
-v
Modo detallado. Hace que ssh imprima mensajes de depuración sobre su progreso. Esto es útil para depurar problemas de conexión, autenticación y configuración. Múltiples opciones -v aumentan la verbosidad. El máximo es 3.
-W host:port
Solicita que la entrada y salida estándar en el cliente sean reenviadas a host en port a través del canal seguro. Implica -N, -T, ExitOnForwardFailure y ClearAllForwardings, aunque estas pueden ser sobrescritas en el archivo de configuración o usando opciones de línea de comandos -o.
-w local_tun[:remote_tun]
Solicita el reenvío de dispositivos de túnel con los dispositivos tun(4) especificados entre el cliente (local_tun) y el servidor (remote_tun).

Los dispositivos pueden ser especificados por ID numérico o por la palabra clave “any”, que utiliza el siguiente dispositivo de túnel disponible. Si remote_tun no se especifica, por defecto es “any”. Vea también las directivas Tunnel y TunnelDevice en ssh_config(5).

Si la directiva Tunnel no está establecida, se establecerá en el modo de túnel por defecto, que es “point-to-point”. Si se desea un modo de reenvío Tunnel diferente, entonces debería especificarse antes de -w.

-X
Habilita el reenvío X11. Esto también puede ser especificado por host en un archivo de configuración.

El reenvío X11 debe habilitarse con precaución. Los usuarios con la capacidad de omitir los permisos de archivo en el host remoto (para la base de datos de autorización X del usuario) pueden acceder a la pantalla X local a través de la conexión reenviada. Un atacante podría entonces ser capaz de realizar actividades como el monitoreo de pulsaciones de teclas.

Por esta razón, el reenvío X11 está sujeto a las restricciones de la extensión X11 SECURITY por defecto. Consulte la opción ssh -Y y la directiva ForwardX11Trusted en ssh_config(5) para más información.

-x
Deshabilita el reenvío X11.
-Y
Habilita el reenvío X11 confiable. Los reenvíos X11 confiables no están sujetos a los controles de la extensión X11 SECURITY.
-y
Envía información de registro usando el módulo del sistema syslog(3). Por defecto esta información se envía a stderr.

ssh puede obtener información de configuración adicional de un archivo de configuración por usuario y un archivo de configuración a nivel de sistema. El formato del archivo y las opciones de configuración se describen en ssh_config(5).

AUTENTICACIÓN

El cliente SSH de OpenSSH soporta el protocolo SSH 2.

Los métodos disponibles para la autenticación son: autenticación basada en GSSAPI, autenticación basada en host, autenticación de clave pública, autenticación interactiva de teclado y autenticación por contraseña. Los métodos de autenticación se prueban en el orden especificado anteriormente, aunque PreferredAuthentications puede ser usado para cambiar el orden por defecto.

La autenticación basada en host funciona de la siguiente manera: Si la máquina desde la que el usuario inicia sesión está listada en /etc/hosts.equiv o /etc/ssh/shosts.equiv en la máquina remota, el usuario no es root y los nombres de usuario son los mismos en ambos lados, o si los archivos ~/.rhosts o ~/.shosts existen en el directorio principal del usuario en la máquina remota y contienen una línea que incluye el nombre de la máquina cliente y el nombre del usuario en esa máquina, se considera al usuario para el inicio de sesión. Adicionalmente, el servidor debe poder verificar la clave del host del cliente (consulte la descripción de /etc/ssh/ssh_known_hosts y ~/.ssh/known_hosts, abajo) para que el inicio de sesión sea permitido. Este método de autenticación cierra agujeros de seguridad debidos a suplantación de IP, suplantación de DNS y suplantación de enrutamiento. [Nota para el administrador: /etc/hosts.equiv, ~/.rhosts, y el protocolo rlogin/rsh en general, son inherentemente inseguros y deberían deshabilitarse si se desea seguridad.]

La autenticación de clave pública funciona de la siguiente manera: El esquema se basa en criptografía de clave pública, utilizando criptosistemas donde el cifrado y descifrado se realizan utilizando claves separadas, y es inviable derivar la clave de descifrado de la clave de cifrado. La idea es que cada usuario cree un par de claves pública/privada para fines de autenticación. El servidor conoce la clave pública, y solo el usuario conoce la clave privada. ssh implementa automáticamente el protocolo de autenticación de clave pública, utilizando uno de los algoritmos ECDSA, Ed25519 o RSA.

El archivo ~/.ssh/authorized_keys lista las claves públicas que están permitidas para iniciar sesión. Cuando el usuario inicia sesión, el programa ssh le informa al servidor qué par de claves desea usar para la autenticación. El cliente demuestra que tiene acceso a la clave privada y el servidor verifica que la clave pública correspondiente está autorizada para aceptar la cuenta.

El servidor puede informar al cliente de errores que impidieron que la autenticación de clave pública tuviera éxito después de que la autenticación se completara utilizando un método diferente. Estos pueden ser vistos aumentando el LogLevel a DEBUG o superior (ej. usando el flag -v).

El usuario crea su par de claves ejecutando ssh-keygen(1). Esto almacena la clave privada en ~/.ssh/id_ecdsa (ECDSA), ~/.ssh/id_ecdsa_sk (ECDSA alojado en autenticador), ~/.ssh/id_ed25519 (Ed25519), ~/.ssh/id_ed25519_sk (Ed25519 alojado en autenticador), o ~/.ssh/id_rsa (RSA) y almacena la clave pública en ~/.ssh/id_ecdsa.pub (ECDSA), ~/.ssh/id_ecdsa_sk.pub (ECDSA alojado en autenticador), ~/.ssh/id_ed25519.pub (Ed25519), ~/.ssh/id_ed25519_sk.pub (Ed25519 alojado en autenticador), o ~/.ssh/id_rsa.pub (RSA) en el directorio principal del usuario. Luego, el usuario debe copiar la clave pública a ~/.ssh/authorized_keys en su directorio principal en la máquina remota. El archivo authorized_keys corresponde al archivo convencional ~/.rhosts, y tiene una clave por línea, aunque las líneas pueden ser muy largas. Después de esto, el usuario puede iniciar sesión sin proporcionar la contraseña.

Una variación de la autenticación de clave pública está disponible en forma de autenticación de certificado: en lugar de un conjunto de claves públicas/privadas, se utilizan certificados firmados. Esto tiene la ventaja de que una única autoridad de certificación confiable puede ser utilizada en lugar de muchas claves públicas/privadas. Consulte la sección CERTIFICATES de ssh-keygen(1) para más información.

La forma más conveniente de usar la autenticación de clave pública o de certificado puede ser con un agente de autenticación. Consulte ssh-agent(1) y (opcionalmente) la directiva AddKeysToAgent en ssh_config(5) para más información.

La autenticación interactiva de teclado funciona de la siguiente manera: El servidor envía un texto arbitrario de "desafío" y solicita una respuesta, posiblemente varias veces. Ejemplos de autenticación interactiva de teclado incluyen la autenticación BSD (consulte login.conf(5)) y PAM (algunos sistemas no-OpenBSD).

Finalmente, si otros métodos de autenticación fallan, ssh solicita al usuario una contraseña. La contraseña se envía al host remoto para su verificación; sin embargo, dado que todas las comunicaciones están cifradas, la contraseña no puede ser vista por alguien que escuche en la red.

ssh mantiene y verifica automáticamente una base de datos que contiene la identificación de todos los hosts con los que se ha utilizado alguna vez. Las claves de host se almacenan en ~/.ssh/known_hosts en el directorio principal del usuario. Adicionalmente, el archivo /etc/ssh/ssh_known_hosts se verifica automáticamente para hosts conocidos

REDES PRIVADAS VIRTUALES BASADAS EN SSH

ssh incluye soporte para túneles de Red Privada Virtual (VPN) utilizando el pseudodispositivo de red tun(4), permitiendo unir dos redes de forma segura. La opción de configuración PermitTunnel de sshd_config(5) controla si el servidor admite esto y a qué nivel (tráfico de capa 2 o 3).

El siguiente ejemplo conectaría la red cliente 10.0.50.0/24 con la red remota 10.0.99.0/24 utilizando una conexión punto a punto de 10.1.1.1 a 10.1.1.2, siempre que el servidor SSH que se ejecuta en la pasarela a la red remota, en 192.168.1.15, lo permita.

En el cliente:

# ssh -f -w 0:1 192.168.1.15 true
# ifconfig tun0 10.1.1.1 10.1.1.2 netmask 255.255.255.252
# route add 10.0.99.0/24 10.1.1.2

En el servidor:

# ifconfig tun1 10.1.1.2 10.1.1.1 netmask 255.255.255.252
# route add 10.0.50.0/24 10.1.1.1

El acceso del cliente puede ajustarse con mayor precisión a través del archivo /root/.ssh/authorized_keys (ver más abajo) y la opción del servidor PermitRootLogin. La siguiente entrada permitiría conexiones en el dispositivo tun(4) 1 del usuario "jane" y en el dispositivo tun 2 del usuario "john", si PermitRootLogin está configurado como "forced-commands-only":

tunnel="1",command="sh /etc/netstart tun1" ssh-rsa ... jane
tunnel="2",command="sh /etc/netstart tun2" ssh-rsa ... john

Dado que una configuración basada en SSH implica una cantidad considerable de sobrecarga, puede ser más adecuada para configuraciones temporales, como VPN inalámbricas. Las VPN más permanentes se proporcionan mejor con herramientas como ipsecctl(8) y isakmpd(8).

ENTORNO

ssh normalmente establecerá las siguientes variables de entorno:

DISPLAY
La variable DISPLAY indica la ubicación del servidor X11. Es establecida automáticamente por ssh para apuntar a un valor del tipo "hostname:n", donde "hostname" indica la máquina donde se ejecuta el shell, y 'n' es un entero ≥ 1. ssh utiliza este valor especial para reenviar conexiones X11 a través del canal seguro. Normalmente, el usuario no debería establecer DISPLAY explícitamente, ya que eso haría que la conexión X11 fuera insegura (y requeriría que el usuario copiara manualmente cualquier cookie de autorización necesaria).
HOME
Establecida en la ruta del directorio de inicio del usuario.
LOGNAME
Sinónimo de USER; establecida por compatibilidad con sistemas que utilizan esta variable.
MAIL
Establecida en la ruta del buzón del usuario.
PATH
Establecida en el PATH por defecto, según lo especificado durante la compilación de ssh.
SSH_ASKPASS
Si ssh necesita una contraseña, leerá la contraseña desde la terminal actual si se ejecutó desde una terminal. Si ssh no tiene una terminal asociada pero DISPLAY y SSH_ASKPASS están establecidos, ejecutará el programa especificado por SSH_ASKPASS y abrirá una ventana X11 para leer la contraseña. Esto es particularmente útil al llamar a ssh desde un script .xsession o similar. (Tenga en cuenta que en algunas máquinas puede ser necesario redirigir la entrada desde /dev/null para que esto funcione).
SSH_ASKPASS_REQUIRE
Permite un mayor control sobre el uso de un programa askpass. Si esta variable está establecida en "never", entonces ssh nunca intentará usar uno. Si está establecida en "prefer", entonces ssh preferirá usar el programa askpass en lugar del TTY al solicitar contraseñas. Finalmente, si la variable está establecida en "force", entonces el programa askpass se usará para toda la entrada de contraseñas, independientemente de si DISPLAY está establecido.
SSH_AUTH_SOCK
Identifica la ruta de un socket de dominio UNIX utilizado para comunicarse con el agente.
SSH_CONNECTION
Identifica los extremos del cliente y del servidor de la conexión. La variable contiene cuatro valores separados por espacios: dirección IP del cliente, número de puerto del cliente, dirección IP del servidor y número de puerto del servidor.
SSH_ORIGINAL_COMMAND
Esta variable contiene la línea de comando original si se ejecuta un comando forzado. Se puede utilizar para extraer los argumentos originales.
SSH_TTY
Se establece en el nombre del tty (ruta del dispositivo) asociado con el shell o comando actual. Si la sesión actual no tiene un tty, esta variable no se establece.
SSH_TUNNEL
Opcionalmente establecido por sshd(8) para contener los nombres de interfaz asignados si el cliente solicitó reenvío de túnel.
SSH_USER_AUTH
Opcionalmente establecido por sshd(8), esta variable puede contener una ruta a un archivo que enumera los métodos de autenticación utilizados con éxito al establecer la sesión, incluidas las claves públicas que se utilizaron.
TZ
Esta variable se establece para indicar la zona horaria actual si se estableció cuando se inició el demonio (es decir, el demonio transmite el valor a las nuevas conexiones).
USER
Establecida en el nombre del usuario que inicia sesión.

Además, ssh lee ~/.ssh/environment y añade líneas del formato "VARNAME=valor" al entorno si el archivo existe y a los usuarios se les permite cambiar su entorno. Para obtener más información, consulte la opción PermitUserEnvironment en sshd_config(5).

ARCHIVOS

~/.rhosts
Este archivo se utiliza para la autenticación basada en host (ver más arriba). En algunas máquinas, este archivo puede necesitar ser legible por todos si el directorio de inicio del usuario está en una partición NFS, ya que sshd(8) lo lee como root. Además, este archivo debe ser propiedad del usuario y no debe tener permisos de escritura para nadie más. El permiso recomendado para la mayoría de las máquinas es lectura/escritura para el usuario, y no accesible por otros.
~/.shosts
Este archivo se utiliza exactamente de la misma manera que .rhosts, pero permite la autenticación basada en host sin permitir el inicio de sesión con rlogin/rsh.
~/.ssh/
Este directorio es la ubicación predeterminada para toda la información de configuración y autenticación específica del usuario. No hay un requisito general para mantener en secreto todo el contenido de este directorio, pero los permisos recomendados son lectura/escritura/ejecución para el usuario, y no accesibles por otros.
~/.ssh/authorized_keys
Enumera las claves públicas (ECDSA, Ed25519, RSA) que se pueden utilizar para iniciar sesión como este usuario. El formato de este archivo se describe en la página del manual de sshd(8). Este archivo no es extremadamente sensible, pero los permisos recomendados son lectura/escritura para el usuario, y no accesibles por otros.
~/.ssh/config
Este es el archivo de configuración por usuario. El formato del archivo y las opciones de configuración se describen en ssh_config(5). Debido al potencial de abuso, este archivo debe tener permisos estrictos: lectura/escritura para el usuario, y no escribible por otros.
~/.ssh/environment
Contiene definiciones adicionales para variables de entorno; consulte ENTORNO, más arriba.
