NOMBRE

sssd-kcm - Gestor de Caché Kerberos de SSSD

DESCRIPCIÓN

Esta página del manual describe la configuración del Gestor de Caché Kerberos de SSSD (KCM). KCM es un proceso que almacena, rastrea y gestiona las cachés de credenciales Kerberos. Se origina en el proyecto Heimdal Kerberos, aunque la biblioteca MIT Kerberos también proporciona soporte del lado del cliente (más detalles a continuación) para la caché de credenciales KCM.

En una configuración donde las cachés Kerberos son gestionadas por KCM, la biblioteca Kerberos (típicamente utilizada a través de una aplicación, como por ejemplo, kinit(1), es un "cliente KCM" y el demonio KCM se denomina "servidor KCM". El cliente y el servidor se comunican a través de un socket UNIX.

El servidor KCM realiza un seguimiento del propietario de cada caché de credenciales y lleva a cabo un control de acceso basado en el UID y GID del cliente KCM. El usuario root tiene acceso a todas las cachés de credenciales.

La caché de credenciales KCM tiene varias propiedades interesantes:

•dado que el proceso se ejecuta en el espacio de usuario, está sujeto al espacio de nombres de UID, a diferencia del keyring del kernel
•a diferencia de la caché basada en el keyring del kernel, que se comparte entre todos los contenedores, el servidor KCM es un proceso separado cuya punto de entrada es un socket UNIX
•la implementación de SSSD almacena las ccaches en una base de datos, típicamente ubicada en /var/lib/sss/secrets lo que permite que las ccaches sobrevivan a reinicios del servidor KCM o reinicios de la máquina.

Esto permite al sistema utilizar una caché de credenciales consciente de la colección, pero compartir la caché de credenciales entre algunos o ningún contenedor montando el socket.

El tiempo de espera inactivo predeterminado del cliente KCM es de 5 minutos, lo que permite más tiempo para la interacción del usuario con herramientas de línea de comandos como kinit.

USANDO LA CACHÉ DE CREDENCIALES KCM

Para usar la caché de credenciales KCM, debe seleccionarse como el tipo de credencial predeterminado en krb5.conf(5). El nombre de la caché de credenciales debe ser solo "KCM:" sin ninguna expansión de plantilla. Por ejemplo:

[libdefaults]
    default_ccache_name = KCM:

A continuación, asegúrese de que las bibliotecas cliente Kerberos y el servidor KCM estén de acuerdo en la ruta del socket UNIX. Por defecto, ambos utilizan la misma ruta /var/run/.heim_org.h5l.kcm-socket. Para configurar la biblioteca Kerberos, cambie su opción "kcm_socket", que se describe en la página del manual de krb5.conf(5).

Finalmente, asegúrese de que se pueda contactar al servidor SSSD KCM. El servicio KCM se activa por socket típicamente por systemd(1). A diferencia de otros servicios SSSD, no se puede iniciar agregando la cadena "kcm" a la directiva "service".

systemctl start sssd-kcm.socket
systemctl enable sssd-kcm.socket

Tenga en cuenta que su distribución puede configurar las unidades por usted.

EL ALMACENAMIENTO DE LA CACHÉ DE CREDENCIALES

Las cachés de credenciales se almacenan en una base de datos, de forma similar a como SSSD cachea las entradas de usuario o grupo. La base de datos se encuentra típicamente en "/var/lib/sss/secrets".

OBTENCIÓN DE REGISTROS DE DEPURACIÓN

El servicio sssd-kcm se activa por socket típicamente systemd(1). Para generar registros de depuración, agregue lo siguiente ya sea directamente al archivo /etc/sssd/sssd.conf o como un fragmento de configuración al directorio /etc/sssd/conf.d/:

[kcm]
debug_level = 10

Luego, reinicie el servicio sssd-kcm:

systemctl restart sssd-kcm.service

Finalmente, ejecute el caso de uso que no le funcione. Los registros de KCM se generarán en /var/log/sssd/sssd_kcm.log. Se recomienda deshabilitar los registros de depuración cuando ya no necesite la depuración activada, ya que el servicio sssd-kcm puede generar una gran cantidad de información de depuración.

Tenga en cuenta que los fragmentos de configuración, en este momento, solo se procesan si el archivo de configuración principal en /etc/sssd/sssd.conf existe.

RENUEVACIONES

El servicio sssd-kcm puede configurarse para intentar la renovación de TGT para TGT renovables almacenados en la caché KCM. Las renovaciones solo se intentan cuando se ha alcanzado la mitad de la vida útil del ticket. Las renovaciones de KCM se configuran cuando se establecen las siguientes opciones en la sección [kcm]:

tgt_renewal = true
krb5_renew_interval = 60m

SSSD también puede heredar opciones de krb5 para renovaciones de un dominio existente.

tgt_renewal = true
tgt_renewal_inherit = domain-name

Las siguientes opciones de krb5 se pueden configurar en la sección [kcm] para controlar el comportamiento de renovación, estas opciones se describen en detalle a continuación.

krb5_renew_interval
krb5_renewable_lifetime
krb5_lifetime
krb5_validate
krb5_canonicalize
krb5_auth_timeout

OPCIONES DE CONFIGURACIÓN

El servicio KCM se configura en la sección "kcm" del archivo sssd.conf. Tenga en cuenta que dado que el servicio KCM se activa por socket típicamente, es suficiente con reiniciar el servicio "sssd-kcm" después de cambiar las opciones en la sección "kcm" de sssd.conf:

systemctl restart sssd-kcm.service

El servicio KCM se configura en la sección "kcm". Para una referencia detallada de la sintaxis, consulte la sección "FORMATO DEL ARCHIVO" de la página del manual de sssd.conf(5).

El servicio kcm acepta las opciones genéricas de SSSD como "debug_level" o "fd_limit". Consulte la página del manual de sssd.conf(5) para una lista completa. Además, existen algunas opciones específicas de KCM.

socket_path (cadena)

El socket en el que escuchará el servicio KCM.

Predeterminado: /var/run/.heim_org.h5l.kcm-socket

Nota: en plataformas donde se soporta systemd, la ruta del socket se sobrescribe con la definida en el archivo de unidad sssd-kcm.socket.

max_ccaches (entero)

Cuántas cachés de credenciales permite la base de datos KCM para todos los usuarios.

Predeterminado: 0 (ilimitado, solo se aplica la cuota por UID)

max_uid_ccaches (entero)

Cuántas cachés de credenciales permite la base de datos KCM por UID. Esto es equivalente a "con cuántos principales puedes hacer kinit".

Predeterminado: 64

max_ccache_size (entero)

Cuán grande puede ser una caché de credenciales por caché. Cada ticket de servicio cuenta para esta cuota.

Predeterminado: 65536

tgt_renewal (booleano)

Habilita la funcionalidad de renovación de TGT.

Predeterminado: False (Renovaciones automáticas deshabilitadas)

tgt_renewal_inherit (cadena)

Dominio del cual heredar las opciones krb5_*, para usar con renovaciones de TGT.

Predeterminado: NULL

krb5_auth_timeout (entero)

Tiempo de espera en segundos después del cual se aborta una solicitud de autenticación en línea o una solicitud de cambio de contraseña. Si es posible, la solicitud de autenticación continúa sin conexión.

Predeterminado: 6

krb5_validate (booleano)

Verifica con la ayuda de krb5_keytab si el TGT obtenido no ha sido falsificado. La keytab se verifica secuencialmente, y se usa la primera entrada con un realm coincidente para la validación. Si ninguna entrada coincide con el realm, se usa la última entrada en la keytab. Este proceso se puede usar para validar entornos que utilizan confianzas entre realms colocando la entrada apropiada de la keytab como la última entrada o la única entrada en el archivo de la keytab.

Predeterminado: false (proveedor IPA y AD: true)

Tenga en cuenta que la validación del ticket es el primer paso al verificar el PAC (ver 'pac_check' en la página del manual de sssd.conf(5) para más detalles). Si la validación del ticket está deshabilitada, las verificaciones del PAC serán

OPCIONES DE CONFIGURACIÓN

krb5_renewable_lifetime (cadena)

Solicita un ticket renovable con una vida útil total, dada como un entero seguido inmediatamente de una unidad de tiempo:

s para segundos

m para minutos

h para horas

d para días.

Si no se da ninguna unidad, se asume s.

NOTA: No es posible mezclar unidades. Para establecer la vida útil renovable en una hora y media, use '90m' en lugar de '1h30m'.

Por defecto: no establecido, es decir, el TGT no es renovable

krb5_lifetime (cadena)

Solicita un ticket con una vida útil, dada como un entero seguido inmediatamente de una unidad de tiempo:

s para segundos

m para minutos

h para horas

d para días.

Si no se da ninguna unidad, se asume s.

NOTA: No es posible mezclar unidades. Para establecer la vida útil en una hora y media, use '90m' en lugar de '1h30m'.

Por defecto: no establecido, es decir, la vida útil predeterminada del ticket configurada en el KDC.

krb5_renew_interval (cadena)

El tiempo en segundos entre dos comprobaciones si el TGT debe ser renovado. Los TGT se renuevan si se supera aproximadamente la mitad de su vida útil, dada como un entero seguido inmediatamente de una unidad de tiempo:

s para segundos

m para minutos

h para horas

d para días.

Si no se da ninguna unidad, se asume s.

NOTA: No es posible mezclar unidades. Para establecer la vida útil renovable en una hora y media, use '90m' en lugar de '1h30m'.

Si esta opción no está establecida o es 0, la renovación automática está deshabilitada.

Por defecto: no establecido

krb5_canonicalize (booleano)

Especifica si el host y el principal del usuario deben ser canonicados. Esta característica está disponible con MIT Kerberos 1.7 y versiones posteriores.

Por defecto: falso
