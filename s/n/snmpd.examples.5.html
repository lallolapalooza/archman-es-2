NOMBRE

snmpd.examples - configuración de ejemplo para el agente Net-SNMP

DESCRIPCIÓN

La página del manual snmpd.conf(5) define la sintaxis y el comportamiento de las diversas directivas de configuración que se pueden utilizar para controlar el funcionamiento del agente Net-SNMP y la información de gestión que proporciona.

Esta página de manual complementaria ilustra estas directivas, mostrando algunos ejemplos prácticos de cómo podrían utilizarse.

COMPORTAMIENTO DEL AGENTE

Direcciones de escucha

El comportamiento predeterminado del agente (escuchar en el puerto UDP SNMP estándar en todas las interfaces) es equivalente a la directiva:

agentaddress udp:161
o simplemente
agentaddress 161
El agente se puede configurar para aceptar únicamente las solicitudes enviadas a la interfaz de loopback local (escuchando de nuevo en el puerto UDP SNMP), usando:
agentaddress localhost:161 # (udp implícito)
o
agentaddress 127.0.0.1 # (udp y puerto estándar implícitos)
Puede configurarse para aceptar solicitudes UDP y TCP (tanto IPv4 como IPv6), usando:
agentaddress udp:161,tcp:161,udp6:161,tcp6:161
Otras combinaciones también son válidas.

Privilegios en tiempo de ejecución

El agente se puede configurar para renunciar a cualquier acceso privilegiado una vez que haya abierto los puertos de escucha iniciales. Dado un grupo "snmp" adecuado (definido en /etc/group), esto podría hacerse usando las directivas:

agentuser  nobody
agentgroup snmp
Un efecto similar podría lograrse utilizando valores numéricos de UID y/o GID: 
agentuser  #10
agentgroup #10

Configuración SNMPv3

En lugar de generarse de forma pseudoaleatoria, el ID del motor para el agente podría calcularse basándose en la dirección MAC de la segunda interfaz de red (eth1), usando las directivas:

engineIDType 3 engineIDNic eth1
o podría calcularse a partir de la dirección IP (la primera), usando:
engineIDType 1
o podría especificarse explícitamente, usando:
engineID "XXX - QUÉ FORMATO"

CONTROL DE ACCESO

Usuarios SNMPv3

Las siguientes directivas crearán tres usuarios, todos utilizando exactamente las mismas configuraciones de autenticación y cifrado:

createUser me     MD5 "frase de paso única"
createUser myself MD5 "frase de paso única" DES
createUser andI   MD5 "frase de paso única" DES "frase de paso única"
Tenga en cuenta que esto define tres usuarios distintos, a los que se les podrían otorgar diferentes niveles de acceso. Cambiar la frase de paso para cualquiera de ellos no afectaría a los otros dos.

Se pueden especificar frases de paso separadas para autenticación y cifrado:

createUser onering SHA "para gobernarlos a todos" AES "para unirlos"
Recuerde que estas directivas createUser deben definirse en el archivo /var/net-snmp/snmpd.conf, en lugar de la ubicación habitual.

Control de acceso tradicional

A los usuarios SNMPv3 definidos anteriormente se les puede otorgar acceso al árbol MIB completo usando las directivas:

rouser me
rwuser onering
O acceso selectivo a subárboles individuales usando: 
rouser myself   .1.3.6.1.2
rwuser andI     system

Tenga en cuenta que una combinación que repite el mismo usuario, como:

rouser onering
rwuser onering
NO debe usarse. Esto configuraría al usuario onering con acceso de solo lectura (e ignoraría la entrada rwuser por completo). Lo mismo ocurre con las directivas basadas en comunidad.

Las directivas:

rocommunity public
rwcommunity private
definirían las cadenas de comunidad de lectura y escritura comúnmente esperadas para las solicitudes SNMPv1 y SNMPv2c. Este comportamiento NO está configurado por defecto y tendría que configurarse explícitamente.
Nota:
¡También sería una muy buena idea cambiar private por algo un poco menos predecible!

Una configuración ligeramente menos vulnerable podría restringir qué información podría recuperarse:

rocommunity public default system
o los sistemas de gestión desde los que se podrían manipular la configuración:
rwcommunity private 10.10.10.0/24
o una combinación de ambos.

Configuración VACM

Este último par de configuraciones es equivalente a las definiciones VACM completas:

#         sec.name  source        community
com2sec   public    default       public
com2sec   mynet     10.10.10.0/24 private
com2sec6  mynet     fec0::/64     private
#                  sec.model  sec.name
group  worldGroup  v1         public
group  worldGroup  v2c        public
group  myGroup     v1         mynet
group  myGroup     v2c        mynet
#              incl/excl   subtree     [mask]
view   all     included    .1
view   sysView included    system
#              context model level   prefix  read    write  notify (unused)
access  worldGroup  ""  any  noauth  exact   system  none   none
access  myGroup     ""  any  noauth  exact   all     all    none

Hay varios puntos a tener en cuenta en este ejemplo:

Las directivas group deben repetirse tanto para las solicitudes SNMPv1 como SNMPv2c.

El nombre de seguridad com2sec es distinto de la cadena de comunidad a la que se mapea. Pueden ser iguales ("public") o diferentes ("mynet"/"private"), pero lo que aparece en la directiva group es el nombre de seguridad, independientemente de la cadena de comunidad original.

Ambas directivas view definen subárboles OID simples, por lo que ninguna de ellas requiere una máscara explícita. Lo mismo ocurre con la vista de subárbol combinada2 definida a continuación. De hecho, un campo de máscara solo es necesario al definir segmentos de fila en una tabla (o vistas similares) y casi siempre se puede omitir.

En general, es aconsejable no mezclar las configuraciones de acceso tradicionales y las basadas en VACM, ya que a veces pueden interferir entre sí de formas inesperadas. Elija un estilo particular de configuración de acceso y manténgalo.

Configuración de vista tipificada

Una configuración similar también podría configurarse de la siguiente manera:

view   sys2View included    system
view   sys2View included    .1.3.6.1.2.1.25.1
authcommunity read       public  default      -v sys2View
authcommunity read,write private 10.10.10.0/8

Este mecanismo permite usar vistas de subárbol múltiple (u otras vistas no simples) con el estilo de configuración rocommunity de una sola línea.

También admitiría la configuración de acceso de "solo escritura", si fuera necesario.

CONFIGURACIÓN BÁSICA

Configuración de Monitoreo de Disco

Los dispositivos que se exploran para su posible inclusión en la hrDiskStorageTable (y hrDeviceTable) pueden ser modificados usando cualquiera de las siguientes directivas:

ignoredisk /dev/rdsk/c0t2d0
que evita que el dispositivo /dev/rdsk/c0t2d0 sea escaneado, 
ignoredisk /dev/rdsk/c0t[!6]d0
ignoredisk /dev/rdsk/c0t[0-57-9a-f]d0
cualquiera de las cuales evita que los dispositivos /dev/rdsk/c0tXd0 (excepto .../c0t6d0) sean escaneados,
ignoredisk /dev/rdsk/c1*
que evita que los dispositivos cuyos nombres comiencen con /dev/rdsk/c1 sean escaneados, o
ignoredisk /dev/rdsk/c?t0d0
que evita que los dispositivos /dev/rdsk/cXt0d0 (donde 'X' es cualquier carácter individual) sean escaneados.

Monitoreo de Procesos

La lista de servicios que se ejecutan en un sistema puede ser monitoreada (y se pueden tomar medidas para corregir cualquier problema) usando:

# Debe haber al menos un proceso de servidor web ejecutándose en todo momento
proc    httpd
procfix httpd  /etc/rc.d/init.d/httpd restart
# Nunca debe haber más de 10 procesos de correo ejecutándose
#    (más implica una probable tormenta de correo, así que detenga el sistema de correo)
proc    sendmail   10
procfix sendmail  /etc/rc.d/init.d/sendmail stop
# Debe haber un único agente de gestión de red en ejecución
#   ("Solo puede haber uno")
proc    snmpd    1  1
Consulte también la sección "DisMan Event MIB" más adelante.

Monitoreo de Uso de Disco

El estado del almacenamiento en disco puede ser monitoreado usando:

includeAllDisks 10%
disk /var 20%
disk /usr  3%
# Mantener 100 MB libres para volcados de emergencia
disk /mnt/crash  100000

Monitoreo de Carga del Sistema

Una comprobación simple de un sistema sobrecargado podría ser:

load 10
Una comprobación más refinada (para permitir breves períodos de uso intenso, pero reconocer una carga sostenida media-alta) podría ser:
load 30 10 5

MONITOREO ACTIVO

Manejo de Notificaciones

La configuración del agente para reportar intentos de acceso inválidos podría hacerse mediante:

authtrapenable 1
trapcommunity  public
trap2sink      localhost
Alternativamente, las segundas y terceras directivas podrían combinarse (y solicitar un acuse de recibo) usando:
informsink localhost public
Una configuración con destinos de recepción repetidos, como: 
trapsink       localhost
trap2sink      localhost
informsink     localhost
NO debe usarse, ya que esto provocará el envío de copias múltiples de cada trampa al mismo receptor de trampas.

DisMan Event MIB

La configuración más simple para el auto-monitoreo activo del agente, por el agente, para el agente, es probablemente:

# Configurar las credenciales para recuperar los valores monitoreados
createUser    _internal MD5 "la primera señal de locura"
iquerySecName _internal
rouser        _internal
# Activar las entradas de monitoreo estándar
defaultMonitors         yes
linkUpDownNotifications yes
# Si hay un problema, ¡entonces díselo a alguien!
trap2sink localhost

El primer bloque configura un usuario adecuado para recuperar la información a monitorear, mientras que el par de directivas siguientes activa varias entradas de monitoreo incorporadas.

Tenga en cuenta que las directivas DisMan por sí solas no son suficientes para reportar activamente problemas; también debe haber un destino adecuado configurado para enviar las notificaciones resultantes.

Un ejemplo de monitor más detallado es:

monitor -u me -o hrSWRunName "alta memoria de proceso" hrSWRunPerfMem > 10000

Esto define una entrada de monitor booleana explícita, que busca cualquier proceso que utilice más de 10 MB de memoria activa. Dichos procesos se reportarán utilizando la trampa (estándar) DisMan mteTriggerFired, pero agregando una variable adicional (con comodín) hrSWRunName.

Esta entrada también especifica un usuario explícito (me, como se definió anteriormente) para recuperar los valores monitoreados y construir la trampa.

Los objetos que potencialmente podrían fluctuar alrededor del nivel especificado se monitorean mejor usando una entrada de monitor de umbral:

monitor -D -r 10 "tráfico de red" ifInOctets 1000000 5000000

Esto enviará una trampa mteTriggerRising cuando el tráfico entrante supere (aproximadamente) 500 kB/s en cualquier interfaz de red, y una trampa mteTriggerFalling correspondiente cuando vuelva a caer por debajo de 100 kB/s.

Tenga en cuenta que esto monitorea las diferencias entre muestras sucesivas (-D) en lugar de los valores de muestra reales. El mismo efecto podría obtenerse usando:

monitor -r 10 "tráfico de red" ifInOctets - - 1000000 5000000

La directiva linkUpDownNotifications anterior es ampliamente equivalente a:

notificationEvent  linkUpTrap    linkUp   ifIndex ifAdminStatus ifOperStatus
notificationEvent  linkDownTrap  linkDown ifIndex ifAdminStatus ifOperStatus
monitor  -r 60 -e linkUpTrap   "Generar linkUp"   ifOperStatus != 2
monitor  -r 60 -e linkDownTrap "Generar linkDown" ifOperStatus == 2

Esto define las trampas que se enviarán (usando notificationEvent), y hace referencia explícita a la notificación relevante en la entrada de monitor correspondiente (en lugar de usar las trampas DisMan predeterminadas).

La directiva defaultMonitors anterior es equivalente a una serie de entradas de monitor (booleanas):

monitor	-o prNames      -o prErrMessage  "procTable" prErrorFlag   != 0
monitor	-o memErrorName -o memSwapErrorMsg "memory"  memSwapError  != 0
monitor	-o extNames     -o extOutput     "extTable"  extResult     != 0
monitor	-o dskPath      -o dskErrorMsg   "dskTable"  dskErrorFlag  != 0
monitor	-o laNames      -o laErrMessage  "laTable"   laErrorFlag   != 0
monitor	-o fileName     -o fileErrorMsg  "fileTable" fileErrorFlag != 0
y enviará una trampa cada vez que alguna de estas entradas indique un problema.

Un enfoque alternativo sería invocar automáticamente la acción "fix" correspondiente:

setEvent   prFixIt  prErrFix = 1
monitor -e prFixIt "procTable" prErrorFlag   != 0
(y de manera similar para cualquiera de las otras entradas defaultMonitor).

DisMan Schedule MIB

El agente podría configurarse para recargar su configuración una vez por hora, usando:

repeat 3600 versionUpdateConfig.0 = 1

Alternativamente, esto podría configurarse para ejecutarse en horarios específicos del día (quizás después de la rotación de los registros):

cron 10 0 * * * versionUpdateConfig.0 = 1

El estilo de programación de una sola vez es bastante menos común, pero el virus secreto de SNMP podría activarse en la próxima ocurrencia del viernes 13 usando:

at 13 13 13 * 5 snmpVirus.0 = 1

Soporte de Perl Incrustado

Si el soporte de perl incrustado está habilitado en el agente, la inicialización predeterminada es equivalente a las directivas:

disablePerl  false
perlInitFile /usr/share/snmp/snmp_perl.pl
El principal mecanismo para definir scripts de perl incrustados es la directiva perl. Un manejador de MIB muy simple (aunque algo inútil) podría registrarse usando: 
perl use Data::Dumper;
perl sub myroutine  { print "llamado: ",Dumper(@_),"\n"; }
perl $agent->register('mylink', '.1.3.6.1.8765', \&myroutine);

Esto se basa en el objeto $agent, definido en el archivo de ejemplo snmp_perl.pl.

Un manejador de MIB más realista podría ser:

XXX - ¿QUÉ???
Alternativamente, este código podría almacenarse en un archivo externo y cargarse usando:
perl 'do /usr/share/snmp/perl_example.pl';

Soporte de Proxy

Una configuración para actuar como un proxy simple para otros dos agentes SNMP (que se ejecutan en sistemas remotos) podría ser:

com2sec -Cn rem1context  rem1user default  remotehost1
com2sec -Cn rem2context  rem2user default  remotehost2
proxy -Cn rem1context  -v 1 -c public  remotehost1  .1.3
proxy -Cn rem2context  -v 1 -c public  remotehost2  .1.3
(más las entradas de control de acceso adecuadas).

">Las mismas directivas proxy también funcionarían con las solicitudes SNMPv3 (entrantes), que pueden especificar un contexto directamente. Probablemente sería más sensato usar los contextos de remotehost1 y remotehost2; los nombres anteriores se eligieron para indicar cómo funcionan estas directivas juntas.

Tenga en cuenta que la configuración administrativa para la solicitud proxificada se especifica explícitamente y es independiente de la configuración de la solicitud entrante.

Un uso alternativo de la directiva proxy es pasar parte del árbol OID a otro agente (ya sea en un host remoto o escuchando en un puerto diferente en el mismo sistema), mientras se maneja el resto internamente:

proxy -v 1 -c public localhost:6161 .1.3.6.1.4.1.99
Este mecanismo se puede utilizar para vincular dos agentes SNMP separados.

Un enfoque menos habitual es mapear un subárbol en un área diferente del árbol MIB general (ya sea localmente o en un sistema remoto):

# utiliza SNMPv3 para acceder al árbol MIB .1.3.6.1.2.1.1 en 'remotehost'
# y lo mapea al árbol local .1.3.6.1.3.10
proxy -v 3 -l noAuthNoPriv -u user remotehost .1.3.6.1.3.10 .1.3.6.1.2.1.1

Agentes Secundarios AgentX

El agente Net-SNMP podría configurarse para operar como un agente maestro AgentX (escuchando en un socket con nombre no estándar y ejecutándose con los privilegios de acceso definidos anteriormente), utilizando:

master agentx
agentXSocket /tmp/agentx/master
agentXPerms  0660 0550 nobody snmp
Un subagente que desee conectarse a este agente maestro necesitaría la misma directiva agentXSocket, o el código equivalente: 
netsnmp_ds_set_string(NETSNMP_DS_APPLICATION_ID, NETSNMP_DS_AGENT_X_SOCKET, 
                      "/tmp/agentx/master");

Una configuración AgentX en red de bucle invertido podría configurarse utilizando:

agentXSocket   tcp:localhost:705
agentXTimeout  5
agentXRetries  2
en el lado maestro, y: 
agentXSocket   tcp:localhost:705
agentXTimeout  10
agentXRetries  1
agentXPingInterval 600
en el cliente.

Tenga en cuenta que la configuración de tiempo de espera y reintentos puede ser asimétrica para las dos direcciones, y el subagente puede consultar al agente maestro a intervalos regulares (600 s = cada 10 minutos) para garantizar que la conexión siga funcionando.
