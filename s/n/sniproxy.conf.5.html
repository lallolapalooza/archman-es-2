NOMBRE

sniproxy.conf - archivo de configuración de sniproxy

SINÓPSIS

/etc/sniproxy.conf

DESCRIPCIÓN

/etc/sniproxy.conf es el archivo de configuración para sniproxy. Las declaraciones están separadas por un salto de línea o un punto y coma. Las líneas que comienzan con # son comentarios. La configuración se divide en secciones delimitadas por llaves. Los caracteres pueden escaparse usando \. Las directivas de configuración pueden abreviarse siempre que no sean ambiguas, por ejemplo, user daemon en lugar de username daemon.

NOMBRE DE USUARIO

username daemon

Especifica el usuario con el que se ejecutará sniproxy. Cuando sniproxy se lanza como superusuario, degradará sus permisos a este usuario.

ARCHIVO PID

pidfile /var/run/sniproxy.pid

Especifica la ruta al archivo PID. El directorio debe ser escribible por el usuario con el que se ejecuta sniproxy.

REGISTRO DE ERRORES

error_log {
    syslog daemon
    priority notice
}

Especifica cómo se deben manejar los mensajes de error. Los mensajes pueden registrarse en syslog usando la directiva syslog, que especifica que los registros deben ir a una instalación de syslog dada. Alternativamente, se puede especificar la directiva filename para registrar en un archivo; estas dos opciones son mutuamente excluyentes. La directiva priority indica qué nivel de severidad de los mensajes deben registrarse. Las prioridades aceptadas son las prioridades estándar de syslog, en orden creciente de verbosidad: emergency, alert, critical, error, warning, notice, info y debug.

REGISTRO DE ACCESO

access_log {
    filename /var/log/sniproxy/access.log
}

Especifica cómo se deben registrar las conexiones, puede ser sobrescrito en un listener específico. Las conexiones se registran después de que los sockets del cliente y del servidor se hayan cerrado. Las directivas syslog y priority pueden usarse aquí, al igual que en error_log.

RESOLVER

resolver {
    nameserver 127.0.0.1
    mode ipv6_first
}

Especifica cómo se deben resolver las consultas DNS. Esto solo es necesario si se utilizan nombres de host como direcciones en la configuración o si se utilizan backends comodín. Si no se especifica, las consultas solo IPv4 se realizarán utilizando los servidores de nombres predeterminados del sistema.

Se admiten cuatro modos:

ipv4_only: consulta registros A, utiliza el primer registro A devuelto (siguiendo registros CNAME).

ipv6_only: consulta registros AAAA, utiliza el primer registro AAAA devuelto (siguiendo registros CNAME).

ipv4_first: consulta registros A y AAAA, espera a que ambas consultas se completen, utiliza el primer registro A si lo hay, de lo contrario utiliza el primer registro AAAA.

ipv6_first: consulta registros A y AAAA, espera a que ambas consultas se completen, utiliza el primer registro AAAA si lo hay, de lo contrario utiliza el primer registro A.

Se recomienda encarecidamente utilizar un servidor de nombres local, ya que un único socket se reutiliza para todas las consultas DNS y, por lo tanto, el número de puerto UDP es predecible, dejando la consulta solo protegida de respuestas falsificadas por el ID de consulta de 16 bits. Además, dado que no se realiza ningún almacenamiento en caché DNS interno, un resolver local puede mejorar el rendimiento.

LISTENER

listener 192.0.2.10:80 {
    protocol http
    reuseport yes
    table http_hosts
    fallback 192.0.2.100:80
    bad_requests log
    source 192.0.2.10
    access_log {
        filename /var/log/sniproxy/http_access.log
    }
}
listener [::]:80 {
    protocol http
    ipv6_v6only yes
    table http_hosts
    fallback unix:/var/run/http_fallback_unix.sock
}

Define una dirección de escucha para aceptar nuevas conexiones de clientes. Las direcciones pueden especificarse como una literal IPv4 seguida de un número de puerto TCP, una literal IPv6 seguida de un número de puerto TCP, un número de puerto TCP solo o una ruta de socket Unix prefijada con 'unix:'.

Protocol define cómo se debe analizar la solicitud del cliente para obtener el nombre de host solicitado. Se admiten dos protocolos: http y tls.

La directiva reuseport controla si el puerto se abre en modo SO_REUSEPORT, lo que permite ejecutar varias instancias de sniproxy en el mismo par ip:puerto. Esto nos permite balancear uniformemente las conexiones entrantes entre estas instancias sin el uso de ningún proxy de balanceo de carga externo. Requiere el kernel de Linux 3.9+. Establecer reuseport en "yes" habilita esta funcionalidad.

La directiva ipv6_v6only controla si al escuchar en la dirección genérica IPv6 '::' se aceptarán conexiones a cualquier dirección IPv4, así como a una dirección IPv6. Esto es útil si el usuario desea configuraciones diferentes para IPv4 e IPv6 o desea manejar el tráfico IPv4 con otro servidor/proxy. Esto solo es aplicable a los listeners IPv6 y se ignora en otros listeners.

Table especifica el nombre de la tabla utilizada para buscar a qué servidor reenviar la conexión basándose en el nombre de host extraído de la solicitud inicial del cliente. Si no se especifica la directiva table, se utilizará la tabla predeterminada, sin nombre.

La directiva fallback especifica un servidor que se utilizará si la solicitud del cliente no se puede analizar, si no se puede encontrar un servidor en la tabla para el nombre de host especificado o si el nombre de host no se puede resolver. Esto debería ser una dirección IP y un puerto, o una ruta de socket Unix.

La directiva bad_requests permite registrar el contenido de la solicitud del cliente si no es analizable, esto es útil para depuración.

La directiva source permite especificar una dirección específica para enlazar antes de conectarse al servidor backend. En la mayoría de los casos, es mejor omitir esta opción y permitir que el sistema operativo seleccione la dirección de salida automáticamente. No incluya un número de puerto en esta dirección, ya que hacerlo limitará el proxy a una sola conexión simultánea a cada servidor a la vez.

La configuración del registro de acceso puede ser sobrescrita en cada listener.

TABLA

table http_hosts {
    ^example\.com$ 192.0.2.101
    ^example\.net$ 192.0.2.102
    ^example\.org$ 192.0.2.103 proxy_protocol
}

Las tablas definen cómo mapear cada nombre de host a un servidor backend. El nombre de host de cada solicitud se compara con las entradas de la tabla en orden, hasta que se encuentra una coincidencia y se utiliza ese servidor. La dirección del servidor puede ser una IP, una IP y un puerto, una ruta de socket Unix, un nombre de host o '*'. Si no se especifica un puerto, se utilizará el puerto del listener en el que se recibió la conexión.

La opción opcional proxy_protocol antepondrá una cabecera de protocolo PROXY v1 de HAProxy a la conexión reenviada, permitiendo a los servidores web compatibles obtener la IP y el puerto de origen y destino de la conexión TCP entrante original.
