snmpd(8)

Paquete: net-snmp

Licencias: BSD

SNMPD(8) Net-SNMP SNMPD(8)

NOMBRE

snmpd - demonio para responder a paquetes de solicitud SNMP.

SINOPSIS

snmpd [OPCIONES] [DIRECCIONES DE ESCUCHA]

DESCRIPCIÓN

snmpd es un agente SNMP que se vincula a un puerto y espera solicitudes del software de gestión SNMP. Al recibir una solicitud, procesa la(s) solicitud(es), recopila la información solicitada y/o realiza la(s) operación(es) solicitada(s) y devuelve la información al remitente.

OPCIONES

-a
Registra las direcciones de origen de las solicitudes entrantes.
-A
Añade al archivo de registro en lugar de truncarlo.
-c FICHERO
Lee FICHERO como un archivo de configuración (o una lista de archivos de configuración separados por comas). Ten en cuenta que el archivo cargado solo entenderá tokens de snmpd.conf, a menos que el tipo de configuración se especifique en el archivo, como se describe en la página del manual de snmp_config bajo CAMBIO DE TIPOS DE CONFIGURACIÓN EN MEDIO DEL ARCHIVO.
-C
No lee ningún archivo de configuración excepto los especificados opcionalmente por la opción -c. Ten en cuenta que este comportamiento también cubre los archivos de configuración persistentes. Esto puede dar lugar a que los valores asignados dinámicamente se restablezcan tras un reinicio del agente, a menos que los archivos de configuración persistentes relevantes se carguen explícitamente usando la opción -c.
-d
Muestra (en hexadecimal) los paquetes SNMP enviados y recibidos.
-D[TOKEN[,...]]
Activa la salida de depuración para el(los) TOKEN(s) dado(s). Sin tokens especificados, por defecto imprime todos los tokens (lo que es equivalente a la palabra clave "ALL"). Puedes probar con ALL para una salida extremadamente detallada. Nota: No puedes poner un espacio entre la bandera -D y los TOKENs listados.
-f
No crea un fork() del shell que llama.
-g GID
Cambia el ID de grupo del proceso snmpd a GID después de abrir los sockets de escucha. Esto anula el parámetro del archivo de configuración agentgroup.
-h, --help
Muestra un breve mensaje de uso y luego sale.
-H
Muestra una lista de directivas de archivo de configuración entendidas por el agente y luego sale.
-I [-]INITLIST
Especifica qué módulos deben (o no deben) inicializarse cuando el agente se inicia. Si la INITLIST separada por comas va precedida de un '-', es la lista de módulos que *no* deben iniciarse. De lo contrario, es la lista de los *únicos* módulos que deben iniciarse.

Para obtener una lista de los módulos compilados, ejecuta el agente con los argumentos -Dmib_init -H (suponiendo que se ha compilado soporte de depuración).

-L[eEfFoOsSnN]
Especifica a dónde se debe dirigir la salida del registro (salida estándar o error, a un archivo o a través de syslog). Consulta OPCIONES DE REGISTRO en snmpcmd(1) para más detalles.
-m LISTA_MIB
Especifica una lista separada por dos puntos de módulos MIB para cargar para esta aplicación. Esto anula la variable de entorno MIBS. Consulta snmpcmd(1) para más detalles.
-M LISTA_DIR
Especifica una lista separada por dos puntos de directorios para buscar MIBs. Esto anula la variable de entorno MIBDIRS. Consulta snmpcmd(1) para más detalles.
-n NOMBRE
Establece un nombre de aplicación alternativo (que afectará a los archivos de configuración cargados). Por defecto será snmpd, independientemente del nombre del binario real.
-p FICHERO
Guarda el ID de proceso del demonio en FICHERO.
-q
Imprime una salida más simple para facilitar el análisis automático.
-r
No requiere acceso root para ejecutar el demonio. Específicamente, no sale si no se pueden abrir archivos accesibles solo para root (como /dev/kmem etc.).
-u UID
Cambia el ID de usuario del proceso snmpd a UID (que puede ser numérico o textual) después de abrir los sockets de escucha. Esto anula el parámetro del archivo de configuración agentuser.
-U
Indica al agente que no elimine su archivo pid (ver opción -p) al cerrarse. Anula el token leave_pidfile en el archivo snmpd.conf, ver snmpd.conf(5).
-v, --version
Imprime la información de la versión del agente y luego sale.
-V
Muestra simbólicamente las transacciones SNMP.
-x DIRECCIÓN
Escucha conexiones AgentX en la dirección especificada en lugar de la predeterminada "/var/agentx/master". La dirección puede ser una ruta de socket de dominio Unix o la dirección de una interfaz de red. El formato es el mismo que el formato de las direcciones de escucha descritas a continuación.
-X
Se ejecuta como subagente AgentX en lugar de como agente maestro SNMP.
--nombre="valor"
Permite especificar cualquier token ("nombre") compatible en el archivo snmpd.conf y establece su valor a "valor". Anula el token correspondiente en el archivo snmpd.conf. Consulta snmpd.conf(5) para la lista completa de tokens.

DIRECCIONES DE ESCUCHA

Por defecto, snmpd escucha las solicitudes SNMP entrantes en el puerto UDP 161 en todas las interfaces IPv4. Sin embargo, es posible modificar este comportamiento especificando una o más direcciones de escucha como argumentos para snmpd. Una dirección de escucha tiene el formato:

[<especificador-transporte>:]<dirección-transporte>

En su forma más simple, una dirección de escucha puede consistir solo en un número de puerto, en cuyo caso snmpd escucha en ese puerto UDP en todas las interfaces IPv4. De lo contrario, la parte de <dirección-transporte> de la especificación se analiza según la siguiente tabla:

<especificador-transporte>
Formato de <dirección-transporte>
udp (predeterminado)
hostname[:puerto] o dirección-IPv4[:puerto]
tcp
hostname[:puerto] o dirección-IPv4[:puerto]
unix
ruta-de-archivo
ipx
[red]:nodo[/puerto]
aal5pvc o pvc
[interfaz.][VPI.]VCI
udp6 o udpv6 o udpipv6
hostname[:puerto] o dirección-IPv6[:puerto]
tcp6 o tcpv6 o tcpipv6
hostname[:puerto] o dirección-IPv6[:puerto]
ssh
hostname:puerto
dtlsudp
hostname:puerto

Ten en cuenta que las cadenas de <especificador-transporte> no distinguen entre mayúsculas y minúsculas, por lo que, por ejemplo, "tcp" y "TCP" son equivalentes. Aquí tienes algunos ejemplos, junto con su interpretación:

127.0.0.1:161
escuchar en el puerto UDP 161, pero solo en la interfaz de loopback. Esto impide que snmpd sea consultado remotamente. La especificación del puerto ":161" no es estrictamente necesaria ya que es el puerto SNMP predeterminado.
TCP:1161
escuchar en el puerto TCP 1161 en todas las interfaces IPv4.
ipx:/40000
escuchar en el puerto IPX 40000 en todas las interfaces IPX.
unix:/tmp/l
escuchar en el socket de dominio Unix especificado.

DIRECCIONES_DE_ESCUCHA

Las siguientes direcciones de transporte son ejemplos que se pueden usar para el parámetro agentAddress. Tenga en cuenta que la sintaxis general es transporte:dirección.

tcp:localhost:161
escuchar en el puerto TCP 161 en la interfaz localhost.
tcp:192.168.0.1:10161
escuchar en el puerto TCP 10161 en la interfaz 192.168.0.1.
udp:161
escuchar en el puerto UDP 161 en todas las interfaces IPv4.
udp6:161
escuchar en el puerto UDP 161 en todas las interfaces IPv6.
tcp6:161
escuchar en el puerto TCP 161 en todas las interfaces IPv6.
unix:/tmp/local-agent
escuchar en el socket de dominio Unix /tmp/local-agent.
/tmp/local-agent
es idéntico a la especificación anterior, ya que se asume el dominio Unix si el primer carácter de la <dirección-transporte> es '/'.
PVC:161
escuchar en el circuito virtual permanente AAL5 con VPI=0 y VCI=161 (decimal) en el primer adaptador ATM de la máquina.
udp6:10161
escuchar en el puerto 10161 en todas las interfaces IPv6.
ssh:127.0.0.1:22
Permite conexiones desde el subsistema snmp en el servidor ssh en el puerto 22. Los detalles del uso de SNMP sobre SSH se definen a continuación.
dtlsudp:127.0.0.1:9161
Escuchar conexiones sobre DTLS en el puerto UDP 9161. El archivo snmp.conf debe tener definidos los tokens de configuración serverCert,.

Tenga en cuenta que no todos los dominios de transporte enumerados anteriormente estarán siempre disponibles; por ejemplo, los hosts sin soporte IPv6 no podrán utilizar direcciones de transporte udp6, y los intentos de hacerlo resultarán en el error "Error al abrir el punto final especificado". Del mismo modo, dado que el soporte de PVC AAL5 solo está disponible actualmente en Linux, fallará con el mismo error en otras plataformas.

Notas Específicas de Transporte

ssh
El transporte SSH, en el lado del servidor, es en realidad solo una tubería con nombre de unix a la que se puede conectar a través de un subsistema ssh configurado en el servidor ssh principal. La ubicación de la tubería (configurable con el token sshtosnmpsocket en snmp.conf) es /var/net-snmp/sshtosnmp. Los paquetes deben enviarse a ella a través de la aplicación sshtosnmp, que también envía el ID de usuario al iniciar la conexión. Se debe utilizar el modelo de seguridad TSM cuando los paquetes deban procesarse.
El comando sshtosnmp sabe cómo conectarse a esta tubería y comunicarse con ella. Debe configurarse en el archivo de configuración de OpenSSH sshd (que normalmente es /etc/ssh/sshd_config utilizando la siguiente línea de configuración:
Subsystem snmp /usr/local/bin/sshtosnmp
El comando sshtosnmp necesitará acceso de lectura/escritura a la tubería /var/net-snmp/sshtosnmp. Aunque debería ser bastante seguro conceder acceso al usuario medio ya que todavía requiere modificaciones en la configuración de la ACM antes de que el usuario pueda realizar operaciones, los administradores paranoicos pueden querer hacer que el directorio /var/net-snmp solo sea accesible por usuarios de un grupo en particular. Utilice la opción de configuración de snmp.conf sshtosnmpsocketperms para establecer los permisos, el propietario y el grupo del socket creado.
Se puede conceder acceso al usuario "foo" utilizando el siguiente estilo de configuraciones sencillas de snmpd.conf:
rouser -s tsm foo authpriv
Tenga en cuenta que "authpriv" es aceptable asumiendo que SSH protege todo de esa manera (asumiendo que tiene una configuración no insana). snmpd no tiene idea de cómo SSH ha protegido realmente un paquete y, por lo tanto, el agente snmp asume que todos los paquetes que pasan por el transporte SSH han sido protegidos al nivel authpriv.
dtlsudp
El protocolo DTLS, que se basa en TLS, requiere certificados tanto del cliente como del servidor para establecer la conexión y autenticar ambas partes. Para hacer esto, el cliente necesitará configurar el archivo snmp.conf con los tokens de configuración clientCert. El servidor necesitará configurar el archivo snmp.conf con los tokens de configuración serverCert definidos.
La configuración del control de acceso es similar al transporte ssh, ya que se debe utilizar el modelo de seguridad TSM para proteger el paquete.

ARCHIVOS_DE_CONFIGURACIÓN

snmpd comprueba la existencia y analiza los siguientes archivos:

/etc/snmp/snmp.conf
Configuración común para el agente y las aplicaciones. Ver snmp.conf(5) para más detalles.
/etc/snmp/snmpd.conf
/etc/snmp/snmpd.local.conf
Configuración específica del agente. Ver snmpd.conf(5) para más detalles. Estos archivos son opcionales y pueden usarse para configurar el control de acceso, la generación de trampas, los protocolos de subagente y mucho más.
Además de estos dos archivos de configuración en /etc/snmp, el agente leerá cualquier archivo con los nombres snmpd.conf y snmpd.local.conf en una ruta separada por dos puntos especificada en la variable de entorno SNMPCONFPATH.
/usr/share/snmp/mibs/
El agente también cargará todos los archivos de este directorio como MIBs. Sin embargo, no cargará ningún archivo que comience con un '.' ni descenderá a subdirectorios.
