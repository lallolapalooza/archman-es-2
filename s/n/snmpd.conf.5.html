NOMBRE

snmpd.conf - archivo de configuración para el agente SNMP de Net-SNMP

DESCRIPCIÓN

El agente Net-SNMP utiliza uno o más archivos de configuración para controlar su funcionamiento y la información de gestión que proporciona. Estos archivos (snmpd.conf y snmpd.local.conf) pueden ubicarse en varias localizaciones, como se describe en la página del manual snmp_config(5).

La aplicación (perl) snmpconf puede utilizarse para generar archivos de configuración para los requisitos más comunes del agente. Vea la página del manual snmpconf(1) para más información, o intente ejecutar el comando:

snmpconf -g basic_setup

Hay un gran número de directivas que se pueden especificar, pero estas se dividen principalmente en cuatro categorías distintas:

  • las que controlan quién puede acceder al agente
  • las que configuran la información que suministra el agente
  • las que controlan la monitorización activa del sistema local
  • las relacionadas con la extensión de la funcionalidad del agente.

Algunas directivas no encajan de forma natural en ninguna de estas cuatro categorías, pero esto cubre la mayoría del contenido de un archivo snmpd.conf típico. Una lista completa de directivas reconocidas se puede obtener ejecutando el comando:

snmpd -H

COMPORTAMIENTO DEL AGENTE

Aunque la mayoría de las directivas de configuración se refieren a la información MIB proporcionada por el agente, hay un puñado de directivas que controlan el comportamiento de snmpd considerado simplemente como un demonio que proporciona un servicio de red.

agentaddress [<especificador-transporte>:]<dirección-transporte>[,...]
define una lista de direcciones de escucha, en las que recibir solicitudes SNMP entrantes. Vea la sección DIRECCIONES DE ESCUCHA en la página del manual snmpd(8) para más información sobre el formato de las direcciones de escucha.
El comportamiento predeterminado es escuchar en el puerto UDP 161 en todas las interfaces IPv4.
agentgroup {GRUPO|#GID}
cambia al grupo especificado después de abrir el(los) puerto(s) de escucha. Esto puede referirse a un grupo por nombre (GRUPO), o a un ID de grupo numérico que comienza con '#' (#GID).
agentuser {USUARIO|#UID}
cambia al usuario especificado después de abrir el(los) puerto(s) de escucha. Esto puede referirse a un usuario por nombre (USUARIO), o a un ID de usuario numérico que comienza con '#' (#UID).
leave_pidfile yes
instruye al agente para que no elimine su archivo pid al apagarse. Equivalente a especificar "-U" en la línea de comandos.
maxGetbulkRepeats NUM
Establece el número máximo de respuestas permitidas para una única variable en una solicitud getbulk. Se establece en 0 para habilitar el valor predeterminado y en -1 para habilitar ilimitado. Dado que la memoria se asigna por adelantado, establecerlo en ilimitado no se considera seguro si su población de usuarios no es confiable. Un número de repetición mayor que este se truncará a este valor.
Esto se establece por defecto en -1.
maxGetbulkResponses NUM
Establece el número máximo de respuestas permitidas para una solicitud getbulk. Esto se establece por defecto en 100. Se establece en 0 para habilitar el valor predeterminado y en -1 para habilitar ilimitado. Dado que la memoria se asigna por adelantado, establecerlo en ilimitado no se considera seguro si su población de usuarios no es confiable.
En general, el número total de respuestas no se permitirá exceder el número de maxGetbulkResponses, y el número total devuelto será un múltiplo entero del número de variables solicitadas multiplicado por el número calculado de repeticiones permitidas para mantenerse por debajo de este número.
Tenga en cuenta también que el procesamiento de maxGetbulkRepeats se maneja primero.
ifmib_max_num_ifaces NUM
Establece el número máximo de interfaces incluidas en la recopilación de datos de IF-MIB. Para servidores con un gran número de interfaces (ppp, dummy, bridge, etc.), el procesamiento de IF-MIB consumirá una gran cantidad de CPU para las llamadas ioctl (en Linux). Establecer un máximo razonable para la CPU utilizada reducirá la carga de CPU para el procesamiento de IF-MIB. Por ejemplo, configurar "ifmib_max_num_ifaces 500" incluirá solo las primeras 500 interfaces basadas en ifindex e ignorará todas las demás para el procesamiento de IF-MIB.
El valor predeterminado (sin configurar esto) es incluir todas las interfaces.
include_ifmib_iface_prefix PREFIJO1 PREFIJO2 ...
Establece los prefijos de nombre de interfaz a incluir en la recopilación de datos de IF-MIB. Para servidores con un gran número de interfaces (ppp, dummy, bridge, etc.), el procesamiento de IF-MIB consumirá una gran cantidad de CPU para las llamadas ioctl (en Linux). Un conjunto de prefijos de nombre de interfaz separados por espacios reducirá la carga de CPU para el procesamiento de IF-MIB. Por ejemplo, configurar "include_ifmib_iface_prefix eth dummy lo" incluirá solo las interfaces con estos prefijos e ignorará todas las demás para el procesamiento de IF-MIB. Si el soporte de expresiones regulares está compilado, cada uno de los prefijos es una expresión regular (que no puede contener un carácter de espacio o tabulación).
El valor predeterminado (sin configurar esto) es incluir todas las interfaces.

Configuración de SNMPv3 - Seguridad Real

SNMPv3 añade modelos de seguridad flexibles a la estructura del paquete SNMP para que se puedan utilizar múltiples soluciones de seguridad. SNMPv3 se definió originalmente con un "Modelo de Seguridad Basado en Usuarios" (USM) [RFC3414] que requería mantener una base de datos de usuarios específica de SNMP. Posteriormente, se determinó que era problemático de mantener y tenía algunos problemas menores de seguridad. El IETF ha añadido desde entonces modelos de seguridad adicionales para tunelizar SNMP sobre SSH [RFC5592] y DTLS/TLS [RFC-por-publicar]. Net-SNMP contiene un soporte robusto para SNMPv3/USM, SNMPv3/TLS y SNMPv3/DTLS. Contiene soporte parcial para SNMPv3/SSH, pero no ha sido tan extensamente probado. También contiene código para soportar un experimental SNMPv3 basado en Kerberos que nunca se estandarizó.

Esperemos que más software y dispositivos SNMP soporten finalmente SNMP sobre (D)TLS o SNMP sobre SSH, pero es probable que los dispositivos con soporte original para SNMP solo contengan soporte para usuarios USM. Si su administrador de red soporta SNMP sobre (D)TLS o SNMP sobre SSH, le sugerimos que utilice uno de estos mecanismos en lugar de usar USM, pero como siempre con Net-SNMP, le damos las opciones para elegir para que pueda tomar la decisión que sea mejor para usted.

Parámetros genéricos de SNMPv3

Estos parámetros son genéricos para todas las formas de SNMPv3. El protocolo SNMPv3 define "engineIDs" que identifican de forma única un agente. La cadena debe ser consistente a lo largo del tiempo y no debe cambiar ni entrar en conflicto con el engineID de otro agente. Nunca. Internamente, Net-SNMP crea por defecto un engineID único basado en la hora actual del sistema y un número aleatorio. Esto debería ser suficiente para la mayoría de los usuarios, a menos que esté incrustando nuestro agente en un dispositivo donde estos números no varíen en el arranque inicial de las máquinas.

Los EngineIDs se utilizan tanto como un "contexto" para seleccionar información del dispositivo, como en SNMPv3 con USM se utilizan para crear entradas únicas para los usuarios en su tabla de usuarios.
El agente Net-SNMP ofrece los siguientes mecanismos para establecer el engineID, pero de nuevo, solo debe usarlos si sabe lo que está haciendo:
engineID CADENA
especifica que el engineID debe construirse a partir de la cadena de texto dada.
engineIDType 1|2|3
especifica que el engineID debe construirse a partir de la dirección IPv4 (1), dirección IPv6 (2) o dirección MAC (3). Tenga en cuenta que cambiar la dirección IP (o cambiar la tarjeta de interfaz de red) puede causar problemas.

Este sitio no está asociado de ninguna forma con Arch Linux ni afiliado a este proyecto. El contenido es únicamente una traducción de las páginas del manual de Arch publicadas en man.archlinux.org.

engineIDNic INTERFAZ
define qué interfaz se utilizará al determinar la dirección MAC. Si el engineIDType 3 no se especifica, esta directiva no tiene ningún efecto.
El valor predeterminado es usar eth0.

SNMPv3 sobre TLS

SNMPv3 puede ser tunelizado sobre TLS y DTLS. TLS se ejecuta sobre TCP y DTLS es el equivalente UDP. Wes Hardaker (el fundador de Net-SNMP) realizó un estudio y lo presentó en una reunión de la IETF que demostró que los protocolos basados en TCP son suficientes para redes estables, pero rápidamente se convierten en un problema en redes inestables con niveles moderados de pérdida de paquetes (~ 20-30%). Si va a usar TLS o DTLS, debe usar el que sea apropiado para su entorno de red. Debería considerar activar ambos para que su sistema de gestión pueda acceder al puerto UDP o TCP según sea necesario.

Muchas de las directivas de configuración descritas a continuación se prefijan con la etiqueta '[snmp]'. Si coloca estas directivas en su archivo snmpd.conf, esta etiqueta es obligatoria. Consulte la página del manual snmp_config(5) para conocer el significado de este cambio de contexto.

[snmp] localCert <especificador>
Esta directiva define la clave pública X.509 predeterminada a utilizar como identidad del servidor. Debe ser una huella digital o un nombre de archivo. Para crear una clave pública para su uso, ejecute la utilidad "net-snmp-cert", que le ayudará a crear el certificado necesario.
El valor predeterminado para esto es el certificado en el archivo de certificado llamado "snmpd".
[snmp] tlsAlgorithms <algoritmos>
Esta cadena seleccionará los algoritmos a utilizar al negociar la seguridad durante el establecimiento de la sesión (D)TLS. Consulte la página del manual de openssl ciphers(1) para obtener detalles sobre el formato. Ejemplos de cadenas incluyen:
DEFAULT
ALL
HIGH
HIGH:!AES128-SHA
El valor predeterminado es el que openssl mismo fue configurado.
[snmp] x509CRLFile
Si está utilizando una Autoridad de Certificación (CA) que publica una Lista de Revocación de Certificados (CRL), entonces esta directiva puede usarse para especificar la ubicación en el sistema de archivos de una copia del archivo CRL. Tenga en cuenta que Net-SNMP no descargará una CRL a través de http y debe ser un archivo, no una URL. Además, OpenSSL no recarga un archivo CRL cuando ha cambiado, por lo que las modificaciones o actualizaciones del archivo solo se notarán al reiniciar el agente snmpd.
certSecName PRIORIDAD HUELLA_DIGITAL OPCIONES
OPCIONES puede ser una de <--sn SECNAME | --rfc822 | --dns | --ip | --cn | --any>.
La directiva certSecName especificará cómo mapear un campo de certificado del certificado X.509 del cliente a un nombre de usuario SNMPv3. Utilice la bandera --sn SECNAME para especificar directamente un nombre de seguridad para un certificado dado. Las otras banderas extraen un componente particular del certificado para usarlo como un nombre de seguridad snmpv3. Estos campos son: un SubjectAltName que contiene un valor rfc822 (por ejemplo, hardaker@net-snmp.org), un SubjectAltName que contiene un valor de nombre dns (por ejemplo, foo.net-snmp.org), una dirección IP (por ejemplo, 192.0.2.1) o un nombre común "Wes Hardaker". La bandera --any especifica que se pueden usar cualquiera de los campos subjecAltName. Asegúrese de que, una vez seleccionado un nombre de seguridad, se le otorgue autorización a través de los controles VACM discutidos más adelante en esta página del manual.
Consulte la página web http://www.net-snmp.org/wiki/index.php/Using_DTLS para obtener instrucciones más detalladas sobre la configuración de (D)TLS.
trustCert <especificador>
Para que X509 verifique correctamente un certificado, debe ser verificable hasta un ancla de confianza para él. Este ancla de confianza es típicamente un certificado de CA, pero también podría ser un certificado autofirmado. La directiva "trustCert" debe usarse para cargar anclas de confianza específicas en el motor de verificación.

SNMP sobre (D)TLS requiere el uso del Modelo de Seguridad de Transporte (TSM), así que lea también la sección sobre el uso del Modelo de Seguridad de Transporte. Asegúrese de que al configurar el VACM para aceptar conexiones de (D)TLS, utilice el modelo de seguridad "tsm". Por ejemplo:

rwuser -s tsm hardaker@net-snmp.org

Soporte SNMPv3 sobre SSH

Para usar SSH, necesitará configurar sshd para invocar el programa sshtosnmp, así como configurar los ajustes de control de acceso para permitir el acceso a través del modelo de seguridad tsm utilizando el nombre de usuario proporcionado a snmpd por el transporte ssh.

SNMPv3 con el Modelo de Seguridad de Transporte (TSM)

El Modelo de Seguridad de Transporte [RFC5591] define un sistema de seguridad SNMPv3 para usar con protocolos de seguridad "tunelizados" como TLS, DTLS y SSH. Es un modelo de seguridad muy simple que simplemente permite que los paquetes debidamente protegidos pasen a la aplicación snmp. El transporte está obligado a pasar un nombre de seguridad a usar al TSM y el TSM puede prefijarlo opcionalmente con una cadena de transporte (ver abajo).

tsmUseTransportPrefix (1|yes|true|0|no|false)
Si se establece en true, el módulo TSM tomará cada nombre de seguridad que se le pase desde los transportes inferiores y lo prefijará con una cadena que identifica específicamente el transporte del que provino. Esto es útil para evitar conflictos de nombres de seguridad con transportes que generan nombres de seguridad idénticos. Por ejemplo, si el transporte de seguridad ssh entregó el nombre de seguridad "hardaker" para una conexión SSH y el transporte de seguridad TLS también entregó el nombre de seguridad "hardaker" para una conexión TLS, entonces sería imposible separar estos dos usuarios para proporcionar derechos de control de acceso separados. Con tsmUseTransportPrefix establecido en true, sin embargo, los nombres de seguridad se prefijarán apropiadamente con uno de: "tls:", "dtls:" o "ssh:".

SNMPv3 con el Modelo de Seguridad Basado en Usuario (USM)

SNMPv3 se definió originalmente utilizando el Modelo de Seguridad Basado en Usuario (USM), que contiene una lista privada de usuarios y claves específicas del protocolo SNMPv3. Sin embargo, la comunidad operativa lo declaró una molestia de manipular otra base de datos y preferiría usar la infraestructura existente. Con ese fin, la IETF creó el grupo de trabajo ISMS para abordar ese problema, y el grupo de trabajo ISMS decidió tunelizar SNMP sobre SSH y DTLS para hacer uso de la infraestructura de usuarios y autenticación existente.

Usuarios SNMPv3 USM

Para usar los usuarios específicos de SNMPv3 basados en USM, deberá crearlos. Se recomienda usar el comando net-snmp-config para hacerlo, pero también puede hacerlo especificando directamente directivas createUser usted mismo en su lugar:

createUser [-e ENGINEID] nombre_usuario (MD5|SHA|SHA-512|SHA-384|SHA-256|SHA-224) contraseña_autenticacion [DES|AES] [contraseña_privacidad]
MD5|SHA|SHA-512|SHA-384|SHA-256|SHA-224 son los tipos de autenticación a usar. DES y AES son los protocolos de privacidad a usar. Si no se especifica la contraseña de privacidad, se asume que es la misma que la contraseña de autenticación. Tenga en cuenta que los usuarios creados serán inútiles a menos que también se agreguen a las tablas de control de acceso VACM descritas anteriormente.
La autenticación SHA|SHA-512|SHA-384|SHA-256|SHA-224 y la privacidad DES/AES requieren que OpenSSL esté instalado y que el agente se compile con soporte para OpenSSL. La autenticación MD5 puede usarse sin OpenSSL.
Advertencia: la longitud mínima de la frase de contraseña es de 8 caracteres.
Los usuarios SNMPv3 se pueden crear en tiempo de ejecución utilizando el comando snmpusm(1).
En lugar de averiguar cómo usar esta directiva y dónde colocarla (ver más abajo), simplemente ejecute "net-snmp-config --create-snmpv3-user" en su lugar, lo que agregará una de estas líneas en el lugar correcto.
Esta directiva debe colocarse en el archivo /var/net-snmp/snmpd.conf en lugar de las otras ubicaciones normales. La razón es que la información se lee del archivo y luego se elimina la línea (eliminando el almacenamiento de la contraseña maestra para ese usuario) y se reemplaza con la clave que se deriva de ella. Esta clave es una clave localizada, por lo que si se roba no se puede usar para acceder a otros agentes. Sin embargo, si se roba la contraseña, sí se puede.
Si necesita localizar el usuario a un EngineID particular (esto es útil principalmente en el archivo snmptrapd.conf similar), puede usar el argumento -e para especificar un EngineID como valor hexadecimal (por ejemplo, "0x01020304").
Si desea generar directamente sus claves maestras o localizadas, reemplace la contraseña dada con una cadena hexadecimal (precedida por un "0x") y preceda la cadena hexadecimal con una directiva -m o -l (respectivamente). Ejemplos:
[estas claves *no* son seguras pero son fáciles de analizar visualmente para
fines de conteo. Por favor, genere claves aleatorias en lugar de usar
estos ejemplos]
createUser miusuario SHA -l 0x0001020304050607080900010203040506070809 AES -l 0x00010203040506070809000102030405
createUser miusuario SHA -m 0x0001020304050607080900010203040506070809 AES -m 0x0001020304050607080900010203040506070809
Debido a la forma en que se realiza la localización, se espera que las claves de privacidad localizadas tengan la longitud requerida por el algoritmo (128 bits para todos los algoritmos admitidos). Sin embargo, las claves de cifrado maestras deben tener la longitud requerida por el algoritmo de autenticación, no la longitud requerida por el algoritmo de cifrado (MD5: 16 bytes, SHA: 20 bytes).

CONTROL DE ACCESO

snmpd admite el Modelo de Control de Acceso Basado en Vistas (VACM) definido en RFC 2575, para controlar quién puede recuperar o actualizar información. Con este fin, reconoce varias directivas relacionadas con el control de acceso.

Control de Acceso Tradicional

La mayoría de los requisitos simples de control de acceso se pueden especificar utilizando las directivas rouser

rwuser (para SNMPv3) o rocommunity/rwcommunity (para SNMPv1 o SNMPv2c).

rouser [-s SECMODEL] USUARIO [noauth|auth|priv [OID | -V VISTA [CONTEXTO]]]
rwuser [-s SECMODEL] USUARIO [noauth|auth|priv [OID | -V VISTA [CONTEXTO]]]
especifica un usuario SNMPv3 al que se le permitirá acceso de solo lectura (GET y GETNEXT) o de lectura-escritura (GET, GETNEXT y SET) respectivamente. Por defecto, esto proporcionará acceso a todo el árbol OID para solicitudes SNMPv3 autenticadas (incluyendo cifradas), utilizando el contexto predeterminado. Se puede especificar un nivel de seguridad mínimo alternativo usando noauth (para permitir solicitudes no autenticadas) o priv (para exigir el uso de cifrado). El campo OID restringe el acceso para ese usuario al subárbol enraizado en el OID dado, o a la vista con nombre. Opcionalmente, también se puede especificar un contexto, o "context*" para denotar un prefijo de contexto. Si no se especifica ningún campo de contexto (o se utiliza el token "*"), la directiva coincidirá con todos los contextos posibles.
Si se especifica SECMODEL, será el modelo de seguridad requerido para ese usuario (tenga en cuenta que nombres de usuario idénticos pueden provenir de diferentes modelos de seguridad y se separarán adecuadamente a través de la configuración de control de acceso). El modelo de seguridad predeterminado es "usm" y los otros modelos de seguridad comunes son probablemente "tsm" cuando se utiliza (D)TLS o soporte SSH y "ksm" si el soporte Kerberos se ha compilado en.
rocommunity COMUNIDAD [FUENTE [OID | -V VISTA [CONTEXTO]]]
rwcommunity COMUNIDAD [FUENTE [OID | -V VISTA [CONTEXTO]]]
especifica una comunidad SNMPv1 o SNMPv2c a la que se le permitirá acceso de solo lectura (GET y GETNEXT) o de lectura-escritura (GET, GETNEXT y SET) respectivamente. Por defecto, esto proporcionará acceso a todo el árbol OID para dichas solicitudes, independientemente de dónde se hayan enviado. El token FUENTE se puede utilizar para restringir el acceso a las solicitudes del sistema especificado (consulte com2sec para obtener todos los detalles). El campo OID restringe el acceso para esa comunidad al subárbol enraizado en el OID dado, o a la vista con nombre. Los contextos suelen ser menos relevantes para las versiones SNMP basadas en comunidad, pero el mismo comportamiento se aplica aquí.
rocommunity6 COMUNIDAD [FUENTE [OID | -V VISTA [CONTEXTO]]]
rwcommunity6 COMUNIDAD [FUENTE [OID | -V VISTA [CONTEXTO]]]
son directivas relacionadas con solicitudes recibidas usando IPv6 (si el agente soporta dichos dominios de transporte). La interpretación de los tokens FUENTE, OID, VISTA y CONTEXTO es exactamente la misma que para las versiones IPv4.

En cada caso, solo se debe especificar una directiva para un usuario SNMPv3 o una cadena de comunidad dada. **No** es apropiado especificar directivas rouser y rwuser que se refieran al mismo usuario SNMPv3 (o configuraciones de comunidad equivalentes). La directiva rwuser proporciona todo el acceso de rouser (además de permitir el soporte SET). Lo mismo ocurre con las directivas basadas en comunidad.

Los requisitos de acceso más complejos (como el acceso a dos o más subárboles OID distintos, o vistas diferentes para solicitudes GET y SET) deben usar uno de los otros mecanismos de control de acceso. Tenga en cuenta que si varias comunidades o usuarios SNMPv3 distintos necesitan obtener el mismo nivel de acceso, también sería más eficiente utilizar las directivas de configuración principales de VACM.

Configuración de VACM

La flexibilidad completa de VACM está disponible utilizando cuatro directivas de configuración: com2sec, group, view y access. Estas proporcionan una configuración directa de las tablas VACM subyacentes.

com2sec [-Cn CONTEXTO] NOMBRE_SEGURIDAD FUENTE COMUNIDAD
com2sec6 [-Cn CONTEXTO] NOMBRE_SEGURIDAD FUENTE COMUNIDAD
mapea una cadena de comunidad SNMPv1 o SNMPv2c a un nombre de seguridad, ya sea desde un rango particular de direcciones de origen o globalmente ("default"). Una fuente restringida puede ser un nombre de host (o dirección) específico, o una subred representada como IP/MÁSCARA (ej. 10.10.10.0/255.255.255.0), o IP/BITS (ej. 10.10.10.0/24), o los equivalentes IPv6. Una restricción precedida por un signo de exclamación (!) niega el acceso desde esa dirección o subred, por ejemplo, !10.10.10.0/24 niega las solicitudes de esas fuentes en esa subred. Las restricciones de negación deben ir antes de las de permiso. Por ejemplo, el siguiente ejemplo permite el acceso desde todo 10.0.0.0/8 excepto para 10.10.10.0/24:
com2sec sec1 !10.10.10.0/24 public
com2sec sec1 10.0.0.0/8 public
El acceso desde fuera de 10.0.0.0/8 seguiría siendo denegado.
La misma cadena de comunidad se puede especificar en varias directivas separadas (presumiblemente con diferentes tokens de fuente), y se seleccionará la primera combinación de fuente/comunidad que coincida con la solicitud entrante. Varias combinaciones de fuente/comunidad también pueden mapear al mismo nombre de seguridad.
Si se especifica un CONTEXTO (usando -Cn), la cadena de comunidad se mapeará a un nombre de seguridad en el contexto SNMPv3 nombrado. De lo contrario, se utilizará el contexto predeterminado ("").
com2secunix [-Cn CONTEXTO] NOMBRE_SEGURIDAD RUTA_SOCKET COMUNIDAD
es la versión de sockets de dominio Unix de com2sec.
group GRUPO {v1|v2c|usm|tsm|ksm} NOMBRE_SEGURIDAD
mapea un nombre de seguridad (en el modelo de seguridad especificado) a un grupo con nombre. Varias directivas group pueden especificar el mismo nombre de grupo, permitiendo que una única configuración de acceso se aplique a varios usuarios y/o cadenas de comunidad.
Tenga en cuenta que los grupos deben configurarse por separado para los dos modelos basados en comunidad: una única directiva com2sec (o equivalente) normalmente irá acompañada de **dos** directivas group.
view NOMBRE_VISTA TIPO OID [MASCARA]
define una "vista" nombrada, un subconjunto del árbol OID general. Esto es comúnmente un solo subárbol, pero se pueden dar varias directivas view con el mismo nombre de vista (NOMBRE_VISTA) para construir una colección más compleja de OIDs. TIPO es included o excluded, lo que puede definir una vista más compleja (por ejemplo, al excluir ciertos objetos sensibles de un subárbol accesible de lo contrario).
MASCARA es una lista de octetos hexadecimales (opcionalmente separados por '.' o ':') con los bits establecidos que indican qué subidentificadores en el OID de la vista deben coincidir. Si no se especifica, esto por defecto coincide exactamente con el OID (todos los bits establecidos), definiendo así un subárbol OID simple. Entonces:
view iso1 included .iso 0xf0
view iso2 included .iso
view iso3 included .iso.org.dod.mgmt 0xf0
todos definirían la misma vista, cubriendo todo el subárbol 'iso(1)' (con el tercer ejemplo ignorando los subidentificadores no cubiertos por la máscara).
Más útilmente, la máscara se puede usar para definir una vista que cubra una fila (o filas) particular en una tabla, al coincidir con el valor apropiado del subidentificador de columna, pero omitiendo el subidentificador de columna:
view ifRow4 included .1.3.6.1.2.1.2.2.1.0.4 0xff:a0
Tenga en cuenta que una máscara de más de 8 bits debe usar ':' para separar los octetos individuales.

Para acceso v1 o v2c, NIVEL deberá ser noauth.

Disk Monitoring

This requires that the agent was built with support for the ucd-snmp/disk module (which is included as part of the default build configuration).

disk PATH [ MINSPACE | MINPERCENT% ]
monitoriza el disco montado en PATH en cuanto a espacio libre disponible. Los discos montados después de que el agente se ha iniciado no serán monitorizados, a menos que se especifique la opción includeAllDisks.
El umbral mínimo puede especificarse en kB (MINSPACE) o como un porcentaje del disco total (MINPERCENT% con un carácter '%'), con un valor por defecto de 100kB si no se especifica ninguno. Si el espacio libre del disco cae por debajo de este umbral, entonces la instancia correspondiente de dskErrorFlag se establecerá en 1, y se informará de un mensaje de descripción adecuado a través de la instancia dskErrorMsg.
Nota:
Esta situación no activará automáticamente una trampa para informar del problema - véase la sección DisMan Event MIB más adelante.
includeAllDisks MINPERCENT%
configura la monitorización de todos los discos encontrados en el sistema, utilizando el umbral (porcentual) especificado. La tabla dskTable se actualiza dinámicamente, los discos desmontados desaparecen de la tabla y los discos recién montados se añaden a la tabla. El umbral para discos individuales se puede ajustar utilizando las directivas disk adecuadas (que pueden ir antes o después de la directiva includeAllDisks).
Nota:
Si las directivas disk aparecen antes o después de includeAllDisks puede afectar la indexación de la tabla dskTable.
Solo se debe especificar una directiva includeAllDisks - cualquier copia subsiguiente será ignorada.
La lista de discos montados se determinará a partir de HOST-RESOURCES-MIB::hrFSTable.

Si no se definen ni directivas disk ni includeAllDisks, entonces la consulta de la tabla dskTable fallará (noSuchObject).

Disk I/O Monitoring

Esto requiere que el agente se haya compilado con soporte para el módulo ucd-snmp/diskio (que no está incluido en la configuración de compilación por defecto).

Por defecto, todos los dispositivos de bloque conocidos por el sistema operativo se incluyen en la tabla diskIOTable. En plataformas distintas de Linux, este módulo no tiene directivas de configuración.

En sistemas Linux, es posible excluir varias clases de dispositivos de bloque de la tabla diskIOTable para evitar saturar la tabla con estadísticas cero inútiles para pseudo-dispositivos que a menudo no se utilizan pero que se configuran por defecto para existir en la mayoría de las distribuciones Linux recientes.

diskio_exclude_fd yes
Excluye todos los dispositivos de bloque de disquete de Linux, cuyos nombres comienzan con "fd", por ejemplo, "fd0".
diskio_exclude_loop yes
Excluye todos los dispositivos de bloque de bucle de Linux, cuyos nombres comienzan con "loop", por ejemplo, "loop0".
diskio_exclude_ram yes
Excluye todos los dispositivos de bloque de disco de RAM de Linux, cuyos nombres comienzan con "ram", por ejemplo, "ram0".

En sistemas Linux, también es posible informar solo de los dispositivos explícitamente aceptados. Puede llevar una cantidad de tiempo considerable procesar los datos de diskIOTable en sistemas con decenas de miles de dispositivos de bloque y aceptar solo los importantes evita un gran consumo de CPU.

diskio <device>
Habilita la lista de aceptación de dispositivos y añade el dispositivo a la lista de aceptación. Solo se informará de los dispositivos explícitamente aceptados. Esta opción se puede utilizar varias veces.

System Load Monitoring

Esto requiere que el agente se haya compilado con soporte para el módulo ucd-snmp/loadave o el módulo ucd-snmp/memory respectivamente (ambos incluidos en la configuración de compilación por defecto).

load MAX1 [MAX5 [MAX15]]
monitoriza el promedio de carga del sistema local, especificando los umbrales para los promedios de 1 minuto, 5 minutos y 15 minutos. Si alguna de estas cargas supera el valor máximo asociado, entonces la instancia correspondiente de la bandera de error laErrorFlag se establecerá en 1, y se informará de un mensaje de descripción adecuado a través de la instancia laErrMessage.
Nota:
Esta situación no activará automáticamente una trampa para informar del problema - véase la sección DisMan Event MIB más adelante.
Si se omite el umbral MAX15, se establecerá por defecto al valor de MAX5. Si se omiten tanto MAX5 como MAX15, se establecerán por defecto al valor de MAX1. Si no se especifica esta directiva, los tres umbrales tendrán por defecto el valor de DEFMAXLOADAVE.
Si se da un valor de umbral de 0, el agente no informará de errores a través de las instancias laErrorFlag o laErrMessage relevantes, independientemente de la carga actual.

A diferencia de las directivas proc y disk, la consulta de la tabla laTable tendrá éxito (asumiendo que el módulo ucd-snmp/loadave se configuró en el agente), incluso si la directiva load no está presente.

swap MIN
monitoriza la cantidad de espacio de intercambio disponible en el sistema local. Si cae por debajo del umbral especificado (MIN kB), entonces el objeto memErrorSwap se establecerá en 1, y se informará de un mensaje de descripción adecuado a través de memSwapErrorMsg.
Nota:
Esta situación no activará automáticamente una trampa para informar del problema - véase la sección DisMan Event MIB más adelante.
Si no se especifica esta directiva, el umbral por defecto es 16 MB.

Log File Monitoring

Esto requiere que el agente se haya compilado con soporte para el módulo ucd-snmp/file o ucd-snmp/logmatch respectivamente (ambos incluidos en la configuración de compilación por defecto).

file FILE [MAXSIZE]
monitoriza el tamaño del archivo especificado (en kB). Si se especifica MAXSIZE, y el tamaño del archivo excede este umbral, entonces la instancia de bandera de error de archivo fileErrorFlag correspondiente se establecerá en 1, y se informará de un mensaje de descripción adecuado a través de la instancia fileErrorMsg.
Nota:
Esta situación no activará automáticamente una trampa para informar del problema - véase la sección DisMan Event MIB más adelante.
Nota: Se pueden monitorizar un máximo de 20 archivos.
Nota: Si no se definen directivas file, entonces la consulta de la tabla fileTable fallará (noSuchObject).
logmatch NAME FILE CYCLETIME REGEX
monitoriza el archivo especificado en busca de ocurrencias del patrón REGEX especificado. La posición del archivo se almacena internamente, por lo que el archivo completo solo se lee inicialmente, y cada pasada subsiguiente solo leerá las nuevas líneas añadidas al archivo desde la última lectura.
NAME
nombre de la instancia logmatch (aparecerá como logMatchName bajo logMatch/logMatchTable/logMatchEntry/logMatchName en el árbol MIB de ucd-snmp).
FILE
ruta absoluta al archivo de registro que se va a monitorizar. Tenga en cuenta que esta ruta puede contener directivas de fecha/hora (como en el comando 'date' de UNIX). Consulte la página del manual de 'strftime' para conocer las diversas directivas aceptadas.
CYCLETIME
intervalo de tiempo para cada lectura del archivo de registro y actualización de variables internas en segundos. Nota: una operación SNMPGET* también activará una lectura inmediata del archivo de registro y una actualización de variables.
REGEX
la expresión regular a utilizar. Nota: NO encierre la expresión regular entre comillas, incluso si hay espacios en la expresión, ya que las comillas también formarán parte del patrón a coincidir.
Ejemplo:
logmatch apache-GETs /usr/local/apache/logs/access.log-%Y-%m-%d 60 GET.*HTTP.*
Esta instancia de logmatch se llama 'apache-GETs', utiliza 'GET.*HTTP.*' como su expresión regular y monitorizará el archivo llamado (suponiendo que hoy es 6 de mayo de 2009): '/usr/local/apache/logs/access.log-2009-05-06', mañana buscará 'access.log-2009-05-07'. El archivo de registro se lee cada 60 segundos.
Nota: Se pueden especificar un máximo de 250 directivas logmatch.
Nota: Si no se definen directivas logmatch, entonces la consulta de la tabla logMatchTable fallará (noSuchObject).

ACTIVE MONITORING

El comportamiento habitual de un agente SNMP es esperar las solicitudes SNMP entrantes y responder a ellas; si no se reciben solicitudes, un agente normalmente no iniciará ninguna acción. Esta sección describe varias directivas que pueden configurar snmpd para que asuma un papel más activo.

Notification Handling

trapcommunity STRING
define la cadena de comunidad por defecto a utilizar al enviar trampas. Tenga en cuenta que esta directiva debe utilizarse antes de cualquier directiva de destino de trampa basada en comunidad que la necesite.

trap2sink [-profile p] [-name n] [-tag t] [-s src] HOST [COMMUNITY [PORT]]

Normalmente el objeto MIB correspondiente (snmpEnableAuthenTraps.0) es de lectura/escritura, pero especificar esta directiva lo hace de solo lectura, y los intentos de establecer el valor mediante solicitudes SET resultarán en una respuesta de error notWritable.

v1trapaddress HOST
define la dirección del agente, que se inserta en los TRAPs SNMPv1. Si se omite esta opción, se elige una dirección IPv4 local arbitraria. Esta opción es útil principalmente cuando el agente es visible desde el exterior solo por una dirección específica (por ejemplo, debido a traducción de direcciones de red o cortafuegos).

DisMan MIB de Eventos

Las directivas anteriores se pueden utilizar para configurar dónde se deben enviar los traps, pero no se ocupan de cuándo enviar dichos traps (o qué traps se deben generar). Este es el dominio de la MIB de Eventos - desarrollada por el grupo de trabajo de Gestión Distribuida (DisMan) del IETF.

Esto requiere que el agente se haya compilado con soporte para el módulo disman/event (que ahora se incluye como parte de la configuración de compilación por defecto para la distribución más reciente).

Nota:
El comportamiento de la última implementación difiere en algunos aspectos menores del código anterior; nada demasiado significativo, pero los scripts existentes posiblemente necesiten algunos ajustes menores.
iquerySecName NAME
agentSecName NAME
especifica el nombre de usuario SNMPv3 por defecto, que se utilizará al realizar consultas internas para recuperar cualquier información necesaria (ya sea para evaluar la expresión monitoreada o para construir una carga útil de notificación). Estas consultas internas siempre utilizan SNMPv3, incluso si la consulta normal al agente se realiza mediante SNMPv1 o SNMPv2c.
Tenga en cuenta que este usuario también debe ser creado explícitamente (createUser) y se le deben otorgar los derechos de acceso apropiados (por ejemplo, rouser). Esta directiva se ocupa únicamente de definir qué usuario se debe utilizar, no de configurar realmente a este usuario.
monitor [OPTIONS] NAME EXPRESSION
define un objeto MIB a monitorear. Si se cumple la condición EXPRESSION (ver más abajo), se activará el evento correspondiente, y se enviará una notificación o se aplicará una asignación SET (o ambas). Tenga en cuenta que el evento solo se activará una vez, cuando la expresión coincida por primera vez. Esta entrada de monitor no se activará de nuevo hasta que la condición monitoreada primero se vuelva falsa y luego vuelva a coincidir. NAME es un nombre administrativo para esta expresión, y se utiliza para indexar la mteTriggerTable (y tablas relacionadas). Cada línea de monitor debe tener un NAME único. Las líneas de monitor con un nombre duplicado se descartan y hacen que snmpd registre una queja de índice duplicado. Tenga en cuenta también que tales monitores utilizan una solicitud interna SNMPv3 para recuperar los valores que se están monitoreando (incluso si las consultas normales del agente suelen utilizar SNMPv1 o SNMPv2c). Consulte el token iquerySecName descrito anteriormente.
EXPRESSION
Hay tres tipos de expresiones de monitor soportadas por la MIB de Eventos: pruebas de existencia, booleanas y de umbral.
OID | ! OID | != OID
define una prueba de monitor de existencia(0). Un OID simple especifica una prueba de presencia(0), que se activará cuando se cree (una instancia de) el OID monitoreado. Una expresión de la forma ! OID especifica una prueba de ausencia(1), que se activará cuando el OID monitoreado sea eliminado. Una expresión de la forma != OID especifica una prueba de cambio(2), que se activará cada vez que los valores monitoreados cambien. Tenga en cuenta que **debe** haber un espacio en blanco antes del token OID.
OID OP VALUE
define una prueba de monitor booleana(1). OP debe ser uno de los operadores de comparación definidos (!=, ==, <, <=, >, >=) y VALUE debe ser un valor entero con el que comparar. Tenga en cuenta que **debe** haber espacios en blanco alrededor del token OP. Una comparación como OID !=0 **no se manejará correctamente**.
OID MIN MAX [DMIN DMAX]
define una prueba de monitor de umbral(2). MIN y MAX son valores enteros, que especifican los umbrales inferior y superior. Si el valor del OID monitoreado cae por debajo del umbral inferior (MIN) o supera el umbral superior (MAX), la entrada del monitor activará el evento correspondiente.
Tenga en cuenta que el evento de umbral ascendente solo se rearma cuando el valor monitoreado cae por debajo del umbral **inferior** (MIN). Del mismo modo, el evento de umbral descendente se rearma con el umbral superior (MAX).
Los parámetros opcionales DMIN y DMAX configuran un par de pruebas de umbral similares, pero que operan con las diferencias delta entre valores de muestra sucesivos.
OPTIONS
Hay varias opciones para controlar el comportamiento de la expresión monitoreada. Estas incluyen:
-D
indica que la expresión debe evaluarse utilizando diferencias delta entre valores de muestra (en lugar de los valores mismos).
-d OID
-di OID
especifica un marcador de discontinuidad para validar diferencias delta. Una instancia de objeto -di se utilizará exactamente como se proporciona. Un objeto -d tendrá los subidentificadores de instancia del objeto de expresión correspondiente (comodín) añadidos. Si se especifica el flag -I, entonces no hay diferencia entre estas dos opciones.
Esta opción también implica -D.
-e EVENT
especifica el evento que se invocará cuando se active esta entrada de monitor. Si no se proporciona esta opción, la entrada del monitor generará una de las notificaciones estándar definidas en la DISMAN-EVENT-MIB.
-I
indica que la expresión monitoreada debe aplicarse al OID especificado como una sola instancia. Por defecto, el OID se tratará como un objeto comodín, y el monitor se expandirá para cubrir todas las instancias coincidentes.
-i OID
/a>
-o OID
define varbinds adicionales que se añadirán a la carga útil de la notificación cuando este monitor se active. Para una expresión comodín, el sufijo de la instancia coincidente se añadirá a los OID especificados con -o, mientras que los OID especificados con -i se tratarán como instancias exactas. Si se especifica la bandera -I, no hay diferencia entre estas dos opciones.
Consulte strictDisman para obtener detalles sobre el orden de las cargas útiles de notificación.
-r FRECUENCIA
monitoriza la expresión dada cada FRECUENCIA, donde FRECUENCIA está en segundos o, opcionalmente, con el sufijo de uno de s (para segundos), m (para minutos), h (para horas), d (para días) o w (para semanas). Por defecto, la expresión se evaluará cada 600s (10 minutos).
-S
indica que la expresión del monitor no debe evaluarse cuando el agente se inicie por primera vez. La primera evaluación se realizará una vez transcurrido el primer intervalo de repetición.
-s
indica que la expresión del monitor debe evaluarse cuando el agente se inicie por primera vez. Este es el comportamiento por defecto.
Nota:
Las notificaciones activadas por esta evaluación inicial se enviarán antes de la trampa coldStart.
-u SECNAME
especifica un nombre de seguridad a utilizar para escanear el host local, en lugar del iquerySecName por defecto. Una vez más, este usuario debe ser creado explícitamente y se le deben conceder los derechos de acceso adecuados.
notificationEvent ENAME NOTIFICATION [-m] [-i OID | -o OID ]*
define un evento de notificación llamado ENAME. Este puede ser activado desde una entrada de monitor dada especificando la opción -e ENAME (ver arriba). NOTIFICATION debe ser el OID de la definición NOTIFICATION-TYPE para la notificación a generar.
Si se proporciona la opción -m, la carga útil de la notificación incluirá los varbinds estándar especificados en la cláusula OBJECTS de la definición MIB de la notificación. Esta opción debe ir después del OID de NOTIFICATION (y el archivo MIB relevante debe estar disponible y cargado por el agente). De lo contrario, estos varbinds deben enumerarse explícitamente (ya sea aquí o en la directiva monitor correspondiente).
Las opciones -i OID y -o OID especifican varbinds adicionales que se añadirán a la carga útil de la notificación, después de la lista estándar. Si la entrada del monitor que activó este evento implicó una expresión comodín, el sufijo de la instancia coincidente se añadirá a los OID especificados con -o, mientras que los OID especificados con -i se tratarán como instancias exactas. Si la bandera -I se especificó para la directiva monitor, no hay diferencia entre estas dos opciones.
setEvent ENAME [-I] OID = VALUE
define un evento de asignación llamado ENAME, asignando el VALUE (entero) al OID especificado. Este puede ser activado desde una entrada de monitor dada especificando la opción -e ENAME (ver arriba).
Si la entrada del monitor que activó este evento implicó una expresión comodín, el sufijo de la instancia coincidente se añadirá normalmente al OID. Si la bandera -I se especificó para la directiva monitor o setEvent, el OID especificado se considerará una instancia única exacta.
strictDisman yes
La definición de notificaciones SNMP establece que los varbinds definidos en la cláusula OBJECT deben ir primero (en el orden especificado), seguidos de cualquier varbind "extra" que el generador de notificaciones considere útil. El enfoque más natural sería asociar estos varbinds obligatorios con la entrada notificationEvent, y añadir cualquier varbind asociado con la entrada del monitor que activó la notificación al final de esta lista. Este es el comportamiento por defecto de la implementación MIB de Eventos de Net-SNMP.
Desafortunadamente, las especificaciones MIB de Eventos de DisMan establecen que los varbinds relacionados con el disparador deben ir primero, seguidos de los relacionados con el evento. Esta directiva puede usarse para restaurar este comportamiento estrictamente correcto (pero inapropiado).
Nota:
El orden estricto de DisMan puede resultar en la generación de listas de carga útil de notificación inválidas si la bandera notificationEvent -n se utiliza junto con las opciones de varbinds monitor -o (o -i).
Si ninguna entrada de monitor especifica varbinds de carga útil, la configuración de esta directiva es irrelevante.
linkUpDownNotifications yes
configurará las tablas MIB de Eventos para monitorizar la ifTable en busca de interfaces de red que se activen o desactiven, y activará una notificación linkUp o linkDown según corresponda.
Esto es exactamente equivalente a la configuración:
notificationEvent  linkUpTrap    linkUp   ifIndex ifAdminStatus ifOperStatus
notificationEvent  linkDownTrap  linkDown ifIndex ifAdminStatus ifOperStatus
monitor  -r 60 -e linkUpTrap   "Generar linkUp" ifOperStatus != 2
monitor  -r 60 -e linkDownTrap "Generar linkDown" ifOperStatus == 2
defaultMonitors yes
configurará las tablas MIB de Eventos para monitorizar las diversas tablas UCD-SNMP-MIB en busca de problemas (indicados por los objetos de columna xxErrFlag apropiados).
Esto es exactamente equivalente a la configuración:
monitor	-o prNames -o prErrMessage "tabla de procesos" prErrorFlag != 0
monitor	-o memErrorName -o memSwapErrorMsg "memoria" memSwapError != 0
monitor	-o extNames -o extOutput "tabla ext" extResult != 0
monitor	-o dskPath -o dskErrorMsg "tabla dsk" dskErrorFlag != 0
monitor	-o laNames -o laErrMessage  "tabla la" laErrorFlag != 0
monitor	-o fileName -o fileErrorMsg  "tabla file" fileErrorFlag != 0

En ambos últimos casos, el archivo snmpd.conf también debe contener una directiva iquerySecName, junto con una entrada createUser correspondiente y una configuración de control de acceso adecuada.

DisMan Schedule MIB

El grupo de trabajo DisMan también produjo un mecanismo para programar acciones particulares (una asignación SET especificada) en momentos dados. Esto requiere que el agente se compilara con soporte para el módulo disman/schedule (que se incluye como parte de la configuración de compilación por defecto para la distribución más reciente).

Hay tres formas de especificar la acción programada:

repeat FRECUENCIA OID = VALUE
configura una asignación SET del VALUE (entero) a la instancia MIB OID, para que se ejecute cada FRECUENCIA segundos, donde FRECUENCIA está en segundos o, opcionalmente, con el sufijo de uno de s (para segundos), m (para minutos), h (para horas), d (para días) o w (para semanas).
cron MINUTO HORA DIA MES DIA_SEMANA OID = VALUE
configura una asignación SET del VALUE (entero) a la instancia MIB OID, para que se ejecute en los momentos especificados por los campos MINUTO a DIA_SEMANA. Estos siguen el mismo patrón que los campos equivalentes de crontab(5).
Nota:
Estos campos deben especificarse como una lista (separada por comas) de valores numéricos. No se admiten valores con nombre para los campos MES y DIA_SEMANA, ni rangos de valores. Se puede especificar un comodín como '*'.
El campo DIA también puede aceptar valores negativos, para indicar días contados hacia atrás desde el final del mes.
at MINUTO HORA DIA MES DIA_SEMANA OID = VALUE
configura una asignación SET de un solo disparo, para que se ejecute en la primera hora coincidente según lo especificado por los campos MINUTO a DIA_SEMANA. La interpretación de estos campos es exactamente la misma que para la directiva cron.

Entrega de datos a través de Notificaciones

Nota: esta funcionalidad solo está disponible si el módulo mib deliver/deliverByNotify se compiló en el agente.

En algunas situaciones, puede ser ventajoso entregar datos SNMP a través de Notificaciones SNMP (TRAPs e INFORMs) en lugar del proceso típico de que el gestor emita solicitudes de datos (mediante GETs y GETNEXTs). Las razones para hacer esto son numerosas, pero frecuentemente son casos extremos. La razón más común para querer este comportamiento podría ser monitorizar dispositivos que residen detrás de NATs o Firewalls que impiden el tráfico SNMP entrante.

Cabe señalar que, aunque la mayoría del software de gestión es capaz de registrar notificaciones, muy poco software de gestión (o ninguno) actualizará su "base de datos de conocimiento" basándose en el contenido de las notificaciones SNMP. Es decir, no actualizará (por ejemplo) el historial de contadores de tráfico de interfaz que se utiliza para generar gráficos. La mayoría de los paquetes de gestión de redes grandes tienen una base de datos separada para almacenar los datos recibidos a través de solicitudes SNMP (GETs y GETNEXTs) frente a los recibidos de las notificaciones. Se requiere investigar las capacidades del software de su estación de gestión antes de asumir que esta funcionalidad resolverá sus requisitos de entrega de datos.

Las notificaciones generadas a través de este mecanismo se enviarán al conjunto estándar de destinos de notificación configurados. Consulte la sección "Manejo de Notificaciones" de este documento para obtener más información.

deliverByNotify [-p] [-m] [-s MAXSIZE] FRECUENCIA OID
Esta directiva indica al agente SNMP que se recorra a sí mismo el OID, recopile todos los datos y los envíe cada FRECUENCIA segundos, donde FRECUENCIA está en segundos o, opcionalmente, con el sufijo de uno de s (para segundos), m (para minutos), h (para horas), d (para días) o w (para semanas). Por defecto, los escalares se incluyen en la notificación que s
pecifica la frecuencia con la que se enviará la notificación (a menos que se especifique la opción -p) y qué número de mensaje de cuántos mensajes tiene una notificación particular (a menos que se especifique -m). Para dividir las notificaciones en tamaños de paquete manejables, use el indicador -s para especificar el número aproximado máximo de bytes a los que debe limitarse un mensaje de notificación. Si se necesitan más de MAXSIZE bytes, se enviarán múltiples notificaciones para entregar los datos. Tenga en cuenta que los cálculos para asegurar que se cumpla el tamaño máximo son aproximaciones y, por lo tanto, no se puede garantizar que estén por debajo de ese tamaño, así que deje un búfer de relleno si es fundamental evitar la fragmentación. Un valor de -1 indica forzar todo en un solo mensaje sin importar cuán grande sea.
Ejemplo de uso: lo siguiente entregará el contenido de ifTable una vez por hora y el contenido del grupo system cada 2 horas:
deliverByNotify 3600 ifTable
deliverByNotify 7200 system
deliverByNotifyMaxPacketSize SIZEINBYTES
Establece el límite de tamaño de notificación predeterminado (consulte el indicador -s anterior).
deliverByNotifyOid OID
deliverByNotifyFrequencyOid OID
deliverByNotifyMessageNumberOid OID
deliverByNotifyMaxMessageNumberOid OID
Estos establecen el OID de datos bajo el cual se enviará la notificación, el OID escalar, el OID del número de mensaje y el OID del número máximo de mensaje. Estos se establecen por defecto en objetos en el NET-SNMP-PERIODIC-NOTIFY-MIB.

AMPLIACION DE LA FUNCIONALIDAD DEL AGENTE

Una de las primeras características distintivas de la suite UCD original fue la capacidad de extender la funcionalidad del agente, no solo recompilando con código para nuevos módulos MIB, sino también configurando el agente en ejecución para que informe información adicional. Existen varias técnicas para dar soporte a esto, incluyendo:

  • ejecución de comandos externos (exec, extend, pass)
  • carga dinámica de nuevo código (perl embebido, dlmod)
  • comunicación con otros agentes (proxy, SMUX, AgentX)

Comandos de Extension Arbitraria

El primer mecanismo de extensión fue la capacidad de ejecutar comandos o scripts de shell arbitrarios. Dichos comandos no necesitan ser conscientes de las operaciones SNMP, ni conformarse a ningún comportamiento particular: las estructuras MIB están diseñadas para acomodar cualquier forma de salida de comando. El uso de este mecanismo requiere que el agente se haya compilado con soporte para los módulos ucd-snmp/extensible y/o agent/extend (que se incluyen ambos como parte de la configuración de compilación predeterminada).

exec [MIBOID] NOMBRE PROG ARGS
sh [MIBOID] NOMBRE PROG ARGS
invoca el PROG nombrado con los argumentos ARGS. Por defecto, el estado de salida y la primera línea de salida del comando se informarán a través de la tabla extTable, descartando cualquier salida adicional.
Nota:
Las entradas en esta tabla aparecen en el orden en que se leen del archivo de configuración. Esto significa que añadir nuevas directivas exec (o sh) y reiniciar el agente puede afectar la indexación de otras entradas.
El argumento PROG para las directivas exec debe ser una ruta completa a un binario real, ya que se ejecuta a través de la llamada al sistema exec(). Para invocar un script de shell, use la directiva sh en su lugar.
Si se especifica MIBOID, los resultados se centrarán en este punto del árbol OID, devolviendo la declaración de salida como MIBOID.100.0 y toda la salida del comando en una pseudo-tabla basada en MIBNUM.101, con una 'fila' por cada línea de salida.
Nota:
La disposición de esta forma "relocalizable" de salida exec (o sh) no forma estrictamente una estructura MIB válida. Este mecanismo está siendo deprecado; consulte la directiva extend (descrita a continuación) en su lugar.
El agente no almacena en caché el estado de salida ni la salida del programa ejecutado.
execfix NOMBRE PROG ARGS
registra un comando que se puede invocar bajo demanda, típicamente para responder o corregir errores con la entrada exec o sh correspondiente. Cuando la instancia extErrFix para una entrada NOMBRE dada se establece en el valor entero de 1, se llamará a este comando.
Nota:
Esta directiva solo se puede utilizar en combinación con una directiva exec o sh correspondiente, que debe definirse primero. Intentar definir una directiva execfix no acompañada fallará.

Las extensiones exec y sh solo se pueden configurar a través del archivo snmpd.conf. No se pueden configurar mediante solicitudes SNMP SET.

extend [-cacheTime TIEMPO] [-execType TIPO] [MIBOID] NOMBRE PROG ARGS
funciona de manera similar a la directiva exec, pero con una serie de mejoras. Las tablas MIB (nsExtendConfigTable, etc.) se indexan por el token NOMBRE, por lo que no se ven afectadas por el orden en que se leen las entradas de los archivos de configuración. Hay dos tablas de resultados: una (nsExtendOutput1Table) que contiene el estado de salida, la primera línea y la salida completa (como una sola cadena) para cada entrada extend, y la otra (nsExtendOutput2Table) que contiene la salida completa como una serie de líneas separadas.
Si se especifica -cacheTime, su argumento se utiliza como tiempo de espera de caché (en segundos enteros) para esta entrada extend. Este mecanismo proporciona una forma no volátil de especificar el tiempo de espera de caché.
Si se especifica -execType y tiene el valor sh, esta entrada extend se ejecutará en un shell. De lo contrario, se ejecutará en el modo exec predeterminado. Este mecanismo proporciona una forma no volátil de especificar el tipo de ejecución.
Si se especifica MIBOID, las tablas de configuración y resultados se centrarán en este punto del árbol OID, pero de lo contrario tendrán la misma estructura. Esto significa que varias directivas extend separadas pueden especificar la misma raíz MIBOID, sin conflictos.
El estado de salida y la salida se almacenan en caché para cada entrada individualmente, y se pueden borrar (y configurar el comportamiento de caché) utilizando la tabla nsCacheTable.
extendfix NOMBRE PROG ARGS
registra un comando que se puede invocar bajo demanda, estableciendo la instancia nsExtendRunType apropiada al valor run-command(3). A diferencia de execfix, esta directiva no necesita emparejarse con una entrada extend correspondiente y puede aparecer por sí sola.

Tanto las directivas extend como extendfix se pueden configurar dinámicamente, utilizando solicitudes SNMP SET a la NET-SNMP-EXTEND-MIB.

Comandos de Extension Específicos de MIB

El primer grupo de directivas de extensión invoca comandos arbitrarios y se basa en la flexibilidad de la estructura MIB (y las aplicaciones de gestión) para acomodar e interpretar la salida. Esta es una forma conveniente de hacer que la información esté disponible de manera rápida y sencilla, pero no es útil al implementar objetos MIB específicos, donde la extensión debe conformarse a la estructura de la MIB (en lugar de viceversa). Los mecanismos de extensión restantes se refieren a tales situaciones específicas de MIB, comenzando con scripts de "paso". El uso de este mecanismo requiere que el agente se haya compilado con soporte para los módulos ucd-snmp/pass y ucd-snmp/pass_persist (que se incluyen ambos como parte de la configuración de compilación predeterminada).

pass [-p prioridad] MIBOID PROG
pasará el control del subárbol anclado en MIBOID al comando PROG especificado. Las solicitudes GET y GETNEXT para OIDs dentro de este árbol activarán este comando, llamado como:
PROG -g OID
PROG -n OID
respectivamente, donde OID es el OID solicitado. El comando PROG debe devolver la variable de respuesta como tres líneas separadas impresas en stdout: la primera línea debe ser el OID del valor devuelto, la segunda debe ser su TIPO (una de las cadenas de texto integer, gauge, counter, timeticks, ipaddress, objectid, octet, o string), y la tercera debe ser el valor en sí. (Nota: los octetos se envían como cadenas hexadecimales separadas por espacios, por ejemplo, "00 3f dd 00 c6 be").
Si el comando no puede devolver una variable adecuada (por ejemplo, el OID especificado no correspondía a una instancia válida para una solicitud GET, o no había instancias siguientes para un GETNEXT), entonces debe salir sin producir ninguna salida. Esto resultará en un error SNMP noSuchName, o una excepción noSuchInstance.
Nota:
Los tipos SMIv2 counter64 y la excepción SNMPv2 noSuchObject no son compatibles.
Una solicitud SET dará como resultado que el comando se llame como:
PROG -s OID TIPO VALOR
donde TIPO es uno de los tokens enumerados anteriormente, indicando el tipo del valor pasado como tercer parámetro.
Si la asignación es exitosa, el comando PROG debe salir sin producir ninguna salida. Los errores deben indicarse escribiendo
uno de los cadenas no-grabable o tipo-incorrecto a stdout, y el agente generará la respuesta de error apropiada.
Nota:
Los otros errores SNMPv2 no son compatibles.
En cualquier caso, el comando debe salir una vez que haya terminado de procesar. Cada solicitud (y cada varbind dentro de una sola solicitud) activará una invocación separada del comando.
La prioridad de registro predeterminada es 127. Esto se puede cambiar proporcionando la bandera opcional -p, con los registros de menor prioridad siendo utilizados en preferencia a los valores más altos.
pass_persist [-p prioridad] MIBOID PROG
también pasará el control del subárbol enraizado en MIBOID al comando PROG especificado. Sin embargo, este comando continuará ejecutándose después de que la solicitud inicial haya sido respondida, por lo que las solicitudes subsiguientes se pueden procesar sin los gastos generales de inicio.
Al inicializar, a PROG se le pasará la cadena "PING\n" en stdin, y debe responder imprimiendo "PONG\n" a stdout.
Para las solicitudes GET y GETNEXT, a PROG se le pasarán dos líneas en stdin, el comando (get o getnext) y el OID solicitado. Debe responder imprimiendo tres líneas a stdout: el OID para la varbind resultante, el TIPO y el VALOR en sí, exactamente como para la directiva pass anterior. Si el comando no puede devolver una varbind apropiada, debe imprimir "NONE\n" a stdout (pero continuar ejecutándose).
Para las solicitudes SET, a PROG se le pasarán tres líneas en stdin, el comando (set) y el OID solicitado, seguido del tipo y el valor (ambos en la misma línea). Si la asignación es exitosa, el comando debe imprimir "DONE\n" a stdout. Los errores deben indicarse escribiendo una de las cadenas no-grabable, tipo-incorrecto, longitud-incorrecta, valor-incorrecto o valor-inconsistente a stdout, y el agente generará la respuesta de error apropiada. En cualquier caso, el comando debe continuar ejecutándose.
La prioridad de registro se puede cambiar utilizando la bandera opcional -p, al igual que para la directiva pass.

Las extensiones pass y pass_persist solo se pueden configurar a través del archivo snmpd.conf. No se pueden configurar mediante solicitudes SNMP SET.

Soporte de Perl Incrustado

Los programas que utilizan los mecanismos de extensión anteriores se pueden escribir en cualquier lenguaje de programación conveniente, incluido perl, que es una opción común para extensiones de paso en particular. Sin embargo, el agente Net-SNMP también incluye soporte para la tecnología de perl incrustada (similar a mod_perl para el servidor web Apache). Esto permite al agente interpretar scripts de perl directamente, evitando así la sobrecarga de iniciar procesos e inicializar el sistema de perl cuando se recibe una solicitud.

El uso de este mecanismo requiere que el agente se haya compilado con soporte para el mecanismo de perl incrustada, que no forma parte del entorno de compilación predeterminado. Debe incluirse explícitamente especificando la opción '--enable-embedded-perl' al script configure al compilar el paquete por primera vez.

Si está habilitado, se reconocerán las siguientes directivas:

disablePerl true
desactivará el soporte de perl incrustada por completo (por ejemplo, si hay problemas con la instalación de perl).
perlInitFile ARCHIVO
carga el archivo de inicialización especificado (si está presente) inmediatamente antes de analizar la primera directiva perl. Si no se especifica explícitamente, el agente buscará el archivo de inicialización predeterminado /usr/share/snmp/snmp_perl.pl.
El archivo de inicialización predeterminado crea una instancia de un objeto NetSNMP::agent, una variable $agent que se puede utilizar para registrar rutinas de manejo de MIB basadas en perl.
perl EXPRESIÓN
evalúa la expresión dada. Esto típicamente registraría una rutina de manejo para ser llamada cuando se solicitara una sección del árbol OID:
perl use Data::Dumper;
perl sub myroutine  { print "got called: ",Dumper(@_),"\n"; }
perl $agent->register('mylink', '.1.3.6.1.8765', \&myroutine);
Esta expresión también podría incluir un archivo externo:
perl 'do /path/to/file.pl';
o realizar cualquier otro procesamiento basado en perl que pueda ser necesario.

Módulos Cargables Dinámicamente

La mayoría de las MIB admitidas por el agente Net-SNMP se implementan como módulos de código C, que se compilaron y enlazaron en las bibliotecas del agente cuando se compiló el conjunto por primera vez. Dichos módulos de implementación también se pueden compilar de forma independiente y cargar en el agente en ejecución una vez que ha comenzado. El uso de este mecanismo requiere que el agente se haya compilado con soporte para el módulo ucd-snmp/dlmod (que se incluye como parte de la configuración de compilación predeterminada).

dlmod NOMBRE RUTA
cargará el módulo de objeto compartido del archivo RUTA (un nombre de archivo absoluto) y llamará a la rutina de inicialización init_NOMBRE.
Nota:
Si la RUTA especificada no es un nombre de archivo completamente calificado, se interpretará en relación con /usr/lib/snmp/dlmod, y se agregará .so al nombre del archivo.

Esta funcionalidad también se puede configurar mediante solicitudes SNMP SET a la UCD-DLMOD-MIB.

Soporte de Proxy

Otro mecanismo para extender la funcionalidad del agente es pasar solicitudes seleccionadas (o varbinds seleccionadas) a otro agente SNMP, que puede estar ejecutándose en el mismo host (presumiblemente escuchando en un puerto diferente), o en un sistema remoto. Esto se puede ver como el agente principal delegando solicitudes al remoto, o actuando como proxy para él. El uso de este mecanismo requiere que el agente se haya compilado con soporte para el módulo ucd-snmp/proxy (que se incluye como parte de la configuración de compilación predeterminada).

proxy [-Cn NOMBRE_CONTEXTO] [ARGUMENTOS_SNMPCMD] HOST OID [OID_REMOTO]
pasará cualquier solicitud entrante bajo OID al agente que escucha en el puerto especificado por la dirección de transporte HOST. Consulte la sección DIRECCIONES DE ESCUCHA en la página del manual snmpd(8) para obtener más información sobre el formato de las direcciones de escucha.
Nota:
Para actuar como proxy de todo el árbol MIB, utilice el OID .1.3 (no el .1 de nivel superior)

Los ARGUMENTOS_SNMPCMD deben proporcionar información de versión y administrativa suficiente para generar una solicitud SNMP válida (consulte snmpcmd(1)).

Nota:
La solicitud proxyada no utilizará la configuración administrativa de la solicitud original.

Si se especifica un NOMBRE_CONTEXTO, registrará la delegación del proxy dentro del contexto con nombre en el agente local. Definir múltiples directivas proxy para el mismo OID pero diferentes contextos se puede utilizar para consultar varios agentes remotos a través de un solo proxy, especificando el contexto SNMPv3 apropiado en la solicitud entrante (o utilizando cadenas de comunidad configuradas adecuadamente, consulte la directiva com2sec).

Especificar el parámetro OID_REMOTO mapeará el árbol MIB local enraizado en OID a un subárbol equivalente enraizado en OID_REMOTO en el agente remoto.

Subagentes SMUX

El agente Net-SNMP admite el protocolo SMUX (RFC 1227) para comunicarse con subagentes basados en SMUX (como gated, zebra o quagga). El uso de este mecanismo requiere que el agente se haya compilado con soporte para el módulo smux, que no forma parte del entorno de compilación predeterminado, y debe incluirse explícitamente especificando la opción '--with-mib-modules=smux' al script configure al compilar el paquete por primera vez.

Nota:
Este protocolo de extensión ha sido oficialmente obsoleto a favor de AgentX (ver abajo).
smuxpeer OID CONTRASEÑA
registrará un subárbol para el procesamiento basado en SMUX, para ser autenticado utilizando la contraseña CONTRASEÑA. Si un subagente (o "peer") se conecta al agente y registra este subárbol, las solicitudes de OIDs dentro de él se pasarán a ese subagente SMUX para su procesamiento.
Una entrada adecuada para un demonio de enrutamiento OSPF (como gated, zebra o quagga) podría ser algo como
smuxpeer .1.3.6.1.2.1.14 ospf_pass
smuxsocket <dirección-IPv4>
define la dirección IPv4 para que los peers SMUX se comuniquen con el agente Net-SNMP. El valor predeterminado es escuchar en todas las interfaces IPv4 ("0.0.0.0"), a menos que el paquete se haya configurado con "--enable-local-smux" en tiempo de compilación, lo que hace que solo escuche en 127.0.0.1 por defecto. SMUX utiliza el puerto TCP bien conocido 199.

Tenga en cuenta que el agente Net-SNMP solo operará como un agente maestro SMUX. No admite el rol de subagente SMUX.

Subagentes AgentX

El agente Net-SNMP admite el protocolo AgentX (RFC 2741) tanto en roles de maestro como de subagente. El uso de este mecanismo requiere que el agente se haya compilado con soporte para el módulo agentx (que se incluye como parte de la configuración de compilación predeterminada), y también que este soporte esté explícitamente habilitado (por ejemplo, a través del archivo snmpd.conf).

Hay dos directivas específicamente relevantes para ejecutarse como un agente maestro AgentX:

AGENT BEHAVIOUR

master agentx
habilitará la funcionalidad AgentX y hará que el agente comience a escuchar las registraciones de AgentX entrantes. Esto también se puede activar especificando la opción de línea de comandos '-x' (para especificar un socket de escucha alternativo).
agentXPerms SOCKPERMS [DIRPERMS [USER|UID [GROUP|GID]]]
Define los permisos y la propiedad del socket de dominio Unix de AgentX, y los directorios padres de este socket. SOCKPERMS y DIRPERMS deben ser dígitos octales (ver chmod(1) ). Por defecto, este socket solo será accesible para subagentes que tengan el mismo ID de usuario que el agente.

Hay una directiva específicamente relevante para ejecutar como subagente AgentX:

agentXPingInterval NUM
hará que el subagente intente reconectarse cada NUM segundos al maestro si alguna vez se desconecta (o se inicia) desconectado.

Las directivas restantes son relevantes tanto para los agentes maestros como para los subagentes AgentX:

agentXSocket [<especificador-de-transporte>:]<dirección-de-transporte>[,...]
define la dirección en la que escucha el agente maestro, o a la que debe conectarse el subagente. El valor predeterminado es el socket de dominio Unix "/var/agentx/master". Otra alternativa común es tcp:localhost:705. Consulte la sección DIRECCIONES DE ESCUCHA en la página del manual de snmpd(8) para obtener más información sobre el formato de las direcciones.
Nota:
Especificar un socket AgentX no habilita automáticamente la funcionalidad AgentX (a diferencia de la opción de línea de comandos '-x').
agentXTimeout NUM
define el período de tiempo de espera (NUM segundos) para una solicitud AgentX. El valor predeterminado es 1 segundo. NUM también se puede especificar con un sufijo de uno de s (para segundos), m (para minutos), h (para horas), d (para días) o w (para semanas).
agentXRetries NUM
define el número de reintentos para una solicitud AgentX. El valor predeterminado es 5 reintentos.

net-snmp incluye APIs en C y Perl para desarrollar su propio subagente AgentX.

OTRA CONFIGURACIÓN

override [-rw] OID TIPO VALOR
Esta directiva le permite anular un OID particular con un valor diferente (y posiblemente un tipo de valor diferente). La bandera -rw permitirá que las operaciones SET de snmp modifiquen su valor también. (tenga en cuenta que si está anulando la funcionalidad original, esa funcionalidad se perderá por completo. Por lo tanto, los SET simplemente modificarán el valor anulado interno y no realizarán ninguna de la funcionalidad original prevista por el objeto MIB. ¡Es solo una emulación!) Un ejemplo:
override sysDescr.0 octet_str "mi propio sysDescr"
Esa línea establecerá el valor de sysDescr.0 en "mi propio sysDescr" así como también lo hará modificable con SNMP SETs (lo cual es en realidad ilegal según las especificaciones MIB).
Tenga cuidado al usar esto. Por ejemplo, si intenta anular una propiedad de la tercera interfaz en ifTable con un nuevo valor y más tarde la numeración dentro de ifTable cambia su orden de índice, tendrá problemas y su valor modificado no aparecerá en el lugar correcto en la tabla.
Los TIPOS válidos son: integer, uinteger, octet_str, object_id, counter, null (para gauges, use "uinteger"; para cadenas de bits, use "octet_str"). Tenga en cuenta que establecer un objeto en "null" efectivamente lo elimina como accesible. No es necesario proporcionar un VALOR si el tipo de objeto es null.
Deberían estar disponibles más tipos en el futuro.

Si está intentando comprender aspectos de los diversos módulos MIB (posiblemente algunos que haya agregado usted mismo), lo siguiente puede ayudarlo a obtener información de depuración útil. En primer lugar, lea la página del manual de snmpd sobre la bandera -D. Luego, el siguiente token de configuración de snmpd.conf, combinado con la bandera -D, puede producir una salida útil:

injectHandler HANDLER nombre_modulo [antes_de_esto]
Esto insertará nuevos manejadores en la sección del árbol MIB a la que hace referencia "nombre_modulo". Si se especifica "antes_de_esto", el módulo se insertará antes del módulo nombrado. Esto es útil para colocar un manejador en la posición exacta de la cadena.
Los tipos de manejadores disponibles para inserción son:
stash_cache
Almacena en caché la información devuelta desde el nivel inferior. Esto mejora en gran medida el rendimiento del agente, a costa de almacenar en caché los datos de tal manera que ya no están "en vivo" durante 30 segundos (en el futuro, esto será configurable). Tenga en cuenta que esto significa que snmpd también utilizará más memoria mientras la información está en caché. Actualmente, esto solo funciona para los manejadores registrados utilizando el soporte table_iterator, que son solo algunas tablas MIB. Para usarlo, debe asegurarse de instalarlo antes del punto table_iterator en la cadena, para hacer esto:


injectHandler stash_cache NOMBRE table_iterator

Si desea una tabla para experimentar, intente caminar por nsModuleTable con y sin este insertado.

debug
Imprime mucha información de depuración cuando se pasa la bandera -Dhelper:debug a la aplicación snmpd.
read_only
Fuerza la desactivación del soporte de escritura para el módulo dado.
serialize
Si un módulo no maneja varias solicitudes correctamente (utilizando la nueva API de módulo 5.0), esto forzará al módulo a recibir solo una solicitud a la vez.
bulk_to_next
Si un módulo se registra para manejar el soporte getbulk, pero por alguna razón no lo implementa correctamente, este módulo convertirá todas las solicitudes getbulk en solicitudes getnext antes de que el módulo final las reciba.
dontLogTCPWrappersConnects
Si snmpd se compiló con soporte de TCP Wrappers, registra cada conexión realizada al agente. Esta configuración deshabilita los mensajes de registro para las conexiones aceptadas. Las conexiones denegadas aún se registrarán.
Cómo averiguar los nombres de los módulos
Para averiguar en qué módulos puede insertar cosas, ejecute snmpwalk en nsModuleTable, lo que le dará una lista de todos los módulos nombrados registrados dentro del agente.
