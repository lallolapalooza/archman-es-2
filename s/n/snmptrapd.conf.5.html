NOMBRE

snmptrapd.conf - archivo de configuración para el receptor de notificaciones Net-SNMP

DESCRIPCIÓN

El receptor de notificaciones (demonio de trampas) de Net-SNMP utiliza uno o más archivos de configuración para controlar su funcionamiento y cómo se deben procesar las trampas (y las solicitudes INFORM) entrantes. Este archivo (snmptrapd.conf) puede encontrarse en varias ubicaciones, como se describe en la página del manual snmp_config(5).

IMPORTANTE

Anteriormente, snmptrapd aceptaba todas las notificaciones entrantes y las registraba automáticamente (incluso si no se proporcionaba ninguna configuración explícita). A partir de la versión 5.3, se aplicarán comprobaciones de control de acceso a las notificaciones entrantes. Si snmptrapd se ejecuta sin un archivo de configuración adecuado (o configuraciones de control de acceso equivalentes), ¡las trampas NO se procesarán! Consulte la sección CONTROL DE ACCESO para obtener más detalles.

Al igual que con la configuración del agente, las directivas de snmptrapd.conf se pueden dividir en cuatro grupos distintos.

COMPORTAMIENTO DE TRAPD

snmpTrapdAddr [<especificador-de-transporte>:]<dirección-de-transporte>[,...]
define una lista de direcciones de escucha, en las que recibir notificaciones SNMP entrantes. Consulte la sección DIRECCIONES DE ESCUCHA en la página del manual snmpd(8) para obtener más información sobre el formato de las direcciones de escucha.
El comportamiento predeterminado es escuchar en el puerto UDP 162 en todas las interfaces IPv4.
doNotRetainNotificationLogs yes
deshabilita el soporte para NOTIFICATION-LOG-MIB. Normalmente, el programa snmptrapd mantiene un registro de las trampas recibidas, que se puede recuperar consultando las tablas nlmLogTable y nlmLogvariableTable. Esta directiva se puede utilizar para suprimir este comportamiento.
Consulte la página del manual snmptrapd(8) y la NOTIFICATION-LOG-MIB para obtener detalles.
doNotLogTraps yes
deshabilita el registro de notificaciones por completo. Esto es útil si la aplicación snmptrapd solo debe ejecutar ganchos traphandle y no debe registrar trampas en ninguna ubicación.
doNotFork yes
no crear un proceso hijo desde la shell que llama.
pidFile RUTA
define un archivo en el que almacenar el ID del proceso del receptor de notificaciones. Por defecto, este ID no se guarda.

CONTROL DE ACCESO

A partir de la versión 5.3, es necesario especificar explícitamente quién está autorizado a enviar trampas e informs al receptor de notificaciones (y qué tipos de procesamiento pueden desencadenar). Esto utiliza una extensión del modelo VACM, utilizado en el agente SNMP principal.

Actualmente existen tres tipos de procesamiento que se pueden especificar:

log
registrar los detalles de la notificación, ya sea en un archivo especificado, en la salida estándar (o stderr), o a través de syslog (o similar).
execute
pasar los detalles de la trampa a un programa manejador especificado, incluyendo Perl incrustado.
net
reenviar la trampa a otro receptor de notificaciones.

En las siguientes directivas, TIPOS será una lista (separada por comas) de uno o más de estos tokens. Lo más común es que sea log,execute,net para cubrir cualquier estilo de procesamiento para una categoría particular de notificación. Pero es perfectamente posible (incluso deseable) limitar ciertas fuentes de notificación a un procesamiento seleccionado solamente.

authCommunity TIPOS COMUNIDAD [FUENTE [OID | -v VISTA ]]
autoriza trampas (y solicitudes INFORM SNMPv2c) con la comunidad especificada a desencadenar los tipos de procesamiento listados. Por defecto, esto permitirá que se procese cualquier notificación que utilice esta comunidad. El campo FUENTE se puede utilizar para especificar que la configuración solo se aplicará a las notificaciones recibidas de fuentes particulares; consulte snmpd.conf(5) para obtener más detalles.
authUser TIPOS [-s MODELO] USUARIO [NIVEL [OID | -v VISTA ]]
autoriza notificaciones SNMPv3 con el usuario especificado a desencadenar los tipos de procesamiento listados. Por defecto, esto aceptará solicitudes autenticadas. (authNoPriv o authPriv). El campo NIVEL se puede utilizar para permitir notificaciones no autenticadas (noauth), o para requerir cifrado (priv), al igual que para el agente SNMP.
Con ambas directivas, el campo OID (o -v VISTA) se puede utilizar para restringir esta configuración al procesamiento de notificaciones particulares.
Nota:
A diferencia del procesamiento VACM descrito en RFC 3415, esta vista solo se compara con el valor snmpTrapOID de la notificación entrante. No se aplica a las varbinds de carga útil contenidas en esa notificación.
authGroup TIPOS [-s MODELO] GRUPO [NIVEL [OID | -v VISTA ]]
authAccess TIPOS [-s MODELO] GRUPO VISTA [NIVEL [CONTEXTO]]
setAccess GRUPO CONTEXTO MODELO NIVEL PREFIJO VISTA TIPOS
autoriza notificaciones en el GRUPO especificado (configurado usando la directiva group) a desencadenar los tipos de procesamiento listados. Consulte snmpd.conf(5) para obtener más detalles.
createUser [-e ENGINEID] nombreusuario (MD5|SHA|SHA-512|SHA-384|SHA-256|SHA-224) contraseñautenticacion [DES|AES]
Consulte la página del manual snmpd.conf(5) para obtener una descripción de cómo crear usuarios SNMPv3. Esto es aproximadamente lo mismo, pero el nombre del archivo cambia de snmpd.conf a snmptrapd.conf.
disableAuthorization yes
deshabilitará las comprobaciones de control de acceso anteriores y volverá al comportamiento anterior de aceptar todas las notificaciones entrantes.

REGISTRO

format1 FORMATO
format2 FORMATO
especifica el formato utilizado para mostrar trampas SNMPv1 y notificaciones SNMPv2 respectivamente. Tenga en cuenta que SNMPv2c y SNMPv3 utilizan el mismo formato de PDU SNMPv2.
format DESTINO FORMATO
especifica el formato utilizado para diferentes destinos. DESTINO es uno de: print, print1, print2, syslog, syslog1, syslog2, execute, execute1, execute2. print1 se utiliza para imprimir trampas SNMPv1, print2 es para SNMPv2. print se utiliza para ambas versiones. syslog se utiliza de forma similar al enviar trampas a syslog, y execute se utiliza al enviar trampas a un programa como traptoemail(1).
Los formatos predeterminados son
format print1 %.4y-%.2m-%.2l %.2h:%.2j:%.2k %B [%b] (via %A [%a]): %N El trampazo %W (%q) Uptime: %#T %v
format print2 %.4y-%.2m-%.2l %.2h:%.2j:%.2k %B [%b]: %v
format syslog1 %a: %W Trampazo (%q) Uptime: %#T%#v
format syslog2 %B [%b]: Trampazo %#v
format execute %B %b %V %v
Consulte snmptrapd(8) para conocer los caracteres de diseño disponibles.
ignoreAuthFailure yes
instruye al receptor para que ignore las trampas de authenticationFailure.

Esto actualmente solo afecta al registro de tales n
snmptrapd.conf(5)

NAME

snmptrapd.conf - configuration file for the snmptrapd(8) daemon

DESCRIPTION

The snmptrapd.conf file is used to configure the behavior of the snmptrapd(8) daemon. It allows you to control which traps are accepted, how they are processed, where they are logged, and how they are forwarded.

The configuration directives are processed in the order they appear in the file. Directives may be commented out by starting the line with a '#' character.

Most directives consist of a token followed by one or more arguments. The syntax is generally:

token argument ...

Directives are case-insensitive.

IMPORTANT

The snmptrapd daemon is a security-sensitive application. Incorrect configuration can expose your network to security risks. Be careful when configuring access control and notification processing.

TRAPD BEHAVIOUR

doNotListen ADDRESS
Do not listen on the specified ADDRESS. The ADDRESS is a list of transport endpoints, separated by commas. See the section LISTENING ADDRESSES in the snmpd(8) manual page for more information about the format of listening addresses.
doListen ADDRESS
Listen on the specified ADDRESS. This is the default behaviour. See the section LISTENING ADDRESSES in the snmpd(8) manual page for more information about the format of listening addresses.
disableAuthorization
Disable authorization checks for incoming traps. This is generally not recommended for security reasons.
dumpFile FILE
Log all received traps to the specified FILE. This is useful for debugging purposes.
explicitIndex yes|no
When forwarding traps, use explicit indexing for the SNMP-COMMUNITY-MIB variables. Default is no.
firewall
Enable firewall mode. In this mode, snmptrapd will only accept traps from hosts that are explicitly allowed by the access control configuration.
format2xecho FORMAT
Specify the format for trap logging when using the logOption of "execute". See the section OUTPUT OPTIONS in the snmpcmd(1) manual page for details.
logOption string
specifies where notifications should be logged - to standard output, standard error, a specified file or via syslog. See the section LOGGING OPTIONS in the snmpcmd(1) manual page for details.
outputOption string
specifies various characteristics of how OIDs and other values should be displayed. See the section OUTPUT OPTIONS in the snmpcmd(1) manual page for details.

ACCESS CONTROL

access TrapReceiver ...
Defines an access control entry for receiving traps. The arguments are typically an IP address or network, and possibly community string information. For details, see the section ACCESS CONTROL in the snmpd(8) manual page.
trapCommunity COMMUNITY
Specifies the community string that will be used when sending traps to remote hosts. This directive is primarily used in conjunction with the forward directive.

LOGGING

The following directives control the logging of notifications:

logOption string
specifies where notifications should be logged - to standard output, standard error, a specified file or via syslog. See the section LOGGING OPTIONS in the snmpcmd(1) manual page for details.
outputOption string
specifies various characteristics of how OIDs and other values should be displayed. See the section OUTPUT OPTIONS in the snmpcmd(1) manual page for details.

MySQL Logging

There are two configuration variables that work together to control when queued traps are logged to the MySQL database. A non-zero value must be specified for sqlSaveInterval to enable MySQL logging.

sqlMaxQueue max
specifies the maximum number of traps to queue before a forced flush to the MySQL database.

sqlSaveInterval seconds
specified the number of seconds between periodic queue flushes. A value of 0 for will disable MySQL logging.

NOTIFICATION PROCESSING

As well as logging incoming notifications, they can also be forwarded on to another notification receiver, or passed to an external program for specialised processing.

traphandle OID|default PROGRAM [ARGS ...]
invokes the specified program (with the given arguments) whenever a notification is received that matches the OID token. For SNMPv2c and SNMPv3 notifications, this token will be compared against the snmpTrapOID value taken from the notification. For SNMPv1 traps, the generic and specific trap values and the enterprise OID will be converted into the equivalent OID (following RFC 2576).
Typically, the OID token will be the name (or numeric OID) of a NOTIFICATION-TYPE object, and the specified program will be invoked for notifications that match this OID exactly. However this token also supports a simple form of wildcard suffixing. By appending the character ´*' to the OID token, the corresponding program will be invoked for any notification based within subtree rooted at the specified OID. For example, an OID token of .1.3.6.1.4.1* would match any enterprise specific notification (including the specified OID itself). An OID token of .1.3.6.1.4.1.* would would work in much the same way, but would not match this exact OID - just notifications that lay strictly below this root. Note that this syntax does not support full regular expressions or wildcards - an OID token of the form oid.*.subids is not valid.
If the OID field is the token default then the program will be invoked for any notification not matching another (OID specific) traphandle entry.

Details of the notification are fed to the program via its standard input. Note that this will always use the SNMPv2-style notification format, with SNMPv1 traps being converted as per RFC 2576, before being passed to the program. The input format is, if you use the default set by the "format execute %B\n%b\n%V\n%v\n", one entry per line:

HOSTNAME
The name of the host that sent the notification, as determined by gethostbyaddr(3).
ADDRESS
The transport address, like
"[UDP: [172.16.10.12]:23456->[10.150.0.8]]"
VARBINDS
A list of variable bindings describing the contents of the notification, one per line. The first token on each line (up until a space) is the OID of the varind, and the remainder of the line is its value. The format of both of these are controlled by the outputOption directive (or similar configuration).
The first OID should always be SNMPv2-MIB::sysUpTime.0, and the second should be SNMPv2-MIB::snmpTrapOID.0. The remaining lines will contain the payload varbind list. For SNMPv1 traps, the final OID will be SNMPv2-MIB::snmpTrapEnterprise.0.
Example:
A traptoemail script has been included in the Net-SNMP package that can be used within a traphandle directive:

traphandle default /usr/bin/perl /usr/bin/traptoemail -s mysmtp.somewhere.com -f admin@somewhere.com me@somewhere.com

forward OID|default DESTINATION
forwards notifications that match the specified OID to another receiver listening on DESTINATION. The interpretation of OID (and default) is the same as for the traphandle directive).
See the section LISTENING ADDRESSES in the snmpd(8) manual page for more information about the format of listening addresses.

addForwarderInfo 1|yes|true|0|no|false

Each time a trap is forwarded, add an OID with the IP address of the system from which the trap has been received. The following OID is added: .1.3.6.1.6.3.18.1.3.x (SNMP-COMMUNITY-MIB::snmpTrapAddress.x) where x is the lowest index >= 0 that does not yet occur in the trap payload. The end recipient (i.e. the monitoring system) can determine the IPv4 address of the original sender by looking for the varbind with OID snmpTrapAddress.0. If that OID is not populated it means that the trap has been sent directly or in other words that it has not been forwarded.

NOTES

o
The daemon blocks while executing the traphandle commands. (This should be fixed in the future with an appropriate signal catch and wait() combination).
o
All directives listed with a value of "yes" actually accept a range of boolean values. These will accept any of 1, yes or true to enable the corresponding behaviour, or any of 0, no or false to disable it. The default in each case is for the feature to be turned off, so these directives are typically only used to enable the appropriate behaviour.
