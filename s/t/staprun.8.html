STAPRUN(8) Manual del Administrador del Sistema STAPRUN(8)

NOMBRE

staprun - tiempo de ejecución de systemtap

SINOPSIS

staprun [ OPCIONES ] MÓDULO [ OPCIONES-DEL-MÓDULO ]

DESCRIPCIÓN

El programa staprun es el backend de la herramienta Systemtap. Espera un módulo del kernel producido por el frontend de la herramienta stap.

Dividir la herramienta systemtap en un frontend y un backend permite a un usuario compilar un script de systemtap en una máquina de desarrollo que tenga las herramientas de desarrollo del kernel (necesarias para compilar el script) y luego transferir el módulo del kernel resultante a una máquina de producción que no tenga ninguna herramienta de desarrollo instalada.

Por favor, consulte stappaths(7) para el número de versión, o ejecute rpm -q systemtap (fedora/red hat) apt-get -v systemtap (ubuntu)

OPCIONES

El programa staprun soporta las siguientes opciones. Cualquier otra opción imprime una lista de las opciones soportadas.

-v
Modo detallado. El nivel de detalle también se establece en la variable de entorno SYSTEMTAP_VERBOSE.
-V
Imprimir número de versión y salir.
-w
Suprimir advertencias del script.
-u
Cargar el módulo uprobes.ko.
-c CMD
Se ejecutará el comando CMD y el programa staprun saldrá cuando CMD lo haga. La variable '_stp_target' contendrá el pid para CMD.
-x PID
La variable '_stp_target' se establecerá en PID.
-N PID
Establece la variable '_stp_namespaces_pid' a PID.
-o ARCHIVO
Enviar la salida a ARCHIVO. Si el módulo utiliza el modo bulk, la salida estará en archivos percpu ARCHIVO_x (ARCHIVO_cpux en modo background y bulk) donde 'x' es el número de cpu. Esto soporta formatos strftime(3) para ARCHIVO.
-b TAMAÑO_DE_BUFFER
El módulo de systemtap especificará un tamaño de buffer. Establecer uno aquí anulará ese valor. El valor debe ser un entero entre 1 y 4095 que se asumirá como el tamaño del buffer en MB. Ese valor será por cpu si se usa el modo bulk.
-L
Cargar el módulo e iniciar los probes, luego desconectarse del módulo dejando los probes ejecutándose. Se puede adjuntar al módulo más tarde usando la opción -A.
-A
Adjuntarse a un módulo de systemtap cargado.
-C CUÁNDO
Controla el coloreado de los mensajes de error. CUÁNDO debe ser "nunca", "siempre", o "auto" (es decir, habilitar solo si está en una terminal). Si falta la opción, se asume "auto". Los colores se pueden modificar usando la variable de entorno SYSTEMTAP_COLORS. Consulte la página del manual de stap(1) para más información sobre sintaxis y comportamiento.
-M INTERVALO
Habilitar modo monitor con INTERVALO segundos entre actualizaciones.
-d
Eliminar un módulo. Solo se eliminarán los módulos desconectados o no utilizados a los que el usuario tenga permiso de acceso. Use "*" (entre comillas) para eliminar todos los módulos no utilizados.
-D
Ejecutar staprun en segundo plano como un demonio y mostrar su pid.
-R
Renombrar el módulo a un nombre único antes de insertarlo.
-r N:URI
Pasar el número y los datos URI dados a las funciones tapset remote_id() y remote_uri().
-S tamaño[,N]
Establece el tamaño máximo del archivo de salida y el número máximo de archivos de salida. Si el tamaño del archivo de salida excede tamaño megabytes, systemtap cambia el archivo de salida al siguiente archivo. Y si el número de archivos de salida excede N, systemtap elimina el archivo de salida más antiguo. Puede omitir el segundo argumento.
-T tiempo_de_espera
Establece el tiempo máximo que el hilo lector esperará antes de volcar el buffer de traza. El valor está en ms, el valor predeterminado es 200ms. Establecer un valor alto disminuye el número de activaciones de stapio, permitiendo un mayor tiempo de espera para plataformas integradas. Pero afecta la interactividad en la terminal, ya que las trazas se vuelcan con menos frecuencia en caso de bajo rendimiento. No hay impacto en la interactividad o el rendimiento para alto rendimiento, ya que la traza se vuelca cuando el buffer está lleno, antes de que expire este tiempo de espera.
var1=val
Establece el valor de la variable global var1 a val. Las variables globales contenidas dentro de un módulo se tratan como opciones del módulo y se pueden establecer desde la línea de comandos de staprun.

ARGUMENTOS

MÓDULO es una ruta de módulo o un nombre de módulo. Si es un nombre de módulo, el módulo se buscará en el siguiente directorio (donde 'VERSIÓN' es la salida de "uname -r"):

/lib/modules/VERSIÓN/systemtap

Cualquier argumento adicional en la línea de comandos se pasa al módulo. Un uso de estos argumentos de módulo adicionales es establecer el valor de las variables globales declaradas dentro del módulo.

$ stap -p4 -m mod1 -e 'global var1="foo"; probe begin{printf("%s\n", var1); exit()}'

Ejecutando esto con un argumento de módulo adicional:

$ staprun mod1.ko var1="HelloWorld"
HelloWorld

Actualmente, los espacios y los signos de exclamación no se pueden pasar a las variables globales de esta manera.

EJEMPLOS

Consulte la página del manual de stapex(3stap) para una colección de scripts de ejemplo.

Aquí hay un ejemplo muy básico de cómo usar staprun. Primero, use stap para compilar un script. El programa stap informará la ruta al módulo resultante.

$ stap -p4 -e 'probe begin { printf("Hello World!\n"); exit() }'
/home/user/.systemtap/cache/85/stap_8553d83f78c_265.ko

Ejecute staprun con la ruta al módulo como argumento.

$ staprun /home/user/.systemtap/cache/85/stap_8553d83f78c_265.ko
Hello World!

DESCONEXIÓN Y CONEXIÓN DEL MÓDULO

Después de que el programa staprun instala un módulo del kernel de Systemtap, los usuarios pueden desconectarse del módulo del kernel y volver a conectarse a él más tarde. La opción -L carga el módulo y se desconecta automáticamente. Los usuarios también pueden desconectarse del módulo del kernel interactivamente enviando la señal SIGQUIT desde el teclado (típicamente escribiendo Ctrl-\).

Para volver a conectarse a un módulo del kernel, se usaría la opción -A de staprun.

CAMBIO DE ARCHIVO POR SEÑAL

Después de que staprun lanzó el programa stapio, los usuarios pueden ordenarle que cambie el archivo de salida al siguiente archivo cuando salga a uno o varios archivos (ejecutando staprun con la opción -o) enviando una señal SIGUSR2 al proceso stapio. Cuando recibe SIGUSR2, cambia el archivo de salida a un nuevo archivo con el sufijo .N donde N es el número secuencial. Por ejemplo,

$ staprun -o foo ...

salida de logs de traza a foo y si recibe la señal SIGUSR2, cambia la salida al archivo foo.1. Y al recibir SIGUSR2 de nuevo, cambia a el archivo foo.2.

SEGURIDAD Y PROTECCIÓN

Systemtap, en el modo de tiempo de ejecución de módulo del kernel por defecto, es una herramienta administrativa. Expone estructuras de datos internas del kernel y potencialmente información privada del usuario. Consulte la página del manual de stap(1) para obtener información adicional sobre seguridad y protección.

Para aumentar la seguridad del sistema, los usuarios de systemtap deben ser root, o estar en el grupo stapusr para poder ejecutar este programa staprun setuid

staprun(8) — SystemTap manual

NAME

staprun ― execute SystemTap scripts

SYNOPSIS

staprun [ OPTIONS ] [ SCRIPT ] [ ARGS... ]

staprun [ OPTIONS ] -d MODULE ...

staprun [ OPTIONS ] -l [ MODULE ... ]

staprun [ OPTIONS ] -k MODULE ...

staprun [ OPTIONS ] -u MODULE ...

staprun [ OPTIONS ] -r MODULE ...

staprun [ OPTIONS ] -p PROCESS ...

DESCRIPTION

The staprun utility is used to load, unload, and list SystemTap script modules. These modules are typically created by the stap command, which translates a SystemTap script into a C program, compiles it into a kernel module, and then uses staprun to load it.

When stap is invoked, it creates a kernel module and uses staprun to load it into the running kernel. The module executes, gathering data and sending it back to the stap client process via debuginfo symbols and the /proc/kernel/debug/systemtap virtual filesystem. When the script finishes or is interrupted, stap unloads the module and cleans up. The staprun utility may be invoked directly by users or scripts to manage these modules.

The security and safety of SystemTap's kernel probing capabilities are enforced through a group-based access control mechanism. A user running stap or staprun must be a member of one or more of the following groups:

stapdev
Members of the stapdev group can write and load script modules with root-equivalent privileges, without particular security constraints. (Many safety constraints remain.)
stapsys
Members of the stapsys group have almost all the privileges of stapdev, except for guru mode constructs.
stapusr
Members of the stapusr group may use any-privileged modules placed into the /lib/modules/VERSION/systemtap by the system administrator.
stapusr
Members only of the stapusr group may also write and load low-privilege script modules, which are normally limited to manipulating their own processes (and not the kernel nor other users' processes).

The stap command itself may be invoked with the --privilege= option to request a specific privilege level, which staprun will later enforce. This option is not available when invoking staprun directly.

OPTIONS

The following options are available:

-d MODULE ...
Unload the specified kernel module(s). This is typically done automatically by stap when a script finishes, but may be invoked directly to unload a module previously loaded by staprun.
-l [MODULE ...]
List loaded SystemTap kernel modules. If MODULE arguments are provided, list only those modules. The output includes the module name, its load address, the SystemTap script name (if available), and the number of active probes.
-k MODULE ...
Kill the specified SystemTap process(es). This sends a signal to the SystemTap client process associated with the kernel module, causing it to terminate and the module to be unloaded.
-u MODULE ...
Update the specified SystemTap module(s). This is used when a SystemTap script has been recompiled and the new module needs to be loaded in place of the old one.
-r MODULE ...
Reload the specified SystemTap module(s). This is similar to -u, but it unloads the module before loading the new one.
-p PROCESS ...
Attach to the specified SystemTap process(es). This is used to attach to an already running SystemTap script.
--module-path=MODULE_PATH ...
Specify a directory in which to search for modules. This option can be specified multiple times. By default, modules are searched for in /lib/modules/$(uname -r)/systemtap.
-v
Verbose mode. Print additional information during execution.
-g
Guru mode. Allows the use of advanced and potentially unsafe SystemTap features. Requires appropriate group membership (e.g., stapdev).

ARGUMENTS

When invoked with a script (e.g., stap compiled script), SCRIPT is the path to the script file or the script itself. Any arguments following the script are passed to the script when it runs.

When invoked with module management options (e.g., -d, -l), MODULE specifies the name of the SystemTap kernel module.

When invoked with the -p option, PROCESS specifies the PID of the SystemTap client process.

EXAMPLES

Load a SystemTap script and pass arguments to it:

staprun my_script.ko --arg1 value1 --arg2 value2

Unload a SystemTap module:

staprun -d my_script.ko

List all loaded SystemTap modules:

staprun -l

List a specific SystemTap module:

staprun -l my_script.ko

MODULE DETACHING AND ATTACHING

SystemTap relies on the kernel's module loading/unloading mechanism to insert and remove probing code. The staprun utility interacts with this mechanism. When a script is loaded, staprun uses the kernel's module interface to load a module compiled from the script. When the script is unloaded or terminates, staprun uses the module interface to remove the module.

The options -d, -u, -r, and -k are used to manage the lifecycle of these modules and their associated processes.

FILE SWITCHING BY SIGNAL

SystemTap can be configured to switch output files upon receiving certain signals. This allows for log rotation or collection of data in segments. The signals to which the script should respond are specified during script development using the `tapset.กอง` directive or similar mechanisms.

When such a script is run via stap and staprun, staprun ensures that the necessary signal handlers are set up in the kernel module to manage the file switching.

SAFETY AND SECURITY

SystemTap's ability to probe the kernel is powerful but carries inherent risks. To mitigate these risks, SystemTap employs a multi-layered security approach:

  • Group Membership: As described in the DESCRIPTION section, users must belong to specific groups (stapdev, stapsys, stapusr) to perform different levels of system tracing. This limits who can run powerful tracing scripts.
  • Privilege Levels: The --privilege= option (used with stap) allows a user to specify a desired privilege level for a script. staprun enforces this level, potentially preventing a script from running if the user lacks the necessary group membership.
  • Guru Mode Restrictions: While stapdev members can use guru mode, stapsys members cannot. Guru mode grants more direct access to kernel internals, increasing the potential for system instability.
  • Module Signing and Trust: For enhanced security, particularly in production environments, SystemTap can leverage a stap-server with cryptographic signing. This ensures that only trusted modules are loaded into the kernel. Refer to the stap-server(8) manual page for more details.

On kernels with FIPS mode enabled, staprun normally prevents the loading of SystemTap-generated kernel modules due to potential kernel panics. If your kernel has specific patches (e.g., linux commit #002c77a48b47), you can override this behavior by setting the environment variable STAP_FIPS_OVERRIDE to any value. Use this override with caution.

Members of the stapdev group can write and load script modules with root-equivalent privileges, without particular security constraints. (Many safety constraints remain.)
stapsys
Members of the stapsys group have almost all the privileges of stapdev, except for guru mode constructs.
stapusr
Members only of the stapusr group may any-privileged modules placed into the /lib/modules/VERSION/systemtap by the system administrator.
stapusr
Members only of the stapusr group may also write and load low-privilege script modules, which are normally limited to manipulating their own processes (and not the kernel nor other users' processes).

Part of the privilege enforcement mechanism may require using a stap-server and administrative trust in its cryptographic signer; see the stap-server(8) manual page for a for more information.

On a kernel with FIPS mode enabled, staprun normally refuses to attempt to load systemtap-generated kernel modules. This is because on some kernels, this results in a panic. If your kernel includes corrections such as linux commit #002c77a48b47, then you can force staprun to attempt module loads anyway, by setting the STAP_FIPS_OVERRIDE environment variable to any value.

FILES

/lib/modules/VERSION/systemtap
If MODULE is a module name, the module will be looked for in this directory. Users who are only in the 'stapusr' group can install modules located in this directory. This directory must be owned by the root user and not be world writable.
