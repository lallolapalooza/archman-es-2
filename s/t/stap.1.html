NOMBRE

stap - traductor/controlador de scripts de systemtap

SINOPSIS

stap [ OPCIONES ] NOMBRE_ARCHIVO [ ARGUMENTOS ]
stap [ OPCIONES ] - [ ARGUMENTOS ]
stap [ OPCIONES ] -e SCRIPT [ ARGUMENTOS ]
stap [ OPCIONES ] -l PROBE [ ARGUMENTOS ]
stap [ OPCIONES ] -L PROBE [ ARGUMENTOS ]
stap [ OPCIONES ] --dump-probe-types
stap [ OPCIONES ] --dump-probe-aliases
stap [ OPCIONES ] --dump-functions

DESCRIPCIÓN

El programa stap es el front-end de la herramienta Systemtap. Acepta instrucciones de sondeo escritas en un lenguaje simple específico del dominio, traduce esas instrucciones a código C, compila ese código C y carga el módulo resultante en un kernel Linux en ejecución o en un mutador de espacio de usuario Dyninst, para realizar las funciones de rastreo/sondeo del sistema solicitadas. Puede suministrar el script en un archivo con nombre (NOMBRE_ARCHIVO), desde la entrada estándar (use - en lugar de NOMBRE_ARCHIVO), o desde la línea de comandos (usando -e SCRIPT). El programa se ejecuta hasta que es interrumpido por el usuario, o si el script invoca voluntariamente la función exit(), o por un número suficiente de errores suaves.

El lenguaje, que se describe en la sección LENGUAJE DE SCRIPT a continuación, está estrictamente tipado, es expresivo, libre de declaraciones, procedimental y amigable con la creación de prototipos, y está inspirado en awk y C. Permite asociar puntos de código fuente o eventos en el sistema con manejadores, que son subrutinas que se ejecutan de forma síncrona. Es algo similar conceptualmente a las "listas de comandos de punto de interrupción" en el depurador gdb.

OPCIONES

El traductor de systemtap admite las siguientes opciones. Cualquier otra opción imprime una lista de opciones admitidas. Las opciones pueden darse en la línea de comandos, como de costumbre. Si el archivo $SYSTEMTAP_DIR/rc existe, las opciones también se cargan desde allí y se interpretan primero. ($SYSTEMTAP_DIR por defecto es $HOME/.systemtap si no está definido).

En algunos casos, el valor predeterminado de una opción depende de la configuración particular del sistema y, por lo tanto, no se puede mencionar aquí directamente. En algunos de esos casos, ejecutar "stap --help" puede mostrar el valor predeterminado.

-i --interactive

-t

--modinfo NAME=VALUE
Agregue el par nombre/valor como una llamada a macro MODULE_INFO al módulo generado. Esto puede ser útil para informar o anular varias comprobaciones relacionadas con el módulo en el kernel.
-G NAME=VALUE
Establece el valor de la variable global NAME a VALUE cuando se invoca staprun. Esto se aplica a las variables escalares declaradas globales en el script/tapset.
-R DIR
Busque las fuentes de tiempo de ejecución de systemtap en el directorio dado. Su valor predeterminado DIR se puede ver usando "stap --help".
-r /DIR
Construya para el kernel en el árbol de compilación dado. También se puede establecer con la variable de entorno SYSTEMTAP_RELEASE.
-r RELEASE
Construya para el kernel en el árbol de compilación /lib/modules/RELEASE/build. También se puede establecer con la variable de entorno SYSTEMTAP_RELEASE.
-m MODULE
Utilice el nombre dado para el módulo de objeto del kernel generado, en lugar de un nombre aleatorio único. El módulo de objeto del kernel generado se copia al directorio actual.
-d MODULE
Agregue información de símbolos/desenrollado para el módulo dado al módulo de objeto del kernel. Esto puede habilitar rastreos simbólicos de esos módulos/programas, incluso si no tienen una sonda explícita colocada en ellos.
--ldd
Agregue información de símbolos/desenrollado para todas las bibliotecas compartidas del espacio de usuario sospechosas por ldd de ser necesarias para los binarios del espacio de usuario que se están sondeando o listando con la opción -d. Precaución: esto puede hacer que los módulos de sonda sean considerablemente más grandes. Tenga en cuenta que esta opción no se ocupa de los módulos del espacio del kernel: vea --all-modules a continuación en su lugar.
--all-modules
Equivalente a especificar "-dkernel" y un "-d" para cada módulo del kernel que esté cargado actualmente. Precaución: esto puede hacer que los módulos de sonda sean considerablemente más grandes.
-o FILE
Envíe la salida estándar al archivo con nombre. En modo masivo, los archivos por CPU comenzarán con FILE_ (FILE_cpu con -F) seguido del número de CPU. Esto admite formatos strftime(3) para FILE.
-c CMD
Inicie las sondas, ejecute CMD y salga cuando CMD termine. Esto también tiene el efecto de establecer target() al pid de ese proceso. Tenga en cuenta que muchos tipos de sondas se activan independientemente de esta configuración. Considere incluir algo como esto para enfocar su script. 
   probe FOO { if (pid() != target()) next; .... }
-x PID
Establece target() a PID. El script se ejecuta independientemente de la vida del PID.
-e SCRIPT
Ejecute el SCRIPT dado especificado en la línea de comandos.
-E SCRIPT
Ejecute el SCRIPT dado especificado. Este SCRIPT se ejecuta además del script principal especificado, a través de -e, o como un archivo de script. Esta opción se puede repetir para ejecutar múltiples scripts y se puede usar en modo de listado (-l/-L).
-l PROBE
En lugar de ejecutar un script de sonda, simplemente liste todos los puntos de sonda disponibles que coincidan con el punto de sonda dado. El patrón puede incluir comodines y alias, pero no puntos de sonda múltiples separados por comas. El código de resultado del proceso indicará un error si no hay coincidencias. 
% stap -e 'probe syscall.* { }'
[...]
% stap -l 'syscall.*'
syscall.accept
[...]
syscall.writev
-L PROBE
Similar a "-l", pero liste los puntos de sonda coincidentes más sus variables de contexto disponibles. Cuando se establece -v con -L, la salida incluye puntos de sonda duplicados que se distinguen por su dirección PC. 
% stap -L 'process("/lib64/libpython*.so.*").mark("*")'
process("/usr/lib64/libpython2.7.so.1.0").mark("function__entry") $arg1:long $arg2:long $arg3:long
process("/usr/lib64/libpython2.7.so.1.0").mark("function__return") $arg1:long $arg2:long $arg3:long
process("/usr/lib64/libpython3.6m.so.1.0").mark("function__entry") $arg1:long $arg2:long $arg3:long
process("/usr/lib64/libpython3.6m.so.1.0").mark("function__return") $arg1:long $arg2:long $arg3:long
process("/usr/lib64/libpython3.6m.so.1.0").mark("gc__done") $arg1:long
process("/usr/lib64/libpython3.6m.so.1.0").mark("gc__start") $arg1:long
process("/usr/lib64/libpython3.6m.so.1.0").mark("line") $arg1:long $arg2:long $arg3:long
-F
Sin la opción -o, cargue el módulo e inicie las sondas, luego desvincúlese del módulo dejando las sondas en ejecución. Con la opción -o, ejecute staprun en segundo plano como un demonio y muestre su pid.
-S size[,N]
Establece el tamaño máximo del archivo de salida y el número máximo de archivos de salida. Si el tamaño del archivo de salida excede los **size** megabytes, systemtap cambia el archivo de salida al siguiente archivo. Y si el número de archivos de salida excede **N**, systemtap elimina el archivo de salida más antiguo. Puede omitir el segundo argumento.
-T TIMEOUT
Salga del script después de TIMEOUT segundos.
--skip-badvars
Ignore las variables de contexto irresolubles o inaccesibles en tiempo de ejecución y sustitúyalas por 0, sin errores.
--prologue-searching[=WHEN]
Modo de búsqueda de prólogo. Active heurísticas para solucionar problemas con información de depuración incorrecta para las variables de contexto del parámetro de función $context. WHEN puede ser "never", "always", o "auto" (es decir, habilitado por heurística). Si WHEN falta, se asume "always". Si la opción falta, se asume "auto".
--suppress-handler-errors
Envuelva todos los manejadores de sondas en algo como esto 
try { ... } catch { next }

bloque, lo que hace que cualquier error en tiempo de ejecución se suprima silenciosamente. Los errores suprimidos no cuentan para los límites de **MAXERRORS**. En este modo, los límites de **MAXSKIPPED** también se suprimen, por lo que se pueden acumular muchos errores y sondas omitidas durante la ejecución de un script. Los recuentos generales aún se informarán al apagar.

--compatible VERSION
Suprima cambios recientes en el lenguaje de script o en los tapsets que sean incompatibles con la versión anterior de systemtap dada. Esto puede ser útil si un script de systemtap mucho más antiguo falla al ejecutarse. Consulte la sección DEPRECACIÓN para obtener más detalles.
--check-version
Esta opción se utiliza para comprobar si el script activo tiene alguna construcción que pueda ser específica de la versión de systemtap. Consulte la sección DEPRECACIÓN para obtener más detalles.
--clean-cache
Esta opción elimina entradas obsoletas del directorio de caché. Esto normalmente se hace automáticamente después de ejecuciones exitosas, pero esta opción activará la limpieza manualmente y luego saldrá. Consulte la sección CACHING para obtener más detalles sobre los límites de caché.
--color[=WHEN], --colour[=WHEN]
Esta opción controla la coloración de los mensajes de error. WHEN puede ser "never", "always", o "auto" (es decir, habilitado solo si está en una terminal). Si WHEN falta, se asume "always". Si la opción falta, se asume "auto".

Los colores se pueden modificar utilizando la variable de entorno SYSTEMTAP_COLORS. El formato debe ser de la forma key1=val1:key2=val2:key3=val3 ...etc. Las claves válidas son "error", "warning", "source", "caret", y "token". Los valores constituyen uno o más parámetros de Representación Gráfica Selectiva (SGR). Consulte la documentación de su terminal para ver los SGR que admite. Como ejemplo, los colores predeterminados se expresarían como error=01;31:warning=00;33:source=00;34:caret=01:token=01. Si SYSTEMTAP_COLORS está ausente, se utilizarán los colores predeterminados. Si está vacío o es inválido, la coloración se desactiva.

--disable-cache
Esta opción deshabilita todo uso del directorio de caché. No se leerán ni escribirán archivos en la caché.
--poison-cache
Esta opción trata los archivos en el directorio de caché como inválidos. No se leerán archivos de la caché, pero los archivos resultantes de esta ejecución aún se escribirán en la caché. Esto está destinado como una ayuda para la resolución de problemas cuando el comportamiento en caché de stap parece estar funcionando mal. Si ayudó, probablemente haya un error en systemtap que los desarrolladores querrían que usted informara.
--privilege[=stapusr | =stapsys | =stapdev]
Esta opción instruye a stap a examinar el script en busca de construcciones que no están permitidas para el nivel de privilegio especificado (ver USUARIOS NO PRIVILEGIADOS). La compilación falla si se utilizan dichas construcciones. Si se especifican stapusr o stapsys al usar un servidor de compilación (ver --use-server), el servidor examinará el script y, si la compilación tiene éxito, el servidor firmará criptográficamente el módulo del kernel resultante, certificando que es seguro para su uso por parte de usuarios en el nivel de privilegio especificado.

--privilege=MODE
Set the privilege level for the script. This affects the set of probes that may be used and the set of functions that may be called. The available modes are:
stapdev
Enable use of all available probes and functions. This is the default mode for the root user, and for users in the stapdev group.
stapusr
Enable use of a restricted set of probes and functions suitable for use by unprivileged users. This is the default mode for unprivileged users.
kernel
This is equivalent to stapdev. It is retained for compatibility with earlier versions of SystemTap.
If --privilege has not been specified, -pN has not been specified with N < 5, and the invoking user is not root, and is not a member of the group stapdev, then stap will automatically add the appropriate --privilege option to the options already specified.
--unprivileged
This option is equivalent to --privilege=stapusr.
--use-server[=HOSTNAME[:PORT] | =IP_ADDRESS[:PORT] | =CERT_SERIAL]
Specify compile-server(s) to be used for compilation and/or in conjunction with --list-servers and --trust-servers (see below) for listing. If no argument is supplied, then the default in unprivileged mode (see --privilege) is to select compatible servers which are trusted as SSL peers and as module signers and currently online. Otherwise the default is to select compatible servers which are trusted as SSL peers and currently online. --use-server may be specified more than once, in which case a list of servers is accumulated in the order specified. Servers may be specified by host name, ip address, or by certificate serial number (obtained using --list-servers). The latter is most commonly used when adding or revoking trust in a server (see --trust-servers below). If a server is specified by host name or ip address, then an optional port number may be specified. This is useful for accessing servers which are not on the local network or to specify a particular server.

IP addresses may be IPv4 or IPv6 addresses.

If a particular IPv6 address is link local and exists on more than one interface, the intended interface may be specified by appending the address with a percent sign (%) followed by the intended interface name. For example, "fe80::5eff:35ff:fe07:55ca%eth0".

In order to specify a port number with an IPv6 address, it is necessary to enclose the IPv6 address in square brackets ([]) in order to separate the port number from the rest of the address. For example, "[fe80::5eff:35ff:fe07:55ca]:5000" or "[fe80::5eff:35ff:fe07:55ca%eth0]:5000".

If --use-server has not been specified, -pN has not been specified with N < 5, and the invoking user not root, is not a member of the group stapdev, but is a member of the group stapusr, then stap will automatically add --use-server to the options already specified.

--use-server-on-error[=yes|=no]
Instructs stap to retry compilation of a script using a compile server if compilation on the local host fails in a manner which suggests that it might succeed using a server. If this option is not specified, the default is no. If no argument is provided, then the default is yes. Compilation will be retried for certain types of errors (e.g. insufficient data or resources) which may not occur during re-compilation by a compile server. Compile servers will be selected automatically for the re-compilation attempt as if --use-server was specified with no arguments.
--list-servers[=SERVERS]
Display the status of the requested SERVERS, where SERVERS is a comma-separated list of server attributes. The list of attributes is combined to filter the list of servers displayed. Supported attributes are:
all
specifies all known servers (trusted SSL peers, trusted module signers, online servers).
specified
specifies servers specified using --use-server.
online
filters the output by retaining information about servers which are currently online.
trusted
filters the output by retaining information about servers which are trusted as SSL peers.
signer
filters the output by retaining information about servers which are trusted as module signers (see --privilege).
compatible
filters the output by retaining information about servers which are compatible with the current kernel release and architecture.
If no argument is provided, then the default is specified. If no servers were specified using --use-server, then the default servers for --use-server are listed.

Note that --list-servers uses the avahi-daemon service to detect online servers. If this service is not available, then --list-servers will fail to detect any online servers. In order for --list-servers to detect servers listening on IPv6 addresses, the avahi-daemon configuration file /etc/avahi/avahi-daemon.conf must contain an active "use-ipv6=yes" line. The service must be restarted after adding this line in order for IPv6 to be enabled.

--trust-servers[=TRUST_SPEC]
Grant or revoke trust in compile-servers, specified using --use-server as specified by TRUST_SPEC, where TRUST_SPEC is a comma-separated list specifying the trust which is to be granted or revoked. Supported elements are:
ssl
trust the specified servers as SSL peers.
signer
trust the specified servers as module signers (see --privilege). Only root can specify signer.
all-users
grant trust as an ssl peer for all users on the local host. The default is to grant trust as an ssl peer for the current user only. Trust as a module signer is always granted for all users. Only root can specify all-users.
revoke
revoke the specified trust. The default is to grant it.
no-prompt
do not prompt the user for confirmation before carrying out the requested action. The default is to prompt the user for confirmation.
If no argument is provided, then the default is ssl. If no servers were specified using --use-server, then no trust will be granted or revoked.
Unless no-prompt has been specified, the user will be prompted to confirm the trust to be granted or revoked before the operation is performed.
--sign-module
Sign the module with a MOK (Machine Owner Key) on UEFI/SecureBoot systems. See the SECUREBOOT section for more details.
--dump-probe-types
Dumps a list of supported probe types and exits. If --privilege=stapusr is also specified, the list will be limited to probe types available to unprivileged users.
--dump-probe-aliases
Dumps a list of all probe aliases found in library files and exits.
--dump-functions
Dumps a list of all the public functions found in library files and exits. Also includes their parameters and types. A function of type 'unknown' indicates a function that does not return a value. Note that not all function/parameter types may be resolved (these are also shown by 'unknown'). This features is very memory-intensive and thus may not work properly with --use-server if the target server imposes an rlimit on process memory (i.e. through the ~stap-server/.systemtap/rc configuration file, see stap-server(8)).
--remote URL
Set the execution target to the given host. This option may be repeated to target multiple execution targets. Passes 1-4 are completed locally as normal to build the script, and then pass 5 will copy the module to the target and run it. Acceptable URL forms include:
[USER@]HOSTNAME, ssh://[USER@]HOSTNAME
This mode uses ssh, optionally using a username not matching your own. If a custom ssh_config file is in use, add SendEnv LANG to retain internationalization functionality.
libvirt://DOMAIN, libvirt://DOMAIN/LIBVIRT_URI
This mode uses stapvirt to execute the script on a domain managed by libvirt. Optionally, LIBVIRT_URI may be specified to connect to a specific driver and/or a remote host. For example, to connect to the local privileged QEMU driver, use: 
--remote libvirt://MyDomain/qemu:///system

See the page at http://libvirt.org/uri.html for supported URIs. Also see stapvirt(1) for more information on how to prepare the domain for stap probing.

unix:PATH
This mode connects to a UNIX socket. This can be used with a QEMU virtio-serial port for executing scripts inside a running virtual machine.
direct://
Special loopback mode to run on the local host.
--remote-prefix
Prefix each line of remote output with "N: ", where N is the index of the remote execution target from which the given line originated.
--download-debuginfo[=OPTION]
Enable, disable or set a timeout for the automatic debuginfo downloading feature offered by abrt as specified by OPTION, where OPTION is one of the following:
yes
enable automatic downloading of debuginfo with no timeout. This is the default behavior when this option is specified without an argument.
no
disable automatic downloading of debuginfo.
TIMEOUT
enable automatic downloading of debuginfo with a timeout of TIMEOUT seconds. If the download does not complete within TIMEOUT seconds, an error message is generated, and the debuginfo is not downloaded.

This option requires that the abrt package be installed.

OPCIONES GENERALES

--download-debuginfo=OPCION
Permite la descarga automática de información de depuración. Las opciones válidas son:
default
Descargar información de depuración solo si es necesario para un script de SystemTap o de un módulo que se está ejecutando. La ausencia de un valor OPTION para --download-debuginfo es lo mismo que no proporcionarlo.
no
desactivar explícitamente la descarga automática de información de depuración. Esto es lo mismo que no usar la opción en absoluto.
ask
mostrar la salida de abrt, y preguntar antes de continuar la descarga. No se establecerá ningún tiempo de espera.
<timeout>
especificar un tiempo de espera como un número positivo para detener la descarga si tarda más de <timeout> segundos.
--rlimit-as=NUM
Especifica el tamaño máximo de la memoria virtual del proceso (espacio de direcciones), en bytes.
--rlimit-cpu=NUM
Especifica el límite de tiempo de CPU, en segundos.
--rlimit-nproc=NUM
Especifica el número máximo de procesos que se pueden crear.
--rlimit-stack=NUM
Especifica el tamaño máximo de la pila del proceso, en bytes.
--rlimit-fsize=NUM
Especifica el tamaño máximo de los archivos que el proceso puede crear, en bytes.
--sysroot=DIR

LENGUAJE DE SCRIPT

El lenguaje de scripts de SystemTap se parece a awk y a C. Hay dos construcciones principales: sondas y funciones. Dentro de estas, las sentencias y expresiones utilizan una sintaxis y precedencia de operadores similar a la de C.

SINTAXIS GENERAL

El espacio en blanco se ignora. Se admiten tres formas de comentarios:


# ... estilo shell, hasta el final de la línea, excepto para $# y @#
// ... estilo C++, hasta el final de la línea
/* ... estilo C ... */
Los literales son cadenas de caracteres encerradas entre comillas dobles (pasando por los códigos de escape C habituales con barras invertidas, y con literales de cadena adyacentes unidos, también como en C), o enteros (en decimal, hexadecimal u octal, utilizando la misma notación que en C). Todas las cadenas están limitadas a una longitud razonable (unos pocos cientos de bytes). Los enteros son cantidades de 64 bits con signo, aunque el analizador también acepta (y envuelve) valores superiores a 2**63 positivos.

Además, los argumentos del script proporcionados al final de la línea de comandos pueden insertarse. Utilice $1 ... $<NN> para la inserción sin comillas, @1 ... @<NN> para la inserción como literal de cadena. El número de argumentos puede accederse a través de $# (como un número sin comillas) o a través de @# (como un número entre comillas). Estos pueden usarse en cualquier lugar donde pueda comenzar un token, incluso dentro de la etapa de preprocesamiento. La referencia a un número de argumento superior al que realmente se proporcionó es un error.

PREPROCESAMIENTO

Una etapa simple de preprocesamiento condicional se ejecuta como parte del análisis. La forma general es similar al operador ternario cond ? exp1 : exp2:

%( CONDICION %? TOKENS-VERDADEROS %)
%( CONDICION %? TOKENS-VERDADEROS %: TOKENS-FALSOS %)

La CONDICION es una expresión cuyo formato se determina por su primer palabra clave, o una comparación de literales de cadena o una comparación de literales numéricos. También puede estar compuesta por muchas alternativas y conjunciones de CONDICIONES (entendidas como en la oración anterior) usando || y && respectivamente. Sin embargo, los paréntesis aún no son compatibles, por lo que es importante recordar que la conjunción tiene precedencia sobre la alternativa.

Si la primera parte es el identificador kernel_vr o kernel_v para referirse al número de versión del kernel, con ("2.6.13-1.322FC3smp") o sin ("2.6.13") el sufijo del código de lanzamiento, entonces la segunda parte es uno de los seis operadores de comparación numérica estándar <, <=, ==, !=, >, y >=, y la tercera parte es un literal de cadena que contiene un valor de versión-lanzamiento estilo RPM. La condición se considera satisfecha si la versión del kernel de destino (según lo anulada opcionalmente por la opción -r) se compara con la cadena de versión dada. La comparación la realiza la función glibc strverscmp. Como caso especial, si el operador es para igualdad simple (==) o desigualdad (!=), y la tercera parte contiene algún carácter comodín (* o ? o [), entonces la expresión se trata como una coincidencia (o no coincidencia) de comodines evaluada por fnmatch.

Si, por otro lado, la primera parte es el identificador arch para referirse a la arquitectura del procesador (como la nombra el sistema de compilación del kernel ARCH/SUBARCH), entonces la segunda parte es uno de los dos operadores de comparación de cadenas == o !=, y la tercera parte es un literal de cadena para compararla. Esta comparación es una coincidencia (o no coincidencia) de comodines.

De manera similar, si la primera parte es un identificador como CONFIG_something para referirse a una opción de configuración del kernel, entonces la segunda parte es == o !=, y la tercera parte es un literal de cadena para comparar el valor (comúnmente "y" o "m"). Las opciones de configuración del kernel inexistentes o no establecidas se representan con una cadena vacía. Esta comparación también es una coincidencia (o no coincidencia) de comodines.

Si la primera parte es el identificador systemtap_v, la prueba se refiere a la versión de compatibilidad de systemtap, que puede ser anulada para scripts antiguos con la opción --compatible. El operador de comparación es el mismo que para kernel_v y el lado derecho

DECLARACIONES DE FLUJO DE CONTROL

while EXP STMT
Execute STMT while the boolean expression EXP is true.
for (INIT; COND; INC) STMT
Execute STMT while the boolean expression COND is true. INIT is executed once before the loop, and INC is executed after each iteration.
foreach (VAR in ARRAY) STMT
Iterate over the elements of the associative array ARRAY. On each iteration, the key of the current element is assigned to the scalar variable VAR. The STMT is executed for each element.
foreach (K_VAR, V_VAR in ARRAY) STMT
This variant iterates over the keys and values of the associative array ARRAY. On each iteration, the key of the current element is assigned to K_VAR and the value is assigned to V_VAR. STMT is executed for each element.
foreach (VAR in ARRAY [INDEX1, INDEX2, ...] [ limit EXP ]) STMT
Lo mismo que el anterior, donde las iteraciones se limitan a los elementos de la matriz cuyas claves coinciden con los valores de índice especificados. El símbolo * se puede utilizar para especificar un índice y se tratará como un comodín.
foreach (VAR0 = VAR in ARRAY [ limit EXP ]) STMT
Esta variante de foreach guarda el valor actual en VAR0 en cada iteración, por lo que es lo mismo que ARRAY[VAR]. Esto también funciona con una tupla de claves. Los sufijos de ordenación en VAR0 tienen el mismo efecto que en ARRAY.
foreach (VAR0 = VAR in ARRAY [INDEX1, INDEX2, ...] [ limit EXP ]) STMT
Lo mismo que el anterior, donde las iteraciones se limitan a los elementos de la matriz cuyas claves coinciden con los valores de índice especificados. El símbolo * se puede utilizar para especificar un índice y se tratará como un comodín.
break, continue
Salga o itere la declaración de bucle anidado más interno (while o for o foreach).
return EXP
Devuelve el valor EXP de la función envolvente. Si el valor de la función no se toma en ningún lugar, no es necesaria una declaración de retorno, y la función tendrá un tipo especial de "desconocido" sin valor de retorno.
next
Regrese ahora del manejador de sonda envolvente. Esto es especialmente útil en alias de sonda que aplican predicados de filtrado de eventos. Cuando se usa en funciones, la ejecución se transferirá inmediatamente a la siguiente función sobrecargada.
try { STMT1 } catch { STMT2 }
Ejecute las declaraciones en el primer bloque. Ante cualquier error en tiempo de ejecución, aborte STMT1 y comience a ejecutar STMT2. Cualquier error en STMT2 se propagará a bloques try/catch externos, si los hay.
try { STMT1 } catch(VAR) { STMT2 }
Igual que el anterior, más la asignación del mensaje de error a la variable escalar de cadena VAR.
delete ARRAY[INDEX1, INDEX2, ...]
Elimine de ARRAY el elemento especificado por la tupla de índice. Si la tupla de índice contiene un * en lugar de un índice, el * se trata como un comodín y todos los elementos con claves que coinciden con la tupla de índice se eliminarán de ARRAY. El valor ya no estará disponible y las iteraciones subsiguientes no informarán el elemento. No es un error eliminar un elemento que no existe.
delete ARRAY
Elimine todos los elementos de ARRAY.
delete SCALAR
Elimina el valor de SCALAR. Los enteros y las cadenas se borran a 0 y "" respectivamente, mientras que las estadísticas se restablecen al estado vacío inicial.

operadores numéricos binarios
* / % + - >> << & ^ | && ||
operadores de cadena binarios
. (concatenación de cadenas)
operadores de asignación numéricos
= *= /= %= += -= >>= <<= &= ^= |=
operadores de asignación de cadena
= .=
operadores numéricos unarios
+ - ! ~ ++ --
operadores de comparación numérica binaria, de cadena o de coincidencia de expresiones regulares
< > <= >= == != =~ !~
operador ternario
cond ? exp1 : exp2
operador de agrupación
( exp )
llamada a función
fn ([ arg1, arg2, ... ])
comprobación de pertenencia a matriz
exp in array
[exp1, exp2, ... ] in array
[*, *, ... ] in array

COINCIDENCIA DE EXPRESIONES REGULARES

El lenguaje de scripting admite la coincidencia de expresiones regulares. La sintaxis básica es la siguiente:

exp =~ regex
exp !~ regex

(El primer operando debe ser una expresión que evalúe a una cadena; el segundo operando debe ser un literal de cadena que contenga una expresión regular sintácticamente válida.)

La sintaxis de expresiones regulares admite características de Expresiones Regulares Extendidas POSIX según se documenta en grep(1), excepto la funcionalidad de reutilización de subexpresiones ("\1").

Después de una coincidencia exitosa, el contenido de la cadena coincidente y las subexpresiones se pueden extraer utilizando las funciones tapset matched() y ngroups() de la siguiente manera:

if ("una cadena de ejemplo" =~ "cad(ena)") {
  matched(0) // -> devuelve "cadena", la subcadena coincidente
  matched(1) // -> devuelve "ena", la primera subexpresión coincidente
  ngroups()  // -> devuelve 2, el número de grupos coincidentes
}

SONDAS

La construcción principal en el lenguaje de scripting identifica las sondas. Las sondas asocian eventos abstractos con un bloque de sentencias ("manejador de sonda") que se ejecutará cuando ocurra cualquiera de esos eventos. La sintaxis general es la siguiente:

probe PROBEPOINT [, PROBEPOINT] { [STMT ...] }
probe PROBEPOINT [, PROBEPOINT] if (CONDITION) { [STMT ...] }

Los eventos se especifican en una sintaxis especial llamada "puntos de sonda". Hay varias variedades de puntos de sonda definidos por el traductor, y los scripts tapset pueden definir otros adicionales usando alias. Los puntos de sonda pueden usar comodines, agruparse o listarse en secuencias de preferencia, o declararse opcionales. Se pueden encontrar más detalles sobre la sintaxis y semántica de los puntos de sonda en la página del manual stapprobes(3stap).

El manejador de sonda se interpreta en relación con el contexto de cada evento. Para los eventos asociados con código del kernel, este contexto puede incluir variables definidas en el código fuente en ese lugar. Estas "variables de contexto" se presentan al script como variables cuyos nombres están prefijados con "$". Solo se pueden acceder si el compilador del kernel las conservó a pesar de la optimización. Esta es la misma restricción que enfrenta un usuario del depurador al trabajar con código optimizado. Además, los objetos deben existir en memoria paginada en el momento de la ejecución del manejador de sonda de systemtap, ya que systemtap no debe causar (suprime) paginación adicional. Algunos tipos de sonda tienen muy poco contexto. Consulte las páginas del manual stapprobes(3stap) para ver los tipos de variables de contexto disponibles en cada tipo de punto de sonda. A partir de la versión 4.3 de systemtap, las funciones llamadas desde los manejadores de algunos tipos de puntos de sonda también pueden referirse a variables de contexto. Estas se tratan como si un clon de esa función se hubiera insertado en el manejador de sonda que llama y las variables $ se evaluaran en su contexto.

Las sondas pueden estar decoradas con una condición de activación, que consiste en una expresión booleana simple sobre variables globales del script de solo lectura. Mientras están desactivadas (inactivas, la condición se evalúa como falsa), algunos tipos de sondas reducen o eliminan sus sobrecargas en tiempo de ejecución. Cuando una condición de activación se evalúa como verdadera, las sondas se rearmarán pronto, y sus manejadores de sonda comenzarán a llamarse a medida que los eventos ocurran. (Algunos eventos pueden perderse durante el intervalo de activación. Si esto es inaceptable, no use condiciones de activación para esas sondas). Ejemplo de la sintaxis:

probe timer.us(TIMER) if (enabled) {
}

Se pueden definir nuevos puntos de sonda usando "alias". Los alias de puntos de sonda se ven similares a las definiciones de sonda, pero en lugar de activar una sonda en el punto dado, simplemente define un nuevo nombre de punto de sonda como un alias de uno existente. Hay dos tipos de alias, es decir, el estilo prólogo y el estilo epílogo, que se identifican por "=" y "+=" respectivamente.

Para el alias de estilo prólogo, el bloque de sentencias que sigue a una definición de alias se agrega implícitamente como un prólogo a cualquier sonda que se refiera al alias. Mientras que para el alias de estilo epílogo, el bloque de sentencias que sigue a una definición de alias se agrega implícitamente como un epílogo a cualquier sonda que se refiera al alias. Por ejemplo:

probe syscall.read = kernel.function("sys_read") {
  fildes = $fd
  if (execname() == "init") next  # omitir el resto de la sonda
}

define un nuevo punto de sonda syscall.read, que se expande a kernel.function("sys_read"), con la declaración dada como prólogo, lo cual es útil para predefinir algunas variables para el usuario del alias y/o para omitir completamente el procesamiento de la sonda basándose en algunas condiciones. Y

probe syscall.read += kernel.function("sys_read") {
  if (tracethis) println ($fd)
}

define un nuevo punto de sonda con la declaración dada como epílogo, lo cual es útil para tomar acciones basadas en variables establecidas o dejadas por el usuario del alias. Tenga en cuenta que en cada caso, las declaraciones en el bloque del manejador del alias se tratan de forma ordinaria, de modo que las variables asignadas allí constituyen una mera inicialización, no una sustitución de macro.

Los alias también se pueden definir para incluir tanto un prólogo como un epílogo.

probe syscall.read = kernel.function("sys_read") {
  fildes = $fd
  if (execname() == "init") next
},{
  if (tracethis) println ($fd)
}

Un alias se usa igual que un tipo de sonda integrado.

probe syscall.read {
  printf("reading fd=%d\n", fildes)
  if (fildes > 10) tracethis = 1
}

Las sondas con un alias pueden utilizar el predicado @probewrite. Esta comprobación se utiliza para detectar si una variable de script o una variable de destino se ha escrito en el cuerpo del manejador de sonda.

>
@probewrite(var)
se expande a 1 si var ha sido escrita en el cuerpo del manejador de sondeo, de lo contrario se expande a 0.

En el siguiente ejemplo, @probewrite(var) se expande a 1 porque var ha sido escrita en el cuerpo del manejador de sondeo y, en consecuencia, se ejecutará la declaración condicional.

probe foo = begin { var = 0 }, { if (@probewrite(var)) println(var) }
probe foo {
  var = 1
}

FUNCIONES

Los scripts de Systemtap pueden definir subrutinas para factorizar trabajos comunes. Las funciones aceptan cualquier número de argumentos escalares (enteros o cadenas) y deben devolver un único valor escalar (entero o cadena). Una declaración de función de ejemplo se ve así:

function thisfn (arg1, arg2) {
   return arg1 + arg2
}

Tenga en cuenta la ausencia general de declaraciones de tipo, que son inferidas por el traductor. Sin embargo, si se desea, una definición de función puede incluir declaraciones de tipo explícitas para su valor de retorno y/o sus argumentos. Esto es especialmente útil para funciones embebidas en C. En el siguiente ejemplo, el motor de inferencia de tipos solo necesita inferir el tipo de arg2 (una cadena).

function thatfn:string (arg1:long, arg2) {
   return sprint(arg1) . arg2
}

Las funciones pueden llamar a otras o a sí mismas de forma recursiva, hasta un límite fijo de anidamiento. Este límite está definido por la macro MAXNESTING en el código C traducido y está en el orden de 10.

Las funciones pueden marcarse como privadas usando la palabra clave private para limitar su ámbito al archivo tapset o de script de usuario en el que se definen. Un ejemplo de definición de una función privada es el siguiente:

private function three:long () { return 3 }

Las funciones que terminan sin alcanzar una declaración de retorno explícita devolverán un 0 o "" implícito, determinado por la inferencia de tipos.

Las funciones pueden ser sobrecargadas tanto en tiempo de ejecución como en tiempo de compilación.

La sobrecarga en tiempo de ejecución permite seleccionar la función ejecutada mientras el módulo se está ejecutando según las condiciones de tiempo de ejecución y se logra utilizando la declaración "next" en funciones de script y la macro STAP_NEXT para funciones embebidas en C. Por ejemplo,

function f() { if (condition) next; print("first function") }
function f() %{ STAP_NEXT; print("second function") %}
function f() { print("third function") }

Durante una llamada a la función f(), la ejecución se transferirá a la tercera función si la condición se evalúa como verdadera e imprimirá "third function". Tenga en cuenta que la segunda función se salta incondicionalmente.

La sobrecarga de parámetros permite seleccionar la función a ejecutar en tiempo de compilación en función del número de argumentos proporcionados a la llamada a la función. Por ejemplo,

function g() { print("first function") }
function g(x) { print("second function") }
g() -> "first function"
g(1) -> "second function"

Tenga en cuenta que la sobrecarga en tiempo de ejecución no ocurre en el ejemplo anterior, ya que exactamente una función se resolverá para la llamada a la función. El uso de una declaración "next" dentro de una función cuando no quedan más sobrecargas activará una excepción en tiempo de ejecución. La sobrecarga en tiempo de ejecución solo ocurrirá si las funciones tienen la misma aridad; las funciones con el mismo nombre pero diferente número de parámetros no están relacionadas en absoluto.

El orden de ejecución se determina mediante un valor de prioridad que puede especificarse. Si no se especifica ninguna prioridad explícita, las funciones de script de usuario tienen una prioridad mayor que las funciones de biblioteca. Las funciones de script de usuario y las funciones de biblioteca reciben un valor de prioridad predeterminado de 0 y 1, respectivamente. Las funciones con la misma prioridad se ejecutan en el orden de declaración. Por ejemplo,

function f():3 { if (condition) next; print("first function") }
function f():1 { if (condition) next; print("second function") }
function f():2 { print("third function") }

Dado que la segunda función tiene la máxima prioridad, se ejecuta primero. La primera función nunca se ejecuta, ya que no hay declaraciones "next" en la tercera función para transferir la ejecución.

IMPRIMIR

Hay un conjunto de nombres de funciones que son tratados especialmente por el traductor. Formatean valores para imprimirlos en el flujo de salida estándar de systemtap de una manera más conveniente (tenga en cuenta que los datos generados en el módulo del kernel deben transferirse al espacio de usuario para ser impresos).


Las variantes sprint* devuelven la cadena formateada en lugar de imprimirla.

print, sprint
Imprime uno o más valores de cualquier tipo, concatenados directamente.
println, sprintln
Imprime valores como print y sprint, pero también añade una nueva línea.
printd, sprintd
Toma un delimitador de cadena y dos o más valores de cualquier tipo, e imprime los valores con el delimitador interpuesto. El delimitador debe ser una constante de cadena literal.
printdln, sprintdln
Imprime valores con un delimitador como printd y sprintd, pero también añade una nueva línea.
printf, sprintf
Toma una cadena de formato y un número de valores de tipos correspondientes, y los imprime todos. El formato debe ser una constante de cadena literal.

Las directivas de formato de printf son similares a las de C, excepto que son completamente verificadas por tipo por el traductor:

%b
Escribe un bloque binario del valor dado, en lugar de texto ASCII. El especificador de ancho determina el número de bytes a escribir; los especificadores válidos son %b %1b %2b %4b %8b. El valor predeterminado (%b) es de 8 bytes.
%c
Carácter.
%d,%i
Decimal con signo.
%m
Lee de forma segura memoria del kernel (sin #) o del espacio de usuario (con #) en la dirección dada, y muestra su contenido. El especificador de precisión opcional (no el ancho del campo) determina el número de bytes a leer - el valor predeterminado es 1 byte. %10.4m imprime 4 bytes de la memoria en un campo de 10 caracteres de ancho. Nota: en algunas arquitecturas, la memoria del usuario todavía puede leerse sin #.
%M
Igual que %m, pero muestra en hexadecimal. El tamaño mínimo de salida es el doble del especificador de precisión opcional - el valor predeterminado es 1 byte (2 caracteres hexadecimales). %10.4M imprime 4 bytes de la memoria como 8 caracteres hexadecimales en un campo de 10 caracteres de ancho. %.*M muestra en hexadecimal un número dado de bytes de un buffer dado.
%o
Octal sin signo.
%p
Dirección de puntero sin signo.
%s
Cadena.
%u
Decimal sin signo.
%x
Valor hexadecimal sin signo, en minúsculas.
%X
Valor hexadecimal sin signo, en mayúsculas.
%%
Escribe un %.

El modificador # selecciona las formas alternativas. Para octal, antepone un 0. Para hexadecimal, antepone 0x o 0X, dependiendo de la capitalización. Para caracteres, escapa los valores no imprimibles con escapes tipo C u octal crudo. En el caso de %#m/%#M, accede de forma segura a la memoria del espacio de usuario en lugar de la memoria del espacio del kernel.

Ejemplos:

a = "alice", b = "bob", p = 0x1234abcd, i = 123, j = -1, id[a] = 1234, id[b] = 4567
print("hello")
	Imprime: hello
println(b)
	Imprime: bob\n
println(a . " is " . sprint(16))
	Imprime: alice is 16
foreach (name in id)  printdln("|", strlen(name), name, id[name])
	Imprime: 5|alice|1234\n3|bob|4567
printf("%c is %s; %x or %X or %p; %d or %u\n",97,a,p,p,p,j,j)
	Imprime: a is alice; 1234abcd or 1234ABCD or 0x1234abcd; -1 or 18446744073709551615\n
printf("2 bytes of kernel buffer at address %p: %2m", p, p)
	Imprime: 2 byte of kernel buffer at address 0x1234abcd: <datos binarios>
printf("%4b", p)
	Imprime (estos valores como datos binarios): 0x1234abcd
printf("%#o %#x %#X\n", 1, 2, 3)
	Imprime: 01 0x2 0X3
printf("%#c %#c %#c\n", 0, 9, 42)
	Imprime: \000 \t *

ESTADISTICAS

A menudo es deseable recopilar estadísticas de una manera que evite las penalizaciones de bloquear de forma exclusiva repetidamente las variables globales en las que se están introduciendo esos números. Systemtap proporciona una solución utilizando un operador especial para acumular valores y varias pseudo-funciones para extraer los agregados estadísticos.

El operador de agregación es <<<, y se parece a una asignación, o a una operación de transmisión de salida de C++. El operando izquierdo especifica un lvalue escalar o de índice de matriz, que debe declararse global. El operando derecho es una expresión numérica. El significado es intuitivo: añade el número dado al montón de números para calcular estadísticas. (La lista específica de estadísticas a recopilar se da por separado, mediante las funciones de extracción).

foo <<< 1
stats[pid()] <<< memsize

Las funciones de extracción también son especiales. Por cada aparición de una función de extracción distinta que opera sobre un identificador dado, el traductor se encarga de calcular un conjunto de estadísticas que lo satisfagan. Por lo tanto, el sistema de estadísticas está "bajo demanda". Cada ejecución de una función de extracción hace que la agregación se calcule en ese momento en todos los procesadores.

Aquí está el conjunto de funciones extractoras. El primer argumento de cada una es del mismo estilo de lvalue utilizado en el lado izquierdo de la operación de acumulación. Las funciones extractoras @count(v), @sum(v), @min(v), @max(v), @avg(v), @variance(v[, b]) calculan el número/total/mínimo/máximo/promedio/varianza de todos los valores acumulados. Los valores resultantes son todos enteros simples. Los arrays que contienen agregados pueden ordenarse e iterarse. Ver la construcción foreach anterior.

La varianza utiliza el algoritmo en línea de Welford. Los cálculos se basan en aritmética entera y, por lo tanto, pueden sufrir de baja precisión y desbordamiento. Para mejorar esto, @variance(v[, b]) acepta un parámetro opcional b, el desplazamiento de bits, que varía de 0 (predeterminado) a 62, para escalado interno. Solo se puede usar un valor de desplazamiento de bits con una variable global dada. Un valor de desplazamiento de bits más grande aumenta la precisión, pero aumenta la probabilidad de desbordamiento.

$ stap -e \
> 'global x probe oneshot { for(i=1;i<=5;i++) x<<<i println(@variance(x)) }'
12
$ stap -e \
> 'global x probe oneshot { for(i=1;i<=5;i++) x<<<i println(@variance(x,1)) }'
2
$ python3 -c 'import statistics; print(statistics
.variance([1, 2, 3, 4, 5]))' 2.5 $

Puede ocurrir un desbordamiento (por la multiplicación interna de números grandes) y podría resultar en una varianza negativa. Considere normalizar sus datos de entrada. Sumar o restar un valor fijo a todas las entradas de la varianza preserva la varianza original. Dividir las entradas de la varianza por un valor fijo reduce la varianza original por ese valor al cuadrado.

También hay histogramas disponibles, pero son más complicados porque tienen un valor de vector en lugar de escalar. @hist_linear(v,start,stop,interval) representa un histograma lineal desde "start" hasta "stop" (inclusive) en incrementos de "interval". El intervalo debe ser positivo. De manera similar, @hist_log(v) representa un histograma logarítmico de base 2. Imprimir un histograma con la familia de funciones print renderiza un objeto de histograma como un gráfico de barras tabular de "arte ASCII".

probe timer.profile {
  x[1] <<< pid()
  x[2] <<< uid()
  y <<< tid()
}
global x // un array que contiene agregados
global y // un escalar
probe end {
  foreach ([i] in x @count+) {
     printf ("x[%d]: avg %d = sum %d / count %d\n",
             i, @avg(x[i]), @sum(x[i]), @count(x[i]))
     println (@hist_log(x[i]))
  }
  println ("y:")
  println (@hist_log(y))
}

Los recuentos de cada cubo del histograma se pueden acceder individualmente a través del operador [index]. Cada cubo se direcciona desde 1 hasta N (para cada cubo natural). Además, el cubo #0 cuenta todas las muestras por debajo del valor de inicio, y el cubo #N+1 cuenta todas las muestras por encima del valor de fin. Los cubos del histograma (incluidos los dos cubos fuera de rango) también se pueden iterar con foreach.

global x
probe oneshot {
  x <<< -100
  x <<< 1
  x <<< 2
  x <<< 3
  x <<< 100
  foreach (bucket in @hist_linear(x,1,3,1))
    // se espera   1 cubo fuera de rango bajo
    //             3 cubos de carga útil
    //             1 cubo fuera de rango alto
    printf("bucket %d count %d\n",
           bucket, @hist_linear(x,1,3,1)[bucket])
}

CONVERSIÓN DE TIPOS

Una vez que un puntero (ver la sección VARIABLES DE CONTEXTO de stapprobes(3stap)) se ha guardado en una variable entera del script, el traductor intenta mantener la información de tipo necesaria para acceder a los miembros de ese puntero.

El traductor intenta rastrear el tipo DWARF asociado con las variables del script asignadas a partir de direcciones de variables de contexto, operadores @cast o @var. Dependiendo de la complejidad del código del script, esta asociación puede pasar a variables relacionadas, de modo que los operadores -> y [] se puedan usar en ellas, al igual que en la variable de contexto original. Por ejemplo:

foo = $param->foo; printf("x:%d y:%d\n", foo->x, foo->y)
printf("mi valor es %d\n", ($type == 42 ? $foo : $bar)->value)
printf("mi pid padre es %d\n", task_parent(task_current())->tgid)

Sin embargo, si esta heurística de asociación no funciona para un script, el uso del operador @cast() le indica al traductor cómo interpretar el número como un puntero tipado.

@cast(p, "nombre_tipo"[, "modulo"])->miembro

Esto interpretará p como un puntero a una estructura/unión llamada nombre_tipo y desreferenciará el valor del miembro. Se pueden agregar más expresiones ->subcampo para desreferenciar más niveles. Tenga en cuenta que para la desreferenciación directa de un puntero, se debe usar {kernel,user}_{char,int,...}($p). (Consulte stapfuncs(5) para más detalles.) NOTA: se utiliza el mismo operador de desreferenciación -> para referirse tanto a la contención directa como a la indirección de puntero. Systemtap determina automáticamente cuál. El módulo opcional le dice al traductor dónde buscar información sobre ese tipo. Se pueden especificar múltiples módulos como una lista separada por :. Si no se especifica el módulo, por defecto será el módulo del sondeo para sondeos DWARF, o "kernel" para funciones y todos los demás tipos de sondeos.

Anteriormente, hasta la versión 4.2 de systemtap, se infería "kernel" si no se especificaba. Use --compatible=4.2 para activar este valor predeterminado.

El traductor puede crear su propio módulo con información de tipo a partir de una cabecera encerrada entre corchetes angulares, en caso de que la información de depuración normal no esté disponible. Para las cabeceras del kernel, prefíjelas con "kernel" para usar el sistema de compilación apropiado. Todas las demás cabeceras se compilan con parámetros predeterminados de GCC en un módulo de usuario. Se pueden especificar múltiples cabeceras en secuencia para resolver una codependencia.

A partir de la versión 5.4 de systemtap, se intenta usar la cabecera del kernel "<vmlinux.h>" antes que cualquier cabecera o módulo del kernel especificado, lo que puede hacer innecesario listar nombres explícitos de módulos o archivos de cabecera para estructuras de datos del kernel.

@cast(tv, "timeval", "<sys/time.h>")->tv_sec
@cast(task, "task_struct", "kernel<linux/sched.h>")->tgid
@cast(task, "task_struct",
      "kernel<linux/sched.h><linux/fs_struct.h>")->fs->umask

Los valores adquiridos por @cast pueden imprimirse de forma bonita mediante los operadores sufijos $ y $$, de la misma manera que se describe en la sección VARIABLES DE CONTEXTO de la página del manual de stapprobes(3stap).

Cuando está en modo experto (guru mode), el traductor también permitirá a los scripts asignar nuevos valores a los miembros de punteros con tipo.

La conversión de tipos también es útil en el caso de miembros void* cuyo tipo puede determinarse en tiempo de ejecución.

probe foo {
  if ($var->type == 1) {
    value = @cast($var->data, "type1")->bar
  } else {
    value = @cast($var->data, "type2")->baz
  }
  print(value)
}

C EMBEBIDO

Cuando está en modo experto, el traductor acepta código C embebido en el nivel superior del script. Dicho código se encierra entre los marcadores %{ y %}, y se transcribe textualmente, sin análisis, en alguna secuencia, al nivel superior del código C generado. En el nivel más externo, esto puede ser útil para agregar instrucciones #include y cualquier definición auxiliar para su uso por otro código embebido.

Otro lugar donde se permite el código embebido es como cuerpo de función. En este caso, el cuerpo del lenguaje de script se reemplaza por completo por un fragmento de código C encerrado nuevamente entre los marcadores %{ y %}. Este código C puede hacer cualquier cosa razonable y segura. Existe una serie de restricciones de seguridad, no documentadas pero complejas, sobre atomicidad, concurrencia, consumo de recursos y límites de tiempo de ejecución, por lo que esta es una técnica avanzada.

Las ubicaciones de memoria reservadas para los valores de entrada y salida se ponen a disposición mediante las macros STAP_ARG_* y STAP_RETVALUE. Los errores se pueden señalar con STAP_ERROR. La salida se puede escribir con STAP_PRINTF. La función puede salir temprano con STAP_RETURN. Aquí hay algunos ejemplos:

function integer_ops (val) %{
  STAP_PRINTF("%d\n", STAP_ARG_val);
  STAP_RETVALUE = STAP_ARG_val + 1;
  if (STAP_RETVALUE == 4)
      STAP_ERROR("adivinanza incorrecta: %d", (int) STAP_RETVALUE);
  if (STAP_RETVALUE == 3)
      STAP_RETURN(0);
  STAP_RETVALUE ++;
%}
function string_ops (val) %{
  strlcpy (STAP_RETVALUE, STAP_ARG_val, MAXSTRINGLEN);
  strlcat (STAP_RETVALUE, "one", MAXSTRINGLEN);
  if (strcmp (STAP_RETVALUE, "three-two-one"))
      STAP_RETURN("el parámetro debe ser three-two-");
%}
function no_ops () %{
    STAP_RETURN(); /* función inferida sin valor de retorno */
%}

El traductor tiene que inferir los tipos de argumento y valor de retorno de la función a partir de los sitios de llamada para que esto funcione. El usuario debe examinar el código C generado para funciones ordinarias del lenguaje de script para escribir funciones C embebidas compatibles.

El último lugar donde se permite el código embebido es como valor de rvalue de una expresión. En este caso, el código C encerrado entre los marcadores %{ y %} se interpreta como un valor de expresión ordinario. Se asume que es un número normal con signo de 64 bits, a menos que se incluya el marcador /* string */, en cuyo caso se trata como una cadena.

function add_one (val) {
  return val + %{ 1 %}
}
function add_string_two (val) {
  return val . %{ /* string */ "two" %}
}
@define SOME_STAP_MACRO %( %{ SOME_C_MACRO %} %)
probe begin {
      printf("SOME_C_MACRO tiene el valor: %d\n", @SOME_STAP_MACRO);
}

El código C embebido puede contener marcadores para afirmar propiedades de optimización y seguridad.

/* pure */
significa que el código C no tiene efectos secundarios y puede ser omitido completamente si su valor no es utilizado por el código del script.
/* stable */
significa que el código C siempre tiene el mismo valor (en cualquier invocación dada de un manejador de sondeo), por lo que las llamadas repetidas pueden ser reemplazadas automáticamente por valores memorizados. Dichas funciones no deben tomar parámetros y también deben ser pure.
/* unprivileged */
significa que el código C es tan seguro que incluso los usuarios no privilegiados tienen permitido usarlo.
/* myproc-unprivileged */
significa que el código C es tan seguro que incluso los usuarios no privilegiados tienen permitido usarlo, siempre que el objetivo del sondeo actual esté dentro del propio proceso del usuario.
/* guru */
significa que el código C es tan inseguro que un usuario de systemtap debe especificar -g (modo experto) para usarlo. (Los tapsets están permitidos y se presume que los llaman de forma segura).
/* unmangled */
en una función C embebida, significa que la sintaxis de acceso a argumentos heredada (pre-1.8) debe estar disponible dentro de la función. Por lo tanto, además de STAP_ARG_foo y STAP_RETVALUE, se pueden usar THIS->foo y THIS->__retvalue respectivamente dentro de la función. Esto es útil para migrar rápidamente código escrito para SystemTap versiones 1.7 y anteriores.
/* pragma:suffix */
emite el archivo de nivel que contiene el código C cerca del final del archivo fuente del módulo de kernel resultante.
/* unmodified-fnargs */
en una función C embebida, significa que los argumentos de la función no se modifican dentro del cuerpo de la función.
/* string */
solo en expresiones C embebidas, significa que la expresión tiene el tipo const char * y debe tratarse como una cadena, en lugar del número entero largo predeterminado.

Las variables globales de nivel de script se pueden acceder en funciones y bloques C embebidos. Para leer o escribir la variable global var, el marcador /* pragma:read:var */ o /* pragma:write:var */ debe colocarse primero en la función o bloque C embebido. Esto proporciona las macros STAP_GLOBAL_GET_* y STAP_GLOBAL_SET_*

VARIABLES GLOBALES

Las variables globales de script son variables que se declaran en el nivel de script y se pueden acceder en las funciones C incrustadas. Todas las variables globales de script se inicializan a cero. Las variables globales de script se pueden declarar como escalares o como matrices multidimensionales. El acceso a los elementos de matriz se realiza utilizando el índice de la matriz, que se pasa a la función C incrustada como argumento. Las variables globales de script se pueden leer y escribir en funciones C incrustadas y expresiones. Las variables solo se pueden declarar en el nivel de script para permitir la inferencia de tipos.

Las siguientes pragmas de directiva de preprocesador C se utilizan para anotar el acceso a las variables globales de script:

/* #pragma:read:identifier */
Este pragma se utiliza para indicar que la variable global identifier se lee en la función C incrustada o en la expresión. Esto es necesario para que el compilador sepa que el valor de la variable debe ser recuperado del almacenamiento global.
/* #pragma:write:identifier */
Este pragma se utiliza para indicar que la variable global identifier se escribe en la función C incrustada o en la expresión. Esto es necesario para que el compilador sepa que el valor de la variable debe ser escrito en el almacenamiento global.

Por ejemplo:

global var
global var2[100]
function increment() %{
    /* pragma:read:var */ /* pragma:write:var */
    /* pragma:read:var2 */ /* pragma:write:var2 */
    STAP_GLOBAL_SET_var(STAP_GLOBAL_GET_var()+1); //var++
    STAP_GLOBAL_SET_var2(1, 1, STAP_GLOBAL_GET_var2(1, 1)+1); //var2[1,1]++
%}

Las variables pueden leerse y establecerse tanto en funciones C incrustadas como en expresiones. Las cadenas devueltas desde el código C incrustado se decaen a punteros. Las variables también deben asignarse a nivel de script para permitir la inferencia de tipos. La asignación de mapas no devuelve el valor escrito, por lo que el encadenamiento no funciona.

DESREFERENCIADO

Los enteros pueden ser desreferenciados de punteros guardados como variables enteras de script utilizando los operadores @kderef() o @uderef(). @kderef() se utiliza para direcciones del espacio del kernel y @uderef() se utiliza para direcciones del espacio del usuario.

@kderef(SIZE, addr)
@uderef(SIZE, addr)

Esto interpretará addr como una dirección del kernel/usuario y leerá SIZE bytes comenzando en esa dirección. SIZE debe ser 1, 2, 4 u 8 bytes.

REGISTROS

El valor almacenado dentro de un registro se puede acceder utilizando los operadores @kregister() o @uregister(). @kregister() se utiliza para registros del espacio del kernel y @uregister() se utiliza para registros del espacio del usuario. El registro de interés se especifica utilizando su número DWARF.

@kregister(0)
@uregister(5)

PROCESAMIENTO

El traductor comienza la pasada 1 analizando el script de entrada dado, y todos los scripts (archivos llamados *.stp) encontrados en un directorio de tapset. Los directorios listados con -I se procesan en secuencia, cada uno procesado en modo "guru". Para cada directorio, también se buscan varios subdirectorios. Estos subdirectorios se derivan de la versión del kernel seleccionada (la opción -R), para permitir que scripts más específicos de la versión del kernel anulen a otros menos específicos. Por ejemplo, para una versión del kernel 2.6.12-23.FC3, se buscarían los siguientes patrones, en secuencia: 2.6.12-23.FC3/*.stp, 2.6.12/*.stp, 2.6/*.stp y, finalmente, *.stp. Detener el traductor después de la pasada 1 hace que imprima los árboles de análisis sintáctico.

En la pasada 2, el traductor analiza el script de entrada para resolver símbolos y tipos. Las referencias a variables, funciones y alias de sondeo que no se resuelven internamente se satisfacen buscando en los archivos de script de tapset analizados. Si algún archivo de script de tapset se selecciona porque define un símbolo no resuelto, entonces la totalidad de ese archivo se agrega a la cola de resolución del traductor. Este proceso se repite hasta que se resuelven todos los símbolos y se selecciona un subconjunto de archivos de script de tapset.

A continuación, se validan todas las descripciones de puntos de sondeo frente a la amplia variedad que admite el traductor. Los puntos de sondeo que se refieren a ubicaciones de código ("puntos de sondeo síncronos") requieren que la información de depuración del kernel apropiada esté instalada. En los manejadores de sondeo asociados, se encuentran variables del lado del objetivo (cuyos nombres comienzan con "$") y se decodifican sus ubicaciones en tiempo de ejecución.

A continuación, se analizan todos los sondeos y funciones en busca de oportunidades de optimización, para eliminar variables, expresiones y funciones que no tengan un valor útil ni efectos secundarios. Se supone que las funciones C incrustadas tienen efectos secundarios, a menos que incluyan la cadena mágica /* pure */. Dado que esta optimización puede ocultar errores de código latentes, como discrepancias de tipos o variables de $context inválidas, a veces puede ser útil deshabilitar las optimizaciones con la opción -u.

Finalmente, se infieren todos los tipos de variables, funciones, parámetros, matrices e índices a partir del contexto (literales y operadores). Detener el traductor después de la pasada 2 hace que enumere todos los sondeos, funciones y variables, junto con todos los tipos inferidos. Cualquier tipo inconsistente o no resuelto provoca un error.

En la pasada 3, el traductor escribe código C que representa las acciones de todos los archivos de script seleccionados y crea un Makefile para compilarlo en un objeto del kernel. Estos archivos se colocan en un directorio temporal. Detener el traductor en este punto hace que imprima el contenido del archivo C.

En la pasada 4, el traductor invoca el sistema de compilación del kernel de Linux para crear el archivo objeto del kernel real. Esto implica ejecutar make en el directorio temporal y requiere un sistema de compilación de módulos del kernel (encabezados, configuración y Makefiles) instalado en la ubicación habitual /lib/modules/VERSION/build. Detener el traductor después de la pasada 4 es la última oportunidad antes de ejecutar el objeto del kernel. Esto puede ser útil si desea archivar el archivo.

En la pasada 5, el traductor invoca el programa auxiliar staprun de systemtap para el objeto del kernel dado. Este programa se encarga de cargar el módulo y luego se comunica con él, copiando los datos de rastreo del kernel a archivos temporales, hasta que el usuario envía una señal de interrupción. Cualquier error en tiempo de ejecución encontrado por los manejadores de sondeo, como quedarse sin memoria, división por cero, exceder los límites de anidamiento o tiempo de ejecución, da como resultado una indicación de error suave. Los errores suaves que exceden un bloque de MAXERRORS bloquean todos los sondeos subsiguientes (excepto los sondeos de manejo de errores) y terminan la sesión. Finalmente, staprun descarga el módulo y realiza la limpieza.

TERMINACIÓN ANORMAL

Se debe evitar matar el proceso stap de forma forzada, por ejemplo, con SIGKILL, porque el proceso stapio (un proceso hijo del proceso stap) y el módulo cargado pueden quedar en ejecución en el sistema. Si esto sucede, envíe SIGTERM o SIGINT a cualquier proceso stapio restante y luego use rmmod para descargar el módulo systemtap.

CACHÉ

El traductor de systemtap almacena en caché la salida de la pasada 3 (el código C generado) y la salida de la pasada 4 (el módulo del kernel compilado) si la pasada 4 se completa correctamente. Esta salida en caché se reutiliza si el mismo script se traduce nuevamente asumiendo que existen las mismas condiciones (misma versión del kernel, misma versión de systemtap, etc.). Los archivos en caché se almacenan en el directorio $SYSTEMTAP_DIR/cache. La caché puede limitarse colocando el archivo cache_mb_limit en el directorio de caché (mostrado anteriormente) que contenga solo un entero ASCII que represente cuántos MiB no debe exceder la caché. En ausencia de este archivo, se creará uno predeterminado con el límite establecido en 256MiB. Este es un límite "suave" en el sentido de que la caché se limpiará después de agregar una nueva entrada si se excede el intervalo de limpieza de caché, por lo que el tamaño total de la caché puede exceder temporalmente este límite. Este intervalo se puede especificar colocando el archivo cache_clean_interval_s en el directorio de caché (mostrado anteriormente) que contenga solo un entero ASCII que represente el intervalo en segundos. En ausencia de este archivo, se creará uno predeterminado con el intervalo establecido en 300 s.

SEGURIDAD Y PROTECCIÓN

Systemtap puede utilizarse como una potente herramienta administrativa. Puede exponer estructuras de datos internas del kernel y potencialmente información privada del usuario. (En el modo de tiempo de ejecución de dyninst, este no es el caso, consulte la sección TIEMPOS DE EJECUCIÓN ALTERNATIVOS a continuación).

El traductor impone muchas restricciones de seguridad durante la compilación y más durante el tiempo de ejecución. Su objetivo es garantizar que ninguna rutina de manejo pueda ejecutarse durante mucho tiempo, asignar memoria ilimitada, realizar operaciones inseguras o interferir involuntariamente con el sistema. El uso de variables globales de script se bloquea automáticamente de lectura/escritura según corresponda, para proteger contra la manipulación por parte de manejadores de sondeo concurrentes. Los bloqueos se toman para ejecutar la porción de manipulación de variables globales de los manejadores de sondeo de forma atómica (los bloqueos se toman todo o nada). Los interbloqueos se detectan con tiempos de espera. Utilice la bandera -t para recibir informes de contención excesiva de bloqueos. Por lo tanto, experimentar con scripts es generalmente **seguro**. La opción -g del modo guru permite a los administradores omitir la mayoría de las medidas de seguridad, lo que permite operaciones invasivas o que cambian el estado, código C incrustado y aumenta el riesgo de problemas. Por defecto, la prevención de sobrecarga está activada para todos los módulos. Si desea deshabilitar el procesamiento de sobrecarga, utilice la opción --suppress-time-limits.

Los errores que se detectan en tiempo de ejecución normalmente dan como resultado un apagado limpio del script y un mensaje de error de pasada 5. La opción --suppress-handler-errors permite que los scripts toleren errores suaves sin apagarse.

Para el tiempo de ejecución normal del módulo del kernel de Linux, para ejecutar los objetos del kernel que systemtap compila, un usuario debe ser uno de los siguientes:

  • un miembro de los grupos stapdev y stapusr;

  • El módulo se compiló utilizando las opciones --privilege=stapsys o --privilege=stapusr.

SECUREBOOT

Si el sistema actual tiene SecureBoot activado en el firmware UEFI, todos los módulos del kernel deben estar firmados. (Algunos kernels pueden permitir desactivar SecureBoot mucho después de arrancar con una secuencia de teclas como SysRq-X, haciendo innecesario firmar módulos). Hay dos formas de firmar un módulo de systemtap. El servidor de compilación de systemtap puede firmar módulos con una MOK (Machine Owner Key) que comparte con un sistema cliente. Por ejemplo:

stap --use-server=HOSTNAME:PORT -e 'SCRIPT'
# Si no hay una clave mok en común con la lista de claves mok de systemtap del servidor
# y la base de datos mok del cliente, entonces stap dirige al usuario a invocar:
sudo mokutil --import signing_key.x509
# luego, después de reiniciar el sistema:
stap --use-server=HOSTNAME:PORT -e 'SCRIPT'
# utilizará el servidor para construir y firmar el módulo, y el módulo se ejecutará
# en el cliente

Otra forma de firmar módulos es usar la opción stap --sign-module, que utiliza una MOK en el sistema cliente sin usar un servidor. Por ejemplo:

stap --sign-module -e 'SCRIPT'
# Si no hay una clave mok de systemtap en la base de datos mok del sistema
# entonces stap dirige al usuario a invocar:
sudo mokutil --import /home/USUARIO/.systemtap/ssl/server/moks/FINGERPRINT/signing_key.x509
# luego, después de reiniciar el sistema:
stap --sign-module -e 'SCRIPT'
# firmará y ejecutará el módulo

Consulte la siguiente página wiki para obtener más detalles:

https://sourceware.org/systemtap/wiki/SecureBoot

Algunos kernels no permiten que systemtap adivine si la firma de módulos está en vigor. En dichas máquinas, establezca la variable de entorno SYSTEMTAP_SIGN a cualquier valor mientras ejecuta stap.

LÍMITES DE RECURSOS

Muchos límites de uso de recursos se establecen mediante macros en el código C generado. Estos pueden ser anulados con flags de -D. Una selección de estos es la siguiente:

MAXNESTING
Número máximo de llamadas anidadas a funciones. El valor predeterminado se determina mediante el análisis del script, con 10 ranuras adicionales para scripts recursivos.
MAXSTRINGLEN
Longitud máxima de las cadenas, por defecto 128.
MAXTRYLOCK
Número máximo de iteraciones para esperar bloqueos en variables globales antes de declarar un posible interbloqueo y omitir la sonda, por defecto 1000.
MAXACTION
Número máximo de sentencias a ejecutar durante cada ejecución de sonda (con interrupciones deshabilitadas), por defecto 1000. Tenga en cuenta que para manejadores de sonda de ejecución directa sin bucles ni recursión, debido a la optimización, este parámetro puede interpretarse de forma demasiado conservadora.
MAXACTION_INTERRUPTIBLE
Número máximo de sentencias a ejecutar durante cada ejecución de sonda que se ejecuta con interrupciones habilitadas (como las sondas begin/end), por defecto (MAXACTION * 10).
MAXBACKTRACE
Número máximo de marcos de pila que serán procesados por el desapilador en tiempo de ejecución de stap, producidos por las funciones de backtrace en los tapsets [u]context-unwind.stp, por defecto 20.
MAXMAPENTRIES
Número máximo de filas en cualquier array global, por defecto 2048. Los arrays individuales pueden declararse con un límite mayor o menor en su lugar: 
global big[10000],little[5]

o denotados con % para que se envuelvan (reemplacen entradas antiguas) automáticamente, como en

global big%

o ambos.

MAPHASHBIAS
El número de potencias de dos a sumar o restar del tamaño natural de la tabla hash que soporta cada array asociativo global. El valor predeterminado es 0. Pruebe con números positivos pequeños para obtener un rendimiento adicional a costa de un mayor consumo de memoria, ya que esto debería reducir las colisiones de la tabla hash. Pruebe con números negativos pequeños para el compromiso opuesto.
MAXERRORS
Número máximo de errores suaves antes de que se active una salida, por defecto 0, lo que significa que el primer error saldrá del script. Tenga en cuenta que con la opción --suppress-handler-errors, este límite no se aplica.
MAXSKIPPED
Número máximo de sondas omitidas antes de que se active una salida, por defecto 100. Ejecutar systemtap en modo -t (temporización) proporciona más detalles sobre las sondas omitidas. Con la configuración predeterminada -DINTERRUPTIBLE=1, las sondas omitidas debido a la reentrada no se acumulan contra este límite. Tenga en cuenta que con la opción --suppress-handler-errors, este límite no se aplica.
MINSTACKSPACE
Número mínimo de bytes libres en la pila del kernel requeridos para ejecutar un manejador de sonda, por defecto 1024. Este número debe ser lo suficientemente grande para las necesidades del propio manejador de sonda, más un margen de seguridad.
MAXUPROBES
Número máximo de sondas de espacio de usuario (uprobes) activas simultáneamente, por defecto algo mayor que el número de puntos de sonda de espacio de usuario nombrados en el script. Este grupo necesita ser potencialmente grande porque se asignan objetos uprobe individuales (aproximadamente 64 bytes cada uno) para cada proceso y cada sonda coincidente a nivel de script.
STP_MAXMEMORY
Cantidad máxima de memoria (en kilobytes) que debe utilizar el módulo systemtap, por defecto ilimitada. El tamaño de la memoria incluye el tamaño del módulo en sí, más las asignaciones adicionales. Esto solo rastrea las asignaciones directas por el tiempo de ejecución de systemtap. Esto no rastrea las asignaciones indirectas (como las realizadas por la interna de kprobes/uprobes/etc.).
STP_OVERLOAD_THRESHOLD, STP_OVERLOAD_INTERVAL
Número máximo de ciclos de máquina gastados en sondas en cualquier cpu por intervalo dado, antes de que se declare una condición de sobrecarga y el script se cierre. Los valores predeterminados son 500 millones y 1 mil millones, para limitar el consumo de CPU de los scripts de stap alrededor del 50%.
STP_PROCFS_BUFSIZE
Tamaño de los búferes de lectura de sondas procfs (en bytes). Por defecto es MAXSTRINGLEN. Este valor puede ser anulado por archivo procfs utilizando el parámetro .maxsize(MAXSIZE) de la sonda de lectura procfs.

Con scripts que contienen sondas en cualquier ruta de interrupción, es posible que esas interrupciones ocurran en medio de otro manejador de sonda. La sonda en el manejador de interrupción se omitiría en este caso para evitar la reentrada. Para solucionar este problema, ejecute stap con la opción -DINTERRUPTIBLE=0 para enmascarar las interrupciones en todo el manejador de sonda. Esto añade una sobrecarga adicional a las sondas, pero puede prevenir la reentrada en casos problemáticos comunes. Sin embargo, las sondas en los manejadores NMI y en la ruta de llamada del tiempo de ejecución de stap aún pueden omitirse debido a la reentrada.

En caso de que algo salga mal con stap o staprun después de que una sonda ya haya comenzado a ejecutarse, puede matar de forma segura ambos procesos de usuario y eliminar el módulo del kernel de sonda activo con rmmod. Es posible que se pierdan mensajes de rastreo pendientes.

USUARIOS NO PRIVILEGIADOS

Systemtap expone estructuras de datos internas del kernel y potencialmente información privada del usuario. Debido a esto, el uso de las capacidades completas de systemtap está restringido a root y a los usuarios que son miembros de los grupos stapdev y stapusr.

Sin embargo, un conjunto restringido de las características de systemtap puede estar disponible para usuarios de confianza no privilegiados. Estos usuarios son miembros solo del grupo stapusr, o miembros de los grupos stapusr y stapsys. Estos usuarios pueden cargar módulos de systemtap que han sido compilados y certificados por un servidor de compilación de systemtap de confianza. Consulte las descripciones de las opciones --privilege y --use-server. Consulte README.unprivileged en el código fuente de systemtap para obtener información sobre la configuración de un servidor de compilación de confianza.

Las restricciones impuestas cuando se especifica --privilege=stapsys están diseñadas para evitar que los usuarios no privilegiados:

•
dañen el sistema de forma maliciosa.

Las restricciones impuestas cuando se especifica --privilege=stapusr están diseñadas para evitar que los usuarios no privilegiados:

  • dañen el sistema de forma maliciosa.

RESTRICCIONES DE TAPSET

En general, las funciones de tapset solo están disponibles para los miembros del grupo stapusr cuando no recopilan información a la que un programa ordinario que se ejecuta con los privilegios de ese usuario tendría denegado el acceso.

Hay dos categorías de funciones de tapset no privilegiadas. La primera categoría consta de funciones de utilidad que están disponibles incondicionalmente para todos los usuarios; estas incluyen cosas como:

cpu:long ()
exit ()
str_replace:string (prnt_str:string, srch_str:string, rplc_str:string)

La segunda categoría consta de las llamadas funciones myproc-unprivileged que solo pueden recopilar información dentro de sus propios procesos. Los scripts que deseen utilizar estas funciones deben probar el resultado de la función de tapset is_myproc y solo llamar a estas funciones si el resultado es 1. El script saldrá inmediatamente si alguna de estas funciones es llamada por un usuario no privilegiado dentro de una sonda dentro de un proceso que no es propiedad de ese usuario. Ejemplos de funciones myproc-unprivileged incluyen:

print_usyms (stk:string)
user_int:long (addr:long)
usymname:string (addr:long)

Se activa un error de compilación cuando cualquier función que no esté en ninguna de las categorías anteriores es utilizada por miembros solo del grupo stapusr.

Ninguna otra función de tapset incorporada puede ser utilizada por miembros solo del grupo stapusr.

TIEMPOS DE EJECUCIÓN ALTERNATIVOS

Como se describió anteriormente, el modo de tiempo de ejecución predeterminado de systemtap implica la compilación y carga de módulos del kernel, con las diversas compensaciones de seguridad presentadas. Systemtap ahora incluye dos nuevos backends prototipo: --runtime=dyninst y --runtime=bpf.

--runtime=dyninst utiliza Dyninst para instrumentar los propios procesos de un usuario en tiempo de ejecución. Este backend no utiliza módulos del kernel y no requiere privilegios de root, pero está restringido con respecto a los tipos de sondas y otras construcciones que un script puede usar. El tiempo de ejecución dyninst opera en modo de adjunción de destino, por lo que requiere un proceso -c COMMAND o -x PID. Por ejemplo:

stap --runtime=dyninst -c 'stap -V' \
     -e 'probe process.function("main")
         { println("hi from dyninst!") }'

Puede ser necesario deshabilitar una verificación conflictiva de selinux con

# setsebool allow_execstack 1

--runtime=bpf compila el script del usuario en programas extendidos de Berkeley Packet Filter (eBPF) en lugar de un módulo del kernel. Los programas eBPF son verificados por el kernel para su seguridad y son ejecutados por una máquina virtual dentro del kernel. Este tiempo de ejecución se encuentra en una etapa temprana de desarrollo y actualmente carece de soporte para una serie de características disponibles en el tiempo de ejecución predeterminado. Consulte la página del manual stapbpf(8) para obtener más información.

ESTADO DE SALIDA

El traductor de systemtap generalmente regresa con un código de éxito de 0 si el script solicitado fue procesado y ejecutado exitosamente a través del pase solicitado. De lo contrario, se pueden imprimir errores en stderr y se devuelve un código de fallo. Utilice -v o -vp N para aumentar la verbosidad (global o por pase) para identificar la fuente del problema.

En el modo de listado (-l y -L), los mensajes de error normalmente se suprimen. Se devuelve un código de éxito de 0 si se encontró al menos una sonda coincidente.

Un script que se ejecuta en el pase 5 y que se interrumpe con ^C / SIGINT se considera exitoso.

OBSOLESCENCIA

Con el tiempo, algunas características del lenguaje de script y la biblioteca de tapset pueden experimentar cambios incompatibles, de modo que un script escrito para una versión antigua de systemtap puede ya no ejecutarse. En estos casos, puede ser útil ejecutar systemtap con la bandera --compatible VERSION, especificando la última versión que funcionó correctamente. Ejecutar systemtap con la bandera --check-version mostrará una advertencia si se han analizado elementos potencialmente incompatibles. Los detalles históricos de la obsolescencia se pueden encontrar en el archivo NEWS.

El propósito de la instalación de obsolescencia es mejorar la experiencia de los scripts escritos para versiones más nuevas de systemtap (al agregar mejores alternativas y eliminar alternativas antiguas conflictivas o confusas), al mismo tiempo que permite que los scripts escritos para versiones anteriores de systemtap continúen ejecutándose. La obsolescencia está, por lo tanto, destinada a ser un servicio a los usuarios (y una inconveniencia para los desarrolladores de systemtap), en lugar de al revés.

Tenga en cuenta que los identificadores que comienzan con guion bajo en el tapset a veces experimentan cambios que son difíciles de preservar para la compatibilidad, incluso con los mecanismos de obsolescencia. Evite depender de ellos en sus scripts; en su lugar, propóngalos para que se promuevan a un estado sin guion bajo.
