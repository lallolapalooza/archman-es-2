NOMBRE

stapprobes - puntos de sondeo de systemtap

DESCRIPCIÓN

Las siguientes secciones enumeran la variedad de puntos de sondeo soportados por el traductor de systemtap, y algunos de los alias adicionales definidos por los scripts de tapset estándar. Muchos están documentados individualmente en la sección manual de 3stap, con el prefijo probe::.

SINTAXIS

probe PUNTO_SONDEO [, PUNTO_SONDEO] { [SENTENCIA ...] }

Una declaración de sondeo puede listar múltiples puntos de sondeo separados por comas para adjuntar un manejador a todos los eventos nombrados. Normalmente, las sentencias del manejador se ejecutan siempre que ocurra cualquiera de los eventos. Dependiendo del tipo de punto de sondeo, las sentencias del manejador pueden referirse a variables de contexto (denotadas con un prefijo de signo de dólar como $foo) para leer o escribir estado. Esto puede incluir parámetros de función para sondeos de funciones, o variables locales para sondeos de sentencias.

La sintaxis de un único punto de sondeo es una secuencia general de símbolos punteados. Esto permite un desglose del espacio de nombres de eventos en partes, algo similar a lo que hace el Sistema de Nombres de Dominio en Internet. Cada identificador de componente puede ser parametrizado por una cadena o un literal numérico, con una sintaxis similar a una llamada a función. Un componente puede incluir un carácter de "*", para expandirse a un conjunto de puntos de sondeo coincidentes. También puede incluir "**" para coincidir con múltiples componentes secuenciales a la vez. Los alias de sondeo también se expanden a otros puntos de sondeo.

Los alias de sondeo se pueden dar por sí solos, o con un sufijo. El sufijo se adjunta al punto de sondeo subyacente al que se expande el alias. Por ejemplo,

syscall.read.return.maxactive(10)

se expande a

kernel.function("sys_read").return.maxactive(10)

con el componente maxactive(10) siendo reconocido como un sufijo.

Normalmente, cada punto de sondeo resultante de la expansión de comodines y alias debe resolverse en alguna instalación de instrumentación del sistema de bajo nivel (por ejemplo, una dirección kprobe, un marcador o una configuración de temporizador), de lo contrario, la fase de elaboración fallará.

Sin embargo, un punto de sondeo puede ir seguido de un carácter de "?", para indicar que es opcional, y que no debe haber ningún error si no se resuelve. La opcionalidad pasa hacia abajo a través de todos los niveles de expansión de alias/comodín. Alternativamente, un punto de sondeo puede ir seguido de un carácter de "!", para indicar que es tanto opcional como suficiente. (Piense vagamente en el operador cut de Prolog). Si se resuelve, entonces ningún otro punto de sondeo en la misma lista separada por comas se resolverá. Por lo tanto, la marca de suficiencia "!" solo tiene sentido en una lista de alternativas de puntos de sondeo.

Adicionalmente, un punto de sondeo puede ir seguido de una sentencia "if (expr)", para habilitar/deshabilitar el punto de sondeo dinámicamente. Con la sentencia "if", si la "expr" es falsa cuando se alcanza el punto de sondeo, se omite todo el cuerpo del sondeo, incluido el cuerpo del alias. La condición se apila a través de todos los niveles de expansión de alias/comodín. Por lo tanto, la condición final se convierte en el AND lógico de las condiciones de todos los alias/comodines expandidos. Las expresiones están necesariamente restringidas a variables globales.

Estos son todos puntos de sondeo **sintácticamente** válidos. (Generalmente son **semánticamente** inválidos, dependiendo del contenido de los tapsets y las versiones del software de kernel/usuario instaladas.)

kernel.function("foo").return
process("/bin/vi").statement(0x2222)
end
syscall.*
syscall.*.return.maxactive(10)
syscall.{open,close}
sys**open
kernel.function("no_such_function") ?
module("awol").function("no_such_function") !
signal.*? if (switch)
kprobe.function("foo")

Los sondeos se pueden clasificar ampliamente en "síncronos" y "asíncronos". Un evento "síncrono" se considera que ocurre cuando cualquier procesador ejecuta una instrucción que coincide con la especificación. Esto da a estos sondeos un punto de referencia (dirección de instrucción) del cual pueden estar disponibles más datos contextuales. Otras familias de puntos de sondeo se refieren a eventos "asíncronos" como temporizadores/contadores que se desbordan, donde no hay un punto de referencia fijo que esté relacionado. Cada especificación de punto de sondeo puede coincidir con múltiples ubicaciones (por ejemplo, usando comodines o alias), y todas ellas son entonces sondeadas. Una declaración de sondeo también puede contener varias especificaciones separadas por comas, todas las cuales son sondeadas.

La expansión de llaves es un mecanismo que permite generar una lista de puntos de sondeo. Es muy similar a la expansión del shell. Un componente puede ser rodeado por un par de llaves para indicar que la secuencia de uno o más subcomponentes separados por comas constituirá cada uno un nuevo punto de sondeo. Las llaves pueden anidarse arbitrariamente. El orden de los resultados expandidos se basa en el orden del producto.

Los indicadores de signo de interrogación (?), signo de exclamación (!) y las condiciones de punto de sondeo no pueden colocarse en ninguna expansión que esté antes del último componente.

El siguiente es un ejemplo de expansión de llaves.

syscall.{write,read}
# Se expande a
syscall.write, syscall.read
{kernel,module("nfs")}.function("nfs*")!
# Se expande a
kernel.function("nfs*")!, module("nfs").function("nfs*")!

INFORMACIÓN DE DEBUG DWARF

Resolver algunos puntos de sondeo requiere información de depuración DWARF o "símbolos de depuración" para el *programa específico* que se está instrumentando. Para otros, DWARF se sintetiza automáticamente sobre la marcha a partir de archivos de encabezado de código fuente. Para otros, no es necesario en absoluto. Dado que un script de systemtap puede usar cualquier mezcla de puntos de sondeo juntos, la unión de sus requisitos DWARF debe cumplirse en el ordenador donde ocurre la compilación del script. (Ver la opción --use-server y la página del manual de stap-server(8) para obtener información sobre la instalación de compilación remota, que permite que estos requisitos se cumplan en una máquina diferente.)

Los puntos de sonda de DWARF y PROCESOS solo están disponibles cuando se utiliza la opción -d al invocar systemtap.

BEGIN/END/ERROR

Los puntos de sonda *begin* y *end* son definidos por el traductor para referirse al momento de inicio y cierre de la sesión. Todos los manejadores de sondas "begin" se ejecutan, en alguna secuencia, durante el inicio de la sesión. Todas las variables globales habrán sido inicializadas antes de este punto. Todas las sondas "end" se ejecutan, en alguna secuencia, durante el cierre *normal* de una sesión, como después de una llamada a la función exit(), o una interrupción del usuario. En caso de un cierre provocado por un error, las sondas "end" no se ejecutan. No hay variables de destino disponibles en ninguno de los contextos.

Si el orden de ejecución entre las sondas "begin" o "end" es significativo, entonces se puede proporcionar un número de secuencia opcional:

begin(N)
end(N)

El número N puede ser positivo o negativo. Los manejadores de sondas se ejecutan en orden creciente, y el orden entre manejadores con el mismo número de secuencia no está especificado. Cuando "begin" o "end" se dan sin una secuencia, son efectivamente secuencia cero.

El punto de sonda *error* es similar al punto de sonda *end*, excepto que cada manejador de sonda se ejecuta cuando la sesión finaliza después de que han ocurrido errores. En tales casos, las sondas "end" se omiten, pero cada sonda "error" todavía se intenta ejecutar. Este tipo de sonda se puede usar para limpiar o emitir un "último suspiro". También puede ser parametrizado numéricamente para establecer una secuencia.

NUNCA

El punto de sonda never (nunca) es definido especialmente por el traductor para significar "nunca". Su manejador de sonda nunca se ejecuta, aunque sus sentencias se analizan para la corrección de símbolos/tipos como de costumbre. Este punto de sonda puede ser útil en conjunción con sondas opcionales.

SYSCALL y ND_SYSCALL

Los alias syscall.* y nd_syscall.* definen varios cientos de sondas, demasiadas para detallar aquí. Son de la forma general:

syscall.NOMBRE
nd_syscall.NOMBRE
syscall.NOMBRE.return
nd_syscall.NOMBRE.return

Generalmente, se define un par de sondas para cada llamada al sistema normal listada en la página del manual syscalls(2), una para la entrada y otra para la salida. Aquellas llamadas al sistema que nunca retornan no tienen una sonda .return correspondiente. La familia de sondas nd_* es aproximadamente la misma, excepto que utiliza mecanismos de búsqueda basados en **no DWARF**, lo que puede resultar en una menor calidad de los datos del contexto simbólico (parámetros) y puede omitir algunas llamadas al sistema. Puede que desee probarlas primero, en caso de que la información de depuración del kernel no esté inmediatamente disponible.

Cada alias de sonda proporciona una variedad de variables. Consultar el código fuente del tapset es la forma más fiable. Generalmente, cada variable listada en la página del manual estándar se pone a disposición como una variable a nivel de script, por lo que syscall.open expone filename, flags y mode. Además, un conjunto estándar de variables está disponible en la mayoría de los alias:

argstr
Una forma formateada de toda la lista de argumentos, sin paréntesis.
name
El nombre de la llamada al sistema.
retval
Para las sondas de retorno, el resultado numérico crudo de la llamada al sistema.
retstr
Para las sondas de retorno, una forma de cadena formateada del resultado de la llamada al sistema.

Como es habitual para los alias de sondas, todas estas variables se inicializan una vez a partir de las variables $context subyacentes, por lo que los cambios posteriores en las variables $context no se reflejan automáticamente. No todos los alias de sondas cumplen todas estas directrices generales. Por favor, informe cualquier caso problemático que encuentre como un error. Tenga en cuenta que en algunas combinaciones de arquitectura de kernel/espacio de usuario (por ejemplo, espacio de usuario de 32 bits en kernel de 64 bits), las variables $context subyacentes pueden necesitar extensión de signo/enmascaramiento explícito. Cuando esto es un problema, considere usar las variables proporcionadas por el tapset en lugar de las variables $context crudas.

Si la disponibilidad de información de depuración es un problema, puede intentar usar los alias de sonda syscall **no DWARF** en su lugar. Use el prefijo nd_syscall. en lugar de syscall. Las mismas variables de contexto están disponibles, en la medida de lo posible.

Las sondas nd_syscall en kernels que utilizan envolturas de syscall para pasar argumentos a través de pt_regs (actualmente 4.17+ en x86_64 y 4.19+ en aarch64) admiten la escritura de argumentos de syscall cuando el modo gurú está habilitado. Si un parámetro de sonda syscall se modifica en el cuerpo de la sonda, inmediatamente antes de que la sonda salga, el valor actual del parámetro se escribirá en pt_regs. Esto sobrescribe el valor anterior. Las sondas nd_syscall también incluyen dos parámetros para cada uno de los parámetros de cadena del syscall. Uno contiene una versión entre comillas de la cadena pasada al syscall. El otro contiene una versión sin comillas de la cadena que se pretende usar al modificar el parámetro. Si la sonda modifica la variable de cadena sin comillas, entonces, cuando la sonda está a punto de salir, el contenido de esta variable se escribirá en el búfer del espacio de usuario pasado al syscall. Es responsabilidad del usuario asegurarse de que este búfer sea lo suficientemente grande como para contener la cadena modificada y que esté ubicado en un segmento de memoria grabable.

TEMPORIZADORES

Hay dos tipos principales de sondas de temporizador: sondas de temporizador de "jiffies" y sondas de temporizador de intervalo de tiempo.

Los intervalos definidos por el temporizador estándar del kernel "jiffies" pueden usarse para activar manejadores de sondas asincrónicamente. El traductor soporta dos variantes de puntos de sonda:

timer.jiffies(N)
timer.jiffies(N).randomize(M)

El manejador de sonda se ejecuta cada N jiffies (una unidad de tiempo definida por el kernel, típicamente entre 1 y 60 ms). Si se proporciona el componente "randomize", se agrega un valor aleatorio distribuido linealmente en el rango [-M..+M] cada vez que se ejecuta el manejador. N está restringido a un rango razonable (1 a alrededor de un millón), y M está restringido a ser menor que N. No se proporcionan variables de destino en ninguno de los contextos. Es posible que tales sondas se ejecuten concurrentemente en una computadora multiprocesador.

Alternativamente, los intervalos se pueden especificar en unidades de tiempo. Hay dos variantes de puntos de sonda similares al temporizador de jiffies:

timer.ms(N)
timer.ms(N).randomize(M)

Aquí, N y M se especifican en milisegundos, pero las opciones completas para unidades son segundos (s/sec), milisegundos (ms/msec), microsegundos (us/usec), nanosegundos (ns/nsec) y hertz (hz). La aleatorización no se admite para temporizadores hertz.

La resolución real de los temporizadores depende del kernel de destino. Para kernels anteriores a 2.6.17, los temporizadores se limitan a la resolución de jiffies, por lo que los intervalos se redondean al intervalo de jiffies más cercano. Después de 2.6.17, la implementación utiliza hrtimers para una mayor precisión, aunque la resolución real dependerá de la arquitectura. En cualquier caso, si se proporciona el componente "randomize", el valor aleatorio se agregará al intervalo antes de que ocurra cualquier redondeo.

También hay disponibles temporizadores de perfil para proporcionar sondas que se ejecutan en todas las CPU a la velocidad del tick del sistema (CONFIG_HZ) o a una frecuencia dada (hz). En algunos kernels, esta es una instalación de un solo usuario concurrente o deshabilitada, lo que resulta en un error -16 (EBUSY) durante el registro de la sonda.

timer.profile.tick
timer.profile.freq.hz(N)

La información completa del contexto del proceso interrumpido está disponible, lo que hace que esta sonda sea adecuada para un generador de perfiles de muestreo basado en tiempo.

Se recomienda utilizar el punto de sonda tapset timer.profile en lugar de timer.profile.tick. Este punto de sonda se comporta de manera idéntica a timer.profile.tick cuando la funcionalidad subyacente está disponible, y recurre a usar perf.sw.cpu_clock en algunos kernels recientes que carecen de la instalación de temporizador de perfil correspondiente.

Los temporizadores de perfil con frecuencias especificadas solo son precisos hasta aproximadamente 100 hz. Puede que necesite proporcionar un valor mayor para lograr la velocidad deseada.

Tenga en cuenta que si una sonda de temporizador está configurada para dispararse a una velocidad muy alta y si el cuerpo de la sonda es complejo, las sondas de temporizador subsiguientes pueden omitirse, ya que el tiempo para que se ejecuten ya ha pasado. Normalmente, systemtap informa las sondas omitidas, pero no informará estas sondas omitidas.

DWARF

Esta familia de puntos de sonda utiliza información de depuración simbólica para el kernel/módulo/programa de destino, como se puede encontrar en ejecutables no despojados, o en paquetes separados de debuginfo. Permiten la colocación de sondas lógicamente en la ruta de ejecución del programa de destino, especificando un conjunto de puntos en el código fuente o en el código objeto. Cuando una sentencia coincidente se ejecuta en cualquier procesador, el manejador de sonda se ejecuta en ese contexto.

Los puntos de sonda de la familia DWARF se pueden identificar por el módulo del kernel (o proceso de usuario) de destino, el archivo fuente, el número de línea, el nombre de la función o alguna combinación de estos.

MÁS SOBRE SONDEOS DE RETORNO

Para los sondeos ".return" del kernel, solo se puede tener un número fijo de retornos pendientes. El valor predeterminado es un número relativamente pequeño, del orden de unas pocas veces el número de CPUs físicas. Si muchos hilos diferentes llaman concurrentemente a la misma función de bloqueo, como futex(2) o read(2), este límite podría excederse y se informarían "kretprobes" omitidos con "stap -t". Para solucionar esto, especifique un

probe FOO.return.maxactive(NNN)

sufijo, con un NNN lo suficientemente grande como para cubrir todos los hilos bloqueados concurrentemente esperados. Alternativamente, use el

stap -DKRETACTIVE=NNNN

macro de línea de comandos de stap para anular el valor predeterminado para todos los sondeos ".return".

Para los sondeos ".return", las variables de contexto distintas de "$return" pueden ser accesibles, como una conveniencia para un programador de scripts que desee acceder a los parámetros de la función. Estos valores son **instantáneas** tomadas en el momento de la entrada de la función. (Las variables locales dentro de la función **no** son generalmente accesibles, ya que esas variables no existían en forma asignada/inicializada en el momento de la instantánea). A estas variables de instantánea de entrada se debe acceder a través de @entry($var).

Además, las expresiones arbitrarias del momento de entrada también se pueden guardar para los sondeos ".return" usando el operador @entry(expr). Por ejemplo, se puede calcular el tiempo transcurrido de una función:

probe kernel.function("do_filp_open").return {
    println( get_timeofday_us() - @entry(get_timeofday_us()) )
}

SIN_DWARF

En ausencia de información de depuración, los puntos de entrada y salida de las funciones del kernel y de los módulos se pueden sondear utilizando la familia de sondeos "kprobe". Sin embargo, estos no permiten buscar los argumentos/variables locales de la función. Se admiten las siguientes construcciones:

kprobe.function(FUNCIÓN)
kprobe.function(FUNCIÓN).call
kprobe.function(FUNCIÓN).return
kprobe.module(NOMBRE).function(FUNCIÓN)
kprobe.module(NOMBRE).function(FUNCIÓN).call
kprobe.module(NOMBRE).function(FUNCIÓN).return
kprobe.statement(DIRECCIÓN).absolute

Se recomiendan los sondeos de tipo function para funciones del kernel, mientras que los sondeos de tipo module se recomiendan para sondear funciones del módulo especificado. En caso de que se conozca la dirección absoluta de una función del kernel o del módulo, se pueden utilizar los sondeos de statement.

Tenga en cuenta que los nombres de FUNCIÓN y MÓDULO **no deben** contener comodines, o el sondeo no se registrará. Además, los sondeos de sentencia deben ejecutarse solo en modo guru.

ESPACIO_DE_USUARIO

Hay soporte para el sondeo en el espacio de usuario disponible para kernels configurados con las extensiones utrace o que tienen la instalación uprobes en linux 3.5. (Se deben habilitar varias opciones de configuración de compilación del kernel; systemtap informará si faltan).

Hay varias formas. Primero, un punto de sondeo no simbólico:

process(PID).statement(DIRECCIÓN).absolute

es análogo a kernel.statement(DIRECCIÓN).absolute en que ambos usan direcciones virtuales en bruto (sin verificar) y no proporcionan $variables. El parámetro PID de destino debe identificar un proceso en ejecución, y DIRECCIÓN debe identificar una dirección de instrucción válida. Todos los hilos de ese proceso serán sondeados.

Segundo, los eventos de interfaz usuario-kernel no simbólicos manejados por utrace pueden ser sondeados:

process(PID).begin
process("RUTACOMPLETA").begin
process.begin
process(PID).thread.begin
process("RUTACOMPLETA").thread.begin
process.thread.begin
process(PID).end
process("RUTACOMPLETA").end
process.end
process(PID).thread.end
process("RUTACOMPLETA").thread.end
process.thread.end
process(PID).syscall
process("RUTACOMPLETA").syscall
process.syscall
process(PID).syscall.return
process("RUTACOMPLETA").syscall.return
process.syscall.return

Un sondeo de process.begin se llama cuando se crea un nuevo proceso descrito por PID o RUTACOMPLETA. Además, se llama una vez desde el contexto de cada proceso preexistente, al inicio del script de systemtap. Esto es útil para rastrear procesos en vivo. Un sondeo de process.thread.begin se llama cuando se crea un nuevo hilo descrito por PID o RUTACOMPLETA. Un sondeo de process.end se llama cuando muere un proceso descrito por PID o RUTACOMPLETA. Un sondeo de process.thread.end se llama cuando muere un hilo descrito por PID o RUTACOMPLETA. Un sondeo de process.syscall se llama cuando un hilo descrito por PID o RUTACOMPLETA realiza una llamada al sistema. El número de llamada al sistema está disponible en la variable de contexto $syscall, y los primeros 6 argumentos de la llamada al sistema están disponibles en la variable de contexto $argN (ej. $arg1, $arg2, ...). Un sondeo de process.syscall.return se llama cuando un hilo descrito por PID o RUTACOMPLETA regresa de una llamada al sistema. El número de llamada al sistema está disponible en la variable de contexto $syscall, y el valor de retorno de la llamada al sistema está disponible en la variable de contexto $return.

Si se especifica un sondeo de proceso sin PID o RUTACOMPLETA, se sondearán todos los hilos de usuario. Sin embargo, si systemtap se invocó con las opciones -c o -x, los sondeos de proceso se restringen a la jerarquía de procesos asociada con el proceso de destino. Si un sondeo de proceso no se especifica (es decir, sin PID o RUTACOMPLETA), pero con la opción -c, la RUTA del comando -c se completará heurísticamente en la RUTA del proceso. En ese caso, solo se permiten parámetros de comando en el comando -c (es decir, no se permite sustitución de comandos ni ocurrencias de ninguno de estos caracteres: '|&;<>(){}').

Tercero, se pueden sondear instrumentaciones estáticas simbólicas compiladas en programas y bibliotecas compartidas:

process("RUTA").mark("ETIQUETA")
process("RUTA").provider("PROVEEDOR").mark("ETIQUETA")
process(PID).mark("ETIQUETA")
process(PID).provider("PROVEEDOR").mark("ETIQUETA")

Un sondeo de .mark se llama a través de un sondeo estático que se define en la aplicación mediante STAP_PROBE1(PROVEEDOR, ETIQUETA, arg1), que son macros definidas en sys/sdt.h. PROVEEDOR es un identificador arbitrario de la aplicación, ETIQUETA es el identificador del sitio de marcador, y arg1 es el argumento de tipo entero. STAP_PROBE1 se utiliza para sondeos con 1 argumento, STAP_PROBE2 se utiliza para sondeos con 2 argumentos, y así sucesivamente. Los argumentos del sondeo están disponibles en las variables de contexto $arg1, $arg2, ... Una alternativa a usar las macros STAP_PROBE es usar el script dtrace para crear macros personalizadas. Además, las variables $$name y $$provider están disponibles como partes del nombre del punto de sondeo. Las macros sys/sdt.h DTRACE_PROBE* están disponibles como alias de STAP_PROBE*.

Finalmente, se admiten sondeos completos a nivel de código fuente simbólico en programas y bibliotecas compartidas del espacio de usuario. Estos son exactamente análogos a los sondeos DWARF simbólicos del kernel/módulo descritos anteriormente. Exponen los mismos tipos de variables de contexto $ para parámetros de función, variables locales, etc.

process("RUTA").function("NOMBRE")
process("RUTA").statement("*@ARCHIVO.c:123")
process("RUTA").plt("NOMBRE")
process("RUTA").library("RUTA").plt("NOMBRE")
process("RUTA").library("RUTA").function("NOMBRE")
process("RUTA").library("RUTA").statement("*@ARCHIVO.c:123")
process("RUTA").function("*").return
process("RUTA").function("mitarea").label("foo")
process("RUTA").function("foo").callee("bar")
process("RUTA").plt("NOMBRE").return
debuginfod.process("RUTA").**
process(PID).function("NOMBRE")
process(PID).statement("*@ARCHIVO.c:123")
process(PID).plt("NOMBRE")

Tenga en cuenta que para todos los sondeos de proceso, los nombres de RUTA se refieren a ejecutables que se buscan de la misma manera que los intérpretes de comandos: relativos al directorio de trabajo si contienen un carácter "/", de lo contrario en $PATH. Si los nombres de RUTA se refieren a scripts, se sondearán los intérpretes reales (especificados en el script en la primera línea después de los caracteres #!). En la familia de sondeos debuginfod, los nombres de RUTA se refieren de manera similar a los ejecutables, pero se buscan en los $DEBUGINFOD_URLS definidos actualmente.

Los sondeos de proceso de tapset ubicados en el directorio especial $prefix/share/systemtap/tapset/RUTA/ con rutas relativas tendrán su parámetro de proceso prefijado con la ubicación del tapset. Por ejemplo,

process("foo").function("NOMBRE")

se expande a

process("/usr/bin/foo").function("NOMBRE")

cuando se coloca en $prefix/share/systemtap/tapset/RUTA/usr/bin/

Si RUTA es un parámetro de componente de proceso que se refiere a bibliotecas compartidas, entonces todos los procesos que la mapeen en tiempo de ejecución serán seleccionados para el sondeo. Si RUTA es un parámetro de componente de biblioteca que se refiere a bibliotecas compartidas, entonces se seleccionará el proceso especificado por el componente de proceso. Tenga en cuenta que el patrón de RUTA en un componente de biblioteca siempre se aplicará a las bibliotecas determinadas estáticamente en uso por el proceso. Sin embargo, también puede especificar la ruta completa a cualquier archivo de biblioteca, incluso si no es necesaria estáticamente por el proceso.

Un sondeo .plt sondeará funciones en la tabla de enlaces de programas correspondientes al resto del punto de sondeo. .plt se puede especificar como un atajo para .plt("*"). El nombre del símbolo está disponible como una variable de contexto $$name; los argumentos de la función no están disponibles, ya que las PLT se procesan sin información de depuración. Un sondeo .plt.return coloca un sondeo en el momento **después** del retorno de la función nombrada.

Si la cadena RUTA contiene

s comodines como en el caso de MPATTERN, entonces se realiza una búsqueda de patrones estándar para encontrar todas las rutas coincidentes. En este caso, la variable de entorno $PATH no se utiliza.

Si systemtap se invocó con las opciones -c o -x, entonces las sondas de procesos se restringen a la jerarquía de procesos asociada con el proceso objetivo.

DEBUGINFOD

Estas sondas tienen la forma

debuginfod.process("PATH").**

Son muy similares a la familia de sondas process("PATH").** La diferencia clave es que las sondas de proceso buscan PATH en el sistema de archivos del host, mientras que las sondas debuginfod buscan en la federación actual de servidores debuginfod, utilizando $DEBUGINFOD_URLS definido actualmente (ver debuginfod(8) ).

Para sondear el contenido de uno o más archivos elf/archive y/o directorios que contienen elf/archive, lo siguiente creará un servidor debuginfod que escaneará y procesará los archivos elf dentro y los preparará para systemtap.

$ debuginfod [opciones] [-F -R -Z etc.] /ruta1 /ruta2
$ env DEBUGINFOD_URLS=http://localhost:8002/ stap ...

JAVA

El soporte para sondear métodos Java está disponible utilizando Byteman como backend. Byteman es una herramienta de instrumentación del proyecto JBoss que systemtap puede usar para monitorear invocaciones de un método o línea específica en un programa Java.

Systemtap lo hace generando un script Byteman que enumera las sondas a instrumentar e invocando la utilidad bminstall de Byteman.

Este soporte de instrumentación Java es actualmente una característica prototipo con limitaciones importantes. Además, la sondeo de Java actualmente no funciona entre usuarios; el script stap debe ejecutarse (con los permisos apropiados) bajo el mismo usuario que el proceso Java que se está sondeando. (Por lo tanto, un script stap bajo root actualmente no puede sondear métodos Java en un proceso Java de usuario no root).

El primer tipo de sonda se refiere a procesos Java por el nombre del proceso Java:

java("PNAME").class("CLASSNAME").method("PATTERN")
java("PNAME").class("CLASSNAME").method("PATTERN").return

El argumento PNAME debe ser un pid de jvm preexistente, y ser identificable mediante una lista jps.

El parámetro PATTERN especifica la firma del método Java a sondear. La firma debe consistir en el nombre exacto del método, seguido de una lista entre corchetes de los tipos de los argumentos, por ejemplo "myMethod(int,double,Foo)". Los comodines no son compatibles.

La sonda puede configurarse para activarse en una línea específica dentro del método agregando un número de línea con dos puntos, al igual que en otros tipos de sondas: "myMethod(int,double,Foo):245".

El parámetro CLASSNAME identifica la clase Java a la que pertenece el método, con o sin la calificación del paquete. Por defecto, la sonda solo se activa en descendientes de la clase que no anulan la definición del método de la clase original. Sin embargo, CLASSNAME puede tomar un prefijo de intercalación opcional, como en ^org.my.MyClass, que especifica que la sonda también se activará en todos los descendientes de MyClass que anulen el método original. Por ejemplo, cada método con la firma foo(int) en el programa org.my.MyApp se puede sondear a la vez utilizando

java("org.my.MyApp").class("^java.lang.Object").method("foo(int)")

El segundo tipo de sonda funciona de manera análoga, pero se refiere a procesos Java por PID:

java(PID).class("CLASSNAME").method("PATTERN")
java(PID).class("CLASSNAME").method("PATTERN").return

(Los PID de un proceso en ejecución se pueden obtener utilizando la utilidad jps(1).)

Las variables de contexto definidas dentro de las sondas java incluyen $arg1 a $arg10 (para hasta los primeros 10 argumentos de un método), representadas como punteros de caracteres para la forma toString() de cada argumento real. Las variables de script arg1 a arg10 brindan acceso a estos como cadenas normales, obtenidas a través de user_string_warn().

Antes de la versión 3.1 de systemtap, $arg1 a $arg10 podían contener enteros o punteros de caracteres, dependiendo de los tipos de los objetos que se pasaban a cada método java particular. Este comportamiento anterior puede invocarse con el indicador stap --compatible=3.0.

PROCFS

Estos puntos de sondeo permiten crear, leer y escribir archivos "procfs" en /proc/systemtap/MODNAME utilizando un permiso que puede modificarse usando el valor umask adecuado. Los permisos predeterminados son 0400 para sondas de lectura y 0200 para sondas de escritura. Si se utilizan tanto una sonda de lectura como una de escritura en el mismo archivo, se utilizará un permiso predeterminado de 0600. El uso de procfs.umask(0040).read resultaría en un conjunto de permisos de 0404 para el archivo. (MODNAME es el nombre del módulo systemtap). El sistema de archivos proc es un sistema de archivos pseudo que se utiliza como interfaz para las estructuras de datos del kernel. Hay varias variantes de puntos de sondeo admitidas por el traductor:

procfs("PATH").read
procfs("PATH").umask(UMASK).read
procfs("PATH").read.maxsize(MAXSIZE)
procfs("PATH").umask(UMASK).maxsize(MAXSIZE)
procfs("PATH").write
procfs("PATH").umask(UMASK).write
procfs.read
procfs.umask(UMASK).read
procfs.read.maxsize(MAXSIZE)
procfs.umask(UMASK).read.maxsize(MAXSIZE)
procfs.write
procfs.umask(UMASK).write

Tenga en cuenta que hay algunas diferencias cuando se utilizan sondas procfs en el tiempo de ejecución stapbpf. Se utilizan archivos FIFO especiales en lugar de archivos del sistema de archivos proc. Estos archivos se crean en /var/tmp/systemtap-USUARIO/MODNAME. (USUARIO es el nombre del usuario). Además, los usuarios no pueden crear sondas de lectura y escritura en el mismo archivo.

PATH es el nombre del archivo (relativo a /proc/systemtap/MODNAME o /var/tmp/systemtap-USUARIO/MODNAME) que se creará. Si no se especifica PATH (como en las dos últimas variantes anteriores), PATH se establece por defecto en "command". El nombre de archivo "__stdin" es utilizado internamente por systemtap para sondas de entrada y no debe usarse como PATH para sondas procfs; consulte la sección de sondas de entrada a continuación.

Cuando un usuario lee /proc/systemtap/MODNAME/PATH (tiempo de ejecución normal) o /var/tmp/systemtap-USUARIO/MODNAME (tiempo de ejecución stapbpf), se activa la sonda read procfs correspondiente. Los datos de cadena a leer deben asignarse a una variable llamada $value, de la siguiente manera:

procfs("PATH").read { $value = "100\n" }

Cuando un usuario escribe en /proc/systemtap/MODNAME/PATH (tiempo de ejecución normal) o /var/tmp/systemtap-USUARIO/MODNAME (tiempo de ejecución stapbpf), se activa la sonda write procfs correspondiente. Los datos que el usuario escribió están disponibles en la variable de cadena llamada $value, de la siguiente manera:

procfs("PATH").write { printf("el usuario escribió: %s", $value) }

MAXSIZE es el tamaño del búfer de lectura procfs. Especificar MAXSIZE permite una salida procfs más grande. Si no se especifica MAXSIZE, el búfer de lectura procfs se establece por defecto en STP_PROCFS_BUFSIZE (que se establece por defecto en MAXSTRINGLEN, la longitud máxima de una cadena). Si se necesita establecer los búferes de lectura procfs para más de un archivo, puede ser más fácil anular la definición de STP_PROCFS_BUFSIZE. Aquí hay un ejemplo de uso de MAXSIZE:

procfs.read.maxsize(1024) {
    $value = "cadena larga..."
    $value .= "otra cadena larga..."
    $value .= "otra cadena larga..."
    $value .= "otra cadena larga..."
}

INPUT

Estos puntos de sondeo hacen que la entrada de stdin esté disponible para el script durante el tiempo de ejecución. El traductor admite actualmente dos variantes de esta familia:

input.char
input.line

input.char se activa cada vez que se lee un carácter de stdin. El carácter actual está disponible en la variable de cadena llamada char. No hay almacenamiento en búfer de saltos de línea; el siguiente carácter se lee de stdin tan pronto como esté disponible.

input.line hace que todos los caracteres leídos de stdin se almacenen en búfer hasta que se lea un salto de línea, momento en el cual se activará la sonda. La línea actual de caracteres (incluido el salto de línea) está disponible en una variable de cadena llamada line. Tenga en cuenta que no se almacenarán más de MAXSTRINGLEN caracteres. Cualquier carácter adicional no se incluirá en line.

Las sondas de entrada son alias de procfs("__stdin").write. Systemtap reconfigura stdin si se detecta la presencia de esta sonda procfs, por lo tanto, no se debe usar "__stdin" como argumento de ruta para sondas procfs. Además, las sondas de entrada no funcionarán con las opciones -F y --remote.

NETFILTER HOOKS

Estos puntos de sondeo permiten la observación de paquetes de red utilizando el mecanismo netfilter. Una sonda netfilter en systemtap corresponde a una función de hook netfilter en la API original de sondas netfilter. Probablemente sea más conveniente usar tapset::netfilter(3stap), que envuelve los hooks netfilter primitivos y realiza el trabajo de extraer información útil de las variables de contexto.

Hay varias variantes de puntos de sondeo admitidas por el traductor:

netfilter.hook("HOOKNAME").pf("PROTOCOL_F")
netfilter.pf("PROTOCOL_F").hook("HOOKNAME")
netfilter.hook("HOOKNAME").pf("PROTOCOL_F").priority("PRIORITY")
netfilter.pf("PROTOCOL_F").hook("HOOKNAME").priority("PRIORITY")

PROTOCOL_F es la familia de protocolos a la que escuchar, actualmente uno de NFPROTO_IPV4, NFPROTO_IPV6, NFPROTO_ARP, o NFPROTO_BRIDGE.

HOOKNAME es el punto, o 'hook', en la pila de protocolos en el que interceptar el paquete. Los nombres de hook disponibles para cada familia de protocolos se toman de los archivos de cabecera del kernel <linux/netfilter_ipv4.h>, <linux/netfilter_ipv6.h>, <linux/netfilter_arp.h> y <linux/netfilter_bridge.h>. Por ejemplo, los nombres de hook permitidos para NFPROTO_IPV4 son NF_INET_PRE_ROUTING, NF_INET_LOCAL_IN, NF_INET_FORWARD, NF_INET_LOCAL_OUT, y NF_INET_POST_ROUTING.

PRIORITY es una prioridad entera que indica el orden en que el punto de sondeo debe b

e activan en relación con cualquier otra función de hook de netfilter que se active en el mismo paquete. Las funciones de hook se ejecutan en cada paquete en orden, desde el número de prioridad más pequeño hasta el más grande. Si no se especifica PRIORITY (como en las dos primeras variantes de punto de sondeo anteriores), PRIORITY por defecto es "0".

Hay una serie de nombres de prioridad predefinidos de la forma NF_IP_PRI_* y NF_IP6_PRI_* que se definen en los archivos de cabecera del kernel <linux/netfilter_ipv4.h> y <linux/netfilter_ipv6.h> respectivamente. Se permite que el script utilice estos en lugar de especificar una prioridad entera. (Los puntos de sondeo para NFPROTO_ARP y NFPROTO_BRIDGE actualmente no exponen prioridades de hook con nombre al escritor del script.) Por lo tanto, las formas admisibles de especificar la prioridad incluyen:

priority("255")
priority("NF_IP_PRI_SELINUX_LAST")

A un script que utiliza el modo guru se le permite especificar cualquier identificador o número como parámetro para hook, pf y priority. Esta función debe usarse con precaución, ya que el parámetro se inserta literalmente en el código C generado por systemtap.

Los puntos de sondeo de netfilter definen las siguientes variables de contexto:

$hooknum
El número de hook.
$skb
La dirección de la estructura sk_buff que representa el paquete. Consulte <linux/skbuff.h> para obtener detalles sobre cómo utilizar esta estructura, o alternativamente utilice el tapset tapset::netfilter(3stap) para un acceso fácil a la información clave.
$in
La dirección de la estructura net_device que representa el dispositivo de red en el que se recibió el paquete (si lo hay). Puede ser 0 si el dispositivo es desconocido o indefinido en esa etapa de la pila del protocolo.
$out
La dirección de la estructura net_device que representa el dispositivo de red en el que se enviará el paquete (si lo hay). Puede ser 0 si el dispositivo es desconocido o indefinido en esa etapa de la pila del protocolo.
$verdict
(Solo modo guru.) Asignar uno de los valores de veredicto definidos en <linux/netfilter.h> a esta variable altera el progreso posterior del paquete a través de la pila del protocolo. Por ejemplo, el siguiente script en modo guru fuerza que todos los paquetes de red ipv6 sean descartados: 
probe netfilter.pf("NFPROTO_IPV6").hook("NF_IP6_PRE_ROUTING") {
  $verdict = 0 /* nf_drop */
}

Para mayor comodidad, a diferencia de los puntos de sondeo primitivos discutidos aquí, los sondeos definidos en tapset::netfilter(3stap) exportan los nombres en minúsculas de las constantes de veredicto (por ejemplo, NF_DROP se convierte en nf_drop) como variables locales.

TRAZAS DEL KERNEL

Esta familia de puntos de sondeo se conecta a puntos de traza de sondeo estático insertados en el kernel o módulos. Al igual que con los marcadores, estos puntos de traza son llamadas de macro especiales insertadas por los desarrolladores del kernel para hacer el sondeo más rápido y confiable que con los sondeos basados en DWARF, y no se requiere información de depuración DWARF para sondear puntos de traza. Los puntos de traza tienen la ventaja adicional de parámetros con tipos más fuertes que los marcadores.

Los sondeos de puntos de traza tienen el aspecto: kernel.trace("nombre"). El nombre del punto de traza, que puede contener los caracteres comodín habituales, se compara con los nombres definidos por los desarrolladores del kernel en los archivos de cabecera de los puntos de traza. Para restringir la búsqueda a subsistemas específicos (por ejemplo, sched, ext3, etc.), se puede utilizar la siguiente sintaxis: kernel.trace("sistema:nombre"). El nombre del subsistema del punto de traza también puede contener los caracteres comodín habituales.

El manejador asociado con un sondeo basado en puntos de traza puede leer los parámetros opcionales especificados en el sitio de la llamada a la macro. Estos se nombran según la declaración del autor del punto de traza. Por ejemplo, el sondeo de punto de traza kernel.trace("sched:sched_switch") proporciona los parámetros $prev y $next. Si el parámetro es un tipo complejo, como en un puntero a una estructura, un script puede acceder a los campos con la misma sintaxis que las variables $target de DWARF. Además, los parámetros de los puntos de traza no se pueden modificar, pero en modo guru un script puede modificar los campos de los parámetros.

El subsistema y el nombre del punto de traza están disponibles en $$system y $$name y una cadena de pares nombre=valor para todos los parámetros del punto de traza está disponible en $$vars o $$parms.

MARCADORES DEL KERNEL (OBSOLETO)

Esta familia de puntos de sondeo se conecta a un estilo más antiguo de marcadores de sondeo estático insertados en kernels o módulos más antiguos. Estos marcadores son llamadas de macro STAP_MARK especiales insertadas por los desarrolladores del kernel para hacer el sondeo más rápido y confiable que con los sondeos basados en DWARF. Además, la información de depuración DWARF *no* es necesaria para sondear marcadores.

Los puntos de sondeo de marcadores comienzan con kernel. La siguiente parte nombra el marcador en sí: mark("nombre"). El nombre del marcador, que puede contener los caracteres comodín habituales, se compara con los nombres dados a las macros de marcador cuando el kernel y/o módulo se compiló. Opcionalmente, se puede especificar format("formato"). Especificar la cadena de formato del marcador permite diferenciar entre dos marcadores con el mismo nombre pero con diferentes cadenas de formato de marcador.

El manejador asociado con un sondeo basado en marcadores puede leer los parámetros opcionales especificados en el sitio de la llamada a la macro. Estos se nombran $arg1 a $argNN, donde NN es el número de parámetros proporcionados por la macro. Los parámetros numéricos y de cadena se pasan de manera segura en cuanto a tipos.

La cadena de formato del marcador asociada con un marcador está disponible en $format. Y también la cadena de nombre del marcador está disponible en $name.

PUNTOS DE INTERRUPCION DE HARDWARE DEL KERNEL

Esta familia de sondeos se utiliza para establecer puntos de vigilancia de hardware para un símbolo de kernel dado (global). Los sondeos toman tres componentes como entrada:

1. La dirección virtual / nombre del símbolo del kernel a rastrear se proporciona como argumento a esta clase de sondeos. (Solo se admiten sondeos para variables del segmento de datos. No se pueden sondear variables locales de una función.)

2. Naturaleza del acceso a sondear: a. El sondeo .write se activa cuando ocurre una escritura en la dirección/nombre de símbolo especificado. b. El sondeo rw se activa cuando ocurre una lectura o una escritura.

3. .length (opcional) Los usuarios tienen la opción de especificar el intervalo de direcciones a sondear utilizando construcciones de "longitud". La longitud especificada por el usuario se aproxima a la longitud de dirección posible más cercana que la arquitectura puede soportar. Si la longitud especificada excede los límites impuestos por la arquitectura, se genera un mensaje de error y el registro del sondeo falla. Donde no se especifica 'length', el traductor solicita un sondeo de punto de interrupción de hardware de longitud 1. Cabe señalar que la construcción "length" no es válida con nombres de símbolos.

Se admiten las siguientes construcciones:

probe kernel.data(DIRECCION).write
probe kernel.data(DIRECCION).rw
probe kernel.data(DIRECCION).length(LEN).write
probe kernel.data(DIRECCION).length(LEN).rw
probe kernel.data("NOMBRE_SIMBOLO").write
probe kernel.data("NOMBRE_SIMBOLO").rw

Este conjunto de sondeos utiliza los registros de depuración del procesador, que son un recurso escaso. (4 en x86, 1 en powerpc) La traducción del script genera una advertencia si un usuario solicita más sondeos de puntos de interrupción de hardware que los límites establecidos por la arquitectura. Por ejemplo, se muestra una advertencia de paso 2 cuando un script de entrada solicita 5 sondeos de puntos de interrupción de hardware en un sistema x86, mientras que la arquitectura x86 admite un máximo de 4 puntos de interrupción. Se advierte a los usuarios que establezcan los sondeos de manera juiciosa.

Es posible especificar direcciones de memoria virtual del espacio de usuario en esta familia de sondeos y los manejadores se activarán ante los eventos de lectura/escritura de memoria correspondientes en esos procesos. Pero no se puede controlar fácilmente qué procesos se supervisan. Usar `if (pid() == target())` es una solución alternativa, pero es ineficiente. Es mejor usar los sondeos de puntos de interrupción de hardware del espacio de usuario a continuación.

PUNTOS DE INTERRUPCION DE HARDWARE DEL ESPACIO DE USUARIO

Esta familia de sondeos es muy similar a su contraparte en el espacio del kernel, pero se dirige solo a los procesos del espacio de usuario.

Actualmente se admiten las siguientes construcciones:

probe process.data(DIRECCION).write
probe process.data(DIRECCION).rw
probe process.data(DIRECCION).length(LEN).write
probe process.data(DIRECCION).length(LEN).rw

Actualmente, solo el proceso objetivo especificado por -x PID o -c CMD tiene los puntos de vigilancia registrados. La DIRECCION debe ser una dirección de memoria virtual válida en el espacio de direcciones de ese proceso.

PERF

Esta familia de puntos de sondeo interactúa con la infraestructura del kernel "perf event" para controlar los contadores de rendimiento de hardware. Los eventos a los que se adjuntan se describen mediante los campos "type" y "config" de la estructura perf_event_attr, y se muestrean a un intervalo regido por los campos "sample_period" y "sample_freq".

Estos campos están disponibles para los scripts de systemtap utilizando la siguiente sintaxis:

probe perf.type(NN).config(MM).sample(XX)
probe perf.type(NN).config(MM).hz(XX)
probe perf.type(NN).config(MM)
probe perf.type(NN).config(MM).process("PROC")
probe perf.type(NN).config(MM).counter("CONTADOR")
probe perf.type(NN).config(MM).process("PROC").counter("NOMBRE")

El manejador del sondeo de systemtap se llama una vez por cada XX incrementos del contador de rendimiento subyacente cuando se utiliza el campo .sample o a una frecuencia en hertz cuando se utiliza el campo .hz. Cuando no se especifica, el comportamiento predeterminado es muestrear a un recuento de 1000000. El rango de tipo/configuración válidos se describe mediante la llamada al sistema perf_event_open(2), y/o el archivo linux/perf_event.h. NAME

stapprobes - SystemTap probe point syntax

DESCRIPTION

SystemTap uses probe points to identify events of interest for instrumentation. This man page describes the syntax for specifying probe points.

Probe points are grouped into families, each representing a different source of events. The following families are available:

BARE PROBE POINTS
begin, end
These probe points fire once at the start and end of the SystemTap script execution, respectively.
tick
This probe point fires periodically, based on the system's timer interrupts (jiffies). It takes an optional argument specifying the frequency in jiffies. For example, tick(1000) fires every 1000 jiffies.
profile
This probe point fires periodically, based on the system's timer interrupts (jiffies), similar to tick. It is intended for sampling-based profiling.
KERNEL PROBE POINTS
kernel.function("IDENT")
Probes the entry into the specified kernel function. IDENT can be a function name, optionally with wildcards. A probe can also target a specific line within a function using `@file:line` or `@file:+-offset` syntax.
kernel.function("IDENT").call
Probes the call site of the specified kernel function.
kernel.function("IDENT").return
Probes the return from the specified kernel function.
kernel.statement("IDENT")
Probes the specified statement within a kernel function. This is more precise than kernel.function and targets specific instructions.
kernel.trace("IDENT")
Probes kernel tracepoints. IDENT typically follows the format `group/name`.
kernel.mark("IDENT")
Probes kernel marker points, which are typically inserted using STAP_MARK macros.
kernel.inject("IDENT")
Injects code at the specified location in the kernel. This is an advanced feature and should be used with caution.
kernel.inline("IDENT")
Probes inline kernel functions. IDENT can be a function name with wildcards.
kernel.modcall("IDENT")
Probes calls to functions within kernel modules.
kernel.modreturn("IDENT")
Probes returns from functions within kernel modules.
USER SPACE PROBE POINTS
process.function("IDENT")
Probes the entry into the specified function within a user-space process. IDENT can be a function name, optionally with wildcards. A probe can also target a specific line within a function using `@file:line` or `@file:+-offset` syntax.
process.function("IDENT").call
Probes the call site of the specified user-space function.
process.function("IDENT").return
Probes the return from the specified user-space function.
process.statement("IDENT")
Probes the specified statement within a user-space function.
process.trace("IDENT")
Probes user-space tracepoints.
process.mark("IDENT")
Probes user-space marker points.
process.syscall.GROUP.EVENT
Probes system calls. GROUP can be a specific syscall name or `*` for all syscalls. EVENT can be entry or return.
PYTHON

Support for probing python 2 and python 3 function is available with the help of an extra python support module. Note that the debuginfo for the version of python being probed is required. To run a python script with the extra python support module you'd add the '-m HelperSDT' option to your python command, like this:

stap foo.stp -c "python -m HelperSDT foo.py"

Python probes look like the following:

python2.module("MPATTERN").function("PATTERN")
python2.module("MPATTERN").function("PATTERN").call
python2.module("MPATTERN").function("PATTERN").return
python3.module("MPATTERN").function("PATTERN")
python3.module("MPATTERN").function("PATTERN").call
python3.module("MPATTERN").function("PATTERN").return

The list above includes multiple variants and modifiers which provide additional functionality or filters. They are:

.function
Places a probe at the beginning of the named function by default, unless modified by PATTERN. Parameters are available as context variables.
.call
Places a probe at the beginning of the named function. Parameters are available as context variables.
.return
Places a probe at the moment before the return from the named function. Parameters and local/global python variables are available as context variables.

PATTERN stands for a string literal that aims to identify a point in the python program. It is made up of three parts:

  • The first part is the name of a function (e.g. "foo") or class method (e.g. "bar.baz"). This part may use the "*" and "?" wildcarding operators to match multiple names.
  • The second part is optional and begins with the "@" character. It is followed by the path to the source file containing the function, which may include a wildcard pattern. The python path is searched for a matching filename.
  • Finally, the third part is optional if the file name part was given, and identifies the line number in the source file preceded by a ":" or a "+". The line number is assumed to be an absolute line number if preceded by a ":", or relative to the declaration line of the function if preceded by a "+". All the lines in the function can be matched with ":*". A range of lines x through y can be matched with ":x-y". Ranges and specific lines can be mixed using commas, e.g. ":x,y-z".

In the above list of probe points, MPATTERN stands for a python module or script name that names the python module of interest. This part may use the "*" and "?" wildcarding operators to match multiple names. The python path is searched for a matching filename.
