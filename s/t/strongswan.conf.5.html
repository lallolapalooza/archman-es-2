NOMBRE

strongswan.conf - Archivo de configuración de strongSwan

DESCRIPCIÓN

Mientras que el archivo de configuración ipsec.conf(5) es adecuado para definir parámetros de configuración relacionados con IPsec, no es útil para que otras aplicaciones de strongSwan lean opciones de este archivo. El archivo es difícil de analizar y solo ipsec starter es capaz de hacerlo. A medida que el número de componentes del proyecto strongSwan crece continuamente, se necesitaba un archivo de configuración más flexible, uno que sea fácil de extender y que pueda ser utilizado por todos los componentes. Con strongSwan 4.2.1 se introdujo strongswan.conf(5) que cumple estos requisitos.

SINTAXIS

El formato del archivo strongswan.conf consiste en secciones jerárquicas y una lista de pares clave/valor en cada sección. Cada sección tiene un nombre, seguido de llaves estilo C que definen el cuerpo de la sección. Cada cuerpo de sección contiene un conjunto de subsecciones y pares clave/valor:

settings := (section|keyvalue)*
section  := name { settings }
keyvalue := key = value\n

Los valores deben terminar con un salto de línea.

Los comentarios son posibles usando el carácter #.

Los nombres de sección y las claves pueden contener cualquier carácter imprimible excepto:

. , : { } = " # \n \t espacio

Un archivo de ejemplo en este formato podría verse así:

a = b
section-one {
	somevalue = asdf
	subsection {
		othervalue = xxx
	}
	# yei, un comentario
	yetanother = zz
}
section-two {
	x = 12
}

La indentación es opcional, puedes usar tabulaciones o espacios.

FORMATOS DE NÚMERO

Las opciones que definen un valor entero se pueden especificar como decimales (el valor predeterminado) o hexadecimales (prefijo "0x", se aceptan letras mayúsculas o minúsculas). Las cadenas dependientes de la configuración regional (por ejemplo, el separador de miles de la configuración regional actual) también pueden ser aceptadas en configuraciones regionales distintas de "C".

Las opciones que definen un valor de punto flotante se pueden especificar como decimales (el valor predeterminado) o hexadecimales (prefijo "0x", se aceptan letras mayúsculas o minúsculas). El carácter separador decimal (separador de miles) en ambos casos depende de la configuración regional, generalmente ".".

FORMATOS DE TIEMPO

A menos que se indique lo contrario, las opciones que definen un tiempo se especifican en segundos. Los sufijos "s", "m", "h" y "d" se pueden utilizar para convertir automáticamente los valores dados en segundos, minutos, horas o días (por ejemplo, en lugar de configurar un tiempo de rekeying de 4 horas como "14400" segundos, se puede usar "4h").

Existen algunas opciones globales que no aceptan estos sufijos ya que están configuradas como valores enteros en segundos o milisegundos, o incluso como números de punto flotante (por ejemplo, el tiempo de espera de retransmisión). Las opciones que aceptan sufijos tienen un valor predeterminado correspondiente.

REFERENCIANDO OTRAS SECCIONES

Es posible heredar configuraciones y secciones de otra sección. Esta característica es principalmente útil en swanctl.conf (que utiliza el mismo formato de archivo). La sintaxis es la siguiente:

section    := name : references { settings }
references := absname[, absname]*
absname    := name[.name]*

Todos los pares clave/valor y todas las subsecciones de las secciones referenciadas serán heredados por la sección que los referencia a través de su nombre absoluto. Los valores pueden ser anulados en la sección o en cualquiera de sus subsecciones (use una asignación vacía para borrar un valor para que se aplique su valor predeterminado, si lo hay). Actualmente no es posible limitar el nivel de inclusión o borrar/eliminar subsecciones heredadas.

Si el orden es importante (por ejemplo, para rondas de autenticación en una conexión, si no se usa round), se debe tener en cuenta que las configuraciones/secciones heredadas seguirán a las definidas en la sección actual (si se referencian varias secciones, sus configuraciones se enumeran de izquierda a derecha).

Las referencias se evalúan dinámicamente en tiempo de ejecución, por lo que referenciar secciones más adelante en el archivo de configuración o incluidas a través de otros archivos no es un problema.

Aquí hay un ejemplo de cómo podría verse esto:

conn-defaults {
	# configuración predeterminada para todas las conexiones (por ejemplo, un certificado o grupos de IP)
}
eap-defaults {
	# configuración predeterminada si se usa EAP (por ejemplo, una ronda de autenticación remota)
}
child-defaults {
	# configuración predeterminada para configuraciones de hijo (por ejemplo, selectores de tráfico)
}
connections {
	conn-a : conn-defaults, eap-defaults {
		# establecer/anular cosas específicas de esta conexión
		children {
			child-a : child-defaults {
				# establecer/anular cosas específicas de este hijo
			}
		}
	}
	conn-b : conn-defaults {
		# establecer/anular cosas específicas de esta conexión
		children {
			child-b : child-defaults {
				# establecer/anular cosas específicas de este hijo
			}
		}
	}
	conn-c : connections.conn-a {
		# todo se hereda, incluyendo todo lo que conn-a
		# ya hereda de las secciones que él y su
		# subsección referencian
	}
}

INCLUYENDO ARCHIVOS

Usando la instrucción include es posible incluir otros archivos en strongswan.conf, por ejemplo:

include /some/path/*.conf

Si el nombre del archivo no es una ruta absoluta, se considera relativo al directorio del archivo que contiene la instrucción include. El nombre del archivo puede incluir comodines de shell (ver sh(1)). Además, tales inclusiones pueden anidarse.

Las secciones cargadas desde archivos incluidos *extienden* las secciones cargadas previamente; los valores ya existentes se *reemplazan*. Es importante notar que las configuraciones se agregan en relación con la sección en la que se encuentra la instrucción include.

Como ejemplo, los siguientes tres archivos resultan en la misma configuración final que la dada anteriormente:

	a = b
	section-one {
		somevalue = before include
		include include.conf
	}
	include other.conf
include.conf:
	# las configuraciones cargadas desde este archivo se agregan a section-one
	# lo siguiente reemplaza el valor anterior
	somevalue = asdf
	subsection {
		othervalue = yyy
	}
	yetanother = zz
other.conf:
	# esto extiende section-one y subsection
	section-one {
		subsection {
			# esto reemplaza el valor anterior
			othervalue = xxx
		}
	}
	section-two {
		x = 12
}

LEYENDO VALORES

Los valores se acceden usando una lista de secciones separadas por puntos y una clave. Con referencia al ejemplo anterior, acceder a section-one.subsection.othervalue devolverá xxx.

charon.plugins.updown.spdh_thresh

XFRM policy hashing threshold configuration for IPv4 and IPv6.

The section defines hashing thresholds to configure in the kernel during daemon startup. Each address family takes a threshold for the local subnet of an IPsec policy (src in out-policies, dst in in- and forward-policies) and the remote subnet (dst in out-policies, src in in- and forward-policies).

If the subnet has more or equal net bits than the threshold, the first threshold bits are used to calculate a hash to lookup the policy.

Policy hashing thresholds are not supported before Linux 3.18 and might conflict with socket policies before Linux 4.8.

charon.rdn_matching [strict]
Cómo se comparan los RDN en los DN de sujeto de los certificados con las identidades configuradas. Los valores posibles son strict (el predeterminado), reordered y relaxed. Con strict, el número, tipo y orden de todos los RDN deben coincidir, se permiten comodines (*) para los valores de los RDN (este es el caso para las tres variantes). Usando reordered también compara DN si los RDN aparecen en un orden diferente, el número y el tipo aún deben coincidir. Finalmente, relaxed también permite la comparación de DN que contienen más RDN que la identidad configurada (los RDN faltantes se tratan como una coincidencia de comodín).

Tenga en cuenta que reordered y relaxed imponen una carga considerable en el uso de memoria y tiempo de ejecución, en particular, para desajustes, en comparación con strict.

GESTIÓN DE PRIORIDAD DE TAREAS

Algunas operaciones en el demonio IKEv2 charon se implementan actualmente de forma síncrona y bloqueante. Dos ejemplos de tales operaciones son la comunicación con un servidor RADIUS a través de EAP-RADIUS, o la obtención de información CRL/OCSP durante la verificación de la cadena de certificados. Bajo condiciones de alta carga, el pool de hilos puede quedarse sin hilos disponibles, y algunas tareas más importantes, como la comprobación de actividad, pueden no ejecutarse a tiempo.

Para prevenir la inanición de hilos en tales situaciones, se introdujeron las prioridades de tareas. El procesador de tareas reservará algunos hilos para tareas de mayor prioridad; estos hilos no están disponibles para tareas bloqueantes de menor prioridad.

Implementación

Actualmente se han definido 4 prioridades, y se utilizan en charon de la siguiente manera:

CRITICAL
Prioridad para tareas de dispatcher de larga duración.
HIGH
Intercambios INFORMACIONALES, como los utilizados por la comprobación de actividad (DPD).
MEDIUM
Todo lo que no sea HIGH/LOW, incluyendo el procesamiento de IKE_SA_INIT.
LOW
Procesamiento de mensajes IKE_AUTH. La obtención de CRL y RADIUS se bloquean aquí

Aunque el procesamiento de IKE_SA_INIT es computacionalmente costoso, se asigna explícitamente a la clase MEDIUM. Esto permite que charon realice el intercambio DH mientras otros hilos están bloqueados en IKE_AUTH. Para evitar que el demonio acepte más solicitudes IKE_SA_INIT de las que puede manejar, utilice IKE_SA_INIT DROPPING.

El pool de hilos procesa las tareas estrictamente por prioridad, lo que significa que consumirá todas las tareas de mayor prioridad antes de buscar las de menor prioridad. Además, reserva hilos para ciertas prioridades. Una clase de prioridad que haya reservado n hilos siempre tendrá n hilos disponibles para esa clase (ya sea procesando una tarea actualmente o esperando una).

Configuración

Para garantizar que siempre haya suficientes hilos disponibles para tareas de mayor prioridad, se deben reservar hilos para cada clase de prioridad.

charon.processor.priority_threads.critical [0]
Hilos reservados para tareas de clase CRITICAL
charon.processor.priority_threads.high [0]
Hilos reservados para tareas de clase HIGH
charon.processor.priority_threads.medium [0]
Hilos reservados para tareas de clase MEDIUM
charon.processor.priority_threads.low [0]
Hilos reservados para tareas de clase LOW

Consideremos la siguiente configuración:

charon {
	processor {
		priority_threads {
			high = 1
			medium = 4
		}
	}
}

Con esta configuración, se reserva un hilo para tareas de alta prioridad (HIGH). Dado que actualmente solo la comprobación de actividad y el procesamiento de mensajes de stroke se realizan con alta prioridad, uno o dos hilos deberían ser suficientes.

La clase MEDIUM procesa principalmente tareas no bloqueantes. A menos que su configuración experimente muchos bloqueos al acceder a recursos compartidos, un número de hilos de una o dos veces el número de núcleos de CPU está bien.

Por lo general, no es necesario reservar hilos para trabajos CRITICAL. Las tareas de esta clase rara vez regresan y no liberan su hilo al pool.

Los hilos restantes están disponibles para tareas de baja prioridad (LOW). Reservar hilos no tiene sentido (hasta que tengamos una prioridad aún más baja).

Monitorización

Para ver qué están haciendo realmente los hilos, invoque ipsec statusall. Bajo alta carga, aparecerá algo como esto:

worker threads: 2 or 32 idle, 5/1/2/22 working,
	job queue: 0/0/1/149, scheduled: 198

De 32 hilos de trabajo,

2
están actualmente inactivos.
5
están ejecutando tareas de prioridad CRITICAL (despachando desde sockets, etc.).
1
está manejando actualmente una tarea de prioridad HIGH. Este es en realidad el hilo que actualmente proporciona esta información a través de stroke.
2
están manejando tareas de prioridad MEDIUM, probablemente mensajes IKE_SA_INIT o CREATE_CHILD_SA.
22
están manejando tareas de prioridad LOW, probablemente esperando una respuesta EAP-RADIUS mientras procesan mensajes IKE_AUTH.

La carga de la cola de tareas muestra cuántas tareas están en cola para cada prioridad, listas para su ejecución. La única tarea de prioridad MEDIUM se ejecutará inmediatamente, ya que tenemos dos hilos de sobra reservados para tareas de clase MEDIUM.

DESCARTE DE IKE_SA_INIT

Si un respondedor recibe más solicitudes de conexión por segundo de las que puede manejar, no tiene sentido aceptar más mensajes IKE_SA_INIT. Y si se ponen en cola pero no se pueden procesar a tiempo, es posible que se envíe una respuesta después de que el cliente ya se haya rendido y reiniciado la configuración de su conexión. Esto aumenta aún más la carga en el respondedor.

Para limitar la carga del respondedor resultante de los intentos de conexión nuevos, el demonio puede descartar mensajes IKE_SA_INIT justo después de recibirlos. Existen dos mecanismos para decidir si esto debe suceder, configurados con las siguientes opciones:

charon.init_limit_half_open [0]
Límite basado en el número de IKE_SA medio abiertas. Las IKE_SA medio abiertas son SA en estado de conexión, pero aún no establecidas.
charon.init_limit_job_load [0]
Límite basado en el número de tareas actualmente en cola para su procesamiento (suma de todas las prioridades de tareas).

El segundo límite incluye la carga de otras tareas, como el rekeying. Elegir un buen valor es difícil y depende del hardware y la carga esperada.

El primer límite es más fácil de calcular, pero solo incluye la carga de conexiones nuevas. Si su respondedor es capaz de negociar 100 túneles por segundo, podría establecer este límite en 1000. El demonio entonces descartará los intentos de conexión nuevos si la generación de una respuesta requiriera más de 10 segundos. Si permite un tiempo de respuesta máximo de más de 30 segundos, considere ajustar el tiempo de espera para las IKE_SA en conexión (charon.half_open_timeout). Un respondedor, por defecto, elimina una IKE_SA si el iniciador no la establece en 30 segundos. Bajo alta carga, puede ser necesario un valor más alto.

PRUEBAS DE CARGA

Para realizar pruebas de estabilidad y optimizaciones de rendimiento, el demonio IKE charon proporciona el plugin load-tester. Este plugin permite configurar miles de túneles concurrentemente contra el propio demonio o contra un host remoto.

ADVERTENCIA: Nunca habilite el plugin de pruebas de carga en sistemas productivos. Proporciona credenciales preconfiguradas y permite que un atacante se autentique como cualquier usuario.

Detalles de configuración

Para la autenticación de clave pública, el respondedor utiliza la identidad "CN=srv, OU=load-test, O=strongSwan". Para el iniciador, cada intento de conexión utiliza una identidad diferente en forma "CN=c1-r1, OU=load-test, O=strongSwan", donde el primer número indica el número de cliente, el segundo la ronda de autenticación (si se utilizan múltiples rondas de autenticación).

Para la autenticación PSK, se utilizan identidades FQDN. El servidor utiliza srv.strongswan.org, el cliente utiliza una identidad en forma c1-r1.strongswan.org.

Para la autenticación EAP, el cliente utiliza un NAI en forma 100000000010001@strongswan.org.

Para configurar múltiples rondas de autenticación, concatene múltiples métodos usando, por ejemplo:

initiator_auth = pubkey|psk|eap-md5|eap-aka

El respondedor utiliza un certificado codificado basado en una clave RSA de 1024 bits. Este certificado sirve adicionalmente como certificado CA. Un par utiliza la misma clave privada, pero genera certificados de cliente a demanda firmados por el certificado CA. Instale el certificado del Respondedor/CA en el host remoto para autenticar a todos los clientes.

Para acelerar las pruebas, el plugin load tester implementa una implementación especial de Diffie-Hellman llamada modpnull. Al establecer

proposal = aes128-sha1-modpnull
se utiliza esta implementación DH extremadamente rápida. No proporciona ninguna seguridad en absoluto, pero permite ejecutar pruebas sin la sobrecarga del cálculo DH.

Ejemplos

En el caso más simple, el demonio inicia IKE_SA contra sí mismo utilizando la interfaz de loopback. Esto establecerá en realidad el doble del número de IKE_SA, ya que el demonio es iniciador y respondedor para cada IKE_SA al mismo tiempo. La instalación de SA IPsec fallaría, ya que cada SA se instala dos veces. Para simular el comportamiento correcto, se puede habilitar una interfaz de kernel falsa que no instale las SA IPsec a nivel de kernel.

Una configuración simple de loopback podría verse así:

charon {
	# crear nuevas IKE_SA para cada CHILD_SA para simular
	# diferentes clientes
	reuse_ikesa = no
	# desactivar la protección contra denegación de servicio
	dos_protection = no

DESCRIPCIÓN

El archivo de configuración /etc/strongswan.conf se utiliza para configurar el demonio charon.

La configuración se divide en secciones, cada una configurada mediante claves. Las secciones pueden anidarse hasta un nivel de profundidad arbitrario.

Una entrada de configuración básica es:

key = value

Se permiten comentarios en la configuración, que se indican con un # al principio de la línea.

# esto es un comentario
key = value # esto también es un comentario

Las claves se agrupan en secciones:

section {
	key1 = value1
	key2 = value2

	subsection {
		key3 = value3
	}
}

El demonio charon lee el archivo de configuración en el siguiente orden:

  1. /etc/strongswan.conf
  2. Todos los archivos terminados en .conf en el directorio /etc/strongswan.d/. Los archivos se leen en orden alfabético.

Las últimas definiciones ganan.

SINTAXIS

El archivo de configuración está escrito en formato de texto plano. Los valores pueden ser números enteros, cadenas de texto o booleanos. Las cadenas de texto se pueden especificar entre comillas dobles. Las claves y los valores se separan mediante un signo de igual (=). Las definiciones de claves pueden anidarse en secciones especificadas entre llaves ({ }). Los comentarios se indican con un signo de almohadilla (#).

# Comentario
key_name = value
string_key = "a string value"
section_name {
	nested_key = nested_value
}

Decimal: 1234
Hexadecimal: 0x1234
Octal: 01234
Binario: 0b101010

Los sufijos k, m, g, t y p se pueden utilizar para especificar kilobyte, megabyte, gigabyte, terabyte y petabyte, respectivamente (es decir, las potencias de 1024).

10k = 10240
10m = 10485760

PRUEBAS DE CARGA

El plugin load-tester se puede utilizar para generar carga en el demonio charon.

plugins {
	load-tester {
		# habilita el plugin
		enable = yes
		# usa 4 hilos para iniciar conexiones
		# simultáneamente
		initiators = 4
		# cada hilo inicia 1000 conexiones
		iterations = 1000
		# retardo de cada inicio en cada hilo por 20ms
		delay = 20
		# habilita la interfaz de kernel falsa para
		# evitar conflictos de SA
		fake_kernel = yes
	}
}

Esto iniciará 4000 IKE_SA en 20 segundos. Puede aumentar el valor de retraso si su sistema no puede manejar tanta carga, o disminuirlo para poner más carga en él. Si el demonio comienza a retransmitir mensajes, su sistema probablemente no pueda manejar todos los intentos de conexión.

El plugin también permite probar contra un host remoto. Esto puede ayudar a probar una configuración del mundo real. Una configuración para realizar pruebas de estrés de una pasarela podría verse así:

charon {
	reuse_ikesa = no
	threads = 32
	plugins {
		load-tester {
			enable = yes
			# 10000 conexiones, diez en paralelo
			initiators = 10
			iterations = 1000
			# usa un retraso de 100ms, tiempo total es:
			# iteraciones * retraso = 100s
			delay = 100
			# dirección de la pasarela
			remote = 1.2.3.4
			# propuesta IKE a usar
			proposal = aes128-sha1-modp1024
			# usa autenticación PSK más rápida en lugar
			# de RSA de 1024 bits
			initiator_auth = psk
			responder_auth = psk
			# solicita una IP virtual usando payloads de configuración
			request_virtual_ip = yes
			# habilita CHILD_SA cada 60s
			child_rekey = 60
		}
	}
}

RETRANSMISIÓN IKEv2

Los tiempos de espera de retransmisión en el demonio charon de IKEv2 se pueden configurar globalmente utilizando las tres claves que se enumeran a continuación:

charon.retransmit_base [1.8]
charon.retransmit_timeout [4.0]
charon.retransmit_tries [5]
charon.retransmit_jitter [0]
charon.retransmit_limit [0]

Se utiliza el siguiente algoritmo para calcular el tiempo de espera:

tiempo relativo de retransmisión = retransmit_timeout * retransmit_base ^ (n-1)

Donde n es el recuento actual de retransmisiones. El tiempo de espera calculado no puede exceder el límite de retransmisión configurado (si existe), lo cual es útil si el número de reintentos es alto.

Si se configura una fluctuación en porcentaje, el tiempo de espera se modifica de la siguiente manera:

tiempo relativo de retransmisión -= aleatorio(0, retransmit_jitter * tiempo relativo de retransmisión)
