stunnel(8) Proxy TLS stunnel stunnel(8)

NOMBRE

stunnel - Proxy de descarga y balanceo de carga TLS

SINOPSIS

Unix:
stunnel [ARCHIVO] | -fd N | -help | -version | -sockets | -options
WIN32:
stunnel [ [ -install | -uninstall | -start | -stop |
-reload | -reopen | -exit ] [-quiet] [ARCHIVO] ] |
-help | -version | -sockets | -options

DESCRIPCIÓN

El programa stunnel está diseñado para funcionar como un envoltorio de cifrado TLS entre clientes remotos y servidores locales (arrancables por inetd) o remotos. El concepto es que, al tener demonios no compatibles con TLS ejecutándose en tu sistema, puedes configurarlos fácilmente para que se comuniquen con los clientes a través de canales TLS seguros.

stunnel se puede utilizar para agregar funcionalidad TLS a demonios Inetd de uso común como servidores POP-2, POP-3 e IMAP, a demonios independientes como NNTP, SMTP y HTTP, y para tunelizar PPP a través de sockets de red sin cambios en el código fuente.

Este producto incluye software criptográfico escrito por Eric Young (eay@cryptsoft.com)

ARCHIVO DE CONFIGURACIÓN

Cada línea del archivo de configuración puede ser:

  • Una línea vacía (ignorada).
  • Un comentario que comienza con ';' (ignorado).
  • Un par 'nombre_opción = valor_opción'.
  • '[nombre_servicio]' indicando el inicio de una definición de servicio.

Un parámetro de dirección de una opción puede ser:

  • Un número de puerto.
  • Un par separado por dos puntos de dirección IP (IPv4, IPv6 o nombre de dominio) y número de puerto.
  • Una ruta de socket de Unix (solo Unix).

OPCIONES GLOBALES

chroot = DIRECTORIO (solo Unix)
directorio para hacer chroot al proceso stunnel

chroot mantiene stunnel en una cárcel de chroot. CApath, CRLpath, pid y exec se encuentran dentro de la cárcel y los parches deben ser relativos al directorio especificado con chroot.

Varias funciones del sistema operativo también necesitan que sus archivos se ubiquen dentro de la cárcel de chroot, por ejemplo:

  • El resolvedor retardado típicamente necesita /etc/nsswitch.conf y /etc/resolv.conf.
  • La hora local en los archivos de registro necesita /etc/timezone.
  • Otras funciones pueden necesitar dispositivos, por ejemplo, /dev/zero o /dev/null.
compression = deflate | zlib
seleccionar algoritmo de compresión de datos

predeterminado: sin compresión

Deflate es el método de compresión estándar descrito en RFC 1951.

debug = [INSTALACIÓN.]NIVEL
nivel de depuración

El nivel es uno de los nombres o números de nivel de syslog: emerg (0), alert (1), crit (2), err (3), warning (4), notice (5), info (6), o debug (7). Se mostrarán todos los registros para el nivel especificado y todos los niveles numéricamente inferiores a él.

El nivel de registro debug (o el equivalente <debug = 7>) produce una salida de registro muy detallada. Este nivel de registro solo está destinado a ser entendido por los desarrolladores de stunnel, y no por los usuarios. Por favor, utiliza el nivel de depuración cuando se te solicite por un desarrollador de stunnel, o cuando intentes confundirte.

El nivel de registro predeterminado es notice (5).

Se utilizará la instalación de syslog 'daemon' a menos que se proporcione un nombre de instalación. (Las instalaciones no son compatibles en Win32).

Se ignora la distinción entre mayúsculas y minúsculas tanto para las instalaciones como para los niveles.

EGD = RUTA_EGD (solo Unix)
ruta al socket del demonio de recolección de entropía

Socket del demonio de recolección de entropía a utilizar para alimentar el generador de números aleatorios de OpenSSL.

engine = auto | ID_ENGINE
seleccionar motor criptográfico de hardware o software

predeterminado: criptografía solo de software

Consulta la sección de Ejemplos para una configuración de motor que utilice el certificado y la clave privada correspondiente de un dispositivo criptográfico.

engineCtrl = COMANDO[:PARÁMETRO]
controlar el motor de hardware
engineDefault = LISTA_TAREAS
establecer tareas de OpenSSL delegadas al motor actual

El parámetro especifica una lista separada por comas de tareas a delegar al motor actual.

Las siguientes tareas pueden estar disponibles, si son admitidas por el motor: ALL, RSA, DSA, ECDH, ECDSA, DH, RAND, CIPHERS, DIGESTS, PKEY, PKEY_CRYPTO, PKEY_ASN1.

fips = sí | no
habilitar o deshabilitar el modo FIPS 140-2.

Esta opción te permite deshabilitar la entrada al modo FIPS si stunnel fue compilado con soporte FIPS 140-2.

predeterminado: no (desde la versión 5.00)

foreground = sí | quiet | no (solo Unix)
modo de primer plano

Permanecer en primer plano (no bifurcar).

Con el parámetro sí, también registra en stderr además de los destinos especificados con syslog y output.

predeterminado: en segundo plano en modo demonio

iconActive = ARCHIVO_ICONO (solo GUI)
icono de la GUI que se mostrará cuando haya conexiones establecidas

En la plataforma Windows, el parámetro debe ser un archivo .ico que contenga una imagen de 16x16 píxeles.

iconError = ARCHIVO_ICONO (solo GUI)
icono de la GUI que se mostrará cuando no haya ninguna configuración válida cargada

En la plataforma Windows, el parámetro debe ser un archivo .ico que contenga una imagen de 16x16 píxeles.

iconIdle = ARCHIVO_ICONO (solo GUI)
icono de la GUI que se mostrará cuando no haya conexiones establecidas

En la plataforma Windows, el parámetro debe ser un archivo .ico que contenga una imagen de 16x16 píxeles.

log = appen

(No se proporciona la parte restante de esta sección en el texto original).

d | overwrite
manejo de archivos de registro

Esta opción te permite elegir si el archivo de registro (especificado con la opción output) se añade o se sobrescribe al abrirse o reabrirse.

predeterminado: append (añadir)

output = FILE
añadir mensajes de registro a un archivo

Se puede usar el dispositivo /dev/stdout para enviar mensajes de registro a la salida estándar (por ejemplo, para registrarlos con splogger de daemontools).

pid = FILE (solo Unix)
ubicación del archivo pid

Si el argumento está vacío, no se creará ningún archivo pid.

La ruta pid es relativa al directorio chroot si se especifica.

provider = ID_PROVEEDOR
Especifica el identificador del proveedor a utilizar. ID_PROVEEDOR es un identificador único que hace referencia a un servicio criptográfico específico.

Esta opción requiere OpenSSL 3.0 o posterior.

providerParameter = ID_PROVEEDOR:PARAMETRO=VALOR
Establece un parámetro específico para el proveedor dado. ID_PROVEEDOR identifica el proveedor, PARAMETRO es el nombre del parámetro y VALOR es su valor. Esta opción permite la personalización de la configuración del proveedor de servicios criptográficos seleccionado.

Esta opción requiere OpenSSL 3.5 o posterior.

RNDbytes = BYTES
bytes a leer de los archivos de semilla aleatoria
RNDfile = ARCHIVO
ruta al archivo con datos de semilla aleatoria

La biblioteca OpenSSL utilizará primero los datos de este archivo para sembrar el generador de números aleatorios.

RNDoverwrite = yes | no
sobrescribir los archivos de semilla aleatoria con nuevos datos aleatorios

predeterminado: yes (sí)

service = SERVICIO (solo Unix)
nombre del servicio stunnel

El nombre del servicio especificado se utiliza para syslog y como el nombre del servicio en modo inetd para TCP Wrappers. Aunque esta opción se puede especificar técnicamente en las secciones de servicio, solo es útil en las opciones globales.

predeterminado: stunnel

setEnv = NOMBRE_VAR=VALOR
Cambia o añade una variable de entorno para los procesos hijos. Si NOMBRE_VAR ya existe, su valor se actualizará; de lo contrario, se creará una nueva variable. Esta modificación se aplica solo a los procesos hijos iniciados y no afecta al entorno actual.
syslog = yes | no (solo Unix)
habilitar el registro a través de syslog

predeterminado: yes (sí)

taskbar = yes | no (solo WIN32)
habilitar el icono de la barra de tareas

predeterminado: yes (sí)

OPCIONES DE NIVEL DE SERVICIO

Cada sección de configuración comienza con un nombre de servicio entre corchetes. El nombre del servicio se utiliza para el control de acceso de libwrap (TCP Wrappers) y te permite distinguir los servicios de stunnel en tus archivos de registro.

Ten en cuenta que si deseas ejecutar stunnel en modo inetd (donde se le proporciona un socket de red un servidor como inetd, xinetd o tcpserver), deberías leer la sección titulada MODO INETD más abajo.

accept = [HOST:]PUERTO
aceptar conexiones en la dirección especificada

Si no se especifica host, se utilizan por defecto todas las direcciones IPv4 del host local.

Para escuchar en todas las direcciones IPv6, utiliza:

accept = :::PUERTO
CAengine = IDENTIFICADOR_DE_CERTIFICADO_CA_ESPECIFICO_DEL_ENGINE
cargar un certificado de CA de confianza desde un engine

Los certificados de CA cargados se utilizarán con las opciones verifyChain y verifyPeer.

Se permiten múltiples opciones CAengine en una sola sección de servicio.

Engines actualmente soportados: pkcs11, cng.

CApath = DIRECTORIO_CA
cargar certificados de CA de confianza desde un directorio

Los certificados de CA cargados se utilizarán con las opciones verifyChain y verifyPeer. Ten en cuenta que los certificados en este directorio deben llamarse XXXXXXXX.0, donde XXXXXXXX es el valor hash del sujeto codificado en DER del certificado.

Este parámetro también se puede utilizar para proporcionar el certificado raíz de CA necesario para validar el stapling OCSP en modo servidor.

El algoritmo hash se ha cambiado en OpenSSL 1.0.0. Es requerido hacer c_rehash al directorio al actualizar de OpenSSL 0.x.x a OpenSSL 1.x.x o posterior.

La ruta CApath es relativa al directorio chroot si se especifica.

CAfile = ARCHIVO_CA
cargar certificados de CA de confianza desde un archivo

Los certificados de CA cargados se utilizarán con las opciones verifyChain y verifyPeer.

Este parámetro también se puede utilizar para proporcionar el certificado raíz de CA necesario para validar el stapling OCSP en modo servidor.

CAstore = URI_CA
cargar certificados de CA de confianza desde un recurso especificado por una URI

Esta opción permite cargar certificados de CA desde una fuente externa compatible con el framework OSSL_STORE, como un módulo PKCS#11 (por ejemplo, token de hardware), el almacén de certificados del sistema o un recurso remoto.

Esta opción se puede usar independientemente de CAfile y CAdir, y de manera similar proporciona certificados utilizados por verifyChain o verifyPeer, así como para validar el stapling OCSP en modo servidor.

Esta opción requiere OpenSSL 3.0 o posterior.

cert = ARCHIVO_CERT | URI
nombre del archivo de cadena de certificados

El parámetro especifica el archivo que contiene los certificados utilizados por stunnel para autenticarse frente al cliente o servidor remoto. El archivo debe contener toda la cadena de certificados, comenzando desde el certificado real del servidor/cliente y terminando con el certificado raíz de CA autofirmado. El archivo debe estar en formato PEM o P12.

Se requiere una cadena de certificados en modo servidor, y es opcional en modo cliente.

La opción cert se puede especificar varias veces. El primer certificado encontrado se utiliza como certificado de servidor o cliente, mientras que los certificados subsiguientes se tratan como elementos intermedios de la cadena. Esta funcionalidad requiere la versión 1.0.2 de OpenSSL o posterior.

Este parámetro también se utiliza como identificador de certificado (URI PKCS#11) cuando se habilita un engine o proveedor de hardware.

Nota: El proveedor requiere OpenSSL 3.0 o posterior

checkEmail = EMAIL
verificar la dirección de correo electrónico del sujeto del certificado del par de extremo (hoja)

Se aceptan certificados si no se especificaron comprobaciones de sujeto, o si la dirección de correo electrónico del certificado del par de extremo (hoja) coincide con alguna de las direcciones de correo electrónico especificadas con checkEmail.

Se permiten múltiples opciones checkEmail en una sola sección de servicio.

Esta opción requiere OpenSSL 1.0.2 o posterior.

checkHost = HOST
verificar el host del sujeto del certificado del par de extremo (hoja)

Se aceptan certificados si no se especificaron comprobaciones de sujeto, o si el nombre de host del certificado del par de extremo (hoja) coincide con alguno de los hosts especificados con checkHost.

Se permiten múltiples opciones checkHost en una sola sección de servicio.

Esta opción requiere OpenSSL 1.0.2 o posterior.

checkIP = IP
verificar la dirección IP del sujeto del certificado del par de extremo (hoja)

Se aceptan certificados si no se especificaron comprobaciones de sujeto, o si la dirección IP del certificado del par de extremo (hoja) coincide con alguna de las direcciones IP especificadas con checkIP.

Se permiten múltiples opciones checkIP en una sola sección de servicio.

Esta opción requiere OpenSSL 1.0.2 o posterior.

ciphers = LISTA_CIFRADOS
seleccionar cifrados TLS permitidos (TLSv1.2 y anteriores)

Esta opción no afecta a los suits de cifrado TLSv1.3.

Una lista separada por dos puntos de los cifrados a permitir en la conexión TLS, por ejemplo DES-CBC3-SHA:IDEA-CBC-MD5.

ciphersuites = LISTA_SUITES_CIFRADO
seleccionar suits de cifrado TLSv1.3 permitidos

Una lista separada por dos puntos de los nombres de suits de cifrado TLSv1.3 en orden de preferencia.

La opción ciphersuites ignora los cifrados desconocidos cuando se compila con OpenSSL 3.0 o posterior.

Esta opción requiere OpenSSL 1.1.1 o posterior.

predeterminado: TLS_CHACHA20_POLY1305_SHA256:TLS_AES_256_GCM_SHA384:TLS_AES_128_GCM_SHA256

client = yes | no
modo cliente (servicio remoto usa TLS)

predeterminado: no (modo servidor)

config = COMANDO[:PARAMETRO]
comando de configuración de OpenSSL

El comando de configuración de OpenSSL se ejecuta con el parámetro especificado. Esto permite invocar cualquier comando de configuración desde el archivo de configuración de stunnel. Los comandos soportados se describen en la página del manual SSL_CONF_cmd(3ssl).

Se pueden usar varias líneas config para especificar múltiples comandos de configuración.

Utiliza la opción curves en lugar de habilitar config = Curves:list_curves para soportar curvas elípticas.

Esta opción requiere OpenSSL 1.0.2 o posterior.

connect = [HOST:]PUERTO
conectarse a una dirección remota

Si no se especifica host, el host por defecto es localhost.

Se permiten múltiples opciones de connect en una única sección de servicio. Si el host se resuelve a múltiples direcciones y/o si se especifican múltiples opciones de connect, entonces la dirección remota se elige utilizando un algoritmo de ronda.

CRLpath = DIRECTORIO
Directorio de listas de revocación de certificados

Este es el directorio en el que stunnel buscará CRLs cuando use las opciones verifyChain y verifyPeer. Tenga en cuenta que las CRLs en este directorio deben llamarse XXXXXXXX.r0 donde XXXXXXXX es el valor hash de la CRL.

El algoritmo de hash ha sido cambiado en OpenSSL 1.0.0. Se requiere rehacer el hash del directorio en la actualización de OpenSSL 0.x.x a OpenSSL 1.x.x.

La ruta CRLpath es relativa al directorio chroot si se especifica.

CRLfile = ARCHIVO_CRL
Archivo de listas de revocación de certificados

Este archivo contiene múltiples CRLs, utilizadas con las opciones verifyChain y verifyPeer.

curves = lista
Curvas ECDH separadas con ':'

Solo se permite un nombre de curva para OpenSSL anterior a 1.1.1.

Para obtener una lista de curvas soportadas use:

openssl ecparam -list_curves

por defecto:

X25519:P-256:X448:P-521:P-384 (OpenSSL 1.1.1 o posterior)
prime256v1 (OpenSSL anterior a 1.1.1)
logId = TIPO
Tipo de identificador de conexión

Este identificador le permite distinguir las entradas de registro generadas para cada una de las conexiones.

Tipos soportados actualmente:

sequential
El identificador secuencial numérico solo es único dentro de una única instancia de stunnel, pero muy compacto. Es muy útil para el análisis manual de registros.
unique
Este identificador alfanumérico es globalmente único, pero más largo que el número secuencial. Es muy útil para el análisis automatizado de registros.
thread
El identificador de hilo del sistema operativo no es ni único (incluso dentro de una sola instancia de stunnel) ni corto. Es muy útil para depurar problemas de software o configuración.
process
El identificador de proceso del sistema operativo (PID) puede ser útil en el modo inetd.

por defecto: sequential

debug = NIVEL
Nivel de depuración

Nivel es uno de los nombres o números de nivel de syslog: emerg (0), alert (1), crit (2), err (3), warning (4), notice (5), info (6), o debug (7). Se mostrarán todos los registros para el nivel especificado y todos los niveles numéricamente inferiores a él. El valor por defecto es notice (5).

Si bien el nivel debug = debug o debug = 7 genera la salida más detallada, solo está destinado a ser utilizado por los desarrolladores de stunnel. Por favor, solo use este valor si es un desarrollador, o si tiene la intención de enviar sus registros a nuestro soporte técnico. De lo contrario, los registros generados serán confusos.

delay = sí | no
Retrasar la resolución DNS para la opción connect

Esta opción es útil para DNS dinámico, o cuando el DNS no está disponible durante el inicio de stunnel (VPN de guerrero de carretera, configuraciones de módem)

El modo de resolución retrasada se activa automáticamente cuando stunnel no puede resolver en el inicio ninguno de los objetivos de connect para un servicio.

El resolvedor retrasado inflige failover = prio.

por defecto: no

engineId = ID_MOTOR
Seleccionar ID de motor para el servicio
engineNum = NUMERO_MOTOR
Seleccionar número de motor para el servicio

Los motores se numeran a partir de 1.

exec = RUTA_EJECUTABLE
Ejecutar un programa local tipo inetd

La ruta exec es relativa al directorio chroot si se especifica.

Las siguientes variables de entorno se establecen en plataformas Unix: REMOTE_HOST, REMOTE_PORT, SSL_CLIENT_DN, SSL_CLIENT_I_DN.

execArgs = $0 $1 $2 ...
Argumentos para exec incluyendo el nombre del programa ($0)

Actualmente no se admite el uso de comillas. Los argumentos se separan con una cantidad arbitraria de espacios en blanco.

failover = rr | prio
Estrategia de failover para múltiples destinos de "connect".
rr
ronda robin - distribución de carga equitativa
prio
prioridad - usar el orden especificado en el archivo de configuración

por defecto: prio

ident = NOMBRE_USUARIO
Usar verificación de nombre de usuario IDENT (RFC 1413)
include = DIRECTORIO
Incluir todas las partes del archivo de configuración ubicadas en DIRECTORIO

Los archivos se incluyen en orden alfabético ascendente de sus nombres. La convención de nombres de archivo recomendada es

para opciones globales:

00-global.conf

para opciones locales a nivel de servicio:

01-service.conf
02-service.conf
key = ARCHIVO_CLAVE | URI
Clave privada para el certificado especificado con la opción cert

Se necesita una clave privada para autenticar al propietario del certificado. Dado que este archivo debe mantenerse en secreto, solo debería ser legible por su propietario. En sistemas Unix, puede usar el siguiente comando:

chmod 600 keyfile

Este parámetro también se utiliza como identificador de clave privada (URI PKCS#11) cuando se habilita un motor o proveedor de hardware.

Nota: El proveedor requiere OpenSSL 3.0 o posterior

por defecto: el valor de la opción cert

libwrap = sí | no
Habilitar o deshabilitar el uso de /etc/hosts.allow y /etc/hosts.deny.

por defecto: no (desde la versión 5.00)

local = HOST
Por defecto, la dirección IP de la interfaz de salida se utiliza como origen para las conexiones remotas. Utilice esta opción para vincular una dirección IP local estática en su lugar.
OCSP = URL
Seleccionar respondedor OCSP para la verificación del certificado del par entidad final (hoja)
OCSPaia = sí | no
Validar certificados con sus respondedores OCSP AIA

Esta opción permite a stunnel validar certificados con la lista de URLs de respondedores OCSP recuperadas de su extensión AIA (Authority Information Access).

OCSPflag = BANDERA_OCSP
Especificar bandera del respondedor OCSP

Varias OCSPflag pueden usarse para especificar múltiples banderas.

banderas soportadas actualmente: NOCERTS, NOINTERN, NOSIGS, NOCHAIN, NOVERIFY, NOEXPLICIT, NOCASIGN, NODELEGATED, NOCHECKS, TRUSTOTHER, RESPID_KEY, NOTIME

OCSPnonce = sí | no
Enviar y verificar la extensión nonce OCSP

Esta opción protege el protocolo OCSP contra ataques de repetición. Debido a su sobrecarga computacional, la extensión nonce generalmente solo se soporta en respondedores internos (por ejemplo, corporativos) y no en respondedores OCSP públicos.

OCSPrequire = sí | no
Requerir una respuesta OCSP concluyente

Desactive esta opción para permitir una conexión incluso si no se recuperó una respuesta OCSP concluyente del apilamiento y una solicitud directa al respondedor OCSP.

por defecto: sí

options = OPCIONES_SSL
Opciones de la biblioteca OpenSSL

El parámetro es el nombre de la opción OpenSSL como se describe en el manual de SSL_CTX_set_options(3ssl), pero sin el prefijo SSL_OP_. stunnel -options lista las opciones que se encontraron permitidas en la combinación actual de stunnel y la biblioteca OpenSSL utilizada para construirlo.

Se pueden usar varias líneas de option para especificar múltiples opciones. Un nombre de opción puede ir precedido por un guion ("-") para deshabilitar la opción.

Por ejemplo, para compatibilidad con la errónea implementación TLS de Eudora, se puede usar la siguiente opción:

options = DONT_INSERT_EMPTY_FRAGMENTS

por defecto:

options = NO_SSLv2
options = NO_SSLv3

Use la opción sslVersionMax o sslVersionMin en lugar de deshabilitar versiones de protocolo TLS específicas cuando se compila con OpenSSL 1.1.0 o posterior.

protocol = PROTO
Protocolo de aplicación para negociar TLS

Esta opción habilita la negociación inicial específica del protocolo de la encriptación TLS. La opción protocol no debe utilizarse con encriptación TLS en un puerto separado.

Protocolos actualmente soportados:

cifs
Extensión propietaria (no documentada) del protocolo CIFS implementada en Samba. El soporte para esta extensión se eliminó en Samba 3.0.0.
capwin
Soporte de aplicación http://www.capwin.org/
capwinctrl
http://www.capwin.org/ soporte de aplicaciones

Este protocolo solo se admite en modo cliente.

connect
Basado en RFC 2817 - Upgrading to TLS Within HTTP/1.1, sección 5.2 - Requesting a Tunnel with CONNECT

Este protocolo solo se admite en modo cliente.

imap
Basado en RFC 2595 - Using TLS with IMAP, POP3 and ACAP
ldap
Basado en RFC 2830 - Lightweight Directory Access Protocol (v3): Extension for Transport Layer Security
nntp
Basado en RFC 4642 - Using Transport Layer Security (TLS) with Network News Transfer Protocol (NNTP)

Este protocolo solo se admite en modo cliente.

pgsql
Basado en http://www.postgresql.org/docs/8.3/static/protocol-flow.html#AEN73982
pop3
Basado en RFC 2449 - POP3 Extension Mechanism
proxy
Paso de la dirección IP original del cliente con el protocolo PROXY de HAProxy, versión 1 https://www.haproxy.org/download/1.8/doc/proxy-protocol.txt
smtp
Basado en RFC 2487 - SMTP Service Extension for Secure SMTP over TLS
socks
Se admiten las versiones 4, 4a y 5 de SOCKS. El propio protocolo SOCKS está encapsulado dentro de la capa de cifrado TLS para proteger la dirección de destino final.

http://www.openssh.com/txt/socks4.protocol

http://www.openssh.com/txt/socks4a.protocol

El comando BIND del protocolo SOCKS no se admite. El parámetro USERID se ignora.

securityLevel = LEVEL
establecer el nivel de seguridad

El significado de cada nivel se describe a continuación:

level 0
Se permite todo.
level 1
El nivel de seguridad corresponde a un mínimo de 80 bits de seguridad. Cualquier parámetro que ofrezca menos de 80 bits de seguridad está excluido. Como resultado, se prohíben las claves RSA, DSA y DH de menos de 1024 bits y las claves ECC de menos de 160 bits. Todas las suites de cifrado de exportación están prohibidas ya que todas ofrecen menos de 80 bits de seguridad. SSL versión 2 está prohibida. Cualquier suite de cifrado que utilice MD5 para la MAC también está prohibida. Además, SSLv3, TLS 1.0 y TLS 1.1 están deshabilitados para OpenSSL 3.0 y posteriores.
level 2
Nivel de seguridad establecido en 112 bits de seguridad. Como resultado, se prohíben las claves RSA, DSA y DH de menos de 2048 bits y las claves ECC de menos de 224 bits. Además de las exclusiones del nivel 1, cualquier suite de cifrado que utilice RC4 también está prohibida. La compresión está deshabilitada. SSL versión 3 tampoco está permitido para OpenSSL anterior a 3.0.
level 3
Nivel de seguridad establecido en 128 bits de seguridad. Como resultado, se prohíben las claves RSA, DSA y DH de menos de 3072 bits y las claves ECC de menos de 256 bits. Además de las exclusiones del nivel 2, se prohíben las suites de cifrado que no ofrezcan secreto directo. Las entradas de sesión están deshabilitadas. Las versiones TLS anteriores a 1.1 no están permitidas para OpenSSL anteriores a 3.0.
level 4
Nivel de seguridad establecido en 192 bits de seguridad. Como resultado, se prohíben las claves RSA, DSA y DH de menos de 7680 bits y las claves ECC de menos de 384 bits. Se prohíben las suites de cifrado que utilizan SHA1 para la MAC. Las versiones TLS anteriores a 1.2 no están permitidas para OpenSSL anteriores a 3.0.
level 5
Nivel de seguridad establecido en 256 bits de seguridad. Como resultado, se prohíben las claves RSA, DSA y DH de menos de 15360 bits y las claves ECC de menos de 512 bits.
predeterminado: 2

La opción securityLevel solo está disponible cuando se compila con OpenSSL 1.1.0 y posteriores.

VALOR DE RETORNO

stunnel devuelve cero en caso de éxito, distinto de cero en caso de error.

SEÑALES

Las siguientes señales se pueden utilizar para controlar stunnel en un entorno Unix:

SIGHUP
Fuerza la recarga del archivo de configuración.

Algunas opciones globales no se recargarán:

  • chroot
  • foreground
  • pid
  • setgid
  • setuid

El uso de la opción 'setuid' también evitará que stunnel se vincule a puertos privilegiados (<1024) durante la recarga de la configuración.

Cuando se utiliza la opción 'chroot', stunnel buscará todos sus archivos (incluido el archivo de configuración, certificados, el archivo de registro y el archivo pid) dentro de la jail de chroot.

SIGUSR1
Cierra y reabre el archivo de registro de stunnel. Esta función se puede utilizar para la rotación de registros.
SIGUSR2
Registra la lista de conexiones activas.
SIGTERM, SIGQUIT, SIGINT
Apaga stunnel.

El resultado de enviar cualquier otra señal al servidor no está definido.

EJEMPLOS

Para proporcionar encapsulación TLS a su servicio local de imapd, utilice:

[imapd]
accept = 993
exec = /usr/sbin/imapd
execArgs = imapd

o en modo remoto:

[imapd]
accept = 993
connect = 143

Para permitir que su cliente de correo local se conecte a un servicio imapd habilitado para TLS en otro servidor, configure el cliente de correo para que se conecte a localhost en el puerto 119 y utilice:

[imap]
client = yes
accept = 143
connect = servername:993

Si desea proporcionar túnel a su demonio pppd en el puerto 2020, utilice algo como:

[vpn]
accept = 2020
exec = /usr/sbin/pppd
execArgs = pppd local
pty = yes

Si desea utilizar stunnel en modo inetd para iniciar su proceso imapd, utilizaría esta stunnel.conf. Tenga en cuenta que no debe haber ninguna sección [nombre_servicio].

exec = /usr/sbin/imapd
execArgs = imapd

Para configurar una VPN SOCKS, configure el siguiente servicio cliente:

[socks_client]
client = yes
accept = 127.0.0.1:1080
connect = vpn_server:9080
verifyPeer = yes
CAfile = stunnel.pem

La configuración correspondiente en el host vpn_server:

[socks_server]
protocol = socks
accept = 9080
cert = stunnel.pem
key = stunnel.key

Ahora pruebe su configuración en la máquina cliente con:

curl --socks4a localhost http://www.example.com/

[sni2]

NOTAS

RESTRICCIONES

stunnel no se puede utilizar para el demonio FTP debido a la naturaleza del protocolo FTP, que utiliza múltiples puertos para las transferencias de datos. Sin embargo, existen versiones habilitadas para TLS de los demonios FTP y telnet.

MODO INETD

El uso más común de stunnel es escuchar en un puerto de red y establecer comunicación con un nuevo puerto a través de la opción connect, o con un nuevo programa a través de la opción exec. Sin embargo, hay un caso especial cuando se desea que otro programa acepte conexiones entrantes y ejecute stunnel, por ejemplo con inetd, xinetd, o tcpserver.

Por ejemplo, si tiene la siguiente línea en inetd.conf:

imaps stream tcp nowait root /usr/bin/stunnel stunnel /etc/stunnel/imaps.conf

En estos casos, el programa de estilo inetd es responsable de vincular un socket de red (imaps arriba) y entregárselo a stunnel cuando se recibe una conexión. Por lo tanto, no desea que stunnel tenga ninguna opción accept. Todas las Opciones de Nivel de Servicio deben colocarse en la sección de opciones globales, y no habrá ninguna sección [nombre_servicio]. Consulte la sección EJEMPLOS para ver ejemplos de configuración.

CERTIFICADOS

Cada demonio habilitado para TLS necesita presentar un certificado X.509 válido al par. También necesita una clave privada para descifrar los datos entrantes. La forma más fácil de obtener un certificado y una clave es generarlos con el paquete gratuito OpenSSL. Puede encontrar más información sobre la generación de certificados en las páginas que se enumeran a continuación.

El archivo .pem debe contener la clave privada sin cifrar y un certificado firmado (no una solicitud de certificado). Por lo tanto, el archivo debería tener este aspecto:

-----BEGIN RSA
-----BEGIN PRIVATE KEY-----
[clave codificada]
-----END PRIVATE KEY-----
-----BEGIN CERTIFICATE-----
[certificado codificado]
-----END CERTIFICATE-----

ALEATORIEDAD

stunnel necesita sembrar el PRNG (generador de números pseudoaleatorios) para que TLS use una buena aleatoriedad. Las siguientes fuentes se cargan en orden hasta que se hayan recopilado suficientes datos aleatorios:

  • El archivo especificado con el flag RNDfile.
  • El archivo especificado por la variable de entorno RANDFILE, si está establecida.
  • El archivo .rnd en tu directorio de inicio, si RANDFILE no está establecido.
  • El archivo especificado con '--with-random' en el momento de la compilación.
  • El contenido de la pantalla si se ejecuta en Windows.
  • El socket EGD especificado con el flag EGD.
  • El socket EGD especificado con '--with-egd-sock' en el momento de la compilación.
  • El dispositivo /dev/urandom.

Ten en cuenta que en máquinas Windows que no tienen interacción del usuario de consola (movimientos del ratón, creación de ventanas, etc.), el contenido de la pantalla no es lo suficientemente variable como para ser suficiente, y debes proporcionar un archivo aleatorio para usar con el flag RNDfile.

Ten en cuenta que el archivo especificado con el flag RNDfile debe contener datos aleatorios, lo que significa que debe contener información diferente cada vez que se ejecuta stunnel. Esto se maneja automáticamente a menos que se utilice el flag RNDoverwrite. Si deseas actualizar este archivo manualmente, el comando openssl rand en versiones recientes de OpenSSL sería útil.

Nota importante: Si /dev/urandom está disponible, OpenSSL a menudo lo usa para sembrar el PRNG mientras verifica el estado aleatorio. En sistemas con /dev/urandom, OpenSSL probablemente lo usará a pesar de estar listado al final de la lista anterior. Este es el comportamiento de OpenSSL y no de stunnel.

PARÁMETROS DH

stunnel 4.40 y posteriores contienen parámetros DH de 2048 bits codificados. A partir de stunnel 5.18, estos parámetros DH codificados se reemplazan cada 24 horas con parámetros DH temporales autogenerados. La generación de parámetros DH puede llevar varios minutos.

Alternativamente, es posible especificar parámetros DH estáticos en el archivo del certificado, lo que deshabilita la generación de parámetros DH temporales:

openssl dhparam 2048 >> stunnel.pem
