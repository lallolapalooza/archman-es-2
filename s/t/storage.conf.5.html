NOMBRE

storage.conf - Archivo de configuración para el gestor de almacenamiento

DESCRIPCIÓN

El archivo ruta/etc/storage.conf contiene las reglas a utilizar en la asignación de artículos a diferentes métodos de almacenamiento. Estas reglas determinan dónde se almacenarán los artículos entrantes.

El gestor de almacenamiento es una interfaz unificada entre INN y una variedad de diferentes métodos de almacenamiento, permitiendo al administrador de noticias elegir entre diferentes métodos de almacenamiento con diferentes compromisos (o incluso usar varios al mismo tiempo para diferentes grupos de noticias, o artículos de diferentes tamaños). El resto de INN no necesita saber qué tipo de método de almacenamiento se utilizó para un artículo dado; el gestor de almacenamiento lo determinará automáticamente cuando se recupere ese artículo a través de la API de almacenamiento. Tenga en cuenta que también puede desear consultar las opciones proporcionadas en inn.conf(5) con respecto al almacenamiento de artículos.

El archivo storage.conf consta de una serie de entradas de método de almacenamiento. Las líneas en blanco y las líneas que comienzan con un signo de número ("#") se ignoran. El número máximo de caracteres en cada línea es 255. El orden de las entradas en este archivo es importante, ver más abajo.

Cada entrada especifica un método de almacenamiento y un conjunto de reglas. Los artículos que coincidan con todas las reglas de una entrada de método de almacenamiento se almacenarán utilizando ese método de almacenamiento; si un artículo coincide con varias entradas de método de almacenamiento, se utilizará la primera.

método <nombre_método> {
    newsgroups: <comodín>
    clase: <clase_almacenamiento>
    tamaño: <tamañomín>[,<tamañomáx>]
    expira: <tiemposin>[,<tiemposin>]
    opciones: <opciones>
    coincidirexacta: <bool>
    filtrado: <bool>
    ruta: <comodín>
}

Si los espacios o tabulaciones se incluyen en un valor, dicho valor debe ir entre comillas dobles (""). Si un signo de número ("#") o una comilla doble se deben incluir literalmente en un valor, deben escaparse con "\".

<nombre_método> es el nombre de un método de almacenamiento a usar para los artículos que coincidan con las reglas de esta entrada. Los métodos de almacenamiento actualmente disponibles son:

cnfs
timecaf
timehash
tradspool
trash

Consulte la sección "MÉTODOS DE ALMACENAMIENTO" a continuación para obtener más detalles.

Los significados de las claves en cada entrada de método de almacenamiento son los siguientes:

newsgroups: <comodín>
Qué grupos de noticias se almacenan utilizando este método de almacenamiento. <comodín> es un patrón uwildmat que se compara con los grupos de noticias a los que se publica un artículo. Si storeonxref en inn.conf es verdadero, este patrón se comparará con los nombres de los grupos de noticias en el cuerpo del encabezado Xref; de lo contrario, se comparará con los nombres de los grupos de noticias en el cuerpo del encabezado Newsgroups (consulte inn.conf(5) para la discusión de las diferencias entre estas posibilidades). Se permiten expresiones comodín de envenenamiento (expresiones que comienzan con "@") y se pueden usar para excluir ciertos patrones de grupo: los artículos publicados en varios grupos de noticias en grupos envenenados no se almacenarán utilizando este método de almacenamiento. El patrón <comodín> se compara en orden.

No hay un patrón de grupos de noticias predeterminado; si una entrada debe coincidir con todos los grupos de noticias, use un explícito "newsgroups: *".

clase: <clase_almacenamiento>
Un identificador para esta entrada de método de almacenamiento. <clase_almacenamiento> debe ser un número entre 0 y 255. Debe ser único en todas las entradas de este archivo. Se utiliza principalmente para especificar los tiempos de expiración por clase de almacenamiento como se describe en expire.ctl(5); "timehash" y "timecaf" también establecerán el directorio de nivel superior en el que se almacenarán los artículos aceptados por esta clase de almacenamiento. Las clases de almacenamiento pueden, por ejemplo, numerarse secuencialmente en storage.conf.

La asignación de un número particular a una clase de almacenamiento es arbitraria pero permanente (ya que se utiliza en los tokens de almacenamiento). De hecho, a un artículo se le asigna una clase de almacenamiento según las reglas de almacenamiento vigentes en el momento de su llegada. Este identificador no cambiará, incluso si storage.conf se modifica posteriormente y el mismo artículo se hubiera asignado a otra clase de almacenamiento, si hubiera sido recibido después de ese cambio. El artículo sigue siendo perfectamente válido y recuperable. La única diferencia será para la expiración con groupbaseexpiry establecido en falso en inn.conf: las reglas en expire.ctl se aplican a la clase de almacenamiento asignada a los artículos en su llegada.

tamaño: <tamañomín>[,<tamañomáx>]
Un rango de tamaños de artículos (en bytes) que deben almacenarse utilizando este método de almacenamiento. Si <tamañomáx> es 0 o no se proporciona, el tamaño superior de los artículos está limitado solo por maxartsize en inn.conf. El campo tamaño: es opcional y puede omitirse por completo si desea que artículos de cualquier tamaño se almacenen en este método de almacenamiento (si, por supuesto, estos artículos cumplen todos los demás requisitos de esta entrada de método de almacenamiento). Por defecto, <tamañomín> se establece en 0.
expira: <tiemposin>[,<tiemposin>]
Un rango de tiempos de expiración de artículos que deben almacenarse utilizando este método de almacenamiento. Tenga cuidado; esto es menos útil de lo que parece a primera vista. Esto se basa **únicamente** en el encabezado Expires del artículo, no en ninguna política de expiración local ni en nada en expire.ctl. Si <tiemposin> no es cero, entonces esta entrada **no coincidirá** con ningún artículo sin un encabezado Expires. Por lo tanto, esta clave solo es realmente útil para asignar artículos con tiempos de expiración solicitados más largos a un método de almacenamiento separado. Los artículos solo coinciden si el tiempo hasta la expiración (es decir, la cantidad de tiempo futuro que el encabezado Expires del artículo solicita que permanezca disponible) cae en el intervalo especificado por <tiemposin> y <tiemposin>.

El formato de estos parámetros es "0d0h0m0s" (días, horas, minutos y segundos en el futuro). Si <tiemposin> es "0s" o no se especifica, no hay límite superior para los tiempos de expiración que caen en esta entrada (tenga en cuenta que esta clave no tiene ningún efecto sobre cuándo expirará realmente el artículo, sino solo sobre si el artículo se almacenará o no utilizando este método de almacenamiento). Este campo también es opcional y puede omitirse por completo si no desea almacenar artículos según su encabezado Expires, si lo hay.

Un valor <tiemposin> mayor que "0s" implica que este método de almacenamiento no coincidirá con ningún artículo sin un encabezado Expires.

opciones: <opciones>
Esta clave es para pasar opciones especiales a los métodos de almacenamiento que las requieren (actualmente solo "cnfs"). Consulte la sección "MÉTODOS DE ALMACENAMIENTO" a continuación para obtener una descripción de su uso.
coincidirexacta: <bool>
Si esta clave se establece en verdadero, se examinarán todos los grupos de noticias en el cuerpo del encabezado Newsgroups (o Xref si storeonxref en inn.conf es verdadero) de los artículos entrantes para ver si coinciden con los patrones de grupos de noticias. (Normalmente, cualquier número distinto de cero de grupos de noticias coincidentes es suficiente, siempre que ningún grupo de noticias coincida con un comodín de envenenamiento como se describe anteriormente). Este es un valor booleano; "true", "yes" y "on" se pueden utilizar para habilitar esta clave. El caso de estos valores no es significativo. El valor predeterminado es falso.
filtrado: <bool>
Si esta clave se establece en verdadero, el artículo debe haber sido rechazado por cualquier filtro de artículos habilitado (Perl o Python) para **innd**. Esto también requiere que dontrejectfiltered esté establecido en verdadero en inn.conf. Los artículos filtrados generalmente se almacenan en un pequeño búfer CNFS, o en otro método de almacenamiento con una política de expiración bastante estricta. Este es un valor booleano; "true", "yes" y "on"

MÉTODOS DE ALMACENAMIENTO

Los siguientes métodos de almacenamiento están disponibles. Consulte también la documentación específica para cada método de almacenamiento para obtener información sobre cómo configurar y utilizar las opciones correspondientes.

cnfs
Almacenamiento en un sistema de archivos de red de solo lectura (como el utilizado por tmda). Se puede especificar un directorio base en el campo options. Debe estar especificado como un argumento numérico; por ejemplo, "options: /path/to/cnfs". Si no se especifica, se utilizará el valor de cnfsdir en inn.conf. Tenga en cuenta que este método ya no se puede utilizar como método de almacenamiento principal porque los artículos se almacenan en directorios creados dinámicamente. Sin embargo, todavía se puede utilizar para almacenar artículos filtrados si dontrejectfiltered es verdadero en inn.conf y el artículo es rechazado por los filtros de artículos.
timecaf
Almacenamiento en caché basado en tiempo. Los artículos se almacenan en una estructura de árbol (hash) y los directorios se organizan por fecha y hora. El directorio base se puede especificar en el campo options. Si no se especifica, se utilizará el valor de storage.timecaf.dir en inn.conf. Los artículos se almacenan en directorios organizados por año, mes y día, con un número de índice dentro de cada día. Este método está diseñado para maximizar la caché de disco. Consulte también inn.conf(5) para las opciones relacionadas.
timehash
Almacenamiento basado en tiempo similar a timecaf, pero utiliza un método de organización de archivos diferente. El directorio base se puede especificar en el campo options. Si no se especifica, se utilizará el valor de storage.timehash.dir en inn.conf. Los artículos se almacenan en directorios organizados por año, mes y día, con un número de índice dentro de cada día. Este método está diseñado para maximizar el rendimiento de recuperación. Consulte también inn.conf(5) para las opciones relacionadas.
tradspool
El método de almacenamiento tradicional de INN (un archivo de "spool" por grupo de noticias). Este es el método predeterminado si no se especifica ningún otro método. Los artículos se almacenan en archivos individuales dentro de directorios correspondientes a los grupos de noticias. Este método puede ser ineficiente para grupos de noticias con muchos artículos o para sistemas de archivos que tienen problemas con muchos archivos pequeños.
trash
Un método de almacenamiento especial utilizado para almacenar artículos que no cumplen ningún criterio de almacenamiento o que se han determinado que deben ser eliminados. Los artículos almacenados en este método generalmente se eliminarán poco después de su almacenamiento. No se recomienda utilizar este método para almacenar artículos de forma permanente.

ORDEN DE PROCESAMIENTO

El gestor de almacenamiento procesa las entradas de storage.conf en el orden en que aparecen. La primera entrada que coincide con un artículo se utiliza para almacenar ese artículo. Por lo tanto, es importante colocar las reglas más específicas antes que las más generales. Por ejemplo, si desea utilizar un método de almacenamiento específico para un grupo de noticias en particular, debe colocar esa entrada antes de una entrada que coincida con todos los grupos de noticias (por ejemplo, "newsgroups: *").

Las entradas de storage.conf se prueban en orden. El primer método que coincide se utiliza para almacenar el artículo. Si ningún método coincide, el artículo se almacena utilizando el método de almacenamiento predeterminado, que es tradspool.

EJEMPLO

Aquí hay un ejemplo de un archivo storage.conf:

# Almacenar artículos grandes (más de 1 MB) en timehash
method timehash {
    newsgroups: *
    size: 1048576,0
    clase: 1
}

# Almacenar artículos filtrados en cnfs
method cnfs {
    filtered: true
    clase: 2
    options: /var/spool/news/filtered
}

# Almacenar todos los demás artículos en tradspool
method tradspool {
    newsgroups: *
    clase: 3
}

En este ejemplo:

  • Los artículos de más de 1 MB se almacenarán utilizando el método timehash en la clase de almacenamiento 1.
  • Los artículos que hayan sido filtrados (y si dontrejectfiltered está habilitado en inn.conf) se almacenarán utilizando el método cnfs en el directorio especificado en las opciones.
  • Cualquier otro artículo se almacenará utilizando el método tradspool en la clase de almacenamiento 3.

STORAGE.CONF

The storage.conf file controls where articles are stored. It consists of a series of entries, each defining a storage method. The entries are processed in the order they appear in the file, and the first entry that matches the article is used to store it. Each entry has the following format:

    <storage_class>:<storage_method> [\
    cnfs_options | timecaf_options | timehash_options | tradspool_options |\
    trash_options \
    ] [options:] [modifiers:]

Where:

<storage_class>
This is an arbitrary name for a storage class. All articles stored using this entry will be associated with this storage class. This name is used for filtering and reporting purposes. The default is to use the newsgroup name (or the highest-level newsgroup name for crossposted articles) as the storage class.

The following storage classes are predefined:

log
All articles for which no other entry matches will be logged as being stored in this storage class. This is used for debugging and reporting purposes.
trash
Articles stored in this storage class will be silently discarded. This is useful for filtering out unwanted articles.
<storage_method>
This specifies the storage method to use. The following methods are available:
cnfs
Stores articles in cyclic buffers.
timecaf
Stores multiple articles in a single file based on arrival time.
timehash
Stores each article in a separate file, organized by arrival time.
tradspool
Stores articles in the traditional news spool format.
trash
Discards articles.
options
These are method-specific options. See the documentation for each storage method for details.

The following options are available for all storage methods:

expires: <integer>
Specifies the maximum age of articles in days. Articles older than this will be expired. The default is 0, which means no expiration.
path: <wildmat>
Specifies a pattern for the Path header field. Articles matching this pattern will be stored using this method. See the documentation for wildmat for details.
filter: <wildmat>
Specifies a pattern for the newsgroups of articles. Articles matching this pattern will be stored using this method. The <wildmat> pattern is matched in order. Poison wildmat expressions (expressions starting with "@") are allowed and can be used to exclude certain newsgroup patterns. The default is to match all newsgroups.
sizemax: <integer>
Specifies the maximum size of articles in bytes. Articles larger than this will not be stored using this method. The default is 0, which means no size limit.
sizemin: <integer>
Specifies the minimum size of articles in bytes. Articles smaller than this will not be stored using this method. The default is 0, which means no size limit.
fastpaths: true | false
If set to true, articles that match this entry and have a Path header field that matches the path option will be stored using this method, even if they do not match any other criteria. The default is false.

If all the storage classes have this key set to false, filtered articles are stored in the same storage class as accepted articles. It is only when at least one storage class has this key set to true than filtered articles and accepted articles are no longer stored mixed together in any storage class.

modifiers
These are optional modifiers that can be applied to the storage method.

The following modifiers are available:

do_not_expire
Articles stored using this entry will not be expired by the expire(8) program. This is useful for articles that should be retained indefinitely.
no_immediate_cancel
If this modifier is present, cancelled articles will not be removed immediately. They will be removed by the expire(8) program.

If an article matches all of the constraints of an entry, it is stored via that storage method and is associated with that <storage_class>. This file is scanned in order and the first matching entry is used to store the article.

If an article does not match any entry, either by being posted to a newsgroup which does not match any of the <wildmat> patterns or by being outside the size and expires ranges of all entries whose newsgroups pattern it does match, the article is not stored and is rejected by innd. When this happens, the error message:

cant store article: no matching entry in storage.conf

is logged to syslog. If you want to silently drop articles matching certain newsgroup patterns or size or expires ranges, assign them to the "trash" storage method rather than having them not match any storage method entry.

MÉTODOS DE ALMACENAMIENTO

Actualmente, hay cinco métodos de almacenamiento disponibles. Cada método tiene sus pros y sus contras; puedes elegir cualquier mezcla de ellos según sea adecuado para tu entorno. Ten en cuenta que cada método tiene un atributo EXPENSIVESTAT que indica si la comprobación de la existencia de un artículo es costosa o no. Esto se utiliza para ejecutar expireover(8).

cnfs
El método de almacenamiento "cnfs" almacena artículos en grandes búferes cíclicos (CNFS significa Cyclic News File System). Los artículos se almacenan en los búferes CNFS en orden de llegada, y cuando el búfer se llena, da la vuelta al principio y almacena los nuevos artículos sobre los artículos más antiguos del búfer. Por lo tanto, el tiempo de expiración de los artículos almacenados en los búferes CNFS está completamente determinado por la rapidez con que el búfer da la vuelta, lo que depende de la rapidez con que se almacenan los datos en él. (Por lo tanto, se dice que este método tiene funcionalidad de auto-expiración. También significa que cuando un artículo se cancela, el cycbuff no retrocede y utiliza espacio hasta que da la vuelta y todo el cycbuff comienza a reutilizarse.) EXPENSIVESTAT es falso para este método.

CNFS tiene su propio archivo de configuración, cycbuff.conf, que describe algunas sutilezas a la descripción básica dada anteriormente. Las entradas del método de almacenamiento para el método de almacenamiento "cnfs" deben tener un campo de opciones: especificando el metacycbuff en el que se deben almacenar los artículos que coinciden con esa entrada; véase cycbuff.conf(5) para obtener detalles sobre los metacycbuffs.

Ventajas: De lejos, el más rápido de todos los métodos de almacenamiento (excepto "trash"), ya que elimina la sobrecarga de tratar con un sistema de archivos y crear nuevos archivos. A diferencia de todos los demás métodos de almacenamiento, no requiere la expiración manual de artículos. Con CNFS, el servidor nunca se ralentizará debido a un disco de spool lleno, y los grupos se limitan solo a los archivos del búfer proporcionados, por lo que nunca podrán utilizar más espacio en disco del asignado.

Desventajas: Los tiempos de retención de artículos son más difíciles de controlar porque los artículos antiguos se sobrescriben automáticamente. Los ataques a Usenet, como inundaciones o grandes cantidades de spam, pueden provocar que los artículos deseados expiren mucho más rápido de lo previsto (sin previo aviso).

timecaf
Este método almacena varios artículos en un solo archivo, cuyo nombre se basa en la hora de llegada del artículo y la clase de almacenamiento. El nombre del archivo será: 
<patharticles>/timecaf-nn/bb/aacc.CF

donde "nn" es el valor hexadecimal de <storage_class>, "bb" y "aacc" son los componentes hexadecimales de la hora de llegada, y "CF" es una extensión codificada. (La hora de llegada, en segundos desde la época, se convierte a hexadecimal y se interpreta como 0xaabbccdd, con "aa", "bb" y "cc" utilizados para construir la ruta). Este método no tiene funcionalidad de auto-expiración (lo que significa que expire tiene que ejecutarse periódicamente para eliminar artículos antiguos, así como artículos cancelados si immediatecancel no está establecido en true en inn.conf). EXPENSIVESTAT es falso para este método.

Un archivo CAF dado contiene todos los artículos recibidos durante un período de tiempo de aproximadamente 4 minutos (256 segundos), y está limitado a 262.144 artículos y aproximadamente 3,5 GB. Es suficiente para operaciones normales. La única advertencia es cuando se alimentan a alta velocidad lotes de artículos entre dos servidores; en ese caso, querrás limitarlo a esa cantidad de artículos durante el período de tiempo en que un archivo CAF almacena los artículos recién llegados.

Ventajas: Es aproximadamente cuatro veces más rápido que "timehash" para escrituras de artículos, ya que se evita gran parte de la sobrecarga del sistema de archivos, al tiempo que se conserva el mismo control fino sobre el tiempo de retención de artículos.

Desventajas: Usar este método significa renunciar a todo menos a la manipulación manual más cuidadosa del spool de artículos; en este aspecto, se parece a "cnfs". Al ser uno de los tipos de almacenamiento más nuevos y menos utilizados, "timecaf" no ha sido tan exhaustivamente probado como los otros métodos. Requiere ejecutar un programa expire nocturno para eliminar artículos antiguos compactando los archivos CAF si aún contienen artículos disponibles, o eliminándolos.

timehash
Este método es muy similar a "timecaf" excepto que cada artículo se almacena en un archivo separado. El nombre del archivo para un artículo dado será: 
<patharticles>/time-nn/bb/cc/yyyy-aadd

donde "nn" es el valor hexadecimal de <storage_class>, "yyyy" es un número de secuencia hexadecimal, y "bb", "cc" y "aadd" son componentes de la hora de llegada en hexadecimal (la hora de llegada se interpreta como se documenta anteriormente en "timecaf"). Este método no tiene funcionalidad de auto-expiración. Los artículos cancelados se eliminan inmediatamente. EXPENSIVESTAT es verdadero para este método.

Ventajas: Los grupos con mucho tráfico no causan cuellos de botella, y todavía es posible un control fino del tiempo de retención de artículos.

Desventajas: Se pierde la capacidad de encontrar fácilmente todos los artículos de un grupo de noticias determinado y de manipular manualmente el spool de artículos, y INN todavía sufre una degradación de la velocidad debido a la sobrecarga del sistema de archivos (crear y eliminar archivos individuales es una operación lenta) y a un mayor uso de inodos. También requiere un programa expire nocturno para eliminar artículos antiguos del spool de noticias.

tradspool
El spool tradicional, o "tradspool", es el formato de almacenamiento tradicional de artículos de noticias. Cada artículo se almacena en un archivo de texto individual llamado: 
<patharticles>/news/group/name/nnnnn

donde "news/group/name" es el nombre del grupo de noticias al que se publicó el artículo, con cada punto cambiado por una barra, y "nnnnn" es el número de secuencia del artículo en ese grupo de noticias. Para artículos cruzados, el artículo se enlaza en cada grupo de noticias al que se cruza (usando enlaces duros o simbólicos). Esta es la forma en que las versiones de INN anteriores a la 2.0 almacenaban todos los artículos, y también es el formato de almacenamiento de artículos utilizado por C News y sistemas de noticias anteriores. Este método no tiene funcionalidad de auto-expiración. Los artículos cancelados se eliminan inmediatamente. EXPENSIVESTAT es verdadero para este método.

Ventajas: Es ampliamente utilizado y bien entendido; puede leer spools de artículos escritos por versiones anteriores de INN y es compatible con todos los complementos de INN de terceros. Este mecanismo de almacenamiento proporciona un acceso fácil y directo a los artículos almacenados en el servidor, facilita la escritura de programas que manipulan el spool de noticias, ofrece un control fino sobre los tiempos de retención de artículos y viene con la utilidad de soporte scanspool para realizar comprobaciones de sanidad.

Desventajas: Necesita un sistema de archivos y un sistema de E/S más rápidos que los métodos de almacenamiento cnfs y timecaf debido a la sobrecarga del sistema de archivos. Los grupos con mucho tráfico tienden a crear un cuello de botella debido a las ineficiencias al almacenar un gran número de archivos de artículos en un solo directorio. Consume más inodos y requiere un programa expire nocturno para eliminar artículos antiguos del spool de noticias.

NAME

storage.conf — storage method selection file for INN

DESCRIPTION

This file describes the different storage methods available to INN. The file is read by inn.conf(5) and is used by innd(8) to decide where to store incoming articles.

Each entry in the file describes a storage method. The methods are tried in the order in which they appear in the file. The first method that matches the article being stored is used. It is important to have a catch-all entry at the end of the file to ensure that all articles are stored.

The following parameters can be specified for each storage method:

method
The name of the storage method to use. The available methods are "tradspool", "timehash", "cnfs", and "metacycbuff". This parameter is mandatory.
class
The storage class for the method. This is an integer value used to group articles. This parameter is mandatory.
newsgroups
A list of newsgroup patterns to match. Articles posted to any of these newsgroups will be considered for this storage method. The patterns are wildmat expressions. This parameter is mandatory.
size
The maximum size of an article in bytes. Articles larger than this size will not be considered for this storage method. This parameter is optional.
options
A comma-separated list of options for the storage method. The available options depend on the method used. For "cnfs", the options are "BINARIES", "LARGE", and "SMALL". This parameter is optional.

STORAGE METHODS

tradspool
This method stores articles in the traditional spool format. It is the default method if no other method is specified. Articles are stored in a directory structure based on the newsgroup name.
timehash
This method stores articles in a time-based hash structure. This method is useful for keeping articles for a limited amount of time. Articles are stored in directories named after the time they were received.
cnfs
This method stores articles in a CNFS (Constant Non-Volatile Storage) buffer. CNFS buffers are typically used for storing large amounts of data, such as binary articles. The options "BINARIES", "LARGE", and "SMALL" can be used to tune the behavior of the CNFS buffer.
metacycbuff
This method stores articles in a metacycbuff. A metacycbuff is a circular buffer that automatically overwrites old articles when it is full. This method is useful for storing articles that do not need to be kept for long periods of time. This method takes up no disk space and can never be retrieved, so this method has self-expire functionality of a sort. EXPENSIVESTAT is false for this method.

EXAMPLES

The following sample storage.conf file would store all articles posted to alt.binaries.* in the "BINARIES" CNFS metacycbuff, all articles over roughly 50 KB in any other hierarchy in the "LARGE" CNFS metacycbuff, all other articles in alt.* in one timehash class, and all other articles in any newsgroups in a second timehash class, except for the internal.* hierarchy which is stored in traditional spool format.

method tradspool {
    class: 1
    newsgroups: internal.*
}
method cnfs {
    class: 2
    newsgroups: alt.binaries.*
    options: BINARIES
}
method cnfs {
    class: 3
    newsgroups: *
    size: 50000
    options: LARGE
}
method timehash {
    class: 4
    newsgroups: alt.*
}
method timehash {
    class: 5
    newsgroups: *
}

Notice that the last storage method entry will catch everything. This is a good habit to get into; make sure that you have at least one catch-all entry just in case something you did not expect falls through the cracks. Notice also that the special rule for the internal.* hierarchy is first, so it will catch even articles crossposted to alt.binaries.* or over 50 KB in size.

As for poison wildmat expressions, if you have for instance an article crossposted between misc.foo and misc.bar, the pattern:

misc.*,!misc.bar

will match that article whereas the pattern:

misc.*,@misc.bar

will not match that article. An article posted only to misc.bar will fail to match either pattern.

Usually, high-volume groups and groups whose articles do not need to be kept around very long (binaries groups, *.jobs*, news.lists.filters, etc.) are stored in CNFS buffers. Use the other methods (or CNFS buffers again) for everything else. However, it is as often as not most convenient to keep in "tradspool" special hierarchies like local hierarchies and hierarchies that should never expire or through the spool of which you need to go manually.
