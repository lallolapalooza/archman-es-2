RPC.STATD(8) Manual del Administrador del Sistema RPC.STATD(8)

NOMBRE

rpc.statd - demonio del servicio NSM

SINOPSIS

rpc.statd [-dh?FLNvV] [-H prog] [-n mi-nombre] [-o puerto-salida] [-p puerto-escucha] [-P ruta] [--nlm-port puerto] [--nlm-udp-port puerto]

DESCRIPCIÓN

Los bloqueos de archivos no forman parte del estado persistente del sistema de archivos. Por lo tanto, el estado de bloqueo se pierde cuando un host se reinicia.

Los sistemas de archivos de red también deben detectar la pérdida del estado de bloqueo debido al reinicio de un host remoto. Después de que un cliente NFS se reinicia, un servidor NFS debe liberar todos los bloqueos de archivos en poder de las aplicaciones que se ejecutaban en ese cliente. Después de que un servidor se reinicia, un cliente debe recordar al servidor los bloqueos de archivos en poder de las aplicaciones que se ejecutan en ese cliente.

Para NFS versión 2 [RFC1094] y NFS versión 3 [RFC1813], el protocolo Network Status Monitor (NSM) se utiliza para notificar a los pares de NFS sobre los reinicios. En Linux, dos componentes separados en el espacio de usuario constituyen el servicio NSM:

rpc.statd
Un demonio que escucha las notificaciones de reinicio de otros hosts y gestiona la lista de hosts que deben ser notificados cuando el sistema local se reinicia.
sm-notify
Un programa auxiliar que notifica a los pares de NFS después de que el sistema local se reinicia.

El administrador de bloqueo NFS local alerta a su rpc.statd local de cada par remoto que debe ser monitorizado. Cuando el sistema local se reinicia, el comando sm-notify notifica al servicio NSM en los pares monitorizados sobre el reinicio. Cuando un remoto se reinicia, ese par notifica al rpc.statd local, que a su vez pasa la notificación de reinicio al administrador de bloqueo NFS local.

OPERACIÓN NSM EN DETALLE

La primera interacción de bloqueo de archivos entre un cliente NFS y un servidor hace que los administradores de bloqueo NFS en ambos pares contacten a su servicio NSM local para almacenar información sobre el par opuesto. En Linux, el administrador de bloqueo local contacta a rpc.statd.

rpc.statd registra información sobre cada par NFS monitorizado en almacenamiento persistente. Esta información describe cómo contactar a un par remoto en caso de que el sistema local se reinicie, cómo reconocer qué par monitorizado informa de un reinicio y cómo notificar al administrador de bloqueo local cuando un par monitorizado indica que se ha reiniciado.

Un cliente NFS envía un nombre de host, conocido como nombre_llamada del cliente, en cada solicitud de bloqueo de archivo. Un servidor NFS puede usar este nombre de host para enviar llamadas GRANT asíncronas a un cliente, o para notificar al cliente que se ha reiniciado.

El servidor NFS de Linux puede proporcionar el nombre_llamada del cliente o la dirección de red del cliente a rpc.statd. A efectos del protocolo NSM, este nombre o dirección se conoce como nombre_monitor del par monitorizado. Además, el administrador de bloqueo local le dice a rpc.statd cuál cree que es su propio nombre de host. A efectos del protocolo NSM, este nombre de host se conoce como mi_nombre.

No existe una interacción equivalente entre un servidor NFS y un cliente para informar al cliente del nombre_llamada del servidor. Por lo tanto, los clientes NFS en realidad no saben qué nombre_monitor podría usar un servidor NFS en una solicitud SM_NOTIFY. El cliente NFS de Linux utiliza el nombre de host del servidor del comando mount para identificar los servidores NFS que se reinician.

Notificación de reinicio

Cuando el sistema local se reinicia, el comando sm-notify lee la lista de pares monitorizados del almacenamiento persistente y envía una solicitud SM_NOTIFY al servicio NSM en cada par remoto listado. Utiliza la cadena nombre_monitor como destino. Para identificar qué host se ha reiniciado, el comando sm-notify envía la cadena mi_nombre registrada cuando ese remoto fue monitorizado. El rpc.statd remoto empareja las solicitudes entrantes SM_NOTIFY utilizando esta cadena, o la dirección de red de la llamada, con uno o más pares de su propia lista de monitorización.

Si rpc.statd no encuentra un par en su lista de monitorización que coincida con una solicitud entrante SM_NOTIFY, la notificación no se reenvía al administrador de bloqueo local. Además, cada par tiene su propio número de estado NSM, un entero de 32 bits que se incrementa después de cada reinicio por el comando sm-notify. rpc.statd utiliza este número para distinguir entre reinicios reales y notificaciones repetidas.

Parte de la recuperación de bloqueos NFS es redescubrir qué pares necesitan ser monitorizados nuevamente. El comando sm-notify borra la lista de monitorización en el almacenamiento persistente después de cada reinicio.

OPCIONES

-d, --no-syslog
Hace que rpc.statd escriba mensajes de registro en stderr en lugar del registro del sistema, si la opción -F también se especificó.
-F, --foreground
Mantiene rpc.statd adjunto a su terminal de control para que la operación NSM pueda ser monitorizada directamente o ejecutada bajo un depurador. Si esta opción no se especifica, rpc.statd se ejecutará en segundo plano poco después de iniciarse.
-h, -?, --help
Hace que rpc.statd muestre información de uso en stderr y luego salga.
-H, --ha-callout prog
Especifica un programa de llamada de alta disponibilidad. Si esta opción no se especifica, no se realizan llamadas. Consulte la sección Llamadas de alta disponibilidad a continuación para obtener más detalles.
-L, --no-notify
Evita que rpc.statd ejecute el comando sm-notify cuando se inicia, conservando el número de estado NSM y la lista de monitorización existentes.
Nota: el comando sm-notify contiene una verificación para asegurar que se ejecute solo una vez después de cada reinicio del sistema. Esto evita notificaciones de reinicio espurias si rpc.statd se reinicia sin la opción -L.
-n, --name ipaddr | hostname
Esta cadena solo la utiliza el comando sm-notify como dirección de origen desde la cual enviar las solicitudes de notificación de reinicio.
La forma ipaddr puede expresarse como una dirección de presentación IPv4 o IPv6. Si esta opción no se especifica, rpc.statd utiliza una dirección wildcard como dirección de enlace de transporte. Consulte sm-notify(8) para obtener más detalles.
-N
Hace que rpc.statd ejecute el comando sm-notify y luego salga. Dado que el comando sm-notify también se puede ejecutar directamente, esta opción está obsoleta.
-o, --outgoing-port port
Especifica el número de puerto de origen que el comando sm-notify debe utilizar al enviar notificaciones de reinicio. Consulte sm-notify(8) para obtener más detalles.
-p, --port port
Especifica el número de puerto utilizado para los sockets del oyente RPC. Si esta opción no se especifica, rpc.statd intentará consultar /etc/services, si la obtención del puerto tiene éxito, establecerá el mismo puerto para todos los sockets del oyente, de lo contrario elegirá un puerto efímero aleatorio para cada socket del oyente.
Esta opción se puede utilizar para fijar el valor del puerto de sus oyentes cuando las solicitudes SM_NOTIFY deben atravesar un firewall entre clientes y servidores.
-T, --nlm-port port
Especifica el número de puerto en el que lockd debe escuchar las solicitudes NLM. Esto establece tanto los puertos TCP como UDP, a menos que el puerto UDP se establezca por separado.
-U, --nlm-udp-port port
Especifica el número de puerto UDP en el que lockd debe escuchar las solicitudes NLM.
-P, --stat

e-directory-path ruta_de_archivo
Especifica la ruta del directorio padre donde reside la información de estado de NSM. Si esta opción no se especifica, rpc.statd utiliza /var/lib/nfs por defecto.
Después de iniciarse, rpc.statd intenta establecer su UID y GID efectivos al propietario y grupo del subdirectorio sm de este directorio. Después de cambiar los IDs efectivos, rpc.statd solo necesita acceder a los archivos en sm y sm.bak dentro de la ruta del directorio de estado.
-v, -V, --version
Hace que rpc.statd muestre información de la versión en stderr y luego salga.

ARCHIVO DE CONFIGURACIÓN

Muchas de las opciones que se pueden establecer en la línea de comandos también se pueden controlar a través de valores establecidos en las secciones [statd] o, en algunos casos, [lockd] del archivo de configuración /etc/nfs.conf. Los valores reconocidos en la sección [statd] incluyen port, outgoing-port, name, state-directory-path y ha-callout, que tienen el mismo efecto que la opción con el mismo nombre.

Los valores reconocidos en la sección [lockd] incluyen port y udp-port, que tienen el mismo efecto que las opciones --nlm-port y --nlm-udp-port, respectivamente.

SEGURIDAD

El demonio rpc.statd debe iniciarse como root para adquirir los privilegios necesarios para crear sockets con puertos de origen privilegiados y para acceder a la base de datos de información de estado. Sin embargo, dado que rpc.statd mantiene un servicio de red de larga duración, renuncia a los privilegios de root tan pronto como se inicia para reducir el riesgo de un ataque de escalada de privilegios.

Durante el funcionamiento normal, el ID de usuario efectivo que elige es el propietario del directorio de estado. Esto le permite continuar accediendo a los archivos de ese directorio después de haber renunciado a sus privilegios de root. Para controlar qué ID de usuario elige rpc.statd, simplemente use chown(1) para establecer el propietario del directorio de estado.

También puede proteger sus escuchadores de rpc.statd utilizando la biblioteca tcp_wrapper o iptables(8). Para usar la biblioteca tcp_wrapper, agregue los nombres de host de los pares a los que se debe permitir el acceso a /etc/hosts.allow. Use el nombre del demonio statd, incluso si el binario rpc.statd tiene un nombre de archivo diferente.

Para más información, consulte las páginas del manual tcpd(8) y hosts_access(5).

NOTAS ADICIONALES

La recuperación de bloqueos después de un reinicio es fundamental para mantener la integridad de los datos y evitar bloqueos innecesarios de aplicaciones. Para ayudar a rpc.statd a hacer coincidir las solicitudes SM_NOTIFY con las solicitudes NLM, se deben observar varias buenas prácticas, que incluyen:

El nombre de nodo UTS de sus sistemas debe coincidir con los nombres DNS que los pares NFS utilizan para contactarlos.
Los nombres de nodo UTS de sus sistemas siempre deben ser nombres de dominio completamente calificados.
El mapeo DNS directo e inverso de los nombres de nodo UTS debe ser coherente.
El nombre de host que el cliente utiliza para montar el servidor debe coincidir con el mon_name del servidor en las solicitudes SM_NOTIFY que envía.

Desmontar un sistema de archivos NFS no necesariamente detiene el monitoreo mutuo del cliente o servidor NFS. Ambos pueden continuar monitoreándose mutuamente durante un tiempo en caso de que el tráfico NFS posterior entre los dos resulte en montajes frescos y bloqueos de archivos adicionales.

En Linux, si el módulo del kernel lockd se descarga durante el funcionamiento normal, todos los pares NFS remotos dejan de ser monitoreados. Esto puede suceder en un cliente NFS, por ejemplo, si un montador automático elimina todos los puntos de montaje NFS debido a la inactividad.

Llamadas de alta disponibilidad

rpc.statd puede ejecutar un programa de llamada especial durante el procesamiento de solicitudes exitosas SM_MON, SM_UNMON y SM_UNMON_ALL, o cuando recibe SM_NOTIFY. Dicho programa puede usarse en entornos NFS de Alta Disponibilidad (HA-NFS) para rastrear el estado de bloqueo que puede necesitar ser migrado después de un reinicio del sistema.

El nombre del programa de llamada se especifica con la opción -H. El programa se ejecuta con 3 argumentos: El primero es add-client, del-client o sm-notify, dependiendo del motivo de la llamada. El segundo es el mon_name del par monitoreado. El tercero es el caller_name del administrador de bloqueo solicitante para add-client o del-client, de lo contrario, es la dirección IP del llamante que envía SM_NOTIFY. El cuarto es el state_value en la solicitud SM_NOTIFY.

Soporte IPv6 y TI-RPC

TI-RPC es un requisito previo para soportar NFS en IPv6. Si el soporte TI-RPC está integrado en rpc.statd, intenta iniciar escuchadores en transportes de red marcados como 'visibles' en /etc/netconfig. Siempre que al menos un escuchador de transporte de red se inicie correctamente, rpc.statd funcionará.

ENTORNO

RPC_STATD_NO_NOTIFY=
Si se establece en un entero positivo, tiene el mismo efecto que --no-notify.
