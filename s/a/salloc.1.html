salloc(1) Comandos Slurm salloc(1)

NOMBRE

salloc - Obtener una asignación de trabajo de Slurm (un conjunto de nodos), ejecutar un comando y luego liberar la asignación cuando el comando haya finalizado.

SINOPSIS

salloc [OPCIONES(0)...] [ : [OPCIONES(N)...]] [comando(0) [args(0)...]]

La opción(es) definen múltiples trabajos en un trabajo heterogéneo co-programado. Para más detalles sobre trabajos heterogéneos, consulte el documento
https://slurm.schedmd.com/heterogeneous_jobs.html

DESCRIPCIÓN

salloc se utiliza para obtener una asignación de trabajo de Slurm, que es un conjunto de recursos (nodos), posiblemente con un conjunto de restricciones (por ejemplo, número de procesadores por nodo). Cuando salloc obtiene con éxito la asignación solicitada, ejecuta el comando especificado por el usuario. Finalmente, cuando el comando especificado por el usuario se completa, salloc renuncia a la asignación del trabajo.

El comando puede ser cualquier programa que el usuario desee. Algunos comandos típicos son xterm, un script de shell que contiene comandos srun y srun (ver la sección EJEMPLOS). Si no se especifica ningún comando, salloc ejecuta el shell predeterminado del usuario.

El siguiente documento describe la influencia de varias opciones en la asignación de CPUs a trabajos y tareas.
https://slurm.schedmd.com/cpu_management.html

NOTA: La lógica de salloc incluye soporte para guardar y restaurar la configuración de la línea del terminal y está diseñada para ser ejecutada en primer plano. Si necesita ejecutar salloc en segundo plano, establezca su entrada estándar a algún archivo, por ejemplo: "salloc -n16 a.out </dev/null &"

VALOR DE RETORNO

Si salloc no puede ejecutar el comando del usuario, devolverá 1 e imprimirá errores en stderr. De lo contrario, si tiene éxito o si es interrumpido por las señales HUP, INT, KILL o QUIT: devolverá 0.

RESOLUCIÓN DE RUTA DE COMANDO

Si se proporciona, el comando se resuelve en el siguiente orden:

1. Si el comando comienza con ".", la ruta se construye como: directorio de trabajo actual / comando
2. Si el comando comienza con "/", la ruta se considera absoluta.
3. Si el comando se puede resolver a través de PATH. Ver path_resolution(7).
4. Si el comando está en el directorio de trabajo actual.

El directorio de trabajo actual es el directorio de trabajo del proceso que llama, a menos que se pase el argumento --chdir, que anulará el directorio de trabajo actual.

OPCIONES

-A, --account=<cuenta>
Cargar los recursos utilizados por este trabajo a la cuenta especificada. La cuenta es una cadena arbitraria. El nombre de la cuenta puede cambiarse después de la presentación del trabajo utilizando el comando scontrol.
--acctg-freq=<datatype>=<intervalo>[,<datatype>=<intervalo>...]
Definir los intervalos de muestreo de contabilidad y perfilado del trabajo en segundos. Esto se puede usar para anular el parámetro JobAcctGatherFrequency en el archivo slurm.conf. <datatype>=<intervalo> especifica el intervalo de muestreo de tareas para el plugin jobacct_gather o un intervalo de muestreo para un tipo de perfilado por el plugin acct_gather_profile. Se pueden especificar múltiples pares de <datatype>=<intervalo> separados por comas. Los valores de datatype admitidos son:
task
Intervalo de muestreo para los plugins jobacct_gather y para el perfilado de tareas por el plugin acct_gather_profile.
NOTA: Esta frecuencia se utiliza para monitorizar el uso de memoria. Si se imponen límites de memoria, la frecuencia más alta que un usuario puede solicitar es la configurada en el archivo slurm.conf. No se puede deshabilitar.
energy
Intervalo de muestreo para el perfilado de energía utilizando el plugin acct_gather_energy.
network
Intervalo de muestreo para el perfilado de infiniband utilizando el plugin acct_gather_interconnect.
filesystem
Intervalo de muestreo para el perfilado del sistema de archivos utilizando el plugin acct_gather_filesystem.

El valor predeterminado para el intervalo de muestreo de tareas es de 30 segundos. El valor predeterminado para todos los demás intervalos es 0. Un intervalo de 0 deshabilita el muestreo del tipo especificado. Si el intervalo de muestreo de tareas es 0, la información de contabilidad se recopila solo al finalizar el trabajo (reduciendo la interferencia de Slurm con el trabajo).
Valores más pequeños (no nulos) tienen un mayor impacto en el rendimiento del trabajo, pero es poco probable que un valor de 30 segundos sea notable para aplicaciones con menos de 10.000 tareas.

--bb=<especificación>
Especificación del buffer de ráfaga. La forma de la especificación depende del sistema. Tenga en cuenta que es posible que el buffer de ráfaga no sea accesible desde un nodo de inicio de sesión, sino que requiera que salloc inicie un shell en uno de sus nodos de cómputo asignados. Cuando se utiliza la opción --bb, Slurm analiza esta opción y crea un archivo de script de buffer de ráfaga temporal que es utilizado internamente por los plugins del buffer de ráfaga. Consulte la guía de buffer de ráfaga de Slurm para obtener más información y ejemplos:
https://slurm.schedmd.com/burst_buffer.html
--bbf=<nombre_archivo>
Ruta del archivo que contiene la especificación del buffer de ráfaga. La forma de la especificación depende del sistema. Consulte también --bb. Tenga en cuenta que es posible que el buffer de ráfaga no sea accesible desde un nodo de inicio de sesión, sino que requiera que salloc inicie un shell en uno de sus nodos de cómputo asignados. Consulte la guía de buffer de ráfaga de Slurm para obtener más información y ejemplos:
https://slurm.schedmd.com/burst_buffer.html
--begin=<tiempo>
Retrasar la elegibilidad de esta asignación de trabajo hasta la hora especificada.

El tiempo puede tener el formato HH:MM:SS para ejecutar un trabajo a una hora específica del día (los segundos son opcionales). (Si esa hora ya ha pasado, se asume el día siguiente). También puede especificar midnight (medianoche), noon (mediodía), elevenses (11 AM), fika (3 PM) o teatime (4 PM) y puede tener una hora del día seguida de AM o PM para ejecutar por la mañana o por la tarde. También puede indicar qué día se ejecutará el trabajo especificando una fecha en formato MMDDYY o MM/DD/YY AAAA-MM-DD. Combine fecha y hora usando el siguiente formato AAAA-MM-DD[THH:MM[:SS]]. También puede dar tiempos como now + cuenta unidades_de_tiempo, donde las unidades_de_tiempo pueden ser seconds (segundos) (predeterminado), minutes (minutos), hours (horas), days (días) o weeks (semanas) y puede indicarle a Slurm que ejecute el trabajo hoy con la palabra clave today y que ejecute el trabajo mañana con la palabra clave tomorrow. El valor puede cambiarse después de la presentación del trabajo utilizando el comando scontrol. Por ejemplo:

   --begin=16:00
   --begin=now+1hour
   --begin=now+60           (segundos por defecto)
   --begin=2010-01-20T12:34:00

Notas sobre las especificaciones de fecha/hora:
- Aunque el campo 'segundos' de la especificación de tiempo HH:MM:SS está permitido por el código, tenga en cuenta que el tiempo de sondeo del programador de Slurm no es lo suficientemente preciso como para garantizar la puesta en marcha del trabajo en el segundo exacto. El trabajo será elegible para comenzar en el siguiente sondeo posterior a la hora especificada. El intervalo de sondeo exacto depende del programador de Slurm (por ejemplo,

- Si no se especifica hora (HH:MM:SS), el valor predeterminado es (00:00:00).
- Si se especifica una fecha sin año (por ejemplo, MM/DD), se asume el año actual, a menos que la combinación de MM/DD y HH:MM:SS ya haya pasado para ese año, en cuyo caso se utiliza el año siguiente.

--bell
Fuerza a salloc a hacer sonar la campana del terminal cuando se concede la asignación del trabajo (y solo si stdout es una tty). Por defecto, salloc solo hace sonar la campana si la asignación está pendiente durante más de diez segundos (y solo si stdout es una tty). Consulte también la opción --no-bell.
-D, --chdir=<ruta>
Cambia al directorio ruta antes de comenzar la ejecución. La ruta puede especificarse como ruta completa o ruta relativa al directorio donde se ejecuta el comando.
--cluster-constraint=<lista>
Especifica las características que debe tener un clúster federado para que se le envíe un trabajo hermano. Slurm intentará enviar un trabajo hermano a un clúster si este tiene al menos una de las características especificadas.
-M, --clusters=<cadena>
Clústeres a los que se enviarán los comandos. Se pueden especificar varios nombres de clúster separados por comas. El trabajo se enviará al clúster que proporcione el tiempo de inicio del trabajo esperado más temprano. El valor predeterminado es el clúster actual. Un valor de 'all' consultará para ejecutarse en todos los clústeres. Tenga en cuenta que slurmdbd debe estar activo para que esta opción funcione correctamente, a menos que se ejecute en una federación con FederationParameters=fed_display configurado.
--comment=<cadena>
Un comentario arbitrario.
--consolidate-segments
Asegura que todos los segmentos de la asignación se consolidarán en un bloque agregado de nivel superior.

Esta opción se aplica a las asignaciones de trabajos. NOTA: Esta opción solo funcionará con el plugin topology/block.

-C, --constraint=<lista>
Los nodos pueden tener características asignadas por el administrador de Slurm. Los usuarios pueden especificar qué características requiere su trabajo utilizando la opción de restricción. Si busca restricciones 'blandas', consulte --prefer para obtener más información. Solo se utilizarán los nodos que tengan características que coincidan con las restricciones del trabajo para satisfacer la solicitud. Se pueden especificar varias restricciones con AND, OR, OR coincidentes, recuentos de recursos, etc. (algunos operadores no son compatibles con todos los tipos de sistemas).

NOTA: Las características cambiantes son características definidas por un plugin NodeFeatures.

Las opciones --constraint admitidas incluyen:

Nombre único
Solo se utilizarán los nodos que tengan la característica especificada. Por ejemplo, --constraint="intel"
Recuento de Nodos
Una solicitud puede especificar el número de nodos necesarios con alguna característica añadiendo un asterisco y un recuento después del nombre de la característica. Por ejemplo, --nodes=16 --constraint="graphics*4" indica que el trabajo requiere 16 nodos y que al menos cuatro de esos nodos deben tener la característica "graphics". Si se solicitan más de una característica y se utilizan recuentos de nodos, la solicitud debe estar rodeada de corchetes.

NOTA: Esta opción no es compatible con el plugin de ayuda NodeFeatures. Se pueden utilizar trabajos heterogéneos en su lugar.

AND
Solo se utilizarán los nodos que tengan todas las características especificadas. Se utiliza el ampersand (&) como operador AND. Por ejemplo, --constraint="intel&gpu"
OR
Solo se utilizarán los nodos que tengan al menos una de las características especificadas. La barra vertical (|) se utiliza como operador OR. Si no se solicitan características cambiantes, los nodos de la asignación pueden tener diferentes características. Por ejemplo, salloc -N2 --constraint="intel|amd" puede resultar en una asignación de trabajo donde un nodo tiene la característica intel y el otro nodo tiene la característica amd. Sin embargo, si la expresión contiene una característica cambiante, todos los operadores OR se tratan automáticamente como OR coincidentes para que todos los nodos de la asignación de trabajo tengan el mismo conjunto de características. Por ejemplo, salloc -N2 --constraint="foo|bar&baz" El trabajo se asigna a dos nodos donde ambos nodos tienen foo, o bar y baz (uno o ambos nodos podrían tener foo, bar y baz). El plugin de ayuda NodeFeatures encontrará el primer conjunto de características de nodo que coincida con todos los nodos de la asignación de trabajo; estas características se establecen como características activas en el nodo y se pasan a RebootProgram (ver slurm.conf(5)) y al script de ayuda (ver helpers.conf(5)). En este caso, el plugin de ayuda utiliza el primero de "foo" o "bar,baz" que coincide con los dos nodos en la asignación del trabajo.
OR Coincidente
Si solo una de un conjunto de opciones posibles debe usarse para todos los nodos asignados, use el operador OR y encierre las opciones entre corchetes. Por ejemplo, --constraint="[rack1|rack2|rack3|rack4]" podría usarse para especificar que todos los nodos deben asignarse en un solo rack del clúster, pero se puede usar cualquiera de esos cuatro racks.
Recuentos Múltiples
Se pueden especificar recuentos específicos de varios recursos utilizando el operador AND y encerrando las opciones entre corchetes. Por ejemplo, --constraint="[rack1*2&rack2*4]" podría usarse para especificar que se deben asignar dos nodos de los nodos con la característica "rack1" y cuatro nodos de los nodos con la característica "rack2".

NOTA: Esta opción no es compatible con el plugin de ayuda NodeFeatures.

NOTA: Los recuentos múltiples pueden hacer que los trabajos se asignen con una disposición de red no óptima.

Corchetes
Los corchetes se pueden usar para indicar que se está buscando un conjunto de nodos con los diferentes requisitos contenidos dentro de los corchetes. Por ejemplo, --constraint="[(rack1|rack2)*1&(rack3)*2]" obtendrá un nodo con las características "rack1" o "rack2" y dos nodos con la característica "rack3". Si solicita más de una característica y utiliza recuentos de nodos, la solicitud debe estar rodeada de corchetes.

NOTA: Los corchetes solo están reservados para la sintaxis de Recuentos Múltiples y OR Coincidente. Los operadores AND requieren un recuento para cada característica dentro de corchetes (es decir, "[quad*2&hemi*1]"). Slurm solo permitirá un único conjunto de restricciones entre corchetes por trabajo.

NOTA: El plugin de ayuda NodeFeatures no admite corchetes. El OR Coincidente se puede solicitar sin corchetes utilizando el carácter de barra vertical con al menos una característica cambiante.

Paréntesis
Los paréntesis se pueden usar para agrupar características de nodos similares. Por ejemplo, --constraint="[(knl&snc4&flat)*4&haswell*1]" podría usarse para especificar que se requieren cuatro nodos con las características "knl", "snc4" y "flat" más un nodo con la característica "haswell". Los paréntesis también se pueden usar para agrupar operaciones. Sin paréntesis, las características de los nodos se analizan estrictamente de izquierda a derecha. Por ejemplo, --constraint="foo&bar|baz" solicita nodos con foo y bar, o baz. --constraint="foo|bar&baz" solicita nodos con foo y baz, o bar y baz (tenga en cuenta cómo baz se combinó con AND con todo). --constraint="foo&(bar|baz)" solicita nodos con foo y al menos uno de bar o baz. NOTA: El OR dentro de paréntesis no debe usarse con un plugin KNL NodeFeatures, pero es compatible con el plugin de ayuda NodeFeatures.
--container=<ruta_al_contenedor>
Ruta absoluta al paquete de contenedor OCI.
--container-id=<id_del_contenedor>
Nombre único para el contenedor OCI.
--contiguous
Si se establece, los nodos asignados deben formar un conjunto contiguo.

NOTA: Esta opción solo funcionará con el plugin topology/flat. Otros plugins de topología modifican el orden de los nodos y evitan que esta opción surta efecto.

-S, --core-spec=<num>
Número de núcleos especializados por nodo reservados por el trabajo para operaciones del sistema y que no son utilizados por la aplicación. Si AllowSpecResourcesUsage está habilitado, un trabajo puede anular el CoreSpecCount de todos sus
nodos asignados con esta opción. Los Núcleos Especializados anulados seguirán siendo reservados para procesos del sistema. El trabajo obtendrá una asignación implícita de --exclusive para el resto de los Núcleos en los nodos, lo que resultará en que los procesos del trabajo puedan usar (y se les cobre por) todos los Núcleos en los nodos, excepto los Núcleos Especializados anulados. Esta opción no se puede usar con la opción --thread-spec.

NOTA: Establecer explícitamente el valor del núcleo especializado de un trabajo establece implícitamente la opción --exclusive.

--cores-per-socket=<cores>
Restringe la selección de nodos a nodos con al menos el número especificado de núcleos por socket. Consulte información adicional en la opción -B anterior cuando el plugin task/affinity está habilitado.
NOTA: Esta opción puede establecer implícitamente el número de tareas (si no se especificó -n) como una tarea por hilo solicitado.
--cpu-freq=<p1>[-p2][:p3]

Solicita que los pasos del trabajo iniciados por comandos srun dentro de esta asignación se ejecuten a alguna frecuencia solicitada si es posible, en las CPU seleccionadas para el paso en los nodos de cómputo.

p1 puede ser [#### | low | medium | high | highm1] lo que establecerá la velocidad de escalado de frecuencia en el valor correspondiente y el gobernador de escalado de frecuencia en UserSpace. Consulte a continuación la definición de los valores.

p1 puede ser [Conservative | OnDemand | Performance | PowerSave] lo que establecerá el gobernador de escalado en el valor correspondiente. El gobernador debe estar en la lista establecida por la opción CpuFreqGovernors de slurm.conf.

Cuando p2 está presente, p1 será la frecuencia mínima de escalado y p2 será la frecuencia máxima de escalado. En ese caso, el gobernador p3 o CpuFreqDef no puede ser UserSpace, ya que no admite un rango.

p2 puede ser [#### | medium | high | highm1]. p2 debe ser mayor que p1 y es incompatible con el gobernador UserSpace.

p3 puede ser [Conservative | OnDemand | Performance | PowerSave | SchedUtil | UserSpace] lo que establecerá el gobernador en el valor correspondiente.

Si p3 es UserSpace, la velocidad de escalado de frecuencia, la frecuencia máxima de escalado y la frecuencia mínima de escalado se establecerán estáticamente al valor definido por p1.

Cualquier frecuencia solicitada por debajo de la frecuencia mínima disponible se redondeará a la frecuencia mínima disponible. De la misma manera, cualquier frecuencia solicitada por encima de la frecuencia máxima disponible se redondeará a la frecuencia máxima disponible.

El parámetro CpuFreqDef en slurm.conf se utilizará para establecer el gobernador en ausencia de p3. Si no hay CpuFreqDef, el gobernador predeterminado será usar el gobernador actual del sistema configurado en cada cpu. Por lo tanto, no se permite especificar un rango sin CpuFreqDef o un gobernador específico.

Los valores aceptables en este momento incluyen:

####
frecuencia en kilohertz
Low
la frecuencia más baja disponible
High
la frecuencia más alta disponible
HighM1
(alta menos uno) seleccionará la siguiente frecuencia disponible más alta
Medium
intenta establecer una frecuencia en el medio del rango disponible
Conservative
intenta usar el gobernador de CPU Conservative
OnDemand
intenta usar el gobernador de CPU OnDemand (el valor predeterminado)
Performance
intenta usar el gobernador de CPU Performance
PowerSave
intenta usar el gobernador de CPU PowerSave
UserSpace
intenta usar el gobernador de CPU UserSpace

La siguiente variable de entorno informativa se establece en el paso del trabajo cuando se solicita la opción --cpu-freq.

        SLURM_CPU_FREQ_REQ

Esta variable de entorno también se puede utilizar para proporcionar el valor para la solicitud de frecuencia de CPU si se establece cuando se emite el comando 'srun'. El --cpu-freq en la línea de comandos anulará el valor de la variable de entorno. La forma en la variable de entorno es la misma que en la línea de comandos. Consulte la sección VARIABLES DE ENTORNO para obtener una descripción de la variable SLURM_CPU_FREQ_REQ.

NOTA: Este parámetro se trata como una solicitud, no como un requisito. Si el nodo del paso del trabajo no admite el establecimiento de la frecuencia de la CPU, o si el valor solicitado está fuera de los límites de las frecuencias legales, se registra un error, pero se permite que el paso del trabajo continúe.

NOTA: Establecer la frecuencia solo para las CPU del paso del trabajo implica que las tareas están confinadas a esas CPU. Si el confinamiento de tareas (es decir, si el plugin de Tareas task/affinity está habilitado, o si el plugin de Tareas task/cgroup está habilitado con "ConstrainCores=yes" establecido en cgroup.conf) no está configurado, este parámetro se ignora.

NOTA: Cuando el paso se completa, la frecuencia y el gobernador de cada CPU seleccionada se restablecen a los valores anteriores.

NOTA: Al enviar trabajos con la opción --cpu-freq con linuxproc como ProctrackType, los trabajos pueden ejecutarse demasiado rápido antes de que Accounting pueda consultar la información del trabajo. Como resultado, no toda la información de contabilidad estará presente.

--cpus-per-gpu=<ncpus>
Solicita que se asignen ncpus procesadores por GPU asignada. Los pasos que heredan este valor implicarán --exact. No es compatible con la opción --cpus-per-task.
-c, --cpus-per-task=<ncpus>
Avisa a Slurm que los pasos del trabajo subsiguientes requerirán ncpus procesadores por tarea. Por defecto, Slurm asignará un procesador por tarea.

Por ejemplo, considere una aplicación que tiene 4 tareas, cada una requiriendo 3 procesadores. Si nuestro clúster está compuesto por nodos con procesadores cuádruples y simplemente solicitamos 12 procesadores, el controlador podría darnos solo 3 nodos. Sin embargo, al usar las opciones --cpus-per-task=3, el controlador sabe que cada tarea requiere 3 procesadores en el mismo nodo, y el controlador otorgará una asignación de 4 nodos, uno para cada una de las 4 tareas.

--deadline=<OPT>
Elimina el trabajo si no es posible un final antes de esta fecha límite (inicio > (fecha límite - tiempo[-mínuto])). El valor predeterminado es sin fecha límite. Tenga en cuenta que si ni DefaultTime ni MaxTime están configurados en la partición en la que se encuentra el trabajo, el trabajo deberá especificar alguna forma de límite de tiempo (--time[-min]) si se va a utilizar una fecha límite.

Los formatos de tiempo válidos son:
HH:MM[:SS] [AM|PM]
MMDD[YY] o MM/DD[/YY] o MM.DD[.YY]
MM/DD[/YY]-HH:MM[:SS]
YYYY-MM-DD[THH:MM[:SS]]
now[+count[seconds(predeterminado)|minutes|hours|days|weeks]]
midnight, elevenses (11 AM), noon, fika (3 PM), teatime (4 PM), o tomorrow

Se pueden especificar una o más cadenas de tiempo (por ejemplo, 'tomorrow18:00'). Si hay un conflicto entre ellas, la última tendrá precedencia silenciosamente.

--delay-boot=<minutes>
No reinicie los nodos para satisfacer la especificación de características de este trabajo si el trabajo ha sido elegible para ejecutarse durante menos tiempo que este período. Si el trabajo ha esperado menos del período especificado, utilizará solo los nodos que ya tengan las características especificadas. El argumento está en unidades de minutos. Un administrador del sistema puede establecer un valor predeterminado utilizando la opción delay_boot del parámetro de configuración SchedulerParameters en el archivo slurm.conf; de lo contrario, el valor predeterminado es cero (sin demora).
-d, --dependency=<dependency_list>
Retrasa el inicio de este trabajo hasta que se hayan satisfecho las dependencias especificadas. Una vez que se satisface una dependencia, se elimina del trabajo. <dependency_list> tiene el formato <type:job_id[:job_id][,type:job_id[:job_id]]> o <type:job_id[:job_id][?type:job_id[:job_id]]>. Todas las dependencias deben satisfacerse si se utiliza el separador ",". Cualquier dependencia puede satisfacerse si se utiliza el separador "?". Solo se puede usar un separador. Por ejemplo: 
-d afterok:20:21,afterany:23
significa que el trabajo solo puede ejecutarse después de un código de retorno 0 de los trabajos 20 y 21 Y la finalización del trabajo 23. Sin embargo: 
-d afterok:20:21?afterany:23
significa que cualquiera de las condiciones (afterok:20 O afterok:21 O afterany:23) será suficiente para liberar el trabajo. Muchos trabajos pueden compartir la misma dependencia y estos trabajos pueden incluso pertenecer a diferentes usuarios. El valor se puede cambiar después de la presentación del trabajo utilizando el comando scontrol. Se permiten dependencias en trabajos remotos en una federación. Una vez que falla una dependencia de trabajo debido al estado de terminación de un trabajo anterior, el trabajo dependiente continuará
never
This job will never be run, even if the preceding job is requeued and has a different termination state in a subsequent execution.
after:job_id[[+time][:jobid[+time]...]]
Después de que los trabajos especificados comiencen o sean cancelados y 'time' en minutos desde el inicio o cancelación del trabajo ocurra, este trabajo puede comenzar su ejecución. Si no se da 'time', entonces no hay retraso después del inicio o cancelación.
afterany:job_id[:jobid...]
Este trabajo puede comenzar su ejecución después de que los trabajos especificados hayan terminado. Este es el tipo de dependencia predeterminado.
afterburstbuffer:job_id[:jobid...]
Este trabajo puede comenzar su ejecución después de que los trabajos especificados hayan terminado y cualquier operación de transferencia de salida de buffer de ráfaga asociada haya completado.

-m, --distribution={*|block|cyclic|arbitrary|plane=<size>}[:{*|block|cyclic|fcyclic}[:{*|block|cyclic|fcyclic}]][,{Pack|NoPack}]

Especifica métodos de distribución alternativos para procesos remotos. Para la asignación de trabajos, esto establece variables de entorno que serán utilizadas por solicitudes srun posteriores y también afecta a qué núcleos se seleccionarán para la asignación de trabajos.

Esta opción controla la distribución de tareas a los nodos en los que se han asignado recursos, y la distribución de esos recursos a las tareas para su vinculación (afinidad de tareas). El primer método de distribución (antes del primer ':') controla la distribución de tareas a los nodos. El segundo método de distribución (después del primer ':') controla la distribución de CPUs asignadas entre sockets para la vinculación a tareas. La tercera distribución (después del segundo ':') controla la distribución de CPUs asignadas entre núcleos para la vinculación a tareas. Las distribuciones segunda y tercera solo se aplican si la afinidad de tareas está habilitada. La tercera distribución solo se admite si el plugin de tarea/cgroup está configurado. El valor predeterminado para cada tipo de distribución se especifica mediante *.

Tenga en cuenta que con select/cons_tres, el número de CPUs asignadas a cada socket y nodo puede ser diferente. Consulte https://slurm.schedmd.com/mc_support.html para obtener más información sobre la asignación de recursos, la distribución de tareas a los nodos y la vinculación de tareas a CPUs.

Primer método de distribución (distribución de tareas entre nodos):
*
Utiliza el método predeterminado para distribuir tareas a nodos (bloque).
block
El método de distribución por bloques distribuirá las tareas a un nodo de tal manera que las tareas consecutivas compartan un nodo. Por ejemplo, considere una asignación de tres nodos, cada uno con dos CPUs. Una solicitud de distribución por bloques de cuatro tareas distribuirá esas tareas a los nodos con las tareas uno y dos en el primer nodo, la tarea tres en el segundo nodo y la tarea cuatro en el tercer nodo. La distribución por bloques es el comportamiento predeterminado si el número de tareas excede el número de nodos asignados.
cyclic
El método de distribución cíclica distribuirá las tareas a un nodo de tal manera que las tareas consecutivas se distribuyan en nodos consecutivos (de forma rotatoria). Por ejemplo, considere una asignación de tres nodos cada uno con dos CPUs. Una solicitud de distribución cíclica de cuatro tareas distribuirá esas tareas a los nodos con las tareas uno y cuatro en el primer nodo, la tarea dos en el segundo nodo y la tarea tres en el tercer nodo. Tenga en cuenta que cuando SelectType es select/cons_tres, es posible que no se asignen el mismo número de CPUs en cada nodo. La distribución de tareas será rotatoria entre todos los nodos con CPUs aún por asignar a tareas. La distribución cíclica es el comportamiento predeterminado si el número de tareas no es mayor que el número de nodos asignados.
plane
Las tareas se distribuyen en bloques de tamaño <size>. Se debe proporcionar el tamaño o establecer SLURM_DIST_PLANESIZE. El número de tareas distribuidas a cada nodo es el mismo que para la distribución cíclica, pero los taskids asignados a cada nodo dependen del tamaño del plano. No se pueden combinar especificaciones de distribución adicionales con esta opción. Para más detalles (incluyendo ejemplos y diagramas), consulte https://slurm.schedmd.com/mc_support.html y https://slurm.schedmd.com/dist_plane.html
arbitrary
El método de distribución arbitraria asignará procesos en orden según lo enumerado en el archivo designado por la variable de entorno SLURM_HOSTFILE. Si esta variable está listada, anulará cualquier otro método especificado. Si no se establece, el método se establecerá como predeterminado (bloque). Dentro del hostfile, debe contener como mínimo el número de hosts solicitados y estar uno por línea o separado por comas. Si se especifica un recuento de tareas (-n, --ntasks=<number>), sus tareas se distribuirán en los nodos en el orden del archivo.
NOTA: La opción de distribución arbitraria en una asignación de trabajo solo controla los nodos que se asignarán al trabajo y no la asignación de CPUs en esos nodos. Esta opción está destinada principalmente a controlar la distribución de tareas de un paso de trabajo en una asignación de trabajo existente para el comando srun.
NOTA: Si se proporciona el número de tareas y también una lista de nodos solicitados, el número de nodos utilizados de esa lista se reducirá para que coincida con el número de tareas si el número de nodos en la lista es mayor que el número de tareas.

Segundo método de distribución (distribución de CPUs entre sockets para vinculación):

*
Utiliza el método predeterminado para distribuir CPUs entre sockets (cíclico).
block
El método de distribución por bloques distribuirá las CPUs asignadas consecutivamente del mismo socket para su vinculación a tareas, antes de usar el siguiente socket consecutivo.
cyclic
El método de distribución cíclica distribuirá las CPUs asignadas para su vinculación a una tarea dada de forma consecutiva desde el mismo socket, y desde el siguiente socket consecutivo para la siguiente tarea, de forma rotatoria entre los sockets. Las tareas que requieran más de una CPU tendrán todas esas CPUs asignadas en un solo socket si es posible.
NOTA: En nodos con hyper-threading habilitado, una tarea que no solicite núcleos completos puede distribuirse entre sockets. Esto se puede evitar especificando --ntasks-per-core=1, lo que fuerza a las tareas a asignar núcleos completos.
fcyclic
El método de distribución fcyclic distribuirá las CPUs asignadas para su vinculación a tareas desde sockets consecutivos de forma rotatoria entre los sockets. Las tareas que requieran más de una CPU tendrán cada CPU asignada de forma cíclica entre los sockets.

Tercer método de distribución (distribución de CPUs entre núcleos para vinculación):

*
Utiliza el método predeterminado para dis
distribuyendo CPUs entre núcleos (heredado del segundo método de distribución).
block
El método de distribución por bloques distribuirá las CPUs asignadas de forma consecutiva desde el mismo núcleo para enlazarlas a las tareas, antes de usar el siguiente núcleo consecutivo.
cyclic
El método de distribución cíclica distribuirá las CPUs asignadas para enlazarlas a una tarea dada de forma consecutiva desde el mismo núcleo, y desde el siguiente núcleo consecutivo para la siguiente tarea, en modo round-robin entre los núcleos.
fcyclic
El método de distribución fcyclic distribuirá las CPUs asignadas para enlazarlas a las tareas desde núcleos consecutivos en modo round-robin entre los núcleos.

En lugar de distribuir uniformemente las tareas de un paso de trabajo entre sus nodos asignados, empaquétalas lo más apretado posible en los nodos. Esto solo se aplica cuando se utiliza el método de distribución de tareas "block".
NoPack
En lugar de empaquetar las tareas de un paso de trabajo lo más apretado posible en los nodos, distribúyelas uniformemente. Esta opción del usuario anulará el parámetro de configuración CR_Pack_Nodes de SelectTypeParameters.

--exclusive[={user|mcs|topo}]

Si un trabajo solicita --threads-per-core con menos hilos en un núcleo que los que existen en el núcleo (o --hint=nomultithread, que implica --threads-per-core=1), el trabajo no podrá usar esos hilos adicionales en el núcleo y esos hilos no se incluirán en el cálculo de memoria por CPU. Pero si el trabajo tiene acceso a todos los hilos del núcleo, esos hilos se incluirán en el cálculo de memoria por CPU, incluso si el trabajo no solicitó explícitamente esos hilos.

Cuando se aplica a una asignación de trabajo (sin incluir trabajos que solicitan acceso exclusivo a los nodos), los recursos se asignan como si solo se solicitara una tarea por nodo. Esto significa que el número solicitado de cpus por tarea (-c, --cpus-per-task) se asignan por nodo en lugar de multiplicarse por el número de tareas. Las opciones utilizadas para especificar el número de tareas por nodo, socket, núcleo, etc. se ignoran.

Cuando se aplica a las asignaciones de pasos de trabajo (el comando srun cuando se ejecuta dentro de una asignación de trabajo existente), esta opción se puede utilizar para lanzar más de una tarea por CPU. Normalmente, srun no asignará más de un proceso por CPU. Al especificar --overcommit se permite explícitamente más de un proceso por CPU. Sin embargo, no se permite que más de MAX_TASKS_PER_NODE tareas se ejecuten por nodo. NOTA: MAX_TASKS_PER_NODE se define en el archivo slurm.h y no es una variable, se establece en el momento de la compilación de Slurm.

--switch-count=<count>[time]
Number of leaf switches desired for job allocation and optionally the maximum time to wait for that number of switches. If Slurm finds an allocation containing more switches than the count specified, the job remains pending until it either finds an allocation with the desired switch count or the time limit expires. If there is no switch count limit, there is no delay in starting the job. Acceptable time formats include "minutes", "minutes:seconds", "hours:minutes:seconds", "days-hours", "days-hours:minutes" and "days-hours:minutes:seconds". The job's maximum time delay may be limited by the system administrator using the SchedulerParameters configuration parameter with the max_switch_wait parameter option. On a dragonfly network the only switch count supported is 1 since communication performance will be highest when a job is allocated resources on one leaf switch or more than 2 leaf switches. The default max-time is the max_switch_wait SchedulerParameters.
--thread-spec=<num>
Count of specialized threads per node reserved by the job for system operations and not used by the application. The application will not use these threads, but will be charged for their allocation. This option can not be used with the --core-spec option.

NOTE: Explicitly setting a job's specialized thread value implicitly sets its --exclusive option, reserving entire nodes for the job.

Restrict node selection to nodes with at least the specified number of threads per core. In task layout, use the specified maximum number of threads per core. -t, --time=<time>
Set a limit on the total run time of the job allocation. If the requested time limit exceeds the partition's time limit, the job will be left in a PENDING state (possibly indefinitely). The default time limit is the partition's default time limit. When the time limit is reached, each task in each job step is sent SIGTERM followed by SIGKILL. The interval between signals is specified by the Slurm configuration parameter KillWait. The OverTimeLimit configuration parameter may permit the job to run longer than scheduled. Time resolution is one minute and second values are rounded up to the next minute.

A time limit of zero requests that no time limit be imposed. Acceptable time formats include "minutes", "minutes:seconds", "hours:minutes:seconds", "days-hours", "days-hours:minutes" and "days-hours:minutes:seconds".

Set a minimum time limit on the job allocation. If specified, the job may have its --time limit lowered to a value no lower than --time-min if doing so permits the job to begin execution earlier than otherwise possible. The job's time limit will not be changed after the job is allocated resources. This is performed by a backfill scheduling algorithm to allocate resources otherwise reserved for higher priority jobs. Acceptable time formats include "minutes", "minutes:seconds", "hours:minutes:seconds", "days-hours", "days-hours:minutes" and "days-hours:minutes:seconds".

[verbose,]<type>...] Specify a list of tres with their task binding options. Currently gres are the only supported tres for this options. Specify gres as "gres/<gres_name>" (e.g. gres/gpu)

Example: --tres-bind=gres/gpu:verbose,map:0,1,2,3+gres/nic:closest

By default, most tres are not bound to individual tasks

Supported binding type options for gres:

closest
Bind each task to the gres(s) which are closest. In a NUMA environment, each task may be bound to more than one gres (i.e. all gres in that NUMA environment).
map:<list>
Bind by setting gres masks on tasks (or ranks) as specified where <list> is <gres_id_for_task_0>,<gres_id_for_task_1>,... gres IDs are interpreted as decimal values. If the number of tasks (or ranks) exceeds the number of elements in this list, elements in the list will be reused as needed starting from the beginning of the list. To simplify support for large task counts, the lists may follow a map with an asterisk and repetition count. For example "map:0*4,1*4". If the task/cgroup plugin is used and ConstrainDevices is set in cgroup.conf, then the gres IDs are zero-based indexes relative to the gress allocated to the job (e.g. the first gres is 0, even if the global ID is 3). Otherwise, the gres IDs are global IDs, and all gres on each node in the job should be allocated for predictable binding results.
mask:<list>
Bind by setting gres masks on tasks (or ranks) as specified where <list> is <gres_mask_for_task_0>,<gres_mask_for_task_1>,... The mapping is specified for a node and identical mapping is applied to the tasks on every node (i.e. the lowest task ID on each node is mapped to the first mask specified in the list, etc.). gres masks are always interpreted as hexadecimal values but can be preceded with an optional '0x'. To simplify support for large task counts, the lists may follow a map with an asterisk and repetition count. For example "mask:0x0f*4,0xf0*4". If the task/cgroup plugin is used and ConstrainDevices is set in cgroup.conf, then the gres IDs are zero-based indexes relative to the gres allocated to the job (e.g. the first gres is 0, even if the global ID is 3). Otherwise, the gres IDs are global IDs, and all gres on each node in the job should be allocated for predictable binding results.
none
Do not bind tasks to this gres (turns off implicit binding from --tres-per-task and --gpus-per-task).
per_task:<gres_per_task>
Each task will be bound to the number of gres specified in <gres_per_task>. Tasks are preferentially assigned gres with affinity to cores in their allocation like in closest, though they will take any gres if they are unavailable. If no affinity exists, the first task will be assigned the first x number of gres on the node etc. Shared gres will prefer to bind one sharing device per task if possible.
single:<tasks_per_gres>
Like closest, except that each task can only be bound to a single gres, even when it can be bound to multiple gres that are equally close. The gres to bind to is determined by <tasks_per_gres>, where the first <tasks_per_gres> tasks are bound to the first gres available, the second <tasks_per_gres> tasks are bound to the second gres available, etc. This is basically a block distribution of tasks onto available gres, where the available gres are determined by the socket affinity of the task and the socket affinity of the gres as specified in gres.conf's Cores parameter.

NOTE: Shared gres binding is currently limited to per_task or none

RENDIMIENTO

La ejecución de salloc envía una llamada de procedimiento remoto a slurmctld. Si llegan suficientes llamadas de salloc u otros comandos cliente de Slurm que envían llamadas de procedimiento remoto al daemon slurmctld a la vez, puede resultar en una degradación del rendimiento del daemon slurmctld, posiblemente resultando en una denegación de servicio.

No ejecute salloc u otros comandos cliente de Slurm que envíen llamadas de procedimiento remoto a slurmctld desde bucles en scripts de shell u otros programas. Asegúrese de que los programas limiten las llamadas a salloc al mínimo necesario para la información que está intentando recopilar.

SIGNALS

El salloc ignorará la mayoría de las señales después de iniciar el comando especificado. salloc no saldrá ni liberará la asignación hasta que el comando termine. Una excepción notable es SIGHUP. Una señal SIGHUP hará que salloc libere la asignación y salga sin esperar a que el comando finalice. Otra excepción es SIGTERM, que se reenviará al proceso generado.

EJEMPLOS

Para obtener una asignación y abrir un nuevo xterm en el que se puedan escribir comandos srun interactivamente:
$ salloc -N16 xterm
salloc: Granted job allocation 65537
# (en este punto aparece el xterm, y salloc espera a que xterm salga)
salloc: Relinquishing job allocation 65537
Para obtener una asignación de nodos y lanzar una aplicación paralela en una sola línea de comandos:
$ salloc -N5 srun -n10 myprogram
Para crear un trabajo heterogéneo con 3 componentes, cada uno asignando un conjunto único de nodos:
$ salloc -w node[2-3] : -w node4 : -w node[5-7] bash
salloc: job 32294 queued and waiting for resources
salloc: job 32294 has been allocated resources
salloc: Granted job allocation 32294
