NAME

sane-scsi - Consejos sobre adaptadores SCSI para escáneres

DESCRIPTION

Esta página del manual contiene varios consejos y trucos específicos del sistema operativo sobre cómo hacer que los escáneres con interfaz SCSI funcionen.

INFORMACIÓN GENERAL

Para escáneres con interfaz SCSI, puede ser necesario editar el archivo de configuración del backend apropiado antes de usar SANE por primera vez. Para la mayoría de los sistemas, el archivo de configuración debe listar el nombre del dispositivo SCSI genérico al que está conectado el escáner (por ejemplo, en Linux, /dev/sg4 o /dev/sge es un dispositivo SCSI genérico de este tipo). Es habitual crear un enlace simbólico desde /dev/scanner al dispositivo SCSI genérico al que está conectado el escáner. En este caso, el archivo de configuración simplemente lista la línea /dev/scanner. Para una descripción detallada del archivo de configuración de cada backend, consulte la página del manual del backend correspondiente (por ejemplo, sane-epson(5) para escáneres Epson, sane-hp(5) para escáneres HP, etc.).

Para algunos sistemas operativos (por ejemplo, Linux y OS/2), existe una forma alternativa de especificar los dispositivos de escáner. Esta forma alternativa permite identificar los escáneres por la cadena de proveedor y modelo SCSI y/o por la dirección del dispositivo SCSI (que consta del número de bus, número de canal, id y número de unidad lógica). La sintaxis para especificar un escáner de esta manera es:

scsi PROVEEDOR MODELO TIPO BUS CANAL ID LUN

donde PROVEEDOR es la cadena del proveedor SCSI, MODELO es la cadena del modelo SCSI, TIPO es la cadena del tipo de dispositivo SCSI, BUS es el número de bus SCSI (llamado "host" en /proc/scsi/scsi), CANAL es el número de canal SCSI, ID es el id SCSI y LUN es el número de unidad lógica del dispositivo escáner. Los dos primeros campos son cadenas que deben ir entre comillas dobles si contienen algún espacio en blanco. Los cuatro campos restantes son números enteros no negativos. Los valores correctos para estos campos se pueden encontrar utilizando herramientas específicas del sistema operativo, por ejemplo, para Linux observando la salida del comando cat /proc/scsi/scsi. Para simplificar la configuración, el valor de un campo se puede reemplazar con un asterisco (``*''). Un asterisco tiene el efecto de que se permitirá cualquier valor para ese campo en particular. Esto puede tener el efecto de que una sola línea scsi coincida con varios dispositivos. Cuando esto sucede, cada dispositivo coincidente será sondeado por el backend uno por uno y registrado si el backend cree que es un dispositivo compatible. Por ejemplo, la línea

scsi MUSTEK MFS-06000CX Scanner 0 00 03 00

conectaría el escáner SCSI Mustek con la siguiente entrada de /proc/scsi/scsi:

Host: scsi0 Channel: 00 Id: 03 Lun: 00
  Vendor: MUSTEK   Model: MFS-06000CX Rev: 4.04
  Type:   Scanner  ANSI SCSI revision: 0

Por lo general, es suficiente utilizar solo las cadenas de proveedor y modelo o incluso solo la cadena del proveedor. El siguiente ejemplo

scsi MUSTEK * * * * * *

tendría el efecto de que todos los dispositivos SCSI del sistema con una cadena de proveedor MUSTEK serían sondeados y reconocidos por el backend.

Si el resto de una cadena scsi consiste solo en asteriscos, los asteriscos se pueden omitir. Por ejemplo, la siguiente línea es equivalente a la especificada anteriormente:

scsi MUSTEK

En algunas plataformas (por ejemplo, OpenStep), los nombres de dispositivos SANE tienen una forma especial. Esto se explica a continuación en la sección específica de la plataforma correspondiente.

Al usar un escáner SCSI, asegúrese de que el permiso de acceso para el dispositivo SCSI genérico esté configurado correctamente. Recomendamos agregar un grupo "scanner" a /etc/group que contenga a todos los usuarios que deberían tener acceso al escáner. Luego, el permiso del dispositivo debe establecerse para permitir el acceso de lectura y escritura al grupo. Por ejemplo, si el escáner está en el dispositivo SCSI genérico /dev/sg0, los siguientes dos comandos establecerían el permiso correctamente:

$ chgrp scanner /dev/sg0
$ chmod 660 /dev/sg0

Cuando su sistema utiliza el sistema de archivos de dispositivos (devfs), debe editar /etc/devfs/perms. Allí debería buscar la línea

REGISTER ^sg[^/]* PERMISSIONS root.root 0600

y agregar una nueva línea (por ejemplo, para cambiar los permisos de sg4):

REGISTER ^sg4 PERMISSIONS root.scanner 0660

INFORMACIÓN DE FREEBSD

La configuración automática utilizando las líneas "scsi *" en los archivos de configuración solo funciona si el usuario que ejecuta el frontend tiene acceso de lectura/escritura a /dev/xpt0. En su lugar, también puede configurar un enlace /dev/scanner al dispositivo /dev/uk apropiado.

Adaptec AHA1542CF
Se informa que funciona bien bajo FreeBSD 2.2.2R con el controlador aha.
Adaptec 2940
Se informa que funciona bien bajo FreeBSD 2.2.2.
Adaptec 1522
El escáner se sondea bien, pero cualquier intento de acceder a él congela todo el sistema. Parece que algo está deshabilitando las interrupciones y luego no las vuelve a habilitar, por lo que parece un error en el controlador aic de FreeBSD.
Adaptec 1505
Funciona en FreeBSD 2.2.5R y 3.0 utilizando el controlador aic, siempre que la compatibilidad Plug-and-Play esté deshabilitada en la tarjeta. Si no hay dispositivos uk, simplemente ejecute sh MAKEDEV uk0 en el directorio /dev. El escáner debería ser accesible como /dev/uk0 si se sondeó durante el arranque.
Tekram DC390
Se informa que funciona bien bajo FreeBSD 2.2.2R con el controlador amd.

INFORMACIÓN DE LINUX

Primero, asegúrese de que su kernel tenga habilitado el soporte genérico SCSI. En make xconfig, esto aparece en "SCSI support->SCSI generic support".

Para minimizar los tiempos de escaneo, se recomienda encarecidamente utilizar un tamaño de búfer grande para el controlador genérico SCSI. A partir de la versión 2.0 del controlador SG, el tamaño máximo del búfer se puede cambiar en tiempo de ejecución del programa y no hay restricción en el tamaño. Esta versión del controlador forma parte de los kernels de Linux a partir de la versión 2.2.7. Si el nuevo controlador SG está disponible, algunos backends (por ejemplo, sane-umax(5), sane-mustek(5), sane-sharp(5)) solicitan automáticamente búferes SCSI más grandes. Si un backend no solicita automáticamente un búfer SCSI más grande, establezca la variable de entorno SANE_SG_BUFFERSIZE al tamaño de búfer deseado en bytes. No se recomienda usar más de 1 MB, ya que para valores grandes aumenta la probabilidad de que el controlador SG no pueda asignar el(los) búfer(es) necesario(s). Para tarjetas ISA, incluso 1 MB podría ser un valor demasiado grande. Para una discusión detallada del controlador SCSI SG de Linux, consulte: https://tldp.org/HOWTO/SCSI-Generic-HOWTO.

Para kernels de Linux anteriores a la versión 2.2.7, el tamaño del búfer es de solo 32 KB. Esto funciona, pero para muchos escáneres más baratos, esto hace que el escaneo sea más lento aproximadamente cuatro veces que cuando se usa un tamaño de 127 KB. Linux define el tamaño de este búfer mediante la macro SG_BIG_BUFF en el archivo de cabecera /usr/include/scsi/sg.h. A menos que un sistema tenga escasez grave de memoria, se recomienda aumentar este valor al valor legal máximo de 128*1024-512=130560 bytes. Después de cambiar este valor, es necesario recompilar tanto el kernel (o el módulo genérico SCSI) como los backends SCSI. Tenga en cuenta que esto solo es necesario con kernels de Linux más antiguos.

Un problema común con los escáneres SCSI es qué hacer cuando se inició el sistema mientras el escáner estaba apagado. En tales casos, el kernel no reconocerá el escáner y SANE no podrá acceder a él. Afortunadamente, Linux proporciona un mecanismo simple para sondear un dispositivo SCSI bajo demanda. Suponga que tiene un escáner conectado al bus SCSI 2 y el escáner tiene un ID SCSI de 5. Cuando el sistema esté en funcionamiento y el escáner esté encendido, puede emitir el comando:

echo "scsi add-single-device 2 0 5 0" > /proc/scsi/scsi

y el kernel sondeará y reconocerá su escáner (esto debe hacerse como root). Es

Los escáneres funcionan con los siguientes adaptadores SCSI bajo Linux. Esta lista no está completa, usualmente cualquier adaptador SCSI soportado por Linux debería funcionar.

Adaptadores SCSI Acard/Advance
Algunas versiones antiguas del controlador del kernel (atp870u.c) cortan la información de consulta. Por lo tanto, el escáner no pudo ser detectado correctamente. Usa un kernel actual.
Adaptec AHA-1505/AHA-1542/AHA-2940
Se informa que funciona bien con Linux desde la v2.0. Si encuentras bloqueos del kernel u otro comportamiento inesperado, obtén el último kernel de Linux (la v2.2.17 parece funcionar) o reduce el tamaño del búfer SCSI a 32 kB.
ASUS SC200
Se informa que funciona bien con Linux v2.0.
BusLogic BT958
Para configurar la tarjeta BusLogic, puede que necesites seguir estas instrucciones (aportadas por Jeremy <jeremy@xxedgexx.com>): Durante el arranque, cuando tu adaptador BusLogic se esté inicializando, presiona Ctrl-B para entrar en la configuración de tu adaptador BusLogic. Elige la dirección en la que se encuentra tu BusLogic que contiene tu escáner. Elige ``SCSI Device Configuration''. Elige ``Scan SCSI Bus''. Elige cualquier ID SCSI que contenga tu escáner y luego elige ``View/Modify SCSI configuration''. Cambia ``Negotiation'' a ``async'' y cambia ``Disconnect'' a ``off''. Presiona Esc, guarda, y presiona Esc de nuevo hasta que te pida reiniciar.
NCR/Symbios 53c400/53c400a o Domex DTC3181E/L/LE (DTCT436/436P) tarjeta ISA SCSI
Esta tarjeta es suministrada por Mustek (y otros vendedores). Está soportada desde Linux 2.2. Las tarjetas SCSI son soportadas por el módulo g_NCR5380. Es necesario indicarle al kernel el puerto de E/S y el tipo de tarjeta. Ejemplo para una 53c400a: modprobe g_NCR5380 ncr_addr=0x280 ncr_53c400a=1 . Una vez que el kernel detecte la tarjeta, debería funcionar bien. Sin embargo, aunque debería funcionar, no esperes un buen rendimiento de esta tarjeta; no tiene línea de interrupción y por lo tanto, mientras un escaneo esté en curso, el sistema se vuelve casi inutilizable. Puedes cambiar los valores de las macros USLEEP en drivers/scsi/g_NCR5380.c. Hay algo de documentación en este archivo y en NCR5380.c.
NCR/Symbios 810
Para algunos escáneres puede ser necesario deshabilitar la desconexión/reconexión. Para lograr esto usa la opción ncr53c8xx="disc:n". Algunas personas han informado que sus escáneres solo funcionaron con el controlador 53c7,8xx, no con el ncr53c8xx. Prueba ambos si tienes problemas.
Para kernels de Linux anteriores a la v2.0.33, puede ser necesario aumentar el tiempo de espera SCSI. El tiempo de espera predeterminado para los kernels de Linux anteriores a la v2.0.33 es de 10 segundos, lo cual es demasiado bajo cuando se escanea un área grande. Si recibes mensajes de la forma ``restart (ncr dead ?)'' en tu archivo /var/log/messages o en la consola del sistema, es una indicación de que el tiempo de espera es demasiado corto. En este caso, encuentra la línea ``if (np->latetime>10)'' en el archivo ncr53c8xx.c (normalmente en el directorio /usr/src/linux/drivers/scsi) y cambia la constante 10 por, digamos, 60 (un minuto). Luego recompila el kernel/módulo y vuelve a intentarlo.
Tekram DC315
El controlador se puede descargar de http://www.garloff.de/kurt/linux/dc395/. Para algunos escáneres más antiguos puede ser necesario deshabilitar todas las características más avanzadas usando, por ejemplo, modprobe dc395x_trm dc395x_trm=7,5,1,32.
Tekram DC390
La versión 1.11 del controlador Tekram parece funcionar bien en su mayoría, excepto que el escaneo no termina correctamente (causa un tiempo de espera SCSI después de 10 minutos). El genérico AM53C974 también parece funcionar bien y no sufre los problemas de tiempo de espera.

INFORMACIÓN DE SOLARIS, OPENSTEP Y NEXTSTEP

En Solaris, OpenStep y NeXTStep, el nombre genérico del dispositivo SCSI se refiere a un bus SCSI, no a un dispositivo individual. Por ejemplo, /dev/sg0 se refiere al primer bus SCSI. Para indicarle a SANE qué dispositivo usar, añade el carácter 'a'+target-id al nombre especial del dispositivo. Por ejemplo, el dispositivo SCSI conectado al primer controlador SCSI y con target-id 0 se llamaría /dev/sg0a, y el dispositivo con target-id 1 en ese mismo bus se llamaría /dev/sg0b, y así sucesivamente.

ENTORNO

SANE_DEBUG_SANEI_SCSI
Si la biblioteca fue compilada con el soporte de depuración habilitado, esta variable de entorno controla el nivel de depuración para el subsistema de E/S SCSI genérico. Por ejemplo, un valor de 128 solicita que el backend imprima toda la salida de depuración. Un valor de 255 también imprime mensajes del kernel del subsistema SCSI (donde estén disponibles). Niveles más bajos reducen la verbosidad.
SANE_SCSICMD_TIMEOUT
establece el valor de tiempo de espera para los comandos SCSI en segundos. Sobrescribir el valor predeterminado de 120 segundos solo debería ser necesario para escáneres muy lentos.
