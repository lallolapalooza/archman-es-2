SASLAUTHD(8) Manual del Administrador del Sistema SASLAUTHD(8)

NOMBRE

saslauthd — servidor de autenticación sasl

SINOPSIS

saslauthd -a authmech [-Tvdchlr] [-O opcion] [-m mux_path] [-n hilos] [-s tamaño] [-t tiempo_espera]

DESCRIPCIÓN

saslauthd es un proceso demonio que maneja solicitudes de autenticación en texto plano en nombre de la biblioteca SASL.

El servidor cumple dos roles: aísla todo el código que requiere privilegios de superusuario en un único proceso y puede ser utilizado para proporcionar servicios de autenticación proxy a clientes que no comprenden la autenticación basada en SASL.

saslauthd debe iniciarse desde los scripts de arranque del sistema al pasar al modo multiusuario. Al ejecutarse contra una base de datos de autenticación protegida (por ejemplo, el mecanismo shadow), debe ejecutarse como superusuario. De lo contrario, se recomienda ejecutar el demonio sin privilegios como saslauth:saslauth, lo que requiere que el directorio de ejecución tenga el propietario root:saslauthd. Puede hacerlo siguiendo estos pasos en máquinas que utilizan systemd(1) :

  1. crear el directorio /etc/systemd/system/saslauthd.service.d/
  2. crear el archivo /etc/systemd/system/saslauthd.service.d/user.conf con el contenido 
    [Service]
User=saslauth
Group=saslauth
  3. Recargar el archivo de servicio de systemd: ejecutar "systemctl daemon-reload"

Opciones

Las opciones nombradas por letras minúsculas configuran el propio servidor. Las opciones en mayúsculas controlan el comportamiento de mecanismos de autenticación específicos; su aplicabilidad a un mecanismo de autenticación particular se describe en la sección MECANISMOS DE AUTENTICACIÓN.

-a authmech
Utilizar authmech como mecanismo de autenticación. (Véase la sección MECANISMOS DE AUTENTICACIÓN más abajo.) Este parámetro es obligatorio.
-O opcion
Una opción específica del mecanismo (por ejemplo, nombre de host de rimap o ruta del archivo de configuración)
-H nombre_host
El host remoto al que contactará el mecanismo de autenticación rimap. (Obsoleto, usar -O en su lugar)
-m ruta
Utilizar ruta como la ruta al socket con nombre en el que escuchar las solicitudes de conexión. Debe ser una ruta absoluta y NO debe incluir el sufijo "/mux". Tenga en cuenta que el valor predeterminado para esto es "/var/state/saslauthd" (o lo que se especificó en tiempo de compilación) y que este directorio debe existir para que saslauthd funcione.
-n hilos
Utilizar hilos procesos para responder a las consultas de autenticación. (predeterminado: 5) Un valor de cero indicará que saslauthd debe crear un proceso individual para cada conexión. Esto puede resolver fugas que ocurren en algunas implementaciones.
-s tamaño
Utilizar tamaño como el tamaño de la tabla del tabla hash (en kilobytes)
-t tiempo_espera
Utilizar tiempo_espera como el tiempo de expiración de la caché de autenticación (en segundos)
-T
Respetar las restricciones de inicio de sesión por hora del día.
-h
Mostrar información de uso
-c
Habilitar el almacenamiento en caché de credenciales de autenticación
-l
Deshabilitar el uso de un archivo de bloqueo para controlar el acceso a accept().
-r
Combinar el reino con el inicio de sesión (con un signo '@' en medio). Por ejemplo, inicio de sesión: "foo" reino: "bar" se pasará como inicio de sesión: "foo@bar". Tenga en cuenta que el reino todavía se pasará, lo que puede provocar un comportamiento inesperado para los mecanismos de autenticación que utilizan el reino, sin embargo, para los mecanismos que no lo hacen, como getpwent, esta es la única forma de autenticar usuarios específicos del dominio que comparten el mismo ID de usuario.
-v
Mostrar el número de versión y los mecanismos de autenticación disponibles en la salida de error estándar, luego salir.
-d
Modo de depuración.

Registro de actividad

saslauthd registra sus actividades a través de syslogd utilizando la facilidad LOG_AUTH.

MECANISMOS DE AUTENTICACIÓN

saslauthd soporta uno o más "mecanismos de autenticación", dependiendo de las facilidades proporcionadas por el sistema operativo subyacente. El mecanismo se selecciona mediante la opción -a de la siguiente lista de opciones:

dce
(AIX)

Autenticar utilizando el entorno de autenticación DCE.

getpwent
(Todos las plataformas)

Autenticar utilizando la función de biblioteca getpwent(). Típicamente esto autentica contra el archivo de contraseñas local. Consulte la página del manual getpwent(3) de su sistema para obtener detalles.

kerberos4
(Todos las plataformas)

Autenticar contra el reino Kerberos 4 local. (Consulte la sección NOTAS para ver advertencias sobre este controlador.)

kerberos5
(Todos las plataformas)

Autenticar contra el reino Kerberos 5 local.

pam
(Linux, Solaris)

Autenticar utilizando Módulos de Autenticación Conectables (PAM).

rimap
(Todos las plataformas)

Reenviar solicitudes de autenticación a un servidor IMAP remoto. Este controlador se conecta a un servidor IMAP remoto, especificado usando la opción -O, y intenta iniciar sesión (a través de un comando IMAP 'LOGIN') utilizando las credenciales suministradas al servidor local. Si la autenticación remota tiene éxito, la conexión local también se considera autenticada. La conexión remota se cierra tan pronto como se recibe la respuesta etiquetada del comando 'LOGIN' del servidor remoto.

/var> al parámetro -O describe el servidor remoto al que se reenviarán las solicitudes de autenticación. hostname puede ser un nombre de host (imap.example.com) o una dirección IP en formato de cuatro puntos (192.168.0.1). Esta última es útil si el servidor remoto es multi-homed y tiene interfaces de red que no son alcanzables desde el servidor IMAP local. El host remoto es contactado en el puerto de servicio ‘imap’. Se puede especificar un puerto no predeterminado añadiendo una barra y el nombre o número de puerto al argumento hostname.

La bandera -O y su argumento son obligatorios cuando se utiliza el mecanismo rimap.

shadow
(AIX, Irix, Linux, Solaris)

Autentica contra el "archivo de contraseñas en sombra" local. El mecanismo exacto depende del sistema. saslauthd actualmente entiende las rutinas de biblioteca getspnam() y getuserpw(). Algunos sistemas respetan la bandera -T.

sasldb
(Todas las plataformas)

Autentica contra la base de datos de autenticación SASL. Tenga en cuenta que probablemente no querrá usar esto, e incluso está deshabilitado en tiempo de compilación por defecto. Si desea usar sasldb con la biblioteca SASL, probablemente querrá usar el método de verificación de contraseña "auxprop" junto con el plugin de auxprop sasldb en su lugar.

ldap
(Todas las plataformas que soportan OpenLDAP 2.0 o superior)

Autentica contra un servidor ldap. Los parámetros de configuración de ldap se leen de /usr/local/etc/saslauthd.conf. La ubicación de este archivo se puede cambiar con el parámetro -O. Vea el archivo LDAP_SASLAUTHD incluido con la distribución para obtener la lista de parámetros disponibles.

sia
(Digital UNIX)

Autentica usando la Arquitectura de Integración de Seguridad de Digital UNIX (también conocida como "seguridad mejorada").

NOTAS

El controlador de autenticación kerberos4 consume recursos considerables. Para realizar una autenticación, debe obtener un ticket de concesión de ticket del servidor TGT en cada solicitud de autenticación. Las rutinas de la biblioteca Kerberos que obtienen el TGT también crean un archivo de ticket local, bajo la suposición razonable de que querrá guardar el TGT para su uso por otras aplicaciones Kerberos. Sin embargo, estos archivos de ticket no son utilizables por saslauthd, aunque no hay forma de no crearlos. La sobrecarga de crear y eliminar estos archivos de ticket puede causar una degradación seria del rendimiento en servidores ocupados. (Kerberos nunca fue concebido para ser utilizado de esta manera, de todos modos).

ARCHIVOS

/var/run/saslauthd/mux
El socket de comunicación predeterminado.
/usr/local/etc/saslauthd.conf
El archivo de configuración predeterminado para el soporte ldap.
