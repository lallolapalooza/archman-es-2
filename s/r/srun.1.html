NOMBRE

srun - Ejecuta trabajos paralelos

SINOPSIS

srun [OPCIONES(0)... [ejecutable(0) [argumentos(0)...]]] [ : [OPCIONES(N)...]] ejecutable(N) [argumentos(N)...]

Las opciones definen trabajos múltiples en un trabajo heterogéneo co-programado. Para más detalles sobre trabajos heterogéneos, consulta el documento
https://slurm.schedmd.com/heterogeneous_jobs.html

DESCRIPCIÓN

Ejecuta un trabajo paralelo en el clúster administrado por Slurm. Si es necesario, srun primero creará una asignación de recursos en la que se ejecutará el trabajo paralelo.

El siguiente documento describe la influencia de varias opciones en la asignación de CPUs a trabajos y tareas.
https://slurm.schedmd.com/cpu_management.html

VALOR DE RETORNO

srun devolverá el código de salida más alto de todas las tareas ejecutadas o la señal más alta (con el bit de orden superior establecido en un entero de 8 bits, por ejemplo, 128 + señal) de cualquier tarea que haya finalizado con una señal.
El valor 253 está reservado para errores de falta de memoria.

RESOLUCIÓN DE RUTA DEL EJECUTABLE

El ejecutable se resuelve en el siguiente orden:

1. Si el ejecutable comienza con ".", la ruta se construye como: directorio de trabajo actual / ejecutable
2. Si el ejecutable comienza con "/", la ruta se considera absoluta.
3. Si el ejecutable se puede resolver a través de PATH. Ver path_resolution(7).
4. Si el ejecutable está en el directorio de trabajo actual.

El directorio de trabajo actual es el directorio de trabajo del proceso que llama, a menos que se pase el argumento --chdir, que anulará el directorio de trabajo actual.

OPCIONES

-A, --account=<cuenta>
Cargar los recursos utilizados por este trabajo a la cuenta especificada. La cuenta es una cadena arbitraria. El nombre de la cuenta puede cambiarse después de la submisión del trabajo usando el comando scontrol. Esta opción se aplica a las asignaciones de trabajos.
--acctg-freq=<tipo_dato>=<intervalo>[,<tipo_dato>=<intervalo>...]
Definir los intervalos de muestreo de contabilidad y perfilado del trabajo en segundos. Esto puede usarse para anular el parámetro JobAcctGatherFrequency en el archivo slurm.conf. <tipo_dato>=<intervalo> especifica el intervalo de muestreo de tareas para el plugin jobacct_gather o un intervalo de muestreo para un tipo de perfilado por el plugin acct_gather_profile. Se pueden especificar múltiples pares <tipo_dato>=<intervalo> separados por comas. Los valores de tipo_dato admitidos son:
tarea
Intervalo de muestreo para los plugins jobacct_gather y para el perfilado de tareas por el plugin acct_gather_profile.
NOTA: Esta frecuencia se utiliza para monitorizar el uso de memoria. Si se aplican límites de memoria, la frecuencia más alta que un usuario puede solicitar es la configurada en el archivo slurm.conf. No se puede deshabilitar.
energía
Intervalo de muestreo para el perfilado de energía usando el plugin acct_gather_energy.
red
Intervalo de muestreo para el perfilado de infiniband usando el plugin acct_gather_interconnect.
sistema_archivos
Intervalo de muestreo para el perfilado del sistema de archivos usando el plugin acct_gather_filesystem.

El valor predeterminado para el intervalo de muestreo de tareas es 30 segundos. El valor predeterminado para todos los demás intervalos es 0. Un intervalo de 0 deshabilita el muestreo del tipo especificado. Si el intervalo de muestreo de tareas es 0, la información de contabilidad se recopila solo al finalizar el trabajo (reduciendo la interferencia de Slurm con el trabajo).
Valores más pequeños (no nulos) tienen un mayor impacto en el rendimiento del trabajo, pero un valor de 30 segundos no es probable que sea perceptible para aplicaciones que tengan menos de 10,000 tareas. Esta opción se aplica a las asignaciones de trabajos.

--bb=<espec>
Especificación del buffer de ráfaga. La forma de la especificación depende del sistema. Ver también --bbf. Esta opción se aplica a las asignaciones de trabajos. Cuando se usa la opción --bb, Slurm analiza esta opción y crea un archivo de script de buffer de ráfaga temporal que es utilizado internamente por los plugins del buffer de ráfaga. Ver la guía de buffer de ráfaga de Slurm para más información y ejemplos:
https://slurm.schedmd.com/burst_buffer.html
--bbf=<nombre_archivo>
Ruta del archivo que contiene la especificación del buffer de ráfaga. La forma de la especificación depende del sistema. Ver también --bb. Esta opción se aplica a las asignaciones de trabajos. Ver la guía de buffer de ráfaga de Slurm para más información y ejemplos:
https://slurm.schedmd.com/burst_buffer.html
--bcast[=<ruta_destino>]
Copiar el archivo ejecutable a los nodos de cómputo asignados. Si se especifica un nombre de archivo, copiar el ejecutable al archivo de destino especificado. Si la ruta especificada termina en '/', se trata como un directorio de destino, y el nombre del archivo de destino será slurm_bcast_<job_id>.<step_id>_<nombre_nodo>. Si no se especifica dest_path y está configurado DestDir en BcastParameters de slurm.conf, se utilizará, y el nombre del archivo seguirá el patrón anterior. Si ninguno de los anteriores se especifica, entonces se utiliza --chdir, y el nombre del archivo también seguirá el patrón anterior. Por ejemplo, "srun --bcast=/tmp/mine -N3 a.out" copiará el archivo "a.out" de tu directorio actual al archivo "/tmp/mine" en cada uno de los tres nodos de cómputo asignados y ejecutará ese archivo. Esta opción se aplica a las asignaciones de pasos.
--bcast-exclude={NINGUNO|<ruta_exclusión>[,<ruta_exclusión>...]}
Lista separada por comas de rutas de directorios absolutas que se excluirán al autodetectar y transmitir las dependencias de objetos compartidos ejecutables a través de --bcast. Si se configura la palabra clave "NINGUNO", no se excluirán rutas de directorio. El valor predeterminado es el de BcastExclude de slurm.conf y esta opción lo anula. Ver también --bcast y --send-libs.
-b, --begin=<tiempo>
Aplazar la iniciación de este trabajo hasta la hora especificada. Acepta horas en formato HH:MM:SS para ejecutar un trabajo a una hora específica del día (los segundos son opcionales). (Si esa hora ya ha pasado, se asume el día siguiente.) También puedes especificar midnight, noon, elevenses (11 AM), fika (3 PM) o teatime (4 PM) y puedes tener una hora del día con el sufijo AM o PM para ejecutar por la mañana o por la tarde. También puedes decir qué día se ejecutará el trabajo, especificando una fecha del formato MMDDYY o MM/DD/YY YYYY-MM-DD. Combina fecha y hora usando el siguiente formato YYYY-MM-DD[THH:MM[:SS]]. También puedes dar tiempos como now + contador unidades_de_tiempo, donde las unidades_de_tiempo pueden ser segundos (predeterminado), minutos, horas, días o semanas

srun - submit a job or command to a partition or a set of jobs, or control running jobs

srun [ options ] [ command [ arguments... ] ]

The srun command is used to submit a job for execution. The job can be a single command or a script. The job will be run on the Slurm cluster using the parameters specified by the user. If no command is specified, then srun will start an interactive session on the allocated resources. If a command is specified, srun will execute that command on the allocated resources and upon completion of the command, the resources will be released.

Some options can be specified before the srun command is issued and will be saved with the job, allowing them to be changed after the job has been submitted using the scontrol command. Other options can only be specified when the job is submitted.

The srun command can also be used to manage existing jobs and job steps. If the job id is specified with the -J option and the job is already running, then srun can be used to kill or suspend job steps. This function is primarily intended for job step management.

--begin=<time>
Job will begin at the specified time. The time can be in any format that the date command understands. Some common formats include:
  • HH:MM[:SS][AM|PM]
  • [[CC]YY]MMDDhhmm[.ss]
  • [[[[CC]YY]MM]DD]hhmm[.ss]
  • MM/DD/[YY]YY[
  • MM/DD/YYYY[
  • YYYY-MM-DD[T]HH:MM:SS]
  • now
  • now+

    seconds

  • now+

    minutes

  • now+

    hours

  • now+

    days

  • now+

    weeks

you can tell Slurm to run the job today with the keyword today and to run the job tomorrow with the keyword tomorrow. The value may be changed after job submission using the scontrol command. For example:
   --begin=16:00
   --begin=now+1hour
   --begin=now+60           (seconds by default)
   --begin=2010-01-20T12:34:00

Notes on date/time specifications:
- Although the 'seconds' field of the HH:MM:SS time specification is allowed by the code, note that the poll time of the Slurm scheduler is not precise enough to guarantee dispatch of the job on the exact second. The job will be eligible to start on the next poll following the specified time. The exact poll interval depends on the Slurm scheduler (e.g., 60 seconds with the default sched/builtin).
- If no time (HH:MM:SS) is specified, the default is (00:00:00).
- If a date is specified without a year (e.g., MM/DD) then the current year is assumed, unless the combination of MM/DD and HH:MM:SS has already passed for that year, in which case the next year is used.
This option applies to job allocations.

-D, --chdir=<path>
Have the remote processes do a chdir to path before beginning execution. The default is to chdir to the current working directory of the srun process. The path can be specified as full path or relative path to the directory where the command is executed. This option applies to job allocations.
--cluster-constraint=<list>
Specifies features that a federated cluster must have to have a sibling job submitted to it. Slurm will attempt to submit a sibling job to a cluster if it has at least one of the specified features.
-M, --clusters=<string>
Clusters to issue commands to. Multiple cluster names may be comma separated. The job will be submitted to the one cluster providing the earliest expected job initiation time. The default value is the current cluster. A value of 'all' will query to run on all clusters. Note the --export option to control environment variables exported between clusters. This option applies only to job allocations. Note that the slurmdbd must be up for this option to work properly, unless running in a federation with FederationParameters=fed_display configured.
--comment=<string>
An arbitrary comment. This option applies to job allocations.
--compress[=type]
Compress file before sending it to compute hosts. The optional argument specifies the data compression library to be used. The default is BcastParameters Compression= if set or "lz4" otherwise. Supported values are "lz4". Some compression libraries may be unavailable on some systems. For use with the --bcast option. This option applies to step allocations.
--consolidate-segments
Ensure that all segments from the allocation will be consolidated into one higher-level aggregated block.

This option applies to job allocations. NOTE: This option will only work with the topology/block plugin.

-C, --constraint=<list>
Nodes can have features assigned to them by the Slurm administrator. Users can specify which of these features are required by their job using the constraint option. If you are looking for 'soft' constraints please see --prefer for more information. Only nodes having features matching the job constraints will be used to satisfy the request. Multiple constraints may be specified with AND, OR, matching OR, resource counts, etc. (some operators are not supported on all system types).

NOTE: Changeable features are features defined by a NodeFeatures plugin.

Supported --constraint options include:

Single Name
Only nodes which have the specified feature will be used. For example, --constraint="intel"
Node Count
A request can specify the number of nodes needed with some feature by appending an asterisk and count after the feature name. For example, --nodes=16 --constraint="graphics*4" indicates that the job requires 16 nodes and that at least four of those nodes must have the feature "graphics." If requesting more than one feature and using node counts, the request must have square brackets surrounding it.

NOTE: This option is not supported by the helpers NodeFeatures plugin. Heterogeneous jobs can be used instead.

AND
Only nodes with all of specified features will be used. The ampersand is used for an AND operator. For example, --constraint="intel&gpu"
OR
Only nodes with at least one of specified features will be used. The vertical bar is used for an OR operator. If changeable features are not requested, nodes in the allocation can have different features. For example, salloc -N2 --constraint="intel|amd" can result in a job allocation where one node has the intel feature and the other node has the amd feature. However, if the expression contains a changeable feature, then all OR operators are automatically treated as Matching OR so that all nodes in the job allocation have the same set of features. For example, salloc -N2 --constraint="foo|bar&baz" The job is allocated two nodes where both nodes have foo, or bar and baz (one or both nodes could have foo, bar, and baz). The helpers NodeFeatures plugin will find the first set of node features that matches all nodes in the job allocation; these features are set as active features on the node and passed to RebootProgram (see slurm.conf(5)) and the helper script (see helpers.conf(5)). In this case, the helpers plugin uses the first of "foo" or "bar,baz" that match the two nodes in the job allocation.
Matching OR
If only one of a set of possible options should be used for all allocated nodes, then use the OR operator and enclose the options within square brackets. For example, --constraint="[rack1|rack2|rack3|rack4]" might be used to specify that all nodes must be allocated on a single rack of the cluster, but any of those four racks can be used.
Multiple Counts
Specific counts of multiple resources may be specified by using the AND operator and enclosing the options within square brackets. For example, --constraint="[rack1*2&rack2*4]" might be used to specify that two nodes must be allocated from nodes with the feature of "rack1" and four nodes must be allocated from nodes with the feature "rack2".

NOTE: This option is not supported by the helpers NodeFeatures plugin.

NOTE: Multiple Counts can cause jobs to be allocated with a non-optimal network layout.

Brackets
Brackets can be used to indicate that you are looking for a set of nodes with the different requirements contained within the brackets. For example, --constraint="[(rack1|rack2)*1&(rack3)*2]" will get you one node with either the "rack1" or "rack2" features and two nodes with the "rack3" feature. If requesting more than one feature and using node counts, the request must have square brackets surrounding it.

NOTE: Brackets are only reserved for Multiple Counts and Matching OR syntax. AND operators require a count for each feature inside square brackets (i.e. "[quad*2&hemi*1]"). Slurm will only allow a single set of bracketed constraints per job.

NOTE: Square brackets are not supported by the helpers NodeFeatures plugin. Matching OR can be requested without square brackets by using the vertical bar character with at least one changeable feature.

Parentheses
Parentheses can be used to group like node features together. For example, --constraint="[(knl&snc4&flat)*4&haswell*1]" might be used to specify that four nodes with the features "knl", "snc4" and "flat" plus one node with the feature "haswell" are required. Parentheses can also be used to group operations. Without parentheses, node features are parsed strictly from left to right. For example, --constraint="foo&bar|baz" requests nodes with foo and bar, or baz. --constraint="foo|bar&baz" requests nodes with foo and baz, or bar and baz (note how baz was AND'd with everything). --constraint="foo&(bar|baz)" requests nodes with foo and at least one of bar or baz. NOT
 E: OR dentro de los paréntesis no debe usarse con un plugin KNL NodeFeatures, pero sí es compatible con los ayudantes del plugin NodeFeatures.

-S, --core-spec=<num>
Número de núcleos especializados por nodo reservados por el trabajo para operaciones del sistema y no utilizados por la aplicación. Si AllowSpecResourcesUsage está habilitado, un trabajo puede anular el CoreSpecCount de todos sus nodos asignados con esta opción. Los núcleos especializados anulados seguirán reservados para procesos del sistema. El trabajo obtendrá una asignación implícita de --exclusive para el resto de los núcleos en los nodos, lo que resultará en que los procesos del trabajo puedan usar (y se les cobre por) todos los núcleos de los nodos, excepto los núcleos especializados anulados. Esta opción no se puede usar con la opción --thread-spec.

NOTA: Establecer explícitamente el valor de núcleos especializados de un trabajo establece implícitamente la opción --exclusive.

Esta opción se aplica a las asignaciones de trabajos.

--cores-per-socket=<núcleos>
Restringe la selección de nodos a aquellos con al menos el número especificado de núcleos por socket. Ver información adicional bajo la opción -B arriba cuando el plugin task/affinity está habilitado. Esta opción se aplica a las asignaciones de trabajos.
--cpu-bind=[{quiet|verbose},]<tipo>
Vincula tareas a CPUs. Se utiliza solo cuando el plugin task/affinity está habilitado. NOTA: Para que Slurm informe siempre sobre la vinculación de CPU seleccionada para todos los comandos ejecutados en un shell, puede habilitar el modo detallado estableciendo la variable de entorno SLURM_CPU_BIND en el valor "verbose".

Las siguientes variables de entorno informativas se establecen cuando se utiliza --cpu-bind:

SLURM_CPU_BIND_VERBOSE
SLURM_CPU_BIND_TYPE
SLURM_CPU_BIND_LIST

Consulte la sección VARIABLES DE ENTORNO para obtener una descripción más detallada de las variables individuales de SLURM_CPU_BIND. Estas variables solo están disponibles si el plugin task/affinity está configurado.

Al usar --cpus-per-task para ejecutar tareas multihilo, tenga en cuenta que la vinculación de CPU se hereda del proceso padre. Esto significa que la tarea multihilo debe especificar o limpiar la vinculación de CPU por sí misma para evitar que todos los hilos de la tarea multihilo utilicen la misma máscara/CPU que el padre. Alternativamente, se podrían usar máscaras amplias (máscaras que especifican más de una CPU permitida) para las tareas con el fin de proporcionar múltiples CPUs para las tareas multihilo.

Tenga en cuenta que un paso de trabajo puede recibir diferentes números de CPUs en cada nodo o recibir CPUs que no comienzan en la ubicación cero. Por lo tanto, se recomienda una de las opciones que generan automáticamente la vinculación de tareas. Las máscaras o vinculaciones especificadas explícitamente solo se respetan cuando el paso de trabajo ha recibido todas las CPUs disponibles en el nodo.

Vincular una tarea a un dominio de localidad NUMA significa vincular la tarea al conjunto de CPUs que pertenecen al dominio de localidad NUMA o "nodo NUMA". Si se utilizan opciones de dominio de localidad NUMA en sistemas sin soporte NUMA, cada socket se considera un dominio de localidad.

Si no se utiliza la opción --cpu-bind, el modo de vinculación predeterminado dependerá de la configuración de Slurm y de la asignación de recursos del paso. Si todos los nodos asignados tienen el mismo modo CpuBind configurado, se utilizará ese. De lo contrario, si la Partición del trabajo tiene un modo CpuBind configurado, se utilizará ese. De lo contrario, si Slurm tiene un valor configurado de TaskPluginParam, se utilizará ese modo. De lo contrario, se realizará una vinculación automática como se describe a continuación.

Vinculación Automática
Se aplica solo cuando task/affinity está habilitado. Si la asignación del paso de trabajo incluye una asignación con un número de sockets, núcleos o hilos igual al número de tareas por cpus-por-tarea, entonces las tareas se vincularán por defecto a los recursos apropiados (vinculación automática). Deshabilite este modo de operación estableciendo explícitamente "--cpu-bind=none". Utilice TaskPluginParam=autobind=[threads|cores|sockets] para establecer una vinculación de CPU predeterminada en caso de que la "vinculación automática" no encuentre una coincidencia.
Las opciones admitidas incluyen:
q[uiet]
Vincula silenciosamente antes de que se ejecute la tarea (predeterminado)
v[erbose]
Informa detalladamente sobre la vinculación antes de que se ejecute la tarea
no[ne]
No vincular tareas a CPUs (predeterminado a menos que se aplique vinculación automática)
map_cpu:<lista>
Vincula estableciendo máscaras de CPU en tareas (o rangos) según lo especificado, donde <lista> es <cpu_id_para_tarea_0>,<cpu_id_para_tarea_1>,... Si el número de tareas (o rangos) excede el número de elementos en esta lista, los elementos de la lista se reutilizarán según sea necesario comenzando desde el principio de la lista. Para simplificar el soporte para grandes cantidades de tareas, las listas pueden seguir un mapa con un asterisco y un recuento de repetición. Por ejemplo, "map_cpu:0*4,3*4".
mask_cpu:<lista>
Vincula estableciendo máscaras de CPU en tareas (o rangos) según lo especificado, donde <lista> es <cpu_mask_para_tarea_0>,<cpu_mask_para_tarea_1>,... El mapeo se especifica para un nodo y se aplica un mapeo idéntico a las tareas en cada nodo (es decir, la tarea de menor ID en cada nodo se mapea a la primera máscara especificada en la lista, etc.). Las máscaras de CPU se interpretan siempre como valores hexadecimales, pero pueden ir precedidas de un '0x' opcional. Si el número de tareas (o rangos) excede el número de elementos en esta lista, los elementos de la lista se reutilizarán según sea necesario comenzando desde el principio de la lista. Para simplificar el soporte para grandes cantidades de tareas, las listas pueden seguir un mapa con un asterisco y un recuento de repetición. Por ejemplo, "mask_cpu:0x0f*4,0xf0*4".
rank_ldom
Vincula a un dominio de localidad NUMA por rango. No compatible a menos que todo el nodo sea asignado al trabajo.
map_ldom:<lista>
Vincula mapeando IDs de dominio de localidad NUMA a tareas según lo especificado, donde <lista> es <ldom1>,<ldom2>,...<ldomN>. Los IDs de dominio de localidad se interpretan como valores decimales a menos que vayan precedidos de '0x', en cuyo caso se interpretan como valores hexadecimales. No compatible a menos que todo el nodo sea asignado al trabajo.
mask_ldom:<lista>
Vincula estableciendo máscaras de dominio de localidad NUMA en tareas según lo especificado, donde <lista> es <mask1>,<mask2>,...<maskN>. Las máscaras de dominio de localidad NUMA se interpretan siempre como valores hexadecimales, pero pueden ir precedidas de un '0x' opcional. No compatible a menos que todo el nodo sea asignado al trabajo.
sockets
Genera automáticamente máscaras que vinculan tareas a sockets. Solo se utilizarán las CPUs del socket que se hayan asignado al trabajo. Si el número de tareas difiere del número de sockets asignados, esto puede resultar en una vinculación subóptima.
cores
Genera automáticamente máscaras que vinculan tareas a núcleos. Si el número de tareas difiere del número de núcleos asignados, esto puede resultar en una vinculación subóptima.
threads
Genera automáticamente máscaras que vinculan tareas a hilos. Si el número de tareas difiere del número de hilos asignados, esto puede resultar en una vinculación subóptima.
ldoms
Genera automáticamente máscaras que vinculan tareas a dominios de localidad NUMA. Si el número de tareas difiere del número de dominios de localidad asignados, esto puede resultar en una vinculación subóptima.
ayuda
Mostrar mensaje de ayuda para cpu-bind
Esta opción se aplica a las asignaciones de trabajos y pasos.
--cpu-freq=<p1>[-p2][:p3]

Solicitar que el paso de trabajo iniciado por este comando srun se ejecute a una frecuencia solicitada, si es posible, en las CPUs seleccionadas para el paso en los nodos de cómputo.

p1 puede ser [#### | bajo | medio | alto | alto-1] lo que establecerá la velocidad de escalado de frecuencia a su valor correspondiente y establecerá el gobernador de escalado de frecuencia a UserSpace. Ver abajo para la definición de los valores.

p1 puede ser [Conservador | OnDemand | Rendimiento | AhorroEnergía] lo que establecerá el gobernador de escalado a su valor correspondiente. El gobernador debe estar en la lista establecida por la opción slurm.conf `CpuFreqGovernors`.

Cuando p2 está presente, p1 será la frecuencia mínima de escalado y p2 será la frecuencia máxima de escalado. En ese caso, el gobernador p3 o `CpuFreqDef` no puede ser UserSpace, ya que no admite un rango.

p2 puede ser [#### | medio | alto | alto-1]. p2 debe ser mayor que p1 y es incompatible con el gobernador UserSpace.

p3 puede ser [Conservador | OnDemand | Rendimiento | AhorroEnergía | SchedUtil | UserSpace] lo que establecerá el gobernador a su valor correspondiente.

Si p3 es UserSpace, la velocidad de escalado de frecuencia, la frecuencia máxima de escalado y la frecuencia mínima de escalado se establecerán estáticamente al valor definido por p1.

Cualquier frecuencia solicitada por debajo de la frecuencia mínima disponible se redondeará a la frecuencia mínima disponible. De la misma manera, cualquier frecuencia solicitada por encima de la frecuencia máxima disponible se redondeará a la frecuencia máxima disponible.

El parámetro CpuFreqDef en slurm.conf se usará para establecer el gobernador en ausencia de p3. Si no hay CpuFreqDef, el gobernador predeterminado será usar el gobernador actual del sistema establecido en cada cpu. Por lo tanto, especificar un rango sin CpuFreqDef o un gobernador específico no está permitido.

NOTA: Establecer la frecuencia solo para las CPUs del paso de trabajo implica que las tareas están confinadas a esas CPUs. Si el confinamiento de tareas (es decir, si el plugin de tareas `task`/`affinity` está habilitado, o si el plugin de tareas `task`/`cgroup` está habilitado con `ConstrainCores=yes` establecido en `cgroup.conf`) no está configurado, este parámetro se ignora.

--cpus-per-gpu=<ncpus>
Solicitar que se asignen ncpus procesadores por GPU asignada. Esta opción implica `--exact`. No es compatible con la opción --cpus-per-task.

Esta opción se aplica a las asignaciones de trabajos y pasos.

-c, --cpus-per-task=<ncpus>
Solicitar que se asignen ncpus por proceso. Esto puede ser útil si el trabajo es multihilo y requiere más de una CPU por tarea para un rendimiento óptimo. Solicitar explícitamente esta opción implica `--exact`. El valor predeterminado es una CPU por proceso y no implica `--exact`. Si se especifica `-c` sin `-n`, se asignarán tantas tareas por nodo como sea posible, cumpliendo la restricción de `-c`. Por ejemplo, en un clúster con 8 CPUs por nodo, una solicitud de trabajo para 4 nodos y 3 CPUs por tarea puede asignar 3 o 6 CPUs por nodo (1 o 2 tareas por nodo) dependiendo del consumo de recursos por otros trabajos. Un trabajo así podría no ser capaz de ejecutar más de un total de 4 tareas.

ADVERTENCIA: Existen configuraciones y opciones interpretadas de manera diferente por las solicitudes de trabajos y pasos de trabajo que pueden resultar en inconsistencias para esta opción. Por ejemplo, `srun -c2 --threads-per-core=1 prog` puede asignar dos núcleos para el trabajo, pero si cada uno de esos núcleos contiene dos hilos, la asignación del trabajo incluirá cuatro CPUs. La asignación del paso de trabajo lanzará entonces dos hilos por CPU para un total de dos tareas.

ADVERTENCIA: Cuando srun se ejecuta desde dentro de salloc o sbatch, existen configuraciones y opciones que pueden resultar en asignaciones inconsistentes cuando -c tiene un valor mayor que -c en salloc o sbatch.

NOTA: Si también se especifica `--mem-per-cpu`, el número de CPUs asignadas puede aumentar si se supera `MaxMemPerCPU`. En caso de que no se especifique `-n`, el número de tareas puede ser mayor de lo esperado.

Esta opción se aplica a las asignaciones de trabajos y pasos.

--deadline=<OPT>

Tenga en cuenta que si ni `DefaultTime` ni `MaxTime` están configurados en la partición en la que se encuentra el trabajo, el trabajo deberá especificar alguna forma de límite de tiempo (--time[-min]) si se va a usar una fecha límite.

Los formatos de tiempo válidos son:
HH:MM[:SS] [AM|PM]
MMDD[AA] o MM/DD[/AA] o MM.DD[.AA]
MM/DD[/AA]-HH:MM[:SS]
AAAA-MM-DD[THH:MM[:SS]]]
now[+cuenta[segundos(predeterminado)|minutos|horas|días|semanas]]

--delay-boot=<minutos>
No reiniciar nodos para satisfacer la especificación de características de este trabajo si el trabajo ha sido elegible para ejecutarse durante menos de este período de tiempo. Si el trabajo ha esperado durante menos del período especificado, utilizará solo los nodos que ya tengan las características especificadas. El argumento está en unidades de minutos. Un valor predeterminado puede ser establecido por un administrador del sistema usando la opción `delay_boot` del parámetro de configuración `SchedulerParameters` en el archivo slurm.conf, de lo contrario, el valor predeterminado es cero (sin demora).

Esta opción se aplica solo a las asignaciones de trabajos.

-d, --dependency=<lista_de_dependencia>
Aplazar el inicio de este trabajo hasta que se satisfagan las dependencias especificadas. Una vez que se satisface una dependencia, se elimina del trabajo. Esta opción no se aplica a los pasos de trabajo (ejecuciones de srun dentro de una asignación existente de salloc o sbatch) solo a las asignaciones de trabajos. <lista_de_dependencia> tiene el formato <tipo:id_trabajo[:id_trabajo][,tipo:id_trabajo[:id_trabajo]]> o <tipo:id_trabajo[:id_trabajo][?tipo:id_trabajo[:id_trabajo]]>. Todas las dependencias deben satisfacerse si se usa el separador ",". Se puede satisfacer cualquier dependencia si se usa el separador "?". Solo se puede usar un separador. Por ejemplo: 
-d aftero
k:20:21,afterany:23 significa que el trabajo solo puede ejecutarse después de un código de retorno 0 de los trabajos 20 y 21 Y la finalización del trabajo 23. Sin embargo: 
-d afterok:20:21?afterany:23
significa que cualquiera de las condiciones (afterok:20 O afterok:21 O afterany:23) será suficiente para liberar el trabajo. Muchos trabajos pueden compartir la misma dependencia y estos trabajos pueden incluso pertenecer a diferentes usuarios. El valor puede ser modificado después de la presentación del trabajo usando el comando scontrol. Se permiten dependencias en trabajos remotos en una federación. Una vez que una dependencia de trabajo falla debido a el estado de terminación de un trabajo anterior, el trabajo dependiente nunca se ejecutará incluso si el trabajo anterior se reinicia y tiene un estado de terminación diferente en una ejecución posterior. Esta opción se aplica a las asignaciones de trabajos.
after:job_id[[+time][:jobid[+time]...]]
Después de que los trabajos especificados comiencen o se cancelen y ocurra 'time' en minutos desde el inicio o cancelación del trabajo, este trabajo puede comenzar su ejecución. Si no se proporciona 'time', no hay retraso después del inicio o cancelación.
afterany:job_id[:jobid...]
Este trabajo puede comenzar su ejecución después de que los trabajos especificados hayan terminado. Este es el tipo de dependencia predeterminado.
afterburstbuffer:job_id[:jobid...]
Este trabajo puede comenzar su ejecución después de que los trabajos especificados hayan terminado y se hayan completado las operaciones de escritura de las etapas del búfer de ráfaga asociadas.
aftercorr:job_id[:jobid...]
Una tarea de esta matriz de trabajos puede comenzar su ejecución después de que la tarea correspondiente ID en el trabajo especificado se haya completado con éxito (se ejecutó hasta la finalización con un código de salida cero). Si el trabajo especificado no es una matriz, se trata lo mismo que afterok.
afternotok:job_id[:jobid...]
Este trabajo puede comenzar su ejecución después de que los trabajos especificados hayan terminado en algún estado fallido (código de salida distinto de cero, fallo de nodo, tiempo de espera agotado, etc.). Este trabajo debe ser presentado mientras el trabajo especificado aún está activo o dentro de MinJobAge segundos después de que el trabajo especificado haya terminado. Si el ID del trabajo dependiente no se encuentra y está en el mismo clúster que la presentación del trabajo, el trabajo es rechazado. Si el ID del trabajo dependiente no se encuentra y está en un clúster diferente del de la presentación del trabajo, la dependencia se marca como fallida.
afterok:job_id[:jobid...]
Este trabajo puede comenzar su ejecución después de que los trabajos especificados se hayan ejecutado con éxito (se ejecutaron hasta la finalización con un código de salida cero). Este trabajo debe ser presentado mientras el trabajo especificado aún está activo o dentro de MinJobAge segundos después de que el trabajo especificado haya terminado. Si el ID del trabajo dependiente no se encuentra y está en el mismo clúster que la presentación del trabajo, el trabajo es rechazado. Si el ID del trabajo dependiente no se encuentra y está en un clúster diferente del de la presentación del trabajo, la dependencia se marca como fallida.
singleton
Este trabajo puede comenzar su ejecución después de que cualquier trabajo previamente lanzado que comparta el mismo nombre de trabajo y usuario haya terminado. En otras palabras, solo un trabajo con ese nombre y propiedad de ese usuario puede estar en ejecución o suspendido en cualquier momento. En una federación, una dependencia singleton debe cumplirse en todos los clústeres a menos que se use DependencyParameters=disable_remote_singleton en slurm.conf.
-X, --disable-status
Deshabilita la visualización del estado de las tareas cuando srun recibe una única SIGINT (Ctrl-C). En su lugar, reenvía inmediatamente la SIGINT al trabajo en ejecución. Sin esta opción, se requiere un segundo Ctrl-C en un segundo para terminar forzosamente el trabajo y srun saldrá inmediatamente. También puede establecerse a través de la variable de entorno SLURM_DISABLE_STATUS. Esta opción se aplica a las asignaciones de trabajos.
-m, --distribution={*|block|cyclic|arbitrary|plane=<size>}[:{*|block|cyclic|fcyclic}[:{*|block|cyclic|fcyclic}]][,{Pack|NoPack}]

Especifica métodos de distribución alternativos para procesos remotos. Para la asignación de trabajos, esto establece variables de entorno que serán utilizadas por solicitudes srun posteriores. La distribución de tareas afecta la asignación de trabajos en la última etapa de la evaluación de recursos disponibles por el plugin cons_tres. En consecuencia, otras opciones (por ejemplo, --ntasks-per-node, --cpus-per-task) pueden afectar la selección de recursos antes de la distribución de tareas. Para asegurar una distribución de tareas específica, los trabajos deben tener acceso a nodos completos, lo que se puede lograr usando la opción --exclusive o solicitando todos los recursos del nodo.

Esta opción controla la distribución de tareas a los nodos en los que se han asignado recursos, y la distribución de esos recursos a las tareas para la vinculación (afinidad de tareas). El primer método de distribución (antes de los dos puntos) controla la distribución de tareas a los nodos. El segundo método de distribución (después de los dos puntos) controla la distribución de las CPU asignadas a través de los sockets para la vinculación a tareas. El tercer método de distribución (después del segundo par de dos puntos) controla la distribución de las CPU asignadas a través de los núcleos para la vinculación a tareas. Las segunda y tercera distribuciones se aplican solo si la afinidad de tareas está habilitada. La tercera distribución solo se admite si el plugin de tarea/cgroup está configurado. El valor predeterminado para cada tipo de distribución se especifica mediante *.

Tenga en cuenta que con select/cons_tres, el número de CPU asignadas a cada socket y nodo puede ser diferente. Consulte https://slurm.schedmd.com/mc_support.html para obtener más información sobre la asignación de recursos, la distribución de tareas a los nodos y la vinculación de tareas a CPU.

Primer método de distribución (distribución de tareas entre nodos):
*
Utiliza el método predeterminado para distribuir tareas a los nodos (bloque).
block
El método de distribución por bloques distribuirá las tareas a un nodo de tal manera que las tareas consecutivas compartan un nodo. Por ejemplo, considere una asignación de tres nodos cada uno con dos CPU. Una solicitud de distribución por bloques de cuatro tareas distribuirá esas tareas a los nodos con las tareas uno y dos en el primer nodo, la tarea tres en el segundo nodo y la tarea cuatro en el tercer nodo. La distribución por bloques es el comportamiento predeterminado si el número de tareas excede el número de nodos asignados.
cyclic
El método de distribución cíclica distribuirá las tareas a un nodo de tal manera que las tareas consecutivas se distribuyan en nodos consecutivos (de forma cíclica). Por ejemplo, considere una asignación de tres nodos cada uno con dos CPU. Una solicitud de distribución cíclica de cuatro tareas distribuirá esas tareas a los nodos con las tareas uno y cuatro en el primer nodo, la tarea dos en el segundo nodo y la tarea tres en el tercer nodo. Tenga en cuenta que cuando SelectType es select/cons_tres, es posible que no se asignen la misma cantidad de CPU en cada nodo. La distribución de tareas será cíclica entre todos los nodos con CPU aún por asignar a tareas. La distribución cíclica es el comportamiento predeterminado si el número de tareas no es mayor que el número de nodos asignados. nodos.
plane
Las tareas se distribuyen en bloques de tamaño <size>. El tamaño debe proporcionarse o debe establecerse SLURM_DIST_PLANESIZE. El número de tareas distribuidas a cada nodo es el mismo que para la distribución cíclica, pero los ids de tarea asignados a cada nodo dependen del tamaño del plano. No se pueden combinar especificaciones de distribución adicionales con esta opción. Para más detalles (incluyendo ejemplos y diagramas), consulte https://slurm.schedmd.com/mc_support.html y https://slurm.schedmd.com/dist_plane.html
arbitrary
El método de distribución arbitraria asignará procesos en orden según lo enumerado en el archivo designado por la variable de entorno SLURM_HOSTFILE. Si se enumera esta variable, anulará cualquier otro método especificado. Si no se establece, el método predeterminará a bloque. Dentro del archivo de hosts debe contener como mínimo el número de hosts solicitados y ser uno por línea o separado por comas. Si se especifica un recuento de tareas (-n, --ntasks=<número>), sus tareas se distribuirán en los nodos en el orden del archivo.
NOTA: La opción de distribución arbitraria en una asignación de trabajos solo controla los nodos que se asignarán al trabajo y no la asignación de CPU en esos nodos. Esta opción está destinada principalmente a controlar la disposición de las tareas de un paso de trabajo en una asignación de trabajo existente para el comando srun.
NOTA: Si se proporciona el número de tareas y también una lista de nodos solicitados, el número de nodos utilizados de esa lista se reducirá para que coincida con el número de tareas si el número de nodos en la lista es mayor que el número de tareas.

Segundo método de distribución (distribución de CPU entre sockets para vinculación):

*
Utiliza el método predeterminado para distribuir CPU entre sockets (cíclico).
block
El método de distribución por bloques distribuirá las CPUs asignadas de forma consecutiva del mismo socket para enlazarlas a las tareas, antes de usar el siguiente socket consecutivo.
cyclic
El método de distribución cíclica distribuirá las CPUs asignadas para enlazarlas a una tarea dada de forma consecutiva desde el mismo socket, y desde el siguiente socket consecutivo para la siguiente tarea, en modo de ronda a través de los sockets. Las tareas que requieran más de una CPU tendrán todas esas CPUs asignadas en un único socket si es posible.
NOTA: En nodos con hyper-threading habilitado, una tarea que no solicite núcleos completos puede distribuirse entre sockets. Esto puede evitarse especificando --ntasks-per-core=1, lo que fuerza a las tareas a asignar núcleos completos.
fcyclic
El método de distribución fcyclic distribuirá las CPUs asignadas para enlazarlas a las tareas desde sockets consecutivos en modo de ronda a través de los sockets. Las tareas que requieran más de una CPU tendrán cada CPU asignada de forma cíclica entre los sockets.

Tercer método de distribución (distribución de CPUs entre núcleos para el enlace):

*
Utiliza el método predeterminado para distribuir CPUs entre núcleos (heredado del segundo método de distribución).
block
El método de distribución por bloques distribuirá las CPUs asignadas de forma consecutiva desde el mismo núcleo para enlazarlas a las tareas, antes de usar el siguiente núcleo consecutivo.
cyclic
El método de distribución cíclica distribuirá las CPUs asignadas para enlazarlas a una tarea dada de forma consecutiva desde el mismo núcleo, y desde el siguiente núcleo consecutivo para la siguiente tarea, en modo de ronda a través de los núcleos.
fcyclic
El método de distribución fcyclic distribuirá las CPUs asignadas para enlazarlas a las tareas desde núcleos consecutivos en modo de ronda a través de los núcleos.

Control opcional para la distribución de tareas en nodos:

Pack
En lugar de distribuir uniformemente las tareas de un paso de trabajo en sus nodos asignados, agruparlas lo más posible en los nodos. Esto solo se aplica cuando se utiliza el método de distribución de tareas "block".
NoPack
En lugar de agrupar las tareas de un paso de trabajo lo más posible en los nodos, distribuirlas uniformemente. Esta opción de usuario anulará el parámetro de configuración CR_Pack_Nodes de SelectTypeParameters.
Esta opción se aplica a las asignaciones de trabajos y pasos.
--epilog={none|<executable>}
srun ejecutará el ejecutable justo después de que el paso de trabajo se complete. Los argumentos de la línea de comandos para el ejecutable serán el comando y los argumentos del paso de trabajo. Si se especifica none, no se ejecutará ningún epílogo de srun. Este parámetro anula el parámetro SrunEpilog en slurm.conf. Este parámetro es completamente independiente del parámetro Epilog en slurm.conf. Esta opción se aplica a las asignaciones de trabajos.
-e, --error=<patrón_nombre_archivo>
Especifica cómo se redirige stderr. Por defecto, en modo interactivo, srun redirige stderr al mismo archivo que stdout, si se especifica uno. La opción --error se proporciona para permitir que stdout y stderr se redirijan a ubicaciones diferentes. Consulte Redirección de IO más abajo para ver más opciones. Si el archivo especificado ya existe, se sobrescribirá. Esta opción se aplica a las asignaciones de trabajos y pasos.
--exact
Permite que un paso acceda solo a los recursos solicitados para el paso. Por defecto, todos los recursos no GRES en cada nodo del paso asignado se utilizarán. Esta opción solo se aplica a los pasos.
NOTA: Los pasos paralelos se bloquearán o rechazarán hasta que los recursos de paso solicitados estén disponibles, a menos que se especifique --overlap. Los recursos del trabajo pueden retenerse después de la finalización de un comando srun mientras Slurm realiza la limpieza del trabajo. Los epílogos de paso y/o los plugins SPANK pueden retrasar aún más la liberación de los recursos del paso.
-x, --exclude={<host1[,<host2>...]|<nombre_archivo>}
Solicita que una lista específica de hosts no se incluya en los recursos asignados a este trabajo. La lista de hosts se asumirá como un nombre de archivo si contiene un carácter "/". Esta opción se aplica a las asignaciones de trabajos y pasos.
--exclusive[={user|mcs|topo}]
Esta opción se aplica a las asignaciones de trabajos y pasos de trabajos, y tiene dos significados ligeramente diferentes para cada uno.

Cuando se utiliza para iniciar un trabajo, la asignación del trabajo no puede compartir nodos (o segmento de topología con "=topo") con otros trabajos en ejecución (o solo con otros usuarios con la opción "=user" o la opción "=mcs"). Si no se especifican user/mcs/topo (es decir, la asignación del trabajo no puede compartir nodos con otros trabajos en ejecución), la asignación del trabajo recibe todas las CPUs y GRES de todos los nodos de la asignación, pero solo se le asigna la memoria que solicitó. Esto es intencional para soportar la programación de pandillas, ya que los trabajos suspendidos aún residen en la memoria. Para solicitar toda la memoria de un nodo, utilice --mem=0. El comportamiento predeterminado compartido/exclusivo depende de la configuración del sistema y la opción OverSubscribe de la partición tiene precedencia sobre la opción del trabajo. NOTA: Dado que los GRES compartidos (MPS) no se pueden asignar al mismo tiempo que un GRES compartido (GPU), esta opción solo asigna todos los GRES compartidos y ningún GRES subyacente compartido.

Esta opción también se puede utilizar al iniciar más de un paso de trabajo dentro de una asignación de recursos existente (predeterminado), donde desea que procesadores separados se dediquen a cada paso de trabajo. El paso de trabajo solo recibe la cantidad de GRES que se solicita. Si no hay suficientes procesadores disponibles para iniciar el paso de trabajo, se pospondrá. Esto puede considerarse un mecanismo para la gestión de recursos dentro del trabajo en su asignación (se implica --exact). La asignación exclusiva de CPUs se aplica a los pasos de trabajo de forma predeterminada, pero --exact no es el valor predeterminado. En otras palabras, el comportamiento predeterminado es el siguiente: los pasos de trabajo no compartirán CPUs, pero a los pasos de trabajo se les asignarán todas las CPUs disponibles para el trabajo en todos los nodos asignados a los pasos.

Para compartir recursos, utilice la opción --overlap.

NOTA: Esta opción es mutuamente excluyente con --oversubscribe.

--export={[ALL,]<variables_entorno>|ALL|NONE}
Identifica qué variables de entorno del entorno de envío se propagan a la aplicación iniciada.
--export=ALL
Modo predeterminado si no se especifica --export. Todo el entorno del usuario se cargará desde el entorno del llamador.
--export=NONE
Ninguno del entorno del usuario se definirá. El usuario debe utilizar la ruta absoluta al binario a ejecutar que definirá el entorno. El usuario no puede especificar variables de entorno explícitas con "NONE".

Esta opción es particularmente importante para trabajos que se envían en un clúster y se ejecutan en un clúster diferente (por ejemplo, con rutas diferentes). Para evitar que los pasos hereden la configuración de exportación del entorno (por ejemplo, "NONE") del comando sbatch, establezca --export=ALL o la variable de entorno SLURM_EXPORT_ENV debe establecerse en "ALL".

--export=[ALL,]<variables_entorno>
Exporta todas las variables de entorno SLURM* junto con las variables explícitamente definidas. Se deben separar varios nombres de variables de entorno por comas. Se pueden especificar nombres de variables de entorno para propagar el valor actual (por ejemplo, "--export=EDITOR") o se pueden exportar valores específicos (por ejemplo, "--export=EDITOR=/bin/emacs"). Si se especifica "ALL", todas las variables de entorno del usuario se cargarán y tendrán precedencia sobre cualquier variable de entorno explícitamente dada.
Ejemplo: --export=EDITOR,ARG1=test
En este ejemplo, el entorno propagado solo contendrá la variable EDITOR del entorno del usuario, las variables de entorno SLURM_* y ARG1=test.
Ejemplo: --export=ALL,EDITOR=/bin/emacs
Hay dos resultados posibles para este ejemplo. Si el llamador tiene la variable de entorno EDITOR definida, entonces el entorno del trabajo heredará la variable del entorno del llamador. Si el llamador
no tiene una variable de entorno definida para EDITOR, entonces el entorno del trabajo usará el valor dado por --export.
--external-launcher
Crea un paso especial en uno o más nodos asignados que no consumirá recursos, pero tendrá acceso a todos los recursos del trabajo asignados en los nodos.

Las opciones como --ntasks-per-*, --mem*, --cpus*, --tres*, --gres*, serán ignoradas.

Esto está destinado a ser utilizado por implementaciones MPI que requieren su propio lanzador. Esto lanza un paso con acceso a todos los recursos y que luego generará cualquier número de procesos de usuario con acceso a todos estos recursos.

El uso de recursos dentro de este paso especial aún se contabilizará si los plugins de contabilidad están habilitados. Este paso especial puede solaparse con cualquier otro paso.

NOTA: Esta opción no está pensada para ser utilizada directamente.

--mem-bind=[{quiet|verbose},]<tipo>
Vincular tareas a la memoria. Se utiliza solo cuando el plugin task/affinity está habilitado y las funciones de memoria NUMA están disponibles. Tenga en cuenta que la resolución de la vinculación de CPU y memoria puede diferir en algunas arquitecturas. Por ejemplo, la vinculación de CPU puede realizarse a nivel de los núcleos dentro de un procesador, mientras que la vinculación de memoria se realizará a nivel de nodos, donde la definición de "nodos" puede diferir entre sistemas. Memoria mínima requerida por CPU asignada utilizable. Las unidades predeterminadas son megabytes. Se pueden especificar diferentes unidades utilizando el sufijo [K|M|G|T]. El valor predeterminado es DefMemPerCPU y el valor máximo es MaxMemPerCPU (ver excepción a continuación). Si están configurados, ambos parámetros se pueden ver usando el comando scontrol show config. Tenga en cuenta que si el valor --mem-per-cpu del trabajo excede el MaxMemPerCPU configurado, entonces el límite del usuario se tratará como un límite de memoria por tarea; --mem-per-cpu se reducirá a un valor no mayor que MaxMemPerCPU; se establecerá --cpus-per-task y el valor de --cpus-per-task multiplicado por el nuevo valor de --mem-per-cpu será igual al valor original de --mem-per-cpu especificado por el usuario. Este parámetro generalmente se usaría si iprocesadores individuales se asignan a los trabajos (SelectType=select/cons_tres). Si los recursos se asignan por núcleo, socket o nodos completos, entonces el número de CPU asignados a un trabajo puede ser mayor que el número de tareas y el valor de --mem-per-cpu debe ajustarse en consecuencia. Especificar un límite de memoria de cero para un paso de trabajo restringirá el paso de trabajo a la cantidad de memoria asignada al trabajo, pero no eliminará ninguna de las asignaciones de memoria del trabajo para que no esté disponible para otros pasos de trabajo. Ver también --mem y --mem-per-gpu. Las opciones --mem, --mem-per-cpu y --mem-per-gpu son mutuamente excluyentes.

NOTA: Si la cantidad final de memoria solicitada por un trabajo no puede ser satisfecha por ninguno de los nodos configurados en la partición, el trabajo será rechazado. Esto podría suceder si se usa --mem-per-cpu con la opción --exclusive para una asignación de trabajo y --mem-per-cpu multiplicado por el número de CPU en un nodo es mayor que la memoria total de ese nodo.

NOTA: Esto se aplica a las CPU **utilizables** asignadas en una asignación de trabajo. Esto es importante cuando se configura más de un hilo por núcleo. Si un trabajo solicita --threads-per-core con menos hilos en un núcleo de los que existen en el núcleo (o --hint=nomultithread que implica --threads-per-core=1), el trabajo no podrá utilizar esos hilos adicionales en el núcleo y esos hilos no se incluirán en el cálculo de memoria por CPU. Pero si el trabajo tiene acceso a todos los hilos del núcleo, esos hilos se incluirán en el cálculo de memoria por CPU, incluso si el trabajo no los solicitó explícitamente.

En los siguientes ejemplos, cada núcleo tiene dos hilos.

En este primer ejemplo, dos tareas pueden ejecutarse en hiper-hilos separados en el mismo núcleo porque no se usa --threads-per-core. La tercera tarea utiliza ambos hilos del segundo núcleo. La memoria asignada por cpu incluye todos los hilos:

$ sacct -j $SLURM_JOB_ID -X -o jobid%7,reqtres%35,alloctres%35
  JobID                             ReqTRES                           AllocTRES
------- ----------------------------------- -----------------------------------
  17199     billing=3,cpu=3,mem=300M,node=1     billing=4,cpu=4,mem=400M,node=1

En este segundo ejemplo, debido a --threads-per-core=1, a cada tarea se le asigna un núcleo completo pero solo puede usar un hilo por núcleo. Las CPU asignadas incluyen todos los hilos en cada núcleo. Sin embargo, la memoria asignada por cpu incluye solo el hilo utilizable en cada núcleo.

$ salloc -n3 --mem-per-cpu=100 --threads-per-core=1
salloc: Granted job allocation 17200
$ sacct -j $SLURM_JOB_ID -X -o jobid%7,reqtres%35,alloctres%35
  JobID                             ReqTRES                           AllocTRES
------- ----------------------------------- -----------------------------------
  17200     billing=3,cpu=3,mem=300M,node=1     billing=6,cpu=6,mem=300M,node=1

-n, --ntasks=<número>
Especifica el número de tareas a ejecutar. Solicita que srun asigne recursos para ntasks tareas. El valor predeterminado es una tarea por nodo, pero ten en cuenta que la opción --cpus-per-task cambiará este valor predeterminado. Esta opción se aplica a las asignaciones de trabajos y pasos.

Solicita que se invoquen como máximo ntasks en cada núcleo. Esta opción se aplica a las asignaciones de trabajos y pasos. Está pensada para usarse con la opción --ntasks. Relacionada con --ntasks-per-node, pero a nivel de núcleo en lugar de a nivel de nodo. Si se establece en 1, implicará --cpu-bind=cores. --ntasks-per-gpu=<ntasks>
Solicita que se invoquen ntasks tareas por cada GPU. Esta opción puede funcionar de dos maneras: 1) o bien se especifica --ntasks además, en cuyo caso se determinará automáticamente una especificación de GPU sin tipo para satisfacer --ntasks-per-gpu, o 2) se especifican las GPUs deseadas (por ejemplo, mediante --gpus o --gres) sin especificar --ntasks, y el recuento total de tareas se determinará automáticamente. Esta opción establecerá implícitamente --tres-bind=gres/gpu:single:<ntasks>, pero eso se puede anular con una especificación explícita de --tres-bind=gres/gpu. Esta opción no es compatible con un rango de nodos (es decir, -N<minnodes-maxnodes>). Esta opción no es compatible con --gpus-per-task, --gpus-per-socket o --ntasks-per-node. Esta opción no se admite a menos que esté configurado SelectType=cons_tres (directa o indirectamente en sistemas Cray).
--ntasks-per-node=<ntasks>
Solicita que se invoquen ntasks en cada nodo. Si se usa con la opción --ntasks, la opción --ntasks tendrá prioridad y --ntasks-per-node se tratará como un recuento *máximo* de tareas por nodo. Está pensada para usarse con la opción --nodes. Está relacionada con --cpus-per-task=ncpus, pero no requiere conocimiento del número real de CPU en cada nodo. En algunos casos, es más conveniente poder solicitar que no se invoquen más de un número específico de tareas en cada nodo. Ejemplos de esto incluyen la presentación de una aplicación híbrida MPI/OpenMP donde solo se debe asignar una "tarea/rango" MPI a cada nodo, permitiendo que la parte OpenMP utilice todo el paralelismo presente en el nodo, o la presentación de un único trabajo de configuración/limpieza/monitorización a cada nodo de una asignación preexistente como un paso en un script de trabajo más grande. Esta opción se aplica a las asignaciones de trabajos.
--ntasks-per-socket=<ntasks>
Solicita que se invoquen como máximo ntasks en cada socket. Esta opción se aplica a la asignación de trabajos, pero no a las asignaciones de pasos. Está pensada para usarse con la opción --ntasks. Relacionada con --ntasks-per-node, pero a nivel de socket en lugar de a nivel de nodo. Se generarán automáticamente máscaras para enlazar las tareas a sockets específicos, a menos que se especifique --cpu-bind=none. NOTA: Esta opción no se admite cuando se utiliza SelectType=select/linear.

-o, --output=<patrón_nombre_archivo>
Especifica el "patrón de nombre de archivo" para la redirección de stdout. Por predeterminado, en modo interactivo, srun recopila la salida estándar de todas las tareas y envía esta salida a través de TCP/IP a la terminal conectada. Con --output, la salida estándar se puede redirigir a un archivo, a un archivo por tarea o a /dev/null. -O, --overcommit
Sobresuscripción de recursos. Esta opción se aplica a las asignaciones de trabajos y pasos.

Cuando se aplica a una asignación de trabajo (sin incluir trabajos que solicitan acceso exclusivo a los nodos), los recursos se asignan como si se solicitara una tarea por nodo. Esto significa que el número solicitado de CPU por tarea (-c, --cpus-per-task) se asigna por nodo en lugar de multiplicarse por el número de tareas. Las opciones utilizadas para especificar el número de tareas por nodo, socket, núcleo, etc., se ignoran.

Cuando se aplica a las asignaciones de pasos de trabajo (el comando srun cuando se ejecuta dentro de una asignación de trabajo existente), esta opción se puede utilizar para lanzar más de una tarea por CPU. Normalmente, srun no asignará más de un proceso por CPU. Al especificar --overcommit, se permite explícitamente más de un proceso por CPU. Sin embargo, no se permite que más de MAX_TASKS_PER_NODE tareas se ejecuten por nodo. NOTA: MAX_TASKS_PER_NODE se define en el archivo slurm.h y no es una variable, se establece en el momento de la compilación de Slurm.

--overlap
Especificar --overlap permite que los pasos compartan todos los recursos (CPU, memoria y GRES) con todos los demás pasos. Un paso que utilice esta opción se superpondrá a todos los demás pasos, incluso a aquellos que no especificaron --overlap.

Por defecto, los pasos no comparten recursos con otros pasos paralelos. Esta opción se aplica a las asignaciones de pasos.

-s, --oversubscribe
La asignación del trabajo puede sobresuscibir recursos con otros trabajos en ejecución. Los recursos a sobresuscibir pueden ser nodos, sockets, núcleos y/o hyperthreads, dependiendo de la configuración. [verbose,]<tipo>...] Especifique una lista de recursos (tres) con sus opciones de enlace de tarea. Actualmente, gres son los únicos tres compatibles para esta opción. Especifique gres como "gres/<nombre_gres>" (por ejemplo, gres/gpu).

Ejemplo: --tres-bind=gres/gpu:verbose,map:0,1,2,3+gres/nic:closest

Por defecto, la mayoría de los tres no están enlazados a tareas individuales.

Opciones de tipo de enlace compatibles para gres:

closest
Enlace cada tarea a los gres que están más cerca. En un entorno NUMA, cada tarea puede enlazarse a más de un gres (es decir, todos los gres de ese entorno NUMA).
map:<lista>
Enlace estableciendo máscaras de gres en tareas (o ranks) según lo especificado, donde <lista> es <id_gres_para_tarea_0>,<id_gres_para_tarea_1>,... Los IDs de gres se interpretan como valores decimales. Si el número de tareas (o ranks) excede el número de elementos en esta lista, los elementos de la lista se reutilizarán según sea necesario comenzando desde el principio de la lista. Para simplificar el soporte para grandes cantidades de tareas, las listas pueden seguir un mapa con un asterisco y un recuento de repetición. Por ejemplo, "map:0*4,1*4". Si el plugin de tarea/cgroup se utiliza y ConstrainDevices está configurado en cgroup.conf, entonces los IDs de gres son índices basados en cero relativos a los gres asignados al trabajo (por ejemplo, el primer gres es 0, incluso si el ID global es 3). De lo contrario, los IDs de gres son IDs globales, y todos los gres en cada nodo del trabajo deben asignarse para obtener resultados de enlace predecibles.
mask:<lista>
Enlace estableciendo máscaras de gres en tareas (o ranks) según lo especificado, donde <lista> es <máscara_gres_para_tarea_0>,<máscara_gres_para_tarea_1>,... El mapeo se especifica para un nodo y se aplica un mapeo idéntico a las tareas en cada nodo (es decir, la tarea con el ID más bajo en cada nodo se mapea a la primera máscara especificada en la lista, etc.). Las máscaras de gres siempre se interpretan como valores hexadecimales, pero pueden ir precedidas de un '0x' opcional. Para simplificar el soporte para grandes recuentos de tareas, las listas pueden seguir un mapa con un asterisco y un recuento de repetición. Por ejemplo, "mask:0x0f*4,0xf0*4". Si el plugin de tarea/cgroup se utiliza y ConstrainDevices está configurado en cgroup.conf, entonces los IDs de gres son índices basados en cero relativos al gres asignado al trabajo (por ejemplo, el primer gres es 0, incluso si el ID global es 3). De lo contrario, los IDs de gres son IDs globales, y todos los gres en cada nodo del trabajo deben asignarse para obtener resultados de enlace predecibles.
none
No enlazar tareas a este gres (deshabilita el enlace implícito de --tres-per-task y --gpus-per-task).
per_task:<gres_por_tarea>
Cada tarea se enlazará a la cantidad de gres especificada en <gres_por_tarea>. Las tareas se asignan preferentemente gres con afinidad a los núcleos en su asignación, como en closest, aunque tomarán cualquier gres si no están disponibles. Si no hay afinidad, la primera tarea recibirá los primeros x números de gres en el nodo, etc. Los gres compartidos preferirán enlazar un dispositivo compartido por tarea si es posible.
single:<tareas_por_gres>
Similar a closest, excepto que cada tarea solo puede enlazarse a un único gres, incluso cuando puede enlazarse a múltiples gres que están igualmente cerca. El gres al que se enlazará se determina por <tareas_por_gres>, donde las primeras <tareas_por_gres> tareas se enlazan al primer gres disponible, las siguientes <tareas_por_gres> tareas se enlazan al segundo gres disponible, etc. Básicamente, se trata de una distribución en bloques de tareas a gres disponibles, donde los gres disponibles se determinan por la afinidad del socket de la tarea y la afinidad del socket del gres según lo especificado en el parámetro Cores de gres.conf.

NOTA: El enlace de gres compartidos está actualmente limitado a per_task o none.

--tres-per-task=<lista>
Especifica una lista separada por comas de recursos rastreables requeridos para el trabajo en cada tarea que se lanzará en la asignación de recursos del trabajo. El formato de cada entrada en la lista es "tipo_tres[/nombre_tres]=cantidad". El tipo_tres es el tipo de recurso rastreable solicitado (por ejemplo, cpu, gres, licencia, etc.). El nombre_tres es el nombre del recurso rastreable, como se puede ver con sacctmgr show tres. Esto es necesario cuando existe para tipos de tres como gres, licencia, etc. (por ejemplo, gpu, gpu:a100). Para solicitar una licencia con esta opción, la(s) licencia(s) deben definirse en el parámetro AccountingStorageTRES de slurm.conf. La cantidad es el número de esos recursos.
La cantidad puede tener un sufijo de
"k" o "K" (múltiplo de 1024),
"m" o "M" (múltiplo de 1024 x 1024),
"g" o "G" (múltiplo de 1024 x 1024 x 1024),
"t" o "T" (múltiplo de 1024 x 1024 x 1024 x 1024),
"p" o "P" (múltiplo de 1024 x 1024 x 1024 x 1024 x 1024).
Ejemplos: 
--tres-per-task=cpu=4
--tres-per-task=cpu=8,license/ansys=1
--tres-per-task=gres/gpu=1
--tres-per-task=gres/gpu:a100=2
Los recursos especificados se asignarán al trabajo en cada nodo. Los recursos rastreables disponibles son configurables por el administrador del sistema.
NOTA: Esta opción con gres/gpu o gres/shard establecerá implícitamente --tres-bind=gres/[gpu|shard]:per_task:<tres_por_tarea>, o si se especifican varios tipos de gpu --tres-bind=gres/gpu:per_task:<suma_gpu_por_tarea_tipo>. Esto puede ser anulado con una especificación explícita de --tres-bind.
NOTA: Los TRES no válidos para --tres-per-task incluyen bb,billing,energy,fs,mem,node,pages,vmem.
-u, --unbuffered
Por defecto, la conexión entre slurmstepd y la aplicación lanzada por el usuario es a través de una tubería. La salida estándar (stdio) escrita por la aplicación se almacena en búfer en glibc hasta que se vacía o la salida se establece como sin búfer. Consulte setbuf(3). Si se especifica esta opción, las tareas se ejecutan con una pseudo-terminal para que la salida de la aplicación no tenga búfer. Esta opción se aplica a las asignaciones de pasos.

--wait-for-children
Espera a que todos los procesos de cada tarea finalicen antes de considerar una tarea como terminada. El comportamiento predeterminado sin esta opción es esperar solo a que el proceso padre de cada tarea finalice.

Dependiendo de la configuración de --kill-on-bad-exit, la tarea puede terminar si el proceso padre sale con un código de salida distinto de cero. Si --kill-on-bad-exit=1 y el proceso padre sale con un código de salida distinto de cero, la tarea terminará. Si --kill-on-bad-exit=0 y el proceso padre sale con un código de salida distinto de cero, la tarea continuará hasta que todos los procesos hijos hayan terminado.

Esta opción requiere proctrack/cgroup y cgroup/v2.

-W, --wait=<segundos>
Especifica cuánto tiempo esperar después de que la primera tarea termine antes de terminar todas las tareas restantes. Un valor de 0 indica una espera ilimitada (se emitirá una advertencia después de 60 segundos). El valor predeterminado lo establece el parámetro WaitTime en el archivo de configuración de slurm (consulte slurm.conf(5)). Esta opción puede ser útil para garantizar que un trabajo se termine de manera oportuna en caso de que una o más tareas terminen prematuramente. Nota: La opción -K, --kill-on-bad-exit tiene prioridad sobre -W, --wait para terminar el trabajo inmediatamente si una tarea sale con un código de salida distinto de cero. Esta opción se aplica a las asignaciones de trabajos.

srun enviará la solicitud de trabajo al controlador de trabajos de slurm, luego iniciará todos los procesos en los nodos remotos. Si la solicitud no se puede satisfacer de inmediato, srun se bloqueará hasta que los recursos estén libres para ejecutar el trabajo. Si se especifica la opción -I (--immediate), srun terminará si los recursos no están disponibles de inmediato.

Al iniciar procesos remotos, srun propagará el directorio de trabajo actual, a menos que se especifique --chdir=<ruta>, en cuyo caso ruta se convertirá en el directorio de trabajo para los procesos remotos.

Las opciones -n, -c y -N controlan cómo se asignarán las CPU y los nodos al trabajo. Al especificar solo el número de procesos a ejecutar con -n, se asigna un valor predeterminado de una CPU por proceso. Al especificar el número de CPU requeridas por tarea (-c), se pueden asignar más de una CPU por proceso. Si se especifica el número de nodos con -N, srun intentará asignar al menos el número de nodos especificado.

Se pueden usar combinaciones de las tres opciones anteriores para cambiar cómo se distribuyen los procesos entre nodos y CPU. Por ejemplo, al especificar tanto el número de procesos como el número de nodos en los que ejecutar, se implica el número de procesos por nodo. Sin embargo, si el número de CPU por proceso es más importante que el número de procesos (-n) y el número de CPU por proceso (-c), se deben especificar.

srun se negará a asignar más de un proceso por CPU a menos que también se especifique --overcommit (-O).

srun intentará cumplir las especificaciones anteriores "como mínimo". Es decir, si se solicitan 16 nodos para 32 procesos, y algunos nodos no tienen 2 CPU, la asignación de nodos aumentará para satisfacer la demanda de CPU. En otras palabras, se están solicitando un mínimo de 16 nodos. Sin embargo, si se solicitan 16 nodos para 15 procesos, srun lo considerará un error, ya que 15 procesos no pueden ejecutarse en 16 nodos.

Redirección de E/S

De forma predeterminada, stdout y stderr se redirigirán desde todas las tareas a stdout y stderr de srun, y stdin se redirigirá desde la entrada estándar de srun a todas las tareas remotas. Si solo se va a leer stdin por un subconjunto de las tareas iniciadas, puede ser preferible especificar un archivo del que leer en lugar de reenviar stdin desde el comando srun, ya que evita mover y almacenar datos que nunca se leerán.

Para OS X, la función poll() no admite stdin, por lo que la entrada desde un terminal no es posible.

Este comportamiento se puede cambiar con las opciones --output, --error e --input (-o, -e, -i). Tenga en cuenta que --error no redirigirá stderr de srun en sí, solo stderr de las tareas. Las especificaciones de formato válidas para estas opciones son

all
stdout y stderr se redirigen desde todas las tareas a srun. stdin se transmite a todas las tareas. (Este es el comportamiento predeterminado)
none
No se recibe stdout ni stderr de ninguna tarea. No se envía stdin a ninguna tarea (stdin se cierra).
taskid
stdout y/o stderr se redirigen solo desde la tarea con el ID relativo igual a taskid, donde 0 <= taskid <= ntasks, donde ntasks es el número total de tareas en el paso de trabajo actual. stdin se redirige desde la entrada estándar de srun a esta misma tarea. Este archivo se escribirá en el nodo que ejecuta la tarea.
filename
srun redirigirá stdout y/o stderr al archivo con nombre desde todas las tareas. stdin se redirigirá desde el archivo con nombre y se transmitirá a todas las tareas del trabajo. filename se refiere a una ruta en el host que ejecuta srun. Dependiendo de la configuración del sistema de archivos del clúster, esto puede hacer que la salida aparezca en diferentes lugares dependiendo de si el trabajo se ejecuta en modo batch.
patrón de nombre de archivo
srun permite usar un patrón de nombre de archivo para generar el archivo de E/S con nombre descrito anteriormente. La siguiente lista de especificadores de formato se puede usar en la cadena de formato para generar un nombre de archivo que sea único para un determinado jobid, stepid, nodo o tarea. En cada caso, se abren los archivos apropiados y se asocian con las tareas correspondientes. Tenga en cuenta que cualquier cadena de formato que contenga %t, %n y/o %N se escribirá en el nodo que ejecuta la tarea en lugar de en el nodo donde se ejecuta srun.
\\
No procesar ninguno de los símbolos de reemplazo.
%%
El carácter "%".
%A
Número de asignación principal del array de trabajos.
%a
Número de ID (índice) del array de trabajos.
%J
jobid.stepid del trabajo en ejecución (por ejemplo, "128.0"). El stepid solo se expande para pasos regulares, no para pasos especiales como "batch" o "extern".
%j
jobid del trabajo en ejecución.
%S
SLUID del trabajo en ejecución.
%s
stepid del trabajo en ejecución.
%N
nombre de host corto. Esto creará un archivo de E/S separado por nodo.
%n
Identificador de nodo relativo al trabajo actual (por ejemplo, "0" es el primer nodo del trabajo en ejecución). Esto creará un archivo de E/S separado por nodo.
%t
Identificador de tarea (rango) relativo al trabajo actual. Esto creará un archivo de E/S separado por tarea.
%u
Nombre de usuario.
%x
Nombre del trabajo.

Se puede colocar un número entre el carácter de porcentaje y el especificador de formato para rellenar con ceros el resultado en el nombre del archivo de E/S hasta un mínimo del número especificado. Este número se ignora si el especificador de formato corresponde a datos no numéricos (por ejemplo, %N). El número máximo es 10; si se utiliza un valor mayor que 10, el resultado se rellena hasta 10 caracteres. A continuación, se incluyen algunos ejemplos de cómo se puede utilizar la cadena de formato para un paso de trabajo de 4 tareas con un JobID de 128 y un step id de 0:

job%J.out
job128.0.out
job%4j.out
job0128.out
job%2j-%2t.out
job128-00.out, job128-01.out, ...

RENDIMIENTO

La ejecución de srun envía una llamada a procedimiento remoto a slurmctld. Si llegan suficientes llamadas de srun u otros comandos cliente de Slurm que envían llamadas a procedimiento remoto al demonio slurmctld al mismo tiempo, puede resultar en una degradación del rendimiento del demonio slurmctld, lo que podría resultar en una denegación de servicio.

No ejecute srun u otros comandos cliente de Slurm que envíen llamadas a procedimiento remoto a slurmctld desde bucles en scripts de shell u otros programas. Asegúrese de que los programas limiten las llamadas a srun al mínimo necesario para la información que está intentando recopilar.

SEñALES Y SECUENCIAS DE ESCAPE

Las señales enviadas al comando srun se reenvían automáticamente a las tareas que está controlando con algunas excepciones. La secuencia de escape <control-c> informará del estado de todas las tareas asociadas con el comando srun. Si se introduce <control-c> dos veces en un segundo, se enviará la señal SIGINT asociada a todas las tareas y se iniciará una secuencia de terminación que enviará SIGCONT, SIGTERM y SIGKILL a todas las tareas generadas. Si se recibe un tercer <control-c>, el programa srun se terminará sin esperar a que las tareas remotas salgan o a que su E/S se complete.

La secuencia de escape <control-z> se ignora actualmente.

SOPORTE MPI

El uso de MPI depende del tipo de MPI que se esté utilizando. Existen tres modos de operación fundamentalmente diferentes utilizados por estas diversas implementaciones de MPI.

1. Slurm lanza directamente las tareas y realiza la inicialización de las comunicaciones a través de las API PMI2 o PMIx. Por ejemplo: "srun -n16 a.out".

2. Slurm crea una asignación de recursos para el trabajo y luego mpirun lanza las tareas utilizando la infraestructura de Slurm (OpenMPI).

3. Slurm crea una asignación de recursos para el trabajo y luego mpirun lanza las tareas utilizando un mecanismo distinto de Slurm, como SSH o RSH. Estas tareas se inician fuera del monitoreo o control de Slurm. Se debe configurar el epílogo de Slurm para purgar estas tareas cuando se ceda la asignación del trabajo, o se recomienda encarecidamente el uso de pam_slurm_adopt.

Consulte https://slurm.schedmd.com/mpi_guide.html para obtener más información sobre el uso de estas diversas implementaciones de MPI con Slurm.

CONFIGURACIÓN DE MÚLTIPLES PROGRAMAS

Los comentarios en el archivo de configuración deben tener un "#" en la columna uno. El archivo de configuración contiene los siguientes campos separados por espacios en blanco:

Rango de tarea
Uno o más rangos de tarea para usar esta configuración. Se pueden separar múltiples valores con comas. Se pueden indicar rangos con dos números separados por un "-" con el número más pequeño primero (por ejemplo, "0-4" y no "4-0"). Para indicar todas las tareas no especificadas de otra manera, especifique un rango de '*' como la última línea del archivo. Si se intenta iniciar una tarea para la que no se ha definido ningún programa ejecutable, se producirá el siguiente mensaje de error: "No se especificó ningún programa ejecutable para esta tarea".
Ejecutable
El nombre del programa a ejecutar. Puede ser una ruta de acceso completamente calificada si se desea.
Argumentos
Argumentos del programa. La expresión "%t" se reemplazará por el número de la tarea. La expresión "%o" se reemplazará por el desplazamiento de la tarea dentro de este rango (por ejemplo, un valor de rango de tarea configurado de "1-5" tendría valores de desplazamiento de "0-4"). Se pueden usar comillas simples para evitar que los valores encerrados se interpreten. Este campo es opcional. Cualquier argumento para el programa introducido en la línea de comandos se añadirá a los argumentos especificados en el archivo de configuración.

Por ejemplo:

$ cat silly.conf
###################################################################
# Archivo de configuración de múltiples programas de srun
#
# srun -n8 -l --multi-prog silly.conf
###################################################################
4-6       hostname
1,7       echo  task:%t
0,2-3     echo  offset:%o
$ srun -n8 -l --multi-prog silly.conf
0: offset:0
1: task:1
2: offset:1
3: offset:2
4: linux15.llnl.gov
5: linux16.llnl.gov
6: linux17.llnl.gov
7: task:7

Este ejemplo demuestra cómo los trabajos que no se dividen uniformemente entre varios nodos pueden tener problemas de que las tareas no puedan iniciarse cuando hay suficientes CPUs libres para ejecutar esa tarea en un solo nodo. $ echo $SLURM_NODELIST; echo $SLURM_JOB_CPUS_PER_NODE

Si se inicia una tarea que ocupa las CPUs en el nodo con menos CPUs, entonces una tarea posterior que debería poder iniciarse en el otro nodo no se iniciará porque hereda el requisito del número de nodos de la asignación del trabajo. $ srun -n4 --exact sleep 1800 &

$ srun -n2 --exact hostname

Si se inicia el paso del trabajo, solicitando explícitamente un solo nodo, entonces el paso puede ejecutarse.

$ srun -n2 -N1 --exact hostname

node02

Este comportamiento se puede cambiar agregando SelectTypeParameters=CR_Pack_Nodes a su slurm.conf. La lógica para empaquetar nodos permitirá que los pasos del trabajo comiencen en un solo nodo sin tener que solicitar explícitamente un solo nodo.

$ srun -l --exclusive  bash -c 'grep Cpus_allowed_list /proc/self/status'

Agregar una solicitud para un cierto número de tareas hará que cada tarea solo tenga acceso a una sola CPU.
