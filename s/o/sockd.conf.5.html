SOCKD.CONF(5) Manual de formatos de archivo SOCKD.CONF(5)

NOMBRE

sockd.conf - Sintaxis del archivo de configuración del servidor Dante

DESCRIPCIÓN

El archivo de configuración del servidor Dante controla tanto los controles de acceso como el registro. Se divide en tres partes: configuración del servidor, reglas y rutas.

Tenga en cuenta que la configuración del servidor debe venir antes que las reglas y las rutas.

Una línea puede comentarse usando el carácter de comentario estándar #.

CONFIGURACIÓN DEL SERVIDOR

La configuración del servidor controla el comportamiento genérico del servidor. Cada palabra clave está separada de su valor por un carácter :.

Las siguientes palabras clave están disponibles:

clientmethod
Una lista de métodos de autenticación aceptables para las reglas de cliente, enumerados en orden de preferencia. Estos son métodos de autenticación que se comprobarán inmediatamente después de que el cliente SOCKS se haya conectado a Dante, y antes de que se haya iniciado cualquier negociación de socks.

Los valores admitidos son pam.address, pam.any, none y rfc931.

Para todos los métodos, la autenticación se basará únicamente en la dirección IP del cliente, posiblemente en combinación con una búsqueda rfc931 ("ident") hacia el host en el que se está ejecutando el cliente.

Cualquier credencial proporcionada durante esta pasada también estará disponible para su uso en reglas de socks posteriores, cuando se evalúe la solicitud de socks del cliente.

El valor predeterminado para esta palabra clave son todos los métodos que puedan ser necesarios para los métodos de autenticación basados en socks posteriores, según se especifica en los valores de la palabra clave global socksmethod. Normalmente, no necesitará establecer esta palabra clave, ya que Dante la establecerá en el valor correcto por sí mismo.

compatibility
Con la palabra clave sameport, el servidor intenta utilizar el mismo puerto en el lado externo del servidor que el que utilizó el cliente en el lado interno del servidor. Esto es normalmente el valor predeterminado, pero cuando se proporciona esta opción, también se utilizará con puertos privilegiados, lo que significa que si un cliente se conecta a Dante desde un puerto privilegiado, Dante intentará conectarse al destino también desde un puerto privilegiado. Puede haber problemas de seguridad asociados con esto, por lo que normalmente no se debe establecer esta opción.

La palabra clave draft-5.05 habilitará el uso de partes del borrador socks v5-05. La única característica de este borrador que Dante admite es la extensión "USECLIENTSPORT". Tenga en cuenta que existe una interpretación conflictiva de esta extensión, por lo que habilitarla podría impedir que los clientes que utilizan la interpretación conflictiva funcionen correctamente. Solo afecta a UDP.

cpu
La configuración de CPU para los diversos tipos de procesos de Dante. Tenga en cuenta que la posibilidad de configurar estas opciones depende de la plataforma en la que se esté ejecutando Dante. No todas las plataformas pueden proporcionar soporte para este tipo de configuración de CPU.

Hay cuatro tipos de procesos: mother, negotiate, request y io.

Las opciones admitidas actualmente son:

schedule.<tipo de proceso>: <política de planificación>/<prioridad>.

Ejemplo: cpu.schedule.mother: SCHED_FIFO/20 Lo anterior solicita que el kernel planifique el(los) proceso(s) madre utilizando una política de primero en entrar, primero en salir, con prioridad 20.

El valor predeterminado es no solicitar ninguna planificación específica.

mask.<tipo de proceso>: <id de cpu 1> [id de cpu 1 ...]/any.

Ejemplo: cpu.mask.mother: any Ejemplo: cpu.mask.io: 0 1

La máscara da control sobre la(s) CPU/núcleo(s) en la(s) que se ejecutarán los diferentes tipos de procesos. Especificar el valor predeterminado (all) permite que el tipo de proceso se ejecute en cualquier id de CPU. Especificar uno o más ids de CPU numéricos limita el proceso a ese conjunto de CPUs.

Las palabras clave de CPU (schedule y mask) en la mayoría de los casos no serán necesarias. Si se van a utilizar, los procesos io son donde se realiza la mayor parte del trabajo y el ajuste de la prioridad o el uso de la CPU es lo que probablemente tendrá el efecto de rendimiento más significativo en el rendimiento del cliente y la sobrecarga del servidor. Los otros procesos se utilizan principalmente durante el establecimiento de conexiones/sesiones y los cambios en la configuración de los procesos que no son de E/S afectarán principalmente a estas operaciones.

El valor predeterminado es no limitar los procesos a ninguna CPU específica.

debug
Imprimir información de depuración en los registros. El valor establece el nivel de depuración.
errorlog
Este valor se puede establecer para recibir solo la salida de registro relacionada con errores. Tenga en cuenta que esto no incluye errores específicos del cliente, sino solo errores "globales" más graves.

Los valores posibles son los mismos que para la palabra clave logoutput mencionada a continuación.

La intención es tener un lugar especial donde solo se registren los errores graves para que puedan descubrirse rápidamente. El valor predeterminado es no tener ningún lugar especial para registrar errores.

external
La dirección que se utilizará para las conexiones salientes. La dirección proporcionada puede ser una dirección IP o un nombre de interfaz. Se puede proporcionar varias veces para diferentes direcciones.
external.log.<loglevel>.error
Ver internal.log.<loglevel>.error. Esta opción tiene una sintaxis y semántica idénticas, pero se aplica a los errores relacionados con el lado de la interfaz externa.
external.protocol
Por defecto, Dante utilizará las familias de direcciones especificadas y disponibles, y no es necesario establecer esta palabra clave.

Sin embargo, en algunos casos, el operador puede desear especificar una dirección en un formato que pueda incluir más de una familia de direcciones, pero no desear que Dante utilice todas las familias de direcciones disponibles para esa forma de dirección.

Esto ocurrirá típicamente si el operador desea especificar que Dante debe usar las direcciones en una tarjeta de interfaz de red que tenga configuradas direcciones IPv4 e IPv6, pero el operador desea que Dante use solo una de estas dos familias de direcciones. El operador puede entonces especificar la familia de direcciones que desea que Dante busque al expandir el nombre de la interfaz para las direcciones IP a utilizar.

Los valores válidos para esta palabra clave son: ipv4 y ipv6, que indican que Dante solo debe usar la familia de direcciones IPv4 o solo la familia de direcciones IPv6, respectivamente. El valor predeterminado es usar ambas familias, si están disponibles.

Existe una palabra clave correspondiente para el lado interno (ver internal.protocol).

external.rotation
Si se proporciona más de una dirección externa, esto rige cuál de las direcciones proporcionadas se selecciona como la dirección de origen para las conexiones/paquetes salientes. Tenga en cuenta que, independientemente del valor de rotación externa utilizado, todas las direcciones externas que se utilizarán deben figurar primero en la palabra clave external.

Los valores válidos son none (el valor predeterminado), route y same-same.

none indica que se debe usar la primera dirección de la lista de direcciones externas.

route indica que se debe consultar la tabla de enrutamiento del kernel para averiguar cuál será la dirección de origen para un destino dado, y puede requerir que establezca user.privileged en root. Tenga en cuenta que route puede crear problemas para los clientes ftp que utilizan ftp activo si la extensión de enlace Dante está habilitada para el cliente ftp.

same-same indica que la dirección de origen para un destino dado debe ser la misma dirección en la que el servidor Dante aceptó la conexión del cliente.

internal
Las direcciones internas. Las conexiones solo se aceptarán en estas direcciones. La dirección proporcionada puede ser una dirección IP o un nombre de interfaz.
internal.log.<loglevel>.error
Ver logoutput. Esta opción permite registrar errores específicos relacionados con la interfaz interna.

Los valores posibles son los mismos que para la palabra clave logoutput.

El valor predeterminado es no tener ningún registro especial para errores de interfaz interna.

internal.protocol
Ver external.protocol. Esta opción tiene una sintaxis y semántica idénticas, pero se aplica a los errores relacionados con el lado de la interfaz interna.
socksmethod
Métodos de autenticación que se utilizarán para la autenticación socks. Estos son métodos de autenticación que se comprueban después de que el cliente SOCKS ha establecido la conexión socks con Dante y se ha negociado la versión socks.

Los valores válidos son: none, guest, user, client, proxy, rfc931, pam.

Los valores que no sean none y guest requieren que el servidor Dante se ejecute como root. La autenticación para estos métodos se realiza de forma segura con el cliente SOCKS.

Los valores client y proxy requieren el uso de servidores de autenticación.

El valor rfc931 requiere que el cliente SOCKS sea capaz de realizar una búsqueda de ident de autenticación. El valor pam requiere que el sistema tenga un módulo de autenticación enchufable (PAM) configurado.

El servidor Dante intentará los métodos de autenticación en el orden especificado. El primer método que tenga éxito se utilizará.

El valor predeterminado es none.

static
Esta palabra clave puede utilizarse para establecer una dirección de origen estática para las conexiones salientes. Esto puede ser útil en casos en los que el enrutamiento de red no pueda determinar la dirección de origen correcta para una conexión saliente.

La dirección dada puede ser una dirección IP o un nombre de interfaz.

syslog
Esto habilita el registro a través de syslog. El valor puede ser un nombre de instalación de syslog (por ejemplo, local0) o la palabra clave -1 para deshabilitar el registro de syslog.
user.privileged
El usuario con el que se ejecutará el servidor Dante cuando necesite realizar operaciones privilegiadas, como escuchar en puertos privilegiados o realizar operaciones de enrutamiento.

Los valores válidos son un nombre de usuario o la palabra clave root. El valor predeterminado es root.

Si el servidor se inicia como un usuario no privilegiado, no podrá realizar operaciones privilegiadas. En tales casos, es posible que sea necesario establecer esta opción en un usuario que tenga los permisos necesarios.

user.unprivileged
El usuario con el que se ejecutará el servidor Dante después de haber realizado las operaciones iniciales que requieren privilegios. Esto incluye la vinculación a puertos de red y la apertura de archivos de registro.

Los valores válidos son un nombre de usuario o la palabra clave nobody. El valor predeterminado es nobody.

Establecer esta opción en un usuario no privilegiado ayuda a reducir el riesgo de seguridad si el servidor se ve comprometido.

REGLAS

Las reglas controlan si se permite o se deniega el acceso a los clientes. Cada regla comienza con la palabra clave rule seguida de una acción (allow o deny) y luego una lista de criterios.

Los siguientes criterios están disponibles:

from
Especifica las direcciones IP de origen permitidas para la regla. Se pueden utilizar caracteres comodín y rangos de red.
to
Especifica las direcciones IP de destino permitidas para la regla. Se pueden utilizar caracteres comodín y rangos de red.
port
Especifica los puertos de destino permitidos para la regla. Se pueden utilizar rangos de puertos y puertos individuales.
user
Especifica los usuarios permitidos para la regla. Esto solo es aplicable si se utiliza la autenticación basada en usuarios.

Ejemplo:

rule allow from 192.168.1.0/24 to 10.0.0.0/8 port 80

Esta regla permitiría el acceso desde la red 192.168.1.0/24 al puerto 80 de cualquier host en la red 10.0.0.0/8.

RUTAS

Las rutas controlan cómo se enrutan las solicitudes de salida. Cada ruta comienza con la palabra clave route seguida de una dirección de destino y luego una dirección de puerta de enlace.

Ejemplo:

route to 0.0.0.0/0 via 192.168.1.1

Esta ruta enrutaría todo el tráfico de salida a través de la dirección 192.168.1.1.

internal.log.<loglevel>.error

internal.log.<loglevel>.error
Especifica que ciertos fallos de llamadas al sistema, listados como valores errno simbólicos, o ciertos fallos de DNS, listados como códigos de fallo simbólicos de libresolv, deben registrarse, posiblemente una vez adicional, en el nivel de registro log-level.

Tenga en cuenta que esto solo se aplica a los errores en el lado de la interfaz interna únicamente.

Existe una palabra clave correspondiente para el lado externo (ver external.log).

Además de los símbolos de error estándar de errno y getaddrinfo(3), se aceptan los siguientes símbolos especiales:

no-route
Cualquier error relacionado con la ausencia de ruta.
dns-any
Cualquier error relacionado con la resolución de DNS/nombres de host.
system-any
Cualquier error del sistema. Es decir, cualquier valor errno.
internal.protocol
Ver external.protocol. Esta opción tiene una sintaxis y semántica idénticas, pero se aplica a la interfaz interna, para las direcciones en las que escuchar conexiones de clientes.
libwrap.hosts_access
Si el servidor se compila con soporte para libwrap, determina si la función hosts_access() debe usarse para el control de acceso. Cuando se habilita estableciendo este valor a yes, la biblioteca libwrap determina si las conexiones TCP o los paquetes UDP deben ser inmediatamente descartados o no, típicamente consultando /etc/hosts.allow y /etc/hosts.deny. Estas comprobaciones se aplican a todo el tráfico, antes de que comience el procesamiento de reglas. El valor predeterminado es no (deshabilitado).
logoutput
Este valor controla a dónde envía el servidor la salida de registro. Puede configurarse como syslog[/facility], stdout, stderr, un nombre de archivo o una combinación. El valor predeterminado es ningún lugar. Tenga en cuenta que si también se establece errorlog, habrá una superposición entre lo que se registra allí (solo errores) y lo que se registrará aquí (errores y todo lo demás).
socksmethod
Una lista de métodos de autenticación aceptables para las reglas socks, listados en orden de preferencia. Por lo tanto, es importante que los especifique en el orden deseado, normalmente con los métodos más seguros primero.

Los valores admitidos son bsdauth, gssapi, none, pam.any, pam.address, pam.username, rfc931 y username.

Si un método no se establece en esta lista, nunca se seleccionará. El valor predeterminado son cero métodos, lo que significa que todas las solicitudes socks serán bloqueadas.

Consulte la sección sobre MÉTODOS DE AUTENTICACIÓN para obtener una explicación de los diferentes métodos y su significado.

srchost
Esta palabra clave le permite configurar algunas opciones relacionadas con el srchost, es decir, el host desde el que el servidor Dante acepta las conexiones entrantes.

Con la palabra clave nodnsmismatch, el servidor no aceptará conexiones de direcciones que tengan una discrepancia entre la dirección IP de DNS y el nombre de host. El valor predeterminado es aceptarlas.

Con la palabra clave nodnsunknown, el servidor no aceptará conexiones de direcciones sin un registro DNS. El valor predeterminado es aceptarlas.

Con la palabra clave checkreplyauth, el servidor comprobará que la autenticación en las respuestas de bind y las respuestas udp coincida con la establecida en la regla y el socksmethod global. Normalmente, la autenticación no es deseable en las respuestas, ya que son respuestas enviadas a los clientes socks desde clientes que no son socks, y por lo tanto, solo un conjunto limitado de métodos de autenticación son posibles.

Los métodos posibles para TCP son los métodos que no involucran el protocolo socks de ninguna manera, y se enumeran en la sección clientmethod mencionada anteriormente. Para las respuestas UDP, no se pueden utilizar métodos.

El valor predeterminado es no comprobar la autenticación en las respuestas.

timeout.connect
El número de segundos que el servidor esperará a que se complete una conexión iniciada en nombre del cliente socks. El valor predeterminado es 30. Establecerlo en 0 utilizará el valor predeterminado del sistema.
timeout.io
El número de segundos que una conexión establecida puede permanecer inactiva. El valor predeterminado es 0, lo que significa para siempre. Ver también la opción "-n" en la página man de sockd(8).

Se pueden establecer tiempos de espera individuales para TCP y UDP añadiendo ".<protocolname>" a io, es decir, timeout.io.tcp o timeout.io.udp.

Los tiempos de espera individuales también se pueden establecer dentro de las reglas, utilizando la misma sintaxis. El tiempo de espera establecido en la regla anulará los tiempos de espera predeterminados para los clientes que coincidan con la regla.

timeout.negotiate
El número de segundos que un cliente puede pasar negociando con el servidor Dante para una sesión socks antes de que Dante cierre la conexión con el cliente. El valor predeterminado es 30. Establécelo en 0 para siempre, aunque esto está fuertemente desaconsejado.
timeout.tcp_fin_wait
El tiempo de espera para el equivalente del FIN-WAIT-2 de TCP. El valor predeterminado es 0, lo que significa usar el valor predeterminado del sistema (normalmente, sin tiempo de espera).
udp.connectdst
Habilita o deshabilita si el servidor debe intentar conectar sockets UDP al destino. Los valores válidos son yes y no.

El valor predeterminado es yes, lo que mejora el rendimiento UDP, pero puede no ser compatible con algunos protocolos de aplicación basados en UDP, ya que significa que el servidor solo puede recibir paquetes de la dirección de destino.

El socket solo permanecerá conectado mientras el cliente envíe paquetes UDP a una sola dirección de destino. Si se envían paquetes a múltiples destinos, el socket ya no permanecerá conectado y las respuestas podrán recibirse de cualquier destino.

Userids
En plataformas que proporcionan un modelo de privilegios compatible con Dante, el servidor Dante no utiliza el cambio de usuario a través de la llamada al sistema seteuid(2). En otras plataformas, es prudente establecer el ID de usuario que será utilizado por el servidor Dante a valores apropiados. El servidor Dante puede usar dos IDs de usuario diferentes, o tres si se compila con soporte para libwrap. Estos son los siguientes:
user.privileged
Nombre de usuario que se utilizará para realizar operaciones privilegiadas. Si necesita privilegios especiales para leer el archivo sockd.conf o para escribir el archivo sockd.pid (puede crearlo manualmente antes de iniciar sockd), tiene algo en su configuración que requiere enlazar puertos TCP/UDP privilegiados (puertos por debajo de 1024), o utiliza algún tipo de autenticación basada en contraseña, esto probablemente necesita ser establecido como root.

Si no es así, probablemente pueda establecerlo al mismo valor que user.unprivileged.

user.unprivileged
Usuario bajo el cual se ejecuta el servidor la mayor parte del tiempo. Este debería ser un ID con el menor privilegio posible. Se recomienda crear un ID de usuario separado para este propósito.
user.libwrap
Usuario utilizado para ejecutar comandos de libwrap. Normalmente, este debería ser el mismo que user.unprivileged.

MÓDULOS

Los siguientes módulos son compatibles con Dante. Los módulos se compran por separado de Inferno Nettverk A/S y pueden agregar funcionalidad adicional que no es necesaria para la mayoría de los usuarios. Consulte la página principal de Dante para obtener más información.

bandwidth
El módulo bandwidth proporciona control sobre la cantidad de ancho de banda que utiliza el servidor Dante en nombre de diferentes clientes o hacia diferentes destinos.
redirect
El módulo redirect le permite controlar qué direcciones utilizará el servidor en nombre de los clientes, además de permitirle redirigir las solicitudes de los clientes a diferentes direcciones.

OPCIONES_DE_SOCKET

El servidor admite la configuración de un gran número de opciones de socket de bajo nivel tanto para el tráfico entrante como saliente. *La mayoría de los usuarios no necesitarán configurar ninguna de estas opciones, pero algunos podrían querer hacerlo para habilitar funciones de red especiales o para realizar diversos experimentos.*

Las opciones se pueden configurar globalmente como valores predeterminados para todo el tráfico, o configurarse en las reglas de control de acceso para afectar solo a los clientes y destinos que coincidan con la regla dada.

Las opciones de socket disponibles varían entre plataformas, por lo que durante la configuración y la compilación del servidor se determinarán las opciones disponibles. Actualmente, las siguientes opciones deberían ser detectadas, cuando estén disponibles, para los niveles de protocolo especificados:

SOCKET
so_bindany, so_broadcast, so_debug, so_dontroute, so_jumbo, so_keepalive, so_oobinline, so_priority, so_rcvbuf, so_rcvbufforce, so_rcvlowat, so_sndbuf, so_sndbufforce, so_sndlowat, so_useloopback
TCP
tcp_cork, tcp_cwnd, tcp_init_cwnd, tcp_keepcnt, tcp_keepidle, tcp_keepintvl, tcp_linger2, tcp_maxrt, tcp_maxseg, tcp_md5sig, tcp_nodelay, tcp_noopt, tcp_nopush, tcp_sack_enable, tcp_stdurg, tcp_syncnt, tcp_window_clamp
UDP
udp_cork
IP
ip_auth_level, ip_dontfrag, ip_esp_network_level, ip_esp_trans_level, ip_freebind, ip_ipcomp_level, ip_minttl, ip_mtu_discover, ip_portrange, ip_recvtos, ip_tos, ip_
ttl

La sintaxis para establecer opciones de socket es la siguiente:

<dirección>.<nivel>.<opción>: <valor>

El campo valor corresponde al valor al que se debe establecer la opción del socket. Para muchas opciones de socket, este es un valor entero. Los valores nivel y opción corresponden a los nombres de socket y niveles de protocolo enumerados anteriormente. Ambos deben estar en minúsculas.

La palabra clave dirección se utiliza para especificar si la opción del socket debe establecerse para el tráfico en la interfaz interna o externa y puede tener los valores internal (interna) y external (externa). Por ejemplo, para establecer la opción de socket IP_TOS en el tráfico saliente, se puede usar la siguiente sintaxis:

external.ip.ip_tos: 0x10

En este ejemplo, el valor del argumento (0x10) se especifica como un valor hexadecimal. Para algunas de las opciones de socket, el valor también se puede establecer simbólicamente. Actualmente, esto es posible para las siguientes opciones, con los valores enumerados:

ip_portrange
ip_portrange_default, ip_portrange_low, ip_portrange_high

La opción de socket IP_TOS también soporta esto, pero el manejo de esta opción se complica un poco por el hecho de que los mismos bits tienen diferentes significados en diferentes RFC. El manejo de esto se realiza con un subcampo que indica el tipo de argumento que se debe usar. Los siguientes subcampos están definidos y deben agregarse al nombre de la opción de socket como se especifica a continuación:

ip_tos.dscp
af11 af12 af13 af21 af22 af23 af31 af32 af33 af41 af42 af43 cs0 cs1 cs2 cs3 cs4 cs5 cs6 cs7 ef
ip_tos.prec
netcontrol internetcontrol critic_ecp flashoverride flash immediate priority routine
ip_tos.tos
lowdelay throughput reliability

Cuando se proporcionan argumentos numéricos a los subcampos, los valores se desplazan para aplicarse solo al rango de bits del subcampo. El siguiente ejemplo muestra las diferentes formas de establecer IP_TOS en lowdelay en tráfico externo:

external.ip.ip_tos:     0x10       # valor base, numéricamente
external.ip.ip_tos.tos: 0x08       # subcampo, numéricamente
external.ip.ip_tos.tos: lowdelay   # subcampo, simbólicamente

El primer valor establece el valor directamente, el segundo establece solo los bits TOS, que se desplazan en relación con el valor base. La última línea establece el valor TOS simbólicamente.

Esta funcionalidad proporciona una gran cantidad de control sobre las opciones de socket, pero no debe usarse sin comprender cómo el kernel permite establecer la opción de socket y las limitaciones que se aplican cuando las opciones de socket se establecen como valores predeterminados o en reglas.

Establecer una opción de socket en una regla de paso de cliente (client pass) o reglas de socks sobrescribirá cualquier valor predeterminado. Las opciones globales se establecen antes de que se llame a bind() en los sockets internos, o antes de que se llame a connect() en los sockets externos. Las opciones establecidas en las reglas de cliente también se aplican antes de que se llame a bind() en el socket interno, pero no se pueden establecer para el socket externo. Para las reglas de socks, se pueden establecer tanto las opciones externas como las internas, pero debido a que la solicitud de socks debe interpretarse antes de que se puedan evaluar las reglas, las opciones de socket solo se pueden establecer en los sockets internos después de que se haya recibido la conexión.

Algunas opciones de socket deben establecerse antes de que se establezca una conexión, mientras que otras solo se pueden establecer después de que se establezca una conexión. Otras se pueden establecer en cualquier momento.

Las opciones de socket que no se enumeran anteriormente también se pueden establecer especificando el nombre de la opción de socket numéricamente, por ejemplo:

external.ip.10: 0x12

En este ejemplo, se establecerá la opción de socket correspondiente al valor 10. Estos números dependen de la plataforma, pero generalmente se pueden determinar consultando los archivos de encabezado del sistema apropiados. Especificar opciones numéricamente puede generar algunas advertencias, pero permite especificar cualquier opción de socket, siempre que acepte un argumento numérico. Este no es el enfoque recomendado para establecer opciones de socket, pero representa una forma sencilla de establecer opciones de socket que no son directamente compatibles con el servidor, como extensiones del kernel local.

MÉTODOS DE AUTENTICACIÓN

El servidor Dante soporta los siguientes métodos de autenticación. Algunas instalaciones de Dante pueden soportar solo un subconjunto de estos, dependiendo del soporte de la plataforma.

none
Este método no requiere ninguna forma de autenticación.
username
Este método requiere que el cliente proporcione un nombre de usuario y una contraseña. Esta información debe coincidir con el nombre de usuario y la contraseña proporcionados en el archivo de contraseñas del sistema.
gssapi
Este método requiere la configuración de un entorno Kerberos y puede proporcionar cifrado y autenticación sólidos, dependiendo de la configuración de gssapi que elija.
rfc931
Este método requiere que el host en el que se ejecuta el cliente socks proporcione un nombre de usuario rfc931 ("ident") para el cliente. Este nombre de usuario debe coincidir con un nombre de usuario dado en el archivo de contraseñas del sistema.
pam.address
Autenticación PAM basada en IP (rhosts).
pam.any
Intentará coincidir con cualquier tipo de autenticación PAM, dependiendo de la información que esté disponible actualmente. Normalmente de uso limitado, y debería establecer en su lugar los métodos basados en PAM que realmente desea.
pam.username
Autenticación PAM basada en nombre de usuario/contraseña. Similar al método username, pero la información se pasa al subsistema PAM para la autenticación, en lugar de que Dante use el archivo de contraseñas del sistema directamente. Al usar PAM, tenga cuidado con las fugas de memoria y otros errores en la biblioteca PAM externa que Dante tendrá que usar en su plataforma.
bsdauth
Este método requiere que los datos disponibles del cliente sean verificados por el sistema de Autenticación BSD. Similar al método username, pero se pasa al sistema de autenticación BSD en su lugar.

DIRECCIONES

Cada campo de dirección puede consistir en una dirección IP (y cuando sea necesario, una máscara de red, separada de la dirección IP por un signo '/'), un nombre de host, un nombre de dominio (designado así por el prefijo '.'), o un nombre de interfaz.

Una dirección IP puede proporcionarse en formato IPv4, formato IPv6 o como el valor especial 0/0, que coincide con todas las direcciones IP, ya sean IPv4 o IPv6. Este último está destinado a su uso en rules (reglas) que deben coincidir con clientes o destinos tanto IPv4 como IPv6.

Cada dirección, excepto la dirección external (externa), puede incluir un especificador de puerto opcional.

REGLAS

Hay dos conjuntos de reglas y funcionan a diferentes niveles. Las reglas precedidas por client se verifican primero y se utilizan para ver si al cliente se le permite conectarse al servidor Dante. Las llamamos "reglas de cliente". Estas reglas comenzarán con client pass para una regla que permite al cliente, o client block para una regla que bloquea al cliente.

Se recomienda que las reglas de cliente no utilicen nombres de host, sino solo direcciones IP, tanto por razones de seguridad como de rendimiento. Estas reglas operan a nivel de TCP.

Las otras reglas, que llamamos "reglas de socks", van precedidas por socks y operan a nivel del protocolo socks.

Estas reglas comenzarán con socks pass para una regla que permite al cliente, o socks block para una regla que bloquea al cliente.

Estas reglas solo se verifican si la conexión del cliente ha sido permitida por las reglas de cliente. Las reglas de socks se utilizan para evaluar la solicitud de socks que envía el cliente.

Si bien es menos importante que estas reglas utilicen solo direcciones IP, siempre que las reglas de cliente se hayan configurado para permitir el acceso solo desde un rango predefinido de direcciones IP de cliente, todavía se recomienda.

Ambos conjuntos de reglas incluyen una palabra clave pass (permitir) o deny (denegar). La palabra clave pass/deny determina si las conexiones que coinciden con la regla se permitirán o se bloquearán.

Tanto las reglas de cliente como las reglas de socks especifican un par de direcciones from (desde)/to (a) que proporcionan las direcciones con las que coincidirá la regla.

En ambos contextos, from se refiere a la dirección del cliente, es decir, la dirección desde la que el cliente se conecta al servidor Dante. Sin embargo, to se refiere a cosas diferentes dependiendo de si se usa en una regla de cliente o en una regla de socks.

En el contexto de la regla de cliente, to significa la dirección en la que se acepta la solicitud, es decir, una dirección en la que escucha el servidor Dante.

En el contexto de la regla de socks, to significa la dirección de destino del cliente, como se expresa en la solicitud de socks del cliente. Es decir, la dirección a la que el servidor Dante debe conectarse (para sesiones TCP) o enviar paquetes (para sesiones UDP) en nombre del cliente.

Ambos conjuntos de reglas se evalúan según el principio de "primera coincidencia es la mejor coincidencia". Eso significa que la primera regla que coincide para un cliente o solicitud de socks particular es la regla que se utilizará.

Además de las direcciones, hay un conjunto de palabras clave opcionales que se pueden proporcionar. Hay dos formas de palabras clave: condiciones y acciones. Para cada regla, se verifican todas las condiciones y, si coinciden con la solicitud, se ejecutan todas las acciones.

La lista de palabras clave de condición es: clientcompatibility, clientmethod, command, from, group, socksmethod, protocol, proxyprotocol, to, user.

La lista de palabras clave de acción es: bandwidth, libwrap, log, session, redirect, timeout.connect, timeout.negotiate, timeout.io, timeout.tcp_fin_wait, y udp.portrange.

El formato y el contenido de la palabra clave tal como se utilizan en las reglas de cliente o en las reglas de socks son idénticos, pero las reglas de cliente solo pueden contener un subconjunto de las palabras clave que pueden contener las reglas de socks.

SESSION

La palabra clave session se puede utilizar en cualquier regla para limitar el número de sesiones activas y la tasa a la que se establecen. Hay dos comandos principales para esto; session.max, que controla el número máximo de sesiones que pueden coincidir, y session.throttle, que controla la tasa de conexión. Estos comandos se pueden aplicar tanto al límite total para todos los clientes coincidentes como a los valores predeterminados globales o a cualquiera de los tipos de reglas. La palabra clave session.max toma un número que corresponde al número máximo de conexiones simultáneas permitidas como argumento. La palabra clave session.throttle toma dos números separados por una barra, y el primero representa el número de conexiones y el segundo una duración de tiempo en segundos. Si se reciben más conexiones de las especificadas en t

se especificó un número de segundos, se descartarán conexiones adicionales.

También se admite el seguimiento de sesiones con estado por dirección IP. Para el seguimiento con estado, los límites se aplican a cada conexión con una dirección IP coincidente, utilizando la palabra clave session.state.key para controlar cómo se determina la dirección IP. Actualmente se admiten dos valores: from y hostid. El primero hace que el límite se aplique a todos los hosts con la misma dirección IP de origen y el segundo a todas las conexiones TCP con el mismo valor hostid. Si se utiliza un valor hostid, la palabra clave session.state.key.hostindex se puede usar para elegir cuál de los dos valores hostid se utilizará, siendo el primer valor el predeterminado.

Los límites se evalúan primero para las reglas de cliente, luego para las reglas de hostid y finalmente para las reglas de socks. De forma predeterminada, un límite establecido en una regla de cliente coincidente se utilizará también en cualquier regla de hostid o socks coincidente posterior, a menos que alguna de estas reglas también tenga palabras clave de límite de sesión. Esta herencia de sesión se puede deshabilitar en las reglas de cliente y hostid, lo que hace que solo se apliquen en la regla en la que aparecen. Esto se hace estableciendo session.inheritable en no.

Las palabras clave de sesión deben establecerse en una regla (ya sea de cliente, hostid o socks); no se admite establecerlas de forma global.

MONITORIZACIÓN DE TRÁFICO

El servidor Dante se puede configurar para monitorizar el tráfico que pasa a través de él y activar alarmas basadas en el tráfico de red observado.

Las alarmas se especifican en los llamados monitores. Estos objetos tienen el mismo formato general que las reglas que Dante utiliza para el control de acceso y permiten realizar una monitorización pasiva del tráfico de red, o la falta de tráfico de red.

El siguiente ejemplo muestra la sintaxis general del monitor, especificando un monitor sin operaciones de monitorización:


monitor {
from: 0.0.0.0/0 to: www.example.org port = 80
protocol: tcp
}

Un monitor puede incluir muchas de las mismas palabras clave que están disponibles en las reglas ACL de Dante. El siguiente subconjunto es compatible actualmente:

from
Normalmente especifica qué direcciones/redes de clientes SOCKS monitorizar.
to
Normalmente especifica qué direcciones/redes de destino monitorizar.
protocol
Se puede utilizar para restringir la monitorización a un protocolo específico (TCP, UDP o ambos). Nota: por ahora, solo se debe usar TCP.
hostid
Se puede utilizar para restringir la monitorización solo a clientes con un valor hostid específico establecido.
hostindex
Se utiliza junto con la palabra clave hostid para controlar cuál de los dos valores hostid posibles se utilizará al coincidir.

NOTA: Actualmente se recomienda especificar siempre la palabra clave protocol y establecerla en tcp, ya que actualmente solo hay soporte limitado para la monitorización de tráfico UDP, y no se han realizado pruebas de monitorización de tráfico UDP.

La función principal de los monitores es proporcionar un contenedor para una o más alarmas, que se especifican utilizando un nuevo conjunto de palabras clave no disponibles para otras reglas. Las alarmas especifican una condición que hará que Dante registre una advertencia si la condición se activa.

Las sesiones TCP activas coincidirán como máximo con un monitor, pero se pueden especificar múltiples alarmas en un solo monitor. Esto hace posible especificar varios conjuntos de condiciones para las mismas sesiones TCP, dependiendo de la interfaz de red en la que se transfiera el tráfico y de si el tráfico se está recibiendo o transmitiendo.

Las alarmas se pueden activar como resultado de períodos de poca o ninguna transmisión de datos, o un gran número de conexiones TCP que se desconectan en un corto período de tiempo, o por otras razones. Consulte a continuación una lista completa de las condiciones para las que se pueden habilitar las alarmas.

Alarmas de datos

Añadir una palabra clave alarm.data a un monitor dará como resultado advertencias registradas si hay períodos con demasiado poco tráfico de red.

Dante tiene cuatro rutas de red y las alarmas de datos se pueden configurar independientemente para cada una de ellas:

internal.alarm.data.recv
Datos recibidos en la interfaz interna de Dante (datos enviados desde los clientes SOCKS a Dante).
internal.alarm.data.send
Datos enviados en la interfaz interna de Dante (datos enviados desde Dante a los clientes SOCKS).
external.alarm.data.recv
Datos recibidos en la interfaz externa de Dante (datos enviados desde los servidores de destino a Dante).
external.alarm.data.send
Datos enviados en la interfaz externa de Dante (datos enviados desde Dante a los servidores de destino).

La palabra clave data.alarm toma dos parámetros: un recuento de bytes y una duración en segundos. La alarma se activará si pasan el número especificado de segundos con solo el número especificado de bytes (o menos) transmitidos.

La sintaxis es la siguiente:

internal.alarm.data.recv: DATALIMIT in INTERVAL

DATALIMIT es un número que especifica el límite de bytes. INTERVAL es un número que especifica la duración. Si solo se han transferido DATALIMIT bytes (o menos) durante un período de INTERVAL segundos, se activará una alarma en Dante.

Las alarmas de datos se activan cuando se detecta un período de inactividad de datos. Una vez que se activa una alarma de datos, permanecerá activa hasta que se desactive. Se registrará una advertencia cuando se active la alarma y luego nuevamente cuando se desactive la condición de alarma. Entre estos dos puntos, no se registrarán advertencias relacionadas con esta alarma. Esto evita repetir la misma alarma/advertencia varias veces durante problemas de red que duran un tiempo prolongado. Cuando se desactiva la alarma, Dante también incluirá información sobre cuánto duró la condición de alarma.

Una alarma de datos se puede desactivar de dos maneras; automáticamente, una vez que se han transferido suficientes datos en un tiempo suficientemente corto, o manualmente, enviando una señal SIGHUP al servidor Dante. Un SIGHUP hará que se desactiven todas las alarmas activas. No se registrarán mensajes de registro que indiquen que las alarmas se han desactivado de esta manera.

Una vez que se ha desactivado una alarma, puede volver a activarse si no se transfiere suficiente cantidad de datos.

Tenga en cuenta que las alarmas de datos se activarán independientemente de si hay sesiones activas que coincidan con el monitor o no; si no se transmite o recibe suficiente tráfico, se activará una alarma de datos. Las alarmas se activarán también poco después del inicio del servidor, si el servidor Dante no recibe suficiente tráfico para evitar que las alarmas se activen.

Tenga en cuenta que el mensaje que indica que una alarma se ha desactivado no se registra si la alarma se desactivó debido a la recepción de una señal SIGHUP.

Alarmas de desconexión

Las alarmas de desconexión están relacionadas con las desconexiones de conexiones y, al utilizar la palabra clave alarm.disconnect, el servidor Dante puede registrar advertencias basadas en el número y la tasa de conexiones terminadas.

Hay dos variantes de la palabra clave de alarma, una para la interfaz de red interna, entre los clientes SOCKS y Dante, y otra para la interfaz externa, entre el servidor Dante y los servidores de destino:

internal.alarm.disconnect
Conexiones entre clientes SOCKS y el servidor Dante.
external.alarm.disconnect
Conexiones entre el servidor Dante y los servidores de destino.

Cada palabra clave de alarma toma tres parámetros: un recuento mínimo, un valor de ratio y un intervalo de tiempo. Se utiliza el siguiente formato:

internal.alarm.disconnect: MINCOUNT/RATIO in INTERVAL

MINCOUNT es el número mínimo de conexiones que deben desconectarse para que se active la alarma. RATIO se utiliza junto con MINCOUNT para expresar el número de conexiones, en relación con el número total de conexiones que han existido en el período de tiempo, que deben desconectarse para que se active la alarma. INTERVAL es el tiempo en segundos dentro del cual deben ocurrir las desconexiones para que se active la alarma.

Para establecer valores útiles, se requiere cierto conocimiento sobre la cantidad esperada de tráfico de red y el número de sesiones. Si la tasa de desconexiones, como porcentaje, es inferior al ratio especificado, no se activará una alarma. Por el contrario, si MINCOUNT se establece demasiado bajo, las alarmas podrían activarse con demasiada frecuencia porque un pequeño número de desconexiones podría ser suficiente para alcanzar el número requerido de desconexiones y ratio de desconexión en momentos en que solo hay unas pocas sesiones activas.

Solo se cuentan las conexiones que se terminan en la interfaz especificada, es decir, una alarma external.alarm.disconnect solo se activará para las conexiones que se terminan en la interfaz de red entre el servidor Dante y el servidor de destino, ya sea porque el servidor de destino cierra la conexión a Dante o porque Dante recibe un error de red fatal desde ese lado de la conexión (por ejemplo, un paquete TCP RST).

Las conexiones que se cierran en la interfaz interna (por los clientes SOCKS) no contarán para una alarma de desconexión en el lado externo. De manera similar, las conexiones cerradas por los servidores de destino no contarán para una alarma de desconexión en el lado interno.

Una consecuencia práctica de esto es que si un gran número de conexiones son cerradas simultáneamente tanto por el cliente como por el servidor de destino, cada conexión solo se contará como una desconexión en uno de los lados; ya sea el lado externo o el lado interno, dependiendo de qué lado cierra la conexión primero.

Las alarmas se activan cada vez que ocurren suficientes desconexiones. Cada ráfaga de desconexiones suficientemente grande dará como resultado una alarma, pero normalmente solo se registrará como máximo una advertencia por alarma durante cada intervalo de tiempo, aunque esto podría cambiar en una versión posterior de Dante.

Se producen alarmas separadas para cada palabra clave de alarma distinta cuando se especifican múltiples alarmas en una regla de monitor.

RUTAS

RUTAS

Las rutas se especifican con la palabra clave route. Dentro de un par de llaves ({}) un conjunto de palabras clave controlan el comportamiento de la ruta. Vea socks.conf(5) para una descripción. Esto se utiliza para realizar la llamada "server-chaining" (encadenamiento de servidores), donde un socks-server se conecta a otro socks-server más arriba en la cadena.

La sintaxis de estas rutas es la misma que las rutas utilizadas por el cliente. Consulte socks.conf(5) para obtener información sobre la sintaxis de las rutas.

Sin embargo, hay algunas cosas especiales que se deben tener en cuenta con respecto al encadenamiento de servidores y las rutas especificadas para el servidor:

En la actualidad, el encadenamiento de servidores solo se admite para el comando tcp connect.
Si la ruta especifica que se debe ofrecer un método de nombre de usuario/contraseña al proxy superior, Dante reenviará el nombre de usuario/contraseña recibido de su propio cliente al proxy superior externo, lo que significa que el proxy superior recibirá el nombre de usuario y la contraseña del usuario en texto plano de Dante.
En la actualidad, el encadenamiento de servidores no escala bien en Dante y no debe utilizarse para nada más que cargas de clientes mínimas.
