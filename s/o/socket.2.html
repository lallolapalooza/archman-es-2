socket(2) Manual de llamadas al sistema socket(2)

NOMBRE

socket(2) — crear un punto final para la comunicación

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

SINOPSIS

#include <sys/socket.h>
int socket(int domain, int type, int protocol);

DESCRIPCIÓN

socket() crea un punto final para la comunicación y devuelve un descriptor de archivo que se refiere a dicho punto final. El descriptor de archivo devuelto por una llamada exitosa será el descriptor de archivo con el número más bajo que no esté actualmente abierto para el proceso.

El argumento domain especifica un dominio de comunicación; esto selecciona la familia de protocolos que se utilizará para la comunicación. Estas familias se definen en <sys/socket.h>. Los formatos que el kernel de Linux entiende actualmente incluyen:

Se pueden encontrar más detalles de las familias de direcciones anteriores, así como información sobre varias familias de direcciones más, en address_families(7).

El socket tiene el type indicado, que especifica la semántica de comunicación. Los tipos actualmente definidos son:

SOCK_STREAM
Proporciona flujos de bytes bidireccionales, basados en conexión, fiables y secuenciados. Se puede admitir un mecanismo de transmisión de datos fuera de banda.
SOCK_DGRAM
Soporta datagramas (mensajes no conectados, no fiables de una longitud máxima fija).
SOCK_SEQPACKET
Proporciona una ruta de transmisión de datos bidireccional basada en conexión, fiable y secuenciada para datagramas de longitud máxima fija; se requiere un consumidor para leer un paquete completo con cada llamada al sistema de entrada.
SOCK_RAW
Proporciona acceso a protocolos de red en bruto.
SOCK_RDM
Proporciona una capa de datagramas fiables que no garantiza el orden.
SOCK_PACKET
Obsoleto y no debe utilizarse en programas nuevos; véase packet(7).

Es posible que algunos tipos de socket no estén implementados por todas las familias de protocolos.

Desde Linux 2.6.27, el argumento type tiene un segundo propósito: además de especificar un tipo de socket, puede incluir el OR bitwise de cualquiera de los siguientes valores para modificar el comportamiento de socket():

SOCK_NONBLOCK
Establece la bandera de estado de archivo O_NONBLOCK en la descripción de archivo (véase open(2)) a la que se refiere el nuevo descriptor de archivo. Utilizar esta bandera ahorra llamadas adicionales a fcntl(2) para lograr el mismo resultado.
SOCK_CLOEXEC
Establece la bandera de cierre al ejecutar (FD_CLOEXEC) en el nuevo descriptor de archivo. Consulte la descripción de la bandera O_CLOEXEC en open(2) para conocer las razones por las que esto puede ser útil.

El argumento protocol especifica un protocolo particular a utilizar con el socket. Normalmente solo existe un protocolo para soportar un tipo de socket determinado dentro de una familia de protocolos dada, en cuyo caso protocol puede especificarse como 0. Sin embargo, es posible que existan muchos protocolos, en cuyo caso se debe especificar un protocolo particular de esta manera. El número de protocolo a utilizar es específico del “dominio de comunicación” en el que se va a realizar la comunicación; véase protocols(5). Véase getprotoent(3) sobre cómo mapear cadenas de nombres de protocolo a números de protocolo.

Los sockets de tipo SOCK_STREAM son flujos de bytes a dúplex completo. No conservan los límites de registro. Un socket de flujo debe estar en estado de conectado antes de que se puedan enviar o recibir datos en él. Una conexión a otro socket se crea con una llamada a connect(2). Una vez conectado, los datos se pueden transferir utilizando llamadas a read(2) y write(2) o alguna variante de las llamadas a send(2) y recv(2). Cuando se ha completado una sesión, se puede realizar una llamada a close(2). También se pueden transmitir datos fuera de banda como se describe en send(2) y recibir como se describe en recv(2).

Los protocolos de comunicación que implementan SOCK_STREAM garantizan que los datos no se pierden ni se duplican. Si una pieza de datos para la que el protocolo par tiene espacio de búfer no puede ser transmitida con éxito dentro de un período de tiempo razonable, entonces la conexión se considera muerta. Cuando SO_KEEPALIVE está habilitado en el socket, el protocolo comprueba de manera específica del protocolo si el otro extremo sigue activo. Se eleva una señal SIGPIPE si un proceso envía o recibe en un flujo roto; esto hace que los procesos ingenuos, que no manejan la señal, salgan. Los sockets SOCK_SEQPACKET emplean las mismas llamadas al sistema que los sockets SOCK_STREAM. La única diferencia es que las llamadas a read(2) devolverán solo la cantidad de datos solicitada, y cualquier dato restante en el paquete entrante se descartará. Además, todos los límites de mensajes en los datagramas entrantes se conservan.

Los sockets SOCK_DGRAM y SOCK_RAW permiten enviar datagramas a corresponsales nombrados en llamadas a sendto(2). Los datagramas generalmente se reciben con recvfrom(2), que devuelve el siguiente datagrama junto con la dirección de su remitente.

SOCK_PACKET es un tipo de socket obsoleto para recibir paquetes crudos directamente del controlador del dispositivo. Utilice packet(7).

DESCRIPCIÓN

La llamada al sistema socket() crea un nuevo extremo de comunicación y devuelve un descriptor de archivo para él. La operación de socket está controlada por el dominio especificado por domain y el tipo de comunicación especificado por type. La familia de protocolos protocol se especifica aún más. Actualmente, solo se permite que protocol sea 0; los protocolos específicos dentro de un dominio deben ser seleccionados usando opciones de socket de nivel de protocolo.

Los dominios de familia de protocolos actualmente soportados son:

AF_LOCAL
(también conocido como AF_UNIX) Soporta la comunicación de procesos locales.
AF_INET
Soporta el protocolo de Internet IPv4.
AF_INET6
Soporta el protocolo de Internet IPv6.
AF_PACKET
Soporta la recepción y envío de paquetes crudos de red.

Los tipos de socket soportados son:

SOCK_STREAM
Proporciona un flujo de datos fiable, bidireccional y ordenado, sin duplicados, sobre una conexión.
SOCK_DGRAM
Soporta datagramas (mensajes sin conexión, no fiables, de tamaño limitado).
SOCK_RAW
Proporciona acceso a protocolos de red de nivel inferior. El uso de este tipo de socket generalmente requiere privilegios de superusuario.
SOCK_RDM
Soporta entrega de mensajes fiable, pero no necesariamente ordenada.
SOCK_SEQPACKET
Soporta dos vías de comunicación bidireccional, ordenado, basado en transacciones con entrega de datos delimitados.

Las siguientes banderas pueden ser especificadas en el argumento type en combinación con cualquier tipo de socket por medio de OR bitwise:

SOCK_NONBLOCK
Establece el descriptor de archivo recién creado en modo no bloqueante. Esto es equivalente a usar la llamada al sistema fcntl(2) con el comando F_SETFL y el argumento O_NONBLOCK después de la llamada a socket().
SOCK_CLOEXEC
Establece la bandera FD_CLOEXEC en el nuevo descriptor de archivo. Esto significa que el descriptor de archivo se cerrará automáticamente durante una llamada exitosa a execve(2). Esto es equivalente a usar la llamada al sistema fcntl(2) con el comando F_SETFD y el argumento FD_CLOEXEC después de la llamada a socket().

El uso de SOCK_NONBLOCK y SOCK_CLOEXEC se describe más en detalle en socket(7).

Una operación fcntl(2) F_SETOWN puede ser usada para especificar un proceso o grupo de procesos para recibir una señal SIGURG cuando llegan datos fuera de banda o una señal SIGPIPE cuando una conexión SOCK_STREAM se rompe inesperadamente. Esta operación también puede ser usada para establecer el proceso o grupo de procesos que recibe notificaciones de E/S y notificaciones asíncronas de eventos de E/S a través de SIGIO. Usar F_SETOWN es equivalente a una llamada a ioctl(2) con el argumento FIOSETOWN o SIOCSPGRP.

Cuando la red señala una condición de error al módulo de protocolo (por ejemplo, usando un mensaje ICMP para IP) se establece la bandera de error pendiente para el socket. La próxima operación en este socket devolverá el código de error del error pendiente. Para algunos protocolos, es posible habilitar una cola de errores por socket para recuperar información detallada sobre el error; ver IP_RECVERR en ip(7).

La operación de los sockets está controlada por las options a nivel de socket. Estas opciones se definen en <sys/socket.h>. Las funciones setsockopt(2) y getsockopt(2) se usan para establecer y obtener opciones.

VALOR DE RETORNO

En caso de éxito, se devuelve un descriptor de archivo para el nuevo socket. En caso de error, se devuelve -1 y la variable errno se establece para indicar el error.

ERRORES

EACCES
Se deniega el permiso para crear un socket del tipo y/o protocolo especificado.
EAFNOSUPPORT
La implementación no soporta la familia de direcciones especificada.
EINVAL
Protocolo desconocido o familia de protocolos no disponible.
EINVAL
Banderas inválidas en type.
EMFILE
Se ha alcanzado el límite por proceso en el número de descriptores de archivo abiertos.
ENFILE
Se ha alcanzado el límite a nivel de sistema del número total de archivos abiertos.
ENOBUFS o ENOMEM
Hay insuficiente memoria disponible. El socket no puede ser creado hasta que se liberen suficientes recursos.
EPROTONOSUPPORT
El tipo de protocolo o el protocolo especificado no es compatible dentro de este dominio.

Otros errores pueden ser generados por los módulos de protocolo subyacentes.

VERSIÓNES

POSIX.1-2024 especifica SOCK_CLOFORK, pero Linux no lo soporta.

ESTÁNDARES

POSIX.1-2024.

HISTORIA

POSIX.1-2001, 4.2BSD.

Es generalmente portable desde/hacia sistemas no-BSD que soportan clones de la capa de sockets BSD (incluyendo variantes de System V).

Las constantes manifiestas usadas bajo 4.x BSD para familias de protocolos son PF_UNIX, PF_INET, y similares, mientras que AF_UNIX, AF_INET, y similares se usan para familias de direcciones. Sin embargo, la página man de BSD ya promete: "La familia de protocolos es generalmente la misma que la familia de direcciones", y los estándares posteriores usan AF_* en todas partes.
