socket(7) Manual de Información Miscelánea socket(7)

NOMBRE

socket - Interfaz de sockets de Linux

SINOPSIS

#include <sys/socket.h>
sockfd = socket(int socket_family, int socket_type, int protocol);

DESCRIPCIÓN

Esta página del manual describe la interfaz de usuario de la capa de red de sockets de Linux. Los sockets compatibles con BSD son la interfaz uniforme entre el proceso de usuario y las pilas de protocolos de red en el kernel. Los módulos de protocolo se agrupan en familias de protocolos como AF_INET, AF_IPX y AF_PACKET, y tipos de socket como SOCK_STREAM o SOCK_DGRAM. Consulte socket(2) para obtener más información sobre familias y tipos.

Funciones de la capa de sockets

Estas funciones son utilizadas por el proceso de usuario para enviar o recibir paquetes y realizar otras operaciones de socket. Para más información, consulte sus páginas de manual respectivas.

socket(2) crea un socket, connect(2) conecta un socket a una dirección de socket remota, la función bind(2) enlaza un socket a una dirección de socket local, listen(2) indica al socket que se aceptarán nuevas conexiones, y accept(2) se utiliza para obtener un nuevo socket con una conexión entrante nueva. socketpair(2) devuelve dos sockets anónimos conectados (implementado solo para algunas familias locales como AF_UNIX)

send(2), sendto(2) y sendmsg(2) envían datos a través de un socket, y recv(2), recvfrom(2), recvmsg(2) reciben datos desde un socket. poll(2) y select(2) esperan la llegada de datos o la disponibilidad para enviar datos. Además, las operaciones de I/O estándar como write(2), writev(2), sendfile(2), read(2) y readv(2) pueden usarse para leer y escribir datos.

getsockname(2) devuelve la dirección local del socket y getpeername(2) devuelve la dirección remota del socket. getsockopt(2) y setsockopt(2) se utilizan para establecer o obtener opciones de la capa de socket o de protocolo. ioctl(2) se puede usar para establecer o leer otras opciones.

close(2) se utiliza para cerrar un socket. shutdown(2) cierra partes de una conexión de socket full-duplex.

La búsqueda, o la llamada a pread(2) o pwrite(2) con una posición distinta de cero no está soportada en sockets.

Es posible realizar E/S no bloqueantes en sockets estableciendo la bandera O_NONBLOCK en un descriptor de archivo de socket usando fcntl(2). Entonces, todas las operaciones que bloquearían devolverán (generalmente) EAGAIN (la operación debe reintentarse más tarde); connect(2) devolverá un error EINPROGRESS. El usuario puede entonces esperar varios eventos a través de poll(2) o select(2).

Eventos de E/S
Evento Bandera de Poll Ocurrencia
Lectura POLLIN Llegaron nuevos datos.
Lectura POLLIN Se completó una configuración de conexión (para sockets orientados a conexión)
Lectura POLLHUP Se inició una solicitud de desconexión por el otro extremo.
Lectura POLLHUP Una conexión está rota (solo para protocolos orientados a conexión). Cuando el socket se escribe, también se envía SIGPIPE.
Escritura POLLOUT El socket tiene suficiente espacio en el búfer de envío para escribir nuevos datos.
Lectura/Escritura POLLIN | POLLOUT Se completó una conexión saliente (2).
Lectura/Escritura POLLERR Ocurrió un error asíncrono.
Lectura/Escritura POLLHUP El otro extremo ha cerrado una dirección.
Excepción POLLPRI Llegaron datos urgentes. Se envía SIGURG entonces.

Una alternativa a poll(2) y select(2) es dejar que el kernel informe a la aplicación sobre los eventos a través de una señal SIGIO. Para ello, la bandera O_ASYNC debe establecerse en un descriptor de archivo de socket a través de fcntl(2) y un manejador de señales válido para SIGIO debe instalarse a través de sigaction(2). Consulte la discusión sobre Señales a continuación.

Estructuras de direcciones de sockets

Cada dominio de socket tiene su propio formato para las direcciones de socket, con una estructura de dirección específica del dominio. Cada una de estas estructuras comienza con un campo entero de "familia" (tipado como sa_family_t) que indica el tipo de la estructura de dirección. Esto permite que las diversas llamadas al sistema (por ejemplo, connect(2), bind(2), accept(2), getsockname(2), getpeername(2)), que son genéricas para todos los dominios de socket, determinen el dominio de una dirección de socket particular.

Para permitir que cualquier tipo de dirección de socket se pase a las interfaces en la API de sockets, se define el tipo struct sockaddr. El propósito de este tipo es puramente permitir la conversión de tipos de dirección de socket específicos del dominio a un tipo "genérico", para evitar advertencias del compilador sobre incompatibilidades de tipos en llamadas a la API de sockets.

Además, la API de sockets proporciona el tipo de dato struct sockaddr_storage. Este tipo es adecuado para alojar todas las estructuras de direcciones de socket específicas del dominio soportadas; es lo suficientemente grande y está correctamente alineado. (En particular, es lo suficientemente grande como para alojar direcciones de socket IPv6). La estructura incluye el siguiente campo, que puede usarse para identificar el tipo de dirección de socket realmente almacenada en la estructura:


    sa_family_t ss_family;

La estructura sockaddr_storage es útil en programas que deben manejar direcciones de socket de forma genérica (por ejemplo, programas que deben tratar tanto con direcciones de socket IPv4 como IPv6).

Opciones de socket

Las opciones de socket que se enumeran a continuación pueden establecerse usando setsockopt(2) y leerse con getsockopt(2) con el nivel de socket establecido en SOL_SOCKET para todos los sockets. A menos que se indique lo contrario, optval es un puntero a un int.

SO_ACCEPTCONN
Devuelve un valor que indica si este socket ha sido marcado para aceptar conexiones con listen(2). El valor 0 indica que este no es un socket de escucha, el valor 1 indica que este es un socket de escucha. Esta opción de socket es de solo lectura.

El argumento para SO_ATTACH_FILTER es una estructura sock_fprog, definida en <linux/filter.h>:

struct sock_fprog {
    unsigned short      len;
    struct sock_filter *filter;

El argumento para SO_ATTACH_BPF es un descriptor de archivo devuelto por la llamada al sistema bpf(2) y debe referirse a un programa de tipo BPF_PROG_TYPE_SOCKET_FILTER.
Estas opciones pueden establecerse varias veces para un socket dado, reemplazando cada vez el programa de filtro anterior. SO_ATTACH_REUSEPORT_CBPF
SO_ATTACH_REUSEPORT_EBPF
Para uso con la opción SO_REUSEPORT, estas opciones permiten al usuario establecer un programa BPF clásico (SO_ATTACH_REUSEPORT_CBPF) o BPF extendido (SO_ATTACH_REUSEPORT_EBPF) que define cómo se asignan los paquetes a los sockets del grupo reuseport (es decir, todos los sockets que tienen SO_REUSEPORT establecido y están utilizando la misma dirección local para recibir paquetes).
El programa BPF debe devolver un índice entre 0 y N-1 que representa el socket que debe recibir el paquete (donde N es el número de sockets en el grupo). Si el programa BPF devuelve un índice no válido, la selección del socket recurrirá al mecanismo simple de SO_REUSEPORT.
Los sockets se numeran en el orden en que se agregan al grupo (es decir, el orden de las llamadas bind(2) para sockets UDP o el orden de las llamadas listen(2) para sockets TCP). Los nuevos sockets agregados a un grupo reuseport heredarán el programa BPF. Cuando un socket se elimina de un grupo reuseport (a través de close(2)), el último socket del grupo se moverá a la posición del socket cerrado.
Estas opciones pueden establecerse repetidamente en cualquier momento en cualquier socket del grupo para reemplazar el programa BPF actual utilizado por todos los sockets del grupo.
SO_ATTACH_REUSEPORT_CBPF toma el mismo tipo de argumento que SO_ATTACH_FILTER y SO_ATTACH_REUSEPORT_EBPF toma el mismo tipo de argumento que SO_ATTACH_BPF.
El soporte UDP para esta característica está disponible desde Linux 4.5; el soporte TCP está disponible desde Linux 4.6.
SO_BINDTODEVICE
Vincula este socket a un dispositivo particular como “eth0”, según se especifica en el nombre de interfaz pasado. Si el nombre es una cadena vacía o el tamaño de la opción es cero, se elimina la vinculación del dispositivo del socket. La opción pasada es una cadena de nombre de interfaz terminada en nulo de tamaño variable con un tamaño máximo de IFNAMSIZ. Si un socket está vinculado a una interfaz, solo los paquetes recibidos de esa interfaz en particular son procesados por el socket. Tenga en cuenta que esto solo funciona para algunos tipos de sockets, en particular los sockets AF_INET. No se admite para sockets de paquetes (use bind(2) normal allí).
Antes de Linux 3.8, esta opción de socket se podía establecer, pero no recuperar con getsockopt(2). Desde Linux 3.8, es legible. El argumento optlen debe contener el tamaño del búfer disponible para recibir el nombre del dispositivo y se recomienda que sea de IFNAMSIZ bytes. La longitud real del nombre del dispositivo se informa en el argumento optlen.
SO_BROADCAST
Establece o obtiene el indicador de broadcast. Cuando está habilitado, los sockets de datagramas tienen permitido enviar paquetes a una dirección de broadcast. Esta opción no tiene efecto en los sockets orientados a flujo.
SO_BSDCOMPAT
Habilita la compatibilidad con errores de BSD. Esto es utilizado por el módulo de protocolo UDP en Linux 2.0 y 2.2. Si está habilitado, los errores ICMP recibidos para un socket UDP no se pasarán al programa de usuario. En versiones posteriores del kernel, el soporte para esta opción se ha eliminado gradualmente: Linux 2.4 la ignora silenciosamente, y Linux 2.6 genera una advertencia del kernel (printk()) si un programa utiliza esta opción. Linux 2.0 también habilitó opciones de compatibilidad con errores de BSD (cambio de encabezado aleatorio, omisión del indicador de broadcast) para sockets raw con esta opción, pero eso se eliminó en Linux 2.2.
SO_DEBUG
Habilita la depuración de sockets. Permitido solo para procesos con la capacidad CAP_NET_ADMIN o un ID de usuario efectivo de 0.
SO_DETACH_FILTER (desde Linux 2.2)
SO_DETACH_BPF (desde Linux 3.19)
Estas dos opciones, que son sinónimos, pueden usarse para eliminar el programa BPF clásico o extendido adjunto a un socket con SO_ATTACH_FILTER o SO_ATTACH_BPF. El valor de la opción se ignora.
SO_DOMAIN (desde Linux 2.6.32)
Recupera el dominio del socket como un entero, devolviendo un valor como AF_INET6. Ver socket(2) para detalles. Esta opción de socket es de solo lectura.
SO_ERROR
Obtiene y borra el error pendiente del socket. Esta opción de socket es de solo lectura. Espera un entero.
SO_DONTROUTE
No enviar a través de una puerta de enlace, enviar solo a hosts directamente conectados. El mismo efecto se puede lograr estableciendo la bandera MSG_DONTROUTE en una operación de send(2) del socket. Espera una bandera entera booleana.
SO_INCOMING_CPU (se puede obtener desde Linux 3.19, se puede establecer desde Linux 4.4)
Establece o obtiene la afinidad de CPU de un socket. Espera una bandera entera.

int cpu = 1;
setsockopt(fd, SOL_SOCKET, SO_INCOMING_CPU, &cpu,
           sizeof(cpu));

Debido a que todos los paquetes para un solo flujo (es decir, todos los paquetes para la misma 4-tupla) llegan a la única cola RX que está asociada con una CPU en particular, el caso de uso típico es emplear un proceso de escucha por cola RX, con el flujo entrante siendo manejado por un oyente en la misma CPU que está manejando la cola RX. Esto proporciona un comportamiento NUMA óptimo y mantiene las cachés de CPU activas.
SO_INCOMING_NAPI_ID (se puede obtener desde Linux 4.12)
Devuelve un ID único a nivel de sistema llamado NAPI ID que está asociado con una cola RX en la que se recibió el último paquete asociado con ese socket.
Esto puede ser utilizado por una aplicación para dividir los flujos entrantes entre hilos de trabajo basándose en la cola RX en la que se reciben los paquetes asociados con los flujos. Permite que cada hilo de trabajo se asocie con una cola de recepción de hardware NIC y atienda todas las solicitudes de conexión recibidas en esa cola RX. Este mapeo entre un hilo de aplicación y una cola NIC de hardware agiliza el flujo de datos de la NIC a la aplicación.
SO_KEEPALIVE
Habilita el envío de mensajes keep-alive en sockets orientados a conexión. Espera una bandera entera booleana.
SO_LINGER
Establece o obtiene la opción SO_LINGER. El argumento es una estructura linger.

struct linger {
    int l_onoff;    /* linger activo */
    int l_linger;   /* cuántos segundos esperar */
};

Cuando está habilitado, una llamada a close(2) o shutdown(2) no regresará hasta que todos los mensajes en cola para el socket se hayan enviado con éxito o se haya alcanzado el tiempo de espera de linger. De lo contrario, la llamada regresa inmediatamente y el cierre se realiza en segundo plano. Cuando el socket se cierra como parte de exit(2), siempre espera en segundo plano.
SO_LOCK_FILTER
Cuando se establece, esta opción evitará cambiar los filtros asociados con el socket. Estos filtros incluyen los establecidos usando las opciones de socket SO_ATTACH_FILTER, SO_ATTACH_BPF, SO_ATTACH_REUSEPORT_CBPF y SO_ATTACH_REUSEPORT_EBPF.
El caso de uso típico es que un proceso privilegiado configure un socket raw (una operación que requiere la capacidad CAP_NET_RAW), aplique un filtro restrictivo, establezca la opción SO_LOCK_FILTER y luego reduzca sus privilegios o pase el descriptor de archivo del socket a un proceso no privilegiado a través de un socket de dominio UNIX.
Una vez que la opción SO_LOCK_FILTER ha sido habilitada, los intentos de cambiar o eliminar el filtro adjunto a un socket, o de deshabilitar la opción SO_LOCK_FILTER fallarán con el error EPERM.
SO_MARK (desde Linux 2.6.25)
Establece la marca para cada paquete enviado a través de este socket (similar al objetivo MARK de netfilter pero basado en socket). Cambiar la marca se puede utilizar para el enrutamiento basado en marcas sin netfilter o para filtrado de paquetes. Establecer esta opción requiere la capacidad CAP_NET_ADMIN o CAP_NET_RAW (desde Linux 5.17).
SO_OOBINLINE
Si esta opción está habilitada, los datos fuera de banda se colocan directamente en el flujo de datos de recepción. De lo contrario, los datos fuera de banda solo se pasan cuando se establece la bandera MSG_OOB durante la recepción.
SO_PASSCRED
Habilita o deshabilita la recepción del mensaje de control SCM_CREDENTIALS. Para más información, ver unix(7).
SO_PASSSEC
SCM_SECURITY
Habilita o deshabilita la recepción del mensaje de control SCM_SECURITY. Para más información, véase unix(7).
SO_PEEK_OFF (desde Linux 3.4)
Esta opción, que actualmente solo se admite para sockets unix(7), establece el valor del "desplazamiento de inspección" para la llamada al sistema recv(2) cuando se utiliza con la bandera MSG_PEEK.
Cuando esta opción se establece a un valor negativo (se establece a -1 para todos los sockets nuevos), se proporciona el comportamiento tradicional: recv(2) con la bandera MSG_PEEK inspeccionará datos desde el frente de la cola.
Cuando la opción se establece a un valor mayor o igual a cero, la siguiente inspección de datos en cola en el socket se realizará en el desplazamiento de bytes especificado por el valor de la opción. Al mismo tiempo, el "desplazamiento de inspección" se incrementará en el número de bytes que se inspeccionaron desde la cola, de modo que una inspección posterior devolverá los siguientes datos en la cola.
Si se eliminan datos del frente de la cola mediante una llamada a recv(2) (o similar) sin la bandera MSG_PEEK, el "desplazamiento de inspección" se reducirá en el número de bytes eliminados. En otras palabras, recibir datos sin la bandera MSG_PEEK hará que el "desplazamiento de inspección" se ajuste para mantener la posición relativa correcta en los datos en cola, de modo que una inspección posterior recuperará los datos que se habrían recuperado si los datos no se hubieran eliminado.
Para sockets de datagramas, si el "desplazamiento de inspección" apunta a la mitad de un paquete, los datos devueltos se marcarán con la bandera MSG_TRUNC.
El siguiente ejemplo sirve para ilustrar el uso de SO_PEEK_OFF. Supongamos que un socket de flujo tiene los siguientes datos de entrada en cola:

aabbccddeeff

La siguiente secuencia de llamadas a recv(2) tendrá el efecto anotado en los comentarios:

int ov = 4;                  // Establece el desplazamiento de inspección a 4
setsockopt(fd, SOL_SOCKET, SO_PEEK_OFF, &ov, sizeof(ov));
recv(fd, buf, 2, MSG_PEEK);  // Inspecciona "cc"; desplazamiento establecido a 6
recv(fd, buf, 2, MSG_PEEK);  // Inspecciona "dd"; desplazamiento establecido a 8
recv(fd, buf, 2, 0);         // Lee "aa"; desplazamiento establecido a 6
recv(fd, buf, 2, MSG_PEEK);  // Inspecciona "ee"; desplazamiento establecido a 8

SO_PEERCRED
Devuelve las credenciales del proceso par conectado a este socket. Para más detalles, véase unix(7).
SO_PEERSEC (desde Linux 2.6.2)
Devuelve el contexto de seguridad del socket par conectado a este socket. Para más detalles, véanse unix(7) y ip(7).
SO_PRIORITY
Establece la prioridad definida por el protocolo para todos los paquetes que se enviarán en este socket. Linux utiliza este valor para ordenar las colas de red: los paquetes con una prioridad más alta pueden ser procesados primero dependiendo de la disciplina de cola del dispositivo seleccionada. Establecer una prioridad fuera del rango de 0 a 6 requiere la capacidad CAP_NET_ADMIN.
SO_PROTOCOL (desde Linux 2.6.32)
Recupera el protocolo del socket como un entero, devolviendo un valor como IPPROTO_SCTP. Véase socket(2) para detalles. Esta opción de socket es de solo lectura.
SO_RCVBUF
Establece o obtiene el búfer máximo de recepción del socket en bytes. El kernel duplica este valor (para permitir espacio para la sobrecarga de contabilidad) cuando se establece mediante setsockopt(2), y este valor duplicado es devuelto por getsockopt(2). El valor predeterminado se establece en el archivo /proc/sys/net/core/rmem_default, y el valor máximo permitido se establece en el archivo /proc/sys/net/core/rmem_max. El mínimo valor (duplicado) para esta opción es 256.
SO_RCVBUFFORCE (desde Linux 2.6.14)
Utilizando esta opción de socket, un proceso privilegiado (CAP_NET_ADMIN) puede realizar la misma tarea que SO_RCVBUF, pero se puede anular el límite rmem_max.
SO_RCVLOWAT
SO_SNDLOWAT
Especifica el número mínimo de bytes en el búfer hasta que la capa de socket pase los datos al protocolo (SO_SNDLOWAT) o al usuario al recibir (SO_RCVLOWAT). Estos dos valores se inicializan a 1. SO_SNDLOWAT no es modificable en Linux (setsockopt(2) falla con el error ENOPROTOOPT). SO_RCVLOWAT es modificable solo desde Linux 2.4.
Antes de Linux 2.6.28, select(2), poll(2) y epoll(7) no respetaban la configuración de SO_RCVLOWAT en Linux, e indicaban un socket como legible cuando había incluso un solo byte de datos disponible. Una lectura posterior del socket se bloquearía hasta que estuvieran disponibles SO_RCVLOWAT bytes. Desde Linux 2.6.28, select(2), poll(2) y epoll(7) indican un socket como legible solo si hay al menos SO_RCVLOWAT bytes disponibles.
SO_RCVTIMEO
SO_SNDTIMEO
Especifica los tiempos de espera de recepción o envío hasta que se informe un error. El argumento es un struct timeval. Si una función de entrada o salida se bloquea durante este período de tiempo, y se han enviado o recibido datos, el valor de retorno de esa función será la cantidad de datos transferidos; si no se han transferido datos y se ha alcanzado el tiempo de espera, entonces se devuelve -1 con errno establecido a EAGAIN o EWOULDBLOCK, o EINPROGRESS (para connect(2)) como si el socket se hubiera especificado como no bloqueante. Si el tiempo de espera se establece a cero (el valor predeterminado), entonces la operación nunca se agotará. Los tiempos de espera solo tienen efecto para las llamadas al sistema que realizan E/S de socket (por ejemplo, accept(2), connect(2), read(2), recvmsg(2), send(2), sendmsg(2)); los tiempos de espera no tienen efecto para select(2), poll(2), epoll_wait(2) y similares.
SO_REUSEADDR
Indica que las reglas utilizadas para validar las direcciones proporcionadas en una llamada a bind(2) deben permitir la reutilización de direcciones locales. Para sockets AF_INET, esto significa que un socket puede enlazarse, excepto cuando hay un socket de escucha activo enlazado a la dirección. Cuando el socket de escucha está enlazado a INADDR_ANY con un puerto específico, entonces no es posible enlazarse a este puerto para ninguna dirección local. El argumento es un indicador booleano entero.
SO_REUSEPORT (desde Linux 3.9)
Permite que múltiples sockets AF_INET o AF_INET6 se enlacen a una dirección de socket idéntica. Esta opción debe establecerse en cada socket (incluido el primer socket) antes de llamar a bind(2) en el socket. Para evitar el secuestro de puertos, todos los procesos que se enlazan a la misma dirección deben tener el mismo UID efectivo. Esta opción se puede emplear tanto con sockets TCP como UDP.
Para sockets TCP, esta opción permite mejorar la distribución de carga de accept(2) en un servidor multihilo utilizando un socket de escucha distinto para cada hilo. Esto proporciona una mejor distribución de carga en comparación con las técnicas tradicionales como el uso de un solo hilo de accept(2) que distribuye las conexiones, o tener múltiples hilos que compiten para realizar accept(2) desde el mismo socket.
Para sockets UDP, el uso de esta opción puede proporcionar una mejor distribución de datagramas entrantes a múltiples procesos (o hilos) en comparación con la técnica tradicional de tener múltiples procesos compitiendo para recibir datagramas en el mismo socket.
SO_RXQ_OVFL (desde Linux 2.6.33)
Indica que se debe adjuntar un mensaje auxiliar (cmsg) de valor sin signo de 32 bits a los skb recibidos, indicando el número de paquetes descartados por el socket desde su creación.
SO_SELECT_ERR_QUEUE (desde Linux 3.10)
Cuando esta opción está establecida en un socket, una condición de error en un socket causa una notificación no solo a través del conjunto exceptfds de select(2). Del mismo modo, poll(2) también devuelve un POLLPRI cada vez que se devuelve un evento POLLERR.
Antecedentes: esta opción se agregó cuando la activación por una condición de error ocurría solo a través de los conjuntos readfds y writefds de select(2). La opción se agregó para permitir el monitoreo de condiciones de error a través del argumento exceptfds sin tener que recibir simultáneamente notificaciones (a través de readfds) para datos regulares que se pueden leer del socket. Después de los cambios en Linux 4.16, el uso de esta bandera para lograr las notificaciones deseadas ya no es necesario. Sin embargo, esta opción se conserva por compatibilidad hacia atrás.
SO_SNDBUF
Establece o obtiene el búfer máximo de envío del socket en bytes. El kernel duplica este valor (para permitir espacio para la sobrecarga de contabilidad) cuando se establece mediante setsockopt(2), y este valor duplicado es devuelto por getsockopt(2). El valor predeterminado se establece en el archivo /proc/sys/net/core/wmem_default y el valor máximo permitido se establece en el archivo /proc/sys/net/core/wmem_max. El mínimo valor (duplicado) para esta opción es 2048.

SO_SNDBUFFORCE

SO_SNDBUFFORCE (desde Linux 2.6.14)
Usando esta opción de socket, un proceso privilegiado (CAP_NET_ADMIN) puede realizar la misma tarea que SO_SNDBUF, pero el límite de wmem_max puede ser anulado.
SO_TIMESTAMP
Habilita o deshabilita la recepción del mensaje de control SO_TIMESTAMP. El mensaje de control de marca de tiempo se envía con el nivel SOL_SOCKET y un tipo de mensaje (cmsg_type) de SCM_TIMESTAMP. El campo cmsg_data es una struct timeval que indica la hora de recepción del último paquete pasado al usuario en esta llamada. Ver cmsg(3) para detalles sobre mensajes de control.
SO_TIMESTAMPNS (desde Linux 2.6.22)
Habilita o deshabilita la recepción del mensaje de control SO_TIMESTAMPNS. El mensaje de control de marca de tiempo se envía con el nivel SOL_SOCKET y un tipo de mensaje (cmsg_type) de SCM_TIMESTAMPNS. El campo cmsg_data es una struct timespec que indica la hora de recepción del último paquete pasado al usuario en esta llamada. El reloj utilizado para la marca de tiempo es CLOCK_REALTIME. Ver cmsg(3) para detalles sobre mensajes de control.
Un socket no puede mezclar SO_TIMESTAMP y SO_TIMESTAMPNS: los dos modos son mutuamente excluyentes.
SO_TYPE
Obtiene el tipo de socket como un entero (por ejemplo, SOCK_STREAM). Esta opción de socket es de solo lectura.
SO_BUSY_POLL (desde Linux 3.11)
Establece el tiempo aproximado en microsegundos para sondeo activo (busy poll) en una recepción bloqueante cuando no hay datos. Incrementar este valor requiere CAP_NET_ADMIN. El valor predeterminado para esta opción se controla a través del archivo /proc/sys/net/core/busy_read.
El valor en el archivo /proc/sys/net/core/busy_poll determina cuánto tiempo select(2) y poll(2) harán sondeo activo cuando operen en sockets con SO_BUSY_POLL establecido y no se encuentren eventos que reportar.
En ambos casos, el sondeo activo solo se realizará cuando el socket haya recibido datos recientemente de un dispositivo de red que soporte esta opción.
Mientras que el sondeo activo puede mejorar la latencia de algunas aplicaciones, se debe tener cuidado al usarlo ya que incrementará el uso de CPU y el consumo de energía.

Señales

Al escribir en un socket orientado a conexión que ha sido cerrado (por el extremo local o remoto), se envía SIGPIPE al proceso que escribe y se devuelve EPIPE. La señal no se envía cuando la llamada de escritura especificó el flag MSG_NOSIGNAL.

Cuando se solicita con FIOSETOWN de fcntl(2) o SIOCSPGRP de ioctl(2), se envía SIGIO cuando ocurre un evento de I/O. Es posible usar poll(2) o select(2) en el manejador de señales para averiguar en qué socket ocurrió el evento. Una alternativa (en Linux 2.2) es establecer una señal en tiempo real usando F_SETSIG de fcntl(2); el manejador de la señal en tiempo real será llamado con el descriptor de archivo en el campo si_fd de su siginfo_t. Ver fcntl(2) para más información.

Bajo algunas circunstancias (por ejemplo, múltiples procesos accediendo a un único socket), la condición que causó SIGIO puede haber desaparecido ya cuando el proceso reacciona a la señal. Si esto sucede, el proceso debe esperar nuevamente ya que Linux reenviará la señal más tarde.

Interfaces /proc

Los parámetros centrales de red de sockets se pueden acceder a través de archivos en el directorio /proc/sys/net/core/.

rmem_default
contiene la configuración predeterminada en bytes del buffer de recepción del socket.
rmem_max
contiene el tamaño máximo del buffer de recepción del socket en bytes que un usuario puede establecer usando la opción de socket SO_RCVBUF.
wmem_default
contiene la configuración predeterminada en bytes del buffer de envío del socket.
wmem_max
contiene el tamaño máximo del buffer de envío del socket en bytes que un usuario puede establecer usando la opción de socket SO_SNDBUF.
message_cost
message_burst
configuran el filtro de cubo de fichas (token bucket) utilizado para limitar las advertencias de mensajes causadas por eventos de red externos.
netdev_max_backlog
Número máximo de paquetes en la cola de entrada global.
optmem_max
Tamaño máximo de datos auxiliares y datos de control de usuario como los iovecs por socket.

Ioctls

Estas operaciones se pueden acceder usando ioctl(2):


error = ioctl(ip_socket, ioctl_type, &value_result);
SIOCGSTAMP
Devuelve una struct timeval con la marca de tiempo de recepción del último paquete pasado al usuario. Esto es útil para mediciones precisas del tiempo de ida y vuelta. Ver setitimer(2) para una descripción de struct timeval. Este ioctl solo debe usarse si las opciones de socket SO_TIMESTAMP y SO_TIMESTAMPNS no están establecidas en el socket. De lo contrario, devuelve la marca de tiempo del último paquete que fue recibido mientras SO_TIMESTAMP y SO_TIMESTAMPNS no estaban establecidas, o falla si no se ha recibido tal paquete (es decir, ioctl(2) devuelve -1 con errno establecido a ENOENT).
SIOCSPGRP
Establece el proceso o grupo de procesos que recibirá señales SIGIO o SIGURG cuando la E/S sea posible o los datos urgentes estén disponibles. El argumento es un puntero a un pid_t. Para más detalles, ver la descripción de F_SETOWN en fcntl(2).
FIOASYNC
Cambia el flag O_ASYNC para habilitar o deshabilitar el modo de E/S asíncrona del socket. El modo de E/S asíncrona significa que la señal SIGIO o la señal establecida con F_SETSIG se dispara cuando ocurre un nuevo evento de E/S.
El argumento es un flag booleano entero. (Esta operación es sinónimo del uso de fcntl(2) para establecer el flag O_ASYNC).
SIOCGPGRP
Obtiene el proceso o grupo de procesos actual que recibe señales SIGIO o SIGURG, o 0 cuando no hay ninguno establecido.

Operaciones válidas de fcntl(2):

FIOGETOWN
Lo mismo que el ioctl(2) SIOCGPGRP.
FIOSETOWN
Lo mismo que el ioctl(2) SIOCSPGRP.

VERSIONES

SO_BINDTODEVICE se introdujo en Linux 2.0.30. SO_PASSCRED es nuevo en Linux 2.2. Las interfaces de /proc se introdujeron en Linux 2.2. SO_RCVTIMEO y SO_SNDTIMEO son soportados desde Linux 2.3.41. Anteriormente, los tiempos de espera eran fijos a una configuración específica del protocolo, y no podían ser leídos ni escritos.

NOTAS

Linux asume que la mitad del buffer de envío/recepción se usa para estructuras internas del kernel; por lo tanto, los valores en los archivos /proc correspondientes son el doble de lo que se puede observar en la red.

Linux permitirá la reutilización de puertos solo con la opción SO_REUSEADDR cuando esta opción fue establecida tanto en el programa anterior que realizó un bind(2) al puerto como en el programa que quiere reutilizar el puerto. Esto difiere de algunas implementaciones (por ejemplo, FreeBSD) donde solo el programa posterior necesita establecer la opción SO_REUSEADDR. Típicamente esta diferencia es invisible, ya que, por ejemplo, un programa servidor está diseñado para establecer siempre esta opción.
