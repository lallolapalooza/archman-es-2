NVCHECKER(1) Manual de Comandos Generales NVCHECKER(1)

NOMBRE

nvchecker - Verificador de nuevas versiones para lanzamientos de software

nvchecker (acrónimo de new version checker) sirve para verificar si se ha lanzado una nueva versión de algún software.

Esta es la rama 2.0. Para la antigua versión 1.x, por favor, cambie a la rama v1.x.
https://github.com/lilydjwg/nvchecker/actions?query=workflow%3A%22run+tests%22
https://badge.fury.io/py/nvchecker

DEPENDENCIA

  • Python 3.8+
  • Biblioteca Python: structlog, platformdirs, tomli (en Python < 3.11)
  • Una de estas combinaciones de bibliotecas Python (ordenadas por preferencia):
  • tornado + pycurl
  • aiohttp
  • httpx con soporte http2 (experimental; solo se admite la última versión)
  • tornado
•
Todos los comandos utilizados en los archivos de configuración de versiones de su software

INSTALACIÓN Y EJECUCIÓN

Para instalar:

pip3 install nvchecker

Para usar el último código, también puede clonar este repositorio y ejecutar:

python3 setup.py install

Para ver las opciones disponibles:

nvchecker --help

Ejecutar con uno o más archivos de versiones de software:

nvchecker -c archivo_configuracion.toml

Un archivo de configuración simple podría verse así:

[nvchecker]
source = "github"
github = "lilydjwg/nvchecker"
[python-toml]
source = "pypi"
pypi = "toml"

Normalmente le gustará especificar algunos "archivos de registro de versiones"; vea a continuación.

Registro JSON

Con --logger=json o --logger=both, puede obtener un registro estructurado para su consumo programático. Puede usar --json-log-fd=FD para especificar el descriptor de archivo al que enviar los registros (tenga cuidado de hacer un búfer de línea). La opción de nivel de registro (-l o --logging) no tiene efecto con esto.

El registro JSON es una cadena JSON por línea. Los siguientes eventos y campos documentados son estables, los no documentados pueden cambiar sin previo aviso.

evento=actualizado
Se detecta una actualización. Los campos name, revision, old_version y version están disponibles. old_version puede ser null y revision puede estar ausente.
evento=actualizado-a-fecha
No hay actualización. Los campos name y version están disponibles.
evento=sin-resultado
No se detecta ninguna versión. Puede haber un error. El campo name está disponible.
nivel=error
Hay un error. Los campos name y exc_info pueden estar disponibles para proporcionar más información.

Actualización desde la versión 1.x

Hay varios cambios incompatibles hacia atrás con la versión anterior 1.x.

1.
La versión 2.x requiere Python 3.7+ para ejecutarse.
2.
La sintaxis del comando cambia un poco. Necesita usar un interruptor -c para especificar el archivo de configuración de versiones de su software (o usar el predeterminado).
3.
El formato del archivo de configuración ha cambiado de ini a toml https://toml.io/ . Puede usar el script nvchecker-ini2toml para convertir sus archivos de configuración antiguos. Sin embargo, los comentarios y el formato se perderán, y es posible que algunas opciones no se conviertan correctamente.
4.
Se han renombrado varias opciones. max_concurrent a max_concurrency, y todos los nombres de opciones tienen su - reemplazado por _.
5.
Todas las tablas de configuración de software necesitan una opción source para especificar qué fuente se utilizará en lugar de deducirse de los nombres de opciones en uso. Esto permite descubrir complementos de origen adicionales.
6.
Los archivos de registro de versiones han cambiado para usar formato JSON (el antiguo formato se convertirá al escribir).
7.
Se elimina el origen vcs. (Está disponible dentro de <lilac> en el momento.) Se proporciona un origen git.
8.
Se eliminan include_tags_pattern e ignored_tags. Use List Options en su lugar.

ARCHIVOS DE REGISTRO DE VERSIONES

Los archivos de registro de versiones registran qué versión del software conoce o está disponible. Son un objeto JSON simple que mapea nombres de software a versiones conocidas.

El comando nvtake

Este comando ayuda a administrar archivos de registro de versiones. Lee archivos de registro de versiones antiguos y nuevos, y una lista de nombres dados en la línea de comandos. Luego actualiza las versiones de esos nombres en el archivo de registro de versiones antiguo.

Esto ayuda cuando ha conocido (y procesado) parte del software actualizado, pero no todo. Puede indicárselo a nvchecker a través de este comando en lugar de editar el archivo manualmente.

Este comando será de gran ayuda si especifica dónde se encuentran sus archivos de registro de versiones en su archivo de configuración. Vea a continuación cómo usar un archivo de configuración.

El comando nvcmp

Este comando compara el archivo newver con el archivo oldver e imprime cualquier diferencia como actualizaciones, por ejemplo:

$ nvcmp -c sample_source.toml
Sparkle Test App None -> 2.0
test 0.0 -> 0.1

ARCHIVOS DE CONFIGURACIÓN

Los archivos de origen de versiones de software están en formato toml https://toml.io/
. El nombre de la clave es el nombre del software. Los siguientes campos se utilizan para indicar a nvchecker cómo determinar la versión actual de ese software.

Vea sample_source.toml https://github.com/lilydjwg/nvchecker/blob/master/sample_config.toml
para un ejemplo.

Tabla de configuración

Una tabla especial llamada __config__ proporciona algunas opciones de configuración.

Las rutas relativas son relativas a los archivos de origen, y ~ y las variables de entorno se expanden.

Las opciones admitidas actualmente son:

oldver
Especifica un archivo de registro de versiones que contiene la información de la versión antigua.
newver
Especifica un archivo de registro de versiones para almacenar la información de la nueva versión.
proxy
El proxy HTTP a utilizar. El formato es proto://host:port, por ejemplo http://localhost:8087. Los diferentes backends tienen diferentes niveles de soporte para esto, por ejemplo, con pycurl puede usar proxies socks5h://host:port.
max_concurrency
Número máximo de trabajos concurrentes. Predeterminado: 20.
http_timeout
Tiempo en segundos para esperar las solicitudes HTTP. Predeterminado: 20.
keyfile
Especifica un archivo de configuración de toml que contiene información de clave (token). Este archivo debe contener una tabla keys, que mapea nombres de clave a valores de clave. Consulte la fuente específica para los nombres de clave a utilizar.

Ejemplo de keyfile.toml:

[keys]
# https://github

Este sitio no está asociado de ninguna forma con Arch Linux ni afiliado a este proyecto. El contenido es únicamente una traducción de las páginas del manual de Arch publicadas en man.archlinux.org.

.com/settings/tokens # scope: repo -> public_repo github = "ghp_"`

Opciones Globales

Las siguientes opciones se aplican a todas las fuentes de verificación. Puedes usarlas en cualquier elemento de tu archivo de configuración.

prefijo
Elimina la cadena de prefijo si la cadena de versión comienza con ella. De lo contrario, la cadena de versión se devuelve tal cual.

Si se usan tanto prefijo como patron_origen/patron_destino, el prefijo se aplica primero.

patron_origen, patron_destino
Ambos son expresiones regulares compatibles con Python. Si se encuentra patron_origen en la cadena de versión, se reemplazará con patron_destino.

Si no se encuentra patron_origen, la cadena de versión permanece sin cambios y no se emite ningún error.

missing_ok
Suprime advertencias y errores si un módulo de verificación de versiones no encuentra nada. No todas las fuentes lo admiten.
proxy
El proxy HTTP a utilizar. El formato es proto://host:puerto, por ejemplo, http://localhost:8087. Diferentes backends tienen diferentes niveles de soporte para esto, por ejemplo, con pycurl puedes usar proxies socks5h://host:puerto.

Establécelo a "" (cadena vacía) para anular la configuración global.

Esto solo funciona cuando la implementación de la fuente utiliza el cliente HTTP incorporado y no funciona con la fuente aur porque está agrupada (sin embargo, la configuración global del proxy todavía se aplica).

user_agent
La cadena de agente de usuario a utilizar para las solicitudes HTTP.
tries
Intenta las veces especificadas cuando ocurre un error de red. El valor predeterminado es 1.

Esto solo funciona cuando la implementación de la fuente utiliza el cliente HTTP incorporado.

httptoken
Un token de autorización personal utilizado para obtener la URL con la cabecera Authorization. El tipo de token depende de la autorización requerida.
  • Para token Bearer, establece: Bearer <Tu_bearer_token>
  • Para token Basic, establece: Basic <Tu_token_codificado_en_base64>

En el archivo de claves, añade el token httptoken_{nombre}.

verify_cert
Si verificar o no el certificado HTTPS. El valor predeterminado es true.

Opciones de Lista

Las siguientes opciones se aplican a las fuentes que devuelven una lista. Consulta las tablas de fuentes individuales para determinar si son compatibles.

include_regex
Considera solo las cadenas de versión que coincidan con la expresión regular dada. Toda la cadena debe coincidir con la expresión regular. ¡Asegúrate de usar .* cuando quieras decir eso!
exclude_regex
No consideres las cadenas de versión que coincidan con la expresión regular dada. Toda la cadena debe coincidir con la expresión regular. ¡Asegúrate de usar .* cuando quieras decir eso! Esta opción tiene mayor precedencia que include_regex; es decir, si coincide con esta, se excluye incluso si también coincide con include_regex.
sort_version_key
Ordena la cadena de versión usando esta función clave. Elige entre parse_version, vercmp y awesomeversion. El valor predeterminado es parse_version. parse_version utiliza una versión antigua de pkg_resources.parse_version. vercmp utiliza pyalpm.vercmp. awesomeversion utiliza <awesomeversion> .
ignored
Cadenas de versión que se ignoran explícitamente, separadas por espacios. Esto puede ser útil para evitar versiones mal nombradas conocidas, para que las más nuevas no sean "sobrescritas" por las antiguas y rotas.

Buscar en una página web

source = "regex"

Busca en una página web específica la cadena de versión. Este tipo de búsqueda de versiones tiene estos campos:

url
La URL de la página web a obtener.
encoding
(Opcional) La codificación de caracteres de la página web, si latin1 no es apropiada.
regex
Una expresión regular utilizada para encontrar la cadena de versión.

Puede tener cero o un grupo de captura. El grupo de captura o la coincidencia completa es la cadena de versión.

Cuando se encuentran varias cadenas de versión, se elige el máximo de ellas.

post_data
(Opcional) Cuando está presente, se utilizará una solicitud POST (en lugar de una GET). El valor debe ser una cadena que contenga el cuerpo completo de la solicitud. La codificación de la cadena se puede especificar usando la opción post_data_type.
post_data_type
(Opcional) Especifica el Content-Type del cuerpo de la solicitud (post_data). Por defecto, es application/x-www-form-urlencoded.

Esta fuente admite Opciones de Lista.

Buscar en una cabecera HTTP

source = "httpheader"

Envía una solicitud HTTP y busca en una cabecera específica.

url
La URL de la solicitud HTTP.
header
(Opcional) La cabecera a examinar. El valor predeterminado es Location. Otra cabecera útil es Content-Disposition.
regex
Una expresión regular utilizada para encontrar la cadena de versión.

Puede tener cero o un grupo de captura. El grupo de captura o la coincidencia completa es la cadena de versión.

Cuando se encuentran varias cadenas de versión, se elige el máximo de ellas.

method
(Opcional) El método HTTP a utilizar. El valor predeterminado es HEAD.
follow_redirects
(Opcional) Si seguir las redirecciones HTTP 3xx o no. El valor predeterminado es false. Si estás examinando una cabecera Location, no deberías cambiar esto.

source = "aur"

Comprueba el Arch User Repository https://aur.archlinux.org/ en busca de actualizaciones. La configuración de proxy por elemento no funciona para esto porque varios elementos se agruparán en una sola solicitud.

aur
El nombre del paquete en AUR. Si está vacío, usa el nombre del software (el nombre de la tabla).
strip_release
Elimina la parte de la versión (release).
use_last_modified
Añade la fecha de última modificación a la versión.

Comprobar GitHub

source = "github"

Comprueba GitHub https://github.com/ en busca de actualizaciones. La versión devuelta está en formato de fecha %Y%m%d.%H%M%S, por ejemplo, 20130701.012212, a menos que se usen use_latest_release, use_max_tag o use_max_release. Ver abajo.

github
El repositorio de GitHub, con el autor, por ejemplo, lilydjwg/nvchecker.
branch
¿Qué rama seguir? Por defecto: la predeterminada del repositorio.
path
Solo se devolverán los commits que contengan esta ruta de archivo.
host
Nombre de host para instancias de GitHub autoalojadas.
use_latest_release
Establece esto en true para comprobar la última versión en GitHub.

Las versiones de GitHub no son lo mismo que las etiquetas git. Verás nombres y descripciones de versiones grandes en la página de versiones para tales versiones, por ejemplo, zfsonlinux/zfs's https://github.com/zfsonlinux/zfs/releases , y esas pequeñas como nvchecker's https://github.com/lilydjwg/nvchecker/releases

son solo etiquetas git que deberían usar use_max_tag abajo.

Devolverá el nombre de la etiqueta de la versión en lugar de la fecha. (Por razones históricas no devuelve el nombre de la versión. Ver abajo para cambiar.)

use_max_release
Establece esto en true para comprobar la versión máxima en GitHub. Esta opción devuelve la mayor ordenada por la opción sort_version_key. Devolverá el nombre de la etiqueta en lugar de la fecha.
use_release_name
Cuando use_latest_release o use_max_release es true, establecer esto en true hará que nvchecker devuelva el nombre de la versión en lugar del nombre de la etiqueta.
include_prereleases
Cuando use_latest_release o use_max_release es true, establece esto en true para tener en cuenta las pre-versiones (prereleases).

Esto devuelve los nombres de las versiones (no los nombres de las etiquetas).

Esto requiere un token porque está utilizando la API GraphQL v4.

use_latest_tag
Establece esto en true para comprobar la última etiqueta en GitHub.

Esto requiere un token porque está utilizando la API GraphQL v4.

query
Cuando use_latest_tag es true, esto establece una consulta para la etiqueta. El método de coincidencia exacta no está documentado por GitHub.
use_max_tag
Establece esto en true para comprobar la etiqueta máxima en GitHub. A diferencia de use_max_release, esta opción incluye etiquetas anotadas y ligeras, y devuelve la mayor ordenada por la opción sort_version_key. Devolverá el nombre de la etiqueta en lugar de la fecha.
token
Un token de autorización personal utilizado para llamar a la API.

Se puede necesitar un token de autorización para usar use_latest_tag, include_prereleases o para solicitar con más frecuencia que de forma anónima.

Para establecer un token de autorización, puedes establecer:

  • la opción token
  • una entrada en el archivo de claves para el host (por ejemplo, github.com)
  • una entrada en tu archivo netrc para el host

Esta fuente admite Opciones de Lista cuando se establece use_max_tag o use_max_release.

NAME

nvchecker - check package updates

SYNOPSIS

nvchecker [-c version_record_files] [-m config] [-s source] [-p package ...]
nvchecker [-h | -v]

DESCRIPTION

nvchecker is a tool to check for new package versions. It supports various sources like PyPI, CRAN, GitHub, etc., and can check your local package databases (like pacman(8), dpkg-query(1), etc.).

It is intended to be used in PKGBUILD(5) files, but can be used standalone as well.

OPTIONS

-c version_record_files
Specifies the version record files. If not specified, nvchecker looks for a file named version_record_files in the current directory. nvchecker checks packages in these files.
-m config
Specifies a configuration file. Defaults to configuration files. See configuration files below.
-s source
Specifies the source to check. If not specified, nvchecker uses sources defined in the configuration file or version record files. This option can be specified multiple times.
-p package
Specifies the package to check. If not specified, nvchecker checks all packages defined in the configuration file or version record files. This option can be specified multiple times.
-h
Show help message and exit.
-v
Show version information and exit.

DEPENDENCY

For some sources, additional Python packages might be required. The following table lists the dependencies:

Comando de extracción registry container
docker pull quay.io/prometheus/node-exporter quay.io prometheus/node-exporter
docker pull quay.io/prometheus/node-exporter:master quay.io prometheus/node-exporter:master
Source Package Dependency
docker docker.io openeuler/openeuler
docker pull openeuler/openeuler:20.03-lts docker.io openeuler/openeuler:20.03-lts
docker pull python docker.io library/python
docker pull python:3.11 docker.io library/python:3.11

INSTALL AND RUN

nvchecker is packaged for Arch Linux as extra/nvchecker.

You can install it using pacman:

sudo pacman -S nvchecker

After installation, you can run nvchecker from your project directory. It will automatically look for a version_record_files file (usually named PKGBUILD or _srcinfo).

Alternatively, you can specify the version record file(s) using the -c option:

nvchecker -c /path/to/version_record_file

To check specific packages, use the -p option:

nvchecker -c /path/to/version_record_file -p package1 -p package2

VERSION RECORD FILES

nvchecker can read version information from various files. The most common ones are:

  • PKGBUILD: This is the standard build script for Arch Linux packages. nvchecker will parse the pkgver= and source= arrays to determine the package name and version.
  • _srcinfo: This file is generated by makepkg --printsrcinfo and contains metadata about the package, including the version.
  • Custom files: You can specify any file containing package names and their current versions in a format like: 
    package_name version
    or using a TOML format for more complex configurations.

When checking sources like PyPI, CRAN, or GitHub, nvchecker will fetch the latest version from the respective service and compare it with the version specified in the version record file.

CONFIGURATION FILES

nvchecker uses configuration files to specify sources, filters, and other settings. These files are typically written in TOML format.

By default, nvchecker looks for configuration files in the following locations, in order:

  • ~/.config/nvchecker/nvchecker.toml
  • /etc/nvchecker/nvchecker.toml

You can specify a custom configuration file using the -m option.

A basic configuration file might look like this:

[sources.pypi]
source = "pypi"
name = "requests"

[sources.github]
source = "github"
user = "gitpython"
repo = "gitpython"

This configuration defines two sources: one for the PyPI package 'requests' and another for the GitHub repository 'gitpython/gitpython'. When nvchecker runs, it will check for updates from these sources.

List Options

Some sources support list options, which allow you to retrieve a list of available versions or tags instead of just the latest one. This is useful for tracking specific branches or historical versions.

The following sources support list options:

  • pypi
  • github
  • gitlab
  • docker
  • opam

When list options are enabled, nvchecker will output all found versions or tags, and you can then filter or process them as needed.

Extending nvchecker

nvchecker is designed to be extensible. You can create custom plugins to support new version sources or add custom logic. Refer to the plugin documentation for details on how to write and use plugins.

EXAMPLES

Check the latest version of the 'requests' package from PyPI:

nvchecker --sources pypi --packages requests

Check for updates in a local PKGBUILD file:

nvchecker -c PKGBUILD

Check for updates from GitHub and PyPI using a configuration file:

nvchecker -m nvchecker.toml
