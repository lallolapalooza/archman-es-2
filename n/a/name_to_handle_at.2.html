NOMBRE

name_to_handle_at, open_by_handle_at - obtener un manejador para una ruta y abrir un archivo a través de un manejador

BIBLIOTECA

Biblioteca C estándar (libc, -lc)

SINOPSIS

#define _GNU_SOURCE         /* Ver feature_test_macros(7) */
#include <fcntl.h>
int name_to_handle_at(int dirfd, const char *path,
                      struct file_handle *handle,
                      int *mount_id, int flags);
int open_by_handle_at(int mount_fd, struct file_handle *handle,
                      int flags);

DESCRIPCIÓN

Las llamadas al sistema name_to_handle_at() y open_by_handle_at() dividen la funcionalidad de openat(2) en dos partes: name_to_handle_at() devuelve un manejador opaco que corresponde a un archivo especificado; open_by_handle_at() abre el archivo correspondiente a un manejador devuelto por una llamada anterior a name_to_handle_at() y devuelve un descriptor de archivo abierto.

name_to_handle_at()

La llamada al sistema name_to_handle_at() devuelve un manejador de archivo y un ID de montaje que corresponden al archivo especificado por los argumentos dirfd y path. El manejador de archivo se devuelve a través del argumento handle, que es un puntero a una estructura del siguiente formato:


struct file_handle {
    unsigned int  handle_bytes;   /* Tamaño de f_handle [entrada, salida] */
    int           handle_type;    /* Tipo de manejador [salida] */
    unsigned char f_handle[0];    /* Identificador del archivo (tamaño
                                     definido por el llamador) [salida] */
};

Es responsabilidad del llamador asignar la estructura con un tamaño lo suficientemente grande como para contener el manejador devuelto en f_handle. Antes de la llamada, el campo handle_bytes debe inicializarse para contener el tamaño asignado para f_handle. (La constante MAX_HANDLE_SZ, definida en <fcntl.h>, especifica el tamaño máximo esperado para un manejador de archivo. No es un límite superior garantizado ya que los sistemas de archivos futuros pueden requerir más espacio.) Tras una devolución exitosa, el campo handle_bytes se actualiza para contener el número de bytes realmente escritos en f_handle.

El llamador puede descubrir el tamaño requerido para la estructura file_handle realizando una llamada en la que handle->handle_bytes sea cero; en este caso, la llamada falla con el error EOVERFLOW y handle->handle_bytes se establece para indicar el tamaño requerido; el llamador puede entonces usar esta información para asignar una estructura del tamaño correcto (ver EJEMPLOS más abajo). Se requiere cierto cuidado aquí ya que EOVERFLOW también puede indicar que no hay un manejador de archivo disponible para este nombre en particular en un sistema de archivos que normalmente admite la búsqueda de manejadores de archivo. Este caso se puede detectar cuando el error EOVERFLOW se devuelve sin que handle_bytes se incremente.

Aparte del uso del campo handle_bytes, el llamador debe tratar la estructura file_handle como un tipo de dato opaco: los campos handle_type y f_handle se pueden usar en una llamada posterior a open_by_handle_at(). El llamador también puede usar el file_handle opaco para comparar la identidad de objetos del sistema de archivos que se consultaron en diferentes momentos y posiblemente en diferentes rutas. El subsistema fanotify(7) puede notificar eventos con un registro de información que contiene un file_handle para identificar el objeto del sistema de archivos.

El argumento flags es una máscara de bits construida combinando con OR cero o más de AT_HANDLE_FID, AT_HANDLE_MNT_ID_UNIQUE, AT_HANDLE_CONNECTABLE, AT_EMPTY_PATH y AT_SYMLINK_FOLLOW, descritos a continuación.

Cuando flags contiene el flag AT_HANDLE_FID (desde Linux 6.5), el llamador indica que el file_handle devuelto se necesita para identificar el objeto del sistema de archivos, y no para abrir el archivo más tarde, por lo que se debe esperar que una llamada posterior a open_by_handle_at() con el file_handle devuelto pueda fallar.

Cuando flags contiene el flag AT_HANDLE_MNT_ID_UNIQUE (desde Linux 6.12), el llamador indica que el ancho del búfer mount_id es al menos de 64 bits, y entonces el ID de montaje devuelto en ese búfer es el ID de montaje único como el devuelto por statx(2) con el flag STATX_MNT_ID_UNIQUE.

Cuando flags contiene el flag AT_HANDLE_CONNECTABLE (desde Linux 6.13), el llamador indica que el file_handle devuelto se necesita para abrir un archivo con una ruta conocida más tarde, por lo que se debe esperar que una llamada posterior a open_by_handle_at() con el file_handle devuelto pueda fallar si el archivo fue movido, pero de lo contrario, se espera que la ruta del archivo abierto sea visible desde el enlace mágico /proc/pid/fd/*. Este flag no se puede usar en combinación con los flags AT_HANDLE_FID y/o AT_EMPTY_PATH.

Juntos, los argumentos path y dirfd identifican el archivo para el cual se debe obtener un manejador. Hay cuatro casos distintos:

•
Si path es una cadena no vacía que contiene una ruta absoluta, entonces se devuelve un manejador para el archivo al que se refiere esa ruta. En este caso, dirfd se ignora.
•
Si path es una cadena no vacía que contiene una ruta relativa y dirfd tiene el valor especial AT_FDCWD, entonces path se interpreta en relación con el directorio de trabajo actual del llamador, y se devuelve un manejador para el archivo al que se refiere.
•
Si path es una cadena no vacía que contiene una ruta relativa y dirfd es un descriptor de archivo que se refiere a un directorio, entonces path se interpreta en relación con el directorio al que se refiere dirfd, y se devuelve un manejador para el archivo al que se refiere. (Ver openat(2) para una explicación de por qué los "descriptores de archivo de directorio" son útiles).
•
Si path es una cadena vacía y flags especifica el valor AT_EMPTY_PATH, entonces dirfd puede ser un descriptor de archivo abierto que se refiere a cualquier tipo de archivo, o AT_FDCWD, que significa el directorio de trabajo actual, y se devuelve un manejador para el archivo al que se refiere.

El argumento mount_id devuelve un identificador para el montaje del sistema de archivos que corresponde a path. Esto corresponde al primer campo en uno de los registros en /proc/self/mountinfo. Abrir la ruta en el quinto campo de ese registro devuelve un descriptor de archivo para el punto de montaje; ese descriptor de archivo se puede usar en una llamada posterior a open_by_handle_at(). mount_id se devuelve tanto para una llamada exitosa como para una llamada que resulta en el error EOVERFLOW.

Por defecto, name_to_handle_at() no desreferencia path si es un enlace simbólico, y por lo tanto devuelve un manejador para el propio enlace. Si se especifica AT_SYMLINK_FOLLOW en flags, path se desreferencia si es un enlace simbólico (para que la llamada devuelva un manejador para el archivo al que se refiere el enlace).

name_to_handle_at() no activa un montaje cuando el último componente de la ruta es un punto de montaje automático. Cuando un sistema de archivos admite manejadores de archivo y puntos de montaje automáticos, una llamada a name_to_handle_at() en un punto de montaje automático devolverá el error EOVERFLOW sin haber incrementado handle_bytes. Esto puede suceder desde Linux 4.13 con NFS al acceder a un directorio que está en un sistema de archivos separado en el servidor. En este caso, el montaje automático se puede activar añadiendo una "/" al final de la ruta.

La llamada al sistema open_by_handle_at() abre el archivo referido por handle, un manejador de archivo devuelto por una llamada anterior a name_to_handle_at().

NAME

name_to_handle_at, open_by_handle_at - obtain a file handle and open a file by file handle

SYNOPSIS

cc name_to_handle_at.c -o name_to_handle_at
cc open_by_handle_at.c -o open_by_handle_at

int name_to_handle_at(int dirfd, const char *path, struct file_handle *handle, int *mount_id, int flags); int open_by_handle_at(int mount_fd, struct file_handle *handle, int flags);
DESCRIPTION

The name_to_handle_at() system call is used to obtain a file handle for the file specified by path. The file handle is returned in the buffer pointed to by handle. The mount ID of the filesystem on which the file resides is returned in the integer pointed to by mount_id.

The dirfd argument is a file descriptor that specifies a directory. path is a pathname relative to the directory specified by dirfd, or an absolute pathname if dirfd is AT_FDCWD (the current working directory).

The handle argument is a pointer to a struct file_handle, which must be initialized before the call. The structure has the following definition:

typedef struct file_handle { unsigned int handle_bytes; const unsigned char data[0]; } file_handle_t;

Before the first call to name_to_handle_at(), the caller should allocate a buffer for handle that is large enough to hold the struct file_handle structure itself, and set handle->handle_bytes to 0. If the call fails with the error EOVERFLOW, then the caller should reallocate the buffer for handle to be sizeof(struct file_handle) + handle->handle_bytes, and then retry the call. On a successful return, the buffer will contain the file handle, and handle->handle_bytes will be set to the actual size of the file handle data.

The flags argument specifies how the handle is obtained. The currently defined flags are:

AT_HANDLE_FID
Obtain a file handle that is guaranteed to be unique across all mounted filesystems.
AT_HANDLE_MOUNTED_DIR
The pathname refers to a mount point directory.
AT_SYMLINK_NOFOLLOW
If path refers to a symbolic link, then return a handle for the link itself rather than the file it refers to. This is the default behavior when AT_SYMLINK_FOLLOW is not specified.
AT_SYMLINK_FOLLOW
If path refers to a symbolic link, then return a handle for the file pointed to by the link, rather than for the link itself. This flag is ignored if path does not refer to a symbolic link.

The open_by_handle_at() system call is used to open a file using a file handle previously obtained using name_to_handle_at().

The mount_fd argument is a file descriptor for a directory that was mounted. This is used to specify which mount point the file handle belongs to. This file descriptor should have been obtained by opening the mount point directory and should not be a relative path. This file descriptor can be obtained by scanning /proc/self/mountinfo to find a mount point whose mount ID matches the mount_id obtained from name_to_handle_at(), and then opening that mount point directory.

The handle argument is a pointer to a struct file_handle containing the file handle previously obtained using name_to_handle_at().

The flags argument specifies how the file should be opened. These flags are the same as for the openat(2) system call, with the addition of the following flags:

O_PATH
Obtain a file descriptor that can be used in subsequent system calls (like fstat(2), read(2), etc.) but does not allow access to the file's data. This is useful for operating on symbolic links, for example.

Note that when using open_by_handle_at(), the symbolic link handling is determined by the flags argument passed to name_to_handle_at() when the handle was created, and not by the flags passed to open_by_handle_at(). If the handle refers to a symbolic link and O_PATH is not specified in the flags argument to open_by_handle_at(), then the symbolic link is not dereferenced; the O_NOFOLLOW flag, if specified, is ignored.

The caller must have the CAP_DAC_READ_SEARCH capability to invoke open_by_handle_at().

RETURN VALUE

On success, name_to_handle_at() returns 0, and open_by_handle_at() returns a file descriptor (a nonnegative integer).

In the event of an error, both system calls return -1 and set errno to indicate the error.

ERRORS

name_to_handle_at() and open_by_handle_at() can fail for the same errors as openat(2). In addition, they can fail with the errors noted below.

name_to_handle_at() can fail with the following errors:

EFAULT
path, mount_id, or handle points outside your accessible address space.
EINVAL
flags includes an invalid bit value or an invalid bit combination.
EINVAL
handle->handle_bytes is greater than MAX_HANDLE_SZ.
ENOENT
path is an empty string, but AT_EMPTY_PATH was not specified in flags.
ENOTDIR
The file descriptor supplied in dirfd does not refer to a directory, and it is not the case that both flags includes AT_EMPTY_PATH and path is an empty string.
EOPNOTSUPP
The filesystem does not support decoding of a pathname to a file handle.
EOVERFLOW
The handle->handle_bytes value passed into the call was too small. When this error occurs, handle->handle_bytes is updated to indicate the required size for the handle.

open_by_handle_at() can fail with the following errors:

EBADF
mount_fd is not an open file descriptor.
EBADF
path is relative but dirfd is neither AT_FDCWD nor a valid file descriptor.
EFAULT
handle points outside your accessible address space.
EINVAL
handle->handle_bytes is greater than MAX_HANDLE_SZ or is equal to zero.
ELOOP
handle refers to a symbolic link, but O_PATH was not specified in flags.
EPERM
The caller does not have the CAP_DAC_READ_SEARCH capability.
ESTALE
The specified handle is not valid for opening a file. This error will occur if, for example, the file has been deleted. This error can also occur if the handle was acquired using the AT_HANDLE_FID flag and the filesystem does not support open_by_handle_at(). This error can also occur if the handle was acquired using the AT_HANDLE_CONNECTABLE flag and the file was moved to a different parent.
VERSIONS

FreeBSD has a broadly similar pair of system calls in the form of getfh() and fhopen().

STANDARDS

Linux.

HISTORY

Linux 2.6.39, glibc 2.14.

NOTES

A file handle can be generated in one process using name_to_handle_at() and later used in a different process that calls open_by_handle_at().

Some filesystem don't support the translation of pathnames to file handles, for example, /proc, /sys, and various network filesystems. Some filesystems support the translation of pathnames to file handles, but do not support using those file handles in open_by_handle_at().

A file handle may become invalid ("stale") if a file is deleted, or for other filesystem-specific reasons. Invalid handles are notified by an ESTALE error from open_by_handle_at().

These system calls are designed for use by user-space file servers. For example, a user-space NFS server might generate a file handle and pass it to an NFS client. Later, when the client wants to open the file, it could pass the handle back to the server. This sort of functionality allows a user-space file server to operate in a stateless fashion with respect to the files it serves.

If path refers to a symbolic link and flags does not specify AT_SYMLINK_FOLLOW, then name_to_handle_at() returns a handle for the link (rather than the file to which it refers). The process receiving the handle can later perform operations on the symbolic link by converting the handle to a file descriptor using open_by_handle_at() with the O_PATH flag, and then passing the file descriptor as the dirfd argument in system calls such as readlinkat(2) and fchownat(2).

Obtaining a persistent filesystem ID

The mount IDs in /proc/self/mountinfo can be reused as filesystems are unmounted and mounted. Therefore, the mount ID returned by name_to_handle_at() (in *mount_id) should not be treated as a persistent identifier for the corresponding mounted filesystem. However, an application can use the information in the mountinfo record that corresponds to the mount ID to derive a persistent identifier.

For example, one can use the device name in the fifth field of the mountinfo record to search for the corresponding device UUID via the symbolic links in /dev/disks/by-uuid. (A more comfortable way of obtaining the UUID is to use the libblkid(3) library.) That process can then be reversed, using the UUID to look up the device name, and then obtaining the corresponding mount point, in order to produce the mount_fd argument used by open_by_handle_at().

EXAMPLES

The two programs below demonstrate the use of name_to_handle_at() and open_by_handle_at(). The first program (t_name_to_handle_at.c) uses name_to_handle_at() to obtain the file handle and mount ID for the file specified in its command-line argument; the handle and mount ID are written to standard output.

The second program (t_open_by_handle_at.c) reads a mount ID and file handle from standard input. The program then employs open_by_handle_at() to open the file using that handle. If an optional command-line argument is supplied, then the mount_fd argument for open_by_handle_at() is obtained by opening the directory named in that argument. Otherwise, mount_fd is obtained by scanning /proc/self/mountinfo to find a record whose mount ID matches the mount ID read from standard input, and the mount directory specified in that record is opened. (These programs do not deal with the fact that mount IDs are not persistent.)

NAME

name_to_handle_at - obtener un manejador de archivo para un nombre de archivo

LIBRARY

Se proporciona por la biblioteca de libc, basada en la versión de Glibc 2.29.

SYNOPSIS

#include <sys/types.h>
#include <sys/stat.h>
#include <fcntl.h>

int name_to_handle_at(int dirfd, const char *pathname,
                      struct file_handle *handle,
                      int *ந்தார், int flags);

DESCRIPTION

La función name_to_handle_at, junto con open_by_handle_at(2), permite obtener un manejador para un archivo y luego abrir dicho archivo usando ese manejador. Esto es útil para implementar sistemas de archivos distribuidos y para escenarios donde un archivo necesita ser referenciado sin ser abierto.

El argumento dirfd es un descriptor de archivo que especifica un directorio. El argumento pathname es una ruta a un archivo relativa a dirfd, o una ruta absoluta si dirfd es AT_FDCWD (la ruta se resuelve con respecto al directorio de trabajo actual).

El argumento handle apunta a una estructura file_handle. La estructura file_handle está definida en <fcntl.h> como:

struct file_handle {
    unsigned int   handle_bytes;
    unsigned int   handle_type;
    unsigned char  f_handle[1];  /* Datos del manejador */
};

La llamada name_to_handle_at llena la estructura file_handle apuntada por handle con la información del manejador del archivo especificado por pathname. El campo handle_bytes indica el tamaño en bytes de los datos del manejador que siguen. El campo handle_type identifica el tipo de manejador. La matriz f_handle contiene los datos reales del manejador. El tamaño de esta matriz es variable y debe ser al menos handle_bytes.

El argumento ந்தார் apunta a un entero que recibirá el tamaño de la estructura file_handle completada. El tamaño incluye los campos fijos más los datos del manejador (handle_bytes).

El argumento flags puede ser 0 o AT_HANDLE_FID.

AT_HANDLE_FID
Si se especifica este flag, el sistema de archivos debe devolver un manejador que sea un file identifier (FID) de NFSv4. Los FIDs son manejadores que no cambian durante la vida útil del archivo y son independientes del punto de montaje.

Al igual que con otras operaciones que toman un descriptor de archivo dirfd y una ruta, pathname puede ser una ruta relativa o absoluta. Si pathname es una ruta absoluta, dirfd se ignora.

Los sistemas de archivos que no soportan la operación name_to_handle_at devolverán un error ENOSYS.

RETURN VALUE

En caso de éxito, name_to_handle_at devuelve 0. En caso de error, devuelve -1 y errno se establece para indicar el error.

ERRORS

Los siguientes son algunos de los errores posibles que name_to_handle_at puede encontrar:

EBADF
dirfd no es un descriptor de archivo válido.
EACCES
No se permite el acceso de búsqueda (X_OK) para el directorio que contiene pathname, o no se permite el acceso de lectura (R_OK) para el archivo.
EFAULT
pathname o handle apuntan a memoria no válida.
EACCES
No se permite el acceso de búsqueda (X_OK) para el directorio que contiene pathname, o no se permite el acceso de lectura (R_OK) para el archivo.
ELOOP
Se encontraron demasiados enlaces simbólicos al resolver pathname.
ENAMETOOLONG
pathname es demasiado largo.
ENOENT
No se encontró un componente de pathname o el propio pathname.
ENOMEM
No hay suficiente memoria disponible para llenar la estructura file_handle.
ENOSYS
El sistema de archivos subyacente no soporta la operación name_to_handle_at.
ENOTDIR
dirfd apunta a un archivo que no es un directorio, o un componente de pathname que no es un directorio (y no es el último componente).
EROFS
El sistema de archivos es de solo lectura y la operación requiere escritura (por ejemplo, para obtener un FID de NFSv4 que podría requerir una consulta al servidor).
ETXTBSY
El archivo es un archivo ejecutable que está abierto para escritura.

VERSIONS

La función name_to_handle_at se introdujo en el kernel de Linux 5.1.

STANDARDS

Esta llamada al sistema es específica de Linux.

HISTORY

La operación name_to_handle_at se agregó al kernel de Linux en la versión 5.1.

NOTES

Para usar name_to_handle_at, la aplicación debe compilarse con _GNU_SOURCE para obtener la definición de AT_HANDLE_FID.

La capacidad de usar name_to_handle_at y open_by_handle_at(2) depende de la implementación del sistema de archivos. Por ejemplo, los sistemas de archivos como Btrfs, ext4 y XFS soportan esta funcionalidad, mientras que los sistemas de archivos de red como NFS (sin configuración específica) pueden no hacerlo o pueden tener limitaciones (por ejemplo, los FIDs de NFSv4 no son portátiles entre diferentes servidores NFS).

El manejo de la estructura file_handle requiere cuidado. El tamaño total de la estructura puede variar, y la memoria para f_handle debe asignarse adecuadamente antes de llamar a name_to_handle_at.

       Primero, necesitamos obtener el tamaño real asignado para el manejador.
       La forma más segura es llamar a name_to_handle_at con handle = NULL
       y obtener el tamaño en el cuarto argumento. Sin embargo, esto no está
       documentado y puede no funcionar en todas las versiones del kernel.
       Un enfoque más común es asignar un tamaño inicial y expandirlo si es necesario.
       Aquí, asumimos un tamaño inicial razonable y lo manejamos si es insuficiente.
    */

    /* Inicialmente, intentamos obtener el tipo y el tamaño del manejador. */
    alloc_size = sizeof(struct file_handle) + 128; /* Tamaño inicial arbitrario */
    fhp = malloc(alloc_size);
    if (fhp == NULL)
        err(EXIT_FAILURE, "malloc");

    /* Llamar a name_to_handle_at para obtener el manejador. */
    /* Inicialmente, podemos usar un tamaño de búfer arbitrario y luego ajustarlo. */
    ret = name_to_handle_at(mount_fd, argv[2], fhp, &handle_bytes, 0);
    if (ret == -1) {
        /* Si el error es ENOMEM, significa que necesitamos un búfer más grande. */
        if (errno == ENOMEM) {
            free(fhp);
            /* El valor en handle_bytes es el tamaño necesario. */
            alloc_size = handle_bytes;
            fhp = malloc(alloc_size);
            if (fhp == NULL)
                err(EXIT_FAILURE, "malloc");
            ret = name_to_handle_at(mount_fd, argv[2], fhp, &handle_bytes, 0);
            if (ret == -1)
                err(EXIT_FAILURE, "name_to_handle_at (second attempt)");
        } else {
            err(EXIT_FAILURE, "name_to_handle_at");
        }
    }

    /* Si name_to_handle_at tuvo éxito, handle_bytes ahora contiene el tamaño total de la estructura file_handle. */
    printf("Handle obtained successfully.\n");
    printf("Handle bytes: %u\n", fhp->handle_bytes);
    printf("Handle type: %u\n", fhp->handle_type);
    printf("Handle data: ");
    for (size_t j = 0; j < fhp->handle_bytes; j++)
        printf("%02x ", fhp->f_handle[j]);
    printf("\n");

    /* Ahora, usamos el manejador para abrir el archivo. */
    fd = open_by_handle_at(mount_fd, fhp, O_RDONLY);
    if (fd == -1)
        err(EXIT_FAILURE, "open_by_handle_at");

    printf("File opened successfully using handle.\n");

    /* Intentar leer algunos bytes del archivo. */
    nread = read(fd, buf, sizeof(buf) - 1);
    if (nread == -1)
        err(EXIT_FAILURE, "read");
    buf[nread] = '\0'; /* Null-terminate para imprimir como cadena */
    printf("Read %zd bytes: %s\n", nread, buf);

    /* Limpieza */
    close(fd);
    close(mount_fd);
    free(fhp);

    exit(EXIT_SUCCESS);
}
