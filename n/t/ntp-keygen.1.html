ntp-keygen(1) Comandos de Usuario ntp-keygen(1)

NOMBRE

ntp-keygen - Crear una clave de host NTP

SINOPSIS

ntp-keygen [-flags] [-flag [valor]] [--nombre-de-opcion[[=| ]valor]]

Todos los argumentos deben ser opciones.

DESCRIPCIÓN

Este programa genera archivos de datos criptográficos utilizados por los esquemas de autenticación e identificación de NTPv4. Puede generar claves de resumen de mensajes utilizadas en criptografía de clave simétrica y, si se ha instalado la biblioteca de software OpenSSL, puede generar claves de host, claves de firma, certificados y claves de identidad y parámetros utilizados en la criptografía de clave pública Autokey. Estos archivos se utilizan para el cifrado de cookies, la firma digital y los algoritmos de identificación de desafío/respuesta compatibles con la infraestructura de seguridad estándar de Internet.

El archivo de claves simétricas de resumen de mensajes se genera en un formato compatible con NTPv3. Todos los demás archivos están en formato ASCII imprimible codificado en PEM, por lo que pueden incrustarse como archivos adjuntos MIME en correos electrónicos a otros sitios y autoridades certificadoras. De forma predeterminada, los archivos no están cifrados.

Cuando se utiliza para generar claves simétricas de resumen de mensajes, el programa produce un archivo que contiene diez cadenas ASCII imprimibles pseudoaleatorias adecuadas para el algoritmo de resumen de mensajes MD5 incluido en la distribución. Si la biblioteca OpenSSL está instalada, produce diez cadenas de bits aleatorias adicionales codificadas en hexadecimal adecuadas para SHA1, AES-128-CMAC y otros algoritmos de resumen de mensajes. El archivo de claves simétricas de resumen de mensajes debe ser distribuido y almacenado utilizando medios seguros más allá del alcance del propio NTP. Además de las claves utilizadas para asociaciones NTP ordinarias, se pueden definir claves adicionales como contraseñas para las utilidades ntpq(1) y ntpdc(1).

Los archivos generados restantes son compatibles con otras aplicaciones OpenSSL y otros recursos de Infraestructura de Clave Pública (PKI). Los certificados generados por este programa son compatibles con la práctica industrial existente, aunque algunos usuarios pueden encontrar un tanto liberal la interpretación de los campos de extensión X509v3. Sin embargo, las claves de identidad probablemente no sean compatibles con nada más que Autokey.

Algunos archivos utilizados por este programa se cifran utilizando una contraseña privada. La opción -p especifica la contraseña de lectura para archivos locales cifrados y la opción -q la contraseña de escritura para archivos cifrados enviados a sitios remotos. Si no se especifica ninguna contraseña, se utiliza el nombre de host devuelto por el comando Unix hostname(1), normalmente el nombre DNS del host, como la contraseña de lectura predeterminada, por conveniencia. El programa ntp-keygen solicita la contraseña si lee un archivo cifrado y la contraseña falta o es incorrecta. Si se lee un archivo cifrado correctamente y no se especifica contraseña de escritura, se utiliza la contraseña de lectura como contraseña de escritura de forma predeterminada.

La opción pw del comando de configuración de ntpd(1) crypto especifica la contraseña de lectura para archivos locales previamente cifrados. Esta debe coincidir con la contraseña de lectura local utilizada por este programa. Si no se especifica, se utiliza el nombre del host. Por lo tanto, si los archivos son generados por este programa sin una contraseña explícita, pueden ser leídos nuevamente por ntpd(1) sin especificar una contraseña explícita pero solo en el mismo host. Si la contraseña de escritura utilizada para el cifrado se especifica como el nombre del host, estos archivos pueden ser leídos por ese host sin contraseña explícita.

Normalmente, los archivos cifrados para cada host son generados por ese host y utilizados solo por ese host, aunque existen excepciones como se indica más adelante en esta página. El archivo de claves simétricas, normalmente llamado ntp.keys, se instala habitualmente en /etc. Otros archivos y enlaces se instalan habitualmente en /usr/local/etc, que normalmente se encuentra en un sistema de archivos compartido en redes montadas por NFS y no puede ser modificado por clientes compartidos. En estos casos, los clientes NFS pueden especificar los archivos en otro directorio como /etc utilizando el comando de configuración keysdir de ntpd(1).

Este programa dirige los comentarios y los mensajes de error al flujo de error estándar stderr y los archivos remotos a la salida estándar stdout, donde pueden ser canalizados a otras aplicaciones o redirigidos a archivos. Los nombres utilizados para los archivos y enlaces generados comienzan todos con la cadena ntpkey* e incluyen el tipo de archivo, el host generador y la marca de tiempo del archivo, como se describe en la sección Archivos de Datos Criptográficos más abajo.

Ejecución del Programa

La forma más segura de ejecutar el programa ntp-keygen es iniciar sesión directamente como root. El procedimiento recomendado es cambiarse al directorio keys, normalmente /usr/local/etc, y luego ejecutar el programa.

Para probar y adquirir experiencia con los conceptos de Autokey, inicie sesión como root y cámbiese al directorio keys, normalmente /usr/local/etc. Cuando se ejecute por primera vez, o si todos los archivos con nombres que comiencen con ntpkey* han sido eliminados, use el comando ntp-keygen sin argumentos para generar una clave de host RSA predeterminada y un archivo de certificado RSA-MD5 a juego con una fecha de vencimiento de un año a partir de ahora, que es todo lo necesario en muchos casos. El programa también genera enlaces simbólicos desde los nombres genéricos a los archivos respectivos. Si se ejecuta de nuevo sin opciones, el programa utiliza las claves y parámetros existentes y genera un nuevo archivo de certificado con una nueva fecha de vencimiento de un año a partir de ahora, y un enlace simbólico.

La clave de host se utiliza para cifrar la cookie cuando sea necesario y, por lo tanto, debe ser de tipo RSA. De forma predeterminada, la clave de host también es la clave de firma utilizada para cifrar firmas. Cuando sea necesario, se puede especificar una clave de firma diferente, que puede ser de tipo RSA o DSA. De forma predeterminada, el tipo de resumen de mensajes es MD5, pero se puede especificar cualquier combinación de tipo de clave de firma y tipo de resumen de mensajes compatible con la biblioteca OpenSSL, incluidos los que utilizan los algoritmos de resumen de mensajes AES128CMAC, MD2, MD5, MDC2, SHA, SHA1 y RIPE160. Sin embargo, el esquema especificado en el certificado debe ser compatible con la clave de firma. Los certificados que utilizan cualquier algoritmo de resumen son compatibles con las claves de firma RSA; sin embargo, solo los certificados SHA y SHA1 son compatibles con las claves de firma DSA.

Los archivos de clave privada/pública y los certificados son compatibles con otras aplicaciones OpenSSL y muy probablemente con otras bibliotecas también. Los certificados o las solicitudes de certificados derivados de ellos deberían ser compatibles con la práctica industrial existente, aunque algunos usuarios pueden encontrar un tanto liberal la interpretación de los campos de extensión X509v3. Sin embargo, los archivos de parámetros de identificación, aunque codificados como los otros archivos, probablemente no sean compatibles con nada más que Autokey.

Ejecutar el programa como otro que no sea root y usar el comando Unix su(1) para asumir el rol de root puede no funcionar correctamente, ya que de forma predeterminada la biblioteca OpenSSL busca el archivo de semilla aleatoria .rnd en el directorio principal del usuario. Sin embargo, solo debe haber un .rnd, lo más conveniente es en el directorio raíz, por lo que es conveniente definir la variable de entorno RANDFILE utilizada por la biblioteca OpenSSL como la ruta a .rnd.

Instalar las claves como root puede no funcionar en sistemas de archivos compartidos montados por NFS, ya que los clientes NFS pueden no poder escribir en el directorio de claves compartido, incluso como root. En este caso, los clientes NFS pueden especificar los archivos en otro directorio como /etc utilizando el comando de configuración keysdir de ntpd(1). No es necesario que un cliente lea las claves y certificados de otros clientes o servidores, ya que estos datos se obtienen automáticamente mediante el protocolo Autokey.

Normalmente, los archivos criptográficos son generados por el host que los utiliza, pero es posible que un agente de confianza (TA) genere estos archivos para otros hosts; sin embargo, en tales casos, los archivos siempre deben estar cifrados. El nombre del sujeto y el nombre de confianza predeterminados son el nombre de host del host que genera los archivos, pero se pueden cambiar mediante opciones de línea de comandos. Es conveniente designar el nombre del propietario y el nombre de confianza como los campos de sujeto y emisor, respectivamente, del certificado. El nombre del propietario también se utiliza para los archivos de host y clave de firma, mientras que el nombre de confianza se utiliza para los archivos de identidad.

Todos los archivos se instalan de forma predeterminada en el directorio de claves /usr/local/etc, que normalmente se encuentra en un sistema de archivos compartido en redes montadas por NFS. La ubicación real del directorio de claves y de cada archivo se puede anular mediante la configuración co

Normalmente, los archivos que contienen valores privados, incluida la clave del host, la clave de firma y los parámetros de identificación, se permiten solo para lectura/escritura de root; mientras que otros que contienen valores públicos se permiten para lectura general. Alternativamente, los archivos que contienen valores privados pueden cifrarse y estos archivos se pueden permitir para lectura general, lo que simplifica el mantenimiento en sistemas de archivos compartidos. Dado que la unicidad está garantizada por las extensiones de nombre de archivo *hostname* y *filestamp*, los archivos para un servidor NTP y sus clientes dependientes pueden instalarse todos en el mismo directorio compartido.

La práctica recomendada es mantener las extensiones de nombre de archivo al instalar un archivo e instalar un enlace simbólico de los nombres genéricos especificados en otros lugares de esta página a los archivos generados. Esto permite activar nuevas generaciones de archivos simplemente cambiando el enlace. Si hay un enlace, ntpd(1) lo sigue hasta el nombre del archivo para extraer la *filestamp*. Si no hay un enlace, ntpd(1) extrae la *filestamp* del archivo mismo. Esto permite a los clientes verificar que los tiempos de archivo y generación siempre estén actualizados. El programa **ntp-keygen** utiliza la misma extensión *filestamp* para todos los archivos generados a la vez, por lo que cada generación es distinta y se puede reconocer fácilmente en los datos de monitorización.

Ejecute el comando en tantos hosts como sea necesario. Designe uno de ellos como host de confianza (TH) utilizando **ntp-keygen** con la opción **-T** y configúrelo para sincronizarse con servidores de Internet fiables. Luego, configure los otros hosts para que se sincronicen directamente o indirectamente con el TH. Se crea una cadena de certificados cuando Autokey le pide al host inmediatamente superior hacia el TH que firme su certificado, el cual se proporciona luego al host inmediatamente inferior bajo petición. Todos los hosts del grupo deben tener cadenas de certificados acíclicas que terminen en el TH.

La clave del host se utiliza para cifrar la cookie cuando sea necesario y, por lo tanto, debe ser de tipo RSA. Por defecto, la clave del host también es la clave de firma utilizada para cifrar las firmas. Se puede asignar una clave de firma diferente utilizando la opción **-S** y esta puede ser de tipo **RSA** o **DSA**. Por defecto, el tipo de resumen de mensajes de la firma es **MD5**, pero se puede especificar cualquier combinación de tipo de clave de firma y tipo de resumen de mensajes compatible con la biblioteca OpenSSL utilizando la opción **-c**.

Las reglas dicen que los medios criptográficos deben generarse con marcas de tiempo provistas, lo que significa que el host ya debería estar sincronizado antes de que se ejecute este programa. Esto, por supuesto, crea un problema de "huevo o gallina" cuando el host se inicia por primera vez. En consecuencia, la hora del host debe establecerse por algún otro medio, como a ojo y con un reloj de pulsera, al menos para que la vida útil del certificado esté dentro del año actual. Después de eso y cuando el host esté sincronizado con una fuente provista, el certificado debe regenerarse.

Información adicional sobre grupos de confianza y esquemas de identidad se encuentra en la página "Autokey Public-Key Authentication".

Los nombres de archivo comienzan con el prefijo *ntpkey*_ y terminan con el sufijo *_hostname*.*filestamp*, donde *hostname* es el nombre del propietario, generalmente la cadena devuelta por el comando Unix hostname(1), y *filestamp* es el tiempo NTP en segundos cuando se generó el archivo, en dígitos decimales. Esto garantiza la unicidad y simplifica los procedimientos de mantenimiento, ya que todos los archivos se pueden eliminar rápidamente con un comando **rm** *ntpkey** o todos los archivos generados en un momento específico se pueden eliminar con un comando **rm** **\***\*filestamp**\*. Para reducir aún más el riesgo de una configuración errónea, las dos primeras líneas de un archivo contienen el nombre del archivo y la fecha y hora de generación como comentarios.

Hosts y Grupos de Confianza

Cada configuración criptográfica implica la selección de un esquema de firma y un esquema de identificación, denominado criptotipo, como se explica en la sección "Opciones de Autenticación" de ntp.conf(5). El criptotipo predeterminado utiliza cifrado **RSA**, resumen de mensajes **MD5** e identificación **TC**. Primero, configure una subred NTP que incluya uno o más hosts de confianza de estrato bajo de los cuales todos los demás hosts derivan la sincronización directa o indirectamente. Los hosts de confianza tienen certificados de confianza; todos los demás hosts tienen certificados no confiables. Estos hosts generarán automática y dinámicamente cadenas de certificados autorizadas a uno o más hosts de confianza. Un grupo de confianza es el conjunto de todos los hosts que tienen, directa o indirectamente, una cadena de certificados que termina en un host de confianza. La cadena se define por entradas de archivo de configuración estáticas o por medios dinámicos descritos en la sección "Opciones de Configuración Automática de NTP" de ntp.conf(5).

En cada host de confianza, como root, cambie al directorio de claves. Para garantizar un conjunto de archivos nuevo, elimine todos los archivos *ntpkey*. Luego, ejecute **ntp-keygen** **-T** para generar claves y un certificado de confianza. En todos los demás hosts, haga lo mismo, pero omita la opción **-T** para generar claves y certificados no confiables. Una vez completado, inicie los demonios NTP comenzando por el estrato más bajo y ascendiendo por el árbol. Puede llevar algún tiempo para que Autokey instancie las cadenas de certificados en toda la subred, pero la configuración del entorno es completamente automática.

Si es necesario utilizar una clave de firma diferente o un esquema de resumen/firma diferente al predeterminado, ejecute **ntp-keygen** con la opción **-S** *type*, donde *type* es **RSA** o **DSA**. La necesidad más frecuente de hacerlo es cuando se utiliza un certificado firmado por **DSA**. Si es necesario utilizar un esquema de certificado diferente al predeterminado, ejecute **ntp-keygen** con la opción **-c** *scheme* y seleccione el *scheme* según sea necesario. Si se ejecuta **ntp-keygen** nuevamente sin estas opciones, genera un nuevo certificado utilizando el mismo esquema y clave de firma, y un enlace simbólico.

Después de configurar el entorno, es aconsejable actualizar los certificados de vez en cuando, aunque solo sea para extender el intervalo de validez. Simplemente ejecute **ntp-keygen** con las mismas banderas que antes para generar nuevos certificados utilizando las claves existentes y enlaces simbólicos. Sin embargo, si se cambia la clave del host o de la firma, se debe reiniciar ntpd(1). Cuando se reinicia ntpd(1), carga los nuevos archivos e inicia el protocolo. Otros hosts dependientes continuarán como de costumbre hasta que se actualicen las firmas, momento en el cual se reinicia el protocolo.

Esquemas de Identidad

Como se mencionó en la página "Autokey Public-Key Authentication", el esquema de identidad predeterminado **TC** es vulnerable a un ataque de intermediario. Sin embargo, existen esquemas de identidad más seguros disponibles, incluidos los esquemas **PC**, **IFF**, **GQ** y **MV** descritos a continuación. Estos esquemas se basan en una TA, uno o más hosts de confianza y un número de hosts no confiables. Los hosts de confianza prueban su identidad utilizando valores proporcionados por la TA, mientras que los hosts restantes prueban su identidad utilizando valores proporcionados por un host de confianza y cadenas de certificados que terminan en ese host. El nombre de un host de confianza es también el nombre de su subgrupo y también el nombre del sujeto y emisor en su certificado de confianza. La TA no es necesariamente un host de confianza en este sentido, pero a menudo lo es.

En algunos esquemas existen claves separadas para servidores y clientes. Un servidor también puede ser cliente de otro servidor, pero un cliente nunca puede ser servidor para otro cliente. En general, los hosts de confianza y los hosts no confiables que operan como servidor y cliente tienen archivos de parámetros que contienen claves de servidor y cliente. Los hosts que operan solo como clientes tienen archivos de claves que contienen solo claves de cliente.

El esquema PC admite un solo host de confianza en el grupo. En el host de confianza *alice*, ejecute **ntp-keygen** **-P** **-p** *password* para generar el archivo de clave del host *ntpkey*_ **RSA** *key_alice*.*filestamp* y el archivo de certificado privado de confianza *ntpkey*_ **RSA-MD5** _ *cert_alice*.*filestamp*, y enlaces simbólicos. Copie ambos archivos a todos los hosts del grupo; reemplazan los archivos que se generarían en otros esquemas. En cada host *bob*, instale un enlace simbólico del nombre genérico *ntpkey_host_*bob* al archivo de clave del host y un enlace simbólico *ntpkey_cert_*bob* al archivo de certificado privado. Tenga en cuenta que los enlaces genéricos están en *bob*, pero apuntan a archivos generados por el host de confianza *alice*. En este esquema, no es posible actualizar las claves ni los certificados sin copiarlos a todos los demás hosts del grupo y recrear los enlaces simbólicos.

Para el esquema **IFF**, proceda como en el esquema **TC** para generar claves y certificados para todos los hosts del grupo, luego, para cada host de confianza en el grupo, genere el archivo de parámetros **IFF**. En el host de confianza *alice*, ejecute **ntp-keygen** **-T** **-I** **-p** *password* para producir su archivo de parámetros *ntpkey_IFFpar_alice*.*filestamp*, que incluye claves de servidor y cliente. Copie este archivo a todos los hosts del grupo que operan como servidores y clientes e instale un enlace simbólico del genérico *ntpkey_iff_alice* a este archivo. Si no hay hosts restringidos a operar solo como clientes, no hay nada más que hacer. Dado que el esquema **IFF** es independiente de las claves y los certificados, estos archivos se pueden actualizar según sea necesario.

Si un cliente no autorizado tiene el archivo de parámetros, podría hacerse pasar por un servidor legítimo y presentar una amenaza de intermediario. Para eliminar esta amenaza, las claves del cliente se pueden extraer del archivo de parámetros y distribuir a todos los clientes restringidos. Después de generar el archivo de parámetros, en *alice* ejecute **ntp-keygen** **-e** y redirija la salida a un archivo o programa de correo electrónico. Copie o envíe por correo electrónico este archivo a todos los clientes restringidos. En estos clientes, instale un enlace simbólico del genérico *ntpkey_iff_alice* a este archivo. Para proteger aún más la integridad de las claves, cada archivo se puede cifrar con una contraseña secreta.

Archivos de datos criptográficos

Todos los formatos de archivo comienzan con dos líneas no cifradas. La primera línea contiene el nombre del archivo, incluyendo el nombre de host generado y la marca de tiempo del archivo, en el formato ntpkey_clave _ nombre. marcadetiempoarchivo, donde clave es el tipo de clave o parámetro, nombre es el nombre del host o grupo y marcadetiempoarchivo es la marca de tiempo del archivo (segundos NTP) cuando se creó el archivo. Por convención, los nombres de clave en los nombres de archivo generados incluyen caracteres tanto en mayúsculas como en minúsculas, mientras que los nombres de clave en los nombres de enlace generados incluyen solo caracteres en minúsculas. La marca de tiempo del archivo no se utiliza en los nombres de enlace generados. La segunda línea contiene la marca de fecha en el formato convencional de fecha de Unix. Las líneas que comienzan con ‘#’ se consideran comentarios y son ignoradas por el programa ntp-keygen y el demonio ntpd(1) .

El resto del archivo contiene datos criptográficos, codificados primero utilizando reglas ASN.1, luego cifrados si es necesario, y finalmente escritos en texto ASCII imprimible codificado en PEM, precedido y seguido por líneas de identificador de contenido MIME.

El formato del archivo de claves simétricas, que normalmente se llama ntp.keys, es algo diferente a los otros archivos en interés de la compatibilidad con versiones anteriores. Normalmente, el archivo es generado por este programa, pero se puede construir y editar con un editor de texto ordinario.

Figura 1. Archivo típico de claves simétricas

La Figura 1 muestra un archivo típico de claves simétricas utilizado por la implementación de referencia. Después de la cabecera, las claves se ingresan una por línea en el formato
numeroclave tipo clave
donde numeroclave es un entero positivo en el rango 1-65535; tipo es el tipo de clave para el algoritmo de resumen de mensajes, que en ausencia de la biblioteca OpenSSL debe ser MD5 para designar el algoritmo de resumen de mensajes MD5; si la biblioteca OpenSSL está instalada, el tipo de clave puede ser cualquier algoritmo de resumen de mensajes admitido por esa biblioteca; sin embargo, si se requiere compatibilidad con FIPS 140-2, el tipo de clave debe ser SHA o SHA1; clave es la clave en sí, que es una cadena ASCII imprimible de 20 caracteres o menos de longitud: cada carácter se elige de los 93 caracteres imprimibles en el rango 0x21 a 0x7e ( ‘’! hasta ‘~’ ) excluyendo el espacio y el carácter ‘#’, y terminado por un espacio en blanco o un carácter ‘#’. Una clave OpenSSL consiste en una cadena ASCII codificada en hexadecimal de 40 caracteres, que se trunca según sea necesario.

Tenga en cuenta que las claves utilizadas por los programas ntpq(1) y ntpdc(1) se verifican con contraseñas solicitadas por los programas y se ingresan manualmente, por lo que generalmente es apropiado especificar estas claves en formato ASCII legible por humanos.

El programa ntp-keygen genera un archivo de claves simétricas ntpkey_MD5key_nombrehost. marcadetiempoarchivo. Dado que el archivo contiene claves compartidas privadas, solo debe ser visible para root y distribuido por medios seguros a otros hosts de la subred. El demonio NTP carga el archivo ntp.keys, por lo que ntp-keygen instala un enlace simbólico de este nombre al archivo generado. Posteriormente, se deben instalar enlaces simbólicos similares de forma manual o automatizada en los otros hosts de la subred. Si bien este archivo no se usa con el protocolo Autokey Versión 2, es necesario para autenticar algunos comandos de configuración remota utilizados por las utilidades ntpq(1) y ntpdc(1).
