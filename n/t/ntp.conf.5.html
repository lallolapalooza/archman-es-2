ntp.conf(5) Formatos de archivo ntp.conf(5)

NOMBRE

ntp.conf - Formato del archivo de configuración del demonio (daemon) del Protocolo de Tiempo de Red (NTP)

SINOPSIS

ntp.conf [--nombre-opcion] [--nombre-opcion valor]

Todos los argumentos deben ser opciones.

DESCRIPCIÓN

El archivo de configuración ntp.conf es leído al inicio por el demonio (daemon) ntpd(1) para especificar las fuentes de sincronización, los modos y otra información relacionada. Usualmente, se instala en el directorio /etc, pero podría instalarse en otro lugar (ver la opción de línea de comandos -c del demonio).

El formato del archivo es similar a otros archivos de configuración de UNIX. Los comentarios comienzan con un carácter ‘#’ y se extienden hasta el final de la línea; las líneas en blanco se ignoran. Los comandos de configuración consisten en una palabra clave inicial seguida de una lista de argumentos, algunos de los cuales pueden ser opcionales, separados por espacios en blanco. Los comandos no pueden continuarse en múltiples líneas. Los argumentos pueden ser nombres de host, direcciones de host escritas en forma numérica de punto cuádruple, enteros, números de punto flotante (al especificar tiempos en segundos) y cadenas de texto.

El resto de esta página describe las opciones de configuración y control. La página "Notas sobre la Configuración de NTP y Configuración de una Subred NTP" (disponible como parte de la documentación HTML proporcionada en /usr/share/doc/ntp) contiene una discusión extendida de estas opciones. Soporte de Configuración

A continuación se describe los comandos de configuración en NTPv4. Estos comandos tienen las mismas funciones básicas que en NTPv3 y en algunos casos nuevas funciones y nuevos argumentos. Hay dos clases de comandos, comandos de configuración que configuran una asociación persistente con un servidor o par remoto o un reloj de referencia, y comandos auxiliares que especifican variables de entorno que controlan diversas operaciones relacionadas.

Comandos de Configuración

Los diferentes modos se determinan por la palabra clave del comando y el tipo de la dirección IP requerida. Las direcciones se clasifican por tipo como (s) un servidor o par remoto (IPv4 clase A, B y C), (b) la dirección de difusión (broadcast) de una interfaz local, (m) una dirección multicast (IPv4 clase D), o (r) una dirección de reloj de referencia (127.127.x.x). Tenga en cuenta que solo se enumeran las opciones aplicables a cada comando. El uso de opciones no enumeradas puede no ser detectado como un error, pero puede resultar en un comportamiento extraño e incluso destructivo.

Si se detectan las Extensiones de Interfaz de Socket Básica para IPv6 (RFC-2553), se genera soporte para la familia de direcciones IPv6 además del soporte predeterminado de la familia de direcciones IPv4. En pocos casos, incluida la tabla reslist generada por ntpq(1) o ntpdc(1), las direcciones IPv6 se generan automáticamente. Las direcciones IPv6 se pueden identificar por la presencia de dos puntos “:” en el campo de dirección. Las direcciones IPv6 se pueden usar casi en cualquier lugar donde se puedan usar direcciones IPv4, con la excepción de las direcciones de reloj de referencia, que son siempre IPv4.

Tenga en cuenta que en contextos donde se espera un nombre de host, un calificador -4 que precede al nombre de host obliga a la resolución DNS al espacio de nombres IPv4, mientras que un calificador -6 obliga a la resolución DNS al espacio de nombres IPv6. Consulte las referencias de IPv6 para las clases equivalentes para esa familia de direcciones.

pool

Para direcciones de tipo s, este comando moviliza una asociación persistente en modo cliente con varios servidores remotos. En este modo, el reloj local puede sincronizarse con el servidor remoto, pero el servidor remoto nunca puede sincronizarse con el reloj local.
server

Para direcciones de tipo s y r, este comando moviliza una asociación persistente en modo cliente con el servidor remoto o el reloj de radio local especificado. En este modo, el reloj local puede sincronizarse con el servidor remoto, pero el servidor remoto nunca puede sincronizarse con el reloj local. Este comando *no* debe usarse para direcciones de tipo b o m.
peer

Para direcciones de tipo s (solamente), este comando moviliza una asociación persistente en modo simétrico-activo con el par remoto especificado. En este modo, el reloj local puede sincronizarse con el par remoto o el par remoto puede sincronizarse con el reloj local. Esto es útil en una red de servidores donde, dependiendo de varios escenarios de fallo, el par local o remoto puede ser la mejor fuente de tiempo. Este comando NO debe usarse para direcciones de tipo b, m o r.
broadcast

Para direcciones de tipo b y m (solamente), este comando moviliza una asociación persistente en modo de difusión (broadcast). Se pueden usar múltiples comandos para especificar múltiples interfaces de difusión (subredes) locales y/o múltiples grupos multicast. Tenga en cuenta que los mensajes de difusión locales solo van a la interfaz asociada con la subred especificada, pero los mensajes multicast van a todas las interfaces. En modo de difusión, el servidor local envía mensajes de difusión periódicos a una población de clientes en la dirección especificada, que suele ser la dirección de difusión en (una de) las redes locales o una dirección multicast asignada a NTP. La IANA ha asignado la dirección de grupo multicast IPv4 224.0.1.1 e IPv6 ff05::101 (local del sitio) exclusivamente a NTP, pero se pueden usar otras direcciones no conflictivas para contener los mensajes dentro de los límites administrativos. manycastclient

Para direcciones de tipo m (solo), este comando moviliza una asociación en modo cliente manycast para la dirección de multidifusión especificada. En este caso, se debe proporcionar una dirección específica que coincida con la dirección utilizada en el comando manycastserver para los servidores manycast designados. La dirección de multidifusión NTP 224.0.1.1 asignada por IANA NO debe usarse, a menos que se tomen medidas específicas para evitar la dispersión de grandes áreas de Internet con estos mensajes y causar una implosión posiblemente masiva de respuestas en el remitente. El comando manycastserver especifica que el servidor local debe operar en modo cliente con los servidores remotos que se descubren como resultado de mensajes de difusión/multidifusión. El cliente envía un mensaje de solicitud a la dirección del grupo asociada con la dirección especificada address y los servidores habilitados específicamente responden a estos mensajes. El cliente selecciona los servidores que proporcionan la mejor hora y continúa como con el comando server. Los servidores restantes se descartan como si nunca se hubieran escuchado.

Opciones:

autokey

Todos los paquetes enviados y recibidos del servidor o par incluirán campos de autenticación cifrados utilizando el esquema autokey descrito en Opciones de autenticación.
burst

cuando el servidor es alcanzable, envía un ráfaga de seis paquetes en lugar del usual uno. El espaciado de los paquetes es de 2 s. Esto está diseñado para mejorar la calidad de la medición del tiempo con el comando server y direcciones s.
iburst

Cuando el servidor no es alcanzable, envía una ráfaga de ocho paquetes en lugar del usual uno. El espaciado de los paquetes es de 2 s. Esto está diseñado para acelerar la adquisición inicial de sincronización con el comando server y direcciones s y cuando ntpd(1) se inicia con -q la opción.
key key

Todos los paquetes enviados y recibidos del servidor o par incluirán campos de autenticación cifrados utilizando el identificador de clave key especificado con valores de 1 a 65535, inclusive. El valor predeterminado es no incluir ningún campo de cifrado.
minpoll minpoll

maxpoll maxpoll

Estas opciones especifican los intervalos de sondeo mínimo y máximo para mensajes NTP , como una potencia de 2 en segundos. El intervalo de sondeo máximo por defecto es 10 (1024 s), pero puede aumentarse con la opción maxpoll hasta un límite superior de 17 (36,4 h). El intervalo de sondeo mínimo por defecto es 6 (64 s), pero puede disminuirse con la opción minpoll hasta un límite inferior de 4 (16 s).
noselect

Marca el servidor como no utilizado, excepto para fines de visualización. El servidor es descartado por el algoritmo de selección.
preempt

Indica que la asociación puede ser preemptada.
prefer

Marca el servidor como preferido. Con todo lo demás igual, este host será elegido para sincronización entre un conjunto de hosts que funcionan correctamente. Consulte la página "Reglas de Mitigación y la Palabra Clave prefer" (disponible como parte de la documentación HTML proporcionada en /usr/share/doc/ntp) para obtener más información.
true

Marca el servidor como un truechimer, obligando a que la asociación sobreviva siempre a los algoritmos de selección y agrupamiento. Esta opción casi con toda seguridad debería usarse solo al probar una asociación.
ttl ttl

Esta opción se utiliza solo en los modos de servidor de difusión y cliente manycast. Especifica el tiempo de vida ttl a utilizar en los paquetes de servidor de difusión y servidor multicast, y el ttl máximo para la búsqueda de anillo expandido con paquetes de cliente manycast. La selección del valor adecuado, que por defecto es 127, es algo de arte negro y debe coordinarse con el administrador de la red.
version version

Especifica el número de versión que se utilizará para los paquetes NTP salientes. Las versiones 1-4 son las opciones, siendo la versión 4 la predeterminada.
xleave

Válida solo en los modos peer y broadcast, esta bandera habilita el modo interleave.
xmtnonce

Válida solo para los modos server y pool, esta bandera coloca un número aleatorio en la marca de tiempo de transmisión del paquete.

Comandos Auxiliares

broadcastclient

Este comando habilita la recepción de mensajes de servidor de difusión a cualquier interfaz local (tipo b) dirección. Al recibir un mensaje por primera vez, el cliente de difusión mide el retraso de propagación nominal del servidor utilizando un breve intercambio cliente/servidor con el servidor, luego entra en el modo de cliente de difusión, en el que se sincroniza con los mensajes de difusión subsiguientes. Tenga en cuenta que, para evitar interrupciones accidentales o maliciosas en este modo, tanto el servidor como el cliente deben operar utilizando autenticación de clave simétrica o de clave pública, según se describe en Opciones de autenticación.
manycastserver address ...

Este comando habilita la recepción de mensajes de cliente manycast a la(s) dirección(es) del grupo multicast (tipo m) especificada(s). Se requiere al menos una dirección, pero la dirección de multidifusión NTP 224.0.1.1 asignada por IANA NO debe usarse, a menos que se tomen medidas específicas para limitar el alcance de la respuesta y evitar una implosión posiblemente masiva en el remitente original. Tenga en cuenta que, para evitar interrupciones accidentales o maliciosas en este modo, tanto el servidor como el cliente deben operar utilizando autenticación de clave simétrica o de clave pública, según se describe en Opciones de autenticación.
multicastclient address ...

Este comando habilita la recepción de mensajes de servidor multicast a la(s) dirección(es) del grupo multicast (tipo m) especificada(s). Al recibir un mensaje por primera vez, el cliente multicast mide el retraso de propagación nominal del servidor utilizando un breve intercambio cliente/servidor con el servidor, luego entra en el modo de cliente de difusión, en el que se sincroniza con los mensajes multicast subsiguientes. Tenga en cuenta que, para evitar interrupciones accidentales o maliciosas en este modo, tanto el servidor como el cliente deben operar utilizando autenticación de clave simétrica o de clave pública, según se describe en Opciones de autenticación.
mdnstries number

Si participamos en mDNS, después de sincronizarnos por primera vez, intentamos registrarnos con el sistema mDNS. Si ese intento de registro falla, lo intentamos de nuevo a intervalos de un minuto hasta mdnstries veces. Después de todo, ntpd puede iniciarse antes que mDNS. El valor predeterminado para mdnstries es 5.

Soporte de Autenticación

El soporte de autenticación permite al cliente NTP verificar que el servidor es de hecho conocido y confiable y no un intruso que pretende accidental o intencionalmente suplantar a ese servidor. La especificación NTPv3 RFC-1305 define un esquema que proporciona autenticación criptográfica de los paquetes NTP recibidos. Originalmente, esto se hacía utilizando el algoritmo Data Encryption Standard (DES) operando en modo Cipher Block Chaining (CBC), comúnmente llamado DES-CBC. Posteriormente, esto fue reemplazado por el algoritmo RSA Message Digest 5 (MD5) utilizando una clave privada, comúnmente llamado MD5 con clave. Cualquiera de los algoritmos calcula un resumen del mensaje, o hash unidireccional, que se puede utilizar para verificar que el servidor tiene la clave privada y el identificador de clave correctos.

NTPv4 conserva el esquema NTPv3, propiamente descrito como criptografía de clave simétrica y, además, proporciona un nuevo esquema Autokey basado en criptografía de clave pública. La criptografía de clave pública generalmente se considera más segura que la criptografía de clave simétrica, ya que la seguridad se basa en un valor privado que es generado por cada servidor y nunca se revela. Con Autokey, todas las funciones de distribución y gestión de claves implican solo valores públicos, lo que simplifica considerablemente la distribución y el almacenamiento de claves. La gestión de claves públicas se basa en certificados X.509, que pueden ser proporcionados por servicios comerciales o producidos por programas de utilidad en la biblioteca de software OpenSSL o la distribución NTPv4.

Si bien los algoritmos de criptografía de clave simétrica se incluyen en la distribución NTPv4, la criptografía de clave pública requiere que la biblioteca de software OpenSSL se instale antes de compilar la distribución NTP. Las instrucciones para hacerlo se encuentran en la página Compilación e Instalación de la Distribución.

La autenticación se configura por separado para cada asociación utilizando el subcomando key o autokey en los comandos de configuración peer, server, broadcast y manycastclient, según se describe en la página de Opciones de Configuración. Las opciones de autenticación descritas a continuación especifican las ubicaciones de los archivos de clave, si son diferentes a las predeterminadas, qué claves simétricas son confiables y el intervalo entre varias operaciones, si es diferente a las predeterminadas.

La autenticación está siempre habilitada, aunque ineficaz si no se configura como se describe a continuación. Si llega un paquete NTP que incluye un código de autenticación de mensaje (MAC), solo se acepta si pasa todas las verificaciones criptográficas. Las verificaciones requieren un ID de clave, valor de clave y resumen de mensaje correctos. Si el paquete ha sido modificado de alguna manera o reproducido por un intruso, fallará una o más de estas verificaciones y será descartado. Además, el esquema Autokey requiere un intercambio de protocolo preliminar para obtener el certificado del servidor, verificar sus credenciales e inicializar el protocolo.

El flag auth controla si las nuevas asociaciones o los comandos de configuración remotos requieren autenticación criptográfica. Esta bandera se puede activar o desactivar con los comandos enable y disable y también con comandos de configuración remota enviados por un programa ntpdc(1) que se ejecuta en otra máquina. Si esta bandera está activada, que es el caso por defecto, las nuevas asociaciones de cliente de transmisión y pasivas simétricas y los comandos de configuración remota deben ser criptográficamente autenticados usando criptografía de clave simétrica o de clave pública. Si esta bandera está desactivada, estas operaciones son efectivas incluso si no están criptográficamente autenticadas. Debe entenderse que operar con la bandera auth desactivada invita a una vulnerabilidad significativa donde un hacker malintencionado puede hacerse pasar por un falso marcador de tiempo y causar graves interrupciones en la sincronización del tiempo del sistema. Es importante tener en cuenta que esta bandera no tiene otro propósito que permitir o denegar una nueva asociación en respuesta a mensajes activos de transmisión y simétricos y comandos de configuración remota y, en particular, la bandera no tiene ningún efecto en el proceso de autenticación en sí.

Una alternativa atractiva donde el soporte multicast está disponible es el modo manycast, en el cual los clientes buscan periódicamente servidores como se describe en la página Automatic NTP Configuration Options. Se puede usar criptografía de autenticación de clave simétrica o de clave pública en este modo. La principal ventaja del modo manycast es que los servidores potenciales no necesitan ser configurados de antemano, ya que el cliente los encuentra durante la operación regular, y los archivos de configuración para todos los clientes pueden ser idénticos.

El modelo de seguridad y los esquemas de protocolo tanto para la criptografía de clave simétrica como para la de clave pública se resumen a continuación; más detalles se encuentran en las presentaciones, documentos e informes de la página del proyecto NTP enlazada desde http://www.ntp.org/.

Criptografía de clave simétrica

La especificación original RFC-1305 permite cualquiera de las posibles 65.535 claves, cada una distinguida por un identificador de clave de 32 bits, para autenticar una asociación. Los servidores y clientes involucrados deben acordar la clave y el identificador de clave para autenticar los paquetes NTP. Las claves e información relacionada se especifican en un archivo de claves, usualmente llamado ntp.keys, que debe ser distribuido y almacenado utilizando medios seguros más allá del alcance del propio protocolo NTP. Además de las claves utilizadas para asociaciones NTP ordinarias, se pueden usar claves adicionales como contraseñas para los programas de utilidad ntpq(1) y ntpdc(1).

Cuando ntpd(1) se inicia por primera vez, lee el archivo de claves especificado en el comando de configuración keys e instala las claves en la caché de claves. Sin embargo, las claves individuales deben ser activadas con el comando trusted antes de su uso. Esto permite, por ejemplo, la instalación de posiblemente varios lotes de claves y luego la activación o desactivación remota de cada lote usando ntpdc(1). Esto también proporciona una capacidad de revocación que puede ser utilizada si una clave se ve comprometida. El comando requestkey selecciona la clave utilizada como contraseña para la utilidad ntpdc(1), mientras que el comando controlkey selecciona la clave utilizada como contraseña para la utilidad ntpq(1).

Criptografía de clave pública

NTPv4 soporta el esquema original de clave simétrica NTPv3 descrito en RFC-1305 y, además, el protocolo Autokey, que se basa en criptografía de clave pública. El protocolo Autokey Versión 2 descrito en la página del Protocolo Autokey verifica la integridad de los paquetes usando resúmenes de mensajes MD5 y verifica la fuente con firmas digitales y cualquiera de varios esquemas de resumen/firma. También están disponibles esquemas de identidad opcionales descritos en la página de Esquemas de Identidad y basados en algoritmos criptográficos de desafío/respuesta. El uso de todos estos esquemas proporciona una seguridad sólida contra la repetición con o sin modificación, suplantación, mascarada y la mayoría de las formas de ataques de saturación.

El protocolo Autokey tiene varios modos de operación que corresponden a los diversos modos NTP soportados. La mayoría de los modos utilizan una "cookie" especial que puede ser calculada independientemente por el cliente y el servidor, pero cifrada en la transmisión. Todos los modos utilizan, además, una variante del esquema S-KEY, en la cual se genera una lista de claves pseudoaleatoria y se utiliza en orden inverso. Estos esquemas se describen junto con un resumen ejecutivo, estado actual, diapositivas de presentación y lista de lectura en la página Autonomous Authentication.

El entorno criptográfico específico utilizado por los servidores y clientes Autokey está determinado por un conjunto de archivos y enlaces simbólicos generados por el programa ntp-keygen(1ntpkeygenmdoc). Esto incluye un archivo de clave de host requerido, un archivo de certificado requerido y un archivo de clave de firma opcional, un archivo de segundos intercalares y archivos de esquema de identidad. El esquema de resumen/firma se especifica en el certificado X.509 junto con la clave de firma correspondiente. Hay varios esquemas disponibles en la biblioteca de software OpenSSL, cada uno identificado por una cadena específica como md5WithRSAEncryption, que representa el esquema de resumen de mensajes MD5 con cifrado RSA. La distribución NTP actual soporta todos los esquemas de la biblioteca OpenSSL, incluyendo los basados en firmas digitales RSA y DSA.

Los grupos seguros NTP se pueden usar para definir compartimentos criptográficos y jerarquías de seguridad. Es importante que cada host en el grupo pueda construir un rastro de certificados hasta uno o más hosts de confianza en el mismo grupo. Cada host del grupo ejecuta el protocolo Autokey para obtener los certificados de todos los hosts en el rastro hasta uno o más hosts de confianza. Esto requiere que el archivo de configuración en todos los hosts esté diseñado de manera que, incluso bajo condiciones de fallo anticipadas, la subred NTP se forme de manera que cada host del grupo pueda encontrar un rastro hasta al menos un host de confianza.

Denominación y dirección IP

Es importante tener en cuenta que Autokey no utiliza DNS para resolver direcciones, ya que DNS no se puede confiar completamente hasta que los servidores de nombres hayan sincronizado los relojes. El nombre criptográfico utilizado por Autokey para vincular las credenciales de identidad del host y los valores criptográficos debe ser independiente de la interfaz, la red y cualquier otra convención de nomenclatura. El nombre aparece en el certificado del host en los campos del sujeto y/o del emisor, por lo que la protección contra el compromiso de DNS es esencial.

Por convención, el nombre de un host Autokey es el nombre devuelto por la llamada al sistema Unix gethostname(2) o su equivalente en otros sistemas. Según el modelo de diseño del sistema, no hay provisiones para permitir nombres o alias alternativos. Sin embargo, esto no quiere decir que los alias de DNS, nombres diferentes para cada interfaz, etc., estén restringidos de alguna manera.

También es importante tener en cuenta que Autokey verifica la autenticidad utilizando el nombre del host, la dirección de red y las claves públicas, todo lo cual está vinculado por el protocolo específicamente para desviar los ataques de suplantación. Por esta razón, Autokey incluye las direcciones IP de origen y destino en los cálculos del resumen del mensaje y, por lo tanto, las mismas direcciones deben estar disponibles tanto en el servidor como en el cliente. Por esta razón, la operación con esquemas de traducción de direcciones de red no es posible. Esto refleja el modelo de seguridad robusto previsto donde los servidores NTP gubernamentales y corporativos se operan fuera de los perímetros del firewall.

Operación

Una combinación específica de esquema de autenticación (ninguno, clave simétrica, clave pública) y esquema de identidad se denomina criptotipo, aunque no todas las combinaciones son compatibles. Puede haber configuraciones de gestión donde los clientes, servidores y pares no soporten todos los mismos criptotipos. Una subred NTPv4 segura se puede configurar de muchas maneras teniendo en cuenta los principios explicados anteriormente y en esta sección. Tenga en cuenta, sin embargo, que algunas combinaciones de criptotipos pueden interoperar exitosamente entre sí, pero pueden no representar buenas prácticas de seguridad.

El criptotipo de una asociación se determina en el momento de la movilización, ya sea en el momento de la configuración o algún tiempo después cuando llega un mensaje del criptotipo apropiado. Cuando se moviliza mediante un comando de configuración server o peer y no hay subcomandos key o autokey presentes, la asociación no se autentica; si el subcomando key está presente, la asociación se autentica utilizando el ID de clave simétrica especificado; si el subcomando autokey está presente, la asociación se autentica utilizando Autokey.

Cuando se soportan múltiples esquemas de identidad en el protocolo Autokey, el primer intercambio de mensajes determina cuál se utiliza. El mensaje de solicitud del cliente contiene bits correspondientes a los esquemas que tiene disponibles. El mensaje de respuesta del servidor contiene bits correspondientes a los esquemas que tiene disponibles. Tanto el servidor como el cliente comparan los bits recibidos con los suyos y seleccionan un esquema común.

Siguiendo el principio de que el tiempo es un valor público, un servidor responde a cualquier paquete del cliente que coincida con sus capacidades de criptotipo. Por lo tanto, un servidor que recibe un paquete no autenticado responderá con un paquete no autenticado, mientras que el mismo servidor que recibe un paquete de un criptotipo que soporta responderá con paquetes de ese criptotipo. Sin embargo, las asociaciones de clientes broadcast o manycast no configuradas o las asociaciones pasivas simétricas no se movilizarán a menos que el servidor soporte un criptotipo compatible con el primer paquete recibido. Por defecto, las asociaciones no autenticadas no se movilizarán a menos que se anule de una manera decididamente peligrosa.

Algunos ejemplos pueden ayudar a reducir la confusión. El cliente Alice no tiene ningún criptotipo específico seleccionado. El servidor Bob tiene tanto un archivo de clave simétrica como archivos Autokey mínimos. Los mensajes no autenticados de Alice llegan a Bob, quien responde con mensajes no autenticados. Cathy tiene una copia del archivo de clave simétrica de Bob y ha seleccionado el ID de clave 4 en los mensajes a Bob. Bob verifica el mensaje con su ID de clave 4. Si es la misma clave y el mensaje se verifica, Bob envía a Cathy una respuesta autenticada con esa clave. Si la verificación falla, Bob envía a Cathy algo llamado crypto-NAK, que le dice que algo falló. Ella puede ver la evidencia usando el programa ntpq(1).

Denise ha creado su propia clave de host y certificado. Ella también utiliza uno de los esquemas de identidad como Bob. Ella envía el primer mensaje Autokey a Bob y ambos realizan los pasos de autenticación e identidad del protocolo. Si todo sale bien, Den

ise y Bob continúan como se describe anteriormente.

De lo anterior debería quedar claro que Bob puede dar soporte a todas las chicas al mismo tiempo, siempre que tenga credenciales de autenticación e identidad compatibles. Ahora, Bob puede actuar igual que las chicas en su propia elección de servidores; puede ejecutar múltiples asociaciones configuradas con múltiples servidores diferentes (o el mismo servidor, aunque eso podría no ser útil). Pero, una política de seguridad prudente podría impedir ciertas combinaciones de tipos de cifrado; por ejemplo, ejecutar un esquema de identidad con un servidor y sin autenticación con otro podría no ser prudente.

Gestión de Claves

Los valores criptográficos utilizados por el protocolo Autokey se incorporan como un conjunto de archivos generados por la utilidad ntp-keygen(1ntpkeygenmdoc), incluyendo archivos de clave simétrica, clave de host y certificado público, así como archivos de clave de firma, parámetros de identidad y leapseconds. Alternativamente, las claves de host y de firma y los archivos de certificado pueden ser generados por las utilidades OpenSSL y los certificados pueden ser importados de autoridades de certificación pública. Tenga en cuenta que las claves simétricas son necesarias para las utilidades ntpq(1) y ntpdc(1). Los archivos restantes solo son necesarios para el protocolo Autokey.

Los certificados importados de OpenSSL o de autoridades de certificación pública tienen ciertas limitaciones. El certificado debe estar en sintaxis ASN.1, formato X.509 Versión 3 y codificado en PEM, que es el mismo formato utilizado por OpenSSL. La longitud total del certificado codificado en ASN.1 no debe exceder los 1024 bytes. El campo del nombre distinguido del sujeto (CN) es el nombre completo del host en el que se utiliza; los campos restantes del sujeto se ignoran. Los campos de extensión del certificado no deben contener un identificador de clave del sujeto ni un identificador de clave del emisor; sin embargo, un campo de uso extendido de clave para un host de confianza debe contener el valor trustRoot;. Otros campos de extensión se ignoran.

Especifica el intervalo entre regeneraciones de la lista de claves de sesión utilizada con el protocolo Autokey. Este comando especifica la ruta del directorio por defecto para claves criptográficas, parámetros y certificados. El valor por defecto es /usr/local/etc/.

Especifica los identificadores de clave en los que se confía para fines de autenticación de pares con criptografía de clave simétrica, así como las claves utilizadas por los programas ntpq(1) y ntpdc(1). Los procedimientos de autenticación requieren que tanto el servidor local como el remoto compartan la misma clave e identificador de clave para este propósito, aunque se pueden utilizar claves diferentes con servidores diferentes. Los argumentos key son enteros sin signo de 32 bits con valores de 1 a 65.535.

Los conjuntos de archivos de generación proporcionan acceso a un conjunto de archivos utilizados para almacenar los datos reales. Este es el tipo de los registros de estadísticas, como se muestra en el comando statistics.

Este es el nombre del archivo para los registros de estadísticas. Los nombres de archivo de los miembros del conjunto se construyen a partir de tres elementos concatenados: prefijo, nombre_archivo y sufijo:

Esta es una ruta de nombre de archivo constante. No está sujeta a modificaciones a través de la opción filegen. Es definida por el servidor, usualmente especificada como una constante en tiempo de compilación. Sin embargo, puede ser configurable para conjuntos de archivos de generación individuales a través de otros comandos. Por ejemplo, el prefijo utilizado con la generación loopstats y peerstats se puede configurar utilizando la opción statsdir explicada anteriormente.

Esta cadena se concatena directamente al prefijo mencionado anteriormente (sin un '/'). Esto se puede modificar utilizando el argumento file de la declaración filegen. No se permiten elementos '..' en este componente para evitar que los nombres de archivo se refieran a partes fuera de la jerarquía del sistema de archivos denotada por prefix.

Esta parte refleja los elementos individuales de un conjunto de archivos. Se genera de acuerdo con el tipo de un conjunto de archivos.

Un conjunto de generación de archivos se caracteriza por su tipo. Se admiten los siguientes tipos:
none

El conjunto de archivos es en realidad un único archivo plano.
pid

Se utiliza un elemento del conjunto de archivos por cada encarnación de un servidor ntpd. Este tipo no realiza ningún cambio en los miembros del conjunto de archivos durante la ejecución, sin embargo, proporciona una forma fácil de separar los archivos que pertenecen a diferentes encarnaciones del servidor ntpd(1). El nombre de archivo del miembro del conjunto se construye añadiendo un ‘.’ a concatenada prefijo y nombre de archivo cadenas, y agregando la representación decimal del ID del proceso del servidor ntpd(1) .

Se crea un elemento de conjunto de generación de archivos por día. Un día se define como el período entre las 00:00 y las 24:00 UTC. El sufijo del miembro del conjunto de archivos consta de un punto (‘.’) y una especificación de día en el formato AAAA MM DD. AAAA es un número de año de 4 dígitos (p. ej., 1992). MM es un número de mes de dos dígitos. DD es un número de día de dos dígitos. Por lo tanto, toda la información escrita el 10 de diciembre de 1992 terminaría en un archivo llamado prefijo nombre de archivo.19921210.

Cualquier miembro del conjunto de archivos contiene datos relacionados con una determinada semana del año. El término semana se define calculando el día del año módulo 7. Los elementos de dicho conjunto de generación de archivos se distinguen agregando el siguiente sufijo a la base del nombre del archivo del conjunto: un punto, un número de año de 4 dígitos, la letra W y un número de semana de 2 dígitos. Por ejemplo, la información del 10 de enero de 1992 terminaría en un archivo con el sufijo
mes

Se genera un elemento de conjunto de generación de archivos por mes. El sufijo del nombre del archivo consta de un punto, un número de año de 4 dígitos y un mes de 2 dígitos.
año

Se genera un elemento de generación de archivos por año. El sufijo del nombre del archivo consta de un punto y un número de año de 4 dígitos.
edad

Este tipo de conjunto de generación de archivos cambia a un nuevo elemento del conjunto de archivos cada 24 horas de operación del servidor. El sufijo del nombre del archivo consta de un punto, la letra a y un número de 8 dígitos. Este número se considera el número de segundos que el servidor ha estado en funcionamiento al comienzo del período de 24 horas correspondiente. La información solo se escribe en un archivo de generación al especificar enable; la salida se evita especificando disable.
link | nolink

Es conveniente poder acceder al elemento actual de un conjunto de generación de archivos con un nombre fijo. Esta función se habilita especificando link y se deshabilita usando nolink. Si se especifica link, se crea un enlace físico (hard link) desde el elemento actual del archivo a un archivo sin sufijo. Cuando ya existe un archivo con este nombre y el número de enlaces de este archivo es uno, se renombra agregando un punto, la letra C y el pid del proceso del servidor ntpd(1). Cuando el número de enlaces es mayor que uno, el archivo se elimina (unlinked). Esto permite que el archivo actual sea accedido por un nombre constante.
enable | disable

Habilita o deshabilita la función de registro.

Soporte de Control de Acceso

El demonio ntpd(1) implementa una lista general de restricciones basada en dirección/máscara. La lista contiene entradas de dirección/coincidencia ordenadas primero por valores de dirección crecientes y luego por valores de máscara crecientes. Se produce una coincidencia cuando el AND bit a bit de la máscara y la dirección fuente del paquete es igual al AND bit a bit de la máscara y la dirección en la lista. La lista se busca en orden, y la última coincidencia encontrada define las banderas de restricción asociadas con la entrada. Se puede encontrar información adicional y ejemplos en la página "Notas sobre la configuración de NTP y la configuración de una subred NTP" (disponible como parte de la documentación HTML proporcionada en /usr/share/doc/ntp).

La instalación de restricciones se implementó de conformidad con las políticas de acceso para los servidores de tiempo de la red troncal original de NSFnet. Posteriormente, la instalación se amplió para desviar ataques criptográficos y de saturación. Si bien esta instalación puede ser útil para evitar que clientes no deseados, defectuosos o maliciosos congestionen servidores inocentes, no debe considerarse una alternativa a las instalaciones de autenticación de NTP. Las restricciones basadas en la dirección fuente se pueden eludir fácilmente con un cracker decidido.

Se puede negar el servicio a los clientes porque están incluidos explícitamente en la lista de restricciones creada por el comando restrict o implícitamente como resultado de violaciones criptográficas o de límite de velocidad. Las violaciones criptográficas incluyen fallas en la verificación del certificado o la identidad; las violaciones de límite de velocidad generalmente resultan de implementaciones NTP defectuosas que envían paquetes a tasas abusivas. Algunas violaciones causan la denegación de servicio solo para el paquete infractor, otras causan la denegación de servicio por un período limitado y otras causan la denegación de servicio por un período indefinido. Cuando a un cliente o red se le niega el acceso por un período indefinido, la única forma actual de eliminar las restricciones es reiniciando el servidor.

El paquete Kiss-of-Death

Normalmente, los paquetes a los que se les niega el servicio simplemente se descartan sin más acción que el incremento de los contadores de estadísticas. A veces, se necesita una respuesta más proactiva, como un mensaje del servidor que solicita explícitamente al cliente que deje de enviar y deje un mensaje para el operador del sistema. Se ha creado un formato de paquete especial para este propósito llamado paquete "kiss-of-death" (KoD). Los paquetes KoD tienen los bits de salto (leap bits) establecidos como no sincronizados y el estrato (stratum) establecido en cero, y el campo de identificador de referencia establecido en un código ASCII de cuatro bytes. Si la bandera noserve o notrust de la entrada de la lista de restricciones coincidente está establecida, el código es "DENY"; si la bandera limited está establecida y se excede el límite de velocidad, el código es "RATE". Finalmente, si ocurre una violación criptográfica, el código es "CRYP".

Un cliente que recibe un KoD realiza un conjunto de comprobaciones de sanidad para minimizar la exposición de seguridad, luego actualiza las variables del par (peer) de estrato e identificador de referencia, establece el bit de acceso denegado (TEST4) en la variable flash del par y envía un mensaje al registro. Mientras el bit TEST4 esté establecido, el cliente no enviará más paquetes al servidor. La única forma actual de recuperarse de esta condición es reiniciar el protocolo tanto en el cliente como en el servidor. Esto sucede automáticamente en el cliente cuando la asociación expira. Sucederá en el servidor solo si el operador del servidor coopera.

discard [average avg] [minimum min] [monitor prob]

Establece los parámetros de la función limited, que protege al servidor del abuso por parte del cliente. El subcomando average especifica el espaciado mínimo promedio de paquetes en segundos log2, con un valor predeterminado de 3 (8s), mientras que el subcomando minimum especifica el espaciado mínimo de paquetes en segundos, con un valor predeterminado de 2. Los paquetes que violan estos mínimos se descartan y se devuelve un paquete kiss-o'-death si está habilitado. El subcomando monitor especifica indirectamente la probabilidad de reemplazar la entrada más antigua de la lista de solicitudes recientes (monitor, MRU) utilizada para aplicar controles de velocidad, cuando esa lista está en su tamaño máximo. La probabilidad de reemplazar la entrada más antigua es la antigüedad de esa entrada en segundos dividida por el valor de monitor, que por defecto es 3000. Por ejemplo, si la entrada más antigua en la lista MRU representa una solicitud de hace 300 segundos, por defecto la probabilidad de reemplazarla con una entrada que represente la solicitud del cliente que se está procesando ahora es del 10%. Por el contrario, si la entrada más antigua tiene más de 3000 segundos de antigüedad, la probabilidad es del 100%.

RESTRICT

The restrict configuration commands specify the access-control rules to be applied to packets from remote hosts. The default restriction list is empty, meaning all packets are permitted. The default restriction entries are inserted into the table at startup to prevent ntpd from attempting to synchronize to itself.

The syntax of the restrict command is:

restrict [address] [[...]]
restrict source [address] [[...]]

Where address is a single IP address, a network number, or a network number and mask. If address is omitted, it defaults to the wildcard address 0.0.0.0.

The optional flags are:

default

This keyword is used to indicate the default restriction entry. It is always present, though if it is otherwise unconfigured; no flags are associated with the default entry (i.e., everything besides your own NTP server is unrestricted).
ignore

Ignore all packets from matching hosts.
interface

Only permit packets if the destination address is the interface address for the incoming packet. This option is intended to prevent certain classes of attacks and should be used with caution.
lowpriotrap

Declare traps set by matching hosts to be low priority. The number of traps a server can maintain is limited (the current limit is 3). Traps are usually assigned on a first come, first served basis, with later trap requestors being denied service. This flag modifies the assignment algorithm by allowing low priority traps to be overridden by later requests for normal priority traps.
noepeer

Deny ephemeral peer requests, even if they come from an authenticated source. Note that the ability to use a symmetric key for authentication may be restricted to one or more IPs or subnets via the third field of the ntp.keys file. This restriction is not enabled by default, to maintain backward compatability. Expect noepeer to become the default in ntp-4.4.
nomodify

Deny ntpq(1) and ntpdc(1) queries which attempt to modify the state of the server (i.e., run time reconfiguration). Queries which return information are permitted.
noquery

Deny ntpq(1) and ntpdc(1) queries. Time service is not affected.
nopeer

Deny unauthenticated packets which would result in mobilizing a new association. This includes broadcast and symmetric active packets when a configured association does not exist. It also includes pool associations, so if you want to use servers from a pool directive and also want to use nopeer by default, you'll want a restrict source ... line as well that does not include the nopeer directive.
noserve

Deny all packets except ntpq(1) and ntpdc(1) queries.
notrap

Decline to provide mode 6 control message trap service to matching hosts. The trap service is a subsystem of the ntpq(1) control message protocol which is intended for use by remote event logging programs.
notrust

Deny service unless the packet is cryptographically authenticated.
ntpport

This is actually a match algorithm modifier, rather than a restriction flag. Its presence causes the restriction entry to be matched only if the source port in the packet is the standard NTP UDP port (123). There can be two restriction entries with the same IP address if one specifies ntpport and the other does not. The ntpport entry is considered more specific and is sorted later in the list.
serverresponse fuzz

When reponding to server requests, fuzz the low order bits of the reftime.
version

Deny packets that do not match the current NTP version.

Default restriction list entries with the flags ignore, interface, ntpport, for each of the local host's interface addresses are inserted into the table at startup to prevent ntpd from attempting to synchronize to itself, such as with manycastclient when manycast is also specified with the same multicast address. A default entry is also always present, though if it is otherwise unconfigured; no flags are associated with the default entry (i.e., everything besides your own NTP server is unrestricted).

delrestrict [source] address

Remove a previously-set restriction. This is useful for runtime configuration via ntpq(1) source is specified, a dynamic restriction created from the restrict source template at the time an association was added is removed. Without source a static restriction is removed.

Manycasting

Manycasting es un paradigma de descubrimiento y configuración automática nuevo en NTPv4. Está destinado a ser un medio para que un cliente multicast busque en el vecindario de red cercano para encontrar servidores manycast cooperativos, validarlos mediante medios criptográficos y evaluar sus valores de tiempo con respecto a otros servidores que puedan estar al acecho en la vecindad. El resultado previsto es que cada cliente manycast moviliza asociaciones de cliente con algunos de los "mejores" servidores manycast cercanos, y aun así se reconfigura automáticamente para mantener este número de servidores en caso de que uno u otro falle.

Tenga en cuenta que el paradigma manycast no coincide con el paradigma anycast descrito en RFC-1546, que está diseñado para encontrar un único servidor de un grupo de servidores que brindan el mismo servicio. El paradigma manycast está diseñado para encontrar una pluralidad de servidores redundantes que cumplen criterios de optimización definidos.

Manycasting se puede usar con criptografía de clave simétrica o de clave pública. La infraestructura de clave pública (PKI) ofrece la mejor protección contra claves comprometidas y generalmente se considera más sólida, al menos con tamaños de clave relativamente grandes. Se implementa utilizando el protocolo Autokey y la biblioteca criptográfica OpenSSL disponible en http://www.openssl.org/. La biblioteca también se puede usar con otros modos de NTPv4 así como y se recomienda encarecidamente, especialmente para modos de difusión.

Una asociación persistente de cliente manycast se configura utilizando el comando manycastclient, que es similar al comando server pero con una dirección de grupo multicast (clase IPv4 D o prefijo IPv6 FF). La IANA ha designado la dirección IPv4 224.1.1.1 y la dirección IPv6 FF05::101 (ámbito de sitio) para NTP. Cuando se necesitan más servidores, transmite mensajes de cliente manycast a esta dirección con la tasa mínima factible y el tiempo mínimo factible para pasar (TTL) saltos, dependiendo de cuántos servidores se hayan encontrado ya. Puede haber tantas asociaciones de cliente manycast como direcciones de grupo diferentes, cada una sirviendo como plantilla para una futura asociación efímera de cliente/servidor unicast.

Los servidores manycast configurados con el comando manycastserver escuchan en la dirección de grupo especificada los mensajes de cliente manycast. Tenga en cuenta la distinción entre cliente manycast, que transmite activamente mensajes, y servidor manycast, que les responde pasivamente. Si un servidor manycast está dentro del alcance del TTL actual y está sincronizado con una fuente válida y opera a un nivel de estrato igual o inferior al del cliente manycast, responde al mensaje de cliente manycast con un mensaje de servidor unicast ordinario.

El cliente manycast que recibe este mensaje moviliza una asociación efímera de cliente/servidor de acuerdo con la plantilla manycast coincidente, pero solo si está autenticado criptográficamente y el estrato del servidor es menor o igual al estrato del cliente. La autenticación es explícitamente requerida y se puede usar clave simétrica o clave pública (Autokey). Luego, el cliente sondea al servidor en su dirección unicast en modo ráfaga para establecer de manera confiable el reloj del host y validar la fuente. Esto normalmente da como resultado una serie de ocho clientes/servidores con intervalos de 2 segundos durante los cuales se ejecutan simultáneamente los protocolos de sincronización y criptográficos. Después de la serie, el cliente ejecuta los algoritmos de intersección y agrupación de NTP, que actúan para descartar todas las asociaciones excepto las "mejores" de acuerdo con el estrato y la distancia de sincronización. Las asociaciones supervivientes continúan en modo cliente/servidor ordinario.

La estrategia de sondeo del cliente manycast está diseñada para reducir tanto como sea posible el volumen de mensajes de cliente manycast y los efectos de implosión debidos a la llegada casi simultánea de mensajes de servidor manycast. La estrategia está determinada por los comandos de configuración manycastclient, tos y ttl. El intervalo de sondeo manycast es normalmente ocho veces el intervalo de sondeo del sistema, que comienza en el valor minpoll especificado en el comando manycastclient y, en circunstancias normales, se incrementa hasta el valor maxpolll especificado en este comando. Inicialmente, el TTL se establece en el número mínimo de saltos especificado por el comando ttl. En cada retransmisión, el TTL se incrementa hasta alcanzar el número máximo de saltos especificado por este comando o se han encontrado suficientes asociaciones de cliente. Las retransmisiones posteriores utilizan el mismo TTL.

La calidad y fiabilidad del conjunto de asociaciones descubiertas por el cliente manycast está determinada por los algoritmos de mitigación de NTP y los valores minclock y minsane especificados en el comando de configuración tos. Deben estar disponibles al menos minsane servidores candidatos y los algoritmos de mitigación producen al menos minclock supervivientes para sincronizar el reloj. Los principios de acuerdo bizantino requieren al menos cuatro candidatos para descartar correctamente un único falseticker. Por motivos de compatibilidad, minsane por defecto es 1 y minclock por defecto es 3. Para el servicio manycast, minsane debe establecerse explícitamente en 4, asumiendo que hay al menos esa cantidad de servidores disponibles.

Si se encuentran al menos minclock servidores, el intervalo de sondeo manycast se establece inmediatamente en ocho veces maxpoll. Si se encuentran menos de minclock servidores cuando el TTL ha alcanzado el número máximo de saltos, el intervalo de sondeo manycast se duplica. Para cada transmisión posterior, el intervalo de sondeo se duplica nuevamente hasta alcanzar el máximo de ocho veces maxpoll. Las transmisiones posteriores utilizan los mismos valores de intervalo de sondeo y TTL. Tenga en cuenta que mientras todo esto ocurre, cada asociación de cliente/servidor encontrada está operando normalmente según el intervalo de sondeo del sistema.

Los límites de multidifusión con ámbito administrativo se especifican normalmente mediante la configuración del enrutador de red y, en el caso de IPv6, el prefijo de ámbito de enlace/sitio. Por defecto, el incremento para los saltos TTL es 32 comenzando desde 31; sin embargo, el comando de configuración ttl puede usarse para modificar los valores y que coincidan con las reglas de ámbito.

Operación del Cliente Manycast

El objetivo de la operación manycast es encontrar y asociarse con uno de varios servidores que usan la misma dirección de grupo, y eventualmente elegir el mejor para la sincronización de tiempo. La selección se basa en el estrato del servidor, la distancia de sincronización y la latencia de ida y vuelta. Para simplificar las cosas, se puede usar la opción tos para modificar el comportamiento de selección. La configuración de muchos clientes manycast con la misma dirección de grupo común podría conducir a la saturación de los servidores, ya que cada cliente envía un mensaje y cada servidor en el rango TTL responde. Por lo tanto, se deben configurar cuidadosamente los parámetros del cliente manycast para evitar este problema.

La opción tos se puede usar para modificar este comportamiento. Se desaconseja encarecidamente a los servidores con un estrato inferior a floor o superior a ceiling especificados en el comando tos durante el proceso de selección; sin embargo, estos servidores pueden ser aceptados temporalmente si el número de servidores dentro del rango TTL es menor que minclock.

Estas acciones ocurren para cada mensaje del cliente manycast, que se repite en el intervalo de sondeo designado. Sin embargo, una vez que se moviliza la asociación del cliente efímero, se descartan las respuestas posteriores del servidor manycast, ya que esto resultaría en una asociación duplicada. Si durante un intervalo de sondeo el número de asociaciones de clientes cae por debajo de minclock, todas las asociaciones de prototipo de clientes manycast se restablecen al intervalo de sondeo inicial y las salidas TTL, y la operación se reanuda desde el principio. Es importante evitar mensajes frecuentes del cliente manycast, ya que cada uno requiere que todos los servidores manycast dentro del rango TTL respondan. El resultado podría ser una implosión, menor o mayor, dependiendo del número de servidores en el rango. El valor recomendado para maxpoll es 12 (4.096 s).

Es posible y frecuentemente útil configurar un host como cliente manycast y servidor manycast. Varios hosts configurados de esta manera y que comparten una dirección de grupo común se organizarán automáticamente en una configuración óptima basada en el estrato y la distancia de sincronización. Por ejemplo, considere una subred NTP de dos servidores primarios y cien o más clientes dependientes. Con dos excepciones, todos los servidores y clientes tienen archivos de configuración idénticos que incluyen los comandos multicastclient y multicastserver utilizando, por ejemplo, la dirección de grupo de multidifusión 239.1.1.1. La única excepción es que cada archivo de configuración del servidor primario debe incluir comandos para la fuente de referencia primaria, como un receptor GPS.

Los archivos de configuración restantes para todos los servidores secundarios y clientes tienen el mismo contenido, excepto por el comando tos, que es específico para cada nivel de estrato. Para servidores de estrato 1 y estrato 2, ese comando no es necesario. Para servidores de estrato 3 y superiores, el valor floor se establece en el número de estrato previsto. Por lo tanto, todos los archivos de configuración de estrato 3 son idénticos, todos los archivos de estrato 4 son idénticos y así sucesivamente.

Una vez que las operaciones se han estabilizado en este escenario, los servidores primarios encontrarán la fuente de referencia primaria y se encontrarán entre sí, ya que ambos operan en el mismo estrato (1), pero no con ningún servidor o cliente secundario, ya que estos operan en un estrato superior. Los servidores secundarios encontrarán los servidores en el mismo nivel de estrato. Si uno de los servidores primarios pierde su receptor GPS, continuará operando como cliente y otros clientes agotarán la asociación correspondiente y se reasociarán en consecuencia.

Algunos administradores prefieren evitar ejecutar ntpd(1) de forma continua y ejecutar sntp(1) o ntpd(1) -q como un trabajo cron. En cualquier caso, los servidores deben configurarse con anticipación y el programa falla si no hay ninguno disponible cuando se ejecuta el trabajo cron. Una aplicación realmente elegante de manycast es con ntpd(1) -q. El programa se despierta, escanea el entorno local buscando a los sospechosos habituales, selecciona el mejor entre los pícaros, ajusta el reloj y luego se va. Los servidores no tienen que configurarse con anticipación y todos los clientes de la red pueden tener el mismo archivo de configuración.

Interacciones Manycast con Autokey

Cada vez que un cliente manycast envía un paquete en modo cliente a una dirección de grupo de multidifusión, todos los servidores manycast en ámbito generan una respuesta que incluye el nombre del host y la palabra de estado. Los clientes manycast luego ejecutan el protocolo Autokey, que recopila y verifica todos los certificados involucrados. Después del intervalo de ráfaga, se descartan todos excepto tres supervivientes, pero los certificados permanecen en la caché local. A menudo sucede que se recopilan varias cadenas de firma completas desde el cliente hasta los servidores primarios de esta manera.

Aproximadamente una vez por hora o con menos frecuencia si el intervalo de sondeo excede esto, el cliente regenera la lista de claves de Autokey. Esto es, en general, transparente en el modo cliente/servidor. Sin embargo, aproximadamente una vez al día, se actualiza el valor privado del servidor utilizado para generar cookies junto con todas las asociaciones manycast. En este caso, se actualizan todos los valores criptográficos, incluidos los certificados. Si se ha generado un nuevo certificado desde la última época de actualización, revocará automáticamente todos los certificados anteriores que se encuentren en la caché de certificados. Al mismo tiempo, el esquema manycast comienza de nuevo desde el principio y el anillo expansivo se reduce al mínimo y se incrementa a partir de ahí mientras se recopilan todos los servidores en ámbito.

CONFIGURACIÓN DE RELOJES DE REFERENCIA

Como regla general, los errores de reloj de referencia solo se registran en el archivo de registro del sistema, pero por lo demás no son peligrosos.

A efectos de configuración, ntpd(1) trata los relojes de referencia de una manera análoga a los pares NTP normales en la medida de lo posible. Los relojes de referencia se identifican mediante una dirección IP sintácticamente correcta pero no válida, para distinguirlos de los pares NTP normales. Las direcciones de los relojes de referencia tienen el formato 127.127.t.u, donde t es un entero que indica el tipo de reloj y u indica el número de unidad en el rango de 0 a 3. Aunque pueda parecer exagerado, a veces es útil configurar múltiples relojes de referencia del mismo tipo, en cuyo caso los números de unidad deben ser únicos.

El comando server se utiliza para configurar un reloj de referencia, donde el argumento de dirección es la dirección del reloj. Las opciones key, version y ttl no se utilizan para la soporte de relojes de referencia. La opción mode se añade para el soporte de relojes de referencia, como se describe a continuación. La opción prefer puede ser útil para persuadir al servidor para que aprecie un reloj de referencia con algo más de entusiasmo que otros relojes de referencia o pares. Se puede encontrar más información sobre esta opción en la página "Mitigation Rules and the prefer Keyword" (disponible como parte de la documentación HTML proporcionada en /usr/share/doc/ntp). Las opciones minpoll y maxpoll solo tienen significado para determinados controladores de reloj. Consulte las páginas de documentación de cada controlador de reloj para obtener información adicional.

El comando fudge se utiliza para proporcionar información adicional para controladores de reloj individuales y normalmente sigue inmediatamente después del comando server. El argumento de dirección especifica la dirección del reloj. Las opciones refid y stratum se pueden utilizar para anular los valores predeterminados del dispositivo. Hay dos desfases de tiempo opcionales dependientes del dispositivo y cuatro banderas que también se pueden incluir en el comando fudge.

El número de estrato de un reloj de referencia es cero por defecto. Dado que el demonio ntpd(1) añade uno al estrato de cada par, un servidor primario normalmente muestra un estrato externo de uno. Para proporcionar copias de seguridad diseñadas, a menudo es útil especificar el estrato del reloj de referencia como superior a cero. La opción stratum se utiliza para este propósito. Además, en casos que involucran tanto un reloj de referencia como una señal de disciplina de pulso por segundo (PPS), es útil especificar el identificador del reloj de referencia como distinto del valor predeterminado, dependiendo del controlador. La opción refid se utiliza para este propósito. Salvo que se indique lo contrario, estas opciones se aplican a todos los controladores de reloj.

Comandos de reloj de referencia

server 127.127.t.u [prefer] [mode int] [minpoll int] [maxpoll int]

Este comando se puede utilizar para configurar relojes de referencia de maneras especiales. Las opciones se interpretan de la siguiente manera:
prefer

Marca el reloj de referencia como preferido. Dentro de lo posible, este host se elegirá para la sincronización entre un conjunto de hosts que funcionan correctamente. Consulte la página "Mitigation Rules and the prefer Keyword" (disponible como parte de la documentación HTML proporcionada en /usr/share/doc/ntp) para obtener más información.
mode int

Especifica un número de modo que se interpreta de forma específica para el dispositivo. Por ejemplo, selecciona un protocolo de marcación en el controlador ACTS y un subtipo de dispositivo en los controladores de análisis.
minpoll int

maxpoll int

Estas opciones especifican el intervalo de sondeo mínimo y máximo para los mensajes del reloj de referencia, como una potencia de 2 en segundos. Para la mayoría de los relojes de referencia conectados directamente, tanto minpoll como maxpoll tienen un valor predeterminado de 6 (64 s). Para los relojes de referencia por módem, minpoll tiene un valor predeterminado de 10 (17.1 m) y maxpoll tiene un valor predeterminado de 14 (4.5 h). El rango permitido es de 4 (16 s) a 17 (36.4 h), ambos inclusive.
fudge 127.127.t.u [time1 sec] [time2 sec] [stratum int] [refid string] [mode int] [flag1 0 | 1] [flag2 0 | 1] [flag3 0 | 1] [flag4 0 | 1]

Este comando se puede utilizar para configurar relojes de referencia de maneras especiales. Debe seguir inmediatamente al comando server que configura el controlador. Tenga en cuenta que la misma funcionalidad es posible en tiempo de ejecución utilizando el programa ntpdc(1). Las opciones se interpretan de la siguiente manera:
time1 sec

Especifica una constante que se añadirá al desfase de tiempo producido por el controlador, un número decimal de punto fijo en segundos. Se utiliza como constante de calibración para ajustar el desfase de tiempo nominal de un reloj particular para que coincida con un estándar externo, como una señal PPS de precisión. También proporciona una forma de corregir un error sistemático o un sesgo debido a latencias del puerto serie o del sistema operativo, diferentes longitudes de cable o retraso interno del receptor. El desfase especificado se suma al retraso de propagación proporcionado por otros medios, como los interruptores DIP internos. Cuando hay disponible una calibración para un sistema y controlador individual, se anota una corrección aproximada en las páginas de documentación del controlador. Nota: para facilitar la calibración cuando se soportan varios relojes de radio o señales PPS, hay disponible una característica especial de calibración. Toma la forma de un argumento al comando enable descrito en la página Opciones Misceláneas y opera como se describe en la página "Reference Clock Drivers" (disponible como parte de la documentación HTML proporcionada en /usr/share/doc/ntp).
time2 secs

Especifica un número decimal de punto fijo en segundos, que se interpreta de forma específica para el dispositivo. Consulte las descripciones de los controladores específicos en la página "Reference Clock Drivers" (disponible como parte de la documentación HTML proporcionada en /usr/share/doc/ntp).
stratum int

Especifica el número de estrato asignado al controlador, un entero entre 0 y 15. Este número anula el número de estrato predeterminado que normalmente asigna el propio controlador, generalmente cero.
refid string

Especifica una cadena ASCII de uno a cuatro caracteres que define el identificador de referencia utilizado por el controlador. Esta cadena anula el identificador predeterminado asignado normalmente por el propio controlador.
mode int

Especifica un número de modo que se interpreta de forma específica para el dispositivo. Por ejemplo, selecciona un protocolo de marcación en el controlador ACTS y un subtipo de dispositivo en los controladores de análisis.
flag1 0 | 1

flag2 0 | 1

flag3 0 | 1

flag4 0 | 1

Estas cuatro banderas se utilizan para personalizar el controlador del reloj. La interpretación de estos valores, y si se utilizan o no, es una función del controlador de reloj en particular. Sin embargo, por convención, flag4 se utiliza para habilitar el registro de datos de monitorización en el archivo clockstats configurado con el comando filegen. Encontrará más información sobre el comando filegen en Opciones de monitorización.

Opciones misceláneas

broadcastdelay seconds

Los modos de difusión y multidifusión requieren una calibración especial para determinar el retraso de la red entre los servidores locales y remotos. Normalmente, esto se hace automáticamente mediante los intercambios de protocolo iniciales entre el cliente y el servidor. En algunos casos, el procedimiento de calibración puede fallar debido a controles de acceso a la red o al servidor, por ejemplo. Este comando especifica el retraso predeterminado que se utilizará en estas circunstancias. Normalmente (para Ethernet), es apropiado un número entre 0.003 y 0.007 segundos. El valor predeterminado cuando no se utiliza este comando es 0.004 segundos.
driftfile driftfile

Este comando especifica la ruta completa y el nombre del archivo utilizado para registrar la frecuencia del oscilador de reloj local. Esta es la misma operación que la opción de línea de comandos -f. Si el archivo existe, se lee al inicio para establecer la frecuencia inicial y luego se actualiza una vez por hora con la frecuencia actual calculada por el demonio. Si se especifica el nombre del archivo, pero el archivo en sí no existe, comienza con una frecuencia inicial de cero y crea el archivo al escribirlo por primera vez. Si no se proporciona este comando, el demonio siempre comenzará con una frecuencia inicial de cero.

El formato del archivo consta de una sola línea que contiene un único número de punto flotante, que registra el desplazamiento de frecuencia medido en partes por millón (PPM). El archivo se actualiza escribiendo primero el valor de deriva actual en un archivo temporal y luego renombrando este archivo para reemplazar la versión antigua.

. Esto implica que ntpd(1) **debe tener permisos de escritura para el directorio donde se encuentra el archivo de deriva, y se deben evitar los enlaces del sistema de archivos, simbólicos o de otro tipo.**

dscp valor

Esta opción especifica el valor del Control Point de Servicios Diferenciados (DSCP), un código de 6 bits. El valor predeterminado es 46, lo que significa Expedited Forwarding.

disable [auth | bclient | calibrate | kernel | mode7 | monitor | ntp | stats | peer_clear_digest_early | unpeer_crypto_early | unpeer_crypto_nak_early | unpeer_digest_early]

Proporciona una forma de habilitar o deshabilitar varias opciones del servidor. Las banderas no mencionadas no se ven afectadas. Tenga en cuenta que todas estas banderas se pueden controlar de forma remota utilizando la utilidad ntpdc(1) .
auth

Permite que el servidor se sincronice con peers no configurados solo si el peer ha sido autenticado correctamente utilizando criptografía de clave pública o privada. El valor predeterminado para esta bandera es **enable**.
bclient

Permite que el servidor escuche un mensaje de un servidor de difusión o multidifusión, como en el comando **multicastclient** con la dirección predeterminada. El valor predeterminado para esta bandera es **disable**.
calibrate

Habilita la función de calibración para relojes de referencia. El valor predeterminado para esta bandera es **disable**.
kernel

Habilita la disciplina de tiempo del kernel, si está disponible. El valor predeterminado para esta bandera es **enable** si el soporte está disponible, de lo contrario es **disable**.
mode7

Permite el procesamiento de solicitudes específicas de la implementación del modo NTP 7, que son utilizadas por el programa obsoleto ntpdc(1) . El valor predeterminado para esta bandera es disable. Esta bandera se excluye de la configuración en tiempo de ejecución usando ntpq(1). El programa ntpq(1) proporciona las mismas capacidades que ntpdc(1) utilizando solicitudes estándar de modo 6.
monitor

Habilita la instalación de monitoreo. Consulte el programa ntpdc(1) y el comando monlist para obtener más información. El valor predeterminado para esta bandera es enable.
ntp

Habilita la disciplina de tiempo y frecuencia. En efecto, este interruptor abre y cierra el bucle de retroalimentación, lo cual es útil para probar. El valor predeterminado para esta bandera es **enable**.
peer_clear_digest_early

Por defecto, si ntpd(1) está usando autokey y recibe un paquete crypto-NAK que pasa las comprobaciones de paquetes duplicados y de marca de tiempo de origen, las variables del peer se borran inmediatamente. Aunque esto es generalmente una característica ya que permite una rápida recuperación si ha cambiado una clave del servidor, un paquete crypto-NAK forjado correctamente y entregado adecuadamente puede ser utilizado en un ataque DoS. Si tiene problemas notables y activos con este tipo de ataque DoS entonces debería considerar deshabilitar esta opción. Puede comprobar su archivo peerstats para obtener evidencia de cualquiera de estos ataques. El valor predeterminado para esta bandera es enable.
stats

Habilita la instalación de estadísticas. Consulte la sección Opciones de Monitoreo para obtener más información. El valor predeterminado para esta bandera es **disable**.
unpeer_crypto_early

Por defecto, si ntpd(1) recibe un paquete autokey que falla la PRUEBA9, una falla criptográfica, la asociación se borra inmediatamente. Esto es casi con certeza una característica, pero si, a pesar de la recomendación actual de no usar autokey, usted todavía está usando autokey y está viendo este tipo de ataque DoS, deshabilitar esta bandera retrasará la disolución de la asociación hasta que el contador de alcanzabilidad sea cero. Puede comprobar su archivo peerstats para obtener evidencia de cualquiera de estos ataques. El valor predeterminado para esta bandera es enable.
unpeer_crypto_nak_early

Por defecto, si ntpd(1) recibe un paquete crypto-NAK que pasa las comprobaciones de paquetes duplicados y de marca de tiempo de origen, la asociación se borra inmediatamente. Aunque esto es generalmente una característica ya que permite una rápida recuperación si ha cambiado una clave del servidor, un paquete crypto-NAK forjado correctamente y entregado adecuadamente puede ser utilizado en un ataque DoS. Si tiene problemas notables y activos con este tipo de ataque DoS entonces debería considerar deshabilitar esta opción. Puede comprobar su archivo peerstats para obtener evidencia de cualquiera de estos ataques. El valor predeterminado para esta bandera es enable.
unpeer_digest_early

Por defecto, si ntpd(1) recibe lo que debería ser un paquete autenticado que pasa otras comprobaciones de sanidad del paquete pero contiene un digest inválido, la asociación se borra inmediatamente. Aunque esto es generalmente una característica ya que permite una rápida recuperación, si este tipo de paquete se forja cuidadosamente y se envía durante una ventana apropiada, puede ser utilizado para un ataque DoS. Si tiene problemas notables y activos con este tipo de ataque DoS entonces debería considerar deshabilitar esta opción. Puede comprobar su archivo peerstats para obtener evidencia de cualquiera de estos ataques. El valor predeterminado para esta bandera es enable.
includefile archivoincluido

Este comando permite incluir comandos de configuración adicionales desde un archivo separado. Los archivos de inclusión pueden anidarse hasta una profundidad de cinco; al llegar al final de cualquier archivo de inclusión, el procesamiento de comandos se reanuda en el archivo de configuración anterior. Esta opción es útil para sitios que ejecutan ntpd(1) en varios hosts, con opciones (mayormente) comunes (por ejemplo, una lista de restricciones).
interface [listen | ignore | drop] [all | ipv4 | ipv6 | wildcard nombre | dirección [/ longitudprefijo]]

La directiva **interface** controla qué direcciones de red abre ntpd(1) , y si la entrada se descarta sin procesamiento. El primer parámetro determina la acción para las direcciones que coinciden con el segundo parámetro. El segundo parámetro especifica una clase de direcciones, o un nombre de interfaz específico, o una dirección. En el caso de la dirección, longitudprefijo determina cuántos bits deben coincidir para que esta regla se aplique. ignore impide abrir direcciones coincidentes, drop hace que ntpd(1) abra la dirección y descarte todos los paquetes recibidos sin examen. Se pueden usar múltiples directivas interface . La última regla que coincide con una dirección particular determina la acción para ella. Las directivas interface se deshabilitan si se especifican opciones de línea de comandos -I, --interface, -L, o --novirtualips en el archivo de configuración, se abren todas las direcciones de red disponibles. La directiva nic es un alias para interface.
leapfile archivobisesto

Este comando carga el archivo de segundos intercalares de la IERS e inicializa los valores de los segundos intercalares para el próximo evento de segundo intercalar, el tiempo de expiración del archivo intercalar y el desplazamiento del TAI. El archivo se puede obtener directamente de la IERS en https://hpiers.obspm.fr/iers/bul/bulc/ntp/leap-seconds.list o ftp://hpiers.obspm.fr/iers/bul/bulc/ntp/leap-seconds.list. El leapfile se escanea cuando ntpd(1) procesa la directiva leapfile o cuando ntpd detecta que el archivobisesto ha cambiado. ntpd comprueba una vez al día para ver si el archivobisesto ha cambiado. El script update-leap(1update_leapmdoc) puede ejecutarse para ver si el archivobisesto debería actualizarse.
leapsmearinterval segundos

Esta opción EXPERIMENTAL solo está disponible si ntpd(1) se compiló con la opción --enable-leap-smear para el script configure . Especifica el intervalo durante el cual se aplicará una corrección de segundo intercalar. Los valores recomendados para esta opción están entre 7200 (2 horas) y 86400 (24 horas). Consulte http://bugs.ntp.org/2855 para más información.
logconfig palabraclaveconfig

Este comando controla la cantidad y el tipo de salida escrita en el syslog del sistema(3) instalación o el alternativo logfile archivo de registro. Por defecto, toda la salida está activada. Todas las configkeyword palabras clave pueden ser prefijadas con ‘=’, ‘+’ y ‘-’, donde ‘=’ establece la syslog(3) máscara de prioridad, ‘+’ añade y ‘-’ elimina mensajes. syslog(3) los mensajes pueden ser controlados en cuatro clases (clock, peer, sys y sync). Dentro de estas clases se pueden controlar cuatro tipos de mensajes: mensajes informativos (info), mensajes de eventos (events), mensajes de estadísticas (statistics) y mensajes de estado (status).

Las palabras clave de configuración se forman concatenando la clase de mensaje con la clase de evento. El prefijo all puede ser usado en lugar de una clase de mensaje. Una clase de mensaje también puede ser seguida de la palabra clave all para habilitar/deshabilitar todos los mensajes de la clase de mensaje respectiva. Así, una configuración mínima de registro podría verse así:



logconfig =syncstatus +sysevents

Esto solo listará el estado de sincronización de ntpd(1) y los eventos importantes del sistema. Para un servidor de referencia simple, la siguiente configuración mínima de mensajes podría ser útil:



logconfig =syncall +clockall

Esta configuración listará toda la información del reloj y la información de sincronización. Todos los demás eventos y mensajes sobre pares, eventos del sistema y demás se suprimen.

logfile logfile

Este comando especifica la ubicación de un archivo de registro alternativo que se utilizará en lugar de la instalación syslog(3) del sistema por defecto. Esta es la misma operación que la opción de línea de comandos -l.
mru [maxdepth count | maxmem kilobytes | mindepth count | maxage seconds | initialloc count | initmem kilobytes | incalloc count | incmem kilobytes]

Controla los límites de tamaño de la lista de direcciones de clientes (MRU - Most Recently Used) de la instalación de monitoreo, que también es utilizada por la instalación de control de tasa.
maxdepth count

maxmem kilobytes

Límites superiores equivalentes para el tamaño de la lista MRU, en términos de entradas o kilobytes. El límite real será hasta incalloc entradas o incmem kilobytes más. Como con todas las opciones de mru ofrecidas en unidades de entradas o kilobytes, si se utilizan tanto maxdepth como maxmem, la última utilizada controla. El valor por defecto es 1024 kilobytes.
mindepth count

Límite inferior para el tamaño de la lista MRU. Cuando la lista MRU tiene menos de mindepth entradas, las entradas existentes nunca se eliminan para dar cabida a otras más nuevas, independientemente de su antigüedad. El valor por defecto es 600 entradas.
maxage seconds

Una vez que la lista MRU tiene mindepth entradas y se debe añadir un cliente adicional a la lista, si la entrada más antigua se actualizó hace más de maxage segundos, esa entrada se elimina y su almacenamiento se reutiliza. Si la entrada más antigua se actualizó más recientemente, la lista MRU crece, sujeto a maxdepth / moxmem. El valor por defecto es 64 segundos.
initalloc count

initmem kilobytes

Asignación inicial de memoria en el momento en que se habilita por primera vez la instalación de monitoreo, en términos de número de entradas o kilobytes. El valor por defecto es 4 kilobytes.
incalloc count

incmem kilobytes

Tamaño de las asignaciones de memoria adicionales al crecer la lista MRU, en entradas o kilobytes. El valor por defecto es 4 kilobytes.
nonvolatile threshold

Especifica el umbral de delta en segundos antes de que se escriba un cambio horario en el driftfile (archivo de frecuencia), con un valor predeterminado de 1e-7 (0.1 PPM). El archivo de frecuencia se inspecciona cada hora. Si la diferencia entre la frecuencia actual y el último valor escrito excede el umbral, el archivo se escribe y el umbral se convierte en el nuevo valor del umbral. Si no se supera el umbral, se reduce a la mitad. Esto está diseñado para reducir el número de escrituras de archivos en sistemas embebidos con memoria no volátil.
phone dial ...

Este comando se utiliza junto con el controlador de módem ACTS (tipo 18) o el controlador JJY (tipo 40, modo 100 - 180). Para el controlador de módem ACTS (tipo 18), los argumentos consisten en un máximo de 10 números telefónicos utilizados para marcar a USNO, NIST o servicios de tiempo europeos. Para el controlador JJY (tipo 40 modo 100 - 180), el argumento es un número de teléfono utilizado para marcar el servicio telefónico JJY. Normalmente, el comando de Hayes ATDT se antepone al número. El número puede contener otros códigos de control de módem.
pollskewlist [poll early late] ... [default early late]

Habilita el sesgo de nuestras solicitudes de sondeo a nuestros servidores. poll es un número entre 3 y 17 inclusive, que identifica un intervalo de sondeo específico. Un intervalo de sondeo dura 2^n segundos, por lo que un valor de sondeo de 3 corresponde a 8 segundos y un intervalo de sondeo de 17 corresponde a 131,072 segundos, o aproximadamente un día y medio. Los dos siguientes números deben estar entre 0 y la mitad del intervalo de sondeo, inclusive. Ar early especifica cuán temprano puede comenzar el sondeo, mientras que Ar late especifica cuán tarde puede retrasarse el sondeo. Sin argumentos, se eligen valores predeterminados especificados internamente.
reset [allpeers] [auth] [ctl] [io] [mem] [sys] [timer]

Restablece uno o más grupos de contadores mantenidos por ntpd y expuestos por ntpq y ntpdc.
rlimit [memlock Nmegabytes | stacksize N4kPages filenum Nfiledescriptors]

memlock Nmegabytes

Especifica la cantidad de megabytes de memoria que deben ser asignados y bloqueados. Probablemente solo disponible en Linux, esta opción puede ser útil al renunciar a root (la opción -i). El valor predeterminado es de 32 megabytes en máquinas que no son Linux, y -1 en Linux. -1 significa "no bloquear el proceso en memoria". 0 significa "bloquear en memoria toda la memoria que el proceso desee".
stacksize N4kPages

Especifica el tamaño máximo de la pila del proceso en sistemas con la función mlockall(). Por defecto son 50 páginas de 4k (200 páginas de 4k en OpenBSD).
filenum Nfiledescriptors

Especifica el número máximo de descriptores de archivo que ntpd puede tener abiertos a la vez. Por defecto es el predeterminado del sistema.
saveconfigdir directory_path

Especifica el directorio en el que se escribirán las instantáneas de configuración solicitadas con el comando saveconfig. Si saveconfigdir no aparece en el archivo de configuración, las solicitudes de saveconfig son rechazadas por ntpd.
saveconfig filename

Escribe la configuración actual, incluyendo cualquier modificación en tiempo de ejecución dada con :config o config-from-file, en el nombre de archivo del host ntpd en el saveconfigdir. Este comando será rechazado a menos que la directiva saveconfigdir aparezca en el archivo de configuración. filename puede usar las directivas de formato de strftime(3) para sustituir la fecha y hora actuales, por ejemplo, saveconfig ntp-%Y%m%d-%H%M%S.conf. El nombre de archivo utilizado se almacena en la variable del sistema savedconfig. Se requiere autenticación.
setvar variable [default]

Este comando añade una variable de sistema adicional. Estas variables se pueden utilizar para distribuir información adicional como la política de acceso. Si la variable del formulario nombre=valor va seguida de la palabra clave default, la variable se listará como parte de las variables del sistema predeterminadas (comando rv de ntpq(1))). Estas variables adicionales son solo para fines informativos. No están relacionadas con el protocolo más que por el hecho de que pueden ser listadas. Las variables de protocolo conocidas siempre anularán cualquier variable definida a través del mecanismo setvar. Hay tres variables especiales que contienen los nombres de todas las variables del mismo grupo. La sys_var_list contiene los nombres de todas las variables del sistema. La peer_var_list contiene los nombres de todas las variables de pares y la clock_var_list contiene los nombres de las variables del reloj de referencia.
sysinfo

Muestra un resumen operativo.
sysstats

Muestra los contadores de estadísticas mantenidos en el módulo de protocolo.

COMANDOS

dd

Este comando se puede utilizar para alterar varias variables del sistema en circunstancias muy excepcionales. Debe aparecer en el archivo de configuración antes que cualquier otra opción de configuración. Los valores predeterminados de estas variables han sido cuidadosamente optimizados para una amplia gama de velocidades de red y expectativas de fiabilidad. En general, interactúan de formas intrincadas que son difíciles de predecir y algunas combinaciones pueden dar lugar a comportamientos muy desagradables. Muy raramente es necesario cambiar los valores predeterminados; sin embargo, a algunos les resulta imposible resistirse a manipularlos y este comando es para ellos. Se enfatiza: los manipuladores están solos y no pueden esperar ayuda del grupo de soporte.

Las variables funcionan de la siguiente manera:

allan allan

El argumento se convierte en el nuevo valor para el intercepto de Allan mínimo, que es un parámetro del algoritmo de disciplina de reloj PLL/FLL. El valor en log2 segundos por defecto es 7 (1024 s), que también es el límite inferior.
dispersion dispersion

El argumento se convierte en el nuevo valor para la tasa de aumento de la dispersión, normalmente 0.000015 s/s.
freq freq

El argumento se convierte en el valor inicial del desplazamiento de frecuencia en partes por millón. Esto anula el valor del archivo de frecuencia, si está presente, y evita el estado de entrenamiento inicial si no lo está.
huffpuff huffpuff

El argumento se convierte en el nuevo valor para el lapso experimental del filtro huff-n'-puff, que determina el intervalo más reciente que el algoritmo buscará para un retardo mínimo. El límite inferior es 900 s (15 m), pero un valor más razonable es 7200 (2 horas). No hay un valor predeterminado, ya que el filtro no se habilita a menos que se proporcione este comando.
panic panic

El argumento es el umbral de pánico, normalmente 1000 s. Si se establece en cero, la verificación de cordura de pánico se deshabilita y se aceptará un desplazamiento de reloj de cualquier valor.
step step

El argumento es el umbral de paso, que por defecto es 0.128 s. Se puede establecer en cualquier número positivo en segundos. Si se establece en cero, los ajustes de paso nunca ocurrirán. Nota: La disciplina de tiempo del kernel se deshabilita si el umbral de paso se establece en cero o es mayor que el valor predeterminado.
stepback stepback

El argumento es el umbral de paso para la dirección hacia atrás, que por defecto es 0.128 s. Se puede establecer en cualquier número positivo en segundos. Si tanto los umbrales de paso hacia adelante como hacia atrás se establecen en cero, los ajustes de paso nunca ocurrirán. Nota: La disciplina de tiempo del kernel se deshabilita si cada dirección del umbral de paso se establece en cero o es mayor que 0.5 segundos.
stepfwd stepfwd

Como para stepback, pero para la dirección hacia adelante.
stepout stepout

El argumento es el tiempo de espera de stepout, que por defecto es 900 s. Se puede establecer en cualquier número positivo en segundos. Si se establece en cero, los pulsos de stepout no se suprimirán.
writevar assocID name = value [,...]

Escribe (crea o actualiza) las variables especificadas. Si el assocID es cero, las variables provienen del espacio de nombres de variables del sistema, de lo contrario, provienen del espacio de nombres de variables del par. Se requiere el assocID, ya que el mismo nombre puede aparecer en ambos espacios de nombres.
trap dirección_host [port número_puerto] [interface dirección_interfaz]

Este comando configura un receptor de trampa en la dirección de host y el número de puerto dados para enviar mensajes con la dirección de interfaz local especificada. Si el número de puerto no se especifica, se utiliza el valor 18447. Si la dirección de la interfaz no se especifica, el mensaje se envía con una dirección de origen de la interfaz local a través de la cual se envía el mensaje. Tenga en cuenta que en un host multihoming, la interfaz utilizada puede variar de vez en cuando con los cambios de enrutamiento.
ttl hop ...

Este comando especifica una lista de valores TTL en orden creciente. Se pueden especificar hasta 8 valores. En el modo manycast, estos valores se utilizan por turnos en una búsqueda de anillo expansivo. El valor predeterminado son ocho múltiplos de 32 comenzando en 31.

El receptor de trampa generalmente registrará mensajes de eventos y otra información del servidor en un archivo de registro. Si bien dichos programas de monitoreo también pueden solicitar sus propias trampas dinámicamente, configurar un receptor de trampa asegurará que no se pierdan mensajes cuando se inicie el servidor.
