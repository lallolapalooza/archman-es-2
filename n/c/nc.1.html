NC(1) Manual de comandos generales NC(1)

NOMBRE

nc — conexiones y escucha arbitrarias de TCP y UDP

SINOPSIS

nc [-46bCDdFhklNnrStUuvZz] [-I longitud] [-i intervalo] [-M ttl] [-m minttl] [-O longitud] [-P nombre_usuario_proxy] [-p puerto_origen] [-q segundos] [-s direccion_origen] [-T palabra_clave] [-V tabla_enrutamiento] [-W limite_recepcion] [-w tiempo_espera] [-X protocolo_proxy] [-x direccion_proxy[:puerto]] [destino] [puerto]

DESCRIPCIÓN

La utilidad nc (o netcat) se utiliza para prácticamente cualquier cosa que involucre sockets TCP, UDP o de dominio UNIX. Puede abrir conexiones TCP, enviar paquetes UDP, escuchar en puertos TCP y UDP arbitrarios, escanear puertos y tratar tanto con IPv4 como con IPv6. A diferencia de telnet(1), nc se puede usar en scripts de forma agradable y separa los mensajes de error en la salida estándar de error en lugar de enviarlos a la salida estándar, como hace telnet(1) con algunos.

Los usos comunes incluyen:

  • proxies TCP simples
  • clientes y servidores HTTP basados en scripts shell
  • pruebas de demonios de red
  • un ProxyCommand SOCKS o HTTP para ssh(1)
  • y mucho más

Las opciones son las siguientes:

-4
Usar solo direcciones IPv4.
-6
Usar solo direcciones IPv6.
-b
Permitir difusión (broadcast).
-C
Enviar CRLF como fin de línea. Cada salto de línea (LF) de los datos de entrada se traduce a CR+LF antes de escribirse en el socket. Los saltos de línea que ya van precedidos por un retorno de carro (CR) no se traducen. Los datos recibidos no se ven afectados.
-D
Habilitar la depuración en el socket.
-d
No intentar leer desde stdin.
-F
Pasar el primer socket conectado usando sendmsg(2) a stdout y salir. Esto es útil en combinación con -X para que nc realice la configuración de la conexión con un proxy, pero deje el resto de la conexión a otro programa (por ejemplo, ssh(1) usando la opción ProxyUseFdpass de ssh_config(5)). No se puede usar con -U.
-h
Mostrar el texto de ayuda de nc y salir.
-I longitud
Especificar el tamaño del búfer de recepción TCP.
-i intervalo
Esperar intervalo segundos entre líneas de texto enviadas y recibidas. También causa un tiempo de espera entre conexiones a múltiples puertos.
-k
Cuando se completa una conexión, escuchar para otra. Requiere -l. Cuando se usa junto con la opción -u, el socket del servidor no está conectado y puede recibir datagramas UDP de múltiples hosts.
-l
Escuchar una conexión entrante en lugar de iniciar una conexión a un host remoto. El destino y el puerto a escuchar se pueden especificar como argumentos no opcionales, o con las opciones -s y -p respectivamente. No se puede usar junto con -x o -z. Además, se ignoran los tiempos de espera especificados con la opción -w.
-M ttl
Establecer el TTL / límite de saltos de los paquetes salientes.
-m minttl
Pedir al kernel que descarte los paquetes entrantes cuyo TTL / límite de saltos esté por debajo de minttl.
-N
Cerrar (shutdown(2)) el socket de red después de EOF en la entrada. Algunos servidores requieren esto para finalizar su trabajo.
-n
No realizar resolución de nombres de dominio. Si un nombre no se puede resolver sin DNS, se informará un error.
-O longitud
Especificar el tamaño del búfer de envío TCP.
-P nombre_usuario_proxy
Especifica un nombre de usuario para presentarlo a un servidor proxy que requiere autenticación. Si no se especifica ningún nombre de usuario, no se intentará la autenticación. La autenticación de proxy solo se admite para proxies HTTP CONNECT en este momento.
-p puerto_origen
Especificar el puerto de origen que debe usar nc, sujeto a restricciones de privilegios y disponibilidad.
-q segundos
después de EOF en stdin, esperar el número especificado de segundos y luego salir. Si segundos es negativo, esperar para siempre (por defecto). Especificar un segundos no negativo implica -N.
-r
Elegir puertos de origen y/o destino aleatoriamente en lugar de secuencialmente dentro de un rango o en el orden en que el sistema se los asigna.
-S
Habilitar la opción de firma TCP MD5 RFC 2385.
-s direccion_origen
Establecer la dirección de origen desde la que se enviarán los paquetes, lo que es útil en máquinas con múltiples interfaces. Para sockets de datagramas de dominio UNIX, especifica el archivo de socket temporal local a crear y usar para que se puedan recibir datagramas. No se puede usar junto con -x.
-T palabra_clave
Cambiar el valor TOS de IPv4 / clase de tráfico de IPv6. palabra_clave puede ser uno de critical, inetcontrol, lowcost, lowdelay, netcontrol, throughput, reliability, o uno de los DiffServ Code Points: ef, af11 ... af43, cs0 ... cs7; o un número en hexadecimal o decimal.
-t
Enviar respuestas DON'T y WON'T de RFC 854 a las solicitudes DO y WILL de RFC 854. Esto hace posible usar nc para crear scripts de sesiones de telnet.
-U
Usar sockets de dominio UNIX. No se puede usar junto con -F o -x. En Linux, si el nombre comienza con un símbolo arroba (`@'), se lee como un socket de espacio de nombres abstracto: el `@' inicial se reemplaza con un byte NUL antes de vincular o conectar. Para más detalles, ver unix(7).
-u
Usar UDP en lugar de TCP. No se puede usar junto con -x. Para sockets de dominio UNIX, usar un socket de datagrama en lugar de un socket de flujo. Si se usa un socket de dominio UNIX, se crea un socket de recepción temporal en /tmp a menos que se proporcione la bandera -s.
-V rtable
Establecer la tabla de enrutamiento a usar.
-v
Producir una salida más detallada.
-W recvlimit
Terminar después de recibir recvlimit paquetes de la red.
-w timeout
Las conexiones que no se puedan establecer o estén inactivas expirarán después de timeout segundos. La bandera -w no tiene efecto en la opción -l, es decir, nc escuchará indefinidamente por una conexión, con o sin la bandera -w. El valor predeterminado es sin tiempo de espera.
-X proxy_protocol
Usar proxy_protocol al comunicarse con el servidor proxy. Los protocolos soportados son 4 (SOCKS v.4), 4A (SOCKS v.4A), 5 (SOCKS v.5) y connect (proxy HTTPS). Si no se especifica el protocolo, se usa SOCKS versión 5. Ten en cuenta que el protocolo SOCKS v.4 es muy limitado y solo se puede usar cuando el host de destino se puede resolver a una dirección IPv4. Los otros protocolos pasan el destino como una cadena para ser interpretada por el proxy remoto y no tienen esta limitación.
-x proxy_address[:port]
Conectar a destination usando un proxy en proxy_address y port. Si no se especifica port, se usa el puerto bien conocido para el protocolo proxy (1080 para SOCKS, 3128 para HTTPS). Se puede especificar una dirección IPv6 de forma inequívoca encerrando proxy_address entre corchetes. Un proxy no se puede usar con ninguna de las opciones -lsuU.
-Z
Modo DCCP.
-z
Solo escanear demonios en escucha, sin enviarles ningún dato. No se puede usar junto con -l.

destination puede ser una dirección IP numérica o un nombre de host simbólico (a menos que se proporcione la opción -n). En general, se debe especificar un destino, a menos que se proporcione la opción -l (en cuyo caso se usa el host local). Para sockets de dominio UNIX, se requiere un destino y es la ruta del socket al que conectar (o en el que escuchar si se proporciona la opción -l).

port se puede especificar como un número de puerto numérico o como un nombre de servicio. Los rangos de puertos se pueden especificar como números de puerto numéricos de la forma nn-mm. En general, se debe especificar un puerto de destino, a menos que se proporcione la opción -U. Para algunas opciones, el valor 0 solicita que el sistema elija un número de puerto.

MODELO CLIENTE/SERVIDOR

Es bastante simple construir un modelo básico de cliente/servidor usando nc. En una consola, inicia nc escuchando en un puerto específico para una conexión. Por ejemplo:

$ nc -l 1234

nc está ahora escuchando en el puerto 1234 para una conexión. En una segunda consola (o una segunda máquina), conéctate a la máquina y al puerto en el que se está escuchando:

$ nc -N 127.0.0.1 1234

Ahora debería haber una conexión entre los puertos. Todo lo que se escriba en la segunda consola se concatenará a la primera, y viceversa. Después de que la conexión se haya establecido, nc no realmente le importa qué lado se usa como 'servidor' y cuál como 'cliente'. La conexión puede terminarse usando un EOF ('^D'), ya que se proporcionó la bandera -N.

No hay una opción -c o -e en este netcat, pero aún puedes ejecutar un comando después de que se establezca la conexión redirigiendo descriptores de archivo. Ten cuidado aquí porque abrir un puerto y permitir que cualquiera que se conecte ejecute comandos arbitrarios en tu sitio es PELIGROSO. Si realmente necesitas hacer esto, aquí tienes un ejemplo:

En el lado del 'servidor':

$ rm -f /tmp/f; mkfifo /tmp/f
$ cat /tmp/f | /bin/sh -i 2>&1 | nc -l 127.0.0.1 1234 > /tmp/f

En el lado del 'cliente':

$ nc host.example.com 1234
$ (prompt del shell desde host.example.com)

Al hacer esto, creas un fifo en /tmp/f y haces que nc escuche en el puerto 1234 de la dirección 127.0.0.1 en el lado del 'servidor', cuando un 'cliente' establece una conexión exitosa a ese puerto, /bin/sh se ejecuta en el lado del 'servidor' y el prompt del shell se da al lado del 'cliente'.

Cuando la conexión se termina, nc también sale. Usa -k si quieres que siga escuchando, pero si el comando sale, esta opción no lo reiniciará ni mantendrá nc en ejecución. Tampoco olvides eliminar el descriptor de archivo una vez que ya no lo necesites:

$ rm -f /tmp/f

TRANSFERENCIA DE DATOS

El ejemplo en la sección anterior se puede expandir para construir un modelo básico de transferencia de datos. Cualquier información introducida en un extremo de la conexión se emitirá al otro extremo, y la entrada y salida se pueden capturar fácilmente para emular la transferencia de archivos.

Comienza usando nc para escuchar en un puerto específico, con la salida capturada en un archivo:

$ nc -l 1234 > nombre_archivo.out

Usando una segunda máquina, conéctate al proceso nc que está escuchando, alimentándolo con el archivo que se va a transferir:

$ nc -N host.example.com 1234 < nombre_archivo.in

Después de que el archivo se haya transferido, la conexión se cerrará automáticamente.

COMUNICACIÓN CON SERVIDORES

A veces es útil comunicarse con servidores "manualmente" en lugar de a través de una interfaz de usuario. Puede ayudar en la solución de problemas, cuando podría ser necesario verificar qué datos envía un servidor en respuesta a los comandos emitidos por el cliente. Por ejemplo, para recuperar la página principal de un sitio web:

$ printf "GET / HTTP/1.0\r\n\r\n" | nc host.example.com 80

Ten en cuenta que esto también muestra las cabeceras enviadas por el servidor web. Se pueden filtrar, usando una herramienta como sed(1), si es necesario.

Se pueden construir ejemplos más complicados cuando el usuario conoce el formato de las solicitudes requeridas por el servidor. Como otro ejemplo, se puede enviar un correo electrónico a un servidor SMTP usando:

$ nc [-C] localhost 25 << EOF
HELO host.example.com
MAIL FROM:<user@host.example.com>
RCPT TO:<user2@host.example.com>
DATA
Cuerpo del correo electrónico.
.
QUIT
EOF

ESCaneo DE PUERTOS

Puede ser útil saber qué puertos están abiertos y ejecutando servicios en una máquina objetivo. La bandera -z se puede usar para indicar a nc que informe sobre puertos abiertos, en lugar de iniciar una conexión. Por lo general, es útil activar la salida detallada en stderr usando esta opción junto con la opción -v.

Por ejemplo:

$ nc -zv host.example.com 20-30
Connection to host.example.com 22 port [tcp/ssh] succeeded!
Connection to host.example.com 25 port [tcp/smtp] succeeded!

Se especificó el rango de puertos para limitar la búsqueda a los puertos 20 - 30, y se escanea en orden creciente (a menos que se establezca la bandera -r).

También puedes especificar una lista de puertos para escanear, por ejemplo:

$ nc -zv host.example.com http 20 22-23
nc: connect to host.example.com 80 (tcp) failed: Connection refused
nc: connect to host.example.com 20 (tcp) failed: Connection refused
Connection to host.example.com port [tcp/ssh] succeeded!
nc: connect to host.example.com 23 (tcp) failed: Connection refused

Los puertos se escanean en el orden que proporciones (a menos que se establezca la bandera -r).

Alternativamente, podría ser útil saber qué software de servidor se está ejecutando y qué versiones. Esta información a menudo se encuentra dentro de los banners de saludo. Para recuperarlos, es necesario primero establecer una conexión y luego romper la conexión cuando se haya recuperado el banner. Esto se puede lograr especificando un tiempo de espera corto con la bandera -w, o quizás emitiendo un comando "QUIT" al servidor:

$ echo "QUIT" | nc host.example.com 20-30
SSH-1.99-OpenSSH_3.6.1p2
Protocol mismatch.
220 host.example.com IMS SMTP Receiver Version 0.84 Ready

EJEMPLOS

EJEMPLOS

Abrir una conexión TCP al puerto 42 de host.example.com, usando el puerto 31337 como puerto de origen, con un tiempo de espera de 5 segundos:

$ nc -p 31337 -w 5 host.example.com 42

Abrir una conexión UDP al puerto 53 de host.example.com:

$ nc -u host.example.com 53

Abrir una conexión TCP al puerto 42 de host.example.com usando 10.1.2.3 como la IP para el extremo local de la conexión:

$ nc -s 10.1.2.3 host.example.com 42

Crear y escuchar en un socket de flujo de dominio UNIX:

$ nc -lU /var/tmp/dsocket

Conectar al puerto 42 de host.example.com a través de un proxy HTTP en 10.2.3.4, puerto 8080. Este ejemplo también podría ser utilizado por ssh(1); ver la directiva ProxyCommand en ssh_config(5) para más información.

$ nc -x10.2.3.4:8080 -Xconnect host.example.com 42

El mismo ejemplo de nuevo, esta vez habilitando la autenticación de proxy con el nombre de usuario "ruser" si el proxy lo requiere:

$ nc -x10.2.3.4:8080 -Xconnect -Pruser host.example.com 42

ADVERTENCIAS

Los escaneos de puertos UDP utilizando la combinación -uz de flags informarán siempre éxito independientemente del estado de la máquina de destino. Sin embargo, junto con un sniffer de tráfico ya sea en la máquina de destino o en un dispositivo intermedio, la combinación -uz podría ser útil para diagnósticos de comunicación. Tenga en cuenta que la cantidad de tráfico UDP generado puede estar limitada ya sea por recursos de hardware y/o por ajustes de configuración.
