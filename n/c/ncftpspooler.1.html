ncftpspooler(1) Manual de Comandos Generales ncftpspooler(1)

NOMBRE

ncftpspooler - Demonio procesador global de trabajos FTP por lotes

SINOPSIS

ncftpspooler -d [opciones]

ncftpspooler -l [opciones]

OPCIONES

Indicadores de línea de comandos:

-d
Inicia el procesamiento en segundo plano de trabajos FTP en el directorio designado de la cola de trabajos FTP.
-q XX
Utilice esta opción para especificar un directorio como cola de trabajos FTP en lugar del directorio predeterminado, /var/spool/ncftp.
-o XX
Utilice esta opción para especificar un nombre de archivo como archivo de registro. Por defecto, (y de forma bastante inapropiada) el programa simplemente utiliza un archivo llamado log en el directorio de la cola de trabajos. Si no desea un registro, utilice esta opción para especificar /dev/null.
-l
Lista el contenido del directorio de la cola de trabajos.
-s XX
Cuando la cola de trabajos está vacía, el programa duerme 120 segundos y luego verifica nuevamente si se ha enviado un nuevo trabajo. Utilice esta opción para cambiar el número de segundos de esta demora.

DESCRIPCIÓN

El programa ncftpspooler evolucionó del programa ncftpbatch. El programa ncftpbatch fue diseñado originalmente como un "spooler FTP personal" que procesaría un solo trabajo en segundo plano para un usuario particular y saldría al finalizar; el programa ncftpspooler es un "spooler FTP global" que permanece en ejecución y procesa trabajos en segundo plano a medida que se envían.

El directorio de la cola de trabajos se supervisa para detectar archivos de texto con nombres y formatos especiales. Cada archivo sirve como un trabajo FTP individual. El nombre del archivo del trabajo contiene el tipo de trabajo FTP (get o put), una marca de tiempo que indica el momento más temprano en que el trabajo debe ser procesado y, opcionalmente, información adicional para facilitar la creación de archivos de trabajo únicos (por ejemplo, un número de secuencia). El contenido de los archivos de trabajo tiene información como la máquina del servidor remoto a la que conectarse por FTP, el nombre de usuario, la contraseña, la ruta remota, etc.

Su directorio de cola de trabajos debe ser legible y escribible por el usuario con el que planea ejecutar ncftpspooler, para que los trabajos puedan ser eliminados o renombrados dentro de la cola.

Más importante aún, el usuario que ejecuta el programa necesitará privilegios adecuados para acceder a los archivos locales involucrados en la transferencia FTP. Es decir, si su spooler va a procesar trabajos que suben archivos a servidores remotos, el usuario necesitará permiso de lectura en los archivos locales que se subirán (y permiso de acceso a los directorios padre). De manera similar, si su spooler va a procesar trabajos que descargan archivos, el usuario deberá poder escribir en los directorios locales.

Una vez que haya creado su directorio de spool con los permisos y la propiedad apropiados, puede ejecutar ncftpspooler -d para iniciar el demonio spooler. Puede ejecutar spoolers adicionales si desea procesar más de un trabajo FTP de la misma cola de trabajos simultáneamente. Luego puede monitorear el archivo de registro (por ejemplo, usando tail -f ) para seguir el progreso del spooler. La mayor parte del tiempo no estará haciendo nada, a menos que aparezcan archivos de trabajo en el directorio de la cola de trabajos.

NOMBRES DE ARCHIVOS DE TRABAJO

Cuando el programa ncftpspooler supervisa el directorio de la cola de trabajos, ignora cualquier archivo que no siga la convención de nomenclatura para archivos de trabajo. Los archivos de trabajo deben prefijarse en el formato X-AAAAMMDD-hhmmss donde X denota un tipo de trabajo, AAAA es el año de cuatro dígitos, MM es el número de mes de dos dígitos, DD es el día del mes de dos dígitos, hh es la hora del día de dos dígitos (00-23), mm es el minuto de dos dígitos y ss es el segundo de dos dígitos. La fecha y hora representan el momento más temprano en que desea que se ejecute el trabajo.

El tipo de trabajo puede ser g para un trabajo de obtención (descarga desde el host remoto), o p para un trabajo de envío (carga al host remoto).

Como ejemplo, si quisiera programar una carga para que ocurra a las 23:45 del 7 de diciembre de 2001, un archivo de trabajo podría llamarse

p-20011207-234500

En la práctica, los archivos de trabajo incluyen información adicional como un número de secuencia o un ID de proceso. Esto facilita la creación de nombres de archivos de trabajo únicos. Aquí está el mismo ejemplo, con un ID de proceso y un número de secuencia:

p-20011207-234500-1234-2

Al enviar archivos de trabajo al directorio de la cola, asegúrese de usar un guion después del campo hhmmss si elige agregar datos adicionales al nombre del archivo de trabajo.

CONTENIDO DEL ARCHIVO DE TRABAJO

Los archivos de trabajo son archivos de texto normales, por lo que pueden ser creados manualmente. Cada línea del archivo es un par clave-valor en el formato variable=valor, o es una línea de comentario que comienza con un carácter de almohadilla (#), o es una línea en blanco. Aquí hay un ejemplo de archivo de trabajo:

# Esta es una entrada de archivo de spool de NcFTP.
job-name=g-20011016-100656-008299-1
op=get
hostname=ftp.freebsd.org
xtype=I
passive=1
remote-dir=pub/FreeBSD
local-dir=/tmp
remote-file=README.TXT
local-file=readme.txt

Los archivos de trabajo son flexibles ya que siguen un formato fácil de usar y no tienen muchos requisitos, pero hay algunos parámetros obligatorios que deben aparecer para que el spooler pueda procesar el trabajo.

op
La operación (tipo de trabajo) a realizar. Los valores válidos son get y put.
hostname
El host remoto al que conectarse por FTP. Puede ser una dirección IP o un nombre DNS (por ejemplo, ftp.example.com).

Para un trabajo get normal, se requieren estos parámetros:

remote-file
La ruta del archivo a descargar desde el servidor remoto.
local-file
La ruta a usar en el servidor local para el archivo descargado.

Para un trabajo put normal, se requieren estos parámetros:

local-file
La ruta del archivo a subir al servidor remoto.
remote-file
La ruta a usar en el servidor remoto para el archivo subido.

Para un trabajo get recursivo, se requieren estos parámetros:

remote-file
La ruta del archivo o directorio a descargar desde el servidor remoto.
local-dir
La ruta del directorio a usar en el servidor local para contener los elementos descargados.

Para un trabajo put recursivo, se requieren estos parámetros:

local-file
La ruta del archivo o directorio a subir al servidor remoto.
remote-dir
La ruta del directorio a usar en el servidor remoto para contener los elementos subidos.

El resto de los parámetros son opcionales. El spooler intentará usar valores predeterminados razonables para estos parámetros si es necesario.

user
El nombre de usuario a usar para iniciar sesión en el servidor remoto. Por defecto es ``anonymous'' para acceso de invitado.
pass
La contraseña a usar junto con el nombre de usuario para iniciar sesión en el servidor remoto.
acct
La cuenta a usar junto con el nombre de usuario para iniciar sesión en el servidor remoto. La necesidad de especificar este parámetro es extremadamente rara.
port
port
El número de puerto que se utilizará junto con el nombre de host remoto para conectarse al servidor remoto. El valor predeterminado es el número de puerto FTP estándar, 21.
host-ip
La dirección IP que se utilizará junto con el nombre de host remoto para conectarse al servidor remoto. Este parámetro puede usarse en lugar del parámetro hostname, pero se debe usar uno u otro. Este parámetro se incluye comúnmente junto con el parámetro hostname como información suplementaria.
xtype
El tipo de transferencia a utilizar. El valor predeterminado es el tipo de transferencia binaria (TYPE I). Los valores válidos son I para binario, A para texto ASCII.
passive
Si se deben usar conexiones de datos FTP pasivas (PASV) o conexiones de datos FTP activas (PORT). Los valores válidos son 0 para activo, 1 para pasivo, o 2 para intentar pasivo, luego recurrir a activo. El valor predeterminado es 2.
recursive
Esto se puede usar para transferir árboles de directorios completos. Por defecto, solo se transfiere un solo archivo. Los valores válidos son yes o no.
delete
Esto se puede usar para eliminar el archivo de origen en la máquina de origen después de transferir con éxito el archivo a la máquina de destino. Por defecto, los archivos de origen no se eliminan. Los valores válidos son yes o no.
job-name
Esto no es utilizado por el programa, pero puede ser utilizado por una entidad que genera automáticamente archivos de trabajo. Como ejemplo, cuando se utiliza la bandera -bbb con ncftpput, crea un archivo de trabajo en stdout con un parámetro job-name para que pueda copiar fácilmente el archivo al directorio de cola de trabajos con el nombre de trabajo sugerido como nombre del archivo de trabajo.
pre-ftp-command
post-ftp-command
Estos parámetros corresponden a las opciones -W y -Y de ncftpget y ncftpput. Es importante notar que estos se refieren a comandos del protocolo de transferencia de archivos RFC959 y **no** a comandos de shell, ni a comandos utilizados desde /usr/bin/ftp o ncftp.
pre-shell-command
post-shell-command
Estos parámetros proporcionan puntos de conexión para que pueda ejecutar un programa personalizado cuando un elemento es procesado por el spooler. Los valores válidos son rutas a scripts o programas ejecutables. Tenga en cuenta que el valor no debe contener ningún argumento de línea de comandos; si desea hacerlo, cree un script de shell y haga que ejecute su programa con los argumentos de línea de comandos que requiere.

En términos generales, post-shell-command es mucho más útil que pre-shell-command, ya que si necesita usar estas opciones, es más probable que quiera hacer algo después de que la transferencia FTP haya completado en lugar de antes. Por ejemplo, podría querer ejecutar un script de shell que alerte a un administrador para notificarle que su descarga de archivo de 37 gigabytes ha finalizado.

Cuando se ejecuta su programa personalizado, recibe en la entrada estándar el contenido del archivo de trabajo (es decir, varias líneas de pares clave-valor variable=valor), así como datos adicionales que el spooler pueda proporcionar, como un par clave-valor result con una descripción textual del estado de finalización del trabajo.

post-shell-command actualiza un archivo de registro llamado /var/log/ncftp_spooler.

#!/usr/bin/perl -w

my ($line);
my (%params) = ();

while (defined($line = <STDIN>)) {
$params{$1} = $2
if ($line =~ /^([^=\#\s]+)=(.*)/);
}

if ((defined($params{"result"})) &&
($params{"result"} =~ /^Succeeded/))
{
open(LOG, ">> /var/log/ncftp_spooler.log")
or exit(1);
print LOG "DOWNLOAD" if ($params{"op"} eq "get");
print LOG "UPLOAD" if ($params{"op"} eq "put");
print LOG " ", $params{"local-file"}, "\n";
close(LOG);
}

DIAGNÓSTICOS

Se debe examinar el archivo de registro para determinar si algún proceso de ncftpspooler está trabajando activamente en trabajos. El registro contiene grandes cantidades de información útil, incluida toda la conversación de la conexión de control FTP entre el cliente y el servidor FTP.

ERRORES

La opción recursive puede no ser confiable ya que ncftpspooler depende de funcionalidades que pueden o no estar presentes en el software del servidor remoto. Además, incluso si la funcionalidad está disponible, ncftpspooler puede necesitar usar heurísticas que no se pueden considerar 100% precisas. Por lo tanto, es mejor crear trabajos individuales para cada archivo en el árbol de directorios, en lugar de un solo trabajo de directorio recursivo.

Para que la reanudación de las descargas funcione, el servidor remoto debe ser compatible con los primitivos FTP SIZE y MDTM. La mayoría del software de servidor FTP moderno puede hacer esto, pero todavía hay un número de implementaciones de ftpd básicas que no lo hacen. En estos casos, ncftpspooler volverá a descargar el archivo en su totalidad cada vez hasta que la descarga tenga éxito.

El programa necesita ser mejorado para detectar trabajos que no tienen ninguna posibilidad de completarse con éxito. Todavía hay un número de casos en los que los trabajos pueden ser puestos en cola pero se reintentan una y otra vez hasta que un administrador de sistemas vigilante elimina manualmente los trabajos.

Los archivos de cola pueden contener nombres de usuario y contraseñas almacenados en texto plano. ¡Estos archivos no deben ser legibles por ningún usuario excepto por el usuario que ejecuta el programa!
