NOMBRE

nnrpd - servidor NNTP para clientes lectores

SINOPSIS

nnrpd [-BDfnoSt] [-4 direccion] [-6 direccion] [-b direccion] [-c archivoconf] [-i inicial] [-I instancia] [-p puerto] [-P previa] [-r motivo] [-s relleno]

DESCRIPCIÓN

nnrpd es un servidor NNTP para lectores de noticias. Acepta comandos en su entrada estándar y responde en su salida estándar. Normalmente es invocado por innd(8) con esos descriptores adjuntos a una conexión de cliente remoto. nnrpd también soporta la ejecución como un demonio independiente.

A diferencia de innd(8), nnrpd soporta todos los comandos NNTP para lectura y publicación orientada al usuario. nnrpd utiliza el archivo readers.conf para controlar quién está autorizado a acceder a la base de datos de Usenet.

Al salir, nnrpd reportará estadísticas de uso a través de syslog(3).

nnrpd es ejecutado desde innd (el predeterminado) o desde inetd(8), xinetd(8), o algún equivalente. Con frecuencia, también se ejecuta como un demonio, con la opción -D, para proporcionar soporte TLS en un puerto dedicado.

nnrpd solo lee los archivos de configuración (readers.conf, inn.conf y inn-secrets.conf) cuando es activado. Por lo tanto, nunca podrás cambiar el comportamiento de un cliente que ya está conectado. Como cada conexión nueva de nnrpd es activada, cualquier cambio en estos archivos de configuración será efectivo inmediatamente para todas las conexiones nuevas. Solo hay una excepción: cuando nnrpd se ejecuta como demonio con la opción -D, cualquier cambio de configuración en inn.conf no tendrá efecto hasta que nnrpd sea reiniciado.

La configuración nnrpdflags de inn.conf puede ser utilizada para pasar cualquiera de las opciones a continuación a las instancias de nnrpd que son activadas directamente desde innd. Muchas opciones solo tienen sentido cuando se usa -D, por lo que estas opciones no deben usarse con nnrpdflags. Véase también la discusión de nnrpdflags en inn.conf(5).

Cuando nnrpdloadlimit en inn.conf no es 0, también rechazará conexiones si la carga promedio es mayor que ese valor (típicamente 16). nnrpd también puede prevenir que publicadores de alto volumen abusen de sus recursos. Véase la discusión sobre el retroceso exponencial en inn.conf(5).

nnrpd inyecta artículos en el servidor local que ejecuta innd a través de un socket de dominio UNIX, o un socket de dominio INET si no es compatible. Si se debe usar otro servidor para la inyección, puedes configurarlo con el parámetro nnrpdposthost en inn.conf. En caso de que se soliciten credenciales de autenticación durante la inyección, nnrpd utilizará el archivo passwd.nntp en pathetc.

OPCIONES

-4 direccion
El parámetro -4 instruye a nnrpd a enlazarse a la dirección IPv4 especificada cuando se inicia como un demonio independiente usando la bandera -D. Esta debe ser una dirección IPv4 válida perteneciente a una interfaz del host local. También puede ser 0.0.0.0, lo que significa enlazar a todas las direcciones (esta es la opción predeterminada).
-6 direccion
El parámetro -6 instruye a nnrpd a enlazarse a la dirección IPv6 especificada cuando se inicia como un demonio independiente usando la bandera -D. Esta debe ser una dirección IPv6 válida perteneciente a una interfaz del host local. También puede ser "::0", lo que significa enlazar a todas las direcciones IPv6.

Por defecto, nnrpd en modo demonio escucha tanto en direcciones IPv4 como IPv6. Con esta opción, solo escuchará en las direcciones IPv6 especificadas. Sin embargo, en algunos sistemas, un valor de "::0" hará que también escuche en todas las direcciones IPv4.

-b direccion
Similar a la bandera -4. -b se mantiene por compatibilidad con versiones anteriores.
-B
Si se especifica, nnrpd reportará los intentos de inicio de sesión a blacklistd(8) para bloqueo automático después de un número de intentos fallidos. Para usar esta bandera, la biblioteca blacklist debe haber sido encontrada en el momento de la configuración, o se debe haber especificado --with-blacklist en el momento de la configuración. Para más información, vea "SOPORTE DE BLACKLISTD" a continuación.
-c archivoconf
Por defecto, nnrpd lee el archivo de configuración readers.conf para determinar cómo autenticar las conexiones. La bandera -c especifica un archivo alternativo para este propósito. Si el nombre del archivo no está completamente calificado, se considera relativo a pathetc en inn.conf. (Esto es útil para tener varias instancias de nnrpd ejecutándose en diferentes puertos o direcciones IP con diferentes configuraciones.)
-D
Si se especifica, este parámetro hace que nnrpd opere como un demonio. Es decir, se desvincula y se ejecuta en segundo plano, creando un proceso por cada conexión. Por defecto, nnrpd escucha en el puerto NNTP (119), por lo que o bien innd(8) debe iniciarse en otro puerto o se debe usar el parámetro -p. Tenga en cuenta que con este parámetro, nnrpd continúa ejecutándose hasta que se detiene. Esto significa que lee inn.conf una vez al inicio y nunca más hasta que se reinicia. Por lo tanto, nnrpd debe reiniciarse si se cambia inn.conf.

Cuando se inicia en modo demonio, nnrpd escribirá su PID en un archivo en el directorio pathrun. El archivo se llamará nnrpd.pid si nnrpd escucha en el puerto 119 (predeterminado), o nnrpd-%d.pid, donde %d se reemplaza con el puerto en el que nnrpd está configurado para escuchar (se da la opción -p y su argumento no es 119).

También puede querer usar -s al ejecutar nnrpd como un demonio.

-f
Si se especifica, nnrpd no se desvincula y se ejecuta en primer plano cuando se inicia como un demonio independiente usando la bandera -D.
-i inicial
Especifica un comando inicial para nnrpd. Cuando se usa, inicial se toma como si fuera el primer comando recibido por nnrpd. Después de haber respondido, nnrpd cerrará la conexión.
-I instancia
Si se especifica, instancia se usa como una porción estática adicional dentro de los Message-IDs generados por nnrpd, cuando virtualhost está configurado en grupos de acceso en readers.conf; típicamente esta opción se usaría donde un grupo de máquinas existen con el mismo nombre de host virtual y deben ser desambiguadas durante las publicaciones.
-n
La bandera -n desactiva la resolución de direcciones IP a nombres. Si solo usa restricciones basadas en IP en readers.conf y puede manejar direcciones IP en sus registros, usar esta bandera puede resultar en una velocidad adicional.
-o
La bandera -o hace que todos los artículos se pongan en cola en lugar de enviarlos a innd(8). rnews con la bandera -U debe ser invocado desde cron regularmente para encargarse de estos artículos. Esta bandera es útil si innd está aceptando artículos y nnrpd se inicia de forma independiente o usando inetd(8).
-p puerto
El parámetro -p instruye a nnrpd a escuchar en puerto cuando se inicia como un demonio independiente usando la bandera -D.
-P previa
El parámetro -P instruye a nnrpd a pre-crear previa hijos en espera de conexiones cuando se inicia como un demonio independiente usando la bandera -D.
-r motivo
Si se usa la bandera -r, entonces nnrpd rechazará la conexión entrante dando motivo como texto. Esta bandera es utilizada por innd(8) cuando está pausado o estrangulado. motivo debe estar codificado

SOPORTE DE BLACKLISTD

Si nnrpd fue compilado con soporte para blacklistd, entonces puede reportar los intentos fallidos de inicio de sesión a la utilidad blacklistd(8). Esta utilidad mantiene un registro de las direcciones IP que han tenido un número excesivo de intentos de conexión fallidos, y las bloquea temporalmente. Esto puede ser muy útil para protegerse contra ataques de fuerza bruta dirigidos a su servidor NNTP. Para habilitar esta característica, simplemente compile nnrpd con la bandera -B.

La configuración real de blacklistd, incluyendo el número de intentos fallidos permitidos y el período de bloqueo, se maneja en el archivo de configuración de blacklistd.

VEASE TAMBIÉN

innd(8), readers.conf(5), inn.conf(5)

-s relleno
A medida que se recibe cada comando de un cliente, nnrpd intenta cambiar su array de "argv" que contiene el título del proceso para que comandos como ps(1) muestren el nombre de host del cliente conectado y el comando que se está ejecutando. Para obtener una visualización completa, la opción -s puede usarse con una cadena larga como argumento, que se sobrescribirá cuando nnrpd cambie su título.

Cuando innd inicia nnrpd, esta opción se usa con un argumento compuesto por 48 espacios.

-S
Si se especifica, nnrpd iniciará una negociación para una sesión TLS tan pronto como se conecte. Para usar esta opción, las bibliotecas SSL y criptográficas de OpenSSL deben haber sido encontradas en el momento de la configuración, o se debe haber especificado --with-openssl en el momento de la configuración. Para más información sobre cómo ejecutar nnrpd con soporte TLS, consulte "SOPORTE TLS".
-t
Si se usa la opción -t, todos los comandos del cliente y las respuestas iniciales serán rastreados informándolos en syslog. Esta opción es establecida por innd(8) bajo el control del comando "trace" de ctlinnd(8), y se alterna al recibir un SIGHUP; consulte signal(2).

SOPORTE TLS

Si INN se compila con --with-openssl o si las bibliotecas SSL y criptográficas de OpenSSL se encuentran en el momento de la configuración, nnrpd soportará la lectura de noticias a través de TLS (también conocido como SSL). Para los clientes que usan el comando STARTTLS, no se necesita ninguna configuración especial más allá de crear un certificado TLS/SSL para el servidor. Debería hacerlo exactamente de la misma manera que generaría un certificado para un servidor web.

Si está satisfecho con un certificado autofirmado (que generará advertencias con algunos clientes de lectores de noticias), puede crear e instalar uno en la ruta predeterminada ejecutando "make cert" después de "make install" al instalar INN, o ejecutando los siguientes comandos:

umask 077
openssl req -new -x509 -nodes -out <pathetc>/cert.pem \
    -days 366 -keyout <pathetc>/key.pem
chown news:news <pathetc>/cert.pem
chmod 640 <pathetc>/cert.pem
chown news:news <pathetc>/key.pem
chmod 600 <pathetc>/key.pem

Reemplace las rutas con algo apropiado para su instalación de INN. Esto creará un certificado autofirmado que expirará en un año. El programa openssl le hará una variedad de preguntas sobre su organización. Ingrese el nombre de dominio completo de su servicio de noticias (ya sea el nombre canónico del servidor o un alias dedicado para el servicio de noticias) como el nombre para el que se genera el certificado.

Luego deberá configurar estos parámetros de inn.conf con las rutas correctas:

tlscapath:      <pathetc>
tlscertfile:    <pathetc>/cert.pem
tlskeyfile:     <pathetc>/key.pem

Si desea utilizar una cadena de certificados completa, puede insertarla directamente en tlscertfile (como la directiva SSLCertificateFile de Apache). Alternativamente, puede colocar un único certificado en tlscertfile y usar tlscafile para certificados adicionales necesarios para completar la cadena, como un certificado raíz de autoridad separado.

Más concretamente, al usar certificados de Let's Encrypt, los archivos de Certbot se pueden instalar de la siguiente manera:

tlscapath:      /etc/letsencrypt/live/news.server.com
tlscertfile:    /etc/letsencrypt/live/news.server.com/fullchain.pem
tlskeyfile:     /etc/letsencrypt/live/news.server.com/privkey.pem

o:

tlscapath:      /etc/letsencrypt/live/news.server.com
tlscafile:      /etc/letsencrypt/live/news.server.com/chain.pem
tlscertfile:    /etc/letsencrypt/live/news.server.com/cert.pem
tlskeyfile:     /etc/letsencrypt/live/news.server.com/privkey.pem

Asegúrese de que los permisos de archivo estén correctamente establecidos para que el usuario o grupo de noticias puedan leer estos directorios y archivos (típicamente, debería tener acceso a /etc/letsencrypt/live/news.server.com y /etc/letsencrypt/archive/news.server.com donde se encuentran las claves reales, y la clave privada no debe ser legible por todos).

Si prefiere apuntar a archivos fuera del directorio de Let's Encrypt, puede agregar un hook posterior a la renovación para que Let's Encrypt copie los archivos generados a otra ubicación y les dé los derechos esperados.

Hay dos formas comunes para que un cliente de noticias negocie una conexión TLS: ya sea mediante el uso de un puerto dedicado (generalmente 563) en el que TLS se negocia inmediatamente al conectarse, o mediante la forma ahora desaconsejada (según RFC 8143) de usar el comando STARTTLS en el puerto NNTP habitual (119) para actualizar dinámicamente de tráfico no cifrado a cifrado TLS durante una sesión NNTP. Sin embargo, innd no sabe cómo escuchar las conexiones a ese puerto separado (563). Por lo tanto, deberá organizar que nnrpd escuche en ese puerto a través de algún otro medio. Esto se puede hacer con la opción -D junto con "-p 563" e incluirlo en sus scripts de inicialización:

su news -s /bin/sh -c '<pathbin>/nnrpd -D -p 563 -S'

pero la forma más fácil es probablemente agregar una línea como:

nntps stream tcp nowait news <pathbin>/nnrpd nnrpd -S

a /etc/inetd.conf o el equivalente en su sistema y dejar que inetd ejecute nnrpd. (Cambie la ruta a nnrpd para que coincida con su instalación). Puede que necesite reemplazar "nntps" con 563 si "nntps" no está definido en /etc/services en su sistema. También puede querer usar la opción en minúsculas -s con una cadena larga como argumento para ver más información sobre las conexiones entrantes en la salida de ps(1).

Opcionalmente, puede configurar los parámetros tlsciphers, tlsciphers13, tlscompression, tlseccurve, tlspreferserverciphers y tlsprotocols en inn.conf para ajustar el comportamiento de la negociación TLS/SSL cada vez que se descubra un nuevo ataque contra el protocolo TLS o algún conjunto de cifrado compatible.

SOPORTE BLACKLISTD

blacklistd(8) es un demonio de FreeBSD/NetBSD para prevenir ataques de fuerza bruta bloqueando a los atacantes después de un número de intentos de inicio de sesión fallidos. Cuando nnrpd se compila con soporte blacklistd, informará los intentos de inicio de sesión al demonio blacklistd para un posible bloqueo.

Agregar la siguiente configuración a /etc/blacklistd.conf bajo la sección "[local]", asumiendo que nnrpd está escuchando en el puerto 563, llevaría a que los atacantes sean bloqueados durante 10 minutos después de 5 intentos de inicio de sesión fallidos.

# adr/mask:port type    proto owner name nfail disable
563             stream  *     *     *    5     10m

Consulte la documentación de blacklistd(8) para más información.

DIFERENCIAS DE PROTOCOLO

nnrpd implementa los comandos NNTP definidos en RFC 3977 (NNTP), RFC 4642 actualizado por RFC 8143 (TLS/NNTP), RFC 4643 (autenticación NNTP), RFC 6048 (adiciones LIST NNTP) y RFC 8054 (compresión NNTP) con las siguientes diferencias:

1.
Se proporciona el comando XGTITLE [wildmat]. Esta extensión es utilizada por ANU-News y documentada en RFC 2980. Devuelve un código de respuesta 282, seguido de una descripción de una línea de todos los grupos de noticias que coinciden con el patrón. El valor predeterminado es el grupo actual.

Tenga en cuenta que LIST NEWSGROUPS debe usarse en lugar de XGTITLE.

2.
Se implementa el comando XHDR cabecera [ID-mensaje|rango]. Devuelve un código de respuesta 221, seguido de campos de cabecera específicos para el rango especificado; el valor predeterminado es devolver los datos del artículo actual. Consulte RFC 2980.

Tenga en cuenta que HDR debe usarse en lugar de XHDR.

3.
Se proporciona el comando XOVER [rango]. Devuelve un código de respuesta 224, seguido de los datos de resumen para el rango especificado; el valor predeterminado es devolver los datos del artículo actual. Consulte RFC 2980.

Tenga en cuenta que OVER debe usarse en lugar de XOVER.

4.
Se proporciona un nuevo comando, XPAT cabecera ID-mensaje|rango patrón [patrón ...]. El primer argumento es el nombre no sensible a mayúsculas y minúsculas del campo de cabecera a buscar. El segundo argumento es un rango de artículos o un único ID de mensaje, como se especifica en RFC 2980. El tercer argumento es un patrón de estilo uwildmat; si hay argumentos adicionales, se unen separados por un único espacio para formar el patrón completo. Este comando es similar al comando XHDR. Devuelve un código de respuesta 221, seguido de la respuesta de texto de todos los números de artículos que coinciden con el patrón.
5.
Un nombre de grupo de noticias es sensible a mayúsculas y minúsculas para nnrpd.
6.
Si IHAVE se ha anunciado, no se anunciará necesariamente durante toda la sesión (contrariamente a la sección 3.4.1 de RFC 3977). nnrpd solo anuncia la capacidad IHAVE cuando está realmente disponible.
7.
nnrpd permite una sintaxis más amplia para wildmats y rangos (especialmente "-" y "-número-artículo").
8.
Cuando se usa la generación de palabras clave, una característica experimental habilitada con el parámetro keywords en inn.conf, se anuncia "Keywords:full" en LIST OVERVIEW.FMT aunque la información de resumen se calcula y no proviene necesariamente de los campos de cabecera Keywords.
