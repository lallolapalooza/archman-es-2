NOHUP(1P) Manual del programador POSIX NOHUP(1P)

PRÓLOGO

Esta página del manual es parte del Manual del programador POSIX. La implementación de Linux de esta interfaz puede diferir (consulte la página del manual de Linux correspondiente para conocer los detalles del comportamiento de Linux), o la interfaz puede no estar implementada en Linux.

NOMBRE

nohup — invocar una utilidad inmune a cuelgues

SINOPSIS

nohup utilidad [argumento...]

DESCRIPCIÓN

La utilidad nohup invocará la utilidad nombrada por el operando utilidad con los argumentos proporcionados como operandos argumento. En el momento en que se invoque la utilidad nombrada, la señal SIGHUP se establecerá para ser ignorada.

Si la entrada estándar está asociada a una terminal, la utilidad nohup puede redirigir la entrada estándar desde un archivo no especificado.

Si la salida estándar es una terminal, toda la salida escrita por la utilidad nombrada a su salida estándar se añadirá al final del archivo nohup.out en el directorio actual. Si nohup.out no se puede crear o abrir para añadir, la salida se añadirá al final del archivo nohup.out en el directorio especificado por la variable de entorno HOME. Si ninguno de los archivos se puede crear o abrir para añadir, la utilidad no se invocará. Si se crea un archivo, los bits de permiso del archivo se establecerán en S_IRUSR | S_IWUSR.

Si el error estándar es una terminal y la salida estándar está abierta pero no es una terminal, toda la salida escrita por la utilidad nombrada a su error estándar se redirigirá a la misma descripción de archivo abierta que la salida estándar. Si el error estándar es una terminal y la salida estándar es una terminal o está cerrada, la misma salida se añadirá en su lugar al final del archivo nohup.out como se describe anteriormente.

OPCIONES

Ninguna.

OPERANDOS

Se admitirán los siguientes operandos:

utilidad
El nombre de una utilidad que debe invocarse. Si el operando utilidad nombra alguna de las utilidades integradas especiales en la Sección 2.14, Utilidades Integradas Especiales, los resultados no están definidos.
argumento
Cualquier cadena que se proporcione como argumento al invocar la utilidad nombrada por el operando utilidad.

ENTRADA ESTÁNDAR

No utilizada.

ARCHIVOS DE ENTRADA

Ninguno.

VARIABLES DE ENTORNO

Las siguientes variables de entorno afectarán a la ejecución de nohup:

HOME
Determina la ruta del directorio de inicio del usuario: si el archivo de salida nohup.out no se puede crear en el directorio actual, la utilidad nohup utilizará el directorio nombrado por HOME para crear el archivo.
LANG
Proporciona un valor predeterminado para las variables de internacionalización que no están establecidas o están vacías. (Consulte el volumen de Definiciones Base de POSIX.1‐2017, Sección 8.2, Variables de Internacionalización para conocer la precedencia de las variables de internacionalización utilizadas para determinar los valores de las categorías de configuración regional).
LC_ALL
Si se establece en una cadena de valor no vacía, anula los valores de todas las demás variables de internacionalización.
LC_CTYPE
Determina la configuración regional para la interpretación de secuencias de bytes de datos de texto como caracteres (por ejemplo, caracteres de un solo byte en lugar de caracteres multibyte en los argumentos).
LC_MESSAGES

Determina la configuración regional que debe utilizarse para afectar el formato y el contenido de los mensajes de diagnóstico escritos en el error estándar.
NLSPATH
Determina la ubicación de los catálogos de mensajes para el procesamiento de LC_MESSAGES.
PATH
Determina la ruta de búsqueda que se utiliza para localizar la utilidad que se va a invocar. Consulte el volumen de Definiciones Base de POSIX.1‐2017, Capítulo 8, Variables de Entorno.

EVENTOS ASÍNCRONOS

La utilidad nohup adoptará la acción estándar para todas las señales, excepto que SIGHUP será ignorada.

SALIDA ESTÁNDAR

Si la salida estándar no es una terminal, la salida estándar de nohup será la salida estándar generada por la ejecución de la utilidad especificada por los operandos. De lo contrario, no se escribirá nada en la salida estándar.

ERROR ESTÁNDAR

Si la salida estándar es una terminal, se escribirá un mensaje en el error estándar, indicando el nombre del archivo al que se está añadiendo la salida. El nombre del archivo será nohup.out o $HOME/nohup.out.

ARCHIVOS DE SALIDA

La salida escrita por la utilidad nombrada se añade al archivo nohup.out (o $HOME/nohup.out), si las condiciones se cumplen según se describe en la DESCRIPCIÓN.

DESCRIPCIÓN EXTENDIDA

Ninguna.

ESTADO DE SALIDA

Se devolverán los siguientes valores de salida:

126
Se encontró la utilidad especificada por utilidad pero no se pudo invocar.
127
Se produjo un error en la utilidad nohup o no se pudo encontrar la utilidad especificada por utilidad.

De lo contrario, el estado de salida de nohup será el de la utilidad especificada por el operando utilidad.

CONSECUENCIAS DE LOS ERRORES

Predeterminado.

Las siguientes secciones son informativas.

USO DE LA APLICACIÓN

Las utilidades command, env, nice, nohup, time y xargs han sido especificadas para usar el código de salida 127 si se produce un error, de modo que las aplicaciones puedan distinguir entre ``fallo al encontrar una utilidad'' y ``la utilidad invocada salió con una indicación de error''. Se eligió el valor 127 porque no se usa comúnmente para otros significados; la mayoría de las utilidades usan valores pequeños para ``condiciones de error normales'' y los valores superiores a 128 pueden confundirse con la terminación debido a la recepción de una señal. El valor 126 se eligió de manera similar para indicar que la utilidad se pudo encontrar, pero no invocar. Algunos scripts producen mensajes de error significativos que diferencian los casos 126 y 127. La distinción entre los códigos de salida 126 y 127 se basa en la práctica de KornShell, que usa 127 cuando todos los intentos de exec de la utilidad fallan con [ENOENT], y usa 126 cuando cualquier intento de exec de la utilidad falla por cualquier otro motivo.

EJEMPLOS

Con frecuencia es deseable aplicar nohup a tuberías o listas de comandos. Esto se puede hacer colocando tuberías y listas de comandos en un solo archivo; este archivo puede luego invocarse como una utilidad, y nohup se aplica a todo lo que hay en el archivo.

Alternativamente, el siguiente comando se puede usar para aplicar nohup a una línea de comandos compleja:

nohup sh -c 'línea-de-comandos-compleja' </dev/null

MOTIVO

La versión 4.3 de BSD ignora SIGTERM y SIGHUP, y si ./nohup.out no se puede usar, falla en lugar de intentar usar $HOME/nohup.out.

La utilidad csh tiene una versión incorporada de nohup que actúa de forma diferente a la nohup definida en este volumen de POSIX.1‐2017.

El término utilidad se utiliza, en lugar de comando, para resaltar el hecho de que los comandos compuestos de shell, pipelines, built-ins especiales, etc., no se pueden usar directamente. Sin embargo, utilidad incluye programas de aplicación de usuario y scripts de shell, no solo las utilidades estándar.

Las versiones históricas de la utilidad nohup utilizan semánticas predeterminadas de creación de archivos. Algunas versiones más recientes utilizan los permisos especificados aquí como una medida de seguridad adicional.

Algunas implementaciones históricas ignoran SIGQUIT además de SIGHUP; otras ignoran SIGTERM. Una propuesta temprana permitía, pero no requería, ignorar SIGQUIT. Varios revisores objetaron que nohup solo debía modificar el manejo de SIGHUP según lo requerido por este volumen de POSIX.1‐2017.

Las versiones históricas de nohup no afectaban a la entrada estándar, pero eso causa problemas en el escenario común donde el usuario inicia sesión en un sistema, escribe el comando:

nohup make &

en el prompt, y luego cierra la sesión. Si la entrada estándar no se ve afectada por nohup, la sesión de inicio de sesión puede no terminar en mucho tiempo, ya que la entrada estándar permanece abierta hasta que make finaliza. Para evitar este problema, POSIX.1‐2008 permite a las implementaciones redirigir la entrada estándar si es un terminal. Dado que el comportamiento depende de la implementación, las aplicaciones portátiles que puedan encontrar el problema deben redirigir la entrada estándar ellas mismas. Por ejemplo, en lugar de:

nohup make &

una aplicación puede invocar:

nohup make </dev/null &
