Paquete: libnbd

Licencias: LGPL-2.1-or-later

nbd_block_status(3) LIBNBD nbd_block_status(3)

NOMBRE

nbd_block_status - envía el comando de estado de bloque, con callback de 32 bits

SINOPSIS

#include <libnbd.h>
typedef struct {
  int (*callback) (void *user_data,
                   const char *metacontext,
                   uint64_t offset, uint32_t *entries,
                   size_t nr_entries, int *error);
  void *user_data;
  void (*free) (void *user_data);
} nbd_extent_callback;
int nbd_block_status (
      struct nbd_handle *h, uint64_t count,
      uint64_t offset, nbd_extent_callback extent_callback,
      uint32_t flags
    );

DESCRIPCIÓN

Emite el comando de estado de bloque al servidor NBD. Si es soportado por el servidor, esto hace que se devuelva información de contexto de metadatos sobre bloques que comienzan desde el desplazamiento especificado. El parámetro "count" es una pista: el servidor puede elegir devolver menos estado, o el bloque final puede extenderse más allá del rango solicitado. Si se soportan múltiples contextos, el número de bloques y la longitud acumulada de esos bloques no tienen que ser idénticos entre contextos.

Tenga en cuenta que no todos los servidores pueden soportar un "count" de 4GiB o más; nbd_get_extended_headers_negotiated(3) indica qué servidores analizarán una solicitud mayor de 32 bits. El protocolo NBD aún no tiene una forma para que un cliente aprenda si el servidor aplicará un tamaño máximo de estado de bloque aún menor, aunque una extensión futura puede agregar una restricción visible en nbd_get_block_size(3). Además, esta función está inherentemente limitada a valores de 32 bits. Si el servidor responde con una extensión mayor, la longitud de esa extensión se truncará a justo por debajo de 32 bits y se ignorar{án,o} cualquier extensión adicional del servidor. Si el servidor responde con un valor de estado mayor de 32 bits (solo posible cuando se usan encabezados extendidos), la función de callback recibirá un error "EOVERFLOW". Para obtener la información de extensión completa de un servidor que soporta extensiones de 64 bits, debe usar nbd_block_status_64(3).

Dependiendo de qué contextos de metadatos se habilitaron antes de conectar (ver nbd_add_meta_context(3)) y cuáles son soportados por el servidor (ver nbd_can_meta_context(3)) esta llamada devuelve información sobre extensiones llamando a la función "extent". El callback no puede llamar a las APIs "nbd_*" en el mismo manejador ya que este mantiene el bloqueo del manejador y causará un deadlock. Si el callback devuelve -1, y no se ha detectado ningún error anterior, entonces el comando general de estado de bloque fallará con cualquier valor distinto de cero almacenado en el parámetro "error" del callback (con un valor por defecto de "EPROTO"); pero cualquier contexto adicional seguirá invocando el callback.

La función "extent" se llama una vez por tipo de metadatos disponibles, con el "user_data" pasado a esta función. El parámetro "metacontext" es una cadena como "base:allocation". El array "entries" es un array de pares de enteros con el primer elemento de cada par siendo la longitud (en bytes) del bloque y el segundo elemento siendo un campo de estado/banderas específico para el contexto de metadatos. El número de pares pasados a la función es "nr_entries/2". El documento del protocolo NBD en la sección sobre "NBD_REPLY_TYPE_BLOCK_STATUS" describe el significado de este array; para contextos conocidos por libnbd, <libnbd.h> contiene constantes que comienzan con "LIBNBD_STATE_" que pueden ayudar a descifrar los valores. Al entrar en el callback, el parámetro "error" contiene el valor errno de cualquier error detectado previamente, pero incluso si se detectó un error anterior, el "metacontext" y "entries" actuales son válidos.

Es posible que la función extent se llame más veces de lo que espera (si el servidor tiene errores), por lo que siempre revise el campo "metacontext" para asegurarse de que está recibiendo los datos que espera. También es posible que la función extent no se llame en absoluto, incluso para contextos de metadatos que solicitó. Esto indica que el servidor no soporta el contexto o por alguna otra razón no puede devolver los datos.

El parámetro "flags" puede ser 0 para ninguna bandera, o puede contener "LIBNBD_CMD_FLAG_REQ_ONE", lo que significa que el servidor debe devolver solo una extensión por contexto de metadatos donde esa extensión no exceda "count" bytes; sin embargo, libnbd no valida si el servidor obedeció la bandera.

Por defecto, libnbd rechazará los intentos de usar esta función con parámetros que probablemente resulten en un fallo del servidor, como solicitar una bandera de comando desconocida. La función nbd_set_strict_mode(3) puede usarse para alterar qué escenarios deben esperar una respuesta del servidor en lugar de fallar rápidamente.

VALOR DE RETORNO

Si la llamada es exitosa, la función devuelve 0.

ERRORES

En caso de error, se devuelve -1.

Consulte "MANEJO DE ERRORES" en libnbd(3) para saber cómo obtener más detalles del error.

Los siguientes parámetros no deben ser NULL: "h". Para más información, consulte "Parámetros no NULL" en libnbd(3).

ESTADO DEL MANEJADOR

nbd_block_status puede ser llamado cuando el manejador se encuentra en el siguiente estado:

┌─────────────────────────────────────┬─────────────────────────┐
│ Manejador creado, antes de conectar │ ❌ error                │
│ Conectando                          │ ❌ error                │
│ Conectando y handshake (opt_mode) │ ❌ error                │
│ Conectado al servidor             │ ✅ permitido            │
│ Conexión cerrada                 │ ❌ error                │
│ Manejador inactivo                │ ❌ error                │
└─────────────────────────────────────┴─────────────────────────┘

VERSIÓN

Esta función apareció por primera vez en libnbd 1.0.

Si necesita probar si esta función está disponible en tiempo de compilación, compruebe si el siguiente macro está definido:

#define LIBNBD_HAVE_NBD_BLOCK_STATUS 1
