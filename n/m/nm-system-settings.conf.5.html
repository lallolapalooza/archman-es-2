NETWORKMANAGER.CONF(5) Configuración NETWORKMANAGER.CONF(5)

NOMBRE

NetworkManager.conf - Archivo de configuración de NetworkManager

SINOPSIS

/etc/NetworkManager/NetworkManager.conf, /etc/NetworkManager/conf.d/nombre.conf, /run/NetworkManager/conf.d/nombre.conf, /usr/lib/NetworkManager/conf.d/nombre.conf, /var/lib/NetworkManager/NetworkManager-intern.conf

DESCRIPCIÓN

NetworkManager.conf es el archivo de configuración de NetworkManager. Se utiliza para configurar varios aspectos del comportamiento de NetworkManager. La ubicación del archivo principal y los directorios de configuración pueden cambiarse mediante el uso de los argumentos --config, --config-dir, --system-config-dir y --intern-config para NetworkManager, respectivamente.

Si una distribución proporciona un NetworkManager.conf por defecto en sus paquetes, no deberías modificarlo, ya que tus cambios podrían ser sobrescritos por actualizaciones de paquetes. En su lugar, puedes añadir archivos .conf adicionales al directorio /etc/NetworkManager/conf.d. Estos se leerán en orden, y los archivos posteriores anularán a los anteriores. Los paquetes pueden instalar fragmentos de configuración adicionales en /usr/lib/NetworkManager/conf.d. Este directorio se analiza primero, incluso antes que NetworkManager.conf. Los scripts también pueden colocar configuración por arranque en /run/NetworkManager/conf.d. Este directorio se analiza en segundo lugar, también antes que NetworkManager.conf. La carga de un archivo /run/NetworkManager/conf.d/nombre.conf puede prevenirse añadiendo un archivo /etc/NetworkManager/conf.d/nombre.conf. Igualmente, un archivo /usr/lib/NetworkManager/conf.d/nombre.conf puede ser ocultado colocando un archivo del mismo nombre en /etc/NetworkManager/conf.d o /run/NetworkManager/conf.d.

NetworkManager puede sobrescribir ciertas opciones de configuración del usuario a través de D-Bus u otras operaciones internas. En este caso, escribe esos cambios en /var/lib/NetworkManager/NetworkManager-intern.conf. Este archivo no está destinado a ser modificado por el usuario, pero se lee al final y puede ocultar la configuración del usuario desde NetworkManager.conf.

Ciertos ajustes de la configuración pueden recargarse en tiempo de ejecución enviando la señal SIGHUP o a través de la llamada Reload de D-Bus.

NetworkManager no requiere ninguna configuración en NetworkManager.conf. Dependiendo de tu caso de uso, puedes eliminar todos los archivos para restaurar la configuración por defecto (restablecimiento de fábrica). Pero ten en cuenta que tu distribución u otros paquetes pueden colocar fragmentos de configuración para NetworkManager, de modo que formen parte de la configuración por defecto.

FORMATO DEL ARCHIVO

El formato del archivo de configuración es el llamado archivo de clave (una especie de formato estilo ini). Consiste en secciones (grupos) de pares clave-valor. Las líneas que comienzan con '#' y las líneas en blanco se consideran comentarios. Las secciones se inician con una línea de encabezado que contiene la sección entre corchetes '[' y ']', y terminan implícitamente con el inicio de la siguiente sección o el final del archivo. Cada par clave-valor debe estar contenido en una sección.

Para las claves que toman una lista de dispositivos como su valor, puedes especificar dispositivos por sus direcciones MAC o nombres de interfaz, o "*" para especificar todos los dispositivos. Consulta la sección "Formato de lista de dispositivos" a continuación.

Un archivo de configuración simple se ve así:

[main]
plugins=keyfile

Como una extensión al formato normal de archivo de clave, también puedes añadir un valor a una clave de valor de lista establecida previamente haciendo:

plugins+=another-plugin
plugins-=remove-me

SECCIÓN PRINCIPAL

plugins

Lista nombres de plugins de configuración del sistema separados por ','. Estos plugins se utilizan para leer y escribir perfiles de conexión a nivel de sistema. Cuando se especifican varios plugins, las conexiones se leen de todos los plugins listados. Al escribir conexiones, se pedirá a los plugins que guarden la conexión en el orden listado aquí; si el primer plugin no puede guardar ese tipo de conexión (o no puede guardar ninguna conexión), se intenta el siguiente plugin, etc. Si ninguno de los plugins puede guardar la conexión, se devuelve un error al usuario.

El valor por defecto y el número de plugins disponibles dependen de la distribución. Consulta la sección "PLUGINS" a continuación para ver los plugins disponibles. Ten en cuenta que el plugin de archivo de clave nativo de NetworkManager siempre se añade al final de esta lista (si no aparece ya antes en la lista).

monitor-connection-files

Esta configuración está obsoleta y no tiene ningún efecto. Los perfiles del disco nunca se recargan automáticamente. Usa, por ejemplo, nmcli connection (re)load para eso.

auth-polkit

Si el sistema utiliza PolicyKit para la autorización. Si es verdadero, las solicitudes no root se autorizan utilizando PolicyKit. Las solicitudes de root (usuario con ID cero) siempre se conceden sin preguntar a PolicyKit. Si es falso, todas las solicitudes se permitirán y PolicyKit no se utilizará. Si se establece en root-only, PolicyKit no se utiliza y todas las solicitudes excepto las de root se denegarán. El valor por defecto es verdadero.

dhcp

Esta clave configura qué cliente DHCP utilizará NetworkManager. Los valores permitidos dependen de la configuración de compilación; esta versión de NetworkManager se compiló con soporte para los siguientes clientes: internal, dhcpcd.

El cliente interno está integrado, mientras que otras opciones pueden requerir la instalación de un cliente DHCP externo.

Si esta clave falta, se utiliza internal con una opción de respaldo a otros clientes compatibles.

no-auto-default

Especifica los dispositivos para los cuales NetworkManager no creará una conexión cableada por defecto (Auto eth0). Por defecto, NetworkManager crea una conexión cableada temporal para cualquier dispositivo Ethernet que sea gestionado y no tenga una conexión configurada. Lista un dispositivo en esta opción para inhibir la creación de la conexión por defecto para el dispositivo. Puede tener el valor especial * para aplicarlo a todos los dispositivos.

Cuando la conexión cableada por defecto se elimina o se guarda en una nueva conexión persistente por un plugin, el dispositivo se añade a una lista en el archivo /var/lib/NetworkManager/no-auto-default.state para evitar crear la conexión por defecto para ese dispositivo de nuevo.

Consulta la sección "Formato de lista de dispositivos" para ver la sintaxis de cómo especificar un dispositivo.

Ejemplo:

no-auto-default=00:22:68:5c:5d:c4,00:1e:65:ff:aa:ee
no-auto-default=eth0,eth1
no-auto-default=*

ignore-carrier

Esta configuración está obsoleta para el ajuste por dispositivo ignore-carrier que anula esta configuración si se especifica (ver ignore-carrier). De lo contrario, es una lista de coincidencias para especificar para qué dispositivo se debe ignorar la portadora. Consulta la sección "Formato de lista de dispositivos" para la sintaxis de cómo especificar un dispositivo. Ten en cuenta que los tipos de controlador como bond, bridge y team ignoran la portadora por defecto. Sin embargo, puedes revertir esa configuración predeterminada usando el especificador "except:" (o mejor aún, usa el ajuste por dispositivo en lugar del ajuste obsoleto).

assume-ipv6ll-only

Especifica los dispositivos para los cuales NetworkManager intentará generar una conexión basada en la configuración inicial cuando el dispositivo solo tenga una dirección de enlace local IPv6.

Consulta la sección "Formato de lista de dispositivos" para ver la sintaxis de cómo especificar un dispositivo.

configure-and-quit

Esta opción ya no es útil para configurar en el archivo NetworkManager.conf. Sin embargo, también se puede configurar en la línea de comandos con los mismos valores, donde tiene cierta utilidad.

Cuando se establece en 'initrd', NetworkManager no se conecta a D-Bus y sale después de configurar la red. Este es un detalle de implementación de cómo el módulo NetworkManager de dracut puede ejecutar NetworkManager. Una alternativa a esto es tener NetworkManager como un servicio systemd con D-Bus en initrd.

El valor 'true' no es compatible desde la versión 1.36. Anteriormente, este era un modo en el que NetworkManager salía después de configurar la red y ejecutaba procesos auxiliares para DHCP y SLAAC.

De lo contrario, NetworkManager ejecuta un servicio del sistema con D-Bus y no sale durante el funcionamiento normal.

hostname-mode

Establece el modo de gestión del nombre de host. Este parámetro solo afectará al nombre de host transitorio. Si se establece un nombre de host estático válido, NetworkManager omitirá la actualización del nombre de host a pesar del valor de esta opción. Un nombre de host vacío o igual a '(none)' se considera inválido.

default: NetworkManager actualizará el nombre de host con el proporcionado a través de DHCP o la búsqueda DNS inversa de la dirección IP en la conexión con el

route o en cualquier conexión con la propiedad hostname.only-from-default establecida en 'false'. Las conexiones se consideran en orden de valor creciente de la propiedad hostname.priority. En caso de que múltiples conexiones tengan la misma prioridad, se consideran primero las conexiones activadas anteriormente. Si no se puede determinar un nombre de host de esta manera, el nombre de host se actualizará al último establecido fuera de NetworkManager o a 'localhost.localdomain'.

dhcp: esto es similar a 'default', con la diferencia de que después de intentar obtener el nombre de host DHCP, no se realiza la búsqueda DNS inversa. Tenga en cuenta que seleccionar esta opción equivale a establecer la propiedad 'hostname.from-dns-lookup' en 'false' globalmente para todas las conexiones en NetworkManager.conf.

none: NetworkManager no administrará el nombre de host transitorio y nunca lo establecerá.

dns

Establece el modo de procesamiento de DNS.

Si la clave no está especificada, se usa el valor predeterminado, a menos que /etc/resolv.conf sea un enlace simbólico a /run/systemd/resolve/stub-resolv.conf, /run/systemd/resolve/resolv.conf, /lib/systemd/resolv.conf o /usr/lib/systemd/resolv.conf. En ese caso, se elige systemd-resolved automáticamente.

default: NetworkManager actualizará /etc/resolv.conf para reflejar los servidores de nombres proporcionados por las conexiones activas actualmente. La configuración de rc-manager (a continuación) controla cómo se hace esto.

dnsmasq: NetworkManager ejecutará dnsmasq como un servidor de nombres de caché local, utilizando "Reenvío Condicional" si está conectado a una VPN, y luego actualizará resolv.conf para que apunte al servidor de nombres local. Es posible pasar opciones personalizadas a la instancia de dnsmasq agregándolas a archivos en el directorio "/etc/NetworkManager/dnsmasq.d/". Tenga en cuenta que cuando hay varios servidores upstream disponibles, dnsmasq los contactará inicialmente en paralelo y luego usará el más rápido en responder, sondeando nuevamente otros servidores después de un tiempo. Este comportamiento se puede modificar pasando las opciones 'all-servers' o 'strict-order' a dnsmasq (consulte la página del manual para más detalles).

systemd-resolved: NetworkManager enviará la configuración de DNS a systemd-resolved

dnsconfd: NetworkManager enviará la configuración de DNS a dnsconfd


y, por defecto, establecerá ipvX.routed-dns a
yes, para que los servidores sean contactados a través de las interfaces correctas.


none: NetworkManager no modificará resolv.conf. Esto implica rc-manager unmanaged

Tenga en cuenta que los plugins dnsmasq, systemd-resolved y dnsconfd son servidores de nombres locales de caché. Por lo tanto, cuando NetworkManager escriba /run/NetworkManager/resolv.conf y /etc/resolv.conf (según la configuración de rc-manager a continuación), el servidor de nombres allí será solo localhost. NetworkManager también escribe un archivo /run/NetworkManager/no-stub-resolv.conf que contiene los servidores de nombres originales enviados al plugin DNS.

Cuando se utiliza dnsmasq, systemd-resolved y dnsconfd, los servidores DNS agregados por conexión siempre se consultarán utilizando el dispositivo en el que se activó la conexión.

rc-manager

Establece el modo de gestión de resolv.conf. Esta opción trata sobre cómo NetworkManager escribe en /etc/resolv.conf, si es que lo hace. El valor predeterminado depende de las opciones de compilación de NetworkManager, y esta versión de NetworkManager se compiló con un valor predeterminado de "symlink". Independientemente de esta configuración, NetworkManager siempre escribirá su versión de resolv.conf en su directorio de estado de ejecución como /run/NetworkManager/resolv.conf.

Si configura dns=none o hace que /etc/resolv.conf sea inmutable con chattr +i, NetworkManager ignorará esta configuración y siempre elegirá unmanaged (a continuación).

auto: si el plugin systemd-resolved está configurado a través de la configuración de dns o si se detecta como el plugin DNS principal, NetworkManager actualizará systemd-resolved sin tocar /etc/resolv.conf. Alternativamente, si resolvconf o netconfig están habilitados en tiempo de compilación y se encuentra el binario respectivo, NetworkManager lo usará automáticamente. Tenga en cuenta que si instala o desinstala estos binarios, deberá recargar la configuración de rc-manager con SIGHUP o systemctl reload NetworkManager. Como último recurso, utiliza la opción symlink (ver la siguiente).

symlink: Si /etc/resolv.conf es un archivo regular o no existe, NetworkManager escribirá el archivo directamente. Si /etc/resolv.conf es en cambio un enlace simbólico, NetworkManager lo dejará solo. A menos que el enlace simbólico apunte al archivo interno /run/NetworkManager/resolv.conf, en cuyo caso el enlace simbólico se actualizará para emitir una notificación inotify. Esto permite al usuario indicar cómodamente a NetworkManager que no gestione /etc/resolv.conf reemplazándolo con un enlace simbólico.

file: NetworkManager escribirá /etc/resolv.conf como un archivo regular. Si encuentra un enlace simbólico a un destino existente, seguirá el enlace simbólico y actualizará el destino en su lugar. En ningún caso se reemplazará un enlace simbólico existente por un archivo. Tenga en cuenta que las versiones anteriores de NetworkManager se comportaban de manera diferente y reemplazaban los enlaces simbólicos caídos con un archivo plano.

resolvconf: NetworkManager ejecutará resolvconf para actualizar la configuración de DNS.

netconfig: NetworkManager ejecutará netconfig para actualizar la configuración de DNS.

unmanaged: no tocar /etc/resolv.conf.

none: alias obsoleto para symlink.

systemd-resolved

Además, envía la configuración de DNS de la conexión a systemd-resolved. Por defecto es "true".

Tenga en cuenta que esta configuración no tiene ningún efecto si el plugin principal dns ya es systemd-resolved. Es complementaria a la configuración dns para configurar systemd-resolved junto con el plugin principal.

Si systemd-resolved está habilitado, ya sea a través de esta configuración o del plugin DNS principal, la verificación de conectividad resuelve el nombre de host por dispositivo.

debug

Lista separada por comas de opciones para ayudar en la depuración. Este valor se combinará con la variable de entorno NM_DEBUG. Actualmente, se admiten los siguientes valores:

RLIMIT_CORE: establece ulimit -c unlimited para escribir volcados de núcleo. Tenga cuidado, ya que un volcado de núcleo puede contener información sensible como contraseñas o configuraciones.

fatal-warnings: establece g_log_set_always_fatal() para volcar el núcleo ante mensajes de advertencia de glib. Esto es equivalente a la opción de línea de comandos --g-fatal-warnings.

autoconnect-retries-default

El número de veces que se debe intentar la activación de una conexión automáticamente antes de cambiar a otra. Este valor se aplica solo a las conexiones que pueden auto-conectarse y tienen la propiedad connection.autoconnect-retries establecida en -1. Si no se especifica, se intentará la activación de las conexiones 4 veces. Establecer este valor en 1 significa intentar la activación una vez, sin reintento.

firewall-backend

El backend de firewall para configurar el enmascaramiento en modo compartido. Establecer en iptables, nftables o none. iptables y nftables requieren la aplicación de iptables y nft, respectivamente. none significa omitir la configuración del firewall si los usuarios desean administrar el firewall ellos mismos. Si no se especifica, se detectará automáticamente.

iwd-config-path

Si el valor es "auto" (el predeterminado), se consulta a IWD su directorio de estado actual cuando aparece en D-Bus — el directorio donde IWD guarda sus archivos de configuración de red — generalmente /var/lib/iwd. NetworkManager intentará escribir copias de los perfiles de conexión nuevos o modificados, convertidos al formato IWD, en este directorio, haciendo así que las propiedades de conexión de IWD sean editables. NM sobrescribirá los archivos existentes sin preservar su contenido.

La ruta también se puede anular apuntando a un directorio específico existente y escribible. Por otro lado, establecer esto a una cadena vacía o cualquier otro valor deshabilita el mecanismo de conversión de perfiles.

Este mecanismo permite editar la configuración del perfil de conexión, como la configuración 802.1x, utilizando clientes de NetworkManager. Sin él, dichos cambios no tienen ningún efecto en IWD.

migrate-ifcfg-rh

Si NetworkManager intenta convertir automáticamente cualquier perfil de conexión almacenado en formato ifcfg-rh al formato keyfile. El soporte para ifcfg-rh está obsoleto y eventualmente se eliminará. Si está habilitado, la migración se realiza en cada inicio del demonio. El valor predeterminado es false.

SECCIÓN KEYFILE

Esta sección contiene opciones específicas del plugin keyfile, y normalmente solo se usa cuando no se está utilizando ningún otro plugin específico de la distribución.

hostname

Esta clave está obsoleta y no tiene ningún efecto ya que el nombre de host ahora se almacena en /etc/hostname u otros archivos de configuración del sistema según las opciones de compilación.

path

La ubicación donde se leen y almacenan los archivos clave. El valor predeterminado es "/etc/NetworkManager/system-connections".

rename

NetworkManager elige automáticamente un nombre de archivo al almacenar un nuevo perfil en el disco. Ese nombre depende del nombre del perfil (connection.id). Al actualizar el nombre de un perfil, el archivo no se renombra para no romper scripts que dependen del nombre del archivo para el perfil. Al establecer esta opción en "true", NetworkManager renombra el archivo clave al actualizar el perfil, para seguir el nombre del perfil. El valor predeterminado es "false".

unmanaged-devices

Establece los dispositivos que deben ser ignorados por NetworkManager.

Un dispositivo no gestionado debido a esta opción es estrictamente no gestionado y no puede ser anulado usando la API como nmcli device set $IFNAME managed yes. Además, un dispositivo que no está gestionado por otras razones, como una regla udev, no puede ser gestionado con esta opción (por ejemplo, usando un especificador except:). Estos dos puntos lo diferencian de la opción device*.managed que por esa razón puede ser una mejor opción.

Vea la sección "Formato de Lista de Dispositivos" para la sintaxis sobre cómo especificar un dispositivo.

Ejemplo:

unmanaged-devices=interface-name:em4
unmanaged-devices=mac:00:22:68:1c:59:b1;mac:00:1E:65:30:D1:C4;interface-name:eth2

SECCIÓN IFUPDOWN

Esta sección contiene opciones específicas de ifupdown y, por lo tanto, solo tiene efecto cuando se utiliza el plugin ifupdown.

managed

Si se establece en true, entonces las interfaces listadas en /etc/network/interfaces son gestionadas por NetworkManager. Si se establece en false, entonces cualquier interfaz listada en /etc/network/interfaces será ignorada por NetworkManager. Recuerde que NetworkManager controla la ruta predeterminada, por lo que, dado que la interfaz se ignora, NetworkManager puede asignar la ruta predeterminada a alguna otra interfaz.

El valor predeterminado es false.

SECCIÓN DE REGISTRO

SECCIÓN DE REGISTRO

Esta sección controla el registro de NetworkManager. El registro es muy importante para comprender lo que hace NetworkManager. Cuando informe de un error, no filtre ni limite innecesariamente el archivo de registro. Simplemente active level=TRACE y domains=ALL para recopilar todo.

La forma recomendada de habilitar el registro es con un archivo /etc/NetworkManager/conf.d/95-logging.conf que contenga

[logging]
level=TRACE
domains=ALL

y reinicie el demonio con systemctl restart NetworkManager. Luego reproduzca el problema. Puede encontrar los registros en syslog (por ejemplo, journalctl, o journalctl -u NetworkManager para mostrar solo los registros de NetworkManager).

Cualquier configuración aquí se anula con las opciones de línea de comandos --log-level y --log-domains. El registro también se puede reconfigurar en tiempo de ejecución con nmcli general logging level "$LEVEL" domains "$DOMAINS". Sin embargo, a menudo es interesante obtener un registro completo desde el principio. Especialmente, al depurar un problema, active el registro de depuración en NetworkManager.conf y reinicie el servicio para habilitar el registro detallado desde el principio.

Al establecer nm.debug en la línea de comandos del kernel (ya sea desde /run/NetworkManager/proc-cmdline o /proc/cmdline), se habilita el registro de depuración. Esto anula tanto las opciones de línea de comandos como la configuración de NetworkManager.conf.

El registro de NetworkManager tiene como objetivo no contener datos privados confidenciales y debería estar bien compartir los registros de depuración. Aún así, habrá direcciones IP y su configuración de red, si considera que eso es privado, revise el registro antes de compartirlo. Sin embargo, intente no alterar el archivo de registro de una manera que distorsione demasiado el significado.

NetworkManager utiliza syslog o systemd-journald, según la configuración. En cualquier caso, los registros de depuración son detallados y pueden ser limitados en velocidad o filtrados por el demonio de registro. Para systemd-journald, consulte RateLimitIntervalSec y RateLimitBurst en el manual de journald.conf para saber cómo deshabilitar eso.

level

El nivel de detalle del registro predeterminado. Uno de OFF, ERR, WARN, INFO, DEBUG, TRACE, en orden de detalle.

OFF deshabilita todo el registro. INFO es el nivel de detalle predeterminado para operaciones regulares. TRACE es para depuración.

Los otros niveles, en la mayoría de los casos, no son útiles. Por ejemplo, DEBUG está entre TRACE e INFO, pero es demasiado detallado para operaciones regulares y carece de mensajes potencialmente interesantes para la depuración. Casi siempre, al depurar un problema o informar un error, recopile registros completos de nivel TRACE para obtener la imagen completa.

domains

Filtra los mensajes por su tema. Al depurar un problema, es mejor recopilar todos los registros (dominio ALL) de antemano. Las partes innecesarias siempre se pueden ignorar más tarde.

En el caso poco común de ajustar ciertos temas, los siguientes dominios de registro están disponibles: PLATFORM, RFKILL, ETHER, WIFI, BT, MB, DHCP4, DHCP6, PPP, WIFI_SCAN, IP4, IP6, AUTOIP4, DNS, VPN, SHARING, SUPPLICANT, AGENTS, SETTINGS, SUSPEND, CORE, DEVICE, OLPC, WIMAX, INFINIBAND, FIREWALL, ADSL, BOND, VLAN, BRIDGE, DBUS_PROPS, TEAM, CONCHECK, DCB, DISPATCH, AUDIT, SYSTEMD, VPN_PLUGIN, PROXY.

Además, se pueden usar estos dominios especiales: NONE, ALL, DEFAULT, DHCP, IP.

Puede especificar anulaciones de nivel de registro por dominio agregando dos puntos y un nivel de registro a cualquier dominio. Por ejemplo, "WIFI:DEBUG,WIFI_SCAN:OFF". Otro ejemplo es ALL,VPN_PLUGIN:TRACE para habilitar todo el registro existente (ver sobre VPN_PLUGIN más abajo).

Puede configurar varias secciones de conexión, teniendo diferentes secciones con un nombre que comience con "connection". Ejemplo:

[connection]

ipv4.route-metric=50
[connection-wifi-other]
match-device=type:wifi
ipv4.route-metric=55
ipv6.ip6-privacy=1

Las secciones dentro de un archivo se consideran en el orden de aparición, con la excepción de que la sección [connection] siempre se considera la última. En el ejemplo anterior, este orden es [connection-wifi-wlan0], [connection-wlan-other] y [connection]. Al buscar un valor de configuración predeterminado, las secciones se buscan hasta que se encuentra el valor solicitado. En el ejemplo anterior, "ipv4.route-metric" para la interfaz wlan0 se establece en 50, y para todas las demás interfaces de tipo Wi-Fi en 55. Además, los dispositivos Wi-Fi tendrían direcciones privadas IPv6 habilitadas por defecto, pero otros dispositivos la tendrían deshabilitada. Tenga en cuenta que "wlan0" también obtiene "ipv6.ip6-privacy=1", porque aunque la sección "[connection-wifi-wlan0]" coincide con el dispositivo, no contiene esa propiedad y la búsqueda continúa.

Al tener diferentes secciones en múltiples archivos, las secciones de los archivos que se leen más tarde tienen mayor prioridad. Por lo tanto, dentro de un archivo, la prioridad de las secciones es de arriba a abajo. Entre múltiples archivos, las definiciones posteriores tienen precedencia.

Propiedades Soportadas

Las siguientes propiedades pueden ser configuradas por dispositivo.

managed

Si el dispositivo es gestionado o no. Un dispositivo puede ser marcado como gestionado a través de reglas udev (ENV{NM_UNMANAGED}), o a través de plugins de configuración (keyfile.unmanaged-devices). Esta es otra forma más. Ten en cuenta que esta configuración puede ser anulada en tiempo de ejecución a través de D-Bus. Además, tiene mayor prioridad que las reglas udev.

carrier-wait-timeout

Especifica el tiempo de espera para la portadora en milisegundos. El valor por defecto es 6000 milisegundos. Esta configuración existe porque ciertos drivers/hardware pueden tardar mucho tiempo en detectar si el cable está enchufado.

Cuando el dispositivo pierde la portadora, NetworkManager no reacciona inmediatamente. En su lugar, espera este tiempo de espera antes de considerar el enlace como perdido.

Además, al iniciar, NetworkManager considera el dispositivo como ocupado durante este tiempo, siempre que el dispositivo no tenga portadora. Esto retrasa la señal de inicio completado y NetworkManager-wait-online. Configurar esto demasiado alto significa bloquear NetworkManager-wait-online más de lo necesario al arrancar con el cable desconectado. Configurar esto demasiado bajo significa que NetworkManager declarará el inicio completado demasiado pronto, aunque la portadora esté a punto de llegar y la autoactivación se active. Ten en cuenta que si un perfil solo tiene configuración IP estática o la configuración de Capa 3 está deshabilitada, entonces ya puede conectarse automáticamente sin portadora en el dispositivo. Una vez que dicho perfil alcanza el estado completamente activado, se considera que el inicio se ha completado incluso si el dispositivo aún no tiene portadora.

ignore-carrier

Especifica los dispositivos para los cuales NetworkManager ignorará (parcialmente) el estado de la portadora. Normalmente, para tipos de dispositivos que soportan detección de portadora, como Ethernet e InfiniBand, NetworkManager solo permitirá la activación de una conexión en el dispositivo si la portadora está presente (es decir, si el cable está enchufado), y desactivará el dispositivo si la portadora cae durante más de unos pocos segundos.

Un dispositivo con portadora ignorada permitirá la activación de conexiones en ese dispositivo incluso cuando no tenga portadora, siempre que la conexión utilice solo direcciones IP configuradas estáticamente. Además, permitirá que cualquier conexión activa (ya sea estática o dinámica) permanezca activa en el dispositivo cuando se pierda la portadora.

Ten en cuenta que la propiedad "carrier" de los NMDevices y las interfaces de D-Bus del dispositivo seguirán reflejando el estado real del dispositivo; es solo que NetworkManager no utilizará esa información.

Los tipos maestros como bond, bridge y team ignoran la portadora por defecto, mientras que otros tipos de dispositivos reaccionan a los cambios de portadora por defecto.

Esta configuración anula la configuración obsoleta main.ignore-carrier mencionada anteriormente.

keep-configuration

Al iniciar, NetworkManager intenta no interferir con las interfaces que ya están configuradas. Lo hace generando una conexión en memoria basada en la configuración actual de la interfaz.

Si esta conexión generada coincide con una de las conexiones persistentes existentes, la conexión persistente se activará. Si no hay coincidencia, la conexión generada se activará como "externa", lo que significa que la conexión se considera activa, pero NetworkManager no toca realmente la interfaz.

Es posible deshabilitar este comportamiento estableciendo keep-configuration a no. De esta manera, al iniciar, NetworkManager siempre intenta activar la conexión persistente más adecuada (la de mayor autoconnect-priority o, en caso de empate, la activada más recientemente).

Ten en cuenta que cuando NetworkManager se reinicia, almacena el estado anterior en /run/NetworkManager; en particular, guarda el UUID de la conexión que estaba activa anteriormente para poder activarla nuevamente después del reinicio. Por lo tanto, keep-configuration no tiene ningún efecto en el reinicio del servicio.

allowed-connections

Una lista de conexiones que pueden ser activadas en el dispositivo. Consulta la sección "Formato de Lista de Conexiones" para conocer la sintaxis para especificar una conexión. Si esta opción no se especifica, todas las conexiones pueden ser potencialmente activadas en el dispositivo, siempre que el tipo de conexión y otras configuraciones coincidan.

Un caso de uso notable para esto es filtrar qué conexiones pueden ser activadas en función de cómo fueron creadas; consulta la palabra clave origin en la sección "Formato de Lista de Conexiones".

SECCIÓN CONNECTIVITY

Esta sección controla la funcionalidad opcional de verificación de conectividad de NetworkManager. Esto permite a NetworkManager detectar si el sistema puede acceder a Internet o si está detrás de un portal cautivo.

La verificación de conectividad tiene dos propósitos. Por un lado, expone un estado de conectividad en D-Bus, que otras aplicaciones pueden usar. Por ejemplo, el ayudante de portal de Gnome utiliza esto como señal para mostrar una página de inicio de sesión de portal cautivo. El otro uso es que la ruta por defecto de los dispositivos sin conectividad global reciben una penalización de +20000 a la métrica de ruta. Esto tiene el propósito de proporcionar una mejor ruta por defecto a los dispositivos que tienen conectividad global. Por ejemplo, cuando se está conectado a WWAN y a una red Wi-Fi que está detrás de un portal cautivo, WWAN sigue siendo preferida hasta el inicio de sesión.

Ten en cuenta que tu distribución podría establecer /proc/sys/net/ipv4/conf/*/rp_filter a filtrado estricto. Eso funciona mal con la verificación de conectividad por dispositivo, que utiliza SO_BINDDEVICE para enviar solicitudes en todos los dispositivos. Una configuración rp_filter estricta rechazará cualquier respuesta y la verificación de conectividad en todas las rutas excepto en la mejor fallará.

enabled

Si la verificación de conectividad está habilitada. Ten en cuenta que para habilitar la verificación de conectividad, también se debe configurar una uri válida. El valor por defecto es true, pero dado que la uri no está definida por defecto, la verificación de conectividad puede estar deshabilitada. El propósito principal de esta opción es tener una sola bandera para deshabilitar la verificación de conectividad. Ten en cuenta que esta configuración también puede ser establecida a través de la API de D-Bus en tiempo de ejecución. En ese caso, el valor se almacena en el archivo /var/lib/NetworkManager/NetworkManager-intern.conf.

uri

La URI de una página web a solicitar periódicamente cuando se está verificando la conectividad. Esta página debe devolver la cabecera "X-NetworkManager-Status" con un valor de "online". Alternativamente, el contenido de su cuerpo debe ser "NetworkManager is online". La comprobación del contenido del cuerpo puede ser controlada por la opción response. Si esta opción está en blanco o no está presente, la verificación de conectividad está deshabilitada.

interval

Especificado en segundos; controla la frecuencia con la que se verifica la conectividad cuando existe una conexión de red. Si se establece en 0, la verificación de conectividad se deshabilita. Si no está presente, el valor por defecto es 300 segundos.

timeout

Especificado en segundos; controla cuánto tiempo esperar una respuesta antes de que la conectividad se marque como limitada. Si no está presente, el valor por defecto es 20 segundos.

response

Si se establece, controla qué contenido del cuerpo verifica NetworkManager al solicitar la URI para la verificación de conectividad. Ten en cuenta que esto solo compara si la respuesta HTTP comienza con el texto especificado, no compara la cadena exacta. Este comportamiento podría cambiar en el futuro, así que evita depender de él. Si no está presente, la respuesta por defecto es "NetworkManager is online". Si se establece en vacío, se espera que el servidor HTTP responda con el código de estado 204 o no envíe datos.

Sections with a name starting with the "global-dns-" prefix allow one to define global DNS configuration that is not tied to any specific connection. Currently, only the Dnsconfd plugin is using this section.

The section name without the prefix defines the domain name which the configuration applies to. The part of section name after "global-dns-" specifies the domain name a section applies to (for example, a section could be named "global-dns-foobar.com"). More specific domains have the precedence over less specific ones and the default domain is represented by the wildcard "*". To be valid, global DNS domains must include a section for the default domain "*". When global DNS domains are valid, the name servers and domains defined globally override the ones from active connections.

servers

A list of addresses of DNS servers to be used for the given domain. Each server can be specified either as a plain IP address or with a URI syntax. When it is specified as an URI, the following forms are supported:
dns+udp://ADDRESS[:PORT] : DNS
dns+tls://ADDRESS[:PORT][#SERVERNAME] : DNS over TLS

ADDRESS is an IPv4 or IPv6 address. When it is IPv6, it must be enclosed in square brackets ('[' and ']'). When it is a IPv6 link-local address, the address should be followed by a percent sign ('%') and an interface name.

hostname

A list of hostnames that are relevant to the current domain.

options

A list of options to be passed to the hostname resolver.

resolve-mode

String indicating how DNS servers retrieved from global configuration and connections should be used. backup - Indicates that they can be freely merged and used for the same purposes. prefer - Forbids DNS servers retrieved from connections to be used for general queries that are not subdomains of domains set by connection. exclusive - Forbids use of connection DNS servers for any query. Currently relevant only for Dnsconfd plugin.

certification-authority

String specifying absolute path to bundle of CA certificates that must be used for validation of certificates presented by DNS servers when encrypted DNS is used. Currently relevant only for Dnsconfd plugin.

GLOBAL-DNS-DOMAIN SECTIONS

Sections with a name starting with the "global-dns-domain-" prefix allow one to define global DNS configuration for specific domains. The part of section name after "global-dns-domain-" specifies the domain name a section applies to (for example, a section could be named "global-dns-domain-foobar.com"). More specific domains have the precedence over less specific ones and the default domain is represented by the wildcard "*". To be valid, global DNS domains must include a section for the default domain "*". When the global DNS domains are valid, the name servers and domains defined globally override the ones from active connections. If any global DNS domain is defined but a [global-dns] section isn't, an empty [global-dns] section is assumed, thus overwriting its connection specific configurations too.

servers

A list of addresses of DNS servers to be used for the given domain. Each server can be specified either as a plain IP address or with a URI syntax. When it is specified as an URI, the following forms are supported:
dns+udp://ADDRESS[:PORT] : DNS
dns+tls://ADDRESS[:PORT][#SERVERNAME] : DNS over TLS

ADDRESS is an IPv4 or IPv6 address. When it is IPv6, it must be enclosed in square brackets ('[' and ']'). When it is a IPv6 link-local address, the address should be followed by a percent sign ('%') and an interface name.

options

A list of domain-specific DNS options. Not used at the moment.

.CONFIG SECTIONS

This is a special section that contains options which apply to the configuration file that contains the option.

enable

Defaults to "true". If "false", the configuration file will be skipped during loading. Note that the main configuration file NetworkManager.conf cannot be disabled. 
# always skip loading the config file
[.config]
enable=false

You can also match against the version of NetworkManager. For example the following are valid configurations:

# only load on version 1.0.6
[.config]
enable=nm-version:1.0.6
# load on all versions 1.0.x, but not 1.2.x
[.config]
enable=nm-version:1.0
# only load on versions >= 1.1.6. This does not match
# with version 1.2.0 or 1.4.4. Only the last digit is considered.
[.config]
enable=nm-version-min:1.1.6
# only load on versions >= 1.2. Contrary to the previous
# example, this also matches with 1.2.0, 1.2.10, 1.4.4, etc.
[.config]
enable=nm-version-min:1.2
# Match against the maximum allowed version. The example matches
# versions 1.2.0, 1.2.2, 1.2.4. Again, only the last version digit
# is allowed to be smaller. So this would not match on 1.1.10.
[.config]
enable=nm-version-max:1.2.6

You can also match against the value of the environment variable NM_CONFIG_ENABLE_TAG, like:

# only load the file when running NetworkManager with
# environment variable "NM_CONFIG_ENABLE_TAG=TAG1"
[.config]
enable=env:TAG1

More then one match can be specified. The configuration will be enabled if one of the predicates matches ("or"). The special prefix "except:" can be used to negate the match. Note that if one except-predicate matches, the entire configuration will be disabled. In other words, a except predicate always wins over other predicates. If the setting only consists of "except:" matches and none of the negative conditions are satisfied, the configuration is still enabled.

# enable the configuration either when the environment variable
# is present or the version is at least 1.2.0.
[.config]
enable=env:TAG2,nm-version-min:1.2
# enable the configuration for version >= 1.2.0, but disable
# it when the environment variable is set to "TAG3"
[.config]
enable=except:env:TAG3,nm-version-min:1.2
# enable the configuration on >= 1.3, >= 1.2.6, and >= 1.0.16.
# Useful if a certain feature is only present since those releases.
[.config]
enable=nm-version-min:1.3,nm-version-min:1.2.6,nm-version-min:1.0.16

PLUGINS

Settings plugins for reading and writing connection profiles. The number of available plugins is distribution specific.

keyfile

The keyfile plugin is the generic plugin that supports all the connection types and capabilities that NetworkManager has. It writes files out in an .ini-style format in /etc/NetworkManager/system-connections. See nm-settings-keyfile(5) for details about the file format.

The stored connection file may contain passwords, secrets and private keys in plain text, so it will be made readable only to root, and the plugin will ignore files that are readable or writable by any user or group other than root. See "Secret flag types" in nm-settings-nmcli(5) for how to avoid storing passwords in plain text.

This plugin is always active, and will automatically be used to store any connections that aren't supported by any other active plugin.

ifcfg-rh

This plugin is now deprecated; it can be used on the Fedora and Red Hat Enterprise Linux distributions to read and write configuration from the standard /etc/sysconfig/network-scripts/ifcfg-* files. It currently supports reading Ethernet, Wi-Fi, InfiniBand, VLAN, Bond, Bridge, and Team connections. Enabling ifcfg-rh implicitly enables ibft plugin, if it is available. This can be disabled by adding no-ibft. See /usr/share/doc/initscripts/sysconfig.txt and nm-settings-ifcfg-rh(5) for more information about the ifcfg file format.

ifupdown

This plugin is used on the Debian and Ubuntu distributions, and reads Ethernet and Wi-Fi connections from /etc/network/interfaces.

This plugin is read-only; any connections (of any type) added from within NetworkManager when you are using this plugin will be saved using the keyfile plugin instead.

ibft, no-ibft

These plugins are deprecated and their selection has no effect. This is now handled by nm-initrd-generator.

ifcfg-suse, ifnet

These plugins are deprecated and their selection has no effect. The keyfile plugin should be used instead.

APPENDIX

Device List Format

The configuration options main.no-auto-default, main.ignore-carrier, keyfile.unmanaged-devices, connection*.match-device and device*.match-device select devices based on a list of matchings. Devices can be specified using the following format:

*

Matches every device.

IFNAME

Case sensitive match of interface name of the device. Globbing is not supported.

HWADDR

Match the permanent MAC address of the device. Globbing is not supported

interface-name:IFNAME, interface-name:~IFNAME

Case sensitive match of interface name of the device. Simple globbing is supported with * and ?. Ranges and escaping is not supported.

interface-name:=IFNAME

Case sensitive match of interface name of the device. Globbing is disabled and IFNAME is taken literally.

mac:HWADDR

Match the permanent MAC address of the device. Globbing is not supported

s390-subchannels:HWADDR

Match the device based on the subchannel address. Globbing is not supported

type:TYPE

Match the device type. Valid type names are as reported by "nmcli -f GENERAL.TYPE device show". Globbing is not supported.

driver:DRIVER

Match the device driver as reported by "nmcli -f GENERAL.DRIVER,GENERAL.DRIVER-VERSION device show". "DRIVER" must match the driver name exactly and does not support globbing. Optionally, a driver version may be specified separated by '/'. Globbing is supported for the version.

dhcp-plugin:DHCP

Match the configured DHCP plugin "main.dhcp".

except:SPEC

Negative match of a device. SPEC must be explicitly qualified with a prefix such as interface-name:. A negative match has higher priority then the positive matches above.

If there is a list consisting only of negative matches, the behavior is the same as if there is also match-all. That means, if none of all the negative matches is satisfied, the overall result is still a positive match. That means, "except:interface-name:eth0" is the same as "*,except:interface-name:eth0".

SPEC[,;]SPEC

Multiple specs can be concatenated with commas or semicolons. The order does not matter as matches are either inclusive or negative (except:), with negative matches having higher priority.

Backslash is supported to escape the separators ';' and ',', and to express special characters such as newline ('\n'), tabulator ('\t'), whitespace ('\s') and backslash ('\\'). The globbing of interface names cannot be escaped. Whitespace is not a separator but will be trimmed between two specs (unless escaped as '\s').

Example:

interface-name:em4
mac:00:22:68:1c:59:b1;mac:00:1E:65:30:D1:C4;interface-name:eth2

Formato de Lista de Conexiones

Las conexiones se pueden especificar usando el siguiente formato:

*

Coincide con todas las conexiones.

uuid:UUID

Coincide con la conexión por UUID, por ejemplo "uuid:83037490-1d17-4986-a397-01f1db3a7fc2"

id:ID

Coincide con la conexión por nombre.

origin:ORIGIN

Coincide con la conexión por origen, almacenado en la etiqueta org.freedesktop.NetworkManager.origin de la configuración del usuario. Por ejemplo, usa "except:origin:nm-initrd-generator" para prohibir la activación de conexiones creadas por el generador initrd.

except:SPEC

Coincidencia negativa de una conexión. Una coincidencia negativa tiene mayor prioridad que las coincidencias positivas anteriores.

Si hay una lista que consiste solo en coincidencias negativas, el comportamiento es el mismo que si también hubiera una coincidencia general. Es decir, si ninguna de todas las coincidencias negativas se satisface, el resultado general sigue siendo una coincidencia positiva.

SPEC[,;]SPEC

Se pueden concatenar varias especificaciones con comas o punto y coma. El orden no importa, ya que las coincidencias son inclusivas o negativas (except:), con las coincidencias negativas teniendo mayor prioridad.

Se admite la barra invertida para escapar los separadores ';' y ',', y para expresar caracteres especiales como nueva línea ('\n'), tabulador ('\t'), espacio en blanco ('\s') y barra invertida ('\\'). El espacio en blanco no es un separador sino que se recortará entre dos especificaciones (a menos que se escape como '\s').
