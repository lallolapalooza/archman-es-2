NM-CLOUD-SETUP(8) Configuración de Red Automática NM-CLOUD-SETUP(8)

NOMBRE

nm-cloud-setup - Descripción general de la configuración de red automática en la nube

DESCRIPCIÓN GENERAL

Al ejecutar una máquina virtual en un entorno de nube pública, es deseable configurar automáticamente la red de esa VM. En configuraciones simples, la VM solo tiene una interfaz de red y la nube pública admite la configuración automática a través de DHCP, DHCP6 o autoconfiguración IPv6. Sin embargo, la máquina virtual podría tener múltiples interfaces de red, o múltiples direcciones IP y subredes IP en una sola interfaz que no se pueden configurar a través de DHCP. Además, el administrador puede reconfigurar la red mientras la máquina está en funcionamiento. nm-cloud-setup de NetworkManager es una herramienta que recopila automáticamente dicha configuración en entornos de nube y actualiza la configuración de red del host.

Se admiten múltiples proveedores de nube. Consulte la sección llamada “PROVEEDORES DE NUBE COMPATIBLES”.

USO

El objetivo de nm-cloud-setup es no requerir configuración y funcionar automáticamente. Todo lo que necesita es optar por los proveedores de nube deseados (consulte la sección llamada “VARIABLES_DE_ENTORNO”) y ejecutar /usr/libexec/nm-cloud-setup.

Por lo general, esto se hace habilitando el servicio systemd nm-cloud-setup.service y dejándolo ejecutarse periódicamente. Para ello, existe tanto un temporizador systemd nm-cloud-setup.timer como un script de dispatcher de NetworkManager.

DETALLES

nm-cloud-setup configura la red obteniendo la configuración del servidor de metadatos conocido del proveedor de la nube. Esto significa que ya necesita que la red esté configurada hasta el punto en que pueda alcanzar el servidor de metadatos. Comúnmente, esto significa que se activa un perfil de conexión simple que posiblemente utiliza DHCP para obtener la dirección IP principal. NetworkManager creará dicho perfil para los dispositivos Ethernet automáticamente si no se configura de otra manera mediante la configuración "no-auto-default" en NetworkManager.conf. Una posible alternativa puede ser crear dicho perfil inicial con nmcli device connect "$DEVICE" o nmcli connection add type ethernet ....

Al establecer la propiedad user-data org.freedesktop.nm-cloud-setup.skip=yes en el perfil, nm-cloud-setup omitirá el dispositivo.

nm-cloud-setup modifica la configuración en tiempo de ejecución de forma similar a nmcli device modify. Con este enfoque, la configuración no se guarda y solo se conserva hasta que el dispositivo se desconecta.

/usr/libexec/nm-cloud-setup

El binario /usr/libexec/nm-cloud-setup hace la mayor parte del trabajo. No admite argumentos de línea de comandos, pero se puede configurar a través de variables de entorno. Consulte la sección llamada “VARIABLES_DE_ENTORNO” para conocer las variables de entorno compatibles.

Por defecto, todos los proveedores de nube están deshabilitados a menos que opte por habilitar uno o varios proveedores. Si los proveedores de nube están habilitados, el programa intenta obtener la configuración del host de un servidor de metadatos de la nube a través de HTTP. Si no se pudo obtener la configuración, no se detectan proveedores de nube y el programa finaliza. Si se obtiene la configuración del host, se detecta correctamente el proveedor de nube correspondiente. Luego se configurará la red del host.

Está previsto volver a ejecutar nm-cloud-setup cada vez que la configuración (quizás) cambie. La herramienta es idempotente, por lo que debería estar bien ejecutarla más veces de las necesarias. Podría ejecutar /usr/libexec/nm-cloud-setup directamente. Sin embargo, puede ser preferible reiniciar el servicio systemd nm-cloud-setup en su lugar o utilizar el temporizador o el script de dispatcher para ejecutarlo periódicamente (ver más abajo).

Unidad systemd nm-cloud-setup.service

Por lo general, /usr/libexec/nm-cloud-setup no se ejecuta directamente, sino solo con systemctl restart nm-cloud-setup.service. Esto garantiza que la herramienta solo se ejecute una vez en cualquier momento. La unidad también es utilizada por el temporizador systemd nm-cloud-setup y permite habilitar/deshabilitar el servicio a través de systemd.

Dado que necesita configurar variables de entorno para el binario nm-cloud-setup, puede hacerlo a través de archivos de anulación de systemd. Pruebe con systemctl edit nm-cloud-setup.service.

Temporizador systemd nm-cloud-setup.timer

/usr/libexec/nm-cloud-setup está diseñado para ejecutarse cada vez que sea necesaria una actualización. Por ejemplo, durante el arranque o cuando se cambia la configuración de red de la máquina virtual a través del proveedor de la nube.

Una forma de hacerlo es habilitando el temporizador systemd nm-cloud-setup.timer con systemctl enable --now nm-cloud-setup.timer.

/usr/lib/NetworkManager/dispatcher.d/90-nm-cloud-setup.sh

También hay un script de dispatcher de NetworkManager que se ejecutará, por ejemplo, cuando NetworkManager active una interfaz. Junto con el temporizador systemd nm-cloud-setup.timer, este script está destinado a detectar automáticamente los cambios en la red.

El script de dispatcher no hará nada, a menos que el servicio systemd esté habilitado. Para usar el script de dispatcher, por lo tanto, debe ejecutar systemctl enable nm-cloud-setup.service una vez.

VARIABLES DE ENTORNO

Las siguientes variables de entorno se utilizan para configurar /usr/libexec/nm-cloud-setup. Es posible que desee configurarlas con un archivo de anulación para el servicio systemd. Por ejemplo, llamando a systemctl edit nm-cloud-setup.service y configurando [Service] Environment=, como se describe en el manual de systemd.exec(5).

•NM_CLOUD_SETUP_LOG: controla la verbosidad del registro. Establézcala en uno de TRACE, DEBUG, INFO, WARN, ERR o OFF. El programa imprimirá mensajes en la salida estándar y el nivel predeterminado es WARN. Cuando se ejecuta como un servicio systemd, el registro será recopilado por journald y se puede ver con journalctl.
•NM_CLOUD_SETUP_AZURE: booleano, si el soporte de Microsoft Azure está habilitado. Por defecto es no.
•NM_CLOUD_SETUP_EC2: booleano, si el soporte de Amazon EC2 (AWS) está habilitado. Por defecto es no.
•NM_CLOUD_SETUP_GCP: booleano, si el soporte de Google GCP está habilitado. Por defecto es no.
•NM_CLOUD_SETUP_ALIYUN: booleano, si el soporte de Alibaba Cloud (Aliyun) está habilitado. Por defecto es no.
•NM_CLOUD_SETUP_OCI: booleano, si el soporte de Oracle Cloud (OCI) está habilitado. Por defecto es no.

DEPURACIÓN

Habilite el registro de depuración estableciendo la variable de entorno NM_CLOUD_SETUP_LOG en TRACE.

En el caso común donde nm-cloud-setup se ejecuta como un servicio systemd, esto se puede hacer editando systemctl edit nm-cloud-setup.service y agregando Environment=NM_CLOUD_SETUP_LOG=TRACE a la sección [Service]. Posteriormente, el registro se puede encontrar en syslog a través de journalctl. También puede que desee habilitar el registro de depuración en NetworkManager como se describe en la sección DEBUGGING del manual de NetworkManager(5). Al compartir registros, es mejor compartir registros completos y no filtrar preventivamente para los registros de NetworkManager o nm-cloud-setup.

EJEMPLO DE CONFIGURACIÓN PARA CONFIGURAR Y PREDEPLOYIR NM-CLOUD-SETUP

Como se detalló anteriormente, nm-cloud-setup debe habilitarse explícitamente. Como se ejecuta como un servicio y temporizador systemd, eso básicamente significa habilitar y configurar esos. Esto se puede hacer colocando los archivos y enlaces simbólicos correctos en el disco.

El siguiente ejemplo habilita nm-cloud-setup para la nube de Amazon EC2:

dnf install -y NetworkManager-cloud-setup
mkdir -p /etc/systemd/system/nm-cloud-setup.service.d
cat > /etc/systemd/system/nm-cloud-setup.service.d/10-enable-ec2.conf << EOF
[Service]
Environment=NM_CLOUD_SETUP_EC2=yes
EOF
# systemctl enable nm-cloud-setup.service
mkdir -p /etc/systemd/system/NetworkManager.service.wants/
ln -s /usr/lib/systemd/system/nm-cloud-setup.service /etc/systemd/system/NetworkManager.service.wants/nm-cloud-setup.service
# systemctl enable nm-cloud-setup.timer
mkdir -p /etc/systemd/system/timers.target.wants/
ln -s /etc/systemd/system/timers.target.wants/nm-cloud-setup.timer /usr/lib/systemd/system/nm-cloud-setup.t

PROVEEDORES DE NUBE SOPORTADOS
Amazon EC2 (AWS) Para AWS, las herramientas intentan obtener la configuración de http://169.254.169.254/ Actualmente, solo configura IPv4 y no hace nada con respecto a IPv6. Hará lo siguiente. Primero obtiene http://169.254.169.254/latest/meta-data/ para determinar si la API esperada está presente. Esto determina si el entorno EC2 se detecta y si se procede a configurar el host utilizando los metadatos de EC2. Obtiene http://169.254.169.254/2018-09-24/meta-data/network/interfaces/macs/ para obtener la lista de interfaces disponibles. Las interfaces se identifican por su dirección MAC. Luego, para cada interfaz, obtiene http://169.254.169.254/2018-09-24/meta-data/network/interfaces/macs/$MAC/subnet-ipv4-cidr-block y http://169.254.169.254/2018-09-24/meta-data/network/interfaces/macs/$MAC/local-ipv4s De esta manera, obtenemos una lista de direcciones IPv4 locales y un bloque de subred CIDR. Luego, nm-cloud-setup itera sobre todas las interfaces para las cuales pudo obtener la configuración IP. Si no se encuentra un dispositivo ethernet para la dirección MAC respectiva, se omite. Además, si el dispositivo no está activado actualmente en NetworkManager o si el perfil activado actualmente tiene datos de usuario org.freedesktop.nm-cloud-setup.skip=yes, se omite. Si solo se configura una interfaz y una dirección, la herramienta no hace nada y deja la configuración automática obtenida vía DHCP. De lo contrario, la herramienta cambiará la configuración en tiempo de ejecución del dispositivo. Añade direcciones IPv4 estáticas para todas las direcciones configuradas de local-ipv4s con longitud de prefijo según subnet-ipv4-cidr-block. Por ejemplo, podríamos tener aquí 2 direcciones IP como "172.16.5.3/24,172.16.5.4/24". Elige una tabla de rutas 30400 + el índice de la interfaz y añade una ruta por defecto 0.0.0.0/0. El gateway es la primera dirección IP en el bloque de subred CIDR. Por ejemplo, podríamos obtener una ruta "0.0.0.0/0 172.16.5.1 10 table=30400". También elige una tabla de rutas 30200 + el índice de la interfaz. Esto contiene rutas directas a las subredes de esta interfaz. Finalmente, añade una regla de enrutamiento por política para cada dirección. Por ejemplo "priority 30200 from 172.16.5.3/32 table 30200, priority 30200 from 172.16.5.4/32 table 30200". y "priority 30400 from 172.16.5.3/32 table 30400, priority 30400 from 172.16.5.4/32 table 30400" Las reglas 30200+ seleccionan la tabla para alcanzar la subred directamente, mientras que las reglas 30400+ usan la ruta por defecto. También añade una regla "priority 30350 table main suppress_prefixlength 0". Esto tiene una prioridad entre las dos reglas anteriores y causa una búsqueda de rutas en la tabla principal mientras ignora la ruta por defecto. El propósito de esto es que otras rutas específicas en la tabla principal se honren sobre la ruta por defecto en la tabla 30400+. Con el ejemplo anterior, esto corresponde aproximadamente para la interfaz eth0 a nmcli device modify "eth0" ipv4.addresses "172.16.5.3/24,172.16.5.4/24" ipv4.routes "172.16.5.0/24 0.0.0.0 10 table=30200, 0.0.0.0/0 172.16.5.1 10 table=30400" ipv4.routing-rules "priority 30200 from 172.16.5.3/32 table 30200, priority 30200 from 172.16.5.4/32 table 30200, priority 20350 table main suppress_prefixlength 0, priority 30400 from 172.16.5.3/32 table 30400, priority 30400 from 172.16.5.4/32 table 30400". Tenga en cuenta que esto reemplaza las direcciones, rutas y reglas anteriores con la nueva información. Pero también tenga en cuenta que esto solo cambia la configuración en tiempo de ejecución del dispositivo. El perfil de conexión en disco no se ve afectado.
Google Cloud Platform (GCP) Para GCP, los metadatos se obtienen de URIs que comienzan con http://metadata.google.internal/computeMetadata/v1/ con una cabecera HTTP "Metadata-Flavor: Google". Actualmente, la herramienta solo configura IPv4 y no hace nada con respecto a IPv6. Hará lo siguiente. Primero obtiene http://metadata.google.internal/computeMetadata/v1/instance/id para detectar si la herramienta se ejecuta en Google Cloud Platform. Solo si se detecta la plataforma, continuará obteniendo la configuración. Obtiene http://metadata.google.internal/computeMetadata/v1/instance/network-interfaces/ para obtener la lista de índices de interfaz disponibles. Estos índices se pueden utilizar para búsquedas posteriores. Luego, para cada interfaz, obtiene http://metadata.google.internal/computeMetadata/v1/instance/network-interfaces/$IFACE_INDEX/mac para obtener la dirección MAC correspondiente de las interfaces encontradas. La dirección MAC se utiliza para identificar el dispositivo más tarde. Luego, para cada interfaz con una dirección MAC, obtiene http://metadata.google.internal/computeMetadata/v1/instance/network-interfaces/$IFACE_INDEX/forwarded-ips/ y luego todas las direcciones IP encontradas en http://metadata.google.internal/computeMetadata/v1/instance/network-interfaces/$IFACE_INDEX/forwarded-ips/$FIPS_INDEX. En este punto, tenemos una lista de todas las interfaces (por dirección MAC) y sus direcciones IPv4 configuradas. Para cada dispositivo, buscamos la conexión actualmente aplicada en NetworkManager. Esto implica que el dispositivo está activado actualmente en NetworkManager. Si no se encontró dicho dispositivo en NetworkManager, o si el perfil tiene datos de usuario org.freedesktop.nm-cloud-setup.skip=yes, omitimos el dispositivo. Ahora, para cada dirección IP encontrada, añadimos una ruta estática "$FIPS_ADDR/32 0.0.0.0 100 type=local" y reaplicamos el cambio. El efecto no es diferente a llamar nmcli device modify "$DEVICE" ipv4.routes "$FIPS_ADDR/32 0.0.0.0 100 type=local [,...]" para todos los dispositivos relevantes y todas las direcciones encontradas.
Microsoft Azure Para Azure, los metadatos se obtienen de URIs que comienzan con http://169.254.169.254/metadata/instance con un parámetro de URL "?format=text&api-version=2017-04-02" y una cabecera HTTP "Metadata:true". Actualmente, la herramienta solo configura IPv4 y no hace nada con respecto a IPv6. Hará lo siguiente. Primero obtiene http://169.254.169.254/metadata/instance?format=text&api-version=2017-04-02 para detectar si la herramienta se ejecuta en Azure Cloud. Solo si se detecta la plataforma, continuará obteniendo la configuración. Obtiene http://169.254.169.254/metadata/instance/network/interface/?format=text&api-version=2017-04-02 para obtener la lista de índices de interfaz disponibles. Estos índices se pueden utilizar para búsquedas posteriores. Luego, para cada interfaz, obtiene http://169.254.169.254/metadata/instance/network/interface/$IFACE_INDEX/macAddress?format=text&api-version=2017-04-02 para obtener la dirección MAC correspondiente de las interfaces encontradas. La dirección MAC se utiliza para identificar el dispositivo más tarde. Luego, para cada interfaz con una dirección MAC, obtiene http://169.254.169.254/metadata/instance/network/interface/$IFACE_INDEX/ipv4/ipAddress/?format=text&api-version=2017-04-02 para obtener la lista de (índices de) direcciones IP en esa interfaz. Luego, para cada índice de dirección IP, obtiene la dirección en http://169.254.169.254/metadata/instance/network/interface/$IFACE_INDEX/ipv4/ipAddress/$ADDR_INDEX/privateIpAddress?format=text&api-version=2017-04-02. También obtiene el tamaño de la subred y el prefijo para la interfaz de http://169.254.169.254/metadata/instance/network/interface/$IFACE_INDEX/ipv4/subnet/0/address/?format=text&api-version=2017-04-02 y http://169.254.169.254/metadata/instance/network/interface/$IFACE_INDEX/ipv4/subnet/0/prefix/?format=text&api-version=2017-04-02. En este punto, tenemos una lista de todas las interfaces (por dirección MAC) y sus direcciones IPv4 configuradas. Luego, la herramienta configura el sistema como lo haría para el entorno AWS. Es decir, utilizando enrutamiento por política basado en fuente con las tablas/reglas 30200/30400.
Alibaba Cloud (Aliyun) Para Aliyun, las herramientas intentan obtener la configuración de http://100.100.100.200/ Actualmente, solo configura IPv4 y no hace nada con respecto a IPv6. Hará lo siguiente. Primero obtiene http://100.100.100.200/2016-01-01/meta-data/ para determinar si la API esperada está presente. Esto determina si el entorno Aliyun se detecta y si se procede a configurar el host utilizando los metadatos de Aliyun. Obtiene http://100.100.100.200/2016-01-01/meta-data/network/interfaces/macs/ para obtener la lista de interfaces disponibles. Las interfaces se identifican por su dirección MAC. Luego, para cada interfaz, obtiene http://100.100.100.200/2016-01-01/meta-data/
nm-cloud-setup(8) — archlinux

NAME

nm-cloud-setup - Cloud instance network setup utility

OVERVIEW

nm-cloud-setup is a daemon that is started by NetworkManager. It detects whether the host is running in a cloud environment and configures the network according to the cloud provider's specifications. It is primarily used for configuring cloud-init enabled cloud instances.

USE

This utility is usually not invoked directly. It is automatically started by NetworkManager when a network interface is brought up. It checks for cloud provider metadata and configures the network accordingly.

DETAILS

The utility runs when NetworkManager brings up a network interface. It tries to detect the cloud provider by querying specific metadata URIs. Based on the detected provider, it fetches network configuration details and applies them to the system.

The following cloud providers are currently supported:

Amazon Web Services (AWS)

For AWS, the tool tries to fetch configuration from http://169.254.169.254/. It currently only configures IPv4 and does nothing about IPv6. It will do the following.

•First fetch http://169.254.169.254/latest/meta-data/instance-id to determine whether the AWS environment is detected and whether to proceed to configure the host using AWS metadata.

•Fetch network configuration for all interfaces from http://100.100.100.200/2016-01-01/meta-data/network/interfaces/macs/$MAC/vpc-cidr-block, http://100.100.100.200/2016-01-01/meta-data/network/interfaces/macs/$MAC/private-ipv4s, http://100.100.100.200/2016-01-01/meta-data/network/interfaces/macs/$MAC/netmask and http://100.100.100.200/2016-01-01/meta-data/network/interfaces/macs/$MAC/gateway. Thereby we get a list of private IPv4 addresses, one CIDR subnet block and private IPv4 addresses prefix.
•Then nm-cloud-setup iterates over all interfaces for which it could fetch IP configuration. If no ethernet device for the respective MAC address is found, it is skipped. Also, if the device is currently not activated in NetworkManager or if the currently activated profile has a user-data org.freedesktop.nm-cloud-setup.skip=yes, it is skipped. Also, there is only one interface and one IP address, the tool does nothing.

Then the tool configures the system like doing for AWS environment. That is, using source based policy routing with the tables/rules 30200/30400. One difference to AWS is that the gateway is also fetched via metadata instead of using the first IP address in the subnet.

Oracle Cloud (OCI)

For OCI, the tools tries to fetch configuration from http://169.254.169.254/. Currently, it only configures IPv4 and does nothing about IPv6. It will do the following.

•First fetch http://169.254.169.254/opc/v2/instance to determine whether the expected API is present. This determines whether OCI environment is detected and whether to proceed to configure the host using OCI meta data.
•Fetch http://169.254.169.254/opc/v2/vnics to get the configuration for all the VNICs, getting their MAC address, private IP address, gateway and subnet block.
•Then nm-cloud-setup iterates over all interfaces for which it could fetch a configuration. If no ethernet device for the respective MAC address is found, it is skipped. Also, if the device is currently not activated in NetworkManager or if the currently activated profile has a user-data org.freedesktop.nm-cloud-setup.skip=yes, it is skipped. Also, there is only one interface and one IP address, the tool does nothing.

Then the tool configures the system like doing for AWS environment. That is, using source based policy routing with the tables/rules 30200/30400.
