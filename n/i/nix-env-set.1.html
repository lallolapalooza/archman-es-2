Nombre

nix-env --set - establece el perfil para que contenga una derivación especificada

Sinopsis

nix-env --set nombre_derivacion

Descripción

La operación --set modifica la generación actual de un perfil para que contenga exactamente la derivación especificada, y nada más.

Opciones

Las siguientes opciones están permitidas para todas las operaciones de nix-env, pero puede que no siempre tengan efecto.

•
--file / -f ruta
Especifica la expresión Nix (designada abajo como la *expresión Nix activa*) utilizada por las operaciones --install, --upgrade y --query --available para obtener derivaciones. El valor por defecto es ~/.nix-defexpr.
Si el argumento comienza con http:// o https://, se interpreta como la URL de un archivo tarball que se descargará y descomprimirá en una ubicación temporal. El tarball debe incluir un único directorio de nivel superior que contenga al menos un archivo llamado default.nix.
•
--profile / -p ruta
Especifica el perfil a ser utilizado por aquellas operaciones que operan sobre un perfil (designado abajo como el *perfil activo*). Un perfil es una secuencia de entornos de usuario llamados *generaciones*, una de las cuales es la *generación actual*.
•
--dry-run
Para las operaciones --install, --upgrade, --uninstall, --switch-generation, --delete-generations y --rollback, esta bandera hará que nix-env imprima lo que *se haría* si esta bandera no se hubiera especificado, sin hacerlo realmente.
--dry-run también imprime qué rutas serán sustituidas (es decir, descargadas) y qué rutas se construirán desde la fuente (porque no hay sustituto disponible).
•
--system-filter sistema
Por defecto, las operaciones como --query --available muestran derivaciones que coinciden con cualquier plataforma. Esta opción permite usar derivaciones para la plataforma especificada sistema.

Opciones Comunes

La mayoría de los comandos Nix aceptan las siguientes opciones de línea de comandos:

•
--help
Imprime un resumen de la sintaxis del comando y sale.
•
--version
Imprime el número de versión de Nix en la salida estándar y sale.
•
--verbose / -v
Aumenta el nivel de verbosidad de los mensajes de diagnóstico impresos en la salida de error estándar. Para cada operación de Nix, la información impresa en la salida estándar está bien definida; cualquier información de diagnóstico se imprime en la salida de error estándar, nunca en la salida estándar.
Esta opción se puede especificar repetidamente. Actualmente, existen los siguientes niveles de verbosidad:
•
0 "Solo errores"
Solo imprime mensajes que expliquen por qué falló la invocación de Nix.
•
1 "Informativo"
Imprime mensajes *útiles* sobre lo que Nix está haciendo. Este es el valor por defecto.
•
2 "Hablador"
Imprime más mensajes informativos.
•
3 "Conversador"
Imprime aún más mensajes informativos.
•
4 "Depuración"
Imprime información de depuración.
•
5 "Vomitar"
Imprime enormes cantidades de información de depuración.
•
--quiet
Disminuye el nivel de verbosidad de los mensajes de diagnóstico impresos en la salida de error estándar. Esta es la opción inversa a -v / --verbose.
Esta opción se puede especificar repetidamente. Ver la lista anterior de niveles de verbosidad.
•
--log-format formato
Esta opción se puede usar para cambiar la salida del formato de registro, con formato siendo uno de:
•
raw
Este es el formato crudo, tal como lo emite nix-build.
•
internal-json
Emite los registros de forma estructurada.
Advertencia
Aunque el esquema en sí es relativamente estable, el formato de los mensajes de error (específicamente del campo msg) puede cambiar entre versiones.
•
bar
Solo muestra una barra de progreso durante las compilaciones.
•
bar-with-logs
Muestra los registros crudos, con la barra de progreso en la parte inferior.
•
--no-build-output / -Q
Por defecto, la salida generada por los constructores a la salida estándar y al error estándar se muestra en el error estándar del comando Nix. Esta opción suprime este comportamiento. Tenga en cuenta que la salida estándar y el error estándar del constructor siempre se escriben en un archivo de registro en prefix/nix/var/log/nix.
•
--max-jobs / -j número
Establece el número máximo de trabajos de compilación que Nix realizará en paralelo al número especificado. Especifique auto para usar el número de CPUs del sistema. El valor por defecto es el especificado en la configuración max-jobs, que a su vez por defecto es 1. Un valor más alto es útil en sistemas SMP o para explotar la latencia de E/S.
Establecerlo en 0 prohíbe la compilación en la máquina local, lo cual es útil cuando desea que las compilaciones ocurran solo en constructores remotos.
•
--cores
>
Establece el valor de la variable de entorno NIX_BUILD_CORES en la invocación de los constructores. Los constructores pueden usar esta variable a su discreción para controlar el paralelismo máximo. Por ejemplo, en Nixpkgs, si el atributo de derivación enableParallelBuilding está establecido en true, el constructor pasa la bandera -jN a GNU Make. Por defecto, toma el valor de la configuración de cores, si está establecida, o 1 en caso contrario. El valor 0 significa que el constructor debe usar todos los núcleos de CPU disponibles en el sistema.
•
--max-silent-time
Establece el número máximo de segundos que un constructor puede pasar sin producir ninguna salida en la salida estándar o el error estándar. El valor predeterminado es especificado por la configuración max-silent-time. 0 significa sin tiempo de espera.
•
--timeout
Establece el número máximo de segundos que un constructor puede ejecutarse. El valor predeterminado es especificado por la configuración timeout. 0 significa sin tiempo de espera.
•
--keep-going / -k
Continuar en caso de fallos en la construcción, en la mayor medida posible. Es decir, si la construcción de una entrada de alguna derivación falla, Nix aún construirá las otras entradas, pero no la derivación en sí. Sin esta opción, Nix se detiene si alguna construcción falla (excepto las construcciones de sustitutos), posiblemente matando las construcciones en progreso (en caso de construcciones paralelas o distribuidas).
•
--keep-failed / -K
Especifica que en caso de fallo de construcción, el directorio temporal (generalmente en /tmp) en el que se realiza la construcción no debe ser eliminado. La ruta del directorio de construcción se imprime como un mensaje informativo.
•
--fallback
Siempre que Nix intente construir una derivación para la cual se conocen sustitutos para cada ruta de salida, pero la realización de las rutas de salida a través de los sustitutos falla, recurrirá a la construcción de la derivación.
El escenario más común en el que esto es útil es cuando hemos registrado sustitutos para realizar la distribución binaria desde, por ejemplo, un repositorio de red. Si el repositorio está caído, la realización de la derivación fallará. Cuando se especifica esta opción, Nix construirá la derivación en su lugar. Por lo tanto, la instalación desde binarios recurre a la instalación desde fuente. Esta opción no es la predeterminada ya que generalmente no es deseable que un fallo transitorio en la obtención de los sustitutos conduzca a una construcción completa desde la fuente (con el consumo relacionado de recursos).
•
--readonly-mode
Cuando se utiliza esta opción, no se intenta abrir la base de datos de Nix. La mayoría de las operaciones de Nix necesitan acceso a la base de datos, por lo que esas operaciones fallarán.
•
--arg nombre valor
Esta opción es aceptada por nix-env, nix-instantiate, nix-shell y nix-build. Al evaluar expresiones Nix, el evaluador de expresiones intentará automáticamente llamar a las funciones que encuentre. Puede llamar automáticamente a funciones para las que cada argumento tiene un valor predeterminado (por ejemplo, { argName ? defaultValue }: ...).
Con --arg, también puedes llamar a funciones que tienen argumentos sin valor predeterminado (o anular un valor predeterminado). Es decir, si el evaluador encuentra una función con un argumento llamado nombre, la llamará con el valor valor.
Por ejemplo, el default.nix de nivel superior en Nixpkgs es en realidad una función:
{ # El sistema (por ejemplo, `i686-linux') para el que se construirán los paquetes.
system ? builtins.currentSystem
...
}: ...
Así que si llamas a esta expresión Nix (por ejemplo, cuando haces nix-env --install --attr pkgname), la función se llamará automáticamente utilizando el valor builtins.currentSystem para el argumento system. Puedes anular esto usando --arg, por ejemplo, nix-env --install --attr pkgname --arg system \"i686-freebsd\". (Ten en cuenta que como el argumento es un literal de cadena Nix, tienes que escapar las comillas.)
•
--argstr nombre valor
Esta opción es como --arg, solo que el valor no es una expresión Nix sino una cadena. Así que en lugar de --arg system \"i686-linux\" (las comillas exteriores son para mantener el shell feliz) puedes decir --argstr system i686-linux.
•
--attr / -A attrPath
Selecciona un atributo de la expresión Nix de nivel superior que se está evaluando. (Solo nix-env, nix-instantiate, nix-build y nix-shell.) El ruta de atributo attrPath es una secuencia de nombres de atributos separados por puntos. Por ejemplo, dada una expresión Nix de nivel superior e, la ruta de atributo xorg.xorgserver haría que se utilizara la expresión e.xorg.xorgserver. Ver nix-env --install para algunos ejemplos concretos.
Además de los nombres de atributos, también puedes especificar índices de arreglos. Por ejemplo, la ruta de atributo foo.3.bar selecciona el atributo bar del cuarto elemento del arreglo en el atributo foo de la expresión de nivel superior.
•
--expr / -E
Interpreta los argumentos de la línea de comandos como una lista de expresiones Nix para ser analizadas y evaluadas, en lugar de como una lista de nombres de archivos de expresiones Nix. (Solo nix-instantiate, nix-build y nix-shell.)
Para nix-shell, esta opción se usa comúnmente para proporcionarte un shell en el que puedas construir los paquetes devueltos por la expresión. Si deseas obtener un shell que contenga los paquetes construidos, listos para usar, proporciona tu expresión a la bandera de conveniencia nix-shell --packages en su lugar.
•
-I / --include ruta
Añade una entrada a la lista de rutas de búsqueda utilizadas para resolver rutas de búsqueda. Esta opción puede darse varias veces.
Las rutas añadidas a través de -I tienen prioridad sobre la configuración nix-path y la variable de entorno NIX_PATH (ver NIX_PATH).
•
--option nombre valor
Establece la opción de configuración de Nix nombre a valor. Esto anula los ajustes en el archivo de configuración de Nix (ver nix.conf5).
•
--repair
Repara rutas de la tienda corruptas o faltantes volviendo a descargarlas o reconstruyéndolas. Ten en cuenta que esto es lento porque requiere calcular un hash criptográfico del contenido de cada ruta en el cierre de la construcción. Ten en cuenta también la advertencia en nix-store --repair-path.

Nota

Ver man nix.conf para anular la configuración con banderas de línea de comandos.

NAME

nix-env-set - Manage user environments

SYNOPSIS

nix-env [NIX-COMMAND] [NIX-OPTIONS] [NIX-ENV-OPTIONS]

nix-env --profile PROFILE --set ATTR...

DESCRIPTION

The command nix-env is used to manage user environments, which are collections of packages installable into a Nix channel.

This manual page describes the options and subcommands of nix-env. Refer to the Nix manual for a more detailed explanation of Nix concepts.

Nix commands

The following commands are available:

•
install (or i)
Install packages into the user environment.
•
uninstall (or rm)
Remove packages from the user environment.
•
upgrade (or up)
Upgrade packages in the user environment.
•
set
Replace the current package set with a new one.
•
query (or q)
List installed packages and perform other queries on the user environment.
•
profile (or p)
Manage user environment profiles.
•
garbage-collect (or gc)
Perform garbage collection on the user environment.

Common Options

The following options are available for most nix-env commands:

•
--profile PROFILE
The user environment profile to operate on. Defaults to $HOME/.nix-profile.
•
--description DESCRIPTION
A description to set for the profile. This is useful for identifying different profiles.
•
--rollback-limit N
The maximum number of old profile generations to keep. Defaults to 10.
•
--switch-generation GENERATION
Switch the profile to the specified generation.
•
--set-flag NAME VALUE
Set a profile flag. Currently supported flags are accept-flakes (set to true or false).
•
--add-root ROOT
Add a garbage collection root for the profile. This ensures that packages in the profile are not garbage collected.
•
--keep-derivations
Keep all derivations that are part of the user environment, even if they are not directly referenced by any installed package. This can be useful for debugging or reproducibility.
•
--keep-outputs
Keep all outputs of derivations that are part of the user environment, even if they are not directly referenced by any installed package. This can be useful for debugging or reproducibility.
•
--print-output-path
Print the output path of the resulting profile generation.
•
--print-root
Print the garbage collection root path for the profile.
•
--json
Output in JSON format.
•
--quiet
Suppress informational output.
•
--verbose
Print debugging information.

ENVIRONMENT VARIABLES

Common Environment Variables

•
NIX_PATH
This variable specifies the search path for Nix expressions. It's a list of directories, separated by colons (:). Nix will search these directories in order for files specified in angle brackets, e.g. <nixpkgs>. This variable overrides the value of the nix-path configuration setting. It can be extended using the -I option.
Example
$ export NIX_PATH=`/home/eelco/Dev:nixos-config=/etc/nixos
If NIX_PATH is set to an empty string, resolving search paths will always fail.
Example
$ NIX_PATH= nix-instantiate --eval '<nixpkgs>'
error: file 'nixpkgs' was not found in the Nix search path (add it using $NIX_PATH or -I)
•
NIX_IGNORE_SYMLINK_STORE
Normally, the Nix store directory (typically /nix/store) is not allowed to contain any symlink components. This is to prevent "impure" builds. Builders sometimes "canonicalise" paths by resolving all symlink components. Thus, builds on different machines (with /nix/store resolving to different locations) could yield different results. This is generally not a problem, except when builds are deployed to machines where /nix/store resolves differently. If you are sure that you're not going to do that, you can set NIX_IGNORE_SYMLINK_STORE to 1.
Note that if you're symlinking the Nix store so that you can put it on another file system than the root file system, on Linux you're better off using bind mount points, e.g.,
$ mkdir /nix
$ mount -o bind /mnt/otherdisk/nix /nix
Consult the mount(8) manual page for details.
•
NIX_STORE_DIR
Overrides the location of the Nix store (default prefix/store).
•
NIX_DATA_DIR
Overrides the location of the Nix static data directory (default prefix/share).
•
NIX_LOG_DIR
Overrides the location of the Nix log directory (default prefix/var/log/nix).
•
NIX_STATE_DIR
Overrides the location of the Nix state directory (default prefix/var/nix).
•
NIX_CONF_DIR
Overrides the location of the system Nix configuration directory (default prefix/etc/nix).
•
NIX_CONFIG
Applies settings from Nix configuration from the environment. The content is treated as if it was read from a Nix configuration file. Settings are separated by the newline character.
•
NIX_USER_CONF_FILES
Overrides the location of the Nix user configuration files to load from.
The default are the locations according to the XDG Base Directory Specification. See the XDG Base Directories sub-section for details.
The variable is treated as a list separated by the : token.
•
TMPDIR
Use the specified directory to store temporary files. In particular, this includes temporary build directories; these can take up substantial amounts of disk space. The default is /tmp.
•
NIX_REMOTE
This variable should be set to daemon if you want to use the Nix daemon to execute Nix operations. This is necessary in multi-user Nix installations. If the Nix daemon's Unix socket is at some non-standard path, this variable should be set to unix://path/to/socket. Otherwise, it should be left unset.
•
NIX_SHOW_STATS
If set to 1, Nix will print some evaluation statistics, such as the number of values allocated.
•
NIX_COUNT_CALLS
If set to 1, Nix will print how often functions were called during Nix expression evaluation. This is useful for profiling your Nix expressions.
•
GC_INITIAL_HEAP_SIZE
If Nix has been configured to use the Boehm garbage collector, this variable sets the initial size of the heap in bytes. It defaults to 384 MiB. Setting it to a low value reduces memory consumption, but will increase runtime due to the overhead of garbage collection.

XDG Base Directories

Nix follows the XDG Base Directory Specification.

For backwards compatibility, Nix commands will follow the standard only when use-xdg-base-directories is enabled. New Nix commands (experimental) conform to the standard by default.

The following environment variables are used to determine locations of various state and configuration files:

  • [XDG_CONFIG_HOME]{#env-XDGCONFIGHOME} (default ~/.config)
  • [XDG_STATE_HOME]{#env-XDGSTATEHOME} (default ~/.local/state)
  • [XDG_CACHE_HOME]{#env-XDGCACHEHOME} (default ~/.cache)

EXAMPLES

The following updates a profile such that its current generation will contain just Firefox:

$ nix-env --profile /nix/var/nix/profiles/browser --set firefox
