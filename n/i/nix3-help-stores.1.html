Nombre

nix help-stores - mostrar ayuda sobre tipos de almacenes y su configuración

Sinopsis

nix help-stores [opción…]

Nix soporta diferentes tipos de almacenes:

  • Almacén Dummy
  • Almacén Experimental de Superposición Local
  • Almacén Experimental SSH
  • Almacén Experimental SSH con sistema de archivos montado
  • Almacén de Caché Binaria HTTP
  • Almacén de Caché Binaria Local
  • Almacén Local de Demonio
  • Almacén Local
  • Almacén de Caché Binaria S3
  • Almacén SSH

Formato URL del almacén

Los almacenes se especifican utilizando una sintaxis similar a una URL. Por ejemplo, el comando

# nix path-info --store https://cache.nixos.org/ --json \
  /nix/store/a7gvj343m05j2s32xcnwr35v31ynlypr-coreutils-9.1

obtiene información sobre una ruta de almacén en la caché binaria HTTP ubicada en https://cache.nixos.org/, que es un tipo de almacén.

Las URLs de almacén pueden especificar configuraciones de almacén utilizando cadenas de consulta de URL, es decir, añadiendo ?nombre1=valor1&nombre2=valor2&... a la URL. Por ejemplo,

--store ssh://machine.example.org?ssh-key=/ruta/a/mi/clave

indica a Nix que acceda al almacén en una máquina remota a través del protocolo SSH, utilizando /ruta/a/mi/clave como clave privada SSH. Las configuraciones admitidas para cada tipo de almacén se documentan a continuación.

La URL de almacén especial auto hace que Nix seleccione automáticamente un almacén de la siguiente manera:

  • Utilizar el [almacén local] /nix/store si /nix/var/nix es escribible por el usuario actual.
  • De lo contrario, si /nix/var/nix/daemon-socket/socket existe, [conectar al demonio Nix que escucha en ese socket].
  • De lo contrario, solo en Linux, usar el [almacén local en chroot] ~/.local/share/nix/root, que se creará automáticamente si no existe.
  • De lo contrario, usar el [almacén local] /nix/store.

Almacén Dummy

Formato URL del almacén: dummy://

Este tipo de almacén representa un almacén que no contiene rutas de almacén y no se puede escribir en él. Es útil cuando desea utilizar el evaluador de Nix cuando no existe ningún almacén Nix real, por ejemplo:

# nix eval --store dummy:// --expr '1 + 2'

Almacén Experimental de Superposición Local

Advertencia

Este almacén es parte de una característica experimental.

Para usar este almacén, asegúrese de que la [característica experimental local-overlay-store] esté habilitada. Por ejemplo, incluya lo siguiente en nix.conf:

extra-experimental-features = local-overlay-store

Formato URL del almacén: local-overlay

Este tipo de almacén es una variación del [almacén local] diseñado para aprovechar el [Sistema de Archivos de Superposición] (OverlayFS en resumen) de Linux. Al igual que OverlayFS combina un sistema de archivos inferior y superior tratándolo el superior como un parche contra el inferior, el almacén de superposición local combina un almacén inferior con un almacén casi-[local]. ( "Casi" porque si bien los sistemas de archivos superiores para OverlayFS son válidos por sí mismos, el almacén casi-superior no es un almacén local válido por sí solo porque algunas referencias quedarán colgadas.) Para usar este almacén, primero deberá configurar un punto de montaje OverlayFS [adecuadamente] ya que Nix no hará esto por usted (aunque verificará que el punto de montaje esté configurado correctamente).

Partes conceptuales de un almacén de superposición local

Esta es una descripción más abstracta/conceptual de las partes de un almacén en capas, una referencia autorizada. Para obtener instrucciones más "prácticas", consulte el ejemplo resuelto en la siguiente subsección.

Las partes de un almacén de superposición local son las siguientes:

•
Almacén inferior:
Especificado con la configuración lower-store.
Este es cualquier implementación de almacén que incluya un directorio de almacén como parte del sistema de archivos nativo del sistema operativo. Por ejemplo, podría ser un [almacén local], un [demonio local...

Entendiendo las tiendas de superposición locales

Una tienda de superposición local (local overlay store) es una tienda que combina el contenido de otra tienda (la tienda inferior) con contenido adicional (la capa superior).

•
Tienda inferior:
Puede ser la tienda de Nix por defecto (/nix/store), o incluso otra tienda local de superposición.
La tienda de superposición local nunca intenta modificar la tienda inferior de ninguna manera. Algo más podría modificar la tienda inferior, pero existen restricciones. Nix en sí mismo requiere que esta tienda solo crezca, y no cambie de otras formas. Por ejemplo, se pueden agregar nuevos objetos a la tienda, pero eliminar o modificar objetos de la tienda no está permitido en general, ya que confundirá y corromperá cualquier tienda de superposición local que utilice esos objetos. (Además, el mecanismo de superposición del sistema de archivos subyacente puede imponer restricciones adicionales, ver más abajo).
La tienda inferior no debe cambiar mientras está montada como parte de una tienda de superposición. Para asegurarse de que no lo haga, puede desear montar el directorio de la tienda en modo de solo lectura (lo que entonces requiere que el parámetro [read-only] se establezca en true).
•
Directorio de la tienda inferior:
Especificado con la configuración lower-store.real.
Este es el directorio utilizado/expuesto por la tienda inferior.
Como se especificó anteriormente, Nix requiere que la tienda local solo pueda crecer y no cambiar de otras formas. OverlayFS de Linux impone además el requisito de que este directorio no pueda cambiar en absoluto. Eso significa que, mientras exista alguna tienda de superposición local que esté utilizando esta tienda como tienda inferior, este directorio no debe cambiar.
•
Fuente de metadatos de la tienda inferior:
No especificado directamente. Una consecuencia de la configuración lower-store, dependiendo del tipo de tienda inferior elegido.
Esto es abstracto, solo una forma de leer los metadatos de los objetos de tienda de la tienda inferior. Por ejemplo, podría ser una base de datos SQLite (para la [tienda local]), o una conexión de socket (para la [tienda del demonio local]).
Esto no necesita ser escribible. Como se mencionó anteriormente, una tienda de superposición local nunca intenta modificar su tienda inferior. Los metadatos de la tienda inferior se consideran parte de la tienda inferior, al igual que los objetos del sistema de archivos de la tienda que aparecen en el directorio de la tienda.
•
Casi-tienda superior:
No especificado directamente. En cambio, las partes constituyentes se especifican de forma independiente como se describe a continuación.
Esto es casi, pero no del todo, una [tienda local]. Eso es porque tomada de forma aislada, no como parte de una tienda de superposición local, por sí sola, parecería corrupta. Pero combinada con todo lo demás como parte de una tienda local de superposición, es válida.
•
Directorio de la capa superior:
Especificado con la configuración upper-layer.
Esto contiene objetos de tienda adicionales (o, estrictamente hablando, sus objetos del sistema de archivos con los que la tienda de superposición local extenderá la tienda inferior).
•
Directorio de la tienda superior:
Especificado con la configuración real. Esto es lo mismo que la configuración base de la tienda local, y también puede especificarse indirectamente con la configuración root.
Esto contiene todos los objetos de tienda de cada uno de los dos directorios.
El directorio de la tienda inferior y el directorio de la capa superior se combinan a través de OverlayFS para crear este directorio. Nix no hace esto por sí mismo, ya que típicamente no tendría los permisos para hacerlo, por lo que es responsabilidad del usuario configurarlo primero. Sin embargo, Nix puede verificar opcionalmente que la configuración del montaje OverlayFS aparezca como se espera, coincidiendo con la configuración de Nix.
•
Base de datos SQLite superior:
No especificado directamente. La ubicación de la base de datos depende en cambio de la configuración state. Siempre es ${state}/db.
Esto contiene los metadatos de todos los objetos de tienda de la capa superior (todo más allá de sus objetos de sistema de archivos), y también copias duplicadas de los metadatos de algunos objetos de tienda de la capa inferior. La duplicación es para que los metadatos de la clausura de los objetos de tienda de la capa superior se puedan encontrar completamente dentro de la capa superior. (Esto nos permite usar el mismo esquema SQL que la base de datos SQLite de la [tienda local], ya que las claves externas en ese esquema aseguran que los metadatos de la clausura sean autosuficientes de esta manera).

Ejemplo de disposición del sistema de archivos

Aquí hay un ejemplo detallado de uso, siguiendo los conceptos de la sección anterior.

Digamos que tenemos las siguientes rutas:

  • /mnt/example/merged-store/nix/store
  • /mnt/example/store-a/nix/store
  • /mnt/example/store-b

Entonces, la siguiente URI de tienda se puede usar para acceder a una tienda de superposición local en /mnt/example/merged-store:

local-overlay://?root=/mnt/example/merged-store&lower-store=/mnt/example/store-a&upper-layer=/mnt/example/store-b

El directorio de la tienda inferior se encuentra en /mnt/example/store-a/nix/store, mientras que la capa superior está en /mnt/example/store-b.

Antes de acceder a la tienda de superposición, deberá asegurarse de que el montaje OverlayFS esté configurado correctamente:

mount -t overlay overlay \
  -o lowerdir="/mnt/example/store-a/nix/store" \
  -o upperdir="/mnt/example/store-b" \
  -o workdir="/mnt/example/workdir" \
  "/mnt/example/merged-store/nix/store"

Tenga en cuenta que OverlayFS requiere que /mnt/example/workdir esté en el mismo volumen que upperdir.

Por defecto, Nix verificará que el punto de montaje se haya configurado correctamente y fallará con un error si no es así. Puede anular este comportamiento pasando check-mount=false si lo necesita.

Configuración

•
check-mount
Verifica que el sistema de archivos de superposición esté montado correctamente.
Nix no administra el punto de montaje overlayfs en sí, pero el correcto funcionamiento de la tienda de superposición depende de que este punto de montaje esté configurado correctamente. En lugar de simplemente asumir que este es el caso, verifica que las opciones lowerdir y upperdir sean lo que esperamos. Esta verificación está activada por defecto, pero puede desactivarse si es necesario.
Por defecto: true
•
log
Directorio donde Nix almacenará los archivos de registro.
Por defecto: /nix/var/log/nix
•
lower-store
URL de tienda para la tienda inferior. El valor por defecto es auto (es decir, usar el demonio Nix o /nix/store directamente).
Debe ser una tienda con un directorio de tienda en el sistema de archivos. Debe usarse como capa inferior de OverlayFS para el directorio de tienda de esta tienda.
Por defecto: vacío
•
path-info-cache-size
Tamaño de la caché de metadatos de rutas de tienda en memoria.
Por defecto: 65536
•
priority
Prioridad de esta tienda cuando se utiliza como sustituto. Un valor menor significa una prioridad mayor.
Por defecto: 0
•
read-only
Permite que esta tienda se abra cuando su base de datos está en un sistema de archivos de solo lectura.
Normalmente, Nix intentará abrir la base de datos de la tienda en modo de lectura/escritura, incluso para consultas (cuando no se necesita acceso de escritura), lo que provocará un error si la base de datos está en un sistema de archivos de solo lectura.
Habilite el modo de solo lectura para deshabilitar el bloqueo y abrir la base de datos SQLite con el parámetro immutable establecido.
Advertencia: No utilice esto a menos que el sistema de archivos sea de solo lectura.
Usarlo cuando el sistema de archivos es escribible puede causar resultados de consulta incorrectos
or corruption errors if the database is changed by another process. While the filesystem the database resides on might appear to be read-only, consider whether another user or system might have write access to it.
Default: false
•
real
Physical path of the Nix store.
Default: /nix/store
•
remount-hook
Script or other executable to run when overlay filesystem needs remounting.
This is occasionally necessary when deleting a store path that exists in both upper and lower layers. In such a situation, bypassing OverlayFS and deleting the path in the upper layer directly is the only way to perform the deletion without creating a “whiteout”. However this causes the OverlayFS kernel data structures to get out-of-sync, and can lead to ‘stale file handle’ errors; remounting solves the problem.
The store directory is passed as an argument to the invoked executable.
Default: empty
•
require-sigs
Whether store paths copied into this store should have a trusted signature.
Default: true
•
root
Directory prefixed to all other paths.
Default: ``
•
state
Directory where Nix will store state.
Default: /dummy
•
store
Logical location of the Nix store, usually /nix/store. Note that you can only copy store paths between stores if they have the same store setting.
Default: /nix/store
•
system-features
Optional system features available on the system this store uses to build derivations.
Example: "kvm"
Default: machine-specific
•
trusted
Whether paths from this store can be used as substitutes even if they are not signed by a key listed in the trusted-public-keys setting.
Default: false
•
upper-layer
Directory containing the OverlayFS upper layer for this store’s store dir.
Default: empty
•
want-mass-query
Whether this store can be queried efficiently for path validity when used as a substituter.
Default: false

Experimental SSH Store con sistema de archivos montado

Advertencia

Este store es parte de una característica experimental.

Para usar este store, asegúrate de que la característica experimental mounted-ssh-store esté habilitada. Por ejemplo, incluye lo siguiente en nix.conf:

extra-experimental-features = mounted-ssh-store

Formato de URL de store: mounted-ssh-ng://[username@]hostname

Tipo de store experimental que permite acceso completo a un Nix store en una máquina remota, y además requiere que ese store esté montado en el sistema de archivos local.

El montaje de dicho store no es gestionado por Nix, y debe ser gestionado manualmente. Podría lograrse con SSHFS o NFS, por ejemplo.

El sistema de archivos local se utiliza para optimizar ciertas operaciones. Por ejemplo, en lugar de serializar archivos Nix y enviarlos a través del canal Nix, podemos acceder directamente a los datos del sistema de archivos a través del punto de montaje.

El sistema de archivos local también se utiliza para hacer posibles ciertas operaciones que de otro modo no serían posibles. Por ejemplo, se pueden crear raíces de GC persistentes si residen en el mismo sistema de archivos que el store remoto: el lado remoto creará los enlaces simbólicos necesarios para evitar condiciones de carrera.

Local Store

Store URL format: local, root

This store type accesses a Nix store in the local filesystem directly (i.e. not via the Nix daemon). root is an absolute path that is prefixed to other directories such as the Nix store directory. The store pseudo-URL local denotes a store that uses / as its root directory.

A store that uses a root other than / is called a chroot store. With such stores, the store directory is “logically” still /nix/store, so programs stored in them can only be built and executed by chroot-ing into root. Chroot stores only support building and running on Linux when mount namespaces and user namespaces are enabled.

For example, the following uses /tmp/root as the chroot environment to build or download nixpkgs#hello and then execute it:

# nix run --store /tmp/root nixpkgs#hello
Hello, world!

Here, the “physical” store location is /tmp/root/nix/store, and Nix’s store metadata is in /tmp/root/nix/var/nix/db.

It is also possible, but not recommended, to change the “logical” location of the Nix store from its default of /nix/store. This makes it impossible to use default substituters such as https://cache.nixos.org/, and thus you may have to build everything locally. Here is an example:

# nix build --store 'local?store=/tmp/my-nix/store&state=/tmp/my-nix/state&log=/tmp/my-nix/log' nixpkgs#hello

S3 Binary Cache Store

Store URL format: s3://bucket-name

This store allows reading and writing a binary cache stored in an AWS S3 (or S3-compatible service) bucket. This store shares many idioms with the HTTP Binary Cache Store.

For AWS S3, the binary cache URL for a bucket named example-nix-cache will be exactly s3://example-nix-cache. For S3 compatible binary caches, consult that cache’s documentation.

Anonymous reads to your S3-compatible binary cache

If your binary cache is publicly accessible and does not require authentication, it is simplest to use the [HTTP Binary Cache Store] rather than S3 Binary Cache Store with https://example-nix-cache.s3.amazonaws.com instead of s3://example-nix-cache.

Your bucket will need a bucket policy like the following to be accessible:

{
    "Id": "Policy1568307603157",
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "AllowPublicRead",
            "Action": [
                "s3:GetObject"
            ],
            "Effect": "Allow",
            "Resource": "arn:aws:s3:::example-nix-cache/*",
            "Principal": "*"
        }
    ]
}

Authenticated access to your S3-compatible binary cache

For authenticated access, Nix uses the standard AWS credential chaining mechanism. This means Nix will look for credentials in the following order:

  1. The netrc-file setting.
  2. Environment variables (e.g. AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_SESSION_TOKEN).
  3. The ~/.aws/credentials file.
  4. IAM roles attached to EC2 instances or ECS tasks.

For S3-compatible services, you can specify a custom endpoint using the endpoint URL parameter:

s3://my-bucket?endpoint=https://s3.example.com

Nix utilizará la cadena de proveedor de credenciales predeterminada para autenticar las solicitudes a Amazon S3.

Tenga en cuenta que esto significa que Nix leerá variables de entorno y archivos con diferentes convenciones que las propias configuraciones de Nix, tal como las implementa el SDK de AWS. Consulte la documentación vinculada anteriormente para obtener más detalles.

Lecturas autenticadas a tu caché binaria de S3

Tu bucket necesitará una política de bucket que permita a los usuarios deseados realizar las acciones s3:GetObject y s3:GetBucketLocation en todos los objetos del bucket. La política anónima dada anteriormente se puede actualizar para tener un Principal restringido para soportar esto.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "UploadToCache",
      "Effect": "Allow",
      "Action": [
        "s3:AbortMultipartUpload",
        "s3:GetBucketLocation",
        "s3:GetObject",
        "s3:ListBucket",
        "s3:ListBucketMultipartUploads",
        "s3:ListMultipartUploadParts",
        "s3:PutObject"

      "Resource": [
        "arn:aws:s3:::example-nix-cache",

    }

NIX.CONF(5)

April 2024NIX.CONF(5)

Name

nix.conf ― Nix configuration file

Synopsis

~/.config/nix/nix.conf, /etc/nix/nix.conf, /etc/nixos/configuration.nix

Description

This page describes the configuration settings available in Nix. These settings can be placed in a configuration file (e.g. ~/.config/nix/nix.conf or /etc/nix/nix.conf) or passed on the command line using the --option flag.

Configuration settings are read in the following order:

  1. /etc/nix/nix.conf
  2. ~/.config/nix/nix.conf
  3. Command-line flags

Command-line flags override settings in configuration files.

Store types

The following settings define the behavior of Nix store accessors.

Dummy Store

Store URL format: dummy:

This is a special store that doesn't represent any real store, but can be used in certain contexts like testing.

Settings

•
store

Default: /nix/store

Experimental Local Overlay Store

Store URL format: local-overlay:

This store type allows users to specify a temporary overlay filesystem on top of the real Nix store. All store operations (like queries, builds, etc.) will first check the overlay, and then fall back to the real Nix store. This is useful for testing changes without committing them to the Nix store.

Note: This feature is experimental and may change or be removed in future versions.

Default: /tmp/nix-local-overlay

Logical location of the Nix store, usually /nix/store. Note that you can only copy store paths between stores if they have the same store setting.
Default: /nix/store

Experimental SSH Store with filesystem mounted

Store URL format: ssh://[user@]host:/path

This store type allows Nix to access a remote store on another machine via SSH, with the remote filesystem mounted using SSHFS.

Tiendas de Nix

Este comando muestra información sobre las diferentes implementaciones de tienda disponibles en Nix.

Tiendas disponibles:

  • local: La tienda Nix local estándar, que almacena los artefactos de construcción en el sistema de archivos local.
  • remote: Una tienda remota, que puede ser una tienda compartida en red o un servicio en la nube.
  • s3: Una tienda remota implementada utilizando Amazon S3 para el almacenamiento de artefactos.
  • ssh: Una tienda remota implementada utilizando SSH para el acceso a sistemas remotos.

Opciones:

Para más detalles sobre las opciones de configuración de las tiendas, consulte la documentación de la configuración de Nix.
