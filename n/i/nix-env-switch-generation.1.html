Nombre

nix-env --switch-generation - establece el entorno del usuario a la generación de perfil dada

Sinopsis

nix-env {--switch-generation | -G} generación

Descripción

Esta operación hace que la generación número generación sea la generación actual del perfil activo. Es decir, si el perfil es la ruta al perfil activo, entonces el enlace simbólico perfil se hará apuntar a perfil-enlace-generación, que a su vez es un enlace simbólico al entorno de usuario real en la tienda Nix.

El cambio fallará si la generación especificada no existe.

Opciones

Las siguientes opciones están permitidas para todas las operaciones de nix-env, pero puede que no siempre tengan un efecto.

•
--file / -f ruta
Especifica la expresión Nix (designada abajo como la expresión Nix activa) utilizada por las operaciones --install, --upgrade y --query --available para obtener derivaciones. El valor predeterminado es ~/.nix-defexpr.
Si el argumento comienza con http:// o https://, se interpreta como la URL de un archivo tar que se descargará y desempaquetará en una ubicación temporal. El archivo tar debe incluir un único directorio de nivel superior que contenga al menos un archivo llamado default.nix.
•
--profile / -p ruta
Especifica el perfil a ser utilizado por las operaciones que operan en un perfil (designado abajo como el perfil activo). Un perfil es una secuencia de entornos de usuario llamados generaciones, una de las cuales es la generación actual.
•
--dry-run
Para las operaciones --install, --upgrade, --uninstall, --switch-generation, --delete-generations y --rollback, esta bandera hará que nix-env imprima lo que se haría si esta bandera no se hubiera especificado, sin hacerlo realmente.
--dry-run también imprime qué rutas serán sustituidas (es decir, descargadas) y qué rutas se construirán desde la fuente (porque no hay sustituto disponible).
•
--system-filter sistema
Por defecto, las operaciones como --query --available muestran derivaciones que coinciden con cualquier plataforma. Esta opción te permite usar derivaciones para la sistema de plataforma especificada.

Description

nix-env is a facility for managing declarative user environments. It allows users to install, upgrade, and remove packages, and to query the set of installed packages.

A user environment is a collection of packages. Nix maintains a set of generations of user environments. Each generation is a snapshot of the user environment at a point in time. This allows users to roll back to previous generations.

The primary interface to nix-env is through Nix profiles. A profile is a collection of generations. By default, each user has a profile located at ~/.nix-profile. This profile contains a symbolic link to the current generation.

A generation is a symbolic link to a Nix store path. This store path is a derivation that builds the user environment. The derivation is generated by nix-env.

The installation of packages happens in the Nix store. Each package is built from a derivation. The derivation is a description of how to build the package. Nix builds the package from the derivation. The result of the build is stored in the Nix store.

The user environment is built from a derivation that depends on the derivations of the installed packages. The derivation of the user environment is generated by nix-env.

The user environment is installed by creating a symbolic link from the user's profile to the Nix store path of the user environment derivation.

The installation of packages can be done using the -i or --install option. For example, to install the hello package, you would run:

$ nix-env -i hello

To install multiple packages, simply list them:

$ nix-env -i bash vim

You can also install packages from a specific Nix expression file using the -f or --file option.

$ nix-env -f my-packages.nix -i

The -u or --upgrade option upgrades installed packages to newer versions. If no package name is given, all installed packages are upgraded:

$ nix-env -u

To upgrade a specific package:

$ nix-env -u bash

The -q or --query option queries the set of installed packages. By default, it lists all installed packages:

$ nix-env -q

To query a specific package:

$ nix-env -q bash

The -e or --delete option removes installed packages. If no package name is given, all installed packages are removed:

$ nix-env -e bash

The --set option sets the current generation of the profile to a specific generation number.

$ nix-env --set-generation 5

The --rollback option rolls back the current generation to the previous one.

$ nix-env --rollback

The --list-generations option lists all generations of the profile.

$ nix-env --list-generations

Options

•
-i, --install attribute name ...
Install the given package(s). The package names are attributes in the Nix expression given by the -f option, or in nixpkgs by default.
•
-u, --upgrade [attribute name ...]
Upgrade the given package(s) to the latest version. If no package name is specified, all installed packages are upgraded.
•
-q, --query [attribute name ...]
Query the set of installed packages. If no package name is specified, all installed packages are listed.
•
-e, --delete attribute name ...
Remove the given package(s). If no package name is specified, all installed packages are removed.
•
-p, --profile profile
Manage the given profile instead of the default user profile (~/.nix-profile).
•
-f, --file file
Use the given Nix expression file to determine package names. Defaults to nixpkgs.
•
-I path
Add a path to the Nix expression search path. See lookup paths.
•
--diff
Show the difference between the current generation and the previous one.
•
--rollback
Roll back to the previous generation.
•
--list-generations
List all generations of the profile.
•
--switch-generation generation
Switch the profile to the specified generation.
•
--delete-generations generation ...
Delete the specified generations.
•
-d, --delete-empty
Remove empty generations. A generation is empty if it contains no packages.

Normally, the Nix store directory (typically /nix/store) is not allowed to contain any symlink components. This is to prevent “impure” builds. Builders sometimes “canonicalise” paths by resolving all symlink components. Thus, builds on different machines (with /nix/store resolving to different locations) could yield different results. This is generally not a problem, except when builds are deployed to machines where /nix/store resolves differently. If you are sure that you ’re not going to do that, you can set NIX_IGNORE_SYMLINK_STORE to 1.
