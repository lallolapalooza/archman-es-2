nix-store-dump-db(1)

Paquete: nix

Licencias: LGPL-2.1-only

nix-store --dump-db(1) Manual de Comandos Generales nix-store --dump-db(1)

Nombre

nix-store --dump-db - exportar base de datos de Nix

Sinopsis

nix-store --dump-db [rutas…]

Descripción

La operación --dump-db escribe un volcado de la base de datos de Nix en la salida estándar. Puede ser cargada en un Nix store vacío usando --load-db. Esto es útil para hacer copias de seguridad y al migrar a diferentes esquemas de bases de datos.

Por defecto, --dump-db volcará toda la base de datos de Nix. Cuando se pasan una o más rutas de store, solo se volcará el subconjunto de la base de datos de Nix para esas rutas de store. Al igual que con --export, el usuario es responsable de pasar todas las rutas de store para un cierre. Ver --export para un ejemplo.

Opciones

Las siguientes opciones están permitidas para todas las operaciones de nix-store, pero pueden no tener efecto siempre.

•
--add-root ruta
Causa que el resultado de una realización (--realise y --force-realise) sea registrado como una raíz del recolector de basura. ruta será creada como un enlace simbólico a la ruta de store resultante. Adicionalmente, un enlace simbólico con nombre único a ruta será creado en /nix/var/nix/gcroots/auto/. Por ejemplo,
$ nix-store --add-root /home/eelco/bla/resultado --realise ...
$ ls -l /nix/var/nix/gcroots/auto
lrwxrwxrwx    1 ... 2005-03-13 21:10 dn54lcypm8f8... -> /home/eelco/bla/resultado
$ ls -l /home/eelco/bla/resultado
lrwxrwxrwx    1 ... 2005-03-13 21:10 /home/eelco/bla/resultado -> /nix/store/1r11343n6qd4...-f-spot-0.0.10
Así, cuando se elimine /home/eelco/bla/resultado, la raíz del GC en el directorio auto se convertirá en un enlace simbólico colgante y será ignorado por el colector.
Advertencia
Ten en cuenta que no es posible mover o renombrar raíces de GC, ya que el enlace simbólico en el directorio auto seguirá apuntando a la ubicación anterior.
Si hay múltiples resultados, se crearán múltiples enlaces simbólicos, numerando secuencialmente los enlaces simbólicos después del primero (ej. foo, foo-2, foo-3, y así sucesivamente).

Opciones Comunes

La mayoría de los comandos de Nix aceptan las siguientes opciones de línea de comandos:

•
--help
Imprime un resumen de la sintaxis del comando y sale.
•
--version
Imprime el número de versión de Nix en la salida estándar y sale.
•
--verbose / -v
Aumenta el nivel de verbosidad de los mensajes de diagnóstico impresos en la salida de error estándar. Para cada operación de Nix, la información impresa en la salida estándar está bien definida; cualquier información de diagnóstico se imprime en la salida de error estándar, nunca en la salida estándar.
Esta opción puede especificarse repetidamente. Actualmente, los siguientes niveles de verbosidad existen:
•
0 "Sólo errores"
Solo imprime mensajes que expliquen por qué falló la invocación de Nix.
•
1 "Informativo"
Imprime mensajes *útiles* sobre lo que Nix está haciendo. Este es el valor por defecto.
•
2 "Hablador"
Imprime más mensajes informativos.
•
3 "Charla"
Imprime aún más mensajes informativos.
•
4 "Depurar"
Imprime información de depuración.
•
5 "Vomitar"
Imprime grandes cantidades de información de depuración.
•
--quiet
Disminuye el nivel de verbosidad de los mensajes de diagnóstico impresos en la salida de error estándar. Esta es la opción inversa a -v / --verbose.
Esta opción puede especificarse repetidamente. Ver la lista anterior de niveles de verbosidad.
•
--log-format formato
Esta opción se puede usar para cambiar la salida del formato de log, con formato siendo uno de:
•
raw
Este es el formato raw, tal como lo genera nix-build.
•
internal-json
Genera los logs en un formato estructurado.
Advertencia
Si bien el esquema es relativamente estable, el formato de los mensajes de error (específicamente del campo msg) puede cambiar entre versiones.
•
bar
Solo muestra una barra de progreso durante las compilaciones.
•
bar-with-logs
Muestra los logs raw, con la barra de progreso en la parte inferior.
•
--no-build-output / -Q
Por defecto, la salida generada por los constructores en la salida estándar y el error estándar se muestra en el error estándar del comando Nix. Esta opción suprime este comportamiento. Ten en cuenta que la salida estándar y el error estándar del constructor siempre se escriben en un archivo de log en prefijo/nix/var/log/nix.
•
--max-jobs / -j número
Establece el número máximo de trabajos de compilación que Nix realizará en paralelo al número especificado. Especifica auto para usar el número de CPUs del sistema. El valor por defecto es especificado por la configuración max-jobs, que por sí misma tiene por defecto 1. Un valor más alto es útil en sistemas SMP o para explotar la latencia de E/S.
Establecerlo en 0 prohíbe la compilación en la máquina local, lo cual es útil cuando se desean compilaciones que solo ocurran en constructores remotos.
•
--cores
Establece el valor de la variable de entorno NIX_BUILD_CORES en la invocación de los constructores. Los constructores pueden usar esta variable a su discreción para controlar la cantidad máxima de paralelismo. Por ejemplo, en Nixpkgs, si el atributo de derivación

OPTIONS

•
--enable-parallel-building / -j
If enableParallelBuilding is set to true, the builder passes the -jN flag to GNU Make. It defaults to the value of the cores configuration setting, if set, or 1 otherwise. The value 0 means that the builder should use all available CPU cores in the system.
•
--max-silent-time
Establece el número máximo de segundos que un compilador puede pasar sin producir ningún dato en la salida estándar o el error estándar. El valor predeterminado es el especificado por la configuración de max-silent-time. 0 significa que no hay tiempo de espera.
•
--timeout
Establece el número máximo de segundos que un compilador puede ejecutarse. El valor predeterminado es el especificado por la configuración de timeout. 0 significa que no hay tiempo de espera.
•
--keep-going / -k
Continúa en caso de fallos en la compilación, en la mayor medida posible. Es decir, si falla la compilación de una entrada de alguna derivación, Nix seguirá compilando las otras entradas, pero no la derivación en sí. Sin esta opción, Nix se detiene si alguna compilación falla (excepto las compilaciones de sustitutos), posiblemente matando compilaciones en curso (en caso de compilaciones paralelas o distribuidas).
•
--keep-failed / -K
Especifica que en caso de fallo de compilación, el directorio temporal (generalmente en /tmp) en el que se realiza la compilación no debe eliminarse. La ruta del directorio de compilación se imprime como un mensaje informativo.
•
--fallback
Siempre que Nix intente compilar una derivación para la que se conocen sustitutos para cada ruta de salida, pero la realización de las rutas de salida a través de los sustitutos falla, recurre a la compilación de la derivación.
El escenario más común en el que esto es útil es cuando hemos registrado sustitutos para realizar la distribución binaria desde, por ejemplo, un repositorio de red. Si el repositorio está caído, la realización de la derivación fallará. Cuando se especifica esta opción, Nix compilará la derivación en su lugar. Por lo tanto, la instalación desde binarios recurre a la instalación desde código fuente. Esta opción no es la predeterminada, ya que generalmente no es deseable que un fallo transitorio en la obtención de los sustitutos lleve a una compilación completa desde código fuente (con el consumo relacionado de recursos).
•
--readonly-mode
Cuando se utiliza esta opción, no se intenta abrir la base de datos de Nix. La mayoría de las operaciones de Nix requieren acceso a la base de datos, por lo que esas operaciones fallarán.
•
--arg nombre valor
Esta opción es aceptada por nix-env, nix-instantiate, nix-shell y nix-build. Al evaluar expresiones Nix, el evaluador de expresiones intentará automáticamente llamar a las funciones que encuentre. Puede llamar automáticamente a funciones para las que cada argumento tenga un valor predeterminado (por ejemplo, { argName ? defaultValue }: ...).
Con --arg, también puede llamar a funciones que tienen argumentos sin valor predeterminado (o anular un valor predeterminado). Es decir, si el evaluador encuentra una función con un argumento llamado nombre, la llamará con el valor valor.
Por ejemplo, el default.nix de nivel superior en Nixpkgs es en realidad una función:
{ # El sistema (por ejemplo, `i686-linux') para el que se compilarán los paquetes.
system ? builtins.currentSystem
...
}: ...
Así, si llama a esta expresión Nix (por ejemplo, cuando ejecuta nix-env --install --attr pkgname), la función se llamará automáticamente usando el valor builtins.currentSystem para el argumento system. Puede anular esto usando --arg, por ejemplo, nix-env --install --attr pkgname --arg system \"i686-freebsd\". (Tenga en cuenta que como el argumento es una cadena literal de Nix, debe escapar las comillas.)
•
--argstr nombre valor
Esta opción es como --arg, solo que el valor no es una expresión Nix sino una cadena. Así que en lugar de --arg system \"i686-linux\" (las comillas exteriores son para que el shell funcione correctamente) puede decir --argstr system i686-linux.
•
--attr / -A attrPath
Selecciona un atributo de la expresión Nix de nivel superior que se está evaluando. (Solo nix-env, nix-instantiate, nix-build y nix-shell.) El ruta de atributo attrPath es una secuencia de nombres de atributos separados por puntos. Por ejemplo, dada una expresión Nix de nivel superior e, la ruta de atributo xorg.xorgserver haría que se utilizara la expresión e.xorg.xorgserver. Consulte nix-env --install para ver algunos ejemplos concretos.
Además de los nombres de atributos, también puede especificar índices de matriz. Por ejemplo, la ruta de atributo foo.3.bar selecciona el atributo bar del cuarto elemento de la matriz en el atributo foo de la expresión de nivel superior.
•
--expr / -E
Interpreta los argumentos de la línea de comandos como una lista de expresiones Nix que se van a analizar y evaluar, en lugar de como una lista de nombres de archivos de expresiones Nix. (Solo nix-instantiate, nix-build y nix-shell.)
Para nix-shell, esta opción se usa comúnmente para proporcionarle un shell en el que puede compilar los paquetes devueltos por la expresión. Si desea obtener un shell que contenga los paquetes compilados listos para usar, proporcione su expresión a la bandera de conveniencia nix-shell --packages en su lugar.
•
-I / --include ruta
Añade una entrada a la lista de rutas de búsqueda utilizadas para resolver rutas de búsqueda. Esta opción se puede proporcionar varias veces.
Las rutas añadidas a través de -I tienen prioridad sobre la configuración de nix-path y la variable de entorno NIX_PATH.
•
--option nombre valor
Establece la opción de configuración de Nix nombre a valor. Esto anula la configuración en el archivo de configuración de Nix (ver nix.conf5).
•
--repair
Repara rutas de tienda corruptas o faltantes volviendo a descargarlas o recompilándolas. Tenga en cuenta que esto es lento porque requiere calcular un hash criptográfico del contenido de cada ruta en el cierre de la compilación. También tenga en cuenta la advertencia en nix-store --repair-path.

Nota

Consulte man nix.conf para anular la configuración con indicadores de línea de comandos.

Variables de Entorno Comunes

La mayoría de los comandos de Nix interpretan las siguientes variables de entorno:

•
IN_NIX_SHELL
Indicador que informa si el entorno actual fue configurado por nix-shell. Puede tener los valores pure o impure.
•
NIX_PATH
Una lista separada por dos puntos de entradas de ruta de búsqueda utilizadas para resolver rutas de búsqueda.
Esta variable de entorno anula el valor de la configuración nix-path.
Se puede extender usando la opción -I.
Ejemplo
$ export NIX_PATH=`/home/eelco/Dev:nixos-config=/etc/nixos
Si NIX_PATH está configurado como una cadena vacía, la resolución de las rutas de búsqueda siempre fallará.
Ejemplo
$ NIX_PATH= nix-instantiate --eval '<nixpkgs>'
error: el archivo 'nixpkgs' no se encontró en la ruta de búsqueda de Nix (añádelo usando $NIX_PATH o -I)
•
NIX_IGNORE_SYMLINK_STORE
Normalmente, el directorio de la tienda Nix (típicamente /nix/store) no tiene permitido contener ningún componente de enlace simbólico. Esto es para prevenir compilaciones "impuras". Los compiladores a veces "canonicen" las rutas resolviendo todos los componentes de enlace simbólico. Por lo tanto, las compilaciones en diferentes máquinas (con /nix/store resolviendo a diferentes ubicaciones) podrían producir resultados diferentes. Esto generalmente no es un problema, excepto cuando las compilaciones se implementan en máquinas donde /nix/store se resuelve de manera diferente. Si estás seguro de que no vas a hacer eso, puedes establecer NIX_IGNORE_SYMLINK_STORE a 1.
Ten en cuenta que si estás enlazando simbólicamente la tienda Nix para poder ponerla en un sistema de archivos diferente al del sistema de archivos raíz, en Linux es mejor usar puntos de montaje de tipo bind, por ejemplo:
$ mkdir /nix
$ mount -o bind /mnt/otherdisk/nix /nix
Consulta la página del manual de mount 8 para más detalles.
•
NIX_STORE_DIR
Anula la ubicación del directorio de la tienda Nix (por defecto prefix/store).
•
NIX_DATA_DIR
Anula la ubicación del directorio de datos estáticos de Nix (por defecto prefix/share).
•
NIX_LOG_DIR
Anula la ubicación del directorio de registros de Nix (por defecto prefix/var/log/nix).
•
NIX_STATE_DIR
Anula la ubicación del directorio de estado de Nix (por defecto prefix/var/nix).
•
NIX_CONF_DIR
Anula la ubicación del directorio de configuración del sistema Nix (por defecto prefix/etc/nix).
•
NIX_CONFIG
Aplica configuraciones de Nix desde el entorno. El contenido se trata como si se hubiera leído de un archivo de configuración de Nix. Las configuraciones están separadas por el carácter de nueva línea.
•
NIX_USER_CONF_FILES
Anula la ubicación de los archivos de configuración de usuario de Nix a cargar desde.
Los valores predeterminados son las ubicaciones según la Especificación de Directorios Base XDG. Consulta la subsección Directorios Base XDG para más detalles.
La variable se trata como una lista separada por el token :.
•
TMPDIR
Utiliza el directorio especificado para almacenar archivos temporales. En particular, esto incluye directorios de compilación temporales; estos pueden ocupar cantidades sustanciales de espacio en disco. El valor predeterminado es /tmp.
•
NIX_REMOTE
Esta variable debe establecerse en daemon si deseas utilizar el demonio de Nix para ejecutar operaciones de Nix. Esto es necesario en instalaciones de Nix multiusuario. Si el socket Unix del demonio de Nix está en una ruta no estándar, esta variable debe establecerse en unix://path/to/socket. De lo contrario, debe dejarse sin establecer.
•
NIX_SHOW_STATS
Si se establece en 1, Nix imprimirá algunas estadísticas de evaluación, como el número de valores asignados.
•
NIX_COUNT_CALLS
Si se establece en 1, Nix imprimirá cuántas veces se llamaron las funciones durante la evaluación de expresiones Nix. Esto es útil para perfilar tus expresiones Nix.
•
GC_INITIAL_HEAP_SIZE
Si Nix se ha configurado para usar el recolector de basura de Boehm, esta variable establece el tamaño inicial del montón en bytes. Por defecto es 384 MiB. Establecerla en un valor bajo reduce el consumo de memoria, pero aumentará el tiempo de ejecución debido a la sobrecarga de la recolección de basura.

Directorios Base XDG

Nix sigue la Especificación de Directorios Base XDG.

Por compatibilidad con versiones anteriores, los comandos de Nix seguirán el estándar solo cuando use-xdg-base-directories esté habilitado. Los nuevos comandos de Nix (experimentales) cumplen con el estándar por defecto.

Las siguientes variables de entorno se utilizan para determinar las ubicaciones de varios archivos de estado y configuración:

  • [XDG_CONFIG_HOME]{#env-XDGCONFIGHOME} (por defecto ~/.config)
  • [XDG_STATE_HOME]{#env-XDGSTATEHOME} (por defecto ~/.local/state)
  • [XDG_CACHE_HOME]{#env-XDGCACHEHOME} (por defecto ~/.cache)
