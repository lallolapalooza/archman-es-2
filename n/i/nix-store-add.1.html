nix-store --add(1) Manual de Comandos Generales nix-store --add(1)

Nombre

nix-store --add - añadir rutas al almacén Nix

Sinopsis

nix-store --add rutas…

Descripción

La operación --add añade las rutas especificadas al almacén Nix. Imprime las rutas resultantes en el almacén Nix en la salida estándar.

Opciones

Las siguientes opciones están permitidas para todas las operaciones de nix-store, pero pueden no tener efecto siempre.

•
--add-root ruta
Hace que el resultado de una realización (--realise y --force-realise) se registre como una raíz del recolector de basura. ruta se creará como un enlace simbólico a la ruta del almacén resultante. Además, se creará un enlace simbólico con nombre único a ruta en /nix/var/nix/gcroots/auto/. Por ejemplo,
$ nix-store --add-root /home/eelco/bla/result --realise ...
$ ls -l /nix/var/nix/gcroots/auto
lrwxrwxrwx    1 ... 2005-03-13 21:10 dn54lcypm8f8... -> /home/eelco/bla/result
$ ls -l /home/eelco/bla/result
lrwxrwxrwx    1 ... 2005-03-13 21:10 /home/eelco/bla/result -> /nix/store/1r11343n6qd4...-f-spot-0.0.10
Por lo tanto, cuando se elimine /home/eelco/bla/result, la raíz del GC en el directorio auto se convertirá en un enlace simbólico colgado y será ignorado por el recolector.
Advertencia
Tenga en cuenta que no es posible mover ni renombrar raíces de GC, ya que el enlace simbólico en el directorio auto seguirá apuntando a la ubicación antigua.
Si hay varios resultados, se crearán varios enlaces simbólicos numerando secuencialmente los enlaces simbólicos más allá del primero (por ejemplo, foo, foo-2, foo-3, y así sucesivamente).

Opciones Comunes

La mayoría de los comandos Nix aceptan las siguientes opciones de línea de comandos:

•
--help
Imprime un resumen de la sintaxis del comando y sale.
•
--version
Imprime el número de versión de Nix en la salida estándar y sale.
•
--verbose / -v
Aumenta el nivel de verbosidad de los mensajes de diagnóstico impresos en la salida estándar de error. Para cada operación de Nix, la información imprimida en la salida estándar es bien definida; cualquier información de diagnóstico se imprime en la salida estándar de error, nunca en la salida estándar.
Esta opción se puede especificar repetidamente. Actualmente, existen los siguientes niveles de verbosidad:
•
0 "Solo errores"
Solo imprime mensajes que explican por qué falló la invocación de Nix.
•
1 "Informativo"
Imprime mensajes *útiles* sobre lo que está haciendo Nix. Este es el predeterminado.
•
2 "Hablador"
Imprime más mensajes informativos.
•
3 "Charla constante"
Imprime aún más mensajes informativos.
•
4 "Depuración"
Imprime información de depuración.
•
5 "Vomitar"
Imprime cantidades enormes de información de depuración.
•
--quiet
Disminuye el nivel de verbosidad de los mensajes de diagnóstico impresos en la salida estándar de error. Esta es la opción inversa a -v / --verbose.
Esta opción se puede especificar repetidamente. Consulte la lista anterior de niveles de verbosidad.
•
--log-format formato
Esta opción se puede usar para cambiar la salida del formato de registro, siendo formato uno de:
•
raw
Este es el formato crudo, tal como lo produce nix-build.
•
internal-json
Imprime los registros de forma estructurada.
Advertencia
Aunque el esquema en sí es relativamente estable, el formato de los mensajes de error (especialmente del campo msg) puede cambiar entre versiones.
•
bar
Solo muestra una barra de progreso durante las compilaciones.
•
bar-with-logs
Muestra los registros crudos, con la barra de progreso en la parte inferior.
•
--no-build-output / -Q
Por defecto, la salida escrita por los compiladores en la salida estándar y la salida estándar de error se repite en la salida estándar de error del comando Nix. Esta opción suprime este comportamiento. Tenga en cuenta que la salida estándar y el error del compilador siempre se escriben en un archivo de registro en prefix/nix/var/log/nix.
•
--max-jobs / -j número
Establece el número máximo de trabajos de compilación que Nix realizará en paralelo al número especificado. Especifique auto para usar el número de CPU del sistema. El valor predeterminado lo especifica la configuración max-jobs, que a su vez predetermina en 1. Un valor más alto es útil en sistemas SMP o para aprovechar la latencia de E/S.
Establecerlo en 0 deshabilita la compilación en la máquina local, lo cual es útil cuando desea que las compilaciones ocurran solo en compiladores remotos.
•
--cores
Establece el valor de la variable de entorno NIX_BUILD_CORES en la invocación de los compiladores. Los compiladores pueden usar esta variable a su discreción para controlar el paralelismo máximo. Por ejemplo, en Nixpkgs, si el atributo de derivación enableParallelBuilding está establecido en true, el compilador pasa el flag -jN a GNU Make. Predetermina al valor de la configuración cores, si está establecida, o a 1 en caso contrario. El valor 0 significa que el compilador debe usar todos los núcleos de CPU disponibles en el sistema.
•

OPTIONS

•
--max-silent-time
Establece el número máximo de segundos que un constructor puede pasar sin producir ningún dato en la salida estándar o en el error estándar. El valor por defecto es el especificado por la configuración max-silent-time. 0 significa sin tiempo de espera.
•
--timeout
Establece el número máximo de segundos que un constructor puede ejecutarse. El valor por defecto es el especificado por la configuración timeout. 0 significa sin tiempo de espera.
•
--keep-going / -k
Continúa en caso de fallos en las compilaciones, en la mayor medida posible. Es decir, si falla la compilación de una entrada de alguna derivación, Nix seguirá compilando las otras entradas, pero no la derivación en sí. Sin esta opción, Nix se detiene si falla alguna compilación (excepto las compilaciones de sustitutos), posiblemente matando compilaciones en curso (en caso de compilaciones paralelas o distribuidas).
•
--keep-failed / -K
Especifica que en caso de fallo de compilación, el directorio temporal (generalmente en /tmp) en el que tiene lugar la compilación no debe ser eliminado. La ruta del directorio de compilación se imprime como un mensaje informativo.
•
--fallback
Cada vez que Nix intente compilar una derivación para la que se conocen sustitutos para cada ruta de salida, pero la realización de las rutas de salida a través de los sustitutos falle, recurrirá a la compilación de la derivación.
El escenario más común en el que esto es útil es cuando hemos registrado sustitutos para realizar la distribución binaria desde, digamos, un repositorio de red. Si el repositorio está caído, la realización de la derivación fallará. Cuando se especifica esta opción, Nix compilará la derivación en su lugar. Por lo tanto, la instalación desde binarios recurrirá a la instalación desde el código fuente. Esta opción no es la predeterminada, ya que generalmente no es deseable que un fallo transitorio en la obtención de los sustitutos conduzca a una compilación completa desde el código fuente (con el consumo relacionado de recursos).
•
--readonly-mode
Cuando se utiliza esta opción, no se intenta abrir la base de datos de Nix. La mayoría de las operaciones de Nix necesitan acceso a la base de datos, por lo que esas operaciones fallarán.
•
--arg name value
Esta opción es aceptada por nix-env, nix-instantiate, nix-shell y nix-build. Al evaluar expresiones Nix, el evaluador de expresiones intentará automáticamente llamar a las funciones que encuentre. Puede llamar automáticamente a funciones para las que todos los argumentos tienen un valor por defecto (p. ej., { argName ? defaultValue }: ...).
Con --arg, también puede llamar a funciones que tienen argumentos sin valor por defecto (o anular un valor por defecto). Es decir, si el evaluador encuentra una función con un argumento llamado name, la llamará con el valor value.
Por ejemplo, el default.nix de nivel superior en Nixpkgs es en realidad una función:
{ # El sistema (p. ej., `i686-linux') para el que se compilarán los paquetes.
system ? builtins.currentSystem
...
}: ...
Así que si llama a esta expresión Nix (por ejemplo, cuando ejecuta nix-env --install --attr pkgname), la función se llamará automáticamente usando el valor builtins.currentSystem para el argumento system. Puede anular esto usando --arg, por ejemplo, nix-env --install --attr pkgname --arg system \"i686-freebsd\". (Tenga en cuenta que dado que el argumento es una cadena literal de Nix, debe escapar las comillas.)
•
--argstr name value
Esta opción es como --arg, solo que el valor no es una expresión Nix sino una cadena. Así que en lugar de --arg system \"i686-linux\" (las comillas exteriores son para que el shell funcione) puede decir --argstr system i686-linux.
•
--attr / -A attrPath
Selecciona un atributo de la expresión Nix de nivel superior que se está evaluando. (Solo nix-env, nix-instantiate, nix-build y nix-shell.) La ruta de atributo attrPath es una secuencia de nombres de atributos separados por puntos. Por ejemplo, dada una expresión Nix de nivel superior e, la ruta de atributo xorg.xorgserver haría que se utilizara la expresión e.xorg.xorgserver. Consulte nix-env --install para ver algunos ejemplos concretos.
Además de los nombres de atributos, también puede especificar índices de arreglos. Por ejemplo, la ruta de atributo foo.3.bar selecciona el atributo bar del cuarto elemento del arreglo en el atributo foo de la expresión de nivel superior.
•
--expr / -E
Interpreta los argumentos de la línea de comandos como una lista de expresiones Nix para analizar y evaluar, en lugar de como una lista de nombres de archivo de expresiones Nix. (Solo nix-instantiate, nix-build y nix-shell.)
Para nix-shell, esta opción se usa comúnmente para proporcionarle un shell en el que puede compilar los paquetes devueltos por la expresión. Si desea obtener un shell que contenga los paquetes compilados listos para usar, proporcione su expresión al indicador de conveniencia nix-shell --packages en su lugar.
•
-I / --include path
Añade una entrada a la lista de rutas de búsqueda utilizadas para resolver rutas de búsqueda. Esta opción puede darse varias veces.
Las rutas añadidas a través de -I tienen prioridad sobre la configuración nix-path y la variable de entorno NIX_PATH.
•
--option name value
Establece la opción de configuración de Nix name a value. Esto anula la configuración en el archivo de configuración de Nix (ver nix.conf5).
•
--repair
Repara rutas de la tienda corruptas o faltantes volviendo a descargarlas o recompilándolas. Tenga en cuenta que esto es lento porque requiere calcular un hash criptográfico del contenido de cada ruta en el cierre de la compilación. Tenga también en cuenta la advertencia en nix-store --repair-path.

Nota

Consulte man nix.conf para anular la configuración con indicadores de línea de comandos.

VARIABLES DE ENTORNO COMUNES

La mayoría de los comandos de Nix interpretan las siguientes variables de entorno:

•
IN_NIX_SHELL
Indicador que informa si el entorno actual fue configurado por nix-shell. Puede tener los valores pure o impure.
•
NIX_PATH
Una lista separada por dos puntos de entradas de ruta de búsqueda utilizadas para resolver rutas de búsqueda.
Esta variable de entorno anula el valor de la configuración nix-path.
Puede extenderse utilizando la opción -I.
Ejemplo
$ export NIX_PATH=`/home/eelco/Dev:nixos-config=/etc/nixos
Si NIX_PATH se establece en una cadena vacía, la resolución de rutas de búsqueda siempre fallará.
Ejemplo
$ NIX_PATH= nix-instantiate --eval '<nixpkgs>'
error: file 'nixpkgs' was not found in the Nix search path (add it using $NIX_PATH or -I)

nix-store --add

Name

nix-store(1), --add — add a file or directory to the Nix store

Synopsis

nix-store --add [--recursive] --

Description

Adds a file or directory to the Nix store. The command produces the path of the new store item on standard output.

This command is intended for adding existing files and directories to the Nix store. For building packages from source, use nix-build(1).

The contents of the added file or directory are hashed, and the hash becomes part of the output path in the Nix store.

The --recursive option causes directories to be added recursively.

Note that this command does not guarantee reproducibility. For instance, if you add a file containing a symbolic link, the link will be followed, and the target file will be added to the store instead. If you want to add the symbolic link itself, you need to use nix-store(1) with the --no-check- Nix-store-references option, and add the file like so:

$ nix-store --no-check- Nix-store-references --add symlink.txt

However, Nix builds are not allowed to contain symlink components. This is to prevent “impure” builds. Builders sometimes “canonicalise” paths by resolving all symlink components. Thus, builds on different machines (with /nix/store resolving to different locations) could yield different results. This is generally not a problem, except when builds are deployed to machines where /nix/store resolves differently. If you are sure that you’re not going to do that, you can set NIX_IGNORE_SYMLINK_STORE to 1.

Note that if you’re symlinking the Nix store so that you can put it on another file system than the root file system, on Linux you’re better off using bind mount points, e.g.,

$ mkdir /nix
$ mount -o bind /mnt/otherdisk/nix /nix

Consult the mount 8 manual page for details.

Options

•
NIX_STORE_DIR
Overrides the location of the Nix store (default prefix/store).
•
NIX_DATA_DIR
Overrides the location of the Nix static data directory (default prefix/share).
•
NIX_LOG_DIR
Overrides the location of the Nix log directory (default prefix/var/log/nix).
•
NIX_STATE_DIR
Overrides the location of the Nix state directory (default prefix/var/nix).
•
NIX_CONF_DIR
Overrides the location of the system Nix configuration directory (default prefix/etc/nix).
•
NIX_CONFIG
Applies settings from Nix configuration from the environment. The content is treated as if it was read from a Nix configuration file. Settings are separated by the newline character.
•
NIX_USER_CONF_FILES
Overrides the location of the Nix user configuration files to load from.
The default are the locations according to the XDG Base Directory Specification. See the XDG Base Directories sub-section for details.
The variable is treated as a list separated by the : token.
•
TMPDIR
Use the specified directory to store temporary files. In particular, this includes temporary build directories; these can take up substantial amounts of disk space. The default is /tmp.
•
NIX_REMOTE
This variable should be set to daemon if you want to use the Nix daemon to execute Nix operations. This is necessary in multi-user Nix installations. If the Nix daemon’s Unix socket is at some non-standard path, this variable should be set to unix://path/to/socket. Otherwise, it should be left unset.
•
NIX_SHOW_STATS
If set to 1, Nix will print some evaluation statistics, such as the number of values allocated.
•
NIX_COUNT_CALLS
If set to 1, Nix will print how often functions were called during Nix expression evaluation. This is useful for profiling your Nix expressions.
•
GC_INITIAL_HEAP_SIZE
If Nix has been configured to use the Boehm garbage collector, this variable sets the initial size of the heap in bytes. It defaults to 384 MiB. Setting it to a low value reduces memory consumption, but will increase runtime due to the overhead of garbage collection.

XDG Base Directories

Nix follows the XDG Base Directory Specification.

For backwards compatibility, Nix commands will follow the standard only when use-xdg-base-directories is enabled. New Nix commands (experimental) conform to the standard by default.

The following environment variables are used to determine locations of various state and configuration files:

  • [XDG_CONFIG_HOME]{#env-XDGCONFIGHOME} (default ~/.config)
  • [XDG_STATE_HOME]{#env-XDGSTATEHOME} (default ~/.local/state)
  • [XDG_CACHE_HOME]{#env-XDGCACHEHOME} (default ~/.cache)

Example

$ nix-store --add ./foo.c
/nix/store/m7lrha58ph6rcnv109yzx1nk1cj7k7zf-foo.c
