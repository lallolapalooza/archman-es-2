nix-build(1)

Paquete: nix

Licencias: LGPL-2.1-only

nix-build(1) Manual de Comandos Generales nix-build(1)

Nombre

nix-build - construye una expresión de Nix

Sintaxis

nix-build [rutas…] [--arg nombre valor] [--argstr nombre valor] [{--attr | -A} RutaDeAtributo] [--no-out-link] [--dry-run] [{--out-link | -o} enlace_salida]

Desambiguación

Esta página del manual describe el comando nix-build, que es distinto de nix build. Para la documentación sobre este último, ejecuta nix build --help o consulta man nix3-build.

Descripción

El comando nix-build construye las derivaciones descritas por las expresiones de Nix en rutas. Si la construcción tiene éxito, coloca un enlace simbólico al resultado en el directorio actual. El enlace simbólico se llama result. Si hay múltiples expresiones de Nix, o si las expresiones de Nix evalúan a múltiples derivaciones, se crean múltiples enlaces simbólicos numerados secuencialmente (result, result-2 y así sucesivamente).

Si no se especifican rutas, entonces nix-build usará default.nix en el directorio actual, si existe.

Si un elemento de rutas comienza con http:// o https://, se interpreta como la URL de un archivo tar que será descargado y desempaquetado en una ubicación temporal. El archivo tar debe incluir un único directorio de nivel superior que contenga al menos un archivo llamado default.nix.

nix-build es esencialmente un envoltorio alrededor de nix-instantiate (para traducir una expresión de Nix de alto nivel a una derivación de almacén de bajo nivel) y nix-store --realise (para construir la derivación de almacén).

Advertencia

El resultado de la construcción se registra automáticamente como una raíz del recolector de basura de Nix. Esta raíz desaparece automáticamente cuando se elimina o renombra el enlace simbólico result. Por lo tanto, no renombres el enlace simbólico.

Opciones

Todas las opciones no listadas aquí se pasan a nix-store --realise, excepto --arg y --attr / -A que se pasan a nix-instantiate.

•
--no-out-link
No crear un enlace simbólico a la ruta de salida. Ten en cuenta que, como resultado, la salida no se convierte en una raíz del recolector de basura y, por lo tanto, podría ser eliminada por nix-store --gc.
•
--dry-run
Mostrar qué rutas de almacén se construirían o descargarían.
•
--out-link / -o enlace_salida
Cambiar el nombre del enlace simbólico a la ruta de salida creado desde result a enlace_salida.

Códigos de salida especiales para fallo de construcción

Los códigos de estado 1xx se utilizan cuando las construcciones solicitadas fallaron. Los siguientes códigos están en uso:

•
100 Fallo genérico de construcción
El proceso constructor devolvió un código de salida distinto de cero.
•
101 Tiempo de espera de construcción agotado
La construcción se abortó porque no se completó dentro del timeout especificado.
•
102 Desajuste de hash
La salida de construcción fue rechazada porque no coincide con el atributo outputHash de la derivación.
•
104 No determinista
La construcción se completó en modo de verificación pero la salida resultante no es binariamente reproducible.

Con la bandera --keep-going es posible que ocurran múltiples fallos. En este caso, los códigos de estado 1xx se combinan usando OR bit a bit.

0b1100100
     ^^^^
     |||`- tiempo agotado
     ||`-- desajuste del hash de salida
     |`--- fallo de construcción
     `---- no determinista

Opciones Comunes

La mayoría de los comandos de Nix aceptan las siguientes opciones de línea de comandos:

•
--help
Imprime un resumen de la sintaxis del comando y sale.
•
--version
Imprime el número de versión de Nix en la salida estándar y sale.
•
--verbose / -v
Aumenta el nivel de verbosidad de los mensajes de diagnóstico impresos en la salida estándar. Para cada operación de Nix, la información impresa en la salida estándar está bien definida; cualquier información de diagnóstico se imprime en la salida estándar, nunca en la salida estándar.
Esta opción se puede especificar repetidamente. Actualmente, existen los siguientes niveles de verbosidad:
•
0 “Solo errores”
Solo imprime mensajes que explican por qué falló la invocación de Nix.
•
1 “Informativo”
Imprime mensajes *útiles* sobre lo que está haciendo Nix. Este es el valor predeterminado.
•
2 “Hablador”
Imprime más mensajes informativos.
•
3 “Conversador”
Imprime aún más mensajes informativos.
•
4 “Depuración”
Imprime información de depuración.
•
5 “Vómito”
Imprime una gran cantidad de información de depuración.
•
--quiet
Disminuye el nivel de verbosidad de los mensajes de diagnóstico impresos en la salida estándar. Esta es la opción inversa a -v / --verbose.
Esta opción se puede especificar repetidamente. Consulte la lista anterior de niveles de verbosidad.
•
--log-format formato
Esta opción se puede usar para cambiar la salida del formato de registro, con formato siendo uno de:
•
raw
Este es el formato crudo, tal como lo genera nix-build.
•
internal-json
Muestra los registros de forma estructurada.
Advertencia
Si bien el esquema en sí es relativamente estable, el formato de los mensajes de error (específicamente del campo msg) puede cambiar entre versiones.
•
bar
Solo muestra una barra de progreso durante las compilaciones.
•
bar-with-logs
Muestra los registros crudos, con la barra de progreso en la parte inferior.
•
--no-build-output / -Q
Por defecto, la salida escrita por los constructores en la salida estándar y el error estándar se reflejan en el error estándar del comando Nix. Esta opción suprime este comportamiento. Tenga en cuenta que la salida estándar y el error estándar del constructor siempre se escriben en un archivo de registro en prefix/nix/var/log/nix.
•
--max-jobs / -j número
Establece el número máximo de trabajos de compilación que Nix realizará en paralelo al número especificado. Especifique auto para usar el número de CPU del sistema. El valor predeterminado es el especificado por la configuración max-jobs, que a su vez tiene como valor predeterminado 1. Un valor más alto es útil en sistemas SMP o para explotar la latencia de I/O.
Establecerlo en 0 deshabilita la compilación en la máquina local, lo cual es útil cuando se desea que las compilaciones ocurran solo en constructores remotos.
•
--cores
Establece el valor de la variable de entorno NIX_BUILD_CORES en la invocación de los constructores. Los constructores pueden usar esta variable a su discreción para controlar el paralelismo máximo. Por ejemplo, en Nixpkgs, si el atributo de derivación enableParallelBuilding está establecido en true, el constructor pasa el flag -jN a GNU Make. Tiene como valor predeterminado el valor de la configuración cores, si está establecida, o 1 en caso contrario. El valor 0 significa que el constructor debe usar todos los núcleos de CPU disponibles en el sistema.
•
--max-silent-time
Establece el número máximo de segundos que un constructor puede pasar sin producir datos en la salida estándar o error estándar. El valor predeterminado es el especificado por la configuración max-silent-time. 0 significa sin tiempo de espera.
•
--timeout
Establece el número máximo de segundos que un constructor puede ejecutarse. El valor predeterminado es el especificado por la configuración timeout. 0 significa sin tiempo de espera.
•
--keep-going / -k
Continúa en caso de fallos de compilación, en la mayor medida posible. Es decir, si falla la compilación de una entrada de una derivación, Nix seguirá compilando las otras entradas, pero no la derivación en sí. Sin esta opción, Nix se detiene si falla alguna compilación (excepto las compilaciones de sustitutos), posiblemente matando las compilaciones en curso (en caso de compilaciones paralelas o distribuidas).
•
--keep-failed / -K
Especifica que en caso de fallo de compilación, el directorio temporal (generalmente en /tmp) en el que se realiza la compilación no debe eliminarse. La ruta del directorio de compilación se imprime como un mensaje informativo.
•
--fallback
Siempre que Nix intente compilar una derivación para la cual se conocen sustitutos para cada ruta de salida, pero la realización de las rutas de salida a través de los sustitutos falla, recurre a la compilación de la derivación.
El escenario más común en el que esto es útil es cuando hemos registrado sustitutos para realizar la distribución binaria desde, por ejemplo, un repositorio de red. Si el repositorio está caído, fallará la realización de la derivación. Cuando se especifica esta opción, Nix compilará la derivación en su lugar. Por lo tanto, la instalación a partir de binarios recurre a la instalación a partir de código fuente. Esta opción no es la predeterminada, ya que generalmente no es deseable que un fallo transitorio en la obtención de los sustitutos lleve a una compilación completa desde el código fuente (con el consumo relacionado de recursos).
•
--readonly-mode
Cuando se utiliza esta opción, no se intenta abrir la base de datos Nix. La mayoría de las operaciones de Nix necesitan acceso a la base de datos, por lo que esas operaciones fallarán.
•
--arg nombre valor
Esta opción es aceptada por nix-env, nix-instantiate, nix-shell y nix-build. Al evaluar expresiones Nix, el evaluador de expresiones intentará automáticamente llamar a las funciones que encuentre. Puede llamar automáticamente a funciones para las cuales cada argumento tiene un valor predeterminado (por ejemplo, { argName ? defaultValue }: ...).
Con --arg, también puedes llamar a funciones que tienen argumentos sin valor predeterminado (o anular un valor predeterminado). Es decir, si el evaluador encuentra una función con un argumento llamado nombre, la llamará con el valor valor.
Por ejemplo, el default.nix de nivel superior en Nixpkgs es en realidad una función:
{ # El sistema (por ejemplo, `i686-linux') para el cual construir los paquetes.
system ? builtins.currentSystem
...
}: ...
Así que si llamas a esta expresión Nix (por ejemplo, cuando haces nix-env --install --attr pkgname), la función se llamará automáticamente usando el valor builtins.currentSystem para el argumento system. Puedes anular esto usando --arg, por ejemplo, nix-env --install --attr pkgname --arg system \"i686-freebsd\". (Ten en cuenta que como el argumento es una cadena literal de Nix, tienes que escapar las comillas.)
•
--argstr nombre valor
Esta opción es como --arg, solo que el valor no es una expresión Nix sino una cadena. Así que en lugar de --arg system \"i686-linux\" (las comillas exteriores son para que el shell lo entienda) puedes decir --argstr system i686-linux.
•
--attr / -A attrPath
Selecciona un atributo de la expresión Nix de nivel superior que se está evaluando. (Solo nix-env, nix-instantiate, nix-build y nix-shell). La ruta de atributo attrPath es una secuencia de nombres de atributos separados por puntos. Por ejemplo, dada una expresión Nix de nivel superior e, la ruta de atributo xorg.xorgserver haría que se usara la expresión e.xorg.xorgserver. Consulta nix-env --install para ver algunos ejemplos concretos.
Además de los nombres de atributos, también puedes especificar índices de arreglos. Por ejemplo, la ruta de atributo foo.3.bar selecciona el atributo bar del cuarto elemento del arreglo en el atributo foo de la expresión de nivel superior.
•
--expr / -E
Interpreta los argumentos de la línea de comandos como una lista de expresiones Nix para ser analizadas y evaluadas, en lugar de como una lista de nombres de archivos de expresiones Nix. (Solo nix-instantiate, nix-build y nix-shell.)
Para nix-shell, esta opción se usa comúnmente para proporcionarte un shell en el que puedas compilar los paquetes devueltos por la expresión. Si deseas obtener un shell que contenga los paquetes *compilados* listos para usar, proporciona tu expresión a la bandera de conveniencia nix-shell --packages en su lugar.
•
-I / --include ruta
Añade una entrada a la lista de rutas de búsqueda utilizadas para resolver rutas de búsqueda. Esta opción puede

Opciones

•
--option nombre valor
Establece la opción de configuración de Nix nombre a valor. Esto anula la configuración en el archivo de configuración de Nix (ver nix.conf5).
•
--repair
Repara rutas de tienda corruptas o faltantes redescargándolas o reconstruyéndolas. Tenga en cuenta que esto es lento porque requiere calcular un hash criptográfico de los contenidos de cada ruta en el cierre de la compilación. Tenga también en cuenta la advertencia bajo nix-store --repair-path.

Nota

Ver man nix.conf para anular la configuración con flags de línea de comandos.

Variables de entorno comunes

La mayoría de los comandos de Nix interpretan las siguientes variables de entorno:

•
IN_NIX_SHELL
Indicador que dice si el entorno actual fue configurado por nix-shell. Puede tener los valores pure o impure.
•
NIX_PATH
Una lista separada por dos puntos de entradas de ruta de búsqueda utilizadas para resolver rutas de búsqueda.
Esta variable de entorno anula el valor de la configuración de Nix nix-path.
Puede ser extendida usando la opción -I.
Ejemplo
$ export NIX_PATH=`/home/eelco/Dev:nixos-config=/etc/nixos
Si NIX_PATH está establecida a una cadena vacía, la resolución de rutas de búsqueda siempre fallará.
Ejemplo
$ NIX_PATH= nix-instantiate --eval '<nixpkgs>'
error: file 'nixpkgs' was not found in the Nix search path (add it using $NIX_PATH or -I)
•
NIX_IGNORE_SYMLINK_STORE
Normalmente, el directorio de la tienda Nix (típicamente /nix/store) no puede contener componentes de enlaces simbólicos. Esto es para prevenir compilaciones "impuras". Los constructores a veces "canonizan" rutas resolviendo todos los componentes de enlaces simbólicos. Por lo tanto, las compilaciones en diferentes máquinas (con /nix/store resolviendo a ubicaciones diferentes) podrían producir resultados diferentes. Esto generalmente no es un problema, excepto cuando las compilaciones se despliegan en máquinas donde /nix/store se resuelve de manera diferente. Si está seguro de que no va a hacer eso, puede establecer NIX_IGNORE_SYMLINK_STORE a 1.
Tenga en cuenta que si está enlazando simbólicamente la tienda Nix para poder ponerla en un sistema de archivos diferente al del sistema de archivos raíz, en Linux es mejor usar puntos de montaje bind, por ejemplo:
$ mkdir /nix
$ mount -o bind /mnt/otherdisk/nix /nix
Consulte la página del manual de mount 8 para más detalles.
•
NIX_STORE_DIR
Anula la ubicación del directorio de la tienda Nix (por defecto prefix/store).
•
NIX_DATA_DIR
Anula la ubicación del directorio de datos estáticos de Nix (por defecto prefix/share).
•
NIX_LOG_DIR
Anula la ubicación del directorio de logs de Nix (por defecto prefix/var/log/nix).
•
NIX_STATE_DIR
Anula la ubicación del directorio de estado de Nix (por defecto prefix/var/nix).
•
NIX_CONF_DIR
Anula la ubicación del directorio de configuración del sistema Nix (por defecto prefix/etc/nix).
•
NIX_CONFIG
Aplica configuraciones de Nix desde el entorno. El contenido se trata como si se hubiera leído de un archivo de configuración de Nix. Las configuraciones están separadas por el carácter de nueva línea.
•
NIX_USER_CONF_FILES
Anula la ubicación de los archivos de configuración de usuario de Nix desde donde cargar.
Los valores predeterminados son las ubicaciones según la Especificación de Directorios Base XDG. Ver la subsección Directorios Base XDG para más detalles.
La variable se trata como una lista separada por el token :.
•
TMPDIR
Utiliza el directorio especificado para almacenar archivos temporales. En particular, esto incluye directorios temporales de compilación; estos pueden ocupar una cantidad considerable de espacio en disco. El valor predeterminado es /tmp.
•
NIX_REMOTE
Esta variable debe establecerse a daemon si desea utilizar el demonio de Nix para ejecutar operaciones de Nix. Esto es necesario en instalaciones de Nix multiusuario. Si el socket Unix del demonio de Nix está en una ruta no estándar, esta variable debe establecerse a unix://ruta/al/socket. De lo contrario, debe dejarse sin establecer.
•
NIX_SHOW_STATS
Si se establece a 1, Nix imprimirá algunas estadísticas de evaluación, como el número de valores asignados.
•
NIX_COUNT_CALLS
Si se establece a 1, Nix imprimirá cuántas veces se llamaron las funciones durante la evaluación de expresiones Nix. Esto es útil para perfilar sus expresiones Nix.
•
GC_INITIAL_HEAP_SIZE
Si Nix ha sido configurado para usar el recolector de basura de Boehm, esta variable establece el tamaño inicial del montón en bytes. Por defecto es 384 MiB. Establecerlo a un valor bajo reduce el consumo de memoria, pero aumentará el tiempo de ejecución debido a la sobrecarga de la recolección de basura.

Directorios base XDG

Nix sigue la Especificación de Directorios Base XDG.

Por compatibilidad con versiones anteriores, los comandos Nix seguirán el estándar solo cuando use-xdg-base-directories esté habilitado. Los comandos Nix nuevos (experimentales) se ajustan al estándar por defecto.

Las siguientes variables de entorno se utilizan para determinar las ubicaciones de varios archivos de estado y configuración:

  • [XDG_CONFIG_HOME]{#env-XDGCONFIGHOME} (por defecto ~/.config)
  • [XDG_STATE_HOME]{#env-XDGSTATEHOME} (por defecto ~/.local/state)
  • [XDG_CACHE_HOME]{#env-XDGCACHEHOME} (por defecto ~/.cache)

nix-build(1)

Name

nix-build - Build Nix expressions.

Synopsis

nix-build [<option>...] [--file <file>] [--attr <attrpath>]

nix-build [<option>...] [--expr <expr>]

nix-build [<option>...] [--url <url>] [--attr <attrpath>]

Disambiguation

By default, nix-build builds the derivation specified by the attribute out in the Nix expression in the file default.nix in the current directory. The result is placed in the symbolic link result in the current directory.

If there is no default.nix, but there is a file shell.nix, it is used as the Nix expression.

If there is no default.nix or shell.nix, it's an error.

Description

The nix-build command builds a Nix expression and makes the result available.

A Nix expression can be provided in several ways:

  • The default file default.nix or shell.nix in the current directory.

  • A specific file using the --file (‐f) option.

  • A Nix expression string using the --expr (‐E) option.

  • A remote tarball or Git repository using the --url option.

By default, nix-build builds the derivation specified by the attribute out in the Nix expression. The result is placed in the symbolic link result in the current directory.

The result is stored in the Nix store (/nix/store). The result symbolic link is updated to point to the newly built derivation in the Nix store.

Most options can be specified multiple times. Their values are concatenated.

Options

--file (or -f) <file>

Build the Nix expression in the specified file.

--expr (or -E) <expr>

Build the given Nix expression.

--url <url>

Build the Nix expression from the given URL. This can be a tarball (.tar.gz, .tar.bz2, etc.) or a Git repository.

--attr <attrpath>

Build the attribute specified by attrpath. For example, hello.man or openssl.

--out-link <name>

Use name instead of result for the output symbolic link.

--no-out-link

Don't create an output symbolic link. Useful when you only want to build derivations for their side effects.

--drv-link <name>

Create a symbolic link named name pointing to the derivation file.

--log-lines <n>

Show the last n lines of build output.

--keep-failed

Do not garbage collect failed builds.

--keep-dependencies

Do not garbage collect dependencies of successful builds.

--allow-pruning

Enable garbage collection of older builds. This is the default behaviour.

--option <name> <value>

Set Nix configuration option name to value. This overrides the Nix configuration file.

--arg <name> <value>

Pass the JSON value value to the Nix expression as the variable name.

--argstr <name> <value>

Pass the string value to the Nix expression as the variable name.

--json

Output build results in JSON format.

--json-file <file>

Write build results to file in JSON format.

--json-pretty

Output build results in pretty-printed JSON format.

--json-key <key>

Use key as the key in the JSON output. Defaults to out.

Special exit codes for build failure

1

Generic build failure.

100

Build dependency failed.

101

The Nix expression failed to evaluate.

102

Build timed out.

Common Options

In addition to the options above, nix-build also accepts the common options found in nix(1).

Common Environment Variables

In addition to the environment variables listed in nix(1), nix-build also recognizes the following:

NIX_BUILD_CORES

The number of CPU cores to use for building derivations. Defaults to the number of CPU cores on the system.

NIX_BUILD_timeouts

Set the maximum build time (in seconds) for each derivation.

NIX_BUILD_MEMLIMIT

Set the maximum amount of memory (in megabytes) that a derivation is allowed to use during the build.

NIX_BUILD_HOOK_PRE_BUILD
NIX_BUILD_HOOK_POST_BUILD
NIX_BUILD_HOOK_PRE_INSTALL
NIX_BUILD_HOOK_POST_INSTALL

Specify a script to be executed before/after the build/install phase of a derivation. These hooks are executed within the sandbox.

Examples

Build the derivation in default.nix and create a symbolic link result:

$ nix-build

Build a specific attribute, e.g. the man pages of openssl:

$ nix-build -A openssl.man

This will create a symlink named result in the current directory, pointing to the built man pages.

Build a specific derivation, e.g. openssl.bin and openssl.man, and put them in separate symlinks:

$ nix-build -A openssl.bin
$ mv result bin
$ nix-build -A openssl.man
$ mv result man

Or more concisely:

$ nix-build --out-link bin -A openssl.bin
$ nix-build --out-link man -A openssl.man

This will create symlinks bin and man.

Build a Nix expression given on the command line:

$ nix-build --expr 'with import <nixpkgs> { }; runCommand "foo" { } "echo bar > $out"'
$ cat ./result
bar

Build the GNU Hello package from the latest revision of the master branch of Nixpkgs:

$ nix-build https://github.com/NixOS/nixpkgs/archive/master.tar.gz --attr hello
