Paquete: nix

Licencias: LGPL-2.1-only

nix-store --dump(1) Manual de Comandos Generales nix-store --dump(1)

Nombre

nix-store --dump - escribir una ruta individual en un Archivo Nix

Sinopsis

nix-store --dump ruta

Descripción

La operación --dump produce un archivo Nix archive (NAR) que contiene los contenidos del árbol de sistema de archivos cuya raíz es ruta. El archivo se escribe en la salida estándar.

Un archivo NAR es similar a un archivo TAR o Zip, pero solo contiene la información que Nix considera importante. Por ejemplo, se omiten las marcas de tiempo porque todos los archivos en el Nix store tienen su marca de tiempo establecida en 0 de todos modos. De manera similar, se omiten todos los permisos excepto el bit de ejecución, porque todos los archivos en el Nix store tienen permisos 444 o 555.

Además, un archivo NAR es canónico, lo que significa que las rutas “iguales” siempre producen el mismo archivo NAR. Por ejemplo, las entradas de directorio siempre se ordenan de manera que el orden real en el disco no influye en el resultado. Esto significa que el hash criptográfico de un volcado NAR de una ruta se puede utilizar como una huella digital del contenido de la ruta. De hecho, los hashes de las rutas del store almacenadas en la base de datos de Nix (ver nix-store --query --hash) son hashes SHA-256 del volcado NAR de cada ruta del store.

Los archivos NAR admiten nombres de archivo de longitud ilimitada y tamaños de archivo de 64 bits. Pueden contener archivos regulares, directorios y enlaces simbólicos, pero no otros tipos de archivos (como nodos de dispositivo).

Un archivo Nix se puede descomprimir usando nix-store --restore.

Opciones

Las siguientes opciones están permitidas para todas las operaciones de nix-store, pero pueden no tener siempre un efecto.

•
--add-root ruta
Hace que el resultado de una realización (--realise y --force-realise) se registre como una raíz del recolector de basura. ruta se creará como un enlace simbólico a la ruta del store resultante. Además, se creará un enlace simbólico con nombre único a ruta en /nix/var/nix/gcroots/auto/. Por ejemplo,
$ nix-store --add-root /home/eelco/bla/result --realise ...
$ ls -l /nix/var/nix/gcroots/auto
lrwxrwxrwx    1 ... 2005-03-13 21:10 dn54lcypm8f8... -> /home/eelco/bla/result
$ ls -l /home/eelco/bla/result
lrwxrwxrwx    1 ... 2005-03-13 21:10 /home/eelco/bla/result -> /nix/store/1r11343n6qd4...-f-spot-0.0.10
Por lo tanto, cuando se elimina /home/eelco/bla/result, la raíz de GC en el directorio auto se convierte en un enlace simbólico colgante y será ignorada por el colector.
Advertencia
Tenga en cuenta que no es posible mover o renombrar raíces de GC, ya que el enlace simbólico en el directorio auto seguirá apuntando a la ubicación anterior.
Si hay varios resultados, se crearán varios enlaces simbólicos numerando secuencialmente los enlaces simbólicos después del primero (por ejemplo, foo, foo-2, foo-3, y así sucesivamente).

Opciones Comunes

La mayoría de los comandos Nix aceptan las siguientes opciones de línea de comandos:

•
--help
Imprime un resumen de la sintaxis del comando y sale.
•
--version
Imprime el número de versión de Nix en la salida estándar y sale.
•
--verbose / -v
Aumenta el nivel de verbosidad de los mensajes de diagnóstico impresos en la salida estándar de error. Para cada operación de Nix, la información impresa en la salida estándar está bien definida; cualquier información de diagnóstico se imprime en la salida estándar de error, nunca en la salida estándar.
Esta opción se puede especificar repetidamente. Actualmente, existen los siguientes niveles de verbosidad:
•
0 "Solo errores"
Solo imprime mensajes que explican por qué falló la invocación de Nix.
•
1 "Informativo"
Imprime mensajes *útiles* sobre lo que está haciendo Nix. Este es el valor predeterminado.
•
2 "Hablador"
Imprime más mensajes informativos.
•
3 "Charla"
Imprime aún más mensajes informativos.
•
4 "Depuración"
Imprime información de depuración.
•
5 "Vómito"
Imprime grandes cantidades de información de depuración.
•
--quiet
Disminuye el nivel de verbosidad de los mensajes de diagnóstico impresos en la salida estándar de error. Esta es la opción inversa a -v / --verbose.
Esta opción se puede especificar repetidamente. Ver la lista anterior de niveles de verbosidad.
•
--log-format formato
Esta opción se puede usar para cambiar la salida del formato de registro, con formato siendo uno de:
•
raw
Este es el formato bruto, como lo emite nix-build.
•
internal-json
Emite los registros en un formato estructurado.
Advertencia
Si bien el esquema en sí es relativamente estable, el formato de los mensajes de error (específicamente el campo msg) puede cambiar entre versiones.
•
bar
Solo muestra una barra de progreso durante las compilaciones.
•
bar-with-logs
Muestra los registros brutos, con la barra de progreso en la parte inferior.
•
--no-build-output / -Q
Por defecto, la salida escrita por los constructores en la salida estándar y la salida estándar de error se refleja en la salida estándar de error del comando Nix. Esta opción suprime este comportamiento. Tenga en cuenta que la salida estándar y el error del constructor siempre se escriben en un archivo de registro en prefix/nix/var/log/nix.
•
--max-jobs / -j número

Este sitio no está asociado de ninguna forma con Arch Linux ni afiliado a este proyecto. El contenido es únicamente una traducción de las páginas del manual de Arch publicadas en man.archlinux.org.

>Establece el número máximo de trabajos de compilación que Nix realizará en paralelo al número especificado. Especifique auto para usar el número de CPUs del sistema. El valor predeterminado es el especificado en la configuración max-jobs, que a su vez tiene por defecto 1. Un valor más alto es útil en sistemas SMP o para aprovechar la latencia de E/S.
Establecerlo en 0 deshabilita la compilación en la máquina local, lo cual es útil cuando desea que las compilaciones ocurran solo en compiladores remotos.
•
--cores
Establece el valor de la variable de entorno NIX_BUILD_CORES en la invocación de los compiladores. Los compiladores pueden usar esta variable a su discreción para controlar el paralelismo máximo. Por ejemplo, en Nixpkgs, si el atributo de derivación enableParallelBuilding está establecido en true, el compilador pasa el flag -jN a GNU Make. Por defecto, toma el valor de la configuración cores, si está establecida, o 1 en caso contrario. El valor 0 significa que el compilador debe usar todos los núcleos de CPU disponibles en el sistema.
•
--max-silent-time
Establece el número máximo de segundos que un compilador puede pasar sin producir ninguna salida en la salida estándar o el error estándar. El valor predeterminado es el especificado en la configuración max-silent-time. 0 significa sin tiempo de espera.
•
--timeout
Establece el número máximo de segundos que un compilador puede ejecutarse. El valor predeterminado es el especificado en la configuración timeout. 0 significa sin tiempo de espera.
•
--keep-going / -k
Continuar en caso de compilaciones fallidas, en la mayor medida posible. Es decir, si falla la compilación de una entrada de una derivación, Nix seguirá compilando las otras entradas, pero no la derivación en sí. Sin esta opción, Nix se detiene si falla alguna compilación (excepto las de sustitutos), posiblemente matando compilaciones en curso (en caso de compilaciones paralelas o distribuidas).
•
--keep-failed / -K
Especifica que en caso de fallo de compilación, el directorio temporal (generalmente en /tmp) en el que se realiza la compilación no debe ser eliminado. La ruta del directorio de compilación se imprime como un mensaje informativo.
•
--fallback
Siempre que Nix intente compilar una derivación para la cual se conocen sustitutos para cada ruta de salida, pero la realización de las rutas de salida a través de los sustitutos falla, recurre a la compilación de la derivación.
El escenario más común en el que esto es útil es cuando hemos registrado sustitutos para realizar la distribución binaria, por ejemplo, desde un repositorio de red. Si el repositorio está caído, la realización de la derivación fallará. Cuando se especifica esta opción, Nix compilará la derivación en su lugar. Por lo tanto, la instalación desde binarios recurre a la instalación desde código fuente. Esta opción no es la predeterminada ya que generalmente no es deseable que un fallo transitorio en la obtención de los sustitutos conduzca a una compilación completa desde código fuente (con el consumo de recursos asociado).
•
--readonly-mode
Cuando se utiliza esta opción, no se intenta abrir la base de datos de Nix. La mayoría de las operaciones de Nix necesitan acceso a la base de datos, por lo que esas operaciones fallarán.
•
--arg nombre valor
Esta opción es aceptada por nix-env, nix-instantiate, nix-shell y nix-build. Al evaluar expresiones Nix, el evaluador de expresiones intentará automáticamente llamar a las funciones que encuentre. Puede llamar automáticamente a funciones para las que todos los argumentos tienen un valor predeterminado (por ejemplo, { argName ? defaultValue }: ...).
Con --arg, también puede llamar a funciones que tienen argumentos sin valor predeterminado (o anular un valor predeterminado). Es decir, si el evaluador encuentra una función con un argumento llamado nombre, la llamará con el valor valor.
Por ejemplo, el default.nix de nivel superior en Nixpkgs es en realidad una función:
{ # El sistema (por ejemplo, `i686-linux') para el que compilar los paquetes.
system ? builtins.currentSystem
...
}: ...
Así que si llama a esta expresión Nix (por ejemplo, cuando ejecuta nix-env --install --attr pkgname), la función se llamará automáticamente utilizando el valor de builtins.currentSystem para el argumento system. Puede anular esto usando --arg, por ejemplo, nix-env --install --attr pkgname --arg system \"i686-freebsd\". (Tenga en cuenta que dado que el argumento es un literal de cadena de Nix, debe escapar las comillas.)
•
--argstr nombre valor
Esta opción es como --arg, solo que el valor no es una expresión Nix sino una cadena. Así que en lugar de --arg system \"i686-linux\" (las comillas exteriores son para que el shell funcione correctamente) puede decir --argstr system i686-linux.
•
--attr / -A rutaAttr
Selecciona un atributo de la expresión Nix de nivel superior que se está evaluando. (Solo nix-env, nix-instantiate, nix-build y nix-shell). La ruta de atributos rutaAttr es una secuencia de nombres de atributos separados por puntos. Por ejemplo, dada una expresión Nix de nivel superior e, la ruta de atributos xorg.xorgserver haría que se usara la expresión e.xorg.xorgserver. Vea nix-env --install para algunos ejemplos concretos.
Además de los nombres de atributos, también puede especificar índices de arrays. Por ejemplo, la ruta de atributos foo.3.bar selecciona el atributo bar del cuarto elemento del array en el atributo foo de la expresión de nivel superior.
•
--expr / -E
Interpreta los argumentos de la línea de comandos como una lista de expresiones Nix para analizar y evaluar, en lugar de como una lista de nombres de archivos de expresiones Nix. (Solo nix-instantiate, nix-build y nix-shell).
Para nix-shell, esta opción se usa comúnmente para proporcionarle un shell en el que pueda compilar los paquetes devueltos por la expresión. Si desea obtener un shell que contenga los paquetes *compilados* listos para usar, proporcione su expresión a la opción de conveniencia nix-shell --packages en su lugar.
•
-I / --include ruta
Agrega una entrada a la lista de rutas de búsqueda utilizadas para resolver rutas de búsqueda. Esta opción se puede proporcionar varias veces.
Las rutas agregadas a través de -I tienen prioridad sobre la configuración nix-path (vea nix.conf) y la variable de entorno NIX_PATH.
•
--option nombre valor
Establece la opción de configuración de Nix nombre en valor. Esto anula la configuración en el archivo de configuración de Nix (ver nix.conf5).
•
--repair
Repara rutas de la tienda (store) corruptas o faltantes, volviendo a descargarlas o reconstruirlas. Tenga en cuenta que esto es lento porque requiere calcular un hash criptográfico del contenido de cada ruta en el cierre de la compilación. También tenga en cuenta la advertencia en nix-store --repair-path.

Nota

Consulte man nix.conf para anular la configuración con flags de línea de comandos.

Variables de Entorno Comunes

La mayoría de los comandos de Nix interpretan las siguientes variables de entorno:

•
IN_NIX_SHELL
Indicador que señala si el entorno actual fue configurado por nix-shell. Puede tener los valores pure o impure.

Name

nix-env - managing user environments

SYNOPSIS

nix-env [option...] NIX_PATH

Description

nix-env is a tool for managing user environments. It allows users to install, upgrade, and remove packages from their Nix profiles. Nix profiles are essentially collections of symlinks in the Nix store that make packages available to the user.

A Nix profile is a collection of package derivations that are linked into the Nix store. Each user has a profile. User environments are managed through nix-env. A user environment is a collection of package derivations that are made available to the user.

The primary operations of nix-env are:

  • Installing packages: nix-env -iA nixpkgs.package_name installs the specified package from the channel.
  • Upgrading packages: nix-env -u upgrades all installed packages to the latest version available in the channel.
  • Uninstalling packages: nix-env -e package_name uninstalls the specified package.
  • Listing installed packages: nix-env -q lists all packages currently installed in the user's profile.
  • Switching between generations: nix-env --rollback reverts the user environment to the previous generation. nix-env --switch-generation N switches to generation N. nix-env --delete-generations N` deletes generations older than N.

Options

-i
--install attr-path ...

Install the specified package derivations. The attribute path syntax (e.g., nixpkgs.hello) is used to refer to packages. You can install multiple packages at once.

-e
--uninstall name ...

Uninstall the specified package names. You can uninstall multiple packages at once.

-u
--upgrade [attr-path ...]

Upgrade installed packages. If no arguments are given, all packages in the current environment are upgraded. If one or more package attribute paths are specified, only those packages and their dependencies will be upgraded.

-q
--query [name ...]

Query the profile. If no arguments are given, all installed packages are listed. If one or more package names are specified, only those packages are queried.

-P
--profile profile-dir

Manipulate the specified profile. The default is ~/.nix-profile.

--set attr-path ...
Install the specified package derivations, and uninstall all others. This effectively makes the specified packages the entire environment.
--set-installation attr-path ...
Same as --set, but this operation is atomic. The old environment is replaced by the new one in a single step.
-A
--install-attribute attr-path ...

Install the specified package derivations from the channel. This is a shortcut for -i when the package is defined in the channel's attribute set (e.g. nixpkgs.hello).

--rollback
Roll back to the previous generation of the user environment.
--switch-generation generation
Switch the user environment to the specified generation.
--delete-generations generation-spec-list
Delete the specified generations. The list can contain generation numbers (e.g., 1,3,5) or ranges (e.g., 1..3). Specifying old deletes all generations except the current one.
--reason reason
Attach a description to the current environment generation. This is useful for tracking changes made to the user environment.
--query-available [glob ...]
List all packages available in the Nix channels accessible from the current environment. If a glob pattern is provided, only packages matching the pattern are listed.
--unpack-program name
Unpack the specified program into the current environment. This is useful for debugging or analyzing Nix expressions.
--unpack-archive archive
Unpack the specified archive into the current environment. The archive must be a tarball containing Nix derivations.
--unpack-operations operations-file
Unpack a set of operations from the specified file into the current environment. This is typically used for debugging or reproducing specific builds.
--print-env
Print the environment variables needed to use the Nix profile. This is useful for setting up the environment in shell scripts.
--profile-name name
Use the specified profile name. The default is ~/.nix-profile.
--impure
Allow impure environment modifications. This is generally discouraged as it can lead to non-reproducible builds.
--pure
Ensure that all build processes are pure. This is the default behavior.
--eval-file file
Evaluate the Nix expression in the specified file and display the result. This is useful for inspecting Nix expressions without installing them.
--allow-downgrade
Allow downgrading packages even if a newer version is already installed.
--reinstall-all
Reinstall all packages in the current environment. This is useful for ensuring that all packages are in a consistent state.

Common Options

This command also accepts the common Nix options as well as the common environment variables.

ENVIRONMENT VARIABLES

•
NIX_PATH
A list of search paths separated by colons used to resolve lookup paths.
This environment variable overrides the value of the nix-path configuration setting.
It can be extended using the -I option.
Example
$ export NIX_PATH=`/home/eelco/Dev:nixos-config=/etc/nixos
If NIX_PATH is set to an empty string, resolving search paths will always fail.
Example
$ NIX_PATH= nix-instantiate --eval '<nixpkgs>'
error: file 'nixpkgs' was not found in the Nix search path (add it using $NIX_PATH or -I)
•
NIX_IGNORE_SYMLINK_STORE
Normally, the Nix store directory (typically /nix/store) is not allowed to contain any symlink components. This is to prevent "impure" builds. Builders sometimes "canonicalise" paths by resolving all symlink components. Thus, builds on different machines (with /nix/store resolving to different locations) could yield different results. This is generally not a problem, except when builds are deployed to machines where /nix/store resolves differently. If you are sure that you're not going to do that, you can set NIX_IGNORE_SYMLINK_STORE to 1.
Note that if you're symlinking the Nix store so that you can put it on another file system than the root file system, on Linux you're better off using bind mount points, e.g.,
$ mkdir /nix
$ mount -o bind /mnt/otherdisk/nix /nix
Consult the mount 8 manual page for details.
•
NIX_STORE_DIR
Overrides the location of the Nix store (default prefix/store).
•
NIX_DATA_DIR
Overrides the location of the Nix static data directory (default prefix/share).
•
NIX_LOG_DIR
Overrides the location of the Nix log directory (default prefix/var/log/nix).
•
NIX_STATE_DIR
Overrides the location of the Nix state directory (default prefix/var/nix).
•
NIX_CONF_DIR
Overrides the location of the system Nix configuration directory (default prefix/etc/nix).
•
NIX_CONFIG
Applies settings from Nix configuration from the environment. The content is treated as if it was read from a Nix configuration file. Settings are separated by the newline character.
•
NIX_USER_CONF_FILES
Overrides the location of the Nix user configuration files to load from.
The default are the locations according to the XDG Base Directory Specification. See the XDG Base Directories sub-section for details.
The variable is treated as a list separated by the : token.
•
TMPDIR
Use the specified directory to store temporary files. In particular, this includes temporary build directories; these can take up substantial amounts of disk space. The default is /tmp.
•
NIX_REMOTE
This variable should be set to daemon if you want to use the Nix daemon to execute Nix operations. This is necessary in multi-user Nix installations. If the Nix daemon's Unix socket is at some non-standard path, this variable should be set to unix://path/to/socket. Otherwise, it should be left unset.
•
NIX_SHOW_STATS
If set to 1, Nix will print some evaluation statistics, such as the number of values allocated.
•
NIX_COUNT_CALLS
If set to 1, Nix will print how often functions were called during Nix expression evaluation. This is useful for profiling your Nix expressions.
•
GC_INITIAL_HEAP_SIZE
If Nix has been configured to use the Boehm garbage collector, this variable sets the initial size of the heap in bytes. It defaults to 384 MiB. Setting it to a low value reduces memory consumption, but will increase runtime due to the overhead of garbage collection.

XDG Base Directories

Nix follows the XDG Base Directory Specification.

For backwards compatibility, Nix commands will follow the standard only when use-xdg-base-directories is enabled. New Nix commands (experimental) conform to the standard by default.

The following environment variables are used to determine locations of various state and configuration files:

  • [XDG_CONFIG_HOME]{#env-XDGCONFIGHOME} (default ~/.config)
  • [XDG_STATE_HOME]{#env-XDGSTATEHOME} (default ~/.local/state)
  • [XDG_CACHE_HOME]{#env-XDGCACHEHOME} (default ~/.cache)

Examples

Install the hello package:

$ nix-env -iA nixpkgs.hello

Upgrade all installed packages:

$ nix-env -u

List all installed packages:

$ nix-env -q

Uninstall the hello package:

$ nix-env -e hello

Roll back to the previous generation:

$ nix-env --rollback

Switch to generation 3:

$ nix-env --switch-generation 3

Delete generations older than 5:

$ nix-env --delete-generations 5

Set the environment to only contain htop and vim:

$ nix-env --set nixpkgs.htop nixpkgs.vim

Files

~/.nix-profile
The default user profile directory. This directory contains symlinks to the installed packages in the Nix store.
~/.nix-channels
A file containing the list of Nix channels the user is subscribed to.
~/.nix-defenv
A Nix expression that defines the user environment. This file is generated by nix-env and should generally not be edited directly.
