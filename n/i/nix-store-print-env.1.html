nix-store --print-env(1) Manual de comandos generales nix-store --print-env(1)

Nombre

nix-store --print-env - imprime el entorno de compilación de una derivación

Sintaxis

nix-store --print-env drvpath

Descripción

La operación --print-env imprime el entorno de una derivación en un formato que puede ser evaluado por un shell. Los argumentos de línea de comandos del compilador se colocan en la variable _args.

Opciones

Las siguientes opciones están permitidas para todas las operaciones de nix-store, pero pueden no tener efecto siempre.

•
--add-root ruta
Hace que el resultado de una realización (--realise y --force-realise) se registre como una raíz del recolector de basura. Se creará ruta como un enlace simbólico a la ruta de almacén resultante. Además, se creará un enlace simbólico con un nombre único a ruta en /nix/var/nix/gcroots/auto/. Por ejemplo,
$ nix-store --add-root /home/eelco/bla/result --realise ...
$ ls -l /nix/var/nix/gcroots/auto
lrwxrwxrwx    1 ... 2005-03-13 21:10 dn54lcypm8f8... -> /home/eelco/bla/result
$ ls -l /home/eelco/bla/result
lrwxrwxrwx    1 ... 2005-03-13 21:10 /home/eelco/bla/result -> /nix/store/1r11343n6qd4...-f-spot-0.0.10
Por lo tanto, cuando se elimina /home/eelco/bla/result, la raíz de GC en el directorio auto se convierte en un enlace simbólico roto y será ignorado por el recolector.
Advertencia
Tenga en cuenta que no es posible mover o renombrar raíces de GC, ya que el enlace simbólico en el directorio auto seguirá apuntando a la ubicación antigua.
Si hay varios resultados, se crearán varios enlaces simbólicos numerando secuencialmente los enlaces simbólicos más allá del primero (por ejemplo, foo, foo-2, foo-3, y así sucesivamente).

Opciones comunes

La mayoría de los comandos de Nix aceptan las siguientes opciones de línea de comandos:

•
--help
Imprime un resumen de la sintaxis del comando y sale.
•
--version
Imprime el número de versión de Nix en la salida estándar y sale.
•
--verbose / -v
Aumenta el nivel de verbosidad de los mensajes de diagnóstico impresos en la salida estándar de error. Para cada operación de Nix, la información impresa en la salida estándar es bien definida; cualquier información de diagnóstico se imprime en la salida estándar de error, nunca en la salida estándar.
Esta opción se puede especificar repetidamente. Actualmente, los siguientes niveles de verbosidad existen:
•
0 "Solo errores"
Solo imprime mensajes que expliquen por qué falló la invocación de Nix.
•
1 "Informativo"
Imprime mensajes *útiles* sobre lo que Nix está haciendo. Este es el valor predeterminado.
•
2 "Hablador"
Imprime más mensajes informativos.
•
3 "Charla"
Imprime aún más mensajes informativos.
•
4 "Depuración"
Imprime información de depuración.
•
5 "Vomitar"
Imprime grandes cantidades de información de depuración.
•
--quiet
Disminuye el nivel de verbosidad de los mensajes de diagnóstico impresos en la salida estándar de error. Esta es la opción inversa a -v / --verbose.
Esta opción se puede especificar repetidamente. Consulte la lista anterior de niveles de verbosidad.
•
--log-format formato
Esta opción se puede utilizar para cambiar la salida del formato del registro, siendo formato uno de:
•
raw
Este es el formato raw, tal como lo produce nix-build.
•
internal-json
Imprime los registros de forma estructurada.
Advertencia
Aunque el esquema en sí es relativamente estable, el formato de los mensajes de error (específicamente el campo msg) puede cambiar entre versiones.
•
bar
Solo muestra una barra de progreso durante las compilaciones.
•
bar-with-logs
Muestra los registros raw, con la barra de progreso en la parte inferior.
•
--no-build-output / -Q
Por defecto, la salida escrita por los compiladores a la salida estándar y a la salida estándar de error se muestra en la salida estándar de error del comando Nix. Esta opción suprime este comportamiento. Tenga en cuenta que la salida y el error estándar del compilador siempre se escriben en un archivo de registro en prefix/nix/var/log/nix.
•
--max-jobs / -j número
Establece el número máximo de trabajos de compilación que Nix realizará en paralelo al número especificado. Especifique auto para usar el número de CPUs en el sistema. El valor predeterminado es el especificado por la configuración max-jobs, que a su vez tiene un valor predeterminado de 1. Un valor más alto es útil en sistemas SMP o para explotar la latencia de E/S.
Establecerlo en 0 prohíbe la compilación en la máquina local, lo cual es útil cuando se desea que las compilaciones se realicen solo en compiladores remotos.
•
--cores
Establece el valor de la variable de entorno NIX_BUILD_CORES en la invocación de los compiladores. Los compiladores pueden usar esta variable a su discreción para controlar la cantidad máxima de paralelismo. Por ejemplo, en Nixpkgs, si el atributo de derivación enableParallelBuilding está configurado como true, el compilador pasa el flag -jN a GNU Make. Por defecto, utiliza el valor de la configuración cores, si está configurada, o 1 en caso contrario. El valor 0 significa que el compilador debe usar todos los núcleos disponibles.

OPTIONS

•
--max-jobs number
The maximum number of store paths that may be built in parallel. The default is the number of CPU cores in the system.
•
--max-silent-time
Sets the maximum number of seconds that a builder can go without producing any data on standard output or standard error. The default is specified by the max-silent-time configuration setting. 0 means no time-out.
•
--timeout
Sets the maximum number of seconds that a builder can run. The default is specified by the timeout configuration setting. 0 means no timeout.
•
--keep-going / -k
Keep going in case of failed builds, to the greatest extent possible. That is, if building an input of some derivation fails, Nix will still build the other inputs, but not the derivation itself. Without this option, Nix stops if any build fails (except for builds of substitutes), possibly killing builds in progress (in case of parallel or distributed builds).
•
--keep-failed / -K
Specifies that in case of a build failure, the temporary directory (usually in /tmp) in which the build takes place should not be deleted. The path of the build directory is printed as an informational message.
•
--fallback
Whenever Nix attempts to build a derivation for which substitutes are known for each output path, but realising the output paths through the substitutes fails, fall back on building the derivation.
The most common scenario in which this is useful is when we have registered substitutes in order to perform binary distribution from, say, a network repository. If the repository is down, the realisation of the derivation will fail. When this option is specified, Nix will build the derivation instead. Thus, installation from binaries falls back on installation from source. This option is not the default since it is generally not desirable for a transient failure in obtaining the substitutes to lead to a full build from source (with the related consumption of resources).
•
--readonly-mode
When this option is used, no attempt is made to open the Nix database. Most Nix operations do need database access, so those operations will fail.
•
--arg name value
This option is accepted by nix-env, nix-instantiate, nix-shell and nix-build. When evaluating Nix expressions, the expression evaluator will automatically try to call functions that it encounters. It can automatically call functions for which every argument has a default value (e.g., { argName ? defaultValue }: ...).
With --arg, you can also call functions that have arguments without a default value (or override a default value). That is, if the evaluator encounters a function with an argument named name, it will call it with value value.
For instance, the top-level default.nix in Nixpkgs is actually a function:
{ # The system (e.g., `i686-linux') for which to build the packages.
system ? builtins.currentSystem
...
}: ...
So if you call this Nix expression (e.g., when you do nix-env --install --attr pkgname), the function will be called automatically using the value builtins.currentSystem for the system argument. You can override this using --arg, e.g., nix-env --install --attr pkgname --arg system \"i686-freebsd\". (Note that since the argument is a Nix string literal, you have to escape the quotes.)
•
--argstr name value
This option is like --arg, only the value is not a Nix expression but a string. So instead of --arg system \"i686-linux\" (the outer quotes are to keep the shell happy) you can say --argstr system i686-linux.
•
--attr / -A attrPath
Select an attribute from the top-level Nix expression being evaluated. (nix-env, nix-instantiate, nix-build and nix-shell only.) The attribute path attrPath is a sequence of attribute names separated by dots. For instance, given a top-level Nix expression e, the attribute path xorg.xorgserver would cause the expression e.xorg.xorgserver to be used. See nix-env --install for some concrete examples.
In addition to attribute names, you can also specify array indices. For instance, the attribute path foo.3.bar selects the bar attribute of the fourth element of the array in the foo attribute of the top-level expression.
•
--expr / -E
Interpret the command line arguments as a list of Nix expressions to be parsed and evaluated, rather than as a list of file names of Nix expressions. (nix-instantiate, nix-build and nix-shell only.)
For nix-shell, this option is commonly used to give you a shell in which you can build the packages returned by the expression. If you want to get a shell which contain the built packages ready for use, give your expression to the nix-shell --packages convenience flag instead.
•
-I / --include path
Add an entry to the list of search paths used to resolve lookup paths. This option may be given multiple times.
Paths added through -I take precedence over the nix-path configuration setting and the NIX_PATH environment variable.
•
--option name value
Set the Nix configuration option name to value. This overrides settings in the Nix configuration file (see nix.conf5).
•
--repair
Fix corrupted or missing store paths by redownloading or rebuilding them. Note that this is slow because it requires computing a cryptographic hash of the contents of every path in the closure of the build. Also note the warning under nix-store --repair-path.

Note

See man nix.conf for overriding configuration settings with command line flags.

Common Environment Variables

Most Nix commands interpret the following environment variables:

•
IN_NIX_SHELL
Indicator that tells if the current environment was set up by nix-shell. It can have the values pure or impure.
•
NIX_PATH
A colon-separated list of search path entries used to resolve lookup paths.
This environment variable overrides the value of the nix-path configuration setting.
It can be extended using the -I option.
Example
$ export NIX_PATH=`/home/eelco/Dev:nixos-config=/etc/nixos
If NIX_PATH is set to an empty string, resolving search paths will always fail.
Example
$ NIX_PATH= nix-instantiate --eval '<nixpkgs>'
error: file 'nixpkgs' was not found in the Nix search path (add it using $NIX_PATH or -I)

NIX_IGNORE_SYMLINK_STORE

NAME

nix-store -- Manipulate the Nix data store

SYNOPSIS

nix-store [option...] subcommand [argument...]

Manipulate the Nix data store

DESCRIPTION

The Nix data store is a collection of files in the Nix store directory (typically /nix/store) that Nix uses to store derivations, build products, and other data.

This manual page documents the various subcommands available to interact with the Nix store.

Store Paths

A Nix store path is a path in the Nix store directory. It is identified by a path like /nix/store/<hash>-<name>, where <hash> is a cryptographic hash of the derivation that produced the path, and <name> is a human-readable name for the derivation (e.g., /nix/store/plpj7qrwcz94z2psh6fchsi7s8yihc7k-firefox-12.0).

Symlink Components in the Nix Store

Normalmente, el directorio de la tienda Nix (típicamente /nix/store) no tiene permitido contener ningún componente de enlace simbólico. Esto es para prevenir compilaciones "impuras". Los compiladores a veces "canonizan" las rutas resolviendo todos los componentes de enlace simbólico. Por lo tanto, las compilaciones en diferentes máquinas (con /nix/store resolviendo a ubicaciones diferentes) podrían producir resultados diferentes. Esto generalmente no es un problema, excepto cuando las compilaciones se despliegan en máquinas donde /nix/store se resuelve de manera diferente. Si está seguro de que no va a hacer eso, puede establecer NIX_IGNORE_SYMLINK_STORE a 1.
Tenga en cuenta que si está enlazando simbólicamente la tienda Nix para poder ponerla en un sistema de archivos diferente al del sistema de archivos raíz, en Linux es mejor usar puntos de montaje bind, por ejemplo:
$ mkdir /nix
$ mount -o bind /mnt/otherdisk/nix /nix
Consulte la página del manual mount 8 para obtener detalles.
•
NIX_STORE_DIR
Sobrescribe la ubicación de la tienda Nix (predeterminado prefix/store).
•
NIX_DATA_DIR
Sobrescribe la ubicación del directorio de datos estáticos de Nix (predeterminado prefix/share).
•
NIX_LOG_DIR
Sobrescribe la ubicación del directorio de registros de Nix (predeterminado prefix/var/log/nix).
•
NIX_STATE_DIR
Sobrescribe la ubicación del directorio de estado de Nix (predeterminado prefix/var/nix).
•
NIX_CONF_DIR
Sobrescribe la ubicación del directorio de configuración del sistema Nix (predeterminado prefix/etc/nix).
•
NIX_CONFIG
Aplica configuraciones de Nix desde el entorno. El contenido se trata como si se hubiera leído de un archivo de configuración de Nix. Las configuraciones están separadas por el carácter de nueva línea.
•
NIX_USER_CONF_FILES
Sobrescribe la ubicación de los archivos de configuración de usuario de Nix para cargar.
Los valores predeterminados son las ubicaciones según la Especificación de Directorios Base XDG. Consulte la subsección Directorios Base XDG para obtener detalles.
La variable se trata como una lista separada por el token :.
•
TMPDIR
Utiliza el directorio especificado para almacenar archivos temporales. En particular, esto incluye directorios de compilación temporales; estos pueden ocupar cantidades sustanciales de espacio en disco. El valor predeterminado es /tmp.
•
NIX_REMOTE
Esta variable debe establecerse en daemon si desea utilizar el demonio Nix para ejecutar operaciones de Nix. Esto es necesario en instalaciones Nix multiusuario. Si el socket Unix del demonio Nix se encuentra en una ruta no estándar, esta variable debe establecerse en unix://path/to/socket. De lo contrario, debe dejarse sin establecer.
•
NIX_SHOW_STATS
Si se establece en 1, Nix imprimirá algunas estadísticas de evaluación, como el número de valores asignados.
•
NIX_COUNT_CALLS
Si se establece en 1, Nix imprimirá cuántas veces se llamaron las funciones durante la evaluación de expresiones Nix. Esto es útil para perfilar sus expresiones Nix.
•
GC_INITIAL_HEAP_SIZE
Si Nix se ha configurado para utilizar el recolector de basura Boehm, esta variable establece el tamaño inicial del montón en bytes. Por defecto es 384 MiB. Establecerla en un valor bajo reduce el consumo de memoria, pero aumentará el tiempo de ejecución debido a la sobrecarga de la recolección de basura.

XDG Directorios Base

Nix sigue la Especificación de Directorios Base XDG.

Para compatibilidad con versiones anteriores, los comandos Nix seguirán el estándar solo cuando use-xdg-base-directories esté habilitado. Los nuevos comandos Nix (experimentales) cumplen con el estándar por defecto.

Las siguientes variables de entorno se utilizan para determinar las ubicaciones de varios archivos de estado y configuración:

  • [XDG_CONFIG_HOME]{#env-XDGCONFIGHOME} (predeterminado ~/.config)
  • [XDG_STATE_HOME]{#env-XDGSTATEHOME} (predeterminado ~/.local/state)
  • [XDG_CACHE_HOME]{#env-XDGCACHEHOME} (predeterminado ~/.cache)

Ejemplo

$ nix-store --print-env $(nix-instantiate '<nixpkgs>' -A firefox)
…
export src; src='/nix/store/plpj7qrwcz94z2psh6fchsi7s8yihc7k-firefox-12.0.source.tar.bz2'
export stdenv; stdenv='/nix/store/7c8asx3yfrg5dg1gzhzyq2236zfgibnn-stdenv'
export system; system='x86_64-linux'
export _args; _args='-e /nix/store/9krlzvny65gdc8s7kpb6lkx8cd02c25c-default-builder.sh'
