nix-store --verify(1) Manual de Comandos Generales nix-store --verify(1)

Nombre

nix-store --verify - comprueba la consistencia de la base de datos Nix

Sinopsis

nix-store --verify [--check-contents] [--repair]

Descripción

La operación --verify verifica la consistencia interna de la base de datos Nix y la consistencia entre la base de datos Nix y el almacén Nix. Cualquier inconsistencia encontrada se repara automáticamente. Las inconsistencias suelen ser el resultado de que el almacén o la base de datos Nix sean modificados por herramientas que no son Nix, o de errores en el propio Nix.

Esta operación tiene las siguientes opciones:

•
--check-contents
Comprueba que el contenido de cada ruta de almacén válida no ha sido alterado calculando un hash SHA-256 del contenido y comparándolo con el hash almacenado en la base de datos Nix en tiempo de compilación. Se imprimen las rutas que han sido modificadas. Para almacenes grandes, --check-contents es obviamente bastante lento.
•
--repair
Si falta alguna ruta válida en el almacén, o (si se proporciona --check-contents) el contenido de una ruta válida ha sido modificado, intenta reparar la ruta volviéndola a descargar. Consulte nix-store --repair-path para obtener más detalles.

Opciones

Se permiten las siguientes opciones para todas las operaciones nix-store, pero puede que no siempre tengan efecto.

•
--add-root ruta
Hace que el resultado de una realización (--realise y --force-realise) se registre como una raíz del recolector de basura. ruta se creará como un enlace simbólico a la ruta de almacén resultante. Además, se creará un enlace simbólico con un nombre único a ruta en /nix/var/nix/gcroots/auto/. Por ejemplo,
$ nix-store --add-root /home/eelco/bla/result --realise ...
$ ls -l /nix/var/nix/gcroots/auto
lrwxrwxrwx    1 ... 2005-03-13 21:10 dn54lcypm8f8... -> /home/eelco/bla/result
$ ls -l /home/eelco/bla/result
lrwxrwxrwx    1 ... 2005-03-13 21:10 /home/eelco/bla/result -> /nix/store/1r11343n6qd4...-f-spot-0.0.10
Por lo tanto, cuando se elimina /home/eelco/bla/result, la raíz de GC en el directorio auto se convierte en un enlace simbólico colgante y será ignorado por el colector.
Advertencia
Tenga en cuenta que no es posible mover o renombrar raíces de GC, ya que el enlace simbólico en el directorio auto seguirá apuntando a la ubicación anterior.
Si hay múltiples resultados, se crearán varios enlaces simbólicos numerando secuencialmente los enlaces simbólicos más allá del primero (por ejemplo, foo, foo-2, foo-3, y así sucesivamente).

Opciones Comunes

La mayoría de los comandos Nix aceptan las siguientes opciones de línea de comandos:

•
--help
Imprime un resumen de la sintaxis del comando y sale.
•
--version
Imprime el número de versión de Nix en la salida estándar y sale.
•
--verbose / -v
Aumenta el nivel de verbosidad de los mensajes de diagnóstico impresos en la salida de error estándar. Para cada operación de Nix, la información impresa en la salida estándar está bien definida; cualquier información de diagnóstico se imprime en la salida de error estándar, nunca en la salida estándar.
Esta opción se puede especificar repetidamente. Actualmente, existen los siguientes niveles de verbosidad:
•
0 "Sólo errores"
Solo imprime mensajes que explican por qué falló la invocación de Nix.
•
1 "Informativo"
Imprime mensajes *útiles* sobre lo que Nix está haciendo. Este es el valor predeterminado.
•
2 "Hablador"
Imprime más mensajes informativos.
•
3 "Charla"
Imprime aún más mensajes informativos.
•
4 "Depuración"
Imprime información de depuración.
•
5 "Vómito"
Imprime grandes cantidades de información de depuración.
•
--quiet
Disminuye el nivel de verbosidad de los mensajes de diagnóstico impresos en la salida de error estándar. Esta es la opción inversa a -v / --verbose.
Esta opción se puede especificar repetidamente. Consulte la lista anterior de niveles de verbosidad.
•
--log-format formato
Esta opción se puede utilizar para cambiar la salida del formato del registro, siendo formato uno de los siguientes:
•
raw
Este es el formato sin procesar, tal como lo genera nix-build.
•
internal-json
Imprime los registros de forma estructurada.
Advertencia
Aunque el esquema en sí es relativamente estable, el formato de los mensajes de error (específicamente el campo msg) puede cambiar entre versiones.
•
bar
Solo muestra una barra de progreso durante las compilaciones.
•
bar-with-logs
Muestra los registros sin procesar, con la barra de progreso en la parte inferior.
•
--no-build-output / -Q
Por defecto, la salida escrita por los constructores en la salida estándar y el error estándar se refleja en el error estándar del comando Nix. Esta opción suprime este comportamiento. Tenga en cuenta que la salida estándar y el error del constructor siempre se escriben en un archivo de registro en prefix/nix/var/log/nix.
•
--max-jobs / -j número
Establece el número máximo de trabajos de compilación que Nix realizará en paralelo al número especificado. Especifique auto para utilizar el número de CPUs del sistema. El valor predeterminado lo especifica la configuración max-jobs, que a su vez, por defecto, es

NIX_BUILD_DEBUG

If set to 1, enables debug output from the builder. Useful for debugging build failures.

NIX_BUILD_KEEP_TMP

If set to 1, prevents the removal of temporary build directories when a build fails. Useful for inspecting the contents of failed build environments.

NIX_BUILD_MAX_FAILURES

Specifies the maximum number of build failures Nix will tolerate before stopping. A higher value is useful on SMP systems or to exploit I/O latency.
Setting it to 0 disallows building on the local machine, which is useful when you want builds to happen only on remote builders.

NIX_BUILD_CORES

Sets the value of the NIX_BUILD_CORES environment variable in the invocation of builders. Builders can use this variable at their discretion to control the maximum amount of parallelism. For instance, in Nixpkgs, if the derivation attribute enableParallelBuilding is set to true, the builder passes the -jN flag to GNU Make. It defaults to the value of the cores configuration setting, if set, or 1 otherwise. The value 0 means that the builder should use all available CPU cores in the system.

NIX_MAX_SILENT_TIME

Sets the maximum number of seconds that a builder can go without producing any data on standard output or standard error. The default is specified by the max-silent-time configuration setting. 0 means no time-out.

NIX_TIMEOUT

Sets the maximum number of seconds that a builder can run. The default is specified by the timeout configuration setting. 0 means no timeout.

NIX_KEEP_GOING

Keep going in case of failed builds, to the greatest extent possible. That is, if building an input of some derivation fails, Nix will still build the other inputs, but not the derivation itself. Without this option, Nix stops if any build fails (except for builds of substitutes), possibly killing builds in progress (in case of parallel or distributed builds).

NIX_KEEP_FAILED

Specifies that in case of a build failure, the temporary directory (usually in /tmp) in which the build takes place should not be deleted. The path of the build directory is printed as an informational message.

NIX_FALLBACK

Whenever Nix attempts to build a derivation for which substitutes are known for each output path, but realising the output paths through the substitutes fails, fall back on building the derivation.
The most common scenario in which this is useful is when we have registered substitutes in order to perform binary distribution from, say, a network repository. If the repository is down, the realisation of the derivation will fail. When this option is specified, Nix will build the derivation instead. Thus, installation from binaries falls back on installation from source. This option is not the default since it is generally not desirable for a transient failure in obtaining the substitutes to lead to a full build from source (with the related consumption of resources).

NIX_READONLY_MODE

When this option is used, no attempt is made to open the Nix database. Most Nix operations do need database access, so those operations will fail.

NIX_ARG

This option is accepted by nix-env, nix-instantiate, nix-shell and nix-build. When evaluating Nix expressions, the expression evaluator will automatically try to call functions that it encounters. It can automatically call functions for which every argument has a default value (e.g., { argName ? defaultValue }: ...).
With --arg, you can also call functions that have arguments without a default value (or override a default value). That is, if the evaluator encounters a function with an argument named name, it will call it with value value.
For instance, the top-level default.nix in Nixpkgs is actually a function:
{ # The system (e.g., `i686-linux') for which to build the packages.
system ? builtins.currentSystem
...
}: ...
So if you call this Nix expression (e.g., when you do nix-env --install --attr pkgname), the function will be called automatically using the value builtins.currentSystem for the system argument. You can override this using --arg, e.g., nix-env --install --attr pkgname --arg system \"i686-freebsd\". (Note that since the argument is a Nix string literal, you have to escape the quotes.)

NIX_ARGSTR

This option is like --arg, only the value is not a Nix expression but a string. So instead of --arg system \"i686-linux\" (the outer quotes are to keep the shell happy) you can say --argstr system i686-linux.

NIX_ATTR

Select an attribute from the top-level Nix expression being evaluated. (nix-env, nix-instantiate, nix-build and nix-shell only.) The attribute path attrPath is a sequence of attribute names separated by dots. For instance, given a top-level Nix expression e, the attribute path xorg.xorgserver would cause the expression e.xorg.xorgserver to be used. See nix-env --install for some concrete examples.
In addition to attribute names, you can also specify array indices. For instance, the attribute path foo.3.bar selects the bar attribute of the fourth element of the array in the foo attribute of the top-level expression.

NIX_EXPR

Interpret the command line arguments as a list of Nix expressions to be parsed and evaluated, rather than as a list of file names of Nix expressions. (nix-instantiate, nix-build and nix-shell only.)
For nix-shell, this option is commonly used to give you a shell in which you can build the packages returned by the expression. If you want to get a shell which contain the built packages ready for use, give your expression to the nix-shell --packages convenience flag instead.

NIX_INCLUDE

Add an entry to the list of search paths used to resolve lookup paths. This option may be given multiple times.
Paths added through -I take precedence over the nix-path configuration setting and the NIX_PATH environment variable.

NIX_OPTION

Set the Nix configuration option name to value. This overrides settings in the Nix configuration file (see nix.conf5).

NIX_REPAIR

Fix corrupted or missing store paths by redownloading or rebuilding them. Note that this is slow because it requires computing a cryptographic hash of the contents of every path in the closure of the build. Also note the warning under nix-store --repair-path.

Note

See man nix.conf for overriding configuration settings with command line flags.

Common Environment Variables

Most Nix commands interpret the following environment variables:

•
IN_NIX_SHELL
Indicator that tells if the current environment was set up by nix-shell. It can have the values pure or impure.
•
NIX_PATH
A colon-separated list of search path entries used to resolve lookup paths.
nix(1)
Esta variable de entorno anula el valor de la configuración de nix-path.
Puede extenderse usando la opción -I.
Ejemplo
$ export NIX_PATH=`/home/eelco/Dev:nixos-config=/etc/nixos
Si NIX_PATH se establece a una cadena vacía, la resolución de las rutas de búsqueda siempre fallará.
Ejemplo
$ NIX_PATH= nix-instantiate --eval '<nixpkgs>'
error: file 'nixpkgs' was not found in the Nix search path (add it using $NIX_PATH or -I)
•
NIX_IGNORE_SYMLINK_STORE
Normalmente, el directorio del almacén de Nix (típicamente /nix/store) no tiene permitido contener ningún componente de enlace simbólico. Esto es para prevenir construcciones "impuras". Los constructores a veces "canonicen" las rutas resolviendo todos los componentes de enlace simbólico. Por lo tanto, las construcciones en máquinas diferentes (con /nix/store resolviendo a ubicaciones diferentes) podrían producir resultados diferentes. Esto generalmente no es un problema, excepto cuando las construcciones se despliegan en máquinas donde /nix/store resuelve de manera diferente. Si estás seguro de que no vas a hacer eso, puedes establecer NIX_IGNORE_SYMLINK_STORE a 1.
Ten en cuenta que si estás enlazando simbólicamente el almacén de Nix para poder ponerlo en un sistema de archivos diferente al del sistema de archivos raíz, en Linux es mejor usar puntos de montaje bind, por ejemplo:
$ mkdir /nix
$ mount -o bind /mnt/otherdisk/nix /nix
Consulta la página del manual de mount 8 para obtener detalles.
•
NIX_STORE_DIR
Anula la ubicación del almacén de Nix (por defecto prefix/store).
•
NIX_DATA_DIR
Anula la ubicación del directorio de datos estáticos de Nix (por defecto prefix/share).
•
NIX_LOG_DIR
Anula la ubicación del directorio de logs de Nix (por defecto prefix/var/log/nix).
•
NIX_STATE_DIR
Anula la ubicación del directorio de estado de Nix (por defecto prefix/var/nix).
•
NIX_CONF_DIR
Anula la ubicación del directorio de configuración del sistema Nix (por defecto prefix/etc/nix).
•
NIX_CONFIG
Aplica configuraciones de Nix desde el entorno. El contenido se trata como si se hubiera leído de un archivo de configuración de Nix. Las configuraciones se separan por el carácter de nueva línea.
•
NIX_USER_CONF_FILES
Anula la ubicación de los archivos de configuración de usuario de Nix de los que cargar.
Los valores predeterminados son las ubicaciones según la Especificación de Directorios Base XDG. Consulta la subsección Directorios Base XDG para obtener más detalles.
La variable se trata como una lista separada por el token :.
•
TMPDIR
Utiliza el directorio especificado para almacenar archivos temporales. En particular, esto incluye directorios temporales de construcción; estos pueden ocupar cantidades sustanciales de espacio en disco. El valor predeterminado es /tmp.
•
NIX_REMOTE
Esta variable debe establecerse a daemon si deseas utilizar el demonio Nix para ejecutar operaciones de Nix. Esto es necesario en instalaciones Nix multiusuario. Si el socket Unix del demonio Nix se encuentra en una ruta no estándar, esta variable debe establecerse a unix://path/to/socket. De lo contrario, debe dejarse sin establecer.
•
NIX_SHOW_STATS
Si se establece a 1, Nix imprimirá algunas estadísticas de evaluación, como el número de valores asignados.
•
NIX_COUNT_CALLS
Si se establece a 1, Nix imprimirá cuántas veces se llamaron las funciones durante la evaluación de expresiones Nix. Esto es útil para perfilar tus expresiones Nix.
•
GC_INITIAL_HEAP_SIZE
Si Nix ha sido configurado para usar el recolector de basura de Boehm, esta variable establece el tamaño inicial del montón en bytes. Por defecto es 384 MiB. Establecerlo a un valor bajo reduce el consumo de memoria, pero aumentará el tiempo de ejecución debido a la sobrecarga de la recolección de basura.

Directorios Base XDG

Nix sigue la Especificación de Directorios Base XDG.

Por compatibilidad hacia atrás, los comandos de Nix seguirán el estándar solo cuando use-xdg-base-directories esté habilitado. Los comandos Nix nuevos (experimentales) cumplen con el estándar por defecto.

Las siguientes variables de entorno se utilizan para determinar las ubicaciones de varios archivos de estado y configuración:

  • [XDG_CONFIG_HOME]{#env-XDGCONFIGHOME} (por defecto ~/.config)
  • [XDG_STATE_HOME]{#env-XDGSTATEHOME} (por defecto ~/.local/state)
  • [XDG_CACHE_HOME]{#env-XDGCACHEHOME} (por defecto ~/.cache)
