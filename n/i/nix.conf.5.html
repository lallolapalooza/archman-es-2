nix.conf(5) Manual de formatos de archivo nix.conf(5)

Nombre

nix.conf - Archivo de configuración de Nix

Descripción

Nix admite una variedad de configuraciones, que se leen desde archivos de configuración o se toman como argumentos de línea de comandos.

Archivo de configuración

Por defecto, Nix lee las configuraciones de los siguientes lugares, en este orden:

1.
El archivo de configuración a nivel de sistema sysconfdir/nix/nix.conf (es decir, /etc/nix/nix.conf en la mayoría de los sistemas), o $NIX_CONF_DIR/nix.conf si NIX_CONF_DIR está configurado.
Los valores cargados en este archivo no se reenvían al demonio de Nix. El cliente asume que el demonio ya los ha cargado.
2.
Si NIX_USER_CONF_FILES está configurado, entonces cada ruta separada por : se cargará en orden inverso.
De lo contrario, buscará archivos nix/nix.conf en XDG_CONFIG_DIRS y XDG_CONFIG_HOME. Si no están configurados, XDG_CONFIG_DIRS tendrá como valor predeterminado /etc/xdg, y XDG_CONFIG_HOME tendrá como valor predeterminado $HOME/.config según la Especificación de Directorios Base de XDG.
3.
Si NIX_CONFIG está configurado, su contenido se tratará como el contenido de un archivo de configuración.

Formato de archivo

Los archivos de configuración consisten en pares de nombre = valor, uno por línea. Los comentarios comienzan con un carácter #.

Ejemplo:

keep-outputs = true       # Bueno para desarrolladores
keep-derivations = true   # Ídem

Se pueden incluir otros archivos con una línea como include <ruta>, donde <ruta> se interpreta en relación con el archivo de configuración actual. Un archivo faltante es un error a menos que se use !include en su lugar.

Una configuración generalmente anula cualquier valor anterior. Sin embargo, para configuraciones que toman una lista de elementos, puede prefijar el nombre de la configuración con extra- para *agregar* al valor anterior.

Por ejemplo:

substituters = a b
extra-substituters = c d

define la configuración substituters como a b c d.

Los nombres de opciones desconocidos no son un error y simplemente se ignoran con una advertencia.

Argumentos de línea de comandos

Las opciones de configuración se pueden establecer en la línea de comandos, anulando los valores establecidos en el archivo de configuración:

•
Cada configuración tiene un argumento de línea de comandos correspondiente (por ejemplo, --max-jobs 16). Las configuraciones booleanas no necesitan argumento y se pueden deshabilitar explícitamente con el prefijo no- (por ejemplo, --keep-failed y --no-keep-failed).
Los nombres de opciones desconocidos son argumentos inválidos (a menos que ya exista un argumento con ese nombre) y se rechazan con un error.
•
El argumento --option <nombre> <valor> se interpreta exactamente como un <nombre> = <valor> en un archivo de configuración.
Los nombres de opciones desconocidos se ignoran con una advertencia.

El prefijo extra- se admite para configuraciones que toman una lista de elementos (por ejemplo, --extra-trusted users alice o --option extra-trusted-users alice).

Configuraciones de enteros

Las configuraciones que tienen un tipo de entero admiten los sufijos K, M, G y T. Estos hacen que el valor especificado se multiplique por 2^10, 2^20, 2^30 y 2^40, respectivamente. Por ejemplo, --min-free 1M es equivalente a --min-free 1048576.

abort-on-warn
Si se establece en verdadero, builtins.warn generará un error al registrar una advertencia.
Esto le proporcionará un rastreo de pila que conduce a la ubicación de la advertencia.
Esto es útil para encontrar información sobre advertencias en código Nix de terceros cuando no se puede iniciar el depurador interactivo, como cuando Nix se llama desde un script no interactivo. Ver debugger-on-warn.
Actualmente, solo se puede producir un rastreo de pila cuando el depurador está habilitado, o cuando la evaluación se interrumpe.
Esta opción se puede habilitar configurando NIX_ABORT_ON_WARN=1 en el entorno.
Predeterminado: false

access-tokens
Tokens de acceso utilizados para acceder a ubicaciones protegidas de GitHub, GitLab u otras que requieran autenticación basada en tokens.
Los tokens de acceso se especifican como una cadena compuesta por host=token separados por espacios. El token específico utilizado se selecciona haciendo coincidir la porción host con la especificación del "host" de la entrada. El uso real del valor token está determinado por el tipo de recurso al que se accede:
  • Github: el valor del token es la cadena OAUTH-TOKEN obtenida como Token de Acceso Personal del servidor de Github (ver https://docs.github.com/en/developers/apps/building-oauth-apps/authorizing-oauth-apps).
  • Gitlab: el valor del token es el token OAuth2 o el Token de Acceso Personal (estos son diferentes tipos de tokens para gitlab, ver https://docs.gitlab.com/12.10/ee/api/README.html#authentication). El valor del token debe ser tipo:cadena_token donde tipo es OAuth2 o PAT para indicar qué tipo de token se está especificando.
Ejemplo ~/.config/nix/nix.conf:
access-tokens = github.com=23ac...b289 gitlab.mycompany.com=PAT:A123Bp_Cd..EfG gitlab.com=O
Auth2:1jklw3jk
Ejemplo en ~/code/flake.nix:
input.foo = {
type = "gitlab";
host = "gitlab.mycompany.com";
owner = "mycompany";
repo = "pro";
};
Este ejemplo especifica tres tokens, uno para acceder a github.com, uno para gitlab.mycompany.com y otro para gitlab.com.
La entrada input.foo utiliza el "fetcher" de tipo "gitlab", que puede requerir la especificación del tipo de token junto con el valor del token.
Por defecto: vacío

build-users-group
Esta opción especifica el grupo de Unix que contiene las cuentas de usuario de compilación de Nix. En instalaciones Nix multiusuario, las compilaciones no deben ser realizadas por la cuenta de Nix, ya que esto permitiría a los usuarios modificar arbitrariamente el almacén y la base de datos de Nix proporcionando constructores especialmente diseñados; y no deben ser realizadas por el usuario que llama, ya que esto le permitiría influir en el resultado de la compilación.
Por lo tanto, si esta opción no está vacía y especifica un grupo válido, las compilaciones se realizarán bajo las cuentas de usuario que son miembros del grupo especificado aquí (tal como se enumeran en /etc/group). ¡Esas cuentas de usuario no deben usarse para ningún otro propósito!
Nix nunca ejecutará dos compilaciones bajo la misma cuenta de usuario al mismo tiempo. Esto es para prevenir una obvia brecha de seguridad: un usuario malicioso que escribe una expresión Nix que modifica el resultado de la compilación de una expresión Nix legítima que está siendo compilada por otro usuario. Por lo tanto, es bueno tener tantas cuentas de usuario de compilación Nix como pueda permitirse. (Recuerde: los uid son baratos.)
Los usuarios de compilación deben tener permiso para crear archivos en el almacén Nix, pero no para eliminarlos. Por lo tanto, /nix/store debe ser propiedad de la cuenta Nix, su grupo debe ser el grupo especificado aquí, y su modo debe ser 1775.
Si el grupo de usuarios de compilación está vacío, las compilaciones se realizarán bajo el uid del proceso Nix (es decir, el uid del llamador si NIX_REMOTE está vacío, el uid bajo el cual se ejecuta el demonio Nix si NIX_REMOTE es daemon). Obviamente, esto no debe usarse con un demonio Nix accesible para clientes no confiables.
Por defecto es nixbld cuando se ejecuta como root, vacío en caso contrario.
Por defecto: específico de la máquina

builders
Una lista de máquinas de compilación separada por punto y coma o nueva línea.
Además de las formas habituales de establecer opciones de configuración, el valor se puede leer de un archivo prefijando su ruta absoluta con @.
Ejemplo
Esta es la configuración por defecto:
builders = @/etc/nix/machines
Cada especificación de máquina consta de los siguientes elementos, separados por espacios. Solo el primer elemento es obligatorio. Para dejar un campo en su valor predeterminado, establécelo en -.
1.
La URI del almacén remoto en el formato ssh://[usuario@]hostname.
Ejemplo
ssh://nix@mac
Para compatibilidad con versiones anteriores, ssh:// se puede omitir. El nombre de host puede ser un alias definido en ~/.ssh/config.
2.
Una lista separada por comas de tipos de sistema Nix. Si se omite, esto tendrá como valor predeterminado el tipo de plataforma local.
Ejemplo
aarch64-darwin
Es posible que una máquina admita varios tipos de plataforma.
Ejemplo
i686-linux,x86_64-linux
3.
El archivo de identidad SSH que se utilizará para iniciar sesión en la máquina remota. Si se omite, SSH utilizará sus identidades habituales.
Ejemplo
/home/user/.ssh/id_mac
4.
El número máximo de compilaciones que Nix ejecutará en paralelo en la máquina. Típicamente, esto debería ser igual al número de núcleos de CPU.
5.
El factor de "velocidad", que indica la velocidad relativa de la máquina como un entero positivo. Si hay varias máquinas del tipo correcto, Nix preferirá la más rápida, teniendo en cuenta la carga.
6.
Una lista separada por comas de características del sistema compatibles.
Una máquina solo se utilizará para compilar una derivación si todas las características del atributo requiredSystemFeatures de la derivación son compatibles con esa máquina.
7.
Una lista separada por comas de características del sistema requeridas.
Una máquina solo se utilizará para compilar una derivación si todas las características requeridas de la máquina aparecen en el atributo requiredSystemFeatures de la derivación.
8.
La clave de host pública (codificada en base64) de la máquina remota. Si se omite, SSH utilizará su archivo known_hosts habitual.
El valor para este campo se puede obtener a través de base64 -w0.
Ejemplo
Varias máquinas de compilación especificadas en la línea de comandos:
--builders 'ssh://mac x86_64-darwin ; ssh://beastie x86_64-freebsd'
Ejemplo
Esto especifica varias máquinas que pueden realizar compilaciones i686-linux:
nix@scratchy.labs.cs.uu.nl i686-linux /home/nix/.ssh/id_scratchy 8 1 kvm
nix@itchy.labs.cs.uu.nl    i686-linux /home/nix/.ssh/id_scratchy 8 2
nix@poochie.labs.cs.uu.nl  i686-linux /home/nix/.ssh/id_scratchy 1 2 kvm benchmark
Sin embargo, poochie solo compilará derivaciones que tengan el atributo
requiredSystemFeatures = [ "benchmark" ];
o
requiredSystemFeatures = [ "benchmark" "kvm" ];
itchy no puede realizar compilaciones que requieran kvm, pero scratchy sí admite dichas compilaciones. Para compilaciones regulares, se preferirá itchy sobre scratchy porque tiene un factor de velocidad más alto.
Para que Nix utilice sustitutos, el usuario que llama debe estar en la lista de trusted-users.
Nota
Una máquina de compilación debe ser accesible a través de SSH y tener Nix instalado. nix debe estar disponible en $PATH para el usuario que se conecta a través de SSH.
Advertencia
Si está compilando a través del demonio Nix (por defecto), la cuenta de usuario del demonio Nix en la máquina local (es decir, root) requiere acceso a una cuenta de usuario en la máquina remota (no necesariamente root).
Si no puede o no desea configurar root para que acceda a la máquina remota, establezca store a cualquier almacén local , por ejemplo, pasando --store /tmp al comando en la máquina local.
Para compilar solo en máquinas remotas y deshabilitar las compilaciones locales, establezca max-jobs a 0.
Si desea que las máquinas remotas utilicen sustitutos, establezca builders-use-substituters a true.
Por defecto: específico de la máquina

builders-use-substitutes
Si se establece en true, Nix instruirá a las máquinas de compilación remotas para que utilicen sus propios sustitutos si están disponibles.
Significa que los hosts de compilación remotos obtendrán tantas dependencias como sea posible de sus propios sustitutos (por ejemplo, de cache.nixos.org) en lugar de esperar a que la máquina local las cargue todas. Esto puede reducir drásticamente los tiempos de compilación si la conexión de red entre la máquina local y el host de compilación remoto es lenta.

diff-hook
Ruta absoluta a un ejecutable capaz de comparar resultados de compilación. El hook se ejecuta si run-diff-hook es true, y se sabe que la salida de una compilación no es la misma. Este programa no se ejecuta para determinar si dos resultados son iguales.
El hook de comparación es ejecutado por el mismo usuario y grupo que ejecutaron la compilación. Sin embargo, el hook de comparación no tiene acceso de escritura a la ruta de la tienda recién compilada.
El programa hook de comparación recibe tres parámetros:
1.
Una ruta a los resultados de la compilación anterior
2.
Una ruta a los resultados de la compilación actual
3.
La ruta a la derivación de la compilación
4.
La ruta al directorio temporal de la compilación. Este directorio existirá solo si la compilación se ejecutó con --keep-failed.
La salida estándar de error y estándar del hook de comparación no se mostrará al usuario. En su lugar, se imprimirá en el registro del daemon de Nix.
Al usar el daemon de Nix, diff-hook debe establecerse en el archivo de configuración nix.conf, y no puede pasarse en la línea de comandos.

extra-platforms
Tipos de sistemas de ejecutables que pueden ser ejecutados en esta máquina.
Nix solo construirá una derivación localmente cuando su atributo system sea igual a alguno de los valores especificados aquí o en la opción system.
Configurar esto puede ser útil para construir derivaciones localmente en máquinas compatibles:
  • los ejecutables i686-linux pueden ejecutarse en máquinas x86_64-linux (configurado por defecto)
  • los ejecutables x86_64-darwin pueden ejecutarse en macOS aarch64-darwin con Rosetta 2 (configurado por defecto donde sea aplicable)

nix.conf(5)

Name

nix.conf — configuration file for Nix

Description

The Nix command-line tool honours a configuration file that allows you to customise its behaviour. The configuration file is located at $NIX_CONFDIR/nix.conf (defaulting to /etc/nix/nix.conf).

The configuration file is a simple text file containing settings in the format key = value. Settings can be prefixed with a subsystem name and a dot (e.g., subsystem.key = value). Boolean values can be true, false, 1, or 0.

The following settings are available:

Available settings

nix.binary-cache-public-keys
A list of public keys of binary caches that should be trusted. Nix will only fetch packages from caches that have a public key listed here.
Default: "" (empty string)
nix.trusted-public-keys
A list of public keys of binary caches that are trusted. Nix will fetch packages from any cache whose public key is listed here. This is used to determine whether to trust a binary cache or not, i.e. whether to download from it, or to use the download as an input for a build (which is a security risk).
Default: "" (empty string)
nix.trusted-users
A space-separated list of users who are allowed to perform Nix operations that require root privileges (like building packages). This is mainly to allow unprivileged users to build packages on systems with a multi-user installation of Nix.
Default: "root"
nix.experimental-features
A space-separated list of experimental features to enable. The following features are available:
  • nix-command: Enable the new Nix command-line interface (e.g., nix build).
  • flakes: Enable support for Nix Flakes.
Default: "" (empty string)
nix.max-build-jobs
The maximum number of build jobs that Nix will run concurrently. Setting this to 0 means unlimited.
Default: 4
nix.substituters
A space-separated list of binary cache URLs. Nix will try to download packages from these caches if they are available.
Default: "https://cache.nixos.org/"
nix.trusted-substituters
A space-separated list of binary cache URLs that are trusted. Nix will download packages from these caches if they are available. This is used to determine whether to trust a binary cache or not, i.e. whether to download from it, or to use the download as an input for a build (which is a security risk).
Default: "" (empty string)
nix.use-xdg-dirs
If set to true, Nix will use the XDG Base Directory Specification for storing its configuration and cache files.
Default: false
nix.fs-max-paths
The maximum number of paths in the Nix store that can be serialised to the NAR format. Set to -1 to disable this limit. This limit is intended to prevent out-of-memory errors when serialising very large paths to the Nix store (as determined by their NAR serialisation).
Default: -1
