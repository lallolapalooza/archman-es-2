Nombre

nix-store --optimise - reducir el uso de espacio en disco

Sintaxis

nix-store --optimise

Descripción

La operación --optimise reduce el uso de espacio en disco del almacén Nix encontrando archivos idénticos en el almacén y enlazándolos rígidamente entre sí. Típicamente reduce el tamaño del almacén en algo así como un 25-35%. Solo se enlazan rígidamente archivos regulares y enlaces simbólicos de esta manera. Los archivos se consideran idénticos cuando tienen la misma serialización de Archivo Nix (NAR): es decir, los archivos regulares deben tener el mismo contenido y permisos (ejecutable o no ejecutable), y los enlaces simbólicos deben tener el mismo contenido.

Al finalizar, o cuando el comando se interrumpe, se imprime un informe sobre los ahorros logrados en la salida de error estándar.

Utilice -vv o -vvv para obtener alguna indicación de progreso.

Opciones

Las siguientes opciones están permitidas para todas las operaciones de nix-store, pero pueden no tener siempre un efecto.

•
--add-root ruta
Hace que el resultado de una realización (--realise y --force-realise) se registre como una raíz del recolector de basura. La ruta se creará como un enlace simbólico a la ruta del almacén resultante. Además, se creará un enlace simbólico con nombre único a ruta en /nix/var/nix/gcroots/auto/. Por ejemplo,
$ nix-store --add-root /home/eelco/bla/resultado --realise ...
$ ls -l /nix/var/nix/gcroots/auto
lrwxrwxrwx    1 ... 2005-03-13 21:10 dn54lcypm8f8... -> /home/eelco/bla/resultado
$ ls -l /home/eelco/bla/resultado
lrwxrwxrwx    1 ... 2005-03-13 21:10 /home/eelco/bla/resultado -> /nix/store/1r11343n6qd4...-f-spot-0.0.10
Por lo tanto, cuando se elimina /home/eelco/bla/resultado, la raíz de GC en el directorio auto se convierte en un enlace simbólico colgado y será ignorada por el recolector.
Advertencia
Tenga en cuenta que no es posible mover o renombrar las raíces de GC, ya que el enlace simbólico en el directorio auto seguirá apuntando a la ubicación antigua.
Si hay varios resultados, se crearán varios enlaces simbólicos numerando secuencialmente los enlaces más allá del primero (por ejemplo, foo, foo-2, foo-3, y así sucesivamente).

Opciones Comunes

La mayoría de los comandos Nix aceptan las siguientes opciones de línea de comandos:

•
--help
Imprime un resumen de la sintaxis del comando y sale.
•
--version
Imprime el número de versión de Nix en la salida estándar y sale.
•
--verbose / -v
Aumenta el nivel de verbosidad de los mensajes de diagnóstico impresos en la salida de error estándar. Para cada operación de Nix, la información impresa en la salida estándar está bien definida; cualquier información de diagnóstico se imprime en la salida de error estándar, nunca en la salida estándar.
Esta opción se puede especificar repetidamente. Actualmente, existen los siguientes niveles de verbosidad:
•
0 "Solo errores"
Solo imprime mensajes que explican por qué falló la invocación de Nix.
•
1 "Informativo"
Imprime mensajes *útiles* sobre lo que Nix está haciendo. Este es el valor predeterminado.
•
2 "Hablador"
Imprime más mensajes informativos.
•
3 "Charla"
Imprime aún más mensajes informativos.
•
4 "Depuración"
Imprime información de depuración.
•
5 "Vómito"
Imprime grandes cantidades de información de depuración.
•
--quiet
Disminuye el nivel de verbosidad de los mensajes de diagnóstico impresos en la salida de error estándar. Esta es la opción inversa a -v / --verbose.
Esta opción se puede especificar repetidamente. Consulte la lista anterior de niveles de verbosidad.
•
--log-format formato
Esta opción se puede utilizar para cambiar la salida del formato de registro, con formato siendo uno de:
•
raw
Este es el formato sin procesar, tal como lo genera nix-build.
•
internal-json
Imprime los registros en un formato estructurado.
Advertencia
Aunque el esquema en sí es relativamente estable, el formato de los mensajes de error (específicamente el campo msg) puede cambiar entre versiones.
•
bar
Solo muestra una barra de progreso durante las compilaciones.
•
bar-with-logs
Muestra los registros sin procesar, con la barra de progreso en la parte inferior.
•
--no-build-output / -Q
Por defecto, la salida escrita por los constructores en la salida estándar y el error estándar se refleja en el error estándar del comando Nix. Esta opción suprime este comportamiento. Tenga en cuenta que la salida estándar y el error del constructor siempre se escriben en un archivo de registro en prefix/nix/var/log/nix.
•
--max-jobs / -j número
Establece el número máximo de trabajos de construcción que Nix realizará en paralelo al número especificado. Especifique auto para usar el número de CPUs en el sistema. El valor predeterminado es el especificado por la configuración max-jobs, que a su vez tiene como valor predeterminado 1. Un valor más alto es útil en sistemas SMP o para explotar la latencia de E/S.
Establecerlo en 0 deshabilita la construcción en la máquina local, lo cual es útil cuando desea que las construcciones ocurran solo en constructores remotos.
•
--cores
Establece el valor de la variable de entorno NIX_BUILD_CORES

NAME

nix-store --optimise - Compact the Nix store

SYNOPSIS

nix-store [option...] --optimise

DESCRIPTION

The --optimise operation walks through the Nix store (usually “/nix/store”) and replaces identical files with hard links. This saves disk space. It only considers files that are already registered in the Nix store.

A potential downside is that builds might become “impure” if they depend on the identity of the file path rather than the contents. If that happens, you can use the NIX_IGNORE_SYMLINK_STORE environment variable to prevent this.

For example, if you have two packages that happen to contain the exact same set of files, this operation will replace all but one of them with hard links to that one package, saving disk space.

OPTIONS

•
NIX_PATH
Sets the list of Nix search paths. This is a colon-separated list of directories. For example, NIX_PATH=nixpkgs=/path/to/nixpkgs:/my-overlay=/path/to/my-overlay. The default search path is typically /nix/var/nix/profiles/default/etc/nixpkgs/config.nix, and Nix may search for other Nix expressions relative to the Nixpkgs checkout.
If NIX_PATH is set to an empty string, resolving search paths will always fail.
Example
$ NIX_PATH= nix-instantiate --eval '<nixpkgs>'
error: file 'nixpkgs' was not found in the Nix search path (add it using $NIX_PATH or -I)
•
NIX_IGNORE_SYMLINK_STORE
Normally, the Nix store directory (typically /nix/store) is not allowed to contain any symlink components. This is to prevent “impure” builds. Builders sometimes “canonicalise” paths by resolving all symlink components. Thus, builds on different machines (with /nix/store resolving to different locations) could yield different results. This is generally not a problem, except when builds are deployed to machines where /nix/store resolves differently. If you are sure that you’re not going to do that, you can set NIX_IGNORE_SYMLINK_STORE to 1.
Note that if you’re symlinking the Nix store so that you can put it on another file system than the root file system, on Linux you’re better off using bind mount points, e.g.,
$ mkdir /nix
$ mount -o bind /mnt/otherdisk/nix /nix
Consult the mount 8 manual page for details.
•
NIX_STORE_DIR
Overrides the location of the Nix store (default prefix/store).
•
NIX_DATA_DIR
Overrides the location of the Nix static data directory (default prefix/share).
•
NIX_LOG_DIR
Overrides the location of the Nix log directory (default prefix/var/log/nix).
•
NIX_STATE_DIR
Overrides the location of the Nix state directory (default prefix/var/nix).
•
NIX_CONF_DIR
Overrides the location of the system Nix configuration directory (default prefix/etc/nix).
•
NIX_CONFIG
Applies settings from Nix configuration from the environment. The content is treated as if it was read from a Nix configuration file. Settings are separated by the newline character.
•
NIX_USER_CONF_FILES
Overrides the location of the Nix user configuration files to load from.
The default are the locations according to the XDG Base Directory Specification. See the XDG Base Directories sub-section for details.
The variable is treated as a list separated by the : token.
•
TMPDIR
Use the specified directory to store temporary files. In particular, this includes temporary build directories; these can take up substantial amounts of disk space. The default is /tmp.
•
NIX_REMOTE
This variable should be set to daemon if you want to use the Nix daemon to execute Nix operations. This is necessary in multi-user Nix installations. If the Nix daemon’s Unix socket is at some non-standard path, this variable should be set to unix://path/to/socket. Otherwise, it should be left unset.
•
NIX_SHOW_STATS
If set to 1, Nix will print some evaluation statistics, such as the number of values allocated.
•
NIX_COUNT_CALLS
If set to 1, Nix will print how often functions were called during Nix expression evaluation. This is useful for profiling your Nix expressions.
•
GC_INITIAL_HEAP_SIZE
If Nix has been configured to use the Boehm garbage collector, this variable sets the initial size of the heap in bytes. It defaults to 384 MiB. Setting it to a low value reduces memory consumption, but will increase runtime due to the overhead of garbage collection.

XDG Base Directories

Nix follows the XDG Base Directory Specification.

For backwards compatibility, Nix commands will follow the standard only when use-xdg-base-directories is enabled. New Nix commands (experimental) conform to the standard by default.

The following environment variables are used to determine locations of various state and configuration files:

  • [XDG_CONFIG_HOME]{#env-XDGCONFIGHOME} (default ~/.config)
  • [XDG_STATE_HOME]{#env-XDGSTATEHOME} (default ~/.local/state)
  • [XDG_CACHE_HOME]{#env-XDGCACHEHOME} (default ~/.cache)

$ nix-store --optimise
hashing files in `/nix/store/qhqx7l2f1kmwihc9bnxs7rc159hsxnf3-gcc-4.1.1'
...
541838819 bytes (516.74 MiB) freed by hard-linking 54143 files;
there are 114486 files with equal contents out of 215894 files in total
