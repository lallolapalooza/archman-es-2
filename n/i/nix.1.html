nix - una herramienta para la gestión de configuraciones declarativas y reproducibles

Sinopsis

nix [opción…] subcomando

donde subcomando es uno de los siguientes:

Comandos de ayuda:

  • nix help - muestra ayuda sobre nix o un subcomando particular
  • nix help-stores - muestra ayuda sobre los tipos de store y su configuración

Comandos principales:

  • nix build - construye una derivación o obtiene una ruta de store
  • nix develop - ejecuta un shell bash que proporciona el entorno de compilación de una derivación
  • nix flake - gestiona flakes de Nix
  • nix profile - gestiona perfiles de Nix
  • nix run - ejecuta una aplicación Nix
  • nix search - busca paquetes

Comandos principales:

•
nix repl - inicia un entorno interactivo para evaluar expresiones Nix

Comandos de uso infrecuente:

  • nix bundle - empaqueta una aplicación para que funcione fuera del Nix store
  • nix copy - copia rutas entre Nix stores
  • nix edit - abre la expresión Nix de un paquete Nix en $EDITOR
  • nix eval - evalúa una expresión Nix
  • nix fmt - reformula tu código con el estilo estándar
  • nix log - muestra el log de construcción de los paquetes o rutas especificadas, si está disponible
  • nix path-info - consulta información sobre rutas de store
  • nix registry - gestiona el registro de flakes
  • nix why-depends - muestra por qué un paquete tiene otro paquete en su cierre

Comandos de utilidad/scripting:

  • nix config - manipula la configuración de Nix
  • nix daemon - demonio para realizar operaciones de store en nombre de clientes no root
  • nix derivation - trabaja con derivaciones, la noción de Nix de un plan de construcción.
  • nix env - manipula el entorno del proceso
  • nix hash - calcula y convierte hashes criptográficos
  • nix key - genera y convierte claves de firma de Nix
  • nix nar - crea o inspecciona archivos NAR
  • nix print-dev-env - imprime código de shell que puede ser sourced por bash para reproducir el entorno de construcción de una derivación
  • nix realisation - manipula una realización de Nix
  • nix store - manipula un Nix store

Comandos para actualizar o solucionar problemas de tu instalación de Nix:

•
nix upgrade-nix - actualiza Nix a la última versión estable

Ejemplos

•
Crear un nuevo flake:
# nix flake new hello
# cd hello
•
Construir el flake en el directorio actual:
# nix build
# ./result/bin/hello
Hello, world!
•
Ejecutar el flake en el directorio actual:
# nix run
Hello, world!
•
Iniciar un entorno de desarrollo para trabajar en este flake:
# nix develop
# unpackPhase
# cd hello-*
# configurePhase
# buildPhase
# ./hello
Hello, world!
# installPhase
# ../outputs/out/bin/hello
Hello, world!

Descripción

Nix es una herramienta para construir software, configuraciones y otros artefactos de manera reproducible y declarativa. Para más información, ver el sitio web de Nix o el manual de Nix.

Instalables

Advertencia
Los instalables son parte de la función experimental inestable nix-command, y están sujetos a cambios sin previo aviso.

Muchos subcomandos de nix operan sobre uno o más instalables. Estos son argumentos de línea de comandos que representan algo que puede ser realizado en el Nix store.

Los siguientes tipos de instalables son soportados por la mayoría de los comandos:

•
Atributo de salida de flake (experimental)
•
Este es el valor por defecto
•
Ruta de store
•
Se asume si el argumento es una ruta de Nix store o un enlace simbólico a una ruta de Nix store
•
Archivo Nix, opcionalmente calificado por una ruta de atributo
•
Especificado con --file/-f
•
Expresión Nix, opcionalmente calificada por una ruta de atributo
•
Especificado con --expr/-E

Para la mayoría de los comandos, si no se especifica ningún instalable, se asume .. Es decir, Nix operará en el atributo de salida por defecto del flake en el directorio actual.

Atributo de salida de flake

Advertencia
Los instalables de atributos de salida de flake dependen tanto de las funciones experimentales flakes como de nix-command, y están sujetos a cambios sin previo aviso.

Ejemplo: nixpkgs#hello

Tienen la forma flakeref[#attrpath], donde flakeref es una referencia de flake y attrpath es un atributo opcional p

Instalables

Most nix subcommands take one or more instalables as arguments. An instalable is an attribute path that evaluates to a derivation, or a derivation itself. The following are all valid forms of instalables:

Atributo de salida de Flake

A flake reference, optionally followed by an attribute path.

A flake reference is one of the following:

•
A flake identifier in the flake registry (e.g. nixpkgs).
•
A raw path (e.g. /path/to/my-flake or . or ../foo).
•
A full URL (e.g. github:nixos/nixpkgs or path:.).

When the flake reference is a raw path (a path without any URL scheme), it is interpreted as a path: or git+file: url in the following way:

•
If the path is within a Git repository, then the url will be of the form git+file://[GIT_REPO_ROOT]?dir=[RELATIVE_FLAKE_DIR_PATH] where GIT_REPO_ROOT is the path to the root of the git repository, and RELATIVE_FLAKE_DIR_PATH is the path (relative to the directory root) of the closest parent of the given path that contains a flake.nix within the git repository. If no such directory exists, then Nix will error-out.
Note that the search will only include files indexed by git. In particular, files which are matched by .gitignore or have never been git add-ed will not be available in the flake. If this is undesirable, specify path:<directory> explicitly;
For example, if /foo/bar is a git repository with the following structure:
.
└── baz
  ├── blah
  │   └── file.txt
  └── flake.nix
Then /foo/bar/baz/blah will resolve to git+file:///foo/bar?dir=baz
•
If the supplied path is not a git repository, then the url will have the form path:FLAKE_DIR_PATH where FLAKE_DIR_PATH is the closest parent of the supplied path that contains a flake.nix file (within the same file-system). If no such directory exists, then Nix will error-out.
For example, if /foo/bar/flake.nix exists, then /foo/bar/baz/ will resolve to path:/foo/bar

If attrpath is omitted, Nix tries some default values; for most subcommands, the default is packages.system.default (e.g. packages.x86_64-linux.default), but some subcommands have other defaults. If attrpath is specified, attrpath is interpreted as relative to one or more prefixes; for most subcommands, these are packages.system, legacyPackages.*system* and the empty prefix. Thus, on x86_64-linux nix build nixpkgs#hello will try to build the attributes packages.x86_64-linux.hello, legacyPackages.x86_64-linux.hello and hello.

If attrpath begins with . then no prefixes or defaults are attempted. This allows the form flakeref[#.attrpath], such as github:NixOS/nixpkgs#.lib.fakeSha256 to avoid a search of packages.*system*.lib.fakeSha256

Ruta de la Tienda

Example: /nix/store/v5sv61sszx301i0x6xysaqzla09nksnd-hello-2.10

These are paths inside the Nix store, or symlinks that resolve to a path in the Nix store.

A derivación de la tienda también se aborda por ruta de la tienda.

Example: /nix/store/p7gp6lxdg32h4ka1q398wd9r2zkbbz2v-hello-2.10.drv

If you want to refer to an output path of that store derivation, add the output name preceded by a caret (^).

Example: /nix/store/p7gp6lxdg32h4ka1q398wd9r2zkbbz2v-hello-2.10.drv^out

All outputs can be referred to at once with the special syntax ^*.

Example: /nix/store/p7gp6lxdg32h4ka1q398wd9r2zkbbz2v-hello-2.10.drv^*

Archivo Nix

Example: --file /path/to/nixpkgs hello

When the option -f / --file path [attrpath…] is given, installables are interpreted as the value of the expression in the Nix file at path. If attribute paths are provided, commands will operate on the corresponding values accessible at these paths. The Nix expression in that file, or any selected attribute, must evaluate to a derivation.

Expresión Nix

Example: --expr 'import <nixpkgs> {}' hello

When the option --expr expression [attrpath…] is given, installables are interpreted as the value of the Nix expression. If attribute paths are provided, commands will operate on the corresponding values accessible at these paths. The Nix expression, or any selected attribute, must evaluate to a derivation.

You may need to specify --impure if the expression references impure inputs (such as <nixpkgs>).

Selección de salida de derivación

Las derivaciones pueden tener múltiples salidas, cada una correspondiente a una ruta de tienda diferente. Por ejemplo, un paquete puede tener una salida bin que contiene programas y una salida dev que proporciona artefactos de desarrollo como archivos de cabecera C/C++. Las salidas sobre las que operan los comandos de nix se determinan de la siguiente manera:

•
Puede especificar explícitamente las salidas deseadas utilizando la sintaxis instalable^salida1,…,salidaN — es decir, un acento circunflejo seguido inmediatamente por una lista separada por comas de las salidas de derivación a seleccionar. Para los instalables especificados como Atributos de salida de Flake o Rutas de la tienda, la salida se especifica en el mismo argumento:
Por ejemplo, puede obtener las salidas dev y static del paquete glibc:
# nix build 'nixpkgs#glibc^dev,static'
# ls ./result-dev/include/ ./result-static/lib/
…
y de manera similar, utilizando una ruta de tienda a un archivo “drv” para especificar la derivación:
# nix build '/nix/store/gzaflydcr6sb3567hap9q6srzx8ggdgg-glibc-2.33-78.drv^dev,static'
…
Para -e/--expr y -f/--file, la salida de la derivación se especifica como parte de la ruta del atributo:
$ nix build -f '<nixpkgs>' 'glibc^dev,static'
$ nix build --impure -E 'import <nixpkgs> { }' 'glibc^dev,static'
Esta sintaxis es la misma incluso si la ruta del atributo real está vacía:
$ nix build -E 'let pkgs = import <nixpkgs> { }; in pkgs.glibc' '^dev,static'
•
También puede especificar que se utilicen *todas* las salidas usando la sintaxis instalable^*. Por ejemplo, lo siguiente muestra el tamaño de todas las salidas del paquete glibc en la caché binaria:
# nix path-info --closure-size --eval-store auto --store https://cache.nixos.org 'nixpkgs#glibc^*'
/nix/store/g02b1lpbddhymmcjb923kf0l7s9nww58-glibc-2.33-123                 33208200
/nix/store/851dp95qqiisjifi639r0zzg5l465ny4-glibc-2.33-123-bin             36142896
/nix/store/kdgs3q6r7xdff1p7a9hnjr43xw2404z7-glibc-2.33-123-debug          155787312
/nix/store/n4xa8h6pbmqmwnq0mmsz08l38abb06zc-glibc-2.33-123-static          42488328
/nix/store/q6580lr01jpcsqs4r5arlh4ki2c1m9rv-glibc-2.33-123-dev             44200560
y de manera similar, utilizando una ruta de tienda a un archivo “drv” para especificar la derivación:
# nix path-info --closure-size '/nix/store/gzaflydcr6sb3567hap9q6srzx8ggdgg-glibc-2.33-78.drv^*'
…
•
Si no especificó las salidas deseadas, pero la derivación tiene un atributo meta.outputsToInstall, Nix usará esas salidas. Por ejemplo, dado que el paquete nixpkgs#libxml2 tiene este atributo:
# nix eval 'nixpkgs#libxml2.meta.outputsToInstall'
[ "bin" "man" ]
un comando como nix shell nixpkgs#libxml2 proporcionará solo esas dos salidas por defecto.
Tenga en cuenta que una derivación de tienda no tiene ningún atributo como meta, y por lo tanto, este caso no se aplica a ella.
•
De lo contrario, Nix utilizará todas las salidas de la derivación.

Description

The nix command is a unified entrypoint for many Nix operations.

Subcommands

The following subcommands are available:

shell
Starts an interactive shell with the specified dependencies available. If --command is used, executes the command and exits.
build
Builds the given Nix expression(s) and puts the results into the Nix store.
run
Builds and runs a command within the specified environment. Similar to nix shell --command, but also applies the Nix search path to the specified executable.
install
Builds the given Nix expression(s) and makes them available on the Nix search path.
edit
Opens the given Nix expression(s) in an editor.
log
Shows build logs for the given derivations.
un Nix
Removes the given Nix store paths from the Nix store.
flake
Interacts with Nix flakes.
help
Shows usage information.

Shebang interpreter

The nix command can be invoked directly from a script using the shebang line:

#!/usr/bin/env nix

This requires the script to be executable and to have the nix executable in its PATH.

The nix command supports interpreting shebang lines specified within the script itself. These lines must start with #! and be followed by the interpreter name. Nix supports the following interpreters:

nix
This is the default interpreter. It runs Nix commands like shell, build, etc.

Arguments to the nix interpreter can be passed directly after #! nix. For example:

# Build the 'hello' package and run it
#! nix build nixpkgs#hello
#! nix run nixpkgs#hello

The nix shell command can be used to create an environment and execute a command within it. The environment can be specified using Nix expressions or flake references.

# Example using nix expression
#! nix shell --expr "with import <nixpkgs> {}; hello" --command hello
# Example using flake reference
#! nix shell nixpkgs#hello --command hello

Arguments provided after the main nix command in the shebang line are passed as arguments to the interpreter. A single argument starting with `` and ending with `` is interpreted as a Nix expression.

The special syntax ``<nixpkgs>`` is expanded to the Nixpkgs channel.

The length of literal backticks (`) inside Nix expressions is handled as follows: n backticks of 3 or longer are parsed as n-1 literal backticks. A single space before the closing `` is ignored if present.

--file and --expr resolve relative paths based on the script location.

Examples:

#!/usr/bin/env nix
#! nix shell --file ``<nixpkgs>`` hello cowsay --command bash
hello | cowsay

or with flakes:

#!/usr/bin/env nix
#! nix shell nixpkgs#bash nixpkgs#hello nixpkgs#cowsay --command bash
hello | cowsay

or with an expression:

#! /usr/bin/env nix
#! nix shell --impure --expr ``
#! nix with (import (builtins.getFlake "nixpkgs") {});
#! nix terraform.withPlugins (plugins: [ plugins.openstack ])
#! nix ``
#! nix --command bash
terraform "$@"

or with cascading interpreters. Note that the #! nix lines don’t need to follow after the first line, to accomodate other interpreters.

#!/usr/bin/env nix
//! ```cargo
//! [dependencies]
//! time = "0.1.25"
//! ```
/*
#!nix shell nixpkgs#rustc nixpkgs#rust-script nixpkgs#cargo --command rust-script
*/
fn main() {
    for argument in std::env::args().skip(1) {
        println!("{}", argument);
    };
    println!("{}", std::env::var("HOME").expect(""));
    println!("{}", time::now().rfc822z());
}
// vim: ft=rust
bash, sh
Executes the script using the specified shell.
python
Executes the script using the Python interpreter.
perl
Executes the script using the Perl interpreter.
node
Executes the script using Node.js.
Any other executable
The script is executed directly using the specified executable.

The interpreter can be specified in a shebang line as #! interpreter, or as a comment line starting with //! or #*, or within a block comment /* ... */.

The nix command itself also supports interpreting shebang lines specified within the script. These lines must start with #! and be followed by the interpreter name.
