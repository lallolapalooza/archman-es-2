nix-env --upgrade(1) Manual de Comandos Generales nix-env --upgrade(1)

Nombre

nix-env --upgrade - actualizar paquetes en el entorno de usuario

Sinopsis

nix-env {--upgrade | -u} args [--lt | --leq | --eq | --always] [{--prebuilt-only | -b}] [{--attr | -A}] [--from-expression] [-E] [--from-profile ruta] [--preserve-installed | -P]

Descripción

La operación de actualización crea un nuevo entorno de usuario, basado en la generación actual del perfil activo, en el que todas las rutas del almacén se reemplazan por aquellas para las que existen versiones más nuevas en el conjunto de rutas descritas por args. Las rutas para las que no existen versiones más nuevas se dejan intactas; esto no es un error. Tampoco es un error si un elemento de args no coincide con ninguna derivación instalada.

Para una descripción de cómo args se mapea a un conjunto de rutas del almacén, consulte --install. Si args describe múltiples rutas de almacén con el mismo nombre simbólico, solo se instalará la de mayor versión.

Banderas

•
--lt
Solo actualiza una derivación a versiones más nuevas. Este es el valor predeterminado.
•
--leq
Además de actualizar a versiones más nuevas, también "actualiza" a derivaciones que tienen la misma versión. Las versiones no son una identificación única de una derivación, por lo que puede haber muchas derivaciones que tengan la misma versión. Esta bandera puede ser útil para forzar la "sincronización" entre las derivaciones instaladas y las disponibles.
•
--eq
Solo "actualiza" a derivaciones que tienen la misma versión. Esto puede no parecer muy útil, pero en realidad lo es, por ejemplo, cuando hay una nueva versión de Nixpkgs y desea reemplazar las aplicaciones instaladas con las mismas versiones compiladas contra dependencias más nuevas (para reducir la cantidad de dependencias que flotan en su sistema).
•
--always
Además de actualizar a versiones más nuevas, también "actualiza" a derivaciones que tienen una versión igual o inferior. Es decir, las derivaciones pueden ser degradadas dependiendo de lo que esté disponible en la expresión Nix activa.
•
--prebuilt-only / -b
Utiliza solo derivaciones para las cuales hay una sustitución registrada, es decir, hay un binario precompilado disponible que se puede descargar en lugar de compilar la derivación. Por lo tanto, no se compilarán paquetes desde el código fuente.
•
--preserve-installed / -P
No elimine las derivaciones con un nombre que coincida con una de las derivaciones que se están instalando. Por lo general, intentar tener dos versiones del mismo paquete instaladas en la misma generación de un perfil llevará a un error al compilar la generación, debido a conflictos de nombres de archivo entre las dos versiones. Sin embargo, este no es el caso para todos los paquetes.

Opciones

Las siguientes opciones están permitidas para todas las operaciones de nix-env, pero pueden no tener efecto en todo momento.

•
--file / -f ruta
Especifica la expresión Nix (designada a continuación como la *expresión Nix activa*) utilizada por las operaciones --install, --upgrade y --query --available para obtener derivaciones. El valor predeterminado es ~/.nix-defexpr.
Si el argumento comienza con http:// o https://, se interpreta como la URL de un archivo tarball que se descargará y desempaquetará en una ubicación temporal. El archivo tarball debe incluir un único directorio de nivel superior que contenga al menos un archivo llamado default.nix.
•
--profile / -p ruta
Especifica el perfil a ser utilizado por aquellas operaciones que operan en un perfil (designado a continuación como el *perfil activo*). Un perfil es una secuencia de entornos de usuario llamados *generaciones*, una de las cuales es la *generación actual*.
•
--dry-run
Para las operaciones --install, --upgrade, --uninstall, --switch-generation, --delete-generations y --rollback, esta bandera hará que nix-env imprima lo que *se haría* si esta bandera no se hubiera especificado, sin hacerlo realmente.
--dry-run también imprime qué rutas serán sustituidas (es decir, descargadas) y qué rutas se compilarán desde el código fuente (porque no hay sustituta disponible).
•
--system-filter sistema
Por defecto, operaciones como --query --available muestran derivaciones que coinciden con cualquier plataforma. Esta opción permite utilizar derivaciones para la plataforma especificada sistema.

Opciones Comunes

La mayoría de los comandos de Nix aceptan las siguientes opciones de línea de comandos:

•
--help
Imprime un resumen de la sintaxis del comando y sale.
•
--version
Imprime el número de versión de Nix en la salida estándar y sale.
•
--verbose / -v
Aumenta el nivel de verbosidad de los mensajes de diagnóstico impresos en la salida de error estándar. Para cada operación de Nix, la información impresa en la salida estándar está bien definida; cualquier información de diagnóstico se imprime en la salida de error estándar, nunca en la salida estándar.
Esta opción se puede especificar repetidamente. Actualmente, existen los siguientes niveles de verbosidad:
•
0 "Solo errores"
Solo imprime mensajes que expliquen por qué falló la invocación de Nix.
•
1 "Informativo"
Imprime mensajes *útiles* sobre lo que está haciendo Nix. Este es el valor predeterminado.
•
2 "Hablador"
Imprime más mensajes informativos.
•
3 "Conversador"
Imprime aún más mensajes informativos.
•
4 "Depurar"
Imprime información de depuración.<
/dd>
•
5 «Vomitar»
Imprime una gran cantidad de información de depuración.
•
--quiet
Disminuye el nivel de detalle de los mensajes de diagnóstico impresos en la salida estándar de error. Esta es la opción inversa a -v / --verbose.
Esta opción se puede especificar varias veces. Consulte la lista anterior de niveles de detalle.
•
--log-format formato
Esta opción se puede utilizar para cambiar el formato de salida del registro, donde formato puede ser uno de los siguientes:
•
raw
Este es el formato sin procesar, tal como lo produce nix-build.
•
internal-json
Imprime los registros de forma estructurada.
Advertencia
Aunque el esquema es relativamente estable, el formato de los mensajes de error (específicamente del campo msg) puede cambiar entre versiones.
•
bar
Solo muestra una barra de progreso durante las compilaciones.
•
bar-with-logs
Muestra los registros sin procesar, con la barra de progreso en la parte inferior.
•
--no-build-output / -Q
Por defecto, la salida escrita por los constructores a la salida estándar y al error estándar se refleja en el error estándar del comando Nix. Esta opción suprime este comportamiento. Tenga en cuenta que la salida estándar y el error del constructor siempre se escriben en un archivo de registro en prefix/nix/var/log/nix.
•
--max-jobs / -j número
Establece el número máximo de trabajos de compilación que Nix realizará en paralelo al número especificado. Especifique auto para usar el número de núcleos de CPU del sistema. El valor predeterminado es especificado por la configuración max-jobs, que a su vez tiene como valor predeterminado 1. Un valor más alto es útil en sistemas SMP o para explotar la latencia de E/S.
Establecerlo en 0 deshabilita la compilación en la máquina local, lo cual es útil cuando se desea que las compilaciones ocurran solo en constructores remotos.
•
--cores
Establece el valor de la variable de entorno NIX_BUILD_CORES en la invocación de los constructores. Los constructores pueden usar esta variable a su discreción para controlar la máxima cantidad de paralelismo. Por ejemplo, en Nixpkgs, si el atributo de derivación enableParallelBuilding está configurado en true, el constructor pasa la bandera -jN a GNU Make. Por defecto, utiliza el valor de la configuración cores, si está configurada, o 1 en caso contrario. El valor 0 significa que el constructor debe usar todos los núcleos de CPU disponibles en el sistema.
•
--max-silent-time
Establece el tiempo máximo en segundos que un constructor puede pasar sin producir ninguna salida en la salida estándar o error estándar. El valor predeterminado es especificado por la configuración max-silent-time. 0 significa que no hay tiempo de espera.
•
--timeout
Establece el tiempo máximo en segundos que puede ejecutarse un constructor. El valor predeterminado es especificado por la configuración timeout. 0 significa que no hay tiempo de espera.
•
--keep-going / -k
Continuar en caso de compilaciones fallidas, en la mayor medida posible. Es decir, si falla la compilación de una entrada de alguna derivación, Nix seguirá compilando las otras entradas, pero no la derivación en sí. Sin esta opción, Nix se detiene si falla alguna compilación (excepto las compilaciones de sustitutos), posiblemente interrumpiendo las compilaciones en curso (en caso de compilaciones paralelas o distribuidas).
•
--keep-failed / -K
Especifica que en caso de fallo de compilación, el directorio temporal (generalmente en /tmp) en el que se realiza la compilación no debe ser eliminado. La ruta del directorio de compilación se imprime como un mensaje informativo.
•
--fallback
Cada vez que Nix intenta compilar una derivación para la que se conocen sustitutos para cada ruta de salida, pero la realización de las rutas de salida a través de los sustitutos falla, recurre a compilar la derivación.
El escenario más común en el que esto es útil es cuando hemos registrado sustitutos para realizar la distribución binaria desde, por ejemplo, un repositorio de red. Si el repositorio está caído, la realización de la derivación fallará. Cuando se especifica esta opción, Nix compilará la derivación en su lugar. Por lo tanto, la instalación desde binarios recurre a la instalación desde el código fuente. Esta opción no es la predeterminada, ya que generalmente no es deseable que un fallo transitorio en la obtención de los sustitutos lleve a una compilación completa desde el código fuente (con el consumo de recursos relacionado).
•
--readonly-mode
Cuando se utiliza esta opción, no se intenta abrir la base de datos de Nix. La mayoría de las operaciones de Nix necesitan acceso a la base de datos, por lo que esas operaciones fallarán.
•
--arg nombre valor
Esta opción es aceptada por nix-env, nix-instantiate, nix-shell y nix-build. Al evaluar expresiones de Nix, el evaluador de expresiones intentará automáticamente llamar a las funciones que encuentre. Puede llamar automáticamente a funciones para las que todos los argumentos tienen un valor predeterminado (por ejemplo, { argName ? defaultValue }: ...).
Con --arg, también puedes llamar a funciones que tienen argumentos sin valor predeterminado (o anular un valor predeterminado). Es decir, si el evaluador encuentra una función con un argumento llamado nombre, la llamará con el valor valor.
Por ejemplo, el default.nix de nivel superior en Nixpkgs es en realidad una función:
{ # El sistema (por ejemplo, `i686-linux') para el que se compilarán los paquetes.
system ? builtins.currentSystem
...
}: ...
Así, si llamas a esta expresión de Nix (por ejemplo, cuando haces nix-env --install --attr pkgname), la función se llamará automáticamente utilizando el valor builtins.currentSystem para el argumento system. Puedes anular esto usando --arg, por ejemplo, nix-env --install --attr pkgname --arg system \"i686-freebsd\". (Ten en cuenta que, dado que el argumento es una cadena literal de Nix, debes escapar las comillas.)
•
--argstr nombre valor
Esta opción es como --arg, solo que el valor no es una expresión de Nix sino una cadena. Así que en lugar de --arg system \"i686-linux\" (las comillas externas son para que el shell funcione correctamente) puedes decir --argstr system i686-linux.
•
--attr / -A attrPath
Selecciona un atributo de la expresión Nix de nivel superior que se está evaluando. (Solo nix-env, nix-instantiate, nix-build y nix-shell.) El ruta de atributo attrPath es una secuencia de nombres de atributos separados por puntos. Por ejemplo, dada una expresión Nix de nivel superior e, la ruta de atributo xorg.xorgserver haría que se utilizara la expresión e.xorg.xorgserver. Consulte nix-env --install para ver algunos ejemplos concretos.
Además de los nombres de atributos, también puedes especificar índices de arreglos. Por ejemplo, la ruta de atributo foo.3.bar selecciona el atributo bar del cuarto elemento del arreglo en el atributo foo de la expresión de nivel superior.
•
--expr / -E
Interpreta los argumentos de la línea de comandos como una lista de expresiones Nix para ser analizadas y evaluadas, en lugar de como una lista de nombres de archivos de expresiones Nix. (nix-instantiate, nix-build
y nix-shell solo.)
Para nix-shell, esta opción se usa comúnmente para proporcionarte un shell en el que puedas construir los paquetes devueltos por la expresión. Si quieres obtener un shell que contenga los paquetes construidos listos para usar, proporciona tu expresión a la opción de conveniencia nix-shell --packages en su lugar.
•
-I / --include ruta
Añade una entrada a la lista de rutas de búsqueda utilizadas para resolver rutas de búsqueda. Esta opción puede darse varias veces.
Las rutas añadidas a través de -I tienen precedencia sobre la configuración nix-path y la variable de entorno NIX_PATH.
•
--option nombre valor
Establece la opción de configuración de Nix nombre a valor. Esto anula los ajustes en el archivo de configuración de Nix (ver nix.conf5).
•
--repair
Repara rutas de tienda corrompidas o faltantes redescargándolas o reconstruyéndolas. Ten en cuenta que esto es lento porque requiere calcular un hash criptográfico del contenido de cada ruta en el cierre de la construcción. También ten en cuenta la advertencia bajo nix-store --repair-path.

Nota

Ver man nix.conf para anular la configuración con flags de línea de comandos.

Variables de entorno

•
NIX_PROFILE
Ubicación del perfil de Nix. Por defecto es el enlace simbólico ~/.nix-profile, si existe, o /nix/var/nix/profiles/default en caso contrario.

Variables de entorno comunes

La mayoría de los comandos de Nix interpretan las siguientes variables de entorno:

•
IN_NIX_SHELL
Indicador que dice si el entorno actual fue configurado por nix-shell. Puede tener los valores pure o impure.
•
NIX_PATH
Una lista separada por dos puntos de entradas de búsqueda usadas para resolver rutas de búsqueda.
Esta variable de entorno anula el valor de la configuración nix-path.
Puede ser extendida usando la opción -I.
Ejemplo
$ export NIX_PATH=`/home/eelco/Dev:nixos-config=/etc/nixos
Si NIX_PATH está configurado a una cadena vacía, la resolución de rutas de búsqueda siempre fallará.
Ejemplo
$ NIX_PATH= nix-instantiate --eval '<nixpkgs>'
error: el archivo 'nixpkgs' no se encontró en la ruta de búsqueda de Nix (añádelo usando $NIX_PATH o -I)
•
NIX_IGNORE_SYMLINK_STORE
Normalmente, el directorio de la tienda Nix (típicamente /nix/store) no tiene permitido contener ningún componente de enlace simbólico. Esto es para prevenir construcciones "impuras". Los constructores a veces "canonizan" rutas resolviendo todos los componentes de enlace simbólico. Por lo tanto, las construcciones en diferentes máquinas (con /nix/store resolviendo a diferentes ubicaciones) podrían producir resultados diferentes. Esto generalmente no es un problema, excepto cuando las construcciones se despliegan en máquinas donde /nix/store se resuelve de manera diferente. Si estás seguro de que no vas a hacer eso, puedes establecer NIX_IGNORE_SYMLINK_STORE a 1.
Ten en cuenta que si estás creando enlaces simbólicos a la tienda Nix para poder ponerla en un sistema de archivos diferente al sistema de archivos raíz, en Linux es mejor usar puntos de montaje bind, por ejemplo:
$ mkdir /nix
$ mount -o bind /mnt/otherdisk/nix /nix
Consulta la página del manual de mount 8 para más detalles.
•
NIX_STORE_DIR
Anula la ubicación de la tienda Nix (por defecto prefix/store).
•
NIX_DATA_DIR
Anula la ubicación del directorio de datos estáticos de Nix (por defecto prefix/share).
•
NIX_LOG_DIR
Anula la ubicación del directorio de logs de Nix (por defecto prefix/var/log/nix).
•
NIX_STATE_DIR
Anula la ubicación del directorio de estado de Nix (por defecto prefix/var/nix).
•
NIX_CONF_DIR
Anula la ubicación del directorio de configuración del sistema Nix (por defecto prefix/etc/nix).
•
NIX_CONFIG
Aplica configuraciones de Nix desde el entorno. El contenido se trata como si se hubiera leído de un archivo de configuración de Nix. Las configuraciones se separan por el carácter de nueva línea.
•
NIX_USER_CONF_FILES
Anula la ubicación de los archivos de configuración de usuario de Nix a cargar.
Los valores por defecto son las ubicaciones según la Especificación de Directorios Base XDG. Ver la subsección Directorios Base XDG para más detalles.
La variable se trata como una lista separada por el token :.
•
TMPDIR
Usa el directorio especificado para almacenar archivos temporales. En particular, esto incluye directorios de construcción temporales; estos pueden ocupar una cantidad considerable de espacio en disco. El valor por defecto es /tmp.
•
NIX_REMOTE
Esta variable debe configurarse a daemon si quieres usar el demonio Nix para ejecutar operaciones de Nix. Esto es necesario en instalaciones Nix multiusuario. Si el socket Unix del demonio Nix está en una ruta no estándar, esta variable debe configurarse a unix://ruta/al/socket. De lo contrario, debe dejarse sin configurar.
•
NIX_SHOW_STATS
Si está configurada a 1, Nix imprimirá algunas estadísticas de evaluación, como el número de valores asignados.
•
NIX_COUNT_CALLS
Si está configurada a 1, Nix imprimirá cuántas veces se llamaron las funciones durante la evaluación de la expresión Nix. Esto es útil para perfilar tus expresiones Nix.
•
GC_INITIAL_HEAP_SIZE
Si Nix ha sido configurado para usar el recolector de basura de Boehm, esta variable establece el tamaño inicial del montón en bytes. Por defecto es 384 MiB. Establecerlo a un valor bajo reduce el consumo de memoria, pero aumentará el tiempo de ejecución debido a la sobrecarga de la recolección de basura.

Directorios Base XDG

Nix sigue la Especificación de Directorios Base XDG.

Para compatibilidad con versiones anteriores, los comandos de Nix seguirán el estándar solo cuando use-xdg-base-directories esté habilitado. Los nuevos comandos Nix (experimentales) siguen el estándar por defecto.

    nix-env(1)
    Nix manual

    Name

    nix-env - Manage user environment

    Synopsis

    nix-env [GC options] [-q] [-qa [glob]] [-qi [glob]] [-qo [glob]] [-qri [glob]] [-qf [glob]] [-qsh [glob]] [-qL] [-i path ...] | [-iA attrPath ...] | [-u [path ...] | -uA attrPath ...] | [-e glob ...] | [-f path [attrPath ...]] [-P] [--attr attrPath ...]

    Description

    nix-env is a tool for managing a user’s declarative environment. It allows users to install, uninstall, and upgrade packages within their user profile.

    The Nix package manager operates on derivations, which are recipes for building packages. A Nix channel is a collection of package derivations. Nix channels can be added and updated. The nix-env command interacts with these channels to manage installed packages.

    The user environment is represented as a set of symlinks in the Nix store (e.g., /nix/var/nix/profiles/per-user/root/profile). Nix-env modifies this profile to reflect the desired set of packages.

    All operations are transactional. If an operation fails, the user’s environment remains unchanged.

    Flags

    -h, --help
    Display help message and exit.
    -v, --verbose
    Produce verbose output.

    Options

    Querying the environment

    -q, --query
    List installed packages.
    -qa [glob]
    Query all available packages matching glob. If glob is omitted, list all available packages.
    -qi [glob]
    Query installed packages matching glob. If glob is omitted, list all installed packages.
    -qo [glob]
    Query outdated installed packages matching glob. If glob is omitted, list all outdated installed packages.
    -qri [glob]
    Query packages that are replacements for installed packages matching glob. If glob is omitted, query all packages that are replacements for installed packages.
    -qsh [glob]
    Query package sources matching glob. If glob is omitted, list all available package sources.
    -qL
    List available channels.

    Installing and upgrading packages

    -i path ...
    Install the packages at the given Nix store paths.
    -iA attrPath ...
    Install the packages named by the given attribute attrPaths. Attribute paths refer to packages within Nix channels (e.g., nixpkgs.firefox).
    -u [path ...]
    Upgrade installed packages. If no arguments are given, upgrade all installed packages. If arguments are given, attempt to upgrade only the specified installed packages.
    -uA attrPath ...
    Upgrade installed packages to the specified attribute attrPaths. This is useful for upgrading to a specific version or package that is not the default upgrade target.
    --attr attrPath ...
    This option is synonymous with -iA. It is used for installing packages via attribute paths.

    Uninstalling packages

    -e glob ...
    Uninstall the packages matching the given glob patterns. This performs an exact match on the package name, but supports globbing.

    Miscellaneous options

    -f path [attrPath ...]
    Use the Nix expression at path as the source of packages. If attrPaths are provided, install those packages from the expression. This allows operating on arbitrary Nix expressions, not just those provided by channels.
    -P
    Switch to profile mode. This is the default behavior. Operations are performed on the user's profile.
    --rollback
    Roll back to the previous generation of the user environment.
    --set-root path
    Set the current generation of the user environment to the specified path.
    --list-generations
    List all available generations of the user environment.
    --delete-generations pattern ...
    Delete generations matching the specified patterns. Patterns are glob expressions that match generation numbers or keywords like @ antigüedad (e.g., “10”, “10!”, “-5”, “~1d”).
    --switch-generation pattern
    Switch to the generation matching the specified pattern.
    --upgrade-all
    Equivalent to -u without arguments.
    --always
    When upgrading, if the target version is older than the currently installed version, still perform the upgrade. This is typically used when specifying a package by name instead of an attribute path.

    Common Options

    These options are common to most Nix commands:

    --option name= value
    Set the Nix option name to value. See nix.conf(5) for a list of available options.
    -I path
    Add path to the Nix expression search path. This option can be specified multiple times to add multiple paths.
    --gc-root name
    Add a GC root named name pointing to the result of the operation. This ensures that the result is not garbage collected.
    --no-gc-root
    Do not add a GC root pointing to the result of the operation.

    Environment variables

    The behavior of nix-env can be influenced by the following environment variables:

    NIX_PATH
    A colon-separated list of paths to search for Nix expressions. For example, NIX_PATH=nixpkgs=/path/to/nixpkgs.
    NIX_CONFIG
    The path to the Nix configuration file. Defaults to ~/.config/nix/nix.conf.
    NIX_PROFILES
    A colon-separated list of profiles to manage. Defaults to ~/.nix-profile:/nix/var/nix/profiles/default.

    Common Environment Variables

    The following environment variables are respected by most Nix commands:

    • [XDG_STATE_HOME]{#env-XDGSTATEHOME} (default ~/.local/state)
    • [XDG_CACHE_HOME]{#env-XDGCACHEHOME} (default ~/.cache)

    Examples

    $ nix-env --upgrade --attr nixpkgs.gcc
upgrading `gcc-3.3.1' to `gcc-3.4'

    When there are no updates available, nothing will happen:

    $ nix-env --upgrade --attr nixpkgs.pan

    Using -A is preferred when possible, as it is faster and unambiguous but it is also possible to upgrade to a specific version by matching the derivation name:

    $ nix-env --upgrade gcc-3.3.2 --always
upgrading `gcc-3.4' to `gcc-3.3.2'

    To try to upgrade everything (matching packages based on the part of the derivation name without version):

    $ nix-env --upgrade
upgrading `hello-2.1.2' to `hello-2.1.3'
upgrading `mozilla-1.2' to `mozilla-1.4'

    Versions

    The upgrade operation determines whether a derivation y is an upgrade of a derivation x by looking at their respective name attributes. The names (e.g., gcc-3.3.1 are split into two parts: the package name (gcc), and the version (3.3.1). The version part starts after the first dash not followed by a letter. y is considered an upgrade of x if their package names match, and the version of y is higher than that of x.

    The versions are compared by splitting them into contiguous components of numbers and letters. E.g., 3.3.1pre5 is split into [3, 3, 1, "pre", 5]. These lists are then compared lexicographically (from left to right). Corresponding components a and b are compared as follows. If they are both numbers, integer comparison is used. If a is an empty string and b is a number, a is considered less than b. The special string component pre (for pre-release) is considered to be less than other components. String components are considered less than number components. Otherwise, they are compared lexicographically (i.e., using case-sensitive string comparison).

    This is illustrated by the following examples:

    1.0 < 2.3
2.1 < 2.3
2.3 = 2.3
2.5 > 2.3
3.1 > 2.3
2.3.1 > 2.3
2.3.1 > 2.3a
2.3pre1 < 2.3
2.3pre3 < 2.3pre12
2.3a < 2.3c
2.3pre1 < 2.3c
2.3pre1 < 2.3q
