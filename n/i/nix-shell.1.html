nix-shell(1)

Paquete: nix

Licencias: LGPL-2.1-only

nix-shell(1) Manual de Comandos Generales nix-shell(1)

Nombre

nix-shell - inicia un shell interactivo basado en una expresión Nix

Sinopsis

nix-shell [--arg nombre valor] [--argstr nombre valor] [{--attr | -A} rutaAtributo] [--command cmd] [--run cmd] [--exclude expReg] [--pure] [--keep nombre] {{--packages | -p} {paquetes | expresiones} … | [ruta]}

Desambiguación

Esta página de manual describe el comando nix-shell, que es distinto de nix shell. Para la documentación del segundo, ejecuta nix shell --help o consulta man nix3-shell.

Descripción

El comando nix-shell construirá las dependencias de la derivación especificada, pero no la derivación en sí. Luego iniciará un shell interactivo en el que todas las variables de entorno definidas por la derivación ruta se habrán establecido a sus valores correspondientes, y el script $stdenv/setup se habrá cargado. Esto es útil para reproducir el entorno de una derivación para el desarrollo.

Si no se proporciona ruta, nix-shell utiliza shell.nix si existe, y default.nix en caso contrario.

Si ruta comienza con http:// o https://, se interpreta como la URL de un archivo tarball que se descargará y descomprimirá en una ubicación temporal. El archivo tarball debe incluir un único directorio de nivel superior que contenga al menos un archivo llamado default.nix.

Si la derivación define la variable shellHook, se ejecutará después de que $stdenv/setup se haya cargado. Dado que este hook no se ejecuta en las compilaciones Nix normales, te permite realizar inicializaciones específicas para nix-shell. Por ejemplo, el atributo de derivación

shellHook =
  ''
    echo "Hola shell"
    export SOME_API_TOKEN="$(cat ~/.config/some-app/api-token)"
  '';

hará que nix-shell imprima Hola shell y establezca la variable de entorno SOME_API_TOKEN a un valor configurado por el usuario.

Opciones

Todas las opciones no listadas aquí se pasan a nix-store --realise, excepto --arg y --attr / -A que se pasan a nix-instantiate.

•
--command cmd
En el entorno de la derivación, ejecuta el comando de shell cmd. Este comando se ejecuta en un shell interactivo. (Usa --run para usar un shell no interactivo en su lugar). Sin embargo, se añade implícitamente una llamada a exit al comando, por lo que el shell saldrá después de ejecutar el comando. Para evitar esto, añade return al final; por ejemplo, --command "echo Hola; return" imprimirá Hola y luego te dejará en el shell interactivo. Esto puede ser útil para realizar cualquier inicialización adicional.
•
--run cmd
Al igual que --command, pero ejecuta el comando en un shell no interactivo. Esto significa (entre otras cosas) que si pulsas Ctrl-C mientras se ejecuta el comando, el shell se cerrará.
•
--exclude expReg
No construir ninguna dependencia cuya ruta de almacén coincida con la expresión regular expReg. Esta opción puede especificarse varias veces.
•
--pure
Si se especifica esta bandera, el entorno se limpia casi por completo antes de iniciar el shell interactivo, de modo que obtienes un entorno que corresponde más estrechamente a la compilación Nix “real”. Se conservan algunas variables, en particular HOME, USER y DISPLAY.
•
--packages / -p paquetes…
Configura un entorno en el que estén presentes los paquetes especificados. Los argumentos de la línea de comandos se interpretan como nombres de atributos dentro de la colección Nix Packages. Por lo tanto, nix-shell --packages libjpeg openjdk iniciará un shell en el que estén presentes los paquetes denotados por los nombres de atributo libjpeg y openjdk.
•
-i intérprete
El intérprete de script encadenado que será invocado por nix-shell. Solo aplicable en scripts #! (descritos a continuación).
•
--keep nombre
Cuando se inicia un shell --pure, se conservan las variables de entorno listadas.

Opciones Comunes

La mayoría de los comandos de Nix aceptan las siguientes opciones de línea de comandos:

•
--help
Imprime un resumen de la sintaxis del comando y sale.
•
--version
Imprime el número de versión de Nix en la salida estándar y sale.
•
--verbose / -v
Aumenta el nivel de verbosidad de los mensajes de diagnóstico impresos en el error estándar. Para cada operación de Nix, la información impresa en la salida estándar está bien definida; cualquier información de diagnóstico se imprime en el error estándar, nunca en la salida estándar.
Esta opción puede especificarse repetidamente. Actualmente, existen los siguientes niveles de verbosidad:
•
0 “Solo errores”
Solo imprime mensajes que explican por qué falló la invocación de Nix.
•
1 “Informativo”
Imprime mensajes *útiles* sobre lo que está haciendo Nix. Este es el valor predeterminado.
•
2 “Hablador”
Imprime más mensajes informativos.
•
3 “Charla”
Imprime aún más mensajes informativos.
•
4 “Depuración”
Imprime información de depuración.
•
5 “Vómito”
Imprime una gran cantidad de información de depuración.
•
--quiet
Disminuye el nivel de verbosidad de
mensajes de diagnóstico impresos en la salida de error estándar. Esta es la opción inversa a -v / --verbose.
Esta opción puede especificarse repetidamente. Ver la lista de niveles de verbosidad anterior.
•
--log-format formato
Esta opción se puede usar para cambiar la salida del formato del registro, con formato siendo uno de:
•
raw
Este es el formato sin procesar, tal como lo genera nix-build.
•
internal-json
Genera los registros de manera estructurada.
Advertencia
Si bien el esquema en sí es relativamente estable, el formato de los mensajes de error (específicamente del campo msg) puede cambiar entre versiones.
•
bar
Solo muestra una barra de progreso durante las compilaciones.
•
bar-with-logs
Muestra los registros sin procesar, con la barra de progreso en la parte inferior.
•
--no-build-output / -Q
Por defecto, la salida escrita por los compiladores en la salida estándar y el error estándar se refleja en el error estándar del comando Nix. Esta opción suprime este comportamiento. Tenga en cuenta que la salida estándar y el error del compilador siempre se escriben en un archivo de registro en prefix/nix/var/log/nix.
•
--max-jobs / -j número
Establece el número máximo de trabajos de compilación que Nix realizará en paralelo al número especificado. Especifique auto para usar el número de CPUs en el sistema. El valor predeterminado es especificado por la configuración max-jobs, que a su vez tiene como valor predeterminado 1. Un valor más alto es útil en sistemas SMP o para explotar la latencia de E/S.
Establecerlo en 0 deshabilita la compilación en la máquina local, lo cual es útil cuando solo desea que las compilaciones ocurran en compiladores remotos.
•
--cores
Establece el valor de la variable de entorno NIX_BUILD_CORES en la invocación de los compiladores. Los compiladores pueden usar esta variable a su discreción para controlar el paralelismo máximo. Por ejemplo, en Nixpkgs, si el atributo de derivación enableParallelBuilding está establecido en true, el compilador pasa el flag -jN a GNU Make. Tiene como valor predeterminado el valor de la configuración cores, si está establecida, o 1 en caso contrario. El valor 0 significa que el compilador debe usar todos los núcleos de CPU disponibles en el sistema.
•
--max-silent-time
Establece el número máximo de segundos que un compilador puede pasar sin producir ningún dato en la salida estándar o el error estándar. El valor predeterminado es especificado por la configuración max-silent-time. 0 significa sin tiempo de espera.
•
--timeout
Establece el número máximo de segundos que un compilador puede ejecutarse. El valor predeterminado es especificado por la configuración timeout. 0 significa sin tiempo de espera.
•
--keep-going / -k
Continúa en caso de fallos en la compilación, en la mayor medida posible. Es decir, si la compilación de una entrada de alguna derivación falla, Nix aún compilará las otras entradas, pero no la derivación en sí. Sin esta opción, Nix se detiene si alguna compilación falla (excepto las compilaciones de sustitutos), posiblemente matando las compilaciones en curso (en caso de compilaciones paralelas o distribuidas).
•
--keep-failed / -K
Especifica que en caso de fallo de compilación, el directorio temporal (generalmente en /tmp) en el que se realiza la compilación no debe ser eliminado. La ruta del directorio de compilación se imprime como un mensaje informativo.
•
--fallback
Cada vez que Nix intenta compilar una derivación para la cual se conocen sustitutos para cada ruta de salida, pero la realización de las rutas de salida a través de los sustitutos falla, recurre a la compilación de la derivación.
El escenario más común en el que esto es útil es cuando hemos registrado sustitutos para realizar la distribución binaria desde, por ejemplo, un repositorio de red. Si el repositorio está caído, la realización de la derivación fallará. Cuando se especifica esta opción, Nix compilará la derivación en su lugar. Por lo tanto, la instalación desde binarios recurre a la instalación desde el código fuente. Esta opción no es la predeterminada ya que generalmente no es deseable que un fallo transitorio en la obtención de los sustitutos lleve a una compilación completa desde el código fuente (con el consumo relacionado de recursos).
•
--readonly-mode
Cuando se utiliza esta opción, no se intenta abrir la base de datos Nix. La mayoría de las operaciones de Nix necesitan acceso a la base de datos, por lo que esas operaciones fallarán.
•
--arg nombre valor
Esta opción es aceptada por nix-env, nix-instantiate, nix-shell y nix-build. Al evaluar expresiones Nix, el evaluador de expresiones intentará automáticamente llamar a las funciones que encuentra. Puede llamar automáticamente a funciones para las que cada argumento tiene un valor predeterminado (por ejemplo, { argName ? defaultValue }: ...).
Con --arg, también puedes llamar a funciones que tienen argumentos sin valor predeterminado (o anular un valor predeterminado). Es decir, si el evaluador encuentra una función con un argumento llamado nombre, la llamará con el valor valor.
Por ejemplo, el default.nix de nivel superior en Nixpkgs es en realidad una función:
{ # El sistema (por ejemplo, `i686-linux') para el que compilar los paquetes.
system ? builtins.currentSystem
...
}: ...
Entonces, si llamas a esta expresión Nix (por ejemplo, cuando haces nix-env --install --attr pkgname), la función se llamará automáticamente usando el valor builtins.currentSystem para el argumento system. Puedes anular esto usando --arg, por ejemplo, nix-env --install --attr pkgname --arg system \"i686-freebsd\". (Ten en cuenta que dado que el argumento es un literal de cadena Nix, debes escapar las comillas.)
•
--argstr nombre valor
Esta opción es como --arg, solo que el valor no es una expresión Nix sino una cadena. Así que en lugar de --arg system \"i686-linux\" (las comillas externas son para que el shell funcione correctamente) puedes decir --argstr system i686-linux.
•
--attr / -A rutaAttr
Selecciona un atributo de la expresión Nix de nivel superior que se está evaluando. (Solo nix-env, nix-instantiate, nix-build y nix-shell.) La ruta de atributo rutaAttr es una secuencia de nombres de atributos separados por puntos. Por ejemplo, dada una expresión Nix de nivel superior e, la ruta de atributo xorg.xorgserver haría que se utilizara la expresión e.xorg.xorgserver. Ver nix-env --install para algunos ejemplos concretos.
Además de los nombres de atributos, también puedes especificar índices de arreglos. Por ejemplo, la ruta de atributo foo.3.bar selecciona el atributo bar del cuarto elemento del arreglo en el atributo foo de la expresión de nivel superior.
•
--expr / -E
Interpreta los argumentos de la línea de comandos como una lista de expresiones Nix a ser analizadas y evaluadas, en lugar de como una lista de nombres de archivo de expresiones Nix. (Solo nix-instantiate, nix-build y nix-shell.)
Para nix-shell, esta opción se usa comúnmente para proporcionarte un shell en el que puedas compilar los paquetes devueltos por la expresión. Si deseas obtener un shell que contenga los paquetes *compilados* listos para usar, proporciona tu expresión a la bandera de conveniencia nix-shell --packages en su lugar.
>
•
-I / --include ruta
Añade una entrada a la lista de rutas de búsqueda que se utilizan para resolver rutas de búsqueda. Esta opción se puede indicar varias veces.
Las rutas añadidas a través de -I tienen prioridad sobre la configuración de `nix-path` y la variable de entorno `NIX_PATH` .
•
--option nombre valor
Establece la opción de configuración de Nix nombre a valor. Esto anula los ajustes en el archivo de configuración de Nix (véase nix.conf5).
•
--repair
Repara rutas de tienda corruptas o faltantes volviendo a descargarlas o reconstruyéndolas. Ten en cuenta que esto es lento porque requiere calcular un hash criptográfico del contenido de cada ruta en el cierre de la construcción. También ten en cuenta la advertencia en nix-store --repair-path.

Nota

Consulta man nix.conf para anular la configuración con flags de línea de comandos.

Variables de entorno

•
NIX_BUILD_SHELL
Shell utilizada para iniciar el entorno interactivo. Por defecto es la bash encontrada en <nixpkgs>, recurriendo a la bash encontrada en PATH si no se encuentra.

Variables de entorno comunes

La mayoría de los comandos de Nix interpretan las siguientes variables de entorno:

•
IN_NIX_SHELL
Indicador que señala si el entorno actual fue configurado por nix-shell. Puede tener los valores pure o impure.
•
NIX_PATH
Una lista separada por dos puntos de entradas de búsqueda utilizadas para resolver rutas de búsqueda.
Esta variable de entorno anula el valor de la configuración de `nix-path` .
Se puede extender usando la opción `-I` .
Ejemplo
$ export NIX_PATH=`/home/eelco/Dev:nixos-config=/etc/nixos
Si NIX_PATH se establece en una cadena vacía, la resolución de rutas de búsqueda siempre fallará.
Ejemplo
$ NIX_PATH= nix-instantiate --eval '<nixpkgs>'
error: file 'nixpkgs' was not found in the Nix search path (add it using $NIX_PATH or -I)
•
NIX_IGNORE_SYMLINK_STORE
Normalmente, el directorio de la tienda Nix (típicamente /nix/store) no tiene permitido contener componentes de enlace simbólico. Esto es para prevenir construcciones "impuras". Los constructores a veces "canonizan" las rutas resolviendo todos los componentes de enlace simbólico. Por lo tanto, las construcciones en diferentes máquinas (con /nix/store resolviendo a diferentes ubicaciones) podrían producir resultados diferentes. Esto generalmente no es un problema, excepto cuando las construcciones se implementan en máquinas donde /nix/store se resuelve de manera diferente. Si estás seguro de que no vas a hacer eso, puedes establecer NIX_IGNORE_SYMLINK_STORE a 1.
Ten en cuenta que si estás enlazando simbólicamente la tienda Nix para poder ponerla en un sistema de archivos diferente al del sistema de archivos raíz, en Linux es mejor usar puntos de montaje bind, por ejemplo:
$ mkdir /nix
$ mount -o bind /mnt/otherdisk/nix /nix
Consulta la página del manual de mount 8 para obtener detalles.
•
NIX_STORE_DIR
Anula la ubicación de la tienda Nix (por defecto prefix/store).
•
NIX_DATA_DIR
Anula la ubicación del directorio de datos estáticos de Nix (por defecto prefix/share).
•
NIX_LOG_DIR
Anula la ubicación del directorio de logs de Nix (por defecto prefix/var/log/nix).
•
NIX_STATE_DIR
Anula la ubicación del directorio de estado de Nix (por defecto prefix/var/nix).
•
NIX_CONF_DIR
Anula la ubicación del directorio de configuración del sistema Nix (por defecto prefix/etc/nix).
•
NIX_CONFIG
Aplica ajustes de la configuración de Nix desde el entorno. El contenido se trata como si se hubiera leído de un archivo de configuración de Nix. Los ajustes se separan por el carácter de nueva línea.
•
NIX_USER_CONF_FILES
Anula la ubicación de los archivos de configuración de usuario de Nix a cargar desde.
Los valores predeterminados son las ubicaciones según la Especificación de Directorios Base XDG . Consulta la subsección Directorios Base XDG para obtener detalles.
La variable se trata como una lista separada por el token :.
•
TMPDIR
Utiliza el directorio especificado para almacenar archivos temporales. En particular, esto incluye directorios de construcción temporales; estos pueden ocupar una cantidad sustancial de espacio en disco. El valor predeterminado es /tmp.
•
NIX_REMOTE
Esta variable debe establecerse en daemon si deseas utilizar el demonio Nix para ejecutar operaciones de Nix. Esto es necesario en instalaciones Nix multiusuario . Si el socket Unix del demonio Nix se encuentra en una ruta no estándar, esta variable debe establecerse en unix://ruta/al/socket. De lo contrario, debe dejarse sin definir.
•
NIX_SHOW_STATS
Si se establece en 1, Nix imprimirá algunas estadísticas de evaluación, como el número de valores asignados.
•
NIX_COUNT_CALLS
Si se establece en 1, Nix imprimirá cuántas veces se llamaron las funciones durante la evaluación de expresiones Nix. Esto es útil para perfilar tus expresiones Nix.
•
GC_INITIAL_HEAP_SIZE
Si Nix ha sido configurado para usar el recolector de basura de Boehm, esta variable establece el tamaño inicial del heap en bytes. Por defecto es 384 MiB. Establecerlo en un valor bajo reduce el consumo de memoria, pero aumentará el tiempo de ejecución debido a la sobrecarga de la recolección de basura.

Directorios Base XDG

Nix sigue la Especificación de Directorios Base XDG .

Por compatibilidad con versiones anteriores, los comandos de Nix seguirán el estándar solo cuando use-xdg-base-directories esté habilitado. Los comandos Nix nuevos (experimentales) cumplen con el estándar por defecto.

Las siguientes variables de entorno se utilizan para determinar las ubicaciones de varios archivos de estado y configuración:

  • [XDG_CONFIG_HOME]{#env-XDGCONFIGHOME} (por defecto ~/.config)
  • [XDG_STATE_HOME]{#env-XDGSTATEHOME} (por defecto ~/.local/state)
  • [XDG_CACHE_HOME]{#env-XDGCACHEHOME} (por defecto ~/.cache)

Ejemplos

nix-shell(1)

Name

nix-shell - Create a shell with specified packages or Nix expressions

Synopsis

nix-shell [-I pathname] [-p package...] [-E expression] [-L] [--run command] [--command command] [-Q] [-r] [--pure] [--drv-path] [--shell-file filename] [shell-file] [attribute-path]

Description

The nix-shell command creates an environment (usually a shell) where the specified packages are available.

The basic idea is that you can build packages in an environment that is guaranteed to contain all their build-time dependencies. This is achieved by using Nix to construct a development environment, which is then entered using nix-shell.

Options

-I pathname
Adds pathname to the Nix search path. This allows you to refer to Nix expressions in other locations. For example, -I nixpkgs=/path/to/nixpkgs makes the Nixpkgs channel available at the attribute nixpkgs.
-p package
Adds the specified package(s) to the build environment. The package names refer to attribute names in nixpkgs. This option can be used multiple times. You can also specify Nix expressions that evaluate to a package derivation.
-E expression
Evaluates the given Nix expression and uses its result. This is often used to create custom build environments. The expression should typically evaluate to a derivation.
-L
Display the phases of the derivation. This is useful for debugging build issues.
--run command
Runs the specified command in the created environment and then exits. This is useful for automating build tasks.
--command command
Similar to --run, but specifically runs a shell command. It can be used to execute arbitrary commands within the Nix environment.
-Q
Query the result of the Nix expression without entering a shell. Useful for inspecting derivations.
-r
Re-enter the shell. This option is typically used with --pure to create a clean environment.
--pure
Creates a minimal environment, removing most environment variables. This ensures that the build process depends only on Nix inputs.
--drv-path
Prints the derivation path instead of entering a shell.
--shell-file filename
Specifies a Nix expression file (a shell.nix file) to use for creating the environment.
shell-file
Specifies a Nix expression file (a shell.nix file) to use for creating the environment. This is a positional argument.
attribute-path
Specifies an attribute path within Nixpkgs to build and enter. For example, pkgs.hello.

Common Options

The following options are common to many Nix commands:

-I pathname
Add pathname to the Nix search path. This can be used multiple times. The Nix search path is a list of directories that Nix searches for input files, such as channel definitions or Nix expressions.
--option option=value
Set a Nix configuration option.

Environment variables

The following environment variables can affect nix-shell:

NIX_PATH
The Nix search path. This can be a colon-separated list of paths. For example, NIX_PATH=nixpkgs=/path/to/nixpkgs.
NIX_BUILD_CORES
The number of CPU cores to use for building packages. Defaults to the number of available cores.
NIX_DEBUG
If set, Nix will print debugging information to standard error.

Examples

To build the dependencies of the package Pan, and start an interactive shell in which to build it:

$ nix-shell '<nixpkgs>' --attr pan
[nix-shell]$ eval ${unpackPhase:-unpackPhase}
[nix-shell]$ cd $sourceRoot
[nix-shell]$ eval ${patchPhase:-patchPhase}
[nix-shell]$ eval ${configurePhase:-configurePhase}
[nix-shell]$ eval ${buildPhase:-buildPhase}
[nix-shell]$ ./pan/gui/pan

The reason we use form eval ${configurePhase:-configurePhase} here is because those packages that override these phases do so by exporting the overridden values in the environment variable of the same name. Here bash is being told to either evaluate the contents of ‘configurePhase’, if it exists as a variable, otherwise evaluate the configurePhase function.

To clear the environment first, and do some additional automatic initialisation of the interactive shell:

$ nix-shell '<nixpkgs>' --attr pan --pure \
                        --command 'export NIX_DEBUG=1; export NIX_CORES=8; return'

Nix expressions can also be given on the command line using the -E and -p flags. For instance, the following starts a shell containing the packages sqlite and libX11:

$ nix-shell --expr 'with import <nixpkgs> { }; runCommand "dummy" { buildInputs = [ sqlite xorg.libX11 ]; } ""'

A shorter way to do the same is:

$ nix-shell --packages sqlite xorg.libX11
[nix-shell]$ echo $NIX_LDFLAGS
… -L/nix/store/j1zg5v…-sqlite-3.8.0.2/lib -L/nix/store/0gmcz9…-libX11-1.6.1/lib …

Note that -p accepts multiple full nix expressions that are valid in the buildInputs = [ ... ] shown above, not only package names. So the following is also legal:

$ nix-shell --packages sqlite 'git.override { withManual = false; }'

The -p flag looks up Nixpkgs in the Nix search path. You can override it by passing -I or setting NIX_PATH. For example, the following gives you a shell containing the Pan package from a specific revision of Nixpkgs:

$ nix-shell --packages pan -I nixpkgs=https://github.com/NixOS/nixpkgs/archive/8a3eea054838b55aca962c3fbde9c83c102b8bf2.tar.gz
[nix-shell:~]$ pan --version
Pan 0.139

Use as a #!-interpreter

You can use nix-shell as a script interpreter to allow scripts written in arbitrary languages to obtain their own dependencies via Nix. This is done by starting the script with the following lines:

#! /usr/bin/env nix-shell
#! nix-shell -i real-interpreter --packages packages

where real-interpreter is the “real” script interpreter that will be invoked by nix-shell after it has obtained the dependencies and initialised the environment, and packages are the attribute names of the dependencies in Nixpkgs.

The lines starting with #! nix-shell specify nix-shell options (see above). Note that you cannot write #! /usr/bin/env nix-shell -i ... because many operating systems only allow one argument in #! lines.

For example, here is a Python script that depends on Python and the prettytable package:

#! /usr/bin/env nix-shell
#! nix-shell -i python3 --packages python3 python3Packages.prettytable
import prettytable
# Print a simple table.
t = prettytable.PrettyTable(["N", "N^2"])
for n in range(1, 10): t.add_row([n, n * n])
print(t)

Similarly, the following is a Perl script that specifies that it requires Perl and the HTML::TokeParser::Simple and LWP packages:

#! /usr/bin/env nix-shell
#! nix-shell -i perl --packages perl perlPackages.HTMLTokeParserSimple perlPackages.LWP
use HTML::TokeParser::Simple;
# Fetch nixos.org and print all hrefs.
my $p = HTML::TokeParser::Simple->new(url => 'http://nixos.org/');
while (my $token = $p->get_tag("a")) {
    my $href = $token->get_attr("href");
    print "$href\n" if $href;
}

Sometimes you need to pass a simple Nix expression to customize a package like Terraform:

#! /usr/bin/env nix-shell
#! nix-shell -i bash --packages 'terraform.withPlugins (plugins: [ plugins.openstack ])'
terraform apply

Note

You must use single or double quotes (', ") when passing a simple Nix expression in a nix-shell shebang.

Finally, using the merging of multiple nix-shell shebangs the following Haskell script uses a specific branch of Nixpkgs/NixOS (the 20.03 stable branch):

#! /usr/bin/env nix-shell
#! nix-shell -i runghc --packages 'haskellPackages.ghcWithPackages (ps: [ps.download-curl ps.tagsoup])'
#! nix-shell -I nixpkgs=https://github.com/NixOS/nixpkgs/archive/nixos-20.03.tar.gz
import Network.Curl.Download
import Text.HTML.TagSoup
import Data.Either
import Data.ByteString.Char8 (unpack)
-- Fetch nixos.org and print all hrefs.
main = do
  resp <- openURI "https://nixos.org/"
  let tags = filter (isTagOpenName "a") $ parseTags $ unpack $ fromRight undefined resp
  let tags' = map (fromAttrib "href") tags
  mapM_ putStrLn $ filter (/= "") tags'

If you want to be even more precise, you can specify a specific revision of Nixpkgs:

#! nix-shell -I nixpkgs=https://github.com/NixOS/nixpkgs/archive/0672315759b3e15e2121365f067c1c8c56bb4722.tar.gz

The examples above all used -p to get dependencies from Nixpkgs. You can also use a Nix expression to build your own dependencies. For example, the Python example could have been written as:

#! /usr/bin/env nix-shell
#! nix-shell deps.nix -i python

where the file deps.nix in the same directory as the #!-script contains:

with import <nixpkgs> {};
runCommand "dummy" { buildInputs = [ python pythonPackages.prettytable ]; } ""

The script’s file name is passed as the first argument to the interpreter specified by the -i flag.

Aside from the very first line, which is a directive to the operating system, the additional #! nix-shell lines do not need to be at the beginning of the file. This allows wrapping them in block comments for languages where # does not start a comment, such as ECMAScript, Erlang, PHP, or Ruby.
