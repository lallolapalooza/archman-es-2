Nombre

nix flake - administrar flujos de Nix

Sinopsis

nix flake [opción…] subcomando

donde subcomando es uno de los siguientes:

  • nix flake archive - copiar un flujo y todas sus entradas a la tienda
  • nix flake check - verificar si el flujo se evalúa y ejecutar sus pruebas
  • nix flake clone - clonar el repositorio del flujo
  • nix flake info - mostrar metadatos del flujo
  • nix flake init - crear un flujo en el directorio actual a partir de una plantilla
  • nix flake lock - crear entradas faltantes en el archivo de bloqueo
  • nix flake metadata - mostrar metadatos del flujo
  • nix flake new - crear un flujo en el directorio especificado a partir de una plantilla
  • nix flake prefetch - descargar el árbol de origen denotado por una referencia de flujo a la tienda Nix
  • nix flake show - mostrar las salidas proporcionadas por un flujo
  • nix flake update - actualizar el archivo de bloqueo del flujo

Descripción

nix flake proporciona subcomandos para crear, modificar y consultar flujos de Nix. Los flujos son la unidad para empaquetar código Nix de manera reproducible y descubrible. Pueden tener dependencias de otros flujos, lo que permite tener proyectos Nix multirepositorio.

Un flujo es un árbol de archivos (típicamente obtenido de un repositorio Git o un archivo tar) que contiene un archivo llamado flake.nix en el directorio raíz. flake.nix especifica metadatos sobre el flujo, como dependencias (llamadas entradas), así como sus salidas (los valores Nix como paquetes o módulos NixOS proporcionados por el flujo).

Referencias de Flujos

Las referencias de flujos (flakerefs) son una forma de especificar la ubicación de un flujo. Estas tienen dos formas diferentes:

Representación de conjunto de atributos

Ejemplo:

{
  type = "github";
  owner = "NixOS";
  repo = "nixpkgs";
}

El único atributo requerido es type. Los tipos soportados se listan a continuación.

Sintaxis similar a URL

Ejemplo:

github:NixOS/nixpkgs

Estas se usan en la línea de comandos como una alternativa más conveniente a la representación de conjunto de atributos. Por ejemplo, en el comando

# nix build github:NixOS/nixpkgs#hello

github:NixOS/nixpkgs es una referencia de flujo (mientras que hello es un atributo de salida). También se permiten en el atributo inputs de un flujo, p.ej.

inputs.nixpkgs.url = "github:NixOS/nixpkgs";

es equivalente a

inputs.nixpkgs = {
  type = "github";
  owner = "NixOS";
  repo = "nixpkgs";
};

Siguiendo RFC 3986, los caracteres fuera del rango permitido (es decir, ni caracteres reservados ni caracteres no reservados) deben estar codificados en porcentaje.

Ejemplos

Aquí hay algunos ejemplos de referencias de flujos en su representación similar a URL:

  • nixpkgs: La entrada nixpkgs en el registro de flujos.
  • nixpkgs/a3a3dda3bacf61e8a39258a0ed9c924eeca8e293: La entrada nixpkgs en el registro de flujos, con su revisión Git anulada a un valor específico.
  • github:NixOS/nixpkgs: La rama master del repositorio NixOS/nixpkgs en GitHub.
  • github:NixOS/nixpkgs/nixos-20.09: La rama nixos-20.09 del repositorio nixpkgs.
  • github:NixOS/nixpkgs/a3a3dda3bacf61e8a39258a0ed9c924eeca8e293: Una revisión específica del repositorio nixpkgs.
  • github:edolstra/nix-warez?dir=blender: Un flujo en un subdirectorio de un repositorio de GitHub.
  • git+https://github.com/NixOS/patchelf: Un repositorio Git.
  • git+https://github.com/NixOS/patchelf?ref=master: Una rama específica de un repositorio Git.
  • git+https://github.com/NixOS/patchelf?ref=master&rev=f34751b88bd07d7f44f5cd3200fb4122bf916c7e: Una rama específica y una revisión de un repositorio Git.
  • https://github.com/NixOS/patchelf/archive/master.tar.gz: Un flujo en un archivo tar.

Sintaxis similar a ruta

Los flujos correspondientes a una ruta local también pueden ser referidos por una referencia de ruta directa, ya sea /ruta/absoluta/al/flujo o./ruta/relativa/al/flujo. Tenga en cuenta que el prefijo ./ es obligatorio para rutas relativas. Si se omite, la ruta se interpretará como sintaxis similar a URL, lo que provocará mensajes de error como este:

error: no se puede encontrar el flujo 'flake:ruta/relativa/al/flujo' en los registros de flujos

La semántica de dicha ruta es la siguiente:

  • Si el directorio es parte de un repositorio Git, entonces la entrada se tratará como una URL git+file:, de lo contrario, se tratará como una URL path:;
  • Si el directorio no contiene un archivo flake.nix, entonces Nix buscará dicho archivo hacia arriba en la jerarquía del sistema de archivos hasta que encuentre alguna de las siguientes opciones:
1.
La raíz del repositorio Git, o
2.
La raíz del sistema de archivos (/), o
3.
Una carpeta en un punto de montaje diferente.

A diferencia de las referencias tipo URL, las referencias de flujo tipo ruta pueden contener caracteres unicode arbitrarios (excepto # y ?).

Ejemplos

  • .: El flujo al que pertenece el directorio actual.
  • /home/alice/src/patchelf: Un flujo en algún otro directorio.
  • ./../sub directorio/con Ûñî©ôδ€: Un flujo en otro directorio relativo que tiene caracteres Unicode en su nombre.

Flake References

A flake reference is a string that specifies how to obtain a flake. These can be used in Nix commands such as nix build, nix run, and nix flake install, and in flake inputs in flake.nix files.

A flake reference can be one of the following types:

•
flake:: flake: references are a special form of indirect flake reference. They are used to specify flakes by their flake ID. The ID is looked up in the user's flake registry, and the corresponding flake URI is used.
flake:<flake-id>(/<rev-or-ref>)?

For example, flake:nixpkgs refers to the flake identified by nixpkgs in the registry. flake:nixpkgs/nixos-unstable refers to the nixpkgs flake, but explicitly requests the branch nixos-unstable.

•
path:: Local directories. The required attribute path specifies the path of the flake.
path:<path>(\?<params>)?

path must be an absolute path to a directory containing a flake.nix file. If the flake is not inside a git repository, the path: prefix is implied and can be omitted.

On the command line, path can be a relative path (e.g. . or ./foo) which is interpreted as relative to the current directory. In this case, it must start with . to avoid ambiguity with registry lookups (e.g. nixpkgs is a registry lookup; ./nixpkgs is a relative path).

For example, these are valid path flake references:

  • path:/home/user/sub/dir
  • /home/user/sub/dir (if dir/flake.nix is not in a git repository)
  • ./sub/dir (when used on the command line and dir/flake.nix is not in a git repository)
•
git:: Git repositories. The location of the repository is specified by the attribute url.
git(+http|+https|+ssh|+git|+file):(//<server>)?<path>(\?<params>)?

If path starts with / (or ./ when used as an argument on the command line) and is a local path to a git repository, the leading git: or +file prefixes are implied and can be omitted.

The ref attribute defaults to resolving the HEAD reference. The rev attribute must denote a commit that exists in the branch or tag specified by the ref attribute, since Nix doesn’t do a full clone of the remote repository by default (and the Git protocol doesn’t allow fetching a rev without a known ref).

When git+file is used without specifying ref or rev, files are fetched directly from the local path as long as they have been added to the Git repository. If there are uncommitted changes, the reference is treated as dirty and a warning is printed.

For example, the following are valid Git flake references:

  • git:/home/user/sub/dir
  • /home/user/sub/dir (if dir/flake.nix is in a git repository)
  • ./sub/dir (when used on the command line and dir/flake.nix is in a git repository)
  • git+https://example.org/my/repo
  • git+https://example.org/my/repo?dir=flake1
  • git+ssh://git@github.com/NixOS/nix?ref=v1.2.3
  • git://github.com/edolstra/dwarffs?ref=unstable&rev=e486d8d40e626a20e06d792db8cc5ac5aba9a5b4
  • git+file:///home/my-user/some-repo/some-repo
•
github:: A more efficient way to fetch repositories from GitHub. The following attributes are required:
  • owner: The owner of the repository.
  • repo: The name of the repository.

These are downloaded as tarball archives, rather than through Git. This is often much faster and uses less disk space since it doesn’t require fetching the entire history of the repository.

The URL syntax for github: flakes is:

github:<owner>/<repo>(/<rev-or-ref>)?(\?<params>)?

<rev-or-ref> specifies the name of a branch or tag (ref), or a commit hash (rev).

You can also specify host as a parameter, to point to a custom GitHub Enterprise server.

Some examples:

  • github:edolstra/dwarffs
  • github:edolstra/dwarffs/unstable
  • github:edolstra/dwarffs/d3f2baba8f425779026c6ec04021b2e927f61e31
  • github:internal/project?host=company-github.example.org
•
gitlab:: Similar to github:, is a more efficient way to fetch GitLab repositories. The following attributes are required:
  • owner: The owner of the repository.
  • repo: The name of the repository.

Like github:, these are downloaded as tarball archives.

The URL syntax for gitlab: flakes is:

gitlab:<owner>/<repo>(/<rev-or-ref>)?(\?<params>)?
•
tarball:: Tarballs. The location of the tarball is specified by the attribute url.
tarball+http://example.com/flake.tar.gz

If the extension corresponds to a known archive format (e.g. .zip, .tar.gz), then the tarball+ prefix can be dropped.

This can also be used to set the location of gitea/forgejo branches. See here.

•
file:: Plain files or directory tarballs, either over http(s) or from the local disk.
file+http://example.com/file.txt
file:///home/user/file.txt

If the extension doesn’t correspond to a known archive format (as defined by the tarball fetcher), then the file+ prefix can be dropped.

The following optional parameters can be specified:

  • dir: The subdirectory of the flake in which flake.nix is located. This parameter enables having multiple flakes in a repository or tarball. The default is the root directory of the flake.
  • narHash: The hash of the Nix Archive (NAR) serialisation (in SRI format) of the contents of the flake. This is useful for flake types such as tarballs that lack a unique content identifier such as a Git commit hash.

In addition, the following attributes are common to several flake reference types:

  • rev: A Git or Mercurial commit hash.
  • ref: A Git or Mercurial branch or tag name.

Finally, some attribute are typically not specified by the user, but can occur in locked flake references and are available to Nix code:

  • revCount: The number of ancestors of the commit rev.
  • lastModified: The timestamp (in seconds since the Unix epoch) of the last modification of this version of the flake. For Git/Mercurial flakes, this is the commit time of commit rev, while for tarball flakes, it’s the most recent timestamp of any file inside the tarball.

Types

Currently the type attribute can be one of the following:

•
indirect: The default. Indirection through the flake registry. These have the form
[flake:]<flake-id>(/<rev-or-ref>(/rev)?)?
These perform a lookup of <flake-id> in the flake registry. For example, nixpkgs and nixpkgs/release-20.09 are indirect flake references. The specified rev and/or ref are merged with the entry in the registry; see nix registry for details.
For example, these are valid indirect flake references:
  • nixpkgs
  • nixpkgs/nixos-unstable
  • nixpkgs/a3a3dda3bacf61e8a39258a0ed9c924eeca8e293
  • nixpkgs/nixos-unstable/a3a3dda3bacf61e8a39258a0ed9c924eeca8e293
  • sub/dir (if a flake named sub is in the registry)
•
path: arbitrary local directories. The required attribute path specifies the path of the flake. The URL form is
path:<path>(\?<params>)?
where path is an absolute path to a directory in the file system containing a file named flake.nix.
If the flake at path is not inside a git repository, the path: prefix is implied and can be omitted.
path generally must be an absolute path. However, on the command line, it can be a relative path (e.g. . or ./foo) which is interpreted as relative to the current directory. In this case, it must start with . to avoid ambiguity with registry lookups (e.g. nixpkgs is a registry lookup; ./nixpkgs is a relative path).
For example, these are valid path flake references:
  • path:/home/user/sub/dir
  • /home/user/sub/dir (if dir/flake.nix is not in a git repository)
  • ./sub/dir (when used on the command line and dir/flake.nix is not in a git repository)
•
git: Git repositories. The location of the repository is specified by the attribute url.
They have the URL form
git(+http|+https|+ssh|+git|+file):(//<server>)?<path>(\?<params>)?
If path starts with / (or ./ when used as an argument on the command line) and is a local path to a git repository, the leading git: or +file prefixes are implied and can be omitted.
The ref attribute defaults to resolving the HEAD reference.
The rev attribute must denote a commit that exists in the branch or tag specified by the ref attribute, since Nix doesn’t do a full clone of the remote repository by default (and the Git protocol doesn’t allow fetching a rev without a known ref). The default is the commit currently pointed to by ref.
When git+file is used without specifying ref or rev, files are fetched directly from the local path as long as they have been added to the Git repository. If there are uncommitted changes, the reference is treated as dirty and a warning is printed.
For example, the following are valid Git flake references:
  • git:/home/user/sub/dir
  • /home/user/sub/dir (if dir/flake.nix is in a git repository)
  • ./sub/dir (when used on the command line and dir/flake.nix is in a git repository)
  • git+https://example.org/my/repo
  • git+https://example.org/my/repo?dir=flake1
  • git+ssh://git@github.com/NixOS/nix?ref=v1.2.3
  • git://github.com/edolstra/dwarffs?ref=unstable&rev=e486d8d40e626a20e06d792db8cc5ac5aba9a5b4
  • git+file:///home/my-user/some-repo/some-repo
  • mercurial: Mercurial repositories. The URL form is similar to the git type, except that the URL schema must be one of hg+http, hg+https, hg+ssh or hg+file.
  • tarball: Tarballs. The location of the tarball is specified by the attribute url.
In URL form, the schema must be tarball+http://, tarball+https:// or tarball+file://. If the extension corresponds to a known archive format (.zip, .tar, .tgz, .tar.gz, .tar.xz, .tar.bz2 or .tar.zst), then the tarball+ can be dropped.
This can also be used to set the location of gitea/forgejo branches. See here
•
file: Plain files or directory tarballs, either over http(s) or from the local disk.
In URL form, the schema must be file+http://, file+https:// or file+file://. If the extension doesn’t correspond to a known archive format (as defined by the tarball fetcher), then the file+ prefix can be dropped.
•
github: A more efficient way to fetch repositories from GitHub. The following attributes are required:
  • owner: The owner of the repository.
  • repo: The name of the repository.
These are downloaded as tarball archives, rather than through Git. This is often much faster and uses less disk space since it doesn’t require fetching the entire history of the repository. On the other hand, it doesn’t allow incremental fetching (but full downloads are often faster than incremental fetches!).
The URL syntax for github flakes is:

<rev-or-ref> specifies the name of a branch or tag (ref), or a commit hash (rev). Note that unlike Git, GitHub allows fetching by commit hash without specifying a branch or tag.
You can also specify host as a parameter, to point to a custom GitHub Enterprise server.
Some examples:

•

  • owner: The owner of the repository.
  • repo: The name of the repository.
Like github, these are downloaded as tarball archives.

Formato de Flake

Como ejemplo, aquí hay una simple flake.nix que depende de la flake de Nixpkgs y proporciona un solo paquete (es decir, una derivación instalable):

{
  description = "Una flake para construir Hola Mundo";
  inputs.nixpkgs.url = "github:NixOS/nixpkgs/nixos-20.03";
  outputs = { self, nixpkgs }: {
    packages.x86_64-linux.default =
      # Nótese la referencia a nixpkgs aquí.
      with import nixpkgs { system = "x86_64-linux"; };
      stdenv.mkDerivation {
        name = "hello";
        src = self;
        buildPhase = "gcc -o hello ./hello.c";
        installPhase = "mkdir -p $out/bin; install -t $out/bin hello";
      };
  };
}

Los siguientes atributos son compatibles en flake.nix:

  • description: Una descripción corta de una línea de la flake.
  • inputs: Un attrset que especifica las dependencias de la flake (descrito a continuación).
  • outputs: Una función que, dado un conjunto de atributos que contiene las salidas de cada una de las flakes de entrada indexadas por su identificador, produce los valores de Nix proporcionados por esta flake. Por lo tanto, en el ejemplo anterior, inputs.nixpkgs contiene el resultado de la llamada a la función outputs de la flake nixpkgs.
Además de las salidas de cada entrada, cada entrada en inputs también contiene algunos metadatos sobre las entradas. Estos son:
  • outPath: La ruta en el almacén de Nix del árbol de fuentes de la flake. De esta manera, el conjunto de atributos puede pasarse a import como si fuera una ruta, como en el ejemplo anterior (import nixpkgs).
  • rev: El hash de commit del repositorio de la flake, si es aplicable.
  • revCount: El número de ancestros de la revisión rev. Esto no está disponible para repositorios de github, ya que se obtienen como tarballs en lugar de como repositorios Git.
  • lastModifiedDate: La fecha de commit de la revisión rev, en el formato %Y%m%d%H%M%S (ej. 20181231100934). A diferencia de revCount, esto está disponible tanto para repositorios Git como de GitHub, por lo que es útil para generar cadenas de versión (con suerte) monótonamente crecientes.
  • lastModified: La fecha de commit de la revisión rev como un entero que denota el número de segundos desde 1970.
  • narHash: El SHA-256 (en formato SRI) de la serialización del Archivo Nix (NAR) del árbol de fuentes de la flake.
El valor devuelto por la función outputs debe ser un conjunto de atributos. Los atributos pueden tener valores arbitrarios; sin embargo, varios subcomandos de nix requieren que atributos específicos tengan un valor específico (por ejemplo, packages.x86_64-linux debe ser un conjunto de atributos de derivaciones construidas para la plataforma x86_64-linux).
•
nixConfig: un conjunto de opciones de nix.conf que se establecerán al evaluar cualquier parte de una flake. En aras de la seguridad, solo un pequeño conjunto de opciones está permitido establecer sin confirmación siempre que accept-flake-config no esté habilitado en la configuración global:
  • bash-prompt
  • bash-prompt-prefix
  • bash-prompt-suffix
  • flake-registry
  • commit-lock-file-summary

Entradas de Flake

El atributo inputs especifica las dependencias de una flake, como un attrset que mapea nombres de entrada a referencias de flake. Por ejemplo, lo siguiente especifica una dependencia de los repositorios nixpkgs e import-cargo:

# Un repositorio de GitHub.
inputs.import-cargo = {
  type = "github";
  owner = "edolstra";
  repo = "import-cargo";
};
# Una indirecta a través del registro de flakes.
inputs.nixpkgs = {
  type = "indirect";
  id = "nixpkgs";
};

Alternativamente, puedes usar la sintaxis similar a URL:

inputs.import-cargo.url = "github:edolstra/import-cargo";
inputs.nixpkgs.url = "nixpkgs";

Cada entrada se obtiene, evalúa y se pasa a la función outputs como un conjunto de atributos con el mismo nombre que la entrada correspondiente. La entrada especial llamada self se refiere a las salidas y al árbol de fuentes de *esta* flake. Por lo tanto, una función outputs típica se ve así:

outputs = { self, nixpkgs, import-cargo }: {
  ... outputs ...
};

También es posible omitir una entrada por completo y solo listarla como argumento de función esperado para outputs. Por lo tanto,

outputs = { self, nixpkgs }: ...;

sin el atributo inputs.nixpkgs es equivalente a

inputs.nixpkgs = {
  type = "indirect";
  id = "nixpkgs";
};

Los repositorios que no contienen un flake.nix también pueden usarse como entradas, estableciendo el atributo flake de la entrada a false:

inputs.grcov = {
  type = "github";
  owner = "mozilla";
  repo = "grcov";
  flake = false;
};
outputs = { self, nixpkgs, grcov }: {
  packages.x86_64-linux.grcov = stdenv.mkDerivation {
    src = grcov;
    ...
  };
};

Las entradas transitivas pueden ser anuladas desde un archivo flake.nix. Por ejemplo, lo siguiente anula la entrada nixpkgs de la entrada nixops:

inputs.nixops.inputs.nixpkgs = {
  type = "github";
  owner = "my-org";
  repo = "nixpkgs";
};

También es posible "heredar" una entrada de otra entrada. Esto es útil para minimizar las dependencias de flakes. Por ejemplo, lo siguiente establece la entrada nixpkgs de la flake de nivel superior para que sea igual a la entrada nixpkgs de la entrada dwarffs de la flake de nivel superior:

inputs.nixpkgs.follows = "dwarffs/nixpkgs";

Inputs

The value of the follows attribute is a /-separated sequence of input names denoting the path of inputs to be followed from the root flake.

Overrides and follows can be combined, e.g.

inputs.nixops.inputs.nixpkgs.follows = "dwarffs/nixpkgs";

sets the nixpkgs input of nixops to be the same as the nixpkgs input of dwarffs. It is worth noting, however, that it is generally not useful to eliminate transitive nixpkgs flake inputs in this way. Most flakes provide their functionality through Nixpkgs overlays or NixOS modules, which are composed into the top-level flake’s nixpkgs input; so their own nixpkgs input is usually irrelevant.

Archivos de bloqueo

Los inputs especificados en flake.nix son típicamente "desbloqueados" en el sentido de que no especifican una revisión exacta. Para garantizar la reproducibilidad, Nix generará y usará automáticamente un *archivo de bloqueo* llamado flake.lock en el directorio del flake. El archivo de bloqueo contiene una estructura de grafo isomorfa al grafo de dependencias del flake raíz. Cada nodo en el grafo (excepto el nodo raíz) mapea las especificaciones de entrada (generalmente desbloqueadas) en flake.nix a especificaciones de entrada bloqueadas. Cada nodo también contiene metadatos, como las dependencias (aristas salientes) del nodo.

Por ejemplo, si flake.nix tiene los inputs del ejemplo anterior, el archivo de bloqueo resultante podría ser:

{
  "version": 7,
  "root": "n1",
  "nodes": {
    "n1": {
      "inputs": {
        "nixpkgs": "n2",
        "import-cargo": "n3",
        "grcov": "n4"
      }
    },
    "n2": {
      "inputs": {},
      "locked": {
        "owner": "edolstra",
        "repo": "nixpkgs",
        "rev": "7f8d4b088e2df7fdb6b513bc2d6941f1d422a013",
        "type": "github",
        "lastModified": 1580555482,
        "narHash": "sha256-OnpEWzNxF/AU4KlqBXM2s5PWvfI5/BS6xQrPvkF5tO8="
      },
      "original": {
        "id": "nixpkgs",
        "type": "indirect"
      }
    },
    "n3": {
      "inputs": {},
      "locked": {
        "owner": "edolstra",
        "repo": "import-cargo",
        "rev": "8abf7b3a8cbe1c8a885391f826357a74d382a422",
        "type": "github",
        "lastModified": 1567183309,
        "narHash": "sha256-wIXWOpX9rRjK5NDsL6WzuuBJl2R0kUCnlpZUrASykSc="
      },
      "original": {
        "owner": "edolstra",
        "repo": "import-cargo",
        "type": "github"
      }
    },
    "n4": {
      "inputs": {},
      "locked": {
        "owner": "mozilla",
        "repo": "grcov",
        "rev": "989a84bb29e95e392589c4e73c29189fd69a1d4e",
        "type": "github",
        "lastModified": 1580729070,
        "narHash": "sha256-235uMxYlHxJ5y92EXZWAYEsEb6mm+b069GAd+BOIOxI="
      },
      "original": {
        "owner": "mozilla",
        "repo": "grcov",
        "type": "github"
      },
      "flake": false
    }
  }
}

Este grafo tiene 4 nodos: el flake raíz y sus 3 dependencias. Los nodos tienen etiquetas arbitrarias (por ejemplo, n1). La etiqueta del nodo raíz del grafo está especificada por el atributo root. Los nodos contienen los siguientes campos:

  • inputs: Las dependencias de este nodo, como un mapeo de nombres de input (por ejemplo, nixpkgs) a etiquetas de nodo (por ejemplo, n2).
  • original: La especificación de input original de flake.lock, como un conjunto de argumentos de builtins.fetchTree.
  • locked: La especificación de input bloqueada, como un conjunto de argumentos de builtins.fetchTree. Por lo tanto, en el ejemplo anterior, cuando construimos este flake, el input nixpkgs se mapea a la revisión 7f8d4b088e2df7fdb6b513bc2d6941f1d422a013 del repositorio edolstra/nixpkgs en GitHub.
También incluye el atributo narHash, que especifica el contenido esperado del árbol en la tienda Nix (calculado por nix hash-path), y puede incluir atributos específicos del tipo de input, como lastModified o revCount. La razón principal de estos atributos es permitir que los inputs de los flakes se sustituyan desde una caché binaria: narHash permite calcular la ruta de la tienda, mientras que los otros atributos son necesarios porque proporcionan información que no se almacena en la ruta de la tienda.
•
flake: Un booleano que indica si es una dependencia de tipo flake o no flake. Corresponde al atributo flake en el atributo inputs en flake.nix.

Los atributos original y locked se omiten para el nodo raíz. Esto se debe a que no podemos registrar el hash del commit o el hash de contenido del flake raíz, ya que modificar flake.lock invalidará estos.

La representación en grafo de los archivos de bloqueo permite dependencias circulares entre flakes. Por ejemplo, aquí hay dos flakes que se referencian mutuamente:

{
  inputs.b = ... ubicación del flake B ...;
  # Indicar al flake 'b' que no obtenga 'a' de nuevo, para asegurar que su 'a' sea
  # *este* 'a'.
  inputs.b.inputs.a.follows = "";
  outputs = { self, b }: {
    foo = 123 + b.bar;
    xyzzy = 1000;
  };
}

y

{
  inputs.a = ... ubicación del flake A ...;
  inputs.a.inputs.b.follows = "";
  outputs = { self, a }: {
    bar = 456 + a.xyzzy;
  };
}

Los archivos de bloqueo bloquean transitivamente tanto las dependencias directas como las indirectas. Es decir, si existe un archivo de bloqueo y está actualizado, Nix no mirará los archivos de bloqueo de las dependencias. Sin embargo, la generación del archivo de bloqueo en sí misma *sí* utiliza los archivos de bloqueo de las dependencias por defecto.

Opciones

Opciones relacionadas con el registro

•
--debug
Establece el nivel de verbosidad del registro en 'debug'.
•
--log-format formato
Establece el formato de la salida del registro; uno de raw, internal-json, bar o bar-with-logs.
•
--print-build-logs / -L
Imprime los registros de construcción completos en la salida de error estándar.
•
--quiet
Disminuye el nivel de verbosidad del registro.
•
--verbose / -v
Aumenta el nivel de verbosidad del registro.

Opciones globales misceláneas

•
--help
Muestra información de uso.
•
--offline
Deshabilita los sustitutos y considera que todos los archivos descargados previamente están actualizados.
•
--option nombre valor
Establece la configuración de Nix nombre a valor (anulando nix.conf).
•
--refresh
Considera que todos los archivos descargados previamente están obsoletos.
•
--version
Muestra información de la versión.
