nix-instantiate(1)

Paquete: nix

Licencias: LGPL-2.1-only

nix-instantiate(1) Manual de Comandos Generales nix-instantiate(1)

Nombre

nix-instantiate - instancia derivaciones del almacén a partir de expresiones Nix

Sinopsis

nix-instantiate [--parse | --eval [--strict] [--json] [--xml] ] [--read-write-mode] [--arg nombre valor] [{--attr| -A} rutaAttr] [--add-root ruta] [--expr | -E] archivos…

nix-instantiate --find-file archivos…

Descripción

El comando nix-instantiate produce derivaciones del almacén a partir de expresiones Nix (de alto nivel). Evalúa las expresiones Nix en cada uno de los archivos (que por defecto es ./default.nix). Cada expresión de nivel superior debe evaluarse como una derivación, una lista de derivaciones o un conjunto de derivaciones. Las rutas de las derivaciones del almacén resultantes se imprimen en la salida estándar.

Si archivos es el carácter -, entonces se leerá una expresión Nix de la entrada estándar.

Opciones

•
--add-root ruta
Ver la opción correspondiente en nix-store.
•
--parse
Simplemente analiza los archivos de entrada e imprime sus árboles de sintaxis abstracta en la salida estándar como una expresión Nix.
•
--eval
Simplemente analiza y evalúa los archivos de entrada, e imprime los valores resultantes en la salida estándar. No se realiza la instanciación de derivaciones del almacén.
Advertencia
Esta opción produce una salida que puede ser analizada como una expresión Nix que producirá un resultado diferente de la expresión de entrada cuando se evalúe. Por ejemplo, estas dos expresiones Nix imprimen el mismo resultado a pesar de tener un significado diferente:
$ nix-instantiate --eval --expr '{ a = {}; }'
{ a = <CÓDIGO>; }
$ nix-instantiate --eval --expr '{ a = <CÓDIGO>; }'
{ a = <CÓDIGO>; }
Para una salida legible por humanos, nix eval (experimental) es más informativa:
$ nix-instantiate --eval --expr 'a: a'
<LAMBDA>
$ nix eval --expr 'a: a'
«lambda @ «cadena»:1:1»
Para una salida legible por máquina, la opción --xml produce una salida sin ambigüedades:
$ nix-instantiate --eval --xml --expr '{ foo = <CÓDIGO>; }'
<?xml version='1.0' encoding='utf-8'?>
<expr>
  <attrs>
    <attr column="3" line="1" name="foo">
      <unevaluated />
    </attr>
  </attrs>
</expr>
•
--find-file
Busca los archivos dados en la ruta de búsqueda de Nix (como se especifica en la variable de entorno NIX_PATH). Si se encuentran, imprime las rutas absolutas correspondientes en la salida estándar. Por ejemplo, si NIX_PATH es nixpkgs=/home/alice/nixpkgs, entonces nix-instantiate --find-file nixpkgs/default.nix imprimirá /home/alice/nixpkgs/default.nix.
•
--strict
Cuando se usa con --eval, evalúa recursivamente los elementos de lista y los atributos. Normalmente, tales subexpresiones se dejan sin evaluar (ya que el lenguaje Nix es perezoso).
Advertencia
Esta opción puede causar no terminación, porque las estructuras de datos perezosas pueden ser infinitamente grandes.
•
--json
Cuando se usa con --eval, imprime el valor resultante como una representación JSON del árbol de sintaxis abstracta en lugar de como una expresión Nix.
•
--xml
Cuando se usa con --eval, imprime el valor resultante como una representación XML del árbol de sintaxis abstracta en lugar de como una expresión Nix. El esquema es el mismo que el utilizado por el builtin toXML .
•
--read-write-mode
Cuando se usa con --eval, realiza la evaluación en modo de lectura/escritura para que las características del lenguaje nix que lo requieran sigan funcionando (al costo de tener que instanciar cada derivación evaluada). Si esta opción no está habilitada, puede haber rutas de almacén no instanciadas en la salida final.

Opciones Comunes

La mayoría de los comandos Nix aceptan las siguientes opciones de línea de comandos:

•
--help
Imprime un resumen de la sintaxis del comando y sale.
•
--version
Imprime el número de versión de Nix en la salida estándar y sale.
•
--verbose / -v
Aumenta el nivel de verbosidad de los mensajes de diagnóstico impresos en la salida de error estándar. Para cada operación de Nix, la información impresa en la salida estándar está bien definida; cualquier información de diagnóstico se imprime en la salida de error estándar, nunca en la salida estándar.
Esta opción se puede especificar repetidamente. Actualmente, existen los siguientes niveles de verbosidad:
•
0 “Solo errores”
Solo imprime mensajes que explican por qué falló la invocación de Nix.
•
1 “Informativo”
Imprime mensajes *útiles* sobre lo que Nix está haciendo. Este es el valor predeterminado.
•
2 “Hablador”
Imprime más mensajes informativos.
•
3 “Charla”
Imprime aún más mensajes informativos.
•
4 “Depuración”
Imprime información de depuración.
•
5 “Vómito”
Imprime una gran cantidad de información de depuración.
•
--quiet
Disminuye el nivel de verbosidad de los mensajes de diagnóstico impresos en la salida de error estándar. Esta es la opción inversa a -v / --verbose.
Esta opción se puede especificar repetidamente. Ver la lista de niveles de verbosidad anterior.
•
--log-format formato
>
Esta opción se puede utilizar para cambiar el formato de salida del registro, siendo formato uno de los siguientes:
•
raw
Este es el formato bruto, tal como lo produce nix-build.
•
internal-json
Muestra los registros de forma estructurada.
Advertencia
Si bien el esquema en sí es relativamente estable, el formato de los mensajes de error (especialmente del campo msg) puede cambiar entre versiones.
•
bar
Solo muestra una barra de progreso durante las compilaciones.
•
bar-with-logs
Muestra los registros brutos, con la barra de progreso en la parte inferior.
•
--no-build-output / -Q
Por defecto, la salida escrita por los constructores a la salida estándar y error estándar se muestra en el error estándar del comando Nix. Esta opción suprime este comportamiento. Tenga en cuenta que la salida estándar y el error del constructor siempre se escriben en un archivo de registro en prefix/nix/var/log/nix.
•
--max-jobs / -j número
Establece el número máximo de trabajos de compilación que Nix realizará en paralelo al número especificado. Especifique auto para usar el número de CPUs del sistema. El valor predeterminado lo especifica la configuración max-jobs, que a su vez tiene un valor predeterminado de 1. Un valor más alto es útil en sistemas SMP o para explotar la latencia de E/S.
Establecerlo en 0 deshabilita la compilación en la máquina local, lo que es útil cuando desea que las compilaciones ocurran solo en constructores remotos.
•
--cores
Establece el valor de la variable de entorno NIX_BUILD_CORES en la invocación de los constructores. Los constructores pueden usar esta variable a su discreción para controlar el paralelismo máximo. Por ejemplo, en Nixpkgs, si el atributo de derivación enableParallelBuilding está configurado en true, el constructor pasa el flag -jN a GNU Make. Por defecto, utiliza el valor de la configuración cores, si está configurada, o 1 en caso contrario. El valor 0 significa que el constructor debe usar todos los núcleos de CPU disponibles en el sistema.
•
--max-silent-time
Establece el número máximo de segundos que un constructor puede pasar sin producir datos en la salida estándar o error estándar. El valor predeterminado lo especifica la configuración max-silent-time. 0 significa sin tiempo de espera.
•
--timeout
Establece el número máximo de segundos que un constructor puede ejecutarse. El valor predeterminado lo especifica la configuración timeout. 0 significa sin tiempo de espera.
•
--keep-going / -k
Continuar en caso de fallos en las compilaciones, en la mayor medida posible. Es decir, si falla la compilación de una entrada de alguna derivación, Nix aún compilará las otras entradas, pero no la derivación en sí. Sin esta opción, Nix se detiene si falla alguna compilación (excepto las compilaciones de sustitutos), matando posiblemente las compilaciones en curso (en caso de compilaciones paralelas o distribuidas).
•
--keep-failed / -K
Especifica que en caso de un fallo de compilación, el directorio temporal (generalmente en /tmp) en el que se realiza la compilación no debe ser eliminado. La ruta del directorio de compilación se imprime como un mensaje informativo.
•
--fallback
Siempre que Nix intente compilar una derivación para la cual se conocen sustitutos para cada ruta de salida, pero la realización de las rutas de salida a través de los sustitutos falla, recurrir a la compilación de la derivación.
El escenario más común en el que esto es útil es cuando hemos registrado sustitutos para realizar la distribución binaria desde, por ejemplo, un repositorio de red. Si el repositorio está caído, la realización de la derivación fallará. Cuando se especifica esta opción, Nix compilará la derivación en su lugar. Por lo tanto, la instalación desde binarios recurre a la instalación desde código fuente. Esta opción no es la predeterminada, ya que generalmente no es deseable que un fallo transitorio en la obtención de los sustitutos conduzca a una compilación completa desde código fuente (con el consumo relacionado de recursos).
•
--readonly-mode
Cuando se utiliza esta opción, no se intenta abrir la base de datos de Nix. La mayoría de las operaciones de Nix requieren acceso a la base de datos, por lo que esas operaciones fallarán.
•
--arg nombre valor
Esta opción es aceptada por nix-env, nix-instantiate, nix-shell y nix-build. Al evaluar expresiones Nix, el evaluador de expresiones intentará automáticamente llamar a las funciones que encuentre. Puede llamar automáticamente a funciones para las cuales cada argumento tiene un valor predeterminado (por ejemplo, { argName ? defaultValue }: ...).
Con --arg, también puede llamar a funciones que tienen argumentos sin un valor predeterminado (o anular un valor predeterminado). Es decir, si el evaluador encuentra una función con un argumento llamado nombre, la llamará con el valor valor.
Por ejemplo, el default.nix de nivel superior en Nixpkgs es en realidad una función:
{ # El sistema (por ejemplo, `i686-linux') para el que se compilarán los paquetes.
system ? builtins.currentSystem
...
}: ...
Así que si llama a esta expresión Nix (por ejemplo, cuando ejecuta nix-env --install --attr pkgname), la función se llamará automáticamente utilizando el valor builtins.currentSystem para el argumento system. Puede anular esto usando --arg, por ejemplo, nix-env --install --attr pkgname --arg system \"i686-freebsd\". (Tenga en cuenta que dado que el argumento es una cadena literal de Nix, debe escapar las comillas).
•
--argstr nombre valor
Esta opción es como --arg, solo que el valor no es una expresión Nix sino una cadena. Así que en lugar de --arg system \"i686-linux\" (las comillas exteriores son para que el shell funcione correctamente) puede decir --argstr system i686-linux.
•
--attr / -A attrPath
Selecciona un atributo de la expresión Nix de nivel superior que se está evaluando. (Solo nix-env, nix-instantiate, nix-build y nix-shell). El ruta del atributo attrPath es una secuencia de nombres de atributos separados por puntos. Por ejemplo, dada una expresión Nix de nivel superior e, la ruta del atributo xorg.xorgserver haría que se utilizara la expresión e.xorg.xorgserver. Consulte nix-env --install para ver algunos ejemplos concretos.
Además de los nombres de atributos, también puede especificar índices de arreglos. Por ejemplo, la ruta del atributo foo.3.bar selecciona el atributo bar del cuarto elemento del arreglo en el atributo foo de la expresión de nivel superior.
•
--expr / -E
Interpreta los argumentos de la línea de comandos como una lista de expresiones Nix para analizar y evaluar, en lugar de como una lista de nombres de archivo de expresiones Nix. (Solo nix-instantiate, nix-build y nix-shell).
Para nix-shell, esta opción se usa comúnmente para proporcionarle un shell en el que pueda compilar los paquetes devueltos por la expresión. Si desea obtener un shell que contenga los paquetes *compilados* listos para usar, proporcione su expresión al flag de conveniencia nix-shell --packages en su lugar.
•
-I / --include ruta
Agrega una entrada a la lista de rutas de búsqueda utilizadas para resolver rutas de búsqueda. Esta opción se puede dar varias veces.
Las rutas añadidas a través de -I tienen prioridad sobre la configuración nix-path y la variable de entorno NIX_PATH.
•
--option nombre valor
Establece la opción de configuración de Nix nombre a valor. Esto anula las configuraciones en el archivo de configuración de Nix (ver nix.conf5).
•
--repair
Repara rutas de la tienda corruptas o faltantes volviendo a descargarlas o reconstruyéndolas. Ten en cuenta que esto es lento porque requiere calcular un hash criptográfico del contenido de cada ruta en el cierre de la compilación. También ten en cuenta la advertencia en nix-store --repair-path.

Nota

Ver man nix.conf para anular configuraciones con indicadores de línea de comandos.

Variables de Entorno Comunes

La mayoría de los comandos de Nix interpretan las siguientes variables de entorno:

•
IN_NIX_SHELL
Indicador que informa si el entorno actual fue configurado por nix-shell. Puede tener los valores pure o impure.
•
NIX_PATH
Una lista separada por dos puntos de entradas de búsqueda utilizadas para resolver rutas de búsqueda.
Esta variable de entorno anula el valor de la configuración nix-path.
Puede extenderse usando la opción -I.
Ejemplo
$ export NIX_PATH=`/home/eelco/Dev:nixos-config=/etc/nixos
Si NIX_PATH se establece a una cadena vacía, la resolución de rutas de búsqueda siempre fallará.
Ejemplo
$ NIX_PATH= nix-instantiate --eval '<nixpkgs>'
error: file 'nixpkgs' was not found in the Nix search path (add it using $NIX_PATH or -I)
•
NIX_IGNORE_SYMLINK_STORE
Normalmente, el directorio de la tienda Nix (típicamente /nix/store) no tiene permitido contener componentes de enlaces simbólicos. Esto es para prevenir compilaciones "impuras". Los constructores a veces "canonicalizan" rutas resolviendo todos los componentes de enlaces simbólicos. Por lo tanto, las compilaciones en diferentes máquinas (con /nix/store resolviendo a diferentes ubicaciones) podrían producir resultados diferentes. Esto generalmente no es un problema, excepto cuando las compilaciones se implementan en máquinas donde /nix/store resuelve de manera diferente. Si estás seguro de que no vas a hacer eso, puedes establecer NIX_IGNORE_SYMLINK_STORE a 1.
Ten en cuenta que si estás enlazando simbólicamente la tienda Nix para poder ponerla en un sistema de archivos diferente al del sistema de archivos raíz, en Linux es mejor usar puntos de montaje bind, p. ej.,
$ mkdir /nix
$ mount -o bind /mnt/otherdisk/nix /nix
Consulta la página del manual de mount 8 para más detalles.
•
NIX_STORE_DIR
Anula la ubicación de la tienda Nix (por defecto prefix/store).
•
NIX_DATA_DIR
Anula la ubicación del directorio de datos estáticos de Nix (por defecto prefix/share).
•
NIX_LOG_DIR
Anula la ubicación del directorio de logs de Nix (por defecto prefix/var/log/nix).
•
NIX_STATE_DIR
Anula la ubicación del directorio de estado de Nix (por defecto prefix/var/nix).
•
NIX_CONF_DIR
Anula la ubicación del directorio de configuración del sistema Nix (por defecto prefix/etc/nix).
•
NIX_CONFIG
Aplica configuraciones de Nix desde el entorno. El contenido se trata como si se hubiera leído de un archivo de configuración de Nix. Las configuraciones se separan por el carácter de nueva línea.
•
NIX_USER_CONF_FILES
Anula la ubicación de los archivos de configuración de usuario de Nix de los que cargar.
Los valores por defecto son las ubicaciones según la Especificación de Directorios Base XDG. Ver la subsección Directorios Base XDG para más detalles.
La variable se trata como una lista separada por el token :.
•
TMPDIR
Utiliza el directorio especificado para almacenar archivos temporales. En particular, esto incluye directorios de compilación temporales; estos pueden ocupar cantidades sustanciales de espacio en disco. El valor por defecto es /tmp.
•
NIX_REMOTE
Esta variable debe establecerse a daemon si deseas utilizar el demonio Nix para ejecutar operaciones de Nix. Esto es necesario en las instalaciones Nix multiusuario. Si el socket Unix del demonio Nix está en una ruta no estándar, esta variable debe establecerse a unix://ruta/al/socket. De lo contrario, debe dejarse sin establecer.
•
NIX_SHOW_STATS
Si se establece a 1, Nix imprimirá algunas estadísticas de evaluación, como el número de valores asignados.
•
NIX_COUNT_CALLS
Si se establece a 1, Nix imprimirá cuántas veces se llamaron las funciones durante la evaluación de expresiones Nix. Esto es útil para perfilar tus expresiones Nix.
•
GC_INITIAL_HEAP_SIZE
Si Nix se ha configurado para usar el recolector de basura de Boehm, esta variable establece el tamaño inicial del heap en bytes. Por defecto es 384 MiB. Establecerlo a un valor bajo reduce el consumo de memoria, pero aumentará el tiempo de ejecución debido a la sobrecarga de la recolección de basura.

Directorios Base XDG

Nix sigue la Especificación de Directorios Base XDG.

Por compatibilidad con versiones anteriores, los comandos de Nix seguirán el estándar solo cuando use-xdg-base-directories esté habilitado. Los nuevos comandos de Nix (experimentales) se ajustan al estándar por defecto.

Las siguientes variables de entorno se utilizan para determinar las ubicaciones de varios archivos de estado y configuración:

  • [XDG_CONFIG_HOME]{#env-XDGCONFIGHOME} (por defecto ~/.config)
  • [XDG_STATE_HOME]{#env-XDGSTATEHOME} (por defecto ~/.local/state)
  • [XDG_CACHE_HOME]{#env-XDGCACHEHOME} (por defecto ~/.cache)

Ejemplos

Instancia derivaciones de tienda de una expresión Nix y las compila usando nix-store:

$ nix-instantiate test.nix (instantiate)
/nix/store/cigxbmvy6dzix98dxxh9b6shg7ar5bvs-perl-BerkeleyDB-0.26.drv
$ nix-store --realise $(nix-instantiate test.nix) (build)
...
/nix/store/qhqk4n8ci095g3sdp93x7rgwyh9rdvgk-perl-BerkeleyDB-0.26 (output path)
$ ls -l /nix/store/qhqk4n8ci095g3sdp93x7rgwyh9rdvgk-perl-BerkeleyDB-0.26
dr-xr-xr-x    2 eelco    users        4096 1970-01-01 01:00 lib
...

También puedes proporcionar una expresión Nix en la línea de comandos:

$ nix-instantiate --expr 'with import <nixpkgs> { }; hello'
/nix/store/j8s4zyv75a724q38cb0r87rlczaiag4y-hello-2.8.drv

Esto es equivalente a:

$ nix-instantiate '<nixpkgs>' --attr hello

Analizando y evaluando expresiones Nix:

$ nix-instantiate --parse --expr '1
+ 2' 1 + 2 
$ nix-instantiate --eval --expr '1 + 2'
3
$ nix-instantiate --eval --xml --expr '1 + 2'
<?xml version='1.0' encoding='utf-8'?>
<expr>
  <int value="3" />
</expr>

La diferencia entre evaluación no estricta y estricta:

$ nix-instantiate --eval --xml --expr '{ x = {}; }'
<?xml version='1.0' encoding='utf-8'?>
<expr>
  <attrs>
    <attr column="3" line="1" name="x">
      <unevaluated />
    </attr>
  </attrs>
</expr>
$ nix-instantiate --eval --xml --strict --expr '{ x = {}; }'
<?xml version='1.0' encoding='utf-8'?>
<expr>
  <attrs>
    <attr column="3" line="1" name="x">
      <attrs>
      </attrs>
    </attr>
  </attrs>
</expr>
