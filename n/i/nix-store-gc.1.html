nix-store --gc(1) Manual de Comandos Generales nix-store --gc(1)

Nombre

nix-store --gc - ejecutar la recolección de basura

Sinopsis

nix-store --gc [--print-roots | --print-live | --print-dead] [--max-freed bytes]

Descripción

Sin indicadores adicionales, la operación --gc realiza una recolección de basura en el almacén Nix. Es decir, se eliminan todas las rutas en el almacén Nix que no sean accesibles mediante referencias del sistema de archivos desde un conjunto de “raíces”.

Se pueden especificar las siguientes suboperaciones:

•
--print-roots
Esta operación imprime en la salida estándar el conjunto de raíces utilizado por el recolector de basura.
•
--print-live
Esta operación imprime en la salida estándar el conjunto de rutas de almacén “vivas”, que son todas las rutas de almacén accesibles desde las raíces. Las rutas vivas nunca deben eliminarse, ya que eso rompería la consistencia; sería posible que se instalaran aplicaciones que referencien elementos que ya no están presentes en el almacén.
•
--print-dead
Esta operación imprime en la salida estándar el conjunto de rutas de almacén “muertas”, que es simplemente lo opuesto al conjunto de rutas vivas: cualquier ruta en el almacén que no esté viva (con respecto a las raíces) está muerta.

Por defecto, se eliminan todas las rutas inalcanzables. Los siguientes indicadores controlan qué se elimina y en qué orden:

•
--max-freed bytes
Sigue eliminando rutas hasta que se hayan liberado al menos bytes bytes, luego se detiene. Al argumento bytes le pueden seguir los sufijos multiplicadores K, M, G o T, que denotan unidades de KiB, MiB, GiB o TiB.

El comportamiento del recolector también está influenciado por la configuración keep-outputs y keep-derivations en el archivo de configuración de Nix.

Por defecto, el recolector imprime el número total de bytes liberados cuando finaliza (o cuando se interrumpe). Con --print-dead, imprime el número de bytes que se liberarían.

Opciones

Se permiten las siguientes opciones para todas las operaciones de nix-store, pero puede que no siempre tengan efecto.

•
--add-root ruta
Hace que el resultado de una realización (--realise y --force-realise) se registre como una raíz del recolector de basura. ruta se creará como un enlace simbólico a la ruta del almacén resultante. Además, se creará un enlace simbólico con un nombre único a ruta en /nix/var/nix/gcroots/auto/. Por ejemplo:
$ nix-store --add-root /home/eelco/bla/result --realise ...
$ ls -l /nix/var/nix/gcroots/auto
lrwxrwxrwx    1 ... 2005-03-13 21:10 dn54lcypm8f8... -> /home/eelco/bla/result
$ ls -l /home/eelco/bla/result
lrwxrwxrwx    1 ... 2005-03-13 21:10 /home/eelco/bla/result -> /nix/store/1r11343n6qd4...-f-spot-0.0.10
Por lo tanto, cuando se elimine /home/eelco/bla/result, la raíz de GC en el directorio auto se convertirá en un enlace simbólico colgante y será ignorada por el recolector.
Advertencia
Tenga en cuenta que no es posible mover o renombrar raíces de GC, ya que el enlace simbólico en el directorio auto seguirá apuntando a la ubicación antigua.
Si hay varios resultados, se crearán varios enlaces simbólicos numerando secuencialmente los enlaces simbólicos más allá del primero (por ejemplo, foo, foo-2, foo-3, y así sucesivamente).

Opciones Comunes

La mayoría de los comandos de Nix aceptan las siguientes opciones de línea de comandos:

•
--help

•
--version

•
--verbose / -v

Para cada operación de Nix, la información imprimida en la salida estándar está bien definida; cualquier información de diagnóstico se imprime en la salida de error estándar, nunca en la salida estándar.
Esta opción se puede especificar repetidamente. Actualmente, existen los siguientes niveles de verbosidad:

0 “Sólo errores”

•
1 “Informativo”

•
2 “Hablador”
Imprime más mensajes informativos.
•
3 “Conversador”
Imprime aún más mensajes informativos.
•
4 “Depuración”
Imprime información de depuración.
•
5 “Vómito”
Imprime grandes cantidades de información de depuración.
•
--quiet
Disminuye el nivel de verbosidad de los mensajes de diagnóstico impresos en la salida de error estándar. Esta es la opción inversa a -v / --verbose.
Esta opción se puede especificar repetidamente. Consulte la lista anterior de niveles de verbosidad.
•
--log-format formato
Esta opción se puede utilizar para cambiar el formato de salida del registro, siendo formato uno de los siguientes:
•
raw
Este es el formato sin procesar, tal como lo emite nix-build.
•
internal-json
Emite los registros de forma estructurada.
Advertencia
Aunque el esquema en sí es relativamente estable, el formato de los mensajes de error (específicamente del campo msg) puede cambiar entre versiones.
•
bar
Solo muestra una barra de progreso durante las compilaciones.
•
bar-with-logs
Muestra una barra de progreso junto con los registros de compilación.

Este sitio no está asociado de ninguna forma con Arch Linux ni afiliado a este proyecto. El contenido es únicamente una traducción de las páginas del manual de Arch publicadas en man.archlinux.org.

Muestra los registros sin procesar, con la barra de progreso en la parte inferior.
•
--no-build-output / -Q
Por defecto, la salida escrita por los constructores en la salida estándar y el error estándar se refleja en el error estándar del comando Nix. Esta opción suprime este comportamiento. Ten en cuenta que la salida estándar y el error estándar del constructor siempre se escriben en un archivo de registro en prefix/nix/var/log/nix.
•
--max-jobs / -j número
Establece el número máximo de trabajos de construcción que Nix realizará en paralelo al número especificado. Especifica auto para usar el número de CPUs en el sistema. El valor por defecto es especificado por la configuración max-jobs, que a su vez tiene un valor por defecto de 1. Un valor más alto es útil en sistemas SMP o para explotar la latencia de E/S.
Establecerlo en 0 prohíbe la construcción en la máquina local, lo cual es útil cuando solo quieres que las construcciones ocurran en constructores remotos.
•
--cores
Establece el valor de la variable de entorno NIX_BUILD_CORES en la invocación de los constructores. Los constructores pueden usar esta variable a su discreción para controlar la máxima cantidad de paralelismo. Por ejemplo, en Nixpkgs, si el atributo de derivación enableParallelBuilding está establecido en true, el constructor pasa el flag -jN a GNU Make. Por defecto, utiliza el valor de la configuración cores, si está configurada, o 1 en caso contrario. El valor 0 significa que el constructor debe usar todos los núcleos de CPU disponibles en el sistema.
•
--max-silent-time
Establece el número máximo de segundos que un constructor puede pasar sin producir datos en la salida estándar o el error estándar. El valor por defecto es especificado por la configuración max-silent-time. 0 significa sin tiempo de espera.
•
--timeout
Establece el número máximo de segundos que un constructor puede ejecutarse. El valor por defecto es especificado por la configuración timeout. 0 significa sin tiempo de espera.
•
--keep-going / -k
Continuar en caso de fallos de construcción, en la mayor medida posible. Es decir, si la construcción de una entrada de alguna derivación falla, Nix seguirá construyendo las otras entradas, pero no la derivación en sí. Sin esta opción, Nix se detiene si falla alguna construcción (excepto las construcciones de sustitutos), posiblemente matando las construcciones en curso (en caso de construcciones paralelas o distribuidas).
•
--keep-failed / -K
Especifica que en caso de fallo de construcción, el directorio temporal (generalmente en /tmp) en el que se realiza la construcción no debe ser eliminado. La ruta del directorio de construcción se imprime como un mensaje informativo.
•
--fallback
Cada vez que Nix intente construir una derivación para la cual se conocen sustitutos para cada ruta de salida, pero la realización de las rutas de salida a través de los sustitutos falla, recurrirá a la construcción de la derivación.
El escenario más común en el que esto es útil es cuando hemos registrado sustitutos para realizar la distribución binaria desde, por ejemplo, un repositorio de red. Si el repositorio está caído, fallará la realización de la derivación. Cuando se especifica esta opción, Nix construirá la derivación en su lugar. Por lo tanto, la instalación desde binarios recurre a la instalación desde código fuente. Esta opción no es la predeterminada, ya que generalmente no es deseable que un fallo transitorio al obtener los sustitutos conduzca a una construcción completa desde cero (con el consumo asociado de recursos).
•
--readonly-mode
Cuando se utiliza esta opción, no se intenta abrir la base de datos de Nix. La mayoría de las operaciones de Nix necesitan acceso a la base de datos, por lo que esas operaciones fallarán.
•
--arg nombre valor
Esta opción es aceptada por nix-env, nix-instantiate, nix-shell y nix-build. Al evaluar expresiones Nix, el evaluador de expresiones intentará automáticamente llamar a las funciones que encuentre. Puede llamar automáticamente a funciones para las cuales todos los argumentos tienen un valor por defecto (por ejemplo, { argName ? defaultValue }: ...).
Con --arg, también puedes llamar a funciones que tienen argumentos sin valor por defecto (o anular un valor por defecto). Es decir, si el evaluador encuentra una función con un argumento llamado nombre, la llamará con el valor valor.
Por ejemplo, el default.nix de nivel superior en Nixpkgs es en realidad una función:
{ # El sistema (por ejemplo, `i686-linux') para el que se construirán los paquetes.
system ? builtins.currentSystem
...
}: ...
Así que si llamas a esta expresión Nix (por ejemplo, cuando haces nix-env --install --attr pkgname), la función se llamará automáticamente usando el valor builtins.currentSystem para el argumento system. Puedes anular esto usando --arg, por ejemplo, nix-env --install --attr pkgname --arg system \"i686-freebsd\". (Ten en cuenta que como el argumento es una cadena literal de Nix, tienes que escapar las comillas.)
•
--argstr nombre valor
Esta opción es como --arg, solo que el valor no es una expresión Nix sino una cadena. Así que en lugar de --arg system \"i686-linux\" (las comillas exteriores son para mantener el shell contento) puedes decir --argstr system i686-linux.
•
--attr / -A attrPath
Selecciona un atributo de la expresión Nix de nivel superior que se está evaluando. (Solo nix-env, nix-instantiate, nix-build y nix-shell.) La ruta de atributo attrPath es una secuencia de nombres de atributos separados por puntos. Por ejemplo, dada una expresión Nix de nivel superior e, la ruta de atributo xorg.xorgserver haría que se utilizara la expresión e.xorg.xorgserver. Ver nix-env --install para algunos ejemplos concretos.
Además de los nombres de atributos, también puedes especificar índices de arreglos. Por ejemplo, la ruta de atributo foo.3.bar selecciona el atributo bar del cuarto elemento del arreglo en el atributo foo de la expresión de nivel superior.
•
--expr / -E
Interpreta los argumentos de la línea de comandos como una lista de expresiones Nix a analizar y evaluar, en lugar de como una lista de nombres de archivos de expresiones Nix. (Solo nix-instantiate, nix-build y nix-shell.)
Para nix-shell, esta opción se usa comúnmente para obtener un shell en el que puedas construir los paquetes devueltos por la expresión. Si quieres obtener un shell que contenga los paquetes *construidos* listos para usar, usa la bandera de conveniencia nix-shell --packages en su lugar.
•
-I / --include ruta
Añade una entrada a la lista de rutas de búsqueda utilizadas para resolver rutas de búsqueda. Esta opción puede proporcionarse varias veces.
Las rutas añadidas a través de -I tienen prioridad sobre la configuración nix-path y la variable de entorno NIX_PATH .
•
--option nombre valor
Establece la opción de configuración de Nix nombre a valor. Esto anula las configuraciones en el archivo de configuración de Nix (ver nix.conf5).
•
--repair
Repara rutas de tienda corruptas o faltantes redescargándolas o reconstruyéndolas. Ten en cuenta que esto es lento porque requiere calcular un hash criptográfico del contenido de cada ruta en el cierre de la construcción. Ten en cuenta también la advertencia en nix-store --repair-path.

Name

nix-store - garbage collector

Synopsis

nix-store --gc [--include-outputs] [--max-freed N] [--state-dir DIR]

Description

The Nix store is a collection of packages and other build products. The garbage collector removes all paths from the store that are no longer reachable from any of the GC roots.

GC roots are paths that are explicitly registered as being "live" by other programs or the system configuration. Examples include:

  • The currently installed system profile.
  • The set of profiles registered by the user (e.g. ~/.nix-profile).
  • The set of profiles registered by the system (e.g. /nix/var/nix/profiles/system).
  • The set of packages currently installed by the user (~/.nix-packages).
  • The set of packages currently installed by the system (/nix/var/nix/profiles/default).

The garbage collector works by first discovering all paths that are reachable from the GC roots. Then, it iterates through all paths in the Nix store. Any path that is not in the set of reachable paths is considered garbage and is deleted.

Note

See man nix.conf for overriding configuration settings with command line flags.

Options

•
--include-outputs
Also consider the outputs of derivations as GC roots. This is useful for cleaning up builds that are no longer referenced by a profile, but whose outputs might be needed by subsequent builds.
•
--max-freed N
The maximum amount of bytes to free. Defaults to infinity. The value is an integer, optionally followed by a multiplicative suffix like M or G.
•
--state-dir DIR
Overrides the location of the Nix state directory (default prefix/var/nix). This option is deprecated; use the NIX_STATE_DIR environment variable instead.

Common Environment Variables

Most Nix commands interpret the following environment variables:

•
IN_NIX_SHELL
Indicator that tells if the current environment was set up by nix-shell. It can have the values pure or impure.
•
NIX_PATH
A colon-separated list of search path entries used to resolve lookup paths.
This environment variable overrides the value of the nix-path configuration setting.
It can be extended using the -I option.
Example
$ export NIX_PATH=`/home/eelco/Dev:nixos-config=/etc/nixos
If NIX_PATH is set to an empty string, resolving search paths will always fail.
Example
$ NIX_PATH= nix-instantiate --eval '<nixpkgs>'
error: file 'nixpkgs' was not found in the Nix search path (add it using $NIX_PATH or -I)
•
NIX_IGNORE_SYMLINK_STORE
Normally, the Nix store directory (typically /nix/store) is not allowed to contain any symlink components. This is to prevent “impure” builds. Builders sometimes “canonicalise” paths by resolving all symlink components. Thus, builds on different machines (with /nix/store resolving to different locations) could yield different results. This is generally not a problem, except when builds are deployed to machines where /nix/store resolves differently. If you are sure that you’re not going to do that, you can set NIX_IGNORE_SYMLINK_STORE to 1.
Note that if you’re symlinking the Nix store so that you can put it on another file system than the root file system, on Linux you’re better off using bind mount points, e.g.,
$ mkdir /nix
$ mount -o bind /mnt/otherdisk/nix /nix
Consult the mount 8 manual page for details.
•
NIX_STORE_DIR
Overrides the location of the Nix store (default prefix/store).
•
NIX_DATA_DIR
Overrides the location of the Nix static data directory (default prefix/share).
•
NIX_LOG_DIR
Overrides the location of the Nix log directory (default prefix/var/log/nix).
•
NIX_STATE_DIR
Overrides the location of the Nix state directory (default prefix/var/nix).
•
NIX_CONF_DIR
Overrides the location of the system Nix configuration directory (default prefix/etc/nix).
•
NIX_CONFIG
Applies settings from Nix configuration from the environment. The content is treated as if it was read from a Nix configuration file. Settings are separated by the newline character.
•
NIX_USER_CONF_FILES
Overrides the location of the Nix user configuration files to load from.
The default are the locations according to the XDG Base Directory Specification. See the XDG Base Directories sub-section for details.
The variable is treated as a list separated by the : token.
•
TMPDIR
Use the specified directory to store temporary files. In particular, this includes temporary build directories; these can take up substantial amounts of disk space. The default is /tmp.
•
NIX_REMOTE
This variable should be set to daemon if you want to use the Nix daemon to execute Nix operations. This is necessary in multi-user Nix installations. If the Nix daemon’s Unix socket is at some non-standard path, this variable should be set to unix://path/to/socket. Otherwise, it should be left unset.
•
NIX_SHOW_STATS
If set to 1, Nix will print some evaluation statistics, such as the number of values allocated.
•
NIX_COUNT_CALLS
If set to 1, Nix will print how often functions were called during Nix expression evaluation. This is useful for profiling your Nix expressions.
•
GC_INITIAL_HEAP_SIZE
If Nix has been configured to use the Boehm garbage collector, this variable sets the initial size of the heap in bytes. It defaults to 384 MiB. Setting it to a low value reduces memory consumption, but will increase runtime due to the overhead of garbage collection.
