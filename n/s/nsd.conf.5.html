NOMBRE

nsd.conf - Archivo de configuración de NSD

SINOPSIS

nsd.conf

DESCRIPCIÓN

Este archivo se utiliza para configurar nsd(8). Especifica las opciones para el servidor nsd, archivos de zona, primarios y secundarios.

El formato del archivo tiene atributos y valores. Algunos atributos tienen atributos dentro de ellos. La notación es:

atributo: valor

Los comentarios comienzan con # y duran hasta el final de la línea. Las líneas vacías se ignoran, al igual que los espacios en blanco al principio de una línea. Se deben usar comillas para los valores con espacios, por ejemplo, "nombre del archivo.zona".

EJEMPLO

A continuación se muestra un ejemplo de un archivo nsd.conf corto.

# Archivo nsd.conf de ejemplo para example.com.
# Este es un comentario.

server:
	server-count: 1 # usar este número de núcleos de cpu
	username: 
	zonelistfile: //var/db/nsd/zone.list
	logfile: //var/log/nsd.log
	pidfile: /run/nsd/nsd.pid
	xfrdfile: //var/db/nsd/xfrd.state

zone:
	name: example.com
	zonefile: //etc/nsd/example.com.zone

zone:
	# este servidor es el primario y 192.0.2.1 es el secundario.
	name: primaryzone.com
	zonefile: //etc/nsd/primaryzone.com.zone
	notify: 192.0.2.1 NOKEY
	provide-xfr: 192.0.2.1 NOKEY

zone:
	# este servidor es el secundario y 192.0.2.2 es el primario.
	name: secondaryzone.com
	zonefile: //etc/nsd/secondaryzone.com.zone
	allow-notify: 192.0.2.2 NOKEY
	request-xfr: 192.0.2.2 NOKEY

Luego, use kill -HUP para recargar los cambios de los archivos de zona primarios. Y use kill -TERM para detener el servidor.

FORMATO DEL ARCHIVO

Debe haber espacio entre las palabras clave. Las palabras clave de los atributos terminan con dos puntos ':'. A un atributo le siguen sus atributos contenedores o un valor.

En el nivel superior, solo se permiten server:, verify:, key:, pattern:, zone:, tls-auth: y remote-control:. Estos van seguidos de sus atributos o de una nueva palabra clave de nivel superior. El atributo zone: va seguido de las opciones de zona. El atributo server: va seguido de las opciones globales para el servidor NSD. El atributo verify: se usa para controlar la verificación de la zona. Un atributo key: se usa para definir claves para autenticación. El atributo pattern: va seguido de las opciones de zona para las zonas que utilizan el patrón. Un atributo tls-auth: se usa para definir los atributos de autenticación para las conexiones TLS utilizadas para XFR-over-TLS.

Los archivos se pueden incluir usando la directiva include:. Puede aparecer en cualquier lugar y toma un solo nombre de archivo como argumento. El procesamiento continúa como si el texto del archivo incluido se hubiera copiado en el archivo de configuración en ese punto. Si se utiliza un chroot, se necesita un nombre de archivo absoluto (con el chroot precedido), para que la inclusión pueda ser analizada antes y después de la aplicación del chroot (y el conocimiento de cuál es ese chroot). Puede usar '*' para incluir una coincidencia comodín de archivos, por ejemplo, "foo/nsd.d/*.conf". También funcionan '?', '{}', '[]' y '~', consulte glob(7). Si ningún archivo coincide con el patrón, esto no es un error.

Opciones del Servidor

Las opciones globales (si no se anulan desde la línea de comandos de NSD) se toman de la cláusula server:. Solo puede haber una cláusula server:.

ip-address: <ip4 o ip6>[@puerto] [servidores] [bindtodevice] [setfib]
NSD se enlazará a la dirección IP listada. Se puede dar varias veces para enlazar múltiples direcciones IP. Opcionalmente, se puede dar un número de puerto. Si no se proporciona ninguno, NSD escucha en la interfaz comodín. Igual que la opción de línea de comandos -a.

Para limitar qué servidor(es) NSD escuchan en la interfaz dada, especifique uno o más servidores separados por espacios después de <ip>[@puerto]. Se pueden usar rangos como un atajo para especificar múltiples servidores consecutivos. Por defecto, cada servidor escuchará.

Si se usa un nombre de interfaz en lugar de ip4 o ip6, la lista de direcciones IP asociadas con esa interfaz se recoge y se utiliza al iniciar el servidor.

Para servidores con múltiples direcciones IP que se pueden usar para enviar tráfico a Internet, enumérelas una por una, o la dirección de origen de las respuestas podría ser incorrecta. Esto se debe a que si el socket udp asocia una dirección de origen de 0.0.0.0, el kernel elige una dirección IP con la que enviar a Internet, y elige la incorrecta. Típicamente necesario para instancias anycast. Use ip-transparent para poder listar direcciones que se activan más tarde (típico para cierta balanceo de carga).

interface: <ip4 o ip6>[@puerto] [servidores] [bindtodevice] [setfib]
Igual que ip-address (por facilidad de compatibilidad con unbound.conf).
ip-transparent: <sí o no>
Permite a NSD enlazarse a direcciones no locales. Esto es útil para que NSD escuche en direcciones IP que aún no se han agregado a la interfaz de red, para que pueda responder inmediatamente cuando se agregue la dirección. Por defecto es no.
ip-freebind: <sí o no>
Establece la opción IP_FREEBIND para enlazar a direcciones y interfaces no locales que están caídas. Similar a ip-transparent. Por defecto es no.
reuseport: <sí o no>
Utiliza la opción de socket SO_REUSEPORT y crea descriptores de archivo para cada servidor en server-count. Esto mejora el rendimiento de la pila de red. Solo es realmente útil si también configura un server-count mayor que 1 (por ejemplo, igual al número de cpus). Por defecto es no. Funciona en Linux, pero no funciona en FreeBSD, y probablemente no funcione en otros sistemas.
send-buffer-size: <número>
Establece el tamaño del búfer de envío para los sockets de servicio de consultas. Establézcalo en 0 para usar la configuración predeterminada.
receive-buffer-size: <número>
Establece el tamaño del búfer de recepción para los sockets de servicio de consultas. Establézcalo en 0 para usar la configuración predeterminada.
debug-mode: <sí o no>
Activa el modo de depuración para nsd, no crea un proceso demonio. Por defecto es no. Igual que la opción de línea de comandos -d. Si se establece en sí, no crea un demonio y permanece en primer plano, lo que puede ser útil para la depuración desde la línea de comandos, pero también es utilizado por ciertos procesos supervisores de servidor para asegurar que el servidor está en funcionamiento.
do-ip4: <sí o no>
Si es sí, NSD escucha las conexiones IPv4. Por defecto es sí.
do-ip6: <sí o no>
Si es sí, NSD escucha las conexiones IPv6. Por defecto es sí.
database: <nombre de archivo>
Esta opción es ignorada por las versiones de NSD 4.8.0 y posteriores, ya que la característica de base de datos ha sido eliminada.
zonelistfile: <nombre de archivo>
Por defecto se utiliza //var/db/nsd/zone.list. El archivo especificado se utiliza para almacenar la lista de zonas agregadas dinámicamente. La lista es escrita por NSD para agregar y eliminar zonas. Es un archivo de texto con un nombre de zona y un nombre de patrón en cada línea. Este archivo se utiliza para los comandos nsd-control addzone y delzone.
identity: <cadena>
Devuelve la identidad especificada cuando se solicita CH TXT ID.SERVER. Por defecto es el nombre devuelto por gethostname(3). Igual que la opción de línea de comandos -i. Consulte hide-identity para configurar el servidor para que no responda a dichas consultas.
version: <cadena>
Devuelve la cadena de versión especificada cuando se solicita version.bind y CH TXT version.server. Por defecto es la versión del paquete compilado. Consulte hide-version para configurar el servidor para que no responda a dichas consultas.
nsid: <cadena>
Agrega el nsid especificado a la sección EDNS de la respuesta cuando se consulta con un paquete habilitado para EDNS NSID. Como una secuencia de caracteres hexadecimales o con el prefijo ascii_ y luego una cadena ascii. Igual que la opción de línea de comandos -I.
logfile:
<filename>
Registra los mensajes en el archivo de registro. Por defecto, se registra en stderr y syslog (con la instalación LOG_DAEMON). Igual que la opción de línea de comandos -l.
log-only-syslog: <sí o no>
Registra los mensajes solo en syslog. Útil con systemd para que la impresión en stderr no cause cadenas de registro duplicadas en journald. Antes de que syslog se haya abierto, el servidor utiliza stderr. Stderr también se utiliza si syslog no está disponible. El valor predeterminado es no.
server-count: <número>
Inicia esta cantidad de servidores NSD. El valor predeterminado es 1. Igual que la opción de línea de comandos -N.
cpu-affinity: <número> <número> ...
Afinidad de CPU general para los servidores NSD. El valor predeterminado es sin afinidad.
server-N-cpu-affinity: <número>
Vincula el servidor NSD especificado por N a un núcleo específico. El valor predeterminado es tener la afinidad establecida en todos los núcleos especificados en cpu-affinity. Esta configuración solo surte efecto si cpu-affinity está habilitado.
xfrd-cpu-affinity: <número>
Vincula xfrd a un núcleo específico. El valor predeterminado es tener la afinidad establecida en todos los núcleos especificados en cpu-affinity. Esta configuración solo surte efecto si cpu-affinity está habilitado.
tcp-count: <número>
El número máximo de conexiones TCP concurrentes y activas por cada servidor. El valor predeterminado es 100. Igual que la opción de línea de comandos -n. Este es el número de solicitudes de clientes a este servidor.
tcp-reject-overflow: <sí o no>
Si se establece en sí, las conexiones TCP que excedan el máximo establecido por tcp-count se descartarán inmediatamente (se aceptarán y cerrarán). El valor predeterminado es no.
tcp-query-count: <número>
El número máximo de consultas atendidas en una única conexión TCP. El valor predeterminado es 0, lo que significa que no hay máximo.
tcp-timeout: <número>
Anula el tiempo de espera predeterminado de TCP. Esto también afecta a las transferencias de zona sobre TCP. El valor predeterminado es 120 segundos.
tcp-mss: <número>
Tamaño máximo de segmento (MSS) del socket TCP en el que el servidor responde a las consultas. Un valor inferior al MSS común en Ethernet (1220, por ejemplo) abordará el problema de MTU de ruta. Tenga en cuenta que no todas las plataformas admiten la opción de socket para establecer MSS (TCP_MAXSEG). El valor predeterminado es el MSS predeterminado del sistema determinado por la MTU de la interfaz y la negociación entre el servidor y el cliente.
outgoing-tcp-mss: <número>
Tamaño máximo de segmento (MSS) del socket TCP para solicitudes XFR salientes a otros servidores de nombres. Un valor inferior al MSS común en Ethernet (1220, por ejemplo) abordará el problema de MTU de ruta. Tenga en cuenta que no todas las plataformas admiten la opción de socket para establecer MSS (TCP_MAXSEG). El valor predeterminado es el MSS predeterminado del sistema determinado por la MTU de la interfaz y la negociación entre NSD y otros servidores.
xfrd-tcp-max: <número>
Número de sockets que xfrd utilizará para transferencias de zona salientes. El valor predeterminado es 128. Aumente este valor para permitir más sockets de transferencia de zona, por ejemplo, a 256. Esto es para las transferencias de zona solicitadas por este servidor a otros servidores. Para ahorrar memoria, esto se puede reducir, configúrelo junto con otras configuraciones para reducir la huella de memoria de NSD. xfrd-tcp-max: 32 y xfrd-tcp-pipeline: 128 y rrl-size: 1000

Esto reduce el uso de memoria; el uso de memoria restante se debe principalmente a la configuración de server-count, el número de procesos de servidor y la configuración de tcp-count, que mantiene buffers por proceso de servidor, y al tamaño de los datos de la zona.

xfrd-tcp-pipeline: <número>
Número de transferencias de zona salientes simultáneas que son posibles en los sockets TCP de xfrd. El máximo es 65536, el valor predeterminado es 128. Esto es para las transferencias de zona solicitadas por este servidor a otros servidores.
ipv4-edns-size: <número>
Tamaño preferido del búfer EDNS para IPv4. El valor predeterminado es 1232.
ipv6-edns-size: <número>
Tamaño preferido del búfer EDNS para IPv6. El valor predeterminado es 1232.
pidfile: <nombre_archivo>
Utiliza el archivo PID en lugar del valor predeterminado específico de la plataforma, normalmente "/run/nsd/nsd.pid". Igual que la opción de línea de comandos -P. Con "" no hay archivo PID, para algunas configuraciones de gestión de inicio donde no es útil tener un archivo PID. El valor predeterminado se puede establecer en tiempo de compilación, a veces a "". Entonces, la opción de configuración y la opción de línea de comandos se pueden utilizar para especificar que se utiliza un archivo PID, diferente de su valor predeterminado en tiempo de compilación. El archivo no se cambia de propietario al usuario de la opción username:, por motivos de seguridad de permisos. Sigue siendo propiedad del usuario con el que se inició el servidor. El archivo puede no eliminarse después de que el servidor finalice y salga, ya que los permisos para el nombre de usuario pueden no hacerlo posible.
port: <número>
Responde a las consultas en el puerto especificado. El valor predeterminado es 53. Igual que la opción de línea de comandos -p.
statistics: <número>
Si no está presente, no se volcarán estadísticas. Las estadísticas se generan cada número de segundos. Igual que la opción de línea de comandos -s.
chroot: <directorio>
NSD hará un chroot al inicio al directorio especificado. Tenga en cuenta que si en otra parte de la configuración especifica una ruta absoluta a un archivo dentro del chroot, debe anteponer la ruta del chroot. De esta manera, puede activar y desactivar la opción chroot sin tener que modificar nada más en la configuración. Establezca el valor en "" (la cadena vacía) para deshabilitar el chroot. Por defecto se utiliza "". Igual que la opción de línea de comandos -t.
username: <nombre_usuario>
Después de vincular el socket, elimine los privilegios de usuario y asuma el nombre de usuario. Puede ser nombre de usuario, id o id.gid. Igual que la opción de línea de comandos -u.
zonesdir: <directorio>
Cambia el directorio de trabajo al directorio especificado antes de acceder a los archivos de zona. Además, NSD accederá a zonelistfile, logfile, pidfile, xfrdfile, xfrdir, server-key-file, server-cert-file, control-key-file y control-cert-file de forma relativa a este directorio. Establezca el valor en "" (la cadena vacía) para deshabilitar el cambio de directorio de trabajo. Por defecto se utiliza "//etc/nsd".
difffile: <nombre_archivo>
Ignorado, para compatibilidad con archivos de configuración de NSD3.
xfrdfile: <nombre_archivo>
El demonio de transferencia de zona y tiempo de espera SOA en NSD guardará su estado en este archivo. El estado se lee después de un reinicio. El archivo de estado se puede eliminar sin demasiados problemas, pero se perderán las marcas de tiempo de las zonas. Si se configura como "", el archivo de estado no se utiliza, se comprueban todas las zonas secundarias en busca de actualizaciones al inicio. Para más detalles, consulte la sección sobre el comportamiento de expiración de zona de NSD. El valor predeterminado es //var/db/nsd/xfrd.state.
xfrdir: <directorio>
Las transferencias de zona se almacenan aquí antes de ser procesadas. Se crea un directorio aquí que se elimina cuando NSD se cierra. El valor predeterminado es /tmp.
xfrd-reload-timeout: <número>
Si este valor es -1, xfrd no activará una recarga después de una transferencia de zona. Si es positivo, xfrd activará una recarga después de una transferencia de zona, luego esperará el número de segundos antes de activar una nueva recarga. Establecer este valor limita las recargas a una vez por cada número de segundos. El valor predeterminado es 1 segundo.
verbosity: <nivel>
Este valor especifica el nivel de verbosidad para el registro (no de depuración). El valor predeterminado es 0. 1 proporciona más información sobre las notificaciones entrantes y las transferencias de zona. 2 enumera las advertencias suaves encontradas. 3 imprime más información. Igual que la opción de línea de comandos -V.

La verbosidad 0 imprimirá advertencias y errores, y otros eventos que son importantes para mantener NSD en funcionamiento.

La verbosidad 1 imprimirá adicionalmente mensajes de interés. Notificaciones exitosas, transferencia de zona entrante exitosa (la zona se actualiza), transferencias de zona entrantes fallidas o la incapacidad de procesar actualizaciones de zona.

La verbosidad 2 imprimirá adicionalmente errores suaves, como reinicios de conexión a través de TCP. Y rechazos de notificación, y rechazos de solicitudes axfr.

hide-version: <sí o no>
Evita que NSD responda con la cadena de versión en consultas de clase CHAOS. El valor predeterminado es no.
hide-identity: <sí o no>
Evita que NSD responda con la cadena de identidad en consultas de clase CHAOS. El valor predeterminado es no.
drop-updates: <sí o no>
Si se establece en sí, descarta los paquetes recibidos con el código de operación UPDATE. El valor predeterminado es no.
use-systemd: <sí o no>
Esta opción está obsoleta y se ignora. Si se compila con libsystemd, NSD señala la preparación a systemd y el uso de la opción no es necesario.
log-time-ascii: <sí o no>
Registra la hora en formato ASCII, si "no", entonces en época de segundos. El valor predeterminado es sí. Esto elige el formato al registrar en el archivo. La impresión a través de syslog tiene una marca de tiempo formateada por syslog.
log-time-iso: <sí o no>
Registra la hora en formato ISO8601, si también se establece log-time-ascii: en sí. El valor predeterminado es no.
round-robin: <sí o no>
Habilita la rotación round robin de registros en la respuesta. Esto cambia el orden de los registros en la respuesta y esto puede equilibrar la carga entre ellos. El valor predeterminado es no.
minimal-responses: <sí o no>
Habilita respuestas mínimas para respuestas más pequeñas. Esto hace que los paquetes sean más pequeños. Los datos adicionales solo se agregan para referencias, cuando es realmente necesario. Esto es diferente de la opción de configuración --enable-minimal-responses, que reduce los paquetes, pero exactamente a la longitud de fragmentación, la opción nsd.conf reduce los paquetes lo más posible. El valor predeterminado es no.
confine-to-zone: <sí o no>
Si se establece en sí, no se agregará información adicional a la respuesta si la zona raíz de la información adicional no coincide con la zona raíz de la consulta inicial (por ejemplo, resolución CNAME). El valor predeterminado es no.
refuse-any: <sí o no>
Rechaza consultas de tipo ANY. Esto es útil para detener inundaciones de consultas que intentan obtener respuestas grandes. Tenga en cuenta que el control de velocidad RRL también tiene el tipo ANY como tipo de control de velocidad. Envía truncamiento en respuesta a consultas UDP de tipo ANY y permite consultas TCP de tipo ANY como de costumbre. El valor predeterminado es no. Con la opción desactivada, NSD se comporta según RFC 8482 4.1. Minimiza la respuesta con un RRset. Los tipos populares y no grandes, como A, AAAA y MX, son preferidos, y los tipos grandes, como DNSKEY y RRSIG, se eligen con una preferencia menor que otros tipos. Esto hace que la respuesta sea más pequeña.
reload-config: <sí o no>
Recarga el archivo de configuración y actualiza las claves TSIG y las zonas en SIGHUP. El valor predeterminado es no.
zonefiles-check: <sí o no>
Hace que NSD verifique la mtime de los archivos de zona al inicio y al recibir SIGHUP. Si lo desactiva, se inicia más rápido (menos actividad de disco en caso de muchas zonas). El valor predeterminado es sí. El comando nsd-control reload recarga los archivos de zona independientemente de esta opción.
zonefiles-write: <segundos>
Escribe las zonas secundarias actualizadas en su archivo de zona cada N segundos. Si la opción "zonefile" de la zona o patrón está establecida en "" (cadena vacía), no se escribe ningún archivo de zona. El valor predeterminado es 3600 (1 hora).
rrl-size: <numbuckets>
Esta opción define el tamaño de la tabla hash. El valor predeterminado es 1000000. Más cubos usan más memoria y reducen la posibilidad de colisiones de hash.
rrl-ratelimit: <qps>
Las qps máximas permitidas (desde una fuente de consulta). El valor predeterminado es activado (con una sugerencia de 200 qps). Si se establece en 0, se desactiva (tasa ilimitada), también establezca rrl-whitelist-ratelimit en 0 para deshabilitar el procesamiento de control de velocidad. Si establece la verbosidad en 2, se registran las subredes bloqueadas y desbloqueadas. Las consultas bloqueadas se bloquean y algunas reciben respuestas de fallback TCP. Una vez alcanzado el límite de velocidad, NSD comienza a descartar respuestas. Sin embargo, uno de cada "rrl-slip" número de respuestas se permite, con el bit TC establecido. Si slip se establece en 2, la tasa de respuesta devuelta se reducirá a la mitad. Si se establece en 3, la tasa de respuesta devuelta será un tercio, y así sucesivamente. Si establece rrl-slip en 10, el tráfico se reduce a 1/10. Las opciones de control de velocidad rrl-ratelimit, rrl-size y rrl-whitelist-ratelimit se actualizan cuando se realiza la reconfiguración de nsd-control (también se actualizan las opciones de control de velocidad específicas de la zona).
rrl-slip: <numpackets>
Esta opción controla el número de paquetes descartados antes de enviar una respuesta SLIP (una respuesta con el bit "truncado" establecido en uno). 0 deshabilita el envío de paquetes SLIP, 1 significa que cada consulta recibirá una respuesta SLIP. El valor predeterminado es 2, reduce el tráfico a la mitad y los usuarios legítimos tienen una oportunidad justa de obtener una respuesta +TC.
rrl-ipv4-prefix-length: <subnet>
Longitud del prefijo IPv4. Las direcciones se agrupan por bloque de red. El valor predeterminado es 24.
rrl-ipv6-prefix-length: <subnet>
Longitud del prefijo IPv6. Las direcciones se agrupan por bloque de red. El valor predeterminado es 64.
rrl-whitelist-ratelimit: <qps>
Las qps máximas para clasificaciones de consultas para una fuente, que han sido incluidas en la lista blanca. El valor predeterminado es activado (con una sugerencia de 2000 qps). Con la opción rrl-whitelist, puede establecer consultas específicas para que reciban este límite de qps en lugar del límite normal. Con el valor 0, la tasa es ilimitada.
answer-cookie: <sí o no>
Habilita la respuesta a solicitudes que contienen Cookies DNS según lo especificado en RFC7873. El valor predeterminado es no.

Las Cookies DNS aumentan la seguridad de las transacciones y brindan protección limitada contra ataques de amplificación de denegación de servicio. Las cookies del servidor se crearán y se incluirán en las respuestas. Las cookies del servidor se crean basándose en la cookie del cliente en la solicitud, la hora actual, la dirección IP del cliente y un secreto. Cuando un cliente incluye una cookie de servidor válida en solicitudes sucesivas, el cliente no estará sujeto a la limitación de velocidad de solicitudes (consulte rrl-ratelimit).

Los servidores en una implementación anycast necesitan poder verificar las cookies del servidor entre sí. Para ello, necesitan compartir el secreto utilizado para construir y verificar las cookies. Estos secretos de cookies se pueden especificar en los archivos de configuración con las opciones cookie-secret y cookie-staging-secret.

Si no se proporcionan secretos de cookies a través del archivo de configuración, los secretos de cookies del servidor se pueden agregar, eliminar y activar con la herramienta nsd-control(8). Estos secretos se almacenarán de forma persistente en el archivo de secretos de cookies, cuya ubicación se puede especificar con la opción cookie-secret-file.

Si no se proporcionan secretos de cookies a través del archivo de configuración, y no hay un archivo de secretos de cookies o está vacío, se generará un secreto de cookies aleatorio.

cookie-secret: <cadena hexadecimal de 128 bits>
El secreto de cookie con el que se crean las cookies del servidor y se pueden verificar. Si se especifica un cookie-secret a través del archivo de configuración, se ignorarán los secretos de cookies del archivo de secretos de cookies.
cookie-staging-secret: <cadena hexadecimal de 128 bits>
Un secreto de cookie con el que se pueden verificar las cookies del servidor, pero no se crearán. Esto es útil para rotar los secretos de cookies en configuraciones anycast.

Un cookie-staging-secret solo se puede configurar cuando también hay un cookie-secret configurado.

cookie-secret-file: <nombre de archivo>
Archivo desde el cual se leen los secretos utilizados en los cálculos de Cookies DNS. Los secretos solo se leerán de este archivo si no se proporcionan secretos de cookies en el archivo de configuración a través de las opciones cookie-secret y cookie-staging-secret. El valor predeterminado es "//var/db/nsd/cookiesecrets.txt"

En la versión 4.10.1 y anteriores de NSD, la ubicación predeterminada del archivo de secretos de cookies era "//etc/nsd/nsd_cookiesecrets.txt". Para fines de migración, los secretos de cookies se leerán de esa ubicación si no se proporciona ningún valor para la opción cookie-secret-file y cuando la ubicación predeterminada actual ("//var/db/nsd/cookiesecrets.txt") no exista.

El contenido del archivo de secretos de cookies debe manipularse con los comandos add_cookie_secret, drop_cookie_secret y activate_cookie_secret de la herramienta nsd-control(8). Consulte ese manual para ver cómo realizar una rotación segura de secretos de cookies.

tls-service-key: <nombre de archivo>
Si está habilitado, el servidor proporciona servicio TLS en sockets TCP con el número de puerto de servicio TLS. El número de puerto (853) se configura con tls-port. Para activarlo, cree una interfaz: línea de opción en la configuración con @puerto agregado a la dirección IP. Esto crea el socket adicional en el que se proporciona el servicio DNS sobre TLS.

El archivo es la clave privada para la sesión TLS. El certificado público se encuentra en el archivo tls-service-pem. El valor predeterminado es "", desactivado. Requiere un reinicio (una recarga no es suficiente) si se cambia, porque la clave privada se lee mientras se tienen permisos de root y antes del chroot (si lo hubiera).

tls-service-pem: <nombre de archivo>
El archivo PEM del certificado de clave pública para el servicio TLS. El valor predeterminado es "", desactivado.
tls-service-ocsp: <nombre de archivo>
El archivo PEM OCSP para el servicio TLS, para el adjunto OCSP. El valor predeterminado es "", desactivado. Un proceso externo prepara y actualiza los datos de adjunto OCSP. Como esto, 
openssl ocsp -no_nonce \
	-respout /path/to/ocsp.pem \
	-CAfile /path/to/ca_and_any_intermediate.pem \
	-issuer /path/to/direct_issuer.pem \
	-cert /path/to/cert.pem \
	-url "$( openssl x509 -noout -ocsp_uri -in /path/to/cert.pem )"
tls-port: <número>
El número de puerto en el que se proporciona el servicio TLS TCP, el valor predeterminado es 853. Solo las interfaces configuradas con ese número de puerto como @número reciben el servicio DNS sobre TLS.
tls-auth-port: <número>
El número de puerto en el que se proporciona el servicio TLS TCP solo a clientes autenticados. Si desea utilizar la autenticación mutua TLS en conexiones de Transferencia sobre TLS (XoT), este es el puerto dedicado que el servidor principal habilita para este propósito. Los certificados en tls-cert-bundle se utilizan para verificar la autenticidad de un cliente o un servidor secundario.

El cliente (secundario) debe habilitar tls-auth, configurar client-cert y client-key, y habilitar tls-auth en la configuración de la zona para autenticarse ante un servidor remoto (principal).

tls-auth-xfr-only: <sí o no>
Permite transferencias de zona solo en el puerto tls-auth-port y solo a clientes autenticados. Esto funciona globalmente para todas las zonas. Un control de acceso provide-xfr con tls-auth también es necesario para permitir y verificar una conexión. Se rechazan las solicitudes de transferencias de zona en otros puertos.
tls-cert-bundle: <nombre de archivo>
Si es nulo o "", se utilizan las ubicaciones de verificación predeterminadas. Establézcalo en el archivo de paquete de certificados, por ejemplo "/etc/pki/tls/certs/ca-bundle.crt". Estos certificados se utilizan para autenticar

XoT options

The xfrd-tcp-port: clause is used to specify the port for connections that use the XoT (eXchanged over TLS) protocol. This protocol is used for zone transfers over TLS (XoT) connections.

xfrd-tcp-port: <number>
The port number for XoT service. If the statement is given multiple times, additional port numbers can be used for XoT service. The interface definitions that use this port number expect XoT traffic.
xfrd-tcp-tls-cert-file: <filename>
Path to the server TLS certificate file. This certificate is used to authenticate the server to clients during XoT connections. Default is //etc/nsd/nsd_server.pem.
xfrd-tcp-tls-key-file: <filename>
Path to the server private key file. This key is used in conjunction with the server certificate for TLS encryption. Default is //etc/nsd/nsd_server.key.
xfrd-tcp-tls-ca-file: <filename>
Path to the CA certificate file. This file is used to verify the client's certificate during the TLS handshake for XoT connections. If not specified, system default CAs are used.

Proxy options

The proxy-protocol-port: clause is used to specify the port for proxy protocol service. This allows NSD to receive traffic that has been proxied using protocols like HAProxy.

proxy-protocol-port: <number>
The port number for proxy protocol service. If the statement is given multiple times, additional port numbers can be used for proxy protocol service. The interface definitions that use this port number expect PROXYv2 proxy protocol traffic, for UDP, TCP and for TLS service.

For XoT connections, TLS is used for the proxy protocol as well. The following options can be used to configure TLS for proxy protocol connections:

proxy-protocol-tls-cert-file: <filename>
Path to the server TLS certificate file for proxy protocol service. Default is //etc/nsd/nsd_server.pem.
proxy-protocol-tls-key-file: <filename>
Path to the server private key file for proxy protocol service. Default is //etc/nsd/nsd_server.key.
proxy-protocol-tls-ca-file: <filename>
Path to the CA certificate file for verifying client certificates in proxy protocol connections. If not specified, system default CAs are used.

Metrics options

The metrics: clause is used to configure the Prometheus metrics endpoint.

metrics-enable: <yes or no>
Enable the prometheus metrics HTTP endpoint. It exposes the same statistics as the nsd-control(8) stats_noreset command, but with metric names following the prometheus specification. (Requires libevent2)

Beware, that when using nsd-control(8) stats (instead of stats_noreset), the statistics will be reset for the HTTP metrics endpoint as well.

metrics-interface: <ip4 or ip6 | interface name>
NSD will bind to the listed addresses or interfaces to serve the prometheus metrics. Can be given multiple times to bind multiple ip-addresses. Use 0.0.0.0 and ::0 to bind to the wildcard interface.

If an interface name is used instead of ip4 or ip6, the list of IP addresses associated with that interface is picked up and used at server start.

Default is 127.0.0.1 and ::1.

metrics-port: <number>
The port number for the HTTP service. Default is 9100.
metrics-path: <string>
The HTTP path to expose the metrics at. Default is "/metrics".

Remote Control

The remote-control: clause is used to set options for using the nsd-control(8) tool to give commands to the running NSD server. It is disabled by default, and listens for localhost by default. It uses TLS over TCP where the server and client authenticate to each other with self-signed certificates. The self-signed certificates can be generated with the nsd-control-setup tool. The key files are read by NSD before the chroot and before dropping user permissions, so they can be outside the chroot and readable by the superuser only.

control-enable: <yes or no>
Enable remote control, default is no.
control-interface: <ip4 or ip6 | interface name | absolute path>
NSD will bind to the listed addresses to service control requests (on TCP). Can be given multiple times to bind multiple ip-addresses. Use 0.0.0.0 and ::0 to service the wildcard interface. If none are given NSD listens to the localhost 127.0.0.1 and ::1 interfaces for control, if control is enabled with control-enable.

If an interface name is used instead of ip4 or ip6, the list of IP addresses associated with that interface is picked up and used at server start.

With an absolute path, a unix local named pipe is used for control. The file is created with user and group that is configured and access bits are set to allow members of the group access. Further access can be controlled by setting permissions on the directory containing the control socket file. The key and cert files are not used when control is via the named pipe, because access control is via file and directory permission.

control-port: <number>
The port number for remote control service. 8952 by default.
server-key-file: <filename>
Path to the server private key, by default //etc/nsd/nsd_server.key. This file is generated by the nsd-control-setup utility. This file is used by the nsd server, but not by nsd-control.
server-cert-file: <filename>
Path to the server self signed certificate, by default //etc/nsd/nsd_server.pem. This file is generated by the nsd-control-setup utility. This file is used by the nsd server, and also by nsd-control.
control-key-file: <filename>
Path to the control client private key, by default //etc/nsd/nsd_control.key. This file is generated by the nsd-control-setup utility. This file is used by nsd-control.
control-cert-file: <filename>
Path to the control client certificate, by default //etc/nsd/nsd_control.pem. This certificate has to be signed with the server certificate. This file is generated by the nsd-control-setup utility. This file is used by nsd-control.

Verifier options

The verify: clause is used to enable or disable zone verification, configure listen interfaces and control the global defaults.

enable: <yes or no>
Enable zone verification. Default is no.
port: <number>
The port to answer verifier queries on. Default is 5347.
ip-address:
Interfaces to bind for zone verification (default are the localhost interfaces, usually 127.0.0.1 and ::1). To bind to multiple IP addresses, list them one by one. Optionally, Socket options cannot be specified for verify ip-address
verify-zones: <yes or no>
Verify zones by default.
verifier: <command>
When an update is received for the zone (by IXFR or AXFR) this program will be run to assess the zone with the update. If the program exits with a status code of 0, the zone is considered good and will be served. Any other status code will designate the zone bad and the received update will be discarded. The zone will continue to be served but without the update.

The following environment variables are available to verifiers:

VERIFY_ZONE
The domain name of the zone to be verified.

VERIFY_ZONE_ON_STDIN
When the zone can be read from standard input (stdin), this variable is set to "yes", otherwise it is set to "no".

VERIFY_IP_ADDRESSES
The first address on which the zones to be assessed will be served. If IPv6 is available an IPv6 address will be preferred over IPv4.

VERIFY_PORT
The port number for VERIFY_IP_ADDRESS.

VERIFY_IPV6_ADDRESS
The first IPv6 address on which the zones to be assessed will be served.

VERIFY_IPV6_PORT
The port number for VERIFY_IPV6_ADDRESS.

VERIFY_IPV4_ADDRESS
The first IPv4 address of which the zones to be assessed will be served.

VERIFY_IPV4_PORT
The port number for VERIFY_IPV4_ADDRESS.

verifier-count: <number>
Maximum number of verifiers to run concurrently. Default is 1.
verifier-feed-zone: <yes or no>
Feed the updated zone to the verifier over standard input (stdin).
verifier-timeout: <seconds>
The maximum number of seconds a verifier is allowed to run for assessing one zone. If the verifier takes longer, it will be terminated and the zone update will be discarded. The default is 0 seconds which means the verifier may take as long as it needs.

Pattern Options

The pattern: clause is used to denote a set of options to apply to some zones. The same zone options as for a zone are allowed.

name: <string>
The name of the pattern. This is a (case sensitive) string. The pattern names that start with "_implicit_" are used internally for zones that have no pattern (they are defined in nsd.conf directly).
include-pattern: <pattern-name>
The options from the given pattern are included at this point in this pattern. The referenced pattern must be defined above this one.
<zone option>: <value>
The zone options such as zonefile, allow-query, allow-notify, request-xfr, allow-axfr-fallback, notify, notify-retry, provide-xfr, store-ixfr, ixfr-number, ixfr-size, create-ixfr, zonestats, outgoing-interface, verify-zone, verifier, verifier-feed-zone, verifier-timeout, catalog, and catalog-member-pattern can be given. They are applied to the patterns and zones that include this pattern.

Zone Options

For every zone the options need to be specified in one zone: clause. The access control list elements can be given multiple times to add multiple servers. These elements need to be added explicitly.

For zones that are configured in the nsd.conf config file their settings are hardcoded (in an implicit pattern for themselves only) and they cannot be deleted via delzone, but remove them from the config file and repattern.

name: <string>
The name of the zone. This is the domain name of the apex of the zone. May end with a '.' (in FQDN notation). For example "example.com", "sub.example.net.". This attribute must be present in each zone.
zonefile: <filename>
The zone file for this zone. The path is relative to the working directory (usually the directory where nsd is started).
El archivo que contiene la información de la zona. Si este atributo está presente, se utiliza para leer y escribir el contenido de la zona. Si el atributo está ausente, impide la escritura de la zona.

La cadena se procesa para que una cadena pueda usarse (en un patrón) para muchas zonas diferentes. Si la etiqueta o el carácter no existen, el carácter de porcentaje se reemplaza con un punto para la salida (es decir, para el tercer carácter en un nombre de dominio de dos letras).

%s se reemplaza con el nombre de la zona.

%1 se reemplaza con el primer carácter del nombre de la zona.

%2 se reemplaza con el segundo carácter del nombre de la zona.

%3 se reemplaza con el tercer carácter del nombre de la zona.

%z se reemplaza con el nombre del dominio de nivel superior de la zona.

%y se reemplaza con la siguiente etiqueta bajo el dominio de nivel superior.

%x se reemplaza con la siguiente etiqueta-siguiente bajo el dominio de nivel superior.

allow-query: <ip-spec> <key-name | NOKEY | BLOCKED>
Lista de control de acceso. Cuando se especifica al menos una opción allow-query, se permite que las direcciones especificadas en las opciones allow-query consulten al servidor para la zona. Las consultas de direcciones no listadas o específicamente BLOCKED se descartan. Si se proporciona NOKEY, no se requiere ninguna firma TSIG. BLOCKED tiene prioridad sobre otras entradas, las otras entradas se escanean en busca de una coincidencia en el orden de las declaraciones. Sin opciones allow-query, se permiten consultas desde cualquier dirección IP sin clave TSIG (que es el valor predeterminado).

El ip-spec es una dirección IP simple (IPv4 o IPv6), o puede ser una subred de la forma 1.2.3.4/24, o enmascarada como 1.2.3.4&255.255.255.0 o un rango de la forma 1.2.3.4-1.2.3.25. Tenga en cuenta que los rangos de ip-spec no usan espacios alrededor de los símbolos /, &, @ y -.

allow-notify: <ip-spec> <key-name | NOKEY | BLOCKED>
Lista de control de acceso. Se permite que la dirección listada (primaria) envíe notificaciones a este servidor (secundario) a través de UDP o TCP. Las notificaciones de direcciones no listadas o específicamente BLOCKED se descartan. Si se proporciona NOKEY, no se requiere ninguna firma TSIG. BLOCKED tiene prioridad sobre otras entradas, las otras entradas se escanean en busca de una coincidencia en el orden de las declaraciones.

El ip-spec es una dirección IP simple (IPv4 o IPv6), o puede ser una subred de la forma 1.2.3.4/24, o enmascarada como 1.2.3.4&255.255.255.0 o un rango de la forma 1.2.3.4-1.2.3.25. Se puede agregar un número de puerto usando un sufijo @número, por ejemplo 1.2.3.4@5300 o 1.2.3.4/24@5300 para el puerto 5300. Tenga en cuenta que los rangos de ip-spec no usan espacios alrededor de los símbolos /, &, @ y -.


request-xfr: [AXFR|UDP] <ip-address> <key-name | NOKEY> [tls-auth-name]
Lista de control de acceso. La dirección listada (la primaria) se consulta para AXFR/IXFR en la actualización. Se puede agregar un número de puerto usando un sufijo @número, por ejemplo 1.2.3.4@5300. La clave especificada se utiliza durante AXFR/IXFR. Si se incluye tls-auth-name, se utilizará la cláusula tls-auth especificada para realizar XFR-over-TLS autenticado.

Si se proporciona la opción AXFR, no se contactará al servidor con consultas IXFR, sino que solo se realizarán solicitudes AXFR al servidor. Esto permite que un secundario de NSD tenga un servidor primario que ejecute NSD. Si se omite la opción AXFR, se realizarán solicitudes IXFR y AXFR al servidor primario.

Si se proporciona la opción UDP, el secundario utilizará UDP para transmitir las solicitudes IXFR. Debe implementar TSIG al permitir el transporte UDP, para autenticar notificaciones y transferencias de zona. De lo contrario, NSD es más vulnerable a ataques de estilo Kaminsky. Si se omite la opción UDP, IXFR se transmitirá usando TCP.

Si se proporciona un nombre tls-auth-name, se utilizará TLS (por defecto en el puerto 853) para todas las transferencias de zona de la zona. Si la autenticación de la primaria, basada en la información de autenticación tls-auth especificada, falla, la solicitud XFR no se enviará. Se requiere soporte para TLS 1.3 para XFR-over-TLS.

allow-axfr-fallback: <yes or no>
Esta opción debe ir acompañada de request-xfr. Permite (o no) que NSD (como secundario) recurra a AXFR si el servidor de nombres primario no admite IXFR. El valor predeterminado es sí.
size-limit-xfr: <number>
Esta opción debe ir acompañada de request-xfr. Especifica el límite de tamaño del archivo temporal XFR. Se puede utilizar para detener la recuperación de zonas muy grandes, que de lo contrario podrían consumir mucha memoria y espacio en disco. Si esta opción es 0, es ilimitado. El valor predeterminado es 0.
notify: <ip-address> <key-name | NOKEY>
Lista de control de acceso. La dirección listada (una secundaria) es notificada de las actualizaciones a esta zona a través de UDP. Se puede agregar un número de puerto usando un sufijo @número, por ejemplo 1.2.3.4@5300. La clave especificada se utiliza para firmar la notificación. Solo en configuraciones secundarias NSD podrá detectar actualizaciones de zona (ya que es notificado o se refresca después de un tiempo).
notify-retry: <number>
Esta opción debe ir acompañada de notify. Establece el número de reintentos al enviar notificaciones.
provide-xfr: <ip-spec> <key-name | NOKEY | BLOCKED> [tls-auth-name]
Lista de control de acceso. Se permite que la dirección listada (una secundaria) solicite XFR a este servidor. Los datos de la zona se proporcionarán a la dirección. La clave especificada se utiliza durante XFR. Para direcciones no listadas o BLOCKED, no se proporcionan datos y las solicitudes se descartan. BLOCKED tiene prioridad sobre otras entradas y las otras entradas se escanean en busca de una coincidencia en el orden de las declaraciones.

El ip-spec es una dirección IP simple (IPv4 o IPv6), o puede ser una subred de la forma 1.2.3.4/24, o enmascarada como 1.2.3.4&255.255.255.0 o un rango de la forma 1.2.3.4-1.2.3.25. Se puede agregar un número de puerto usando un sufijo @número, por ejemplo 1.2.3.4@5300 o 1.2.3.4/24@5300 para el puerto 5300. Tenga en cuenta que los rangos de ip-spec no usan espacios alrededor de los símbolos /, &, @ y -.

Si se proporciona un nombre tls-auth-name, se realizará la autenticación TLS de la secundaria para las solicitudes de transferencia de zona de la zona. El extremo remoto debe conectarse al tls-auth-port y debe presentar un certificado con una entrada SAN (Nombre Alternativo del Sujeto) o CN (Nombre Común) igual al auth-domain-name del tls-auth definido. La validez del certificado también se verifica con tls-cert-bundle. Si la autenticación de la secundaria, basada en la información de autenticación tls-auth especificada, falla, la transferencia de zona XFR será rechazada. Si la conexión se realiza en el tls-port, no se realizará ninguna autenticación y la transferencia no será rechazada. Para forzar transferencias de zona solo autenticadas, también se debe habilitar tls-auth-xfr-only. Se requiere soporte para TLS 1.3 para XFR-over-TLS.

outgoing-interface: <ip-address>
Lista de control de acceso. La dirección listada se utiliza para solicitar AXFR|IXFR (en caso de una secundaria) o se utiliza para enviar notificaciones (en caso de una primaria).

La ip-address es una dirección IP simple (IPv4 o IPv6). Se puede agregar un número de puerto usando un sufijo @número, por ejemplo 1.2.3.4@5300.

store-ixfr: <yes or no>
Si está habilitado, el contenido IXFR se almacena y se proporciona al conjunto de clientes especificados en la declaración provide-xfr. El valor predeterminado es no. El contenido IXFR es un conjunto más pequeño de cambios que difieren entre versiones de zona, mientras que un AXFR contiene el contenido completo de la zona.
ixfr-number: <number>
El número de versiones IXFR a almacenar para esta zona, como máximo. El valor predeterminado es 5.
ixfr-size: <number>
El tamaño máximo de almacenamiento a utilizar para las versiones IXFR de esta zona, en bytes. El valor predeterminado es 1048576. Un valor de 0 significa ilimitado. Si desea desactivar el almacenamiento IXFR, establezca la opción store-ixfr en no. NSD no omite el contenido IXFR de las versiones que agregan y eliminan los mismos datos. Almacena y transmite IXFRs tal como fueron transmitidos por el servidor superior.
create-ixfr: <yes or no>
Si está habilitado, se crean datos IXFR cuando el servidor lee un archivo de zona. Esto requiere que store-ixfr esté configurado en sí, para que el contenido IXFR se guarde en el disco. El valor predeterminado está desactivado. Si el servidor no se está ejecutando, se puede usar la opción nsd-checkzone -i para crear un archivo IXFR. Cuando se crea un IXFR, el servidor pone en cola una versión de la zona en un archivo temporal, en la ubicación donde se almacenan los archivos ixfr. Esto crea datos IXFR cuando la zona se lee del archivo, pero no cuando una zona se lee por transferencia AXFR de un servidor, porque entonces el servidor superior que origina los datos es el único lugar donde se calculan las diferencias IXFR y esas diferencias se transmiten verbatim a todos los demás servidores.
max-refresh-time: <seconds>
Limita el tiempo de refresco para zonas secundarias. Este es el temporizador que verifica si la zona tiene que ser recuperada cuando expira. Normalmente se utiliza el valor del registro SOA, pero esta opción restringe ese valor.
min-refresh-time: <seconds>
Limita el tiempo de refresco para zonas secundarias.
max-retry-time: <seconds>
Limita el tiempo de reintento para zonas secundarias. Este es el temporizador que reintenta después de un intento de obtención fallido de la zona. Normalmente se utiliza el valor del registro SOA, seguido de un retroceso exponencial, pero esta opción restringe ese valor.
min-retry-time: <seconds>
Limita el tiempo de reintento para zonas secundarias.
min-expire-time: <seconds or refresh+retry+1>
Limita el tiempo de expiración para zonas secundarias. El valor se puede expresar ya sea por un número de segundos, o la cadena "refresh+retry+1". Con esta última, el tiempo de expiración se limitará inferiormente al tiempo de refresco más el valor de reintento del registro SOA, más 1. Los valores de refresco y reintento estarán sujetos a los límites

ZONE OPTIONS

The following options can be specified for each zone.

max-refresh-time: <seconds>
Set the maximum refresh time for this zone, if specified.
min-refresh-time: <seconds>
Set the minimum refresh time for this zone, if specified.
max-retry-time: <seconds>
Set the maximum retry time for this zone, if specified.
min-retry-time: <seconds>
Set the minimum retry time for this zone, if specified.
zonestats: <name>
When compiled with --enable-zone-stats, NSD can collect statistics per zone. This name gives the group where statistics are added to. The groups are output from nsd-control stats and stats_noreset. Default is "". You can use "%s" to use the name of the zone to track its statistics. If not compiled in, the option can be given but is ignored.
include-pattern: <pattern-name>
The options from the given pattern are included at this point. The referenced pattern must be defined above this zone.
rrl-whitelist: <rrltype>
This option causes queries of this rrltype to be whitelisted, for this zone. They receive the whitelist-ratelimit. You can give multiple lines, each enables a new rrltype to be whitelisted for the zone. Default has none whitelisted. The rrltype is the query classification that the NSD RRL employs to make different types not interfere with one another. The types are logged in the loglines when a subnet is blocked (in verbosity 2). The RRL classification types are: nxdomain, error, referral, any, rrsig, wildcard, nodata, dnskey, positive, all.
multi-primary-check: <yes or no>
Default no. If enabled, checks all primaries for the last version. It uses the higher version of all the configured primaries. Useful if you have multiple primaries that have different version numbers served.
verify-zone: <yes or no>
Enable or disable verification for this zone. Default is value-zones configured in verify:.
verifier: <command>
Command to execute to assess this zone. Default is verifier configured in verify:.
verifier-feed-zone: <yes or no>
Feed updated zone to verifier over standard input. Default is verifier-feed-zone configured in verify:.
verifier-timeout: <seconds>
Number of seconds before verifier is forcefully terminated. Specify 0 (zero) to not use a specific timeout. Default is verifier-timeout from verify:.
catalog: <consumer or producer>
If set to consumer, catalog zone processing is enabled for the zone. Only a single zone may be configured as a catalog consumer zone. When more than one catalog consumer zone is configured, none of them will be processed. Member zones of the catalog will use the pattern specified by the group property, or if a group property is missing or invalid, the pattern specified by the catalog-member-pattern option is used. Group properties are valid if there is only a single value matching the name of a for member zones valid pattern.

A zone with the option set to producer, can be used to produce a catalog zone. Member zones for catalog producer zones can be added with "nsd-control addzone <zone> <pattern>", where <pattern> has a catalog-producer-zone option pointing to a catalog producer zone. Members will get a group property with the pattern name as value. Catalog producer zones must be primary zones and may not have a request-xfr option. Catalog producer zones will not read content from zone files, but will reconstruct the zone on startup from the member zone entries in //var/db/nsd/zone.list, specified with the zonelistfile option.

The status of both catalog consumer and producer zones can be verified with nsd-control zonestatus. It will show the number of member zones and, if the catalog zone is invalid, the reason for it to be invalid is shown. nsd-control zonestatus will also show the entry of a catalog member zone in the catalog (consumer or producer) zone as catalog-member-id:.

A catalog zone can either be catalog consumer zone or a catalog producer zone but not both. Likewise, catalog member zones can be either a member of catalog consumer zone or a catalog producer zone but not both.

Catalog zones contain a list of zones that are served. Use allow-query: 0.0.0.0/0 BLOCKED and allow-query: ::0/0 BLOCKED in a catalog zone zone or pattern clause to prevent revealing the catalog. Also consider using transfers over TLS to further protect the catalog against eavesdroppers.

catalog-member-pattern: <pattern-name>
If this option is provided for a catalog consumer zone, members of that catalog that have a missing or an invalid group property will be added using pattern <pattern-name>.
catalog-producer-zone: <zone-name>
This option can only be used in a pattern. Adding a zone using "nsd-control addzone <zone> <pattern>" with a <pattern> containing this option, will cause a catalog member entry to be created in the catalog producer zone <zone-name>. <zone-name> must exist and must be a valid catalog producer zone.

Key Declarations

The key: clause establishes a key for use in access control lists. It has the following attributes.

name: <string>
The key name. Used to refer to this key in the access control list. The key name has to be correct for tsig to work. This is because the key name is output on the wire.
algorithm: <string>
Authentication algorithm for this key. Such as hmac-md5, hmac-sha1, hmac-sha224, hmac-sha256, hmac-sha384 and hmac-sha512. Can also be abbreviated as 'sha1', 'sha256'. Default is sha256. Algorithms are only available when they were compiled in (available in the crypto library).
secret: <base64 blob>
The base64 encoded shared secret. It is possible to put the secret: declaration (and base64 blob) into a different file, and then to include: that file. In this way the key secret and the rest of the configuration file, which may have different security policies, can be split apart. The content of the secret is the agreed base64 secret content. To make it up, enter a password (its length must be a multiple of 4 characters, A-Za-z0-9), or use dev-random output through a base64 encode filter.

TLS Auth Declarations

The tls-auth: clause establishes attributes to use when authenticating the far end of a TLS connection as well as to define credentials to authenticate to a remote server. It is used in access control lists for XFR-over-TLS. It has the following attributes.

name: <string>
The tls-auth name. Used to refer to this TLS authentication information in the access control list.
auth-domain-name: <string>
The authentication domain name as defined in RFC8310. Used to verify the certificate of the remote connecting server. When used by a primary server in provide-xfr it verifies the secondary. When used by a secondary server in request-xfr it verifies the primary.
client-cert: <file name of clientcert.pem>
If you want to use mutual TLS authentication, this is where the client certificates can be configured that NSD uses to connect to the upstream server to download the zone. The client public key pem cert file can be configured here. Also configure a private key with client-key.
client-key: <file name of clientkey.key>
If you want to use mutual TLS authentication, the private key file can be configured here for the client authentication.
client-key-pw: <string>
If the client-key file uses a password to decrypt the key before it can be used, then the password can be specified here as a string. It is possible to include other config files with the include: option, and this can be used to move that sensitive data to another file, if you wish.

CONFIGURACIÓN DE NSD PARA HACKERS DE BIND9

BIND9 es una implementación de servidor de nombres con su propio formato de archivo de configuración, named.conf(5). BIND9 clasifica las zonas como 'Primaria' o 'Secundaria'.

Zonas secundarias

Para una zona secundaria, se enumeran los servidores primarios. Los servidores primarios son consultados para obtener datos de la zona y se les escucha para recibir notificaciones de actualización. En NSD, estas dos propiedades deben configurarse por separado, enumerando la dirección primaria en las declaraciones allow-notify y request-xfr.

En BIND9, solo necesita proporcionar elementos allow-notify para cualquier fuente adicional de notificaciones (es decir, los operadores); NSD necesita tener allow-notify tanto para primarios como para operadores. BIND9 permite fuentes de transferencia adicionales; en NSD, estas se enumeran como request-xfr.

Aquí hay un ejemplo de una zona secundaria en sintaxis BIND9.

# Archivo de configuración para example.org
options {
	dnssec-enable yes;
};

key tsig.example.org. {
	algorithm hmac-md5;
	secret "aaaaaabbbbbbccccccdddddd";
};

server 162.0.4.49 {
	keys { tsig.example.org. ; };
};

zone "example.org" {
	type secondary;
	file "secondary/example.org.signed";
	primaries { 162.0.4.49; };
};
Para NSD, DNSSEC se habilita automáticamente para las zonas que están firmadas. La declaración dnssec-enable en la cláusula de opciones no es necesaria. En NSD, las claves se asocian con una dirección IP en la declaración de la lista de control de acceso, por lo tanto, la declaración server{} no es necesaria. A continuación se muestra el mismo ejemplo en un archivo de configuración de NSD. 
# Archivo de configuración para example.org
key:
	name: tsig.example.org.
	algorithm: hmac-md5
	secret: "aaaaaabbbbbbccccccdddddd"

zone:
	name: "example.org"
	zonefile: "secondary/example.org.signed"
	# se permite al primario notificar y proporcionará datos de la zona.
	allow-notify: 162.0.4.49 NOKEY
	request-xfr: 162.0.4.49 tsig.example.org.

Observe que el primario se enumera dos veces, una para permitirle enviar notificaciones a este servidor secundario y otra para indicar al servidor secundario dónde buscar los datos de la zona de actualizaciones. Se pueden agregar más líneas allow-notify y request-xfr para especificar más primarios.

Es posible especificar líneas allow-notify adicionales para direcciones que también tienen permitido enviar notificaciones a este servidor secundario.

Zonas primarias

Para una zona primaria en BIND9, se enumeran los servidores secundarios. A estos servidores secundarios se les envían notificaciones de actualizaciones y tienen permiso para solicitar la transferencia de los datos de la zona. En NSD, estas dos propiedades deben configurarse por separado.

Aquí hay un ejemplo de una zona primaria en sintaxis BIND9.

zone "example.nl" {
	type primary;
	file "example.nl";
};

En sintaxis NSD, esto se convierte en:

zone:
	name: "example.nl"
	zonefile: "example.nl"
	# permite a cualquiera solicitar xfr.
	provide-xfr: 0.0.0.0/0 NOKEY
	provide-xfr: ::0/0 NOKEY

# para enumerar un servidor secundario, en general darías
# provide-xfr: 1.2.3.4 tsig-key.name.
# notify: 1.2.3.4 NOKEY

Otro

NSD es un servidor DNS únicamente autoritativo. Esto significa que está destinado a ser un servidor primario o secundario para zonas, proporcionando datos DNS a resolvedores y cachés DNS. BIND9 puede funcionar como un servidor DNS autoritativo; las opciones de configuración para eso se comparan con las de NSD en esta sección. Sin embargo, BIND9 también puede funcionar como un resolvedor o caché. Las opciones de configuración que BIND9 tiene para el resolvedor o caché, por lo tanto, no tienen equivalentes para NSD.
