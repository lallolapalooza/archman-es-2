NUTUPSDRV(8) Manual de NUT NUTUPSDRV(8)

NOMBRE

nutupsdrv - Manual genérico para drivers unificados de NUT

SINOPSIS

nutupsdrv -h

nutupsdrv [OPCIONES]

DESCRIPCIÓN

nutupsdrv no es realmente un driver. Esta es una página de manual combinada para el código compartido que es el núcleo de muchos drivers dentro del paquete Network UPS Tools.

Para obtener información sobre los drivers específicos, consulte sus páginas de manual individuales.

Los drivers de UPS proporcionan un canal de comunicación entre el hardware físico de la UPS y el servidor upsd(8). El driver es responsable de traducir el protocolo nativo de la UPS al formato común utilizado por el resto de este paquete.

El núcleo tiene tres modos de operación que se determinan por los interruptores de línea de comandos. En el modo normal, el driver consultará periódicamente la UPS para conocer su estado y parámetros, según el parámetro pollinterval en ups.conf(5). Los resultados de este comando se presentan a upsd. El driver también manejará la configuración de variables y comandos instantáneos si están disponibles.

En el segundo modo, usando -k, el driver puede instruir a la UPS para que apague la carga, posiblemente después de algún retraso. Este modo de operación está destinado a casos en los que se sabe que la UPS se está quedando sin energía de la batería y los sistemas conectados deben apagarse para garantizar un reinicio adecuado cuando se restablezca la energía.

En el tercer modo, usando -d, el driver saldrá después de algunos bucles de actualización, volcando el árbol de datos (en formato similar a upsc(8)) a la salida estándar. Esto puede ser útil para complementar nut-scanner(8) para descubrir dispositivos, junto con datos en profundidad.


Nota

Probablemente no querrá usar ninguna de estas opciones directamente. Debería usar upsdrvctl(8) (o upsdrvsvcctl(8) en sistemas con un framework de gestión de servicios como systemd o SMF) para controlar sus drivers, y ups.conf(5) para configurarlos. El resto de este manual describe las opciones y parámetros que generalmente no son necesarios para los usuarios normales.

OPCIONES

-h

Muestra un mensaje de ayuda sin hacer nada más. Esto también listará los valores posibles para -x en ese driver, y otro texto de ayuda que el autor del driver haya proporcionado.

-a id

Autoconfigura este driver usando la sección id de ups.conf(5). ¡Este argumento es obligatorio al llamar al driver directamente!

-s id

Configura este driver solo con argumentos de línea de comandos en lugar de leer ups.conf(5). Se usará en lugar de la opción -a cuando necesite ejecutar un driver que no esté presente en el archivo de configuración del driver. En su lugar, la configuración del driver debe establecerse con las opciones -x directamente en la línea de comandos. Dado que esta instancia del driver no puede ser controlada por upsdrvctl(8) o upsdrvsvcctl(8), esta opción debe usarse solo para necesidades específicas.

-D

Aumenta el nivel de depuración. Úselo varias veces para ver más detalles. Ejecutar un driver en modo de depuración (por defecto) evitará que se ejecute en segundo plano después de iniciarse. Continuará registrando información en la consola hasta que reciba una señal SIGINT (generalmente Ctrl-C) o SIGTERM.

El nivel de depuración necesario depende tanto del driver como del problema que esté intentando diagnosticar. Por lo tanto, primero explique el problema que tiene con un driver a un desarrollador/mantenedor, antes de enviarle la salida de depuración. Es muy probable que, si simplemente elige un nivel, la salida sea demasiado limitada o demasiado detallada para ser útil.

-d conteo_actualizaciones

Vuelca el árbol de datos (en formato similar a upsc(8)) a la salida estándar después de ejecutar el bucle de actualización del driver para el número especificado de conteo_actualizaciones y sale.

Por defecto, esto evita que el proceso del driver se ejecute en segundo plano después de iniciarse. Tenga en cuenta que también se imprimirá el banner del driver, por lo que al usar esta opción en scripts, no olvide recortar la primera línea o usar la variable de entorno NUT_QUIET_INIT_BANNER.

-q

Aumenta el umbral del nivel de registro. Úselo varias veces para registrar más detalles.

El comentario de depuración anterior también se aplica aquí.

-c comando

Envía el comando al proceso en segundo plano como una señal. Los comandos válidos son:

reload

vuelve a leer los archivos de configuración, ignorando los ajustes modificados que no se pueden aplicar "al vuelo".

reload-or-error

vuelve a leer los archivos de configuración, ignorando pero contando los valores cambiados que requieren un reinicio del driver (no se pueden cambiar "al vuelo"), y devuelve un código de éxito/fallo basado en ese recuento, para que el llamador pueda decidir el destino de la instancia del driver en ejecución

reload-or-exit

vuelve a leer los archivos de configuración, saliendo del antiguo proceso del driver si encuentra ajustes modificados que no se pueden aplicar "al vuelo" (para que el llamador como systemd pueda lanzar otra copia del driver)

exit

indica a la instancia del driver en ejecución que simplemente salga (para que un llamador externo como la nueva instancia del driver, o los frameworks systemd o SMF, inicien otra copia)

Con las versiones recientes de NUT v2.8.x, dichos comandos se pueden enviar utilizando el socket Unix para la interacción driver-servidor. Como último recurso, al igual que en versiones anteriores, se pueden enviar señales al PID de la instancia del driver anterior (donde sea posible).

-P pid

Envía la señal de comando anterior utilizando el número de PID especificado, en lugar de consultar el archivo PID. Esto puede ayudar a definir unidades de servicio que inician cada driver de NUT como un proceso en primer plano para que no cree un archivo PID. Vea también la opción -FF como alternativa.

-F

Forzar la ejecución del driver como un proceso en primer plano, independientemente de la configuración de depuración o de volcado de datos. Especifique dos veces (-FF o -F -F) para guardar el archivo PID incluso en este modo.

-B

Forzar la ejecución del driver como un proceso en segundo plano, independientemente de la configuración de depuración o de volcado de datos.

-i intervalo

Establece el intervalo de sondeo para el dispositivo. El valor predeterminado es 2 (en segundos).

-V

Muestra solo la información de la versión y sale.

-L

Muestra una lista analizable de variables del driver. Principalmente útil para programas de asistentes de configuración.

-k

Modo de apagado forzado ("Kill" power). La UPS apagará la carga conectada, si es posible.

Debería usar `upsdrvctl shutdown` siempre que sea posible en lugar de llamar directamente a esto. Tenga en cuenta que el contexto restringido del sistema operativo para el apagado típicamente excluye el uso de `upsdrvsvcctl shutdown`.

-r directorio

El driver realizará un chroot(2) al directorio durante la inicialización. Esto puede ser útil al asegurar sistemas.

Además de la ruta de estado, muchos sistemas requerirán que /dev/null exista dentro de directorio para que esto funcione. Los puertos serie se abren antes de la llamada a chroot, por lo que no necesita crearlos dentro de la "prisión". De hecho, es algo más seguro si no lo hace (pero la reconexión a los dispositivos puede que ya no sea posible y podría requerir un reinicio completo del driver).

-u nombre_usuario

Anula el nombre de usuario no privilegiado que el driver puede usar después de iniciarse. Si se inicia como root, después de abrir los archivos de configuración (y opcionalmente llamar a chroot(2), como se describe en la opción anterior), el driver buscará nombre_usuario en la base de datos de contraseñas, luego cambiará a las identidades de usuario y grupo asociadas con nombre_usuario. (Si se inicia con un UID o UID efectivo distinto de cero, el driver ignorará silenciosamente esta opción).

Al compilar NUT desde la fuente, el nombre de usuario predeterminado suele ser `nobody`, y esto puede causar errores de permisos cuando el driver abre el nodo del dispositivo UPS. Puede usar esta opción para anular temporalmente los valores predeterminados. OPTIONS

The drivers may also be started with a specific -x variable. These are intended for specialized cases and are described in the driver man pages.

-a UPS

Enable polling for the specified UPS. This is typically used when starting multiple drivers from a single instance of the driver executable.

-c UPS

Load the specified UPS configuration. This is typically used when starting multiple drivers from a single instance of the driver executable.

-d level

Set the debug level. Higher numbers mean more debug output. Level 0 is silent, 1 is normal verbose, and 2-4 are increasingly verbose. Level 5 or higher will print debug messages to stdout and/or stderr, rather than just to syslog.

-f UPS

Force the specified UPS to be started. This is useful if you are manually starting a driver and it is already running (e.g. managed by upsdrvctl(8)). You will want to remove this option later in order to avoid permission conflicts between the driver and the unprivileged copy of upsd(8).

-g groupname

Override the unprivileged group name that the driver may use after startup to set permissions for the filesystem socket so upsd may still access it if the run-time user of the driver normally would deny that access.

-x var=val

Define a variable called var with the value of var in the driver. This varies from driver to driver — see their specific man pages for more information.

This is like setting var=val in ups.conf(5), but -x on command line overrides any settings from that file.

Note that for fallback values of NUT variables poorly supported by a specific device and/or its NUT driver, you can specify default.var.name=val to set a default value (may be replaced at run-time by a reading from the device, if one does arrive), or override.var.name=val to hard-code a value and ignore its readings from the device even if they are served. For example, this is often used with override.battery.voltage.nominal when the device reports a single cell in 2V range, and you are interested in a standard battery package in 12V range, for PbAc.

DIAGNOSTICS

Information about the startup process is printed to stdout and/or stderr. Additional messages after that point are only available in the syslog, unless the driver remains in foreground (e.g. due to raised debugging verbosity).

After upsd(8) starts, the UPS clients such as upsc(8) can be used to query the status of an UPS.

PROGRAM CONTROL

You should always use upsdrvctl(8) (or upsdrvsvcctl(8) on systems with a service management framework like systemd or SMF) to control the drivers. While drivers can be started by hand for testing purposes, it is not recommended for production use.

FILES

ups.conf

Required configuration file. This contains all details on which drivers to start and where the hardware is attached.

ENVIRONMENT VARIABLES

NUT_DEBUG_LEVEL sets default debug verbosity if no -D arguments were provided on command line, but does not request that the daemon runs in foreground mode.

NUT_CONFPATH is the path name of the directory that contains ups.conf and other configuration files. If this variable is not set, drivers use a built-in default, which is often /usr/local/ups/etc.

NUT_STATEPATH is the path name of the directory in which upsd and drivers keep shared state information. If this variable is not set, upsd and drivers use a built-in default, which is often /var/state/ups. The STATEPATH directive in upsd.conf(5) overrides this variable.

NUT_ALTPIDPATH is the path name of the directory in which upsd and drivers store .pid files. If this variable is not set, upsd and drivers use either NUT_STATEPATH if set, or ALTPIDPATH if set, or otherwise the built-in default STATEPATH.

NUT_QUIET_INIT_UPSNOTIFY=true can be used to prevent daemons which can notify service management frameworks (such as systemd) about passing their lifecycle milestones from emitting such notifications (including those about lack of system support for such modern features, once per run).

NUT_QUIET_INIT_BANNER=true can be used to suppress NUT tool name and version banner. NOT recommended for services due to adverse troubleshooting impact, but may be helpful in shell profiles or scripts which process NUT tool outputs.

BUGS

Some of the drivers may have bugs. See their manuals for more information.
