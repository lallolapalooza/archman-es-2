NOMBRE

nft - Herramienta de administración del framework nftables para filtrado y clasificación de paquetes

SINOPSIS

nft [ -nNscaeSupyjtT ] [ -I directorio ] [ -f archivo | -i | comando ...]
nft -h
nft -v

DESCRIPCIÓN

nft es la herramienta de línea de comandos utilizada para configurar, mantener e inspeccionar las reglas de filtrado y clasificación de paquetes en el kernel de Linux, en el framework de nftables. El subsistema del kernel de Linux se conoce como nf_tables, y 'nf' significa Netfilter.

OPCIONES

El comando acepta varias opciones diferentes que se documentan aquí en grupos para una mejor comprensión de su significado. Puede obtener información sobre las opciones ejecutando nft --help.

Opciones generales:

-h, --help

Muestra el mensaje de ayuda y todas las opciones.

-v, --version

Muestra la versión.

-V

Muestra información detallada de la versión, incluida la configuración en tiempo de compilación.

Opciones de manejo de entrada de conjuntos de reglas que especifican cómo cargar los conjuntos de reglas:

-f, --file archivo

Lee la entrada del archivo. Si archivo es -, lee desde la entrada estándar. La ruta del directorio de este archivo se inserta al principio de la lista de directorios que se buscarán para los archivos incluidos (ver -I/--includepath).

-D, --define nombre=valor

Define una variable. Solo puede combinar esta opción con -f.

-i, --interactive

Lee la entrada desde una CLI interactiva de readline. Puede usar 'quit' para salir, o usar el marcador EOF, normalmente es CTRL-D.

-I, --includepath directorio

Agrega el directorio a la lista de directorios que se buscarán para los archivos incluidos. Esta opción puede especificarse varias veces.

-c, --check

Verifica la validez de los comandos sin aplicar realmente los cambios.

-o, --optimize

Optimiza su conjunto de reglas. Puede combinar esta opción con -c para inspeccionar las optimizaciones propuestas.

Formato de salida de lista de conjuntos de reglas que modifica la salida del comando list ruleset:

-a, --handle

Muestra los identificadores de objeto en la salida.

-s, --stateless

Omite la información de estado de las reglas y los objetos de estado.

-t, --terse

Omite el contenido de los conjuntos de la salida.

-S, --service

Traduce los puertos a nombres de servicio según se definen en /etc/services.

-N, --reversedns

Traduce direcciones IP a nombres mediante resolución inversa de DNS. Esto puede ralentizar su listado ya que genera tráfico de red.

-u, --guid

Traduce UID/GID numéricos a nombres según se definen en /etc/passwd y /etc/group.

-n, --numeric

Muestra una salida completamente numérica.

-y, --numeric-priority

Muestra la prioridad de la cadena base numéricamente.

-p, --numeric-protocol

Muestra el protocolo de capa 4 numéricamente.

-T, --numeric-time

Muestra los valores de tiempo, día y hora en formato numérico.

Formato de salida de comandos:

-e, --echo

Al insertar elementos en el conjunto de reglas usando los comandos add, insert o replace, imprime notificaciones como nft monitor.

-j, --json

Formatea la salida en JSON. Consulte libnftables-json(5) para una descripción del esquema.

-d, --debug nivel

Habilita la salida de depuración. El nivel de depuración puede ser cualquiera de scanner, parser, eval, netlink, mnl, proto-ctx, segtree, all. Puede combinar más de uno separándolos con el símbolo ',', por ejemplo -d eval,mnl.

CONVENCIONES LÉXICAS

La entrada se analiza línea por línea. Cuando el último carácter de una línea, justo antes del carácter de nueva línea, es una barra invertida (\) sin comillas, la siguiente línea se trata como una continuación. Se pueden separar varios comandos en la misma línea utilizando un punto y coma (;).

Un signo de almohadilla (#) inicia un comentario. Todos los caracteres siguientes en la misma línea se ignoran.

Los identificadores comienzan con un carácter alfabético (a-z, A-Z), seguido de cero o más caracteres alfanuméricos (a-z, A-Z, 0-9) y los caracteres barra (/), barra invertida (\), guion bajo (_) y punto (.). Los identificadores que utilizan caracteres diferentes o que entran en conflicto con una palabra clave deben encerrarse entre comillas dobles (").

ARCHIVOS DE INCLUSIÓN

include archivo

Se pueden incluir otros archivos utilizando la declaración include. Los directorios que se buscarán para los archivos de inclusión se pueden especificar utilizando la opción -I/--includepath. Puede anular este comportamiento anteponiendo '’./’' a su ruta para forzar la inclusión de archivos ubicados en el directorio de trabajo actual (es decir, ruta relativa) o '/' para la ubicación del archivo expresada como una ruta absoluta.

Si no se especifica -I/--includepath, entonces nft se basa en el directorio predeterminado que se especifica en el momento de la compilación. Puede recuperar este directorio predeterminado a través de la opción -h/--help.

Las declaraciones de inclusión admiten los símbolos comodín habituales del shell (,?,[]). No tener coincidencias para una declaración de inclusión no es un error, si se utilizan símbolos comodín en la declaración de inclusión. Esto permite tener directorios de inclusión potencialmente vacíos para declaraciones como include "/etc/firewall/rules/". Las coincidencias de comodín se cargan en orden alfabético. Los archivos que comienzan con un punto (.) no coinciden con las declaraciones de inclusión.

VARIABLES SIMBÓLICAS

define variable = expresión
undefine variable
redefine variable = expresión
$variable

Las variables simbólicas se pueden definir utilizando la declaración define. Las referencias a variables son expresiones y se pueden utilizar para inicializar otras variables. El alcance de una definición es el bloque actual y todos los bloques contenidos dentro. Las variables simbólicas se pueden anular utilizando la declaración undefine y modificar utilizando la declaración redefine.

Uso de variables simbólicas.

define int_if1 = eth0
define int_if2 = eth1
define int_ifs = { $int_if1, $int_if2 }
redefine int_if2 = wlan0
undefine int_if2
filter input iif $int_ifs accept

FAMILIAS DE DIRECCIONES

Las familias de direcciones determinan el tipo de paquetes que se procesan. Para cada familia de direcciones, el kernel contiene los llamados "ganchos" (hooks) en etapas específicas de las rutas de procesamiento de paquetes, que invocan a nftables si existen reglas para esos ganchos.

ip Familia de direcciones IPv4.
ip6 Familia de direcciones IPv6.
inet Familia de direcciones Internet (IPv4/IPv6).
arp Familia de direcciones ARP, que maneja paquetes ARP IPv4.
bridge Familia de direcciones Bridge, que maneja paquetes que atraviesan un dispositivo bridge.
netdev Familia de direcciones Netdev, que maneja p
ip6tables filter packets that are destined to be sent out via IPv6. The list of hooks are identical to IPv4/IPv6/Inet address families above.

Todas las objetos de nftables existen en espacios de nombres específicos de la familia de direcciones, por lo tanto, todos los identificadores incluyen una familia de direcciones. Si se especifica un identificador sin una familia de direcciones, la familia ip se usa por defecto.

FAMILIAS DE DIRECCIONES IPV4/IPV6/INET

Las familias de direcciones IPv4/IPv6/Inet manejan paquetes IPv4, IPv6 o ambos tipos. Contienen cinco ganchos en diferentes etapas de procesamiento de paquetes en la pila de red.

Tabla 1. Ganchos de la familia de direcciones IPv4/IPv6/Inet

Gancho Descripción
prerouting Todos los paquetes que entran al sistema son procesados por el gancho prerouting. Se invoca antes del proceso de enrutamiento y se utiliza para filtrado temprano o para cambiar atributos de paquetes que afectan el enrutamiento.
input Los paquetes entregados al sistema local son procesados por el gancho input.
forward Los paquetes reenviados a otro host son procesados por el gancho forward.
output Los paquetes enviados por procesos locales son procesados por el gancho output.
postrouting Todos los paquetes que salen del sistema son procesados por el gancho postrouting.
ingress Todos los paquetes que entran al sistema son procesados por este gancho. Se invoca antes de los manejadores de protocolos de capa 3, por lo tanto, antes del gancho prerouting, y puede usarse para filtrado y control de tráfico. Ingress solo está disponible para la familia Inet (desde el kernel de Linux 5.10).

FAMILIA DE DIRECCIONES ARP

La familia de direcciones ARP maneja paquetes ARP recibidos y enviados por el sistema. Se utiliza comúnmente para manipular paquetes ARP para clústeres.

Tabla 2. Ganchos de la familia de direcciones ARP

Gancho Descripción
input Los paquetes entregados al sistema local son procesados por el gancho input.
output Los paquetes enviados por el sistema local son procesados por el gancho output.

FAMILIA DE DIRECCIONES BRIDGE

La familia de direcciones bridge maneja paquetes Ethernet que atraviesan dispositivos bridge.

La lista de ganchos compatibles es idéntica a las familias de direcciones IPv4/IPv6/Inet anteriores.

FAMILIA DE DIRECCIONES NETDEV

La familia de direcciones Netdev maneja paquetes de la ruta de entrada y salida del dispositivo. Esta familia le permite filtrar paquetes de cualquier ethertype como ARP, VLAN 802.1q, VLAN 802.1ad (Q-in-Q), así como paquetes IPv4 e IPv6.

Tabla 3. Ganchos de la familia de direcciones Netdev

Gancho Descripción
ingress Todos los paquetes que entran al sistema son procesados por este gancho. Se invoca después de los taps de red (es decir, tcpdump), justo después de tc ingress y antes de los manejadores de protocolos de capa 3, puede usarse para filtrado y control de tráfico temprano.
egress Todos los paquetes que salen del sistema son procesados por este gancho. Se invoca después de los manejadores de protocolos de capa 3 y antes de tc egress. Puede usarse para filtrado y control de tráfico tardío.

Los paquetes tunelizados (como vxlan) son procesados por los ganchos de la familia netdev tanto en su forma decapsulada como encapsulada (tunelizada). Por lo tanto, un paquete puede ser filtrado en la red superpuesta, así como en la red subyacente.

Tenga en cuenta que el orden de netfilter y tc se invierte en ingress versus egress. Esto asegura la simetría para NAT y otras manipulaciones de paquetes.

Los paquetes ingress que son redirigidos hacia otra interfaz solo son procesados por netfilter en egress si han pasado previamente por el procesamiento ingress de netfilter. Por lo tanto, los paquetes ingress que son redirigidos por tc no están sujetos a netfilter. Pero lo están si son redirigidos por netfilter en ingress. Conceptualmente, tc y netfilter pueden considerarse capas, con netfilter superpuesto a tc: Si el paquete no ha sido pasado de la capa tc a la capa netfilter, no está sujeto a netfilter en egress.

CONJUNTO DE REGLAS

{list | flush} ruleset [family]

La palabra clave ruleset se utiliza para identificar el conjunto completo de tablas, cadenas, etc. actualmente en el kernel. Los siguientes comandos de ruleset existen:

list Imprime el conjunto de reglas en formato legible por humanos.
flush Borra todo el conjunto de reglas. Tenga en cuenta que, a diferencia de iptables, esto eliminará todas las tablas y lo que contengan, lo que efectivamente conducirá a un conjunto de reglas vacío; ya no se filtrará ningún paquete, por lo que el kernel aceptará cualquier paquete válido que reciba.

Es posible limitar list y flush a una familia de direcciones específica. Para obtener una lista de nombres de familia válidos, consulte la sección llamada “FAMILIAS DE DIRECCIONES” anterior.

Por diseño, la salida del comando list ruleset puede usarse como entrada para nft -f. Efectivamente, este es el equivalente de nft de iptables-save y iptables-restore.

TABLAS

{add | create} table [family] table [{ [comment comment ;] [flags flags ;] }]
{delete | destroy | list | flush} table [family] table
list tables [family]
delete table [family] handle handle
destroy table [family] handle handle

Las tablas son contenedores para cadenas, conjuntos y objetos con estado. Se identifican por su familia de direcciones y su nombre. La familia de direcciones debe ser una de ip, ip6, inet, arp, bridge, netdev. La familia de direcciones inet es una familia ficticia que se utiliza para crear tablas híbridas IPv4/IPv6. La palabra clave de expresión meta nfproto se puede utilizar para probar en qué contexto de familia (ipv4 o ipv6) se está procesando el paquete. Cuando no se especifica ninguna familia de direcciones, se usa ip por defecto. La única diferencia entre add y create es que la primera no devolverá un error si la tabla especificada ya existe, mientras que create devolverá un error.

Tabla 4. Banderas de tabla

Bandera Descripción
dormant la tabla ya no se evalúa (las cadenas base no están registradas).
owner la tabla es propiedad del proceso que la creó.
persist la tabla sobrevivirá al proceso propietario.

Crear una tabla con la bandera owner excluye a otros procesos de manipularla o su contenido. Por defecto, se eliminará cuando el proceso finalice. Establecer la bandera persist evitará esto y la tabla huérfana resultante aceptará un nuevo propietario, por ejemplo, un demonio reiniciándose que mantiene la tabla.

Agregar, cambiar, eliminar una tabla.

# iniciar nft en modo interactivo
nft --interactive
# crear una nueva tabla.
create table inet mytable
# agregar una nueva cadena base: obtener paquetes de entrada
add chain inet mytable myin { type filter hook input priority filter; }
# agregar un único contador a la cadena
add rule inet mytable myin counter
# deshabilitar la tabla temporalmente -- las reglas ya no se evalúan
add table inet mytable { flags dormant; }
# hacer que la tabla vuelva a estar activa:
add table inet mytable

delete Elimina la tabla especificada.
destroy Elimina la tabla especificada, no falla si no existe.
list Lista todas las cadenas y reglas de la tabla especificada.
flush Vacía todas las cadenas y reglas de la tabla especificada.

SETS

nftables ofrece dos tipos de conceptos de conjuntos. Los conjuntos anónimos son conjuntos que no tienen un nombre específico. Los miembros del conjunto se encierran entre llaves, con comas para separar los elementos al crear la regla en la que se utiliza el conjunto. Una vez que se elimina esa regla, el conjunto también se elimina. No se pueden actualizar, es decir, una vez que se declara un conjunto anónimo, no se puede modificar más, excepto eliminando o alterando la regla que utiliza el conjunto anónimo.

Usar conjuntos anónimos para aceptar subredes y puertos particulares.

nft add rule filter input ip saddr { 10.0.0.0/8, 192.168.0.0/16 } tcp dport { 22, 443 } accept

Los conjuntos nombrados son conjuntos que deben definirse primero antes de poder hacer referencia a ellos en las reglas. A diferencia de los conjuntos anónimos, los elementos se pueden añadir o eliminar de un conjunto nombrado en cualquier momento. Los conjuntos se referencian desde las reglas utilizando un prefijo @ al nombre del conjunto.

Usar conjuntos nombrados para aceptar direcciones y puertos.

nft add rule filter input ip saddr @allowed_hosts tcp dport @allowed_ports accept

Los conjuntos allowed_hosts y allowed_ports deben crearse primero. La siguiente sección describe la sintaxis de los conjuntos de nft con más detalle.

{delete | destroy | list | flush | reset } set [familia] tabla conjunto
list sets [familia] [tabla]

{add | delete | destroy } element [familia] tabla conjunto { elemento[, ...] }

Los conjuntos son contenedores de elementos de un tipo de dato definido por el usuario; se identifican de forma única por un nombre definido por el usuario y se adjuntan a tablas. Su comportamiento se puede ajustar con las banderas que se pueden especificar en el momento de la creación del conjunto.

Consulte las banderas de Conjuntos y Mapas a continuación para obtener más detalles.

El gc-interval no afecta al tiempo de espera de los elementos, pero sí a la recuperación de memoria. Un conjunto grande que rara vez tiene elementos que caducan puede utilizar una recolección de basura más alta (menos frecuente) para ahorrar tiempo de CPU, mientras que los conjuntos que ven muchas actualizaciones con elementos de corta duración se beneficiarán de un intervalo más bajo. Los intervalos más bajos aseguran que el conjunto permanezca por debajo de su tamaño máximo. Internamente, una entrada caducada permanece hasta que es eliminada por el recolector de basura, que también decrementa el recuento de elementos del conjunto. Esto también significa que es posible tener un conjunto que no pueda aceptar más elementos, incluso si todos los elementos han caducado, si el gc-interval se establece demasiado alto.

El size define el límite superior de la cantidad de elementos que el conjunto puede admitir. Obligatorio para los conjuntos a los que se añade desde el ruleset con las palabras clave add y update. Proporcionar la palabra clave size para los conjuntos a los que solo se añade mediante nft add element permite una selección de implementación de conjunto más compacta (conservadora de memoria), pero no es obligatorio.

La palabra clave opcional policy se puede utilizar para solicitar una implementación de conjunto más conservadora de memoria.

auto-merge instruye al frontend de nftables a fusionar rangos adyacentes y superpuestos. Ejemplo: Cuando el conjunto contiene el rango 1.2.3.1-1.2.3.4, añadir el elemento 1.2.3.2 no tiene efecto. Añadir 1.2.3.5 cambia el rango existente para cubrir 1.2.3.1-1.2.3.5. Sin esta bandera, 1.2.3.2 no se puede añadir y 1.2.3.5 se inserta como una nueva entrada.

Sets and maps are finite collections of elements that can be used in rules. Sets are only used for matching, maps are used for matching and to provide a data payload. The elements are defined by their key_type. Maps further require a value_type.

The key and value types are specified using the same syntax as the data types in the nftables language. Example: for a set of IP addresses you would specify set ip, for a map from IP addresses to interface names you would specify map ip : string.

Table 9. Set and Map properties

Property Description Type
flags map flags string, same as set flags
elements elements contained by the map map data type
size maximum number of elements in the map unsigned integer (64 bit)
policy map policy string: performance [default], memory

Users can specifiy the properties/features that the set/map must support. This allows the kernel to pick an optimal internal representation. If a required flag is missing, the ruleset might still work, as nftables will auto-enable features if it can infer this from the ruleset. This may not work for all cases, however, so it is recommended to specify all required features in the set/map definition manually. Also, some features are mutually exclusive. For example, it is not possible for a set to support intervals and insertion from the packet path.

Table 10. Set and Map flags

Flag Description

dynamic Set must support updates from the packet path with the add, update or delete keywords.
interval Set must be able to store intervals (ranges). Cannot be combined with the dynamic flag.
timeout Set must support element timeouts (auto-removal of elements once they expire).

ELEMENTOS

{add | create | delete | destroy | get | reset } element [family] table set { ELEMENT[, ...] }

Los comandos relacionados con elementos permiten modificar el contenido de conjuntos y mapas nombrados. key_expression suele ser un valor que coincide con el tipo del conjunto. value_expression no está permitido en conjuntos, pero es obligatorio al añadir a mapas, donde coincide con la parte de datos en su definición de tipo. Al eliminar de mapas, se puede especificar pero es opcional, ya que key_expression identifica de forma única el elemento.

El comando create es similar a add con la excepción de que ninguno de los elementos listados puede existir previamente.

El comando get es útil para comprobar si un elemento está contenido en un conjunto, lo que puede ser no trivial en conjuntos muy grandes y/o de intervalos. En este último caso, se devolverá el intervalo que lo contiene en lugar de solo el elemento en sí.

TABLAS DE FLUJO

{add | create} flowtable [family] table flowtable { hook hook priority priority ; devices = { device[, ...] } ; }

Las tablas de flujo le permiten acelerar el reenvío de paquetes en software. Las entradas de las tablas de flujo se representan mediante una tupla que se compone de la interfaz de entrada, la dirección de origen y destino, el puerto de origen y destino; y los protocolos de capa 3/4. Cada entrada también almacena en caché la interfaz de destino y la dirección de la puerta de enlace, para actualizar la dirección de enlace de datos de destino, para reenviar paquetes. Los campos ttl y hoplimit también se decrementan. Por lo tanto, las tablas de flujo proporcionan una ruta alternativa que permite que los paquetes omitan la ruta de reenvío clásica. Las tablas de flujo residen en el hook de entrada que se encuentra antes del hook de prerrouting. Puede seleccionar qué flujos descargar a través de la expresión de flujo de la cadena de reenvío. Las tablas de flujo se identifican por su familia de direcciones y su nombre. La familia de direcciones debe ser una de ip, ip6 o inet. La familia de direcciones inet es una familia ficticia que se utiliza para crear tablas híbridas IPv4/IPv6. Cuando no se especifica ninguna familia de direcciones, se utiliza ip por defecto.

La priority puede ser un entero con signo o filter que representa 0. Se pueden usar sumas y restas para establecer una prioridad relativa, por ejemplo, filter + 5 equivale a 5.

EXPRESIONES

Las expresiones representan valores, ya sean constantes como direcciones de red, números de puerto, etc., o datos recopilados del paquete durante la evaluación de reglas. Las expresiones se pueden combinar usando expresiones binarias, lógicas, relacionales y de otros tipos para formar expresiones complejas o relacionales (de coincidencia). También se utilizan como argumentos para ciertos tipos de operaciones, como NAT, marcado de paquetes, etc.

Cada expresión tiene un tipo de dato, que determina el tamaño, el análisis y la representación de valores simbólicos y la compatibilidad de tipos con otras expresiones.

El comando describe muestra información sobre el tipo de una expresión y su tipo de dato. También se puede proporcionar un tipo de dato, en cuyo caso nft mostrará más información sobre el tipo.

TIPOS DE DATOS

Los tipos de datos determinan el tamaño, el análisis y la representación de valores simbólicos y la compatibilidad de tipos de las expresiones. Existen varios tipos de datos globales; además, algunos tipos de expresión definen tipos de datos adicionales específicos del tipo de expresión. La mayoría de los tipos de datos tienen un tamaño fijo, pero algunos pueden tener un tamaño dinámico, por ejemplo, el tipo string. Algunos tipos también tienen constantes simbólicas predefinidas. Estas se pueden enumerar usando el comando describe de nft:

$ nft describe ct_state

invalid                         0x00000001
new ...

Socket expression can be used to search for an existing open TCP/UDP socket and its attributes that can be associated with a packet. It looks for an established or non-zero bound listening socket (possibly with a non-local address). You can also use it to match on the socket cgroupv2 at a given ancestor level, e.g. if the socket belongs to cgroupv2 a/b, ancestor level 1 checks for a matching on cgroup a and ancestor level 2 checks for a matching on cgroup b.

HASH EXPRESSION

The hash expression matches packets based on a hash value derived from specified fields. This can be used to distribute traffic across multiple chains or rules.

Modifiers.

* random: Use a random hash. The value is a number between 0 and 100.
* src: Use the source field as the hash input.
* dst: Use the destination field as the hash input.
* both: Use both source and destination fields as the hash input.

Attributes.

* eth: Use the Ethernet MAC address.
* ip: Use the IP address.
* sport: Use the source port.
* dport: Use the destination port.

Ranges.

A range is specified as a start and end value, separated by a hyphen. For example, 0-100.

table inet filter {

fib TUPLA_FIB RESULTADO_FIB
TUPLA_FIB := { saddr | daddr} [ . { iif | oif } . mark ]
RESULTADO_FIB  := { oif | oifname | check | type }

Una expresión fib consulta la fib (tabla de información de reenvío) para obtener información como el índice de la interfaz de salida.

Los primeros argumentos de la expresión fib son las claves de entrada que se pasarán a la función de búsqueda fib. Se requiere una de las opciones saddr o daddr, y son mutuamente excluyentes.

Las palabras clave mark, iif y oif son modificadores opcionales para influir en el resultado de la búsqueda, consulte la tabla de palabras clave TUPLA_FIB a continuación para obtener una descripción. Las palabras clave de tupla iif y oif también son mutuamente excluyentes.

El último argumento de la expresión fib es el tipo de resultado deseado.

oif solicita obtener el índice de la interfaz que se utilizaría para enviar paquetes a la fuente (clave saddr) o destino (clave daddr) de los paquetes. Si no se encuentra ninguna entrada de enrutamiento, el índice de interfaz devuelto es 0.

oifname es similar a oif, pero rellena el nombre de la interfaz en su lugar. Esto es útil para comprobar interfaces dinámicas como dispositivos ppp. Si no se encuentra ninguna entrada, se devuelve un nombre de interfaz vacío.

type devuelve el tipo de dirección, como unicast o multicast. Una lista completa de tipos de dirección admitidos se puede mostrar con nft describe fib_addrtype.

Tabla 31. Palabras clave de FIB_TUPLE

clave Descripción
daddr Realizar una búsqueda de ruta normal: buscar en la fib una ruta hacia la dirección de destino del paquete.
saddr Realizar una búsqueda de ruta inversa: buscar en la fib una ruta hacia la dirección de origen del paquete.
mark Considerar la marca del paquete (nfmark) al consultar la fib.
iif Si las búsquedas de fib proporcionan una ruta, comprobar que su interfaz de salida sea idéntica a la interfaz de entrada del paquete.

El resultado oif y oifname solo es válido en los ganchos prerouting, input y forward. El tipo type se puede consultar en cualquiera de los ganchos prerouting, input, forward output y postrouting.

Para type, la presencia de la palabra clave iif en los modificadores de TUPLA_FIB restringe los ganchos disponibles a aquellos donde el paquete está asociado con una interfaz de entrada, es decir, prerouting, input y forward. Igualmente, la palabra clave oif en la lista de modificadores de TUPLA_FIB limitará los ganchos disponibles a forward, output y postrouting.

Uso de expresiones fib.

# descartar paquetes sin ruta de retorno
filter prerouting fib saddr . iif oif missing drop
En este ejemplo, 'saddr . iif' busca una ruta hacia la *dirección de origen* del paquete y restringe los resultados coincidentes a la interfaz por la que llegó el paquete, luego almacena el índice de la interfaz de salida del resultado de la fib obtenido.
Si no se encontró ninguna ruta para la combinación de dirección de origen/interfaz de entrada, el índice de la interfaz de salida es cero.
Por lo tanto, esta regla descartará todos los paquetes que no tengan una ruta de retorno estricta (el paquete de respuesta hipotético se enviaría a través de la interfaz por la que llegó el paquete probado).
Si solo se usa 'saddr oif' como clave de entrada, entonces esta regla solo descartará los paquetes para los que la fib no pueda encontrar una ruta. En la mayoría de las configuraciones, esto nunca descartará paquetes porque se devuelve la ruta predeterminada.
# descartar paquetes si la dirección ip de destino no está configurada en la interfaz de entrada
filter prerouting fib daddr . iif type != { local, broadcast, multicast } drop
Esto consulta la fib basándose en la dirección de destino del paquete actual y la interfaz de entrada.
Si el paquete se envía a una dirección unicast que está configurada en una interfaz diferente, entonces el paquete
se descartará ya que tal dirección se clasificaría como de tipo 'unicast'.
Sin el modificador 'iif', cualquier dirección configurada en la máquina local es 'local', y las direcciones unicast no configuradas en ninguna interfaz devolverían el tipo 'unicast'.
# realizar búsqueda en una tabla específica 'blackhole' (0xdead, requiere regla ip apropiada)
filter prerouting meta mark set 0xdead fib daddr . mark type vmap { blackhole : drop, prohibit : jump prohibited, unreachable : drop }

EXPRESIONES NUMGEN

numgen mod NUM [ inc NUM ] [ offset NUM ]

Utiliza una función para generar un número. El valor después de la palabra clave mod especifica un límite superior (no incluido) para los números devueltos. Las palabras clave opcionales inc y offset permiten incrementar el valor devuelto en un desplazamiento fijo.

Un caso de uso típico para numgen es el balanceo de carga:

Usando la expresión numgen.

# round-robin entre 192.168.10.100 y 192.168.20.200:
add rule nat prerouting dnat to numgen inc mod 2 map \
        { 0 : 192.168.10.100, 1 : 192.168.20.200 }
# basado en probabilidad con sesgo impar usando intervalos:
add rule nat prerouting dnat to numgen random mod 10 map \
        { 0-2 : 192.168.10.100, 3-9 : 192.168.20.200 }

EXPRESIONES HASH

jhash {ip saddr | ip6 daddr | tcp dport | udp sport | ether saddr} [. ...] mod NUM [ seed NUM ] [ offset NUM ]
symhash mod NUM [ offset NUM ]

Utiliza una función hash para generar un número. Las funciones disponibles son jhash, conocida como Jenkins Hash, y symhash, para Symmetric Hash. jhash requiere una expresión para determinar los parámetros de la cabecera del paquete a los que aplicar el hash, también son posibles las concatenaciones. El valor después de la palabra clave mod especifica un límite superior (no incluido) para los números devueltos. La palabra clave opcional seed se usa para especificar un valor inicial utilizado como semilla en la función hash. La palabra clave opcional offset permite incrementar el valor devuelto en un desplazamiento fijo.

Un caso de uso típico para jhash y symhash es el balanceo de carga:

Usando expresiones hash.

# balanceo de carga basado en la IP de origen entre 2 direcciones IP:
add rule nat prerouting dnat to jhash ip saddr mod 2 map \
        { 0 : 192.168.10.100, 1 : 192.168.20.200 }
# balanceo de carga simétrico entre 2 direcciones IP:
add rule nat prerouting dnat to symhash mod 2 map \
        { 0 : 192.168.10.100, 1 : 192.168.20.200 }

DECLARACIONES

Las declaraciones representan acciones a realizar. Pueden alterar el flujo de control (retornar, saltar a otra cadena, aceptar o descartar el paquete) o realizar acciones, como registrar, rechazar un paquete, etc.

Las declaraciones existen en dos tipos. Las declaraciones terminales terminan incondicionalmente la evaluación de la regla actual, las declaraciones no terminales terminan solo condicionalmente o nunca la evaluación de la regla actual, en otras palabras, son pasivas desde la perspectiva de la evaluación del conjunto de reglas. Puede haber una cantidad arbitraria de declaraciones no terminales en una regla, pero solo una única declaración terminal como declaración final.

DECLARACIÓN DE VEREDICTO

La declaración de veredicto altera el flujo de control en el conjunto de reglas y emite decisiones de política para los paquetes.

{accept | drop | queue | continue | return}
{jump | goto} CADENA
CADENA := nombre_cadena | { declaración ... }

accept y drop son veredictos absolutos: terminan la evaluación del conjunto de reglas inmediatamente.

accept Termina la evaluación del conjunto de reglas y acepta el paquete. El paquete aún puede ser descartado más tarde por otro hook, por ejemplo, aceptar en el hook de reenvío aún permite descartar el paquete más tarde en el hook de postrouting, o en otra cadena base de reenvío que tenga un número de prioridad más alto y se evalúe después en la canalización de procesamiento.
drop Termina la evaluación del conjunto de reglas y descarta el paquete. El descarte ocurre instantáneamente, no se evalúan más cadenas o hooks. No es posible aceptar el paquete en una cadena posterior nuevamente, ya que estas ya no se evalúan para el paquete.
queue Termina la evaluación del conjunto de reglas y pone el paquete en cola para el espacio de usuario. El espacio de usuario debe proporcionar un veredicto de descarte o aceptación. En caso de aceptación, el procesamiento se reanuda con el siguiente hook de cadena base, no con la regla que sigue al veredicto de cola.
continue Continúa la evaluación del conjunto de reglas con la siguiente regla. Este es el comportamiento predeterminado en caso de que una regla no emita ningún veredicto.
return Retorna de la cadena actual y continúa la evaluación en la siguiente regla de la última cadena. Si se emite en una cadena base, es equivalente a la política de la cadena base.
jump CADENA Continúa la evaluación en la primera regla de CADENA. La posición actual en el conjunto de reglas se empuja a una pila de llamadas y la evaluación continuará allí cuando la nueva cadena se evalúe completamente o se emita un veredicto de return. En caso de que una regla en la cadena emita un veredicto absoluto, la evaluación del conjunto de reglas termina inmediatamente y se toma la acción específica.
goto CADENA Similar a jump, pero la posición actual no se empuja a la pila de llamadas, lo que significa que después de la nueva cadena, la evaluación continuará en la última cadena en lugar de la que contiene la declaración goto.

Una alternativa a especificar el nombre de una cadena regular existente en CADENA es especificar una cadena anónima ad-hoc. Al igual que con los conjuntos anónimos, no se puede hacer referencia desde otra regla y se eliminará junto con la regla que la contiene.

Usando declaraciones de veredicto.

# procesar paquetes de eth0 y la red interna en from_lan
# cadena, descartar todos los paquetes de eth0 con direcciones de origen diferentes.
filter input iif eth0 ip saddr 192.168.0.0/24 jump from_lan
filter input iif eth0 drop
# las declaraciones jump y goto admiten la creación de cadenas anónimas
filter input iif eth0 jump { ip saddr 192.168.0.0/24 drop ; udp dport domain drop; }

DECLARACIÓN DE REGISTRO

log [prefix cadena_entrecomillada] [level nivel_syslog] [flags banderas_registro]
log group grupo_nflog [prefix cadena_entrecomillada] [queue-threshold valor] [snaplen tamaño]
log level audit

La declaración de registro permite el registro de paquetes que coinciden. Cuando se utiliza esta declaración desde una regla, el kernel de Linux imprimirá información sobre todos los paquetes que coinciden, como campos de encabezado, a través del registro del kernel (donde se puede leer con dmesg(1) o leer en syslog).

En la segunda forma de invocación (si se especifica grupo_nflog), el kernel de Linux pasará el paquete a nfnetlink_log, que enviará el registro a través de un socket netlink al grupo especificado. Un proceso de espacio de usuario puede suscribirse al grupo para recibir los registros; consulte man(8) ulogd para ver el demonio de registro de espacio de usuario Netfilter y la documentación de libnetfilter_log en caso de que desee desarrollar un programa personalizado para digerir sus registros.

En la tercera forma de invocación (si se especifica el nivel audit), el kernel de Linux escribe un mensaje en el búfer de auditoría adecuadamente formateado para ser leído con auditd. Por lo tanto, no se permiten opciones de formato adicionales (como prefijo o banderas) en este modo.

Esta es una declaración no terminante, por lo que la evaluación de la regla continúa después de que se registra el paquete.

LIMIT STATEMENT

limit rate [over] packet_number / TIME_UNIT [burst packet_number packets]
limit rate [over] byte_number BYTE_UNIT / TIME_UNIT [burst byte_number BYTE_UNIT]
TIME_UNIT := second | minute | hour | day
BYTE_UNIT := bytes | kbytes | mbytes

A limit statement matches at a limited rate using a token bucket filter. A rule using this statement will match until this limit is reached. It can be used in combination with the log statement to give limited logging. The optional over keyword makes it match over the specified rate.

The burst value influences the bucket size, i.e. jitter tolerance. With packet-based limit, the bucket holds exactly burst packets, by default five. If you specify packet burst, it must be a non-zero value. With byte-based limit, the bucket’s minimum size is the given rate’s byte value and the burst value adds to that, by default zero bytes.

NAT STATEMENTS

snat [[ip | ip6] [ prefix ] to] TARGET_SPEC [FLAGS]
dnat [[ip | ip6] [ prefix ] to] TARGET_SPEC [FLAGS]
masquerade [to :PORT_SPEC] [FLAGS]
redirect [to :PORT_SPEC] [FLAGS]
TARGET_SPEC := ADDR_SPEC | [ADDR_SPEC] :PORT_SPEC
ADDR_SPEC := address | address - address
PORT_SPEC := port | port - port
FLAGS  := FLAG [, FLAGS]
FLAG  := persistent | random | fully-random

The nat statements are only valid from nat chain types.

The snat and masquerade statements specify that the source address/port of the packet should be modified. While snat is only valid in the postrouting and input chains, masquerade makes sense only in postrouting. The dnat and redirect statements are only valid in the prerouting and output chains, they specify that the destination address/port of the packet should be modified. You can use non-base chains which are called from base chains of nat chain type too. All future packets in this connection will also be mangled, and rules should cease being examined.

The masquerade statement is a special form of snat which always uses the outgoing interface’s IP address to translate to. It is particularly useful on gateways with dynamic (public) IP addresses.

The redirect statement is a special form of dnat which always translates the destination address to the local host’s one. It comes in handy to intercept traffic passing a router and feeding it to a locally running daemon, e.g. when building a transparent proxy or application-layer gateway.

For TARGET_SPEC, one may specify addresses, ports, or both. If no address or no port is specified, the respective packet header field remains unchanged.

When used in the inet family (available with kernel 5.2), the dnat and snat statements require the use of the ip and ip6 keyword in case an address is provided, see the examples below.

Before kernel 4.18 nat statements require both prerouting and postrouting base chains to be present since otherwise packets on the return path won’t be seen by netfilter and therefore no reverse translation will take place.

The optional prefix keyword allows to map n source addresses to n destination addresses. See Advanced NAT examples below.

If the address for dnat is an IPv4 loopback address (i.e. 127.0.0.0/8) the "net.ipv4.conf.*.route_localnet" sysctl for the input interface needs to be set to 1. Otherwise packets will be dropped by the routing code as "martians".

DECLARACIÓN TPROXY

La declaración tproxy se utiliza para desviar el tráfico de red a un socket de escucha con la opción IP_TRANSPARENT habilitada. Esto se hace típicamente para aplicaciones de proxy o balanceadores de carga que necesitan recibir tráfico destinado a otra dirección IP. Es importante tener en cuenta que el objetivo tproxy no es terminal, lo que significa que el procesamiento del paquete puede continuar después de su ejecución. Esto permite acciones como registrar paquetes o marcar metadatos para el enrutamiento posterior.

La sintaxis básica para la declaración tproxy es la siguiente:

tproxy [ip | ip6] to dirección[:puerto]
tproxy to :puerto

Esta sintaxis se puede usar en tablas inet. El parámetro ip/ip6 define la familia de la regla que coincidirá. El parámetro dirección debe ser de esta familia. Cuando solo se define puerto, la familia de direcciones no debe especificarse. En este caso, la regla coincidirá para ambas familias.

Nombre Descripción
dirección Dirección IP a la que está enlazado el socket de escucha con la opción IP_TRANSPARENT.
puerto Puerto al que está enlazado el socket de escucha con la opción IP_TRANSPARENT.

Reglas de ejemplo para la declaración tproxy.

table ip x {
    chain y {
        type filter hook prerouting priority mangle; policy accept;
        tcp dport ntp tproxy to 1.1.1.1 accept
        udp dport ssh tproxy to :2222 accept
    }
}
table ip6 x {
    chain y {
       type filter hook prerouting priority mangle; policy accept;
       tcp dport ntp tproxy to [dead::beef] accept
       udp dport ssh tproxy to :2222 accept
    }
}
table inet x {
    chain y {
        type filter hook prerouting priority mangle; policy accept;
        tcp dport 321 tproxy to :22 accept
        tcp dport 99 tproxy ip to 1.1.1.1:999 accept
        udp dport 155 tproxy ip6 to [dead::beef]:smux accept
    }
}

Tenga en cuenta que la declaración tproxy no es terminal para permitir el postprocesamiento de paquetes. Esto permite registrar paquetes para depuración, así como actualizar la marca para garantizar que los paquetes se entreguen localmente a través de reglas de enrutamiento de políticas.

Reglas de ejemplo para la declaración tproxy con registro y marca de metadatos.

table inet x {
    chain y {
        type filter hook prerouting priority mangle; policy accept;
        udp dport 9999 goto {
            tproxy to :1234 log prefix "packet tproxied: " meta mark set 1 accept
            log prefix "no socket on port 1234 or not transparent?: " drop
        }
    }
}

Dado que las cabeceras de los paquetes no se modifican, los paquetes podrían ser reenviados en lugar de entregados localmente. Como se mencionó anteriormente, esto se puede evitar agregando reglas de enrutamiento de políticas y la marca del paquete.

Reglas de enrutamiento de políticas de ejemplo para redireccionamiento local.

ip rule add fwmark 1 lookup 100
ip route add local 0.0.0.0/0 dev lo table 100

Este es un cambio de comportamiento en comparación con el objetivo TPROXY de iptables heredado, que es terminal. Para terminar el procesamiento del paquete después de la declaración tproxy, recuerde emitir un veredicto como en el ejemplo anterior.

STATEMENT FORMAT

The nft command language is a stateless, expression language that describes the packet processing policy. It consists of statements that are used to add or delete objects, to iterate over them, or to emit them to standard output.

Statements are separated by newlines or semicolons.

Statements can be grouped into blocks using curly braces { }.

Statements can be commented using # to the end of the line.

COMMENT STATEMENT

This statement is used to add comments to the ruleset. Any text after the # character is ignored.

# This is a comment.
# This line is also a comment.

DEFINE STATEMENT

This statement is used to define aliases for frequently used expressions. These aliases can then be used in ruleset in place of the full expression.

define NAME = expression

Define a name for a port range.

define RFC1918 = 192.168.0.0/16
define webports = { 80, 443 }
nft add rule ip filter input ip saddr $RFC1918 tcp dport $webports accept

CLONE STATEMENT

The clone statement is used to clone a packet and direct it to another destination. It is only available in the netdev family ingress and egress hooks.

clone to interface [ src address ] [ dst address ]

Example usage.

# clone packet to eth1
netdev ingress clone to "eth1"
# clone packet to eth1, set source address to 192.168.1.1 and destination to 192.168.1.2
netdev ingress clone to "eth1" src 192.168.1.1 dst 192.168.1.2

DUP STATEMENT

The dup statement is used to duplicate a packet and send the copy to another interface. This is useful for network taps or packet capturing. It is only available in the netdev family ingress and egress hooks.

dup to interface [ src address ] [ dst address ]

Using the dup statement.

# duplicate packet to eth0
netdev ingress dup to "eth0"
# duplicate packet to eth1, set source address to 192.168.1.1 and destination to 192.168.1.2
netdev ingress dup to "eth1" src 192.168.1.1 dst 192.168.1.2

The dup statement can also be used in conjunction with maps to specify the destination interface based on the source IP address.

dup to ip daddr map { 192.168.7.1 : "eth0", 192.168.7.2 : "eth1" }

FWD STATEMENT

The fwd statement is used to redirect a raw packet to another interface. It is only available in the netdev family ingress and egress hooks. It is similar to the dup statement except that no copy is made.

You can also specify the address of the next hop and the device to forward the packet to. This updates the source and destination MAC address of the packet by transmitting it through the neighboring layer. This also decrements the ttl field of the IP packet. This provides a way to effectively bypass the classical forwarding path, thus skipping the fib (forwarding information base) lookup.

fwd to device
fwd [ip | ip6] to address device device

Using the fwd statement.

# redirect raw packet to device
netdev ingress fwd to "eth0"
# forward packet to next hop 192.168.200.1 via eth0 device
netdev ingress ether saddr set fwd ip to 192.168.200.1 device "eth0"

SET STATEMENT

The set statement is used to dynamically add or update elements in a set from the packet path. The set setname must already exist in the given table and must have been created with one or both of the dynamic and the timeout flags. The dynamic flag is required if the set statement expression includes a stateful object. The timeout flag is implied if the set is created with a timeout, and is required if the set statement updates elements, rather than adding them. Furthermore, these sets should specify both a maximum set size (to prevent memory exhaustion), and their elements should have a timeout (so their number will not grow indefinitely) either from the set definition or from the statement that adds or updates them. The set statement can be used to e.g. create dynamic blacklists.

Dynamic updates are also supported with maps. In this case, the add or update rule needs to provide both the key and the data element (value), separated via :.

{add | update} @setname { expression [timeout timeout] [comment string] }

Example for simple blacklist.

# declare a set, bound to table "filter", in family "ip".
# Timeout and size are mandatory because we will add elements from packet path.
# Entries will timeout after one minute, after which they might be
# re-added if limit condition persists.
nft add set ip filter blackhole \
    "{ type ipv4_addr; flags dynamic; timeout 1m; size 65536; }"
# declare a set to store the limit per saddr.
# This must be separate from blackhole since the timeout is different
nft add set ip filter flood \
    "{ type ipv4_addr; flags dynamic; timeout 10s; size 128000; }"
# whitelist internal interface.
nft add rule ip filter input meta iifname "internal" accept
# drop packets coming from blacklisted ip addresses.
nft add rule ip filter input ip saddr @blackhole counter drop
# add source ip addresses to the blacklist if more than 10 tcp connection
# requests occurred per second and ip address.
nft add rule ip filter input tcp flags syn tcp dport ssh \
    add @flood { ip saddr limit rate over 10/second } \
    add @blackhole { ip saddr } \
    drop
# inspect state of the sets.
nft list set ip filter flood
nft list set ip filter blackhole
# manually add two addresses to the blackhole.
nft add element filter blackhole { 10.2.3.4, 10.23.1.42 }

MAP STATEMENT

The map statement is used to lookup data based on some specific input key.

expression map { MAP_ELEMENTS }
MAP_ELEMENTS := MAP_ELEMENT [, MAP_ELEMENTS]
MAP_ELEMENT  := key : value

The key is a value returned by expression.

Using the map statement.

# select DNAT target based on TCP dport:
# connections to port 80 are redirected to 192.168.1.100,
# connections to port 8888 are redirected to 192.168.1.101
nft add rule ip nat prerouting dnat tcp dport map { 80 : 192.168.1.100, 8888 : 192.168.1.101 }
# source address based SNAT:
# packets from net 192.168.1.0/24 will appear as originating from 10.0.0.1,
# packets from net 192.168.2.0/24 will appear as originating from 10.0.0.2
nft add rule ip nat postrouting snat to ip saddr map { 192.168.1.0/24 : 10.0.0.1, 192.168.2.0/24 : 10.0.0.2 }

VMAP STATEMENT

The verdict map (vmap) statement works analogous to the map statement, but contains verdicts as values.

expression vmap { VMAP_ELEMENTS }
VMAP_ELEMENTS := VMAP_ELEMENT [, VMAP_ELEMENTS]
VMAP_ELEMENT  := key : verdict

Using the vmap statement.

# jump to different chains depending on layer 4 protocol type:
nft add rule ip filter input ip protocol vmap { tcp : jump tcp-chain, udp : jump udp-chain , icmp : jump icmp-chain }

XT STATEMENT

This represents an xt statement from xtables compat interface. It is a fallback if translation is not available or not complete.

Seeing this means the ruleset (or parts of it) were created by iptables-nft and one should use that to manage it.

ADDITIONAL COMMANDS

These are some additional commands included in nft.

LIST HOOKS

This shows the list of functions that have been registered for the given protocol family, including functions that have been registered implicitly by kernel modules such as nf_conntrack.

list hooks [family]
list hooks netdev [ device DEVICE_NAME ]

list hooks is enough to display everything that is active on the system. Hooks in the netdev family are tied to a network device. If no device name is given, nft will query all network devices in the current network namespace. Example Usage:

List all active netfilter hooks in either the ip or ip6 stack.

% nft list hooks inet
family ip {
        hook prerouting {
                -0000000400 ipv4_conntrack_defrag [nf_defrag_ipv4]
                -0000000200 ipv4_conntrack_in [nf_conntrack]
                -0000000100 nf_nat_ipv4_pre_routing [nf_nat]
        }
        hook input {
                 0000000000 chain inet filter input [nf_tables]
                +0000000100 nf_nat_ipv4_local_in [nf_nat]
[..]

The above shows a host that has nat, conntrack and ipv4 packet defragmentation enabled. For each hook location for the queried family a list of active hooks using the format

priority identifier [module_name]

will be shown.

The priority value dictates the order in which the hooks are called. The list is sorted, the lowest number is run first.

The priority value of hooks registered by the kernel cannot be changed. For basechains registered by nftables, this value corresponds to the priority value specified in the base chain definition.

After the numerical value, information about the hook is shown. For basechains defined in nftables this includes the table family, the table name and the basechains name. For hooks coming from kernel modules, the function name is used instead.

If a module name is given, the hook was registered by the kernel module with this name. You can use modinfo module name to obtain more information about the module.

This functionality requires a kernel built with the option CONFIG_NETFILTER_NETLINK_HOOK enabled, either as a module or builtin. The module is named nfnetlink_hook.

MONITOR

The monitor command allows you to listen to Netlink events produced by the nf_tables subsystem. These are either related to creation and deletion of objects or to packets for which meta nftrace was enabled. When they occur, nft will print to stdout the monitored events in either JSON or native nft format.

monitor [new | destroy] MONITOR_OBJECT
monitor trace
MONITOR_OBJECT := tables | chains | sets | rules | elements | ruleset

To filter events related to a concrete object, use one of the keywords in MONITOR_OBJECT.

To filter events related to a concrete action, use keyword new or destroy.

The second form of invocation takes no further options and exclusively prints events generated for packets with nftrace enabled.

Hit ^C to finish the monitor operation.

Listen to all events, report in native nft format.

% nft monitor

Listen to deleted rules, report in JSON format.

% nft -j monitor destroy rules

Listen to both new and destroyed chains, in native nft format.

% nft monitor chains

Listen to ruleset events such as table, chain, rule, set, counters and quotas, in native nft format.

% nft monitor ruleset

Trace incoming packets from host 10.0.0.1.

% nft add rule filter input ip saddr 10.0.0.1 meta nftrace set 1
% nft monitor trace

ESTADO DE SALIDA

En caso de éxito, nft sale con un estado de 0. Los errores no especificados provocan que salga con un estado de 1, los errores de asignación de memoria con un estado de 2, y la incapacidad de abrir un socket Netlink con 3.
