NOMBRE

nfsdcld - Demonio de rastreo de clientes NFSv4

SINOPSIS

nfsdcld [-d] [-F] [-p ruta] [-s dir de almacenamiento estable]

DESCRIPCIÓN

nfsdcld es el demonio de rastreo de clientes NFSv4. No es necesario ejecutar este demonio en máquinas que no actúen como servidores NFSv4.

Cuando una partición de red se combina con un reinicio del servidor, existen condiciones límite que pueden hacer que el servidor otorgue la recuperación de bloqueos cuando otros clientes han tomado bloqueos en conflicto en el ínterin. Una explicación más detallada de este problema se describe en la RFC 3530, sección 8.6.3.

Para evitar estos problemas, el servidor debe rastrear una pequeña cantidad de información por cliente en almacenamiento estable. Este demonio proporciona la pieza del espacio de usuario de esa funcionalidad.

OPCIONES

-d, --debug
Habilita el registro de nivel de depuración.
-F, --foreground
Ejecuta el demonio en primer plano e imprime toda la salida en stderr
-p ruta, --pipefsdir=ruta
Ubicación del sistema de archivos rpc_pipefs. El valor predeterminado es /var/lib/nfs/rpc_pipefs.
-s dir_almacenamiento, --storagedir=dir_almacenamiento
Directorio donde se debe mantener la información de almacenamiento estable. El valor predeterminado es /var/lib/nfs/nfsdcld.

ARCHIVO DE CONFIGURACIÓN

Los siguientes valores se reconocen en la sección [nfsdcld] del archivo de configuración /etc/nfs.conf:

storagedir
Equivalente a -s/--storagedir.
debug
Establecer "debug = 1" es equivalente a -d/--debug.

Además, el siguiente valor se reconoce de la sección [general]:

pipefs-directory
Equivalente a -p/--pipefsdir.

NOTAS

El servidor NFSv4 del kernel de Linux ha rastreado históricamente esta información en almacenamiento estable manipulando información en el sistema de archivos directamente, en el directorio al que apunta /proc/fs/nfsd/nfsv4recoverydir.

Esto cambió con la introducción original de la llamada `upcall` de nfsdcld en la versión del kernel 3.4, que luego fue depreciada en favor del programa `usermodehelper` nfsdcltrack(8), cuyo soporte se añadió en la versión del kernel 3.8. Sin embargo, dado que la llamada `upcall` de `usermodehelper` no funciona en contenedores, se añadió soporte para una nueva versión de la llamada `upcall` de nfsdcld en la versión del kernel 5.2.

Este demonio requiere un kernel que soporte la llamada `upcall` de nfsdcld. En kernels más antiguos, si se utilizaba el código heredado de rastreo de nombres de cliente, el kernel no crearía la tubería que nfsdcld utiliza para comunicarse con el kernel. En kernels más nuevos, nfsd intenta inicializar el rastreo de clientes en el siguiente orden: Primero, la llamada `upcall` de nfsdcld. Segundo, la llamada `upcall` de `usermodehelper` de nfsdcltrack. Finalmente, el rastreo de clientes heredado.

Este demonio debe ejecutarse como root, ya que la tubería que utiliza para comunicarse con el kernel solo es accesible por root. Sin embargo, el demonio elimina todas las capacidades de superusuario después de arrancar. Debido a esto, el storagedir debe ser propiedad de root, y ser legible y escribible por el propietario.

El demonio ahora soporta diferentes versiones de `upcall` para permitir que el kernel pase datos adicionales para ser almacenados en la base de datos en disco. El kernel consultará la versión de `upcall` soportada de nfsdcld durante la inicialización del rastreo de clientes. No es necesario reiniciar nfsd después de actualizar nfsdcld; sin embargo, nfsd no utilizará una versión posterior de `upcall` hasta que se reinicie. Es necesario reiniciar nfsd después de degradar nfsdcld, para asegurar que nfsd no utilice una versión de `upcall` que nfsdcld no soporte. Además, una degradación de nfsdcld requiere que el esquema de la base de datos en disco también se degrade. Eso se puede lograr utilizando la utilidad nfsdclddb(8).
