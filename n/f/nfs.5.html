NFS(5) Manual de formatos de archivo NFS(5)

NOMBRE

nfs - Formato y opciones de fstab para los sistemas de archivos nfs

SINOPSIS

/etc/fstab

DESCRIPCIÓN

NFS es un protocolo estándar de Internet creado por Sun Microsystems en 1984. NFS se desarrolló para permitir el intercambio de archivos entre sistemas ubicados en una red de área local. Dependiendo de la configuración del kernel, el cliente NFS de Linux puede admitir las versiones 3, 4.0, 4.1 o 4.2 de NFS.

El comando mount(8) monta un sistema de archivos en la jerarquía de espacios de nombres del sistema en un punto de montaje dado. El archivo /etc/fstab describe cómo mount(8) debe ensamblar la jerarquía de nombres de archivo de un sistema a partir de varios sistemas de archivos independientes (incluidos los sistemas de archivos exportados por servidores NFS). Cada línea en el archivo /etc/fstab describe un único sistema de archivos, su punto de montaje y un conjunto de opciones de montaje predeterminadas para ese punto de montaje.

Para montajes de sistemas de archivos NFS, una línea en el archivo /etc/fstab especifica el nombre del servidor, el nombre de ruta del directorio exportado del servidor a montar, el directorio local que es el punto de montaje, el tipo de sistema de archivos que se está montando y una lista de opciones de montaje que controlan cómo se monta el sistema de archivos y cómo se comporta el cliente NFS al acceder a archivos en este punto de montaje. Los campos quinto y sexto de cada línea no son utilizados por NFS, por lo que convencionalmente cada uno contiene el dígito cero. Por ejemplo:

servidor:ruta	/punto_montaje	tipo_fs	opcion,opcion,...	0 0

El nombre de host del servidor y la ruta exportada están separados por dos puntos, mientras que las opciones de montaje están separadas por comas. Los campos restantes están separados por espacios en blanco o tabulaciones.

El nombre de host del servidor puede ser un nombre de host no calificado, un nombre de dominio completamente calificado, una dirección IPv4 de punto cuádruple o una dirección IPv6 entre corchetes. Las direcciones IPv6 de enlace local y de sitio local deben ir acompañadas de un identificador de interfaz. Consulte ipv6(7) para obtener detalles sobre cómo especificar direcciones IPv6 en bruto.

El campo tipo_fs contiene "nfs". El uso del tipo de sistema de archivos "nfs4" en /etc/fstab está obsoleto.

OPCIONES DE MONTAJE

Consulte mount(8) para obtener una descripción de las opciones de montaje genéricas disponibles para todos los sistemas de archivos. Si no necesita especificar ninguna opción de montaje, utilice la opción genérica defaults en /etc/fstab.

Opciones soportadas por todas las versiones

Estas opciones son válidas para usar con cualquier versión de NFS.

nfsvers=n
El número de versión del protocolo NFS utilizado para contactar el servicio NFS del servidor. Si el servidor no admite la versión solicitada, la solicitud de montaje falla. Si esta opción no se especifica, el cliente intenta primero la versión 4.2, luego negocia hacia abajo hasta que encuentra una versión admitida por el servidor.
vers=n
Esta opción es una alternativa a la opción nfsvers. Se incluye por compatibilidad con otros sistemas operativos.
soft / softerr / hard
Determina el comportamiento de recuperación del cliente NFS después de que una solicitud NFS caduca. Si no se especifica ninguna opción (o si se especifica la opción hard), las solicitudes NFS se reintentan indefinidamente. Si se especifica la opción soft o softerr, el cliente NFS falla una solicitud NFS después de que se hayan enviado retrans reintentos, provocando que el cliente NFS devuelva el error EIO (para la opción soft) o ETIMEDOUT (para la opción softerr) a la aplicación que llama.
Nota: Un tiempo de espera supuestamente "suave" puede causar corrupción silenciosa de datos en ciertos casos. Por lo tanto, use la opción soft o softerr solo cuando la capacidad de respuesta del cliente sea más importante que la integridad de los datos. Usar NFS sobre TCP o aumentar el valor de la opción retrans puede mitigar algunos de los riesgos de usar la opción soft o softerr.
softreval / nosoftreval
En casos donde el servidor NFS está caído, puede ser útil permitir que el cliente NFS continúe sirviendo rutas y atributos de la caché después de que los intentos de retrans para revalidar esa caché hayan caducado. Esto puede ser útil, por ejemplo, al intentar desmontar un árbol de sistema de archivos de un servidor que está permanentemente caído.
Es posible combinar softreval con la opción de montaje soft, en cuyo caso las operaciones que no se pueden servir desde la caché caducarán y devolverán un error después de retrans intentos. La combinación con la opción de montaje predeterminada hard implica que las operaciones no en caché continuarán reintentándose hasta que se reciba una respuesta del servidor.
Nota: la opción de montaje predeterminada es nosoftreval, que no permite recurrir a la caché cuando falla la revalidación, y en su lugar sigue el comportamiento dictado por la opción de montaje hard o soft.
intr / nointr
Esta opción se proporciona por compatibilidad con versiones anteriores. Se ignora después del kernel 2.6.25.
timeo=n
El tiempo en decisegundos (décimas de segundo) que el cliente NFS espera una respuesta antes de reintentar una solicitud NFS.
Para NFS sobre TCP, el valor timeo predeterminado es 600 (60 segundos). El cliente NFS realiza un retroceso lineal: después de cada retransmisión, el tiempo de espera se incrementa en timeo hasta un máximo de 600 segundos.
Sin embargo, para NFS sobre UDP, el cliente utiliza un algoritmo adaptativo para estimar un valor de tiempo de espera adecuado para los tipos de solicitud usados con frecuencia (como las solicitudes READ y WRITE), pero utiliza la configuración timeo para los tipos de solicitud usados con poca frecuencia (como las solicitudes FSINFO). Si la opción timeo no se especifica, las solicitudes de uso infrecuente se reintentan después de 1.1 segundos. Después de cada retransmisión, el cliente NFS duplica el tiempo de espera para esa solicitud, hasta una longitud máxima de tiempo de espera de 60 segundos.
Cualquier valor de timeo mayor que el valor predeterminado se establecerá en el valor predeterminado. Para TCP y RDMA, el valor predeterminado es 600 (60 segundos). Para UDP, el valor predeterminado es 60 (6 segundos).
retrans=n
El número de veces que el cliente NFS reintenta una solicitud antes de intentar una acción de recuperación adicional. Si la opción retrans no se especifica, el cliente NFS intenta cada solicitud UDP tres veces y cada solicitud TCP dos veces.
El cliente NFS genera un mensaje de "el servidor no responde" después de retrans reintentos, luego intenta una recuperación adicional (dependiendo de si la opción de montaje hard está en vigor).
rsize=n
El número máximo de bytes en cada solicitud READ de red que el cliente NFS puede recibir al leer datos de un archivo en un servidor NFS. El tamaño real de la carga útil de datos de cada solicitud NFS READ es igual o menor que la configuración de rsize. La carga útil de lectura más grande admitida por el cliente NFS de Linux es 1.048.576 bytes (un megabyte).
El valor rsize permitido es un múltiplo entero positivo del tamaño de página del sistema o una potencia de dos si es menor que el tamaño de página del sistema. Los valores de rsize especificados inferiores a 1024 se reemplazan por 4096; los valores superiores a 1048576 se reemplazan por 1048576. Si un valor especificado está dentro del rango admitido pero no es un valor permitido, se redondea hacia abajo al valor permitido más cercano.
Si no se especifica un valor de rsize, o si el valor de rsize especificado es mayor que el máximo que el cliente o el servidor pueden admitir, el cliente y el servidor negocian el valor de rsize más grande que ambos pueden admitir.
La opción de montaje rsize especificada en la línea de comandos de mount(8) aparece en el archivo /etc/mtab. Sin embargo, el e
fectivo valor rsize negociado por el cliente y el servidor se informa en el archivo /proc/mounts.
wsize=n
El número máximo de bytes por solicitud de escritura de red que el cliente NFS puede enviar al escribir datos en un archivo en un servidor NFS. El tamaño real de la carga útil de datos de cada solicitud de escritura NFS es igual o inferior a la configuración wsize. La carga útil de escritura más grande admitida por el cliente NFS de Linux es de 1.048.576 bytes (un megabyte).
Similar a rsize, el valor permitido de wsize es un múltiplo integral positivo del tamaño de página del sistema o una potencia de dos si es inferior al tamaño de página del sistema. Los valores de wsize especificados inferiores a 1024 se reemplazan por 4096; los valores superiores a 1048576 se reemplazan por 1048576. Si un valor especificado está dentro del rango admitido pero no es un valor permitido, se redondea a la baja al valor permitido más cercano.
Si no se especifica un valor wsize, o si el valor wsize especificado es mayor que el máximo que el cliente o el servidor pueden admitir, el cliente y el servidor negocian el valor wsize más grande que ambos pueden admitir.
La opción de montaje wsize especificada en la línea de comandos de mount(8) aparece en el archivo /etc/mtab. Sin embargo, el valor efectivo wsize negociado por el cliente y el servidor se informa en el archivo /proc/mounts.
ac / noac
Selecciona si el cliente puede almacenar en caché los atributos del archivo. Si no se especifica ninguna de las opciones (o si se especifica ac), el cliente almacena en caché los atributos del archivo.
Para mejorar el rendimiento, los clientes NFS almacenan en caché los atributos de los archivos. Cada pocos segundos, un cliente NFS verifica la versión del servidor de los atributos de cada archivo en busca de actualizaciones. Los cambios que ocurren en el servidor en esos pequeños intervalos permanecen sin detectar hasta que el cliente verifica el servidor nuevamente. La opción noac evita que los clientes almacenen en caché los atributos de los archivos, de modo que las aplicaciones puedan detectar cambios en los archivos en el servidor más rápidamente.
Además de evitar que el cliente almacene en caché los atributos de los archivos, la opción noac fuerza que las escrituras de aplicaciones sean síncronas, de modo que los cambios locales en un archivo sean visibles en el servidor inmediatamente. De esa manera, otros clientes pueden detectar rápidamente escrituras recientes cuando verifican los atributos del archivo.
El uso de la opción noac proporciona una mayor coherencia de caché entre los clientes NFS que acceden a los mismos archivos, pero tiene una penalización de rendimiento significativa. Como tal, se recomienda el uso juicioso del bloqueo de archivos en su lugar. La sección COHERENCIA DE DATOS Y METADATOS contiene una discusión detallada de estas compensaciones.
acregmin=n
El tiempo mínimo (en segundos) que el cliente NFS almacena en caché los atributos de un archivo regular antes de solicitar información de atributos actualizada a un servidor. Si no se especifica esta opción, el cliente NFS utiliza un mínimo de 3 segundos. Consulte la sección COHERENCIA DE DATOS Y METADATOS para obtener una discusión completa sobre el almacenamiento en caché de atributos.
acregmax=n
El tiempo máximo (en segundos) que el cliente NFS almacena en caché los atributos de un archivo regular antes de solicitar información de atributos actualizada a un servidor. Si no se especifica esta opción, el cliente NFS utiliza un máximo de 60 segundos. Consulte la sección COHERENCIA DE DATOS Y METADATOS para obtener una discusión completa sobre el almacenamiento en caché de atributos.
acdirmin=n
El tiempo mínimo (en segundos) que el cliente NFS almacena en caché los atributos de un directorio antes de solicitar información de atributos actualizada a un servidor. Si no se especifica esta opción, el cliente NFS utiliza un mínimo de 30 segundos. Consulte la sección COHERENCIA DE DATOS Y METADATOS para obtener una discusión completa sobre el almacenamiento en caché de atributos.
acdirmax=n
El tiempo máximo (en segundos) que el cliente NFS almacena en caché los atributos de un directorio antes de solicitar información de atributos actualizada a un servidor. Si no se especifica esta opción, el cliente NFS utiliza un máximo de 60 segundos. Consulte la sección COHERENCIA DE DATOS Y METADATOS para obtener una discusión completa sobre el almacenamiento en caché de atributos.
actimeo=n
El uso de actimeo establece todos los valores de acregmin, acregmax, acdirmin y acdirmax al mismo valor. Si no se especifica esta opción, el cliente NFS utiliza los valores predeterminados para cada una de estas opciones enumeradas anteriormente.
bg / fg
Determina cómo se comporta el comando mount(8) si un intento de montar una exportación falla. La opción fg hace que mount(8) salga con un estado de error si alguna parte de la solicitud de montaje expira o falla completamente. Esto se llama montaje en "primer plano" y es el comportamiento predeterminado si no se especifica ninguna de las opciones de montaje fg ni bg.
Si se especifica la opción bg, un tiempo de espera o un error hace que el comando mount(8) bifurque un hijo que continúa intentando montar la exportación. El proceso padre regresa inmediatamente con un código de salida cero. Esto se conoce como montaje en "segundo plano".
Si falta el directorio de punto de montaje local, el comando mount(8) actúa como si la solicitud de montaje hubiera expirado. Esto permite que los montajes NFS anidados especificados en /etc/fstab procedan en cualquier orden durante la inicialización del sistema, incluso si algunos servidores NFS aún no están disponibles. Alternativamente, estos problemas se pueden abordar utilizando un automontador (consulte automount(8) para obtener detalles).
nconnect=n
Al utilizar un protocolo orientado a conexión como TCP, a veces puede ser ventajoso establecer múltiples conexiones entre el cliente y el servidor. Por ejemplo, si sus clientes y/o servidores están equipados con múltiples tarjetas de interfaz de red (NIC), el uso de múltiples conexiones para distribuir la carga puede mejorar el rendimiento general. En tales casos, la opción nconnect permite al usuario especificar el número de conexiones que se deben establecer entre el cliente y el servidor hasta un límite de 16.
Tenga en cuenta que la opción nconnect también puede ser utilizada por algunos controladores pNFS para decidir cuántas conexiones establecer con los servidores de datos.
rdirplus / nordirplus
Selecciona si se utilizan las solicitudes READDIRPLUS de NFS v3 o v4. Si no se especifica esta opción, el cliente NFS utiliza una heurística para optimizar el rendimiento eligiendo READDIR vs READDIRPLUS en función de la frecuencia con la que el proceso que llama utiliza los atributos adicionales devueltos por READDIRPLUS. Algunas aplicaciones funcionan mejor si el cliente utiliza solo solicitudes READDIR para todos los directorios.
rdirplus={none|force}
Si se establece en "force", el cliente NFS siempre intenta utilizar solicitudes READDIRPLUS. Si se establece en "none", el comportamiento es el mismo que nordirplus.
retry=n
El número de minutos que el comando mount(8) reintenta una operación de montaje NFS en primer plano o segundo plano antes de rendirse. Si no se especifica esta opción, el valor predeterminado para los montajes en primer plano es de 2 minutos, y el valor predeterminado para los montajes en segundo plano es de 10000 minutos (80 minutos menos de una semana). Si se especifica un valor de cero, el comando mount(8) sale inmediatamente después del primer fallo.
Tenga en cuenta que esto solo afecta a cuántos reintentos se realizan y no afecta el retraso causado por cada reintento. Para UDP, cada reintento toma el tiempo determinado por las opciones timeo y retrans, que por defecto serán de aproximadamente 7 segundos. Para TCP, el valor predeterminado es de 3 minutos, pero los tiempos de espera de conexión TCP del sistema a veces limitarán el tiempo de espera de cada retransmisión a aproximadamente 2 minutos.
sec=flavors
Una lista separada por dos puntos de uno o más sabores de seguridad para utilizar para acceder a archivos en la exportación montada. Si el servidor no admite ninguno de estos sabores, la operación de montaje falla. Si no se especifica sec=, el cliente intenta encontrar un sabor de seguridad que tanto el cliente como el servidor admitan. Los sabores válidos son none, sys, krb5, krb5i y krb5p. Consulte la sección CONSIDERACIONES DE SEGURIDAD para obtener detalles.
sharecache / nosharecache
Determina cómo se comparten la caché de datos y la caché de atributos del cliente al montar la misma exportación más de una vez simultáneamente. El uso de la misma caché reduce los requisitos de memoria en el cliente y presenta contenido de archivo idéntico a las aplicaciones cuando el mismo archivo remoto se accede a través de diferentes puntos de montaje.
Si no se especifica ninguna opción, o si se especifica la opción sharecache, entonces se utiliza una única caché para todos los puntos de montaje que acceden a la misma exportación. Si se especifica la opción nosharecache, entonces ese punto de montaje obtiene una caché única. Tenga en cuenta que cuando las cachés de datos y atributos se comparten, las opciones de montaje del primer punto de montaje entran en vigor para montajes concurrentes posteriores de la misma exportación.
A partir del kernel 2.6.18, el comportamiento especificado por nosharecache es comportamiento de caché heredado. Esto se considera un riesgo de datos, ya que múltiples copias cacheadas del mismo archivo en el mismo cliente pueden desincronizarse después de una actualización local de una de las copias.
resvport / noresvport
Especifica si el cliente NFS debe utilizar un puerto de origen privilegiado al comunicarse con un servidor NFS para este punto de montaje. Si no se especifica esta opción, o si se especifica la opción resvport, el cliente NFS utiliza un puerto de origen privilegiado. Si se especifica la opción noresvport, el cliente NFS utiliza un puerto de origen no privilegiado. Esta opción es compatible con los kernels 2.6.28 y posteriores.

OPCIONES

acdirmax=n
Establece el tiempo de vida máximo para la información de atributos modificados de directorios a n segundos. El valor predeterminado es 60 segundos.
acdirmin=n
Establece el tiempo de vida mínimo para la información de atributos modificados de directorios a n segundos. El valor predeterminado es 30 segundos.
acregmax=n
Establece el tiempo de vida máximo para la información de atributos modificados de archivos regulares a n segundos. El valor predeterminado es 60 segundos.
acregmin=n
Establece el tiempo de vida mínimo para la información de atributos modificados de archivos regulares a n segundos. El valor predeterminado es 30 segundos.
acitimeout=n
Establece el tiempo de vida para la información de atributos en caché a n segundos. El valor predeterminado es 60 segundos.
actimeo=n
Establece tanto el tiempo de vida mínimo como el máximo para la información de atributos en caché a n segundos.
acnocto / noacnocto
El comportamiento predeterminado es que el cliente NFS considera que los atributos en caché no han expirado después de un cierre con éxito de un archivo, incluso si el tiempo de vida del atributo en caché ya ha expirado. Esto se conoce como la opción acnocto.
Si se especifica noacnocto, el cliente NFS no extiende el tiempo de vida de los atributos en caché más allá de su tiempo de vida de expiración, incluso si el cierre del archivo fue exitoso. Esto asegura que los cambios realizados por otros clientes se vean más rápidamente, pero puede degradar el rendimiento si se accede a un archivo frecuentemente.
async / sync
El cliente NFS escribe los datos en el servidor de forma asíncrona. Esto significa que el cliente no espera la confirmación del servidor antes de que una operación de escritura se considere completa. La escritura asíncrona mejora el rendimiento, pero aumenta el riesgo de pérdida de datos si el cliente o el servidor fallan antes de que los datos sean escritos en el almacenamiento persistente.
Si se especifica sync, el cliente NFS espera la confirmación del servidor antes de que una operación de escritura se considere completa. Esto garantiza que los datos se escriban de forma segura en el servidor, pero puede degradar significativamente el rendimiento.
atime / noatime / relatime
Estas opciones controlan cómo se actualiza el tiempo de último acceso (atime) a los archivos. El tiempo de último acceso se registra cada vez que se accede a un archivo. Actualizar el atime para cada acceso puede generar una gran cantidad de tráfico de metadatos en el servidor NFS, degradando el rendimiento. Las opciones son:
atime: Actualiza el atime en cada acceso. Es la opción predeterminada.
noatime: Desactiva completamente la actualización del atime. Esto mejora el rendimiento al eliminar la sobrecarga de actualizar los tiempos de acceso.
relatime: Actualiza el atime solo si el nuevo tiempo de acceso es posterior al tiempo de modificación o al tiempo de último cambio del inode, o si el archivo se ha accedido en los últimos 24 horas. Esta es una opción de compromiso que mejora el rendimiento sobre atime sin desactivar por completo la actualización del atime.
biods=n
Establece el número de procesos de E/S en segundo plano (biod) utilizados por el cliente NFS. El valor predeterminado es 8. El aumento de este valor puede mejorar el rendimiento para operaciones de lectura y escritura intensivas, pero también puede aumentar el uso de recursos.
btime=n
Establece el tiempo de vida para los atributos de directorio en caché a n segundos. El valor predeterminado es 60 segundos.
cachenfscache
Esta opción se ha eliminado y ya no tiene efecto.
cachenfscache.shared
Esta opción se ha eliminado y ya no tiene efecto.
clientaddr=addr
Especifica la dirección IP de origen que se utilizará para las conexiones NFS. Esto puede ser útil cuando un cliente tiene varias interfaces de red y desea forzar el uso de una interfaz específica para las conexiones NFS. Si no se especifica, el cliente NFS elegirá una dirección IP de origen apropiada.
closefmode=mode
Especifica cómo el cliente NFS maneja los cierres de archivos al usar la opción nocto. Los valores posibles para mode son auto, immediate y renegotiate. El valor predeterminado es auto.
cto / nocto
El cliente NFS extiende el tiempo de vida de los atributos en caché de un archivo después de un cierre exitoso. Esto puede mejorar el rendimiento al evitar la necesidad de volver a consultar los atributos del servidor. Sin embargo, puede provocar que otros clientes vean cambios en el archivo con retraso. Si se especifica nocto, el cliente no extiende el tiempo de vida de los atributos en caché después de un cierre exitoso, lo que garantiza que los cambios realizados por otros clientes se vean más rápidamente, pero puede degradar el rendimiento si se accede a un archivo frecuentemente.
debug
Habilita la depuración detallada para el cliente NFS. Esto generará una gran cantidad de información de registro y solo debe usarse cuando se intenta diagnosticar problemas.
dev / nodev
Controla si se permiten los archivos de dispositivo en el sistema de archivos montado. Por defecto, se permiten los archivos de dispositivo (dev). Si se especifica nodev, no se permitirá el acceso a los archivos de dispositivo.
dirbcsize=n
Establece el tamaño del bloque de caché de directorio. El valor predeterminado es 4096 bytes.
dirbuffcache
Habilita el almacenamiento en caché de los datos de los directorios. Esto puede mejorar el rendimiento al leer directorios, pero puede aumentar el uso de memoria.
dirheadcache
Habilita el almacenamiento en caché de los encabezados de los directorios. Esto puede mejorar el rendimiento al enumerar directorios, pero puede aumentar el uso de memoria.
dirscontext=scontext
Establece el contexto de seguridad SELinux para los directorios montados. Esto es útil para aplicar políticas de SELinux a sistemas de archivos montados.
dirsync
Asegura que las escrituras en directorios se sincronicen con el servidor antes de que se devuelvan al proceso de llamada. Esto es más seguro que la escritura asíncrona, pero puede ser más lento.
drsync / nodrsync
Controla si las escrituras en directorios se sincronizan inmediatamente con el servidor. Si se especifica drsync, las escrituras en directorios se sincronizan inmediatamente. Si se especifica nodrsync (el valor predeterminado), las escrituras en directorios se manejan de forma asíncrona.
file_bg / nofile_bg
Esta opción controla si se utilizan las escrituras en segundo plano para archivos. Si se especifica file_bg, las escrituras en archivos se realizan en segundo plano, lo que puede mejorar el rendimiento. Si se especifica nofile_bg (el valor predeterminado), las escrituras en archivos se realizan de forma síncrona.
filesize=n
Establece el tamaño máximo de archivo que el cliente NFS puede manejar. Esto se usa para notificar a las aplicaciones que el servidor puede tener limitaciones de tamaño de archivo. El valor predeterminado es 2^31-1.
fsc / nofsc
Habilita/deshabilita la caché de páginas de datos (solo lectura) en el disco local utilizando la instalación FS-Cache. Consulte cachefilesd(8) y <kernel_source>/Documentation/filesystems/caching para obtener detalles sobre cómo configurar la instalación FS-Cache. El valor predeterminado es nofsc.
intr / noint
Permite que las operaciones de NFS interrumpibles sean interrumpidas por señales. Por defecto, las operaciones de NFS no son interrumpibles. Si se monta un sistema de archivos con intr, las operaciones de NFS que se bloquean pueden ser interrumpidas por una señal. Esto es útil para evitar que los procesos se bloqueen indefinidamente si el servidor NFS no responde.
llforce
Fuerza el uso del protocolo de bloqueo de nivel de enlace (LL) con el servidor NFS. Esto se utiliza principalmente para la compatibilidad con versiones anteriores y generalmente no se recomienda para su uso con versiones modernas de NFS.
lockdir=dir
Especifica un directorio en el cliente local que se utilizará para el almacenamiento en caché de bloqueos de archivos. Esto puede mejorar el rendimiento de las operaciones de bloqueo de archivos, especialmente en redes de alta latencia.
lockreplication=policy
Especifica la política de replicación para los bloqueos de archivos. Los valores posibles son none, all, primary y secondary. Esto se utiliza en entornos de alta disponibilidad para garantizar que los bloqueos de archivos se mantengan consistentes entre múltiples servidores.
locktimeout=seconds
Establece el tiempo de espera para las solicitudes de bloqueo de archivos en el servidor NFS. Si un bloqueo no se puede adquirir dentro del tiempo especificado, la solicitud de bloqueo falla. El valor predeterminado es de 10 segundos.
lookupcache=mode
Especifica cómo el kernel gestiona su caché de entradas de directorio para un punto de montaje determinado. mode puede ser uno de all, none, pos, o positive. Esta opción se soporta en kernels 2.6.28 y posteriores.
El cliente NFS de Linux almacena en caché el resultado de todas las solicitudes NFS LOOKUP. Si la entrada de directorio solicitada existe en el servidor, el resultado se denomina *positivo*. Si la entrada de directorio solicitada no existe en el servidor, el resultado se denomina *negativo*.
Si esta opción no se especifica, o si se especifica all, el cliente asume que ambos tipos de entradas de caché de directorio son válidos hasta que expiren los atributos en caché de su directorio padre.
Si se especifica pos o positive, el cliente asume que las entradas positivas son válidas hasta que expiren los atributos en caché de su directorio padre, pero siempre revalida las entradas negativas antes de que una aplicación pueda utilizarlas.
Si se especifica none, el cliente revalida ambos tipos de entradas de caché de directorio antes de que una aplicación pueda utilizarlas. Esto permite la detección rápida de archivos que fueron creados o eliminados por otros clientes, pero puede afectar el rendimiento de la aplicación y del servidor.
La sección DATA AND METADATA COHERENCE contiene una discusión detallada de estos compromisos.
mmap / nommap
Controla si se permite la operación mmap(2) en archivos remotos. Por defecto, se permite mmap. Si se especifica nommap, no se permitirá mmap. Esto puede ser necesario para algunos sistemas de archivos o aplicaciones que no funcionan correctamente con mmap en NFS.
mountport=n
El valor numérico del puerto del servicio mountd del servidor. Si el servicio mountd del servidor no está disponible en el puerto especificado, la solicitud de montaje falla.
Si esta opción no se especifica, o si el valor del puerto especificado es 0, entonces el comando mount utiliza el número de puerto del servicio mountd anunciado por el servicio rpcbind del servidor. La solicitud de montaje falla si el servicio rpcbind del servidor no está disponible, el servicio mountd del servidor no está registrado con su servicio rpcbind, o el servicio mountd del servidor no está disponible en el puerto anunciado.
Esta opción se puede utilizar al montar un servidor NFS a través de un firewall que bloquea el protocolo rpcbind.
mountproto=netid
El transporte que el cliente NFS utiliza para transmitir solicitudes al servicio mountd del servidor NFS al realizar esta solicitud de montaje, y al desmontar posteriormente este punto de montaje.
netid puede ser uno de udp, y tcp que utilizan direcciones IPv4 o, si TI-RPC está incorporado en el comando mount.nfs, udp6, y tcp6 que utilizan direcciones IPv6.
Esta opción se puede utilizar al montar un servidor NFS a través de un firewall que bloquea un transporte particular. Cuando se utiliza en combinación con la opción proto, se pueden especificar diferentes transportes para las solicitudes mountd y las solicitudes NFS. Si el servicio mountd del servidor no está disponible a través del transporte especificado, la solicitud de montaje falla.
Consulte la sección TRANSPORT METHODS para obtener más información sobre cómo interactúa la opción de montaje mountproto con la opción de montaje proto.
mounthost=name
El nombre de host de la máquina que ejecuta mountd. Si esta opción no se especifica, el comando mount asume que el servicio mountd se ejecuta en la misma máquina que el servicio NFS.
mountvers=n
El número de versión RPC utilizado para contactar el mountd del servidor. Si esta opción no se especifica, el cliente utiliza un número de versión apropiado para la versión NFS solicitada. Esta opción es útil cuando se ejecutan múltiples servicios NFS en la misma máquina remota servidora.
namlen=n
La longitud máxima de un componente de ruta en este montaje. Si esta opción no se especifica, la longitud máxima se negocia con el servidor. En la mayoría de los casos, esta longitud máxima es de 255 caracteres.
Algunas versiones tempranas de NFS no soportaban esta negociación. El uso de esta opción asegura que pathconf(3) informe la longitud máxima de componente adecuada a las aplicaciones en tales casos.
nfsvers=n
Especifica la versión del protocolo NFS a utilizar. Los valores válidos son 2, 3, 4, 4.0, 4.1, 4.2. El valor predeterminado es intentar negociar la versión más alta soportada por el cliente y el servidor, comenzando por la versión 4.
noacl
Deshabilita el soporte de listas de control de acceso (ACL) para el sistema de archivos montado. Esto puede ser necesario si el servidor NFS no soporta ACLs o si está experimentando problemas con ACLs.
noaligndir
Esta opción deshabilita el comportamiento predeterminado de extender las operaciones de escritura de directorios a límites de página completos.
Normalmente, el cliente NFS redondea las escrituras de directorio en segundo plano no alineadas al tamaño de página del sistema, lo que puede provocar "escrituras perdidas" cuando varios clientes escriben concurrentemente en regiones distintas y no superpuestas. Utilice esta opción cuando sus aplicaciones realicen escrituras en segundo plano no alineadas y pueda garantizar que las regiones de archivo no se superponen, evitando así la necesidad de bloqueo de archivos.
noalignwrite
Esta opción deshabilita el comportamiento predeterminado de extender las operaciones de escritura en búfer a límites de página completos.
Normalmente, el cliente NFS redondea las escrituras en búfer no alineadas al tamaño de página del sistema, lo que puede provocar "escrituras perdidas" cuando varios clientes escriben concurrentemente en regiones distintas y no superpuestas. Utilice esta opción cuando sus aplicaciones realicen escrituras en búfer no alineadas y pueda garantizar que las regiones de archivo no se superponen, evitando así la necesidad de bloqueo de archivos.
nolock
Deshabilita el uso del protocolo de bloqueo de lado de banda NLM para bloquear archivos en el servidor. Cuando se utiliza la opción nolock, las aplicaciones pueden bloquear archivos, pero dichos bloqueos solo proporcionan exclusión contra otras aplicaciones que se ejecutan en el mismo cliente. Las aplicaciones remotas no se ven afectadas por estos bloqueos.
nolockd
No utiliza el demonio lockd del servidor para el bloqueo de archivos. Esto es útil cuando el servidor NFS no soporta el bloqueo de archivos o cuando se desea evitar la sobrecarga del demonio lockd.
nomaproxy
Deshabilita el uso del proxy de mapeo de autenticación. Esto se utiliza cuando se accede a un servidor NFS en un dominio de seguridad diferente o cuando se utilizan métodos de autenticación alternativos.
nonetcache
Deshabilita la caché de red. Esto significa que cada solicitud se envía directamente al servidor sin pasar por la caché de red. Esto puede ser útil para depurar problemas de red, pero generalmente degrada el rendimiento.
nosuid / suid
Controla si se respetan los bits SUID y SGID en los archivos. Por defecto, los bits SUID y SGID se respetan (suid). Si se especifica nosuid, los bits SUID y SGID se ignoran. Esto es una medida de seguridad importante para evitar que los usuarios ejecuten programas con privilegios elevados en un sistema de archivos remoto.
nrconnect
Esta opción permite que el cliente NFS intente conectarse a un servidor NFS sin usar la opción port= o el servicio rpcbind. Está diseñado para funcionar a través de firewalls que podrían bloquear el tráfico a puertos RPC estándar. Cuando se utiliza, el cliente NFS intenta conectarse a un puerto de origen no privilegiado (generalmente por encima de 1024) y luego busca el servicio NFS en el servidor. Esto permite a los clientes conectar a través de puertos de origen no privilegiados.
Consulte la sección SECURITY CONSIDERATIONS para obtener detalles importantes.
port=n
El valor numérico del puerto del servicio NFS del servidor. Si el servicio NFS del servidor no está disponible en el puerto especificado, la solicitud de montaje falla.
Si esta opción no se especifica, o si el valor del puerto especificado es 0, entonces el cliente NFS utiliza el número de puerto del servicio NFS anunciado por el servicio rpcbind del servidor. La solicitud de montaje falla si el servicio rpcbind del servidor no está disponible, el servicio NFS del servidor no está registrado con su servicio rpcbind, o el servicio NFS del servidor no está disponible en el puerto anunciado.
proto=netid
El netid determina el transporte que se utiliza para comunicarse con el servidor NFS. Las opciones disponibles son udp, udp6, tcp, tcp6, rdma, y rdma6. Aquellos que terminan en 6 utilizan direcciones IPv6 y solo están disponibles si se ha integrado soporte para TI-RPC. Otros utilizan direcciones IPv4.
Cada protocolo de transporte utiliza diferentes configuraciones predeterminadas de retrans y timeo. Consulte la descripción de estas dos opciones de montaje para obtener detalles.
Además de controlar cómo el cliente NFS transmite solicitudes al servidor, esta opción de montaje también controla cómo el comando mount(8) se comunica con los servicios rpcbind y mountd del servidor. Especificar un netid que utiliza TCP obliga a todo el tráfico del comando mount(8) y del cliente NFS a utilizar TCP. Especificar un netid que utiliza UDP obliga a todos los tipos de tráfico a utilizar UDP.
Antes de utilizar NFS sobre UDP, consulte la sección TRANSPORT METHODS.
Si la opción de montaje proto no se especifica, el comando mount(8) descubre qué protocolos soporta el servidor y elige un transporte apropiado para cada servicio. Consulte la sección TRANSPORT METHODS para obtener más detalles.
rdma
La opción rdma es una alternativa a especificar proto=rdma.
retrans=n
El número de retransmisiones antes de que se considere que una operación ha fallado. El valor predeterminado es 5 para TCP y 3 para UDP.
resvport / noresvport
Controla si el cliente NFS intenta utilizar un puerto de origen reservado (inferior a 1024) para las conexiones NFS. Por defecto, se utiliza un puerto reservado (resvport). Si se especifica noresvport, el cliente utilizará un puerto de origen no privilegiado (generalmente por encima de 1024). Esto puede ser útil cuando se montan sistemas de archivos NFS desde clientes que no tienen privilegios de red suficientes para utilizar puertos reservados, o cuando se intenta evitar problemas de firewall que bloquean el tráfico desde puertos de origen reservados.
rsize=n
Establece el tamaño máximo en bytes de las operaciones de lectura del cliente NFS. El valor predeterminado es 1048576 bytes (1MB) para NFSv4 y 32768 bytes para NFSv3/v2. Los valores más grandes pueden mejorar el rendimiento al leer archivos grandes, pero también pueden aumentar la latencia si el servidor no puede manejar lecturas grandes de manera eficiente.
secureflavor=flavor
Especifica el mecanismo de autenticación utilizado para las conexiones NFS. Los valores posibles incluyen sys (autenticación tradicional UNIX), krb5 (Kerberos), krb5i (Kerberos con integridad) y krb5p (Kerberos con privacidad).
sloppy
La opción sloppy es una alternativa a especificar mount.nfs -s option.
timecached
Habilita el almacenamiento en caché de los tiempos de acceso. Esto puede mejorar el rendimiento al leer archivos, pero puede hacer que los tiempos de acceso no estén completamente actualizados.
timecomp / notimecomp
Controla si el cliente NFS comprime los tiempos de acceso de los archivos. Si se especifica timecomp, el cliente NFS comprime los tiempos de acceso. Esto puede reducir la cantidad de datos transferidos entre el cliente y el servidor, pero puede aumentar la carga de la CPU en ambos extremos. Si se especifica notimecomp (el valor predeterminado), los tiempos de acceso no se comprimen.
timeo=n
El tiempo inicial de espera (en décimas de segundo) antes de que se retansmita una operación NFS. El valor predeterminado es 600 (60 segundos) para UDP y 60 (6 segundos) para TCP. Los valores más altos pueden ser necesarios en redes de alta latencia, pero pueden hacer que las operaciones fallidas tarden más en detectarse.
tintr / notintr
Permite que las operaciones de NFS de transporte (tcp) sean interrumpidas por señales. Por defecto, las operaciones de NFS de transporte no son interrumpibles. Si se monta un sistema de archivos con tintr, las operaciones de NFS de transporte que se bloquean pueden ser interrumpidas por una señal. Esto es útil para evitar que los procesos se bloqueen indefinidamente si el servidor NFS no responde.
vers=n
Esta opción es una abreviatura de nfsvers=.
wdelay / nowdelay
Habilita el retraso de escritura para mejorar el rendimiento de las escrituras. El cliente NFS espera hasta que se acumulan varias escrituras antes de enviarlas al servidor en una sola operación. Esto reduce la sobrecarga de la red, pero puede aumentar el riesgo de pérdida de datos si el cliente falla antes de que los datos sean enviados. El comportamiento predeterminado es wdelay.
writeback
Habilita la escritura en segundo plano. Esto significa que el cliente NFS no espera la confirmación del servidor antes de que una operación de escritura se considere completa. La escritura en segundo plano mejora el rendimiento, pero aumenta el riesgo de pérdida de datos si el cliente o el servidor fallan antes de que los datos se escriban de forma persistente.
wsize=n
Establece el tamaño máximo en bytes de las operaciones de escritura del cliente NFS. El valor predeterminado es 1048576 bytes (1MB) para NFSv4 y 32768 bytes para NFSv3/v2. Los valores más grandes pueden mejorar el rendimiento al escribir archivos grandes, pero también pueden aumentar la latencia si el servidor no puede manejar escrituras grandes de manera eficiente.
xprtsec=policy
Especifica el uso de seguridad a nivel de transporte para proteger el tráfico de red NFS en nombre de este punto de montaje. policy puede ser uno de none, tls, o mtls.
Si se especifica none, la seguridad a nivel de transporte se fuerza desactivada, incluso si el servidor NFS soporta seguridad a nivel de transporte.
Si se especifica tls, el cliente utiliza RPC-con-TLS para proporcionar confidencialidad en tránsito.
Si se especifica mtls, el cliente utiliza RPC-con-TLS para autenticarse y para proporcionar confidencialidad en tránsito.
Si se especifica tls o mtls y el servidor no soporta RPC-con-TLS o la autenticación del par falla, el intento de montaje falla.
Si la opción xprtsec= no se especifica, el comportamiento predeterminado depende de la versión del kernel, pero generalmente es equivalente a xprtsec=none.

Opciones solo para NFS versión 4

Use estas opciones, junto con las opciones de la primera subsección anterior, para NFS versión 4.0 y posteriores.

La solicitud de montaje falla si el servicio rpcbind del servidor no está disponible, el servicio NFS del servidor no está registrado con su servicio rpcbind, o el servicio NFS del servidor no está disponible en el puerto anunciado.
cto / nocto
Selecciona si se utilizan semánticas de coherencia de caché de cerrar-a-abrir para directorios NFS en este punto de montaje. Si no se especifica cto ni nocto, el valor predeterminado es utilizar semánticas de coherencia de caché de cerrar-a-abrir para directorios.
El comportamiento del caché de datos de archivos no se ve afectado por esta opción. La sección COHERENCIA DE DATOS Y METADATOS discute el comportamiento de esta opción con más detalle.
clientaddr=n.n.n.n
clientaddr=n:n:...:n
Especifica una única dirección IPv4 (en formato de cuádruple punto), o una dirección IPv6 no local de enlace, que el cliente NFS anuncia para permitir que los servidores realicen solicitudes de devolución de llamada NFS versión 4.0 contra archivos en este punto de montaje. Si el servidor no puede establecer conexiones de devolución de llamada con los clientes, el rendimiento puede degradarse o los accesos a los archivos pueden colgarse temporalmente. Se puede especificar un valor de IPv4_ANY (0.0.0.0) o el equivalente de dirección cualquiera IPv6 que indicará al servidor NFS que este cliente NFS no desea delegaciones.
Si esta opción no se especifica, el comando mount(8) intenta descubrir automáticamente una dirección de devolución de llamada adecuada. Sin embargo, el proceso de descubrimiento automático no es perfecto. En presencia de múltiples interfaces de red del cliente, políticas de enrutamiento especiales o topologías de red atípicas, la dirección exacta a usar para las devoluciones de llamada puede ser difícil de determinar.
Las versiones 4.1 y 4.2 del protocolo NFS utilizan la conexión TCP establecida por el cliente para las solicitudes de devolución de llamada, por lo que no requieren que el servidor se conecte al cliente. Por lo tanto, esta opción solo afecta a los montajes NFS versión 4.0.
migration / nomigration
Selecciona si el cliente utiliza una cadena de identificación que es compatible con la Migración Transparente de Estado (TSM) de NFSv4. Si el servidor montado soporta la migración NFSv4 con TSM, especifique la opción migration.
Algunas características del servidor se comportan de forma incorrecta ante una cadena de identificación compatible con la migración. La opción nomigration conserva el uso de una cadena de identificación de cliente tradicional que es compatible con servidores NFS heredados. Este es también el comportamiento si no se especifica ninguna de las opciones. El estado de apertura y bloqueo de un cliente no puede migrarse de forma transparente cuando se identifica a través de una cadena de identificación tradicional.
Esta opción de montaje no tiene efecto con versiones menores de NFSv4 posteriores a la cero, que siempre utilizan cadenas de identificación de cliente compatibles con TSM.
max_connect=n
Mientras que la opción nconnect establece un límite en el número de conexiones que se pueden establecer a una IP de servidor dada, la opción max_connect permite al usuario especificar el número máximo de conexiones a diferentes IPs de servidor que pertenecen al mismo servidor NFSv4.1+ (conexiones encadenables de sesión) hasta un límite de 16. Cuando el cliente descubre que ha establecido un ID de cliente a un servidor ya existente, en lugar de descartar el transporte de red recién creado, el cliente agregará esta nueva conexión a la lista de transportes disponibles para ese cliente RPC.
trunkdiscovery / notrunkdiscovery
Cuando el cliente descubre un nuevo sistema de archivos en un servidor NFSv4.1+, la opción de montaje trunkdiscovery hará que envíe un GETATTR para el atributo fs_locations. Si recibe una respuesta de longitud no cero, iterará a través de la respuesta, y para cada ubicación del servidor establecerá una conexión, enviará un EXCHANGE_ID y probará la concatenación de sesiones. Si la prueba de concatenación tiene éxito, la conexión se agregará al conjunto existente de transportes para el servidor, sujeta al límite especificado por la opción max_connect. El valor predeterminado es notrunkdiscovery.

MÉTODOS DE TRANSPORTE

Los clientes NFS envían solicitudes a los servidores NFS a través de llamadas a procedimientos remotos, o RPC. El cliente RPC descubre los puntos de conexión de servicio remotos automáticamente, maneja la autenticación por solicitud, ajusta los parámetros de solicitud para la diferente representación de bytes entre el cliente y el servidor, y vuelve a transmitir las solicitudes que pueden haberse perdido en la red o en el servidor. Las solicitudes y respuestas RPC fluyen a través de un transporte de red.

En la mayoría de los casos, el comando mount(8), el cliente NFS y el servidor NFS pueden negociar automáticamente la configuración adecuada del transporte y del tamaño de transferencia de datos para un punto de montaje. En algunos casos, sin embargo, vale la pena especificar estas configuraciones explícitamente usando opciones de montaje.

Tradicionalmente, los clientes NFS utilizaban exclusivamente el transporte UDP para transmitir solicitudes a los servidores. Aunque su implementación es simple, NFS sobre UDP tiene muchas limitaciones que impiden un funcionamiento fluido y un buen rendimiento en algunos entornos de implementación comunes. Incluso una tasa insignificante de pérdida de paquetes resulta en la pérdida de solicitudes NFS completas; por lo tanto, los tiempos de espera de retransmisión suelen estar en el rango de subsegundos para permitir que los clientes se recuperen rápidamente de las solicitudes omitidas, pero esto puede generar tráfico de red y carga de servidor extraneous.

Sin embargo, UDP puede ser bastante eficaz en entornos especializados donde la MTU de la red es grande en relación con el tamaño de transferencia de datos de NFS (como entornos de red que habilitan marcos Ethernet jumbo). En tales entornos, se aconseja recortar la configuración de rsize y wsize para que cada solicitud de lectura o escritura de NFS quepa en unos pocos marcos de red (o incluso en un solo marco). Esto reduce la probabilidad de que la pérdida de un solo marco de red de tamaño MTU resulte en la pérdida de una solicitud de lectura o escritura grande completa.

TCP es el protocolo de transporte predeterminado utilizado para todas las implementaciones modernas de NFS. Funciona bien en casi todos los entornos de red imaginables y proporciona excelentes garantías contra la corrupción de datos causada por la falta de fiabilidad de la red. TCP es a menudo un requisito para montar un servidor a través de un firewall de red.

En circunstancias normales, las redes pierden paquetes con mucha más frecuencia de la que los servidores NFS pierden solicitudes. Como tal, una configuración agresiva del tiempo de espera de retransmisión para NFS sobre TCP es innecesaria. Los tiempos de espera típicos para NFS sobre TCP están entre uno y diez minutos. Después de que el cliente agota sus retransmisiones (el valor de la opción de montaje retrans), asume que ha ocurrido una partición de red e intenta reconectarse al servidor en un socket nuevo. Dado que TCP en sí mismo hace que la transferencia de datos de red sea fiable, rsize y wsize pueden configurarse de forma segura con los valores más grandes admitidos por el cliente y el servidor, independientemente del tamaño MTU de la red.

Usando la opción de montaje mountproto

Esta sección se aplica solo a los montajes de NFS versión 3, ya que la versión 4 de NFS no utiliza un protocolo separado para las solicitudes de montaje.

El cliente NFS de Linux puede usar un transporte diferente para contactar el servicio rpcbind del servidor NFS, su servicio mountd, su Network Lock Manager (NLM) y su servicio NFS. Los transportes exactos empleados por el cliente NFS de Linux para cada punto de montaje dependen de la configuración de las opciones de montaje de transporte, que incluyen proto, mountproto, udp y tcp.

El cliente envía notificaciones del Network Status Manager (NSM) a través de UDP independientemente de las opciones de transporte especificadas, pero escucha las notificaciones NSM del servidor tanto en UDP como en TCP. El protocolo NFS Access Control List (NFSACL) comparte el mismo transporte que el servicio NFS principal.

Si no se especifican opciones de transporte, el cliente NFS de Linux utiliza UDP para contactar el servicio mountd del servidor y TCP para contactar sus servicios NLM y NFS de forma predeterminada.

Si el servidor no admite estos transportes para estos servicios, el comando mount(8) intenta descubrir lo que el servidor admite y luego reintenta la solicitud de montaje una vez usando los transportes descubiertos. Si el servidor no anuncia ningún transporte compatible con el cliente o está mal configurado, la solicitud de montaje falla. Si la opción bg está activa, el comando mount se ejecuta en segundo plano y continúa intentando la solicitud de montaje especificada.

Cuando se especifica la opción proto, la opción udp, o la opción tcp, pero no la opción mountproto, el transporte especificado se utiliza para contactar el servicio mountd del servidor y para los servicios NLM y NFS.

Si se especifica la opción mountproto pero no se especifican las opciones proto, udp o tcp, entonces el transporte especificado se utiliza para la solicitud inicial de mountd, pero el comando mount intenta descubrir lo que el servidor admite para el protocolo NFS, prefiriendo TCP si se admiten ambos transportes.

Si tanto las opciones mountproto como proto (o udp o tcp) se especifican, entonces el transporte especificado por la opción mountproto se utiliza para la solicitud inicial de mountd, y el transporte especificado por la opción proto (o las opciones udp o tcp) se utiliza para NFS, independientemente del orden en que aparezcan estas opciones. No se realiza ningún descubrimiento automático de servicios si se especifican estas opciones.

Si alguna de las opciones proto, udp, tcp, o mountproto se especifica más de una vez en la misma línea de comando de montaje, entonces el valor de la instancia más a la derecha de cada una de estas opciones entra en vigor.

Usando NFS sobre UDP en enlaces de alta velocidad

Usar NFS sobre UDP en enlaces de alta velocidad como Gigabit puede causar corrupción silenciosa de datos.

El problema puede desencadenarse con cargas altas y se debe a problemas en el reensamblaje de fragmentos IP. Las lecturas y escrituras de NFS suelen transmitir paquetes UDP de 4 Kilobytes o más, que deben dividirse en varios fragmentos para ser enviados a través del enlace Ethernet, que limita los paquetes a 1500 bytes por defecto. Este proceso ocurre en la capa de red IP y se llama fragmentación.

Para identificar los fragmentos que pertenecen juntos, IP asigna un valor de 16 bits de ID IP a cada paquete; los fragmentos generados del mismo paquete UDP tendrán el mismo ID IP. El sistema receptor recopilará estos fragmentos y los combinará para formar el paquete UDP original. Este proceso se llama reensamblaje. El tiempo de espera predeterminado para el reensamblaje de paquetes es de 30 segundos; si la pila de red no recibe todos los fragmentos de un paquete dado dentro de este intervalo, asume que el(los) fragmento(s) faltante(s) se perdieron y descarta los que ya recibió.

El problema que esto crea en enlaces de alta velocidad es que es posible enviar más de 65536 paquetes en 30 segundos. De hecho, con tráfico NFS intenso se puede observar que los ID IP se repiten después de unos 5 segundos.

Esto tiene serios efectos en el reensamblaje: si se pierde un fragmento, otro fragmento de otro paquete pero con el mismo ID IP llegará dentro del tiempo de espera de 30 segundos, y la pila de red combinará estos fragmentos para formar un nuevo paquete. La mayoría de las veces, las capas de red por encima de IP detectarán este reensamblaje incorrecto; en el caso de UDP, la suma de verificación UDP, que es una suma de verificación de 16 bits sobre toda la carga útil del paquete, generalmente no coincidirá, y UDP descartará el paquete erróneo.

Sin embargo, la suma de verificación UDP es de solo 16 bits, por lo que existe una probabilidad de 1 en 65536 de que coincida incluso si la carga útil del paquete es completamente aleatoria (lo que muy a menudo no es el caso). Si eso sucede, ocurrirá una corrupción silenciosa de datos.

Este potencial debe tomarse en serio, al menos en Ethernet Gigabit. Las velocidades de red de 100Mbit/s deberían considerarse menos problemáticas, porque con la mayoría de los patrones de tráfico, el ciclo del contador de ID IP tardará mucho más de 30 segundos.

Por lo tanto, se recomienda encarecidamente usar NFS sobre TCP siempre que sea posible, ya que TCP no realiza fragmentación.

Si absolutamente debe usar NFS sobre UDP en Ethernet Gigabit, se pueden tomar algunas medidas para mitigar el problema y reducir la probabilidad de corrupción:

Marcos Jumbo:
Muchas tarjetas de red Gigabit son capaces de transmitir marcos más grandes que el límite de 1500 bytes de Ethernet tradicional, típicamente 9000 bytes. Usar marcos jumbo de 9000 bytes le permitirá ejecutar NFS sobre UDP a un tamaño de página de 8K sin fragmentación. Por supuesto, esto sólo es factible si todas las estaciones implicadas admiten marcos jumbo.
Para permitir que una máquina envíe marcos jumbo en tarjetas que lo admitan, es suficiente configurar la interfaz para un valor de MTU de 9000.
Tiempo de espera de reensamblaje inferior:
Al reducir este tiempo de espera por debajo del tiempo que tarda el contador de ID IP en dar la vuelta, también se puede prevenir el reensamblaje incorrecto de fragmentos. Para hacerlo, simplemente escriba el nuevo valor de tiempo de espera (en segundos) en el archivo /proc/sys/net/ipv4/ipfrag_time.
Un valor de 2 segundos reducirá significativamente la probabilidad de colisiones de IPID en un enlace Gigabit, al tiempo que permitirá un tiempo de espera razonable al recibir tráfico fragmentado de peers distantes.

COHERENCIA DE DATOS Y METADATOS

Algunos sistemas de archivos de clúster modernos proporcionan una coherencia de caché perfecta entre sus clientes. Lograr una coherencia de caché perfecta entre clientes NFS dispares es costoso, especialmente en redes de área amplia. Como tal, NFS se conforma con una coherencia de caché más débil que satisface los requisitos de la mayoría de los tipos de intercambio de archivos.

Consistencia de caché de cerrar-a-abrir

CLOSE-TO-OPEN CACHE CONSISTENCY

Típicamente, el intercambio de archivos es completamente secuencial. Primero, el cliente A abre un archivo, escribe algo en él, y luego lo cierra. Después, el cliente B abre el mismo archivo y lee los cambios.

Cuando una aplicación abre un archivo almacenado en un servidor NFS versión 3, el cliente NFS comprueba que el archivo existe en el servidor y que está permitido al que lo abre enviando una solicitud GETATTR o ACCESS. El cliente NFS envía estas solicitudes independientemente de la actualidad de los atributos en caché del archivo.

Cuando la aplicación cierra el archivo, el cliente NFS escribe de vuelta cualquier cambio pendiente en el archivo para que el próximo que lo abra pueda ver los cambios. Esto también le da al cliente NFS la oportunidad de informar errores de escritura a la aplicación a través del código de retorno de close(2).

El comportamiento de comprobar en el momento de abrir y vaciar al cerrar se denomina consistencia de caché de cerrar a abrir, o CTO. Se puede deshabilitar para todo el punto de montaje utilizando la opción de montaje nocto.

Consistencia débil de caché

Todavía existen oportunidades para que la caché de datos de un cliente contenga datos obsoletos. El protocolo NFS versión 3 introdujo la "consistencia débil de caché" (también conocida como WCC) que proporciona una forma eficiente de comprobar los atributos de un archivo antes y después de una única solicitud. Esto permite a un cliente ayudar a identificar cambios que podrían haber sido realizados por otros clientes.

Cuando un cliente utiliza muchas operaciones concurrentes que actualizan el mismo archivo al mismo tiempo (por ejemplo, durante la escritura en segundo plano asíncrona), todavía es difícil saber si fueron las actualizaciones de ese cliente o las de algún otro cliente las que alteraron el archivo.

Caché de atributos

Utilice la opción de montaje noac para lograr la coherencia de la caché de atributos entre varios clientes. Casi todas las operaciones del sistema de archivos comprueban la información de atributos del archivo. El cliente mantiene esta información en caché durante un período de tiempo para reducir la carga de red y del servidor. Cuando noac está en vigor, la caché de atributos de archivos del cliente está deshabilitada, por lo que cada operación que necesite comprobar los atributos de un archivo se ve obligada a volver al servidor. Esto permite que un cliente vea los cambios en un archivo muy rápidamente, a costa de muchas operaciones de red adicionales.

Tenga cuidado de no confundir la opción noac con "sin caché de datos". La opción de montaje noac evita que el cliente almacene en caché metadatos de archivos, pero todavía existen condiciones de carrera que pueden resultar en incoherencia de la caché de datos entre el cliente y el servidor.

El protocolo NFS no está diseñado para soportar una coherencia de caché de sistema de archivos de clúster real sin algún tipo de serialización de aplicaciones. Si se requiere coherencia de caché absoluta entre clientes, las aplicaciones deben utilizar bloqueos de archivos. Alternativamente, las aplicaciones también pueden abrir sus archivos con el flag O_DIRECT para deshabilitar completamente la caché de datos.

Mantenimiento de marcas de tiempo de archivos

Los servidores NFS son responsables de administrar las marcas de tiempo de archivos y directorios (atime, ctime y mtime). Cuando se accede o se actualiza un archivo en un servidor NFS, las marcas de tiempo del archivo se actualizan de la misma manera que lo harían en un sistema de archivos local para una aplicación.

Los clientes NFS almacenan en caché los atributos de los archivos, incluidas las marcas de tiempo. Las marcas de tiempo de un archivo se actualizan en los clientes NFS cuando sus atributos se recuperan del servidor NFS. Por lo tanto, puede haber un retraso antes de que las actualizaciones de marcas de tiempo en un servidor NFS aparezcan en las aplicaciones de los clientes NFS.

Para cumplir con el estándar de sistemas de archivos POSIX, el cliente NFS de Linux se basa en los servidores NFS para mantener las marcas de tiempo mtime y ctime de un archivo correctamente actualizadas. Lo hace vaciando los cambios de datos locales al servidor antes de informar mtime a las aplicaciones a través de llamadas al sistema como stat(2).

Sin embargo, el cliente de Linux maneja las actualizaciones de atime de manera más flexible. Los clientes NFS mantienen un buen rendimiento almacenando datos en caché, pero eso significa que las lecturas de aplicaciones, que normalmente actualizan atime, no se reflejan en el servidor donde se mantiene realmente el atime de un archivo.

Debido a este comportamiento de caché, el cliente NFS de Linux no soporta opciones genéricas de montaje relacionadas con atime. Consulte mount(8) para obtener detalles sobre estas opciones.

En particular, las opciones de montaje atime/noatime, diratime/nodiratime, relatime/norelatime y strictatime/nostrictatime no tienen ningún efecto en los montajes NFS.

/proc/mounts puede informar que la opción de montaje relatime está configurada en montajes NFS, pero de hecho las semánticas de atime son siempre como se describen aquí, y no son como las semánticas de relatime.

Caché de entradas de directorio

El cliente NFS de Linux almacena en caché el resultado de todas las solicitudes NFS LOOKUP. Si la entrada de directorio solicitada existe en el servidor, el resultado se denomina resultado de búsqueda *positivo*. Si la entrada de directorio solicitada no existe en el servidor (es decir, el servidor devolvió ENOENT), el resultado se denomina resultado de búsqueda *negativo*.

Para detectar cuándo se han añadido o eliminado entradas de directorio en el servidor, el cliente NFS de Linux vigila la mtime de un directorio. Si el cliente detecta un cambio en la mtime de un directorio, el cliente descarta todos los resultados LOOKUP almacenados en caché para ese directorio. Dado que la mtime del directorio es un atributo en caché, puede pasar algún tiempo antes de que un cliente note que ha cambiado. Consulte las descripciones de las opciones de montaje acdirmin, acdirmax y noac para obtener más información sobre cuánto tiempo se almacena en caché la mtime de un directorio.

El almacenamiento en caché de entradas de directorio mejora el rendimiento de las aplicaciones que no comparten archivos con aplicaciones en otros clientes. Sin embargo, el uso de información en caché sobre directorios puede interferir con las aplicaciones que se ejecutan concurrentemente en múltiples clientes y necesitan detectar la creación o eliminación de archivos rápidamente. La opción de montaje lookupcache permite ajustar el comportamiento del almacenamiento en caché de entradas de directorio.

Antes de la versión del kernel 2.6.28, el cliente NFS de Linux solo hacía un seguimiento de los resultados de búsqueda positivos. Esto permitía a las aplicaciones detectar rápidamente las nuevas entradas de directorio creadas por otros clientes, al tiempo que proporcionaba algunos de los beneficios de rendimiento del almacenamiento en caché. Si una aplicación depende del comportamiento anterior de almacenamiento en caché de búsqueda del cliente NFS de Linux, puede usar lookupcache=positive.

Si el cliente ignora su caché y valida cada solicitud de búsqueda de aplicación con el servidor, ese cliente puede detectar inmediatamente cuándo se ha creado o eliminado una nueva entrada de directorio por otro cliente. Puede especificar este comportamiento usando lookupcache=none. Las solicitudes NFS adicionales necesarias si el cliente no almacena en caché las entradas de directorio pueden tener un impacto negativo en el rendimiento. Deshabilitar el almacenamiento en caché de búsqueda debería resultar en un impacto de rendimiento menor que usar noac, y no tiene ningún efecto en cómo el cliente NFS almacena en caché los atributos de los archivos.

La opción de montaje sync

El cliente NFS trata la opción de montaje sync de manera diferente a algunos otros sistemas de archivos (consulte mount(8) para una descripción de las opciones genéricas de montaje sync y async). Si no se especifica ni sync ni async (o si se especifica la opción async), el cliente NFS retrasa el envío de las escrituras de aplicación al servidor hasta que ocurra alguno de estos eventos:

La presión de memoria fuerza la recuperación de recursos de memoria del sistema.
Una aplicación vacía los datos del archivo explícitamente con sync(2), msync(2) o fsync(3).
Una aplicación cierra un archivo con close(2).
El archivo se bloquea/desbloquea mediante fcntl(2).

En otras palabras, en circunstancias normales, los datos escritos por una aplicación pueden no aparecer inmediatamente en el servidor que aloja el archivo.

Si se especifica la opción sync en un punto de montaje, cualquier llamada al sistema que escriba datos en archivos en ese punto de montaje provoca que esos datos se envíen al servidor antes de que la llamada al sistema devuelva el control al espacio de usuario. Esto proporciona una mayor coherencia de la caché de datos entre clientes, pero a un coste de rendimiento significativo.

Las aplicaciones pueden usar el flag de apertura O_SYNC para forzar que las escrituras de aplicaciones a archivos individuales vayan al servidor inmediatamente sin el uso de la opción de montaje sync.

Uso de bloqueos de archivos con NFS

El protocolo Network Lock Manager es un protocolo auxiliar separado que se utiliza para administrar bloqueos de archivos en NFS versión 3. Para soportar la recuperación de bloqueos después de un reinicio del cliente o servidor, también se requiere un segundo protocolo auxiliar, conocido como el protocolo Network Status Manager. En NFS versión 4, el bloqueo de archivos se soporta directamente en el protocolo NFS principal, y los protocolos auxiliares NLM y NSM no se utilizan.

En la mayoría de los casos, los servicios NLM y NSM se inician automáticamente y no se requiere configuración adicional. Configure todos los clientes NFS con nombres de dominio completamente calificados para asegurar que los servidores NFS puedan encontrar los clientes para notificarles sobre reinicios del servidor.

NLM soporta solo bloqueos de archivos de asesoramiento. Para bloquear archivos NFS, utilice fcntl(2) con los comandos F_GETLK y F_SETLK. El cliente NFS convierte los bloqueos de archivos obtenidos a través de flock(2) en bloqueos de asesoramiento.

Al montar servidores que no soportan el protocolo NLM, o al montar un servidor NFS a través de un firewall que bloquea el puerto de servicio NLM, especifique la opción de montaje nolock. El bloqueo NLM debe ser deshabilitado con la opción nolock al usar NFS para montar /var porque /var contiene archivos utilizados por la implementación NLM en Linux.

Especificar la opción nolock también puede ser aconsejable para mejorar el rendimiento de una aplicación propietaria que se ejecuta en un único cliente y utiliza bloqueos de archivos extensivamente.

Características de caché de NFS versión 4

El comportamiento de almacenamiento en caché de datos y metadatos de los clientes NFS versión 4 es similar al de versiones anteriores. Sin embargo, NFS versión 4 añade dos características que mejoran el comportamiento de la caché: *atributos de cambio* y *delegación de archivos*.

El atributo de cambio es una nueva parte de los metadatos de archivos y directorios de NFS que rastrea los cambios de datos. Reemplaza el uso de las marcas de tiempo de modificación y cambio de un archivo como una forma para que los clientes validen el contenido de sus cachés. Los atributos de cambio son independientes de la resolución de la marca de tiempo en el servidor o en el cliente, sin embargo.

Una delegación de archivo es un contrato entre un cliente y un servidor NFS versión 4 que permite al cliente tratar un archivo temporalmente como si ningún otro cliente estuviera accediendo a él. El servidor promete notificar al cliente (mediante una solicitud de devolución de llamada) si otro cliente intenta acceder a ese archivo. Una vez que un archivo ha sido delegado a un cliente, el cliente puede almacenar en caché los datos y metadatos de ese archivo agresivamente sin contactar al servidor.

Las delegaciones de archivos vienen en dos variantes: lectura y escritura. Una delegación de lectura significa que el servidor notifica al cliente sobre cualquier otro cliente que quiera escribir en el archivo. Una delegación de escritura significa que el cliente es notificado sobre los accesos de lectura o escritura.

Los servidores otorgan delegaciones de archivos cuando se abre un archivo, y pueden revocar delegaciones en cualquier momento cuando otro cliente desea acceder al archivo de una manera que entra en conflicto con cualquier delegación ya otorgada. No se admiten delegaciones en directorios.

Para admitir la devolución de llamada de delegación, el servidor verifica la ruta de retorno de la red al cliente durante el contacto inicial del cliente con el servidor. Si no se puede establecer contacto con el cliente, el servidor simplemente no otorga ninguna delegación a ese cliente.

CONSIDERACIONES DE SEGURIDAD

Los servidores NFS controlan el acceso a los datos de los archivos, pero dependen de su implementación RPC para proporcionar autenticación de las solicitudes NFS. El control de acceso NFS tradicional imita el control de acceso estándar de bits de modo proporcionado en los sistemas de archivos locales. La autenticación RPC tradicional utiliza un número para representar a cada usuario (generalmente el uid del usuario), un número para representar al grupo del usuario (el gid del usuario) y un conjunto de hasta 16 números de grupo auxiliares para representar otros grupos de los que el usuario puede ser miembro.

Típicamente, los datos del archivo y los valores de ID de usuario aparecen sin cifrar (es decir, "en texto plano") en la red. Además, las versiones 2 y 3 de NFS utilizan protocolos de banda lateral separados para montar, bloquear y desbloquear archivos, e informar el estado del sistema de clientes y servidores. Estos protocolos auxiliares no utilizan autenticación.

Además de combinar estos protocolos de banda lateral con el protocolo NFS principal, la versión 4 de NFS introduce formas más avanzadas de control de acceso, autenticación y protección de datos en tránsito. La especificación NFS versión 4 exige la compatibilidad con autenticación robusta y sabores de seguridad que proporcionan verificación de integridad y cifrado por RPC. Debido a que NFS versión 4 combina la función de los protocolos de banda lateral en el protocolo NFS principal, las nuevas características de seguridad se aplican a todas las operaciones de NFS versión 4, incluido el montaje, el bloqueo de archivos, etc. La autenticación RPCGSS también se puede utilizar con las versiones 2 y 3 de NFS, pero no protege sus protocolos de banda lateral.

La opción de montaje sec especifica el sabor de seguridad utilizado para las operaciones en nombre de los usuarios en ese punto de montaje NFS. Especificar sec=krb5 proporciona prueba criptográfica de la identidad de un usuario en cada solicitud RPC. Esto proporciona una verificación sólida de la identidad de los usuarios que acceden a los datos en el servidor. Tenga en cuenta que se requiere configuración adicional además de agregar esta opción de montaje para habilitar la seguridad Kerberos. Consulte la página del manual de rpc.gssd(8) para obtener detalles.

Se admiten dos sabores adicionales de seguridad Kerberos: krb5i y krb5p. El sabor de seguridad krb5i proporciona una garantía criptográficamente sólida de que los datos en cada solicitud RPC no han sido manipulados. El sabor de seguridad krb5p cifra cada solicitud RPC para evitar la exposición de datos durante el tránsito por la red; sin embargo, espere un cierto impacto en el rendimiento al usar la verificación de integridad o el cifrado. También hay disponible soporte similar para otras formas de seguridad criptográfica.

Cruce de sistemas de archivos NFS versión 4

El protocolo NFS versión 4 permite a un cliente renegociar el sabor de seguridad cuando el cliente cruza a un nuevo sistema de archivos en el servidor. El sabor recién negociado afecta solo a los accesos del nuevo sistema de archivos.

Dicha negociación suele ocurrir cuando un cliente cruza desde un pseudo-sistema de archivos de un servidor a uno de los sistemas de archivos físicos exportados por el servidor, que a menudo tienen configuraciones de seguridad más restrictivas que el pseudo-sistema de archivos.

Concesiones NFS versión 4

En NFS versión 4, una concesión es un período durante el cual un servidor otorga irrevocablemente bloqueos de archivos a un cliente. Una vez que la concesión expira, el servidor puede revocar esos bloqueos. Los clientes renuevan sus concesiones periódicamente para evitar la revocación de bloqueos.

Después de que un servidor NFS versión 4 se reinicia, cada cliente informa al servidor sobre el estado de apertura y bloqueo de archivos existente bajo su concesión antes de que la operación pueda continuar. Si un cliente se reinicia, el servidor libera todo el estado de apertura y bloqueo asociado con la concesión de ese cliente.

Por lo tanto, al establecer una concesión, un cliente debe identificarse ante un servidor. Cada cliente presenta una cadena arbitraria para distinguirse de otros clientes. El administrador del cliente puede complementar la cadena de identidad predeterminada utilizando el parámetro del módulo nfs4.nfs4_unique_id para evitar colisiones con otras cadenas de identidad de cliente.

Un cliente también utiliza un sabor de seguridad y un principal únicos cuando establece su concesión. Si dos clientes presentan la misma cadena de identidad, un servidor puede usar los principales del cliente para distinguirlos, evitando así de forma segura que un cliente interfiera con la concesión del otro.

El cliente NFS de Linux establece una concesión en cada servidor NFS versión 4. Las operaciones de administración de concesiones, como la renovación de concesiones, no se realizan en nombre de un archivo, bloqueo, usuario o punto de montaje específico, sino en nombre del cliente que posee esa concesión. Un cliente utiliza una cadena de identidad, un sabor de seguridad y un principal consistentes entre reinicios del cliente para garantizar que el servidor pueda liberar rápidamente el estado de concesión expirado.

Cuando Kerberos está configurado en un cliente NFS de Linux (es decir, hay un archivo /etc/krb5.keytab en ese cliente), el cliente intenta utilizar un sabor de seguridad Kerberos para sus operaciones de administración de concesiones. Kerberos proporciona autenticación segura de cada cliente. De forma predeterminada, el cliente utiliza el principal de servicio host/ o nfs/ en su /etc/krb5.keytab para este propósito, como se describe en rpc.gssd(8).

Si el cliente tiene Kerberos configurado, pero el servidor no, o si el cliente no tiene un keytab o los principales de servicio necesarios, el cliente utiliza AUTH_SYS y UID 0 para la administración de concesiones.

Uso de puertos de origen no privilegiados

Los clientes NFS normalmente se comunican con los servidores NFS a través de sockets de red. A cada extremo de un socket se le asigna un valor de puerto, que es simplemente un número entre 1 y 65535 que distingue los puntos finales del socket en la misma dirección IP. Un socket se define de forma única por una tupla que incluye el protocolo de transporte (TCP o UDP) y los valores de puerto y las direcciones IP de ambos puntos finales.

El cliente NFS puede elegir cualquier valor de puerto de origen para sus sockets, pero generalmente elige un puerto privilegiado. Un puerto privilegiado es un valor de puerto inferior a 1024. Solo un proceso con privilegios de root puede crear un socket con un puerto de origen privilegiado.

El rango exacto de puertos de origen privilegiados que se pueden elegir se establece mediante un par de sysctls para evitar elegir un puerto conocido, como el puerto utilizado por ssh. Esto significa que el número de puertos de origen disponibles para el cliente NFS, y por lo tanto el número de conexiones de socket que se pueden utilizar al mismo tiempo, está limitado prácticamente a solo unos pocos cientos.

Como se describe anteriormente, el esquema de autenticación NFS predeterminado tradicional, conocido como AUTH_SYS, se basa en enviar números de UID y GID locales para identificar a los usuarios que realizan solicitudes NFS. Un servidor NFS asume que si una conexión proviene de un puerto privilegiado, los números de UID y GID en las solicitudes NFS en esta conexión han sido verificados por el kernel del cliente u otra autoridad local. Este es un sistema fácil de falsificar, pero en una red física de confianza entre hosts de confianza, es totalmente adecuado.

A grandes rasgos, se utiliza un socket para cada punto de montaje NFS. Si un cliente pudiera usar también puertos de origen no privilegiados, el número de sockets permitidos, y por lo tanto el número máximo de puntos de montaje concurrentes, sería mucho mayor.

El uso de puertos de origen no privilegiados puede comprometer ligeramente la seguridad del servidor, ya que cualquier usuario en puntos de montaje AUTH_SYS ahora puede pretender ser cualquier otro al realizar solicitudes NFS. Por lo tanto, los servidores NFS no lo admiten de forma predeterminada. Lo permiten explícitamente, generalmente a través de una opción de exportación.

Para mantener una buena seguridad y al mismo tiempo permitir el mayor número posible de puntos de montaje, es mejor permitir conexiones de clientes no privilegiados solo si el servidor y el cliente requieren una autenticación sólida, como Kerberos.

Montaje a través de un firewall

Un firewall puede residir entre un cliente y un servidor NFS, o el cliente o servidor pueden bloquear algunos de sus propios puertos mediante reglas de filtrado IP. Todavía es posible montar un servidor NFS a través de un firewall, aunque algunos de los mecanismos de descubrimiento automático de puntos finales de servicio del comando mount(8) pueden no funcionar; esto requiere que usted proporcione detalles específicos del punto final a través de opciones de montaje NFS.

Los servidores NFS normalmente ejecutan un demonio portmapper o rpcbind para anunciar sus puntos finales de servicio a los clientes. Los clientes utilizan el demonio rpcbind para determinar:

Qué puerto de red está utilizando cada servicio basado en RPC
Qué protocolos de transporte admite cada servicio basado en RPC

El demonio rpcbind utiliza un número de puerto conocido (111) para ayudar a los clientes a encontrar un punto final de servicio. Aunque NFS a menudo utiliza un número de puerto estándar (2049), servicios auxiliares como el servicio NLM pueden elegir cualquier número de puerto no utilizado al azar.

Las configuraciones comunes de firewall bloquean el puerto rpcbind conocido. En ausencia de un servicio rpcbind, el administrador del servidor establece el número de puerto de los servicios relacionados con NFS para que el firewall pueda permitir el acceso a puertos de servicio NFS específicos. MÉTODOS DE TRANSPORTE

NFS puede funcionar sobre TCP o UDP. TCP es un protocolo de transporte orientado a la conexión y con control de flujo. UDP es un protocolo sin conexión y sin control de flujo. NFS sobre TCP es generalmente más robusto y permite manejar mejor los fallos de red y las fluctuaciones de la carga. NFS sobre UDP puede ofrecer un rendimiento ligeramente mejor en redes de baja latencia y alta fiabilidad, pero es más susceptible a la pérdida de paquetes y a la retransmisión. La mayoría de los clientes NFS modernos tienen la capacidad de forzar el uso de TCP o UDP si el cortafuegos bloquea uno de esos transportes.

LISTAS DE CONTROL DE ACCESO NFS

Solaris permite a los clientes NFS versión 3 acceder directamente a las Listas de Control de Acceso POSIX almacenadas en sus sistemas de archivos locales. Este protocolo propietario de banda lateral, conocido como NFSACL, proporciona un control de acceso más rico que los bits de modo. Linux implementa este protocolo para compatibilidad con la implementación NFS de Solaris. Sin embargo, el protocolo NFSACL nunca se convirtió en una parte estándar de la especificación NFS versión 3.

La especificación NFS versión 4 exige una nueva versión de las Listas de Control de Acceso que son semánticamente más ricas que las ACL POSIX. Las ACL NFS versión 4 no son totalmente compatibles con las ACL POSIX; por lo tanto, se requiere cierta traducción entre ambas en un entorno que mezcle ACL POSIX y NFS versión 4.

LA OPCIÓN REMOUNT

Las opciones genéricas de montaje como rw y sync se pueden modificar en puntos de montaje NFS usando la opción remount. Consulte mount(8) para obtener más información sobre las opciones genéricas de montaje.

Con pocas excepciones, las opciones específicas de NFS no pueden ser modificadas durante un remount. El transporte subyacente o la versión NFS no pueden cambiarse mediante un remount, por ejemplo.

Realizar un remount en un sistema de archivos NFS montado con la opción noac puede tener consecuencias no deseadas. La opción noac es una combinación de la opción genérica sync y la opción específica de NFS actimeo=0.

Desmontar después de un remount

Para los puntos de montaje que utilizan NFS versión 2 o 3, el subcomando umount de NFS depende de conocer el conjunto original de opciones de montaje utilizadas para realizar la operación MNT. Estas opciones se almacenan en disco por el subcomando mount de NFS y pueden ser borradas por un remount.

Para asegurar que las opciones de montaje guardadas no se borren durante un remount, especifique el directorio de montaje local o el nombre del host del servidor y la ruta exportada, pero no ambos, durante un remount. Por ejemplo,

mount -o remount,ro /mnt

fusiona la opción de montaje ro con las opciones de montaje ya guardadas en disco para el servidor NFS montado en /mnt.
