NETSNIFF-NG(8) Kit de herramientas netsniff-ng NETSNIFF-NG(8)

NOMBRE

netsniff-ng - la bestia para el sniffing de paquetes

SINOPSIS

netsniff-ng { [opciones] [expresión-de-filtro] }

DESCRIPCIÓN

netsniff-ng es una herramienta rápida y mínima para analizar paquetes de red, capturar archivos pcap, reproducir archivos pcap y redirigir tráfico entre interfaces con la ayuda de sockets de paquetes (packet(7)) de copia cero (zero-copy). netsniff-ng utiliza las interfaces RX_RING y TX_RING específicas de Linux para realizar la copia cero. Esto es para evitar la sobrecarga de copias y llamadas al sistema entre el espacio de direcciones del kernel y el del usuario. Cuando comenzamos a trabajar en netsniff-ng, la biblioteca pcap(3) no utilizaba esta facilidad de copia cero.

netsniff-ng es específico de Linux, lo que significa que no hay soporte para otros sistemas operativos. Por lo tanto, podemos mantener el tamaño del código bastante mínimo y al grano. Los sockets de paquetes (packet(7)) de Linux y sus interfaces RX_RING y TX_RING evitan la ruta normal de procesamiento de paquetes a través de la pila de red. Este es el rendimiento de captura o transmisión más rápido que se puede obtener desde el espacio de usuario tal cual, sin tener que cargar módulos de kernel de terceros no soportados o que no forman parte del kernel principal. Nos negamos explícitamente a construir netsniff-ng sobre ntop/PF_RING. No porque no nos guste (nos parece interesante), sino por el hecho de que no forma parte del kernel principal. Por lo tanto, el proyecto ntop tiene que mantener y sincronizar controladores fuera del árbol para adaptarlos a su ADN. Con el tiempo, optamos por un kernel de Linux sin adulterar, ya que su código tiene una mayor tasa de revisión, mantenimiento, seguridad y corrección de errores.

netsniff-ng también admite filtrado temprano de paquetes en el kernel. Tiene soporte para filtros de paquetes de bajo nivel y alto nivel que se traducen en instrucciones de Berkeley Packet Filter.

netsniff-ng puede capturar archivos pcap en varios formatos pcap diferentes que son interoperables con otras herramientas. Los siguientes métodos de E/S pcap son compatibles para una captura eficiente en disco: scatter-gather, mmap(2), read(2) y write(2). netsniff-ng también es capaz de rotar archivos pcap basándose en el tamaño de los datos o en intervalos de tiempo, lo que lo convierte en una herramienta backend útil para el análisis de tráfico posterior.

netsniff-ng en sí mismo también admite el análisis, la reproducción y el volcado de tramas 802.11 brutas. Para el análisis en línea u offline, netsniff-ng tiene un disector de paquetes incorporado para los 802.3 actuales (Ethernet), 802.11* (WLAN), ARP, MPLS, 802.1Q (VLAN), 802.1QinQ, LLDP, IPv4, IPv6, ICMPv4, ICMPv6, IGMP, TCP y UDP, incluido el análisis de ubicación GeoIP. Dado que netsniff-ng no establece ningún estado ni realiza reensamblaje durante la disección de paquetes, su huella de memoria es bastante baja, lo que hace que netsniff-ng sea bastante eficiente para el análisis offline de archivos pcap grandes también.

Tenga en cuenta que netsniff-ng no está multihilo actualmente. Sin embargo, esto no le impide iniciar múltiples instancias de netsniff-ng que estén fijadas a CPUs diferentes y no superpuestas y, por ejemplo, tener diferentes filtros BPF adjuntos. Es probable que en algún momento su disco duro se convierta en un cuello de botella, asumiendo que no rota dichos pcap en RAM (y desde allí se muevan periódicamente a medios más lentos programados). Puede usar mergecap(1) para transformar todos los archivos pcap en un solo archivo pcap grande. Por lo tanto, netsniff-ng funcionará finalmente en multihilo.

netsniff-ng también se puede usar para depurar tráfico netlink.

OPCIONES

-i <dev|pcap|->, -d <dev|pcap|->, --in <dev|pcap|->, --dev <dev|pcap|->
Define un dispositivo de entrada. Puede ser un dispositivo de red, un archivo pcap o stdin (“-”). En caso de un archivo pcap, el tipo de pcap (opción -D) se determina automáticamente por la magia del archivo pcap. En caso de stdin, se asume que el flujo de entrada es un archivo pcap. Si el tipo de enlace pcap es Netlink y el tipo pcap es el formato predeterminado (usec o nsec), cada paquete se envolverá con una cabecera cocida pcap [2].
-o <dev|pcap|dir|cfg|->, --out <dev|pcap|dir|cfg|->
Define el dispositivo de salida. Puede ser un dispositivo de red, un archivo pcap, un directorio, un archivo de configuración de trafgen(8) o stdout (“-”). Si el dispositivo de salida es un archivo pcap o un archivo de configuración de trafgen(8), puede incluir un formato de tiempo definido por strfime(3). Si se usa junto con la opción -F, cada archivo rotado tendrá una marca de tiempo única. En el caso de un archivo pcap que no deba tener el tipo pcap predeterminado (0xa1b2c3d4), se debe proporcionar la opción adicional -T. Si se da un directorio, entonces, en lugar de un único archivo pcap, se generan múltiples archivos pcap con rotación basada en el tamaño máximo del archivo o en un intervalo dado (opción -F). Opcionalmente, enviar la señal SIGHUP al proceso netsniff-ng provoca una rotación prematura del archivo. Un archivo de configuración de trafgen actualmente solo se puede especificar si el dispositivo de entrada es un archivo pcap. Para especificar un archivo pcap como dispositivo de salida, el nombre del archivo debe tener “.pcap” como extensión. Si se proporciona stdout como dispositivo, entonces se escribirá una configuración de trafgen en stdout si el dispositivo de entrada es un archivo pcap, o un archivo pcap si el dispositivo de entrada es un dispositivo de red. Si el dispositivo de entrada es un dispositivo monitor Netlink y el tipo pcap es predeterminado (usec o nsec), cada paquete se envolverá con una cabecera cocida pcap [2] para mantener el número de familia Netlink (los tipos pcap de Kuznetzov y netsniff-ng ya contienen el número de familia en el campo del número de protocolo).
-C <id>, --fanout-group <id>
Si se inician múltiples instancias de netsniff-ng que tienen el mismo id de grupo de fanout de paquetes, entonces el tráfico de red entrante se distribuye/equilibra entre estos participantes del grupo. Esto proporciona una mejor escalabilidad que ejecutar múltiples procesos netsniff-ng sin un parámetro de grupo de fanout en paralelo, sino solo con un filtro BPF adjunto, ya que un paquete de lo contrario tendría que ser entregado a todos los procesos de captura, en lugar de solo una vez a un miembro del fanout. Naturalmente, cada miembro del fanout puede tener sus propios filtros BPF adjuntos.
-K <hash|lb|cpu|rnd|roll|qm>, --fanout-type <hash|lb|cpu|rnd|roll|qm>
Este parámetro especifica la disciplina de fanout, en otras palabras, cómo se despacha el tráfico de red capturado a los miembros del grupo de fanout. Las opciones son distribuir el tráfico por el hash del paquete (“hash”), de forma cíclica (“lb”), por la CPU en la que llegó el paquete (“cpu”), de forma aleatoria (“rnd”), por desbordamiento de sockets (“roll”) que significa que si la cola de un socket está llena, pasamos al siguiente, o por mapeo de cola de hardware de la NIC (“qm”).
-L <defrag|roll>, --fanout-opts <defrag|roll>
Define algunas opciones auxiliares de fanout para ser usadas además de un tipo de fanout dado. Estas opciones se aplican a cualquier tipo de fanout. En caso de “defrag”, se le indica al kernel que desfragmente los paquetes antes de entregarlos al espacio de usuario, y “roll” proporciona la misma opción de desbordamiento que el tipo de fanout “roll”, de modo que en cualquier tipo de fanout diferente que se utilice (por ejemplo, “qm”) el socket puede desbordarse temporalmente al siguiente miembro del grupo de fanout en caso de que la cola del original esté llena.
-f, --filter <bpf-file|-|expr>
Especifica no volcar todo el tráfico, sino filtrar el pajar de paquetes de red. Como filtro, se puede pasar un archivo compilado de bpfc(8) / stdin como parámetro o una expresión de filtro tipo tcpdump(1) entre comillas. Para detalles sobre el archivo bpf, consulte bpfc(8), para detalles sobre un filtro tipo tcpdump(1), consulte la sección “ejemplo de filtro” o pcap-filter(7). Una expresión de filtro también se puede pasar a netsniff-ng sin la opción -f en caso de que no haya ninguna opción posterior después de la expresión de filtro de la línea de comandos.
-t, --type <type>
Esto define algún tipo de mecanismos de filtrado en términos de direccionamiento. Los valores posibles para type son “host” (hacia nosotros), “broadcast” (a todos), “multicast” (a grupo), “

OPTIONS

-o <interface>, --out <interface>
The interface to write packets to. This can be a network device (e.g. eth0), a pcap file (e.g. dump.pcap), or a directory. If a directory is specified, netsniff-ng will create timestamped pcap files inside it.
-i <interface>, --in <interface>
The interface to read packets from. Can be a network device, a pcap file, or the keyword “any” to capture from all devices. Default is “any”.
-t, --trace
Trace mode. Instead of dumping packets to stdout, netsniff-ng will print packet dissector information to stderr. This is useful for debugging.
-f <file>, --filter <file>
Load a Berkeley Packet Filter (BPF) from the specified file. This allows you to filter traffic before it is processed.
-p <packets>, --packets <packets>
The number of packets to capture. If set to 0, capture indefinitely.
-X, --hex
Output packets in hexadecimal format.
-A, --ascii
Output packets in ASCII format.
-J, --jumbo
Enable jumbo frame support. This increases the ring buffer size to accommodate larger frames.
-r, --ring-size <size>
Set the ring buffer size. Size can be specified in bytes, kilobytes (KiB), megabytes (MiB), or gigabytes (GiB).
-s, --silent
Silent mode. Do not print any packet information to the terminal.
-m, --mmap
Use memory-mapped I/O for pcap files. This is the default for replaying pcap files.
-g, --sg
Use scatter-gather I/O for pcap files. This is the default for capturing pcap files.
-c, --clrw
Use read/write I/O for pcap files. This is slower but may have lower latency.
-F, --interval <size|time>
Set the pcap file rotation interval. Can be specified in size (e.g., 100MiB) or time (e.g., 1h).
-P <name>, --prefix <name>
Set a prefix for pcap file names. Default is "dump-".
-O <N>, --overwrite <N>
Use a number from 0 to N-1 in the filename instead of a timestamp. Overwrites previous files when the number wraps around.
-T <pcap-magic>, --magic <pcap-magic>
Specify the pcap file type magic number. Default is the standard tcpdump format (0xa1b2c3d4).
-D, --dump-pcap-types
Dump available pcap types and their capabilities to stdout and exit.
-B, --dump-bpf
Dump the BPF disassembly to stdout during ring setup.
-r, --rand
Randomize packet order in the output ring buffer when input and output devices are both network devices.
-M, --no-promisc
Do not put the network interface into promiscuous mode. Default is promiscuous mode enabled.
-N, --no-hwtimestamp
Disable hardware timestamping for RX packets. Force the use of software timestamps instead.
-A, --no-sock-mem
Prevent netsniff-ng from adjusting socket read/write buffers.
-G, --sg
Use scatter-gather I/O for pcap file I/O. This is the default when capturing pcap files.
-k <uint>, --kernel-pull <uint>
Manually define the interval in microseconds for the kernel to process ring buffer frames. Default is 10us.
-b <cpu>, --bind-cpu <cpu>
Pin netsniff-ng to a specific CPU and migrate the NIC's IRQ affinity to that CPU.
-u <uid>, --user <uid> resp. -g <gid>, --group <gid>
Drop privileges to the specified user/group ID after ring setup.
-H, --prio-high
Set the process priority to high to achieve a higher scheduling rate.
-Q, --notouch-irq
Do not reassign the NIC's IRQ CPU affinity settings.
-s, --silent
Do not enter the packet dissector and do not print any packet information to the terminal.
-q, --less
Print less verbose one-line information for each packet.
-X, --hex
Only dump packets in hex format to the terminal.
-l, --ascii
Only display ASCII printable characters.
-U, --update
Update the GeoIP database. Configuration is in /etc/netsniff-ng/geoip.conf.
-w, --cooked
Replace the frame link header with a Linux "cooked" header, preserving link type and protocol information.
-V, --verbose
Be more verbose during startup, showing detailed ring setup information.
-v, --version
Show version information and exit.
-h, --help
Show user help and exit.
-R, --rfraw
Enable monitor mode for wireless devices. Creates a mon<X> device for listening and allows analysis, dumping, or replaying of raw 802.11 frames.
-n <0|uint>, --num <0|uint>
Process a specified number of packets and then exit. 0 means infinite packets.

USAGE EXAMPLE

netsniff-ng
Capture all traffic in promiscuous mode and display dissector output to the terminal. No files are recorded.
netsniff-ng --in eth0 --out dump.pcap -s -T 0xa1e2cb12 -b 0 tcp or udp
Capture TCP or UDP traffic from eth0 into dump.pcap with netsniff-ng specific extensions. Do not print to terminal. Pin process and NIC IRQ to CPU 0. Use scatter-gather I/O.
netsniff-ng --in wlan0 --rfraw --out dump.pcap --silent --bind-cpu 0
Capture raw 802.11 frames from wlan0 in monitor mode into dump.pcap. Be silent and pin to CPU 0. Use scatter-gather I/O.
netsniff-ng --in dump.pcap --mmap --out eth0 -k1000 --silent --bind-cpu 0
Replay dump.pcap using mmap I/O, sending packets to eth0. Be silent and pin to CPU 0. Trigger kernel every 1000us. Pcap magic type detected automatically.
netsniff-ng --in eth0 --out eth1 --silent --bind-cpu 0 --type host -r
Redirect traffic from eth0 to eth1, only for host-bound traffic. Randomize output packet order. Be silent and pin to CPU 0.
netsniff-ng --in team0 --out /opt/probe/ -s -m --interval 100MiB -b 0
Capture on team0, split into 100MiB files in /opt/probe/. Use mmap I/O and pin to CPU 0.

EXAMPLE

netsniff-ng --in em1 --out dump.pcap -p -s -S
Captures network traffic on device em1 and writes it to dump.pcap. This example uses mmap(2) I/O as a pcap write method, support for super jumbo frames is built-in (does not need to be configured here), and does not print the captured data to the terminal. Pin netsniff-ng and NIC IRQ affinity to CPU 0. The default pcap magic type is 0xa1b2c3d4 (tcpdump-capable pcap).
netsniff-ng --in vlan0 --out dump.pcap -c -u `id -u bob` -g `id -g bob`
Capture network traffic on device vlan0 into a pcap file called dump.pcap by using normal read(2), write(2) I/O for the pcap file (slower but less latency). Also, after setting up the RX_RING for capture, drop privileges from root to the user and group “bob”. Invoke the packet dissector and print packet contents to the terminal for further analysis.
netsniff-ng --in any --filter http.bpf -B --ascii -V
Capture from all available networking interfaces and install a low-level filter that was previously compiled by bpfc(8) into http.bpf in order to filter HTTP traffic. Super jumbo frame support is automatically enabled and only print human readable packet data to the terminal, and also be more verbose during setup phase. Moreover, dump a BPF disassembly of http.bpf.
netsniff-ng --in dump.pcap --out dump.cfg --silent
Convert the pcap file dump.pcap into a trafgen(8) configuration file dump.cfg. Do not print pcap contents to the terminal.
netsniff-ng -i dump.pcap -f beacon.bpf -o -
Convert the pcap file dump.pcap into a trafgen(8) configuration file and write it to stdout. However, do not dump all of its content, but only the one that passes the low-level filter for raw 802.11 from beacon.bpf. The BPF engine here is invoked in user space inside of netsniff-ng, so Linux extensions are not available.
cat foo.pcap | netsniff-ng -i - -o -
Read a pcap file from stdin and convert it into a trafgen(8) configuration file to stdout.
netsniff-ng -i nlmon0 -o dump.pcap -s
Capture netlink traffic to a pcap file. This command needs a netlink monitoring device to be set up beforehand using the follwing commands using ip(1) from the iproute2 utility collection:


modprobe nlmon
ip link add type nlmon
ip link set nlmon0 up

To tear down the nlmon0 device, use the following commands:


ip link set nlmon0 down
ip link del dev nlmon0
rmmod nlmon

netsniff-ng --fanout-group 1 --fanout-type cpu --fanout-opts defrag --bind-cpu 0 --notouch-irq --silent --in em1 --out /var/cap/cpu0/ --interval 120sec
Start two netsniff-ng fanout instances. Both are assigned into the same fanout group membership and traffic is splitted among them by incoming cpu. Furthermore, the kernel is supposed to defragment possible incoming fragments. First instance is assigned to CPU 0 and the second one to CPU 1, IRQ bindings are not altered as they might have been adapted to this scenario by the user a-priori, and traffic is captured on interface em1, and written out in 120 second intervals as pcap files into /var/cap/cpu0/. Tools like mergecap(1) will be able to merge the cpu0/1 split back together if needed.

FILTER EXAMPLE

netsniff-ng supports both, low-level and high-level filters that are attached to its packet(7) socket. Low-level filters are described in the bpfc(8) man page.

Low-level filters can be used with netsniff-ng in the following way:


1. bpfc foo > bar
2. netsniff-ng -f bar
3. bpfc foo | netsniff-ng -i nlmon0 -f -

Here, foo is the bpfc program that will be translated into a netsniff-ng readable “opcodes” file and passed to netsniff-ng through the -f option.

Similarly, high-level filter can be either passed through the -f option, e.g. -f "tcp or udp" or at the end of all options without the “-f”.

The filter syntax is the same as in tcpdump(8), which is described in the man page pcap-filter(7). Just to quote some examples:

host sundown
To select all packets arriving at or departing from sundown.
host helios and (hot or ace)
To select traffic between helios and either hot or ace.
ip host ace and not helios
To select all IP packets between ace and any host except helios.
net ucb-ether
To select all traffic between local hosts and hosts at Berkeley.
gateway snup and (port ftp or ftp-data)
To select all FTP traffic through Internet gateway snup.
ip and not net localnet
To select traffic neither sourced from, nor destined for, local hosts. If you have a gateway to another network, this traffic should never make it onto your local network.
tcp[tcpflags] & (tcp-syn|tcp-fin) != 0 and not src and dst net localnet
To select the start and end packets (the SYN and FIN packets) of each TCP conversation that involve a non-local host.
tcp port 80 and (((ip[2:2] - ((ip[0]&0xf)<<2)) - ((tcp[12]&0xf0)>>2)) != 0)
To select all IPv4 HTTP packets to and from port 80, that is to say, print only packets that contain data, not, for example, SYN and FIN packets and ACK-only packets. (IPv6 is left as an exercise for the reader.)
gateway snup and ip[2:2] > 576
To select IP packets longer than 576 bytes sent through gateway snup.
ether[0] & 1 = 0 and ip[16] >= 224
To select IP broadcast or multicast packets that were not sent via Ethernet broadcast or multicast.
icmp[icmptype] != icmp-echo and icmp[icmptype] != icmp-echoreply
To select all ICMP packets that are not echo requests or replies (that is to say, not "ping" packets).

PCAP FORMATS:

netsniff-ng supports a couple of pcap formats, visible through ``netsniff-ng -D'':

tcpdump-capable pcap (default)
Pcap magic number is encoded as 0xa1b2c3d4 resp. 0xd4c3b2a1. As packet meta data this format contains the timeval in microseconds, the original packet length and the captured packet length.
tcpdump-capable pcap with ns resolution
Pcap magic number is encoded as 0xa1b23c4d resp. 0x4d3cb2a1. As packet meta data this format contains the timeval in nanoseconds, the original packet length and the captured packet length.
Alexey Kuznetzov's pcap
Pcap magic number is encoded as 0xa1b2cd34 resp. 0x34cdb2a1. As packet meta data this format contains the timeval in microseconds, the original packet length, the captured packet length, the interface index (sll_ifindex), the packet's protocol (sll_protocol), and the packet type (sll_pkttype).
netsniff-ng pcap
Pcap magic number is encoded as 0xa1e2cb12 resp. 0x12cbe2a1. As packet meta data this format contains the timeval in nanoseconds, the original packet length, the captured packet length, the timestamp hw/sw source, the interface index (sll_ifindex), the packet's protocol (sll_protocol), the packet type (sll_pkttype) and the hardware type (sll_hatype).

For further implementation details or format support in your application, have a look at pcap_io.h in the netsniff-ng sources.

NOTE

To avoid confusion, it should be noted that there is another network analyzer with a similar name, called NetSniff, that is unrelated to the netsniff-ng project.

For introducing bit errors, delays with random variation and more while replaying pcaps, make use of tc(8) with its disciplines such as netem.

netsniff-ng does only some basic, architecture generic tuning on startup. If you are considering to do high performance capturing, you need to carefully tune your machine, both hardware and software. Simply letting netsniff-ng run without thinking about your underlying system might not necessarily give you the desired performance. Note that tuning your system is always a tradeoff and fine-grained balancing act (throughput versus latency). You should know what you are doing!

One recommendation for software-based tuning is tuned(8). Besides that, there are many other things to consider. Just to throw you a few things that you might want to look at: NAPI networking drivers, tickless kernel, I/OAT DMA engine, Direct Cache Access, RAM-based file systems, multi-queues, and many more things. Also, you might want to read the kernel's Documentation/networking/scaling.txt file regarding technologies such as RSS, RPS, RFS, aRFS and XPS. Also check your ethtool(8) settings, for example regarding offloading or Ethernet pause frames.

Moreover, to get a deeper understanding of netsniff-ng internals and how it interacts with the Linux kernel, the kernel documentation under Documentation/networking/{packet_mmap.txt, filter.txt, multiqueue.txt} might be of interest.

La ruta más fácil es simplemente suplantar la pasarela local, robando el tráfico del cliente en ruta a algún destino remoto. Por supuesto, el tráfico debe ser reenviado por su máquina atacante, ya sea habilitando el reenvío de IP del kernel o con un programa de espacio de usuario que logre lo mismo (fragrouter -B1).

Varias personas han informado haber destruido la conectividad de su LAN con el mundo exterior mediante ARP spoofing de la pasarela, y olvidando habilitar el reenvío de IP en la máquina atacante. No hagas esto. Has sido advertido.

Una opción más segura que el ARP spoofing sería utilizar la función de "reflejo de puerto" si el hardware de su switch lo admite y si tiene acceso al switch.

Si no necesita volcar todo el tráfico posible, debe considerar ejecutar netsniff-ng con un filtro BPF para la ruta de entrada. Para este propósito, lea la página del manual de bpfc(8).

Además, para agregar múltiples NIC en las que desea capturar, debería considerar el uso de dispositivos de equipo (team devices), que se explican en libteam o teamd(8), respectivamente.

BUGS

Al reproducir archivos pcap, la información de tiempo del encabezado del paquete pcap se ignora actualmente.

Además, al reproducir archivos pcap, la desmultiplexación del tráfico entre múltiples interfaces de red no funciona. Actualmente, solo se envía a través de la interfaz que se proporciona con el parámetro --out.

Al capturar tráfico en la interfaz Ethernet, se crea el archivo pcap y se reciben paquetes, pero sin un encabezado 802.1Q. Cuando se usa tshark, todos los encabezados son visibles, pero netsniff-ng elimina los encabezados 802.1Q. ¿Es ese el comportamiento normal?

Sí y no. La forma en que los encabezados VLAN se manejan en los sockets PF_PACKET por el kernel es algo "problemática" [1]. El problema en el kernel de Linux es que algunos controladores ya manejan VLANs, otros no. Aquellos que lo manejan pueden tener implementaciones diferentes, como aceleración de hardware y demás. Así que en algunos casos la etiqueta VLAN se elimina incluso antes de entrar en la pila de protocolos, en otros casos probablemente no. En resumen, se introdujo un "hack" en PF_PACKET para que una ID de VLAN sea visible en alguna estructura de datos auxiliar accesible desde el RX_RING.

Luego se vuelve realmente complicado en el espacio de usuario para volver a colocar artificialmente el encabezado VLAN en el lugar correcto. Sin mencionar las implicaciones de rendimiento resultantes en todas las herramientas de libpcap(3), ya que partes del paquete deben copiarse para el reasamblaje mediante memmove(3).

Un usuario informó lo siguiente, solo para demostrar este lío: se hicieron algunas pruebas con dos máquinas, y parece que los resultados dependen del controlador...


AR8131:
ethtool -k eth0 da "rx-vlan-offload: on"
- wireshark obtiene el encabezado vlan
- netsniff-ng no obtiene el encabezado vlan
ethtool -K eth0 rxvlan off
- wireshark obtiene un encabezado QinQ aunque nadie envió QinQ
- netsniff-ng obtiene el encabezado vlan


RTL8111/8168B:
ethtool -k eth0 da "rx-vlan-offload: on"
- wireshark obtiene el encabezado vlan
- netsniff-ng no obtiene el encabezado vlan
ethtool -K eth0 rxvlan off
- wireshark obtiene el encabezado vlan
- netsniff-ng no obtiene el encabezado vlan

Incluso si estuviéramos de acuerdo en hacer la misma solución alternativa que libpcap, todavía no podríamos ver QinQ, por ejemplo, debido al hecho de que solo una etiqueta VLAN se almacena en la estructura de datos auxiliar del kernel. Creemos que debería haber un buen consenso en el lado del espacio del kernel sobre lo que se transfiere primero al espacio de usuario.

Actualización (28.11.2012): el kernel de Linux y también bpfc(8) tienen soporte incorporado para el filtrado de VLAN acelerado por hardware, aunque las etiquetas pueden no ser visibles en la carga útil en sí, como se informa aquí. Sin embargo, el filtrado para VLANs funciona de manera confiable si su NIC lo admite. Consulte bpfc(8) para ver un ejemplo.
