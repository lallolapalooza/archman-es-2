netplan(5)

Introducción a Netplan(5) Introducción a Netplan(5)

NOMBRE

netplan - abstracción de configuración de red YAML para varios backends

SINOPSIS

netplan [COMANDO|help]

COMANDOS

Consulte netplan help para obtener una lista de comandos disponibles en este sistema.

DESCRIPCIÓN

Los instaladores de distribución, la instanciación en la nube, las compilaciones de imágenes para dispositivos particulares o cualquier otra forma de desplegar un sistema operativo colocan su configuración de red deseada en archivos de configuración YAML. Durante el arranque temprano, se ejecuta el "network renderer" de Netplan, que lee /{lib,etc,run}/netplan/*.yaml y escribe la configuración en /run para ceder el control de los dispositivos al demonio de red especificado.

•
Los dispositivos configurados son manejados por systemd-networkd por defecto, a menos que se marquen explícitamente como gestionados por un renderizador específico (NetworkManager)
•
Los dispositivos no cubiertos por la configuración de red no se tocan en absoluto.
•
Utilizable en initramfs (pocas dependencias y rápido)
•
Sin configuración generada persistente, solo configuración YAML original
•
El analizador soporta múltiples archivos de configuración para permitir que aplicaciones como libvirt o lxd empaqueten la configuración de red esperada (virbr0, lxdbr0), o para cambiar la política predeterminada global para usar NetworkManager para todo.
•
Conserva la flexibilidad para cambiar backends/políticas más tarde o adaptarse a la eliminación de NetworkManager, ya que la configuración generada es efímera.

Estructura general

Los archivos de configuración de Netplan utilizan el formato YAML. Se consideran todos los archivos /{lib,etc,run}/netplan/*.yaml. Los archivos lexicográficamente posteriores (independientemente del directorio en el que se encuentren) modifican (nuevas claves de mapeo) o anulan (mismas claves de mapeo) los anteriores. Un archivo en /run/netplan sombrea completamente un archivo con el mismo nombre en /etc/netplan, y un archivo en cualquiera de esos directorios sombrea un archivo con el mismo nombre en /lib/netplan.

El nodo de nivel superior en un archivo de configuración de Netplan es un mapeo network: que contiene version: 2 (el YAML que está siendo utilizado actualmente por curtin, MAAS, etc. es la versión 1), y luego definiciones de dispositivos agrupadas por su tipo, como ethernets:, modems:, wifis: o bridges:. Estos son los tipos que nuestro renderizador puede entender y son compatibles con nuestros backends.

Cada bloque de tipo contiene definiciones de dispositivos como un mapa donde las claves (llamadas "IDs de configuración") se definen a continuación.

IDs de configuración de dispositivo

Los nombres de las claves debajo de los mapas de definición por tipo de dispositivo (como ethernets:) se denominan "IDs". Deben ser únicos en todo el conjunto de archivos de configuración. Su propósito principal es servir como nombres de anclaje para dispositivos compuestos, por ejemplo, para enumerar los miembros de un puente que se está definiendo actualmente.

(Desde 0.97) Si una interfaz se define con un ID en un archivo de configuración, será activada por el renderizador aplicable. Para que Netplan no toque una interfaz en absoluto, debe omitirse por completo de los archivos de configuración de Netplan.

Hay dos clases de definiciones de dispositivos, física y estructuralmente diferentes, y el campo ID tiene una interpretación diferente para cada una:

Dispositivos físicos

(Ejemplos: Ethernet, módem, Wi-Fi) Estos pueden aparecer y desaparecer dinámicamente entre reinicios e incluso durante el tiempo de ejecución (hot plugging). En el caso genérico, se pueden seleccionar mediante reglas match: sobre propiedades deseadas, como nombre/patrón de nombre, dirección MAC, controlador o rutas de dispositivo. En general, estos coincidirán con cualquier número de dispositivos (a menos que se refieran a propiedades únicas como la ruta completa o la dirección MAC), por lo que sin más conocimiento sobre el hardware, estos siempre se considerarán como un grupo.

Es válido no especificar ninguna regla de coincidencia, en cuyo caso el campo ID es simplemente el nombre de la interfaz que se debe hacer coincidir. Esto es útil principalmente si desea mantener simples los casos simples, y así es como se ha hecho la configuración del dispositivo de red durante mucho tiempo.

Si hay reglas match:, entonces el campo ID es un nombre puramente opaco que solo se utiliza para referencias de definiciones de dispositivos compuestos en la configuración.

Dispositivos virtuales

(Ejemplos: veth, bridge, bond, vrf) Estos están completamente bajo el control del archivo(s) de configuración y la pila de red. Es decir, estos dispositivos se crean en lugar de coincidir. Por lo tanto, match: y set-name: no son aplicables para estos, y el campo ID es el nombre del dispositivo virtual creado.

Configuración YAML

Estructura de configuración de nivel superior

La estructura general de un archivo YAML de Netplan se muestra a continuación.

network:
  version: NUMBER
  renderer: STRING
  bonds: MAPPING
  bridges: MAPPING
  dummy-devices: MAPPING
  ethernets: MAPPING
  modems: MAPPING
  tunnels: MAPPING
  virtual-ethernets: MAPPING
  vlans: MAPPING
  vrfs: MAPPING
  wifis: MAPPING
  nm-devices: MAPPING
•
version (número)

Define qué versión del formato de configuración se utiliza. El único valor admitido es 2. Por defecto es 2 si no se define.

•
renderer (escalar)

Define qué herramienta de configuración de red se utilizará para configurar su configuración. Los valores válidos son networkd y NetworkManager. Por defecto es networkd si no se define.

•
bonds (mapeo)

Crea y configura dispositivos de agregación de enlaces (bonding).

•
bridges (mapeo)

Crea y configura dispositivos de puente (bridge).

•
dummy-devices (mapeo) – desde 0.107

Crea y configura dispositivos virtuales.

•
ethernets (mapeo)

Configura interfaces Ethernet físicas.

•
modems (mapeo)

Configura módems

•
tunnels (mapeo)

Crea y configura diferentes tipos de túneles virtuales.

•
virtual-ethernets (mapeo) – desde 0.107

Crea y configura dispositivos de Ethernet Virtual (veth).

•
vlans (mapeo)

Crea y configura VLANs.

•
vrfs (mapeo)

Configura dispositivos de Virtual Routing and Forwarding (VRF).

•
wifis (mapeo)

Configura interfaces Wi-Fi físicas como cliente, adhoc o punto de acceso.

•
nm-devices (mapeo)

nm-devices se utilizan en situaciones en las que Netplan no admite el tipo de conexión. La configuración sin procesar esperada por NetworkManager se puede definir y se pasará tal cual (passthrough) al archivo .nmconnection. Los usuarios normalmente no utilizarán este tipo de dispositivo.

Todas las propiedades para todos los tipos de dispositivos se describirán en las siguientes secciones.

Propiedades para tipos de dispositivos físicos

Estas propiedades se utilizan con dispositivos físicos como interfaces de red Ethernet y Wi-Fi.

Nota: Algunas opciones no funcionarán de manera fiable para dispositivos coincididos solo por nombre y renderizados por networkd, debido a interacciones con el cambio de nombre de dispositivos en udev. Empareje los dispositivos por MAC al establecer opciones como: wakeonlan o *-offload.

•
match (mapeo)

Esto selecciona un subconjunto de dispositivos físicos disponibles por varias propiedades de hardware. La siguiente configuración se aplicará a todos los dispositivos coincidentes, tan pronto como aparezcan. *Todas* las propiedades especificadas deben coincidir.

•
name (escalar)

Nombre de la interfaz actual. Se admiten comodines (globs), y el caso de uso principal para coincidir con nombres, ya que seleccionar un nombre fijo se puede lograr más fácilmente no teniendo match: en absoluto y simplemente usando el ID (ver arriba). (NetworkManager: a partir de v1.14.0)

•
macaddress (escalar)

Dirección MAC permanente de 6 bytes del dispositivo en el formato XX:XX:XX:XX:XX:XX o 20 bytes para dispositivos InfiniBand (IPoIB). No se permiten comodines. Esto no coincide con las direcciones MAC virtuales para veth, bridge, bond, vlan, ...

•
driver (escalar o secuencia de escalares) – secuencia desde 0.104

Nombre del controlador del kernel, correspondiente a la propiedad udev DRIVER. Se admite una secuencia de comodines, cualquiera de los cuales debe coincidir. La coincidencia por controlador *solo* se admite con networkd.

Ejemplos:

•
Todas las tarjetas en el segundo bus PCI:
network:
  ethernets:
    myinterface:
      match:
        name: enp2*
•
Dirección MAC fija:
network:
  ethernets:
    interface0:
      match:
        macaddress: 11:22:33:AA:BB:FF
•
Primera tarjeta del controlador ixgbe:
network:
  ethernets:
    nic0:
      match:
        driver: ixgbe
        name: en*s0
•
Primera tarjeta con un controlador que coincide con bcmgenet o smsc*:
network:
  ethernets:
    nic0:
      match:
        driver: ["bcmgenet", "smsc*"]
        name: en*
•
set-name (escalar)

Al coincidir con propiedades únicas como la ruta o la MAC, o con supuestos adicionales como "solo habrá un dispositivo Wi-Fi", las reglas de coincidencia se pueden escribir de modo que solo coincidan con un dispositivo. Luego, esta propiedad se puede usar para darle a ese dispositivo un nombre más específico o deseable que el predeterminado de los ifnames de udev. Cualquier dispositivo adicional que cumpla con las reglas de coincidencia fallará en renombrarse y conservará el nombre original del kernel (y dmesg mostrará un error).

•
wakeonlan (booleano)

Habilita Wake on LAN. Desactivado por defecto.

•
emit-lldp (booleano) – desde 0.99

(solo backend de networkd) Si emitir paquetes LLDP. Desactivado por defecto.

•
receive-checksum-offload (booleano) – desde 0.104

(solo backend de networkd) Si se establece en true (false), se habilita (deshabilita) la descarga de hardware para la suma de verificación de paquetes de red de entrada. Cuando no se establece, se utilizará el valor predeterminado del kernel.

•
transmit-checksum-offload (booleano) – desde 0.104

(solo backend de networkd) Si se establece en true (false), se habilita (deshabilita) la descarga de hardware para la suma de verificación de paquetes de red de salida. Cuando no se establece, se utilizará el valor predeterminado del kernel.

•
tcp-segmentation-offload (booleano) – desde 0.104

(solo backend de networkd) Si se establece en true (false), se habilita (deshabilita) la descarga de segmentación TCP (TSO). Cuando no se establece, se utilizará el valor predeterminado del kernel.

•
tcp6-segmentation-offload (booleano) – desde 0.104

(solo backend de networkd) Si se establece en true (false), se habilita (deshabilita) la descarga de segmentación TCP6 (tx-tcp6-segmentation). Cuando no se establece, se utilizará el valor predeterminado del kernel.

•
generic-segmentation-offload (booleano) – desde 0.104

(solo backend de networkd) Si se establece en true (false), se habilita (deshabilita) la descarga de segmentación genérica (GSO). Cuando no se establece, se utilizará el valor predeterminado del kernel.

•
generic-receive-offload (booleano) – desde 0.104

(solo backend de networkd) Si se establece en true (false), se habilita (deshabilita) la descarga de recepción genérica (GRO). Cuando no se establece, se utilizará el valor predeterminado del kernel.

•
large-receive-offload (booleano) – desde 0.104

(solo backend de networkd) Si se establece en true (false), se habilita (deshabilita) la descarga de recepción grande (LRO). Cuando no se establece, se utilizará el valor predeterminado del kernel.

•
openvswitch (mapeo) – desde 0.100

Esto proporciona configuración adicional para el dispositivo de red openvswitch. Si Open vSwitch no está disponible en el sistema, Netplan trata la presencia de la configuración openvswitch como un error.

Cualquier dispositivo de red compatible que se declare con el mapeo openvswitch (o cualquier bond/bridge que incluya una interfaz con una configuración openvswitch) se creará en openvswitch en lugar del renderizador definido. En el caso de una definición de vlan declarada de la misma manera, Netplan creará un puente VLAN ficticio en openvswitch con las propiedades de vlan solicitadas.

•
external-ids (mapeo) – desde 0.100

Pasado directamente a Open vSwitch

•
other-config (mapeo) – desde 0.100

Pasado directamente a Open vSwitch

Routing

Static routes can be defined per device or globally.

•
routes (sequence of mappings)

A list of static routes. Each route has the following attributes:

to (scalar) – destination network in CIDR notation.
via (scalar) – gateway address.
metric (scalar) – route metric (lower is preferred).
table (scalar) – route table ID.

Example:

network:
  ethernets:
    eth0:
      routes:
        - to: 10.0.0.0/16
          via: 172.16.0.1
          metric: 100
        - to: 0.0.0.0/0
          via: 172.16.0.1
•
routing-policy (sequence of mappings)

A list of policy routing rules. Each rule has the following attributes:

from (scalar) – source network in CIDR notation.
to (scalar) – destination network in CIDR notation.
via (scalar) – gateway address.
metric (scalar) – rule priority (lower is preferred).
table (scalar) – route table ID.

Example:

network:
  rules:
    - from: 10.0.0.0/16
      to: 0.0.0.0/0
      table: 100

Renderers

Netplan supports multiple network configuration backends, called renderers. The supported renderers are:

  • networkd: systemd-networkd is a system service that manages network configuration.
  • NetworkManager: NetworkManager is a system service that manages network connections.

The renderer can be specified globally in the renderer: field of the network: section. If not specified, Netplan will default to networkd.

Some configurations are renderer-specific. For example, Wi-Fi support is only available in NetworkManager. If a configuration option is only supported by a specific renderer, it will be noted in the relevant section.

Device Matching

Netplan can match devices by various attributes. This is useful for applying specific configurations to devices, especially when device names might change.

•
match (mapping)

This key introduces a map of device attributes to match against. The following attributes are supported:

macaddress (scalar)

Matches the device's MAC address.

name (scalar)

Matches the device's name (e.g., eth0).

parent (scalar)

Matches the parent device of a virtual interface (e.g., the parent of a VLAN interface).

sriov-total-vfs (scalar)

Matches the total number of Virtual Functions (VFs) available on an SR-IOV Physical Function (PF).

Example:

network:
  ethernets:
    enp3s0:
      match:
        macaddress: 52:54:00:11:22:33
      dhcp4: true

Renaming Devices

Netplan allows renaming devices using the set-name option.

•
set-name (scalar)

The new name for the device.

Example:

network:
  ethernets:
    enp3s0:
      set-name: eno1
      dhcp4: true

Note: Renaming devices can interfere with other tools that rely on predictable device names, like udev rules. It is generally recommended to use MAC address matching instead of relying on device names.

IPv6 Router Advertisement Overrides

This section is only relevant when using the systemd-networkd backend. It allows you to override the default behavior of Router Advertisements (RAs).

•
ipv6-ra-set-flag-managed-address-configuration (boolean)

When set to true, the 'M' flag in RAs is set, indicating that hosts should use stateful configuration (DHCPv6) for addresses.

•
ipv6-ra-set-flag-other-configuration (boolean)

When set to true, the 'O' flag in RAs is set, indicating that hosts should use stateful configuration (DHCPv6) for other information (like DNS servers).

•
ipv6-ra-allow-change (boolean)

When set to true, allows changing the default RA settings.

•
ipv6-ra-default-hop-limit (scalar) – since 0.103

Sets the default hop limit for outgoing Router Advertisements. Default is 64.

•
ipv6-ra-default-lifetime (scalar) – since 0.103

Sets the default lifetime for Router Advertisements. Default is 1800 seconds.

•
ipv6-ra-reachable-time (scalar) – since 0.103

Sets the reachable time for neighbor discovery. Default is 30000 ms.

•
ipv6-ra-retrans-timer (scalar) – since 0.103

Sets the retransmission timer for neighbor discovery. Default is 0 ms.

Sobrescrituras de DHCP

Hay varias sobrescrituras de comportamiento de DHCP disponibles. La mayoría actualmente solo tienen efecto cuando se usa el backend networkd, con la excepción de use-routes y route-metric.

Las sobrescrituras solo tienen efecto si el dhcp4 o dhcp6 correspondiente está configurado como true.

Si tanto dhcp4 como dhcp6 son true, el backend networkd requiere que dhcp4-overrides y dhcp6-overrides contengan las mismas claves y valores. Si los valores no coinciden, se mostrará un error y la configuración de red no se aplicará.

Al usar el backend NetworkManager, se pueden especificar diferentes valores para dhcp4-overrides y dhcp6-overrides, y se aplicarán a los procesos del cliente DHCP según lo especificado en el YAML de Netplan.

•
dhcp4-overrides, dhcp6-overrides (mapeo)

Los mapeos dhcp4-overrides y dhcp6-override sobrescriben el comportamiento predeterminado de DHCP.

•
use-dns (booleano)

Predeterminado: true. Cuando es true, se utilizarán los servidores DNS recibidos del servidor DHCP y tendrán prioridad sobre los configurados estáticamente. Actualmente, solo tiene efecto en el backend networkd.

•
use-ntp (booleano)

Predeterminado: true. Cuando es true, los servidores NTP recibidos del servidor DHCP serán utilizados por systemd-timesyncd y tendrán prioridad sobre los configurados estáticamente. Actualmente, solo tiene efecto en el backend networkd.

•
send-hostname (booleano)

Predeterminado: true. Cuando es true, el nombre de host de la máquina se enviará al servidor DHCP. Actualmente, solo tiene efecto en el backend networkd.

•
use-hostname (booleano)

Predeterminado: true. Cuando es true, el nombre de host recibido del servidor DHCP se establecerá como el nombre de host transitorio del sistema. Actualmente, solo tiene efecto en el backend networkd.

•
use-mtu (booleano)

Predeterminado: true. Cuando es true, el MTU recibido del servidor DHCP se establecerá como el MTU de la interfaz de red. Cuando es false, se ignorará el MTU anunciado por el servidor DHCP. Actualmente, solo tiene efecto en el backend networkd.

•
hostname (escalar)

Utiliza este valor para el nombre de host que se envía al servidor DHCP, en lugar del nombre de host de la máquina. Actualmente, solo tiene efecto en el backend networkd.

•
use-routes (booleano)

Predeterminado: true. Cuando es true, las rutas recibidas del servidor DHCP se instalarán en la tabla de enrutamiento normalmente. Cuando se establece en false, se ignorarán las rutas del servidor DHCP: en este caso, el usuario es responsable de agregar rutas estáticas si es necesario para un funcionamiento correcto de la red. Esto permite a los usuarios evitar instalar una puerta de enlace predeterminada para las interfaces configuradas a través de DHCP. Disponible para los backends networkd y NetworkManager.

•
route-metric (escalar)

Utiliza este valor para la métrica predeterminada de las rutas agregadas automáticamente. Úsalo para priorizar rutas para dispositivos estableciendo una métrica más baja en una interfaz preferida. Disponible para los backends networkd y NetworkManager.

•
use-domains (escalar) – desde 0.98

Toma un booleano, o el valor especial route. Cuando es verdadero, el nombre de dominio recibido del servidor DHCP se utilizará como dominio de búsqueda DNS en este enlace, similar al efecto de la configuración Domains=. Si se establece en route, el nombre de dominio recibido del servidor DHCP se utilizará solo para enrutar consultas DNS, pero no para la búsqueda, similar al efecto de la configuración Domains= cuando el argumento va precedido de ~ (tilde).

Requiere característica: dhcp-use-domains

Sobrescrituras de Anuncio de Router IPv6

Sobrescrituras del comportamiento del Anuncio de Router IPv6 (RA) (solo compatible con el backend networkd).

•
ra-overrides (mapeo) – desde 1.1

Los mapeos ra-overrides sobrescriben el comportamiento predeterminado del Anuncio de Router IPv6.

•
use-dns (booleano)

Predeterminado: true. Cuando es true, se utilizarán los servidores DNS recibidos del Anuncio de Router. Actualmente, solo tiene efecto en el backend networkd.

•
use-domains (escalar)

Toma un booleano, o el valor especial route. Cuando es verdadero, el nombre de dominio recibido del Anuncio de Router se utilizará como dominio de búsqueda DNS en este enlace. Si se establece en route, el nombre de dominio recibido del RA IPv6 se utilizará solo para enrutar consultas DNS, pero no para la búsqueda. Predeterminado es false.

•
table (escalar)

El número de tabla de enrutamiento para las rutas recibidas en el RA IPv6. Los valores permitidos son enteros positivos a partir de 1. Algunos valores ya están en uso para referirse a tablas de enrutamiento específicas: ver {/etc,/usr/share}/iproute2/rt_tables.

Enrutamiento

Es posible un enrutamiento complejo con Netplan. Las rutas estáticas estándar, así como el enrutamiento de políticas que utiliza tablas de enrutamiento, son compatibles a través del backend networkd.

Estas opciones están disponibles para todos los tipos de interfaces.

Rutas predeterminadas

La necesidad más común de enrutamiento se refiere a la definición de rutas predeterminadas para acceder a Internet. Estas rutas predeterminadas solo se pueden definir una vez por familia IP y tabla de enrutamiento. Un ejemplo típico se vería así:

network:
  ethernets:
    eth0:
      [...]
      routes:
        - to: default # puede ser 0.0.0.0/0 opcionalmente
          via: 10.0.0.1
          metric: 100
          on-link: true
          advertised-mss: 1400
        - to: default # puede ser ::/0 opcionalmente
          via: cf02:de:ad:be:ef::2
    eth1:
      [...]
      routes:
        - to: default
          via: 172.134.67.1
          metric: 100
          on-link: true
          # No en la tabla de enrutamiento principal,
          # no entra en conflicto con la ruta predeterminada de eth0
      table: 76
•
routes (mapeo)

El bloque routes define rutas estáticas estándar para una interfaz. Se debe especificar al menos to. Si el tipo es local o nat, se asume un alcance predeterminado de host. Si el tipo es unicast y no se proporciona una puerta de enlace (via) o el tipo es broadcast, multicast o anycast, se asume un alcance predeterminado de link. De lo contrario, global es la configuración predeterminada.

Para from, to y via, se reconocen tanto direcciones IPv4 como IPv6, y deben estar en el formato addr/prefijo o addr.

•
from (escalar)

Establece una dirección IP de origen para el tráfico que pasa por la ruta. (NetworkManager: a partir de v1.8.0)

•
to (escalar)

Dirección de destino para la ruta.

•
via (escalar)

Dirección de la puerta de enlace a utilizar para esta ruta.

•
routing-policy (mapeo)

El bloque routing-policy define políticas de enrutamiento adicionales para una red, donde el tráfico puede ser manejado especialmente según la IP de origen, marca de firewall, etc.

Para from, to, se reconocen tanto direcciones IPv4 como IPv6, y deben estar en el formato addr/prefixlen o addr.

•
from (escalar)

Establece una dirección IP de origen para que coincida con el tráfico de esta regla de política.

•
to (escalar)

Coincide con el tráfico que va al destino especificado.

•
table (escalar)

El número de tabla para que coincida la ruta. En algunos escenarios, puede ser útil establecer rutas en una tabla de enrutamiento separada. También puede usarse para referirse a rutas que también aceptan un parámetro table. Los valores permitidos son enteros positivos a partir de 1. Algunos valores ya se utilizan para referirse a tablas de enrutamiento específicas: consulte /etc/iproute2/rt_tables.

•
priority (escalar)

Especifica una prioridad para la regla de política de enrutamiento, para influir en el orden en que se procesan las reglas de enrutamiento. Un número más alto significa menor prioridad: las reglas se procesan en orden por número de prioridad creciente. Se recomienda encarecidamente especificar una prioridad explícita y única para cada regla de política de enrutamiento y es obligatorio en el backend NetworkManager.

•
mark (escalar)

Haz que esta regla de política de enrutamiento coincida con el tráfico que ha sido marcado por el firewall iptables con este valor. Los valores permitidos son enteros positivos a partir de 1.

•
type-of-service (escalar)

Coincide esta regla de política en función del número de tipo de servicio aplicado al tráfico.

(yaml-auth)= ## Autenticación

Netplan admite configuraciones de autenticación avanzadas para interfaces Ethernet y Wi-Fi, así como redes Wi-Fi individuales, mediante el bloque auth.

•
auth (mapeo)

Especifica la configuración de autenticación para un dispositivo de tipo ethernets:, o una entrada access-points: en un dispositivo wifis:.

El bloque auth admite las siguientes propiedades:

•
key-management (escalar)

Los modos de gestión de claves admitidos son none (sin gestión de claves); psk (WPA con clave precompartida, común para Wi-Fi doméstico); psk-sha256 (WPA2 con clave precompartida, común para Wi-Fi doméstico); eap (WPA con EAP, común para Wi-Fi empresarial); eap-sha256 (se usa con WPA3-Enterprise); eap-suite-b-192 (se usa con WPA3-Enterprise); sae (utilizado por WPA3); y 802.1x (utilizado principalmente para conexiones Ethernet cableadas).

•
password (escalar)

La cadena de contraseña para EAP, o la clave precompartida para WPA-PSK.

Las siguientes propiedades se pueden usar si key-management es eap o 802.1x:

•
method (escalar)

El método EAP a utilizar. Los métodos EAP admitidos son tls (TLS), peap (Protected EAP), leap (Lightweight EAP), pwd (EAP Password) y ttls (Tunnelled TLS).

•
identity (escalar)

La identidad a utilizar para EAP.

•
anonymous-identity (escalar)

La identidad a pasar por el canal no cifrado si el método EAP elegido admite el paso de una identidad tunelizada diferente.

•
ca-certificate (escalar)

Ruta a un archivo con uno o más certificados de autoridad de certificación (CA) de confianza.

•
client-certificate (escalar)

Ruta a un archivo que contiene el certificado a ser utilizado por el cliente durante la autenticación.

•
client-key (escalar)

Ruta a un archivo que contiene la clave privada correspondiente al client-certificate.

•
client-key-password (escalar)

Contraseña a utilizar para descifrar la clave privada especificada en client-key si está cifrada.

•
phase2-auth (escalar) – desde 0.99

Mecanismo de autenticación de Fase 2.

Propiedades para el tipo de dispositivo ethernets

Estado: Opcional.

Propósito: Utilice la clave ethernets para configurar las interfaces Ethernet.

Estructura: La clave consiste en un mapeo de IDs de interfaz Ethernet. Cada ethernet tiene una serie de opciones de configuración. No es necesario definir cada interfaz por su nombre dentro del mapeo ethernets. Puede usar cualquier ID que describa la interfaz y emparejar la tarjeta de red real usando la clave match. La estructura general de configuración para Ethernet se muestra a continuación.

network:
  ethernets:
    device-id:
      ...

device-id es el identificador de la interfaz. Si utiliza el nombre de la interfaz como ID, Netplan emparejará esa interfaz.

Considere el siguiente ejemplo. En este caso, una interfaz llamada eth0 se configurará con DHCP.

network:
  ethernets:
    eth0:
      dhcp4: true

El device-id puede ser cualquier nombre descriptivo que usted considere significativo. Sin embargo, si no coincide con un nombre de interfaz real, debe usar la propiedad match para identificar el dispositivo que desea configurar.

El siguiente ejemplo define una conexión Ethernet llamada isp-interface (supuestamente una interfaz externa conectada al Proveedor de Servicios de Internet) y utiliza match para aplicar la configuración al dispositivo físico con la dirección MAC aa:bb:cc:00:11:22.

network:
  ethernets:
    isp-interface:
      match:
        macaddress: aa:bb:cc:00:11:22
      dhcp4: true

Las definiciones de dispositivos Ethernet, además de las comunes descritas anteriormente, también admiten algunas propiedades adicionales que se pueden utilizar para dispositivos SR-IOV.

•
link (escalar) – desde 0.99

(Solo dispositivos SR-IOV) La propiedad link declara el dispositivo como una Función Virtual del dispositivo de Función Física seleccionado, identificado por el ID de Netplan proporcionado.

Ejemplo:

network:
  ethernets:
    enp1: {...}
    enp1s16f1:
      link: enp1
•
virtual-function-count (escalar) – desde 0.99

(Solo dispositivos SR-IOV) En ciertos casos especiales, las VF pueden necesitar configurarse fuera de Netplan. Para tales configuraciones, virtual-function-count se puede usar opcionalmente para establecer un número explícito de Funciones Virtuales para la Función Física dada. Si no se establece, el valor predeterminado es crear solo tantas VF como se definan en la configuración de Netplan. Esto solo debe usarse para casos especiales.

Requiere característica: sriov

•
embedded-switch-mode (escalar) – desde 0.104

(Solo dispositivos SR-IOV) Cambia el modo operativo del switch integrado de un dispositivo PCI SmartNIC compatible (por ejemplo, Mellanox ConnectX-5). Los valores posibles son switchdev o legacy; si no se especifica, se utiliza la configuración predeterminada del proveedor.

Requiere característica: eswitch-mode

•
delay-virtual-functions-rebind (booleano) – desde 0.104

(Solo dispositivos SR-IOV) Retrasa la reasignación de funciones virtuales SR-IOV a su controlador después de cambiar la configuración de embedded-switch-mode a una etapa posterior. Se puede habilitar cuando se utiliza bonding/VF LAG. El valor predeterminado es false.

Requiere característica: eswitch-mode

•
infiniband-mode (escalar) – desde 0.105

(Solo dispositivos InfiniBand) Cambia el modo operativo de un dispositivo IPoIB. Los valores posibles son datagram o connected. Si no se especifica, se utiliza la configuración predeterminada del kernel.

Requiere característica: infiniband

(yaml-modems)= ## Propiedades para el tipo de dispositivo modems

Estado: Opcional.

Propósito: Utilice la clave modems para configurar interfaces de módem. La configuración de módem GSM/CDMA solo se admite para el backend NetworkManager. systemd-networkd no admite módems.

Estructura: La clave consta de un mapeo de IDs de módem. Cada modem tiene una serie de opciones de configuración. La estructura general de configuración para módems se muestra a continuación.

network:
  version: 2
  renderer: NetworkManager
  modems:
    cdc-wdm1:
      mtu: 1600
      apn: ISP.CINGULAR
      username: ISP@CINGULARGPRS.COM
      password: CINGULAR1
      number: "*99#"
      network-id: 24005
      device-id: da812de91eec16620b06cd0ca5cbc7ea25245222
      pin: 2345
      sim-id: 89148000000060671234
      sim-operator-id: 310260

Requiere característica: modems

•
apn (escalar) – desde 0.99

Establece el APN (Nombre de Punto de Acceso) del operador. Esto se puede omitir si auto-config está habilitado.

•
auto-config (booleano) – desde 0.99

Especifica si se debe intentar auto-configurar el módem buscando el operador en la base de datos del Proveedor de Banda Ancha Móvil. Esto puede no funcionar para todos los operadores.

•
device-id (escalar) – desde 0.99

Especifica el ID del dispositivo (proporcionado por el servicio de gestión WWAN) del módem a emparejar. Esto se puede encontrar usando mmcli.

•
network-id (escalar) – desde 0.99

Especifica el ID de Red (formato GSM LAI). Si se especifica, el dispositivo no recorrerá redes.

•
number (escalar) – desde 0.99

El número a marcar para establecer la conexión a la red de banda ancha móvil. (Obsoleto para GSM)

•
password (escalar) – desde 0.99

Especifica la contraseña utilizada para autenticarse en la red del operador. Esto se puede omitir si auto-config está habilitado.

•
pin (escalar) – desde 0.99

Especifica el PIN de la SIM para permitir su funcionamiento si se ha configurado un PIN.

•
sim-id (escalar) – desde 0.99

Especifica el identificador único de la SIM (proporcionado por el servicio de gestión WWAN) al que se aplica esta conexión. Si se proporciona, la conexión se aplicará a cualquier dispositivo también permitido por device-id que contenga una tarjeta SIM que coincida con el identificador dado.

•
sim-operator-id (escalar) – desde 0.99

Especifica la cadena MCC/MNC (como 310260 o 21601) que identifica al operador al que se debe aplicar esta conexión. Si se proporciona, la conexión se aplicará a cualquier dispositivo permitido también por device-id y sim-id que contenga una tarjeta SIM proporcionada por el operador dado.

•
username (escalar) – desde 0.99

Especifica el nombre de usuario utilizado para autenticarse en la red del operador. Esto se puede omitir si auto-config está habilitado.

Propiedades para el tipo de dispositivo wifis

Estado: Opcional.

Propósito: Utilice la clave wifis para configurar puntos de acceso Wi-Fi.

Estructura: La clave consiste en un mapeo de IDs de Wi-Fi. Cada wifi tiene una serie de opciones de configuración. La estructura general de configuración para Wi-Fi se muestra a continuación.

network:
  version: 2
  wifis:
    wlp0s1:
      access-points:
        "network_ssid_name":
          password: "**********"

Tenga en cuenta que systemd-networkd no tiene soporte nativo para Wi-Fi, por lo que necesita tener instalado wpasupplicant si deja que el renderizador networkd gestione el Wi-Fi.

•
access-points (mapeo)

Esto proporciona conexiones preconfiguradas a NetworkManager. Tenga en cuenta que los usuarios, por supuesto, pueden seleccionar otros puntos de acceso/SSID. Las claves del mapeo son los SSID y los valores son mapeos con las siguientes propiedades compatibles:

•
password (escalar
)

Habilita la autenticación WPA/WPA2 y establece la contraseña para ella. Si no se proporciona ni esto ni un bloque auth, se asume que la red está abierta. La configuración

password: "S3kr1t"

es equivalente a

auth:
  key-management: psk
  password: "S3kr1t"
•
mode (escalar)

Los modos posibles de punto de acceso son infrastructure (el valor predeterminado), ap (crear un punto de acceso al que otros dispositivos puedan conectarse) y adhoc (redes punto a punto sin un punto de acceso central). ap solo es compatible con NetworkManager.

•
bssid (escalar) – desde 0.99

Si se especifica, dirige al dispositivo a asociarse únicamente con el punto de acceso dado.

•
band (escalar) – desde 0.99

Las bandas posibles son 5GHz (para 802.11a de 5GHz) y 2.4GHz (para 802.11 de 2.4GHz), no restrinja la banda de frecuencia 802.11 de la red si no está configurada (el valor predeterminado).

•
channel (escalar) – desde 0.99

Canal inalámbrico a utilizar para la conexión Wi-Fi. Dado que los números de canal se solapan entre bandas, esta propiedad solo tiene efecto si la propiedad band también está configurada.

•
hidden (booleano) – desde 0.100

Establecer en true para cambiar la técnica de escaneo SSID para conectarse a redes Wi-Fi ocultas. Tenga en cuenta que esto puede tener un rendimiento más lento en comparación con false (el valor predeterminado) al conectarse a SSIDs transmitidos públicamente.

•
wakeonwlan (secuencia de escalares) – desde 0.99

Esto habilita WakeOnWLan en dispositivos compatibles. No todos los controladores admiten todas las opciones. Puede ser cualquier combinación de any, disconnect, magic_pkt, gtk_rekey_failure, eap_identity_req, four_way_handshake, rfkill_release o tcp (solo NetworkManager). O la bandera exclusiva default (el valor predeterminado).

•
regulatory-domain (escalar) – desde 0.105

Esto se puede usar para definir el dominio regulatorio de la radio, para utilizar canales Wi-Fi adicionales fuera del "dominio mundial". Toma un código de país ISO/IEC 3166 (como GB) o 00 para restablecer al "dominio mundial". Consulte wireless-regdb para ver los valores disponibles.

Requiere dependencia: iw, si se va a utilizar fuera del backend de networkd (wpasupplicant).

Propiedades para el tipo de dispositivo bridges

Estado: Opcional.

Propósito: Utilice la clave bridges para crear interfaces de Bridge.

Estructura: La clave consiste en un mapeo de nombres de interfaz de Bridge. Cada bridge tiene una lista opcional de interfaces que se interconectarán. Las interfaces listadas en la clave interfaces (enp5s0 y enp5s1 a continuación) también deben definirse en su configuración de Netplan. La estructura general de configuración para Bridges se muestra a continuación.

network:
  bridges:
    br0:
      interfaces:
        - enp5s0
        - enp5s1
      dhcp4: true
      ...

Cuando se aplique, se creará una interfaz virtual de tipo bridge llamada br0 en el sistema.

La configuración específica para los bridges se define a continuación.

•
interfaces (secuencia de escalares)

Todos los dispositivos que coincidan con esta lista de ID se añadirán al bridge. Esta puede ser una lista vacía, en cuyo caso el bridge se pondrá en línea sin interfaces miembro.

Ejemplo:

network:
  ethernets:
    switchports:
      match: {name: "enp2*"}
  [...]
  bridges:
    br0:
      interfaces: [switchports]
•
parameters (mapeo)

Parámetros de personalización para opciones especiales de bridging. Los intervalos de tiempo pueden necesitar expresarse como un número de segundos o milisegundos: el tipo de valor predeterminado se especifica a continuación. Si es necesario, los intervalos de tiempo se pueden calificar utilizando un sufijo de tiempo (como s para segundos, ms para milisegundos) para permitir un mayor control sobre su comportamiento.

•
ageing-time, aging-time (escalar)

Establece el período de tiempo para mantener una dirección MAC en la base de datos de reenvío después de recibir un paquete. Esto se corresponde con la propiedad AgeingTimeSec= cuando se utiliza el renderizador networkd. Si no se especifica ningún sufijo de tiempo, el valor se interpretará como segundos.

•
priority (escalar)

Establece el valor de prioridad para el bridge. Este valor debe ser un número entre 0 y 65535. Valores más bajos significan mayor prioridad. El bridge con mayor prioridad será elegido como el bridge raíz.

•
port-priority (mapeo)

Establece la prioridad del puerto por interfaz. El valor de prioridad es un número entre 0 y 63. Esta métrica se utiliza en los algoritmos de selección de puertos designados y puertos raíz.

Ejemplo:

network:
  ethernets:
    eth0:
      dhcp4: false
    eth1:
      dhcp4: false
  bridges:
    br0:
      interfaces: [eth0, eth1]
      parameters:
        port-priority:
          eth0: 10
          eth1: 20
•
forward-delay (escalar)

Especifica el período de tiempo que el bridge permanecerá en los estados de Escucha y Aprendizaje antes de pasar al estado de Reenvío. Este campo se corresponde con la propiedad ForwardDelaySec= para el renderizador networkd. Si no se especifica ningún sufijo de tiempo, el valor se interpretará como segundos.

•
hello-time (escalar)

Especifica el intervalo entre dos paquetes de saludo que se envían desde los bridges raíz y designados. Los paquetes de saludo comunican información sobre la topología de la red. Cuando se utiliza el renderizador networkd, esto se corresponde con la propiedad HelloTimeSec=. Si no se especifica ningún sufijo de tiempo, el valor se interpretará como segundos.

•
max-age (escalar)

Establece la edad máxima de un paquete de saludo. Si el último paquete de saludo tiene una antigüedad superior a este valor, el bridge intentará convertirse en el bridge raíz. Esto se corresponde con la propiedad MaxAgeSec= cuando se utiliza el renderizador networkd. Si no se especifica ningún sufijo de tiempo, el valor se interpretará como segundos.

•
path-cost (mapeo)

Establece el costo por interfaz de una ruta en el bridge. Las interfaces más rápidas deben tener un costo menor. Esto permite un control más fino sobre la topología de la red para que las rutas más rápidas estén disponibles siempre que sea posible.

Ejemplo:

network:
  ethernets:
    eth0:
      dhcp4: false
    eth1:
      dhcp4: false
  bridges:
    br0:
      interfaces: [eth0, eth1]
      parameters:
        path-cost:
          eth0: 100
          eth1: 200
•
stp (booleano)

Define si el bridge debe utilizar el Protocolo de Árbol de Expansión. El valor predeterminado es true, lo que significa que se debe utilizar el Árbol de Expansión.

Propiedades para el tipo de dispositivo dummy-devices

BONDING

(yaml-bond)= ## Properties for device type bond

Status: Optional.

Purpose: Use the bond key to create bonding devices.

Structure: The key consists of a mapping of bond interface names. Each bond requires the identification of the bonding mode (see the section mode below for the list of supported modes). The general configuration structure for Bonds is shown below.

network:
  bonds:
    bond0:
      mode: SCALAR
      ...

When applied, a virtual interface called bond0 will be created in the system. Its operation mode is defined by the property mode.

Bonding allows multiple network interfaces to be combined into a single logical interface. This can be used to increase throughput, provide redundancy, or both. See Link_aggregation for more general information about bonding.

The specific settings for bonds are defined below.

•
mode (scalar)

Defines the bonding mode. Valid options are balance-rr, active-backup, balance-xor, broadcast, balance-tlb, balance-alb, group-policy, 802.3ad, 802.1ax.

The balance-rr mode provides sequential starting packet transmission round robin to all slaves. This mode provides load balancing and fault tolerance.

The active-backup mode provides fault tolerance. Only one slave is active at a time, while the others are passive, waiting to take over in case of failure.

The balance-xor mode transmits packets with the cyclical redundancy check (CRC) generated packet, and uses this value to select the slave which will transmit the packet. This mode provides load balancing and fault tolerance.

The broadcast mode transmits packets via all slaves. This mode only provides fault tolerance.

The balance-tlb mode computes the transmit load balancing based on the current load of the slave. The egress network traffic is distributed according to the load of the interface. This mode provides load balancing and fault tolerance.

The balance-alb mode is the same as balance-tlb, but with the addition of receiving traffic load balancing based on perceived, but not necessarily accurate, current load of the slave. This mode provides load balancing and fault tolerance.

The 802.3ad and 802.1ax modes are for IEEE 802.3ad aggregate type. This mode provides load balancing and fault tolerance and requires switch support for Link Aggregation Control Protocol (LACP).

•
mii-monitor-interval (scalar)

Set the MII link monitoring interval in milliseconds. A value of 0 disables MII link monitoring.

•
packets-per-slave (scalar)

Set the maximum number of packets that will be transmitted per slave device. This option is only used with the balance-rr mode.

•
primary-reselect-policy (scalar)

Set the reselection policy for the primary port. On failure of the active port, the system will use this policy to decide how the new active port will be chosen and how recovery will be handled. The possible values are always, better and failure.

•
resend-igmp (scalar)

In modes balance-rr, active-backup, balance-tlb and balance-alb, a failover can switch IGMP traffic from one port to another.

This parameter specifies how many IGMP membership reports are issued on a failover event. Values range from 0 to 255. 0 disables sending membership reports. Otherwise, the first membership report is sent on failover and subsequent reports are sent at 200ms intervals.

•
learn-packet-interval (scalar)

Specify the interval between sending learning packets to each port. The value range is between 1 and 0x7fffffff. The default value is 1. This option only affects balance-tlb and balance-alb modes. Using the networkd renderer, this field maps to the LearnPacketIntervalSec= property. If no time suffix is specified, the value will be interpreted as seconds.

•
primary (scalar)

Specify a device to be used as a primary port, or preferred device to use as a port for the bond (i.e. the preferred device to send data through), whenever it is available. This only affects active-backup, balance-alb and balance-tlb modes.

(yaml-tunnels)= ## Properties for device type tunnels

Status: Optional.

Purpose: Use the tunnels key to create virtual tunnel interfaces.

Structure: The key consists of a mapping of tunnel interface names. Each tunnel requires the identification of the tunnel mode (see the section mode below for the list of supported modes). The general configuration structure for Tunnels is shown below.

Tunnels allow traffic to pass as if it was between systems on the same local network, although systems may be far from each other but reachable via the Internet. They may be used to support IPv6 traffic on a network where the ISP does not provide the service, or to extend and "connect" separate local networks. See Tunneling_protocol for more general information about tunnels.

The specific settings for tunnels are defined below.

•
mode (scalar)

Defines the tunnel mode. Valid options are sit, gre, ip6gre, ipip, ipip6, ip6ip6, vti, vti6, wireguard, vxlan, gretap and ip6gretap modes. In addition, the NetworkManager back end supports isatap tunnels.

•
local (scalar)

Defines the address of the local endpoint of the tunnel. (For VXLAN) This should match one of the parent's IP addresses or make use of the networkd special values.

•
remote (scalar)

Defines the address of the remote endpoint of the tunnel or multicast group IP address for VXLAN.

•
ttl (scalar) – since 0.103

Defines the Time To Live (TTL) of the tunnel. Takes a number in the range 1..255.

•
key (scalar or mapping)

Define keys to use for the tunnel. The key can be a number or a dotted quad (an IPv4 address). For wireguard it can be a base64-encoded private key or (as of networkd v242+) an absolute path to a file, containing the private key (since 0.100). It is used for identification of IP transforms. This is only required for vti and vti6 when using the networkd back end.

This field may be used as a scalar (meaning that a single key is specified and to be used for input, output and private key), or as a mapping, where you can further specify input/output/private.

•
input (scalar)

The input key for the tunnel

•
output (scalar)

The output key for the tunnel

•
private (scalar) – since 0.100

A base64-encoded private key required for WireGuard tunnels. When the systemd-networkd back end (v242+) is used, this can also be an absolute path to a file containing the private key.

Private key flags used by NetworkManager. Possible values are: agent-owned, not-saved and not-required.

agent-owned: a user-session secret agent is responsible for providing and storing this secret.

not-saved: this secret should not be saved but should be requested from the user each time it is required.

not-required: this flag hints that the secret is not required and should not be requested from the user.

      link: eno1
      addresses: [...]

Properties for device type vrfs

Status: Optional.

Purpose: Use the vrfs key to create Virtual Routing and Forwarding (VRF) interfaces.

Structure: The key consists of a mapping of VRF interface names. The interface used in the link option (enp5s0 in the example below) must also be defined in the Netplan configuration. The general configuration structure for VRFs is shown below.

network:
  renderer: networkd
  vrfs:
    vrf1:
      table: 1
      interfaces:
        - enp5s0
      routes:
        - to: default
          via: 10.10.10.4
      routing-policy:
        - from: 10.10.10.42
•
table (scalar) – since 0.105

The numeric routing table identifier. This setting is compulsory.

•
interfaces (sequence of scalars) – since 0.105

All devices matching this ID list will be added to the VRF. This may be an empty list, in which case the VRF will be brought online with no member interfaces.

•
routes (sequence of mappings) – since 0.105

Configure static routing for the device; see the Routing section. The table value is implicitly set to the VRF table.

•
routing-policy (sequence of mappings) – since 0.105

Configure policy routing for the device; see the Routing section. The table value is implicitly set to the VRF table.

Example:

network:
  vrfs:
    vrf20:
      table: 20
      interfaces: [ br0 ]
      routes:
        - to: default
          via: 10.10.10.3
      routing-policy:
        - from: 10.10.10.42
    [...]
  bridges:
    br0:
      interfaces: []

Properties for device type nm-devices

Status: Optional. Its use is not recommended.

Purpose: Use the nm-devices key to configure device types that are not supported by Netplan. This is NetworkManager specific configuration.

Structure: The key consists of a mapping of NetworkManager connections. The nm-devices device type is for internal use only and should not be used in normal configuration files. It enables a fallback mode for unsupported settings, using the passthrough mapping. The general configuration structure for NM connections is shown below.

network:
  version: 2
  nm-devices:
    NM-db5f0f67-1f4c-4d59-8ab8-3d278389cf87:
      renderer: NetworkManager
      networkmanager:
        uuid: "db5f0f67-1f4c-4d59-8ab8-3d278389cf87"
        name: "myvpnconnection"
        passthrough:
          connection.type: "vpn"
          vpn.ca: "path to ca.crt"
          vpn.cert: "path to client.crt"
          vpn.cipher: "AES-256-GCM"
          vpn.connection-type: "tls"
          vpn.dev: "tun"
          vpn.key: "path to client.key"
          vpn.remote: "1.2.3.4:1194"
          vpn.service-type: "org.freedesktop.NetworkManager.openvpn"

Back end-specific configuration parameters

In addition to the other fields available to configure interfaces, some back ends may require to record some of their own parameters in Netplan, especially if the Netplan definitions are generated automatically by the consumer of that back end. Currently, this is only used with NetworkManager.

•
networkmanager (mapping) – since 0.99

Keeps the NetworkManager-specific configuration parameters used by the daemon to recognise connections.

•
name (scalar) – since 0.99

Set the display name for the connection.

•
uuid (scalar) – since 0.99

Defines the UUID (unique identifier) for this connection, as generated by NetworkManager itself.

•
stable-id (scalar) – since 0.99

Defines the stable ID (a different form of a connection name) used by NetworkManager in case the name of the connection might otherwise change, such as when sharing connections between users.

•
device (scalar) – since 0.99

Defines the interface name for which this connection applies.

•
passthrough (mapping) – since 0.102

Can be used as a fallback mechanism to missing key-file settings.
