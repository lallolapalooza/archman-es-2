NOMBRE

neon - biblioteca cliente HTTP y WebDAV

DESCRIPCIÓN

neon es una biblioteca cliente HTTP y WebDAV. Las principales abstracciones expuestas son la sesión HTTP, creada por ne_session_create; y la solicitud HTTP, creada por ne_request_create. La autenticación HTTP se maneja de forma transparente para los servidores y proxies, consulte ne_set_server_auth; también se incluye soporte SSL/TLS completo, consulte ne_ssl_set_verify.

CONVENCIONES

Se utilizan algunas convenciones en toda la API de neon, para proporcionar una interfaz consistente y simple; estas se documentan a continuación.

Seguridad de hilos e inicialización global

La propia neon está implementada para ser segura en hilos (evitando cualquier uso de estado global), pero depende de que el sistema operativo proporcione una interfaz de resolución segura en hilos. Los sistemas operativos modernos ofrecen la interfaz segura en hilos getaddrinfo, que neon soporta; otros implementan gethostbyname utilizando almacenamiento local de hilos.

Para permitir el uso seguro de SSL en los hilos de las bibliotecas OpenSSL y GnuTLS, neon debe configurarse con --enable-threadsafe-ssl; si esto se hace, se registrarán callbacks de bloqueo mediante ne_sock_init; tenga en cuenta que se debe tener cuidado si neon se utiliza junto con otra biblioteca que utilice OpenSSL o GnuTLS.

Algunas plataformas y bibliotecas utilizadas por neon requieren inicialización global antes de su uso; en particular:

•La disposición de la señal SIGPIPE debe establecerse en ignorar o manejarse de otra manera para evitar la terminación del proceso al escribir en un socket que ha sido cerrado por el par.
•OpenSSL y GnuTLS requieren inicialización global para cargar tablas de búsqueda compartidas.
•La biblioteca de sockets Win32 requiere inicialización antes de su uso.

La función ne_sock_init debe llamarse antes de cualquier otro uso de neon para realizar cualquier inicialización necesaria para la plataforma en particular. Las aplicaciones que deseen realizar todos los pasos de inicialización necesarios a nivel de proceso global pueden omitir la llamada a ne_sock_init (y ne_sock_exit); neon no comprueba si estas funciones se llaman ni las llama.

Para algunas aplicaciones y configuraciones, puede ser necesario llamar a ne_i18n_init para inicializar el soporte de internacionalización en neon.

Seguridad asíncrona de señales

Ninguna función en neon está definida como “segura para señales asíncronas”, es decir, ninguna función es segura para ser llamada desde un manejador de señales. Cualquier llamada a la biblioteca neon desde un manejador de señales tendrá un comportamiento indefinido; en otras palabras, puede bloquear el proceso.

Funciones que utilizan estado global

Cualquier función en neon puede modificar la variable global errno como efecto secundario. Excepto donde se documenta explícitamente, el valor de errno no se especifica después de cualquier llamada a una función de neon.

Aparte del uso de errno, las únicas funciones que utilizan o modifican el estado global del proceso en neon son las siguientes:

•ne_sock_init, ne_i18n_init y ne_sock_exit, como se describe anteriormente
•ne_debug_init y ne_debug, si están habilitados en tiempo de compilación; para la salida de depuración
•ne_oom_callback para instalar un callback global del proceso que se invocará en caso de fallo de malloc

Espacios de nombres

Para evitar posibles colisiones entre nombres utilizados para símbolos y macros preprocesador por una aplicación y las bibliotecas que utiliza, es una buena práctica que cada biblioteca reserve un prefijo de espacio de nombres particular. Una aplicación que se asegure de no utilizar ningún nombre con estos prefijos evitará así dichas colisiones.

La biblioteca neon reserva el uso de los prefijos de espacio de nombres ne_ y NE_. Las bibliotecas utilizadas por neon también pueden reservar ciertos espacios de nombres; las colisiones entre estas bibliotecas y una aplicación basada en neon no se detectarán en tiempo de compilación, ya que las interfaces de biblioteca subyacentes no se exponen a través de los archivos de cabecera de neon. Dichas colisiones solo se pueden detectar en tiempo de enlace, cuando el enlazador intenta resolver símbolos. La siguiente lista documenta algunos de los espacios de nombres reclamados por las bibliotecas utilizadas por neon; esta lista puede estar incompleta.

SSL, ssl, TLS, tls, ERR_, BIO_, d2i_, i2d_, ASN1_

Algunos de los muchos prefijos utilizados por la biblioteca OpenSSL; se ha hecho poco intento de mantener los símbolos exportados dentro de prefijos particulares para esta biblioteca.

gnutls_, gcry_, gpg_

Espacios de nombres utilizados por la biblioteca GnuTLS (y sus dependencias)

XML_, Xml[A-Z]

Espacios de nombres utilizados por la biblioteca expat.

xml[A-Z], html[A-Z], docb[A-Z]

Espacios de nombres utilizados por la biblioteca libxml2; se utiliza un número relativamente pequeño de símbolos sin estos prefijos.

inflate, deflate, crc32, compress, uncompress, adler32, zlib

Espacios de nombres utilizados por la biblioteca zlib; se utiliza un número relativamente pequeño de símbolos sin estos prefijos.

krb5, gss, GSS, asn1, decode_krb5, encode_krb5, profile, mit

Algunos de los prefijos utilizados por la biblioteca MIT GSSAPI y sus dependencias; un número de símbolos se encuentran fuera de estos prefijos.

pakchois_

Espacio de nombres utilizado por la biblioteca pakchois.

px_

Espacio de nombres utilizado por la biblioteca libproxy.

Validación de argumentos

Neon no intenta validar que los parámetros pasados a las funciones se ajustan a la API (por ejemplo, comprobando que los argumentos de puntero no sean NULL). Se dice que cualquier uso de la API de neon que no se documente que produzca un comportamiento específico produce comportamiento indefinido; es probable que neon produzca un segfault en estas condiciones.

Rutas de URI, metadatos WebDAV

Las cadenas de ruta pasadas a cualquier función deben ser codificadas en URI por la aplicación; neon nunca realiza ninguna codificación o decodificación de URI internamente. Los nombres y valores de propiedades WebDAV deben ser cadenas Unicode codificadas en UTF-8 válidas.

Interacción del usuario

Como interfaz de biblioteca pura, neon nunca producirá salida en stdout o stderr; toda la interacción del usuario es responsabilidad de la aplicación.

Manejo de memoria

Neon no intenta lidiar con gracia con una situación de falta de memoria; en su lugar, por defecto, se llama a la función abort para terminar inmediatamente el proceso. Una aplicación puede registrar una función personalizada que se llamará antes de abort en tal situación; consulte ne_oom_callback.

Callbacks y userdata

Cada vez que se registra un callback, también se utiliza un puntero userdata para permitir a la aplicación asociar un contexto con el callback. El userdata es de tipo void *, lo que permite usar cualquier puntero.

Soporte para archivos grandes

Desde la versión 0.27.0, neon utiliza de forma transparente las interfaces "LFS transicional" en las funciones que utilizan descriptores de archivo. Esto permite el uso de archivos mayores de 2GiB en plataformas con un tipo off_t nativo de 32 bits, donde el soporte LFS está disponible.

Algunas interfaces de neon utilizan el tipo ne_off_t, que se define como off_t u off64_t según si se detecta el soporte LFS en el momento de la compilación. Neon no utiliza ni requiere la definición de macro -D_FILE_OFFSET_BITS=64.

NAME

neon

DESCRIPTION

neon is a small, object-oriented client-side HTTP library. It is designed to provide a flexible and efficient way to interact with HTTP services. The library offers support for various HTTP methods, authentication mechanisms, and content encoding. neon can be used to build applications that require robust HTTP client capabilities, such as web crawlers, API clients, and synchronization tools.
