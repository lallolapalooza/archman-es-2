NOMBRE

ppmtompeg - codificar un flujo de bits MPEG-1

SINOPSIS

ppmtompeg [opciones] archivo-de-parámetros

DESCRIPCIÓN

Este programa es parte de Netpbm(1)

ppmtompeg produce un flujo de video MPEG-1. MPEG-1 es el primer gran método de compresión de video, y es lo que se usa en Video CDs (VCD). ppmtompeg se originó en el año 1995. DVD usa un método más avanzado, MPEG-2. Existe un método aún más nuevo llamado MPEG-4 que también se llama Divx. No sé dónde se usa.

Técnicamente existe una diferencia entre un método de compresión de video y un formato de archivo (flujo) real para una película, y no sé si se puede decir válidamente que el formato del flujo que ppmtompeg produce es MPEG-1.

Mencoder del paquete Mplayer es probablemente superior para la mayoría de las necesidades de generación de formatos de video, si no fuera por otra razón que su mayor popularidad.

La biblioteca de programación PM2V genera flujos MPEG-2.

Utilice Mplayer (no es parte de Netpbm) para realizar la conversión inversa: crear una serie de archivos PNM a partir de un flujo MPEG.

archivo_parametros es un archivo de parámetros que incluye una lista de archivos de entrada y otros parámetros. El archivo se describe en detalle a continuación.

Para comprender este programa, necesita entender algo sobre el complejo formato MPEG-1. Una fuente de información sobre este formato estándar es la sección Introducción a MPEG en el FAQ de Compresión.

OPCIONES

Las opciones -gop, -combine_gops, -frames y -combine_frames son mutuamente excluyentes.

-stat archivo_estadisticas
Esta opción hace que ppmtompeg añada las estadísticas que escribe en la Salida Estándar al archivo archivo_estadisticas también. Las estadísticas usan las siguientes abreviaturas: bits por bloque (bpb), bits por fotograma (bpf), segundos por fotograma (spf) y bits por segundo (bps).

Estas estadísticas incluyen cuántos fotogramas I, P y B hubo, e información sobre compresión y calidad.

-quiet segundos

hace que ppmtompeg no informe el tiempo restante con más frecuencia que cada segundos segundos (a menos que el tiempo estimado aumente, lo que ocurrirá cerca del inicio de la ejecución). Un valor negativo le indica a ppmtompeg que no informe en absoluto. 0 es el valor por defecto (informa una vez después de cada fotograma). Tenga en cuenta que el tiempo restante es una estimación y no tiene en cuenta el tiempo de lectura de los fotogramas.
-realquiet

hace que ppmtompeg se ejecute en silencio, y que la única salida en pantalla sean los errores. Particularmente útil cuando se lee la entrada desde stdin.
-no_frame_summary

Esta opción evita que ppmtompeg imprima una línea de resumen para cada fotograma.
-float_dct

obliga a ppmtompeg a usar una versión más precisa, aunque computacionalmente más costosa, de la DCT.
-gop num_gop
hace que ppmtompeg codifique solo el GOP numerado (el primer GOP es 0). El archivo de parámetros es el mismo que para el uso normal. El archivo de salida será el archivo de salida normal con el sufijo .gop.num_gop. ppmtompeg no genera información de secuencia.
-combine_gops

hace que ppmtompeg simplemente combine algunos archivos GOP en un único flujo de salida MPEG. ppmtompeg inserta una cabecera y un remolque de secuencia. En este caso, el archivo de parámetros solo necesita contener el valor SIZE, un archivo de salida y, quizás, una lista de archivos GOP de entrada (ver abajo).

Si no proporciona una lista de archivos GOP de entrada, entonces ppmtompeg asume que está utilizando el mismo archivo de parámetros que utilizó cuando creó la entrada (con la opción -gop) y calcula él mismo los nombres de archivo GOP correspondientes. Si no es así, puede especificar los archivos GOP de entrada de la misma manera que los archivos de entrada normales: en lugar de usar INPUT_DIR, INPUT y END_INPUT, utilice GOP_INPUT_DIR, GOP_INPUT y GOP_END_INPUT. Si no se especifican archivos GOP de entrada, el valor predeterminado es usar el nombre del archivo de salida con el sufijo .gop.num_gop, donde num_gop comienza desde 0, como archivos de entrada.

Por lo tanto, a menos que esté mezclando y combinando archivos GOP de diferentes fuentes, puede simplemente usar el mismo archivo de parámetros tanto para crear los archivos GOP (-gop) como para convertirlos posteriormente en un flujo MPEG (-combine_gops).

-frames primer_fotograma ultimo_fotograma
Esta opción hace que ppmtompeg codifique solo los fotogramas numerados desde primer_fotograma hasta ultimo_fotograma, inclusive. El archivo de parámetros es el mismo que para el uso normal. La salida se colocará en archivos separados, uno por fotograma, con los nombres de archivo siendo el nombre del archivo de salida normal con el sufijo .frame.num_fotograma. No se genera información de cabecera GOP. (Por lo tanto, el archivo de parámetros no necesita incluir el valor GOP_SIZE).

Utilice ppmtompeg -combine_frames para combinar estos fotogramas posteriormente en un flujo MPEG.

-combine_frames

Esta opción hace que ppmtompeg simplemente combine algunos fotogramas MPEG individuales (tales como los que podría haber creado con una ejecución anterior de ppmtompeg -frames) en un único flujo MPEG. Se insertan cabeceras de secuencia y GOP apropiadamente. En este caso, el archivo de parámetros solo necesita contener los valores SIZE, GOP_SIZE, un archivo de salida y, quizás, una lista de archivos de fotogramas (ver abajo).

El archivo de parámetros puede especificar archivos de fotogramas de entrada de la misma manera que los archivos de entrada normales: en lugar de usar INPUT_DIR, INPUT y END_INPUT, utilice FRAME_INPUT_DIR, FRAME_INPUT y FRAME_END_INPUT. Si no se especifican archivos de fotogramas de entrada, el valor predeterminado es usar el nombre del archivo de salida con el sufijo .frame.num_fotograma, donde num_fotograma comienza desde 0, como archivos de entrada.

-nice
Esta opción hace que ppmtompeg ejecute cualquier proceso remoto "amablemente", es decir, a baja prioridad. (Esto solo es relevante si está ejecutando ppmtompeg en modo paralelo. De lo contrario, no hay procesos remotos). Véase 'man nice'.
-max_machines num_maquinas
Esta opción hace que ppmtompeg no utilice más de num_maquinas máquinas como esclavas para su uso en codificación paralela.
-snr
Esta opción hace que ppmtompeg incluya la relación señal-ruido en las estadísticas reportadas. Imprime SNR (Y U V) y SNR pico (Y U V) para cada fotograma. En resumen, imprime promedios solo de luminancia (Y). El SNR se define como 10*log(varianza de original/varianza de error). El SNR pico se define como 20*log(255/RMSE). Tenga en cuenta que ppmtompeg se ejecuta un poco más lento cuando utiliza esta opción.
-mse
Esta opción hace que ppmtompeg informe el error cuadrático medio por bloque. También informa automáticamente la calidad de las imágenes, por lo que no es necesario especificar -snr.
-bit_rate_info archivo_tasa

Esta opción hace que ppmtompeg escriba información de tasa de bits en el archivo archivo_tasa. La información de tasa de bits son bits por fotograma, y también bits por fotograma de I a fotograma de I.
-mv_histogram

Esta opción hace que ppmtompeg imprima un histograma de los vectores de movimiento como

La salida tiene la forma de una matriz, cada entrada corresponde a un vector de movimiento en la ventana de búsqueda. El centro de la matriz representa vectores de movimiento (0,0).

-debug_sockets
Esta opción hace que ppmtompeg imprima en la salida estándar mensajes que narran la comunicación entre las máquinas cuando ejecuta ppmtompeg en modo paralelo .
-debug_machines
Esta opción hace que ppmtompeg imprima en la salida estándar mensajes que narran el progreso de la conversión en las diversas máquinas cuando ejecuta ppmtompeg en modo paralelo .

ARCHIVO DE PARÁMETROS

El archivo de parámetros debe contener las siguientes líneas (excepto cuando se utilizan las opciones -combine_gops o -combine_frames):

PATTERN patrón
Esta declaración especifica el patrón (secuencia) de fotogramas I, P y B. patrón es solo una secuencia de las letras I, P y B sin nada entre ellas. Ejemplo: 
    PATTERN IBBPBBPBBPBBPBB

Ver Fotogramas I, Fotogramas P, Fotogramas B .

OUTPUT archivo de salida
Este nombre de archivo donde va la secuencia MPEG de salida.
INPUT_DIR directorio
Esta declaración indica de dónde provienen las imágenes de entrada (fotogramas). Si cada fotograma está en un archivo separado, directorio es el directorio donde se encuentran todos. Puede usar . para referirse al directorio actual. Un directorio nulo se refiere al directorio raíz del árbol de archivos del sistema.

Para que ppmtompeg lea todos los fotogramas en serie desde la entrada estándar, especifique

    INPUT_DIR stdin
INPUT
Esta línea debe ir seguida de una lista de los archivos de entrada (en orden de visualización) y luego la línea END_INPUT.

Hay tres tipos de líneas entre INPUT y END_INPUT. Primero, una línea puede ser simplemente el nombre de un archivo de entrada. Segundo, la línea puede tener la forma expresión_estrella_simple [x-y]. expresión_estrella_simple puede tener una sola *. Se reemplaza por todos los números entre x e y inclusive. Por lo tanto, por ejemplo, la línea tennis*.ppm [12-15] se refiere a los archivos tennis12.ppm, tennis13.ppm, tennis14.ppm, tennis15.ppm.

También se produce relleno de ceros uniforme. Por ejemplo, la línea football.*.ppm [001-130] se refiere a los archivos football.001.ppm, football.002.ppm, ..., football.009.ppm, football.010.ppm, ..., football.130.ppm.

El tercer tipo de línea es: expresión_estrella_simple [x-y+s], donde la línea se trata exactamente como se describió anteriormente, excepto que saltamos por s. Por lo tanto, la línea football.*.ppm [001-130+4] se refiere a los archivos football.001.ppm, football.005.ppm, football.009.ppm, football.013.ppm, etc.

Además, una línea puede especificar un comando shell para ejecutar y generar líneas que se interpretarán como se describe anteriormente, como si esas líneas estuvieran en el archivo de parámetros en su lugar. Use comillas invertidas, como en el Bourne Shell, de esta manera:

    `cat myfilelist`

Si la entrada proviene de la entrada estándar (según la declaración INPUT_DIR), ppmtompeg ignora el bloque INPUT/END_INPUT, pero aún debe estar presente.

BASE_FILE_FORMAT {PPM | PNM | YUV |

JPEG | JMOVIE} ppmtompeg debe convertir todos los archivos de entrada a uno de los siguientes formatos como primer paso del procesamiento: PNM, YUV, JPEG(v4) o JMOVIE. (La conversión puede ser trivial si sus archivos de entrada ya están en uno de estos formatos). Esta línea especifica cuál de los cuatro formatos. PPM es en realidad un subconjunto de PNM. La especificación separada está permitida para compatibilidad con versiones anteriores. Utilice PNM en lugar de PPM en aplicaciones nuevas.
INPUT_CONVERT comando_conversión
Debe especificar cómo convertir un archivo al formato base. Si no se necesita ninguna conversión, simplemente diría: 
     INPUT_CONVERT *

De lo contrario, comando_conversión es un comando shell que provoca que se escriba una imagen en el formato especificado con BASE_FILE_FORMAT en la salida estándar. ppmtompeg ejecuta el comando una vez por cada línea entre INPUT y END_INPUT (que normalmente, pero no necesariamente, es un nombre de archivo). En el comando de conversión, ppmtompeg reemplaza cada '*' con el contenido de esa línea.


Si tuviera un montón de archivos gif, podría decir:

     INPUT_CONVERT giftopnm *


Si tiene un montón de archivos a.Y, a.U y a.V separados (donde
U y V ya han sido submuestreados), entonces podría decir:

     INPUT_CONVERT cat *.Y *.U *.V

La conversión de entrada no está permitida con entrada desde stdin, así que use

     INPUT_CONVERT *

como se describe anteriormente.

SIZE anchoxalto

ancho y alto son el ancho y el alto de cada fotograma en píxeles.

Cuando ppmtompeg puede obtener esta información de los archivos de imagen de entrada, ignora el parámetro SIZE y puede omitirlo.

Cuando los archivos de imagen están en formato YUV, los archivos no contienen información de dimensiones, por lo que SIZE es obligatorio.

Cuando ppmtompeg se ejecuta en modo paralelo, no todos los procesos de la red tienen acceso a los archivos de imagen, por lo que SIZE es obligatorio y debe proporcionar las mismas dimensiones que los archivos de imagen de entrada.

YUV_SIZE anchoxalto
Este es un sinónimo obsoleto de SIZE.
YUV_FORMAT {ABEKAS | PHILLIPS | UCB |

EYUV | patrón} Esto solo es significativo cuando BASE_FILE_FORMAT especifica el formato YUV, y en ese caso es obligatorio. Especifica el subformato de la clase YUV.
GOP_SIZE n
n es el número de fotogramas en un Grupo de Imágenes. Excepto que, dado que un GOP debe comenzar con un fotograma I, ppmtompeg hace que un GOP sea tanto más largo que n como sea necesario para que el siguiente GOP comience con un fotograma I.

Normalmente, tiene sentido hacer que el tamaño de su GOP sea un múltiplo de la longitud de su patrón (este último determinado por la declaración del archivo de patrón PATTERN).

Ver Grupo de Imágenes .

SLICES_PER_FRAME n
n es aproximadamente el número de rebanadas por fotograma. Tenga en cuenta que al menos un reproductor MPEG puede quejarse si las rebanadas no comienzan en el borde izquierdo de una imagen. Para asegurarse de que esto no suceda, asegúrese de que el número de filas sea divisible por SLICES_PER_FRAME.
PIXEL {FULL | HALF}
usa vectores de movimiento de medio píxel, o solo de píxel completo. Por lo general, es importante usar vectores de movimiento de medio píxel, ya que resulta en una mejor calidad y una mejor compresión.
RANGE n
Use un rango de búsqueda de n píxeles en cada una de las cuatro direcciones desde un píxel sujeto. (Por lo tanto, la ventana de búsqueda es un cuadrado de n*2 píxeles de lado).
PSEARCH_ALG {EXHAUSTIVE | TWOLEVEL |

SUBSAMPLE | LOGARITHMIC} Esta declaración le dice ppmtompeg qué tipo de técnica
(algoritmo) de búsqueda utilizar para los fotogramas P. Usted selecciona la combinación deseada
de velocidad y compresión. EXHAUSTIVE proporciona la
mejor compresión, pero LOGARITHMIC es la más rápida.
TWOLEVEL es una búsqueda exhaustiva de píxel completo, seguida de una
búsqueda local de medio píxel alrededor del mejor vector de píxel completo (la
opción PIXEL se ignora para esta técnica de búsqueda).
BSEARCH_ALG {SIMPLE | CROSS2 | EXHAUSTIVE}
Esta declaración le dice a ppmtompeg qué tipo de técnica
(algoritmo) de búsqueda utilizar para los fotogramas B. SIMPLE significa
encontrar los mejores vectores hacia adelante y hacia atrás, luego interpolar.
CROSS2 significa encontrar esos dos vectores, luego ver qué vector hacia atrás
coincide mejor con el mejor vector hacia adelante, y viceversa.
EXHAUSTIVE realiza una búsqueda n-cuadrado y es
*extremadamente* lenta en relación con las otras (CROSS2
es aproximadamente la mitad de rápida que SIMPLE).
IQSCALE n
Use n como qscale para los fotogramas I.
Ver Qscale .
PQSCALE n
Use n como qscale para los fotogramas P.
Ver Qscale .
BQSCALE n
Use n como qscale para los fotogramas B.
Ver Qscale .
REFERENCE_FRAME {ORIGINAL | DECODED}
Esta declaración determina si ppmtompeg utiliza las imágenes originales o las imágenes decodificadas al calcular los vectores de movimiento. Usar imágenes decodificadas es más preciso y debería aumentar la calidad de reproducción de la salida, pero hace que la codificación lleve más tiempo y parece gi peor compresión. También causa algunas complicaciones con la codificación en paralelo. (ver la sección sobre codificación en paralelo). Una cosa que puedes hacer como contrapartida es seleccionar ORIGINAL aquí, y bajar la qscale (ver QSCALE si la calidad no es lo suficientemente buena.

Las siguientes líneas son opcionales:

FORCE_ENCODE_LAST_FRAME
Esta declaración está obsoleta. No hace nada.

Antes de Netpbm 10.26 (enero de 2005), ppmtompeg descartaba los fotogramas B finales de tu película, ya que una película no puede terminar con un fotograma B. (Ver Fotogramas I, Fotogramas P, Fotogramas B. Tenías que especificar FORCE_ENCODE_LAST_FRAME para evitar que eso sucediera y obtener la misma función que ppmtompeg tiene hoy.

NIQTABLE
Esta declaración especifica una tabla de cuantización no intra personalizada. Si no especificas esta declaración, ppmtompeg usa una tabla de cuantización no intra por defecto.

Las 8 líneas inmediatamente posteriores a NIQTABLE especifican la tabla de cuantización. Cada línea define una fila de la tabla y consta de 8 enteros, separados por espacios en blanco, que definen las columnas de la tabla.

IQTABLE
Esto es análogo a NIQTABLE, pero para la tabla de cuantización intra.
ASPECT_RATIO ratio
Esta declaración especifica la relación de aspecto para que ppmtompeg la especifique en la salida MPEG. No estoy seguro de para qué se utiliza esto.

ratio debe ser 1.0, 0.6735, 0.7031, 0.7615, 0.8055, 0.8437, 0.8935, 0.9157, 0.9815, 1.0255, 1.0695, 1.0950, 1.1575 o 1.2015.

FRAME_RATE rate
Esto especifica la tasa de fotogramas para que ppmtompeg la especifique en la salida MPEG. Algunos reproductores utilizan este valor para determinar la velocidad de reproducción.

rate debe ser 23.976, 24, 25, 29.97, 30, 50, 59.94 o 60.

BIT_RATE rate
Esto especifica la tasa de bits para la codificación de Tasa de Bits Constante (CBR).

rate debe ser un entero.

BUFFER_SIZE size
Esto especifica el valor que ppmtompeg debe especificar en la salida MPEG para el tamaño del búfer del Verificador de Búfer de Vídeo (VBV) necesario para decodificar la secuencia.

Un Búfer de Verificación de Vídeo es un búfer en el que un decodificador mantiene los bits decodificados para igualar la velocidad irregular de la decodificación con la velocidad de reproducción constante requerida.

Mientras ppmtompeg codifica la imagen, simula el proceso de decodificación en términos de cuántos bits habría en el VBV a medida que se decodifica cada fotograma, asumiendo un VBV del tamaño que indiques.

Si especificas la declaración WARN_VBV_UNDERFLOW, ppmtompeg emite una advertencia cada vez que la simulación produce un subdesbordamiento del búfer, lo que sugiere que ocurriría un subdesbordamiento en la reproducción, lo que sugiere que el búfer es demasiado pequeño.

Si especificas la declaración WARN_VBV_OVERFLOW, ppmtompeg emite una advertencia cada vez que la simulación produce un desbordamiento del búfer, lo que sugiere que ocurriría un desbordamiento en la reproducción, lo que sugiere que el búfer es demasiado pequeño.

WARN_VBV_UNDERFLOW
WARN_VBV_OVERFLOW
Ver BUFFER_SIZE.

Estas opciones son nuevas en Netpbm 10.26 (enero de 2005). Antes de eso, ppmtompeg emitía las advertencias siempre.

Las siguientes declaraciones se aplican solo a la operación en paralelo:

PARALLEL
Esta declaración, emparejada con END PARALLEL, es lo que hace que ppmtompeg opere en modo paralelo. Ver Operación en Paralelo .
END PARALLEL
Esto va con PARALLEL.
PARALLEL_TEST_FRAMES n
El maestro comienza midiendo la velocidad de cada esclavo. Lo hace dando a cada esclavo n fotogramas para codificar y anotando cuánto tiempo tarda el esclavo en terminar. Estos no son solo fotogramas de prueba, sino fotogramas reales y los resultados se convierten en parte de la salida. ppmtompeg es antiguo y mide el tiempo en segundos indivisos, por lo que para obtener tiempos útiles, especifica suficientes fotogramas para que tarde al menos 5 segundos en procesarlos. El valor por defecto es 10.

Si especificas FORCE_I_ALIGN, ppmtompeg aumentará el valor de fotogramas de prueba lo suficiente como para mantener la alineación.

Si no hay suficientes fotogramas para que cada esclavo tenga el número indicado de fotogramas de prueba, ppmtompeg dará a algunos esclavos menos.

PARALLEL_TIME_CHUNKS t
Cuando especificas esta declaración, el maestro intenta alimentar trabajo a los esclavos en trozos que tardan t segundos en procesarse. Utiliza la medición de velocidad que hizo al iniciarse (ver PARALLEL_TEST_FRAMES) para decidir cuántos fotogramas incluir en el trozo. Esta declaración obviamente no afecta al primer lote de trabajo enviado a cada esclavo, que es el que se utiliza para medir la velocidad del esclavo.

Valores más pequeños de t aumentan la comunicación, pero mejoran el equilibrio de carga. El valor por defecto es 30 segundos.

Puedes especificar solo una de PARALLEL_TIME_CHUNKS, PARALLEL_CHUNK_TAPER y PARALLEL_PERFECT. PARALLEL_CHUNK_TAPER suele ser la mejor.

PARALLEL_CHUNK_TAPER
Cuando especificas esta declaración, el maestro distribuye el trabajo como con PARALLEL_TIME_CHUNKS, excepto que el maestro elige el número de segundos para los trozos. Comienza con un número grande y, a medida que se acerca a terminar el trabajo, lo reduce. De esta manera, reduce la sobrecarga de planificación cuando la planificación precisa no es útil, pero aún así evita que un esclavo termine temprano después de que todo el trabajo ya ha sido distribuido a los otros esclavos, y luego permanezca inactivo mientras todavía hay trabajo por hacer.

Puedes especificar solo una de PARALLEL_TIME_CHUNKS, PARALLEL_CHUNK_TAPER y PARALLEL_PERFECT. PARALLEL_CHUNK_TAPER suele ser la mejor.

PARALLEL_PERFECT
Si esta declaración está presente, ppmtompeg planifica asumiendo que cada máquina tiene aproximadamente la misma velocidad. El maestro simplemente dividirá los fotogramas de manera uniforme entre los esclavos: cada esclavo recibe el mismo número de fotogramas. Si algunos esclavos son más rápidos que otros, terminarán primero y permanecerán inactivos mientras los esclavos más lentos continúan.

Esto tiene la ventaja de una sobrecarga mínima de planificación. Donde los esclavos tienen diferentes velocidades, sin embargo, hace un uso ineficiente de los rápidos. Donde los esclavos son de la misma velocidad, también tiene la desventaja de que todos terminan al mismo tiempo y envían su salida al servidor Combine único en una ráfaga, lo que hace un uso menos eficiente del servidor Combine y, por lo tanto, puede aumentar el tiempo total transcurrido.

Puedes especificar solo una de PARALLEL_TIME_CHUNKS, PARALLEL_CHUNK_TAPER y PARALLEL_PERFECT. PARALLEL_CHUNK_TAPER suele ser la mejor.

RSH remote_shell_command
ppmtompeg ejecuta el comando de shell remote_shell_command para iniciar un proceso en otra máquina. El comando por defecto es rsh, y cualquier comando que especifiques debe tener semántica compatible. ssh suele ser compatible. El comando que utiliza ppmtompeg es algo como: ssh remote.host.com -l username shellcommand.

Asegúrate de configurar archivos .rhosts o autorizaciones de clave SSH donde sea necesario. De lo contrario, tendrás que escribir contraseñas.

En algunas máquinas HP, rsh es el shell restringido, y quieres especificar remsh.

FORCE_I_ALIGN
Esta declaración fuerza a cada esclavo a codificar un trozo de fotogramas que es múltiplo de la longitud del patrón (ver PATTERN). Dado que el primer fotograma de cualquier patrón es un fotograma I, esto fuerza a que cada trozo codificado por un esclavo comience con un fotograma I.

Este documento solía decir que había un argumento para FORCE_I_ALIGN que era el número de fotogramas que ppmtompeg utilizaría (y que debía ser múltiplo de la longitud del patrón). Pero ppmtompeg aparentemente siempre ignoró ese argumento, y lo hace ahora.

KEEP_TEMP_FILES
Esta declaración hace que ppmtompeg no elimine los archivos temporales que utiliza para transmitir los fotogramas codificados al servidor combinador. Esto significa que te quedarás con un archivo por cada fotograma, igual que obtendrías con la opción -frames.

Esto es principalmente útil para la depuración.

Esto solo funciona si estás utilizando un sistema de archivos compartido para comunicarte entre los servidores.

Esta opción es nueva en Netpbm 10.26 (enero de 2005).

Parámetros

Notas del Archivo de Parámetros


Si usa la opción -combine_gops, entonces solo necesita especificar los valores SIZE y OUTPUT en el archivo de parámetros. Además, el archivo de parámetros puede especificar archivos GOP de entrada de la misma manera que los archivos de entrada normales, excepto que en lugar de usar INPUT_DIR, INPUT y END_INPUT, use GOP_INPUT_DIR, GOP_INPUT y GOP_END_INPUT. Si no especifica ningún archivo GOP de entrada, entonces ppmtompeg usa por defecto el nombre del archivo de salida con el sufijo .gop.gop_num, donde gop_num comienza desde 0, como archivos de entrada.

Si usa la opción -combine_frames, entonces solo necesita especificar los valores SIZE, GOP_SIZE y OUTPUT en el archivo de parámetros. Además, el archivo de parámetros puede especificar archivos de fotogramas de entrada de la misma manera que los archivos de entrada normales, excepto que en lugar de usar INPUT_DIR, INPUT y END_INPUT, use FRAME_INPUT_DIR, FRAME_INPUT y FRAME_END_INPUT. Si no se especifican archivos de fotogramas de entrada, entonces el valor predeterminado es usar el nombre del archivo de salida con el sufijo .frame.frame_num, donde frame_num comienza desde 0, como archivos de entrada.

Se puede usar cualquier cantidad de espacios y tabulaciones entre cada opción y valor. Las líneas que comienzan con # se ignoran. Cualquier otra línea se ignora excepto las que están entre INPUT y END_INPUT. Esto le permite usar el mismo archivo de parámetros para el uso normal y para -combine_gops y -combine_frames.

El formato del archivo distingue entre mayúsculas y minúsculas, por lo que todas las palabras clave deben estar en mayúsculas.

Las declaraciones pueden aparecer en cualquier orden, excepto que el orden dentro de una declaración de bloque (como INPUT ... END INPUT) es significativo.

ppmtompeg está preparado para manejar hasta 16 fotogramas B entre fotogramas de referencia al codificar con entrada desde stdin. (Para construir un ppmtompeg modificado con un límite mayor, cambie la constante B_FRAME_RUN en frame.c y recompílelo).

INFORMACIÓN GENERAL DE USO

Qscale

Los valores de escala de cuantificación (qscale) ofrecen un equilibrio entre calidad y compresión. El uso de diferentes valores de Qscale tiene muy poco efecto en la velocidad. Los valores de qscale se pueden establecer por separado para los fotogramas I, P y B.

Selecciona los valores de qscale con las declaraciones del archivo de parámetros IQSCALE, PQSCALE y BSCALE.

Un valor de qscale es un entero entre 1 y 31. Los números más grandes ofrecen una mejor compresión, pero una peor calidad. En lo siguiente, los números de calidad son la relación señal-ruido pico, definida como: fórmula de relación señal-ruido, donde MSE es el error cuadrático medio.

Técnicas de Búsqueda

Hay varias técnicas diferentes de búsqueda de vectores de movimiento disponibles. Hay diferentes técnicas disponibles para la búsqueda de fotogramas P y la búsqueda de fotogramas B. El uso de diferentes técnicas de búsqueda presenta poca diferencia en la calidad, pero una gran diferencia en la compresión y la velocidad.

Hay 4 tipos de búsqueda de fotogramas P: Exhaustiva, DosNiveles, MuestraDeSubconjunto y Logarítmica.

Hay 3 tipos de búsqueda de fotogramas B: Exhaustiva, Cruz2 y Simple.

Las técnicas de búsqueda recomendadas son DosNiveles y Logarítmica para la búsqueda de fotogramas P, y Cruz2 y Simple para la búsqueda de fotogramas B. Aquí hay algunos números que comparan los diferentes métodos de búsqueda:

Búsqueda de Vectores de Movimiento de Fotogramas P (Normalizada)

Técnica Compresión #smallbetter 1 Velocidad #largefaster 2 Calidad #largebetter 3
Exhaustiva 1000 1000 1000
MuestraDeSubconjunto 1008 2456 1000
DosNiveles 1009 3237 1000
Logarítmica 1085 8229 998

Búsqueda de Vectores de Movimiento de Fotogramas B (Normalizada)

Técnica Compresión #smallbetter 1 Velocidad #largefaster 2 Calidad #largebetter 3
Exhaustiva 1000 1000 1000
Cruz2 975 1000 996
Simple 938 1765 991

1Los números más pequeños son mejor compresión.

2Los números más grandes significan una ejecución más rápida.

3Los números más grandes significan mejor calidad.

Por alguna razón, Simple parece ofrecer una mejor compresión, pero depende de la secuencia de imágenes.

Selecciona las técnicas de búsqueda con las declaraciones del archivo de parámetros PSEARCH_ALG y BSEARCH_ALG.

Grupo de Imágenes (GOP)

Un Grupo de Imágenes (GOP) es una secuencia de fotogramas aproximadamente decodificable de forma independiente. Una transmisión de video MPEG se compone de uno o más GOP. Puede especificar cuántos fotogramas debe haber en cada GOP con la declaración del archivo de parámetros GOP_SIZE. Un GOP siempre comienza con un fotograma I.

En lugar de codificar una secuencia completa, puede codificar un solo GOP. Para hacerlo, use la opción de comando -gop. Posteriormente, puede unir los archivos GOP resultantes en cualquier momento ejecutando ppmtompeg con la opción de comando -combine_gops.

Segmentos

Un segmento es una unidad decodificable de forma independiente en un fotograma. Puede ser tan pequeño como un macrobloque, o tan grande como todo el fotograma. Salvo error de transmisión, añadir segmentos no cambia la calidad ni la velocidad; el único efecto es una compresión ligeramente peor. Se utilizan más segmentos para transmisiones ruidosas para que los errores sean más recuperables. Dado que los errores no suelen ser un problema, generalmente usamos un segmento por fotograma.

Controle el tamaño del segmento con la declaración del archivo de parámetros SLICES_PER_FRAME.

Algunos sistemas de reproducción de MPEG requieren que cada segmento consista en filas completas de macrobloques. Si está codificando para este tipo de reproductor, si la altura de la imagen es H píxeles, entonces debe establecer SLICES_PER_FRAME a un número que divida H/16. Por ejemplo, si la imagen tiene 240 píxeles (15 macrobloques) de alto, entonces solo debe usar 15, 5, 3 o 1 segmentos por fotograma.

Nota: estos sistemas de reproducción de MPEG están realmente equivocados, ya que el estándar MPEG dice que esto no tiene por qué ser así.

NAME

ppmtompeg - create an MPEG-1 stream from PPM images

SYNOPSIS

ppmtompeg [parameter-file]

DESCRIPTION

This program creates an MPEG-1 stream from a sequence of PPM images. You can also feed it JPEG or YUV files.

This program is part of the netpbm package.

The program uses a parameter file to control most of its functions. See Parameter File Statements below.

Motion Vector Search

ppmtompeg searches for motion vectors. The window is a square. You can specify the size of the square, and whether to allow half-pixel motion vectors or not, with the RANGE and PIXEL parameter file statements.

I Frames, P Frames, B Frames

In MPEG-1, a movie is represented as a sequence of MPEG frames, each of which is an I Frame, a P Frame, or a B Frame. Each represents an actual frame of the movie (don't get confused by the dual use of the word "frame." A movie frame is a graphical image. An MPEG frame is a set of data that describes a movie frame).

An I frame ("intra" frame) describes a movie frame in isolation -- without respect to any other frame in the movie. A P frame ("predictive" frame) describes a movie frame by describing how it differs from the movie frame described by the latest preceding I or P frame. A B frame ("bidirectional" frame) describes a movie frame by describing how it differs from the movie frames described by the nearest I or P frame before and after it.

Note that the first frame of a movie must be described by an I frame (because there is no previous movie frame) and the last movie frame must be described by an I or P frame (because there is no subsequent movie frame).

Beyond that, you can choose which frames are represented by which types. You specify a pattern, such as IBPBP and ppmtompeg simply repeats it over and over throughout the movie. The pattern affects speed, quality, and stream size. Here is a chart which shows some of the trade-offs:

Comparison of I/P/B Frames (Normalized)

Frame Type Size Speed Quality
I frames 1000 1000 1000
P frames 409 609 969
B frames 72 260 919

(this is with constant qscale)

A standard sequence is IBBPBBPBBPBBPBB.

Select the sequence with the PATTERN parameter file statement.

Since the last MPEG frame cannot be a B frame (see above), if the pattern you specify indicates a B frame for the last movie frame of the movie, ppmtompeg makes it an I frame instead.

Before Netpbm 10.26 (January 2005), ppmtompeg instead drops the trailing B frames by default, and you need the FORCE_ENCODE_LAST_FRAME parameter file statement to make it do this.

The MPEG frames don't appear in the MPEG-1 stream in the same order that the corresponding movie frames appear in the movie -- the B frames come after the I and P frames on which they are based. For example, if the movie is 4 frames that you will represent with the pattern IBBP, the MPEG-1 stream will start with an I frame describing movie frame 0. The next frame in the MPEG-1 stream is a P frame describing movie frame 3. The last two frames in the MPEG-1 stream are B frames describing movie frames 1 and 2, respectively.

Specifying Input and Output Files

Specify the input frame images with the INPUT_DIR, INPUT, END_INPUT, BASE_FILE_FORMAT, SIZE, YUV_FORMAT and INPUT_CONVERT parameter file statements.

Specify the output file with the OUTPUT parameter file statement.

Statistics

ppmtompeg can generate a variety of statistics about the encoding. See the -stat, -snr, -mv_histogram, -quiet, -no_frame_summary, and -bit_rate_info options.

PARALLEL OPERATION

You can run ppmtompeg on multiple machines at once, encoding the same MPEG stream. When you do, the machines are used as shown in the following diagram. We call this 'parallel mode.'

ppmtompeg-par.gif

To do parallel processing, put the statement

    PARALLEL

in the parameter file, followed by a listing of the machines, one machine per line, then

    END_PARALLEL

Each of the machine lines must be in one of two forms. If the machine has filesystem access to the input files, then the line is:

machine user executable

The executable is normally ppmtompeg (you may need to give the complete path if you've built for different architectures). If the machine does not have filesystem access to the input files, the line is:

REMOTE machine user executable parameter file

The -max_machines command option limits the number of machines ppmtompeg will use. If you specify more machines in the parameter file than -max_machines allows, ppmtompeg uses only the machines listed first. This is handy if you want to experiment with different amounts of parallelism.

In general, you should use full path file names when describing executables and parameter files. This includes the parameter file argument on the original invocation of ppmtompeg.

All file names must be the same on all systems (so if e.g. you're using an NFS filesystem, you must make sure it is mounted at the same mountpoint on all systems).

Because not all of the processes involved in parallel operation have easy access to the input files, you must specify the SIZE parameter file statement when you do parallel operation.

The machine on which you originally invoke ppmtompeg is the master machine. It hosts a 'combine server,', a 'decode server,' and a number of 'i/o servers,' all as separate processes. The other machines in the network (listed in the parameter file) are slave machines. Each hosts a single process that continuously requests work from the master and does it. The slave process does the computation to encode MPEG frames. It processes frames in batches identified by the master.

The master uses a remote shell command to start a process on a slave machine. By default, it uses an rsh shell command to do this. But use the RSH parameter file statement to control this. The shell command the master executes remotely is ppmtompeg, but with options to indicate that it is to perform slave functions.

The various machines talk to each other over TCP connections. Each machine finds and binds to a free TCP port number and tells its partners the port number. These port numbers are at least 2048.

Use the PARALLEL_TEST_FRAMES, PARALLEL_TIME_CHUNKS, and PARALLEL_PERFECT parameter file statements to control the way the master divides up work among the slaves.

Use the -nice command option to cause all slave processes to run "nicely," i.e. as low priority processes. That way, this substantial and long-running CPU load will have minimal impact on other, possibly interactive, users of the systems.

SPEED

Here is a look at ppmtompeg speed, in single-node (not parallel) operation:

Compression Speed

Machine Type Macroblocks per second1
HP 9000/755 280
DEC 3000/400 247
HP 9000/750 191
Sparc 10 104
DEC 5000 68
1A macroblock is a 16x16 pixel square

The measurements in the table are with inputs and outputs via a conventional locally attached filesystem. If you are using a network filesystem over a single 10 MB/s Ethernet, that constrains your speed more than your CPU speed. In that case, don't expect to get better than 4 or 5 frames per second no matter how fast your CPUs are.

Network speed is even more of a bottleneck when the slaves do not have filesystem access to the input files -- i.e. you declare them REMOTE.

Where I/O is the bottleneck, size of the input frames can make a big difference. So YUV input is better than PPM, and JPEG is better than both.

When you're first trying to get parallel mode working, be sure to use the -debug_machines option so you can see what's going on. Also, -debug_sockets can help you diagnose communication problems.
