Paquete: tcl

Licencias: TCL

pkg_mkIndex(n) Comandos integrados de Tcl pkg_mkIndex(n)

NOMBRE

pkg_mkIndex - Crear un índice para la carga automática de paquetes

SINOPSIS

pkg_mkIndex ?opciones...? dir ?patrón patrón ...?

DESCRIPCIÓN

Pkg_mkIndex es un procedimiento de utilidad que forma parte de la biblioteca estándar de Tcl. Se utiliza para crear archivos de índice que permiten cargar paquetes automáticamente cuando se ejecutan comandos package require. Para usar pkg_mkIndex, siga estos pasos:

[1]
Crear los paquetes. Cada paquete puede constar de uno o más archivos de script Tcl o archivos binarios. Los archivos binarios deben ser adecuados para cargarlos con el comando load con un único argumento; por ejemplo, si el archivo es test.so debe ser posible cargar este archivo con el comando load test.so. Cada archivo de script debe contener un comando package provide para declarar el paquete y el número de versión, y cada archivo binario debe contener una llamada a Tcl_PkgProvide.
[2]
Crear el índice invocando pkg_mkIndex. El argumento dir indica el nombre de un directorio y cada argumento patrón es un patrón estilo glob que selecciona archivos de script o binarios en dir. El patrón predeterminado es *.tcl y *.[info sharedlibextension].

Pkg_mkIndex creará un archivo pkgIndex.tcl en dir con información del paquete sobre todos los archivos dados por los argumentos patrón. Lo hace cargando cada archivo en un intérprete hijo y viendo qué paquetes y comandos nuevos aparecen (por eso es esencial tener comandos package provide o llamadas Tcl_PkgProvide en los archivos, como se describió anteriormente). Si tiene un paquete dividido entre scripts y archivos binarios, o si tiene dependencias entre archivos, puede que tenga que usar la opción -load o ajustar el orden en que pkg_mkIndex procesa los archivos. Consulte CASOS COMPLEJOS a continuación.

[3]
Instalar el paquete como un subdirectorio de uno de los directorios dados por la variable tcl_pkgPath. Si $tcl_pkgPath contiene más de un directorio, los paquetes dependientes de la máquina (por ejemplo, aquellos que contienen bibliotecas compartidas binarias) normalmente deben instalarse bajo el primer directorio y los paquetes independientes de la máquina (por ejemplo, aquellos que contienen solo scripts Tcl) deben instalarse bajo el segundo directorio. El subdirectorio debe incluir los archivos de script y/o binarios del paquete, así como el archivo pkgIndex.tcl. Siempre que el paquete se instale como un subdirectorio de un directorio en $tcl_pkgPath, será encontrado automáticamente durante los comandos package require.

Si instala el paquete en cualquier otro lugar, debe asegurarse de que el directorio que contiene el paquete esté en la variable global auto_path o en un subdirectorio inmediato de uno de los directorios en auto_path. Auto_path contiene una lista de directorios que son buscados por el cargador automático y el cargador de paquetes; por defecto incluye $tcl_pkgPath. El cargador de paquetes también verifica todos los subdirectorios de los directorios en auto_path. Puede añadir un directorio a auto_path explícitamente en su aplicación, o puede añadir el directorio a su variable de entorno TCLLIBPATH: si esta variable de entorno está presente, Tcl inicializa auto_path a partir de ella durante el inicio de la aplicación.

[4]
Una vez tomados los pasos anteriores, todo lo que necesita hacer para usar un paquete es invocar package require. Por ejemplo, si las versiones 2.1, 2.3 y 3.1 del paquete Test han sido indexadas por pkg_mkIndex, el comando package require Test hará que la versión 3.1 esté disponible y el comando package require -exact Test 2.1 hará que la versión 2.1 esté disponible. Puede haber muchas versiones de un paquete en los diversos archivos de índice en auto_path, pero solo una será cargada realmente en un intérprete dado, basándose en la primera llamada a package require. Diferentes versiones de un paquete pueden ser cargadas en diferentes intérpretes.

OPCIONES

Los modificadores opcionales son:

-directo
El índice generado implementará la carga directa del paquete al ejecutar package require. Este es el valor predeterminado.
-perezoso
El índice generado gestionará el retraso de la carga del paquete hasta el uso de uno de los comandos proporcionados por el paquete, en lugar de cargarlo inmediatamente tras la ejecución de package require. Esto no es compatible con el uso de auto_reset y, por lo tanto, su uso no se recomienda.
-cargar pkgPat
El proceso de indexación precargará cualquier paquete que exista en el intérprete actual y coincida con pkgPat en el intérprete hijo utilizado para generar el índice. La coincidencia de patrones utiliza reglas de coincidencia de cadenas, pero sin distinguir mayúsculas y minúsculas. Consulte CASOS COMPLEJOS a continuación.
-verboso
Genera salida durante el proceso de indexación. La salida se realiza a través del procedimiento tclLog, que por defecto imprime en stderr.
--
Fin de las banderas, en caso de que dir comience con un guión.

PAQUETES Y EL CARGADOR AUTOMÁTICO

Las facilidades de gestión de paquetes se solapan en parte con el cargador automático, ya que ambos organizan la carga de archivos bajo demanda. Sin embargo, la gestión de paquetes es un mecanismo de nivel superior que utiliza el cargador automático para el último paso del proceso de carga. Generalmente es mejor indexar un paquete con pkg_mkIndex en lugar de auto_mkindex porque el mecanismo de paquetes proporciona control de versiones: se pueden poner a disposición varias versiones de un paquete en los archivos de índice, y diferentes aplicaciones utilizan diferentes versiones basándose en los comandos package require. En contraste, auto_mkindex no entiende de versiones, por lo que solo puede manejar una única versión de cada paquete. Probablemente no sea una buena idea indexar un paquete dado tanto con pkg_mkIndex como con auto_mkindex. Si usa pkg_mkIndex para indexar un paquete, sus comandos no se pueden invocar hasta que se haya utilizado package require para seleccionar una versión; en contraste, los paquetes indexados con auto_mkindex se pueden usar inmediatamente ya que no hay control de versiones.

CÓMO FUNCIONA

Pkg_mkIndex depende del comando package unknown, del comando package ifneeded y del cargador automático. La primera vez que se invoca un comando package require, se invoca el script package unknown. Este script se establece mediante la inicialización de Tcl a un script que evalúa todos los archivos pkgIndex.tcl en el auto_path. Los archivos pkgIndex.tcl contienen comandos package ifneeded para cada versión de cada paquete disponible; estos comandos invocan comandos package provide para anunciar la disponibilidad del paquete y configuran información del cargador automático para cargar los archivos del paquete. Si se proporcionó el modificador -perezoso al generar el pkgIndex.tcl, un archivo dado de una versión dada de un paquete no se carga realmente hasta la primera vez que se invoca uno de sus comandos. Por lo tanto, después de invocar package require puede que no vea los comandos del paquete en el intérprete, pero podrá invocar los comandos y se cargarán automáticamente.

CARGA DIRECTA

Algunos paquetes, por ejemplo, paquetes que utilizan espacios de nombres y exportan comandos o aquellos que requieren inicialización especial, pueden optar por que sus archivos de paquete se carguen inmediatamente al ejecutar package require en lugar de retrasar la carga real hasta el primer uso de uno de los comandos del paquete. Este es el modo predeterminado al generar el índice del paquete. Se puede anular especificando el argumento -perezoso.

CASOS COMPLEJOS

La mayoría de los casos complejos de dependencias entre scripts y archivos binarios, y paquetes divididos entre scripts y archivos binarios se manejan correctamente. Sin embargo, puede que tenga que ajustar el orden en que los archivos son procesados por pkg_mkIndex. Estos problemas se describen en detalle a continuación.

pkgMkIndex(n)

NAME

pkg_mkIndex - create package index file

SYNOPSIS

pkg_mkIndex ?options? file ?file ...?

DESCRIPTION

The pkg_mkIndex command scans the specified Tcl script files, determines the packages they define, and creates an index file (typically named "pkgIndex.tcl") in the same directory. This index file is used by the Tcl auto-loader to load packages into an interpreter. The command also supports indexing of compiled Tcl/C extensions.

The generated index file contains Tcl commands that, when executed, will load the specified packages. The exact format of the index file depends on the version of Tcl being used, but it generally involves a series of commands like:

    package ifneeded package_name version {
        source /path/to/package.tcl
    }
or for binary extensions:

    package ifneeded package_name version {
        load /path/to/package.so
    }
The auto-loader uses these definitions to load packages on demand when a script calls package require.

OPTIONS

-ignore globPattern
Ignores files matching the glob pattern. Multiple -ignore options may be specified.
-load pkgPat
Loads packages matching the glob pattern pkgPat into the interpreter used by pkg_mkIndex to process the files. This is particularly useful when dealing with binary extensions that have dependencies on other packages. See the "COMPLEX CASES" section below.
-noCompat
By default, pkg_mkIndex tries to generate an index file that is compatible with older versions of Tcl. The -noCompat option disables this compatibility mode, potentially generating a more efficient index file for newer Tcl versions.

PACKAGES AND THE AUTO-LOADER

The Tcl auto-loader mechanism allows packages to be loaded dynamically when they are first needed. This is achieved by creating package index files that map package names and versions to the commands required to load them. The pkg_mkIndex command is the tool used to generate these index files.

A Tcl script typically defines a package using commands like package provide and package require. When pkg_mkIndex processes such a script, it records the provided package name and version. It also analyzes the script for dependencies on other packages, noted by package require commands.

HOW IT WORKS

pkg_mkIndex operates by creating a temporary Tcl interpreter. It then sources each of the specified input files into this interpreter. As each file is sourced, pkg_mkIndex monitors the interpreter for calls to package provide to identify the packages being defined. It also inspects package require commands to understand package dependencies.

For Tcl scripts, dependencies specified with package require are handled by stubbing out the package loading mechanism within the temporary interpreter. This prevents actual loading of dependent packages, which might not be available or could cause conflicts. Similarly, calls into other packages in global code are intercepted by a stub unknown command.

The primary challenge arises with binary extensions (shared libraries). When a binary extension requires another package, it often does so using a C-level API like Tcl_PkgRequire. It is not possible to stub out these low-level calls directly within the temporary interpreter in the same way as Tcl commands.

DIRECT LOADING

If your package is a single Tcl script or a single binary file, and it defines exactly one package, and that package is not contained within another package file, the process is straightforward. You simply list all the files to be indexed, possibly using glob patterns, in any order.

COMPLEX CASES

Dealing with dependencies, especially in binary files, requires careful handling.

When binary files have dependencies on other packages, it can be tricky because C-level APIs like Tcl_PkgRequire cannot be easily stubbed out. For example, if the BLT package depends on Tk, and its initialization routine (e.g., Blt_Init) calls Tcl_PkgRequire("Tk"), you must ensure Tk is available when pkg_mkIndex processes the BLT package. This is achieved using the -load pkgPat option. If specified, pkg_mkIndex loads any already loaded packages that match pkgPat into its temporary interpreter. This usually satisfies the Tcl_PkgRequire calls made by binary files.

If you are indexing two binary files where one depends on the other, list the dependent file last. This ensures the dependency is loaded first. You might need to use the -load flag to explicitly load the first package into the temporary interpreter. Specifying package patterns that are not yet loaded with -load will not cause errors.

If a package is split across Tcl scripts and a binary file, avoid the -load flag if possible. Loading a package before indexing can mask other files that are part of the same package. If you must use -load, specify the Tcl scripts first. Otherwise, the package loaded from the binary file might overshadow the package defined by the scripts.
