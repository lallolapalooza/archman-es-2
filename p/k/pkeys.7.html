NOMBRE

pkeys - resumen de las claves de protección de memoria

DESCRIPCIÓN

Las Claves de Protección de Memoria (pkeys) son una extensión de los permisos de memoria existentes basados en páginas. Los permisos de página normales que utilizan tablas de páginas requieren llamadas al sistema costosas e invalidaciones de TLB al cambiar permisos. Las Claves de Protección de Memoria proporcionan un mecanismo para cambiar las protecciones sin requerir la modificación de las tablas de páginas en cada cambio de permiso.

Para usar pkeys, el software primero debe "etiquetar" una página en las tablas de páginas con una pkey. Después de que esta etiqueta esté en su lugar, una aplicación solo tiene que cambiar el contenido de un registro para eliminar el acceso de escritura, o todo acceso a una página etiquetada.

Las claves de protección funcionan en conjunto con los permisos PROT_READ, PROT_WRITE y PROT_EXEC existentes pasados a llamadas al sistema como mprotect(2) y mmap(2), pero siempre actúan para restringir aún más estos mecanismos de permisos tradicionales.

Si un proceso realiza un acceso que viola las restricciones de pkey, recibe una señal SIGSEGV. Consulte sigaction(2) para obtener detalles sobre la información disponible con esa señal.

Para utilizar la función pkeys, el procesador debe ser compatible y el kernel debe contener soporte para la función en un procesador dado. A principios de 2016, solo los futuros procesadores Intel x86 son compatibles, y este hardware admite 16 claves de protección en cada proceso. Sin embargo, la pkey 0 se utiliza como clave predeterminada, por lo que un máximo de 15 están disponibles para el uso real de la aplicación. La clave predeterminada se asigna a cualquier región de memoria para la que no se haya asignado explícitamente una pkey a través de pkey_mprotect(2).

Las claves de protección tienen el potencial de agregar una capa de seguridad y confiabilidad a las aplicaciones. Pero no han sido diseñadas principalmente como una característica de seguridad. Por ejemplo, WRPKRU es una instrucción completamente no privilegiada, por lo que las pkeys son inútiles en cualquier caso en que un atacante controle el registro PKRU o pueda ejecutar instrucciones arbitrarias.

Las aplicaciones deben tener mucho cuidado para asegurarse de que no "filtren" claves de protección. Por ejemplo, antes de llamar a pkey_free(2), la aplicación debe asegurarse de que ninguna memoria tenga esa pkey asignada. Si la aplicación dejara la pkey liberada asignada, un usuario futuro de esa pkey podría inadvertidamente cambiar los permisos de una estructura de datos no relacionada, lo que podría afectar la seguridad o la estabilidad. El kernel actualmente permite que las pkeys en uso tengan pkey_free(2) llamadas sobre ellas porque tendría implicaciones de rendimiento del procesador o de memoria realizar las verificaciones adicionales necesarias para desautorizarlo. La implementación de las verificaciones necesarias queda a cargo de las aplicaciones. Las aplicaciones pueden implementar estas verificaciones buscando en el archivo /proc/pid/smaps regiones de memoria con la pkey asignada. Se pueden encontrar más detalles en proc(5).

Cualquier aplicación que quiera usar claves de protección necesita poder funcionar sin ellas. Podrían no estar disponibles porque el hardware en el que se ejecuta la aplicación no las admite, el código del kernel no contiene soporte, el soporte del kernel se ha deshabilitado, o porque todas las claves se han asignado, quizás por una biblioteca que la aplicación está utilizando. Se recomienda que las aplicaciones que deseen usar claves de protección simplemente llamen a pkey_alloc(2) y prueben si la llamada tiene éxito, en lugar de intentar detectar el soporte para la función de cualquier otra manera.

Aunque innecesario, el soporte de hardware para claves de protección puede enumerarse con la instrucción cpuid. Los detalles de cómo hacer esto se pueden encontrar en el Manual del Desarrollador de Software de Intel. El kernel realiza esta enumeración y expone la información en /proc/cpuinfo bajo el campo "flags". La cadena "pku" en este campo indica soporte de hardware para claves de protección y la cadena "ospke" indica que el kernel contiene y ha habilitado el soporte de claves de protección.

Las aplicaciones que utilizan hilos y claves de protección deben ser especialmente cuidadosas. Los hilos heredan los derechos de clave de protección del padre en el momento de la llamada al sistema clone(2). Las aplicaciones deben asegurarse de que sus propios permisos sean apropiados para los hilos hijos en el momento en que se llama a clone(2), o asegurarse de que cada hilo hijo pueda realizar su propia inicialización de los derechos de clave de protección.

Comportamiento del manejador de señales

Cada vez que se invoca un manejador de señales (incluidas señales anidadas), el hilo recibe temporalmente un nuevo conjunto predeterminado de derechos de clave de protección que anulan los derechos del contexto interrumpido. Esto significa que las aplicaciones deben restablecer sus derechos de clave de protección deseados al ingresar a un manejador de señales si los derechos deseados difieren de los predeterminados. Los derechos de cualquier contexto interrumpido se restauran cuando el manejador de señales regresa.

Este comportamiento de señal es inusual y se debe al hecho de que el registro PKRU de x86 (que almacena los derechos de acceso de la clave de protección) se administra con el mismo mecanismo de hardware (XSAVE) que administra los registros de punto flotante. El comportamiento de la señal es el mismo que el de los registros de punto flotante.

Llamadas al sistema de claves de protección

El kernel de Linux implementa las siguientes llamadas al sistema relacionadas con pkey: pkey_mprotect(2), pkey_alloc(2) y pkey_free(2).

Las llamadas al sistema pkey de Linux solo están disponibles si el kernel fue configurado y compilado con la opción CONFIG_X86_INTEL_MEMORY_PROTECTION_KEYS.

EJEMPLOS

El siguiente programa asigna una página de memoria con permisos de lectura y escritura. Luego escribe algunos datos en la memoria y los lee correctamente. Después de eso, intenta asignar una clave de protección y deshabilita el acceso a la página usando la instrucción WRPKRU. Luego intenta acceder a la página, lo que ahora se espera que cause una señal fatal a la aplicación.


$ ./a.out
buffer contains: 73
about to read buffer again...
Segmentation fault (core dumped)

Fuente del programa

#define _GNU_SOURCE
#include <err.h>
#include <unistd.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/mman.h>
int
main(void)
{
    int status;
    int pkey;
    int *buffer;
    /*
     * Asigna una página de memoria.
     */
    buffer = mmap(NULL, getpagesize(), PROT_READ | PROT_WRITE,
                  MAP_ANONYMOUS | MAP_PRIVATE, -1, 0);
    if (buffer == MAP_FAILED)
        err(EXIT_FAILURE, "mmap");
    /*
     * Pon algunos datos aleatorios en la página (todavía se puede acceder).
     */
    *buffer = __LINE__;
    printf("buffer contains: %d\n", *buffer);
    /*
     * Asigna una clave de protección:
     */
    pkey = pkey_alloc(0, 0);
    if (pkey == -1)
        err(EXIT_FAILURE, "pkey_alloc");
    /*
     * Deshabilita el acceso a cualquier memoria con "pkey" establecido,
     * aunque no haya ninguna en este momento.
     */
    status = pkey_set(pkey, PKEY_DISABLE_ACCESS);
    if (status)
        err(EXIT_FAILURE, "pkey_set");
    /*
     * Establece la clave de protección en "buffer".
     * Nota que sigue siendo de lectura/escritura en lo que respecta a mprotect()
     * y el anterior pkey_set() lo anula.
     */
    status = pkey_mprotect(buffer, getpagesize(),
                           PROT_READ | PROT_WRITE, pkey);
    if (status == -1)
        err(EXIT_FAILURE, "pkey_mprotect");
    printf("about to read buffer again...\n");
    /*
     * Esto fallará, porque hemos deshabilitado el acceso.
     */
    printf("buffer contains: %d\n", *buffer);
    status = pkey_free(pkey);
    if (status == -1)
        err(EXIT_FAILURE, "pkey_free");
    exit(EXIT_SUCCESS);
}
