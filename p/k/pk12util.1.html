PK12UTIL(1) Herramientas de Seguridad NSS PK12UTIL(1)

NOMBRE

pk12util - Exportar e importar claves y certificados a o desde un archivo PKCS #12 y la base de datos NSS

SINOPSIS

pk12util [-i archivoP12|-l archivoP12|-o archivoP12] [-c cifradoClave] [-C cifradoCertificado] [-d directorio] [-h nombreToken] [-m | --longitud-clave longitudClave] [-M algHash] [-n nombreCert] [-P prefijoDb] [-r] [-v] [--longitud-clave-cert longitudClaveCert] [-k archivoContraseñaRanura|-K contraseñaRanura] [-w archivoContraseñaArchivoP12|-W contraseñaArchivoP12]

ESTADO

Esta documentación todavía está en progreso. Por favor, contribuya a la revisión inicial en el bug 836477 de Mozilla NSS[1]

DESCRIPCION

La utilidad PKCS #12, pk12util, permite compartir certificados entre cualquier servidor que soporte PKCS #12. La herramienta puede importar certificados y claves desde archivos PKCS #12 a bases de datos de seguridad, exportar certificados y listar certificados y claves.

OPCIONES Y ARGUMENTOS

Opciones

-i archivoP12

Importa claves y certificados de un archivo PKCS #12 a una base de datos de seguridad.

-l archivoP12

Lista las claves y certificados en el archivo PKCS #12.

-o archivoP12

Exporta claves y certificados de la base de datos de seguridad a un archivo PKCS #12.

Argumentos

-c cifradoClave

Especifica el algoritmo de cifrado de clave.

-C cifradoCertificado

Especifica el algoritmo de cifrado de certificado.

-d directorio

Especifica el directorio de la base de datos al que importar o desde el que exportar certificados y claves.

pk12util soporta dos tipos de bases de datos: las bases de datos de seguridad heredadas (cert8.db, key3.db y secmod.db) y las nuevas bases de datos SQLite (cert9.db, key4.db y pkcs11.txt). Si no se usa el prefijo dbm:, la herramienta asume que las bases de datos dadas están en formato SQLite.

-h nombreToken

Especifica el nombre del token al que importar o desde el que exportar.

-k archivoContraseñaRanura

Especifica el archivo de texto que contiene la contraseña de la ranura.

-K contraseñaRanura

Especifica la contraseña de la ranura.

-m | --longitud-clave longitudClave

Especifica la longitud deseada de la clave simétrica que se utilizará para cifrar la clave privada.

-M algHash

Especifica el algoritmo hash utilizado en el MAC de pkcs #12. Este algoritmo también especifica el HMAC utilizado en el PRF al usar pkcs #5 v2.

--longitud-clave-cert longitudClaveCert

Especifica la longitud deseada de la clave simétrica que se utilizará para cifrar los certificados y otros metadatos.

-n nombreCert

Especifica el apodo (nickname) del certificado y clave privada a exportar.

El apodo también puede ser una URI PKCS #11. Por ejemplo, si tiene un certificado llamado "mi-cert-servidor" en el almacén de certificados interno, se puede especificar inequívocamente como "pkcs11:token=Base%20de%20datos%20de%20certificados%20NSS;object=mi-cert-servidor". Para más detalles sobre el formato, consulte RFC 7512.

-P prefijo

Especifica el prefijo utilizado en las bases de datos de certificados y claves. Esta opción se proporciona como un caso especial. No se recomienda cambiar los nombres de las bases de datos de certificados y claves.

-r

Descarga todos los datos en formato bruto (binario). Esto debe guardarse como un archivo DER. El valor predeterminado es devolver la información en un formato de texto plano legible, que muestra información sobre los certificados y claves públicas en el archivo p12.

-v

Habilita el registro de depuración al importar.

-w archivoContraseñaArchivoP12

Especifica el archivo de texto que contiene la contraseña del archivo PKCS #12.

-W contraseñaArchivoP12

Especifica la contraseña del archivo PKCS #12.

CÓDIGOS DE RETORNO

•0 - Sin error
•1 - Cancelado por el usuario
•2 - Error de uso
•6 - Error de inicialización NLS
•8 - Error al abrir la base de datos de certificados
•9 - Error al abrir la base de datos de claves
•10 - Error de inicialización del archivo
•11 - Error de conversión Unicode
•12 - Error de creación de archivo temporal
•13 - Error al obtener la ranura PKCS11
•14 - Error al iniciar el decodificador PKCS12
•15 - Error al leer del archivo de importación
•16 - Error de decodificación pkcs12
•17 - Error de verificación del decodificador pkcs12
•18 - Error de validación de bolsas del decodificador pkcs12
•19 - Error de importación de bolsas del decodificador pkcs12
•20 - Error de conversión de base de datos de claves versión 3 a versión 2
•21 - Error de conversión de base de datos de certificados versión 7 a versión 5
•22 - Error de parche de bases de datos de certificados y claves
•23 - Error al obtener la base de datos de certificados predeterminada
•24 - Error al encontrar certificado por apodo
•25 - Error al crear contexto de exportación
•26 - Error de integridad de contraseña de adición PKCS12
•27 - Error de creación de bolsas de certificados y claves PKCS12
•28 - Error al agregar certificado y clave PKCS12
•29 - Error de codificación PKCS12

EJEMPLOS

Importación de Claves y Certificados

El uso más básico de pk12util para importar un certificado o clave es el archivo de entrada PKCS #12 (-i) y alguna forma de especificar la base de datos de seguridad que se está accediendo (ya sea -d para un directorio o -h para un token).

pk12util -i archivoP12 [-h nombreToken] [-v] [-d directorio] [-P prefijoDb] [-k archivoContraseñaRanura|-K contraseñaRanura] [-w archivoContraseñaArchivoP12|-W contraseñaArchivoP12]

Por ejemplo:

# pk12util -i /tmp/cert-files/users.p12 -d /home/my/sharednssdb
Introduce una contraseña que se utilizará para cifrar tus claves.
La contraseña debe tener al menos 8 caracteres de longitud,
y debe contener al menos un carácter no alfabético.

Introduce la contraseña para el archivo PKCS12: 
pk12util: IMPORTACIÓN PKCS12 EXITOSA

Exportación de Claves y Certificados

El uso del comando pk12util para exportar certificados y claves requiere tanto el nombre del certificado a extraer de la base de datos (-n) como el archivo de salida con formato PKCS #12 a escribir. Hay parámetros opcionales que se pueden usar para cifrar el archivo y proteger el material del certificado.

pk12util -o archivoP12 -n nombreCert [-c cifradoClave] [-C cifradoCertificado] [-m|--longitud-clave longitudClave] [-n|--longitud-clave-cert longitudClaveCert] [-d directorio] [-P prefijoDb] [-k archivoContraseñaRanura|-K contraseñaRanura] [-w archivoContraseñaArchivoP12|-W contraseñaArchivoP12]

Por ejemplo:

# pk12util -o certs.p12 -n Server-Cert -d /home/my/sharednssdb

Vuelve a introducir la contraseña:

Listado de Claves y Certificados

La información en un archivo .p12 no es legible por humanos. Los certificados y claves en el archivo pueden ser impresos (listados) en un formato de texto plano legible que muestra información para cada certificado y cualquier clave pública en el archivo .p12.

pk12util -l archivoP12 [-h nombreToken] [-r] [-d directorio] [-P prefijoDb] [-k archivoContraseñaRanura|-K contraseñaRanura] [-w archivoContraseñaArchivoP12|-W contraseñaArchivoP12]

Por ejemplo, esto imprime la salida ASCII predeterminada:

pk12util(1) — Arch Linux man pages

NAME

pk12util — PKCS #12 import and export utility

SYNOPSIS

pk12util [options]

Options:

-i file
Import PKCS #12 file. Requires -d.
-o file
Export PKCS #12 file. Requires -d.
-l file
List contents of PKCS #12 file. Requires -d.
-e file
Export private key and certificate.
-c file
Import certificate file.
-a
Export in ASCII armor format.
-n name
Nickname of certificate. Defaults to Thawte Personal Freemail Member's Thawte Consulting (Pty) Ltd. ID.
-d dir
Directory containing NSS security databases. Defaults to $HOME/.netscape.
-r
Export certificates to separate DER binary files.
-C cipher
Specify cipher to use for certificate encryption. Use NONE for no encryption.
-P cipher
Specify cipher to use for private key encryption.
-F file
Write PKCS #12 file to file.
-v
Verbose mode.
-h
Display help message.

STATUS

This utility is part of the nss-tools package.

The pk12util command is a tool to import and export PKCS #12 files. PKCS #12 files are used to bundle a private key and its associated public key certificate into a single, password-protected file. This format is commonly used to transfer certificates and private keys between different applications and servers.

By default, pk12util operates on the NSS security database in the default directory (usually $HOME/.netscape). The database contains certificates and keys used by applications that utilize the NSS library.

OPTIONS AND ARGUMENTS

The options are:

-i file
Import the contents of the specified PKCS #12 file into the NSS database.
-o file
Export the contents of the NSS database to the specified PKCS #12 file.
-l file
List the contents (certificates and friendly names) of the specified PKCS #12 file. This operation does not require access to the NSS database.
-e file
Export the private key and associated certificate(s) from the NSS database to the specified file in PKCS #12 format. If the private key is protected by a password, you will be prompted to enter it.
-c file
Import a certificate from the specified file into the NSS database.
-a
When exporting a PKCS #12 file (using -o or -e), encode the output in ASCII Armor format. This is useful for transferring files via email or other text-based mediums.
-n name
Specify the nickname of the certificate to be exported (using -e) or the certificate to be imported (using -c). If not specified, a default nickname is used, which may vary depending on the context.
-d dir
Specify the directory containing the NSS security databases. This option is required for import (-i), export (-o), and list (-l) operations when operating on the NSS database. If not specified, the default directory ($HOME/.netscape) is used.
-r
When listing the contents of a PKCS #12 file (using -l), export each certificate found into a separate DER binary file. The files are named sequentially starting from file0001.der.
-C cipher
Specify the cipher algorithm to be used for encrypting certificates when exporting a PKCS #12 file. If set to "NONE", certificates will not be encrypted. See the PASSWORD ENCRYPTION section for available ciphers.
-P cipher
Specify the cipher algorithm to be used for encrypting the private key when exporting a PKCS #12 file. See the PASSWORD ENCRYPTION section for available ciphers.
-F file
Specify the output file name when exporting a PKCS #12 file using -o. If not specified, the output is written to standard output.
-v
Enable verbose output, providing more detailed information about the operations being performed.
-h
Display a help message outlining the available options and their usage.

RETURN CODES

The exit status of pk12util is 0 upon success, and non-zero upon failure.

EXAMPLES

To list the contents of a PKCS #12 file named test.p12:

pk12util -l test.p12
Enter password for PKCS12 file: 
Certificate    Friendly Name: Thawte Personal Freemail Issuing CA - Thawte Consulting
Certificate    Friendly Name: Thawte Freemail Member's Thawte Consulting (Pty) Ltd. ID
The following certificates are represented in the PKCS #12 file:

1.   ["Thawte Personal Freemail Issuing CA - Thawte Consulting"]
       ...
2.   ["Thawte Freemail Member's Thawte Consulting (Pty) Ltd. ID"]
       Alias: Thawte Freemail Member's Thawte Consulting (Pty) Ltd. ID
       Creation date: 1499881561
       Modification date: 1499881561
       -----BEGIN CERTIFICATE-----
       MIIDfzCCAmegAwIBAgIRALjOQ8G...
       -----END CERTIFICATE-----

The PKCS #12 file contains one or more certificates, and may contain a key.

Alternatively, the -r prints the certificates and then exports them into separate DER binary files. This allows the certificates to be fed to another application that supports .p12 files. Each certificate is written to a sequentially-number file, beginning with file0001.der and continuing through file000N.der, incrementing the number for every certificate:

pk12util -l test.p12 -r
Enter password for PKCS12 file: 
Key(shrouded):
    Friendly Name: Thawte Freemail Member's Thawte Consulting (Pty) Ltd. ID
    Encryption algorithm: PKCS #12 V2 PBE With SHA-1 And 3KEY Triple DES-CBC
        Parameters:
            Salt:
                45:2e:6a:a0:03:4d:7b:a1:63:3c:15:ea:67:37:62:1f
            Iteration Count: 1 (0x1)
Certificate    Friendly Name: Thawte Personal Freemail Issuing CA - Thawte Consulting
Certificate    Friendly Name: Thawte Freemail Member's Thawte Consulting (Pty) Ltd. ID

PASSWORD ENCRYPTION

PKCS #12 provides for not only the protection of the private keys but also the certificate and meta-data associated with the keys. Password-based encryption is used to protect private keys on export to a PKCS #12 file and, optionally, the associated certificates. If no algorithm is specified, the tool defaults to using PKCS #12 SHA-1 and 3-key triple DES for private key encryption. When not in FIPS mode, PKCS #12 SHA-1 and 40-bit RC4 is used for certificate encryption. When in FIPS mode, there is no certificate encryption. If certificate encryption is not wanted, specify "NONE" as the argument of the -C option.

The private key is always protected with strong encryption by default.

Several types of ciphers are supported.

PKCS #5 password-based encryption

•PBES2 with AES-CBC-Pad as underlying encryption scheme ("AES-128-CBC", "AES-192-CBC", and "AES-256-CBC")

PKCS #12 password-based encryption

•SHA-1 and 128-bit RC4 ("PKCS #12 V2 PBE With SHA-1 And 128 Bit RC4" or "RC4")
•SHA-1 and 40-bit RC4 ("PKCS #12 V2 PBE With SHA-1 And 40 Bit RC4") (used by default for certificate encryption in non-FIPS mode)
•SHA-1 and 3-key triple-DES ("PKCS #12 V2 PBE With SHA-1 And 3KEY Triple DES-CBC" or "DES-EDE3-CBC")
•SHA-1 and 128-bit RC2 ("PKCS #12 V2 PBE With SHA-1 And 128 Bit RC2 CBC" or "RC2-CBC")
•SHA-1 and 40-bit RC2 ("PKCS #12 V2 PBE With SHA-1 And 40 Bit RC2 CBC")

With PKCS #12, the crypto provider may be the soft token module or an external hardware module. If the cryptographic module does not support the requested algorithm, then the next best fit will be selected (usually the default). If no suitable replacement for the desired algorithm can be found, the tool returns the error no security module can perform the requested operation.

NSS DATABASE TYPES

NSS originally used BerkeleyDB databases to store security information. The last versions of these legacy databases are:

•cert8.db for certificates
•key3.db for keys
•secmod.db for PKCS #11 module information

BerkeleyDB has performance limitations, though, which prevent it from being easily used by multiple applications simultaneously. NSS has some flexibility that allows applications to use their own, independent database engine while keeping a shared database and working around the access issues. Still, NSS requires more flexibility to provide a truly shared security database.

In 2009, NSS introduced a new set of databases that are SQLite databases rather than BerkleyDB. These new databases provide more accessibility and performance:

•cert9.db for certificates
•key4.db for keys
•pkcs11.txt, which is listing of all of the PKCS #11 modules contained in a new subdirectory in the security databases directory

Because the SQLite databases are designed to be shared, these are the shared database type. The shared database type is preferred; the legacy format is included for backward compatibility.

By default, the tools (certutil, pk12util, modutil) assume that the given security databases use the SQLite type Using the legacy databases must be manually specified by using the dbm: prefix with the given security directory. For example:

# pk12util -i /tmp/cert-files/users.p12 -d dbm:/home/my/sharednssdb

To set the legacy database type as the default type for the tools, set the NSS_DEFAULT_DB_TYPE environment variable to dbm:

export NSS_DEFAULT_DB_TYPE="dbm"

This line can be set added to the ~/.bashrc file to make the change permanent.

•https://wiki.mozilla.org/NSS_Shared_DB_Howto

For an engineering draft on the changes in the shared NSS databases, see the NSS project wiki:

•https://wiki.mozilla.org/NSS_Shared_DB

COMPATIBILITY NOTES

The exporting behavior of pk12util has changed over time, while importing files exported with older versions of NSS is still supported.

Until the 3.30 release, pk12util used the UTF-16 encoding for the PKCS #5 password-based encryption schemes, while the recommendation is to encode passwords in UTF-8 if the used encryption scheme is defined outside of the PKCS #12 standard.

Until the 3.31 release, even when "AES-128-CBC" or "AES-192-CBC" is given from the command line, pk12util always used 256-bit AES as the underlying encryption scheme.

For historical reasons, pk12util accepts password-based encryption schemes not listed in this document. However, those schemes are not officially supported and may have issues in interoperability with other tools.
