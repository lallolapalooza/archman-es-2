pkg_mkIndex(n) Comandos integrados de Tcl pkg_mkIndex(n)

NOMBRE

pkg_mkIndex - Construye un índice para la carga automática de paquetes

SINOSIS

pkg_mkIndex ?opciones...? dir ?patrón patrón ...?

DESCRIPCIÓN

Pkg_mkIndex es un procedimiento de utilidad que forma parte de la biblioteca estándar de Tcl. Se utiliza para crear archivos de índice que permiten que los paquetes se carguen automáticamente cuando se ejecutan los comandos package require. Para usar pkg_mkIndex, sigue estos pasos:

[1]
Crea el(los) paquete(s). Cada paquete puede constar de uno o más archivos de script Tcl o archivos binarios. Los archivos binarios deben ser aptos para cargarse con el comando load con un solo argumento; por ejemplo, si el archivo es test.so, debe ser posible cargar este archivo con el comando load test.so. Cada archivo de script debe contener un comando package provide para declarar el paquete y su número de versión, y cada archivo binario debe contener una llamada a Tcl_PkgProvide.
[2]
Crea el índice invocando pkg_mkIndex. El argumento dir da el nombre de un directorio y cada argumento patrón es un patrón estilo glob que selecciona archivos de script o binarios en dir. El patrón predeterminado es *.tcl y *.[info sharedlibextension].

Pkg_mkIndex creará un archivo pkgIndex.tcl en dir con información de paquetes sobre todos los archivos dados por los argumentos patrón. Lo hace cargando cada archivo en un intérprete hijo y viendo qué paquetes y comandos nuevos aparecen (por eso es esencial tener comandos package provide o llamadas a Tcl_PkgProvide en los archivos, como se describió anteriormente). Si tienes un paquete dividido entre scripts y archivos binarios, o si tienes dependencias entre archivos, puede que tengas que usar la opción -load o ajustar el orden en que pkg_mkIndex procesa los archivos. Véase CASOS COMPLEJOS más abajo.

[3]
Instala el paquete como un subdirectorio de uno de los directorios dados por la variable tcl_pkgPath. Si $tcl_pkgPath contiene más de un directorio, los paquetes dependientes de la máquina (por ejemplo, aquellos que contienen bibliotecas compartidas binarias) normalmente deben instalarse en el primer directorio y los paquetes independientes de la máquina (por ejemplo, aquellos que solo contienen scripts Tcl) deben instalarse en el segundo directorio. El subdirectorio debe incluir el script y/o los archivos binarios del paquete, así como el archivo pkgIndex.tcl. Mientras el paquete esté instalado como un subdirectorio de un directorio en $tcl_pkgPath, será encontrado automáticamente durante los comandos package require.

Si instalas el paquete en cualquier otro lugar, debes asegurarte de que el directorio que contiene el paquete esté en la variable global auto_path o sea un subdirectorio inmediato de uno de los directorios en auto_path. Auto_path contiene una lista de directorios que son buscados tanto por el cargador automático como por el cargador de paquetes; por defecto incluye $tcl_pkgPath. El cargador de paquetes también revisa todos los subdirectorios de los directorios en auto_path. Puedes agregar un directorio a auto_path explícitamente en tu aplicación, o puedes agregar el directorio a tu variable de entorno TCLLIBPATH: si esta variable de entorno está presente, Tcl inicializa auto_path a partir de ella durante el inicio de la aplicación.

[4]
Una vez que se han tomado los pasos anteriores, todo lo que necesitas hacer para usar un paquete es invocar package require. Por ejemplo, si las versiones 2.1, 2.3 y 3.1 del paquete Test han sido indexadas por pkg_mkIndex, el comando package require Test hará que la versión 3.1 esté disponible y el comando package require -exact Test 2.1 hará que la versión 2.1 esté disponible. Puede haber muchas versiones de un paquete en los diversos archivos de índice en auto_path, pero solo una será cargada realmente en un intérprete dado, basándose en la primera llamada a package require. Diferentes versiones de un paquete pueden ser cargadas en diferentes intérpretes.

OPCIONES

Las opciones opcionales son:

-directo
El índice generado implementará la carga directa del paquete al ejecutar package require. Este es el comportamiento predeterminado.
-perezoso
El índice generado gestionará el retraso de la carga del paquete hasta el uso de uno de los comandos proporcionados por el paquete, en lugar de cargarlo inmediatamente al ejecutar package require. Esto no es compatible con el uso de auto_reset, y por lo tanto su uso se desaconseja.
-cargar pkgPat
El proceso de índice precargará cualquier paquete que exista en el intérprete actual y que coincida con pkgPat en el intérprete hijo utilizado para generar el índice. La coincidencia de patrones utiliza las reglas de coincidencia de cadenas, pero sin distinguir mayúsculas y minúsculas. Véase CASOS COMPLEJOS más abajo.
-verboso
Genera salida durante el proceso de indexación. La salida se realiza a través del procedimiento tclLog, que por defecto imprime en stderr.
--
Fin de los indicadores, en caso de que dir comience con un guion.

PAQUETES Y EL CARGADOR AUTOMÁTICO

Las facilidades de gestión de paquetes se superponen parcialmente con el cargador automático, ya que ambos organizan la carga de archivos bajo demanda. Sin embargo, la gestión de paquetes es un mecanismo de nivel superior que utiliza el cargador automático para el último paso del proceso de carga. Generalmente es mejor indexar un paquete con pkg_mkIndex en lugar de auto_mkindex porque el mecanismo de paquetes proporciona control de versiones: varias versiones de un paquete pueden ser puestas a disposición en los archivos de índice, con diferentes aplicaciones utilizando diferentes versiones basándose en comandos package require. En contraste, auto_mkindex no entiende versiones, por lo que solo puede manejar una única versión de cada paquete. Probablemente no sea una buena idea indexar un paquete dado tanto con pkg_mkIndex como con auto_mkindex. Si usas pkg_mkIndex para indexar un paquete, sus comandos no se podrán invocar hasta que se haya utilizado package require para seleccionar una versión; en contraste, los paquetes indexados con auto_mkindex se pueden usar inmediatamente ya que no hay control de versiones.

CÓMO FUNCIONA

Pkg_mkIndex depende del comando package unknown, del comando package ifneeded y del cargador automático. La primera vez que se invoca un comando package require, se invoca el script package unknown. Este se establece en la inicialización de Tcl a un script que evalúa todos los archivos pkgIndex.tcl en el auto_path. Los archivos pkgIndex.tcl contienen comandos package ifneeded para cada versión de cada paquete disponible; estos comandos invocan comandos package provide para anunciar la disponibilidad del paquete y configuran información del cargador automático para cargar los archivos del paquete. Si se proporcionó el indicador -perezoso cuando se generó el pkgIndex.tcl, un archivo dado de una versión dada de un paquete no se carga realmente hasta la primera vez que se invoca uno de sus comandos. Por lo tanto, después de invocar package require, es posible que no veas los comandos del paquete en el intérprete, pero podrás invocar los comandos y se cargarán automáticamente.

CARGA DIRECTA

Algunos paquetes, por ejemplo aquellos que usan namespaces y exportan comandos o aquellos que requieren inicialización especial, podrían seleccionar que sus archivos de paquete se carguen inmediatamente al ejecutar package require en lugar de retrasar la carga real hasta el primer uso de uno de los comandos del paquete. Este es el modo predeterminado al generar el índice del paquete. Se puede anular especificando el argumento -perezoso.

CASOS COMPLEJOS

La mayoría de los casos complejos de dependencias entre scripts y archivos binarios, y paquetes divididos entre scripts y archivos binarios, se manejan bien. Sin embargo, puede que tengas que ajustar el orden en que pkg_mkIndex procesa los archivos. Estos problemas se describen en detalle a continuación.

.

Si cada script o archivo contiene un paquete y los paquetes solo están contenidos en un archivo, entonces las cosas son fáciles. Simplemente especifique todos los archivos a indexar en cualquier orden con algunos patrones glob.

En general, está bien que los scripts tengan dependencias de otros paquetes. Si los scripts contienen comandos package require, estos se sustituyen en el intérprete utilizado para procesar los scripts, por lo que no causan problemas. Si los scripts llaman a otros paquetes en código global, estas llamadas son manejadas por un comando unknown ficticio. Sin embargo, si los scripts realizan referencias a variables de otros paquetes en código global, esto causará errores. Eso también es un mal estilo de codificación.

Si los archivos binarios tienen dependencias de otros paquetes, las cosas pueden volverse complicadas porque no es posible sustituir APIs a nivel de C, como la API Tcl_PkgRequire, al cargar un archivo binario. Por ejemplo, suponga que el paquete BLT requiere Tk y lo expresa con una llamada a Tcl_PkgRequire en su rutina Blt_Init. Para soportar esto, debe ejecutar pkg_mkIndex en un intérprete que tenga Tk cargado. Puede lograr esto con la opción -load pkgPat. Si especifica esta opción, pkg_mkIndex cargará cualquier paquete listado por info loaded y que coincida con pkgPat en el intérprete utilizado para procesar archivos. En la mayoría de los casos, esto satisfará las llamadas a Tcl_PkgRequire realizadas por archivos binarios.

Si está indexando dos archivos binarios y uno depende del otro, debe especificar el que tiene dependencias al final. De esta manera, el que no tiene dependencias se cargará e indexará, y luego el paquete que proporciona estará disponible cuando se procese el segundo archivo. También puede que necesite cargar el primer paquete en el intérprete temporal utilizado para crear el índice utilizando la bandera -load; no hará daño especificar patrones de paquetes que aún no están cargados.

Si tiene un paquete que está dividido entre scripts y un archivo binario, debe evitar la bandera -load. El problema es que si carga un paquete antes de calcular el índice, enmascara cualquier otro archivo que proporcione parte del mismo paquete. Si debe usar -load, entonces debe especificar los scripts primero; de lo contrario, el paquete cargado desde el archivo binario puede enmascarar el paquete definido por los scripts.
