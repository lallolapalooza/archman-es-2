NOMBRE

perlperf - Técnicas de rendimiento y optimización de Perl

DESCRIPCIÓN

Esta es una introducción al uso de técnicas de rendimiento y optimización que se pueden utilizar con particular referencia a los programas de perl. Si bien muchos desarrolladores de perl provienen de otros lenguajes y pueden utilizar sus conocimientos previos cuando sea apropiado, hay muchas otras personas que podrían beneficiarse de algunos consejos específicos para perl. Si desea la versión condensada, quizás el mejor consejo provenga del reconocido Samurai japonés, Miyamoto Musashi, quien dijo:

"No te involucres en actividades inútiles"

en 1645.

VISTA GENERAL

Quizás el error más común que cometen los programadores es intentar optimizar su código antes de que un programa haga algo útil; esto es una mala idea. No tiene sentido tener un programa extremadamente rápido que no funciona. El primer trabajo es conseguir que un programa haga algo correctamente y que sea útil (sin mencionar asegurar que el conjunto de pruebas sea completamente funcional), y solo entonces considerar optimizarlo. Habiendo decidido optimizar código de trabajo existente, hay varios pasos simples pero esenciales a considerar que son intrínsecos a cualquier proceso de optimización.

UN PASO LATERAL

En primer lugar, necesita establecer un tiempo de referencia para el código existente, cuyo tiempo debe ser confiable y repetible. Probablemente querrá usar los módulos "Benchmark" o "Devel::NYTProf", o algo similar, para este paso, o quizás la utilidad del sistema Unix "time", lo que sea apropiado. Consulte la base de este documento para obtener una lista más larga de módulos de benchmarking y profiling, y lecturas recomendadas.

UN PASO ADELANTE

A continuación, habiendo examinado el programa en busca de puntos calientes (lugares donde el código parece ejecutarse lentamente), cambie el código con la intención de hacerlo más rápido. Usar software de control de versiones, como "subversion", asegurará que los cambios no sean irreversibles. Es demasiado fácil tocar aquí y tocar allá; no cambie demasiado a la vez o podría no descubrir qué parte del código era realmente la lenta.

OTRO PASO LATERAL

No es suficiente decir: "eso hará que funcione más rápido"; tiene que comprobarlo. Vuelva a ejecutar el código bajo el control de los módulos de benchmarking o profiling, del primer paso anterior, y compruebe que el nuevo código ejecutó la misma tarea en menos tiempo. Guarde su trabajo y repita...

DIRECTRICES GENERALES

Lo crítico al considerar el rendimiento es recordar que no existe una "Bala de Plata", razón por la cual no hay reglas, solo directrices.

Está claro que el código en línea será más rápido que las llamadas a subrutinas o métodos, porque hay menos sobrecarga, pero este enfoque tiene la desventaja de ser menos mantenible y tiene el costo de un mayor uso de memoria; no hay almuerzo gratis. Si está buscando un elemento en una lista, puede ser más eficiente almacenar los datos en una estructura de hash y luego simplemente verificar si la clave está definida, en lugar de recorrer toda la matriz usando grep(), por ejemplo. substr() puede ser (mucho) más rápido que grep() pero no tan flexible, por lo que tiene otra compensación a considerar. Su código puede contener una línea que tarde 0.01 segundos en ejecutarse, que si la llama 1.000 veces, muy probablemente en un programa que analice archivos incluso de tamaño mediano, por ejemplo, ya tiene un retraso de 10 segundos, en una sola ubicación de código, y si llama a esa línea 100.000 veces, todo su programa se ralentizará hasta un arrastre insoportable.

Usar una subrutina como parte de su ordenación es una forma poderosa de obtener exactamente lo que desea, pero generalmente será más lento que los operadores de ordenación alfabéticos "cmp" y numéricos "<=>" incorporados. Es posible realizar múltiples pasadas sobre sus datos, construyendo índices para hacer la próxima ordenación más eficiente, y usar lo que se conoce como "OM" (Maniobra Orca) para almacenar en caché las claves de ordenación con anticipación. La búsqueda en caché, si bien es una buena idea, puede ser en sí misma una fuente de ralentización al forzar una doble pasada sobre los datos: una para configurar la caché y otra para ordenar los datos. Usar pack() para extraer la clave de ordenación requerida en una cadena consistente puede ser una forma eficiente de construir una sola cadena para comparar, en lugar de usar múltiples claves de ordenación, lo que hace posible usar la función de ordenación estándar de perl, escrita en "c" y rápida, sobre la salida, y es la base de "GRT" (Transformación Guttman Rossler). Algunas combinaciones de cadenas pueden ralentizar "GRT", simplemente por ser demasiado simples para su propio bien.

Para aplicaciones que utilizan bases de datos como backend, el espacio de nombres estándar "DBIx" ha intentado ayudar a mantener las cosas ágiles, en gran parte porque intenta no consultar la base de datos hasta el último momento posible, pero siempre lea la documentación que viene con su elección de bibliotecas. Entre los muchos problemas que enfrentan los desarrolladores al tratar con bases de datos, deben ser conscientes de usar siempre los marcadores de posición de "SQL" y considerar la pre-carga de conjuntos de datos cuando esto pueda resultar ventajoso. Dividir un archivo grande asignando múltiples procesos para analizar un solo archivo, utilizando por ejemplo "POE", "threads" o "fork" también puede ser una forma útil de optimizar su uso de los recursos de "CPU" disponibles, aunque esta técnica está llena de problemas de concurrencia y exige gran atención al detalle.

Cada caso tiene una aplicación específica y una o más excepciones, y no hay sustituto para ejecutar algunas pruebas y descubrir qué método funciona mejor para su entorno particular; es por eso que escribir código óptimo no es una ciencia exacta, y por qué nos encanta usar Perl tanto: TMTOWTDI.

BENCHMARKS

Aquí hay algunos ejemplos para demostrar el uso de las herramientas de benchmarking de Perl.

Asignación y Desreferenciación de Variables

Estoy seguro de que la mayoría de nosotros hemos visto código que se ve así, (o peor):

if ( $obj->{_ref}->{_myscore} >= $obj->{_ref}->{_yourscore} ) {
    ...

Este tipo de código puede ser una verdadera molestia de leer, además de ser muy sensible a errores tipográficos, y es mucho más claro desreferenciar la variable explícitamente. Estamos esquivando el problema de trabajar con técnicas de programación orientada a objetos para encapsular el acceso a variables a través de métodos, solo accesibles a través de un objeto. Aquí solo estamos discutiendo la implementación técnica de elección, y si esto tiene un efecto en el rendimiento. Podemos ver si esta operación de desreferenciación tiene alguna sobrecarga colocando código comparativo en un archivo y ejecutando una prueba de "Benchmark".

# desreferencia

#!/usr/bin/perl
use v5.36;
use Benchmark;
my $ref = {
        'ref'   => {
            _myscore    => '100 + 1',
            _yourscore  => '102 - 1',
        },
};
timethese(1000000, {
        'direct'       => sub {
          my $x = $ref->{ref}->{_myscore} . $ref->{ref}->{_yourscore} ;
        },
        'dereference'  => sub {
            my $ref  = $ref->{ref};
            my $myscore = $ref->{_myscore};
            my $yourscore = $ref->{_yourscore};
            my $x = $myscore . $yourscore;
        },
});

Es esencial ejecutar cualquier medición de tiempo un número suficiente de veces para que los números se estabilicen en un promedio numérico, de lo contrario, cada ejecución fluctuará naturalmente debido a variaciones en el entorno, para reducir el efecto de la contención de recursos de "CPU" y ancho de banda de red, por ejemplo. $> perl dereference

dereference:  2 wallclock secs ( 1.59 usr +  0.00 sys =  1.59 CPU) @ 628930.82/s (n=1000000)

La diferencia es clara y el enfoque de desreferenciación es más lento. Mientras que logró ejecutar un promedio de 628,930 veces por segundo durante nuestra prueba, el enfoque directo logró ejecutarse 204,403 veces más, desafortunadamente. Desafortunadamente, porque hay muchos ejemplos de código escrito usando el acceso directo a variables de múltiples capas, y generalmente es horrible. Sin embargo, es minúsculamente más rápido. La pregunta sigue siendo si la ganancia minúscula realmente vale la pena el esfuerzo visual, o la pérdida de mantenibilidad.

Búsqueda y reemplazo o tr

Si tenemos una cadena que necesita ser modificada, mientras que una expresión regular será casi siempre mucho más flexible, "tr", una herramienta a menudo infrautilizada, todavía puede ser útil. Un escenario podría ser reemplazar todas las vocales con otro carácter. La solución regex podría verse así:

$str =~ s/[aeiou]/x/g

La alternativa "tr" podría verse así:

$str =~ tr/aeiou/xxxxx/

Podemos poner eso en un archivo de prueba que podamos ejecutar para verificar qué enfoque es el más rápido, utilizando una variable global $STR para asignar a la variable "my $str" para evitar que perl intente optimizar cualquiera de las tareas al notar que solo se asigna una vez.

# regex-transliterate

#!/usr/bin/perl
use v5.36;
use Benchmark;
my $STR = "$$-this and that";
timethese(1000000, {
'sr'  => sub { my $str = $STR; $str =~ s/[aeiou]/x/g; return $str; },
'tr'  => sub { my $str = $STR; $str =~ tr/aeiou/xxxxx/; return $str; },
});

Ejecutar el código nos da nuestros resultados:

$> perl regex-transliterate
Benchmark: timing 1000000 iterations of sr, tr...
        sr:  2 wallclock secs ( 1.19 usr +  0.00 sys =  1.19 CPU) @ 840336.13/s (n=1000000)
        tr:  0 wallclock secs ( 0.49 usr +  0.00 sys =  0.49 CPU) @ 2040816.33/s (n=1000000)

La versión "tr" es una clara ganadora. Una solución es flexible, la otra es rápida, y es apropiadamente la elección del programador cuál usar.

Consulta la documentación de "Benchmark" para conocer más técnicas útiles.

HERRAMIENTAS DE PERFILADO

Un fragmento de código ligeramente más grande proporcionará algo sobre lo cual un perfilador puede producir estadísticas de informes más extensas. Este ejemplo utiliza el simplista programa "wordmatch" que analiza un archivo de entrada dado y arroja un breve informe sobre el contenido.

# wordmatch

#!/usr/bin/perl
use v5.36;
=head1 NAME
filewords - análisis de palabras de archivo de entrada
=head1 SYNOPSIS
    filewords -f nombre_archivo_entrada [-d]
=head1 DESCRIPTION
Este programa analiza el nombre de archivo dado, especificado con C<-f>, y
muestra un análisis simple de las palabras encontradas en él. Use el
interruptor C<-d> para habilitar los mensajes de depuración.
=cut
use FileHandle;
use Getopt::Long;
my $debug   =  0;
my $file    = '';
my $result = GetOptions (
    'debug'         => \$debug,
    'file=s'        => \$file,
);
die("invalid args") unless $result;
unless ( -f $file ) {
    die("Usage: $0 -f filename [-d]");
}
my $FH = FileHandle->new("< $file")
                              or die("unable to open file($file): $!");
my $i_LINES = 0;
my $i_WORDS = 0;
my %count   = ();
my @lines = <$FH>;
foreach my $line ( @lines ) {
    $i_LINES++;
    $line =~ s/\n//;
    my @words = split(/ +/, $line);
    my $i_words = scalar(@words);
    $i_WORDS = $i_WORDS + $i_words;
    debug("line: $i_LINES supplying $i_words words: @words");
    my $i_word = 0;
    foreach my $word ( @words ) {
        $i_word++;
        $count{$i_LINES}{spec} += matches($i_word, $word,
                                          '[^a-zA-Z0-9]');
        $count{$i_LINES}{only} += matches($i_word, $word,
                                          '^[^a-zA-Z0-9]+$');
        $count{$i_LINES}{cons} += matches($i_word, $word,
                                    '^[(?i:bcdfghjklmnpqrstvwxyz)]+$');
        $count{$i_LINES}{vows} += matches($i_word, $word,
                                          '^[(?i:aeiou)]+$');
        $count{$i_LINES}{caps} += matches($i_word, $word,
                                          '^[(A-Z)]+$');
    }
}
print report( %count );
sub matches {
    my $i_wd  = shift;
    my $word  = shift;
    my $regex = shift;
    my $has = 0;
    if ( $word =~ /($regex)/ ) {
        $has++ if $1;
    }
    debug( "word: $i_wd "
          . ($has ? 'matches' : 'does not match')
          . " chars: /$regex/");
    return $has;
}
sub report {
    my %report = @_;
    my %rep;
    foreach my $line ( keys %report ) {
        foreach my $key ( keys $report{$line}->%* ) {
            $rep{$key} += $report{$line}{$key};
        }
    }
    my $report = qq|
$0 report for $file:
lines in file: $i_LINES
words in file: $i_WORDS
words with special (non-word) characters: $i_spec
words with only special (non-word) characters: $i_only
words with only consonants: $i_cons
words with only capital letters: $i_caps
words with only vowels: $i_vows
|;
    return $report;
}
sub debug {
    my $message = shift;
    if ( $debug ) {
        print STDERR "DBG: $message\n";
    }
}
exit 0;

Devel::DProf

Este venerable módulo ha sido el estándar de facto para el perfilado de código Perl durante más de una década, pero ha sido reemplazado por varios otros módulos que nos han traído de vuelta al siglo XXI. Aunque se recomienda evaluar su herramienta entre las varias mencionadas aquí y en la lista CPAN en la base de este documento (y actualmente Devel::NYTProf parece ser el arma preferida, ver más abajo), echaremos un vistazo rápido a la salida de Devel::DProf primero, para establecer una línea de base para las herramientas de perfilado de Perl. Ejecute el programa anterior bajo el control de "Devel::DProf" usando el interruptor "-d" en la línea de comandos.

Devel::FastProf

"Devel::FastProf" es otro perfilador de líneas de Perl. Fue escrito con el objetivo de obtener un perfilador de líneas más rápido que el que es posible con, por ejemplo, "Devel::SmallProf", porque está escrito en "C". Para usar "Devel::FastProf", proporciona el argumento "-d" a Perl:

$> perl -d:FastProf wordmatch -f perl5db.pl
<...múltiples líneas omitidas...>
Informe de wordmatch para perl5db.pl:
líneas en el archivo: 9428

ORDENAR

Los módulos de Perl no son las únicas herramientas que un analista de rendimiento tiene a su disposición, herramientas del sistema como "time" no deben pasarse por alto, como muestra el siguiente ejemplo, donde echamos un vistazo rápido a la ordenación. Se han escrito muchos libros, tesis y artículos sobre algoritmos de ordenación eficientes, y este no es el lugar para repetir dicho trabajo, también hay varios módulos de ordenación buenos que merecen ser vistos: "Sort::Maker", "Sort::Key" vienen a la mente. Sin embargo, todavía es posible hacer algunas observaciones sobre ciertas interpretaciones específicas de Perl sobre cuestiones relacionadas con la ordenación de conjuntos de datos y dar un par de ejemplos sobre cómo la ordenación de grandes volúmenes de datos puede afectar al rendimiento. En primer lugar, un punto que a menudo se pasa por alto al ordenar grandes cantidades de datos, se puede intentar reducir el conjunto de datos a tratar y, en muchos casos, grep() puede ser bastante útil como un filtro simple:

@data = sort grep { /$filter/ } @incoming

Un comando como este puede reducir enormemente el volumen de material a ordenar en primer lugar, y no debe ser despreciado a la ligera basándose puramente en su simplicidad. El principio "KISS" (Keep It Simple, Stupid) se pasa por alto con demasiada frecuencia; el siguiente ejemplo utiliza la utilidad de sistema simple "time" para demostrar. # sort-apache-log


#!/usr/bin/perl -n
use v5.36;
my @data;
LINE:
while ( <> ) {
    my $line = $_;
    if (
        $line =~ m/^(
            ([\w\.\-]+)             # cliente
            \s*-\s*-\s*\[
            ([^]]+)                 # fecha
            \]\s*"\w+\s*
            (\S+)                   # consulta
            [^"]+"\s*
            (\d+)                   # estado
            \s+\S+\s+"[^"]*"\s+"
            ([^"]*)                 # navegador
            "
            .*
        )$/x
    ) {
        my @chunks = split(/ +/, $line);
        my $ip      = $1;
        my $date    = $2;
        my $query   = $3;
        my $status  = $4;
        my $browser = $5;
        push(@data, [$ip, $date, $query, $status, $browser, $line]);
    }
}
my @sorted = sort {
    $a->[3] cmp $b->[3]
            ||
    $a->[2] cmp $b->[2]
            ||
    $a->[0] cmp $b->[0]
            ||
    $a->[1] cmp $b->[1]
            ||
    $a->[4] cmp $b->[4]
} @data;
foreach my $data ( @sorted ) {
    print $data->[5];
}
exit 0;

El programa tardó poco más de 17 segundos de reloj en ejecutarse. Tenga
en cuenta los diferentes valores que "time"
muestra, es importante usar siempre el mismo y no confundir lo que cada uno
significa.



  
Tiempo real transcurrido

  
El tiempo total, o tiempo de reloj, entre cuando se llamó a
      "time" y cuando terminó. El tiempo
      transcurrido incluye tanto el tiempo de usuario como el de sistema, y el
      tiempo dedicado a esperar a otros usuarios y procesos en el sistema.
      Inevitablemente, esta es la más aproximada de las mediciones
      proporcionadas.

  
Tiempo de CPU de usuario

  
El tiempo de usuario es la cantidad de tiempo que todo el proceso pasó en
      nombre del usuario en este sistema ejecutando este programa.

  
Tiempo de sistema

  
El tiempo de sistema es la cantidad de tiempo que el kernel en sí mismo
      pasó ejecutando rutinas, o llamadas al sistema, en nombre de este usuario
      del proceso.




Ejecutar este mismo proceso como una "Transformación
    Schwarziana" permite eliminar los arreglos de entrada y salida para
    almacenar todos los datos, y trabajar directamente con la entrada a medida que
    llega. De lo contrario, el código se ve bastante similar:


# sort-apache-log-schwarzian


#!/usr/bin/perl -n
use v5.36;
print
    map $_->[0] =>
    sort {
        $a->[4] cmp $b->[4]
                ||
        $a->[3] cmp $b->[3]
                ||
        $a->[1] cmp $b->[1]
                ||
        $a->[2] cmp $b->[2]
                ||
        $a->[5] cmp $b->[5]
    }
    map  [ $_, m/^(
        ([\w\.\-]+)             # cliente
        \s*-\s*-\s*\[
        ([^]]+)                 # fecha
        \]\s*"\w+\s*
        (\S+)                   # consulta
        [^"]+"\s*
        (\d+)                   # estado
        \s+\S+\s+"[^"]*"\s+"
        ([^"]*)                 # navegador
        "
        .*
    )$/xo ]
    => <>;
exit 0;

El tiempo se ha reducido a la mitad, lo que representa una mejora de
velocidad respetable para cualquier estándar. Naturalmente, es importante
verificar que la salida sea coherente con la primera ejecución del programa,
aquí es donde entra en juego la utilidad "cksum"
del sistema Unix.


$> cksum out-sort out-schwarz
3044173777 52029194 out-sort
3044173777 52029194 out-schwarz


Por cierto. Tenga cuidado también con la presión de los gerentes que
ven que usted acelera un programa en un 50% del tiempo de ejecución una vez, solo
para recibir una solicitud un mes después para hacer lo mismo nuevamente (historia
real): simplemente tendrá que señalar que usted es solo un humano, incluso si es
un programador de Perl, y verá qué puede hacer...

REGISTRO

Una parte esencial de cualquier buen proceso de desarrollo es un manejo de errores apropiado con mensajes lo suficientemente informativos; sin embargo, existe una corriente de pensamiento que sugiere que los archivos de registro deben ser habladores, como si la cadena de salida ininterrumpida garantizara de alguna manera la supervivencia del programa. Si la velocidad es un problema de alguna manera, este enfoque es incorrecto.

Un espectáculo común es código que se ve algo así:

logger->debug( "Un mensaje de registro a través del ID de proceso: $$ INC: "
                                                      . Dumper(\%INC) )

El problema es que este código siempre será analizado y ejecutado, incluso cuando el nivel de depuración establecido en el archivo de configuración de registro sea cero. Una vez que se haya ingresado a la subrutina debug() y se confirme que la variable interna $debug es cero, por ejemplo, el mensaje que se envió se descartará y el programa continuará. En el ejemplo dado, sin embargo, el hash "\%INC" ya se habrá volcado y la cadena de mensaje se habrá construido, todo lo cual podría ser omitido por una variable de depuración a nivel de instrucción, así:

logger->debug( "Un mensaje de registro a través del ID de proceso: $$ INC: "
                                           . Dumper(\%INC) ) if $DEBUG;

Este efecto se puede demostrar configurando un script de prueba con ambas formas, incluida una subrutina debug() para emular la funcionalidad típica de logger().

# ifdebug

#!/usr/bin/perl
use v5.36;
use Benchmark;
use Data::Dumper;
my $DEBUG = 0;
sub debug {
    my $msg = shift;
    if ( $DEBUG ) {
        print "DEBUG: $msg\n";
    }
};
timethese(100000, {
        'debug'       => sub {
            debug( "Un mensaje de registro $0 a través del ID de proceso: $$" . Dumper(\%INC) )
        },
        'ifdebug'  => sub {
            debug( "Un mensaje de registro $0 a través del ID de proceso: $$" . Dumper(\%INC) ) if $DEBUG
        },
});

Veamos qué opina "Benchmark" de esto:

$> perl ifdebug
Benchmark: timing 100000 iterations of constant, sub...
   ifdebug:  0 wallclock secs ( 0.01 usr +  0.00 sys =  0.01 CPU) @ 10000000.00/s (n=100000)
            (warning: too few iterations for a reliable count)
     debug: 14 wallclock secs (13.18 usr +  0.04 sys = 13.22 CPU) @ 7564.30/s (n=100000)

En un caso el código, que hace exactamente lo mismo en cuanto a mostrar información de depuración, en otras palabras, nada, tarda 14 segundos, y en el otro caso el código tarda una centésima de segundo. Parece bastante definitivo. Utilice una variable $DEBUG ANTES de llamar a la subrutina, en lugar de depender de la funcionalidad inteligente dentro de ella.

Registro si DEBUG (constante)

Es posible llevar la idea anterior un poco más allá, utilizando una constante "DEBUG" en tiempo de compilación.

# ifdebug-constant

#!/usr/bin/perl
use v5.36;
use Benchmark;
use Data::Dumper;
use constant
    DEBUG => 0
;
sub debug {
    if ( DEBUG ) {
        my $msg = shift;
        print "DEBUG: $msg\n";
    }
};
timethese(100000, {
        'debug'       => sub {
            debug( "Un mensaje de registro $0 a través del ID de proceso: $$" . Dumper(\%INC) )
        },
        'constant'  => sub {
            debug( "Un mensaje de registro $0 a través del ID de proceso: $$" . Dumper(\%INC) ) if DEBUG
        },
});

Ejecutar este programa produce la siguiente salida:

$> perl ifdebug-constant
Benchmark: timing 100000 iterations of constant, sub...
  constant:  0 wallclock secs (-0.00 usr +  0.00 sys = -0.00 CPU) @ -7205759403792793600000.00/s (n=100000)
            (warning: too few iterations for a reliable count)
       sub: 14 wallclock secs (13.09 usr +  0.00 sys = 13.09 CPU) @ 7639.42/s (n=100000)

La constante "DEBUG" barre el suelo incluso con la variable $debug, registrando cero segundos, y además genera un mensaje de advertencia: "too few iterations for a reliable count". Para ver lo que realmente está pasando, y por qué tuvimos muy pocas iteraciones cuando creíamos haber pedido 100000, podemos usar el muy útil "B::Deparse" para inspeccionar el nuevo código:

$> perl -MO=Deparse ifdebug-constant
use Benchmark;
use Data::Dumper;
use constant ('DEBUG', 0);
sub debug {
    use warnings;
    use strict 'refs';
    0;
}
use warnings;
use strict 'refs';
timethese(100000, {'sub', sub {
    debug "Un mensaje de registro $0 a través del ID de proceso: $$" . Dumper(\%INC);
}
, 'constant', sub {
    0;
}
});
ifdebug-constant syntax OK

La salida muestra que la subrutina constant() que estamos probando se reemplaza con el valor de la constante "DEBUG": cero. La línea que se va a probar se ha optimizado por completo y no se puede obtener nada mucho más eficiente que eso.

PÓSTUMO

Este documento ha proporcionado varias formas de identificar puntos críticos y verificar si las modificaciones han mejorado el tiempo de ejecución del código.

Como pensamiento final, recuerde que (en el momento de escribir esto) no es posible producir un programa útil que se ejecute en tiempo cero o negativo y este principio básico se puede escribir como: los programas útiles son lentos por su propia definición. Por supuesto, es posible escribir un programa casi instantáneo, pero no hará mucho, aquí hay uno muy eficiente:

$> perl -e 0

Optimizar eso más allá es un trabajo para "p5p".
