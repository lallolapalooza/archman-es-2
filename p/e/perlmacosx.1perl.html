PERLMACOSX(1perl) Guía de Referencia del Programador de Perl PERLMACOSX(1perl)

NOMBRE

perlmacosx - Perl en Mac OS X

SINOPSIS

Este documento describe brevemente Perl en Mac OS X.

curl -O https://www.cpan.org/src/perl-5.42.0.tar.gz
tar -xzf perl-5.42.0.tar.gz
cd perl-5.42.0
./Configure -des -Dprefix=/usr/local/
make
make test
sudo make install

DESCRIPCIÓN

La última versión de Perl (5.42.0 en el momento de escribir esto) se compila sin cambios en todas las versiones de Mac OS X desde 10.3 "Panther" en adelante.

Para compilar tu propia versión de Perl necesitarás 'make', que forma parte de las herramientas de desarrollador de Apple, también conocidas como Xcode. Desde Mac OS X 10.7 "Lion" en adelante, se puede descargar por separado como el paquete 'Command Line Tools' directamente desde https://developer.apple.com/downloads/ (necesitarás una cuenta gratuita para iniciar sesión), o como parte de la suite Xcode, disponible gratuitamente en la App Store. Xcode es una aplicación bastante grande, así que a menos que ya la tengas o realmente la quieras, te recomendamos descargar el paquete 'Command Line Tools' por separado desde el enlace anterior. Si quieres hacerlo desde Xcode, ve a Xcode -> Preferencias -> Descargas y selecciona la opción 'Command Line Tools'.

Entre Mac OS X 10.3 "Panther" y 10.6 "Snow Leopard", el paquete 'Command Line Tools' se llamaba 'unix tools', y generalmente se suministraba con los DVDs de instalación de Mac OS.

Las versiones anteriores de Mac OS X (10.2 "Jaguar" y anteriores) no incluían una libc completamente segura para hilos, por lo que la multitarea no es totalmente compatible. Además, las versiones anteriores incluían una libdb defectuosa, por lo que algunas de las pruebas de DB_File se sabe que fallan en esas versiones.

Prefijo de Instalación

La ubicación de instalación predeterminada para esta versión utiliza la disposición tradicional de directorios de UNIX en /usr/local. Esta es la ubicación recomendada para la mayoría de los usuarios y dejará intacto el Perl proporcionado por Apple y sus módulos.

Usar un prefijo de instalación de '/usr' resultará en una disposición de directorios que refleja la del Perl predeterminado de Apple, con los módulos principales almacenados en '/System/Library/Perl/${version}', los módulos CPAN almacenados en '/Library/Perl/${version}', y la adición de '/Network/Library/Perl/${version}' a @INC para módulos almacenados en un servidor de archivos y utilizados por varios Macs.

Soporte de SDK

Primero, exporta la ruta al SDK al entorno de compilación:

export SDK=/Applications/Xcode.app/Contents/Developer/Platforms/MacOSX.platform/Developer/SDKs/MacOSX10.8.sdk

Asegúrate de que la versión del SDK (es decir, los números antes de '.sdk') coincida con la de tu sistema (en este caso, Mac OS X 10.8 "Mountain Lion"), ya que es posible tener más de un SDK instalado. Asegúrate también de que la ruta exista en tu sistema, y si no es así, asegúrate de que el SDK esté correctamente instalado, ya que debería venir con el paquete 'Command Line Tools' mencionado anteriormente. Finalmente, si tienes un Mac OS X más antiguo (10.6 "Snow Leopard" y anteriores) con Xcode 4.2 o inferior, la ruta del SDK podría ser algo como '/Developer/SDKs/MacOSX10.3.9.sdk'.

Puedes usar el SDK exportando algunas adiciones a las variables de configuración 'ccflags' y '..flags' de Perl:

./Configure -Accflags="-nostdinc -B$SDK/usr/include/gcc \
                       -B$SDK/usr/lib/gcc -isystem$SDK/usr/include \
                       -F$SDK/System/Library/Frameworks" \
            -Aldflags="-Wl,-syslibroot,$SDK" \
            -de

Soporte de Binarios Universales

Nota: Desde Mac OS X 10.6 "Snow Leopard" en adelante, Apple solo admite hardware basado en Intel. Esto significa que puedes omitir esta sección de forma segura a menos que tengas una computadora Apple más antigua que funcione con ppc o desees crear un binario de perl con compatibilidad retroactiva.

Puedes compilar perl como un binario universal (compilado para ppc e intel). En Mac OS X 10.4 "Tiger", debes exportar la variante 'u' del SDK:

export SDK=/Developer/SDKs/MacOSX10.4u.sdk

Mac OS X 10.5 "Leopard" y versiones posteriores no requieren la variante 'u'.

Además de las banderas del compilador utilizadas para seleccionar el SDK, también agrega las banderas para crear un binario universal:

./Configure -Accflags="-arch i686 -arch ppc -nostdinc               \
                        -B$SDK/usr/include/gcc                      \
                       -B$SDK/usr/lib/gcc -isystem$SDK/usr/include  \
                       -F$SDK/System/Library/Frameworks"            \
            -Aldflags="-arch i686 -arch ppc -Wl,-syslibroot,$SDK"   \
            -de

Ten en cuenta que esta configuración del compilador y el enlazador también se utilizará al compilar módulos CPAN. Para que los módulos XS se compilen como un binario universal, cualquier biblioteca a la que enlacen también debe ser un binario universal. Las bibliotecas del sistema que Apple incluye con el SDK 10.4u son todas universales, pero es posible que las bibliotecas instaladas por el usuario deban reinstalarse como binarios universales.

Soporte PPC de 64 bits

Sigue las instrucciones en INSTALL para compilar perl con soporte para enteros de 64 bits ("use64bitint") o tanto enteros de 64 bits como direccionamiento de 64 bits ("use64bitall"). En este último caso, el binario resultante solo se ejecutará en hosts basados en G5.

El soporte para direccionamiento de 64 bits es experimental: algunos aspectos de Perl pueden omitirse o tener errores. Ten en cuenta los mensajes que produce Configure para obtener más información. Utiliza https://github.com/Perl/perl5/issues para enviar un informe de problema en caso de que encuentres dificultades.

Al compilar módulos de 64 bits, es tu responsabilidad asegurarte de que las bibliotecas y frameworks externos enlazados proporcionen soporte de 64 bits: si no lo hacen, la compilación del módulo puede parecer exitosa, pero los intentos de usar el módulo resultarán en errores de enlace dinámico en tiempo de ejecución y fallos posteriores en las pruebas. Puedes usar "file" para descubrir las arquitecturas compatibles con una biblioteca:

$ file libgdbm.3.0.0.dylib 
libgdbm.3.0.0.dylib: Mach-O fat file with 2 architectures
libgdbm.3.0.0.dylib (for architecture ppc):      Mach-O dynamically linked shared library ppc
libgdbm.3.0.0.dylib (for architecture ppc64):    Mach-O 64-bit dynamically linked shared library ppc64

Ten en cuenta que este problema impide la compilación de muchos módulos CPAN específicos de Macintosh ("Mac::*"), ya que los frameworks de Apple necesarios no proporcionan soporte PPC64. De manera similar, es poco probable que las descargas de Fink o Darwinports proporcionen soporte de 64 bits; las bibliotecas deben recompilarse desde la fuente con las banderas del compilador y enlazador apropiadas. Para más información, consulta la Guía de Transición a 64 bits de Apple en https://developer.apple.com/library/archive/documentation/Darwin/Conceptual/64bitPorting/transition/transition.html.

libperl y Prebinding

Mac OS X viene con una libperl cargada dinámicamente, pero la opción predeterminada para esta versión es compilar una libperl estática. La razón de esto es el prebinding. Las bibliotecas dinámicas se pueden pre-enlazar a una dirección específica en memoria para disminuir el tiempo de carga. Para hacer esto, es necesario conocer la ubicación y el tamaño de todas las bibliotecas cargadas previamente. Apple recopila esta información como parte de su proceso general de compilación del sistema operativo, y por lo tanto tiene fácil acceso a ella al compilar Perl, pero los usuarios comunes tendrían que hacer un gran esfuerzo para obtener la información necesaria para el prebinding.

Puedes anular la opción predeterminada y compilar una libperl compartida si lo deseas (Configure ... -Duseshrplib).

Con Mac OS X 10.4 "Tiger" y versiones posteriores, casi no hay penalización de rendimiento para las bibliotecas no pre-enlazadas. Las versiones anteriores sufrirán un mayor tiempo de carga que la biblioteca estática o la biblioteca dinámica pre-enlazada de Apple.

perlmacosx - Perl on Mac OS X

NAME

perlmacosx - Perl on Mac OS X

SYNOPSIS

perl ...

DESCRIPTION

The Perl distribution which ships with Mac OS X has been compiled to use Apple's static libperl.dylib. This is done for performance reasons and so that Perl scripts can be distributed on their own without needing to ship the Perl dynamic library with them.

You can distinguish the system Perl by the fact that it is installed into /System/Library/Perl, and that its executable is installed into /usr/bin/perl. The latter is the interpreter that will be used by default when you type "perl" at the command line, or when scripts are invoked that start with "#!/usr/bin/perl". Scripts supplied by Apple and other third parties as part of installation packages and such have generally only been tested with the /usr/bin/perl that's installed by Apple.

If you find that you do need to update the system Perl, one issue worth keeping in mind is the question of static vs. dynamic libraries. If you upgrade using the default static libperl, you will find that the dynamic libperl supplied by Apple will not be deleted. If both libraries are present when an application that links against libperl is built, ld will link against the dynamic library by default. So, if you need to replace Apple's dynamic libperl with a static libperl, you need to be sure to delete the older dynamic library after you've installed the update.

Known problems

If you have installed extra libraries such as GDBM through Fink (in other words, you have libraries under /sw/lib), or libdlcompat to /usr/local/lib, you may need to be extra careful when running Configure to not to confuse Configure and Perl about which libraries to use. Being confused will show up for example as "dyld" errors about symbol problems, for example during "make test". The safest bet is to run Configure as

Configure ... -Uloclibpth -Dlibpth=/usr/lib

to make Configure look only into the system libraries. If you have some extra library directories that you really want to use (such as newer Berkeley DB libraries in pre-Panther systems), add those to the libpth:

Configure ... -Uloclibpth -Dlibpth='/usr/lib /opt/lib'

The default of building Perl statically may cause problems with complex applications like Tk: in that case consider building shared Perl

Configure ... -Duseshrplib

but remember that there's a startup cost to pay in that case (see above "libperl and Prebinding").

Starting with Tiger (Mac OS X 10.4), Apple shipped broken locale files for the eu_ES locale (Basque-Spain). In previous releases of Perl, this resulted in failures in the lib/locale test. These failures have been suppressed in the current release of Perl by making the test ignore the broken locale. If you need to use the eu_ES locale, you should contact Apple support.

Cocoa

There are two ways to use Cocoa from Perl. Apple's PerlObjCBridge module, included with Mac OS X, can be used by standalone scripts to access Foundation (i.e. non-GUI) classes and objects.

An alternative is CamelBones, a framework that allows access to both Foundation and AppKit classes and objects, so that full GUI applications can be built in Perl. CamelBones can be found on SourceForge, at https://www.sourceforge.net/projects/camelbones/.

Starting From Scratch

Unfortunately it is not that difficult somehow manage to break one's Mac OS X Perl rather severely. If all else fails and you want to really, REALLY, start from scratch and remove even your Apple Perl installation (which has become corrupted somehow), the following instructions should do it. Please think twice before following these instructions: they are much like conducting brain surgery to yourself. Without anesthesia. We will not come to fix your system if you do this.

First, get rid of the libperl.dylib:

# cd /System/Library/Perl/darwin/CORE
# rm libperl.dylib

Then delete every .bundle file found anywhere in the folders:

/System/Library/Perl
/Library/Perl

You can find them for example by

# find /System/Library/Perl /Library/Perl -name '*.bundle' -print

After this you can either copy Perl from your operating system media (you will need at least the /System/Library/Perl and /usr/bin/perl), or rebuild Perl from the source code with "Configure -Dprefix=/usr -Duseshrplib" NOTE: the "-Dprefix=/usr" to replace the system Perl works much better with Perl 5.8.1 and later, in Perl 5.8.0 the settings were not quite right.

"Pacifist" from CharlesSoft (https://www.charlessoft.com/) is a nice way to extract the Perl binaries from the OS media, without having to reinstall the entire OS.
