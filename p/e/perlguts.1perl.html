Variables

Tipos de datos

Perl tiene tres tipos de datos (typedefs) que manejan los tres tipos principales de datos de Perl:

SV  Valor escalar
AV  Valor de array
HV  Valor de hash

Cada tipo de dato tiene rutinas específicas que manipulan los diversos tipos de datos.

¿Qué es un "IV"?

Perl usa un tipo de dato especial IV, que es un tipo entero simple con signo garantizado para ser lo suficientemente grande como para contener un puntero, pero puede ser más grande, dependiendo de cómo se haya configurado Perl. Adicionalmente, existe el UV, que es simplemente un IV sin signo.

Perl también utiliza varios tipos de datos especiales para declarar variables que almacenen enteros de (al menos) un tamaño dado. Use I8, I16, I32 e I64 para declarar una variable entera con signo que tenga al menos tantos bits como el número en su nombre. Todos estos se evalúan al tipo C nativo que está más cerca del número dado de bits, pero no más pequeño que ese número. Por ejemplo, en muchas plataformas, un "short" tiene 16 bits de longitud, y si es así, I16 se evaluará como un "short". Pero en plataformas donde un "short" no tiene exactamente 16 bits, Perl usará el tipo más pequeño que contenga 16 bits o más.

U8, U16, U32 y U64 son para declarar los tipos enteros sin signo correspondientes.

Si la plataforma no soporta enteros de 64 bits, tanto I64 como U64 estarán indefinidos. Use IV y UV para declarar el tipo más grande practicable, y "WIDEST_UTYPE" en perlapi para el tipo sin signo máximo absoluto, pero que puede no ser utilizable en todas las circunstancias.

Una constante numérica se puede especificar con ""INT16_C"" en perlapi, ""UINTMAX_C"" en perlapi, y similares.

Trabajando con SVs

Un SV puede crearse y cargarse con un solo comando. Hay cinco tipos de valores que se pueden cargar: un valor entero (IV), un valor entero sin signo (UV), un doble (NV), una cadena (PV) y otro escalar (SV). ("PV" significa "Pointer Value" o Valor Puntero. Podrías pensar que tiene un nombre equivocado porque se describe como que solo apunta a cadenas. Sin embargo, es posible que apunte a otras cosas. Por ejemplo, podría apuntar a un array de UVs. Pero, usarlo para elementos que no son cadenas requiere cuidado, ya que la suposición subyacente de gran parte de la interna es que los PV son solo para cadenas. A menudo, por ejemplo, se agrega automáticamente un carácter "NUL" al final. El uso no de cadenas solo se documenta en este párrafo).

Existen más de unas pocas rutinas que crean e inicializan SVs, con nuevas que se añaden ocasionalmente. Todas están documentadas en "SV Handling" en perlapi; cada una de sus nombres comienza con "newSV". Aquí están las básicas:

SV*  newSVbool(boolean_value);
SV*  newSViv(IV);
SV*  newSVuv(UV);
SV*  newSVnv(double);
SV*  newSVpv(const char*, STRLEN);
SV*  newSVpvf_nocontext(const char * const pat, ...)
SV*  newSVpvn(const char*, STRLEN);
SV*  newSVpvs("cadena literal")
SV*  newSVpvz(STRLEN)
SV*  newSVsv(SV*);

"STRLEN" es un tipo entero ("Size_t", usualmente definido como "size_t" en config.h) garantizado para ser lo suficientemente grande como para representar el tamaño de cualquier cadena que Perl pueda manejar.

"cadena literal" es una cadena encerrada entre comillas dobles, y el SV creado es de tipo cadena (un PV), inicializado para contener una copia de la cadena literal del parámetro. newSVpvs("") crea un SV que contiene una cadena vacía (de longitud cero) y devuelve un puntero a él.

"newSVpvz" es como newSVpvs(""), pero reserva el número de bytes especificado por su parámetro para crecimiento futuro, sin tener que reasignar memoria. Es útil en situaciones donde no sabes cuál será eventualmente la cadena, pero tienes una buena idea de su tamaño mínimo eventual.

En el caso de un SV que requiera una inicialización más compleja, puedes crear un SV vacío con newSV(len). Si "len" es 0, se devuelve un SV vacío de tipo NULL, de lo contrario, se devuelve un SV de tipo PV con len + 1 (para el carácter "NUL") bytes de almacenamiento asignados, accesibles a través de SvPVX. En ambos casos, el SV tiene el valor indefinido.

SV *sv = newSV(0);   /* no se asigna almacenamiento  */
SV *sv = newSV(10);  /* se asignan 10 (+1) bytes de almacenamiento
                      * no inicializado */

Para cambiar el valor de un SV *ya existente*, estas son las rutinas básicas (con más detalles en "SV Handling" en perlapi):

void  sv_setbool(SV*, bool);
void  sv_setiv(SV*, IV);
void  sv_setuv(SV*, UV);
void  sv_setnv(SV*, double);
void  sv_setpv(SV*, const char*);
void  sv_setpvn(SV*, const char*, STRLEN)
void  sv_setpvf(SV*, const char*, ...);
void  sv_vsetpvfn(SV*, const char*, STRLEN, va_list *,
                                    SV **, Size_t, bool *);
void  sv_setsv(SV*, SV*);

Observa que puedes elegir especificar la longitud de la cadena a asignar usando "sv_setpvn", "newSVpvn" o "newSVpv", o puedes permitir que Perl calcule la longitud usando "sv_setpv" o especificando 0 como segundo argumento de "newSVpv". Ten cuidado, sin embargo, que Perl determinará la longitud de la cadena usando "strlen", que depende de que la cadena termine con un carácter "NUL", y no contenga otros caracteres NUL.

Los argumentos de "sv_setpvf" se procesan como "sprintf", y la salida formateada se convierte en el valor.

"sv_vsetpvfn" es un análogo de "vsprintf", pero te permite especificar ya sea un puntero a una lista de argumentos variables o la dirección y longitud de un array de SVs. El último argumento apunta a un booleano; al regresar, si ese booleano es verdadero, entonces se ha utilizado información específica de la configuración regional para formatear la cadena, y por lo tanto el contenido de la cadena no es confiable (ver perlsec). Este puntero puede ser NULL si esa información no es importante. Ten en cuenta que esta función requiere que especifiques la longitud del formato.

Las funciones "sv_set*()" no son lo suficientemente genéricas como para operar sobre valores que tienen "magia". Ver "Magic Virtual Tables" más adelante en este documento.

Todos los SV que contengan cadenas deben estar terminados con un carácter "NUL". Si no está terminado con "NUL", existe el riesgo de caídas del núcleo y corrupciones por código que pasa la cadena a funciones C o llamadas al sistema que esperan una cadena terminada en "NUL". Las propias funciones de Perl típicamente agregan un "NUL" final por esta razón. Sin embargo, debes tener mucho cuidado cuando pasas una cadena almacenada en un SV a una función C o llamada al sistema.

Para acceder al valor real al que apunta un SV, la API de Perl expone varias macros que fuerzan el tipo escalar real a IV, UV, doble o cadena:

  • SvIV(SV*) ("IV") y SvUV(SV*) ("UV")
  • SvNV(SV*) ("double")
  • Las cadenas son un poco complicadas:
  • Cadena de bytes: "SvPVbyte(SV*, STRLEN len)" o SvPVbyte_nolen(SV*)

    Si la cadena de Perl es "\xff\xff", esto devuelve una cadena de 2 bytes (un PV*) que representa esos dos bytes. Si la cadena de Perl es "Müller", este valor se devuelve como una cadena de 8 bytes que incluye esos caracteres multibyte. El parámetro len se establece a la longitud de la cadena devuelta.

    Las cadenas de bytes son útiles cuando no te importa realmente el valor de los caracteres, pero sí su valor crudo. Esto incluye los casos en los que no quieres que Perl intente interpretar o manipular caracteres multibyte o caracteres no ASCII. Por ejemplo, cuando se trabaja con datos binarios, se debe usar SvPVbyte.

  • Cadena de anchos: "SvPVutf8(SV*, STRLEN len)" o SvPVutf8_nolen(SV*)

    Si la cadena de Perl es "Müller", esto devuelve una cadena de 7 caracteres (un PV*) que representa esa cadena como UTF-8.

    Las cadenas de ancho son útiles cuando quieres que Perl trabaje con cadenas como secuencias de caracteres de ancho completo (puntos de código Unicode) en lugar de secuencias de bytes. Por ejemplo, cuando se trabaja con texto de usuario, se debe usar SvPVutf8.

A veces, querrás poder obtener la cadena y su longitud sin preocuparte de si está codificada en bytes o en UTF-8, por ejemplo, si solo la vas a imprimir sin más manipulación. En esos casos, puedes usar SvPV(SV*, STRLEN len). El comportamiento de SvPV es el mismo que SvPVbyte, excepto que si la cadena se encuentra en UTF-8, se convierte primero en una cadena de bytes. Ten en cuenta que SvPV siempre te devolverá la longitud en bytes. SvPV_nolen(SV*) devuelve la cadena sin establecer la longitud.

Tenga en cuenta que al obtener una cadena de un SV, no debe asumir que la cadena está terminada en NUL. Las cadenas de Perl no están necesariamente terminadas en NUL; es solo una convención que la mayoría de las rutinas de Perl siguen. Si necesita una cadena terminada en NUL, deberá crearla usted mismo. Por ejemplo:

char *str = SvPVdup_nocontext(sv, STRLEN len);
char *nul_str = safemalloc(len + 1);
memcpy(nul_str, str, len);
nul_str[len] = '\0';

Para liberar la memoria asignada por SvPVdup_nocontext, use Safefree().

Hay muchas más rutinas para manipular SVs, la mayoría de las cuales están documentadas en "SV Handling" en perlapi. Por ejemplo, hay rutinas para ver el tipo de un SV (`SvTYPE`), para ver si un SV está vacío (`sv_is_empty`), para obtener el número de referencias (`sv_refcount`), etc.

Acceso a AVs

Un AV (array value) es una secuencia ordenada de SVs. Perl gestiona los arrays dinámicamente, por lo que pueden crecer o encogerse según sea necesario. Para crear un AV nuevo, use:

AV*  newAV();

Para agregar un SV al final de un AV, use:

void  av_push(AV* av, SV* sv);

Para obtener el SV en un índice particular de un AV, use:

SV*  av_fetch(AV* av, IV index, bool croak_on_undef);

Si croak_on_undef es verdadero, la función generará un error si el índice está fuera de rango. Si es falso, devolverá NULL.

Para establecer el SV en un índice particular de un AV, use:

void  av_store(AV* av, IV index, SV* sv);

Si el índice está fuera de rango, el array se extenderá para acomodarlo, llenando las nuevas ranuras con undef. Si el índice ya existe, el SV existente se reemplazará y se decrementará su recuento de referencias.

Para obtener la longitud de un AV, use:

IV  av_len(AV* av);

Esto devuelve el índice del último elemento del array. El número de elementos es av_len(av) + 1.

Para eliminar el último elemento de un AV, use:

SV*  av_pop(AV* av);

Esto devuelve el SV eliminado.

Hay muchas más rutinas para manipular AVs, la mayoría de las cuales están documentadas en "Array Handling" en perlapi.

Acceso a HVs

Un HV (hash value) es una colección de pares clave-valor. Las claves siempre son cadenas, y los valores son SVs. Perl gestiona los hashes dinámicamente. Para crear un HV nuevo, use:

HV*  newHV();

Para insertar un par clave-valor en un HV, use:

SV*  hv_store(HV* hv, const char* key, STRLEN keylen, SV* value, U32 hash);

El argumento hash es el valor hash de la clave. Si lo establece a 0, Perl calculará el hash por usted. Si el par clave-valor ya existe, el valor existente se reemplazará y su recuento de referencias se decrementará.

Para recuperar un valor de un HV, use:

SV*  hv_fetch(HV* hv, const char* key, STRLEN keylen, bool croak_on_undef);

Si croak_on_undef es verdadero, la función generará un error si la clave no se encuentra. Si es falso, devolverá NULL.

Para iterar sobre los elementos de un HV, use:

void  hv_iterinit(HV* hv);
char* hv_iternext(HV* hv, STRLEN* keylen, U32* hash);

hv_iterinit inicializa el iterador para el HV especificado. hv_iternext devuelve la siguiente clave en el iterador, y opcionalmente establece *keylen a la longitud de la clave. Devuelve NULL cuando no quedan más elementos.

Para obtener el número de elementos en un HV, use:

IV  hv_len(HV* hv);

Hay muchas más rutinas para manipular HVs, la mayoría de las cuales están documentadas en "Hash Handling" en perlapi.

Internos de Perl

Si estás escribiendo código C que interactúa con Perl (por ejemplo, escribiendo módulos C o interactuando directamente con el intérprete de Perl), necesitarás una comprensión básica de cómo Perl almacena y manipula datos internamente.

Aquí hay algunos conceptos clave:

  • Recuento de referencias: Perl utiliza el recuento de referencias para gestionar la memoria. Cada SV, AV y HV tiene un recuento de referencias que indica cuántas variables apuntan a él. Cuando el recuento de referencias de un objeto cae a cero, Perl libera la memoria asignada a ese objeto. Debe tener cuidado de incrementar el recuento de referencias cuando cree una nueva referencia a un objeto y disminuirlo cuando una referencia ya no sea necesaria.
  • Contexto: Las operaciones de Perl a menudo dependen del contexto en el que se ejecutan. Por ejemplo, una llamada a una función que devuelve un array se comportará de manera diferente si se llama en un contexto escalar (donde solo se devuelve el primer elemento) o en un contexto de lista (donde se devuelve el array completo).
  • Magia: Perl tiene un mecanismo llamado "magia" que permite adjuntar información adicional o comportamiento a SVs, AVs y HVs. Por ejemplo, la magia se utiliza para implementar variables especiales como $_ y $!, así como para sobrecargar operadores.

Para obtener información más detallada sobre los internos de Perl, consulte el archivo EXTERN.h en el código fuente de Perl y la documentación en línea de la API de Perl.

For accessing the contents of an "SV*" as a C string, you have three main options:

  • Byte string: "SvPVbyte(SV*, STRLEN len)" or SvPVbyte_nolen(SV*)

    This is suitable for Perl strings that represent bytes.

  • UTF-8 string: "SvPVutf8(SV*, STRLEN len)" or SvPVutf8_nolen(SV*)

    If the Perl string is "\xff\xff", then this returns a 4-byte "char*".

    This is suitable for Perl strings that represent characters.

    CAVEAT: That "char*" will be encoded via Perl's internal UTF-8 variant, which means that if the SV contains non-Unicode code points (e.g., 0x110000), then the result may contain extensions over valid UTF-8. See "is_strict_utf8_string" in perlapi for some methods Perl gives you to check the UTF-8 validity of these macros' returns.

  • You can also use "SvPV(SV*, STRLEN len)" or SvPV_nolen(SV*) to fetch the SV's raw internal buffer. This is tricky, though; if your Perl string is "\xff\xff", then depending on the SV's internal encoding you might get back a 2-byte OR a 4-byte "char*". Moreover, if it's the 4-byte string, that could come from either Perl "\xff\xff" stored UTF-8 encoded, or Perl "\xc3\xbf\xc3\xbf" stored as raw octets. To differentiate between these you MUST look up the SV's UTF8 bit (cf. "SvUTF8") to know whether the source Perl string is 2 characters ("SvUTF8" would be on) or 4 characters ("SvUTF8" would be off).

    IMPORTANT: Use of "SvPV", "SvPV_nolen", or similarly-named macros without looking up the SV's UTF8 bit is almost certainly a bug if non-ASCII input is allowed.

    When the UTF8 bit is on, the same CAVEAT about UTF-8 validity applies here as for "SvPVutf8".

(See "How do I pass a Perl string to a C library?" for more details.)

In "SvPVbyte", "SvPVutf8", and "SvPV", the length of the "char*" returned is placed into the variable "len" (these are macros, so you do not use &len). If you do not care what the length of the data is, use "SvPVbyte_nolen", "SvPVutf8_nolen", or "SvPV_nolen" instead. The global variable "PL_na" can also be given to "SvPVbyte"/"SvPVutf8"/"SvPV" in this case. But that can be quite inefficient because "PL_na" must be accessed in thread-local storage in threaded Perl. In any case, remember that Perl allows arbitrary strings of data that may both contain NULs and might not be terminated by a "NUL".

Also remember that C doesn't allow you to safely say "foo(SvPVbyte(s, len), len);". It might work with your compiler, but it won't work for everyone. Break this sort of statement up into separate assignments:

SV *s;
STRLEN len;
char *ptr;
ptr = SvPVbyte(s, len);
foo(ptr, len);

If you want to know if the scalar value is TRUE, you can use:

SvTRUE(SV*)

Although Perl will automatically grow strings for you, if you need to force Perl to allocate more memory for your SV, you can use the macro

SvGROW(SV*, STRLEN newlen)

which will determine if more memory needs to be allocated. If so, it will call the function "sv_grow". Note that "SvGROW" can only increase, not decrease, the allocated memory of an SV and that it does not automatically add space for the trailing "NUL" byte (perl's own string functions typically do "SvGROW(sv, len + 1)").

If you want to write to an existing SV's buffer and set its value to a string, use SvPVbyte_force() or one of its variants to force the SV to be a PV. This will remove any of various types of non-stringness from the SV while preserving the content of the SV in the PV. This can be used, for example, to append data from an API function to a buffer without extra copying:

(void)SvPVbyte_force(sv, len);
s = SvGROW(sv, len + needlen + 1);
/* something that modifies up to needlen bytes at s+len, but
   modifies newlen bytes
     eg. newlen = read(fd, s + len, needlen);
   ignoring errors for these examples
 */
s[len + newlen] = '\0';
SvCUR_set(sv, len + newlen);
SvUTF8_off(sv);
SvSETMAGIC(sv);

If you already have the data in memory or if you want to keep your code simple, you can use one of the sv_cat*() variants, such as sv_catpvn(). If you want to insert anywhere in the string you can use sv_insert() or sv_insert_flags().

If you don't need the existing content of the SV, you can avoid some copying with:

SvPVCLEAR(sv);
s = SvGROW(sv, needlen + 1);
/* something that modifies up to needlen bytes at s, but modifies
   newlen bytes
     eg. newlen = read(fd, s, needlen);
 */
s[newlen] = '\0';
SvCUR_set(sv, newlen);
SvPOK_only(sv); /* also clears SVf_UTF8 */
SvSETMAGIC(sv);

Again, if you already have the data in memory or want to avoid the complexity of the above, you can use sv_setpvn().

If you have a buffer allocated with Newx() and want to set that as the SV's value, you can use sv_usepvn_flags(). That has some requirements if you want to avoid perl re-allocating the buffer to fit the trailing NUL:

Newx(buf, somesize+1, char);
/* ... fill in buf ... */
buf[somesize] = '\0';
sv_usepvn_flags(sv, buf, somesize, SV_SMAGIC | SV_HAS_TRAILING_NUL);
/* buf now belongs to perl, don't release it */

If you have an SV and want to know what kind of data Perl thinks is stored in it, you can use the following macros to check the type of SV you have.

SvIOK(SV*)
SvNOK(SV*)
SvPOK(SV*)

Be aware that retrieving the numeric value of an SV can set IOK or NOK on that SV, even when the SV started as a string. Prior to Perl 5.36.0 retrieving the string value of an integer could set POK, but this can no longer occur. From 5.36.0 this can be used to distinguish the original representation of an SV and is intended to make life simpler for serializers:

/* references handled elsewhere */
if (SvIsBOOL(sv)) {
    /* originally boolean */
    ...
}
else if (SvPOK(sv)) {
    /* originally a string */
    ...
}
else if (SvNIOK(sv)) {
    /* originally numeric */
    ...
}
else {
    /* something special or undef */
}

You can get and set the current length of the string stored in an SV with the following macros:

SvCUR(SV*)
SvCUR_set(SV*, I32 val)

You can also get a pointer to the end of the string stored in the SV with the macro:

SvEND(SV*)

But note that these last three macros are valid only if SvPOK() is true.

If you want to append something to the end of string stored in an "SV*", you can use the following functions:

void  sv_catpv(SV*, const char*);
void  sv_catpvn(SV*, const char*, STRLEN);
void  sv_catpvf(SV*, const char*, ...);
void  sv_vcatpvfn(SV*, const char*, STRLEN, va_list *, SV **,
                                                         I32, bool);
void  sv_catsv(SV*, SV*);

The first function calculates the length of the string to be appended by using "strlen". In the second, you specify the length of the string yourself. The third function processes its arguments like "sprintf" and appends the formatted output. The fourth function works like "vsprintf". You can specify the address and length of an array of SVs instead of the va_list argument. The fifth function extends the string stored in the first SV with the string stored in the second SV. It also forces the second SV to be interpreted as a string.

The "sv_cat*()" functions are not generic enough to operate on values that have "magic". See "Magic Virtual Tables" later in this document.

If you know the name of a scalar variable, you can get a pointer to its SV by using the following:

SV*  get_sv("package::varname", 0);

This returns NULL if the variable does not exist.

If you want to know if this variable (or any other SV) is actually "defined", you can call:

SvOK(SV*)

The scalar "undef" value is stored in an SV instance called "PL_sv_undef".

Its address can be used whenever an "SV*" is needed. Make sure that you don't try to compare a random sv with &PL_sv_undef. For example when interfacing Perl code, it'll work correctly for:

foo(undef);

But won't work when called as:

$x = undef;
foo($x);

So to repeat always use SvOK() to check whether an sv is defined.

Also you have to be careful when using &PL_sv_undef as a value in AVs or HVs (see "AVs, HVs and undefined values").

There are also the two values "PL_sv_yes" and "PL_sv_no", which contain boolean TRUE and FALSE values, respectively. Like "PL_sv_undef", their addresses can be used whenever an "SV*" is needed.

Do not be fooled into thinking that "(SV *) 0" is the same as &PL_sv_undef. Take this code:

SV* sv = (SV*) 0;
if (I-am-to-return-a-real-value) {
        sv = sv_2mortal(newSViv(42));
}
sv_setsv(ST(0), sv);

This code tries to return a new SV (which contains the value 42) if it should return a real value, or undef otherwise. Instead it has returned a NULL pointer which, somewhere down the line, will cause a segmentation violation, bus error, or just weird results. Change the zero to &PL_sv_undef in the first line and all will be well.

Offsets

Perl proporciona la función "sv_chop" para eliminar eficientemente caracteres del principio de una cadena; le das una SV y un puntero a algún lugar dentro de la PV, y descarta todo lo que está antes del puntero. La eficiencia proviene de un pequeño truco: en lugar de eliminar realmente los caracteres, "sv_chop" establece la bandera "OOK" (offset OK) para señalar a otras funciones que el truco del offset está en efecto, y mueve el puntero PV (llamado "SvPVX") hacia adelante por el número de bytes recortados, y ajusta "SvCUR" y "SvLEN" en consecuencia. (Una parte del espacio entre los punteros PV antiguo y nuevo se utiliza para almacenar el recuento de bytes recortados).

Por lo tanto, en este punto, el inicio del búfer que asignamos reside en "SvPVX(sv) - SvIV(sv)" en memoria y el puntero PV apunta al medio de este almacenamiento asignado.

Esto se demuestra mejor con un ejemplo. Normalmente, la copia en escritura (copy-on-write) evitará que la sustitución del operador utilice este truco, pero si puedes crear una cadena para la cual la copia en escritura no sea posible, puedes verla en acción. En la implementación actual, el último byte del búfer de una cadena se utiliza como contador de referencias de copia en escritura. Si el búfer no es lo suficientemente grande, la copia en escritura se omite. Primero, eche un vistazo a una cadena vacía:

% ./perl -Ilib -MDevel::Peek -le '$a=""; $a .= ""; Dump $a'
SV = PV(0x7ffb7c008a70) at 0x7ffb7c030390
  REFCNT = 1
  FLAGS = (POK,pPOK)
  PV = 0x7ffb7bc05b50 ""\0
  CUR = 0
  LEN = 10

Observe aquí que LEN es 10. (Puede variar en su plataforma). Extienda la longitud de la cadena a uno menos que 10, y haga una sustitución:

% ./perl -Ilib -MDevel::Peek -le '$a=""; $a.="123456789"; $a=~s/.//; \
                                                           Dump($a)'
SV = PV(0x7ffa04008a70) at 0x7ffa04030390
  REFCNT = 1
  FLAGS = (POK,OOK,pPOK)
  OFFSET = 1
  PV = 0x7ffa03c05b61 ( "\1" . ) "23456789"\0
  CUR = 8
  LEN = 9

Aquí, el número de bytes recortados (1) se muestra a continuación como OFFSET. La porción de la cadena entre el principio "real" y el principio "falso" se muestra entre paréntesis, y los valores de "SvCUR" y "SvLEN" reflejan el principio falso, no el real. (El primer carácter del búfer de cadena ha cambiado a "\1" en lugar de "1" aquí, porque la implementación actual almacena el recuento de desplazamiento en el búfer de cadena. Esto está sujeto a cambios).

Algo similar al truco de desplazamiento se realiza en los AV para permitir el desplazamiento y el empalme eficientes del principio de la matriz; mientras que "AvARRAY" apunta al primer elemento de la matriz visible desde Perl, "AvALLOC" apunta al inicio real del arreglo C. Estos suelen ser los mismos, pero una operación de "shift" se puede realizar aumentando "AvARRAY" en uno y disminuyendo "AvFILL" y "AvMAX". Nuevamente, la ubicación del inicio real del arreglo C solo entra en juego al liberar la matriz. Ver "av_shift" en av.c.

¿Qué se almacena realmente en una SV?

Recuerde que el método habitual para determinar el tipo de escalar que tiene es usar las macros "Sv*OK". Debido a que un escalar puede ser tanto un número como una cadena, normalmente estas macros siempre devuelven TRUE y llamar a las macros "Sv*V" realizará la conversión apropiada de cadena a entero/doble o entero/doble a cadena.

Si *realmente* necesita saber si tiene un puntero a entero, doble o cadena en una SV, puede usar las siguientes tres macros en su lugar:

SvIOKp(SV*)
SvNOKp(SV*)
SvPOKp(SV*)

Estas le dirán si realmente tiene un entero, doble o puntero de cadena almacenado en su SV. La "p" significa privado.

Hay varias maneras en que las banderas privadas y públicas pueden diferir. Por ejemplo, en perl 5.16 y anteriores, una SV enlazada puede tener un valor subyacente válido en la ranura IV (por lo que SvIOKp es verdadero), pero los datos deben accederse a través de la rutina FETCH en lugar de directamente, por lo que SvIOK es falso. (En perl 5.18 y posteriores, los escalares enlazados utilizan las banderas de la misma manera que los escalares no enlazados). Otro caso es cuando se ha producido una conversión numérica y se ha perdido precisión: solo la bandera privada se establece en valores 'con pérdida'. Por lo tanto, cuando un NV se convierte en un IV con pérdida, SvIOKp, SvNOKp y SvNOK se establecerán, mientras que SvIOK no lo hará.

En general, sin embargo, es mejor usar las macros "Sv*V".

Valores de Solo Lectura

En Perl 5.16 y anteriores, la copia en escritura (ver la siguiente sección) compartía un bit de bandera con los escalares de solo lectura. Por lo tanto, la única forma de probar si "sv_setsv", etc., generará un error de "Modificación de un valor de solo lectura" en esas versiones es:

SvREADONLY(sv) && !SvIsCOW(sv)

En Perl 5.18 y posteriores, SvREADONLY solo se aplica a variables de solo lectura, y, en la versión 5.20, los escalares de copia en escritura también pueden ser de solo lectura, por lo que la verificación anterior es incorrecta. Solo desea:

SvREADONLY(sv)

Si necesita realizar esta verificación con frecuencia, defina su propia macro de la siguiente manera:

#if PERL_VERSION >= 18
# define SvTRULYREADONLY(sv) SvREADONLY(sv)
#else
# define SvTRULYREADONLY(sv) (SvREADONLY(sv) && !SvIsCOW(sv))
#endif

O mejor aún, lea sobre las macros THINKFIRST a continuación.

Copia en Escritura

Perl implementa un mecanismo de copia en escritura (COW) para escalares, en el que las copias de cadenas no se realizan inmediatamente cuando se solicitan, sino que se posponen hasta que una u otra cadena cambie y lo haga necesario. Esto es mayormente transparente, pero hay que tener cuidado de no modificar los búferes de cadena que son compartidos por múltiples SVs.

Puede probar si una SV está utilizando copia en escritura con SvIsCOW(sv).

Puede forzar a una SV a hacer su propia copia de su búfer de cadena llamando a sv_force_normal(sv) o SvPV_force_nolen(sv).

Si desea que la SV elimine su búfer de cadena, use "sv_force_normal_flags(sv, SV_COW_DROP_PV)" o simplemente "sv_setsv(sv, NULL)".

Todas estas funciones generarán un error en escalares de solo lectura (ver la sección anterior para más detalles sobre ellos).

Para probar que su código se está comportando correctamente y no está modificando búferes COW, en sistemas que admiten mmap(2) (por ejemplo, Unix, Linux, BSDs, macOS) puede configurar perl con "-Accflags=-DPERL_DEBUG_READONLY_COW" y convertirá las violaciones de búfer en bloqueos. Encontrará que es maravillosamente lento, por lo que es posible que desee omitir las propias pruebas de perl.

PIENSE PRIMERO antes de escribir en un búfer de cadena

Es más probable que vea (y normalmente *debería* ver) la macro SvTHINKFIRST(sv) utilizada para verificar si una SV está lista para ser escrita, ya que esta es una comprobación única combinada para ver si la SV:

  • Apunta a un búfer COW
  • Es READONLY
  • Contiene una referencia
  • Tiene alguna magia relevante asignada

Dos macros relacionadas se pueden usar para realizar esas verificaciones y, si es necesario, también realizar alguna acción:

  • SV_CHECK_THINKFIRST(sv) llama a sv_force_normal(sv) para copiar el búfer de cadena, convirtiéndolo en una cadena mutable.
  • SV_CHECK_THINKFIRST_COW_DROP(sv) llama a "sv_force_normal_flags(sv, SV_COW_DROP_PV)", que elimina cualquier búfer de cadena apuntado por "sv". Esto se usa generalmente para evitar copiar cualquier cadena COW a un nuevo búfer, antes de escribir una cadena completamente nueva en "sv".
Trabajando con AVs

Hay dos formas principales y antiguas de crear y cargar un AV. El primer método crea un AV vacío:

AV*  newAV();

El segundo método crea el AV y lo puebla inicialmente con SVs:

AV*  av_make(SSize_t num, SV **ptr);

El segundo argumento apunta a una matriz que contiene "num" "SV*". Una vez que el AV ha sido creado, las SVs pueden ser destruidas, si se desea.

Perl v5.36 agregó dos nuevas formas de crear un AV y asignar una matriz SV** sin poblarla. Estas son más eficientes que un newAV() seguido de un av_extend().

/* Crea pero no inicializa (cero) la matriz SV** */

/* Crea e inicializa (cero) la matriz SV** */

El argumento numérico se refiere al número de elementos de matriz a asignar, no a un índice de matriz, y debe ser >0. La primera forma solo debe usarse cuando todos los elementos se inicializarán antes de que ocurra cualquier lectura. Leer una SV* no inicializada, es decir, tratar una dirección de memoria aleatoria como una SV*, es un error grave.

AVs, HVs y valores indefinidos

A veces tienes que almacenar valores indefinidos en AVs o HVs. Aunque este puede ser un caso raro, puede ser complicado. Esto se debe a que estás acostumbrado a usar &PL_sv_undef si necesitas un SV indefinido.

Por ejemplo, la intuición te dice que este código XS:

AV *av = newAV();
av_store( av, 0, &PL_sv_undef );

es equivalente a este código Perl:

my @av;
$av[0] = undef;

Desafortunadamente, esto no es cierto. En perl 5.18 y anteriores, los AVs usan &PL_sv_undef como marcador para indicar que un elemento del array aún no se ha inicializado. Por lo tanto, "exists $av[0]" sería verdadero para el código Perl anterior, pero falso para el array generado por el código XS. En perl 5.20, almacenar &PL_sv_undef creará un elemento de solo lectura, ya que se almacena el escalar &PL_sv_undef, no una copia.

Problemas similares pueden ocurrir al almacenar &PL_sv_undef en HVs:

hv_store( hv, "key", 3, &PL_sv_undef, 0 );

Esto hará que el valor sea "undef", pero si intentas modificar el valor de "key", obtendrás el siguiente error:

Modification of non-creatable hash value attempted

En perl 5.8.0, &PL_sv_undef también se usaba para marcar marcadores de posición en hashes restringidos. Esto causó que dichas entradas de hash no aparecieran al iterar sobre el hash o al verificar las claves con la función "hv_exists".

Puedes encontrarte con problemas similares cuando almacenas &PL_sv_yes o &PL_sv_no en AVs o HVs. Intentar modificar tales elementos te dará el siguiente error:

Modification of a read-only value attempted

En resumen, puedes usar las variables especiales &PL_sv_undef, &PL_sv_yes y &PL_sv_no con AVs y HVs, pero debes asegurarte de saber lo que estás haciendo.

En general, si deseas almacenar un valor indefinido en un AV o HV, no debes usar &PL_sv_undef, sino crear un nuevo valor indefinido usando la función "newSV", por ejemplo:

av_store( av, 42, newSV(0) );
hv_store( hv, "foo", 3, newSV(0), 0 );

Referencias

Las referencias son un tipo especial de escalar que apunta a otros tipos de datos (incluyendo otras referencias).

Para crear una referencia, usa cualquiera de las siguientes funciones:

SV* newRV_inc((SV*) thing);
SV* newRV_noinc((SV*) thing);

El argumento "thing" puede ser cualquiera de un "SV*", "AV*" o "HV*". Las funciones son idénticas excepto que "newRV_inc" incrementa el contador de referencias de "thing", mientras que "newRV_noinc" no lo hace. Por razones históricas, "newRV" es un sinónimo de "newRV_inc".

Una vez que tienes una referencia, puedes usar la siguiente macro para desreferenciar la referencia:

SvRV(SV*)

luego llamar a las rutinas apropiadas, convirtiendo el "SV*" devuelto a un "AV*" o "HV*", si es necesario.

Para determinar si un SV es una referencia, puedes usar la siguiente macro:

SvROK(SV*)

Para descubrir a qué tipo de valor se refiere la referencia, usa la siguiente macro y luego verifica el valor de retorno.

SvTYPE(SvRV(SV*))

Los tipos más útiles que se devolverán son:

SVt_PVAV    Array
SVt_PVHV    Hash
SVt_PVCV    Código
SVt_PVGV    Glob (posiblemente un manejador de archivos)

Cualquier valor numérico devuelto que sea menor que SVt_PVAV será un escalar de alguna forma.

Consulta "svtype" en perlapi para más detalles.

Referencias bendecidas y objetos de clase

Las referencias también se utilizan para soportar la programación orientada a objetos. En el léxico de OO de Perl, un objeto es simplemente una referencia que ha sido bendecida en un paquete (o clase). Una vez bendecido, el programador puede usar la referencia para acceder a los diversos métodos de la clase.

Una referencia puede ser bendecida en un paquete con la siguiente función:

SV* sv_bless(SV* sv, HV* stash);

El argumento "sv" debe ser un valor de referencia. El argumento "stash" especifica a qué clase pertenecerá la referencia. Consulta "Stashes and Globs" para obtener información sobre cómo convertir nombres de clase en stashes.

/* Todavía en construcción */

La siguiente función actualiza rv a referencia si aún no lo es. Crea un nuevo SV al que apuntará rv. Si "classname" no es nulo, el SV se bendice en la clase especificada. Se devuelve SV.

SV* newSVrv(SV* rv, const char* classname);

Las siguientes tres funciones copian un entero, un entero sin signo o un doble en un SV cuya referencia es "rv". El SV se bendice si "classname" no es nulo.

SV* sv_setref_iv(SV* rv, const char* classname, IV iv);
SV* sv_setref_uv(SV* rv, const char* classname, UV uv);
SV* sv_setref_nv(SV* rv, const char* classname, NV iv);

La siguiente función copia el valor del puntero (¡la dirección, no la cadena!) en un SV cuya referencia es rv. El SV se bendice si "classname" no es nulo.

SV* sv_setref_pv(SV* rv, const char* classname, void* pv);

La siguiente función copia una cadena en un SV cuya referencia es "rv". Establece la longitud a 0 para que Perl calcule la longitud de la cadena. El SV se bendice si "classname" no es nulo.

SV* sv_setref_pvn(SV* rv, const char* classname, char* pv,
                                                     STRLEN length);

La siguiente función comprueba si el SV está bendecido en la clase especificada. No comprueba las relaciones de herencia.

int  sv_isa(SV* sv, const char* name);

La siguiente función comprueba si el SV es una referencia a un objeto bendecido.

int  sv_isobject(SV* sv);

La siguiente función comprueba si el SV se deriva de la clase especificada. SV puede ser una referencia a un objeto bendecido o una cadena que contiene un nombre de clase. Esta es la función que implementa la funcionalidad de "UNIVERSAL::isa".

bool sv_derived_from(SV* sv, const char* name);

Para comprobar si tienes un objeto derivado de una clase específica, tienes que escribir:

if (sv_isobject(sv) && sv_derived_from(sv, class)) { ... }

Creación de nuevas variables

Para crear una nueva variable Perl con un valor indefinido al que se pueda acceder desde tu script Perl, usa las siguientes rutinas, dependiendo del tipo de variable.

SV*  get_sv("package::varname", GV_ADD);

Contadores de referencias y mortalidad

Perl utiliza un mecanismo de recolección de basura impulsado por el contador de referencias. Los SVs, AVs o HVs (xV en adelante en el siguiente texto) comienzan su vida con un contador de referencias de 1. Si el contador de referencias de un xV llega a 0, entonces será destruido y su memoria se pondrá a disposición para su reutilización. En el nivel interno más básico, los contadores de referencias se pueden manipular con las siguientes macros:

int SvREFCNT(SV* sv);
SV* SvREFCNT_inc(SV* sv);
void SvREFCNT_dec(SV* sv);

(También existen versiones con sufijos de las macros de incremento y decremento, para situaciones en las que la generalidad completa de estas macros básicas puede ser intercambiada por algo de rendimiento.)

Sin embargo, la forma en que un programador debe pensar sobre las referencias no es tanto en términos del contador de referencias desnudo, sino en términos de la *posesión* de referencias. Una referencia a un xV puede ser poseída por cualquiera de una variedad de entidades: otro xV, el intérprete de Perl, una estructura de datos XS, una pieza de código en ejecución o un ámbito dinámico. Un xV generalmente no sabe qué entidades poseen las referencias a él; solo sabe cuántas referencias hay, que es el contador de referencias.

Referencias y Propiedad

El código XS está manipulando. El programador debe saber siempre de dónde proviene una referencia y quién la posee, y ser consciente de cualquier creación o destrucción de referencias, y de cualquier transferencia de propiedad. Debido a que la propiedad no está representada explícitamente en las estructuras de datos de xV, solo el contador de referencias debe ser realmente mantenido por el código, y eso significa que esta comprensión de la propiedad no es realmente evidente en el código. Por ejemplo, transferir la propiedad de una referencia de un propietario a otro no cambia el contador de referencias en absoluto, por lo que puede lograrse con código real. (El código de transferencia no toca el objeto referenciado, pero sí necesita asegurar que el antiguo propietario sepa que ya no posee la referencia, y que el nuevo propietario sepa que ahora sí la posee).

Un xV que es visible a nivel de Perl no debe quedar sin referencia y, por lo tanto, ser destruido. Normalmente, un objeto solo quedará sin referencia cuando ya no sea visible, a menudo por los mismos medios que lo hacen invisible. Por ejemplo, un valor de referencia de Perl (RV) posee una referencia a su referenciado, por lo que si el RV se sobrescribe, esa referencia se destruye y el referenciado, que ya no es alcanzable, puede destruirse como resultado.

Muchas funciones tienen algún tipo de manipulación de referencias como parte de su propósito. A veces esto se documenta en términos de propiedad de referencias, y a veces se documenta (menos útilmente) en términos de cambios en los contadores de referencias. Por ejemplo, la función newRV_inc() se documenta como que crea un nuevo RV (con contador de referencias 1) e incrementa el contador de referencias del referenciado que fue proporcionado por el llamador. Esto se entiende mejor como la creación de una nueva referencia al referenciado, que es propiedad del RV creado, y la devolución al llamador de la propiedad de la única referencia al RV. La función newRV_noinc(), en cambio, no incrementa el contador de referencias del referenciado, pero el RV, sin embargo, termina poseyendo una referencia al referenciado. Por lo tanto, se implica que el llamador de newRV_noinc() está renunciando a una referencia al referenciado, lo que hace que esto sea conceptualmente una operación más complicada aunque haga menos a las estructuras de datos.

Por ejemplo, imagina que quieres devolver una referencia desde una función XSUB. Dentro de la rutina XSUB, creas un SV que inicialmente tiene solo una referencia, propiedad de la rutina XSUB. Esta referencia debe ser desechada antes de que la rutina se complete, de lo contrario tendrá fugas, impidiendo que el SV sea destruido alguna vez. Así que para crear un RV que haga referencia al SV, es más conveniente pasar el SV a newRV_noinc(), que consume esa referencia. Ahora la rutina XSUB ya no posee una referencia al SV, sino que posee una referencia al RV, que a su vez posee una referencia al SV. La propiedad de la referencia al RV se transfiere por el proceso de devolver el RV desde la XSUB.

Hay algunas funciones de conveniencia disponibles que pueden ayudar con la destrucción de xVs. Estas funciones introducen el concepto de "mortalidad". Mucha documentación habla de que un xV en sí mismo es mortal, pero esto es engañoso. En realidad, es *una referencia a* un xV lo que es mortal, y es posible que haya más de una referencia mortal a un solo xV. Que una referencia sea mortal significa que es propiedad de la pila de temporales, una de las muchas pilas internas de Perl, que destruirá esa referencia "un poco más tarde". Normalmente, el "un poco más tarde" es el final de la declaración de Perl actual. Sin embargo, se vuelve más complicado alrededor de los ámbitos dinámicos: puede haber varios conjuntos de referencias mortales rondando al mismo tiempo, con diferentes fechas de caducidad. Internamente, el determinante real de cuándo se destruyen las referencias mortales de xV depende de dos macros, SAVETMPS y FREETMPS. Consulte perlcall y perlxs y "Pila de Temporales" a continuación para obtener más detalles sobre estas macros.

Las referencias mortales se utilizan principalmente para xVs que se colocan en la pila principal de Perl. La pila es problemática para el seguimiento de referencias, porque contiene muchas referencias de xV, pero no posee esas referencias: no se cuentan. Actualmente, hay muchos errores que resultan de la destrucción de xVs mientras son referenciados por la pila, porque las referencias no contadas de la pila no son suficientes para mantener vivos los xVs. Por lo tanto, al colocar una referencia (no contada) en la pila, es de vital importancia asegurarse de que habrá una referencia contada a la misma xV que dure al menos tanto como la referencia no contada. Pero también es importante que esa referencia contada se limpie en un momento apropiado y no prolongue indebidamente la vida del xV. Tener una referencia mortal es a menudo la mejor manera de satisfacer este requisito, especialmente si el xV fue creado especialmente para ser colocado en la pila y de lo contrario quedaría sin referencia.

Para crear una referencia mortal, use las funciones:

SV*  sv_newmortal()
SV*  sv_mortalcopy(SV*)
SV*  sv_2mortal(SV*)

sv_newmortal() crea un SV (con el valor indefinido) cuya única referencia es mortal. sv_mortalcopy() crea un xV cuyo valor es una copia de un xV suministrado y cuya única referencia es mortal. sv_2mortal() hace mortal una referencia de xV existente: transfiere la propiedad de una referencia del llamador a la pila de temporales. Debido a que "sv_newmortal" no le da valor al nuevo SV, normalmente debe dársele uno a través de "sv_setpv", "sv_setiv", etc.:

SV *tmp = sv_newmortal();
sv_setiv(tmp, an_integer);

Dado que son múltiples declaraciones de C, es muy común ver este modismo en su lugar:

SV *tmp = sv_2mortal(newSViv(an_integer));

Las rutinas mortales no son solo para SVs; los AVs y HVs pueden hacerse mortales pasando su dirección (convertida a "SV*") a las rutinas "sv_2mortal" o "sv_mortalcopy".

SV*  sv_bless(SV*, HV* stash)

Al igual que los AVs y HVs, los objetos IO son otro tipo de SV no escalar que puede contener objetos PerlIO de entrada y salida o un "DIR *" de opendir().

A diferencia de otros SVs, un nuevo objeto IO se "bendice" (blessed) automáticamente en la clase IO::File.

SCALAR VARIABLES

A scalar variable (SV) is a generic data type that can hold any single scalar value. Perl internally uses a union to store the value, so a scalar can hold a floating-point number, an integer, or a string. If a scalar is not holding a value, it is considered to be undefined. A scalar variable can also be in a state where it has more than one type of scalar data, see Forcing Multiple Data Values.

Access to SVs is normally done through the Perl interpreter's public API (which is documented in perlguts and perlapi). Here we will briefly describe the various ways in which an SV can hold data.

Scalar Types

A scalar variable can contain any of the following types of data:

Integer
An integer value. You can retrieve this using SvIV(). It is marked as valid by SvIOK().
Floating-point
A floating-point value. You can retrieve this using SvNV(). It is marked as valid by SvNTOK().
String
A character string. You can retrieve this using SvPV() or SvPVX(). It is marked as valid by SvPOK().
Undefined
An undefined scalar. It is marked as valid by SvUVOK(). (No, that's not a typo. This is the way it is currently implemented.)

The macros SvIOK_on(), SvNTOK_on(), and SvPOK_on() can be used to turn on the appropriate bits. For example, to turn on the integer flag, you would use SvIOK_on(sv).

The macros SvIOK_off(), SvNTOK_off(), and SvPOK_off() can be used to turn off the appropriate bits.

Use sv_setiv(), sv_setnv(), and sv_setpv() to set the value and type of an SV.

sv_setsv() can be used to copy the value from one SV to another. Note that this does not duplicate the string data if the destination is a string.

sv_usepvn() and sv_usepv() are similar to sv_setpv(), but they do not make a copy of the string data. The SV will point to the original string data. This is generally only safe if the original string data is guaranteed to remain valid for the lifetime of the SV.

sv_catpv() and sv_catpvn() can be used to append a string to the existing string in an SV. If the SV is not already a string, it will be converted to one.

Forcing Multiple Data Values

Some scalar variables contain more than one type of scalar data. For example, the variable $! contains either the numeric value of "errno" or its string equivalent from either "strerror" or "sys_errlist[]".

To force multiple data values into an SV, you must do two things: use the "sv_set*v" routines to add the additional scalar type, then set a flag so that Perl will believe it contains more than one type of data. The four macros to set the flags are:

SvIOK_on
SvNOK_on
SvPOK_on
SvROK_on

The particular macro you must use depends on which "sv_set*v" routine you called first. This is because every "sv_set*v" routine turns on only the bit for the particular type of data being set, and turns off all the rest.

For example, to create a new Perl variable called "dberror" that contains both the numeric and descriptive string error values, you could use the following code:

extern int  dberror;
extern char *dberror_list;
SV* sv = get_sv("dberror", GV_ADD);
sv_setiv(sv, (IV) dberror);
sv_setpv(sv, dberror_list[dberror]);
SvIOK_on(sv);

If the order of "sv_setiv" and "sv_setpv" had been reversed, then the macro "SvPOK_on" would need to be called instead of "SvIOK_on".

Any SV may be magical, that is, it has special features that a normal SV does not have. These features are stored in the SV structure in a linked list of "struct magic"'s, typedef'ed to "MAGIC".

    U8          mg_flags;
    I32         mg_len;
    SV*         mg_obj;
    char*       mg_ptr;
};

Note this is current as of patchlevel 0, and could change at any time.

Assigning Magic

Perl adds magic to an SV using the sv_magic function:

void sv_magic(SV* sv, SV* obj, int how, const char* name, I32 namlen);

The "sv" argument is a pointer to the SV that is to acquire a new magical feature.

If "sv" is not already magical, Perl uses the "SvUPGRADE" macro to convert "sv" to type "SVt_PVMG". Perl then continues by adding new magic to the beginning of the linked list of magical features. Any prior entry of the same type of magic is deleted. Note that this can be overridden, and multiple instances of the same type of magic can be associated with an SV.

The "name" and "namlen" arguments are used to associate a string with the magic, typically the name of a variable. "namlen" is stored in the "mg_len" field and if "name" is non-null then either a "savepvn" copy of "name" or "name" itself is stored in the "mg_ptr" field, depending on whether "namlen" is greater than zero or equal to zero respectively. As a special case, if "(name && namlen == HEf_SVKEY)" then "name" is assumed to contain an "SV*" and is stored as-is with its REFCNT incremented.

The sv_magic function uses "how" to determine which, if any, predefined "Magic Virtual Table" should be assigned to the "mg_virtual" field. See the "Magic Virtual Tables" section below. The "how" argument is also stored in the "mg_type" field. The value of "how" should be chosen from the set of macros "PERL_MAGIC_foo" found in perl.h. Note that before these macros were added, Perl internals used to directly use character literals, so you may occasionally come across old code or documentation referring to 'U' magic rather than "PERL_MAGIC_uvar" for example.

The "obj" argument is stored in the "mg_obj" field of the "MAGIC" structure. If it is not the same as the "sv" argument, the reference count of the "obj" object is incremented. If it is the same, or if the "how" argument is "PERL_MAGIC_arylen", "PERL_MAGIC_regdatum", "PERL_MAGIC_regdata", or if it is a NULL pointer, then "obj" is merely stored, without the reference count being incremented.

See also "sv_magicext" in perlapi for a more flexible way to add magic to an SV.

There is also a function to add magic to an "HV":

void hv_magic(HV *hv, GV *gv, int how);

This simply calls "sv_magic" and coerces the "gv" argument into an "SV".

To remove the magic from an SV, call the function sv_unmagic:

int sv_unmagic(SV *sv, int type);

The "type" argument should be equal to the "how" value when the "SV" was initially made magical.

However, note that "sv_unmagic" removes all magic of a certain "type" from the "SV". If you want to remove only certain magic of a "type" based on the magic virtual table, use "sv_unmagicext" instead:

int sv_unmagicext(SV *sv, int type, MGVTBL *vtbl);

Localización de cambios

Perl tiene una construcción muy útil

{
  local $var = 2;
  ...
}

Esta construcción es *aproximadamente* equivalente a

{
  my $oldvar = $var;
  $var = 2;
  ...
  $var = $oldvar;
}

La principal diferencia es que la primera construcción restablecería el valor inicial de $var, independientemente de cómo salga el control del bloque: "goto", "return", "die"/"eval", etc. También es un poco más eficiente.

Hay una manera de lograr una tarea similar desde C a través de la API de Perl: crear un *pseudobloque*, y organizar que algunos cambios se deshagan automáticamente al final de él, ya sea explícitamente, o mediante una salida no local (a través de die()). Una construcción similar a un *bloque* se crea mediante un par de macros "ENTER"/"LEAVE" (ver "Returning a Scalar" en perlcall). Dicha construcción puede crearse especialmente para alguna tarea localizada importante, o se puede utilizar una existente (como los límites de la subrutina/bloque de Perl envolvente, o un par existente para liberar TMP). (En el segundo caso, la sobrecarga de la localización adicional debe ser casi insignificante). Tenga en cuenta que cualquier XSUB está automáticamente encerrado en un par "ENTER"/"LEAVE".

Estas macros organizan la restauración del valor de los punteros "s" y "p". "s" debe ser un puntero de un tipo que sobreviva a la conversión a "SV*" y de vuelta, "p" debe poder sobrevivir a la conversión a "char*" y de vuelta.

Esta macro organiza la restauración del valor de una variable "char *" que fue asignada con una llamada a rcpv_new() a su estado anterior cuando se completa el pseudobloque actual. El puntero almacenado en *ppv en el momento de la llamada se incrementará en el recuento de referencias y se almacenará en la pila de guardado. XSUBs y la Pila de Argumentos

El mecanismo XSUB es una forma sencilla para que los programas Perl accedan a subrutinas C. Una rutina XSUB tendrá una pila que contiene los argumentos del programa Perl y una forma de mapear las estructuras de datos de Perl a un equivalente C.

Los argumentos de la pila son accesibles a través de la macro ST(n), que devuelve el argumento de pila "n". El argumento 0 es el primer argumento pasado en la llamada a la subrutina Perl. Estos argumentos son "SV*", y pueden usarse en cualquier lugar donde se use un "SV*".

La mayoría de las veces, la salida de la rutina C se puede manejar mediante el uso de las directivas RETVAL y OUTPUT. Sin embargo, hay algunos casos en los que la pila de argumentos aún no es lo suficientemente larga para manejar todos los valores de retorno. Un ejemplo es la llamada a tzname() de POSIX, que no toma argumentos, pero devuelve dos: las abreviaturas de la zona horaria local estándar y de horario de verano.

Para manejar esta situación, se utiliza la directiva PPCODE y la pila se extiende usando la macro:

EXTEND(SP, num);

donde "SP" es la macro que representa la copia local del puntero de pila, y "num" es el número de elementos por los que se debe extender la pila.

Ahora que hay espacio en la pila, los valores se pueden agregar a ella usando la macro "PUSHs". Los valores agregados a menudo necesitarán ser "mortales" (Ver "Recuento de referencias y mortalidad"):

PUSHs(sv_2mortal(newSViv(an_integer)))
PUSHs(sv_2mortal(newSVuv(an_unsigned_integer)))
PUSHs(sv_2mortal(newSVnv(a_double)))
PUSHs(sv_2mortal(newSVpv("Some String",0)))
/* Aunque el último ejemplo se escribe mejor como el más
 * eficiente: */
PUSHs(newSVpvs_flags("Some String", SVs_TEMP))

Y ahora el programa Perl que llama a "tzname", los dos valores se asignarán como en:

($standard_abbrev, $summer_abbrev) = POSIX::tzname;

Un método alternativo (y posiblemente más simple) para agregar valores a la pila es usar la macro:

XPUSHs(SV*)

Esta macro ajusta automáticamente la pila por usted, si es necesario. Por lo tanto, no necesita llamar a "EXTEND" para extender la pila.

A pesar de sus sugerencias en versiones anteriores de este documento, las macros "(X)PUSH[iunp]" no son adecuadas para XSUBs que devuelven múltiples resultados. Para eso, quédese con las macros "(X)PUSHs" que se muestran arriba, o use las nuevas macros "m(X)PUSH[iunp]" en su lugar; consulte "Poner un valor C en la pila de Perl".

Para más información, consulte perlxs y perlxstut.

Autoloading con XSUBs

Si una rutina AUTOLOAD es una XSUB, al igual que con las subrutinas Perl, Perl coloca el nombre completamente calificado de la subrutina cargada automáticamente en la variable $AUTOLOAD del paquete de la XSUB.

Pero también coloca la misma información en ciertos campos de la propia XSUB:

HV *stash           = CvSTASH(cv);
const char *subname = SvPVX(cv);
STRLEN name_length  = SvCUR(cv); /* en bytes */
U32 is_utf8         = SvUTF8(cv);

SvPVX(cv) contiene solo el nombre de la subrutina, sin incluir el paquete. Para una rutina AUTOLOAD en UNIVERSAL o en una de sus superclases, CvSTASH(cv) devuelve NULL durante una llamada a método en un paquete inexistente.

Nota: Establecer $AUTOLOAD dejó de funcionar en 5.6.1, que no soportaba subrutinas AUTOLOAD XS en absoluto. Perl 5.8.0 introdujo el uso de campos en la propia XSUB. Perl 5.16.0 restauró el establecimiento de $AUTOLOAD. Si necesita soportar 5.8-5.14, use los campos de la XSUB.

Stack d'arguments

Il existe un certain nombre de macros pour accéder et manipuler la pile d'arguments. La plupart d'entre elles sont des wrappers autour de "sv_2mortal()" et de "PUSHs". Elles sont là pour la commodité et l'efficacité. Vous devriez les utiliser autant que possible.

Toutes les macros qui manipulent la pile d'arguments font la distinction entre les arguments qui sont des références à des SV et ceux qui sont des valeurs brutes. Les références aux SVs sont traitées comme des pointeurs "SV*", et les valeurs brutes sont traitées comme des valeurs C ordinaires. La raison pour laquelle nous faisons cette distinction est que le coût de la création d'un SV mortel à partir d'une valeur brute est significativement plus élevé que le coût de la poussée d'un SV existant sur la pile.

Les macros qui poussent des valeurs brutes sont les suivantes :

XPUSHs(value)
XPUSHii(value)
XPUSHiu(value)
XPUSHup(value)
XPUSHpp(value)

Où "value" est une valeur C (par exemple, un entier, un flottant, etc.). Notez que "XPUSHs" pousse un "SV*" et les autres poussent des valeurs C et les convertissent en SVs mortels avant de les pousser sur la pile. "XPUSHs" n'a pas besoin que "TARG" soit défini, mais les autres ont besoin de "TARG" pour créer et initialiser le nouvel SV.

Les macros qui poussent des références aux SVs sont les suivantes :

XPUSHs(sv)

Où "sv" est un "SV*". Notez que "XPUSHs" est la seule macro qui peut pousser un "SV*" sur la pile. Les autres macros poussent des valeurs C et les convertissent en SVs mortels avant de les pousser sur la pile.

Pour pousser plusieurs valeurs différentes, vous devriez soit utiliser les macros "(X)PUSHs", soit utiliser les nouvelles macros "m(X)PUSH[iunp]", dont aucune n'utilise "TARG". Les macros "(X)PUSHs" poussent simplement un "SV*" sur la pile, qui, comme indiqué dans "XSUBs et la pile d'arguments", devra souvent être "mortel". Les nouvelles macros "m(X)PUSH[iunp]" rendent cela un peu plus facile à réaliser en créant un nouveau mortel pour vous (via "(X)PUSHmortal"), en le poussant sur la pile (en l'étendant si nécessaire dans le cas des macros "mXPUSH[iunp]"), puis en définissant sa valeur. Ainsi, au lieu d'écrire ceci pour "corriger" l'exemple ci-dessus :

XPUSHs(sv_2mortal(newSViv(10)))
XPUSHs(sv_2mortal(newSViv(20)))

vous pouvez simplement écrire :

mXPUSHi(10)
mXPUSHi(20)

Dans un ordre d'idées connexe, si vous utilisez "(X)PUSH[iunp]", alors vous aurez besoin d'un "dTARG" dans vos déclarations de variables afin que les macros "*PUSH*" puissent utiliser la variable locale "TARG". Voir aussi "dTARGET" et "dXSTARG".

Soyez prudent avec TARG : chaque appel non récursif à votre OP, ou XSUB pour dXSTARG, utilisera le même SV pour TARG à chaque appel, vous ne pouvez donc pas supposer que le SV est vierge car les résultats de l'appel précédent à votre OP ou XSUB peuvent toujours être dans TARG.

D'autres états tels qu'une version numérique mise en cache d'un PV ou la longueur UTF-8 mise en cache peuvent également être définis. Vous pouvez éviter les problèmes avec cela en utilisant les API sv_set*() normales au lieu d'essayer d'optimiser en manipulant directement le SV.

Pour les OPs qui implémentent l'optimisation "OA_TARGLEX", TARG peut être spécial d'autres manières, il peut y avoir des références à celui-ci, il peut être béni, lié ou magique d'autres manières.

Vous ne devez pas utiliser TARG pour renvoyer une référence, car cette référence sera active jusqu'à la prochaine fois que l'OP ou l'XSUB s'exécutera de manière non récursive, ou jusqu'à la sortie de Perl.

Scratchpads

La question demeure sur le moment où les SV qui sont des cibles pour les opcodes sont créés. La réponse est qu'ils sont créés lorsque l'unité actuelle - une sous-routine ou un fichier (pour les opcodes des instructions en dehors des sous-routines) - est compilée. Pendant ce temps, un tableau Perl anonyme spécial est créé, appelé scratchpad pour l'unité actuelle.

Un scratchpad conserve les SV qui sont des léxicaux pour l'unité actuelle et qui sont des cibles pour les opcodes. Une version précédente de ce document indiquait qu'on pouvait déduire qu'un SV réside dans un scratchpad en regardant ses indicateurs : les léxicaux ont "SVs_PADMY" défini, et les cibles ont "SVs_PADTMP" défini. Mais cela n'a jamais été entièrement vrai. "SVs_PADMY" pouvait être défini sur une variable qui ne résidait plus dans aucun pad. Bien que les cibles aient "SVs_PADTMP" défini, il peut également être défini sur des variables qui n'ont jamais résidé dans un pad, mais qui agissent néanmoins comme des cibles. Depuis la version 5.21.5 de Perl, l'indicateur "SVs_PADMY" n'est plus utilisé et est défini comme 0. SvPADMY() renvoie maintenant vrai pour tout ce qui n'a pas "SVs_PADTMP".

La correspondance entre les OPs et les cibles n'est pas de 1 pour 1. Différents OPs dans l'arbre de compilation de l'unité peuvent utiliser la même cible, si cela ne conflictait pas avec la durée de vie attendue du temporaire.

Scratchpads et récursion

En fait, il n'est pas vrai à 100% qu'une unité compilée contienne un pointeur vers le tableau AV du scratchpad. En fait, il contient un pointeur vers un tableau AV de (initialement) un élément, et cet élément est le tableau AV du scratchpad. Pourquoi avons-nous besoin d'un niveau d'indirection supplémentaire ?

La réponse est la **récursion**, et peut-être les **threads**. Ces deux éléments peuvent créer plusieurs pointeurs d'exécution pointant vers la même sous-routine. Pour que l'enfant de la sous-routine n'écrasent pas les temporaires du parent de la sous-routine (dont la durée de vie couvre l'appel à l'enfant), le parent et l'enfant devraient avoir des scratchpads différents. (Et les léxicaux devraient être séparés de toute façon !)

Ainsi, chaque sous-routine naît avec un tableau de scratchpads (de longueur 1). À chaque entrée dans la sous-routine, on vérifie que la profondeur actuelle de la récursion n'est pas supérieure à la longueur de ce tableau, et si c'est le cas, un nouveau scratchpad est créé et poussé dans le tableau.

Les cibles sur ce scratchpad sont des "undef", mais elles sont déjà marquées avec les bons indicateurs.

Allocation de mémoire

Allocation

Toute mémoire destinée à être utilisée avec les fonctions de l'API Perl doit être manipulée à l'aide des macros décrites dans cette section. Les macros fournissent la transparence nécessaire entre les différences dans l'implémentation réelle de malloc utilisée dans Perl. Ne passez jamais de pointeurs entre "Newx", "Renew", "Safefree" et les équivalents de libc "malloc", "realloc", "free". Ils ne proviennent pas du même pool de mémoire ou allocateur. Une arrestation immédiate ou différée provoquera une SEGV, ou des fuites de mémoire subtiles ou une corruption subtile du tas.

Les trois macros suivantes sont utilisées pour allouer initialement de la mémoire :

Newx(pointer, number, type);
Newxc(pointer, number, type, cast);
Newxz(pointer, number, type);

Le premier argument "pointer" doit être le nom d'une variable qui pointera vers la mémoire nouvellement allouée.

Les deuxième et troisième arguments "number" et "type" spécifient combien d'instances du type de structure de données spécifié doivent être allouées. L'argument "type" est passé à "sizeof". Le dernier argument de "Newxc", "cast", doit être utilisé si l'argument "pointer" est différent de l'argument "type".

Contrairement aux macros "Newx" et "Newxc", la macro "Newxz" appelle "memzero" pour mettre à zéro toute la mémoire nouvellement allouée.

Réallocation

Renew(pointer, number, type);
Renewc(pointer, number, type, cast);
Safefree(pointer)

Ces trois macros sont utilisées pour modifier la taille d'un tampon de mémoire ou pour libérer une partie de la mémoire qui n'est plus nécessaire. Les arguments de "Renew" et "Renewc" correspondent à ceux de "New" et "Newc", à l'exception de ne pas avoir besoin de l'argument « magic cookie ».

Déplacement

Move(source, dest, number, type);
Copy(source, dest, number, type);
Zero(dest, number, type);

Ces trois macros sont utilisées pour déplacer, copier ou mettre à zéro de la mémoire précédemment allouée. Les arguments "source" et "dest" pointent vers les points de départ de la source et de la destination. Perl déplacera, copiera ou mettra à zéro "number" instances de la taille de la structure de données de "type" (en utilisant la fonction "sizeof").

Arbre de code

Ici, nous décrivons la forme interne à laquelle votre code est converti par Perl. Commençons par un exemple simple :

Ceci est converti en un arbre similaire à celui-ci :

       assign-to
     /           \
    +             $a
  /   \
$b     $c

(mais légèrement plus compliqué). Cet arbre reflète la façon dont Perl a analysé votre code, mais n'a rien à voir avec l'ordre d'exécution. $b ---> $c ---> + ---> $a ---> assign-to

Cómo se admiten múltiples intérpretes y la concurrencia

Antecedentes y MULTIPLICIDAD

El intérprete de Perl puede considerarse una caja cerrada: tiene una API para alimentarle código o hacer que haga cosas de alguna otra manera, pero también tiene funciones para su propio uso. Esto huele mucho a un objeto, y hay una forma de construir Perl para que pueda tener múltiples intérpretes, con un intérprete representado ya sea como una estructura C, o dentro de una estructura específica de hilo. Estas estructuras contienen todo el contexto, el estado de ese intérprete.

La macro que controla el sabor principal de la compilación de Perl es MULTIPLICITY. La compilación MULTIPLICITY tiene una estructura C que empaqueta todo el estado del intérprete, que se pasa a varias funciones de Perl como un primer argumento "oculto". MULTIPLICITY hace posibles las Perl multihilo (con el modelo de hilos ithreads, relacionado con la macro USE_ITHREADS.)

PERL_IMPLICIT_CONTEXT es un sinónimo obsoleto de MULTIPLICITY.

Para ver si tiene datos no constantes puede usar un "nm" compatible con BSD (o GNU):

nm libperl.a | grep -v ' [TURtr] '

Si esto muestra algún símbolo "D" o "d" (o posiblemente "C" o "c"), tiene datos no constantes. Los símbolos que el "grep" eliminó son los siguientes: "Tt" son texto, o código, los "Rr" son datos de solo lectura (constantes), y la "U" es <indefinido>, símbolos externos referenciados.

La prueba t/porting/libperl.t realiza este tipo de verificación de consistencia de símbolos en "libperl.a".

Todo esto obviamente requiere una forma para que las funciones internas de Perl sean subrutinas que tomen algún tipo de estructura como primer argumento, o subrutinas que no tomen nada como primer argumento. Para habilitar estas dos formas muy diferentes de compilar el intérprete, el código fuente de Perl (como lo hace en tantas otras situaciones) hace un uso intensivo de macros y convenciones de nombres de subrutinas.

Primer problema: decidir qué funciones serán funciones de API pública y cuáles serán privadas. Todas las funciones cuyos nombres comienzan con "S_" son privadas (piense en "S" como "secreto" o "estático"). Todas las demás funciones comienzan con "Perl_", pero el hecho de que una función comience con "Perl_" no significa que sea parte de la API. (Ver "Funciones Internas".) Cuando Perl se compila sin opciones que establezcan MULTIPLICITY, no hay un primer argumento que contenga el contexto del intérprete. El guión bajo final en la macro pTHX_ indica que la expansión de la macro necesita una coma después del argumento de contexto porque le siguen otros argumentos. Si MULTIPLICITY no está definido, pTHX_ se ignorará, y la subrutina no estará prototipada para tomar el argumento adicional. El Argumento de Contexto

Este documento describe el argumento de contexto de Perl. Si no está familiarizado con él, no se preocupe. A menos que esté escribiendo código C que interactúa con Perl (ya sea desde el núcleo de Perl o desde una extensión), puede ignorarlo casi por completo.

¿Qué es?

En la época en que Perl se compilaba con el modelo de hilos opcional (MULTIPLICITY), tuvo que encontrar una manera de pasar un puntero al intérprete de Perl actual a todas las funciones de la API de Perl. Este puntero se conoce como el context. En C, se pasa como el primer argumento a la mayoría de las funciones de la API de Perl. Por ejemplo, la función sv_setiv es en realidad Perl_sv_setiv y se llama como:

Perl_sv_setiv(aTHX_ sv, iv);

donde aTHX_ es una macro que representa el puntero de contexto.

Afortunadamente, para las extensiones, no tiene que preocuparse por pasar este argumento usted mismo. La macro XS() se encarga de ello. Las funciones que no son XSUBs (es decir, las funciones que se llaman directamente desde C) pueden usar la macro dTHX para obtener el contexto.

Cuando Perl se compila sin MULTIPLICITY, las funciones de la API no toman este argumento adicional. Por ejemplo, sv_setiv se llama como:

sv_setiv(sv, iv);

Sin embargo, debe escribir su código de extensión de tal manera que compile independientemente de si MULTIPLICITY está habilitado o no. Esto se logra mediante el uso de macros.

Cuando Perl se compila con MULTIPLICITY, el archivo de cabecera XSUB.h redefine las macros aTHX y aTHX_ para llamar a la función Perl_get_context() y obtener el contexto. Por lo tanto, puede escribir:

sv_setiv(foo, bar);

y seguirá funcionando tanto si Perl se compila con MULTIPLICITY como si no.

Esto no funciona tan bien para las funciones de varargs, ya que las macros implican que el número de argumentos se conoce de antemano. En su lugar, tenemos que escribirlas completamente, pasando "aTHX_" como el primer argumento (el núcleo de Perl tiende a hacer esto con funciones como Perl_warner), o usar una versión contextual.

La versión contextual de Perl_warner se llama Perl_warner_nocontext, y no toma el argumento adicional. En su lugar, hace "dTHX;" para obtener el contexto del almacenamiento local del hilo. Nosotros "#define warner Perl_warner_nocontext" para que las extensiones obtengan compatibilidad de código fuente a expensas del rendimiento. (Pasar un argumento es más barato que obtenerlo del almacenamiento local del hilo.)

Puede ignorar [pad]THXx al navegar por las cabeceras/fuentes de Perl. Estos son estrictamente para uso dentro del núcleo. Las extensiones y los incrustadores solo necesitan ser conscientes de [pad]THX.

Entonces, ¿qué pasó con dTHR?

"dTHR" se introdujo en perl 5.005 para dar soporte al modelo de hilos antiguo. El modelo de hilos antiguo ahora utiliza el mecanismo "THX" para pasar punteros de contexto, por lo que "dTHR" ya no es útil. Perl 5.6.0 y posteriores todavía lo tienen para compatibilidad de código fuente anterior, pero está definido como una operación nula.

¿Cómo uso todo esto en extensiones?

Vea también "Dealing with embedded perls and threads" en perlclib.

Lo complicado es que necesitará escribirlo de tal manera que la extensión siga compilando cuando Perl no se haya compilado con MULTIPLICITY habilitado.

¿Debo hacer algo especial si llamo a perl desde múltiples hilos?

Si crea intérpretes en un hilo y luego procede a llamarlos en otro, debe asegurarse de que la ranura de Almacenamiento Local del Hilo (TLS) de Perl esté inicializada correctamente en cada uno de esos hilos.

Las funciones de la API "perl_alloc" y "perl_clone" establecerán automáticamente la ranura TLS al intérprete que crearon, por lo que no es necesario hacer nada especial siempre que el intérprete se acceda en el mismo hilo que lo creó, y ese hilo no creó ni llamó a ningún otro intérprete después. Si no es así, tiene que establecer la ranura TLS del hilo antes de llamar a cualquier función de la API de Perl en ese intérprete en particular. Esto se hace llamando a la macro "PERL_SET_CONTEXT" en ese hilo como la primera cosa que hace:

/* haz esto antes de hacer cualquier otra cosa con some_perl */
PERL_SET_CONTEXT(some_perl);
... otras llamadas a la API de Perl en some_perl van aquí ...

(Siempre puede obtener el contexto actual a través de "PERL_GET_CONTEXT".)

Planes Futuros y PERL_IMPLICIT_SYS

Así como MULTIPLICITY proporciona una forma de agrupar todo lo que el intérprete sabe sobre sí mismo y pasarlo, también hay planes para permitir que el intérprete agrupe todo lo que sabe sobre el entorno en el que se está ejecutando. Esto se habilita con la macro PERL_IMPLICIT_SYS. Actualmente, solo funciona con USE_ITHREADS en Windows.

Esto permite la capacidad de proporcionar un puntero adicional (llamado entorno "host") para todas las llamadas al sistema. Esto hace posible que todo el asunto del sistema mantenga su propio estado, desglosado en siete estructuras C. Estos son delgados envoltorios alrededor de las llamadas habituales al sistema (ver win32/perllib.c) para el ejecutable de Perl predeterminado, pero para un host más ambicioso (como el que haría la emulación de fork()), todo el trabajo adicional necesario para pretender que diferentes intérpretes son en realidad diferentes "procesos", se haría aquí.

El motor/intérprete de Perl y el host son entidades ortogonales. Podría haber uno o más intérpretes en un proceso, y uno o más "hosts", con asociación libre entre ellos.

Funciones Internas

Todas las funciones internas de Perl que se expondrán al mundo exterior van precedidas de "Perl_" para que no entren en conflicto con las funciones XS o las funciones utilizadas en un programa en el que Perl está incrustado. Del mismo modo, todas las variables globales comienzan con "PL_". (Por convención, las funciones estáticas comienzan con "S_".)

Dentro del núcleo de Perl ("PERL_CORE" definido), puede acceder a las funciones con o sin el prefijo "Perl_", gracias a un montón de defines que viven en embed.h. Tenga en cuenta que el código de extensión *no* debe establecer "PERL_CORE"; esto expone los internos completos de Perl, y es probable que cause la rotura de XS en cada nueva versión de Perl.

El archivo embed.h se genera automáticamente a partir de embed.pl y embed.fnc. embed.pl también crea los archivos de cabecera de prototipado para las funciones internas, genera la documentación y muchas otras piezas. Es importante que cuando agregue una nueva función al núcleo o modifique una existente, también modifique los datos en la tabla de embed.fnc. Aquí hay una entrada de ejemplo de esa tabla:

Apd |SV**   |av_fetch   |AV* ar|I32 key|I32 lval

La primera columna es un conjunto de flags, la segunda columna el tipo de retorno, la tercera columna el nombre. Las columnas posteriores son los argumentos. Los flags se documentan en la parte superior de embed.fnc.

Si edita embed.pl o embed.fnc, deberá ejecutar "make regen_headers" para forzar una reconstrucción de embed.h y otros archivos generados automáticamente.

Si está imprimiendo IVs, UVs o NVs en lugar de los códigos de formato estilo stdio(3) como %d, %ld, %f, debería usar las siguientes macros para portabilidad

IVdf            IV en decimal
UVuf            UV en decimal
UVof            UV en octal
UVxf            UV en hexadecimal
NVef            NV tipo %e
NVff            NV tipo %f
NVgf            NV tipo %g

Estos se encargarán de los enteros de 64 bits y los dobles largos. Por ejemplo:

printf("IV is %" IVdf "\n", iv);

El "IVdf" se expandirá a lo que sea el formato correcto para los IVs. Tenga en cuenta que los espacios son requeridos alrededor del formato en caso de que el código se compile con C++, para mantener el cumplimiento con su estándar.

Tenga en cuenta que hay diferentes "dobles largos": Perl usará lo que sea que el com

Si está imprimiendo las direcciones de los punteros, use %p o UVxf combinado con PTR2UV().

Impresión formateada de SVs

El contenido de los SVs se puede imprimir usando el formato "SVf", de la siguiente manera:

Perl_croak(aTHX_ "Esto falló porque: %" SVf "\n", SVfARG(err_msg))

donde "err_msg" es un SV.

No todos los tipos de escalares son imprimibles. Los valores simples, ciertamente lo son: uno de IV, UV, NV, o PV. Además, si el SV es una referencia a algún valor, o bien se desreferenciará y se imprimirá el valor, o se mostrará información sobre el tipo de ese valor y su dirección. Los resultados de imprimir cualquier otro tipo de SV no están definidos y probablemente conducirán a un bloqueo del intérprete. Los NV se imprimen usando un formato similar a %g.

Tenga en cuenta que se requieren espacios alrededor de "SVf" en caso de que el código se compile con C++, para mantener la compatibilidad con su estándar.

Tenga en cuenta que cualquier manejador de archivos al que se imprima en modo UTF-8 debe estar esperando UTF-8 para obtener buenos resultados y evitar advertencias de caracteres anchos. Una forma de hacerlo para los manejadores de archivos típicos es invocar Perl con el parámetro "-C". (Ver "-C [número/lista]" en perlrun.

Puede usar esto para concatenar dos escalares:

SV *var2 = get_sv("var2", GV_ADD);
SV *var3 = newSVpvf("var1=%" SVf " y var2=%" SVf,

"SVf_QUOTEDPREFIX" es similar a "SVf" excepto que restringe el número de caracteres impresos, mostrando como máximo los primeros "PERL_QUOTEDPREFIX_LEN" caracteres del argumento, y representándolo con comillas dobles y con el contenido escapado usando las reglas de escape de cadenas entre comillas dobles. Esto está pensado para mensajes de error donde se asume que la cadena es un nombre de clase.

"HvNAMEf" y "HvNAMEf_QUOTEDPREFIX" son similares a "SVf" excepto que extraen la cadena, la longitud y las banderas utf8 del argumento usando las macros HvNAME(), HvNAMELEN(), HvNAMEUTF8(). Esto está pensado para convertir un nombre de clase directamente desde un stash HV a cadena.

Pero si existe la posibilidad de que el valor esté codificado en UTF-8 o contenga bytes por encima de 0x7F (y, por lo tanto, de 8 bits), debería usar en su lugar el formato "UTF8f". Y como parámetro, use la macro UTF8fARG():

chr * msg;
/* U+2018: \xE2\x80\x98 MARCA DE COMILLA SIMPLE IZQUIERDA

if (can_utf8)
  msg = "\xE2\x80\x98Utiliza comillas elegantes\xE2\x80\x99";
else

Perl_croak(aTHX_ "El mensaje es: %" UTF8f "\n",

El primer parámetro de "UTF8fARG" es un booleano: 1 si la cadena está en UTF-8; 0 si la cadena está en codificación de bytes nativa (Latin1). El segundo parámetro es el número de bytes de la cadena a imprimir. Y el tercer y último parámetro es un puntero al primer byte de la cadena.

Puntero-A-Entero y Entero-A-Puntero

Debido a que el tamaño del puntero no es necesariamente igual al tamaño del entero, use las siguientes macros para hacerlo correctamente.

PTR2IV(puntero)
PTR2NV(puntero)

y

Manejo de excepciones

Existen un par de macros para hacer un manejo de excepciones muy básico en módulos XS. Tiene que definir "NO_XSLOCKS" antes de incluir XSUB.h para poder usar estas macros:

#define NO_XSLOCKS
#include "XSUB.h"

Puede usar estas macros si llama a código que puede fallar (croak), pero necesita hacer alguna limpieza antes de devolver el control a Perl. Por ejemplo:

dXCPT;    /* configura las variables necesarias */
XCPT_TRY_START {
  codigo_que_puede_fallar();
} XCPT_TRY_END
XCPT_CATCH
{
  /* hacer limpieza aquí */
  XCPT_RETHROW;
}

Tenga en cuenta que siempre debe volver a lanzar una excepción que ha sido capturada. Usando estas macros, no es posible simplemente capturar la excepción e ignorarla. Si necesita ignorar la excepción, debe usar la función "call_*".

La ventaja de usar las macros anteriores es que no tiene que configurar una función adicional para "call_*", y que el uso de estas macros es más rápido que el uso de "call_*".

Para más detalles, ver "perldoc ppport.h".

Soporte Unicode

Perl 5.6.0 introdujo el soporte Unicode. Es importante para los portadores y escritores de XS comprender este soporte y asegurarse de que el código que escriben no corrompa los datos Unicode.

¿Qué es Unicode, de todas formas?

En los tiempos antiguos, menos ilustrados, todos solíamos usar ASCII. La mayoría de nosotros, de todos modos. El gran problema con ASCII es que es americano. Bueno, no, ese no es realmente el problema; el problema es que no es particularmente útil para las personas que no usan el alfabeto romano. Lo que solía suceder era que idiomas particulares insertaban su propio alfabeto en el rango superior de la secuencia, entre 128 y 255. Por supuesto, luego terminamos con muchas variantes que no eran exactamente ASCII, y se perdió todo el propósito de que fuera un estándar.

Peor aún, si tienes un idioma como el chino o el japonés que tiene cientos o miles de caracteres, entonces realmente no puedes encajarlos en unos escasos 256, por lo que tuvieron que olvidarse de ASCII por completo y construir sus propios sistemas us

ng pares de números para referirse a un carácter.

Para solucionar esto, algunas personas formaron Unicode, Inc. y produjeron un nuevo conjunto de caracteres que contenía todos los caracteres que puedas imaginar y más. Hay varias formas de representar estos caracteres, y la que utiliza Perl se llama UTF-8. UTF-8 utiliza un número variable de bytes para representar un carácter. Puedes aprender más sobre Unicode y el modelo Unicode de Perl en perlunicode.

(En plataformas EBCDIC, Perl usa en su lugar UTF-EBCDIC, que es una forma de UTF-8 adaptada para plataformas EBCDIC. A continuación, solo hablamos de UTF-8. UTF-EBCDIC es como UTF-8, pero los detalles son diferentes. Las macros ocultan las diferencias para ti, solo recuerda que los números y patrones de bits específicos presentados a continuación diferirán en UTF-EBCDIC.)

¿Cómo puedo reconocer una cadena UTF-8?

No puedes. Esto se debe a que los datos UTF-8 se almacenan en bytes al igual que los datos que no son UTF-8. El carácter Unicode 200, (0xC8 para ti, tipos hexadecimales) E mayúscula con acento grave, está representado por los dos bytes "v196.172". Desafortunadamente, la cadena no Unicode "chr(196).chr(172)" tiene esa secuencia de bytes también. Así que no puedes saberlo solo mirándolo; esto es lo que hace que la entrada Unicode sea un problema interesante.

En general, tienes que saber con qué estás tratando o tienes que adivinar. La función de la API "is_utf8_string" puede ayudar; te dirá si una cadena contiene solo caracteres UTF-8 válidos, y las posibilidades de que una cadena que no sea UTF-8 parezca UTF-8 válido se vuelven muy pequeñas muy rápidamente a medida que aumenta la longitud de la cadena. A nivel de carácter individual, "isUTF8_CHAR" te dirá si el carácter actual en una cadena es UTF-8 válido.

¿Cómo representa UTF-8 los caracteres Unicode?

Como se mencionó anteriormente, UTF-8 utiliza un número variable de bytes para almacenar un carácter. Los caracteres con valores 0...127 se almacenan en un byte, al igual que el buen y viejo ASCII. El carácter 128 se almacena como "v194.128"; esto continúa hasta el carácter 191, que es "v194.191". Ahora nos hemos quedado sin bits (191 es binario 10111111), así que pasamos a lo siguiente; el carácter 192 es "v195.128". Y así sucesivamente, pasando a tres bytes en el carácter 2048.     /* Debe tratarse como UTF-8 */

    utf8 = uvchr_to_utf8(utf8, uv);

    /* OK para tratar este carácter como un byte */
    *utf8++ = uv;

Debes convertir los caracteres a UV utilizando las funciones anteriores si alguna vez te encuentras en una situación en la que tengas que comparar caracteres UTF-8 y no UTF-8. No puedes saltarte caracteres UTF-8 en este caso. Si haces esto, perderás la capacidad de comparar caracteres no UTF-8 de alto bit; por ejemplo, si tu cadena UTF-8 contiene "v196.172", y te saltas ese carácter, nunca podrás comparar un chr(200) en una cadena no UTF-8. ¡Así que no hagas eso!

(Nota que no tenemos que probar los caracteres invariantes en los ejemplos anteriores. Las funciones funcionan en cualquier entrada UTF-8 bien formada. Es solo que es más rápido evitar la sobrecarga de la función cuando no es necesaria).

¿Cómo almacena Perl las cadenas UTF-8?

Actualmente, Perl maneja las cadenas UTF-8 y las cadenas no UTF-8 de manera ligeramente diferente. Un indicador en el SV, "SVf_UTF8", indica que la cadena está codificada internamente como UTF-8. Sin él, el valor del byte es el número del punto de código y viceversa. Este indicador solo es significativo si el SV es "SvPOK" o inmediatamente después de la conversión a cadena a través de "SvPV" o una macro similar. Puedes verificar y manipular este indicador con las siguientes macros:

SvUTF8(sv)
SvUTF8_on(sv)
SvUTF8_off(sv)

Este indicador tiene un efecto importante en el tratamiento que Perl le da a la cadena: si los datos UTF-8 no se distinguen correctamente, las expresiones regulares, "length", "substr" y otras operaciones de manejo de cadenas tendrán resultados indeseables (incorrectos).

El problema surge cuando tienes, por ejemplo, una cadena que no está marcada como UTF-8 y contiene una secuencia de bytes que podría ser UTF-8, especialmente al combinar cadenas no UTF-8 y UTF-8.

Nunca olvides que el indicador "SVf_UTF8" está separado del valor PV; necesitas asegurarte de no apagarlo accidentalmente mientras manipulas los SV. Más específicamente, no puedes esperar hacer esto:

SV *sv;
SV *nsv;
STRLEN len;
char *p;
p = SvPV(sv, len);
frobnicate(p);
nsv = newSVpvn(p, len);

La cadena "char*" no te cuenta toda la historia, y no puedes copiar o reconstruir un SV simplemente copiando el valor de la cadena. Verifica si el SV antiguo tiene el indicador UTF8 establecido (después de la llamada a "SvPV"), y actúa en consecuencia:

p = SvPV(sv, len);
is_utf8 = SvUTF8(sv);
frobnicate(p, is_utf8);
nsv = newSVpvn(p, len);
if (is_utf8)
    SvUTF8_on(nsv);

En lo anterior, tu función "frobnicate" ha sido modificada para que sea consciente de si está tratando con datos UTF-8 o no, para que pueda manejar la cadena de manera apropiada.

Dado que simplemente pasar un SV a una función XS y copiar los datos del SV no es suficiente para copiar los indicadores UTF8, menos correcto es simplemente pasar un "char *" a una función XS.

Para una generalidad completa, usa la macro "DO_UTF8" para ver si la cadena en un SV debe ser *tratada* como UTF-8. Esto tiene en cuenta si la llamada a la función XS se realiza dentro del ámbito de "use bytes". Si es así, se deben exponer los bytes subyacentes que componen la cadena UTF-8, en lugar del carácter que representan. Pero este pragma solo debe usarse realmente para depuración y quizás para pruebas de bajo nivel a nivel de bytes. Por lo tanto, la mayoría del código XS no necesita preocuparse por esto, pero varias áreas del núcleo de perl necesitan admitirlo.

Y esto no es toda la historia. A partir de Perl v5.12, las cadenas que no están codificadas en UTF-8 también pueden tratarse como Unicode bajo diversas condiciones (ver "ASCII Rules versus Unicode Rules" en perlunicode). Esto es realmente un problema solo para los caracteres cuyos ordinales están entre 128 y 255, y su comportamiento varía bajo las reglas ASCII frente a Unicode de maneras que a tu código le importan (ver "The "Unicode Bug"" en perlunicode). No hay una API publicada para tratar con esto, ya que está sujeta a cambios, pero puedes mirar el código de "pp_lc" en *pp.c* como ejemplo de cómo se hace actualmente.

¿Cómo paso una cadena de Perl a una biblioteca C?

Una cadena de Perl, conceptualmente, es una secuencia opaca de puntos de código. Muchas bibliotecas C esperan que sus entradas sean cadenas C "clásicas", que son arreglos de octetos 1-255, terminados con un byte NUL. Tu trabajo al escribir una interfaz entre Perl y una biblioteca C es definir el mapeo entre Perl y esa biblioteca.

En términos generales, "SvPVbyte" y macros relacionadas se adaptan bien a esta tarea. Estas asumen que tu cadena de Perl es una "cadena de bytes", es decir, es una entrada cruda y sin decodificar a Perl o está pre-codificada, por ejemplo, en UTF-8.

Alternativamente, si tu biblioteca C espera texto UTF-8, puedes usar "SvPVutf8" y macros relacionadas. Esto tiene el mismo efecto que codificar a UTF-8 y luego llamar a la macro correspondiente relacionada con "SvPVbyte".

Algunas bibliotecas C pueden esperar otras codificaciones (por ejemplo, UTF-16LE). Para pasar cadenas de Perl a tales bibliotecas, debes realizar esa codificación en Perl y luego usar "SvPVbyte", o usar una biblioteca C intermedia para convertir desde como sea que Perl almacene la cadena a la codificación deseada.

Ten cuidado también de que los NUL en tu cadena de Perl no confundan a la biblioteca C. Si es posible, proporciona la longitud de la cadena a la biblioteca C; si eso no es posible, considera rechazar cadenas que contengan bytes NUL.

The final value pushed is stored in the "UV" field which encodes the kind of item held by the preceding items; the count and types of which will depend on what kind of item is being stored. The kind field is pushed last because that will be the first field to be popped when unwinding items from the stack. The base of this stack is pointed to by the interpreter variable "PL_savestack", of type "ANY *". The head of the stack is indexed by "PL_savestack_ix", un entero que almacena el índice en el array en el que se debe agregar el siguiente elemento. (Tenga en cuenta que esto es diferente a la mayoría de las otras pilas, que hacen referencia al elemento agregado más recientemente).

Los elementos se agregan a la pila de guardado utilizando las diversas macros "SAVE...()". Muchas de estas macros toman una variable y almacenan tanto su dirección como su valor actual en la pila de guardado, asegurando que ese valor se restaure al salir del ámbito.

SAVEI8(i8)
SAVEI16(i16)
SAVEI32(i32)
SAVEINT(i)
...

También hay una variedad de otras macros de propósito especial que guardan tipos o valores particulares de interés. "SAVETMPS" ya ha sido mencionado anteriormente. Otros incluyen "SAVEFREEPV" que organiza la liberación de un PV (es decir, un búfer de cadena), o "SAVEDESTRUCTOR" que organiza la invocación de un puntero de función dado al salir del ámbito. Una lista completa de dichas macros se puede encontrar en scope.h.

No hay una API pública para extraer elementos individuales o de la pila de guardado. En cambio, a través de la pila de ámbitos, el par "ENTER" y "LEAVE" forma una manera de iniciar y detener ámbitos anidados. Salir de un ámbito anidado a través de "LEAVE" restaurará todos los valores guardados que se hayan agregado desde la invocación más reciente de "ENTER".

Pila de ámbitos

Al igual que con la pila de marcas de la pila de valores, la pila de ámbitos forma un par con la pila de guardado. La pila de ámbitos almacena la altura de la pila de guardado desde la que comienzan los ámbitos anidados, y permite que la pila de guardado se desenrolle hasta ese punto cuando se sale del ámbito.

Cuando Perl se compila con la depuración habilitada, hay una segunda parte en esta pila que almacena nombres de cadenas legibles por humanos que describen el tipo de contexto de la pila. Cada operación de agregar guarda el nombre y la altura de la pila de guardado, y cada operación de extraer comprueba el nombre superior con lo que se espera, causando un fallo de aserción si el nombre no coincide.

La base de esta pila está apuntada por la variable del intérprete "PL_scopestack", de tipo "I32 *". Si está habilitada, los nombres de la pila de ámbitos se almacenan en un array separado apuntado por "PL_scopestack_name", de tipo "const char **".

La cabeza de la pila está indexada por "PL_scopestack_ix", un entero que almacena el índice del array o arrays en el que se debe agregar el siguiente elemento. (Tenga en cuenta que esto es diferente a la mayoría de las otras pilas, que hacen referencia al elemento agregado más recientemente).

Los valores se agregan a la pila de ámbitos utilizando la macro "ENTER", que inicia un nuevo ámbito anidado. Cualquier elemento agregado a la pila de guardado se restaura luego en la siguiente invocación anidada de la macro "LEAVE".

Ámbito dinámico y la pila de contexto

Nota: esta sección describe una API interna no pública que está sujeta a cambios sin previo aviso.

Introducción a la pila de contexto

En Perl, el ámbito dinámico se refiere a la anidación en tiempo de ejecución de cosas como llamadas a subrutinas, evals, etc., así como la entrada y salida de ámbitos de bloque. Por ejemplo, la restauración de una variable "local"izada está determinada por el ámbito dinámico.

Perl rastrea el ámbito dinámico mediante una estructura de datos llamada pila de contexto, que es un array de estructuras "PERL_CONTEXT", y que a su vez es una gran unión para todos los tipos de contexto. Cada vez que se entra en un nuevo ámbito (como un bloque, un bucle "for" o una llamada a subrutina), se agrega una nueva entrada de contexto a la pila. Del mismo modo, al salir de un bloque o regresar de una llamada a subrutina, etc., se extrae un contexto. Dado que la pila de contexto representa el ámbito dinámico actual, se puede buscar. Por ejemplo, "next LABEL" busca hacia atrás en la pila buscando un contexto de bucle que coincida con la etiqueta; "return" extrae contextos hasta que encuentra un contexto de subrutina o eval o similar; "caller" examina los contextos de subrutina en la pila.

Cada entrada de contexto está etiquetada con un tipo de contexto, "cx_type". Los tipos de contexto típicos son "CXt_SUB", "CXt_EVAL", etc., así como "CXt_BLOCK" y "CXt_NULL" que representan un ámbito básico (tal como se agregó con "pp_enter") y un bloque de orden. El tipo determina qué parte de la unión de contexto son válidas.

La división principal en la estructura de contexto es entre un ámbito de sustitución ("CXt_SUBST") y los ámbitos de bloque, que son todo lo demás. El primero se utiliza solo mientras se ejecuta "s///e", y no se discutirá más aquí.

Todos los tipos de ámbitos de bloque comparten una base común, que corresponde a "CXt_BLOCK". Esto almacena los valores antiguos de varias variables relacionadas con el ámbito, como "PL_curpm", así como información sobre el ámbito actual, como "gimme". Al salir del ámbito, se restauran las variables antiguas.

Los tipos de ámbitos de bloque particulares almacenan información adicional específica del tipo. Por ejemplo, "CXt_SUB" almacena la CV que se está ejecutando actualmente, mientras que los diversos tipos de bucle for pueden contener la variable de bucle original. Al salir del ámbito, se procesan los datos específicos del tipo; por ejemplo, se decrementa el contador de referencias de la CV y se restaura la variable de bucle original.

La macro "cxstack" devuelve la base de la pila de contexto actual, mientras que "cxstack_ix" es el índice del marco actual dentro de esa pila.

De hecho, la pila de contexto es en realidad parte de un sistema de pila de pilas; cada vez que se hace algo inusual, como llamar a un manejador de "DESTROY" o de tie, se agrega una nueva pila, luego se extrae al final.

Tenga en cuenta que la API descrita aquí cambió considerablemente en Perl 5.24; antes de eso, se utilizaban macros grandes como "PUSHBLOCK" y "POPSUB"; en 5.24 fueron reemplazadas por las funciones estáticas en línea descritas a continuación. Además, el orden y el detalle de cómo funcionan estas macros/funciones cambiaron de muchas maneras, a menudo de forma sutil. En particular, no manejaban el guardado de las posiciones de las pilas de guardado y temporales, y requerían "ENTER", "SAVETMPS" y "LEAVE" adicionales en comparación con las nuevas funciones. Las macros de estilo antiguo no se describirán más.

Agregar contextos

Para agregar un nuevo contexto, las dos funciones básicas son "cx = cx_pushblock()", que agrega un nuevo bloque de contexto básico y devuelve su dirección, y una familia de funciones similares con nombres como cx_pushsub(cx) que poblan los campos adicionales dependientes del tipo en la estructura "cx". Tenga en cuenta que "CXt_NULL" y "CXt_BLOCK" no tienen sus propias funciones de agregado, ya que no almacenan ningún dato más allá de lo agregado por "cx_pushblock".

Los campos de la estructura de contexto y los argumentos de las funciones "cx_*" están sujetos a cambios entre las versiones de Perl, representando lo que sea conveniente o eficiente para esa versión.

Una adición típica de pila de contexto se puede encontrar en "pp_entersub"; lo siguiente muestra un ejemplo simplificado y despojado de una llamada que no es XS, junto con comentarios que muestran aproximadamente lo que hace cada función.

dMARK;
U8 gimme      = GIMME_V;
bool hasargs  = cBOOL(PL_op->op_flags & OPf_STACKED);
OP *retop     = PL_op->op_next;
I32 old_ss_ix = PL_savestack_ix;
CV *cv        = ....;
/* ... hacer copias mortales de los argumentos de la pila que son PADTMPs aquí ... */
/* ... hacer cualquier agregado adicional a la pila de guardado aquí ... */
/* Ahora agregar una nueva entrada de contexto de tipo 'CXt_SUB'; inicialmente
 * solo haciendo las acciones comunes a todos los tipos de bloque: */
cx = cx_pushblock(CXt_SUB, gimme, MARK, old_ss_ix);
    /* esto hace (aproximadamente):
        CXINC;              /* cxstack_ix++ (crecer si es necesario) */
        cx = CX_CUR();      /* y obtener la dirección del nuevo marco */
        cx->cx_type        = CXt_SUB;
        cx->blk_gimme      = gimme;
        cx->blk_oldsp      = MARK - PL_stack_base;
        cx->blk_oldsaveix  = old_ss_ix;
        cx->blk_oldcop     = PL_curcop;
        cx->blk_oldmarksp  = PL_markstack_ptr - PL_markstack;
        cx->blk_oldscopesp = PL_scopestack_ix;
        cx->blk_oldpm      = PL_curpm;
        cx->blk_old_tmpsfloor = PL_tmps_floor;
        PL_tmps_floor        = PL_tmps_ix;
    */
/* luego actualizar el nuevo marco de contexto con información específica de la subrutina,
 * como la CV que se va a ejecutar: */
cx_pushsub(cx, cv, retop, hasargs);
    /* esto hace (aproximadamente):
        cx->blk_sub.cv          = cv;
        cx->blk_sub.olddepth    = CvDEPTH(cv);
        cx->blk_sub.prevcomppad = PL_comppad;
        cx->cx_type            |= (hasargs) ? CXp_HASARGS : 0;
        cx->blk_sub.retop       = retop;
        SvREFCNT_inc_simple_void_NN(cv);
    */

Tenga en cuenta que cx_pushblock() establece dos nuevos límites: para la pila de argumentos (a "MARK") y la pila de temporales (a "PL_tmps_ix"). Mientras se ejecuta en este nivel de ámbito, cada "nextstate" (entre otros) restablecerá los niveles de la pila de argumentos y temporales a estos límites. Tenga en cuenta que dado que "cx_pushblock" utiliza el valor actual de "PL_tmps_ix" en lugar de pasarlo como argumento, esto dicta en qué punto se debe llamar a "cx_pushblock". En particular, cualquier mortal nuevo que deba liberarse solo al salir del ámbito (en lugar de en el siguiente "nextstate") debe crearse primero.

Empujar contextos

Los contextos se empujan utilizando cx_pushblock() y sus derivados, como cx_pushfoo(). El propósito principal de cx_pushblock() es establecer un nuevo registro de contexto en el campo cxstack. Se utiliza CX_PUSH() para esto.

El argumento blk_oldsp se inicializa al valor superior de la pila de argumentos que se está empujando en el contexto. Para la mayoría de los tipos de contexto, este es el valor superior del marco de pila anterior. Sin embargo, para CXt_LOOP_LIST, almacena los elementos que se están iterando en la pila y, por lo tanto, establece blk_oldsp en la parte superior de estos elementos en su lugar. Tenga en cuenta que, contrariamente a su nombre, blk_oldsp no siempre representa el valor al que se restaurará PL_stack_sp al salir del ámbito.

Observe la captura temprana de PL_savestack_ix en old_ss_ix, que posteriormente se pasa como argumento a cx_pushblock(). En el caso de pp_entersub, esto se debe a que, aunque la mayoría de los valores que necesitan guardarse se almacenan en campos de la estructura de contexto, solo se necesita guardar un valor adicional cuando el depurador se está ejecutando, y no tiene sentido hinchar la estructura para este caso raro. Por lo tanto, en su lugar, se guarda en la pila de guardado. Dado que este valor se calcula y se guarda antes de que se empuje el contexto, es necesario pasar el valor anterior de PL_savestack_ix a cx_pushblock(), para garantizar que el valor guardado se libere durante la salida del ámbito. Para la mayoría de los usuarios de cx_pushblock(), donde no es necesario empujar nada en la pila de guardado, PL_savestack_ix simplemente se pasa directamente como argumento a cx_pushblock().

Tenga en cuenta que siempre que sea posible, los valores deben guardarse en la estructura de contexto en lugar de en la pila de guardado; es mucho más rápido de esa manera.

Normalmente, cx_pushblock() debe ir seguido inmediatamente por el cx_pushfoo() apropiado, sin nada entre ellos; esto se debe a que si el código intermedio pudiera morir (por ejemplo, una advertencia elevada a fatal), el código de desenrollado de la pila de contexto en dounwind() vería (en el ejemplo anterior) un marco de contexto CXt_SUB, pero sin todos los campos específicos de la subrutina configurados, y pronto se producirían fallos.

Donde los dos deben estar separados, inicialmente establezca el tipo en CXt_NULL o CXt_BLOCK, y más tarde cámbielo a CXt_foo al hacer el cx_pushfoo(). Esto es exactamente lo que hace pp_enteriter(), una vez que se determina qué tipo de bucle está empujando.

Sacar contextos

Los contextos se sacan utilizando cx_popsub(), etc., y cx_popblock(). Tenga en cuenta, sin embargo, que a diferencia de cx_pushblock(), ninguna de estas funciones disminuye realmente el índice de la pila de contexto actual; esto se hace por separado utilizando CX_POP().

Hay dos formas principales en que se sacan los contextos. Durante la ejecución normal, a medida que se salen los ámbitos, funciones como pp_leave, pp_leaveloop y pp_leavesub procesan y sacan un solo contexto utilizando cx_popfoo() y cx_popblock(). Por otro lado, elementos como pp_return y next pueden tener que retroceder varios ámbitos hasta que se encuentre un contexto de sub o de bucle, y las excepciones (como die) necesitan retroceder contextos hasta que se encuentre un contexto de evaluación. Ambas cosas se logran mediante dounwind(), que es capaz de procesar y sacar todos los contextos por encima del objetivo.

Aquí hay un ejemplo típico de extracción de contexto, tal como se encuentra en pp_leavesub (simplificado ligeramente):

U8 gimme;
PERL_CONTEXT *cx;
SV **oldsp;
OP *retop;
cx = CX_CUR();
gimme = cx->blk_gimme;
oldsp = PL_stack_base + cx->blk_oldsp; /* último argumento del marco anterior */
if (gimme == G_VOID)
    PL_stack_sp = oldsp;
else
    leave_adjust_stacks(oldsp, oldsp, gimme, 0);
CX_LEAVE_SCOPE(cx);
cx_popsub(cx);
cx_popblock(cx);
retop = cx->blk_sub.retop;
CX_POP(cx);
return retop;

Los pasos anteriores están en un orden muy específico, diseñado para ser el orden inverso de cuando se empujó el contexto. Lo primero que hay que hacer es copiar y/o proteger cualquier argumento de retorno y liberar cualquier temporal en el ámbito actual. La salida del ámbito, como una subrutina rvalue, normalmente devuelve una copia mortal de sus argumentos de retorno (a diferencia de las subrutinas lvalue). Es importante hacer esta copia antes de que se saque la pila de guardado o se restauren las variables, o pueden ocurrir cosas malas como las siguientes:

sub f { my $x =...; $x }  # $x se libera antes de que lo copiemos
sub f { /(...)/;    $1 }  # PL_curpm se restaura antes de que se copie $1

Aunque deseamos liberar cualquier temporal al mismo tiempo, debemos tener cuidado de no liberar ningún temporal que mantenga vivos los argumentos de retorno; ni liberar los temporales que acabamos de crear al copiar mortalmente los argumentos de retorno. Afortunadamente, leave_adjust_stacks() es capaz de hacer copias mortales de los argumentos de retorno, mover los argumentos hacia abajo en la pila y solo procesar aquellas entradas en la pila de temporales que sean seguras de hacerlo.

En contexto void, no se devuelven argumentos, por lo que es más eficiente omitir la llamada a leave_adjust_stacks(). También en contexto void, es probable que se llame inminentemente a un op nextstate que realizará un FREETMPS, por lo que tampoco es necesario hacerlo.

El siguiente paso es sacar las entradas de la pila de guardado: CX_LEAVE_SCOPE(cx) se define simplemente como LEAVE_SCOPE(cx->blk_oldsaveix). Tenga en cuenta que durante la extracción, es posible que Perl llame a destructores, llame a STORE para deshacer las localizaciones de variables enlazadas, etc. Cualquiera de estas acciones puede fallar o llamar a exit(). En este caso, se llamará a dounwind(), y el marco de contexto actual se reprocesará. Por lo tanto, es vital que todos los pasos en la extracción de un contexto se realicen de manera que admita la reentrada. La otra alternativa, de disminuir cxstack_ix *antes* de procesar el marco, provocaría fugas y similares si algo fallaba a mitad de camino, o la sobrescritura del marco actual.

CX_LEAVE_SCOPE en sí mismo admite reentrada segura: si solo la mitad de los elementos de la pila de guardado se han extraído antes de fallar y ser atrapados por eval, entonces los CX_LEAVE_SCOPE en dounwind() o pp_leaveeval() continuarán desde donde lo dejó el primero.

El siguiente paso es el procesamiento del contexto específico del tipo; en este caso cx_popsub(). En parte, esto se ve así:

cv = cx->blk_sub.cv;
CvDEPTH(cv) = cx->blk_sub.olddepth;
cx->blk_sub.cv = NULL;
SvREFCNT_dec(cv);

donde está procesando la CV recién ejecutada. Tenga en cuenta que antes de disminuir el recuento de referencias de la CV, anula blk_sub.cv. Esto significa que si se vuelve a entrar, la CV no se liberará dos veces. También significa que no puede confiar en que los campos específicos del tipo tengan valores útiles después del retorno de cx_popfoo().

A continuación, cx_popblock() restaura todas las diversas variables del intérprete a sus valores anteriores o marcas de agua anteriores; se expande a:

PL_markstack_ptr = PL_markstack + cx->blk_oldmarksp;
PL_scopestack_ix = cx->blk_oldscopesp;
PL_curpm         = cx->blk_oldpm;
PL_curcop        = cx->blk_oldcop;
PL_tmps_floor    = cx->blk_old_tmpsfloor;

Tenga en cuenta que *no* restaura PL_stack_sp; como se mencionó anteriormente, el valor al que se restaura depende del tipo de contexto (específicamente for (list) {}), y de los argumentos (si los hay) que devuelve; y eso ya se habrá resuelto anteriormente mediante leave_adjust_stacks().

Finalmente, el puntero de la pila de contexto se disminuye realmente mediante CX_POP(cx). Después de este punto, es posible que el marco de contexto actual se sobrescriba con otros contextos que se estén empujando. Aunque se supone que los enlaces y DESTROY funcionan dentro de un nuevo contexto de pila, es mejor no asumir esto. De hecho, en las compilaciones de depuración, CX_POP(cx) establece deliberadamente cx a nulo para detectar código que todavía depende de los valores de los campos en ese marco de contexto. Tenga en cuenta que en el ejemplo de pp_leavesub() anterior, obtenemos blk_sub.retop *antes* de llamar a CX_POP().

Rehaciendo contextos

Finalmente, está cx_topblock(cx), que actúa como un super-nextstate en cuanto a restablecer varias variables a sus valores base. Se utiliza en lugares como pp_next, pp_redo y pp_goto, donde en lugar de salir de un ámbito, queremos reinicializar el ámbito. Además de restablecer PL_stack_sp como nextstate, también restablece PL_markstack_ptr, PL_scopestack_ix y PL_curpm. Tenga en cuenta que no realiza un FREETMPS.

Pila de argumentos de recuento de referencias

Introducción

A partir de Perl 5.40, existe una opción de compilación, PERL_RC_STACK, que no está habilitada por defecto, y que requiere que los elementos que se empujan o sacan de la pila de argumentos tengan sus recuentos de referencias ajustados. La intención es que con el tiempo esta sea la forma predeterminada (y finalmente la única) de configurar Perl.

Las macros que manipulan la pila, como PUSHs() y POPs(), no ajustan el recuento de referencias del SV. La mayoría de las veces esto está bien, ya que algo más mantiene vivo el SV mientras está en la pila de argumentos, como un puntero de la pila TEMPs, o del pad (por ejemplo, una variable léxica o un PADTMP). En la mayoría de los casos

ally esto puede salir terriblemente mal. Por ejemplo, este código:

my @a = (1,2,3);
sub f { @a = (); print "(@_)\n" };
f(@a, 4);

puede imprimir valores indefinidos o liberados aleatoriamente, ya que algunos de los elementos de @_, que han sido alias de los elementos de @a, han sido liberados. "PERL_RC_STACK" está destinado a solucionar esto al hacer que cada puntero SV en la pila de argumentos incremente el contador de referencias (RC) del SV en uno.

En este nuevo entorno, las funciones PP y XS existentes sin modificar, que han sido escritas asumiendo una pila sin conteo de referencias (non-RC para abreviar), se llaman a través de funciones envoltorio especiales que ajustan la pila antes y después. Por el momento, no hay API para escribir una función XS RC, por lo que todo el código XS seguirá llamándose a través de un envoltorio (lo que las hace ligeramente más lentas), pero significa que, en general, las distribuciones CPAN que contienen código XS continúan funcionando sin modificaciones.

Sin embargo, las funciones PP, ya sea en el núcleo de Perl, o las que se encuentran en funciones XS utilizadas para implementar operaciones personalizadas o para anular las funciones PP de operaciones integradas, necesitan un tratamiento especial. Para estas últimas, simplemente se pueden envolver; esto implica el menor trabajo, pero tiene un impacto en el rendimiento. A largo plazo, y para las funciones PP del núcleo, necesitan ser desempaquetadas y reescritas utilizando una nueva API. Con esto, las macros antiguas como PUSHs() han sido reemplazadas por un nuevo conjunto de funciones (en su mayoría en línea) con un prefijo común, como rpp_push_1(). "RPP" significa "funciones de empuje y extracción con conteo de referencias". Las nuevas funciones modifican el contador de referencias en las compilaciones de "PERL_RC_STACK", mientras que las dejan sin ajustar en otros casos. Por lo tanto, en el núcleo, generalmente funcionan en ambos casos, mientras que en el código XS son portátiles a versiones anteriores de Perl a través de "PPPort" (XXX asumiendo que se añaden a "PPPort").

El resto de esta sección se centra principalmente en cómo convertir las funciones PP existentes y cómo escribir nuevas funciones PP para utilizar la nueva API de "rpp_".

Se puede compilar un Perl con conteo de referencias utilizando la definición PERL_RC_STACK. Para fines de desarrollo y depuración, es mejor habilitar también la depuración de fugas de escalares, ya que esto muestra información adicional sobre los escalares que se han filtrado o liberado prematuramente.

Estados de pila con conteo de referencias

En el nuevo régimen, la pila de argumentos actual puede estar en uno de los tres estados, que se puede determinar mediante la expresión mostrada.

  • sin conteo de referencias 
    !AvREAL(PL_curstack)

    En este caso, Perl asumirá al vaciar la pila (como durante un croak()) que los elementos en ella no necesitan ser liberados. Este es el comportamiento tradicional de Perl. En las compilaciones de "PERL_RC_STACK", tales pilas se encontrarán raramente.

  • conteo de referencias completo 
    AvREAL(PL_curstack) && !PL_curstackinfo->si_stack_nonrc_base

    Todos los elementos en la pila tienen conteo de referencias y serán liberados por funciones como rpp_popfree_1() o si Perl hace croak(). Este es el estado normal de la pila en las compilaciones de "PERL_RC_STACK".

  • conteo de referencias parcial (dividido) 
    AvREAL(PL_curstack) && PL_curstackinfo->si_stack_nonrc_base > 0

    En este caso, los elementos de la pila desde el índice "si_stack_nonrc_base" hacia arriba no tienen RC; los de abajo sí lo tienen. Este estado ocurre cuando una función PP o XS ha sido envuelta. En este caso, la función envoltorio inserta una copia sin RC de los punteros de argumento por encima del corte y luego llama a la función real. Cuando esta retorna, la función envoltorio incrementa el RC de los argumentos devueltos. Ver más abajo para más detalles.

Tenga en cuenta que Perl utiliza una pila de pilas, y los estados AvREAL() y "si_stack_nonrc_base" son por pila. Cuando Perl se inicia, la pila principal tiene RC, pero por defecto, las nuevas pilas insertadas en código XS a través de PUSHSTACKi() no tienen RC, por lo que es bastante posible obtener una mezcla. El núcleo de Perl en sí utiliza la nueva función push_stackinfo() que reemplaza a PUSHSTACKi() y le permite especificar que la nueva pila debe tener RC por defecto. La mayoría de los lugares en el núcleo asumen un entorno RC particular. En particular, se asume que dentro de un bucle runops, todas las funciones PP son conscientes de RC, ya sea porque han sido (re)escritas para ser conscientes, o porque han sido envueltas. Cada vez que se ingresa a un bucle runops a través de CALLRUNOPS(), se comprobará el estado actual de la pila y, si no es completamente RC, se actualizará temporalmente su contenido para que sea completamente RC antes de ingresar al bucle runops principal. Luego, si es necesario, se restaurará la pila a su estado anterior al regresar. Esto significa que funciones como call_sv(), que se pueden llamar desde cualquier entorno (por ejemplo, núcleo RC o código XS envuelto y temporalmente sin RC) siempre harán lo correcto al invocar el bucle runops, independientemente del estado actual de la pila.

De manera similar, las croaks y similares (que pueden ocurrir en cualquier lugar) tienen que poder manejar ambos tipos de pila. Por lo tanto, hay algunos lugares en el núcleo - call_sv(), eval_sv() etc., Perl_die_unwind() y S_my_exit_jump() - que han sido especialmente diseñados para manejar ambos casos; todo lo demás puede asumir un entorno fijo.

Envoltura

Normalmente, una función PP del núcleo se declara de la siguiente manera:

PP(pp_foo)
{
    ...
}

Esto se expande a algo como:

OP* Perl_pp_foo(pTHX)
{
    ...
}

Cuando una función de este tipo necesita ser envuelta, se declara en su lugar como:

PP_wrapped(pp_foo, nargs, nlists)
{
    ...
}

que en compilaciones sin RC, se expande a lo mismo que PP() (los argumentos adicionales se ignoran). En compilaciones RC, se expande a algo como

OP* Perl_pp_foo(pTHX)
{
    return Perl_pp_wrap(aTHX_ S_Perl_pp_foo_norc, nargs, nlists);
}
STATIC OP* S_Perl_pp_foo_norc(pTHX)
{
    ...
}

Aquí, la función PP visible externamente llama a pp_wrap(), que ajusta el contenido de la pila, luego llama al cuerpo real oculto de la función PP, y al regresar, ajusta la pila de nuevo.

Hay una macro de API, XSPP_wrapped(), destinada a su uso en funciones PP declaradas en código XS. Es idéntica a PP_wrapped(), excepto que no antepone un prefijo "Perl_" al nombre de la función.

Los parámetros "nargs" y "nlists" de la macro son constantes numéricas o expresiones simples que especifican cuántos argumentos espera la función PP, o cuántas listas espera. Por ejemplo,

PP_wrapped(pp_add, 2, 0);     /* consume dos argumentos de la pila */
PP_wrapped(pp_readline,       /* consume uno o dos argumentos */
        ((PL_op->op_flags & OPf_STACKED) ? 2 : 1), 0);
PP_wrapped(pp_push, 0, 1);    /* consume una lista */
PP_wrapped(pp_aassign, 0, 2); /* consume dos listas */

Para entender lo que hace pp_wrap(), considere llamar a Perl_pp_foo() que espera tres argumentos. A la entrada, la pila puede verse así:

... A+ B+ C+

(donde el "+" indica que los punteros a A, B y C tienen cada uno un contador de referencias). La función envoltorio pp_wrap() marca un corte en la posición actual de la pila usando "si_stack_nonrc_base", luego, basándose en el valor de "nargs", inserta una copia de esos tres punteros por encima del corte:

... A+ B+ C+ | A0 B0 C0

(donde el 0 indica que los punteros no tienen RC), luego llama a la función PP real, S_Perl_pp_foo_norc(). Esa función procesa A, B y C, los extrae de la pila e inserta algunos SVs de resultado. Ninguna de estas manipulaciones ajusta los RC. Al regresar a pp_wrap(), la pila puede verse algo así:

... A+ B+ C+ | X0 Y0

La función envoltorio incrementa los RC de X e Y, decrementa A B C, desplaza los resultados hacia abajo y establece "si_stack_nonrc_base" a cero, dejando la pila como:

... X+ Y+

En lugares como pp_entersub(), se realiza un envoltorio similar (a través de las funciones rpp_invoke_xs() y luego xs_wrap()) al llamar a subs XS.

Cuando "nlists" es positivo, ocurre una acción similar, excepto que la pila de marcas se examina (y ajusta) para determinar el número de argumentos que necesitan copiarse.

Un entorno de llamada complejo puede tener múltiples pilas anidadas con diferentes estados de RC. Perl comienza con una pila RC. Luego, por ejemplo, se llama a pp_entersub(), que (a través de xs_wrap()) divide la pila y ejecuta la función XS en un entorno sin RC. Esa función puede llamar a PUSHSTACKi(), que crea una nueva pila sin RC, luego llama a call_sv(), que hace CALLRUNOPS(), lo que provoca que la nueva pila se convierta temporalmente en RC. Luego se llama a un método enlazado, que inserta una nueva pila RC, y así sucesivamente. (XXX actualmente los métodos enlazados insertan una pila sin RC. Se corregirá pronto).

(Re)escribir una función PP usando la API rpp_()

Envolver una función PP tiene una sobrecarga de rendimiento y está ahí principalmente como una muleta temporal. Finalmente, las funciones PP deben actualizarse para usar las funciones rpp_(), y cualquier nueva función PP debe escribirse de esta manera desde cero y, por lo tanto, nunca necesitar ser envuelta.

Un par de ejemplos de funciones PP del núcleo que se están convirtiendo se pueden ver en los commits "v5.39.1-304-g205fcd8410" y "v5.39.1-303-g2fe263a83a", que demuestran la conversión de un operador unario y uno binario (pp_not() y pp_and()).

La API tradicional de la pila PP consistía en una declaración "dSP", más un número de macros para insertar, extraer y extender la pila. Una función pp_add() *muy simplificada* podría parecer algo así:

PP(pp_add)
{
    dSP;
    dTARGET;
    IV right = SvIV(POPs);
    IV left  = SvIV(POPs);
    TARGi(left + right, 1);
    PUSHs(TARG);
    PUTBACK;
    return NORMAL;
}

que se expande a algo como:

{
    SV **sp = PL_stack_sp;
    SV *targ =
PAD_SV(PL_op_op_targ); IV right = SvIV(*sp--); IV left = SvIV(*sp--); sv_setiv(targ, left + right); *++sp = targ; PL_stack_sp = sp; return PL_op->op_next; }

Todo el asunto de "dSP" se remonta a los días anteriores a los compiladores optimizadores decentes. Siempre era propenso a errores, por ejemplo, si olvidaba un "PUTBACK" o "SPAGAIN". La nueva API siempre accede directamente a "PL_stack_sp". De hecho, el primer paso para actualizar una función PP es siempre eliminar la declaración "dSP". Esto tiene el efecto secundario beneficioso de que cualquier macro de estilo antiguo que quede en la función pp y que implícitamente use "sp" se convertirá en un error de compilación. La existencia de un "dSP" en algún lugar del núcleo es una buena señal de que esa función todavía necesita ser actualizada.

Una pregunta obvia es: ¿por qué no modificar las definiciones de las macros PUSHs(), etc., para modificar los contadores de referencias en las compilaciones RC? El problema básico es que un SV ahora puede ser mantenido vivo solo por una única cuenta de referencia de la pila (anteriormente, también solían estar en la pila TEMPs). Así que en código como:

SV *sv = POPs;
IV i = SvIV(sv);

incluir un SvREFCNT_dec() en la definición de la macro "POPs" causaría que "sv" se liberara inmediatamente, antes de que su valor entero pudiera ser leído.

Un problema potencial con el nuevo régimen es que perl puede fallar en básicamente cualquier punto de la ejecución (por ejemplo, el SvIV() anterior podría llamar a FETCH() en una variable enlazada que luego falla). Por lo tanto, en todo momento, el RC de cada SV debe ser debidamente contabilizado. En el ejemplo anterior, un enfoque ingenuo para evitar una liberación prematura de "sv" podría ser:

SV *sv = *PL_stack_sp--;
IV i = SvIV(sv);
SvREFCNT_dec(sv); // obtuve i, así que está bien liberar sv ahora

pero eso significa que "sv" se fuga si SvIV() provoca un fallo.

Para evitar eso, el nuevo régimen tiene el esquema general de que los argumentos se dejan en la pila *hasta que se terminan de usar*, luego se eliminan y su cuenta de referencia se ajusta en ese momento. Con la nueva API, la función pp_add() se ve algo así:

{
    dTARGET;
    IV right = SvIV(PL_stack_sp[ 0]); // NOTA: argumentos dejados en la pila
    IV left  = SvIV(PL_stack_sp[-1]);
    TARGi(left + right, 1);
    rpp_replace_2_1(targ);
    return NORMAL;
}

La función rpp_replace_2_1() saca dos valores de la pila y empuja un nuevo valor, mientras ajusta las cuentas de referencia según corresponda (dependiendo de si se compiló con "PERL_RC_STACK" o no).

Tenga en cuenta que rpp_popfree_1(), etc., no son reemplazos directos de "POPs". Las variantes rpp_() no devuelven un valor y están destinadas a ser llamadas cuando el SV se deja de usar. Entonces

SV *sv = POPs;
... hacer algo con sv ...

se convierte en

SV *sv = *PL_stack_sp;
... hacer algo con sv ...
rpp_popfree_1(); /* hace SvREFCNT_dec(*PL_stack_sp--) */

Las funciones rpp_replace_M_N() son atajos para sacar y liberar "M" elementos, luego empujar y aumentar los RC de "N" elementos. Tenga en cuenta que manejan casos extremos, como que un SV antiguo y uno nuevo sean el mismo.

rpp_replace_at(sp, sv) es similar a rpp_replace_1_1(), excepto que reemplaza un SV en una dirección en la pila en lugar de en la parte superior.

rpp_replace_at_norc(sp, sv) es similar a rpp_replace_at(), excepto que asume que "sv" ya tiene una cuenta de referencia aumentada. Por lo tanto, un poco como rpp_push_1_norc() (ver más abajo), no se molesta en aumentar la cuenta de referencia de "sv", o en compilaciones no-RC lo mortaliza en su lugar.

rpp_popfree_to(svp) está diseñado para reemplazar código como

PL_stack_sp = PL_stack_base + cx->blk_oldsp;

que típicamente aparece en operaciones de lista o salidas de alcance cuando se terminan de usar los argumentos. Sin alterar, todos los SVs por encima de "oldsp" se filtrarían. El nuevo enfoque es

rpp_popfree_to(PL_stack_base + cx->blk_oldsp);

Hay una variante de esto, raramente utilizada, rpp_obliterate_stack_to(), que saca la pila hasta el índice especificado independientemente del estado actual de RC de la pila. Por ejemplo, si la pila está dividida, solo ajustará los RC de cualquier SV que esté por debajo del punto de división, mientras que rpp_popfree_to() liberaría sin pensar *todos* los SVs (en compilaciones RC de todos modos). Para funciones PP normales, solo debe usar rpp_popfree_to(), que es más rápido.

No hay nuevos equivalentes para todas las macros de conveniencia como POPi() y (horror) dPOPPOPiirl(). Estas deben ser reemplazadas con las funciones rpp_() anteriores y con las conversiones y declaraciones de variables que se hacen explícitas, por ejemplo, dPOPPOPiirl() se convierte en:

IV right = SvIV(PL_stack_sp[ 0]);
IV left  = SvIV(PL_stack_sp[-1]);
rpp_popfree_2();

Un par de las funciones rpp_() con "norc" en sus nombres no ajustan la cuenta de referencia en compilaciones RC (pero, por el contrario, lo hacen en compilaciones no-RC).

rpp_push_1_norc(sv) hace un simple "*++PL_stack_sp = sv" en compilaciones RC. Típicamente se usa para "raizar" un SV recién creado, que ya tiene un RC de 1. En compilaciones no-RC, lo mortaliza en su lugar. Por ejemplo, el código que solía verse como

mPUSHs(newSViv(i));

y que se expandía al equivalente de:

PUSHs(sv_2mortal(newSViv(i));

debería reescribirse como:

rpp_push_1_norc(newSViv(i));

Esto se debe a que newSViv() y similares crean un nuevo SV con una cuenta de referencia demasiado alta (1 en lugar de 0). Esta cuenta se "dona" luego a la pila al empujarla. Por el contrario, en compilaciones no-RC, la cuenta se dona a la pila TEMPs.

De manera similar, en compilaciones RC, "sv = rpp_pop_1_norc()" hace un simple "sv = *PL_stack_sv--" sin ajustar la cuenta de referencia, mientras que en compilaciones no-RC, en realidad incrementa la cuenta de referencia del SV. Está destinado a casos en los que desea incrementar inmediatamente la cuenta de referencia nuevamente después de sacar, por ejemplo, donde el SV será incrustado inmediatamente en algún lugar. Por ejemplo, este código:

SV *sv = PL_stack_sp[0];
SvREFCNT_inc(sv);
av_store(av, i, sv); /* en la vida real debería verificar el valor de retorno */
rpp_popfree_1();

puede ser escrito de manera más eficiente como

av_store(av, i, rpp_pop_1_norc());

Al usar esta función, el código funciona correctamente tanto en compilaciones RC como no-RC.

Una operación común en las operaciones de lista es imponer contexto void, scalar o list en los argumentos de retorno, posiblemente descartando todos, o todos excepto uno, de ellos. rpp_context(mark, gimme, extra) hace esto. Como primer paso (para conveniencia y eficiencia) saca notablemente "extra" argumentos de la pila. Luego, para el contexto de lista, deja las cosas como están. Para el contexto void, el puntero de pila se restablece a mark, y todo lo de arriba se saca. Para scalar, el argumento superior (o &PL_sv_undef) se mueve desde la parte superior a mark+1 y todo lo de arriba se descarta.

Las macros que aparecen al principio de muchas funciones PP para verificar sobrecargas de op unarias o binarias (entre otras cosas) han sido reemplazadas por funciones en línea rpp_try_AMAGIC_1() y _2(), que ahora dependen de la función PP que llama para elegir si regresar inmediatamente en lugar de que el retorno se oculte en la macro.

La función rpp_invoke_xs() llama a la función XS asociada con el CV, pero puede hacerlo a través de una función envoltorio para ajustar la pila según sea necesario.

Manipulación de la pila y recuento de referencias

Este documento describe algunas de las partes más bajas de la pila de Perl, y las implicaciones de "PERL_RC_STACK" en ellas. En el pasado, los operadores (ops) eran empujados a la pila de argumentos de Perl, que a veces también se conocía como la pila de evaluación. Ahora, cada uno de estos se conoce como una "stackinfo".

Para la mayoría de los fines, esto no es más que un cambio de nombre. Sin embargo, la estructura de las macros de la pila ha cambiado. Las macros como "PUSHs" y "OP_push" ahora funcionan de manera diferente y, en general, deberían ser evitadas en favor de las funciones en línea que se describen a continuación.

Las macros que manipulaban la pila de Perl se han sustituido por funciones en línea, que se documentan en perlapi(3). Estas funciones son más portátiles y menos propensas a errores, ya que no requieren que "dSP" esté en el ámbito, y sus nombres son más descriptivos. Por ejemplo, "rpp_xpush_1" se ha sustituido por "push_stackinfo".

La principal diferencia funcional es cómo se maneja el recuento de referencias de los valores devueltos cuando se utiliza "PERL_RC_STACK". Tradicionalmente, se esperaba que los valores devueltos por una llamada a subroutine estuvieran en la cima de la pila de argumentos. Si ese valor todavía estaba allí al final de la función, su recuento de referencias se incrementaba automáticamente para reflejar que la función lo estaba reteniendo. Si el valor no estaba en la cima de la pila, se asumía que ya había sido consumido, y no se hacía nada.

Con "PERL_RC_STACK", este comportamiento ya no es suficiente. El valor devuelto puede haber sido movido a la pila temporal ("temps") o incluso haber sido copiado a otro lugar. Por lo tanto, el recuento de referencias solo se incrementa si el valor de retorno todavía está en la pila de argumentos o en la pila temporal.

En lugar de usar macros como "rpp_xpush_1()", la función "call_sv()" ahora usa explícitamente "rpp_extend(1); *++PL_stack_sp = sv; #ifdef PERL_RC_STACK if (rpp_stack_is_rc()) SvREFCNT_inc_simple_void_NN(sv); #endif". Esto garantiza que el recuento de referencias se maneje correctamente tanto en las compilaciones estándar como en las RC, y también funciona tanto si "call_sv()" se llama desde una función PP estándar (donde "rpp_stack_is_rc()" es verdadero) como desde una función PP o XS envuelta (donde "rpp_stack_is_rc()" es falso).

De manera similar, las macros para empujar nuevas "stackinfos" han sido reemplazadas por funciones en línea. La función "push_stackinfo()" toma un argumento booleano que indica si la nueva pila de argumentos debe ser de recuento de referencias o no. Para compatibilidad con versiones anteriores, "PUSHSTACKi(type)" se define como "push_stackinfo(type, 0)".

Algunos scripts de prueba verifican si hay fugas probando que el recuento de referencias de una variable particular tiene un valor esperado. Si este valor es diferente en una compilación de perl con "PERL_RC_STACK", se puede usar la función de perl "Internals::stack_refcounted()". Esta función devuelve un entero, cuyo bit más bajo indica si perl se compiló con "PERL_RC_STACK". Otros bits están reservados para uso futuro y deben ser enmascarados.

Finalmente, un par de funciones "rpp()" proporcionan información en lugar de manipular la pila:

"rpp_is_lone(sv)" indica si "sv", asumiendo que todavía está en la pila, se mantiene vivo solo por un único puntero de recuento de referencias de los argumentos y/o pilas temporales, y por lo tanto es un candidato para algunas optimizaciones (como omitir la copia de argumentos de retorno de una llamada a subrutina).

"rpp_stack_is_rc()" indica si la pila actual está actualmente bajo recuento de referencias. Se utiliza principalmente en algunos lugares como "call_sv()", que puede ser llamada desde cualquier lugar, y por lo tanto tiene que lidiar con ambos casos.

Asignación de operadores basada en slabs

Nota: esta sección describe una API interna no pública que está sujeta a cambios sin previo aviso.

Los mecanismos internos de manejo de errores de Perl implementan "die" (y sus equivalentes internos) usando "longjmp". Si esto ocurre durante la lexicalización, el análisis sintáctico o la compilación, debemos asegurarnos de que todos los ops asignados como parte del proceso de compilación se liberen. (Las versiones anteriores de Perl no manejaban adecuadamente esta situación: al fallar un análisis sintáctico, filtraban ops que se almacenaban en variables C "auto" y no estaban vinculados a ningún otro lugar).

Para manejar esta situación, Perl utiliza "op slabs" que están adjuntos al CV que se está compilando actualmente. Un slab es un bloque de memoria asignada. Los nuevos ops se asignan como regiones del slab. Si el slab se llena, se crea uno nuevo (y se vincula desde el anterior). Cuando ocurre un error y el CV se libera, los ops restantes se liberan.

Cada op va precedido por dos punteros: uno apunta al siguiente op en el slab, y el otro apunta al slab que lo posee. El puntero al siguiente op es necesario para que Perl pueda iterar sobre un slab y liberar todos sus ops. (Las estructuras de ops tienen diferentes tamaños, por lo que los ops del slab no pueden tratarse simplemente como un array denso.) El puntero al slab es necesario para acceder a un recuento de referencias en el slab: cuando el último op en un slab se libera, el slab en sí mismo se libera.

El asignador de slabs coloca los ops al final del slab primero. Esto tenderá a asignar primero las hojas del árbol de ops, y por lo tanto, esperemos que el diseño sea amigable con la caché. Además, esto significa que no hay necesidad de almacenar el tamaño del slab (ver más abajo por qué los slabs varían en tamaño), porque Perl puede seguir punteros para encontrar el último op.

Podría parecer posible eliminar por completo los recuentos de referencias de los slabs, haciendo que todos los ops estén implícitamente adjuntos a "PL_compcv" cuando se asignan y se liberan cuando se libera el CV. Eso también permitiría que "op_free" omitiera "FreeOp" por completo, y así liberar los ops más rápido. Pero eso no funciona en aquellos casos en que los ops necesitan sobrevivir más allá de sus CVs, como las re-evaluaciones.

El CV también tiene que tener un recuento de referencias en el slab. A veces, el primer op creado se libera inmediatamente. Si el recuento de referencias del slab llega a 0, se liberará mientras el CV todavía apunta a él.

Los CVs utilizan el flag "CVf_SLABBED" para indicar que el CV tiene un recuento de referencias en el slab. Cuando este flag está establecido, el slab es accesible a través de "CvSTART" cuando "CvROOT" no está establecido, o restando dos punteros "(2*sizeof(I32 *))" de "CvROOT" cuando está establecido. La alternativa a este enfoque de colar el slab en "CvSTART" durante la compilación sería ampliar la estructura "xpvcv" con otro puntero. Pero eso haría que todos los CVs fueran más grandes, a pesar de que la liberación de ops basada en slabs normalmente solo beneficia a los programas que hacen un uso significativo de la evaluación de cadenas.

Cuando el flag "CVf_SLABBED" está establecido, el CV se responsabiliza de liberar el slab. Si "CvROOT" no está establecido cuando el CV se libera o se desdefine, se asume que ha ocurrido un error de compilación, por lo que se recorre el slab de ops y se liberan todos los ops.

En circunstancias normales, el CV se olvida de su slab (decrementando el recuento de referencias) cuando se adjunta la raíz. Por lo tanto, el recuento de referencias del slab que ocurre cuando se liberan los ops se encarga de liberar el slab. En algunos casos, se le dice al CV que se olvide del slab ("cv_forget_slab") precisamente para que los ops puedan sobrevivir después de que el CV sea eliminado.

Olvidarse del slab cuando se adjunta la raíz no es estrictamente necesario, pero evita posibles problemas con "CvROOT" siendo sobrescrito. Hay código en todas partes, tanto en el núcleo como en CPAN, que hace cosas con "CvROOT", por lo que olvidarse del slab hace las cosas más robustas y evita posibles problemas.

Dado que el CV toma posesión de su slab cuando está marcado, ese flag nunca se copia cuando se clona un CV, ya que un CV podría liberar un slab al que otro CV todavía apunta, ya que la liberación forzada de ops ignora el recuento de referencias (pero afirma que se ve bien).

Para evitar la fragmentación del slab, los ops liberados se marcan como liberados y se adjuntan a la cadena de liberados del slab (una idea robada de DBM::Deep). Esos ops liberados se reutilizan cuando es posible. No reutilizar los ops liberados sería más simple, pero resultaría en un uso de memoria significativamente mayor para programas con grandes bloques de "if (DEBUG) {...}".

"SAVEFREEOP" es ligeramente problemático bajo este esquema. A veces puede causar que un op se libere después de su CV. Si el CV ha liberado forzosamente los ops en su slab y el slab en sí, entonces estaremos manipulando un slab liberado. Hacer que "SAVEFREEOP" no haga nada no ayuda, ya que a veces un op puede ser guardado y liberado cuando no hay un error de compilación, por lo que el op nunca sería liberado. Mantiene un recuento de referencias en el slab, por lo que todo el slab se filtraría. Por lo tanto, "SAVEFREEOP" ahora establece un flag especial en el op ("->op_savefree"). La liberación forzada de ops después de un error de compilación no liberará ningún op marcado de esta manera.

Dado que muchas piezas de código crean subrutinas diminutas que consisten en solo unos pocos ops, y dado que un slab enorme sería una carga bastante grande para que las lleven consigo, el primer slab es siempre muy pequeño. Para evitar asignar demasiados slabs para un solo CV, cada slab subsiguiente es el doble del tamaño del anterior.

Smartmatch espera poder asignar un op en tiempo de ejecución, ejecutarlo y luego desecharlo. Para que eso funcione, el op se asigna simplemente con malloc cuando "PL_compcv" no se ha configurado. Por lo tanto, todos los ops asignados en slab están marcados como tales ("->op_slabbed"), para distinguirlos de los ops con malloc.
