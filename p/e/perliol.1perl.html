PERLIOL(1perl) Guía de Referencia del Programador de Perl PERLIOL(1perl)

NOMBRE

perliol - API de C para la implementación de IO en Capas de Perl.

SINOPSIS

/* Definiendo una capa ... */
#include <perliol.h>

DESCRIPCIÓN

Este documento describe el comportamiento y la implementación de la abstracción PerlIO descrita en perlapio cuando "USE_PERLIO" está definida.

Historia y Antecedentes

La abstracción PerlIO se introdujo en perl5.003_02 pero languideció como solo una abstracción hasta perl5.7.0. Sin embargo, durante ese tiempo, varias extensiones de perl cambiaron a usarla, por lo que la API está en gran parte fija para mantener la compatibilidad (fuente).

El objetivo de la implementación es proporcionar la API de PerlIO de manera flexible y neutral en cuanto a plataforma. También es una prueba de un enfoque de "C Orientada a Objetos, con vtables" que puede ser aplicado a Raku.

Estructura Básica

PerlIO es una pila de capas.

Los niveles bajos de la pila trabajan con las llamadas de bajo nivel del sistema operativo (descriptores de archivo en C) obteniendo bytes de entrada y salida, las capas más altas de la pila almacenan en búfer, filtran y manipulan de otra manera la E/S, y devuelven caracteres (o bytes) a Perl. Se utilizan los términos *superior* e *inferior* para referirse a la posición relativa de las capas de la pila.

Una capa contiene una "vtable", la tabla de operaciones de E/S (en nivel C una tabla de punteros a funciones), y banderas de estado. Las funciones de la vtable implementan operaciones como "open", "read" y "write".

Cuando se solicita una E/S, por ejemplo "read", la solicitud va desde Perl primero hacia abajo en la pila usando las funciones "read" de cada capa, luego en la parte inferior se solicita la entrada a los servicios del sistema operativo, luego el resultado se devuelve hacia arriba en la pila, finalmente siendo interpretado como datos de Perl.

Las solicitudes no necesariamente van siempre hasta abajo del todo hacia el sistema operativo: ahí es donde entra en juego el almacenamiento en búfer de PerlIO.

Cuando haces un open() y especificas capas PerlIO adicionales que se implementarán, las capas que especificas se "insertan" encima de la pila predeterminada ya existente. Una forma de verlo es que "el sistema operativo está a la izquierda" y "Perl está a la derecha".

Qué capas exactas están en esta pila predeterminada depende de muchas cosas: tu sistema operativo, la versión de Perl, la configuración de compilación de Perl y la configuración de ejecución de Perl. Ver PerlIO, "PERLIO" en perlrun, y open para más información.

binmode() opera de manera similar a open(): por defecto, las capas especificadas se insertan encima de la pila existente.

Sin embargo, ten en cuenta que incluso cuando las capas especificadas se "insertan encima" para open() y binmode(), esto no significa que los efectos se limiten a la "cima": las capas PerlIO pueden ser muy 'activas' e inspeccionar y afectar capas también más profundas en la pila. Por ejemplo, existe una capa llamada "raw" que "elimina" capas repetidamente hasta que llega a la primera capa que se ha declarado capaz de manejar datos binarios. Las capas "insertadas" se procesan en orden de izquierda a derecha.

sysopen() opera (como era de esperar) a un nivel más bajo en la pila que open(). Por ejemplo, en sistemas Unix o similares a Unix, sysopen() opera directamente en el nivel de los descriptores de archivo: en los términos de las capas PerlIO, solo utiliza la capa "unix", que es un envoltorio bastante delgado sobre los descriptores de archivo de Unix.

Capas vs Disciplinas

La discusión inicial sobre la capacidad de modificar el comportamiento de los flujos de E/S utilizó el término "disciplina" para las entidades que se agregaban. Esto vino (creo) del uso del término en "sfio", que a su vez lo tomó prestado de las "disciplinas de línea" en los terminales Unix. Sin embargo, este documento (y el código C) utiliza el término "capa".

Esto es, espero, un término natural dada la implementación, y debería evitar connotaciones inherentes a usos anteriores de "disciplina" para cosas que son bastante diferentes.

Estructuras de Datos

La estructura de datos básica es un PerlIOl:

typedef struct _PerlIO PerlIOl;
typedef struct _PerlIO_funcs PerlIO_funcs;
typedef PerlIOl *PerlIO;
struct _PerlIO
{
 PerlIOl *      next;       /* Capa inferior */
 PerlIO_funcs * tab;        /* Funciones para esta capa */
 U32            flags;      /* Varios flags para el estado */
};

Un "PerlIOl *" es un puntero a la estructura, y el nivel de *aplicación* "PerlIO *" es un puntero a un "PerlIOl *" - es decir, un puntero a un puntero a la estructura. Esto permite que el nivel de aplicación "PerlIO *" permanezca constante mientras el "PerlIOl *" real debajo cambia. (Compare el "SV *" de Perl que permanece constante mientras su campo "sv_any" cambia a medida que el tipo del escalar cambia). Un flujo de E/S se representa generalmente como un puntero a esta lista enlazada de "capas".

Cabe señalar que debido a la doble indirección en un "PerlIO *", un "&(perlio->next)" "es" un "PerlIO *", y por lo tanto, hasta cierto punto al menos una capa puede usar la API "estándar" en la siguiente capa inferior.

Una "capa" se compone de dos partes:

1.
Las funciones y atributos de la "clase de capa".
2.
Los datos por instancia para un manejador particular.

PerlIO implementation details

This document describes the design and implementation of the PerlIO system introduced in Perl 5.7.0.

The PerlIO interface

The PerlIO system is based on a table of functions that operate on a PerlIO object. This table is specific to the layer. The layer itself is specified when opening a file.

1.
Funciones de apertura e inicialización
2.
Operaciones básicas de E/S
3.
Opciones de bufferizado de la clase Stdio.
4.
Funciones para soportar el acceso tradicionalmente "rápido" de Perl al buffer.

Una capa no tiene que implementar todas las funciones, pero la tabla completa debe estar presente. Las ranuras no implementadas pueden ser NULL (lo que resultará en un error al ser llamadas) o pueden ser rellenadas con stubs para "heredar" el comportamiento de una "clase base". Esta "herencia" es fija para todas las instancias de la capa, pero como la capa elige qué stubs poblar la tabla, es posible una "herencia múltiple" limitada.

Datos por instancia

Los datos por instancia se mantienen en memoria más allá de la estructura básica PerlIOl, haciendo de PerlIOl el primer miembro de la estructura de la capa de la siguiente manera:

typedef struct
{
 struct _PerlIO base;       /* Información de la "clase" base */
 STDCHAR *      buf;        /* Inicio del buffer */
 STDCHAR *      end;        /* Fin de la parte válida del buffer */
 STDCHAR *      ptr;        /* Posición actual en el buffer */
 Off_t          posn;       /* Desplazamiento de buf en el archivo */
 Size_t         bufsiz;     /* Tamaño real del buffer */
 IV             oneword;    /* Buffer de emergencia */
} PerlIOBuf;

De esta manera (como para los escalares de perl) un puntero a un PerlIOBuf puede ser tratado como un puntero a un PerlIOl.

Capas en acción

             table           perlio          unix
         |           |
         +-----------+    +----------+    +--------+
PerlIO ->|           |--->|  next    |--->|  NULL  |
         +-----------+    +----------+    +--------+
         |           |    |  buffer  |    |   fd   |
         +-----------+    |          |    +--------+
         |           |    +----------+

Lo anterior intenta mostrar cómo funciona el esquema de capas en un caso simple. El "PerlIO *" de la aplicación apunta a una entrada en la(s) tabla(s) que representa(n) handles abiertos (asignados). Por ejemplo, las tres primeras ranuras de la tabla corresponden a "stdin", "stdout" y "stderr". La tabla a su vez apunta a la capa "superior" actual para el handle - en este caso, una instancia de la capa de bufferizado genérico "perlio". Esa capa a su vez apunta a la siguiente capa inferior - en este caso, la capa de bajo nivel "unix".

Lo anterior es aproximadamente equivalente a un stream bufferizado "stdio", pero con mucha más flexibilidad:

  • Si la "lectura"/"escritura"/"lseek" de nivel Unix no es apropiada para (por ejemplo) sockets, entonces la capa "unix" puede ser reemplazada (en el momento de la apertura o incluso dinámicamente) con una capa de "socket".
  • Diferentes handles pueden tener diferentes esquemas de bufferizado. La capa "superior" podría ser la capa "mmap" si leer archivos de disco fuera más rápido usando "mmap" que "read". Un stream "sin bufferizar" se puede implementar simplemente no teniendo una capa de buffer.
  • Se pueden insertar capas adicionales para procesar los datos mientras fluyen. Esta fue la necesidad principal para incluir el esquema en perl 5.7.0+ - necesitábamos un mecanismo para permitir la traducción de datos entre la codificación interna de perl (conceptualmente al menos Unicode como UTF-8) y el formato "nativo" utilizado por el sistema. Esto lo proporciona la capa ":encoding(xxxx)" que normalmente se sitúa por encima de la capa de bufferizado.
  • Se puede añadir una capa que realice la traducción de "\n" a CRLF. Esta capa se puede usar en cualquier plataforma, no solo en aquellas que normalmente hacen tales cosas.

Bits de flags por instancia

Los bits de flags genéricos son un híbrido de flags estilo "O_XXXXX" deducidos de la cadena de modo pasada a PerlIO_open(), y bits de estado para capas de buffer típicas.

PERLIO_F_EOF
Fin de archivo.
PERLIO_F_CANWRITE
Se permiten escrituras, es decir, abierto como "w" o "r+" o "a", etc.
PERLIO_F_CANREAD
Se permiten lecturas, es decir, abierto "r" o "w+" (o incluso "a+" - puaj).
PERLIO_F_ERROR
Ha ocurrido un error (para PerlIO_error()).
PERLIO_F_TRUNCATE
Se sugirió truncar el archivo por el modo de apertura.
PERLIO_F_APPEND
Todas las escrituras deben ser de adición.
PERLIO_F_CRLF
La capa está realizando la traducción de "\n" a CR, LF para salida y CR, LF a "\n" para entrada, similar a Win32. Normalmente, la capa "crlf" proporcionada es la única que necesita preocuparse por esto. PerlIO_binmode() modificará este flag en lugar de añadir/eliminar capas si el bit "PERLIO_K_CANCRLF" está activado para la clase de la capa.
PERLIO_F_UTF8
Los datos escritos en esta capa deben ser codificados en UTF-8; los datos proporcionados por esta capa deben considerarse codificados en UTF-8. Puede ser establecido en cualquier capa por la capa dummy ":utf8". También se establece en la capa ":encoding".
PERLIO_F_UNBUF
La capa está sin bufferizar - es decir, la escritura a la capa inferior debe ocurrir por cada escritura a esta capa.
PERLIO_F_WRBUF
El buffer de esta capa contiene actualmente datos escritos en ella pero no enviados a la capa inferior.
PERLIO_F_RDBUF
El buffer de esta capa contiene actualmente datos no consumidos leídos de la capa inferior.
PERLIO_F_LINEBUF
La capa está bufferizada por línea. Los datos de escritura deben ser pasados a la capa inferior cada vez que se ve un "\n". Cualquier dato posterior al "\n" debe ser procesado.
PERLIO_F_TEMP
El archivo ha sido unlink()ado, o debe ser eliminado al cerrar (close()).
PERLIO_F_OPEN
El handle está abierto.
PERLIO_F_FASTGETS
Esta instancia de esta capa soporta la interfaz de "obtención rápida "gets"". Normalmente se establece basándose en "PERLIO_K_FASTGETS" para la clase y por la existencia de la(s) función(es) en la tabla. Sin embargo, una clase que normalmente proporciona esa interfaz puede necesitar evitarla en una instancia particular. La capa "pending" necesita hacer esto cuando se inserta por encima de una capa que no soporta la interfaz. (El sv_gets() de Perl no espera que el comportamiento de "obtención rápida" de los streams cambie durante una "obtención".)

Métodos en detalle

fsize
Size_t fsize;

Tamaño de la tabla de funciones. Esto se compara con el valor que el código Perl "conoce" como una comprobación de compatibilidad. Las versiones futuras *pueden* ser capaces de tolerar capas compiladas contra una versión antigua de las cabeceras.

name
char * name;

El nombre de la capa cuyo método open() Perl debería invocar en open(). Por ejemplo, si la capa se llama APR, se invocará:

open $fh, ">:APR", ...

y Perl sabrá que tiene que invocar el método PerlIOAPR_open() implementado por la capa APR.

size
Size_t size;

El tamaño de la estructura de datos por instancia, por ejemplo:

sizeof(PerlIOAPR)

Si este campo es cero, entonces "PerlIO_pushed" no asigna memoria y asume que la función Pushed de la capa se encargará de cualquier manipulación necesaria de la pila de capas - se utiliza para evitar la sobrecarga de malloc/free para capas dummy. Si el campo no es cero, debe ser al menos del tamaño de "PerlIOl", "PerlIO_pushed" asignará memoria para las estructuras de datos de la capa y enlazará la nueva capa a la pila del stream. (Si el método Pushed de la capa devuelve una indicación de error, la capa se vuelve a sacar de la pila.)

kind
IV kind;
  • PERLIO_K_BUFFERED

    La capa está bufferizada.

  • PERLIO_K_RAW

    La capa es aceptable para tenerla en una pila binmode(FH) - es decir, no transforma (o se configurará para no transformar) los bytes que pasan a través de ella.

  • PERLIO_K_CANCRLF

    La capa puede traducir entre finales de línea "\n" y CRLF.

  • PERLIO_K_FASTGETS

    La capa permite la inspección del buffer.

  • PERLIO_K_MULTIARG

    Se usa cuando el open() de la capa acepta más argumentos de lo normal. Los argumentos adicionales no deben ir antes del argumento "MODE". Cuando se usa este flag, depende de la capa validar los argumentos.

Pushed
IV     (*Pushed)(pTHX_ PerlIO *f,const char *mode, SV *arg);

El único método absolutamente obligatorio. Se llama cuando la capa se inserta en la pila. El argumento "mode" puede ser NULL si esto ocurre después de la apertura. El "arg" no será "NULL" si se pasó una cadena de argumento. En la mayoría de los casos, esto debería llamar a PerlIOBase_pushe

PerlIO - Implementación de PerlIO

SYNOPSIS

    PerlIO *f;
    char *buf;
    size_t len;

DESCRIPTION

This document describes the PerlIO interface, the implementation details, and how to implement new PerlIO layers.

The PerlIO system is a C API for managing I/O streams, providing a way to layer different I/O behaviors (like buffering, character encoding, line ending conversion, etc.) on top of each other. Each layer implements a standard set of methods, and these methods can call the methods of the layer below them.

PerlIO_vtbl

The core of the PerlIO system is the PerlIO_vtbl structure, which is a virtual function table containing pointers to the methods implemented by a specific PerlIO layer.

Read
IV      (*Read)(pTHX_ PerlIO *f, void *vbuf, STRLEN len);

Read up to len bytes from the stream f into the buffer vbuf. Should normally call PerlIOBase_read() to handle buffering and call the layer below.

Returns the number of bytes read on success, or -1 on failure.

Write
IV      (*Write)(pTHX_ PerlIO *f, const void *vbuf, STRLEN len);

Write up to len bytes from the buffer vbuf to the stream f. Should normally call PerlIOBase_write() to handle buffering and call the layer below.

Returns the number of bytes written on success, or -1 on failure.

Seek
IV      (*Seek)(pTHX_ PerlIO *f, IV offset, int whence);

Set the stream position. whence can be SEEK_SET, SEEK_CUR, or SEEK_END. Should normally call PerlIOBase_seek().

Returns the new position on success, or -1 on failure.

Tell
IV      (*Tell)(pTHX_ PerlIO *f);

Return the current stream position. Should normally call PerlIOBase_tell().

Returns the current position on success, or -1 on failure.

Close
IV      (*Close)(pTHX_ PerlIO *f);

Close the stream. Should normally call PerlIOBase_close() to flush itself and close layers below, and then deallocate any data structures (buffers, translation tables, ...) not held directly in the data structure.

Returns 0 on success, -1 on failure.

Flush
IV      (*Flush)(pTHX_ PerlIO *f);

Should make stream's state consistent with layers below. That is, any buffered write data should be written, and file position of lower layers adjusted for data read from below but not actually consumed. (Should perhaps Unread() such data to the lower layer.)

Returns 0 on success, -1 on failure.

Fill
IV      (*Fill)(pTHX_ PerlIO *f);

The buffer for this layer should be filled (for read) from layer below. When you "subclass" PerlIOBuf layer, you want to use its _read method and to supply your own fill method, which fills the PerlIOBuf's buffer.

Returns 0 on success, -1 on failure.

Eof
IV      (*Eof)(pTHX_ PerlIO *f);

Return end-of-file indicator. PerlIOBase_eof() is normally sufficient.

Returns 0 on end-of-file, 1 if not end-of-file, -1 on error.

Error
IV      (*Error)(pTHX_ PerlIO *f);

Return error indicator. PerlIOBase_error() is normally sufficient.

Returns 1 if there is an error (usually when "PERLIO_F_ERROR" is set), 0 otherwise.

Clearerr
void    (*Clearerr)(pTHX_ PerlIO *f);

Clear end-of-file and error indicators. Should call PerlIOBase_clearerr() to set the "PERLIO_F_XXXXX" flags, which may suffice.

Setlinebuf
void    (*Setlinebuf)(pTHX_ PerlIO *f);

Mark the stream as line buffered. PerlIOBase_setlinebuf() sets the PERLIO_F_LINEBUF flag and is normally sufficient.

Get_base
STDCHAR *       (*Get_base)(pTHX_ PerlIO *f);

Allocate (if not already done so) the read buffer for this layer and return pointer to it. Return NULL on failure.

Get_bufsiz
Size_t  (*Get_bufsiz)(pTHX_ PerlIO *f);

Return the number of bytes that last Fill() put in the buffer.

Get_ptr
STDCHAR *       (*Get_ptr)(pTHX_ PerlIO *f);

Return the current read pointer relative to this layer's buffer.

Get_cnt
SSize_t (*Get_cnt)(pTHX_ PerlIO *f);

Return the number of bytes left to be read in the current buffer.

Set_ptrcnt
void    (*Set_ptrcnt)(pTHX_ PerlIO *f,
                      STDCHAR *ptr, SSize_t cnt);

Adjust the read pointer and count of bytes to match "ptr" and/or "cnt". The application (or layer above) must ensure they are consistent. (Checking is allowed by the paranoid.)

Utilities

To ask for the next layer down use PerlIONext(PerlIO *f).

To check that a PerlIO* is valid use PerlIOValid(PerlIO *f). (All this does is really just to check that the pointer is non-NULL and that the pointer behind that is non-NULL.)

PerlIOBase(PerlIO *f) returns the "Base" pointer, or in other words, the "PerlIOl*" pointer.

PerlIOSelf(PerlIO* f, type) return the PerlIOBase cast to a type.

Perl_PerlIO_or_Base(PerlIO* f, callback, base, failure, args) either calls the callback from the functions of the layer f (just by the name of the IO function, like "Read") with the args, or if there is no such callback, calls the base version of the callback with the same args, or if the f is invalid, set errno to EBADF and return failure.

Perl_PerlIO_or_fail(PerlIO* f, callback, failure, args) either calls the callback of the functions of the layer f with the args, or if there is no such callback, set errno to EINVAL. Or if the f is invalid, set errno to EBADF and return failure.

Perl_PerlIO_or_Base_void(PerlIO* f, callback, base, args) either calls the callback of the functions of the layer f with the args, or if there is no such callback, calls the base version of the callback with the same args, or if the f is invalid, set errno to EBADF.

Perl_PerlIO_or_fail_void(PerlIO* f, callback, args) either calls the callback of the functions of the layer f with the args, or if there is no such callback, set errno to EINVAL. Or if the f is invalid, set errno to EBADF.

Implementing PerlIO Layers

If you find the implementation document unclear or not sufficient, look at the existing PerlIO layer implementations, which include:

  • C implementations

    The perlio.c and perliol.h in the Perl core implement the "unix", "perlio", "stdio", "crlf", "utf8", "byte", "raw", "pending" layers, and also the "mmap" and "win32" layers if applicable. (The "win32" is currently unfinished and unused, to see what is used instead in Win32, see "Querying the layers of filehandles" in PerlIO .)

    PerlIO::encoding, PerlIO::scalar, PerlIO::via in the Perl core.

    PerlIO::gzip and APR::PerlIO (mod_perl 2.0) on CPAN.

  • Perl implementations

    PerlIO::via::QuotedPrint in the Perl core and PerlIO::via::* on CPAN.

If you are creating a PerlIO layer, you may want to be lazy, in other words, implement only the methods that interest you. The other methods you can either replace with the "blank" methods

    PerlIOBase_noop_ok
    PerlIOBase_noop_fail

(which do nothing, and return zero and -1, respectively) or for certain methods you may assume a default behaviour by using a NULL method. The Open method looks for help in the 'parent' layer. The following table summarizes the behaviour:

   method      behaviour with NULL
   Clearerr    PerlIOBase_clearerr
   Close       PerlIOBase_close
   Dup         PerlIOBase_dup
   Eof         PerlIOBase_eof
   Error       PerlIOBase_error
   Fileno      PerlIOBase_fileno
   Fill        FAILURE
   Flush       SUCCESS
   Getarg      SUCCESS
   Get_base    FAILURE
   Get_bufsiz  FAILURE
   Get_cnt     FAILURE
   Get_ptr     FAILURE
   Open        INHERITED
   Popped      SUCCESS
   Pushed      SUCCESS
   Read        PerlIOBase_read
   Seek        FAILURE
   Set_cnt     FAILURE
   Set_ptrcnt  FAILURE
   Setlinebuf  PerlIOBase_setlinebuf
   Tell        FAILURE
   Unread      PerlIOBase_unread
   Write       FAILURE

FAILURE Set errno (to EINVAL in Unixish, to LIB$_INVARG in VMS) and return -1 (for numeric return values) or NULL (for pointers)

INHERITED Inherited from the layer below

SUCCESS Return 0 (for numeric return values) or a pointer

Core Layers

The file "perlio.c" provides the following layers:

"unix"
A basic non-buffered layer which calls Unix/POSIX read(), write(), lseek(), close(). No buffering. Even on platforms that distinguish between O_TEXT and O_BINARY this layer is always O_BINARY.
"perlio"
A very complete generic buffering layer which provides the whole of PerlIO API. It is also intended to be used as a "base class" for other layers. (For example its Read() method is implemented in terms of the Get_cnt()/Get_ptr()/Set_ptrcnt() methods).

"perlio" over "unix" provides a complete replacement for stdio as seen via PerlIO API. This is the default for USE_PERLIO when system's stdio does not permit perl's "fast gets" access, and which do not distinguish between "O_TEXT" and "O_BINARY".

"stdio"
A layer which provides the PerlIO API via the layer scheme, but implements it by calling system's stdio. This is (currently) the default if system's stdio provides sufficient access to allow perl's "fast gets" access and which do not distinguish between "O_TEXT" and "O_BINARY".
"crlf"
A layer derived using "perlio" as a base class. It provides Win32-like "\n" to CR,LF translation. Can either be applied above "perlio" or serve as the buffer layer itself. "crlf" over "unix" is the default if system distinguishes between "O_TEXT" and "O_BINARY" opens. (At some point "unix" will be replaced by a "native" Win32 IO layer on that platform, as Win32's read/write layer has various drawbacks.) The "crlf" layer is a reasonable model for a layer which transforms data in some way.
"mmap"
If Configure detects mmap() functions this layer is provided (with "perlio" as a "base") which does "read" operations by mmap()ing the file. This is typically only useful for reading.

DESCRIPCIÓN

Las capas de PerlIO son una forma de modificar el comportamiento de E/S de archivos de Perl. Permiten a los módulos de extensión o al código incorporado agregar funcionalidades como codificación, compresión o manejo de datos en memoria.

Capas Incluidas

Estas capas están disponibles directamente desde el núcleo de PerlIO.

"mmap"
Intenta usar mmap() para acceder al archivo. La mejora de rendimiento es marginal en sistemas modernos, por lo que existe principalmente como prueba de concepto. Es probable que se desvincule del núcleo en algún momento. La capa "mmap" es un modelo razonable para una capa "derivada" minimalista.
"pending"
Un derivado "interno" de "perlio" que se puede usar para proporcionar la función Unread() para capas que no tienen búfer o no quieren molestarse. (Básicamente, el Fill() de esta capa se saca de la pila y, por lo tanto, reanuda la lectura de la capa inferior).
"raw"
Una capa ficticia que nunca existe en la pila de capas. En cambio, cuando se "empuja", realmente saca la pila eliminándose a sí misma, y luego llama a la entrada de la tabla de funciones Binmode en todas las capas de la pila, lo que normalmente (a través de PerlIOBase_binmode) elimina cualquier capa que no tenga el bit "PERLIO_K_RAW" establecido. Las capas pueden modificar ese comportamiento definiendo su propia entrada Binmode.
"utf8"
Otra capa ficticia. Cuando se empuja, se saca a sí misma y establece la bandera "PERLIO_F_UTF8" en la capa que era (y ahora vuelve a ser) la parte superior de la pila.

Además, perlio.c proporciona una serie de funciones PerlIOBase_xxxx() que están destinadas a ser utilizadas en las ranuras de tabla de clases que no necesitan hacer nada especial para un método en particular.

Capas de Extensión

Las capas se pueden poner a disposición mediante módulos de extensión. Cuando se encuentra una capa desconocida, el código PerlIO realizará el equivalente a:

use PerlIO 'layer';

Donde layer es la capa desconocida. PerlIO.pm intentará entonces:

require PerlIO::layer;

Si después de ese proceso la capa aún no está definida, la llamada a "open" fallará.

Las siguientes capas de extensión se incluyen con perl:

":encoding"
use Encoding;

hace que esta capa esté disponible, aunque PerlIO.pm "sabe" dónde encontrarla. Es un ejemplo de una capa que toma un argumento, ya que se llama así:

open( $fh, "<:encoding(iso-8859-7)", $pathname );
":scalar"
Proporciona soporte para leer datos desde y escribir datos a un escalar. 
open( $fh, "+<:scalar", \$scalar );

Cuando un manejador se abre de esta manera, las lecturas obtienen bytes del valor de cadena de $scalar y las escrituras cambian el valor. En ambos casos, la posición en $scalar comienza en cero pero puede ser alterada mediante "seek" y determinada mediante "tell".

Tenga en cuenta que esta capa se implica al llamar a open() de esta manera:

open( $fh, "+<", \$scalar );
":via"
Proporcionado para permitir que las capas se implementen como código Perl. Por ejemplo: 
use PerlIO::via::StripHTML;
open( my $fh, "<:via(StripHTML)", "index.html" );

Ver PerlIO::via para más detalles.
