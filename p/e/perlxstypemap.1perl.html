PERLXSTYPEMAP(1perl) Perl Programmers Reference Guide PERLXSTYPEMAP(1perl)

NOMBRE

perlxstypemap - Mapeo de tipos C/Perl de Perl XS

DESCRIPCIÓN

Cuanto más pienses en la interconexión entre dos lenguajes, más te darás cuenta de que la mayor parte del esfuerzo del programador debe dedicarse a la conversión entre las estructuras de datos nativas de cada uno de los lenguajes involucrados. Esto tiene prioridad sobre otros asuntos como las diferentes convenciones de llamada, porque el espacio del problema es mucho mayor. Simplemente hay más formas de meter datos en memoria que formas de implementar una llamada a función.

El intento de solución de Perl XS a esto es el concepto de mapeos de tipos (typemaps). En un nivel abstracto, un mapeo de tipos XS de Perl no es más que una receta para convertir de una cierta estructura de datos de Perl a una cierta estructura de datos de C y viceversa. Dado que puede haber tipos de C que sean suficientemente similares entre sí como para justificar la conversión con la misma lógica, los mapeos de tipos XS se representan mediante un identificador único, de ahora en adelante llamado un tipo XS en este documento. Luego puedes decirle al compilador XS que múltiples tipos de C deben ser mapeados con el mismo mapeo de tipos XS.

En tu código XS, cuando defines un argumento con un tipo de C o cuando estás usando una sección "CODE:" y una sección "OUTPUT:" juntas con un tipo de retorno de C de tu XSUB, será el mecanismo de mapeo de tipos el que lo haga fácil.

Anatomía de un mapeo de tipos

En términos más prácticos, el mapeo de tipos es una colección de fragmentos de código que son utilizados por el compilador xsubpp para mapear parámetros y valores de funciones de C a valores de Perl. El archivo de mapeo de tipos puede consistir en tres secciones etiquetadas "TYPEMAP", "INPUT" y "OUTPUT". Una sección inicial sin etiqueta se asume como una sección "TYPEMAP". La sección INPUT le dice al compilador cómo traducir valores de Perl a variables de ciertos tipos de C. La sección OUTPUT le dice al compilador cómo traducir los valores de ciertos tipos de C a valores que Perl pueda entender. La sección TYPEMAP le dice al compilador qué fragmentos de código de INPUT y OUTPUT deben usarse para mapear un tipo de C dado a un valor de Perl. Las etiquetas de sección "TYPEMAP", "INPUT" o "OUTPUT" deben comenzar en la primera columna en líneas separadas y deben estar en mayúsculas.

Cada tipo de sección puede aparecer un número arbitrario de veces y no tiene por qué aparecer. Por ejemplo, un mapeo de tipos comúnmente puede carecer de secciones "INPUT" y "OUTPUT" si todo lo que necesita hacer es asociar tipos de C adicionales con tipos XS centrales como T_PTROBJ. Las líneas que comienzan con una almohadilla "#" se consideran comentarios y se ignoran en la sección "TYPEMAP", pero se consideran significativas en las secciones "INPUT" y "OUTPUT". Las líneas en blanco generalmente se ignoran.

Tradicionalmente, los mapeos de tipos debían escribirse en un archivo separado, convencionalmente llamado "typemap" en una distribución CPAN. Con ExtUtils::ParseXS (el compilador XS) versión 3.12 o mejor, que viene con perl 5.16, los mapeos de tipos también pueden ser incrustados directamente en el código XS utilizando una sintaxis similar a HERE-doc:

TYPEMAP: <<HERE
...
HERE

donde "HERE" puede ser reemplazado por otros identificadores como con los HERE-docs normales de Perl. Todos los detalles a continuación sobre el formato textual del mapeo de tipos siguen siendo válidos.

La sección "TYPEMAP" debe contener un par de tipo de C y tipo de XS por línea, como sigue. Un ejemplo del archivo de mapeo de tipos central:

TYPEMAP
# todas las variantes de char* son manejadas por el mapeo T_PV
char *          T_PV
const char *    T_PV
unsigned char * T_PV
...

Las secciones "INPUT" y "OUTPUT" tienen formatos idénticos, es decir, cada línea sin indentar inicia un nuevo mapeo de entrada o salida respectivamente. Un nuevo mapeo de entrada o salida debe comenzar con el nombre del tipo XS a mapear en una línea por sí solo, seguido del código que lo implementa indentado en las siguientes líneas. Ejemplo:

INPUT
T_PV
  $var = ($type)SvPV_nolen($arg)
T_PTR
  $var = INT2PTR($type,SvIV($arg))

Más adelante veremos el significado de esas variables que parecen Perlish.

Finalmente, aquí hay un ejemplo del archivo de mapeo de tipos completo para mapear cadenas de C del tipo "char *" a escalares/cadenas de Perl:

TYPEMAP
char *  T_PV
INPUT
T_PV
  $var = ($type)SvPV_nolen($arg)
OUTPUT
T_PV
  sv_setpv((SV*)$arg, $var);

Aquí hay un ejemplo más complicado: supongamos que querías que "struct netconfig" fuera bendecido a la clase "Net::Config". Una forma de hacerlo es usar guiones bajos (_) para separar los nombres de paquetes, como sigue:

typedef struct netconfig * Net_Config;

Y luego proporcionar una entrada de mapeo de tipos "T_PTROBJ_SPECIAL" que mapee guiones bajos a doble-dos puntos (::), y declarar "Net_Config" como de ese tipo:

TYPEMAP
Net_Config      T_PTROBJ_SPECIAL
INPUT
T_PTROBJ_SPECIAL
  if (sv_derived_from($arg, \"${(my $ntt=$ntype)=~s/_/::/g;\$ntt}\")){
    IV tmp = SvIV((SV*)SvRV($arg));
    $var = INT2PTR($type, tmp);
  }
  else
    croak(\"$var is not of type ${(my $ntt=$ntype)=~s/_/::/g;\$ntt}\")
OUTPUT
T_PTROBJ_SPECIAL
  sv_setref_pv($arg, \"${(my $ntt=$ntype)=~s/_/::/g;\$ntt}\",
               (void*)$var);

Las secciones INPUT y OUTPUT sustituyen los guiones bajos por doble-dos puntos sobre la marcha, dando el efecto deseado. Este ejemplo demuestra parte del poder y la versatilidad de la instalación de mapeo de tipos.

La macro "INT2PTR" (definida en perl.h) convierte un entero a un puntero de un tipo dado, teniendo en cuenta el posible tamaño diferente de enteros y punteros. También existen las macros "PTR2IV", "PTR2UV" y "PTR2NV", para mapear en la otra dirección, que pueden ser útiles en secciones OUTPUT.

El rol del archivo typemap en tu distribución

El mapeo de tipos predeterminado en el directorio lib/ExtUtils del código fuente de Perl contiene muchos tipos útiles que pueden ser utilizados por extensiones de Perl. Algunas extensiones definen mapeos de tipos adicionales que guardan en su propio directorio. Estos mapeos de tipos adicionales pueden referenciar mapeos INPUT y OUTPUT en el mapeo principal. El compilador xsubpp permitirá que el mapeo de tipos propio de la extensión anule cualquier mapeo que esté en el mapeo de tipos predeterminado. En lugar de usar un archivo typemap adicional, los mapeos de tipos pueden ser incrustados textualmente en XS con una sintaxis similar a heredoc. Ver la documentación sobre la palabra clave XS "TYPEMAP:".

Para distribuciones CPAN, puedes asumir que los tipos XS definidos por el núcleo de perl ya están disponibles. Adicionalmente, el mapeo de tipos central tiene tipos XS predeterminados para una gran cantidad de tipos de C. Por ejemplo, si simplemente devuelves un "char *" de tu XSUB, el mapeo de tipos central tendrá este tipo de C asociado con el tipo XS T_PV. Eso significa que tu cadena C será copiada al espacio PV (valor del puntero) de un nuevo escalar que será devuelto desde tu XSUB a Perl.

Si estás desarrollando una distribución CPAN usando XS, puedes añadir tu propio archivo llamado typemap a la distribución. Ese archivo puede contener mapeos de tipos que o bien mapean tipos específicos de tu código o que anulan los mapeos del archivo de mapeo de tipos central para tipos comunes de C.

Compartir mapeos de tipos entre distribuciones CPAN

A partir de ExtUtils::ParseXS versión 3.13_01 (viene con perl 5.16 y mejor), es bastante fácil compartir código de mapeo de tipos entre múltiples distribuciones CPAN. Asegurando que se use el Typemap

Para que el sistema de compilación de Perl use su archivo typemap, debe incluirlo como una dependencia de compilación en "Makefile.PL" (use "BUILD_REQUIRES") o en su "Build.PL" (use "build_requires").

Incluya la siguiente línea en la sección XS de su archivo XS (no rompa la línea):

INCLUDE_COMMAND: $^X -MExtUtils::Typemaps::Cmd
                 -e "print embeddable_typemap(q{Basic})"

Escribiendo Entradas de Typemap

Cada entrada de typemap de ENTRADA o SALIDA es una cadena de Perl entre comillas dobles que se evaluará en presencia de ciertas variables para obtener el código C final para mapear un cierto tipo C.

Esto significa que puede incrustar código Perl en su código (C) del typemap usando construcciones como "${ código perl que se evalúa a una referencia escalar aquí }". Un caso de uso común es generar mensajes de error que se refieren al nombre real de la función, incluso cuando se usa la característica ALIAS de XS:

${ $ALIAS ? \q[GvNAME(CvGV(cv))] : \qq["$pname"] }

Para muchos ejemplos de typemap, consulte el archivo typemap principal que se puede encontrar en el árbol de fuentes de perl en lib/ExtUtils/typemap.

Las variables de Perl que están disponibles para la interpolación en los typemaps son las siguientes:

  • $var - el nombre de la variable de entrada o salida, por ejemplo, RETVAL para valores de retorno.
  • $type - el tipo C bruto del parámetro, cualquier ":" reemplazado por "_". por ejemplo, para un tipo de "Foo::Bar", $type es "Foo__Bar"
  • $ntype - el tipo proporcionado con "*" reemplazado por "Ptr". por ejemplo, para un tipo de "Foo*", $ntype es "FooPtr"
  • $arg - la entrada de la pila, de la cual el parámetro es de entrada o salida, por ejemplo, ST(0)
  • $argoff - el desplazamiento de la pila de argumentos del argumento. es decir, 0 para el primer argumento, etc.
  • $pname - el nombre completo de la XSUB, incluyendo el nombre "PACKAGE", con cualquier "PREFIX" eliminado. Este es el nombre no-ALIAS.
  • $Package - el paquete especificado por la palabra clave "PACKAGE" más reciente.
  • $ALIAS - distinto de cero si la XSUB actual tiene algún alias declarado con "ALIAS".

Listado Completo de Typemaps Principales

Cada tipo C se representa mediante una entrada en el archivo typemap que es responsable de convertir variables de perl (SV, AV, HV, CV, etc.) desde y hacia ese tipo. Las siguientes secciones enumeran todos los tipos XS que vienen con perl por defecto.

T_SV
Esto simplemente pasa la representación C de la variable Perl (un SV*) dentro y fuera de la capa XS. Esto se puede usar si el código C quiere tratar directamente con la variable Perl.
T_SVREF
Se usa para pasar y devolver una referencia a un SV.

Tenga en cuenta que este typemap no decrementa el contador de referencia al devolver la referencia a un SV*. Ver también: T_SVREF_REFCOUNT_FIXED

T_SVREF_FIXED
Se usa para pasar y devolver una referencia a un SV. Esta es una variante fija de T_SVREF que decrementa el contador de referencias adecuadamente al devolver una referencia a un SV*. Introducido en perl 5.15.4.
T_AVREF
Desde el nivel de perl, esta es una referencia a un array de perl. Desde el nivel C, este es un puntero a un AV.

Tenga en cuenta que este typemap no decrementa el contador de referencia al devolver un AV*. Ver también: T_AVREF_REFCOUNT_FIXED

T_AVREF_REFCOUNT_FIXED
Desde el nivel de perl, esta es una referencia a un array de perl. Desde el nivel C, este es un puntero a un AV. Esta es una variante fija de T_AVREF que decrementa el contador de referencias adecuadamente al devolver un AV*. Introducido en perl 5.15.4.
T_HVREF
Desde el nivel de perl, esta es una referencia a un hash de perl. Desde el nivel C, este es un puntero a un HV.

Tenga en cuenta que este typemap no decrementa el contador de referencia al devolver un HV*. Ver también: T_HVREF_REFCOUNT_FIXED

T_HVREF_REFCOUNT_FIXED
Desde el nivel de perl, esta es una referencia a un hash de perl. Desde el nivel C, este es un puntero a un HV. Esta es una variante fija de T_HVREF que decrementa el contador de referencias adecuadamente al devolver un HV*. Introducido en perl 5.15.4.
T_CVREF
Desde el nivel de perl, esta es una referencia a una subrutina de perl (por ejemplo, $sub = sub { 1 };). Desde el nivel C, este es un puntero a un CV.

Tenga en cuenta que este typemap no decrementa el contador de referencia al devolver un HV*. Ver también: T_HVREF_REFCOUNT_FIXED

T_CVREF_REFCOUNT_FIXED
Desde el nivel de perl, esta es una referencia a una subrutina de perl (por ejemplo, $sub = sub { 1 };). Desde el nivel C, este es un puntero a un CV.

Esta es una variante fija de T_HVREF que decrementa el contador de referencias adecuadamente al devolver un HV*. Introducido en perl 5.15.4.

T_SYSRET
El typemap T_SYSRET se utiliza para procesar los valores de retorno de las llamadas al sistema. Solo es significativo al pasar valores de C a perl (no existe el concepto de pasar un valor de retorno del sistema de Perl a C).

Las llamadas al sistema devuelven -1 en caso de error (estableciendo ERRNO con la razón) y (generalmente) 0 en caso de éxito. Si el valor de retorno es -1, este typemap devuelve "undef". Si el valor de retorno no es -1, este typemap traduce un 0 (falso de perl) a "0 pero verdadero" (que es verdadero de perl) o devuelve el valor en sí, para indicar que el comando tuvo éxito.

El módulo POSIX hace un uso extensivo de este tipo.

T_UV
Un entero sin signo.
T_IV
Un entero con signo. Esto se convierte al tipo entero requerido cuando se pasa a C y se convierte a un IV cuando se pasa de vuelta a Perl.
T_INT
Un entero con signo. Este typemap convierte el valor de Perl a un tipo entero nativo (el tipo "int" en la plataforma actual). Al devolver el valor a perl, se procesa de la misma manera que para T_IV.

Su comportamiento es idéntico al uso de un tipo "int" en XS con T_IV.

T_ENUM
Un valor de enumeración. Se utiliza para transferir un componente de enumeración desde C. No hay razón para pasar un valor de enumeración a C ya que se almacena como un IV dentro de Perl.
T_BOOL
Un tipo booleano. Esto se puede usar para pasar valores verdaderos y falsos hacia y desde C.
T_U_INT
Esto es para enteros sin signo. Es equivalente a usar T_UV pero convierte explícitamente la variable al tipo "unsigned int". El tipo predeterminado para "unsigned int" es T_UV.
T_SHORT
Enteros cortos. Esto es equivalente a T_IV pero convierte explícitamente el retorno al tipo "short". El typemap predeterminado para "short" es T_IV.
T_U_SHORT
Enteros cortos sin signo. Esto es equivalente a T_UV pero convierte explícitamente el retorno al tipo "unsigned short". El typemap predeterminado para "unsigned short" es T_UV.

T_U_SHORT se utiliza para el tipo "U16" en el typemap estándar.

T_LONG
Enteros largos. Esto es equivalente a T_IV pero convierte explícitamente el retorno al tipo "long". El typemap predeterminado para "long" es T_IV.
T_U_LONG
Enteros largos sin signo. Esto es equivalente a T_UV pero convierte explícitamente el retorno al tipo "unsigned long". El typemap predeterminado para "unsigned long" es T_UV.

T_U_LONG se utiliza para el tipo "U32" en el typemap estándar.

T_CHAR
Caracteres individuales de 8 bits.
T_U_CHAR
Un byte sin signo.
T_FLOAT
Un número de punto flotante. Este typemap garantiza devolver una variable convertida a un "float".
T_NV
Un número de punto flotante de Perl. Similar a T_IV y T_UV en que el tipo de retorno se convierte al tipo numérico solicitado en lugar de a un tipo específico.
T_DOUBLE
Un número de punto flotante de doble precisión. Este typemap garantiza devolver una variable convertida a un "double".
T_PV
Una cadena (char *).
T_PTR
Una dirección de memoria (puntero). Típicamente asociado con un tipo "void *".
T_PTR
RREF
Similar a T_PTR excepto que el puntero se almacena en un escalar y la referencia a ese escalar se devuelve al llamante. Esto se puede usar para ocultar el valor real del puntero al programador ya que generalmente no se requiere directamente desde Perl.

El mapa de tipos verifica que se pase una referencia escalar de Perl a XS.

T_PTROBJ
Similar a T_PTRREF excepto que la referencia es "bendecida" (blessed) en una clase. Esto permite que el puntero se utilice como un objeto. Se usa más comúnmente para tratar con estructuras C. El mapa de tipos verifica que el objeto de Perl pasado a la rutina XS sea de la clase correcta (o parte de una subclase).

El puntero se "bendice" en una clase que se deriva del nombre del tipo del puntero, pero con todos los '*' en el nombre reemplazados por 'Ptr'.

Solo para XSubs de "DESTROY", T_PTROBJ se optimiza a T_PTRREF. Esto significa que la verificación de clase se omite.

T_REF_IV_REF
AÚN NO
T_REF_IV_PTR
Similar a T_PTROBJ en que el puntero se "bendice" en un objeto escalar. La diferencia es que cuando el objeto se pasa de vuelta a XS, debe ser del tipo correcto (la herencia no es compatible), mientras que T_PTROBJ admite la herencia.

El puntero se "bendice" en una clase que se deriva del nombre del tipo del puntero, pero con todos los '*' en el nombre reemplazados por 'Ptr'.

Solo para XSubs de "DESTROY", T_REF_IV_PTR se optimiza a T_PTRREF. Esto significa que la verificación de clase se omite.

T_PTRDESC
AÚN NO
T_REFREF
Similar a T_PTRREF, excepto que el puntero almacenado en el escalar referenciado se "desreferencia" y se copia a la variable de salida. Esto significa que T_REFREF es a T_PTRREF lo que T_OPAQUE es a T_OPAQUEPTR. ¿Todo claro?

Solo la parte de ENTRADA de esto está implementada (Perl a XSUB) y no hay usuarios conocidos en el núcleo o en CPAN.

T_REFOBJ
Como T_REFREF, excepto que realiza una verificación estricta de tipos (la herencia no es compatible).

Solo para XSubs de "DESTROY", T_REFOBJ se optimiza a T_REFREF. Esto significa que la verificación de clase se omite.

T_OPAQUEPTR
Esto se puede usar para almacenar bytes en el componente de cadena del SV. Aquí la representación de los datos es irrelevante para Perl y los bytes en sí mismos simplemente se almacenan en el SV. Se asume que la variable C es un puntero (los bytes se copian de esa ubicación de memoria). Si el puntero apunta a algo que está representado por 8 bytes, entonces esos 8 bytes se almacenan en el SV (y length() informará un valor de 8). Esta entrada es similar a T_OPAQUE.

En principio, el comando unpack() se puede usar para convertir los bytes de nuevo a un número (si el tipo subyacente se conoce como un número).

Esta entrada se puede usar para almacenar una estructura C (el número de bytes a copiar se calcula usando la función C "sizeof") y se puede usar como una alternativa a T_PTRREF sin tener que preocuparse por una fuga de memoria (ya que Perl limpiará el SV).

T_OPAQUE
Esto se puede usar para almacenar datos de tipos no puntero en la parte de cadena de un SV. Es similar a T_OPAQUEPTR excepto que el mapa de tipos recupera el puntero directamente en lugar de asumir que se está suministrando. Por ejemplo, si un entero se importa a Perl usando T_OPAQUE en lugar de T_IV, los bytes subyacentes que representan el entero se almacenarán en el SV, pero el valor entero real no estará disponible. Es decir, los datos son opacos para Perl.

Los datos pueden recuperarse usando la función "unpack" si se conoce el tipo subyacente del flujo de bytes.

T_OPAQUE admite la entrada y salida de tipos simples. T_OPAQUEPTR se puede usar para pasar estos bytes de vuelta a C si se acepta un puntero.

array implícita
xsubpp admite una sintaxis especial para devolver arreglos C empaquetados a Perl. Si el tipo de retorno XS se da como 
array(type, nelem)

xsubpp copiará el contenido de "nelem * sizeof(type)" bytes de RETVAL a un SV y lo empujará a la pila. Esto es realmente útil solo si el número de elementos a devolver se conoce en tiempo de compilación y no le importa tener una cadena de bytes en su SV. Use T_ARRAY para empujar un número variable de argumentos a la pila de retorno (aunque no se empaquetarán como una sola cadena).

Esto es similar a usar T_OPAQUEPTR pero se puede usar para procesar más de un elemento.

T_PACKED
Llama a funciones proporcionadas por el usuario para la conversión. Para "OUTPUT" (XSUB a Perl), se llama a una función llamada "XS_pack_$ntype" con el escalar de Perl de salida y la variable C de la que convertir. $ntype es el tipo C normalizado que se va a mapear a Perl. Normalizado significa que todos los "*" se reemplazan por la cadena "Ptr". El valor de retorno de la función se ignora.

Por el contrario, para el mapeo de "INPUT" (Perl a XSUB), se llama a la función llamada "XS_unpack_$ntype" con el escalar de Perl de entrada como argumento y el valor de retorno se convierte al tipo C mapeado y se asigna a la variable C de salida.

Una función de conversión de ejemplo para una estructura "mapeada por tipo" "foo_t *" podría ser:

static void
XS_pack_foo_tPtr(SV *out, foo_t *in)
{
  dTHX; /* por desgracia, la firma no incluye pTHX_ */
  HV* hash = newHV();
  hv_stores(hash, "int_member", newSViv(in->int_member));
  hv_stores(hash, "float_member", newSVnv(in->float_member));
  /* ... */
  /* mortalizar ya que tu pila no tiene conteo de referencias */
  sv_setsv(out, sv_2mortal(newRV_noinc((SV*)hash)));
}

La conversión de Perl a C se deja como ejercicio para el lector, pero el prototipo sería:

static foo_t *
XS_unpack_foo_tPtr(SV *in);

En lugar de una función C real que tenga que obtener el contexto del hilo usando "dTHX", puedes definir macros del mismo nombre y evitar la sobrecarga. Además, ten en cuenta liberar la memoria asignada por "XS_unpack_foo_tPtr".

T_PACKEDARRAY
T_PACKEDARRAY es similar a T_PACKED. De hecho, el mapa de tipos de "INPUT" (Perl a XSUB) es idéntico, pero el mapa de tipos de "OUTPUT" pasa un argumento adicional a la función "XS_pack_$ntype". Este tercer parámetro indica el número de elementos en la salida para que la función pueda manejar arreglos C de manera sensata. La variable debe ser declarada por el usuario y debe tener el nombre "count_$ntype" donde $ntype es el nombre normalizado del tipo C, como se explicó anteriormente. La firma de la función sería para el ejemplo anterior y "foo_t **": 
static void
XS_pack_foo_tPtrPtr(SV *out, foo_t *in, UV count_foo_tPtrPtr);

El tipo del tercer parámetro es arbitrario en lo que respecta al mapa de tipos. Simplemente tiene que estar en línea con la variable declarada.

Por supuesto, a menos que conozcas el número de elementos en el arreglo C "sometype **", dentro de tu XSUB, el valor de retorno de "foo_t ** XS_unpack_foo_tPtrPtr(...)" será difícil de descifrar. Dado que los detalles dependen del autor de XS (el usuario del mapa de tipos), existen varias soluciones, ninguna de las cuales es particularmente elegante. La solución más vista ha sido asignar memoria para N+1 punteros y asignar "NULL" al (N+1) ésimo para facilitar la iteración.

Alternativamente, usar un mapa de tipos personalizado para tus propósitos en primer lugar es probablemente preferible.

T_ARRAY
Esto se usa para convertir la lista de argumentos de Perl a un arreglo C y para empujar el contenido de un arreglo C a la pila de argumentos de Perl.

La firma de llamada habitual es

@out = array_func( @in );

Cualquier número de argumentos puede aparecer en la lista antes del arreglo, pero los arreglos de entrada y salida deben ser los últimos elementos de la lista.

Cuando se usa para pasar una lista de Perl a C, el escritor de XS debe proporcionar una función (con el nombre del tipo de arreglo pero con 'Ptr' sustituyendo a '*') para asignar la memoria requerida para contener la lista. Se debe devolver un puntero. Es responsabilidad del escritor de XS liberar la memoria al salir de la función. La variable "ix_$var" se establece en el número de elementos en el nuevo arreglo.

Al devolver un arreglo C a Perl, el escritor de XS debe proporcionar una variable entera llamada "size_$var" que contenga el número de elementos en el arreglo. Esto se usa para determinar cuántos elementos se deben empujar a la pila de argumentos de retorno. Esto no es necesario en la entrada ya que Perl sabe cuántos argumentos hay en la pila cuando se llama a la rutina. Normalmente, esta variable se llamaría "size_RETVAL".

Además, el tipo de cada elemento se determina a partir del tipo del arreglo. Si el arreglo usa el tipo "intArray *", xsubpp deducirá automáticamente que contiene variables de tipo "int" y usará esa entrada del mapa de tipos para realizar la copia de cada elemento. Todas las etiquetas de puntero '*' y 'Array' se eliminan del nombre para determinar el subtipo.

perlxstypemap — Map types between Perl and C in XS code

NAME

perlxstypemap — Map types between Perl and C in XS code

DESCRIPTION

This document describes the typemaps used by Perl’s XS mechanism. Typemaps are used to define how Perl data types are converted to and from C data types when calling C functions from Perl modules (or vice versa).

The typemap file is searched for in the following order:

  1. The typemap file specified by the TYPEMAP environment variable.

  2. The typemap file specified by the typemap file in the current directory.

  3. The typemap file specified by the typemap file in the Perl library directory (usually /usr/lib/perl5/5.x/Typemap).

A typemap file contains a series of entries, each defining a mapping between a Perl type and a C type. The format of an entry is:

  PerlType
    C_type T_ATTRS
    CODE

Where:

  • PerlType is the name of the Perl type (e.g., SV, IV, AV, HV, CV, GV, REGEXP, FILE*, PerlIO*, undef, null, int, double, char*, void*).

  • C_type is the corresponding C type (e.g., SV*, IV, AV*, HV*, CV*, GV*, REGEXP*, FILE*, PerlIO*, SV*, void, int, double, char*, void*).

  • T_ATTRS are optional attributes for the type mapping. Common attributes include:

    • T_IN: The type is used for passing arguments from Perl to C.
    • T_OUT: The type is used for passing return values from C to Perl.
    • T_INOUT: The type is used for both passing arguments from Perl to C and for return values from C to Perl.

  • CODE is a block of C code that performs the actual conversion between the Perl and C types.

The following are some common predefined typemaps:

T_INOUT
This is used for passing Perl filehandles to and from C using "PerlIO *" structures. The file handle can be used for reading and writing. This corresponds to the "+<" mode, see also T_IN and T_OUT.

See perliol for more information on the Perl IO abstraction layer. Perl must have been built with "-Duseperlio".

There is no check to assert that the filehandle passed from Perl to C was created with the right open() mode.

Hint: The perlxstut tutorial covers the T_INOUT, T_IN, and T_OUT XS types nicely.

T_IN
Same as T_INOUT, but the filehandle that is returned from C to Perl can only be used for reading (mode "<").
T_OUT
Same as T_INOUT, but the filehandle that is returned from C to Perl is set to use the open mode "+>".
