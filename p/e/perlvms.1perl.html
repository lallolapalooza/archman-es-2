NOMBRE

perlvms - Documentación específica de VMS para Perl

DESCRIPCIÓN

A continuación se presentan notas que describen detalles del comportamiento de Perl 5 en VMS. Son un complemento a la documentación regular de Perl 5, por lo que nos hemos centrado en las formas en que Perl 5 funciona de manera diferente bajo VMS en comparación con Unix, y en las interacciones entre Perl y el resto del sistema operativo. No hemos intentado duplicar descripciones completas de las características de Perl de la documentación principal de Perl, que se puede encontrar en el subdirectorio [.pod] de la distribución de Perl.

Esperamos que estas notas le ahorren confusión y noches de insomnio al escribir scripts de Perl en VMS. Si encuentra que hemos omitido algo que cree que debería aparecer aquí, no dude en enviar un mensaje a vmsperl@perl.org.

INSTALACIÓN

Las instrucciones para compilar e instalar Perl 5 se pueden encontrar en el archivo README.vms en el directorio raíz de la distribución de código fuente de Perl.

ORGANIZACIÓN DE LAS IMÁGENES DE PERL

Imágenes Principales

Durante el proceso de compilación, se producen tres imágenes de Perl. Miniperl.Exe es una imagen ejecutable que contiene toda la funcionalidad básica de Perl, pero no puede aprovechar las extensiones XS de Perl y tiene una lista codificada de ubicaciones de bibliotecas para cargar módulos puros de Perl. Se utiliza ampliamente para compilar y probar Perl y varias extensiones, pero no se instala.

La mayor parte de Perl completo reside en la imagen compartible PerlShr.Exe, que proporciona un núcleo al que se enlazan la imagen ejecutable de Perl y todas las extensiones de Perl. Generalmente se localiza a través del nombre lógico PERLSHR. Si bien es posible colocar la imagen en SYS$SHARE para que sea cargable, no se recomienda. Y aunque puede que desee INSTALAR la imagen por razones de rendimiento, no debe instalarla con privilegios; si lo hace, el resultado no será el esperado, ya que los privilegios de la imagen se deshabilitan durante el inicio de Perl.

Finalmente, Perl.Exe es una imagen ejecutable que contiene el punto de entrada principal para Perl, así como algo de código de inicialización. Debe colocarse en un directorio público y hacerse ejecutable para todos. Para ejecutar Perl con argumentos de línea de comandos, debe definir un comando externo para invocar esta imagen.

Extensiones de Perl

Las extensiones de Perl son paquetes que proporcionan código tanto XS como Perl para agregar nueva funcionalidad a perl. (XS es un metalenguaje que simplifica la escritura de código C que interactúa con Perl, vea perlxs para más detalles.) El código Perl de una extensión se trata como cualquier otro módulo de biblioteca: se pone a disposición en su script a través de la declaración "use" o "require" apropiada, y generalmente define un paquete Perl que contiene la extensión.

La porción de la extensión proporcionada por el código XS puede conectarse al resto de Perl de una de dos maneras. En la configuración estática, el código objeto de la extensión se enlaza directamente a PerlShr.Exe y se inicializa cada vez que se invoca Perl. En la configuración dinámica, el código máquina de la extensión se coloca en una imagen compartible separada, que es mapeada por DynaLoader de Perl cuando la extensión se "use" o "require" en su script. Esto le permite mantener la extensión como una entidad separada, a costa de llevar un registro de la imagen compartible adicional. La mayoría de las extensiones se pueden configurar como estáticas o dinámicas.

El código fuente de una extensión generalmente reside en su propio directorio. Por lo general, se proporcionan al menos tres archivos: Extshortname.xs (donde Extshortname es la parte del nombre de la extensión después del último "::"), que contiene el código XS, Extshortname.pm, el módulo de biblioteca de Perl para la extensión, y Makefile.PL, un script de Perl que utiliza los módulos de la biblioteca "MakeMaker" suministrados con Perl para generar un archivo Descrip.MMS para la extensión.

Instalación de extensiones estáticas

Dado que las extensiones estáticas se incorporan directamente a PerlShr.Exe, tendrá que reconstruir Perl para incorporar una nueva extensión. Deberá editar el Descrip.MMS o Makefile principal que utilice para compilar Perl, añadiendo el nombre de la extensión a la macro "ext" y el archivo objeto de la extensión a la macro "extobj". También necesitará compilar el archivo objeto de la extensión, ya sea añadiendo dependencias al Descrip.MMS principal o utilizando un Descrip.MMS separado para la extensión. Luego, reconstruya PerlShr.Exe para incorporar el nuevo código.

Finalmente, deberá copiar el módulo de biblioteca de Perl de la extensión al subdirectorio [.Extname] debajo de uno de los directorios en @INC, donde Extname es el nombre de la extensión, con todos los "::" reemplazados por "." (por ejemplo, el módulo de biblioteca para la extensión Foo::Bar se copiaría a un subdirectorio [.Foo.Bar]).

Instalación de extensiones dinámicas

En general, el kit distribuido para una extensión de Perl incluye un archivo llamado Makefile.PL, que es un programa de Perl que se utiliza para crear un archivo Descrip.MMS que se puede usar para compilar e instalar los archivos requeridos por la extensión. El kit debe ser descomprimido en un árbol de directorios **no** bajo el directorio raíz de Perl, y el procedimiento para compilar la extensión es simplemente

$ perl Makefile.PL  ! Crear Descrip.MMS
$ mmk               ! Compilar archivos necesarios
$ mmk test          ! Ejecutar código de prueba, si se suministra
$ mmk install       ! Instalar en el árbol público de Perl

El soporte de VMS para este proceso en la versión actual de Perl es suficiente para manejar la mayoría de las extensiones. (Vea la documentación de MakeMaker para más detalles sobre las opciones de instalación para extensiones.)

  • el subdirectorio [.Lib.Auto.Arch$PVersExtname] de uno de los directorios en @INC (donde PVers es la versión de Perl que está utilizando, tal como se proporciona en $], con '.' convertido a '_'), o
  • uno de los directorios en @INC, o
  • un directorio que el módulo de biblioteca de Perl de la extensión pasa a DynaLoader al pedirle que mapee la imagen compartible, o
  • Sys$Share o Sys$Library.

Si la imagen compartible no se encuentra en ninguno de estos lugares, necesitará definir un nombre lógico Extshortname, donde Extshortname es la porción del nombre de la extensión después del último "::", que traduce a la especificación completa del archivo de la imagen compartible.

Especificaciones de archivos

Sintaxis

Hemos intentado hacer que Perl sea consciente de las especificaciones de archivos tanto al estilo VMS como al estilo Unix siempre que sea posible. Puede usar cualquiera de los dos estilos, o ambos, en la línea de comandos y en scripts, pero no puede combinar los dos estilos dentro de una sola especificación de archivo. VMS Perl interpreta los nombres de ruta de Unix de manera muy similar a como lo hace el CRTL (por ejemplo, el primer componente de una ruta absoluta se lee como el nombre del dispositivo para la especificación del archivo VMS). Existe un conjunto de funciones proporcionadas en el paquete "VMS::Filespec" para la interconversión explícita entre la sintaxis VMS y Unix; su documentación proporciona más detalles.

Hemos intentado minimizar la dependencia de los módulos de biblioteca de Perl de la sintaxis de Unix, pero puede encontrar que algunos de ellos, así como algunos scripts escritos para sistemas Unix, requerirán que utilice la sintaxis de Unix, ya que asumirán que '/' es el separador de directorios, etc. Si encuentra instancias de esto en la propia distribución de Perl, por favor, háganoslo saber, para que podamos intentar solucionarlo.

Platform-Specific Issues

The following issues are specific to the OpenVMS port of Perl.

Filename Conventions

OpenVMS has two distinct filename conventions: the traditional VMS style (e.g., "DEVICES:[DIRECTORY]FILENAME.TYPE;VERSION") and the POSIX/Unix style (e.g., "/devices/directory/filename.type"). Perl can work with either convention. However, there are issues to consider when interacting with other tools or when specific OpenVMS features are enabled.

When Perl needs to convert a filename from one convention to another, it calls conversion routines which rely on the C run-time library (CRTL). The behavior of these routines can be modified by the presence of certain logical names. If you need a specific operating system format, then you need either to check the appropriate DECC$ feature logical, or call a conversion routine to force it to that format.

The feature logical name DECC$FILENAME_UNIX_REPORT modifies traditional Perl behavior in the conversion of file specifications from Unix to VMS format in order to follow the extended character handling rules now expected by the CRTL. Specifically, when this feature is in effect, the "./.../" in a Unix path is now translated to "[.^.^.^.]" instead of the traditional VMS "[...]". To be compatible with what MakeMaker expects, if a VMS path cannot be translated to a Unix path, it is passed through unchanged, so unixify("[...]") will return "[...]".

There are several ambiguous cases where a conversion routine cannot determine whether an input filename is in Unix format or in VMS format, since now both VMS and Unix file specifications may have characters in them that could be mistaken for syntax delimiters of the other type. So some pathnames simply cannot be used in a mode that allows either type of pathname to be present. Perl will tend to assume that an ambiguous filename is in Unix format.

Allowing "." as a version delimiter is simply incompatible with determining whether a pathname is in VMS format or in Unix format with extended file syntax. There is no way to know whether "perl-5.8.6" is a Unix "perl-5.8.6" or a VMS "perl-5.8;6" when passing it to unixify() or vmsify().

The DECC$FILENAME_UNIX_REPORT logical name controls how Perl interprets filenames to the extent that Perl uses the CRTL internally for many purposes, and attempts to follow CRTL conventions for reporting filenames. The DECC$FILENAME_UNIX_ONLY feature differs in that it expects all filenames passed to the C run-time to be already in Unix format. This feature is not yet supported in Perl since Perl uses traditional OpenVMS file specifications internally and in the test harness, and it is not yet clear whether this mode will be useful or useable. The feature logical name DECC$POSIX_COMPLIANT_PATHNAMES is new with the RMS Symbolic Link SDK and included with OpenVMS v8.3, but is not yet supported in Perl.

Filename Case

Perl enables DECC$EFS_CASE_PRESERVE and DECC$ARGV_PARSE_STYLE by default. Note that the latter only takes effect when extended parse is set in the process in which Perl is running. When these features are explicitly disabled in the environment or the CRTL does not support them, Perl follows the traditional CRTL behavior of downcasing command-line arguments and returning file specifications in lower case only.

N. B. It is very easy to get tripped up using a mixture of other programs, external utilities, and Perl scripts that are in varying states of being able to handle case preservation. For example, a file created by an older version of an archive utility or a build utility such as MMK or MMS may generate a filename in all upper case even on an ODS-5 volume. If this filename is later retrieved by a Perl script or module in a case preserving environment, that upper case name may not match the mixed-case or lower-case expectations of the Perl code. Your best bet is to follow an all-or-nothing approach to case preservation: either don't use it at all, or make sure your entire toolchain and application environment support and use it.

OpenVMS Alpha v7.3-1 and later and all version of OpenVMS I64 support case sensitivity as a process setting (see "SET PROCESS /CASE_LOOKUP=SENSITIVE"). Perl does not currently support case sensitivity on VMS, but it may in the future, so Perl programs should use the "File::Spec->case_tolerant" method to determine the state, and not the $^O variable.

Symbolic Links

When built on an ODS-5 volume with symbolic links enabled, Perl by default supports symbolic links when the requisite support is available in the filesystem and CRTL (generally 64-bit OpenVMS v8.3 and later). There are a number of limitations and caveats to be aware of when working with symbolic links on VMS. Most notably, the target of a valid symbolic link must be expressed as a Unix-style path and it must exist on a volume visible from your POSIX root (see the "SHOW ROOT" command in DCL help). For further details on symbolic link capabilities and requirements, see chapter 12 of the CRTL manual that ships with OpenVMS v8.3 or later.

Wildcard expansion

File specifications containing wildcards are allowed both on the command line and within Perl globs (e.g. "<*.c>"). If the wildcard filespec uses VMS syntax, the resultant filespecs will follow VMS syntax; if a Unix-style filespec is passed in, Unix-style filespecs will be returned. Similar to the behavior of wildcard globbing for a Unix shell, one can escape command line wildcards with double quotation marks """ around a perl program command line argument. However, owing to the stripping of """ characters carried out by the C handling of argv you will need to escape a construct such as this one (in a directory containing the files PERL.C, PERL.EXE, PERL.H, and PERL.OBJ):

$ perl -e "print join(' ',@ARGV)" perl.*
perl.c perl.exe perl.h perl.obj

in the following triple quoted manner:

$ perl -e "print join(' ',@ARGV)" """perl.*"""
perl.*

In both the case of unquoted command line arguments or in calls to glob() VMS wildcard expansion is performed. (csh-style wildcard expansion is available if you use "File::Glob::glob".) If the wildcard filespec contains a device or directory specification, then the resultant filespecs will also contain a device and directory; otherwise, device and directory information are removed. VMS-style resultant filespecs will contain a full device and directory, while Unix-style resultant filespecs will contain only as much of a directory path as was present in the input filespec. For example, if your default directory is Perl_Root:[000000], the expansion of "[.t]*.*" will yield filespecs like "perl_root:[t]base.dir", while the expansion of "t/*/*" will yield filespecs like "t/base.dir". (This is done to match the behavior of glob expansion performed by Unix shells.)

Similarly, the resultant filespec will contain the file version only if one was present in the input filespec.

Pipes

Input and output pipes to Perl filehandles are supported; the "file name" is passed to lib$spawn() for asynchronous execution. You should be careful to close any pipes you have opened in a Perl script, lest you leave any "orphaned" subprocesses around when Perl exits.

You may also use backticks to invoke a DCL subprocess, whose output is used as the return value of the expression. The string between the backticks is handled as if it were the argument to the "system" operator (see below). In this case, Perl will wait for the subprocess to complete before continuing.

The mailbox (MBX) that perl can create to communicate with a pipe defaults to a buffer size of 8192 on 64-bit systems, 512 on VAX. The default buffer size is adjustable via the logical name PERL_MBX_SIZE provided that the value falls between 128 and the SYSGEN parameter MAXBUF inclusive. For example, to set the mailbox size to 32767 use "$ENV{'PERL_MBX_SIZE'} = 32767;" and then open and use pipe constructs. An alternative would be to issue the command:

$ Define PERL_MBX_SIZE 32767

before running your wide record pipe program. A larger value may improve performance at the expense of the BYTLM UAF quota.

PERL5LIB and PERLLIB

The PERL5LIB and PERLLIB environment elements work as documented in perl, except that the element separator is, by default, '|' instead of ':'. However, when running under a Unix shell as determined by the logical name "GNV$UNIX_SHELL", the separator will be ':' as on Unix systems. The directory specifications may use either VMS or Unix syntax.

The Perl Forked Debugger

The Perl forked debugger places the debugger commands and output in a separate X-11 terminal window so that commands and output from multiple processes are not mixed together.

Perl on VMS supports an emulation of the forked debugger when Perl is run on a VMS system that has X11 support installed.

To use the forked debugger, you need to have the default display set to an X-11 Server and some environment variables set that Unix expects.

The forked debugger requires the environment variable "TERM" to be "xterm", and the environment variable "DISPLAY" to exist. "xterm" must be in lower case.

$define TERM "xterm"
$define DISPLAY "hostname:0.0"

Currently the value of "DISPLAY" is ignored. It is recommended that it be set to be the hostname of the display, the server and screen in Unix notation. In the future the value of DISPLAY may be honored by Perl instead of using the default display.

It may be helpful to always use the forked debugger so that script I/O is separated from debugger I/O. You can force the debugger to be forked by assigning a value to the logical name <PERLDB_PIDS> that is not a process identification number.

$define PERLDB_PIDS XXXX

PERL_VMS_EXCEPTION_DEBUG

The PERL_VMS_EXCEPTION_DEBUG being defined as "ENABLE" will cause the VMS debugger to be invoked if a fatal exception that is not otherwise handled is raised. The purpose of this is to allow debugging of

problemas internos de Perl que causarían tal condición.

Esto permite al programador examinar la pila de ejecución y las variables para descubrir la causa de la excepción. Dado que el depurador se invoca justo cuando el intérprete de Perl está a punto de salir de forma fatal, continuar la ejecución en modo de depuración no suele ser práctico.

Iniciar Perl en el depurador de VMS puede alterar el perfil de ejecución del programa de tal manera que tales problemas no se reproduzcan.

La función "kill" se puede usar para probar esta funcionalidad desde dentro de un programa.

Al estilo típico de VMS, solo la primera letra del valor de este nombre lógico se verifica realmente de forma insensible a mayúsculas y minúsculas, y se considera habilitado si su valor es "T", "1" o "E".

Este nombre lógico debe definirse antes de iniciar Perl.

Línea de comandos

Redirección de E/S y ejecución en segundo plano

Perl para VMS admite la redirección de entrada y salida en la línea de comandos, utilizando un subconjunto de la sintaxis de Bourne shell:

  • "<archivo" lee stdin desde "archivo",
  • ">archivo" escribe stdout a "archivo",
  • ">>archivo" añade stdout a "archivo",
  • "2>archivo" escribe stderr a "archivo",
  • "2>>archivo" añade stderr a "archivo", y
  • "2>&1" redirige stderr a stdout.

Además, la salida puede enviarse a un subproceso mediante el carácter '|'. Todo lo que aparezca después de este carácter en la línea de comandos se pasa a un subproceso para su ejecución; el subproceso toma la salida de Perl como su entrada.

Finalmente, si la línea de comandos termina con '&', todo el comando se ejecuta en segundo plano como un subproceso asíncrono.

Conmutadores de línea de comandos

Los siguientes conmutadores de línea de comandos se comportan de manera diferente en VMS de lo descrito en perlrun. Tenga en cuenta también que, para pasar conmutadores en mayúsculas a Perl, debe encerrarlos entre comillas dobles en la línea de comandos, ya que el CRTL convierte en minúsculas todas las cadenas no entrecomilladas.

En las versiones más recientes de 64 bits de OpenVMS, una configuración del proceso ahora controla si se necesita entrecomillado para preservar la mayúsculas de los argumentos de la línea de comandos.

-i
Si está presente el conmutador "-i" pero no se proporciona una extensión para una copia de seguridad, la edición en el lugar crea una nueva versión de un archivo; la copia existente no se elimina. (Tenga en cuenta que si se proporciona una extensión, un archivo existente se renombra al archivo de copia de seguridad, como ocurre en otros sistemas operativos, por lo que no permanece como una versión anterior bajo el nombre de archivo original).
-S
Si está presente el conmutador "-S" o "-"S"" *y* el nombre del script no contiene un directorio, Perl traduce el nombre lógico DCL$PATH como una lista de búsqueda, utilizando cada traducción como un directorio en el que buscar el script. Además, si no se especifica un tipo de archivo, Perl busca en cada directorio un archivo que coincida con el nombre especificado, con un tipo en blanco, un tipo de .pl y un tipo de .com, en ese orden.
-u
El conmutador "-u" hace que el depurador de VMS se invoque después de que el programa Perl se compile, pero antes de que se ejecute. No crea un archivo de volcado de núcleo.

Pruebas de archivo
Las pruebas "-b", "-B", "-c", "-C", "-d", "-e", "-f", "-o", "-M", "-s", "-S", "-t", "-T" y "-z" funcionan como se describe. Los valores de retorno para "-r", "-w" y "-x" indican si realmente puede acceder al archivo; esto puede no reflejar las protecciones de archivo basadas en UIC. Dado que las UIC real y efectiva no difieren en VMS, "-O", "-R", "-W" y "-X" son equivalentes a "-o", "-r", "-w" y "-x". De manera similar, varias otras pruebas, incluyendo "-A", "-g", "-k", "-l", "-p" y "-u", no son particularmente significativas en VMS, y los valores devueltos por estas pruebas reflejan lo que su rutina CRTL stat() hace con los bits equivalentes en el campo st_mode. Finalmente, "-d" devuelve verdadero si se le pasa una especificación de dispositivo sin un directorio explícito (por ejemplo, "DUA1:"), así como si se le pasa un directorio.

Existen nombres lógicos de característica DECC y atributos de volumen ODS-5 que también controlan qué valores se devuelven para los campos de fecha.

Nota: Algunos sitios han informado problemas al usar las pruebas de acceso a archivos ("-r", "-w" y "-x") en archivos a los que se accede a través de DFS de DEC. Específicamente, dado que DFS no proporciona actualmente acceso a la cabecera de archivo extendida de archivos en volúmenes remotos, los intentos de examinar la ACL fallan y las pruebas de archivo devolverán falso, con $! indicando que el archivo no existe. Puede usar "stat" en estos archivos, ya que solo verifica la protección basada en UIC, y luego verificar manualmente los bits apropiados, según lo definido por su archivo stat.h del compilador C, en el valor de modo que devuelve, si necesita una aproximación de las protecciones del archivo.

backticks
Los backticks crean un subproceso y le pasan la cadena encerrada para su ejecución como un comando DCL. Dado que el subproceso se crea directamente a través de "lib$spawn()", se puede especificar cualquier cadena de comando DCL válida.

El operador "binmode" intentará asegurar que no ocurra ninguna traducción de control de retorno al leer o escribir en este manejador de archivo. Dado que esto implica reabrir el archivo y luego restaurar su indicador de posición de archivo, si esta función r
Devuelve `FALSE`, el manejador de archivo subyacente puede que ya no apunte a un archivo abierto, o puede que apunte a una posición diferente en el archivo que antes de que se llamase "binmode".

Tenga en cuenta que "binmode" no es generalmente necesario cuando se utilizan manejadores de archivo normales; se proporciona para que pueda controlar la E/S de archivos con estructura de registros existente cuando sea necesario. También puede utilizar la función "vmsfopen" en la extensión VMS::Stdio para obtener un control más preciso de la E/S a archivos y dispositivos con diferentes estructuras de registros.

crypt TEXTO_PLANO, USUARIO
El operador "crypt" utiliza el servicio del sistema "sys$hash_password" para generar la representación hasheada de TEXTO_PLANO. Si USUARIO es un nombre de usuario válido, el algoritmo y los valores de la sal se toman del registro UAF de ese usuario. Si no lo es, se utiliza el algoritmo preferido y una sal de 0. El valor cifrado de cuádruple palabra se devuelve como una cadena de 8 caracteres.

El valor devuelto por "crypt" puede compararse con la contraseña cifrada del UAF devuelta por las funciones "getpw*", para autenticar a los usuarios. Si va a hacer esto, recuerde que la contraseña cifrada en el UAF se generó utilizando cadenas de nombre de usuario y contraseña en mayúsculas; tendrá que convertir a mayúsculas los argumentos para "crypt" para asegurarse de que obtendrá el valor correcto:

sub validate_passwd {
    my($user,$passwd) = @_;
    my($pwdhash);
    if ( !($pwdhash = (getpwnam($user))[1]) ||
           $pwdhash ne crypt("\U$passwd","\U$name") ) {
        intruder_alert($name);
    }
    return 1;
}
die
"die" forzará que el estado de salida nativo de VMS sea un código SS$_ABORT si ninguno de los valores de estado $! o $? son tales que harían que el estado nativo se interpretase como SEVERO_ERROR para el manejo de errores de DCL.

Cuando "PERL_VMS_POSIX_EXIT" está activo (ver "$?" más abajo), el valor del estado de salida nativo de VMS tendrá uno de los $! o $? o $^E o el valor Unix 255 codificado de forma que el valor original efectivo pueda ser decodificado por otros programas escritos en C, incluyendo Perl y el paquete GNV. Según el comportamiento normal de "die" fuera de VMS, si $! o $? son distintos de cero, uno de esos valores se codificará en un valor de estado nativo de VMS. Si ambos valores Unix son 0, y el valor de $^E tiene un nivel de severidad ERROR o SEVERE_ERROR, entonces el valor de $^E se usará como código de salida tal cual. Si ninguna de las anteriores aplica, el valor Unix 255 se codificará en un valor de estado de salida nativo de VMS.

Por favor, tenga en cuenta una diferencia significativa en el comportamiento de "die" en el modo "PERL_VMS_POSIX_EXIT": no fuerza un estado SEVERE_ERROR de VMS al salir. Los valores de salida Unix de 2 a 255 se codificarán en valores de estado de VMS con niveles de severidad SUCCESS. El valor de salida Unix 1 se codificará en un valor de estado de VMS con un nivel de severidad ERROR. Esto es para ser compatible con la forma en que la biblioteca C de VMS codifica estos valores.

El nivel de severidad mínimo establecido por "die" en modo "PERL_VMS_POSIX_EXIT" puede cambiarse a ERROR o superior en el futuro dependiendo de los resultados de las pruebas y una revisión adicional.

Consulte "$?" para una descripción de la codificación del valor Unix para producir un estado nativo de VMS que lo contenga.

dump
En lugar de hacer que Perl aborte y vuelque el núcleo, el operador "dump" invoca el depurador de VMS. Si continúa ejecutando el programa Perl bajo el depurador, el control se transferirá a la etiqueta especificada como argumento para "dump", o, si no se especificó ninguna etiqueta, de vuelta al principio del programa. Todo el estado restante del programa (por ejemplo, valores de variables, manejadores de archivos abiertos) no se ve afectado al llamar a "dump".
exec LISTA
Una llamada a "exec" hará que Perl salga e invoque el comando dado como argumento a "exec" a través de "lib$do_command". Si el argumento comienza con '@' o '$' (que no sea parte de un especificador de archivo), entonces se ejecuta como un comando DCL. De lo contrario, el primer token de la línea de comandos se trata como el especificador de archivo de una imagen para ejecutar, y se intenta invocarla (utilizando .Exe y los valores predeterminados del proceso para expandir el especificador de archivo) y pasar el resto del argumento de "exec" como parámetros. Si el token no tiene tipo de archivo y coincide con un archivo con tipo nulo, se intenta determinar si el archivo es una imagen ejecutable que debería invocarse usando "MCR" o un archivo de texto que debería pasarse a DCL como un procedimiento de comando.
fork
Aunque en principio el operador "fork" podría implementarse a través de (y con las mismas limitaciones bastante severas que) la rutina vfork() de CRTL, y aunque hay soporte interno para hacer precisamente eso, la implementación nunca se completó, lo que hace que "fork" no esté disponible actualmente. Se espera un verdadero fork() del kernel en una futura versión de VMS, y el pseudo-fork basado en hilos del intérprete puede estar disponible en una futura versión de Perl en VMS (ver perlfork). Mientras tanto, utilice "system", las comillas invertidas o los manejadores de archivo en tubería para crear subprocesos.
getpwent
getpwnam
getpwuid
Estos operadores obtienen la información descrita en perlfunc, si tiene los privilegios necesarios para recuperar la información UAF del usuario nombrado a través de "sys$getuai". Si no, solo se devuelven los elementos $name, $uid y $gid. El elemento $dir contiene el directorio de inicio de sesión en sintaxis VMS, mientras que el elemento $comment contiene el directorio de inicio de sesión en sintaxis Unix. El elemento $gcos contiene el campo del propietario del registro UAF. El elemento $quota no se utiliza.
gmtime
El operador "gmtime" funcionará correctamente si tiene una rutina gmtime() de CRTL que funcione, o si el nombre lógico SYS$TIMEZONE_DIFFERENTIAL está definido como el número de segundos que deben añadirse a UTC para obtener la hora local. (Este nombre lógico se define automáticamente si está ejecutando una versión de VMS con soporte UTC incorporado). Si ninguno de estos casos es cierto, se imprime un mensaje de advertencia y se devuelve "undef".
kill
En la mayoría de los casos, "kill" se implementa a través del servicio del sistema no documentado $SIGPRC, que tiene la misma secuencia de llamada que $FORCEX, pero lanza una excepción en el proceso de destino en lugar de forzarlo a llamar a $EXIT. En general, "kill" sigue el comportamiento de la función kill() de CRTL, pero a diferencia de esa función puede ser llamado desde dentro de un manejador de señales. Además, a diferencia de "kill" en algunas versiones de CRTL, el "kill" de Perl verifica la validez de la señal pasada y devuelve un error en lugar de intentar enviar una señal no reconocida.

Además, los valores de señal negativos no hacen nada especial en VMS; simplemente se convierten al valor positivo correspondiente.

qx//
Consulte la entrada sobre "comillas invertidas" más arriba.
select (llamada al sistema)
Si Perl no se compiló con soporte para sockets, la versión de llamada al sistema de "select" no está disponible en absoluto. Si hay soporte para sockets, entonces la versión de llamada al sistema de "select" solo funciona para descriptores de archivo adjuntos a sockets. No proporcionará información sobre archivos regulares o tuberías, ya que la rutina select() de CRTL no proporciona esta funcionalidad.
stat EXPR
Dado que VMS realiza un seguimiento de los archivos según un esquema diferente al de Unix, no es realmente posible representar el ID del archivo en los campos "st_dev" y "st_ino" de una "struct stat". Perl hace lo mejor que puede, sin embargo, y los valores que utiliza son bastante improbables que sean los mismos para dos archivos diferentes. Sin embargo, no podemos garantizar esto, así que ten cuidado al escribir scripts.
system LISTA
El operador "system" crea un subproceso y pasa sus argumentos al subproceso para su ejecución como un comando DCL. Dado que el subproceso se crea directamente a través de "lib$spawn()", se puede especificar cualquier cadena de comando DCL válida. Si la cadena comienza con '@', se trata como un comando DCL incondicionalmente. De lo contrario, si el primer token contiene un carácter utilizado como delimitador en la especificación de archivo (por ejemplo, ":" o "]"), se intenta expandirlo utilizando un tipo predeterminado de .Exe y los valores predeterminados del proceso, y si tiene éxito, el archivo resultante se invoca a través de "MCR". Esto le permite invocar una imagen directamente simplemente pasando la especificación del archivo a "system"

Funciones y operadores integrados de Perl

system LIST
La forma system() en VMS utiliza el método de invocación de comandos de DCL. A menos que especifique "use vmsish 'csh'", que le permite invocar un comando de la shell C si está disponible, o si ha establecido la variable de entorno PERLSH para que apunte a un intérprete de shell alternativo, el comando se invoca como lo haría el intérprete de DCL.

Si el primer elemento de LIST es un nombre de archivo potencialmente calificado (es decir, contiene un punto), Perl intenta determinar si el archivo es un ejecutable y si tiene permisos de ejecución. Si es así, se invoca usando el método de ejecución de comandos de DCL. Si no es así, o si el nombre del archivo no está cualificado, Perl lo pasa a DCL tal cual, para que sea interpretado por DCL. Si se confía en el método de ejecución de comandos de DCL, y si no se puede determinar el tipo de archivo y se puede determinar si el archivo es ejecutable, entonces DCL intentará tratar el comando como un comando en línea, como un procedimiento de comandos o como un ejecutable, de acuerdo con las reglas de DCL. Si no se puede determinar si el archivo es ejecutable (por ejemplo, si el tipo de archivo no se especifica y el nombre del archivo no se ajusta al patrón común de los archivos ejecutables de VMS, como.EXE o .COM), Perl intenta determinar si el archivo es una imagen ejecutable que debería invocarse con "MCR" o un archivo de texto que debería pasarse a DCL como un procedimiento de comandos.

Si LIST es una cadena vacía, "system" inicia un subproceso interactivo de DCL, de la misma manera que al escribir SPAWN en el símbolo del sistema de DCL.

Perl espera a que el subproceso complete antes de continuar la ejecución en el proceso actual. Como se describe en perlfunc, el valor de retorno de "system" es un "estado" falso que sigue la semántica POSIX a menos que el pragmático "use vmsish 'status'" esté en vigor; consulte la descripción de $? en este documento para obtener más detalles.

time
El valor devuelto por "time" es el desplazamiento en segundos desde 01-ENE-1970 00:00:00 (al igual que la rutina times() de CRTL), para facilitar la vida al código que proviene del mundo POSIX/Unix.
times
El array devuelto por el operador "times" se divide según las mismas reglas que la rutina times() de CRTL. Por lo tanto, los elementos de "tiempo de sistema" siempre serán 0, ya que no hay diferencia entre el "tiempo de usuario" y el "tiempo de sistema" en VMS, y el tiempo acumulado por un subproceso puede o no aparecer por separado en el campo "tiempo hijo", dependiendo de si times() realiza un seguimiento de los subprocesos por separado. Tenga en cuenta especialmente que VAXCRTL (al menos) solo realiza un seguimiento de los subprocesos iniciados mediante fork() y exec(); no acumulará los tiempos de los subprocesos iniciados a través de tuberías, system() o comillas invertidas.
unlink LIST
"unlink" eliminará solo la versión más alta de un archivo; para eliminar todas las versiones, debe decir 
1 while unlink LIST;

Es posible que necesite realizar este cambio en scripts escritos para un sistema Unix que esperan que después de una llamada a "unlink", no existan archivos con los nombres pasados a "unlink". (Nota: Esto se puede cambiar en tiempo de compilación; si "use Config" y $Config{'d_unlink_all_versions'} es "define", entonces "unlink" eliminará todas las versiones de un archivo en la primera llamada.)

"unlink" eliminará un archivo si es posible, incluso si requiere cambiar la protección del archivo (aunque no intentará cambiar la protección del directorio padre). Puede saber si tiene acceso explícito de eliminación a un archivo utilizando el operador "VMS::Filespec::candelete". Por ejemplo, para eliminar solo los archivos a los que tiene acceso de eliminación, podría decir algo como

sub safe_unlink {
    my($file,$num);
    foreach $file (@_) {
        next unless VMS::Filespec::candelete($file);
        $num += unlink $file;
    }
    $num;
}

(o podría simplemente usar "VMS::Stdio::remove", si ha instalado la extensión VMS::Stdio distribuida con Perl). Si "unlink" tiene que cambiar la protección del archivo para eliminarlo, y lo interrumpe a mitad de camino, el archivo puede quedar intacto, pero con una ACL modificada que le permite acceso de eliminación.

Este comportamiento de "unlink" es para ser compatible con el comportamiento POSIX y no con el comportamiento tradicional de VMS.

utime LIST
Este operador solo cambia la hora de modificación del archivo (fecha de revisión de VMS) en volúmenes ODS-2 y volúmenes ODS-5 sin fechas de acceso habilitadas. En volúmenes ODS-5 con fechas de acceso habilitadas, se modifica la hora de acceso real.
waitpid PID,FLAGS
Si PID es un subproceso iniciado por un open() con tubería (ver open), "waitpid" esperará a ese subproceso y devolverá su valor de estado final en $?. Si PID es un subproceso creado de alguna otra manera (por ejemplo, iniciado con SPAWN antes de invocar Perl), "waitpid" simplemente verificará una vez por segundo si el proceso ha completado y regresará cuando lo haya hecho. (Si PID especifica un proceso que no es un subproceso del proceso actual, y invocó Perl con el modificador "-w", se emitirá una advertencia).

Devuelve PID en caso de éxito, -1 en caso de error. El argumento FLAGS se ignora en todos los casos.

Variables de Perl

La siguiente información específica de VMS se aplica a las "variables especiales" de Perl indicadas, además de la información general de perlvar. Cuando hay un conflicto, esta información tiene precedencia.

%ENV
La operación del array %ENV depende de la traducción del nombre lógico PERL_ENV_TABLES. Si está definido, debe ser una lista de búsqueda, cada elemento de la cual especifica una ubicación para los elementos de %ENV. Si le dice a Perl que lea o establezca el elemento "$ENV{"nombre"}", entonces Perl utiliza las traducciones de PERL_ENV_TABLES de la siguiente manera:
CRTL_ENV
Esta cadena le dice a Perl que consulte el array interno "environ" de pares clave-valor de CRTL, utilizando nombre como clave. En la mayoría de los casos, esto contiene solo unas pocas claves, pero si Perl fue invocado a través de la función C "exec[lv]e()", como es el caso de algunas aplicaciones Perl incrustadas o al ejecutarse bajo un shell como GNV bash, el array "environ" puede haber sido poblado por el programa que llama.
CLISYM_[LOCAL]
Una cadena que comienza con "CLISYM_" le dice a Perl que consulte las tablas de símbolos del CLI, utilizando nombre como el nombre del símbolo. Al leer un elemento de %ENV, primero se escanea la tabla de símbolos local, seguida por la tabla de símbolos global. Los caracteres que siguen a "CLISYM_" son significativos cuando se establece o elimina un elemento de %ENV: si la cadena completa es "CLISYM_LOCAL", el cambio se realiza en la tabla de símbolos local; de lo contrario, se cambia la tabla de símbolos global.
Cualquier otra cadena
Si un elemento de PERL_ENV_TABLES se traduce a cualquier otra cadena, esa cadena se utiliza como el nombre de una tabla de nombres lógicos, que se consulta utilizando nombre como el nombre lógico. Se utiliza el orden de búsqueda normal de los modos de acceso.

PERL_ENV_TABLES se traduce una vez cuando Perl se inicia; cualquier cambio que realice mientras Perl se está ejecutando no afecta el comportamiento de %ENV. Si PERL_ENV_TABLES no está definido, Perl recurre primero a consultar las tablas de nombres lógicos especificadas por LNM$FILE_DEV y luego el array "environ" de CRTL. Este orden predeterminado se invierte cuando se define el nombre lógico GNV$UNIX_SHELL, como cuando se ejecuta bajo GNV bash.

Para operaciones en entradas de %ENV basadas en nombres lógicos o símbolos DCL, la cadena clave se trata como si fuera completamente mayúscula, independientemente de la capitalización realmente especificada en la expresión de Perl. Las entradas en %ENV basadas en el array environ de CRTL conservan la capitalización de la cadena clave al almacenarse, y las búsquedas son sensibles a mayúsculas y minúsculas.

Cuando se lee un elemento de %ENV, las ubicaciones a las que apunta PERL_ENV_TABLES se verifican en orden, y se devuelve el valor obtenido de la primera búsqueda exitosa. Si el nombre del elemento de %ENV contiene un punto y coma, este y cualquier carácter posterior se eliminan. Estos se ignoran cuando se consulta el array "environ" de CRTL o una tabla de símbolos CLI. Sin embargo, el nombre se busca en una tabla de nombres lógicos, el sufijo después del punto y coma se trata como el índice de traducción que se utilizará para la búsqueda. Esto le permite buscar valores sucesivos para nombres lógicos de listas de búsqueda. Por ejemplo, si dice

$  Define STORY  once,upon,a,time,there,was
$  perl -e "for ($i = 0; $i <= 6; $i++) " -
_$ -e "{ print $ENV{'story;'.$i},' '}"

Perl imprimirá "ONCE UPON A TIME THERE WAS", asumiendo, por supuesto, que PERL_ENV_TABLES está configurado de manera que se encuentre el nombre lógico "story", en lugar de un símbolo CLI o un elemento "environ" de CRTL con el mismo nombre.

Cuando se establece un elemento de %ENV en una cadena definida, la definición correspondiente se realiza en la ubicación a la que apunta la primera traducción de PERL_ENV_TABLES. Si esto provoca la creación de un nombre lógico, se define en modo supervisor. (Lo mismo se hace si un nombre lógico existente se definió en modo ejecutivo o de kernel; un nombre lógico existente de usuario o supervisor se restablece al nuevo valor). Si el valor es una cadena vacía, la traducción del nombre lógico se define como un solo carácter "NUL" (carácter ASCII "\0"), ya que un nombre lógico no puede traducirse a una cadena de longitud cero. (Esta restricción no se aplica a los símbolos CLI o a los valores "environ" de CRTL; se establecen en una cadena vacía).

Cuando se establece un elemento de %ENV en "undef", el elemento se busca como si se estuviera leyendo, y si se encuentra, se elimina. (Un elemento "eliminado" del array "environ" de CRTL se establece en la cadena vacía). Usar "delete" para eliminar un elemento de %ENV tiene

un efecto similar, pero después de que el elemento es eliminado, se intenta nuevamente buscar el elemento, por lo que un nombre lógico de modo interno o un nombre en otra ubicación reemplazará al nombre lógico recién eliminado. En cualquier caso, solo se altera el primer valor encontrado al buscar en PERL_ENV_TABLES. Actualmente no es posible definir un nombre lógico de lista de búsqueda a través de %ENV.

El elemento $ENV{DEFAULT} es especial: cuando se lee, devuelve el dispositivo y directorio predeterminados actuales de Perl, y cuando se establece, los restablece, independientemente de la definición de PERL_ENV_TABLES. No se puede borrar ni eliminar; los intentos de hacerlo se ignoran silenciosamente.

Tenga en cuenta que si desea pasar elementos de la matriz de entorno local de C a un subproceso que no se inicia mediante fork/exec, o que no está ejecutando un programa C, puede "promoverlos" a nombres lógicos en el proceso actual, que luego serán heredados por todos los subprocesos, diciendo:

foreach my $key (qw[C-local keys you want promoted]) {
    my $temp = $ENV{$key}; # read from C-local array
    $ENV{$key} = $temp;    # and define as logical name
}

(No puede simplemente decir "$ENV{$key} = $ENV{$key}", ya que el optimizador de Perl es lo suficientemente inteligente como para omitir la expresión).

No intente borrar %ENV diciendo "%ENV = ();", lanzará un error fatal. Esto es equivalente a hacer lo siguiente desde DCL:

DELETE/LOGICAL *

Puede imaginar lo mal que estarían las cosas si, por ejemplo, se eliminaran los nombres lógicos SYS$MANAGER o SYS$SYSTEM.

Por el momento, la primera vez que itera sobre %ENV usando "keys" o "values", incurrirá en una penalización de tiempo, ya que se leen todos los nombres lógicos, para poblar completamente %ENV. Las iteraciones posteriores no volverán a leer los nombres lógicos, por lo que no serán tan lentas, pero tampoco reflejarán los cambios en las tablas de nombres lógicos causados por otros programas.

Debe tener cuidado con los nombres lógicos que representan archivos permanentes del proceso, como "SYS$INPUT" y "SYS$OUTPUT". Las traducciones de estos nombres lógicos van precedidas de un valor binario de dos bytes (0x1B 0x00) que debe eliminarse si desea utilizarlo. (En versiones anteriores de Perl, no era posible obtener los valores de estos nombres lógicos, ya que el byte nulo actuaba como un marcador de fin de cadena).

$!
El valor de cadena de $! es el devuelto por la función strerror() de CRTL, por lo que incluirá el mensaje de VMS para errores específicos de VMS. El valor numérico de $! es el valor de "errno", excepto si errno es EVMSERR, en cuyo caso $! contiene el valor de vaxc$errno. Establecer $! siempre establece errno al valor especificado. Si este valor es EVMSERR, también establece vaxc$errno a 4 (NONAME-F-NOMSG), para que el valor de cadena de $! no refleje el mensaje de error de VMS de antes de que se estableciera $!.
$^E
Esta variable proporciona acceso directo a los valores de estado de VMS en vaxc$errno, que a menudo son más específicos que los mensajes de error genéricos de estilo Unix en $!. Su valor numérico es el valor de vaxc$errno, y su valor de cadena es el mensaje de VMS correspondiente, tal como lo recupera sys$getmsg(). Establecer $^E establece vaxc$errno al valor especificado.

Aunque Perl intenta mantener el valor de vaxc$errno actual, si errno no es EVMSERR, es posible que no provenga de la operación actual.

$?
El "valor de estado" devuelto en $? se sintetiza del estado de salida real del subproceso de una manera que se aproxima a las semánticas de wait(5) de POSIX, para permitir que los programas Perl prueben de forma portable la finalización exitosa de subprocesos. Los 8 bits de orden inferior de $? son siempre 0 en VMS, ya que el estado de terminación de un proceso puede o no haber sido generado por una excepción.

Los siguientes 8 bits contienen el estado de terminación del programa.

Si el proceso hijo sigue la convención de los programas C compilados con la macro _POSIX_EXIT establecida, el valor de estado contendrá el valor real de 0 a 255 devuelto por ese programa en una salida normal.

Con la macro _POSIX_EXIT establecida, el valor de salida de Unix cero se representa como un estado nativo de VMS de 1, y los valores de Unix de 2 a 255 se codifican mediante la ecuación:

VMS_status = 0x35a000 + (unix_value * 8) + 1.

Y en el caso especial del valor Unix 1, la codificación es:

VMS_status = 0x35a000 + 8 + 2 + 0x10000000.

Para otros estados de terminación, se utiliza la porción de severidad del estado de salida del subproceso: si la severidad fue éxito o información, estos bits son todos 0; si la severidad fue advertencia, contienen un valor de 1; si la severidad fue error o error fatal, contienen los bits de severidad reales, que resultan ser un valor de 2 para error y 4 para error grave. Fatal es otro término para el estado de error grave.

Como resultado, $? será siempre cero si el estado de salida del subproceso indicó una finalización exitosa, y distinto de cero si ocurrió una advertencia o un error, o si se ejecutó un programa compatible con la codificación de valores de _POSIX_EXIT y estableció un estado.

¿Cómo se puede diferenciar entre un estado distinto de cero que es el resultado de un estado de error nativo de VMS o un estado de Unix codificado? No se puede a menos que se mire el valor de ${^CHILD_ERROR_NATIVE}. El valor ${^CHILD_ERROR_NATIVE} devuelve el valor de estado real de VMS y verifica los bits de severidad. Si los bits de severidad son iguales a 1, entonces si el valor numérico de $? está entre 2 y 255 o es 0, entonces $? refleja con precisión un valor devuelto desde una aplicación de Unix. Si $? es 1, y los bits de severidad indican un error de VMS (2), entonces $? proviene de un valor de salida de una aplicación de Unix.

En la práctica, los scripts de Perl que llaman a programas que devuelven valores de estado de tipo _POSIX_EXIT esperarán esos valores, y los programas que llaman a programas VMS tradicionales esperarán el comportamiento anterior o simplemente verificarán un estado distinto de cero.

Y el éxito es siempre el valor 0 en todos los comportamientos.

Cuando el estado de terminación real de VMS del hijo es un error, internamente el valor de $! se establecerá en el valor errno de Unix más cercano a ese error para que los scripts de Perl que prueban mensajes de error vean el mensaje de error de estilo Unix esperado en lugar de un mensaje de VMS.

Por el contrario, al establecer $? en un bloque END, se intenta convertir el valor POSIX en un estado nativo inteligible para el sistema operativo al salir de Perl. Lo que esto significa es que establecer $? a cero da como resultado el valor genérico de éxito SS$_NORMAL, y establecer $? a un valor distinto de cero da como resultado el estado genérico de fallo SS$_ABORT. Ver también "exit" en perlport.

Con el nombre lógico "PERL_VMS_POSIX_EXIT" definido como "ENABLE", establecer $? hará que el nuevo valor se codifique en $^E para que los valores de estado de salida del proceso padre o hijo originales
de 0 a 255 puedan recuperarse automáticamente por programas C que esperan el comportamiento de _POSIX_EXIT. Si tanto el valor de salida del padre como el del hijo son distintos de cero, se asumirá que esto es en realidad un valor de estado nativo de VMS que se pasará. El valor especial de 0xFFFF es casi un NOOP, ya que hará que el estado nativo de VMS actual en la biblioteca C se convierta en el estado VMS nativo actual de Perl, y se maneja de esta manera ya que se sabe que no es un valor de estado nativo de VMS válido. Se recomienda que solo se utilicen valores en el rango de los números de estado de padre o hijo normales de Unix, de 0 a 255.

El pragmas "use vmsish 'status'" hace que $? refleje el estado de salida real de VMS en lugar de la emulación predeterminada del estado POSIX descrita anteriormente. Este pragmas también deshabilita la conversión de valores distintos de cero a SS$_ABORT al establecer $? en un bloque END (pero cero aún se convertirá a SS$_NORMAL).

No utilice el pragmas "use vmsish 'status'" con "PERL_VMS_POSIX_EXIT" habilitado, ya que a veces solicitan acciones contradictorias y la consecuencia de ignorar este consejo será indefinida para permitir mejoras futuras en el manejo de salida POSIX.

En general, con "PERL_VMS_POSIX_EXIT" habilitado, habrá información más detallada disponible en el estado de salida para scripts DCL u otras herramientas nativas de VMS, y proporcionará la información esperada para programas Posix. No se ha hecho predeterminado para preservar la compatibilidad con versiones anteriores.

N.B. Establecer "DECC$FILENAME_UNIX_REPORT" habilita implícitamente "PERL_VMS_POSIX_EXIT".

$|
Establecer $| para un flujo de E/S provoca que los datos se envíen hasta el disco en cada escritura (es decir, no solo a los búferes RMS subyacentes de un archivo). En otras palabras, es equivalente a llamar a fflush() y fsync() desde C.

Módulos estándar con diferencias específicas de VMS

SDBM_File

SDBM_File funciona correctamente en VMS. Tiene, sin embargo, una diferencia menor. El archivo de directorio de la base de datos creado tiene una extensión .sdbm_dir en lugar de una extensión .dir. Los archivos .dir son archivos de directorio del sistema de archivos VMS, y usarlos para otros fines podría causar problemas inaceptables.

NAME

perlvms - Perl para VMS

DESCRIPCIÓN

Este manual describe la organización de las imágenes de Perl, las variables de entorno y algunas de las diferencias específicas de VMS.

Instalación

La instalación de Perl para VMS es un proceso estándar para un sistema VMS. El script de instalación debería encargarse de la mayor parte del trabajo. Los detalles específicos pueden variar ligeramente dependiendo de la versión de VMS y de cómo se obtenga el código fuente de Perl.

Organización de las imágenes de Perl

Las imágenes ejecutables de Perl en VMS suelen estar ubicadas en los siguientes directorios:

  • PERL_ROOT:[perl.exe]: Contiene el ejecutable principal de Perl.
  • PERL_ROOT:[lib]: Contiene los módulos de la biblioteca estándar de Perl.
  • PERL_ROOT:[site.lib]: Contiene los módulos instalados por el usuario.

PERL_ROOT es una variable de símbolo de VMS que apunta al directorio raíz de la instalación de Perl.

Especificaciones de archivos

En VMS, los archivos Perl se organizan en directorios lógicos, y los nombres de archivo suelen seguir el formato nombre.extensión;versión. Por ejemplo, un módulo podría ser PERL_ROOT:[lib]LIST.XMI;1. Perl para VMS está diseñado para manejar esto correctamente.

PERL5LIB y PERLLIB

Las variables de entorno PERL5LIB y PERLLIB se utilizan para especificar directorios adicionales donde buscar módulos Perl. En VMS, estas variables se pueden establecer como símbolos de proceso o de sistema:

$ DEFINE PERL5LIB PERL_ROOT:[site.lib]
$ DEFINE PERLLIB PERL_ROOT:[lib]

Se recomienda definir ambas variables para asegurar la compatibilidad con diferentes versiones y utilidades de Perl.

El depurador bifurcado de Perl

El depurador de Perl para VMS puede bifurcarse, lo que significa que puede iniciar un nuevo proceso para la depuración. Esto se controla mediante la variable de entorno PERL_FORK_DEBUG.

PERL_VMS_EXCEPTION_DEBUG

Cuando esta variable se establece en un valor verdadero (por ejemplo, 1), Perl para VMS generará un volcado de excepción cuando ocurra una excepción no manejada. Esto es útil para la depuración de programas de Perl que fallan.

Línea de comandos

La invocación de Perl desde la línea de comandos de VMS es similar a otros sistemas operativos:

$ PERL script.pl

Los argumentos se pasan de la forma habitual. Por ejemplo:

$ PERL mi_script.pl argumento1 argumento2

Funciones de Perl

La mayoría de las funciones de Perl estándar están disponibles en la versión de VMS. Sin embargo, algunas funciones que dependen en gran medida de características específicas del sistema operativo subyacente (como la manipulación de procesos o la E/S de red de bajo nivel) pueden tener comportamientos o implementaciones diferentes.

Variables de Perl

Las variables de entorno de Perl, como %ENV{'PATH'}, se manejan de manera que se integran con el sistema de símbolos de VMS. Por ejemplo, el valor de PATH de VMS se puede acceder y modificar a través de la variable %ENV{'PATH'}.

Módulos estándar con diferencias específicas de VMS

Algunos módulos de la biblioteca estándar de Perl que interactúan estrechamente con el sistema operativo pueden tener implementaciones específicas para VMS. Estos módulos están diseñados para proporcionar una interfaz consistente tanto como sea posible, pero pueden exponer o requerir un conocimiento de las características de VMS.

Consulte la documentación específica del módulo para obtener detalles sobre las diferencias en VMS.
