NOMBRE

perlfilter - Filtros de código fuente

DESCRIPCIÓN

Este artículo trata sobre una característica poco conocida de Perl llamada filtros de código fuente. Los filtros de código fuente modifican el texto del programa de un módulo antes de que Perl lo vea, de forma similar a como un preprocesador C modifica el texto fuente de un programa C antes de que el compilador lo vea. Este artículo te cuenta más sobre qué son los filtros de código fuente, cómo funcionan y cómo escribir los tuyos propios.

El propósito original de los filtros de código fuente era permitirte cifrar el código fuente de tu programa para evitar lecturas casuales. Esto no es todo lo que pueden hacer, como pronto aprenderás. Pero primero, lo básico.

CONCEPTOS

Antes de que el intérprete de Perl pueda ejecutar un script de Perl, primero debe leerlo desde un archivo a la memoria para su análisis y compilación. Si ese script, a su vez, incluye otros scripts con una declaración "use" o "require", entonces cada uno de esos scripts deberá leerse también de sus respectivos archivos.

Ahora piensa en cada conexión lógica entre el analizador de Perl y un archivo individual como un flujo de código fuente. Se crea un flujo de código fuente cuando el analizador de Perl abre un archivo, continúa existiendo mientras el código fuente se lee en memoria y se destruye cuando Perl termina de analizar el archivo. Si el analizador encuentra una declaración de "require" o "use" en un flujo de código fuente, se crea un flujo nuevo y distinto solo para ese archivo.

El siguiente diagrama representa un único flujo de código fuente, con el flujo del código fuente de un archivo de script de Perl a la izquierda hacia el analizador de Perl a la derecha. Así es como Perl opera normalmente.

archivo -------> analizador

Hay dos puntos importantes a recordar:

1.
Aunque puede haber cualquier número de flujos de código fuente en existencia en un momento dado, solo uno estará activo.
2.
Cada flujo de código fuente está asociado con un solo archivo.

Un filtro de código fuente es un tipo especial de módulo de Perl que intercepta y modifica un flujo de código fuente antes de que llegue al analizador. Un filtro de código fuente cambia nuestro diagrama de esta manera:

archivo ----> filtro ----> analizador

Si eso no tiene mucho sentido, considera la analogía de una tubería de comandos. Supongamos que tienes un script de shell almacenado en el archivo comprimido trial.gz. El simple comando de tubería a continuación ejecuta el script sin necesidad de crear un archivo temporal para contener el archivo descomprimido.

gunzip -c trial.gz | sh

En este caso, el flujo de datos de la tubería se puede representar de la siguiente manera:

trial.gz ----> gunzip ----> sh

Con los filtros de código fuente, puedes almacenar el texto de tu script comprimido y usar un filtro de código fuente para descomprimirlo para el analizador de Perl:

 código fuente        descompresión
Perl ---> filtro de código fuente ---> analizador

USO DE FILTROS

Entonces, ¿cómo se usa un filtro de código fuente en un script de Perl? Arriba, dije que un filtro de código fuente es solo un tipo especial de módulo. Como todos los módulos de Perl, un filtro de código fuente se invoca con una declaración use.

Digamos que quieres pasar tu código fuente de Perl a través del preprocesador C antes de la ejecución. Da la casualidad de que la distribución de filtros de código fuente viene con un módulo de filtro preprocesador C llamado Filter::cpp.

A continuación se muestra un programa de ejemplo, "cpp_test", que utiliza este filtro. Se han añadido números de línea para permitir la referencia específica de líneas.

1: use Filter::cpp;
2: #define TRUE 1
3: $a = TRUE;
4: print "a = $a\n";

Cuando ejecutas este script, Perl crea un flujo de código fuente para el archivo. Antes de que el analizador procese alguna de las líneas del archivo, el flujo de código fuente se ve así:

cpp_test ---------> analizador

La línea 1, "use Filter::cpp", incluye e instala el módulo de filtro "cpp". Todos los filtros de código fuente funcionan de esta manera. La declaración use se compila y ejecuta en tiempo de compilación, antes de que se lea más del archivo, y adjunta el filtro cpp al flujo de código fuente en segundo plano. Ahora el flujo de datos se ve así:

cpp_test ----> filtro cpp ----> analizador

A medida que el analizador lee la segunda y las líneas subsiguientes del flujo de código fuente, las pasa a través del filtro de código fuente "cpp" antes de procesarlas. El filtro "cpp" simplemente pasa cada línea a través del preprocesador C real. La salida del preprocesador C se inserta nuevamente en el flujo de código fuente por el filtro.

               .-> cpp --.
               |         |
               |         |
               |       <-'
cpp_test ----> filtro cpp ----> analizador

El analizador ve entonces el siguiente código:

use Filter::cpp;
$a = 1;
print "a = $a\n";

Consideremos qué sucede cuando el código filtrado incluye otro módulo con use:

1: use Filter::cpp;
2: #define TRUE 1
3: use Fred;
4: $a = TRUE;
5: print "a = $a\n";

El filtro "cpp" no se aplica al texto del módulo Fred, solo al texto del archivo que lo utilizó ( "cpp_test"). Aunque la declaración use en la línea 3 pasará a través del filtro cpp, el módulo que se incluirá ( "Fred") no lo hará. Los flujos de código fuente se ven así después de que la línea 3 ha sido analizada y antes de que la línea 4 sea analizada:

cpp_test ---> filtro cpp ---> analizador (INACTIVO)
Fred.pm ----> analizador

Como puedes ver, se ha creado un nuevo flujo para leer el código fuente de "Fred.pm". Este flujo permanecerá activo hasta que se haya analizado todo "Fred.pm". El flujo de código fuente para "cpp_test" seguirá existiendo, pero está inactivo. Una vez que el analizador termine de leer Fred.pm, el flujo de código fuente asociado con él será destruido. El flujo de código fuente para "cpp_test" se vuelve a activar y el analizador lee la línea 4 y las subsiguientes de "cpp_test".

Puedes usar más de un filtro de código fuente en un solo archivo. De manera similar, puedes reutilizar el mismo filtro en tantos archivos como desees.

Por ejemplo, si tienes un archivo fuente codificado en uuencoded y comprimido, es posible apilar un filtro de decodificación uu y un filtro de descompresión de esta manera:

use Filter::uudecode; use Filter::uncompress;
M'XL(".H<US4''V9I;F%L')Q;>7/;1I;_>_I3=&E=%:F*I"T?22Q/
M6]9*<IQCO*XFT"0[PL%%'Y+IG?WN^ZYN-$'J.[.JE$,20/?K=_[>
...

Una vez que se ha procesado la primera línea, el flujo se verá así:

archivo ---> decodificador uu ---> descompresor ---> analizador
             filtro             filtro

Los datos fluyen a través de los filtros en el mismo orden en que aparecen en el archivo fuente. El filtro de decodificación uu apareció antes que el filtro de descompresión, por lo que el archivo fuente se decodificará uu antes de descomprimirse.

ESCRIBIR UN FILTRO DE CÓDIGO FUENTE

Hay tres formas de escribir tu propio filtro de código fuente. Puedes escribirlo en C, usar un programa externo como filtro o escribir el filtro en Perl. No cubriré los dos primeros en gran detalle, así que me los quitaré de encima primero. Escribir el filtro en Perl es lo más conveniente, así que dedicaré más espacio a ello.

ESCRIBIR UN FILTRO DE CÓDIGO FUENTE EN C

La primera de las tres técnicas disponibles es escribir el filtro completamente en C. El módulo externo que creas se interconecta directamente con los ganchos de filtro de código fuente proporcionados por Perl.

La ventaja de esta técnica es que tienes control total sobre la implementación de tu filtro. La gran desventaja es la mayor complejidad requerida para escribir el filtro: no solo necesitas comprender los ganchos de filtro de código fuente, sino que también necesitas un conocimiento razonable de las tripas de Perl. Una de las pocas veces que vale la pena pasar por este problema es al escribir un ofuscador de código. El filtro "decrypt" (que descifra el código fuente antes de que Perl lo analice) incluido con la distribución de filtros de código fuente es un ejemplo de filtro de código fuente en C (ver Filtros de Descifrado, abajo).

Por muy bien que escribas un filtro de descifrado y por muy robusto que sea tu algoritmo de cifrado, cualquiera con suficiente determinación podrá recuperar el código fuente original. CREACIÓN DE UN FILTRO DE CÓDIGO FUENTE COMO EJECUTABLE SEPARADO

Una alternativa a escribir el filtro en C es crear un ejecutable separado en el lenguaje de tu elección. El ejecutable separado lee de la entrada estándar, realiza cualquier procesamiento necesario y escribe los datos filtrados en la salida estándar. "Filter::cpp" es un ejemplo de filtro de código fuente implementado como un ejecutable separado: el ejecutable es el preprocesador C incluido con tu compilador C.

La distribución de filtros de código fuente incluye dos módulos que simplifican esta tarea: "Filter::exec" y "Filter::sh". Ambos te permiten ejecutar cualquier ejecutable externo. Ambos utilizan un coproceso para controlar el flujo de datos hacia y desde el ejecutable externo. (Para obtener detalles sobre coprocesos, consulta Stephens, W.R., "Advanced Programming in the UNIX Environment." Addison-Wesley, ISBN 0-210-56317-7, páginas 441-445.) La diferencia entre ellos es que "Filter::exec" lanza el comando externo directamente, mientras que "Filter::sh" lanza un shell para ejecutar el comando externo. (Unix utiliza el shell Bourne; NT utiliza el shell cmd.) Lanzar un shell te permite utilizar los metacaracteres y las facilidades de redirección del shell.

Aquí tienes un ejemplo de script que utiliza "Filter::sh":

use Filter::sh 'tr XYZ PQR';
$a = 1;
print "XYZ a = $a\n";

La salida que obtendrás cuando se ejecute el script:

PQR a = 1

Escribir un filtro de código fuente como un ejecutable separado funciona bien, pero se incurre en una pequeña penalización de rendimiento. Por ejemplo, si ejecutas el pequeño ejemplo anterior, se creará un subproceso separado para ejecutar el comando "tr" de Unix. Cada uso del filtro requiere su propio subproceso. Si la creación de subprocesos es costosa en tu sistema, podrías considerar otras opciones para crear filtros de código fuente.

ESCRIBIR UN FILTRO DE CÓDIGO FUENTE EN PERL

La opción más fácil y portátil disponible para crear tu propio filtro de código fuente es escribirlo completamente en Perl. Para distinguirlo de las dos técnicas anteriores, lo llamaré un filtro de código fuente Perl.

Para comprender cómo escribir un filtro de código fuente Perl, necesitamos un ejemplo para estudiar. Aquí tienes un filtro de código fuente completo que realiza la decodificación rot13. (Rot13 es un esquema de cifrado muy simple utilizado en las publicaciones de Usenet para ocultar el contenido de las publicaciones ofensivas. Mueve cada letra trece posiciones hacia adelante, de modo que A se convierte en N, B en O y Z en M).

package Rot13;
use Filter::Util::Call;
sub import {
   my ($type) = @_;
   my ($ref) = [];
   filter_add(bless $ref);
}
sub filter {
   my ($self) = @_;
   my ($status);
   tr/n-za-mN-ZA-M/a-zA-Z/
      if ($status = filter_read()) > 0;
   $status;
}
1;

Todos los filtros de código fuente de Perl se implementan como clases de Perl y tienen la misma estructura básica que el ejemplo anterior.

Primero, incluimos el módulo "Filter::Util::Call", que exporta varias funciones a tu espacio de nombres de filtro. El filtro que se muestra arriba utiliza dos de estas funciones, filter_add() y filter_read().

A continuación, creamos el objeto filtro y lo asociamos con el flujo de código fuente definiendo la función "import". Si conoces Perl lo suficiente, sabrás que "import" se llama automáticamente cada vez que se incluye un módulo con una declaración use. Esto hace de "import" el lugar ideal para crear e instalar un objeto filtro.

En el filtro de ejemplo, el objeto ($ref) se bendice (blessed) como cualquier otro objeto Perl. Nuestro ejemplo utiliza un array anónimo, pero esto no es un requisito. Como este ejemplo no necesita almacenar ninguna información de contexto, podríamos haber utilizado una referencia escalar o de hash igual de bien. La siguiente sección demuestra los datos de contexto.

La asociación entre el objeto filtro y el flujo de código fuente se realiza con la función filter_add(). Esta toma un objeto filtro como parámetro ($ref en este caso) y lo instala en el flujo de código fuente.

Finalmente, está el código que realmente realiza el filtrado. Para este tipo de filtro de código fuente Perl, todo el filtrado se realiza en un método llamado filter(). (También es posible escribir un filtro de código fuente Perl utilizando un cierre. Consulta la página del manual de "Filter::Util::Call" para obtener más detalles.) Se llama cada vez que el analizador de Perl necesita otra línea de código fuente para procesar. El método filter(), a su vez, lee líneas del flujo de código fuente utilizando la función filter_read().

Si había una línea disponible en el flujo de código fuente, filter_read() devuelve un valor de estado mayor que cero y añade la línea a $_. Un valor de estado de cero indica fin de archivo, y menos de cero significa un error. Se espera que la función de filtro devuelva su estado de la misma manera, y que ponga la línea filtrada que quiere que se escriba en el flujo de código fuente en $_. El uso de $_ explica la brevedad de la mayoría de los filtros de código fuente de Perl.

Para poder utilizar el filtro rot13, necesitamos alguna forma de cifrar el archivo fuente en formato rot13. El script siguiente, "mkrot13", hace precisamente eso.

die "usage mkrot13 filename\n" unless @ARGV;
my $in = $ARGV[0];
my $out = "$in.tmp";
open(IN, "<$in") or die "Cannot open file $in: $!\n";
open(OUT, ">$out") or die "Cannot open file $out: $!\n";
print OUT "use Rot13;\n";
while (<IN>) {
   tr/a-zA-Z/n-za-mN-ZA-M/;
   print OUT;
}
close IN;
close OUT;
unlink $in;
rename $out, $in;

Si ciframos esto con "mkrot13":

print " hello fred \n";

el resultado será este:

use Rot13;
cevag "uryyb serq\a";

Ejecutarlo produce esta salida:

hello fred

USO DE CONTEXTO: EL FILTRO DEBUG

El ejemplo rot13 fue un ejemplo trivial. Aquí tienes otra demostración que muestra algunas características más.

Supongamos que quieres incluir mucho código de depuración en tu script de Perl durante el desarrollo, pero no quieres que esté disponible en el producto final. Los filtros de código fuente ofrecen una solución. Para mantener el ejemplo simple, digamos que quieres que la salida de depuración sea controlada por una variable de entorno, "DEBUG". El código de depuración se habilita si la variable existe, de lo contrario se deshabilita.

Dos líneas marcadoras especiales delimitarán el código de depuración, así:

## DEBUG_BEGIN
if ($year > 1999) {
   warn "Debug: millennium bug in year $year\n";
}
## DEBUG_END

El filtro asegura que Perl analice el código entre los marcadores <DEBUG_BEGIN> y "DEBUG_END" solo cuando la variable de entorno "DEBUG" exista. Esto significa que cuando "DEBUG" exista, el código anterior debería pasar a través del filtro sin cambios. Las líneas marcadoras también pueden pasarse tal cual, ya que el analizador de Perl las verá como líneas de comentario. Cuando "DEBUG" no está configurado, necesitamos una forma de deshabilitar el código de depuración. Una forma sencilla de lograrlo es convertir las líneas entre los dos marcadores en comentarios:

## DEBUG_BEGIN
#if ($year > 1999) {
#     warn "Debug: millennium bug in year $year\n";
#}
## DEBUG_END

Aquí tienes el filtro Debug completo:

package Debug;
use v5.36;
use Filter::Util::Call;
use constant TRUE => 1;
use constant FALSE => 0;
sub import {
   my ($type) = @_;
   my (%context) = (
     Enabled => defined $ENV{DEBUG},
     InTraceBlock => FALSE,
     Filename => (caller)[1],
     LineNo => 0,
     LastBegin => 0,
   );
   filter_add(bless \%context);
}
sub Die {
   my ($self) = shift;
   my ($message) = shift;
   my ($line_no) = shift || $self->{LastBegin};
   die "$message at $self->{Filename} line $line_no.\n"
}
sub filter {
   my ($self) = @_;
   my ($status);
   $status = filter_read();
   ++ $self->{LineNo};
   # deal with EOF/error first
   if ($status <= 0) {
       $self->Die("DEBUG_BEGIN has no DEBUG_END")
           if $self->{InTraceBlock};
       return $status;
   }
   if ($self->{InTraceBlock}) {
      if (/^\s*##\s*DEBUG_BEGIN/ ) {
          $self->Die("Nested DEBUG_BEGIN", $self->{LineNo})
      } elsif (/^\s*##\s*DEBUG_END/) {
          $self->{InTraceBlock} = FALSE;
      }
      # comment out the debug lines when the filter is disabled
      s/^/#/ if ! $self->{Enabled};
   } elsif ( /^\s*##\s*DEBUG_BEGIN/ ) {
      $self->{InTraceBlock} = TRUE;
      $self->{LastBegin} = $self->{LineNo};
   } elsif ( /^\s*##\s*DEBUG_END/ ) {
      $self->Die("DEBUG_END has no DEBUG_BEGIN", $self->{LineNo});
   }
   return $status;
}
1;

La gran diferencia entre este filtro y el ejemplo anterior es el uso de datos de contexto en el objeto filtro. El objeto filtro se basa en una referencia de hash y se utiliza para mantener varias piezas de información de contexto entre llamadas a la función de filtro. Todos los campos del hash, excepto dos, se utilizan para informar de errores. El primero de esos dos, Enabled, lo utiliza el filtro para determinar si el código de depuración debe pasarse al analizador de Perl. NAME

perlfilter — The Perl Source Filter facility

DESCRIPTION

Perl source filters are a mechanism whereby the source code for a Perl script or module can be preprocessed before Perl compiles it. This allows for transformations of the source code to be performed on the fly.

Source filters are implemented as a stack. When Perl reads a source file, it passes the file through each filter in the stack, in order. Each filter receives the output of the previous filter, processes it, and passes its own output to the next filter. The output of the last filter is then compiled by Perl.

Filters can be added to the stack using the "use Filter::*" pragma. The most common ones are:

  • use Filter::Simple;
  • use Filter::pmpp;
  • use Filter::Discard;
  • use Filter::String;
  • use Filter::Substitute;
  • use Filter::Decl::Syntax;
  • use Filter::Decl::Rewrite;

The standard source filter distribution comes with a set of example filters, including the Filter::Debug module, which is used in the example below.

CONCEPTS

Source filters operate on the text of a Perl program before it is compiled. They allow you to modify the source code on the fly. This is achieved by inserting filter modules into the source code compilation pipeline. When Perl starts compiling a script or module, it reads the source code. If any source filters have been invoked via "use Filter::*", the source code is passed through each filter in turn before compilation takes place.

Think of it as a pipeline. The source code enters at one end, and the compiled code emerges at the other. Filters sit in the middle, each receiving the output of the previous one and passing its own output to the next.

The Filter::Util::Call module provides the core functionality for writing source filters. It allows you to create a filter that reads input line by line, or in chunks, processes it, and returns the modified source code.

USING FILTERS

To use a source filter, you simply "use" it at the beginning of your script or module:

    #!/usr/bin/perl
    use strict;
    use warnings;

    use Filter::Debug; # Invoke the Debug filter

    print "Hello, world!\n";
    ## DEBUG BEGIN
    print "This is a debug message.\n";
    ## DEBUG END
    print "Goodbye, world!\n";

When this script is run, the Filter::Debug module will process the source code. It recognizes the ## DEBUG_BEGIN and ## DEBUG_END lines. The DEBUG_BEGIN line sets an internal flag $InTraceBlock to TRUE. The DEBUG_END line resets this flag to FALSE. Any lines between these two markers are treated as debugging code. If the filter is enabled (which it is by default), these lines are passed through to the compiler. If the filter is disabled (e.g., by setting the $Filter::Debug::Enabled variable to FALSE), the debugging lines are commented out by prepending a # to them.

WRITING A SOURCE FILTER

Writing a source filter can be done in several ways:

  • As a Perl module using Filter::Util::Call or Filter::Simple.

  • As a separate executable program.

  • As a C extension module.

The most common and recommended way is to write a Perl module.

WRITING A SOURCE FILTER IN C

This is the most powerful but also the most complex method. You write a C module that implements the xs_init function and registers a filter callback. This callback receives the source code (usually line by line) and returns the modified source code. This approach is typically used for performance-critical filters or when interfacing with external C libraries.

CREATING A SOURCE FILTER AS A SEPARATE EXECUTABLE

You can write a standalone program that reads source code from standard input and writes the processed source code to standard output. Perl can then be configured to use this executable as a filter. This is less common but can be useful for integrating external tools or scripts.

WRITING A SOURCE FILTER IN PERL

This is the easiest and most common way to write a source filter. The Filter::Simple module provides a convenient high-level interface. You define a subroutine that takes the source code (usually as a list of lines) and returns the modified source code. Filter::Simple handles the low-level details of interacting with Perl's compilation system.

Here's a simplified example of a filter that comments out lines starting with ## DEBUG:

    package Filter::MyDebug;
    use strict;
    use warnings;
    use Filter::Simple;

    our $DEBUG = 1; # Set to 0 to disable debugging

    # This is the filter subroutine
    sub filter {
        my @lines = @_;
        my @output;
        for my $line (@lines) {
            if ($line =~ /^\s*##\s*DEBUG/) {
                $line = "# $line" unless $DEBUG;
            }
            push @output, $line;
        }
        return @output;
    }

    1;

USING CONTEXT: THE DEBUG FILTER

The Filter::Debug module provides a simple way to include or exclude blocks of debugging code from your script. It uses special comment markers "## DEBUG_BEGIN" and "## DEBUG_END" to delimit these blocks.

The filter operates by maintaining a state variable, $self->{InTraceBlock}, which indicates whether the current line being processed is inside a debugging block. When the filter encounters a ## DEBUG_BEGIN line, it sets this flag to TRUE. When it sees a ## DEBUG_END line, it sets the flag to FALSE. Lines within a debugging block (i.e., when $self->{InTraceBlock} is TRUE) are subject to conditional processing. If debugging is disabled (controlled by another variable, likely $self->{Enabled}), these lines are commented out.

Here is a simplified representation of the filter's logic:

sub filter {
   my ($self) = @_;
   my ($status);
   $status = filter_read(); # Read the next chunk of source code
   # deal with EOF/error first
   return $status if $status <= 0;
   if ($self->{InTraceBlock}) {
      if (/^\s*##\s*DEBUG_END/) {
         $self->{InTraceBlock} = FALSE
      }
      # comment out debug lines when the filter is disabled
      s/^/#/ if ! $self->{Enabled};
   } elsif ( /^\s*##\s*DEBUG_BEGIN/ ) {
      $self->{InTraceBlock} = TRUE;
   }
   return $status;
}

It's important to note that source filters work on the text level and have no understanding of Perl's syntax. This can lead to unexpected behavior. For instance, a here-doc that contains the marker strings could fool the filter:

print <<EOM;
##DEBUG_BEGIN
EOM

Despite these limitations, source filters offer a flexible way to modify Perl code behavior.

CONCLUSION

Source filters provide a powerful mechanism for modifying Perl source code before compilation. They can be used for various purposes, from conditional debugging to implementing new syntax or language features.

If you want to experiment further with source filters, consider these extensions to the Debug filter:

  • Allowing specific named debugging blocks to be enabled or disabled via the DEBUG environment variable.

  • Implementing nested debugging blocks.

  • Creating a source filter that supports named parameters for subroutines, transforming:

            sub MySub ($first, $second, @rest) { ... }

    into:

            sub MySub($$@) {
           my ($first) = shift;
           my ($second) = shift;
           my (@rest) = @_;
           ...
        }

  • Developing a full-fledged macro preprocessor, similar to C's preprocessor, as a source filter.

LIMITATIONS

Source filters operate at the string level and have limited ability to understand the nuances of Perl's syntax. They cannot reliably distinguish between code, comments, strings, or heredocs. Therefore, they are not a replacement for a full parser. Their most stable uses are for tasks like encryption, compression, or enabling binary code loaders (byteloader).

The Switch module, which uses source filters, illustrates some limitations. It may not work correctly within string evaluations. Additionally, regex delimiters like "/.../" can be ambiguous. For example, a regex with embedded newlines might be mistaken for code beginning with the division operator. The recommended workaround is to use explicit delimiters like "m/.../" or "m?...?". Similarly, raw "?...?" delimiters in regexes can cause issues, and using "m?...?" is advised.

The content of "__DATA__" blocks is currently not filtered.

Internal buffer lengths are currently limited to 32-bit integers.

THINGS TO LOOK OUT FOR

Some Filters Clobber the "DATA" Handle
Some source filters utilize the "DATA" handle to read the calling program. When using such filters, you should not rely on this handle or expect any specific behavior when operating on it. Filters based on Filter::Util::Call (and thus Filter::Simple) do not modify the "DATA" filehandle but, conversely, ignore any text following "__DATA__".

REQUIREMENTS

The Source Filters distribution is available on CPAN, under the directory:

CPAN/modules/by-module/Filter

Starting with Perl 5.8, Filter::Util::Call, which forms the core of the Source Filters distribution, is included in the standard Perl distribution. A more user-friendly interface, Filter::Simple by Damian Conway, is also included.
