IPMI-CONFIG(8) Comandos del sistema IPMI-CONFIG(8)

NOMBRE

ipmi-config - configurar valores de IPMI

SINOPSIS

ipmi-config [OPCIÓN...]

DESCRIPCIÓN

ipmi-config se utiliza para obtener y establecer parámetros de configuración en IPMI. Puede usarse para configurar nombres de usuario, contraseñas, información de red, seguridad, Serial-over-LAN (SOL), Platform Event Filtering (PEF), dispositivos de arranque, política de restauración de energía, umbrales de sensores, eventos de sensores y muchas otras opciones de configuración. Por lo general, se requiere alguna configuración antes de que la mayoría de las herramientas de IPMI puedan usarse para acceder a una máquina de forma remota. Por defecto, ipmi-config le permitirá hacer --checkout o --commit solo los valores core de IPMI necesarios para la configuración de IPMI. Para campos de configuración avanzados adicionales relacionados con la configuración del chasis (incluidas las opciones de arranque), Platform Event Filtering (PEF) o sensores, consulte la opción --category a continuación. Para más detalles sobre la configuración core de IPMI, consulte ipmi-config.conf(5). La mayoría de las operaciones de configuración requieren privilegio ADMIN al usar ipmi-config fuera de banda. Aunque conectar a través de un usuario con privilegios ADMIN no es necesario para el uso fuera de banda, la gran mayoría de las opciones de configuración no se recuperarán ni se establecerán.

A continuación se enumeran las opciones generales de IPMI, las opciones específicas de la herramienta, la información de resolución de problemas, la información de soluciones alternativas, los ejemplos y los problemas conocidos. Para una introducción general a FreeIPMI, consulte freeipmi(7). Consulte USO GENERAL a continuación para ver una descripción del uso básico de ipmi-config.

OPCIONES GENERALES

Las siguientes opciones son generales para configurar la comunicación IPMI y ejecutar comandos generales de la herramienta.

-D IPMIDRIVER, --driver-type=IPMIDRIVER
Especifica el tipo de controlador a usar en lugar de hacer una selección automática. Los controladores fuera de banda actualmente disponibles son LAN y LAN_2_0, que realizan IPMI 1.5 e IPMI 2.0 respectivamente. Los controladores en banda actualmente disponibles son KCS, SSIF, OPENIPMI, SUNBMC e INTELDCMI.
--disable-auto-probe
No sondear dispositivos IPMI en banda en busca de configuraciones por defecto.
--driver-address=DIRECCION-CONTROLADOR
Especifica la dirección del controlador en banda que se utilizará en lugar del valor detectado. DIRECCION-CONTROLADOR debe ir precedida de "0x" para un valor hexadecimal y '0' para un valor octal.
--driver-device=DISPOSITIVO
Especifica la ruta del dispositivo del controlador en banda que se utilizará en lugar de la ruta detectada.
--register-spacing=ESPACIADO-REGISTRO
Especifica el espaciado de registro del controlador en banda en lugar del valor detectado. El argumento está en bytes (es decir, espaciado de registro de 32 bits = 4)
--target-channel-number=NUMERO-CANAL
Especifica el número de canal de destino del controlador en banda al que se enviarán las solicitudes IPMI.
--target-slave-address=DIRECCION-ESCLAVO
Especifica el número de esclavo de destino del controlador en banda al que se enviarán las solicitudes IPMI.
-h IPMIHOST1,IPMIHOST2,..., --hostname=IPMIHOST1[:PUERTO],IPMIHOST2[:PUERTO],...
Especifica el(los) host(s) remoto(s) con el(los) que comunicarse. Se pueden separar varios nombres de host con coma o especificarse en formato de rango; consulte SOPORTE DE RANGO DE HOSTOS a continuación. Se puede especificar un puerto opcional con cada host, lo que puede ser útil en situaciones de reenvío de puertos o similares. Si especifica una dirección IPv6 y un puerto, use el formato [DIRECCION]:PUERTO.
-u NOMBRE-DE-USUARIO, --username=NOMBRE-DE-USUARIO
Especifica el nombre de usuario a utilizar al autenticarse con el host remoto. Si no se especifica, se asume un nombre de usuario nulo (es decir, anónimo). El usuario debe tener al menos privilegios ADMIN para que esta herramienta funcione completamente.
-p CONTRASEÑA, --password=CONTRASEÑA
Especifica la contraseña a utilizar al autenticarse con el host remoto. Si no se especifica, se asume una contraseña nula. La longitud máxima de la contraseña es de 16 para IPMI 1.5 y de 20 para IPMI 2.0.
-P, --password-prompt
Solicita la contraseña para evitar la posibilidad de incluirla en las listas de procesos.
-k K_G, --k-g=K_G
Especifica la clave K_g del BMC a utilizar al autenticarse con el host remoto para IPMI 2.0. Si no se especifica, se asume una clave nula. Para introducir la clave en formato hexadecimal, prefije la cadena con '0x'. Por ejemplo, la clave 'abc' se puede introducir con la cadena 'abc' o la cadena '0x616263'
-K, --k-g-prompt
Solicita la clave k-g para evitar la posibilidad de incluirla en las listas de procesos.
--session-timeout=MILISEGUNDOS
Especifica el tiempo de espera de la sesión en milisegundos. El valor por defecto es 20000 milisegundos (20 segundos) si no se especifica.
--retransmission-timeout=MILISEGUNDOS
Especifica el tiempo de espera de retransmisión de paquetes en milisegundos. El valor por defecto es 1000 milisegundos (1 segundo) si no se especifica. El tiempo de espera de retransmisión no puede ser mayor que el tiempo de espera de la sesión.
-a TIPO-AUTENTICACION, --authentication-type=TIPO-AUTENTICACION
Especifica el tipo de autenticación IPMI 1.5 a utilizar. Los tipos de autenticación disponibles actualmente son NONE, STRAIGHT_PASSWORD_KEY, MD2 y MD5. El valor por defecto es MD5 si no se especifica.
-I ID-SUITE-CIFRADO, --cipher-suite-id=ID-SUITE-CIFRADO
Especifica el ID de la suite de cifrado IPMI 2.0 a utilizar. El ID de la suite de cifrado identifica un conjunto de algoritmos de autenticación, integridad y confidencialidad a utilizar para la comunicación IPMI 2.0. El algoritmo de autenticación identifica el algoritmo a utilizar para la configuración de la sesión, el algoritmo de integridad identifica el algoritmo a utilizar para las firmas de paquetes de sesión, y el algoritmo de confidencialidad identifica el algoritmo a utilizar para el cifrado de la carga útil. El valor por defecto es el ID de la suite de cifrado 3 si no se especifica. Los siguientes IDs de suites de cifrado son compatibles actualmente:

0 - Algoritmo de Autenticación = Ninguno; Algoritmo de Integridad = Ninguno; Algoritmo de Confidencialidad = Ninguno

1 - Algoritmo de Autenticación = HMAC-SHA1; Algoritmo de Integridad = Ninguno; Algoritmo de Confidencialidad = Ninguno

2 - Algoritmo de Autenticación = HMAC-SHA1; Algoritmo de Integridad = HMAC-SHA1-96; Algoritmo de Confidencialidad = Ninguno

3 - Algoritmo de Autenticación = HMAC-SHA1; Algoritmo de Integridad = HMAC-SHA1-96; Algoritmo de Confidencialidad = AES-CBC-128

6 - Algoritmo de Autenticación = HMAC-MD5; Algoritmo de Integridad = Ninguno; Algoritmo de Confidencialidad = Ninguno

7 - Algoritmo de Autenticación = HMAC-MD5; Algoritmo de Integridad = HMAC-MD5-128; Algoritmo de Confidencialidad = Ninguno

8 - Algoritmo de Autenticación = HMAC-MD5; Algoritmo de Integridad = HMAC-MD5-128; Algoritmo de Confidencialidad = AES-CBC-128

11 - Algoritmo de Autenticación = HMAC-MD5; Algoritmo de Integridad = MD5-128; Algoritmo de Confidencialidad = Ninguno

12 - Algoritmo de Autenticación = HMAC-MD5; Algoritmo de Integridad = MD5-128; Algoritmo de Confidencialidad = AES-CBC-128

15 - Algoritmo de Autenticación = HMAC-SHA256; Algoritmo de Integridad = Ninguno; Algoritmo de Confidencialidad = Ninguno

16 - Algoritmo de Autenticación = HMAC-SHA256; Algoritmo de Integridad = HMAC_SHA256_128; Algoritmo de Confidencialidad = Ninguno

17 - Algoritmo de Autenticación = HMAC-SHA256; Algoritmo de Integridad = HMAC_SHA256_128; Algoritmo de Confidencialidad = AES-CBC-128

-l NIVEL-PRIVILEGIO, --privilege-level=NIVEL-PRIVILEGIO
Especifica el nivel de privilegio a utilizar. Los niveles de privilegio disponibles actualmente son USER, OPERATOR y ADMIN. El valor por defecto es ADMIN si no se especifica.
--config-file=ARCHIVO
Especifica un archivo de configuración alternativo.

OPCIONES DE IPMI-CONFIG

Las siguientes opciones se utilizan para leer, escribir y encontrar diferencias en los valores de configuración.

-g CATEGORÍA, --category=CATEGORÍA
Especificar la categoría o categorías de datos de configuración a configurar. Opciones actualmente disponibles: core, chassis, sensors, pef, dcmi. Se pueden especificar varias categorías separadas por comas. core incluye toda la configuración principal de IPMI necesaria para que IPMI funcione en un sistema, como la configuración de usuarios, contraseñas, autenticación, redes y serial-over-lan (SOL). chassis incluye toda la configuración relevante del chasis, incluidas las opciones de arranque, los botones del panel frontal y el comportamiento de la alimentación. dcmi incluye funciones especializadas proporcionadas por la Interfaz de Gestión del Centro de Datos (DCMI). El valor predeterminado es core si no se especifica.
-o, --checkout
Obtener información de configuración.
-c, --commit
Actualizar información de configuración desde un archivo de configuración o pares de claves.
-d, --diff
Mostrar diferencias entre la información almacenada y un archivo de configuración o pares de claves.
-n NOMBRE_ARCHIVO, --filename=NOMBRE_ARCHIVO
Especificar un archivo de configuración para checkout/commit/diff. Si se especifica con checkout, no se puede usar con varios hosts ni con --always-prefix.
-e "CLAVE=VALOR", --key-pair="CLAVE=VALOR"
Especificar pares CLAVE=VALOR para checkout/commit/diff. Especifique CLAVE por NombreDeSección:NombreDeCampo. Esta opción se puede usar varias veces. En commit, cualquier par CLAVE=VALOR sobrescribirá cualquier par especificado en un archivo con --filename.
-S SECCIÓN, --section=SECCIÓN
Especificar una SECCIÓN para checkout. Esta opción se puede usar varias veces. La SECCIÓN que especifique debe estar dentro de la categoría o categorías especificadas con --category.
-L, --listsections
Listar las secciones disponibles para checkout con respecto a la categoría o categorías en --category. Algunas secciones de la lista pueden no ser extraídas por defecto y pueden requerir que se aumente la verbosidad.
-v, --verbose
Mostrar información detallada. Cuando se usa con --checkout, se mostrarán secciones y/o campos adicionales poco comunes. En la categoría core, esto incluye la extracción de parámetros de configuración serie, parámetros de Vlan, parámetros de encabezado IPv4, puerto RMCP, todas las direcciones configurables IPv6 (si se soporta más de 1) y secciones para cada canal en un sistema (si existen varios canales). En la categoría pef, esto incluye la extracción de secciones para cada canal en un sistema (si existen varios canales).
-vv
Mostrar información muy detallada. Mostrar información detallada adicional sobre qué campos se pueden y no se pueden extraer, y a veces la razón por la que. A veces muestra campos que se identifican como no compatibles en la placa base.
--lan-channel-number=NÚMERO
Usar un número de canal específico para la configuración LAN. Particularmente útil si la placa base contiene varios canales LAN y un usuario desea usar uno específico.
--serial-channel-number=NÚMERO
Usar un número de canal específico para la configuración serie. Particularmente útil si la placa base contiene varios canales serie y un usuario desea usar uno específico.
--sol-channel-number=NÚMERO
Usar un número de canal específico para la configuración SOL. Particularmente útil si la placa base contiene varios canales SOL y un usuario desea usar uno específico.

OPCIONES DE CACHÉ SDR

Esta herramienta requiere acceso a la caché del repositorio de datos del sensor (SDR) para su funcionamiento general. Por defecto, los datos SDR se descargarán y almacenarán en caché en la máquina local. Las siguientes opciones se aplican a la caché SDR.

--flush-cache
Vaciar una versión en caché del repositorio de datos del sensor (SDR). El SDR se almacena en caché normalmente para un acceso posterior más rápido. Sin embargo, puede ser necesario vaciarlo y regenerarlo si el SDR se ha actualizado en un sistema.
--quiet-cache
No mostrar información sobre la creación/eliminación de caché. Puede ser útil en scripts.
--sdr-cache-recreate
Si la caché SDR está desactualizada o es inválida, recrear automáticamente la caché del repositorio de datos del sensor (SDR). Esta opción puede ser útil para fines de scripting.
--sdr-cache-file=ARCHIVO
Especificar un archivo de caché de repositorio de datos del sensor (SDR) específico para almacenar o leer. Si se utiliza esta opción cuando se especifican varios hosts, se utilizará el mismo archivo de caché SDR para todos los hosts.
--sdr-cache-directory=DIRECTORIO
Especificar un directorio alternativo para almacenar o leer las cachés del repositorio de datos del sensor (SDR). Por defecto, se utilizará el directorio de inicio si no se especifica.

OPCIONES DE HOSTRANGED

Las siguientes opciones manipulan la salida de hostranged. Consulte SOPORTE DE HOSTRANGED a continuación para obtener información adicional sobre hostranges.

-B, --buffer-output
Almacenar en búfer la salida de hostranged. Para cada nodo, almacenar en búfer la salida estándar hasta que el nodo haya completado su operación IPMI. Al especificar esta opción, los datos pueden parecer que salen más lentamente para el usuario, ya que la operación IPMI completa debe completarse antes de que se puedan mostrar los datos. Consulte SOPORTE DE HOSTRANGED a continuación para obtener información adicional.
-C, --consolidate-output
Consolidar la salida de hostranged. La salida estándar completa de cada nodo especificado se consolidará de modo que los nodos con salida idéntica no se muestren dos veces. Un encabezado listará los nodos con la salida consolidada. Cuando se especifica esta opción, no se verá ninguna salida hasta que se hayan completado las operaciones IPMI en todos los nodos. Si el usuario sale del programa de forma anticipada, se volcará toda la salida consolidada actualmente. Consulte SOPORTE DE HOSTRANGED a continuación para obtener información adicional.
-F NUM, --fanout=NUM
Especificar la salida múltiple de hosts. Se utiliza un algoritmo de "ventana deslizante" (o fanout) para la comunicación IPMI paralela, de modo que los nodos más lentos o los que agotan el tiempo de espera no impidan la comunicación paralela. El número máximo de hilos disponibles al mismo tiempo está limitado por el fanout. El valor predeterminado es 64.
-E, --eliminate
Eliminar hosts determinados como no detectados por ipmidetect. Esto intenta eliminar el problema común de que la ejecución de hostranged agote el tiempo de espera debido a que varios nodos se retiran del servicio en un clúster grande. El demonio ipmidetectd debe estar ejecutándose en el nodo que ejecuta el comando.
--always-prefix
Prefijar siempre la salida, incluso si solo se especifica un host o se comunica en banda. Esta opción es principalmente útil para fines de scripting. La opción se ignorará si se especifica con la opción -C.

USO GENERAL

La mayoría de los usuarios querrán:

A) Ejecutar con --checkout para obtener una copia de la configuración actual y almacenarla en un archivo. La salida estándar se puede redirigir a un archivo o se puede especificar un archivo con la opción --filename.

B) Editar el archivo de configuración con un editor.

C) Enviar la configuración de vuelta usando la opción --commit y especificando el archivo de configuración con la opción --filename. La configuración se puede enviar a varios hosts en paralelo a través del soporte de hostrange.

Aunque normalmente no es necesario, algunas placas base no almacenan valores de configuración en memoria no volátil. Por lo tanto, después de los reinicios del sistema, algunos valores de configuración pueden haber cambiado. Es posible que el usuario desee ejecutar herramientas de configuración en cada arranque para asegurarse de que los valores de configuración permanezcan.

Los comentarios se listarán ocasionalmente en los archivos extraídos con información sobre cómo configurar los campos. La página man ipmi-config.conf(5) también proporciona información adicional sobre el significado de los diferentes campos.

Para usuarios con clústeres grandes o conjuntos de nodos, es posible que desee utilizar el mismo archivo de configuración para todos los nodos. El único problema con esto es que la dirección IP y la dirección MAC serán diferentes en cada nodo de su clúster y, por lo tanto, no se pueden configurar a través del mismo archivo de configuración. La dirección IP y la dirección MAC en su archivo de configuración se pueden sobrescribir en la línea de comandos utilizando la opción --key-pair. El siguiente ejemplo podría usarse en un script para configurar cada nodo de un clúster con el mismo archivo de configuración BMC. El script solo necesita determinar la dirección IP y la dirección MAC correctas para usar.

# ipmi-config --commit -k Lan_Conf:Ip_Address=$MY_IP -k Lan_Conf:Mac_Address=$MY_MAC --filename=my_bmc.conf

INFORMACIÓN DE CONFIGURACIÓN DE CASOS ESPECIALES DEL NÚCLEO

Los campos UserN:Password (donde N es un número) no se pueden extraer en algunos sistemas, por lo tanto, el valor extraído siempre estará en blanco.

El campo UserN:Enable_User (donde N es un número) no se puede extraer en sistemas IPMI antiguos, por lo tanto, el valor extraído a veces estará en blanco.

Los campos UserN:Lan_Session_Limit y UserN:Serial_Session_Limit (donde N es un número) no se pueden extraer en algunos sistemas, por lo tanto, el valor extraído siempre estará en blanco. Si no se especifica en confirmaciones posteriores de configuraciones, el campo puede restablecerse a 0 debido a un requisito de que otros campos (configurados junto con el límite de sesión) requerirán un valor de entrada para el límite de sesión. En la mayoría de las condiciones, no es necesario establecer este campo y la mayoría de los usuarios pueden optar por ignorarlo. Este campo se considera opcional según los estándares IPMI y puede resultar en errores al intentar configurarlo a un valor distinto de cero. Si se producen errores, restablecer el valor a 0 debería resolver los problemas.

Los campos Lan_Conf:IP_Address y Lan_Conf:MAC_Address no se pueden confirmar en paralelo a través de la compatibilidad con rangos de hosts. Cada máquina debe configurarse con una tupla única de dirección IP y dirección MAC, por lo tanto, prohibimos esta configuración en ipmi-config.

En algunas placas base, Lan_Conf:MAC_Address puede ser de solo lectura y la dirección MAC se configura automáticamente.

En algunas placas base, Lan_Conf:MAC_Address puede ser de solo lectura y la dirección MAC se configura mediante un comando OEM. Consulte ipmi-oem(8) para ver si se admite la configuración OEM para su placa base.

En algunas placas base, una serie de campos de configuración del usuario no se pueden leer ni configurar hasta después de que se haya configurado un nombre de usuario no nulo o una contraseña no nula. En algunos de estos casos, una salida adecuada en el archivo de configuración indicará esta situación. Sin embargo, no se pueden detectar todos los casos extremos de placas base. Los usuarios pueden desear experimentar con el orden de los campos para solucionar estos problemas.

En algunas placas base, la autenticación OEM en Lan_Conf_Auth no se puede habilitar. Sin embargo, la configuración predeterminada de la placa base tiene estos campos habilitados. Se recomienda a los usuarios que deshabiliten toda la autenticación OEM en esta sección.

En algunas placas base, pueden existir varios canales para la comunicación IPMI LAN o serie. Si existen varios canales, la configuración de ambos canales se puede ver y, en última instancia, configurar ejecutando --checkout en modo detallado. Cada sección o nombre de clave se sufijará apropiadamente con la palabra Channel y el número del canal. Por ejemplo, podría ver un Lan_Conf_Channel_1 y Lan_Conf_Channel_3, donde puede configurar la configuración LAN en los canales 1 y 3 respectivamente.

En algunas placas base, los cambios de configuración no serán "absorbidos" por el sistema hasta que la placa base se reinicie de forma física. Esto se puede lograr apagando y encendiendo físicamente el sistema (por ejemplo, pulsando un botón), o se puede lograr mediante un reinicio en frío. Se puede ejecutar un reinicio en frío a través de bmc-device.

INFORMACIÓN DE CONFIGURACIÓN DE CASOS ESPECIALES DEL CHASIS

Los campos Chassis_Front_Panel_Buttons:Enable_Standby_Button_For_Entering_Standby, Chassis_Front_Panel_Buttons:Enable_Diagnostic_Interrupt_Button Chassis_Front_Panel_Buttons:Enable_Reset_Button, y Chassis_Front_Panel_Buttons:Enable_Power_Off_Button_For_Power_Off_Only es posible que no se puedan extraer en algunos sistemas IPMI, por lo tanto, el valor extraído puede estar en blanco. Algunos de estos campos pueden ser deshabilitables, mientras que otros no. El campo Chassis_Power_Conf:Power_Control_Interval no se puede extraer. Por lo tanto, el valor extraído siempre estará en blanco.

INFORMACIÓN DE CONFIGURACIÓN DE CASOS ESPECIALES DE PEF

En algunas placas base, pueden existir varios canales para la comunicación IPMI LAN. Si existen varios canales, la configuración de ambos canales se puede ver y, en última instancia, configurar ejecutando --checkout en modo detallado. Cada nombre de sección se sufijará apropiadamente con la palabra Channel y el número del canal. Por ejemplo, podría ver un Community_String_Channel_1 y Community_String_Channel_3, donde puede configurar la Cadena de Comunidad en los Canales 1 y 3 respectivamente. Las siguientes son las opciones adecuadas para la entrada de Sensor_Type en la configuración de PEF.

Opciones de Sensor_Type
Reservado, Temperatura, Voltaje, Corriente, Ventilador, Seguridad Física, Intento de Violación de Seguridad de Plataforma, Procesador, Fuente de Alimentación, Unidad de Alimentación, Dispositivo de Refrigeración, Sensor Basado en Otras Unidades, Memoria, Ranura de Unidad, Redimensionamiento de Memoria Posterior, Progreso del Firmware del Sistema, Registro de Eventos Deshabilitado, Watchdog1, Evento del Sistema, Interrupción Crítica, Botón, Placa Módulo, Coprocesador Microcontrolador, Tarjeta Add-in, Chasis, Chipset, Otra FRU, Interconexión de Cable, Terminador, Inicio del Arranque del Sistema, Error de Arranque, Arranque del SO, Parada Crítica del SO, Conector de Ranura, Estado de Alimentación ACPI del Sistema, Watchdog2, Alerta de Plataforma, Presencia de Entidad, IC de ASIC de Monitor, Lan, Estado de Salud del Subsistema de Gestión, Batería, Auditoría de Sesión, Cambio de Versión, Estado de FRU y Cualquiera

INFORMACIÓN DE CONFIGURACIÓN DE CASOS ESPECIALES DE SENSORES

Dado que muchos campos configurables involucran números decimales, pueden ocurrir imprecisiones de precisión/punto flotante al configurar nuevos umbrales. Las imprecisiones pueden no ser aparentes de inmediato. Se recomienda a los usuarios que verifiquen sus cambios después de configurar nuevos umbrales.

COMPATIBILIDAD CON HOSTRANGED

Se pueden introducir varios hosts como listas explícitas de hosts separadas por comas o un rango de nombres de host en la forma general: prefijo[n-m,l-k,...], donde n < m y l < k, etc. Esta última forma no debe confundirse con las clases de caracteres de expresiones regulares (también denotadas por []). Por ejemplo, foo[19] no representa foo1 o foo9, sino que representa un rango degenerado: foo19.

Esta sintaxis de rango está destinada solo como una conveniencia en clústeres con una convención de nomenclatura prefijoNN y la especificación de rangos no debe considerarse necesaria: la lista foo1,foo9 se puede especificar como tal, o mediante el rango foo[1,9].

A continuación, se muestran algunos ejemplos de uso de rangos:

    foo[01-05] en lugar de foo01,foo02,foo03,foo04,foo05
    foo[7,9-10] en lugar de foo7,foo9,foo10
    foo[0-3] en lugar de foo0,foo1,foo2,foo3

Como recordatorio para el lector, algunos shells interpretarán los corchetes ([ y ]) para la coincidencia de patrones. Dependiendo de su shell, puede ser necesario encerrar las listas de rangos entre comillas.

Cuando el usuario especifica varios hosts, se ejecutará un hilo para cada host en paralelo hasta el número de salidas configurado (que se puede ajustar mediante la opción -F). Esto permitirá la comunicación con un gran número de nodos mucho más rápidamente que si se hiciera en serie.

De forma predeterminada, la salida estándar de cada nodo especificado se presentará con el nombre del host antepuesto a cada línea. Aunque esta salida es legible en muchas situaciones, puede ser difícil de leer en otras situaciones. Por ejemplo, la salida de varios nodos puede mezclarse. Las opciones -B y -C se pueden usar para cambiar este comportamiento predeterminado.

La comunicación IPMI en banda se utilizará cuando se especifique el host "localhost". Esto permite al usuario agregar el localhost a la salida de rangos de hosts.

SOLUCIÓN GENERAL DE PROBLEMAS

La mayoría de las veces, los problemas de IPMI se deben a problemas de configuración.

Los problemas de IPMI sobre LAN implican una configuración incorrecta del BMC de la máquina remota. Verifique cuidadosamente que lo siguiente esté configurado correctamente en el BMC de la máquina remota: dirección IP, dirección MAC, máscara de subred, nombre de usuario, habilitación de usuario, privilegio de usuario, contraseña, privilegio LAN, habilitación LAN y tipos de autenticación permitidos. Para conexiones IPMI 2.0, verifique cuidadosamente que los privilegios del conjunto de cifrado y la clave K_g estén configurados correctamente. La herramienta ipmi-config(8) se puede usar para verificar y/o cambiar esta configuración.

Los problemas de IPMI en banda suelen ser causados por controladores mal configurados o BMC no estándar.

Además de los consejos de solución de problemas a continuación, consulte también las SOLUCIONES DE ACCESO DE EMERGENCIA si existen errores específicos del proveedor que se han descubierto y solucionado.

A continuación, se enumeran muchos de los problemas comunes de mensajes de error. Para obtener asistencia adicional, envíe un correo electrónico a la lista de correo <freeipmi-users@gnu.org>.

"username invalid" - El nombre de usuario introducido (o un nombre de usuario NULL si no se introdujo ninguno) no está disponible en la máquina remota. También es posible que la configuración del nombre de usuario del BMC remoto sea incorrecta.

"password invalid" - La contraseña introducida (o una contraseña NULL si no se introdujo ninguna) es incorrecta. También es posible que la contraseña del usuario no esté configurada correctamente en el BMC remoto.

"password verification timeout" - La verificación de contraseña ha expirado. Se produjo un error de "contraseña inválida" (descrito anteriormente) o un error genérico de "tiempo de espera de sesión" (descrito a continuación). Durante este punto del protocolo, no se puede diferenciar cuál ocurrió.

"k_g invalid" - La clave K_g introducida (o una clave K_g NULL si no se introdujo ninguna) es incorrecta. También es posible que la clave K_g no esté configurada correctamente en el BMC remoto.

"privilege level insufficient" - Un comando IPMI requiere un privilegio de usuario superior al que se autenticó. Intente autenticarse con un privilegio superior. Esto puede requerir autenticarse con un usuario diferente que tenga un privilegio máximo superior.

"privilege level cannot be obtained for this user" - El nivel de privilegio con el que intenta autenticarse es superior al máximo permitido para este usuario. Intente nuevamente con un privilegio inferior. También es posible que el nivel de privilegio máximo permitido para un usuario no esté configurado correctamente en el BMC remoto.

"authentication type unavailable for attempted privilege level" - El tipo de autenticación con el que desea autenticarse no está disponib

MENSAJES DE ERROR

"nivel de privilegio no válido" - No se pudo autenticar con el nivel de privilegio especificado. Intente nuevamente con un tipo de autenticación alternativo o un nivel de privilegio alternativo. También puede ser que los tipos de autenticación disponibles con los que puede autenticarse no estén configurados correctamente en el BMC remoto.

"id de suite de cifrado no disponible" - El id de suite de cifrado con el que desea autenticarse no está disponible en el BMC remoto. Intente nuevamente con un id de suite de cifrado alternativo. También puede ser que los id de suite de cifrado disponibles no estén configurados correctamente en el BMC remoto.

"ipmi 2.0 no disponible" - No se detectó IPMI 2.0 en la máquina remota. Intente usar IPMI 1.5 en su lugar.

"tiempo de espera de conexión" - La comunicación inicial de IPMI falló. Es posible que haya varios errores potenciales, que incluyen un nombre de host inválido especificado, una dirección IP de IPMI que no se puede resolver, IPMI no está habilitado en el servidor remoto, la conexión de red es deficiente, etc. Verifique la configuración y la conectividad.

"tiempo de espera de sesión" - La sesión IPMI ha expirado. Por favor, reconéctese. Si este error ocurre con frecuencia, es posible que desee aumentar el tiempo de espera de retransmisión. Algunos BMC remotos son considerablemente más lentos que otros.

"dispositivo no encontrado" - No se pudo encontrar el dispositivo especificado. Verifique la configuración o las entradas e intente nuevamente.

"tiempo de espera del controlador" - La comunicación con el controlador o dispositivo ha expirado. Intente nuevamente.

"tiempo de espera del mensaje" - La comunicación con el controlador o dispositivo ha expirado. Intente nuevamente.

"BMC ocupado" - El BMC está actualmente ocupado. Puede estar procesando información o tener demasiadas sesiones simultáneas para gestionar. Espere e intente nuevamente.

"no se pudo encontrar dispositivo inband" - No se pudo encontrar un dispositivo inband. Verifique la configuración o especifique un dispositivo o controlador específico en la línea de comandos.

"tiempo de espera del controlador" - El controlador inband ha expirado al comunicarse con el BMC local o el procesador de servicio. El BMC o el procesador de servicio pueden estar ocupados o (en el peor de los casos) posiblemente no funcionen.

SOLUCIONES ALTERNATIVAS

Con tantos proveedores diferentes implementando sus propias soluciones IPMI, diferentes proveedores pueden implementar sus protocolos IPMI incorrectamente. Lo siguiente describe una serie de soluciones alternativas disponibles actualmente para manejar los problemas de cumplimiento detectados. Cuando sea posible, las soluciones alternativas se han implementado para que sean transparentes para el usuario. Sin embargo, algunas requerirán que el usuario especifique que se use una solución alternativa a través de la opción -W.

El hardware que se enumera a continuación puede indicar solo el hardware en el que se descubrió un problema. Las versiones más nuevas de hardware pueden corregir los problemas indicados a continuación. Máquinas similares de diferentes proveedores pueden o no exhibir los mismos problemas. Diferentes proveedores pueden licenciar su firmware del mismo desarrollador de firmware IPMI, por lo que puede valer la pena probar las soluciones alternativas enumeradas a continuación, incluso si su placa base no aparece.

Si cree que su hardware tiene un problema de cumplimiento adicional que requiere una solución alternativa, comuníquese con los mantenedores de FreeIPMI en <freeipmi-users@gnu.org> o <freeipmi-devel@gnu.org>.

assumeio - Esta bandera de solución alternativa asumirá que las interfaces inband se comunican con la E/S del sistema en lugar de estar mapeadas en memoria. Esto solucionará sistemas que informan direcciones base inválidas. Aquellos que encuentren este problema pueden ver errores como "dispositivo no compatible" o "no se pudo encontrar dispositivo inband". Problema observado en HP ProLiant DL145 G1.

spinpoll - Esta bandera de solución alternativa indicará a algunos controladores inband (en particular, el controlador KCS) que giren mientras sondea en lugar de poner el proceso en suspensión. Esto puede mejorar significativamente el tiempo de ejecución en tiempo real de las herramientas, ya que la granularidad del programador del sistema operativo puede ser mucho mayor que el tiempo necesario para realizar una única transacción de mensaje IPMI. Sin embargo, al girar, su sistema puede estar realizando menos trabajo útil al no cambiar el contexto de la herramienta para una tarea más útil.

authcap - Esta bandera de solución alternativa omitirá las verificaciones tempranas de las capacidades del nombre de usuario, las capacidades de autenticación y el soporte de K_g, y permitirá que la autenticación IPMI se realice correctamente. Soluciona múltiples problemas en los que el sistema remoto no informa correctamente las capacidades del nombre de usuario, las capacidades de autenticación o el estado de K_g. Aquellos que encuentren este problema pueden ver errores como "nombre de usuario inválido", "tipo de autenticación no disponible para el nivel de privilegio intentado" o "k_g inválido". Problema observado en Asus P5M2/P5MT-R/RS162-E4/RX4, Intel SR1520ML/X38ML y Sun Fire 2200/4150/4450 con ELOM.

nochecksumcheck - Esta bandera de solución alternativa le dirá a FreeIPMI que no verifique las sumas de verificación devueltas de las respuestas de comandos IPMI. Soluciona sistemas que devuelven sumas de verificación inválidas debido a errores de implementación, pero el paquete es válido de lo contrario. Se advierte a los usuarios sobre el uso de esta opción, ya que elimina la validación de la integridad del paquete en varias circunstancias. Sin embargo, es poco probable que sea un problema en la mayoría de las situaciones. Aquellos que encuentren este problema pueden ver errores como "tiempo de espera de conexión", "tiempo de espera de sesión" o "tiempo de espera de verificación de contraseña". En conexiones IPMI 1.5, también puede ser necesaria la solución alternativa "noauthcodecheck". Problema observado en Supermicro X9SCM-iiF, Supermicro X9DRi-F y Supermicro X9DRFR.

idzero - Esta bandera de solución alternativa permitirá que los identificadores de sesión vacíos sean aceptados por el cliente. Soluciona sesiones IPMI que informan identificadores de sesión vacíos al cliente. Aquellos que encuentren este problema pueden ver errores de "tiempo de espera de sesión". Problema observado en Tyan S2882 con BMC M3289.

unexpectedauth - Esta bandera de solución alternativa permitirá que los authcodes inesperados no nulos se verifiquen como si fueran esperados. Soluciona un problema cuando los paquetes contienen datos de autenticación no nulos cuando deberían ser nulos debido a la autenticación por mensaje deshabilitada. Aquellos que encuentren este problema pueden ver errores de "tiempo de espera de sesión". Problema observado en Dell PowerEdge 2850, SC1425. Confirmado que se ha corregido en firmware más reciente.

forcepermsg - Esta bandera de solución alternativa forzará el uso de autenticación por mensaje independientemente de lo que anuncie el sistema remoto. Soluciona un problema en el que la autenticación por mensaje se anuncia como deshabilitada en el sistema remoto, pero en realidad es requerida para el protocolo. Aquellos que encuentren este problema pueden ver errores de "tiempo de espera de sesión". Problema observado en IBM eServer 325.

endianseq - Esta bandera de solución alternativa invertirá el orden de los números de secuencia de la sesión para permitir que la sesión continúe correctamente. Soluciona números de secuencia IPMI 1.5 que tienen el orden de bytes incorrecto. Aquellos que encuentren este problema pueden ver errores de "tiempo de espera de sesión". Problema observado en algunos Sun ILOM 1.0/2.0 (depende del orden de bytes del procesador de servicio).

noauthcodecheck - Esta bandera de solución alternativa le dirá a FreeIPMI que no verifique los códigos de autenticación devueltos de las respuestas de comandos IPMI 1.5. Soluciona sistemas que devuelven códigos de autenticación inválidos debido a errores de hash o de implementación. Se advierte a los usuarios sobre el uso de esta opción, ya que elimina una verificación de autenticación que valida la integridad de un paquete. Sin embargo, en la mayoría de las organizaciones, es poco probable que sea un problema de seguridad. Aquellos que encuentren este problema pueden ver errores como "tiempo de espera de conexión", "tiempo de espera de sesión" o "tiempo de espera de verificación de contraseña". Problema observado en Xyratex FB-H8-SRAY, Intel Windmill, Quanta Winterfell y Wiwynn Windmill.

intel20 - Esta bandera de solución alternativa solucionará varios problemas de autenticación IPMI 2.0 de Intel. Los problemas cubiertos incluyen el relleno de nombres de usuario y la truncación de contraseñas si el algoritmo de autenticación es HMAC-MD5-128. Aquellos que encuentren este problema pueden ver errores como "nombre de usuario inválido", "contraseña inválida" o "k_g inválido". Problema observado en Intel SE7520AF2 con Intel Server Management Module (Professional Edition).

supermicro20 - Esta bandera de solución alternativa solucionará varios problemas de autenticación IPMI 2.0 de Supermicro en placas base con firmware IPMI Peppercon. Los problemas cubiertos incluyen el manejo de códigos de autenticación de longitud inválida. Aquellos que encuentren este problema pueden ver errores de "contraseña inválida". Problema observado en Supermicro H8QME con tarjeta hija SIMSO. Confirmado que se ha corregido en firmware más reciente.

sun20 - Esta bandera de solución alternativa solucionará varios problemas de autenticación IPMI 2.0 de Sun. Los problemas cubiertos incluyen claves hash de longitud inválida, claves hasheadas incorrectamente y registros de suite de cifrado inválidos. Aquellos que encuentren este problema pueden ver errores como "contraseña inválida" o "error de bmc". Problema observado en Sun Fire 4100/4200/4500 con ILOM. Esta solución alternativa incluye automáticamente la solución alternativa "opensesspriv".

opensesspriv - Esta bandera de solución alternativa alterará ligeramente el protocolo de conexión IPMI 2.0 de FreeIPMI para solucionar un algoritmo de hash inválido utilizado por el sistema remoto. El nivel de privilegio enviado durante la etapa de Apertura de Sesión de una conexión IPMI 2.0 se utiliza para hashear claves en lugar del nivel de privilegio enviado durante la etapa de conexión RAKP1. Aquellos que encuentren este problema pueden ver errores como "contraseña inválida", "k_g inválido", "código de estado rmcpplus incorrecto" o "no se puede obtener el nivel de privilegio para este usuario". Problema observado en Sun Fire 4100/4200/4500 con ILOM, Inventec 5441/Dell Xanadu II, Supermicro X8DTH, Supermicro X8DTG, Intel S5500WBV/Penguin Relion 700, Intel S2600JF/Appro 512X, Quanta QSSC-S4R/Appro GB812X-CN, Dell C5220 y el BMC de software OpenIPMI. Esta solución alternativa se activa automáticamente con la solución alternativa "sun20".

integritycheckvalue - Esta bandera de solución alternativa solucionará un valor de verificación de integridad inválido durante el establecimiento de una sesión IPMI 2.0 cuando se utiliza la Suite de Cifrado ID 0. El valor de verificación de integridad debería ser de longitud 0, sin embargo, la placa base remota responde con un campo no vacío. Aquellos que encuentren este problema pueden ver errores de "k_g inválido". Problema observado en Supermicro X8DTG, Supermicro X8DTU e Intel S5500WBV/Penguin Relion 700, e Intel S2600JF/Appro 512X.

No hay soporte para IPMI 1.5 - Se ha descubierto que algunas placas base que admiten IPMI 2.0 no admiten IPMI 1.5. Aquellos que encuentren este problema pueden ver errores como "ipmi 2.0 no disponible" o "tiempo de espera de conexión". Este problema se puede solucionar utilizando IPMI 2.0 en lugar de IPMI 1.5 especificando --driver-type=LAN_2_0. Problema observado en varias placas base HP y Supermicro.

slowcommit - Esta solución alternativa ralentizará las confirmaciones al BMC durmiendo un segundo entre la confirmación de secciones. Soluciona placas base que tienen BMC que pueden verse sobrecargados por las confirmaciones. Aquellos que encuentren este problema pueden ver errores de confirmación o confirmaciones que no se escriben en el BMC. Problema observado en Supermicro H8QME.

TRABAJO ALREDEDOR

Este workaround intenta la comunicación con el BMC a través del canal de comunicación especificado en cada clave.

Cada clave contiene una lista de canales de comunicación de la BMC. `ipmi-config` intentará realizar el commit de cada clave en cada canal hasta que tenga éxito.

Cuando se le indica al programa que envíe un commit de una clave de configuración, es decir, cuando las opciones --commit y --key-pair están especificadas, `ipmi-config` registrará un error si el commit falla. Sin embargo, `ipmi-config` continuará intentando enviar el commit al resto de los canales de comunicación de la BMC. Cuando se especifican múltiples claves de configuración a través de la opción --key-pair, `ipmi-config` enviará las claves especificadas en todos los canales de comunicación de la BMC hasta que tenga éxito. Si un commit falla en todos los canales para una clave, `ipmi-config` registrará un error para esa clave específica.

forcecommitsinglekey - Este workaround forzará la comunicación con el BMC para enviar un commit a cada clave individualmente. Funciona en placas base que tienen BMCs que pueden verse abrumadas por los commits. Quienes se encuentren con este problema pueden ver errores de commit o commits que no se escriben en la BMC. Problema observado en Quanta S99Q/Dell FS12-TY y Dell PowerEdge T320.

solchannelassumelanchannel - Este workaround forzará a ipmi-config a asumir que el canal utilizado para SOL es idéntico al canal utilizado para LAN. En algunas placas base, el canal SOL se reporta incorrectamente, lo que lleva a una configuración incorrecta. Notablemente, este problema surgió al intentar configurar múltiples canales. Problema observado en Intel S5500WBV/Penguin Relion 700.

EJEMPLOS

# ipmi-config --checkout

Muestra toda la información de configuración principal en la consola. # ipmi-config --checkout --category=pef

Muestra toda la información de configuración de pef en la consola. # ipmi-config --checkout --category=pef,chassis

Muestra toda la información de configuración de pef y chassis en la consola.

# ipmi-config --checkout --filename=bmc-data1.conf

Almacena toda la información de configuración principal en bmc-data1.conf.

# ipmi-config --diff --filename=bmc-data2.conf

Muestra todas las diferencias entre la configuración actual y el archivo bmc-data2.conf.

# ipmi-config --diff --key-pair="lan_conf_misc:gratuitous_arp_interval=8"

Muestra la diferencia entre la configuración actual y 'lan_conf_misc:gratuitous_arp_interval' con el valor '8'.

# ipmi-config --commit --filename=bmc-data1.conf

Confirma todos los valores de configuración del archivo bmc-data1.conf.

# ipmi-config --commit --key-pair="lan_conf_misc:gratuitous_arp_interval=4"

Confirma la clave 'lan_conf_misc:gratuitous_arp_interval' con el valor '4'.

# ipmi-config --commit --filename=bmc-data-updt.conf --key-pair="lan_conf_misc:gratuitous_arp_interval=4"

Confirma todos los valores de configuración del archivo bmc-data-updt.conf y la clave 'lan_conf_misc:gratuitous_arp_interval' con el valor '4'.

DIAGNOSTICO

Tras una ejecución exitosa, el estado de salida es 0. En caso de error no fatal, el estado de salida es 1. En caso de error fatal, el estado de salida es 2.

Si se especifican múltiples hosts para la comunicación, el estado de salida es 0 si y solo si todos los objetivos se ejecutan correctamente. Si ocurre algún error no fatal, el estado de salida es 1. Si ocurre algún error fatal, el estado de salida es 2.

PROBLEMAS CONOCIDOS

En sistemas operativos más antiguos, si introduce su nombre de usuario, contraseña y otra información potencialmente relevante para la seguridad en la línea de comandos, esta información puede ser descubierta por otros usuarios al utilizar herramientas como el comando ps(1) o al mirar en el sistema de archivos /proc. Generalmente es más seguro introducir la información de la contraseña con opciones como las opciones -P o -K. Configurar información relevante para la seguridad en el archivo de configuración de FreeIPMI también sería una forma apropiada de ocultar esta información.

Para prevenir ataques de fuerza bruta, algunas BMCs se "bloquearán" temporalmente después de un número de errores de autenticación remota. Puede que necesite esperar un tiempo para que este "bloqueo" temporal pase antes de poder autenticarse de nuevo.
