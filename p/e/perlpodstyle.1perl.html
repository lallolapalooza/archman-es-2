PERLPODSTYLE(1perl) Perl Programmers Reference Guide PERLPODSTYLE(1perl)

NOMBRE

perlpodstyle - Guía de estilo de documentación de Perl POD

DESCRIPCIÓN

Estas son pautas generales para escribir documentación POD para scripts y módulos de Perl, basadas en las pautas generales para escribir buenas páginas de manual de UNIX. Todas estas pautas son, por supuesto, opcionales, pero seguirlas hará que su documentación sea más consistente con otra documentación del sistema.

El nombre del programa que se documenta se escribe convencionalmente en negrita (usando B<>) dondequiera que aparezca, al igual que todas las opciones del programa. Los argumentos deben escribirse en cursiva (I<>). Los nombres de las funciones se escriben tradicionalmente en cursiva; si escribe una función como function(), Pod::Man se encargará de esto por usted. El código o comandos literales deben estar en C<>. Las referencias a otras páginas de manual deben tener el formato manpage(section) o "L<manpage(section)>", y Pod::Man las formateará automáticamente de forma adecuada. La segunda forma, con L<>, se utiliza para solicitar que un formateador POD cree un enlace a la página de manual si es posible. Como excepción, normalmente se omite la sección al referirse a la documentación de módulos, ya que no está claro en qué sección se encontrará la documentación de los módulos; use "L<Module::Name>" en su lugar para las referencias de módulos.

Las referencias a otros programas o funciones normalmente tienen el formato de referencias de páginas de manual para que las herramientas de referencia cruzada puedan proporcionar al usuario enlaces y similares. Sin embargo, es posible exagerar, así que tenga cuidado de no saturar su documentación con demasiadas marcas. Las referencias a otros programas que no se dan como referencias de páginas de manual deben ir entre B<>.

Los encabezados principales deben establecerse usando una directiva "=head1", y se escriben históricamente en el formato TODO EN MAYÚSCULAS bastante llamativo; esto no es obligatorio, pero se recomienda encarecidamente para que las secciones tengan nombres consistentes en diferentes paquetes de software. Los encabezados menores se pueden incluir usando "=head2", y suelen estar en mayúsculas y minúsculas.

Las secciones estándar de una página de manual son:

NOMBRE
Sección obligatoria; debe ser una lista separada por comas de los programas o funciones documentados por esta página POD, como: 
foo, bar - programas para hacer algo

Los indexadores de páginas de manual a menudo son extremadamente exigentes con el formato de esta sección, así que no ponga nada en ella excepto esta línea. Cada programa o función documentado por esta página POD debe estar listado, separado por una coma y un espacio. Para un módulo Perl, simplemente proporcione el nombre del módulo. Un guión único, y solo un guión único, debe separar la lista de programas o funciones de la descripción. No use ninguna marca como C<> o B<> en ninguna parte de esta línea. Las funciones no deben calificarse con "()" o similares. La descripción idealmente debería caber en una sola línea, incluso si un programa de manual reemplaza el guión con algunas tabulaciones.

SINOPSIS
Un resumen breve de uso para programas y funciones. Esta sección es obligatoria para las páginas de la sección 3. Para la documentación de módulos Perl, suele ser conveniente que el contenido de esta sección sea un bloque literal que muestre algunos (breves) ejemplos de formas típicas en que se utiliza el módulo.
DESCRIPCIÓN
Descripción y discusión extendida del programa o funciones, o el cuerpo de la documentación para páginas de manual que documentan algo más. Si es particularmente larga, es una buena idea dividirla en subsecciones con directivas "=head2" como: 
=head2 Uso Normal
=head2 Características Avanzadas
=head2 Escribiendo Archivos de Configuración

o lo que sea apropiado para su documentación.

Para un módulo, aquí es generalmente donde va la documentación de las interfaces proporcionadas por el módulo, generalmente en forma de una lista con un "=item" para cada interfaz. Dependiendo de cuántas interfaces haya, puede que desee poner esa documentación en secciones separadas de MÉTODOS, FUNCIONES, MÉTODOS DE CLASE o MÉTODOS DE INSTANCIA en su lugar y reservar la sección DESCRIPCIÓN para una descripción general.

OPCIONES
Descripción detallada de cada una de las opciones de línea de comandos que acepta el programa. Esto debe estar separado de la descripción para el uso de analizadores como Pod::Usage. Normalmente se presenta como una lista, con cada opción como un "=item" separado. La cadena de opción específica debe ir entre B<>. Cualquier valor que tome la opción debe ir entre I<>. Por ejemplo, la sección para la opción --section=manext se introduciría con: 
=item B<--section>=I<manext>

Las opciones sinónimas (como las formas corta y larga) se separan por una coma y un espacio en la misma línea de "=item", o se enumeran opcionalmente como su propio elemento con una referencia al nombre canónico. Por ejemplo, dado que --section también se puede escribir como -s, lo anterior sería:

=item B<-s> I<manext>, B<--section>=I<manext>

Se recomienda escribir primero la opción corta porque es más fácil de leer. La opción larga es lo suficientemente larga como para atraer la atención de todos modos y la opción corta puede perderse en el ruido visual.

VALOR DE RETORNO
Lo que el programa o función devuelve, si tiene éxito. Esta sección puede omitirse para programas cuyos códigos de salida precisos no son importantes, siempre que devuelvan 0 en caso de éxito y un valor distinto de cero en caso de fallo, como es estándar. Siempre debe estar presente para las funciones. Para los módulos, puede ser útil resumir los valores de retorno de la interfaz del módulo aquí, o puede ser más útil discutir los valores de retorno por separado en la documentación de cada función o método que proporciona el módulo.
ERRORES
Excepciones, códigos de retorno de error, estados de salida y configuraciones de errno. Normalmente se usa para la documentación de funciones o módulos; la documentación de programas utiliza DIAGNÓSTICOS en su lugar. La regla general es que los errores impresos en "STDOUT" o "STDERR" y destinados al usuario final se documentan en DIAGNÓSTICOS, mientras que los errores que se pasan internamente al programa que llama y están destinados a otros programadores se documentan en ERRORES. Al documentar una función que establece errno, se debe dar una lista completa de los posibles valores de errno aquí.
DIAGNÓSTICOS
Todos los mensajes posibles que el programa puede imprimir y qué significan. Es posible que desee seguir el mismo estilo de documentación que la documentación de Perl; consulte perldiag(1) para más detalles (y mire también la fuente POD).

Si corresponde, incluya detalles sobre lo que el usuario debe hacer para corregir el error; documentar un error como que indica "el búfer de entrada es demasiado pequeño" sin decirle al usuario cómo aumentar el tamaño del búfer de entrada (o al menos decirle que no es posible) no es muy útil.

EJEMPLOS
Proporcione algunos ejemplos de uso del programa o función. No escatime; los usuarios a menudo encuentran esta la parte más útil de la documentación. Los ejemplos generalmente se presentan como párrafos literales.

No presente un ejemplo sin explicar lo que hace. Agregar un párrafo corto que diga lo que hará el ejemplo puede aumentar enormemente el valor del ejemplo.

AMBIENTE
Variables de entorno que le importan al programa, normalmente presentadas como una lista usando "=over", "=item" y "=back". Por ejemplo: 
=over 6
=item HOME
Se utiliza para determinar el directorio principal del usuario. F<.foorc>
en este directorio se lee para detalles de configuración, si existe.
=back

Dado que las variables de entorno normalmente están en todas mayúsculas, generalmente no se necesita ningún formato especial adicional; ya son lo suficientemente llamativas.

ARCHIVOS
Todos los archivos utilizados por el programa o función, normalmente presentados como una lista, y para qué se utilizan.

NAME

perlpodstyle - Conventions for writing POD documentation

DESCRIPTION

This document describes the conventions for writing POD (Plain Old Documentation) documentation for Perl modules and programs. Following these conventions will make your documentation more consistent and easier for users to understand.

NAME
The name of the module or program, followed by a brief description. For example: 
NAME
    My::Module - A brief description of what this module does.
The name should be the same as the name used in the use statement if it's a module. If it's a program, it should be the name of the program.
SYNOPSIS
A short example of how to use the module or program. This is often the first thing users look at. It should be clear, concise, and demonstrate the most common usage.
DESCRIPTION
A more detailed explanation of what the module or program does, its features, and how it works. This section can be quite long.
OPTIONS
If the program accepts command-line options, they should be documented here. List each option and explain what it does.
METHODS
For object-oriented modules, document the methods provided by the module. This section is often broken down further into subsections like CONSTRUCTORS and INSTANCE METHODS.
FUNCTIONS
If the module provides functions directly (not as methods), document them here.
DIAGNOSTICS
Describe any error messages or warnings that the module or program might produce, and explain what they mean and how to fix them.
FILES
List any important files that the module or program uses or creates. File names should be enclosed in F<>. It's particularly important to document files that will be potentially modified.
CAVEATS
Things to take special care with, sometimes called WARNINGS.
BUGS
Things that are broken or just don't work quite right.
RESTRICTIONS
Bugs you don't plan to fix. :-)
NOTES
Miscellaneous commentary.
AUTHOR
Who wrote it (use AUTHORS for multiple people). It's a good idea to include your current e-mail address (or some e-mail address to which bug reports should be sent) or some other contact information so that users have a way of contacting you. Remember that program documentation tends to roam the wild for far longer than you expect and pick a contact method that's likely to last.
HISTORY
Programs derived from other sources sometimes have this. Some people keep a modification log here, but that usually gets long and is normally better maintained in a separate file.
COPYRIGHT AND LICENSE
For copyright 
Copyright YEAR(s) YOUR NAME(s)

(No, (C) is not needed. No, "all rights reserved" is not needed.)

For licensing the easiest way is to use the same licensing as Perl itself:

This library is free software; you may redistribute it and/or
modify it under the same terms as Perl itself.

This makes it easy for people to use your module with Perl. Note that this licensing example is neither an endorsement nor a requirement, you are of course free to choose any licensing.

SEE ALSO
Other man pages to check out, like man(1), man(7), makewhatis(8), or catman(8). Normally a simple list of man pages separated by commas, or a paragraph giving the name of a reference work. Man page references, if they use the standard name(section) form, don't have to be enclosed in L<> (although it's recommended), but other things in this section probably should be when appropriate.

If the package has a mailing list, include a URL or subscription instructions here.

If the package has a web site, include a URL here.

Documentation of object-oriented libraries or modules may want to use CONSTRUCTORS and METHODS sections, or CLASS METHODS and INSTANCE METHODS sections, for detailed documentation of the parts of the library and save the DESCRIPTION section for an overview. Large modules with a function interface may want to use FUNCTIONS for similar reasons. Some people use OVERVIEW to summarize the description if it's quite long.

Section ordering varies, although NAME must always be the first section (you'll break some man page systems otherwise), and NAME, SYNOPSIS, DESCRIPTION, and OPTIONS generally always occur first and in that order if present. In general, SEE ALSO, AUTHOR, and similar material should be left for last. Some systems also move WARNINGS and NOTES to last. The order given above should be reasonable for most purposes.

Some systems use CONFORMING TO to note conformance to relevant standards and MT-LEVEL to note safeness for use in threaded programs or signal handlers. These headings are primarily useful when documenting parts of a C library.

Finally, as a general note, try not to use an excessive amount of markup. As documented here and in Pod::Man, you can safely leave Perl variables, function names, man page references, and the like unadorned by markup and the POD translators will figure it out for you. This makes it much easier to later edit the documentation. Note that many existing translators will do the wrong thing with e-mail addresses when wrapped in L<>, so don't do that.
