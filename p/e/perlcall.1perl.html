NOMBRE

perlcall - Convenciones de llamada de Perl desde C

DESCRIPCIÓN

El propósito de este documento es mostrarle cómo llamar a subrutinas de Perl directamente desde C, es decir, cómo escribir callbacks.

Además de discutir la interfaz C proporcionada por Perl para escribir callbacks, el documento utiliza una serie de ejemplos para mostrar cómo funciona realmente la interfaz en la práctica. Además, se cubren algunas técnicas para codificar callbacks.

Ejemplos donde los callbacks son necesarios incluyen:

  • Un manejador de errores

    Ha creado una interfaz XSUB para la API C de una aplicación.

    Una característica bastante común en las aplicaciones es permitirle definir una función C que se llamará cada vez que ocurra algo desagradable. Lo que nos gustaría es poder especificar una subrutina Perl que se llame en su lugar.

  • Un programa impulsado por eventos

    El ejemplo clásico de dónde se utilizan los callbacks es al escribir un programa impulsado por eventos, como para una aplicación X11. En este caso, registra funciones para que se llamen cada vez que ocurran eventos específicos, por ejemplo, se presiona un botón del ratón, el cursor entra en una ventana o se selecciona un elemento del menú.

Aunque las técnicas descritas aquí son aplicables al incrustar Perl en un programa C, este no es el objetivo principal de este documento. Hay otros detalles que deben considerarse y son específicos de incrustar Perl. Para obtener detalles sobre cómo incrustar Perl en C, consulte perlembed.

Antes de lanzarse de cabeza al resto de este documento, sería una buena idea haber leído los siguientes dos documentos: perlxs y perlguts.

LAS FUNCIONES CALL

Aunque esto es más fácil de explicar usando ejemplos, primero debe tener en cuenta algunas definiciones importantes.

Perl tiene una serie de funciones C que le permiten llamar a subrutinas de Perl. Son:

I32 call_sv(SV* sv, I32 flags);
I32 call_pv(char *subname, I32 flags);
I32 call_method(char *methname, I32 flags);
I32 call_argv(char *subname, I32 flags, char **argv);

La función clave es call_sv. Todas las demás funciones son envoltorios bastante simples que facilitan la llamada a subrutinas de Perl en casos especiales. Al final, todas llamarán a call_sv para invocar la subrutina de Perl.

Todas las funciones call_* tienen un parámetro "flags" que se utiliza para pasar una máscara de bits de opciones a Perl. Esta máscara de bits opera de manera idéntica para cada una de las funciones. La configuración disponible en la máscara de bits se discute en "VALORES DE FLAG".

Cada una de las funciones se discutirá a su vez.

call_sv
call_sv toma dos parámetros. El primero, "sv", es un SV*. Esto le permite especificar la subrutina de Perl a llamar, ya sea como una cadena C (que primero se ha convertido a un SV) o una referencia a una subrutina. La sección, "Usando call_sv", muestra cómo puede hacer uso de call_sv.
call_pv
La función, call_pv, es similar a call_sv excepto que espera que su primer parámetro sea un char* C que identifica la subrutina de Perl que desea llamar, por ejemplo, "call_pv("fred", 0)". Si la subrutina que desea llamar está en otro paquete, simplemente incluya el nombre del paquete en la cadena, por ejemplo, "pkg::fred".
call_method
La función call_method se utiliza para llamar a un método de una clase Perl. El parámetro "methname" corresponde al nombre del método a llamar. Tenga en cuenta que la clase a la que pertenece el método se pasa en la pila de Perl en lugar de en la lista de parámetros. Esta clase puede ser el nombre de la clase (para un método estático) o una referencia a un objeto (para un método virtual). Consulte perlobj para obtener más información sobre métodos estáticos y virtuales y "Usando call_method" para un ejemplo de uso de call_method.
call_argv
call_argv llama a la subrutina de Perl especificada por la cadena C almacenada en el parámetro "subname". También toma el parámetro habitual "flags". El parámetro final, "argv", consiste en una lista terminada en NULL de cadenas C que se pasarán como parámetros a la subrutina de Perl. Consulte "Usando call_argv".

Todas las funciones devuelven un entero. Este es el número de elementos devueltos por la subrutina de Perl. Los elementos reales devueltos por la subrutina se almacenan en la pila de Perl.

Como regla general, siempre debe verificar el valor de retorno de estas funciones. Incluso si solo espera un número particular de valores que se devuelvan de la subrutina de Perl, no hay nada que impida que alguien haga algo inesperado; no diga que no se le ha advertido.

VALORES DE FLAG

El parámetro "flags" en todas las funciones call_* es uno de "G_VOID", "G_SCALAR", o "G_LIST", que indican el contexto de llamada, combinados OR con una máscara de bits de cualquier combinación de los otros símbolos G_* definidos a continuación.

G_VOID

Llama a la subrutina de Perl en un contexto nulo.

Este flag tiene 2 efectos:

1.
Indica a la subrutina que se está llamando que se está ejecutando en un contexto nulo (si ejecuta wantarray, el resultado será el valor indefinido).
2.
Asegura que no se devuelva nada de la subrutina.

El valor devuelto por la función call_* indica cuántos elementos se han devuelto de la subrutina de Perl; en este caso, será 0.

G_SCALAR

Llama a la subrutina de Perl en un contexto escalar. Esta es la configuración predeterminada del flag de contexto para todas las funciones call_*.

Este flag tiene 2 efectos:

1.
Indica a la subrutina que se está llamando que se está ejecutando en un contexto escalar (si ejecuta wantarray, el resultado será falso).
2.
Asegura que solo se devuelva un escalar de la subrutina. La subrutina puede, por supuesto, ignorar wantarray y devolver una lista de todas formas. Si es así, solo se devolverá el último elemento de la lista.

El valor devuelto por la función call_* indica cuántos elementos se han devuelto de la subrutina de Perl; en este caso, será 0 o 1.

Si es 0, entonces ha especificado el flag G_DISCARD.

Si es 1, entonces el elemento devuelto por la subrutina de Perl se almacenará en la pila de Perl; la sección "Devolver un escalar" muestra cómo acceder a este valor en la pila. Recuerde que independientemente de cuántos elementos devuelva la subrutina de Perl, solo el último será accesible desde la pila; piense en el caso en que solo se devuelve un valor como una lista con un solo elemento. Cualquier otro elemento que se haya devuelto no existirá cuando el control regrese de la función call_*. La sección "Devolver una lista en contexto escalar" muestra un ejemplo de este comportamiento.

G_LIST

Llama a la subrutina de Perl en un contexto de lista. Antes de la versión 5.35.1 de Perl, esto se llamaba "G_ARRAY".

Al igual que con G_SCALAR, este flag tiene 2 efectos:

1.
Indica a la subrutina que se está llamando que se está ejecutando en un contexto de lista (si ejecuta wantarray, el resultado será verdadero).
2.
Asegura que todos los elementos devueltos por la subrutina serán accesibles cuando el control regrese de la función call_*.

El valor devuelto por la función call_* indica cuántos elementos se han devuelto de la subrutina de Perl.

Flags

The call_* functions can be modified using a variety of flags. All flags are defined in the EXTERN.h header file.

G_SCALAR

This flag indicates that the Perl subroutine is expected to return a single scalar value. This value will be placed on the top of the Perl stack.

If the subroutine returns multiple values, only the first one will be placed on the stack. If the subroutine returns no values, then undef will be placed on the stack.

The section "Returning a Scalar" gives an example of using the G_SCALAR flag.

G_LIST

This flag indicates that the Perl subroutine is expected to return a list of values. These values will be pushed onto the Perl stack.

The number of items returned by the subroutine will be counted. These items will be stored on the Perl stack. The section "Returning a List of Values" gives an example of using the G_LIST flag and the mechanics of accessing the returned items from the Perl stack.

G_DISCARD

By default, the call_* functions place the items returned from by the Perl subroutine on the stack. If you are not interested in these items, then setting this flag will make Perl get rid of them automatically for you. Note that it is still possible to indicate a context to the Perl subroutine by using either G_SCALAR or G_LIST.

If you do not set this flag then it is very important that you make sure that any temporaries (i.e., parameters passed to the Perl subroutine and values returned from the subroutine) are disposed of yourself. The section "Returning a Scalar" gives details of how to dispose of these temporaries explicitly and the section "Using Perl to Dispose of Temporaries" discusses the specific circumstances where you can ignore the problem and let Perl deal with it for you.

G_NOARGS

Whenever a Perl subroutine is called using one of the call_* functions, it is assumed by default that parameters are to be passed to the subroutine. If you are not passing any parameters to the Perl subroutine, you can save a bit of time by setting this flag. It has the effect of not creating the @_ array for the Perl subroutine.

Although the functionality provided by this flag may seem straightforward, it should be used only if there is a good reason to do so. The reason for being cautious is that, even if you have specified the G_NOARGS flag, it is still possible for the Perl subroutine that has been called to think that you have passed it parameters.

In fact, what can happen is that the Perl subroutine you have called can access the @_ array from a previous Perl subroutine. This will occur when the code that is executing the call_* function has itself been called from another Perl subroutine. The code below illustrates this

sub fred
  { print "@_\n"  }
sub joe
  { &fred }
&joe(1,2,3);

This will print

1 2 3

What has happened is that "fred" accesses the @_ array which belongs to "joe".

G_EVAL

It is possible for the Perl subroutine you are calling to terminate abnormally, e.g., by calling die explicitly or by not actually existing. By default, when either of these events occurs, the process will terminate immediately. If you want to trap this type of event, specify the G_EVAL flag. It will put an eval { } around the subroutine call.

Whenever control returns from the call_* function you need to check the $@ variable as you would in a normal Perl script.

The value returned from the call_* function is dependent on what other flags have been specified and whether an error has occurred. Here are all the different cases that can occur:

  • If the call_* function returns normally, then the value returned is as specified in the previous sections.
  • If G_DISCARD is specified, the return value will always be 0.
  • If G_LIST is specified and an error has occurred, the return value will always be 0.
  • If G_SCALAR is specified and an error has occurred, the return value will be 1 and the value on the top of the stack will be undef. This means that if you have already detected the error by checking $@ and you want the program to continue, you must remember to pop the undef from the stack.

See "Using G_EVAL" for details on using G_EVAL.

G_KEEPERR

Using the G_EVAL flag described above will always set $@: clearing it if there was no error, and setting it to describe the error if there was an error in the called code. This is what you want if your intention is to handle possible errors, but sometimes you just want to trap errors and stop them interfering with the rest of the program.

This scenario will mostly be applicable to code that is meant to be called from within destructors, asynchronous callbacks, and signal handlers. In such situations, where the code being called has little relation to the surrounding dynamic context, the main program needs to be insulated from errors in the called code, even if they can't be handled intelligently. It may also be useful to do this with code for "__DIE__" or "__WARN__" hooks, and "tie" functions.

The G_KEEPERR flag is meant to be used in conjunction with G_EVAL in call_* functions that are used to implement such code, or with "eval_sv". This flag has no effect on the "call_*" functions when G_EVAL is not used.

When G_KEEPERR is used, any error in the called code will terminate the call as usual, and the error will not propagate beyond the call (as usual for G_EVAL), but it will not go into $@. Instead the error will be converted into a warning, prefixed with the string "\t(in cleanup)". This can be disabled using "no warnings 'misc'". If there is no error, $@ will not be cleared.

Note that the G_KEEPERR flag does not propagate into inner evals; these may still set $@.

The G_KEEPERR flag was introduced in Perl version 5.002.

See "Using G_KEEPERR" for an example of a situation that warrants the use of this flag.

Determining the Context

As mentioned above, you can determine the context of the currently executing subroutine in Perl with wantarray. The equivalent test can be made in C by using the "GIMME_V" macro, which returns "G_LIST" if you have been called in a list context, "G_SCALAR" if in a scalar context, or "G_VOID" if in a void context (i.e., the return value will not be used). A deprecated older version of this macro is called "GIMME"; in a void context it returns "G_SCALAR" instead of "G_VOID". An example of using the "GIMME_V" macro is shown in section "Using GIMME_V".

EXAMPLES

Enough of the definition talk! Let's have a few examples.

Perl provides many macros to assist in accessing the Perl stack. Wherever possible, these macros should always be used when interfacing to Perl internals. We hope this should make the code less vulnerable to any changes made to Perl in the future.

Another point worth noting is that in the first series of examples I have made use of only the call_pv function. This has been done to keep the code simpler and ease you into the topic. Wherever possible, if the choice is between using call_pv and call_sv, you should always try to use call_sv. See "Using call_sv" for details.

No Parameters, Nothing Returned

This first trivial example will call a Perl subroutine, PrintUID, to print out the UID of the process.

sub PrintUID
{
    print "UID is $<\n";
}

and here is a C function to call it

static void
call_PrintUID()
{
    dSP;
    PUSHMARK(SP);
    call_pv("PrintUID", G_DISCARD|G_NOARGS);
}

Simple, eh?

A few points to note about this example:

1.
Ignore "dSP" and PUSHMARK(SP) for now. They will be discussed in the next example.
2.
We aren't passing any parameters to PrintUID so G_NOARGS can be specified.
3.
We aren't interested in anything returned from PrintUID, so G_DISCARD is specified. Even if PrintUID was changed to return some value(s), having specified G_DISCARD will mean that they will be wiped by the time control returns from call_pv.
4.
As call_pv is being used, the Perl subroutine is specified as a C string. In this case the subroutine name has been 'hard-wired' into the code.
5.
Because we specified G_DISCARD, it is not necessary to check the value returned from call_pv. It will always be 0.

Passing Parameters

Now let's make a slightly more complex example. This time we want to call a Perl subroutine, "LeftString", which will take 2 parameters--a string ($s) and an integer ($n). The subroutine will simply print the first $n characters of the string.

So the Perl subroutine would look like this:

sub LeftString
{
    my($s, $n) = @_;
    print substr($s, 0, $n), "\n";
}

The C function required to call LeftString would look like this:

static void
call_LeftString(a, b)
char * a;
int b;
{
    dSP;
    ENTER;
    SAVETMPS;
    PUSHMARK(SP);
    EXTEND(SP, 2);
    PUSHs(sv_2mortal(newSVpv(a, 0)));
    PUSHs(sv_2mortal(newSViv(b)));
    PUTBACK;
    call_pv("LeftString", G_DISCARD);
    FREETMPS;
    LEAVE;
}

Here are a few notes on the C function call_LeftString.

1.
Parameters are passed to the Perl subroutine using the Perl stack. This is the purpose of the code beginning with the line "dSP" and ending with the line "PUTBACK". The "dSP" declares a local copy of the stack pointer. This local copy should always be accessed as "SP".

Llamar a subrutinas de Perl

Hay dos maneras básicas de llamar a una subrutina de Perl desde un código C o C++:

  • Llamar directamente a una subrutina específica (por ejemplo, Adder).

  • Llamar a una subrutina por su nombre como una cadena (por ejemplo, call_pv("Adder", G_SCALAR)).

Este último enfoque es mucho más flexible, ya que significa que puede decidir qué subrutina llamar en tiempo de ejecución, por ejemplo, basándose en una entrada del usuario. Por esta razón, nos centraremos principalmente en esta segunda forma de llamar a las subrutinas de Perl.

La forma más sencilla de llamar a una subrutina es utilizando la función call_pv. Hay una serie de otras funciones disponibles, pero call_pv es la más común.

Para la mayoría de las llamadas, se utilizará la pila de Perl. Por lo tanto, es esencial comprender cómo funciona la pila de Perl y cómo manipularla. Por suerte, hay una serie de macros disponibles para hacer esto por usted. Si no está familiarizado con el uso de macros C, puede pensar en ellas como abreviaturas de fragmentos de código C.

A continuación, se explica cómo llamar a una subrutina de Perl que no toma ni devuelve ningún valor.

    perl_call_pv("LeftString", G_DISCARD);

¡Eso es todo! Tan simple como eso. Solo tiene que proporcionar el nombre de la subrutina como una cadena y cualquier indicador que desee. En este caso, G_DISCARD significa que estamos descartando cualquier valor que la subrutina de Perl pueda devolver.

Sin embargo, en el momento en que necesite pasar parámetros a la subrutina de Perl o recuperar un valor de ella, las cosas se vuelven un poco más complicadas. Esto se debe a que necesitamos manipular la pila de Perl y la forma en que se hace esto es una fuente común de errores para los principiantes.

Sin parámetros, sin retorno

Para empezar, veamos el ejemplo más simple que podemos:

sub LeftString { print "Hello World\n" }

Para llamar a esta subrutina desde C, tendríamos que escribir lo siguiente:

call_LeftString()
{
    perl_call_pv("LeftString", G_DISCARD);
}

En este caso, no hay nada más que añadir. Sin embargo, los ejemplos que siguen son más complejos y requieren una explicación más detallada de las macros utilizadas.

Empujar parámetros en la pila

Para poder pasar parámetros a una subrutina de Perl, necesitamos utilizar la pila de Perl. A continuación, se describen las macros que se utilizan para ello.

1.
dSP. Este macro se utiliza para declarar una copia local del puntero de pila de Perl. Es necesario porque manipula la pila de Perl y, por lo tanto, el puntero de pila global podría cambiar. Al declarar una copia local, podemos manipularla sin afectar a la pila global hasta que estemos listos para hacerlo.
2.
PUSHMARK. Este macro se utiliza para marcar el principio de una lista de parámetros que se van a pasar a una subrutina de Perl. Le dice a Perl que debe hacer una nota mental del puntero de pila actual. Esto es importante porque Perl utiliza esta marca para saber cuántos parámetros se han pasado a la subrutina.
3.
PUTBACK. Este macro se utiliza para restablecer el puntero de pila global a la copia local que hemos estado manipulando. Esto es necesario porque, de lo contrario, Perl no sabría dónde encontrar los parámetros que hemos empujado en la pila.
4.
call_pv. Como se mencionó anteriormente, esta función se utiliza para llamar a una subrutina de Perl. Se le pasa el nombre de la subrutina como una cadena y un conjunto de indicadores. En este caso, hemos utilizado G_VOID, que indica que no esperamos ningún valor de retorno de la subrutina.

A continuación, se muestra un ejemplo de cómo llamar a una subrutina de Perl que toma dos parámetros:

sub PrintArgs
{
    my($arg1, $arg2) = @_;
    print "Arg1: $arg1\n";
    print "Arg2: $arg2\n";
}

La función C para llamar a esto es la siguiente:

static void
call_PrintArgs(s1, s2)
char *s1;
char *s2;
{
    dSP;                // Declara un puntero de pila local
    ENTER;              // Crea un límite para las temporales
    SAVETMPS;           // Guarda el estado de las temporales
    PUSHMARK(SP);       // Marca el inicio de los parámetros
    EXTEND(SP, 2);      // Asegura que hay espacio para 2 elementos
    PUSHs(sv_2mortal(newSVpv(s1, 0))); // Empuja el primer argumento
    PUSHs(sv_2mortal(newSVpv(s2, 0))); // Empuja el segundo argumento
    PUTBACK;            // Restablece el puntero de pila global
    call_pv("PrintArgs", G_VOID); // Llama a la subrutina de Perl
    PUTBACK;            // Restablece el puntero de pila global de nuevo
    FREETMPS;           // Libera las temporales
    LEAVE;              // Restaura el estado anterior
}

Los puntos a tener en cuenta aquí son:

1.
dSP. Si va a poner algo en la pila de Perl, necesita saber dónde ponerlo. Este es el propósito de la macro "dSP": declara e inicializa una copia local del puntero de pila de Perl.

Todas las demás macros que se utilizarán en este ejemplo requieren que haya utilizado esta macro.

La excepción a esta regla es si está llamando a una subrutina de Perl directamente desde una función XSUB. En este caso, no es necesario usar explícitamente la macro "dSP"; se declarará para usted automáticamente.

2.
Cualquier parámetro que se vaya a empujar en la pila debe estar delimitado por las macros "PUSHMARK" y "PUTBACK". El propósito de estas dos macros, en este contexto, es contar automáticamente el número de parámetros que está empujando. Luego, cada vez que Perl crea el array @_ para la subrutina, sabe qué tamaño darle.

La macro "PUSHMARK" le dice a Perl que tome nota del puntero de pila actual. Incluso si no está pasando ningún parámetro (como en el ejemplo que se muestra en la sección "Sin parámetros, sin retorno"), aún debe llamar a la macro "PUSHMARK" antes de poder llamar a cualquiera de las funciones de tipo call_*; Perl todavía necesita saber que no hay parámetros.

La macro "PUTBACK" establece la copia global del puntero de pila para que sea la misma que nuestra copia local. Si no hiciéramos esto, call_pv no sabría dónde están los dos parámetros que hemos empujado; recuerde que hasta ahora toda la manipulación del puntero de pila que hemos hecho ha sido con nuestra copia local, no con la copia global.

3.
A continuación, llegamos a EXTEND y PUSHs. Aquí es donde los parámetros realmente se empujan en la pila. En este caso, estamos empujando una cadena y un entero.

Alternativamente, puede utilizar la macro XPUSHs(), que combina un "EXTEND(SP, 1)" y PUSHs(). Esto es menos eficiente si está empujando varios valores.

Consulte "XSUBs y la pila de argumentos" en perlguts para obtener detalles sobre cómo funcionan las macros PUSH.

4.
Debido a que creamos valores temporales (mediante llamadas a sv_2mortal()) tendremos que ordenar la pila de Perl y deshacernos de los SVs mortales.

Este es el propósito de

ENTER;
SAVETMPS;

al principio de la función, y

FREETMPS;
LEAVE;

al final. El par "ENTER"/"SAVETMPS" crea un límite para cualquier temporal que creemos. Esto significa que las temporales de las que nos desharemos se limitarán a aquellas que se crearon después de estas llamadas.

El par "FREETMPS"/"LEAVE" se deshace de cualquier valor devuelto por la subrutina de Perl (ver el siguiente ejemplo), además de que también volcará los SVs mortales que hemos creado. Tener "ENTER"/"SAVETMPS" al principio del código asegura que no se destruyan otros mortales.

Piense en estas macros como si funcionaran un poco como "{" y "}" en Perl para limitar el ámbito de las variables locales.

Consulte la sección "Uso de Perl para deshacerse de temporales" para obtener detalles sobre una alternativa al uso de estas macros.

5.
Finalmente, LeftString ahora puede ser llamado a través de la función call_pv. La única bandera especificada esta vez es G_DISCARD. Debido a que estamos pasando 2 parámetros a la subrutina de Perl esta vez, no hemos especificado G_NOARGS.

Devolviendo un escalar

Ahora, un ejemplo de cómo tratar con los elementos devueltos por una subrutina de Perl.

Aquí hay una subrutina de Perl, Adder, que toma 2 parámetros enteros y simplemente devuelve su suma.

sub Adder
{
    my($x, $y) = @_;
    $x + $y;
}

Debido a que ahora nos preocupa el valor de retorno de Adder, la función C requerida para llamarla es ahora un poco más compleja.

static void
call_Adder(a, b)
int a;
int b;
{
    dSP;
    int count;
    ENTER;
    SAVETMPS;
    PUSHMARK(SP);
    EXTEND(SP, 2);
    PUSHs(sv_2mortal(newSViv(a)));
    PUSHs(sv_2mortal(newSViv(b)));
    PUTBACK;
    count = call_pv("Adder", G_SCALAR);
    SPAGAIN;
    if (count != 1)
        croak("Big trouble\n");
    printf ("The sum of %d and %d is %d\n", a, b, POPi);
    PUTBACK;
    FREETMPS;
    LEAVE;
}

Los puntos a tener en cuenta esta vez son

1.
La única bandera especificada esta vez fue G_SCALAR. Eso significa que el array @_ se creará y que el valor devuelto por Adder todavía existirá después de la llamada a call_pv.
2.
El propósito de la macro "SPAGAIN" es refrescar la copia local del puntero de pila. Esto es necesario porque es posible que la memoria asignada a la pila de Perl se haya realocado durante la llamada a call_pv.

Si está utilizando el puntero de pila de Perl en su código, siempre debe actualizar la copia local usando SPAGAIN cada vez que utilice las funciones call_* o cualquier otra función interna de Perl.

3.
Aunque solo se esperaba que se devolviera un solo valor de Adder, sigue siendo una buena práctica comprobar el código de retorno de call_pv de todos modos.

Esperar un solo valor no es lo mismo que saber que habrá uno. Si alguien modificara Adder para devolver una lista y no comprobáramos esa posibilidad y tomáramos las medidas adecuadas, la pila de Perl terminaría en un estado inconsistente. Eso es algo que realmente no querrá que suceda nunca.

4.
La macro "POPi" se utiliza aquí para sacar el valor de retorno de la pila. En este caso, queríamos un entero, por lo que se utilizó "POPi".

Aquí está la lista completa de macros POP disponibles, junto con los tipos que devuelven.

POPs        SV
POPp        pointer (PV)
POPpbytex   pointer to bytes (PV)
POPn        double (NV)
POPi        integer (IV)
POPu        unsigned integer (UV)
POPl        long
POPul       unsigned long

Dado que estas macros tienen efectos secundarios, no las use como argumentos para macros que pueden evaluar sus argumentos varias veces, por ejemplo:

/* Bad idea, don't do this */
STRLEN len;
const char *s = SvPV(POPs, len);

En su lugar, use una temporal:

STRLEN len;
SV *sv = POPs;
const char *s = SvPV(sv, len);

o una macro que garantice que evaluará sus argumentos solo una vez:

STRLEN len;
const char *s = SvPVx(POPs, len);
5.
El "PUTBACK" final se utiliza para dejar la pila de Perl en un estado consistente antes de salir de la función. Esto es necesario porque cuando sacamos el valor de retorno de la pila con "POPi", solo actualizó nuestra copia local del puntero de pila. Recuerde, "PUTBACK" establece el puntero de pila global para que sea el mismo que nuestra copia local.

Devolviendo una lista de valores

Ahora, ampliemos el ejemplo anterior para devolver tanto la suma de los parámetros como la diferencia.

Aquí está la subrutina de Perl

sub AddSubtract
{
   my($x, $y) = @_;
   ($x+$y, $x-$y);
}

y esta es la función C

static void
call_AddSubtract(a, b)
int a;
int b;
{
    dSP;
    int count;
    ENTER;
    SAVETMPS;
    PUSHMARK(SP);
    EXTEND(SP, 2);
    PUSHs(sv_2mortal(newSViv(a)));
    PUSHs(sv_2mortal(newSViv(b)));
    PUTBACK;
    count = call_pv("AddSubtract", G_LIST);
    SPAGAIN;
    if (count != 2)
        croak("Big trouble\n");
    printf ("%d - %d = %d\n", a, b, POPi);
    printf ("%d + %d = %d\n", a, b, POPi);
    PUTBACK;
    FREETMPS;
    LEAVE;
}

Si call_AddSubtract se llama así

entonces esta es la salida

7 + 4 = 11

Notas

1.
Queríamos contexto de lista, así que se usó G_LIST.
2.
No sorprende que "POPi" se use dos veces esta vez porque estábamos recuperando 2 valores de la pila. Lo importante a notar es que al usar las macros "POP*", salen de la pila en orden inverso.

Devolviendo una lista en contexto escalar

sub PrintList

Usando call_method

Considera el siguiente código de Perl:

{
    package Mine;
    sub new
    {
        my($type) = shift;
        bless [@_]
    }
    sub Display
    {
        my ($self, $index) = @_;
        print "$index: $$self[$index]\n";
    }
    sub PrintID
    {
        my($class) = @_;
        print "This is Class $class version 1.0\n";
    }
}

Implementa una clase muy simple para administrar una matriz. Aparte del constructor, "new", declara métodos, uno estático y uno virtual. El método estático, "PrintID", imprime simplemente el nombre de la clase y un número de versión. El método virtual, "Display", imprime un solo elemento de la matriz. Aquí hay un ejemplo completo en Perl de cómo usarlo.

$x = Mine->new('red', 'green', 'blue');
$x->Display(1);
Mine->PrintID;

imprimirá

1: green
This is Class Mine version 1.0

Llamar a un método de Perl desde C es bastante sencillo. Se requieren las siguientes cosas:

  • Una referencia al objeto para un método virtual o el nombre de la clase para un método estático
  • El nombre del método
  • Cualquier otro parámetro específico del método

Aquí hay un XSUB simple que ilustra la mecánica de llamar tanto al método "PrintID" como al método "Display" desde C.

void
call_Method(ref, method, index)
    SV *    ref
    char *  method
    int             index
    CODE:
    PUSHMARK(SP);
    EXTEND(SP, 2);
    PUSHs(ref);
    PUSHs(sv_2mortal(newSViv(index)));
    PUTBACK;
    call_method(method, G_DISCARD);
void
call_PrintID(class, method)
    char *  class
    char *  method
    CODE:
    PUSHMARK(SP);
    XPUSHs(sv_2mortal(newSVpv(class, 0)));
    PUTBACK;
    call_method(method, G_DISCARD);

Por lo tanto, los métodos "PrintID" y "Display" se pueden invocar de la siguiente manera:

$x = Mine->new('red', 'green', 'blue');
call_Method($x, 'Display', 1);
call_PrintID('Mine', 'PrintID');

Lo único a tener en cuenta es que, tanto en los métodos estáticos como en los virtuales, el nombre del método no se pasa a través de la pila, sino que se utiliza como primer parámetro para call_method.

Usando Perl para desechar temporales

En los ejemplos presentados hasta la fecha, cualquier temporal creado en la devolución de llamada (es decir, parámetros pasados en la pila a la función call_* o valores devueltos a través de la pila) se ha liberado mediante uno de estos métodos:

  • Especificando la bandera G_DISCARD con call_*
  • Usando explícitamente el par "ENTER"/"SAVETMPS"--"FREETMPS"/"LEAVE"

Hay otro método que se puede usar, que es dejar que Perl lo haga automáticamente cada vez que recupera el control después de que la devolución de llamada haya terminado. Esto se hace simplemente no usando la secuencia

ENTER;
SAVETMPS;
...
FREETMPS;
LEAVE;

en la devolución de llamada (y, por supuesto, no especificando la bandera G_DISCARD).

Si va a utilizar este método, debe ser consciente de una posible fuga de memoria que puede surgir en circunstancias muy específicas. Para explicar estas circunstancias, necesita saber un poco sobre el flujo de control entre Perl y la rutina de devolución de llamada.

Los ejemplos dados al principio del documento (un manejador de errores y un programa dirigido por eventos) son típicos de los dos tipos principales de flujo de control que es probable que encuentre con las devoluciones de llamada. Hay una distinción muy importante entre ellos, así que preste atención.

En el primer ejemplo, un manejador de errores, el flujo de control podría ser el siguiente. Ha creado una interfaz a una biblioteca externa. El control puede llegar a la biblioteca externa de esta manera

perl --> XSUB --> biblioteca externa

Mientras el control está en la biblioteca, ocurre una condición de error. Ha configurado previamente una devolución de llamada de Perl para manejar esta situación, por lo que se ejecutará. Una vez que la devolución de llamada haya terminado, el control volverá a Perl nuevamente. Aquí está cómo será el flujo de control en esa situación

perl --> XSUB --> biblioteca externa
                  ...
                  ocurre un error
                  ...
                  biblioteca externa --> call_* --> perl
                                                      |
perl <-- XSUB <-- biblioteca externa <-- call_* <----+

Después de que se completa el procesamiento del error utilizando call_*, el control vuelve a Perl casi inmediatamente.

En el diagrama, cuanto más a la derecha vaya, más anidado estará el ámbito. Solo cuando el control regresa a perl en el extremo izquierdo del diagrama habrá vuelto al ámbito envolvente y se liberarán los temporales que haya dejado.

En el segundo ejemplo, un programa dirigido por eventos, el flujo de control será más o menos así

perl --> XSUB --> manejador de eventos
                  ...
                  manejador de eventos --> call_* --> perl
                                                   |
                  manejador de eventos <-- call_* <----+
                  ...
                  manejador de eventos --> call_* --> perl
                                                   |
                  manejador de eventos <-- call_* <----+
                  ...
                  manejador de eventos --> call_* --> perl
                                                   |
                  manejador de eventos <-- call_* <----+

En este caso, el flujo de control puede consistir solo en la secuencia repetida

manejador de eventos --> call_* --> perl

durante prácticamente toda la duración del programa. Esto significa que el control puede nunca volver al ámbito circundante en Perl en el extremo izquierdo.

Entonces, ¿cuál es el gran problema? Bueno, si espera que Perl se encargue de esos temporales, podría tener una larga espera. Para que Perl deseche sus temporales, el control debe volver al ámbito envolvente en algún momento. En el escenario dirigido por eventos, eso puede que nunca suceda. Esto significa que, con el tiempo, su programa creará más y más temporales, ninguno de los cuales será liberado jamás. Como cada uno de estos temporales consume algo de memoria, su programa eventualmente consumirá toda la memoria disponible en su sistema. ¡Boom!

Así que esta es la conclusión: si está seguro de que el control volverá al ámbito de Perl circundante con bastante rapidez después del final de su devolución de llamada, entonces no es absolutamente necesario desechar explícitamente ningún temporal que pueda haber creado. Sin embargo, si tiene alguna duda sobre qué hacer, no hace daño arreglar las cosas de todos modos.

Estrategias para almacenar información de contexto de devolución de llamada

Potencialmente, uno de los problemas más difíciles de superar al diseñar una interfaz de devolución de llamada puede ser descubrir cómo almacenar el mapeo entre la función de devolución de llamada C y su equivalente en Perl.

Para ayudar a comprender por qué esto puede ser un problema real, primero considere cómo se configura una devolución de llamada en un entorno totalmente C. Típicamente, una API C proporcionará una función para registrar una devolución de llamada. Esta esperará un puntero a una función como uno de sus parámetros. A continuación se muestra una llamada a una función hipotética "register_fatal" que registra la función C que se llamará cuando ocurra un error fatal.

register_fatal(cb1);

El único parámetro "cb1" es un puntero a una función, por lo que debe haber definido "cb1" en su código, digamos algo como esto

static void
cb1()
{
    printf ("Fatal Error\n");
    exit(1);
}

Ahora cambie eso para llamar a una subrutina de Perl en su lugar

static SV * callback = (SV*)NULL;
static void
cb1()
{
    dSP;
    PUSHMARK(SP);
    /* Call the Perl sub to process the callback */
    call_sv(callback, G_DISCARD);
}
void
register_fatal(fn)
    SV *    fn
    CODE:
    /* Remember the Perl sub */
    if (callback == (SV*)NULL)
        callback = newSVsv(fn);
    else
        SvSetSV(callback, fn);
    /* register the callback with the external library */
    register_fatal(cb1);

donde el equivalente en Perl de "register_fatal" y la devolución de llamada que registra, "pcb1", podrían verse así

# Register the sub pcb1
register_fatal(\&pcb1);
sub pcb1
{
    die "I'm dying...\n";
}

Manejo de Callbacks

Esto será suficiente si alguna vez necesita tener solo un callback registrado en cualquier momento. Un ejemplo podría ser un manejador de errores como el código esbozado anteriormente. Recuerde, sin embargo, que las llamadas repetidas a "register_fatal" reemplazarán la función de callback registrada previamente con la nueva.

Supongamos, por ejemplo, que desea interactuar con una biblioteca que permite E/S de archivos asíncrona. En este caso, es posible que pueda registrar un callback cada vez que una operación de lectura se haya completado. Para que sea útil, queremos poder llamar a subrutinas de Perl separadas para cada archivo que se abre. Tal como está, el ejemplo del manejador de errores anterior no sería suficiente, ya que permite definir solo un callback a la vez. Lo que requerimos es un medio para almacenar el mapeo entre el archivo abierto y la subrutina de Perl que queremos que se llame para ese archivo.

Supongamos que la biblioteca de E/S tiene una función "asynch_read" que asocia una función C "ProcessRead" con un manejador de archivos "fh"; esto asume que también ha proporcionado alguna rutina para abrir el archivo y obtener así el manejador de archivos.

asynch_read(fh, ProcessRead)

Esto puede esperar que la función C *ProcessRead* tenga esta forma:

void
ProcessRead(fh, buffer)
int fh;
char *      buffer;
{
     ...
}

Para proporcionar una interfaz de Perl a esta biblioteca, necesitamos poder mapear entre el parámetro "fh" y la subrutina de Perl que queremos llamar. Un hash es un mecanismo conveniente para almacenar este mapeo. El siguiente código muestra una implementación posible:

static HV * Mapping = (HV*)NULL;
void
asynch_read(fh, callback)
    int     fh
    SV *    callback
    CODE:
    /* Si el hash aún no existe, créalo */
    if (Mapping == (HV*)NULL)
        Mapping = newHV();
    /* Guarda el mapeo fh -> callback */
    hv_store(Mapping, (char*)&fh, sizeof(fh), newSVsv(callback), 0);
    /* Registra con la Biblioteca C */
    asynch_read(fh, asynch_read_if);

y "asynch_read_if" podría verse así:

static void
asynch_read_if(fh, buffer)
int fh;
char *      buffer;
{
    dSP;
    SV ** sv;
    /* Obtiene el callback asociado con fh */
    sv =  hv_fetch(Mapping, (char*)&fh , sizeof(fh), FALSE);
    if (sv == (SV**)NULL)
        croak("Error interno...\n");
    PUSHMARK(SP);
    EXTEND(SP, 2);
    PUSHs(sv_2mortal(newSViv(fh)));
    PUSHs(sv_2mortal(newSVpv(buffer, 0)));
    PUTBACK;
    /* Llama a la subrutina de Perl */
    call_sv(*sv, G_DISCARD);
}

Para completar, aquí está "asynch_close". Esto muestra cómo eliminar la entrada del hash "Mapping".

void
asynch_close(fh)
    int     fh
    CODE:
    /* Elimina la entrada del hash */
    (void) hv_delete(Mapping, (char*)&fh, sizeof(fh), G_DISCARD);
    /* Ahora llama al asynch_close real */
    asynch_close(fh);

Así que la interfaz de Perl se vería así:

sub callback1
{
    my($handle, $buffer) = @_;
}
# Registra el callback de Perl
asynch_read($fh, \&callback1);
asynch_close($fh);

El mapeo entre el callback C y Perl se almacena en el hash global "Mapping" esta vez. Usar un hash tiene la ventaja distintiva de que permite registrar un número ilimitado de callbacks.

¿Qué pasa si la interfaz proporcionada por el callback C no contiene un parámetro que permita el mapeo del manejador de archivos a la subrutina de Perl? Digamos que en el paquete de E/S asíncrona, la función de callback solo recibe el parámetro "buffer" de esta manera:

void
ProcessRead(buffer)
char *      buffer;
{
    ...
}

Sin el manejador de archivos, no hay una forma sencilla de mapear desde el callback C a la subrutina de Perl.

En este caso, una forma posible de solucionar este problema es predefinir una serie de funciones C para que actúen como interfaz a Perl, así:

#define MAX_CB              3
#define NULL_HANDLE -1
typedef void (*FnMap)();
struct MapStruct {
    FnMap    Function;
    SV *     PerlSub;
    int      Handle;
  };
static void  fn1();
static void  fn2();
static void  fn3();
static struct MapStruct Map [MAX_CB] =
    {
        { fn1, NULL, NULL_HANDLE },
        { fn2, NULL, NULL_HANDLE },
        { fn3, NULL, NULL_HANDLE }
    };
static void
Pcb(index, buffer)
int index;
char * buffer;
{
    dSP;
    PUSHMARK(SP);
    XPUSHs(sv_2mortal(newSVpv(buffer, 0)));
    PUTBACK;
    /* Llama a la subrutina de Perl */
    call_sv(Map[index].PerlSub, G_DISCARD);
}
static void
fn1(buffer)
char * buffer;
{
    Pcb(0, buffer);
}
static void
fn2(buffer)
char * buffer;
{
    Pcb(1, buffer);
}
static void
fn3(buffer)
char * buffer;
{
    Pcb(2, buffer);
}
void
array_asynch_read(fh, callback)
    int             fh
    SV *    callback
    CODE:
    int index;
    int null_index = MAX_CB;
    /* Encuentra el mismo manejador o una entrada vacía */
    for (index = 0; index < MAX_CB; ++index)
    {
        if (Map[index].Handle == fh)
            break;
        if (Map[index].Handle == NULL_HANDLE)
            null_index = index;
    }
    if (index == MAX_CB && null_index == MAX_CB)
        croak ("Demasiadas funciones de callback registradas\n");
    if (index == MAX_CB)
        index = null_index;
    /* Guarda el manejador de archivos */
    Map[index].Handle = fh;
    /* Recuerda la subrutina de Perl */
    if (Map[index].PerlSub == (SV*)NULL)
        Map[index].PerlSub = newSVsv(callback);
    else
        SvSetSV(Map[index].PerlSub, callback);
    asynch_read(fh, Map[index].Function);
void
array_asynch_close(fh)
    int     fh
    CODE:
    int index;
    /* Encuentra el manejador de archivos */
    for (index = 0; index < MAX_CB; ++ index)
        if (Map[index].Handle == fh)
            break;
    if (index == MAX_CB)
        croak ("no se pudo cerrar fh %d\n", fh);
    Map[index].Handle = NULL_HANDLE;
    SvREFCNT_dec(Map[index].PerlSub);
    Map[index].PerlSub = (SV*)NULL;
    asynch_close(fh);

En este caso, las funciones "fn1", "fn2" y "fn3" se utilizan para recordar la subrutina de Perl que se debe llamar. Cada una de las funciones contiene un índice separado codificado que se utiliza en la función "Pcb" para acceder a la matriz "Map" y llamar realmente a la subrutina de Perl.

Hay algunas desventajas obvias con esta técnica.

En primer lugar, el código es considerablemente más complejo que con el ejemplo anterior.

En segundo lugar, existe un límite codificado (en este caso 3) en el número de callbacks que pueden existir simultáneamente. La única forma de aumentar el límite es modificando el código para agregar más funciones y luego recompilar. Sin embargo, mientras el número de funciones se elija con cierto cuidado, sigue siendo una solución viable y en algunos casos es la única disponible.

Para resumir, aquí hay una serie de métodos posibles que puede considerar para almacenar el mapeo entre C y el callback de Perl:

1. Ignorar el problema - Permitir solo 1 callback
Para muchas situaciones, como la interacción con un manejador de errores, esta puede ser una solución perfectamente adecuada.
2. Crear una secuencia de callbacks - límite codificado
Si es imposible saber por los parámetros pasados desde el callback C cuál es el contexto, entonces puede que necesite crear una secuencia de funciones de interfaz de callback C y almacenar punteros a cada una en una matriz.
3. Usar un parámetro para mapear al callback de Perl
Un hash es un mecanismo ideal para almacenar el mapeo entre C y Perl.

Manipulación Alternativa de la Pila

Aunque solo he utilizado las macros "POP*" para acceder a los valores devueltos por las subrutinas de Perl, también es posible omitir estas macros y leer la pila usando la macro "ST" (ver perlxs para una descripción completa de la macro "ST").

La mayoría de las veces, las macros "POP*" deberían ser suficientes; el principal problema con ellas es que le obligan a procesar los valores devueltos en secuencia. Esta puede no ser la forma más adecuada de procesar los valores en algunos casos. Lo que queremos es poder acceder a la pila en orden aleatorio. La macro "ST", tal como se usa al codificar un XSUB, es ideal para este propósito.

El siguiente código es el ejemplo dado en la sección "Devolución de una lista de valores" recreado para usar "ST" en lugar de "POP*".

static void
call_AddSubtract2(a, b)
int a;
int b;
{
    dSP;
    I32 ax;
    int count;
    ENTER;
    SAVETMPS;
    PUSHMARK(SP);
    EXTEND(SP, 2);
    PUSHs(sv_2mortal(newSViv(a)));
    PUSHs(sv_2mortal(newSViv(b)));
    PUTBACK;
    count = call_pv("AddSubtract", G_LIST);
    SPAGAIN;
    SP -= count;
    ax = (SP - PL_stack_base) + 1;
    if (count != 2)
        croak("Gran problema\n");
    printf ("%d + %d = %d\n", a, b, SvIV(ST(0)));
    printf ("%d - %d = %d\n", a, b, SvIV(ST(1)));
    PUTBACK;
    FREETMPS;
    LEAVE;
}

Notas

1.
Observe que fue necesario definir la variable "ax". Esto se debe a que la macro "ST" espera que exista. Si estuviéramos en un XSUB, no sería necesario definir "ax" ya que ya está definido para nosotros.
2.
El código 
SPAGAIN;
SP -= count;
ax = (SP - PL_stack_base) + 1;

configura la pila para que podamos usar la macro "ST".

3.
A diferencia de la codificación original de este ejemplo, los valores devueltos no se acceden en orden inverso. Por lo tanto, ST(0) se refiere al primer valor devuelto por la subrutina de Perl y ST(count-1) se refiere al último.

NAME

perlcall — cómo llamar a subrutinas Perl desde C

DESCRIPTION

Este documento explica cómo llamar a subrutinas Perl desde código C. Para usar las funciones descritas aquí, necesitará incluir EXTERN.h en su código fuente C.

Las subrutinas Perl se invocan utilizando un puntero a una entrada de tabla de subrutinas (una tabla de subrutinas definida en el Tcl/Tk .c file for the extension) or a CV* (code visualization) that you've obtained by other means. The most common way to get a CV* is to use perl_get_cv().

A CV* is a pointer to a Perl subroutine. The Perl_call_sv() function takes a SV* argument, which can be a CV* or a reference to a subroutine. The Perl_call_pv() function takes a string name and looks up the subroutine in the current package.

The simplest function to use is Perl_call_pv(). It takes the name of the subroutine, and any arguments to be passed to it. The return value of the subroutine is returned as an SV*.

SV *
Perl_call_pv(aTHX_ const char *sv_name, I32die);

The sv_name argument is the name of the subroutine to call. The die argument is a flag that indicates whether to die if the subroutine does not exist. If die is non-zero, the call will die if the subroutine is not found. If die is zero, the call will return NULL if the subroutine is not found.

The arguments to the subroutine are pushed onto the Perl stack before the call. They are popped off after the call returns. The return value is left on top of the stack.

void
Perl_call_list(aTHX_ CV *cv, ...)
    /*@null@*/ /*@returns@*/ SV *;

The cv argument is a pointer to the subroutine to call. The remaining arguments are the arguments to be passed to the subroutine. The return value of the subroutine is returned as an SV*.

The arguments are passed as a variable-length argument list. The arguments must be pushed onto the Perl stack before calling Perl_call_list().

void
Perl_call_sv(aTHX_ SV *sv, I32die);

The sv argument is an SV* that refers to the subroutine to be called. It can be a CV* or a reference to a subroutine. The die argument is the same as for Perl_call_pv().

The arguments to the subroutine are pushed onto the Perl stack before the call. They are popped off after the call returns. The return value is left on top of the stack.

To pass arguments to the subroutine, you use the PUSHs() macro to push them onto the stack. The sv_2pv() function can be used to convert an SV* to a C string. The newSVpv() function can be used to create a new SV* from a C string.

SV *
perl_get_cv(aTHX_ const char *name, sigarg sig);

The name argument is the name of the subroutine to look up. The sig argument is the signature of the subroutine. This is usually PERL_IMPLICIT_CONTEXT. Returns a CV* representing the subroutine, or NULL if not found.

SV *
perl_get_sv(aTHX_ const char *name, sigarg sig);

Similar to perl_get_cv(), but looks up a scalar variable.

SV *
perl_get_av(aTHX_ const char *name, sigarg sig);

Similar to perl_get_cv(), but looks up an array variable.

SV *
perl_get_hv(aTHX_ const char *name, sigarg sig);

Similar to perl_get_cv(), but looks up a hash variable.

THE CALL FUNCTIONS

There are three main functions for calling Perl code from C:

  • Perl_call_pv(): Calls a subroutine by name.
  • Perl_call_sv(): Calls a subroutine given an SV* reference to it.
  • Perl_call_list(): Calls a subroutine given a CV* and a variable argument list.

These functions all operate on the Perl stack. Arguments are pushed onto the stack before the call, and the return value is left on the stack after the call.

FLAG VALUES

The die argument to Perl_call_pv() and Perl_call_sv() can be one of the following values:

  • G_VOID: Do not expect a return value.
  • G_SCALAR: Expect a single scalar return value.
  • G_LIST: Expect a list of return values.

If the subroutine does not exist and die is non-zero, the call will die.

EXAMPLES

Here are some examples of how to use the call functions:

Calling a subroutine with no arguments:

    Perl_call_pv(aTHX_ "my_sub", G_VOID);

Calling a subroutine with one scalar argument:

    PUSHs(sv_2mortal(newSVpv("hello", 0)));
    Perl_call_pv(aTHX_ "my_sub_with_arg", G_VOID);

Calling a subroutine and getting a scalar return value:

    PUSHs(sv_2mortal(newSViv(42)));
    SV *ret = Perl_call_pv(aTHX_ "my_sub_ret", G_SCALAR);
    if (ret && sv_isobject(ret) && sv_derived_from(ret, "Some::Class")) {
        /* It's an object of Some::Class */
    }

Calling a subroutine and getting a list return value:

    PUSHs(sv_2mortal(newSVpv("world", 0)));
    Perl_call_pv(aTHX_ "my_list_sub", G_LIST);
    /* Now the return values are on the stack */
    SV *third = POPs; /* if there were at least 3 */
    SV *second = POPs;
    SV *first = POPs;

Calling a subroutine using a CV* obtained from perl_get_cv():

    CV *cv = perl_get_cv(aTHX_ "my_sub", PERL_IMPLICIT_CONTEXT);
    if (cv) {
        PUSHs(sv_2mortal(newSViv(10)));
        PUSHs(sv_2mortal(newSViv(20)));
        SV *ret = Perl_call_list(aTHX_ cv, 3); /* 3 args */
        /* Process return value */
    }

It is also possible to call subs that are stored in scalar variables, using Perl_call_sv(). This is useful if you have obtained a reference to a subroutine from somewhere else, e.g. from another Perl subroutine.

    /* Assume 'ref_to_sub' is an SV* pointing to a subroutine reference */
    PUSHs(sv_2mortal(newSVpv("argument", 0)));
    SV *ret = Perl_call_sv(aTHX_ ref_to_sub, G_SCALAR);

To use a subroutine reference obtained from a previous call to perl_get_sv() (for example, if you fetch a subroutine from a hash):

    SV *sub_ref = perl_get_sv(aTHX_ "My::Package::HASH->{key}",
                                  PERL_IMPLICIT_CONTEXT);
    if (sub_ref && sv_isobject(sub_ref) && sv_derived_from(sub_ref, "CODE")) {
        PUSHs(sv_2mortal(newSVpv("some_data", 0)));
        SV* result = Perl_call_sv(aTHX, sub_ref, G_SCALAR);
        /* ... process result ... */
    }

If you have a code reference, you can also call it directly using the call_sv method on the SV itself. This is slightly more efficient than using the Perl_call_sv() function.

    /* Assume 'sub_ref' is an SV* pointing to a subroutine reference */
    PUSHs(sv_2mortal(newSVpv("argument", 0)));
    SV *ret = sub_ref->call_sv(aTHX_ G_SCALAR);

The perl_get_pv("eval_pv", TRUE) call retrieves the CV* for the built-in eval subroutine. Once you have this code reference, it can be mixed in with all the previous examples we've shown.

LIGHTWEIGHT CALLBACKS

Sometimes you need to invoke the same subroutine repeatedly. This usually happens with a function that acts on a list of values, such as Perl's built-in sort(). You can pass a comparison function to sort(), which will then be invoked for every pair of values that needs to be compared. The first() and reduce() functions from List::Util follow a similar pattern.

In this case it is possible to speed up the routine (often quite substantially) by using the lightweight callback API. The idea is that the calling context only needs to be created and destroyed once, and the sub can be called arbitrarily many times in between.

It is usual to pass parameters using global variables (typically $_ for one parameter, or $a and $b for two parameters) rather than via @_. (It is possible to use the @_ mechanism if you know what you're doing, though there is as yet no supported API for it. It's also inherently slower.)

The pattern of macro calls is like this:

dMULTICALL;                 /* Declare local variables */
U8 gimme = G_SCALAR;        /* context of the call: G_SCALAR,
                             * G_LIST, or G_VOID */
PUSH_MULTICALL(cv);         /* Set up the context for calling cv,
                               and set local vars appropriately */
/* loop */ {
    /* set the value(s) af your parameter variables */
    MULTICALL;              /* Make the actual call */
} /* end of loop */
POP_MULTICALL;              /* Tear down the calling context */

For some concrete examples, see the implementation of the first() and reduce() functions of List::Util 1.18. There you will also find a header file that emulates the multicall API on older versions of perl.
