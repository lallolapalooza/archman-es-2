Entrañas del Depurador

Perl tiene ganchos especiales de depuración en tiempo de compilación y en tiempo de ejecución utilizados para crear entornos de depuración. Estos ganchos no deben confundirse con el comando perl -Dxxx descrito en perlrun, que solo se puede usar si se compila una Perl especial según las instrucciones del archivo INSTALL en el árbol de fuentes de Perl.

Por ejemplo, cada vez que llamas a la función incorporada de Perl "caller" desde el paquete "DB", los argumentos con los que se llamó al marco de pila correspondiente se copian a la matriz @DB::args. Estos mecanismos se activan llamando a Perl con el modificador -d. Específicamente, se habilitan las siguientes características adicionales (cf. "$<^P>" en perlvar):

  • Perl inserta el contenido de $ENV{PERL5DB} (o "BEGIN {require 'perl5db.pl'}" si no está presente) antes de la primera línea de tu programa.
  • Si se proporciona el modificador "-dt", se establece "PERL5DB_THREADED=1" en el entorno. "perl5db.pl" o tu depurador personalizado pueden usar esto para habilitar el soporte de hilos.
  • Cada matriz "@{"_<$nombre_archivo"}" contiene las líneas de $nombre_archivo para un archivo compilado por Perl. Lo mismo ocurre con las cadenas "eval"uadas que contienen subrutinas, o que se están ejecutando actualmente. El $nombre_archivo para las cadenas "eval"uadas se ve como "(eval 34)".

    Los valores en esta matriz son mágicos en contexto numérico: comparan igual a cero solo si la línea no se puede interrumpir.

  • Cada hash "%{"_<$nombre_archivo"}" contiene puntos de interrupción y acciones indexados por número de línea. Las entradas individuales (en contraposición al hash completo) se pueden establecer. Perl solo se preocupa por el valor booleano verdadero aquí, aunque los valores utilizados por perl5db.pl tienen el formato "$condición_de_corte\0$acción".

    Lo mismo aplica para cadenas evaluadas que contienen subrutinas, o que se están ejecutando actualmente. El $nombre_archivo para las cadenas "eval"uadas se ve como "(eval 34)".

  • Cada escalar "${"_<$nombre_archivo"}" contiene $nombre_archivo. Este también es el caso de las cadenas evaluadas que contienen subrutinas, o que se están ejecutando actualmente. El $nombre_archivo para las cadenas "eval"uadas se ve como "(eval 34)".
  • Después de compilar cada archivo "require"d, pero antes de ejecutarlo, se llama a DB::postponed(*{"_<$nombre_archivo"}) si existe la subrutina "DB::postponed". Aquí, $nombre_archivo es el nombre expandido del archivo "require"d, como se encuentra en los valores de %INC.
  • Después de compilar cada subrutina "nombre_subrutina", se verifica la existencia de $DB::postponed{nombre_subrutina}. Si esta clave existe, se llama a DB::postponed(nombre_subrutina) si la subrutina "DB::postponed" también existe.
  • Se mantiene un hash %DB::sub, cuyas claves son nombres de subrutinas y cuyos valores tienen el formato "nombre_archivo:linea_inicio-linea_fin". "nombre_archivo" tiene el formato "(eval 34)" para subrutinas definidas dentro de "eval"s.
  • Cuando la ejecución de tu programa llega a un punto que puede contener un punto de interrupción, se llama a la subrutina DB::DB() si alguna de las variables $DB::trace, $DB::single, o $DB::signal es verdadera. Estas variables no son "local"izables. Esta característica se deshabilita al ejecutarse dentro de DB::DB(), incluidas las funciones llamadas desde ella a menos que "$<^P> & (1<<30)" sea verdadera.
  • Cuando la ejecución del programa llega a una llamada a subrutina, se hace una llamada a &DB::sub(argumentos) en su lugar, con $DB::sub establecido para identificar la subrutina llamada. (Esto no sucede si la subrutina llamadora fue compilada en el paquete "DB"). $DB::sub normalmente contiene el nombre de la subrutina llamada, si tiene un nombre por el cual se pueda buscar. De lo contrario, $DB::sub contendrá una referencia a la subrutina llamada. En cualquier caso, la subrutina &DB::sub puede usar $DB::sub como referencia para llamar a la subrutina llamada, lo cual normalmente querrá hacer.

    Si la llamada es a una subrutina lvalue, y &DB::lsub está definida, se llama a &DB::lsub(argumentos), de lo contrario se recurre a &DB::sub(argumentos).

  • Cuando la ejecución del programa utiliza "goto" para entrar en una subrutina que no es XS y el bit 0x80 está establecido en $^P, se realiza una llamada a &DB::goto, con $DB::sub establecido para identificar la subrutina que se está ingresando. La llamada a &DB::goto no reemplaza el "goto"; la subrutina solicitada aún se ingresará una vez que &DB::goto haya retornado. $DB::sub normalmente contiene el nombre de la subrutina que se está ingresando, si tiene uno. De lo contrario, $DB::sub contendrá una referencia a la subrutina que se está ingresando. A diferencia de cuando se llama a &DB::sub, no se garantiza que $DB::sub pueda usarse como referencia para operar sobre la subrutina que se está ingresando.

Tenga en cuenta que si &DB::sub necesita datos externos para funcionar, no es posible ninguna llamada a subrutina sin ellos. Como ejemplo, el depurador estándar &DB::sub depende de la variable $DB::deep (define cuántos niveles de recursión dentro del depurador puedes ir antes de un corte forzado). Si $DB::deep no está definida, no son posibles las llamadas a subrutinas, aunque exista &DB::sub.

Escribiendo tu Propio Depurador

Variables de Entorno

La variable de entorno "PERL5DB" puede usarse para definir un depurador. Por ejemplo, el depurador mínimo "funcional" (en realidad no hace nada) consta de una línea:

sub DB::DB {}

Se puede definir fácilmente así:

$ PERL5DB="sub DB::DB {}" perl -d tu-script

Otro depurador breve, ligeramente más útil, se puede crear solo con la línea:

sub DB::DB {print ++$i; scalar <STDIN>}

Este depurador imprime un número que se incrementa por cada declaración encontrada y espera a que presiones una nueva línea antes de continuar a la siguiente declaración.

El siguiente depurador es realmente útil:

{
  package DB;
  sub DB  {}
  sub sub {print ++$i, " $sub\n"; &$sub}
}

Imprime el número de secuencia de cada llamada a subrutina y el nombre de la subrutina llamada. Tenga en cuenta que &DB::sub se está compilando en el paquete "DB" mediante el uso de la directiva "package".

rc file

When it starts, the debugger reads your rc file (./.perldb or ~/.perldb under Unix), which can set important options. (A subroutine (&afterinit) can be defined here as well; it is executed after the debugger completes its own initialization.)

After the rc file is read, the debugger reads the PERLDB_OPTS environment variable and uses it to set debugger options. The contents of this variable are treated as if they were the argument of an "o ..." debugger command (q.v. in "Configurable Options" in perldebug).

Debugger Internal Variables

In addition to the file and subroutine-related variables mentioned above, the debugger also maintains various magical internal variables.

  • @DB::dbline is an alias for "@{"::_<current_file"}", which holds the lines of the currently-selected file (compiled by Perl), either explicitly chosen with the debugger's "f" command, or implicitly by flow of execution.

    Values in this array are magical in numeric context: they compare equal to zero only if the line is not breakable.

  • %DB::dbline is an alias for "%{"::_<current_file"}", which contains breakpoints and actions keyed by line number in the currently-selected file, either explicitly chosen with the debugger's "f" command, or implicitly by flow of execution.

    As previously noted, individual entries (as opposed to the whole hash) are settable. Perl only cares about Boolean true here, although the values used by perl5db.pl have the form "$break_condition\0$action".

Debugger Customization Functions

Some functions are provided to simplify customization.

  • See "Configurable Options" in perldebug for a description of options parsed by DB::parse_options(string).
  • "DB::dump_trace(skip[,count])" skips the specified number of frames and returns a list containing information about the calling frames (all of them, if "count" is missing). Each entry is reference to a hash with keys "context" (either ".", "$", or "@"), "sub" (subroutine name, or info about "eval"), "args" ("undef" or a reference to an array), "file", and "line".
  • "DB::print_trace(FH, skip[, count[, short]])" prints formatted info about caller frames. The last two functions may be convenient as arguments to "<", "<<" commands.

Note that any variables and functions that are not documented in this manpages (or in perldebug) are considered for internal use only, and as such are subject to change without notice.

Debugging Regular Expressions

There are two ways to enable debugging output for regular expressions.

If your perl is compiled with "-DDEBUGGING", you may use the -Dr flag on the command line, and "-Drv" for more verbose information.

Otherwise, one can "use re 'debug'", which has effects at both compile time and run time. Since Perl 5.9.5, this pragma is lexically scoped.

perldebguts - Internal details for the Perl debugger

DESCRIPCIÓN

This document describes the internals of the Perl debugger. Most of this is unlikely to be interesting to the average user. If you're trying to understand how the debugger works, this is the place to look.

The debugger is implemented as a package named "Perl::Debug". It is loaded by the main Perl interpreter when the "-d" command-line switch is used, or when the "use Perl::Debug" statement is encountered in the code. The debugger can also be loaded directly via "use Devel::Debugging".

When the debugger is loaded, it takes control of the interpreter. It uses Perl's low-level debugging hooks (see perlapi) to monitor the execution of the program. The user interacts with the debugger through a command interface, which is typically provided by the perl5db.pl(1) script.

Internos del depurador

The debugger works by intercepting Perl's execution at various points. These points are called 'debug hooks'. The main hooks are:

*OP_HOOK
Called before executing any basic operation (OP).
*LINE_HOOK
Called before executing a new line of source code.
*SUB_HOOK
Called before entering a subroutine.
*EVAL_HOOK
Called before executing an eval().
*THROTTLE_HOOK
Called at regular intervals to allow the debugger to update its UI or check for user input, even during long-running operations.

The debugger uses these hooks to implement features like stepping through code, setting breakpoints, inspecting variables, and evaluating expressions in the current context.

Ejemplos de salida de lista de fotogramas

When you list the call stack (e.g., using the "L" command in the debugger), you'll see output similar to this:

  DB<1> L
    0  DB::readline(SIZE=24) called from top level (./script.pl:5)
    1  main(SIZE=32) called from top level (./script.pl:10)
    2  DB::sv_FETCH(SIZE=40) called from DB::readline (./script.pl:6)

Each line represents a frame in the call stack. The information provided includes:

  • The frame number (starting from 0 for the current innermost frame).
  • The name of the subroutine or the context (e.g., 'top level').
  • The size of the arguments passed to the subroutine (in parentheses).
  • The location where the subroutine was called (file and line number).

Depuración de expresiones regulares

Perl provides extensive debugging capabilities for regular expressions. You can enable this by passing the "/r" flag to the "use re" pragma:

use re 'debug';

This will cause Perl to print detailed information about how each regular expression is matched, including:

  • The regex pattern being matched.
  • The string being searched.
  • The steps taken during the matching process.
  • Which alternatives were tried and which succeeded or failed.
  • Information about backtracking.

This can be incredibly helpful when trying to understand why a particular regex isn't behaving as expected.

The output of use re 'debug' can be quite verbose. You can control the level of detail by passing a numeric argument:

use re 'debug(1)'; # Default level
use re 'debug(0)'; # Less verbose
use re 'debug(16)'; # Even more verbose

You can also enable regex debugging from the command line:

perl -Dr my_script.pl

For more fine-grained control, you can use the $RegEnableDebug and $RegDisableDebug functions within your code.

Depuración del uso de memoria de Perl

Perl's memory usage can sometimes be a complex issue. Understanding how Perl allocates and manages memory is crucial for optimizing performance and preventing memory leaks.

A simple integer variable might take up more than 20 bytes of memory, a float cannot take less than 24 bytes, a string cannot take less than 32 bytes (all these examples assume 32-bit architectures, the results are quite a bit worse on 64-bit architectures). If a variable is accessed in two of three different ways (which require an integer, a float, or a string), the memory footprint may increase yet another 20 bytes. A sloppy malloc(3) implementation can inflate these numbers dramatically.

On the opposite end of the scale, a declaration like

sub foo;

may take up to 500 bytes of memory, depending on which release of Perl you're running.

Anecdotal estimates of source-to-compiled code bloat suggest an eightfold increase. This means that the compiled form of reasonable (normally commented, properly indented etc.) code will take about eight times more space in memory than the code took on disk.

The -DL command-line switch is obsolete since circa Perl 5.6.0 (it was available only if Perl was built with "-DDEBUGGING"). The switch was used to track Perl's memory allocations and possible memory leaks. These days the use of malloc debugging tools like Purify or valgrind is suggested instead. See also "PERL_MEM_LOG" in perlhacktips(1).

One way to find out how much memory is being used by Perl data structures is to install the Devel::Size module from CPAN: it gives you the minimum number of bytes required to store a particular data structure. Please be mindful of the difference between the size() and total_size().

If Perl has been compiled using Perl's malloc you can analyze Perl memory usage by setting $ENV{PERL_DEBUG_MSTATS}.

Uso de $ENV{PERL_DEBUG_MSTATS}

If your perl is using Perl's malloc() and was compiled with the necessary switches (this is the default), then it will print memory usage statistics after compiling your code when "$ENV{PERL_DEBUG_MSTATS} > 1", and before termination of the program when "$ENV{PERL_DEBUG_MSTATS} >= 1". The report format is similar to the following example:

$ PERL_DEBUG_MSTATS=2 perl -e "require Carp"
Memory allocation statistics after compilation: (buckets 4(4)..8188(8192)
   14216 free:   130   117    28     7     9   0   2     2   1 0 0
               437    61    36     0     5
   60924 used:   125   137   161    55     7   8   6    16   2 0 1
                74   109   304    84    20
Total sbrk(): 77824/21:119. Odd ends: pad+heads+chain+tail: 0+636+0+2048.
Memory allocation statistics after execution:   (buckets 4(4)..8188(8192)
   30888 free:   245    78    85    13     6   2   1     3   2 0 1
               315   162    39    42    11
  175816 used:   265   176  1112   111    26  22  11    27   2 1 1
               196   178  1066   798    39
Total sbrk(): 215040/47:145. Odd ends: pad+heads+chain+tail: 0+2192+0+6144.

It is possible to ask for such a statistic at arbitrary points in your execution using the mstat() function out of the standard Devel::Peek module.

Here is some explanation of that format:

"buckets SMALLEST(APPROX)..GREATEST(APPROX)"
Perl's malloc() uses bucketed allocations. Every request is rounded up to the closest bucket size available, and a bucket is taken from the pool of buckets of that size.

The line above describes the limits of buckets currently in use. Each bucket has two sizes: memory footprint and the maximal size of user data that can fit into this bucket. Suppose in the above example that the smallest bucket were size 4. The biggest bucket would have usable size 8188, and the memory footprint would be 8192.

In a Perl built for debugging, some buckets may have negative usable size. This means that these buckets cannot (and will not) be used. For larger buckets, the memory footprint may be one page greater than a power of 2. If so, the corresponding power of two is printed in the "APPROX" field above.

Libre/Usado
The 1 or 2 rows of numbers following that correspond to the number of buckets of each size between "SMALLEST" and "GREATEST". In the first row, the sizes (memory footprints) of buckets are powers of two--or possibly one page greater. In the second row, if present, the memory footprints of the buckets are between the memory footprints of two buckets "above".

For example, suppose under the previous example, the memory footprints were

free:    8     16    32    64    128  256 512 1024 2048 4096 8192
        4     12    24    48    80

With a non-"DEBUGGING" perl, the buckets starting from 128 have a 4-byte overhead, and thus an 8192-long bucket may take up to 8188-byte allocations.

"Total sbrk(): SBRKed/SBRKs:CONTINUOUS"
The first two fields give the total amount of memory perl sbrk(2)ed (ess-broken? :-) and number of sbrk(2)s used. The third number is what perl thinks about continuity of returned chunks. So long as this number is positive, malloc() will assume that it is probable that sbrk(2) will provide continuous memory.

Memory allocated by external libraries is not counted.

"pad: 0"
The amount of sbrk(2)ed memory needed to keep buckets aligned.
"heads: 2192"
Although memory overhead of bigger buckets is kept inside the bucket, for smaller buckets, it is kept in separate areas. This field gives the total size of these areas.
"chain: 0"
malloc() may want to subdivide a bigger bucket into smaller buckets. If only a part of the deceased bucket is left unsubdivided, the rest is kept as an element of a linked list. This field gives the total size of these chunks.
"tail: 6144"
To minimize the number of sbrk(2)s, malloc() asks for more memory. This field gives the size of the yet unused part, which is sbrk(2)ed, but never touched.
