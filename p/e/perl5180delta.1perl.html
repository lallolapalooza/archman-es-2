NOMBRE

perl5180delta - Novedades de la versión v5.18.0 de perl

DESCRIPCIÓN

Este documento describe las diferencias entre la versión v5.16.0 y la versión v5.18.0.

Si estás actualizando desde una versión anterior como la v5.14.0, primero lee perl5160delta, que describe las diferencias entre v5.14.0 y v5.16.0.

Mejoras del núcleo

Nuevo mecanismo para funciones experimentales

Las funciones experimentales recién añadidas requerirán ahora esta incantación:

no warnings "experimental::nombre_funcion";
use feature "nombre_funcion";  # advertiría sin la línea anterior

Hay una nueva categoría de advertencias, llamada "experimental", que contiene las advertencias que emite el pragma feature al habilitar funciones experimentales.

Las funciones experimentales recién añadidas también recibirán IDs de advertencia especiales, que consisten en "experimental::" seguido del nombre de la función. (El plan es extender este mecanismo eventualmente a todas las advertencias, para permitir que se habiliten o deshabiliten individualmente, y no solo por categoría).

Al decir

no warnings "experimental::nombre_funcion";

asumes la responsabilidad de cualquier interrupción que los cambios futuros en la función, o su eliminación, puedan causar.

Dado que algunas funciones (como "~~" o "my $_") ahora emiten advertencias experimentales, y es posible que desees deshabilitarlas en código que también se ejecuta en versiones de perl que no reconocen estas categorías de advertencia, considera usar el pragma "if" de la siguiente manera:

no if $] >= 5.018, warnings => "experimental::nombre_funcion";

Las funciones experimentales existentes también pueden comenzar a emitir estas advertencias. Consulta perlexperiment para obtener información sobre qué funciones se consideran experimentales.

Revisión de hashes

Los cambios en la implementación de los hashes en la versión v5.18.0 de Perl serán uno de los cambios más visibles en el comportamiento del código existente.

Por defecto, dos variables de hash distintas con claves y valores idénticos ahora pueden proporcionar su contenido en un orden diferente donde anteriormente era idéntico.

Al encontrarte con estos cambios, la clave para limpiar a partir de ellos es aceptar que los hashes son colecciones desordenadas y actuar en consecuencia.

Aleatorización de hashes

La semilla utilizada por la función hash de Perl ahora es aleatoria. Esto significa que el orden en que las claves/valores se devolverán de funciones como keys(), values() y each() diferirá de una ejecución a otra.

Este cambio se introdujo para hacer que los hashes de Perl sean más resistentes a ataques de complejidad algorítmica, y también porque descubrimos que expone errores de dependencia del orden de los hashes y los hace más fáciles de rastrear.

Los mantenedores de herramientas podrían querer invertir en infraestructura adicional para probar este tipo de cosas. Ejecutar las pruebas varias veces seguidas y luego comparar los resultados facilitará la detección de dependencias del orden de los hashes en el código. Se recomienda encarecidamente a los autores que no expongan el orden de las claves de los hashes de Perl a audiencias inseguras.

Además, cada hash tiene su propio orden de iteración, lo que debería hacer mucho más difícil determinar cuál es la semilla hash actual.

Nuevas funciones hash

Perl v5.18 incluye soporte para múltiples funciones hash y cambió la predeterminada (a ONE_AT_A_TIME_HARD), puedes elegir un algoritmo diferente definiendo un símbolo en tiempo de compilación. Para una lista actual, consulta el documento INSTALL. Ten en cuenta que a partir de Perl v5.18 solo podemos recomendar el uso de la predeterminada o SIPHASH. Todas las demás se sabe que tienen problemas de seguridad y son solo para fines de investigación.

La variable de entorno PERL_HASH_SEED ahora toma un valor hexadecimal

"PERL_HASH_SEED" ya no acepta un entero como parámetro; en su lugar, se espera que el valor sea un valor binario codificado en una cadena hexadecimal, como "0xf5867c55039dc724". Esto es para que la infraestructura admita semillas hash de longitudes arbitrarias, que podrían exceder las de un entero. (SipHash utiliza una semilla de 16 bytes).

Se añadió la variable de entorno PERL_PERTURB_KEYS

La variable de entorno "PERL_PERTURB_KEYS" permite controlar el nivel de aleatorización aplicado a "keys" y similares.

Cuando "PERL_PERTURB_KEYS" es 0, perl no aleatorizará el orden de las claves en absoluto. La probabilidad de que "keys" cambie debido a una inserción será la misma que en las versiones anteriores de perl, básicamente solo cuando se cambia el tamaño del bucket.

Cuando "PERL_PERTURB_KEYS" es 1, perl aleatorizará las claves de forma no repetible. La probabilidad de que "keys" cambie debido a una inserción será muy alta. Este es el modo más seguro y predeterminado.

Cuando "PERL_PERTURB_KEYS" es 2, perl aleatorizará las claves de forma repetible. Las ejecuciones repetidas del mismo programa deberían producir el mismo resultado cada vez.

"PERL_HASH_SEED" implica una configuración no predeterminada de "PERL_PERTURB_KEYS". Establecer "PERL_HASH_SEED=0" (exactamente un 0) implica "PERL_PERTURB_KEYS=0" (aleatorización de claves hash deshabilitada); establecer "PERL_HASH_SEED" a cualquier otro valor implica "PERL_PERTURB_KEYS=2" (aleatorización de claves hash determinista y repetible). Especificar "PERL_PERTURB_KEYS" explícitamente a un nivel diferente anula este comportamiento.

Hash::Util::hash_seed() ahora devuelve una cadena

Hash::Util::hash_seed() ahora devuelve una cadena en lugar de un entero. Esto es para que la infraestructura admita semillas hash de longitudes arbitrarias que podrían exceder las de un entero. (SipHash utiliza una semilla de 16 bytes).

La salida de PERL_HASH_SEED_DEBUG ha cambiado

La variable de entorno PERL_HASH_SEED_DEBUG ahora hace que perl muestre tanto la función hash con la que se compiló perl, como la semilla, en hexadecimal, en uso para ese proceso. El código que analice esta salida, si es que existe, debe cambiar para adaptarse al nuevo formato. Ejemplo del nuevo formato:

$ PERL_HASH_SEED_DEBUG=1 ./perl -e1
HASH_FUNCTION = MURMUR3 HASH_SEED = 0x1476bb9f

Actualización a Unicode 6.2

Perl ahora soporta Unicode 6.2. Una lista de cambios desde Unicode 6.1 está en http://www.unicode.org/versions/Unicode6.2.0.

Las alias de nombres de caracteres ahora pueden incluir caracteres fuera del rango Latin1

Es posible definir tus propios nombres para caracteres para su uso en "\N{...}", charnames::vianame(), etc. Estos nombres ahora pueden consistir en caracteres de todo el rango Unicode. Esto permite que los nombres estén en tu idioma nativo, y no solo en inglés. Ciertas restricciones se aplican a los caracteres que se pueden usar (por ejemplo, no puedes definir un nombre que tenga puntuación). Ver "CUSTOM ALIASES" en charnames.

Cambios para Perl 5.20.0

Subrutinas léxicas y subrutinas anónimas en el ámbito actual

En versiones anteriores de Perl, "our sub" y "our sub { ... }" eran equivalentes a un simple "sub", por lo que se podía crear incluso una subrutina anónima con "our sub { ... }". Esto ahora está prohibido fuera de la característica "lexical_subs". Bajo la característica "lexical_subs", tienen nuevos significados descritos en "Lexical Subroutines" en perlsub.

Los valores definidos almacenados en el entorno se fuerzan a cadenas de bytes

Un valor almacenado en una variable de entorno siempre se ha convertido en cadena al ser heredado por procesos hijos.

En esta versión, al asignar a %ENV, los valores se convierten inmediatamente en cadena y se convierten solo en una cadena de bytes.

Primero, se fuerza a que sea solo una cadena. Luego, si la cadena es utf8 y el equivalente de utf8::downgrade() funciona, se usa ese resultado; de lo contrario, se usa el equivalente de utf8::encode() y se emite una advertencia sobre caracteres anchos ("Diagnostics").

"require" falla para archivos ilegibles

Cuando "require" encuentra un archivo ilegible, ahora falla. Antes ignoraba el archivo y continuaba buscando en los directorios de @INC [perl #113422].

"gv_fetchmeth_*" y SUPER

Las diversas funciones XS "gv_fetchmeth_*" solían tratar un paquete cuyo nombre terminaba en "::SUPER" de manera especial. Una búsqueda de método en el paquete "Foo::SUPER" se trataría como una búsqueda de método "SUPER" en el paquete "Foo". Ya no es así. Para realizar una búsqueda "SUPER", pase el stash de "Foo" y el indicador "GV_SUPER".

El primer argumento de "split" se interpreta de forma más coherente

Después de algunos cambios anteriores en la v5.17, el comportamiento de "split" se ha simplificado: si el argumento PATTERN se evalúa como una cadena que contiene un espacio, se trata como lo que una cadena literal que contenía un espacio solía ser.

Deprecaciones

Eliminaciones de módulos

Los siguientes módulos se eliminarán de la distribución principal en una versión futura y, en ese momento, deberán instalarse desde CPAN. Las distribuciones en CPAN que requieran estos módulos deberán listarlos como requisitos previos.

Las versiones principales de estos módulos emitirán ahora advertencias de la categoría "deprecated" para alertarle de este hecho. Para silenciar estas advertencias de deprecación, instale los módulos en cuestión desde CPAN.

Tenga en cuenta que estos son (con raras excepciones) módulos excelentes que se recomienda seguir utilizando. Su exclusión del núcleo se debe principalmente a su necesidad para iniciar una instalación de Perl completamente funcional y compatible con CPAN, no generalmente a preocupaciones sobre su diseño.

encoding
El uso de este pragm se desaconseja enérgicamente. Confunde la codificación del texto fuente con la codificación de los datos de E/S, reinterpreta secuencias de escape en el texto fuente (una opción cuestionable) e introduce el error UTF-8 en todo el manejo en tiempo de ejecución de las cadenas de caracteres. Está roto tal como está diseñado y más allá de la reparación.

Para usar caracteres literales no ASCII en el texto fuente, consulte utf8. Para tratar con datos de E/S textuales, consulte Encode y open.

Cinco caracteres adicionales deben escaparse en patrones con "/x"

Cuando un patrón de expresión regular se compila con "/x", Perl trata 6 caracteres como espacios en blanco para ignorar, como ESPACIO y TAB. Sin embargo, Unicode recomienda tratar 11 caracteres de esta manera. Nos conformaremos con esto en una futura versión de Perl. Mientras tanto, el uso de cualquiera de los caracteres faltantes generará una advertencia de deprecación, a menos que se desactive. Los cinco caracteres son:

U+0085 NEXT LINE
U+200E LEFT-TO-RIGHT MARK
U+200F RIGHT-TO-LEFT MARK
U+2028 LINE SEPARATOR
U+2029 PARAGRAPH SEPARATOR

Nombres de caracteres definidos por el usuario con espacios en blanco sorprendentes

Un nombre de carácter definido por el usuario con espacios finales o múltiples espacios seguidos probablemente sea un error tipográfico. Esto ahora genera una advertencia cuando se define, asumiendo que los usos del mismo probablemente no incluirán los espacios en blanco adicionales.

    • Subrutina "&%s" no disponible

      (W closure) Durante la compilación, una subrutina nombrada interna o eval está intentando capturar una subrutina léxica externa que no está disponible actualmente. Esto puede suceder por una de dos razones. Primero, la subrutina léxica puede declararse en una subrutina anónima externa que aún no se ha creado. (Recuerde que las subs nombradas se crean en tiempo de compilación, mientras que las subs anónimas se crean en tiempo de ejecución). Por ejemplo,

      sub { my sub a {...} sub f { \&a } }

      En el momento en que se crea f, no puede capturar la subrutina actual "a", ya que la subrutina anónima aún no se ha creado. Por el contrario, lo siguiente no generará una advertencia, ya que la subrutina anónima ya se ha creado y está activa:

      sub { my sub a {...} eval 'sub f { \&a }' }->();

      La segunda situación es causada por un eval que accede a una variable que ha salido del ámbito, por ejemplo,

      sub f {
    my sub a {...}
    sub { eval '\&a' }
}
f()->();

      Aquí, cuando se compila el '\&a' en el eval, f() no se está ejecutando actualmente, por lo que su &a no está disponible para captura.

    • La subrutina "%s" &%s enmascara la declaración anterior en el mismo %s

      (W misc) Se ha vuelto a declarar una subrutina "my" o "state" en el ámbito o instrucción actual, eliminando efectivamente todo acceso a la instancia anterior. Esto es casi siempre un error tipográfico. Tenga en cuenta que la subrutina anterior todavía existirá hasta el final del ámbito o hasta que se destruyan todas las referencias de cierre a ella.

    • La característica %s es experimental

      (S experimental) Esta advertencia se emite si habilita una característica experimental a través de "use feature". Simplemente suprima la advertencia si desea usar la característica, pero sepa que al hacerlo corre el riesgo de usar una característica experimental que puede cambiar o ser eliminada en una futura versión de Perl:

      no warnings "experimental::lexical_subs";
use feature "lexical_subs";
    • sleep(%u) demasiado grande

      (W overflow) Llamó a "sleep" con un número mayor del que puede manejar de manera confiable y "sleep" probablemente durmió menos tiempo del solicitado.

    • Caracter ancho en setenv

      Los intentos de colocar caracteres anchos en variables de entorno a través de %ENV ahora provocan esta advertencia.

    • "Número negativo inválido (%s) en chr"

      chr() ahora advierte cuando se le pasa un valor negativo [perl #83048].

    • "Desbordamiento de entero en srand"

      srand() ahora advierte cuando se le pasa un valor que no cabe en un "UV" (ya que el valor se truncará en lugar de desbordarse) [perl #40605].

    • "-i usado sin nombres de archivo en la línea de comandos, leyendo desde STDIN"

      Ejecutar perl con el indicador "-i" ahora advierte si no se proporcionan archivos de entrada en la línea de comandos [perl #113410].

      Perl 5.18.0 Changelog

      This is a summary of the changes between Perl 5.16.0 and Perl 5.18.0.

      Language changes

      • A call checker attached to a closure prototype via "cv_set_call_checker" is now copied to closures cloned from it. So "cv_set_call_checker" now works inside an attribute handler for a closure.
      • Writing to $^N used to have no effect. Now it croaks with "Modification of a read-only value" by default, but that can be overridden by a custom regular expression engine, as with $1 [perl #112184].
      • "undef" on a control character glob ("undef *^H") no longer emits an erroneous warning about ambiguity [perl #112456].
      • For efficiency's sake, many operators and built-in functions return the same scalar each time. Lvalue subroutines and subroutines in the CORE:: namespace were allowing this implementation detail to leak through. "print &CORE::uc("a"), &CORE::uc("b")" used to print "BB". The same thing would happen with an lvalue subroutine returning the return value of "uc". Now the value is copied in such cases.
      • "method {}" syntax with an empty block or a block returning an empty list used to crash or use some random value left on the stack as its invocant. Now it produces an error.
      • "vec" now works with extremely large offsets (>2 GB) [perl #111730].
      • Changes to overload settings now take effect immediately, as do changes to inheritance that affect overloading. They used to take effect only after "bless".

        Objects that were created before a class had any overloading used to remain non-overloaded even if the class gained overloading through "use overload" or @ISA changes, and even after "bless". This has been fixed [perl #112708].

      • Classes with overloading can now inherit fallback values.
      • Overloading was not respecting a fallback value of 0 if there were overloaded objects on both sides of an assignment operator like "+=" [perl #111856].
      • "pos" now croaks with hash and array arguments, instead of producing erroneous warnings.
      • "while(each %h)" now implies "while(defined($_ = each %h))", like "readline" and "readdir".
      • Subs in the CORE:: namespace no longer crash after "undef *_" when called with no argument list (&CORE::time with no parentheses).
      • "unpack" no longer produces the "'/' must follow a numeric type in unpack" error when it is the data that are at fault [perl #60204].
      • "join" and "@array" now call FETCH only once on a tied $" [perl #8931].
      • Some subroutine calls generated by compiling core ops affected by a "CORE::GLOBAL" override had op checking performed twice. The checking is always idempotent for pure Perl code, but the double checking can matter when custom call checkers are involved.
      • A race condition used to exist around fork that could cause a signal sent to the parent to be handled by both parent and child. Signals are now blocked briefly around fork to prevent this from happening [perl #82580].
      • The implementation of code blocks in regular expressions, such as "(?{})" and "(??{})", has been heavily reworked to eliminate a whole slew of bugs. The main user-visible changes are:
        • Code blocks within patterns are now parsed in the same pass as the surrounding code; in particular it is no longer necessary to have balanced braces: this now works: 
          /(?{  $x='{'  })/

          This means that this error message is no longer generated:

          Sequence (?{...}) not terminated or not {}-balanced in regex

          but a new error may be seen:

          Sequence (?{...}) not terminated with ')'

          In addition, literal code blocks within run-time patterns are only compiled once, at perl compile-time:

          for my $p (...) {
    # this 'FOO' block of code is compiled once,
    # at the same time as the surrounding 'for' loop
    /$p{(?{FOO;})/;
}
        • Lexical variables are now sane as regards scope, recursion and closure behavior. In particular, "/A(?{B})C/" behaves (from a closure viewpoint) exactly like "/A/ && do { B } && /C/", while "qr/A(?{B})C/" is like "sub {/A/ && do { B } && /C/}". So this code now works how you might expect, creating three regexes that match 0, 1, and 2: 
          for my $i (0..2) {
    push @r, qr/^(??{$i})$/;
}
"1" =~ $r[1]; # matches
        • The "use re 'eval'" pragma is now only required for code blocks defined at runtime; in particular in the following, the text of the $r pattern is still interpolated into the new pattern and recompiled, but the individual compiled code-blocks within $r are reused rather than being recompiled, and "use re 'eval'" isn't needed any more: 
          my $r = qr/abc(?{....})def/;
/xyz$r/;
        • Flow control operators no longer crash. Each code block runs in a new dynamic scope, so "next" etc. will not see any enclosing loops. "return" returns a value from the code block, not from any enclosing subroutine.
        • Perl normally caches the compilation of run-time patterns, and doesn't recompile if the pattern hasn't changed, but this is now disabled if required for the correct behavior of closures. For example: 
          my $code = '(??{$x})';
for my $x (1..3) {
    # recompile to see fresh value of $x each time
    $x =~ /$code/;
}
        • The "/msix" and "(?msix)" etc. flags are now propagated into the return value from "(??{})"; this now works: 
          "AB" =~ /a(??{'b'})/i;
        • Warnings and errors will appear to come from the surrounding code (or for run-time code blocks, from an eval) rather than from an "re_eval": 
          use re 'eval'; $c = '(?{ warn "foo" })'; /$c/;
/(?{ warn "foo" })/;

          formerly gave:

          foo at (re_eval 1) line 1.
foo at (re_eval 2) line 1.

          and now gives:

          foo at (eval 1) line 1.
foo at /some/prog line 2.

      • Perl now can be recompiled to use any Unicode version. In v5.16, it worked on Unicodes 6.0 and 6.1, but there were various bugs if earlier releases were used; the older the release the more problems.
      • "vec" no longer produces "uninitialized" warnings in lvalue context [perl #9423].
      • An optimization involving fixed strings in regular expressions could cause a severe performance penalty in edge cases. This has been fixed [perl #76546].
      • In certain cases, including empty subpatterns within a regular expression (such as "(?:)" or "(?:|)") could disable some optimizations. This has been fixed.
      • The "Can't find an opnumber" message that "prototype" produces when passed a string like "CORE::nonexistent_keyword" now passes UTF-8 and embedded NULs through unchanged [perl #97478].
      • "prototype" now treats magical variables like $1 the same way as non-magical variables when checking for the CORE:: prefix, instead of treating them as subroutine names.
      • Under threaded perls, a runtime code block in a regular expression could corrupt the package name stored in the op tree, resulting in bad reads in "caller", and possibly crashes [perl #113060].
      • Referencing a closure prototype ("\&{$_[1]}" in an attribute handler for a closure) no longer results in a copy of the subroutine (or assertion failures on debugging builds).
      • "eval '__PACKAGE__'" now returns the right answer on threaded builds if the current package has been assigned over (as in "*ThisPackage:: = *ThatPackage::") [perl #78742].

      • "UNIVERSAL::can" no longer treats its first argument differently depending on whether it is a string or number internally.
      • "open" with "<&" for the mode checks to see whether the third argument is a number, in determining whether to treat it as a file descriptor or a handle name. Magical variables like $1 were always failing the numeric check and being treated as handle names.
