perlbug - cómo enviar informes de errores sobre Perl

DESCRIPCIÓN

Este programa está diseñado para ayudarte a generar informes de errores (y notas de agradecimiento) sobre perl5 y los módulos que vienen con él.

En la mayoría de los casos, puedes ejecutarlo interactivamente desde una línea de comandos sin argumentos especiales y seguir las indicaciones.

Si has encontrado un error en un port no estándar (uno que no formaba parte de la distribución estándar), una distribución binaria o un módulo no principal (como Tk, DBI, etc.), por favor, consulta la documentación que vino con esa distribución para determinar el lugar correcto para reportar errores.

Los informes de errores deben enviarse al rastreador de incidencias de GitHub en https://github.com/Perl/perl5/issues. La dirección perlbug@perl.org ya no abre tickets automáticamente. Puedes usar esta herramienta para componer tu informe y guardarlo en un archivo que luego podrás enviar al rastreador de incidencias.

En casos extremos, perlbug puede no funcionar lo suficientemente bien en tu sistema para guiarte en la redacción de un informe de errores. En esos casos, puedes intentar usar perlbug -d o perl -V para obtener información de configuración del sistema para incluir en tu informe de incidencia.

Al reportar un error, por favor repasa esta lista de verificación:

¿Qué versión de Perl estás ejecutando?
Escribe "perl -v" en la línea de comandos para descubrirlo.
¿Estás ejecutando la última versión liberada de perl?
Consulta http://www.perl.org/ para averiguarlo. Si no estás usando la última versión liberada, por favor, intenta replicar tu error en la última versión estable.

Ten en cuenta que los informes sobre errores en versiones antiguas de Perl, especialmente aquellos que indican que no has probado tampoco la última versión estable de Perl, probablemente recibirán menos atención por parte de los voluntarios que construyen y mantienen Perl que los informes sobre errores en la versión actual.

¿Estás seguro de que lo que has encontrado es un error?
Un número significativo de los informes de errores que recibimos resultan ser características documentadas de Perl. Asegúrate de que el problema que has encontrado no es intencional consultando la documentación que viene con la distribución de Perl.

Dado el gran volumen de documentación de Perl, esto no es una tarea trivial, pero si puedes señalar la documentación que sugiere que el comportamiento que estás viendo es incorrecto, es probable que tu incidencia reciba más atención. Puede que quieras empezar consultando perldoc perltrap para obtener indicaciones sobre trampas comunes en las que caen los programadores de Perl nuevos (y experimentados).

Si no estás seguro del significado de un mensaje de error que has encontrado, consulta perldoc perldiag para obtener una explicación. Si el mensaje no está en perldiag, probablemente no lo genera Perl. Puede que tengas suerte consultando la documentación de tu sistema operativo en su lugar.

Si estás en una plataforma no UNIX, consulta perldoc perlport, ya que algunas características pueden no estar implementadas o funcionar de manera diferente.

Puede que puedas averiguar qué está saliendo mal usando el depurador de Perl. Para obtener información sobre cómo usar el depurador, consulta perldoc perldebug.

¿Tienes un caso de prueba adecuado?
Cuanto más fácil sea reproducir tu error, más probable será que se corrija -- si nadie puede duplicar tu problema, probablemente no se abordará.

Un buen caso de prueba tiene la mayoría de estos atributos: código corto y simple; pocas dependencias de comandos externos, módulos o bibliotecas; sin código dependiente de la plataforma (a menos que sea un error específico de la plataforma); documentación clara y simple.

Un buen caso de prueba es casi siempre un buen candidato para ser incluido en el conjunto de pruebas de Perl. Si tienes tiempo, considera escribir tu caso de prueba para que pueda incluirse fácilmente en el conjunto de pruebas estándar.

¿Has incluido toda la información relevante?
Asegúrate de incluir los mensajes de error **exactos**, si los hay. "Perl dio un error" no es un mensaje de error exacto.

Si obtienes un volcado de núcleo (o equivalente), puedes usar un depurador (dbx, gdb, etc.) para producir un rastreo de pila para incluir en el informe de errores.

NOTA: a menos que tu Perl haya sido compilado con información de depuración (a menudo -g), el rastreo de pila probablemente será algo difícil de usar, ya que muy probablemente contendrá solo los nombres de las funciones y no sus argumentos. Si es posible, recompila tu Perl con información de depuración y reproduce el bloqueo y el rastreo de pila.

¿Puedes describir el error en lenguaje claro?
Cuanto más fácil sea entender un error reproducible, más probable será que se corrija. Cualquier perspectiva que puedas proporcionar sobre el problema ayudará mucho. En otras palabras, intenta analizar el problema (en la medida en que puedas) e informa de tus hallazgos.
¿Puedes corregir el error tú mismo?
Si es así, ¡excelente noticia! Los informes de errores con parches probablemente recibirán mucha más atención e interés que aquellos sin parches. Por favor, envía tu parche a través del flujo de trabajo de Solicitud de Extracción de GitHub como se describe en perldoc perlhack. También puedes enviar parches a perl5-porters@perl.org. Al enviar un parche, créalo usando "git format-patch" si es posible, aunque un diff unificado creado con "diff -pu" servirá casi igual de bien.

Tu parche puede ser devuelto con solicitudes de cambios, o solicitudes de explicaciones más detalladas sobre tu corrección.

Aquí tienes algunos consejos para crear parches de alta calidad:

Asegúrate de que el parche no esté invertido (el primer argumento de diff es típicamente el archivo original, el segundo tu archivo modificado). Asegúrate de probar tu parche aplicándolo con "git am" o el programa "patch" antes de enviarlo. Intenta seguir el mismo estilo que el código que intentas parchear. Asegúrate de que tu parche realmente funcione ("make test", si lo que estás parcheando está cubierto por el conjunto de pruebas de Perl).

¿Puedes usar "perlbug" para enviar una nota de agradecimiento?
Sí, puedes hacerlo usando la opción "-T", o invocando el programa como "perlthanks". Las notas de agradecimiento son buenas. Hacen sonreír a la gente.

Por favor, haz que el título de tu incidencia sea informativo. "un error" no es informativo. Tampoco lo es "perl se bloquea" ni "¡¡¡AYUDA!!!". Esto no ayuda. Una descripción concisa de lo que está mal está bien.

Habiendo hecho tu parte, prepárate para esperar, para que te digan que el error está en tu código, o posiblemente para no recibir ninguna respuesta. Los voluntarios que mantienen Perl son gente ocupada, así que si tu problema es un error obvio en tu propio código, es difícil de entender o es un duplicado de un informe existente, es posible que no recibas una respuesta personal.

Si es importante para ti que tu error sea corregido, monitoriza el rastreador de incidencias (te suscribirás a las notificaciones de las incidencias que envíes o en las que comentes) y los registros de confirmación de las versiones de desarrollo de Perl, y anima a los mantenedores con palabras amables u ofertas de bebidas frías. (Por favor, sé amable con los mantenedores. Acosarlos o insultarlos es inútil)

NAME

perlbug - report a Perl problem

SYNOPSIS

perlbug [options] [file ...]

DESCRIPTION

perlbug is a script that helps you report bugs in Perl. It gathers information about your system and the bug you are experiencing, and then either saves the report to a file or mails it to the Perl porters.

When run, perlbug will prompt you for the following information:

  • A subject line for the report.
  • A description of the bug.
  • Your email address for reply.
  • Confirmation of the system configuration information.
  • Confirmation of the included patches.
  • Confirmation before sending the report.

If you redirect standard output or standard error to a file or pipe, perlbug will enter data mode and print configuration information without asking questions.

You can also provide a file containing the bug report using the -f option.

For more information on reporting bugs effectively, see perltrap(1).

You can find the official Perl bug tracker at https://github.com/Perl/perl5/issues.

If you are reporting a bug, please try to reproduce it with the latest development version of Perl. It's possible your bug has already been fixed. If you are reporting a bug in a specific version of Perl, please mention that in your report. It's also a good idea to try to minimize the code required to reproduce the bug. This makes it easier for the developers to find and fix the problem.

Be aware that some configuration options may cause perlbug to ask questions that are irrelevant to your situation. This is unlikely to have the opposite effect of the one you want.)

Feel free to update the ticket about your bug on https://github.com/Perl/perl5/issues if a new version of Perl is released and your bug is still present.

OPTIONS

-a
Address to send the report to instead of saving to a file.
-b
Body of the report. If not included on the command line, or in a file with -f, you will get a chance to edit the report.
-C
Don't send copy to administrator when sending report by mail.
-c
Address to send copy of report to when sending report by mail. Defaults to the address of the local perl administrator (recorded when perl was built).
-d
Data mode (the default if you redirect or pipe output). This prints out your configuration data, without saving or mailing anything. You can use this with -v to get more complete data.
-e
Editor to use.
-f
File containing the body of the report. Use this to quickly send a prepared report.
-F
File to output the results to. Defaults to perlbug.rep.
-h
Prints a brief summary of the options.
-ok
Report successful build on this system to perl porters. Forces -S and -C. Forces and supplies values for -s and -b. Only prompts for a return address if it cannot guess it (for use with make). Honors return address specified with -r. You can use this with -v to get more complete data. Only makes a report if this system is less than 60 days old.
-okay
As -ok except it will report on older systems.
-nok
Report unsuccessful build on this system. Forces -C. Forces and supplies a value for -s, then requires you to edit the report and say what went wrong. Alternatively, a prepared report may be supplied using -f. Only prompts for a return address if it cannot guess it (for use with make). Honors return address specified with -r. You can use this with -v to get more complete data. Only makes a report if this system is less than 60 days old.
-nokay
As -nok except it will report on older systems.
-p
The names of one or more patch files or other text attachments to be included with the report. Multiple files must be separated with commas.
-r
Your return address. The program will ask you to confirm its default if you don't use this option.
-S
Save or send the report without asking for confirmation.
-s
Subject to include with the report. You will be prompted if you don't supply one on the command line.
-t
Test mode. Makes it possible to command perlbug from a pipe or file, for testing purposes.
-T
Send a thank-you note instead of a bug report.
-v
Include verbose configuration data in the report.
