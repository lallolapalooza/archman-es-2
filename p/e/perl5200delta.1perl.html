NOMBRE

perl5200delta - qué hay de nuevo para perl v5.20.0

DESCRIPCIÓN

Este documento describe las diferencias entre la versión 5.18.0 y la versión 5.20.0.

Si está actualizando desde una versión anterior como la 5.16.0, primero lea perl5180delta, que describe las diferencias entre 5.16.0 y 5.18.0.

Mejoras principales

Firmas experimentales de subrutinas

Sintaxis declarativa para desempaquetar la lista de argumentos en variables léxicas. "sub foo ($a,$b) {...}" verifica el número de argumentos y los coloca en variables léxicas. Las firmas no son equivalentes al modismo existente de "sub foo { my($a,$b) = @_; ... }". Las firmas solo están disponibles habilitando una característica que no es la predeterminada y generan advertencias por ser experimentales. El choque sintáctico con los prototipos se gestiona deshabilitando la sintaxis corta de prototipos cuando las firmas están habilitadas.

Vea "Firmas" en perlsub para obtener detalles.

Las "sub"s ahora aceptan un "prototype" atributo

Al declarar o definir una "sub", el prototipo ahora se puede especificar dentro de un atributo "prototype" en lugar de entre paréntesis después del nombre.

Por ejemplo, "sub foo($$){}" podría reescribirse como "sub foo : prototype($$){}".

Análisis de prototipos más consistente

Múltiples puntos y comas en los prototipos de subrutinas se han tolerado durante mucho tiempo y se han tratado como un solo punto y coma. Había un caso en el que esto no ocurría. Una subrutina cuyo prototipo comienza con "*" o ";*" puede afectar si un bareword se considera un nombre de método o una llamada a subrutina. Esto ahora también se aplica a ";;;*".

El espacio en blanco se ha permitido durante mucho tiempo dentro de los prototipos de subrutinas, por lo que "sub( $ $ )" es equivalente a sub($$), pero hasta ahora se eliminaba cuando se analizaba la subrutina. Por lo tanto, el espacio en blanco *no* estaba permitido en los prototipos establecidos por "Scalar::Util::set_prototype". Ahora está permitido, y el analizador ya no elimina los espacios en blanco. Esto significa que "prototype &mysub" devuelve el prototipo original, con espacios en blanco y todo.

"rand" ahora usa un generador de números aleatorios consistente

Anteriormente, perl utilizaba un generador de números aleatorios específico de la plataforma, variando entre rand(), random() o drand48() de libc.

Esto significaba que la calidad de los números aleatorios de perl variaría de una plataforma a otra, desde los 15 bits de rand() en Windows hasta 48 bits en plataformas POSIX como Linux con drand48().

Perl ahora utiliza su propia implementación interna de drand48() en todas las plataformas. Esto no hace que el "rand" de perl sea criptográficamente seguro. [perl #115928]

Nueva sintaxis de slice

La nueva sintaxis %hash{...} y %array[...] devuelve una lista de pares clave/valor (o índice/valor). Vea "Slices de Clave/Valor de Hash" en perldata.

Desreferenciación postfija experimental

Cuando la característica "postderef" está activa, se establecen las siguientes equivalencias sintácticas:

$sref->$*;  # igual que ${ $sref }  # interpola
$aref->@*;  # igual que @{ $aref }  # interpola
$href->%*;  # igual que %{ $href }
$cref->&*;  # igual que &{ $cref }
$gref->**;  # igual que *{ $gref }
$aref->$#*; # igual que $#{ $aref }
$gref->*{ $slot }; # igual que *{ $gref }{ $slot }
$aref->@[ ... ];  # igual que @$aref[ ... ]  # interpola
$href->@{ ... };  # igual que @$href{ ... }  # interpola
$aref->%[ ... ];  # igual que %$aref[ ... ]
$href->%{ ... };  # igual que %$href{ ... }

Los marcados como interpolantes solo interpolan si la característica "postderef_qq" asociada también está habilitada. Esta característica es experimental y activará advertencias de la categoría "experimental::postderef" cuando se use, a menos que se supriman.

Para más información, consulte la sección Sintaxis de Desreferenciación Postfija de perlref.

Unicode 6.3 ahora soportado

Perl ahora soporta y se distribuye con Unicode 6.3 (aunque Perl puede ser recompilado con cualquier lanzamiento anterior de Unicode también). Una lista detallada de los cambios de Unicode 6.3 está en http://www.unicode.org/versions/Unicode6.3.0/.

Nueva "\p{Unicode}" propiedad de propiedad de expresión regular

Este es un sinónimo de "\p{Any}" y coincide con el conjunto de puntos de código definidos por Unicode 0 - 0x10FFFF.

Mejor soporte de 64 bits

En plataformas de 64 bits, las funciones internas de array ahora usan offsets de 64 bits, permitiendo que los arrays de Perl contengan más de 2**31 elementos, si tiene la memoria disponible.

El motor de expresiones regulares ahora soporta cadenas de más de 2**31 caracteres. [perl #112790, #116907]

Las funciones PerlIO_get_bufsiz, PerlIO_get_cnt, PerlIO_set_cnt y PerlIO_set_ptrcnt ahora tienen SSize_t, en lugar de int, como valores de retorno y parámetros.

"use locale" ahora funciona en locales UTF-8

Hasta esta versión, solo se soportaban locales de un solo byte, como la serie ISO 8859. Ahora, los cada vez más comunes locales multibyte UTF-8 también son soportados. Un locale UTF-8 es aquel en el que el conjunto de caracteres es Unicode y la codificación es UTF-8. Las operaciones de la categoría "LC_CTYPE" de POSIX (cambio de mayúsculas/minúsculas (como lc(), "\U"), y clasificación de caracteres ("\w", "\D", "qr/[[:punct:]]/")) bajo tal locale funcionan igual que si no estuvieran bajo locale, sino como si estuvieran bajo "use feature 'unicode_strings'", excepto que se siguen las reglas de "taint". La ordenación permanece por orden de punto de código en esta versión. [perl #56820].

"use locale" ahora compila en sistemas sin capacidad de locale

Anteriormente, hacer esto causaba que el programa no compilara. Dentro de su ámbito, el programa se comporta como si estuviera en el locale "C". Por lo tanto, los programas escritos para plataformas que soportan locales pueden ejecutarse en plataformas sin locales sin cambios. Los intentos de cambiar el locale del locale "C" fallarán, por supuesto.

Más opciones de fallback para la inicialización de locale

Si hubo un error con los locales durante el inicio de Perl, se rendía inmediatamente e intentaba usar el locale "C". Ahora primero intenta usar otros locales dados por las variables de entorno, como se detalla en "ENVIRONMENT" en perllocale. Por ejemplo, si "LC_ALL" y "LANG" están ambos establecidos, y falla el uso del locale "LC_ALL", Perl intentará usar "LANG".

Novedades

El comportamiento de la configuración local ha cambiado

En el pasado, la configuración local se configuraba de forma un tanto arbitraria. Ahora, Perl intentará primero la configuración local especificada por la variable de entorno "LANG" y, solo si eso falla, recurrirá a "C". En las máquinas con Windows, Perl intentará, antes de usar "C", la configuración local predeterminada del sistema si todas las configuraciones locales dadas por las variables de entorno fallan.

"-DL" opción de tiempo de ejecución ahora añadida para el rastreo de la configuración local

Esto está diseñado para los desarrolladores principales de Perl para ayudar en la depuración de errores relacionados con las configuraciones locales.

-F ahora implica -a y -a implica -n

Anteriormente, -F sin -a era una operación nula, y -a sin -n o -p era una operación nula. Con este cambio, si proporciona -F, entonces se implican tanto -a como -n, y si proporciona -a, entonces se implica -n.

Todavía puede usar -p para su comportamiento adicional. [perl #116190]

Exención de advertencias para $a y $b

Las variables especiales $a y $b, utilizadas en "sort", ahora están exentas de las advertencias de "usado una vez", incluso cuando "sort" no se utiliza. Esto facilita que los módulos CPAN proporcionen funciones que utilizan $a y $b para propósitos similares. [perl #120462]

Seguridad

Evita la posible lectura de memoria liberada (free()) durante el análisis sintáctico

Era posible leer memoria liberada (free()) durante el análisis sintáctico en la circunstancia inusual de que el programa Perl terminara con un heredoc y la última línea del archivo en disco no tuviera un carácter de nueva línea de terminación. Esto se ha corregido.

Cambios incompatibles

"do" ya no se puede usar para llamar a subrutinas

La forma "do SUBROUTINE(LIST)" ha generado una advertencia de deprecación desde Perl v5.0.0, y ahora es un error de sintaxis.

Cambios en las secuencias de escape tipo comilla

El carácter después de "\c" en una cadena entre comillas dobles ("..." o qq(...)) o una expresión regular debe ser ahora un carácter imprimible y no puede ser "{".

Una "{" literal después de "\B" o "\b" es ahora fatal.

Estos fueron deprecados en perl v5.14.0.

El "tainting" ocurre en más circunstancias; ahora se ajusta a la documentación

Esto afecta a la coincidencia de expresiones regulares y al cambio de mayúsculas/minúsculas de una cadena ("lc", "\U", etc.) dentro del ámbito de "use locale". El resultado ahora está "tainted" basado en la operación, sin importar el contenido de la cadena, como indica la documentación (perlsec, "SECURITY" en perllocale). Anteriormente, para la operación de cambio de mayúsculas/minúsculas, si la cadena no contenía caracteres cuyo cambio de mayúsculas/minúsculas pudiera verse afectado por la configuración local, el resultado no estaría "tainted". Por ejemplo, el resultado de uc() en una cadena vacía o en una que solo contiene puntos de código por encima de Latin1 ahora está "tainted", y antes no lo estaba. Esto conduce a resultados de "tainting" más consistentes. Los patrones de expresiones regulares "taint" sus resultados no binarios (como $&, $2) si y solo si el patrón contiene elementos cuya coincidencia depende de la configuración local actual (potencialmente "tainted"). Al igual que las funciones de cambio de mayúsculas/minúsculas, el contenido real de la cadena que se está comparando ya no importa, mientras que antes sí lo hacía. Por ejemplo, si el patrón contiene un "\w", los resultados estarán "tainted" incluso si la coincidencia no tuvo que usar esa porción del patrón para tener éxito o fallar, porque lo que coincide un "\w" depende de la configuración local. Sin embargo, por ejemplo, un "." en un patrón no habilitará el "tainting", porque el punto coincide con cualquier carácter individual, y la configuración local actual no cambia de ninguna manera lo que coincide y lo que no.

"\p{}", "\P{}" la coincidencia ha cambiado para puntos de código no Unicode.

"\p{}" y "\P{}" están definidos por Unicode solo en puntos de código definidos por Unicode ("U+0000" hasta "U+10FFFF"). Su comportamiento al hacer coincidir estos puntos de código Unicode válidos no ha cambiado, pero hay cambios para los puntos de código 0x110000 y superiores. Anteriormente, Perl trataba el resultado de la coincidencia de "\p{}" y "\P{}" contra estos como "undef", que se traduce en "falso". Para "\P{}", esto se complementaba en "verdadero". Se suponía que se debía generar una advertencia cuando esto ocurría. Sin embargo, varias optimizaciones podían impedir la advertencia, y los resultados a menudo eran contraintuitivos, con un éxito y su aparente complemento siendo falsos. Ahora todos los puntos de código no Unicode se tratan como puntos de código Unicode no asignados típicos. Esto generalmente es más "Haz lo que quiero". Se genera una advertencia solo si los resultados son discutiblemente diferentes de un enfoque Unicode estricto y de lo que Perl solía hacer. El código que necesita ser estrictamente compatible con Unicode puede hacer que esta advertencia sea fatal, y entonces Perl siempre genera la advertencia.

Los detalles se encuentran en "Beyond Unicode code points" en perlunicode.

"\p{All}" se ha ampliado para que coincida con todos los puntos de código posibles

El elemento de patrón de expresión regular definido por Perl "\p{All}", no utilizado en CPAN, solía coincidir solo con los puntos de código Unicode; ahora coincide con todos los puntos de código posibles; es decir, es equivalente a "qr/./s". Por lo tanto, "\p{All}" ya no es sinónimo de "\p{Any}", que continúa coincidiendo solo con los puntos de código Unicode, como dice Unicode que debería.

La salida de Data::Dumper puede cambiar

Dependiendo de las estructuras de datos volcadas y la configuración establecida para Data::Dumper, la salida volcada puede haber cambiado con respecto a versiones anteriores.

Si tiene pruebas que dependen de la salida exacta de Data::Dumper, pueden fallar.

Para evitar este problema en su código, pruebe con la estructura de datos resultante de evaluar la estructura volcada, en lugar del volcado en sí.

El carácter del punto decimal de la configuración local ya no se filtra fuera del ámbito de "use locale"

Este es en realidad una corrección de errores, pero algunos códigos se han acostumbrado a que el error esté presente, por lo que este cambio se enumera aquí. La configuración local actual bajo la que se está ejecutando el programa no debería ser visible para el código Perl excepto dentro del ámbito de "use locale". Sin embargo, hasta ahora, en ciertas circunstancias, el carácter utilizado para el punto decimal (a menudo una coma) se filtraba fuera del ámbito. Si su código se ve afectado por este cambio, simplemente agregue un "use locale".

Las asignaciones de códigos de error de sockets de Windows a $! ahora prefieren los valores de errno.h sobre los valores de WSAGetLastError()

En versiones anteriores de Perl, los códigos de error de sockets de Windows devueltos por WSAGetLastError() se asignaban a $!, y algunas constantes como ECONNABORTED, no presentes en errno.h en VC++ (o los diversos puertos de Windows de gcc), se definían con valores WSAE* correspondientes para permitir que $! se probara contra las constantes E* exportadas por Errno y POSIX.

Esto funcionó bien hasta VC++ 2010 y posteriores, que introdujeron nuevas constantes E* con valores > 100 en errno.h, incluyendo algunas que fueron (re)definidas por perl a valores WSAE*. Esto causó problemas al enlazar código XS con otras bibliotecas que utilizaban las definiciones originales de las constantes de errno.h.

Para evitar esta incompatibilidad, perl ahora mapea los códigos de error WSAE* a valores E* cuando es posible, y asigna esos valores a $!. Las constantes E* exportadas por Errno y POSIX se actualizan para que coincidan, de modo que la prueba de $! contra ellas, donde antes era posible, continúe funcionando como se esperaba, y todas las constantes E* que se encuentran en errno.h ahora se exportan desde esos módulos con sus valores originales de errno.h.

Para evitar roturas en el código Perl existente que asigna valores WSAE* a $!, perl ahora intercepta la asignación y realiza el mismo mapeo a valores E* que utiliza internamente al asignar a $! en sí.

Sin embargo, queda una incompatibilidad hacia atrás: el código Perl existente que compara $! con los valores numéricos de los códigos de error WSAE* que se asignaron previamente a $! ahora estará roto en aquellos casos en los que se ha asignado un valor E* correspondiente. Esto solo es un problema para aquellos valores E* < 100, que siempre se exportaron desde Errno y POSIX con sus valores originales de errno.h, y por lo tanto no se podían utilizar para pruebas de códigos de error WSAE* (por ejemplo, WSAEINVAL es 10022, pero el EINVAL correspondiente es 22

). (Los valores E* > 100, si están presentes, se redefinieron de todos modos a valores WSAE*, por lo que se puede lograr la compatibilidad utilizando las constantes E*, que funcionarán antes y después de este cambio, aunque utilizando valores numéricos diferentes internamente).

Las funciones "PerlIO_vsprintf" y "PerlIO_sprintf" han sido eliminadas

Estas dos funciones, no documentadas, no utilizadas en CPAN y problemáticas, han sido eliminadas.

Deprecaciones

La clase de caracteres "/\C/"

La clase de caracteres de expresiones regulares "/\C/" está deprecada. A partir de perl 5.22 generará una advertencia, y a partir de perl 5.24 será un error del compilador de expresiones regulares. Si necesita examinar los bytes individuales que componen un carácter codificado en UTF8, utilice utf8::encode() en la cadena (o una copia) primero.

Caracteres de control literales en nombres de variables

Esta deprecación afecta a cosas como $\cT, donde \cT es un carácter de control literal (como un carácter "NAK" o "NEGATIVE ACKNOWLEDGE") en el código fuente. Sorprendentemente, parece que originalmente se pretendía que esta fuera la forma canónica de acceder a variables como $^T, y que la forma de la tilde solo se añadiera como una alternativa.

La forma de control literal está siendo deprecada por dos razones principales. Tiene errores que probablemente no se puedan corregir, como $\cI no funcionando como un alias para $^I, y su uso no es portable a plataformas no ASCII: mientras que $^T funcionará en todas partes, \cT es espacio en blanco en EBCDIC. [perl #119123]

Referencias a no enteros y enteros no positivos en $/

Establecer $/ a una referencia a cero o a una referencia a un entero negativo ahora está deprecado y se comportará **exactamente** como si se hubiera establecido a "undef". Si desea el comportamiento de "slurp" (leer todo el archivo), establezca $/ explícitamente a "undef".

Establecer $/ a una referencia a un no entero ahora está prohibido y generará un error. Perl nunca documentó lo que sucedería en este contexto y, si bien solía comportarse igual que establecer $/ a la dirección de las referencias, en el futuro puede comportarse de manera diferente, por lo que hemos prohibido este uso.

Rutinas de coincidencia de caracteres en POSIX

El uso de cualquiera de estas funciones en el módulo "POSIX" ahora está deprecado: "isalnum", "isalpha", "iscntrl", "isdigit", "isgraph", "islower", "isprint", "ispunct", "isspace", "isupper" y "isxdigit". Las funciones tienen errores y no funcionan con cadenas codificadas en UTF-8. Consulte sus entradas en POSIX para obtener más información.

Se genera una advertencia en la primera llamada a cualquiera de ellas desde cada lugar del código donde se llaman. (Por lo tanto, una declaración repetida en un bucle generará solo una advertencia).

Los hilos basados en intérprete están ahora desaconsejados

Los "hilos basados en intérprete" proporcionados por Perl no son el sistema rápido y ligero para la multitarea que uno podría esperar o desear. Los hilos están implementados de una manera que los hace fáciles de malinterpretar. Pocas personas saben cómo usarlos correctamente o podrán brindar ayuda.

El uso de hilos basados en intérprete en perl está oficialmente desaconsejado.

Mejoras de rendimiento

  • Perl tiene un nuevo mecanismo de copia en escritura (copy-on-write) que evita la necesidad de copiar el búfer interno de cadenas al asignar de un escalar a otro. Esto hace que la copia de cadenas grandes parezca mucho más rápida. Modificar una de las dos (o más) cadenas después de una asignación forzará una copia internamente. Esto hace que no sea necesario pasar cadenas por referencia por eficiencia.

    Esta característica ya estaba disponible en 5.18.0, pero no estaba habilitada por defecto. Ahora es la predeterminada, por lo que ya no necesita compilar perl con el argumento de *Configure*:

    -Accflags=-DPERL_NEW_COPY_ON_WRITE

    Se puede deshabilitar (por ahora) en una compilación de perl con:

    -Accflags=-DPERL_NO_COW

    En algunos sistemas operativos, Perl se puede compilar de tal manera que cualquier intento de modificar búferes de cadenas compartidos por múltiples SVs provocará un bloqueo. De esta forma, los autores de XS pueden probar que sus módulos manejan correctamente los escalares de copia en escritura. Consulte "Copy on Write" en perlguts para obtener más detalles.

  • Perl tiene un optimizador para patrones de expresiones regulares. Analiza el patrón para encontrar cosas como la longitud mínima que debe tener una cadena para coincidir, etc. Ahora maneja mejor los puntos de código que están por encima del rango Latin1.
  • La ejecución de una expresión regular que contiene el ancla "^" (o su variante bajo el flag "/m") se ha hecho mucho más rápida en varias situaciones.
  • Los valores hash precalculados ahora se utilizan en más lugares durante la búsqueda de métodos.
  • Las búsquedas de claves hash constantes ($hash{key} en contraposición a $hash{$key}) han tenido durante mucho tiempo el valor hash interno calculado en tiempo de compilación, para acelerar la búsqueda. Esta optimización ahora se ha aplicado también a las "slices" de hash.
  • Los operadores "and" y "or" combinados en contexto void, como los generados para "unless ($a && $b)" y "if ($a || b)" ahora se cortocircuitan directamente al final de la sentencia. [perl #120128]
  • En ciertas situaciones, cuando "return" es la última sentencia en el ámbito principal de una subrutina, se optimizará. Esto significa que un código como: 
    sub baz { return $cat; }

    Ahora se comportará como:

    sub baz { $cat; }

    lo cual es notablemente más rápido.

    [perl #120765]

  • Código como: 
    my $x; # o @x, %x
my $y;

    Ahora se optimiza a:

    my ($x, $y);

    En combinación con la optimización de "padrange" introducida en v5.18.0, esto significa que las sentencias de variables my más largas y no inicializadas también se optimizan, por lo que:

    my $x; my @y; my %z;

    se convierte en:

    my ($x, @y, %z);

    [perl #121077]

  • La creación de ciertos tipos de listas, incluidas las "slices" de arrays y hashes, es ahora más rápida.
  • La optimización para arrays indexados con un entero constante pequeño ahora se aplica para enteros en el rango -128..127, en lugar de 0..255. Esto debería acelerar el código Perl que utiliza expresiones como $x[-1], a expensas del código (presumiblemente mucho más raro) que utiliza expresiones como $x[200].
  • La primera iteración sobre un hash grande (usando "keys" o "each") es ahora más rápida. Esto se logra preasignando el estado del iterador interno del hash, en lugar de crearlo perezosamente cuando el hash se itera por primera vez. (Para hashes pequeños, el iterador todavía se crea solo cuando se necesita por primera vez. La suposición es que los hashes pequeños son más propensos a usarse como objetos, y por lo tanto, nunca se asignan. Para hashes grandes, es menos probable que esto sea cierto, y el costo de asignar el iterador se ve superado por el costo de asignar espacio para el hash en sí).

Novedades de Perl

Mejoras del Núcleo de Perl

  • Una coincidencia global de expresiones regulares en una cadena obtenida del operador "readline" o "<>" ya no copia los datos innecesariamente. [perl #121259]
  • La desreferenciación (como en "$obj->[0]" o "$obj->{k}") es ahora más rápida cuando $obj es una instancia de una clase que tiene métodos sobrecargados, pero no sobrecarga ninguno de los métodos de desreferenciación "@{}", "%{}", y similares.
  • El optimizador de Perl ya no omite la optimización de código que sigue a ciertas expresiones "eval {}" (incluidas aquellas con un bucle infinito aparente).
  • La implementación ahora hace un mejor trabajo al evitar trabajo sin sentido en tiempo de ejecución. Las operaciones internas de "nulo" sin efecto (creadas como un efecto secundario del análisis de programas Perl) se eliminan normalmente durante la compilación. Esa eliminación se aplica ahora en algunas situaciones que no se manejaban previamente.
  • Perl ahora realiza menos E/S de disco al tratar con propiedades Unicode que cubren hasta tres rangos de puntos de código consecutivos.

    Nuevas Advertencias

    • %s en referencia es experimental:

      La característica de "desreferencia automática" es experimental.

      A partir de v5.14.0, fue posible usar push, pop, keys y otras funciones integradas no solo en tipos agregados, sino también en referencias a ellos. La característica no se implementó según su especificación original prevista y ahora puede volverse redundante para la desreferenciación postfija. Siempre se ha clasificado como una característica experimental y, en v5.20.0, lleva una advertencia como tal.

      Las advertencias ahora se emitirán en tiempo de compilación cuando se detecten estas operaciones.

      no if $] >= 5.01908, warnings => "experimental::autoderef";

      Considere, sin embargo, reemplazar el uso de estas características, ya que pueden cambiar de comportamiento nuevamente antes de estabilizarse.

    • Una secuencia de múltiples espacios en una definición de alias de charnames está obsoleta

      El espacio en blanco al final en una definición de alias de charnames está obsoleto

      Estas dos advertencias de obsolescencia que involucran "\N{...}" se implementaron incorrectamente. No advertían por defecto (ahora lo hacen) y no se podían hacer fatales a través de "use warnings FATAL => 'deprecated'" (ahora sí).

    • El prototipo de atributo (%s) descarta el prototipo de atributo anterior en la misma sub

      (W misc) Una sub se declaró como "sub foo : prototype(A) : prototype(B) {}", por ejemplo. Dado que cada sub solo puede tener un prototipo, la(s) declaración(es) anterior(es) se descarta(n) mientras se aplica la última.

    • Carácter \0 inválido en %s para %s:

      Nuevos Diagnósticos

      • Caracteres nulos (\0) en nombres de archivo u otros argumentos de llamadas al sistema producen una advertencia.

        (W syscalls) Los caracteres nulos incrustados en nombres de archivo u otros argumentos de llamadas al sistema producen una advertencia a partir de la versión 5.20. Las partes posteriores al \0 eran anteriormente ignoradas por las llamadas al sistema.

      • Coincidencia de un punto de código no Unicode 0x%X con una propiedad Unicode; puede no ser portátil.

        Esto reemplaza el mensaje "El punto de código 0x%X no es Unicode, todas las coincidencias \p{} fallan; todas las coincidencias \P{} tienen éxito".

      • Falta ']' en el prototipo para %s : %s

        (W illegalproto) Se inició una agrupación con "[" pero nunca se cerró con "]".

      • Posible problema de precedencia con el operador de flujo de control

        (W syntax) Existe un posible problema al mezclar un operador de flujo de control (por ejemplo, "return") y un operador de baja precedencia como "or". Considere:

        sub { return $a or $b; }

        Esto se analiza como:

        sub { (return $a) or $b; }

        Lo que es efectivamente solo:

        sub { return $a; }

        Use paréntesis o la variante de alta precedencia del operador.

        Tenga en cuenta que esto también puede activarse para construcciones como:

        sub { 1 if die; }
      • La desreferencia postfija es experimental

        (S experimental::postderef) Esta advertencia se emite si utiliza la sintaxis experimental de desreferencia postfija. Simplemente suprima la advertencia si desea utilizar la función, pero sepa que al hacerlo corre el riesgo de utilizar una función experimental que puede cambiar o eliminarse en una versión futura de Perl:

        no warnings "experimental::postderef";
use feature "postderef", "postderef_qq";
$ref->$*;
$aref->@*;
$aref->@[@indices];
... etc ...
      • El prototipo '%s' es anulado por el atributo 'prototype(%s)' en %s

        (W prototype) Se declaró un prototipo tanto en los paréntesis después del nombre de la subrutina como a través del atributo prototype. El prototipo entre paréntesis es inútil, ya que será reemplazado por el prototipo del atributo antes de que se utilice.

      • El valor escalar @%s[%s] se escribe mejor como $%s[%s]

        (W syntax) En contexto escalar, ha utilizado un índice de matriz/un corte de valor (indicado por %) para seleccionar un solo elemento de una matriz. Generalmente es mejor solicitar un valor escalar (indicado por $). La diferencia es que $foo[&bar] siempre se comporta como un escalar, tanto en el valor que devuelve como al evaluar su argumento, mientras que %foo[&bar] proporciona un contexto de lista a su subíndice, lo que puede hacer cosas extrañas si espera solo un subíndice. Cuando se llama en contexto de lista, también devuelve el índice (lo que devuelve &bar) además del valor.

      • El valor escalar @%s{%s} se escribe mejor como $%s{%s}

        (W syntax) En contexto escalar, ha utilizado una clave de hash/un corte de valor (indicado por %) para seleccionar un solo elemento de un hash. Generalmente es mejor solicitar un valor escalar (indicado por $). La diferencia es que $foo{&bar} siempre se comporta como un escalar, tanto en el valor que devuelve como al evaluar su argumento, mientras que @foo{&bar} proporciona un contexto de lista a su subíndice, lo que puede hacer cosas extrañas si espera solo un subíndice. Cuando se llama en contexto de lista, también devuelve la clave además del valor.

      • Fallo de salida inesperado %d

        (S) Se llamó a un die() no capturado cuando "PERL_EXIT_WARN" se estableció en "PL_exit_flags".

    • El mensaje de error "Unknown switch condition" (Condición de interruptor desconocida) ha sufrido algunos cambios leves. Este error se activa cuando hay una condición desconocida en un condicional "(?(foo))". El mensaje de error solía decir:

      Pero lo que podía ser %s dependía en gran medida de la suerte. Para "(?(foobar))", podrías haber visto "fo" o "f". Para caracteres Unicode, generalmente obtendrías una cadena corrupta. El mensaje ha sido cambiado para decir:

      Unknown switch condition (?(...)) in regex;

      Además, el marcador '<-- HERE' en el error ahora apuntará al lugar correcto en la expresión regular.

    • La advertencia "%s "\x%X" does not map to Unicode" ("%s '\x%X' no se mapea a Unicode") ahora se enumera correctamente como una advertencia grave en lugar de un error fatal.
    • Bajo circunstancias raras, se podía obtener un "Can't coerce readonly REF to string" en lugar del habitual "Modification of a read-only value". Este mensaje de error alternativo ha sido eliminado.
    • "Ambiguous use of * resolved as operator *" (Uso ambiguo de * resuelto como operador *): Esta y advertencias similares sobre "%" y "&" solían ocurrir en algunas circunstancias en las que no había un operador del tipo citado, por lo que la advertencia era completamente incorrecta. Esto se ha corregido [perl #117535, #76910].
    • Las advertencias sobre prototipos de subrutinas mal formados ahora son más consistentes en la forma en que se representan los prototipos. Algunas de estas advertencias truncaban prototipos que contenían nulos. En otros casos, una advertencia suprimía otra. La advertencia sobre caracteres ilegales en prototipos ya no dice "después de '_'" si el carácter incorrecto estaba antes del guion bajo.
    • Las reglas de plegado de Perl no están actualizadas para 0x%X; por favor, utilice la utilidad perlbug para informar; en regex; marcado por <-- HERE en m/%s/

      Este mensaje ahora solo está en la categoría de expresiones regulares y no en la categoría obsoleta. Sigue siendo una advertencia por defecto (es decir, grave) [perl #89648].

    • %%s[%s] en contexto escalar se escribe mejor como $%s[%s]

      Esta advertencia ahora ocurre para cualquier %array[$index] o %hash{key} que se sepa que está en contexto escalar en tiempo de compilación. Anteriormente, se decía "Scalar value %%s[%s] better written as $%s[%s]" ("Valor escalar %%s[%s] se escribe mejor como $%s[%s]").

    • La condición del interruptor no se reconoce en la expresión regular; marcada por <-- HERE en m/%s/:

      La descripción de este diagnóstico se ha ampliado para cubrir todos los casos en los que puede ocurrir la advertencia. También se han resuelto problemas con la posición del indicador de flecha.

    • Los mensajes de error para my($a?$b$c) y my(do{}) ahora mencionan "conditional expression" (expresión condicional) y "do block" (bloque do), respectivamente, en lugar de decir 'Can't declare null operation in "my"' ('No se puede declarar una operación nula en "my"').
    • Cuando "use re "debug"" ejecuta una expresión regular que contiene una referencia inversa, la salida de depuración ahora muestra qué cadena se está comparando.
    • El mensaje de error ahora fatal "Character following \"\\c\" must be ASCII" ("El carácter que sigue a "\c" debe ser ASCII") se ha reformulado como "Character following \"\\c\" must be printable ASCII" ("El carácter que sigue a "\c" debe ser ASCII imprimible") para enfatizar que en "\\cX\", X debe ser un carácter ASCII *imprimible (no de control)*.

      • Donde ha sido posible, la compilación ahora evita invocaciones recursivas de `make` al compilar extensiones puras de Perl, sin eliminar ningún paralelismo de la compilación. Actualmente, alrededor de 80 extensiones pueden ser procesadas directamente por la herramienta `make_ext.pl`, lo que significa que ya no se realizan 80 invocaciones de `make` y 160 invocaciones de `miniperl`.

        Al compilar perl con esta opción, los archivos de biblioteca para módulos XS se nombran de forma "única", por ejemplo, Hash/Util/Util.so se convierte en Hash/Util/PL_Hash__Util.so. Este comportamiento es similar a lo que ocurre actualmente en VMS y sirve como base para el puerto de Android.

      • Opción `sysroot` para indicar el directorio raíz lógico bajo gcc y clang.

        Al compilar con esta opción establecida, tanto Configure como los compiladores buscan todos los encabezados y bibliotecas bajo este nuevo sysroot, en lugar de `/`.

        Esto ahorra mucho tiempo si se compila cruzado, pero también puede ayudar en compilaciones nativas si los archivos de tu toolchain tienen ubicaciones no estándar.

      • El modelo de compilación cruzada ha sido renovado. Hay varias opciones nuevas y algunos cambios incompatibles con versiones anteriores:

        Ahora compilamos binarios para miniperl y generate_uudmap para ser usados en el host, en lugar de ejecutar cada llamada a miniperl en el destino; esto significa que, aparte de 'make test', ya no necesitamos acceso al sistema de destino una vez que Configure ha terminado. Puedes proporcionar binarios ya compilados a través de las opciones `hostperl` y `hostgenerate` para Configure.

        Además, si te diriges a una plataforma EBCDIC desde un host ASCII, o viceversa, necesitarás ejecutar Configure con `-Uhostgenerate`, para indicar que generate_uudmap debe ejecutarse en el destino.

        Finalmente, también hay una forma de que Configure termine temprano, justo después de compilar los binarios del host, compilando cruzado sin especificar un `targethost`.

        Los cambios incompatibles incluyen el no uso de xconfig.h, xlib o Cross.pm, por lo que los archivos de configuración predeterminados y los Makefiles deberán actualizarse.

      • Relacionado con lo anterior, ahora hay una forma de especificar la ubicación de sh (o equivalente) en el sistema de destino: `targetsh`.

        Por ejemplo, Android tiene su sh en /system/bin/sh, por lo que si compilas cruzado desde un sistema Unix más normal con sh en /bin/sh, `targetsh` terminará siendo /system/bin/sh, y `sh` será /bin/sh.

      • Por defecto, `gcc` 4.9 realiza algunas optimizaciones que rompen perl. La opción `-fwrapv` deshabilita esas optimizaciones (y probablemente otras), por lo que para `gcc` 4.3 y posteriores (ya que puede haber problemas similares latentes en versiones anteriores, pero `-fwrapv` estaba roto antes de 4.3, y las optimizaciones probablemente no desaparecerán), `Configure` ahora agrega `-fwrapv` a menos que el usuario solicite `-fno-wrapv`, que deshabilita `-fwrapv`, o `-fsanitize=undefined`, que convierte los desbordamientos que `-fwrapv` ignora en errores de tiempo de ejecución. [GH #13690] https://github.com/Perl/perl5/issues/13690

      • El objetivo `make test.valgrind` ahora permite que las pruebas se ejecuten en paralelo. Este objetivo permite que la suite de pruebas de Perl se ejecute bajo Valgrind, que detecta ciertos tipos de errores de programación en C, aunque a un costo significativo en tiempo de ejecución. En hardware adecuado, permitir la ejecución paralela recupera gran parte de ese costo adicional. [perl #121431]

      Esto significa que el código XS que desee modificar el búfer SvPVX() de un SV debería llamar a SvPV_force() o similar primero, para asegurar un búfer válido (y no compartido), y llamar a SvSETMAGIC() después. Esto de hecho siempre ha sido así (por ejemplo, las claves de hash ya eran copy-on-write); este cambio simplemente extiende el comportamiento COW a una variedad más amplia de SVs.

      Una diferencia importante es que antes de la versión 5.18.0, los escalares de clave de hash compartidos solían tener establecido el flag "SvREADONLY"; esto ya no es así.

      Este nuevo comportamiento aún se puede deshabilitar ejecutando Configure con -Accflags=-DPERL_NO_COW. Esta opción probablemente se eliminará en Perl 5.22.

    • "PL_sawampersand" es ahora una constante. El interruptor que proporcionaba esta variable (para habilitar/deshabilitar la copia previa a la coincidencia dependiendo de si se había visto $&) se ha eliminado y reemplazado por copy-on-write, eliminando algunos errores.

      El comportamiento anterior aún se puede habilitar ejecutando Configure con -Accflags=-DPERL_SAWAMPERSAND.

    • Las funciones "my_swap", "my_htonl" y "my_ntohl" han sido eliminadas. No está claro por qué estas funciones se marcaron alguna vez como *A*, parte de la API. El código XS no puede llamarlas directamente, ya que no puede depender de que estén compiladas. Como era de esperar, ningún código en CPAN las referencia.
    • La firma de la función de expresiones regulares Perl_re_intuit_start() ha cambiado; el puntero de función "intuit" en la estructura del plugin del motor de expresiones regulares también ha cambiado correspondientemente. Se ha añadido un nuevo parámetro, "strbeg"; este tiene el mismo significado que el parámetro del mismo nombre en "Perl_regexec_flags". Anteriormente, intuit intentaba adivinar el inicio de la cadena a partir del SV pasado (si lo había), y a veces se equivocaba (por ejemplo, con un SV sobrecargado).
    • La firma de la función de expresiones regulares Perl_regexec_flags() ha cambiado; el puntero de función "exec" en la estructura del plugin del motor de expresiones regulares también ha cambiado para coincidir. El parámetro "minend" ahora tiene el tipo "SSize_t" para soportar mejor los sistemas de 64 bits.
    • El código XS puede usar varias macros para cambiar la mayúscula/minúscula de un carácter o punto de código (por ejemplo, toLOWER_utf8()). Solo un par de estas estaban documentadas hasta ahora; y ahora deberían usarse en lugar de llamar a las funciones subyacentes. Consulte "Character case changing" en perlapi.
    • El código manejaba de forma bastante inconsistente los uid y gid. Algunos lugares asumían que podían almacenarse de forma segura en UVs, otros en IVs, otros en ints. Se introducen cuatro nuevas macros: SvUID(), sv_setuid(), SvGID() y sv_setgid()
    • Se ha añadido "sv_pos_b2u_flags" a la API. Es similar a "sv_pos_b2u", pero soporta cadenas largas en plataformas de 64 bits.
    • "PL_exit_flags" ahora puede ser utilizado por embebedores de perl u otro código XS para que perl "warn" o "abort" ante un intento de salida. [perl #52000]
    • Compilar con "-Accflags=-PERL_BOOL_AS_CHAR" ahora permite a los compiladores C99 y C++ emular el alias de "bool" a "char" que perl hace para los compiladores C89. [perl #120314]
    • El argumento "sv" en "sv_2pv_flags" en perlapi, "sv_2iv_flags" en perlapi, "sv_2uv_flags" en perlapi, y "sv_2nv_flags" en perlapi y sus wrappers más antiguos sv_2pv, sv_2iv, sv_2uv, sv_2nv, ahora es no nulo. Pasar NULL ahora provocará un fallo. Cuando el marcador no nulo se introdujo en masa en la versión 5.9.3, las funciones se marcaron como no nulas, pero desde la creación de la API SV en la versión alfa 2 de Perl 5.0, si se pasaba NULL, las funciones devolvían 0 o valores de tipo booleano falso. El código que soporta el argumento "sv" como no nulo data de la versión alfa 2 de Perl 5.0 directamente, e indirectamente de Perl 1.0 (API previa a la versión 5.0). La falta de documentación de que las funciones aceptaban un "sv" nulo se corrigió en la versión 5.11.0 y entre las versiones 5.11.0 y 5.19.5 las funciones se marcaron como NULLOK. Como optimización, el código NULLOK se ha eliminado y las funciones volvieron a ser marcadas como no nulas, porque las macros de tipo "getter" del núcleo nunca pasan NULL a estas funciones y fallarían antes de pasar NULL.

      La única forma en que se puede pasar un "sv" nulo a las funciones sv_2*v* es si el código XS llama directamente a sv_2*v*. Esto es poco probable ya que el código XS utiliza las macros Sv*V* para obtener el valor subyacente del SV. Una situación posible que conduce a pasar un "sv" nulo a las funciones sv_2*v* es si el código XS define sus propias macros de tipo "getter" Sv*V*, que verifican si es NULL **antes** de desreferenciar y verificar los flags del SV a través de macros de API pública Sv*OK* o directamente usando la API privada "SvFLAGS", y si "sv" es nulo, entonces llamar a las funciones sv_2*v con un literal nulo o pasar el "sv" que contiene un valor nulo.

    • newATTRSUB es ahora una macro

      La API pública newATTRSUB era anteriormente una macro para la función privada Perl_newATTRSUB. La función Perl_newATTRSUB ha sido eliminada. newATTRSUB es ahora una macro para una función interna diferente.

    • Cambios en las advertencias generadas por utf8n_to_uvchr()

      Esta función de nivel inferior decodifica el primer carácter de una cadena UTF-8 en un punto de código. Es accesible para el código de nivel "XS", pero se desaconseja su uso directo. Hay funciones de nivel superior que la llaman y que deberían usarse en su lugar, como "utf8_to_uvchr_buf" en perlapi. Sin embargo, para mayor exhaustividad, esto documenta algunos cambios en ella. Ahora, las pruebas de malformaciones se realizan antes que las pruebas de otros posibles problemas. Uno de esos problemas implica puntos de código tan grandes que nunca han aparecido en ningún estándar oficial (el estándar actual ha reducido el punto de código aceptable más alto de versiones anteriores). Es posible (aunque no se hace en CPAN) advertir y/o prohibir estos puntos de código, mientras se aceptan puntos de código más pequeños que aún están por encima del máximo legal de Unicode. El mensaje de advertencia para esto ahora incluye el punto de código si es representable en la máquina. Anteriormente, siempre mostraba bytes crudos, que es lo que todavía hace para los puntos de código no representables.

    • Cambios en el motor de expresiones regulares que afectan a la interfaz del motor de expresiones regulares enchufable

      Muchas flags que solían exponerse a través de regexp.h y que solían poblar el miembro extflags de la estructura regexp han sido eliminadas. Estos campos eran técnicamente privados del propio motor de expresiones regulares de Perl y no deberían haberse expuesto allí en primer lugar.

      Las flags afectadas son:

      RXf_NOSCAN
RXf_CANY_SEEN
RXf_GPOS_SEEN
RXf_GPOS_FLOAT
RXf_ANCH_BOL
RXf_ANCH_MBOL
RXf_ANCH_SBOL
RXf_ANCH_GPOS

      Así como las siguientes máscaras de flags:

      RXf_ANCH_SINGLE
RXf_ANCH

      Todas han sido renombradas a equivalentes PREGf_ y movidas a regcomp.h.

      El comportamiento anteriormente logrado estableciendo una o más de las flags RXf_ANCH_ (a través de la máscara RXf_ANCH) ahora ha sido reemplazado por un **único** bit de flag en extflags:

      RXf_IS_ANCHORED

      Los motores de expresiones regulares enchufables que anteriormente establecían estas flags ahora deben establecer esta flag SOLA.

    • El núcleo de Perl ahora utiliza consistentemente av_tindex() ("el índice superior de un array") como un sinónimo más claro para av_len().
    • La oscura variable del intérprete "PL_timesbuf" se espera que sea eliminada al principio de la serie de desarrollo 5.21.x, de modo que Perl 5.22.0 no la proporcionará a los autores de XS. Aunque la variable todavía existe en la versión 5.20.0, esperamos que esta advertencia anticipada de su deprecación ayude a cualquiera que esté utilizando esa variable.

    Errores Corregidos Seleccionados

    Expresiones Regulares

    • Se corrigió un pequeño número de construcciones de expresiones regulares que podían fallar al coincidir o hacer que perl fallara cuando la cadena que se comparaba estaba asignada por encima de la línea de 2 GB en sistemas de 32 bits. [RT #118175]
    • Se corrigieron varias fugas de memoria relacionadas con el análisis de la construcción de expresiones regulares "(?[...])".
    • "(?[...])" ahora permite la interpolación de patrones precompilados que consisten en "(?[...])" con clases de caracteres entre corchetes dentro ("$pat = qr/(?[ [a] ])/; /(?[ $pat ])/"). Anteriormente, los corchetes confundían al analizador de expresiones regulares.
    • El mensaje de advertencia "Cuantificador inesperado en expresión de longitud cero" podía aparecer dos veces a partir de Perl v5.10 para una expresión regular que también contenía alternancias (por ejemplo, "a|b") que activaban la optimización del trie.
    • Perl v5.18 introdujo inadvertidamente un error por el cual la interpolación de cadenas UTF-8 mixtas, de mayor y menor categoría, en una expresión regular podía resultar en UTF-8 malformado en el patrón: específicamente si un carácter de menor categoría en el rango "\x80..\xff" seguía a una cadena UTF-8, por ejemplo: 
      utf8::upgrade(  my $u = "\x{e5}");
utf8::downgrade(my $d = "\x{e5}");
/$u$d/

      [RT

    #118297]

  • En expresiones regulares que contienen múltiples bloques de código, los valores de $1, $2, etc., establecidos por llamadas anidadas a expresiones regulares se filtraban de un bloque a otro. Ahora estas variables siempre hacen referencia a la expresión regular externa al inicio de un bloque incrustado [perl #117917].
  • "/$qr/p" estaba roto en Perl 5.18.0; la bandera "/p" se ignoraba. Esto ha sido corregido. [perl #118213]
  • A partir de Perl 5.18.0, una construcción como "/[#](?{})/x" interpretaba incorrectamente el "#" como un comentario. El bloque de código se omitía, sin analizar. Esto se ha corregido.
  • A partir de Perl 5.001, una expresión regular como "/[#$a]/x" o "/[#]$a/x" interpretaba incorrectamente el "#" como un comentario, por lo que la variable no se interpolaba. Esto se ha corregido. [perl #45667]
  • Perl 5.18.0 hizo involuntariamente que las expresiones regulares desreferenciadas ("${ qr// }") fueran falsas como booleanos. Esto ha sido corregido.
  • El uso de "\G" en expresiones regulares, donde no está al principio del patrón, es ahora ligeramente menos propenso a errores (aunque todavía es algo problemático).
  • Donde una expresión regular incluía bloques de código ("/(?{...})/"), y donde el uso de sobrecarga de constantes activaba una recompilación del bloque de código, la segunda compilación no veía su ámbito léxico externo. Esto fue una regresión en Perl 5.18.0.
  • La posición de la cadena establecida por "pos" podía cambiar si la cadena cambiaba de representación internamente a utf8 o desde utf8. Esto podía ocurrir, por ejemplo, con referencias a objetos con sobrecarga de cadenas.
  • Tomar referencias de los valores de retorno de dos llamadas a "pos" con el mismo argumento, y luego asignar una referencia a una y "undef" a la otra, podía resultar en fallos de aserción o fugas de memoria.
  • Los elementos de @- y @+ ahora se actualizan correctamente cuando se refieren a capturas inexistentes. Anteriormente, un elemento referenciado ("$ref = \$-[1]") podía referirse a una coincidencia incorrecta después de coincidencias posteriores.
  • El código que analiza las referencias inversas de regex (o referencias inversas/octales ambiguos) como \123 realizaba un simple atoi(), que podía dar la vuelta a valores negativos en cadenas largas de dígitos y causar fallos de segmentación. Esto ahora ha sido corregido. [perl #119505]
  • Asignar otro typeglob a "*^R" ya no hace que el motor de expresiones regulares falle.
  • El escape de expresión regular "\N", cuando se usa sin las llaves (para significar "[^\n]"), ignoraba un "*" siguiente si iba seguido de espacio en blanco bajo /x. Había sido así desde que "\N" para significar "[^\n]" se introdujo en 5.12.0.
  • "s///", "tr///" y "y///" ahora funcionan cuando se utiliza un carácter ancho como delimitador. [perl #120463]
  • Se han corregido algunos casos de secuencias (?...) no terminadas en expresiones regulares (por ejemplo, "/(?</") para producir el mensaje de error adecuado en lugar de "panic: memory wrap". Otros casos (por ejemplo, "/(?(/") aún no se han corregido.
  • Cuando una referencia a una referencia a un objeto sobrecargado se devolvía desde un bloque de código de expresión regular "(??{...})", podía producirse una desreferenciación implícita incorrecta si la referencia interna había sido devuelta por un bloque de código anteriormente.
  • Una variable enlazada devuelta desde "(??{...})" ve los valores internos de las variables de coincidencia (es decir, el $1, etc. de cualquier coincidencia dentro del bloque) en su método FETCH. Esto no ocurría si una referencia a un objeto sobrecargado era lo último asignado a la variable enlazada. En su lugar, las variables de coincidencia se referían al patrón externo durante la llamada FETCH.
  • Corrección de la enturbación inesperada a través de expresiones regulares usando locales. Anteriormente, bajo ciertas condiciones, el uso de clases de caracteres podía causar enturbación cuando no debía. Algunas clases de caracteres dependen de la configuración regional, pero antes de este parche, a veces se producía enturbación incluso para clases de caracteres que no dependían de la configuración regional. [perl #120675]
  • Bajo ciertas condiciones, Perl lanzaba un error si en una aserción de lookbehind en una expresión regular, la aserción se refería a un subpatrón con nombre, quejándose de que el lookbehind era variable cuando no lo era. Esto ha sido corregido. [perl #120600], [perl #120618]. La corrección actual puede mejorarse en el futuro.
  • $^R no estaba disponible fuera de la expresión regular que lo inicializaba. [perl #121070]
  • Se fusionó un gran conjunto de correcciones y refactorizaciones para re_intuit_start(), los puntos destacados son:
    • Se corrigió un pánico al compilar la expresión regular "/\x{100}[xy]\x{100}{2}/".
    • Se corrigió una regresión de rendimiento al realizar una coincidencia de patrón global contra una cadena UTF-8. [perl #120692]
    • Se corrigió otro problema de rendimiento en el que la coincidencia de una expresión regular como "/ab.{1,2}x/" contra una cadena UTF-8 larga calculaba innecesariamente desplazamientos de bytes para una gran parte de la cadena. [perl #120692]
    • Se corrigió un error de alineación al compilar expresiones regulares cuando se compilaban con GCC en HP-UX de 64 bits.
    • En plataformas de 64 bits, "pos" ahora se puede establecer en un valor superior a 2**31-1. [perl #72766]

    • Las constantes léxicas ("my sub a() { 42 }") ya no fallan cuando se insertan en línea.
    • Los prototipos de parámetros adjuntos a subrutinas léxicas ahora se respetan al compilar llamadas a subs sin paréntesis. Anteriormente, los prototipos solo se honraban para llamadas *con* paréntesis. [RT #116735]
    • Los errores de sintaxis en subrutinas léxicas en combinación con llamadas a las mismas subrutinas ya no provocan fallos en tiempo de compilación.
    • Las advertencias de recursión profunda ya no hacen fallar las subrutinas léxicas. [RT #118521]
    • La sonda de entrada de sub dtrace ahora funciona con subs léxicas, en lugar de fallar [perl #118305].
    • Anular una subrutina léxica in-lineable (my sub foo() { 42 } undef &foo) resultaba en un fallo si las advertencias estaban activadas.
    • Una sub léxica anulada utilizada como método heredado ya no provoca un fallo.
    • La presencia de una sub léxica llamada "CORE" ya no impide que el prefijo CORE:: funcione.

      Correcciones y mejoras

      • El método DESTROY que redefine el mismo `glob` ahora es seguro. Solía producir advertencias de "Attempt to free unreferenced glob pointer" y filtrar memoria.
      • Si la redefinición de una subrutina ("eval 'sub foo{}'" o "newXS" para código XS) desencadena un método DESTROY en la subrutina que se está redefiniendo, y ese método asigna una subrutina al mismo espacio ("*foo = sub {}"), $_[0] ya no apunta a un escalar liberado. Ahora DESTOY se retrasa hasta que la nueva subrutina se ha instalado.
      • En Windows, Perl ya no llama a CloseHandle() en un manejador de socket. Esto facilita la depuración en Windows al eliminar ciertas excepciones de manejadores incorrectos irrelevantes. También corrige una condición de carrera que hacía que las funciones de socket fallaran aleatoriamente en un proceso de Perl con múltiples hilos del sistema operativo, y posibles fallos de prueba en dist/IO/t/cachepropagate-tcp.t. [perl #120091/118059]
      • Los formatos que involucran cadenas codificadas en UTF-8, o variables extrañas como ties, overloads, o referencias stringificadas (y en perls recientes, variables NOK puras) generalmente hacían lo incorrecto en los formatos cuando la variable se trataba como una cadena y se troceaba repetidamente, como en "^<<<~~" y similares. Esto se ha resuelto. [perl #33832/45325/113868/119847/119849/119851]
      • "semctl(..., SETVAL, ...)" establecía el semáforo en los 32 bits superiores del entero proporcionado en lugar de los 32 bits inferiores en sistemas big-endian de 64 bits. [perl #120635]
      • readdir() ahora solo establece $! en caso de error. $! ya no se establece en "EBADF" cuando la terminación "undef" se lee del directorio a menos que la llamada al sistema establezca $!. [perl #118651]
      • &CORE::glob ya no provoca un bloqueo intermitente debido a la corrupción de la pila de Perl. [perl #119993]
      • "open" con capas que cargan módulos (por ejemplo, "<:encoding(utf8)") ya no corre el riesgo de bloquearse debido a la corrupción de la pila.
      • Perl 5.18 rompió la carga automática a través de llamadas de método "->SUPER::foo" al buscar AUTOLOAD desde el paquete actual en lugar de la superclase del paquete actual. Esto se ha corregido. [perl #120694]
      • Se ha resuelto un error de larga data que causaba que "do {} until CONSTANT", donde la constante tenía un valor verdadero, leyera memoria no asignada. Esto solía ocurrir después de un error de sintaxis. En versiones anteriores de Perl, provocaba bloqueos intermitentes. [perl #72406]
      • Fallo de $! en HP-UX. El strerror() de HP-UX devuelve una cadena vacía para un código de error desconocido. Esto provocaba un fallo de aserción en las compilaciones con DEBUGGING. Ahora, en su lugar, la cadena devuelta para "$!" contiene texto que indica que el código es para un error desconocido.
      • Los elementos individualmente enlazados de @INC (como en "tie $INC[0]...") ahora se manejan correctamente. Anteriormente, si una subrutina devuelta por un elemento enlazado se trataba como una subrutina dependía de si se había producido un FETCH previamente.
      • "getc" en un manejador de tamaño de byte después de que el mismo operador "getc" se hubiera utilizado en un manejador utf8 solía tratar los bytes como utf8, lo que resultaba en un comportamiento errático (por ejemplo, advertencias de UTF-8 mal formado).
      • Una "{" inicial al principio de una línea de argumento de formato siempre se interpretaba como el principio de un bloque antes de la v5.18. En Perl v5.18, comenzó a tratarse como un token ambiguo. El analizador intentaba adivinar si debía ser un constructor de hash anónimo o un bloque basándose en el contenido. Ahora se ha restaurado el comportamiento anterior. [perl #119973]
      • En Perl v5.18, "undef *_; goto &sub" y "local *_; goto &sub" comenzaron a fallar. Esto se ha corregido. [perl #119949]
      • Las comillas invertidas ( `` o " qx// ") combinadas con múltiples hilos en Win32 podían resultar en que la salida enviada a stdout en un hilo fuera capturada por las comillas invertidas de un comando externo en otro hilo.

        Esto también podía ocurrir para procesos pseudo-forked, ya que el pseudo-fork de Win32 se implementa en términos de hilos. [perl #77672]

      • "open $fh, ">+", undef" ya no filtra memoria cuando TMPDIR está configurado pero apunta a un directorio donde no se puede crear un archivo temporal. [perl #120951]
      • " for ( $h{k} || '' ) " ya no auto-vivifica $h{k}. [perl #120374]
      • En máquinas con Windows, Perl ahora emula el uso POSIX del entorno para la inicialización de la configuración regional. Anteriormente, se ignoraba el entorno. Ver "ENVIRONMENT" en perllocale.
      • Se corrigió un bloqueo al destruir un GLOB autorreferencial. [perl #121242]

      REPORTING BUGS

      If you find a bug, please try to make a small, self-contained example that demonstrates it. Then, upload it to CPAN (if it's a module) or send it to perlbug@perl.org. The bug report, along with the example, will be sent to perlbug@perl.org to be analysed by the Perl porting team.

      If the bug you are reporting has security implications, which make it inappropriate to send to a publicly archived mailing list, then please send it to perl5-security-report@perl.org. This points to a closed subscription unarchived mailing list, which includes all the core committers, who will be able to help assess the impact of issues, figure out a resolution, and help co-ordinate the release of patches to mitigate or fix the problem across all platforms on which Perl is supported. Please only use this address for security issues in the Perl core, not for modules independently distributed on CPAN.
