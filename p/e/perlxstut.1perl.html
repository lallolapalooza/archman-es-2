NOMBRE

perlxstut - Tutorial para escribir XSUBs

DESCRIPCIÓN

Este tutorial educará al lector sobre los pasos involucrados en la creación de una extensión de Perl. Se asume que el lector tiene acceso a perlguts, perlclib, perlapi y perlxs.

Este tutorial comienza con ejemplos muy simples y se vuelve más complejo, y cada nuevo ejemplo agrega nuevas características. Ciertos conceptos pueden no explicarse completamente hasta más adelante en el tutorial, para facilitar gradualmente al lector la creación de extensiones.

Este tutorial fue escrito desde una perspectiva de Unix. Donde sé que son diferentes para otras plataformas (por ejemplo, Win32), los mencionaré. Si encuentra algo que se omitió, por favor hágame saber.

NOTAS ESPECIALES

make

Este tutorial asume que el programa make al que está configurado Perl se llama "make". En lugar de ejecutar "make" en los ejemplos que siguen, es posible que deba sustituir cualquier programa make para el que Perl se haya configurado. Ejecutar perl -V:make debería indicarle cuál es.

Advertencia de versión

Al escribir una extensión de Perl para consumo general, se debe esperar que la extensión se utilice con versiones de Perl diferentes a la versión disponible en su máquina. Dado que está leyendo este documento, la versión de Perl en su máquina es probablemente 5.005 o posterior, pero los usuarios de su extensión pueden tener versiones más antiguas.

Para comprender qué tipos de incompatibilidades se pueden esperar, y en el raro caso de que la versión de Perl en su máquina sea anterior a este documento, consulte la sección sobre "Solución de problemas de estos ejemplos" para obtener más información.

Si su extensión utiliza algunas características de Perl que no están disponibles en versiones anteriores de Perl, sus usuarios agradecerán una advertencia temprana y significativa. Probablemente pondría esta información en el archivo README, pero hoy en día la instalación de extensiones puede realizarse automáticamente, guiada por el módulo CPAN.pm u otras herramientas.

En las instalaciones basadas en MakeMaker, Makefile.PL proporciona la primera oportunidad para realizar verificaciones de versión. Se puede poner algo como esto en Makefile.PL para este propósito:

eval { require 5.007 }
    or die <<EOD;
############
### Este módulo utiliza el framework de frobnication que no está disponible
### antes de la versión 5.007 de Perl. Actualice su Perl antes de
### instalar Kara::Mba.
############
EOD

Carga Dinámica versus Carga Estática

Se piensa comúnmente que si un sistema no tiene la capacidad de cargar una biblioteca dinámicamente, no se pueden construir XSUBs. Esto es incorrecto. Se *pueden* construir, pero debe enlazar las subrutinas XSUB con el resto de Perl, creando un nuevo ejecutable. Esta situación es similar a Perl 4.

Este tutorial aún se puede usar en un sistema de este tipo. El mecanismo de compilación de XSUB verificará el sistema y construirá una biblioteca cargable dinámicamente si es posible, o de lo contrario, una biblioteca estática y luego, opcionalmente, un nuevo ejecutable enlazado estáticamente con esa biblioteca estática enlazada.

Si desea compilar un ejecutable enlazado estáticamente en un sistema que puede cargar bibliotecas dinámicamente, puede, en todos los ejemplos siguientes, donde se ejecuta el comando ""make"" sin argumentos, ejecutar en su lugar el comando ""make perl"".

Si ha generado un ejecutable enlazado estáticamente de esta manera por elección, entonces en lugar de decir ""make test"", debería decir ""make test_static"". En los sistemas que no pueden compilar bibliotecas cargables dinámicamente en absoluto, simplemente decir ""make test"" es suficiente.

Hilos y PERL_NO_GET_CONTEXT

Para compilaciones con hilos, perl requiere el puntero de contexto para el hilo actual, sin "PERL_NO_GET_CONTEXT", perl llamará a una función para recuperar el contexto.

Para mejorar el rendimiento, incluya:

#define PERL_NO_GET_CONTEXT

como se muestra a continuación.

Para más detalles, vea perlguts.

EJEMPLO 1

Nuestra primera extensión será muy simple. Cuando llamemos a la rutina en la extensión, imprimirá un mensaje bien conocido y regresará.

Ejecute ""h2xs -A -n Mytest"". Esto crea un directorio llamado Mytest, posiblemente bajo ext/ si ese directorio existe en el directorio de trabajo actual. Se crearán varios archivos bajo el directorio Mytest, incluyendo MANIFEST, Makefile.PL, lib/Mytest.pm, Mytest.xs, t/Mytest.t y Changes.

El archivo MANIFEST contiene los nombres de todos los archivos creados recientemente en el directorio Mytest.

El archivo Makefile.PL debería verse algo así:

use ExtUtils::MakeMaker;
# See lib/ExtUtils/MakeMaker.pm for details of how to influence
# the contents of the Makefile that is written.
WriteMakefile(
    NAME         => 'Mytest',
    VERSION_FROM => 'Mytest.pm', # finds $VERSION
    LIBS         => [''],        # e.g., '-lm'
    DEFINE       => '',          # e.g., '-DHAVE_SOMETHING'
    INC          => '-I',        # e.g., '-I. -I/usr/include/other'
);

El archivo Mytest.pm debería comenzar con algo como esto:

package Mytest;
use 5.008008;
use strict;
use warnings;
require Exporter;
our @ISA = qw(Exporter);
our %EXPORT_TAGS = ( 'all' => [ qw(
) ] );
our @EXPORT_OK = ( @{ $EXPORT_TAGS{'all'} } );
our @EXPORT = qw(
);
our $VERSION = '0.01';
require XSLoader;
XSLoader::load('Mytest', $VERSION);
# Preloaded methods go here.
1;
__END__
# Below is the stub of documentation for your module. You better
# edit it!

El resto del archivo .pm contiene código de ejemplo para proporcionar documentación para la extensión.

Finalmente, el archivo Mytest.xs debería verse algo así:

#define PERL_NO_GET_CONTEXT
#include "EXTERN.h"
#include "perl.h"
#include "XSUB.h"
#include "ppport.h"
MODULE = Mytest             PACKAGE = Mytest

Editaremos el archivo .xs agregando esto al final del archivo:

void
hello()
    CODE:
        printf("Hello, world!\n");

Está bien que las líneas que comienzan en la línea "CODE:" no estén indentadas. Sin embargo, por razones de legibilidad, se sugiere que indente CODE: un nivel y las líneas siguientes un nivel más.

Ahora ejecutaremos ""perl Makefile.PL"". Esto creará un Makefile real, que make necesita. Su salida se ve algo así:

% perl Makefile.PL
Checking if your kit is complete...
Looks good
Writing Makefile for Mytest
%

Ahora, ejecutar make producirá una salida que se ve algo así (algunas líneas largas se han acortado para mayor claridad y se han eliminado algunas líneas superfluas):

% make
cp lib/Mytest.pm blib/lib/Mytest.pm
perl xsubpp  -typemap typemap  Mytest.xs > Mytest.xsc && \
mv Mytest.xsc Mytest.c
Please specify prototyping behavior for Mytest.xs (see perlxs manual)
cc -c     Mytest.c
Running Mkbootstrap for Mytest ()
chmod 644 Mytest.bs
rm -f blib/arch/auto/Mytest/Mytest.so
cc -shared -L/usr/local/lib Mytest.o -o blib/arch/auto/Mytest/Mytest.so
chmod 755 blib/arch/auto/Mytest/Mytest.so
cp Mytest.bs blib/arch/auto/Mytest/Mytest.bs
chmod 644 blib/arch/auto/Mytest/Mytest.bs
Manifying blib/man3/Mytest.3pm
%

Puede ignorar de forma segura la línea sobre "comportamiento de prototipado"; se explica en "La palabra clave PROTOTYPES:" en perlxs.

Perl tiene su propia forma especial de escribir fácilmente scripts de prueba, pero solo para este ejemplo, crearemos nuestro propio script de prueba. Cree un archivo llamado hello que se vea así:

#! /opt/perl5/bin/perl
use ExtUtils::testlib;
use Mytest;
Mytest::hello();

Ahora hacemos que el script sea ejecutable ("chmod +x hello"), ejecutamos el script y deberíamos ver la siguiente salida:

% ./hello
Hello, world!
%

EJEMPLO 2

Ahora agregaremos a nuestra extensión una subrutina que tomará un único argumento numérico como entrada y devolverá 1 si el número es par o 0 si es impar.

Agrega lo siguiente al final de Mytest.xs:

int
is_even(input)
        int input
    CODE:
        RETVAL = (input % 2 == 0);
    OUTPUT:
        RETVAL

No es necesario que haya espacios al principio de la línea ""int input"", pero es útil para mejorar la legibilidad. Poner un punto y coma al final de esa línea también es opcional. Cualquier cantidad y tipo de espacio en blanco se puede colocar entre ""int"" y ""input"".

Ahora vuelve a ejecutar `make` para reconstruir nuestra nueva biblioteca compartida.

Ahora realiza los mismos pasos que antes, generando un Makefile a partir del archivo Makefile.PL y ejecutando `make`.

Para probar que nuestra extensión funciona, ahora necesitamos mirar el archivo Mytest.t. Este archivo está configurado para imitar el mismo tipo de estructura de prueba que tiene el propio Perl. Dentro del script de prueba, realizas una serie de pruebas para confirmar el comportamiento de la extensión, imprimiendo "ok" cuando la prueba es correcta, "not ok" cuando no lo es.

use Test::More tests => 4;
BEGIN { use_ok('Mytest') };
#########################
# Inserta tu código de prueba a continuación, el módulo Test::More está en use() aquí
# así que lee su página man (perldoc Test::More) para obtener ayuda para escribir este
# script de prueba.
is( Mytest::is_even(0), 1 );
is( Mytest::is_even(1), 0 );
is( Mytest::is_even(2), 1 );

Llamaremos al script de prueba a través del comando ""make test"". Deberías ver una salida que se parezca a esto:

%make test
PERL_DL_NONLAZY=1 /usr/bin/perl "-MExtUtils::Command::MM" "-e"
"test_harness(0, 'blib/lib', 'blib/arch')" t/*.t
t/Mytest....ok
All tests successful.
Files=1, Tests=4, 0 wallclock secs ( 0.03 cusr + 0.00 csys = 0.03 CPU)
%

¿Qué ha pasado?

El programa h2xs es el punto de partida para crear extensiones. En ejemplos posteriores veremos cómo podemos usar h2xs para leer archivos de cabecera y generar plantillas para conectar con rutinas C.

h2xs crea una serie de archivos en el directorio de la extensión. El archivo Makefile.PL es un script de perl que generará un Makefile real para compilar la extensión. Le echaremos un vistazo más de cerca más adelante.

Los archivos .pm y .xs contienen la médula de la extensión. El archivo .xs contiene las rutinas C que componen la extensión. El archivo .pm contiene rutinas que le dicen a Perl cómo cargar tu extensión.

Generar el Makefile y ejecutar "make" creó un directorio llamado blib (que significa "build library") en el directorio de trabajo actual. Este directorio contendrá la biblioteca compartida que construiremos. Una vez que la hayamos probado, podremos instalarla en su ubicación final.

Invocar el script de prueba a través de ""make test"" hizo algo muy importante. Invocó perl con todos esos argumentos "-I" para que pudiera encontrar los diversos archivos que forman parte de la extensión. Es *muy* importante que mientras sigas probando extensiones uses ""make test"". Si intentas ejecutar el script de prueba por sí solo, obtendrás un error fatal. Otra razón por la que es importante usar ""make test"" para ejecutar tu script de prueba es que si estás probando una actualización de una versión ya existente, usar ""make test"" asegura que probarás tu nueva extensión, no la versión ya existente.

Cuando Perl ve un "use extension;", busca un archivo con el mismo nombre que la extensión en "use"d que tenga el sufijo .pm. Si no se puede encontrar ese archivo, Perl muere con un error fatal. La ruta de búsqueda predeterminada está contenida en el array @INC.

En nuestro caso, Mytest.pm le dice a perl que necesitará las extensiones Exporter y Dynamic Loader. Luego establece los arrays @ISA y @EXPORT y el escalar $VERSION; finalmente, le dice a perl que inicie el módulo. Perl llamará a su rutina de cargador dinámico (si la hay) y cargará la biblioteca compartida.

Los dos arrays @ISA y @EXPORT son muy importantes. El array @ISA contiene una lista de otros paquetes en los que buscar métodos (o subrutinas) que no existen en el paquete actual. Esto generalmente solo es importante para extensiones orientadas a objetos (de las que hablaremos mucho más adelante), y por lo tanto, generalmente no necesita ser modificado.

El array @EXPORT le dice a Perl cuáles de las variables y subrutinas de la extensión deben colocarse en el espacio de nombres del paquete que llama. Dado que no sabes si el usuario ya ha utilizado los nombres de tus variables y subrutinas, es de vital importancia seleccionar cuidadosamente qué exportar. No exportes nombres de métodos o variables *por defecto* sin una buena razón.

Como regla general, si el módulo intenta ser orientado a objetos, no exportes nada. Si es solo una colección de funciones y variables, puedes exportarlas a través de otro array, llamado @EXPORT_OK. Este array no coloca automáticamente sus nombres de subrutinas y variables en el espacio de nombres a menos que el usuario solicite específicamente que se haga.

Ver perlmod para más información.

La variable $VERSION se utiliza para asegurar que el archivo .pm y la biblioteca compartida estén "sincronizados" entre sí. Cada vez que realices cambios en los archivos .pm o .xs, debes incrementar el valor de esta variable.

Escribiendo buenos scripts de prueba

La importancia de escribir buenos scripts de prueba no se puede enfatizar lo suficiente. Debes seguir de cerca el estilo "ok/not ok" que utiliza el propio Perl, para que sea muy fácil y sin ambigüedades determinar el resultado de cada caso de prueba. Cuando encuentres y corrijas un error, asegúrate de agregar un caso de prueba para él.

Al ejecutar ""make test"", te aseguras de que tu script Mytest.t se ejecute y utilice la versión correcta de tu extensión. Si tienes muchos casos de prueba, guarda tus archivos de prueba en el directorio "t" y usa el sufijo ".t". Cuando ejecutes ""make test"", se ejecutarán todos estos archivos de prueba.

EJEMPLO 3

Nuestra tercera extensión tomará un argumento como entrada, redondeará ese valor y establecerá el *argumento* al valor redondeado.

Agrega lo siguiente al final de Mytest.xs:

void
round(arg)
        double  arg
    CODE:
        if (arg > 0.0) {
                arg = floor(arg + 0.5);
        } else if (arg < 0.0) {
                arg = ceil(arg - 0.5);
        } else {
                arg = 0.0;
        }
    OUTPUT:
        arg

Edita el archivo Makefile.PL para que la línea correspondiente se vea así:

LIBS      => ['-lm'],   # e.g., '-lm'

Genera el Makefile y ejecuta `make`. Cambia el número de prueba en Mytest.t a "9" y agrega las siguientes pruebas:

my $i;
$i = -1.5;
Mytest::round($i);
is( $i, -2.0, 'Rounding -1.5 to -2.0' );
$i = -1.1;
Mytest::round($i);
is( $i, -1.0, 'Rounding -1.1 to -1.0' );
$i = 0.0;
Mytest::round($i);
is( $i, 0.0, 'Rounding 0.0 to 0.0' );
$i = 0.5;
Mytest::round($i);
is( $i, 1.0, 'Rounding 0.5 to 1.0' );
$i = 1.2;
Mytest::round($i);
is( $i, 1.0, 'Rounding 1.2 to 1.0' );

Ejecutar ""make test"" ahora debería imprimir que las nueve pruebas están bien.

Observa que en estos nuevos casos de prueba, el argumento pasado a round era una variable escalar. Quizás te preguntes si puedes redondear una constante o literal. Para ver qué sucede, agrega temporalmente la siguiente línea a Mytest.t:

Mytest::round(3);

Ejecuta ""make test"" y observa que Perl muere con un error fatal. ¡Perl no te permitirá cambiar el valor de las constantes!

¿Qué's nuevo aquí?

  • Hemos realizado algunos cambios en Makefile.PL. En este caso, hemos especificado una biblioteca adicional para enlazar en la biblioteca compartida de la extensión, la biblioteca matemática libm en este caso. Hablaremos más adelante sobre cómo escribir XSUBs que puedan llamar a todas las rutinas de una biblioteca.
  • El valor de la función no se devuelve como valor de retorno de la función, sino cambiando el valor de la variable que se pasó a la función. Podrías haberlo adivinado al ver que el valor de retorno de `round` es de tipo "void".

Parámetros de entrada y salida

Especificas los parámetros que se pasarán a la XSUB en la(s) línea(s) después de declarar el valor de retorno y el nombre de la función. Cada línea de parámetro de entrada comienza con un espacio opcional y puede tener un punto y coma final opcional.

La lista de parámetros de salida se encuentra al final de la función, justo después de la directiva OUTPUT:. El uso de RETVAL le dice a Perl que deseas enviar este valor como el valor de retorno de la función XSUB. En el Ejemplo 3, queríamos que el "valor de retorno" se colocara en la variable original que pasamos, por lo que la listamos (y no RETVAL) en la sección OUTPUT:.

El Programa XSUBPP

El programa xsubpp toma el código XS en el archivo .xs y lo traduce a código C, colocándolo en un archivo cuyo sufijo es .c. El código C creado hace un uso intensivo de las funciones C dentro de Perl.

El Archivo TYPEMAP

El programa xsubpp utiliza reglas para convertir de los tipos de datos de Perl (escalar, array, etc.) a los tipos de datos de C (int, char, etc.). Estas reglas se almacenan en el archivo typemap ($PERLLIB/ExtUtils/typemap). Hay una breve discusión a continuación, pero todos los detalles se pueden encontrar en perlxstypemap. Si tienes una versión de perl lo suficientemente nueva (5.16 y posteriores) o un XS actualizado

Typemaps

Si tiene el compilador ("ExtUtils::ParseXS" 3.13_01 o mejor), puede incrustar typemaps en su XS en lugar de escribir archivos separados. De cualquier manera, esta cosa de typemap se divide en tres partes:

La primera sección mapea varios tipos de datos C a un nombre, que se corresponde en cierta medida con los diversos tipos de Perl. La segunda sección contiene código C que xsubpp utiliza para manejar los parámetros de entrada. La tercera sección contiene código C que xsubpp utiliza para manejar los parámetros de salida.

Echemos un vistazo a una parte del archivo .c creado para nuestra extensión. El nombre del archivo es Mytest.c:

XS(XS_Mytest_round)
{
    dXSARGS;
    if (items != 1)
        Perl_croak(aTHX_ "Usage: Mytest::round(arg)");
    PERL_UNUSED_VAR(cv); /* -W */
    {
        double  arg = (double)SvNV(ST(0));      /* XXXXX */
        if (arg > 0.0) {
                arg = floor(arg + 0.5);
        } else if (arg < 0.0) {
                arg = ceil(arg - 0.5);
        } else {
                arg = 0.0;
        }
        sv_setnv(ST(0), (double)arg);   /* XXXXX */
        SvSETMAGIC(ST(0));
    }
    XSRETURN_EMPTY;
}

Observe las dos líneas comentadas con "XXXXX". Si revisa la primera parte del archivo typemap (o sección), verá que los dobles son del tipo T_DOUBLE. En la parte INPUT del typemap, a un argumento que es T_DOUBLE se le asigna la variable arg llamando a la rutina SvNV sobre algo, luego convirtiéndolo a double, luego asignándolo a la variable arg. De manera similar, en la sección OUTPUT, una vez que arg tiene su valor final, se pasa a la función sv_setnv para ser devuelto a la subrutina que llama. Estas dos funciones se explican en perlguts; hablaremos más adelante sobre lo que significa "ST(0)" en la sección de la pila de argumentos.

Advertencia sobre Argumentos de Salida

En general, no es una buena idea escribir extensiones que modifiquen sus parámetros de entrada, como en el Ejemplo 3. En su lugar, debería devolver varios valores en un array y dejar que el llamador los maneje (lo haremos en un ejemplo posterior). Sin embargo, para acomodar mejor la llamada a rutinas C preexistentes, que a menudo modifican sus parámetros de entrada, este comportamiento se tolera.

EJEMPLO 4

En este ejemplo, comenzaremos a escribir XSUBs que interactuarán con bibliotecas C predefinidas. Para empezar, construiremos una pequeña biblioteca propia, luego dejaremos que h2xs escriba nuestros archivos .pm y .xs por nosotros.

Cree un nuevo directorio llamado Mytest2 al mismo nivel que el directorio Mytest. En el directorio Mytest2, cree otro directorio llamado mylib y navegue hasta ese directorio.

Aquí crearemos algunos archivos que generarán una biblioteca de prueba. Estos incluirán un archivo fuente C y un archivo de encabezado. También crearemos un Makefile.PL en este directorio. Luego nos aseguraremos de que la ejecución de make en el nivel Mytest2 ejecute automáticamente este archivo Makefile.PL y el Makefile resultante.

En el directorio mylib, cree un archivo mylib.h que se vea así:

#define TESTVAL 4
extern double   foo(int, long, const char*);

También cree un archivo mylib.c que se vea así:

#include <stdlib.h>
#include "mylib.h"
double
foo(int a, long b, const char *c)
{
        return (a + b + atof(c) + TESTVAL);
}

Y finalmente cree un archivo Makefile.PL que se vea así:

use ExtUtils::MakeMaker;
$Verbose = 1;
WriteMakefile(
    NAME  => 'Mytest2::mylib',
    SKIP  => [qw(all static static_lib dynamic dynamic_lib)],
    clean => {'FILES' => 'libmylib$(LIB_EXT)'},
);
sub MY::top_targets {
        '
all :: static
pure_all :: static
static ::       libmylib$(LIB_EXT)
libmylib$(LIB_EXT): $(O_FILES)
        $(AR) cr libmylib$(LIB_EXT) $(O_FILES)
        $(RANLIB) libmylib$(LIB_EXT)
';
}

Asegúrese de usar una tabulación y no espacios en las líneas que comienzan con "$(AR)" y "$(RANLIB)". Make no funcionará correctamente si utiliza espacios. También se ha informado que el argumento "cr" para $(AR) no es necesario en sistemas Win32.

Ahora crearemos los archivos principales del nivel superior de Mytest2. Cambie al directorio anterior a Mytest2 y ejecute el siguiente comando:

% h2xs -O -n Mytest2 Mytest2/mylib/mylib.h

Esto imprimirá una advertencia sobre la sobrescritura de Mytest2, pero está bien. Nuestros archivos están almacenados en Mytest2/mylib y no se verán afectados.

El Makefile.PL normal que genera h2xs no conoce el directorio mylib. Necesitamos decirle que hay un subdirectorio y que generaremos una biblioteca en él. Agreguemos el argumento MYEXTLIB a la llamada WriteMakefile para que se vea así:

WriteMakefile(
    NAME         => 'Mytest2',
    VERSION_FROM => 'Mytest2.pm', # encuentra $VERSION
    LIBS         => [''],   # ej., '-lm'
    DEFINE       => '',     # ej., '-DHAVE_SOMETHING'
    INC          => '',     # ej., '-I/usr/include/other'
    MYEXTLIB     => 'mylib/libmylib$(LIB_EXT)',
);

y luego al final agregue una subrutina (que reemplazará la subrutina preexistente). ¡Recuerde usar un carácter de tabulación para indentar la línea que comienza con "cd"!

sub MY::postamble {
'
$(MYEXTLIB): mylib/Makefile
        cd mylib && $(MAKE) $(PASSTHRU)
';
}

También corrijamos el archivo MANIFEST agregando las siguientes tres líneas:

mylib/Makefile.PL
mylib/mylib.c
mylib/mylib.h

Para mantener nuestro espacio de nombres agradable y sin contaminar, edite el archivo .pm y cambie la variable @EXPORT a @EXPORT_OK. Finalmente, en el archivo .xs, edite la línea #include para que diga:

#include "mylib/mylib.h"

Y también agregue la siguiente definición de función al final del archivo .xs:

double
foo(a,b,c)
        int             a
        long            b
        const char *    c
    OUTPUT:
        RETVAL

Ahora también necesitamos crear un typemap porque el Perl predeterminado actualmente no admite el tipo "const char *". Incluya una nueva sección TYPEMAP en su código XS antes de la función anterior:

TYPEMAP: <<END
const char *    T_PV
END

Ahora ejecute perl en el Makefile.PL de nivel superior. Observe que también creó un Makefile en el directorio mylib. Ejecute make y observe que navega al directorio mylib y ejecuta make allí también.

Ahora edite el script Mytest2.t y cambie el número de pruebas a "5", y agregue las siguientes líneas al final del script:

is( Mytest2::foo( 1, 2, "Hello, world!" ), 7 );
is( Mytest2::foo( 1, 2, "0.0" ),           7 );
ok( abs( Mytest2::foo( 0, 0, "-3.4" ) - 0.6 ) <= 0.01 );

(Al tratar con comparaciones de punto flotante, es mejor no verificar la igualdad, sino que la diferencia entre el resultado esperado y el real esté por debajo de una cierta cantidad (llamada épsilon) que en este caso es 0.01)

Ejecute ""make test"" y todo debería estar bien. Hay algunas advertencias sobre pruebas faltantes para la extensión Mytest2::mylib, pero puede ignorarlas.

¿Qué ha pasado aquí?

A diferencia de ejemplos anteriores, hemos ejecutado h2xs en un archivo de inclusión real. Esto ha provocado que aparezcan algunas mejoras adicionales tanto en los archivos .pm como en los .xs.

  • En el archivo .xs, ahora hay una directiva #include con la ruta absoluta al archivo de encabezado mylib.h. Cambiamos esto a una ruta relativa para poder mover el directorio de extensión si quisiéramos.
  • Ahora hay algo de código C nuevo que se ha agregado al archivo .xs. El propósito de la rutina "constant" es hacer que los valores que están #define'd en el archivo de encabezado sean accesibles por el script Perl (llamando a "TESTVAL" o &Mytest2::TESTVAL). También hay código XS para permitir llamadas a la rutina "constant".
  • El archivo .pm originalmente exportó el nombre "TESTVAL" en el array @EXPORT. Esto podría generar conflictos de nombres. Una buena regla general es que si el #define solo será utilizado por las propias rutinas C, y no por el usuario, deben eliminarse del array @EXPORT. Alternativamente, si no le importa usar el "nombre completamente calificado" de una variable, podría mover la mayoría o todos los elementos del array @EXPORT al array @EXPORT_OK.
  • Si nuestro archivo de inclusión hubiera contenido directivas #include, estas no habrían sido procesadas por h2xs. No hay una buena solución para esto en este momento.
  • También le hemos informado a Perl sobre la biblioteca que construimos en el subdirectorio mylib. Eso solo requirió la adición de la variable "MYEXTLIB" a la llamada WriteMakefile y el reemplazo de la subrutina postamble para navegar al subdirectorio y ejecutar make. El Makefile.PL para la biblioteca es un poco más complicado, pero no excesivamente. Nuevamente reemplazamos la subrutina postamble para insertar nuestro propio código. Este código simplemente especificó que la biblioteca que se creará aquí era una biblioteca de archivo estática (en contraposición a una biblioteca cargable dinámicamente) y proporcionó los comandos para construirla.

Anatomía del archivo .xs

El archivo .xs del "EJEMPLO 4" contenía algunos elementos nuevos. Para comprender el significado de estos elementos, preste atención a la línea que dice

MODULE = Mytest2                PACKAGE = Mytest2

Cualquier cosa antes de esta línea es código C simple que describe qué encabezados incluir y define algunas funciones de conveniencia. No se realizan traducciones en esta parte, aparte de omitir la documentación POD incrustada (ver perlpod), va tal cual al archivo C de salida generado.

Cualquier cosa después de esta línea es la descripción de las funciones XSUB. Estas descripciones son traducidas por xsubpp a código C que implementa estas funciones utilizando convenciones de llamada de Perl, y que hace que estas funciones sean visibles desde el intérprete de Perl.

Preste especial atención a la función "constant". Este nombre aparece dos veces en el archivo .xs generado: una vez en la primera parte, como una función C estática, y luego otra vez en la segunda parte, cuando se define una interfaz XSUB para esta función C estática.

Esto es bastante típico para los archivos .xs: por lo general, el archivo .xs proporciona una interfaz a una función C existente. Luego, esta función C se define en algún lugar (ya sea en una biblioteca externa, o en la primera parte de .xs f

ile), y una interfaz Perl para esta función (es decir, "pegamento Perl") se describe en la segunda parte del archivo .xs. La situación en el "EJEMPLO 1", "EJEMPLO 2" y "EJEMPLO 3", cuando todo el trabajo se realiza dentro del "pegamento Perl", es más bien una excepción que la regla.

Sacando la grasa de los XSUBs

En el "EJEMPLO 4", la segunda parte del archivo .xs contenía la siguiente descripción de un XSUB:

double
foo(a,b,c)
        int             a
        long            b
        const char *    c
    OUTPUT:
        RETVAL

Nótese que, en contraste con el "EJEMPLO 1", el "EJEMPLO 2" y el "EJEMPLO 3", esta descripción no contiene el *código* real de lo que se hace durante una llamada a la función Perl foo(). Para entender lo que sucede aquí, se puede añadir una sección CODE a este XSUB:

double
foo(a,b,c)
        int             a
        long            b
        const char *    c
    CODE:
        RETVAL = foo(a,b,c);
    OUTPUT:
        RETVAL

Sin embargo, estos dos XSUBs proporcionan código C generado casi idéntico: el compilador xsubpp es lo suficientemente inteligente como para deducir la sección "CODE:" de las dos primeras líneas de la descripción del XSUB. ¿Y qué hay de la sección "OUTPUT:"? ¡De hecho, es absolutamente lo mismo! La sección "OUTPUT:" también se puede eliminar, *siempre y cuando* no se especifique una sección "CODE:" o "PPCODE:": xsubpp puede ver que necesita generar una sección de llamada a función y también generará automáticamente la sección OUTPUT. Por lo tanto, se puede acortar el XSUB a:

double
foo(a,b,c)
        int             a
        long            b
        const char *    c

¿Podemos hacer lo mismo con un XSUB?

int
is_even(input)
        int     input
    CODE:
        RETVAL = (input % 2 == 0);
    OUTPUT:
        RETVAL

del "EJEMPLO 2"? Para hacer esto, se necesita definir una función C "int is_even(int input)". Como vimos en "Anatomía de un archivo .xs", un lugar adecuado para esta definición está en la primera parte del archivo .xs. De hecho, una función C

int
is_even(int arg)
{
        return (arg % 2 == 0);
}

es probablemente excesiva para esto. Algo tan simple como una "#define" también servirá:

#define is_even(arg)    ((arg) % 2 == 0)

Después de tener esto en la primera parte del archivo .xs, la parte del "pegamento Perl" se simplifica a:

int
is_even(input)
        int     input

Esta técnica de separar la parte del pegamento de la parte del caballo de batalla tiene evidentes compensaciones: si desea cambiar una interfaz Perl, necesita cambiar dos lugares en su código. Sin embargo, elimina mucha suciedad y hace que la parte del caballo de batalla sea independiente de las idiosincrasias de la convención de llamadas de Perl. (De hecho, no hay nada específico de Perl en la descripción anterior; una versión diferente de xsubpp podría haberlo traducido también a pegamento TCL o pegamento Python).

Más sobre argumentos de XSUB

Con la finalización del Ejemplo 4, ahora tenemos una forma fácil de simular algunas bibliotecas de la vida real cuyas interfaces pueden no ser las más limpias del mundo. Ahora continuaremos con una discusión de los argumentos pasados al compilador xsubpp.

Cuando especifica argumentos para las rutinas en el archivo .xs, está realmente pasando tres piezas de información por cada argumento listado. La primera pieza es el orden de ese argumento en relación con los demás (primero, segundo, etc.). La segunda es el tipo de argumento y consiste en la declaración del tipo del argumento (por ejemplo, int, char*, etc.). La tercera pieza es la convención de llamada para el argumento en la llamada a la función de la biblioteca.

Mientras que Perl pasa argumentos a funciones por referencia, C pasa argumentos por valor; para implementar una función C que modifica los datos de uno de los "argumentos", el argumento real de esta función C sería un puntero a los datos. Por lo tanto, dos funciones C con las declaraciones

int string_length(char *s);
int upper_case_char(char *cp);

pueden tener semánticas completamente diferentes: la primera puede inspeccionar un array de caracteres apuntado por s, y la segunda puede desreferenciar inmediatamente "cp" y manipular solo *cp (usando el valor de retorno como, por ejemplo, un indicador de éxito). Desde Perl se usarían estas funciones de manera completamente diferente.

Uno transmite esta información a xsubpp reemplazando el "*" antes del argumento por "&". "&" significa que el argumento debe pasarse a una función de biblioteca por su dirección. Las dos funciones anteriores se pueden convertir a XSUB como:

int
string_length(s)
        char *  s
int
upper_case_char(cp)
        char    &cp

Por ejemplo, considere:

int
foo(a,b)
        char    &a
        char *  b

El primer argumento Perl a esta función se trataría como un char y se asignaría a la variable a, y su dirección se pasaría a la función foo. El segundo argumento Perl se trataría como un puntero a cadena y se asignaría a la variable b. El *valor* de b se pasaría a la función foo. La llamada real a la función foo que xsubpp genera se vería así:

foo(&a, b);

xsubpp analizará las siguientes listas de argumentos de función de manera idéntica:

char    &a
char&a
char    & a

Sin embargo, para ayudar a facilitar la comprensión, se sugiere que coloque un "&" junto al nombre de la variable y alejado del tipo de variable, y coloque un "*" cerca del tipo de variable, pero alejado del nombre de la variable (como en la llamada a foo anterior). Al hacerlo, es fácil entender exactamente qué se pasará a la función C; será lo que sea que esté en la "última columna".

Debe hacer grandes esfuerzos para intentar pasar a la función el tipo de variable que desea, cuando sea posible. Le ahorrará muchos problemas a largo plazo.

La Pila de Argumentos

Si observamos cualquier código C generado por cualquiera de los ejemplos, excepto el ejemplo 1, notará una serie de referencias a ST(n), donde n suele ser 0. "ST" es en realidad una macro que apunta al n-ésimo argumento en la pila de argumentos. ST(0) es, por lo tanto, el primer argumento en la pila y, por lo tanto, el primer argumento pasado al XSUB, ST(1) es el segundo argumento, y así sucesivamente.

Cuando enumera los argumentos para el XSUB en el archivo .xs, eso le dice a xsubpp qué argumento corresponde a cuál de la pila de argumentos (es decir, el primero listado es el primer argumento, y así sucesivamente). Invita al desastre si no los enumera en el mismo orden en que la función los espera.

Los valores reales en la pila de argumentos son punteros a los valores pasados. Cuando se lista un argumento como valor de SALIDA, su valor correspondiente en la pila (es decir, ST(0) si fue el primer argumento) se modifica. Puede verificar esto mirando el código C generado para el Ejemplo 3. El código para la rutina XSUB round() contiene líneas que se ven así:

double  arg = (double)SvNV(ST(0));
/* Redondea el contenido de la variable arg */
sv_setnv(ST(0), (double)arg);

La variable arg se inicializa tomando el valor de ST(0), luego se almacena de nuevo en ST(0) al final de la rutina.

Los XSUBs también pueden devolver listas, no solo escalares. Esto debe hacerse manipulando los valores de la pila ST(0), ST(1), etc., de una manera sutilmente diferente. Consulte perlxs para obtener detalles.

Los XSUBs también pueden evitar la conversión automática de argumentos de función Perl a argumentos de función C. Consulte perlxs para obtener detalles. Algunas personas prefieren la conversión manual inspeccionando ST(i) incluso en los casos en que la conversión automática funciona, argumentando que esto aclara la lógica de una llamada XSUB. Compare con "Sacando la grasa de los XSUBs" para una compensación similar de una separación completa de las partes de "pegamento Perl" y "caballo de batalla" de un XSUB.

Si bien los expertos pueden discutir sobre estos modismos, un novato en las entrañas de Perl puede preferir una forma que sea lo menos específica posible de las entrañas de Perl, lo que significa conversión automática y generación de llamadas automática, como en "Sacando la grasa de los XSUBs". Este enfoque tiene el beneficio adicional de proteger al escritor del XSUB de futuros cambios en la API de Perl.

Extender tu Extensión

A veces, es posible que desee proporcionar métodos o subrutinas adicionales para ayudar a simplificar o hacer que la interfaz entre Perl y su extensión sea más fácil de entender. Estas rutinas deben residir en el archivo .pm. Si se cargan automáticamente cuando se carga la extensión misma o solo se cargan cuando se llaman depende de dónde se coloque la definición de la subrutina en el archivo .pm. También puede consultar AutoLoader para conocer una forma alternativa de almacenar y cargar sus subrutinas adicionales.

Documentar tu Extensión

No hay ninguna excusa para no documentar tu extensión. La documentación pertenece al archivo .pm. Este archivo se alimentará a pod2man, y la documentación incrustada se convertirá al formato de página man, y luego se colocará en el directorio blib. Se copiará al directorio de páginas man de Perl cuando se instale la extensión.

Puede intercalar documentación y código Perl dentro del archivo .pm. De hecho, si desea utilizar la carga automática de métodos, debe hacerlo, como explica el comentario dentro del archivo .pm.

Consulte perlpod para obtener más información sobre el formato pod.

Instalar tu Extensión

Una vez que tu extensión esté completa y pase todas sus pruebas, instalarla es muy simple: simplemente ejecuta "make install". Necesitarás tener permiso de escritura en los directorios donde está instalado Perl, o pedirle a tu administrador del sistema que ejecute make por ti.

Alternativamente, puedes especificar el directorio exacto para colocar el extension's files colocando un "PREFIX=/directorio/destino" después de make install (o entre make e install si tienes una versión de make obsoleta). Esto puede ser muy útil si estás compilando una extensión que eventualmente se distribuirá a múltiples sistemas. Puedes archivar los archivos en el directorio de destino y distribuirlos a tus sistemas de destino.

EJEMPLO 5

En este ejemplo, haremos más trabajo con la pila de argumentos. Los ejemplos anteriores solo han devuelto un único valor. Ahora crearemos una extensión que devuelva un array.

Esta extensión está muy orientada a Unix (struct statfs y la llamada al sistema statfs). Si no estás ejecutando en un sistema Unix, puedes sustituir statfs por cualquier otra función que devuelva múltiples valores, puedes codificar valores para que sean devueltos al llamante (aunque esto será un poco más difícil de probar el caso de error), o puedes simplemente no hacer este ejemplo. Si cambias el XSUB, asegúrate de arreglar los casos de prueba para que coincidan con los cambios.

Regresa al directorio Mytest y agrega el siguiente código al final de Mytest.xs:

void
statfs(path)
        char *  path
    INIT:
        int i;
        struct statfs buf;
    PPCODE:
        i = statfs(path, &buf);
        if (i == 0) {
                XPUSHs(sv_2mortal(newSVnv(buf.f_bavail)));
                XPUSHs(sv_2mortal(newSVnv(buf.f_bfree)));
                XPUSHs(sv_2mortal(newSVnv(buf.f_blocks)));
                XPUSHs(sv_2mortal(newSVnv(buf.f_bsize)));
                XPUSHs(sv_2mortal(newSVnv(buf.f_ffree)));
                XPUSHs(sv_2mortal(newSVnv(buf.f_files)));
                XPUSHs(sv_2mortal(newSVnv(buf.f_type)));
        } else {
                XPUSHs(sv_2mortal(newSVnv(errno)));
        }

También necesitarás agregar el siguiente código al principio del archivo .xs, justo después de la inclusión de "XSUB.h":

#include <sys/vfs.h>

Agrega también el siguiente segmento de código a Mytest.t mientras incrementas las pruebas "9" a "11":

my @a;
    @a = Mytest::statfs("/blech");
    ok( scalar(@a) == 1 && $a[0] == 2 );
    @a = Mytest::statfs("/");
    is( scalar(@a), 7 );

Novedades en este ejemplo

Este ejemplo añadió bastantes conceptos nuevos. Los veremos uno por uno.

  • La directiva INIT: contiene código que se colocará inmediatamente después de que la pila de argumentos sea decodificada. C no permite declaraciones de variables en ubicaciones arbitrarias dentro de una función, por lo que esta es generalmente la mejor manera de declarar variables locales necesarias para el XSUB. (Alternativamente, se podría poner toda la sección "PPCODE:" entre llaves, y poner estas declaraciones en la parte superior.)
  • Esta rutina también devuelve un número diferente de argumentos dependiendo del éxito o fracaso de la llamada a statfs. Si hay un error, el número de error se devuelve como un array de un solo elemento. Si la llamada es exitosa, se devuelve un array de 7 elementos. Dado que solo se pasa un argumento a esta función, necesitamos espacio en la pila para contener los 7 valores que pueden ser devueltos.

    Hacemos esto usando la directiva PPCODE:, en lugar de la directiva CODE:. Esto le dice a xsubpp que gestionaremos nosotros mismos los valores de retorno que se colocarán en la pila de argumentos.

  • Cuando queremos colocar valores a devolver al llamante en la pila, usamos la serie de macros que comienzan con "XPUSH". Hay cinco versiones diferentes, para colocar enteros, enteros sin signo, doubles, cadenas y escalares de Perl en la pila. En nuestro ejemplo, colocamos un escalar de Perl en la pila. (De hecho, esta es la única macro que se puede usar para devolver múltiples valores.)

    Las macros XPUSH* extenderán automáticamente la pila de retorno para evitar que se desborde. Empujas valores a la pila en el orden en que deseas que sean vistos por el programa llamante.

  • Los valores que se empujan en la pila de retorno del XSUB son en realidad SV's mortales. Se hacen mortales para que una vez que los valores sean copiados por el programa llamante, los SV's que contenían los valores de retorno puedan ser desasignados. Si no fueran mortales, continuarían existiendo después de que la rutina XSUB regresara, pero no serían accesibles. Esto es una fuga de memoria.
  • Si estuviéramos interesados en el rendimiento, no en la compacidad del código, en la rama de éxito no usaríamos las macros "XPUSHs", sino las macros "PUSHs", y pre-extenderíamos la pila antes de empujar los valores de retorno: 
    EXTEND(SP, 7);

    La contrapartida es que uno necesita calcular el número de valores de retorno por adelantado (aunque extender demasiado la pila típicamente no perjudicará nada más que el consumo de memoria).

    Del mismo modo, en la rama de fallo podríamos usar "PUSHs" *sin* extender la pila: la referencia a la función de Perl llega a un XSUB en la pila, por lo tanto la pila es *siempre* lo suficientemente grande como para tomar un valor de retorno.

EJEMPLO 6

En este ejemplo, aceptaremos una referencia a un array como parámetro de entrada y devolveremos una referencia a un array de hashes. Esto demostrará la manipulación de tipos de datos complejos de Perl desde un XSUB.

Esta extensión es algo artificial. Se basa en el código del ejemplo anterior. Llama a la función statfs múltiples veces, aceptando una referencia a un array de nombres de archivo como entrada, y devolviendo una referencia a un array de hashes que contiene los datos para cada uno de los sistemas de archivos.

Regresa al directorio Mytest y agrega el siguiente código al final de Mytest.xs:

SV *
multi_statfs(paths)
        SV * paths
    INIT:
        AV * results;
        SSize_t numpaths = 0, n;
        int i;
        struct statfs buf;
        SvGETMAGIC(paths);
        if ((!SvROK(paths))
            || (SvTYPE(SvRV(paths)) != SVt_PVAV)
            || ((numpaths = av_top_index((AV *)SvRV(paths))) < 0))
        {
            XSRETURN_UNDEF;
        }
        results = (AV *)sv_2mortal((SV *)newAV());
    CODE:
        for (n = 0; n <= numpaths; n++) {
            HV * rh;
            STRLEN l;
            SV * path = *av_fetch((AV *)SvRV(paths), n, 0);
            char * fn = SvPVbyte(path, l);
            i = statfs(fn, &buf);
            if (i != 0) {
                av_push(results, newSVnv(errno));
                continue;
            }
            rh = (HV *)sv_2mortal((SV *)newHV());
            hv_store(rh, "f_bavail", 8, newSVnv(buf.f_bavail), 0);
            hv_store(rh, "f_bfree",  7, newSVnv(buf.f_bfree),  0);
            hv_store(rh, "f_blocks", 8, newSVnv(buf.f_blocks), 0);
            hv_store(rh, "f_bsize",  7, newSVnv(buf.f_bsize),  0);
            hv_store(rh, "f_ffree",  7, newSVnv(buf.f_ffree),  0);
            hv_store(rh, "f_files",  7, newSVnv(buf.f_files),  0);
            hv_store(rh, "f_type",   6, newSVnv(buf.f_type),   0);
            av_push(results, newRV_inc((SV *)rh));
        }
        RETVAL = newRV_inc((SV *)results);
    OUTPUT:
        RETVAL

Y agrega el siguiente código a Mytest.t, mientras incrementas las pruebas "11" a "13":

my $results = Mytest::multi_statfs([ '/', '/blech' ]);
ok( ref $results->[0] );
ok( ! ref $results->[1] );

Novedades en este ejemplo

Aquí se introducen una serie de nuevos conceptos, descritos a continuación:

  • Esta función no utiliza un typemap. En su lugar, la declaramos como que acepta un parámetro SV* (escalar) y devuelve un valor SV*, y nos encargamos de poblar estos escalares dentro del código. Dado que solo devolvemos un valor, no necesitamos una directiva "PPCODE:"; en su lugar, usamos las directivas "CODE:" y "OUTPUT:".
  • Al tratar con referencias, es importante manejarlas con precaución. El bloque "INIT:" primero llama a SvGETMAGIC(paths), en caso de que paths sea una variable enlazada. Luego verifica que "SvROK" devuelva verdadero, lo que indica que paths es una referencia válida. (Simplemente verificar "SvROK" no activará FETCH en una variable enlazada.) Luego verifica que el objeto referenciado por paths sea un array, usando "SvRV" para desenlazar paths, y "SvTYPE" para descubrir su tipo. Como prueba adicional, verifica que el array referenciado por paths no esté vacío, usando la función "av_top_index" (que devuelve -1 si el array está vacío). La macro XSRETURN_UNDEF se usa para abortar el XSUB y devolver el valor indefinido siempre que no se cumplan las tres condiciones.
  • Manipulamos varios arrays en este XSUB. Ten en cuenta que un array se representa internamente mediante un puntero AV*. Las funciones y macros para manipular arrays son similares a las funciones de Perl: "av_top_index" devuelve el índice más alto en un AV*, muy parecido a $#array; "av_fetch" recupera un único valor escalar de un array, dado su índice; "av_push" empuja un valor escalar al final del array, extendiendo automáticamente el array según sea necesario.

    Específicamente, leemos nombres de ruta uno por uno del array de entrada y almacenamos los resultados en un array de salida (results) en el mismo orden. Si statfs falla, el elemento empujado al array de retorno es el valor de errno después del fallo. Si statfs tiene éxito, el valor empujado al array de retorno es una referencia a un hash que contiene parte de la información en la estructura statfs.

    Al igual que con la pila de retorno, sería posible (y una pequeña ganancia de rendimiento) pre-extender el array de retorno antes de empujar datos en él, ya que sabemos cuántos elementos devolveremos:

    av_extend(results, numpaths);
  • Realizamos solo una operación de hash en esta función, que es almacenar un nuevo escalar bajo una clave usando "hv_store". Un hash se representa mediante un puntero HV*. Al igual que los arrays, las funciones para manipular hashes desde un XSUB reflejan la funcionalidad disponible desde Perl. Consulte perlguts y perlapi para obtener detalles.
  • Para crear una referencia, usamos la función "newRV_inc". Tenga en cuenta que puede convertir un AV* o un HV* al tipo SV* en este caso (y en muchos otros). Esto le permite tomar referencias a arrays, hashes y escalares con la misma función. A la inversa, la función "SvRV" siempre devuelve un SV*, que puede necesitar ser convertido al tipo apropiado si
es algo distinto de un escalar (compruébalo con "SvTYPE").
  • En este punto, xsubpp realiza muy poco trabajo: las diferencias entre Mytest.xs y Mytest.c son mínimas.

    EJEMPLO 9 Pasando archivos abiertos a XSes

    Podrías pensar que pasar archivos a un XS es difícil, con todos los typeglobs y esas cosas. Bueno, no lo es.

    Supongamos que por alguna extraña razón necesitamos una envoltura alrededor de la función estándar de la biblioteca C fputs(). Esto es todo lo que necesitamos:

    #define PERLIO_NOT_STDIO 0  /* Para coexistencia con stdio solamente */
#define PERL_NO_GET_CONTEXT /* Esto es más eficiente */
#include "EXTERN.h"
#include "perl.h"
#include "XSUB.h"
#include <stdio.h>
int
fputs(s, stream)
  char *          s
  FILE *          stream

    El trabajo real lo realiza el typemap estándar.

    Para más detalles, véase "Coexistencia con stdio" en perlapio.

    Pero pierdes toda la funcionalidad fina realizada por las capas perlio. Esto llama a la función stdio fputs(), que no sabe nada de ellas.

    El typemap estándar ofrece tres variantes de PerlIO *: "InputStream" (T_IN), "InOutStream" (T_INOUT) y "OutputStream" (T_OUT). Un "PerlIO *" desnudo se considera un T_INOUT. Si es importante en tu código (ver más abajo por qué podría serlo) #define o typedef uno de los nombres específicos y úsalo como argumento o tipo de resultado en tu archivo XS.

    El typemap estándar no contiene PerlIO * antes de perl 5.7, pero tiene las tres variantes de stream. Usar un PerlIO * directamente no es compatible con versiones anteriores a menos que proporciones tu propio typemap.

    Para streams que vienen *desde* perl, la principal diferencia es que "OutputStream" obtendrá el PerlIO * de salida, lo que puede marcar la diferencia en un socket. Como en nuestro ejemplo...

    Para streams que se entregan *a* perl, se crea un nuevo manejador de archivo (es decir, una referencia a un nuevo glob) y se asocia con el PerlIO * proporcionado. Si el estado de lectura/escritura del PerlIO * no es correcto, podrías obtener errores o advertencias cuando se utilice el manejador de archivo. Así que si abriste el PerlIO * como "w", realmente debería ser un "OutputStream"; si se abrió como "r", debería ser un "InputStream".

    Ahora, supongamos que quieres usar capas perlio en tu XS. Usaremos la función perlio PerlIO_puts() como ejemplo.

    En la parte C del archivo XS (antes de la primera línea MODULE) tienes

        #define OutputStream    PerlIO *
o
    typedef PerlIO *        OutputStream;

    Y este es el código XS:

    int
perlioputs(s, stream)
        char *          s
        OutputStream    stream
CODE:
        RETVAL = PerlIO_puts(stream, s);
OUTPUT:
        RETVAL

    Tenemos que usar una sección "CODE" porque PerlIO_puts() tiene los argumentos invertidos en comparación con fputs(), y queremos mantener los argumentos iguales.

    Queriendo explorar esto a fondo, queremos usar el stdio fputs() en un PerlIO *. Esto significa que tenemos que pedirle al sistema perlio un stdio "FILE *":

    int
perliofputs(s, stream)
        char *          s
        OutputStream    stream
PREINIT:
        FILE *fp = PerlIO_findFILE(stream);
CODE:
        if (fp != (FILE*) 0) {
                RETVAL = fputs(s, fp);
        } else {
                RETVAL = -1;
        }
OUTPUT:
        RETVAL

    Nota: PerlIO_findFILE() buscará en las capas una capa stdio. Si no encuentra una, llamará a PerlIO_exportFILE() para generar un nuevo stdio "FILE". Por favor, llama solo a PerlIO_exportFILE() si quieres un *nuevo* "FILE". Generará uno en cada llamada y añadirá una nueva capa stdio. Así que no la llames repetidamente en el mismo archivo. PerlIO_findFILE() recuperará la capa stdio una vez que haya sido generada por PerlIO_exportFILE().

    Esto se aplica solo al sistema perlio. Para versiones anteriores a 5.7, PerlIO_exportFILE() es equivalente a PerlIO_findFILE().

    Solución de problemas de estos Ejemplos

    Como se mencionó al principio de este documento, si tienes problemas con estas extensiones de ejemplo, puedes ver si alguna de las siguientes opciones te ayuda.

    • En versiones de 5.002 anteriores a la versión gamma, el script de prueba en el Ejemplo 1 no funcionará correctamente. Debes cambiar la línea "use lib" para que diga: 
      use lib './blib';
    • En versiones de 5.002 anteriores a la versión 5.002b1h, el archivo test.pl no era creado automáticamente por h2xs. Esto significa que no puedes decir "make test" para ejecutar el script de prueba. Necesitarás añadir la siguiente línea antes de la declaración "use extension": 
      use lib './blib';
    • En las versiones 5.000 y 5.001, en lugar de usar la línea anterior, necesitarás usar la siguiente línea: 
      BEGIN { unshift(@INC, "./blib") }
    • Este documento asume que el ejecutable llamado "perl" es Perl versión 5. Algunos sistemas pueden haber instalado Perl versión 5 como "perl5".
