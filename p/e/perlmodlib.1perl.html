NOMBRE

LA BIBLIOTECA DE MÓDULOS PERL

Muchos módulos se incluyen en la distribución de Perl. Se describen a continuación y todos terminan en .pm. Es posible que descubra archivos de biblioteca compilados (que normalmente terminan en .so) o pequeños fragmentos de módulos para ser cargados automáticamente (que terminan en .al); estos fueron generados automáticamente por el proceso de instalación. También puede descubrir archivos en el directorio de la biblioteca que terminan en .pl o .ph. Estas son bibliotecas antiguas que se suministran para que los programas antiguos que las usan sigan funcionando. Los archivos .pl se convertirán eventualmente en módulos estándar, y los archivos .ph creados por h2ph probablemente se convertirán en módulos de extensión creados por h2xs. (Algunos valores .ph ya pueden estar disponibles a través de los módulos POSIX, Errno o Fcntl.) El archivo pl2pm de la distribución puede ayudar en su conversión, pero es solo un proceso mecánico y, por lo tanto, está lejos de ser infalible.

Módulos Pragmáticos

Funcionan de forma similar a las directivas del compilador (pragmata) en el sentido de que tienden a afectar a la compilación de su programa, y por lo tanto, generalmente funcionarán bien solo cuando se utilicen dentro de un "use" o "no". La mayoría de estos tienen un alcance léxico, por lo que un BLOQUE interno puede contradecirlos diciendo:

no integer;
no strict 'refs';
no warnings;

lo cual dura hasta el final de ese BLOQUE.

Algunas pragmas tienen un alcance léxico, típicamente aquellas que afectan a la variable de pistas $^H. Otras afectan al paquete actual en su lugar, como "use vars" y "use subs", que le permiten pre-declarar variables o subrutinas dentro de un archivo particular en lugar de solo un bloque. Dichas declaraciones son efectivas para todo el archivo para el que fueron declaradas. No puede rescindirlas con "no vars" o "no subs".

    Módulos: Creación, Uso y Abuso

    (La siguiente sección se toma directamente del archivo de módulos de Tim Bunce, disponible en su sitio CPAN más cercano.)

    Perl implementa una clase usando un paquete, pero la presencia de un paquete no implica la presencia de una clase. Un paquete es solo un espacio de nombres. Una clase es un paquete que proporciona subrutinas que pueden usarse como métodos. Un método es solo una subrutina que espera, como su primer argumento, ya sea el nombre de un paquete (para llamadas "estáticas" o de clase), o una referencia a un paquete (para llamadas de instancia o de objeto).

    un método), o una referencia a algo (para métodos "virtuales").

    Un módulo es un archivo que (por convención) proporciona una clase del mismo nombre (sin el .pm), además de un método `import` en esa clase que puede ser llamado para obtener símbolos exportados. Este módulo puede implementar algunos de sus métodos cargando objetos dinámicos de C o C++, pero eso debería ser totalmente transparente para el usuario del módulo. Igualmente, el módulo podría configurar una función AUTOLOAD para cargar definiciones de subrutinas bajo demanda, pero esto también es transparente. Solo el archivo .pm es requerido. Consulte perlsub, perlobj y AutoLoader para más detalles sobre el mecanismo AUTOLOAD.

    Pautas para la Creación de Módulos

    • ¿Ya existen módulos similares de alguna forma?

      Si es así, intente reutilizar los módulos existentes, ya sea en su totalidad o heredando características útiles en una nueva clase. Si esto no es práctico, intente reunirse con los autores de los módulos para trabajar en la extensión o mejora de la funcionalidad de los módulos existentes. Un ejemplo perfecto es la plétora de paquetes en perl4 para tratar opciones de línea de comandos.

      Si está escribiendo un módulo para expandir un conjunto de módulos ya existente, coordine con el autor del paquete. Ayuda si sigue el mismo esquema de nombres y el mismo esquema de interacción de módulos que el autor original.

    • Intente diseñar el nuevo módulo para que sea fácil de extender y reutilizar.

      Intente usar "use warnings;" (o "use warnings qw(...);"). Recuerde que puede añadir "no warnings qw(...);" a bloques de código individuales que necesiten menos advertencias.

      Use referencias bendecidas. Use la forma de dos argumentos de `bless` para bendecir en el nombre de la clase dada como primer parámetro del constructor, por ejemplo:

      sub new {
    my $class = shift;
    return bless {}, $class;
}

      o incluso esto si desea que se use como un método estático o virtual.

      sub new {
    my $self  = shift;
    my $class = ref($self) || $self;
    return bless {}, $class;
}

      Pase arrays como referencias para poder añadir más parámetros más tarde (también es más rápido). Convierta funciones en métodos cuando sea apropiado. Divida métodos grandes en otros más pequeños y flexibles. Herede métodos de otros módulos si es apropiado.

      Evite pruebas de nombres de clase como: "die "Inválido" unless ref $ref eq 'FOO'". Generalmente, puede eliminar la parte "eq 'FOO'" sin ningún daño. ¡Deje que los objetos se cuiden solos! En general, evite nombres de clase codificados tanto como sea posible.

      Evite "$r->Class::func()" donde usar "@ISA=qw(... Class ...)" y "$r->func()" funcionaría.

      Use autosplit para que las funciones poco usadas o recién añadidas no sean una carga para los programas que no las usan. Añada funciones de prueba al módulo después de __END__ ya sea usando AutoSplit o diciendo:

      eval join('',<main::DATA>) || die $@ unless caller();

      ¿Pasa su módulo la prueba de 'subclase vacía'? Si dice "@SUBCLASS::ISA = qw(YOURCLASS);" sus aplicaciones deberían poder usar SUBCLASS de la misma manera que YOURCLASS. Por ejemplo, ¿su aplicación sigue funcionando si cambia: "$obj = YOURCLASS->new();" por: "$obj = SUBCLASS->new();"?

      Evite mantener información de estado en sus paquetes. Esto dificulta que otros paquetes la utilicen. Mantenga la información de estado en los objetos.

      Use siempre -w.

      Intente usar "use strict;" (o "use strict qw(...);"). Recuerde que puede añadir "no strict qw(...);" a bloques de código individuales que necesiten menos restricciones.

      Use siempre -w.

      Siga las pautas de perlstyle.

      Use siempre -w.

    • Algunas pautas de estilo sencillas

      El manual perlstyle que viene con Perl tiene muchos puntos útiles.

      El estilo de codificación es una cuestión de gusto personal. Mucha gente evoluciona su estilo a lo largo de varios años a medida que aprende qué le ayuda a escribir y mantener buen código. Aquí hay un conjunto de sugerencias variadas que parecen ser ampliamente utilizadas por desarrolladores experimentados:

      Use guiones bajos para separar palabras. Generalmente es más fácil leer $nombres_de_variables_asi que $NombresDeVariablesAsi, especialmente para los que no son hablantes nativos de inglés. También es una regla simple que funciona consistentemente con NOMBRES_DE_VARIABLES_ASI.

      Los nombres de paquetes/módulos son una excepción a esta regla. Perl reserva informalmente nombres de módulos en minúsculas para módulos 'pragma' como `integer` y `strict`. Otros módulos normalmente comienzan con una letra mayúscula y usan mayúsculas y minúsculas mixtas sin guiones bajos (necesitan ser cortos y portátiles).

      Puede encontrar útil usar mayúsculas y minúsculas para indicar el alcance o la naturaleza de una variable. Por ejemplo:

      $TODO_EN_MAYUSCULAS   solo constantes (cuidado con colisiones con variables de Perl)
$Alguna_Mayuscula      global/estático de todo el paquete
$sin_mayusculas        variables `my()` o `local()` en alcance de función

      Los nombres de funciones y métodos parecen funcionar mejor en minúsculas. Ej: "$obj->as_string()".

      Puede usar un guion bajo inicial para indicar que una variable o función no debe usarse fuera del paquete que la definió.

    • Seleccione qué exportar.

      ¡NO exporte nombres de métodos!

      ¡NO exporte nada más por defecto sin una buena razón!

      Las exportaciones contaminan el espacio de nombres del usuario del módulo. Si debe exportar, intente usar @EXPORT_OK en lugar de @EXPORT y evite nombres cortos o comunes para reducir el riesgo de colisiones de nombres.

      Generalmente, cualquier cosa no exportada todavía es accesible desde fuera del módulo usando la sintaxis `ModuleName::nombre_del_item` (o "$ref_bendecido->metodo"). Por convención, puede usar un guion bajo inicial en los nombres para indicar informalmente que son 'internos' y no para uso público.

      (En realidad, es posible obtener funciones privadas diciendo: "my $subref = sub { ... }; &$subref;". Pero no hay forma de llamarla directamente como un método, porque un método debe tener un nombre en la tabla de símbolos.)

      Como regla general, si el módulo está intentando ser orientado a objetos, entonces no exporte nada. Si es solo una colección de funciones, entonces @EXPORT_OK cualquier cosa, pero use @EXPORT con precaución.

    • Seleccione un nombre para el módulo.

      Este nombre debe ser tan descriptivo, preciso y completo como sea posible. Evite cualquier riesgo de ambigüedad. Siempre intente usar dos o más palabras completas. Generalmente, el nombre debe reflejar lo especial de lo que hace el módulo, en lugar de cómo lo hace. Por favor, use nombres de módulos anidados para agrupar informalmente o categorizar un módulo. Debería haber una muy buena razón para que un módulo no tenga un nombre anidado. Los nombres de los módulos deben comenzar con una letra mayúscula.

      Tener 57 módulos llamados todos `Sort` no facilitará la vida a nadie (aunque tener 23 llamados `Sort::Quick` es solo marginalmente mejor :-). Imagine a alguien intentando instalar su módulo junto con muchos otros.

      Si está desarrollando un conjunto de módulos/clases relacionados, es una buena práctica usar clases anidadas con un prefijo común, ya que esto evitará colisiones de nombres. Por ejemplo: `Xyz::Control`, `Xyz::View`, `Xyz::Model`, etc. Use los módulos en esta lista como guía de nombres.

      Si añade un nuevo módulo a un conjunto, siga los estándares del autor original para nombrar módulos y la interfaz a los métodos en esos módulos.

      Si desarrolla módulos para uso interno privado o específico del proyecto, que nunca se publicarán, entonces debe asegurarse de que sus nombres no colisionarán con ningún módulo público futuro. Puede hacer esto usando la categoría reservada `Local::*` o usando un nombre de categoría que incluya un guion bajo como `Foo_Corp::*`.

      Para ser portable, cada componente de un nombre de módulo debe limitarse a 11 caracteres. Si puede usarse en MS-DOS, intente asegurarse de que cada uno sea único en los primeros 8 caracteres. Los módulos anidados facilitan esto.

      Para obtener orientación adicional sobre la nomenclatura de módulos, consulte:

      https://pause.perl.org/pause/query?ACTION=pause_namingmodules

      o envíe un correo electrónico a la lista de correo <module-authors@perl.org>.

    • ¿Lo ha hecho bien?

      ¿Cómo sabe que ha tomado las decisiones correctas? ¿Ha elegido un diseño de interfaz que causará problemas más adelante? ¿Ha elegido el nombre más apropiado? ¿Tiene alguna pregunta?

      La mejor manera de saberlo con seguridad, y de obtener muchas sugerencias útiles, es preguntar a alguien que sepa. La lista de correo <module-authors@perl.org> es útil para este propósito; también es accesible a través de la interfaz de noticias como perl.module-authors en nntp.perl.org.

      Todo lo que necesita hacer es publicar un breve resumen del módulo, su propósito e interfaces. Unas pocas líneas sobre cada uno de los métodos principales es probablemente suficiente. (Si publica el módulo completo, podría ser ignorado por personas ocupadas, ¡generalmente las mismas personas que usted quiere que lo lean!)

      No se preocupe por publicar si no puede decir cuándo estará listo el módulo, simplemente dígalo en el mensaje. ¡Podría valer la pena invitar a otros a ayudarle, podrían completarlo por usted!

    • README y otros Archivos Adicionales.

      Es bien sabido que los desarrolladores de software suelen documentar completamente el software que escriben. Si, sin embargo, el mundo necesita urgentemente su software y no hay tiempo suficiente para escribir la documentación completa, al menos proporcione un archivo README que contenga:

    • Una descripción del módulo/paquete/extensión, etc.
    • Un aviso de copyright - ver más abajo.
    • Prerrequisitos - qué más puede necesitar.
    • Cómo construirlo - posibles cambios en Makefile.PL, etc.
    • Cómo instalarlo.
    • Cambios recientes en esta versión
    , especialmente incompatibilidades
  • Cambios / mejoras que planeas hacer en el futuro.

    • Si el archivo README parece ser demasiado grande, puedes considerar dividir algunas secciones en archivos separados: INSTALL, Copying, ToDo, etc.

    • Agregar un aviso de copyright.

      Cómo eliges licenciar tu trabajo es una decisión personal. El mecanismo general es afirmar tu copyright y luego hacer una declaración de cómo otros pueden copiar/usar/modificar tu trabajo.

      Perl, por ejemplo, se distribuye con dos tipos de licencia: La GNU GPL y La Licencia Artística (ver los archivos README, Copying y Artistic, o perlgpl y perlartistic). Larry tiene buenas razones para NO usar solo la GNU GPL.

      Mi recomendación personal, por respeto a Larry, Perl y la comunidad Perl en general, es decir algo tan simple como:

      Copyright (c) 1995 Tu Nombre. Todos los derechos reservados.
Este programa es software libre; puedes redistribuirlo y/o
modificarlo bajo los mismos términos que el propio Perl.

      Esta declaración al menos debería aparecer en el archivo README. También podrías desear incluirla en un archivo Copying y en tus archivos fuente. Recuerda incluir las otras palabras además del Copyright.

    • Darle al módulo un número de versión/incidencia/lanzamiento.

      Para ser totalmente compatible con los módulos Exporter y MakeMaker, debes almacenar el número de versión de tu módulo en una variable de paquete no-my llamada $VERSION. Este debe ser un número de punto flotante positivo con al menos dos dígitos después del decimal (es decir, centésimas, por ejemplo, "$VERSION = "0.01""). No uses una versión estilo "1.3.2". Ver Exporter para más detalles.

      Puede ser útil agregar una función o método para recuperar el número. Usa el número en anuncios y nombres de archivos de archivo al lanzar el módulo (NombreModulo-1.02.tar.Z). Ver perldoc ExtUtils::MakeMaker.pm para más detalles.

    • Cómo lanzar y distribuir un módulo.

      Si es posible, registra el módulo con CPAN. Sigue las instrucciones y enlaces en:

      https://www.cpan.org/modules/04pause.html

      y sube a:

      https://pause.perl.org/

      y notifica a <modules@perl.org>. Esto permitirá que cualquiera instale tu módulo usando la herramienta "cpan" distribuida con Perl.

      Usando la interfaz WWW puedes pedir al Servidor de Subida que refleje tus módulos desde tu sitio ftp o WWW en tu propio directorio en CPAN.

    • Ten cuidado al cambiar un módulo lanzado.

      Siempre esfuérzate por mantener la compatibilidad con versiones anteriores lanzadas. De lo contrario, intenta agregar un mecanismo para revertir al comportamiento anterior si la gente depende de él. Documenta los cambios incompatibles.

    Directrices para convertir scripts de biblioteca de Perl 4 en módulos

    • No hay requisito para convertir nada.

      ¡Si no está roto, no lo arregles! Los scripts de biblioteca de Perl 4 deberían seguir funcionando sin problemas. Puede que necesites hacer algunos cambios menores (como escapar '@' no de arreglo en cadenas entre comillas dobles) pero no hay necesidad de convertir un archivo .pl en un Módulo solo por eso.

    • Considera las implicaciones.

      Todas las aplicaciones Perl que usen el script necesitarán ser cambiadas (ligeramente) si el script se convierte en un módulo. ¿Vale la pena a menos que planees hacer otros cambios al mismo tiempo?

    • Aprovecha la oportunidad.

      Si vas a convertir el script en un módulo, puedes usar la oportunidad para rediseñar la interfaz. Las directrices para la creación de módulos anteriores incluyen muchos de los problemas que deberías considerar.

    • La utilidad pl2pm te ayudará a empezar.

      Esta utilidad leerá archivos *.pl (dados como parámetros) y escribirá archivos *.pm correspondientes. La utilidad pl2pm hace lo siguiente:

    • Agrega las líneas de prólogo estándar del Módulo
    • Convierte especificadores de paquete de ' a ::
    • Convierte die(...) a croak(...)
    • Varios otros cambios menores

    Al ser un proceso mecánico, pl2pm no es infalible. El código convertido necesitará una revisión cuidadosa, especialmente cualquier declaración de paquete. ¡No elimines el archivo .pl original hasta que el nuevo .pm funcione!

    Directrices para reutilizar código de aplicaciones

    • Las aplicaciones completas rara vez pertenecen a la Biblioteca de Módulos de Perl.
    • Muchas aplicaciones contienen código Perl que podría ser reutilizado.

      ¡Ayuda a salvar el mundo! Comparte tu código de una forma que facilite su reutilización.

    • Divide el código reutilizable en uno o más archivos de módulo separados.
    • Aprovecha la oportunidad para reconsiderar y rediseñar las interfaces.
    • En algunos casos, la 'aplicación' puede entonces reducirse a un pequeño

      fragmento de código construido sobre los módulos reutilizables. En estos casos, la aplicación podría invocarse como:

           % perl -e 'use NombreModulo::Nombre; metodo(@ARGV)' ...
o
     % perl -mNombreModulo::Nombre ...    (en perl5.002 o superior)

    NOTA

    Perl no impone partes privadas y públicas de sus módulos como quizás hayas estado acostumbrado en otros lenguajes como C++, Ada o Modula-17. Perl no tiene una fascinación por la privacidad forzada. Preferiría que te mantuvieras fuera de su sala de estar porque no fuiste invitado, no porque tenga una escopeta.

    El módulo y su usuario tienen un contrato, parte del cual es ley común y parte del cual está "escrito". Parte del contrato de ley común es que un módulo no contamina ningún espacio de nombres que no se le pidió que contaminara. El contrato escrito para el módulo (también conocido como documentación) puede hacer otras estipulaciones. Pero entonces sabes cuando "use RedefineTheWorld" que estás redefiniendo el mundo y estás dispuesto a asumir las consecuencias.
