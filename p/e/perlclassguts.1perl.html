NOMBRE

perlclassguts - Detalles internos de cómo funciona `feature 'class'` y la sintaxis de clases

DESCRIPCIÓN

Este documento proporciona información detallada sobre la forma en que el intérprete de Perl implementa la sintaxis "feature 'class'" y su comportamiento general. No está destinado a ser una guía para el usuario final sobre cómo usar la característica. Para eso, consulte perlclass.

Se asume que el lector está familiarizado en general con los detalles internos del intérprete de Perl. Para una visión más general de estos detalles, consulte también perlguts.

ALMACENAMIENTO DE DATOS

Clases

Una clase es fundamentalmente un paquete y existe en la tabla de símbolos como un HV con una estructura auxiliar de la misma manera que un paquete que no es de clase. Se distingue de un paquete que no es de clase por el hecho de que la macro HvSTASH_IS_CLASS() devolverá verdadero en él.

Información adicional relacionada con que sea una clase se almacena en la estructura "struct xpvhv_aux" adjunta al stash, en los siguientes campos:

HV          *xhv_class_superclass;
CV          *xhv_class_initfields_cv;
AV          *xhv_class_adjust_blocks;
PADNAMELIST *xhv_class_fields;
PADOFFSET    xhv_class_next_fieldix;
HV          *xhv_class_param_map;
  • "xhv_class_superclass" será "NULL" para una clase sin superclase. Apuntará directamente al stash de la clase padre si se ha establecido una con el atributo de clase :isa().
  • "xhv_class_initfields_cv" contendrá un "CV *" apuntando a una función que se invocará como parte del constructor de esta clase o de cualquier subclase de la misma. Este CV es responsable de inicializar todos los campos definidos por esta clase para una nueva instancia. Este CV será una función real anónima; es decir, aunque no tenga nombre ni GV, no es un protosub y puede ser invocado directamente.
  • "xhv_class_adjust_blocks" puede apuntar a un AV que contiene punteros CV a cada uno de los bloques "ADJUST" definidos en la clase. Si la clase tiene una superclase, este array contendrá además punteros duplicados de los CV de su clase padre. El AV se crea de forma diferida la primera vez que se agrega un elemento; es válido que no exista, y este puntero será "NULL" en ese caso.

    Los CV se almacenan directamente, no a través de RVs. Cada CV será una función real anónima.

  • "xhv_class_fields" apuntará a un "PADNAMELIST" que contiene "PADNAME"s, cada uno siendo un campo definido de la clase. Se almacenan en orden de declaración. Tenga en cuenta, sin embargo, que el índice en este array no será necesariamente igual al "fieldix" de cada campo, porque en el caso de una subclase, el array comenzará en cero, pero el índice del primer campo en él será distinto de cero si su clase padre contiene algún campo en absoluto.

    Para obtener más información sobre cómo se representan los campos individuales, consulte "Campos".

  • "xhv_class_next_fieldix" proporciona el índice de campo que se asignará al próximo campo que se agregue a la clase. Solo es útil en tiempo de compilación.
  • "xhv_class_param_map" puede apuntar a un HV que mapea nombres de atributos de campo ":param" al índice de campo del campo con ese nombre. Este mapeo se copia de las clases padre; cada clase contendrá la suma total de todos sus padres además de los suyos propios.

Campos

Un campo sigue siendo fundamentalmente una variable léxica declarada en un ámbito y existe en la "PADNAMELIST" de su CV correspondiente. Los métodos y otros CV similares a métodos pueden capturarlos exactamente como lo hacen con léxicos regulares. Un campo se distingue de otros tipos de entradas de pad porque la macro PadnameIsFIELD() devolverá verdadero en él.

La información adicional relacionada con que sea un campo se almacena en una estructura adicional accesible a través de la macro PadnameFIELDINFO() en el padname. Esta estructura tiene los siguientes campos:

PADOFFSET  fieldix;
HV        *fieldstash;
OP        *defop;
SV        *paramname;
bool       def_if_undef;
bool       def_if_false;
  • "fieldix" almacena el "índice de campo" del campo; es decir, el índice en el array de campos de instancia donde se almacenará el valor de este campo. Tenga en cuenta que el primer índice en el array no está especialmente reservado. El primer campo en una clase comenzará desde el índice de campo 0.
  • "fieldstash" almacena un puntero al stash de la clase que definió este campo. Esto es necesario en caso de que haya varias clases definidas dentro del mismo ámbito; se utiliza para desambiguar los campos de cada una. 
    {
    class C1; field $x;
    class C2; field $x;
}
  • "defop" puede almacenar un puntero a un árbol de operaciones de expresión de valor predeterminado para este campo. Las expresiones de valor predeterminado son opcionales; este campo puede ser "NULL".
  • "paramname" puede apuntar a un SV de cadena regular que contiene el nombre del atributo ":param" dado al campo. Si no hay ninguno, será "NULL".
  • Uno de "def_if_undef" y "def_if_false" será verdadero si la expresión de valor predeterminado se estableció utilizando los operadores "//=" o "||=", respectivamente.

Métodos

Un método sigue siendo fundamentalmente un CV y tiene la misma representación básica que uno. Tiene un árbol de operaciones y un pad, y se almacena a través de un GV en el stash de su paquete contenedor. Se distingue de un CV que no es un método porque la macro CvIsMETHOD() devuelve verdadero en él.

(Nota: Esta macro no debe confundirse con la que anteriormente se llamaba CvMETHOD(). Esa no se relaciona con el sistema de clases y se renombró a CvNOWARN_AMBIGUOUS() para evitar esta confusión).

Actualmente no hay información adicional que necesite almacenarse sobre un CV de método, por lo que la estructura no agrega nuevos campos.

Instancias

Las instancias de objetos están representadas por un tipo de SV completamente nuevo, cuyo tipo base es "SVt_PVOBJ". Todavía debe ser bendecido en el stash de su clase y envuelto en un RV de la manera habitual para los objetos clásicos.

Dado que son su propio tipo de contenedor único, distinto de los hashes o arrays, la función principal "builtin::reftype" devuelve un valor nuevo cuando se le pregunta sobre ellos. Ese valor es "OBJECT".

Internamente, un objeto de este tipo es un array de punteros SV cuyo tamaño se fija en el momento de la creación (porque el número de campos en una clase se conoce después de la compilación). Una instancia de objeto almacena el índice de campo máximo dentro de ella (para la verificación básica de errores en el acceso) y un array de tamaño fijo de punteros SV que almacenan los valores de los campos individuales.

Los campos de tipo array y hash almacenan directamente punteros AV o HV en el array; no se almacenan a través de un RV intermedio.

class_add_field

``` void class_add_field(HV *stash, PADNAME *pn); ```

Llamada por pad.c como parte de la definición de un nuevo nombre de campo en el pad actual. Tenga en cuenta que esta función *no* crea el nombre del pad; eso debe haberlo hecho ya pad.c. Esta función de la API simplemente informa a la clase que se ha creado el nuevo nombre del campo y que ahora está disponible para ella.

class_add_ADJUST

``` void class_add_ADJUST(HV *stash, CV *cv); ```

Llamada por el analizador una vez que ha analizado y construido un CV para un nuevo bloque "ADJUST". Esto se agrega a la lista almacenada por la clase.

Manipulación de Campos

class_prepare_initfield_parse

``` void class_prepare_initfield_parse(); ```

Llamada por el analizador justo antes de analizar una expresión de inicialización para una variable de campo. Esto hace uso de un compcv suspendido para combinar todas las expresiones de inicialización de campos en el mismo CV.

class_set_field_defop

``` void class_set_field_defop(PADNAME *pn, OPCODE defmode, OP *defop); ```

Llamada por el analizador después de haber analizado una expresión de inicialización para el campo. Establece la expresión de predeterminación y el modo de aplicación. "defmode" debe ser cero, o uno de "OP_ORASSIGN" o "OP_DORASSIGN" dependiendo del modo de predeterminación.

padadd_FIELD

``` #define padadd_FIELD ```

Esta constante de bandera le dice a la familia de funciones "pad_add_name_*" que el nuevo nombre debe agregarse como un campo. No es necesario llamar class_add_field(); esto se hará automáticamente.

Manipulación de Métodos

class_prepare_method_parse

``` void class_prepare_method_parse(CV *cv); ```

Llamada por el analizador después de start_subparse() pero inmediatamente antes de hacer cualquier otra cosa. Esto prepara el "PL_compcv" para analizar un método; organizando que la prueba "CvIsMETHOD" sea verdadera, agregando el léxico $self y cualquier otra actividad que pueda ser requerida.

class_wrap_method_body

``` OP *class_wrap_method_body(OP *o); ```

Llamada por el analizador al final de analizar el cuerpo de un método en un optree, pero justo antes de envolverlo en el CV eventual. Esta función inserta ops adicionales en el optree para que el método funcione correctamente.

Instancias de Objetos

SVt_PVOBJ

``` #define SVt_PVOBJ ```

Una constante de tipo SV utilizada para la comparación con la macro SvTYPE().

ObjectMAXFIELD

``` SSize_t ObjectMAXFIELD(sv); ```

Una macro similar a una función que obtiene el índice máximo de campo válido que se puede acceder desde la matriz "ObjectFIELDS".

ObjectFIELDS

``` SV **ObjectFIELDS(sv); ```

Una macro similar a una función que obtiene la matriz de campos directamente de una instancia de objeto. Los campos se pueden acceder por su índice de campo, desde 0 hasta el índice máximo válido dado por "ObjectMAXFIELD".

OPCODES

OP_METHSTART

``` newUNOP_AUX(OP_METHSTART, ...); ```

Un "OP_METHSTART" es un "UNOP_AUX" que debe estar presente al inicio de un CV de método para que funcione correctamente. Esto es insertado por class_wrap_method_body(), e incluso aparece antes de cualquier fragmento de optree asociado con la verificación o extracción de argumentos de la firma.

Este op es responsable de desplazar el valor de $self de la lista de argumentos y enlazar cualquier variable de campo a la que el método requiera acceso en el pad. El vector AUX contendrá detalles de los emparejamientos de índice de campo/pad requeridos.

Este op también realiza comprobaciones de integridad en el valor invocante. Comprueba que sea definitivamente una referencia de objeto de un tipo de clase compatible. Si no lo es, se lanza una excepción.

Si el campo "op_private" incluye la bandera "OPpINITFIELDS", esto indica que el op comienza el CV especial "xhv_class_initfields_cv". En este caso, también debe tomar el segundo valor de la lista de argumentos, que debe ser un puntero HV simple ( *directamente*, no a través de RV), y enlazarlo al segundo slot del pad, donde el optree generado esperará encontrarlo.

OP_INITFIELD

Un "OP_INITFIELD" solo se invoca como parte del CV "xhv_class_initfields_cv" durante la fase de construcción de una instancia. Este es el momento en que los SV individuales que componen los campos mutables de la instancia (incluidos AVs y HVs) se asignan realmente al array "ObjectFIELDS". Las banderas privadas "OPpINITFIELD_AV" y "OPpINITFIELD_HV" indican si está creando un AV o un HV; si no se establece ninguna, se crea un SV.

Si el op tiene la bandera "OPf_STACKED" espera encontrar un valor de inicialización en la pila. Para SVs, este es el SV superior en la pila de datos. Para AVs y HVs, espera una lista marcada.

COMPORTAMIENTO EN TIEMPO DE COMPILACIÓN

Fasores "ADJUST"

Durante el tiempo de compilación, el análisis de un fasor "ADJUST" se maneja de una manera fundamentalmente diferente a los fasores existentes de perl ("BEGIN", etc...)

En lugar de tomar la ruta habitual, el tokenizador reconoce que la palabra clave "ADJUST" introduce un bloque fasor. El analizador luego analiza el cuerpo de este bloque de manera similar a como analizaría el cuerpo de un método (anónimo), creando un CV que no tiene un nombre GV. Luego se inserta directamente en la información de la clase llamando a "class_add_ADJUST", omitiendo por completo la tabla de símbolos.

Atributos

Durante la compilación, los atributos tanto de clases como de campos se manejan de manera diferente a los atributos existentes de perl en subrutinas y variables léxicas.

El analizador todavía forma un optree "OP_LIST" de nodos "OP_CONST", pero estos se pasan a las funciones "class_apply_attributes" o "class_apply_field_attributes". En lugar de usar una búsqueda de clase para un método en la clase que se está analizando, se utiliza una lista interna fija de atributos conocidos para encontrar funciones para aplicar el atributo a la clase o al campo. En el futuro, esto puede admitir atributos de extensión proporcionados por el usuario, aunque en la actualidad solo reconoce los definidos por el propio núcleo.

Expresiones de Inicialización de Campos

Durante la compilación, el analizador utiliza un compcv suspendido al analizar la expresión de predeterminación para un campo. Todas las expresiones para todos los campos de la clase comparten el mismo compcv suspendido, que luego se compila en el mismo CV interno llamado por el constructor para inicializar todos los campos proporcionados por esa clase.

COMPORTAMIENTO EN TIEMPO DE EJECUCIÓN

Constructor

El constructor generado para una clase es en sí mismo un XSUB que realiza tres tareas en orden: crea el SV de instancia en sí, invoca los inicializadores de campo, luego invoca los CVs de bloque ADJUST. El constructor para cualquier clase siempre tiene la misma forma básica, independientemente de si la clase tiene una superclase o no.

Los inicializadores de campo se recopilan en un CV generado basado en optree llamado CV inicializador de campo. Este es el CV que contiene todos los fragmentos de optree para las expresiones de inicialización de campo. Cuando se invoca, el CV inicializador de campo puede realizar una llamada encadenada al inicializador de la superclase si existe, antes de invocar todos los ops de inicialización de campo individuales. El CV inicializador de campo se invoca con dos elementos en la pila; siendo el SV de instancia y un HV directo que contiene los parámetros del constructor. Tenga en cuenta: este HV se pasa *directamente*, no a través de una referencia RV. Esto está permitido porque tanto el llamador como el llamado son código generado directamente y no subrutinas puras de perl arbitrarias.

Los CVs de bloque ADJUST se recopilan en una única lista plana, fusionando también todos los definidos por la superclase. Se invocan todos en orden, después del CV inicializador de campo.

Acceso a $self Durante los Métodos

Cuando se llama a class_prepare_method_parse(), se organiza para que el pad del cuerpo del nuevo CV comience con un léxico llamado $self. Debido a que el pad debe ser recién creado en este punto, tendrá el índice de pad de 1. La función verifica esto y aborta si no es así.

NAME

perlclassguts - internals of class definitions

DESCRIPTION

This document describes the internal data structures and mechanisms used to implement Perl classes and object-oriented programming.

DATA STORAGE

Class data is stored in a structure that is a hash-like container (an HV). This structure is known as the Class Table.

For each class, there is a global SV* which points to the Class Table HV. These global SVs are stored in the interpreter's symbol table.

API

Internally, Perl uses a set of API calls to manage class definitions and operations. These include functions for creating, accessing, and modifying class data.

COMPILE-TIME BEHAVIOUR

During compilation, Perl generates code to set up class definitions. This includes creating the Class Table HV and populating it with necessary information.

RUNTIME BEHAVIOUR

At runtime, Perl executes the compiled code to perform class operations such as method calls, object creation, and inheritance.

The OP_INITFIELD opcode is used to initialize instance fields. It relies on the fact that within the body of a method or method-like CV, pad index 1 can reliably be used to obtain the invocant reference. The "OP_INITFIELD" opcode also relies on this fact.

In similar fashion, during the "xhv_class_initfields_cv" the next pad slot is relied on to store the constructor parameters HV, at pad index 2.
