NOMBRE

perlhacktips - Consejos para modificar el código C del núcleo de Perl

DESCRIPCIÓN

Este documento te ayudará a aprender la mejor manera de modificar el código C del núcleo de Perl. Cubre problemas comunes, depuración, creación de perfiles y más.

Si aún no has leído perlhack y perlhacktut, quizás quieras hacerlo primero.

PROBLEMAS COMUNES

El código fuente de Perl ahora permite algunas características específicas de C99 que sabemos que son compatibles con todas las plataformas, pero en su mayoría sigue las reglas de ANSI C89. ¿No te importa que alguna plataforma en particular tenga un Perl roto? Escuché que todavía hay una gran demanda de programadores J2EE.

Problemas del entorno de Perl

  • No compilar con hilos (threading)

    Compilar con hilos (-Duseithreads) reescribe completamente los prototipos de función de Perl. Es mejor probar tus cambios con eso. Relacionado con esto está la diferencia entre las APIs "Perl_-less" y "Perl_-ly", por ejemplo:

    Perl_sv_setiv(aTHX_ ...);
sv_setiv(...);

    La primera pasa explícitamente el contexto, que es necesario para, por ejemplo, compilaciones con hilos. La segunda lo hace implícitamente; no las mezcles. Si no estás pasando un aTHX_, necesitarás usar un dTHX como primera cosa en la función.

    Ver "How multiple interpreters and concurrency are supported" en perlguts para una discusión más detallada sobre el contexto.

  • No compilar con -DDEBUGGING

    La definición DEBUGGING expone más código al compilador, por lo tanto, más formas para que las cosas salgan mal. Deberías probarlo.

  • Introducir globales (no de solo lectura)

    No introduzcas globales modificables, verdaderamente globales o estáticas de archivo. Son de mala calidad y complican la multithreading y otras formas de concurrencia. La forma correcta es introducirlos como nuevas variables del intérprete, ver intrpvar.h (al final para compatibilidad binaria).

    Introducir globales de solo lectura (const) está bien, siempre que verifiques con, por ejemplo, "nm libperl.a|egrep -v ' [TURtr] '" (si tu "nm" tiene salida estilo BSD) que los datos que agregaste son realmente de solo lectura. (Si lo son, no deberían aparecer en la salida de ese comando.)

    Si quieres tener cadenas estáticas, hazlas constantes:

    static const char etc[] = "...";

    Si quieres tener arreglos de cadenas constantes, ten en cuenta cuidadosamente la combinación correcta de "const"s:

    static const char * const yippee[] =
    {"hi", "ho", "silver"};
  • No exportar tu nueva función

    Algunas plataformas (Win32, AIX, VMS, OS/2, por nombrar algunas) requieren que cualquier función que sea parte de la API pública (la biblioteca compartida de Perl) esté explícitamente marcada como exportada. Ver la discusión sobre embed.pl en perlguts.

  • Exportar tu nueva función

    El nuevo y brillante resultado de una funcionalidad genuinamente nueva o de tu arduo refactorización ahora está listo y correctamente exportado. Entonces, ¿qué podría salir mal?

    Quizás simplemente que tu función no necesitaba ser exportada en primer lugar. Perl tiene una historia larga y no tan gloriosa de exportar funciones que no debería haberlo hecho.

    Si la función se usa solo dentro de un archivo de código fuente, hazla estática. Ver la discusión sobre embed.pl en perlguts.

    Si la función se usa en varios archivos, pero está destinada solo al uso interno de Perl (y este debería ser el caso común), no la exportes a la API pública. Ver la discusión sobre embed.pl en perlguts.

C99

A partir de la versión 5.35.5, permitimos algunas características de C99 en el código fuente C del núcleo. Sin embargo, el código en extensiones de doble vida todavía debe ser solo C89, porque necesita compilar contra versiones anteriores de Perl que se ejecutan en plataformas más antiguas. Ten en cuenta también que nuestras cabeceras también deben ser válidas como C++, porque las extensiones XS escritas en C++ necesitan incluirlas, por lo tanto, los inicializadores de miembros de estructura no se pueden usar en las cabeceras.

El soporte de C99 todavía está lejos de ser completo en todas las plataformas que soportamos actualmente. Como base, solo podemos asumir la semántica de C89 con las características específicas de C99 descritas a continuación, que hemos verificado que funcionan en todas partes. Está bien sondear características C99 adicionales y usarlas donde estén disponibles, siempre que también haya una alternativa para compiladores que no soporten la característica. Por ejemplo, usamos almacenamiento local de hilos C11 cuando está disponible, pero recurrimos a las APIs específicas de hilos POSIX en su lugar.

El código puede usar (y depender de) las siguientes características de C99:

  • declaraciones mixtas y código
  • tipos de enteros de 64 bits

    Para consistencia con el código fuente existente, usa los typedefs "I64" y "U64", en lugar de usar "long long" y "unsigned long long" directamente.

  • macros variádicas 
    void greet(char *file, unsigned int line, char *format, ...);
#define logged_greet(...) greet(__FILE__, __LINE__, __VA_ARGS__);

    Ten en cuenta que "__VA_OPT__" se estandariza a partir de C23 y C++20. Antes de eso era una extensión de gcc.

  • declaraciones en bucles for 
    for (const char *p = message; *p; ++p) {
    putchar(*p);
}
  • inicializadores de miembros de estructura

    Pero no en cabeceras, ya que el soporte se agregó a C++ muy recientemente.

    Por lo tanto, esto está bien en código C y XS, pero no en cabeceras:

    struct message {
    char *action;
    char *target;
};
struct message mcguffin = {
    .target = "member structure initialisers",
    .action = "Built"
 };

    No puedes usar la sintaxis similar para literales compuestos, ya que también compilamos perl usando compiladores C++:

    /* esto está bien */
struct message m = {
    .target = "some target",
    .action = "some action"
};
/* esto no es válido en C++ */
m = (struct message){
    .target = "some target",
    .action = "some action"
};

    Si bien los designadores de estructura son utilizables, los designadores de arreglo relacionados no lo son, ya que C++ no los soporta en absoluto.

  • miembros flexibles de arreglo

    Esto es conforme al estándar:

    struct greeting {
    unsigned int len;
    char message[];
};

    Sin embargo, el código fuente ya usa el hack de "chumminess inmerecida con el compilador" en muchos lugares:

    struct greeting {
    unsigned int len;
    char message[1];
};

    Estrictamente, es un comportamiento indefinido acceder más allá de "message[0]", pero este ha sido un hack comúnmente utilizado desde los tiempos de K&R, y usarlo no ha sido un problema práctico en ninguna parte (en el código fuente de perl o en cualquier otro código C común). Por lo tanto, no está claro qué ganaríamos al cambiar activamente al enfoque C99.

  • comentarios "//"

    Todos los compiladores que probamos soportan su uso. No todos los humanos que probamos soportan su uso.

  • booleanos

    Puedes usar "bool", "true" y "false" como los proporciona "<stdbool.h>" (o nativamente en C++).

El código explícitamente no debe usar ninguna otra característica de C99. Por ejemplo:

  • arreglos de longitud variable

    No soportados por **ningún** MSVC, y esto no va a cambiar.

    Incluso los arreglos de longitud "variable" donde la variable es una expresión constante son errores de sintaxis bajo MSVC.

  • tipos C99 en "<stdint.h>"

    Usa "PERL_INT_FAST8_T" etc. como se define en handy.h

  • cadenas de formato C99 en "<inttypes.h>"

    "snprintf" en la libc de VMS solo agregó soporte para "PRIdN" etc. muy recientemente, lo que significa que hay versiones

instalaciones portadas sin esto, o formatos como %zu.

(El "sv_catpvf" de Perl, etc., utilizan código de análisis en sv.c, que admite el modificador "z", junto con formatos específicos de Perl como "SVf".)

Si desea utilizar una característica de C99 no enumerada anteriormente, debe hacer una de las siguientes opciones:

  • Buscarla en Configure, establecer una variable en config.sh y agregar lógica de respaldo en los encabezados para las plataformas que no la tengan.
  • Escribir código de prueba y verificar que funcione en las plataformas que necesitamos soportar, antes de confiar en él incondicionalmente.

Lo más probable es que desee repetir el mismo plan que utilizamos para obtener el conjunto de características C99 actual. Consulte el mensaje en https://markmail.org/thread/odr4fjrn72u2fkpz para las sondas C99 que utilizamos anteriormente. Tenga en cuenta que los dos compiladores más "exigentes" parecen ser MSVC y el compilador del proveedor en VMS. Hasta la fecha, todos los compiladores *nix han sido mucho más flexibles en lo que admiten.

En las plataformas *nix, Configure intenta establecer las banderas del compilador adecuadamente. Todos los compiladores de proveedores que probamos por defecto admitían C99 (o C11). Sin embargo, las versiones anteriores de gcc por defecto admiten C89, o permiten *la mayoría* de C99 (con advertencias), pero prohíben *declaraciones en bucles for* a menos que se agregue "-std=gnu99". La alternativa "-std=c99" *podría* parecer mejor, pero usarla en algunas plataformas puede evitar que "<unistd.h>" declare algunos prototipos que se declaran, lo que interrumpe la compilación. El flag "-ansi" de gcc implica "-std=c89", por lo que ya no podemos establecerlo. Por lo tanto, la opción de Configure "-gccansipedantic" ahora solo agrega "-pedantic".

Los archivos de código fuente principal de Perl (los que están en el nivel superior de la distribución de código fuente) se compilan automáticamente con tantas banderas como sea posible de "-std=gnu99", "-pedantic" y una selección de banderas "-W" (ver cflags.SH). Los archivos en ext/, dist/, cpan/, etc., se compilan con las mismas banderas que el Perl instalado usaría para compilar extensiones XS.

Básicamente, es seguro asumir que Configure y cflags.SH han elegido la mejor combinación de banderas para la versión de gcc en la plataforma, e intentar agregar más banderas relacionadas con la aplicación de un dialecto C causará problemas, ya sea localmente o en otros sistemas a los que se envíe el código.

Creemos que el soporte C99 en gcc 3.1 es lo suficientemente bueno para nosotros, pero no tenemos un gcc de 19 años a mano para verificarlo :-) Si tiene compiladores de proveedores antiguos que no admiten C99 por defecto, las banderas que podría intentar son:

AIX
"-qlanglvl=stdc99"
HP/UX
"-AC99"
Solaris
"-xc99"

Nombres de símbolos y contaminación del espacio de nombres

Elección de nombres de símbolos legales

C reserva para su implementación cualquier símbolo cuyo nombre comience con un guión bajo seguido inmediatamente por una letra mayúscula "[A-Z]" u otro guión bajo. C++ además reserva cualquier símbolo que contenga dos guiones bajos consecutivos, y además reserva en el espacio de nombres global cualquier símbolo que comience con un guión bajo, no solo aquellos seguidos por una mayúscula. Nos importa C++ porque los archivos de encabezado (*.h) deben poder ser compilados por él, y algunas personas realizan todo su desarrollo utilizando un compilador C++.

Las consecuencias de no hacerlo son probablemente ninguna. A menos que se tropiece con un nombre que la implementación utilice, las cosas funcionarán. De hecho, el núcleo de Perl tiene más de unas pocas instancias de uso de símbolos reservados por la implementación. (Estos se están cambiando gradualmente). Pero su código podría dejar de funcionar en cualquier momento en que la implementación decida utilizar un nombre que usted ya había elegido, potencialmente muchos años antes.

Es mejor entonces:

No comience un nombre de símbolo a nivel de archivo con un guión bajo; (por ejemplo, no use: "_FOOBAR")
Está bien tener un símbolo en una función o bloque como "_ref", que comience con un guión bajo seguido de una letra minúscula.
No use dos guiones bajos consecutivos en un nombre de símbolo; (por ejemplo, no use "FOO__BAR")

POSIX también reserva muchos símbolos. Consulte la Sección 2.2.2 en https://pubs.opengroup.org/onlinepubs/9699919799/functions/V2_chap02.html. Perl también tiene conflictos con eso.

Perl reserva para su uso cualquier símbolo que comience con "Perl", "perl" o "PL_". Cada vez que introduzca una macro en un archivo de encabezado que no siga esa convención, estará creando la posibilidad de una colisión de nombres con un módulo XS existente, a menos que la restrinja, por ejemplo, con:

#ifdef PERL_CORE
#  define my_symbol
#endif

Hay muchos símbolos en los archivos de encabezado que no son de esta forma, y que son accesibles desde el espacio de nombres XS, intencionalmente o no, casi cualquier cosa en config.h, por ejemplo.

Tener que usar uno de estos prefijos resta legibilidad al código y no ha sido un problema real para nombres no triviales. Cosas como que Perl defina su propia macro "MAX" han sido problemáticas, pero se descubrieron rápidamente y se agregó una protección de "#ifdef PERL_CORE".

Por lo tanto, no hay una regla impuesta sobre el uso de tales símbolos, solo sea consciente de los problemas.

Elección de buenos nombres de símbolos

Idealmente, un nombre de símbolo debería describir correcta y precisamente su propósito previsto. Pero existe una tensión entre eso y obtener nombres que sean excesivamente largos y, por lo tanto, incómodos de escribir y leer. Las metáforas podrían ser útiles (un nombre poético), pero tienden a ser culturalmente específicas y pueden no traducirse para alguien cuyo idioma nativo no sea el inglés, o incluso provenga de un trasfondo cultural diferente. Además, el talento para escribir poesía parece ser raro en los programadores.

Ciertos nombres de símbolos no reflejan su propósito, pero aun así están bien usarlos debido a convenciones de larga data. Estos a menudo se originaron en el campo de las Matemáticas, donde "i" y "j" se utilizan frecuentemente como subíndices, y "n" como un recuento de población. Desde al menos la década de 1950, los programas informáticos han utilizado "i", etc. como variables de bucle.

Nuestra guía es elegir un nombre que describa razonablemente el propósito y comentar su declaración de forma más precisa.

Ciertamente, uno no debería usar nombres engañosos o ambiguos. "last_foo" podría significar el último "foo" o el anterior "foo", y por lo tanto podría ser confuso para el lector, o incluso para el escritor que regresa al código después de unos meses de trabajar en otra cosa. A veces, el programador tiene una línea de pensamiento particular en mente y no se le ocurre que existe ambigüedad.

Probablemente todavía hay muchos errores de "off-by-1" alrededor porque el nombre """av_len""" en perlapi no se corresponde con lo que significan otras construcciones de -len, como """sv_len""" en perlapi. Se crearon sinónimos incómodos (y controvertidos) para usar en su lugar que transmitían su verdadero significado (""av_top_index""" en perlapi). Sin embargo, finalmente, alguien tuvo la mejor idea de crear un nuevo nombre para significar lo que la mayoría de la gente piensa que significa "-len". Así nació ""av_count""" en perlapi. Y desearíamos que se hubiera pensado mucho antes.

Escribir macros más seguras

Las macros se utilizan ampliamente en el núcleo de Perl para cosas como ocultar detalles internos del llamador, para que este no tenga que preocuparse por ellos. Por ejemplo, la mayoría de las líneas de código no necesitan saber si se están ejecutando en un Perl con hilos o sin hilos. Ese detalle se oculta automáticamente en su mayor parte.

A menudo es mejor usar una función en línea en lugar de una macro. Son inmunes a colisiones de nombres con el llamador y no magnifican los problemas cuando se llaman con parámetros que son expresiones con efectos secundarios. Hubo un tiempo en que se podía elegir una macro sobre una función en línea porque el soporte del compilador para funciones en línea era bastante limitado. Algunos solo inlinerizaban las dos o tres primeras encontradas en una compilación. Pero esos días han pasado, y las funciones en línea son totalmente compatibles en los compiladores modernos.

Sin embargo, hay situaciones en las que una función no servirá y se requiere una macro. Un ejemplo es cuando un parámetro puede ser de varios tipos. Una función debe declararse con un único tipo de parámetro explícito, por lo que se puede llamar a una macro.

O tal vez el código involucrado es tan trivial que una función sería simplemente una complicación excesiva, como cuando la macro simplemente crea un nombre mnemotécnico para algún valor constante.

Si decide utilizar una macro no trivial, tenga en cuenta que existen varios escollos evitables que pueden ocurrir. Tenga en cuenta que una macro se expande dentro del contexto léxico de cada lugar en la fuente donde se llama. Si tiene un token "foo" en la macro y la fuente también tiene "foo", el significado de "foo" de la macro se convertirá en el del llamador. A veces, ese es exactamente el comportamiento que desea, pero tenga en cuenta que esto tiende a ser confuso más adelante. Efectivamente, convierte "foo" en una palabra reservada para cualquier código que llame a la macro, y este hecho generalmente no se documenta ni se considera. WARNINGS AND PITFALLS

Macro and function names

The C preprocessor makes macro names visible everywhere. If you #define something, say

#define foo bar

then the name "foo" is no longer available for use as a variable name, or string literal, or whatever. It will be replaced by "bar" everywhere it appears. In particular, if the C macro "foo" is defined as,

#define foo  some_function(123)

and you write

printf("foo\n");

then the compiler will see

printf("some_function(123)\n");

which is probably not what you want. The macro interface is explicitly specified, and the macro definition remains freely available to the caller and the macro interface is explicitly specified.

Worse is when the equivalence between the two "foo"'s is coincidental. Suppose for example, that the macro declares a variable

int foo

That works fine as long as the caller doesn't define the string "foo" in some way. And it might not be until years later that someone comes along with an instance where "foo" is used. For example a future caller could do this:

#define foo  bar

Then that declaration of "foo" in the macro suddenly becomes

int bar

That could mean that something completely different happens than intended. It is hard to debug; the macro and call may not even be in the same file, so it would require some digging and gnashing of teeth to figure out.

Therefore, if a macro does use variables, their names should be such that it is very unlikely that they would collide with any caller, now or forever. One way to do that, now being used in the perl source, is to include the name of the macro itself as part of the name of each variable in the macro. Suppose the macro is named "SvPV". Then we could have

int foo_svpv_ = 0;

This is harder to read than plain "foo", but it is pretty much guaranteed that a caller will never naively use "foo_svpv_" (and run into problems). (The lowercasing makes it clearer that this is a variable, but assumes that there won't be two elements whose names differ only in the case of their letters.) The trailing underscore makes it even more unlikely to clash, as those, by convention, signify a private variable name. (See "Choosing legal symbol names" for restrictions on what names you can use.)

This kind of name collision doesn't happen with the macro's formal parameters, so they don't need to have complicated names. But there are pitfalls when a parameter is an expression, or has some Perl magic attached. When calling a function, C will evaluate the parameter once, and pass the result to the function. But when calling a macro, the parameter is copied as-is by the C preprocessor to each instance inside the macro. This means that when evaluating a parameter having side effects, the function and macro results differ. This is particularly fraught when a parameter has overload magic, say it is a tied variable that reads the next line in a file upon each evaluation. Having it read multiple lines per call is probably not what the caller intended. If a macro refers to a potentially overloadable parameter more than once, it should first make a copy and then use that copy the rest of the time. There are macros in the perl core that violate this, but are gradually being converted, usually by changing to use inline functions instead.

Above we said "first make a copy". In a macro, that is easier said than done, because macros are normally expressions, and declarations aren't allowed in expressions. But the "STMT_START" .. "STMT_END" construct, described in perlapi, allows you to have declarations in most contexts, as long as you don't need a return value. If you do need a value returned, you can make the interface such that a pointer is passed to the construct, which then stores its result there. (Or you can use GCC brace groups. But these require a fallback if the code will ever get executed on a platform that lacks this non-standard extension to C. And that fallback would be another code path, which can get out-of-sync with the brace group one, so doing this isn't advisable.) In situations where there's no other way, Perl does furnish ""PL_Sv"" in perlintern and ""PL_na"" in perlapi to use (with a slight performance penalty) for some such common cases. But beware that a call chain involving multiple macros using them will zap the other's use. These have been very difficult to debug.

For a concrete example of these pitfalls in action, see https://perlmonks.org/?node_id=11144355.

Portability problems

The following are common causes of compilation and/or execution failures, not specific to Perl as such. The C FAQ is good bedtime reading. Please test your changes with as many C compilers and platforms as possible; we will, anyway, and it's nice to save oneself from public embarrassment.

Also study perlport carefully to avoid any bad assumptions about the operating system, filesystems, character set, and so forth.

Do not assume an operating system indicates a certain compiler.

  • Casting pointers to integers or casting integers to pointers 
    void castaway(U8* p)
{
  IV i = p;

    or

    void castaway(U8* p)
{
  IV i = (IV)p;

    Both are bad, and broken, and unportable. Use the PTR2IV() macro that does it right. (Likewise, there are PTR2UV(), PTR2NV(), INT2PTR(), and NUM2PTR().)

  • Casting between function pointers and data pointers

    Technically speaking casting between function pointers and data pointers is unportable and undefined, but practically speaking it seems to work, but you should use the FPTR2DPTR() and DPTR2FPTR() macros. Sometimes you can also play games with unions.

  • Assuming "sizeof(int) == sizeof(long)"

    There are platforms where longs are 64 bits, and platforms where ints are 64 bits, and while we are out to shock you, even platforms where shorts are 64 bits. This is all legal according to the C standard. (In other words, "long long" is not a portable way to specify 64 bits, and "long long" is not even guaranteed to be any wider than "long".)

    Instead, use the definitions "IV", "UV", "IVSIZE", "I32SIZE", and so forth. Avoid things like "I32" because they are not guaranteed to be exactly 32 bits (they are at least 32 bits), nor are they guaranteed to be "int" or "long". If you explicitly need 64-bit variables, use "I64" and "U64".

  • Assuming one can dereference any type of pointer for any type of data 
    char *p = ...;
long pony = *(long *)p;    /* BAD */

    Many platforms, quite rightly so, will give you a core dump instead of a pony if the p happens not to be correctly aligned.

  • Lvalue casts 
    (int)*p = ...;    /* BAD */

    Simply not portable. Get your lvalue to be of the right type, or maybe use temporary variables, or dirty tricks with unions.

  • Assume anything about structs (especially the ones you don't control, like the ones coming from the system headers)
    • That a certain field exists in a struct
    • That no other fields exist besides the ones you know of

  • Assuming the character set is ASCIIish

    Perl can compile and run under EBCDIC platforms. See perlebcdic. This is transparent for the most part, but because the character sets differ, you shouldn't use numeric (decimal, octal, nor hex) constants to refer to characters. You can safely say 'A', but not 0x41. You can safely say '\n', but not "\012". However, you can use macros defined in utf8.h to specify any code point portably. LATIN1_TO_NATIVE(0xDF) is going to be the code point that means LATIN SMALL LETTER SHARP S on whatever platform you are running on (on ASCII platforms it compiles without adding any extra code, so there is zero performance hit on those). The acceptable inputs to "LATIN1_TO_NATIVE" are from 0x00 through 0xFF. If your input isn't guaranteed to be in that range, use "UNICODE_TO_NATIVE" instead. "NATIVE_TO_LATIN1" and "NATIVE_TO_UNICODE" translate the opposite direction.

    If you need the string representation of a character that doesn't have a mnemonic name in C, you should add it to the list in regen/unicode_constants.pl, and have Perl create "#define"'s for you, based on the current platform.

    Note that the "isFOO" and "toFOO" macros in handy.h work properly on native code points and strings.

    Also, the range 'A' - 'Z' in ASCII is an unbroken sequence of 26 upper case alphabetic characters. That is not true in EBCDIC. Nor for 'a' to 'z'. But '0' - '9' is an unbroken range in both systems. Don't assume anything about other ranges. (Note that special handling of ranges in regular expression patterns and transliterations makes it appear to Perl code that the aforementioned ranges are all unbroken.)

UTF-8 y UTF-EBCDIC son dos codificaciones diferentes utilizadas para representar puntos de código Unicode como secuencias de bytes. Se utilizan macros con los mismos nombres (pero definiciones diferentes) en utf8.h y utfebcdic.h para permitir que el código de llamada piense que solo hay una codificación de este tipo. Esto se conoce casi siempre como "utf8", pero también se refiere a la versión EBCDIC. Nuevamente, los comentarios en el código pueden estar equivocados incluso si el código en sí es correcto. Por ejemplo, el concepto de caracteres "invariantes" de UTF-8 difiere entre ASCII y EBCDIC. En plataformas ASCII, solo los caracteres que no tienen el bit de orden superior establecido (es decir, cuyos ordinales son estrictamente ASCII, 0-127) son invariantes, y la documentación y los comentarios en el código pueden asumir eso, refiriéndose a menudo a algo como, por ejemplo, "hibit". La situación difiere y no es tan simple en máquinas EBCDIC, pero mientras el código en sí use la macro NATIVE_IS_INVARIANT() apropiadamente, funcionará, incluso si los comentarios son incorrectos.

Como se señaló en "TESTING" en perlhack, al escribir scripts de prueba, el archivo t/charset_tools.pl contiene algunas funciones útiles para escribir pruebas válidas tanto en plataformas ASCII como EBCDIC. A veces, sin embargo, una prueba no puede usar una función y es inconveniente tener diferentes versiones de prueba dependiendo de la plataforma. Hay 20 puntos de código que son los mismos en los 4 conjuntos de caracteres actualmente reconocidos por Perl (las 3 páginas de códigos EBCDIC más ISO 8859-1 (ASCII/Latin1)). Estos se pueden usar en tales pruebas, aunque existe una pequeña posibilidad de que Perl esté disponible en otro conjunto de caracteres, lo que podría romper tu prueba. Todos menos uno de estos puntos de código son caracteres de control C0. Los controles más significativos que son los mismos son "\0", "\r" y "\N{VT}" (también especificable como "\cK", "\x0B", "\N{U+0B}" o "\013"). El único no control es U+00B6 PILCROW SIGN. Los controles que son los mismos tienen el mismo patrón de bits en los 4 conjuntos de caracteres, independientemente de la codificación UTF8 de la cadena que los contiene. El patrón de bits para U+B6 es el mismo en los 4 para cadenas no UTF8, pero difiere en cada una cuando su cadena contenedora está codificada en UTF-8. Los únicos otros puntos de código que tienen algún tipo de similitud en los 4 conjuntos de caracteres son el par 0xDC y 0xFC. Juntos representan letras LATINAS U CON DIÉRESIS mayúscula y minúscula, pero cuál es mayúscula y cuál es minúscula puede invertirse: 0xDC es la mayúscula en Latin1 y 0xFC es la minúscula, mientras que 0xFC es la mayúscula en EBCDIC y 0xDC es la minúscula. Este dato puede ser explotado al escribir pruebas sensibles a mayúsculas y minúsculas que sean iguales en los 4 conjuntos de caracteres.

    IV i = ...;

    Uid_t who = ...;

    El problema aquí es que Uid_t podría no solo no ser del tamaño de un "int", sino que también podría ser sin signo, en cuyo caso los uids grandes se imprimirían como valores negativos.

    IVdf /* IV en decimal */
UVxf /* UV en hexadecimal */

printf("i = %"IVdf"\n", i); /* El IVdf es una constante de cadena. */
Uid_t_f /* Uid_t en decimal */

    La opción de gcc "-Wformat" busca tales problemas.

    • Interfaces del sistema problemáticas

    Hay muchos problemas al usar varias funciones de la biblioteca de C, incluidas las de seguridad. Deberías leer perlclib, que cubre las cosas en detalle.

    Recuerda que las cadenas de Perl NO son lo mismo que las cadenas de C: pueden contener caracteres de "NUL", mientras que una cadena de C termina en el primer "NUL". Esa es la razón por la que las funciones de la API de Perl que manejan cadenas generalmente toman un puntero al primer byte y una longitud o un puntero al byte justo después del último.

    Y esta es la razón por la que muchas de las funciones de manejo de cadenas de la biblioteca de C no deben usarse. No manejan la generalidad completa de las cadenas de Perl. Puede ser que tus casos de prueba no tengan "NUL" incrustados, y por lo tanto las pruebas pasen, mientras que bien puede haber casos del mundo real en los que fallen. Una lección aquí es incluir "NUL"s en tus pruebas. Ahora es bastante raro en la mayoría de los casos del mundo real obtener "NUL"s, por lo que tu código puede parecer funcionar, hasta que un día aparezca un "NUL".

    Aquí tienes un ejemplo. Solía ser un paradigma común, durante décadas, en el núcleo de Perl usar "strchr("lista", c)" para ver si el carácter "c" es alguno de los dados en "lista", una cadena entre comillas dobles con el conjunto de caracteres que estamos viendo si "c" es uno de ellos. Mientras "c" no sea un "NUL", funciona. Pero cuando "c" es un "NUL", "strchr" devuelve un puntero al "NUL" terminador en "lista". Esto probablemente resultará en un fallo de segmentación o un problema de seguridad cuando el llamador use ese puntero final como el punto de partida para leer.

    Una solución para este y muchos otros problemas similares es usar las funciones de la biblioteca de C "mem"-foo en su lugar. En este caso, "memchr" puede usarse para ver si "c" está en "lista" y funciona incluso si "c" es "NUL". Estas funciones necesitan un parámetro adicional para dar la longitud de la cadena. En el caso de parámetros de cadena literales, Perl ha definido macros que calculan la longitud por ti. Ver "String Handling" en perlapi.

    Usar gdb para mirar partes específicas de un programa

    Con el ejemplo anterior, sabías que debías buscar "Perl_pp_add", pero ¿qué pasa si había múltiples llamadas a él por todas partes, o si no sabías qué op estabas buscando?

    study;

    (gdb) break Perl_pp_study

    Y luego dar pasos hasta que encuentres lo que buscas. Esto funciona bien en un bucle si solo quieres detenerte en ciertas iteraciones:

    for my $i (1..100) {

}

    Usar gdb para ver lo que está haciendo el parser/lexer

    print "Before\n";

    (gdb) break Perl_pp_study

    ANÁLISIS ESTÁTICO DEL CÓDIGO FUENTE

    Existen varias herramientas para analizar el código fuente de C **estáticamente**, a diferencia de **dinámicamente**, es decir, sin ejecutar el código. Es posible detectar fugas de recursos, comportamiento indefinido, discrepancias de tipos, problemas de portabilidad, rutas de código que causarían accesos ilegales a memoria y otros problemas similares simplemente analizando el código C y observando el grafo resultante, qué nos dice sobre la ejecución y los flujos de datos. De hecho, así es como los compiladores de C saben dar advertencias sobre código dudoso.

    lint

    El viejo inspector de calidad de código C, "lint", está disponible en varias plataformas, pero ten en cuenta que existen varias implementaciones diferentes por parte de distintos proveedores, lo que significa que las opciones no son idénticas entre plataformas.

    Hay un objetivo "lint" en el Makefile, pero es posible que tengas que ajustar las opciones (ver arriba).

    Coverity

    Coverity (https://www.coverity.com/) es un producto similar a lint y, como campo de pruebas para su producto, analizan periódicamente varios proyectos de código abierto, y otorgan cuentas a los desarrolladores de código abierto para las bases de datos de defectos.

    Hay una configuración de Coverity para el proyecto perl5: https://scan.coverity.com/projects/perl5

    HP-UX cadvise (Code Advisor)

    HP tiene un producto de análisis estático de C/C++ para HP-UX llamado Code Advisor. (El enlace no se proporciona aquí porque la URL es terriblemente larga y parece terriblemente inestable; usa el motor de búsqueda de tu elección para encontrarlo). Se recomienda el uso de la receta "cadvise_cc" con "Configure ... -Dcc=./cadvise_cc" (ver la "Guía del usuario" de cadvise); así como el uso de "+wall".

    cpd (detector de copiar y pegar)

    La herramienta cpd detecta código copiado y pegado. Si una instancia del código copiado y pegado cambia, todos los demás lugares probablemente también deberían cambiarse. Por lo tanto, dicho código debería convertirse probablemente en una subrutina o una macro.

    cpd (https://docs.pmd-code.org/latest/pmd_userdocs_cpd.html) es parte del proyecto pmd (https://pmd.github.io/). pmd fue escrito originalmente para el análisis estático de código Java, pero luego la parte cpd se extendió para analizar también C y C++.

    Descarga pmd-bin-X.Y.zip () del sitio de SourceForge, extrae pmd-X.Y.jar de él, y luego ejecútalo en el código fuente así:

    java -cp pmd-X.Y.jar net.sourceforge.pmd.cpd.CPD \
 --minimum-tokens 100 --files /some/where/src --language c > cpd.txt

    Es posible que te encuentres con límites de memoria, en cuyo caso deberías usar la opción -Xmx:

    java -Xmx512M ...

    Advertencias de gcc

    Aunque se puede escribir mucho sobre la inconsistencia y los problemas de cobertura de las advertencias de gcc (como que "-Wall" no significa "todas las advertencias", o que algunos problemas comunes de portabilidad no están cubiertos por "-Wall", o que "-ansi" y "-pedantic" son ambas una colección mal definida de advertencias, y así sucesivamente), gcc sigue siendo una herramienta útil para mantener nuestra escritura de código limpia.

    "-Wall" está activado por defecto.

    Sería bueno que "-pedantic" estuviera siempre activado, pero lamentablemente no es seguro en todas las plataformas – por ejemplo, conflictos fatales con las cabeceras del sistema (Solaris es un ejemplo principal). Si Configure "-Dgccansipedantic" se usa, el frontend "cflags" selecciona "-pedantic" para las plataformas donde se sabe que es seguro.

    Se añaden las siguientes opciones adicionales:

    • "-Wendif-labels"
    • "-Wextra"
    • "-Wc++-compat"
    • "-Wwrite-strings"
    • "-Werror=pointer-arith"
    • "-Werror=vla"

    Las siguientes opciones serían deseables, pero primero necesitarían su propio gran limpiador:

    • "-Wshadow"
    • "-Wstrict-prototypes"

    "-Wtraditional" es otro ejemplo de la molesta tendencia de gcc a agrupar muchas advertencias bajo un solo interruptor (sería imposible de implementar en la práctica porque se quejaría mucho), pero contiene algunas advertencias que serían beneficiosas tener disponibles por sí solas, como la advertencia sobre constantes de cadena dentro de macros que contienen los argumentos de la macro: esto se comportó de manera diferente antes de ANSI de lo que lo hace en ANSI, y algunos compiladores de C todavía están en transición, siendo AIX un ejemplo.

    Advertencias de otros compiladores C

    Otros compiladores C (sí, **hay** otros compiladores C además de gcc) a menudo tienen sus modos "ANSI estricto" o "ANSI estricto con algunas extensiones de portabilidad" activados, como por ejemplo el Sun Workshop tiene su modo "-Xa" activado (aunque implícitamente), o el DEC (hoy en día, HP...) tiene su modo "-std1" activado.

    DEPURADORES DE MEMORIA

    NOTA 1: Ejecutar bajo depuradores de memoria antiguos como Purify, valgrind o Third Degree ralentiza enormemente la ejecución: los segundos se convierten en minutos, los minutos en horas. Por ejemplo, a partir de Perl 5.8.1, la prueba de *ext/Encode/t/Unicode.t* tarda extraordinariamente mucho en completarse bajo, por ejemplo, Purify, Third Degree y valgrind. Bajo valgrind tarda más de seis horas, incluso en un ordenador rápido. Dicha prueba debe estar haciendo algo bastante poco amigable para los depuradores de memoria. Si no tienes ganas de esperar, puedes simplemente matar el proceso de perl. Aproximadamente, valgrind ralentiza la ejecución en un factor de 10, AddressSanitizer en un factor de 2.

    NOTA 2: Para minimizar el número de falsas alarmas de fugas de memoria (ver "PERL_DESTRUCT_LEVEL" para más información), tienes que establecer la variable de entorno "PERL_DESTRUCT_LEVEL"

    """ a 2. Por ejemplo, así:

    env PERL_DESTRUCT_LEVEL=2 valgrind ./perl -Ilib ...

    NOTA 3: Existen fugas de memoria conocidas cuando hay errores en tiempo de compilación dentro de "eval" o "require"; ver "S_doeval" en la pila de llamadas es un buen indicador de esto. Desafortunadamente, solucionar estas fugas no es trivial, pero deben solucionarse eventualmente.

    NOTA 4: DynaLoader no se limpiará completamente a sí mismo a menos que Perl se compile con la opción de Configuración "-Accflags=-DDL_UNLOAD_ALL_AT_EXIT".

    valgrind

    La herramienta valgrind se puede utilizar para detectar fugas de memoria y accesos ilegales a la memoria del montón. A partir de la versión 3.3.0, Valgrind solo admite Linux en x86, x86-64 y PowerPC, y Darwin (OS X) en x86 y x86-64. El objetivo especial "test.valgrind" se puede usar para ejecutar las pruebas bajo valgrind. Los errores encontrados y las fugas de memoria se registran en archivos llamados testfile.valgrind y, por defecto, la salida se muestra en línea.

    Ejemplo de uso:

    make test.valgrind

    Dado que valgrind agrega una sobrecarga significativa, las pruebas tardarán mucho más en ejecutarse. Las pruebas de valgrind admiten la ejecución en paralelo para ayudar con esto:

    TEST_JOBS=9 make test.valgrind

    Tenga en cuenta que las dos invocaciones anteriores serán muy verborreicas, ya que la memoria accesible y la verificación de fugas están habilitadas por defecto. Si solo desea ver errores puros, intente:

    VG_OPTS='-q --leak-check=no --show-reachable=no' TEST_JOBS=9 \
    make test.valgrind

    Valgrind también proporciona una herramienta llamada cachegrind, que se invoca en perl de la siguiente manera:

    VG_OPTS=--tool=cachegrind make test.valgrind

    Dado que las bibliotecas del sistema (en particular glibc) también generan errores, valgrind permite suprimir dichos errores utilizando archivos de supresión. El archivo de supresión predeterminado que viene con valgrind ya captura muchos de ellos. Algunas supresiones adicionales se definen en t/perl.supp.

    Para obtener valgrind y más información, consulte https://valgrind.org/.

    AddressSanitizer

    AddressSanitizer ("ASan") consta de un módulo de instrumentación del compilador y una biblioteca de ejecución de "malloc". ASan está disponible para una variedad de arquitecturas, sistemas operativos y compiladores (ver enlace del proyecto a continuación). Verifica el uso inseguro de la memoria, como el uso después de la liberación y las condiciones de desbordamiento de búfer, y es lo suficientemente rápido como para compilar fácilmente su perl de depuración u optimizado con él. Las versiones modernas de ASan verifican las fugas de memoria por defecto en la mayoría de las plataformas; de lo contrario (por ejemplo, x86_64 OS X), esta función se puede habilitar a través de "ASAN_OPTIONS=detect_leaks=1".

    Para compilar perl con AddressSanitizer, su invocación de Configure debería verse así:

    sh Configure -des -Dcc=clang \
   -Accflags=-fsanitize=address -Aldflags=-fsanitize=address \
   -Alddlflags=-shared\ -fsanitize=address \
   -fsanitize-blacklist=`pwd`/asan_ignore

    donde estos argumentos significan:

    • -Dcc=clang

      Esto debe reemplazarse con la ruta completa a su ejecutable clang si no está en su PATH.

    • -Accflags=-fsanitize=address

      Compila el código fuente de perl y las extensiones con AddressSanitizer.

    • -Aldflags=-fsanitize=address

      Vincula el ejecutable de perl con AddressSanitizer.

    • -Alddlflags=-shared\ -fsanitize=address

      Vincula las extensiones dinámicas con AddressSanitizer. Debe especificar manualmente "-shared" porque usar "-Alddlflags=-shared" impedirá que Configure establezca un valor predeterminado para "lddlflags", que generalmente contiene "-shared" (al menos en Linux).

    • -fsanitize-blacklist=`pwd`/asan_ignore

      AddressSanitizer ignorará las funciones enumeradas en el archivo "asan_ignore". (Este archivo debe contener una breve explicación de por qué se enumeran cada una de las funciones).

    Ver también https://github.com/google/sanitizers/wiki/AddressSanitizer.

    Dr Memory

    Dr. Memory es una herramienta similar a valgrind que se puede usar en Windows y Linux.

    Admite la verificación del montón como "memcheck" de valgrind. También hay otras herramientas incluidas.

    Ver https://drmemory.org/.

    PERFILADO

    Dependiendo de su plataforma, existen diversas formas de perfilar Perl.

    Hay dos técnicas comúnmente utilizadas para perfilar ejecutables: muestreo estadístico de tiempo y conteo de bloques básicos.

    El primer método toma muestras periódicas del contador de programa de la CPU y, dado que el contador de programa se puede correlacionar con el código generado para funciones, obtenemos una visión estadística de en qué funciones está gastando tiempo el programa. Las advertencias son que las funciones muy pequeñas/rápidas tienen una menor probabilidad de aparecer en el perfil, y que interrumpir el programa periódicamente (esto generalmente se hace con bastante frecuencia, en la escala de milisegundos) impone una sobrecarga adicional que puede sesgar los resultados. El primer problema se puede aliviar ejecutando el código durante más tiempo (en general, esto es una buena idea para perfilar), el segundo problema se mantiene bajo control por las propias herramientas de perfilado.

    El segundo método divide el código generado en bloques básicos. Los bloques básicos son secciones de código a las que solo se accede al principio y solo se sale al final. Por ejemplo, un salto condicional inicia un bloque básico. El perfilado de bloques básicos generalmente funciona instrumentando el código al agregar código de contabilidad de entrada al bloque básico n.º nnnn al código generado. Durante la ejecución del código, los contadores de bloques básicos se actualizan apropiadamente. La advertencia es que el código adicional agregado puede sesgar los resultados: nuevamente, las herramientas de perfilado generalmente intentan excluir sus propios efectos de los resultados.

    Perfilado Gprof

    gprof es una herramienta de perfilado disponible en muchas plataformas Unix que utiliza muestreo estadístico de tiempo. Puede compilar una versión perfilada de perl compilando con gcc y la bandera "-pg". Edite config.sh o vuelva a ejecutar Configure. La ejecución de la versión perfilada de Perl creará un archivo de salida llamado gmon.out que contiene los datos de perfilado recopilados durante la ejecución.

    consejo rápido:

    $ sh Configure -des -Dusedevel -Accflags='-pg' \
    -Aldflags='-pg' -Alddlflags='-pg -shared' \
    && make perl
$ ./perl ... # crea gmon.out en el directorio actual
$ gprof ./perl > out
$ less out

    (probablemente necesite agregar "-shared" a la línea <-Alddlflags> hasta que se resuelva RT #118199)

    La herramienta gprof puede mostrar los datos recopilados de varias maneras. Por lo general, gprof entiende las siguientes opciones:

    • -a

      Suprimir funciones definidas estáticamente del perfil.

    • -b

      Suprimir las descripciones detalladas en el perfil.

    • -e rutina

      Excluir la rutina dada y sus descendientes del perfil.

    • -f routine

      Mostrar solo la rutina dada y sus descendientes en el perfil.

    • -s

      Generar un archivo resumen llamado gmon.sum que luego puede darse a ejecuciones posteriores de gprof para acumular datos durante varias ejecuciones.

    • -z

      Mostrar rutinas que tienen cero uso.

    Para una explicación más detallada de los comandos disponibles y los formatos de salida, consulte la documentación local de gprof.

    Perfilado GCC gcov

    El perfilado de bloques básicos está disponible oficialmente en gcc 3.0 y posteriores. Puede compilar una versión perfilada de perl compilando con gcc y las banderas "-fprofile-arcs -ftest-coverage". Edite config.sh o vuelva a ejecutar Configure.

    consejo rápido:

    $ sh Configure -des -Dusedevel -Doptimize='-g' \
    -Accflags='-fprofile-arcs -ftest-coverage' \
    -Aldflags='-fprofile-arcs -ftest-coverage' \
    -Alddlflags='-fprofile-arcs -ftest-coverage -shared' \
    && make perl
$ rm -f regexec.c.gcov regexec.gcda
$ ./perl ...
$ gcov regexec.c
$ less regexec.c.gcov

    (probablemente necesite agregar "-shared" a la línea <-Alddlflags> hasta que se resuelva RT #118199)

    La ejecución de la versión perfilada de Perl generará una salida de perfil. Para cada archivo fuente, se creará un archivo .gcda correspondiente.

    Para mostrar los resultados, utilice la utilidad gcov (que debería estar instalada si tiene gcc 3.0 o posterior). gcov se ejecuta en archivos de código fuente, como este:

    gcov sv.c

    lo que hará que se cree sv.c.gcov. Los archivos .gcov contienen el código fuente anotado con frecuencias relativas de ejecución indicadas por marcadores "#". Si desea generar archivos .gcov para todos los archivos objeto perfilados, puede ejecutar algo como esto:

    for file in `find . -name \*.gcno`
do sh -c "cd `dirname $file` && gcov `basename $file .gcno`"
done

    Las opciones útiles de gcov incluyen "-b", que resumirá la cobertura de bloques básicos, ramas y llamadas a funciones, y "-c", que en lugar de frecuencias relativas utilizará los recuentos reales. Para obtener más información sobre el uso de gcov y el perfilado de bloques básicos con gcc, consulte el último manual de GNU CC. A partir de gcc 4.8, se encuentra en https://gcc.gnu.org/onlinedocs/gcc/Gcov-Intro.html#Gcov-Intro.

    NAME

    perl - tips for hacking on Perl

    DESCRIPTION

    This document contains various tips and tricks for hacking on Perl itself, or for developing extensions for Perl.

    It is not intended as a guide to writing Perl programs, but rather as a collection of hints for those who wish to understand or modify Perl's internals, or to write C extensions for Perl.

    Building Perl

    Most Perl source code is maintained in a Git repository. For details on obtaining and using the repository, see the README file in the repository root.

    Building Perl on Unix-like systems is usually done using the "Configure" script and then "make".

    A typical configuration might look like:

    sh Configure -des -Dprefix=/path/to/perl
make
make install

    You may want to add options to Configure to enable debugging, profiling, or other features. See "Configure -h" for a full list of options.

    The Perl Core List

    The "perl5-porters@perl.org" mailing list is where the development of Perl happens. You can find the list archives online. Subscribe to the list if you want to be involved or stay informed.

    COMMON PROBLEMS

    If you're new to hacking Perl, you may find yourself running into some common pitfalls. Here are a few tips:

    Integer overflows

    Perl's numbers are usually doubles, but they can be silently converted to integers when appropriate. This can lead to overflows, especially on 32-bit systems. Configure Perl with "-Dusemorebits" to use 64-bit integers where possible. Also consider using "-Dusemathiota" for better math support, and "-Dlongwarn" to warn about long values that might truncate on conversion.

    String to number conversions

    Perl's string-to-number conversion can sometimes be surprising. If you're debugging code that relies on these conversions, you might want to enable warnings in Perl itself. Configure Perl with "-Dwarnings".

    Memory leaks

    Memory leaks are a common problem in C development, and Perl is no exception. If you suspect a memory leak, try using a memory debugger like Valgrind or build Perl with debugging options enabled. The "Perl_debug" macro can be helpful here.

    DEBUGGING

    Using gdb

    To debug Perl with gdb, you'll need to compile Perl with debugging symbols. Use the "-g" flag during compilation. You may also want to disable optimizations (e.g., use "-O0").

    Once Perl is compiled, you can run it under gdb like this:

    gdb perl
(gdb) run script.pl

    You can set breakpoints in C code using "break function_name" or in Perl code using "break file.pl:line".

    C backtrace

    On some platforms Perl supports retrieving the C level backtrace (similar to what symbolic debuggers like gdb do).

    The backtrace returns the stack trace of the C call frames, with the symbol names (function names), the object names (like "perl"), and if it can, also the source code locations (file:line).

    The supported platforms are Linux, and OS X (some *BSD might work at least partly, but they have not yet been tested).

    This feature hasn't been tested with multiple threads, but it will only show the backtrace of the thread doing the backtracing.

    The feature needs to be enabled with "Configure -Dusecbacktrace".

    The "-Dusecbacktrace" also enables keeping the debug information when compiling/linking (often: "-g"). Many compilers/linkers do support having both optimization and keeping the debug information. The debug information is needed for the symbol names and the source locations.

    Static functions might not be visible for the backtrace.

    Source code locations, even if available, can often be missing or misleading if the compiler has e.g. inlined code. Optimizer can make matching the source code and the object code quite challenging.

    Linux
    You must have the BFD (-lbfd) library installed, otherwise "perl" will fail to link. The BFD is usually distributed as part of the GNU binutils.

    Summary: "Configure ... -Dusecbacktrace" and you need "-lbfd".

    OS X
    The source code locations are supported only if you have the Developer Tools installed. (BFD is not needed.)

    Summary: "Configure ... -Dusecbacktrace" and installing the Developer Tools would be good.

    Optionally, for trying out the feature, you may want to enable automatic dumping of the backtrace just before a warning or croak (die) message is emitted, by adding "-Accflags=-DUSE_C_BACKTRACE_ON_ERROR" for Configure.

    Unless the above additional feature is enabled, nothing about the backtrace functionality is visible, except for the Perl/XS level.

    Furthermore, even if you have enabled this feature to be compiled, you need to enable it in runtime with an environment variable: "PERL_C_BACKTRACE_ON_ERROR=10". It must be an integer higher than zero, telling the desired frame count.

    Retrieving the backtrace from Perl level (using for example an XS extension) would be much less exciting than one would hope: normally you would see "runops", "entersub", and not much else. This API is intended to be called from within the Perl implementation, not from Perl level execution.

    The C API for the backtrace is as follows:

    get_c_backtrace
    free_c_backtrace
    get_c_backtrace_dump
    dump_c_backtrace

    SOURCE CODE STATIC ANALYSIS

    Some tools can help find potential bugs in C code before runtime.

    Finding unsafe truncations

    You may wish to run "Configure" with something like

    -Accflags='-Wconversion -Wno-sign-conversion -Wno-shorten-64-to-32'

    or your compiler's equivalent to make it easier to spot any unsafe truncations that show up.

    MEMORY DEBUGGERS

    Poison

    If you see in a debugger a memory area mysteriously full of 0xABABABAB or 0xEFEFEFEF, you may be seeing the effect of the Poison() macros, see perlclib.

    PROFILING

    To profile Perl itself, you can use standard C profiling tools like gprof. Compile Perl with the "-pg" flag, then run your script. You can then analyze the results with gprof.

    You can also use perf (Linux) or dtrace (macOS/BSD) for more advanced profiling.

    MISCELLANEOUS TRICKS

    Read-only optrees

    Under ithreads the optree is read only. If you want to enforce this, to check for write accesses from buggy code, compile with "-Accflags=-DPERL_DEBUG_READONLY_OPS" to enable code that allocates op memory via "mmap", and sets it read-only when it is attached to a subroutine. Any write access to an op results in a "SIGBUS" and abort.

    This code is intended for development only, and may not be portable even to all Unix variants. Also, it is an 80% solution, in that it isn't able to make all ops read only. Specifically it does not apply to op slabs belonging to "BEGIN" blocks.

    However, as an 80% solution it is still effective, as it has caught bugs in the past.

    When is a bool not a bool?

    There wasn't necessarily a standard "bool" type on compilers prior to C99, and so some workarounds were created. The "TRUE" and "FALSE" macros are still available as alternatives for "true" and "false". And the "cBOOL" macro was created to correctly cast to a true/false value in all circumstances, but should no longer be necessary. Using "(bool)" expr should now always work.

    There are no plans to remove any of "TRUE", "FALSE", nor "cBOOL".

    The .i Targets

    You can expand the macros in a foo.c file by saying

    make foo.i

    which will expand the macros using cpp. Don't be scared by the results.
