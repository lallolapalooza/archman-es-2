PERF-RECORD(1) Manual de perf PERF-RECORD(1)

NOMBRE

perf-record - Ejecuta un comando y registra su perfil en perf.data

SINOPSIS

perf record [-e <EVENTO> | --event=EVENTO] [-a] <comando>
perf record [-e <EVENTO> | --event=EVENTO] [-a] -- <comando> [<opciones>]

DESCRIPCIÓN

Este comando ejecuta un comando y recopila un perfil de contador de rendimiento del mismo, en perf.data, sin mostrar nada.

Este archivo puede ser inspeccionado posteriormente, usando perf report.

OPCIONES

<comando>...

Cualquier comando que puedas especificar en un shell.

-e, --event=

Selecciona el evento PMU. La selección puede ser:
•un nombre de evento simbólico (usa perf list para listar todos los eventos)
•un evento PMU crudo en el formato rN donde N es un valor hexadecimal que representa la codificación del registro crudo con el diseño de los registros de control de eventos descrito por las entradas en /sys/bus/event_source/devices/cpu/format/*.
•un evento PMU simbólico o crudo seguido opcionalmente por dos puntos y una lista de modificadores de eventos, por ejemplo, cpu-cycles:p. Consulta la página del manual de perf-list(1) para obtener detalles sobre los modificadores de eventos.
•un evento PMU formado simbólicamente como pmu/param1=0x3,param2/ donde param1, param2, etc. se definen como formatos para el PMU en /sys/bus/event_source/devices/<pmu>/format/*.
•un evento formado simbólicamente como pmu/config=M,config1=N,config3=K/ 
donde M, N, K son números (en formato decimal, hexadecimal, octal). Los
valores aceptables para cada uno de 'config', 'config1' y 'config2' se
definen por entradas correspondientes en /sys/bus/event_source/devices/<pmu>/format/*
param1 y param2 se definen como formatos para el PMU en:
/sys/bus/event_source/devices/<pmu>/format/*
También hay algunos parámetros que no están definidos en .../<pmu>/format/*.
Estos parámetros se pueden usar para sobreescribir los valores de configuración
predeterminados por evento. Aquí hay algunos parámetros comunes:
- 'period': Establece el período de muestreo del evento
- 'freq': Establece la frecuencia de muestreo del evento
- 'time': Deshabilita/habilita la marca de tiempo. Los valores aceptables son 1
          para habilitar la marca de tiempo. 0 para deshabilitar la marca de tiempo.
          El valor predeterminado es 1.
- 'call-graph': Deshabilita/habilita el grafo de llamadas. Las cadenas aceptables
                son "fp" para el modo FP, "dwarf" para el modo DWARF, "lbr" para
                el modo LBR y "no" para deshabilitar el grafo de llamadas.
- 'stack-size': tamaño de la pila del usuario para el modo dwarf
- 'name' : Nombre de evento definido por el usuario. Las comillas simples (') pueden
          usarse para escapar símbolos en el nombre del análisis por el shell y
          herramientas como esta: name=\'CPU_CLK_UNHALTED.THREAD:cmask=0x1\'.
- 'aux-output': Genera registros AUX en lugar de eventos. Esto requiere que también
                se proporcione un evento de área AUX.
- 'aux-action': "pause" o "resume" para pausar o reanudar un área AUX (el líder del
                grupo) cuando ocurre este evento. "start-paused" en un evento de
                área AUX, comenzará en estado pausado.
- 'aux-sample-size': Establece el tamaño de muestra para el muestreo de área AUX. Si
'--aux-sample' se ha utilizado, establezca aux-sample-size=0 para deshabilitar
el muestreo de área AUX para el evento.
Consulta la página del manual perf:perf-list[1] para más parámetros.
Nota: Si el usuario establece explícitamente opciones que entran en conflicto con
los parámetros, el valor establecido por los parámetros será anulado.
Tampoco se definen en .../<pmu>/format/* parámetros de configuración
específicos del controlador PMU. Cualquier parámetro de configuración precedido
por la letra '@' no se interpreta en el espacio de usuario y se envía
directamente al controlador PMU. Por ejemplo:
perf record -e some_event/@cfg1,@cfg2=config/ ...
verá 'cfg1' y 'cfg2=config' enviados al controlador PMU asociado con el evento
para su procesamiento posterior. No hay restricción en cuáles son los parámetros
de configuración, siempre que su semántica sea entendida y soportada por el
controlador PMU.
•un evento de punto de interrupción de hardware en el formato \mem:dirección[/longitud][:acceso] donde dirección es la dirección en memoria en la que deseas interrumpir. Acceso es el tipo de acceso a memoria (lectura, escritura, ejecución) se puede pasar de la siguiente manera: \mem:dirección[:[r][w][x]]. longitud es el rango, número de bytes desde la dirección especificada, que cubrirá el punto de interrupción. Si deseas perfilar accesos de lectura-escritura en 0x1000, simplemente establece mem:0x1000:rw. Si deseas perfilar accesos de escritura en [0x1000~1008), simplemente establece mem:0x1000/8:w.
•un grupo de eventos rodeados por un par de llaves ("{evento1,evento2,...}"). Cada evento se separa por comas y el grupo debe estar entre comillas para evitar la interpretación del shell. También necesitarás usar --group en "perf report" para ver los eventos de grupo juntos.

--filter=<filtro>

Filtro de eventos. Esta opción debe seguir a un selector de eventos (-e). Si el evento es un tracepoint, la cadena de filtro será analizada por el kernel. Si el evento es un PMU de traza de hardware (por ejemplo, Intel PT o CoreSight), se procesará como un filtro de dirección. De lo contrario, significa un filtro general usando BPF que se puede aplicar a cualquier tipo de evento.
•filtros de tracepoint 
En el caso de tracepoints, múltiples opciones '--filter' se combinan usando
'&&'.
•filtros de dirección 
Un PMU de traza de hardware anuncia su capacidad para aceptar un número de
filtros de dirección especificando un valor distinto de cero en
/sys/bus/event_source/devices/<pmu>/nr_addr_filters.
Los filtros de dirección tienen el formato:
filtro|inicio|parar|tracestop <inicio> [/ <tamaño>] [@<nombre de archivo>]
Donde:
- 'filtro': define una región que será rastreada.
- 'inicio': define una dirección en la que comenzará el rastreo.
- 'parar': define una dirección en la que se detendrá el rastreo.
- 'tracestop': define una región en la que se detendrá el rastreo.
<nombre de archivo> es el nombre del archivo objeto, <inicio> es el desplazamiento
al código a rastrear en ese archivo, y <tamaño> es el tamaño de la región a
rastrear. Los filtros 'inicio' y 'parar' no necesitan especificar un <tamaño>.
Si no se especifica un archivo objeto, se asume el kernel, en cuyo caso
la dirección de inicio debe ser una dirección de memoria del kernel actual.
<inicio> también se puede especificar proporcionando el nombre de un símbolo. Si
el nombre del símbolo no es único, se puede desambiguar insertando #n donde 'n'
selecciona el n-ésimo símbolo en orden de dirección. Alternativamente, #0, #g o #G
seleccionan solo un símbolo global. <tamaño> también se puede especificar
proporcionando el nombre de un símbolo, en cuyo caso el tamaño se calcula hasta el
final de ese símbolo. Para los filtros 'filtro' y 'tracestop', si se omite
<tamaño> y <inicio> es un símbolo, entonces el tamaño se calcula hasta el final
de ese símbolo.
Si se omite <tamaño> y <inicio> es '*', entonces el inicio y el tamaño se
calcularán a partir del primer y último símbolo, es decir, para rastrear todo el
archivo.
Si se proporcionan nombres de símbolos (o '*'), deben estar rodeados por espacios
en blanco.
El filtro que se pasa al kernel no es necesariamente el mismo que se ingresó.
Para ver el filtro que se pasa, usa la opción -v.
Es posible que el kernel no pueda configurar una región de traza si no está
dentro de un único mapeo. Los eventos MMAP (o /proc/<pid>/maps) se pueden
examinar para determinar si esa es una posibilidad.
Múltiples filtros pueden separarse con espacio o coma.
•filtros bpf 
Un filtro BPF puede acceder a los datos de muestra y tomar una decisión basada en
los datos. Los usuarios deben establecer un tipo de muestra apropiado para usar el
filtro BPF. Los filtros BPF requieren privilegios de root.
El campo de datos de muestra se puede especificar en letras minúsculas. Múltiples
filtros se pueden separar con comas. Por ejemplo,
  --filter 'period > 1000, cpu == 1'
o
  --filter 'mem_op == load || mem_op == store, mem_lvl > l1'
El primer filtro solo acepta muestras con un período mayor que 1000 Y el número
de CPU es 1. El segundo acepta operaciones de memoria de carga o almacenamiento,
pero debería tener un nivel de memoria por encima de L1. Dado que los campos
mem_op y mem_lvl provienen de la fuente de datos (memoria)

PERF-RECORD --filter <filter> Filter events based on BPF programs. Example: Record only load events: 
$ sudo perf record -e cycles --filter 'mem_op == load' -d
Note that this only works with some events which set the data_source field. Also user should request to collect that information (with -d option in the above case). Otherwise, the following message will be shown. 
$ sudo perf record -e cycles --filter 'mem_op == load'
Error: cycles event does not have PERF_SAMPLE_DATA_SRC
 Hint: please add -d option to perf record.
failed to set filter "BPF" on event cycles with 22 (Invalid
argument)
Essentially the BPF filter expression is: 
<term> <operator> <value> (("," | "||") <term> <operator> <value>)*
The <term> can be one of: ip, id, tid, pid, cpu, time, addr, period, txn, weight, phys_addr, code_pgsz, data_pgsz, weight1, weight2, weight3, ins_lat, retire_lat, p_stage_cyc, mem_op, mem_lvl, mem_snoop, mem_remote, mem_lock, mem_dtlb, mem_blk, mem_hops, uid, gid The <operator> can be one of: ==, !=, >, >=, <, <=, & The <value> can be one of: <number> (for any term) na, load, store, pfetch, exec (for mem_op) l1, l2, l3, l4, cxl, io, any_cache, lfb, ram, pmem (for mem_lvl) na, none, hit, miss, hitm, fwd, peer (for mem_snoop) remote (for mem_remote) na, locked (for mem_locked) na, l1_hit, l1_miss, l2_hit, l2_miss, any_hit, any_miss, walk, fault (for mem_dtlb) na, by_data, by_addr (for mem_blk) hops0, hops1, hops2, hops3 (for mem_hops) --exclude-perf Don’t record events issued by perf itself. This option should follow an event selector (-e) which selects tracepoint event(s). It adds a filter expression common_pid != $PERFPID to filters. If other --filter exists, the new filter expression will be combined with them by &&. --latency Enable data collection for latency profiling. Use perf report --latency for latency-centric profile. -a, --all-cpus System-wide collection from all CPUs (default if no target is specified). -p, --pid= Record events on existing process ID (comma separated list). -t, --tid= Record events on existing thread ID (comma separated list). This option also disables inheritance by default. Enable it by adding --inherit. -u, --uid= Record events in threads owned by uid. Name or number. -r, --realtime= Collect data with this RT SCHED_FIFO priority. --no-buffering Collect data without buffering. -c, --count= Event period to sample. -o, --output= Output file name. -i, --no-inherit Child tasks do not inherit counters. -F, --freq= Profile at this frequency. Use max to use the currently maximum allowed frequency, i.e. the value in the kernel.perf_event_max_sample_rate sysctl. Will throttle down to the currently maximum allowed frequency. See --strict-freq. --strict-freq Fail if the specified frequency can’t be used. -m, --mmap-pages= Number of mmap data pages (must be a power of two) or size specification in bytes with appended unit character - B/K/M/G. The size is rounded up to the nearest power-of-two page value. By adding a comma, an additional parameter with the same semantics used for the normal mmap areas can be specified for AUX tracing area. -g Enables call-graph (stack chain/backtrace) recording for both kernel space and user space. --call-graph Setup and enable call-graph (stack chain/backtrace) recording, implies -g. Default is "fp" (for user space). The unwinding method used for kernel space is dependent on the unwinder used by the active kernel configuration, i.e CONFIG_UNWINDER_FRAME_POINTER (fp) or CONFIG_UNWINDER_ORC (orc) Any option specified here controls the method used for user space. Valid options are "fp" (frame pointer), "dwarf" (DWARF's CFI - Call Frame Information) or "lbr" (Hardware Last Branch Record facility). In some systems, where binaries are build with gcc --fomit-frame-pointer, using the "fp" method will produce bogus call graphs, using "dwarf", if available (perf tools linked to the libunwind or libdw library) should be used instead. Using the "lbr" method doesn't require any compiler options. It will produce call graphs from the hardware LBR registers. The main limitation is that it is only available on new Intel platforms, such as Haswell. It can only get user call chain. It doesn't work with branch stack sampling at the same time. When "dwarf" recording is used, perf also records (user) stack dump when sampled. Default size of the stack dump is 8192 (bytes). User can change the size by passing the size after comma like "--call-graph dwarf,4096". When "fp" recording is used, perf tries to save stack entries up to the number specified in sysctl.kernel.perf_event_max_stack by default. User can change the number by passing it after comma like "--call-graph fp,32". -q, --quiet Don’t print any warnings or messages, useful for scripting. -v, --verbose Be more verbose (show counter open errors, etc). -s, --stat Record per-thread event counts. Use it with perf report -T to see the values. -d, --data Record the sample virtual addresses. Implies --sample-mem-info. --phys-data Record the sample physical addresses. --data-page-size Record the sampled data address data page size. --code-page-size Record the sampled code address (ip) page size -T, --timestamp Record the sample timestamps. Use it with perf report -D to see the timestamps, for instance. -P, --period Record the sample period. --sample-cpu Record the sample cpu. --sample-identifier Record the sample identifier i.e. PERF_SAMPLE_IDENTIFIER bit set in the sample_type member of the struct perf_event_attr argument to the perf_event_open system call. --sample-mem-info Record the sample data source information for memory operations. It requires hardware supports and may work on specific events only. Please consider using perf mem record instead if you’re not sure. -n, --no-samples Don’t sample. -R, --raw-samples Collect raw sample records from all opened counters (default for tracepoint counters). -C, --cpu Collect samples only on the list of CPUs provided. Multiple CPUs can be provided as a comma-separated list with no space: 0,1. Ranges of CPUs are specified with -: 0-2. In per-thread mode with inheritance mode on (default), samples are captured only when the thread executes on the designated CPUs. Default is to monitor all CPUs. User space tasks can migrate between CPUs, so when tracing selected CPUs, a dummy event is created to track sideband for all CPUs. -B, --no-buildid Do not save the build ids of binaries in the perf.data files. This skips post processing after recording, which sometimes makes the final step in the recording process to take a long time, as it needs to process all events looking for mmap records. The downside is that it can misresolve symbols if the workload binaries used when recording get locally rebuilt or upgraded, because the only key available in this case is the pathname. You can also set the "record.build-id" config variable to 'skip to have this behaviour permanently. -N, --no-buildid-cache Do not update the buildid cache. This saves some overhead in situations where the information in the perf.data file (which includes buildids) is sufficient. You can also set the "record.build-id" config variable to no-cache to have the same effect. -G name,..., --cgroup name,... monitor only in the container (cgroup) called "name". This option is available only in per-cpu mode. The cgroup filesystem must be mounted. All threads belonging to container "name" are monitored when they run on the monitored CPUs. Multiple cgroups can be provided. Each cgroup is applied to the corresponding event, i.e., first cgroup to first event, second cgroup to second event and so on. It is possible to provide an empty cgroup (monitor all the time) using, e.g., -G foo,,bar. Cgroups must have corresponding events, i.e., they always refer to events defined earlier on the command line. If the user wants to track multiple events for a specific cgroup, the user can use -e e1 -e e2 -G foo,foo or just use -e e1 -e e2 -G foo. If wanting to monitor, say, cycles for a cgroup and also for system wide, this command line can be used: perf stat -e cycles -G cgroup_name -a -e cycles. -b, --branch-any Enable taken branch stack sampling. Any type of taken branch may be sampled. This is a shortcut for --branch-filter any. See --branch-filter for more infos. -j, --branch-filter Enable taken branch stack sampling. Each sample captures a series of consecutive taken branches. The number of branches captured with each sample depends on the underlying hardware, the type of branches of interest, and the executed code. It is possible to select the types of branches captured by enabling filters. The following filters are defined: •any: any type of branches •any_call: any function call or system call •any_ret: any function return or system call return •ind_call: any indirect branch •ind_jmp: any indirect jump •call: direct calls, including far (to/from kernel) calls •u: only when the branch target is at the user level •k: only when the branch target is in the kernel •hv: only when the target is at the hypervisor level
•in_tx: solo cuando el objetivo está en una transacción de hardware
•no_tx: solo cuando el objetivo no está en una transacción de hardware
•abort_tx: solo cuando el objetivo es un aborto de transacción de hardware
•cond: ramas condicionales
•call_stack: guardar pila de llamadas
•no_flags: no guardar flags de rama, por ejemplo, predicción, predicción errónea, etc.
•no_cycles: no guardar ciclos de rama
•hw_index: guardar índice de hardware de rama
•save_type: guardar tipo de rama durante el muestreo en caso de que el binario no esté disponible más tarde. Para las plataformas con soporte de Intel Arch LBR (cliente de 12ª generación o posterior o servidor Xeon de 4ª generación o posterior), el tipo de rama guardada se habilita incondicionalmente cuando se habilita el muestreo de la pila de ramas tomadas.
•priv: guardar estado de privilegio durante el muestreo en caso de que el binario no esté disponible más tarde
•counter: guardar ocurrencias del evento desde la última entrada de rama. Actualmente, la función solo es compatible con CPUs más nuevas, por ejemplo, Intel Sierra Forest y plataformas posteriores. Se espera un error si se utiliza en un kernel o CPUs no compatibles.

La opción requiere al menos un tipo de rama entre any, any_call, any_ret, ind_call, cond. Los niveles de privilegio pueden omitirse, en cuyo caso, los niveles de privilegio del evento asociado se aplican al filtro de rama. Tanto los niveles de privilegio del kernel (k) como del hipervisor (hv) están sujetos a permisos. Al muestrear en varios eventos, el muestreo de la pila de ramas se habilita para todos los eventos de muestreo. El tipo de rama muestreado es el mismo para todos los eventos. Los diversos filtros deben especificarse como una lista separada por comas: --branch-filter any_ret,u,k. Tenga en cuenta que esta función puede no estar disponible en todos los procesadores.

-W, --weight

Habilita el muestreo ponderado. Se registra un peso adicional por muestra y se puede mostrar con las claves de ordenación weight y local_weight. Actualmente, esto funciona para eventos de aborto TSX y algunos eventos de memoria en modo preciso en CPUs Intel modernas.

--namespaces

Registra eventos de tipo PERF_RECORD_NAMESPACES. Esto habilita la clave de ordenación cgroup_id.

--all-cgroups

Registra eventos de tipo PERF_RECORD_CGROUP. Esto habilita la clave de ordenación cgroup.

--transaction

Registra flags de transacción para eventos relacionados con transacciones.

--per-thread

Utiliza mmaps por hilo. Por defecto, se crean mmaps por CPU. Esta opción anula eso y utiliza mmaps por hilo. Un efecto secundario de esto es que la herencia se deshabilita automáticamente. --per-thread se ignora con una advertencia si se combina con las opciones -a o -C.

-D, --delay=

Después de iniciar el programa, espere milisegundos antes de medir (-1: iniciar con eventos deshabilitados), o habilite eventos solo para rangos especificados de milisegundos (por ejemplo, -D 10-20,30-40 significa esperar 10 ms, habilitar durante 10 ms, esperar 10 ms, habilitar durante 10 ms, luego detener). Tenga en cuenta que retrasar la habilitación de eventos es útil para filtrar la fase de inicio del programa, que a menudo es muy diferente.

-I, --intr-regs

Captura el estado de la máquina (registros) en la interrupción, es decir, en desbordamientos de contador para cada muestra. La lista de registros capturados depende de la arquitectura. Esta opción está desactivada por defecto. Es posible seleccionar los registros a muestrear utilizando sus nombres simbólicos, por ejemplo, en x86, ax, si. Para listar los registros disponibles use --intr-regs=\?. Para nombrar registros, pase una lista separada por comas como --intr-regs=ax,bx. La lista de registros depende de la arquitectura.

--user-regs

Similar a -I, pero captura registros de usuario en el momento de la muestra. Para listar los registros de usuario disponibles use --user-regs=\?.

--running-time

Registra el tiempo de ejecución y habilitado para eventos de lectura (:S)

-k, --clockid

Establece el ID de reloj a utilizar para los diversos campos de tiempo en los registros perf_event_type. Consulte clock_gettime(). En particular, se admiten CLOCK_MONOTONIC y CLOCK_MONOTONIC_RAW, algunos eventos también pueden permitir CLOCK_BOOTTIME, CLOCK_REALTIME y CLOCK_TAI.

-S, --snapshot

Selecciona el modo Snapshot del trazado del área AUX. Esta opción solo es válida con un evento de trazado del área AUX. Opcionalmente, ciertos parámetros de captura de snapshot se pueden especificar en una cadena que sigue a esta opción:
•e: toma una última instantánea al salir; garantiza que haya al menos una instantánea en el archivo de salida;
•<size>: si el PMU lo admite, especifique el tamaño de instantánea deseado.

En el Modo Snapshot, los datos de trazado se capturan solo cuando se recibe la señal SIGUSR2 y al salir si se proporciona la opción e anterior.

--aux-sample[=OPTIONS]

Selecciona el muestreo del área AUX. Al menos uno de los eventos seleccionados por la opción -e debe ser un evento del área AUX. Se crearán muestras en otros eventos que contendrán datos del área AUX. Opcionalmente, se puede especificar el tamaño de la muestra; de lo contrario, el valor predeterminado es 4KiB.

--proc-map-timeout

Al procesar hilos preexistentes /proc/XXX/mmap, puede llevar mucho tiempo, ya que el archivo puede ser enorme. Se necesita un tiempo de espera en tales casos. Esta opción establece el límite de tiempo de espera. El valor predeterminado es 500 ms.

--switch-events

Registra eventos de cambio de contexto, es decir, eventos de tipo PERF_RECORD_SWITCH o PERF_RECORD_SWITCH_CPU_WIDE. En algunos casos (por ejemplo, Intel PT, CoreSight o Arm SPE), los eventos de cambio se habilitarán automáticamente, lo que se puede suprimir con la opción --no-switch-events.

--vmlinux=PATH

Especifica la ruta de vmlinux que tiene información de depuración. (habilitado cuando el prólogo BPF está activado)

--buildid-all

Registra el ID de compilación de todos los DSO, independientemente de si se alcanzan o no.

--buildid-mmap

Opción heredada para registrar build-id en eventos map, que ahora es el valor predeterminado. Se comporta de manera idéntica a --no-buildid. Deshabilítelo con --no-buildid-mmap.

--aio[=n]

Utiliza <n> bloques de control en modo de escritura de traza asíncrona (Posix AIO) (predeterminado: 1, máximo: 4). El modo asíncrono solo se admite al vincular la herramienta Perf con la biblioteca libc que proporciona la implementación de la API Posix AIO.

--affinity=mode

Establece la máscara de afinidad del hilo de lectura de trazas según la política definida por el valor mode:
•node - la máscara de afinidad del hilo se establece en la máscara de CPU del nodo NUMA del búfer mmap procesado
•cpu - la máscara de afinidad del hilo se establece en la CPU del búfer mmap procesado

--mmap-flush=number

Especifica el número mínimo de bytes que se extraen de las páginas de datos mmap y se procesan para la salida. Se puede especificar el número utilizando sufijos B/K/M/G.

El valor máximo permitido es una cuarta parte del tamaño de las páginas de datos mmaped.

La opción predeterminada es 1 byte, lo que significa que cada vez que el hilo de escritura de salida encuentra datos nuevos en el búfer mmaped, los datos se extraen, posiblemente se comprimen (-z) y se escriben en la salida, perf.data o tubería.

Los fragmentos de datos más grandes se comprimen de manera más efectiva en comparación con los fragmentos más pequeños, por lo que la extracción de fragmentos más grandes de las páginas de datos mmap es preferible desde la perspectiva de la reducción del tamaño de la salida.

Además, en algunos casos, ejecutar menos llamadas al sistema de escritura de salida con un tamaño de datos mayor puede llevar menos tiempo que ejecutar más llamadas al sistema de escritura de salida con un tamaño de datos menor, lo que reduce la sobrecarga del perfilado en tiempo de ejecución.

-z, --compression-level[=n]

Produce traza comprimida utilizando el nivel n especificado (predeterminado: 1 - compresión más rápida, 22 - traza más pequeña)

--all-kernel

Configura todos los eventos utilizados para ejecutarse en el espacio del kernel.

--all-user

Configura todos los eventos utilizados para ejecutarse en el espacio del usuario.

--kernel-callchains

Recopila cadenas de llamadas solo desde el espacio del kernel. Es decir, esta opción establece perf_event_attr.exclude_callchain_user a 1.

--user-callchains

Recopila cadenas de llamadas solo desde el espacio del usuario. Es decir, esta opción establece perf_event_attr.exclude_callchain_kernel a 1.

No utilice --kernel-callchains y --user-callchains al mismo tiempo, o no se recopilarán cadenas de llamadas.

--timestamp-filename Anexa la marca de tiempo al nombre del archivo de salida.

--timestamp-boundary

Registra el límite de marca de tiempo (hora de la primera/última muestra).

--switch-output[=mode]

Genera múltiples archivos perf.data, con prefijo de marca de tiempo, cambiando a uno nuevo según el valor mode:
•"signal" - al recibir una SIGUSR2 (valor predeterminado) o
•<size> - al alcanzar el umbral de tamaño, se espera que el tamaño sea un número con una unidad de sufijo - B/K/M/G
•<time> - al alcanzar el umbral de tiempo, se espera que el tamaño sea un número con una unidad de sufijo - s/m/h/d 
Nota: la precisión del umbral de tamaño depende en gran medida
de su configuración: el número y el tamaño de sus búferes de
anillo (-m). Generalmente es más preciso para tamaños mayores
(como >5M), para valores más bajos espere tamaños diferentes.

Un caso de uso posible es, dado un evento externo, dividir el archivo perf.data que luego se procesa, posiblemente a través de un script perf, para decidir si se debe conservar o no esa instantánea particular de perf.data.

Implica --timestamp-filename, --no-buildid y --no-buildid-cache. La razón de estos dos últimos es reducir la sobrecarga del cambio de archivo de datos. Aún puede activarlos con:

--switch-output --no-no-buildid  --no-no-buildid-cache

--switch-output-event

Eventos que provocarán el cambio del archivo perf.data, seleccionando automáticamente --switch-output=signal, los resultados son similares ya que internamente el hilo de banda lateral también enviará una SIGUSR2 al principal.

Utiliza la misma sintaxis que --event, simplemente no se registrará, sirviendo solo para cambiar el archivo perf.data tan pronto como el evento --switch-output sea procesado por un hilo de banda lateral separado.

Este hilo de banda lateral también se utiliza para otros propósitos, como procesar los registros PERF_RECORD_BPF_EVENT a medida que ocurren, solicitando al kernel información adicional de BPF, etc.

--switch-max-files=N

Al rotar perf.data con --switch-output, solo mantenga N archivos.

--dry-run

Analiza las opciones y sale. --dry-run se puede utilizar para detectar errores en las opciones de la línea de comandos.

perf record --dry-run -e puede actuar como un compilador de scripts BPF si llvm.dump-obj en config file is set to true.

--synth=TYPE

Recopila y sintetiza el tipo de eventos dado (separado por comas). Ten en cuenta que esta opción controla la síntesis del sistema de archivos /proc, que representa el estado de las tareas para los hilos preexistentes.

Los eventos del kernel (y algunos otros) se registran independientemente de la elección en esta opción. Por ejemplo, --synth=no tendría eventos MMAP para el kernel y los módulos.

Los tipos disponibles son:

•task - sintetiza eventos FORK y COMM para cada tarea
•mmap - sintetiza eventos MMAP para cada proceso (implica task)
•cgroup - sintetiza eventos CGROUP para cada cgroup
•all - sintetiza todos los eventos (por defecto)
•no - no sintetiza ninguno de los eventos anteriores.

--tail-synthesize

En lugar de recopilar eventos no de muestra (por ejemplo, fork, comm, mmap) al principio de la grabación, los recopila durante la finalización de un archivo de salida. Los eventos no de muestra recopilados reflejan el estado del sistema cuando finaliza la grabación.

--overwrite

Hace que todos los eventos utilicen un búfer de anillo sobrescribible. Un búfer de anillo sobrescribible funciona como un grabador de vuelo: cuando se llena, el kernel sobrescribirá los registros más antiguos, que así nunca llegarán al archivo perf.data.

Cuando se utilizan --overwrite y --switch-output, perf graba y descarta eventos hasta que recibe una señal, lo que significa que se detectó algo inusual que justifica la toma de una instantánea de los eventos más actuales, aquellos que caben en el búfer de anillo en ese momento.

El atributo overwrite también se puede establecer o cancelar para un evento utilizando términos de configuración. Por ejemplo: cycles/overwrite/ e instructions/no-overwrite/.

Implica --tail-synthesize.

--kcore

Crea una copia de /proc/kcore y la coloca en un directorio con el archivo de datos de perf.

--max-size=<tamaño>

Limita el tamaño máximo de los datos de muestra, se espera que <tamaño> sea un número con un carácter de unidad añadido - B/K/M/G

--num-thread-synthesize

El número de hilos a ejecutar al sintetizar eventos para procesos existentes. Por defecto, el número de hilos es 1.

--pfm-events eventos

Selecciona un evento PMU utilizando la sintaxis de libpfm4 (ver http://perfmon2.sf.net) incluyendo soporte para filtros de eventos. Por ejemplo --pfm-events inst_retired:any_p:u:c=1:i. Se pueden pasar varios eventos a la opción usando el separador de comas. Los eventos de hardware y los eventos genéricos de hardware no se pueden mezclar. Estos últimos deben usarse con la opción -e. La opción -e y esta se pueden mezclar. Los eventos se pueden agrupar usando la notación {}.

--control=fifo:ctl-fifo[,ack-fifo], --control=fd:ctl-fd[,ack-fd]

ctl-fifo / ack-fifo se abren y se utilizan como ctl-fd / ack-fd de la siguiente manera. Escucha en el descriptor ctl-fd comandos para controlar la medición.

Comandos disponibles:

•enable : habilita eventos
•disable : deshabilita eventos
•enable nombre : habilita el evento nombre
•disable nombre : deshabilita el evento nombre
•snapshot : instantánea de trazado de área AUX).
•stop : detiene la grabación de perf
•ping : ping
•'evlist [-v|-g|-F] : muestra todos los eventos 
-F  Muestra solo la frecuencia de muestra utilizada para cada evento.
-v  Muestra todos los campos.
-g  Muestra información del grupo de eventos.

Las mediciones se pueden iniciar con eventos deshabilitados usando la opción --delay=-1. Opcionalmente, envía la finalización del comando de control (ack\n) al descriptor ack-fd para sincronizar con el proceso de control. Ejemplo de script de shell bash para habilitar y deshabilitar eventos durante las mediciones:

#!/bin/bash
ctl_dir=/tmp/
ctl_fifo=${ctl_dir}perf_ctl.fifo
test -p ${ctl_fifo} && unlink ${ctl_fifo}
mkfifo ${ctl_fifo}
exec {ctl_fd}<>${ctl_fifo}
ctl_ack_fifo=${ctl_dir}perf_ctl_ack.fifo
test -p ${ctl_ack_fifo} && unlink ${ctl_ack_fifo}
mkfifo ${ctl_ack_fifo}
exec {ctl_fd_ack}<>${ctl_ack_fifo}
perf record -D -1 -e cpu-cycles -a               \
            --control fd:${ctl_fd},${ctl_fd_ack} \
            -- sleep 30 &
perf_pid=$!
sleep 5  && echo 'enable' >&${ctl_fd} && read -u ${ctl_fd_ack} e1 && echo "enabled(${e1})"
sleep 10 && echo 'disable' >&${ctl_fd} && read -u ${ctl_fd_ack} d1 && echo "disabled(${d1})"
exec {ctl_fd_ack}>&-
unlink ${ctl_ack_fifo}
exec {ctl_fd}>&-
unlink ${ctl_fifo}
wait -n ${perf_pid}
exit $?

--threads=<espec>

Escribe los datos de trazado recopilados en varios archivos de datos utilizando hilos paralelos. El valor de <espec> puede ser una lista de máscaras definidas por el usuario. Las máscaras separadas por dos puntos definen las CPU a monitorear por un hilo y la máscara de afinidad de ese hilo se separa por una barra inclinada: 
<máscara cpus 1>/<máscara afinidad 1>:<máscara cpus 2>/<máscara afinidad 2>:...

Las CPU o las máscaras de afinidad no deben superponerse con otras máscaras correspondientes. Se ignoran las CPU no válidas, pero no se permiten máscaras que contengan solo CPU no válidas.

Por ejemplo, una especificación de usuario como la siguiente:

0,2-4/2-4:1,5-7/5-7

especifica una disposición de hilos paralelos que consta de dos hilos, el primer hilo monitorea las CPU 0 y 2-4 con la máscara de afinidad 2-4, el segundo monitorea las CPU 1 y 5-7 con la máscara de afinidad 5-7.

El valor de <espec> también puede ser una cadena que significa una disposición predefinida de hilos paralelos:

•cpu - crea un nuevo hilo de transmisión de datos para cada cpu monitoreada
•core - crea un nuevo hilo para monitorear CPU agrupadas por un núcleo
•package - crea un nuevo hilo para monitorear CPU agrupadas por un paquete
•numa - crea un nuevo hilo para monitorear CPU agrupadas por un dominio NUMA

Las disposiciones predefinidas se pueden usar en sistemas con un gran número de CPU para evitar generar múltiples hilos de transmisión por cpu, pero aún así evitar eventos PERDIDOS en los archivos del directorio de datos. La opción especificada sin valor o con valor vacío, por defecto, utiliza la disposición de CPU. Las máscaras definidas o proporcionadas por el valor de la opción se filtran a través de la máscara proporcionada por la opción -C.

--debuginfod[=URLs]

Especifica la URL de debuginfod a utilizar al almacenar en caché los binarios de perf.data, sigue la misma sintaxis que la variable DEBUGINFOD_URLS, como:
http://192.168.122.174:8002 
Si no se especifican las URLs, se utiliza el valor de la variable
del entorno del sistema DEBUGINFOD_URLS.

--off-cpu

Habilita el perfilado off-cpu con BPF. El programa BPF recopilará información de programación de tareas con el rastreo de pila (del usuario) y los guardará como datos de muestra de un evento de software llamado "offcpu-time". El período de muestra tendrá el tiempo que la tarea durmió en nanosegundos. 
Ten en cuenta que BPF solo puede recopilar rastreos de pila utilizando el
puntero de marco ("fp"), por ahora. Por lo tanto, las aplicaciones compiladas
sin el puntero de marco pueden mostrar direcciones erróneas.
El perfilado off-cpu consta de dos tipos de muestras: muestras directas,
que comparten el mismo comportamiento que las muestras regulares, y muestras
acumuladas, almacenadas en el mapa de rastreo de pila BPF, presentadas
después de todas las muestras regulares.

--off-cpu-thresh

Una vez que el tiempo off-cpu de una tarea alcanza este umbral (en milisegundos), genera una muestra off-cpu directa. El valor por defecto es 500ms.

--setup-filter=<accion>

Prepara un filtro BPF para ser utilizado por usuarios regulares. La acción debe ser "pin" o "unpin". El filtro se puede usar después de que se haya fijado.

SOPORTE INTEL HÍBRIDO

Soporte para eventos híbridos de Intel dentro de las herramientas de perf.

Para algunas plataformas Intel, como AlderLake, que es una plataforma híbrida y consta de CPU de átomo y CPU de núcleo. Cada CPU tiene una lista de eventos dedicada. Parte de los eventos están disponibles en la CPU de núcleo, parte de los eventos están disponibles en la CPU de átomo e incluso parte de los eventos están disponibles en ambas.

El kernel exporta dos nuevos pmu de CPU a través de sysfs: /sys/bus/event_source/devices/cpu_core /sys/bus/event_source/devices/cpu_atom

Los archivos cpus se crean dentro de los directorios. Por ejemplo,

cat /sys/bus/event_source/devices/cpu_core/cpus 0-15

cat /sys/bus/event_source/devices/cpu_atom/cpus 16-23

Indica que las CPU 0-15 son CPU de núcleo y las CPU 16-23 son CPU de átomo.

Como antes, usa perf-list para listar el evento simbólico.

perf list

inst_retired.any [Contador Fijo: Cuenta el número de instrucciones retiradas. Unidad: cpu_atom] inst_retired.any [Número de instrucciones retiradas. Contador Fijo - evento arquitectónico. Unidad: cpu_core]

La indicación Unidad: xxx se añade a la descripción breve para indicar a qué pmu pertenece el evento. Se pueden soportar el mismo nombre de evento pero con diferente pmu.

Habilitar evento híbrido con un pmu específico

Para habilitar un evento solo de núcleo o solo de átomo, se soporta la siguiente sintaxis:

        cpu_core/<nombre del evento>/
o
        cpu_atom/<nombre del evento>/

Por ejemplo, contar el evento cycles en las CPU de núcleo.

perf stat -e cpu_core/cycles/

Crear dos eventos para un evento de hardware automáticamente

Al crear un evento y este está disponible tanto en átomo como en núcleo, se crean dos eventos automáticamente. Uno es para átomo, el otro es para núcleo. La mayoría de los eventos de hardware y eventos de caché están disponibles tanto en cpu_core como en cpu_atom.

Para los eventos de hardware, tienen configuraciones predefinidas (por ejemplo, 0 para cycles). Pero en la plataforma híbrida, el kernel necesita saber de dónde proviene el evento (del átomo o del núcleo). El tipo original de evento perf PERF_TYPE_HARDWARE no puede transportar información de pmu. Así que ahora este tipo se extiende para ser un tipo consciente de PMU. El ID del tipo PMU se almacena en attr.config[63:32].

NAME

perf-record, perf-stat, perf-top, perf-report - CPU performance analysis tool

SYNOPSIS

perf [options] record [record-options] [command]
perf [options] stat [stat-options] [command]
perf [options] top [top-options]
perf [options] report [report-options]

DESCRIPTION

This document describes the usage of the perf command and its various subcommands. perf is a powerful performance analysis tool that leverages the Linux kernel's performance counter subsystem (perf_events). It can be used to profile code, count events, and analyze performance bottlenecks.

The primary subcommands are:

  • record: Collect performance counter data.
  • stat: Collect and display performance counter statistics.
  • top: Display performance counter information in real-time, similar to top.
  • report: Display the data collected by perf record in a human-readable format.

This document focuses on the perf-record and perf-stat commands, particularly their support for Intel Hybrid architectures.

OPTIONS

The general options for perf are described in the perf(1) manual page. This section details options relevant to event selection and hybrid platform support.

INTEL HYBRID SUPPORT

Intel Hybrid architectures combine different types of CPU cores (e.g., Performance-cores and Efficient-cores) on the same chip. perf supports this by allowing PMUs (Performance Monitoring Units) to be specified when selecting events. The PMU type ID is retrieved from sysfs.

Example paths in sysfs:

  • /sys/bus/event_source/devices/cpu_atom/type
  • /sys/bus/event_source/devices/cpu_core/type

The layout of the attr.config field is extended to accommodate PMU type information.

For PERF_TYPE_HARDWARE events:

PERF_TYPE_HARDWARE: 0xEEEEEEEE000000AA
AA:
Hardware event ID
EEEEEEEE:
PMU type ID

For PERF_TYPE_HW_CACHE events:

PERF_TYPE_HW_CACHE: 0xEEEEEEEE00DDCCBB
BB:
Hardware cache ID
CC:
Hardware cache operation ID
DD:
Hardware cache operation result ID
EEEEEEEE:
PMU type ID

When enabling a hardware event without specifying the PMU, perf automatically creates events for the detected hybrid PMUs. For example, running perf stat -e cycles -a (system-wide) on a hybrid system will create two cycles events:

------------------------------------------------------------
perf_event_attr:
  size                             120
  config                           0x400000000
  sample_type                      IDENTIFIER
  read_format                      TOTAL_TIME_ENABLED|TOTAL_TIME_RUNNING
  disabled                         1
  inherit                          1
  exclude_guest                    1
------------------------------------------------------------

and

------------------------------------------------------------
perf_event_attr:
  size                             120
  config                           0x800000000
  sample_type                      IDENTIFIER
  read_format                      TOTAL_TIME_ENABLED|TOTAL_TIME_RUNNING
  disabled                         1
  inherit                          1
  exclude_guest                    1
------------------------------------------------------------

Here, type 0 is PERF_TYPE_HARDWARE. The upper bits of config indicate the PMU type: 0x4 for cpu_core PMU and 0x8 for cpu_atom PMU. The kernel creates cycles events for both core and atom PMUs, potentially on different CPU sets.

The output of perf stat will reflect these separate events:

Performance counter stats for 'system wide':
6,744,979      cpu_core/cycles/
1,965,552      cpu_atom/cycles/

The first line represents the cycles count from the core PMU, and the second from the atom PMU.

Thread mode example:

perf-stat reports scaled counts and percentages for hybrid events. The percentage indicates the event's running time relative to its enabled time.

Consider the command:

perf stat -e cycles -- taskset -c 16 ./triad_loop

If triad_loop runs on CPU 16 (an atom core), perf will generate two cycles events, one for each PMU type:

.ft C
perf_event_attr:
  size                             120
  config                           0x400000000
  sample_type                      IDENTIFIER
  read_format                      TOTAL_TIME_ENABLED|TOTAL_TIME_RUNNING
  disabled                         1
  inherit                          1
  enable_on_exec                   1
  exclude_guest                    1
.ft

and

.ft C
perf_event_attr:
  size                             120
  config                           0x800000000
  sample_type                      IDENTIFIER
  read_format                      TOTAL_TIME_ENABLED|TOTAL_TIME_RUNNING
  disabled                         1
  inherit                          1
  enable_on_exec                   1
  exclude_guest                    1
.ft

The output might look like this:

Performance counter stats for 'taskset -c 16 ./triad_loop':
233,066,666      cpu_core/cycles/                                              (0.43%)
604,097,080      cpu_atom/cycles/                                              (99.57%)

The percentages clearly show that the workload primarily utilizes the atom cores.

Default events:

perf-record: If no -e is specified on a hybrid platform, perf record creates default cycles events for both core and atom PMUs.

perf-stat: If no -e is specified on a hybrid platform, perf stat creates a default list of events that includes:

cpu_core/cycles/, cpu_atom/cycles/, cpu_core/instructions/, cpu_atom/instructions/, cpu_core/branches/, cpu_atom/branches/, cpu_core/branch-misses/, cpu_atom/branch-misses/

Explicit PMU selection:

You can explicitly specify events for a particular PMU:

  • perf stat -e cpu_core/cycles/
  • perf stat -e cpu_atom/cycles/
  • perf stat -e cpu_core/r1a/
  • perf stat -e cpu_atom/L1-icache-loads/
  • perf stat -e cpu_core/cycles/,cpu_atom/instructions/
  • perf stat -e {cpu_core/cycles/,cpu_core/instructions/}

Note that grouping events from different PMUs (e.g., {cpu_core/cycles/,cpu_atom/instructions/}) will result in a warning and disable grouping, as the PMUs do not match.
