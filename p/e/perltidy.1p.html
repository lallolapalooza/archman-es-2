NOMBRE

perltidy - un script de perl para indentar y reformatear

SINOPSIS

perltidy [ opciones ] archivo1 archivo2 archivo3 ...
        (la salida va a archivo1.tdy, archivo2.tdy, archivo3.tdy, ...)
perltidy [ opciones ] archivo1 -o archivo_salida
perltidy [ opciones ] archivo1 -st >archivo_salida
perltidy [ opciones ] <archivo_entrada >archivo_salida

DESCRIPCIÓN

Perltidy lee un script de perl y escribe un script indentado y reformatado. El proceso de formato implica convertir el script en una cadena de tokens, eliminando cualquier espacio en blanco no esencial y luego reescribiendo la cadena de tokens con espacios en blanco usando las reglas que se especifiquen o las predeterminadas. Esto ocurre en una serie de operaciones que se pueden controlar con los parámetros descritos en este documento.

Perltidy es un frontend de línea de comandos para el módulo Perl::Tidy. Para obtener documentación que describa cómo llamar al módulo Perl::Tidy desde otras aplicaciones, consulte la documentación separada para Perl::Tidy. Es el archivo Perl::Tidy.pod en la distribución fuente.

Muchos usuarios encontrarán suficiente información en "EJEMPLOS" para comenzar. Los nuevos usuarios pueden beneficiarse del breve tutorial que se encuentra en http://perltidy.sourceforge.net/tutorial.html

Una ayuda conveniente para definir sistemáticamente un conjunto de parámetros de estilo se puede encontrar en http://perltidy.sourceforge.net/stylekey.html

Perltidy puede producir salida en uno de dos modos, dependiendo de la existencia de un flag -html. Sin este flag, la salida se pasa a través de un formateador. El formato predeterminado intenta seguir las recomendaciones de perlstyle(1), pero puede ser controlado en detalle con numerosos parámetros de entrada, que se describen en "OPCIONES DE FORMATO". Son posibles muchas variaciones de estilo, pero vale la pena notar que el estilo predeterminado es particularmente conveniente para trabajar en fragmentos de código con un editor de líneas porque es fácil seleccionar una secuencia de líneas con contenedores balanceados, lo cual es necesario para formatear un fragmento de código con perltidy.

Cuando se da el flag -html, la salida se pasa a través de un formateador HTML que se describe en "OPCIONES HTML".

EJEMPLOS

Aquí hay algunos comandos de ejemplo de perltidy y sus significados:

  • Esto producirá un archivo somefile.pl.tdy que contiene el script reformatado usando las opciones predeterminadas, que se aproximan al estilo sugerido en perlstyle(1). El archivo fuente somefile.pl no se modifica. 
    perltidy somefile.pl
  • Ejecuta perltidy en todos los archivos .pl en el directorio actual con las opciones predeterminadas. La salida estará en archivos con una extensión .tdy añadida. Para cualquier archivo con un error, habrá un archivo con la extensión .ERR. 
    perltidy *.pl
  • Modifica file1.pl y file2.pl en el lugar, y haz una copia de seguridad de los originales en file1.pl.bak y file2.pl.bak. Si file1.pl.bak y/o file2.pl.bak ya existen, serán sobrescritos. 
    perltidy -b file1.pl file2.pl
  • Igual que el ejemplo anterior, excepto que los archivos de copia de seguridad file1.pl.bak y file2.pl.bak se eliminarán si no hay errores. 
    perltidy -b -bext='/' file1.pl file2.pl
  • Ejecuta perltidy en el archivo somefile.pl, con 4 columnas para cada nivel de indentación de continuación (-ci=4) en lugar de las 2 columnas predeterminadas, de modo que sea lo mismo que la indentación primaria predeterminada (-i=4). No habrá tabulaciones en el script reformatado, excepto las que ya existan en comentarios, documentos pod, comillas y here documents. La salida será somefile.pl.tdy. 
    perltidy -ci=4 somefile.pl
  • Igual que el ejemplo anterior, excepto que los espacios en blanco iniciales se convertirán a tabulaciones con un carácter de tabulación por cada 4 espacios, y por lo tanto una tabulación por cada nivel de indentación. 
    perltidy -ci=4 -et=4 somefile.pl
  • Ejecuta perltidy en el archivo somefile.pl con todas las predeterminadas excepto el uso de "else acurrucados" (-ce) y una longitud máxima de línea de 72 columnas (-l=72) en lugar de las 80 columnas predeterminadas. 
    perltidy -ce -l=72 somefile.pl
  • Volca una tabla de métricas separadas por comas para subrutinas de más de 10 líneas a blocks.csv y sale inmediatamente sin formatear: 
    perltidy -dbs -dbl=10 somefile.pl >blocks.csv
  • Volca una lista de nombres de variables léxicas no utilizadas y reutilizadas a vars.txt: 
    perltidy -duv somefile.pl >vars.txt
  • Esto producirá un archivo somefile.pl.html que contiene el script con marcado html. El archivo de salida contendrá una hoja de estilos incrustada en la sección "<HEAD"> que puede ser editada para cambiar la apariencia. 
    perltidy -html somefile.pl
  • Esto producirá un archivo somefile.pl.html que contiene el script con marcado html. Este archivo de salida contendrá un enlace a un archivo de hoja de estilos separado mystyle.css. Si el archivo mystyle.css no existe, se creará. Si existe, no será sobrescrito. 
    perltidy -html -css=mystyle.css somefile.pl
  • Escribe un fragmento html con solo la sección "<PRE"> a somefile.pl.html. Esto es útil cuando se formatean fragmentos de código para incluirlos en una página web más grande. No se escribirá ninguna hoja de estilos en este caso. 
    perltidy -html -pre somefile.pl
  • Escribe una hoja de estilos a mystyle.css y sale. 
    perltidy -html -ss >mystyle.css
  • Escribe html con un frame que contiene una tabla de contenidos y el código fuente. Los archivos de salida serán mymodule.pm.html (el frame), mymodule.pm.toc.html (la tabla de contenidos) y mymodule.pm.src.html (el código fuente). 
    perltidy -html -frm mymodule.pm

OPCIONES - VISIÓN GENERAL

Toda la línea de comandos se escanea en busca de opciones, y se procesan antes de procesar cualquier archivo. Como resultado, no importa si los flags están antes o después de los nombres de archivo. Sin embargo, el orden relativo de los parámetros es importante, y los parámetros posteriores anulan los valores de los parámetros anteriores.

Para la mayoría de los parámetros, hay un nombre largo y un nombre corto. Los nombres cortos son convenientes para la entrada del teclado, mientras que los nombres largos se autodescriben y, por lo tanto, son útiles en scripts. Se acostumbra a usar dos guiones iniciales para los nombres largos, pero se puede usar un solo guion para cualquier parámetro.

La mayoría de los parámetros que sirven como flags de encendido/apagado pueden ser negados con una "n" inicial (para el nombre corto) o una "no" o "no-" inicial (para el nombre largo). Por ejemplo, el flag para desindentar comillas largas es -olq o --outdent-long-quotes. El flag para omitir esto es -nolq o --nooutdent-long-quotes o --no-outdent-long-quotes.

Las opciones no se pueden agrupar. En otras palabras, las opciones -q y -g NO se pueden introducir como -qg.

Control de E/S

Los siguientes parámetros se refieren a los archivos que se leen y escriben.

-h, --help
Muestra un resumen del uso y sale.
-v, --version
Muestra el número de versión de perltidy y sale.
-o=nombre_archivo, --outfile=nombre_archivo
Nombre del archivo de salida (solo si se está procesando un único archivo de entrada). Si no se especifica ningún archivo de salida, y la salida no se redirige a la salida estándar (ver -st), la salida irá a nombre_archivo.tdy. [Nota: - no redirige a la salida estándar. Use -st en su lugar.]
-st, --standard-output
Perltidy debe ser capaz de operar en un número arbitrario de archivos en una sola ejecución, con cada salida dirigida a un archivo de salida diferente. Obviamente, esto entraría en conflicto con la salida al único dispositivo de salida estándar, por lo que se requiere un flag especial, -st, para solicitar la salida al dispositivo de salida estándar. Por ejemplo, 
perltidy somefile.pl -st >some

Este sitio no está asociado de ninguna forma con Arch Linux ni afiliado a este proyecto. El contenido es únicamente una traducción de las páginas del manual de Arch publicadas en man.archlinux.org.

file.new.pl

Esta opción solo puede usarse si hay un único archivo de entrada. El valor predeterminado es -nst o --nostandard-output.

-se, --standard-error-output
Si perltidy detecta un error al procesar el archivo somefile.pl, su comportamiento predeterminado es escribir mensajes de error en el archivo somefile.pl.ERR. Utilice -se para que todos los mensajes de error se envíen al flujo de salida de error estándar en su lugar. Esta directiva puede ser negada con -nse. Por lo tanto, puede colocar -se en un .perltidyrc y anularla cuando lo desee con -nse en la línea de comandos.
-oext=ext, --output-file-extension=ext
Cambie la extensión del archivo de salida a ext en lugar de la predeterminada tdy (o html en caso de que se utilice la opción --html). Véase "Especificación de extensiones de archivo".
-opath=path, --output-path=path
Cuando perltidy crea un nombre de archivo para un archivo de salida, por defecto simplemente agrega una extensión a la ruta y al nombre base del archivo de entrada. Este parámetro hace que la ruta se cambie a path en su lugar.

La ruta debe terminar en un carácter separador de ruta válido, pero perltidy intentará agregar uno si falta.

Por ejemplo

perltidy somefile.pl -opath=/tmp/

producirá /tmp/somefile.pl.tdy. De lo contrario, somefile.pl.tdy aparecerá en el directorio que contiene somefile.pl.

Si la ruta contiene espacios, debe colocarse entre comillas.

Este parámetro se ignorará si la salida se dirige a la salida estándar, o si se especifica explícitamente con el parámetro --outfile=s.

-b, --backup-and-modify-in-place
Modifique el archivo o archivos de entrada en el lugar y guarde el original con la extensión .bak. Cualquier archivo .bak existente se eliminará. Consulte el siguiente elemento para cambiar la extensión de copia de seguridad predeterminada y para eliminar el archivo de copia de seguridad por completo.

¡Tenga en cuenta!: Escribir de nuevo en el archivo de entrada aumenta el riesgo de pérdida o corrupción de datos en caso de un mal funcionamiento del software o hardware. Antes de utilizar el parámetro -b, asegúrese de tener copias de seguridad y verifique que funcione correctamente en su entorno y sistema operativo.

Se ignorará una bandera -b si la entrada proviene de la entrada estándar o va a la salida estándar, o si está configurada la bandera -html.

En particular, si desea utilizar tanto la bandera -b como la bandera --perl-best-practices (-pbp), deberá colocar una bandera --nostandard-output (-nst) después de la bandera -pbp porque contiene una bandera --standard-output como uno de sus componentes, lo que significa que la salida irá al flujo de salida estándar.

-bext=ext, --backup-file-extension=ext
Este parámetro tiene dos propósitos: (1) cambiar la extensión del archivo de copia de seguridad a algo que no sea la predeterminada .bak, y (2) indicar que no se guardará ningún archivo de copia de seguridad.

Para cambiar la extensión predeterminada a algo que no sea .bak, consulte "Especificación de extensiones de archivo".

Siempre se escribe una copia de seguridad de la fuente, pero puede solicitar que se elimine al final del procesamiento si no hubo errores. Esto es arriesgado a menos que el código fuente se mantenga con un sistema de control de código fuente.

Para indicar que la copia de seguridad debe eliminarse, incluya una barra diagonal, /, en la extensión. Si queda algún texto después de eliminar la barra, se utilizará para definir la extensión del archivo de copia de seguridad (que siempre se crea y solo se elimina si no hubo errores).

Aquí hay algunos ejemplos:

Parámetro          Extensión      Tratamiento del archivo de copia de seguridad
-bext=bak         .bak            Mantener (igual que el comportamiento predeterminado)
-bext='/'         .bak            Eliminar si no hay errores
-bext='/backup'   .backup         Eliminar si no hay errores
-bext='original/' .original       Eliminar si no hay errores
-bm=s, --backup-method=s
Este parámetro no debe usarse normalmente, pero está disponible en caso de que surjan problemas durante la transición de una implementación anterior de la lógica de copia de seguridad a una implementación más nueva. La implementación más nueva es la predeterminada y se especifica con -bm='copy'. La implementación anterior se especifica con -bm='move'. La diferencia es que la implementación anterior realizaba la copia de seguridad moviendo el archivo de entrada al archivo de copia de seguridad, y la implementación más nueva realiza la copia de seguridad copiando el archivo de entrada. La implementación más nueva conserva el valor inode del sistema de archivos. Esto puede evitar problemas con otro software que se ejecuta simultáneamente. Este cambio se realizó como parte del problema git #103 en github.
-w, --warning-output
Configurar -w hace que los mensajes de advertencia no críticos se informen como errores. Estos incluyen mensajes sobre posibles problemas de pod, un nivel de indentación inicial posiblemente incorrecto y advertencias sobre el uso de objetos indirectos. El valor predeterminado, -nw o --nowarning-output, es no incluir estas advertencias.
-q, --quiet
Desactivar mensajes de error (para ejecutar dentro de un editor).

Por ejemplo, si utiliza un editor de estilo vi, como vim, puede ejecutar perltidy como un filtro dentro del editor usando algo como

:n1,n2!perltidy -q

donde "n1,n2" representa el texto seleccionado. Sin la bandera -q, cualquier mensaje de error puede desordenar su pantalla, así que prepárese para usar su tecla de "deshacer".

-log, --logfile
Guardar el archivo .LOG, que contiene muchos diagnósticos útiles. Perltidy siempre crea un archivo .LOG, pero por defecto se elimina a menos que se sospeche un error del programa. Establecer la bandera -log fuerza a que se guarde el archivo de registro.
-g=n, --logfile-gap=n
Establece el intervalo máximo entre líneas de código de entrada en el archivo de registro. El propósito de esta bandera es ayudar a depurar errores de anidamiento. El valor de "n" es opcional. Si establece la bandera -g sin el valor de "n", se tomará como 1, lo que significa que cada línea se escribirá en el archivo de registro. Esto puede ser útil si está buscando un error de anidamiento de llaves, paréntesis o corchetes.

Establecer -g también hace que se guarde el archivo de registro, por lo que no es necesario incluir también -log.

Si no se proporciona ninguna bandera -g, se usará un valor de 50, lo que significa que al menos cada 50ª línea se registrará en el archivo de registro. Esto ayuda a evitar archivos de registro excesivamente largos.

Establecer un valor negativo de "n" es lo mismo que no establecer -g en absoluto.

-npro --noprofile
Ignorar cualquier archivo de comandos .perltidyrc. Normalmente, perltidy busca primero en su directorio actual un archivo .perltidyrc de parámetros. (El formato se describe a continuación). Si encuentra uno, aplica esas opciones a los valores predeterminados iniciales y luego aplica los que se hayan definido en la línea de comandos. Si no se encuentra ningún archivo .perltidyrc, busca uno en su directorio de inicio.

Si establece la bandera -npro, perltidy no buscará este archivo.

-pro=filename o --profile=filename
Para simplificar las pruebas y el cambio de archivos .perltidyrc, este comando se puede utilizar para especificar un archivo de configuración que anulará el nombre predeterminado de .perltidyrc. No debe haber ningún espacio a ambos lados del signo =. Por ejemplo, la línea 
perltidy -pro=testcfg

utilizaría el archivo testcfg en lugar del valor predeterminado .perltidyrc.

Una ruta que comienza con tres puntos, por ejemplo, ".../.perltidyrc", indica que el archivo debe buscarse comenzando en el directorio actual y subiendo. Esto facilita tener múltiples proyectos, cada uno con su propio .perltidyrc en sus directorios raíz.

-opt, --show-options
Escribir una lista de todas las opciones utilizadas en el archivo .LOG. Consulte --dump-options para una forma más sencilla de hacerlo.
-f, --force-read-binary
Forzar a perltidy a procesar archivos binarios. Para evitar producir mensajes de error excesivos, perltidy omite los archivos identificados por el sistema como no textuales. Sin embargo, los scripts de Perl válidos que contienen datos binarios a veces pueden ser identificados como no textuales, y esta bandera fuerza a perltidy a procesarlos.
-ast, --assert-tidy
Esta bandera afirma que las corrientes de código de entrada y salida son idénticas, o en otras palabras, que el código de entrada ya está 'ordenado' según los parámetros de formato. Si no es así, se produce un mensaje de error que lo indica. Este mensaje de error hará que el proceso devuelva un código de salida distinto de cero. La prueba para esto se realiza comparando un valor hash MD5 para las corrientes de código de entrada y salida. Esta bandera no tiene ningún otro efecto en el funcionamiento de perltidy. Esto podría ser útil para ciertas operaciones de mantenimiento de código. Nota: no verá este mensaje si tiene los mensajes de error desactivados con la bandera -quiet.
-asu, --assert-untidy
Esta bandera afirma que las corrientes de código de entrada y salida son diferentes, o en otras palabras, que el código de entrada está 'desordenado' según los parámetros de formato. Si no es así, se produce un mensaje de error que lo indica. Esta bandera no tiene ningún otro efecto en el funcionamiento de perltidy.
-tos=n, --timeout-in-seconds=n
Cuando la entrada estándar suministra la corriente de entrada, y la entrada no ha sido recibida dentro de los n segundos, perltidy finalizará con un mensaje de tiempo de espera. La intención es detectar una situación en la que perltidy se invoca accidentalmente sin un archivo que procesar y, por lo tanto, espera la entrada de la entrada estándar del sistema (stdin), que nunca llega.
. El valor predeterminado es **n=10** segundos. Esta verificación se puede desactivar con **n=0**.

OPCIONES DE FORMATO

Opciones básicas

-fmt=s, --format=s
Si **--format=tidy** (el valor predeterminado), perltidy reformateará el archivo de entrada y, si **--format=html**, perltidy generará salida html.

Para mayor comodidad, la abreviatura **--tidy** es equivalente a **--format=tidy**, y **-html** es equivalente a **--format=html**.

--notidy
Este indicador deshabilita todo el formateo y hace que la entrada se copie sin cambios a la salida, excepto por posibles cambios en los caracteres de fin de línea y cualquier filtro previo y posterior. Esto puede ser útil en conjunción con un conjunto jerárquico de archivos .perltidyrc para evitar el formateo no deseado del código. Consulte también "Omitir secciones de código seleccionadas" para saber cómo evitar formatear secciones específicas de código.
-i=n, --indent-columns=n
Utilice n columnas por nivel de sangría (el valor predeterminado es n=4).
-l=n, --maximum-line-length=n
La longitud máxima de línea predeterminada es **n=80** caracteres. Perltidy intentará encontrar puntos de salto de línea para mantener las líneas por debajo de esta longitud. Sin embargo, las comillas largas y los comentarios laterales pueden hacer que las líneas excedan esta longitud. Y las líneas largas a veces se pueden dividir con una longitud inferior a **n** caracteres porque algunas de las decisiones de salto de línea emplean pequeñas tolerancias para evitar inestabilidades en el formato.

La longitud predeterminada de 80 proviene del pasado, cuando este era el ancho de pantalla CRT estándar. Muchos programadores prefieren aumentar esto a algo como 120.

Establecer **-l=0** es equivalente a establecer **-l=(un número muy grande)**. Pero esto no se recomienda porque, por ejemplo, una lista muy larga se formateará en una sola línea larga.

-vmll, --variable-maximum-line-length
Surge un problema al usar una longitud máxima de línea fija con estructuras de código y datos muy anidadas, ya que eventualmente la cantidad de espacio en blanco inicial utilizada para indicar la sangría ocupa la mayor parte o todo el ancho de línea disponible, dejando poco o ningún espacio para el código o los datos reales. Una solución es usar una longitud de línea muy larga. Otra solución es usar el indicador **-vmll**, que básicamente le dice a perltidy que ignore el espacio en blanco inicial al medir la longitud de la línea.

Para ser precisos, cuando se establece el parámetro **-vmll**, la longitud máxima de línea de una línea de código será M+L*I, donde

M es el valor de --maximum-line-length=M (-l=M), predeterminado 80,
I es el valor de --indent-columns=I (-i=I), predeterminado 4,
L es el nivel de sangría de la línea de código

Cuando se establece este indicador, la elección de los puntos de ruptura para un bloque de código debería ser esencialmente independiente de su profundidad de anidamiento. Sin embargo, las longitudes absolutas de línea, incluido el espacio en blanco inicial, aún pueden ser arbitrariamente grandes. Este problema se puede evitar incluyendo el siguiente parámetro.

El valor predeterminado es no hacer esto (**-nvmll**).

-wc=n, --whitespace-cycle=n
Este indicador también aborda problemas con estructuras de código y datos muy anidadas. Cuando la profundidad de anidamiento excede el valor **n**, el espacio en blanco inicial se reducirá y comenzará de nuevo desde una profundidad de 1. El resultado es que los bloques de código se desplazarán hacia la izquierda en lugar de hacia la derecha arbitrariamente. Esto ocurre cíclicamente a cualquier profundidad.

Por ejemplo, si un nivel de sangría equivale a 4 espacios (**-i=4**, el valor predeterminado) y se utiliza **-wc=15**, entonces si el espacio en blanco inicial en una línea supera aproximadamente 4*15=60 espacios, se reducirá a 4*1=4 espacios y continuará aumentando a partir de ahí. Si el espacio en blanco nunca supera este límite, el formato permanece sin cambios.

La combinación de **--variable-maximum-line-length** y **--whitespace-cycle=n** proporciona una solución al problema de mostrar estructuras de datos y código arbitrariamente profundas en una ventana finita, aunque **--whitespace-cycle=n** puede usarse sin **--variable-maximum-line-length**.

El valor predeterminado es no usar esto, lo que también se puede indicar usando **-wc=0**.

Pestañas
El uso de caracteres de tabulación casi seguramente conducirá a futuros problemas de portabilidad y mantenimiento, por lo que el valor predeterminado y la recomendación es no usarlos. Sin embargo, para aquellos que prefieren las tabulaciones, hay dos opciones diferentes.

Excepto por la posible introducción de caracteres de tabulación para sangría, como se describe a continuación, perltidy no introduce ningún carácter de tabulación en su archivo y elimina cualquier tabulación del código (a menos que se solicite lo contrario con **--freeze-whitespace**). Si tiene alguna tabulación en sus comentarios, citas o here-documents, estas permanecerán.

-et=n, --entab-leading-whitespace
Este indicador hace que cada **n** caracteres de espacio en blanco inicial producidos por el proceso de formato se reemplacen por un carácter de tabulación. El proceso de formato en sí mismo funciona con caracteres de espacio. El parámetro **-et=n** se aplica como un último paso, después de que el formato se completa, para convertir los espacios iniciales en tabulaciones. Antes de comenzar a usar tabulaciones, es esencial primero configurar los controles de sangría según lo deseado sin tabulaciones, particularmente los dos parámetros **--indent-columns=n** (o **-i=n**) y **--continuation-indentation=n** (o **-ci=n**).

El valor del entero **n** puede ser cualquier valor pero puede coordinarse con el número de espacios utilizados para la sangría. Por ejemplo, **-et=4 -ci=4 -i=4** producirá una tabulación por cada nivel de sangría y una por cada nivel de sangría de continuación. Es posible que desee coordinar el valor de **n** con lo que su software de visualización asume para el espaciado de una tabulación.

El valor predeterminado es no usar esto, lo que también se puede indicar usando **-et=0**.

-t, --tabs
Este indicador hace que se inserte un carácter de tabulación inicial por cada nivel de sangría. Ciertas otras características son incompatibles con esta opción, y si estas opciones también se proporcionan, se emitirá un mensaje de advertencia y este indicador se desactivará. Un ejemplo es la opción **--line-up-parentheses**. Este indicador se mantiene por compatibilidad con versiones anteriores, pero si usa tabulaciones, se recomienda el indicador **--entab-leading-whitespace=n**. Si tanto **--tabs** como **--entab-leading-whitespace=n** están configurados, se utiliza **--entab-leading-whitespace=n**.
-dt=n, --default-tabsize=n
Si la primera línea de código pasada a perltidy contiene tabulaciones iniciales pero no se especifica ningún esquema de tabulación para el flujo de salida, perltidy debe adivinar cuántos espacios corresponden a cada tabulación inicial. Este número de espacios **n** que corresponden a cada tabulación inicial del flujo de entrada se puede especificar con **-dt=n**. El valor predeterminado es **n=8**.

Este indicador no tiene ningún efecto si se especifica un esquema de tabulación para el flujo de salida, ya que se asume que el flujo de entrada utiliza el mismo esquema de tabulación y espacios de sangría que para el flujo de salida (cualquier otra suposición conduciría a una edición inestable).

-io, --indent-only
Este indicador se utiliza para desactivar todos los cambios de espacio en blanco y salto de línea dentro de las líneas de código no en blanco. Cuando está en efecto, el único cambio en el script será la sangría y el número de líneas en blanco. Y se ignorarán todos los indicadores que controlan el espacio en blanco y los saltos de línea. Es posible que desee utilizar esto si está perfectamente satisfecho con su espacio en blanco y saltos de línea, y simplemente desea que perltidy se encargue de la sangría. (Esto también acelera perltidy en más del doble, por lo que podría ser útil cuando perltidy se utiliza simplemente para ayudar a encontrar un error de llave en un script grande).

Establecer este indicador es equivalente a establecer **--freeze-newlines** y **--freeze-whitespace**.

Si también desea mantener sus líneas en blanco existentes exactamente como están, puede agregar **--freeze-blank-lines**.

Con esta opción, perltidy todavía puede modificar la sangría (y desangría) del código y los comentarios como lo haría normalmente. Si también desea evitar que las líneas de comentarios largas se desangren, puede agregar **--nooutdent-long-lines** (**-noll**) o **--maximum-line-length=0** (**l=0**).

Establecer este indicador evitará que perltidy realice operaciones especiales en los comentarios laterales de cierre. Aún puede eliminar todos los comentarios laterales cuando este indicador está en efecto.

-enc=s, --character-encoding=s
Este indicador indica si el flujo de datos de entrada utiliza una codificación de caracteres. Perltidy no busca las directivas de codificación en el flujo fuente, como **use utf8**, y en su lugar se basa en este indicador para determinar la codificación. (Esto se debe a que perltidy a menudo trabaja con fragmentos de código en lugar de archivos completos, por lo que no puede confiar en las directivas **use utf8**). En consecuencia, es probable que perltidy encuentre problemas al formatear un archivo que solo está parcialmente codificado.

Los valores posibles para **s** son:

-enc=none si no se utiliza ninguna codificación, o
-enc=utf8 para codificación en utf8
-enc=guess si perltidy debe adivinar entre estas dos posibilidades.

El valor **none** hace que el flujo se procese sin suposiciones especiales de codificación. Esto es apropiado para archivos que están escritos en codificaciones de caracteres de un solo byte, como latin-1.

El valor **utf8** hace que el flujo se lea y escriba como UTF-8. Si el flujo de entrada no se puede decodificar con esta codificación, no se realiza ningún procesamiento.

El valor **guess** le dice a perltidy que adivine entre la codificación utf8 o ninguna codificación (lo que significa un carácter por byte). La opción **guess** utiliza el módulo Encode::Guess, que ha demostrado ser confiable para detectar si un archivo está codificado en utf8 o no.

El valor predeterminado actual es **guess**.

Las abreviaturas **-utf8** o **-UTF8** son equivalen

t a -enc=utf8, y el abreviado -guess es equivalente a -enc=guess. Así que para procesar un archivo llamado file.pl codificado en UTF-8 puedes usar:

perltidy -utf8 file.pl

o

perltidy -guess file.pl

o simplemente

perltidy file.pl

ya que -guess es el predeterminado.

Para procesar archivos con una codificación diferente a UTF-8, sería necesario escribir un programa corto que llame al módulo Perl::Tidy con algún pre- y post-procesamiento para manejar la decodificación y codificación.

-eos=s, --encode-output-strings=s
Esta bandera se añadió para resolver un problema con la interfaz entre Perl::Tidy y los programas que lo llaman, y en particular con Code::TidyAll (tidyall).

Si solo ejecutas el binario perltidy esta bandera no tiene efecto. Si ejecutas un programa que llama al módulo Perl::Tidy y recibe una cadena de retorno, entonces el significado de la bandera es el siguiente:

  • La configuración -eos significa que Perl::Tidy debe codificar cualquier cadena que decodifique. Este es el valor predeterminado porque hace que perltidy funcione bien como un filtro y es la configuración correcta para la mayoría de los programas.
  • La configuración -neos significa que una cadena debe permanecer decodificada si fue decodificada por Perl::Tidy. Esto solo es apropiado si el programa que llama manejará cualquier codificación necesaria antes de mostrar la cadena.

El valor predeterminado se cambió de -neos a -eos en versiones posteriores a 20220217. Si este cambio hace que un programa comience a ejecutarse incorrectamente en archivos codificados, una solución de emergencia podría ser configurar -neos. Se puede encontrar información adicional en las páginas man del módulo Perl::Tidy y también en https://github.com/perltidy/perltidy/blob/master/docs/eos_flag.md

-gcs, --use-unicode-gcstring
Esta bandera controla si perltidy puede usar el módulo Unicode::GCString para obtener anchos de visualización precisos de caracteres anchos. El valor predeterminado es --nouse-unicode-gcstring.

Si se activa esta bandera y el texto está codificado, perltidy buscará el módulo Unicode::GCString y, si lo encuentra, lo usará para obtener los anchos de visualización de los caracteres. Esto puede mejorar la alineación vertical de la visualización para archivos con caracteres anchos. Es una buena característica, pero está desactivada por predeterminado para evitar conflictos de formato cuando hay varios desarrolladores. La instalación de Perltidy no requiere Unicode::GCString, por lo que los usuarios que deseen utilizar esta característica deben activar esta bandera e instalar Unicode::GCString por separado.

Si se activa esta bandera y perltidy no encuentra el módulo Unicode::GCString, se mostrará un mensaje de advertencia y el procesamiento continuará, pero sin el beneficio potencial que proporciona el módulo.

También ten en cuenta que la alineación vertical real depende de las fuentes utilizadas por el software de visualización de texto, por lo que la alineación vertical puede no ser óptima incluso cuando se utiliza Unicode::GCString.

-ole=s, --output-line-ending=s
donde s="win", "dos", "unix", o "mac". Esta bandera le dice a perltidy que genere finales de línea para un sistema específico. Normalmente, perltidy escribe archivos con el carácter separador de línea del sistema anfitrión. Las banderas "win" y "dos" tienen el mismo resultado.
-ple, --preserve-line-endings
Esta bandera le dice a perltidy que escriba sus archivos de salida con los mismos finales de línea que el archivo de entrada, si es posible. Debería funcionar para finales de línea dos, unix y mac. Solo funcionará si la entrada de perltidy proviene de un nombre de archivo (en lugar de stdin, por ejemplo). Si perltidy tiene problemas para determinar el final de línea del archivo de entrada, volverá al comportamiento predeterminado de usar el final de línea del sistema anfitrión.
-atnl, --add-terminal-newline
Esta bandera, que está activada por defecto, permite a perltidy terminar la última línea del flujo de salida con un carácter de nueva línea, independientemente de si el flujo de entrada estaba terminado con un carácter de nueva línea o no. Si se niega esta bandera, con -natnl, entonces perltidy añadirá una nueva línea terminal al flujo de salida solo si el flujo de entrada está terminado con una nueva línea.

Negar esta bandera puede ser útil para manipular scripts de una sola línea destinados a usarse en la línea de comandos.

-it=n, --iterations=n
Esta bandera hace que perltidy realice n iteraciones completas. La razón de esta bandera es que el formato del código es un proceso iterativo y en algunos casos la salida de perltidy puede ser diferente si se aplica una segunda vez. Para la mayoría de los propósitos, el valor predeterminado de n=1 debería ser satisfactorio. Sin embargo, n=2 puede ser útil cuando se realiza un cambio de estilo importante, o cuando el código se está embelleciendo al enviarlo a un sistema de control de código fuente. Se ha descubierto que es extremadamente raro que la salida cambie después de 2 iteraciones. Si se introduce un valor n mayor que 2, se utilizará una prueba de convergencia para detener las iteraciones tan pronto como sea posible, casi siempre después de 2 iteraciones. Consulte el siguiente elemento para obtener un control de iteración simplificado.

Esta bandera no tiene efecto cuando se utiliza perltidy para generar html.

-conv, --converge
Esta bandera es equivalente a -it=4 y se incluye para simplificar el control de iteraciones. Perltidy comprobará la convergencia y dejará de iterar tan pronto como sea posible. El valor predeterminado es -nconv (sin comprobación de convergencia). El uso de -conv aproximadamente duplicará el tiempo de ejecución, ya que normalmente se requiere una iteración adicional para verificar la convergencia. No se requieren iteraciones adicionales si no se realizan nuevas rupturas de línea, y ocasionalmente se necesitan dos iteraciones adicionales al reformatear estructuras de código complejas, como sentencias ternarias profundamente anidadas.

Control de la Indentación del Código

El modelo de indentación básico utilizado por perltidy establece la indentación de una línea igual a la suma de cualquier número de niveles de indentación primarios, cada uno de los cuales corresponde a la entrada en un nuevo contenedor, más un nivel de continuación, que surge cuando una sentencia se rompe en varias líneas. Este no es el modelo más general posible, pero ha funcionado bien con la mayoría del código perl y al mismo tiempo permite una codificación robusta que evita inestabilidades.

El número de espacios correspondientes a estos niveles primarios y secundarios (de continuación) se puede controlar de forma independiente. El número de espacios para la indentación primaria es --indent-columns=n, o -i=n, como se describe anteriormente. El número de espacios para la indentación secundaria se describe en la siguiente sección.

-ci=n, --continuation-indentation=n
La indentación de continuación son espacios de indentación adicionales que se aplican cuando se rompe una línea larga. El valor predeterminado es n=2, ilustrado aquí: 
my $level =   # -ci=2
  ( $max_index_to_go >= 0 ) ? $levels_to_go[0] : $last_output_level;

El mismo ejemplo, con n=0, es un poco más difícil de leer:

my $level =   # -ci=0
( $max_index_to_go >= 0 ) ? $levels_to_go[0] : $last_output_level;

El valor dado a -ci también es utilizado por algunos comandos cuando se requiere un espacio pequeño. Ejemplos son los comandos para desindentar etiquetas, --outdent-labels (-ola), y palabras clave de control, --outdent-keywords (-okw).

Cuando no se usan los valores predeterminados, se recomienda que ya sea

(1) el valor n dado con -ci=n no sea más de aproximadamente la mitad del número de espacios asignados a un nivel de indentación completo en el comando -i=n, o

(2) se utilice la bandera --extended-continuation-indentation (ver sección siguiente).

-xci, --extended-continuation-indentation
Esta bandera permite a perltidy utilizar algunas mejoras que se han hecho en su modelo de indentación. Una de las cosas que hace es "extender" la indentación de continuación más profundamente en las estructuras, de ahí el nombre. La indentación mejorada es particularmente notable cuando las banderas -ci=n y -i=n utilizan el mismo valor de n. No hay desventajas significativas en el uso de esta bandera, pero para evitar alterar el formato existente, el valor predeterminado es no usarla, -nxci.

Por favor, consulte la sección "-pbp, --perl-best-practices" para un ejemplo de cómo esta bandera puede mejorar el formato de las sentencias ternarias. También puede mejorar la indentación de algunas listas qw multilínea como se muestra a continuación.

# perltidy
foreach $color (
    qw(
    AntiqueWhite3 Bisque1 Bisque2 Bisque3 Bisque4
    SlateBlue3 RoyalBlue1 SteelBlue2 DeepSkyBlue3
    ),
    qw(
    LightBlue1 DarkSlateGray1 Aquamarine2 DarkSeaGreen2
    SeaGreen1 Yellow1 IndianRed1 IndianRed2 Tan1 Tan4
    )
  )
# perltidy -xci
foreach $color (
    qw(
        AntiqueWhite3 Bisque1 Bisque2 Bisque3 Bisque4
        SlateBlue3 RoyalBlue1 SteelBlue2 DeepSkyBlue3
    ),
    qw(
        LightBlue1 DarkSlateGray1 Aquamarine2 DarkSeaGreen2
        SeaGreen1 Yellow1 IndianRed1 IndianRed2 Tan1 Tan4
    )
  )
-mci, --minimize-continuation-indentation
Esta bandera permite a perltidy eliminar la indentación de continuación en algunos casos especiales donde no es realmente innecesaria. Para un ejemplo simple, el formato predeterminado para el siguiente fragmento es: 
# perltidy -nmci
$self->blurt( "Error: No INPUT for type '$type', typekind '"
      . $type->xstype
      . "' found" );

Las segunda y tercera líneas están un nivel de profundidad en un contenedor y también son continuaciones de sentencia, por lo que se indentan por la suma del valor de indentación completa -i y el valor de indentación de continuación -ci. Si se activa esta bandera, la indentación se reduce en -ci espacios, dando:

# perltidy -mci
$self->blurt( "Error: No INPUT for type '$type', typekind '"
    . $type->xstype
    . "' found" );

Esta bandera i

s desactivado por defecto.

-sil=n --starting-indentation-level=n
Por defecto, perltidy examina el archivo de entrada y trata de determinar el nivel de indentación de inicio. Aunque a menudo es cero, puede no serlo para un fragmento de código que se envía desde una sesión de edición.

Para adivinar el nivel de indentación de inicio, perltidy simplemente asume que el esquema de indentación utilizado para crear el fragmento de código es el mismo que se está utilizando para el proceso actual de perltidy. Esta es la única suposición sensata que se puede hacer. Debería ser correcto si esto es cierto, pero de lo contrario probablemente no lo será. Por ejemplo, si el script de entrada se escribió con -i=2 y las banderas actuales de perltidy tienen -i=4, se adivinará una indentación inicial incorrecta para un fragmento de código que tenga una indentación inicial distinta de cero. Del mismo modo, si se utiliza un esquema de tabulación en el script de entrada y no en el proceso actual, la indentación adivinada será incorrecta.

Si el método por defecto no funciona correctamente, o si desea cambiar el nivel de inicio, utilice -sil=n para forzar que el nivel de inicio sea n.

Indentación de listas usando --line-up-parentheses, -lp o --extended--line-up-parentheses, -xlp
Estas banderas proporcionan un método de indentación alternativo para los datos de lista. La bandera original para esto es -lp, pero tiene algunas limitaciones (explicadas a continuación) que se evitan con la nueva bandera -xlp. Por lo tanto, -xlp es probablemente la mejor opción para trabajos nuevos, pero la bandera -lp se conserva para minimizar los cambios en el formato existente. Si introduce tanto -lp como -xlp, se utilizará -xlp.

En el método de indentación por defecto, perltidy indenta las listas con 4 espacios, o cualquier valor especificado con -i=n. Aquí hay una pequeña lista formateada de esta manera:

# perltidy (por defecto)
@month_of_year = (
    'Jan', 'Feb', 'Mar', 'Apr', 'May', 'Jun',
    'Jul', 'Aug', 'Sep', 'Oct', 'Nov', 'Dec'
);

Las banderas -lp o -xlp añaden indentación adicional para hacer que los datos comiencen más allá de los paréntesis de apertura de una llamada a subrutina o lista, o el corchete de apertura de un array anónimo, o la llave de apertura de un hash anónimo. Con esta opción, la lista anterior se convertiría en:

# perltidy -lp o -xlp
@month_of_year = (
                   'Jan', 'Feb', 'Mar', 'Apr', 'May', 'Jun',
                   'Jul', 'Aug', 'Sep', 'Oct', 'Nov', 'Dec'
);

Si la longitud de línea disponible (ver -l=n) no permite tanto espacio, perltidy utilizará menos. Para la colocación alternativa del paréntesis de cierre, ver la siguiente sección.

Estas banderas no tienen ningún efecto en los BLOQUES de código, como los bloques if/then/else, que siempre utilizan lo que se especifica con -i=n.

Algunas limitaciones de estas banderas son:

  • Una limitación en -lp, pero no en -xlp, ocurre en situaciones donde perltidy no tiene libertad total para elegir saltos de línea. Entonces puede revertir temporalmente a su método de indentación por defecto. Esto puede ocurrir, por ejemplo, si hay líneas en blanco, comentarios de bloque, comillas multilínea o comentarios laterales entre los paréntesis, llaves o corchetes de apertura y cierre. También ocurrirá si una subrutina anónima multilínea ocurre dentro de un contenedor, ya que esto impondrá saltos de línea específicos (como saltos de línea después de las sentencias).
  • Tanto para las banderas -lp como -xlp, cualquier parámetro que restrinja significativamente la capacidad de perltidy para elegir saltos de línea entrará en conflicto con estas banderas y provocará su desactivación. Estos incluyen --indent-only, --freeze-newlines, --noadd-newlines y --nodelete-old-newlines.
  • Las opciones -lp y -xlp no se pueden usar junto con la opción de tabulaciones -t. Sin embargo, se pueden usar con el método de tabulación -et=n

Hay algunas desventajas potenciales de este método de indentación en comparación con el método por defecto que deben tenerse en cuenta:

  • La longitud de línea disponible se puede agotar rápidamente si los nombres de las variables son largos. Esto puede hacer que el código profundamente anidado alcance rápidamente el límite de longitud de línea y tenga un formato deficiente, mucho antes de lo que ocurriría con el método de indentación por defecto.
  • Dado que la indentación depende de la longitud de los nombres de las variables, pequeños cambios en los nombres de las variables pueden causar cambios en la indentación a lo largo de muchas líneas en un archivo. Esto significa que cambios menores en los nombres pueden producir diferencias significativas en el archivo. Esto puede ser molesto y no ocurre con el método de indentación por defecto.

Algunas cosas que se pueden hacer para minimizar estos problemas son:

  • Aumente --maximum-line-length=n por encima del valor por defecto n=80 caracteres si es necesario.
  • Si utiliza -xlp, los comentarios laterales largos pueden limitar la indentación en varias líneas. Considere añadir la bandera --ignore-side-comment-lengths para evitar esto, o minimizar el uso de comentarios laterales.
  • Aplique este estilo de forma limitada. Por defecto, se aplica a todos los contenedores de listas (no solo a las listas entre paréntesis). La siguiente sección describe cómo limitar este estilo, por ejemplo, solo a las llamadas a funciones. El método de indentación por defecto se aplicará en otros lugares.
-lpil=s, --line-up-parentheses-inclusion-list y -lpxl=s, --line-up-parentheses-exclusion-list
La siguiente discusión está escrita para -lp pero se aplica igualmente a la versión más nueva -xlp. Por defecto, la bandera -lp se aplica a tantos contenedores como sea posible. El conjunto de contenedores a los que se aplica el estilo -lp puede reducirse mediante cualquiera de estas dos banderas:

Utilice --line-up-parentheses-inclusion-list=s (-lpil=s) para especificar los contenedores a los que se aplica -lp, o

utilice --line-up-parentheses-exclusion-list=s (-lpxl=s) para especificar los contenedores a los que NO se aplica -lp.

Solo se puede utilizar una de estas dos banderas. Ambas banderas pueden lograr el mismo resultado, pero la bandera -lpil=s es mucho más fácil de describir y usar, y se recomienda. La bandera -lpxl=s fue la implementación original y solo se conserva por compatibilidad retroactiva.

Esta lista s para estos parámetros es una cadena con elementos separados por espacios. Cada elemento consta de hasta tres piezas de información en este orden: (1) un código de letra opcional (2) un tipo de contenedor requerido y (3) un código numérico opcional.

La única pieza de información requerida es un tipo de contenedor, que es uno de '(', '[', o '{'. Por ejemplo, la cadena

-lpil='('

significa usar el formato -lp solo en listas dentro de paréntesis, no en listas entre corchetes o llaves. Lo mismo podría haberse especificado alternativamente con

-lpxl = '[ {'

que dice excluir listas dentro de corchetes y llaves. Así que lo que queda son listas dentro de paréntesis.

Un segundo elemento opcional de información que se puede dar para los paréntesis es una letra alfanumérica que se utiliza para limitar aún más la selección dependiendo del tipo de token inmediatamente anterior al paréntesis. Las letras posibles son actualmente 'k', 'K', 'f', 'F', 'w', y 'W', con estos significados para que coincida con lo que precede a un paréntesis de apertura (ver "Especificar tipos de paréntesis"):

'k' coincide si el token no en blanco anterior es una palabra clave de perl
    (como 'if', 'while'),
'K' coincide si 'k' no coincide: el token anterior no es una palabra clave
'f' coincide si el token anterior es una función (no una palabra clave)
'F' coincide si 'f' no coincide.
'w' coincide si 'k' o 'f' coinciden.
'W' coincide si 'w' no coincide.

Por ejemplo:

-lpil = 'f('

significa aplicar -lp solo a llamadas a funciones, y

-lpil = 'w('

significa aplicar -lp solo a listas entre paréntesis que siguen a una función o a una palabra clave.

Este último ejemplo podría escribirse alternativamente usando la bandera -lpxl=s como

-lpxl = '[ { W('

que dice excluir -lp para listas dentro de corchetes, llaves y paréntesis NO precedidos por una palabra clave o función. Claramente, el método -lpil=s es más fácil de entender.

Un código numérico opcional puede seguir a cualquiera de los tipos de contenedor para refinar aún más la selección basada en el contenido del contenedor. Los códigos numéricos son:

'0' o en blanco: no se aplica ninguna restricción al contenido del contenedor
'1' el contenido del contenedor debe ser una lista simple sin sublistas
'2' el contenido del contenedor debe ser una lista simple sin sublistas,
    sin bloques de código y sin operadores ternarios

Por ejemplo,

-lpil = 'f(2'

significa aplicar -lp solo a llamadas a funciones con listas simples (que no contengan sublistas, bloques de código o expresiones ternarias).

-cti=n, --closing-token-indentation

-cti = 0 sin indentación adicional (por defecto)

-cti = 2 un nivel de indentación adicional si la línea parece:

Algunos son más sutiles e involucran los espacios en blanco alrededor de símbolos de palabras desnudas y ubicaciones de posibles identificadores de archivos. Por ejemplo, considere el problema de formatear la siguiente subrutina: 
sub print_div {
   my ($x,$y)=@_;
   print $x/$y;
}

Supongamos que el usuario solicita que los signos / tengan un espacio a la izquierda pero no a la derecha. Perltidy se negará a hacer esto, pero si se hiciera, el resultado sería

sub print_div {
    my ($x,$y)=@_;
    print $x /$y;
}

Si se formatea de esta manera, el programa no se ejecutará (al menos con versiones recientes de perl) porque $x se toma como un identificador de archivo y / se asume que inicia una cita. En un programa complejo, podría haber un / que termine la cita multilínea sin un error de sintaxis, lo que permitiría que el programa se ejecute, pero no como se pretendía.

Problemas relacionados surgen con otros símbolos de operadores binarios, como + y -, y en versiones anteriores de perl, podría haber problemas con operadores ternarios. Por lo tanto, para evitar cambiar el comportamiento del programa, perltidy tiene la regla simple de que los espacios en blanco alrededor de posibles identificadores de archivos se dejan sin cambios. Asimismo, los espacios en blanco alrededor de palabras desnudas desconocidas se dejan sin cambios. La razón es que si las palabras desnudas se definen en otros módulos, o en código que ni siquiera se ha escrito todavía, perltidy no habrá visto sus prototipos y debe tratarlos con cautela.

En perltidy, esto se implementa en el tokenizador marcando el token que sigue a la palabra clave print como un tipo especial Z. Cuando se está formateando, el espacio en blanco que sigue a este tipo de token generalmente se deja sin cambios como una precaución contra el cambio del comportamiento del programa. Esto es excesivamente conservador pero simple y fácil de implementar. Las palabras clave que se tratan de manera similar a print incluyen printf, sort, exec, system. Es posible que deban realizarse cambios en el espaciado alrededor de los parámetros que siguen a estas palabras clave de forma manual. Por ejemplo, el espacio, o la falta de espacio, después del parámetro $foo en la siguiente línea no se modificará en el formateo.

system($foo );
system($foo);

Para saber si un token es de tipo Z, puede usar perltidy -DEBUG. Para la primera línea anterior, el resultado es

1: system($foo );
1: kkkkkk{ZZZZb};

lo que demuestra que system es de tipo k (palabra clave) y $foo es de tipo Z.

Nota2: Las reglas de espacio en blanco de Perltidy no son perfectas
A pesar de estas precauciones, todavía es posible introducir errores de sintaxis con algunas reglas de espacio en blanco asimétricas, particularmente cuando los parámetros de llamada no se colocan entre paréntesis o llaves de contención. Por ejemplo, las siguientes dos líneas serán analizadas por perl sin un error de sintaxis:

# programación original, sintaxis ok
my @newkeys = map $_-$nrecs+@data, @oldkeys;
# perltidy por defecto, sintaxis ok
my @newkeys = map $_ - $nrecs + @data, @oldkeys;

Pero lo siguiente dará un error de sintaxis:

# perltidy -nwrs='-'
my @newkeys = map $_ -$nrecs + @data, @oldkeys;

Para otro ejemplo, las siguientes dos líneas serán analizadas sin error de sintaxis:

# programación original, sintaxis ok
for my $severity ( reverse $LOWEST+1 .. $HIGHEST ) { ...  }
# perltidy por defecto, sintaxis ok
for my $severity ( reverse $LOWEST + 1 .. $HIGHEST ) { ... }

Pero lo siguiente dará un error de sintaxis:

# perltidy -nwrs='+', error de sintaxis:
for my $severity ( reverse $LOWEST +1 .. $HIGHEST ) { ... }

Para evitar problemas sutiles de análisis como este, es mejor evitar espaciar un operador binario de forma asimétrica con un espacio a la izquierda pero no a la derecha.

Espacio entre palabras clave específicas y paréntesis de apertura
Cuando un paréntesis de apertura sigue a una palabra clave de Perl, no se introduce ningún espacio después de la palabra clave, a menos que sea (por defecto) una de las siguientes: 
my local our state and or xor err eq ne if else elsif until unless
while for foreach return switch case given when catch

Estos valores predeterminados se pueden modificar con dos comandos:

-sak=s o --space-after-keyword=s agrega palabras clave.

-nsak=s o --nospace-after-keyword=s elimina palabras clave.

donde s es una lista de palabras clave (entre comillas si es necesario). Por ejemplo,

my ( $a, $b, $c ) = @_;    # por defecto
my( $a, $b, $c ) = @_;     # -nsak="my local our"

La abreviatura -nsak='*' es equivalente a incluir todas las palabras clave de la lista anterior.

Cuando se incluyen los comandos -nsak=s y -sak=s, el comando -nsak=s se ejecuta primero. Por ejemplo, para tener espacio solo después de las palabras clave (my, local, our), podría usar -nsak="*" -sak="my local our".

Para colocar un espacio después de todas las palabras clave, consulte el siguiente elemento.

Espacio entre todas las palabras clave y los paréntesis de apertura
Cuando un paréntesis de apertura sigue a una función o palabra clave, no se introduce ningún espacio después de la palabra clave, excepto para las palabras clave que se anotan en el elemento anterior. Para colocar siempre un espacio entre una función o palabra clave y su paréntesis de apertura, use el comando:

-skp o --space-keyword-paren

También es posible que desee utilizar también la opción -sfp (siguiente elemento).

Espacio entre todos los nombres de funciones y los paréntesis de apertura
Cuando un paréntesis de apertura sigue a una función, el formateo predeterminado y recomendado es no introducir un espacio. Para que se introduzca un espacio, use:

-sfp o --space-function-paren

myfunc( $a, $b, $c );    # por defecto
myfunc ( $a, $b, $c );   # -sfp

Probablemente también querrá usar la opción -skp (elemento anterior).

El parámetro no se recomienda porque espaciar un paréntesis de función puede hacer que un programa sea vulnerable a problemas de análisis por parte de Perl. Por ejemplo, el siguiente programa de dos líneas se ejecutará tal como está escrito, pero tendrá un error de sintaxis si se reformatea con -sfp:

if ( -e filename() ) { print "I'm here\n"; }
sub filename { return $0 }

En este caso particular, el error de sintaxis se puede eliminar si se invierte el orden de las líneas, de modo que Perl analice primero 'sub filename'.

-fpva o --function-paren-vertical-alignment
Un efecto secundario de usar la opción -sfp es que los paréntesis pueden alinearse verticalmente. Por ejemplo,

# perltidy -sfp
myfun     ( $aaa, $b, $cc );
mylongfun ( $a, $b, $c );

Este es el comportamiento predeterminado. Para evitar esta alineación, use -nfpva:

# perltidy -sfp -nfpva
myfun ( $aaa, $b, $cc );
mylongfun ( $a, $b, $c );
-spp=n o --space-prototype-paren=n
Esta opción se puede usar para controlar si un prototipo de función va precedido de un espacio. Por ejemplo, el siguiente prototipo no tiene espacio. 
sub usage();

Este entero n puede tener el valor 0, 1 o 2 de la siguiente manera:

-spp=0 significa sin espacio antes del paréntesis
-spp=1 significa seguir el ejemplo del código fuente [POR DEFECTO]
-spp=2 significa poner siempre un espacio antes del paréntesis

El valor predeterminado es -spp=1, lo que significa que se usará un espacio si, y solo si, hay uno en el código fuente. Dada la línea de código anterior, el resultado de aplicar las diferentes opciones sería:

sub usage();    # n=0 [sin espacio]
sub usage();    # n=1 [por defecto; sigue la entrada]
sub usage ();   # n=2 [espacio]
-ssp=n o --space-signature-paren=n
Esta opción es análoga a la anterior, excepto que se aplica al espacio antes del paréntesis de apertura de una firma de subrutina en lugar de un prototipo de subrutina.

Por ejemplo, considere la siguiente línea:

sub circle( $xc, $yc, $rad )

Este espacio antes del paréntesis de apertura se puede controlar con el entero n, que puede tener el valor 0, 1 o 2 con estos significados:

-ssp=0 significa sin espacio antes del paréntesis
-ssp=1 significa seguir el ejemplo del código fuente [POR DEFECTO]
-ssp=2 significa poner siempre un espacio antes del paréntesis

El valor predeterminado es -ssp=1, lo que significa que habrá un espacio en la salida si, y solo si, hay uno en la entrada. Dada la línea de código anterior, el resultado de aplicar las diferentes opciones sería:

sub circle( $xc, $yc, $rad )   # n=0 [sin espacio]
sub circle( $xc, $yc, $rad )   # n=1 [por defecto; igual que la entrada]
sub circle ( $xc, $yc, $rad )  # n=2 [espacio]
-kpit=n o --keyword-paren-inner-tightness=n
El espacio dentro de un paréntesis de apertura, que a su vez sigue a una palabra clave determinada, puede controlarse mediante este parámetro. El espacio en el interior del paréntesis de cierre correspondiente se tratará de la misma manera (equilibrada). Este parámetro tiene prioridad sobre cualquier otra regla de espaciado de paréntesis. Los valores de n son los siguientes: 
-kpit=0 significa poner siempre un espacio (no ajustado)
-kpit=1 significa ignorar este parámetro [por defecto]
-kpit=2 significa no poner nunca un espacio (ajustado)

Para ilustrar, el siguiente fragmento se muestra formateado de tres maneras:

if ( seek( DATA, 0, 0 ) ) { ... }    # perltidy (por defecto)
if (seek(DATA, 0, 0)) { ... }        # perltidy -pt=2
if ( seek(DATA, 0, 0) ) { ... }      # perltidy -pt=2 -kpit=0

En el segundo caso, el parámetro -pt=2 hace que todos los paréntesis queden ajustados. En el tercer caso, la opción -kpit=0 hace que el espacio dentro de los paréntesis de 'if' tenga un espacio, ya que 'if' es una de las palabras clave a las que se aplica la opción -kpit por defecto. Los paréntesis restantes siguen ajustados debido al parámetro -pt=2.

El conjunto de palabras clave a las que se aplica este parámetro son por defecto:

if elsif unless while until for foreach

Estos se pueden cambiar con el parámetro -kpitl=s descrito en la siguiente sección.

-kpitl=string o --keyword-paren-inner-tightness-list=string
Este comando se puede usar para cambiar las palabras clave a las que se aplica el parámetro anterior, -kpit=n. El parámetro string es una lista requerida de palabras clave o funciones,

Opciones

-kpitl=n
Este parámetro opcional, que puede ser una lista de palabras clave, indica qué palabras clave deben ser tratadas de forma especial en cuanto a los espacios dentro de los paréntesis. Si hay más de una palabra clave, deben ir entre comillas. Por sí solo, este parámetro no provoca ningún cambio en el espaciado, por lo que el comando -kpit=n sigue siendo necesario.

Por ejemplo, los comandos "-kpitl="if else while" -kpit=2" harán que solo los espacios dentro de los paréntesis que siguen a las palabras clave 'if', 'else' y 'while' sigan el valor de ajuste indicado por el flag -kpit=2.

-lop o --logical-padding
En el siguiente ejemplo se ha insertado un espacio adicional en la segunda línea entre los dos paréntesis de apertura. Este espacio adicional se denomina "relleno lógico" (logical padding) y tiene como objetivo ayudar a alinear verticalmente elementos similares en algunas expresiones lógicas o ternarias. 
# perltidy [formato por defecto]
$same =
  (      ( $aP eq $bP )
      && ( $aS eq $bS )
      && ( $aT eq $bT )
      && ( $a->{'title'} eq $b->{'title'} )
      && ( $a->{'href'} eq $b->{'href'} ) );

Nótese que esto se considera una operación diferente de la "alineación vertical" porque se ajusta el espacio en una sola línea, mientras que en la "alineación vertical" se ajustan los espacios en todas las líneas. Por lo tanto, es una especie de versión local de la alineación vertical.

Aquí hay un ejemplo que involucra un operador ternario:

# perltidy [formato por defecto]
$bits =
    $top > 0xffff ? 32
  : $top > 0xff   ? 16
  : $top > 1      ? 8
  :                 1;

Este comportamiento se controla con el flag --logical-padding, que está activado por defecto. Si no se desea, se puede desactivar usando --nological-padding o -nlop. Los dos ejemplos anteriores, con -nlop, quedan así:

# perltidy -nlop
$same =
  ( ( $aP eq $bP )
      && ( $aS eq $bS )
      && ( $aT eq $bT )
      && ( $a->{'title'} eq $b->{'title'} )
      && ( $a->{'href'} eq $b->{'href'} ) );
# perltidy -nlop
$bits =
  $top > 0xffff ? 32
  : $top > 0xff ? 16
  : $top > 1    ? 8
  :               1;
Recorte de espacios en blanco alrededor de comillas "qw"
-tqw o --trim-qw proporcionan el comportamiento por defecto de recortar los espacios alrededor de comillas "qw" multilínea e indentarlos adecuadamente.

-ntqw o --notrim-qw hacen que los espacios en blanco iniciales y finales alrededor de comillas "qw" multilínea se dejen sin cambios. Esta opción normalmente no será necesaria, pero se añadió con fines de prueba, ya que en algunas versiones de perl, el recorte de comillas "qw" cambia el árbol de sintaxis.

-sbq=n o --space-backslash-quote=n
líneas como 
$str1=\"string1";
$str2=\'string2';

pueden confundir a los resaltadores de sintaxis a menos que se incluya un espacio entre la barra invertida y la comilla simple o doble.

esto se puede controlar con el valor de n de la siguiente manera:

-sbq=0 significa sin espacio entre la barra invertida y la comilla
-sbq=1 significa seguir el ejemplo del código fuente
-sbq=2 significa poner siempre un espacio entre la barra invertida y la comilla

El valor por defecto es -sbq=1, lo que significa que se usará un espacio si hay uno en el código fuente.

Recorte de espacios en blanco finales de líneas de POD
-trp o --trim-pod eliminarán los espacios en blanco finales de las líneas de POD. El valor por defecto es no hacer esto.

Controles de Comentarios

Perltidy tiene varias formas de controlar la apariencia tanto de comentarios de bloque como de comentarios laterales. El término comentario de bloque se refiere aquí a un comentario de línea completa, mientras que comentario lateral se referirá a un comentario que aparece en una línea a la derecha de algún código.

Perltidy no realiza ningún ajuste de línea de texto comentado para hacer coincidir una longitud de línea máxima seleccionada. Esto se debe a que no hay forma de determinar si es apropiado para el contenido dado. Sin embargo, un programa interactivo llamado perlcomment.pl está disponible en la carpeta examples de la distribución de perltidy que puede ayudar a hacer esto.

-ibc, --indent-block-comments
Los comentarios de bloque normalmente lucen mejor cuando están indentados al mismo nivel que el código que les sigue. Este es el comportamiento por defecto, pero puede usar -nibc para mantener los comentarios de bloque justificados a la izquierda. Aquí hay un ejemplo: 
# este comentario está indentado      (-ibc, por defecto)
if ($task) { yyy(); }

La alternativa es -nibc:

# este comentario no está indentado              (-nibc)
            if ($task) { yyy(); }

Vea también el siguiente elemento, -isbc, así como -sbc, para otras formas de tener comentarios de bloque indentados y no indentados.

-isbc, --indent-spaced-block-comments
Si no hay un espacio inicial en la línea, entonces el comentario no se indentará, y de lo contrario sí podrá hacerlo.

Si tanto -ibc como -isbc están activados, entonces -isbc tiene prioridad.

-olc, --outdent-long-comments
Cuando -olc está activado, las líneas que son comentarios de bloque (de línea completa) más largos que el valor de maximum-line-length verán eliminada su indentación. Este es el valor por defecto; use -nolc para evitar la indentación hacia afuera (outdenting).
-msc=n, --minimum-space-to-comment=n
Los comentarios laterales lucen mejor cuando están alineados varios espacios a la derecha del código. Perltidy intentará mantener los comentarios al menos n espacios a la derecha. El valor por defecto es n=4 espacios.
-fpsc=n, --fixed-position-side-comment=n
Este parámetro indica a perltidy que alinee los comentarios laterales en la columna número n siempre que sea posible. El valor por defecto, n=0, no hará esto.
-iscl, --ignore-side-comment-lengths
Este parámetro hace que perltidy ignore la longitud de los comentarios laterales al establecer saltos de línea. El valor por defecto, -niscl, es incluir la longitud de los comentarios laterales al romper líneas para mantenerse dentro de la longitud prescrita por el parámetro de longitud máxima de línea -l=n. Por ejemplo, la siguiente línea única permanecerá intacta con -l=50 y -iscl: 
# perltidy -l=50 -iscl
$vmsfile =~ s/;[\d\-]*$//;    # Clip off version number

mientras que sin el flag -iscl la línea se romperá:

# perltidy -l=50
$vmsfile =~
  s/;[\d\-]*$//;    # Clip off version number
-ipc, --ignore-perlcritic-comments
Perltidy, por defecto, buscará comentarios laterales que comiencen con ## no critic e ignorará sus longitudes al tomar decisiones sobre saltos de línea, incluso si el usuario no ha establecido -iscl. La razón es que un salto de línea no deseado puede hacer que estos comentarios especiales sean ineficaces para controlar perlcritic.

Establecer --ignore-perlcritic-comments indica a perltidy que no busque estos comentarios ## no critic.

-hsc, --hanging-side-comments
Por defecto, perltidy intenta identificar y alinear "comentarios laterales colgantes" (hanging side comments), que son algo así como esto: 
my $IGNORE = 0;    # Este es un comentario lateral
                   # Este es un comentario lateral colgante
                   # Y este también

Un comentario se considera un comentario lateral colgante si (1) sigue inmediatamente a una línea con un comentario lateral, u otro comentario lateral colgante, y (2) hay algún espacio inicial en la línea. Para desactivar esta característica, use -nhsc o --nohanging-side-comments. Si los comentarios de bloque están precedidos por una línea en blanco, o no tienen espacio inicial, no se confundirán con comentarios laterales colgantes.

Los comentarios laterales de cierre son comentarios especiales que perltidy puede crear y colocar automáticamente después de las llaves de cierre de bloques de código seleccionados. Pueden ser útiles para el mantenimiento y la depuración del código. Los parámetros de control son los siguientes.
-csc, o --closing-side-comments
El comando -csc (o --closing-side-comments) añade o actualiza comentarios laterales de cierre. Por ejemplo, aquí hay un pequeño fragmento de código 
sub message {
    if ( !defined( $_[0] ) ) {
        print("Hello, World\n");
    }
    else {
        print( $_[0], "\n" );
    }
}

Y este es el resultado de procesar con "perltidy -csc":

sub message {
    if ( !defined( $_[0] ) ) {
        print("Hello, World\n");
    }
    else {
        print( $_[0], "\n" );
    }
} ## end sub message

En este caso, se añadió un comentario lateral de cierre para "sub message", pero no para los bloques "if" y "else", porque estaban por debajo del límite de 6 líneas para añadir comentarios laterales de cierre. Este límite puede cambiarse con el comando -csci, descrito a continuación.

-dcsc, o --delete-closing-side-comments
El comando -dcsc (o --delete-closing-side-comments) elimina estos comentarios. Sin embargo, solo elimina comentarios laterales que tienen el prefijo especial, que es '## end' por defecto.

Si tanto -dcsc como -csc se incluyen en la misma ejecución, entonces -dcsc opera primero para eliminar los comentarios laterales de cierre antiguos. Luego, -csc opera para crear nuevos comentarios laterales de cierre según la configuración de parámetros actual.

donde "n" es el número mínimo de líneas que debe tener un bloque para que se añada un comentario lateral de cierre. El valor por defecto es "n=6". Para ilustrar:

perltidy -csc -ncscb

However this causes a problem with editors which cannot recognize comments or are not configured to do so because they cannot "bounce" around in the text correctly. The -cscb flag has been added to help them by appending appropriate balancing structure:

perltidy -csc -cscb
} ## end foreach my $foo (sort { $b cmp $a ... })

The default is -cscb.

-csce=n, or --closing-side-comment-else-flag=n
The default, n=0, places the text of the opening "if" statement after any terminal "else".

If n=2 is used, then each "elsif" is also given the text of the opening "if" statement. Also, an "else" will include the text of a preceding "elsif" statement. Note that this may result some long closing side comments.

If n=1 is used, the results will be the same as n=2 whenever the resulting line length is less than the maximum allowed.

-cscw, or --closing-side-comment-warnings
This parameter is intended to help make the initial transition to the use of closing side comments. It causes two things to happen if a closing side comment replaces an existing, different closing side comment: first, an error message will be issued, and second, the original side comment will be placed alone on a new specially marked comment line for later attention.

The intent is to avoid clobbering existing hand-written side comments which happen to match the pattern of closing side comments. This flag should only be needed on the first run with -csc.

-cscp=string, or --closing-side-comment-prefix=string
This parameter changes the prefix which is used for closing side comments. The default prefix is "## end". All closing side comments begin with this prefix, and it is used to recognize them in order to update, delete, and format them. Any comment identified as a closing side comment will be placed just a single space to the right of its closing brace.

This parameter is available in case the default causes a conflict with other software, but it should not normally be used because it can complicate keeping code updated in the event that code formatted with different prefixes are mixed. The problem is that in any formatting pass, the various -csc* parameters are restricted to working with a single closing side comment prefix. So if code has closing side comments with differing prefixes, it will take multiple passes to convert them back to a single new prefix.

For a simple example, suppose we have code which was formatted with prefix -cscp='## END', and we want to convert those comments back to the default prefix. It would take two passes, such as:

Pass 1 would find and remove old closing side comments with prefix '## END':

perltidy -cscp='## END' -dcsc oldfile -o tmpfile

Pass 2 could then adds new comments with the default prefix:

perltidy -csc tmpfile -o newfile

Notas importantes sobre comentarios laterales de cierre:

  • Los comentarios laterales de cierre solo se colocan en líneas terminadas con una llave de cierre. Ciertos estilos de cierre, como el uso de `else` agrupados (-ce), impiden la generación de algunos comentarios laterales de cierre.
  • Tenga en cuenta que la adición o eliminación de comentarios laterales de cierre solo se realiza a través de los comandos -csc o -dcsc. Los otros comandos, si se utilizan, simplemente modifican el comportamiento de estos dos comandos.
  • Se recomienda utilizar la bandera -cscw junto con -csc en el primer uso de perltidy en un archivo determinado. Esto evitará la pérdida de cualquier dato de comentario lateral existente que coincida con el prefijo de comentario lateral de cierre.
  • Una vez que use -csc, debe continuar usándolo para que cualquier comentario lateral de cierre permanezca correcto a medida que el código cambia. De lo contrario, estos comentarios se volverán incorrectos a medida que se actualice el código.
  • Si edita los comentarios laterales de cierre generados por perltidy, también debe cambiar el prefijo para que sea diferente del prefijo del comentario lateral de cierre. De lo contrario, sus ediciones se perderán cuando vuelva a ejecutar perltidy con -csc. Por ejemplo, podría simplemente cambiar "## end" por "## End", ya que la prueba distingue entre mayúsculas y minúsculas. Es posible que también desee utilizar la bandera -ssc para mantener estos comentarios laterales de cierre modificados espaciados de la misma manera que los comentarios laterales de cierre reales.
  • Generar temporalmente comentarios laterales de cierre es una técnica útil para explorar y/o depurar un script de perl, especialmente uno escrito por otra persona. Siempre puede eliminarlos con -dcsc.
Comentarios de Bloque Estáticos
Los comentarios de bloque estáticos son comentarios de bloque con un patrón de encabezado especial, "##" por defecto, que se tratarán de manera ligeramente diferente a otros comentarios de bloque. Se comportan efectivamente como si tuvieran pegamento en sus bordes izquierdo y superior, ya que se adhieren al borde izquierdo y a la línea anterior cuando no hay espacios en blanco en esos lugares. Esta opción es particularmente útil para controlar cómo se muestran los códigos comentados.
-sbc, --static-block-comments
Cuando se utiliza -sbc, un comentario de bloque con un patrón de encabezado especial, "##" por defecto, se tratará especialmente.

Los comentarios identificados de esta manera se tratan de la siguiente manera:

  • Si no hay espacio al principio de la línea, el comentario no se indentará, y de lo contrario sí podrá serlo.
  • No se insertará una nueva línea en blanco antes de dicho comentario.
  • Dicho comentario nunca se convertirá en un comentario lateral colgado.

Por ejemplo, asumiendo que @month_of_year está alineado a la izquierda, el formato predeterminado para el siguiente fragmento es:

# perltidy -sbc [predeterminado]
@month_of_year = (
    'Jan', 'Feb', 'Mar', 'Apr', 'May', 'Jun',
##  'Jul', 'Aug', 'Sep', 'Oct', 'Dec', 'Nov'
    'Jul', 'Aug', 'Sep', 'Oct', 'Nov', 'Dec'
);

Esto puede ser útil para mostrar código que ha sido comentado. Sin esta convención, el código anterior se convertiría en

# perltidy -nsbc
@month_of_year = (
    'Jan', 'Feb', 'Mar', 'Apr', 'May', 'Jun',
    ##  'Jul', 'Aug', 'Sep', 'Oct', 'Dec', 'Nov'
    'Jul', 'Aug', 'Sep', 'Oct', 'Nov', 'Dec'
);

lo cual es menos claro. El valor predeterminado es usar -sbc. Esto puede desactivarse con -nsbc.

Static Block Comments

Static block comments are comments with a special leading pattern.

-sbc, --static-block-comments
When -sbc is used, a comment with a static block comment leading pattern, which is "##" by default, will be treated as a static block comment. This means that it will be spaced only a single space from previous character, and it will not be vertically aligned with other block comments.

The default is -nsbc.

-sbcp=string, --static-block-comment-prefix=string
This parameter defines the prefix used to identify static block comments when the -sbc parameter is set. The default prefix is "##", corresponding to "-sbcp=##". The prefix is actually part of a perl pattern used to match lines and it must either begin with "#" or "^#". In the first case a prefix ^\s* will be added to match any leading whitespace, while in the second case the pattern will match only comments with no leading whitespace. For example, to identify all comments as static block comments, one would use "-sbcp=#". To identify all left-adjusted comments as static block comments, use "-sbcp='^#'".

Please note that -sbcp merely defines the pattern used to identify static block comments; it will not be used unless the switch -sbc is set. Also, please be aware that since this string is used in a perl regular expression which identifies these comments, it must enable a valid regular expression to be formed.

A pattern which can be useful is:

-sbcp=^#{2,}[^\s#]

This pattern requires a static block comment to have at least one character which is neither a # nor a space. It allows a line containing only '#' characters to be rejected as a static block comment. Such lines are often used at the start and end of header information in subroutines and should not be separated from the intervening comments, which typically begin with just a single '#'.

-osbc, --outdent-static-block-comments
The command -osbc will cause static block comments to be outdented by the number of --continuation-spaces=n, if possible.
Static Side Comments
Static side comments are side comments with a special leading pattern. This option can be useful for controlling how commented code is displayed when it is a side comment.
-ssc, --static-side-comments
When -ssc is used, a side comment with a static leading pattern, which is "##" by default, will be spaced only a single space from previous character, and it will not be vertically aligned with other side comments.

The default is -nssc.

-sscp=string, --static-side-comment-prefix=string
This parameter defines the prefix used to identify static side comments when the -ssc parameter is set. The default prefix is "##", corresponding to "-sscp=##".

Please note that -sscp merely defines the pattern used to identify static side comments; it will not be used unless the switch -ssc is set. Also, note that this string is used in a perl regular expression which identifies these comments, so it must enable a valid regular expression to be formed.

Saltando Secciones Seleccionadas de Código

Se pueden pasar líneas de código seleccionadas tal cual a la salida sin ningún formato marcando las líneas de inicio y fin con comentarios especiales. Hay dos opciones para hacer esto. La primera opción se llama --format-skipping o -fs, y la segunda opción se llama --code-skipping o -cs.

En ambos casos, las líneas de código se mostrarán sin cambios. La diferencia es que en --format-skipping perltidy seguirá analizando las líneas de código marcadas y comprobando si hay errores, mientras que en --code-skipping perltidy simplemente pasará las líneas a la salida sin ninguna comprobación.

Ambas características están habilitadas por defecto y se invocan con marcadores de comentarios especiales. --format-skipping utiliza los marcadores de inicio y fin '#<<<' y '#>>>', así:

#<<< formato omitido: no dejes que perltidy cambie mi formato agradable
   my @list = (1,
               1, 1,
               1, 2, 1,
               1, 3, 3, 1,
               1, 4, 6, 4, 1,);
#>>>

--code-skipping utiliza los marcadores de inicio y fin '#<<V' y '#>>V', así:

#<<V  código omitido: perltidy pasa esto tal cual, sin comprobación de errores
   token ident_digit {
       [ [ <?word> | _ | <?digit> ] <?ident_digit>
       |   <''>
       ]
   };
#>>V

(La última letra V es como una < o > rotada 90 grados). Se puede incluir texto adicional en las líneas de comentarios especiales siempre que esté separado del marcador por al menos un espacio, como en los ejemplos anteriores.

Se recomienda usar --code-skipping solo si necesita ocultar un bloque de sintaxis extendida que produciría errores si fuera analizado por perltidy, y usar --format-skipping en caso contrario. Esto se debe a que la opción --format-skipping proporciona los beneficios de la comprobación de errores, y esencialmente no hay limitaciones en cuanto a las líneas a las que se puede aplicar. La opción --code-skipping, por otro lado, no realiza comprobación de errores y su uso es más restrictivo porque el código que queda, después de omitir las líneas marcadas, debe ser código sintácticamente correcto con contenedores equilibrados.

Puede aparecer cualquier número de secciones de omisión de código o de formato en un archivo.

Cuando se marcan múltiples secciones de código para format-skipping, los marcadores de inicio y fin deben alternarse desde el principio del archivo hasta el final (es decir, las secciones de omisión de código no se pueden apilar). Si los marcadores no alternan, se producirá una advertencia y no se realizará el formateo. Esto es para ayudar a detectar errores de forma temprana. Normalmente, el primer marcador en un archivo será un marcador de inicio y el último será un marcador de fin, pero esto no es necesario. Si el primer marcador es un marcador de fin, entonces la omisión del formato comienza en la primera línea y continúa hasta ese marcador de fin (a menos que se haya desactivado el indicador --detect-format-skipping-from-start; véase más abajo). Si el último marcador es un marcador de inicio, entonces la omisión continúa hasta el final del archivo.

Para code-skipping, las reglas para múltiples secciones son un poco más primitivas porque perltidy está analizando simultáneamente el texto mientras busca marcadores. Hay dos casos, dependiendo del indicador complementario --code-skipping-from-start, descrito más abajo. Si este indicador no se ha establecido, que es el valor por defecto, entonces la omisión de código comienza cuando se encuentra un marcador de inicio y continúa hasta que se alcanza un marcador de fin, o el final del archivo. Si el indicador --code-skipping-from-start está establecido, entonces la omisión de código comienza con la primera línea y continúa hasta un marcador de fin, o el final del archivo. En ambos casos, la omisión de código se reiniciará si se encuentra un marcador de inicio.

Estas características deben usarse con moderación para evitar ensuciar el código con marcadores, pero pueden ser útiles para solucionar problemas ocasionales.

Tenga en cuenta que puede ser posible evitar el uso de --format-skipping para el caso específico de una lista de valores separados por comas, como en el ejemplo anterior, simplemente insertando una línea en blanco o un comentario en algún lugar entre los paréntesis de apertura y cierre. Consulte la sección "Control de Formato de Listas".

Las siguientes secciones describen los controles disponibles para estas opciones. Normalmente no deberían ser necesarios.

-fs, --format-skipping
Este es el interruptor maestro para la omisión de formato. Como se explicó anteriormente, este indicador, que está habilitado por defecto, hace que cualquier código entre marcadores de comentarios especiales de inicio y fin se pase a la salida sin formatear. Sin embargo, el código entre los comentarios todavía se comprueba en busca de errores. El marcador de inicio por defecto es #<<< y el marcador de fin por defecto es #>>>.

Esta característica se puede deshabilitar con -nfs. Normalmente no debería ser necesario.

-fsb=string, --format-skipping-begin=string
Este y el siguiente parámetro permiten cambiar los comentarios especiales de inicio y fin. Sin embargo, se recomienda cambiarlos solo si hay un conflicto entre los valores por defecto y algún otro uso. Si se utilizan, se recomienda que solo se introduzcan en un archivo .perltidyrc, en lugar de en la línea de comandos. Esto se debe a que escapar correctamente estos parámetros en la línea de comandos puede ser difícil.

Si los marcadores de comentarios cambiados no parecen funcionar, use el indicador -log y examine el archivo .LOG para ver si se detectan y dónde.

El valor por defecto es equivalente a -fsb='#<<<'. La cadena que introduzca debe comenzar con un # y debe estar entre comillas según sea necesario para pasar el shell de comandos de su sistema. En realidad, es el texto inicial de un patrón que se construye añadiendo un '\s', por lo que también debe incluir barras invertidas para que los caracteres se tomen literalmente en lugar de como patrones.

Algunos ejemplos muestran cómo las cadenas de ejemplo se convierten en patrones:

-fsb='#\{\{\{' se convierte en /^#\{\{\{\s/ que coincide con #{{{ pero no con #{{{{
-fsb='#\*\*'   se convierte en /^#\*\*\s/   que coincide con #** pero no con #***
-fsb='#\*{2,}' se convierte en /^#\*{2,}\s/ que coincide con #** y #*****
-fse=string, --format-skipping-end=string
-fse=string es el parámetro correspondiente utilizado para cambiar el marcador de fin para la omisión de formato. El valor por defecto es equivalente a -fse='#<<<'.
-dfsfs, --detect-format-skipping-from-start
Si perltidy encuentra un comentario de fin de omisión de formato antes de cualquier comentario de inicio de omisión de formato, entonces por defecto asumirá que la omisión de formato comienza con la primera línea del archivo. Use -ndfsfs, o --nodetect-format-skipping-from-start para evitar hacer esta suposición. En ese caso, si el primer marcador de omisión de formato en un archivo es un marcador de fin, será ignorado.
-cs, --code-skipping
Este es el interruptor maestro para la omisión de código. Este indicador, que está habilitado por defecto, hace que cualquier código entre marcadores de comentarios especiales de inicio y fin se pase directamente a la salida sin ninguna comprobación de errores ni formato. Esencialmente, perltidy simplemente emite las líneas sin cambios.
perltidy lo trata como si fuera un bloque de texto arbitrario. El marcador de inicio predeterminado es #<<V y el marcador de fin predeterminado es #>>V.

Esta característica se puede desactivar con -ncs. Normalmente, esto no debería ser necesario.

-csb=cadena, --code-skipping-begin=cadena
Esto se puede usar para cambiar el comentario de inicio de una sección de --code-skipping, y su uso es similar a -fsb=cadena. El valor predeterminado es equivalente a -csb='#<<V'.
-cse=cadena, --code-skipping-end=cadena
Esto se puede usar para cambiar el comentario de fin de una sección de --code-skipping, y su uso es similar a -fse=cadena. El valor predeterminado es equivalente a -cse='#>V'>.
-csfs, --code-skipping-from-start
Cuando esta bandera está activada y el salto de código no ha sido desactivado, el salto de código comienza desde el inicio de un archivo, incluso si no hay un comentario de inicio de salto de código. En otras palabras, establecer esta bandera es como tener una línea de marcador de inicio '#<<V' justo antes de la primera línea del archivo. El salto de código continuará hasta que se alcance un comentario de fin.

Formatear Solo Secciones de Código Etiquetadas

Un comando --skip-formatting-except-id=etiqueta, o -sfei=etiqueta, está disponible para hacer que perltidy formatee **solo** las secciones de código que están etiquetadas con la etiqueta seleccionada en los comentarios de "format-skipping".

Por ejemplo, las secciones etiquetadas podrían contener tablas que se formatean mejor con valores especiales del parámetro --maximum-line-length. O quizás una sección etiquetada es una tabla profundamente anidada que evitaría saltos de línea no deseados si se formatea con menos sangría, usando un valor especial de --starting-indentation-level=n.

El nombre de la etiqueta se introduce con el texto agregado id=NOMBRE después de uno o más espacios en el comentario de apertura de format-skipping. La etiqueta NOMBRE puede ser cualquier combinación de letras y números, y no debe haber ningún espacio alrededor del signo igual.

Por ejemplo

#<<< id=LineasLargas
  ...
#>>>

El código en esta sección se tratará como cualquier otra sección de salto de formato, a menos que se introduzca el parámetro --skip-formatting-except-id=LineasLargas. En ese caso, se formateará.

Aquí hay algunos puntos sobre esta opción:

  • La opción especial --skip-formatting-except-id='-', o -sfei='-', significa omitir todo el formato (ya que una etiqueta llamada '-' no existe). Esto permitirá que el código sea escaneado en busca de problemas, pero el formato no se cambiará. El parámetro -notidy también se puede usar para omitir el formato, pero sale en un punto anterior del proceso, por lo que se ejecuta más rápido pero no realiza tantas comprobaciones de código.
  • La opción especial --skip-formatting-except-id='*', o -sfei='*', significa formatear todas las secciones marcadas para omitir formato, independientemente de cualquier comentario id=. Esto puede eliminar la necesidad de agregar id= a los marcadores de omisión de formato en casos simples.
  • Las secciones que se están omitiendo o formateando se pueden determinar volcando un archivo de registro con el parámetro -g.
  • Cuando se utiliza esta opción, la sangría inicial todavía se adivina a partir del primer código en el archivo, incluso si no se está formateando. Si esto da como resultado una sangría no deseada de la sección etiquetada, entonces el parámetro --starting-indentation-level=n, o -sil=n, se puede usar para establecer la sangría deseada.
  • Si el primer marcador de omisión de formato en un archivo es un marcador de fin, entonces termina una sección de omisión de formato que comienza desde la primera línea del archivo sin un marcador de inicio. Por lo tanto, el método habitual de colocar una etiqueta de identificador en el marcador de inicio no se puede utilizar. En este caso especial, se puede colocar un identificador para esa sección en el marcador de fin. Este es el único caso en el que se lee un identificador desde un marcador de fin.

Formatear un Rango Limitado de Líneas

Un comando --line-range-tidy=n1:n2 está disponible para procesar solo un rango seleccionado de líneas de una secuencia de entrada con perltidy. Este comando es principalmente de interés para programar editores de código interactivos. Cuando se usa, se lee toda la secuencia de entrada, pero solo el rango seleccionado de líneas del archivo de entrada es procesado por el tokenizador y formateador de perltidy, y luego la secuencia se reensambla para su salida. Las líneas seleccionadas deben contener una sentencia completa o un contenedor equilibrado. De lo contrario, ocurrirá un error de sintaxis y el código no se ordenará. Hay un par de limitaciones en el uso de este comando: (1) no se puede aplicar a múltiples archivos y (2) solo se aplica a la corrección de código y no, por ejemplo, al formato html.

-lrt=n1:n2, --line-range-tidy=n1:n2
El rango de líneas se especifica mediante los enteros n1 y n2, donde n1 es el primer número de línea a formatear (comenzando a contar desde 1) y n2 es el último número de línea a formatear. Si no se proporciona n2, o excede el número real de líneas, el formateo continúa hasta el final del archivo.

Ejemplos:

--line-range-tidy=43:109      # ordenar las líneas 43 a 109
--line-range-tidy=' 43 : 109' # ordenar las líneas 43 a 109
--line-range-tidy=1:          # ordenar todas las líneas
--line-range-tidy=0:90        # ERROR (n1 debe ser >= 1)

El segundo ejemplo muestra que los espacios están permitidos si se colocan entre comillas.

Control de Saltos de Línea

Los parámetros en esta y las siguientes secciones controlan los saltos después de líneas de código no en blanco. Las líneas en blanco se controlan por separado mediante parámetros en la sección "Control de Líneas en Blanco".

-dnl, --delete-old-newlines
Por defecto, perltidy primero elimina todas las ubicaciones de saltos de línea antiguos, y luego busca buenos puntos de salto para que coincidan con la longitud de línea deseada. Usa -ndnl o --nodelete-old-newlines para forzar a perltidy a retener todos los puntos de salto de línea antiguos.
-anl, --add-newlines
Por defecto, perltidy agregará saltos de línea cuando sea necesario para crear continuaciones de líneas largas y mejorar la apariencia del script. Usa -nanl o --noadd-newlines para evitar cualquier nuevo salto de línea.

Esta bandera no evita que perltidy elimine los saltos de línea existentes; consulta --freeze-newlines para evitar por completo los cambios en los puntos de salto de línea.

-fnl, --freeze-newlines
Si no deseas ningún cambio en los saltos de línea dentro de las líneas de código de tu script, establece -fnl, y permanecerán fijos, al igual que el resto de los comandos de esta sección y las secciones "Control de Formato de Listas", "Retener o Ignorar Saltos de Línea Existentes". Es posible que desees usar --nooutdent-long-lines con esto.

Nota: Si también deseas mantener tus líneas en blanco exactamente como están, puedes usar la bandera --freeze-blank-lines que se describe en la sección "Control de Líneas en Blanco".

Control de Saltos en Llaves, Paréntesis y Corchetes

-ce, --cuddled-else
Habilita el estilo de "else acurrucado", en el que "else" y "elsif" siguen inmediatamente después de la llave que cierra el bloque anterior. Por defecto, no se usan else acurrucados, y se indica con la bandera -nce o --nocuddled-else. Aquí hay una comparación de las alternativas: 
# -ce
if ($task) {
    yyy();
} else {
    zzz();
}
# -nce (por defecto)
if ($task) {
    yyy();
}
else {
    zzz();
}

En este ejemplo, la palabra clave else se coloca en la misma línea que comienza con la llave de cierre del bloque anterior y va seguida por su propia llave de apertura en la misma línea. Otras palabras clave y nombres de funciones que se formatean con este estilo "acurrucado" son elsif, continue, catch, finally.

Otros tipos de bloques pueden ser formateados especificando sus nombres en un parámetro separado --cuddled-block-list, descrito en una sección posterior.

El acurrucamiento entre un par de bloques de código requiere que la llave de cierre del primer bloque comience una nueva línea. Si este bloque está completamente en una sola línea en el archivo de entrada, es necesario decidir si se romperá para permitir el acurrucamiento. Esta decisión se controla mediante la bandera --cuddled-break-options=n (-cbo=n) discutida a continuación. El valor predeterminado y recomendado de -cbo=1 basa esta decisión en el primer bloque de la cadena. Si abarca varias líneas, se realiza el acurrucamiento y continúa a lo largo de la cadena, independientemente de los tamaños de los bloques subsiguientes. De lo contrario, las líneas cortas permanecen intactas.

Así, por ejemplo, la bandera --cuddled-else no tendría ningún efecto si el fragmento anterior se reescribe como

if ($task) { yyy() }
else {    zzz() }

Si el primer bloque abarca varias líneas, entonces se puede realizar el acurrucamiento y continuará para los bloques subsiguientes en la cadena, como se ilustra en el fragmento anterior.

Si hay líneas en blanco entre bloques acurrucados, se eliminarán. Si hay comentarios después de la llave de cierre donde ocurriría el acurrucamiento, se evitará el acurrucamiento. Si esto ocurre, el acurrucamiento se reiniciará más adelante en la cadena si es posible.

-cb, --cuddled-blocks
Esta bandera es equivalente a --cuddled-else (-ce).
-cbl, --cuddled-block-list
Los tipos de bloques acurrucados predeterminados incorporados son else, elsif, continue, catch, finally.

Se pueden definir tipos de bloques adicionales a los que se aplica el estilo --cuddled-blocks mediante este parámetro. Este parámetro es una cadena de caracteres g, dando una lista de tipos de bloques separados por comas o espacios. Por ejemplo, para juntar bloques de código de tipo sort, map y grep, además de los tipos predeterminados, la cadena podría configurarse como

-cbl="sort map grep"

o equivalentemente

-cbl=sort,map,grep

Sin embargo, ten en cuenta que estos tipos de bloques en particular suelen ser cortos, por lo que es posible que no haya muchas oportunidades para el estilo de formato "cuddled".

El uso de comas evita la necesidad de proteger los espacios con comillas.

Como comprobación diagnóstica, el indicador --dump-cuddled-block-list o -dcbl se puede utilizar para ver el hash de valores que se generan con este indicador.

Finalmente, ten en cuenta que el parámetro --cuddled-block-list por sí solo simplemente especifica qué bloques se formatean con el formato "cuddled". No tiene ningún efecto a menos que este estilo de formato se active con --cuddled-else.

-cblx, --cuddled-block-list-exclusive
Cuando se selecciona el formato "cuddled else" con --cuddled-else, establecer este indicador hace que perltidy ignore sus valores predeterminados integrados y dependa exclusivamente de los tipos de bloques especificados en el indicador --cuddled-block-list descrito en la sección anterior. Por ejemplo, para evitar usar "cuddled" para catch y finally, que están entre los valores predeterminados, se podría utilizar el siguiente conjunto de parámetros: 
perltidy -ce -cbl='else elsif continue' -cblx
-cbo=n, --cuddled-break-option=n
El formato "cuddled" solo es posible entre un par de bloques de código si la llave de cierre del primer bloque comienza en una nueva línea. Si se encuentra un bloque que está completamente en una sola línea, y se selecciona el formato "cuddled", es necesario tomar una decisión sobre si "romper" o no el bloque, lo que significa hacer que abarque varias líneas. Este parámetro controla esa decisión. Las opciones son: 
cbo=0  Nunca forzar la ruptura de un bloque corto.
cbo=1  Si el primero de un par de bloques se rompe en el archivo
       de entrada, entonces romper el segundo [PREDETERMINADO].
cbo=2  Romper todos los bloques para un formato "cuddled" máximo.

El valor predeterminado y recomendado es cbo=1. Con este valor, si el bloque de inicio de una cadena abarca varias líneas, se producirá una cascada de rupturas para los bloques restantes, haciendo que toda la cadena se junte ("cuddled").

La opción cbo=0 puede producir un formato "cuddled" errático si hay numerosos bloques de una sola línea.

La opción cbo=2 produce un formato "cuddled" máximo, pero no permitirá ningún bloque corto.

Welding

-wn, --weld-nested-containers
The -wn flag causes closely nested pairs of opening and closing container symbols (curly braces, brackets, or parens) to be "welded" together, meaning that they are treated as if combined into a single unit, with the indentation of the innermost code reduced to be as if there were just a single container symbol.

For example:

# default formatting
do {
    {
        next if $x == $y;
    }
} until $x++ > $z;
# perltidy -wn
do { {
    next if $x == $y;
} } until $x++ > $z;

When this flag is set perltidy makes a preliminary pass through the file and identifies all nested pairs of containers. To qualify as a nested pair, the closing container symbols must be immediately adjacent and the opening symbols must either (1) be adjacent as in the above example, or (2) have an anonymous sub declaration following an outer opening container symbol which is not a code block brace, or (3) have an outer opening paren separated from the inner opening symbol by any single non-container symbol or something that looks like a function evaluation, as illustrated in the next examples. An additional option (4) which can be turned on with the flag --weld-fat-comma is when the opening container symbols are separated by a hash key and fat comma (=>).

Any container symbol may serve as both the inner container of one pair and as the outer container of an adjacent pair. Consequently, any number of adjacent opening or closing symbols may join together in weld. For example, here are three levels of wrapped function calls:

# default formatting
my (@date_time) = Localtime(
    Date_to_Time(
        Add_Delta_DHMS(
            $year, $month,  $day, $hour, $minute, $second,
            '0',   $offset, '0',  '0'
        )
    )
);
# perltidy -wn
my (@date_time) = Localtime( Date_to_Time( Add_Delta_DHMS(
    $year, $month,  $day, $hour, $minute, $second,
    '0',   $offset, '0',  '0'
) ) );

Notice how the indentation of the inner lines are reduced by two levels in this case. This example also shows the typical result of this formatting, namely it is a sandwich consisting of an initial opening layer, a central section of any complexity forming the "meat" of the sandwich, and a final closing layer. This predictable structure helps keep the compacted structure readable.

The inner sandwich layer is required to be at least one line thick. If this cannot be achieved, welding does not occur. This constraint can cause formatting to take a couple of iterations to stabilize when it is first applied to a script. The --converge flag can be used to insure that the final format is achieved in a single run.

Here is an example illustrating a welded container within a welded containers:

# default formatting
$x->badd(
    bmul(
        $class->new(
            abs(
                $sx * int( $xr->num() ) & $sy * int( $yr->num() )
            )
        ),
        $m
    )
);
# perltidy -wn
$x->badd( bmul(
    $class->new( abs(
        $sx * int( $xr->num() ) & $sy * int( $yr->num() )
    ) ),
    $m
) );

Una limitación es que cualquier límite de longitud de línea sigue aplicándose y puede hacer que secciones soldadas largas se dividan en múltiples líneas.

Además, el apilamiento de contenedores definidos por este flag tiene prioridad sobre cualquier otro flag de apilamiento de contenedores. Esto se debe a que cualquier soldadura se realiza primero.

-wfc, --weld-fat-comma
Cuando se activa el flag -wfc, junto con -wn (--weld-nested-containers), a perltidy se le permite soldar un paréntesis de apertura a un contenedor interior de apertura cuando están separados por una clave hash y una coma gorda (=>). Por ejemplo: 
# perltidy -wn -wfc
elf->call_method( method_name_foo => {
    some_arg1       => $foo,
    some_other_arg3 => $bar->{'baz'},
} );

Esta opción está desactivada por defecto.

-wnxl=s, --weld-nested-exclusion-list
El flag -wnxl=s proporciona cierto control sobre los tipos de contenedores que se pueden soldar. El flag -wn por defecto es "codicioso" al soldar contenedores adyacentes. Si suelda más tipos de contenedores de los deseados, este flag proporciona la capacidad de reducir la cantidad de soldadura especificando una lista de elementos que *no* deben soldarse.

La lógica en perltidy para aplicar esto es sencilla. A medida que cada token de contenedor se considera para unir una soldadura, se consultan las reglas de exclusión y se utilizan para rechazar la soldadura si es necesario.

Esta lista es una cadena con elementos separados por espacios. Cada elemento consta de hasta tres piezas de información: (1) una posición opcional, (2) un tipo precedente opcional y (3) un tipo de contenedor.

La única pieza de información requerida es un tipo de contenedor, que es uno de '(', '[', '{' o 'q'. Los tres primeros son tokens de contenedor y el último representa una lista entre comillas. Por ejemplo, la cadena

-wnxl='[ { q'

significa *NO* incluir corchetes, llaves o comillas en ninguna soldadura. El único contenedor no especificado es '(', por lo que esta cadena significa que solo se realizarán soldaduras que involucren paréntesis.

Para ilustrar, el siguiente fragmento soldado consiste en una cadena de tres contenedores soldados con tipos '(', '[' y 'q':

# perltidy -wn
skip_symbols( [ qw(
    Perl_dump_fds
    Perl_ErrorNo
    Perl_GetVars
    PL_sys_intern
) ] );

Aunque el término qw utiliza paréntesis como delimitador de comillas, tiene un tipo especial 'q' aquí. Si aparece en una soldadura, siempre aparece al final de la cadena soldada.

Cualquiera de los tipos de contenedor '[', '{' y '(' puede ser precedido por un indicador de posición que es '^', para indicar el primer token de una secuencia soldada, o '.', para indicar un token interior de una secuencia soldada. (Dado que una cadena entre comillas 'q' siempre termina una cadena, no necesita un indicador de posición).

Por ejemplo, si no queremos que una secuencia de contenedores soldados comience con un corchete, podríamos usar

-wnxl='^['

En el fragmento anterior, hay un corchete pero no inicia la cadena, por lo que el formato no cambiaría si se formateara con esta restricción.

Un tercer elemento opcional de información que se puede proporcionar es una letra alfanumérica que se utiliza para limitar aún más la selección dependiendo del tipo de token inmediatamente antes del contenedor. Si se proporciona, va justo antes del símbolo del contenedor. Las letras posibles son actualmente 'k', 'K', 'f', 'F', 'w' y 'W', con los siguientes significados (ver "Especificación de tipos de paréntesis"):

'k' coincide si el token anterior no en blanco es una palabra clave de Perl
    (como 'if', 'while'),
'K' coincide si 'k' no lo hace: el token anterior no es una palabra clave
'f' coincide si el token anterior es una función (no una palabra clave)
'F' coincide si 'f' no lo hace
'w' coincide si coinciden 'k' o 'f'
'W' coincide si 'w' no lo hace

Por ejemplo, compara

# perltidy -wn
if ( defined( $_Cgi_Query{
    $Config{'methods'}{'auth'}{'remote'}{'cgi'}{'username'}
} ) )

con

# perltidy -wn -wnxl='^K( {'
if ( defined(
    $_Cgi_Query{ $Config{'methods'}{'auth'}{'remote'}{'cgi'}
          {'username'} }
) )

El primer caso realiza la soldadura máxima. En el segundo caso, el paréntesis inicial se conserva por la regla (se habría rechazado si estuviera precedido por una no palabra clave) pero la llave se rechaza por la regla.

Aquí hay algunas cadenas de ejemplo adicionales y sus significados:

'^('   - la soldadura no debe comenzar con un paréntesis
'.('   - los tokens segundo y posteriores no pueden ser paréntesis
'.w('  - los tokens segundo y posteriores no pueden ser de palabras clave o paréntesis de llamada
'('    - sin paréntesis en una soldadura
'^K('  - excluir un paréntesis inicial precedido por una no palabra clave
'.k('  - excluir un paréntesis secundario precedido por una palabra clave
'[ {'  - excluir todos los corchetes y llaves
'[ ( ^K{' - excluir todas excepto estructuras anidadas como do {{  ... }}
Estanqueidad vertical de llaves, paréntesis y corchetes que no son de bloque.
Estos parámetros controlan lo que se denominará estanqueidad vertical. Aquí están los puntos principales:
  • Los tokens de apertura (excepto las llaves de bloque) se controlan con -vt=n, o --vertical-tightness=n, donde 
    -vt=0 siempre dividir una línea después del token de apertura (por defecto).
-vt=1 no dividir a menos que esto produzca más de un
        nivel de indentación en una línea.
-vt=2 nunca dividir una línea después del token de apertura
  • También debes usar el flag -lp (--line-up-parentheses) cuando uses el flag -vt; la razón se explica a continuación.
  • Los tokens de cierre (excepto las llaves de bloque) se controlan con -vtc=n, o --vertical-tightness-closing=n, donde 
    -vtc=0 siempre dividir una línea antes de un token de cierre (por defecto),
-vtc=1 no dividir antes de un token de cierre que esté seguido
       por un punto y coma o por otro token de cierre, y que no esté
       en un entorno de lista.
-vtc=2 nunca dividir antes de un token de cierre.
-vtc=3 Similar a -vtc=1, excepto que siempre se divide antes de un token de cierre
       si el token de apertura correspondiente sigue a un = o =>.

    Las reglas para -vtc=1 y -vtc=3 están diseñadas para mantener un equilibrio razonable entre estanqueidad y legibilidad en listas complejas.

  • Se pueden aplicar diferentes controles a cada tipo de token, y también es posible controlar las llaves de bloque; ver más abajo.
  • Finalmente, ten en cuenta que estos flags de estanqueidad vertical son simples indicaciones para el formateador, y no siempre puede seguirlas. Las cosas que lo hacen difícil o imposible incluyen comentarios, líneas en blanco, bloques de código dentro de una lista y posiblemente la falta del parámetro --line-up-parentheses. Además, estos flags pueden ser ignorados para listas muy pequeñas (2 o 3 líneas de longitud).

Aquí hay algunos ejemplos:

# perltidy -lp -vt=0 -vtc=0
%romanNumerals = (
                   one   => 'I',
                   two   => 'II',
                   three => 'III',
                   four  => 'IV',
);
# perltidy -lp -vt=1 -vtc=0
%romanNumerals = ( one   => 'I',
                   two   => 'II',
                   three => 'III',
                   four  => 'IV',
);
# perltidy -lp -vt=1 -vtc=1
%romanNumerals = ( one   => 'I',
                   two   => 'II',
                   three => 'III',
                   four  => 'IV', );
# perltidy -vtc=3
my_function(
    one   => 'I',
    two   => 'II',
    three => 'III',
    four  => 'IV', );
# perltidy -vtc=3
%romanNumerals = (
    one   => 'I',
    two   => 'II',
    three => 'III',
    four  => 'IV',
);

En el último ejemplo para -vtc=3, el paréntesis de apertura está precedido por un igual, por lo que el paréntesis de cierre se coloca en una nueva línea.

La diferencia entre -vt=1 y -vt=2 se muestra aquí:

# perltidy -lp -vt=1
$init->add(
            mysprintf( "(void)find_threadsv(%s);",
                       cstring( $threadsv_names[ $op->targ ] )
            )
);
# perltidy -lp -vt=2
$init->add( mysprintf( "(void)find_threadsv(%s);",
                       cstring( $threadsv_names[ $op->targ ] )
            )
);

Con -vt=1, la línea que termina en "add(" no se combina con la siguiente línea porque la siguiente línea no está equilibrada. Esto puede ayudar a la legibilidad, pero -vt=2 se puede usar para ignorar esta regla.

El código más compacto y menos legible se produce con "-vt=2" y "-vtc=2":

# perltidy -lp -vt=2 -vtc=2
$init->add( mysprintf( "(void)find_threadsv(%s);",
                       cstring( $threadsv_names[ $op->targ ] ) ) );

Observa cómo el código en todos estos ejemplos colapsa verticalmente a medida que aumenta -vt, pero la indentación permanece sin cambios. Esto se debe a que perltidy implementa el parámetro -vt formateando primero como si fuera -vt=0, y luego simplemente sobrescribiendo una línea de salida sobre la siguiente, si es posible, para lograr la estanqueidad vertical deseada. El estilo de indentación -lp (--line-up-parentheses) ha sido diseñado para permitir este colapso vertical, razón por la cual es requerido para el parámetro -vt.

Los parámetros -vt=n y -vtc=n se aplican a cada tipo de token de contenedor. Si se desea, se pueden aplicar controles de estanqueidad vertical de forma independiente a cada uno de los tipos de token de cierre de contenedor.

Los parámetros para controlar los paréntesis son -pvt=n o --paren-vertical-tightness=n, y -pvtc=n o --paren-vertical-tightness-closing=n.

Asimismo, los parámetros para los corchetes son -sbvt=n o --square-bracket-vertical-tightness=n, y -sbvtc=n o --square-bracket-vertical-tightness-closing=n.

Finalmente, los parámetros para controlar las llaves que no son de bloque de código son -bvt=n o --brace-vertical-tightness=n, y -bvtc=n o --brace-vertical-tightness-closing=n.

De hecho, el parámetro -vt=n es en realidad solo una abreviatura de -pvt=n -bvt=n sbvt=n, y de manera similar -vtc=n es una abreviatura de -pvtc=n -bvtc=n -sbvtc=n.

-bbvt=n o --block-brace-vertical-tightness=n
<

OPTIONS

-bbvt=n, --block-brace-vertical-tightness=n
The -bbvt=n flag is just like the -vt=n flag but applies to opening code block braces. 
-bbvt=0 break after opening block brace (default).
-bbvt=1 do not break unless this would produce more than one
        step in indentation in a line.
-bbvt=2 do not break after opening block brace.

It is necessary to also use either -bl or -bli for this to work, because, as with other vertical tightness controls, it is implemented by simply overwriting a line ending with an opening block brace with the subsequent line. For example:

# perltidy -bli -bbvt=0
if ( open( FILE, "< $File" ) )
  {
    while ( $File = <FILE> )
      {
        $In .= $File;
        $count++;
      }
    close(FILE);
  }
# perltidy -bli -bbvt=1
if ( open( FILE, "< $File" ) )
  { while ( $File = <FILE> )
      { $In .= $File;
        $count++;
      }
    close(FILE);
  }

By default this applies to blocks associated with keywords if, elsif, else, unless, for, foreach, sub, while, until, and also with a preceding label. This can be changed with the parameter -bbvtl=string, or --block-brace-vertical-tightness-list=string, where string is a space-separated list of block types. For more information on the possible values of this string, see "Specifying Block Types"

For example, if we want to just apply this style to "if", "elsif", and "else" blocks, we could use "perltidy -bli -bbvt=1 -bbvtl='if elsif else'".

There is no vertical tightness control for closing block braces; with one exception they will be placed on separate lines. The exception is that a cascade of closing block braces may be stacked on a single line. See --stack-closing-block-brace.

-sot, --stack-opening-tokens and related flags
The -sot flag tells perltidy to "stack" opening tokens when possible to avoid lines with isolated opening tokens.

For example:

# default
$opt_c = Text::CSV_XS->new(
    {
        binary       => 1,
        sep_char     => $opt_c,
        always_quote => 1,
    }
);
# -sot
$opt_c = Text::CSV_XS->new( {
        binary       => 1,
        sep_char     => $opt_c,
        always_quote => 1,
    }
);

For detailed control of individual closing tokens the following controls can be used:

-sop  or --stack-opening-paren
-sohb or --stack-opening-hash-brace
-sosb or --stack-opening-square-bracket
-sobb or --stack-opening-block-brace

The flag -sot is an abbreviation for -sop -sohb -sosb.

The flag -sobb is an abbreviation for -bbvt=2 -bbvtl='*'. This will case a cascade of opening block braces to appear on a single line, although this an uncommon occurrence except in test scripts.

-sct, --stack-closing-tokens and related flags
The -sct flag tells perltidy to "stack" closing tokens when possible to avoid lines with isolated closing tokens.

For example:

# default
$opt_c = Text::CSV_XS->new(
    {
        binary       => 1,
        sep_char     => $opt_c,
        always_quote => 1,
    }
);
# -sct
$opt_c = Text::CSV_XS->new(
    {
        binary       => 1,
        sep_char     => $opt_c,
        always_quote => 1,
    } );

The -sct flag is somewhat similar to the -vtc (--vertical-tightness-closing flags, and in some cases it can give a similar result. The difference is that the -vtc flags try to avoid lines with leading opening tokens by "hiding" them at the end of a previous line, whereas the -sct flag merely tries to reduce the number of lines with isolated closing tokens by stacking them but does not try to hide them. For example:

# -vtc=2
$opt_c = Text::CSV_XS->new(
    {
        binary       => 1,
        sep_char     => $opt_c,
        always_quote => 1, } );

For detailed control of the stacking of individual closing tokens the following controls can be used:

-scp  or --stack-closing-paren
-schb or --stack-closing-hash-brace
-scsb or --stack-closing-square-bracket
-scbb or --stack-closing-block-brace

The flag -sct is an abbreviation for stacking the non-block closing tokens, -scp -schb -scsb.

Stacking of closing block braces, -scbb, causes a cascade of isolated closing block braces to be combined into a single line as in the following example:

# -scbb:
for $w1 (@w1) {
    for $w2 (@w2) {
        for $w3 (@w3) {
            for $w4 (@w4) {
                push( @lines, "$w1 $w2 $w3 $w4\n" );
            } } } }

To simplify input even further for the case in which both opening and closing non-block containers are stacked, the flag -sac or --stack-all-containers is an abbreviation for --stack-opening-tokens --stack-closing-tokens.

Please note that if both opening and closing tokens are to be stacked, then the newer flag --weld-nested-containers may be preferable because it insures that stacking is always done symmetrically. It also removes an extra level of unnecessary indentation within welded containers. It is able to do this because it works on formatting globally rather than locally, as the --stack-opening-tokens and --stack-closing-tokens flags do.

Breaking Before or After Operators

Four command line parameters provide some control over whether a line break should be before or after specific token types. Two parameters give detailed control:

-wba=s or --want-break-after=s, and

-wbb=s or --want-break-before=s.

These parameters are each followed by a quoted string, s, containing a list of token types (separated only by spaces). No more than one of each of these parameters should be specified, because repeating a command-line parameter always overwrites the previous one before perltidy ever sees it.

By default, perltidy breaks after these token types:
% + - * / x != == >= <= =~ !~ < > | &
= **= += *= &= <<= &&= -= /= |= >>= ||= //= .= %= ^= x=

And perltidy breaks before these token types by default:
. << >> -> && || //

To illustrate, to cause a break after a concatenation operator, '.', rather than before it, the command line would be

-wba="."

As another example, the following command would cause a break before math operators '+', '-', '/', and '*':

-wbb="+ - / *"

These commands should work well for most of the token types that perltidy uses (use --dump-token-types for a list). Also try the -D flag on a short snippet of code and look at the .DEBUG file to see the tokenization. However, for a few token types there may be conflicts with hardwired logic which cause unexpected results. One example is curly braces, which should be controlled with the parameter --opening-brace-on-new-line provided for that purpose.

WARNING Be sure to put these tokens in quotes to avoid having them misinterpreted by your command shell.

Two additional parameters are available which, though they provide no further capability, can simplify input are:

-baao or --break-after-all-operators,

-bbao or --break-before-all-operators.

The -baao flag sets the default to be to break after all of the following operators:

% + - * / x != == >= <= =~ !~ < > | &
= **= += *= &= <<= &&= -= /= |= >>= ||= //= .= %= ^= x=
. : ? && || and or err xor

and the -bbao flag sets the default to break before all of these operators. These can be used to define an initial break preference which can be fine-tuned with the --want-break-after and --want-break-before flags. For example, to break before all operators except an = one could use "-bbao -wba='='" rather than listing every single perl operator except = on a -wbb flag.

-bal=n, --break-after-labels=n
This flag controls whether or not a line break occurs after a label. There are three possible values for n: 
-bal=0  break if there is a break in the input [DEFAULT]
-bal=1  always break after a label
-bal=2  never break after a label

For example,

# perltidy -bal=1
RETURN:
  return;
# perltidy -bal=2
RETURN: return;

Controlling List Formatting

Perltidy attempts to format lists of comma-separated values in tables which look good. Its default algorithms usually work well, but sometimes they don't. In this case, there are several methods available to control list formatting.

A very simple way to prevent perltidy from changing the line breaks within a comma-separated list of values is to insert a blank line, comment, or side-comment anywhere between the opening and closing parens (or braces or brackets). This causes perltidy to skip over its list formatting logic. (The reason is that any of these items put a constraint on line breaks, and perltidy needs complete control over line breaks within a container to adjust a list layout). For example, let us consider

my @list = (1,
            1, 1,
            1, 2, 1,
            1, 3, 3, 1,
            1, 4, 6, 4, 1,);

The default formatting, which allows a maximum line length of 80, will flatten this down to one line:

# perltidy (default)
my @list = ( 1, 1, 1, 1, 2, 1, 1, 3, 3, 1, 1, 4, 6, 4, 1, );

This formatting loses the nice structure. The original line breaks can be retained by adding comment or a blank line somewhere between the two parens. For example,

my @list = (
    1,    # a side comment forces the original breakpoints to be kept
    1, 1,
    1, 2, 1,
1, 3, 3, 1, 1, 4, 6, 4, 1, );

Podríamos lograr el mismo resultado con una línea en blanco o un comentario completo en cualquier lugar entre los paréntesis de apertura y cierre. La alineación vertical de los elementos de la lista aún ocurrirá si es posible. El método de la línea en blanco se muestra aquí:

my @list = (
    1,
    1, 1,
    1, 2, 1,
    1, 3, 3, 1,
    1, 4, 6, 4, 1,
);

Para otra posibilidad, consulte el indicador -fs en "Omitir secciones de código seleccionadas".

-boc, --break-at-old-comma-breakpoints
El indicador -boc es otra forma de evitar que las listas separadas por comas se reformateen. Usar -boc en el ejemplo anterior, junto con indicadores adicionales para conservar el estilo original, produce 
# perltidy -boc -lp -pt=2 -vt=1 -vtc=1
my @list = (1,
            1, 1,
            1, 2, 1,
            1, 3, 3, 1,
            1, 4, 6, 4, 1,);

Una desventaja de este indicador en comparación con los métodos discutidos anteriormente es que todas las tablas del archivo ya deben estar bien formateadas. El parámetro de la siguiente sección se puede usar para limitar las tablas a las que se aplica.

-boct=s, --break-at-old-comma-types=s
Este parámetro se puede usar para que el indicador -boc de la sección anterior se aplique solo a las comas en ciertos tipos de contenedores. La cadena de parámetro s es una lista separada por espacios de los tipos de contenedores. Puede incluir cualquiera de los tokens de contenedor de lista (, { y [. Además, un token de paréntesis puede ir precedido por cualquiera de las letras 'k', 'K', 'f', 'F', 'w' y 'W', para restringir aún más los tipos de paréntesis a los que se aplica -boc (consulte "Especificar tipos de paréntesis").

Por ejemplo:

-boct='(' significa mantener los saltos de coma antiguos en las listas de paréntesis
-boct='f(' significa mantener los saltos de coma antiguos en las listas de llamadas a funciones

Las comas que no están contenidas dentro de uno de los tres tipos de contenedores de lista, como las de una llamada a función sin paréntesis, se pueden seleccionar con un carácter ';'. Y las selecciones múltiples deben separarse con espacios.

Por ejemplo, -boct='; (' significa mantener los saltos en las comas no contenidas y en las comas en los paréntesis.

Tenga en cuenta que este parámetro no tiene ningún efecto a menos que también se establezca -break-at-old-comma-breakpoints o -boc.

-btct=s, --break-at-trailing-comma-types=s
Una coma final es una coma opcional que sigue al último elemento de una lista. El -btct=s indica a perltidy que termine una línea en las comas finales seleccionadas. La cadena s selecciona las comas finales, de la siguiente manera: 
s=1 o '*' : cada coma final
s=m una coma final en una lista multilínea
s=b una coma final desnuda
s=0 ninguna

Por ejemplo, dada la siguiente entrada

$w->bind(
    '<Page_Down>' => xx,
);

El formato predeterminado la aplastaría en una sola línea. Pero el contenedor se puede mantener abierto con

# perltidy -btct='b'
$w->bind(
    '<Page_Down>' => xx,
);

Esto puede ser particularmente útil para llamadas a funciones cortas como esta, donde el formato predeterminado de perltidy no mantiene el contenedor abierto.

Las opciones s=m y s=1 se pueden usar para abrir contenedores con comas finales no desnudas. Por ejemplo, dada esta entrada

$w->bind( '<Page_Down>' => xx, );

podemos abrirla con

# perltidy -btct=1
$w->bind(
    '<Page_Down>' => xx,
);

Después, podríamos cambiar a -btct='b' ya que la coma final ahora está desnuda. Pero el parámetro -btct debe conservarse en este caso porque, de lo contrario, esta lista pequeña se aplastará la próxima vez que se formatee.

Esta lógica se puede restringir a tipos de contenedores específicos incluyendo un token de apertura antes de la letra en la tabla anterior. Por ejemplo

-btct='(b'

significa que esta operación solo se aplicará a comas finales desnudas dentro de paréntesis.

Para paréntesis, información adicional que se puede proporcionar es una letra alfanumérica que se utiliza para limitar aún más la selección dependiendo del tipo de token inmediatamente anterior al paréntesis de apertura. Las letras posibles son actualmente 'k', 'K', 'f', 'F', 'w' y 'W', con estos significados para hacer coincidir lo que precede a un paréntesis de apertura (consulte "Especificar tipos de paréntesis"):

'k' coincide si el token no en blanco anterior es una palabra clave de perl
    (como 'if', 'while'),
'K' coincide si 'k' no coincide: el token anterior no es una palabra clave
'f' coincide si el token anterior es una función (no una palabra clave)
'F' coincide si 'f' no coincide.
'w' coincide si coinciden 'k' o 'f'.
'W' coincide si 'w' no coincide.

Estos son los mismos códigos utilizados para --line-up-parentheses-inclusion-list. Por ejemplo,

-btct='f(b'

significa que las comas finales desnudas en las listas de llamadas a funciones en el flujo de entrada deben ir seguidas de saltos de línea en el flujo de salida formateado.

La sección "Agregar y eliminar comas" describe controles adicionales para trabajar con comas finales. Estos se pueden combinar con el parámetro -break-trailing-comma-types para un control adicional del formato de lista.

-bocp=s, --break-open-compact-parens=s
Cuando una lista contenida entre paréntesis es demasiado larga para mostrarse en una sola línea, pero lo suficientemente corta para mostrarse en dos líneas, la acción predeterminada es mostrarla de forma compacta en dos líneas. Si se requieren más de dos líneas, la acción predeterminada es colocar saltos de línea después del paréntesis de apertura y antes del paréntesis de cierre. Por ejemplo, la siguiente lista corta se muestra con el formato predeterminado: 
initialize_warn_variable_types( $wvt_in_args, $num_files,
    $line_range_clipped );

El parámetro -bocp=s se puede utilizar para que listas cortas como esta se abran de la misma manera que las listas más largas. El parámetro s es una sola letra que indica los tipos de paréntesis a los que se aplica. Esta letra puede ser una de las siguientes (consulte "Especificar tipos de paréntesis"):

'1' o '*' coincide con todos los paréntesis
'k' coincide si el token no en blanco anterior es una palabra clave de perl
    (como 'my', 'return'),
'K' coincide si 'k' no coincide: el token anterior no es una palabra clave
'f' coincide si el token anterior es una función (no una palabra clave)
'F' coincide si 'f' no coincide.
'w' coincide si coinciden 'k' o 'f'.
'W' coincide si 'w' no coincide.
'0' desactiva este parámetro [PREDETERMINADO]

En este caso, los más útiles son f (función), k (palabra clave) y w (ambos).

Así, para ilustrar:

# perltidy -bocp='f'
initialize_warn_variable_types(
    $wvt_in_args, $num_files, $line_range_clipped
);
-mft=s, --maximum-fields-per-table=s
Perltidy utilizará reglas de formato especiales para listas que son relativamente pequeñas, irregulares o asociadas con ciertas palabras clave como "sprintf". En otras palabras, para datos que pueden no mostrarse bien como una tabla. Para otras listas, creará una tabla con un cierto número de campos n que se calcula para ajustarse al ancho de página y a los datos. Este número n se puede controlar con este parámetro de entrada.

Si s es un número positivo n, y el número calculado de campos para una tabla excede n, se reducirá a n. Este parámetro podría usarse, por ejemplo, en una pequeña sección de código para forzar que una lista tenga un número particular de campos por línea, y luego se podría usar el indicador -boc para conservar este formato, o se podría introducir una línea en blanco o un comentario en algún lugar para congelar el formato en aplicaciones futuras de perltidy. Por ejemplo,

# perltidy -mft=2
@month_of_year = (
    'Jan', 'Feb',
    'Mar', 'Apr',
    'May', 'Jun',
    'Jul', 'Aug',
    'Sep', 'Oct',
    'Nov', 'Dec'
);

El valor predeterminado es n=0, que no impone un límite al número de campos en una tabla.

A partir de la versión 20250311.05 de perltidy, un parámetro de entrada opcional más general permite seleccionar algunas de las tablas a las que se aplica esta opción. El entero n puede ir precedido por uno de los tipos de contenedor "(", "[" o "{" para seleccionar solo ese tipo de contenedor. Se pueden asignar diferentes valores numéricos a diferentes tipos de contenedores. Por ejemplo, la entrada

-mft='(1 [2'

significaría usar 1 campo para tablas dentro de paréntesis, 2 campos para tablas dentro de corchetes y no controlar los campos dentro de llaves.

Además, los paréntesis pueden ir precedidos por una de las letras de control de paréntesis "k f w K F W" para limitar aún más las tablas para las que se controlará el número de campos (consulte la tabla anterior o "Especificar tipos de paréntesis"). Un uso para esto sería hacer coincidir el control del número de campos de una tabla con el parámetro --break-open-compact-parens descrito anteriormente. Por lo tanto, la combinación

-bocp='f' -mft='f(1'

dice que las listas de paréntesis que siguen a las llamadas a funciones se abrirán, y estas mismas listas tendrán 1 campo por línea cuando se formateen como una tabla.

-cab=n, --comma-arrow-breakpoints=n
Una coma que sigue a una flecha de coma, '=>', recibe una consideración especial. En una lista larga, es común dividir en todas esas comas. Este parámetro se puede utilizar para controlar cómo perltidy divide en estas comas. (Sin embargo, no tendrá efecto si se fuerzan saltos de coma antiguos porque se usa -boc). Los valores posibles de n son: 
n=0 dividir en todas las comas después de =>
n=1 estable: dividir en todas las comas después de => si el contenedor está abierto,
    EXCEPTO los contenedores de una sola línea
n=2 dividir en todas las comas después de =>, PERO intentar formar la máxima
    longitud de contenedor de una sola línea
n=3 no tratar las comas después de => de forma especial en absoluto
n=4 dividir todo: como n=0 pero TAMBIÉN dividir un contenedor corto con
    un => no seguido de una coma cuando se usa -vt=0
n=5 estable: como n=1 pero TAMBIÉN dividir en contenedores abiertos de una sola línea cuando
    se usa -vt=0 (predeterminado)

Por ejemplo, dada la siguiente línea única, perltidy por defecto no agregará ningún salto de línea porque rompería el contenedor de una sola línea existente:

bless { B => $B, Root => $Root } => $package;

Esta línea se formatearía como:

bless { B => $B, Root => $Root } => $package;

Pero si se agrega un indicador para permitir un salto de línea, como

# perltidy -cab=1
bless {
    B => $B,
    Root => $Root,
} => $package;

La opción -cab=0 o -cab=4 también dividiría en la coma después de $Root porque eso permitiría una línea adicional para esa coma. Solo se utiliza la coma después de => para forzar el salto de línea.

El parámetro -cab=1 se considera "estable" porque solo aplicará saltos de línea a las listas que ya están abiertas. Si el código está en una sola línea, no lo romperá. Esto puede ser útil para evitar la necesidad de un comentario de supresión de perltidy. Sin embargo, la mayoría de las veces, es posible que desee romper todas las listas que contienen una flecha de coma. En esos casos, use -cab=0. O si desea que incluso las listas cortas se rompan, use -cab=4.

Control de Comas

-cab, --comma-after-branch
Este parámetro controla dónde se realizan las rupturas de línea en el interior de las listas o los contenedores. Los valores posibles son:
-cab=0
Forzará una ruptura después de cada elemento con flecha de coma.

Usar -cab=0 forzará una ruptura después de cada elemento con flecha de coma:

# perltidy -cab=0:
bless {
    B    => $B,
    Root => $Root
} => $package;

Si posteriormente se ejecuta perltidy con este contenedor roto, entonces por defecto se romperá después de cada '=>' porque el contenedor está ahora roto. Para reformar un contenedor de una sola línea, se podría usar el parámetro -cab=2.

El flag -cab=3 se puede usar para evitar que estas comas sean tratadas de forma especial. En este caso, un elemento como "01" => 31 se trata como un solo elemento en una tabla. El número de campos en esta tabla se determinará por las mismas reglas que se usan para cualquier otra tabla. Aquí hay un ejemplo.

# perltidy -cab=3
my %last_day = (
    "01" => 31, "02" => 29, "03" => 31, "04" => 30,
    "05" => 31, "06" => 30, "07" => 31, "08" => 31,
    "09" => 30, "10" => 31, "11" => 30, "12" => 31
);
-qwaf, --qw-as-function
Esta opción indica a perltidy que formatee una lista qw delimitada por paréntesis como si fuera una llamada a función cuyos argumentos son una lista de elementos entre comillas. Normalmente, una lista qw se imprime tal cual, excepto por un ajuste del espacio en blanco inicial para indicar el nivel de indentación. Por ejemplo, aquí hay un ejemplo del formato por defecto de una lista qw mal formateada:
# perltidy
@fields = qw( $st_dev     $st_ino    $st_mode $st_nlink   $st_uid
  $st_gid $st_rdev    $st_size $st_atime   $st_mtime  $st_ctime
  $st_blksize $st_blocks);

Si formateamos con -qwaf, el resultado será:

# perltidy -qwaf
@fields = qw(
    $st_dev   $st_ino   $st_mode  $st_nlink
    $st_uid   $st_gid   $st_rdev  $st_size
    $atime $st_mtime $st_ctime $st_blksize
    $st_blocks
);

La forma en que esto funciona es que justo antes de que comience el formato, los tokens del texto qw son reemplazados por los tokens de una llamada a función equivalente con una lista de elementos entre comillas separados por comas como argumentos de llamada. Luego se formatea como cualquier otra lista. Se emplean tokens de coma especiales que no tienen texto visible, por lo que cuando el código se muestra finalmente, sigue siendo una cita qw válida.

Algunas cosas a tener en cuenta son:

  • Esto solo funciona para citas qw que comienzan con qw(, sin espacio antes del paréntesis.
  • Si se emplea la opción --space-function-paren, se ignora para estas llamadas a función especiales porque las desactivaría.
  • De lo contrario, los diversos flags de control de formato operan sobre estas listas de la misma manera que para otras listas separadas por comas. En particular, tenga en cuenta que si se establece --break-at-old-comma-breakpoints, o -boc, se conservarán las antiguas ubicaciones de salto de línea. Y se conservarán los saltos de línea antiguos si hay alguna línea en blanco entre los paréntesis de apertura y cierre.
  • Antes de usar esta opción por primera vez, es una buena idea escanear el código y decidir si alguna lista tiene un orden especial que deba conservarse. Esto se puede lograr, por ejemplo, cambiando los delimitadores de cita a algo distinto de paréntesis, o insertando una línea en blanco como se discutió al principio de esta sección.

Añadir y Eliminar Comas

-drc, --delete-repeated-commas
Esta opción hace que se eliminen las comas repetidas. Por ejemplo, dada esta lista con una coma repetida 
ignoreSpec( $file, "file",, \%spec, \%Rspec );

podemos eliminarla con -drc

# perltidy -drc:
ignoreSpec( $file, "file", \%spec, \%Rspec );

Este parámetro también elimina las flechas dobles, '=>'. La lista completa de acciones tomadas cuando se establece este flag son las siguientes:

  • Las comas repetidas como ',,' se eliminan con una advertencia.
  • Las flechas dobles repetidas como '=> =>' se eliminan con una advertencia.
  • La combinación '=>,' produce una advertencia pero no se cambia (probablemente es un error, pero solo su autor sabría cómo arreglarlo).
  • La combinación restante ',=>' (a veces llamada 'flecha guiñando') es ignorada por este parámetro.
  • Estas advertencias solo se emiten si se establece el flag --warning-output, o -w.

Esta opción está activada por defecto. Use -ndrc para desactivarla.

Añadir y Eliminar Comas Finales
Una coma final es una coma que sigue al último elemento de una lista. Perl permite comas finales pero no son obligatorias. Incluirlas a veces puede simplificar el mantenimiento de listas grandes o complejas, y ayudar a mostrar la estructura. Pero pueden no ser apropiadas en todas las listas, por ejemplo en una lista que siempre tiene solo un término. Por defecto, perltidy no añade ni elimina comas finales, pero es posible manipularlas con el siguiente conjunto de parámetros relacionados:
  • --want-trailing-commas=s, -wtc=s - define dónde se desean comas finales (el estilo)
  • --add-trailing-commas, -atc - da permiso para añadir comas finales para que coincidan con el estilo deseado
  • --delete-trailing-commas, -dtc - da permiso para eliminar comas finales que no coinciden con el estilo deseado

El parámetro --want-trailing-commas=s, o -wtc=s, define un estilo preferido. La cadena s indica qué listas deben tener comas finales, como sigue:

s=1 or '*' : cada lista
s=m una lista multilínea
s=b una lista multilínea, coma final desnuda
s=i una lista multilínea, coma final desnuda, aproximadamente una coma por línea
s=h una lista multilínea, coma final desnuda, aproximadamente un par clave=>valor por línea
s=0 : ninguna lista
s=' ' o no definido : deja las comas finales sin cambios [POR DEFECTO]

donde:

  • Una lista aquí se toma básicamente como un contenedor de elementos (paréntesis, corchetes o llaves), que no es un bloque de código, que contiene una o más comas o flechas. Estos parámetros solo se aplican a algo que se ajusta a esta definición de lista.

    Una lista de parámetros sin paréntesis no es una lista según esta definición, por lo que estos parámetros no se aplican a una lista sin paréntesis.

  • Una lista multilínea es una lista para la cual los corchetes de apertura y cierre están en líneas diferentes.
  • Una coma final desnuda es una coma que está al final de una línea. Es decir, el token de contenedor de cierre sigue en una línea diferente. Por lo tanto, una lista con una coma final desnuda es un caso especial de una lista multilínea.
  • De hecho, las opciones anteriores para comas finales se pueden ver como una jerarquía de conjuntos anidados que se pueden expresar como 
    1 > m > b > i > h > 0

    Esto indica que las comas finales multilínea m son un subconjunto de todas las comas finales, y las comas finales desnudas b son un subconjunto de todas las comas finales multilínea, y así sucesivamente.

Este parámetro por sí solo solo indica dónde se desean las comas finales. Perltidy solo añade estas comas finales si se otorga permiso estableciendo el flag --add-trailing-commas, o -atc. Y perltidy solo elimina las comas finales no deseadas si se establece el flag --delete-trailing-commas, o -dtc.

Aquí hay algunas combinaciones de parámetros de ejemplo y sus significados

-wtc=0 -dtc : elimina todas las comas finales
-wtc=1 -atc : añade comas finales a todas las listas
-wtc=m -atc : añade comas finales a todas las listas multilínea
                (las listas de una sola línea permanecen sin cambios)
-wtc=b -atc : añade comas para que todas las listas cuyo corchete de
                cierre comienza una nueva línea tengan comas finales
-wtc=b -dtc : todas las comas finales que no son desnudas
                (no seguidas por una nueva línea) se eliminan.
-wtc=b -atc -dtc : hace ambas operaciones anteriores para que
                    todas las comas finales sean desnudas

Por ejemplo, dada la siguiente entrada

$wine_list = $top->Box(
    "-length" => 5,
    "-width"  => 3
)->select( "red", "white", "gold", );

tenemos

# perltidy -wtc=b -atc -dtc
$wine_list = $top->Box(
    "-length" => 5,
    "-width"  => 3,
)->select( "red", "white", "gold" );

Se añadió una coma después del 3, ya que es desnuda, y se eliminó una coma después de "gold", ya que no es desnuda.

Es posible aplicar un estilo diferente a cada tipo de token de contenedor incluyendo un token de apertura delante del carácter de estilo en la tabla anterior. Por ejemplo

-wtc='(m [b'

significa que las listas dentro de paréntesis deben tener comas finales multilínea, y que las listas dentro de corchetes tienen comas finales desnudas. Dado que no hay especificación para llaves en este ejemplo, sus comas finales permanecerían sin cambios.

Para los paréntesis, un elemento adicional de información que se puede dar es una letra alfanumérica que se utiliza para limitar aún más la selección dependiendo del tipo de token que precede inmediatamente al paréntesis de apertura. Las letras posibles son actualmente 'k', 'K', 'f', 'F', 'w', y 'W', con estos significados para coincidir con lo que precede a un paréntesis de apertura (ver "Especificación de Tipos de Paréntesis"):

'k' coincide si el token no vacío anterior es una palabra clave de perl
    (como 'if', 'while'),
'K' coincide si 'k' no: el token anterior no es una palabra clave
'f' coincide si el token anterior es una función (no una palabra clave)
'F' coincide si 'f' no.
'w' coincide si coinciden 'k' o 'f'.
'W' coincide si 'w' no.

Estos son los mismos códigos que se utilizan para --line-up-parentheses-inclusion-list. Por ejemplo,

-wtc='w(m'

significa que se desean comas finales para listas entre paréntesis multilínea que siguen a una llamada a función o palabra clave.

Finalmente, se puede colocar un + inicial en cualquier término para indicar que solo se aplica al añadir comas. Un - inicial indica que solo se aplica al eliminar comas. Por ejemplo,

-wtc='+h -b' -atc -dtc

significa que se deben añadir las comas finales que faltan a las listas de pares clave => valor, y se deben eliminar las comas finales que no son desnudas. No se realizan otros cambios. Cuando se usan términos más y menos de esta manera, no deben entrar en conflicto. No hay conflicto en este ejemplo porque las ubicaciones de las comas finales de los pares clave=>valor seleccionados

por el término +h son un subconjunto de todas las comas finales desnudas, y por lo tanto no serán eliminadas por el término -b. La regla general es que la letra del término positivo debe ocurrir después de la letra del término negativo en el orden de anidamiento jerárquico, 1 > m > b > i > h > 0.

Algunos puntos a tener en cuenta con respecto a la adición y eliminación de comas finales:

  • Se recomienda utilizar también el parámetro --converge al agregar y/o eliminar comas finales, especialmente si el formateador puede estar realizando otros cambios de salto de línea al mismo tiempo. La razón es que la decisión sobre si una lista es multilínea o desnuda se basa en el flujo de entrada si solo se realiza una iteración, que es la predeterminada.

    Cuando se solicitan iteraciones con el parámetro --converge, todas las operaciones de eliminación de comas se posponen hasta el inicio de la segunda iteración, después de que se hayan realizado la mayoría de los cambios en los saltos de línea.

    Para ilustrar, si comenzamos con

    f(
    a => 1,
    b => 2, );

    y intentamos eliminar comas no desnudas,

    # perltidy -wtc=b -dtc
f(
    a => 1,
    b => 2
);

    eliminamos una coma que se ha vuelto desnuda, lo cual no es lo deseado. Esto sucedió porque el cambio se basó en los saltos de línea iniciales en lugar de los finales. Ejecutar con --converge da el resultado deseado:

    # perltidy -wtc=b -dtc --converge
f(
    a => 1,
    b => 2,
);

    porque los cambios de coma se basan en los saltos de línea después de la primera iteración.

    Un parámetro --delay-trailing-comma-operations, o -dtco, está disponible para controlar este comportamiento si se desea. Negar este parámetro, con -ndtco, le dice a perltidy que siempre use el estado de inicio para tomar decisiones con respecto a la adición y eliminación de comas, incluso cuando se solicitan iteraciones. Esto normalmente no debería ser necesario.

  • Perltidy no agrega una coma final en algunos casos extremos que parecen estar cerca de un límite de estabilidad. Por lo tanto, si una coma no se agrega inesperadamente, esta es probablemente la razón.
  • Si el parámetro --break-at-trailing-comma-types, o -btct. también se emplea, opera sobre el estado después de cualquier adición o eliminación de comas. Y permitirá que se agreguen comas finales en la mayoría de los casos extremos. Por ejemplo, dado el siguiente texto de entrada 
    plot(
    'g', Canvas => $overview_canvas
);

    formatear con "-wtc=f(b) -atc" no agregará una coma final porque la lista se aplanará y la coma no permanecerá desnuda. Pero podemos agregar una coma final, y mantener el contenedor abierto, con

    # perltidy -wtc='f(b' -atc -btct='f(b'
plot(
    'g', Canvas => $overview_canvas,
);

    Como otro ejemplo, dada la misma línea de código en una sola línea sin una coma final

    plot( 'g', Canvas => $overview_canvas );

    podemos agregar una coma final y abrir el contenedor con

    # perltidy -wtc=1 -atc -btct=1
plot(
    'g', Canvas => $overview_canvas,
);

    Después de eso, podríamos usar "-btct='f(b'" para mantener el contenedor abierto.

  • Al utilizar estos parámetros por primera vez, es una buena idea practicar con algunos scripts de prueba y verificar que los resultados sean los esperados.

Consideraciones especiales para comas finales solitarias

Agregar o eliminar la única coma en una lista puede tener algunas implicaciones que deben explicarse y, posiblemente, controlarse. Hay dos controles adicionales disponibles para estas comas solitarias:

  • --add-lone-trailing-commas, -altc - da permiso para agregar una coma si será la única. Esto está activado por defecto y se explica a continuación.
  • --delete-lone-trailing-commas, -dltc - da permiso para eliminar la única coma en una lista. Esto está activado por defecto y se explica a continuación.

Un problema al eliminar una coma solitaria es que si se elimina, es posible que no se pueda volver a agregar automáticamente, ya que perltidy utiliza la existencia de comas para ayudar a localizar contenedores donde las comas son apropiadas. Por ejemplo, dado

my ( $self, ) = @_;

y si eliminamos la coma con

# perltidy -wtc=m -dtc
my ( $self ) = @_;

entonces no podemos usar los controles de coma final para agregar esta coma de nuevo. El parámetro --delete-lone-trailing-commas permite que dicha coma sea eliminada, y está activado por defecto, pero puede ser desactivado para prevenirlo. Esto podría ser útil si uno está experimentando con opciones de formato y quiere restringir las pruebas a operaciones que sean reversibles. Tenga en cuenta que este parámetro es un control de ajuste fino para --delete-trailing-commas que también debe estar configurado para que tenga algún efecto.

Sin embargo, si un solo elemento en una lista es en sí mismo una lista con múltiples líneas, como el elemento entre llaves aquí

$self->make_grammar(
    {
        iterator => $self->_iterator,
        parser   => $self,
    }
);

entonces perltidy puede agregar y/o eliminar una coma solitaria:

# perltidy -atc -wtc=b
$self->make_grammar(
    {
        iterator => $self->_iterator,
        parser   => $self,
    },
);

Pero resulta que estos casos generalmente coinciden con situaciones donde el parámetro --weld-nested-containers, o -wn, se aplicaría, y agregar tales comas puede bloquear la soldadura. Por ejemplo, el parámetro -wn funcionaría en el primer fragmento de los anteriores, pero fallaría en el segundo debido a la coma final agregada.

El parámetro --add-lone-trailing-commas, o -altc permite que estas comas se agreguen, siempre que --add-trailing-commas también esté configurado. Está activado por defecto. Los usuarios de -wn pueden querer desactivarlo con --noadd-lone-trailing-commas, -naltc para evitar que se agreguen dichas comas.

Si tales comas se agregan, entonces pueden eliminarse para permitir la soldadura con el control descrito en la siguiente sección.

-dwic, --delete-weld-interfering-commas
Si los tokens de cierre de dos contenedores anidados están separados por una coma, entonces la soldadura solicitada con --weld-nested-containers no puede ocurrir. Cualquier coma en esta situación son comas finales opcionales y pueden eliminarse con -dwic. Por ejemplo, una coma en este script impide la soldadura: 
# perltidy -wn
$self->make_grammar(
    {
        iterator => $self->_iterator,
        parser   => $self,
    },
);

Agregar -dwic elimina la coma y permite la soldadura:

# perltidy -wn -dwic
$self->make_grammar( {
    iterator => $self->_iterator,
    parser   => $self,
} );

Esta característica está desactivada por defecto. Aquí hay algunos puntos a tener en cuenta sobre el parámetro -dwic

  • Esta operación no siempre es reversible, así que por favor revise cuidadosamente los resultados de usar este parámetro.
  • Eliminar este tipo de coma final aislada es necesario para que la soldadura sea posible, pero no suficiente. Por lo tanto, la soldadura no siempre ocurrirá donde se eliminen estas comas.
  • Esta operación es independiente de --add-trailing-commas y --delete-trailing-commas. Si entra en conflicto con alguna de esas configuraciones, tiene prioridad.

Adición y Eliminación de Flechas Inter-corchetes

En la siguiente expresión, el operador flecha '->' entre los corchetes de cierre y apertura de las claves de hash y los índices de array son opcionales:

return $self->{'commandline'}->{'args'}->[0]->[0]->{'hgroups'};

Estos se llamarán flechas inter-corchetes aquí, por falta de un término mejor. Perltidy no los cambiará por defecto, pero se pueden agregar o eliminar con los siguientes parámetros.

-dia, --delete-interbracket-arrows
Este parámetro elimina las flechas inter-corchetes. Aplicado al ejemplo anterior, tenemos 
# perltidy -dia
return $self->{'commandline'}{'args'}[0][0]{'hgroups'};

Por defecto, esto se aplica a todas las flechas inter-corchetes, pero es posible la eliminación selectiva con los controles descritos a continuación.

-aia, --add-interbracket-arrows
Este parámetro agrega flechas inter-corchetes. Aplicado a la línea de código anterior, recuperamos la línea original. 
# perltidy -aia
return $self->{'commandline'}->{'args'}->[0]->[0]->{'hgroups'};

Los cambios selectivos se pueden realizar con los controles descritos a continuación.

-ias=s, --interbracket-arrow-style=s
Por defecto, los parámetros --add- y --delete- se aplican a todas las flechas inter-corchetes.

Se puede especificar un estilo opcional con esta cadena de parámetro s. En ese caso, los parámetros --add-interbracket-arrows y --delete-interbracket-arrows solo se aplican donde llevarían el formato a coincidir con el estilo especificado. Ambos pueden usarse en una sola ejecución si se especifica un estilo mixto, ya que no hay conflicto.

La cadena de estilo s proporciona una descripción gráfica del estilo deseado. Enumera hasta cuatro pares posibles de tipos de corchetes con una flecha opcional entre ellos. Por ejemplo:

-ias='][   }->{'

Esto significa que no se desean flechas entre '][' pero sí entre '}{'. Y significa que los pares no listados ']{' y '}[' permanecerán sin cambios, con o sin flechas.

En este ejemplo en particular, si se utiliza el parámetro --delete-interbracket-arrows, entonces solo se eliminarán las flechas como ']->[' , ya que son las únicas que no coinciden con el estilo.

Y de manera similar, si se utiliza --add-interbracket-arrows, entonces se insertarán flechas entre corchetes como '}{' para que el formato coincida con el estilo en este ejemplo.

Los espacios en la cadena s son opcionales. Se ignoran cuando se analiza la expresión.

El estilo correspondiente a todas las flechas posibles es

-ias=']->[ ]->{ }->[ }->{'

Para mayor comodidad, esto también se puede solicitar con -ias=1 o -ias='*'.

El estilo correspondiente a ninguna flecha inter-corchete es

-ias=']  [ ]  { }  [ }  {'

Bloques Else Faltantes

Una técnica de programación defensiva es requerir que cada cadena de if-elsif- termine con un bloque else, aunque no sea estrictamente necesario. Esto ayuda a asegurar que no haya lagunas en la lógica.

Por ejemplo, considere el siguiente fragmento:

my $type = get_cards();
if    ( $type = 1 ) { action("hold 'em") }
elsif ( $type = 2 ) { action("fold 'em") }
elsif ( $type = 3 ) { action("walk away") }

¿Qué pasa si la variable $type es algún otro valor? Podría haber sido obvio que esto estaba bien cuando el código se escribió por primera vez, pero podría no ser tan claro cuando se revisa el código unos años después. Un bloque else terminal con un comentario ayudaría a aclarar las cosas.

Los parámetros en esta sección pueden ayudar ya sea emitiendo una advertencia si falta un else, o incluso insertando un bloque else vacío donde falte uno, o ambos.

-wme, --warn-missing-else
Este indicador le dice a perltidy que emita una advertencia si un programa carece de un bloque else terminal. La acción predeterminada es no emitir dicha advertencia.
-ame, --add-missing-else
Este indicador le dice a perltidy que genere un bloque else vacío dondequiera que un programa carezca de un bloque else terminal. Para obtener una advertencia cuando se hace esto, también debe establecer -wme. La acción predeterminada es no agregar bloques else faltantes.
-amec=s, --add-missing-else-comment=s
Esta cadena es un comentario lateral que se escribirá para resaltar un nuevo bloque else vacío. La cadena predeterminada es: 
-amec='##FIXME - added with perltidy -ame'

Por ejemplo, en el ejemplo anterior podemos agregar un else faltante y también obtener un aviso de advertencia con:

# perltidy -ame -wme
my $type = get_cards();
if    ( $type == 1 ) { action("hold 'em") }
elsif ( $type == 2 ) { action("fold 'em") }
elsif ( $type == 3 ) { action("walk away") }
else {
    ##FIXME - added with perltidy -ame
}

Cualquier comentario ##FIXME creado de esta manera debe ser revisado y modificado apropiadamente. Por ejemplo, uno podría decidir que el código está bien como está, y simplemente cambiar el comentario para indicar que no se ha pasado nada por alto:

my $type = get_cards();
if    ( $type == 1 ) { action("hold 'em") }
elsif ( $type == 2 ) { action("fold 'em") }
elsif ( $type == 3 ) { action("walk away") }
else {
    # ok - no worries
}

O tal vez un análisis más profundo revela que algo se pasó por alto:

my $type = get_cards();
if    ( $type == 1 ) { action("hold 'em") }
elsif ( $type == 2 ) { action("fold 'em") }
elsif ( $type == 3 ) { action("walk away") }
else                 { action("run") }

A veces resulta que el bloque else no debería ser alcanzable, en cuyo caso una salida de error podría ser apropiada. En cualquier caso, tener el bloque else puede mejorar la mantenibilidad del código.

Control de Saltos en Ciertos Operadores de Cadena

Para una sentencia que consiste en una cadena de ciertos operadores binarios, la lógica de salto de línea predeterminada es: (1) si una sentencia cabe en una línea, entonces se formatea como una sola línea, o (2) si la sentencia requiere múltiples líneas, entonces se hace un salto en todos los operadores de cadena. Se aplican reglas adicionales, pero esta es la básica.

El parámetro --pack-operator-types=s, o -pot=s, se puede usar para cambiar esto para ciertos operadores que pueden ser especificados con la cadena s. Estos son el operador de concatenación s='.' y la flecha de llamada de método s='->'. Cuando este parámetro se selecciona para un operador, no se realizan saltos especiales, por lo que habrá un número mínimo de saltos de línea. Por ejemplo, aquí está el formateo predeterminado para una cadena de llamadas a métodos:

# perltidy -l=60
Data::Dumper->new( [ \%errors ] )
  ->Indent(2)
  ->Terse(1)
  ->Sortkeys(1)
  ->Dump;

y este es el formateo alternativo con este parámetro:

# perltidy -l=60 -pot='->'
Data::Dumper->new( [ \%errors ] )->Indent(2)->Terse(1)
  ->Sortkeys(1)->Dump;

Tenga en cuenta que esta opción solo se aplica a las flechas que siguen a un paréntesis de cierre.

Conservar o Ignorar Saltos de Línea Existentes

Varios parámetros adicionales están disponibles para controlar la medida en que los saltos de línea en el script de entrada influyen en el script de salida. En la mayoría de los casos, los valores predeterminados de los parámetros se establecen de modo que, si es posible una elección, el estilo de salida siga el estilo de entrada. Por ejemplo, si un contenedor corto se rompe en el script de entrada, entonces el comportamiento predeterminado es que permanezca roto en el script de salida.

La mayoría de los parámetros en esta sección solo serían necesarios para una conversión única de un script de longitudes de contenedor cortas a longitudes de contenedor más largas. El efecto opuesto, de convertir longitudes de contenedor largas a longitudes más cortas, se puede obtener utilizando temporalmente una longitud de línea máxima corta.

-bol, --break-at-old-logical-breakpoints
Por defecto, si una expresión lógica se rompe en un "&&", "||", "and", o "or", entonces el contenedor permanecerá roto. Además, los saltos en las palabras clave internas "if" y "unless" normalmente se conservarán. Para evitar esto, y así formar líneas más largas, use -nbol.

Tenga en cuenta que este indicador no duplica los puntos de ruptura lógicos antiguos. Simplemente se utilizan como una pista con este indicador de que una sentencia debe permanecer rota. Sin este indicador, perltidy normalmente intentará combinar expresiones relativamente cortas en una sola línea.

Por ejemplo, dada esta fragmento:

return unless $cmd = $cmd || ($dot
    && $Last) || &prompt('|');
# perltidy -bol [por defecto]
return
  unless $cmd = $cmd
  || ( $dot
    && $Last )
  || &prompt('|');
# perltidy -nbol
return unless $cmd = $cmd || ( $dot && $Last ) || &prompt('|');
-bom, --break-at-old-method-breakpoints
Por defecto, una flecha de llamada de método "->" se considera un candidato para un punto de interrupción, pero las cadenas de métodos se llenarán hasta el ancho de línea antes de considerar un punto de interrupción. Con -bom, se conservan los saltos antes de la flecha, por lo que si ha preformateado una cadena de métodos: 
# perltidy -bom
$Document
  ->schild(0)
  ->schildren();

el indicador -bom **mantendrá** estos saltos de línea, en lugar de convertirse en esto:

# perltidy [POR DEFECTO]
$Document->schild(0)->schildren();

Este indicador también buscará y conservará un estilo de llamadas 'apretadas', en las que las líneas comienzan con un paréntesis de cierre seguido de una flecha de llamada, como en este ejemplo:

# perltidy -bom
my $q = $rs->related_resultset(
    'CDs'
)->related_resultset(
    'Tracks'
)->search(
    {
        'track.id' => { -ident => 'none_search.id' },
    }
)->as_query;
-bos, --break-at-old-semicolon-breakpoints
Los puntos y comas normalmente se colocan al final de una sentencia. Esto significa que las líneas formateadas normalmente no comienzan con puntos y comas. Si el flujo de entrada tiene algunas líneas que comienzan con puntos y comas, estas pueden conservarse estableciendo este indicador. Por ejemplo, considere el siguiente fragmento de entrada de dos líneas: 
$z = sqrt($x**2 + $y**2)
;

El formateo predeterminado será:

$z = sqrt( $x**2 + $y**2 );

Usar el indicador -bos mantiene el punto y coma aislado:

# perltidy -bos
$z = sqrt( $x**2 + $y**2 )

Nota sobre el uso de las opciones -blao y -blbc.
Estos controles de líneas en blanco introducen un cierto número mínimo de líneas en blanco en el texto, pero el número final de líneas en blanco puede ser mayor, dependiendo de los valores de otros controles de líneas en blanco y del número de líneas en blanco antiguas. Una consecuencia es que la introducción de líneas en blanco con estos y otros controles no se puede deshacer exactamente, por lo que se recomienda experimentar con estos controles antes de usarlos.

Si es necesario, es posible deshacer aproximadamente estos y otros controles de líneas en blanco con el parámetro --keep-old-blank-lines-exceptions=s descrito más abajo.

-mbl=n --maximum-consecutive-blank-lines=n
Este parámetro especifica el número máximo de líneas en blanco consecutivas que se generarán dentro de las secciones de código de un script. El valor predeterminado es n=1. Si el archivo de entrada tiene más de n líneas en blanco consecutivas, el número se reducirá a n, excepto como se mencionó anteriormente para los parámetros --blank-lines-before-subs y --blank-lines-before-subs. Si n=0, no se generarán líneas en blanco (a menos que se conserven todas las líneas en blanco antiguas con el indicador --keep-old-blank-lines=2 de la siguiente sección).

Este indicador obviamente no se aplica a las secciones de pod, here-documents y citas.

-kbl=n, --keep-old-blank-lines=n
El indicador -kbl=n le permite controlar cómo se tratan sus líneas en blanco existentes.

Los valores posibles de n son:

n=0 ignora todas las líneas en blanco antiguas
n=1 estable: conserva las líneas en blanco antiguas, pero limitado por el indicador B<-mbl=n>, pero
    elimina las líneas en blanco existentes que coinciden con el indicador B<--kblx=s> (ver más abajo)
n=2 conserva todas las líneas en blanco antiguas, independientemente del indicador B<-mbl=n>

El valor predeterminado y recomendado es n=1. Con esta opción, puede filtrar selectivamente líneas en blanco seleccionadas del flujo de entrada antes de que comience el formato utilizando el parámetro descrito en la siguiente sección.

El ajuste n=0 debe usarse con precaución, ya que eliminará todas las líneas en blanco, incluidas las que podrían ser esenciales para controlar la alineación vertical y para evitar comentarios laterales no deseados.

-kblx=s, --keep-old-blank-lines-exceptions=s
La mayoría de los controles de líneas en blanco descritos anteriormente especifican un número mínimo de líneas en blanco, en lugar de un máximo, por lo que no se pueden usar para eliminar líneas. Este parámetro permite eliminar líneas en blanco al ignorarlas selectivamente en el flujo de entrada. Funciona cuando --keep-old-blank-lines=1, que es el valor predeterminado como se describió anteriormente. La selección de líneas en blanco a excluir se realiza con una cadena con uno o más de los siguientes valores especiales: 
'b{' 'b}' '{b' '}b' 'bp' 'bs' 'bc' 'cb'

En estos símbolos, el carácter b indica la ubicación de las líneas en blanco con respecto al tipo de token siguiente o anterior. Los tipos de token { y } son llaves de apertura y cierre de bloques de código, el carácter p es una declaración de paquete, s es una definición de sub y c es un comentario de bloque.

Así, por ejemplo, bs significa que una o más líneas en blanco antes de un sub se ignorarán en el flujo de entrada. Tenga en cuenta que esto es aproximadamente lo opuesto al parámetro -blanks-before-subs descrito anteriormente.

De hecho, estos parámetros proporcionan inversos aproximados a todos los parámetros de líneas en blanco descritos anteriormente. Para simplificar, los tipos de bloque a los que se aplican los operadores "{" y "}" son los mismos que el operador correspondiente que agrega líneas en blanco, descrito anteriormente. La siguiente tabla muestra estas relaciones:

kblx=   Inverso  Aplica a tipos de bloque
b{      -bbb      if unless while until for foreach
b}      -blbc=i  -blbcl=s [predeterminado = sub]
{b      -blao=i  -blaol=s [predeterminado = sub]
}b      [ninguno]   -blaol=s
bp      -blbp=n
bs      -blbs=n
bc      -bbc
cb      [ninguno - comentarios antes de líneas en blanco]

Por lo tanto, por ejemplo, la tabla indica que para eliminar aproximadamente las líneas en blanco introducidas por una operación -blao, podríamos usar -kblx='{b'.

Algunas notas sobre el uso de este parámetro:

  • El string del parámetro puede contener múltiples operadores siempre que estén separados por espacios.
  • Los controles de eliminación de comentarios conservarán al menos una línea en blanco entre grupos de comentarios y entre un comentario lateral y un comentario de línea siguiente.
  • Estas operaciones ocurren en el flujo de entrada, antes de otras operaciones de líneas en blanco, por lo que pueden usarse en la misma ejecución que otros controles de líneas en blanco. Por lo tanto, puede suceder que estos controles eliminen líneas en blanco del flujo de entrada mientras que otros controles agregan líneas en blanco.
  • Estas operaciones normalmente solo serán necesarias ocasionalmente para corregir algunos problemas o deshacer una operación no deseada.
-sob, --swallow-optional-blank-lines
Esto es equivalente a --keep-old-blank-lines=0 y se incluye para compatibilidad con versiones anteriores.
-nsob, --noswallow-optional-blank-lines
Esto es equivalente a --keep-old-blank-lines=1 y se incluye para compatibilidad con versiones anteriores.

Controles para líneas en blanco alrededor de líneas de palabras clave consecutivas

Los parámetros en esta sección proporcionan cierto control sobre la colocación de líneas en blanco dentro y alrededor de grupos de sentencias que comienzan con palabras clave seleccionadas. Estas líneas en blanco se denominan aquí líneas en blanco de grupo de palabras clave, y todos los parámetros comienzan con --keyword-group-blanks*, o -kgb* de forma abreviada. Los valores predeterminados no emplean estos controles, pero se pueden habilitar con los siguientes parámetros:

-kgbl=s o --keyword-group-blanks-list=s; s es una cadena entre comillas de palabras clave

-kgbs=s o --keyword-group-blanks-size=s; s indica el número de palabras clave necesarias para formar un grupo.

-kgbb=n o --keyword-group-blanks-before=n; n = (0, 1 o 2) controla una línea en blanco inicial

-kgba=n o --keyword-group-blanks-after=n; n = (0, 1 o 2) controla una línea en blanco final

-kgbi o --keyword-group-blanks-inside es un interruptor para agregar líneas en blanco entre subgrupos

-kgbd o --keyword-group-blanks-delete es un interruptor para eliminar líneas en blanco iniciales entre palabras clave

-kgbr=n o --keyword-group-blanks-repeat-count=n puede limitar el número de veces que se aplica esta lógica

Además, las siguientes abreviaturas están disponibles para un uso simplificado:

-kgb o --keyword-group-blanks es abreviatura de -kgbb=2 -kgba=2 kgbi

-nkgb o --nokeyword-group-blanks, es abreviatura de -kgbb=1 -kgba=1 nkgbi

Antes de describir el significado de los parámetros en detalle, veamos un ejemplo que se formatea con los parámetros predeterminados. 

print "Entering test 2\n";
use Test;
use Encode qw(from_to encode decode
  encode_utf8 decode_utf8
  find_encoding is_utf8);
use charnames qw(greek);
my @encodings     = grep( /iso-?8859/, Encode::encodings() );
my @character_set = ( '0' .. '9', 'A' .. 'Z', 'a' .. 'z' );
my @source        = qw(ascii iso8859-1 cp1250);
my @destiny       = qw(cp1047 cp37 posix-bc);
my @ebcdic_sets   = qw(cp1047 cp37 posix-bc);
my $str           = join( '', map( chr($_), 0x20 .. 0x7E ) );
return unless ($str);

usando perltidy -kgb da:

print "Entering test 2\n";
                          <----------esta línea en blanco controlada por -kgbb
use Test;
use Encode qw(from_to encode decode
  encode_utf8 decode_utf8
  find_encoding is_utf8);
use charnames qw(greek);
                          <---------esta línea en blanco controlada por -kgbi
my @encodings     = grep( /iso-?8859/, Encode::encodings() );
my @character_set = ( '0' .. '9', 'A' .. 'Z', 'a' .. 'z' );
my @source        = qw(ascii iso8859-1 cp1250);
my @destiny       = qw(cp1047 cp37 posix-bc);
my @ebcdic_sets   = qw(cp1047 cp37 posix-bc);
my $str           = join( '', map( chr($_), 0x20 .. 0x7E ) );
                          <----------esta línea en blanco controlada por -kgba
return unless ($str);

Se han introducido líneas en blanco alrededor de las secuencias my y use. Lo que sucedió es que la lista de palabras clave predeterminada incluye my y use, pero no print y return. Por lo tanto, se encontró una secuencia continua de nueve declaraciones my y use. Este número excede el umbral predeterminado de cinco, por lo que se colocaron líneas en blanco antes y después de todo el grupo. Luego, dado que también hubo una sub-secuencia de seis líneas my, se introdujo una línea en blanco para separarlas.

Se puede lograr un control más fino de la colocación de líneas en blanco utilizando los parámetros individuales en lugar del indicador -kgb. Los controles individuales son los siguientes.

-kgbl=s o --keyword-group-blanks-list=s, donde s es una cadena entre comillas, define el conjunto de palabras clave que se formarán en grupos. La cadena es una lista de palabras clave separadas por espacios. El conjunto predeterminado es s="use require local our my", pero se puede usar cualquier lista de palabras clave. Las líneas de comentarios también pueden incluirse en un grupo de palabras clave, aunque no sean palabras clave. Para incluir comentarios de bloque ordinarios, incluya el símbolo BC. Para incluir comentarios de bloque estáticos

comentarios (que normalmente comienzan con '##'), incluyen el símbolo SBC.

-kgbs=s o --keyword-group-blanks-size=s, donde s es una cadena que describe el número de declaraciones de palabras clave consecutivas que forman un grupo (Nota: las declaraciones separadas por líneas en blanco en el archivo de entrada se consideran consecutivas a efectos de este recuento). Si s es un entero, entonces es el número mínimo requerido para un grupo. También se puede dar un valor máximo con el formato s=min.max, donde min es el número mínimo y max es el número máximo, y los valores min y max están separados por uno o más puntos. No se encontrarán grupos si el máximo es menor que el mínimo. El máximo es ilimitado si no se proporciona. El valor predeterminado es s=5. Algunos ejemplos:

s      min   max         número para grupo
3      3     ilimitado   3 o más
1.1    1     1           1
1..3   1     3           1 a 3
1.0    1     0           (sin coincidencias)

No hay un valor predeterminado realmente bueno para este parámetro. Si se establece demasiado bajo, se puede generar un número excesivo de líneas en blanco. Sin embargo, algunos usuarios pueden preferir reducir el valor un poco por debajo del predeterminado, quizás a s=3.

-kgbb=n o --keyword-group-blanks-before=n especifica si debe aparecer un espacio en blanco antes de la primera línea del grupo, como sigue:

n=0 => (eliminar) se eliminará una línea en blanco existente
n=1 => (estable) no se realiza ningún cambio en el archivo de entrada [PREDETERMINADO]
n=2 => (insertar) se introduce una línea en blanco si es posible

-kgba=n o --keyword-group-blanks-after=n especifica de manera similar si debe aparecer un espacio en blanco después de la última línea del grupo, utilizando el mismo esquema (0=eliminar, 1=estable, 2=insertar).

-kgbi o --keyword-group-blanks-inside controla la inserción de líneas en blanco entre la primera y la última declaración de todo el grupo. Si hay una secuencia continua de un solo tipo de declaración con más que el número umbral mínimo (según lo especificado con -kgbs=s), entonces este interruptor provoca que se inserte una línea en blanco entre este subgrupo y los demás. En el ejemplo anterior, esto sucedió entre las declaraciones use y my.

-kgbd o --keyword-group-blanks-delete controla la eliminación de cualquier línea en blanco que exista en el grupo cuando se escanea por primera vez. Cuando se escanean las declaraciones inicialmente, se incluyen en la colección las líneas en blanco existentes. Cualquier línea en blanco original de este tipo se eliminará antes de realizar cualquier otra inserción cuando se establezca el parámetro -kgbd. El valor predeterminado es no hacer esto, -nkgbd.

-kgbr=n o --keyword-group-blanks-repeat-count=n especifica n, el número máximo de veces que esta lógica se aplicará a cualquier archivo. El valor especial n=0 es lo mismo que n=infinito, lo que significa que se aplicará a todo el script [Predeterminado]. Un valor n=1 podría usarse para aplicarlo solo una vez, por ejemplo. Esto podría ser útil para ajustar solo las declaraciones use en la parte superior de un módulo, por ejemplo.

-kgb o --keyword-group-blanks es una abreviatura equivalente a establecer -kgbb=1 -kgba=1 -kgbi. Esto activa el formato de grupo de palabras clave con un conjunto de valores predeterminados.

-nkgb o --nokeyword-group-blanks es equivalente a -kgbb=0 -kgba nkgbi. Este indicador desactiva las líneas en blanco de grupo de palabras clave y es la configuración predeterminada.

Aquí hay algunas notas sobre el funcionamiento de esta técnica.

  • Estos parámetros son probablemente más útiles como parte de una operación importante de reformateo de código en lugar de una operación de formateo rutinaria.

    En particular, tenga en cuenta que eliminar líneas en blanco antiguas con -kgbd es una operación irreversible, por lo que debe aplicarse con cuidado. Las líneas en blanco existentes pueden estar desempeñando un papel importante en el control de la alineación vertical.

  • Los conflictos que surgen entre estos parámetros kgb* y otros controles de línea en blanco generalmente se resuelven produciendo el número máximo de líneas en blanco implícito por cualquier parámetro.

    Por ejemplo, si se establecen los indicadores --freeze-blank-lines o --keep-old-blank-lines=2, entonces tienen prioridad sobre cualquier eliminación de línea en blanco implícita por los indicadores -kgb de esta sección, por lo que no se eliminarán líneas en blanco.

    Para otro ejemplo, si un grupo de palabras clave termina en un sub y el indicador kgba=0 no solicita una línea en blanco allí, pero también tenemos --blank-lines-before-subs=2, entonces todavía se introducirán dos líneas en blanco antes del sub.

  • La introducción de líneas en blanco no se produce si entra en conflicto con otros controles de entrada o validez del código. Por ejemplo, no se colocará una línea en blanco dentro de un here-doc o dentro de una sección de código marcada con comentarios de omisión de formato. Y en general, solo se introducirá una línea en blanco al final de un grupo si la siguiente declaración es una línea de código.
  • El recuento que se utiliza para determinar el tamaño del grupo no es el número de líneas, sino el número total de palabras clave encontradas. Las declaraciones individuales con un cierto tipo de palabra clave principal pueden continuar en varias líneas, pero si alguna de estas líneas está anidada más de un nivel de profundidad, ese grupo terminará.
  • La búsqueda de grupos de líneas con palabras clave principales similares se basa en el código fuente de entrada, no en el código fuente final formateado. En consecuencia, si el código fuente está mal formateado, sería mejor hacer primero un pase de formato sin estas opciones.

Estilos

Un estilo se refiere a una colección conveniente de parámetros existentes.

-gnu, --gnu-style
-gnu proporciona una aproximación a los Estándares de Codificación GNU (que no se aplican a perl) tal como se implementan a veces. En la actualidad, este estilo anula el estilo predeterminado con los siguientes parámetros: 
-lp -bl -noll -pt=2 -bt=2 -sbt=2 -icp

Para usar este estilo con -xlp (--extended-line-up-parentheses) en lugar de -lp (--line-up-parentheses) use -gnu -xlp.

-pbp, --perl-best-practices
-pbp es una abreviatura de los parámetros del libro Perl Best Practices de Damian Conway: 
-l=78 -i=4 -ci=4 -st -se -vt=2 -cti=0 -pt=1 -bt=1 -sbt=1 -bbt=1
-nsfs -nolq
-wbb="% + - * / x != == >= <= =~ !~ < > | & =
      **= += *= &= <<= &&= -= /= |= >>= ||= //= .= %= ^= x="

Tenga en cuenta que este conjunto de parámetros incluye los indicadores -st (--standard-output) y -se (--standard-error-output), que hacen que perltidy actúe como un filtro en un solo archivo. Estos pueden ser anulados colocando -nst y/o -nse después del parámetro -pbp.

También tenga en cuenta que el valor de la indentación de continuación, -ci=4, es igual al valor de la indentación completa, -i=4. Se recomienda que (1) se use el parámetro -ci=2 en su lugar, o (2) se establezca el indicador -xci. Esto ayudará a mostrar la estructura, especialmente cuando hay declaraciones ternarias. El siguiente fragmento ilustra estas opciones.

# perltidy -pbp
$self->{_text} = (
     !$section        ? ''
    : $type eq 'item' ? "the $section entry"
    :                   "the section on $section"
    )
    . (
    $page
    ? ( $section ? ' in ' : '' ) . "the $page_ext manpage"
    : ' elsewhere in this document'
    );
# perltidy -pbp -ci=2
$self->{_text} = (
     !$section        ? ''
    : $type eq 'item' ? "the $section entry"
    :                   "the section on $section"
  )
  . (
    $page
    ? ( $section ? ' in ' : '' ) . "the $page_ext manpage"
    : ' elsewhere in this document'
  );
# perltidy -pbp -xci
$self->{_text} = (
     !$section        ? ''
    : $type eq 'item' ? "the $section entry"
    :                   "the section on $section"
    )
    . ( $page
        ? ( $section ? ' in ' : '' ) . "the $page_ext manpage"
        : ' elsewhere in this document'
    );

El indicador -xci se desarrolló después de que se publicaran los parámetros -pbp, por lo que debe incluirlo por separado.

Crear un archivo ilegible
El objetivo de perltidy es mejorar la legibilidad de los archivos, pero hay dos comandos que tienen el efecto opuesto, --mangle y --extrude. En realidad, son simplemente alias para combinaciones de otros parámetros. Ambos eliminan todo el espacio en blanco posible, pero dejan los comentarios y los documentos pod, de modo que son esencialmente reversibles. La diferencia entre estos es que --mangle pone el mínimo número posible de saltos de línea en un script, mientras que --extrude pone el máximo posible. Tenga en cuenta que estas opciones no proporcionan una ofuscación significativa, porque perltidy puede usarse para reformatear los archivos. Originalmente se desarrollaron para ayudar a probar la lógica de tokenización de perltidy, pero tienen otros usos. Un uso para --mangle es el siguiente: 
perltidy --mangle myfile.pl -st | perltidy -o myfile.pl.new

Esto formará el número máximo posible de bloques de una sola línea (ver la siguiente sección) y a veces puede ayudar a limpiar un script mal formateado.

Se puede usar una técnica similar con --extrude en lugar de --mangle para hacer el número mínimo de bloques de una sola línea.

Otro uso para --mangle es combinarlo con --delete-all-comments (-dac) para reducir el tamaño del archivo de un script de perl.

Bloques de una línea

Un bloque de una línea es un bloque de código donde el contenido dentro de las llaves es lo suficientemente corto como para caber en una sola línea. Por ejemplo,

if ( -e $file ) { print "'$file' exists\n" }

La alternativa, un bloque que abarca varias líneas, se dice que es un bloque roto. Con pocas excepciones, perltidy conserva los bloques de una línea existentes, si es posible dentro de la restricción de longitud de línea, pero no intenta formar nuevos. En otras palabras, perltidy intentará seguir el archivo de entrada con respecto a los bloques rotos y no rotos.

La principal excepción a esta regla es que perltidy intentará formar nuevos bloques de una línea después de las palabras clave "map", "eval" y "sort", "eval", porque estos bloques de código a menudo son pequeños y se muestran de forma más clara en una sola línea. Este comportamiento se puede controlar con el indicador --one-line-block-exclusion-list descrito a continuación.

Cuando el estilo cuddled-else está

Control de bloques de una sola línea

Este es el control de la formación y el formato de bloques de código que están contenidos en una sola línea. Los bloques de una sola línea son líneas que contienen código y llaves de apertura y cierre, por ejemplo:

if ( $foo ) { bar() }

Por defecto, perltidy intentará convertir en bloques de una sola línea cualquier bloque que pueda ser formateado en una sola línea. Por ejemplo, el siguiente código:

foreach (@list) {
    if ( $_ eq $asked_for ) {
        last;
    }
    ++$found;
}

será formateado como:

foreach (@list) { if ( $_ eq $asked_for ) { last } ++$found }

Esto se hace para los siguientes tipos de bloques:

  • sort
  • map
  • grep
  • eval

Por supuesto, el estilo de sangría de los bloques de una sola línea está controlado por el parámetro --cuddled-else y el parámetro --cuddled-break-option. Si el estilo de sangría de los bloques de una sola línea está establecido en cuddled, entonces la llave de cierre del bloque se colocará en la misma línea que el código, o en la línea anterior si no existe código. Si se usa el estilo de sangría continue, entonces la llave de cierre del bloque se colocará en una línea nueva, con sangría igual a la línea del bloque de código. El estilo de sangría de los bloques de una sola línea es el mismo que el de los bloques de varias líneas.

Cuando se usa, el tratamiento por defecto de los bloques de una sola línea puede interferir con el estilo abrazado. En este caso, el comportamiento por defecto puede cambiarse con el flag --cuddled-break-option=n descrito en otra parte.

Cuando un bloque de una sola línea existente es más largo que la longitud máxima de línea y, por lo tanto, debe dividirse en varias líneas, perltidy busca y agrega cualquier punto y coma opcional final (a menos que se use la opción -nasc) si el bloque es un bloque de código.

-olbxl=s, --one-line-block-exclusion-list=s
Como se señaló anteriormente, perltidy, por defecto, intentará crear nuevos bloques de una sola línea para ciertos tipos de bloques. Este flag permite al usuario evitar este comportamiento para los tipos de bloques que se enumeran en la cadena s. La lista s puede incluir cualquiera de las palabras "sort", "map", "grep", "eval", o puede ser "*" para indicar todos estos.

Así, por ejemplo, para evitar que los bloques eval multilínea se conviertan en bloques de una sola línea, el comando sería -olbxl='eval'. En este caso, los bloques de una sola línea eval existentes permanecerán en una sola línea si es posible, y los bloques multilínea eval existentes permanecerán como bloques multilínea.

-olbn=n, --one-line-block-nesting=n
Los bloques anidados de una sola línea son líneas con bloques de código que a su vez contienen bloques de código. Por ejemplo, la siguiente línea es un bloque anidado de una sola línea. 
foreach (@list) { if ($_ eq $asked_for) { last } ++$found }

El comportamiento por defecto es dividir tales líneas en múltiples líneas, pero este comportamiento puede controlarse con este flag. Los valores de n son:

n=0 dividir bloques anidados de una sola línea en múltiples líneas [POR DEFECTO]
n=1 estable: mantener intactos los bloques anidados de una sola línea existentes

Para el ejemplo anterior, el formato por defecto (-olbn=0) es

foreach (@list) {
    if ( $_ eq $asked_for ) { last }
    ++$found;
}

Si se proporciona el parámetro -olbn=1, la línea se dejará intacta si está en una sola línea en el código fuente, o se dividirá en múltiples líneas si está dividida en múltiples líneas en el código fuente.

-olbs=n, --one-line-block-semicolons=n
Este flag controla la colocación de puntos y comas al final de los bloques de una sola línea. Los puntos y comas son opcionales antes de una llave de cierre de bloque, y con frecuencia se omiten al final de un bloque de una sola línea que contiene solo una única sentencia. Por defecto, perltidy sigue el archivo de entrada con respecto a estos puntos y comas, pero este comportamiento puede ser controlado por este flag. Los valores de n son:

n=0 eliminar puntos y comas terminales en bloques de una sola línea de una única sentencia
n=1 estable; mantener los puntos y comas terminales de entrada [POR DEFECTO]
n=2 agregar puntos y comas terminales en todos los bloques de una sola línea

Tenga en cuenta que la opción n=2 no tiene ningún efecto si se prohíbe agregar puntos y comas con el flag -nasc. También tenga en cuenta que mientras n=2 agrega puntos y comas faltantes a todos los bloques de una sola línea, independientemente de su complejidad, la opción n=0 solo elimina los puntos y comas finales que terminan bloques de una sola línea que contienen solo un punto y coma. Por lo tanto, estas dos opciones no son inversas exactas.

Formación de nuevos bloques de una sola línea
A veces, puede ser deseable convertir un script para que tenga bloques de una sola línea siempre que sea posible. Aunque actualmente no hay un flag para esto, una solución simple es ejecutar perltidy dos veces, una vez con el flag --noadd-newlines y luego una vez más con parámetros normales, de esta manera:

cat infile | perltidy -nanl | perltidy >outfile

Cuando se ejecuta en este fragmento

if ( $? == -1 ) {
    die "failed to execute: $!\n";
}
if ( $? == -1 ) {
    print "Had enough.\n";
    die "failed to execute: $!\n";
}

el resultado es

if ( $? == -1 ) { die "failed to execute: $!\n"; }
if ( $? == -1 ) {
    print "Had enough.\n";
    die "failed to execute: $!\n";
}

Esto muestra que los bloques con una sola sentencia se convierten en bloques de una sola línea.

División de bloques existentes de una sola línea
No hay una forma automática de dividir bloques largos existentes de una sola línea en múltiples líneas, pero esto se puede lograr procesando un script, o una sección de un script, con un valor corto del parámetro maximum-line-length=n. Luego, cuando el script se reformatea nuevamente con los parámetros normales, los bloques que se dividieron permanecerán divididos (con las excepciones mencionadas anteriormente).

Otro truco para hacer esto para ciertos tipos de bloques es formatear una vez con el flag --cuddled-else y --cuddled-break-option=2. Luego, formatear nuevamente con los parámetros normales. Esto dividirá cualquier bloque de una sola línea que esté involucrado en un estilo de cuddled-else.

Control de la alineación vertical

La alineación vertical se refiere a alinear ciertos símbolos en una lista de líneas consecutivas similares para mejorar la legibilidad. Por ejemplo, las "comas gordas" están alineadas en la siguiente sentencia:

$data = $pkg->new(
    PeerAddr => join( ".", @port[ 0 .. 3 ] ),
    PeerPort => $port[4] * 256 + $port[5],
    Proto    => 'tcp'
);

La alineación vertical se puede desactivar por completo usando el flag -novalign mencionado a continuación. Sin embargo, la alineación vertical puede forzarse a detenerse y reiniciarse introduciendo selectivamente líneas en blanco. Por ejemplo, se ha insertado un espacio en blanco en el siguiente código para mantener alineadas cosas algo similares.

%option_range = (
    'format'             => [ 'tidy', 'html', 'user' ],
    'output-line-ending' => [ 'dos',  'win',  'mac', 'unix' ],
    'character-encoding' => [ 'none', 'utf8' ],
    'block-brace-tightness'    => [ 0, 2 ],
    'brace-tightness'          => [ 0, 2 ],
    'paren-tightness'          => [ 0, 2 ],
    'square-bracket-tightness' => [ 0, 2 ],
);

La alineación vertical se implementa aumentando localmente un espacio en blanco existente para producir alineación con una línea adyacente. No puede ocurrir si no hay espacio en blanco para aumentar. Por lo tanto, si un espacio particular se elimina por uno de los controles existentes, la alineación vertical no puede ocurrir.

Por ejemplo, si eliminamos el espacio antes de las "comas gordas" en el ejemplo anterior, la alineación vertical no puede ocurrir:

# perltidy --no-want-left-space='=>'
$data = $pkg->new(
    PeerAddr=> join( ".", @port[ 0 .. 3 ] ),
    PeerPort=> $port[4] * 256 + $port[5],
    Proto=> 'tcp'
);
Desactivar completamente la alineación vertical con -novalign
Por defecto se utiliza la alineación vertical, pero la alineación vertical puede desactivarse por completo con el flag -novalign.

Es posible un nivel de control más bajo de la alineación vertical con tres parámetros: -vc, -vsc, y -vbc. Estos controlan independientemente la alineación del código, los comentarios laterales y los comentarios de bloque. Se describen en la siguiente sección.

El parámetro -valign es en realidad un alias para -vc -vsc -vbc, y su negativo -novalign es un alias para -nvc -nvsc -nvbc.

Control de la alineación de código con --valign-code o -vc
El flag -vc habilita la alineación de símbolos de código como <=>. El valor por defecto es -vc. Para un control detallado de qué símbolos alinear, consulte el parámetro --valign-exclude-list a continuación.
Control de la alineación de comentarios laterales con --valign-side-comments o -vsc
La regla básica para la alineación de comentarios laterales es que los comentarios laterales en una secuencia de líneas con la misma sangría inicial se alinearán si el espacio lo permite. Los comentarios laterales en líneas con diferentes sangrías iniciales generalmente no se alinearán.

El flag -vsc habilita la alineación de comentarios laterales y está habilitado por defecto. Si la alineación de comentarios laterales está deshabilitada con -nvsc, aparecerán a un espacio fijo del token de código anterior. El valor por defecto es -vsc.

Control de la alineación de comentarios de bloque con --valign-block-comments o -vbc
Cuando -vbc está habilitado, los comentarios de bloque pueden alinearse, por ejemplo, si un comentario de una secuencia consecutiva de comentarios se des-sangra debido a una longitud que excede la longitud máxima de línea. Si esto ocurre, todo el grupo de comentarios permanecerá alineado y se des-sangrará en la misma cantidad. Esta alineación coordinada no ocurrirá si se establece -nvbc. El valor por defecto es -vbc.
Control de alineación más detallado con --valign-exclusion-list=s o -vxl=s y --valign-inclusion-list=s o -vil=s
Se dispone de un control más detallado de los tipos de alineación con estos dos parámetros. La mayoría de las alineaciones verticales en programas típicos ocurren en uno de los tokens ',', '=', y '=>', pero muchas otras alineaciones son posibles y se dan en la siguiente lista: 
= **= += *= &= <<= &&= -= /= |= >>= ||= //= .= %= ^= x= ^^=
{ ( ? : , ; => && || ~~ !~~ =~ !~ // <=> -> q
if unless and or err for foreach while until

Estos tipos de alineación corresponden a símbolos, operadores y palabras clave de Perl, excepto por 'q', que se refiere al caso especial de alineación en una sentencia 'use' de comillas qw y paréntesis vacíos.

Todos están habilitados por defecto, pero pueden ser deshabilitados selectivamente incluyendo uno o más de estos tokens en la lista separada por espacios valign-exclusion-list=s. Por ejemplo, lo siguiente evitaría la alineación en = e if:

--valign-exclusion-list='= if'

Si es más simple especificar solo los tipos de token que se van a alinear, incluya los tipos que se van a alinear en la lista de --valign-inclusion-list. En ese caso, puede dejar valign-exclusion-list indefinido, o usar el símbolo especial * para la lista de exclusión. Por ejemplo, los siguientes parámetros habilitan la alineación solo en comas y "comas gordas":

--valign-inclusion-list=', =>'
--valign-exclusion-list='*'  ( esto es opcional y puede omitirse )

Estas listas de parámetros deben consistir

espacios de tokens separados por espacios de la lista anterior de tokens de alineación posibles, o un '*'. Si un token no reconocido aparece, simplemente se ignora. Y si un token específico se ingresa en ambas listas por error, la lista de exclusión tiene prioridad.

Los valores predeterminados de estos parámetros habilitan todas las alineaciones y son equivalentes a

--valign-exclusion-list=' '
--valign-inclusion-list='*'

Para ilustrar, considere el siguiente fragmento con formato predeterminado

# perltidy
$co_description = ($color) ? 'bold cyan'  : '';           # descr
$co_prompt      = ($color) ? 'bold green' : '';           # prompt
$co_unused      = ($color) ? 'on_green'   : 'reverse';    # unused

Para excluir todas las alineaciones excepto las de igual (es decir, incluir solo las de igual) podríamos usar:

# perltidy -vil='='
$co_description = ($color) ? 'bold cyan' : '';          # descr
$co_prompt      = ($color) ? 'bold green' : '';         # prompt
$co_unused      = ($color) ? 'on_green' : 'reverse';    # unused

Para excluir solo las de igual podríamos usar:

# perltidy -vxl='='
$co_description = ($color) ? 'bold cyan' : '';     # descr
$co_prompt = ($color) ? 'bold green' : '';         # prompt
$co_unused = ($color) ? 'on_green' : 'reverse';    # unused

Observe en este último ejemplo que, aunque solo se excluyó la alineación de igual, las alineaciones ternarias también se perdieron. Esto sucede porque el alineador vertical barre de izquierda a derecha y generalmente se detiene si una alineación importante no se puede hacer por alguna razón.

Pero también observe que los comentarios laterales permanecen alineados porque su alineación se controla por separado con el parámetro --valign-side-comments descrito anteriormente.

Alineando unfin y si con --valign-if-unless o -viu
Por defecto, los términos if de sufijo se alinean y los términos unless de sufijo se alinean, pero por separado. Por ejemplo, 
# perltidy [PREDETERMINADO]
print "Tried to add: @Resolve\n" if ( @Resolve and !$Quiet );
print "Would need: @DepList\n"   if ( @DepList and !$Quiet );
print "Output:\n"                  unless $Quiet;
print join( "\n", @Output ) . "\n" unless $Quiet;

La opción -viu hace que un unless de sufijo se trate como si fuera un if de sufijo a efectos de alineación, y por lo tanto se alinean:

# perltidy -viu
print "Tried to add: @Resolve\n"   if ( @Resolve and !$Quiet );
print "Would need: @DepList\n"     if ( @DepList and !$Quiet );
print "Output:\n"                  unless $Quiet;
print join( "\n", @Output ) . "\n" unless $Quiet;
Alineando números con signo con --valign-signed-numbers o -vsn
Establecer -vsn hace que las columnas de números que contienen valores tanto con signo como sin signo tengan signos iniciales colocados en su propia columna. Por ejemplo: 
# perltidy -vsn
my @correct = (
    [  123456.79,   86753090000.868,  11 ],
    [ -123456.79,  -86753090000.868, -11 ],
    [  123456.001,  80.080,           10 ],
    [ -123456.001, -80.080,           0 ],
    [  10.9,        10.9,             11 ],
);

El valor predeterminado es -vsn. Esto se puede desactivar para obtener una justificación estricta a la izquierda:

# perltidy -nvsn
my @correct = (
    [ 123456.79,   86753090000.868,  11 ],
    [ -123456.79,  -86753090000.868, -11 ],
    [ 123456.001,  80.080,           10 ],
    [ -123456.001, -80.080,          0 ],
    [ 10.9,        10.9,             11 ],
);

Algunos puntos sobre -vsn son:

  • Esta opción funciona insertando un solo espacio delante de los números sin signo cuando es posible. Esto no se hace si requiere aumentar el ancho máximo de una columna.
  • Esta opción se limita principalmente a listas de números separados por comas. Para listas de números multilínea, tener comas finales a veces puede mejorar los resultados. Si faltan, perltidy puede agregarlas, por ejemplo, con los parámetros -wtc=b -atc. Vea "Agregar y eliminar comas".
  • Esta opción tiene un parámetro de control --valign-signed-number-limit=N, o -vsnl=N. Este valor controla el formato de columnas muy largas de números y normalmente no debería necesitar ser cambiado. Para ver su propósito, considere una columna muy larga de solo números sin signo, digamos 1000 líneas. Si agregamos un solo número negativo, es indeseable mover todos los demás números un espacio. Esto podría crear muchas líneas de diferencias en el archivo pero sin mejorar realmente la apariencia cuando se ve una sección local de la tabla. El número N evita este problema al no agregar indentación adicional a una secuencia de más de N líneas de números sin signo. El valor predeterminado, N=20, se establece como un número de líneas para las cuales los extremos de una columna larga de números sin signo normalmente no están ambos a la vista.
Alineando operadores de asignación con --valign-wide-equals o -vwe
Los siguientes operadores de asignación se alinean de forma independiente por defecto: 
= **= += *= &= <<= &&= -= /= |= >>= ||= //= .= %= ^= x= ^^=

Establecer --valign-wide-equals, o -vwe, hace que se alineen verticalmente junto con el último = alineado. Por ejemplo, aquí está el formato predeterminado para un código con varios de estos operadores:

$str .= SPACE x $total_pad_count;
$str_len += $total_pad_count;
$total_pad_count = 0;
$str .= $rfields->[$j];
$str_len += $rfield_lengths->[$j];

Y aquí está el mismo código formateado con -vwe:

# perltidy -vwe
$str             .= SPACE x $total_pad_count;
$str_len         += $total_pad_count;
$total_pad_count  = 0;
$str             .= $rfields->[$j];
$str_len         += $rfield_lengths->[$j];

Esta opción se agregó para el problema git #135 y puede mejorar la legibilidad, pero está desactivada por defecto para evitar cambiar el formato existente.

Sintaxis Extendida

Esta sección describe algunos parámetros para tratar con sintaxis extendida.

Para otro método de manejo de sintaxis extendida vea la sección "Omitir secciones de código seleccionadas".

También tenga en cuenta que el módulo Perl::Tidy suministra una capacidad de pre-filtro y post-filtro. Esto requiere llamar al módulo desde un programa separado en lugar de hacerlo a través del binario perltidy.

-xs, --extended-syntax
Esta opción permite a perltidy manejar ciertas extensiones comunes a la sintaxis estándar sin quejarse.

Por ejemplo, sin esta opción una estructura como la siguiente generaría un error de sintaxis:

Method deposit( Num $amount) {
    $self->balance( $self->balance + $amount );
}

Esta opción está habilitada por defecto, pero se puede desactivar con -nxs. Probablemente la única razón para desactivar esta opción es generar más mensajes de diagnóstico al depurar un script.

-sal=s, --sub-alias-list=s
Esta opción hace que una o más palabras se traten igual que si fueran la palabra clave sub. La cadena s contiene una o más palabras alias, separadas por espacios o comas.

Por ejemplo,

perltidy -sal='method fun _sub M4'

hará que perltidy trate las palabras 'method', 'fun', '_sub' y 'M4' igual que si fueran 'sub'. Tenga en cuenta que si las palabras alias están separadas por espacios, la cadena de palabras debe colocarse entre comillas.

Tenga en cuenta que varios otros parámetros aceptan una lista de palabras clave, incluyendo 'sub' (vea "Especificar tipos de bloque"). No necesita incluir alias de sub en estas listas. Simplemente incluya la palabra clave 'sub' si lo desea, y todas las alias se incluirán automáticamente.

-gal=s, --grep-alias-list=s
Esta opción permite que un bloque de código que sigue a una función externa de 'operador de lista' se formatee como si siguiera a una de las palabras clave integradas grep, map o sort. La cadena s contiene los nombres de uno o más de dichos operadores de lista, separados por espacios o comas.

Por 'operador de lista' se entiende una función que se invoca en la forma

palabra {BLOQUE} @lista

Perltidy intenta mantener intactos los bloques de código para estas funciones, ya que suelen ser cortos, y no rompe automáticamente después de la llave de cierre ya que puede seguir una lista. También realiza un manejo especial de la indentación de continuación.

Por ejemplo, los argumentos de bloque de código para las funciones 'My_grep' y 'My_map' pueden recibir un formato como 'grep' con

perltidy -gal='My_grep My_map'

Por defecto, los siguientes operadores de lista en List::Util se incluyen automáticamente:

all any first none notall reduce reductions

Cualquier operador especificado con --grep-alias-list se añade a esta lista. El siguiente parámetro se puede utilizar para eliminar palabras de esta lista predeterminada.

-gaxl=s, --grep-alias-exclusion-list=s
La opción -gaxl=s proporciona un método para eliminar cualquiera de los operadores de lista predeterminados dados anteriormente listándolos en la cadena s. Para eliminar todos los operadores predeterminados use -gaxl='*'.
-uf=s, --use-feature=s
Esta opción le dice a perltidy que permita o prohíba la sintaxis asociada a un pragma en la cadena s. Los posibles ajustes actuales son:
  • --use-feature='class'. Esto le dice a perltidy que reconozca las palabras especiales class, method, field y ADJUST tal como se definen para esta característica.
  • --use-feature='noclass'. Esto le dice a perltidy que no trate las palabras class, method, field, ADJUST especialmente.
  • Ninguna de estas (--use-feature no definido). Este es el AJUSTE PREDETERMINADO y recomendado. En este caso, perltidy intentará manejar automáticamente tanto la sintaxis más reciente de "feature 'class'" como algunos usos conflictivos de algunas de estas palabras especiales por módulos existentes.

Tenga en cuenta que este parámetro es independiente de cualquier línea de control use feature dentro de un script. Perltidy no busca ni lee s

Depuración de la entrada de perltidy

Parámetros --dump-...
Las siguientes banderas están disponibles para la depuración. Tenga en cuenta que todos los comandos llamados --dump-... simplemente escribirán la información solicitada en la salida estándar y luego saldrán inmediatamente.

--dump-cuddled-block-list o -dcbl volcará en la salida estándar el hash interno de tipos de bloques acurrucados creado por una cadena de entrada --cuddled-block-list.

--dump-defaults o -ddf escribirá el conjunto de opciones predeterminadas en la salida estándar y saldrá.

--dump-integer-option-range o -dior escribirá una lista de valores separados por comas. Cada línea contendrá el nombre de una opción entera junto con sus valores mínimo, máximo y predeterminado.

--dump-profile o -dpro escribirá el nombre del archivo de configuración actual y su contenido en la salida estándar y saldrá.

--dump-options o -dop escribirá el conjunto de opciones actual en la salida estándar y saldrá.

--dump-long-names o -dln escribirá todos los nombres largos de la línea de comandos (pasados a Get_options) en la salida estándar y saldrá.

--dump-short-names o -dsn escribirá todos los nombres cortos de la línea de comandos en la salida estándar y saldrá.

--dump-token-types o -dtt escribirá una lista de todos los tipos de tokens en la salida estándar y saldrá.

--dump-want-left-space o -dwls escribirá el hash %want_left_space en la salida estándar y saldrá. Consulte la sección sobre cómo controlar los espacios en blanco alrededor de los tokens.

--dump-want-right-space o -dwrs escribirá el hash %want_right_space en la salida estándar y saldrá. Consulte la sección sobre cómo controlar los espacios en blanco alrededor de los tokens.

Consulte "Analizando código" para ver parámetros --dump- adicionales.

Otros parámetros relacionados con el procesamiento
--no-memoize o -nmem desactivará la memorización. La memorización puede reducir el tiempo de ejecución cuando se ejecuta perltidy repetidamente en un solo proceso. Está activada por defecto, pero puede desactivarse para pruebas con -nmem.

--no-timestamp o -nts eliminará cualquier marca de tiempo en los archivos de salida para evitar que las diferencias en las fechas provoquen fallos en los scripts de instalación de pruebas. Solo hay un par de lugares donde normalmente aparecen las marcas de tiempo. Una es en las cabeceras de los archivos html, y otra es cuando se selecciona la opción -cscw. El valor predeterminado es permitir marcas de tiempo (--timestamp o -ts).

--file-size-order o -fso hará que los archivos se procesen en orden de tamaño creciente, cuando se procesan varios archivos. Esto es particularmente útil durante el desarrollo del programa, cuando se procesan grandes cantidades de archivos con tamaños variables, ya que puede reducir el uso de memoria virtual. Este es el valor predeterminado y puede desactivarse con -nfso.

--maximum-file-size-mb=n o -maxfs=n especifica el tamaño máximo de archivo en megabytes que perltidy intentará formatear. Este parámetro se proporciona para evitar causar problemas en el sistema al intentar formatear accidentalmente un archivo de datos extremadamente grande. La mayoría de los scripts de perl tienen menos de 2 MB de tamaño. El entero n tiene un valor predeterminado de 10, por lo que perltidy omitirá el formateo de archivos cuyo tamaño sea superior a 10 MB. El comando para aumentar el límite a 20 MB, por ejemplo, sería

perltidy -maxfs=20

Esta prueba de longitud se aplica a los archivos con nombre antes de leerlos en memoria. Se aplica a los archivos que llegan de la entrada estándar después de haber sido leídos en memoria. No se aplica a cadenas de caracteres que llegan mediante una llamada al módulo Perl::Tidy.

Controles para decidir cuándo detener el procesamiento
--maximum-level-errors=n o -maxle=n especifica el número máximo de errores de nivel de indentación permitidos antes de que perltidy omita el formateo y simplemente imprima un archivo tal cual. El valor predeterminado es n=1. Esto significa que si la indentación final de un script difiere de la indentación inicial en más de 1 nivel, el archivo se imprimirá tal cual. Para evitar el formateo si hay algún error de nivel de indentación, use -maxle=0. Para omitir esta comprobación, puede establecer n en un número grande, como n=100, o establecer n=-1.

Por ejemplo, el siguiente script tiene un error de nivel de 3 y se imprimirá tal cual

Entrada y salida predeterminada:
{{{
perltidy -maxle=100
{
    {
        {

--maximum-unexpected-errors=n o -maxue=n especifica el número máximo de errores de tokenización inesperados permitidos antes de que se omita el formateo y se imprima un script tal cual. La intención es evitar formatear accidentalmente un script que no sea de perl, como un archivo html, por ejemplo. Esta comprobación se puede desactivar estableciendo n=0.

Un valor recomendado es n=3. Sin embargo, el valor predeterminado es n=0 (omitir esta comprobación) para evitar causar problemas con scripts que tienen sintaxis extendidas.

Manejo de errores en opciones que toman valores enteros
Muchos de los parámetros de entrada toman valores enteros. Antes de que comience el procesamiento, se realiza una comprobación para ver si alguno de estos parámetros enteros excede sus rangos válidos. El comportamiento predeterminado cuando se excede un rango es escribir un mensaje de advertencia y restablecer el valor a su configuración predeterminada. Este comportamiento predeterminado se puede cambiar con el parámetro --integer-range-check=n, o -irc=n, de la siguiente manera: 
n=1  restablece valores incorrectos a los predeterminados pero no emite advertencia
n=2  restablece valores incorrectos a los predeterminados y emite advertencia [PREDETERMINADO]
n=3  detiene si algún valor está fuera de los límites

El valor n=1 es principalmente útil para fines de prueba.

Depuración de la tokenización de perltidy
-DEBUG, -D escribirá un archivo con la extensión .DEBUG por cada archivo de entrada que muestre la tokenización de todas las líneas de código. Esto puede producir una gran cantidad de salida y es principalmente útil para depurar problemas de tokenización durante el desarrollo de perltidy.

Analizando Código

Perltidy informa de cualquier problema obvio que se encuentre durante el formateo, como llaves desequilibradas. Pero hay varios parámetros disponibles para realizar comprobaciones adicionales de problemas que podrían interesar a un programador. Estos parámetros se dividen en dos categorías, indicadas por su prefijo, --dump- o --warn-:

  • Los parámetros --dump- leen un archivo, escriben información en la salida estándar y luego salen sin realizar ningún formateo.
  • Los parámetros --warn-, por otro lado, hacen que perltidy funcione normalmente pero emiten advertencias en la salida de errores cuando se encuentran ciertas condiciones.

Algunos de estos tienen parámetros de control asociados.

Use --dump-block-summary para crear una tabla de información sobre bloques de código
Se puede crear una tabla que liste información sobre los bloques de código en un archivo con --dump-block-summary, o -dbs. Esto hace que perltidy lea y analice el archivo, escriba una tabla de valores separados por comas para bloques de código seleccionados en la salida estándar y luego salga. Este parámetro debe estar en la línea de comandos, no en un archivo .perltidyrc, y requiere un solo nombre de archivo en la línea de comandos. Por ejemplo 
perltidy -dbs somefile.pl >blocks.csv

produce un archivo de salida blocks.csv cuyas líneas contienen estos parámetros:

filename     - nombre del archivo
line         - número de línea de la llave de apertura de este bloque
line_count   - número de líneas entre la llave de apertura y cierre
code_lines   - número de líneas excluyendo espacios en blanco, comentarios y pod
type         - tipo de bloque (sub, for, foreach, ...)
name         - nombre del bloque si es aplicable (nombre de sub o asub, etiqueta..)
depth        - profundidad de anidamiento de la llave del bloque de apertura
max_change   - cambio en la profundidad del bloque de código anidado más profundo
block_count  - número total de bloques de código anidados en este bloque
mccabe1      - medida de complejidad de McCabe de este bloque de código
mccabe2      - modificado: las subs tienen eliminada la complejidad de subs anónimas
comment_lines - número de líneas de comentarios o POD con algún texto

Esta característica se desarrolló para ayudar a identificar secciones de código complejas como una ayuda para la refactorización. La medida de complejidad de McCabe, 'mccabe1', coincide con la definición utilizada por Perl::Critic. El valor de complejidad alternativo, 'mccabe2', es el mismo excepto que para las subrutinas, la complejidad de cualquier sub anónima contenida se elimina y se muestra por separado. Este valor alternativo puede ser más representativo de la complejidad real, y a veces mucho menor. Por ejemplo, en una de las subs de perltidy, los dos valores son 77 y 6. La diferencia es compartida por las subs anónimas que contiene, de las cuales el máximo es 36.

Por defecto, la tabla contiene estos valores para subrutinas, pero el usuario puede solicitarlos para cualquier bloque de código o paquete. Para los bloques que son bucles anidados dentro de bucles, se añade un sufijo '+' al "type" para indicar posible complejidad del código. Aunque la tabla no indica de otra manera qué bloques están anidados en otros bloques, esto se puede determinar calculando y comparando los números de línea de finalización del bloque.

Para las subrutinas, el número de argumentos de llamada (args) se lista entre paréntesis en la columna "type". Por ejemplo, sub(9) indica una sub con 9 argumentos. Las subrutinas cuyo número de argumentos no se puede determinar fácilmente se indican como sub(*). El recuento incluye cualquier objeto principal pasado en una llamada a un método (como $self).

También para las subrutinas, la existencia de comentarios o texto pod antes y después de la definición de los argumentos de llamada se indica con símbolos de almohadilla alrededor del número de argumentos. Así, sub(9#) indica una sub con 9 argumentos y algunos comentarios después de su definición. Y sub(#0) indica una sub con algunos comentarios o texto pod iniciales pero sin argumentos de llamada.

Por defecto, la tabla lista las subrutinas con más de 20 "code_lines", pero esto se puede cambiar con los dos parámetros siguientes:

--dump-block-minimum-lines=n, o

-dbl=n, donde n es el número mínimo de "líneas_de_código" a incluir. El valor predeterminado es -n=20. Ten en cuenta que "líneas_de_código" es el número de líneas excluyendo comentarios, líneas en blanco y pod.

--dump-block-types=s, o -dbt=s, donde la cadena s es una lista de tipos de bloques a incluir. El tipo de un bloque es el nombre de la palabra clave incorporada de perl para ese bloque (como sub if elsif else for foreach ...) o la palabra inmediatamente anterior a la llave de apertura. Además, hay algunos símbolos para tipos de bloques especiales, como los siguientes:

if elsif else for foreach ... cualquier palabra clave que introduzca un bloque
sub  - cualquier sub o sub anónima
asub - cualquier sub anónima
*    - cualquier bloque excepto bloques sin nombre
+    - cualquier bucle interno anidado
package - cualquier paquete o clase
closure - cualquier bloque sin nombre
elsif3  - una cadena if-elsif-... con 3 o más elsif's (ver más abajo)

Una cadena de bloques if-elsif-... puede ser reportada como un solo elemento de línea al ingresar la palabra elsif con un entero appended, como se indica en el último elemento de esta lista. El entero indica el número de bloques elsif requeridos para que una cadena sea reportada. Si usas esto, puede que quieras usar también -dbl=n, con un número menor de líneas n que el predeterminado.

Además, se pueden seleccionar tipos específicos de bucles de bloques que están anidados en otros bucles añadiendo un + después del nombre del bloque. (Los bucles anidados son a veces buenos candidatos para la reestructuración).

El valor predeterminado es -dbt='sub'.

En los siguientes ejemplos se crea una tabla "block.csv" para un archivo "somefile.pl":

  • Esto selecciona tanto "subs" como "packages" que tienen 20 o más líneas de código. Esto puede ser útil en código que contiene múltiples paquetes. 
    perltidy -dbs -dbt='sub package' somefile.pl >blocks.csv
  • Esto selecciona bloques con 2 o más líneas de código que son de tipo "sub" o que son bucles internos. 
    perltidy -dbs -dbl=2 -dbt='sub +' somefile.pl >blocks.csv
  • Esto selecciona cada bloque y paquete. 
    perltidy -dbs -dbl=1 -dbt='* closure' somefile.pl >blocks.csv
  • Esto selecciona cada cadena if que contiene 2 o más bloques "elsif": 
    perltidy -dbs -dbl=1 -dbt='elsif2' somefile.pl >blocks.csv
  • Esto selecciona cada bloque "while" con 6 o más líneas de código 
    perltidy -dbs -dbt=while -dbl=6 somefile.pl >while.csv
Uso --dump-unusual-variables para encontrar variables no utilizadas, reutilizadas y ciertas otras variables de interés
Las variables con ciertas propiedades de interés para un programador pueden ser listadas con --dump-unusual-variables o -duv. Este parámetro debe estar en la línea de comandos, junto con el nombre de un solo archivo. Hace que perltidy escanee el archivo en busca de ciertos tipos de variables, escriba las encontradas en la salida estándar y luego salga inmediatamente sin realizar ningún formateo. Por ejemplo 
perltidy -duv somefile.pl >vars.txt

produce un archivo con líneas que se ven algo así como

1778:u: my $input_file
6089:r: my $j: reutilizada - ver línea 6076

Los valores en la línea están separados por dos puntos y tienen el siguiente significado:

número de línea   - el número de la línea del archivo de entrada
incidente         - una sola letra que indica el incidente, ver abajo
nombre de variable - el nombre de la variable, precedido por una palabra clave
nota          - una nota opcional que se refiere a otra línea

Si hay un gran número de incidentes, puede ser conveniente leer el archivo en una hoja de cálculo.

Las verificaciones se realizan para variables introducidas por las palabras clave my, state y our, junto con variables definidas con use vars y use constant. Es una buena idea también establecer use strict en un script para que Perl pueda encontrar incidentes con variables que aparecen en un script sin uno de estos métodos.

Los tipos de verificaciones que se realizan se identifican en la salida con una de las letras r, s, p, u y c, como sigue:

r: nombre de variable reutilizado
Estas son variables que se redeclaran en el ámbito de una variable con el mismo nombre. Esto puede ser confuso, tal vez no cuando el código se escribió por primera vez, pero posiblemente más tarde durante el trabajo de mantenimiento. Por ejemplo, esto puede dificultar la localización de la variable correcta con un editor cuando se realizan cambios. Este incidente puede evitarse renombrando una de las variables en conflicto. Tenga en cuenta que esto es similar a la política de Perl::Critic Variables::ProhibitReusedNames.
s: cambio de sigilo pero bareword reutilizado
Estas son variables que tienen el mismo nombre de bareword pero un sigilo diferente ($, @ o %) que otra variable en el mismo ámbito. Por ejemplo, esto ocurre si las variables $data y %data comparten el mismo ámbito. Esto también puede ser confuso por las razones mencionadas anteriormente y puede evitarse renombrando una de las variables.
p: variables que cruzan paquetes
Estas son variables léxicas que se declaran en un paquete y aún son visibles en subrutinas de un paquete diferente en el mismo archivo. Esto puede ser confuso y podría hacer que el programa se ejecute de manera diferente, o falle, si los paquetes se dividieran alguna vez en archivos separados. Este incidente generalmente puede evitarse colocando el código entre llaves de algún tipo. Por ejemplo, este incidente a menudo se encuentra en el código de prueba y a veces se puede solucionar utilizando la estructura 
main();
sub main { #<<<
## el antiguo código de main va aquí
}

El comentario lateral non-indenting-braces "#<<<" no es obligatorio, pero mantendrá la indentación del código antiguo sin cambios.

Esta verificación solo se aplica a las declaraciones de paquete que no están encerradas en llaves para evitar advertencias en cambios temporales de paquete.

u: variables no utilizadas
Estas son variables léxicas declaradas con "my" o "state" (pero no "our") y que no se vuelven a referenciar dentro de su ámbito. Llamarlas no utilizadas es conveniente pero no muy preciso; esta es un "área gris" para un programa. Hay algunas buenas razones para tener tales variables. Por ejemplo, podrían aparecer en una lista de valores proporcionados por otra rutina o estructura de datos, y por lo tanto deben ser listadas, aunque no se vuelvan a referenciar. Tener tales variables puede hacerlas inmediatamente disponibles para el desarrollo y la depuración futuros, y puede ser beneficioso para la claridad del programa.

Sin embargo, a veces pueden ocurrir debido a haber sido olvidadas por un cambio de codificación, debido a un error tipográfico, o por tener un "my" precedente no intencional. Por lo tanto, vale la pena revisarlas, especialmente para el código nuevo. Aquí hay un ejemplo de una variable no utilizada en un script que se localiza con este método:

BEGIN { my $string = "" }
...
$string .= "ok";

Esto parece agradable a primera vista, pero el ámbito de la declaración "my" se limita a las llaves circundantes, por lo que no es la misma variable que el otro $string y, por lo tanto, debe ser reportada como no utilizada. Este problema en particular también habría sido detectado por perl si el autor hubiera usado "strict".

c: constantes no utilizadas
Estos son nombres que se declaran con un "use constant" y no se vio una referencia a ellos nuevamente dentro de su paquete. Pueden ser necesarios para un paquete externo, o un conjunto de definiciones estándar, o estar disponibles para el desarrollo futuro. Y en algunos casos inusuales, perltidy puede haber omitido una referencia. Pero también pueden ser restos no utilizados del desarrollo de código, o debido a un error tipográfico, por lo que puede valer la pena revisarlos.

Excepción: Las siguientes variables our están exentas de advertencias: $VERSION, @EXPORT, @EXPORT_OK, %EXPORT_TAGS, @ISA, $AUTOLOAD.

Uso --warn-variable-types para advertir sobre ciertos tipos de variables
El indicador --warn-variable-types=string, o -wvt=string, es el contraparte de --warn para --dump-unusual-variables, y puede ser utilizado para producir un mensaje de advertencia si se encuentran ciertos tipos de variables antes mencionados durante el formateo. Todas las posibles advertencias de variables se pueden solicitar con -wvt='*' o -wvt=1.

Por ejemplo,

perltidy -wvt='*' somefile.pl

El valor predeterminado es no realizar ninguna de estas verificaciones, y también se puede indicar con -wvt=0.

Para restringir la verificación a un conjunto específico de advertencias, establezca la cadena de entrada para que sea una lista separada por espacios o comas de las letras asociadas con los tipos de variables a verificar. Por ejemplo:

perltidy -wvt='s r' somefile.pl

procesará somefile.pl normalmente pero emitirá una advertencia si se encuentran alguno de los incidentes s o r, descritos anteriormente.

Un indicador complementario, --warn-variable-exclusion-list=string, o -wvxl=string, puede ser utilizado para omitir las verificaciones de advertencia para una lista de nombres de variables. Se puede colocar un '*' inicial y/o final en cualquiera de estos nombres de variables para permitir una coincidencia parcial.

Por ejemplo,

perltidy -wvt=1 -wvxl='$self $class *_unused'  somefile.pl

realizará todas las verificaciones posibles pero no informará ninguna advertencia para las variables $self, $class, y por ejemplo

Use --extra-unmatched-argument-length-exceptions=$value_unused para excluir argumentos de longitud de coincidencia parcial
Este parámetro proporciona una forma de especificar un número máximo de argumentos de coincidencia parcial que se permiten sin generar una advertencia. Si se excede este número, se genera una advertencia. Esta opción es útil para evitar advertencias para variables no utilizadas en el código, especialmente en situaciones en las que se utilizan comodines para excluir múltiples variables. Por ejemplo, puede especificar un valor para $value_unused que permita que un cierto número de variables no utilizadas pasen sin generar una advertencia.
Use --dump-unique-keys para ayudar a localizar claves de hash mal escritas
El parámetro --dump-unique-keys, o -duk, vuelca una lista de claves de hash que parecen usarse solo una vez y no aparecen entre las cadenas entre comillas en un archivo. Por ejemplo: 
perltidy -duk File.pm >output.txt

Las líneas en el archivo de salida enumeran claves únicas y números de línea.

Muchos programas contienen conjuntos de claves de hash que son en gran medida únicos para ese programa pero que se utilizan para la comunicación con otros programas. Se utiliza un filtro para evitar listar dichas claves. Este filtro se describe en la siguiente sección.

Un programa "dump_unique_keys.pl" en https://github.com/perltidy/perltidy/tree/master/examples puede ejecutar perltidy con -duk en varios archivos y luego eliminar las claves comunes de la lista.

Use --warn-unique-keys-cutoff=N, o -wukc=N, para ajustar el filtro de claves únicas.
Este parámetro controla el filtro utilizado tanto por --dump-unique-keys como por su contraparte --warn-unique-keys, descrita a continuación. El filtro funciona de la siguiente manera: si un conjunto relacionado de claves tiene más de N claves únicas, entonces ninguna de ellas se lista. El valor predeterminado es N=1, lo que provoca que se informe el número mínimo de claves. Aumentar N por encima de 1 permitirá que se informen más claves únicas.

Por lo tanto, un valor N=1 detectará hasta 1 error por conjunto de claves relacionadas. Un valor N=2 detectará hasta dos errores por conjunto, pero al mismo tiempo puede producir advertencias indeseables.

Para el caso especial N=1, se realiza un filtrado adicional para minimizar las advertencias no deseadas. Por ejemplo, las claves únicas en MAYÚSCULAS NO se informan para N=1.

Use --warn-unique-keys para advertir sobre posibles claves de hash mal escritas
El parámetro --warn-unique-keys, o -wuk, se puede utilizar para generar una advertencia de una posible clave de hash mal escrita durante el procesamiento normal. Funciona como la versión -dump anterior, pero escribe en la salida de error estándar si se encuentran claves únicas durante el formateo normal.

Para algunos scripts, esto producirá advertencias no deseadas para algunas claves, a pesar de que el filtro descrito anteriormente intenta evitarlo. Una forma de evitar advertencias para claves específicas es enumerarlas en algún lugar del programa en una lista qw. Esto se verá durante el escaneo de claves y, por lo tanto, las claves no se considerarán únicas.

Use --dump-similar-keys para ayudar a localizar claves de hash mal escritas
El parámetro --dump-similar-keys, o -dsk, proporciona otra forma de ayudar a localizar errores en las claves de hash. Vuelca una lista de claves de hash que son muy similares pero diferentes. Por ejemplo: 
perltidy -dsk File.pm >output.txt

Las líneas en el archivo de salida contienen pares de claves similares y el número de veces que se encontró cada una en el archivo. Por ejemplo, la siguiente línea es de un script real:

recieve,receive,2,6

Esto nos dice que la clave "recieve" (un error de ortografía) aparece 2 veces y la clave correcta "receive" aparece 6 veces:

Tenga en cuenta que si este error hubiera ocurrido solo una vez, también podría haberse encontrado con --dump-unique-keys o --warn-unique-keys. Pero como ocurre más de una vez, se necesita la opción --dump-similar-keys o su versión --warn- para localizarlo.

Use --warn-similar-keys, o -wsk, para advertir sobre claves de hash que son similares pero diferentes.
Esto es similar a la opción --dump-similar-keys pero escribe en el archivo de salida de error durante el formateo normal.

En la mayoría de los casos, las advertencias serán para claves de hash perfectamente válidas. Por lo tanto, este parámetro es probablemente más útil para la depuración ocasional. Vea "Creación de una nueva abreviatura" para una forma conveniente de incluirlo en un .perltidyrc.

Controles para --dump-similar y --warn-similar
Los parámetros predeterminados que controlan la búsqueda de claves similares normalmente deberían ser adecuados, pero se pueden modificar si es necesario. Son los siguientes:
--similar-keys-maximum-difference=n, o -skmd=n, especifica la diferencia máxima entre dos claves para considerarlas similares.
El entero n da el número máximo de diferencias a usar al verificar la similitud de claves de hash. El valor predeterminado es n=1. Las reglas básicas son que se cuenta una diferencia por cada una de las siguientes condiciones:
  • un cambio de mayúsculas/minúsculas de una letra, cualquier número de veces, como "LONGITUD, longitud". Esto se implementa haciendo comparaciones con copias en minúsculas de las cadenas si se detecta algún cambio de mayúsculas/minúsculas.
  • uno o más cambios de caracteres iguales, como "número-de-líneas, número_de_líneas". Esto se implementa recordando cualquier cambio, como de - a _ en este ejemplo, y contándolo solo una vez.
  • caracteres transpuestos, como "recibir, recibir"
  • un carácter faltante o extra, como "color, color" o "color, _color"
  • cualquier otra diferencia de caracteres, como "transparente, transparente"

Para ayudar a filtrar coincidencias no deseadas, una regla adicional es que se cuenta una diferencia extra si las letras **iniciales** son diferentes cuando ignoramos sus mayúsculas/minúsculas.

Por ejemplo, "_xmin, _Xmin" tiene una diferencia de uno debido al cambio de mayúsculas/minúsculas, pero la primera letra es la misma excepto por el cambio de mayúsculas/minúsculas. Entonces, la diferencia es uno y este par se informará con la configuración predeterminada n=1.

Por otro lado, el par "_xmin, _ymin" tiene una primera letra diferente que no se debe a un cambio de mayúsculas/minúsculas, por lo que la puntuación total de diferencia es 2, y no se informará con la configuración predeterminada n=1. Y es poco probable que este tipo de diferencia sea un error.

Por lo tanto, el valor predeterminado -skmd=1 detectará la mayoría de los errores comunes sin producir una salida excesiva, pero para una verificación más exhaustiva se puede aumentar a n=2.

Los valores superiores a 2 pueden producir una gran cantidad de salida, por lo que en lugar de usar valores más altos, podría ser mejor volcar todas las claves y examinarlas con el parámetro --dump-hash-keys descrito a continuación.

--similar-keys-minimum-length=n, o -skml=n, define una longitud mínima para las claves de hash.
Las claves de hash con menos de n caracteres se ignorarán al verificar claves similares. El valor predeterminado es n=4.
--similar-keys-maximum-pairs=n, o -skmp=n, define el número máximo de pares similares a mostrar
Cada par similar encontrado se muestra en una línea de salida, por lo que esto es equivalente al número máximo de líneas de salida. El valor predeterminado es 25.
Use --dump-hash-keys para volcar una lista de claves de hash
El parámetro --dump-hash-keys, o -dhk, vuelca una lista de todas las claves de hash encontradas por perltidy a la salida estándar y sale. Puede producir mucha salida, pero podría ser útil como último recurso al buscar un problema con una clave de hash. Por ejemplo: 
perltidy -dhk File.pm >output.txt

Las líneas en el archivo de salida enumeran las claves y el número de ocurrencias.

Use --dump-mixed-call-parens para encontrar funciones llamadas tanto con como sin paréntesis
El parámetro --dump-mixed-call-parens, o -dmcp, proporciona información sobre el uso de paréntesis de llamada dentro de un programa. Produce una lista de palabras clave y nombres de subrutinas que aparecen tanto con como sin paréntesis. En otras palabras, con un estilo mixto. Esto podría ser útil si se está trabajando para estandarizar el estilo de llamada para una palabra clave o función en particular. Por ejemplo, 
perltidy -dmcp somefile.pl >output.txt

analizará el texto de somefile.pl, escribirá los resultados en output.txt y luego saldrá inmediatamente (como todos los parámetros dump-).

La salida muestra una lista de operadores y el número de veces que se usaron con paréntesis y el número de veces sin paréntesis. Por ejemplo, aquí hay una pequeña sección de la salida de un archivo en una distribución anterior de Perl:

k:length:17:9
k:open:30:9
k:pop:3:4

La primera línea muestra que la función "length" ocurre 17 veces con paréntesis y 9 veces sin paréntesis. La 'k' indica que "length" es una palabra clave incorporada de Perl ('U' significaría subrutina definida por el usuario y 'w' significaría bareword desconocido). Por lo tanto, de esta salida parcial vemos que el autor tenía preferencia por los paréntesis alrededor de los argumentos de "length" y "open", mientras que "pop" estaba más o menos igualado

Uso de --want-call-parens=s y --nowant-call-parens=s para advertir sobre paréntesis de llamada faltantes o extra específicos
El parámetro --want-call-parens=s, o -wcp=s, se puede usar para producir un mensaje de advertencia si faltan paréntesis de llamada en funciones seleccionadas. De manera similar, --nowant-call-parens=s, o -nwcp=s, puede advertir si existen paréntesis de llamada para funciones seleccionadas. Cuando alguno de estos parámetros se establece, perltidy informará cualquier discrepancia del estilo solicitado en su salida de errores.

Antes de usar cualquiera de estos parámetros, puede ser útil usar primero --dump-mixed-call-parens=s, descrito en la sección anterior, para obtener una visión general del uso existente de paréntesis en un archivo.

Los argumentos de cadena s son listas separadas por espacios de los nombres de las funciones que se van a verificar. Los nombres de las funciones pueden ser palabras clave integradas o subs definidas por el usuario. No pueden incluir un prefijo de paquete ni un sigilo. Para ilustrar,

perltidy -wcp='length open' -nwcp='pop'   somefile.pl

significa que las funciones integradas "length" y "open" deben tener paréntesis alrededor de sus argumentos de llamada, pero "pop" no. La salida de error podría contener líneas como:

2314:open FD_TO_CLOSE: no call parens
3652:pop (: has call parens
3783:length $DB: no call parens
...

Para palabras clave integradas que tienen tanto una forma de bloque como una forma de modificador de sufijo, como "if", solo se verificará la forma de modificador de sufijo, ya que los paréntesis son obligatorios para la forma de bloque.

El símbolo & se puede ingresar en lugar de un nombre de función para significar todos los subs definidos por el usuario no listados explícitamente. Por lo tanto, la expresión compacta

perltidy -wcp='&' somefile.pl

significa que las llamadas a todos los subs definidos por el usuario en el archivo que se está procesando deben tener sus argumentos de llamada entre paréntesis.

Perltidy no tiene la capacidad de agregar o eliminar paréntesis de llamada porque es difícil de automatizar, por lo que los cambios deben hacerse manualmente. Al agregar o eliminar paréntesis, es esencial prestar atención a los problemas de precedencia de operadores. Por ejemplo, si se eliminan los paréntesis en la siguiente declaración, entonces "||" debe cambiarse a "or":

open( IN, "<", $infile ) || die("cannot open $infile:$!\n");

De lo contrario, "||" operará sobre $infile en lugar del valor de retorno de "open".

Uso de --dump-mismatched-args para encontrar llamadas a funciones con argumentos que no coinciden con las declaraciones de sub
El parámetro --dump-mismatched-args, o -dma, hace que perltidy examine las definiciones de subrutinas en un archivo y las llamadas a esos subs, e informe ciertas diferencias. Como todos los comandos --dump, escribe su informe en la salida estándar y sale inmediatamente. Por ejemplo 
perltidy -dma somefile.pl >results.txt

Se informan cuatro tipos de problemas, tipos a, o, u e i:

a: llamadas realizadas a un sub tanto con como sin el operador flecha
Por ejemplo, las siguientes dos líneas se informarían como una discrepancia: 
Fault();

y

$self->Fault();

Esto puede ser o no un error, pero vale la pena revisarlo. Podría convertirse en un error en el futuro si el sub "Fault" comienza a acceder a $self.

o: (overcount): el número de argumentos de llamada excede el número esperado.
u: (undercount): el número de argumentos de llamada es menor que el número esperado.
Por ejemplo 
sub gnab_gib {
    my $self=shift;
    my ($v1,$v2)=@_;
    ...
}
$self->gnab_gib(42);

En este caso, el sub espera un total de tres argumentos ($self, $v1 y $v2) pero solo recibe dos ($self y 42), por lo que se informa un recuento insuficiente. Esto no es necesariamente un error porque el sub puede permitir esta posibilidad, pero vale la pena revisarlo.

Aunque no es posible determinar automáticamente qué argumentos de sub son opcionales, si los argumentos de sub opcionales están entre un conjunto adicional de paréntesis, perltidy los tomará como una señal de que son opcionales y no emitirá una advertencia. Entonces, si el ejemplo anterior se escribe como

sub gnab_gib {
    my $self = shift;
    my ( $v1, ($v2) ) = @_;  # <-- $v2 is optional
    ...;
}

entonces perltidy considerará que el segundo argumento es opcional y no emitirá una advertencia para:

$self->gnab_gib(42);

Para múltiples argumentos de llamada predeterminados, coloque un conjunto de paréntesis alrededor de todos ellos. Algunos ejemplos:

my ( ($v1) ) = @_;              # <-- $v1 is optional
my ( $v1, ( $v2, $v3 ) ) = @_;  # <-- $v2, $v3 are optional
i: indeterminado: no se pudo determinar un número específico de argumentos esperados para un sub, pero se llama con un número específico. Este problema se informa para la opción --dump- pero no para la opción --warn-.

Notas y limitaciones:

  • Esta opción funciona mejor para subs que desempaquetan argumentos de llamada de manera ordenada al principio del sub desde @_ y/o con operaciones de "shift". También funcionará para el acceso directo a elementos específicos de la matriz @_. Sin embargo, si la codificación para la extracción de argumentos es compleja, el número de argumentos del sub se considerará indeterminado y no se podrá verificar un recuento.
  • No se verifican las llamadas a subs realizadas sin paréntesis alrededor de los argumentos.
  • No se verifican subs anónimos ni subs léxicos (introducidos con "my").
  • Solo se verifican las llamadas que parecen ser a subs definidos dentro del archivo que se está procesando. Pero tenga en cuenta que un archivo puede contener varios paquetes.
Uso de --warn-mismatched-args para producir una advertencia para llamadas a funciones con argumentos que no coinciden con las declaraciones de sub.
Esto es similar al parámetro -dump descrito anteriormente, excepto que cualquier discrepancia se informa en el archivo de errores y, de lo contrario, el formateo continúa normalmente. El uso básico es 
perltidy -wma somefile.pl

Hay varios controles complementarios disponibles para evitar mensajes de error no deseados:

  • --warn-mismatched-arg-types=s, o -wmat=s, se puede usar para seleccionar pruebas específicas, tipo a (prueba de flecha) o o (recuentos excesivos) o u (recuentos insuficientes). Se pueden solicitar todas las comprobaciones con -wmat='*' o -wmat=1. Este es el valor predeterminado.

    Para restringir la comprobación a un tipo específico de advertencia, establezca la cadena igual a la letra de esa advertencia, cualquiera de a, o o u. Por ejemplo

    perltidy -wmat='a o' somefile.pl

    formateará somefile.pl e informará cualquier discrepancia de tipo flecha y de recuento excesivo, pero omitirá las discrepancias de recuento insuficiente.

  • Se puede proporcionar --warn-mismatched-arg-exclusion-list, o -wmaxl=string, para omitir las comprobaciones de advertencia para una lista de nombres de subrutinas, ingresados como una cadena entre comillas de nombres separados por espacios o comas, sin un prefijo de paquete. Se omitirán todos los subs con esos nombres, independientemente del paquete. Se puede usar un * inicial y/o final en un nombre para indicar una coincidencia de cadena parcial.
  • Se puede usar --warn-mismatched-arg-undercount-cutoff=n, o -wmauc=n, para evitar advertencias de recuento insuficiente cuando el número esperado de argumentos es menor que n. Tenga en cuenta que este número n es el número de argumentos desde el punto de vista de la definición del sub, por lo que un objeto como $self pasado con un operador de flecha cuenta como un argumento.

    El valor predeterminado es n=4. Se ha descubierto que esto permite que la mayoría de los programas pasen sin advertencias, pero debería reducirse si es posible para una mejor verificación de errores. El valor mínimo posible de n necesario para evitar activar un error para un programa se puede determinar ejecutando con -wma -wmauc=0. Si hay errores de recuento insuficiente, una nota al final de la salida de error indica el valor de n necesario para evitar informarlos.

    Como se mencionó anteriormente para el parámetro --dump-mismatched-args, si los argumentos de llamada opcionales están entre paréntesis separados, perltidy los reconocerá como argumentos opcionales y evitará advertencias innecesarias. Si se utiliza este método, entonces se debe usar -wmauc=0 para una comprobación máxima.

  • Se puede usar --warn-mismatched-arg-overcount-cutoff=n, o -wmaoc=n, para evitar advertencias de recuento excesivo cuando el número esperado de argumentos es menor que n. El valor predeterminado es n=1. Esto evita mensajes de advertencia para subrutinas que son marcadores de posición ficticios para posible expansión.

Para ilustrar estos controles,

perltidy -wma -wmat='o u' -wmaxl='new old' -wmauc=2 somefile.pl

significa formatear somefile.pl como de costumbre y verificar recuentos excesivos y recuentos insuficientes que no coinciden, pero no flechas. Omitir la verificación de cualquier sub llamado "new" u "old", y solo advertir sobre recuentos insuficientes para subs que esperan más de 2 argumentos.

Uso de --dump-mismatched-returns para encontrar llamadas a funciones donde el número de valores solicitados puede diferir de las declaraciones de retorno de sub
El parámetro --dump-mismatched-returns, o -dmr, examina el lado de retorno de las declaraciones de llamada de sub. Como todos los comandos --dump, escribe su informe en la salida estándar y sale inmediatamente. Por ejemplo 
perltidy -dmr somefile.pl >results.txt

Se informan los siguientes tipos de problemas:

x: llamadas que solicitan un array de una subrutina sin sentencias return.
y: llamadas que solicitan un escalar de una subrutina sin sentencias return.
o: (overwant): llamadas que solicitan un array con un número de elementos que excede el número máximo devuelto por la subrutina.
u: (underwant): llamadas que solicitan un array con un número de elementos que está por debajo del máximo y que no coincide con un número devuelto por la subrutina.
s: llamadas que solicitan un escalar de una subrutina que solo devuelve dos o más elementos.
m: tamaños de array de retorno múltiples.

La mayoría de estos tipos de problemas se ilustran con el siguiente código

sub macho {
    ...
    ( $name, $flags ); # 2 valores pero sin sentencia 'return'
}
( $name, $flags ) = macho();  # 'x' (se desea array, pero no hay return)
$name = macho();              # 'y' (se desea escalar pero no hay return)
sub wimp {
    ...;
    return ( $name, $flags );  # 2 valores con sentencia 'return'
}
( $name, $flags, $access) = wimp(); # 'o' (se desea array 3 > 2)
($name) = wimp();                   # 'u' (se desea array 1 < 2)
$name   = wimp();  # 's' (se desea escalar pero se devuelven 2 valores)

El problema de tipo m ocurre cuando una subrutina tiene múltiples retornos de listas finitas con diferentes cantidades mayores que 1, y no todas ellas se corresponden con las llamadas. Por ejemplo:

sub find_libs {
    ...;
    return ( $libjava, $libjvm, $libhpi, $libawt );  # 4 elementos
    ...;
    return ( $libjava, $libawt );                    # 2 elementos
}
my ( $libjava, $libjvm, $libhpi, $libawt ) = find_libs();

Este análisis funciona escaneando todas las sentencias de llamada y todas las sentencias de retorno de subrutinas, y comparando el número de elementos solicitados con el número de elementos que se pueden devolver. Si no se puede determinar un valor específico para alguno de estos números para una llamada, entonces no se puede verificar.

Dado que solo se escanean las sentencias de retorno para obtener los valores de retorno, este análisis no será útil para la programación que se basa en el mecanismo de retorno predeterminado, como en la primera subrutina anterior. Tenga en cuenta que la política Perl::Critic RequireFinalReturn se puede usar para verificar código en esta situación.

Los problemas reportados no son necesariamente errores, pero podrían serlo, o podrían indicar código potencialmente confuso.

Usar --warn-mismatched-returns para emitir advertencias cuando el número de valores solicitados puede diferir de las sentencias de retorno de las subrutinas
Esto es similar al parámetro -dump descrito anteriormente, excepto que cualquier discrepancia se informa en el archivo de errores y, de lo contrario, el formato continúa normalmente. El uso básico es 
perltidy -wmr somefile.pl

Los siguientes controles complementarios están disponibles para evitar mensajes de error no deseados:

  • --warn-mismatched-return-types=string, o -wmrt=string, se puede usar para limitar las comprobaciones.

    Para restringir la comprobación, establezca la cadena igual a la(s) letra(s) de esa advertencia, cualquier x, y, o, u, o s. Por ejemplo

    perltidy -wmr -wmrt='x o s' somefile.pl

    formateará somefile.pl e informará los tipos de problemas x, o y s, pero no los tipos u y y. Se pueden solicitar todas las comprobaciones con -wmrt='*' o -wmrt=1. Este es el valor predeterminado si este parámetro no se especifica.

  • --warn-mismatched-return-exclusion-list, o -wmrxl=string, se puede proporcionar para omitir las comprobaciones de advertencia para una lista de nombres de subrutinas, ingresados como una cadena entre comillas de nombres separados por espacios o comas, sin prefijo de paquete. Todas las subrutinas con esos nombres se omitirán, independientemente del paquete. Se puede usar un * inicial y/o final en un nombre para indicar una coincidencia de cadena parcial.
Usar --dump-nested-ternaries para volcar una lista de ternarios anidados.
Al igual que otros comandos -dump-, esto escribe en la salida estándar y luego sale inmediatamente, sin realizar ningún formato. Una sentencia ternaria tiene la forma 
Condicion ? Valor_si_verdadero : Valor_si_falso

Si el término "Valor_si_verdadero" es en sí mismo un ternario, entonces ese ternario está anidado un nivel más profundo. Los ternarios anidados son relativamente fáciles de crear pero pueden ser tediosos de leer. Y a veces se pueden reescribir de una manera más simple.

Este parámetro comprueba la profundidad de anidamiento de cada ternario en un script y, si no es cero, entonces su número de línea y profundidad de anidamiento se enumeran en la salida. La lista puede limitarse a ternarios con una profundidad mayor que un valor determinado con el siguiente parámetro.

Usar --nested-ternary-maximum-depth=n para ignorar ternarios anidados hasta una profundidad de n o menos.
Las sentencias ternarias con una profundidad menor o igual a n son ignoradas por --dump-nested-ternaries y su compañero --warn-nested-ternaries. El valor predeterminado n=0 hará que se listen todos los ternarios anidados. Un valor n=1, por ejemplo, hará que los ternarios con una profundidad de 0 o 1 sean ignorados por estos comandos.
Usar --warn-nested-ternaries para escribir una advertencia cuando se encuentra un ternario anidado.
Esto es lo mismo que el parámetro -dump descrito anteriormente, excepto que cualquier ternario anidado se informa en el archivo de errores y el formato continúa normalmente.

Comentarios adicionales sobre ternarios anidados:

  • La profundidad de anidamiento de un ternario arbitrario se puede encontrar escribiendo una lista de solo los símbolos de "?" y ":" de toda la expresión, junto con cualquier corchete contenedor que encierre completamente alguno de ellos. Luego, la profundidad de anidamiento del "?" que introduce un ternario es el número de símbolos de "?" que lo preceden inmediatamente. Por ejemplo, para esta sentencia que da el máximo de tres valores 
    $a > $b ? $a > $c ? $a : $c : $b > $c ? $b : $c;

    obtenemos

    ? ? : : ? :

    Dado que hay una secuencia de dos símbolos "?" adyacentes, la profundidad máxima de anidamiento es 1.

  • Los paréntesis alrededor de un término hacen que su profundidad se restablezca a cero. Los paréntesis pueden ser para una llamada a función, o solo para agrupación. Por lo tanto, una forma de evitar una advertencia para un ternario determinado es introducir paréntesis. Por ejemplo, modificando el ejemplo anterior para que sea 
    $a > $b ? ( $a > $c ? $a : $c ) : $b > $c ? $b : $c;

    obtenemos

    ? ( ? : ) : ? :

    En este caso, no hay símbolos "?" adyacentes, por lo que la profundidad de anidamiento es cero.

Trabajar con MakeMaker, AutoLoader y SelfLoader

La primera línea $VERSION de un archivo que podría ser evaluado por MakeMaker se pasa sin cambios excepto por la indentación. El valor predeterminado --pass-version-line, o -pvl, es hacer esto. Use --nopass-version-line, o -npvl, para desactivar esta característica.

Si se usa el módulo AutoLoader, perltidy continuará formateando el código después de ver una línea __END__. El valor predeterminado --look-for-autoloader, o -lal, es hacer esto. Use --nolook-for-autoloader, o -nlal, para desactivar esta característica.

Del mismo modo, si se usa el módulo SelfLoader, perltidy continuará formateando el código después de ver una línea __DATA__. El valor predeterminado --look-for-selfloader, o -lsl, es hacer esto. Use --nolook-for-selfloader, o -nlsl, para desactivar esta característica.

OPCIONES HTML

El interruptor maestro -html
El indicador -html hace que perltidy escriba un archivo html con extensión .html. Por lo tanto, por ejemplo, el siguiente comando 
perltidy -html somefile.pl

producirá un archivo html con color de sintaxis llamado somefile.pl.html que se puede ver con un navegador.

Nota: En este caso, perltidy no realiza ningún formato en el archivo de entrada y no escribe un archivo formateado con la extensión .tdy. Esto significa que se requieren dos ejecuciones de perltidy para crear una copia html completamente reformateada de un script.

El indicador -pre para fragmentos de código
Cuando se proporciona el indicador -pre, solo se generará la sección preformateada, dentro de las etiquetas "<PRE"> y "</PRE">. Esto simplifica la inclusión de la salida en otros archivos. El valor predeterminado es generar una página web completa.
El indicador -nnn para numeración de líneas
Cuando se proporciona el indicador -nnn, las líneas de salida se numerarán.
El indicador -toc, o --html-table-of-contents
Por defecto, se escribirá una tabla de contenidos de paquetes y subrutinas al principio de la salida html. Use -ntoc para evitar esto. Esto podría ser útil, por ejemplo, para un documento pod que contiene una serie de fragmentos de código no relacionados. Este indicador solo influye en la tabla de contenidos del código; no tiene ningún efecto en ninguna tabla de contenidos producida por pod2html (ver siguiente elemento).
El indicador -pod, o --pod2html
Hay dos opciones para formatear la documentación pod. El valor predeterminado es pasar el pod a través del módulo Pod::Html (que forma la base de la utilidad pod2html). Cualquier sección de código es formateada por perltidy, y los resultados luego se fusionan. Nota: perltidy crea un archivo temporal cuando se usa Pod::Html; ver "FILES". Además, Pod::Html crea archivos temporales para su caché.
