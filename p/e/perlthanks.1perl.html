NOMBRE

perlbug - cómo enviar informes de errores sobre Perl

perlthanks

DESCRIPCIÓN

Este programa está diseñado para ayudarte a generar informes de errores (y notas de agradecimiento) sobre perl5 y los módulos que vienen con él.

En la mayoría de los casos, puedes ejecutarlo interactivamente desde la línea de comandos sin argumentos especiales y seguir las indicaciones.

Si has encontrado un error en un puerto no estándar (uno que no formaba parte de la distribución estándar), una distribución binaria, o un módulo no principal (como Tk, DBI, etc.), por favor, consulta la documentación que vino con esa distribución para determinar el lugar correcto para reportar errores.

Los informes de errores deben enviarse al rastreador de incidencias de GitHub en https://github.com/Perl/perl5/issues. La dirección perlbug@perl.org ya no abre tickets automáticamente. Puedes usar esta herramienta para redactar tu informe y guardarlo en un archivo que luego podrás enviar al rastreador de incidencias.

En casos extremos, perlbug puede no funcionar lo suficientemente bien en tu sistema para guiarte en la redacción de un informe de error. En esos casos, puede que puedas usar perlbug -d o perl -V para obtener información de configuración del sistema para incluirla en tu informe de incidencia.

Al informar de un error, por favor, repasa esta lista de verificación:

¿Qué versión de Perl estás ejecutando?
Escribe "perl -v" en la línea de comandos para averiguarlo.
¿Estás ejecutando la última versión liberada de perl?
Consulta http://www.perl.org/ para averiguarlo. Si no usas la última versión liberada, por favor, intenta reproducir tu error en la última versión estable.

Ten en cuenta que los informes sobre errores en versiones antiguas de Perl, especialmente aquellos que indican que no has probado tampoco la versión estable actual de Perl, probablemente recibirán menos atención de los voluntarios que construyen y mantienen Perl que los informes sobre errores en la versión actual.

¿Estás seguro de que lo que has encontrado es un error?
Un número significativo de los informes de errores que recibimos resultan ser características documentadas de Perl. Asegúrate de que el problema que has encontrado no es intencional consultando la documentación que viene con la distribución de Perl.

Dado el gran volumen de documentación de Perl, esto no es una tarea trivial, pero si puedes señalar documentación que sugiera que el comportamiento que estás viendo es incorrecto, es probable que tu incidencia reciba más atención. Puede que quieras empezar con perldoc perltrap para obtener punteros a las trampas comunes en las que caen los programadores de Perl nuevos (y experimentados).

Si no estás seguro del significado de un mensaje de error que has encontrado, consulta perldoc perldiag para obtener una explicación. Si el mensaje no está en perldiag, probablemente no lo genera Perl. Puede que tengas suerte consultando la documentación de tu sistema operativo en su lugar.

Si estás en una plataforma no UNIX, consulta perldoc perlport, ya que algunas características pueden no estar implementadas o funcionar de manera diferente.

Puede que puedas averiguar qué está fallando usando el depurador de Perl. Para obtener información sobre cómo usar el depurador, consulta perldoc perldebug.

¿Tienes un caso de prueba adecuado?
Cuanto más fácil sea reproducir tu error, más probable será que se corrija: si nadie puede duplicar tu problema, probablemente no se abordará.

Un buen caso de prueba tiene la mayoría de estos atributos: código corto y simple; pocas dependencias de comandos externos, módulos o bibliotecas; código que no dependa de la plataforma (a menos que sea un error específico de la plataforma); documentación clara y simple.

Un buen caso de prueba es casi siempre un buen candidato para ser incluido en el conjunto de pruebas de Perl. Si tienes tiempo, considera escribir tu caso de prueba de manera que pueda incluirse fácilmente en el conjunto de pruebas estándar.

¿Has incluido toda la información relevante?
Asegúrate de incluir los mensajes de error **exactos**, si los hay. "Perl dio un error" no es un mensaje de error exacto.

Si obtienes un volcado de núcleo (o equivalente), puedes usar un depurador (dbx, gdb, etc.) para producir un rastreo de pila para incluirlo en el informe de error.

NOTA: a menos que tu Perl haya sido compilado con información de depuración (a menudo -g), es probable que el rastreo de pila sea algo difícil de usar, ya que muy probablemente contendrá solo los nombres de las funciones y no sus argumentos. Si es posible, recompila tu Perl con información de depuración y reproduce el bloqueo y el rastreo de pila.

¿Puedes describir el error en lenguaje claro?
Cuanto más fácil sea entender un error reproducible, más probable será que se corrija. Cualquier información que puedas proporcionar sobre el problema ayudará mucho. En otras palabras, intenta analizar el problema (hasta donde puedas) e informa de tus hallazgos.
¿Puedes corregir el error tú mismo?
Si es así, ¡excelente noticia! Los informes de errores con parches probablemente recibirán mucha más atención e interés que los que no los tienen. Por favor, envía tu parche a través del flujo de trabajo de Solicitud de Extracción de GitHub como se describe en perldoc perlhack. También puedes enviar parches a perl5-porters@perl.org. Al enviar un parche, créalo usando "git format-patch" si es posible, aunque un diff unificado creado con "diff -pu" servirá casi igual de bien.

Tu parche puede ser devuelto con solicitudes de cambios, o solicitudes de explicaciones más detalladas sobre tu corrección.

Aquí tienes algunos consejos para crear parches de alta calidad:

Asegúrate de que el parche no esté invertido (el primer argumento de diff suele ser el archivo original, el segundo tu archivo modificado). Asegúrate de probar tu parche aplicándolo con "git am" o el programa "patch" antes de enviarlo. Intenta seguir el mismo estilo que el código que estás intentando parchear. Asegúrate de que tu parche realmente funcione ("make test", si lo que estás parcheando está cubierto por el conjunto de pruebas de Perl).

¿Puedes usar "perlbug" para enviar una nota de agradecimiento?
Sí, puedes hacerlo utilizando la opción "-T", o invocando el programa como "perlthanks". Las notas de agradecimiento son buenas. Hacen sonreír a la gente.

Por favor, haz que el título de tu incidencia sea informativo. "un error" no es informativo. Tampoco lo es "perl se bloquea" ni "¡¡¡AYUDA!!!". Esto no ayuda. Una descripción concisa de lo que está mal está bien.

Habiendo hecho tu parte, prepárate para esperar, para que te digan que el error está en tu código, o posiblemente para no recibir ninguna respuesta. Los voluntarios que mantienen Perl están ocupados, así que si tu problema es un error obvio en tu propio código, es difícil de entender o es un duplicado de un informe existente, puede que no recibas una respuesta personal.

Si es importante para ti que tu error se corrija, monitoriza el rastreador de incidencias (te suscribirás a las notificaciones de las incidencias que envíes o en las que comentes) y los registros de confirmación de las versiones de desarrollo de Perl, y anima a los mantenedores con palabras amables u ofertas de bebidas frías. OPCIONES

-a
Dirección a la que enviar el informe en lugar de guardarlo en un archivo.
-b
Cuerpo del informe. Si no se incluye en la línea de comandos, o en un archivo con -f, tendrás la oportunidad de editar el informe.
-C
No enviar copia al administrador cuando se envíe el informe por correo.
-c
Dirección a la que enviar copia del informe cuando se envíe el informe por correo. Por defecto, la dirección del administrador local de perl (registrada cuando se compiló perl).
-d
Modo de datos (el predeterminado si rediriges o canalizas la salida). Esto imprime tus datos de configuración, sin guardar ni enviar nada por correo. Puedes usar esto con -v para obtener datos más completos.
-e
Editor a usar.
-f
Archivo que contiene el cuerpo del informe. Úsalo para enviar rápidamente un informe preparado.
-F
Archivo de salida para los resultados. Por defecto, es perlbug.rep.
-h
Imprime un breve resumen de las opciones.
-ok
Informa de la compilación exitosa en este sistema a los porteros de perl. Fuerza -S y -C. Fuerza y proporciona valores para -s y -b. Solo solicita una dirección de respuesta si no puede adivinarla (para usar con make). Respeta la dirección de respuesta especificada con -r. Puedes usar esto con -v para obtener datos más completos. Solo crea un informe si este sistema tiene menos de 60 días de antigüedad.
-okay
Igual que -ok, excepto que informará sobre sistemas más antiguos.
-nok
Informa de la compilación fallida en este sistema. Fuerza -C. Fuerza y proporciona un valor para -s, luego te pide que edites el informe y digas qué salió mal. Alternativamente, se puede proporcionar un informe preparado usando -f. Solo solicita una dirección de respuesta si no puede adivinarla (para usar con make). Respeta la dirección de respuesta especificada con -r. Puedes usar esto con -v para obtener datos más completos. Solo crea un informe si este sistema tiene menos de 60 días de antigüedad.
-nokay
Igual que -nok, excepto que informará sobre sistemas más antiguos.
-p
Los nombres de uno o más archivos de parches u otros archivos adjuntos de texto para incluir con el informe. Los archivos múltiples deben estar separados por comas.
-r
Tu dirección de respuesta. El programa te pedirá que confirmes su valor predeterminado si no usas esta opción.
-S
Guarda o envía el informe sin pedir confirmación.
-s
Asunto a incluir con el informe. Se te pedirá si no proporcionas uno en la línea de comandos.
-t
Modo de prueba. Permite comandar perlbug desde una tubería o un archivo, para fines de prueba.
-T
Envía una nota de agradecimiento en lugar de un informe de error.
-v
Incluye datos de configuración detallados en el informe.
