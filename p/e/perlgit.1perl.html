PERLGIT(1perl) Guía de Referencia para Programadores de Perl PERLGIT(1perl)

NOMBRE

perlgit - Información detallada sobre git y el repositorio de Perl

DESCRIPCIÓN

Este documento proporciona detalles sobre el uso de git para desarrollar Perl. Si sólo te interesa trabajar en un parche rápido, consulta perlhack primero. Este documento está destinado a personas que son colaboradores habituales de Perl, incluyendo a aquellos con acceso de escritura al repositorio de git.

CLONANDO EL REPOSITORIO

Todo el código fuente de Perl se mantiene centralmente en un repositorio de Git en github.com.

Puedes hacer un clon de sólo lectura del repositorio ejecutando:

% git clone git@github.com:Perl/perl5.git perl

Si no puedes usar eso por razones de firewall, también puedes clonar vía http:

% git clone https://github.com/Perl/perl5.git perl

TRABAJANDO CON EL REPOSITORIO

Una vez que hayas entrado en el directorio del repositorio, puedes inspeccionarlo. Después de un clon, el repositorio contendrá una única rama local, que también será la rama actual, como indica el asterisco.

% git branch
* blead

Usando el modificador -a para "branch" también mostrará las ramas de seguimiento remoto en el repositorio:

% git branch -a
* blead
  origin/HEAD
  origin/blead
...

Las ramas que empiezan con "origin" corresponden al "git remote" del que clonaste (que se llama "origin"). Cada rama en el remoto será seguida exactamente por estas ramas. NUNCA debes trabajar en estas ramas de seguimiento remoto. Sólo trabajas en una rama local. Las ramas locales pueden configurarse para fusionar automáticamente (al hacer pull) desde una rama de seguimiento remoto designada. Este es el caso de la rama predeterminada "blead", que se configurará para fusionar desde la rama de seguimiento remoto "origin/blead".

Puedes ver commits recientes:

% git log

Y traer nuevos cambios del repositorio, y actualizar tu repositorio local (debe estar limpio primero)

% git pull

Asumiendo que estamos en la rama "blead" inmediatamente después de un pull, este comando sería más o menos equivalente a:

% git fetch
% git merge origin/blead

De hecho, si quieres actualizar tu repositorio local sin tocar tu directorio de trabajo, haces:

% git fetch

Y si quieres actualizar tus ramas de seguimiento remoto para todos los remotos definidos simultáneamente, puedes hacer

% git remote update

Ninguno de estos dos últimos comandos actualizará tu directorio de trabajo, sin embargo, ambos actualizarán las ramas de seguimiento remoto en tu repositorio.

Para crear una rama local de una rama remota:

% git checkout -b maint-5.10 origin/maint-5.10

Para volver a blead:

% git checkout blead

Cómo averiguar tu estado

El comando git más común que probablemente usarás será

% git status

Este comando producirá como salida una descripción del estado actual del repositorio, incluyendo archivos modificados y archivos no rastreados no ignorados, y además mostrará cosas como qué archivos se han preparado para el próximo commit, y usualmente alguna información útil sobre cómo cambiar las cosas. Por ejemplo, lo siguiente:

% git status
On branch blead
Your branch is ahead of 'origin/blead' by 1 commit.
Changes to be committed:
  (use "git reset HEAD <file>..." to unstage)
      modified:   pod/perlgit.pod
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git checkout -- <file>..." to discard changes in working
                                                             directory)
      modified:   pod/perlgit.pod
Untracked files:
  (use "git add <file>..." to include in what will be committed)
      deliberate.untracked

Esto muestra que hubo cambios en este documento preparados para commit, y que hubo cambios adicionales en el directorio de trabajo aún no preparados. También muestra que había un archivo no rastreado en el directorio de trabajo, y como puedes ver muestra cómo cambiar todo esto. También muestra que hay un commit en la rama de trabajo "blead" que aún no se ha subido al remoto "origin". **NOTA**: Esta salida es también lo que ves como plantilla si no proporcionas un mensaje a "git commit".

Flujo de trabajo de parches

Primero, por favor lee perlhack para detalles sobre cómo hackear el core de Perl. Ese documento cubre muchos detalles sobre cómo crear un buen parche.

Si ya tienes un repositorio de Perl, deberías asegurarte de que estás en la rama blead, y que tu repositorio está actualizado:

% git checkout blead
% git pull

Es preferible parchear contra la última versión de blead, ya que es aquí donde ocurre el nuevo desarrollo para todos los cambios que no sean correcciones de errores críticos. Los parches de corrección de errores críticos deben hacerse contra las ramas maint relevantes, o deben enviarse con una nota que indique todas las ramas a las que se debe aplicar la corrección.

Ahora que tenemos todo actualizado, necesitamos crear una nueva rama temporal para estos cambios y cambiarnos a ella:

% git checkout -b orange

que es la forma corta de

% git branch orange
% git checkout orange

Crear una rama de tema facilita que los mantenedores hagan rebase o fusionen de vuelta a blead maestro para un historial más lineal. Si no trabajas en una rama de tema, el mantenedor tiene que seleccionar manualmente tus cambios en blead antes de que puedan ser aplicados.

Eso te hará ser regañado en perl5-porters, así que no lo hagas. Sé Genial.

Luego haz tus cambios. Por ejemplo, si Leon Brocard cambia su nombre a Orange Brocard, deberíamos cambiar su nombre en el archivo AUTHORS:

% perl -pi -e 's{Leon Brocard}{Orange Brocard}' AUTHORS

Puedes ver qué archivos se han modificado:

% git status
On branch orange
Changes to be committed:
  (use "git reset HEAD <file>..." to unstage)
   modified:   AUTHORS

Y puedes ver los cambios:

% git diff
diff --git a/AUTHORS b/AUTHORS
index 293dd70..722c93e 100644
--- a/AUTHORS
+++ b/AUTHORS
@@ -541,7 +541,7 @@    Lars Hecking              <lhecking@nmrc.ucc.ie>

+Orange Brocard                 <acme@astray.com>

Ahora guarda tu cambio localmente:

% git commit -a -m 'Cambiar el nombre de Leon Brocard a Orange Brocard'
Created commit 6196c1d: Rename Leon Brocard to Orange Brocard
 1 files changed, 1 insertions(+), 1 deletions(-)

El modificador "-a" se usa para incluir todos los archivos que git rastrea y que has modificado. Si en este momento, sólo quieres confirmar algunos de los archivos en los que has trabajado, puedes omitir "-a" y usar el comando "git add FILE ..." antes de hacer el commit. "git add --interactive" te permite incluso confirmar sólo porciones de archivos en lugar de todos los cambios en ellos.

El modificador "-m" se usa para especificar el mensaje del commit. Si lo omites, git abrirá un editor de texto para que compongas el mensaje interactivamente. Esto es útil cuando los cambios son más complejos que el ejemplo dado aquí, y, dependiendo del editor, saber que la primera línea del mensaje del commit no excede el máximo legal de 50 caracteres. Ver "Mensaje de commit" en perlhack para más información sobre qué hace que un mensaje de commit sea bueno.

Una vez que hayas terminado de escribir tu mensaje de commit y hayas salido de tu editor, git escribirá tu cambio en el disco y te dirá algo como esto:

Created commit daf8e63: explain git status and stuff about remotes
 1 files changed, 83 insertions(+), 3 deletions(-)

Conceptos básicos de Git

Si alguna vez te encuentras en una situación embarazosa, por ejemplo, si no estás seguro de si tus cambios han sido commitidos, o si solo has introducido una parte de los cambios que esperabas, puedes usar el comando "git status". Deberías ver algo como esto:

% git status
On branch orange
Untracked files:
  (use "git add <file>..." to include in what will be committed)
      deliberate.untracked
nothing added to commit but untracked files present (use "git add" to
                                                                 track)

En caso de duda, antes de hacer cualquier otra cosa, comprueba tu estado y léelo atentamente, muchas preguntas se responden directamente en la salida de "git status".

Puedes examinar tu último commit con:

% git show HEAD

Y si no estás contento ni con la descripción ni con el parche en sí, puedes arreglarlo editando los archivos una vez más y luego emitiendo:

% git commit -a --amend

Ahora, crea un fork en GitHub para empujar tu rama, y añádelo como un remoto si aún no lo has hecho, como se describe en la documentación de GitHub en https://help.github.com/en/articles/working-with-forks:

% git remote add fork git@github.com:MyUser/perl5.git

Y empuja la rama a tu fork:

% git push -u fork orange

Ahora deberías enviar una Solicitud de Extracción (PR) en GitHub desde la nueva rama a blead. Para más información, consulta la documentación de GitHub en https://help.github.com/en/articles/creating-a-pull-request-from-a-fork.

También puedes enviar archivos de parche a perl5-porters@perl.org perl5-porters@perl.org directamente si el parche no está listo para ser aplicado, pero está destinado a la discusión.

Para crear un archivo de parche para todos tus cambios locales:

% git format-patch -M blead..
0001-Rename-Leon-Brocard-to-Orange-Brocard.patch

O para muchos cambios, por ejemplo, desde una rama temática:

% git format-patch --stdout -M blead.. > topic-branch-changes.patch

Si deseas eliminar tu rama temporal, puedes hacerlo con:

% git checkout blead
% git branch -d orange
error: The branch 'orange' is not an ancestor of your current HEAD.
If you are sure you want to delete it, run 'git branch -D orange'.
% git branch -D orange
Deleted branch orange.

Una nota sobre archivos derivados

Ten en cuenta que muchos archivos de la distribución son derivados; evita parchearlos, ya que git no verá los cambios en ellos y el proceso de compilación los sobrescribirá. Parchea los originales en su lugar. La mayoría de las utilidades (como perldoc) están en esta categoría, es decir, parchea utils/perldoc.PL en lugar de utils/perldoc. Del mismo modo, no crees parches para archivos bajo $src_root/ext a partir de sus copias encontradas en $install_root/lib. Si no estás seguro sobre la ubicación correcta de un archivo que puede haber sido copiado durante la compilación de la distribución fuente, consulta el MANIFEST.

Limpieza de un directorio de trabajo

El comando "git clean" puede usarse, con argumentos variables, como reemplazo de "make clean".

Para restablecer tu directorio de trabajo a un estado prístino, puedes hacer:

% git clean -dxf

Sin embargo, ten en cuenta que esto eliminará TODO el contenido no rastreado. Puedes usar

% git clean -Xf

para eliminar todos los archivos no rastreados ignorados, como subproductos de compilación y prueba, pero dejar intactos los archivos creados manualmente.

Si solo deseas cancelar algunas ediciones no commitidas, puedes usar "git checkout" y darle una lista de archivos a revertir, o "git checkout -f" para revertirlos todos.

Si deseas cancelar uno o varios commits, puedes usar "git reset".

Bisecting

"git" proporciona una forma integrada para determinar qué commit debe culparse por introducir un error determinado. "git bisect" realiza una búsqueda binaria en el historial para localizar el primer commit que falla. Es rápido, potente y flexible, pero requiere cierta configuración y para automatizar el proceso se necesita un script auxiliar de shell.

El núcleo proporciona un programa envoltorio, Porting/bisect.pl, que intenta simplificarlo al máximo, haciendo que el bisecting sea tan simple como ejecutar un one-liner de Perl. Por ejemplo, si quieres saber cuándo esto se convirtió en un error:

perl -e 'my $x := 2'

simplemente ejecutas esto:

.../Porting/bisect.pl -e 'my $x := 2;'

Usando Porting/bisect.pl, con un solo comando (y ningún otro archivo) es fácil averiguar

  • ¿Qué commit causó que este código de ejemplo fallara?
  • ¿Qué commit hizo que este código de ejemplo empezara a funcionar?
  • ¿Qué commit añadió el primer archivo que coincide con esta expresión regular?
  • ¿Qué commit eliminó el último archivo que coincide con esta expresión regular?

generalmente sin necesidad de saber qué versiones de perl usar como revisiones de inicio y fin, ya que Porting/bisect.pl busca automáticamente para encontrar la versión estable más temprana para la que el caso de prueba pasa. Ejecuta "Porting/bisect.pl --help" para la documentación completa, incluyendo cómo configurar las opciones de "Configure" y de tiempo de compilación.

Si requieres más flexibilidad de la que ofrece Porting/bisect.pl, necesitarás ejecutar "git bisect" tú mismo. Es muy útil usar "git bisect run" para automatizar la compilación y prueba de revisiones de Perl. Para esto necesitarás un script de shell para que "git" llame para probar una revisión particular. Un script de ejemplo es Porting/bisect-example.sh, que debes copiar **fuera** del repositorio, ya que el proceso de bisect reiniciará el estado a un checkout limpio mientras se ejecuta. Las instrucciones a continuación asumen que lo copiaste como ~/run y luego lo editaste según corresponda.

Primero entras en modo bisect con:

% git bisect start

Por ejemplo, si el error está presente en "HEAD" pero no lo estaba en 5.10.0, "git" lo aprenderá cuando ingreses:

% git bisect bad
% git bisect good perl-5.10.0
Bisecting: 853 revisions left to test after this

Esto resulta en el checkout del commit mediano entre "HEAD" y "perl-5.10.0". Luego puedes ejecutar el proceso de bisect con:

% git bisect run ~/run

Cuando el primer commit defectuoso se aísla, "git bisect" te lo dirá:

ca4cfd28534303b82a216cfe83a1c80cbc3b9dc5 is first bad commit
commit ca4cfd28534303b82a216cfe83a1c80cbc3b9dc5
Author: Dave Mitchell <davem@fdisolutions.com>
Date:   Sat Feb 9 14:56:23 2008 +0000
    [perl #49472] Attributes + Unknown Error
    ...
bisect run success

Puedes echar un vistazo al proceso de bisect con "git bisect log" y "git bisect visualize". "git bisect reset" te sacará del modo bisect.

Ten en cuenta que el primer estado "bueno" debe ser un ancestro del primer estado "malo". Si deseas buscar el commit que *resolvió* algún error, debes negar tu caso de prueba (es decir, salir con 1 si está OK y 0 si no) y aun así marcar el límite inferior como "bueno" y el superior como "malo". El "primer commit malo" debe entonces entenderse como el "primer commit donde el error se resuelve".

"git help bisect" tiene mucha más información sobre cómo puedes ajustar tus búsquedas binarias.

Después del bisección, es posible que desees configurar, compilar y probar Perl en los commits identificados por el proceso de bisección. A veces, particularmente con versiones antiguas de Perl, "make" puede fallar durante este proceso. En ese caso, es posible que puedas parchear el código fuente en el punto del commit antiguo. Para hacerlo, sigue las sugerencias proporcionadas en "Building perl at older commits" en perlhack.

Ramas temáticas y reescritura del historial

Los confirmantes individuales deben crear ramas temáticas bajo tunombre/un-nombre-descriptivo:

% branch="$yourname/$some_descriptive_name"
% git checkout -b $branch
... haz ediciones locales, commits, etc ...
% git push origin -u $branch

Si te quedas atascado con una versión antigua de git (anterior a 1.7), entonces "git push" no tendrá el interruptor "-u", y deberás reemplazar el último paso con la siguiente secuencia:

% git push origin $branch:refs/heads/$branch
% git config branch.$branch.remote origin
% git config branch.$branch.merge refs/heads/$branch

Si deseas hacer cambios en la rama temática de otra persona, debes consultar con su creador antes de hacer cualquier cambio en ella.

A veces puedes encontrar que el autor original ha editado el historial de la rama. Hay muchas buenas razones para esto. A veces, un autor puede simplemente estar rebasando la rama a un punto fuente más reciente. A veces, un autor puede haber encontrado un error en un commit temprano que quería corregir antes de fusionar la rama a blead.

Actualmente, el repositorio maestro está configurado para prohibir fusiones no fast-forward. Esto significa que las ramas internas no pueden ser rebasadas y empujadas como un solo paso.

La única forma en que se te permitirá rebasar o modificar el historial de una rama empujada es eliminarla y empujarla como una nueva versión de ella. Por favor, piensa cuidadosamente antes de hacer esto. Podría ser mejor renombrar secuencialmente tus ramas para que sea más fácil para otros que trabajan contigo extraer sus cambios locales a la nueva versión. (XXX: necesita explicación).

Si deseas rebasar una rama temática personal, tendrás que eliminar tu rama temática existente y empujarla como una nueva versión de ella. Puedes hacer esto a través de la siguiente fórmula (ver la explicación sobre "refspec" en la documentación de git push para más detalles) después de haber rebasado tu rama:

# primero rebase
% git checkout $user/$topic
% git fetch
% git rebase origin/blead
# el
n "eliminar-y-empujar" % git push origin :$user/$topic % git push origin $user/$topic

NOTA: Está prohibido a nivel de repositorio eliminar cualquiera de las ramas "primarias". Es decir, cualquier rama que coincida con "m!^(blead|maint|perl)!". Cualquier intento de hacerlo resultará en que git produzca un error como este:

% git push origin :blead
*** Está prohibido eliminar las ramas blead/maint en este repositorio
error: hooks/update salió con código de error 1
error: hook rechazó actualizar refs/heads/blead
To ssh://perl5.git.perl.org/perl
 ! [remoto rechazado] blead (hook rechazado)
 error: no se pudieron empujar algunas refs a 'ssh://perl5.git.perl.org/perl'

Como cuestión de política, no editamos el historial de las ramas blead y maint-*. Si un error tipográfico (o algo peor) se cuela en un commit a blead o maint-*, lo corregiremos en otro commit. Los únicos tipos de actualizaciones permitidas en estas ramas son los "fast-forwards", donde se conserva todo el historial.

Las etiquetas anotadas en el repositorio canónico perl.git nunca serán eliminadas ni modificadas. Piensa mucho si quieres empujar una etiqueta local a perl.git antes de hacerlo. (Empujar etiquetas simples no está permitido).

Grafts

El historial de perl contiene un error que no se detectó en la conversión: se registró una fusión en el historial entre blead y maint-5.10 donde en realidad no ocurrió ninguna fusión. Debido a la naturaleza de git, ahora es imposible corregir esto en el repositorio público. Puedes eliminar esta fusión errónea localmente agregando la siguiente línea a tu archivo ".git/info/grafts":

296f12bbbbaa06de9be9d09d3dcf8f4528898a49 434946e0cb7a32589ed92d18008aaa1d88515930

Es particularmente importante tener esta línea de graft si se realiza alguna operación de 'bisect' en el área de la "fusión" en cuestión.

ACCESO DE ESCRITURA AL REPOSITORIO GIT

Una vez que tengas acceso de escritura, necesitarás modificar la URL del remoto 'origin' para permitir el empuje. Edita .git/config con el comando git-config(1):

% git config remote.origin.url git@github.com:Perl/perl5.git

También puedes configurar tu nombre de usuario y dirección de correo electrónico. La mayoría de las personas lo hacen una vez de forma global en su ~/.gitconfig haciendo algo como:

% git config --global user.name "Ævar Arnfjörð Bjarmason"
% git config --global user.email avarab@gmail.com

Sin embargo, si deseas anular esto solo para perl, ejecuta algo como lo siguiente en perl:

% git config user.email avar@cpan.org

También es posible mantener "origin" como un remoto de git y agregar un nuevo remoto para acceso ssh:

% git remote add camel git@github.com:Perl/perl5.git

Esto te permite actualizar tu repositorio local trayendo cambios de "origin", lo cual es más rápido y no requiere autenticación, y empujar tus cambios de vuelta con el remoto "camel":

% git fetch camel
% git push camel

El comando "fetch" solo actualiza las refs de "camel", ya que los objetos en sí deberían haber sido traídos al hacer pull de "origin".

Trabajar con pull requests de GitHub

Los pull requests normalmente se originan fuera del repositorio "Perl/perl.git", por lo que si deseas probarlos o trabajar con ellos localmente, un simple "git fetch" del repositorio "Perl/perl5.git" no los traerá.

Sin embargo, GitHub proporciona un mecanismo para traer un pull request a una rama local. Están disponibles en los remotos de GitHub bajo "pull/", por lo que puedes usar "git fetch pull/PRID/head:nombrelocal" para hacer una copia local. Por ejemplo, para traer el pull request 9999 a la rama local "nombre-rama-local" ejecuta:

git fetch origin pull/9999/head:nombre-rama-local

y luego:

git checkout nombre-rama-local

Nota: esta rama no está rebasada sobre "blead", por lo que en lugar del checkout anterior, podrías querer:

git rebase origin/blead nombre-rama-local

lo que rebasa "nombre-rama-local" sobre "blead", y la extrae.

Alternativamente, puedes configurar el remoto para traer todos los pull requests como ramas de seguimiento remoto. Para hacer esto, edita el remoto en .git/config, por ejemplo, si tu remoto de GitHub es "origin" tendrías:

[remote "origin"]
        url = git@github.com:/Perl/perl5.git
        fetch = +refs/heads/*:refs/remotes/origin/*

Agrega una línea para mapear las ramas de pull request remotas a ramas de seguimiento remoto:

[remote "origin"]
        url = git@github.com:/Perl/perl5.git
        fetch = +refs/heads/*:refs/remotes/origin/*
        fetch = +refs/pull/*/head:refs/remotes/origin/pull/*

y luego haz un fetch como de costumbre:

git fetch origin

Esto creará una rama de seguimiento remoto para cada pull request, incluidas las solicitudes cerradas.

Para eliminar esas ramas de seguimiento remoto, elimina la línea agregada arriba y haz un prune:

git fetch -p origin # o git remote prune origin

Aceptar un parche

Si has recibido un archivo de parche generado usando la sección anterior, deberías probar el parche.

Primero necesitamos crear una nueva rama temporal para estos cambios y cambiarnos a ella:

% git checkout -b experimental

Los parches que fueron formateados por "git format-patch" se aplican con "git am":

% git am 0001-Renombrar-Leon-Brocard-a-Orange-Brocard.patch
Applying Rename Leon Brocard to Orange Brocard

Ten en cuenta que algunos sistemas de correo electrónico UNIX pueden interferir con los archivos adjuntos de texto que contienen 'From '. Esto los corregirá:

% perl -pi -e's/^>From /From /' \
                       0001-Renombrar-Leon-Brocard-a-Orange-Brocard.patch

Si solo se proporciona un diff crudo, también es posible usar este proceso de dos pasos:

% git apply bugfix.diff
% git commit -a -m "Alguna corrección" \
                           --author="Ese Tipo <ese.tipo@internets.com>"

Ahora podemos inspeccionar el cambio:

% git show HEAD

Date:   Vie Dic 19 17:02:59 2008 +0000

Si eres un commitero de Perl y crees que el parche es bueno, puedes fusionarlo en blead y luego empujarlo al repositorio principal:

% git checkout blead
% git merge experimental
% git push origin blead

Si deseas eliminar tu rama temporal, puedes hacerlo con:

% git checkout blead
% git branch -d experimental
error: La rama 'experimental' no es un antepasado de tu HEAD actual. Si estás seguro de que quieres eliminarla, ejecuta 'git branch -D experimental'.
% git branch -D experimental
Rama experimental eliminada.

Commit a blead

La rama 'blead' se convertirá en la próxima versión de producción de Perl.

Antes de empujar cualquier cambio local a blead, es increíblemente importante que hagas algunas cosas, para evitar que otros commitores vengan detrás de ti con horcas y antorchas:

  • Asegúrate de tener un buen mensaje de commit. Consulta "Commit message" en perlhack para más detalles.
  • Ejecuta la suite de pruebas. Puede que no creas que una simple corrección de error tipográfico rompa un archivo de prueba. Te equivocarás. Aquí tienes un ejemplo de dónde no ejecutar la suite causó problemas. Se presentó un parche que añadía un par de pruebas a un .t existente. Era imposible que afectara a nada más, así que no había necesidad de probar más allá del único .t afectado, ¿verdad? Pero, la dirección de correo electrónico del remitente había cambiado desde la última de sus presentaciones, y esto hizo que fallaran otras pruebas. Ejecutar el objetivo de prueba dado en el siguiente punto habría detectado este problema.
  • Si no ejecutas la suite de pruebas completa, al menos ejecuta "make test_porting". Esto ejecutará verificaciones básicas de cordura. Para ver cuáles son esas verificaciones de cordura, echa un vistazo en t/porting.
  • Si realizas algún cambio que afecte a miniperl o a rutinas principales que tengan diferentes rutas de código para miniperl, asegúrate de ejecutar "make minitest". Esto detectará problemas que incluso la suite de pruebas completa no detectará porque ejecuta un subconjunto de pruebas bajo miniperl en lugar de perl.

Sobre fusionar y rebasar

Los commits simples, de un solo uso, empujados a la rama 'blead' deben ser commits simples que se apliquen limpiamente. En otras palabras, debes asegurarte de que tu trabajo se confirme contra la posición actual de blead, de modo que puedas empujar de vuelta al repositorio maestro sin fusionar.

A veces, blead se moverá mientras estás construyendo o probando tus cambios. Cuando esto sucede, tu empuje será rechazado con un mensaje como este:

To ssh://perl5.git.perl.org/perl.git
 ! [rechazado]        blead -> blead (actualización no fast-forward)
error: no se pudieron empujar algunas refs a 'ssh://perl5.git.perl.org/perl.git'
Para evitar que pierdas historial, las actualizaciones no fast-forward fueron
rechazadas. Fusiona los cambios remotos (p.ej., 'git pull') antes de empujar
de nuevo. Consulta la sección 'Nota sobre fast-forwards' de 'git push --help'
para más detalles.

Cuando esto sucede, simplemente puedes rebasar tu trabajo de nuevo

Committing to maintenance versions

Maintenance versions should only be altered to add critical bug fixes, see perlpolicy.

To commit to a maintenance version of perl, you need to create a local tracking branch:

% git checkout --track -b maint-5.005 origin/maint-5.005

This creates a local branch named "maint-5.005", which tracks the remote branch "origin/maint-5.005". Then you can pull, commit, merge and push as before.

You can also cherry-pick commits from blead and another branch, by using the "git cherry-pick" command. It is recommended to use the -x option to "git cherry-pick" in order to record the SHA1 of the original commit in the new commit message.

Before pushing any change to a maint version, make sure you've satisfied the steps in "Committing to blead" above.

Using a smoke-me branch to test changes

Sometimes a change affects code paths which you cannot test on the OSes which are directly available to you and it would be wise to have users on other OSes test the change before you commit it to blead.

Fortunately, there is a way to get your change smoke-tested on various OSes: push it to a "smoke-me" branch and wait for certain automated smoke-testers to report the results from their OSes. A "smoke-me" branch is identified by the branch name: specifically, as seen on github.com it must be a local branch whose first name component is precisely "smoke-me".

The procedure for doing this is roughly as follows (using the example of tonyc's smoke-me branch called win32stat):

First, make a local branch and switch to it:

% git checkout -b win32stat

Make some changes, build perl and test your changes, then commit them to your local branch. Then push your local branch to a remote smoke-me branch:

% git push origin win32stat:smoke-me/tonyc/win32stat

Now you can switch back to blead locally:

% git checkout blead

and continue working on other things while you wait a day or two, keeping an eye on the results reported for your "smoke-me" branch at https://perl.develop-help.com/?b=smoke-me/tonyc/win32state.

If all is well then update your blead branch:

% git pull

then checkout your smoke-me branch once more and rebase it on blead:

% git rebase blead win32stat

Now switch back to blead and merge your smoke-me branch into it:

% git checkout blead
% git merge win32stat

As described earlier, if there are many changes on your smoke-me branch then you should prepare a merge commit in which to give an overview of those changes by using the following command instead of the last command above:

% git merge win32stat --no-ff --no-commit

You should now build perl and test your (merged) changes one last time (ideally run the whole test suite, but failing that at least run the t/porting/*.t tests) before pushing your changes as usual:

% git push origin blead

Finally, you should then delete the remote smoke-me branch:

% git push origin :smoke-me/tonyc/win32stat

(which is likely to produce a warning like this, which can be ignored:

remote: fatal: ambiguous argument
                                 'refs/heads/smoke-me/tonyc/win32stat':
unknown revision or path not in the working tree.
remote: Use '--' to separate paths from revisions

) and then delete your local branch:

% git branch -d win32stat
