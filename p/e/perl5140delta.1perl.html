NOMBRE

perl5140delta - novedades para perl v5.14.0

DESCRIPCIÓN

Este documento describe las diferencias entre la versión 5.12.0 y la versión 5.14.0.

Si está actualizando desde una versión anterior como la 5.10.0, primero lea perl5120delta, que describe las diferencias entre 5.10.0 y 5.12.0.

Algunas de las correcciones de errores en esta versión han sido portadas a versiones posteriores de 5.12.x. Estas se indican con la versión 5.12.x entre paréntesis.

Aviso

Como se describe en perlpolicy, el lanzamiento de Perl 5.14.0 marca el fin oficial del soporte para Perl 5.10. Los usuarios de Perl 5.10 o anteriores deberían considerar actualizarse a una versión más reciente de Perl.

Mejoras Centrales

Unicode

Ahora se soporta (en su mayoría) Unicode Versión 6.0

Perl viene con la base de datos Unicode 6.0 actualizada con la Corrección #8 http://www.unicode.org/versions/corrigendum8.html, con una excepción señalada a continuación. Consulte http://unicode.org/versions/Unicode6.0.0/ para obtener detalles sobre la nueva versión. Perl no soporta ninguna propiedad provisional de Unicode, incluidas las nuevas para esta versión.

Unicode 6.0 ha elegido usar el nombre "BELL" para el carácter en U+1F514, que es un símbolo que parece una campana y se usa en teléfonos móviles japoneses. Esto entra en conflicto con el uso tradicional de Perl de que "BELL" signifique el carácter ASCII "BEL", U+0007. En Perl 5.14, "\N{BELL}" sigue significando U+0007, pero su uso genera un mensaje de advertencia de deprecación a menos que dichas advertencias estén desactivadas. El nuevo nombre para U+0007 en Perl es "ALERT", que se corresponde bien con la secuencia abreviada existente para él, "\a". "\N{BEL}" significa U+0007, sin advertencia. El carácter en U+1F514 no tiene nombre en 5.14, pero se puede referir a él mediante "\N{U+1F514}". En Perl 5.16, "\N{BELL}" se referirá a U+1F514; todo el código que use "\N{BELL}" debería ser convertido para usar "\N{ALERT}", "\N{BEL}" o "\a" antes de actualizarse.

Funcionalidad completa para "use feature 'unicode_strings'"

Esta versión proporciona funcionalidad completa para use feature 'unicode_strings'. Bajo su ámbito, todas las operaciones de cadenas ejecutadas y las expresiones regulares compiladas (incluso si se ejecutan fuera de su ámbito) tienen semántica Unicode. Consulte "la característica 'unicode_strings'" en feature. Sin embargo, consulte "Clases de caracteres entre corchetes invertidos y plegados multicarácter", a continuación.

Esta característica evita la mayoría de las formas del "Error Unicode" (consulte "El "Error Unicode"" en perlunicode para obtener detalles). Si existe alguna posibilidad de que su código procese cadenas Unicode, se le anima *encarecidamente* a utilizar esta subpragma para evitar sorpresas desagradables.

"\N{NAME}" y mejoras de "charnames"

  • "\N{NOMBRE}" y "charnames::vianame" ahora conocen los nombres abreviados de caracteres listados por Unicode, como NBSP, SHY, LRO, ZWJ, etc.; todas las abreviaturas habituales para los caracteres de control C0 y C1 (como ACK, BEL, CAN, etc.); y algunas variantes nuevas de algunos nombres completos de C1 que están en uso común.
  • Unicode tiene varias *secuencias de caracteres con nombre*, en las que secuencias particulares de puntos de código reciben nombres. "\N{NOMBRE}" ahora las reconoce.
  • "\N{ NOMBRE}", "charnames::vianame" y "charnames::viacode" ahora conocen cada carácter de Unicode. En versiones anteriores de Perl, no conocían las sílabas Hangul ni varios caracteres CJK (chino/japonés/coreano).
  • Ahora es posible anular las abreviaturas de Perl con sus propios alias personalizados.
  • Ahora puede crear un alias personalizado del ordinal de un carácter, conocido por "\N{ NOMBRE}", charnames::vianame() y charnames::viacode(). Anteriormente, los alias tenían que ser de nombres de caracteres oficiales de Unicode. Esto hacía imposible crear un alias para puntos de código sin nombre, como los reservados para uso privado.
  • La nueva función charnames::string_vianame() es una versión en tiempo de ejecución de "\N{ NOMBRE}}", que devuelve la cadena de caracteres cuyo nombre Unicode es su parámetro. Puede manejar secuencias de caracteres con nombre de Unicode, mientras que la función preexistente charnames::vianame() no puede, ya que esta última devuelve un solo punto de código.

Consulte charnames para obtener detalles sobre todos estos cambios.

Nuevas categorías de advertencia para puntos de código (no)problemáticos (no)Unicode

Se han añadido tres nuevas subcategorías de advertencia de "utf8". Estas le permiten desactivar algunas advertencias de "utf8", mientras permite que otras advertencias permanezcan activas. Las tres categorías son: "surrogate" cuando se encuentran sustitutos UTF-16; "nonchar" cuando se encuentran puntos de código no caracteres de Unicode; y "non_unicode" cuando se encuentran puntos de código por encima del máximo legal de Unicode de 0x10FFFF.

Cualquier valor sin signo puede codificarse como carácter

Con esta versión, Perl adopta un modelo en el que cualquier valor sin signo puede tratarse como un punto de código y codificarse internamente (como utf8) sin advertencias, no solo los puntos de código que son legales en Unicode. Sin embargo, a menos que utf8 o la subcategoría correspondiente (ver elemento anterior) de advertencias léxicas se hayan desactivado explícitamente, la salida o ejecución de una operación definida por Unicode, como la conversión a mayúsculas en dicho punto de código, genera una advertencia. Intentar introducir estos mediante reglas estrictas (como con la capa :encoding(UTF-8)) seguirá fallando. Antes de esta versión, el manejo era inconsistente y en algunos lugares, incorrecto.

Los no caracteres Unicode, algunos de los cuales anteriormente eran considerados erróneamente ilegales en algunos lugares por Perl, contrariamente al Estándar Unicode, ahora son siempre legales internamente. Introducirlos o salirlos funciona igual que con los puntos de código Unicode no legales, porque el Estándar Unicode dice que son (solo) ilegales para el "intercambio abierto".

Archivos de base de datos Unicode no instalados

Los archivos de base de datos Unicode ya no se instalan con Perl. Esto no afecta ninguna funcionalidad en Perl y ahorra un espacio significativo en disco. Si necesita estos archivos, puede descargarlos desde http://www.unicode.org/Public/zipped/6.0.0/.

Expresiones Regulares

La construcción "(?^...)" significa modificadores predeterminados

Un signo de intercalación ASCII "^" inmediatamente después de un "(?" en una expresión regular ahora significa que la subexpresión no hereda modificadores circundantes como "/i", sino que vuelve a los valores predeterminados de Perl. Cualquier modificador que siga al signo de intercalación anula los valores predeterminados.

La conversión a cadena de las expresiones regulares ahora usa esta notación. Por ejemplo, "qr/hlagh/i" previamente se convertiría a cadena como "(?i-xsm:hlagh)", pero ahora se convierte a cadena como "(?^i:hlagh)".

Abstract

This document describes some of the new features and incompatibilities introduced by Perl version 5.14.

New Features

Exception Handling and Warnings

The handling of exceptions and warnings has been improved:

  • The implicit call to "die()" that occurs when an exception is being unwound has been changed. Previously, an exception being unwound was sometimes emitted as a warning, and then either was string-appended to the surrounding $@ or completely replaced the surrounding $@, depending on whether that exception and the surrounding $@ were strings or objects. Now, an exception in this situation is always emitted as a warning, leaving the surrounding $@ untouched. In addition to object destructors, this also affects any function call run by XS code using the "G_KEEPERR" flag.

  • Warnings for "warn" can now be objects in the same way as exceptions for "die". If an object-based warning gets the default handling of writing to standard error, it is stringified as before with the filename and line number appended. But a $SIG{__WARN__} handler now receives an object-based warning as an object, where previously it was passed the result of stringifying the object.

Other Enhancements

Assignment to $0 sets the legacy process name with prctl() on Linux

On Linux the legacy process name is now set with prctl(2), in addition to altering the POSIX name via "argv[0]", as Perl has done since version 4.000. Now system utilities that read the legacy process name such as ps, top, and killall recognize the name you set when assigning to $0. The string you supply is truncated at 16 bytes; this limitation is imposed by Linux.

srand() now returns the seed

This allows programs that need to have repeatable results not to have to come up with their own seed-generating mechanism. Instead, they can use srand() and stash the return value for future use. One example is a test program with too many combinations to test comprehensively in the time available for each run. It can test a random subset each time and, should there be a failure, log the seed used for that run so this can later be used to produce the same results.

printf-like functions understand post-1980 size modifiers

Perl's printf and sprintf operators, and Perl's internal printf replacement function, now understand the C90 size modifiers "hh" ("char"), "z" ("size_t"), and "t" ("ptrdiff_t"). Also, when compiled with a C99 compiler, Perl now understands the size modifier "j" ("intmax_t") (but this is not portable).

So, for example, on any modern machine, "sprintf("%hhd", 257)" returns "1".

New global variable "${^GLOBAL_PHASE}"

A new global variable, "${^GLOBAL_PHASE}", has been added to allow introspection of the current phase of the Perl interpreter. It's explained in detail in "${^GLOBAL_PHASE}" in perlvar and in "BEGIN, UNITCHECK, CHECK, INIT and END" in perlmod.

"-d:-foo" calls "Devel::foo::unimport"

The syntax -d:foo was extended in 5.6.1 to make -d:foo=bar equivalent to -MDevel::foo=bar, which expands internally to "use Devel::foo 'bar'". Perl now allows prefixing the module name with -, with the same semantics as -M; that is:

"-d:-foo"
Equivalent to -M-Devel::foo: expands to "no Devel::foo" and calls "Devel::foo->unimport()" if that method exists.
"-d:-foo=bar"
Equivalent to -M-Devel::foo=bar: expands to "no Devel::foo 'bar'", and calls "Devel::foo->unimport("bar")" if that method exists.

This is particularly useful for suppressing the default actions of a "Devel::*" module's "import" method whilst still loading it for debugging.

Filehandle method calls load IO::File on demand

When a method call on a filehandle would die because the method cannot be resolved and IO::File has not been loaded, Perl now loads IO::File via "require" and attempts method resolution again:

open my $fh, ">", $file;
$fh->binmode(":raw");     # loads IO::File and succeeds

This also works for globs like "STDOUT", "STDERR", and "STDIN":

STDOUT->autoflush(1);

Because this on-demand load happens only if method resolution fails, the legacy approach of manually loading an IO::File parent class for partial method support still works as expected:

use IO::Handle;
open my $fh, ">", $file;
$fh->autoflush(1);        # IO::File not loaded

Improved IPv6 support

The "Socket" module provides new affordances for IPv6, including implementations of the Socket::getaddrinfo() and Socket::getnameinfo() functions, along with related constants and a handful of new functions. See Socket.

DTrace probes now include package name

The "DTrace" probes now include an additional argument, "arg3", which contains the package the subroutine being entered or left was compiled in.

For example, using the following DTrace script:

perl$target:::sub-entry
{
    printf("%s::%s\n", copyinstr(arg0), copyinstr(arg3));
}

and then running:

$ perl -e 'sub test { }; test'

"DTrace" will print:

main::test

Security

User-defined regular expression properties

"User-Defined Character Properties" in perlunicode documented that you can create custom properties by defining subroutines whose names begin with "In" or "Is". However, Perl did not actually enforce that naming restriction, so "\p{foo::bar}" could call foo::bar() if it existed. The documented convention is now enforced.

Also, Perl no longer allows tainted regular expressions to invoke a user-defined property. It simply dies instead [perl #82616].

Incompatible Changes

Perl 5.14.0 is not binary-compatible with any previous stable release.

In addition to the sections that follow, see "C API Changes".

Regular Expressions and String Escapes

Inverted bracketed character classes and multi-character folds

Some characters match a sequence of two or three characters in "/i" regular expression matching under Unicode rules. One example is "LATIN SMALL LETTER SHARP S" which matches the sequence "ss".

'ss' =~ /\A[\N{LATIN SMALL LETTER SHARP S}]\z/i  # Matches

This, however, can lead to very counter-intuitive results, especially when inverted. Because of this, Perl 5.14 does not use multi-character "/i" matching in inverted character classes.

'ss' =~ /\A[^\N{LATIN SMALL LETTER SHARP S}]+\z/i  # ???

This should match any sequences of characters that aren't the "SHARP S" nor what "SHARP S" matches under "/i". "s" isn't "SHARP S", but Unicode says that "ss" is what "SHARP S" matches under "/i". So which one "wins"? Do you fail the match because the string has "ss" or accept it because it has an "s" followed by another "s"?

Earlier releases of Perl did allow this multi-character matching, but due to bugs, it mostly did not work.

\400-\777

In certain circumstances, "\400"-"\777" in regexes have behaved differently than they behave in all other doublequote-like contexts. Since 5.10.1, Perl has issued a deprecation warning when this happens. Now, these literals behave the same in all doublequote-like contexts, namely to be equivalent to "\x{100}"-"\x{1FF}", with no deprecation warning.

Use of "\400"-"\777" in the command-line option -0 retain their conventional meaning. They slurp whole input files; previously, this was documented only for -0777.

Because of various ambiguities, you should use the new "\o{...}" construct to represent characters in octal instead.

Most "\p{}" properties are now immune to case-insensitive matching

For most Unicode properties, it doesn't make sense to have them match differently under "/i" case-insensitive matching. Doing so can lead to unexpected results and potential security holes. For example

m/\p{ASCII_Hex_Digit}+/i

could previously match non-ASCII characters because of the Unicode context.

Expresiones Regulares

Semántica de la bandera de insensibilidad a mayúsculas y minúsculas en propiedades Unicode

Hasta Perl 5.28, las propiedades Unicode especificadas en un patrón, como "\p{Property}", ignoraban la bandera de insensibilidad a mayúsculas y minúsculas /i. Es decir, "m/\p{ASCII}/i" se comportaba igual que "m/\p{ASCII}/". Las reglas de coincidencia de las propiedades Unicode se basan en el estándar Unicode y no se ven afectadas por la bandera /i, lo que provocaba algunos errores de coincidencia (aunque hubo varios errores con esto). Ahora, la coincidencia con "/i" produce los mismos resultados que la coincidencia sin "/i", excepto para aquellas pocas propiedades en las que la gente ha llegado a esperar diferencias, específicamente aquellas en las que las mayúsculas y minúsculas son parte integral de su significado, como "m/\p{Uppercase}/i" y "m/\p{Lowercase}/i", ambas coinciden con los mismos puntos de código que coinciden con "m/\p{Cased}/i". Los detalles se encuentran en "Unicode Properties" en perlrecharclass.

Los manejadores de propiedades definidos por el usuario que necesiten coincidir de manera diferente con "/i" deben modificarse para leer el nuevo parámetro booleano que se les pasa, el cual es distinto de cero si la coincidencia sin distinción de mayúsculas y minúsculas está activa y cero en caso contrario. Ver "User-Defined Character Properties" en perlunicode.

\p{} implica semántica Unicode

Especificar una propiedad Unicode en el patrón indica que el patrón está destinado a coincidir según las reglas de Unicode, de la misma manera que lo hace "\N{NAME}".

Las expresiones regulares conservan su localismo cuando se interpolan

Las expresiones regulares compiladas bajo "use locale" ahora conservan esto cuando se interpolan en una nueva expresión regular compilada fuera de un "use locale", y viceversa.

Anteriormente, una expresión regular interpolada en otra heredaba el localismo de la regex circundante, perdiendo cualquier estado que tuviera originalmente. Esto se considera una corrección de error, pero puede afectar al código que ha llegado a depender del comportamiento incorrecto.

La representación de cadenas de las regex ha cambiado

Los modificadores de expresiones regulares predeterminados ahora se anotan usando "(?^...)". El código que dependa de la antigua representación de cadenas fallará. Esto es para que, cuando se agreguen nuevos modificadores, dicho código no tenga que cambiar cada vez que ocurra esto, ya que la representación de cadenas incorporará automáticamente los nuevos modificadores.

El código que necesita funcionar correctamente tanto con regex de estilo antiguo como nuevo puede evitar todo el problema usando (para perls desde 5.9.5; ver re):

use re qw(regexp_pattern);
my ($pat, $mods) = regexp_pattern($re_ref);

Si la representación de cadenas real es importante o se necesitan soportar perls más antiguos, puede usar algo como lo siguiente:

# Acepta tanto la representación de cadenas de estilo antiguo como el nuevo
my $modifiers = (qr/foobar/ =~ /\Q(?^/) ? "^" : "-xism";

Y luego use $modifiers en lugar de "-xism".

Los bloques de código en tiempo de ejecución en expresiones regulares heredan pragmas

Los bloques de código en expresiones regulares ("(?{...})" y "(??{...})") anteriormente no heredaban pragmas (strict, warnings, etc.) si la expresión regular se compilaba en tiempo de ejecución, como ocurre en casos como estos dos:

use re "eval";
$foo =~ $bar; # cuando $bar contiene (?{...})
$foo =~ /$bar(?{ $finished = 1 })/;

Este error ahora ha sido corregido, pero el código que dependía del comportamiento erróneo puede necesitar ser corregido para tener en cuenta el comportamiento correcto.

Stashes y Variables de Paquete

Los hashes y arrays enlazados localizados ya no están enlazados

En lo siguiente:

tie @a, ...;
{
        local @a;
        # aquí, @a es ahora un nuevo array no enlazado
}
# aquí, @a se refiere de nuevo al array enlazado antiguo

Las versiones anteriores de Perl enlazaban incorrectamente el nuevo array local. Esto ha sido corregido. Sin embargo, esta corrección podría causar un cambio en el comportamiento de algún código.

Los stashes ahora siempre están definidos

"defined %Foo::" ahora siempre devuelve verdadero, incluso cuando aún no se han definido símbolos en ese paquete.

Esto es un efecto secundario de la eliminación de una solución especial en el tokenizador, añadida para 5.10.0, para ocultar los efectos secundarios de los cambios en el almacenamiento interno de los hashes. La corrección reduce drásticamente el consumo de memoria de los hashes.

Llamar a defined en un stash ha sido obsoleto desde 5.6.0, advertido en léxicos desde 5.6.0, y advertido para stashes y otras variables de paquete desde 5.12.0. "defined %hash" siempre ha expuesto un detalle de implementación: vaciar un hash eliminando todas sus entradas no hace que "defined %hash" sea falso. Por lo tanto, "defined %hash" no es un código válido para determinar si un hash arbitrario está vacío. En su lugar, use el comportamiento de un %hash vacío que siempre devuelve falso en contexto escalar.

Limpieza de stashes

La asignación de lista de stash "%foo:: = ()" solía hacer que el stash fuera temporalmente anónimo mientras se vaciaba. En consecuencia, cualquiera de sus subrutinas referenciadas en otros lugares se volvería anónima, apareciendo como "(unknown)" en "caller". Ahora conservan sus nombres de paquete, de modo que "caller" devuelve el nombre de sub original si todavía hay una referencia a su typeglob y "foo::__ANON__" en caso contrario [perl #79208].

Desreferenciación de typeglobs

Si asigna un typeglob a una variable escalar:

$glob = *foo;

el glob que se copia a $glob se marca con un indicador especial que indica que el glob es solo una copia. Esto permite que las asignaciones posteriores a $glob sobrescriban el glob. Sin embargo, el glob original es inmutable.

Algunos operadores de Perl no distinguían entre estos dos tipos de globs. Esto resultaría en un comportamiento extraño en casos extremos: "untie $scalar" no desataría el escalar si lo último asignado a él fuera un glob (porque lo trataba como "untie *$scalar", que desata un handle). La asignación a una ranura de glob (como "*$glob = \@some_array") simplemente asignaría "\@some_array" a $glob.

Para solucionar esto, el operador "*{}" (incluyendo sus formas *foo y *$foo) ha sido modificado para crear un nuevo glob inmutable si su operando es una copia de glob. Esto permite que los operadores que distinguen entre globs y escalares se modifiquen para tratar solo los globs inmutables como globs. ( "tie", "tied" y "untie" se han dejado como están por motivos de compatibilidad, pero advertirán. Ver "Deprecations".)

Esto causa un cambio incompatible en el código que asigna un glob al valor de retorno de "*{}" cuando a ese operador se le pasó una copia de glob. Considere el siguiente código, por ejemplo:

$glob = *foo;
*$glob = *bar;

El *$glob en la segunda línea devuelve un nuevo glob inmutable. Ese nuevo glob se hace un alias de *bar. Luego se descarta. Por lo tanto, la segunda asignación no tiene ningún efecto.

Ver https://github.com/Perl/perl5/issues/10625 para más detalles.

Variables mágicas fuera del paquete principal

En versiones anteriores de Perl, las variables mágicas como $!, %SIG, etc., se "filtraban" a otros paquetes. Por lo tanto, %foo::SIG podría usarse para acceder a señales, "${"foo::!"}" (con el modo strict desactivado) para acceder a "errno" de C, etc.

Esto era un error, o una característica "no intencionada", que causaba varios efectos negativos, como que los manejadores de señales se borraran al cargar módulos, etc.

Esto ha sido corregido (o la característica ha sido eliminada, dependiendo de cómo se mire).

local($_) elimina toda la magia de $_

local() en variables escalares les da un nuevo valor pero conserva toda su magia intacta. Esto ha demostrado ser problemático para la variable escalar predeterminada $_, donde perlsub recomienda que cualquier subrutina que asigne a $_ primero la localice. Esto lanzaría una excepción si $_ está aliased a una variable de solo lectura, y en general podría tener varios efectos secundarios no intencionados.

Por lo tanto, como una excepción a la regla general, local($_) no solo asignará un nuevo valor a $_, sino que también eliminará toda la magia existente de él.

Análisis de nombres de paquetes y variables

El análisis de los nombres de paquetes y variables de paquetes ha cambiado: múltiples pares adyacentes de dos puntos, como en "foo::::bar", ahora se tratan como separadores de paquete.

Independientemente de este cambio, el análisis exacto de los separadores de paquete nunca ha estado garantizado y está sujeto a cambios en futuras versiones de Perl.

Hilos y Procesos


Los manejadores de directorio no se copian a los hilos


En sistemas que no son Windows y que no tienen una función
    "fchdir", los hilos recién creados ya no
    heredan manejadores de directorio de sus hilos padre. Dichos programas normalmente
    se habrían bloqueado de todos modos [perl #75154].


"close" en tuberías
    compartidas


Para evitar interbloqueos, la función "close"
    ya no espera a que el proceso hijo termine si el descriptor de archivo subyacente
    todavía está en uso por otro hilo. Devuelve verdadero en tales casos.


fork() la emulación no esperará a los hijos
    señalados


En Windows, los procesos padre no terminaban hasta que todos los hijos
    generados terminaban primero. Sin embargo, "kill("KILL", ...)"
    es inherentemente inestable en pseudo-procesos, y "kill("TERM", ...)"
    podría no ser entregado si el hijo está bloqueado en una llamada al sistema.


Para evitar el interbloqueo y aún proporcionar un mecanismo seguro para
    terminar el proceso anfitrión, Perl ahora ya no espera a los hijos a los que
    se les ha enviado una señal SIGTERM. Corresponde al proceso padre hacer
    waitpid() por estos hijos si se debe permitir que el procesamiento de
    limpieza del hijo finalice. Sin embargo, también es responsabilidad del padre
    evitar el interbloqueo asegurándose de que el proceso hijo no pueda estar bloqueado
    en E/S.


Vea perlfork para más información sobre la emulación de
    fork() en Windows.






Configuración


Correcciones de nombres en Policy_sh.SH pueden invalidar Policy.sh


Se han corregido varios errores tipográficos y confusiones de nombres
    de larga data en Policy_sh.SH, estandarizando los nombres de variables
    utilizados en config.sh.


Esto cambiará el comportamiento de Policy.sh si por casualidad
    ha dependido accidentalmente de su comportamiento incorrecto.


El código fuente de Perl se lee en modo texto en Windows


Los scripts de Perl solían leerse en modo binario en Windows para el

    Esto tuvo el efecto secundario de romper varias operaciones en el manejador
    de archivo "DATA", incluyendo
    seek()/tell(), e incluso simplemente leer de
    "DATA" después de que los manejadores de
    archivo hayan sido vaciados por una llamada a system(), comillas invertidas,
    fork(), etc.


Las opciones de compilación predeterminadas para Windows se han
    cambiado para leer el código fuente de Perl en modo texto ahora. ByteLoader
    será (con suerte) actualizado en CPAN para manejar automáticamente esta
    situación [perl #28106].

Omitir un espacio entre una expresión regular y la palabra subsiguiente


Omitir el espacio entre un operador de expresión regular o sus
    modificadores y la siguiente palabra está obsoleto. Por ejemplo,
    "m/foo/sand $bar" todavía se analiza como
    "m/foo/s and $bar", pero ahora emitirá una
    advertencia.






"\cX"


La construcción de barra invertida seguida de 'c' fue diseñada como
    una forma de especificar caracteres no imprimibles, pero no había restricciones
    (en plataformas ASCII) sobre cuál podía ser el carácter que seguía a la
    "c". Ahora, se emite una advertencia de
    obsolescencia si ese carácter no es un carácter ASCII. Además, se emite una
    advertencia de obsolescencia para "\c{" (que
    es lo mismo que decir simplemente ";").






"\b{" y "\B{"


En expresiones regulares, una "{"
    literal inmediatamente después de un "\b"
    (no en una clase de caracteres entre corchetes) o un "\B{"
    está ahora obsoleto para permitir su uso futuro por parte del propio Perl.






Bibliotecas .pl de la era Perl 4


Perl incluye un puñado de archivos de biblioteca anteriores a Perl 5.
    Esta inclusión ahora está obsoleta para la mayoría de estos archivos, que ahora
    están disponibles en CPAN. Los archivos afectados ahora advierten cuando se
    ejecutan, si se instalaron como parte del núcleo.


Esta es una advertencia obligatoria, que no obedece a
    -X ni a bits de advertencia léxicos. La advertencia se modela según
    la proporcionada por deprecate.pm para bibliotecas .pm obsoletas
    en el núcleo. Señala la distribución CPAN específica que contiene las bibliotecas
    .pl. Las versiones de CPAN, por supuesto, no generan la advertencia.






Asignación de lista a $[


La asignación a $[ fue obsoleta y comenzó a
    emitir advertencias en la versión 5.12.0 de Perl. Esta versión de Perl (5.14)
    ahora también emite una advertencia al asignar a $[
    en contexto de lista. Esto corrige una omisión en 5.12.0.






Uso de qw(...) como paréntesis


Históricamente, el analizador se engañaba a sí mismo pensando que los
    literales qw(...) siempre estaban entre
    paréntesis, y como resultado, a veces se podían omitir los paréntesis
    alrededor de ellos:


for $x qw(a b c) { ... }


El analizador ya no se miente a sí mismo de esta manera. Envuelva el
    literal de lista entre paréntesis así:


for $x (qw(a b c)) { ... }


Esto está obsoleto porque los paréntesis en
    "for $i (1,2,3) { ... }" no son parte de la
    sintaxis de la expresión. Son parte de la sintaxis de la declaración, con la
    declaración "for" queriendo paréntesis
    literales. Los paréntesis sintéticos que adquirió una expresión
    "qw" solo estaban destinados a ser tratados
    como parte de la sintaxis de la expresión.


Tenga en cuenta que esto no cambia el comportamiento de casos como:


use POSIX qw(setlocale localeconv);
our @EXPORT = qw(foo bar baz);


donde los paréntesis nunca fueron requeridos alrededor de la expresión.






"\N{BELL}"


Esto se debe a que Unicode está usando ese nombre para un carácter
    diferente. Vea "Unicode Versión 6.0 ahora es compatible (en su mayoría)"
    para más explicaciones.






"?PATTERN?"


"?PATTERN?" (sin la
    "m" inicial) ha sido obsoleto y ahora produce
    una advertencia. Esto es para permitir el uso futuro de
    "?" en nuevos operadores. La funcionalidad de
    coincidencia única todavía está disponible como
    "m?PATTERN?".






Funciones de enlace en escalares que contienen typeglobs


Llamar a una función de enlace ("tie",
    "tied", "untie")
    con un argumento escalar actúa sobre un manejador de archivo si el escalar
    contiene un typeglob.


Este es un error de larga data que se eliminará en Perl 5.16, ya que
    actualmente no hay forma de enlazar el escalar en sí cuando contiene un
    typeglob, y no hay forma de desenlazar un escalar al que se le ha asignado un
    typeglob.


Ahora hay una advertencia de obsolescencia cada vez que se utiliza una
    función de enlace en un manejador sin un "*"
    explícito.






Mapeo de mayúsculas y minúsculas definido por el usuario


Se está introduciendo una nueva característica,
    "use feature 'unicode_strings'", que permite
    el mapeo de mayúsculas y minúsculas definido por el usuario para expresiones
    regulares. Cuando esta característica está habilitada, las expresiones
    regulares usan la tabla de mapeo de mayúsculas y minúsculas de Unicode
    en lugar de las reglas de ASCII para las operaciones de coincidencia de mayúsculas
    y minúsculas.


Los detalles completos están en la página del manual
    perlop, sección "Unicode".


Tenga en cuenta que la supresión de la compatibilidad con versiones
    anteriores para el mapeo de mayúsculas y minúsculas se pospuso al menos hasta
    Perl 5.16.

Mejoras de rendimiento




Optimización de "señales seguras"


La distribución de señales se ha trasladado del bucle de ejecución a las operaciones de control. Esto debería proporcionar un aumento de velocidad de unos pocos puntos porcentuales y elimina casi toda la penalización de velocidad causada por la introducción de "señales seguras" en 5.8.0. Las señales aún deben distribuirse dentro de la misma instrucción que anteriormente. Si esto *no* sucede, o si descubre que es posible crear bucles ininterrumpibles, esto es un error y se agradecen los informes sobre cómo recrear dichos problemas.






Optimización de llamadas a shift() y pop() sin argumentos


Se utilizan dos OPs menos para llamadas a shift() y pop() sin argumento (con @_ implícito). Este cambio hace que shift() sea un 5% más rápido que "shift @_" en perl no anidados y un 25% más rápido en los anidados.






Optimización del trabajo de comparación de cadenas del motor de expresiones regulares


La función de API "foldEQ_utf8" para la comparación de cadenas sin distinción entre mayúsculas y minúsculas (que es utilizada intensamente por el motor de expresiones regulares) fue sustancialmente refactorizada y optimizada, y su documentación mejoró mucho como un beneficio adicional.






Aceleración de la compilación de expresiones regulares


La compilación de expresiones regulares se ha vuelto más rápida cuando la actualización de la expresión regular a utf8 es necesaria, pero esto no se sabe cuándo comienza la compilación.






La concatenación de cadenas es 100 veces más rápida


Al realizar muchas concatenaciones de cadenas, los perls compilados para usar el "malloc" del sistema podían terminar asignando mucha más memoria de la necesaria de manera ineficiente.


"sv_grow", la función utilizada para asignar más memoria si es necesario al concatenar una cadena, ha aprendido a redondear la memoria que solicita a una cierta progresión geométrica, lo que la hace mucho más rápida en ciertas plataformas y configuraciones. En Win32, ahora es aproximadamente 100 veces más rápida.






Eliminación de las funciones accesoras "PL_*" bajo ithreads


Cuando se desarrolló por primera vez "MULTIPLICITY", y el estado del intérprete se trasladó a una estructura de intérprete, las variables "PL_*" locales al hilo y al intérprete se definieron como macros que llamaban a funciones accesoras (que devuelven la dirección del valor) fuera del núcleo de Perl. La intención era permitir que los miembros dentro de la estructura del intérprete cambiaran de tamaño sin romper la compatibilidad binaria, de modo que las correcciones de errores pudieran fusionarse en una rama de mantenimiento que requiriera dicho cambio de tamaño. Este mecanismo era redundante y penalizaba el código bien comportado. Ha sido eliminado.






Liberación de referencias débiles


Cuando hay muchas referencias débiles a un objeto, la liberación de ese objeto puede, bajo ciertas circunstancias, llevar O(N*N) tiempo para liberarse, donde N es el número de referencias. Las circunstancias en las que esto puede suceder se han reducido [perl #75254]






Asignaciones léxicas de matrices y hashes


Una optimización anterior para acelerar las asignaciones de "my @array = ..." y "my %hash = ..." causó un error y se deshabilitó en Perl 5.12.0.


Ahora hemos encontrado otra forma de acelerar estas asignaciones [perl #82110].






@_ usa menos memoria


Anteriormente, @_ se asignaba para cada subrutina en tiempo de compilación con suficiente espacio para cuatro entradas. Ahora, esta asignación se realiza bajo demanda cuando se llama a la subrutina [perl #72416].






Optimizaciones de tamaño para las estructuras SV y HV


"xhv_fill" se ha eliminado de "struct xpvhv", lo que ahorra 1 IV por hash y, en algunos sistemas, hará que "struct xpvhv" se alinee en la caché. Para evitar que este ahorro de memoria cause una desaceleración en otro lugar, el uso booleano de "HvFILL" ahora llama a "HvTOTALKEYS" en su lugar (que es equivalente), por lo que, si bien los datos de relleno cuando son realmente necesarios ahora se calculan bajo demanda, los casos en los que esto debe hacerse deberían ser raros.


Se ha cambiado el orden de los elementos de la estructura en los cuerpos SV. Efectivamente, la ranura NV ha intercambiado la ubicación con STASH y MAGIC. Como todo acceso a los miembros de SV se realiza a través de macros, esto debería ser completamente transparente. Este cambio permite el ahorro de espacio para PVHV documentado anteriormente y puede reducir la asignación de memoria necesaria para PVIV en algunas arquitecturas.


"XPV", "XPVIV" y "XPVNV" ahora asignan solo las partes del cuerpo "SV" que realmente utilizan, lo que ahorra algo de espacio.


Los escalares que contienen expresiones regulares ahora solo asignan la parte del cuerpo "SV" que realmente utilizan, lo que ahorra algo de espacio.






Mejoras en el consumo de memoria para Exporter


El AV @EXPORT_FAIL ya no se crea a menos que sea necesario, por lo tanto, tampoco lo hace el tipo glob que lo respalda. Esto ahorra aproximadamente 200 bytes por cada paquete que utiliza Exporter pero no utiliza esta funcionalidad.






Ahorro de memoria para referencias débiles


Para las referencias débiles, el caso común de una sola referencia débil por referente se ha optimizado para reducir el almacenamiento requerido. En este caso, ahorra el equivalente a una pequeña matriz Perl por referente.






"%+" y "%-" usan menos memoria


La mayor parte del módulo "Tie::Hash::NamedCapture" solía estar en el núcleo de Perl. Ahora se ha trasladado a un módulo XS para reducir la sobrecarga para los programas que no utilizan "%+" o "%-".






Múltiples mejoras pequeñas para hilos


Las estructuras internas de subprocesos ahora realizan menos llamadas a la API y menos asignaciones, lo que resulta en un código objeto notablemente más pequeño. Además, muchas comprobaciones de contexto de hilos se han pospuesto para que se realicen solo cuando sea necesario (aunque esto solo es posible para compilaciones sin depuración).






Los pares adyacentes de opcodes nextstate ahora se optimizan


Anteriormente, en código como


use constant DEBUG => 0;
sub GAK {
    warn if DEBUG;
    print "stuff\n";
}


los opcodes para "warn if DEBUG" se fusionarían en un



"null" op
    ("ex-const"), pero el
    op "nextstate" permanecería, lo que resultaría en
    una ejecución de op en tiempo de ejecución de "nextstate",
    "nextstate", etc.


La ejecución de una secuencia de
    ops "nextstate" es indistinguible de
    solo el último op "nextstate", por lo que
    el optimizador peephole ahora elimina el primero de un par de
    ops "nextstate" excepto cuando el primero
    lleva una etiqueta, ya que las etiquetas no deben ser eliminadas por el optimizador y
    el uso de etiquetas no se conoce de forma concluyente en tiempo de compilación.

    Internal Changes
    

    

    New APIs
    

    CLONE_PARAMS structure added to ease correct thread creation
    

    Modules that create threads should now create "CLONE_PARAMS"
    structures by calling the new function Perl_clone_params_new(), and
    free them with Perl_clone_params_del(). This will ensure compatibility
    with any future changes to the internals of the "CLONE_PARAMS"
    structure layout, and that it is correctly allocated and initialised.
    

    New parsing functions
    

    Several functions have been added for parsing Perl statements and
    expressions. These functions are meant to be used by XS code invoked during
    Perl parsing, in a recursive-descent manner, to allow modules to augment the
    standard Perl syntax.
    

      
  
    • parse_stmtseq() parses a sequence of statements, up to closing
      brace or EOF.
      • 
  
    • parse_fullstmt() parses a complete Perl statement, including
      optional label.
      • 
  
    • parse_barestmt() parses a statement without a label.
      • 
  
    • parse_block() parses a code block.
      • 
  
    • parse_label() parses a statement label, separate from
      statements.
      • 
  
    • parse_fullexpr(), parse_listexpr(),
      parse_termexpr(), and parse_arithexpr()
      parse expressions at various precedence levels.
      • 

    

    Hints hash API
    

    A new C API for introspecting the hinthash "%^H"
    at runtime has been added. See "cop_hints_2hv",
    "cop_hints_fetchpvn",
    "cop_hints_fetchpvs",
    "cop_hints_fetchsv", and
    "hv_copy_hints_hv" in perlapi for
    details.
    

    A new, experimental API has been added for accessing the internal
    structure that Perl uses for "%^H". See
    the functions beginning with "cophh_" in
    perlapi.
    

    C interface to caller()
    

    The "caller_cx" function has
    been added as an XSUB-writer’s equivalent of caller(). See
    perlapi for details.
    

    Custom per-subroutine check hooks
    

    XS code in an extension module can now annotate a subroutine
    (whether implemented in XS or in Perl) so that nominated XS code will be
    called at compile time (specifically as part of op checking) to change the
    op tree of that subroutine. The compile-time check function (supplied by the
    extension module) can implement argument processing that can’t be
    expressed as a prototype, generate customised compile-time warnings, perform
    constant folding for a pure function, inline a subroutine consisting of
    sufficiently simple ops, replace the whole call with a custom op, and so on.
    This was previously all possible by hooking the "entersub"
    op checker, but the new mechanism makes it easy to tie the hook to a specific
    subroutine. See "cv_set_call_checker" in perlapi.
    

    To help in writing custom check hooks, several subtasks within
    standard "entersub" op checking have been
    separated out and exposed in the API.
    

    Improved support for custom OPs
    

    Custom ops can now be registered with the new
    "custom_op_register" C function and the
    "XOP" structure. This will make it easier
    to add new properties of custom ops in the future. Two new properties have
    been added already, "xop_class" and
    "xop_peep".
    

    "xop_class" is one of the OA_*OP
    constants. It allows B and other introspection mechanisms to work with
    custom ops that aren’t BASEOPs. "xop_peep"
    is a pointer to a function that will be called for ops of this type from
    "Perl_rpeep".
    

    See "Custom Operators" in perlguts and "Custom
    Operators" in perlapi for more detail.
    

    The old "PL_custom_op_names"/"PL_custom_op_descs"
    interface is still supported but discouraged.
    

    Scope hooks
    

    It is now possible for XS code to hook into Perl’s lexical
    scope mechanism at compile time, using the new
    "Perl_blockhook_register" function. See
    "Compile-time scope hooks" in perlguts.
    

    The recursive part of the peephole optimizer is now
    hookable
    

    In addition to "PL_peepp", for
    hooking into the toplevel peephole optimizer, a
    "PL_rpeepp" is now available to hook into
    the optimizer recursing into side-chains of the optree.
    

    New non-magical variants of existing functions
    

    The following functions/macros have been added to the API. The
    *_nomg macros are equivalent to their
    non-"_nomg" variants, except that they
    ignore get-magic. Those ending in "_flags"
    allow one to specify whether get-magic is processed.
    

    sv_2bool_flags
SvTRUE_nomg
sv_2nv_flags
SvNV_nomg
sv_cmp_flags
sv_cmp_locale_flags
sv_eq_flags
sv_collxfrm_flags
    

    In some of these cases, the non-"_flags"
    functions have been replaced with wrappers around the new functions.
    

    pv/pvs/sv versions of existing functions
    

    Many functions ending with pvn now have equivalent
    "pv/pvs/sv" versions.
    

    List op-building functions
    

    List op-building functions have been added to the API. See
    op_append_elem, op_append_list, and op_prepend_elem in perlapi.
    

    "LINKLIST"
    

    The LINKLIST macro, part of op building that constructs the
    execution-order op chain, has been added to the API.
    

    Localisation functions
    

    The "save_freeop",
    "save_op",
    "save_pushi32ptr" and
    "save_pushptrptr" functions have been
    added to the API.
    

    Stash names
    

    A stash can now have a list of effective names in addition to its
    usual name. The first effective name can be accessed via the
    "HvENAME" macro, which is now the
    recommended name to use in MRO linearisations ("HvNAME"
    being a fallback if there is no "HvENAME").
    

    These names are added and deleted via
    "hv_ename_add" and
    "hv_ename_delete". These two functions are
    not part of the API.
    

    New functions for finding and removing magic
    

    The mg_findext() and
    sv_unmagicext() functions have been added to the
    API. They allow extension authors to find and remove magic attached to
    scalars based on both the magic type and the magic virtual table, similar to
    how sv_magicext() attaches magic of a certain type and with a given
    virtual table to a scalar. This eliminates the need for extensions to walk
    the list of "MAGIC" pointers of an
    "SV" to find the magic that belongs to
    them.
    

    "find_rundefsv"
    

    This function returns the SV representing $_, whether it’s
    lexical or dynamic.
    

    "Perl_croak_no_modify"
    

    Perl_croak_no_modify() is short-hand for
    "Perl_croak(\"%s\", PL_no_modify)".
    

    "PERL_STATIC_INLINE" define
    

    The "PERL_STATIC_INLINE" define
    has been added to provide the best-guess incantation to use for static
    inline functions, if the C compiler supports C99-style static inline. If it
    doesn’t, it’ll give a plain "static".
    

    "HAS_STATIC_INLINE" can be used
    to check if the compiler actually supports inline functions.
    

    New "pv_escape"
    option for hexadecimal escapes
    

    A new option, "PERL_PV_ESCAPE_NONASCII",
    has been added to "pv_escape" to dump all
    characters above ASCII in hexadecimal. Before, one could get all characters
    as hexadecimal or the Latin1 non-ASCII as octal.
    

    "lex_start"
    

    "lex_start" has been added to
    the API, but is considered experimental.

    Arreglos de Errores de Archivo y E/S
    

      
  
    • La detección de la falta de memoria ahora funciona correctamente para los
      lectores y escritores de PerlIO. Esto significa que los errores de
      memoria agotada ahora serán informados como tales, en lugar de simplemente
      fallar en silencio o causar corrupción de memoria.
      • 
  
    • La supresión de advertencias sobre valores no inicializados para la clave
      de un hash ahora funciona correctamente. Anteriormente, si se accedía a una
      clave no inicializada de un hash dentro de un contexto que suprimía
      advertencias (por ejemplo, con un modificador de sigilo), la advertencia
      todavía se emitía. Esto se ha corregido.
      • 
  
    • Se ha corregido un error que podía ocurrir al intentar leer desde un archivo
      abierto en modo binario con un codificador de PerlIO. Anteriormente, si se
      intentaba leer una cantidad de bytes que no coincidía con los límites de
      caracteres codificados, podía ocurrir un bloqueo o un resultado incorrecto.
      Esto ahora se maneja correctamente.
      • 
  
    • Se ha corregido un problema con la capa ":unlock"
      de PerlIO que podía hacer que los manejadores de archivos se bloquearan si
      se intentaba desbloquear un manejador de archivos que ya había sido
      desbloqueado.
      • 
  
    • Se ha corregido un problema con la capa ":crlf"
      de PerlIO que podía hacer que los manejadores de archivos se bloquearan si
      se intentaba cerrar un manejador de archivos que ya había sido cerrado.
      • 
  
    • Se ha corregido un error que podía causar que las advertencias sobre valores
      no inicializados no se activaran cuando un archivo se abría en modo de
      lectura y escritura, pero se escribía en él antes de que se abriera
      completamente. Ahora, la condición "unopened"
      es necesaria para activar estas advertencias, como siempre fue la
      intención.
      • 
  
    • Ha habido varias correcciones en las capas PerlIO:
    
      Cuando "binmode(FH,
        ":crlf")" empuja la capa
        ":crlf" encima de la pila, ya no habilita
        capas crlf más abajo en la pila para evitar resultados inesperados
        [perl #38456].
      
    
      Abrir un archivo en modo ":raw"
        ahora hace lo que anuncia (primero abre el archivo, luego lo pone en
        "binmode"), en lugar de simplemente
        quitar la capa superior [perl #80764].
      
    
      Las tres capas ":pop",
        ":utf8" y
        ":bytes" no permitían el apilamiento al
        abrir un archivo. Por ejemplo, esto:
      
        
      open(FH, ">:pop:perlio", "some.file") or die $!;

      
    
      lanzaría un error de "Argumento inválido". Esto se ha
        corregido en este lanzamiento [perl #82484].

    Arreglos de Errores de Expresiones Regulares
    

      
  
    • El motor de expresiones regulares ya no entra en bucle al hacer coincidir
      ""\N{LATIN SMALL LIGATURE FF}" =~
      /f+/i" y expresiones similares [perl #72998] (5.12.1).
      • 
  
    • El código de tiempo de ejecución de trie ya no debería asignar una gran
      cantidad de memoria, corrigiendo #74484.
      • 
  
    • Los errores de sintaxis en bloques "(?{...})"
      ya no causan mensajes de pánico [perl #2353].
      • 
  
    • Un patrón como "(?:(o){2})?" ya no causa
      un error de "pánico" [perl #39233].
      • 
  
    • Se ha corregido un error fatal en expresiones regulares que contenían
      "(.*?)" al procesar datos UTF-8
      [perl #75680] (5.12.2).
      • 
  
    • Se ha eliminado una optimización errónea del motor de expresiones
      regulares que hacía que los verbos de regex como *COMMIT
      a veces fueran ignorados.
      • 
  
    • La clase de caracteres entre corchetes de expresiones regulares
      "[\8\9]" era efectivamente lo mismo que
      "[89\000]", lo que coincidía incorrectamente
      con un carácter NULL. También emitía advertencias incorrectas de que
      8 y 9 eran ignorados. Ahora
      "[\8\9]" es lo mismo que
      "[89]" y emite advertencias legítimas
      de que "\8" y
      "\9" son secuencias de escape no
      reconocidas, que se pasan sin cambios.
      • 
  
    • Una coincidencia de expresión regular en el lado derecho de una sustitución
      global ("s///g") que está en el mismo
      ámbito ya no hará que las variables de coincidencia tengan valores
      incorrectos en iteraciones posteriores. Esto puede suceder cuando una
      subíndice de arreglo o hash se interpola en el lado derecho, como en
      "s|(.)|@a{ print($1), /./ }|g" [perl
      #19078].
      • 
  
    • Se han corregido varios casos en los que caracteres del rango no ASCII de
      Latin-1 (0x80 a 0xFF) solían no coincidir consigo mismos, o solían
      coincidir tanto con una clase de caracteres como con su complemento. Por
      ejemplo, U+00E2 podía coincidir tanto con "\w"
      como con "\W" [perl #78464] [perl #18281]
      [perl #60156].
      • 
  
    • La coincidencia de un carácter Unicode con una alternancia que contenía
      caracteres que coincidían casualmente con bytes de continuación en la
      representación UTF8 del primero (como "qq{\x{30ab}} =~
      /\xab|\xa9/") provocaba advertencias erróneas [perl
    #70998].
      • 
  
    • La optimización de trie no tenía en cuenta los grupos vacíos, impidiendo
      que "foo" coincidiera con
      "\A(?:(?:)foo|bar|zot)\z/" [perl
      #78356].
      • 
  
    • Un patrón que contenía un "+" dentro de una
      mirada adelantada a veces causaba un fallo de coincidencia incorrecto en una
      coincidencia global (por ejemplo, "/(?=(\S+))/g")
      [perl #68564].
      • 
  
    • Una optimización de expresiones regulares a veces provocaba que una
      coincidencia con un cuantificador "{n,m}"
      fallara cuando debería haber coincidido [perl #79152].
      • 
  
    • La coincidencia insensible a mayúsculas y minúsculas en expresiones
      regulares compiladas bajo "use locale" ahora
      funciona mucho más sensatamente cuando el patrón o la cadena de destino
      están codificados internamente en UTF8. Anteriormente, bajo estas
      condiciones, la configuración regional se perdía por completo. Ahora, los
      puntos de código superiores a 255 se tratan como Unicode, pero los puntos
      de código entre 0 y 255 se tratan utilizando las reglas de la configuración
      regional actual, independientemente de si el patrón o la cadena están
      codificados en UTF8. Las pocas coincidencias insensibles a mayúsculas y
      minúsculas que cruzan el límite de 255/256 no están permitidas. Por
      ejemplo, 0xFF no coincide sin distinción de mayúsculas y minúsculas con el
      carácter en 0x178, LATIN CAPITAL LETTER Y WITH DIAERESIS, porque 0xFF puede
      no ser LATIN SMALL LETTER Y en la configuración regional actual, y Perl no
      tiene forma de saber si ese carácter existe en la configuración regional,
      y mucho menos qué punto de código es.
      • 
  
    • La construcción de expresiones regulares "(?|...)"
      ya no falla si la rama final tiene más conjuntos de paréntesis de captura
      que cualquier otra rama. Esto se corrigió en Perl 5.10.1 para el caso de
      una sola rama, pero esa corrección no tuvo en cuenta múltiples ramas
      [perl #84746].
      • 
  
    • Se ha corregido un error en la implementación de cuantificadores
      "{...}" en expresiones regulares que
      impedía que el bloque de código en
      "/((\w+)(?{ print $2 })){2}/" viera a
      $2 a veces [perl #84294].

    Typeglobs, Stashes and Method Resolution
    

    The method cache in Perl has been re-written to use @ISA arrays directly, rather than relying on a separate cache. This should be more efficient, as the @ISA arrays would not have to be searched repeatedly. Unfortunately, this brought with it quite a few bugs. Almost all of these have been fixed now, along with a few MRO-related bugs that existed before 5.10.0:
    

    
  
    •
    
  
    The following used to have erratic effects on method resolution, because
      the "isa" caches were not reset or otherwise ended up listing
      the wrong classes. These have been fixed.
    

    

    

    
  
    Aliasing packages by
    assigning to globs [perl #77358]
    
  
    
  
    Deleting packages by
    deleting their containing stash elements
    
  
    
  
    Undefining the
    glob containing a package ("undef *Foo::")
    
  
    
  
    Undefining an
    ISA glob ("undef *Foo::ISA")
    
  
    
  
    Deleting an ISA
    stash element ("delete $Foo::{ISA}")
    
  
    
  
    Sharing @ISA arrays
    between classes (via "*Foo::ISA = \@Bar::ISA" or "*Foo::ISA =
    *Bar::ISA") [perl #77238]
    
  
    

    

    

    

    "undef *Foo::ISA" would even
    stop a new @Foo::ISA array from updating caches.
    

    

      
  
    • Typeglob assignments would crash if the glob's stash no longer existed, so
      long as the glob assigned to were named
      "ISA" or the glob on either side of the
      assignment contained a subroutine.
      • 
  
    • "PL_isarev", which is accessible to Perl
      via "mro::get_isarev" is now updated
      properly when packages are deleted or removed from the
      @ISA of other classes. This allows many packages
      to be created and deleted without causing a memory leak [perl
    #75176].
      • 

    

    In addition, various other bugs related to typeglobs and stashes
    have been fixed:
    

      
  
    • Some work has been done on the internal pointers that link between symbol
      tables (stashes), typeglobs, and subroutines. This has the effect that
      various edge cases related to deleting stashes or stash entries (for
      example, <%FOO:: = ()>), and complex typeglob or code-reference
      aliasing, will no longer crash the interpreter.
      • 
  
    • Assigning a reference to a glob copy now assigns to a glob slot instead of
      overwriting the glob with a scalar [perl #1804] [perl #77508].
      • 
  
    • A bug when replacing the glob of a loop variable within the loop has been
      fixed [perl #21469]. This means the following code will no longer crash:
        
      for $x (...) {
    *x = *y;
}

      
  
      • 
  
    • Assigning a glob to a PVLV used to convert it to a plain string. Now it
      works correctly, and a PVLV can hold a glob. This would happen when a
      nonexistent hash or array element was passed to a subroutine:
        
      sub { $_[0] = *foo }->($hash{key});
# $_[0] would have been the string "*main::foo"

      
    
      It also happened when a glob was assigned to, or returned
        from, an element of a tied array or hash [perl #36051].
      
  
      • 
  
    • When trying to report "Use of uninitialized value
      $Foo::BAR", crashes could occur if the glob holding the global
      variable in question had been detached from its original stash by, for
      example, "delete
      $::{'Foo::'}". This has been fixed by disabling the
      reporting of variable names in those cases.
      • 
  
    • During the restoration of a localised typeglob on scope exit, any
      destructors called as a result would be able to see the typeglob in an
      inconsistent state, containing freed entries, which could result in a
      crash. This would affect code like this:
        
      local *@;
eval { die bless [] }; # puts an object in $@
sub DESTROY {
  local $@; # boom
}

      
    
      Now the glob entries are cleared before any destructors are
        called. This also means that destructors can vivify entries in the glob.
        So Perl tries again and, if the entries are re-created too many times,
        dies with a "panic: gp_free ..." error message.
      
  
      • 
  
    • If a typeglob is freed while a subroutine attached to it is still
      referenced elsewhere, the subroutine is renamed to
      "__ANON__" in the same package, unless
      the package has been undefined, in which case the
      "__ANON__" package is used. This could
      cause packages to be sometimes autovivified, such as if the package had
      been deleted. Now this no longer occurs. The
      "__ANON__" package is also now used when
      the original package is no longer attached to the symbol table. This
      avoids memory leaks in some cases [perl #87664].
      • 
  
    • Subroutines and package variables inside a package whose name ends with
      "::" can now be accessed with a fully
      qualified name.

    Unicode
    

    
  
    •
    
  
    What has become known as "the Unicode Bug" is almost completely
      resolved in this release. Under "use feature
      'unicode_strings'" (which is automatically selected by
      "use 5.012" and above), the internal
      storage format of a string no longer affects the external semantics. [perl
      #58182].

    1.
    
  
    The now-deprecated, user-defined case-changing functions require
      utf8-encoded strings to operate. The CPAN module Unicode::Casing has been
      written to replace this feature without its drawbacks, and the feature is
      scheduled to be removed in 5.16.
    
  
    2.
    
  
    quotemeta() (and its in-line equivalent
      "\Q") can also give different results
      depending on whether a string is encoded in UTF-8. See "The
      "Unicode Bug"" in perlunicode.
    

    

    

      
  
    • Handling of Unicode non-character code points has changed. Previously they
      were mostly considered illegal, except that in some place only one of the
      66 of them was known. The Unicode Standard considers them all legal, but
      forbids their "open interchange". This is part of the change to
      allow internal use of any code point (see "Core Enhancements").
      Together, these changes resolve [perl #38722], [perl #51918], [perl
      #51936], and [perl #63446].
      • 
  
    • Case-insensitive  regular expression
      matching of Unicode characters that match multiple characters now works
      much more as intended. For example
        
      "\N{LATIN SMALL LIGATURE FFI}" =~ /ffi/ui

      
    
      and
      
        
      "ffi" =~ /\N{LATIN SMALL LIGATURE FFI}/ui

      
    
      are both true. Previously, there were many bugs with this
        feature. What hasn't been fixed are the places where the pattern
        contains the multiple characters, but the characters are split up by
        other things, such as in
      
        
      "\N{LATIN SMALL LIGATURE FFI}" =~ /(f)(f)i/ui

      
    
      or
      
        
      "\N{LATIN SMALL LIGATURE FFI}" =~ /ffi*/ui

      
    
      or
      
        
      "\N{LATIN SMALL LIGATURE FFI}" =~ /[a-f][f-m][g-z]/ui

      
    
      None of these match.
      
    
      Also, this matching doesn't fully conform to the current
        Unicode Standard, which asks that the matching be made upon the NFD
        (Normalization Form Decomposed) of the text. However, as of this writing
        (April 2010), the Unicode Standard is currently in flux about what they
        will recommend doing with regard in such scenarios. It may be that they
        will throw out the whole concept of multi-character matches. [perl
        #71736].
      
  
      • 
  
    • Naming a deprecated character in
      "\N{NAME}"
      no longer leaks memory.
      • 
  
    • We fixed a bug that could cause
      "\N{NAME}"
      constructs followed by a single "." to
      be parsed incorrectly [perl #74978] (5.12.1).
      • 
  
    • "chop" now correctly handles characters
      above  [perl #73246].
      •

      end of the string when the string is encoded internally in UTF8 no longer
      causes panics [perl #75898].
      •

      #45549].

    Correcciones y Arreglos
    

    Esta versión incluye correcciones para una serie de errores, incluyendo:
    

      
  
    • Una regresión en versiones recientes permitía que la función
      "import" corrompiera la pila, lo que
      resultaba en comportamientos extraños.
      Por ejemplo,
        
      push @a, "foo", $b = bar->import;

      
    
      asignaría "foo" a $b
        [perl #63790].
      
  
      • 
  
    • La función "recv" podía fallar al ser
      llamada con la bandera MSG_TRUNC [perl #75082].
      • 
  
    • "formline" ya no falla cuando se le pasa
      una imagen de formato taintada. También taintará $^A
      si sus argumentos están taintados [perl #79138].
      • 
  
    • Un error en el procesamiento de las operaciones de prueba de archivos
      podía causar un fallo de segmentación. Las pruebas de archivos no siempre
      esperan una operación en la pila, por lo que ahora solo usamos TOPs si
      estamos seguros de que no estamos haciendo un "stat"
      del manejador de archivo "_". Esto se indica
      mediante "OPf_KIDS" (como se comprueba en
      ck_ftst) [perl #74542] (5.12.1).
      • 
  
    • unpack() ahora maneja el contexto escalar correctamente para
      %32H y %32u, corrigiendo un
      posible fallo. split() fallaba porque el tercer elemento en la
      pila no era la expresión regular que esperaba.
      "unpack("%2H",
      ...)" devolvía tanto el resultado desempaquetado
      como la suma de verificación en la pila, al igual que
      "unpack("%2u", ...)" [perl
      #73814] (5.12.2).

    Problemas Conocidos
    

    Esta es una lista de problemas significativos no resueltos que
    son regresiones de versiones anteriores de Perl o que afectan a módulos de
    CPAN ampliamente utilizados.
    

      
  
    • "List::Util::first" se comporta incorrectamente
      en presencia de un $_ léxico (normalmente introducido
      por "my $_" o implícitamente por
      "given"). La variable que se establece para
      cada iteración es la variable del paquete $_, no
      el $_ léxico.
    
      Puede ocurrir un problema similar en otros módulos que
        proporcionan funciones que toman un bloque como primer argumento, como
      
        
      foo { ... $_ ...} list

      
    
      Ver también:
      https://github.com/Perl/perl5/issues/9798

      en caché cuando es interrumpido por una señal.

      expiraba, pero no si el temporizador se reiniciaba antes de expirar. HP

    Fe de erratas
    

    

    keys(), values() y each() funcionan en
  arrays
    

    Ahora puede usar las funciones integradas keys(),
    values() y each() en arrays; anteriormente solo podía usarlas
    en hashes. Consulte perlfunc para obtener detalles. Este es en realidad un
    cambio introducido en perl 5.12.0, pero se omitió del perl5120delta de esa
    versión.
    

    

    

    split() y @_
    

    split() ya no modifica @_ cuando
    se llama en contexto escalar o void. En contexto void, ahora produce una
    advertencia de "Useless use of split". Este también fue un cambio
    de perl 5.12.0 que se omitió en el perldelta.
