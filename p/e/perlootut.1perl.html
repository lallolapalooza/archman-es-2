DESCRIPCIÓN

Este documento proporciona una introducción a la programación orientada a objetos en Perl. Comienza con una breve descripción general de los conceptos detrás del diseño orientado a objetos. Luego introduce varios sistemas OO diferentes de CPAN https://www.cpan.org que se basan en lo que Perl proporciona.

Por defecto, el sistema OO incorporado de Perl es muy minimalista, dejándote hacer la mayor parte del trabajo. Este minimalismo tuvo mucho sentido en 1994, pero en los años transcurridos desde Perl 5.0, hemos visto una serie de patrones comunes emerger en la POO de Perl. Afortunadamente, la flexibilidad de Perl ha permitido que florezca un rico ecosistema de sistemas OO de Perl.

Si quieres saber cómo funciona la POO de Perl internamente, el documento perlobj explica los detalles técnicos.

Este documento asume que ya entiendes los conceptos básicos de la sintaxis de Perl, tipos de variables, operadores y llamadas a subrutinas. Si aún no comprendes estos conceptos, por favor lee perlintro primero. También deberías leer los documentos perlsyn, perlop y perlsub.

FUNDAMENTOS ORIENTADOS A OBJETOS

La mayoría de los sistemas de objetos comparten una serie de conceptos comunes. Probablemente hayas escuchado términos como "clase", "objeto", "método" y "atributo" antes. Comprender los conceptos hará que sea mucho más fácil leer y escribir código orientado a objetos. Si ya estás familiarizado con estos términos, aún deberías repasar esta sección, ya que explica cada concepto en términos de la implementación OO de Perl.

El sistema OO de Perl está basado en clases. La POO basada en clases es bastante común. Es utilizada por Java, C++, C#, Python, Ruby y muchos otros lenguajes. Existen otros paradigmas de orientación a objetos también. JavaScript es el lenguaje más popular para usar otro paradigma. El sistema OO de JavaScript está basado en prototipos.

Objeto

Un objeto es una estructura de datos que agrupa datos y subrutinas que operan sobre esos datos. Los datos de un objeto se llaman atributos, y sus subrutinas se llaman métodos. Un objeto puede ser pensado como un sustantivo (una persona, un servicio web, una computadora).

Un objeto representa una única cosa discreta. Por ejemplo, un objeto podría representar un archivo. Los atributos de un objeto archivo podrían incluir su ruta, contenido y la hora de la última modificación. Si creáramos un objeto para representar /etc/hostname en una máquina llamada "foo.example.com", la ruta de ese objeto sería "/etc/hostname", su contenido sería "foo\n", y su hora de última modificación sería 1304974868 segundos desde el inicio de la época.

Los métodos asociados con un archivo podrían incluir rename() y write().

En Perl, la mayoría de los objetos son hashes, pero los sistemas OO que recomendamos te evitan tener que preocuparte por esto. En la práctica, es mejor considerar la estructura de datos interna de un objeto como opaca.

Clase

Una clase define el comportamiento de una categoría de objetos. Una clase es un nombre para una categoría (como "Archivo"), y una clase también define el comportamiento de los objetos de esa categoría.

Todos los objetos pertenecen a una clase específica. Por ejemplo, nuestro objeto /etc/hostname pertenece a la clase "Archivo". Cuando queremos crear un objeto específico, comenzamos con su clase y construimos o instanciamos un objeto. Un objeto específico a menudo se denomina una instancia de una clase.

En Perl, cualquier paquete puede ser una clase. La diferencia entre un paquete que es una clase y uno que no lo es se basa en cómo se utiliza el paquete. Aquí está nuestra "declaración de clase" para la clase "Archivo":

package File;

En Perl, no hay una palabra clave especial para construir un objeto. Sin embargo, la mayoría de los módulos OO en CPAN utilizan un método llamado new() para construir un nuevo objeto:

my $hostname = File->new(
    path          => '/etc/hostname',
    content       => "foo\n",
    last_mod_time => 1304974868,
);

(No te preocupes por ese operador "->", se explicará más tarde.)

Bendición

Como dijimos antes, la mayoría de los objetos Perl son hashes, pero un objeto puede ser una instancia de cualquier tipo de datos de Perl (escalar, arreglo, etc.). Convertir una estructura de datos simple en un objeto se hace bendiciendo esa estructura de datos usando la función "bless" de Perl.

Si bien te sugerimos encarecidamente que no construyas tus objetos desde cero, deberías conocer el término bless. Una estructura de datos bendecida (también conocida como "referente") es un objeto. A veces decimos que un objeto ha sido "bendecido en una clase".

Una vez que un referente ha sido bendecido, la subrutina "blessed" del módulo principal Scalar::Util puede decirnos el nombre de su clase. Esta subrutina devuelve la clase de un objeto cuando se le pasa un objeto, y falso en caso contrario.

use Scalar::Util 'blessed';
print blessed($hash);      # undef
print blessed($hostname);  # File

Constructor

Un constructor crea un nuevo objeto. En Perl, el constructor de una clase es simplemente otra subrutina, a diferencia de algunos otros lenguajes, que proporcionan sintaxis para constructores. La mayoría de las clases de Perl usan "new" como nombre para su constructor:

my $file = File->new(...);

Métodos

Ya aprendiste que un método es una subrutina que opera sobre un objeto. Puedes pensar en un método como las cosas que un objeto puede hacer. Si un objeto es un sustantivo, entonces los métodos son sus verbos (guardar, imprimir, abrir).

En Perl, los métodos son simplemente subrutinas que viven en el paquete de una clase. Los métodos siempre se escriben para recibir el objeto como su primer argumento:

sub print_info {
    my $self = shift;
    print "Este archivo está en ", $self->path, "\n";
}
$file->print_info;
# Este archivo está en /etc/hostname

Lo que hace especial a un método es cómo se llama. El operador flecha ("->") le dice a Perl que estamos llamando a un método.

Cuando hacemos una llamada a un método, Perl se encarga de que el invocante del método se pase como primer argumento. Invocante es un nombre elegante para la cosa que está a la izquierda de la flecha. El invocante puede ser un nombre de clase o un objeto. También podemos pasar argumentos adicionales al método:

sub print_info {
    my $self   = shift;
    my $prefix = shift // "Este archivo está en ";
    print $prefix, ", ", $self->path, "\n";
}
$file->print_info("El archivo se encuentra en ");
# El archivo se encuentra en /etc/hostname

Atributos

Cada clase puede definir sus atributos. Cuando instanciamos un objeto, asignamos valores a esos atributos. Por ejemplo, cada objeto "Archivo" tiene una ruta. Los atributos a veces se denominan propiedades.

Perl no tiene una sintaxis especial para los atributos. Internamente, los atributos a menudo se almacenan como claves en el hash subyacente del objeto, pero no te preocupes por esto.

Recomendamos que solo accedas a los atributos a través de métodos accesor. Estos son métodos que pueden obtener o establecer el valor de cada atributo. Vimos esto anteriormente en el ejemplo print_info(), que llama a "$self->path".

También puedes ver los términos getter (obtener) y setter (establecer). Estos son dos tipos de accesores. Un getter obtiene el valor del atributo, mientras que un setter lo establece. Otro término para un setter es mutador.

Los atributos suelen definirse como de solo lectura o de lectura/escritura. Los atributos de solo lectura solo se pueden establecer cuando el objeto se crea por primera vez, mientras que los atributos de lectura/escritura se pueden modificar en cualquier momento.

El valor de un atributo puede ser él mismo otro objeto. Por ejemplo, en lugar de devolver la hora de la última modificación como un número, la clase "File" podría devolver un objeto DateTime que represente ese valor.

Es posible tener una clase que no exponga ningún atributo que se pueda establecer públicamente. No todas las clases tienen atributos y métodos.

Polimorfismo

Polimorfismo es una forma elegante de decir que objetos de dos clases diferentes comparten una API. Por ejemplo, podríamos tener las clases "File" y "WebPage" que ambas tengan un método print_content(). Este método podría producir una salida diferente para cada clase, pero comparten una interfaz común.

Si bien las dos clases pueden diferir en muchos aspectos, cuando se trata del método print_content(), son iguales. Esto significa que podemos intentar llamar al método print_content() en un objeto de cualquiera de las clases, ¡y no necesitamos saber a qué clase pertenece el objeto!

El polimorfismo es uno de los conceptos clave del diseño orientado a objetos.

Herencia

Herencia te permite crear una versión especializada de una clase existente. La herencia permite que la nueva clase reutilice los métodos y atributos de otra clase.

Por ejemplo, podríamos crear una clase "File::MP3" que herede de "File". Un "File::MP3" es un tipo más específico de "File". Todos los archivos mp3 son archivos, pero no todos los archivos son archivos mp3.

A menudo nos referimos a las relaciones de herencia como relaciones de padre-hijo o de "superclase"/"subclase". A veces decimos que el hijo tiene una relación es un con su clase padre.

"File" es una superclase de "File::MP3", y "File::MP3" es una subclase de "File".

package File::MP3;
use parent 'File';

El módulo `parent` es una de las varias formas en que Perl te permite definir relaciones de herencia.

Perl permite la herencia múltiple, lo que significa que una clase puede heredar de varios padres. Si bien esto es posible, desaconsejamos firmemente su uso. En general, puedes usar roles para hacer todo lo que puedes hacer con la herencia múltiple, pero de una manera más limpia.

Ten en cuenta que no hay nada de malo en definir múltiples subclases de una clase dada. Esto es común y seguro. Por ejemplo, podríamos definir las clases "File::MP3::FixedBitrate" y "File::MP3::VariableBitrate" para distinguir entre diferentes tipos de archivos mp3.

Anulación de métodos y resolución de métodos

La herencia permite que dos clases compartan código. Por defecto, cada método en la clase padre también está disponible en la clase hija. La clase hija puede anular explícitamente un método del padre para proporcionar su propia implementación. Por ejemplo, si tenemos un objeto "File::MP3", tiene el método print_info() de "File":

my $cage = File::MP3->new(
    path          => 'mp3s/My-Body-Is-a-Cage.mp3',
    content       => $mp3_data,
    last_mod_time => 1304974868,
    title         => 'My Body Is a Cage',
);
$cage->print_info;
# The file is at mp3s/My-Body-Is-a-Cage.mp3

Si quisiéramos incluir el título del mp3 en el saludo, podríamos anular el método:

package File::MP3;
use parent 'File';
sub print_info {
    my $self = shift;
    print "This file is at ", $self->path, "\n";
    print "Its title is ", $self->title, "\n";
}
$cage->print_info;
# The file is at mp3s/My-Body-Is-a-Cage.mp3
# Its title is My Body Is a Cage

El proceso de determinar qué método se debe utilizar se llama resolución de métodos. Lo que hace Perl es buscar primero en la clase del objeto (en este caso, "File::MP3"). Si esa clase define el método, se llama a la versión de esa clase del método. Si no, Perl busca en cada clase padre en orden. Para "File::MP3", su único padre es "File". Si "File::MP3" no define el método, pero "File" sí lo hace, entonces Perl llama al método en "File".

Si "File" heredara de "DataSource", que heredara de "Thing", entonces Perl seguiría buscando "hacia arriba en la cadena" si fuera necesario.

Es posible llamar explícitamente a un método padre desde un hijo:

package File::MP3;
use parent 'File';
sub print_info {
    my $self = shift;
    $self->SUPER::print_info();
    print "Its title is ", $self->title, "\n";
}

La parte "SUPER::" le dice a Perl que busque el método print_info() en la cadena de herencia de la clase "File::MP3". Cuando encuentra la clase padre que implementa este método, se llama al método.

Mencionamos la herencia múltiple anteriormente. El principal problema con la herencia múltiple es que complica enormemente la resolución de métodos. Consulte perlobj para obtener más detalles.

Encapsulación

Encapsulación es la idea de que un objeto es opaco. Cuando otro desarrollador utiliza tu clase, no necesita saber cómo se implementa, solo necesita saber qué hace.

La encapsulación es importante por varias razones. Primero, te permite separar la API pública de la implementación privada. Esto significa que puedes cambiar esa implementación sin romper la API.

Segundo, cuando las clases están bien encapsuladas, se vuelven más fáciles de subclase. Idealmente, una subclase utiliza las mismas API para acceder a los datos del objeto que utiliza su clase padre. En realidad, la subclase a veces implica violar la encapsulación, pero una buena API puede minimizar la necesidad de hacerlo.

Mencionamos anteriormente que la mayoría de los objetos de Perl se implementan como hashes internamente. El principio de encapsulación nos dice que no debemos confiar en esto. En cambio, debemos usar métodos accesores para acceder a los datos en ese hash. Los sistemas de objetos que recomendamos a continuación automatizan la generación de métodos accesores. Si usa uno de ellos, nunca debería tener que acceder al objeto como un hash directamente.

Composición

En el código orientado a objetos, a menudo encontramos que un objeto hace referencia a otro objeto. Esto se llama composición o una relación tiene un.

Anteriormente, mencionamos que el accesor "last_mod_time" de la clase "File" podría devolver un objeto DateTime. Este es un ejemplo perfecto de composición. Podríamos ir más allá y hacer que los accesores "path" y "content" también devuelvan objetos. La clase "File" estaría entonces compuesta por varios otros objetos.

Roles

Los Roles son algo que una clase hace, en lugar de algo que es. Los roles son relativamente nuevos en Perl, pero se han vuelto bastante populares. Los roles se aplican a las clases. A veces decimos que las clases consumen roles.

Los roles son una alternativa a la herencia para proporcionar polimorfismo. Supongamos que tenemos dos clases, "Radio" y "Computer". Ambas cosas tienen interruptores de encendido/apagado. Queremos modelar eso en nuestras definiciones de clase.

Podríamos hacer que ambas clases hereden de un padre común, como "Machine", pero no todas las máquinas tienen interruptores de encendido/apagado. Podríamos crear una clase padre llamada "HasOnOffSwitch", pero eso es muy artificial. Las radios y las computadoras no son especializaciones de este padre. Este padre es realmente una creación bastante ridícula.

Aquí es donde entran los roles. Tiene mucho sentido crear un rol "HasOnOffSwitch" y aplicarlo a ambas clases. Este rol definiría una API conocida, como proporcionar los métodos turn_on() y turn_off().

Perl no tiene ninguna forma incorporada de expresar roles. En el pasado, la gente simplemente aceptaba la situación y usaba la herencia múltiple. Hoy en día, hay varias buenas opciones en CPAN para usar roles.

Cuándo usar OO

La Orientación a Objetos no es la mejor solución para todos los problemas. En Perl Best Practices (copyright 2004, Publicado por O'Reilly Media, Inc.), Damian Conway proporciona una lista de criterios para usar al decidir si OO es la opción adecuada para tu problema:

  • El sistema que se está diseñando es grande, o es probable que crezca.
  • Los datos se pueden agregar en estructuras obvias, especialmente si hay una gran cantidad de datos en cada agregado.
  • Los diversos tipos de agregados de datos forman una jerarquía natural que facilita el uso de la herencia y el polimorfismo.
  • Tienes una pieza de datos sobre la que se aplican muchas operaciones diferentes.
  • Necesitas realizar las mismas operaciones generales en tipos de datos relacionados, pero con ligeras variaciones dependiendo del tipo específico de datos a los que se aplican las operaciones.
  • Es probable que tengas que agregar nuevos tipos de datos más adelante.
  • Las interacciones típicas entre piezas de datos se representan mejor mediante operadores.
  • Es probable que la implementación de componentes individuales del sistema cambie con el tiempo.
  • El diseño del sistema ya está orientado a objetos.
  • Un gran número de otros programadores utilizarán tus módulos de código.

SISTEMAS OO DE PERL

Como mencionamos anteriormente, el sistema OO incorporado de Perl es muy minimalista, pero también bastante flexible. A lo largo de los años, muchas personas han desarrollado sistemas w

que se basan en el sistema incorporado de Perl para proporcionar más funciones y comodidad.

Recomendamos encarecidamente que utilice uno de estos sistemas. Incluso el más mínimo de ellos elimina una gran cantidad de código repetitivo. Realmente no hay ninguna buena razón para escribir sus clases desde cero en Perl.

Si está interesado en las entrañas que sustentan estos sistemas, consulte perlobj.

Moose

Moose se autodenomina un "sistema de objetos posmoderno para Perl 5". No se asuste, la etiqueta "posmoderno" es una referencia a la descripción de Perl por parte de Larry como "el primer lenguaje informático posmoderno".

"Moose" proporciona un sistema de OO completo y moderno. Su mayor influencia es el Common Lisp Object System, pero también toma ideas de Smalltalk y otros lenguajes. "Moose" fue creado por Stevan Little y se basa en gran medida en su trabajo en el diseño de OO de Raku.

Aquí está nuestra clase "File" usando "Moose":

package File;
use Moose;
has path          => ( is => 'ro' );
has content       => ( is => 'ro' );
has last_mod_time => ( is => 'ro' );
sub print_info {
    my $self = shift;
    print "This file is at ", $self->path, "\n";
}

"Moose" proporciona una serie de características:

  • Azúcar declarativo

    "Moose" proporciona una capa de "azúcar" declarativo para definir clases. Ese azúcar es solo un conjunto de funciones exportadas que hacen que la declaración de cómo funciona su clase sea más simple y palatable. Esto le permite describir qué es su clase, en lugar de tener que decirle a Perl cómo implementar su clase.

    La subrutina has() declara un atributo, y "Moose" crea automáticamente los accesores para estos atributos. También se encarga de crear un método new() para usted. Este constructor conoce los atributos que ha declarado, por lo que puede establecerlos al crear un nuevo "File".

  • Roles integrados

    "Moose" le permite definir roles de la misma manera que define clases:

    package HasOnOffSwitch;
use Moose::Role;
has is_on => (
    is  => 'rw',
    isa => 'Bool',
);
sub turn_on {
    my $self = shift;
    $self->is_on(1);
}
sub turn_off {
    my $self = shift;
    $self->is_on(0);
}
  • Un sistema de tipos en miniatura

    En el ejemplo anterior, puede ver que pasamos "isa => 'Bool'" a has() al crear nuestro atributo "is_on". Esto le dice a "Moose" que este atributo debe ser un valor booleano. Si intentamos establecerlo en un valor inválido, nuestro código generará un error.

  • Introspección y manipulación completas

    Las características de introspección integradas de Perl son bastante mínimas. "Moose" se basa en ellas y crea una capa de introspección completa para sus clases. Esto le permite hacer preguntas como "¿qué métodos implementa la clase File?" También le permite modificar sus clases programáticamente.

  • Autoalojado y extensible

    "Moose" se describe a sí mismo utilizando su propia API de introspección. Además de ser un truco genial, esto significa que puede extender "Moose" usando "Moose" mismo.

  • Rico ecosistema

    Hay un rico ecosistema de extensiones de "Moose" en CPAN bajo el espacio de nombres MooseX https://metacpan.org/search?q=MooseX. Además, muchos módulos en CPAN ya utilizan "Moose", lo que le proporciona muchos ejemplos para aprender.

  • Muchas más características

    "Moose" es una herramienta muy potente, y no podemos cubrir todas sus características aquí. Le animamos a aprender más leyendo la documentación de "Moose", comenzando con Moose::Manual https://metacpan.org/pod/Moose::Manual.

Por supuesto, "Moose" no es perfecto.

"Moose" puede hacer que su código tarde más en cargarse. "Moose" en sí no es pequeño, y realiza una gran cantidad de generación de código cuando define su clase. Esta generación de código significa que su código en tiempo de ejecución es lo más rápido posible, pero paga por ello cuando sus módulos se cargan por primera vez.

Este impacto en el tiempo de carga puede ser un problema cuando la velocidad de inicio es importante, como con un script de línea de comandos o un script CGI "vainilla" que debe cargarse cada vez que se ejecuta.

Antes de que entre en pánico, sepa que muchas personas usan "Moose" para herramientas de línea de comandos y otro código sensible al inicio. Le animamos a probar "Moose" primero antes de preocuparse por la velocidad de inicio.

"Moose" también tiene varias dependencias de otros módulos. La mayoría de estos son módulos pequeños e independientes, varios de los cuales se han desprendido de "Moose". "Moose" en sí, y algunas de sus dependencias, requieren un compilador. Si necesita instalar su software en un sistema sin compilador, o si tener alguna dependencia es un problema, entonces "Moose" puede no ser adecuado para usted.

Moo

Si prueba "Moose" y descubre que uno de estos problemas le impide usar "Moose", le animamos a considerar Moo a continuación. "Moo" implementa un subconjunto de la funcionalidad de "Moose" en un paquete más simple. Para la mayoría de las características que implementa, la API del usuario final es idéntica a la de "Moose", lo que significa que puede cambiar de "Moo" a "Moose" con bastante facilidad.

"Moo" no implementa la mayor parte de la API de introspección de "Moose", por lo que a menudo es más rápido al cargar sus módulos. Además, ninguna de sus dependencias requiere XS, por lo que se puede instalar en máquinas sin compilador.

Una de las características más atractivas de "Moo" es su interoperabilidad con "Moose". Cuando alguien intenta usar la API de introspección de "Moose" en una clase o rol de "Moo", se infla de forma transparente en una clase o rol de "Moose". Esto facilita la incorporación de código que utiliza "Moo" en una base de código de "Moose" y viceversa.

Por ejemplo, una clase de "Moose" puede heredar de una clase de "Moo" usando "extends" o consumir un rol de "Moo" usando "with".

Los autores de "Moose" esperan que algún día "Moo" pueda quedar obsoleto al mejorar "Moose" lo suficiente, pero por ahora proporciona una alternativa valiosa a "Moose".

Class::Accessor

Class::Accessor es lo polar opuesto a "Moose". Proporciona muy pocas características, ni es autoalojado.

Sin embargo, es muy simple, puro Perl, y no tiene dependencias no principales. También proporciona una API "similar a Moose" bajo demanda para las características que admite.

A pesar de que no hace mucho, sigue siendo preferible a escribir sus propias clases desde cero.

Aquí está nuestra clase "File" con "Class::Accessor":

package File;
use Class::Accessor 'antlers';
has path          => ( is => 'ro' );
has content       => ( is => 'ro' );
has last_mod_time => ( is => 'ro' );
sub print_info {
    my $self = shift;
    print "This file is at ", $self->path, "\n";
}

El indicador de importación "antlers" le dice a "Class::Accessor" que desea definir sus atributos utilizando la sintaxis similar a "Moose". El único parámetro que puede pasar a has es "is". Recomendamos que utilice esta sintaxis similar a Moose si elige "Class::Accessor", ya que esto significa que tendrá una ruta de actualización más fluida si más adelante decide migrar a "Moose".

Al igual que "Moose", "Class::Accessor" genera métodos accesores y un constructor para su clase.

Class::Tiny

Finalmente, tenemos Class::Tiny. Este módulo realmente hace honor a su nombre. Tiene una API increíblemente mínima y absolutamente ninguna dependencia de Perl reciente. Aún así, creemos que es mucho más fácil de usar que escribir su propio código OO desde cero.

Aquí está nuestra clase "File" una vez más:

package File;
use Class::Tiny qw( path content last_mod_time );
sub print_info {
    my $self = shift;
    print "This file is at ", $self->path, "\n";
}

¡Eso es todo!

Con "Class::Tiny", todos los accesores son de lectura y escritura. Genera un constructor para usted, así como los accesorios que defina.

También puede usar Class::Tiny::Antlers para la sintaxis similar a "Moose".

Role::Tiny

Como mencionamos anteriormente, los roles proporcionan una alternativa a la herencia, pero Perl no tiene ningún soporte de roles incorporado. Si elige usar Moose, viene con una implementación completa de roles. Cómo

Role::Tiny

Incluso si utiliza uno de nuestros otros módulos OO recomendados, aún puede usar roles con Role::Tiny.

Role::Tiny proporciona algunas de las mismas características que el sistema de roles de Moose, pero en un paquete mucho más pequeño. En particular, no admite ningún tipo de declaración de atributos, por lo que debe hacerlo manualmente. Aún así, es útil y funciona bien con Class::Accessor y Class::Tiny.

Resumen del sistema OO

Aquí hay un breve resumen de las opciones que cubrimos:

  • Moose

    Moose es la opción máxima. Tiene muchas características, un gran ecosistema y una base de usuarios próspera. También cubrimos Moo brevemente. Moo es Moose lite, y una alternativa razonable cuando Moose no funciona para su aplicación.

  • Class::Accessor

    Class::Accessor hace mucho menos que Moose, y es una buena alternativa si encuentra Moose abrumador. Ha existido durante mucho tiempo y está bien probado en batalla. También tiene un modo de compatibilidad Moose mínimo que facilita la migración de Class::Accessor a Moose.

  • Class::Tiny

    Class::Tiny es la opción absolutamente mínima. No tiene dependencias, y casi ninguna sintaxis que aprender. Es una buena opción para un entorno súper mínimo y para armar algo rápidamente sin tener que preocuparse por los detalles.

  • Role::Tiny

    Utilice Role::Tiny con Class::Accessor o Class::Tiny si se encuentra considerando la herencia múltiple. Si opta por Moose, viene con su propia implementación de roles.

Otros sistemas OO

Literalmente hay docenas de otros módulos relacionados con OO en CPAN además de los cubiertos aquí, y es probable que se encuentre con uno o más de ellos si trabaja con el código de otras personas.

Además, mucho código en la naturaleza hace toda su OO "manualmente", utilizando solo las características OO integradas de Perl. Si necesita mantener dicho código, debe leer perlobj para comprender exactamente cómo funciona la OO integrada de Perl.

CONCLUSIÓN

Como dijimos antes, el sistema OO mínimo de Perl ha llevado a una profusión de sistemas OO en CPAN. Si bien todavía puede bajar al metal y escribir sus clases manualmente, realmente no hay razón para hacerlo con el Perl moderno.

Para sistemas pequeños, Class::Tiny y Class::Accessor proporcionan sistemas de objetos mínimos que se encargan del código repetitivo básico por usted.

Para proyectos más grandes, Moose proporciona un rico conjunto de características que le permitirán concentrarse en implementar su lógica de negocio. Moo proporciona una buena alternativa a Moose cuando desea muchas características pero necesita un tiempo de compilación más rápido o para evitar XS.

Lo alentamos a que juegue y evalúe Moose, Moo, Class::Accessor y Class::Tiny para ver qué sistema OO es el adecuado para usted.
