NOMBRE

perf-intel-pt - Soporte para Intel Processor Trace dentro de las herramientas perf

SINOPSIS

perf record -e intel_pt//

DESCRIPCIÓN

Intel Processor Trace (Intel PT) es una extensión de la Arquitectura Intel que recopila información sobre la ejecución del software, como el flujo de control, los modos de ejecución y los tiempos, y la formatea en paquetes binarios altamente comprimidos. Los detalles técnicos se documentan en los Manuales del Desarrollador de Software de las Arquitecturas Intel 64 e IA-32, capítulo 36 Intel Processor Trace.

Intel PT se soporta por primera vez en los procesadores Intel Core M y la 5ª generación de procesadores Intel Core basados en la microarquitectura con nombre en clave Broadwell.

Los datos de traza se recopilan mediante perf record y se almacenan dentro del archivo perf.data. Ver abajo para ver las opciones de perf record.

Los datos de traza deben ser *decodificados*, lo que implica recorrer el código objeto y hacer coincidir los paquetes de datos de traza. Por ejemplo, un paquete TNT solo indica si una rama condicional fue tomada o no, por lo que para utilizar ese paquete, el decodificador debe saber exactamente qué instrucción se estaba ejecutando.

La decodificación se realiza sobre la marcha. El decodificador genera muestras en el mismo formato que las muestras generadas por los eventos de hardware de perf, por ejemplo, como si se hubieran registrado los eventos "instructions" o "branches". Actualmente, 3 herramientas soportan esto: perf script, perf report y perf inject. Ver abajo para más información sobre el uso de estas herramientas.

La principal característica distintiva de Intel PT es que el decodificador puede determinar el flujo exacto de la ejecución del software. Intel PT se puede utilizar para entender por qué y cómo el software llegó a cierto punto, o se comportó de cierta manera. El software no necesita ser recompilado, por lo que Intel PT funciona con compilaciones de depuración o de lanzamiento, sin embargo, se necesitan las imágenes ejecutadas, lo que dificulta su uso en entornos compilados JIT o con código que se auto-modifica. Además, se deben proporcionar símbolos para dar sentido a las direcciones.

Una limitación de Intel PT es que produce enormes cantidades de datos de traza (cientos de megabytes por segundo por núcleo) que tardan mucho tiempo en decodificarse, por ejemplo, dos o tres órdenes de magnitud más de lo que tardó en recopilarse. Otra limitación es el impacto en el rendimiento del seguimiento, algo que variará dependiendo del caso de uso y la arquitectura.

GUÍA RÁPIDA

Es importante empezar poco a poco. Esto se debe a que es fácil capturar muchos más datos de los que se pueden procesar.

Lo más sencillo de hacer con Intel PT es el perfilado en modo usuario de programas pequeños. Los datos se capturan con perf record, por ejemplo, para rastrear solo el modo usuario de ls:

perf record -e intel_pt//u ls

Y se perfila con perf report, por ejemplo:

perf report

Para rastrear también el espacio del kernel, surge un problema: el código que se auto-modifica del kernel. Una imagen del kernel bastante buena está disponible en /proc/kcore, pero para obtener una imagen precisa, se debe crear una copia de /proc/kcore en las mismas condiciones que la captura de datos. perf record puede hacer una copia de /proc/kcore si se utiliza la opción --kcore, pero el acceso a /proc/kcore está restringido, por ejemplo:

sudo perf record -o pt_ls --kcore -e intel_pt// -- ls

Esto creará un directorio llamado pt_ls y colocará allí el archivo perf.data (llamado simplemente data) y copias de /proc/kcore, /proc/kallsyms y /proc/modules. Las otras herramientas entienden el formato de directorio, por lo que el uso de perf report se convierte en:

sudo perf report -i pt_ls

Dado que las muestras se sintetizan a posteriori, el período de muestreo se puede seleccionar para la generación de informes. Por ejemplo, muestrear cada microsegundo:

sudo perf report pt_ls --itrace=i1usge

Ver las secciones de abajo para más información sobre la opción --itrace.

Tenga cuidado, cuanto menor sea el período, más muestras se producirán y más tiempo tardará en procesarlas.

También tenga en cuenta que la granularidad de la información de tiempos de Intel PT comenzará a distorsionar el valor estadístico del muestreo a medida que el período de muestreo sea menor.

Para representar el flujo de control del software, se generan muestras de "branches". Por defecto, se sintetiza una muestra de rama por cada rama individual. Para tener una idea de los datos disponibles, puede utilizar la herramienta perf script con todas las opciones de muestreo de itrace, que enumerará todas las muestras.

perf record -e intel_pt//u ls
perf script --itrace=iybxwpe

Un campo interesante que no se imprime por defecto es flags, que se puede mostrar de la siguiente manera:

perf script --itrace=iybxwpe -F+flags

Las banderas son "bcrosyiABExghDt" que representan rama, llamada, retorno, condicional, sistema, asíncrono, interrupción, aborto de transacción, inicio de traza, fin de traza, en transacción, entrada a VM, salida de VM, interrupción deshabilitada e interrupción de alternancia deshabilitada respectivamente.

perf script también soporta formas de nivel superior para volcar trazas de instrucciones:

perf script --insn-trace=disasm

o para usar el desensamblador xed, que requiere instalar la herramienta xed (ver XED abajo):

perf script --insn-trace --xed

Volcar todas las instrucciones en una traza larga puede ser bastante lento. Por lo general, es mejor empezar con decodificación de nivel superior, como

perf script --call-trace

o

perf script --call-ret-trace

y luego seleccionar un rango de tiempo de interés. El rango de tiempo se puede examinar en detalle con

perf script --time starttime,stoptime --insn-trace=disasm

Mientras se examina la traza, también es útil filtrar por CPUs específicas usando la opción -C

perf script --time starttime,stoptime --insn-trace=disasm -C 1

Volcar todas las instrucciones en el rango de tiempo en la CPU 1.

Otro campo interesante que no se imprime por defecto es ipc, que se puede mostrar de la siguiente manera:

perf script --itrace=be -F+ipc

Hay dos formas en que se pueden calcular las instrucciones por ciclo (IPC), dependiendo de la grabación.

Si se utilizó el término de configuración cyc (ver la sección de términos de configuración abajo), entonces los eventos de IPC y ciclo se calculan utilizando el recuento de ciclos de los paquetes CYC, de lo contrario se utilizan los paquetes MTC, consulte el término de configuración mtc. Sin embargo, cuando se utiliza MTC, los valores son menos precisos porque el tiempo es menos preciso.

Dado que Intel PT no actualiza el recuento de ciclos en cada rama o instrucción, los valores a menudo serán cero. Cuando hay valores, serán el número de instrucciones y el número de ciclos desde la última actualización, y por lo tanto representan el recuento promedio de ciclos de IPC desde el último IPC para ese tipo de evento. Tenga en cuenta que el IPC para los eventos de "branches" se calcula por separado del IPC para los eventos de "instructions".

Incluso con el término de configuración cyc, es posible generar información de IPC para cada cambio de marca de tiempo, pero a costa de la precisión. Esto se selecciona especificando la opción A de itrace. Debido a la granularidad de las marcas de tiempo, el número real de ciclos aumenta aunque los ciclos informados no lo hagan. Se conoce el número de instrucciones, pero si se informa el IPC, los ciclos pueden ser demasiado bajos y, por lo tanto, el IPC demasiado alto. Tenga en cuenta que la inexactitud disminuye a medida que aumenta el período de muestreo, es decir, si el número de ciclos es demasiado bajo en una pequeña cantidad, eso se vuelve menos significativo si el número de ciclos es grande. También puede ser útil usar la opción A junto con dlfilter-show-cycles.so para proporcionar información de ciclos de mayor granularidad.

También tenga en cuenta que el recuento de instrucciones de IPC puede o no incluir la instrucción actual. Si el recuento de ciclos está asociado con una rama asíncrona (por ejemplo, falla de página o interrupción), entonces el recuento de instrucciones no incluye la instrucción actual; de lo contrario, sí lo hace. Esto es consistente con si la instrucción se ha retirado o no cuando se actualiza el recuento de ciclos.

Otra nota, en el caso de los eventos de "branches", las ramas no tomadas no se muestrean actualmente, por lo que no aparecen valores de IPC para ellas, por ejemplo, un paquete CYC con un paquete TNT que comienza con una rama no tomada. Para ver cada valor de IPC posible, se pueden usar los eventos "instructions", por ejemplo, --itrace=i0ns

nuevo evento

El controlador del kernel Intel PT crea una nueva PMU para Intel PT. Los eventos de PMU se seleccionan proporcionando el nombre de la PMU seguido de "config" separado por barras. Se ha realizado una mejora para permitir la "config" predeterminada, por ejemplo, la opción

-e intel_pt//

utilizará un valor de configuración predeterminado. Actualmente, este es el mismo que

-e intel_pt/tsc,noretcomp=0/

que es lo mismo que

-e intel_pt/tsc=1,noretcomp=0/

Tenga en cuenta que existen otros términos de configuración; consulte la sección config terms más adelante.

Los términos de configuración se enumeran en /sys/devices/intel_pt/format. Son campos de bits dentro del miembro "config" de la estructura perf_event_attr, que se pasa al kernel mediante la llamada al sistema perf_event_open. Corresponden a campos de bits en el MSR IA32_RTIT_CTL. Aquí hay una lista de ellos y sus definiciones:

$ grep -H . /sys/bus/event_source/devices/intel_pt/format/*
/sys/bus/event_source/devices/intel_pt/format/cyc:config:1
/sys/bus/event_source/devices/intel_pt/format/cyc_thresh:config:19-22
/sys/bus/event_source/devices/intel_pt/format/mtc:config:9
/sys/bus/event_source/devices/intel_pt/format/mtc_period:config:14-17
/sys/bus/event_source/devices/intel_pt/format/noretcomp:config:11
/sys/bus/event_source/devices/intel_pt/format/psb_period:config:24-27
/sys/bus/event_source/devices/intel_pt/format/tsc:config:10

Tenga en cuenta que la configuración predeterminada debe anularse para cada término, es decir,

-e intel_pt/noretcomp=0/

es lo mismo que:

-e intel_pt/tsc=1,noretcomp=0/

Por lo tanto, para deshabilitar los paquetes TSC, use:

-e intel_pt/tsc=0/

También es posible especificar el valor de configuración explícitamente:

-e intel_pt/config=0x400/

Tenga en cuenta que, al igual que con todos los eventos, el evento se sufija con modificadores de evento:

u       espacio de usuario
k       núcleo
h       hipervisor
G       invitado
H       anfitrión
p       ip preciso

h, G y H son para virtualización y no son utilizados por Intel PT. p tampoco es relevante para Intel PT. Por lo tanto, solo las opciones u y k son significativas para Intel PT.

términos de configuración

Los términos de configuración son parámetros especificados con la opción de evento -e intel_pt//, por ejemplo:

-e intel_pt/cyc/

que selecciona el modo de precisión de ciclo. Cada término de configuración puede tener un valor que, por defecto, es 1, por lo que lo anterior es lo mismo que:

-e intel_pt/cyc=1/

Algunos términos se establecen por defecto, por lo que deben establecerse en 0 para desactivarlos. Por ejemplo, para desactivar el rastreo de ramas:

-e intel_pt/branch=0/

Múltiples términos de configuración se separan por comas, por ejemplo:

-e intel_pt/cyc,mtc_period=9/

También hay términos de configuración comunes; consulte la documentación de perf-record(1).

Los términos de configuración de Intel PT se describen a continuación.

tsc

Siempre soportado. Produce paquetes de marca de tiempo TSC para proporcionar información de temporización. En algunos casos, es posible decodificar sin información de temporización, por ejemplo, un contexto por hilo que no se superpone con los mapas de memoria ejecutables.

La configuración predeterminada selecciona tsc (es decir, tsc=1).

noretcomp

Siempre soportado. Deshabilita la "compresión de retorno" para que se produzca un paquete TIP cuando una función retorna. Produce más paquetes, pero puede hacer que la decodificación sea más fiable.

La configuración predeterminada no selecciona noretcomp (es decir, noretcomp=0).

psb_period

Permite especificar la frecuencia de los paquetes PSB.

El paquete PSB es un paquete de sincronización que proporciona un punto de partida para la decodificación o la recuperación de errores.

La compatibilidad con psb_period se indica mediante:

/sys/bus/event_source/devices/intel_pt/caps/psb_cyc

que contiene "1" si la característica es compatible y "0" en caso contrario.

Los valores válidos se obtienen de:

/sys/bus/event_source/devices/intel_pt/caps/psb_periods

que contiene un valor hexadecimal, cuyos bits representan valores válidos, por ejemplo, el bit 2 establecido significa que el valor 2 es válido.

El valor de psb_period se convierte al número aproximado de bytes de rastreo entre paquetes PSB como:

2 ^ (valor + 11)

por ejemplo, valor 3 significa 16 KiB de bytes entre PSBs

Si se introduce un valor no válido, el mensaje de error proporcionará una lista de valores válidos, por ejemplo:

$ perf record -e intel_pt/psb_period=15/u uname
Invalid psb_period for intel_pt. Valid values are: 0-5

Si se seleccionan paquetes MTC, la configuración predeterminada selecciona un valor de 3 (es decir, psb_period=3) o el valor inferior más cercano que sea compatible (0 siempre es compatible). De lo contrario, el predeterminado es 0.

Si se espera que la decodificación sea fiable y el búfer sea grande, se puede utilizar un período PSB grande.

Debido a que se produce un paquete TSC con PSB, el período PSB también puede afectar la granularidad de la información de temporización en ausencia de MTC o CYC.

mtc

Produce paquetes de temporización MTC.

Los paquetes MTC proporcionan información de temporización de grano más fino que los paquetes TSC. Un paquete MTC registra el tiempo utilizando el reloj de cristal de hardware (CTC), que se relaciona con los paquetes TSC mediante un paquete TMA.

La compatibilidad con esta característica se indica mediante:

/sys/bus/event_source/devices/intel_pt/caps/mtc

que contiene "1" si la característica es compatible y "0" en caso contrario.

La frecuencia de los paquetes MTC también se puede especificar; consulte mtc_period más adelante.

mtc_period

Especifica la frecuencia con la que se producen los paquetes MTC; consulte mtc para determinar si los paquetes MTC son compatibles.

Los valores válidos se obtienen de:

/sys/bus/event_source/devices/intel_pt/caps/mtc_periods

que contiene un valor hexadecimal, cuyos bits representan valores válidos, por ejemplo, el bit 2 establecido significa que el valor 2 es válido.

El valor de mtc_period se convierte a la frecuencia MTC como:

Frecuencia CTC / (2 ^ valor)

por ejemplo, valor 3 significa una octava parte de la frecuencia CTC

Donde CTC es el reloj de cristal de hardware, cuya frecuencia se puede relacionar con TSC mediante los valores proporcionados en cpuid leaf 0x15.

Si se introduce un valor no válido, el mensaje de error proporcionará una lista de valores válidos, por ejemplo:

$ perf record -e intel_pt/mtc_period=15/u uname
Invalid mtc_period for intel_pt. Valid values are: 0,3,6,9

El valor predeterminado es 3 o el valor inferior más cercano que sea compatible (0 siempre es compatible).

cyc

Produce paquetes de temporización CYC.

Los paquetes CYC proporcionan información de temporización de grano aún más fino que los paquetes MTC y TSC. Un paquete CYC contiene el número de ciclos de CPU desde el último paquete CYC. A diferencia de los paquetes MTC y TSC, los paquetes CYC solo se envían cuando también se envía otro paquete.

La compatibilidad con esta característica se indica mediante:

/sys/bus/event_source/devices/intel_pt/caps/psb_cyc

que contiene "1" si la característica es compatible y "0" en caso contrario.

El número de paquetes CYC producidos se puede reducir especificando un umbral; consulte cyc_thresh más adelante.

config terms for Intel PT

The following config terms can be used with the intel_pt event:

cyc
Enable CYC packets. These packets mark the passage of time, measured in CPU cycles, and are used to determine the time elapsed between trace entries. This feature is useful for calculating CPU frequency or for profiling at a specific frequency. Support for this feature is indicated by:
/sys/bus/event_source/devices/intel_pt/caps/cyc_count

which contains "1" if CYC packets are supported.

Valid cyc_thresh values are given by:

/sys/bus/event_source/devices/intel_pt/caps/cycle_thresholds

which contains a hexadecimal value, the bits of which represent valid values e.g. bit 2 set means value 2 is valid.

The cyc_thresh value represents the minimum number of CPU cycles that must have passed before a CYC packet can be sent. The number of CPU cycles is:

2 ^ (value - 1)

e.g. value 4 means 8 CPU cycles must pass before a CYC packet can be sent. Note a CYC packet is still only sent when another packet is sent, not at, e.g. every 8 CPU cycles.

If an invalid value is entered, the error message will give a list of valid values e.g.

$ perf record -e intel_pt/cyc,cyc_thresh=15/u uname
Invalid cyc_thresh for intel_pt. Valid values are: 0-12

CYC packets are not requested by default.

pt
Specifies pass-through which enables the branch config term.

The default config selects pt if it is available, so a user will never need to specify this term.

branch
Enable branch tracing. Branch tracing is enabled by default so to disable branch tracing use branch=0.

The default config selects branch if it is available.

ptw
Enable PTWRITE packets which are produced when a ptwrite instruction is executed.

Support for this feature is indicated by:

/sys/bus/event_source/devices/intel_pt/caps/ptwrite

which contains "1" if the feature is supported and "0" otherwise.

As an alternative, refer to "Emulated PTWRITE" further below.

fup_on_ptw
Enable a FUP packet to follow the PTWRITE packet. The FUP packet provides the address of the ptwrite instruction. In the absence of fup_on_ptw, the decoder will use the address of the previous branch if branch tracing is enabled, otherwise the address will be zero. Note that fup_on_ptw will work even when branch tracing is disabled.
pwr_evt
Enable power events. The power events provide information about changes to the CPU C-state.

Support for this feature is indicated by:

/sys/bus/event_source/devices/intel_pt/caps/power_event_trace

which contains "1" if the feature is supported and "0" otherwise.

event
Enable Event Trace. The events provide information about asynchronous events.

Support for this feature is indicated by:

/sys/bus/event_source/devices/intel_pt/caps/event_trace

which contains "1" if the feature is supported and "0" otherwise.

notnt
Disable TNT packets. Without TNT packets, it is not possible to walk executable code to reconstruct control flow, however FUP, TIP, TIP.PGE and TIP.PGD packets still indicate asynchronous control flow, and (if return compression is disabled - see noretcomp) return statements. The advantage of eliminating TNT packets is reducing the size of the trace and corresponding tracing overhead.

Support for this feature is indicated by:

/sys/bus/event_source/devices/intel_pt/caps/tnt_disable

which contains "1" if the feature is supported and "0" otherwise.

AUX area sampling option

To select Intel PT "sampling" the AUX area sampling option can be used:

--aux-sample

Optionally it can be followed by the sample size in bytes e.g.

--aux-sample=8192

In addition, the Intel PT event to sample must be defined e.g.

-e intel_pt//u

Samples on other events will be created containing Intel PT data e.g. the following will create Intel PT samples on the branch-misses event, note the events must be grouped using {}:

perf record --aux-sample -e '{intel_pt//u,branch-misses:u}'

An alternative to --aux-sample is to add the config term aux-sample-size to events. In this case, the grouping is implied e.g.

perf record -e intel_pt//u -e branch-misses/aux-sample-size=8192/u

is the same as:

perf record -e '{intel_pt//u,branch-misses/aux-sample-size=8192/u}'

but allows for also using an address filter e.g.:

perf record -e intel_pt//u --filter 'filter * @/bin/ls' -e branch-misses/aux-sample-size=8192/u -- ls

It is important to select a sample size that is big enough to contain at least one PSB packet. If not a warning will be displayed:

Intel PT sample size (%zu) may be too small for PSB period (%zu)

The calculation used for that is: if sample_size ⟨ psb_period + 256 display the warning. When sampling is used, psb_period defaults to 0 (2KiB).

The default sample size is 4KiB.

The sample size is passed in aux_sample_size in struct perf_event_attr. The sample size is limited by the maximum event size which is 64KiB. It is difficult to know how big the event might be without the trace sample attached, but the tool validates that the sample size is not greater than 60KiB.

new snapshot option

The difference between full trace and snapshot from the kernel’s perspective is that in full trace we don’t overwrite trace data that the user hasn’t collected yet (and indicated that by advancing aux_tail), whereas in snapshot mode we let the trace run and overwrite older data in the buffer so that whenever something interesting happens, we can stop it and grab a snapshot of what was going on around that interesting moment.

To select snapshot mode a new option has been added:

-S

Optionally it can be followed by the snapshot size e.g.

-S0x100000

The default snapshot size is the auxtrace mmap size. If neither auxtrace mmap size nor snapshot size is specified, then the default is 4MiB for privileged users (or if /proc/sys/kernel/perf_event_paranoid < 0), 128KiB for unprivileged users. If an unprivileged user does not specify mmap pages, the mmap pages will be reduced as described in the new auxtrace mmap size option section below.

The snapshot size is displayed if the option -vv is used e.g.

Intel PT snapshot size: %zu

new auxtrace mmap size option

Intel PT buffer size is specified by an addition to the -m option e.g.

-m,16

selects a buffer size of 16 pages i.e. 64KiB.

Note that the existing functionality of -m is unchanged. The auxtrace mmap size is specified by the optional addition of a comma and the value.

The default auxtrace mmap size for Intel PT is 4MiB/page_size for privileged users (or if /proc/sys/kernel/perf_event_paranoid < 0), 128KiB for unprivileged users. If an unprivileged user does not specify mmap pages, the mmap pages will be reduced from the default 512KiB/page_size to 256KiB/page_size, otherwise the user is likely to get an error as they exceed their mlock limit (Max locked memory as shown in /proc/self/limits). Note that perf does not count the first 512KiB (actually /proc/sys/kernel/perf_event_mlock_kb minus 1 page) per cpu against the mlock limit so an unprivileged user is allowed 512KiB per cpu plus their mlock limit (which defaults to 64KiB but is not multiplied by the number of cpus).

In full-trace mode, powers of two are allowed for buffer size, with a minimum size of 2 pages. In snapshot mode or sampling mode, it is the same but the minimum size is 1 page.

The mmap size and auxtrace mmap size are displayed if the -vv option is used e.g.

mmap length 528384
auxtrace mmap length 4198400

Intel PT modes of operation

Intel PT can be used in 3 modes: full-trace mode sample mode snapshot mode

Full-trace mode traces continuously e.g.

perf record -e intel_pt//u uname

Sample mode attaches a Intel PT sample to other events e.g.

perf record --aux-sample -e intel_pt//u -e branch-misses:u

Snapshot mode captures the available data when a signal is sent or "snapshot" control command is issued. e.g. using a signal

perf record -v -e intel_pt//u -S ./loopy 1000000000 &
[1] 11435
kill -USR2 11435
Recording AUX area tracing snapshot

ITRACE OPTIONS

La opción -d hará que se cree un archivo intel_pt.log que contenga todos los paquetes e instrucciones decodificados. Tenga en cuenta que esta opción ralentiza el decodificador y que el archivo resultante puede ser muy grande. La opción -d puede ir seguida de indicadores que afectan a los mensajes de depuración que se registrarán o no. Cada indicador debe ir precedido de + o -. Los indicadores compatibles con Intel PT son:

-a      Suprimir el registro de eventos perf
+a      Registrar todos los eventos perf
+e      Salida solo en caso de errores de decodificación (tamaño configurable)
+o      Salida a stdout en lugar de "intel_pt.log"

Por defecto, los eventos perf registrados se filtran por cualquier intervalo de tiempo especificado, pero el indicador +a anula esto. El indicador +e puede ser útil para analizar errores. Por defecto, el tamaño del registro en ese caso es de 16384 bytes, pero puede modificarse mediante perf-config(1), por ejemplo, perf config itrace.debug-log-buffer-size=30000

Además, se puede especificar el período del evento "instructions". Por ejemplo,

--itrace=i10us

establece el período en 10 us, es decir, se sintetiza una muestra de instrucción por cada 10 microsegundos de traza. Las alternativas a "us" son "ms" (milisegundos), "ns" (nanosegundos), "t" (ticks de TSC) o "i" (instrucciones).

"ms", "us" y "ns" se convierten a ticks de TSC.

La información de tiempo incluida con Intel PT no proporciona el tiempo de cada instrucción. En consecuencia, para fines de muestreo, el decodificador estima el tiempo transcurrido desde el último paquete de tiempo basándose en 1 tick por instrucción. El tiempo en la muestra **no** se ajusta y refleja el último valor conocido de TSC.

Para Intel PT, el período predeterminado es 100 us.

Establecerlo en un período cero significa "tan a menudo como sea posible".

En el caso de Intel PT, eso es lo mismo que un período de 1 y una unidad de *instrucciones* (es decir, --itrace=i1i).

También se puede especificar el tamaño de la cadena de llamadas (predeterminado 16, máximo 1024) para los eventos de instrucciones o transacciones. Por ejemplo,

--itrace=ig32
--itrace=xg32

También se puede especificar el número de entradas de rama más recientes (predeterminado 64, máximo 1024) para los eventos de instrucciones o transacciones. Por ejemplo,

--itrace=il10
--itrace=xl10

Tenga en cuenta que las entradas de rama más recientes se borran para cada muestra, por lo que no hay superposición de una muestra a la siguiente.

Las opciones G y L están diseñadas en particular para el modo de muestreo y funcionan de manera similar a g y l, pero añaden la cadena de llamadas y la pila de ramas a los otros eventos seleccionados en lugar de eventos sintetizados. Por ejemplo, para registrar eventos de errores de rama para ls y luego añadir una cadena de llamadas derivada de la traza de Intel PT:

perf record --aux-sample -e '{intel_pt//u,branch-misses:u}' -- ls
perf report --itrace=Ge

Aunque, de hecho, G es el valor predeterminado para perf report, por lo que es lo mismo que simplemente:

perf report

Una advertencia con las opciones G y L es que funcionan mal con "Large PEBS". Large PEBS significa que los registros PEBS serán acumulados por el hardware y escritos en el búfer de eventos de una sola vez. Esto reduce las interrupciones, pero puede dar marcas de tiempo muy tardías. Dado que la traza de Intel PT se sincroniza mediante marcas de tiempo, los eventos PEBS no coinciden con la traza. Actualmente, Large PEBS solo se utiliza en ciertas circunstancias: - el hardware lo soporta - se utiliza PEBS - se especifica el período del evento, en lugar de la frecuencia - el tipo de muestra se limita a los siguientes indicadores: PERF_SAMPLE_IP | PERF_SAMPLE_TID | PERF_SAMPLE_ADDR | PERF_SAMPLE_ID | PERF_SAMPLE_CPU | PERF_SAMPLE_STREAM_ID | PERF_SAMPLE_DATA_SRC | PERF_SAMPLE_IDENTIFIER | PERF_SAMPLE_TRANSACTION | PERF_SAMPLE_PHYS_ADDR | PERF_SAMPLE_REGS_INTR | PERF_SAMPLE_REGS_USER | PERF_SAMPLE_PERIOD (y a veces) | PERF_SAMPLE_TIME Dado que el modo de muestreo de Intel PT utiliza un tipo de muestra diferente al de la lista anterior, Large PEBS no se utiliza con el modo de muestreo de Intel PT. Para evitar Large PEBS en otros casos, evite especificar el período del evento, es decir, evite la opción -c de perf record, la opción --count, o el término de configuración period.

Para deshabilitar completamente la decodificación de trazas, use la opción --no-itrace.

También es posible omitir eventos generados (instrucciones, ramas, transacciones) al principio. Esto es útil para ignorar el código de inicialización.

--itrace=i0nss1000000

omite el primer millón de instrucciones.

La opción q cambia la forma en que se decodifica la traza. La decodificación es mucho más rápida pero mucho menos detallada. Específicamente, con la opción q, el decodificador no decodifica paquetes TNT y no recorre el código objeto, sino que obtiene la IP de los paquetes FUP y TIP. La opción q se puede usar con las opciones b e i pero el período no se usa. La opción q decodifica más rápidamente, pero solo es útil si el flujo de control de interés está representado o indicado por paquetes FUP, TIP, TIP.PGE o TIP.PGD (consulte más abajo). Sin embargo, la opción q podría usarse para encontrar rangos de tiempo que luego podrían decodificarse completamente usando la opción --time.

Lo que **no** se decodificará con la opción q (simple):

•llamadas y saltos directos
•ramas condicionales
•instrucciones no de rama

Lo que **se** decodificará con la opción q (simple):

•ramas asíncronas como interrupciones
•ramas indirectas
•dirección de destino del retorno de función **si** se utilizó el término de configuración noretcomp (consulte la sección de términos de configuración)
•inicio del rastreo (de flujo de control)
•fin del rastreo (de flujo de control), si no está fuera de contexto
•eventos de energía, ptwrite, inicio y aborto de transacciones
•puntero de instrucción asociado con paquetes PSB

Tenga en cuenta que la opción q no especifica qué eventos se sintetizarán, por ejemplo, la opción p también debe usarse para mostrar eventos de energía.

Repetir la opción q (doble q, es decir, qq) resulta en una decodificación aún más rápida y aún menos detalle. El decodificador solo decodifica paquetes PSB extendidos (PSB+), obteniendo el puntero de instrucción si hay un paquete FUP dentro de PSB+ (es decir, entre PSB y PSBEND). Tenga en cuenta que los paquetes PSB ocurren regularmente en la traza según el término de configuración psb_period (consulte la sección de términos de configuración). Habrá un paquete FUP si el PSB+ ocurre mientras se está rastreando el flujo de control.

Lo que **no** se decodificará con la opción qq:

•todo excepto el puntero de instrucción asociado con los paquetes PSB

Lo que **se** decodificará con la opción qq:

•puntero de instrucción asociado con los paquetes PSB

La opción Z es equivalente a haber registrado una traza sin TSC (es decir, término de configuración tsc=0). Puede ser útil para evitar problemas de marcas de tiempo al decodificar una traza de una máquina virtual.

First, use perf kvm to list the virtual machines.

In the example output above, the main virtual machine PID is 64055. Each virtual CPU is shown as a separate thread, with the PIDs 17006, 17007, and 17008. These PIDs need to be specified when tracing the virtual machine.

Start an open-ended perf record, tracing the VM process, do something on the VM, and then ctrl-C to stop. IPC can be determined, hence cyc=1 can be added. Only kernel decoding is supported, so k must be specified. Intel PT traces both the host and the guest so --guest and --host need to be specified.

$ sudo perf kvm --guest --host --guestkallsyms $KALLSYMS record --kcore -e intel_pt/cyc=1/k -p 16998
^C[ perf record: Woken up 1 times to write data ]
[ perf record: Captured and wrote 9.041 MB perf.data.kvm ]

Now perf inject can be used to determine the VMX TCS Offset. Note, Intel PT TSC packets are only 7-bytes, so the TSC Offset might differ from the actual value in the 8th byte. That will have no effect i.e. the resulting timestamps will be correct anyway.

$ perf inject -i perf.data.kvm --vm-time-correlation=dry-run
ERROR: Unknown TSC Offset for VMCS 0x1bff6a
VMCS: 0x1bff6a  TSC Offset 0xffffe42722c64c41
ERROR: Unknown TSC Offset for VMCS 0x1cbc08
VMCS: 0x1cbc08  TSC Offset 0xffffe42722c64c41
ERROR: Unknown TSC Offset for VMCS 0x1c3ce8
VMCS: 0x1c3ce8  TSC Offset 0xffffe42722c64c41
ERROR: Unknown TSC Offset for VMCS 0x1cbce9
VMCS: 0x1cbce9  TSC Offset 0xffffe42722c64c41

Each virtual CPU has a different Virtual Machine Control Structure (VMCS) shown above with the calculated TSC Offset. For an unchanging TSC Offset they should all be the same for the same virtual machine.

Now that the TSC Offset is known, it can be provided to perf inject

$ perf inject -i perf.data.kvm --vm-time-correlation="dry-run 0xffffe42722c64c41"

Note the options for perf inject --vm-time-correlation are:

[ dry-run ] [ <TSC Offset> [ : <VMCS> [ , <VMCS> ]... ]  ]...

So it is possible to specify different TSC Offsets for different VMCS. The option "dry-run" will cause the file to be processed but without updating it. Note it is also possible to get a intel_pt.log file by adding option --itrace=d

There were no errors so, do it for real

$ perf inject -i perf.data.kvm --vm-time-correlation=0xffffe42722c64c41 --force

perf script can be used to see if there are any decoder errors

$ perf script -i perf.data.kvm --guestkallsyms $KALLSYMS --itrace=e-o

There were none.

TRACING VIRTUAL MACHINES (INCLUDING USER SPACE)

It is possible to use perf record to record sideband events within a virtual machine, so that an Intel PT trace on the host can be decoded. Sideband events from the guest perf.data file can be injected into the host perf.data file using perf inject.

Here is an example of the steps needed:

On the guest machine:

Check that no-kvmclock kernel command line option was used to boot:

Note, this is essential to enable time correlation between host and guest machines.

$ cat /proc/cmdline
BOOT_IMAGE=/boot/vmlinuz-5.10.0-16-amd64 root=UUID=cb49c910-e573-47e0-bce7-79e293df8e1d ro no-kvmclock

$ echo 0 | sudo tee /proc/sys/net/core/bpf_jit_enable

Start perf record to collect Intel PT trace:

TRAZADO DE EVENTOS

El Trazado de Eventos registra información sobre eventos asíncronos, por ejemplo, interrupciones, fallos, salidas y entradas de VM. La información se registra en paquetes CFE y EVD, y también la Bandera de Interrupción se registra en el paquete MODE.Exec. El paquete CFE contiene un campo de tipo para identificar uno de los siguientes:

 1      INTR            interrupción, fallo, excepción, NMI
 2      IRET            retorno de interrupción
 3      SMI             interrupción de gestión del sistema
 4      RSM             reanudación desde el modo de gestión del sistema
 5      SIPI            interrupción interprocesador de inicio
 6      INIT            señal INIT
 7      VMENTRY         Entrada a VM
 8      VMEXIT          Salida de VM
 9      VMEXIT_INTR     Salida de VM debido a interrupción
10      SHUTDOWN        Apagado

Para más detalles, consulte los Manuales del Desarrollador de Software de Arquitecturas Intel 64 y IA-32 (versión 076 o posterior).

La capacidad de realizar Trazado de Eventos se indica mediante el archivo /sys/bus/event_source/devices/intel_pt/caps/event_trace.

El trazado de eventos se selecciona para su registro utilizando el término de configuración "event". Por ejemplo:

perf record -e intel_pt/event/u uname

Los eventos de trazado de eventos se muestran utilizando la opción --itrace I. Por ejemplo:

perf script --itrace=Ie

perf script muestra eventos que contienen el tipo CFE, vector y datos del evento, en el formato:

evt:   hw int            (t)  cfe: INTR IP: 1 vector: 3 PFA: 0x8877665544332211

La bandera IP indica si el evento se vincula a un IP, lo que incluye cualquier caso en el que se habilite la generación de paquetes de control de flujo, así como cuando se establece el bit IP del paquete CFE.

perf script muestra eventos que contienen cambios en la Bandera de Interrupción en el formato:

iflag:   t                      IFLAG: 1>0 via branch

donde "via branch" indica una rama (interrupción o retorno de interrupción) y "non branch" indica una instrucción como CFI, STI o POPF).

Además, el estado actual de la bandera de interrupción se indica por la presencia o ausencia de la bandera "D" (interrupt disabled) de perf script. Si la bandera de interrupción cambia, entonces la bandera "t" también se incluye, es decir:

        no flag, interrupts enabled IF=1
t       interrupts become disabled IF=1 -> IF=0
D       interrupts are disabled IF=0
Dt      interrupts become enabled  IF=0 -> IF=1

El script intel-pt-events.py ilustra cómo acceder a la información de Event Trace utilizando un script de Python.

DESACTIVAR TNT

Los paquetes TNT se deshabilitan usando el término de configuración "notnt". Por ejemplo:

perf record -e intel_pt/notnt/u uname

En ese caso, la opción --itrace q se fuerza porque no es posible recorrer el código ejecutable para reconstruir el flujo de control.

perf_emulate_ptwrite, PERF_EMULATE_PTWRITE_8_BITS, PERF_EMULATE_PTWRITE_UD2, PERF_EMULATE_PTWRITE_MAGIC - Emulate Intel Processor Trace PTWRITE instruction

SYNOPSIS

#define PERF_EMULATE_PTWRITE_8_BITS \
        "        shl %rax\n"     \
        "        jc 1f\n"        \
        "1:      shl %rax\n"     \
        "        jc 1f\n"        \
        "1:      shl %rax\n"     \
        "        jc 1f\n"        \
        "1:      shl %rax\n"     \
        "        jc 1f\n"
/* Undefined instruction */
#define PERF_EMULATE_PTWRITE_UD2        ".byte 0x0f, 0x0b\n"
#define PERF_EMULATE_PTWRITE_MAGIC        PERF_EMULATE_PTWRITE_UD2 ".ascii \"perf,ptwrite  \"\n"

void perf_emulate_ptwrite(uint64_t x __attribute__ ((__unused__)))

DESCRIPTION

The PTWRITE instruction is an Intel Processor Trace instruction that is used to write data into the trace stream. The instruction is not available on all processors. This function emulates the instruction using inline assembly. The instruction is emulated by using the UD2 (Undefined Instruction) opcode, followed by an ASCII string "perf,ptwrite". The actual data is passed in the RDI register and is emulated by shifting the value in RDI 8 times and writing it to RAX. The instruction is followed by a return instruction.

The value of x is passed in RDI, as per the SysV ABI.

The function is declared as __attribute__ ((__unused__)) to suppress compiler warnings about unused parameters, as the value is passed through inline assembly.

The definition of the macros are as follows:

PERF_EMULATE_PTWRITE_8_BITS:
        This macro expands to a sequence of 8 left shift instructions (shl)
        and conditional jump instructions (jc). Each shl instruction shifts
        the value in the %rax register one bit to the left. The jc instruction
        jumps to the next instruction if the carry flag is set, which indicates
        that a set bit was shifted out of the most significant bit position.
        This sequence effectively processes 8 bits of the input value at a time.

PERF_EMULATE_PTWRITE_UD2:
        This macro defines the byte sequence for the UD2 instruction, which
        is an undefined instruction. The byte sequence is 0x0f, 0x0b.

PERF_EMULATE_PTWRITE_MAGIC:
        This macro combines the UD2 instruction with an ASCII string literal
        "perf,ptwrite ". This serves as a marker or signature in the trace
        data, indicating that a PTWRITE emulation has occurred.

The perf_emulate_ptwrite function itself combines these pieces:

  1. A jump instruction to label 1f. This is to skip over the magic signature if the emulation is not intended to be triggered by the jump itself.

  2. The PERF_EMULATE_PTWRITE_MAGIC, which places the UD2 instruction and the signature string into the code stream.

  3. A label 1:.

  4. An instruction to move the input value from RDI (where it's passed according to the SysV ABI) to RAX.

  5. Eight instances of the PERF_EMULATE_PTWRITE_8_BITS macro. Each instance effectively processes 8 bits of the input value by repeatedly shifting RAX. This part of the emulation seems to be a simplified way to consume the input value within the emulated code, possibly to ensure it's processed or to align with how PTWRITE might interact with registers.

  6. A label 1: (reused).

  7. A ret instruction to return from the function.

When Intel PT tracing is enabled, the execution of the UD2 instruction within the PERF_EMULATE_PTWRITE_MAGIC macro will trigger an event that the tracing mechanism can capture. The subsequent assembly code modifies the %rax register based on the input argument, potentially serving as the payload for the trace event.

For example, a test program with the function above:

#include <stdio.h>
#include <stdint.h>
#include <stdlib.h>
#include "perf_emulate_ptwrite.h"
int main(int argc, char *argv[])
{
        uint64_t x = 0;

        if (argc > 1)
                x = strtoull(argv[1], NULL, 0);
        perf_emulate_ptwrite(x);
        return 0;
}

PIPE MODE

Pipe mode is a problem for Intel PT and possibly other auxtrace users. It’s not recommended to use a pipe as data output with Intel PT because of the following reason.

Essentially the auxtrace buffers do not behave like the regular perf event buffers. That is because the head and tail are updated by software, but in the auxtrace case the data is written by hardware. So the head and tail do not get updated as data is written.

In the Intel PT case, the head and tail are updated only when the trace is disabled by software, for example: - full-trace, system wide : when buffer passes watermark - full-trace, not system-wide : when buffer passes watermark or context switches - snapshot mode : as above but also when a snapshot is made - sample mode : as above but also when a sample is made

That means finished-round ordering doesn’t work. An auxtrace buffer can turn up that has data that extends back in time, possibly to the very beginning of tracing.

For a perf.data file, that problem is solved by going through the trace and queuing up the auxtrace buffers in advance.

For pipe mode, the order of events and timestamps can presumably be messed up.

PAUSE OR RESUME TRACING

With newer Kernels, it is possible to use other selected events to pause or resume Intel PT tracing. This is configured by using the "aux-action" config term:

"aux-action=pause" is used with events that are to pause Intel PT tracing.

"aux-action=resume" is used with events that are to resume Intel PT tracing.

"aux-action=start-paused" is used with the Intel PT event to start in a paused state.
